# [observability] Preserve tracing through the multi-tokenizer router

[Upstream PR](https://github.com/sgl-project/sglang/pull/45306) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-trace --tokenizer-worker-num 2` (or more), tokenizer spans are exported but downstream scheduler/prefill/decode spans disappear. `MultiTokenizerRouter` unpickles requests without initializing native tracing in its process. `TraceReqContext.__setstate__` consequently sets `tracing_enable=False`, and the router forwards that disabled context to the scheduler even when tracing is enabled there.

## Modifications

- Initialize native tracing before the router starts its receiving thread, honoring the configured OTLP endpoint and trace-module filter.
- Reuse tracing when the parent process has already initialized it.
- Add CPU regression cases for worker → router → scheduler context serialization and prefill/decode span export, tracing disabled, and tracing already initialized.

## Accuracy Tests

- The serialization/span regression fails against the unmodified upstream router and passes with this change.
- All 3 new cases pass in a focused local CPU harness using the real router class, native trace implementation, pickle serialization, and OpenTelemetry in-memory exporter. The harness bypasses heavyweight model/GPU module imports and mocks router I/O/thread startup.
- Ruff formatting and `F401,F821,UP037` checks pass; import ordering was checked with `sglang` configured as first party.
- Full SGLang module-import and GPU serving integration tests have not been run locally. The added registered CPU test can be run in the SGLang CI environment with `python -m unittest discover -s test/registered/unit/managers -p test_multi_tokenizer_tracing.py`.

Model outputs are unchanged; this change only initializes observability in the intermediary router process.

## Speed Tests and Profiling

No inference benchmark was run. Initialization happens once at router startup; no per-request hook is added.
