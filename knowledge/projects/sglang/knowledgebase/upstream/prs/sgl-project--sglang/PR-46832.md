# [Perf] [AMD] qwen3: Use the fused QK-norm + RoPE + KV write in decode with an fp8 KV cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/46832) · state: closed · merged: True

## Original PR description

## Motivation

#44267 fused dense Qwen3's decode QK-norm, RoPE and KV-cache write into one aiter kernel on ROCm, but only for a KV cache in the activation dtype. With `--kv-cache-dtype fp8_e4m3` every decode layer still runs two `add_rmsnorm_quant` launches, two contiguous copies of the strided q/k views, `rotary_embedding` and the Triton `reshape_and_cache_flash` fp8 write. The aiter kernels that path calls already quantize the cache write with a per-tensor scale.

## Modifications

- `Qwen3Attention.forward` also takes the fused decode path when the NHD cache is `aiter.dtypes.fp8`, the only fp8 dtype aiter's binding accepts (e4m3fn on gfx950, e4m3fnuz on gfx942).
- The kernel gets the layer's own k/v scales: `k_scale_float` / `v_scale_float` from `BaseKVCacheMethod`, a plain float from `load_kv_cache_scales`, or 1.0 when the layer has none. They are cached as CPU tensors on first use, because the kernel reads them on the host and a device tensor would sync inside graph capture; a scale without a host copy raises.
- The mRoPE (Qwen3-VL) kernel shares the gate and gets the same support; it is covered by the unit test, not benchmarked. bf16 caches are unchanged.
- Reached by dense Qwen3 and the models that use its decoder as their language model (Qwen3-VL dense, the Qwen3 variants of InternVL and Intern-S1, MiniCPM-V 4.5, LightOnOCR, Step3-VL-10B, Qwen3-ASR). Qwen3-MoE and Qwen3.5 have their own attention and are not affected.
- `test_qwen3_aiter_fused_qk_norm_rope.py` adds fp8-cache cases for both kernels with k/v scales (1, 1), (0.5, 2) and (2, 0.5), checking q, the dequantized K, V against `(v / scale).to(fp8)`, and that no other slot is written. Passing inverted, swapped or unit scales to the kernel fails every case whose scales are not 1.

## Accuracy Tests

MI355X (gfx950), torch 2.11.0+rocm10.0.0, sglang-kernel 0.4.10, aiter `285579b62`, `SGLANG_USE_AITER=1` (attention backend resolves to `aiter`, decode CUDA graphs on). Every server runs `--kv-cache-dtype fp8_e4m3` with otherwise default args. Baseline is main `132b0f0ae7`.

**Unit test.** `test/registered/amd/test_qwen3_aiter_fused_qk_norm_rope.py`: 6 passed, 64 subtests passed.

#### 1. 🟠 Should fix: Fused fp8 KV scale prefers stale `scale_float` over plain float
`python/sglang/srt/models/qwen3.py:151`

`_host_kv_scale` returns `scale_float` before checking the plain-float `scale`, so after `load_kv_cache_scales` rebinds `k_scale`/`v_scale` to new plain floats while leaving `k_scale_float`/`v_scale_float` at checkpoint values, the fused write quantizes with the stale float. The aiter backend's descale and unfused write use the new `layer.k_scale`, silently mis-scaling decode-written KV against prefill and reads. Prefer the live plain-float `scale` or verify the pair is consistent.

**Who is affected:** Qwen3 on ROCm with `SGLANG_USE_AITER=1`, a quant config that attaches a `BaseKVCacheMethod` (fp8/modelopt/compressed-tensors/quark), `--kv-cache-dtype fp8_e4m3` and `--quantization-param-path`, during decode on the new fused fp8 path.

_Verified by running it._

#### 2. 🔵 Nit: Cached fused KV scales never invalidated on scale/weight reload
`python/sglang/srt/models/qwen3.py:276`

`_aiter_fused_kv_scales` caches the host KV scales on the first fused forward and never rebuilds them. `load_kv_cache_scales` is not affected: it runs in `load_model`, before any forward. `update_weights_from_disk` is affected: it reloads into the live model and re-runs `BaseKVCacheMethod.process_weights_after_loading`, which reassigns `k_scale_float`/`v_scale_float`. If the reloaded checkpoint has different KV scales, fused decode keeps quantizing K/V with the old scales while the unfused prefill write and the attention descale use the new ones. Consider resetting `_fused_kv_scales` when the scales are reprocessed, or documenting the limitation.

**Who is affected:** Qwen3 on ROCm with `SGLANG_USE_AITER=1` and an fp8 KV cache, after an online `update_weights_from_disk` whose checkpoint changes the KV scales (eager mode, or with `recapture_cuda_graph`).

_Verified by running it._

#### 3. 🔵 Nit: Tests cover kernel wrapper only, not forward gate or scale wiring
`test/registered/amd/test_qwen3_aiter_fused_qk_norm_rope.py:32`

The new tests exercise `aiter_fused_qk_norm_rope_set_kv` on hand-built fp8 buffers with scales they construct, and `_host_kv_scale` on its own. Nothing covers the `forward()` dtype gate (`k_cache.dtype in (hidden_states.dtype, aiter_dtypes.fp8)`) or how `_aiter_fused_kv_scales` reads and caches `attn.k_scale`/`k_scale_float`. So a regression in that wiring (swapped k/v, wrong source, fp8 dropped from the gate) would not fail any test. `test_rope_nhd_fp8_cache`/`test_mrope_nhd_fp8_cache` nearly duplicate the bf16 tests and could be folded into them as a dtype/scales subTest loop. A small test through `Qwen3Attention` with preset RadixAttention scales would close the gap.

**Who is affected:** Maintainers relying on CI to catch regressions in the fp8 KV-scale wiring of the Qwen3 aiter fused decode path (ROCm, SGLANG_USE_AITER=1, fp8 KV cache).

_Verified by running it._

#### 4. 🔵 Nit: `_host_kv_scale` duplicates existing `_resolve_fused_scale` helper
`python/sglang/srt/models/qwen3.py:146`

`_host_kv_scale` reimplements `_resolve_fused_scale` in memory_pool.py, which already resolves the same per-tensor KV scales (plain float, CPU 0-d tensor, device scalar paired with `*_scale_float`) for the pool's fp8 fused write. A thin wrapper mapping missing scale to 1.0 and raising the capture `ValueError` could reuse the existing helper instead of a parallel implementation. Consolidate to one resolver.

**Who is affected:** Maintainers of the KV-scale resolution logic; no runtime behaviour differs for scales set by `BaseKVCacheMethod` or `load_kv_cache_scales`.
