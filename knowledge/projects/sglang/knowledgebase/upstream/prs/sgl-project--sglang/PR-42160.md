# [Fix] Use int64 token offsets in the fused QK RMSNorm + RoPE + gate kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/42160) · state: closed · merged: False

## Original PR description

## Motivation

`_fused_qk_rmsnorm_rope_gate_kernel` computes each row's address as `token * stride`, with `token = tl.program_id(0)`, which is int32 ([fused_qk_rmsnorm_rope_gate.py#L64](https://github.com/sgl-project/sglang/blob/5423a4d88526416b45395d69164bfcd23835e507/python/sglang/kernels/ops/attention/fused_qk_rmsnorm_rope_gate.py#L64)). Only the cos/sin offset is widened to int64 ([#L117](https://github.com/sgl-project/sglang/blob/5423a4d88526416b45395d69164bfcd23835e507/python/sglang/kernels/ops/attention/fused_qk_rmsnorm_rope_gate.py#L117)). So when a call has T tokens and T x row stride passes 2^31 elements, the q/k/gate loads go out of bounds.

For Qwen/Qwen3.5-4B at TP 1 that happens at about 209,716 tokens in a single forward pass. In practice that takes a prefill batch of that many tokens: chunked prefill disabled, or a chunk size of that order. The default chunk sizes stay far below it. Qwen3.5's native context length is 262,144, so a one-shot prefill of a full-length prompt is enough.

Calling the kernel directly on main (5423a4d885) with Qwen3.5-4B's shapes, 200,000 tokens give correct output and 262,144 tokens fail with `CUDA error: an illegal memory access was encountered`.

<details>
<summary>Where the limit comes from, and the reproduction</summary>

- Qwen3.5 calls the kernel on column views of the fused `qkv_proj` output ([qwen3_5.py#L1371-L1380](https://github.com/sgl-project/sglang/blob/5423a4d88526416b45395d69164bfcd23835e507/python/sglang/srt/models/qwen3_5.py#L1371-L1380)), so the row stride is the full qkv width per rank. For Qwen/Qwen3.5-4B at TP 1 that width is 10,240 elements. Wider rows reach the limit sooner, and narrower ones (higher TP) later.
- The outputs are new contiguous tensors with narrower rows, so the stores stay in bounds until about 524,288 tokens for Qwen3.5-4B at TP 1.
- Reproduction on main (5423a4d885), on one GH200, with Qwen3.5-4B's shapes (16 q heads with gate, 4 kv heads, head_dim 256, rotary_dim 64), calling the kernel directly:

  | Tokens | Largest element offset | Result |
  |---|---|---|
  | 200,000 | 2,047,997,951 | correct (last token matches a PyTorch reference) |
  | 262,144 | 2,684,352,511 | `CUDA error: an illegal memory access was encountered` |

</details>

## Modifications

`token` becomes `tl.program_id(0).to(tl.int64)`, so every per-token offset is computed in int64. Nothing else changes.

`test_row_offsets_past_int32` in `test_fused_qk_rmsnorm_rope_gate.py` runs the kernel on 1,025 rows at a stride of 2^21 + 64 elements, so the last row starts past element 2^31. It checks the first and last rows against the existing reference helpers. It allocates about 4.3 GB of GPU memory, which the file's `1-gpu-large` runner has.

## Accuracy Tests

On one GH200 (torch 2.13.0+cu130, Triton 3.7.1):
- The new test fails on main with the illegal memory access and passes with this change. The whole test file passes (4 tests).
- With this change, the 262,144-token reproduction above runs, and its last token matches the reference exactly (max |diff| 0 for q, k and gate).
- The 200,000-token case gives the same result before and after.

## Speed Tests and Profiling

Not measured. The change only widens the per-token offset arithmetic from int32 to int64.
