# [Fix] linker: Order loads behind the forward that may still use the pages

[Upstream PR](https://github.com/sgl-project/sglang/pull/45580) · state: closed · merged: True

## Original PR description

- Linker loads now wait for the forward in flight, as offloads already do (#45559). Under read-done the scheduler's stream runs ahead of that forward, and the pages a load writes may have been freed while the forward still uses them: a stashed chunk's duplicates, or a finished request's last decode slot. A load released only behind the scheduler's stream could write them under that forward.
- `UnifiedCacheLinker.record_offload_ready` becomes `record_transfer_ready`, shared by loads and offloads. It returns a `TransferReady` that owns the wait: the Mooncake and UMBP transfer threads call `synchronize()` on it, and the MLA dedup broadcast calls `wait(stream)`. Out-of-tree linkers calling the old name, or looping over its old list result, need the change.
- The earlier fence in `stash_chunked_request`, which made the scheduler's stream wait for the forward when a checkpoint freed duplicate KV, is removed; the load-side wait covers that case and every other way such pages get reused, without a scheduler-side wait.

Found by code reading and not reproduced. Behavior changes only when an external linker loads: the load starts after the forward in flight ends, so a batch that hits the linker waits longer in the existing per-layer wait, as it did before prefill read-done.
