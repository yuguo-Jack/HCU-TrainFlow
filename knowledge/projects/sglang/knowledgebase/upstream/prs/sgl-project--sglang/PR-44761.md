# [Perf] [NVIDIA] diffusion/FLUX.3: Run dynamic LoRA through PrimsTS GEMMs

[Upstream PR](https://github.com/sgl-project/sglang/pull/44761) · state: closed · merged: True

## Original PR description

## Motivation

With dynamic LoRA, FLUX.3 disables the FlashInfer PrimsTS GEMMs and falls back to the generic quantized path, which makes LoRA requests much slower than base requests. flashinfer-ai/flashinfer#6585 adds an optional `delta` epilogue input to the PrimsTS GEMMs, so the LoRA contribution can be added inside the fused kernels instead.

This PR depends on flashinfer-ai/flashinfer#6585 for the speedup, but is safe to merge before that is released: the new path is only enabled when the installed FlashInfer exposes `delta` on all PrimsTS GEMM entry points. With current FlashInfer releases the behavior is unchanged.

## Modifications

- `BaseLayerWithLoRA.fused_lora_delta` computes the per-layer LoRA delta `[M, N]` (strength, runtime scale, alpha/rank, output offset, stacked QKV, SwiGLU row interleave) with cached factors.
- `flux3_fused_ops` passes the delta of LoRA-wrapped layers to the PrimsTS linear, SwiGLU and QKV/QK-norm/RoPE GEMMs. The NVFP4 packed SwiGLU handoff is skipped for layers with an active LoRA.
- PrimsTS stays enabled with LoRA, and runtime `set_lora` is accepted, only when the installed FlashInfer supports `delta` (`flux3_prims_ts_supports_lora`). With older FlashInfer, PrimsTS is disabled under `--lora-path` and late LoRA on PrimsTS weights is rejected, as before.
- Unit tests:
  - `test_lora_dynamic_delta_in_gemm.py`: the fused delta matches the LoRA layer forward (scaling, stacked QKV, runtime scale, output offset, SwiGLU order, cache invalidation, inactive layers).
  - `test_flux3_image_dit.py`: deltas reach the PrimsTS epilogues; LoRA skips the packed NVFP4 handoff.
  - `test_flux3_image_served.py`: late LoRA is rejected without `delta` support and accepted with it.

## Accuracy Tests

End-to-end images, PrimsTS + LoRA vs. the generic LoRA path (B200, 1024x1024, 50 steps, same seeds, mean PSNR over 4 images per prompt). "No LoRA" is the noise floor between the two GEMM paths; "LoRA effect" is generic LoRA vs. generic without LoRA, i.e. how much the adapter changes the image.

| Prompt | Variant | PrimsTS vs generic, no LoRA | PrimsTS vs generic, LoRA | LoRA effect |
|---|---|---|---|---|
| Generic prompt | FP8R  | 39.8 dB | 37.0 dB | 13.8 dB |
| Generic prompt | NVFP4 | 32.8 dB | 28.8 dB | 13.7 dB |
| Adapter trigger prompt | FP8R  | 36.4 dB | 31.0 dB | 9.7 dB |
| Adapter trigger prompt | NVFP4 | 30.1 dB | 26.2 dB | 10.0 dB |

With LoRA, the two paths stay within 3-5 dB of their no-LoRA agreement, far above the 10-14 dB change the adapter itself makes.

Single DiT forward (FP8R): the LoRA effect (LoRA output minus base output) of the PrimsTS path matches the generic path with cosine similarity 0.92; swapping the SwiGLU value/gate column order drops it to 0.26.

The kernel-level `delta` epilogue is covered by the FlashInfer tests in flashinfer-ai/flashinfer#6585; the SGLang delta is unit-tested against the LoRA layer forward. With FlashInfer 0.7.1 (no `delta`), PrimsTS is disabled under `--lora-path` as before, and the unit tests pass against both FlashInfer versions.

## Speed Tests and Profiling

B200, FLUX.3 image, 1024x1024, 50 steps, rank-16 LoRA, `bench_offline_throughput`, median latency per image, FlashInfer built from flashinfer-ai/flashinfer#6585:

| Variant | LoRA, generic path | LoRA, PrimsTS + delta | Speedup |
|---|---|---|---|
| FP8R  | 4.20 s | 3.29 s | 1.28x |
| NVFP4 | 3.79 s | 2.72 s | 1.39x |
