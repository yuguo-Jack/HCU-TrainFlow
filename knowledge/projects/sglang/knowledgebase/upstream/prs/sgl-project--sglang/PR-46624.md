# [Feat] openai: support field-specific assistant continuation

[Upstream PR](https://github.com/sgl-project/sglang/pull/46624) · state: open · merged: False

## Original PR description

## Motivation

An interrupted assistant turn can stop inside reasoning or inside the answer. The current boolean continuation path removes the final assistant message and appends its content after rendering, so it cannot express which field should resume or preserve the reasoning/answer boundary.

Refs #46598. This implements the Python OpenAI server's generic Hugging Face renderer slice. Native encoders and the separate Rust model processor/router do not yet support these string selectors.

## Modifications

Accept `continue_final_message="content"` or `"reasoning_content"` in Python Chat and Tokenize, while retaining the existing boolean behavior. Keep the complete final assistant message and let `apply_chat_template` render the selected continuation boundary without a fresh generation header. Empty prefixes are valid. Rendering cache keys distinguish the target, and both text and direct-ID tokenization paths use it. Tokenize disables output separation on its internal Chat request for explicit selectors, so input rendering does not require an output parser; normal Chat generation retains that guard.

For separated output, Qwen3 and DeepSeek-R1 tag detectors start in the selected field, overriding their default state without repeating the supplied prefix. Native encoders, legacy conversation templates, unsupported separated-output parsers, conflicting template options, and raw `input_ids` reject explicit targets before generation. Plain content needs no reasoning parser; `separate_reasoning=false` retains raw output.

- jairuigou · comment · 2026-10-30T10:50:30Z · [source](https://github.com/sgl-project/sglang/pull/46624#issuecomment-6520888973)

@LeslieWylie  Thanks for working on this! We’re really looking forward to this feature—it would be very useful for resuming interrupted responses. We encountered a few related issues while implementing continuation in our internal version. Looking at this PR, the same cases seem worth checking:

1. **Content continuation can re-enter reasoning.**

   With `continue_final_message="content"`, a generated suffix such as `<think>literal</think> tail` should remain in `content`, but `literal` can be classified as reasoning.

   In streaming parsing, detecting `<think>` can set `_in_reasoning=True` again. Non-streaming parsing also infers reasoning from the presence of `<think>`, overriding the initial content state.

2. **Reasoning continuation can strip a literal `<think>`.**

   With `continue_final_message="reasoning_content"`, suppose the existing prefix is `"I mention "` and the generated suffix is `<think> as an example.</think>Answer.`. The literal `<think>` can be removed from the reasoning text.

   The parser only receives the newly generated suffix. Streaming parsing still considers the opening tag unprocessed, while non-streaming parsing unconditionally strips leading `<think>` tags.

3. **A tool tag mentioned inside reasoning can end reasoning prematurely.**

   For Qwen3, consider the generated suffix `<tool_call> is the tag being discussed.</think>Answer.` during reasoning continuation.

   If the tool tag arrives before `</think>`, streaming parsing can treat it as an implicit end of reasoning and move the text into normal output. If both arrive in the same buffer, the parser handles `</think>` first and keeps the tool tag in reasoning.

   Non-streaming parsing similarly preserves it when the complete output contains `</think>`, but can take the tool-interruption path when generation ends before that tag. This comes from the existing fallback for models that start tool calls without explicitly closing reasoning.
