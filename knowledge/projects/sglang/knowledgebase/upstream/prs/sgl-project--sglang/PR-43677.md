# [Fix] GGUF: Qwen3-MoE renormalizes its top-k weights again

[Upstream PR](https://github.com/sgl-project/sglang/pull/43677) · state: open · merged: False

## Original PR description

## Motivation

GGUF Qwen3-MoE models (e.g. Qwen3-30B-A3B) score far worse in SGLang than the same GGUF in llama.cpp. On Qwen3-30B-A3B Q4_K_M, mean NLL is 3.25 against llama.cpp's 0.63.

The cause is in `Qwen3MoeSparseMoeBlock.__init__`, which forces `renormalize=False` whenever the quant config is `GGUFConfig`:

```python
norm_topk_prob = getattr(config, "norm_topk_prob", True)
if isinstance(quant_config, GGUFConfig):
    norm_topk_prob = False
```

- Qwen3 MoE configs set `norm_topk_prob: true`. llama.cpp's `qwen3moe` graph also always normalizes the top-k weights.
- No GGUF MoE path renormalizes the weights later. `GGUFMoEMethod.apply` passes `topk_weights` straight to `fused_moe_gguf`, which only multiplies by them.
- So every MoE layer's output is scaled by the sum of the top-k softmax probabilities. In layer 0 of Qwen3-30B-A3B that sum is about 0.24.

The override came in with #17883 (Ascend GGUF support). The NPU top-k (`fused_topk_npu`) honours `renormalize` as well, so the override affects the NPU path the same way.

## Modifications

`python/sglang/srt/models/qwen3_moe.py`: remove the GGUF override. `TopK` takes `renormalize` from `config.norm_topk_prob` again, defaulting to `True` as before. A GGUF-only launch (no `config.json`) also yields `norm_topk_prob=True` with the pinned transformers 5.19.

## Accuracy Tests

The test model is Qwen3-30B-A3B Q4_K_M, run with `--tp 2 --ep-size 2` on 2x RTX 5070 Ti.

On main, the CUDA GGUF MoE path cannot run this model at all: an assert in `GGUFMoEMethod.apply` references a removed attribute, and EP-masked expert ids crash the kernel. These measurements therefore use a local branch that also carries fixes for those two problems; they will be submitted separately. The change in this PR does not depend on the MoE kernel. With every GGUF matmul (dense and MoE) replaced by dequantization plus a torch matmul, the NLL before this fix was essentially unchanged (2.15 vs 2.21 at window 128).

How the cause was isolated:
- Token ids match llama.cpp's for all 7,486 tokens. Neither side adds a BOS.
- An HF transformers reference, loading the same GGUF on CPU, agrees with llama.cpp. SGLang is the outlier.
- Layer 0 compared op by op against a gguf-py dequantized fp32 reference:

  | | relative error |
  |---|---|
  | attention output | ≤ 0.007 |
  | router logits | 0.0002 |
  | chosen expert ids | 100% identical |
  | top-k weights | off by exactly the factor above (0.0833 vs 0.353 for the first route of row 0) |

Mean NLL on the GPL-3 text, scored like `llama-perplexity` (second half of each window):

| window | llama.cpp | HF transformers (CPU) | main | this PR |
|---|---|---|---|---|
| 128 | 0.271 | 0.245 | 2.209 | 0.242 |
| 256 | 0.447 | 0.437 | 2.668 | 0.434 |
| 512 | 0.460 | 0.445 | 2.672 | 0.469 |
| 1024 | 0.399 | – | 3.688 | 0.400 |
| `-c 2048 --chunks 2` | 0.627 | – | 3.254 | 0.622 |

Before the fix, a 512-token prefix of the same text continued with garbage. After it, the continuation is the license text.

Not run: Ascend NPU (no hardware here). The NPU top-k honours the same flag, so I expect the same correction there. @TheKonka, could you confirm on NPU?

## Speed Tests and Profiling

No change. Prefill is 3,593 tok/s at 4K, and decode is 147 tok/s at batch 1 and 702 tok/s at batch 8, the same as before within noise.
