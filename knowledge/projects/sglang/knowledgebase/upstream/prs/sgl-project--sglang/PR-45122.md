# [Fix] metrics: don't publish cache_hit_rate from empty prefill reports

[Upstream PR](https://github.com/sgl-project/sglang/pull/45122) · state: open · merged: False

## Original PR description

## Motivation

`report_prefill_stats` computed the hit rate with a zero-denominator fallback and then published it
unconditionally:

```python
total_tokens = effective_input_tokens + effective_hit_tokens
cache_hit_rate = effective_hit_tokens / total_tokens if total_tokens > 0 else 0.0
...
self.stats.cache_hit_rate = cache_hit_rate
```

When a report carries no effective tokens, the `else 0.0` branch produces a fabricated zero — not a
"no data" signal — and overwrites the gauge. A report that actually prefilled tokens and hit none
still publishes a real `0.0`, which is correct and unchanged here.

This mirrors the guard already applied to the decode path, where the same class of overwrite was
fixed by #24427 (`cache_hit_rate is prefill-owned (per-report semantics); decode ticks must not
reset it`).

### Scope — this is hardening, not the reported symptom

Instrumenting a live server showed the `total_tokens == 0` branch does **not** fire under normal
chunked-prefill traffic (`0` of 261 reports had both `#new-token: 0` and `#cached-token: 0`), so this
PR is **not** a fix for "the gauge reads 0.0" as usually observed. That symptom comes from
per-report semantics — ~85% of prefill reports are chunk continuations with no prefix hit, so each
legitimately publishes `0.0` — which is a deliberate design choice, documented in the code, and not
something this PR changes. Full analysis and measurements: #45119.

The path this PR does protect is the retraction/reprocess case, where `effective_input_tokens` and
`effective_hit_tokens` are computed as differences and can both reach zero.

Happy to rework this as a windowed export (`recent_cache_hit_rate`, already maintained for
waiting-queue load estimation) if maintainers would prefer that instead.

## Modifications

- `_prefill_cache_hit_rate()` returns `None` when the report carried no prefill tokens.
- New `_record_prefill_cache_hit_rate()` holds the guard and is called from
  `report_prefill_stats`; the gauge is only assigned when there is a rate to publish.
- Genuine misses still publish a real `0.0`; a fully cached report still publishes `1.0`.
- `recent_cache_hit_rate` / `cache_hit_rate_window` advancement is unchanged and still runs for
  empty reports, so window-expiry semantics are preserved.
- Added `test/registered/unit/observability/test_prefill_cache_hit_rate.py`.

### Notes

- This skips **assignment**, not publication — the collector still exports the retained value. Before
  the first valid prefill report that is the `SchedulerStats.cache_hit_rate = 0.0` default. That
  startup behaviour is pre-existing and deliberately out of scope here.
- Negative effective components with a positive sum (e.g. `hit=-5, total=5`) are not validated; that
  arithmetic already existed and clamping it silently would hide malformed accounting.

## Accuracy Tests

```
helper:
  (96,100)  -> 0.96   OK
  (0,100)   -> 0.0    OK   real zero-hit, still published
  (0,0)     -> None   OK   nothing to measure
  (-5,-2)   -> None   OK

guard sequence:
  valid 0.96                              -> 0.96  OK
  valid then empty keeps 0.96             -> 0.96  OK
  genuine zero-hit                        -> 0.0   OK
  then empty keeps 0.0                    -> 0.0   OK
  fully cached                            -> 1.0   OK
  reprocessed-only keeps previous 0.8     -> 0.8   OK
ALL PASS
```

Mutation check: reintroducing the old unconditional zero fallback fails 2 of the guard cases
(`valid then empty keeps 0.96`, `reprocessed-only keeps previous 0.8`), so the regression is covered.

Refs #45119.
