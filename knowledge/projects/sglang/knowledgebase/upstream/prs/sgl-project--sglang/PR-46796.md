# [Perf] openai: Skip the prompt encode/decode round trip for multimodal chat (opt-in)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46796) · state: open · merged: False

## Original PR description

## Motivation

For a chat request with images, video or audio, the OpenAI chat handler does this today:

1. It renders the chat template.
2. It encodes the result and decodes it back to text.
3. The multimodal processor then tokenizes that text again.

For long multimodal prompts, the extra encode and decode in step 2 is serial work in the tokenizer process, and its result is thrown away. We measured it at about 31 ms per 16K-token video chat request. When the text round trip is the identity, sending the rendered template directly gives the processor the same text.

## Modifications

- `SGLANG_CHAT_MM_SKIP_PROMPT_REENCODE` in `environ.py` (default off).
- `OpenAIServingChat._apply_jinja_template`: the handler renders the template with `tokenize=False` and sends it as the prompt with empty `prompt_ids` only when all of these hold:
  - the variable is on;
  - the request has media;
  - there are no tools and no assistant prefix;
  - the tokenizer's text round trip is not lossy (the existing `_prompt_text_round_trip_is_lossy` probe).

  Every other request, and every request with the variable off, takes the current path.
- Tests in `test/registered/unit/entrypoints/openai/test_serving_chat.py`: with the variable on, the rendered template is sent without encode/decode; with the default (off), the current path is kept.

## Accuracy Tests

From a clean checkout (CPU):

```bash
python3 test/registered/unit/entrypoints/openai/test_serving_chat.py
```

This passed on a downstream fork whose `python/` and `test/` trees match this repository's layout. The patch applies cleanly to this repository's main.

On an earlier version of this change, with an internal multimodal model:

- Greedy outputs with the variable on and off were identical on 8/8 multimodal requests, with equal prompt token counts.
- A prompt re-encode check matched on 16/16 requests.

## Speed Tests and Profiling

Measured on an earlier version of this change, with the same model:

- The change removes about 31 ms of serial tokenizer-process work per 16K-token video chat request.
- Measured together with the SHM change (separate PR) and processor-side changes, first-wave TTFT P50 went from 8.2 s to 4.1 s. Throughput did not change, because the workload is device-bound.
