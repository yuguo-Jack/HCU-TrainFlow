# [Perf] diffusion: Stop the idle loop from starving async-save replies

[Upstream PR](https://github.com/sgl-project/sglang/pull/46221) · state: closed · merged: True

## Original PR description

## Motivation

With `--async-output-save`, single requests got slower and noisier instead of
staying flat. On 1xH200, Z-Image-Turbo went from 0.92 s to 1.00 s median (max
1.27 s) and Qwen-Image-2.1 from 4.45 s to 4.49–4.60 s (max 4.84 s), with almost
no throughput gain on Qwen-Image-2.1.

The finalize thread sends its reply on the ROUTER socket under `_socket_lock`.
While that finalize ran, the idle event loop waited with
`with self._socket_lock: self._poller.poll(timeout=1)` and took the lock straight
back in `recv_reqs()`. The loop held the lock almost all the time, and
`threading.Lock` is not fair (a semaphore on Linux / CPython 3.12): each release
wakes the finalize thread, but the loop re-acquires the lock a few microseconds
later, before the woken thread runs. The reply sat behind that loop for tens to
hundreds of milliseconds.

## Modifications

`Scheduler._wait_idle()` replaces both idle waits (in-flight finalize and the
dynamic-batching delay). With a finalize in flight it waits on the finalize
futures without the socket lock, for at most 1 ms, so new requests are still
picked up as before; with none in flight it polls the socket as before.

## Accuracy Tests

No numerical change: only the scheduler's idle wait changes.

## Benchmarking and Profiling

1xH200, `--model-type diffusion --warmup-mode server --performance-mode speed`,
1024x1024 PNG returned as b64_json. Each arm runs on a fresh server: two 3-step
warmups, then 10 sequential requests with distinct prompts, then 8 requests at
concurrency 2. Arms are interleaved and repeated twice; main is 49a2fbf817.

| case | arm | single median (s) | single max (s) | throughput (req/s) |
|---|---|---|---|---|
| Z-Image-Turbo, 9 steps | main | 0.920 / 0.922 | 0.925 / 0.927 | 1.094 / 1.094 |
| | main + `--async-output-save` | 1.006 / 1.000 | 1.246 / 1.269 | 1.117 / 1.129 |
| | **this PR** + `--async-output-save` | **0.921 / 0.920** | **0.924 / 0.924** | **1.128 / 1.128** |
| Qwen-Image-2.1, 40 steps | main | 4.450 / 4.446 | 4.459 / 4.464 | 0.2261 / 0.2261 |
| | main + `--async-output-save` | 4.490 / 4.604 | 4.569 / 4.838 | 0.2268 / 0.2271 |
| | **this PR** + `--async-output-save` | **4.446 / 4.446** | **4.459 / 4.461** | **0.2279 / 0.2280** |

With this PR, single-request latency under `--async-output-save` matches the
synchronous path, and the flag now gives the throughput it was meant to: +3.1%
on Z-Image and +0.8% on Qwen-Image-2.1 at concurrency 2.

Instrumented run (Qwen-Image-2.1, temporary timestamps around the reply's
`send_multipart`; 10 single requests per arm): the time the finalize thread
waited for `_socket_lock` after finishing the save was 14–51 ms median and up
to 262 ms on main, and 0.00 ms for every request with this PR. The save itself
took ~92 ms on either path. At concurrency 2 the wait was already ~0 on main:
the loop is inside the next forward instead of idling on the lock.
