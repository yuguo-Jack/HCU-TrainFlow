# [AMD] Enable the GDN decode projection/Conv1D fusion on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/37113) · state: open · merged: False

## Original PR description

## Summary

The fused GDN decode path that unpacks the QKVZ/BA projection outputs and applies
the indexed causal Conv1D update in a single kernel is currently gated to CUDA.
The kernel is device-agnostic Triton with no CUDA intrinsics, and the update it
performs is the same `causal_conv1d_triton` step ROCm already runs at decode, so
this widens the gate to HIP.

Please be noted that this PR deals with Triton path fusion, while #33113 could improve Aiter path. 

Measured on MI355X with TP=2 on Qwen3.5 at 8k in / 1k out, the fusion is worth
**+1.2% total throughput / -1.1% median TPOT** averaged across concurrency, with
gsm8k unchanged.

## Changes

**1. Widen the platform gate** (`python/sglang/srt/models/qwen3_5.py`)

`_gdn_decode_fused_proj_conv` moves from `_is_cuda` to `_is_cuda or _is_hip`.
This is the feature; the remaining changes follow from it.

**2. Keep the HIP empty-batch guard alive on the enabled path**
(`python/sglang/srt/layers/attention/linear/gdn_backend.py`)

Widening the gate changes what the HIP zero-row short-circuit receives. The fused
path hands down a `(projected_qkvz, projected_ba)` tuple, and the guard's
`isinstance(mixed_qkv, torch.Tensor)` test silently reads false on a tuple, so the
guard would stop firing on precisely the path being enabled - it does not raise,
it just quietly stops protecting. It now reads rows off the first element when a
tuple arrives.

**3. Register the kernel suite for AMD CI**
(`test/registered/kernels/ops/attention/test_gdn_decode_fused_proj_conv.py`)

The suite was `register_cuda_ci` only. Enabling an AMD path whose only coverage
runs on NVIDIA is how hardware-specific regressions get through review, so it
gains `register_amd_ci(est_time=10, suite="stage-b-test-1-gpu-small-amd")`
alongside the existing registration. Dual registration follows the pattern in
`test_session_control.py` and `test_data_parallelism.py`.

## Benchmarks

MI355X, TP=2, `/data/amd/Qwen35-V2-pr4`, aiter attention backend, fp8 KV cache,
`--enable-dense-fp8`, `--enable-aiter-allreduce-fusion`. Arms differ only in
`SGLANG_ENABLE_GDN_DECODE_FUSED_PROJ_CONV` (1 vs 0); `random-range-ratio 0.8`,
`num-prompts = max(32, 10*cc)`, seed 0. Arm validity was checked per launch: ON
servers logged the fused path engaging, OFF servers logged zero.

**One disclosure about the measurement environment.** Both arms also ran with
`SGLANG_GDN_FUSE_QKVZBA=1`, a separate merged-projection feature that is not part
of this PR and is off by default. It was held identical across arms, so it does
not bias the ON-vs-OFF comparison, but it does mean these numbers were taken on
the merged-projection path rather than on the two-GEMM path that is the default
today. The fusion applies to both; only the numbers were gathered on the former.

The gain decays with concurrency, largest at cc=4 and roughly zero at cc=64. That
is the shape expected from removing a fixed per-decode-step kernel launch: the
saving is constant while the work it hides behind grows with batch size. A second
input-length configuration reproduced the same decay shape.
