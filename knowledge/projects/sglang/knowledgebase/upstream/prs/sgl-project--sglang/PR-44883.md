# [Feat] [NPU] multimodal: Enable device-side multimodal feature transport via torch_npu IPC

[Upstream PR](https://github.com/sgl-project/sglang/pull/44883) · state: open · merged: False

## Original PR description

Part of #43519 (roadmap item: *Single-node device-side feature transport — provide an NPU-capable alternative to CUDA IPC for transferring multimodal feature tensors between local processes*).

## Motivation

`--mm-feature-transport cuda_ipc` currently requires NVIDIA CUDA: the feature pool, proxy lifecycle, and device primitives are hardcoded against `torch.cuda.*` and CUDA IPC handles. On Ascend NPU, multimodal features produced by the tokenizer process must therefore detour through host memory (CPU transport) even when both processes sit on the same node and the features already live in device HBM.

This PR makes the existing `cuda_ipc` transport NPU-capable with **zero behavior change on CUDA**. CUDA keeps the bounded pool + lease/ACK design unchanged; NPU follows the official torch_npu IPC recipe (`docs/memory_sharing_ipc.md`, method two): `torch.multiprocessing.reductions.reduce_tensor` → `rebuild_npu_tensor`, using public APIs only (no undocumented ACL calls).

## Design

- **No new CLI option**: NPU reuses the existing `--mm-feature-transport cuda_ipc` entry, gated per platform.
- **Features never leave NPU HBM**: the producer packs `(rebuild_func, args)` via the public `reduce_tensor` and pickles it into `proxy_state["ipc_extra"]["npu_ipc_payload"]` — a ~377 B descriptor regardless of feature size. The consumer rebuilds the tensor on its own device by redirecting the storage device index (`args[6]`), guarded by a layout/type check so an upstream layout change degrades with a warning instead of silently corrupting an unrelated argument.
- **Cross-device rebuild copies once into local HBM**: when the consumer rebuilds on a different device than the producer (e.g. TP2 on NPU), the redirected open returns a tensor backed by peer HBM through the IPC mapping. Compute reads work, but the DMA engine rejects host copies from that mapping (`memcpy exception`, 507001 — hit by the `.cpu()` inside `hash_feature`), which would abort the rank. Only in that branch the rebuild performs one D2D copy (~1.5 MiB per feature, microseconds); same-device rebuilds keep the zero-copy behaviour.
- **No pool on NPU**: zero HBM reservation, no lease/ACK bookkeeping; the KV-cache budget is no longer deducted for a pool that does not exist.
- **Platform code isolated in one inheriting pair**: the new `srt/multimodal/transport/npu_ipc.py` hosts the torch_npu `reductions` patch import (single side-effect point), the device primitives, the pack/rebuild pair, and two classes. `NpuIpcTensorTransportProxy` **inherits** the existing `CudaIpcTensorTransportProxy`, so every `isinstance` dispatch, pickle and msgpack path keeps working unchanged; it only fills the fields those consumers read and overrides the lifecycle hooks. `NpuIpcFeatureTransport` does **not** inherit `MmItemMemoryPool`: nothing dispatches on its type and the transport layer only calls `wrap_tensor` / `cancel_proxy`, so the NPU transport carries no pool, no lease/ACK and no constructor arguments. `cuda_ipc.py` itself is left byte-identical to `main`.

## Scope

Multimodal feature reconstruction has two paths:

- **Eager (shared path)** - 53 of the 56 registered processors. The scheduler rebuilds proxies before the model runs. All changes for this path live in shared code (`schedule_batch.py`, `mm_utils.py`, `base_processor.py`); no model file is touched. Verified end to end on Ascend with 9 families: Qwen2.5-VL, MiniCPM-V, Gemma3, Janus-Pro, Phi-4-multimodal, Kimi-VL, DeepSeek-OCR, GLM-OCR and Unlimited-OCR.
- **Deferred** - 3 processors (`qwen_vl.py`, `kimi_k3.py`, `kimi_k25.py`), used when the vision tower is DP-sharded and each rank must materialize only its own images. This PR adapts `qwen_vl.py` only (verified end to end on Ascend, TP1 and TP2).

`kimi_k3.py` / `kimi_k25.py` are not adapted in this PR: their reconstruction gate is limited to CUDA devices, so deferred reconstruction is not supported on Ascend when `--mm-feature-transport cuda_ipc` is explicitly enabled. The default transport is unaffected. Equivalent one-line changes were prototyped and validated only via cross-process mocks; they were dropped because Kimi-K3 / K2.5 (2.8T MoE, ~1.56 TB weights) cannot be run end to end on the available hardware, and unverified code does not meet the bar for this PR. NPU support for those two families is left as follow-up work.

## Roadmap item coverage

| Roadmap requirement | How it is covered |
|---|---|
| Bounded memory use | No pool on NPU → zero HBM reservation; `kv_cache_configurator` skips the pool deduction on NPU, recovering ~2–3 GB of usable KV |
| Tensor lifetime | torch_npu ref-counter keeps the shared block alive while consumers exist; rebuilt tensors verified bitwise-identical even after the producer drops its source tensor |
| Cancellation | `cancel_proxy` handles NPU proxies on the processor rollback path |
| Pool exhaustion | Not applicable — NPU has no pool; the failure mode is `reduce_tensor` raising, which falls back to the CPU transport |
| Fallback to CPU path | `wrap_tensor` returns `None` on any pack failure → CPU transport; A/B runs show 0 fallbacks |
| Transfer cost & TTFT comparison | Benchmarks below |

## Modifications

8 files: 7 modified + 1 new (net **+315 / −49**).

**NEW** `srt/multimodal/transport/npu_ipc.py` (217 lines)

- `NpuIpcTensorTransportProxy(CudaIpcTensorTransportProxy)` — inheritance is what keeps the 20+ `isinstance(..., CudaIpcTensorTransportProxy)` dispatch sites, pickle and msgpack decoding valid. `__init__` / `from_proxy_state` only populate the fields those consumers read (`npu_ipc_payload`, `reconstruct_tensor`, sync/borrow placeholders) and mark the consumer as acknowledged. `borrow_on_target_device` returns `None` so the scheduler falls back to reconstruction, `acknowledge_consumption` is a no-op, and `reconstruct_on_target_device` caches the rebuilt tensor per device.
- `NpuIpcFeatureTransport` — no inheritance from `MmItemMemoryPool`, no pool and no constructor arguments: only `wrap_tensor` (packs via `reduce_tensor`, returns `None` on failure → CPU transport) and `cancel_proxy` (no-op, there is no lease) are reachable.
- Device primitives: `is_device_tensor`, `current_device`, `_device_guard`, `_pack_tensor`, `_rebuild_tensor` (with the `args[6]` redirect, the layout guard and the cross-device local copy), plus the single torch_npu `reductions` patch import.

- `srt/multimodal/processors/base_processor.py` (+35 −26): choose `NpuIpcFeatureTransport` or `MmItemMemoryPool` per platform. The CUDA pool budget computation and its reservation log stay inside the CUDA branch, so NPU no longer runs the per-worker split (and `SGLANG_MM_FEATURE_CACHE_MB=0` no longer raises there).
- `srt/utils/msgpack_utils.py` (+10 −1): rebuild NPU proxies from `transport_mode` instead of hard-coding the CUDA class's `__new__`.
- `srt/arg_groups/serving_hook.py` (+27 −13): accept NPU for `cuda_ipc`; merge the two branch logs into one template, with the pool-handle cache note kept CUDA-only.
- `srt/managers/schedule_batch.py` (+10 −3), `srt/managers/mm_utils.py` (+4 −1), `srt/models/qwen3_vl.py` (+8 −4): resolve the transport device through `npu_ipc.current_device` instead of `torch.cuda.current_device()`.
- `srt/mem_cache/kv_cache_configurator.py` (+4 −1): skip the feature-pool KV deduction on NPU.

`srt/multimodal/transport/cuda_ipc.py` is **not modified** — zero diff against `main`. On CUDA, every modified call site either executes identical code or is unreachable, so behaviour is unchanged (regression below).

## Benchmarks (Ascend 910, CANN 9.1.0, torch_npu 2.10.0, Qwen3-VL-8B-Thinking)

Transfer-level, two processes, 16 producer threads, in-flight depth 8, 800 frames per group:

| Feature size | CPU ms/frame | NPU IPC ms/frame | Saved |
|---|---|---|---|
| 1.5 MiB | 0.98 | 0.52 | 46.8% |
| 18.4 MiB | 13.07 | 0.54 | 95.9% |
| 47.6 MiB | 56.30 | 0.52 | 99.1% |

IPC cost is constant (~0.52 ms/frame — only the 377 B descriptor crosses processes) while CPU transfer is strictly linear in feature size.

End-to-end (4×1024² images per request, 16 concurrency, 90 s): 0 errors and 0 fallbacks on both arms; p50 delta −13.5% is within the noise band (p99 +11.1%, single round, transfer explains ~0.4% of end-to-end latency at this scale) and is not claimed as a win.

Accuracy: MMBench EN DEV v1.1, 1292 questions, CircularEval, greedy decoding, `cuda_ipc` vs `cpu` on the same node with a position-swap control over 3 rounds — no transport-induced accuracy delta (observed ±0.7 pp shifts do not follow the transport arm and flip sign after swapping dies).

## CUDA regression (unchanged behaviour)

Environment: RTX 4090 48G, Ubuntu 22.04, torch 2.13.0+cu130, transformers 5.19.0, `sglang-kernel` 0.4.10, `--attention-backend triton`, TP1.

Method: dual-tree A/B (`baseline` = `c9bf6c84eb^`, `candidate` = this PR) × 2×2 matrix {baseline, candidate} × {default transport, `--mm-feature-transport cuda_ipc`}, one server per configuration, greedy decoding with a fixed seed, three request types (single image / two images / text-only) plus a 16-way concurrency round. Both paths touched by this PR are covered: `qwen3_vl.py` via a deferred-reconstruction model and the shared eager path via a model that never defers.

| Model | Path | Outputs (single / two images / text) | prompt/completion tokens | 16-way concurrency | `Using CUDA IPC` |
|---|---|---|---|---|---|
| Qwen3-VL-8B-Instruct | deferred | identical in all 4 configurations (57 tokens) | 787 / 57, all 4 identical | 16/16, `distinct=1`, 0 errors | 0 (default) / 3 (cuda_ipc) |
| Qwen2.5-VL-3B-Instruct | eager | identical in all 4 configurations | 118/12, 217/3, 33/3 — all 4 identical | 16/16, `distinct=1`, 0 errors | 0 (default) / 1 (cuda_ipc) |

- Token ids are 100% identical across all comparison pairs; no `Traceback` in any of the 8 server runs.
- IPC switch is verified to be effective: the default-transport arms log 0 `Using CUDA IPC` lines, the `cuda_ipc` arms log the pool reservation line, so the comparison is not running an empty path.
- The only observed difference is a logprob jitter (±0.11 max) on the **first** image request of a server instance; it reproduces in the baseline tree with the same magnitude, and repeated requests within one server session are bit-identical, i.e. environment non-determinism unrelated to this PR. Token ids and texts never differ.
- Unit tests: 6 test files (IPC transport, pool budget, GPU feature transport, Qwen3-VL materialization) — 61 passed + 19 subtests, 0 failures on both trees.
