# [Fix] [NPU] hc_pre: Fix DeepSeek-V4 hc_pre in dual-machine PD disaggregation on Ascend 950

[Upstream PR](https://github.com/sgl-project/sglang/pull/43955) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V4 pre-processes each layer's mHC residual with a single fused op,
`torch.ops.custom.npu_hc_pre` (from `cann-recipes-infer`). **Running DeepSeek-V4
with dual-machine PD disaggregation (prefill/decode separation) on Ascend 950
fails on this path** — `hc_pre` raises an error during the disaggregated run.

<!-- paste the exact error / traceback here once captured -->

Ascend 950 (NPU arch35) also ships the official, CANN-maintained ops
`torch_npu.npu_mhc_pre` + `torch_npu.npu_mhc_sinkhorn`. This PR routes `hc_pre`
through those on 950 to fix the PD-disaggregation failure, while A2/A3 keep the
legacy `custom.npu_hc_pre` path unchanged.


Two API facts shape the implementation:

- The legacy fused op returns `(y, post, comb)`, and its `comb` is already
  Sinkhorn-normalised.
- The official `npu_mhc_pre` returns `h_res` **before** the Sinkhorn transform,
  so `comb` must be produced by chaining `npu_mhc_sinkhorn` (the old op did this
  inline). A naive op-name swap would silently feed a non-normalised `comb` into
  `hc_post`.
<!-- Describe the purpose and goals of this pull request. -->

## Modifications

1. `python/sglang/kernels/ops/layernorm/mhc.py`
   - `npu_hc_pre` is now an arch dispatcher:
     - On Ascend 950 (`is_npu_arch35()`): `torch_npu.npu_mhc_pre(x, hc_fn, hc_scale, hc_base, gamma=None, norm_eps=rms_norm_eps, hc_eps=hc_eps, out_flag=0)` → `(h_in, h_post, h_res)`, then `torch_npu.npu_mhc_sinkhorn(h_res, eps=hc_eps, num_iters=hc_sinkhorn_iters)` → `comb`. `gamma=None` because the legacy op's RMS is unweighted (the caller applies `input_layernorm` separately).
     - On A2/A3: the legacy `custom.npu_hc_pre` call, **unchanged**.
   - The 4-tuple return contract `(y, post, comb, norm_fused=False)` and the idle/empty short-circuit are preserved.
   - `inner_precise` is intentionally not passed: older `torch_npu` builds do not declare it, and where it exists its default is `0` (FP32).
<!-- Detail the changes made in this pull request. -->
### Scope note

- **A2/A3 keep the exact legacy path** — they never import `torch_npu`. Only 950 (arch35) takes the new branch.
- `hc_post` is intentionally **not** changed: it already has its own arch35 branch and consumes `(post, comb)`, whose shape/dtype are unchanged. The `custom` extension remains a dependency on 950 (via `custom.npu_hc_post`), which is fine for this change.
- Out of scope (possible follow-up): migrating `hc_post` to `torch_npu.npu_mhc_post`.
