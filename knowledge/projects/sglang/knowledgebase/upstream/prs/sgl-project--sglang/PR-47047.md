# [Fix] glm5_next: Gather DFlash aux hidden states for every scattered MoE all-to-all backend

## Summary

**TL;DR: This PR makes GLM-5.3-Flash gather the hidden states it captures for a DFlash draft whenever the MoE input is split so that each attention-TP rank holds only its own rows (any MoE all-to-all backend, the FlashInfer FP4 all-gather path or DWDP), not just for deepep, mooncake and deepep_v2.** The gate now uses `is_moe_input_scattered_across_dp_ranks()`, the same predicate the layer boundaries use to put the MoE on those rows, instead of a list of three backends. The three listed backends, and every configuration whose MoE input is not split, keep main's behavior.

- **Enables:** GLM-5.3-Flash with DFLASH speculative decoding and `--moe-a2a-backend megamoe` (8x H200, TP8, EP8) now serves; on main the first request fails with an `index out of bounds` device assert.
- **Performance:** against main serving the same megamoe configuration without speculative decoding (the only way main can serve it), the median time per output token with DFLASH is **2.6x shorter at 1 request** (8.92 -> 3.40 ms, 61.8% shorter) and **1.3x shorter at 128 concurrent requests** (30.06 -> 23.13 ms); steady decode throughput is 1.7-2.5x higher (8.2k-token prompts, 1024 output tokens).
- **Accuracy:** effectively lossless. GSM8K (all 1319 questions) with DFLASH on this PR is **96.89-97.27%** on repeat servers, against **97.42%** on main without speculative decoding on the same configuration. Main and this PR answer 12-13 questions differently, fewer than repeat servers of this PR do (15). Single requests give the same greedy text.
- **Cost:** none. The gate is evaluated once when the model is built. The extra all-gather runs only for the layers captured for a draft, and only when the rows are split, exactly as it already does for deepep on main. No new flags or environment variables.

## Motivation

GLM-5.3-Flash support (#36507) captures hidden states of selected layers for an EAGLE3 or DFlash draft in `Glm5NextModel.forward` (`capture_output`). After a MoE layer whose input is split across the attention-TP ranks, each rank holds only its own rows, so `capture_output` all-gathers them over the attention-TP group when `self.enable_a2a_moe` is set. #40466 added deepep_v2 to the list that sets it; the list now reads deepep, mooncake and deepep_v2.

Every other all-to-all backend splits the rows the same way: the layer boundaries run the sparse MoE on a rank's own rows whenever `is_moe_input_scattered_across_dp_ranks()` is true (`_ffn_on_rank_rows` in `python/sglang/srt/layers/layer_boundary/factories.py`), and that predicate is true for any `--moe-a2a-backend` other than `none`, for the FlashInfer CUTLASS FP4 all-gather path and for DWDP. With `--moe-a2a-backend megamoe`, for example, the captured states are not gathered, the draft receives one eighth of the rows at attention TP8, and the logits processor indexes past them on the first request:

```
IndexKernel.cu:111: ... Assertion `-sizes[i] <= index && index < sizes[i] && "index out of bounds"` failed.
RuntimeError: Triton Error [CUDA]: device-side assert triggered
```

## Modifications

- **`python/sglang/srt/models/glm5_next.py`** -- `self.enable_a2a_moe = is_moe_input_scattered_across_dp_ranks()` replaces the deepep / mooncake / deepep_v2 list.

Design notes:

- Unchanged on main's paths: with `--moe-a2a-backend none` (and neither the FP4 all-gather nor DWDP) the gate stays false; with deepep, mooncake or deepep_v2 it stays true. It becomes true for the other all-to-all backends (megamoe, flashinfer, nixl, mori and the rest) and for the FP4 all-gather and DWDP paths, which are exactly the cases where the layer boundaries split the MoE rows.
- `enable_a2a_moe` is read only in `capture_output`, which runs only for the layers captured for an EAGLE3 or DFlash draft. A server without such a draft is not affected.
- No new flags or environment variables.

## Accuracy Tests

**The change only decides whether captured rows are gathered, so the target model's own forward is unchanged; with DFLASH the server's output should match main without speculative decoding.** **Measured: GSM8K 96.89-97.27% on this PR with DFLASH against 97.42% on main without speculative decoding; main and this PR answer fewer questions differently than repeat servers of this PR do, and single requests give the same greedy text.**

Setup, measured in this environment: main `1ec902e00f`, this PR `00fcb858a3` on it; torch 2.14.1 (CUDA 13.0), FlashInfer 0.7.2, sglang-kernel 0.4.10; the server command below. sgl-eval 0.1.3 `gsm8k`, all 1319 questions, temperature 0, top_p 0.95 and max tokens 32768 (its defaults), 32 threads:

| server | GSM8K | truncated |
|---|---|---|
| main, no speculative decoding | 97.42% | 0.23% |
| main, DFLASH | first request fails (device assert) | - |
| this PR, DFLASH (repeat servers) | 96.89-97.27% | 0.38-0.53% |

Question by question, main and this PR answer 12-13 of the 1319 questions differently (exact McNemar p = 0.09-0.77), while repeat servers of this PR answer 15 differently from each other, so the gap is within the run-to-run variation of DFLASH itself. Two single greedy requests (a short question and an 8,144-token LongBench-v2 document) give the same text on this PR with DFLASH as on main without speculative decoding.

<details><summary>Server and eval commands</summary>

```bash
python3 -m sglang.launch_server --model-path zai-org/GLM-5.3-Flash --trust-remote-code \
  --tp-size 8 --ep-size 8 --mem-fraction-static 0.75 \
  --dsa-prefill-backend flashmla_sparse_q8 --dsa-decode-backend tilelang --kv-cache-dtype bfloat16 \
  --moe-runner-backend deep_gemm --moe-a2a-backend megamoe \
  --cuda-graph-max-bs-decode 128 --max-running-requests 128 --chunked-prefill-size 8192 --disable-radix-cache \
  --speculative-algorithm DFLASH --speculative-draft-model-path incoai/GLM-5.3-Flash-DFlash2 \
  --speculative-draft-attention-backend fa4
sgl-eval run gsm8k --base-url http://localhost:30000/v1 --num-threads 32 --max-tokens 32768
```

The main run without speculative decoding drops the three `--speculative-*` flags.

## Speed Tests and Profiling

**Why this test:** on main this configuration can be served only without speculative decoding, so that is the baseline. **Result:** with DFLASH on this PR every concurrency measured (1 to 128 requests) is faster; the median time per output token is 2.6x shorter at 1 request and 1.3x shorter at 128 concurrent requests.

Setup, measured in this environment: main `1ec902e00f`, this PR `00fcb858a3` on it; torch 2.14.1 (CUDA 13.0), FlashInfer 0.7.2, sglang-kernel 0.4.10; the server command under Accuracy Tests, main without the three `--speculative-*` flags. Workload: LongBench-v2 prompts of about 8.2k tokens, 1024 output tokens (`ignore_eos`), all requests of a burst sent at once; bursts of 1, 8, 64 and 128 requests on a freshly started server after two warm-up bursts. Main is measured first and last, this PR second and second to last. TPOT is the benchmark's median time per output token after the first, so it includes decode steps slowed by the other requests' prefills; steady decode throughput is the median `Decode batch` gen throughput while every request of the burst is decoding and none is queued. Values are medians; repeat servers of the same tree agree within 3.3% on TPOT. The accept length with this PR is 3.5-4.3 tokens per step, including the bonus token.

**Main without speculative decoding -> this PR with DFLASH (+% = this PR better):**

| concurrent requests | median TPOT (ms) | steady decode throughput (tok/s) | output throughput over the whole burst (tok/s, including the 8k-token prefill) |
|---|---|---|---|
| 1 | 8.92 -> 3.40 (61.8% shorter) | 112 -> 276 (+146%) | 109 -> 273 (+149%) |
| 8 | 11.00 -> 5.08 (53.9% shorter) | 745 -> 1,702 (+129%) | 660 -> 1,203 (+82%) |
| 64 | 22.17 -> 13.32 (39.9% shorter) | 3,750 -> 7,794 (+108%) | 2,166 -> 3,059 (+41%) |
| 128 | 30.06 -> 23.13 (23.0% shorter) | 6,544 -> 10,966 (+68%) | 3,122 -> 3,518 (+13%) |

The per-PR CUDA suites (`base-a` and `base-b` 1-GPU and 2-GPU, `base-c` 4-GPU H100 and 8-GPU H200) and the five CPU suites ran on main `1ec902e00f` with this PR and a three-line DFLASH worker change (`dflash_worker_v2.py`) that main has since taken in #45925 (this PR does not depend on it) applied together, and no test file fails only with them: every file that fails there also fails on main. With this PR, the GLM-5.3-Flash H200 model tests `test/registered/e2e/models/test_glm53_flash_h200_low_latency.py` and `test_glm53_flash_h200_high_throughput.py` pass. Not run here: the PD disaggregation and Mooncake HiCache tests, and other GPU architectures.

## Scope and limitations

- **Measured:** GLM-5.3-Flash on 8x H200 (SM90), TP8, EP8, attention TP8, `--moe-a2a-backend megamoe`, DFLASH with `incoai/GLM-5.3-Flash-DFlash2`.
- **Same code path, not measured:** EAGLE3 and DSpark drafts on GLM-5.3-Flash (same capture); the other all-to-all backends and the FP4 all-gather / DWDP paths, by reading the code: the gate now agrees with the layer boundaries' own predicate on every architecture. DFLASH with DP attention, which main serves on CUDA since #46330, goes through the same gate.
- **Not affected:** `--moe-a2a-backend none`, deepep, mooncake and deepep_v2 (gate value unchanged); servers without an EAGLE3, DFlash or DSpark draft, MTP included (the gate is never read).
