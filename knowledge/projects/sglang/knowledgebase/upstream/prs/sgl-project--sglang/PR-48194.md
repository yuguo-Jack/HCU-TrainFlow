## Original PR description

# [Fix] [AMD] kimi-k3: Restore the KDA in-proj fusion for quantized checkpoints

## Motivation

On ROCm, [#35176](https://github.com/sgl-project/sglang/pull/35176) runs the whole KDA input projection `[q, k, v, g | f_a | b]` as one GEMM (N = 6288 per rank at TP8) for batches up to `SGLANG_ROCM_K3_FUSE_KDA_INPROJ_MAX_TOKENS` (256) tokens. Otherwise decode runs the wide `[q, k, v, g]` GEMM plus a separate `[f_a | b]` GEMV on each of Kimi-K3's 69 KDA layers. #35176 measured 0.7–2.1% more throughput and 1.0–2.6% lower median ITL from the fusion at concurrency 4–32 (ISL 8192 / OSL 1024, 8× MI355X).

[#39589](https://github.com/sgl-project/sglang/pull/39589) changed `do_fuse_qkvbfg` to `quant_config is None and attn_tp_size == tp_size`. The in-proj gate, `_may_fuse_kda_inproj()`, checks that flag, so the fusion is now off for every quantized Kimi-K3 checkpoint. That includes the MXFP4 checkpoint, whose attention linears are plain bf16, which is what the fusion needs.

The fusion feeds both fused KDA decode backends on gfx950:

- **`gfx950`** (`SGLANG_ROCM_K3_KDA_FUSED_BACKEND`'s default since [#45713](https://github.com/sgl-project/sglang/pull/45713); [#45710](https://github.com/sgl-project/sglang/pull/45710) added the matching HIP chunked-prefill kernel). It takes an fp32 SSM state, so it serves `--mamba-ssm-dtype float32`.
- **`aiter`** (FlyDSL), which used to be the fused path. Its kernel also has a bf16-state build for `--mamba-ssm-dtype bfloat16`, which [#41570](https://github.com/sgl-project/sglang/pull/41570) and [#41794](https://github.com/sgl-project/sglang/pull/41794) wire up.

Both run with `f_b` deferred: they take the `f_a` slice of the in-proj output and apply `f_b` themselves. Both accept the strided `f_a` slice of the merged buffer: the adapters check only `f_a.stride(-1) == 1`, and the `gfx950` kernel indexes rows by `f_a.stride(0)`. The in-proj fusion therefore pays off with either backend and either SSM dtype. Today a quantized checkpoint gets neither.

## Modifications

`_may_fuse_kda_inproj()` in `python/sglang/srt/models/kimi_k3.py`:

```python
# Not do_fuse_qkvbfg: it requires quant_config is None, which quantized
# checkpoints never meet even though their attention linears stay bf16.
if not (self.use_full_rank_gate and self.attn_tp_size == self.tp_size):
    return False
...
mods = (self.fused_qkvg_proj, self.f_a_proj, self.b_proj)
# The merged buffer is applied through fused_qkvg_proj's quant method and
# carries only .weight, and online quantization replaces .weight after
# this runs, so every projection must stay unquantized.
if not all(isinstance(m.quant_method, UnquantizedLinearMethod) for m in mods):
    return False
```

- **The gate** checks what the fusion needs instead of `do_fuse_qkvbfg`: the full-rank gate, which creates `fused_qkvg_proj`, and `attn_tp_size == tp_size`. DP attention keeps the split path, as it does today.
- **`UnquantizedLinearMethod` on all three projections.** The fused GEMM runs the merged buffer through `fused_qkvg_proj.quant_method.apply()`, and the buffer holds only `.weight`. The merge runs in `post_load_weights()`, which is before `process_weights_after_loading()`. With online quantization (for example `--quantization fp8` on a bf16 checkpoint), the weights would still be bf16 at that point and pass the dtype check, and the quantized method would then get a bf16 buffer without scales. Quant methods without a `.weight` (GPTQ / AWQ `qweight`, compressed-tensors `weight_packed`) are also rejected here, before `.weight` is read.
- **Unchanged checks:** block-FP8 `[f_a | b]`; plain 2-D bf16 / fp16 weights of one dtype and width. These still reject checkpoints whose attention weights are quantized on disk (per-channel or block FP8, int8, packed MXFP4).

Checkpoints that fuse after this change:

| Checkpoint | Attention linears | Fuses |
| --- | --- | --- |
| Unquantized (`quant_config is None`) | `UnquantizedLinearMethod` | yes, as today |
| Quark MXFP4, attention excluded | `UnquantizedLinearMethod` | yes (was no) |
| compressed-tensors, attention without a scheme | `UnquantizedLinearMethod` | yes (was no) |
| Quark with `excluded_fp8_config`, attention in FP8 | `Fp8LinearMethod` | no |
| Attention quantized on disk, or online-quantized | quantized method | no |

Non-ROCm platforms are unaffected: the gate starts with `_is_hip`, and `SGLANG_ROCM_K3_FUSE_KDA_INPROJ=0` still turns the fusion off.

## Unit Tests

`test_gate_allows_quantized_checkpoint_with_bf16_attention` in `test_kimi_k3_kda_inproj_fusion.py` calls `KimiK3DeltaAttention._may_fuse_kda_inproj` on a stand-in with `do_fuse_qkvbfg=False` and checks that:

- bf16 weights on `UnquantizedLinearMethod` fuse;
- `float8_e4m3fn` weights do not;
- `attn_tp_size != tp_size` does not;
- bf16 weights on any other quant method (the online-quantization case) do not.

The existing tests in the file still cover the merged layout, the views, and agreement between the fused and split paths, including the deferred-`f_b` output.

Not run yet.

## Accuracy Tests

Pending. The fused and split paths use the same weights through views and agree to bf16 rounding, not bit for bit, because they run different GEMM kernels. #35176 reported GSM8K 0.951–0.952 with the fusion on. gsm8k on the MXFP4 checkpoint will be added, with the `gfx950` backend (fp32 SSM) and the `aiter` backend (bf16 SSM).

## Speed Tests and Profiling

Pending. Planned on 8× MI355X, Kimi-K3 MXFP4, TP8, ISL 8192 / OSL 1024, concurrency 4–64, with `SGLANG_ROCM_K3_FUSE_KDA_INPROJ=0` against the default:

1. `gfx950` fused decode, `--mamba-ssm-dtype float32` (the current default).
2. `aiter` fused decode, `--mamba-ssm-dtype bfloat16`.
