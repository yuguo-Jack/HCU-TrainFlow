# [Fix] flashinfer: Trim DP-padded query rows in the prefill path

[Upstream PR](https://github.com/sgl-project/sglang/pull/42862) · state: closed · merged: False

## Original PR description

## Motivation

- With `--enable-dp-attention` and `--attention-backend flashinfer`, any prefill whose token count is not a multiple of `attn_tp_size` crashes the scheduler on main. A 1-token prompt at TP4/DP2 is enough:
  ```
  ValueError: q.shape[0] (2) does not match qo_indptr[-1] (1). For paged prefill, q must have shape [total_tokens, num_heads, head_dim] where total_tokens = qo_indptr[-1].
  ```
- DP attention pads each rank's rows to a multiple of `attn_tp_size` (and to the longest rank). The FlashInfer prefill plan is built from the real extend lengths, so the padded query has more rows than the plan.
- #35876 fixes the same mismatch on the DeepSeek MLA backend. This PR covers the plain FlashInfer backend, which that PR does not touch.

## Modifications

- `FlashInferAttnBackend.forward_extend` passes only the real query rows to the kernel and pads the output back with zero rows, so the caller still gets the padded shape.
- Keys and values stay padded. Their padded rows are written to cache slot 0, as `out_cache_loc` already says.
- Only `EXTEND` and `MIXED` batches are trimmed. Target-verify and draft-extend batches are left as they are.
- New CPU unit test `test_flashinfer_dp_padded_prefill.py`. It fails on main with the error above and passes with the fix.

## Accuracy Tests

Qwen/Qwen3.8-27B on 4x B300. The reference is the same build without DP attention.

```bash
# fix
python3 -m sglang.launch_server --model-path Qwen/Qwen3.8-27B --tp-size 4 --dp-size 2 --enable-dp-attention --attention-backend flashinfer
# reference
python3 -m sglang.launch_server --model-path Qwen/Qwen3.8-27B --tp-size 2 --attention-backend flashinfer
# eval
python3 -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --num-threads 128
```

| Server | GSM8K (1319) | Scheduler exceptions |
|---|---|---|
| main, TP4/DP2 | not run, crashes on the first 1-token prompt | every rank |
| fix, TP4/DP2 | 0.961 | 0 |
| reference, TP2 | 0.966 | 0 |

- The GSM8K gap is 0.005, and the standard error at this sample size is about 0.005 per run.
- Greedy first-token check: prompts of 1 to 2001 tokens, sent alone and at the same time to both DP ranks with unequal lengths, plus several odd-length prompts batched on one rank. 126 requests, 3 repeats each.
  - The top token matches the reference in 126 of 126.
  - The largest logprob difference from the reference is 0.058. Two runs of the reference differ from each other by up to 0.066.
- The fix was also run with `--disable-cuda-graph` on prompts of 1 to 255 tokens: no exceptions, and first-token logprobs within 0.054 of the reference.

## Speed Tests and Profiling

- Not measured. Batches without padding take the same code path as before. For padded batches, the trim is a tensor view, so nothing is copied. Those batches crashed before, so there is no earlier number to compare with.
