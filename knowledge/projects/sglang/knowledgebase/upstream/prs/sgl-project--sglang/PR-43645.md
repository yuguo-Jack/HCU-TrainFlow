# [Fix] mem_cache: charge the req_to_token table in the pre-capture KV budget

[Upstream PR](https://github.com/sgl-project/sglang/pull/43645) · state: open · merged: False

## Original PR description

## Motivation

A bare launch of a 1M-context model can OOM while building the KV pools. Reproduced on 1x H200 with `thinkingmachines/Inkling` (`test` revision, `context_len=1048576`) and no flags:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 2.30 GiB. ... of which 2.08 GiB is free.
```

`_profile_available_bytes` sizes the pre-capture KV budget as `free - slack - mamba state`, and the KV pools then consume all of it. The `req_to_token` table is never charged, so it silently lives in the slack. The slack (`pre_model_load * (1 - mem_fraction_static)`) is meant for activations and CUDA graph buffers (see `handle_gpu_memory_settings`). That only works while the table is small:

| | rows x context x 4 B | slack at 0.903 on H200 |
|---|---|---|
| 40K-context model | 4097 x 40964 x 4 = 0.6 GiB | 13.5 GB |
| Inkling (1M context) | 4097 x 1048580 x 4 = 16 GiB | 13.5 GB |

Measured around pool construction for that run: the req pool step takes 27.07 GiB (mamba 11.05 + `req_to_token` 16.02). Full KV (92.1 GiB) then fits, but SWA (18.4 GiB) does not. With KV sizes unchanged, either `--max-running-requests 256` or `--context-length 131072` alone gets past pool construction, which confirms the cause.

## Modifications

- `_profile_available_bytes` subtracts an upper bound of the `req_to_token` table before the mamba/KV split, the same way the mamba state pool is already charged. The upper bound is `(max running requests per DP worker, or the 4096 auto-estimate cap) + decode pre-alloc rows + 1 padding row`, times `(context_len + extra) x int32`.
- The post-capture KV sizing path is unchanged: it measures free memory after the table already exists.
- Extract `MAX_AUTO_RUNNING_REQUESTS_PER_WORKER` (shared with `resolve_max_num_reqs`) and `_decode_req_pool_pre_alloc_size()` (shared with `_build_req_to_token_pool`, behavior unchanged).
- `TestReqToTokenBudget` in `test_pool_configurator.py` (CPU): builds the real pool from the `max_num_reqs` that `resolve_max_num_reqs` returns, and asserts that the reserved bound covers its `req_to_token.nbytes` (PD decode with pre-alloc rows; auto-sized and per-DP-worker requests; small and large token capacity). The test turns red if the bound drops the pre-alloc rows, drops the padding row, or if `resolve_max_num_reqs` is allowed past the 4096 cap.

Trade-off: every model's pre-capture KV capacity shrinks by the table size, memory the table was already taking from the activation slack. When `--max-running-requests` is unset, the bound uses the 4096 cap even where the auto-estimate resolves lower, so it is conservative by at most that difference.
