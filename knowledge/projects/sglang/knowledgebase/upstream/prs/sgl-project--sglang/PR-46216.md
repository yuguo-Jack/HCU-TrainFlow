# [Feat] rust-server: Let an embedding package add keys to /generate frames

[Upstream PR](https://github.com/sgl-project/sglang/pull/46216) · state: closed · merged: True

## Original PR description

Stacked on #46205 (weight versions and media token counts in `/generate` meta_info): this PR's fixture column and header position build on that one, so review the top commit only.

## Motivation

A package that embeds `sglang-server` behind its own Python server class can add its own metadata to `/generate` responses in Python mode through a `TokenizerManager` subclass, but the Rust frontend replaces that `TokenizerManager`, and such a package had no way to add keys to the frames the native `/generate` route emits. This PR adds the seam; it changes nothing for a server that does not use it.

## Modifications

- **`GenerateHook`**, exported from `sglang-server`. `Server::start_with_extensions` takes it next to `http_layer`: the two single-purpose constructors (`start`, `start_with_http_layer`) became one entry point that a package can use to install both. The hook starts one `GenerateFrameHook` per request from its sampling params (preferred params applied, not yet normalized). The native `/generate` adapter calls it for every frame it emits (unary, cumulative or incremental stream, batch item) and passes the decode latency on the terminal frame. The hook's keys go into `meta_info` or into the frame object, after the schema's own keys; the hook-aware serializer writes the generated serializer's keys first, in its order. Without a hook the frames are byte-for-byte unchanged, and gRPC and the OpenAI routes do not call the hook.
- **`RustServer._server_kwargs(scheduler)`**: keyword arguments for the package's server class beyond the shared ones (`{}` by default), so a package can pass its hook through the Python launcher.
- **`SamplingParams::sampled_temperature_top_k`**: `normalize`'s greedy and `top_k = -1` rules as one function, so a hook can report the values the scheduler samples with. `post_init` now uses it.

The decode latency follows the Python `TokenizerManager` (`get_decode_latency`): from the first output the frontend receives to the terminal one, except that a non-streaming request starts at the scheduler's prefill-finished stamp, which the `TokenizerManager` receives only when metrics are on. The Rust frontend sees a non-streaming request's first output up to `SGLANG_FORCE_STREAM_INTERVAL` tokens late, so its own timing would put a short unary request's decode time near zero. The scheduler therefore measures that case itself: for a finished non-streaming row only, `perf_counter()` minus the prefill stamp, under the same metrics condition, sent as one more optional header column after the media counts. Every other case falls back to the frontend's first and terminal outputs, as Python's does. Streaming and unfinished rows cost nothing extra, and Python mode is unchanged.

Tests:

- `generate_hook_keys_reach_every_frame`: through the `/generate` router, a test hook's keys reach every frame of both items of a batch (unary, cumulative stream, incremental stream). Each item's hook starts from its own `top_p`, the first-frame key lands on each item's first frame only, and the decode latency on its terminal frame only: the scheduler's value for a unary item, the frontend's for a streamed one. Without a hook, no key is added.
- `generate_hook_annotates_intermediate_cumulative_frames` and `scheduler_decode_latency_reaches_the_hook` pin the cumulative-stream path and the scheduler-side latency hand-off.
- `native_frame_keeps_the_schema_keys_first`: with no added keys, the hook-aware serializer writes the generated serializer's bytes; added keys follow the schema's.
- `frame_metadata_matches_python` and `request_timing_records_ttft_once_and_e2e_on_finish` now also check the decode-latency column and value.
- Python: `test_output_streamer_customized_info.py` (`test_rust_mode_times_finished_non_streaming_requests`: in Rust mode only a finished non-streaming request with metrics on and a prefill stamp gets a latency, at least the stamp's age; streaming, unfinished, metrics-off and stampless requests, and Python mode, get none; the `push_generation` hand-off is covered too) and `test_rust_server_extension.py` (the launch test passes a package's `_server_kwargs`; the fixture carries a decode latency).

## Accuracy Tests

Not applicable: no model forward or kernel code changes. Generation output is unchanged; without a hook the frames are byte-for-byte what they were.

## Speed Tests and Profiling

Not run. The per-frame cost without a hook is one `Option` check; the scheduler's extra work is one `perf_counter()` call per finished non-streaming request, and only when metrics are on.
