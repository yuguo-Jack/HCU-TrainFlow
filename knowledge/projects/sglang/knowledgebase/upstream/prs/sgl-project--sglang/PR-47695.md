# [Feat] [AMD] quark: Quark int4 W4A16 on ROCm, and gfx1151 kernels for Strix Halo decode and prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/47695) · state: open · merged: False

## Original PR description

Co-author: @clintg6  @peizhang56

## Motivation

On `main`, `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16` does not load. It is a Quark AWQ export (dense, int4 weight-only, group 128), and Quark has no int4 weight-only scheme, so loading raises `NotImplementedError: No quark compatible scheme was found`. #41389 and #47408 added W4A16 execution for Quark MXFP4 MoE checkpoints only.

On a Strix Halo APU (gfx1151, Radeon 8060S, RDNA3.5, 256 GB/s LPDDR5X), single-stream decode with the DFlash2 drafter is memory-bound, and the generic kernels run well below the memory roof:

- At M <= 8, W4A16 GEMMs read weights at 40-70 GB/s.
- Target-verify attention walks the cached prefix once per query block; the split-KV verify kernels are gfx95-only.
- Without aiter or vllm, `GemmaRMSNorm` falls back to an 11-op eager chain: about 1,400 of the about 2,600 kernel launches in one 8-token verify step (counted from the forward code).

This PR adds the Quark int4 W4A16 scheme for ROCm, gfx1151 kernels for those paths, and two exact one-kernel replacements on HIP fallback paths.

## Modifications

### Design

- One gate: every gfx115x path checks `use_gfx115_kernels()` (`srt/utils/common.py`): `is_gfx115_supported()` (RDNA3.5, the same check #46327 uses) and the kill switch `SGLANG_DISABLE_GFX115_KERNELS` not set, read once. The kernels were tuned and measured on gfx1151 (Strix Halo); the other gfx115x parts share the ISA. Each kernel module also has a `covered()` predicate that admits only measured shapes; anything else falls back to the existing code.
- Decisions are made at init where possible: the Quark scheme decides at weight load (including whether the Gluon kernel is usable, see below), and the Triton backend's verify path decides in `__init__`.
- Generic layers are untouched: unquantized linears, the LM head and DFlash's candidate ranking keep their `main` code paths. Only the Quark int4 scheme reaches the gfx1151 GEMMs, and one early return in the Triton backend sends verify attention to its kernel.
- The kernels live in arch-named files under `kernels/ops`, like the existing `*_gfx950` and `*_sm100` files, and no generic function signature gains an arch parameter.

### Quark int4 W4A16 scheme (ROCm)

- `QuarkConfig._is_int4_w4a16` selects `QuarkW4A16Int4` (`srt/layers/quantization/quark/schemes/quark_w4a16_int4.py`) on HIP for int4, symmetric, per group of 32/64/128, static, weight-only quantization. On CUDA it returns False, so CUDA behaves as on `main`. The scheme rejects asymmetric checkpoints. Their zero points would need repacking and a wrapped loader in the fused GDN projection, and there is no checkpoint to test them.
- Quark stores signed codes in AWQ packing. At load the weights are repacked once to `[N, K / 8]` with unsigned codes and zero point 8 (`repack_awq_w4_to_skinny(..., signed=True)`), which is lossless.
- The GEMM is a Triton skinny GEMM (`kernels/ops/quantization/w4a16_skinny_triton.py`) with generic block sizes by shape and a gfx1151 config table. On gfx1151 with symmetric group-128 weights, the small-M and prefill kernels below take the shapes they cover.
- `qwen3_5.py`: the fused GDN projection loader splits packed int4 tensors in packed units.
- Credit: the Quark int4 scheme, `_is_int4_w4a16`, the skinny GEMM with its AWQ repack kernels and gfx1151 config table, and the `qwen3_5.py` loader fix start from Clint Greene's Strix Halo branch ([clintg6/sglang@3c8a486](https://github.com/clintg6/sglang/commit/3c8a486f63b91733df8091758cc75cc53ff49345)), whose Triton GEMM is adapted from vLLM's (vllm-project/vllm#37352). This PR drops the GPTQ parts and the HIP `wvSplitK` kernels of that branch, restricts the scheme to ROCm, and adds the gfx1151 kernels and the row pad.

### gfx1151 kernels

- W4A16 small-M GEMM (`kernels/ops/quantization/w4a16_small_m_gfx1151.py`): a Gluon WMMA kernel for at most 16 rows (decode, a DFlash verify block). The int4 codes become bf16 WMMA operands with one `and_or` per register: `(w >> 4i) & 0x000F000F | 0x43004300` is bf16 `128 + q`. Weights and scales are prefetched into loop-carried registers and no load is masked. Split-K is capped at 2, so the fp32 atomic sum is order-independent. It reads at 165-190 GB/s on the Qwen3.8 projections at M = 8. It needs Triton >= 3.7 (`AMDWMMALayout` with register and warp bases); the Quark scheme checks this once at load and otherwise logs a warning and leaves small-M calls to the skinny GEMM. The public gfx1151 images ship Triton 3.7.
- W4A16 prefill GEMM (`kernels/ops/quantization/w4a16_prefill_gfx1151.py`): the same operand trick in `tl.dot`, from 256 rows, bf16 activations.
- int4 row pad (`pad_rows` in `w4a16_skinny_triton.py`, applied when Quark W4A16 weights load on gfx1151): rows read together alias onto the same L2/MALL channels. A 128 B pad per row makes the prefill GEMM 1.10x and an 8-row verify step's small-M GEMMs 1.06x faster, summed over the Qwen3.8 projections (up to 1.2x on `down` and `o_proj`); results are bitwise equal with and without it. This is the int4 counterpart of #46327 for bf16. The three W4A16 kernels take the row stride from the tensor.
- Verify attention (`kernels/ops/attention/verify_attention_gfx1151.py`, called from the Triton backend's `forward_extend` in TARGET_VERIFY): one program per (request, kv head, split) reads its share of the prefix once for all draft tokens and q heads. Numerics follow `extend_attention_fwd`: fp32 online softmax, with `p` rounded to bf16 for PV. It runs only for page size 1, full-attention layers, no KV id translation, causal attention, dense q and o, contiguous bf16 KV caches, and none of soft cap, sinks, custom mask, sliding window or KV descale.
- GDN prefill: a grouped three-head `chunk_fwd_o` kernel for the Qwen3.5/3.8 head ratio (`fla/chunk_o.py`) that computes the chunk's `q·kᵀ` once for the three value heads sharing a q/k head, and head-major launch order for `chunk_gated_delta_rule_fwd_kkt_solve_kernel` and `recompute_w_u_fwd_kernel` (`fla/chunk_fwd.py`, `fla/wy_fast.py`), so concurrently running programs read the same token rows.

### HIP without aiter or vllm (exact one-kernel replacements of eager fallbacks)

- `GemmaRMSNorm.forward_hip` calls the Triton `gemma_fused_add_rmsnorm` / `gemma_rmsnorm` instead of `forward_native`. Those kernels were added for MiniMax-M3 in #28715 (moved to `kernels/ops` in #32045), and `main` uses them only when aiter is on. The new `round_sum=True` normalizes the residual sum rounded to the activation dtype, as `forward_native` does. It is bitwise equal on the tested shapes, and goes from 24.5 to 3.2 us per call in a CUDA graph on gfx1151. This complements #45540, which replaces the same fallback for `RMSNorm` with `torch.nn.functional.rms_norm`; Qwen3.5/3.8 use `GemmaRMSNorm`, whose eager path rounds the residual sum and applies `1 + w` in fp32, so reusing the existing Triton kernel keeps it bitwise equal.
- `_GDN_FUSED_QKVZBA_RATIOS` includes head ratio 3 on HIP without aiter. The fused split kernel is from #34421; ratio 3 was enabled for CUDA in #34859 and for AMD with aiter in #44302. It is bitwise equal to the unfused split.

## Accuracy Tests

Setup: Radeon 8060S (gfx1151), Windows 11 with WSL2, ROCm 7.2.4, image `rocm/sgl-dev:v0.5.19-rocm724-gfx1151-20260914`.

Server (CUDA graphs on):

```bash
SGLANG_MAMBA_SSM_DTYPE=bfloat16 python3 -m sglang.launch_server \
    --model-path amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16 \
    --served-model-name qwen38-awq \
    --attention-backend triton \
    --host 127.0.0.1 --port 30000 \
    --mem-fraction-static 0.85 \
    --max-running-requests 4 \
    --chunked-prefill-size 4096 \
    --max-total-tokens 131072 \
    --reasoning-parser qwen3 \
    --speculative-algorithm DFLASH \
    --speculative-draft-model-path incoai/Qwen3.8-27B-DFlash2 \
    --speculative-draft-attention-backend triton \
    --speculative-num-draft-tokens 8
```

GSM8K:

```bash
python3 -m sglang.test.few_shot_gsm8k \
    --host 127.0.0.1 --port 30000 \
    --num-questions 200 --num-shots 5 --parallel 4 \
    --max-new-tokens 512 --temperature 0
```

| | `main`, bf16 `Qwen/Qwen3.8-27B` | int4, `SGLANG_DISABLE_GFX115_KERNELS=1` | int4, this PR |
| --- | --- | --- | --- |
| GSM8K, 5-shot, 200 questions | 0.980 | 0.965 | 0.965 |

`main` cannot load the int4 checkpoint, so its column serves the bf16 model the checkpoint was quantized from, using the same command. The drop from 0.980 to 0.965 is the accuracy cost of the Quark int4 export. On the same int4 checkpoint, the gfx1151 kernels do not change accuracy. After the review changes, both int4 arms again gave 0.965 on `rocm/sgl-dev:v0.5.23-rocm724-gfx1151-20261102`.

Unit tests, 94 passed on gfx1151 (`rocm/sgl-dev:v0.5.23-rocm724-gfx1151-20261102`):

- Registered for AMD CI (they cover code that runs on any ROCm GPU):
  - `test/registered/kernels/ops/quantization/test_w4a16_skinny_triton.py`: the AWQ -> skinny repack against a torch reference (signed and unsigned codes), and the skinny GEMM, with and without the row pad, against a dequantized matmul at M = 1 / 8 / 33 / 300;
  - `test/registered/kernels/ops/layernorm/test_gemma_rmsnorm_round_sum.py`: the Gemma norm against eager;
  - `test/registered/kernels/ops/attention/test_gdn_fused_split_ratio3.py`: the ratio-3 split against the unfused split.
- `test/manual/test_gfx1151_small_m_kernels.py`, which skips on anything but gfx1151:
  - the small-M GEMM over shapes and M in {1, 5, 8, 16}, padded and unpadded (bitwise equal), and its fallback to the skinny GEMM when Triton is older than 3.7;
  - the int4 quantizer round trip, the prefill GEMM and the skinny GEMM on padded rows;
  - verify attention against a torch reference with scattered KV slots, batch 1 and 2, for (q heads, KV heads, head dim, draft tokens) = (24, 4, 256, 8), (32, 4, 128, 8), (12, 2, 128, 4), (8, 8, 64, 8), and its rejection of a q sliced from a fused qkv buffer;
  - the GDN chunk forward at Qwen3.8 shapes with the head-major grids and the grouped `chunk_fwd_o` against the default kernels.

Verify attention against the generic kernel (Qwen3.8-27B attention shapes: 24 q heads, 4 KV heads, head dim 256, 8 draft tokens, scattered KV slots). Both kernels get the same cache and inputs and are compared with an fp32 reference; they are equally close to it:

## Speed Tests and Profiling

End to end, same server and GSM8K setup as above, single request:

| Metric | `main`, bf16 `Qwen/Qwen3.8-27B` | int4, `SGLANG_DISABLE_GFX115_KERNELS=1` | int4, this PR |
| --- | --- | --- | --- |
| Decode tok/s, short prompt | 5.64 | 18.32 | 29.82 |
| Decode tok/s, 8.7k-token context | 5.22 | 15.13 | 30.91 |
| Decode tok/s, 39k-token context | 3.75 | 6.82 | 21.49 |
| HumanEval+ greedy, tasks 114/0/15, thinking on (weighted tok/s) | 7.12 | 21.12 | 32.95 |
| Prefill tok/s, 1k / 4k / 16k | 175 / 138 / 127 | 240 / 119 / 112 | 410 / 367 / 337 |
| TTFT, 8.7k-token prompt | 62.3 s | 71.8 s | 24.0 s |

- `SGLANG_DISABLE_GFX115_KERNELS=1` runs this PR's Quark scheme with the generic skinny GEMM configs and the two HIP fallbacks, and none of the gfx115x kernels.
- The last column was measured on `main` at 1813806, the other two on an earlier `main` (2c6b95e), all on `rocm/sgl-dev:v0.5.19-rocm724-gfx1151-20260914`. HumanEval tok/s depends on the greedy outputs and acceptance lengths, which differ between the two bases.
- These runs predate the review changes, which removed a bf16 small-M GEMM for unquantized linears and the LM head (hipBLASLt was as fast or faster once weights are streamed). A rerun after the review changes gave a similar speedup over `SGLANG_DISABLE_GFX115_KERNELS=1`.
- Decode tok/s is from stream timestamps with TTFT excluded, on fixed real-text prompts at 0 / 8k / 32k tokens of context with 256 output tokens. Prefill is TTFT on fresh random ids with one output token, median of 2 after a warmup.
- The server processes were pinned to a few CPU cores with `taskset` after startup, which keeps the HIP runtime's busy-waiting threads from taking power from the GPU on this APU. Under WSL, `--max-total-tokens 131072` keeps verify time flat; with the default 650k-token pool it alternates between about 89 and 100 ms.
