# [OpenAI] Let a named tool_choice keep every tool in the prompt

[Upstream PR](https://github.com/sgl-project/sglang/pull/42207) · state: open · merged: False

## Original PR description

## Motivation

This pull request adds an opt-in switch, `SGLANG_NAMED_TOOL_CHOICE_KEEPS_TOOLS`. With the switch on, a chat request whose `tool_choice` names a function keeps every request tool in the prompt. The request then extends the prompt of the turns before it and reuses their prefix cache.

It also fixes the legacy structural tag, which accepted a call to any request tool for a named `tool_choice`. Now the first call must be the named tool. This fix is not behind the switch. It changes the default grammar of the parsers on that path, and it is the main risk of this pull request.

Background: when `tool_choice` names a function, the chat endpoint renders only that tool into the chat template. Chat templates that write the tools at the start of the prompt (GLM, for example) then produce a prompt that shares only a short prefix with the turns before it.

Our case: an agent workload runs long tool-calling sessions with 81 tools and `tool_choice` `auto`. At the turn limit, the harness wants to force one tool by name. With GLM-5.3-Flash, that single request reads the whole session again.

## Modifications

- `SGLANG_NAMED_TOOL_CHOICE_KEEPS_TOOLS` (default off). When it is on, a request with a named `tool_choice` renders every request tool into the chat template, as a request with `tool_choice` `auto` does.
- The switch applies only when the request has an output constraint. Parsers that build no output constraint for a named tool (`hunyuan`, `muse`, `spark25`) keep the one-tool prompt. There the prompt is the only thing that selects the tool.
- The legacy structural tag lists only the named tool when `tool_choice` names one. Before, it listed every tool. This affects `apertus2509`, `deepseekv3`, `deepseekv31`, `hermes`, `inkling`, `interns1`, `llama3`, `mistral`, `qwen`, `qwen25` and `trinity`. It does not depend on the switch, and the switch needs it.
- Without the switch, the rendered prompt does not change.
- One row in the environment variable reference, and unit tests (see Accuracy Tests).

Scope: the Python HTTP server, for prompts built by a Jinja chat template or the Inkling encoder. The DeepSeek and Kimi K3 encoders already render every request tool. The gRPC gateway (it has its own filter) and the Rust server are not changed.

I made it a switch because it changes the model input on a turn that names a tool, and I tested one model family only. I can change it to the default, a server flag, or a request field.

Measurement setup: SGLang v0.5.20 with a backport of the prompt change (every tool stays in the prompt for a named `tool_choice`), an FP8 GLM-5.3-Flash checkpoint, one node with 8 B200 GPUs and two servers of 4 GPUs each, `--tool-call-parser glm47`.

## Accuracy Tests

The model weights and kernels are not touched.

- Reply format: with every tool kept in the prompt, the reply to a request that forces the conclusion tool still has reasoning followed by a call to that tool (on the backport). This is a format check on a synthetic conversation. It is not a quality evaluation.
- Unit tests in `test_serving_chat.py`: the default renders only the named tool. With the switch, the template gets the same tool list as a request with `tool_choice` `auto`, and the structural tag has only the named tool (`hermes`). With the switch and no output constraint (`hunyuan`), the prompt keeps only the named tool. The last two tests fail without the structural tag fix and the constraint check.
- Parser sweep: I ran `_process_messages` for every tool-call parser name, with the switch on and a request that names one of several tools. `hunyuan`, `muse` and `spark25` get no constraint and the one-tool prompt. Every other name gets every tool in the prompt and a constraint that does not mention another tool.
- Grammar check (strings, no tokenizer): for each parser on the legacy tag path, the compiled grammar accepts the named tool as the first call and rejects another tool there. With `tool_choice` `required` it still accepts every tool.
- Limit: on the legacy tag path, text after a call is free, as before this pull request. In the same check, a second call to another tool passes for `inkling`, where each tool has its own trigger. It also passes for `llama3` and `deepseekv3` when the second call has no trigger token. The parser returns that call.
- Local run on macOS without a GPU: the command below passes, and pre-commit passes on the changed files.

```bash
python -m pytest test/registered/unit/entrypoints/openai/test_serving_chat.py test/registered/unit/function_call
```

## Speed Tests and Profiling

The probe numbers are in the table above. The probe sends one request at a time to an idle server. Each request follows a long cached tool-calling conversation with 81 tools. I have no complete measurement of the full tool list on a server that renders only the named tool, so the table compares with a request that sends only the named tool. ## Not verified

- Answer quality with the full tool list on a turn that names a tool. I checked only the reply format.
- Whole sessions with a named `tool_choice`. The session runs kept the tool list with `tool_choice` `auto` on the last call.
- A build of this branch on a live server, and a stock build. The probe ran on a v0.5.20 backport of the prompt change, before the structural tag fix and the constraint check were added. The fix and the check do not act on the `glm47` path.
- Models and parsers other than GLM-5.3-Flash with `glm47` (unit tests only), and hardware other than B200 GPUs.
- A second call to another tool on a live model (see the limit above).
- The cost of the longer prompt. With the switch on and a cold cache, a request that names a tool prefills more tokens.
- Upstream CI. No test job has run yet, because the gate blocks draft pull requests.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Keep the one-tool prompt for non-forcing constraints**

When `SGLANG_NAMED_TOOL_CHOICE_KEEPS_TOOLS=1` is used with the llguidance grammar backend and a parser on the legacy-tag path, this non-null check is too weak: `llguidance_backend.dispatch_structural_tag` rebuilds the grammar from only `structures` and `triggers` (`python/sglang/srt/constrained/llguidance_backend.py:300-321`), dropping the tag's `at_least_one=True`, so it does not force a named call. The new branch nevertheless advertises every tool; with a per-tool trigger such as Inkling's, another advertised tool can then pass as unconstrained text and be parsed as a call, violating the named `tool_choice`. Keep the filtered prompt unless the active backend honors the forcing property, or implement `at_least_one` in llguidance.
