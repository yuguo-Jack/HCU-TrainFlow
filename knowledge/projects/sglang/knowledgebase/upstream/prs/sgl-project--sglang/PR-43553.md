# [Bugfix] DeepSeekV3 streaming: emit every complete tool call in a buffered backlog

[Upstream PR](https://github.com/sgl-project/sglang/pull/43553) · state: open · merged: False

## Original PR description

## Motivation

With `--tool-call-parser deepseekv3`, when one streaming increment carries more than one complete tool call — a coalesced backlog from `_coalesce_streaming_chunks` (`python/sglang/srt/managers/tokenizer_manager.py:1803`) or a large `--stream-interval` — `parse_streaming_increment` emits only the last call, at `tool_index` 0. Every earlier call is silently dropped and never reaches the client.

Fixes #43523.

## Root cause

The streaming regex uses greedy `(.*)` groups:

````python
r"<｜tool▁call▁begin｜>(.*)<｜tool▁sep｜>(.*)\n```json\n(.*)\n```.*"  # re.DOTALL
````

On a buffer with two complete calls, the match extends to the last `\n```\n`, so `group(2)` / `group(3)` return the second call's name and arguments and the first call is dropped. Two more defects share the same root cause:

- Two calls arriving in separate increments: the same greediness mis-attributes the second call's arguments to the first.
- A single call whose JSON completed inside its increment keeps waiting for the next delta, but the serving layer feeds one delta at a time with no end-of-stream flush — the arguments are stranded forever.

## Modifications

- Match the **first** complete call with lazy quantifiers (`(.*?)`), so the name and arguments always come from the same call.
- Drain the buffer in a loop: after the name is emitted, `continue` so the arguments stream in the same increment; after a call completes, consume it from the buffer and `continue` to the next one; stop when the remaining call is still incomplete (the `_is_complete_json` guard). The buffer strictly shrinks on each consumed call, so the loop terminates.
- The usual multi-delta path keeps its incremental argument-diff behavior.

## Verification

- 14-scenario probe (coalesced / split / straddling increments, multi-call buffers, ground truth checked against `detect_and_parse`): upstream main `260551ebe9` fails 13/14; this patch passes 14/14. Negative control by reverting only the detector file restores the 13 failures (red → green → red → green).
- `pytest test/registered/unit/function_call/test_function_call_parser.py`: 255 passed; `TestDeepSeekV3Detector`: 6 passed (1 pre-existing + 5 new regression tests: two complete calls in one increment; complete call followed by an incomplete tail; a single call complete within one increment; two calls across increments (argument attribution); closing fence + `<｜tool_call_end｜>` split across deltas).
- `ruff check --select=F401,F821,F823,UP037` (the repo gate) and `ruff format --check` with the repo-pinned v0.15.1: clean.
- Micro-benchmark of `parse_streaming_increment` (µs per increment): plain text 2.3 (main: 2.5); single call 9.2 (main: 8.1); two calls 14.5 (main: 10.6 — but main drops the second call there, so that pair is not like-for-like). Cost is linear in the number of completed calls per increment, as expected.

No GPU is needed for this code path (detector-level parsing); CI covers the rest.
