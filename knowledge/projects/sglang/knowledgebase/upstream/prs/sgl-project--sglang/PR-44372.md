# [Fix] mem_cache: Fit automatic hybrid speculative state caches to available memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/44372) · state: open · merged: False

## Original PR description


## Motivation

Fixes #44355.

Adding `--disable-radix-cache` can make a working hybrid attention model failduring cache sizing when speculative decoding is enabled.

If `--max-running-requests` is unset, speculative decoding defaults it to 48. With radix caching disabled, the cache planner treats that default as a user-supplied limit. The saved state and temporary draft state for those requests can consume all the memory left for caches.

Without speculative decoding, the request limit stays unset and the plannerfits the state cache to available memory. It also skips the temporary draft states.

This change uses the existing memory-based sizing path when that automatic state cache would leave no room for the KV cache.

The trigger for this issue depends on the state size and memory budget, not just the model's parameter count.

## Modifications

Track whether the user set `--max-running-requests`, so cache sizing can distinguish an explicit limit from the automatic default. Store this through the existing derived schedule settings. When radix caching is disabled and the automatic state cache would leave no KV memory, use the existing memory-based sizing path.

Explicit request limits, explicit state-cache limits, and automatically chosen pools that already fit keep their current sizing. Non-speculative, radix-enabled, ReplaySSM, and PD-prefill paths that skip intermediate state are unchanged. No model code, forward kernels, public signatures, or speculative defaults change.

Add a registered CPU test that catches the original failure, with checks for an automatic pool that already fits, explicit request limits (including 48), and an explicit state-cache limit.

[by Claude Code] **Severity: functional | Confidence: High**

**Issue**

`auto_fit_spec_state` turns on only when the default pool needs all of `total_rest_memory`. Just below that point, the 48-slot pool stays and KV gets almost nothing. More memory then gives far less KV.

**Example**

With the new test's Qwen3-Next shapes, `_handle_max_mamba_cache(24.68)` leaves 13.09 GiB for KV, but `24.70` leaves 0.018 GiB. That tiny pool caps `max_req_len` in `tp_worker.py`, or fails `MemoryPoolConfig.__post_init__` if it rounds to zero tokens.

**Fix**

Compare against the auto-fit Mamba share, `total_rest_memory * r / (1 + r)` with `r = mamba_full_memory_ratio`. With that change, the four new tests still pass locally and KV grows with memory. It also shrinks some pools that fit today (30 GiB: 48 to 27 slots), like the radix-enabled path does. Add a 24.70 GiB case.

[by Claude Code] **Severity: style | Confidence: High**

**Issue**

`max_running_requests_is_explicit_of` adds `getattr(record, "_raw_input", None)`. New defensive `getattr` is not allowed, and this one is not needed. `resolve_once` freezes the record during resolution, and defaults such as the speculative 48 go through `declare_resolution`, not the record. So `record.max_running_requests` already equals `_raw_input["max_running_requests"]`.

**Fix**

```python
def max_running_requests_is_explicit_of(cfg) -> bool:
    from sglang.srt.arg_groups.model_override_base import record_of

    return record_of(cfg).max_running_requests is not None
```

With this change, the new tests and `test_mamba_donated_alloc_ratio.py` still pass locally.
