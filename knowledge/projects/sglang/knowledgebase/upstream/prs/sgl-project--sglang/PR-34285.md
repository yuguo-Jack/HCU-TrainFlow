# [speculative] Support DFlash speculative decoding under PD disaggregation

[Upstream PR](https://github.com/sgl-project/sglang/pull/34285) · state: closed · merged: False

## Original PR description

## Motivation

  DFlash speculative decoding does not engage on the decode side under PD disaggregation.

  Before this change, `SpeculativeAlgorithm.build_disagg_draft_input()` handles EAGLE and DSpark but has no DFLASH branch. For DFLASH it returns `None`, so `decode_schedule_batch_mixin.py` takes the non-speculative fallback:
  `spec_info` is not assigned, the last target token is relayed through the non-speculative path, and DFlash draft decoding never starts. No explicit error is raised.
  
  Thanks to @moehanabi for identifying this issue in #28390 and proposing the original fix direction.
  
  ## Changes

  - Add the missing `is_dflash()` dispatch to `SpeculativeAlgorithm.build_disagg_draft_input()`.
  - Reuse the existing upstream `build_dflash_family_disagg_draft_input()` helper unchanged.
  - Add a registered 2-GPU PD accuracy test with prefill on GPU 0 and decode on GPU 1.
  - Use Llama-3.1-8B and its matching DFlash draft for the registered GSM8K test.
  - Set `SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1` on both PD sides because the draft checkpoint has a shorter configured context length than the target checkpoint.
  
  The runtime change is intentionally limited to the missing DFLASH dispatch.

  ### Earlier accuracy evidence
  
  Before the latest branch update, an additional 80-example GPQA-diamond comparison was run with Qwen3.6-35B-A3B and a matching DFlash draft using `max_tokens=8192`, `temperature=0`, and 16 client threads.

  | Setup | GPQA | Output tok/s | Wall time |
  |---|---:|---:|---:|
  | Single-node, no speculative decoding | 0.750 | 1324 | 339.1s |
  | Single-node, MTP | 0.750 | 1227 | 375.5s |
  | Single-node, DFlash | 0.7625 | 1364 | 339.5s |
  | Two-node PD, DFlash | 0.738 | 1344 | 330.4s |

  The PD result differs from the non-speculative single-node reference by one answer out of 80. This sample is too small to establish an accuracy regression, and no measurable loss was observed in this run. `KVTransferError`
  remained zero throughout the 80-question evaluation.

  The observed PD output throughput was approximately 1.5% lower than the single-node DFlash reference. This is a single comparison rather than a repeated performance benchmark, so it should not be interpreted as a precise
  performance estimate.

  ## Scope
  
  This PR only adds the missing DFLASH dispatch for PD decode and its registered coverage. It does not change:

  - DFlash acceptance logic
  - Speculative sampling behavior
  - KV-transfer implementation
  - TP synchronization
  - The shared DFlash PD input-construction helper

Thanks for the independent validation and for preparing the patch.

1. I don't think we should fall back to `eagle_prepare_for_decode` here. For a real relayed DFlash request, this PR constructs `DFlashDraftInputV2` before decode preparation. If `spec_info` is still `None`, that indicates a broken DFlash state-construction path and should remain visible as an error rather than silently continuing with EAGLE-specific allocation and bookkeeping. Idle execution should also use DFlash's own idle representation instead of the EAGLE path. In addition, this branch uses `is_dflash_family()`, so the fallback would also change the DSpark `None` path.

2. I agree that checking the decode acceptance length would strengthen the registered test. I think it can be added as a small check at the end of the existing 200-example GSM8K test: query the decode `/server_info` endpoint and verify that `avg_spec_accept_length > 1`. This avoids adding a separate request loop, polling logic, and `/metrics` fallback.

3. I have not observed the context-length-related Mooncake failure in my environment. The registered Llama-3.1-8B target/draft test passed locally on 2 GPUs without `--context-length 8192`, and the current source also passed my 4P+4D Mooncake/RDMA smoke test. If you are willing, could you try the same registered target/draft models and test configuration without the explicit context bound and share the transfer error or startup memory logs if it still reproduces? That would help determine whether 8192 is required for this CI test or specific to the Qwen3.8-27B setup.

I'm very open to incorporating your helpful code contribution. If you'd like, please open a PR against `simple-sun/sglang:dflash-pd-disagg` with the focused `/server_info` acceptance-length check and any context-bound change supported by the same-model reproduction. I'll review and merge the changes that fit this PR's scope, which will also preserve your authorship directly.

- Leslie360 · comment · 2026-09-15T02:51:13Z · [source](https://github.com/sgl-project/sglang/pull/34285#issuecomment-5673931796)

Two None-guards needed for DFLASH spec_info during PD disaggregation warmup

While validating DFLASH under PD disaggregation we hit two crashes that both stem from the same window: during decode-side warmup / idle batching, a batch can reach DFLASH code paths before any draft verify input is attached (`spec_info is None`).

1. **`DFlashDraftInputV2.merge_batch(spec_info)`** dereferences `spec_info.nxt_kv_lens_cpu` unconditionally. When a warmup merge carries `spec_info=None` this raises `AttributeError` on `NoneType`. Guard: return early when `spec_info is None` — there is nothing to merge.

2. **`spec_prepare_for_decode(batch)`** calls `batch.spec_info.prepare_for_decode(batch)` whenever `batch.spec_algorithm.is_dflash_family()`. During PD decode warmup an idle/decode batch reaches here before any draft verify input is attached. The dflash worker itself already creates an idle input on `None` (dflash_worker_v2), so skipping the headroom prep when `spec_info is None` is safe and matches that path; a real speculative batch always has spec_info set.

Both guards are one-liners; patch available (validated on our PD+DFLASH deployment: before, decode-side warmup crashes with the traces above; after, warmup passes and speculative serving proceeds normally).

Happy to send a PR if maintainers prefer it land ahead of / separately from #34285.
