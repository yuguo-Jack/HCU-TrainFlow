# [Fix] Protect GDN state pool from SM90 FlashInfer decode padding

[Upstream PR](https://github.com/sgl-project/sglang/pull/44014) · state: open · merged: False

## Original PR description

## Motivation

On SM90, FlashInfer GDN decode still gathers and scatters recurrent states with `ssm_states[cache_indices]`. When CUDA Graph padding supplies `-1`, PyTorch interprets it as the last pool slot. That slot is allocatable, so a padded row can overwrite another request's recurrent state. The gathered batch also hides the negative padding sentinel from FlashInfer.

We observed intermittent incoherent generated text, including U+FFFD replacement characters, with FlashInfer GDN decode and padded decode CUDA Graphs. Requests completed successfully without a server crash. This was observed with SGLang v0.5.20, FlashInfer 0.6.18, SM90 GPUs, and BF16 recurrent states. The same unsafe decode path remains in main at `7ff3a112846a3fcc12a27bba09d644885a226e4d`; the kernel source is identical to the validated snapshot at `17c3b259f5be84638617b4dce345c4b10f47bb2b`.

FlashInfer already supports pool-and-index decode on SM90 ([flashinfer-ai/flashinfer#2521](https://github.com/flashinfer-ai/flashinfer/pull/2521)). Passing the original negative indices lets its kernels apply their padding handling instead of updating an allocatable slot.

Related: [#27905](https://github.com/sgl-project/sglang/pull/27905) also proposes SM90 pool-indexed decode alongside broader MTP and configuration changes. This patch focuses on the decode padding corruption and its regression test, preserving main's existing alignment preparation and fallback checks.

## Modifications

- Use the indexed state-pool interface for SM90 decode, as already done for SM100+.
- Normalize SM90 indices to int32 for the pooled kernel's negative-index branch.
- Keep the existing prefill and MTP routing and state handling.
- Add a synthetic GPU regression test for BF16/FP32 states and int32/int64 input indices. It checks untouched real slots, valid outputs and state updates against an unpadded reference, and changed indices across CUDA Graph replays.

## Accuracy Tests

The regression test was run against the exact main module and the patched module on SM90 with both FlashInfer 0.6.18 and 0.7.1 (main's pinned version). With each version, unpatched main fails all eight dtype/index/mode combinations because an inactive real state slot changes; the patch passes eager execution and graph replay with both index patterns. This tests the main kernel module in isolation, not a full-server deployment of main.

Separate full-server validation on v0.5.20 with FlashInfer 0.6.18 used the equivalent decode-only change. Both runs completed 12,800 requests without request errors. The baseline had seven outputs containing U+FFFD; the patched run had none. This is a corruption check, not a general model-accuracy benchmark.

## Speed Tests and Profiling

In the same full-server validation, decode CUDA Graphs remained enabled. Request latency p50/p95 was 6.105/23.650 seconds for the baseline and 5.703/21.898 seconds with the patch. These are end-to-end observations, not an isolated kernel benchmark.
