# [Fix] openai: Sync token usage for streaming gpt-oss /v1/responses

[Upstream PR](https://github.com/sgl-project/sglang/pull/45395) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45186.

Streaming `/v1/responses` requests using the gpt-oss Harmony parser report
`input_tokens: 0`, `output_tokens: 0`, `total_tokens: 0` in the terminal
`response.completed` event, even though the request generated content.

Root cause: `responses_stream_generator` hands each engine chunk to
`StreamingHarmonyContext.append_output`, and at the end of the stream it
builds the terminal response through `responses_full_generator`, which reads
`context.num_prompt_tokens`, `context.num_output_tokens`, and
`context.num_cached_tokens`. The parent class `HarmonyContext.append_output`
updates those counters from the chunk `meta_info`, but the streaming override
never did — it only fed tokens to the parser and recorded the finish reason —
so the counters stayed at their initial `0`.

## Modifications

- `python/sglang/srt/entrypoints/context.py`:
  - `StreamingHarmonyContext.append_output` now syncs the usage counters from
    each chunk's `meta_info`:
    - `num_prompt_tokens` / `num_cached_tokens`: assigned directly (per-request
      constants, matching the parent's assignment semantics).
    - `num_output_tokens`: only the delta of the cumulative
      `completion_tokens` since the previous chunk is added, mirroring the
      parent's per-turn `+=`. A plain assignment would be wrong for
      multi-chunk streams and a plain `+=` would double-count cumulative
      values, in both `--incremental-streaming-output` modes.
  - New `_last_chunk_completion_tokens` baseline, reset to `0` in `__init__`
    and in the tool-output branch of `append_output`, since a builtin-tool
    call starts a new generation turn whose cumulative `completion_tokens`
    begins from zero again.
- `test/registered/unit/entrypoints/openai/test_serving_responses_stream.py`:
  new `HarmonyUsageCountersTestCase` with three regression tests: cumulative
  chunks, `--incremental-streaming-output` chunks (no double counting), and
  the builtin-tool-turn baseline reset.

## Tests

- Reproduced the issue exactly as described (single `append_output` with
  `meta_info = {prompt_tokens: 5, cached_tokens: 1, completion_tokens: 2}`):
  before the fix the counters stayed `(0, 0, 0)`; after the fix they read
  `(5, 1, 2)`.
- Verified the real `HarmonyContext`/`StreamingHarmonyContext` classes via
  AST extraction executed against stubs (8/8 checks pass): the issue repro,
  multi-chunk cumulative streams, incremental-streaming mode, chunks with
  empty/partial `meta_info`, the builtin-tool-turn reset, finish-reason
  recording unchanged, and the parent class behavior unchanged.
- Added `HarmonyUsageCountersTestCase` to the registered unit tests.
- `ruff check --select F401,F821,F823,UP037`, `ruff format --check`,
  `python3 -m py_compile`, and `git diff --check` all pass on both touched
  files.

Not verifiable on this machine: no GPU/torch/openai-harmony here, so the
end-to-end streaming path against a live gpt-oss model was not run; the
per-chunk `meta_info` keys used (`prompt_tokens`, `cached_tokens`,
`completion_tokens`) were confirmed against the scheduler output in
`tokenizer_manager.py`, and the wiring from `responses_stream_generator`
through `responses_full_generator` was verified by source inspection.
