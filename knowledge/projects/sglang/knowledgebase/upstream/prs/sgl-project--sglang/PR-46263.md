# [Perf] [NVIDIA] deepseek-v4.1: Default aggregated servers to MegaAttention only when each rank holds 64 query heads

[Upstream PR](https://github.com/sgl-project/sglang/pull/46263) · state: closed · merged: True

## Original PR description

## Motivation

Since #43922, `--dsv4-attn-backend auto` resolves to `flashmla_mega` for DeepSeek-V4.1 on SM100/SM103 with an `fp8_e4m3` KV cache, whatever the attention TP width. MegaAttention always runs a 64-head tile (`kernel_num_heads = 64 if n_local_heads <= 64 else 128`), and `pack_query` zero-fills the missing heads. DeepSeek-V4.1-Flash has 64 query heads, so TP2 (32 heads per rank) runs 2x and TP4 (16 heads per rank) runs 4x the attention work it needs. The `flashmla` path has a small-batch SM100 kernel specialized for 16 and 32 heads (`can_use_swapab_attention`), so it wins at these widths.

At TP4 the target-verify graph of one decode step gains the MegaAttention kernel (~1.45 ms over 40 layers) and the fp8 `wo_a` GEMM it feeds (~0.29 ms). It drops the FlashMLA partial/combine, fused `wo_a`, Q-norm-RoPE and quant kernels (~0.85 ms), so each step is ~1.1 ms slower.

## Modifications

- For an aggregated server (`--disaggregation-mode null`), `_default_dsv4_attention_backend` returns `flashmla` when attention is tensor-parallel across ranks (`attn_tp_size > 1`). This mirrors `_kernel_num_heads`, which pads to the 64-head tile exactly when `attn_tp_size > 1`.
  - TP1, DP attention at attention TP 1 and prefill CP are not sharded, so they still resolve to `flashmla_mega`.
  - Prefill CP counts as attention TP 1 directly, because `validate_deepseek_v4_cp` sets `attn_cp_size` only after this default runs.
  - An explicit `--dsv4-attn-backend` is unchanged.
- PD roles keep today's default (#45075): `flashmla_mega` on both prefill and decode, whatever their attention TP size.
  - The two backends do not store the same KV layout. `SGLANG_DSV4_KV_LAYOUT` defaults to `v4`, so `flashmla` stores V4, while `flashmla_mega` forces V4.1.
  - Gating PD roles by head count would let a TP prefill and a DP-attention decode resolve differently. They would then fail the KV-layout handshake: on GB300 such a pair failed its first request with `KV layout mismatch: prefill server has kv_layout=v4,c1:v4,c2:v4, but decode server has kv_layout=v41,c1:v41_fp4,c2:v41_fp4`.
- The `--dsv4-attn-backend` help text describes the new default. The cookbook PD note now says both roles run MegaAttention whatever their attention TP size; it previously said "as a single server does".

## Accuracy Tests

The change selects an existing backend; no kernel or model code changes. Paired runs:
- Aggregated TP4 EP1 server, same image as below, DSpark with real acceptance.
- `sgl-eval` 0.1.3, GSM8K, all 1319 examples, `--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash` (temperature 1.0, top_p 0.95, thinking, reasoning effort high), 128 threads.
- The two servers differ only in the attention backend.

| backend | GSM8K 1319 | errors / truncated | mean output tokens |
|---|---|---|---|
| `auto` with this PR (resolves to `flashmla`) | **96.82%** | 0 / 0 | 266.7 |
| explicit `flashmla_mega` (main's `auto` here) | 96.59% | 0 / 0 | 270.5 |

The 0.23-point gap is 3 of 1319 questions, inside one standard error (about 0.5 points at this score).

## Speed Tests and Profiling

DeepSeek-V4.1-Flash FP4 on GB300, `lmsysorg/sglang:nightly-dev-cu13-20261021-c1c287a4`. Aggregated serving behind the Dynamo frontend, DSpark (MTP), agentic multi-turn coding trace replay, full warmup, then a 60-minute measurement window. One server per row, with the same recipe except `--dsv4-attn-backend`. `auto` resolved to `flashmla_mega` on this image.

| Point | Backend | Requests / errors | Total tok/s/GPU | Interactivity P50 / P90 (tok/s/user) | TTFT P90 | Clean decode step, 1 / 4 running |
|---|---|---|---|---|---|---|
| TP4, conc 4 | `auto` (mega) | 751 / 0 | 9,881 | 537.6 / 465.8 | 0.288 s | 6.41 ms / - |
| TP4, conc 4 | `flashmla` | 741 / 0 | 9,736 | **683.7 / 590.8** | 0.254 s | **5.05 / 6.72 ms** |
| TP4, conc 16 | `auto` (mega) | 2671 / 0 | 29,051 | 473.8 / 403.7 | 1.888 s | 6.40 / 7.85 ms |
| TP4, conc 16 | `flashmla` | 2714 / 0 | 29,371 | **593.2 / 468.6** | 1.401 s | **5.06 / 6.84 ms** |
| TP2 EP2, conc 16 | `auto` (mega) | 2662 / 0 | 57,766 | 376.2 / 309.0 | 1.310 s | 7.19 / 9.67 ms |
| TP2 EP2, conc 16 | `flashmla` | 2675 / 0 | 57,999 | **414.8 / 315.4** | 1.176 s | **6.07 / 9.22 ms** |

The decode step is taken from scheduler log intervals with no prefill batch: `running x accept length / generation throughput`. P90 interactivity rises 27% (TP4 c4), 16% (TP4 c16) and 2% (TP2 c16, P50 +10%), at matching throughput.

Larger batches, same setup. TP2 c32 uses `--max-running-requests 64`. TP4 c64 uses `--max-running-requests 256` and `--prefill-decode-interval 24`. With DSpark block size 5, every bucket of 9 or more running requests is above the swap-AB row cap, so `flashmla` pads to 64 heads there too:

| Point | Backend | Requests / errors | Total tok/s/GPU | Interactivity P50 / P90 | TTFT P90 | Clean decode step by running requests |
|---|---|---|---|---|---|---|
| TP2 EP2, conc 32 | `auto` (mega) | 4792 / 0 | 120,870 | 282.4 / 220.5 | 1.978 s | 1-8: 9.06 ms, 9-16: 12.82 ms |
| TP2 EP2, conc 32 | `flashmla` | 4817 / 0 | 122,250 | **291.5 / 227.4** | 1.780 s | 1-8: **8.31** ms, 9-16: **12.46** ms |
| TP4, conc 64 | `auto` (mega) | 11501 / 0 | 116,866 | 210.9 / 176.0 | 2.000 s | 1-16: 9.38 ms, 17-32: 12.13 ms |
| TP4, conc 64 | `flashmla` | 11604 / 0 | 118,577 | **220.9 / 184.8** | 1.754 s | 1-16: **8.40** ms, 17-32: **11.57** ms |

The TP4 margin narrows as the batch grows: -10% at 1-16 running, -5% at 17-32, and -4% at 33-48 (steps with prefill, 23.44 vs 22.58 ms).

Fixed batches at TP4 EP1, to cover the high-throughput regime the trace does not reach:
- `bench_serving --dataset-name random-ids`, 4096 input / 1024 output tokens, C requests sent at once, two rounds per C.
- DSpark, simulated acceptance 3.51, `--max-running-requests 256`, `--cuda-graph-max-bs-decode 256`.
- Clean decode step from scheduler log intervals at that running count:

| running requests | `flashmla` | `flashmla_mega` | delta |
|---|---|---|---|
| 57-64 | **17.50 ms** | 18.25 ms | -4.1% |
| 121-128 | **26.48 ms** | 26.98 ms | -1.9% |
| 241-256 | **42.64 ms** | 43.58 ms | -2.2% |

`flashmla` decodes faster at every batch size up to 256. MegaAttention prefills slightly faster (median TTFT at C=128: 4.54 s vs 5.22 s), which leaves end-to-end bench throughput within 1.7% at C=128/256.

Side effects on aggregated TP2/TP4 servers:
- **KV layout:** they now store the V4 KV layout instead of V4.1. The swap-AB kernel reads V4. The KV pool at `--mem-fraction-static 0.8` was 66.86M vs 67.19M tokens (-0.5%) in the fixed-batch runs.
- **Shared HiCache stores:** a HiCache storage backend shared with a V4.1-layout server (a DEP server or a PD role on `auto`) would see a different layout. The store key does not include the layout.

Not measured:
- `--enable-cp-decode-attn-tp` (opt-in), which splits heads across CP ranks at decode. It still resolves to `flashmla_mega`, as on main.

The GB300 TP2 CI suites with `--attn-dp-size 1` now run `flashmla` instead of padded `flashmla_mega`.
