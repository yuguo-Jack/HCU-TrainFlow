# [Fix] benchmark: Keep the Mooncake trace's 512-token blocks in the mooncake dataset

[Upstream PR](https://github.com/sgl-project/sglang/pull/45687) · state: open · merged: False

## Original PR description

## Motivation

A Mooncake trace record (`--dataset-name mooncake`, the FAST'25 release) describes its prompt as a list of 512-token block ids, and two records that share a block id share that part of their prompts. `get_mooncake_request_over_time` expanded every block id to the id and the word "hi" repeated 128 times, about 130 tokens, and ran the text through the chat template. Prompts came out about four times shorter than the trace says, so the attention cost of the long contexts the trace is known for was lost, and the shared prefixes had the wrong lengths too. The warmup request used a different expansion, 512 "hi" per block, so its blocks matched nothing in the replay.

We hit this when replaying the tool-and-agent trace to evaluate a scheduling change: the built-in replay reproduced neither the trace's prefix sharing nor its prompt lengths, so we had to write our own replayer. This change makes `bench_serving` do what the trace file says.

## Modifications

- `MooncakeBlocks` in `python/sglang/benchmark/datasets/mooncake.py` expands a block id to the same 512 token ids for every record, drawn from the model's vocabulary with the block id as the seed, and cuts the prompt to the record's `input_length` (the last block is partial).
- The generator yields token ids with `prompt_len` as their count; the tokenizer only supplies `vocab_size`. `bench_serving` sends a list prompt as `input_ids`, which the `sglang` backend accepts, and the Mooncake generator already runs only with that backend.
- Multi-round sessions keep their shape: round n carries the previous prompt, a placeholder answer of `output_length` tokens, and the query again, as the chat-history version did with placeholder text.
- The warmup request uses the same expansion, so its blocks are the ones the replay later shares.
- One paragraph under the Mooncake example in `docs/docs/developer_guide/bench_serving.mdx`.

The old text expansion is not kept behind an option: its lengths were wrong by a factor of four, so no result produced with it is comparable to one produced after this change either way. The command line is unchanged; anyone comparing against earlier numbers from this dataset should rerun the baseline.

## Notes for reviewers

- 512 deterministic tokens per block id rather than filler text, because the trace defines a block as 512 tokens and `input_length` is only consistent with `hash_ids` at that size. Seeding by the block id makes sharing exact across records, rounds and the warmup without a shared table. Random tokens from the vocabulary are what the `random` dataset sends too.
- Token ids instead of text is fine for what this dataset is for, a scheduling and cache benchmark: prefill cost, prefix hits and KV usage depend on the ids and their sharing, not on whether they spell words.
- The expansion is the one our own replayer used for a 75-row table on Qwen3-8B, where the server's cached-token counts confirmed the sharing (59% of requests in the one-minute windows are returning turns and hit the cache). Through `bench_serving` itself, against Qwen3-8B on an A100 (the first 60 records of the tool-and-agent trace at 15x slowdown): 60 of 60 requests succeeded, 581,461 input tokens in all, 9,691 per request on average, which is the trace's length; 0.41 requests per second; mean TTFT 4.7 s; and the server log shows prefill batches with up to 28,672 cached tokens, the shared blocks hitting the radix cache. Not tested: `--mooncake-num-rounds` above 2 beyond the unit test, and the `synthetic` workload file.

## Tests

`test/registered/unit/bench/test_mooncake_dataset_blocks.py` (CPU): two records sharing block ids get identical leading tokens, one per shared block of 512, and prompts have the record's `input_length`; a second builder expands the ids the same way; the generator's rows carry token ids with their count, and round two carries round one, its placeholder answer and the query again.

Run on an A100 pod with this branch installed at upstream main `da7b97a737`: the three cases pass on the branch; against main's sources the file does not import (`MooncakeBlocks` does not exist there). CI has not run yet (draft).
