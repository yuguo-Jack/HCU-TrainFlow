# [MoE] Extend FlashInfer CUTLASS MoE autotune coverage to prefill chunks

[Upstream PR](https://github.com/sgl-project/sglang/pull/43363) · state: open · merged: False

## Original PR description

## Summary

**TL;DR: This PR enables sglang's startup autotune to tune FlashInfer's CUTLASS MoE kernel for prefill sizes too, not only for decode sizes.** sglang already autotunes this kernel (`cutlass_fused_moe`, FlashInfer's MoE kernel, not its attention backend) at startup, but each call tells FlashInfer to tune only up to its own token count. The startup run is one decode-sized batch, so only decode sizes get a tuned kernel configuration (tactic), and prefill chunks above that size run FlashInfer's untuned fallback tactic (its default kernel configuration). This PR gives FlashInfer one tuning range per server instead: the largest prefill batch the MoE layer sees (chunk size × attention data-parallel size, capped at 8192, FlashInfer's own default range for this call), so the same startup autotune also covers prefill. No new flag, kernel or extra pass. It applies on every GPU this kernel runs on (SM90, SM100, SM110, SM120), where it is the default MoE kernel of DeepSeek-V4.1/V4, Ling-3.0, Nemotron-H, gpt-oss and ModelOpt NVFP4 MoE models (which GPU for which model: Design notes), and to any other MoE model that runs on it. Other MoE kernels and the decode servers of prefill-decode (PD) disaggregation are unchanged. Measured on H200 (SM90).

- **Performance** (H200, medians, newly started servers unless stated; decode ITL is unchanged, since decode batches use the buckets main already tunes):
  - DeepSeek-V4.1-Flash, 8×H200: TTFT for 8000-token prompts **30.3% lower** (573.9 → 400.0 ms), for 32000-token prompts **25.7% lower**; prefill throughput for 8000-token prompts **43.4% higher**.
  - Nemotron-3.5-Lightning-30B-A3B (BF16), 1×H200: TTFT for 8000-token prompts **52.4% lower** (312.6 → 148.8 ms), for 32000-token prompts **49.0% lower**; prefill throughput for 8000-token prompts **113.8% higher**.
  - gpt-oss-20b, 1×H200, `--moe-runner-backend flashinfer_mxfp4` (its default on SM120): TTFT for 8000-token prompts **57.8% lower** (422.0 → 177.9 ms), for 32000-token prompts **52.8% lower**; prefill throughput for 8000-token prompts **143.4% higher**.
  - DeepSeek-V4.1-Flash against a main server that has already served large decode batches (65–128 requests), which switch main's prefill to the 128-token bucket's tactic (Motivation, item 2): TTFT for 8000-token prompts **19.8% lower**.
  - With open PR #42736, which tunes the same sizes with an extra startup pass: adding this PR improves TTFT for 8000-token prompts by **24.7%** against #42736 alone.
- **Accuracy:** unchanged by design: only the tile configuration (tactic) of the same GEMM changes, and one MoE call gives output bit-identical to FlashInfer's fallback tactic at 8192–32768 tokens. GSM8K on DeepSeek-V4.1-Flash and gpt-oss-20b and the DeepSeek-V4-Flash CI GSM8K test all stay within their 95% noise range (Accuracy Tests).
- **Cost:** a longer startup and less free memory. The startup autotune that main already runs takes longer when it has no saved results: 41–42 → 176–177 s on DeepSeek-V4.1-Flash 8×H200 (server ready 153–154 → 288–289 s), and 16–26 s more on the other models (details under Experimental Results). Later starts reuse the saved results, but with expert parallelism (EP > 1) it currently re-runs at every start (open PR #40420 fixes that); `--disable-flashinfer-autotune` turns the whole startup autotune off. While the server runs, each GPU has 0.5–1.1 GiB less free memory (1.08 GiB on DeepSeek-V4.1-Flash), mostly because FlashInfer keeps a larger tuning workspace (sized for up to 8192 tokens instead of the decode batch); the KV cache size is unchanged. PD decode servers pay nothing.
