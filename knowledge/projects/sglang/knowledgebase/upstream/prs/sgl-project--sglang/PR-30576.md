# Fix ROCm/HIP silently attempting real CUDA-IPC reconstruction (#29687)

[Upstream PR](https://github.com/sgl-project/sglang/pull/30576) · state: closed · merged: False

## Original PR description

fixes #29687

the bug: pytorch doesn't have a separate device type for hip. rocm tensors report `tensor.is_cuda == True` and live on `torch.device("cuda:N")` just like real cuda tensors. the multimodal cuda-ipc transport (`SGLANG_USE_CUDA_IPC_TRANSPORT=1`, opt-in, default off) was gating every call site on either the raw env var or `tensor.is_cuda`, and neither of those excludes rocm. so on a rocm build with this feature on, the raw ipc handle reconstruction in `CudaIpcTensorTransportProxy.reconstruct_on_target_device` gets attempted anyway and crashes with `HIP error: invalid device pointer`. a device-redirected ipc handle isn't something hip's ipc implementation can reopen the way real cuda does. that's what's reported in the issue, and the predecessor #29227 worked around it with an env var rather than fixing the gate.

the obvious quick fix is wrapping the two crash sites in an `is_hip()` check. i didn't do that: `MmItemMemoryPool` already logs "falling back to non-ipc transport" when the pool overflows, which means there's already a working backend-agnostic fallback path (`reconstruct_on_target_device`'s `tensor_data` branch, an ordinary `Tensor.to(device)` copy, no raw pointer handles). a narrow `is_hip()` guard at the crash site would just turn a hardware crash into a python exception, it wouldn't make multimodal inference work on rocm with this feature on. felt like the wrong bar to stop at.

so the gate moved to where the decision is made, the producer side in `base_processor.py`: `CUDA_IPC_TRANSPORT_SUPPORTED = SGL_USE_CUDA_IPC and not is_hip()`, and every call site that would construct a `CudaIpcTensorTransportProxy` with a real ipc handle (pool construction, the tensor-wrap helper, the post-process step) uses that flag instead of the raw env var. on rocm the code never builds an ipc-bearing proxy in the first place, it falls through to the passthrough that's already there and already exercised on every platform.

while tracing this i found `ernie45_vl.py` had its own copy of the same bug, it re-derives the raw env var via its own `get_bool_env_var()` call with zero rocm awareness instead of importing the shared flag. fixed it to import `CUDA_IPC_TRANSPORT_SUPPORTED` from `base_processor.py` so it can't drift out of sync. `moss_vl.py` had the same pattern and got the same fix.

the `is_hip()` assertions at the two raw-reconstruction call sites in `cuda_ipc_transport_utils.py` stay, on top of the producer-side fix. not because i think they're reachable anymore, but if someone adds a new call site without going through the gate i'd rather it die with a clear assertion naming this issue than reproduce the original opaque hip crash.

two smaller refactors, done for real reasons:

- the `CUDA_IPC_TRANSPORT_SUPPORTED` derivation is now a small pure function, `_compute_cuda_ipc_transport_supported(use_ipc_env, is_hip_platform)`. simpler to reason about and test as a function of two booleans than a module-level expression tangled with import-time `is_hip()` calls.
- `reconstruct_on_target_device` had `torch.device(f"cuda:{idx}")` hardcoded inline in two places. pulled into `_cuda_device_for_index()` and added a keyword-only `_rebuild_device_override` parameter defaulting to `None`. real callers are unaffected, they only pass the positional index. the reason for the seam: the `tensor_data` passthrough branch is the one part of the method that's backend-agnostic (just `.to(device)`), so it's the one branch that can be tested against a real `torch.device("cpu")` without a gpu. i didn't want to prove that by monkeypatching `torch` in the test, that tests the mock, not the code.

testing: two new test files, 21 tests, no gpu required: `test/registered/unit/multimodal/test_cuda_ipc_rocm_gate.py` and `test/registered/unit/utils/test_cuda_ipc_transport_rocm_gate.py`. covers the platform-gate derivation as a pure function over real booleans (no mocking), the two `is_hip()` assertion guards firing correctly, and a real non-mocked round-trip through the `tensor_data` passthrough that rocm now uses unconditionally. the existing `test/registered/unit/multimodal/` suite still passes unchanged.

what i couldn't verify: i don't have real rocm hardware. everything here is verified by tracing the actual code paths and testing the platform-gating logic directly, not by reproducing the original `hipErrorInvalidDevicePointer` crash and confirming it's gone. the raw cuda-ipc branches are untouched aside from the extracted device-index helper, so the real-cuda path should carry zero risk, but a sanity check from someone with an mi300-class box before merge would be good.
