# [Feat] rust-server: Let a multimodal processor observe the final result before scheduling

[Upstream PR](https://github.com/sgl-project/sglang/pull/46946) · state: closed · merged: True

## Original PR description

## Motivation

An external `MmProcessor` sees a request only inside `process`, before the caller's `mm_hashes` are applied, `finalize` has run, the item layout has been validated, and the expanded ids have been fitted to the context. A processor that hands the processed request on to another consumer (the decode side of a disaggregated deployment, for example, which needs the expanded ids and item layout before the request is scheduled) therefore had to wait for the scheduler to drain the request before it could know what the scheduler received.

## Modifications

- `MmProcessor::processed(MmRequestInfo, &MmProcessOutput)` is a new default no-op hook. The MM worker calls it once the result is in its final shape (caller hashes applied, finalized, validated, ids fitted), before the request is queued for the scheduler. `MmRequestInfo` carries the client-facing rid (not the scheduler's uniquified one) and the request's `bootstrap_room`; both are re-exported from `lib.rs` for external processors.
- `fit_input` is split out of `check_total_tokens` in `to_scheduler_validation.rs`: the input-length half, truncating the ids to the context under `--allow-auto-truncate` and rejecting an input that does not fit otherwise. Intake keeps calling it through `check_total_tokens`, with `input_ids: None` treated as empty as before. The MM worker applies it to the expanded ids before `processed`, so the hook sees the ids intake will forward; a prompt intake will reject is not observed, and the worker's result for it is unchanged.
- Intake's `Limits` reach the pool: `MmWiring` carries them (built from the server args in `Runtime::start`), and both `Runtime::start_mm_workers` and `start_mm_workers_with_processor` build their `MmContext` with `with_limits`. A context built without limits (unit tests) leaves the ids as processed.

Files: `rust/sglang-server/src/multi_modality/worker.rs`, `tokenizer_manager/to_scheduler_validation.rs`, `tokenizer_manager/to_scheduler.rs` (crate-visible `fit_input`), `utils/runtime.rs`, `lib.rs`.

## Accuracy Tests

Not applicable: no model forward or kernel code changes. Unit coverage in `cargo test -p sglang-server` (397 tests pass; `cargo fmt --check` and `cargo clippy --all-targets -D warnings` clean):

- `worker::tests::processed_observes_the_final_result_with_request_identity`: through a running `MmWorker`, `processed` sees the caller's hash applied, the client's rid and the bootstrap room.
- `worker::tests::processed_sees_the_ids_fitted_to_the_context`: a 12-token prompt on an 8-token context is observed truncated to 8 under auto-truncate and not observed at all when intake will reject it; the forwarded ids match in both cases.
- `worker::tests::finalization_runs_after_caller_hashes_and_is_validated` now also asserts that `processed` observes only a valid finalized result.
- The existing `to_scheduler` intake tests (`input_length_is_checked_unconditionally`, `reserved_tokens_count_toward_the_limit`, `auto_truncate_clamps_and_unknowns_skip`, ...) cover `check_total_tokens` through `fit_input` unchanged.

## Speed Tests and Profiling

Not applicable: one virtual call (a no-op by default) and an in-place length check per multimodal request on the MM worker.
