# [Metrics] Expose multi-detokenizer router CPU usage

[Upstream PR](https://github.com/sgl-project/sglang/pull/43323) · state: open · merged: False

## Original PR description

## Motivation

With multiple detokenizer workers, the router runs in its own process but does not report CPU usage. Operators cannot see router saturation in the existing process CPU metric.

Related to #43304. This PR implements the router CPU metric item; the remaining metrics are separate work.

## Modifications

Pass the launcher's resolved `enable_metrics` flag to the router process and start the existing CPU monitor when enabled. This exports `sglang:process_cpu_seconds_total{component="detokenizer_router"}` using the existing Prometheus multiprocess setup and five-second sampling interval.

The production change adds six lines across two files. A regression case in the existing multi-tokenizer unit test checks the actual counter value and that disabled metrics produce no sample.

## Validation

- `PYTHONPATH=python python test/registered/unit/managers/test_multi_tokenizer_mixin.py`: 8 tests passed.
- `PYTHONPATH=python python test/registered/unit/observability/test_cpu_monitor.py`: 2 tests passed.
- Confirmed the regression fails with `None != 2.0` when monitor startup is removed.
- `pre-commit run --files` for all three changed files: passed.

Validation ran in an isolated Python 3.12 environment on macOS. A full server launch and GPU integration were not run; those require project CI.

## Accuracy Tests

Not applicable: this adds process CPU monitoring and does not change model output.

## Speed Tests and Profiling

No inference benchmark was run. This reuses the existing five-second CPU monitor and performs no additional work in the routing loop.
