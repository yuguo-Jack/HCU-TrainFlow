# [sglang-miles] Restore FP8 checkpoint semantics on every in-place reload path (gfx94x)

[Upstream PR](https://github.com/sgl-project/sglang/pull/41360) · state: open · merged: False

## Original PR description

## Motivation

RL weight updates on `sglang-miles` load new checkpoint values into layers that `process_weights_after_loading` has already converted for serving. On gfx94x two conversions are not idempotent, so a second session corrupts values unless the layer is first put back in checkpoint form. This PR makes that restore happen on every path that writes weights in place.


## Modifications

1. **`fix(quantization): preserve KV scale semantics across reloads`**
   On FNUZ the processed KV scale is 2x the raw checkpoint value, and "unchanged" was inferred by comparing current to last-processed, so a new checkpoint whose raw scale equalled the previous runtime value was silently dropped. KV-cache methods now keep the checkpoint value separately and restore it before a load (`restore_weights_before_loading`); the disk loader (`load_weights_only`) restores before consuming weights, so `update_weights_from_disk` is covered as well as sessions.
2. **`fix(rocm): restore block FP8 checkpoint format across weight-update sessions`**
   gfx94x block-FP8 finalization reinterprets FN bytes as FNUZ (with the scale doubled) and applies AITER's (16, 16) shuffle. A restore hook undoes both before a session writes, keeping the same `Parameter`/storage, so empty and partial sessions leave untouched layers valid and a second finalize does not double-shuffle or double-scale.

   **The same commit makes the MoE shuffle follow the runner.** The plain FNUZ branch of `Fp8MoEMethod.process_weights_after_loading_block_quant` shuffled the experts into AITER's layout whenever `SGLANG_USE_AITER` was set, whichever runner served the layer. The Triton runner then read AITER's layout as if it were checkpoint order, so every MoE output was wrong and nothing reported it. It now shuffles only when the layer's runner is AITER, as the MXFP8 -> block branch already did (with no runner it falls back to the global MoE runner backend). Affected were configurations with AITER on and the Triton runner: an explicit `--moe-runner-backend triton`, which the miles DeepSeek-V4 recipe uses on gfx942, or an A2A backend without AITER support. `test_fp8_fnuz_weight_reload.py::test_triton_runner_does_not_shuffle` covers it. `main` has the same bug, in this branch and in the non-FNUZ one; sgl-project/sglang#41636 fixes both there.
3. **`fix(checkpoint-engine): restore checkpoint semantics before an IPC reload writes`** (review follow-up)
   `update_weights_from_ipc` opens no session, and `SGLangCheckpointEngineWorkerExtensionImpl.get_model_loader` returned `model.load_weights` directly, so neither restore ran on that path (a regression the first commit would otherwise have introduced for checkpoint-engine users on gfx942). The loader now restores before each load (idempotent, so the per-bucket calls after the first are no-ops). Also scopes the restore docstring: on gfx95 the AITER shuffles are neither flagged nor undone, so partial/empty sessions there are still unsafe.
4. **`test(checkpoint-engine): run the IPC reload restore test in CI`** (test only)
   The previous revision of commit 3's test never ran in CI: it sat after `unittest.main()`, and it skipped without the checkpoint-engine extra. See Accuracy Tests.
5. **`fix(quantization): restore KV scales from host state, not the device copies`**
   Colocated RL releases the weights region without CPU backup and the trainer never resends k/v scales, so after resume their device copies are whatever the allocator hands back. Commit 1's restore read them back and took any value other than the last runtime one for a newly written scale. On a fresh 2 x 8 MI308X DeepSeek-V4 run, one engine's TP rank got `k <= 0, v > 0` and died on `assert k_scale > 0.0` at the end of the startup weight sync; positive garbage would instead have been doubled into the runtime scales without an error. Zeroed memory maps to "no scales", which is why the same flow had passed across 27 weight syncs before. Restore now writes the checkpoint values kept on the host; loaders restore before writing, so nothing written is pending then, and a write that skips restore is still folded in by the next postprocessing.

## Why finalization returns early on finalized weights

A restored layer is finalized once per session, but finalizing an already-finalized layer is also part of normal use, so finalization returns early on weights that are already FNUZ instead of raising. `update_weights_from_disk` and `update_weights_from_ipc` do not check for an open session and finalize themselves, so called inside a session they are followed by the session's own `end_weight_update`, which finalizes again; the tests here require `end` to be repeatable for that reason. Every write path restores first: `update_weights_from_tensor` and `update_weights_from_distributed` require an open session whose `begin` restored the selected runners, base tensors in a `sync_base=False` session are rejected by an assertion, and the disk and IPC paths restore before each load. The case that remains is a session whose `begin_weight_update` selected only the draft runner while an update wrote to the target as well. The target is then never finalized again, so raising at finalization would not catch it; catching it takes a check where the loader writes, which is left for a follow-up.

## Why the three are one PR

The disk-path gap the reviewers found in commit 2 (a silent early return where `update_weights_from_disk` used to fail loudly) is closed by commit 1's restore in `load_weights_only`; separately they each leave a path unrestored.

## Merge order

Base `sglang-miles`, the branch miles runs on. They combine with sgl-project/sglang#41359, the `main` counterpart, whose first commit edits one shared hunk in the same way.

`main` has since gained its own, restructured weight-update session code, and these commits do not apply to it as they are (`model_loader/loader.py` was reorganized). sgl-project/sglang#41359 ports all of them to that code: the block-FP8 restore, the disk and IPC restore-first calls and the FNUZ KV-scale restore (commits 1 and 5 here). The runner-aware MoE shuffle from commit 2 goes to `main` separately, in sgl-project/sglang#41636.

Supersedes sgl-project/sglang#40586 and #40587.
