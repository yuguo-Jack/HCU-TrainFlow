# [Fix] [XPU] runtime: Device-agnostic fixes for scripted chunked-prefill and DWDP

## Notes on three deliberate choices

**DWDP platform gate (`arg_groups/parallel_hook.py`).** The #31996 reference in an
earlier commit message is wrong: #31996 is closed, not merged, and
`layers/moe/dwdp/page_pool.py:9` still carries a bare
`from cuda.bindings import driver as cuda`. The accurate justification is that the
import chain described in #31995 no longer exists on main --
`model_runner.py:1331-1335` imports `DwdpManager` lazily inside `maybe_init_dwdp`
behind `if get_parallel().dwdp_size <= 1: return`, and
`fused_moe_triton/layer.py:78` reaches the manager through
`get_global_dwdp_manager`, which pulls in nothing CUDA-specific. So the only
remaining route to `ModuleNotFoundError: No module named 'cuda'` is
`--dwdp-size >= 2` on a platform without cuda-python, which is exactly what
`handle_dwdp` now rejects with a message. This PR changes nothing under
`layers/moe/dwdp/`.

**`ScriptedReqHandle.lock_refs` contract (`scripted_runtime/req_handle.py:56-59`).**
A root `last_node` now folds to 0 instead of returning the tree's permanent
sentinel. `inc_lock_ref` / `dec_lock_ref` both loop `while node != self.root_node`
(`radix_cache.py:668,683`), so the root's `lock_ref` is fixed at 1 for the process
lifetime and no req's lock can move it. The pre-change value on a root `last_node`
was therefore a constant unrelated to the req, and this is the fix for that, not a
weakening.

**Deleted XPU GDN fork
(`srt/hardware_backend/xpu/kernels/fla/fused_sigmoid_gating_recurrent.py`).** That
fork imported the shared `fused_sigmoid_gating_delta_rule_update_kernel` and
launched it by keyword without `stride_h0_source`, which has no default in the
kernel signature, so every XPU GDN decode on main raises at launch. Removing it
cannot regress a working path. XPU now takes the shared wrapper, whose only
XPU-specific behavior is the `BV` cap at 16.

This guard is on the wrong side of `resolve_node`, and it makes `lock_refs` raise instead of returning 0 in exactly the state it is polled in.

`UnifiedRadixCache` is the default tree cache (`default_radix_cache_factory` falls through to `_create_unified_radix_cache`), so `req.last_node` is a `NodeId` int. `UnifiedRadixCache.is_root` -> `tree_core.is_root` -> `node_by_id` -> `self._node_arena[node_id]`, and `_node_arena` is a dict that is `pop`-ed when a node is freed (`unified_tree_core.py:613`). A freed id therefore raises `KeyError`. `resolve_node` exists precisely to absorb that -- its docstring says "Returns None when the handle no longer maps to a live node, which only happens once the node has been freed -- and a freed node holds no locks." Calling `is_root` above it re-introduces the crash the helper was written to avoid.

Failure path in this PR: `test_scripted_pp.py:35` now polls `h.lock_refs == 0` inside `_drain_until_released`, which runs immediately after `t.abort(r)` -- i.e. while the req's last_node is being freed. First iteration after the free raises `KeyError` out of the script instead of the drain loop converging.

Second break: with `--disable-radix-cache` the tree cache is `ChunkCache`, which never assigns `root_node`, so `BasePrefixCache.is_root` (`return node is self.root_node`) raises `AttributeError: 'ChunkCache' object has no attribute 'root_node'`. No existing test reads `lock_refs` under `ChunkCache` today, but `TestSpecialCaseIgnoreEosNoRadix` and `TestRadixDisabled` are one assertion away from it.

Swapping the order fixes both, because a handle that resolved is by definition live:

```python
tree_cache = self.context.scheduler.tree_cache
node = resolve_node(tree_cache, req.last_node)
if node is None:
    return 0
if tree_cache.is_root(req.last_node):
    # The root's lock_ref is a permanent sentinel, never a req's lock.
    return 0
return _node_lock_ref(node)
```

Separately, please call out the semantic change in the PR body: root `lock_ref` is a permanent 1 in every cache variant (`radix_cache.py:380`, `swa_radix_cache.py:402`, `mamba_radix_cache.py:490`, `unified_tree_core.py:455`), so folding it to 0 means the ~10 existing `assert r.lock_refs == 0` sites in `test_scripted_radix.py` / `test_scripted_special_case.py` can no longer distinguish "the radix lock was released" from "last_node reverted to the root". That is a real loss of guard strength in files this PR does not touch.
