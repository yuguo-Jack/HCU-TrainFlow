# [Fix] scheduler: let a client abort yield to the stop or length cap of its step

[Upstream PR](https://github.com/sgl-project/sglang/pull/48226) · state: open · merged: False

## Original PR description


## Motivation

`Req.update_finish_state` applies a pending abort before it checks the step's own stop token, stop string and length cap. When the step that commits a client abort (`/abort_request`) also reached EOS or `max_new_tokens`, the request finishes as an abort with every committed token. With speculative decoding one step commits several tokens, so the output can carry tokens after the EOS or past `max_new_tokens`. Clients that abort requests and keep the partial outputs then receive tokens past a stop.

Related: open #44874 caps aborted speculative output at `max_new_tokens` and keeps the abort reason. This PR covers stop tokens and stop strings too, and reports the step's own finish (`stop` / `length`) for client aborts only; aborts that carry a status code (intake rejections, timeouts, the 499 case in #44874) keep their reason, so the two do not conflict in behavior.

## Modifications

- `Req.update_finish_state`: a client abort (`FINISH_ABORT` with no status code) yields to the stop token, stop string or length cap reached in the same step, which then trims the output as usual. Aborts with a status code keep their reason.
- Visible to clients: a request aborted with `/abort_request` (or by a session abort) in the step where it reaches a stop token, a stop string or `max_new_tokens` now returns `finish_reason` `stop` or `length` instead of `abort`, with the output trimmed at the stop or the cap.
- `test/registered/unit/managers/test_finish_length_speculative.py` (CPU), 5 new cases: EOS, stop string and length cap in the abort step win and trim; an abort without a step finish stays an abort; an abort with a status code keeps its reason. The first 3 fail on main.

## Accuracy Tests

Requests that are not aborted run the same code. Driving the real `Req.update_finish_state` on CPU, with a client abort pending:

| step commits | main | this PR |
|---|---|---|
| `[10, 11, EOS, 20]` (EOS mid-run) | abort, 4 tokens incl. one after EOS | `stop`, `[10, 11, EOS]` |
| `[10, STOP, 20]`, stop string "STOP" | abort, 3 tokens | `stop`, `[10, STOP]` |
| run crossing `max_new_tokens=4` | abort, 5 tokens | `length`, 4 tokens |
| no stop, no cap | abort | abort (unchanged) |
| abort with status 503 + EOS | abort | abort (unchanged) |

End to end, the race (abort arriving in exactly the finishing step) is timing-dependent and was not reproduced on GPU.

## Speed Tests and Profiling

No speed impact: the finish checks run once more only in the step that applies a client abort.
