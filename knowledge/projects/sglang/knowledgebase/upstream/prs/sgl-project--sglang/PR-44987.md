# [Perf] [AMD] kimi-k3: Decode routing on gfx950: fused router top-k + MoE route sort, split greedy-verify argmax

[Upstream PR](https://github.com/sgl-project/sglang/pull/44987) · state: open · merged: False

## Original PR description

> Kimi-K3 on gfx950, grouped into larger drafts: prefill #44981 (with #44980) · TP8 LL collectives #44985 (with #44986) · decode routing #44987 (now includes #44978's argmax) · KDA verify #44982 · then #44988. Closed as superseded on main: #44979, #44983, #44984, #44989.

## Motivation

Two decode-side costs for Kimi-K3 with speculative decoding on gfx950:
- each MoE layer runs aiter's biased top-k, two moe_sorting phases and the MXFP8 activation quant before the experts;
- greedy verify reduces each vocab row with `torch.argmax`, one workgroup per row.

This PR now also carries the greedy-verify argmax from #44978.

## Modifications

Gated on gfx950 with aiter (`SGLANG_USE_AITER`).

- **Fused route sort** (`kimi_k3_route_sort`: `route_sort.cuh`, `route_topk.cuh`): the router top-k and aiter's block-padded moe_sorting layout run in one launch for decode batches (`SGLANG_ROCM_K3_FUSED_ROUTE_SORT_MAX_TOKENS`, 16).
  - Selection is sigmoid + bias, as in aiter's topk kernel, with renormalized pre-bias weights.
  - The bias is main's fp32 correction bias, added in fp32 (#44797).
  - Up to 8 tokens, the A8W4 experts' MXFP8 activation quant and scale sort are folded in (`SGLANG_ROCM_K3_FUSED_ROUTE_QUANT`).
  - The routes reach aiter's `fused_moe` through `moe_sort_handoff`. aiter's `moe_sorting` / `fused_dynamic_mxfp8_quant_moe_sort` hooks consume them only for the exact call they were staged for; aiter's own sort runs otherwise.
- **Split greedy-verify argmax (from #44978):** from a 32K vocab, `split_argmax` (`kernels/ops/speculative/topk1.py`) splits each row across CTAs, with the same first-max tie order.

Changes since the original PRs:
- `TopKConfig.num_shared_topk_slots` (main renamed it from `num_fused_shared_experts`).
- The fp32 bias, where it was previously cast to the logits' bf16.
- No separate zero-copy MoE output (main's #33916 does it).
- None of #44978's GEMM-row dispatch or packed broadcast (main's `_verify_outputs` packs).

| New env var | Default |
|---|---|
| `SGLANG_ROCM_K3_FUSED_ROUTE_SORT_MAX_TOKENS` | 16 |
| `SGLANG_ROCM_K3_FUSED_ROUTE_QUANT` | on |

## Accuracy Tests

- Kernel tests on MI355X, on this branch merged with current `main`: 9 passed, 21 subtests.
  - `test_kimi_k3_route_sort.py` checks against aiter's top-k + sort + quant chain, plus a new test that the fp32-bias top-k picks the experts and weights of sigmoid(logits) + bias computed in fp32.
  - `test_spec_topk1.py` checks the split argmax against `torch.argmax`, including ties and NaN rows.
- GSM8K 200 on `main` 3a01d4cc8c (2026-10-29), Kimi-K3 TP8 + EAGLE3 (`lightseekorg/kimi-k3-eagle3.1-mla`), MI350X: 98.0-98.5 across these runs. The fp32 bias costs nothing: C1 24.90 ms with it vs 24.84 ms with the bf16 bias.

## Speed Tests and Profiling

Same setup, PRs added one at a time:
- **Fused route sort:** C1 verify cycle -5%.
- **Split argmax:** C1 verify cycle -3.1%, C4 -1.3%.

Note: in those runs, 64-token cached extends were 7-12% slower from the fused route sort on; not yet explained.
