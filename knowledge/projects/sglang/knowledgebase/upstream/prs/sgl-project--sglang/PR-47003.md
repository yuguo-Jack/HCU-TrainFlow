# [Perf] [XPU] quantization: Run block-FP8 linears weight-only (W8A16) on Xe2

[Upstream PR](https://github.com/sgl-project/sglang/pull/47003) · state: open · merged: False

## Original PR description

## Motivation

Block-FP8 checkpoints (128x128 weight scales, e.g. Qwen3-32B-FP8, Qwen3-30B-A3B-FP8) run their linears on XPU in two steps. First `per_token_group_quant_fp8` quantizes the activation. Then `torch_w8a8_block_fp8_linear` calls `scaled_mm` (oneDNN).

At decode sizes that path streams the fp8 weight at only 175-350 GB/s on Arc Pro B70; the bf16 GEMM reaches 510-590 GB/s. So Qwen3-32B-FP8 decodes no faster than bf16, even though it reads half the bytes. Xe2 has no FP8 math, so fp8 activations buy nothing. The win is bandwidth: keep the activation in bf16 and stream the fp8 weight once.

## Dependency

The fused GEMM is `torch.ops.sgl_kernel.fp8_w8a16_mm_xe20`, added in sgl-project/sgl-kernel-xpu#587. sglang currently pins sgl-kernel-xpu 0.5.0, which does not have it.

- This PR detects the op (`has_xpu_w8a16_gemm`). Without it, block-FP8 linears keep today's `scaled_mm` path unchanged, so this PR is safe to merge before the kernel release.
- The speedup arrives with the sgl-kernel-xpu version bump that includes #587.
- Until then, the fused-path unit test skips in CI and the dequant test runs.

## Modifications

- New `kernels/ops/gemm/fp8_w8a16_xpu.py`, with `xpu_w8a16_block_fp8_linear(input, weight, weight_scale, bias)`:
  - Up to 512 rows it calls `fp8_w8a16_mm_xe20`, which dequantizes in registers and streams the weight once.
  - Above 512 rows the GEMM is compute-bound. The weight is dequantized to bf16 by a small Triton kernel (one program per 128x128 scale block, edge blocks masked) and multiplied with `F.linear`. On these shapes that is faster than both `scaled_mm` and the fused kernel.
  - 512 is where the two paths tie at Qwen3-32B TP4 shapes on B70; the comment says so.
- `layers/quantization/fp8_utils.py`: on XPU, `_dispatch_auto_backend` returns `xpu_w8a16_block_fp8_linear_with_fallback` when the op exists. That function falls back to `torch_w8a8_block_fp8_linear` when there is a static input scale, when the input is not bf16, or when the block size is not `[128, 128]`.
- The fused path asserts a row-contiguous `weight` and a k-contiguous `weight_scale`, the only layouts sgl-kernel-xpu#587 was validated on. The dequant kernel reads `weight_scale` through both of its strides, so it is correct for either scale layout.
- New `test/registered/kernels/ops/gemm/test_fp8_w8a16_xpu.py`:
  - The dequant kernel must be bit-exact against a reference, including partial scale blocks (N=320, K=448).
  - Both paths (1, 24, 512 and 513 rows, with bias) must match the dequantized-weight reference.

## Speed Tests and Profiling

**Setup:**
- Arc Pro B70, torch 2.14.0+xpu, compute-runtime 26.31.
- The op from sgl-project/sgl-kernel-xpu#587 was loaded as a torch library fragment on top of the released wheel.
- Server flags: cookbook BMG flags plus `--attention-backend intel_xpu --page-size 64 --cuda-graph-backend-decode full --cuda-graph-backend-prefill breakable`.

Per GEMM at decode (M=1, cold weights, in an XPU graph), Qwen3-32B TP4 shapes:

| GEMM | old `scaled_mm` path | this PR |
|---|---|---|
| qkv (N=2560, K=5120) | 49.7 us | 28.5 us (460 GB/s) |
| o_proj (N=5120, K=2048) | 38.4 | 21.7 (482 GB/s) |
| gate_up (N=12800, K=5120) | 222.6 | 119.2 (550 GB/s) |
| down (N=5120, K=6400) | 113.4 | 61.7 (531 GB/s) |
| per layer | 424 | 231 (1.84x) |

Prefill, one layer of 4 linears, in an XPU graph:

| rows | bf16 checkpoint | old `scaled_mm` | this PR |
|---|---|---|---|
| 128 | 547 us | 774 | 545 (fused) |
| 512 | 926 | 1943 | 1973 (fused) |
| 2048 | 3432 | 8295 | 4410 (dequant + bf16) |
| 4096 | 6783 | 16952 | 7975 (dequant + bf16) |

Prefill stays slower than the bf16 checkpoint, because the weight is still dequantized or streamed as fp8. It is much faster than the old path, though: c=16 TTFT for Qwen3-32B is 1049 ms, against 935 ms for bf16 and 1669 ms for the old FP8 path.

End to end, `bench_serving` random 512 in / 256 out:

| Qwen3-32B, TP4 | c=1 TPOT | c=4 | c=16 | c=32 | c=16 tok/s | c=32 tok/s |
|---|---|---|---|---|---|---|
| bf16 checkpoint | 31.57 ms | 32.48 | 34.97 | 40.28 | 415 | 715 |
| FP8, old path | 30.98 | 31.80 | 35.23 | 40.91 | 384 | 653 |
| FP8, this PR | **19.88** | 20.98 | 23.78 | 29.58 | **575** | **926** |

| Qwen3-30B-A3B-FP8, TP2 (attention linears) | c=1 TPOT | c=4 | c=16 | c=32 | c=32 tok/s |
|---|---|---|---|---|---|
| old path | 8.95 ms | 13.65 | 22.70 | 29.82 | 1010 |
| this PR | **7.34** | 11.93 | 21.08 | 28.18 | 1070 |

Qwen3-30B-A3B-FP8 does not load at TP4: the per-rank MoE intermediate size, 768/4 = 192, is not a multiple of the 128 block. TP2 works.
