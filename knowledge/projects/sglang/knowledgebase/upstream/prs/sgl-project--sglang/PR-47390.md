## Motivation

With NGRAM speculative decoding, the overlap scheduler (the default) and a grammar-constrained request, `event_loop_overlap` plans the next decode batch, then processes the previous result (the grammar sync), then launches the batch it already planned. If that result finished a request, the request has released its KV and its `req_to_token` row but is launched once more. `_reqs_finishing_inflight` (#42720) only drops a request whose next single token reaches `max_new_tokens`; a verify commits several tokens, and EOS or the end of the grammar is known only after the result is processed.

Example: `unsloth/Llama-3.2-1B-Instruct`, `--speculative-algorithm NGRAM --speculative-num-draft-tokens 8 --page-size 16`, one request with `regex: "[A-Za-z ,]+"` and `max_new_tokens: 30`. The pending verify reaches 31 output tokens, so the request finishes and frees row 8. The next verify still launches row 8, which is on the free list with `kv_allocated_len == 0`. Its result is discarded and client output is unchanged, but the forward runs on a released row and released pages.

Duplicate-work check: I searched open and closed issues and PRs for NGRAM with grammar or structured output, `grammar_needs_sync`, `is_disable_overlap_for_batch` and finished requests at the grammar sync. #42720 (merged) covers only the one-token length case, #42401 (open) syncs grammar before mixed steps for overlap-capable algorithms, and #25361/#28039 concern the PD decode loop. None covers this case.

## Modifications

- `Scheduler._needs_grammar_sync_before_plan()` is true when a result is pending, the running or last batch holds a grammar request, and the algorithm cannot overlap grammar (NGRAM). In that case `event_loop_overlap` processes the pending result before `get_next_batch_to_run`, so the planner drops the finished requests. Other algorithms and grammar-free batches keep today's order.
- `test/registered/unit/managers/test_scheduler_grammar_sync_before_plan.py` covers decode-to-decode and extend-to-decode iterations in which the pending result finishes the request, and checks that NGRAM without grammar, EAGLE with grammar and non-speculative grammar batches still plan first.
- `event_loop_overlap_disagg_decode` has the same order and is not changed here; PD decode with NGRAM and grammar was not tested.

## Speed Tests and Profiling

Only NGRAM batches holding a grammar request lose planning overlap, and those already wait for the previous result before launch. Unconstrained batches take the unchanged path.

Setup: 8 concurrent requests, NGRAM 8, on an RTX A6000 with no other jobs. Main and this PR were launched alternately, with two repeats per launch. Each cell is the mean output throughput, with the range in parentheses.

| Workload | main (tok/s) | this PR (tok/s) | Diff |
| --- | ---: | ---: | ---: |
| 32 requests x 128 tokens, grammar | 3,048 (2,738 to 3,161) | 3,125 (2,860 to 3,243) | +2.5% |
| 32 requests x 128 tokens, unconstrained | 5,697 (5,435 to 5,777) | 5,490 (4,983 to 5,779) | -3.6% |
| 64 requests x 256 tokens, grammar | 3,095 (3,017 to 3,191) | 3,104 (3,015 to 3,228) | +0.3% |
| 64 requests x 256 tokens, unconstrained | 5,876 (5,751 to 5,985) | 5,918 (5,841 to 6,044) | +0.7% |

The short workload had six launches of main and five of this PR, and each phase lasts under a second. The longer workload had three launches of each and shows no difference.
