# [Fix] disaggregation: Avoid extra GPU contexts with PD

[Upstream PR](https://github.com/sgl-project/sglang/pull/45678) · state: closed · merged: True

## Original PR description

## Summary

With PD disagg, an extra GPU context is accidently created on GPU0 by the other GPU workers which wastes about 1GB of gpu memory.

[by Claude Code]

## Motivation

A PD prefill rank whose GPU is not CUDA device 0 opens a second CUDA context on device 0 the first time it sends KV
for a request with a cached prefix. That rank then holds about 0.6–1 GiB on another rank's GPU (656 MiB in the repro
below, about 1 GiB with DeepSeek-V4.1 attention-DP2 prefill). The memory is taken after that GPU's KV pool was sized
against its free memory, so it eats into the headroom left for activations and graphs.

**Cause.**
- With overlap scheduling, `maybe_send_cached_prefix_chunk` (`disaggregation/prefill.py`) records a `torch.cuda.Event`
  on the forward stream for the early cached-prefix send.
- Mooncake's prefill `transfer_worker` thread calls `wait_event.synchronize()` on that event before it reads the KV.
- That thread never selects a device, so the CUDA runtime runs the call on device 0 and creates device 0's primary
  context in the process.
- Ranks that already live on device 0 reuse their own context. Every other rank gets a new one.
- mori's `_transfer_worker` does the same `wait_event.synchronize()`.

## Modifications

- `disaggregation/common/utils.py` adds two helpers:
  - `bind_thread_to_device(gpu_id)` sets the calling thread's device through `current_platform`. It is a no-op on
    platforms that do not implement `set_device`.
  - `run_on_device(gpu_id, fn, *args)` is a thread target that binds the thread, then runs `fn(*args)`.
- Mooncake:
  - The prefill `transfer_worker` threads start through `run_on_device(kv_args.gpu_id, ...)`.
  - The transfer thread pools bind each pool thread with `initializer=bind_thread_to_device`.
- mori: the `_transfer_worker` threads start through `run_on_device`.

The worker functions themselves are unchanged, so existing unit tests that drive them directly need no changes.

## Repro (dummy weights, one 4-GPU node)

Prefill runs TP2 on GPUs 0,1, so rank 1 lives on GPU 1. Decode runs TP1 on GPU 2. The same ~2k-token prompt is
sent three times, so requests 2 and 3 hit the radix cache and take the early cached-prefix send.

```bash
MODEL=Qwen/Qwen3-0.6B
COMMON="--model-path $MODEL --load-format dummy --disaggregation-transfer-backend mooncake --mem-fraction-static 0.5"
CUDA_VISIBLE_DEVICES=0,1 python3 -m sglang.launch_server $COMMON --tp-size 2 --disaggregation-mode prefill --port 30000 &
CUDA_VISIBLE_DEVICES=2 python3 -m sglang.launch_server $COMMON --tp-size 1 --disaggregation-mode decode --port 30001 &
# wait for both /health, then:
python3 -m sglang_router.launch_router --pd-disaggregation --prefill http://127.0.0.1:30000 8998 \
  --decode http://127.0.0.1:30001 --port 8000 &
PROMPT=$(python3 -c "print(' '.join(['The quick brown fox jumps over the lazy dog.'] * 200))")
for i in 1 2 3; do
  curl -s localhost:8000/generate -H 'Content-Type: application/json' \
    -d "{\"text\": \"$PROMPT\", \"sampling_params\": {\"max_new_tokens\": 8, \"temperature\": 0}}" > /dev/null
done
nvidia-smi
```

On our nodes, Mooncake moved the KV over NVLink (`MC_FORCE_MNNVL=1 SGLANG_MOONCAKE_CUSTOM_MEM_POOL=True`). The bug
does not depend on the transport.

holds a context on GPU 0.
