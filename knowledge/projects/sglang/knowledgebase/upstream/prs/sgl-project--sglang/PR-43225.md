# [Fix] dspark: Select DSv4.1 candidate verify graphs from committed lengths under compact verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/43225) · state: open · merged: False

## Original PR description

## Motivation

Some verify attention backends add the verify window to the sequence lengths themselves; `TargetVerifyExecutor._verify_backend_self_adds_seq_lens()` detects these (the DeepSeek-V4 backends). For them, static verify (`run_non_compact`) leaves `batch.seq_lens_cpu` at the committed lengths. Compact verify (`_run_ragged`) always added `verify_lens` first.

When the CPU length mirror is present, `Dsv41CandidateGraphVariants.select` adds `verify_extra_tokens` (the verify width) to `seq_lens_cpu`. Under compact verify the window was therefore counted twice. With full-width verify (width `W`), a graph-eligible batch whose longest committed length `L` satisfies `limit - 2W < L <= limit - W` selected the `candidate_filtered` graph, while static verify selected `candidate_unfiltered` for the same batch.

Eager verify on the HIP DeepSeek-V4 backend applies the same length-plus-width check (`low_ratio_decode_rows_fit_candidate_span`) and also filtered unnecessarily.

## Modifications

`_run_ragged` adds `verify_lens` to `seq_lens_cpu` only when the backend does not add them itself.

## Accuracy Tests

`test/registered/unit/spec/test_dspark_verify_seq_lens.py` (CPU):
- With a self-adding backend, static and compact verify both hand the forward the committed lengths. At a committed length of `limit - width`, the DSv4.1 selector picks `candidate_unfiltered`.
- With other backends, compact verify still passes `committed + verify_lens`.
- Both tests check `seq_lens_sum` and the committed `live_seq_lens_cpu` at verify preparation, and that the batch lengths are restored afterward. The first test also checks that the selector picks `candidate_filtered` once the longest committed length exceeds `limit - width`.
