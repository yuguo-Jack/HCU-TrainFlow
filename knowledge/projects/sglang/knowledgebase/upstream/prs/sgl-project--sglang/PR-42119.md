## Original PR description

# [AMD] Enable GPTQ and AutoRound INT4 checkpoints

## Why this is needed

AutoRound and GPTQ checkpoints, such as
`Intel/Qwen3.6-27B-int4-AutoRound`, fail to load on ROCm. INT4 checkpoints reduce memory requirements and are widely used for local LLM serving. This PR enables support on ROCm RDNA and CDNA GPUs, validated on gfx1151 and gfx950.

Two issues prevent these checkpoints from loading:

1. ROCm device capabilities can incorrectly select the CUDA-only Marlin path.
2. After skipping Marlin, no supported dense GPTQ kernel is available.

This PR adds a ROCm-compatible Triton path for 4-bit GPTQ checkpoints.

## Changes

- Restrict Marlin selection to CUDA devices. On ROCm, dense GPTQ layers now
  use the new Triton path and MoE layers use the existing `MoeWNA16` path.
- Add a Triton W4A16 GPTQ kernel for ROCm, including load-time weight
  repacking and tuned configurations for gfx1151.
- Add `GPTQTritonLinearKernel`, with support for symmetric and asymmetric
  zero points in GPTQ v1 and v2 formats.
- Route HIP GPTQ linear layers to the new kernel and propagate AutoRound's
  `sym` setting to the GPTQ configuration.
- Add load-path and GEMM tests to AMD CI.

The dense kernel supports 4-bit weights, `fp16` and `bf16`,
`desc_act=False`, and group sizes `-1`, `32`, `64`, `128`, and `256`.
Unsupported configurations fail with a clear error.

## Validation

Unit tests compare the load path and GEMM output with fp32 dequantization.
They cover symmetric and asymmetric GPTQ v1/v2 checkpoints, all supported
group sizes, `fp16`, `bf16`, bias, 2D/3D inputs, and invalid configurations.
All cases stay below `1e-2` relative error.

On gfx1151 the worst relative error is 4.2e-3 (bf16) and 4.1e-4 (fp16),
which matches the rounding error of the output dtype.

GSM8K on `Intel/Qwen3.6-27B-int4-AutoRound`:

- GPU: gfx950
- Questions: 200
- Accuracy: 0.91

- GPU: gfx1151
- Questions: 200
- Accuracy: 0.90

## Performance

This PR focuses on correctness. Additional optimized INT4 HIP GEMM and MoE kernels will be submitted separately.

## Reproduce

```bash
sglang serve --model-path Intel/Qwen3.6-27B-int4-AutoRound \
  --reasoning-parser qwen3 --tool-call-parser qwen3_coder \
  --mem-fraction-static 0.93 --max-running-requests 4 \
  --chunked-prefill-size 4096 --attention-backend triton

python3 benchmark/gsm8k/bench_sglang.py \
  --port 30000 --num-questions 200 --parallel 10

python3 -m unittest \
  test/registered/kernels/ops/quantization/test_gptq_triton.py
```

Validated on RDNA4 (gfx1201), stock `rocm/pytorch` image, no aiter/vLLM.

- **Base:** current `main` + #43679 (gfx1201 kernel build) + #47254 (RDNA default attention) + a local quark-import guard. Arms: base with/without this PR.
- **Model:** Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4, default server flags (Triton attention, decode CUDA graphs).

| | without this PR | with this PR |
|---|---|---|
| server start | ❌ `ValueError: gptq_marlin quantization is currently not supported in ROCm.` | ✅ up in 30–40 s |
| `test/registered/kernels/ops/quantization/test_gptq_triton.py` | — | ✅ 5 passed, 247 subtests passed |
| bench_serving random-ids 512/256, c=1 | — | 66.5 tok/s (median TPOT 14.7 ms) |
| c=8 | — | 479.1 tok/s (median TPOT 14.4 ms) |

For accuracy I compared against the bf16 checkpoint (Qwen/Qwen2.5-7B-Instruct) in the same server build: `sgl-eval==0.1.2` gsm8k, greedy, 400 questions. bf16 scored 29.75% and GPTQ-Int4 24.75%; at sampled temperature 0.7 on 100 questions it was 33% vs 27–28%.

The absolute numbers are low for both because of how this harness extracts answers for Qwen2.5 without thinking, so treat this as a relative check only. It shows GPTQ within ~5 points of its own bf16 baseline, roughly 1.6σ at n=400. I'd still suggest a CDNA accuracy reference on the same checkpoint before merge, to tell kernel error apart from ordinary INT4 quantization loss. `--disable-cuda-graph` gives the same score (27% vs 28% on 100 questions), so CUDA graphs aren't a factor.
