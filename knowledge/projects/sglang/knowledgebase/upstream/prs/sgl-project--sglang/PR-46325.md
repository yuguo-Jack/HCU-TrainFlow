# [Perf] [AMD] deterministic: Use a fixed-order two-stage all-reduce for large inputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46325) · state: closed · merged: True

## Original PR description

## Motivation

In deterministic mode on ROCm every custom all-reduce runs the 1-stage kernel: each GPU reads every peer's whole input and sums the ranks in the order 0..n-1. That order is what makes the result independent of the input size, but each GPU reads n times the data, so at TP4/TP8 the all-reduce takes a large share of the step: on MI350X, Qwen3-8B deterministic decode/prefill spends 48% of GPU time in it at TP4 and 63% at TP8 (8k-token inputs), and deterministic throughput at TP8 was about half of normal mode. The 2-stage kernel (reduce-scatter + all-gather) reads far less, but it cannot be used as is: each owner starts its sum at its own rank, so an element's result depends on which rank owns it, which changes with the input size. This PR adds a fixed-order option to the 2-stage kernel that sums the ranks in the same order as the 1-stage kernel, so the two give the same bits for every element at every size, and uses it for large inputs at 4 and 8 ranks. Results do not change; on MI350X deterministic throughput rises 16-24% at TP4 and 29-57% at TP8 on Qwen3-8B, and 28-54% at TP8 on Qwen3.8-27B, with every determinism check passing.

## Modifications

- `custom_all_reduce_hip.cuh`: `cross_device_reduce_2stage` gets a template parameter `kFixedOrder` (default `false`, so normal mode is unchanged). With it, stage 1 reads the ranks in the order 0..n-1 instead of starting at its own rank; stage 2 (the gather) is unchanged.
- `deterministic_all_reduce.hip`: one templated launcher instead of three copies per dtype. Inputs copied into the registered buffer (`deterministic_all_reduce_unreg`, which every deterministic call of `CustomAllreduce` uses for inputs that fit the buffer, including in CUDA graphs and the pieces of larger inputs) take the fixed-order 2-stage kernel with 32 blocks at or above 512 KiB at 4 ranks and 256 KiB at 8 ranks (the thresholds `CustomAllreduce::allreduce` uses); everything else keeps the 1-stage kernel with 16 blocks: smaller inputs, 2 and 6 ranks, and `deterministic_all_reduce_reg` (its inputs can be larger than the IPC buffer that the 2-stage kernel stages 1/n of the input in).
- New test `test/registered/kernels/ops/communication/test_amd_deterministic_allreduce_fixed_order.py` (`stage-c-test-large-8-gpu-amd-mi35x`): at 4 and 8 ranks, bf16 and fp16, sizes on both sides of the thresholds, eager and CUDA graphs, the all-reduce output must equal, bit for bit, the sum of the ranks' inputs computed in torch in the order 0..n-1 (float32 accumulation). The data is chosen so its float32 sum depends on the order of the ranks.

## Accuracy Tests

MI350X, ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`.

Kernel level (bf16, hidden 4096 and 7168, 1-2,040 rows eager and 1-512 rows in CUDA graphs, order-sensitive data, 2/4/8 ranks): the fixed-order 2-stage kernel's output equals the current 1-stage kernel's output bit for bit at every size, is identical on every rank, and a row's result does not depend on the number of rows. Control: the current (unordered) 2-stage kernel differs from the 1-stage kernel at 42-44 of 42-44 sizes at 4 and 8 ranks.

End to end, deterministic mode (`--enable-deterministic-inference`, Triton prefill and AITER decode attention, together with the other open MI350X deterministic-mode PRs), `python3 -m sglang.test.test_deterministic` (`single`, `prefix`, `prefix --return-logprob`, `radix_cache`, 50 trials) plus a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response): every check passes (`single` 1 output, `prefix` 1/1/1/1, prefix logprobs identical, radix cache consistent, bitwise 1,275 / 1,275). With this branch's build (sgl-kernel rebuilt for gfx950):

- the new test passes at 4 and 8 ranks, and the existing 2-rank deterministic all-reduce test passes;
- every check above passes on Qwen3-8B TP2, TP4 and TP8, Qwen3-30B-A3B TP4, Qwen3.8-27B TP4 and Qwen3.8-27B TP8, and again on fresh servers: Qwen3-8B TP8 4 / 4, Qwen3-30B-A3B TP4 3 / 3, Qwen3.8-27B TP4 2 / 2;
- GSM8K (sgl-eval 0.1.2, temperature 0, 1,319 questions) is unchanged: Qwen3-8B 93.40% / 93.25% / 93.48% at TP2 / TP4 / TP8 (93.48% at TP8 before), Qwen3.8-27B 96.21% at TP4 and 96.13% at TP8.

Through the experiment-only switch (same kernel and selection) the checks also passed on Qwen3-30B-A3B TP4 with GSM8K 95.15% (95.15% before).

- hubertlu-tw · APPROVED · 2026-10-26T23:36:25Z · [source](https://github.com/sgl-project/sglang/pull/46325#pullrequestreview-5660520236)

I reproduced the kernel-level numbers on 8x MI355X (gfx950) with [benchmark_rocm.py](https://github.com/hubertlu-tw/sglang/blob/cc36b182efae2b1e4b90eb6d542da669ab99b53e/benchmark/kernels/all_reduce/benchmark_rocm.py), building sgl-kernel from the base (8252e3af63) and from this PR, and running the deterministic path (`SGLANG_USE_1STAGE_ALLREDUCE=1`, bf16, 16 MiB buffer).

Above the thresholds the fixed-order 2-stage kernel is clearly faster. In CUDA graph mode TP4 goes from 1.19x at 512 KiB to 1.88x at 16 MiB (317 to 169 us), and TP8 goes from 1.30x at 512 KiB to 3.03x at 16 MiB (326 to 107 us). Eager mode shows the same trend (1.84x and 2.97x at 16 MiB). TP2 and all sizes below the thresholds are unchanged, and normal mode stays within run-to-run noise. In one run TP8 at exactly 256 KiB looked slightly slower, but three interleaved repeats came out break-even (0.98-1.01x), so the threshold sits right at the crossover rather than past it. The PR's bitwise test passes at TP4/TP8, and a manual fp32 check matches RCCL exactly.

A few small follow-ups that don't need to block this PR: the new test also passes against the base kernel, which has no 2-stage path, so it can't catch the 2-stage kernel never being selected. Checking for cross_device_reduce_2stage in a profiler trace, or adding the unordered 2-stage kernel as a negative control, would close that gap. `DET_AR_CASE(6)` instantiates a 2-stage kernel that never runs, since 6 ranks always take 1-stage, so case 6 can launch 1-stage directly like case 2. And the comment on `deterministic_all_reduce_reg `should say its input isn't bounded by `max_size`, so nobody later turns on the 2-stage path there without a size check. A quick spot check on MI300X would also be good, since the 32-block setting was tuned on MI350X. I'd expect it to work correctly there, but the speedup may be smaller.
