# [Perf] [AMD] Qwen3.5: enable fused GDN decode unpack + Conv1D for ROCm platform

[Upstream PR](https://github.com/sgl-project/sglang/pull/47287) · state: open · merged: False

## Original PR description

Qwen3.5 uses a type of layer called GDN (a linear-attention layer). On AMD GPUs, every GDN layer ran two small GPU kernels in a row during decode. This PR combines them into one. Nothing changes for NVIDIA GPUs.

## Motivation

Decode is the step where the model writes its answer one token at a time. In each GDN layer, the model needs to do two small jobs before the main computation:

| Kernel | What it does |
|---|---|
| `fused_qkvzba_split_reshape_cat_contiguous` | Splits one big packed tensor into the separate pieces the layer needs |
| `causal_conv1d_update` | Updates a small saved state and applies a short convolution |

Together they took 10.5 µs per layer. Each one does very little work, so most of that time is not real computation. It is the cost of starting a kernel and waiting for it to finish.

SGLang already has a single fused kernel that does both jobs, but only for NVIDIA GPUs. The code checked `_is_cuda`, so on AMD the setting `SGLANG_ENABLE_GDN_DECODE_FUSED_PROJ_CONV` did nothing, even though it was on by default.

Qwen3.5-397B has 45 GDN layers. So every decode step on AMD started 90 of these small kernels.

## Modifications

- **`srt/models/qwen3_5.py`**: the check is now `(_is_cuda or _is_hip)`, so AMD also uses the fused path. The model gives the GDN backend the two packed tensors together, as it already does on NVIDIA.
- **`kernels/ops/attention/triton_gdn_fused_proj.py`**
  - Adds a new kernel, `_fused_qkvzba_causal_conv1d_update_contiguous_kernel_amd`. It runs only on AMD.
  - Its results are exactly the same as the existing kernel. The difference is that it reads each piece of the saved state once and reuses it, where the existing kernel reads it twice.
  - On AMD it runs with `BLOCK_SIZE=256` and `num_warps=4`. This gives each lane of an AMD wavefront (64 lanes) one element to work on. On NVIDIA, the existing kernel keeps its own settings, `BLOCK_SIZE=256` and `num_warps=8`.
- **`srt/layers/attention/linear/gdn_backend.py`**: on AMD, `forward_decode` now returns an empty result pair when it receives zero rows. This can happen, for example, on an idle rank when data-parallel attention is used. Before this PR, only a plain tensor input had this early return. The new input type never reached it, because the fused path was NVIDIA-only. Other AMD kernels next to this one already handle empty input the same way.

NVIDIA behavior does not change.

## Accuracy Tests

I ran GSM8K (a math word-problem test) with 5 examples shown in each prompt, on all 1319 questions. I used lm-eval through the OpenAI-compatible API. The model is Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2, on 2 GPUs (TP2) of type MI355X.

| | flexible-extract | strict-match |
|---|---|---|
| Baseline | 0.9750 ± 0.0043 | 0.9765 ± 0.0042 |
| This PR | 0.9704 ± 0.0047 | 0.9735 ± 0.0044 |

The scores differ by 0.0046 (flexible) and 0.0030 (strict). The "±" values are the standard error, which says how much a score can move by chance. The standard error of the difference is about 0.006, so the gap is within normal noise. Note that the scores for this PR are slightly lower. I ran it only once.

## Speed Tests and Profiling

Setup: Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2, MI355X, 2 GPUs (TP2), 8192 input tokens and 1024 output tokens.

For each GDN layer, the time goes from 10.5 µs (the two kernels together) to 5.1 µs. With 45 GDN layers, that saves about 0.24 ms per decode step.

How to read the table:
- **Concurrency**: how many requests run at the same time.
- **Throughput/GPU**: tokens produced per second on each GPU. Higher is better.
- **TPOT**: the median time to produce one token. Lower is better.
- **TTFT**: the median time until the first token appears. Lower is better.

| Concurrency | Throughput/GPU before (tok/s) | Throughput/GPU after (tok/s) | Change | Median TPOT before (ms) | Median TPOT after (ms) | Change | Median TTFT before (ms) | Median TTFT after (ms) |
|---|---|---|---|---|---|---|---|---|
| 4 | 2,378.69 | 2,452.37 | +3.10% | 7.07 | 6.85 | -3.11% | 290.72 | 289.05 |
| 8 | 3,566.68 | 3,641.11 | +2.09% | 9.69 | 9.48 | -2.17% | 293.38 | 295.49 |
| 16 | 4,730.91 | 4,808.92 | +1.65% | 14.59 | 14.35 | -1.64% | 292.12 | 291.89 |
| 32 | 5,871.85 | 5,923.43 | +0.88% | 23.70 | 23.50 | -0.84% | 311.17 | 310.16 |
| 64 | 7,857.84 | 7,959.61 | +1.30% | 35.99 | 35.52 | -1.31% | 407.43 | 408.42 |

Throughput goes up by 0.9% to 3.1% at every concurrency, and the time per token goes down by about the same amount. At concurrency 4, the time per token drops by 0.22 ms. This is close to the 0.24 ms per step we expect from the kernel time. The gain is largest when concurrency is low, because a decode step is shortest there, so the same saving is a bigger share. The time to first token does not change. This is expected, because this PR only changes decode.
