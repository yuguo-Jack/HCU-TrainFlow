# [Fix] attention: Restore block pointers on Triton 3.9 for FLA kernels

## Motivation

Fixes #45426.

The `lmsysorg/sglang:nightly-cu134-*` images from 2026-10-20 ship torch `2.15.0.dev20261005+cu134`, which pins **Triton `3.9.0+gitaad2a60d`**. That Triton includes triton-lang/triton#10833, which removed block pointers: `tl.make_block_ptr` and `tl.advance` now raise `NotImplementedError` at compile time. The vendored FLA kernels (GDN / KDA: Qwen3.5, Qwen3-Next, Kimi linear attention) use block pointers about 200 times, so these models fail at their first kernel compile. Qwen3.5 dies at prefill CUDA-graph capture in `l2norm_fwd_kernel`.

The MiniMax sparse attention kernels had the same problem, plus a Triton 3.9 autotune-key error. #46135 has since ported them off block pointers and fixed the key on main, so this PR now covers only FLA.

The Triton 3.8.0 release still has block pointers (lowered in its Python frontend to plain pointer loads), so the regular images (torch 2.14.1 + Triton 3.8.0) and Triton 3.7.1 are unaffected.

As in #40805, this is a guarded compatibility shim with a TODO, not a port.

## Modifications

- New `python/sglang/kernels/ops/attention/triton_block_ptr_compat.py`. It does something only when `triton.language` has no `advance` (the Triton build removed block pointers). It then defines `tl.make_block_ptr` / `tl.advance` on top of a small Triton aggregate, and wraps `tl.load` / `tl.store` so they accept `boundary_check` and `padding_option` for it. The lowering follows Triton 3.8.0's own frontend implementation: int64 shape / strides / offsets, per-dimension coordinates broadcast to the block, a bounds mask only on the checked dimensions, and `padding_option` mapped to `other`. On Triton builds that still have block pointers the module does nothing, so behaviour there is unchanged.
- The shim is imported from `fla/utils.py` and `fla/fused_norm_gate.py`. Every module that uses block pointers (the FLA kernels, including the XPU copies) imports one of them.
- TODO: drop the shim once the kernels are ported off block pointers, as upstream FLA did in fla-org/flash-linear-attention#1062.

Alternatives considered:
- Port every call site to plain pointers. Upstream FLA did this in fla-org/flash-linear-attention#1062, a diff of +6088/-5512 lines over 88 files.
- Use tensor descriptors. They can't express the transposed and strided 1-D blocks these kernels load, and they need 16-byte alignment.

## Accuracy Tests

These runs predate the merge of #46135. The MiniMax sparse tests below exercised the shim on MiniMax's old block-pointer kernels, which main no longer has.

**Unit tests**: FLA and MiniMax sparse kernel tests on one B300, run in the `lmsysorg/sglang:dev-cu13` image's tree (ab580b2e) with this patch applied. Each Triton version used a fresh Triton cache. The 3.7.1 and 3.9 builds were put on `PYTHONPATH`, ahead of the image's own Triton 3.8.0.

Files: `test_chunk_gated_delta_rule.py`, `test_kda_kernels.py`, `test_gdn_prefill_layout.py`, `test_fused_norm_gate_strided.py`, `test_kda_gate_beta_cumsum.py`, `test_kda_track_state.py`, `test_minimax_sparse_decode_paged_tile.py`, `test_minimax_decode_topk_page_table.py`.

MiniMax sparse tests that sit at their pre-#45112 path in that tree (`test_flash_with_topk_idx.py`, `test_sparse_gqa.py`; these cover the decode kernels, including the ones that use `tl.advance`): 74 passed on Triton 3.9 + shim and on Triton 3.8.0. `test_minimax_sparse_fp8_attn_gemm.py`, taken from main: 10 passed on Triton 3.9 + shim and on Triton 3.8.0.

The same test list also ran natively in the `nightly-cu134-20261020-306ccf6` image (torch 2.15 + Triton 3.9) on GB200. That run found that zero-padded fp8 loads failed to compile (`cannot cast int32 to fp8e4nv`); the second commit fixes it and is what the `test_minimax_sparse_fp8_attn_gemm.py` result above covers. Everything else passed: 220 tests.

**Generated code**: I compiled test kernels to TTIR on a CPU-only machine with fresh caches. They cover 1-D, 2-D and 3-D blocks, transposed `order`, strided 1-D blocks, `padding_option="zero"`, partial `boundary_check`, and `tl.advance` inside a loop. Triton 3.9 + this shim emits the same TTIR as Triton 3.8.0's own block-pointer lowering. The one difference is the lowering of an fp16-to-bf16 `.to()` cast that isn't on a block-pointer path.

**End to end**: Qwen3.5-35B-A3B (hybrid GDN) on one GB200, TP1, `--reasoning-parser qwen3`. sgl-eval GSM8K, n=200, temperature 1.0, top_p 0.95, max_tokens 16384, top_k 20 from the model's generation config.

## Speed Tests and Profiling

With Triton 3.8.0 or older the shim is inactive and no kernel changes. With Triton 3.9 the shim produces the same IR as Triton 3.8.0's lowering of these block pointers, so I don't expect a speed change against 3.8.0. Not benchmarked.

[by Claude Code] **Severity: style | Confidence: High**

**Issue**

This line adds a new `hasattr(tl, "advance")` check. SGLang's review rules do not allow new `hasattr`/`getattr` checks (`.claude/rules/no-getattr-defensive.md`).

**Fix**

Probe the symbol with an explicit import, as the Triton 3.8 shim in #40805 does:

```python
try:
    from triton.language import advance as _triton_advance  # noqa: F401

    _HAS_BLOCK_PTR = True
except ImportError:  # removed in triton-lang/triton#10833
    _HAS_BLOCK_PTR = False

if not _HAS_BLOCK_PTR:
    ...
```

triton-lang/triton#10833 removes `advance` from `triton.language`, so the `ImportError` branch runs on exactly the builds that need the shim.
