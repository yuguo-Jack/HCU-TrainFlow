# [Perf] [AMD] dsa: Opt-in single-pass Triton top-k for long-context decode rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/47872) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, DSA decode and MTP verify run their top-2048 + page transform through the top-k v2 kernel. At long contexts with 72 or more rows per rank, v2 takes 113 to 127 us per call on MI355X. This PR adds a single-pass Triton/Gluon selector that takes 58 to 82 us there, 1.5x to 1.9x faster. It is opt-in via `SGLANG_DSA_TOPK_TRITON=1` because it is slower than v2 at short contexts; see the table below.

## Modifications

- **New `kernels/ops/attention/dsa/triton_topk_transform.py`**: three launches whose shape depends only on the row count (CUDA-graph safe).
  - `est`: per row, samples about 8192 logits and bit-searches a threshold that leaves about 2 x topk elements above it. Rounding down admits more candidates, but a biased sample can still overestimate the full-row threshold; the selector handles candidate underflow explicitly.
  - `collect`: one pass over the logits on a persistent grid; keys at or above the threshold go to a per-row candidate buffer of 8192 entries.
  - `select`: the exact k-th largest key among the candidates, then exactly min(L, topk) slots through the compact page table (`real_page_table`, page_size 64). This is the table the v2 decode graph keeps, so it needs no page_size=1 table.
- **Exact fallback.** If a row has fewer than min(L, topk) candidates or overflows the 8192-entry buffer, `select` takes the k-th largest key over the whole row and emits from it. This path is slow and rare, but it keeps the result an exact top-k for any input.
- **Dispatch** (`dsa_topk_backend.topk_transform`): this path is used, instead of v2, for decode-shaped PAGED rows when all of these hold:
  - `SGLANG_DSA_TOPK_TRITON=1`;
  - ROCm;
  - 128 rows or fewer;
  - fp32 logits with unit column stride.
- The ROCm and opt-in guards run before importing the optional Gluon selector, so disabled/non-ROCm routes keep their existing dependencies.
- **Tie order.** When the k-th key has ties, which tied elements are taken depends on candidate arrival order. The set is always a valid top-k, but it is not deterministic across calls.
- **Tests** (`test/registered/amd/test_dsa_triton_topk_transform.py`) check against a torch reference, accepting either choice among boundary ties. Cases: random rows (1 to 128 rows, up to 300k), short rows, a row built to overflow the candidate buffer (only the exact path gets it right), an all-equal row, and a biased sample that admits only 256 candidates for top-2048. A separate CPU regression checks that disabled/non-ROCm routes do not import the optional kernel.

## Accuracy Tests

- **Kernel.** The top-k sets equal v2's on every row of the benchmark below (synthetic logits) and on real GLM-5.2 workset logits (48 to 84 rows, contexts up to 659k).
- **gsm8k.** GLM-5.2-MXFP4, TP8 DP8 DP-attention, MTP with acceptance not simulated, 400 questions. This path: 0.953 (one server). Main on the same node and day: 0.943 / 0.945 / 0.932 / 0.930 / 0.920 (five servers). These prompts are short; this checks that nothing else changed.

## Speed Tests and Profiling

**Kernel.** On MI355X:
- inputs: fp32 logits 1M columns wide, 6 rows per request with lengths ctx+1..ctx+6;
- one CUDA graph over 4 logits buffers; us per call, median.

| context | rows | v2 | this PR |
|---|---|---|---|
| 32k | 24 / 48 / 96 / 128 | 18.1 / 18.3 / 19.2 / 19.1 | 33.7 / 34.3 / 38.7 / 39.7 |
| 120k | 24 / 48 / 96 / 128 | 27.5 / 34.0 / 47.6 / 49.9 | 35.2 / 37.9 / 46.4 / 51.3 |
| 400k | 24 / 48 / 72 / 96 / 120 / 128 | 41.0 / 52.9 / 113.0 / 117.5 / 126.6 / 120.8 | 39.9 / 48.7 / 58.1 / 68.5 / 78.0 / 82.0 |

On real workset logits (contexts 235k to 659k), 72 / 84 rows: v2 92.7 / 91.4 us, this PR 44.3 / 44.9 us.

**End to end, short context (where v2 is faster).**
- Setup: GLM-5.2-MXFP4, TP8 DP8 with DP attention, MTP, simulated acceptance 3.61, 96 verify rows per rank.
- Benchmark: random 32k input / 1k output, concurrency 128.
- Result: median ITL is 14.11 to 14.15 ms with this path, against 13.93 to 13.95 ms on main, so it is 1.3% slower. That is why it is opt-in.
- The long-context end-to-end case (where the kernel is 1.5x to 1.9x faster) was not measured here.

## How to reproduce

```bash
python3 test/registered/amd/test_dsa_triton_topk_transform.py -v
SGLANG_DSA_TOPK_TRITON=1 SGLANG_SIMULATE_ACC_LEN=3.61 SGLANG_SIMULATE_ACC_METHOD=match-expected \
SGLANG_SIMULATE_ACC_TOKEN_MODE=real-draft-token python3 -m sglang.launch_server --model-path amd/GLM-5.2-MXFP4 \
  --trust-remote-code --kv-cache-dtype fp8_e4m3 --dsa-prefill-backend triton --dsa-decode-backend triton \
  --mem-fraction-static 0.85 --speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 6 --tensor-parallel-size 8 --data-parallel-size 8 --enable-dp-attention \
  --max-running-requests 128 --cuda-graph-max-bs-decode 16
python3 -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 32000 --random-output-len 1000 \
  --random-range-ratio 1.0 --num-prompts 256 --max-concurrency 128
```

The selector was found with an automated kernel-optimization search. This PR moves it onto the compact page table, adds exact underflow/overflow fallback, and adds the opt-in dispatch and tests.

For a row of length 131072 with top-k 2048, place 256 scores of 100 at sampled positions and leave all other scores zero. The sampled threshold admits only 256 candidates. The current selector takes its exact whole-row fallback only when the buffer overflows, so it returns 256 valid slots and 1792 padding entries instead of 2048 valid slots. The interpreter check does not exercise the Gluon collector or GPU compilation.

The repair will use the existing exact fallback for candidate underflow as well as overflow, add an adversarial regression, and keep optional Gluon imports behind the ROCm/opt-in guards.
