# [Fix] pp: Post the first rank's output recv after its own forward

[Upstream PR](https://github.com/sgl-project/sglang/pull/46027) · state: closed · merged: True

## Original PR description

The first rank posts its output irecv right after launching its forward, but the last rank sends only after its own forward, so the recv spins and holds an SM in the meantime. That blocks any kernel that needs every SM (e.g. flashinfer's MLA), so PP0 stalls each decode step; since #44453 the last rank's relay recv also spins through its forward, and the two stages deadlock.

Add `SGLANG_ENABLE_PP_OUTPUT_RECV_AFTER_FORWARD` (default off), which fences that recv on the rank's `launch_event` (depth 0, no spec relay). With it set, tp8pp2 on 2x8 A100 with flashinfer goes from a hang to TPOT 23.9 ms. It is off by default because triton pays +1.8% TPOT: rank 0 then processes an earlier microbatch's result after its forward instead of during it. With it unset, behavior is the same as main.

## Motivation

Under PP, the first rank posts its output `irecv` right after launching its forward, but the last rank only sends after its own forward finishes. In the meantime the recv kernel spins and holds an SM, which blocks any kernel that needs every SM to make progress. flashinfer's MLA kernel (FA2 on SM80, FA3 on SM90) is one example. Kernels that do not need every SM (e.g. triton attention) do not stall.

- Before #44453: PP0 stalls on every decode step (flashinfer: TPOT 36.5 ms). With this PR it no longer stalls (TPOT 23.8 ms).
- Since #44453: the last rank also posts its relay `irecv` before waiting on its own forward, so its forward can be blocked the same way. The two stages then wait on each other (the TP all-reduce couples the ranks inside each stage) and decode hangs. Reproduced 4/4 on tp8pp2 and tp4pp4, 2x8 A100. With this PR decode no longer hangs.

## Modifications

- Add `SGLANG_ENABLE_PP_OUTPUT_RECV_AFTER_FORWARD = EnvBool(False)` next to the other PP env vars. Off by default, so the default path is unchanged from main. The call-site comment says to turn it on when PP hangs or stalls on kernels that need every SM (e.g. flashinfer MLA).
- When it is set, before the first rank posts its output recv (depth 0, no spec relay), make the comm stream wait on`launch_event`, so the recv starts only after the rank's own forward and never spins alongside it. No host blocking. The check does not depend on the attention backend, and other ranks are unchanged.
- Add a unit test asserting that, with the env var set, only the first rank fences this recv (not later ranks, the specrelay, or depth > 0). The existing two-in-flight deadlock test is unchanged and still covers the default path.

## Accuracy Tests

Greedy outputs are token-identical with the fence on and off (flashinfer and triton, pp2 and pp4). With the env var unset, the code path is the same as main.

- ehuaa · comment · 2026-10-28T05:01:45Z · [source](https://github.com/sgl-project/sglang/pull/46027#issuecomment-6461092211)

> Looks good. But on main, rank 0 can process the next microbatch's result while its own forward is still running. With this PR, that processing has to wait until the forward ends, right?

@ShangmingCai Thanks for your quick review. 
Yes. The overlap you describe only exists because the recv is posted while rank 0's forward runs, and it buys little in either case:

- With persistent kernels that need every SM (e.g. flashinfer's MLA decode, which does a grid-wide sync), there is effectively no such window on main: the spinning recv holds an SM, so rank 0's forward itself waits until the result lands (9.7 -> 17.9 ms on tp8pp2), and decode eventually hangs. With this PR TPOT is 23.9 ms.
- With triton the window is real but small: the last stage can only start that microbatch after rank 0's forward of it, so the result arrived before rank 0's forward ended in only ~13-14% of decode steps, by ~0.2-0.3 ms. Measured on latest main (same server process, fence toggled at runtime), the cost is +1.8% TPOT on tp8pp2 and +0.9% on tp4pp4.

Persistent kernels without a barrier (FA3/FA4, FlashMLA, DeepGEMM) don't hang, but they run one SM short whenever the recv spins, which on main is most of rank 0's forward, so the fence should help them too. If you'd like to keep the overlap for non-persistent backends like triton, I can add an opt-out env var, default on.
