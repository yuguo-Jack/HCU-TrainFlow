[Upstream PR](https://github.com/sgl-project/sglang/pull/31822) · state: open · merged: False

## Original PR description

# TOP dense parity (sglang side): delegate RMSNorm to the fused kernel under TOP + always-on tp-invariant row-linear

## Summary

Two rollout-side changes that make dense Qwen3 true-on-policy (TOP) parity contractual instead of coincidental: under TOP, sglang's RMSNorm and row-parallel matmul now run the *identical* kernel the Megatron training side uses, so `train_rollout_logprob_abs_diff == 0` holds by construction rather than by two implementations happening to agree. Pairs with the Megatron-LM training-side change.

## Changes (2 files)

### `layers/layernorm.py` — RMSNorm delegates to the fused kernel under TOP
Today, under batch-invariant mode + `is_true_on_policy_enabled()`, `RMSNorm.forward_cuda` routes to `forward_native`, which computes the norm as `x * rsqrt(mean(x²) + eps)`. That is a torch reimplementation, not the fused kernel. This change makes the TOP path run `rms_norm_batch_invariant(x, ones, eps)` — the same kernel the Megatron side now calls by direct import.

Why this matters (not cosmetic): the fused `rms_norm_batch_invariant` and `mean + rsqrt` are both batch-invariant but are **not the same op** — they differ by ~3.8e-6. So a `mean+rsqrt` rollout matches a fused-norm training side only by coincidence, and any drift (dtype, torch version) silently breaks `abs_diff == 0`. Delegating both engines to the one kernel makes parity a contract, not a coincidence.

Gated on `is_true_on_policy_enabled()` (non-TOP inference untouched) and `variance_size_override is None` — the fused kernel reduces over the full last dim and can't express partial-slice variance, so those layers keep `mean + rsqrt`. Dense Qwen3 has it `None`, so it always delegates.

### `true_on_policy/contracts.py` — always use the tp-invariant row-linear
`policy_for` sets `uses_tp_invariant_rollout = True` unconditionally instead of gating on `tp_size > 1`. `matmul_tp_inv` is TP-degree-invariant, so always-on matches every `(train_tp, rollout_tp)` combination — including tp=1 both sides (the deterministic tree is marginally slower than a single GEMM but never mismatches). Gating on the local `tp_size` silently diverges whenever the two engines' TP differ (e.g. train_tp>1, rollout_tp=1). The all-reduce-related flags are no-ops at tp_size=1.

## Relationship to the training side
The Megatron plugin imports `rms_norm_batch_invariant` directly and routes its RMSNorm through it, and routes row-parallel matmul through `matmul_tp_inv`. These two sglang changes are the rollout halves of that same delegation, so both engines run bit-identical norm and row-linear reductions.

## Testing
Exercised end-to-end by the TOP parity run (Qwen3 dense, 4×GB300 tp=4): `train_rollout_logprob_abs_diff == 0` depends on the rollout norm and row-linear matching training, which is exactly what these provide. (Note: without the RMSNorm change, a fused-norm training side vs `mean+rsqrt` rollout gives Δ≈3.8e-6, not 0.)

## Follow-up
- `variance_size_override` TOP models fall back to `mean+rsqrt` here, so they'd need a matching sliced path on the Megatron side to stay bitwise-equal. Not a concern for dense Qwen3.
