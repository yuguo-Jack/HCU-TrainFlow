# [Fix] glm: Handle unserializable tool arguments

[Upstream PR](https://github.com/sgl-project/sglang/pull/44111) · state: closed · merged: False

## Original PR description

## Motivation

When a GLM model writes a tool argument as a Python set, bytes, or complex literal, main returns raw markup instead of the tool call. Chat completions streams end with no finish reason or `[DONE]`, and the server logs `TypeError: Object of type set is not JSON serializable`.

GLM-4.5 and GLM-4.6 (`glm45`) and IQuest-Q1 (`iquest_q1`) can reach this on any non-string-typed parameter, because `tool_choice` auto has no grammar. GLM-4.7 and GLM-5.x (`glm47`) reach it through a schema the grammar leaves free, such as `$ref`, or a client constraint.

On one B200 with GLM-4.7-Flash weights, `glm45` and `glm47` failed this way on main and finished with `tool_calls` with this fix. Every run prompted or forced the literal, so unprompted frequency is unmeasured and may be low. An issue search found no user report.

These parsers fall back to Python literal parsing when an argument is not valid JSON, and the result later fails JSON serialization.

Open #43270 and #43264 edit the same lines for a separate tuple bug, and a search of open PRs found no other fix for this crash.

## Modifications

Check the literal result with `json.dumps` in both parsers. If that fails, keep the original argument text, as the Poolside parser does. `iquest_q1` and `ling3` inherit this check.

Two limits stay as on main:

- Where values stream verbatim, a Python literal gives invalid JSON deltas: array, object, and boolean with `glm47`, and declared non-string types with `glm45`. Fixing this needs buffering. Open #43275 changes these `glm47` deltas.
- `{'a': 1e999}` gives non-standard `Infinity`.

#43270 and #43264 conflict with this PR. The second to land keeps both changes, with `json.dumps` before the tuple branch.
