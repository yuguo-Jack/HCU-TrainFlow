# [Feat] rust-server: Report weight versions and media token counts in generate meta_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/46205) · state: closed · merged: True

## Original PR description

## Motivation

The `/generate` schema carries `weight_version` and `weight_versions`, and the Python server's `TokenizerManager` reports them along with the `image_tokens` / `audio_tokens` / `video_tokens` prompt counts. The Rust frontend reported none of them, so a client that records which weight version produced a completion, or reads the per-modality prompt token counts, saw nothing from a Rust-mode server.

## Modifications

The scheduler already computes the weight-version spans of finished requests and the media token counts in every mode. They now ride the scheduler-to-Rust batch header as optional columns after the logprob and hidden-state extras:

- `weight_versions`: per request, the spans of a finished request (`None` for one still running). Sent only when a request in the batch finished, and on a scheduler abort (`push_abort`), whose spans Python's `_handle_abort_req` reports too.
- `image_tokens`, `audio_tokens`, `video_tokens`: sent on every frame of a multimodal model only.

A text decode step with no finished request sends the same six-column header as before. The header stops at its last non-empty column, and a frame that sends the new columns without logprobs pads the 12 extras columns with empty lists; `push_generation` asserts that count whenever it sends extras, so a new extras family cannot shift the later columns silently. The Rust decoder reads these columns per row without the logprob machinery and boxes a `ChunkExtras` only for a row that carries any, so the common `ChunkEvent` does not grow and an unfinished text row allocates nothing.

`GenerateMetaInfo` gains the three media counts (proto tags 18-20, regenerated with `cargo gen-api`; the weight-version fields were already in the schema), and HTTP (unary, streaming, batch) and gRPC frames now carry:

- `weight_version` on every frame: the last span's on a terminal frame, the launch `--weight-version` before it. The Rust frontend has no weight-update endpoint, so the launch value is the current one.
- `weight_versions` on terminal frames, clipped to the completion as `add_weight_versions_to_meta_info` clips them.
- The media counts on every frame when nonzero, as in Python. A scheduler abort frame keeps the counts the stream reported.

A fixture built by Python (`rust/sglang-server/testdata/frame_metadata.json`, from `push_generation`, `push_abort` and `add_weight_versions_to_meta_info`) pins the header encoding, with and without logprob columns, and the rendered keys on both sides: `test_frame_metadata_fixture_matches_python` fails if Python drifts from it, and `frame_metadata_matches_python` decodes it on the Rust side. `metadata_columns_box_only_the_rows_that_carry_them` checks that in a frame with one finished row and no logprobs only that row gets a `ChunkExtras`. The cross-language fixture (`json_parity.json`) has a terminal frame with the new keys.

Not included: `cached_tokens_details`. Python computes it per request on every decode step; sending it in Rust mode would put that work on the scheduler's hot path or need a sparse terminal-only channel.

## Accuracy Tests

Not applicable: no model forward or kernel code changes. Generation output is unchanged; only `meta_info` gains keys.

## Speed Tests and Profiling

Not run. The common decode frame is unchanged: a text decode step with no finished request sends the same header as before, and the new per-row metadata is boxed only for rows that carry it.
