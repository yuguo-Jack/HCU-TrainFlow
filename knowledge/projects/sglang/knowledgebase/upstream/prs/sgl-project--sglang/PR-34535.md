# [Fix] Fix hybrid-SSM DP attention failures at low concurrency

[Upstream PR](https://github.com/sgl-project/sglang/pull/34535) · state: open · merged: False

## Original PR description

## Motivation

Two failures hit a hybrid-SSM (Nemotron-H) deployment running DP attention over a
concurrency sweep (`--tp 4 --ep 4 --dp 4 --enable-dp-attention`, one server per
concurrency level, `--max-running-requests` set to the concurrency).

**1. `--max-running-requests` smaller than `attn_dp_size` gives every worker zero slots.**

The per-DP-worker share `max_running_requests // attn_dp_size` floors to `0`
(e.g. `1 // 4`), so the server fails to launch. On hybrid models it surfaces as a
misleading mamba error, even though the mamba pool has plenty of slots
(`348 // 5 = 69` available, `0` requested):

```
RuntimeError: Hybrid (mamba/linear-attention) state cache is too small to serve any
requests. max_mamba_cache_size=348, mamba_ratio=5, resulting max_num_reqs=0.
```

**2. A decoding rank relabeled as a 1-token extend crashes on a mamba track boundary.**

For hybrid-SSM models `DpPaddingMode.get_dp_padding_mode` forces `MAX_LEN` as soon as
any DP rank is idle while another extends, and `ForwardBatch.prepare_mlp_sync_batch`
then relabels a decoding rank as `EXTEND`, padding each row to a 1-token extend so
every rank presents one shape to the collectives. The rows are still decode rows, but
the mamba metadata reads the label and builds prefill metadata for them. On a step
where one of those rows sits on a `--mamba-track-interval` boundary, the decode
batch's `mamba_track_mask` is set while `mamba_track_seqlens` — populated only by
`prepare_for_extend` — is `None`, and the scheduler dies (traceback from the
`cae69be584` run):

```
  File "python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py", line 297, in _forward_metadata
  File "python/sglang/srt/layers/attention/hybrid_linear_attn_backend.py", line 399, in _init_track_conv_indices
    assert aligned_len is not None, (
AssertionError: conv-state tracking requires mamba_track_seqlens and extend_prefix_lens; this path should only run when the track mask is set on an extend batch
```

With only fix 1 applied, one DP scheduler died this way at every sweep point from
concurrency 64 up (see Testing).

By code inspection, the same relabel also sends the KDA gate preprocessing in
`kimi_linear` / `kimi_k3` down the prefill branch, handing the decode kernel a
`[1, T, H, K]` forget gate and a pre-sigmoided beta, and makes `qwen3_5` build the
strided GDN input views meant for prefill and hand them to the decode kernels.

## Modifications

**1. Per-worker request split** — floor every per-DP-worker split of the global
`--max-running-requests` at 1. Requests are load balanced across workers, so a worker
with 0 slots can never serve anything. The division itself stays floored, so every
consumer keeps sizing from the same per-worker count:

- `KVCacheConfigurator`: the request pool, the mamba pools (including the
  `disable_radix_cache` path, which produced 0-sized pools), the spec-decoding
  intermediate buffers and the GDN ReplaySSM ring reserve
- `compute_swa_request_cap` and `DSV4PoolConfigurator`
- the PD decode in-transfer reserve (`pd_disaggregation_hook`)
- the LoRA MoE CUDA graph buffers
- the MLX resolver, which returned 0 unchecked outside its hybrid branch

**2. `ForwardBatch.logical_forward_mode`** — a new property that reads back through
the decode→extend relabel.
The relabel only decouples tokens from rows for the DP collectives, so the consumers
that need the decode semantics behind the label read it instead of `forward_mode`:

- `Mamba2Metadata.prepare_mixed` builds decode metadata for relabeled rows
- `MambaAttnBackendBase._forward_metadata` builds the decode-side linear-attention
  metadata, and `HybridLinearAttnBackend.forward` dispatches linear layers to decode
- the KDA gate preprocessing in `kimi_linear` and `kimi_k3`
- the GDN input layout in `qwen3_5`, which uses the strided prefill views only for
  real extends

Full attention still runs the 1-token extend; only the state-carrying side is routed
back to decode.

## Testing

Unit tests (CPU), run on the rebased branch:
- `test/registered/unit/server_args/test_server_args.py::TestPdDecodeExtraSlots`:
  the PD decode in-transfer reserve keeps headroom when the cap is below the DP size.
- `test/registered/unit/model_executor/test_pool_configurator.py::TestPerWorkerRequestSplit`:
  with `--max-running-requests 1` on 4 attention DP workers, `resolve_max_num_reqs`
  returns 1 (was 0) and the SWA chunk cap sizes one request (was 0 tokens).
- `test/registered/unit/layers/test_mamba_prefill_track_metadata.py::TestDpDecodeRelabel`:
  a relabeled decode batch on a track boundary goes through
  `MambaAttnBackendBase._forward_metadata` as decode (was the `AssertionError` above);
  `Mamba2Metadata.prepare_mixed` builds decode metadata for relabeled rows and keeps
  real extends as prefills; idle-rank relabels are not read back as decode.

The regression cases in `TestPerWorkerRequestSplit` and `TestDpDecodeRelabel` each
fail with their fix reverted and pass with it.

both fixes on `cae69be584`, before the rebase onto `f3fe753475`. The rebase only
re-applied the per-worker floor where upstream renamed the divisor
