# [Perf] speculative: opt-in step CUDA graph and fused verify / relay paths for EAGLE v2 chains

[Upstream PR](https://github.com/sgl-project/sglang/pull/46211) · state: open · merged: False

## Original PR description

## Motivation

At one to four requests with topk-1 EAGLE v2 chains, a decode step on a fast model is a few milliseconds, and a large
share of it is host work and small launches between the per-stage CUDA graphs (draft, target verify, draft extend):
the verify result's three broadcasts, the sampling-info setup, the relay stash and gathers, the draft-extend tail, and
the step graph's input copies. This PR adds one opt-in flag, `--enable-speculative-step-cuda-graph`, which captures the
decode step as one CUDA graph and turns on six pieces that remove that work. With the flag off (the default), each
changed file runs its existing code. The pieces do not depend on any model or on the megakernel layer.

## Modifications

Every piece below is on with `--enable-speculative-step-cuda-graph` and off without it (the default).

| piece | test / bisect override | what it does | outputs |
|---|---|---|---|
| child-graph splice | none (used by the step graph) | a full-backend graph replay inside an active capture is recorded as a child-graph node | unchanged |
| step CUDA graph | none (the flag itself) | each eligible decode step (draft, target verify, draft extend and the eager work between them) is captured once per key and replayed as one CUDA graph; batch size up to 8; the first two steps of each key run the existing path | bitwise (replays equal eager steps) |
| packed verify broadcast | `SGLANG_SPEC_PACKED_VERIFY_BROADCAST` | one collective per broadcast site instead of three | bitwise |
| lean sampled verify | `SGLANG_SPEC_LEAN_SAMPLED_VERIFY` | temperature through a broadcast view; the target-only tree sampling path without the zero-filled `draft_probs` | bitwise |
| fused relay | `SGLANG_SPEC_FUSED_RELAY` | one scatter launch for the relay stash; row views instead of gathered copies for a single request | bitwise |
| fused draft-extend tail | `SGLANG_SPEC_FUSED_DRAFT_EXTEND_TAIL` | a split-row argmax whose last launch also writes the unit probabilities and the DSA seed rows; meant for use with the step graph, which captures it | bitwise |
| fused input copy | `SGLANG_SPEC_STEP_GRAPH_FUSED_INPUT_COPY` | the step graph's input copies in one launch (13 copies at batch size 1) | bitwise |
| chunked verify sampling | `SGLANG_SPEC_CHUNKED_VERIFY_SAMPLING` (under the lean sampled verify) | the target-only sampling kernel split into per-chunk statistics and a finish kernel, with the same floating-point operations in the same order | bitwise |

- One flag: an override that is not set follows the flag as resolved at startup, so a setup that turns the flag off
  (pipeline parallelism, attention DP, topk above 1, ...) turns the six pieces off too. `=0` turns one piece off
  under the flag, for bisecting; `=1` turns it on without the flag, for tests. Each piece keeps its own eligibility
  checks and falls back to the existing code where they fail.
- Credit: the fused relay carries the change proposed in #41170 behind a switch, rebased onto the current FutureMap;
  the fused draft-extend tail uses the two-stage argmax in `row_argmax.py`, the form proposed for the draft argmax in
  #41172. The chunked kernels set their shared memory with `runtime::set_max_dynamic_smem_per_device` (#41147).
- Related PRs, both now on SGLang main (this branch merges it): #45266 adds a Qwen3.5 binding for megakernel plugins,
  runs a plugin's EAGLE draft entries in the draft and draft-extend graphs and captures a megakernel's KV-length
  attention graph variants; without `--enable-nvidia-megakernel` it changes nothing. #45474 moves the host work between
  the Qwen3.5 MTP decode graphs into graphs, into fewer launches or off the critical path, each piece behind a switch
  that defaults to off; among them are post-verify CUDA graphs for the EAGLE verify's sampling, acceptance and commits,
  and a sampled verify result sent in one broadcast instead of three (the idea of this PR's packed verify broadcast; the
  two now share one allocation, see Base below). This PR captures the whole decode step for any model with full decode
  graphs and needs no megakernel; a step that does not replay exactly the three per-stage graphs is never captured and
  runs the existing path.
- Limitation: while `--enable-speculative-step-cuda-graph` is on, `/update_weights_from_disk` with
  `recapture_cuda_graph` is refused before any weight is loaded. The step graph replays the per-stage graphs it
  captured, and a recapture replaces their runners; recapture support is a follow-up.
- Main's verify opt-ins: with `SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH` set (#45474's post-verify graphs run their
  own graphs inside the verify) or `SGLANG_Q35MF_EDGE_SPARSE_VERIFY_SAMPLING` set (it picks its top-k branch per batch,
  outside the step graph's key), the launch turns `--enable-speculative-step-cuda-graph` off with a warning naming the
  variable and keeps the per-stage graphs.
- Start-up warm-up: when the flag is on and a step graph runner is active, the HTTP server's start-up sends short
  requests with the sampling that a chat request setting no sampling field resolves to (the chat API's own
  `to_sampling_params` over the model's generation config; the tokenizer manager merges `--preferred-sampling-params`
  into it as into any request), in batches of 1, 2, ..., N requests per DP rank. N is the smallest of 8, the largest
  batch size of the per-stage decode graphs and `--max-running-requests` per DP rank. Each batch is one request with
  distinct 3-token prompts and 64 new tokens; the tokenizer manager sends it to the scheduler in one message, so with
  one DP rank its prompts are prefilled together and decode as one batch. The step graph therefore captures the key of
  every batch size from 1 to N, as client requests without sampling fields produce it, before the server takes
  requests; SGLang's own warm-up request captures the greedy batch-size-1 key. A batch size that still has no
  unconstrained key with the warm-up's sampling flags (greedy, top-k, top-p, min-p) afterwards gets one more batch; if
  it is still missing, a warning names it and its key is captured at first use.
  One log line gives the warm-up's time and each captured key with its memory. The warm-up is skipped with
  `--skip-server-warmup` and in the offline engine, and with `SGLANG_RUST_SERVER=1` one log line says it is skipped;
  then every key is captured at its first use, as before.
- Start-up cost: with SGLang's own warm-up request, the server handles 1 + N(N+1)/2 requests per DP rank at start-up
  (2 at `--max-running-requests` 1, 37 at 8; one more batch for a missing size); the N(N+1)/2 added ones each have a
  3-token prompt and 64 new tokens. They appear in the server's request metrics like SGLang's own warm-up request, so
  a client that checks for a server with no earlier requests has to allow for them. In the GLM-5.3 runs below
  (8 x B300, TP 8), the warm-up took 7.7 s at `--max-running-requests` 8, on a host where the same build had started
  before, and 49.0 s at `--max-running-requests` 1, on the first start of this build on its host. The step graphs then
  held 394 MB per GPU at `--max-running-requests` 8 (batch sizes 1 to 8 sampled, 372 MB, plus the greedy batch-size-1
  key, 22 MB) and 44 MB at 1.
- Memory: a key is captured only when every rank has free device memory of at least the largest key captured so far
  (256 MiB before the first) plus 1 GiB. If that check fails while PyTorch's caching allocator holds enough unused
  memory on every rank to cover the need, that cache is released once for the key (`torch.cuda.empty_cache()`, at
  most once per key and 32 times per process) and the check is repeated. Otherwise that key's steps run the existing
  path, the capture is retried every 256 steps, and each rank logs the refusal once per key with its free, needed,
  reserved and allocated memory; each release is logged with the free memory before and after it.
  `/get_server_info` reports under `spec_step_cuda_graph` the `memory_refusals` count, the `last_memory_refusal`
  (batch size, greedy or sampled, constrained or not, and those four memory figures), the `cache_releases` count,
  the `captured_keys` (batch size, greedy or sampled, the top-k / top-p / min-p flags, constrained or not, and MB of
  each), the runner's `max_batch_size` and the caching allocator's `num_alloc_retries` and `num_ooms`. Device memory
  in use can grow
  while serving, so a key first met while serving (a greedy batch above 1, a constrained batch, or a batch size the
  start-up warm-up did not capture) may still be refused (see the agentic-trace runs below for the previous
  revision, which captured batch size 1 only at start-up).
- Kernel inventory: `kernels/ops/speculative/__init__.py` registers the fused draft-extend tail
  (`speculative.draft_extend_tail`, Triton, CUDA only) next to `div_argmax`, as `unit/kernels/test_kernels_namespace.py`
  requires of a public kernel entry point.
- Docs: the new flag in `server_arguments.mdx`; the flag, its six pieces and their overrides, the start-up warm-up,
  the memory check and the cache release in `speculative_decoding.mdx`.
- Tests in this PR: `cuda_graph/spec_step/test_child_graph_capture.py`, `cuda_graph/spec_step/test_eagle_step_cuda_graph_runner.py`,
  `unit/managers/test_single_request_relay.py`, `unit/spec/test_spec_step_graph_fused_input_copy.py` (1 GPU),
  `unit/spec/test_eagle_step_cuda_graph_eligibility.py` (with the memory refusal, the cache release, the start-up

  `e2e/models/test_dsa_glm52_nvfp4_tp_mtp_step_graph.py` (4 GPUs, GLM-5.2 NVFP4).
