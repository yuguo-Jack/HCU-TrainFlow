# [Fix] multi-tokenizer: Broadcast a non-owner's abort to the owning worker

[Upstream PR](https://github.com/sgl-project/sglang/pull/47693) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #47546, covering its "Not covered" case (`tokenizer_worker_num > 1`).

With multiple tokenizer workers, `/abort_request` usually lands on an HTTP worker that does
not hold the rid. That worker forwards the `AbortReq` straight to the scheduler while the
owning worker is still preprocessing the request (pause gate, tokenization, multimodal
feature publication). The scheduler drops an abort for a rid it has not received, and
`abort_request` never resends one, so the request is dispatched afterwards and runs
unaborted while its caller is gone.

The PD consequence is the same one #47546 describes, at scale: on a decode server each
leaked request holds its preallocated KV. We hit this on a production 1P1D
deployment with tens of tokenizer workers: a router retrying prefill capacity
rejections sent ~9,000 aborts in 75 s, most landed on non-owning workers and were dropped,
and the decode KV pool filled with transfers whose senders were gone.

## Modifications

- A tokenizer worker that receives an abort for a rid it does not hold marks the
  `AbortReq` with a new `forward: bool` field (the scheduler does not read it).
- `MultiTokenizerRouter` forwards such an abort to the scheduler as before, and
  broadcasts a new `AbortBroadcastReq(rid)` to all registered workers, reusing the
  pause/continue broadcast channel. The forward handling is factored into
  `_route_worker_obj` so it is unit-testable.
- The worker that holds the rid aborts it locally through `abort_request`:
  - not yet dispatched → finished in place by #47546's skip-dispatch path;
  - already dispatched → the abort is re-sent on that worker's own socket, whose FIFO
    ordering guarantees the scheduler sees it after the generate.
  Workers that do not hold the rid ignore the broadcast (re-forwarding would loop it
  through the router).
- `AbortBroadcastReq` is deliberately a distinct type: a plain `AbortReq` on the worker
  result channel is consumed by `_handle_abort_req` as the scheduler's abort echo, which
  would finish the caller without the dispatched request ever being aborted.

Not covered here (possible follow-up): an abort that arrives before the owning worker has
registered the rid (i.e. during HTTP body parsing). Registration happens before the pause
gate and tokenization, so the broadcast covers the whole preprocessing window that
#47546's scenario needs; the parse-time window needs a pending-abort record and is left
out to keep this change free of false-abort risk.

## Tests

`test/registered/unit/managers/test_tokenizer_manager_rid_cleanup.py::TestAbortForwardBroadcast`
(each behavioral case fails on the pre-fix code):

- a non-owner's abort is marked `forward=True`; an owner's abort and `abort_all` are not;
- the router forwards + broadcasts a `forward` abort, and does not broadcast an owner's;
- a broadcast aborts the owner's undispatched request in place (never dispatched) and
  re-sends the abort for a dispatched one;
- a broadcast for an unknown rid is a no-op (loop prevention).

### issue_comments

- huaiyu-jiang · comment · 2026-11-01T04:23:59Z · [source](https://github.com/sgl-project/sglang/pull/47693#issuecomment-6553371124)

Validation update: I replayed the production incident (an 8,132-request window with an
abort storm) against a 1P1D test deployment whose decode runs 32 tokenizer workers.

- The broadcast works as intended for rids the owning worker has registered: aborts that
  reached a registered owner were handled locally (in the run with #47711 on top, owners
  claimed 35k pending entries back through the router; nearly all of these are
  broadcast-handled aborts, since an abort lands on the owning worker directly only
  ~1/32 of the time).
- It does not cover an abort that arrives before the owner registers the rid. Under the
  storm the owner can enter `generate_request` seconds after the abort (measured p50
  0.1 s / p90 1.3 s / max 26 s before scheduler admission), and those requests still ran
  unaborted and held their preallocated decode KV until the transfer timeout — enough of
  them to fill the decode KV pool.
- #47711 (stacked on this PR) closes that window with a pending-abort table in the
  router; with both, the same replay went from 1,075 to 4,697 successful requests, the
  per-rank transfer/prealloc residue went from 18–31 / 202–244 to 0 / 0, and the
  deployment recovered instantly when idle.
