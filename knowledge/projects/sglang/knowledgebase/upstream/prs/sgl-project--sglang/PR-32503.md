## Original PR description

# Enable HiCache L1<->L2 support on Intel XPU

## Motivation

HiCache, SGLang's hierarchical KV cache, is currently gated to CUDA and ROCm. This PR enables the **L1 (device) <-> L2 (host)** tier on Intel XPU: the host KV pools and the `sgl_kernel.kvcacheio` transfer kernels, which XPU gets from the out-of-tree `sgl-kernel-xpu` wheel.

**Scope: L2 only.** Nothing in this PR calls a storage backend, so it adds no NIXL dependency to the XPU image or CI. L3 (storage) on XPU is a separate, experimental follow-up.

CUDA and ROCm behavior is unchanged. New branches are gated on `_is_cuda or _is_hip` or on `_is_xpu`, and the `record_stream` predicate swap below is a no-op on both.

This PR also fixes a device-generic bug in the L2 transfer path. `L2TransferEngine._record_stream` used `indices.is_cuda` to decide whether index tensors should be recorded on the transfer stream. That predicate is `True` on ROCm but `False` on XPU, NPU and MUSA. On those backends the tensors used by asynchronous transfers were never recorded on the transfer stream, so the caching allocator could reuse them in the middle of a copy. The check is now `indices.device.type != "cpu"`, which covers every accelerator.

## Modifications

### 1. Make L2 transfer stream handling device-generic

- Replace `indices.is_cuda` with `indices.device.type != "cpu"` in `mem_cache/l2_transfer.py`.
- On CUDA/HIP this is a no-op: a device tensor satisfies both predicates and a pinned CPU tensor satisfies neither.
- The same CUDA-specific guard remains at six sites in `hisparse_coordinator.py`. HiSparse is CUDA/ROCm-only and outside this PR.

### 2. Centralize `sgl_kernel.kvcacheio` loading

Add `mem_cache/pool_host/_kvcacheio.py` as the single import gate for the 13 kvcacheio transfer ops. It replaces the five near-identical import blocks in `memory_pool_host.py` and `pool_host/{mha,mla,dsa,mamba}.py`. `pool_host` is on the scheduler import path, so a build without the ops must not break `import scheduler`.

| device | all 13 ops present | some ops missing | module absent |
|---|---|---|---|
| CUDA / ROCm | bound | `ImportError` at import (unchanged) | `ImportError` at import (unchanged) |
| XPU | bound | only the missing ops are stubbed; a pool that needs one is refused at construction | every op stubbed; every host pool refused at construction |
| NPU / CPU / MPS | - | - | stubs that raise `RuntimeError` naming the op at first transfer |

- **CUDA/ROCm keep a single `from sgl_kernel.kvcacheio import (...)`.** It is checked first: an XPU visible next to a CUDA/ROCm GPU is still a CUDA/ROCm build, and a missing op there means a broken build.
- **Other builds bind each op individually via `getattr`.** `sgl-kernel-xpu` can lag the CUDA op set, so the binding is not all-or-nothing. A wheel missing `transfer_kv_all_layer_mla` stubs only that op. MHA still builds on every layout, and MLA is refused only on `kernel` / `layer_first`.
- **Ops that are missing from a kvcacheio-shipping build are recorded in `missing_ops`.** `unavailable_reason` is set only when the module itself is absent.
- **Behavior change for NPU/CPU/MPS (last row).** These devices used to hit a bare `NameError` from a write-back thread. They now get a `RuntimeError` that names the missing op and the reason.

### 3. Refuse unsupported host pools at construction

- `require_kvcacheio_ops(pool=..., layout=..., ops=...)` fails when a host pool is built instead of mid-request in a cache-controller thread. The server never comes up healthy and then fails later.
- `_kvcacheio.py` owns only the import handling and this generic check. It has no knowledge of layouts or pools.
- Each host pool declares its own `_kvcacheio_ops = {io_backend: {layout: op names}}` table directly above its `load_to_device_per_layer` / `backup_from_device_all_layer`. This keeps the table next to the branches it describes.
- A pool is refused only when an op for **its own** `(io_backend, layout)` is missing.
- Every host pool calls it:
  - `MHATokenToKVPoolHost` (the MXFP8 and HiSparse subclasses inherit its table)
  - `AsymmetricMHATokenToKVPoolHost`
  - `MHATokenToKOnlyPoolHost`
  - `MLATokenToKVPoolHost`
  - `DSAIndexerPoolHost`
  - `DeepSeekV4PagedHostPool` and `DeepSeekV4StateHostPool`
- **The check is not device-gated.** It returns immediately when `missing_ops` is empty, which is always the case on CUDA/ROCm (a missing op fails at import) and on CPU/NPU/MPS (no build ships kvcacheio there). In practice only an incomplete XPU wheel reaches it, and the pool files contain no XPU-specific call.
- **The io backend is read lazily.** Host pools are not given the io backend, so the check reads `get_memory().hicache_io_backend`, and only when some op is missing. A complete build never needs published server args, and neither does the CPU suite, which builds pools directly.
- **`is_dummy` MLA/DSA pools skip the check.** They are allocator metadata only, never reach a transfer op, and must stay constructible on a CPU-only box.
- **DSA keeps its every-device `_kvcacheio.unavailable_reason` refusal.**
- **Mamba stays device-keyed.** Its `transfer_kv_mamba_*` kernels are JIT-built from CUDA source, so no accelerator wheel can supply them.

### 4. Harden host-memory allocation

- **Look up the allocator through `get_alloc_memory_func()`.** This is hardening, not a fix for an observed XPU error.
  - On the paths this PR exercises the device is the bare `"xpu"` (`ModelRunner.device`), which `ALLOC_MEMORY_FUNCS` already maps to `alloc_with_pin_memory`.
  - `ALLOC_MEMORY_FUNCS` is a `defaultdict` that defaults to the CUDA `cudaHostRegister` path. A caller passing an indexed device (`"xpu:0"`) or a `torch.device` would get the CUDA allocator without an error. The helper normalizes to the bare device type.
  - It replaces the two inline device-type resolutions in the DeepSeek-V4 pools; the other host pools and `state_capturer/base.py` now call it too.
  - `pool_host/unified.py` still indexes the table with a `torch.device`. That pool is CUDA/ROCm-only and is left unchanged.
- **Raise an explicit error when a pinned allocation returns a null pointer.**
  - torch 2.13.0+xpu returns `data_ptr() == 0` from a failed pinned allocation instead of raising. Measured: 8 GiB succeeds, 2048 GiB returns null.
  - This is pinned host memory for the L2 pool, sized from host RAM; it is unrelated to device free memory.
  - Without the check, the pool is built on a null buffer and the first transfer faults in a cache-controller thread.
  - The check sits in the shared `alloc_with_pin_memory`, so it also runs on NPU and MUSA; whether their runtimes return null here has not been verified.

### 5. Comments and error text

- `hisparse_memory_pool.py`: comment and error text only. They claimed kvcacheio is absent from every non-CUDA/ROCm build, which is no longer true. HiSparse stays CUDA/ROCm-only, and no HiSparse functionality changes.
- The DSA/Mamba error messages name both `--enable-hierarchical-cache` and `--disaggregation-decode-retraction-backup=host_pool`, since the latter reaches the same pools with hierarchical cache off.

### 6. CI

- `pr-test-xpu.yml`: path filter for the new per-commit e2e file.
- `nightly-test-intel.yml` (`nightly-xpu-1-gpu`): installs sglang from the checked-out source (`pip install ".[diffusion]"` with `pyproject_xpu.toml`, as `docker/xpu.Dockerfile` does), replacing the `ci_utils.py` overlay.
  - Without it, the nightly job would run the new tests against the sglang baked into `intel/sglang-dev:latest` until the image is rebuilt.
  - The whole package is replaced, so tests and runtime always come from the same commit. Copying individual files could mix old and new code.
  - The separate `pip install "sglang[diffusion]"` is dropped; the source install already provides the extras.

## Accuracy Tests

### XPU transfer round trip (`stage-a-test-1-gpu-xpu`)

`xpu/test_hicache_transfer_round_trip_xpu.py` checks that `backup_from_device_all_layer` -> `load_to_device_per_layer` is a **bit-exact identity**. It covers every `(io_backend, mem_layout)` pair the XPU build dispatches to: 5 MHA pairs and 2 MLA pairs, **13 distinct kernels** in total. Host indices are offset by one page from device indices, so a kernel that ignores either index tensor fails the round trip.

### XPU end-to-end

- **`e2e/hicache/test_hicache_xpu_no_storage.py`** (`stage-b-test-1-gpu-xpu`, per commit): L1+L2 on both io backends with `Qwen2.5-1.5B-Instruct`.
- **`e2e/hicache/test_hicache_xpu_mla_kernels.py`** (`nightly-xpu-1-gpu`):
  - Launches one server per `(io_backend, mem_layout)`.
  - The model is a locally generated 2-layer DeepseekV3 with real MLA dimensions, so no private HF repo is needed.
- **Shared helper:** `python/sglang/test/hicache_xpu_common.py`.

What every restore case checks:

- **Restores are real.** Each restore asserts that `sglang:load_back_tokens_total` increases, so a pass means the KV actually crossed host -> device and was not served from the device radix cache.
- **Output is bit-exact.** Restored output is compared against a golden that is primed from the device tier. Only the tier differs between golden and restore, not the prefill path.
- **One skip per file is expected.** The abstract `_*Server` base class raises `SkipTest`; each config is a concrete subclass.

### CPU

- `unit/mem_cache/test_hicache_kvcacheio_gate.py` (new) has two parts.
- **Table/dispatch sync.** It parses the host-pool source with `ast` and checks each pool's `_kvcacheio_ops` against the kvcacheio ops its methods actually call:
  - Every called op must be declared, or the construction check would miss it.
  - Every declared op must be called, or the check would refuse a pool that works.
  - `MambaPoolHost` and `UnifiedPageEnvelopeHostPool` are excluded by name; they keep their own device gates.
  - Dropping `page_head` from the MHA table, or adding a stale op to the DSA table, fails it.
- **Gate behavior.** It reloads `_kvcacheio` against a fake `sgl_kernel.kvcacheio`, with the device predicates patched, and covers every row of the table in section 2:
  - CUDA with one op missing fails at import.
  - XPU with one op missing refuses only the pools/layouts that dispatch to it (MHA builds on every layout; MLA is refused on `kernel`/`layer_first` only).
  - XPU without the module refuses every pool.
  - A complete XPU wheel, and a device with no kvcacheio build, never read server args.
  - Reverting XPU to the all-or-nothing import fails two of its cases.
- `unit/mem_cache/test_hicache_host_register.py` adds `test_null_pinned_allocation_raises`: a pinned allocation returning a null buffer raises, while an empty tensor (also `data_ptr() == 0`) does not. Removing the check fails it.
- `unit/mem_cache/test_hicache_staged_write_back_dispatch.py` adds `TestL2TransferRecordStream`.
- The `record_stream` case is mutation-checked: reverting the predicate to `is_cuda` fails `test_non_cuda_accelerator_indices_are_kept_alive`.
- CUDA CI cannot tell the two predicates apart, so the test uses a stub non-CUDA index tensor.

## Performance Tests

### Environment

- Hardware: 4x Intel Arc Pro B60, `tp=4`
- `--page-size 16`, `--max-total-tokens 16384`, `--mem-fraction-static 0.8`
- `TORCHDYNAMO_DISABLE=1` for all configurations (see Environment Notes)


### 1. Shared-prefix workload

**Model:** `Qwen2.5-1.5B-Instruct`

**Workload:**

- `generated-shared-prefix`
- 32 groups x 2 prompts
- 2,048-token system prompt, 128-token question, 64 output tokens
- Concurrency 8
- Shared working set: 65,536 tokens (~4x L1)
- `--hicache-ratio 2.0`

| Configuration | Duration | Req/s | Output tok/s | p50 TTFT | Mean TTFT | p50 TPOT | p50 E2E |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline | 39.6s | 1.62 | 103.4 | 781.6ms | 1521.5ms | 47.9ms | 3710.9ms |
| L2 | 43.8s | 1.46 | 93.6 | 795.7ms | 1666.7ms | 53.0ms | 4166.9ms |

L2 alone is slightly slower here. The working set is ~4x L1, and `--hicache-ratio 2.0` gives L2 room for only half of it, so most prefix lookups still miss and the host transfers are not offset by the prefill they save.

This PR's goal for L2 is a correct tier: the transfer kernels and host pools, verified bit-exact. That tier is what the storage tier builds on, and the TTFT improvement from hierarchical cache on XPU will be reported in the L3 follow-up.

### 2. Low-prefix-reuse workload

**Model:** `Llama3.1-8B`

**Workload:** random ShareGPT prompts, 200 prompts, concurrency 32, `--hicache-ratio 3`.

| Configuration | Req/s | Output tok/s | Total tok/s | Median TTFT | p99 TTFT | Median TPOT | Median E2E |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline | 2.16 | 452.9 | 1108.4 | 151ms | 7454ms | 53.3ms | 8294ms |
| L2 | 1.86 | 389.2 | 952.5 | 185ms | 8601ms | 61.9ms | 9826ms |

This workload has little cross-request prefix reuse, so the tiering and transfer overhead is not offset by cache hits. It is the complementary case to the shared-prefix benchmark: whether HiCache helps depends on how much prefix reuse the workload has.

No performance change is intended for CUDA/ROCm:

- The `record_stream` fix makes the same number of calls.
- `get_alloc_memory_func()` runs once per pool construction.

## Environment Notes

### `TORCHDYNAMO_DISABLE=1` for XPU `tp > 1`

- **Symptom:** without it, the scheduler can segfault (exit code `-11`) while loading a kernel through `torch._inductor`.
- **Trigger:** the `@torch.compile` path for `get_masked_input_and_mask` in `vocab_parallel_embedding.py` when the vocabulary is sharded. It does not reproduce with `tp=1`.
- **Relation to this PR:** none. It is a pre-existing XPU issue, and the setting is applied to every benchmark configuration. The underlying `torch.compile` issue should be fixed in a separate PR.

## Known gaps

- **Mamba on XPU is still refused.** `pool_host/mamba.py` refuses every device except CUDA/ROCm/NPU, because the `kernel` io backend needs the CUDA-JIT `transfer_kv_mamba_*`. The `direct` backend uses only kvcacheio direct ops, which the XPU wheel ships, so it could work on XPU. That is left for a separate change with its own test.
- **`DSAIndexerPoolHost` can now be built on XPU when the wheel supplies the ops, but no DSA model has been run on XPU.**
- **The table/dispatch sync test compares op sets per pool, not per `(io_backend, layout)` branch.** A mis-assigned op fails at first transfer with a `RuntimeError` naming it, not at construction.

I think there may be a distinction worth clarifying here: this check is specifically for **pinned host memory**, rather than device memory.

`alloc_with_pin_memory` allocates the L2 host KV pool in CPU RAM with `pin_memory=True`. The pool size is derived from host RAM (`host_memory_budget_bytes()`), so the device free-memory calculation does not affect this allocation, and the card size (BMG vs. CRI) does not change the behavior.

I would view this less as a workaround and more as a validation of the allocation result before using it to construct the pool. `alloc_with_pin_memory` is shared by XPU, NPU, and MUSA, and the resulting buffer is passed directly to the transfer kernels.

With torch 2.13.0+xpu, a failed pinned-memory allocation does not raise an exception; instead, it can return a tensor with `data_ptr() == 0`. Without this check, the pool can be constructed using that invalid buffer, and the first backup/load operation may subsequently segfault inside a cache-controller thread during a request. With the check, we fail early during startup with a clear error message.

The check is only performed once during pool construction and has no impact when the allocation succeeds.

Ideally, torch-xpu could raise an exception for a failed pinned allocation, consistent with the behavior on CUDA and CPU. I'm also happy to mention this explicitly in the comment so the intent of the check is clear.

For the unit test, I added `test_null_pinned_allocation_raises` to `test_hicache_host_register.py`. It verifies that a null pinned-memory allocation raises an error, while an empty tensor—which can also have `data_ptr() == 0`—does not incorrectly trigger the check. Disabling the check causes this test to fail.
