# [Fix] [AMD] bugfix: Wan2.2 crash due to Triton kernel compilation

[Upstream PR](https://github.com/sgl-project/sglang/pull/40850) · state: open · merged: False

## Summary

On gfx1250 with the Triton that ships in the ROCm SDK, `fuse_scale_shift_kernel` silently computed `x * scale + shift` instead of `x * (1 + scale) + shift`, dropping the identity term from adaLN modulation in every DiT block of every diffusion step. Output was wrong but plausible-looking — no crash, no warning.

This gates the affected modulation math to fp32 on gfx1250 only. All other targets keep byte-identical codegen.

## Root cause

The bug is in Triton's instruction encoding, not in SGLang. gfx1250 is the only target where Triton lowers bf16 elementwise math to packed `v_pk_*_bf16`; every other target promotes to fp32 first. Comparing the two Triton builds for `bf16 + 1.0`:

```
upstream 76940ad3 (fixed):  v_pk_add_bf16 v1, v1, 1.0 op_sel:[0,1]
ROCm SDK 4cff872c (broken): v_pk_add_bf16 v1, v1, 1.0 op_sel_hi:[1,0]
```

The inline constant `1.0` is the **fp32** pattern `0x3F800000`. Its high half `0x3F80` is bf16 `1.0`; its low half is `0x0000`. The SDK build selects the low half for `src1` in both lanes, so the addend is bf16 zero and the operation becomes a no-op.

This affects `+`, `-` and `*` against any AMDGPU hardware inline float constant — `±0.5, ±1.0, ±2.0, ±4.0` — and nothing else. Ordinary literals (`1.5`, `100.0`) are encoded as a packed bf16 pair and are correct; tensor operands are correct. In this kernel `scale_constant` is exactly `1.0`, so it hit the broken case.

The bug is fixed in upstream Triton, and `3865efc` (`[AMD] support gfx1250 on ROCM 10`) already moved the gfx1250 image onto a build that carries the fix (`BUILD_TRITON=1`, `TRITON_COMMIT=76940ad3`). This change keeps SGLang correct on the SDK Triton as well, so correctness no longer depends on which Triton the image happens to ship.

## Why fp32 and not `tl.full`

`tl.full` looks like it should keep the constant out of the immediate, but it does not — LLVM folds the splat straight back in. Measured on the broken build:

| form | result | emitted ISA |
|---|---|---|
| `scale_constant + scale` | wrong | `v_pk_add_bf16` + inline const |
| `tl.full(...) + scale` | wrong | `v_pk_add_bf16` + inline const |
| fp32 promote | **correct** | no packed bf16 immediate |

fp32 promotion was the only form that produced clean ISA. It also keeps a single rounding on store, matching what the layernorm scale/shift kernels in this same file already do.

## Scope

Gated behind `is_gfx1250_supported()` and passed as a `tl.constexpr`, so Triton resolves the branch at compile time — no runtime branch, and the `else` arm is the original code verbatim. NVIDIA, XPU, gfx942 and gfx950 compile to exactly what they did before, including the `tl.full` splat, so their numerics stay bit-identical. `is_gfx1250_supported()` is `lru_cache`d and returns `False` on non-HIP builds without touching CUDA.

The kernel is shared by 11 DiT families, so this is not Wan-only: `wanvideo`, `causal_wanvideo`, `hunyuanvideo`, `hunyuan3d`, `qwen_image`, `glm_image`, `joy_image`, `helios`, `lingbot_world`, `longlive2`, `mova_video_dit`. They reach it through `LayerNormScaleShift` / `RMSNormScaleShift` / `ScaleResidualRMSNormScaleShift` with the default `scale_constant=1.0`. The VAE is unaffected — adaLN is a transformer construct, and an ISA scan over a full Wan2.2 run (1307 kernels, 118 using packed bf16) found this kernel as the only affected one.

## Testing

After this PR is applied, the video can be played. Extracted pic comparison as below:

<img width="1852" height="564" alt="comparison_patched_and_unpatched" src="https://github.com/user-attachments/assets/83afe6b6-d62a-4dff-9827-e7a4a59508b2" />

Tested on rocm/sgl-dev:v0.5.20-rocm10-mi45x-test-triton4cff872c-20260923.

Existing unit test `test_scale_shift_4d_matches_torch`, run against both Triton builds:

| Configuration | Result |
|---|---|
| ROCm SDK Triton (broken), with fix | 16 passed |
| Upstream Triton (fixed), with fix | 16 passed — no regression |
| ROCm SDK Triton, fix reverted | **3 failed** (the bf16 + `scale_constant=1` cases) |
| ROCm SDK Triton, gate forced off | **3 failed** — confirms the `else` arm is the original path |

End-to-end Wan2.2-T2V-A14B on the broken SDK Triton (720×1280, 193 frames, 8 steps, seed 42) completed cleanly and matches a known-good baseline generated on the fixed Triton: correlation **0.991**, PSNR **29.3 dB**, mean abs diff 4.3/255. A dropped identity term collapses structure, so this margin is rounding and sampling non-determinism, not lost conditioning.

Performance is unchanged. `bench_scale_shift_4d.py`, 3 runs each way, medians: 117.7 vs 119.9 µs (wan), 16.23 vs 16.24 µs (longlive). Within-group spread was ±20% on the larger workloads, so those deltas are noise — the kernel reads three tensors and writes one with no reuse, so it is bandwidth-bound and the extra `v_cvt` ops hide behind memory latency.
