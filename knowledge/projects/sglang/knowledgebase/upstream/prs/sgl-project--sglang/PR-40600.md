# [Bug][mem_cache] Split abort cleanup so FlexKV cancels before STORE and LMCache ends the session after it

[Upstream PR](https://github.com/sgl-project/sglang/pull/40600) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #40360.

`LMCacheUnifiedRadixCache.release_aborted_request` previously closed the LMCache session during cancel. That is the #40334 failure mode: abort paths that still STORE (optimistic retry, decode waiting-queue abort, transfer failure) would finish the session before STORE. Main deleted `lmc_radix_cache.py`; this PR ports the two-phase fix onto the unified cache.

FlexKV has the opposite constraint. It must cancel in-flight lookup/prefetch *before* KV finalization / STORE, otherwise abort cleanup can `dec_lock_ref` a node whose async STORE is still on `store_stream`.

A single hook cannot sit both before and after KV finalization.

## Modifications

Split abort cleanup into two phases:

1. `cancel_aborted_request_work` — drop pending lookup/prefetch before optional STORE. FlexKV keeps its existing `release_aborted_request` on this path. LMCache cancels external flows / markers only; it does **not** `finish_request` here.
2. `finish_request_session` — close backend session state after optional STORE, or immediately when no STORE runs. LMCache `finish_request` lives here and is once-per-session (idempotent). Other backends default to no-op.

`abort_prefix_cache_request` orchestrates: cancel, then optional `release_kv_cache` (STORE via `insert_req`, then session close), else session close immediately. Success-path `release_kv_cache` / `insert_req` also request session finish after STORE.

Prefill transfer/bootstrap failure and waiting-queue aborts go through the same helper so FlexKV still cancels first. `StreamingSession` forwards the new methods to the inner cache.

CPU fake-connector tests cover abort-after-lookup, cancel-does-not-finish-session, insert_req STORE-before-finish, waiting-queue abort with no STORE, and the FlexKV cancel-before-STORE lock (`CustomTestCase`).

- copilot-pull-request-reviewer[bot] · comment · 2026-09-21T16:32:06Z · [source](https://github.com/sgl-project/sglang/pull/40600#discussion_r4064238523)

File: `python/sglang/srt/mem_cache/storage/lmcache/lmc_radix_cache.py` · line None

`finish_request_session` unconditionally sends `END_SESSION`, but an aborted prefill-bootstrap request can be finalized twice: `abort_request` calls the new helper while the request remains in `PrefillBootstrapQueue`, then `sender.abort()` makes the next `pop_bootstrapped` call `handle_bootstrap_failure`, which calls the helper again. The LMCache contract is not guaranteed to make duplicate `end_session` calls safe; make finalization once-per-active-session (resetting that state when a new session starts), or remove/mark the queue entry before the second path.

- copilot-pull-request-reviewer[bot] · comment · 2026-09-21T16:32:07Z · [source](https://github.com/sgl-project/sglang/pull/40600#discussion_r4064238590)

This ordering test calls the fake connector's `store_kv` directly, so it never executes the production `LMCRadixCache.cache_finished_req` path whose `end_session` call was moved, nor the LMCache-specific `release_kv_cache` integration. A regression that closes the session inside `cache_finished_req` (before STORE) would still pass. Add a CPU fixture that drives the actual MP cache finalization path and asserts `store -> end_session`.
