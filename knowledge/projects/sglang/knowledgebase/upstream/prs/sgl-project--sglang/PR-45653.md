# [Fix] anthropic: reject non-string tools[*].type with a 400, not a plain-text 500

[Upstream PR](https://github.com/sgl-project/sglang/pull/45653) · state: open · merged: False

## Original PR description

## Motivation

A request to `/v1/messages` or `/v1/messages/count_tokens` whose `tools[*].type` is not a string (e.g. `["web_search_2025"]` or `true`) returns `500 Internal Server Error` as **text/plain**, instead of the Anthropic-style 400 JSON error that every other malformed field gets. Clients that parse the error body fail twice. The engine itself stays healthy.

Cause: `_tool_discriminator` (the `Discriminator` callable on the `AnthropicTool` union) calls `t.startswith(...)` on the tag. A non-string tag raises `AttributeError` *inside the discriminator*; pydantic surfaces that as a bare exception rather than a `ValidationError`, so FastAPI's `RequestValidationError` handler never runs and Starlette emits its default 500.

```
File ".../sglang/srt/entrypoints/anthropic/protocol.py", in _tool_discriminator
    if t.startswith("web_search_"):
AttributeError: 'list' object has no attribute 'startswith'
```

## Modifications

- `protocol.py`: a non-string tag selects the `custom` variant, so `AnthropicCustomTool.type: Optional[Literal["custom"]]` rejects it as a normal `ValidationError` at `tools.N.type`. The existing `/v1/messages*` handler then returns `400 {"type":"error","error":{"type":"invalid_request_error","message":"tools.0.custom.type: Input should be 'custom'"}}`. String tags take exactly the same path as before. (Raising from the discriminator is not an option; that is the bug.)
- `test/registered/unit/entrypoints/anthropic/test_serving.py`: `test_non_string_tool_type_is_a_validation_error` (list / bool / int / dict, asserts the error loc names `tools`, the index and `type`), the same for `AnthropicCountTokensRequest`, and `test_string_tool_types_still_select_their_variant` (absent, `custom`, `web_search_*`, `computer_*`, `bash_*`, `text_editor_*`).
