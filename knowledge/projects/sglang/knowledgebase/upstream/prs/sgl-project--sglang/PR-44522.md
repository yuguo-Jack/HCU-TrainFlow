# [CI] [AMD] rust-ext: Build Rust extensions once in stage-a and reuse them in later stages

[Upstream PR](https://github.com/sgl-project/sglang/pull/44522) · state: open · merged: False

## Original PR description

## Motivation

Every AMD CI job compiles Rust from scratch. In a full post-merge `PR Test (AMD)` run (38714215467, 28 jobs):

- 22 jobs built `sglang-radix-tree` (`mem_cache`) at server start, ~70–85 s each, about 27 min per run inside the test step.
- Every job's editable install compiled `_multimodal` in place. In a source checkout under the default `SGLANG_RUST_BUILD_MODE=auto` the loader never imports in-package modules, only fingerprinted ones from its cache, so that build went unused.

CUDA solves this with `_pr-test-rust-ext-build.yml`, which builds once per run and hands the modules to the test stages. That can't be reused as-is on AMD: `sglang-radix-tree` links the CI image's own ROCm libtorch, so it has to be built in that image.

## Modifications

- **stage-a** (`stage-a-test-1-gpu-small-amd`) builds `mem_cache`, `mem_cache_inspection` and `_multimodal` through the real loader after installing dependencies. Its own tests reuse them from the cache, and it uploads the loader's `artifacts/` tree as `rust-ext-amd-<rocm_version>-<runner_arch>` (one-day retention), tagged with the container's image ID. Both steps are `continue-on-error`.
- **stage-b/c jobs** on the same runner arch (1-gpu small, nondeterministic, 1-gpu large, 2-gpu large, 4-gpu, 8-gpu) download it when their `wait-for-stage-*` dependency succeeded. The install script then seeds the container's runtime cache with it.
- **All AMD installs** use `SGLANG_BUILD_RUST_EXTS=none` for the editable install.
- New helpers: `scripts/ci/amd/amd_ci_rust_ext_cache.{sh,py}`.

### No stale modules

Reuse is gated twice, and either gate falling through just means building at runtime, as today:

1. The artifact is only imported into a container running the exact image that built it. This covers libtorch bytes that differ between images of one torch release, e.g. mi30x vs mi35x.
2. The build mode stays `auto`, so the loader looks modules up by its own fingerprint (Rust sources, cargo/rustc, Python ABI, torch version/HIP/C++ ABI). A module built from anything different is never found.

Not covered:
- mi35x jobs run a different image, so they would always miss and get no download step.
- `pr-test-amd-extra.yml` and the nightly run as separate workflow runs, so they only get the install-time saving.
- There is no cross-run actions/cache layer, because the repo cache is at its 10 GB limit.

## Accuracy Tests

N/A. CI-only change; runtime code is untouched.

## Benchmarking and Profiling

Validated locally with CPU torch 2.14.1:
- **Export:** builds all three modules; `mem_cache_inspection` reuses the production target dir and takes ~17 s.
- **Import:** a fresh cache loads all three in 2.6 s, with no cargo invocation.
- **Changed source:** after editing a radix-tree source file, the seeded module is not found, so the job rebuilds.
- **Image check:** the host script declines a missing or mismatched image ID.

### Expected savings

| Scope | Runner time saved | Share |
|---|---|---|
| Full AMD PR run (run 38714215467, 28 jobs, 11.6 h) | ~26–47 min | 3.8–6.7% |
| All AMD workflows, Oct 8–15 (5,858 jobs, 2,913 h) | ~73–144 h/week | 2.5–4.9% |

- **Lower bound:** only the removed `mem_cache` builds (~74 h/week across 3,548 stage-b/c PR jobs), net of ~1.5 h/week of extra inspection builds in stage-a.
- **Upper bound:** also counts the whole ~44 s editable build in every AMD job. The Rust share of that step wasn't measured; comparing the step's duration on this PR's AMD run will pin it down.
