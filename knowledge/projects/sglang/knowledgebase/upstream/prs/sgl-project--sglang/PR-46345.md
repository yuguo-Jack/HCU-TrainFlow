# [Fix] processor: Keep repr digits for floats at a power of two

[Upstream PR](https://github.com/sgl-project/sglang/pull/46345) · state: open · merged: False

## Original PR description

## Motivation

`python_float` in `rust/sglang-processor/src/py.rs` reproduces Python's `repr(float)`, which `json.dumps` uses. The Qwen3-Coder and Kimi-K3 tool parsers use it to write typed tool-call arguments, and so does `python_json_reencode` for JSON object and array arguments.

For 46 of the 2046 positive powers of two, it prints a decimal that parses back to a different float. One of them is 2^-24, the smallest positive fp16 subnormal, which a model can plausibly write as a tool argument:

| value | Python `repr` | `python_float` on main |
|---|---|---|
| 2^-24 | `5.960464477539063e-08` | `5.960464477539062e-08` |
| 2^-44 | `5.684341886080802e-14` | `5.684341886080801e-14` |
| 2^89 | `6.189700196426902e+26` | `6.189700196426901e+26` |
| 2^-791 | `7.678447687145631e-239` | `7.678447687145630e-239` |

The output on main is never the float the model wrote. A client therefore receives tool-call arguments with a changed value, and the arguments differ from what the Python server returns for the same output.

The non-streaming path is `POST /v1/chat/completions` with `--tool-call-parser qwen3_coder`: `sglang-server/src/api_server/http/openai/chat.rs:489` calls `parse_chat_tool_calls` (`openai/tools.rs:84`), then `sglang-processor/src/parser/tools.rs:280` picks `Qwen3CoderDetector`, and `convert_param_value` calls `python_float` (`tool_call/models/qwen3_coder.rs:407`) or `python_json_reencode`, which calls it at `py.rs:394`.

### Root cause

`python_float` takes the digit count from Rust's shortest round-trip formatting (`{:e}`). It then reformats with that many digits (`{:.*e}`) to get the nearest decimal, which picks the same tie-breaking as `repr`. At a power of two, the gap to the float below is half the gap to the float above. The nearest decimal with the shortest length can then fall inside the interval of the float below. For 2^-24 the exact value is `5.9604644775390625e-08`, a tie at 16 digits. Rounding half to even gives `...062e-08`, and that decimal is closer to the float below 2^-24 than to 2^-24 itself. `repr` gives `...063e-08`, the 16-digit decimal that round-trips.

## Modifications

Keep the reformatted digits only when they parse back to the input. Otherwise use the shortest digits from `{:e}`, which always round-trip. The tie case the reformatting exists for (`77947932308658.125` to `77947932308658.12`) is unchanged, because its rounded digits round-trip.

### Tests

Thanks for the review! The use case is tool-call arguments on the Rust server. With `--tool-call-parser qwen3_coder` (or `kimi_k3`), a `number` parameter, or any float inside an object/array argument, goes through `python_float` to match Python's `json.dumps`. For the affected values the client gets a different float from the one the model wrote, and a different response from the Python server for the same output. For example, a model passing `5.960464477539063e-08` (2^-24, the smallest fp16 subnormal, a plausible `eps`/tolerance argument) gets `5.960464477539062e-08` back.

To be transparent: I found this with a differential sweep of `python_float` against CPython `repr`, not from a user report. 46 of the 2046 positive powers of two were affected, and every other value in the sweep already matched.
