## Motivation

A tree keeping several windows still singled out its first window (only it set a match's branch point, deferred its host backup and dropped the lower locks on an early release), the storage's public surface exposed a "primary" window name, and the storage plan handed out the tree's slot ids. This PR keeps the target window off the storage surface, lets the tree number its own slots, and treats every window of a several-window tree alike.

## Modifications

- Target window: readers that size a single window (the decode queue's window budget, a running request's retention, the static window pools' name) ask the allocator (`target_window_pool`); `primary_window_name` is removed from both storages. The static pools' window pool name is declared once (`BaseSWAKVPool.WINDOW_SUB_POOL`).
- Slot ids: `tree_slot_ids` lives with `ComponentType`; the plan describes slots by name and family only, and the storage maps a tree slot to its sub-pool by name (`KVStorage.tree_sub_pool(slot)`). Every slot keeps the id it had.
- Windows alike: whether windows stand alone is decided once (`windows_stand_alone`). A single window stays coupled to the token slot as before. With several windows, every window sets the branch point, backs up inline, and releases its own prefix lock early; the lower locks on the node go once every window has gone (`dec_locks_below_windows`).
- Scalar reads by name: `window_evictable_size(sub_pool)` / `window_protected_size(sub_pool)` replace `swa_evictable_size` / `swa_protected_size` in the caches, tree-core interface and native adapter; `swa_reprefill_tail_tokens` becomes `window_reprefill_tail_tokens`.
- Tests: the prefix-cache trace now records each match's window branch point and a three-window tree (16, 8 and 4 tokens) with the re-prefill tail; every window of a three-window tree releases its prefix lock the same way.

**Behavior changes (trees with several window slots only, i.e. a fused draft window of another length):**
- The first window of a several-window tree backs up inline instead of deferring to the controller.
- Lower locks (such as a state slot's) are released once every window has released, not with the first window.
- The re-prefill tail uses the longest window's length (it used the first window slot's, which differs only when a further window is longer).

With one window every answer is unchanged; the recorded branch points and re-prefill tails are unchanged.
