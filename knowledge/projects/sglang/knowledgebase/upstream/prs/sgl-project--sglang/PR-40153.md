# Let decode ranks contribute passive Mooncake store capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/40153) · state: open · merged: False

## Original PR description

## Motivation

Only ranks that link to the Mooncake store mount a segment into it. In a
disaggregated deployment the decode ranks default to a chunk cache, so their
host memory never joins the pool no matter how free it is, and the shared
prefix cache is bounded by prefill-node DRAM alone. Under a long-context
agentic workload the store then evicts prefixes that the decode nodes had room
to hold.

## Modifications

A disaggregated decode rank now lends host memory to the Mooncake store when it
is configured the same way a prefill rank sizes its segment:
`MOONCAKE_GLOBAL_SEGMENT_SIZE` explicitly set to a positive size, with
`MOONCAKE_MASTER` set. This mirrors vLLM's embedded store mode, where every
worker that has the store configured contributes `global_segment_size` and the
role only decides whether it reads or writes. The decode rank mounts a segment
but attaches no cache pool, so it neither reads nor writes KV.

The contributor is created in `build_kv_cache` and held by the scheduler for the
process lifetime, independent of the KV transfer backend (NIXL, MoRI or
Mooncake).

No capacity is lent when:
- the size is unset or 0;
- `MOONCAKE_STANDALONE_STORAGE=1`, where a local store service owns the node's capacity;
- the decode rank runs the external cache linker, which already mounts its own segment;
- `MOONCAKE_MASTER` is unset, in which case the size is ignored with a warning rather than failing startup.

**Behavior change:** deployments that already export
`MOONCAKE_GLOBAL_SEGMENT_SIZE` and `MOONCAKE_MASTER` to decode workers (for
example one environment shared by all roles) will now mount decode capacity. To
opt out, leave the size unset on decode, set it to 0, or use standalone mode.

## Accuracy Tests

No change to generated output: the contributing rank attaches no cache pool and
performs no cache I/O, so the KV path is untouched.

## Benchmarking and Profiling

DeepSeek-V4-Pro, NVFP4, on GB300, disaggregated with 8 prefill nodes (TP8/EP8
per worker) and 4 decode nodes (TP16/EP16), agentic coding trajectories at
concurrency 1920, MTP with a fixed acceptance length, one hour of measurement
per run.

| | store capacity (host DRAM) | objects evicted | steady-state prefix hit | output tok/s | total tok/s | total tok/s/GPU |
| --- | --- | --- | --- | --- | --- | --- |
| baseline | 4.5 TB (32 ranks x 140 GB) | 12.6M / 12.9M / 12.3M | 92.7-92.9% | 33,739 / 34,737 / 33,919 | 4,397,386 / 4,536,507 / 4,434,760 | 91,612 / 94,511 / 92,391 |
| decode sized | 6.7 TB (48 ranks x 140 GB) | 10.9M / 10.9M / 10.5M | 95.2% | 44,612 / 44,724 / 44,671 | 5,908,589 / 5,928,177 / 5,947,669 | 123,096 / 123,504 / 123,910 |
| mean | +50% | -15% | +2.4 pts | 34,132 -> 44,669 (+30.9%) | 4,456,218 -> 5,928,145 (+33.0%) | 92,838 -> 123,503 |

Three runs per arm. Run-to-run spread is 1.6% on the baseline and 0.3% with decode
capacity, well below the gap. Total tok/s counts cached prefill input, so it rises
faster than output tok/s: the extra capacity is exactly what stops those
prefixes from being evicted and recomputed.

The eviction count falls by less than the capacity grows because the store
evicts a fixed fraction of a now larger population each time it crosses its high
watermark. What changes is how long a prefix survives before its turn comes,
which is what the hit rate measures.

The two arms differ only in decode capacity and the branch under test; the image,
recipe, topology and acceptance length are identical.

[by Claude Code] **Severity: functional | Confidence: High**

**Issue**

This check misses decode KV offload. With `--disaggregation-decode-enable-offload-kvcache`, `DecodeKVCacheOffloadManager` builds a `HiCacheController` with `--hicache-storage-backend`, and that controller creates its own `MooncakeStore` and segment. Offload forces `cpu_tensor` retraction and does not enable HiCache, so this function returns `False` for both the chunk cache and the decode radix cache. `build_kv_cache` then mounts a second segment through the contributor.

**Example**

Decode with offload, `--hicache-storage-backend mooncake`, `MOONCAKE_MASTER`, and `MOONCAKE_GLOBAL_SEGMENT_SIZE=140gb`: each rank now runs two Mooncake clients and pins twice the host memory. On CPU, the two helpers return `False` and 140 GiB for this config.

**Fix**

When `disaggregation_decode_enable_offload_kvcache` is set, return `hicache_storage_backend is not None`. Add this case to `test_decode_cache_owns_store_matches_tree_cache_selection`.

**Issue**

This config leaves `dp_rank` at its default of 0. `MooncakeStore.__init__` names each rank's SSD offload dir `rank_{dp_rank}_{tp_rank}_{pp_rank}_{attn_cp_rank}`. With DP attention, every decode rank also has `attn_tp_rank=0`, so all DP ranks on a node share one dir. The comment in `MooncakeStore.__init__` says a shared dir silently truncates another rank's bucket files.

**Example**

Decode TP16 with DP attention, and `MOONCAKE_ENABLE_SSD_OFFLOAD=1` plus `MOONCAKE_OFFLOAD_FILE_STORAGE_PATH` in the env shared with prefill: the 4 decode ranks on each node all use `rank_0_0_0_0`.

**Fix**

Pass `dp_rank=parallel.attn_dp_rank`, as `HiCacheController._generate_storage_config` does.

- ShangmingCai · comment · 2026-10-12T10:01:20Z · [source](https://github.com/sgl-project/sglang/pull/40153#discussion_r4246762640)

File: `python/sglang/srt/mem_cache/kv_cache_builder.py` · line 273

This is not true for the linker. On decode the chunk cache still goes through `create_unified_radix_cache` (the `ctx.disable_radix_cache` branch in `registry.py`), and the `elif enable_unified_cache_external_linker` there still attaches the linker, which creates its own `MooncakeStore(storage_config, mem_pool=None)` in `MooncakeDirectLinker.__init__`. So decode + mooncake linker + `cpu_tensor` retraction will mount two segments per rank.

`cpu_tensor` is also the default retraction for MLA/DSV4 decode since host_pool only supports MHA/SWA pools, so anyone who launches decode with the same linker flags as prefill will hit this.

Together with the decode offload case in the other comment, I think it's simpler and safer to just skip the contributor when decode has offload or the linker enabled, instead of mirroring the tree cache selection logic here, which is easy to get out of sync later.
