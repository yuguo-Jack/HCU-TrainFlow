# [Fix] KDA: Compile the CuTe DSL decode kernel for the caller's dt_bias dtype

## Motivation

`_get_compiled_kernel` in `cutedsl_kda.py` compiles the CuTe DSL KDA decode kernels against a bf16 `dt_bias` placeholder, and the dtype is not part of the compile-cache key. CuTe launches do not check tensor dtypes, so when a caller passes an fp32 `dt_bias`, the kernel reads the fp32 bytes as bf16. Kimi-Linear keeps `dt_bias` in fp32 (`kimi_linear.py`), and `kda_cutedsl.py` forwards it without a cast. So with `--linear-attn-decode-backend cutedsl` the forget gates are wrong, and NaN shows up in the decode output and in every state slot the batch touches.

## Modifications

- `cutedsl_kda.py`: compile with the caller's `dt_bias` dtype, and add the dtype to the compile-cache key. The kernel bodies are unchanged; they already convert `dt_bias` to fp32 on load.
- New `test/registered/kernels/ops/attention/test_cutedsl_kda.py`, modeled on `test_cutedsl_gdn.py`. For batch sizes 16 and 128, with dense and varlen inputs, it runs bf16 and then fp32 `dt_bias` at the same shape. Over 3 decode steps it compares the outputs and the whole state pool against Triton `fused_sigmoid_gating_delta_rule_update(is_kda=True)`, with one padded `-1` slot. Running both dtypes at one shape means a kernel compiled for one dtype cannot quietly serve the other.

## Accuracy Tests

The new test on one H200 (H = HV = 32, K = V = 128):

| | bf16 `dt_bias` | fp32 `dt_bias` (as in Kimi-Linear) | test |
|---|---|---|---|
| main | matches Triton | NaN, 97% of outputs mismatched | 4/4 fail |
| placeholder dtype fixed, cache key unchanged | matches Triton | NaN (reuses the bf16 kernel) | 4/4 fail |
| this PR | matches Triton | matches Triton | 4/4 pass |

`test_cutedsl_gdn.py` still passes.

## Speed Tests and Profiling

The kernels are unchanged. A model compiles one variant for its `dt_bias` dtype, and nothing is added per call.
