# [AMD] Support compressed-tensors W4A16 linear layers on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/39135) · state: open · merged: False

## Original PR description

Enable symmetric compressed-tensors W4A16 linear layers on ROCm using optional vLLM GPTQ operators, with format/shape guards and FP16 arithmetic. Supports the vLLM operator signatures from before and after vllm-project/vllm#54809.

Ported from patch 7 in my [strix-halo-sglang](https://github.com/JeremiahM37/strix-halo-sglang) repo.

Validation on gfx1151: 26 tests passed, with real numerical cases on standalone builds of both vLLM GPTQ kernel versions; pre-commit passed. `jy395/Qwen3-8B-rtn-w4a16` with every quantized Linear served through this scheme scored 85/100 on gsm8k, against 88/100 for a dense model from the same checkpoint. Full-server integration and a real vLLM install have not been tested.

- JeremiahM37 · comment · 2026-11-04T01:23:35Z · [source](https://github.com/sgl-project/sglang/pull/39135#issuecomment-6619954937)

Thanks @vivienfanghuagood. Try `jy395/Qwen3-8B-rtn-w4a16`: symmetric 4-bit, group size 128, `pack-quantized`, no `actorder`. Its config validates under compressed-tensors 0.16.0, 0.18.0 and 0.20.1. `nm-testing/TinyLlama-1.1B-Chat-v1.0-W4A16-e2e` is the same format if you want a quick load first.

I've rebased onto current `main` and added a commit for vllm-project/vllm#54809, which removed `g_idx` from `gptq_gemm` and `gptq_shuffle`. Both signatures now work, so please test the new head.

What I ran with that checkpoint on gfx1151, with every quantized Linear served through this scheme, against a dense model built from the same checkpoint:

| | This PR | Dense FP16 |
|---|---:|---:|
| gsm8k, first 100, greedy | 85/100 | 88/100 |
| Throughput, batch 8 | 51.6 tok/s | 26.4 tok/s |
| Relative error per layer, against exact | 0.09–0.15% | 0.02% |

- The kernel shows no scale bias (1.00000 on the layers I checked), so I read the extra error as its FP16 accumulation. The gsm8k gap is 3 questions on a sample of 100, so it doesn't separate the two.
- This isn't a server run. It used a Hugging Face model with standalone builds of vLLM's GPTQ kernels, not a vLLM install, and I stubbed `sgl_kernel` at import because this path doesn't call it. I also haven't run it on RDNA3 or RDNA4, so your gsm8k and throughput run would cover what's missing.
- `actorder: weight` or `static` checkpoints, which is most current GPTQ uploads, are still refused here. compressed-tensors documents that these don't change the stored format, so they could be allowed, but I haven't tested that. I can add it if you think it belongs in this PR.

- vivienfanghuagood · comment · 2026-11-04T02:57:41Z · [source](https://github.com/sgl-project/sglang/pull/39135#issuecomment-6621305265)

RDNA4 (gfx1201) results at your head `e90f32d86d`, applied on `main` 57bfde9f2c. Setup:
- `rocm/vllm` ROCm 10.0 image: vLLM 0.27.1, which has the pre-vllm-project/vllm#54809 GPTQ signatures, and torch 2.12.
- `SGLANG_USE_AITER=0`, Triton attention, one GPU.

**What works**
- `test_compressed_tensors_wna16_rocm.py`: 26 passed, 76 subtests passed.
- `nm-testing/TinyLlama-1.1B-Chat-v1.0-W4A16-e2e` loads and serves.
- Op level, this PR's conversion followed by `gptq_shuffle` / `gptq_gemm` (ExLlama), against an fp32 dequantized reference. Inputs were random symmetric int4 weights, group size 128, with shapes N x K = 4096 x 4096, 12288 x 4096 and 4096 x 12288, and M = 1, 8, 64 and 512. Relative error was at most 1.5e-3.
- In the served model, layer 0's packed weights and scales match the checkpoint exactly. That includes the merged qkv and gate_up.
- On raw-text requests, every W4A16 Linear in `jy395/Qwen3-8B-rtn-w4a16` matches x @ dequant(W)^T within 7e-3 relative error.

**What fails: chat-template prompts give NaN**
- With raw text the model is fine. "The capital of France is" continues with " Paris. The capital", the same as bf16 Qwen3-8B. Raw prompts from 5 to 446 tokens all gave sensible continuations.
- Any prompt in the chat template returns `!!!!...` (token 0). gsm8k (100 questions, chat template, as `sgl-eval` sends it) scores 0%.
- Where it starts: on a 20-token chat-template prompt, the input to block 6's `down_proj` reaches |x| = 9408. The fp32 reference output peaks at 18912, which fits in fp16, but `gptq_gemm` returns 2 non-finite values. From block 7 on, every layer's input is NaN.
- So the overflow appears to be inside the ExLlama kernel's fp16 arithmetic, not in the final values. It shows up with Qwen3's large activations, which appear on prompts with the chat special tokens.
- Did your gsm8k run use the chat template? The raw-text prompts I tried don't trigger it.

**Throughput**

Random 512 in / 256 out (token ids, so no chat tokens), same server settings:

| | c=1 tok/s (TPOT) | c=8 tok/s (TPOT) |
|---|---|---|
| bf16 `Qwen/Qwen3-8B` | 37.8 (26.2 ms) | 273.5 (28.0 ms) |
| this PR, `jy395/Qwen3-8B-rtn-w4a16` | 63.3 (14.9 ms) | 303.8 (21.3 ms) |

bf16 Qwen3-8B in the same environment scores 95% on the same gsm8k setup.

I'll post RDNA3 (gfx1100) results with vLLM 0.31, which has the new signatures, in a follow-up.
