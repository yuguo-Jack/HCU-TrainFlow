# [Feat] scheduler: Hardware governor that scales prefill knobs from GPU telemetry

[Upstream PR](https://github.com/sgl-project/sglang/pull/48222) · state: open · merged: False

## Original PR description

## Motivation

Prefill is compute-bound and sets a GPU's peak power. Long chunked-prefill passes can push a GPU into its power cap or a thermal slowdown. Clocks then drop, and under tensor parallelism every rank waits at each collective for the slowest GPU. Today nothing in the scheduler reads the hardware: every admission decision comes from KV-pool usage, free slots or queue length.

This PR adds an opt-in **hardware governor**. It bridges GPU telemetry (power, temperature, clocks, clock-event reasons) to the scheduling knobs SGLang already has. It adds no new scheduling mechanism. When the GPU runs hot or near its power limit, a configurable policy shrinks per-pass prefill work through those knobs.


## Modifications

New package `python/sglang/srt/managers/hw_governor/`, with three stages behind separate interfaces:

- **`TelemetrySource`** (`telemetry.py`, `nvml_source.py`) reads one `DeviceTelemetry` per watched GPU. The default `nvml` source reads in-process NVML and matches devices by UUID, so `CUDA_VISIBLE_DEVICES` reordering doesn't matter. Any `package.module:ClassName` subclass can be plugged in with `--hw-telemetry-source`, for example a DCGM or BMC source.
- **`GovernorPolicy`** (`policy.py`) turns samples into a `GovernorDecision`: a level plus `KnobOverrides`. The default `stepwise` policy is modeled on the Linux thermal step_wise governor. JSON trip rules (`trip`/`clear` with a hysteresis band, or `clock_event_reasons` with `any_of`) move up and down a ladder of knob overrides, one level per sustained streak. Missing telemetry counts as cool, so a dead sensor eventually releases the throttle. The policy is pluggable through `--hw-governor-policy` and configured with `--hw-governor-config`. The config is validated in the launching process at startup.
- **`HardwareGovernor`** (`governor.py`) is the bridge.
  - Only the leader rank, the same rank that adds `local_reqs` in `ingest_requests`, samples and evaluates the policy. It does this in a background thread, so the scheduler loop never waits on NVML.
  - Each new decision is sent as a `HwGovernorAdviceReq` through the existing `local_reqs` request broadcast, the same path timeout aborts already use. Every rank therefore applies it at the same iteration and resolves knobs identically. No new collective is added.
  - The advice is resent until it is applied (a skipped receive drops local requests), and applying it twice is a no-op.

**Knobs reused.** Overrides only shrink sizes and only lengthen the interval:

| Knob | Override | Where it applies |
|---|---|---|
| `chunked_prefill_size` | fraction, aligned to `max(page_size, 64)` (same as `DynamicChunkSizer`) | per-pass chunk in `_get_new_batch_prefill_raw` |
| `max_prefill_tokens` | fraction, same alignment | `PrefillAdder(rem_input_tokens=...)` |
| `max_running_requests` | fraction, at least 1 | `get_num_allocatable_reqs`; stops admissions, never retracts |
| `prefill_decode_interval` | `max(configured, override)` | `_arm_prefill_decode_interval` |

**Flags:** `--enable-hw-governor` (default off), `--hw-telemetry-source` (default `nvml`), `--hw-telemetry-interval-ms` (default 500), `--hw-governor-policy` (default `stepwise`), `--hw-governor-config` (JSON). All five are documented in `server_arguments.mdx`. PP and DP attention are rejected at startup for now: the leader only sees its own stage's GPUs, and per-DP-group advice would desync the shared prefill-decode cadence.

**Metrics** (with `--enable-metrics`, leader rank): `sglang:hw_gpu_temperature_celsius`, `sglang:hw_gpu_power_watts`, `sglang:hw_gpu_sm_clock_mhz`, `sglang:hw_gpu_clock_event_reasons`, `sglang:hw_governor_level`. Each level change is also logged.

**Scheduler changes** are construction and delegation only: `maybe_init_hw_governor`, a dispatcher entry, `handle_hw_governor_advice`, and an `if self.hw_governor is not None` override at each existing knob read site.

## Accuracy Tests

The governor never touches model math, but it changes chunk boundaries mid-request and admission order, so the eval forces it to its most aggressive setting. The rule is always hot (`gpu_temp_c` with `trip 0`), and the single level sets `chunked_prefill_size x0.03` (64-token chunks, so most prompts span several passes), `max_prefill_tokens x0.05` (768), `max_running_requests x0.01` (33 running) and `prefill_decode_interval>=2`. The server log confirms every prefill pass was at most 64 tokens and decode ran at most 33 requests, against 128 at baseline.

`sgl-eval==0.1.3 run gsm8k` on the full 1319 examples, with the model card's sampling (`--temperature 0.7 --top-p 0.8 --max-tokens 2048`, 128 threads), Qwen3-4B-Instruct-2507, 1x L40S:

| Server | GSM8K |
|---|---|
| governor off | 93.25% |
| governor forced to the level above | 93.56% |

The difference is within sampling noise.

## Speed Tests and Profiling

Qwen3-4B-Instruct-2507 on 1x L40S (350 W limit). TP1 BF16 with defaults per the Qwen3 cookbook, plus `--context-length 32768` (the cookbook's memory tip) and `--enable-metrics`; defaults resolve to `chunked_prefill_size=4096` and `max_prefill_tokens=16384`. Load: `sglang.benchmark.serving --dataset-name random-ids --random-input-len 6000 --random-output-len 64 --random-range-ratio 1.0 --num-prompts 600 --request-rate inf`. GPU power, temperature and clocks were sampled with nvidia-smi every 500 ms over the benchmark window.

| Case | Input tok/s | Median ITL | p99 ITL | Avg power | Peak temp | Min SM clock | Tokens/J |
|---|---|---|---|---|---|---|---|
| governor off | 13,394 | 57.4 ms | 2,824 ms | 254 W | 81 C | 1485 MHz | 35.7 |
| `--enable-hw-governor` (default config) | 13,349 | 57.5 ms | 2,806 ms | 241 W | 84 C | 1530 MHz | 34.0 |
| demo thresholds (`power_ratio` trip 0.6 / clear 0.35) | 10,463 | 33.1 ms | 70 ms | 239 W | 77 C | 1755 MHz | 28.9 |

- **The default config engaged on real heat.** The GPU reached 84 C, which leaves a 4 C NVML margin to its 88 C max operating temperature (slowdown is at 95 C), so the default `temp_margin_c` rule (trip 5) moved to level 1. Prefill passes were cut from 4096 to 2048 tokens for 42 s, then recovered after 15 s of margin at 10 C or more. Throughput was unchanged within noise, so the governor itself costs nothing when idle.
- **Demo thresholds show the trade-off.** They hold level 2 (1024-token passes, prefill-decode interval 2) for the whole run. The result trades 22% prefill throughput for a 40x lower p99 ITL, a 4 C lower peak temperature and a higher SM clock floor. Per-token energy got worse here, because small chunks are less efficient and this L40S never left the routine `SW_POWER_CAP` state. Thresholds need to be tuned to the deployment's actual constraint.
- The three cases ran back to back, with the demo case first from a cool GPU, so their starting temperatures differ.

Not covered: TP > 1 and multi-node hardware (only one GPU was available). The rank-consistency path (leader advice through `local_reqs`, applied on every rank) is covered by design and unit tests, but has not run on multi-GPU hardware.
