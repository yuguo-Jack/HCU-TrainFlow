# [PD] Propagate stable request ID across prefill and decode workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/36162) · state: closed · merged: False

## Original PR description

## Motivation

When a PD request does not provide an explicit rid, the prefill and decode
workers normalize the request independently and generate different local
request IDs. This makes it difficult to correlate logs and latency metrics
across the router, prefill worker, and decode worker.

## What this PR does

- Expose the resolved router request ID to downstream handlers through
  x-request-id.
- Generate or preserve one logical request ID before PD retry dispatch.
- Propagate the same rid to prefill and decode workers.
- Keep rid stable across retries.
- Preserve bootstrap_room as an attempt-scoped KV transfer identifier.
- Add unit tests for middleware propagation, PD header forwarding, batch IDs,
  and explicit rid preservation.

- ShangmingCai · comment · 2026-08-24T17:24:22Z · [source](https://github.com/sgl-project/sglang/pull/36162#discussion_r3845843479)

This could break `/v1/chat/completions` with `n > 1` in PD mode.

For a chat request `get_chat_batch_size` returns `Some(n)`, so this injects `rid` as an array of length `n`. But a chat request is a *single prompt* — the engine treats `n` as parallel sampling, not a batch. So the `GenerateReqInput` built in `serving_chat.py` ends up with `batch_size == 1` (single prompt, `parallel_sample_num == n`) while `rid` has length `n`, and `GenerateReqInput._normalize_rid` raises:

```python
elif isinstance(self.rid, list):
    if len(self.rid) != self.batch_size:   # n != 1
        raise ValueError("The specified rids length mismatch with the batch_size for batch processing.")
```
