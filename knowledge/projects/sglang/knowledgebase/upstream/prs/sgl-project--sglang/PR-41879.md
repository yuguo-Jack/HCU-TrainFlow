# [Perf] [AMD] Qwen3.5/Qwen3.8: Opt-in AITER FlyDSL causal conv1d prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/41879) · state: open · merged: False

## Original PR description

Requires AITER with [ROCm/aiter#5992](https://github.com/ROCm/aiter/pull/5992) (merged), which adds `causal_conv1d_prefill_flydsl_fn`.

## Motivation

On ROCm, the GDN layers of Qwen3.5/Qwen3.8 run the prefill causal conv1d through Triton. AITER has a FlyDSL kernel for it on gfx950 that is 1.1x to 1.8x faster. This PR adds it behind an opt-in flag. Triton stays the default and the fallback.

## Modifications

`layers/attention/linear/gdn_backend.py` only:

- The prefill convolution dispatches through `_prefill_causal_conv1d`. With `SGLANG_USE_AITER=1` and `SGLANG_AITER_GDN_CONV=1` it calls AITER's `causal_conv1d_prefill_flydsl_fn`, which has the same contract as `causal_conv1d_fn`: one output, `conv_states` updated in place.
- **Fallback:** an AITER `ValueError` (unsupported shape or dtype) falls back to Triton `causal_conv1d_fn`. When the flags are off or the import fails, that choice is cached and Triton is used.
- **Block-table launches** (`conv_block_table` set) stay on Triton.

Nothing changes on CUDA or when the flags are unset.

## Accuracy Tests

Kernel level, on Qwen3.8 shapes, against Triton `causal_conv1d_fn`:
- **Output:** max abs diff 3.1e-2, which is 1 bf16 ULP.
- **`conv_states`:** bit-identical.

## Speed Tests and Profiling

MI355X (gfx950), BF16, Qwen3.8 TP1 shapes (dim 10240, width 4), eager timing:

| tokens in batch | Triton (µs) | FlyDSL (µs) | speedup |
|---|---:|---:|---:|
| 1 × 1024 | 22.5 | 19.6 | 1.14x |
| 1 × 4096 | 62.6 | 47.6 | 1.32x |
| 1 × 16384 | 313.8 | 181.2 | 1.73x |
| 16 × 1024 | 324.9 | 179.8 | 1.81x |

### End to end

**Setup:**
- **Hardware and model:** MI355X, TP1, `amd/Qwen3.8-Flash-Next-Quark-MXFP4-PLEFP8`.
- **Server:** NEXTN MTP (3 steps, 4 draft tokens), chunked prefill 16384, page size 64, the model's default fp32 SSM state.
- **A/B:** the arms differ only in `SGLANG_AITER_GDN_CONV`.
- **Source tree:** `main` cannot serve this model on ROCm yet, so these runs used the Qwen3.8 bring-up branch with this PR's hook applied. The hook code is byte-identical to this PR.

Because `supports_packed_decode` may be `True`, so the decode part runs into `packed_decode()` and returns there. It may not reach `decode()`.

```python
# gdn_triton.py
supports_packed_decode = not is_cpu() and not is_npu()
# gdn_backend.py
# early return
if self.kernel_dispatcher.supports_packed_decode:
    core_attn_out = self.kernel_dispatcher.packed_decode(
        ......
    )
    return
# your change is inside this decode()
core_attn_out = self.kernel_dispatcher.decode(
    ......
)
```

Also, the current results look kernel-level only, so we cannot tell whether sglang actually runs these kernels. Could we add an e2e test? We may see improvement on TTFT for `prefill()`, ITL for `decode()`, and ITL with speculative decoding for `verify()`.
