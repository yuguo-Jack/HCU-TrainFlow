# [Fix] diffusion/zimage: Stop serving a previous request's RoPE tables

[Upstream PR](https://github.com/sgl-project/sglang/pull/46044) · state: closed · merged: True

## Original PR description

## Motivation

The Z-Image DiT caches the fp32 cos/sin tables it derives from the image, caption and unified RoPE tables. The key was the source tensors' `data_ptr()`, shape and dtype, and the entry did not keep the sources alive. Once a request finished, its tables were freed, and the next request could allocate its own tables at the same address. With the same shape the key matched, and the next request ran on the previous request's positions.

The unified `[image, caption]` table makes this reachable in normal serving. Its length is the padded caption plus the padded image tokens, so a request with a different split of the same length matches the previous one. The server warmup (1024x1024, caption padded to 32 tokens) poisons every 1472x704 request whose caption pads to 64 tokens (4064 + 64 = 4128 = 4096 + 32).

Reproduced on 2xH200, TP2, eager: a 1472x704 request after the default warmup hit the stale unified table on all 9 steps on both ranks, and the image came out as horizontal streaks (PSNR 12.2 dB against the same request on a server started with `--warmup-mode off`).

## Modifications

- `_get_rope_cache` keeps its source tensors in the cache entry and matches them by identity, so a new tensor never hits an old entry.
- The unified table, previously rebuilt by every forward, is built once per request's pair of image and caption tables (`_get_unified_freqs_cis`), which keeps its cache entry hitting across steps.
- The caches are initialized in `__init__` (`_rope_caches`, `_unified_freqs_cis`).

Tests: `test_zimage_rope_cache.py`
- a new table allocated at a freed table's address gets its own cache entry (fails on main: the stale entry is returned);
- the unified table is built once per request and rebuilt for another split of the same length.

E2E guard, in the CI case `zimage_image_t2i_2_gpus` (2 GPUs, Ulysses 2):
- A lead request at 1360x768 is sent first after the server warmup, before the case's 1024x1024 request, and is checked against its own golden `h100/zimage_image_t2i_2_gpus_lead_2gpu.jpg`. 1360x768 has 85x48 = 4080 image tokens, which pad to the 4096 of the 1024x1024 warmup (2048 per rank) over another grid, so on main it runs on the warmup's image positions.
- It has to be the first request after the warmup. On instrumented main, the first request after the warmup reused the warmup's tables on 18/18 step-rank forwards (TP2 and Ulysses 2), while 1360x768 and 1472x704 sent after a 1024x1024 request ran on fresh tables. On one GPU the unified table missed on every step, so a 1-GPU case cannot show the bug.
- `DiffusionTestCase.lead_sampling_params`: a consistency-only request (no performance baseline) with the case's quality pin; GT generation saves its golden as `<case id>_lead`. Unit tests in `test_sequential_server_requests.py`.
- `SGL_TEST_FILES_CI_DATA_REVISION` moves to ci-data-diffusion `4188b35b`, which is the previous pin `252df495` plus this one golden. The golden was generated on H100 by the GT workflow ([run 40061167040](https://github.com/sgl-project/sglang/actions/runs/40061167040)) and is also published on ci-data-diffusion main (`4aa2bacb`). The pin stays off main because main lacks the MiniMax-H3 references that `252df495` carries.
