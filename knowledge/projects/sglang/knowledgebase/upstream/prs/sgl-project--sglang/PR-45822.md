# [Fix] eplb: Support expert rebalancing with pipeline parallelism

[Upstream PR](https://github.com/sgl-project/sglang/pull/45822) · state: open · merged: False

## Original PR description

## Motivation

Large MoE deployments may use pipeline parallelism (PP) to partition model layers across GPU groups for memory capacity and placement, while expert parallelism (EP) distributes the routed experts within each stage. These deployments need load balancing without changing their chosen PP/EP topology.

Inference traffic can favor different experts as prompts and request mixes change. Even when each EP rank stores the same number of expert slots, it may receive a very different amount of token work. A heavily loaded EP rank can delay its pipeline stage and limit progress through the pipeline. For example, in the tested PP2/TP2/EP2 configuration, a hot expert on one rank in stage 0 needs to be diagnosed and rebalanced using stage 0's traffic and expert weights; stage 1 owns different layers and cannot share that placement decision.

The user-visible value is a complete PP EPLB workflow: operators can inspect each stage's expert load, enable the existing placement algorithm to redistribute expert replicas within that stage's configured expert-slot budget, and continue inference after migration. This makes the existing load-balancing mechanism usable for PP deployments and provides a way to respond to changing expert demand. It addresses imbalance among EP ranks within a stage; repartitioning layers between stages is outside this change. Throughput or latency gains depend on workload skew and migration cost and still require service-level measurements.

Several existing EPLB paths use WORLD size, a global root, or launch-wide node counts. With PP enabled, those assumptions can mix statistics across stages or send expert weights to the wrong peers. This change gives recording, placement, migration, and control completion the same stage-local ownership contract, including acknowledgements from every stage that received a manual recorder request.

Continues the EP-group ownership work in #13629 by @qiaoning13256. This also covers stage topology, model-owned weight discovery, recorder control completion, and end-to-end regression tests.

## Modifications

- Introduce one stage EP domain for collective groups, roots, local/global rank mapping, and node ownership. Reject placements that the hierarchical solver cannot represent.
- Scope recorder reductions, balancedness broadcasts, solver topology, replica locality, and expert P2P transfers to that domain. Validate the whole update chunk before moving any weights.
- Keep the existing PP request relay; correlate terminal replies from each stage/EP owner, handle duplicate and late replies, and aggregate failures. Reset recorder buffers after a failed dump so a later recording window can recover.
- Restrict GLM5 expert weight discovery to materialized stage-owned layers and preserve errors from lazy weight discovery.
- Preserve rank-local EPLB metrics when PP reconstructs ordinary, speculative, and skipped-output results; exclude foreign-stage and dense/inactive zero rows from balancedness averages (an entirely empty window still reports 1). This restores PP observability and prevents inactive layers from hiding real skew.
- Add CPU/Gloo ownership and control regressions plus a registered four-GPU PP2 recorder/automatic-EPLB test using `lmsys/sglang-ci-dsv3-test`.

## Speed Tests and Profiling

### End-to-end result: no established overall speedup

**The full Control → Recorder → Automatic → return-Control comparison is complete. Automatic improves measured expert balancedness, but its delivered throughput falls inside the bracketing controls and hot mean TTFT increases. Keep automatic EPLB opt-in; these results do not justify enabling it by default for this workload.** Stage-local load inspection and real expert migration with continued correct inference remain the capability value of this PR.

Deployment: **16×H20**, GLM-5.3-Flash, FP8 KV, 8 GPUs per role. Prefill: TP4/CP1/PP2/EP4, 24/21 layers, memory fraction .70, max running 32, PP microbatch 1, Triton MoE, 8 redundant experts, PP overlap disabled. Decode: TP8/attention-DP8/EP8/PP1, memory fraction .90, max running 128 (16/DP), MTP 5/1/6, Replay16, full CUDA Graph and overlap, DeepGemm/MegaMoE. The Decode process, source, image, model content, devices, routing and workload remain fixed through the formal arms. Control disables recorder/reporting/EPLB; Recorder enables stat buffer 32 and Prometheus reporting; Automatic additionally enables EPLB at interval 32/default threshold 1. No canary/layout diagnostics run in the timing windows.

Each arm receives the same four 65K warmup seeds. Cold: 65,536 → 1, C1, seeds 1000–1003, cache reset at the start of the series, distinct random prompts. Append: 57,344-token prime → 65,536 → 1, four pairs, reset per pair. Hot: two fully primed 65,536-token prefixes → 1,536, C128/N512. These repeated control-character prefixes are a reproducible synthetic workload, not representative production traffic.

**Interpretation:** Automatic versus Control A / return-Control yields **+2.09% / −1.23% throughput**, **−2.73% / +1.21% mean E2E latency**, and **+32.43% / +37.18% mean hot TTFT**. Its +0.35% throughput over Recorder is also insufficient to establish a rebalance gain. There is one hot run per arm; the controls drift, so neither stable recorder overhead nor an overall throughput gain/regression is established. The retained configuration is Control (recording/reporting/EPLB off).

Cold median observations improve by 2.42–2.95%, but Automatic's samples are **5701.70, 6141.28, 5698.28, 5692.55 ms**; including the slow point reduces the mean improvement to 0.60–2.42%. Return-Control also contains a 6233.35 ms slow point. Append median observations improve by 3.33–3.64%, with only four pairs. No samples were dropped; these observations are not production SLO/p99 or general speedup claims. The earlier partial Control/Recorder measurements remain historical evidence and are superseded by this matched full matrix.

### Mechanism, runtime and quality checks

- **Balancedness:** active-layer extend-forward mean (sum/count) improves from Recorder **0.574 / 0.625** to Automatic **0.807 / 0.813** for PP0 / PP1. This is a stage metric improvement, not an E2E speedup.
- **Real normal updates:** each stage completes 16 updates in the hot window, with nonzero normal P2P transfer logs on all ranks. Stage-root pauses are **0.309–0.435 s, cumulative 6.072 s** on PP0, and **0.309–0.372 s, cumulative 5.595 s** on PP1. Cold has one update per stage, 0.260 / 0.261 s. These normal timings exclude canary diagnostics; stage sums cannot be added to infer service pause. Server-log window mapping has one-second precision. Existing separate canary evidence supplies the before → target == after layout readback; no new layout/weight hash is claimed for the formal run.
- **Actual path:** cold cache hits 0%; hot Prefill device hits 99.61%, with no observed host/storage reload. Decode reaches 128 active requests, with zero observed queue/retraction and growing CUDA Graph counters in every formal arm. Prefill supply queueing exists, so this is PD service throughput, not isolated Decode capacity. Decode stores full KV per request and does not share Prefill's prefix cache.
- **Speculation:** at D_running ≥112, sampled mean acceptance lengths are 5.953 / 5.881 / 5.972 / 5.888 across the four arms. Corresponding sampled acceptance rates are .9907 / .9762 / .9944 / .9775. These are gauge observations, not token-weighted rates; Control A's verification counter was not collected. Do not attribute small throughput changes to a proven invariant speculation cost.
- **Small quality scope:** all arms pass eight routed finite-logprob checks and six fixed questions. After Automatic, a 65K question answers `4` with all output logprobs finite. This does not establish full-corpus accuracy or bitwise identity.

### Source and final traces

All formal arms run combined source **`cb9b288ea2be38d71348661bc8e6f7b136312cf4`**, incorporating this PR's head **`3e7926c29b01b12e1c11cc165d8e8fbd473212a6`** plus the separate FP8 masked-KV correctness fix from **#45988** (`1b74fe5ee3154ad7fac537e6c8a641c16541fb43`). The latter is required for correct outputs and is not included in this PR's code diff. Incorrect-output pre-fix runs are not performance baselines. Dependencies include Torch 2.14.1+cu130, TileLang 0.1.12, Mooncake CUDA13 0.3.13.post1, the retained DeepGemm 0.1.7 overlay, and official sgl-flash-mla 1.0.0. The tested main-compatible topology is **CP1**; the separate original CP2/PD configuration remains unvalidated.

Final retained-Control traces were newly captured, persisted with verified SHA256 and actually parsed: **8 P cold + 8 P hot + 8 D hot rank files**. P cold covers eight 8192-token extend chunks; hot P covers 256-token residual extends. D hot contains 12 verify steps/rank at actual batch 15–16, draft/draft-extend and 288 total CUDA Graph launches. These profile timings are excluded from the performance table.

**Profiling recovery limitation:** after exporting the traces, the profiled hot load stalled at 164/256. Saved stacks show P0 in KDA index preparation, P1 waiting for PP input, and mixed DP synchronization/idle states on D; the underlying cause is unknown. This occurred with EPLB disabled. The owned load was cancelled and both services stopped normally; restarting the same functional configuration restored eight finite-logprob routes and a normal 65K→1536/C128/N128 burst (128/128, zero errors). This is restart recovery, not transparent recovery. No node reboot or Graph/MTP disabling was needed. Trace export skew/host gaps cannot quantify normal pipeline bubbles or service gain. All validation Pods and the GPU Permit were subsequently released.

Validation covers the Python PP control path and recoverable dump I/O failures. Cross-node EP GPU execution, hard-rank-failure recovery, Rust PP control, and the separate GLM CP2/PD configuration remain unvalidated. Freeze policies, new placement algorithms and CP/PD adaptations remain outside this PR.
