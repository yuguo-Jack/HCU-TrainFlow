# [Fix] scheduler: Tell a step's middle chunk from the batch's chunked request, not a per-request counter

[Upstream PR](https://github.com/sgl-project/sglang/pull/43906) · state: closed · merged: True

## Original PR description

Facts about work in flight now come from what each step recorded when it was built or launched, instead of a per-request counter or a batch snapshot. This fixes a miscount of chunked prefill on main.

## The fix
`Req.inflight_middle_chunks` was raised whenever a chunked request existed after an admission pass that admitted something, even when the chunked request got no chunk in that pass. Under the hybrid-SWA joint prefill budget, a chunk whose remaining prompt does not fit with its new-token headroom is parked, while a smaller waiting request can still be admitted in the same pass. The counter then never came back down, and the request's final chunk was processed as a middle chunk: its first token was not committed (PD prefill: it was requeued as if it had yielded).

The same state made `contains_last_prefill_chunk` False for a batch whose only row ran a final prefill, so pipeline parallelism with `SGLANG_PP_SKIP_PURE_CHUNKED_OUTPUT_COMM` skipped its output exchange.

A pause that retracts under pipeline parallelism reset the counter while other micro-batches still carried the request, so their results could be labelled wrongly too; each step's own record labels it by itself.

## Changes
- Result processing (prefill, embedding, PD prefill, the pipeline-parallel output check, the grammar skip) asks whether a row is its batch's `chunked_req`, which the batch already records at build: the request that runs a chunk in this batch and is still chunked after it. A parked request is named there too but is not a row, so it is never asked about. `copy()` now carries `chunked_req`, since overlap processes the copy. The counter, its resets and the never-read dLLM increments are removed.
- `contains_last_prefill_chunk` counts the chunked request only when it is admitted in this pass.
- A PD optimistic request that yields the chunked slot is requeued once no step of it is in flight (`Req.inflight_steps`): at once at the yield, otherwise when its last step in flight is processed. This replaces the overlap flag and the `extend_end` inference; both rules agree wherever the yield can happen (optimistic prefill is off with pipeline parallelism, and a request otherwise has at most one step in flight).
- `_reqs_finishing_inflight` finds running requests whose queued result finishes them by `inflight_steps > 0` instead of reading the queued batch copy, and drops the one-batch assert. Same result: only the overlap loop enables it, and there the queued step is the only step in flight.

Behavior changes: only the parked-chunk and pipeline-parallel retract states above.
