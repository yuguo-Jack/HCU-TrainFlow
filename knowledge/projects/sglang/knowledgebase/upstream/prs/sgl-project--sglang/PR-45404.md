# [Fix] dsv41: Escape literal image placeholder in user text instead of rejecting

[Upstream PR](https://github.com/sgl-project/sglang/pull/45404) · state: open · merged: False

## Original PR description

## Motivation

Fixes #39274. Continues and rebases #40758 by @cs-fisha (same approach; see the delta below).

A literal `<｜deepseek_image｜>` typed or echoed by the user (quoting the token, pasting an error message that contains it, or a tool result that happens to include it) is hard-rejected with HTTP 400 by `_validate_no_image_sp_tokens`. Because most clients keep the failed turn in history, **every subsequent request in that conversation replays the poisoned message and is rejected too, permanently wedging the conversation**. Reproduced on `lmsysorg/sglang:v0.5.22` serving DeepSeek-V4.1-Flash: any message role with the token in a string `content` gets the 400, while a proper `image_url` block works fine.

## Modifications

Same neutralize pattern as #40758 (and as the Kimi encoder): rewrite a user-supplied occurrence of the fullwidth-bar token to the ASCII-pipe spelling `<|deepseek_image|>` instead of raising. Genuine `image_url` blocks still insert the real placeholder, so the escaped spelling can never be confused with one downstream.

- Add `IMAGE_PLACEHOLDER_ESCAPED` and `_escape_image_placeholder` in `encoding_dsv41.py`
- Rename `_validate_no_image_sp_tokens` → `_escape_image_sp_tokens`, rewriting the `content` / `reasoning_content` raise paths to escape in place
- Escape text blocks and string `tool_result` content in `_process_image_blocks` instead of raising

Delta vs #40758 (why a rebase was needed):

- #44751 added a **second call site** of `_validate_no_image_sp_tokens` in `encode_messages` (pre-merge pass, "escape before merging can discard message-level textual fields"). The rename in #40758 predates that commit: the patch still applies textually to current `main`, but the untouched new call site would hit a `NameError` on every request. This PR updates **both** call sites.
- The pre-merge pass now operates on deep copies so the caller's message objects are never mutated (escaping rewrites `content`/`reasoning_content` in place).

## Accuracy Tests

CPU unit tests in `test/registered/unit/entrypoints/openai/test_encoding_dsv41.py`:

- The five cases from #40758: tool-result string, user text block, string `content`, `reasoning_content`, plus a control that a genuine `image_url` block still inserts the real placeholder and yields one image record
- New: `context` messages containing the token no longer raise (covers the pre-merge pass added by #44751)
- New: the caller's `messages` are not mutated by the escape pass

All previously-accepted requests encode byte-identically; only requests that used to fail with the 400 change behavior (they now render with the escaped spelling).
