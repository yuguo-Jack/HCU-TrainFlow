# [Fix] model_loader: Read each shard sequentially before the multi-thread loader maps it

[Upstream PR](https://github.com/sgl-project/sglang/pull/46128) · state: open · merged: False

## Original PR description

## Motivation

Loading `nvidia/Qwen3.8-Flash-Next-FP4-Local` (about 95 GiB in 21 safetensors shards, about 23k tensors per shard) took about 13 minutes. Other checkpoints of similar total size load in under 100 seconds on the same machine, and the same checkpoint loads in 61 seconds with NVIDIA's vLLM image.

The default loader (`enable_multithread_load` is on unless set otherwise) is `buffered_multi_thread_safetensors_weights_iterator`. Each worker thread creates every tensor view of a shard with `{k: f.get_tensor(k) for k in f.keys()}` before any tensor is copied to the GPU. On a cold page cache this reads the shard through one 4 KiB page fault at a time.

Measured on one shard (4771 MiB, 22908 tensors, cold page cache, copying to the GPU), reproducing the loader's two access patterns with safetensors `safe_open` and `get_tensor`:

| pattern | time | rate | page faults |
|---|---|---|---|
| create all views, then copy each | 31.1 s | 153 MiB/s | 1,107,812 |
| create a view and copy it, one tensor at a time | 3.2 s | 1495 MiB/s | 3 |

Both read the same 4771 MiB from disk, and a second run reproduced the numbers within 1%.

## Modifications

`buffered_multi_thread_safetensors_weights_iterator` now calls the existing `_prefetch_checkpoint_file` on a shard in its worker thread before opening it. The file is read sequentially in 16 MB blocks into the page cache, so the views that follow fault in from memory. The `disable_mmap` branch is unchanged.

A unit test checks that each shard is read before it is opened.

## Results

Checkpoint: 21 safetensors shards, about 95 GiB, `--tp 1`, on a 990 EVO Plus 2TB NVMe SSD. Times are "Load weight begin" to "Load weight end" in the server log.

| | Multi-thread loading, 21 shards | Target model | MTP draft |
|---|---|---|---|
| Without this PR | 8:58 (25.6 s per shard) | 587.7 s | 20.0 s |
| With this PR | 2:03 (5.9 s per shard) | 134 s | 6 s |

The "before" figure is from an earlier run on the same machine, not from a back-to-back comparison.

Hardware: NVIDIA RTX PRO 6000 Blackwell (SM120), driver 615.78.08, torch 2.14.1+cu130, safetensors 0.8.0.

## Not measured

- Other checkpoints. This was only measured on the checkpoint above. A checkpoint already in the page cache pays one extra sequential read pass, and I did not time that.
- Hosts where RAM is smaller than a shard times the number of workers.
- The remaining gap to vLLM (2:03 against 61 s).

I have not established why creating every view first causes 4 KiB faults in `safetensors` / torch. The test above shows the effect and that reading sequentially first removes it.
