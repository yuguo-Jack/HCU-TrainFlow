# [Perf] multimodal: Lazily initialize CUDA VMM feature transport

[Upstream PR](https://github.com/sgl-project/sglang/pull/45384) · state: open · merged: False

## Original PR description

## Motivation

Related to #45345.

While investigating #45345, we found that `CudaVmmFeatureTransport` eagerly creates a tokenizer-owned `CudaVmmMemoryPool` as soon as `cuda_vmm` is selected, before any multimodal feature dispatch occurs. Text-only workloads on multimodal-capable models therefore pay per-worker CUDA/VMM initialization and HBM reservation even if the transport is never used.

This PR defers that allocation until the first non-empty multimodal dispatch.

## Modifications

- Keep the existing per-worker pool budget unchanged, but save the pool construction arguments during transport initialization instead of allocating immediately.
- Add `_ensure_pool()` with a lock, double-check, and shutdown veto so the pool is created exactly once on first non-empty multimodal dispatch from the publisher thread.
- Track transport enablement explicitly because `self.pool is None` now also means “enabled but not initialized”.
- Preserve the eager CPU-only single-thread publisher executor.
- Preserve existing cancellation and rollback behavior.
- On shutdown, set `_closing`, drain the publisher executor, then shut down the pool if it was created. The pool reference is intentionally retained to preserve the existing idempotent/retry shutdown contract.

### Unit tests

Coverage is added to the existing CPU-registered `test/registered/unit/multimodal/test_gpu_feature_transport.py`.

The new `TestCudaVmmLazyInit(CustomTestCase)` is intentionally kept small and covers four lifecycle invariants:
- startup allocates no pool; first non-empty MM dispatch creates it and subsequent use reuses it
- concurrent first use creates exactly one pool
- shutdown before first use prevents late pool creation
- if initialization wins the race, shutdown waits and releases the created pool

The existing text-only async-bypass test now also asserts that `pool` remains `None`, directly covering `cuda_vmm` enabled + text-only dispatch → no allocation. Existing `object.__new__` fixtures are updated only for the newly explicit lifecycle state. The pre-existing disabled-transport test continues to cover the no-op path, so no duplicate lazy-init test is added for it.

Whole-file validation after the final test refinements: **43 passed + 2 subtests**. The production diff is unchanged by the test-only refinements.

## Accuracy Tests

No model computation or output path is changed; this only changes when the transport pool is initialized.

End-to-end correctness check on 2 nodes × 4 GB300, `cuda_vmm`, 32 tokenizer workers, MF=0.90:
- with `--skip-server-warmup`, the server reaches READY without eager tokenizer-side VMM allocation
- the first real image creates the CUDA VMM allocation on demand and succeeds
- shutdown is clean

## Speed Tests and Profiling

This is primarily a startup/lifecycle memory change rather than a steady-state throughput optimization.

Observed on the GB300 setup above:
- startup with `--skip-server-warmup`: tokenizer workers do not reserve the VMM pool before first multimodal use
- first real image: tokenizer-side aggregate CUDA VMM allocation on GPU0 reaches ~0.9 GiB on demand

The default 448×448 Kimi-K3 multimodal startup warmup still OOMs on the #45345 reproduction. Free memory falls from ~24.1 GiB to ~6.0 GiB before failure, with ~0.32 GiB free reported at OOM.

A follow-up source review shows an important distinction for multi-tokenizer mode: each tokenizer worker starts its own general server warmup, so with 32 tokenizer workers the 448×448 VLM warmup can be issued concurrently from many worker processes. In that path, lazy initialization is immediately exercised by the warmup itself, so it cannot avoid the startup-time transport allocation; concurrent multimodal preprocessing / transport work can also amplify the peak.

The N=1/2/4/8/16/32 scaling profile and N=32 concurrent/serialized A/B have now been collected in #45345. The sweep observed exactly N warmups, READY through N=16, and OOM at N=32. Serializing all 32 per-worker warmups reduced recorded peak GPU0 usage from 282,299 MiB (OOM) to 263,275 MiB (READY), with all 32 serialized warmups completed. #45584 proposes the separate general-warmup serialization fix while preserving each worker's warmup and post-warmup/GC lifecycle.

Those hardware results were collected in the investigation's v0.5.22-based environment with lazy initialization. They do not constitute a hardware rerun of #45584's current-main commit or establish that serialization alone on an eager-init baseline is sufficient. This PR remains scoped to lazy CUDA VMM transport initialization.

Therefore this PR does **not** claim to fix #45345. It addresses the narrower lifecycle inefficiency: CUDA VMM transport resources should not be allocated before the transport is actually used. The duplicated/concurrent multi-tokenizer warmup behavior is being tracked separately in #45345 and is intentionally out of scope here.
