# [Perf] [AMD] gdn: ReplaySSM verify uses one pipeline stage at every batch size on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/47433) · state: open · merged: False

## Original PR description


## Motivation

With `--enable-linear-replayssm-spec`, `gdn_replayssm_spec_decode` runs once per GDN layer per draft/verify cycle (48 layers on
Qwen3.8-27B). On gfx950 at the Qwen3.5/3.8 MTP shape (K = V = 128, ring 16, 4 draft tokens) it switches to one 128-wide V tile and one
pipeline stage only from batch 32; below that it runs the generic launch (64-wide tile, two stages).

The kernel is not bandwidth-bound there. One call reads about 3.4 MB per request, almost all of it the fp32 checkpoint
(48 x 128 x 128 x 4 B), so ~55 MB at batch 16: 47.7 us is 1.1 TB/s before and 21.2 us is 2.6 TB/s after, against 8 TB/s HBM on
MI355X. With one wavefront per program and a few programs per CU, latency dominates, so the second pipeline stage does not pay for itself,
and once the grid has enough programs the 64-wide tile only duplicates the q/k/gate work of each (request, head) across two programs.

## Modifications

On gfx950 at that shape: one pipeline stage at every batch size, and the wide tile when `batch_size * num_value_heads >= 768` instead of
`batch_size >= 32`. At 48 value heads (Qwen3.8-27B TP1) the wide tile starts at batch 16; at 24 value heads per rank (TP2) it stays at
batch 32. Other GPUs and shapes are unchanged.

Relation to #46633 (env-configurable ReplaySSM verify stages, NVIDIA): no textual conflict. #46633 passes
`SGLANG_GDN_REPLAYSSM_VERIFY_NUM_STAGES` (default 2) as `num_stages`; on gfx950 at this shape the launch override here sets the stages
after that, as main already does from batch 32, so the env var does not apply there. If both land, the override can respect an explicitly
set env var.

## Accuracy Tests

- Kernel: outputs and the ring entries the kernel writes (d, k, g, raw v, raw k) of the old and new launch compared element-wise on inputs
  dumped from a live Qwen3.8-27B TP1 server: max abs diff 0 at batch 4, 8, 16, 32 and 64. A sweep (block_v 16-128, warps 1-8, stages
  1-2, nk 1-4) found no faster bit-exact configuration.
- End to end, MI355X, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`, TP1, `--attention-backend aiter --kv-cache-dtype fp8_e4m3`, MTP 3/1/4 +
  `--enable-linear-replayssm-spec`: upstream main 8080507c3e + this PR starts and serves text and image requests (accept length 2.66).
  Greedy outputs with rejection sampling off (`--speculative-accept-threshold-single 0.9999999`), 50 ShareGPT prompts, 256 tokens, batch size 1,
  upstream main + #47430 with and without this PR: identical, 50/50 (and 50/50 on a second pass in the same server).
- GSM8K (5-shot, all 1319 questions, `sglang.test.few_shot_gsm8k`) on the Qwen3.8 build below with this change: 0.925 (1 invalid answer, a
  thinking block cut at 512 tokens), vs 0.933 without speculative decoding on the same GPU (binomial sd 0.7 points).

## Speed Tests and Profiling

The kernel file is the same on current main as on the build these numbers come from (a Qwen3.8 build of main: e732f5d41e + 14 open AMD
Qwen3.8 PRs, among them #39912, #39998, #43785, #47154; SD arms also with #47430, #47431, #47432).

Per-call time inside a CUDA graph (20 calls per graph, as the server replays it), MI355X, 48 value heads, inputs dumped from a live
Qwen3.8-27B TP1 server (MTP 3/1/4; batch 8 = the first 8 requests of the batch-16 dump):

| batch | before | after | |
|---|---|---|---|
| 4 | 19.2 us | 11.8 us | 1.63x |
| 8 | 25.1 us | 13.2 us | 1.90x |
| 16 | 47.7 us | 21.2 us | 2.25x |
| 32 | 38.4 us | 38.4 us | unchanged |
| 64 | 58.5 us | 58.5 us | unchanged |

Serving, MI355X TP1, MTP 3/1/4 + `--enable-linear-replayssm-spec`, output tok/s with `python -m sglang.bench_serving` (random, range ratio
0.8), same GPU, alternating A-B-A-B (2 runs each, mean and range). "Before" here is an intermediate version (wide tile and one stage from
batch 16), so 16 concurrent runs the same launch in both arms and serves as the control:

| workload | before | this PR | change |
|---|---|---|---|
| 8k / 1k out, 4 concurrent | 863.9 (856-872) | 912.9 (899-926) | +5.7% |
| 8k / 1k out, 8 concurrent | 1355.8 (1355-1357) | 1410.3 (1402-1418) | +4.0% |
| 60k / 600 out, 4 concurrent | 262.0 (259-265) | 264.3 (264-264) | +0.9% |
| 8k / 1k out, 16 concurrent (same launch) | 1876.1 (1873-1879) | 1884.9 (1884-1886) | +0.5% |

Against the original launch at 16 concurrent (same GPU, one after another): 1791.4 -> 1888.2 tok/s (+5.4%; 114.6% -> 120.8% of no
speculative decoding). A torch profile at 16 concurrent shows the kernel at 1.57 ms per draft/verify cycle (2.86 ms before).
