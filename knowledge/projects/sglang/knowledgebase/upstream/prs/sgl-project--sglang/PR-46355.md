# [RFC] [Feat] megakernel: Platform seams for out-of-tree megakernel plugins

[Upstream PR](https://github.com/sgl-project/sglang/pull/46355) · state: open · merged: False

## Original PR description

> **RFC / draft.** This proposes small platform seams so the plugin-kernel (megakernel) contract can be served by out-of-tree platforms. Feedback on the shape of the seams matters more than the code right now; the names are open.

## Motivation

The megakernel contract (`sglang.kernels.plugin_kernels.nvidia.spec` + `sglang.srt.kernel_plugins.nvidia.binding`) is mostly hardware-neutral: a registry of per-architecture specs, refused-by-default features, `BuildContext` / `Step` / `BuiltMegakernel`, an install point after model load and before KV sizing, and the `plan` / `forward` split. Only a few places tie it to CUDA:

1. The only flag is `--enable-nvidia-megakernel`.
2. Specs are matched on a `torch.cuda` ISA probe (`sm_XY`); with no CUDA device every spec is refused with "no GPU is visible".
3. Install calls `torch.cuda.mem_get_info()` and reads the SM count unconditionally.
4. Dispatch is always a `model.forward` wrapper plus a CUDA-graph capture check. A platform whose graph runner never calls `model.forward` for decode (it runs precompiled graphs) has no place to hook in.
5. A megakernel can't ask for KV / state pools in its own layout, even though it is built before the KV cache is sized.

How we found this: we are bringing up a whole-model decode kernel on AWS Trainium (trn3) as an out-of-tree SGLang platform plugin (the plugin repo is private for now). To use the upstream contract we had to copy it into the plugin and monkeypatch around the five points above: an env var stood in for the flag, we wrapped the `handle_nvidia_megakernel` resolution step and the `install_megakernel` module name, the Neuron graph runner did the dispatch, and the platform's `get_kv_pool_cls` hook selected pools in the kernel's layout. Every one of those patches maps to one of the small seams below.

## Modifications

All changes are backward compatible. With no new flag set and an in-tree platform, behavior is unchanged.

- **`--enable-megakernel`** (new `exec` field, appended to `POSITIONAL_FIELD_ORDER`): the platform-agnostic flag. `--enable-nvidia-megakernel` still works and means the same thing: `flag_enabled()` accepts either one, in both resolution and `megakernel_enabled()`.
- **Device target through the platform:** new `SRTPlatform.get_megakernel_target() -> Optional[str]`. The default returns the same `sm_<major><minor>` that `device_isa()` computed before, for CUDA-alike platforms, and None otherwise. `binding.device_isa()` now delegates to it. `Requirements.isas` now documents that it holds these target strings (e.g. `"trn3"` out of tree).
- **Out-of-tree platforms skip CUDA-only checks:** the `sgl-nvidia-mega` entry-point check (an OOT platform registers specs from its own plugin; an empty registry is still reported by `find_spec`), `torch.cuda.mem_get_info` in the build log, and the SM-count residency check. An OOT spec that sets `resident_blocks` is refused with a message pointing to `model_disable_reasons`.
- **Optional decode-graph-backend requirement:** this already worked (an empty `Requirements.decode_graph_backends` accepts any backend). It is now documented for platforms whose own runner dispatches.
- **Platform-owned dispatch:** new `SRTPlatform.install_megakernel_dispatch(*, model, built, binding) -> bool`, called once after the build. Returning True means the platform's graph runner plans and runs covered steps (`built.plan` / `built.forward`), so core installs neither the `model.forward` wrapper nor the CUDA-graph capture check. The default False keeps today's wrapper.
- **Optional `pool_layout` on the built megakernel:** if `getattr(built, "pool_layout", None)` is not None, it goes to the new `SRTPlatform.activate_megakernel_pool_layout(pool_layout)` right after the build, which is before KV sizing. The platform's `get_kv_pool_cls` (and friends) can then build pools in that layout. The base implementation raises `NotImplementedError`, which becomes the binding's usual "cannot run this setup" refusal. In-tree pools have one layout each, so nothing in-tree accepts a layout yet.

Design rationale:
- **Platform hooks instead of a parallel `kernel_plugins/<vendor>` copy.** The contract and registry stay shared; the platform answers three questions: what the device target is, whether it owns dispatch, and whether it can build a given pool layout.
- **Extend the existing contract instead of forking it.** Field names stay the same, so specs written for NVIDIA keep working unchanged and an OOT spec reads the same.
- **Dispatch through the platform runner.** On platforms where decode never goes through `model.forward` (precompiled graphs), the graph runner is the only place a step is actually chosen.
- **`pool_layout` is optional and refused by default.** Only a platform that implements `activate_megakernel_pool_layout` can accept one. A kernel that declares a layout implicitly promises to cover every decode step, because the standard path cannot read those pools. This PR leaves that check to the platform. It could move into core, see open questions.

- **Not tested:** any GPU run, an actual `sgl-nvidia-mega` spec, and the Trainium integration against this exact branch. The plugin's version of these seams runs as monkeypatches against an older main.

## Open questions

1. **Naming:** should `Requirements.isas` become `targets` (with `isas` as an alias)? Should the contract move out of the `nvidia` package (e.g. `plugin_kernels/spec.py`, re-exported from `nvidia`)? This PR keeps file locations to stay minimal.
2. **Messages and log lines** still say `--enable-nvidia-megakernel` / "NVIDIA megakernel". Should those strings come from the platform?
3. **AMD monokernel:** should `--enable-megakernel` also cover the AMD monokernel binding, or should the two contracts be unified first?
4. **`pool_layout` coverage:** should core enforce that a kernel declaring `pool_layout` covers every decode step (e.g. `plan` returning None becomes an error)?
5. **Draft models:** should a draft spec be allowed to declare a `pool_layout`? It is currently passed through like the target's.
