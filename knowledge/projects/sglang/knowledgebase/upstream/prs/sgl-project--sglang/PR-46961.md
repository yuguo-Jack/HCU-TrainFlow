# [Feat] rust-server: Report cached tokens by cache tier in native /generate meta_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/46961) · state: closed · merged: True

## Original PR description

Stacked on #46949 (customized_info through the Rust frontend): this PR's own change is its last commit, and its base moves to `main` once that one lands.

## Motivation

In Rust frontend mode, native `/generate` frames carried only the `cached_tokens` total: `meta_info.cached_tokens_details` was missing (#46205 left it out), and `sglang:cached_tokens_total` counted every cached token as `cache_source="device"`. With a hierarchical cache or a storage backend attached, a client could not tell a host or storage hit from a device hit, and a test that reads HiCache or storage hit counts from `meta_info` sees zero host and storage hits even though the cache works. Python's server reports the breakdown on every frame.

## Modifications

Each request's cached tokens per tier travel from the scheduler to the Rust frontend:

- **Scheduler side:** when the cache has a host or storage tier (HiCache, LMCache), or on a PD decode server (which takes the split from prefill), the scheduler sends each row's `(device, host, storage)` counts as a new optional `BatchHeader` column, plus the attached storage backend's type once per frame. A device-only cache sends nothing, and the frontend reports every cached token on device.
- **Frontend side:** the frontend renders `meta_info.cached_tokens_details` with Python's shape and presence rule:
  - present on every frame, `null` without cached tokens;
  - `{device, host}`, plus `storage` when it is nonzero or a storage tier is attached, plus `storage_backend` while one is attached.
- **Metric:** `sglang:cached_tokens_total` is split by `cache_source`, and a source's series is registered at its first hit, as in Python.
- **Hot path:** a device-only cache adds no per-row work. Where the split is sent, it costs one tuple per row on the scheduler thread. The details ride in the boxed `ChunkExtras`, so `ChunkEvent` keeps its size.
- **API:** `api.v1` gains `CachedTokensDetails` and `GenerateMetaInfo.cached_tokens_details` (field 21), regenerated with `cargo gen-api`. Every Rust `/generate` frame now carries the key, as Python's does.
- **Scope:** abort frames keep the details the stream reported; Python reports none for them. The OpenAI-compatible endpoints are unchanged.

A fixture built by Python (`rust/sglang-server/testdata/frame_metadata.json`) pins both sides: the headers `push_generation` sends, the details the scheduler's `get_cached_tokens_details` derives, and the `cached_tokens_total` increments the Python metrics collector records. It covers miss, device, host, storage, unsplit and short-split rows, with and without a storage tier; `frame_metadata_matches_python` and `cached_tokens_split_by_source_matches_python` decode it on the Rust side, and `test_frame_metadata_fixture_matches_python` fails if Python drifts from it. Weakening the `storage` presence rule fails the fixture test.

## Adaptation beyond the change

One test-only commit sits on top of the port and is not part of the original change: after #47166, `SchedulerOutputStreamer.__post_init__` also reads `get_observability().enable_metrics`, so the two tests in this PR that build a streamer by hand now stub `get_observability` with both `enable_metrics` and `enable_request_time_stats_logging` (`TestOutputStreamerCachedTokensSplit` had stubbed only the latter; `build_rust_frame_metadata_fixture` in `test_rust_server_extension.py` had no stub at all). No runtime code changes.

After #47178, which split `_GenerationStreamAccumulator.accept` into an `if self.rust_server_mode:` branch and an `else:` branch, the per-row `cached_tokens_split` append that this PR had attached as an `elif` to the old `if not self.rust_server_mode:` now sits inside the new `if self.rust_server_mode:` block as a plain `if self.cached_tokens_split is not None:`. Same eight lines, re-indented; no other change.
