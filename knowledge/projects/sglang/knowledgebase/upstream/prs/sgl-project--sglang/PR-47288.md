# [Fix] parser: Prefer native token id for think-end markers

[Upstream PR](https://github.com/sgl-project/sglang/pull/47288) · state: open · merged: False

## Original PR description

Fixes #47205

## Problem

When `split_special_tokens=True`, `tokenizer.encode()` splits a special-added marker like `<|end|>` into ordinary ids (`[27, 91, 419, 91, 29]`) instead of returning the native id (`200007`). The grammar gate (`ReasonerGrammarObject`) waits for the encoded sequence, but the model emits the single native id, so the gate never opens. Requests with `require_reasoning=True` (structured output, forced tool calls with reasoning) generate without their grammar, and nothing reports it.

`InklingDetector` already avoids this by returning native ids directly. #47205 names two places that had no such path: `BaseReasoningFormatDetector.get_think_end_token_ids` and `ResponseTemplateReasoningDetector.get_think_end_token_ids`, plus the scheduler's request-selectable terminator encoding.

## Fix

All three now prefer `convert_tokens_to_ids()` over `encode()`. A marker that is one vocabulary entry resolves to its native id; only markers absent from the vocabulary fall back to encoding:

- `BaseReasoningFormatDetector.get_think_end_token_ids` (reasoning_parser.py)
- `ResponseTemplateReasoningDetector.get_think_end_token_ids` (response_template.py)
- the scheduler's `request_selectable_think_end_tokens` loop

Completing this fix for #47205. The issue names two `get_think_end_token_ids` that derive the marker ids by encoding its printed text, `BaseReasoningFormatDetector` and `ResponseTemplateReasoningDetector`. This PR already covered the base detector and the scheduler's request-selectable terminator loop, but the `ResponseTemplateReasoningDetector` sibling in `response_template.py` was still on `encode()`, so a response-template-driven reasoning request would hit the same never-opening grammar gate under `split_special_tokens`.

Pushed `fa1217cbfa`, which gives that sibling the same native-id preference already reviewed here: prefer `convert_tokens_to_ids`, and fall back to `encode` only for tokens absent from the vocabulary. I added `test_get_think_end_token_ids_prefers_native_id` and `test_get_think_end_token_ids_falls_back_to_encode_for_unknown_token` in `test_response_template.py`, and widened the existing `test_reasoning_detector_supports_think_end_token_lookups` tokenizer mock to carry `convert_tokens_to_ids` and `unk_token_id` so it exercises the fallback path the way a real tokenizer does.

The sibling method body is a parity copy of the base fix. I verified its logic directly (native id wins, unknown token falls back to encode, existing lookup path preserved), and both changed files pass py_compile and ruff. This host has no sglang Python environment, so the full pytest run stays behind the `run-ci` gate. Both detectors in #47205 now resolve the marker to its native id, so the issue is fully addressed.
