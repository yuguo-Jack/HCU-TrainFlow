# [Perf] [NVIDIA] nvfp4: Fuse SiLU-and-mul with the next linear layer's NVFP4 activation quant

[Upstream PR](https://github.com/sgl-project/sglang/pull/48263) · state: open · merged: False

## Original PR description

## Motivation

In a dense MLP whose down projection is a compressed-tensors W4A4 NVFP4 linear, `silu_and_mul` writes a BF16
activation that `fp4_quantize` immediately reads back. This PR uses FlashInfer's activation+quantization fused kernel  `flashinfer.quantization.silu_and_mul_nvfp4_quantize` for this scenario, plus a fix for 3-D inputs to the NVFP4 linear.

## Modifications

- `SiluAndMul.fuse_output_quant(down_proj)` registers the consumer once at build time: only W4A4 NVFP4 linears, only
  on NVIDIA GPUs (`is_cuda()`), and only when FlashInfer's kernel and CuTe-DSL are available. `forward_cuda` keeps the
  unfused path first and uses it for other dtypes, widths not divisible by 32, non-contiguous inputs, LoRA and sequence
  parallelism. There is no batch-size threshold: see the speed tests below.
- `CompressedTensorsW4A4Fp4.apply_weights` accepts the pre-quantized `(fp4, block_scale, dtype, leading_dims)` input
  or a plain activation, and inputs with leading dims (`[batch, seq, hidden]`, as vision towers pass): flattened for the
  quant and GEMM, output restored to the leading dims. Before, `mm_fp4` rejected 3-D inputs.
- Wired into `LlamaMLP` and `Qwen2MLP`. The existing block-FP8 decode fusion (`DenseSiluAndMulQuant`) is unaffected. On by default where it applies.
- Tests: `test/registered/kernels/ops/quantization/test_silu_and_mul_nvfp4_quant.py` (SM100+: the kernel's output vs
`silu_and_mul` + `fp4_quantize`, codes and swizzled scales, 1 to 4100 tokens, leading dims),
`test/registered/unit/layers/test_silu_and_mul_nvfp4_fusion.py` (CPU: which linears are fused, fallbacks, non-NVIDIA
and no-FlashInfer cases), and a manual benchmark `test/manual/kernels/bench_silu_and_mul_nvfp4_quant.py` (CUDA graph,
several seeds)

## Accuracy Tests

- Kernel: 0 byte mismatches vs `silu_and_mul` + `fp4_quantize` (FP4 codes and swizzled block scales) at every
  benchmarked shape (1 to 32768 tokens, three widths, several seeds) on RTX 5090
- RedHatAI/Llama-3.1-8B-Instruct-NVFP4, GSM8K 5-shot, all 1319 questions, RTX 5090: main (f2d3188) 0.682, this PR: 0.688

**Issue**

`_accepts_nvfp4_input` uses `getattr(linear, "scheme", None)` and `getattr(scheme, "accepts_prequantized_input", False)`. SGLang does not allow defensive `getattr`. `LinearBase` already defines `scheme = None` for exactly this `is None` check. If the flag is renamed later, this code silently turns the fusion off instead of failing.

**Fix**

Type the argument as `LinearBase` and read the field directly: `isinstance(linear.scheme, CompressedTensorsW4A4Fp4)` with a local import. Or declare `accepts_prequantized_input: bool = False` on `BaseLinearScheme` and check `linear.scheme is not None and linear.scheme.accepts_prequantized_input`. The CPU test's `_linear()` helper then needs a real `scheme` field.

[by Claude Code] **Severity: style | Confidence: Medium**

**Issue**

This adds a second way for an NVFP4 linear to take a pre-quantized input. `ModelOptFp4LinearMethod.apply` already accepts an `(fp4, scale)` tuple when `layer._accepts_prequantized_fp4` is set (used by `qwen3_5.py` and `deepseek_v2.py`). This PR adds a scheme flag and a different 4-tuple, `(fp4, scale, dtype, leading_dims)`, for compressed-tensors only. So `SiluAndMul.fuse_output_quant` never fuses ModelOpt NVFP4 Llama/Qwen2/Qwen3 checkpoints, although their `down_proj` can already take a quantized input.

**Fix**

Use one opt-in and one tuple layout for both NVFP4 linear methods, and let `fuse_output_quant` accept ModelOpt W4A4 linears too. If ModelOpt is out of scope for this PR, say so in the description.
