# [Feat] [SM120] deepseek-v4: Support NVFP4 KV cache for target and DSpark

[Upstream PR](https://github.com/sgl-project/sglang/pull/45417) · state: open · merged: False

## Original PR description

## Summary

Add NVFP4 KV cache support for DeepSeek-V4 DSpark on SM120/SM121, reusing FlashInfer's existing NVFP4 attention and quantize/append kernels. The implementation supports independent target and draft cache formats and retains DSpark's PP=1 configuration.

This PR includes the two original commits from #38646, preserving their authorship, plus the DSpark integration commit.

## Implementation

- Route DSpark context and query KV writes through BF16 norm/RoPE followed by `nvfp4_quantize_append_sparse_mla_cache`.
- Select attention dispatch from the actual cache pool format, supporting mixed target/draft formats in one process.
- Add `SGLANG_SM120_DRAFT_KV_CACHE_FORMAT=auto|fp8|nvfp4`; `auto` follows the target format.

| Target KV | Draft KV | `SGLANG_SM120_KV_CACHE_FORMAT` | `SGLANG_SM120_DRAFT_KV_CACHE_FORMAT` |
| --- | --- | --- | --- |
| FP8 | FP8 | `fp8` | `fp8` |
| NVFP4 | FP8 | `nvfp4` | `fp8` |
| NVFP4 | NVFP4 | `nvfp4` | `nvfp4` |

Use `--kv-cache-dtype fp8_e4m3` for byte storage; the environment variables select the cache ABI. The measured DSpark configuration uses `--speculative-algorithm DSPARK --speculative-dspark-block-size 5`.

Requires FlashInfer's NVFP4 sparse-MLA APIs from flashinfer-ai/flashinfer#4955 and TOPK=192 dispatch/planner support. Validation used FlashInfer `5d0c89eacae6ca08f2a1ce92eba557bbad7a1bfc` with the NVFP4/TOPK=192 patches. Here 192 is the sparse index width; head dimension is 512.

## Performance

Measured on four PRO5000 GPUs (SM120), **TP4 / PP1 / EP1**, with the full DeepSeek-V4-Flash-DSpark checkpoint at commit `4625ff90c` on 2026-10-20. The target-only NVFP4 cache configuration improved output throughput by **1.82%–3.64%** over FP8/FP8; using NVFP4 for both target and draft improved throughput by **0.48%–3.54%** over the same baseline.

Spec-Bench prompts with the DeepSeek chat template, input 92–1478 tokens, output 256 tokens, temperature 0, three repeats per point. All formats used the same full/SWA token capacity of 65536. Values below are medians of run-level output throughput for the unified prefill/decode service.

| Concurrency | FP8 target / FP8 draft (tok/s) | NVFP4 target / FP8 draft (tok/s) | Gain vs FP8/FP8 | NVFP4 target / NVFP4 draft (tok/s) | Gain vs FP8/FP8 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 195.17 | 198.72 | +1.82% | 196.11 | +0.48% |
| 4 | 462.55 | 478.37 | +3.42% | 468.70 | +1.33% |
| 16 | 759.67 | 787.29 | +3.64% | 781.59 | +2.88% |
| 32 | 1046.69 | 1082.43 | +3.41% | 1083.72 | +3.54% |

With target NVFP4 / draft FP8, TPOT speedup over FP8/FP8 was **1.018× / 1.041× / 1.030× / 1.042×** at concurrency 1 / 4 / 16 / 32. These ratios use the median of the three run-level mean TPOT measurements.

## Accuracy

**DSpark NVFP4 showed accuracy comparable to the FP8 baseline in this GSM8K evaluation, with no statistically significant accuracy difference observed.**

Evaluated on four PRO5000 GPUs at **TP4 / PP1 / EP1**, commit `4625ff90c`, on 2026-10-22: the full **1,319-question GSM8K test set**, zero-shot, thinking disabled, temperature 0, concurrency 8, and a 4096-token generation limit with normal EOS stopping. All three variants used the same model weights, prompts and generation settings.

| Target KV / Draft KV | Strict answer match | Last-number match |
| --- | ---: | ---: |
| FP8 / FP8 | 1274/1319 (**96.59%**) | 1276/1319 (**96.74%**) |
| NVFP4 / FP8 | 1276/1319 (**96.74%**) | 1275/1319 (**96.66%**) |
| NVFP4 / NVFP4 | 1273/1319 (**96.51%**) | 1274/1319 (**96.59%**) |

Strict matching extracts the numeric answer after `####`; last-number matching extracts the final numeric value. Both scoring rules were fixed across formats, and prompts were matched by hash for every question.

Relative to FP8/FP8, the NVFP4 configurations differ by at most **2 correct answers (0.152 percentage points)** under either scorer. Paired exact McNemar tests against FP8/FP8 give **p ≥ 0.8145**. Across all three variants, **3,957 requests completed with zero HTTP errors and zero truncated outputs**.

### Static review notes (no hardware involved)

A few checks against current `main` (`4387a94cf`) and the pinned FlashInfer release, plus some questions on how the benefit is measured. Nothing here is a judgement on the kernel work itself.

### 1. `test/srt/` is rejected by Lint and never collected by the suite

Both new test files sit in `test/srt/mem_cache/`. On `main`, `.pre-commit-config.yaml` has a local hook `forbid-test-srt-path` with `language: fail` and `files: ^test/srt/`, added in `240862923e` (2026-10-28) — after this branch's last push (2026-10-22), so the failure is not yet visible locally. `test/README.md` on `main` states the directory is retired, and `test/run_suite.py` only scans `test/registered/` via `sglang.test.ci.ci_register.collect_tests`, which requires a `register_cuda_ci(est_time=..., stage=..., runner_config=...)` literal in each file plus the `if __name__ == "__main__":` block. As written, the "33 GPU regression cases" would neither pass Lint nor be collected; moving them under `test/registered/` with registration looks required.

Also on the CI picture: the only check runs present on head `4625ff90c` are `Check PR title` (five failures, the latest one passing), `label` and `update-pr-body`. There is no `Lint` and no `pr-test` run, because this fork PR has no `run-ci` label. So none of the above has been surfaced by CI yet.

### 2. Two private FlashInfer import paths do not exist in the pinned release

The PR imports

```
from flashinfer.mla._sparse_mla_nvfp4_sm120 import _sparse_mla_nvfp4_sm120_paged_attention
from flashinfer.mla._sparse_mla_nvfp4_sm120_plan import NVFP4KernelVariant, plan_nvfp4_sparse_mla_sm120
```

`sglang` pins `flashinfer_python[cu13]==0.7.2` (`python/pyproject.toml:41`, unchanged on `main` and unchanged by this PR). In v0.7.2 there is no `flashinfer/mla/_sparse_mla_nvfp4_sm120.py` — the flat modules were folded into the `_sparse_mla_sm120/` package:

| symbol | v0.7.2 location |
| --- | --- |
| `_sparse_mla_nvfp4_sm120_paged_attention` | `flashinfer/mla/_sparse_mla_sm120/_dsv4_nvfp4.py:135` |
| `nvfp4_quantize_append_sparse_mla_cache` | same file, `:305`, also re-exported from `flashinfer.mla` |
| `NVFP4KernelVariant` | `flashinfer/mla/_sparse_mla_sm120/_dsv4_nvfp4_policy.py:117` |
| `plan_nvfp4_sparse_mla_sm120` | same file, `:296` |

`from flashinfer.mla import nvfp4_quantize_append_sparse_mla_cache` (also used in this PR) works as-is, and `from flashinfer import nvfp4_kv_quantize` (used by a test) resolves in v0.7.2. So only the two private paths need retargeting.

On the dependency note in the description: flashinfer-ai/flashinfer#4955 was merged 2026-09-07, and the commit cited for validation (`5d0c89eac`, 2026-09-14) predates the v0.7.2 release (2026-10-15). Against v0.7.2 no out-of-tree patch is needed — TOPK=192 is already whitelisted, `_DECODE_DSV4_TOPKS = frozenset({128, 192, 256, 512, 1024})` in `_sparse_mla_sm120/_policy.py:191`. Suggest restating the requirement as a version floor (e.g. `flashinfer_python>=0.7.2`), and bumping the pin in this PR if 0.7.2 turns out to be that floor, otherwise the nvfp4 arm stays unreachable in CI.

### 3. Format selection is spreading across four surfaces

Main already has three knobs for this: `--kv-cache-dtype`, `--speculative-draft-kv-cache-dtype` (choices `auto/fp8_e5m2/fp8_e4m3/bf16/bfloat16`, `python/sglang/srt/arg_groups/fields/spec.py:151`, already plumbed through `configure_kv_cache_dtype` and `draft_kv_budget.py`, with a per-model override precedent), and `SGLANG_DSV4_KV_LAYOUT` (`auto/v4/v41/v41_new`, read by `select_dsv4_kv_layout`, `deepseek_v4_memory_pool.py:206`). `SGLANG_SM120_KV_CACHE_FORMAT` and `SGLANG_SM120_DRAFT_KV_CACHE_FORMAT` would make five. `.agents/skills/env-var-conventions/SKILL.md` Rule 6 says: "don't add an env var that duplicates an existing CLI flag. Pick one surface." Since draft-vs-target split is exactly what `--speculative-draft-kv-cache-dtype` already models, adding `nvfp4` to its choices looks like the smaller change, and the `auto` = follow-target semantics comes free with it.

Related: the nvfp4 branch of `create_buffer` computes `bytes_per_page_padded = nvfp4_page_size * 384` directly. `KVLayout.page_bytes()` in `python/sglang/kernels/ops/attention/dsv4/kv_layout.py` is where the repo models "raw = page_size * bytes_per_token, then pad up to the reader's TMA row stride" (`page_align`), and the registry already carries fp4 entries (`V41_FP4` = 256+32 with `page_align` 256, `V41_FP4_NEW` = 256+32 with `page_align` 288) plus `is_fp4` and `row_addressing`. Question: is `64 * 384 = 24576` already a multiple of the stride the nvfp4 reader requires, making padding a no-op? If so it is worth a comment saying why; if not, bypassing the registry is a live bug, and adding an `NVFP4` enum entry would keep padding and row addressing in one place either way.

### 4. Byte saving is 1.52x, and the benchmark holds capacity fixed

SM120's FP8 baseline here is the `V4` layout (576 data + 8 scales = 584 B/token, `select_dsv4_kv_layout` returns `V4` whenever `mode == "auto"` on a non-SM100 device). Against 384 B/token that is 584/384 = 1.52x, not 2x, because the 128 B of BF16 rope is untouched. Worth putting in the description so reviewers don't read "NVFP4 KV" as a halving.

The throughput table then fixes the thing that changed: "All formats used the same full/SWA token capacity of 65536", so the 1.52x-cheaper cache is never converted into more concurrency or a longer context — which is the reason to accept 4-bit KV error in the first place. +0.48%...+3.64% at matched token capacity is also inside the range where I would want an A-A repeat before reading it as signal. A comparison at matched memory (FP8 at 65536 vs NVFP4 at ~99500 tokens, or FP8 vs NVFP4 at the same `--mem-fraction-static` with max concurrency / longest context as the reported quantity) would measure the actual benefit. The GSM8K section is already careful about the matched-prompt and paired-test discipline; the gap is only that nothing here measures the other side of the trade.

### 5. Smaller items

- `is_nvfp4_kv_cache` is wrapped in `@lru_cache(maxsize=2)`, so the `envs.SGLANG_SM120_KV_CACHE_FORMAT.get()` inside it resolves once per process. Rule 3 of the env doc asks for `.get()` at each read site precisely so `envs.X.override()` works in tests; with the cache, an override in a test has no effect unless the cache is cleared. In the same spirit, `flash_mla_sm120.py` binds `_sm120_kv_cache_format = envs.SGLANG_SM120_KV_CACHE_FORMAT.get()` at import and uses `kwargs.get("kv_cache_format", _sm120_kv_cache_format)` — the accompanying comment says dispatch should come from the pool's format, so the import-time fallback may be worth dropping.
- `self.nvfp4_page_size = min(self.page_size, 64)` together with the backend's `assert self.page_size == 256` means "four nvfp4 kernel pages per allocator page" is the only reachable configuration. Which `page_size` values do the "page boundaries" regression cases actually cover?
- The description reports serving numbers on four PRO5000 GPUs but the 33 regression cases on an RTX PRO 6000. Which SKU is the kernel-level coverage on, and does it match the SM120 part most users of this path will run?
- The branch is currently marked unmergeable. Applying the diff hunk by hunk to current `main`: `deepseek_v4_memory_pool.py` 9 of 16 hunks fail, `flash_mla_sm120.py` 1 of 3, `deepseek_v4_backend.py` 1 of 2, `environ.py`, `kv_cache_configurator.py` and `models/deepseek_v4.py` 1 of 1 each; `compressor_v2.py` applies clean. So a rebase is needed regardless of the above.
