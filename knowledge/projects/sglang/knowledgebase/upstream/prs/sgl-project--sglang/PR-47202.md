# [Fix] [AMD] dsv4: stop per-batch Triton recompiles of the FP4 prefill schedule prep kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47202) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1-Flash PD prefill servers on MI355X keep logging the warning below. The setup is DP attention TP2/DP2 and TP4/DP4, `--chunked-prefill-size 16384`, and AgentX traffic with median ISL ~97K and p95 ~420K tokens, on sglang main of 2026-10-28. The files involved are unchanged on current main.

```
Triton kernel '_prefill_schedule_prep_kernel' took 1.43 s to compile after serving started. Serving-time compilation can stall the engine; pre-compile it during engine init.
```

| run (prefill servers) | warnings | per server | compile stall |
|---|---|---|---|
| 4 x TP2/DP2 (4 runs) | 153-175 | 34-46 | 222-256 s |
| 2 x TP4/DP4 (3 runs) | 89-91 | 44-46 | 128-132 s |

Each warning is one rank's forward stalled for 1.00-4.05 s (median 1.43 s). The rate falls over a run but does not stop: 595 of the 936 warnings come in the first 15 minutes and 33 come after the first hour. sglang only warns on compiles of at least 1 s, which here means the `BLOCK_T=4096` variants and some `BLOCK_T=2048` ones. Smaller buckets also recompile, at 0.3-0.8 s each, without being logged.

**Root cause.** `_prefill_schedule_prep_kernel` lets Triton specialize every runtime argument. Triton compiles a separate variant for each combination of: each int being 1 (baked in as a constexpr) or a multiple of 16, and each pointer being 16-byte aligned. All of these change from batch to batch:

- `T` (rows) and `P = max(1024, rows)`.
- The page-table width and row stride, and the tile count `cdiv(w_dst, 256)`. The tile count is 1 for contexts up to ~24K and 16 near 0.5M.
- `local_ends` and the page table arrive as row slices. The V4.1 ratio-2 indexer scores a long request in chunks of `131072 // ceil(L / 8192)` rows, which is what fits the 2 GiB pooled logits block. `aiter_fp4_paged_mqa_logits` then rebuilds the schedule for each chunk, so the alignment of these pointers follows the chunk's row offset.
- `incl`, `excl`, `row_to_batch` and `scalars` are views into one scratch allocation at `4 * rows`-byte offsets, so their alignment follows `rows % 4`.

`BLOCK_T` (a power of two from 16 to 4096) is the only argument that has to be a compile-time key.

**Offline evidence** (no GPU; Triton 3.8 HIP backend, gfx950). I replayed the launches that the logged single-request batches imply through the real `build_prefill_schedule`: the whole-batch workspace plus the ratio-2 row chunks. Triton's launch key was computed on the host with the same binder and `compute_cache_key` that `JITFunction.run` uses.

- Before the change: 145-207 distinct variants per prefill server in the six runs where most batches hold a single request, and 299 across all runs. Batches that mix requests are not replayed, so these counts are lower bounds. The `BLOCK_T=4096` bucket alone has 27-36 per server, against 34-46 logged warnings per server.
- After the change: 9 per server, one per `BLOCK_T`.

## Modifications

- `fp4_indexer_schedule_hip.py`:
  - `_prefill_schedule_prep_kernel` gets `do_not_specialize` on its 8 ints and `do_not_specialize_on_alignment` on its 9 pointers.
  - `_pad_page_table_kernel` gets the same treatment. It receives the same per-batch arguments on the non-fused (> 4096 rows) path; it compiles in ~0.02 s, so this keeps it to one pre-compiled variant rather than fixing a stall.
  - Pointers keep Triton's within-2 GB buffer-ops specialization.
  - The kernel code is unchanged and the outputs are integer-exact.
- New `warmup_prefill_schedule(device)`: runs one `build_prefill_schedule` per `BLOCK_T` bucket plus one pad.
- `DeepseekV4HipRadixBackend.__init__` calls it when the backend can build a prefill schedule (C4 FP4 indexer, or the V4.1 low-ratio indexers) and is not a draft worker. Nothing is left to compile after `mark_serving_started()`. The cost is 9 compiles, about 5.3 s in total when the cache is cold (offline gfx950 measurement; 0.35 s for `BLOCK_T=16` up to 1.45 s for `BLOCK_T=4096`). Later starts load them from Triton's disk cache.
- New test `test/registered/kernels/ops/attention/test_fp4_indexer_schedule_hip.py`.

## Accuracy Tests

- The kernel is integer-only and its body is unchanged; only Triton's specialization hints differ.
- New GPU tests (gfx95):
  - `build_prefill_schedule` equals AITER `compute_prefill_schedule` (`cta_info`, `safe`) and a zero-padded reference table, over 16 realistic shapes: row-sliced tables at odd offsets, bucket 4 and 64, 1-4096 rows.
  - After `warmup_prefill_schedule`, these launches add no JIT cache entries.
- New GPU-free tests: Triton's host-computed gfx950 launch key gives exactly one variant per `BLOCK_T` over 48 shapes. With the two decorators reverted, this test fails (5 variants for `BLOCK_T=16`). Both pass in the ROCm image without a GPU.
- MI355X GPU validation is pending.

## Speed Tests and Profiling

- Serving: this removes every serving-time compile of these two kernels. On these runs that is 34-46 logged compiles of at least 1 s per prefill server, plus the unlogged sub-second ones.
- Instruction streams (gfx950, offline compile):
  - `BLOCK_T=16`: the patched kernel is instruction-for-instruction identical to the original's least-specialized variant (2004 instructions).
  - `BLOCK_T=4096`: 13139 instructions, against 12674-13418 for the original variants these runs compiled.
- MI355X device timings, original vs patched, are pending.
