# [Feat] metrics: expose scheduler-to-router delivery latency

[Upstream PR](https://github.com/sgl-project/sglang/pull/46596) · state: open · merged: False

## Original PR description

## Motivation

Part of #43304: router CPU and processing-time metrics cannot expose a backlog between the scheduler's send and the detokenizer router's receive. Add a histogram for this delivery boundary, complementary to the existing CPU metric and the throughput, worker-identity, processing-time, and tracing proposals.

## Modifications

- Add `sglang:detokenizer_router_delivery_seconds` when metrics are enabled with multiple detokenizer workers. Buckets span 100 microseconds through 120 seconds, covering the issue's reported backlog.
- Timestamp immediately before serialization and observe after decoding, once per incoming message before grouping or fan-out. The interval includes serialization, send blocking, IPC waiting, and decoding. No request labels are added.
- Carry the timestamp after the normal payload in an atomic multipart message and reuse the existing receive codec. Accept legacy single-frame messages without a delivery observation. Metrics-off, single-worker, and skip-tokenizer paths keep the existing single-frame path without new clock reads.
- Document the same-host monotonic-clock and compatible-endpoint requirements. This implements one part of #43304 and does not close the whole issue.

## Accuracy Tests

Local validation on Ubuntu 24.04/WSL2, RTX 5070 Laptop, Python 3.12, Torch 2.14.1+cu130, Triton 3.8.0, sglang-kernel 0.4.10, and FlashInfer 0.7.2:

- Focused manager/sender/transport modules: **29 passed, 18 subtests passed** using the actual installed runtime dependencies; the tested changes are included in `7040d357`.
- Real ZMQ subprocess tests cover both msgpack and pickle, a controlled receiver backlog, actual Prometheus count/sum, control/empty-batch fan-out, legacy input, and metrics-off frame/clock checks. Four timed messages produce four observations despite seven downstream messages.
- Native Qwen2.5-1.5B-Instruct smoke at `37a69e8` with two detokenizers: ordinary, batched, and streaming generation passed with metrics on and off. All four final texts, including the streaming output, matched across both modes. With metrics enabled, the histogram count increased from 3 to 17 and its sum was positive; with metrics disabled, the metrics endpoint returned 404. The latest commit `7040d357` changes only tests; its production code is identical to the smoke-tested commit.
- Single-detokenizer control: Qwen2.5-1.5B-Instruct passed twice in fresh processes with the same CLI arguments as the earlier failed attempt (only the HTTP port changes). Ordinary, batched, and streaming generation passed; generated text matched across both repeats, and the delivery metric stayed absent. The 0.5B control also passed. The historical CUDA allocation failure is retained; its cause has not been established.
- The new regression fails on the unmodified base because delivery instrumentation is absent.

## Speed Tests and Profiling

The CPU transport test retains per-send overhead samples for small control messages. These are sender/encoding diagnostics, not serving throughput or full-router benchmarks. No inference speedup is claimed. The model smoke used eager `torch_native` attention with CUDA Graph disabled.

All applicable changed-file pre-commit hooks pass. A full-repository run reached the unchanged Rust Clippy hook, then the local WSL environment failed without a Clippy diagnostic; that whole-repository run is not reported as passing. Official CI remains required.
