# [Bug] Gate caller mm_hashes behind --trust-caller-mm-hashes

[Upstream PR](https://github.com/sgl-project/sglang/pull/44653) · state: open · merged: False

## Original PR description

Thanks for the thorough report and the reproducer, @yyymk — the cross-tenant disclosure angle makes this worth fixing properly.

Fixes #44641.

## Root cause

The native `/generate` endpoint accepts a caller-declared `mm_hashes` field, and `TokenizerManager` applied it unconditionally to each `MultimodalDataItem` via `item.set_hash(int(hex_hash, 16))`. Since `MultimodalDataItem.hash` determines `pad_value` (`schedule_batch.py`), and the image region of the token sequence is that pad value repeated, the declared hash *is* the prefix-cache identity of the image segment. A request sending image B but declaring image A's hash produced A's token sequence for the image region and hit A's cached KV — silent wrong-image reuse, with the radix cache shared across tenants. The embedding path never had this problem: `EmbeddingReqInput` has no `mm_hashes` field at all (the #34411 precedent).

## Fix

Caller-declared `mm_hashes` are now honored only when the server is launched with the new opt-in flag `--trust-caller-mm-hashes`:

- Default (flag unset): caller `mm_hashes` are ignored (one warning per tokenizer worker), and the content-based hash is recomputed downstream via `set_pad_value()` → `hash_feature()`, as before.
- Flag set: today's behavior is preserved exactly (same length check, same per-item parse fallback) for the external-KV-router use case the field was built for.

Design invariants:

1. A caller-declared hash must never become a cache identity by default — it is untrusted input from the network, and the radix cache is shared across tenants.
2. The flag is the *only* gate: there is no per-request allowlist, no partial application. With the flag off, `MultimodalDataItem.hash` stays `None` until the content hash is computed, so no code path can observe the declared value.
3. Malformed input never blocks a request: length mismatch ignores the whole list, a bad hex entry falls back per item (unchanged from before).
4. `mm_content_hashes` (SHA-256 content identities, already gated by `--trust-mm-content-hashes`) are untouched.

## Reproducer (unit-level; no GPU on this machine)

I don't have a GPU here, so I verified at the logic level: the real `MultimodalDataItem` class and the real `_apply_caller_mm_hashes` method, extracted verbatim from the repo files, driven with mock multimodal items. Scenario: request sends image B (content hash `0xAAAA...0002`) but declares image A's hash (`0xDEADBEEF...0001`).

```
=== BEFORE (pre-fix code): caller hash applied unconditionally ===
old code, image B declares A's hash: item.hash=0xdeadbeef00000001 pad_value=1000001
pad_value derived from declared hash => prefix-cache identity = image A (pad matches A's own: True)

=== AFTER (fixed code): default --trust-caller-mm-hashes unset ===
WARNING Ignoring caller-provided mm_hashes: --trust-caller-mm-hashes is not set, ...
new code flag OFF, image B declares A's hash: item.hash=0xaaaa0000bbbb0002 pad_value=1003110978
caller hash ignored: item.hash is content hash of B (True), pad matches B's own: True

=== AFTER (fixed code): --trust-caller-mm-hashes set (KV-router use case) ===
new code flag ON, image B declares A's hash: item.hash=0xdeadbeef00000001 pad_value=1000001
caller hash honored: True, pad matches old behavior: True

=== edge cases (fixed code) ===
length mismatch (2 hashes, 1 item): ignored -> hash=None
malformed entry: ignored -> hash=None
no mm_hashes field value: untouched -> hash=None
obj without mm_hashes attr (EmbeddingReqInput-like): untouched -> hash=None
```

These are verbatim outputs of the script; the before/after comparison shows the declared hash no longer controls the pad value (prefix-cache identity) by default, and the flag restores the old behavior bit-for-bit.
