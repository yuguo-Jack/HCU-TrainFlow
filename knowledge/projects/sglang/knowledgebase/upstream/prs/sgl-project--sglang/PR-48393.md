# [Fix] kimi-k3: Cap cached_tokens at prompt_tokens in the Rust processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/48393) · state: open · merged: False

## Original PR description

## Motivation

For Kimi K3, usage leaves the three-token assistant generation stub out of `prompt_tokens` (`_reported_prompt_tokens`), but `cached_tokens` is reported as the engine counted it. The stub is model input, so a prefix-cache hit on the whole prompt covers it, and usage can report more cached tokens than prompt tokens, for example `prompt_tokens: 1022` with `cached_tokens: 1024`. Anything that computes uncached input as `prompt_tokens - cached_tokens` then gets a negative number; we hit this in a billing pipeline that rejected the usage of every full-prompt cache hit.

#35863 fixes this in the Python OpenAI layer by capping the reported cached tokens at the reported prompt tokens (`_reported_cached_tokens`). The Rust port in `rust/sglang-processor` has the same gap: `report_prompt_tokens` subtracts the stub from `prompt_tokens` and leaves `cached_tokens` as is. This PR applies the same cap there so both paths report the same usage.

## Modifications

- `rust/sglang-processor/src/openai/chat.rs`: when prompt tokens are left out of usage (Kimi K3), `report_prompt_tokens` also caps `cached_tokens` at the reported `prompt_tokens`. It feeds the unary, streaming and continuous usage. Partial hits that end before the stub, and every other model, are unchanged.
- A unit test covers a K3 cache hit that reaches the stub, one that ends before it, and another model, each as a unary reply, a streamed final usage chunk and continuous usage:

  | Model | Engine prompt / cached | Reported prompt / cached |
  |---|---|---|
  | Kimi K3, hit reaches the stub | 2075 / 2073 | 2072 / 2072 |
  | Kimi K3, hit ends before the stub | 2075 / 2000 | 2072 / 2000 |
  | Other model | 2075 / 2073 | 2075 / 2073 |

  Without the fix the first case fails (`cached_tokens` 2073).
