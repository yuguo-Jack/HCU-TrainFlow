# [Feat] [AMD] fp4: Select the Quark MXFP4 dense GEMM with --fp4-gemm-backend aiter|triton

[Upstream PR](https://github.com/sgl-project/sglang/pull/43360) · state: open · merged: False

## Original PR description

## Summary

Follow-up to #39598, as requested in its review. #39598 has merged, so this PR is now based directly on `main` and contains only its own two commits.

Extends the existing `--fp4-gemm-backend` argument with two ROCm choices for Quark MXFP4 dense linear layers, replacing the `SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM` environment variable.

- Add `aiter` (gfx95 only; AITER CK/ASM `gemm_a4w4` with preshuffled weights and AITER's a4w4 tuned configs) and `triton` (AITER Triton `gemm_afp4wfp4`) to `Fp4GemmRunnerBackend` and the valid choices.
- `--fp4-gemm-backend auto` on ROCm gfx95 picks the GEMM per Quark MXFP4 layer: AITER `gemm_a4w4` when AITER's a4w4 tuned CSV has a row for the layer's (N, K) on this GPU, Triton otherwise. On other ROCm GPUs `auto` resolves to `triton`.
- `aiter` uses the AITER GEMM for every eligible layer (layers with N <= 128 stay on Triton, as in #39598). `aiter` off gfx95, and `aiter`/`triton` off ROCm, raise at startup.
- DeepSeek MLA `kv_b_proj`, which receives the Triton-only fused split + cat tuple, opts out via `requires_triton_mxfp4_gemm` and always uses Triton.
- `QuarkW4A4MXFP4` reads the resolved backend at construction instead of the env var at import.
- `SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM` is deprecated: still honored with a deprecation warning while the flag is `auto`, ignored with a warning when the flag is set explicitly.
- Docs: `server_arguments.mdx`, `quantization.mdx`. Unit tests: `test_quark_mxfp4_asm.py`.

## Testing

CPU only so far: `test_quark_mxfp4_asm.py`, `test_quark_config.py` and `test_quark_utils.py` pass; `--fp4-gemm-backend` accepts `auto`/`aiter`/`triton` and rejects unknown values; pre-commit is clean.

Pending: GPU A/B on Qwen3.8-27B and a DeepSeek smoke test before review.

- auto vs triton and aiter vs triton have the same sign in both rounds on all three metrics. Run-to-run spread (the two runs of one arm): output throughput within 0.9% on the text rows and within 3% on the image rows.
- TTFT: -20% on the text rows. On the two image rows at concurrency 4 and 16 with 64 output tokens, the mean and median TTFT are higher with `aiter`/`auto` (c4 median 220-225 vs 131 ms), while p99 TTFT (307-322 vs 356 ms) and e2e latency (665-667 vs 891 ms) are lower. We have not root-caused this yet.
- `auto` vs `aiter`: within noise on every metric, as expected with identical layer choices.

Kernel time per forward step (torch profiler; FP4 GEMM kernels in brackets):

| Step | triton | aiter | auto |
|---|---|---|---|
| Prefill, 2048 tokens | 68.5 ms (40.0) | 57.3 ms (30.3) | 57.5 ms (30.2) |
| Decode, batch 1 | 9.7 ms (6.0) | 5.5 ms (2.75) | 5.5 ms (2.75) |

The step gain there comes from fusions that only apply on the AITER GEMM path in this image: #47154's fused MXFP4 input quantization and #43785's qkvz+ba packing. On `main` without those PRs, the `triton` vs `aiter` decode gap at batch 32 would be smaller.
