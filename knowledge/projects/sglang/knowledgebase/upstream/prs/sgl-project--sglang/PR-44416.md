# [Perf] [AMD] GLM-5.3-Flash: One-launch MoE router and narrower KDA V tile for MTP verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44416) · state: open · merged: False

## Original PR description

## Summary

At concurrency 1, a GLM-5.3-Flash MTP verify forward pushes 6 tokens through 42 MoE and 34 KDA layers. On MI355X, launch count and grid width set its time, not math.

1. Routing one MoE layer took three launches: the gate GEMM, aiter `grouped_topk` and `_fused_append_shared_experts`. `smallm_router_glm` does the gate GEMV, sigmoid + fp32-bias top-8, renormalisation and the shared-expert slot in one launch, for 1–16 tokens.
2. The KDA verify recurrence ran with `BV=32`: 64 programs on 256 CUs. `BV` 4 / 8 / 16 for ≤2 / ≤8 / ≤16 requests widens the grid; outputs are bit-identical.

| Kernel, per decode step (profiler on) | Base (µs) | This PR (µs) |
| --- | --- | --- |
| Gate GEMM `_gemm_a16_w16` (M ≤ 16) | 291.1 | 30.4 |
| aiter `grouped_topk_kernel` | 279.1 | 28.7 |
| `_fused_append_shared_experts_kernel` | 187.1 | 0 |
| `smallm_router_glm` | 0 | 363.7 |
| **Routing total** | 757.3 | **422.8** |
| KDA `fused_sigmoid_gating_delta_rule_update_kernel` | 663.0 | **352.9** |

## Scope

MI355X (gfx950) with aiter only. The router engages for GLM-5.x sigmoid top-8 MoE with one fused shared expert, 288 experts, hidden 4096, fp32 bias and 1–16 tokens; it stays off for expert parallelism, EPLB remapping, hash MoE, vision top-k and simulated routing, and the existing `SGLANG_ROCM_SMALLM_ROUTER=0` turns it off with the Qwen3.5 router. The KDA tile change needs HIP + gfx95 + KDA target verify, K = V = 128 and at most 16 heads per GPU (the measured case); other KDA models keep `BV=32`. CUDA and the Qwen3.5 router are unchanged. Stacked on #44415 (the router needs its fp32 bias).

### inline_comments

- Raiden-Makoto · comment · 2026-10-19T15:43:45Z · [source](https://github.com/sgl-project/sglang/pull/44416#discussion_r4315840224)

File: `python/sglang/srt/models/deepseek_v2.py` · line 1442

This optimized branch does not receive `num_token_non_padded`, unlike `_gate_and_topk` immediately below. On padded CUDA-graph/DP batches that bypasses the HIP contract which masks padded expert IDs and zeroes their weights, so stale padded rows can be routed and executed. Please pass the valid-token count into the fused path and add padded replay coverage.

- Raiden-Makoto · comment · 2026-10-19T15:43:45Z · [source](https://github.com/sgl-project/sglang/pull/44416#discussion_r4315840266)

File: `python/sglang/kernels/ops/moe/smallm_router_gfx950/smallm_router.hip` · line 319

The fallback renormalizes with `sum + 1e-20`, while this kernel divides by `sum` whenever it is merely positive. For deeply negative logits, a nonzero sum below `1e-20` is therefore scaled to the full routed weight instead of being attenuated like the reference path. Please match the fallback epsilon and add an extreme-negative-logit parity case.

- Raiden-Makoto · comment · 2026-10-19T15:43:58Z · [source](https://github.com/sgl-project/sglang/pull/44416#discussion_r4315842457)

File: `python/sglang/kernels/ops/moe/smallm_router_gfx950/__init__.py` · line 273

At 17 tokens this returns to the default AITER grouped-top-k path, which currently converts the FP32 correction bias back to `router_logits.dtype`; the fused path and fallback can therefore choose different experts across the 16/17 boundary. Please preserve FP32 in the fallback (the dependency issue also raised on #44415) and add an explicit M=16/17 parity test.

- Jacob0226 · comment · 2026-10-20T02:41:51Z · [source](https://github.com/sgl-project/sglang/pull/44416#discussion_r4320935380)

File: `python/sglang/kernels/ops/moe/smallm_router_gfx950/smallm_router.hip` · line 319

The fallback this replaces is aiter's `biased_grouped_topk`, which renormalizes with `sum > 0 ? rsf / sum : 0` and no epsilon; `_RENORMALIZE_SUM_EPSILON` only applies to the non-aiter paths. The kernel matches aiter (`ssum > 0 ? ssum : 1`). Sigmoid scores are > 0, so the sum is never 0 for real tokens. Happy to add `+1e-20f` if you prefer; it is a no-op in fp32 at these magnitudes.
