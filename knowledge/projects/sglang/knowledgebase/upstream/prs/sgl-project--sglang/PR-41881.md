# [AMD] Opt-in AITER FlyDSL paged decode for Qwen3.8 QSA sparse attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/41881) · state: open · merged: False

## Original PR description

## Motivation

After the indexer runs, Qwen3.8's QSA attention computes each decode row against its own compacted top-k KV set (budget 2048; Hq=24, Hkv=2, D=256).

On ROCm this goes through `flash_attn_varlen_func`, which is CK's group-mode `FmhaFwdKernel`. That is a prefill kernel: its `TileFmhaShape<128,64,32,256,32,256>` puts only `seqlen_q` on the MFMA M axis, so a length-1 decode query fills 1 of 128 rows. A B200 vs MI355X trace comparison put the AMD QSA attention core at a 149.3 µs median against 9.8 µs on NVIDIA, which uses a multi-CTA paged decode kernel.

AITER's FlyDSL `pa_decode_tile` is a kernel of that kind:
- It flattens `query_length × group` onto M, so one query fills 12 of 16 rows.
- It splits KV across CTAs.

## Modifications

**`layers/attention/qsa/pa_decode_flydsl.py`** (new)

- `flydsl_qsa_pa_decode_supported(...)`: the flag, device, dtype and shape gate. It keeps AITER imports off every other path.
- `paged_cache_views(...)`: relabels the gathered scratch as the kernel's vectorized-5D K/V cache. It creates views only; nothing is copied.

**`layers/attention/qsa/sparse_attn.py`**

`_compact_kv_paged` / `qwen_sparse_kv_extraction_paged_triton` is the existing `_compact_kv` gather with the vectorized-5D paged cache as its destination, instead of linear `[token, head, dim]` scratch:

```
out_k[block, head, d // VEC, slot, d % VEC]
out_v[block, head, slot // VEC, d, slot % VEC]
```

The loads are unchanged, so the layout costs only address arithmetic. The output is bit-identical to gather + permute at batch 1/4/16/64.

This replaces a permute + copy that cost as much as the attention itself: 9.3 µs vs 10.8 µs at one row, and 198 µs vs 71 µs at 64 rows.

**`layers/attention/qwen_sparse_attn_backend.py`**

`_forward_flydsl_sparse` reuses `_forward_trtllm_sparse`'s setup unchanged:
- the page-aligned gather;
- the static arange block table from `_get_trtllm_sparse_tables`;
- page size 64;
- the valid-count pass.

Only the cache layout and the kernel differ.

Every query row is its own length-1 sequence, which also holds for speculative verify rows.

Two constraints come from CUDA-graph capture:
- `num_partitions` is a compile-time constant of the kernel. It is chosen once at the captured maximum batch and reused.
- The split-KV partials are allocated once at that capacity, cached, and sliced per call, because the kernel refuses to allocate during capture.

**`environ.py`**, AMD/ROCm/AITER section:

- `SGLANG_AITER_QSA_PA_DECODE = EnvBool(False)` opts in.
- `SGLANG_AITER_QSA_PA_DECODE_SPLITS = EnvInt(0)` pins the KV split count. `0` means use AITER's recommendation at the captured maximum batch. AITER clamps that to [4, 8], which was tuned for batched serving; at low concurrency a larger value may be worth forcing.

## Accuracy Tests

The kernel is **not bit-exact with CK**:
- 45% of output elements match exactly;
- the max absolute difference is 9.77e-4 (1 bf16 ULP at the output magnitude).

It is equally accurate: over 48 shapes, the max error against an FP32 reference was 9.8e-4 for FlyDSL and 1.05e-3 for CK, with neither consistently ahead. The difference is reduction order.

Different rounding can still change which draft tokens are accepted, so the path stays **opt-in** until end-to-end acceptance length is confirmed.

## Speed Tests and Profiling

Setup: MI355X (gfx950), BF16, QSA shape Hq=24, Hkv=2, D=256, budget 2048, page 64.

**Attention call only**, on identical KV (from AITER's `op_tests/flydsl_tests/test_flydsl_pa_decode.py`):

| rows | CK varlen (µs) | FlyDSL pa_decode (µs) | speedup |
|---:|---:|---:|---:|
| 1 | 125.8 | 10.1 | 12.5x |
| 4 | 147.5 | 19.1 | 7.7x |
| 16 | 293.3 | 23.0 | 12.7x |
| 64 | 881.8 | 71.8 | 12.3x |

**Full post-indexer path** (gather + attention), against the CK path's compact gather + `flash_attn_varlen_func`:

| batch | CK gather | CK attn | CK total | FlyDSL gather | FlyDSL attn | FlyDSL total | speedup |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 3.0 | 127.8 | 130.8 | 3.9 | 8.7 | 12.6 | **10.4x** |
| 4 | 5.9 | 147.9 | 153.8 | 7.5 | 12.4 | 19.9 | **7.7x** |
| 16 | 20.9 | 293.9 | 314.8 | 21.8 | 21.3 | 43.2 | **7.3x** |
| 64 | 89.7 | 881.4 | 971.0 | 121.1 | 69.1 | 190.2 | **5.1x** |

All times are in µs. The paged destination makes the gather 0.9–1.6 µs slower than the linear one at small batch, and 35% slower at batch 64.
