# [Perf] [AMD] GLM5: Use Triton sparse attention for GLM-5.3 on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/41615) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.3-Flash uses BF16 sparse MLA with a 512-wide absorbed query/KV row, no RoPE tail, and a 2,051-column K-pool page table. The existing gfx950 path pads it to 2,112 columns and sends it through TileLang for both prefill and decode.

This change removes zero-width RoPE operations at compile time and lets the existing HIP default select Triton for the validated GLM-5.3 prefill and decode geometry. Explicit TileLang selection remains TileLang; unsupported K-pool/Triton geometry is rejected during backend initialization.

Inside the same geometry, the new `aiter_sparse_mla` DSA backend routes the batch sizes where AITER's Gluon `sparse_mla_fwd` is faster to AITER and keeps Triton elsewhere. It is selected explicitly with `--dsa-prefill-backend aiter_sparse_mla --dsa-decode-backend aiter_sparse_mla`. Its measured gains depend on the BF16 gather fix in [ROCm/aiter#6276](https://github.com/ROCm/aiter/pull/6276), merged in AITER as `9fd025ef`; AITER builds without it remain correct.

## Modifications

- Compile out zero-width query/KV RoPE fragments and their dot products in the Triton sparse prefill and graph-safe split-K decode kernels.
- Enable Triton for gfx950 BF16 GLM-5.3 sparse attention with 16 local heads at TP4 and 8 local heads at TP8.
- Consume the natural K-pool top-k 2,051 and existing absorbed query views without TileLang's padding or `q_all` copies.
- Use the single-pass Triton path for prefill and the reusable-workspace split-K path for decode.
- Keep explicit TileLang selection as a true TileLang path and validate K-pool/Triton geometry at initialization.
- Add the `aiter_sparse_mla` value for `--dsa-prefill-backend` and `--dsa-decode-backend`. It serves decode batches of at least 16 and prefill batches of at most 256 tokens with AITER `sparse_mla_fwd`; all other batches stay on Triton. Selecting it outside the geometry below raises at initialization.
- Extend tests across token boundaries, live-index counts, index locality, physical padding, CUDA graphs, the AITER dispatch bounds, and AITER-versus-Triton agreement.

The existing HIP backend default selects Triton when no explicit DSA backend is provided. K-pool accepts that selection, and `aiter_sparse_mla`, only for:

```text
gfx950 + BF16 KV + H={8,16} + D=512 + K-pool top-k=2051
```

## Accuracy Tests

Full GLM-5.3-Flash GSM8K, 1,319 examples, thinking enabled, temperature 1.0, top-p 0.95, with `--dsa-prefill-backend aiter_sparse_mla --dsa-decode-backend aiter_sparse_mla`:

| Configuration | Score | Stop rate | Truncated rate | Error rate |
| --- | ---: | ---: | ---: | ---: |
| TP4 — `aiter_sparse_mla` | 97.19% | 100.00% | 0.00% | 0.00% |
| TP8 — `aiter_sparse_mla` | 96.74% | 99.62% | 0.38% | 0.00% |

TP4 used a 65,536-token context, 64 evaluator threads, and 32,768 maximum output tokens. TP8 used a 131,072-token context, 1,200 evaluator threads, and 4,096 maximum output tokens. Decode CUDA graphs were enabled for TP4 and TP8.

Component validation: `test_tilelang_dsa_zero_rope.py` **24 tests passed, 47 subtests passed** with both the image's AITER and AITER with ROCm/aiter#6276. Coverage includes TP4/TP8 head geometry, zero through 2,051 live indices, duplicate and mixed rows, all-masked physical padding, production token boundaries through 131,072, finite and deterministic output, the explicit TileLang path, split-K workspace reuse, CUDA-graph capture/replay, the AITER dispatch bounds, and AITER agreement with the Triton prefill and decode kernels at 16, 64, and 256 tokens.
