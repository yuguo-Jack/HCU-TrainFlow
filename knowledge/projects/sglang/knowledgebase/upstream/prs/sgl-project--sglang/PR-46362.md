# [Fix] disaggregation: Gate the decode retraction host-pool default on host-memory support

[Upstream PR](https://github.com/sgl-project/sglang/pull/46362) · state: open · merged: False

## Original PR description

## Motivation

When `--disaggregation-decode-retraction-backup` is unset, a PD decode server resolves it (`kv_cache_builder.resolve_decode_retraction_backup`) to `host_pool` whenever the KV pool supports it. That builds a HiCache host pool. The host pool picks its allocator from `pool_host.common.ALLOC_MEMORY_FUNCS` by device type. Only `npu`, `musa` and `xpu` have entries, and every other device falls back to `alloc_with_host_register`, i.e. `cudaHostRegister`. On a device that is neither CUDA nor ROCm the server therefore crashes at startup, just because the user didn't pass a flag. That includes CPU and out-of-tree platforms such as Neuron/Trainium.

## Modifications

- New `kv_cache_builder.device_can_back_host_pool(device)`. It is True when the device type has an explicit host allocator in `ALLOC_MEMORY_FUNCS`, or when it is a CUDA/ROCm device. It checks keys with `in`, so it doesn't insert defaultdict entries.
- `resolve_decode_retraction_backup` only defaults to `host_pool` when that is true. Otherwise it defaults to `cpu_tensor`, the existing fallback used for HIP, DCP, recurrent-state models, etc.
- An explicit `--disaggregation-decode-retraction-backup host_pool` is unchanged and still honored.

## How it was found

Found bringing up PD on an out-of-tree Neuron/Trainium platform plugin. The decode server crashed in `cudaHostRegister` while building the backup-only host pool. The plugin currently works around it by setting `disaggregation_decode_retraction_backup = "cpu_tensor"` in its `apply_server_args_defaults`.

## Tests

- Run (macOS, CPU only): `test/registered/unit/mem_cache/test_retraction_backup_platform_default.py` (new). It checks that devices with a host allocator return True, that `cuda` returns True only on CUDA/ROCm builds, that CPU and unknown out-of-tree devices return False, and that the check doesn't mutate `ALLOC_MEMORY_FUNCS`.
- Not run: `test_decode_retraction_backup.py` is a CUDA test and cannot run here. No GPU PD e2e. The full `resolve_decode_retraction_backup` was not exercised end to end on CPU.

## Open questions

- Should this be a platform hook instead, e.g. `SRTPlatform.supports_host_memory_registration()` or a platform-provided host allocator? Then an out-of-tree platform could opt in to `host_pool` with its own pinned allocator, instead of inserting into `ALLOC_MEMORY_FUNCS`. I kept the device-type check because it matches how the allocator is chosen today.
- HiCache itself (`--enable-hierarchical-cache`) on such devices has the same `cudaHostRegister` fallback. Not addressed here.
