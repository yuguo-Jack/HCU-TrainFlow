# [Perf] [AMD] mla: Pack cached prefixes end to end in chunked-prefix MHA on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/47037) · state: open · merged: False

## Original PR description

## Motivation

- DeepSeek-style MLA models (DeepSeek V2/V3, Kimi) run chunked-prefix MHA when a prefill batch has cached prefixes; prefix keys are attended in chunks of at most `SGLANG_MAX_KV_CHUNK_CAPACITY` (`C`) keys.
- Today every chunk gives every request the same `C // batch_size` keys. When a batch mixes one long prefix with short or empty ones, most of each chunk is wasted, and the longest prefix alone sets the chunk count: `ceil(max_prefix / (C // bs))`.
- Cost: prefixes `[350000, 15000, 7495, 0]` with `C = 65536` take 22 chunks per layer, while the 372,495 cached keys fit in 6.
- This PR changes the layout on ROCm only; every other platform keeps today's layout and chunk metadata.

## Modifications

- `test: make the manual prefix chunk info test run again`: `test/manual/attention/test_prefix_chunk_info.py` failed on main (fake backend without `runner_ids`, no published config). It now publishes a default config and uses a real non-translating `RunnerIds`.
- New `model_executor/forward_batch_deepseek_mha_rocm.py`:
  - `get_num_packed_prefix_chunks`, `get_packed_prefix_chunk_seq_lens`.
  - All cached prefixes are laid end to end in request order; chunk `i` holds keys `[i*C, (i+1)*C)` of that sequence.
  - Output keeps the existing per-request `(start, length)` shape, `(num_prefix_chunks, batch_size)` int32.
- `prepare_chunked_prefix_cache_info` (shared mixin) picks the layout:

| Condition | Layout | `num_prefix_chunks` | `prefix_chunk_len` |
|---|---|---|---|
| Not HIP | request-major (unchanged) | `ceil(max_prefix / (C // bs))` | `C // bs` |
| `single_chunk` (fused prefix + extend), any platform | request-major (unchanged) | 1 | `max_prefix` |
| HIP, packing needs fewer chunks | packed | `ceil(sum_prefix / C)` | `C` |
| HIP, packing saves no chunk (e.g. equal prefixes) | request-major | `ceil(max_prefix / (C // bs))` | `C // bs` |

- Packing adds keyless rows to most chunks, and aiter on main runs such a chunk on the bf16 varlen fallback instead of the fp8 PS prefill, so HIP packs only when it saves chunks.

Consumers of the chunk metadata on HIP:

| Consumer | Status |
|---|---|
| Callers: DeepSeek-style `MHA_CHUNKED_KV(_ROCM)`, `sarvam_moe`, `dots3` | Same mixin |
| AITER (`init_mha_chunk_metadata`, `_forward_extend_prefix_chunk`), Triton gfx95 dense fp8 chunked path | Read per-request `prefix_chunk_seq_lens(_cpu)`, `prefix_chunk_cu_seq_lens`, `prefix_chunk_max_seq_lens`, `prefix_chunk_num_tokens`, `prefix_chunk_has_zero_kv`; no equal-start assumption, no read of `prefix_chunk_len` |
| Other HIP backends (wave, torch_native, flex, dsa/nsa) | Never reach chunked MHA with a prefix |
| DCP (AITER + DCP) | `filter_dcp_local_chunk_kv_indices`, `all_gather_kv_cache_for_dcp` already take arbitrary starts from `prefix_chunk_starts_cpu` |
| Prefill CUDA graph runner | Builds its own request-major metadata and sets `prefix_chunk_len`, so `prepare_chunked_prefix_cache_info` returns early |
| Zero-length rows | Already produced by short prefixes and handled via `prefix_chunk_has_zero_kv`; AITER varlen returns `out = 0`, `lse = -inf` for them. On main such chunks skip the asm fp8 prefill; #47035 runs them on it |

## Accuracy Tests

- The math does not change: every prefix key is still attended exactly once and per-chunk results are merged by LSE; only the grouping of keys into chunks changes.
- GSM8K A/B with the chunk capacity lowered so cached prefixes need several chunks: `sgl-eval 0.1.3 run gsm8k --load-preset-from-model-id moonshotai/Kimi-K3 --num-threads 32 --n-repeats 2` (full 1319 x 2; repeats hit the radix cache with prefixes of different lengths).

| Build | pass@1 (2 repeats) | Truncated | Errors |
|---|---:|---:|---:|
| this PR (`d5903ec164`) | 97.46% | 0 | 0 |
| without it | 97.65% | 0 | 0 |

  - Within sampling noise. Setup: 8x MI355X, `Kimi-K3-Quark-MXFP4-AttnFP8`, AgentX c4 layout (TP8, DCP1, Gluon MLA, DSpark block 5) with `MAX_RUNNING_REQUESTS=32` and `SGLANG_MAX_KV_CHUNK_CAPACITY=512`, simulated acceptance off. Build: `k3-agentx-pr-stack` @ `39d944c57d`, with and without this PR merged; ROCm/aiter stack @ `f9b5308b2`.
  - A measurement-only log line in the PR arm confirmed packing ran on every rank (2 uniform chunks -> 1 packed), but only a few times: sgl-eval's steady request stream mostly extends one request with a cached prefix at a time, where both layouts need the same number of chunks. So this A/B shows no regression on a live server; the tests below are the main evidence for the packed layout itself.

| Test | Device | Checks |
|---|---|---|
| `test/registered/unit/model_executor/test_forward_batch_deepseek_mha_rocm.py` (`base-a-test-cpu`) | CPU | Helpers cover each prefix token once and in order, every chunk but the last is full; non-HIP gives main's 22 chunks for the example above, HIP gives 6; HIP keeps request-major for equal prefixes (no keyless rows). |
| `test/manual/attention/test_prefix_chunk_info.py` | 1x MI355X | Packed tables where HIP packs, request-major otherwise; chunk KV indices from the GPU kernel vs a reference built from `req_to_token`. |

## Speed Tests and Profiling

Per-layer chunked prefix attention time, one run, Kimi-K3 integration build (8x MI355X, `Kimi-K3-Quark-MXFP4-AttnFP8`), request-major vs packed layout for one extend batch:

| prefixes `[350000, 15000, 7495, 0]`, `C = 65536` | chunks per layer | time per layer |
|---|---:|---:|
| request-major (main) | 22 | 163.75 ms |
| packed (this PR) | 6 | 108.78 ms |

- The measurement predates moving the layout behind `_is_hip`; the packed path it timed is the one HIP now takes for this batch.
- That build also carries #47035, so chunks with keyless requests ran on the AITER asm fp8 prefill in both columns. Without #47035, AITER on main sends them to the bf16 varlen fallback, so this number does not carry over to main by itself.

Prefill end to end:

| Setup | Value |
|---|---|
| Hardware / model | 8x MI355X, `Kimi-K3-Quark-MXFP4-AttnFP8`, TP8, DCP 1, DSpark block 3 with real acceptance |
| Build | Kimi-K3 integration build (`k3-agentx-c56` plus the open K3 PRs), AITER `6ae4bf0f2` (`yuychang/aiter` `k3-agentx-c56`), ROCm 7.2.4 |
| A/B | Integration build vs the same build with only this change reverted |
| Workload | `bench_serving` `generated-shared-prefix`, 32 groups x 8 prompts, 16K shared prefix, 1K question, 256 output, concurrency 16; one unrecorded warm-up, then 3 passes with the cache flushed before each |

| | Reverted | This PR |
|---|---:|---:|
| Mean TTFT | 1,322 ms | 1,324 ms |

- No difference, as expected: these prompts share one 16K prefix and rarely need more than one chunk. Two servers with identical code differ by up to about 2.5% in mean TTFT on this workload.
- Other platforms are not affected: the layout change is gated on HIP.
