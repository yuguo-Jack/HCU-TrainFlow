# [Fix] multimodal: Make CUDA VMM feature transport opt-in

[Upstream PR](https://github.com/sgl-project/sglang/pull/47754) · state: closed · merged: False

## Original PR description

## Summary

Make multimodal CUDA VMM transport opt-in, just like CUDA IPC. An unset
`--mm-feature-transport` now resolves to CPU on every topology, including
GB200/GB300 with IMEX. Explicit GPU transports and the deprecated IPC env opt-in
remain supported.

This avoids automatically reserving a GPU feature pool and exposing deployments
to the pool-full GPU-to-CPU fallback reported in #43402. Thanks to @StarDuster
for the report and native-stack evidence. The lifecycle fixes from #43475 are
already on main; **this is a safe-default mitigation, not a fix for the unresolved
CUDA D2H hang**, and must not close #43402.

Update CLI help, the K3 command picker, K3/GLM cookbooks and common VLM guidance:
the transport pool budget is not a GPU preprocessing peak-memory limit. Main
already accounts for the pool in the KV budget. CPU transport does not force
CPU-only decoding/preprocessing and can cost transfer latency; GPU transport is
still available for deployments that explicitly choose and validate it.

## Validation

- Original main + new regression: GB200/GB300 with IMEX both fail the intended
  CPU-default assertion. These are mocked topology-selection tests, not a real
  MNNVL deployment.
- Dedicated B200, driver 580.126.09, PyTorch 2.14.1+cu130, Transformers 5.19.0:
  430 unit tests + 206 subtests passed with CUDA hidden; 6 real CUDA IPC
  cross-process/lifecycle tests passed.
- Real-weight Qwen3.5-2B: default CPU and explicit IPC both start, expose the
  expected resolved setting, and answer four alternating/repeated red/blue image
  requests correctly (8 requests total). Both servers shut down; GPU use returned
  to 0 MiB. IPC teardown printed a PyTorch shared-tensor warning; this smoke does
  not establish long-running IPC/VMM lifetime correctness.
- Pre-commit, cookbook config validation, Mintlify build and broken-links passed.
  The build reports six warnings on unchanged pages.

Not validated: full K3, multi-node MNNVL/EPD, performance, or the incident's
aarch64/580.126.20 hang. The existing 15-case VMM GPU suite requires at least three
GPUs and was skipped on this one-GPU allocation.
