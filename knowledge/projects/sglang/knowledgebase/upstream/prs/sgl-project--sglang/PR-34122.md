# [Diffusion] Enable vectorized JointThreshold decoding on CUDA

[Upstream PR](https://github.com/sgl-project/sglang/pull/34122) · state: open · merged: False

## Original PR description

## Motivation

JointThreshold decoding already has a batched tensor implementation, but CUDA defaults to the per-row Python path. At higher concurrency, that path serializes argmax, confidence, edit, and completion work across requests and repeatedly synchronizes the host with the device.

This PR enables the existing vectorized JointThreshold path by default on CUDA. The change targets JointThreshold specifically: LowConfidence is already vectorized, and DiffusionGemma uses the separate Gemma4Renoise sampler.

## Modifications

- Default `vectorized_decoding` to true on CUDA, matching the existing NPU policy.
- Preserve `vectorized_decoding: false` as a compatibility/debug escape hatch.
- Document the default and its applicability to `LLaDA2MoeModelLM`, `SDARForCausalLM`, and `SDARMoeForCausalLM`.

## Accuracy Tests

SGLang already has a registered CUDA E2E test for this exact path:
`test/registered/dllm/test_dllm_fdfo_joint_threshold.py`. It launches
`inclusionAI/LLaDA2.1-mini` with JointThreshold and requires byte-identical
outputs between FDFO and synchronous execution. Since this PR changes the CUDA
default, both arms exercise the vectorized implementation.

I also ran an external real-model E2E A/B matrix by launching two SGLang HTTP
servers with `sglang.launch_server` and driving them with
`sglang.benchmark.serving`. All 3,968/3,968 measured LLaDA2.1-mini requests
completed with the requested output token count and no request errors.

This validates the real serving path and output completion, not downstream task
accuracy. No locally available SDAR checkpoint was available, so this PR does
not claim real-model SDAR coverage.

## Speed Tests and Profiling

Configuration:

- H200, TP1, BF16, FDFO;
- FlashInfer attention;
- radix cache disabled;
- maximum 128 running requests;
- 8,192-token context;
- exact token-ID inputs;
- baseline and vectorized arms used identical server and benchmark settings;
- each result below contains 32, 64, 128, 256, or 512 requests at concurrency 1, 8, 32, 64, or 128 respectively.

**Metric definitions:** request throughput is the achieved end-to-end client
throughput (`completed requests / benchmark duration`). TPOT is time per output
token excluding the first token:
`(request E2E latency - TTFT) / (output tokens - 1)`. The latency columns below
are TPOT, not full end-to-end request latency.

A GPU-swapped control reproduced the concurrency-64 gains:

- decode-heavy: +49.0% request throughput and -33.4% mean TPOT;
- long-prefill: +12.5% request throughput and -10.2% mean TPOT.

The batch-1 regression is an intentional tradeoff for one consistent CUDA execution path; the benefit grows with batch size because it removes per-request Python work and host synchronization.

Benchmark runtime used PyTorch `2.11.0+cu130` and FlashInfer `0.6.14`. Current SGLang pins FlashInfer `0.6.15.post1`.
