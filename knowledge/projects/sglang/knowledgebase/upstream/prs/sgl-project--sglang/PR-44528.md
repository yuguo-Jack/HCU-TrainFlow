# [Fix] scheduler: Count all pending work in DP load snapshots

[Upstream PR](https://github.com/sgl-project/sglang/pull/44528) · state: open · merged: False

## Original PR description

## Motivation

With `--load-balance-method total_tokens`, the DP controller adds each request's token count to its estimate for the rank it picks. At most every 20 ms it replaces that estimate with the rank's latest load snapshot. So any snapshot that is newer than a dispatch but does not include that request erases it, and the next request goes to the same rank again (ties go to the lowest index).

Three cases make a rank's snapshot miss work it already has:

1. **Grammar queue.** Requests waiting for their grammar to compile are not counted in `num_total_tokens` or `num_waiting_reqs`. The rank is not idle, so it keeps publishing zero-load snapshots (every 50 ms or more) while xgrammar compiles.
   - This affects any request with `json_schema`, `regex`, `ebnf` or `structural_tag` whose grammar is not yet in that rank's cache, including tool calls under the glm47 parser.
   - Measured on our host: 0.66 s to compile the glm47 tool-call EBNF with 8 threads (5.1 s with 1).
2. **Chunked prefill.** The request being chunk-prefilled counts only the KV of the chunks already run. The rest of its prompt is still this rank's work but is not counted: up to ~42k tokens for a 50k-token prompt with 8k-token chunks.
3. **Publish order.** A rank publishes right after each forward, before it reads the requests sent during that forward. That snapshot is newer than those dispatches but does not include them.

Observed with GLM-5.3-Flash, PD prefill on DWDP8 (8x H20), `--chunked-prefill-size 65536`, and 16 concurrent 48k–56k-token chat requests through the router. Tokenization is serial, so dispatches arrive ~185 ms apart and every dispatch triggers a refresh. Each cold rank took the next ~4 requests (0.66 s / 0.185 s) before the controller moved on:

| | requests per rank (DP0..7) | mean / max wait before prefill | P-side makespan |
|---|---|---|---|
| before | 5/4/4/3/0/0/0/0 | 17.8 / 44.0 s | 58.7 s |
| + 1 | 3/2/2/2/2/2/1/2 | 5.2 / 18.4 s | 34.1 s |
| + 1, 2 | 2/3/2/2/2/2/2/1 | 5.1 / 18.5 s | 36.3 s |
| + 1, 2, 3 (this PR) | 2/2/2/2/2/2/2/2 | 4.6 / 9.2 s | 25.4 s |

The trigger in that run was v0.5.21 attaching the glm47 full-assistant EBNF to every chat request. #39273 limits that to requests with tools, but the scheduler-side gaps above are unchanged on `main`.

## Modifications

- `SchedulerLoadInquirer.get_loads`:
  - Counts grammar-queue requests in `num_waiting_reqs` and `num_total_tokens`.
  - Adds the chunked request's unprefilled tokens, `seqlen - extend_end`. At publish time the KV covers `[0, extend_end)`; on the live server `used == extend_end`, while `prefix_len` still lags by one chunk.
- `Scheduler.init_load_inquirer` passes `get_grammar_queue`.
- `Scheduler.ingest_requests` publishes a forced snapshot once newly received requests are queued.
- Tests, each failing without its change:
  - `test_load_inquirer.py`: grammar-queue case and chunked-prefill case.
  - `test_scheduler_on_idle_load.py`: publish after ingest.
- Two existing bare-`Scheduler` stubs gain the `publish_load_snapshot` / `load_snapshot_writer` attributes that the new call reads.

## Accuracy Tests

Load balancing only; no model compute changes. All end-to-end runs used a v0.5.21 backport of the same three changes (v0.5.21 names `extend_end` `extend_range.end`), mounted on both P and D in the "fix" arm.

- GSM8K-200 (20-shot, through the router): 0.955 before, 0.975 after.
- 16-prompt long-context needle check: 16/16 after.
- 0 KV transfer errors in every run.

## Speed Tests and Profiling

ShareGPT through the router, with P = DWDP8 using `total_tokens` and D = TP8. Each scenario was run twice per arm (a / b), one server session per arm:

| scenario | metric | before (a / b) | after (a / b) |
|---|---|---|---|
| 64k in / 8 out, c16, 48 req | input tok/s | 30510 / 30399 | 30255 / 30360 |
| | mean TTFT | 27.4 / 27.4 s | 27.8 / 27.8 s |
| 2k in / 8 out, c128, 200 req | input tok/s | 27681 / 28851 | 29873 / 27898 |
| 2k in / 1024 out, c64, 200 req | output tok/s | 1852 / 1866 | 1849 / 1860 |
| | mean TPOT | 28.69 / 28.54 ms | 28.76 / 28.60 ms |

- **Overhead.** The decode-heavy run (D also patched) and the 2k prefill runs are within noise. The extra cost is one `get_loads()` per scheduler loop iteration that received requests; empty polls are unchanged.
- **Steady load.** Closed-loop load with equal-length prompts and no grammar is balanced about equally either way. Requests per rank in the 64k runs were 7/6/7/6/6/6/5/6 and 7/7/6/6/5/6/6/6 before, 7/6/7/6/5/7/5/6 and 7/7/5/6/6/7/5/6 after.
- **Where the fix matters.** The gain appears when snapshots lag behind dispatches: cold grammar caches, and long prompts arriving spaced more than 20 ms apart. That is the burst table in Motivation.

## Not covered

- `get_num_waiting_uncached_tokens` uses `seqlen - prefix_len` for the chunked request, which overcounts by one chunk at publish time. That field is not used for balancing; left as is.
- A refresh can still land between the post-forward publish and the post-ingest one. Closing that window exactly would need the snapshot to acknowledge dispatched requests, for example with a received-request counter.
