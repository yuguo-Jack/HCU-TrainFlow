# [MiniMax-M3] Keep the fused q/k/v + index GEMM writable by online weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/47612) · state: closed · merged: True

## Original PR description

## Motivation

MiniMax-M3's sparse-attention layers fuse `qkv_proj` and `index_qkv_proj` into one GEMM after loading and free the originals. `update_weights_from_tensor` then writes into the emptied `qkv_proj`, so the first RL weight sync fails:

```
IndexError: start out of range ([0, 0], got 128)
```

## Modifications

In `maybe_build_fused_qkv_index`, for bf16 the original `qkv_proj` / `index_qkv_proj` weights become views into the fused weight instead of being freed. An online weight update through the regular loader then writes the fused weight in place (same storage, so captured CUDA graphs keep reading the same buffer), with no extra memory. MXFP8 scales are re-laid out when fused, so MXFP8 originals are still freed as before; online updates into an MXFP8 checkpoint stay unsupported.

## Validation

Colocated RL in miles (Megatron trainer + this engine, BF16 rollout, GB300):

- Without this change, the first weight sync fails with the `IndexError` above.
- With it, MiniMax-M3 4-layer cut (2 dense-attention + 2 sparse layers), TP4/EP4, 3 steps: `--check-weight-update-equal` passes after every update, train/rollout log-prob abs diff 0.0050 / 0.0050 / 0.0050.

Run on the `radixark/miles:dev` image's sglang (before the v0.5.23 rebase of `sglang-miles`) with this function patched in; `maybe_build_fused_qkv_index` is unchanged between that base and the current one.

On the current `sglang-miles` (v0.5.23) with this PR, miles CI on 4 × H200 passes both MiniMax 4-layer e2e tests (colocated RL, weight check after every update): MiniMax-M3 https://github.com/radixark/miles/actions/runs/41275852481, MiniMax-M3.1-Flash https://github.com/radixark/miles/actions/runs/41275851020.

miles side: radixark/miles#4581 (MiniMax-M3 support) and its stack.
