# [Feat] [NPU] layernorm-sp: Support sequence parallel on NPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/41496) · state: open · merged: False

## Original PR description

## Motivation

`--enable-layernorm-sp` (Megatron-style LayerNorm sequence parallelism) had no NPU fast path. On CUDA the SP region fuses the matmul with the collective via torch's `symm_mem` operators; Ascend has no equivalent, so on NPU the flag either ran the slower un-fused reduce-scatter/all-gather path or did not engage the intended fast path at all. This PR wires an NPU fast path on top of the CANN MC2 (Matmul + Collective-Communication) fused kernels — `npu_all_gather_base_mm` / `npu_mm_reduce_scatter_base` — and makes fused-eligibility device-aware, so `--enable-layernorm-sp` on Ascend matches CUDA's fused behavior.

It also removes an NPU startup crash in TP>1 caused by the TP memory-balance heuristic, which assumes CUDA idle-capacity semantics that `torch.npu.mem_get_info()` does not model.

## Modifications

- `layers/layernorm_sp.py`:
  - Probe the CANN MC2 fused ops once at import on NPU (`_HAS_NPU_MC2_FUSED`); on non-NPU builds the flag stays `False` and the existing fallback is used.
  - Disable the MC2 fast path on arch35 (Ascend 950): its fused ops accumulate at lower GEMM precision and regress accuracy (GSM8K ~0.95 → ~0.8), so arch35 uses the plain all-gather/reduce-scatter + `F.linear` fallback while arch22 (A2/A3) keeps the fused path.
  - Route `column_parallel_g_matmul` / `row_parallel_gbar_matmul` through `npu_all_gather_base_mm` / `npu_mm_reduce_scatter_base` using the TP group's HCCL `hcom` handle (`_npu_hccl_comm_name()`), falling through to the plain collective path if the fused op raises (e.g. shape/dtype unsupported).
  - Make `sp_fused_matmul_eligible()` device-aware: NPU additionally requires MC2 availability and a 2-D weight; CUDA keeps CUTLASS / `symm_mem` selection. All paths still require an unquantized, bias-free fp16/bf16 linear.
  - `initialize_layernorm_sp()` now emits `LayerNorm sequence parallelism (SP) ENABLED ...` so activation is observable in startup logs instead of silently no-op'ing.
- `arg_groups/layernorm_sp_hook.py` — emit a startup warning on NPU that the path is currently covered only by the NPU e2e test, so it is not silently exercised in production on Ascend.
- `distributed/bootstrap.py` — skip `_check_tp_memory_balance` when `device == "npu"`; the heuristic mis-fires on Ascend and hard-crashes TP2 startup during model init. `pre_model_load_memory` used for KV sizing is unaffected.

No operator names, signatures, or checkpoint layout change; non-NPU behavior is unchanged, and the fallback keeps the un-fused collective path.

## Accuracy Tests

The NPU path is exercised by `test_npu_layernorm_sp.py` in the companion test branch `feat/npu-layernorm-sp-tests`: Qwen3-8B, `tp=2`, bf16, `--enable-layernorm-sp`, asserting

- few-shot GSM8K accuracy >= 0.85, and
- the `LayerNorm sequence parallelism (SP) ENABLED` marker is present in the server startup log, proving SP truly engaged rather than silently no-op'ing.

The fused and un-fused paths are mathematically equivalent up to floating-point reordering; on arch35 the test exercises the unfused fallback.

## Speed Tests and Profiling

The MC2 fused ops replace a separate matmul + reduce-scatter/all-gather with a single fused kernel, avoiding an extra collective round trip, mirroring CUDA's fused path. No dedicated benchmark numbers are included in this PR; a throughput regression is not expected, and the fallback path only triggers when the CANN kernels are unavailable or on arch35.
