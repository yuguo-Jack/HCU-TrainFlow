# [Perf] cosmos3: support nvenc convert image to videos

[Upstream PR](https://github.com/sgl-project/sglang/pull/47669) · state: open · merged: False

## Original PR description

## Motivation

This PR follows [#46172](https://github.com/sgl-project/sglang/pull/46172) by @mickqian , which added CPU FFmpeg encode-while-decoding for eligible Cosmos3 videos. An output-encoding tail can still remain after the final VAE frame chunk. This PR adds an opt-in H.264 NVENC writer to that overlap path and supports NVENC for eligible videos saved after decoding. CPU encoding remains the default.

## Modifications

- Add `SGLANG_USE_NVENC=1` to opt in to H.264 NVENC output (`False` by default). Query H.264 encoder capability before selecting NVENC, so GPUs without an encoder use the existing CPU path. See NVIDIA's [Video Encode and Decode GPU Support Matrix](https://developer.nvidia.com/video-encode-decode-support-matrix) for supported hardware. `PyNvVideoCodec` is required only when using NVENC.
- Add an MP4 NVENC writer with synchronous and queued-worker modes. Eligible Cosmos3 video outputs, including Nano Sim-Bimanual, use the queued mode: a CUDA event marks each decoded chunk as ready, and the background worker encodes it on a separate CUDA stream while decoding proceeds. If NVENC cannot start, use the CPU overlap writer; if streaming fails later, save after decoding. The synchronous writer mode is available for future model integrations but is not wired into Cosmos3.
- For Cosmos3 video-with-sound requests, encode the video during VAE decoding, then decode the sound tokenizer output and mux it into the MP4 with the existing FFmpeg helper. A GPU without H.264 NVENC keeps the existing CPU video-and-audio path.
- Reuse NVENC sessions within a process. The cache holds one idle session per `(GPU, width, height, FPS, CQ)` configuration, with up to four idle sessions total and eviction of the least recently used idle entry.
- Keep decoded frames for the post-decode fallback, including Sim-Bimanual's pinned CPU copy. Preserve its action output when returning an already-encoded video. Add focused tests for encoder selection, audio muxing, hardware capability, session reuse across resolutions, and both writer modes.

## Accuracy Tests

- Targeted GPU tests passed on an NVIDIA RTX PRO 6000 Blackwell Workstation Edition: Cosmos3 encode/decode `6 passed, 3 subtests passed`; the NVENC audio MP4 timing and validation test `1 passed`. Earlier NVENC tests also passed (`3 passed`). The asynchronous test checks that frame submission returns while the NVENC worker is busy; the synchronous test checks MP4 output and session reuse across resolutions. The Cosmos3 audio test checks stream selection, audio muxing, and the CPU fallback path. In the 90-frame audio sample, CPU video-and-audio saving took 167 ms, while NVENC video encoding plus separate audio muxing took 44 ms (including 25 ms for muxing), all medians.
- On an NVIDIA H100 with PyNvVideoCodec installed, H.264 encoder capability probing reported no NVENC support. The NVENC tests reported `1 passed, 2 skipped`; the Cosmos3 targeted tests reported `5 passed, 4 subtests passed`. A separate H100 probe confirmed that Cosmos3 selects the CPU overlap writer when NVENC is unavailable.
- All 36 measured MP4s and 36 saved-video warmup MP4s decoded as 45-frame H.264 at 24 FPS with the requested dimensions. A complete `save_output=True` warmup populated the session cache before each timed NVENC request; no encoder creation was observed during measurement.
- In the additional-model matrix, all 30 measured MP4s and 30 saved-video warmup MP4s decoded with the expected dimensions and frame counts. Every video-with-sound MP4 had a decodable audio track. All paired measurements used one physical GPU, and no measured NVENC request recreated the encoder session.

**Protocol:** Edge and Nano V2V, 45 output frames at 24 FPS, 35 denoising steps, seed 42. Compare CPU overlap (`SGLANG_USE_NVENC=0`) with NVENC overlap (`SGLANG_USE_NVENC=1`). ### Additional Cosmos3 video modes

The additional measurements use the sample or cookbook resolution for each mode: Edge I2V at 832×480, Nano I2V and Nano video-with-sound at 1280×720, and Nano Sim-Bimanual's 640×352 encoded output from an 832×480 request canvas. The first four modes use 81 frames at 24 FPS and 35 denoising steps. Sim-Bimanual uses the 901-frame, 30 FPS, four-step example. Guardrails are disabled so eligible videos take the streamed path. Each variant has a complete `save_output=True` warmup followed by one measured request in a fresh process; the table reports medians of three paired rounds on one GPU. The CPU path is CPU encode-while-decoding for silent Edge and Nano videos, and the existing CPU save path for video with sound and Sim-Bimanual. The exposed output tail runs from the final VAE GPU activity to completed MP4 saving; for sound requests it includes audio muxing.
