# [Perf] [AMD] glm5_next: Allow Quark MXFP4 shared expert fusion at TP2

[Upstream PR](https://github.com/sgl-project/sglang/pull/46578) · state: open · merged: False

## Original PR description

## Motivation

On HIP, `Glm5NextForConditionalGeneration` fuses the shared expert into the AITER MoE only at TP4 and TP8 (#41161; Quark MXFP4 added in #41870, measured at TP4). At TP2 the shared expert runs as separate MXFP4 GEMMs and is added to the routed output.

This PR admits TP2 for Quark MXFP4 checkpoints. The fused path does not depend on the TP size without expert parallelism:
- The shared expert is loaded into slot 288 and TP-sharded like the routed experts (1024 per rank at TP2).
- The router appends that slot with weight 1.0 for every token.

Scope:
- Models: `Glm5NextForConditionalGeneration` with Quark MXFP4 experts (e.g. `amd/GLM-5.3-Flash-Quark-MXFP4`). Measured: that model at TP2. The NextN draft has its own gate and is not changed.
- Platform: ROCm, AITER on gfx950, TP2 with EP1 and no MoE all-to-all backend, as for TP4/TP8.
- Unchanged: block FP8 (still TP4/TP8), TP1/TP16, CUDA.

Fusion is on by default whenever the gate admits it, so TP2 Quark MXFP4 servers now fuse unless `--disable-shared-experts-fusion` is passed.

## Modifications

- `python/sglang/srt/models/glm5_next.py`: in `shared_experts_fusion_disable_reason`, the HIP TP check accepts TP2, TP4 and TP8 when the quant config is Quark, and TP4 and TP8 otherwise; the refusal message names the TP set that applies. The Quark MXFP4 layout check that follows is unchanged.
- `test/registered/unit/models/test_shared_experts_fusion_gates.py` (CPU): the Quark MXFP4 admission case runs at TP2, TP4 and TP8 (TP2 fails without this change), and a Quark config at TP1 is still refused.

AITER at the pinned commit (`285579b6`) has no tuned MXFP4 fused-MoE rows for GLM-5.3-Flash at TP2, either for the routed-only shape (E=288, top-k 8, inter_dim 1024) or the fused one (E=289, top-k 9). Both run AITER's default configs. This is also the case for MXFP4 at TP4/TP8 today. ROCm/aiter#6435 (merged after the pin) adds tuned rows for both shapes.

## Accuracy Tests

Fusion changes the numerics: the shared expert's activation quantization and its accumulation into the MoE output differ from the separate path, so outputs are not bitwise identical.

- GSM8K (`sgl-eval run gsm8k`, sgl-eval 0.1.3, all 1319 problems, `--num-threads 32 --max-tokens 32768`, temperature 0; server as below with `--context-length 40960`; one launch per arm): baseline 97.19 % (1282), this PR 97.27 % (1283), +0.08 pp; paired by problem, 10 correct only in the baseline and 11 only in this PR. Thinking was on in both arms (about 195 reasoning tokens per answer), so these are not comparable to the non-thinking numbers in the model docs.
- Mean probability of the gold answer letter (P(gold)) over 805 single-image multiple-choice MMMU validation items, thinking off, concurrency 1, two launches per arm, paired by item: baseline 0.6539, this PR 0.6533, drop +0.06 pp (95 % CI −0.67 … +0.79 pp).

**Setup**

  ```bash
    --attention-backend dsa --dsa-prefill-backend tilelang --dsa-decode-backend tilelang \

    --max-running-requests 64 --cuda-graph-backend-decode full --cuda-graph-max-bs-decode 64 \
    --mem-fraction-static 0.92 --model-loader-extra-config '{"enable_multithread_load":true,"num_threads":8}' \
    --trust-remote-code --reasoning-parser glm45 --tool-call-parser glm47 --enable-multimodal \
    --limit-mm-data-per-request '{"image": 1}' \
    --mm-process-config '{"image": {"min_image_tokens": 16, "max_image_tokens": 8000}}' \
    --mm-preprocess-cache-size-mb 0 --mm-enable-dp-encoder --mm-attention-backend aiter_attn
  ```

  ```bash
  python3 -m sglang.benchmark.serving --backend sglang-oai-chat --dataset-name image \
  ```
