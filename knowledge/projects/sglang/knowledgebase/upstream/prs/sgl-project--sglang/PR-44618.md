# [Perf] deepseek_v4: size the masked silu-mul-quant grid to the GPU, not the padded capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/44618) · state: closed · merged: True

## Original PR description

## Motivation

In short: the DeepSeek-V4 masked SiLU-mul-quant kernel runs on every MoE layer of DeepEP low-latency decode, and it launches one CTA for every row the padded DeepEP buffer could hold. At decode almost none of those rows are real, so most CTAs only scan the per-expert counts and exit. On the Flash TP4 shape that is 24,576 CTAs for about 400 real rows, and on H100 the kernel takes 15.9 us even with zero real rows. This PR sizes the grid to the GPU instead: 17.1 -> 3.3 us at 64 decode tokens per GPU, with bit-identical output.

<img width="1754" height="562" alt="pr_overview" src="https://github.com/user-attachments/assets/2097cef0-fdac-4040-99cf-50a84ad364ff" />

Details:

`silu_and_mul_masked_post_quant` (`python/sglang/kernels/jit/csrc/deepseek_v4/silu_and_mul_masked_post_quant.cuh`) runs the SiLU-mul + FP8 quant between the two masked DeepGEMM GEMMs on the DeepEP low-latency path. DeepSeek-V4 takes it on every decode MoE layer because of its `swiglu_limit` (10.0 in the Flash config), through `_varlen_deep_gemm_silu_mul_quant` in `moe_runner/deep_gemm.py`. That covers the DeepEP balanced and high-throughput recipes in the DSV4 cookbook (B200/B300/GB200/GB300 FP4 with `--moe-a2a-backend deepep`, and the H200 FP8 ones).

The input is the DeepEP buffer `[E_local, T, 2D]`, where T is the padded per-expert capacity (`SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK` x ranks) and `masked_m[e]` (on the GPU) says how many rows of expert e are real. The host can't read `masked_m` without a sync, so the kernel launched `T * topk` CTAs, one per possible real row. Every CTA loads `masked_m`, does a block prefix scan with 2 `__syncthreads`, and then all but the CTAs that own a real row exit.

On the Flash B200 TP4 recipe that is `4096 * 6 = 24,576` CTAs per call, for about 400 real rows at 64 decode tokens per GPU. On H100 the kernel costs 15.9 us with zero real rows and 17.1 us at 64 tokens per GPU; almost all of it is empty CTAs going through the scheduler.

## Modifications

In short: launch only as many CTAs as the GPU can hold at once, instead of one per possible row, and let each CTA loop over the real rows. The output is bit-identical to main. On H100 the kernel goes from 15.9 to 1.6 us with no real rows and from 17.1 to 3.3 us at 64 decode tokens per GPU (Flash TP4 shape), and every decode point up to the dispatch cap is faster (1.09x-16.25x). The one slower case is when every one of the `T * topk` rows is real, 2-4%, which uniform routing doesn't get near (details in Speed Tests).

How it works: the host still can't read `masked_m`, so the grid stays fixed, but it is now one resident wave (1,056 CTAs on H100) instead of `T * topk` (24,576 on the Flash TP4 shape). Each CTA prefix-scans `masked_m` once, keeps the result in shared memory, and then takes rows `b, b + grid, b + 2 * grid, ...` of the flattened real-row list. At decode there are fewer real rows than CTAs, so each CTA handles at most one row, exactly like before, just without the other ~23,500 CTAs (24,576 - 1,056) that found no row.

Changes, in simple terms:

- Smaller grid: sized to the GPU, not to the padded capacity.
- One `masked_m` scan per CTA, kept in shared memory, instead of one scan per possible row.
- A loop over real rows in each CTA; the per-row math is the same code as before.
- A new test that checks every real row matches the contig kernel and no padded row is written.

Details:

- Launch `min(SMs x resident CTAs, T * topk)` CTAs instead of `T * topk` (1,056 on H100 at 256 threads; about 1,184 on B200, not measured). Occupancy comes from `cudaOccupancyMaxActiveBlocksPerMultiprocessor`, cached per block size.
- Each CTA scans `masked_m` once into shared memory (`s_row_end`, inclusive prefix, 1 KB), exits before the PDL wait if it has no row, then walks the flattened real rows with a grid stride. A row's expert comes from a binary search over `s_row_end`.
- The per-row body moved verbatim into `silu_mul_quant_varlen_row`, so the math and the output bytes don't change. The PDL wait now runs once before the loop; the trigger stays where it was in the row body.
- `max_rows = T * topk` keeps the old implicit cap (rows past it were never processed before and still aren't).
- New test `test_masked_post_quant_writes_exactly_the_real_rows`: masked vs contig kernel byte-equal on real rows, sentinel untouched on padded rows, for both scale layouts and all-zero / one hot expert / uneven / full `masked_m`. Capacity is 4x the resident CTAs so "full" makes each CTA loop over several rows.

Same idea as vLLM's Silu v2 `persistent_masked_m_silu_mul_quant` ([vllm-project/vllm#25074](https://github.com/vllm-project/vllm/pull/25074)): fixed grid, one scan of the counts per CTA into shared memory, then each CTA walks the real rows.

Not a duplicate: no open PR touches this kernel's grid (searched `silu_and_mul_masked_post_quant`, `masked silu quant`, `silu_mul_quant_varlen`). [sgl-project/sglang#32066](https://github.com/sgl-project/sglang/pull/32066) adds a launch guard on the same launcher lines, so whichever lands second needs a small rebase.

## Accuracy Tests

The output is bit-identical to main, so model accuracy can't change. I checked it at the kernel level instead of with an e2e eval:

- Bitwise vs main, in one process (main's kernel built from the base file under its own namespace), CPU-seeded inputs, outputs pre-filled with a sentinel and compared as whole buffers including padded rows: **464 identical, 0 mismatched**. Matrix: 5 shapes (up to 256 experts, and a `full` case where `sum(masked_m) > T * topk` to check the cap), group size 32 and 128, 3 scale layouts (fp32, UE8M0, transposed packed UE8M0), swizzle on/off, swiglu_limit on/off, 4 `masked_m` patterns.
- `test_per_token_group_quant.py`: 121 passed (8 new). `test_humming_fp8_dispatch.py` (the other caller): 2 passed.
- The new test fails on each of 3 broken mappings (wrong loop stride, `>=` in the binary search, wrong row offset).
- Registers: 32/thread before and after (`__launch_bounds__(1024, 2)` cap), 0 spills.

## Speed Tests and Profiling

H100 80GB HBM3, driver 595.71.05, nvcc 13.2, torch 2.14.1+cu130, triton 3.8.0. Validated on main 97d3150a6a; the branch is rebased onto ed8c3139f1 and neither the kernel nor the test file changed upstream in between. `triton.testing.do_bench_cudagraph` on the op, 2 interleaved rounds (main, PR, main, PR) in one process. Shapes from the DSV4 cookbook DeepEP recipes, group 128, swiglu_limit 10. Real rows come from uniform top-6 routing at the given decode tokens per GPU, up to the dispatch cap; "all real" sets every one of the `T * topk` rows real. On H100 the kernel takes the fp32-scale layout; I didn't have a B200 for the transposed UE8M0 layout.

All numbers are from one H100. The GPU in brackets is the cookbook recipe the shape comes from, not where it ran.

Every decode point up to the dispatch cap is faster (1.09x-16.25x). The one slower regime is "all real", 2-4%: every token on every rank routing all 6 experts to the same rank, which uniform routing doesn't get near. There each CTA loops over about 9-47 rows and pays a binary search per row. A contiguous per-CTA split (search once, then step forward) brings it to 1.00-1.03x but is 2-5% slower at decode and more code, so I kept the stride loop; happy to switch if you'd rather have no regime below 1.0x.

For the Flash B200 TP4 recipe at 64 decode tokens per GPU, the H100 number is 13.8 us saved per call, so about 0.6 ms per decode step over 43 MoE layers. That's arithmetic from the microbench, not an e2e measurement; e2e needs 4x B200 with DeepEP, which I haven't run.
