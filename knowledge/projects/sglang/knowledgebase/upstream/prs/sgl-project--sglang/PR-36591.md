# [Fix] hisparse: state-preserving retraction and recovery for DSV4

[Upstream PR](https://github.com/sgl-project/sglang/pull/36591) · state: open · merged: False

## Original PR description

**Note: the head branch name (`fix/hisparse-cpu-copy-retraction`) predates this rework and no longer matches the approach — the copy-based method was reverted; this PR now implements state-preserving retraction per review feedback.**

## Problem

With PD disaggregation + HiSparse enabled on DSV4, a decode-side retraction (memory pressure) crashes the decode worker:

```
retract_decode -> release_req -> retraction_backup -> get_cpu_copy -> NotImplementedError
```

The upstream retraction path assumes it can bulk-copy the full KV from GPU to CPU and back on resume. That assumption is wrong for HiSparse in two ways: the op is unimplemented for the HiSparse pool, and the copy itself is unnecessary — HiSparse already maintains a host copy of every committed C4 KV token.

## Approach (per review feedback)

Reworked per @huangtingwei9988's guidance: no full GPU<->CPU KV copy; preserve and restore the request's state instead.

**Retraction (`retract_req_state_preserving`)**
- Device buffer indices and full->device mappings are released.
- The `req_to_host_pool` row (HiSparse's own offloaded copy — which IS the backup) and its `req_to_token` row are kept, keyed by the unchanged `req_pool_idx`.
- Two small sidecars are captured for state HiSparse does NOT offload (both live in device logical-slot space, so a resume's fresh slots would read garbage):
  - **indexer K** — the DSA top-k selection data (~136B/token)
  - **SWA window** — the live ~window_size-token window only

**Resume (`resume_after_retraction`)**
- Fresh logical slots via the normal pre-alloc path; all-miss device buffer, top-k swap-in from host on demand (HiSparse-aware recovery).
- Sidecars restored into the fresh slots' pages before the first forward.

**Abort path** (`discard_retracted_request`): frees the retained host row, the kept `req_to_token` row, and the sidecars — no leaks.

## Verification (DSV4-Flash-0731, 1 node, H100x8, PD + mooncake)

| tree | retraction | output vs control |
|------|-----------|-------------------|
| PR base | crash: `NotImplementedError`, 3/4 in-flight requests lost | — |
| this fix | 228 real retractions, 0 exceptions | **4/4 token-identical** |

Determinism controls: 4/4 self-consistent across repeated no-retraction runs (greedy, fixed seeds, text prompts).

Topology note: the pod run used greedy decoding, so speculative decoding was OFF. Commit 9 covers the spec-on edge (a verify reservation can leave `kv_allocated_len` past the committed length; the sidecars now back up committed pages only, so the restore's page-count invariant holds by construction). A spec-on retract/resume arm on the pushed head is the recommended follow-up validation.

## Design question for maintainers

The two sidecars are small one-shot retraction-time copies (together ~25% of the affected request's C4 KV bytes), but they are GPU->CPU copies nonetheless. Alternatives considered:
- re-transfer from prefill on resume: heavier, keeps prefill coupled to decode's retraction policy
- keep the original logical slots alive: changes allocator semantics under exactly the memory pressure that triggered the retraction

Happy to switch the sidecars to an eager per-step backup (extending `_eager_backup_previous_token`) if maintainers prefer HiSparse to own the offloading of the indexer K / SWA end-to-end, at the cost of extra per-step backup traffic.
