## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Wide constrained beam search for generative retrieval materializes large vocabulary logits and repeatedly reads the same prompt KV for every beam. Add model-native trie constraints, compact semantic-ID (SID) output projection, and optional shared-context attention, with beam width selected independently for each request.

The implementation is based directly on upstream `main`, without release-branch backports or unrelated input-handling changes.

## Modifications

<!-- Detail the changes made in this pull request. -->

- Discover and validate an optional model-bundled `trie_output_head.safetensors` artifact containing a three-codebook SID trie. Support dense or sparse valid-child masks, on-device prefix state, and constrained joint beam selection.
- Project active SID codebooks instead of materializing full-vocabulary decode logits on compatible CUDA/TP=1, unquantized, non-LoRA configurations. Preserve full-vocabulary normalization by default; `SGLANG_OPT_BEAM_TRIE_TOPK_LOGPROB=true` explicitly opts into approximate candidate-only normalization, which can change rankings.
- Add opt-in `SGLANG_ENABLE_BEAM_SHARED_CONTEXT_ATTENTION=true` for FlashInfer MHA with FP16/BF16 KV. Bucket groups by their request-specific widths and share prompt attention work while retaining per-beam decode suffixes. Unsupported backend/cache configurations use standard attention; attention logit caps are rejected on the shared-context path.
- Account for beam decode headroom at admission and retain histories on-device for fixed-length SID decoding. Separate native trie CUDA-graph variants from ordinary captures and replay trie/shared-context graphs with freshly staged metadata.
- Preserve speculative CUDA-graph runner compatibility with an inherited non-trie capture default and beam-only preparation keywords only for actual trie captures.
- Add CPU and CUDA-registered correctness tests, with documentation for the artifact schema, supported configurations, approximation semantics, and per-request beam widths in `python/sglang/srt/beam_search/README.md`. Benchmark and profiling utilities, model bundles, prompt corpora, valid-SID indexes, raw results, and profiles are outside this PR.

### Primary capacity result: 1.67x at the same p95 latency limit

For **configuration B**, with **beam width 2,000**, **3 output tokens per sequence**, and **client concurrency cap 10**, Trie-Head increases the highest passing tested offered load from **6 to 10 QPS** under the same **p95 <=1,200 ms** criterion.

| CLP | 6 | 5.978 | 967.95 |

**Capacity gain at the fixed latency limit: 10 / 6 = 1.67x (+66.7%).** Both paths meet the same latency criterion at their respective loads. The open-loop boundary table below includes the next tested loads that fail the criterion.

The fixed-concurrency tables answer a different question: at concurrency 8, configuration B completes **8.142 QPS with CLP versus 11.094 QPS with Trie-Head (1.36x)**. This is throughput at equal concurrency; **1.67x is the capacity improvement under the latency limit**.

The workspace resize is dropped, since it only served 20k-row trie decode graphs (59fe6636e6).

- **Trie decode graph variant**: trie and shared-context batches run eagerly, which removes the capture kwargs shim and the extra `ShapeKey` field (0e91bff157).
- **Hub lookup on every model start**: the trie head loads only when `config.json` sets `"beam_trie_output_head": true`, through `cached_file`; a declared but missing artifact now fails startup instead of silently dropping the constraint (2e20e9605a).
- `BeamCoordinator` loads the trie itself, so `scheduler.py` is back to main (455831aa74).
- The trie and shared-context forward-batch fields are built in the beam modules; `ForwardBatch.init_new` makes two calls (6a3b3886bf).
- The Triton kernels move to `sglang.kernels.ops` (`attention.beam_shared_context`, `gemm.codebook_projection`, `grammar.trie_mask`) with their tests (881da8d2a5).

Verified on one H200 with a synthetic Qwen3-0.6B + 3x8192 SID model and a 1M-item trie, beam width 1000 and 2000: ordered beams match the previous head at concurrency 1 in eager, graph, shared-context, and mixed-width runs; the differences at concurrency 4-10 are within the previous head's own run-to-run variance; ordinary beam search matches main. Throughput is equal or higher, and peak memory is about 20 GB lower in graph mode.

Model bundles need `"beam_trie_output_head": true` in `config.json`.
