# [Fix] kimi-k3: mark the shared-expert output on its producing stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/45817) · state: open · merged: False

## Original PR description

## Motivation

Kimi-K3's tp1 shared-expert output is allocated from the symmetric-memory pool on the MoE side stream, and `wait_and_finalize_shared_experts` marks its lifetime on the **forward** stream with `shared_output.record_stream(current_stream)`. A block marked that way returns to the side stream's free list only after the forward stream passes the consumer, and that consumer sits behind this layer's routed kernel. A rank whose forward stream lags therefore cannot reuse the block and grows the pool by one segment while the other ranks reuse theirs. The next registration round then runs on some ranks only: those ranks block in `ncclCommWindowRegister`, which is a collective that requires every rank in the group, while the others launch the MegaMoE kernel and park in its cross-rank barrier. Neither side can finish, and the engine hangs until the barrier timeout fires (#36943).

DeepSeek-V4 already handles this same tensor the other way: it marks it on `self.alt_stream`, the stream that produced it, so reuse is ordered by that stream's own sequence and cannot differ across ranks. This PR makes Kimi-K3 do the same for the same case, instead of introducing a new rule.

### Why this is safe

The side stream never runs ahead of the forward stream: every layer's side-stream work starts after `self.alt_stream.wait_stream(current_stream)` (`kimi_k3.py:1131` and `:1161`), and the layer's tail add is the only reader. The block therefore cannot be reused for layer N+1 before the forward stream has executed that read at layer N.

### Relationship to #44976

Both PRs remove the same deadlock and differ in where they cut:

- #44976 takes the tensor out of the symmetric pool, so the failure mode disappears at its source; it comes with unit tests and start-level A/B data.
- This PR keeps the allocation and makes the reuse decision deterministic again, matching DeepSeek-V4.

## Modifications

`wait_and_finalize_shared_experts` keeps the replicated output's lifetime on the stream that produced it:

```python
if self._sbo_shared_overlap and self._shared_experts_tp1 and not fine_grained_overlap:
    shared_output.record_stream(self.alt_stream)
else:
    shared_output.record_stream(current_stream)
```

Of the three conditions, `_shared_experts_tp1` is the substantive one: that output is complete per rank and enters no collective. `_sbo_shared_overlap` and `not fine_grained_overlap` only assert that this path really runs on the side stream.

Every other path keeps the current marking, including TP-sharded shared experts, whose output is reduce-scattered on the forward stream.

## Risk

- The safety argument rests on the per-layer `wait_stream` join named above. If a later path allocates on `alt_stream` without that join, the block could be reused while the forward stream still reads it, producing wrong values with no error. The comment in the code points at the invariant.
- Dropping the forward-stream marking also drops the implicit "do not reuse until this layer's routed kernel finishes" ordering. Nothing in this path relies on it, but that is the part worth reviewing closely.
- Not validated at runtime: the deterministic trigger used for #44976 pins blocks regardless of the marking, so it cannot separate this change from the baseline. This is why #44976 is the primary PR and this one is offered as the alternative direction.

## Verification

- Code-level: on every layer the reuse point is ordered after the join at `kimi_k3.py:1131` and `:1161`, and no other allocation takes this block.
- Not verified at start level: no A/B separates this change from the unmodified baseline (see Risk). The reproduction and the measurements for the underlying stall are in #36943 and #44976.
- No unit test added: the change is a stream-lifetime choice, and a CPU test cannot observe stream ordering.
