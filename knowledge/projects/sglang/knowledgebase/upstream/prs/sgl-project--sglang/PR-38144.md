# fix(jit-kernel): exact fallback for fast_topk threshold-bin overflow (#36807)

[Upstream PR](https://github.com/sgl-project/sglang/pull/38144) · state: open · merged: False

## Original PR description

## Motivation

`radix_select_topk` in `fast_topk.cuh` treats "at most SMEM_INPUT_SIZE candidates in the threshold bin" as a correctness assumption. The coarse fp16 binning (~2 mantissa bits per bin) lets a concentrated row place far more candidates in one bin — 16K at L=30,938 and 34K at L=65,504 for QSA k=512 (reported in #36807 by @mochgolf). Overflowing candidates are dropped *together with* their fused histogram contributions, so the staged subset no longer represents the threshold-bin population and refinement silently selects from a truncated set: wrong top-k, run-to-run unstable, and no error is surfaced since the output still looks like exactly-k valid indices.

## Fix

Keep the fast path unchanged. Detect the overflow (`s_num_input[0] > SMEM_INPUT_SIZE`), then refine by rescanning the full row, filtering candidates by the coarse bin plus the refined radix digits selected in previous rounds (`s_prefix_bins`). No API change, no smem layout change, CUDA-graph / PDL safe.

The coarse-stage threshold selection itself stays exact: it runs on the full first-pass histogram *before* any staging truncation, and kTopK (512/2048) < SMEM_INPUT_SIZE (4096) makes a post-truncation boundary unreachable.

## Tests

- New regression `test_fast_topk_regression.py` (registered CUDA CI): concentrated rows at L=30,938 / 65,504 x k in {512, 2048} **fail on the unpatched source** (8 failed / 2 passed — wrong rows and unstable selections) and **pass with the fix** (10 passed); non-overflow N(0,1) controls unchanged.
  - **Update (09-28)**: the regression matrix has since been expanded to 33 cases — unpatched 8 failed / 25 passed, with the fix 33 passed / 0 failed (details in the 09-21 comment below).
- Existing `test_fast_topk.py`: 23 passed (no regression).
- End-to-end smoke on 8x A800 (SM80), TP8, Qwen3.8-Flash-Next: health 200, CUDA-graph capture (32 batch sizes) + replay OK, and a 42K-token long-context request answered correctly through the QSA `fast_topk` path (needle retrieval at the compressed attention layer).

## Performance

No measurable regression on non-overflow inputs (kernel micro-benchmark medians within run-to-run noise).

## Notes

- Complements #37786 (padded-extend-plan OOB); different root cause, different path.
- `fast_topk.cuh` now lives on main (imported by `python/sglang/srt/layers/attention/qsa/kernel.py` and `qsa_indexer.py`), so this patch applies directly to `main` with no stacking. Note that main's copy is still the unfixed one — the staging-overflow path this PR guards is live on main today.

- nabe2030 · comment · 2026-10-03T15:46:22Z · [source](https://github.com/sgl-project/sglang/pull/38144#issuecomment-5970725287)

**GB10 (DGX Spark, SM121) verification of #38144: the k=512 overflow is real on a real Flash-Next workload, and the patch removes it.**

Independent verification from a different architecture, in case it helps: the PR has SM80 (A800) evidence from the author, this is SM121 (GB10) from someone unrelated to the PR.

**Setup.** DGX Spark (GB10, SM121), Qwen3.8-Flash-Next (senfu NVFP4), SGLang fork `4fb9b5b5ba` (2026-09-17) with only the kernel hunk of #38144 applied to `python/sglang/kernels/jit/csrc/elementwise/fast_topk.cuh`. The file in our fork matched the PR's base blob (`b30f4636c819`) and the patched file is blob-identical to the PR head (`851244a87954`). QSA indexer, `kTopK=512` (`indexer_budget 2048 / compress_ratio 4`), chunked prefill 1024, one request at a time. #37893 was not applied (it touches the AOT `topk.cu` and `kpool_topk_transform.cuh`, not this file).

**1. Regression conditions** (standalone port of the PR's test, no pytest; value-multiset comparison against `torch.topk`, same semantics as `_check_topk_values`). 23 cases: concentrated `10.0 + 0.1*N(0,1)` at L=30,938 / 65,504 for k=512 and 2048, 5-run stability, N(0,1) controls, plus decode-shaped `uniform(1.0,1.2)` (B=1/2, L=8,000–95,000), mixed `row_starts`/lengths, and short/boundary rows (L=84…2048).

- Unpatched: **17 of 23 fail** (all concentrated cases, all stability cases, all decode-shaped uniform cases, the row_starts case); controls and short rows pass.
- Patched: **0 of 23 fail.**

**2. Real indexer scores before/after** (observation-only wrapper around `fast_topk`, returning the kernel's own output unchanged; sampled rows compared with `torch.topk`; "wrong" = selected entry strictly below the true k-th value). Inputs: real source-code prompts of 20K–380K tokens (L = compressed blocks = tokens/4, up to ~95K).

- Unpatched (66,537 sampled rows): 0 wrong rows for L ≤ 16K blocks (~22,000 rows); for L > 32K blocks, **prefill 84 / 12,112 rows (0.7%) and decode 114 / 19,569 rows (0.6%)**, up to 84 of 512 entries wrong in a row; threshold bin up to 7,307 entries (> 4096). In a second run that also recorded ranks (26 wrong rows) the best missed rank was 297 at minimum, 443 median, none within the top 256.
- Patched (28,230 sampled rows, 25,254 with L > 16K blocks): **0 wrong rows**, 0 hook errors. 146 rows had a threshold bin above 4096 (max 7,244) — the kind that is wrong without the patch — and all were selected exactly. At the unpatched rate (0.31%) about 86 wrong rows would have been expected.
- Needle retrieval in the final answer at 100K / 150K / 256K / 380K tokens: 1/1, 1/1, 2/2, 3/3 (patched). I did not find an output difference attributable to the missed entries before the patch either (needle retrieval was also correct unpatched), so I cannot claim a visible quality effect — only that the selection is now exact.

**3. CUDA graph.** The wrapper cannot observe graph-replayed decode, so I tested the patched kernel separately: capture once, then replay with changed buffer contents and lengths (B=1/2, overflowing and non-overflowing rows, 18 rows): 0 inexact rows. The server also ran with CUDA graphs enabled in production for 256K/380K needle requests without errors.

**4. Speed.**

- Kernel micro-benchmark (medians, patched → unpatched → patched, same script): non-overflow shapes within noise (e.g. B=1 L=36,000: 18.5 µs both; B=1024 L=32,000: 637–644 µs vs 644 µs); an overflowing row (L=65,504, concentrated) goes 31.9 → 108.7 µs (the exact fallback), which is the cost of being correct.
- End to end (same scripts, unpatched vs patched server): 14-turn growing conversation (70K) 117.9 s vs 114.4 s; prefill-only 93K: 53.9 s vs 54.5 s (3 runs within 0.2%), 260K: 170.2 s vs 170–172 s, 379K: 269.9 s vs 271–273 s (≈ +1%, 1–3 runs per condition). One slower patched measurement right after server start (the first long prompts after startup were ~20–28% slower) was also seen on the unpatched server and disappears on repeat, so I attribute it to start-up, not to the patch.

**Not covered:** the AOT `topk.cu`, k=2048 on a real model path (QSA uses 512; k=2048 only in the synthetic regression cases), content other than concatenated Python source, and the observation wrapper sampled rows (≤ 8 per call; 1 in 8 prefill calls, 1 in 4 decode calls).

For what it is worth, this reproduced and fixed a real failure on hardware the author does not have, so the fix does not look SM80-specific. The kernel blob I tested (`851244a879`) is still the current head here, so these numbers apply to the branch as it stands.
