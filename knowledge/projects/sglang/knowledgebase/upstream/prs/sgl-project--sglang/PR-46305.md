# [Fix] step3: Keep tool-call parameter values that contain '<'

## Motivation

`Step3Detector` (`--tool-call-parser step3`) silently drops every tool-call parameter whose value contains `<`, in both `detect_and_parse` and `parse_streaming_increment`. The value group of `param_regex` is `([^<]*)`. It stops at the first `<`, so the closing `</steptml:parameter>` is never reached, `finditer` yields no match, and the parameter is missing from the arguments with no warning:

```
<steptml:parameter name="content">x = 1
if x < 2:
    print(x)</steptml:parameter><steptml:parameter name="path">main.py</steptml:parameter>
```

parses to `{"path": "main.py"}`. Step3's chat template writes values raw (`'<steptml:parameter name="' + name + '">' + param | string + '</steptml:parameter>'`), so code, comparisons and HTML in a value are ordinary output. `re.DOTALL` is already on the pattern but has no effect with `[^<]`.

This carries forward #31547 (@sohumt123), which made the same regex change but was closed by the stale bot without a review. Unlike that PR, this one also bounds the scan, explained below.

## Modifications

`python/sglang/srt/function_call/step3_detector.py`:

- `param_regex` now matches the value lazily up to the closing tag: `(.*?)</steptml:parameter>`, with the existing `re.DOTALL`.
- New helper `_find_complete_params()` runs `finditer` only up to the end of the last `</steptml:parameter>`. Both call sites (one-shot and streaming) use it. Every match ends at a closing tag, so the matches are identical. Without the bound, the lazy group scans from each opening tag that has no closing tag yet to the end of the text. Streaming re-runs the scan on the whole buffer for every chunk, so this cost grows with (open tags) × (buffer length).

Time for the full parse (Python 3.12, CPU). "One-liner" is the regex change without the bound:

| mode | input | main | one-liner | this PR |
|---|---|---|---|---|
| stream, 4-char chunks | 20 KB code value with `<` | 0.082 s | 0.668 s | 0.055 s |
| stream, 4-char chunks | 16 KB value containing 200 literal `<steptml:parameter name="x">` | 0.249 s | 23.193 s | 0.045 s |
| stream, 4-char chunks | 8 KB of unclosed opening tags (malformed) | 0.047 s | 7.520 s | 0.016 s |
| one-shot | 200 KB of unclosed opening tags, no closing tag | 0.006 s | 7.012 s | 0.005 s |

The parsed arguments of this PR and the one-liner were compared over 23 inputs (well-formed and malformed) at every chunk size and on random splits, 11,060 chunkings in total, with 0 differences.

Behaviour change on malformed output: when a parameter is never closed and a closed parameter follows it, the two now merge into the first value. Before, the unclosed one was dropped and the next one kept. Well-formed output is not affected.

Other step3 issues (streaming chunk boundaries, parameterless calls) are handled by open PRs #34925, #35625, #36695 and #41909. None of them changes `param_regex`, and this PR leaves those code paths alone. It merges cleanly with each of them.

`test/registered/unit/function_call/test_function_call_parser.py`: adds `TestStep3Detector` with two regression tests, one for each call site:

- `detect_and_parse`: a multiline value containing `<`, followed by another parameter.
- `parse_streaming_increment` in 6-character chunks: a multiline HTML value, followed by another parameter.

Both fail on main, where `content` is missing, and pass with this change. They also fail if the group is greedy, if `re.DOTALL` is dropped, or if the bound cuts at the wrong position.
