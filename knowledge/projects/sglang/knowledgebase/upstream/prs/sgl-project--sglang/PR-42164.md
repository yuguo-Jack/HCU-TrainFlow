# [DSA] Read the MQA logits budget once per forward batch in the k-pool indexer

[Upstream PR](https://github.com/sgl-project/sglang/pull/42164) · state: open · merged: False

## Original PR description

## Motivation

The k-pool DSA indexer now reads the MQA logits budget once per forward batch and device. On `main`, every sparse-attention layer of a prefill forward reads it. The budget still follows free memory from one forward to the next. Model outputs do not change.

For a logits matrix at or above `MQA_LOGITS_STATIC_SKIP_ELEMS`, each read calls `torch.cuda.mem_get_info`. #40854 added this read, and its review discussed a cache ([first comment](https://github.com/sgl-project/sglang/pull/40854#discussion_r4092665319), [measurement](https://github.com/sgl-project/sglang/pull/40854#discussion_r4109685960)). This pull request follows that review:

- The review measured a budget kept per device for the process lifetime and declined it. The budget stayed at its first value while free memory fell, and the allocator needed out-of-memory retries. The first revision of this pull request (commit c6a62e1a88) had that design. This revision does not use a reading for a later forward batch.
- The review found that the layers of one forward saw the same budget in almost every forward. So one reading per forward gives the same chunk plan as one reading per layer in almost every forward. The first comment also named one reading per forward batch as an option.
- The review measured the call with nsys on GB300. I read its setup as eager prefill, because the review names no prefill graph flag. The call was short and did not wait for queued GPU work. So this pull request does not claim that the call syncs the host, and it does not claim a gain in eager prefill.

I still propose the change for one case. With the breakable prefill graph on B200, I measured a gain in two cases, and neither case isolates this exact code. The first case is the first revision alone. The second case is a backport of this revision together with a second fix. See "Speed Tests and Profiling".

## Modifications

- `dsa_indexer_kpool.py`: `_get_mqa_logits_budget_bytes` keeps the last reading per device together with a weak reference to its `ForwardBatch`. A call with another batch reads free memory again. `_mqa_logits_row_chunks` takes `forward_batch`, and both callers pass it. The early return under graph capture is unchanged.
- Breakable-graph replay needs no change. `PrefillCudaGraphRunner.load_batch` builds a new `ForwardBatch` for each replay, so each forward reads again in its eager breaks.
- `test_kpool_stream_scheduling.py`: two tests replace the test of the first revision. One forward batch reads the budget once per device. The next forward batch reads again and plans more chunks after a lower reading.

The non-pooled DSA indexer keeps its budget per device for the process lifetime (#25299). This pull request does not change it.

## Expected improvement and risk

| Change | Expected improvement | Risk | What limits or turns it off |
|---|---|---|---|
| One budget reading per forward batch and device in the k-pool indexer | Prefill only. I did not measure the isolated effect with this exact code, so this row gives no number. A prefill forward over the skip threshold makes one `mem_get_info` call per device in place of one call per sparse-attention layer. The only gain I measured for this scope is with the breakable prefill graph on B200, for this change together with a second fix (see "Speed Tests and Profiling"). In eager prefill, the review of #40854 found no measurable cost of the calls, so expect no gain there. | Low. Outputs: each query row is scored independently, so the chunk plan cannot change a score. Memory: the later layers of one forward use the reading of the first layer. If free memory falls inside one forward, a later layer can plan a larger chunk than a new reading allows. A reading never serves a later forward batch. | Only the ragged prefill path reaches this code, and only for a logits matrix at or above `MQA_LOGITS_STATIC_SKIP_ELEMS`. Decode does not reach it. Graph capture returns before the read. The change has no switch. `SGLANG_DSA_MQA_LOGITS_FREE_MEM_FRACTION` still sets the share of free memory that the budget can use. |

## Speed Tests and Profiling

I have not measured this revision on a GPU, so this section has no speed result for it.

The first revision of this body had a latency table and a py-spy percentage. I removed both. The table measured the process-lifetime cache, which this revision does not have. I could not check the percentage against a saved run log.

Related measurement, not a result of this pull request. My benchmark stack on v0.5.20 carries a backport of this change with the same scope of one forward batch. It also carries a fix that reads the token count once per forward batch, which v0.5.21 already has. One run removed both fixes at the same time. I compared it with three reference runs.

- Setup: an FP8 GLM-5.3-Flash checkpoint, TP4 on 4 B200, breakable prefill graph on, whole replayed sessions of an agent workload at temperature 1.0 and top-p 0.95.
- 16 sessions in flight: engine time per output token was 6.57 ms without both fixes, against 6.12 to 6.16 ms with them. That is about 6.9% more than the mean of two of the reference runs (6.16 and 6.12 ms). Median time to first token was 0.31 s against 0.24 to 0.25 s.
- 4 sessions in flight: engine time per output token was 3.52 ms against 3.38 to 3.44 ms. That is about 3.7% more than the mean of two of the reference runs (3.38 and 3.40 ms). Median time to first token was 0.24 s against 0.20 s.
- A difference under about 1.5% is noise in this benchmark.

I cannot split these numbers between the two fixes. `main` already has the token-count fix, so the share of this pull request can be much smaller, and it can be zero.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Retain budget entries for both TBO children**

When `--enable-two-batch-overlap` is used with a k-pool DSA prefill whose child logits exceed the budget-check threshold, this single per-device slot is overwritten on every child switch. `execute_overlapped_operations` runs child A then child B for each stage (`python/sglang/srt/batch_overlap/operations.py:63-65`), while the DeepSeek prefill strategy yields within every layer (`python/sglang/srt/batch_overlap/operations_strategy.py:113-125`), and each child has its own `ForwardBatch`; consequently A's entry is replaced by B before A reaches the next sparse layer, and vice versa. This path therefore still calls `mem_get_info` once per sparse layer per child, so the cache needs to retain both live `(device, batch)` entries.
