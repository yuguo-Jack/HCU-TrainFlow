# [gRPC] Forward caller mm_hashes and advertise multimodal inputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43886) · state: open · merged: False

## Original PR description

## Motivation

This PR is stacked on #42833, which adds image, video and audio fields to the `runtime.v1` `GenerateRequest`. Please review the last three commits. A tokens-in client, such as an external KV-aware router, needs three more things to use them safely. It must send its own image hashes, so that its cache key and the SGLang prefix cache agree. It must know which media the server reads, because an older server, a text-only model, or a processor without a modality's placeholder ignores that media with no error. And `n > 1` must work with more than one media item. `GenerateReqInput` turns a single `n > 1` request into a batch of one prompt and wraps `text` and `input_ids`, but not the media lists, so each flat list is read as one entry per sample. Two images fail the batch size check, and two videos keep only the first. This also breaks OpenAI chat today (#5954).

## Modifications

- `GenerateReqInput` wraps a single request's flat `image_data`, `video_data`, `audio_data`, `mm_hashes` and `mm_content_hashes` when `n > 1` turns it into a batch. Lists that are already nested keep their shape. The gRPC bridge sends flat lists.
- New `GenerateRequest.mm_hashes`, forwarded to `GenerateReqInput.mm_hashes`. It takes one hex hash per image in an image-only request. Any other shape, or a hash that is not hex, gets `INVALID_ARGUMENT`. Mixed requests are rejected because `TokenizerManager` pairs hashes with all media items, while `GenerateReqInput` counts them against images when `n > 1`.
- `GetServerInfo` returns `grpc_features` with `image_inputs`, `video_inputs` and `audio_inputs` for each modality whose placeholder token the processor has. A processor without placeholder tokens lists none.

Caller hashes need #41375 to work end to end. Without it, the first request with caller hashes crashes the scheduler. HTTP `/generate` has the same crash today (by code read).

## Accuracy Tests

`Qwen/Qwen3-VL-2B-Instruct` over `--grpc-port` and HTTP. The gRPC client sends chat-template token ids with one unexpanded placeholder per item, plus the media. Image A has a red circle and a blue square. Image B has a green triangle. The middle column is the first commit of this PR, which nested the media lists in the bridge instead.

| Request | earlier head | this PR |
|---|---|---|
| `grpc_features` | `["multimodal_inputs"]` | `["image_inputs", "video_inputs"]` |
| OpenAI chat, images A and B, `n = 2` | 400: length of `image_data` should equal the batch size | both choices describe both images (630 prompt tokens, same as `n = 1`) |
| OpenAI chat, two videos, `n = 2` | 500: error while loading multimodal data | 719 prompt tokens, same as `n = 1` |
| gRPC, images A and B, or two videos, `n = 2` | works | works |
| gRPC hash `zz` | 200, hash ignored with a warning | `INVALID_ARGUMENT` |
| two hashes for one image, or a hash with a video | `INVALID_ARGUMENT` | `INVALID_ARGUMENT` |
| image A twice, same hash, with #41375 | cached_tokens 0, then 320, correct answer | not changed |
| image B with image A's hash, with #41375 | cached_tokens 320, the answer describes image A | not changed |

The last row shows that the caller hash becomes the image's cache identity, so callers must send a hash of the image bytes. Audio sent to this vision-only model still gets an answer that ignores the audio, which is why clients must check `audio_inputs` first.

Unit tests: `cargo test -p sglang-grpc` 20 passed. `test_io_struct.py` (`TestGenerateReqInputNormalization`), `test_grpc_bridge.py` and `test_mm_hashes.py` pass. The new `n > 1` media test fails without the `GenerateReqInput` change.
