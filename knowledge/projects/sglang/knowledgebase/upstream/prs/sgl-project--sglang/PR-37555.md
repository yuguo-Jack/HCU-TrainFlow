# fix(gateway): don't register a worker with no model identity under IGW

[Upstream PR](https://github.com/sgl-project/sglang/pull/37555) · state: closed · merged: False

## Original PR description

Fixes #37554.

## Motivation

Under IGW, a worker whose metadata discovery failed is registered as `model_id: "unknown"`, stays healthy, takes no traffic for the life of the router process, and is never corrected.

Kubernetes service discovery submits an `AddWorker` as soon as a pod has an IP, which is before a starting engine can answer `/model_info` or `/server_info`. `discover_metadata` is `FailureAction::ContinueNextStep`, so that worker still reaches `create_worker`, which falls back to `UNKNOWN_MODEL_ID` and registers it.

Under IGW that worker is unreachable: `select_pd_pair` and the regular router both narrow candidates with `worker_registry.get_by_model(model_id)`, so `"unknown"` is never a candidate for any named model. It is also never corrected — the service-discovery resync only re-submits pods for which no worker is registered at all, and this one is registered, while `tracked_pods` deduplicates the later watch events. `--service-discovery` enables IGW automatically, so every discovery-driven deployment is in that mode.

The visible result is a router serving on a fraction of its fleet with every pod `Ready`, `/workers` reporting `is_healthy: true`, and no log line saying a metadata call failed. We hit this in production after an engine rollout: routing to roughly 40% of the workers for hours, cleared by a router restart.

This path became reachable when `ContinueNextStep` started being honoured (#37249, wfaas 1.0.2). Before that the workflow deadlocked at `discover_metadata` instead, which lost the worker too but did so visibly and left the resync able to recover it.

## Modifications

**`create_worker.rs` — refuse, when and only when IGW is on.** An unregistered pod is the one state the resync retries, so the worker is picked up with its real `model_id` as soon as it answers. Outside IGW the model filter is off and an unnamed worker still serves, so the `UNKNOWN_MODEL_ID` fallback stays for backends that expose no metadata endpoints (the case #25293 addressed). The error names its cause, so a failed `AddWorker` is readable.

**`discover_metadata.rs` — log each failed metadata call.** The step keeps swallowing its HTTP errors: it is optional by design, and making it fail would burn its 3 × 10 s of retries before reaching the check above without changing the outcome. What was missing was any record that the call failed, which is why the incident was invisible.

**Tests** — two, over the real `CreateLocalWorkerStep` rather than a stand-in, one per IGW mode. No network: empty `discovered_labels` is exactly what a failed discovery leaves behind.

- Juhyun-Kim-Memphis · comment · 2026-09-02T07:03:10Z · [source](https://github.com/sgl-project/sglang/pull/37555#issuecomment-5505792558)

Converting this to draft: I overstated the recovery path, and on `main` as it stands this change would trade one failure for another rather than fixing it.

The PR argues that refusing the registration is safe because "an unregistered pod is the one state the resync retries". That is true of a deployment carrying #32322, which is where I measured it. It is **not** true of `main` today:

- there is no `--service-discovery-resync-secs` flag and no periodic reconcile — `service_discovery.rs` has no `reconcile_from_list` equivalent;
- the pod is inserted into `tracked_pods` before the `AddWorker` job runs, and a later watch event for the same pod is dropped as a duplicate (`service_discovery.rs:547`);
- `tracked_pods.remove(...)` happens only when *submitting* the job fails, not when the job itself fails.

So on `main` a refused `AddWorker` leaves the pod tracked and unregistered with nothing to re-submit it, which is a worker lost until the router restarts — the same end state as the `"unknown"` registration this PR removes, minus the registry entry. The bug in #37554 is real either way, but this patch alone does not fix it here.

Two ways forward, and I would rather a maintainer chose than guess:

1. **Take #32322 first** (open since July, mergeable). It adds the periodic full LIST reconcile that makes an unregistered pod recoverable; this PR then does what it claims, and I will rebase and undraft it.
2. **Make this PR self-contained** by adding the missing retry path to the add path itself — untrack the pod when the `AddWorker` job fails, so the next watch event re-submits it — instead of relying on a reconcile. That is a larger change to this PR and overlaps #32322's territory, so I did not do it unilaterally.

Either way #37554 stands as a bug report; the fix is what needs sequencing. Sorry for the noise.


- Juhyun-Kim-Memphis · comment · 2026-09-02T07:35:23Z · [source](https://github.com/sgl-project/sglang/pull/37555#issuecomment-5506130966)

Following up on the above: I am taking option 1 — this stays in draft until #32322 merges, then I rebase and undraft it. Two corrections and one piece of evidence.

**Option 2 as I described it does not work.** Untracking the pod when the `AddWorker` job fails gives it nothing to re-submit it: `handle_pod_event` only adds a pod that `is_healthy()`, and a pod that was already `Ready` when the job failed produces no further watch event. Untracking alone would need its own retry loop next to it — that is #32322's reconcile, reimplemented worse. So there is no self-contained version of this patch that does not duplicate #32322.

**#32322's red CI is `main`'s, not that PR's.** `PR Test (SMG)` fails the same four jobs on `main`, three of them at *Install SGLang dependencies* where the editable install cannot link libtorch while compiling `sglang-radix-tree`; it has failed that way on every `main` run since 9cf157c25 (#32710, 2026-08-31). Details and run links: https://github.com/sgl-project/sglang/pull/32322#issuecomment-5506125468.

**The change measured on a deployment that carries #32322.** Two stub workers with `/model_info` and `/server_info` hanging from boot, unhung by hand, same flags and same stubs in both arms:

| | without this change | with it |
| -- | -- | -- |
| while metadata hangs | 2 workers, both `model_id: "unknown"`, both healthy | 0 workers — `create_worker` refuses, and says why |
| once the workers answer | still `"unknown"` over the 2 min 34 s observed | registered as their real model within 18 s |

The 18 s is one `--service-discovery-resync-secs 10` tick plus the `AddWorker` that follows it, which is exactly the recovery path this PR needs and `main` does not have.
