# [AMD][gfx950] Restore fused block-scale FP8 projection paths and fix the MHA_ONE_SHOT KV reload

[Upstream PR](https://github.com/sgl-project/sglang/pull/39409) · state: open · merged: False

## Original PR description

## Motivation

**On MI350/MI355 (gfx950), DeepSeek-V3.2 FP8 runs its attention projections on a slower fallback path. This PR puts them back on AMD's faster fused FP8 kernels, and fixes a latent crash that switching them on would otherwise expose.**

**Expected gain: small but consistent, concentrated in short-prompt, long-reply traffic at low concurrency** — the shape typical of chatbot and coding-agent use. On DeepSeek-V3.2 at TP4 with a 128-token prompt, a 1024-token reply and one concurrent request, median inter-token latency improved from 11.78 to 11.55 ms (**-1.95%**) and warm output throughput from 82.79 to 83.67 tok/s (**+1.1%**), with median ITL identical across all three runs on each side. A prefill-heavy run at 8-way concurrency showed no measurable change, and accuracy was unaffected.

### What the PR changes

On `main`, the model loads block-scale FP8 weights correctly, but a scale-name mismatch sends five observed projection contexts through their bf16-input fallbacks. This PR makes them use the existing AITER fused FP8 preparation paths:

- `fused_rms_fp8_group_quant` combines RMSNorm with group-128 FP8 activation quantization before `q_b_proj` and `kv_b_proj`.
- `fused_flatten_fp8_group_quant` combines flattening with group-128 FP8 activation quantization before `o_proj`.
- The FP8 linear layers then consume the pre-quantized activation and scale instead of quantizing a bf16 activation internally.

This is not only a prefill change, which is why the gain shows up in reply latency: the detector also controls the `q_b_proj` and `o_proj` fast paths in MLA decode, so the affected projection work repeats on every generated token.

Turning that pipeline on for DeepSeek-V3.2 also makes a latent `MHA_ONE_SHOT` prefix-reload bug reachable, so this PR fixes that bug in the same change. Without the fix, a cached-prefix request can feed a current-chunk-only quantized `kv_a` to `kv_b_proj` and take the server down; with it, the reload uses full-sequence bf16 `kv_a` instead.

### Which attention kernel is involved?

[PR #30808](https://github.com/sgl-project/sglang/pull/30808) already enabled gfx950 dispatch to the existing dense-MHA attention path. On ROCm that path calls AITER's `flash_attn_varlen_func`; the fresh ROCm 7.24 test loaded the FMHA v3 `fmha_fwd_hd128_bf16_causal_group` kernel.

This PR does **not** add `flash_attn_varlen_func`, change which kernel binary it resolves to, or alter the `use_mha` gate in `set_dsa_prefill_impl` that dispatches to it. What it changes is the FP8 activation preparation feeding the projections around that kernel: `fused_rms_fp8_group_quant` ahead of `q_b_proj` and `kv_b_proj`, and `fused_flatten_fp8_group_quant` ahead of `o_proj`. It then fixes the `kv_b_proj` cached-prefix failure that enabling those paths exposes, and adds gfx950 CI coverage for the existing dense-MHA dispatch.

For DSA prefill, dense-MHA is the short-context fallback: `max_kv_len` must be no larger than `SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD`, which defaults to the model's `index_topk` (2048 for DeepSeek-V3.2), in addition to the existing dtype and batch-capacity checks. The measured performance gain, however, came from a decode-heavy end-to-end workload and should not be described as a proven short-prefill speedup; the one prefill-heavier run showed no clear throughput or TTFT benefit.

Net effect for DeepSeek-V3.2 on gfx950:

| | `main` | This PR |
| --- | --- | --- |
| `fused_rms_fp8_group_quant` / `fused_flatten_fp8_group_quant` paths | not selected | selected |
| Median ITL (decode-heavy case) | 11.78 ms | 11.55 ms (**-1.95%**) |
| Warm output throughput (same case) | 82.79 tok/s | 83.67 tok/s (**+1.1%**) |
| GSM8K (200 questions, 5-shot) | 0.960 | 0.965 (within run-to-run noise) |
| Cached-prefix `MHA_ONE_SHOT` request | succeeds, but no fused path was ever selected | succeeds, with the reload guarded onto bf16 `kv_a` |

All runtime and performance results below use **DeepSeek-V3.2 on MI355X (gfx950)**. GLM-5.1-FP8 is covered only by checkpoint and source inspection; no GLM runtime result is claimed.

## What is wrong on `main`

### 1. Block-scale FP8 is misdetected

`_is_block_scale_fp8()` looks up `weight_scale`, but `Fp8LinearMethod` registers block scales as `weight_scale_inv` and never renames them. On a real DeepSeek-V3.2 TP4 run it returned `False` at all five executed projection contexts — `q_b_proj` and `kv_b_proj` (twice) in `forward_mha_rocm.py`, `o_proj` and `q_b_proj` in `forward_mla_rocm.py` — whose scale shapes `(48, 12)`, `(64, 4)` and `(56, 32)` each imply the K-block of 128 these paths require.

`_detect_gfx95_quant_format()` repeats the check independently: with only the helper fixed it still returned `"fp8_pending"` on all 488 calls (61 layers x 2 checks x 4 ranks), so both sites need fixing.

The checkpoints confirm it: DeepSeek-V3.2 has 45932 `.weight_scale_inv` tensors and 0 `.weight_scale`, GLM-5.1-FP8 has 59158 and 0, and both declare `weight_block_size: [128, 128]`.

### 2. A latent stale-`kv_a` bug becomes reachable

`forward_mha_rocm.py` quantizes `kv_a` for the current extend tokens; an `MHA_ONE_SHOT` batch with a non-empty prefix then reloads full-sequence `kv_a` and `k_pe` from cache but can still hand the stale current-chunk-only `kv_a_quanted` to `kv_b_proj`:

```
RuntimeError: The expanded size of the tensor (90) must match the existing size (166)
  Target sizes: [90, 32, 64]. Tensor sizes: [166, 1, 64]
```

The scheduler exits and all TP ranks receive SIGQUIT. Across 1-, 76- and 666-token prefixes the mismatch was always `extend_seq_lens` versus `seq_lens`.

Native DeepSeek and GLM FP8 cannot reach this on `main`: defect 1 keeps the detector false and no flag overrides it. Other formats can, since `main` accepts any multi-column 2-D `weight_scale` with no block-size check, and compressed-tensors BLOCK FP8 registers exactly that. Such a run would also need gfx950 with `SGLANG_USE_AITER=1`, `MHA_ONE_SHOT_ROCM` dispatch (a DSA model within `SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD`, default `index_topk` of 2048, or `aiter` with `--dcp-size > 1`), and a cached prefix of at least one page, as DSA forces page size to 1 or 64. That path is source-derived, not served here; the reproduction above corrected the detector and omitted the guard.

## Changes

- `deepseek_common/utils.py`
  - Look for both `weight_scale` and `weight_scale_inv`.
  - Require FP8 weights, a 2-D scale, and an implied K-block of 128.
  - Continue rejecting per-channel scales and group-32 MXFP8 layouts.
- `deepseek_v2.py`
  - Use the same two-name check in `_detect_gfx95_quant_format()`.
- `forward_mha_rocm.py`
  - Record when `kv_a` is reloaded from cache.
  - Use the pre-quantized input only when no reload occurred; after a reload, pass full-sequence bf16 `kv_a` and let the quantized linear quantize it.
- `test/registered/amd/test_fp8_per_channel_detection.py`
  - Add direct coverage for `weight_scale_inv`, the selector, per-channel FP8, non-FP8, group-32 MXFP8, and non-128 block sizes.
- `test/registered/amd/test_dsa_dense_mha_gfx950.py`
  - Add gfx950 coverage for the existing DSA dense-MHA dispatch and attention kernel.

The dense-MHA test covers backend dispatch and attention with synthetic q/k/v. It does not call `kv_b_proj`, so it does not cover the reload guard.

## Validation

### Path and reload validation

The comparison is `main` against this PR. A third, throwaway build carrying only the detection change was used once, solely to demonstrate why the reload guard belongs in this PR; it is not a proposed state.

This PR was run with real DeepSeek-V3.2 using `--trust-remote-code --tp 4 --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.9`. Both test images had the gfx950 AITER paths enabled. The server auto-selected the DSA backend; radix cache and CUDA graphs were left enabled.

- `lmsysorg/sglang-rocm:v0.5.19-rocm700-mi35x-20260909` exercised the non-bpreshuffle gfx950 paths.
- `lmsysorg/sglang-rocm:v0.5.19-rocm724-mi35x-20260909` reported HIP 7.2.26015 and `_use_aiter_bpreshuffle_gfx95=True`.
- On HIP 7.2, branch logging on all four ranks confirmed q-side and kv-side bpreshuffle materialization, the normal pre-quantized `kv_b_proj` path, the cached-prefix reload, and the reload's bf16 `kv_b_proj` fallback.
- The instrumented 768-token cache-hit case completed without a shape mismatch or server failure.

The cached and uncached paths need not generate bitwise-identical text: after a reload, `kv_a` is quantized inside `kv_b_proj`; without a reload, the already-quantized fused output is used. In the observed probe both outputs were coherent and answered the prompt, but exact text equality is not used as a correctness criterion.

### Accuracy

GSM8K was run with 200 questions and 5 shots:

- ROCm 7.0, `main`: accuracy 0.960, invalid 0.000.
- ROCm 7.0, this PR: accuracy 0.965, invalid 0.000.
- HIP 7.2, this PR: accuracy 0.965, invalid 0.000.

No regression was observed in this 200-question check. The 0.005 difference is not claimed as an accuracy improvement, and these results do not establish exact numerical equivalence.

### Performance

`sglang.bench_serving` used the random dataset with `--random-range-ratio 1.0`.

The two benchmark builds differed only by the detection commit, and the reload guard is inert when no prefix is reused, so this A/B measures the effect of selecting the fused projection paths.

For the decode-heavy case (128 input tokens, 1024 output tokens, concurrency 1, 8 prompts), both sides had a slower first run, so the reported throughput mean uses runs 2 and 3:

- `main` output throughput: 79.56, 82.85, 82.72 tok/s; warm mean 82.79 tok/s.
- This PR: 77.72, 83.30, 84.04 tok/s; warm mean 83.67 tok/s (**+1.1%**).
- Median ITL was 11.78 ms in all three `main` runs and 11.55 ms in all three runs with this PR (**-1.95%**).

This is evidence for a small improvement in this specific low-concurrency, decode-heavy case. It is not generalized to production traffic or other concurrency levels.

A single prefill-heavier run (1024 input, 512 output, concurrency 8, 64 prompts) showed no clear throughput or TTFT benefit: output throughput was 439.75 vs 439.18 tok/s, median TTFT 552.53 vs 557.38 ms, and median ITL 16.58 vs 16.26 ms. No broader prefill-performance conclusion is drawn from one run.

## Scope and limitations

- Hardware execution covered MI355X (gfx950) only. MI350 was not tested separately.
- Runtime testing covered DeepSeek-V3.2 only. GLM-5.1-FP8's scale layout and inherited code path were inspected, but no GLM model was served.
- The `aiter` + DCP dispatch route was not run.
- The reload guard was verified with branch instrumentation on a real checkpoint but has no direct automated regression test.
- Per-channel FP8 and MXFP8 exclusions were tested with synthetic modules, not real served checkpoints.
- Accuracy used 200 GSM8K questions. The performance result uses a small eight-prompt decode-heavy benchmark; the prefill-heavier comparison is one run.
