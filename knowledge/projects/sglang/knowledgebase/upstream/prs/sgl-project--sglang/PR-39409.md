# [Fix] [AMD] deepseek: Restore fused block-scale FP8 projections on gfx950 and fix the MHA_ONE_SHOT KV reload

[Upstream PR](https://github.com/sgl-project/sglang/pull/39409) · state: open · merged: False

## Original PR description

## Motivation

On MI355X, FP8 models such as DeepSeek-V3.2 miss SGLang's faster fused FP8 kernels: the check that turns them on looks for the wrong weight name, so it never fires. This PR fixes the check, which makes decode 1.4 to 2.2 % faster on DeepSeek-V3.2, and fixes a crash that the faster path would otherwise cause on requests with a cached prefix.

In detail: on gfx950, the DeepSeek-V3.2, DeepSeek-V3.1 and GLM-5.1-FP8 checkpoints we checked store block scales as weight_scale_inv, but main's block-scale check looks only for weight_scale. So the fused FP8 projection paths (fused_rms_fp8_group_quant before q_b_proj and kv_b_proj, fused_flatten_fp8_group_quant before o_proj, and the fused RMSNorm + FP8 quant at the attention input) are never selected, and turning them on exposes a latent MHA_ONE_SHOT crash on cached-prefix requests. As the contribution guide asks for bug fixes, the detection fix has focused regression tests; the reload fix is checked by the cached-prefix GPU probe below and has no direct unit test.

## Modifications

- **Detection** (`deepseek_common/utils.py`, `_is_block_scale_fp8`; `deepseek_v2.py`, `_detect_gfx95_quant_format`): accept `weight_scale` or `weight_scale_inv`, and require FP8 weights, a 2-D scale and a K-block of 128; per-channel and group-32 MXFP8 scales stay rejected. Both sites need the fix. DeepSeek-V3.2 has 45932 `.weight_scale_inv` tensors and 0 `.weight_scale`; GLM-5.1-FP8 has 59158 and 0.
- **Reload** (`forward_mha_rocm.py`): after an `MHA_ONE_SHOT` prefix reload, `kv_b_proj` got the current-chunk-only `kv_a_quanted` while `k_pe` covered the full sequence, and the server crashed. After a reload, the full-sequence bf16 `kv_a` is now passed and the quantized linear quantizes it.
- **`o_proj` gate** (`forward_mla_rocm.py`): the fused `o_proj` quant now also requires the gfx950 AITER path, where its kernel is imported. Without AITER, `o_proj` keeps main's bf16 path instead of reaching an unimported kernel now that detection passes. All runs below had AITER on, where this check is true, so it changes no measured path.
- **Tests**: `test/registered/amd/test_fp8_per_channel_detection.py` (`weight_scale_inv`, the selector, per-channel FP8, non-FP8, group-32 MXFP8, non-128 blocks). The 4 `_detect_gfx95_quant_format` cases run only on a gfx95x GPU. The gfx950 DSA dense-MHA test moved to its own PR, #45820.
- No change to the attention kernel or its dispatch. #41408 (open) fixes the same reload bug on its own.

## Accuracy Tests

Setup (2026-10-19): DeepSeek-V3.2, TP4 on 4 x MI355X, image `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261015` (SGLang `bba535ebb4`), with and without this PR's three source files, `--tp 4 --kv-cache-dtype fp8_e4m3`, and the image's default `SGLANG_USE_AITER=1`.

- Unit tests on GPU: with this PR the detection test passes 18 of 18; without it, exactly the 3 `weight_scale_inv` cases fail.
- Fused path: this PR's profile (real weights) has 549 fused FP8 group-quant kernel events; main's (random weights, with the same `weight_scale_inv` names that decide the path) has 0.
- Reload: with this PR, 30 of 30 probe requests are correct, 27 of them with a cached prefix (64, 640 or 1,472 tokens). With only the detection fix, the server crashes at the first cached-prefix request (`expanded size of the tensor (39) must match the existing size (103)`: 64 cached plus 39 new tokens). So both fixes are needed.
- GSM8K (`few_shot_gsm8k`, 5-shot, 1,319 questions, temperature 0, one run per arm): 0.950 with this PR, 0.948 without.

## Speed Tests and Profiling

Random weights (`--load-format dummy`, the same kernels and shapes), 1,024 output tokens, five sessions in the order main, PR, main, PR, main. A change counts only when it is larger than both arms' run-to-run spread.

| Input x users | Median TPOT | Output tok/s | Median TTFT |
|---|---|---|---|
| 128 x 1 | -1.6 % | +1.8 % | same |
| 128 x 4 | -2.2 % | +2.2 % | +2.7 % |
| 128 x 16 | -1.4 % | +1.4 % | same |
| 1k x 1 | -1.5 % | +1.6 % | +2.5 % |
| 1k x 4 | -2.1 % | +2.2 % | +1.1 % |
| 1k x 16 | -1.4 % | +1.4 % | same |

Decode is 1.4 to 2.2 % faster at every point. TTFT is 1.1 to 2.7 % higher at 3 of 6 points; its cause is not profiled yet (this PR also moves the prefill projections to the fused FP8 path).

Not tested: GLM-5.1-FP8 (same scale names, by inspection only), MI350, gfx950 without `SGLANG_USE_AITER=1`, and the aiter + DCP route.
