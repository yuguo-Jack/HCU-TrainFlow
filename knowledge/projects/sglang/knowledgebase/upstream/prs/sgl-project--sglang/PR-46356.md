# [RFC] [Feat] disaggregation: PD bootstrap for a linear-attention state group spanning attention-DP groups

[Upstream PR](https://github.com/sgl-project/sglang/pull/46356) · state: open · merged: False

## Original PR description

> **RFC / draft.** This proposes a PD bootstrap protocol extension and lands only the backward-compatible pieces: the pairing arithmetic, one optional wire field, and a clear refusal. The receiver wiring is left for discussion. Feedback on the protocol shape matters more than the code at this stage.

## Motivation

Today PD pairs ranks per server through `CommonKVManager._resolve_rank_mapping`. That assumes the linear-attention (GDN / Mamba) state is sharded over the same group as attention, so the ranks that hold a request's state are the ranks that hold its KV, all inside one attention-DP group.

Some deployments shard the state over a wider group than attention. Example: decode with attention TP8 x DP16 and GDN TP64 x DP2. There, one GDN state group is 8 consecutive attention-DP groups. Qwen3-Next / Qwen3.5 have 16 key heads and 64 value heads, so GDN tolerates a much wider TP than the 2 KV heads of full attention. For such a room:

1. every rank of the request's **state group**, not only its attention group, must hold a receiver for the room and register with the prefill;
2. the prefill must count those extra decode ranks in `required_dst_info_num`, and each decode rank's `required_prefill_response_num` must count its state senders;
3. both sides need the peer's state TP size, and each pair needs its state TP ranks, to slice the state;
4. prefill senders from different attention-DP groups answer the same room, so the per-sender id the decode counts responses by (`_prefill_unique_rank`) must be unique across them.

Today such a peer pairs by attention TP. The extra state ranks get no receiver and the state slice uses the wrong TP. The result is a hang or wrong state, not an error.

How this was found: Neuron / Trainium out-of-tree platform work. We run a Qwen3.5 decode kernel on trn3 with exactly this layout, attention TP8 x DP16 with GDN TP64. The out-of-tree plugin currently patches the bootstrap and receiver to do the per-room pairing described below. That plugin is private, so it is not linked. This RFC proposes the upstream shape of that patch.

## Proposed protocol

**Rank numbering** (per role): the global rank of `(attn_dp_rank, attn_tp_rank)` is `attn_dp_rank * attn_tp + attn_tp_rank`. State group `g` covers global ranks `[g * state_tp, (g + 1) * state_tp)`, which is attention-DP groups `[g * k, (g + 1) * k)` with `k = state_tp / attn_tp`. A rank's state TP rank is its global rank mod `state_tp`. `state_tp` must be a multiple of `attn_tp` and must divide `attn_tp * attn_dp`.

**Edges for one room** (prefill attention-DP group `pd`, decode attention-DP group `dd`), identical on every rank:
- **KV**: decode attention group `dd` <- prefill attention group `pd`, paired by attention TP with today's non-MLA rule.
- **State**: decode state group `dd // k_d` <- prefill state group `pd // k_p`, paired by *state* TP with the same rule.
- A decode rank sends one metadata message per prefill rank it has an edge to, with KV and state edges to the same rank merged. So `required_dst_info_num[p]` is the number of decode ranks with an edge to `p`, and `required_prefill_response_num[d]` is `|senders(d)|`. The message carries KV indices only on KV edges and state indices only on state edges.
- With `state_tp == attn_tp` on both sides, this reduces exactly to today's mapping (tested).

**Bootstrap / registration**
- Prefill: `register_to_bootstrap` adds `state_tp_size` to the PUT only when it differs from attention TP. The bootstrap server checks that it is consistent across ranks and serves it in the `/route` server info, again only when set. *(implemented)*
- Decode: `try_ensure_parallel_info` reads `PrefillServerInfo.state_tp_size`. The mapping becomes per room, because it depends on both `pd` and `dd`, so it can no longer be cached per bootstrap address. *(not implemented: refused for now, see below)*
- Decode receiver init: fetch bootstrap info for, and register with, every prefill rank of the room's prefill state group. Registration stays cached per prefill rank. *(not implemented)*
- Registration message: the decode sends its `state_tp_size` / `state_tp_rank` so the prefill slices the state by state TP rather than attention TP. Today `KVArgsRegisterInfo` only carries `decode_tp_size` / `decode_tp_rank`, which are attention TP. *(not implemented)*
- Sender id: fold `attn_dp_rank % k_p` into `_prefill_unique_rank` when the prefill state group spans attention-DP groups. The helper `prefill_sender_id` is added, but `_prefill_unique_rank` is not switched yet.

**Scheduler-side contract (open):** every rank of the state group must hold the request. On the prefill, each state-group rank keeps the request's state in its own pool slot and has a sender for the room. On the decode, each state-group rank has a receiver and a state slot. Stock attention-DP scheduling routes a request to one attention-DP group, so this needs either TP-wide scheduling or a state-group-aware DP router. On Neuron we run the decode as TP=128, so every rank already sees every request.

## Modifications

- `python/sglang/srt/disaggregation/common/state_group.py` (new): pure planning code with no torch / zmq. It holds `StateGroupLayout`, `plan_state_group_room` (per-room KV / state / merged senders and `required_dst_info_num`), `tp_targets` (today's non-MLA rank rule), and `prefill_sender_id`.
- `KVArgs.state_group_tp_size` (default `None`): the state group width, set by whoever builds the KV args. In-tree nothing sets it yet. Where it should come from in-tree is an open question.
- `CommonKVManager`: publishes `state_tp_size` on the bootstrap PUT when set and different from attention TP. A new `_check_state_group_supported` makes `try_ensure_parallel_info` raise `NotImplementedError` when either side's state group spans attention-DP groups. Before, such a peer was mis-paired silently.
- `CommonKVBootstrapServer` / `PrefillServerInfo`: optional `state_tp_size`. A PUT that is inconsistent across ranks gets a 400, and the field is omitted from `/route` when unset, so older decodes still parse the server info.

Backward compatibility: no behavior change unless `KVArgs.state_group_tp_size` is set. The existing `state_tp_size` (`linear_attn_tp_size()`, used for CP-TP group sharing) is untouched. CP-TP group sharing already relabels CP as TP in registration, and that case does not span attention-DP groups.

## Open questions

1. Where should in-tree code get the state group width? Options: a `--linear-attn-tp-size` server arg with a matching parallel group, a model / platform hook, or only `KVArgs` for out-of-tree platforms.
2. Per-room mapping vs. per-server caching: should `PrefillServerInfo` keep a per-`(pd, dd)` cache of plans, or should `CommonKVReceiver` compute it at init?
3. Aux: which sender owns each decode rank's aux buffer when a rank has several senders, or only state senders? Out-of-tree we give each decode rank exactly one aux edge: its lowest data sender, or round-robin over prefill participants for ranks with no data edge. This also needs `send_aux` to post nothing on non-aux pairs.
4. Should state edges always ship the whole state-group slice, or can a prefill rank outside the request's attention group be skipped when the state is replicated?
5. Should this live in the common manager, or behind a backend capability flag, given that NIXL / Mooncake / Mori each implement their own state slice senders?
