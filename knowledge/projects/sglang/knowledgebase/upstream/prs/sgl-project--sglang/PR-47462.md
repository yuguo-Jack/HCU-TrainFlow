# [Refactor] pd: Extract MoriTransport behind the common Transport interface

[Upstream PR](https://github.com/sgl-project/sglang/pull/47462) · state: open · merged: False

## Original PR description

## Motivation

Step 2 of #34510 for Mori: move the Mori IOEngine calls behind a `MoriTransport` on the interface proposed in #46455.

Stacked on #46460 (MooncakeTransport).

**Merge order:** #46460 should be merged first. This PR is then rebased onto main. It does not depend on #46614 (NixlTransport); both edit the shared stub transport in `test_receiver_connection_pool.py`, so whichever lands second resolves a small conflict there.

## Modifications

- `mori/transport.py`: `MoriTransport` owns the Mori IOEngine and makes every engine call: engine creation, memory registration, peer import, writes, waits and teardown. It keeps the `MemoryDesc` of every registered buffer. `mori/conn.py` keeps only the `BufferKeys` of each side and a `PeerBuffers` per decode peer; it no longer calls the engine or holds anything the engine created.
- Refactor only: the wire format and transfer behavior are unchanged. Every `batch_write` gets the same descriptors, offsets, sizes and number of transfer uids as before, and the failure reasons keep their text. The differences are listed in Notes.
- Aligned with the Mooncake side so that the protocol code can be shared later: `mori/buffers.py` holds the part of `mooncake/buffers.py` that Mori uses (`BufferKind`, the key class, `BufferKeys`, `copy_ranges`), apart from the key class name. `mori/conn.py` follows `MooncakeKVManager`: `init_engine()`, `BufferKeys` built once per side, `PeerBuffers`, and `src`/`dst` keys on the send paths. Transfer plans are `(N, 3)` byte ranges, the form a `Copy` carries.
- `transport/base.py` and the Mooncake and NIXL files are untouched. Mori-only types stay under `mori/`. The types Mori shares with the other backends (buffer keys, `PeerBuffers`) are copied for now; the shared parts are left to a follow-up PR once every backend has a Transport.

Commits:
1. `Plan Mori transfers as Copy byte ranges`: protocol-side only; `BatchTransferPlan` becomes `(N, 3)` uint64 ranges.
2. `Extract MoriTransport behind the common Transport interface`: every engine call goes through the Transport; the engine is still created in `_init_engine()`.
3. `Create the Mori IOEngine in MoriTransport.create()`: the creation code moves unchanged.

## What `MoriTransport` adds over `MooncakeTransport`

`write()`, `write_all()`, `status()`, `deregister()` and `close()` implement the same interface as `MooncakeTransport`. The rest follows from how the Mori engine differs from Mooncake's. Apart from the interface methods, each item is engine handling that `mori/conn.py` already had before this PR and that moved into the Transport.

| Added or different in `MoriTransport` | Why Mori needs it |
|---|---|
| `MoriTransport.create()` | Mooncake borrows the process-wide engine. Mori creates one IOEngine per KVManager, with its RDMA backend and the `MORI_RDMA_DEVICES` device selection. `create()` makes the engine and returns the Transport that holds it; the KVManager keeps no reference. Moved from `MoriKVManager._init_engine()`; `init_engine()` calls it. |
| `engine_key`, `engine_desc_blob` | Carried by the metadata and registration messages, as `session_id` is for Mooncake. Both come from the engine's `EngineDesc`. |
| `register()` keeps a `MemoryDesc` per key; `mem_desc_blobs()` | A Mori peer addresses a write by the destination `MemoryDesc` and an offset, so the registration message carries a packed `MemoryDesc` per buffer instead of a base address. Each key gets its own engine registration, as before, so there is no `register_all()` or region sharing. A zero-length buffer keeps a `None` slot in the message. |
| `import_registration(engine_desc, descs)` | Mori registers the peer's engine (`register_remote_engine`) before any transfer and addresses writes with the peer's `MemoryDesc` of each key. Mooncake only needs the session id and base addresses. |
| `write()` and `write_all()` post without blocking | One `batch_write` per call, with a transfer uid and a handle per copy. The KV, state and mamba paths use `write()` per layer or block, as they called `batch_write` before; the aux path's single batch is `write_all()`. Mooncake's `write_all()` blocks in `batch_transfer_sync`. |
| `status()` reads the `TransferStatus` | Non-blocking: `InProgress()` is PENDING, `Failed()` is FAILED, anything else is DONE. Mooncake's handle already holds the final result. |
| `wait_all(handles, timeout_ms)`, `wait(handles)` | The transfer worker polls with the engine's bounded `wait_all` (`SGLANG_MORI_WAIT_POLL_MS`), which returns as soon as the writes settle; polling the non-blocking `status()` instead would change that loop. `wait_all()` keeps the call, and as with `status_all()` its FAILED result can leave other handles PENDING. `wait()` is the drainer's unbounded wait. The poll loop and the SLA check stay in `mori/conn.py`. |
| `close()` deregisters local memory and drops the engine | The Transport owns the engine instead of borrowing it. As `teardown()` did, a failed deregistration is ignored, and peer engines stay registered until the engine is dropped. |

There is no counterpart to `NixlResult.quiescent`. `mori/conn.py` poisons the room on any failed write and computes its own `is_quiescent` (no handle still PENDING), so it does not need to know whether a failed write has stopped touching memory.

## Notes

Behavior differences from main:
- **Zero-length buffers.** `register()` leaves a zero-length buffer of any kind unregistered, with a `None` slot in the registration message. Before, only state buffers were checked, and a zero-length KV or aux buffer was passed to `register_memory`, where main's comment says `ibv_reg_mr` aborts. It applies only to a zero-length KV or aux buffer; I have not confirmed whether any current pool produces one.
- **TransferStatus queries.** `status()` calls `InProgress()` and then `Failed()` (and `Message()` for a failed status). The quiescence check and the poison check now go through `status()` and `status_all()`, so they make these calls on every status instead of only `InProgress()` or only `Failed()`, and the poison check no longer stops at the first failure. The results are the same: the extra calls are read-only queries, and the poison check runs only on settled statuses.
- **CPU cost on the heterogeneous-TP MHA path.** Its per-token ranges are converted to lists on each layer's write instead of once per chunk: about 0.2 ms per write for 8192 rows on one CPU core, or about 25 ms per chunk for 61 layers. The other paths convert one row per contiguous page group.
- **Logger name.** The engine init debug log and the port assertion moved to `mori/transport.py`, so the log record's logger is `sglang.srt.disaggregation.mori.transport`; the text is unchanged.
- **Exceptions from `batch_write`.** `write()` and `write_all()` let them propagate, as `MooncakeTransport` does, and `mori/conn.py` still raises `_MoriTransferSubmissionError`. The `write()` docstring in `transport/base.py` asks for a FAILED handle instead.

Other notes:
- `deregister()` implements the abstract interface; `mori/conn.py` has no memory release/resume path and does not call it. `register()` is called once per key and does not replace an earlier registration of the key, unlike `MooncakeTransport.register_all()`.
- `KVArgsRegisterInfo` still keeps the decoded `EngineDesc` and `MemoryDesc` lists of the registration message, as Mooncake's keeps the peer's pointers. The engine key inside the `EngineDesc` is the peer's identity in the protocol; the transfer paths use keys and the Transport's copy of the descriptors.
- `_register_local_buffers()` reads `kv_args.state_data_lens` directly instead of through `getattr(..., [])`: `setup_state_kv_args()` sets it before prefill and decode build a KVManager.
- In `test_failed_status_never_acks`, the `TransferStatus` mock leaves `InProgress()` once `Wait()` returns. It reported `InProgress()` and `Failed()` at once, which a `TransferStatus` cannot, and `status()` reads that state as PENDING.

## Tests

`test/registered/unit/disaggregation/` passes on CPU (370 passed, 17 skipped), the same counts as the head of #46460. On that head one `test_kv_events` subtest failed once; the file has no Mori code and passed 5 of 5 reruns on this branch.

A temporary script (not committed) ran the send paths (MHA, heterogeneous-TP slice, MLA, PP layer ids, DCP, aux RDMA and TCP, mamba, mamba slice, elided DSA state), the wait, drain and poison paths, registration and metadata messages, engine creation and teardown over a recording fake engine, on main and after each commit. Every engine call and every result matched; the only differences are the `TransferStatus` queries described in Notes.

Not yet run with a real Mori/RDMA backend.
