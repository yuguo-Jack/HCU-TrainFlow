# [Fix] rust-server: Advertise the rendezvous-facing host and refuse a cross-node loopback endpoint

[Upstream PR](https://github.com/sgl-project/sglang/pull/47541) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #47509

With `SGLANG_RUST_SERVER=1` on a multi-node launch, `RustServer.gather_server_endpoints` publishes the address every other listener dials for control fan-out (`/flush_cache`, `/start_profile`, `/weights_checker`, ...). For a wildcard bind it used `get_local_ip_auto`, which can pick an interface the other nodes can't reach (a bridge or management address), or fall back to `127.0.0.1`. A loopback entry only logged a warning. Listener ports are node-local offsets, so another node that dials a loopback entry reaches its own listener at that offset, and the reply is attributed to the wrong rank.

## Modifications

- `utils/network.py`: new `get_local_ip_towards(addr, family)` returns the source address of a UDP socket connected to `addr` in the given family (`getsockname`, no packets sent). `get_local_ip_auto` takes optional `towards=` and `towards_family=`. The explicit settings still win, in this order: `SGLANG_HOST_IP`/`HOST_IP`, then `SGLANG_LOCAL_IP_NIC`, then the probe, which replaces only the 8.8.8.8 default-route guess. A loopback answer is skipped, which happens when the rendezvous name resolves to this machine, e.g. a hostname `/etc/hosts` maps to `127.0.1.1` on the rendezvous node. Other callers pass no `towards` and are unchanged.
- `rust_server/server.py`: a wildcard bind on `nnodes > 1` advertises the address facing `dist_init_addr`, probed with `AF_INET` for a `0.0.0.0` bind (an IPv4-only listener), so an IPv6 rendezvous can't produce an IPv6 endpoint that listener can't accept. Each rank gathers `(node_rank, entry)`. When the listeners span nodes, every rank checks the gathered table and raises `ValueError` naming the loopback entries and `dist_init_addr` (and pointing at `--host 0.0.0.0` for `SGLANG_HOST_IP`), unless the nodes rendezvous on loopback (emulated on one machine). The check runs after the collective, so all ranks fail together and none is left blocked in the gather. Listeners on one node, such as plain multi-node TP with the default `--host 127.0.0.1`, never dial each other across machines and still start. The published table keeps its shape, so nothing on the Rust side changes.

#47534 targets the same issue. This version differs in three ways: it raises after the gather rather than before it, skips a loopback probe answer, and keeps single-node listener layouts (the default `--host`) starting.

## Accuracy Tests

No model or kernel path changes. Unit tests on macOS (Apple M4, Python 3.11.15):

| | base `7146002be8` + new tests | this PR |
|---|---|---|
| `pytest test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py -k gather_server_endpoints` | 3 failed | 3 passed |
| `pytest test/registered/utils/test_network_address.py -k GetLocalIpTowards` | import error (`get_local_ip_towards` doesn't exist) | 2 passed |

The new tests cover:
- a `0.0.0.0` bind probes the rendezvous with `AF_INET`, and an IPv6 target gives no IPv4 address (real sockets);
- `SGLANG_LOCAL_IP_NIC` and `SGLANG_HOST_IP` each win over a non-loopback probe answer, and the probe isn't consulted;
- a loopback probe answer falls through to the default-route guess (a real UDP probe, not mocked);
- a table spanning nodes with a loopback entry raises;
- listeners on a single node, or a single loopback listener, start.

Moving the probe back ahead of `SGLANG_LOCAL_IP_NIC` makes the gather test fail.

`test_rust_server_extension.py` + `test_network_address.py`: 60 passed, 1 skipped, 2 failed. Both failures also fail on base `7146002be8`: `test_mixed_logprob_batch_frame` (a mock missing `output_ids_offsets`) and `test_scheduler_aborts_reach_the_rust_egress` (needs `mlx`).

## Speed Tests and Profiling

This runs once per scheduler process at startup and doesn't touch the request path. Measured on Apple M4, Python 3.11.15, 2000 rounds each, base `7146002be8` vs this PR:

| startup step | before (median / p99) | after (median / p99) |
|---|---|---|
| host resolution, IP `--dist-init-addr 10.0.0.1:5000` | 161 µs / 214 µs | 167 µs / 239 µs |
| host resolution, hostname that resolves to loopback (`localhost:5000`) | 159 µs / 209 µs | 388 µs / 493 µs |
| `gather_server_endpoints`, 8 listeners on 2 nodes (fake collective) | 227 µs / 396 µs | 221 µs / 403 µs |

(One run each side; medians from a repeat run were within 2%.)

Why (cProfile, per call):
- **Before:** `get_local_ip_by_remote` spends 112 µs in `getaddrinfo("8.8.8.8", AI_ADDRCONFIG)` and 38 µs in `connect`.
- **After, IP rendezvous:** one `getaddrinfo` in the bind's family (108 µs) plus `connect` (32 µs), so the cost is about the same as before.
- **After, loopback-resolving hostname:** the probe answer is skipped and the default-route guess runs as before, so `getaddrinfo` runs twice (297 µs).

A hostname rendezvous that resolves through DNS adds one lookup at startup; that case wasn't measured here.

def all_gather_object(obj):

    fn()
    s = []
    for _ in range(ROUNDS):
        t = time.perf_counter_ns(); fn(); s.append(time.perf_counter_ns() - t)
