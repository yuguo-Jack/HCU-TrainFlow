# [Fix] sampling: Correct the stale Cake softmax text

[Upstream PR](https://github.com/sgl-project/sglang/pull/48184) · state: closed · merged: False

## Original PR description

## Motivation

#47512 made the JIT softmax the first choice on the SM100 family, but three pieces of text still say that Cake does this work: a comment in `test_softmax.py`, the Cake README, and the name of a CPU test. On a B200, these statements are false. Serving is not affected, but the text can mislead a person who debugs SM100 sampling.

## Modifications

This PR changes text only. The comment now names the JIT softmax. The test name now says fallback, because the JIT softmax is not selected on a CPU runner. The README now says that Cake runs in `sampling.softmax` only when the JIT softmax rejects a call in the Cake domain, and that DSpark's draft softmax still reaches Cake through FlashInfer.

Temporary counters, not in this PR, show where Cake still runs on B200 with FlashInfer 0.7.2:

| Run | `sampling.softmax` | FlashInfer Cake softmax |
| --- | --- | --- |
| `test_softmax.py` | JIT for eligible shapes, otherwise Torch | Not called |
| Llama-3.2-1B, TP 1 and TP 2, sampled requests | JIT | Not called |
| Llama-3.1-8B with EAGLE3, sampled requests | JIT | Not called |
| Qwen3-14B with `dspark_qwen3_14b_block7`, sampled requests | JIT | Called with shapes such as `(28, 151936)` |
| Same DSpark server, greedy requests | Not called | Not called |

Llama's vocabulary (128256) is inside the `supports_softmax` domain, so the JIT softmax takes inputs that Cake also accepts. The DSpark server used the flags and environment of `test_basic_sanity_dspark.py`. `SoftmaxTemp` is the only serving caller of FlashInfer's softmax outside the Cake adapter.

The Cake branch of `sampling.softmax` ran only for tensors that I built by hand, such as `x[:, :V]` from a tensor of width `V + 1`, with temperatures. A code read found no serving caller that passes such a tensor, but it was not a full audit.

## Accuracy Tests

Not applicable, because this PR changes no runtime code. On a trial merge with main at `b6a59c4938`, these checks are clean: `test_softmax.py` on a B200, `test_kernels_namespace.py` on a CPU-only lease, and pre-commit on the changed files.

Nothing ran on SM103, GB200, or GB300. The SM103 statements come from reading `_device_supported` and FlashInfer's `_supports_blackwell_softmax`. I read the DSpark shard and blockwise-rejection branches but did not run them.

The Cake tests that call `sampling.softmax` fail on a B200 host with `AttributeError: 'types.SimpleNamespace' object has no attribute 'stride'`, because the JIT softmax is selected there. CI runs them on CPU runners only, so it does not see this existing failure.
