# [HiCache] Do not shrink full L3 prefetch hits to available host capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/40193) · state: closed · merged: False

## Original PR description

## Motivation

In cache mode, a full L3 storage hit can currently be silently shortened to the L2 host pool's currently available capacity. The store reports a complete prefix, but the request later sees only a partial storage hit.

For example, a controlled Qwen3-4B / H20 run reported `16010 / 16010` pages from Mooncake `batch_exists()`, but the L2 allocator could only stage 2,551 tokens. The old fallback allocated that shorter prefix and returned `cached_tokens=2551`, making the result look like a partial L3 hit even though the L3 objects were complete.

## Modifications

- Remove the cache-mode fallback that allocates a shorter page-aligned prefix when the full L3 hit cannot be staged in L2.
- Keep the existing `host_capacity` path: finish the prefetch with zero fulfilled tokens, revoke it, and expose the deferred/unfulfilled metrics.
- Add a CPU regression proving that a complete storage hit is not shortened to the available host capacity and does not enter the transfer queue.

This is intentionally a correctness fix, not a full-restore optimization. A later optimization can reclaim host values only after their L3 copies are confirmed, or defer the full staging until capacity is available.
