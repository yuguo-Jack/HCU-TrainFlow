# [Perf] Foundry: adding the adapter of foundry to enable fast CUDA graph save/load

## Motivation

[Foundry](https://github.com/foundry-org/foundry) persists CUDA graphs across restarts. The first start (`save`) archives the captured graphs, their kernels and the device-memory layout. Later starts (`load`) rebuild the graphs from the archive instead of capturing them, so an engine that spends 40-120 s capturing 128 decode graphs per rank is serving within a few seconds of the eager engine.

Foundry hooks the CUDA driver (an `LD_PRELOAD` library, like `torch_memory_saver`) and needs SGLang to call it at a few points of the engine bring-up. This PR adds it the way SGLang integrates `torch_memory_saver`: an optional dependency behind an adapter that is a no-op unless the feature is enabled, a server argument, and explicit one-line call sites. The call sites pass only the values Foundry needs (the loaded model, the draft-worker flag, the resolved pool config, the prefill request slots), never a runner or backend object. It replaces the plugin approach of #41791, which maintainers considered unsuitable for an extension that needs runtime call sites.

**No-op guarantee:** with `--cuda-graph-persistence` unset, every call site resolves to the no-op adapter and no runtime path changes.

## Modifications

Four commits on `main` (`[Feature]`, `[Test]`, `[CI]`, `[Docs]`), 25 files, +1327 / -1. `layers/moe/token_dispatcher/standard.py` and the other runner backends are not touched.
- **Server arguments**: `--cuda-graph-persistence {save,load}` (default off) and `--cuda-graph-persistence-config PATH` (Foundry TOML; the flag's mode wins over the file's).
- **Adapter** (`srt/utils/foundry_adapter.py`, the `torch_memory_saver_adapter.py` shape): lazy import of `foundry.integration.sglang.api`; `create(enable)` returns the real or the no-op adapter, raises with an install hint only when the flag is set and Foundry is missing, and checks `INTEGRATION_API_VERSION` 2.x. Optional extra `sglang[foundry] = ["foundry-core>=0.1.0rc2,<0.2"]`.
- **Resolution** (`arg_groups/cuda_graph_hook.py`): pins the fields a restored graph cannot replay and rejects unsupported features (speculative decoding, LoRA, non-full graph backends, ...); every pin states its reason.
- **Call sites** (Foundry integration API 2.0). Each is one adapter call or one `with` and passes plain values, never a runner or backend:

  | site | call |
  |---|---|
  | `engine.py`, `data_parallel_controller.py` (the two scheduler spawn sites, next to `memory_saver_adapter.configure_subprocess`) | `configure_subprocess(server_args)`: hook preload scoped to the spawn |
  | `run_scheduler_process`, `run_data_parallel_controller_process` (before `publish`) | `activate_foundry(server_args)` |
  | `bootstrap.init_parallel_runtime` | `before_parallel_init(device)` / `after_parallel_init()` |
  | `ModelRunner.init_torch_distributed` (end) | `after_runner_distributed_init(is_draft_worker)` |
  | `KVCacheConfigurator._resolve_memory_pool_config` | `replay_saved_memory_pool_config()` / `record_memory_pool_overrides()`: `load` reuses the pool config `save` resolved, because the pool sizes come from a free-memory profile that differs between the two |
  | `ModelRunner.alloc_memory_pool` (begin / end) | `before_alloc_memory_pool(is_draft_worker)` / `after_alloc_memory_pool(memory_pool_config=..., is_draft_worker=...)` |
  | `DecodeCudaGraphRunner.capture`, `PrefillCudaGraphRunner.capture` | `with capture_scope(phase, model=..., req_slots=None)`; the existing body moves unchanged into `_capture_graphs()` and SGLang's own capture loop still runs |
  | `FullCudaGraphBackend.capture_one` | `capture_one(shape_key, forward_fn, pool=..., stream=...)`: `save` captures and archives, `load` restores in place of capturing; the backend stores the returned graph and output |
  | `_set_envs_and_config` | `apply_env_pins(server_args)` |

  Foundry pins `TORCHDYNAMO_DISABLE=1` in the scheduler processes because `save` runs each shape's first forward inside the capture and torch >= 2.14 refuses to trace during capture; SGLang's remaining `@torch.compile` helpers then run eagerly.
- **Tests**: `test/registered/unit/utils/test_foundry_adapter.py` (CPU: the adapter against a stub API, plus an AST contract on every call site and its exact arguments); `test/registered/cuda_graph/persistence/test_cuda_graph_persistence.py` and `test_cuda_graph_persistence_prefill.py` (1 GPU, nightly: native, `save`, `load` on Qwen3.5-2B and Qwen3-1.7B with prefill graphs; greedy parity, TPOT, restore time, no hook errors).
- **CI**: `scripts/ci/cuda/ci_install_foundry.sh` installs the extra with `--no-deps` from the wheel index of the installed torch/CUDA pair; suite `nightly-test-1-gpu-large-foundry` on runner `1-gpu-large-foundry` (the `1-gpu-h100` pool) in `nightly-test-nvidia.yml`. The runners need PyPI access and the two models in the HF cache.
- **Docs**: `advanced_features/cuda_graph_persistence.mdx` (registered in `docs.json`) and two rows in `server_arguments.mdx`.

## Accuracy Tests

This PR changes no model outputs and no kernels. The restored graphs are checked with a strict comparison of the native graph, `save` and `load` engines on the same host, code and weights: 74 requests (9 batched calls of 1-32 requests, greedy, 12 tokens), comparing the selected token and the top-3 logprobs of every step, batched and one request at a time. A layout passes when every pair (native/save, native/load, save/load) has identical tokens and a logprob max-abs difference of 0. Per-layout results are in the "strict check" column below.

- **E2E tests** on H200: 12/12 passed (6 per file). Greedy output of `save` and `load` is token-identical to native, restore takes 0.02-0.15 s (8 graphs), and median `load` TPOT is 4.50 vs 4.41 ms native (Qwen3.5-2B) and 3.61 vs 3.61 ms (Qwen3-1.7B).
- **CPU**: adapter and call-site tests pass (12 tests, 33 subtests). Deleting any call site, or passing a runner where a value is expected, fails the contract test.

## Speed Tests and Profiling

The PR does not touch the inference path; the numbers measure Foundry's startup effect through these call sites. Setup:

- 4xH200, this branch + foundry-core 0.1.0rc2, torch 2.14.1 / cu130, overlap scheduler on.
- Decode graphs for batch sizes 1-128 (1-256 on three rows). Prefill FULL graphs at power-of-two buckets where SGLang can capture them (Qwen3 family, gpt-oss). Qwen3.5, DeepSeek-V4 and GLM run decode graphs only, an SGLang limitation.
- TTFT: 128 prompts of the largest bucket at concurrency 32, after a throwaway pass. TPOT: decode bench.

Each `/health` time is the first `200` after launch in the engine log, one run per row. On every row the SAVE and LOAD VMM offsets are equal and the hook logs no error. ¹ Batched Qwen3.5 differs by 0.002 on every pair, native/save included (DeltaNet batch composition), so not from the restore. The gpt-oss output is not comparable (dummy mxfp4 experts); graph == load parity holds and save/load sequential is exact. Its LOAD TPOT is 5-9% above native (two samples) because its MoE swiglu (`swiglu_gpt_oss_sigmoid_alpha`) is a real `torch.compile` fusion that runs as eager kernels under the Dynamo pin; a native engine launched with the same pin runs at `load` speed (bs 1/8/32/128: native 5.08 / 5.29 / 6.05 / 9.26 ms, native with the pin 5.56 / 5.77 / 6.54 / 9.72, `load` 5.50 / 5.71 / 6.46 / 9.61). With `--moe-runner-backend triton_kernel` (TP4, ep_size 1), whose activation is a hand-written kernel, `load` equals native (3.57 / 3.81 / 4.27 / 5.99 vs 3.58 / 3.76 / 4.24 / 5.97 ms) and the strict check is exact on every pair.

On the attention-TP rows `load` TPOT reads 5-8% below native. That is not the graphs: a profiler window at bs 32 shows identical kernel counts and per-step kernel time on both engines. The native engines in these runs did not have `TORCHDYNAMO_DISABLE=1`, so their eager steps (bs below the TP multiple, mixed steps) pay Dynamo's guard checks and graph-break frames per MoE layer; a native engine launched with the same pin matches `load` (Qwen3-30B attn TP2 x DP2 + EP4, bs 1/8/32/128: native 100.3 / 13.9 / 21.4 / 23.5 ms, native with the pin 93.7 / 13.0 / 20.1 / 23.5, `load` 92.2 / 12.8 / 20.0 / 22.1). The EP-only rows run every batch as a graph and show no gap.

One SGLang-side observation from the runs, not caused by this PR: with attention TP > 1, a FULL prefill bucket that is not divisible by the TP size cannot be captured. The layer boundary reduce-scatters tokens over attention TP; real batches are padded, but the capture bucket is not. The attention-TP rows therefore start their buckets at the TP size.
