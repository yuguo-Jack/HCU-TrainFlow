# [Perf] [NVIDIA] KDA: Extend the CuTe DSL MTP verify kernel to SM90

[Upstream PR](https://github.com/sgl-project/sglang/pull/44612) · state: open · merged: False

## Original PR description

## Summary

**TL;DR: This PR lets the fused CuTe DSL KDA verify kernel run on Hopper (SM90).** Today it does not compile for SM90 and the gate admits only SM100 / SM103, so SM90 always runs the Triton path, even with `--linear-attn-verify-backend nv_cutedsl`. This PR replaces the kernel's two SM100-only packed FP32 instructions with scalar FP32 math on SM90 and admits SM90 in the gate. GLM-5-Next now defaults to the kernel on SM90 with ReplaySSM, and Kimi-K3, whose speculative-decoding defaults already request it, now passes the gate on Hopper. SM100 is unchanged.

- **Performance** (GLM-5.3-Flash on H200, attention DP8, ReplaySSM): **steady-state decode throughput +5.1–6.3%** and **3.6–6.0% shorter decode steps** at 64 and 128 concurrent requests, gains that include [#43659](https://github.com/sgl-project/sglang/pull/43659), whose fused output norm reaches SM90 only through this PR. Per KDA layer with ReplaySSM, the kernel alone runs the verify **1.7–2.3x** faster than main's Triton path for GLM-5-Next shapes and **2.0–3.0x** for Kimi-K3's Hopper shapes.
- **Accuracy: effectively lossless.** Kernel outputs match the Triton path to **about one BF16 rounding step** across 35 shapes, and GSM8K stays **within one standard error** of main (**97.08% → 97.27%** with ReplaySSM).
- **Cost:** **no new flags and no memory change**; only a **one-time 18–41 s** CuTe compile on the first start, as on SM100, cached for later starts.

## Motivation

#32890 added the fused CuTe DSL KDA (Kimi Delta Attention) verify kernel, #32541 made it the `nv_cutedsl` verify backend for Kimi-K3's speculative decoding, and #42905 made it GLM-5-Next's default verify backend on SM100. For each KDA layer of a target verify (the step that checks the MTP (multi-token prediction) or DSpark draft tokens), one kernel replaces main's default Triton path (`causal_conv1d_update` and the gated delta-rule recurrence as separate kernels) and keeps the recurrent state in registers across the draft tokens. With ReplaySSM spec-verify (`--enable-linear-replayssm-spec`), which replaces the verify's per-draft full-state snapshots with a per-slot window of raw inputs (the ReplaySSM ring), the same kernel also writes that ring in the same pass.

Hopper cannot use it today. The recurrence uses two packed FP32 instructions, `cute.arch.mul_packed_f32x2` and `cute.arch.fma_packed_f32x2` (each does two FP32 multiplies or two FP32 FMAs at once), which NVVM accepts only for SM100 and newer (`F32x2 intrinsics are not supported on this architecture` for `sm_90a`), and `_can_run_dspark_cutedsl_mtp` admits only capability major 10. So on SM90 the gate falls back to Triton without a message: every KDA layer of every target verify runs the unfused Triton kernels, which are markedly slower, above all with ReplaySSM (per-layer table below). This hits Kimi-K3, whose model defaults ask for the fused kernel on every GPU whenever speculative decoding is on, and every server that passes `--linear-attn-verify-backend nv_cutedsl`. On Hopper both silently get the slower Triton path instead of the kernel they asked for: Kimi-K3's startup log even says it pins `nv_cutedsl` and "uses the fused Kimi-K3/DSPARK CuTeDSL kernel", and nothing logs the fallback.

## Modifications

The two packed FP32 instructions, `cute.arch.mul_packed_f32x2` and `cute.arch.fma_packed_f32x2`, are the only Blackwell-specific part of the kernel, and the GDN ReplaySSM verify kernel vendored from FlashInfer (`cutedsl_gdn_mtp_ring.py`, #33102) already guards the same two instructions with a `use_packed_fma` switch, so this PR adds the same switch, admits SM90 in the gate and extends GLM-5-Next's default:

- **`python/sglang/kernels/ops/attention/kda_decode_mtp.py`** (`fused_kda_decode_mtp_dspark`) -- a `USE_PACKED_FMA` compile-time constant (capability major >= 10) keeps the packed instructions on SM100 and newer, and uses scalar FP32 multiplies and multiply-adds on SM90, at the 4 call sites in the recurrence (1 `mul_packed_f32x2`, 3 `fma_packed_f32x2`). The capability was already part of the kernel's compile cache key.
- **`python/sglang/srt/layers/attention/linear/kda_backend.py`** -- `_can_run_dspark_cutedsl_mtp` accepts capability major 9 as well as 10.
- **`python/sglang/srt/arg_groups/glm5_next_hook.py`** -- GLM-5-Next's speculative-decoding default `--linear-attn-verify-backend nv_cutedsl` ([#42905](https://github.com/sgl-project/sglang/pull/42905)) now also applies on SM90 when `--enable-linear-replayssm-spec` is on.
- **Tests**
  - Three existing kernel tests now also run on CI's `1-gpu-large` (H100) runner and no longer skip SM90: `test_kda_mtp_cutedsl_replayssm_ring.py` (ReplaySSM parity, the fused output-norm option, CUDA-graph padding requests), `test_kda_decode_mtp.py`, and `test_kda_decode_mtp_slot_stride.py`. On main the last one is registered only for the RTX 5090 (SM120) runner, where its SM100-only skip always applies.
  - The new `test_nv_cutedsl_verify_matches_triton` (in `test_kda_fused_verify_backend.py`) runs the real backend with `nv_cutedsl` and with `triton`, checks that the CuTe kernel ran, and compares the outputs and every per-step SSM state.
  - CPU tests (in `test_kda_helion_dispatcher.py`) pin the gate (SM90 and SM100 admitted, SM80 and SM120 rejected) and the GLM-5-Next default (SM90 with and without ReplaySSM, SM100).
  - Running this PR's tests against main's kernel and gate on H200, the three kernel tests fail to compile for `sm_90a` (`F32x2 intrinsics are not supported on this architecture`) and the new parity test finds that the CuTe kernel never ran; with this PR all four test files pass.

To opt out, `--linear-attn-verify-backend triton` selects the Triton verify path on any GPU, which is what SM90 ran before this PR.

## Accuracy Tests

**The kernel computes the same recurrence in FP32; on SM90 only the instruction form changes.** The reference is a different kernel (main's Triton path) and the output is BF16, so the two agree to BF16 rounding, not bit for bit. At kernel level on H200, across 35 shapes (3 to 64 KDA heads per GPU, 2 to 8 tokens per verify, with and without the ring, with and without the fused output norm from #43659), **every output is within 1.03e-2 of the Triton path** (max absolute difference / max absolute reference value), every per-step state within 6.8e-4 and every ring entry within 4.7e-4; neither path writes the persistent SSM state during the verify.

**End to end, GSM8K stays within one standard error of main (about 0.46 points) in both configurations.** `sgl-eval run gsm8k --num-threads 32 --max-tokens 32768` (sgl-eval 0.1.2, all 1,319 questions, temperature 0, top_p 0.95, the chat template's defaults, no errors), GLM-5.3-Flash on H200; MTP a/b/c = draft steps / top-k / tokens per verify:

| Configuration | main | this PR |
|---|---|---|
| Attention DP8, ReplaySSM ring, MTP 3/1/4 (where this PR changes the default; medians) | 97.08% | 97.27% |
| TP8, MTP 5/1/6 (this PR with `--linear-attn-verify-backend nv_cutedsl`) | 97.19% | 97.04% |

The TP8 row applies the dispatcher change from #43330 (open) to both builds: without it, both builds of this configuration stopped with an illegal memory access on the last expert-parallel rank (issue #43324; GLM-5.3-Flash's H200 CI test runs TP8 without expert parallelism and does not take that path).

## Speed Tests and Profiling

**With the ReplaySSM ring, this PR is faster at every measured load: steady-state decode +5.1–6.3%, whole request bursts +3.2–4.4% output throughput.** This measures the configuration where this PR changes the default. **Both builds include [#43659](https://github.com/sgl-project/sglang/pull/43659) and [#44262](https://github.com/sgl-project/sglang/pull/44262), so "this PR" here includes [#43659](https://github.com/sgl-project/sglang/pull/43659)'s fused output norm** (builds under "Commands and builds" below). GLM-5.3-Flash on H200: `--tp-size 8 --ep-size 8 --attn-dp-size 8`, `--enable-linear-replayssm-spec`, EAGLE MTP 3/1/4, MegaMoE all-to-all with the DeepGEMM MoE runner for target and draft, BF16 KV cache, TileLang DSA prefill and decode; full command below. Workload: 503 LongBench-v2 documents cut to their first 8,000 tokens plus the question (median prompt 8,156 tokens), 1,024 output tokens, all requests sent at once (64, 128 and 256 requests). Each repetition restarts the server for both versions and alternates which runs first; medians. Main's own restarts differ by at most 0.4% in steady-state decode.

Steady-state decode reads the server's own decode log lines while every attention rank decodes the same number of requests with nothing queued, so it is comparable to a decode-only node; node throughput is the sum over the 8 ranks. At 256 requests (32 per GPU) no decode line had all 32 running with nothing queued, so that load appears only in the burst table.

**Steady-state decode (+% = this PR better)**

| Requests (per GPU) | main, node tok/s | this PR, node tok/s | throughput | decode step | accept length (main / this PR) |
|---|---|---|---|---|---|
| 64 (8) | 8,357 | 8,783 | **+5.1%** | 23.93 -> 23.06 ms (**3.6% shorter**) | 3.18 / 3.22 |
| 128 (16) | 14,121 | 15,014 | **+6.3%** | 28.72 -> 27.01 ms (**6.0% shorter**) | 3.19 / 3.19 |

The next table is the whole run as the benchmark client reports it, the first prefills included: **3.2–4.4% higher output throughput and 3.5–8.2% lower median ITL (inter-token latency).**

**Whole request burst (+% = this PR better)**

| Requests | main, output tok/s | this PR, output tok/s | output throughput | median ITL |
|---|---|---|---|---|
| 64 | 4,087 | 4,218 | **+3.2%** | **3.5% lower** |
| 128 | 5,095 | 5,319 | **+4.4%** | **5.7% lower** |
| 256 | 4,900 | 5,066 | **+3.4%** | **8.2% lower** |

A profile of 8 decode steps at 128 requests confirms which kernels run: **`kernel_cutlass_kda_decode_mtp_kernel` once per KDA layer and verify on every rank with this PR and no `causal_conv1d_update` or `fused_sigmoid_gating_delta_rule_update`; main shows the reverse.**


**Startup and memory: only a one-time compile.** Both builds have the same KV-cache capacity and the same verify CUDA-graph memory (1.40 GB with ReplaySSM, 2.00 GB for TP8). The first start with an empty CuTe kernel cache takes longer to capture the verify CUDA graphs because it compiles the CuTe kernels: 31.8 s instead of about 14 s with ReplaySSM (+18 s), and 57.6 s instead of about 16.6 s for TP8 with `nv_cutedsl` (+41 s), against a main whose Triton kernels were already cached. The compiled kernels persist in the existing CuTe kernel cache (`SGLANG_CUTE_AOT_CACHE_DIR`, default `{SGLANG_CACHE_DIR}/cute_aot`), which SM100 uses the same way, so later starts match main: 13.2 s vs 12.1–15.8 s with ReplaySSM, 16.1 s vs 16.0–17.1 s for TP8.
