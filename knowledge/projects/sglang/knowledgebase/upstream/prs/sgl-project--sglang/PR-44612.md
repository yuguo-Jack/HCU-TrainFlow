# [Perf] [NVIDIA] KDA: Extend the CuTe DSL MTP verify kernel to SM90

[Upstream PR](https://github.com/sgl-project/sglang/pull/44612) · state: open · merged: False

## Original PR description

Co-authored-by: @HanHan009527

## Summary

**TL;DR: This PR lets the fused CuTe DSL KDA verify kernel run on Hopper (SM90).** Today it does not compile for SM90 and the gate admits only SM100 / SM103, so SM90 always runs the Triton path, even with `--linear-attn-verify-backend nv_cutedsl`. This PR replaces the kernel's two SM100-only packed FP32 instructions with scalar FP32 math on SM90 and admits SM90 in the gate for verifies inside CUDA graphs; an eager verify on SM90 keeps Triton. GLM-5-Next now defaults to the kernel on SM90 with ReplaySSM, and Kimi-K3, whose speculative-decoding defaults already request it, now passes the gate on Hopper. SM100 is unchanged.

- **Performance** (GLM-5.3-Flash on H200, attention DP8, ReplaySSM): **steady-state decode throughput +2.7–6.5%** and **TPOT 3.0–6.0% lower** at 64 and 128 concurrent requests; at the load ends, steady-state TPOT is **5.1% lower for a single request** and **10.5% lower at the heaviest load measured** (63 running requests per GPU, **+11.7% throughput**). On H20 with the same configuration, whole-run output throughput is **+1.6–5.2%** at 64–256 requests with MTP 3/1/4 and **+2.5–7.0%** at 128 requests with MTP 5/1/6 ([H20 results](https://github.com/sgl-project/sglang/pull/44612#issuecomment-6321851933)). Per KDA layer with ReplaySSM, the kernel alone runs the verify **1.7–2.3x** faster than main's Triton path for GLM-5-Next shapes and **2.0–3.0x** for Kimi-K3's Hopper shapes.
- **Accuracy: effectively lossless.** Kernel outputs match the Triton path to **about one BF16 rounding step** across 35 shapes, and GSM8K stays **within one standard error** of main (**97.08% → 97.27%** with ReplaySSM).
- **Cost:** **no new flags and no memory change**; only a **one-time 18–41 s** CuTe compile on the first start, as on SM100, cached for later starts.

## Motivation

#32890 added the fused CuTe DSL KDA (Kimi Delta Attention) verify kernel, #32541 made it the `nv_cutedsl` verify backend for Kimi-K3's speculative decoding, and #42905 made it GLM-5-Next's default verify backend on SM100. For each KDA layer of a target verify (the step that checks the MTP (multi-token prediction) or DSpark draft tokens), one kernel replaces main's default Triton path (`causal_conv1d_update` and the gated delta-rule recurrence as separate kernels) and keeps the recurrent state in registers across the draft tokens. With ReplaySSM spec-verify (`--enable-linear-replayssm-spec`), which replaces the verify's per-draft full-state snapshots with a per-slot window of raw inputs (the ReplaySSM ring), the same kernel also writes that ring in the same pass.

Hopper cannot use it today. The recurrence uses two packed FP32 instructions, `cute.arch.mul_packed_f32x2` and `cute.arch.fma_packed_f32x2` (each does two FP32 multiplies or two FP32 FMAs at once), which NVVM accepts only for SM100 and newer (`F32x2 intrinsics are not supported on this architecture` for `sm_90a`), and `_can_run_dspark_cutedsl_mtp` admits only capability major 10. So on SM90 the gate falls back to Triton without a message: every KDA layer of every target verify runs the unfused Triton kernels, which are markedly slower, above all with ReplaySSM (per-layer table below). This hits Kimi-K3, whose model defaults ask for the fused kernel on every GPU whenever speculative decoding is on, and every server that passes `--linear-attn-verify-backend nv_cutedsl`. On Hopper both silently get the slower Triton path instead of the kernel they asked for: Kimi-K3's startup log even says it pins `nv_cutedsl` and "uses the fused Kimi-K3/DSPARK CuTeDSL kernel", and nothing logs the fallback.

## Modifications

**Only SM90 changes: on SM100 / SM103 the kernel runs main's code unchanged, and the gate and GLM-5-Next's default behave as before.** The two packed FP32 instructions, `cute.arch.mul_packed_f32x2` and `cute.arch.fma_packed_f32x2`, are the only Blackwell-specific part of the kernel, and the GDN ReplaySSM verify kernel vendored from FlashInfer (`cutedsl_gdn_mtp_ring.py`, #33102) already guards the same two instructions with a `use_packed_fma` switch, so this PR adds the same switch, admits SM90 in the gate and extends GLM-5-Next's default:

- **`python/sglang/kernels/ops/attention/kda_decode_mtp.py`** (`fused_kda_decode_mtp_dspark`) -- a `USE_PACKED_FMA` compile-time constant (capability major >= 10) keeps the packed instructions on SM100 and newer (that branch is main's code verbatim), and uses scalar FP32 multiplies and multiply-adds on SM90, at the 4 call sites in the recurrence (1 `mul_packed_f32x2`, 3 `fma_packed_f32x2`). The capability was already part of the kernel's compile cache key.
- **`python/sglang/srt/layers/attention/linear/kda_backend.py`** -- `_can_run_dspark_cutedsl_mtp` accepts capability major 9 as well as 10. On SM90 it also requires CUDA graph capture mode (`get_is_capture_mode()`, which covers the graph runner's warm-up runs, where the kernel compiles), so an eager verify on SM90 keeps Triton: outside CUDA graphs the verify is bound by host launch time, and the CuTe launch takes longer than Triton's (eager table below). The gate reads the architecture from the cached `current_arch()`.
- **`python/sglang/srt/arg_groups/glm5_next_hook.py`** -- GLM-5-Next's speculative-decoding default `--linear-attn-verify-backend nv_cutedsl` ([#42905](https://github.com/sgl-project/sglang/pull/42905)) now also applies on SM90 when `--enable-linear-replayssm-spec` is on.
- **Tests**
  - Three existing kernel tests now also run on CI's `1-gpu-large` (H100) runner and no longer skip SM90: `test_kda_mtp_cutedsl_replayssm_ring.py` (ReplaySSM parity, the fused output-norm option, CUDA-graph padding requests), `test_kda_decode_mtp.py`, and `test_kda_decode_mtp_slot_stride.py`. On main the last one is registered only for the RTX 5090 (SM120) runner, where its SM100-only skip always applies.
  - The new `test_nv_cutedsl_verify_matches_triton` (in `test_kda_fused_verify_backend.py`) runs the real backend with `nv_cutedsl` (in capture mode, as the CUDA graph runner does) and with `triton`, checks that the CuTe kernel ran, and compares the outputs and every per-step SSM state; on SM90 it also checks that an eager verify takes the Triton path.
  - CPU tests (in `test_kda_helion_dispatcher.py`) pin the gate (SM100 admitted, SM90 admitted only in capture mode, SM80 and SM120 rejected) and the GLM-5-Next default (SM90 with and without ReplaySSM, SM100).
  - Running this PR's tests against main's kernel and gate on H200, the three kernel tests fail to compile for `sm_90a` (`F32x2 intrinsics are not supported on this architecture`) and the new parity test finds that the CuTe kernel never ran; with this PR all four test files pass.

To opt out, `--linear-attn-verify-backend triton` selects the Triton verify path on any GPU, which is what SM90 ran before this PR.

## Accuracy Tests

**Effectively lossless: GSM8K stays within one standard error of main, and the kernel's outputs match the Triton path to about one BF16 rounding step.** The kernel computes the same FP32 recurrence; on SM90 only the instruction form changes.

### End to end: GSM8K

`sgl-eval run gsm8k --num-threads 32 --max-tokens 32768` (sgl-eval 0.1.2, all 1,319 questions, temperature 0, top_p 0.95, the chat template's defaults, no errors), GLM-5.3-Flash on H200; MTP a/b/c = draft steps / top-k / tokens per verify. One standard error is about 0.46 points.

| Configuration | main | this PR |
|---|---|---|
| Attention DP8, ReplaySSM, MTP 3/1/4 (where this PR changes the default) | 97.08% | 97.27% |
| TP8, MTP 5/1/6 (this PR with `--linear-attn-verify-backend nv_cutedsl`) | 97.19% | 97.04% |

The TP8 GSM8K builds also carry the MoE dispatch fix from #40498, which merged into main after the measured base; without it, expert-parallel TP8 crashes partway through GSM8K on that base, with or without this PR. The ReplaySSM GSM8K builds also carried #43659 (since closed without merging), so there the kernel fused the gated output norm; without it the kernel's output goes through main's separate norm, a path the kernel-level check below also covers.

### Kernel level: 35 shapes on H200

The reference is a different kernel (main's Triton path) and the output is BF16, so the two agree to BF16 rounding, not bit for bit. Across 35 shapes (3 to 64 KDA heads per GPU, 2 to 8 tokens per verify, with and without ReplaySSM, with and without the kernel's fused output norm), **every output is within 1.03e-2 of the Triton path** (max absolute difference / max absolute reference value), every per-step SSM state within 6.8e-4 and every ReplaySSM ring entry within 4.7e-4; neither path writes the persistent SSM state during the verify.

## Speed Tests and Profiling

**With ReplaySSM, this PR's steady-state decode is 2.7–6.5% faster at 64–128 requests and 11.7% faster at 63 running requests per GPU.** This measures the configuration where this PR changes the default (builds under "Commands and builds" below). GLM-5.3-Flash on H200: `--tp-size 8 --ep-size 8 --attn-dp-size 8`, `--enable-linear-replayssm-spec`, EAGLE MTP 3/1/4, MegaMoE all-to-all with the DeepGEMM MoE runner for target and draft, BF16 KV cache, TileLang DSA prefill and decode; full command below. Workload: 503 LongBench-v2 documents cut to their first 8,000 tokens plus the question (median prompt 8,156 tokens), 1,024 output tokens, all requests sent at once (64, 128 and 256 requests), after two untimed warm-up bursts. Server restarts alternate between the two versions; the tables show the median and, in parentheses, the range over the restarts. In steady-state decode, every restart of this PR is faster than every restart of main.

Steady-state decode uses the server's own decode log lines: for each attention rank, only the lines where that rank decodes all of its requests with nothing queued, so it is comparable to a decode-only node; node throughput is the sum of the 8 ranks' medians, and TPOT is #running-req / gen throughput from the same lines (the time per output token of each running request), the median over the 8 ranks. At 256 requests (32 per GPU) no decode line had all 32 running with nothing queued, because the KDA state pool has 32 slots per GPU with `--max-running-requests 256`; the load-end table below raises that limit.

**Startup and memory: only a one-time compile.** Both builds have the same KV-cache capacity and the same verify CUDA-graph memory (1.40 GB with ReplaySSM, 2.00 GB for TP8). The first start with an empty CuTe kernel cache takes longer to capture the verify CUDA graphs because it compiles the CuTe kernels: 31.8 s instead of about 14 s with ReplaySSM (+18 s; about +19 s on H20), and 57.6 s instead of about 16.6 s for TP8 with `nv_cutedsl` (+41 s), against a main whose Triton kernels were already cached. The compiled kernels persist in the existing CuTe kernel cache (`SGLANG_CUTE_AOT_CACHE_DIR`, default `{SGLANG_CACHE_DIR}/cute_aot`), which SM100 uses the same way, so later starts match main: 12.0–13.2 s vs 11.6–15.8 s with ReplaySSM, 16.1 s vs 16.0–17.1 s for TP8.

## Scope and limitations

- **Measured:** GLM-5.3-Flash on H200 end to end, with ReplaySSM (attention DP8, MTP 3/1/4; where this PR changes the default; from 1 request to 63 running requests per GPU) and without it (TP8, MTP 5/1/6, with `nv_cutedsl`); GLM-5.3-Flash on H20 end to end with ReplaySSM (attention DP8, MTP 3/1/4 and 5/1/6); the kernel alone on H200 for 35 shapes.
- **Same backend gate and kernel, not measured end to end:**
  - Kimi-K3 on Hopper, which needs more GPUs than the single 8-GPU node used here. Its [Hopper cookbook commands](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3) default to DSPARK (block size 7) with ReplaySSM; every gate input was checked against the model code, the published `config.json` and those flags, and its shapes are in the kernel table.
  - GLM-5-Next with other speculative algorithms when ReplaySSM is on.
  - H100, which runs the same `sm_90a` code; three of this PR's test files now also run on CI's H100 runner.
- **Not affected** (these keep main's behavior):
  - SM100 / SM103: same instructions and defaults as before.
  - SM110 and SM12x: the gate still rejects them.
  - ROCm, CPU, NPU and XPU: the gate checks `is_cuda()` first.
  - GLM-5-Next on SM90 without ReplaySSM, unless `nv_cutedsl` is passed: Triton stays the default.
  - `--linear-attn-verify-backend triton`.
  - An eager verify on SM90 (outside CUDA graphs): it keeps Triton.
  - Every batch the gate rejects, which keeps the Triton path: for example ragged verify layouts, tree drafts, fewer than 2 or more than 8 tokens per verify, a non-FP32 SSM state, or Kimi-Linear's layers without a gate lower bound.
- **Open question:** whether GLM-5-Next on SM90 should also default to `nv_cutedsl` without ReplaySSM; in the TP8 test above it lowers TPOT at 1–4 concurrent requests and raises it slightly at 16–64.

## H20 results

Tested this PR on one 8×H20 node with GLM-5.3-Flash, attention DP8, ReplaySSM, BF16 KV, TileLang DSA, MegaMoE/DeepGEMM and full target-verify CUDA Graph. Both sides used the same source tree containing #44262, #43659 and #44612; the only A/B change was `--linear-attn-verify-backend triton` versus `nv_cutedsl`.

Software: Torch 2.14.1+cu130, CUDA 13.0, nvidia-cutlass-dsl 4.8.0. Workload: all 503 LongBench-v2 records, first 8,000 context tokens plus the question (median rendered prompt 8,149 tokens), fixed 1,024 outputs. This dataset was regenerated from THUDM/LongBench-v2 revision `2b48e494...` according to the PR description and is not claimed byte-identical to the original H200 JSON.

### ReplaySSM, MTP 3/1/4

Two interleaved B0/C0 pairs completed with 100% success, exact 1,024 outputs, all ranks at the requested BS, queue 0, and CUDA Graph execution:

| Requests | Triton output tok/s range | CuTe+norm output tok/s range | Paired gains |
| ---: | ---: | ---: | ---: |
| 64 | 2,102.72–2,106.40 | 2,137.81–2,141.58 | +1.67%, +1.67% |

| 256 | 2,559.25–2,631.70 | 2,674.34–2,691.69 | +5.17%, +1.62% |

The candidate range was above the control range at every load. Median and p99 TPOT also improved in every paired run. Accept-length deltas were small (−0.019 to +0.038), so they do not explain the direction.

### ReplaySSM, MTP 5/1/6

At 128 requests, two independent pairs measured 2,234.24→2,390.40 tok/s (+6.99%) and 2,318.08→2,374.82 tok/s (+2.45%). Median TPOT improved by 8.19% and 2.98%; p99 TPOT improved by 5.89% and 2.92%. All requests completed and all correlated rank logs showed BS16, queue 0 and CUDA Graph execution.

### Dispatch and quality

Across 8/8 rank traces, Triton had 272 conv + 272 delta-rule launches and no CuTe target-verify launch; the candidate had 272 CuTe target-verify launches and no Triton conv/delta launches. Target norm fusion also reduced `layer_norm_gated` from 544 to 272 launches per rank.

Targeted H20 backend/ring/state tests passed. A fixed GSM8K-100 smoke was 90/100 for Triton and 94/100 for the candidate (6 paired wins, 2 losses); this is limited smoke coverage, not a claim of quality improvement. The physical-H20 eager component harness was slower than Triton (CuTe+fused norm: 1.31–2.04× slower for T4 and 1.47–2.04× slower for T6), so that microbenchmark did not predict the warmed CUDA Graph serving result and is retained as a diagnostic caveat. The first CuTe Graph capture added ~19 s; later warmed captures matched control closely. No memory-capacity change or OOM was observed.
