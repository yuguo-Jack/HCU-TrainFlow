# [Fix] state_capturer: Prevent routed-expert capture overflow during unchunked prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/47248) · state: open · merged: False

## Original PR description

## Motivation

`RoutedExpertsCapturer` sizes its device buffer as

```python
max(chunked_prefill_size * num_dp_ranks, max_running_requests * num_dp_ranks)
```

`BaseDeviceCache.capture` writes `buffer[:topk_indices.shape[0]]` with no bounds check, so the buffer
has to hold the most rows any single forward can route. The first term assumes chunked prefill is on.
`--chunked-prefill-size -1` is a supported setting and some model hooks select it; with `-1` the term
goes negative and only the decode bound survives. That is #26860: the config allocated 2048 rows, one
forward routed 8192, and the step died on a shape mismatch instead of returning routings.

`max_prefill_tokens` is not a usable replacement ceiling because it is a scheduling budget, not a
limit -- `PrefillAdder` admits the first request of a batch even past it. On that same config a
24576-token request is accepted and still overflows a 16384-row buffer.

## Changes

Bound the prefill term by `max_req_len`, the longest request the engine accepts
(`min(context_len - 1, kv_capacity - 1)`, enforced by `validate_input_length`), which is what actually
limits a forward once chunking is off. It was already derived inline in `TpModelWorker.get_worker_info`
and becomes a `ModelRunner` property, so the capturer and the worker-info report read one value.

```python
if chunked_prefill_size and chunked_prefill_size > 0:
    prefill_rows = chunked_prefill_size
else:
    prefill_rows = max(max_prefill_tokens, max_req_len)
return max(prefill_rows, max_running_requests) * num_dp_ranks
```

Without chunking a forward is either budget-limited (page-ceiled extend and replay under
`max_prefill_tokens`) or exactly one request under `max_req_len`, so the max of the two covers the
path. The `else` branch is the engine's own fallback shape, not a new one:
`pre_capture_activation_reserve_mb` (`runtime_context.py:1798`) switches on `chunked_prefill_size > 0`
and falls back to `max_prefill_tokens` at :1810-1813. The nearby helper `max_prefill_buffer_tokens()`
(:1779) can't replace the bound -- it folds a non-positive `chunked_prefill_size` to 0 (:1784-1788),
which is the same budget-not-a-limit gap as above. Spec-decode verify rows and the scattered-a2a width
multiplication are pre-existing and stay out.

`IndexerTopkCapturer` had the same missing term in the same expression, so it shares the bound:
`device_cache_rows` moved to `state_capturer/base.py` and the indexer calls it with `num_dp_ranks=1`,
since its capture is per-rank-local.

#38717 edits the same two source files and the same `max(...)`, but the other arm: it widens the decode
term for spec-verify rows and clears the `FIXME` about `num_verify_tokens`. The two arms are orthogonal,
so whichever merges first the other still adds a term it leaves out; the `FIXME` stays for #38717.

## Tests

`test/registered/unit/state_capturer/test_device_cache_sizing.py` (new, CPU tensors only,
`base-a-test-cpu`) covers the bound over a table of configs, equality with today's expression for
chunked configs (18 combinations), `max_req_len` reaching the budget through both capturers'
constructors, and capture at the bound with 8192, 16384 and 24576 rows -- the last two past
`max_prefill_tokens`, which is the case that used to overflow. Measured `Ran 7 tests ... OK`, plus
`Ran 4 tests ... OK` for `test_npu_indexer_topk_capturer.py` and `Ran 6 tests ... OK` for the existing
`test_routed_experts_scattered_a2a.py`; both needed the new keyword at their call sites. Negative
control: swapping `device_cache_rows` back to the expression on main turns the same suite into
`FAILED (failures=3, errors=5)`, including the two indexer cases.

The overflow itself is reproduced at buffer level on #26860's shape (48 layers, top-8) by driving
`BaseDeviceCache` with CPU tensors -- not an engine run:

```text
decode term only   rows= 2048  capture(8192)  -> RuntimeError, expanded size 2048 vs 8192
budget only        rows=16384  capture(24576) -> RuntimeError, expanded size 16384 vs 24576
this patch                   capture(24576) -> OK
```

No accuracy or speed results: with chunking on the bound is the same number as today, so nothing that
works today changes; with chunking off the current behavior is a crash, so there is no baseline to diff
against.

## Memory impact

int32 `[rows, 48, 8]` is 1.5 MiB per 1024 rows. `--enable-return-routed-experts` is opt-in and chunked
configs are unchanged, so only unchunked runs grow, and the growth tracks the engine's own request cap.

| config (DP 1, 48 layers, top-8) | rows today | rows with patch | device buffer |
| --- | --- | --- | --- |
| chunked 8192, budget 16384 | 8192 | 8192 | 12.00 MiB, unchanged |
| `-1`, budget 16384, request cap 8191 | 2048 | 16384 | 3.00 -> 24.00 MiB |

The indexer buffer is `[rows, num_indexer_layers, index_topk]` int32, so a row costs
`num_indexer_layers * index_topk * 4` B -- 488 KiB for a DSA shape (61 indexer layers, `index_topk`
2048) against 1.5 KiB for routed experts. It is behind its own opt-in flag and chunked configs are
unchanged, but on the unchunked row above that buffer goes 0.95 -> 7.63 GiB, where the default chunked
8192 already costs 3.81 GiB today. Both capturers allocate after the KV pool is sized, so the extra
comes out of the remaining headroom rather than the pool's.
