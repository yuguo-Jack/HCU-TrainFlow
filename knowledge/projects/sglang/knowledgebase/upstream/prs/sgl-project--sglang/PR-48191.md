# [Feat] diffusion/realtime: Add a client-side benchmark for realtime video sessions

[Upstream PR](https://github.com/sgl-project/sglang/pull/48191) · state: open · merged: False

## Original PR description

## Motivation

`bench_serving.py` covers the HTTP video and image APIs. Nothing measures a `/v1/realtime_video/generate` session from the client side. The server's `chunk_stats` report per-chunk compute. The realtime web UI shows an event cutover time. Neither gives a repeatable number for what a viewer waits for:

- how long until the first frame arrives;
- how long after a control event (camera action, prompt update) the first frame that answers it arrives;
- the frame rate that actually reaches the client, and whether chunks stall.

## Modifications

- `benchmarks/bench_realtime.py` runs one or more realtime sessions one after another, since the server admits one active session. It sends `init` (fields from a JSON file, optional `--first-frame` image) and an optional event template every `--event-every` chunks with an increasing `event_id`. It reports:
  - time to first frame, from sending `init` to the first non-empty frame batch;
  - event latency, from sending event N to the first frame batch whose header echoes `event_id` N;
  - delivered fps after the first frame, chunk inter-arrival gaps and stalls (gaps longer than `--stall-factor` × the median);
  - the median server `scheduler_forward_ms` and `chunk_total_ms`.

  The first `--warmup-sessions` sessions are discarded (compilation, cache allocation). `--json` prints per-session results.
- `test/unit/realtime/test_bench_realtime.py` covers the metric arithmetic on a fixed timeline, a session with no frames, and a full session against an in-process fake realtime server.

## Accuracy Tests

No model or server change. The unit tests pass locally (3 passed).

## Speed Tests and Profiling

1× H100 80GB, `lmsysorg/sglang:v0.5.23` (`297e54f`), serving `robbyant/lingbot-world-fast-diffusers` with the flags of the `lingbot_world_realtime_plastic_beach` CI case (`--text-encoder-cpu-offload --pipeline-class-name LingBotWorldCausalDMDPipeline --warmup-mode off`). The init matches that case: 832×480, 4 steps, sink 9, KV window 18. Each row is 3 measured sessions of 12 chunks, after 1 warmup session. The event is `camera_actions` `[["d"], ["d"], ["d"]]`.

| Events | First frame (median) | Event → frame (median / p90) | Delivered fps | Server `chunk_total_ms` (median) | Stalls |
|---|---|---|---|---|---|
| every 2 chunks | 1724 ms | 4846 / 4881 ms (15 events) | 5.33 | 2428 ms | 0 |
| every chunk | 1715 ms | 4854 / 4879 ms (30 events) | 5.25 | 2431 ms | 0 |
| none | 1714 ms | – | 5.98 | 2132 ms | 0 |

Unanswered events are the ones sent after the last chunk (one per session in the first row, two in the second).

Two things the server-side numbers do not show:

- Event latency is about two chunks (4.85 s against a 2.43 s chunk), whatever the event rate. `_generate_loop` prepares chunk N+1 as soon as chunk N's forward returns and sends chunk N in the background, so an event sent after the viewer receives chunk N is first sampled by chunk N+2.
- Sessions that send camera actions run about 300 ms slower per chunk than sessions without them (2.43 s against 2.13 s).
