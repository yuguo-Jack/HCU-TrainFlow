# [Feat] multimodal: Add bounded GPU feature publication admission

[Upstream PR](https://github.com/sgl-project/sglang/pull/47769) · state: open · merged: False

## Original PR description

## Summary

Add opt-in, bounded admission for CUDA IPC/VMM feature publication. Related to #43402; this does **not** claim to fix its CUDA-driver hang or bound upstream GPU preprocessing.

- Reserve the whole publication batch atomically (including alignment, fragmentation and IPC control slots); wait without holding partial slices or occupying the copy worker.
- `--mm-admission-timeout-ms 0` rejects on pressure; positive values wait up to the deadline. Oversized batches return 413, temporary pressure 429. HTTP/OpenAI/SSE and Python/Rust gRPC preserve these errors.
- Keep reservations and source ownership until native copy completion, including cancellation and failed dispatch. Preserve generation/ACK semantics and existing VMM packing.
- Add pool/pending/lease-lifetime diagnostics and concise VLM/argument/K3 documentation.

Unset preserves existing behavior. No default transport/backend change, extra HBM pool, silent CPU fallback on the guarded path, or EPD/PD support.

## Development validation

Isolated NVIDIA B200, driver 580.126.09, PyTorch 2.14.1+cu130, Transformers 5.19.0; production head `db2fb5d0a319a3c4cac2734315c414c166bf69ac`:

- 661 CPU tests + 494 subtests and 10 CUDA IPC / single-device POSIX-VMM tests passed (exit 0). A CUDA IPC process-teardown warning remains recorded, not claimed resolved.
- Python gRPC boundary tests and 19 Rust `sglang-grpc` tests passed; workspace Clippy passed with the pinned Rust toolchain. Subsequent changes do not modify Rust/gRPC code.
- Real-weight Qwen2.5-VL-3B (revision `66285546d2b821cf421d4f5eb2576359d3770cd3`) IPC and Qwen3-VL-2B (`89644892e4d85e24eaac8bacfd4f463576704203`) POSIX VMM: normal requests, multi-image/color checks, 413/429 under a 2 MiB pool, idle drain and successful recovery passed.
- Both transports passed three 16-request rounds of actual abort, pool/pending drain, cache flush and a successful subsequent image request.
- Cookbook configuration, MDX build and link validation passed.

### Performance gate — draft, not a recommended default

Same-commit opt-in/off IPC replay: 64 MiB pool, cache off, CUDA graphs off, 448-square image, up to 8 output tokens, concurrency 1/8. Per mode: 96 warmups per concurrency, then 3 x 256 measured requests per concurrency; all 1,539 recorded requests succeeded, plus 192 unrecorded warmups.

Guarded-first order at `db2fb5d0`:

| Concurrency | Legacy median RPS (range) | Guarded median RPS (range) |
|---|---:|---:|
| 1 | 24.341 (24.202–24.514) | 24.252 (24.156–24.572) |
| 8 | 112.907 (112.402–116.162) | 102.148 (101.094–110.191) |

Concurrency-8 throughput regresses about 9.53%; an earlier legacy-first replay also regressed. This exceeds the 3% acceptance target and remains a merge-readiness gate. These are E2E serving measurements, not TTFT or a universal speedup claim.

A second matched replay with two processor workers per mode also completed with all requests successful: concurrency-8 median 108.890 RPS (104.738–110.196) legacy vs 104.826 RPS (98.377–105.975) guarded, a 3.73% regression. Increasing processor concurrency does not establish that the performance gate is met, and does not replace the default-worker result above.

Not validated: full Kimi-K3, multi-node FABRIC/MNNVL, multi-tokenizer-worker/session serving, or incident-shaped long soak. Pre-decode/native-memory budgeting remains a separate follow-up; accounting only torch tensors would miss native decoder workspace.
