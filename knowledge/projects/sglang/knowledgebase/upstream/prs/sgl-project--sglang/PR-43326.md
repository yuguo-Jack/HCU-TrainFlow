# [unified-memory] Fuse MTP drafts with sliding-window and recurrent-state layers

[Upstream PR](https://github.com/sgl-project/sglang/pull/43326) · state: open · merged: False

## Original PR description

**Stack:** #42930 → #43168 → #43169 → #43170 → #43171 → #43325 → this PR. Merge it after those; until they land, its diff against main also shows their commits. This PR's own changes are its top eight commits, `bea47a72c6` through `328cc684e9` (43 files, +3,744/−339).

## Motivation

Under `--enable-unified-memory` a speculative draft's KV lives inside the target's pages (a fused draft), but only a draft whose layers are all full-attention can fuse: it goes into the full-attention sub-pool. An MTP head with sliding-window layers (MiMo-V2-Flash) or with recurrent state (Inkling's per-depth conv-chain head) declines, and on a hybrid-SWA or mamba host main then refuses the boot ("needs the draft's KV fused into the target's pages, but this draft cannot fuse"). So neither model can run NEXTN with `--enable-unified-memory`.

## Modifications

1. **Place fused drafts through a host-kind registry** (`51e8c198f1`). A placement separates what the draft has (full-attention, sliding-window and state layers) from what a sub-pool can carry (a `HostKind`, keyed by sub-pool name). `place_fused_draft` walks the registered kinds over the sub-pools the target builds; regions and per-runner lanes are keyed by host. Only "full" is registered in this commit, so every draft places or declines exactly as before.
2. **Register the "swa" host kind** (`df2d823e83`). A draft's sliding-window layers fuse into the target's sliding-window sub-pool when the draft's window is no wider than the target's; otherwise they fold into the full sub-pool with their own geometry, or the draft declines when the geometries differ. The sliding-window sub-pool now retains what the draft reads: a multi-layer MTP draft's widened extend starts a few front rows below the committed length, so `CacheInitParams.swa_retain_window` takes the wider of the target's window and the draft's reach; only the paths that free or unlock a running request's window read it. Window layers fuse only on the Triton multi-step draft backend, the one that builds per-step window rails. The draft worker binds `UnifiedDraftSWAKVPool`, routed per layer like the target's composite. A multi-layer draft plans each draft extend once, through its first depth's runner, and a later depth can route window layers the first one does not: `KVLocPlan.has_read_table` and `read_table` now resolve the sub-pool through the reader, as `write_ids` already does, so every depth still shares one table per sub-pool.
3. **Register the "mamba" host kind** (`9ed6955590`). A per-depth conv-chain MTP head's recurrent state goes into the mamba sub-pool, laid out after the host's own streams in each slot entry. `UnifiedMambaPool.clear_slots`, `copy_from` and `move_kv_cache` act on whole entries, so a radix checkpoint, a slot reset and a compaction move carry the draft's state with the target's. The draft binds `UnifiedDraftMambaPool`, whose own slot ops reset the draft block on decode and draft extend. The boot solve prices the fused entry.
4. **Per-step sliding-window read rail for the multi-step draft** (`83aa763160`). A draft's window layer at step s attends the last `min(seq_len + s + 1, window)` tokens of its own chain, which no existing builder produced: a window draft layer reached the Triton decode kernel without window indices. `generate_draft_decode_window_kv_indices` is the window-clipped sibling of `generate_draft_decode_kv_indices`, reads the iteration's sliding-window read source the same way, and fills both an eager buffer and a persistent buffer for CUDA graph replay; the captured draft extend builds the rail too.
5. **Per-step sliding-window write target** (`4ae03f33cd`). Each per-step backend took its sliding-window write ids as a prefix of the whole draft window, which is laid out step-minor per row, so eager window writes landed in other steps' slots and the captured path had no target. Each step now binds its own columns of the iteration's write window in eager, capture and replay.
6. **Three fixes that also affect the default pool.** The Triton extend kernel narrows its int8 custom mask to i1 before combining it (`bea47a72c6`): with both a custom mask (speculative verify) and a `score_mod` (Inkling's relative bias), Triton failed to build the kernel. `SWAKVPool.get_v_head_dim` answers from whichever side has layers (`760e2184c9`): an MTP depth whose block is sliding-window has an empty full side and raised `IndexError` at backend construction. The Inkling MTP head reports its window the way the trunk does (`328cc684e9`): it ran one token wider than the trunk's window layers.

Tests (CPU unless noted): window, state and fold placement rows, including the declines; per-runner binding against a clipped config; the translator handing a fused draft the target's sliding-window write ids and window table byte for byte, including from a plan a dense first depth built; the retained window on the radix cache, enabled and disabled; the fused state entry math and the whole-entry clear, copy and move; the window rail kernel against a reference, at page sizes 1 and 2 and topk 1 and 2 (CUDA); each draft step's sliding-window write ids; and the head's window convention (CUDA).

## Speed Tests and Profiling

`bench_serving`, unified pool against the default pool, which runs twice per configuration; the spread of its two runs (A/A) is the noise floor.

**The drafts this PR fuses**, same configurations as above with CUDA graphs on, under two load tests: 100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests that share a 4096-token system prompt, each with a 128-token question and 2048 output tokens, at concurrency 192.

MiMo's gain is the unified pool's capacity: either layer kind can take the bytes the default pool splits between them at boot. On Inkling-Small's 192 requests sharing a 4096-token prefix, serving traces at the same batch size show the unified pool's verify cycles 1.3% longer, all of it in the Triton attention kernel of the sliding-window layers (about 7% slower per call); the full-attention layers' kernel time is unchanged.

**Targets without speculation:** Qwen3.5-9B, 200 requests of 2048 input / 512 output tokens at concurrency 64, run back to back on one host with and without this PR. Unified-vs-default-pool req/s gap: −0.9% (fa3), −0.9% (triton), −0.9% (trtllm_mha) with this PR, against −0.7%, −0.6% and −0.8% without it; A/A at most 0.2%.
