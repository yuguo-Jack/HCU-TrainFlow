## Motivation

Under `--enable-unified-memory` a speculative draft's KV lives inside the target's pages (a fused draft), but only a draft whose layers are all full-attention can fuse: it goes into the full-attention sub-pool. An MTP head with sliding-window layers (MiMo-V2-Flash) or with recurrent state (Inkling's per-depth conv-chain head) declines, and for a hybrid sliding-window or Mamba-hybrid target, main then refuses to boot ("needs the draft's KV fused into the target's pages, but this draft cannot fuse"). So neither model can run NEXTN with `--enable-unified-memory`.

## Modifications

The Gemma4 graph and HiSparse registry test fixtures now follow the window-reader and retained-history interfaces.

Window layers build clipped decode indices whether placement uses FULL or SWA storage. Cache retention, locks, matching, replay floors and transfers share the widened draft history span in both Python and Rust TreeCore.

1. **Place fused drafts through a registry of sub-pool kinds** (`938efad6b4`). A placement separates what the draft has (full-attention, sliding-window and state layers) from what a sub-pool can carry (a `HostKind`, keyed by sub-pool name). `place_fused_draft` walks the registered kinds over the sub-pools the target builds; the draft's share of each sub-pool's entries, and which part of it each draft runner uses, are keyed by sub-pool. Only "full" is registered in this commit, so every draft places or declines exactly as before.
2. **Register the "swa" kind** (`dc703be11b`). A draft's sliding-window layers fuse into the target's sliding-window sub-pool when the draft's window is no wider than the target's; otherwise they fold into the full sub-pool with their own geometry, or the draft declines when the geometries differ. The sliding-window sub-pool now retains what the draft reads: a multi-layer MTP draft's extend starts a few tokens below the committed length, so `CacheInitParams.swa_retain_window` takes the wider of the target's window and the draft's reach; the tree's locks, prefix matching, backup/load-back and request retention all use that same span. Window layers fuse only on the Triton multi-step draft backend, the one that builds per-step sliding-window KV indices. The draft worker binds `UnifiedDraftSWAKVPool`, routed per layer like the target's composite. A multi-layer draft plans each draft extend once, through its first depth's runner, and a later depth can route window layers the first one does not: `KVLocPlan.has_read_table` and `read_table` now resolve the sub-pool through the reader, as `write_ids` already does, so every depth still shares one table per sub-pool.
3. **Register the "mamba" kind** (`696947f22f`). A per-depth conv-chain MTP head's recurrent state goes into the mamba sub-pool, laid out after the target's own state in each slot's entry. `UnifiedMambaPool.clear_slots`, `copy_from` and `move_kv_cache` act on whole entries, so a radix checkpoint, a slot reset and a compaction move carry the draft's state with the target's. The rebase preserves main's whole-page compaction copy and invokes sibling reset/copy callbacks for ShortConv and NGram state as well. The draft binds `UnifiedDraftMambaPool`, whose own slot ops reset the draft block on decode and draft extend. The memory sizing at startup counts the larger entry.
4. **Per-step sliding-window read indices for the multi-step draft** (`22c9d158b2`). A draft's window layer at step s attends the last `min(seq_len + s + 1, window)` tokens of its own chain, which no existing builder produced: a window draft layer reached the Triton decode kernel without window indices. `generate_draft_decode_window_kv_indices` is the window-clipped sibling of `generate_draft_decode_kv_indices`, selects FULL or SWA addresses through the runner's reader, and fills both an eager buffer and a persistent buffer for CUDA graph replay; the captured draft extend builds these indices too.
5. **Per-step sliding-window write target** (`dcb671120b`). Each per-step backend took its sliding-window write ids as a prefix of the whole draft window, which is laid out step-minor per row, so eager window writes landed in other steps' slots and the captured path had no target. Each step now binds its own columns of the iteration's write window in eager, capture and replay.
6. **Three fixes that also affect the default pool.** The Triton extend kernel narrows its int8 custom mask to i1 before combining it (`b3102250ff`): with both a custom mask (speculative verify) and a `score_mod` (Inkling's relative bias), Triton failed to build the kernel. `SWAKVPool.get_v_head_dim` answers from whichever side has layers (`a3f8458c59`): an MTP depth whose block is sliding-window has an empty full side and raised `IndexError` at backend construction. The Inkling MTP head reports its window the way the trunk does (`7ed6dfa304`): it ran one token wider than the trunk's window layers.

Tests (CPU unless noted): window, state and fold placement rows, including the declines; per-runner binding against a clipped config; the KV index translator handing a fused draft the target's sliding-window write ids and window table byte for byte, including from a plan a dense first depth built; the retained window on the radix cache, enabled and disabled; the fused state entry math and the whole-entry clear, copy and move; the window index kernel against a reference, at page sizes 1 and 2 and topk 1 and 2 (CUDA); each draft step's sliding-window write ids; and the head's window convention (CUDA).

## Speed Tests and Profiling

The measurements in this section are historical results from before this rebase, at the revisions/configurations stated below. Current combined-stack validation is linked above.

`bench_serving`, unified pool against the default pool, which runs twice per configuration; the spread of its two runs (A/A) is the noise floor.

**The drafts this PR fuses**, same configurations as above with CUDA graphs on, under two load tests (accept length as `bench_serving` reports it): 100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests that share a 4096-token system prompt, each with a 128-token question and 2048 output tokens, at concurrency 192.

MiMo's gain is the unified pool's capacity: either layer kind can take the bytes the default pool splits between them at boot. On Inkling-Small's 192 requests sharing a 4096-token prefix, serving traces at the same batch size show the unified pool's verify cycles 1.3% longer, all of it in the Triton attention kernel of the sliding-window layers (about 7% slower per call); the full-attention layers' kernel time is unchanged.
