# [Perf] cuda-graph: Capture FlashInfer KDA prefill with context parallelism

[Upstream PR](https://github.com/sgl-project/sglang/pull/45473) · state: closed · merged: True

## Original PR description

## Motivation

FlashInfer KDA breaks out of each prefill graph, leaving every KDA layer eager, including with context parallelism enabled.

## Modifications

- Capture FlashInfer KDA using per-bucket, per-layer `RecurrentKDAPrefillWrapper` plans. Refresh sequence lengths, state indices and radix-cache checkpoint mappings before replay; guard empty padded sequences and handle small buckets whose sequence-slot count would otherwise select decode.
- Size KDA graph metadata from global `extend_num_tokens`, since CP positions can describe only the local shard. Keep the selected FlashInfer backend; installations without the experimental wrapper retain the eager graph break.
- Extend the GPU regression to FlashInfer, multi-request replay, CP global token capacity, radix checkpoints, unused state slots and small buckets. Run it on Blackwell CI.

## Validation

The GPU results below were collected at `8f7d7cc9c7`, before restoring the original `memory_hook.py`. This PR no longer changes the MLA/DSA capture default (2048); reproducing the earlier 16384-token run requires an explicit capture-maximum override. GPU tests were not rerun for this exact restoration; pre-commit and base-file equality checks passed.

On `glm53-dev` (4× GB300):

- GPU KDA graph tests: **9 passed, 20 subtests passed**. The new small-bucket regression reproduced the original capture failure before the fix.
- Linear-attention configuration, FlashInfer adapter and Mamba checkpoint metadata tests: **23 passed, 113 subtests passed**.
- GLM-5.3-Flash + DFlash2, using `test_glm53_flash_cp.py` settings: **GSM8K 473/500 (94.6%)**, average speculative acceptance **4.862**, both image-input checks passed. Batched four-request outputs match individual requests exactly.
- Capture maximum in that validation run: **16384**, 74 prefill buckets captured successfully, approximately **31.98 GiB / 66.62 s** on TP0, with `mem_fraction_static=0.75`.
- Pre-commit and `git diff --check` passed.

**Integration scope:** GLM CP serving still depends on open #43182. The end-to-end run used this PR's `43aebae1e0` base plus this change and a temporary three-way integration of #43182 at `2aa855c0e8`. Those dependency changes are not included in this PR. The devbox has FlashInfer 0.7.1 with the experimental wrapper, PyTorch 2.14.1+cu130 and Triton 3.8.0; the wrapper is capability-gated because it is not present in every FlashInfer installation.

## Profiling

`bench_serving`: concurrency 4, ISL 1024, OSL 10, 160 requests, 20 target steps. **160/160 requests succeeded**, all requested lengths verified. The profile contains 7 prefill steps (actual scheduler batch sizes 1–3) and 13 verify steps, plus draft work.

All four rank traces confirm **34 FlashInfer KDA prefill kernels per prefill are associated with `cudaGraphLaunch` and nonzero graph IDs; zero KDA prefill kernels run eagerly**. Each prefill has **23 graph launches**, versus 57 in the earlier trace with 34 KDA breaks. FlashInfer's planned path uses one core kernel per layer; the earlier eager path used a prep/chain pair. This is graph-replay evidence, not a controlled throughput comparison. All four traces and logs were downloaded and their SHA-256 hashes verified.

- Fridge003 · comment · 2026-10-21T08:58:50Z · [source](https://github.com/sgl-project/sglang/pull/45473#issuecomment-6312110294)

GLM-5.3-Flash comparison against eager, following the fixed-continuation approach in #41400. This run additionally compares **the complete 154,880-token vocabulary at each position**, rather than treating selected-token logprob differences as exact KL.

**Setup:** 4×GB300, TP4/EP1, FlashInfer KDA prefill, TRT-LLM DSA prefill/decode, FlashInfer TRT-LLM MoE, FP8 E4M3 KV, default FP32 SSM state. Speculative decoding and decode CUDA graphs were disabled in all arms. The runtime combines #45473 at `d7426a7d99` with the CP support from #43182 at `2aa855c0e8`. Current #45473 head `70ae2f1750` only changes tests relative to that runtime. Model revision: `46a050bec13002ad29ee795c16e61cf4fa3c4a9c`; Torch 2.14.1+cu130, FlashInfer 0.7.1 with the experimental prefill wrapper, Triton 3.8.0.

**Inputs/method:** 32 LongBench-v2 contexts, eight each at prompt lengths 1024/3584/7680/15872. Generate 512 greedy continuation tokens once with eager, then teacher-force exactly those token IDs in every arm. Scoring prefill lengths are 1536/4096/8192/16384. Flush cache before every scoring request and verify `cached_tokens == 0`. The primary comparison uses BS1: **16,384 scored positions**. An additional BS4 check uses eight of the same sequences, with aggregate prefill sizes 6144 and 16384: **4,096 scored positions**. Capture ceiling 16384 and the five exact buckets were explicit experiment settings; this does not change the default capture limit.

A read-only observer copies logits from the eager LM-head tail, outside the captured model body. It returns the original logits unchanged and is disabled during trace collection. Saved logits were independently checked against the API's token logprobs; maximum alignment error was **7.35e-7**. KL uses float64 log-softmax and full-vocabulary summation:

`KL(P_eager || P_variant) = sum_v P_eager(v) * (log P_eager(v) - log P_variant(v))`

All values below are nats per scored position.

| Configuration | BS1 mean KL | BS1 p99 KL | BS1 max KL | BS4 mean KL |
| --- | ---: | ---: | ---: | ---: |
| no CP, BCG enabled, FlashInfer KDA **outside** BCG | 0.0205614 | 0.241198 | 13.2973 | 0.0149231 |
| no CP, BCG enabled, FlashInfer KDA **inside** BCG | 0.0213972 | 0.257803 | 12.8141 | 0.0160125 |
| interleave CP4, BCG enabled, FlashInfer KDA **inside** BCG | 0.0223550 | 0.243694 | 12.9691 | 0.0153601 |
| Control: repeat eager scoring in the same process | 0.0165804 | 0.194767 | 12.9025 | 0.00995240 |
| Control: restart eager and rescore | 0.0170379 | 0.182722 | 11.8344 | 0.00997516 |

BS1 mean KL by total prefill length (eight requests / 4096 scored positions per row):

| Total tokens | Eager repeat | Eager restart | no CP, KDA outside | no CP, KDA inside | CP4, KDA inside |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1536 | 0 | 0 | 0.0168183 | 0.0148123 | 0.0152357 |
| 4096 | 0.0249772 | 0.0239733 | 0.0251165 | 0.0295114 | 0.0277594 |
| 8192 | 0.00621537 | 0.00669612 | 0.00695572 | 0.00785857 | 0.00827280 |
| 16384 | 0.0351290 | 0.0374821 | 0.0333552 | 0.0334067 | 0.0381522 |

For the selected continuation tokens, mean absolute logprob differences versus eager are **0.0496913 / 0.0496394 / 0.0493533** for the three requested configurations, versus **0.0369836 / 0.0359466** for the two eager controls.

The change in mean BS1 KL to the common eager reference is **+0.0008358** when KDA is added to BCG, and **+0.0009578** when CP is additionally enabled. A paired bootstrap over whole requests (10,000 resamples) gives 95% intervals of **[-0.0006839, 0.0023361]** and **[-0.0011208, 0.0041356]**, respectively. These are differences of mean distances to the reference, not pairwise KL: the direct BS1 `KL(no-CP/KDA-out || no-CP/KDA-in)` is **0.0239597**, and `KL(no-CP/KDA-in || CP4/KDA-in)` is **0.0237306**.

**Interpretation:** the three requested configurations have similar mean KL on this sample, but this is not bitwise equivalence or a strict numerical-equivalence pass. Eager itself has nonzero long-input repeat/restart differences and substantial tails. At 1536 tokens, the eager controls are exactly zero while BCG already differs with KDA outside the graph, so that discrepancy cannot be attributed solely to the new KDA capture path. The current measurements do not isolate the operator responsible for those differences.

**Replay verification:** all four ranks were checked for four BS1 shapes and both BS4 shapes, **96 profiled prefill steps total**:

| Arm | Graph launches per step | FlashInfer KDA kernels inside graph | FlashInfer KDA kernels outside graph |
| --- | ---: | ---: | ---: |
| eager | 0 | 0 | 68 |
| no CP, KDA outside BCG | 57 | 0 | 68 |
| no CP, KDA inside BCG | 23 | 34 | 0 |
| CP4, KDA inside BCG | 23 | 34 | 0 |

The graph-backed implementation uses one planned core kernel per KDA layer, while the eager path uses prep + chain kernels. Graph membership was verified from CUDA graph launch correlations and graph IDs, not just server configuration. This comparison covers cold, prefix-free prefill within the capture range; cached-prefix replay, multimodal input, and speculative decoding are outside this experiment.
