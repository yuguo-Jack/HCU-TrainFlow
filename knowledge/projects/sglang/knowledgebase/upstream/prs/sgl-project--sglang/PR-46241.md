# [Perf] diffusion/loader: Avoid temporary GPU tensors when loading encoders

[Upstream PR](https://github.com/sgl-project/sglang/pull/46241) · state: closed · merged: True

## Original PR description

## Motivation

Native text encoders allocate their final parameters before loading the checkpoint. For GPU-resident encoders, the checkpoint reader currently materializes each source tensor on the GPU as well, then the weight loader copies it into the existing parameter. This adds an unnecessary GPU allocation/copy and can transfer the full source-dtype tensor before casting or TP slicing.

## Modifications

- Read native encoder checkpoint tensors on the CPU and let the existing per-parameter loaders copy/cast/shard them into their final destinations. Safetensors stays memory-mapped instead of building a second GPU weight tensor.
- Keep the destination device, offload policy, quantization postprocessing, and customized `_get_all_weights(..., to_cpu)` interface unchanged. GGUF and Transformers fallback loading are unchanged.
- Add a small real T5 safetensors loading regression to the existing loader test file, checking both CPU/offloaded and GPU/resident parameters, exact FP32-to-BF16 values, and fused QKV weights.

Production diff: **+2/-1 lines** in one existing file. Tests: **+46 lines** in one existing file. No new configuration, helper, or production module.

## Accuracy Tests

Validated on an isolated 2x H200 development machine, baseline `3c6a6c806865` versus final head `6a1e42bd117b`:

- New regression fails on the baseline GPU-resident path and passes with this change.
- Relevant loader, parallel linear, Qwen3, H3, Ming, image encoder, folding, Ideogram and reader suites: **224 passed, 3 skipped**, plus 18 passing subtests. The three NVFP4 hardware tests require Blackwell and were skipped on Hopper.
- Real two-GPU SRT CLIP folding test: **passed**, including forward-output parity against single-rank loading.
- Real HTTP generation: Wan2.1-T2V-1.3B, single GPU and Ulysses2; Z-Image-Turbo, single GPU. Within each configuration, baseline and modified decoded pixels are **bit-identical**. This is not a claim of single-GPU versus multi-GPU equivalence.
- Pre-commit passes.

## Speed Tests and Profiling

H200, driver 595.71.05, Python 3.12.15, Torch 2.14.1+cu130, Transformers 5.19.0, Diffusers 0.37.0, safetensors 0.8.0. Cached checkpoints, offline HF access, fresh server processes, `--warmup-mode off`, otherwise default deployment policy. Time is process launch to successful `/health`, polled every 50 ms. First downloads and JIT priming are excluded.

Three alternating baseline/modified pairs per single-GPU model, all on the final code:

| Model | Baseline startup median | PR startup median | Reduction | Loading peak allocated, MiB | Loading peak reserved, MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Wan2.1-T2V-1.3B | 31.573 s | 29.845 s | 5.5% | 25740.95 -> 24983.28 | 26126 -> 25132 |
| Z-Image-Turbo | 30.853 s | 30.213 s | 2.1% | 20217.47 -> 19644.10 | 20546 -> 19812 |

Raw startup seconds, baseline / PR:

- Wan: `[31.573, 31.717, 31.372]` / `[29.845, 30.007, 29.749]`.
- Z-Image: `[32.377, 30.853, 30.646]` / `[30.213, 30.549, 30.131]`.

The Ulysses2 validation also reduces loading peak allocated from 14906.86 to 13865.42 MiB, and reserved from 15292 to 14010 MiB. These are PyTorch allocator peaks, max across replica ranks, not total device memory or steady-state inference gains. Z-Image startup peak host anonymous memory was effectively unchanged (~18250 MiB), sampled across the process tree every 100 ms. No general host-memory claim is made for legacy `.pt` checkpoints or other models.

After every launch, validate a real request with prompt `A small sailboat on a calm blue lake in daylight.`, seed 42, quality `exact`, 4 steps: Wan 512x320 / 17 frames / 8 fps; Z-Image 512x512. Download/decode the output and compare pixel SHA256. Each server is stopped and checked for surviving children before the next launch.

This is a small loading optimization, not a new direct-storage backend. The Z-Image gain is modest; these measurements do not establish a universal startup speedup across hardware or checkpoints. No public API or command changes, so no documentation update is needed.
