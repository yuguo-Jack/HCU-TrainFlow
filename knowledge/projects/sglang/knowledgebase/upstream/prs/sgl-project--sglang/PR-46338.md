# [Perf] engram: Use reduce-scatter for large uniform prefill shards

[Upstream PR](https://github.com/sgl-project/sglang/pull/46338) · state: closed · merged: False

## Original PR description

## Motivation

Engram's sharded lookup currently all-reduces the full embedding buffer and then scatters it for SUM_LEN prefill batches, including large batches whose attention-DP shards are equal. Those batches can return their local reduced shard directly with reduce-scatter.

## Modifications

- Admit native reduce-scatter using shared padded CPU token counts, the published global buffer size, and the existing TP/layout contract. Collective selection does not depend on a rank-local token count or forward mode.
- Restrict the new path to CUDA, eager uniform prefill with at least 32,768 rows per rank, TP equal to attention DP, attention TP/CP equal to one, GATHERV disabled, and deterministic inference disabled. Other cases retain the existing collective selection.
- Allocate the output from the shared count and check the local-size contract after the collective. The size restriction is conservative and is not a measured optimal crossover.

Recorded runtime dependencies: PyTorch `2.14.1`, `sglang-kernel==0.4.10`, `sgl-deep-gemm==0.2.3.post2`, and `sgl-flash-mla==1.0.0`. The source revisions below identify the engine, independently of installed wheel metadata. Unspecified optimization switches retain their pinned-source defaults.

Tested candidate: `44f034aa770f7a39365b81abdb074fee00c132a8`, against `773cb938fe9484a8f7e7e46fb1b1fe96412c59ed`. Final commit `65c8716919750e9f4277540df8843c2eac69a7e5` adds only the registered CPU test; the production file is byte-identical to the measured candidate.

## Accuracy Tests

- Five registered CPU tests directly exercise the production admission helper and real DP metadata/layout helpers; all pass with CUDA hidden. Additional local coverage: 28 CPU admission cases, plus six checks using the actual TP/layout eligibility helper for scoped and WORLD layouts.
- Two-rank directed NCCL checks: 16 cases per rank, including threshold boundaries, uneven/zero counts, nonfinite values, MAX_LEN/CUDA-graph fallbacks, and an expected invalid-local-size assertion. These use controlled tables and do not substitute for the production-provider checks below.
- Actual-checkpoint comparisons cover both Engram layers on both ranks, twice per layer. At 33,792 physical rows, the original all-reduce/scatter and the new reduce-scatter produce bitwise-identical outputs. At 4,224 rows, the candidate retains the original path and also matches bitwise. These are sampled embedding-boundary checks, not exhaustive generation equivalence.
- Standard zero-shot GSM8K, 200 identical inputs, max 4,096 output tokens: baseline **195/200**, candidate **194/200**; both pass the unchanged 0.95 threshold, with zero errors or truncation. Per-rank draft acceptance lengths are 4.325088/4.265133 for baseline and 4.376026/4.181248 for candidate (ranks 0/1). Native quality does not establish that the large-row branch was exercised; its direct coverage comes from the checkpoint comparisons above.

## Speed Tests and Profiling

Two independent full-model engine-step comparisons on two GB300 GPUs, TP2/EP2/attention-DP2/replica-DP1, MegaMoE, per-rank Engram tables, GATHERV disabled, and prefill/decode CUDA graphs disabled. DSPARK and both bounded replay paths are enabled. Performance runs use simulated acceptance length 3.51 (`match-expected`, `real-draft-token`); the separate native-quality runs disable simulation.

Both groups use the official `benchmark/engine_steps/bench_engine_steps.py` from #46006 at `543a2804d5c8f3167c8fd8bb5c3a3ef862c3774f`: engine transport, device-resident prefix, context 131,072, suffix 4,096, 4,096 requests per rank, five warmup steps, seed 733427905, and eight in-flight steps. The target is 32,768 new tokens per rank per step; replay raises the physical row count to 33,792 (global chunk budget 67,584). Each arm starts a fresh engine/store with fixed source, checkpoint and runtime configuration.

| Independent group | Baseline ms/step | Candidate ms/step | Paired throughput changes | Mean throughput change |
|---|---:|---:|---:|---:|
| BAAB | 333.6972 / 333.7973 | 332.6572 / 332.5472 | +0.3127% / +0.3759% | **+0.3443%** |

Baseline/candidate spans are 0.0300%/0.0331% in the first group and 0.0135%/0.0268% in the second. All original benchmark guards pass. Replaying the saved completions through the exact official scorer reproduces steps, elapsed time, token counts, and all per-step durations. These results establish a small benefit for this fixed 32K engine-step workload, not application-level E2E throughput.

**4K limitation:** a separate 4K ABBA, where the candidate retains the original collective, measured 89.4181 / 88.8188 / 90.6711 / 86.2778 ms/step. Its paired throughput changes were +0.6747% and −4.8454%, with a −2.1138% mean and substantial same-source drift (3.5747% baseline, 2.0640% candidate). This does not establish no regression at 4K or cleanly attribute the difference to the change. All arms are retained. An independent supplemental 4K ABBA measured 88.3945 / 88.2979 / 87.7421 / 88.7247 ms/step, paired changes +0.1094%/+1.1198%, mean +0.6130%; baseline/candidate spans were 0.3728%/0.6314%. Its original guards and exact scorer replays also pass. The two 4K groups have opposite mean directions; the new reduce-scatter branch is not selected at this shape. Both groups are retained, and neither a general 4K speedup nor an environment-independent no-regression guarantee is claimed.

- hnyls2002 · comment · 2026-10-28T03:01:53Z · [source](https://github.com/sgl-project/sglang/pull/46338#issuecomment-6459501784)

Thanks @alphabetc1! This PR showed that uniform prefill shards can skip the full all-reduce of the Engram lookup. #46917, now merged, takes that further: under DP attention, eager prefill lookups gather the hash ids with `all_gatherv`, and the default `lookup: auto` exchanges the rows with an all-to-all whenever the 24 hash columns divide over the TP group (1/tp of the bytes a reduce-scatter moves), for uniform and uneven batches alike. Where the columns do not divide (DP 16, say), `--engram-config '{"lookup": "reduce_scatter"}'` takes the variable-length reduce-scatter path. You are a co-author on #46917. Closing as superseded; please reopen if a shape it leaves on the all-reduce matters to you.
