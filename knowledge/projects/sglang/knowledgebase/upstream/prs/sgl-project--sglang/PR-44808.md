# [Fix] minimax-h3: validate sigma shift scales before loading weights

[Upstream PR](https://github.com/sgl-project/sglang/pull/44808) · state: open · merged: False

## Original PR description

## Motivation

`MiniMaxH3Pipeline._load_config` fetched the checkpoint first (`maybe_download_model`) and only then parsed `_minimax_h3.sigma_shift_scales` with a bare `float()`. On the real MiniMax-H3 index this accepted `-12.0`, `NaN` and the string `"12"` (silently turned into 12.0). The request-time timestep stage rejects non-positive values, but only after the whole model has loaded, and then for every request.

## Modifications

- Add `validate_minimax_h3_sigma_shift_scales` (`configs/minimax_h3_metadata.py`), which requires a positive finite number (not a bool) for both modalities. It is shared by the full release metadata parser (`.../minimax_h3/release_metadata.py`) and a new `_preflight_model_config` hook.
- `composed_pipeline_base.py` / `minimax_h3_pipeline.py`: the hook runs before the weights are fetched. It is a no-op for other pipelines. For H3 it reads `model_index.json` from the selected partition, or the overlay metadata for the FastH3 and VDN-H3 source repositories, without downloading any weights.
- `test/unit/test_minimax_h3_metadata.py`: invalid values are rejected before any weight download for the plain, FastH3 and VDN-H3 pipelines, local and remote; the parser rejects bad values before float coercion; the selected index matches the weight directory and revision; a missing or damaged index does not fall back to a weight download; other pipelines do not fetch metadata.

## Accuracy Tests

Unit: `test_minimax_h3_metadata.py` 7 passed, 68 subtests passed. Without the fix the new tests fail.

Real MiniMax-H3 FL2VA checkpoint, TP2 on 2 x B200, t2va, 4 s, 50 steps, seed 42. Server runs on this branch head, on a merge of the three H3 fixes (this PR, the VAE tile validation and the sigma preflight), and on unpatched `main` (`2948662026`).

![time to report](https://raw.githubusercontent.com/fusheng-ji/sglang/423113d8a26b0cda0e5b8586899655c2be2514db/minimax-h3-sigma-time.png)

Times are seconds from server start. For `main`, healthy time and request time come from the harness; for this branch, the time is the timestamp of the startup error in the server log relative to the first log line (a few seconds after process start). The branch's process then takes about 1.5-2 more minutes to exit (existing shutdown behaviour), which is not counted. Weights were warm in the page cache, so the saving here is the rest of the load plus the failing request; for a remote repository it would also include the download. Run-to-run load time varies (main healthy in 249-312 s across these runs).

Calling `_load_config()` directly on the real `model_index.json`: `main` accepts all three values, and for `-12.0` only reaches a verdict after the weight-fetch call; this branch rejects each in about 0.002 s without calling it.

## Speed Tests and Profiling

Not a performance change. The fix only touches the failure path / load-time validation; the regression run below produced bit-identical output, but latency was not measured.

The benefit on a local checkpoint is small (weights were already in the page cache, so loading took 25-40 s); for a remote repository the saving is the weight download, which was not measured.

Limitations: the preflight rejects quoted numbers such as `"12"`, which the old code accepted. The real checkpoint uses numbers and is unaffected, but a third-party `model_index.json` that stores the scales as strings will go from loading to failing. The FastH3 / VDN-H3 overlay and remote-download paths are covered by mocked unit tests only. Only the FL2VA partition, t2va, TP2 and one prompt/seed were run on real weights.
