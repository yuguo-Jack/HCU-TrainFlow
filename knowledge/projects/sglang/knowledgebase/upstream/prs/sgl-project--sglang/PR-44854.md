## Motivation

A one-step frozen-KV draft still executes an assistant seed forward. The current `<= 1` capture guard skips that forward and leaves it eager.

## Modifications

Allow capture for one draft step while keeping the zero-step/disabled cases excluded. Add a one-step XPU fixture that verifies repeated generation, acceptance statistics, and nonzero draft graph capture.

Depends on #44853. Target weights and verification are unchanged.

## Accuracy Tests

The new capture regression fails on the old code with `0.0 not greater than 0`; both one-step serving tests pass after the fix. Six greedy prompts match the validated control, including prompts crossing the sliding-window boundary.

GSM8K via `sgl-eval==0.1.3`: 82.5%/200, zero errors, one truncation. This is an accuracy smoke check.

- alexnails · comment · 2026-10-17T05:26:50Z · [source](https://github.com/sgl-project/sglang/pull/44854#issuecomment-6230170451)

Agent:

The research supports keeping the change. The strongest evidence is upstream history: this appears to fix a stale guard left behind by an earlier refactor.

Merged [PR #25539 (https://github.com/sgl-project/sglang/pull/25539)](https://github.com/sgl-project/sglang/pull/25539) moved the assistant seed forward from eager execution into draft_forward(), specifically to avoid its extra launch and synchronization overhead. It also removed a num_steps > 1 condition around attention initialization, explaining that initialization must now run even with one step.

I inspected that PR’s merged code: it retained the separate num_steps <= 1 graph-capture guard, despite moving a real model forward into the one-step draft path. That mismatch is concrete evidence for changing the threshold. The conclusion that it was overlooked is my inference; I found no documented reason for deliberately keeping one-step frozen-KV drafting eager.

Ordinary EAGLE remains different. Its separate implementation still skips capture for one step and explicitly comments that draft_forward only performs sampling in that case. This PR changes the frozen-KV worker’s guard, leaving EAGLE’s condition intact. [EAGLE source at the PR revision (https://github.com/sgl-project/sglang/blob/767fa00745f1d16f205a50cf5c47b3ff9186bf7e/python/sglang/srt/speculative/eagle_worker_v2.py#L656)](https://github.com/sgl-project/sglang/blob/767fa00745f1d16f205a50cf5c47b3ff9186bf7e/python/sglang/srt/speculative/eagle_worker_v2.py#L656)

The performance rationale also matches PyTorch’s guidance: graphs reduce CPU dispatch overhead for repeated, graph-safe GPU work, especially when individual operations are short. One model forward can contain many kernel launches; it need not contain multiple recurrent steps to benefit. [PyTorch documentation (https://docs.pytorch.org/docs/stable/notes/cuda#cuda-graphs)](https://docs.pytorch.org/docs/stable/notes/cuda#cuda-graphs)

My recommendation is to retain the implementation and add a one-step eager-versus-replay regression before merging. That would address the validation gap. Restricting the fix to XPU solely because the benchmark used XPU would be unnecessarily narrow—the architectural rationale applies to CUDA too, although CUDA still needs validation.

My earlier answers were too categorical before checking this history. The historical evidence makes the implementation substantially better justified; it does not establish correctness across every backend configuration.
