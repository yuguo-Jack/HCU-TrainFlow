# [AMD][Unified Cache] Split UMBP loads across TP ranks

[Upstream PR](https://github.com/sgl-project/sglang/pull/39911) · state: open · merged: False

## Original PR description

## Motivation

For rank-replicated KV (MLA / DSA under pure TP), every TP rank restores the same pages from the UMBP tier. The loader's cost is driven by the number of objects and range descriptors rather than bytes, so each rank pays the full cost for data its peers are fetching at the same time.

## Modifications

With `UMBP_LOAD_SPLIT=1` (default off), each rank reads 1/N of the restored pages, and the rest is recovered with one all-gather per layer group on the forward stream.

- Ranks first agree on the batch and on the pages common to all of them (two small CPU all-reduces). Each rank reads its share of the common pages plus any pages only it needs. If the batches differ or any rank vetoes, all ranks fall back to the unsplit path, so a mismatch cannot deadlock the all-gather.
- Only KV-source pools of a `rank_replicated` pool group are split, on the shared-key layout from #38778. Offload is never split. CP, PP, DP attention and disaggregation decode are rejected at startup.
- A rank whose read fails still joins every all-gather. The vote is read once at the end of the batch and reported through `finish_layer_wise_loading`, so the scheduler aborts the batch's requests.
- An optional gate, `UMBP_LOAD_SPLIT_MIN_RESTORE_RATE`, skips splitting while restores are too infrequent for it to pay off.
- With `UMBP_LOAD_SPLIT` unset, none of this runs: no collectives, no staging buffer, and no split settings are read. Loads take the existing path.

All changes are in `umbp_direct_linker.py`.

| env | default | meaning |
|---|---|---|
| `UMBP_LOAD_SPLIT` | `0` | enable split load |
| `UMBP_LOAD_SPLIT_STAGING_MIB` | `512` | per-rank device staging; a batch that does not fit is not split |
| `UMBP_LOAD_SPLIT_MAX_RIDS` | `256` | max requests in a split batch |
| `UMBP_LOAD_SPLIT_MIN_PAGES` | `16` | smaller batches are not split |
| `UMBP_LOAD_SPLIT_MIN_RESTORE_RATE` | `0` | restores/s below which splitting is skipped (`0` = gate off) |
| `UMBP_LOAD_SPLIT_RATE_MIN_SECONDS` | `300` | warm-up period before the gate starts judging |

## Accuracy Tests

- `test_umbp_direct_linker_split_load.py` (28 CPU tests): byte-exact reconstruction against a reference pool, partially covered layer groups, fallback on every rank for every veto reason, a failed loader still joining the all-gather and every rank reporting the batch as failed, the restore-rate gate, and a disabled path that matches the unsplit behavior.
- GLM-5.1-FP8, TP8, 8x MI355X: `cache_test_len` passes at 2K/8K/16K. A byte-level check of 2,340 page-layer slices on all ranks found 0 mismatches.

## Speed Tests

DeepSeek-V4-Pro, 8x MI355X, TP8, MTP, multi-turn agentic traces (mean ISL ~98K, OSL ~900), 740 GB DRAM tier, concurrency 128, 3600 s. Both arms run on the same node with `lmsysorg/sglang-rocm:v0.5.21-rocm724-mi35x-20261007` and this PR applied; the only difference is `UMBP_LOAD_SPLIT`. The split arm uses `UMBP_LOAD_SPLIT_STAGING_MIB=6144` and `UMBP_LOAD_SPLIT_MIN_RESTORE_RATE=0.3`.

| metric | split off | split on | delta |
|---|---:|---:|---:|
| input tok/s | 183,880 | 190,005 | +3.3% |
| TTFT p50 (s) | 41.3 | 39.2 | -5.1% |
| completed requests | 6,799 | 6,940 | +2.1% |

On an earlier build (2026-09-16) the gain was +5.3% at concurrency 128 and +4.2% at 256. At 64 there was no gain, because the device cache serves most hits; with the gate at 0.3 the split is skipped there.
