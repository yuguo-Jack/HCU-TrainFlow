# fix(dsv4): support R3 capture and MXFP4 online updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/39392) · state: closed · merged: True

## Original PR description

Replaces #38282, which GitHub auto-closed when its base branch was deleted and recreated.

## Summary

- Capture logical expert IDs from DeepSeek V4 HashTopK before logical-to-physical remapping for R3 replay. Mask CUDA-graph padding, disable target capture from draft modules, and reject the unsupported HashTopK waterfill/capture combination.
- Synchronize CUDA IPC tensor imports in the weight updater before returning to the producer, including flattened buckets and other tensor load formats.
- Support repeated TRT-LLM MXFP4 online loads: permute expert weights in place, retain checkpoint-layout scale parameters, and maintain separate shuffled scale copies with stable kernel addresses. Pass unsigned byte views at the FlashInfer packed-FP4 call boundary without changing load parameters.
- Register the GEMM1 clamp limit as a non-persistent buffer so memory offload preserves it.
- Keep the padded-row Triton fast path off CPU tensors.

LGTM — nice set of fixes, and the comments explaining *why* each invariant exists make this much easier to review than it could have been.

Things I checked independently and that hold up:

- The shuffle refactor is equivalent against FlashInfer 0.6.18: `shuffle_matrix_a(x, t) == x[get_shuffle_matrix_a_row_indices(x, t)]` and `shuffle_matrix_sf_a(x, t) == block_scale_interleave(x[get_shuffle_matrix_sf_a_row_indices(x, t)])`, with `num_elts_per_sf` defaulting to 16. Folding `[w1, w3] -> [w3, w1]` into the gather as `w3_w1_rows[perm[r]]` reproduces the old `shuffle(reorder(w))` ordering, and `half` is valid for the scales too since their row count matches `w13.shape[1]`.
- `supports_output_view` is a real per-backend attribute in `flashinfer/moe_ep` (`modes/mega_layer.py` plus the cutedsl backends), so gating on it is a genuine fix rather than a guess — the DeepGEMM mega path doesn't advertise it.
- `get_platform().is_sm100` resolves to `device_capability_majors=[10]`, so sm_103 (B300/GB300) passes. Good, given where this was validated.
- Every call site of the new `capture_routed_experts_if_allowed(allow_capture, ...)` signature is updated, and `HashTopK` is a plain `nn.Module`, so the `isinstance` chain in `disable_routed_experts_capture_for_draft` is safe.
- Merges cleanly onto current `sglang-miles` (only `topk.py` overlaps the 12 commits since the base).

A few comments, none blocking.

## 1. `Mxfp4FlashinferTrtllmMoEMethod` has no `restore_weights_before_loading`

This is the one I'd most like addressed. `process_weights_after_loading` now permutes `w13_weight` / `w2_weight` in place, which makes it non-idempotent. `restore_weight` in `model_loader/loader.py` is the hook for exactly this ("Undo in-place quant packing so fresh weights can be loaded"), and `Mxfp4MoEMethod.restore_weights_before_loading` implements it for the Marlin path.

Without it, `begin_weight_update` -> a session that updates only non-MoE tensors -> `end_weight_update` runs `postprocess_weight` over already-permuted weights and permutes them a second time, silently. A full-model sync is unaffected, so this doesn't touch the validated recipe — but `/begin_weight_update` and `/update_weights_from_tensor` are public endpoints and the name list is caller-controlled. Applying the inverse permutation (`argsort(w13_rows)` / `argsort(w2_rows)`) in a restore hook would make the postprocess correct either way.

Related, in `test_mxfp4_flashinfer_trtllm_hot_reload.py`: the `restore_weight(layer, torch.device("cuda"))` call and the assertions after it are currently a no-op, since `_apply_quant_method_hook` does a `hasattr` check and skips the method. So the "loader hooks bracket every update session; neither may disturb the checkpoint-layout parameters" half of that test isn't actually exercised yet.

## 2. The `*_shuffled` split has two consequences worth a comment

- **Memory**: the fp32 checkpoint-layout scales used to be freed when they were replaced by the shuffled version. Now both layouts stay resident; the fp32 copy alone is roughly a quarter the size of `w13_weight`. Necessary for reloadability, just worth stating.
- **EPLB**: `DeepseekV2MoE.get_moe_weights` picks up `w13_weight_scale_inv_shuffled` only because `copy_or_rebind_param` registers it as a `Parameter` and `filter_moe_weight_param_global_expert` admits anything with `shape[0] == num_local_experts`. That's load-bearing — if these ever became buffers, a rebalance would update the checkpoint-layout scales and leave the kernel reading stale shuffled ones. A one-line comment pinning that would help.

## 3. `apply()` reads the method attribute, not the buffer

`gemm1_clamp_limit=self._gemm1_clamp_limit_tensor` — but the reason for `register_buffer` is that the *layer's* copy is what offload maintains. They agree today because `_import_static_state` restores in place, but `nn.Module._apply` (`.to()`, `.cuda()`) replaces `_buffers[key]` outright and would strand the method's reference. Reading `layer._gemm1_clamp_limit_tensor` matches what the FP8 side already does.

## 4. `_can_fuse_padded_region`: `x.is_cuda` also excludes XPU

On XPU both `_is_cuda` and `_is_npu` are False, so a tensor reaches this predicate and now falls back to eager even though Triton works there. The comment says "fall back to eager for host tensors"; `not x.is_cpu` matches that intent exactly and keeps ROCm and XPU on the fused path.

## 5. Smaller things

- `get_quant_method`: after the SM100 raise, the `is_sm90 or is_sm120` branch is unreachable for `flashinfer_trtllm_routed`, so the comment above it now describes only the `flashinfer_mxfp4` arm. One check placed just before the TRT-LLM return would cover both backends and remove the dead branch — at the cost of changing `flashinfer_mxfp4` behaviour on unsupported arches, which may be a separate decision.
- `apply()`: `w13` / `w2` are now unconditionally uint8 views, so `... if w2.dtype == torch.uint8 else ...` can't take the `else`.
- `_update_weights_from_flattened_bucket`'s `return True, "Success"` is now discarded by the caller.
- `_prepare_flashinfer_trtllm_activation_params`: `existing.fill_(float(value))` would skip building `tensor` on the reload path. Also `existing is not None and tensor is None` falls into the `register_buffer` branch, which is the pointer-orphaning case the in-place branch exists to prevent — unreachable while `moe_runner_config` is fixed for the layer's lifetime, but the condition reads as though it were handled.
- `torch.cuda.empty_cache()` at the end of `process_weights_after_loading` now runs per MoE layer on every weight-update session. With the in-place design there's far less to reclaim than before, so it may be worth restricting to the first build.
- `disable_routed_experts_capture_for_draft`: `elif hasattr(module, "allow_routed_experts_capture")` would cover `HashTopK` and any future router class without the lazy import and without another `elif` next time.
- `HashTopK.allow_routed_experts_capture` could be a class attribute next to the docstring with the same "draft-side blocks set this False" comment that `TopKConfig` carries; right now the HashTopK side has no explanation of what the flag is for.
