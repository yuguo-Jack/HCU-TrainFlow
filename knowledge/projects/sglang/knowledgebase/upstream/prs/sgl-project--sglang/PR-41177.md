# [Fix] rust-server: Align Jinja chat inputs with Python

[Upstream PR](https://github.com/sgl-project/sglang/pull/41177) · state: closed · merged: False

## Original PR description

## Motivation

Identical OpenAI chat requests can produce different model inputs in the Python frontend and Rust server. For example, omitted tool defaults become prompt text in Python but are omitted in Rust; multipart text and final-assistant handling can also change the input sequence.

Relates to #39843. This patch follows the current Python preprocessing behavior for the selected Hugging Face Jinja text-chat path. The acceptance criterion is complete rendered prompt bytes and ordered final input token IDs, not token counts or generated answers. It does not settle future normalization policy or claim complete Python/Rust API equivalence.

## Modifications

- Build Python-compatible prompt-facing tools, including defaults, nulls, field order, named tool selection, and schema type-alias normalization. Preserve original schema parameters for typed grammar handling.
- Normalize text message content and assistant tool-call arguments, select named templates at startup, and match final-assistant conversion and continuation. Encode continuation separately and remove exactly one matching leading BOS. Pass the loaded Python tokenizer's resolved BOS through the launch boundary, distinguishing unresolved state, known absence, and ID 0.
- Normalize top-level and nested reasoning aliases before Jinja rendering, including thinking flags and kwargs precedence. Preserve the different top-level Pydantic and nested Python float rules for whitespace, underscores, and Unicode digits.
- Retain typed extraction for native/legacy formatters and add unit/route regressions for their existing behavior. The patch uses the existing renderer; it does not vendor a renderer or add a dependency package.

It also checks that nested whitespace/underscore inputs remain accepted. The BOS probe uses an isolated PyO3 build with BOS-related source hashes identical to the final candidate. It runs extracted current scheduler/tokenizer initialization and launch functions through the real Rust HTTP runtime and tokenizer worker, then stops at the scheduler ring. It does not execute model inference or the full GPU scheduler constructor. Python references are actual protocol/preprocessing/rendering/tokenization calls, not a running Python HTTP server.

### Known boundaries

- Full Draft 2020-12 metaschema validation is not implemented. Seven recorded invalid-schema controls are rejected by Python but still accepted by Rust. Accepted-schema prompt normalization is covered separately; typed grammar semantics are not changed by that normalization.
- This is finite text-chat coverage, not exhaustive compatibility for arbitrary templates, tokenizer backends, multimodal requests, or native/legacy Python parity. Native/legacy regression controls cover their existing Rust behavior.
- The inherited automatic special-token stripping policy is not generalized for arbitrary EOS-only or BOS-plus-EOS post-processors; standalone BOS fallback remains metadata-based. The Python scheduler handoff supplies class defaults for the integrated path.
- Special-token kwargs, constrained-decoding correctness, generated outputs, model accuracy, and remote CI success are not established by these local checks.
