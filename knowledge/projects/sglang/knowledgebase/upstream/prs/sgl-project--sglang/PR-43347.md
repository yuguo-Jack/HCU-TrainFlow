# fix(spec): assemble --speculative-token-map hot lm_head rows across vocab shards at TP>1

[Upstream PR](https://github.com/sgl-project/sglang/pull/43347) · state: open · merged: False

## Original PR description

## Motivation

Fixes #42397 

`--speculative-token-map` (FR-Spec hot-token map) holds **global** vocab ids, but `init_lm_head` bound each rank's copy of the target `lm_head` with

```python
head = head.clone()
head.data = head.data[self.hot_token_id]   # global ids into the local ~vocab/tp shard
```

so any hot id beyond the local shard tripped a device-side assert in `vectorized_gather_kernel` at TP>1, and even in-range ids selected the wrong rows on rank >= 1. Community FR-Spec gains were all measured at TP=1, so this path had never been exercised above one GPU.

Two adjacent pre-existing defects surfaced while fixing this:

1. **Block-scale quantized lm_heads never worked with a token map, at any TP.** E.g. ModelOpt NVFP4 checkpoints quantize an untied lm_head with `ModelOptFp4LinearMethod` (uint8-packed rows + per-block scales); the historical path silently bound garbage packed rows -- no error, wrong outputs. ModelOpt FP8 checkpoints keep `lm_head` in BF16 (verified against `Qwen3.8-27B-FP8`'s safetensors index) and are unaffected.
2. The replicated-reduction interaction with the draft logits processor's vocab-parallel gather needed a decision (see Modifications).

## Modifications

**`eagle_worker_common.py` -- `build_hot_token_lm_head()`**

Each rank selects the hot rows that live in its own shard (the same masking/offset math `VocabParallelEmbedding.forward` applies, inlined to avoid its torch.compile'd helper at init time), then the full reduced head `[len(hot), hidden]` is rebuilt on **every** rank via one padded all-gather over the lm_head's sharding group. The design goal is that the TP>1 draft logits path becomes shape- and value-identical to the working TP=1 layout, so every downstream consumer (topk + `hot_token_id[topk_index]` remap, draft CUDA-graph buffers, verify) is unchanged.

- Rows are exchanged together with their hot-order positions; padding writes land in one sentinel row that is sliced off, so duplicate-index assignment stays deterministic.
- Per-rank counts are exchanged first so every rank pads to the same width; the last shard being ragged (vocab not divisible by TP) is covered by the unit test.
- Row extraction is quantization-aware (`_select_head_rows`): heads whose quant method implements `embedding()` (unquantized, and NVFP4 *embedding* heads, which dequantize on gather) go through it -- the same call `VocabParallelEmbedding.forward` makes for a sharded lookup. Float rows (bf16/fp16/fp32) index directly. Everything else -- block-scale quantized *linear* lm_heads whose per-block scales cannot follow selected rows -- is rejected with an explicit `ValueError` naming the dtype, the quant method, and the escape hatch, instead of binding garbage (the historical TP=1 behavior).
- Hot ids are validated against `[0, vocab_size)` up front; an empty or 2-D map is rejected.
- The TP=1 fast path keeps the historical semantics (row select of the full head) but allocates only the reduced copy instead of cloning the whole vocab first.

**`eagle_worker_v2.py` -- `init_lm_head`**

- The hot branch calls the builder and then disables the draft logits processor's vocab-parallel gather (`do_tensor_parallel_all_gather(_dp_attn)`): the reduced head is replicated, so each rank's `[tokens, len(hot)]` logits are already complete and gathering would concatenate TP copies of them.
- `--speculative-token-map` + dp-attention at TP>1 fails fast as unverified rather than misbehaving; a missing target lm_head module at TP>1 (needed for the shard ranges) is reported explicitly.
- The EAGLE3 branch is untouched: EAGLE3 drafts carry their own `draft_vocab_size` head that shards natively and already works at TP>1.

**Tests**

- `test/registered/unit/spec/test_build_hot_token_lm_head.py` (CPU): a 4-process gloo test that mirrors a vocab-sharded head (ragged last shard, org padding included) and asserts the assembled head equals `full[hot]` **exactly** on every rank; plus TP=1 row-select + Parameter-wrap preservation, and the empty / out-of-range / packed-quantized-row rejections.
- `test/registered/spec/eagle/test_spec_token_map_tp.py` (CUDA, `2-gpu-large`): TP=2 (the regression: stock main crashes during startup) and TP=1 control, launching `Qwen/Qwen3.5-9B` + NEXTN with a deterministic token map generated on the fly, spanning both shards evenly. Asserts healthy greedy generation, repeat-greedy determinism, and that the speculative path is active. The map is synthetic (not frequency-curated), so only accept-length sanity (> 1.0) is claimed, not parity with a full-vocab draft.

Both test files are red on main (the unit file fails to import; the TP=2 E2E server dies with the reported assert) and green with this PR.

## Accuracy Tests

All local runs on 2x RTX 5090 32GB, sglang 0.5.20 tree (`aiharbor.msxf.local/test/sglang:0.5.20-cu130` image), EAGLE/NEXTN with the same-checkpoint MTP draft, fp8_e4m3 KV, flashinfer attention, `--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`. The token map is 81,920 ids spread evenly over `[0, 248320)` -- 40,960 per TP shard at tp=2, so the cross-rank assembly is exercised.

| tree | model (lm_head) | config | result |
| --- | --- | --- | --- |
| stock | Qwen3.8-27B-NVFP4 (`ModelOptFp4LinearMethod`, uint8) | tp=2 + map | device-side assert in `vectorized_gather_kernel` during `init_lm_head`, same stack as the issue |
| this PR | Qwen3.8-27B-NVFP4 | tp=2 + map | clear `ValueError` up front (dtype, quant method, escape hatch) |
| this PR | Qwen3.8-27B-FP8 (BF16 `[248320, 5120]`) | tp=2 + map | server healthy; greedy outputs correct; accept length 1.26-1.78; repeated greedy calls byte-identical |
| this PR | Qwen3.8-27B-FP8 | tp=2, no map | unchanged (accept length ~2.9), confirming the gather bypass only engages with a token map |

Greedy samples from the fixed tp=2 + map run: `"The capital of France is" -> " Paris.\nThe capital of Germany is Berlin..."`, `"1+1=2, 2+2=4, 4+4=" -> "8, 8+8=16, 16+16=32, 32+32=64..."`, and a correct `reverse_string` slice-notation answer; `completion_tokens / spec_verify_ct` in [1.26, 1.78] with the synthetic spanning map (expected: most drafts fall outside the hot set).

The gloo unit test asserts exact `torch.equal` per rank, including a ragged final shard (232 of 256 rows) and org padding.

TP=1 E2E equivalence is covered by the CI control test above; it was not run on this host because the 27B FP8 checkpoint does not fit one 32GB card, but the TP=1 fast path is asserted exactly (row select of the full head) in the unit tests, matching the historical `clone()` + row-index semantics for float heads.

## Speed Tests and Profiling

Init-time only cost: one tiny count exchange plus two padded all-gathers over the lm_head group (~0.4 GB/rank of hot rows at the 81,920-entry map, a ~0.8 GB transient for the gathered buffer, both freed before KV-pool sizing via the existing `set_embed_and_head` empty-cache). No benchmark was run for steady-state: with a real (frequency-curated) map the draft lm_head matmul shrinks from a `vocab/tp` shard to `len(hot)` rows and the draft logits buffer shrinks accordingly, but accept length with the synthetic map used here is not representative, so no throughput claim is made. The TP=1 path also stops cloning the full `[vocab, hidden]` head before slicing it (2.5 GiB transient on a 248k vocab) and allocates only the reduced copy.

- jvzibro · comment · 2026-10-09T12:50:27Z · [source](https://github.com/sgl-project/sglang/pull/43347#issuecomment-6081238172)

While working on this PR I became aware of two other PRs for #42397 — linking them here so the trade-offs are in one place for reviewers:

- #42424 — fail fast: reject `--speculative-token-map` at TP>1
- #43249 — make it work: keep the hot head sharded, pad each rank's block to a common width with real non-hot tokens from the same shard, and reuse the existing vocab-dim all-gather of draft logits

This PR and #43249 share the "make it work" goal; the difference is where the hot head lives:

|     | This PR | #43249 |
| --- | --- | --- |
| Hot head | replicated `[H, hidden]` on every rank, assembled once at init via a padded all-gather | sharded: each rank keeps `width` rows (its hot rows + non-hot fill) |
| Per-step collectives | none on the hot path — the draft-logits vocab gather is skipped | vocab-dim all-gather on every draft forward |
| TP>1 vs TP=1 | identical by construction; the map stays a hard bound on the draft candidate set | identical for balanced maps; for skewed maps the candidate set grows to `tp × width` (map + fill tokens) |
| Block-quantized lm_head | fails fast with a clear error (float and embedding-capable heads are handled; ModelOpt-FP4-style packed heads are rejected) | `head.data[local_rows]` indexes weight rows directly, as the original code did; packed quantized weights are not addressed |
| Per-rank cost | `H × hidden` matmul and head memory, i.e. TP=1's profile on every rank | `width × hidden` (≈ `H / tp` for balanced maps) plus the per-step gather |

The point of the replicated design is exactness: TP>1 with the map behaves exactly like the TP=1 configuration that already works, so a map used to *restrict* the draft vocabulary (not just to shrink the head) keeps that guarantee at every TP size. The price is the replicated hot head noted above.

For reference on the quantized-head row: on `Qwen3.8-27B-NVFP4` the target `lm_head` is `ModelOptFp4LinearMethod` (packed `uint8 [124160, 2560]` + block scales), where raw row indexing selects packed bytes — that is what the `ValueError` in this PR guards against. #43249's end-to-end run used an NVFP4 checkpoint whose head apparently is not block-quantized.

#42424's analysis that 56/136 model files pass `use_attn_tp_group` (lm_head shards over `attn_tp_size`, which can be 1 under attention DP) is also relevant to both PRs; this PR guards that case explicitly rather than deriving shard width from `tp_size`. A TP=2 regression test is registered in the CI suite (`test/registered/spec/eagle/test_spec_token_map_tp.py`), alongside CPU unit tests for the assembly.

Happy to rebase or help review whichever design the maintainers prefer.
