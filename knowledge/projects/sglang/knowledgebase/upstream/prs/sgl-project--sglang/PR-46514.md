# [Fix] [Intel] qwen4_decode: Import CustomAllReduceV2 lazily

[Upstream PR](https://github.com/sgl-project/sglang/pull/46514) · state: open · merged: False

## Original PR description

## Motivation

#46417 skipped the `CustomAllReduceV2` import on XPU in `dp_attention.py`: `custom_all_reduce_v2` pulls in `tvm_ffi`, which is not in the XPU image, and the module-level import made every XPU launch fail.

`qwen4_decode.py` still has the same module-level import, and after that PR it is the only one left — every other import site is TYPE_CHECKING-guarded or function-lazy. It only fires when a Qwen4-Exp model loads on XPU (qwen4_exp imports it lazily at model init), which is why the XPU CI never saw it, but there it dies the same way:

```
ModuleNotFoundError: No module named 'tvm_ffi'
```

## Modifications

The name moves under TYPE_CHECKING for the annotations, and the two runtime uses import it inside their functions. Both sit behind `prepare_qwen4_decode_comm`'s `not torch.cuda.is_available()` early return, so on XPU (and anywhere without a CUDA device) the import is never executed — the fast path returns None before reaching it.

No behavior change on CUDA/ROCm: same import, just bound at first use of a cached, called-once constructor.

This is also the convention the neighboring communication modules (`k3_sp_collective`, `k3_ar_fusion`, `muse_spark_gemm_ag`) already use for this import.

## Accuracy Tests

No inference-path change. Ran ruff format, the pre-commit ruff selection, and py_compile locally. No XPU machine on my side, so the XPU claim is import-graph reasoning on top of what #46417 documented for the image.
