## Motivation

`UnifiedSWAAllocatorBase` (`--enable-unified-memory` with a hybrid sliding-window model) filtered every segment free by swa liveness with a boolean mask (`reps[swa_v2p > 0]`). A mask index runs `nonzero`, which copies its count to the host and blocks the scheduler until the in-flight forward drains, so under the overlap scheduler the next batch is prepared only after the GPU went idle. In gpt-oss-20b serving traces (SM90, page size 256) the free of tokens that left the window (`free_swa_segment`) and the request release (`_release_page_reps` at `free_group_end`) issued about 2.6 such syncs per prefill. Prefill cycles ran +1.3..+3.3% (speculative) and +2.5..+7.0% (non-speculative) longer than with the paged SWA allocator at matched batch size, all of it GPU idle.

## Modifications

Two-pool allocation reclaim flushes the deferred FULL-only segment queue before sizing eviction. A regression test fills that queue alone and verifies allocation succeeds without evicting the tree.

The paged SWA allocator frees the same segments with a fixed shape: its callers split a kv row by host bookkeeping, and it trusts that split. The unified callers make the same split: `free_kv_row_segments` sends `[swa_dead_lo, swa_evicted_seqlen)` through `free_full_segment`, the tree picks `FreeDeviceKV` or `FreeDeviceKVFullOnly` per node, and the out-of-window free releases only tokens above `swa_dead_lo`, with a cursor that only moves up. So `free_swa_segment` and `free_segment` now free every page they are handed on the swa side, and `free_full_segment` releases the full side only, through its own deferred list for the free group (`full_free_group`), which `flush_deferred_full_frees` also drains when Mamba state needs memory. Each checks its premise with `expect`, as the paged allocator's `swa.peer_mapped` does: asynchronous, and loud from `SGLANG_INVARIANT_CHECK=warn` up. The two invariants are declared in `allocator/swa.py` beside the paged allocator's: the registry refuses a name it already holds, and a test fixture that patches `sys.modules` makes the next test import `unified_hybrid_swa` again. Page size 1 takes the same path. The set-shaped `free()` and `free_swa()` keep their filter; `RecoverSWAWithLockedFull` relies on it.

A second out-of-window free over the same range was filtered to a no-op. No caller issues one; under strict checks it is now reported instead.

Tests (CPU):
- `test_segment_frees_dispatch_no_data_dependent_shape` records, with a `TorchDispatchMode`, every op whose output shape depends on values (a boolean-mask index, `nonzero`, `unique`, `item`). Before: three mask indexes at page size 1 and at 4. After: none, and both sides' capacity comes back.
- `test_a_double_ratchet_is_reported` (replaces `test_double_ratchet_is_filtered_not_crashed`) and `test_a_full_only_free_of_a_bound_swa_page_is_reported` fail before (nothing raises) and pass after.
- The test that reclaims full-attention KV for Mamba state (on a model with both Mamba state and sliding-window layers) and the eviction fixture name the new list.
- `test_importing_the_module_again_registers_nothing_twice` runs the module again as such a fixture does: a duplicate-invariant error before, none after (`test_lmcache_component_cursors.py` errors in 3 of its 4 cases with the invariants in `unified_hybrid_swa` and passes with them in `allocator/swa.py`).
- The unified-memory CPU tests pass with `SGLANG_INVARIANT_CHECK=2` exactly as without it, so none of them frees an already released sliding-window page through a segment free.

**[bug]** Two-pool `evict_to_free_tokens` still flushes the old 3-tuple, so this new list is invisible there.

`_flush_deferred_free_group` returns when `not any(pending_groups)`. After this change, `free_full_segment` queues into `full_page_reps_group` instead of `free_page_reps_group` (or `full_free_group` at page size 1). A group that only has those full-only segment frees is treated as empty on the two-pool path (`UnifiedSWAAllocatorBase.evict_to_free_tokens`) and left queued, so `reclaim_plan` can over-evict or fail while the pages are already waiting to be released. The tri-pool override goes through this method and is fine; gpt-oss is two-pool.

**Suggestion:** Pass `self.full_page_reps_group` in the two-pool tuple as well, or share one pending-groups helper with this flush.
