# [unified-memory] Free SWA segments without a host sync

[Upstream PR](https://github.com/sgl-project/sglang/pull/43170) · state: open · merged: False

## Original PR description

## Motivation

`UnifiedSWAAllocatorBase` (`--enable-unified-memory` with a hybrid sliding-window model) filtered every segment free by swa liveness with a boolean mask (`reps[swa_v2p > 0]`). A mask index runs `nonzero`, which copies its count to the host and blocks the scheduler until the in-flight forward drains, so under the overlap scheduler the next batch is prepared only after the GPU went idle. In gpt-oss-20b serving traces (SM90, page size 256) the out-of-window ratchet (`free_swa_segment`) and the request release (`_release_page_reps` at `free_group_end`) issued about 2.6 such syncs per prefill. Prefill cycles ran +1.3..+3.3% (speculative) and +2.5..+7.0% (non-speculative) longer than with the paged SWA allocator at matched batch size, all of it GPU idle.

## Modifications

The paged SWA allocator frees the same segments with a fixed shape: its callers split a kv row by host bookkeeping, and it trusts that split. The unified callers make the same split: `free_kv_row_segments` sends `[swa_dead_lo, swa_evicted_seqlen)` through `free_full_segment`, the tree picks `FreeDeviceKV` or `FreeDeviceKVFullOnly` per node, and the ratchet frees only above `swa_dead_lo` with a cursor that only moves up. So `free_swa_segment` and `free_segment` now free every page rep on the swa side, and `free_full_segment` releases the full side only, through its own free-group pile (which the mamba donor's flush also sees). Each checks its premise with `expect`, as the paged allocator's `swa.peer_mapped` does: asynchronous, and loud from `SGLANG_INVARIANT_CHECK=warn` up. The two invariants are declared in `allocator/swa.py` beside the paged allocator's: the registry refuses a name it already holds, and a test fixture that patches `sys.modules` makes the next test import `unified_hybrid_swa` again. Page size 1 takes the same path. The set-shaped `free()` and `free_swa()` keep their filter; `RecoverSWAWithLockedFull` relies on it.

A second ratchet over a range was filtered to a no-op. No caller issues one; under strict checks it is now reported instead.

Tests (CPU):
- `test_segment_frees_dispatch_no_data_dependent_shape` records, with a `TorchDispatchMode`, every op whose output shape depends on values (a boolean-mask index, `nonzero`, `unique`, `item`). Before: three mask indexes at page size 1 and at 4. After: none, and both sides' capacity comes back.
- `test_a_double_ratchet_is_reported` (replaces `test_double_ratchet_is_filtered_not_crashed`) and `test_a_full_only_free_of_a_bound_swa_page_is_reported` fail before (nothing raises) and pass after.
- The tri-pool donor test and the eviction fixture name the new pile.
- `test_importing_the_module_again_registers_nothing_twice` runs the module again as such a fixture does: a duplicate-invariant error before, none after (`test_lmcache_component_cursors.py` errors in 3 of its 4 cases with the invariants in `unified_hybrid_swa` and passes with them in `allocator/swa.py`).
- The unified CPU scope passes with `SGLANG_INVARIANT_CHECK=2` exactly as without it, so no flow in it frees a tombstoned swa page through a segment free.

## Accuracy Tests

SM90, TP1, gpt-oss-20b, no speculation, radix cache, overlap scheduler, CUDA graphs on, `--mem-fraction-static 0.8`. Baseline: the default pool. Unified: `--enable-unified-memory`. Every server ran with the per-step pool checks and the allocator invariants on (`SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY=1 SGLANG_CHECK_KV_PAGE_INVARIANTS=1 SGLANG_INVARIANT_CHECK=1`), so a free that this change gets wrong stops the server or is reported. GSM8K, all 1314 test questions, 5-shot, greedy:

| page size | backend | baseline | unified |
|---|---|---|---|
| 256 | triton | 0.572 | 0.527 |
| 256 | fa3 | 0.559 | 0.588 |
| 1 | triton | 0.551 | 0.561 |
| 1 | fa3 | 0.565 | 0.591 |

gpt-oss-20b's GSM8K score moves by several points between identical runs (up to ~6 in our runs of one configuration), and three of the four rows favour the unified pool.

Under the same checks, a load test at page size 256: one that forces retraction (one 4096-token system prompt, 192 requests with 128-token questions and 2048 output tokens, concurrency 192) and one with long outputs (100 requests, 512 input / 4096 output tokens, concurrency 128). Every request completed on both arms and both backends, and no server reported a leak, double free, invariant violation or illegal memory access.

## Speed Tests and Profiling

`bench_serving` with random prompts at concurrency 64, in two shapes: 2048 input / 512 output tokens (200 prompts) and 8192 input / 64 output tokens (100 prompts). gpt-oss-20b, no speculation, page size 256, radix cache, overlap scheduler, CUDA graphs on, `--mem-fraction-static 0.55`. Each entry is the unified pool's gap to the default pool on the same tree, before (main) and after this PR; the default pool runs twice and the gap is against the mean of the two runs, with their spread (A/A) as the noise floor.
