# [Feat] engine_snapshot: Add CRIU-based engine initialization snapshot and restore

[Upstream PR](https://github.com/sgl-project/sglang/pull/40736) · state: open · merged: False

## Original PR description

## Summary

This RFC proposes adding initialized engine snapshots to sglang:
```
sglang snapshot create [options] -- <server args>   # boot once, capture, exit
sglang snapshot restore <artifact-dir> [--host H] [--port P]
sglang snapshot inspect <artifact-dir> [--verify-files] [--json]
```

`create` boots the engine through the normal launch path and captures the whole process tree into a snapshot artifact: CPU state via CRIU, GPU contexts via NVIDIA `cuda-checkpoint`. The capture point is deterministic: **fully initialized, before HTTP binds**.

`restore` recovers the sglang process from a snapshot produced by `create` and serves requests. It skips engine initialization, JIT compilation and CUDA graph capture, so startup is much faster.

`inspect` checks the contents of an artifact produced by `create`.

vLLM already has a similar implementation: [vLLM PR #51360](https://github.com/vllm-project/vllm/pull/51360).

Scope of this PR: TP=1, a single GPU, same host, model and software stack. Weights are re-read from the original path, not stored in the artifact. Anything else is out of scope.

## Motivation

The engine spends most of its startup time on initialization and CUDA graph capture. Measured on a single NVIDIA GPU, Qwen3-8B BF16, TP=1, with weights staged in memory (`/dev/shm`) so disk reads do not affect the timing:

| Stage | Time |
| --- | --- |
| Init torch distributed | ~0.03 s |
| Load weights (15.3 GB) | ~2.5 s |
| Capture prefill CUDA graphs | ~26 s |
| Capture decode CUDA graphs | ~3.4 s |
| **Total to `/health` 200 (KV pool allocation and remaining init included)** | **~53 s** |

CUDA graph capture alone accounts for ~29 s of the measured startup. Weight caching ([#27139](https://github.com/sgl-project/sglang/pull/27139)) cannot eliminate graph capture or the other initialization steps. A snapshot skips the initialization phase entirely: a measured restore completes in 16.6 s.

Use cases:
- **Fast scaling**: engine replicas (e.g. for PD-disaggregated or elastic deployments) start from a snapshot, so graph capture is not repeated for each replica.
- **Fast recovery**: a crashed or preempted engine returns to service in seconds instead of a minute or more.

## Prior discussion and related work
- [#27139 (weight cache daemon)](https://github.com/sgl-project/sglang/pull/27139) — complementary: it removes the weight-load step; a snapshot restore also skips initialization, JIT compilation and CUDA graph capture. Our create/restore reuses sglang's existing memory-saver release/resume path, as does the weight cache.
- [#39683 (cold-start process init)](https://github.com/sgl-project/sglang/pull/39683) — complementary: it shortens process initialization on the normal launch path (fork-safe imports, an early forkserver and pre-spawned workers behind opt-in flags). Workers then fork instead of re-importing. It leaves weight loading and CUDA graph capture untouched; a snapshot restore skips those along with the rest of initialization.
- [#30226 (lighter top-level import)](https://github.com/sgl-project/sglang/pull/30226) — orthogonal: it trims the cost of `import sglang` by moving heavy runtime deps off the top-level path. It targets launcher and frontend startup and does not interact with the snapshot mechanism.
- [#27310 (GPU Memory Service RFC)](https://github.com/sgl-project/sglang/issues/27310) — orthogonal: out-of-process memory management; a snapshot restore works with it in principle but does not depend on it.
- This PR depends on sglang's existing `--enable-memory-saver`, `release_memory_occupation`, `resume_memory_occupation` and `update_weights_from_disk`.

## Design

### The snapshot boundary

The capture point is after `_launch_subprocesses` completes (weights loaded, KV pool allocated, CUDA graphs captured) and before the HTTP service binds. At this point:
- the state is deterministic: there are no in-flight requests and no HTTP service yet, so there is no complex network state to handle;
- the engine is ready, so a canary (a correctness probe) can verify that inference results are correct before and after the snapshot.

### Artifact contents

One artifact directory per snapshot, containing:
- CRIU images of the sglang process tree (launcher/tokenizer-manager, scheduler, detokenizer, resource tracker), plus the GPU data exported by `cuda-checkpoint`;
- files produced by sglang: caches created during initialization, such as the sglang JIT, Triton and FlashInfer caches;
- the `/dev/shm` contents: temporary files used by sglang, such as `sglang_loads_*.shm`, plus the link-remap files produced by the CRIU dump;
- `manifest.json`: snapshot metadata such as the model path, the model file inventory and the torch, sglang-kernel and CUDA versions.

Model weights are **not** in the artifact. Restore re-reads them from the original `model_path` via the normal loading path. For Qwen3-8B the artifact is 4.6 GB, while the weights alone are 15.3 GB.

### Flow

This PR implements snapshot creation and restore as CLI commands. A CLI process, the controller, starts and stops the engine.

### Create flow
1. Environment check: the controller validates the provided arguments and checks that CRIU and the other tools are available;
2. Start the engine: the controller launches the engine with the provided arguments;
3. Reach the sync point: the engine starts normally, completes initialization (weight loading, KV pool allocation and CUDA graph capture) and runs the canary check;
4. Create the snapshot: the controller dumps the engine process tree using `cuda-checkpoint` and CRIU, and saves the accompanying files;
5. Once the snapshot is complete, the engine exits.

### Restore flow
1. Snapshot validation: the controller validates the snapshot using the manifest file;
2. Snapshot restore: the controller restores the accompanying files and recovers the engine process tree using `cuda-checkpoint` and CRIU;
3. Correctness check: the engine runs a canary inference and passes the result to the controller for verification;
4. Restore complete: the engine serves HTTP normally.

## Runtime requirements and constraints
- Linux >= v5.3 (pidfd support);
- CRIU 4.x;
- NVIDIA `cuda-checkpoint`;
- io_uring disabled.

## Measurements

Qwen3-8B BF16, TP=1, a single NVIDIA GPU, CRIU 4.2 + NVIDIA `cuda-checkpoint`.

|  | Time |
| --- | --- |
| Cold start → `/health` | ~53 s |
| `snapshot create` | 68.3 s |
| `snapshot restore` | 16.6 s (Python startup and imports ~5 s, identity check ~0.4 s, CRIU restore ~1.2 s, CUDA context restore ~0.6 s, weight re-read ~3 s, engine resume to ready ~6 s) |

## Roadmap
- **Phase 1** (this PR): TP=1, single GPU, in-place create/restore.
- **Phase 2**: TP=1, single GPU, cross-host create/restore.
- **Phase 3**: TP>1, multi-GPU on a single host, create/restore.
