# [model-gateway] Release prefill worker load when the prefill response arrives

[Upstream PR](https://github.com/sgl-project/sglang/pull/39951) · state: closed · merged: False

## Original PR description

## Motivation

In PD mode the router counts a request against both its prefill and its decode
worker and releases both counts when the client response body is dropped. The
prefill worker is done with a request as soon as it has answered, so its load
stays inflated for the whole decode phase and ends up measuring "requests that
passed through this worker and are still decoding" rather than "requests this
worker is still working on".

With `--prefill-policy cache_aware` this hides idle prefill workers from the
balance check. On a 24P/24D production cell serving long prompts, 15 prefill
workers had an empty engine queue while the router saw ~16 in-flight requests
on each of them, the same as on the workers with 20 requests queued, so traffic
kept going to the cache-preferred workers and adding prefill workers did not
help.

## Modifications

All changes are in `sgl-model-gateway/src/routers/http/pd_router.rs`.

- `execute_dual_dispatch_internal` creates the prefill `WorkerLoadGuard` at dispatch for both streaming and non-streaming requests, and drops it as soon as the prefill response status is confirmed successful, before awaiting the decode response. Every error path (request preparation failure, prefill failure, decode error status, transport error) drops it exactly once by falling out of scope.
- `create_streaming_response` attaches only the decode guard to the streaming response body. Its unused prefill worker parameter is removed, along with the same parameter on `handle_decode_error_response`.
- Decode load accounting, the routing policies and the balance thresholds are unchanged.

Two regression tests (`test_prefill_load_released_on_prefill_response_streaming` and `..._non_streaming`) run a mock prefill server that holds its response and a mock decode server that holds its response, and check three points: prefill load is 1 while the prefill response is pending, prefill load is 0 and decode load is 1 while decode is still generating, and both are 0 after the response is dropped. Both tests fail on the current `main` and pass with this change. The existing `test_streaming_load_tracking` expectations are updated to the new prefill lifetime.

Related: #34850 moves the streaming guards to dispatch time; this PR is independent of it and only changes when the prefill guard is released. #27547 reported the same symptom (all long-input requests herded onto one prefill worker).
