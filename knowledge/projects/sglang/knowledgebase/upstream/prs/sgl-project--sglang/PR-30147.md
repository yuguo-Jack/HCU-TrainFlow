# [MLX] Fix decode-KV pool sync writing to unallocated or stale slots

[Upstream PR](https://github.com/sgl-project/sglang/pull/30147) · state: closed · merged: False

## Original PR description

## Summary

Part of #30093.

MLX overlap chained decode steps advance per-request cache offsets without allocator bookkeeping, so `_sync_decode_kv_to_pool` read `req_to_token` positions the scheduler never wrote and treated them as pool slot ids:

- **fresh row**: reads zeros, so decode KV lands in reserved padding slot 0 and is silently dropped for radix reuse
- **reused row**: reads a previous request's slot ids, so another live request's KV gets overwritten (silent wrong output on a later radix hit)

Both are deterministic once the preconditions line up, on the default MLX serving path (radix on, overlap on).

## Fix

**1. Clamp the sync window to the scheduler-committed bound.** The TP worker records each request's committed row length on every scheduler-built forward (prefill, extend, decode) via `note_committed_len`; chained steps deliberately leave the bound untouched. `_sync_decode_kv_to_pool` clamps to that bound, so chain-produced tokens stay non-cacheable until the scheduler commits their positions. A later sync recovers the clamped range from the still-live per-request cache once the allocator catches up, so post-chain decode KV still reaches the pool.

**2. Flush a finished request's committed decode KV before its row is freed.** `prepare_for_kv_cache_release` now syncs at the radix-insert point, while the request still owns its `req_to_token` row. `release_kv_cache` (called right after) frees the row for reuse, and without this a later `remove_request` sync could read the new owner's slot ids out of the reused row.

## Tests

`test/registered/unit/hardware_backend/mlx/test_decode_kv_pool_sync.py` drives the real `_sync_decode_kv_to_pool` through both repro scenarios from the issue (fresh row, reused row), the committed fast path, the post-chain catch-up path, and the release-before-reuse window. Reverting either the clamp or the release flush turns the corresponding tests red.

On the MLX backend it already lives on CPU (the stub creates `ReqToTokenPool(..., device="cpu")` and `ScheduleBatch` inherits that device), so `.cpu()` returns the same object without a copy. Nothing here touches the Metal stream, so it can't force pending lazy MLX work to evaluate.

Chained decode steps never call `_note_committed_lens` (that's part of the fix, they must not advance the committed bound). It only runs on scheduler-built launches, where the extend path already does `input_ids.cpu().tolist()` right below. I timed the whole function anyway: 0.2us at bs=1, 2.3us at bs=64, vs ~7ms for one decode step.
