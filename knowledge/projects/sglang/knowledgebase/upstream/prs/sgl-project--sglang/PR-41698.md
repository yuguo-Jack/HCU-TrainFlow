# [Perf] [AMD] dsa: Fuse AITER decode RoPE and KV-cache preparation

[Upstream PR](https://github.com/sgl-project/sglang/pull/41698) · state: open · merged: False

## Original PR description

# [AMD] Fuse AITER DSA decode RoPE and KV-cache preparation

**Depends on:** #39083 and #41697

## Motivation

The ROCm MLA path already has a fused operation that applies RoPE, concatenates
the absorbed query, and writes the KV cache. DSA decode using the AITER backend
did not select that path, so it applied RoPE separately before entering the
attention core.

## Modifications

- Recognize AITER DSA decode on ROCm gfx950 as eligible for fused RoPE and
  KV-cache preparation.
- Defer RoPE from the prepare phase to the existing fused operation in the
  attention core.
- For FP8 KV-cache AITER DSA decode, emit FP8 `q_cat` from fused preparation.
  Together with #39083's explicit query/KV scales and BF16 output contract,
  this moves decode from AITER's `a16w8` kernel to its `a8w8` kernel.
- Preserve the existing behavior for other architectures and DSA backends.
- Keep AITER DSA on the already-absorbed query path rather than enabling the
  separate fused absorb optimization.

## Accuracy Tests

Unit coverage verifies AITER DSA fused-preparation dispatch and ensures the
separate fused-absorb predicate remains unaffected.

A registered MI355X regression exercises the production FP8 path end to end:
fused preparation emits FP8 `q_cat`, `_forward_aiter` consumes it with an FP8
KV cache and explicit scales, and decode produces finite BF16 output.

On MI355X TP4 with `amd/GLM-5.2-MXFP4`, FP8 KV cache, AITER prefill/decode and
CUDA graphs, the complete #39083/#41696-#41698 stack completed the full
1,319-example 5-shot GSM8K evaluation:

- strict exact match: 0.9272 ± 0.0072;
- flexible exact match: 0.9265 ± 0.0072.

Parent and candidate also produced exact matching text and exact matching
retokenized output for fixed-seed 60k-input/600-output greedy generation.

## Speed Tests and Profiling

Hardware: AMD MI355X, TP4, `amd/GLM-5.2-MXFP4`, FP8 KV cache.

To isolate decode backend selection, prefill remains AITER in all three arms:

| Workload | AITER prefill / Triton decode | AITER prefill / AITER decode with #41697 | AITER prefill / AITER decode with #41698 | #41698 vs Triton decode |
|---|---:|---:|---:|---:|
| 8k input, concurrency 16 | 693.15 tok/s | 587.21 tok/s | 727.01 tok/s | **+4.89%** |
| 8k input, concurrency 64 | 1,268.43 tok/s | 985.12 tok/s | 1,360.03 tok/s | **+7.22%** |
| 60k input, concurrency 4 | 133.75 tok/s | 90.44 tok/s | 135.02 tok/s | **+0.95%** |
| 60k input, concurrency 16 | 174.85 tok/s | 114.03 tok/s | 184.58 tok/s | **+5.57%** |

Metadata reuse alone does not make AITER decode faster than Triton decode.
With fused preparation added, AITER decode is faster at all four tested points
when prefill is held constant.

## Reproduction

Launch the candidate on MI355X:

```bash
SGLANG_USE_AITER=1 python3 -m sglang.launch_server \
  --model amd/GLM-5.2-MXFP4 \
  --tp 4 \
  --trust-remote-code \
  --attention-backend dsa \
  --dsa-prefill-backend aiter \
  --dsa-decode-backend aiter \
  --dsa-topk-backend sgl-kernel \
  --kv-cache-dtype fp8_e4m3 \
  --page-size 64 \
  --enforce-shared-experts-fusion \
  --cuda-graph-max-bs-decode 256 \
  --disable-radix-cache \
  --chunked-prefill-size 32768 \
  --max-prefill-tokens 32768
```

For the Triton decode control, change only `--dsa-decode-backend` from `aiter`
to `triton`.

After an unrecorded 60k-input/8-output warmup at concurrency 4 and seed 0, run:

- 8,192 input / 1,024 output, concurrency 16, seed 6, 96 prompts;
- 8,192 input / 1,024 output, concurrency 64, seed 10, 256 prompts;
- 60,000 input / 600 output, concurrency 4, seed 15, 32 prompts;
- 60,000 input / 600 output, concurrency 16, seed 16, 96 prompts.

File: `python/sglang/srt/models/deepseek_common/attention_forward_methods/forward_mla_rocm.py` · line 1108

With `--kv-cache-dtype fp8_e4m3`, this sends AITER DSA decode through `_fused_rope_cat_and_cache`, which returns FP8 `q_cat`. `_forward_aiter` then passes `q_scale=None` and allocates `o` with `q.new_empty`, so `o` is FP8 too. On pinned AITER `e7d2453f` this aborts in `mla_decode_stage1_asm_fwd` ("fp8 Q requires q_scale and kv_scale"). With a unit `q_scale` it aborts in `kn_mla_reduce_v1` instead (no FP8 output). I reproduced both on MI355X with the same calls. Suggest keeping BF16 q for AITER DSA in `q_out_dtype`, like the existing `current_attention_backend == "aiter"` case.

- pbkowalski · comment · 2026-10-12T14:49:44Z · [source](https://github.com/sgl-project/sglang/pull/41698#discussion_r4249337545)

File: `python/sglang/srt/models/deepseek_common/attention_forward_methods/forward_mla_rocm.py` · line 1108

This is correct and a good catch; the reason this bug sneaked through is that this PR was tested in conjunction with #39083, which while being primarily a correctness fix also defines the shared FP8 DSA decode contract:
  • If the query is FP8, allocate o and o_kernel as BF16.
  • Pass an identity q_scale.
  • Pass the KV scale from the attention layer, falling back to an identity scale.
As such I incorporated #39083 into this branch so it is included in the CI and also explicitly listed it as a dependency.

The BF16 fallback works, but it negatively affects performance.  Keeping FP8 Q preserves the implementation that produced the measured uplift.
