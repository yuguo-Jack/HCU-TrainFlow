# [Fix] attention: Use ModelRunner query width for DSpark FlashAttention drafts

[Upstream PR](https://github.com/sgl-project/sglang/pull/46478) · state: closed · merged: True

## Original PR description

Fixes #46476.

## Motivation

For DSpark draft checkpoints with `sample_from_anchor=False` such as DFlash style checkpoints, the draft forward pass produces **γ+1 query rows per request**, but `FlashAttentionBackend` previously used the generic target verification resolver, which returned **γ rows** for draft workers. This mismatch produces incorrect `cu_seqlens_q` request boundaries in FA3/FA4 when multiple draft requests are batched. The server may continue running, but draft acceptance degrades as batch size increases. With `sample_from_anchor=True`, the correct width remains γ.

`ModelRunner.decode_num_tokens_per_req()` already implements the checkpoint dependent draft width contract. The attention backend should use that same source of truth.

## Modifications

- Use `model_runner.decode_num_tokens_per_req(num_draft_tokens=...)` when initializing the FlashAttention draft worker's static query width, replacing the independent `target_verify` resolution.
- Add regression tests for both FA3 and FA4 metadata, covering:
  - DSpark draft with `sample_from_anchor=False` (γ+1 rows).
  - DSpark draft with `sample_from_anchor=True` (γ rows).
  - DSpark target and non-DSpark (EAGLE) draft behavior.
  - Both regular forward and CUDA Graph metadata (`cu_seqlens_q`), including the flattened query length for the affected case.

The runtime fix is localized to `FlashAttentionBackend` and does not change the draft forward implementation or the model runner's existing width calculation.

## Accuracy Tests

- **PASS:** Focused unit tests in `test/registered/unit/layers/attention/test_flashattention_graph_metadata.py` and `test/registered/unit/layers/attention`.
- The tests construct FA3/FA4 attention metadata with mocked kernel imports and check the cumulative query boundaries for each configuration. For the affected DSpark case at batch size 2, they verify `[0, 8, 16]` rather than the incorrect `[0, 7, 14]`.

## Speed Tests and Profiling

No new end-to-end benchmark is claimed for this upstream PR. The prior FA3 reproduction documented in #46476 used Fun-CosyVoice3 with a SpeechSpec DSpark draft on one H100, evaluating 2,020 Seed-TTS Chinese prompts:

| Batch size | Tokens/verify before | Tokens/verify after |
| ---: | ---: | ---: |
| 1 | 3.01 | 3.04 |
| 8 | 2.37 | 3.03 |
| 16 | 1.81 | 3.03 |
| 64 | 1.27 | 3.03 |

At batch size 64, reported LLM throughput relative to non-speculative decoding improved from **0.78× to 1.38×** after correcting the width. These numbers are **prior downstream reproduction results**, not a fresh performance measurement on this PR's head SHA. FA4 has source-level and unit-test coverage here, but no independent GPU benchmark is claimed.
