# [Perf] dsv41: Pick the Engram DP lookup collective automatically

[Upstream PR](https://github.com/sgl-project/sglang/pull/46917) · state: closed · merged: True

## Original PR description

- `--engram-config` `lookup` gains `auto` (the new default), `all_reduce`, `reduce_scatter` and `all_to_all`, next to `peer_read`; `collective`, the old default, is still accepted as `auto`.
- Under DP attention, every rank needs rows for its own tokens while each Engram table is split across the TP group. For eager prefill (SUM_LEN) batches on CUDA with one DP rank per TP rank, the lookup now gathers the hash ids with `all_gatherv` and then:
  - `all_to_all`: each rank looks up only the hash columns it holds, for every rank's tokens, and sends each rank its part; it moves 1/tp of the bytes the reductions move. It needs the 24 hash columns to divide over the TP group.
  - `reduce_scatter`: the zero-filled lookup summed with a variable-length reduce-scatter.
- `auto` picks `all_to_all` whenever the columns divide. Decode (MAX_LEN) batches, CUDA-graph captures, prefill CP, ROCm and layouts the columns do not divide over keep their current collective, as does `all_reduce`. The choice no longer depends on `SGLANG_DP_USE_GATHERV`.
- An explicit `reduce_scatter` or `all_to_all` is rejected at startup without DP attention on CUDA, and `all_to_all` when the columns do not divide over `--tp-size`.
- Docs: the Engram tables page explains the choices and how `auto` picks; the server argument row lists the values.

No behavior change outside eager prefill lookups under DP attention on CUDA; those return the same rows, bit for bit.

Related: #46338 (reduce-scatter for uniform prefill batches of 32K rows or more per rank).

## Microbenchmark

One DeepSeek-V4.1-Flash Engram layer at its real size (24 hash columns, 256-wide rows) as a host `per_rank` table, each rank bound to its GPU's NUMA node; the full DP lookup (gather the ids, look up the rows, exchange them), eager, slowest rank's median per layer. Every `all_to_all` result was checked bit for bit against `reduce_scatter`, in all 144 shapes.

`all_to_all` is the fastest choice almost everywhere and never slower than `all_reduce` by more than 8 us. On GB300 at DP 2, `reduce_scatter` is about 5% ahead at large batches: `all_to_all` then spends ~440 us at 32K tokens per rank reordering the received rows from [source rank, token] to [token], a copy that can later fold into the quantization before `wkv`.

## Checks

- The `EngramEmbedding` DP lookup itself on GB300, DP 2 and 4, host `per_rank`, randomly filled rows: `reduce_scatter`, `all_to_all` and `auto` match `all_reduce` bit for bit with uniform, skewed, one empty rank, and 3-6 tokens per rank. At 32K tokens per rank, DP 4: `all_reduce` 5,860 us per layer, `auto` 2,765 us.
- Serving on GB300, DP 2 with MegaMoE, host `per_rank` tables and DSpark, 16K-token prompts with 1 output token at concurrency 64: input throughput 141,733 and 144,409 tok/s with `all_reduce`, 143,798 / 140,759 / 142,753 / 143,391 tok/s with `auto`, within run-to-run spread (the change saves about 0.5 ms of a ~115 ms step at 8K tokens per rank).
