# [Perf] [AMD] kda: Use a HIP fused decode kernel by default for KDA (Kimi-K3) on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45713) · state: closed · merged: True

## Original PR description

## Motivation

On MI350X / MI355X (gfx950), Kimi-K3 KDA decode runs the unfused chain by default (`f_b` tiny GEMM, causal Conv1D update, Triton recurrent decode, gated RMSNorm), or the AITER FlyDSL fused boundary with `SGLANG_ROCM_K3_KDA_FUSED_BACKEND=aiter`. This PR adds a HIP kernel for the same fused boundary and makes it the default on gfx950. It is the decode companion of #45710 (KDA prefill); the two PRs change disjoint runtime files.

**Note: This kernel is generated by [KDAgent](https://nvlabs.github.io/kda/blog/2026-09-27-kda-for-kda/) in AMD ecosystems. Cost around 5k dollars in humanize2 flow to get this.**

## Modifications

The kernel follows the `sglang.kernels` layout of RFC #29630: it was produced with the Kernel Design Agents workflow, so the implementation lives in `kernels/kda_kernels`, it is registered with `KernelBackend.KDA`, and runtime code reaches it only through the `sglang.kernels.ops` facade.

- `kernels/kda_kernels/csrc/attention/kda_decode_gfx950.cu` and its loader `kernels/kda_kernels/kda_decode_gfx950.py`, JIT-compiled on first use. One 256-thread workgroup per (token, head), for 12 heads of 128 per rank (Kimi-K3 TP8), runs the `f_b` projection, the depthwise Conv1D update with SiLU, the q/k L2 norms and gate decay, the delta-rule update of the 128 x 128 fp32 state, and the gated RMSNorm. State and Conv1D slot strides are read from the tensors, so padded hybrid cache layouts work. Slot 0, the mamba pool's padding slot, returns zeros without touching either cache.
- `kernels/kda_kernels/README.md`: provenance entry.
- `kernels/ops/attention/__init__.py`: registers `attention.kda_decode_gfx950` (`KernelBackend.KDA`, HIP).
- `kernels/ops/attention/kda_fused_decode_gfx950.py` (facade): the same fail-closed `available` / `covered` / `warmup` / `run` interface as `kda_fused_decode_aiter_hip`; `run` calls the kernel through `get_kernel`.
- `srt/models/kimi_k3.py` (ROCm branch of `_prepare_fused_decode`): maps `SGLANG_ROCM_K3_KDA_FUSED_BACKEND` to a facade, `gfx950` (the new default) or `aiter`; any other value keeps the unfused chain. The chosen facade is stored on the layer.
- `srt/layers/attention/linear/kda_backend.py` (gfx950 fused-decode branch): calls the facade stored on the layer instead of the hard-coded AITER adapter.
- `test/registered/kernels/ops/attention/test_kda_fused_decode_gfx950.py` (MI35x suite): matches the Triton chain over 4 steps under the default backend, skips slots <= 0, and CUDA graph replay equals eager.

Behavior change: on gfx950 the fused decode is now on by default. `SGLANG_ROCM_K3_KDA_FUSED_BACKEND=aiter` selects FlyDSL, and any other value (for example `none`) selects the unfused chain. Both edits in `srt/` are inside the existing ROCm-only branches.

## Accuracy Tests

MI355X, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261020`.

- Against a per-token fp32 PyTorch reference (batch 1, 2, 8 and 37 with padded rows, and batch 16 over 64 steps): output relative RMSE at most 7.1e-6 (the Triton chain reaches 1.2e-5 and FlyDSL 2.7e-5 in the same checks). The Conv1D state is bit-identical; padded rows return zeros and slot 0 is untouched.
- Pass: the new test, `unit/kernels/test_kernels_namespace.py` (includes the KDA directory/backend pairing check), `kernels/ops/attention/kda_flydsl/test_kimi_k3_kda_decode.py`, `attention/unittests/kda/test_triton.py`, `attention/test_kda_kernels.py`, `kernels/ops/attention/test_fused_kda_conv_recurrent_verify.py` and `amd/test_kimi_k3_kda_inproj_fusion.py`.
- Kimi-K3 TP8 GSM8K (8-shot, 1319 questions): 0.960 with both HIP kernels off, 0.961 with this PR and #45710 on.

## Speed Tests and Profiling

**Kernel.** Per-layer time inside a 69-layer CUDA graph with a separate cache per layer (median of 11 trials):

| Batch | Triton chain | FlyDSL | HIP | vs Triton chain | vs FlyDSL |
|---|---|---|---|---|---|
| 1 | 11.51 us | 8.54 us | 5.96 us | 1.93x | 1.43x |
| 2 | 11.60 us | 8.45 us | 6.09 us | 1.90x | 1.39x |
| 4 | 13.45 us | 10.44 us | 7.15 us | 1.88x | 1.46x |
| 8 | 27.42 us | 11.82 us | 7.93 us | 3.46x | 1.49x |
| 16 | 29.87 us | 13.92 us | 9.91 us | 3.02x | 1.41x |
| 32 | 33.60 us | 19.65 us | 16.21 us | 2.07x | 1.21x |
| 64 | 38.26 us | 31.50 us | 26.28 us | 1.46x | 1.20x |
| 128 | 61.11 us | 56.29 us | 46.68 us | 1.31x | 1.21x |
| 256 | 108.86 us | 100.83 us | 86.48 us | 1.26x | 1.17x |

For reference, AITER's Triton/Gluon packed KDA decode (not a SGLang backend) is 1.10x-1.30x slower than HIP up to batch 32 and 3%-6% faster from batch 64.

**The model runs the kernel.** Kimi-K3 TP8, rank-0 GPU profile (`/start_profile`) of one 10,244-token request with 8 output tokens (7 decode steps x 69 KDA layers = 483 layer steps):

| Kernels (calls) | Baseline | This PR + #45710 |
|---|---|---|
| KDA decode | `_causal_conv1d_update_kernel` (483), `fused_sigmoid_gating_delta_rule_update_kernel` (483), `layer_norm_gated_fwd_kernel` (483 of 552) | `kda_decode_gfx950_kernel` (483); none of the three |

**Kimi-K3 TP8 E2E.** Measured with this PR and #45710 applied; the baseline sets `SGLANG_ROCM_KDA_HIP_PREFILL=0 SGLANG_ROCM_K3_KDA_FUSED_BACKEND=none`, which is the current `main` behavior. Baseline and candidate servers were launched alternately, two rounds each; the table shows the mean of the two rounds.

```bash
SGLANG_USE_AITER=1 SGLANG_AITER_K3_OPT=1 AITER_FLYDSL_FORCE=1 AITER_SITUV2_A8W4=1 \
python3 -m sglang.launch_server --model-path moonshotai/Kimi-K3 --tp-size 8 \
  --attention-backend triton --dtype bfloat16 --mem-fraction-static 0.85 \
  --cuda-graph-max-bs-decode 64 --max-running-requests 64 \
  --reasoning-parser kimi_k3 --tool-call-parser kimi_k3 --trust-remote-code
python3 -m sglang.bench_serving --backend sglang --dataset-name random-ids \
  --random-input-len 1024 --random-output-len 512 --random-range-ratio 1 \
  --num-prompts 80 --max-concurrency 16 --warmup-requests 16 --flush-cache --seed 42
# also: --num-prompts 320 --max-concurrency 64; and --random-input-len 8192
# --random-output-len 64 --num-prompts 40 --max-concurrency 8 --warmup-requests 8
python3 -m sglang.test.few_shot_gsm8k --num-shots 8 --num-questions 1319 \
  --max-new-tokens 512 --parallel 64
```
