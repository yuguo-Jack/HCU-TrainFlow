# [Fix] scheduler: keep auto-truncated prompts schedulable

[Upstream PR](https://github.com/sgl-project/sglang/pull/48253) · state: open · merged: False

## Original PR description

## Motivation

A prompt longer than the KV pool, sent with `--allow-auto-truncate`, is cut to `max_req_input_len` by the scheduler. Two bugs make that request either generate nothing or never run:

1. **max_new_tokens is clipped against the untruncated prompt.** `handle_generate_request` calls `init_req_max_new_tokens(req)` *before* `validate_input_length` truncates the prompt. When the original prompt exceeds the pool, `max_new_tokens` is clipped to 0 and stays 0 after truncation, so the request finishes with `length` and no output.
2. **With `page_size > 1` the truncated request is never admitted.**
   - `max_req_input_len = max_req_len - 5` ignores page rounding.
   - `max_new_tokens_for_memory` clips `max_new_tokens` to `capacity - ceil_page(prompt) - page_size - 1`, which is 0 within a page of the pool size.
   - `PrefillAdder` still needs `prompt + max_new_tokens + page_size < capacity`.
   - The request stays at the head of the FCFS queue forever and every later request waits behind it.
   - The same happens without auto-truncate for an untruncated prompt in that last page (e.g. 4080 tokens in a 4096-token pool with page size 16): it passes validation and then never runs.

Repro: Qwen/Qwen2.5-0.5B-Instruct, `--max-total-tokens 4096 --allow-auto-truncate --page-size P`. One 8192-token prompt (`max_new_tokens=16`), then a short prompt 3 s later. Timeouts: long 120 s, short 60 s.

| page size | main: long request | main: short request | this PR: long request | this PR: short request |
|---|---|---|---|---|
| 1 | 4090 prompt tokens, **0** output tokens | served | 4090 prompt, 4 output | served |
| 16 | **hangs** (timeout) | **hangs** (timeout) | 4064 prompt, 15 output | served |
| 64 | **hangs** (timeout) | **hangs** (timeout) | 3968 prompt, 16 output | served |

Without `--allow-auto-truncate`, page size 16, a 4080-token prompt: main hangs and blocks the short request. With this PR it is rejected with the existing `Input length ... exceeds the maximum allowed length (4064 tokens)` error (HTTP 400), and the short request is served.

## Modifications

- `scheduler.py`: `_validate_input_and_init_max_new_tokens(req)` validates (and possibly truncates) the prompt, then calls `init_req_max_new_tokens(req)`, so `max_new_tokens` is clipped against the prompt that remains. `handle_generate_request` uses it; the init still happens before the error return.
- `managers/utils.py`: `max_schedulable_input_len(*, max_req_len, kv_capacity, page_size, kv_shard_widening)` returns `min(max_req_len - 5, floor_page(kv_capacity - page_size * kv_shard_widening - 2))`.
  - This is the longest prompt whose page-rounded length, the reserved page per KV shard and one new token fit an empty pool, matching `init_req_max_new_tokens` and PrefillAdder's per-request overhead.
  - `TpModelWorker.get_worker_info` uses it for `max_req_input_len`, passing the page-interleave shard count it already multiplies into `kv_capacity`.
- The value is unchanged whenever `floor_page(kv_capacity - page_size * kv_shard_widening - 2) >= max_req_len - 5`. For example: `page_size == 1` without KV sharding, or a pool comfortably larger than the context length.

## Accuracy Tests

- Unchanged for prompts below the old limit. Same GPU, `--enable-deterministic-inference`, Qwen/Qwen2.5-0.5B-Instruct, 4 greedy prompts x2 plus a batch of 4: generated text is byte-identical between main and this PR.
- The only output change is the intended one: truncated prompts now generate tokens instead of 0 or a hang (table above).
