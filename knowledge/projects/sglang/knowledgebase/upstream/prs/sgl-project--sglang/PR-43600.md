# [Perf] mem_cache: Batch the KV release of requests that finish in the same step

[Upstream PR](https://github.com/sgl-project/sglang/pull/43600) · state: open · merged: False

## Original PR description

## Motivation

When many requests finish in the same decode step, `release_kv_cache` runs once per request on the scheduler thread, and each call is ~25 small torch ops (~1.3 ms per request on GB300). The scheduler is CPU-bound in that step, so the GPU waits for all of it.

Inkling-Small-NVFP4 (TP4, MXFP8 KV, 4x GB300), 128 concurrent multi-turn lanes, torch profiler over 400 decode steps: only 4 steps release requests (32 each), and those 4 steps hold 254 ms of the 853 ms GPU idle (63 ms per step vs 1.5 ms in the other 396). Per request:

| part of `release_kv_cache` | per request |
|---|---|
| `free_kv_row` (SWA `get_and_clear_swa_pages` + full-side page free, per request) | 0.35 ms |
| Rust `begin_insert` (one `narrow` per walked node + zero-filled copy) | 0.27 ms |
| `path_device_indices` + `req_to_token_pool.write` after the insert | 0.13 ms |
| everything else (match, locks, mamba checkpoint, actions) | ~0.6 ms |

## Modifications

1. **Free a free group's kv-row segments in one pass** (`SWATokenToKVPoolAllocator`). Inside a free group, `free_segments` / `free_full_segments` (only called for a request's own kv row, via `free_kv_row_segments`) record each segment's page representatives; `free_group_end` resolves them with one `get_and_clear_swa_pages` and one full-side page free. Row segments belong to the request, so nothing in the group can re-point their SWA peers; `free_swa` / `free` keep resolving at call time, because tombstone recovery can re-map those slots within a group. Subclasses that override `free_segment` / `free_full_segment`, per-request SWA rings, and debug mode keep the per-segment path.
2. **Skip the row rewrite when checkpointing a finished request.** After the insert, `checkpoint_into_tree` rewrites `req_to_token[protected:new_len)` with the tree's indices. A finished request's row is released right after, and that release only reads from the new protected length on, so the rewrite (and materializing the path's indices to feed it) is dead work. The new protected length comes from `full_device_path_len`, a new tree-core query equal to `len(collect_full_device_indices(...))` without the concatenation (Rust and Python cores). Kept as is with the session radix cache.
3. **Rust insert walk**: slice the request's value only on the steps that free or recover (the SWA overlap hook reads it from `params.value`), and copy tree tensors with `empty_like` + `copy_` instead of `tch::Tensor::copy` (which zero-fills first).
4. **Paged `free_segment`** stops cloning the page ids it just computed with `//`.

## Accuracy / correctness

No change to what is freed or cached. Unit, on `de487f8039`: mem_cache pytest main 3233 / PR 3234 passed, the same 5 failed + 4 errors on both (`test_unified_hicache_transfer_lifecycle`, `test_unified_mha_views`, unrelated); Rust lib 923 passed on both; Rust-core entry 2910 OK on both.
- New `test_grouped_rows_free_in_one_pass_like_one_segment_at_a_time`: batched and per-segment group frees leave identical free lists on both pools and an identical full->swa mapping. Fails if the batched pass skips the SWA side.
- `_path_indices` in the Rust-core integration tests now asserts `full_device_path_len == len(collect_full_device_indices)` at every call site; stale-handle table covers the new query.
- Under-counting the finished protected length by one page fails 27 tests on each tree core.

## Benchmark

Inkling-Small-NVFP4, TP4, `--kv-cache-dtype mxfp8`, 4x GB300, multi-turn lanes (each lane sends its next turn when the previous one returns; 16 timed turns), interleaved rounds, paired by round.

| lanes | L1 | L2 (`--enable-hierarchical-cache`) |
|---|---|---|
| 64 | +0.47% (sd 0.14) | +0.06% (sd 0.03) |
| 128 | +0.79% (sd 0.04) | +0.96% (sd 0.12) |
| 192 | +1.07% (sd 0.26) | +1.74% (sd 0.64) |
| 256 | +0.85% (sd 0.65) | +0.89% (sd 1.39) |

n=3 paired rounds per row, base `de487f8039`. `--kv-tokens` = 16384 x lanes, `--max-mamba-cache-size` = 8 x lanes. Each finish step releases lanes / 4 requests here; the gain grows with that up to 192 lanes, and the 256-lane rows are within their noise.

Profile at 128 lanes (L1, 400 steps): `release_kv_cache` 172 -> 117 ms, GPU idle in the release steps 63 -> 47.5 ms per step.
