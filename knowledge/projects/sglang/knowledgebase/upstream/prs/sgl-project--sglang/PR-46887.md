# [Perf][DSA]: Capture DSA prefill attention and the NextN draft prefill in the prefill CUDA graph

[Upstream PR](https://github.com/sgl-project/sglang/pull/46887) · state: open · merged: False

## Original PR description

## Motivation

With the breakable prefill CUDA graph, every DSA layer's sparse attention and indexer still run as eager graph breaks, and the NextN (MTP) draft extend that follows each prefill chunk runs eagerly. Short prefills and prefix-cache hits are then bound by host launch work rather than GPU time. This records the DSA prefill attention, the indexer's Q/K prep and the NextN draft extend inside the prefill graph, which cuts TTFT on GLM-5.2 NVFP4 (GB300) by up to 44% for short fresh prompts and by up to 37% for cached-prefix prefill under concurrency, with outputs bitwise equal to the eager breaks.

## Modifications

One commit, `[Perf] dsa: Capture DSA prefill attention and the NextN draft prefill in the prefill CUDA graph`:

- DSA prefill attention (k_b bmm, RoPE + FP8, KV write, TRT-LLM sparse MLA) runs inside the breakable prefill graph. Per-row lengths come from a static buffer that `init_forward_metadata` refreshes; padded rows attend to the dummy slot. Buckets below the smallest one whose rows all exceed SMs / 2 (96 on GB300) keep the eager break, so every prefill stays bitwise equal to it.
- With it, the indexer's Q/K prep and index-K store are captured too; only logits + top-k stay a break.
- `DeepseekModelNextN` exposes its decoder as a one-layer `layers` view (no DP attention, PP or prefill CP), so the draft extend replays the prefill graph. The DSA index-share seed is published from a graph break at replay; multimodal batches stay eager.
- Off for DCP, DP attention, prefill CP, hisparse, k-pool, TBO, page-sharded KV caches (#44280) and per-layer KV loaders (FlexKV, external cache linker, radix cache plug-ins, host-pool retraction backup). HiCache load-backs are waited for in full before the forward.
- Tests: CPU unit tests for the bucket floor, the length refresh, the HiCache wait and the gates (`test/registered/unit/layers/attention/test_dsa_prefill_cuda_graph.py`, `test/registered/unit/models/test_deepseek_nextn_draft_prefill_graph.py`); a GB300 nightly e2e test (`test/registered/e2e/models/test_dsa_glm52_nvfp4_prefill_graph.py`) comparing captured vs eager servers bitwise, with and without HiCache load-back. Env var docs updated.

Kill switches (default on): `SGLANG_ENABLE_DSA_PREFILL_ATTN_IN_CUDA_GRAPH`, `SGLANG_ENABLE_DSA_PREFILL_INDEXER_PREP_IN_CUDA_GRAPH`, `SGLANG_ENABLE_NEXTN_DRAFT_PREFILL_CUDA_GRAPH`.

## Speed Tests and Profiling

Setup: GB300, GLM-5.2 NVFP4, HiCache on, chunked prefill 8192, default prefill graph capture size. The 2026-10-26 SGLang nightly image (`lmsysorg/sglang:nightly-dev-cu13-20261026-8252e3af`, SGLang `8252e3af63`) is the main arm; the other arm is this branch on top of it. TP4 is one tray (EAGLE 4/1/5, max 8 running requests); TP8 is two trays in one NVL72 rack (EAGLE 5/1/6, max 16).
- Both arms ran in the same allocation, interleaved main / PR / PR / main / main / PR (3 server instances per arm).
- Prompts are random tokens; "fresh" prompts have no cache hit, "cached" ones reuse a warmed 32k / 128k prefix and add 1024 or 4096 new tokens. 64-token answers, 16 requests at concurrency 1 and 8 per lane above it. Acceptance is pinned to the recipe's accept length (3.33 / 3.61) with real draft tokens, so both arms do the same decode work.

Gains come from fewer host-bound graph breaks: at concurrency 1 they are largest where the extend is short (fresh 512-1k; at TP8 also 32k + 1k). Under concurrency, shorter prefill steps cut the queueing of the other lanes.

**Steady decode** (fresh 1000 in / 512 out, median TPOT ms, main → PR):

| | concurrency 1 | concurrency 4 |
|---|---|---|
| TP4 | 2.87 → 2.86 | 4.61 → 4.61 |
| TP8 | 2.44 → 2.45 | 3.75 → 3.71 |

**64-token answers.** TPOT is not a per-step measure here, and two effects show up in it:
- At concurrency 1, TPOT of fresh 512 / 1k prompts is +1.7-2.2%: most likely because the first token now leaves before the GPU tail of the prefill step (draft extend), so ~2-3 ms move from TTFT into the first inter-token gap. E2E still falls (TP4 -8% / -2%, TP8 -15% / -9%).
- At concurrency 4-16, TPOT rises (up to 2x) because faster prefills let the lanes drift out of lockstep, and the other lanes' prefills then land in a request's decode window instead of before its first token. E2E moves by -3.6% to +1.0% at these points, except at TP4 fresh 512 and 2048 at concurrency 4. There, E2E is +9% and +5% with the client's default lane offset, which depends on each arm's latency. With the same fixed offset for both arms, it is -4% and +3%. At 2048, the four prefills on main batch into one 8192-token chunk and the lanes stay in lockstep. At TP8, the same two points are -2.7% and -0.5%.

Graph memory (rank 0): target prefill graph 4.04 → 3.61 GB (TP4) and 3.79 → 3.37 GB (TP8), plus 0.25 GB for the draft prefill graph; the KV pool size is unchanged.
