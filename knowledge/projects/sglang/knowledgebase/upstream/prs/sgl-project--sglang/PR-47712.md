# [Fix] [NVIDIA] fused-a-gemm: Check the selected backend's K alignment before taking the fused path

[Upstream PR](https://github.com/sgl-project/sglang/pull/47712) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #47710.

On SM120 the fused-A GEMM dispatcher auto-selects the CuTe DSL kernel, which requires `K % 1024 == 0`, but `fused_a_gemm_weight_eligible()` only checks the JIT kernel's `K % 256 == 0`. A DeepSeek-style MLA model with `hidden_size=3584` (or 2560) therefore passes the check and then crashes in `fused_qkv_a_proj_with_mqa` on the first <= 16-token batch:

```
AssertionError: K must be a multiple of 1024, got 3584
```

The same shape works on Hopper, where `auto` resolves to the JIT kernel.

## Modifications

- `python/sglang/kernels/ops/gemm/fused_a_gemm.py`
  - Add a per-backend K alignment table (`JIT: 256`, `CUTEDSL: 1024`) mirroring each kernel's assert.
  - Factor the `auto` resolution into `_resolve_backend()` and use it in both `dsv3_fused_a_gemm` and `fused_a_gemm_weight_eligible`.
  - `fused_a_gemm_weight_eligible` takes a keyword-only `backend` (default `auto`) and checks K against the resolved backend. The dtype, `N % 16`, CUDA and SM >= 90 checks are unchanged.
- `python/sglang/srt/models/deepseek_v2.py`: pass `backend=self.fused_a_gemm_backend` to both eligibility checks, so the check matches the backend the subsequent `linear_with_fused_a_gemm` call uses. `nemotron_h.py` uses the default (`auto`) for both calls already, so it needs no change.
- `test/registered/kernels/ops/gemm/test_fused_a_gemm.py` (new, registered on `base-b-kernel-unit` / `1-gpu-small`, i.e. the RTX 5090 runner, skipped elsewhere): on SM120, a K=3584 weight must be ineligible and the guarded path must match `F.linear`; a K=7168 weight must stay on the fused CuTe DSL path and match `F.linear`. This is a separate file because it needs the 5090 runner; adding that registration to `test_cutedsl_dsv3_fused_a_gemm.py` would also move its full kernel matrix onto the 5090.

Behavior:

| GPU | backend | K % 256 == 0, K % 1024 != 0 (e.g. 3584) | K % 1024 == 0 |
|---|---|---|---|
| non-SM120 | auto (-> JIT) | fused (unchanged) | fused (unchanged) |
| SM120 | auto (-> CuTe DSL) | **unfused fallback** (was: AssertionError) | fused (unchanged) |
| any | explicit `cutedsl` | unfused fallback (was: AssertionError) | fused |
| any | explicit `jit` | fused (unchanged) | fused (unchanged) |

Why gate in the eligibility check rather than fall back inside `dsv3_fused_a_gemm`:

- The kernel entry points keep their shape asserts as their contract. A silent fallback in the kernel wrapper would hide a caller that passes a shape the kernel can't run.
- On SM120 there is no fused fallback to switch to: the JIT kernel sizes its pipeline for Hopper's shared memory (see #29897), so the only fallback would be a plain torch matmul inside a kernel op.
- Callers already treat `fused_a_gemm_weight_eligible` as the gate (cached once per layer) with the regular linear layer as the fallback, so fixing the predicate fixes all of them.

## Accuracy Tests

Not a numerics change: shapes that run the fused kernel are the same as before, except the SM120 shapes that used to crash, which now use the regular linear layer.

RTX 5090 (SM120), CUDA 13.0, PyTorch 2.14.1+cu130, run before and after the fix (repro scripts are attached to the issue).

End to end: a config-only `DeepseekV3ForCausalLM` (DeepSeek-V3 MLA dims, hidden_size=3584, 4 layers, 16 experts), `--load-format dummy --skip-tokenizer-init`, one `/generate` request with `input_ids`:

Not run on Hopper. Eligibility there is unchanged (`auto` resolves to JIT, which keeps the 256 check), and the existing `test_dsv3_fused_a_gemm.py` / `test_cutedsl_dsv3_fused_a_gemm.py` run in CI on H100.

## Speed Tests and Profiling

No change on non-SM120 GPUs: same predicate result, same kernel. On SM120, K values that are 1024-aligned keep the fused CuTe DSL path. K values that are only 256-aligned, which used to crash, now run the regular linear layer.

Possible follow-up, not in this PR: the CuTe DSL kernel's K indexing (`TILE_K=256`, split-K inside each tile) does not obviously need `K % 1024`. With the assert bypassed on the 5090 it matched `F.linear` at K=3584 and K=2560 (N=2112, M in {1, 4, 16}; max |diff| <= 0.016, same order as K=7168). Relaxing the assert to 256 would need a wider shape sweep and a perf comparison against the unfused path, so it is left for a separate PR.
