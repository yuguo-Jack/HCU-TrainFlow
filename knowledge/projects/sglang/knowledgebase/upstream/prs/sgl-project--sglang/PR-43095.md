# [Test] scheduler: Test that the admission re-match records num_matched_prefix_tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/43095) · state: open · merged: False

## Original PR description

## Motivation

Regression coverage for #43094. With a cache-agnostic policy (`fcfs`, `lof`, `random`, `routing-key`), `calc_priority` skips the sort-time prefix match, so the admission re-match in `Req.init_next_round_input` is the only place these requests record `num_matched_prefix_tokens`. Before #42823 that re-match never wrote the field. Every request kept 0 while still reusing cached prefixes, so load snapshots (`get_num_waiting_uncached_tokens`) and cache-hit reporting read zero reuse: a 30-minute fcfs replay reported 0 matched tokens against a 91.6% token-weighted hit rate.

#42823 fixed this by recording the match length inside `match_kv_cache`, but no test asserts it for the admission path. These tests guard against a refactor of `match_kv_cache` / `init_next_round_input` silently dropping that write again.

## Modifications

`test/registered/unit/managers/test_schedule_policy.py`: `TestAdmissionMatchedPrefixTokens`, three CPU cases on a simulated radix tree that holds a 64-token prefix.
- `test_warm_req_records_match_length`: a request sharing the prefix records 64 at admission.
- `test_cold_req_records_zero`: a request that shares no tokens with the cached prefix records 0, so the write does not count unrelated tokens.
- `test_rematch_after_retraction_records_again`: `reset_for_retract()` zeroes the field, and the next admission re-match records 64 again.

Test-only; no runtime change.
