# [Fix] dspark: Stage each request's own SWA ring slot at batch size 1

[Upstream PR](https://github.com/sgl-project/sglang/pull/47728) · state: open · merged: False

## Original PR description

## Root cause

When the DSpark draft keeps its SWA KV in a per-request ring (for example with `--enable-encoder-swa-bounded-replay`), the static verify epilogue (`DsparkVerifyEpilogue.run_static`) builds the per-row state slots like this:

```python
io.req_pool_indices.view(-1, 1).expand(bs, self.stride).reshape(-1)
```

At `bs == 1` this reshape returns a stride-0 view instead of a copy. The one-launch staging kernel (`stage_commit`, used when `SGLANG_OPT_DSV41_DSPARK_ONE_LAUNCH_COMMIT_STAGE` is on, which is the default under `SGLANG_ENABLE_NV_MEGA_RUNTIME_OPTIMIZATION`) reads `state_slot` as a flat contiguous tensor. So rows `1..stride-1` pick up `req_pool_indices[1..stride-1]` from the graph's static buffer (stale or padding values) instead of request 0's slot. The deferred commit then writes those tokens' draft KV into other requests' rings, and the draft loses that context.

At `bs >= 2` the reshape has to copy, so only single-request steps are affected. Configs without a draft SWA ring pass `state_slot=None` and are unaffected.

## Fix

- `run_static` makes the state slots contiguous before staging.
- `stage_commit` asserts that `state_slot` is contiguous, as it already does for `cache_loc` and `positions`.

## Validation

- Extended `test/registered/unit/spec/test_dspark_deferred_commit.py`: the static epilogue now runs with a ring and the one-launch stage at bs 1 and bs 2, and the test checks that every staged row carries its own request's slot.
- On GB300 (CUDA) the file passes 6/6. Without the fix, the bs 1 subtest fails and bs 2 passes.
- End to end on GB300: DeepSeek-V4.1-Flash, TP4, one concurrent request, real DSpark acceptance, `--enable-encoder-swa-bounded-replay` with deferred commit and the one-launch stage, GSM8K via sgl-eval 0.1.3 (300 examples, temperature 1). Both arms ran on the same node. Mean accept length went from 2.13 to 3.56 with the fix. Accuracy was 98.33% without the fix and 98.00% with it, the same within noise because the target verifies every token.
