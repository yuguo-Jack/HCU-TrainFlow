# [Perf] dsv4: Publish prefill read-done under the request window and on V4.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/45582) · state: closed · merged: True

## Original PR description

Builds on #45559, #45577 and #45573, all merged. Follow-up: #45580 fences a chunk stash that frees duplicate KV of an in-flight chunk, which only shortest-prefill-first scheduling can reach; it is kept out of this PR.

- `DeepseekV4AttnBackend._snapshot_prefill_shared_reads` no longer returns `UNKNOWN` when the encoder SWA request window is active. Dense prefill reads only the request-window layout built at metadata init, and the sparse prefill chunk cache built in the snapshot takes that layout without reading `req_to_token` or `full_to_swa`.
- It no longer returns `UNKNOWN` for V4.1: the low-ratio indexer reads the index-K slots gathered at metadata init (#45577) instead of `req_to_token` in every layer. HiSparse keeps the whole-forward barrier.
- Adjust the existing snapshot test.

Behavior change: DeepSeek V4.1 prefill with the request window now publishes prefill read-done when the speculative algorithm allows it (none or DFLASH), so the scheduler's next batch waits only for the forward's metadata reads instead of the whole forward. DSPARK prefill still takes the whole-forward barrier (`SpeculativeAlgorithm.supports_prefill_shared_read_done`). Not yet measured on a workload: the multi-turn prefill workload that motivated it runs DSPARK, which keeps the whole-forward barrier.
