# [Feat] [AMD] kv-shard: Support GLM DSA KV cache sharding on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/48396) · state: open · merged: False

## Original PR description

## Motivation

Stacked on #44660 (ROCm kv-shard with aiter and MoRI): only the last commit is new; please review after #44660.

KV cache sharding (`--enable-kv-cache-sharding`, #30501) supports DSA models only on CUDA, where pages are striped across interleaved prefill CP with TRTLLM DSA and Mooncake. ROCm has no DSA prefill CP. This PR stripes pages across attention TP instead (CP=1), the axis plain MLA already uses on ROCm, so GLM-5.2/5.3 PD prefill on MI355X gets a sharded radix cache, together with CPU HiCache.

## Modifications

- **Gate:** on HIP, DSA kv-shard is accepted with attention CP 1 and PP1, tilelang/triton DSA prefill and decode, fp8_e4m3 KV, page size 64 (which requires aiter's preshuffle paged-MQA path; the error message names the requirement), MoRI transfer, and an uncompressed `index_kpool=1`. The CUDA requirements are unchanged.
- **ROCm writers are shard-aware:**
  - The gfx950 fused rope+cat+cache MLA writer is bypassed for a page-sharded pool, so latent writes go through `set_mla_kv_buffer` (scratch staging plus owned rows).
  - The aiter indexer writers (fused FP8 Q/K writer and `indexer_k_quant_and_cache`) write every token to its scratch slot and owned tokens to their local slots. Non-owned tokens get slot -1, which both kernels skip, so there is no host sync. The index-K format decode reads is unchanged.
- **MoRI:** the DSA indexer state is narrowed to the pages this prefill rank owns and paired with the destinations at the same logical positions. The helper moves from Mooncake to the common connector, so both backends share it, and the per-sender transfer metric uses the same owner filter.
- **Tests:** HIP DSA gate cases (accept/reject, including Mooncake and page size), MoRI owned-page DSA state pairing, the masked slot mapping against the filtered write targets, and the fused-writer bypass for a sharded pool.

## Accuracy Tests

8x MI355X, `lmsysorg/sglang-rocm:v0.5.23-rocm10-mi35x-20261101`, amd/GLM-5.2-MXFP4 (fp8_e4m3 KV, DSA triton/triton, page 64, EAGLE MTP 5/1/6), single-node 1P1D: prefill TP2 and decode TP2, MoRI transfer, mini-lb router. Each rank's pool is capped with `--max-total-tokens 262144` (see the S1 notes on ROCm/mori#721). The arms differ only in prefill flags.

**Notation.**
- **Baseline PD**: 1P1D with no kv-shard and no HiCache. **HiCache only**: `--enable-hierarchical-cache --hicache-size 180` (write_through, kernel io, page_first). **kv-shard only**: `--enable-kv-cache-sharding`. **kv-shard + HiCache**: both.
- **agg TP4** (S1 only): one non-disaggregated TP4/EP4 server with HiCache on 4 GPUs, the single-node baseline.
- **|dlogprob|**: absolute difference between teacher-forced per-token logprobs of the same sequence (prompt + the cold greedy output). Mean and max are over 8 prompts x 24 tokens.

### A1. GSM8K and MTP accept length, repeated runs

`sglang.test.few_shot_gsm8k`, 5-shot, all 1,319 questions, parallel 32, through the router. Each run uses a fresh server. Accept length is the decode-side weighted mean over the GSM8K window.

| Arm | Runs | GSM8K mean (min - max) | Invalid (max) | MTP accept length mean (min - max) |
|---|---|---|---|---|
| Baseline PD | 10 | 0.932 (0.925 - 0.941) | 0.002 | 3.90 (3.83 - 3.95), 9 runs |
| kv-shard only | 10 | 0.929 (0.921 - 0.934) | 0.001 | 3.89 (3.80 - 3.96) |
| kv-shard + HiCache | 9 | 0.932 (0.925 - 0.949) | 0.001 | 3.89 (3.83 - 3.93) |

The binomial SE of one 1,319-question run is about 0.007. The arm means differ by at most 0.004, which is within the run-to-run spread.

### A2. Long-prefix logprob parity, including host load-back

8 prompts of 24,028 tokens (key/value facts plus a retrieval question). Each run goes through these phases:
1. Cold greedy run (the reference).
2. Device-hit greedy and teacher-forced runs.
3. A fresh no-cache teacher-forced run (`logprob_start_len=0`).
4. Eviction with 786,432 filler tokens (1.5x the sharded logical pool).
5. First touch after eviction, served from host in the HiCache arm.
6. A second device hit, which gives the same-path noise.

The prefill is not bit-reproducible run to run, so the check is per-token logprob parity against the stock arm's own noise. Each cell gives the range of the per-run mean and per-run max |dlogprob| across runs.

| Arm | Runs | Retrieval correct (every phase) | Host-hit tokens after eviction | After eviction vs device hit: mean / max | Device hit vs fresh: mean / max | Device hit vs device hit (noise): mean / max |
|---|---|---|---|---|---|---|
| Baseline PD | 9 | 8/8 | 0 (recompute) | 0.037-0.057 / 0.68-2.60 | 0.036-0.065 / 1.44-3.85 | 0.029-0.075 / 0.73-3.91 |
| kv-shard only | 10 | 8/8 | 0 (recompute) | 0.026-0.077 / 1.05-4.62 | 0.026-0.068 / 0.62-3.43 | 0.024-0.076 / 0.67-3.99 |
| kv-shard + HiCache | 9 | 8/8 | 192,192 of 192,224 | 0.033-0.058 / 0.87-2.80 | 0.033-0.067 / 0.92-2.55 | 0.029-0.074 / 0.87-3.00 |

With kv-shard + HiCache, every prefix comes back from the sharded host pool, and its deltas stay within Baseline PD's same-path noise. Max outliers of up to about 4 nats also appear in Baseline PD: on a non-reproducible prefill, near-tie tokens swing.

### A3. Mutation: MoRI owner filter removed

Same setup as A2, with the MoRI sharded-DSA owner filter deleted in a scratch build (kv-shard only arm). A wrong index-K transfer is caught by the long-prompt tests through request failures and retrieval collapse; short-prompt GSM8K alone does not catch it.

| Probe | Result |
|---|---|
| GSM8K, 1,319 questions (short prompts) | 0.938: not caught |
| GSM8K, 200 questions | 0.955: not caught |
| Parity, 24k-token prompts | HTTP 500 (the decode-side transfer fails) |
| Parity, 8k-token prompts | HTTP 500, plus 1,435 MoRI "length out of range" errors |
| Parity, 8k-token prompts, error-tolerant client | Retrieval 0/8, 1/8, 0/8, 0/8 with garbage answers; 7,886 transfer errors |

Short-prompt GSM8K alone does not catch this. Prompts below the DSA top-k (2048) keep every token, so index-K does not affect the result, which is why A2 uses long prompts.

## Speed Tests and Profiling

### S1. AgentX vs the single-node baseline

The setup follows the InferenceX glm5.2 MI355X FP4 MTP recipe: GLM-5.2-MXFP4, fp8_e4m3 KV, DSA triton/triton, EAGLE 5/1/6, chunked prefill 32,768, max running 64, `--cuda-graph-max-bs-decode 64`. Every arm uses `lmsysorg/sglang-rocm:v0.5.23-rocm10-mi35x-20261101`.
- **agg TP4** is the recipe's single-node server: TP4/EP4 with HiCache (180 GB per rank, write_through) on 4 GPUs.
- **PD arms** are 1P1D: prefill TP4 on GPUs 0-3 and decode TP4 on GPUs 4-7, with MoRI over one NIC and the mini-lb router. HiCache arms use the same HiCache settings as agg TP4.

The client is InferenceX AgentX FULL (3,600 s window) on the `glm5.2` corpus, with a fresh server per point. tok/s/GPU counts 4 GPUs for agg TP4 and 8 for PD. Prefix hit is the server-side rate over the window; the trace's reusable prefix is about 96%. Each point is a single run.

Pool sizes:
- **Logical device pool:** tokens the prefill (or agg) radix cache can hold. With kv-shard it is 4 x 886,336 per rank; the per-rank pool is smaller because sharding reserves gather scratch.
- **Host pool:** logical tokens. HiCache without kv-shard keeps a full replica on every rank.

- **kv-shard + HiCache is the only arm that holds the reusable prefix:** total hit is 96.9% at c32 and 94.0% at c64, mostly from the sharded host pool, which is 4x the replicated one. In every other arm the prefill radix cache misses most of the reusable prefix.
- **kv-shard alone** gives 2.6x the device pool of Baseline PD and raises the hit rate from 34.7% to 58.2% at c32. That is still short of the working set, so throughput improves only 1.29x.
- **Decode is the remaining limit, so the absolute PD numbers are conservative.**
  - The decode pool holds 1,385,728 tokens (plain TP4 at mem 0.60), and decode token usage averages 0.85-0.88 in every PD arm.
  - In kv-shard + HiCache, decode averages 3-4 running requests, with about 20 (c32) and 59 (c64) waiting in the prealloc queue.
- **At the recipe's top point (c16)**, agg TP4 is not capacity-bound: 17,462 tok/s/GPU, 94.2% hit, TTFT P50 0.32 s. PD at c16 was not run.
- **Deviations from the recipe:**
  - agg TP4 uses `--mem-fraction-static 0.80`, because 0.85 crashed at c32 with hipErrorLaunchOutOfResources.
  - c32 and c64 are above the recipe's top point of c16.
  - The PD arms use mem 0.60 on both roles and plain TP4 decode. MoRI's dma-buf pin double-counts VRAM on these hosts (ROCm/mori#721), and a larger pool crashes after the first transfers.
- No client errors in any arm. Single run per point.
