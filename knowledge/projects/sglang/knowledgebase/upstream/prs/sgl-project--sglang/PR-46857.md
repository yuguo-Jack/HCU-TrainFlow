# [Perf] GLM-5.3: Restore TP decode fusion and graph sizing with CP prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/46857) · state: closed · merged: True

## Original PR description

## Motivation

Reduce GLM-5.3 long-context time to first token by using context-parallel (CP) prefill to distribute query rows, then retain tensor-parallel (TP) execution for the small decode/verify batches. On the measured 8 × B300 workload (262,144 input / 1,024 output tokens), the final combination reduces warmed, uncached-prefix TTFT from **16.5848 s to 5.6954 s (−65.66%)**, while the decode iteration-cost proxy returns approximately to the native TP level.

The prefill speedup and this commit's code changes are related but distinct: **existing CP prefill removes redundant long-context indexer work; this commit repairs the packed-scale layout, reduction/fusion contract, and graph sizing needed to combine that prefill path with efficient TP decode.** It does not introduce CP, a new top-k algorithm, or a new GPU kernel, and it does not change global parallel configuration during a forward.

### Why prefill becomes faster

The original native-TP8 profile exposed a long-context DSA indexer bottleneck: although the following attention is sparse, the indexer still scores each new query against its causal history and selects the top 2,048 positions. Native TP shards attention heads, but the indexer projections are replicated and the measured baseline repeats the full-query logits/top-k work on every TP rank. Across the prefill trace, logits and top-k together account for approximately 41% of the summed kernel time on the representative ranks; that is a profiling attribution, not a directly removable percentage of TTFT.

Interleaved CP8 assigns query row `i` to rank `i % 8`. Each 32,768-token prefill chunk therefore gives each rank **4,096 query rows**, instead of having all eight ranks repeat indexer work for all 32,768 rows. For example, rank 0 handles `q0, q8, q16, …`, and rank 1 handles `q1, q9, q17, …`. Every row still uses its required causal history and the existing top-k selection; CP partitions the queries, **not the historical key range for each query**. Existing CP cache exchange and layer-boundary collectives remain necessary.

| Work per rank, at the final 256K-context chunk | Native TP8 baseline | CP8 interleaved prefill |
| --- | --- | --- |
| New query rows processed by the indexer | 32,768, repeated on every rank | 4,096, different rows on each rank |
| Historical-key column capacity | 262,144 | 262,144; not divided by 8 |
| Logical FP32 logits footprint before scratch sub-chunking | `32768 × 262144 × 4 B = 32 GiB` | `4096 × 262144 × 4 B = 4 GiB` |
| Attention-head layout in this configuration | 8 of 64 heads per rank | All 64 heads for that rank's query rows |

The footprint row describes the rectangular score workspace, not the actual peak allocation or the number of unmasked causal pairs. The original approximately 10.7 GiB scratch budget split the last baseline chunk into `10964 + 10964 + 10840` query rows; the 4 GiB CP-local matrix fits that budget. This reduces both replicated score/selection work and the need for query sub-chunking. It does not reduce the request from eight 32K prefill chunks to one, reduce the model's top-k, or truncate its context.

The existing implementation to read alongside this explanation is `InterleaveCPStrategy._interleave_shard` / `local_q_indices` in `python/sglang/srt/layers/cp/interleave.py`, and the replicated indexer projections plus logits/top-k path in `python/sglang/srt/layers/attention/dsa/dsa_indexer.py`. Neither file is modified by this commit; the new changes below make the phase-specific CP-prefill/TP-decode combination work efficiently.

Historical prefill profiles corroborate this mechanism: median per-rank cumulative top-k time fell from about **4.185 s to 0.533 s**, and MQA logits from **2.591 s to 0.318 s**. Sparse-attention time also fell, but that is a different execution shape (fewer query rows and more heads), not evidence that all attention FLOPs fell eightfold. TRT-LLM BMM time remained approximately **1.84 s**. The detailed profile comparison below is historical supporting evidence, separate from the final unprofiled five-trial benchmark.

### Why the decode fixes belong in the same optimization

Long prefill benefits from distributing thousands of query rows; a decode/verify step has only a few rows and benefits from partitioning the supported attention weights/heads instead. The existing `--enable-cp-decode-attn-tp` path provides that phase-specific dispatch, but on this Blackwell FP8 stack its packed UE8M0 scale shards initially violated DeepGEMM's MN-major layout. After fixing the layout, the attention boundary still did not retain the ordinary TP reduction/fusion contract, and decode CUDA Graph capture still applied CP row alignment. One request with six speculative verification tokens therefore selected a four-request bucket and executed 24 rows.

This commit makes that combination usable and restores its TP-like steady-state execution: preserve packed scales and stable cached pointers, defer the required attention sum to the boundary for existing all-reduce/add/RMSNorm fusion, and select graph buckets according to the actual decode row layout. Actual CP-prefill computation remains on the existing path. Thus the contribution is **making fast CP prefill coexist with efficient TP decode**, not claiming that decode fusion itself produced the 65.66% TTFT reduction.

## Modifications

- Preserve the MN-major, TMA-aligned layout of packed UE8M0 scale shards without unpacking or requantizing them; cache the shards to retain CUDA Graph pointer stability.
- Add an ordinary-batch TP-group override to attention stage declarations. DSA attention can defer its decode reduction to the stage boundary, while actual CP-prefill batches retain their original contract.
- Reuse the existing fused all-reduce workspace only when its ordered peer list matches the CP group; retain an unfused completion when the fusion declines the batch.
- Distinguish an actual CP batch from a server merely configured for CP when deciding whether to defer an FFN output reduction.
- Omit CP-only decode graph alignment for the supported DSA dispatch path, but preserve the alignment required by gathered buffers and leave the helper's default behavior unchanged.
- Add regression coverage for exactly-once reductions, fusion fallback, peer mismatch, topology/configuration guards, exception-safe restoration, graph bucket selection, and real Blackwell packed-scale GEMMs. Update existing boundary fixtures to publish the required runtime topology.

The new deferred-reduction path requires CUDA DSA with `q_lora_rank`, CP = TP > 1, attention TP = 1, and attention DP = 1. Layernorm sequence parallelism, LoRA, two-batch overlap, and quantized communication retain the existing inline-reduction behavior. The existing decode-attention-TP architecture allowlist is unchanged; end-to-end measurements below cover GLM-5.3 only.

## Speed Tests and Profiling

### Setup and protocol

- Hardware/model: 8 × B300, GLM-5.3 with FP8 weights/KV cache; CUDA 13.0, PyTorch 2.14.1+cu130, FlashInfer 0.7.2, and DeepGEMM 0.2.3.post2.
- Both configurations: TP8, attention DP1, EP1/no MoE all-to-all, EAGLE with 5 steps / top-k 1 / 6 draft tokens, chunked prefill 32,768, context limit 270,336, and decode graph maximum batch size 8.
- Native reference: CP disabled. Candidate: CP8 interleaved prefill with decode-attention TP enabled. The TTFT comparison measures the combined serving configuration, including the benefit of existing CP prefill; it is not a standalone kernel speedup attributable entirely to this patch.
- Single request, exactly **262,144 input tokens and 1,024 output tokens**; two warmups followed by five measured trials. Same prompt, startup/sampling seed 260126, temperature 1, and top-p 0.95.
- Unique cache salts, zero cached prompt tokens, no allocator flush, and no retractions. TTFT ends at the first generated-token SSE chunk; tokenization is outside the timer. Profiling was disabled during these trials.

### Results

| Metric, median of five trials | Native TP8 | CP8 prefill / TP8 decode | Change |
| --- | ---: | ---: | ---: |
| TTFT | 16.5848 s | 5.6954 s | -65.66% |
| End-to-end latency | 21.0974 s | 10.0606 s | -52.31% |
| Decode throughput | 226.41 tok/s | 234.68 tok/s | +3.65% |
| MTP acceptance length | 2.5664 | 2.6528 | +3.37% |
| Per-trial acceptance-length / decode-rate proxy | 11.3213 ms | 11.3006 ms | -0.18% |

The final row is the median of the per-trial ratios, not the ratio of the medians and not a device timing measurement. Decode throughput is affected by speculative acceptance; the +3.65% increase should not be presented as an equivalent kernel speedup. The iteration-cost proxy is approximately at the native TP level.

Candidate ranges were 5.6842-5.7014 s TTFT, 9.8751-10.4487 s end-to-end, and 215.22-244.40 tok/s decode. Two individual decode samples were below the reference median. Five single-request trials do not establish a per-request, multi-batch, or p95/p99 no-regression guarantee.

**Warm-up limitation:** the candidate's first 256K warmup took **168.95 s TTFT**, followed by 5.69 s on the second warmup. The reported 5.70 s is warmed, uncached-prefix performance, not the first request after server startup. This patch does not claim to eliminate or fully attribute the first-use overhead.

### Profiling

The final profile includes all eight TP ranks, with separate EXTEND and DECODE traces. TP1 contains eight 32,768-token EXTEND steps covering the 256K prompt and 32 VERIFY steps in the decode trace.

#### Prefill: evidence for the query-row partitioning benefit

The earlier native-TP8 and CP8-plus-packed-scale-fix profiles provide the following median of eight ranks' cumulative kernel-family durations over the complete prefill stage, including target and draft prefill. These are **historical intermediate-revision profiles**, not a fresh final-commit A/B and not additive wall-clock TTFT components.

| Kernel family | Native TP8 | CP8 prefill + TP decode (layout fix only) |
| --- | ---: | ---: |
| DSA prefill top-k | 4,184.9 ms | 532.5 ms |
| DeepGEMM MQA logits | 2,590.8 ms | 317.9 ms |
| TRT-LLM sparse attention | 3,460.9 ms | 509.2 ms |
| TRT-LLM BMM | 1,841.9 ms | 1,832.8 ms |

The same earlier study measured nearly identical warmed TTFT for CP8 alone and CP8 with the decode-TP scale-layout fix: **5.69395 s and 5.69589 s**, respectively. Those development runs did not fix the server startup seed across configurations, so they are supporting attribution evidence, not a strict causal ablation. They reinforce the distinction: CP supplied the major prefill benefit; the scale-layout and subsequent dispatch changes addressed decode compatibility/performance. Do not mix those historical results with the final benchmark when calculating speedup.

#### Decode: evidence for restoring the TP execution path

The final TP1 decode trace has 83,846 kernel calls, including 5,504 fused all-reduce calls and 192 standalone add/RMSNorm calls, matching the historical native-TP trace counts. The earlier CP/decode-TP trace had 94,502 total calls, 5,120 separate all-reduce calls, and 5,312 standalone add/RMSNorm calls. These traces corroborate restoration of the fusion path; historical profiles are not substitutes for the controlled, unprofiled measurements above.

Retain the observed **22.77 ms all-reduce outlier** in the final trace; its cause is not established. Kernel-duration sums and profiler windows are not end-to-end latency measurements, and no tail-latency improvement is claimed.
