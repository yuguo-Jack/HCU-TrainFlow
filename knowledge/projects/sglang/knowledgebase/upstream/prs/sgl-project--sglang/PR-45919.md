# [Feat] diffusion/openai: Report per-step progress for async video jobs

[Upstream PR](https://github.com/sgl-project/sglang/pull/45919) · state: closed · merged: True

## Original PR description

## Motivation

Right now `GET /v1/videos/{id}` returns `queued` with `progress: 0` for the whole run and then jumps to `completed` / `100`. A client polling a long video job can't tell whether the job is still queued or already running, or how far along it is. The OpenAI Videos API has `in_progress` and a 0-100 `progress` for this.

With this PR a job goes to `in_progress` when the scheduler starts it, and `progress` follows the denoising steps. It stays at 99 max until the job is `completed`.

Related: #44083 (item 7) / #44082 wire the ComfyUI progress bar to this API, and note that the server only reports 0 then 100. This PR fixes the server side of that.

#33314 did this as part of a bigger job-control change (status, cancel, idempotent dispatch) and was closed. This PR only does the progress part. It should also fit with #24547 (cancel between denoise steps), the check there could go in `ReportingTqdm.update` as well.

## Modifications

The driver rank of each DP replica pushes `[request_id, completed, total]` as JSON over a ZMQ PUSH socket to an `ipc://` endpoint. A PULL listener in the HTTP server lifespan reads it and updates the job store. The send is non-blocking, so if nobody listens or the queue is full the message is just dropped.

- New `managers/progress_reporter.py` with `ReportingTqdm`. It sends once per integer percent, and also when the bar is hidden, because the driver of replica 1 is not world rank 0.
- `PipelineStage.progress_bar` in `stages/base.py` returns a `ReportingTqdm` on the driver for non-warmup requests, so every denoise loop that passes `batch=` reports. `longlive2.py` did not pass it before, now it does.
- Scheduler: the driver creates the reporter on the existing ZMQ context and reports when a request is dispatched. This is what moves the job to `in_progress`.
- For dynamic batching, `Req.merged_request_ids` and `Req.client_request_ids()` so a merged batch reports for each request in it.
- New `entrypoints/openai/video_progress.py` maps request ids to jobs and updates `VIDEO_STORE`. A job with N outputs runs as `{job}:0..N-1` and reports the mean; the id format is now shared with `expand_request_outputs` through `output_request_id` / `split_output_request_id` in `request_utils.py`. It moves `queued` to `in_progress` and only raises progress. It does not set 100 (completion does that) and skips completed, failed and deleted jobs. A malformed message is logged and skipped, like in the broker.
- `ServerArgs.progress_endpoint` is a property next to `broker_port`: an `ipc://` path in the temp dir keyed by the HTTP port, `None` for non-monolithic roles. No new field, port or CLI flag. If the driver can't connect (e.g. a very long `TMPDIR`), it logs a warning and runs without progress.
- Docs: added `GET /v1/videos/{video_id}` to the OpenAI API page.

It is on by default. It only fills fields the API already returns, and reporting is limited to one non-blocking update per integer percent of each denoising bar, plus dispatch notifications (see speed numbers below).

Limitations:
- With `--nnodes > 1`, a replica driver on another node can't reach the ipc endpoint. Those jobs behave like today (`queued` / 0 until completion).
- Progress estimates denoising-loop advancement, not elapsed time or completed GPU work. Multiple denoising stages split the progress range equally.
- Video jobs only, image jobs are unchanged.

## Progress Correctness Follow-up

- Validate IPC IDs and counts, including non-finite values and overflowing ratios, so malformed messages cannot stop the listener.
- Keep progress monotonic across multiple denoising stages and outputs; ignore late updates to completed, failed, or deleted jobs.
- Opt in only async video requests, leaving image requests unchanged.
- Cover progress-channel absence, backpressure, receiver restart and shutdown.
- Add progress assertions to the existing video polling helper without extra generation requests, and document the API's job ownership and lifecycle limits.

Validation: 50 focused progress/lifecycle and scheduler-client tests pass on the scope-reduction commit `ae0d4fe9e7a`; pre-commit passes. The retained tree is identical to `b1edee30ec6a`. Earlier real-GPU checks on two H200s covered single GPU, DP2, dynamic batch2, Ulysses2, BCG and an unavailable progress endpoint, including decoded output checks. The original author's H100 measurements are retained below.

The unrelated output-save collective fix and broad fault-recovery E2E suite have been removed from this PR and are being handled separately. This PR adds best-effort progress reporting, not durable job storage, worker recovery, or production failover.

## Tests

Unit tests (CPU, real ZMQ sockets): 9 new tests in `test/unit/test_video_job_lifecycle.py`.

E2E on one 8x H100 node, polling `GET /v1/videos/{id}` every second. I applied the changed files on top of the v0.5.21 release (`e00930c`), in an image built from `lmsysorg/sglang:v0.5.21`. MiniMax-H3 `ref2va` (fp8) does not fit on 4 GPUs, so the DP 2 and dynamic batching cases use Wan2.1-T2V-1.3B.
