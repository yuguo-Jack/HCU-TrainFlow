# [sglang-miles] [Feat] lora: serve MiMo-V2.6 Flash/Pro adapters on the native FP8 + MXFP4 checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/45939) · state: closed · merged: True

## Original PR description

## Summary
Serve LoRA adapters on MiMo-V2.6-Flash and -Pro (`MiMoV2ForCausalLM`) with the checkpoints as released: FP8 128-block linears, MXFP4 routed experts run as W4A16 on the Marlin MoE runner, BF16 elsewhere. This unblocks LoRA RL rollouts on these models: the trainer works on BF16 weights, the rollout serves the original quantization. One commit per fix.

## Changes
- **MiMo-V2: adapt only the language model's projections** (`models/mimo_v2.py`). The audio encoders reuse `layers.<i>.*_proj` names with plain `nn.Linear` `o_proj` / `down_proj`, so LoRA tried to wrap them and failed at startup. `should_apply_lora` limits LoRA to the decoder's `model.layers`.
- **MiMo-V2: size attention adapters per layer** (`models/mimo_v2.py`). Sliding-window and full-attention layers differ in KV heads (Flash: 8 vs 4), and V heads are 128 wide against 192 for Q/K. `get_hidden_dim` reads each layer's geometry, shared with the fused-QKV checkpoint loader.
- **LoRA: size the qkv V slice by the V head width** (`lora/layers.py`). `QKVParallelLinearWithLoRA` treated V as wide as K. It split `lora_B` into wrong q/k/v pieces, and its V output offset ended past the shard, so the Triton and CSGMV qkv LoRA-B kernels wrote past each token's row. It now uses the base layer's `v_head_size` / `v_proj_shard_size`. Nothing changes when V is as wide as K, which holds for every other model.
- **LoRA: allocate dense MLP buffers in MoE models without shared experts** (`lora/mem_pool.py`). MiMo's dense first layer had no `gate_up_proj` / `down_proj` buffer, so `update_lora_info` raised `KeyError`. The buffer is allocated on the layers that have a dense linear, with zero-width placeholders on the rest. A config-sized buffer on every MoE layer would cost about 1.1 GiB/GPU for Flash at TP4 and 1.6 GiB for Pro at TP8 (rank 64, 8 slots). Models with shared experts allocate exactly as before.
- **LoRA MoE: expose Marlin quant info on the FP8-config MXFP4 experts** (`layers/quantization/mxfp4_marlin_moe.py`). `Mxfp4MarlinMoEMethod` had no `get_marlin_quant_info`, so `FusedMoEWithLoRA`'s Marlin branch asserted.
- **LoRA MoE: align Marlin LoRA routes over the global expert count under EP** (`lora/lora_moe_runner_marlin.py`). The LoRA wrapper caches the Marlin quant info before the dispatcher creates its EP map, so `global_num_experts` stays -1, and the Marlin kernel faulted under EP. This hit every Marlin LoRA model, not just MiMo: reproduced on Qwen3-30B-A3B NVFP4 and W4A16. It now reads `runner_config.num_experts`; without EP nothing changes.
- **MXFP4 Marlin MoE: allow SM100 and pick Marlin for MiMo-V2 expert LoRA** (`mxfp4_marlin_moe.py`, `arg_groups/model_overrides/mimo_v2.py`, `arg_groups/lora_hook.py`).
  - `Mxfp4MarlinMoEMethod` accepted only SM90 and SM120. It now also accepts SM100, as K3's MXFP4 Marlin path already does.
  - MiMo's override picked `flashinfer_mxfp4` on SM100, which has no LoRA path. When LoRA wraps the experts, `auto` now resolves to Marlin, and any other MoE runner or an all-to-all backend is rejected at startup with an error naming the supported flags.
  - Whether LoRA wraps the experts follows the targets LoRAManager resolves: `--lora-target-modules`, or else the initial adapters' configs, read with `LoRAConfig` and normalized by `get_normalized_target_modules`. The `--lora-paths` parsing moves into a shared `parse_lora_paths`. Targets that cannot be read at startup keep the expert checks. LoRA on attention only keeps the default runner.
- **Test: run the narrow-V qkv GPU test on the CSGMV backend too.** CSGMV is the server's default LoRA backend.
- **MiMo-V2 MTP: load the fused block-FP8 qkv below the checkpoint's shard count** (`models/mimo_v2.py`, `models/mimo_v2_nextn.py`), by @guapisolo, from jybsuper/sglang#35. The checkpoints store qkv as interleaved shards, 4 for Flash and 8 for Pro. At a lower attention TP, each rank merges shards, so their block scales must be re-quantized after loading. The main model already did this, but `MiMoV2MTP.load_weights` did not, so EAGLE drafting from the MTP layer failed at load with a `scale_inv` shape mismatch (Flash at TP2). The MTP loader now defers and resolves the scales the same way, and `_get_ckpt_qkv_shard_sizes` sizes the MTP layer with the sliding-window dimensions it is built with. At or above the shard count nothing changes.

## How to run
```bash
# MiMo-V2.6-Flash: 4x H200 / B200 / GB300 (TP4). Tested on H200 and GB300.
python -m sglang.launch_server --model-path XiaomiMiMo/MiMo-V2.6-Flash-RL --trust-remote-code \
  --tp 4 --mem-fraction-static 0.7 \
  --enable-lora --lora-paths my_lora=/path/to/adapter --max-lora-rank 16 --max-loras-per-batch 4 \
  --lora-use-virtual-experts

# Same with expert parallelism: add --ep 4

# MiMo-V2.6-Pro: 4x GB300 (TP4; 573 GB checkpoint). Tested on GB300.
python -m sglang.launch_server --model-path XiaomiMiMo/MiMo-V2.6-Pro-RL --trust-remote-code \
  --tp 4 --mem-fraction-static 0.75 \
  --enable-lora --lora-paths my_lora=/path/to/adapter --max-lora-rank 8 --max-loras-per-batch 3 \
  --lora-use-virtual-experts

# Request
curl -s localhost:30000/generate -d '{"text": "...", "lora_path": "my_lora", "sampling_params": {"max_new_tokens": 64}}'
```
- **Runner:** expert LoRA runs on the Marlin MoE runner, which `--moe-runner-backend auto` picks; the old default was `flashinfer_mxfp4` on SM100. It needs the standard dispatcher (`--moe-a2a-backend none`, the default). DeepEP, DeepGEMM and FlashInfer runners are rejected at startup when LoRA covers the experts.
- **Adapter format:** PEFT, with split `q_proj` / `k_proj` / `v_proj` (V rows = KV heads × 128) and per-expert `mlp.experts.<e>.{gate,up,down}_proj`. This is what the Miles MiMo-V2 bridge exports, by reading its code.
- **Memory:** per-expert LoRA buffers per adapter slot and GPU, at TP4: about 5.3 GB for Flash at rank 16, and about 8.5 GB for Pro at rank 8.
- **EAGLE (MTP drafting):** add `--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`. Run with LoRA by @guapisolo on Flash at TP2 (H200); not run on Pro.
- **Untested:** Pro on 8x H200 (TP8).

## Validation
4x H200 (SM90) and 4x GB300 (SM103).

**Unit tests (CPU).**
- Each commit's tests pass at that commit.
- At the tip, there are no failures that base `412be60` doesn't also have. Already failing at base: 21 in `unit/lora`, 1 in `test_model_overrides`, 2 in `test_server_args`.
- New or extended tests:
  - `test_mimo_v2_lora`;
  - `test_lora_fused_member_load` (narrow V);
  - `test_mem_pool_ep_unit` (per-layer dense buffers, real shapes);
  - `test_lora_moe_runner_marlin_ep` (quant info, EP alignment);
  - `test_model_overrides`: runner choice, including targets read from adapter configs. Against the old override, exactly the 4 attention-only cases fail.

**GPU tests (H200 and GB300).**
- `test_lora_qkv_narrow_v`: the real wrapper with the Triton and CSGMV kernels, on Flash full / sliding-window and Pro shapes, TP 1/4/8, with member, partial and fused adapters.
- `test_lora_moe_marlin_mxfp4`: production MXFP4 repack, then the Marlin LoRA core with hooks, compared with the stock Marlin path and an fp32 reference.
  - Base and zero-adapter outputs are bitwise equal to the stock path.
  - Mixed adapters are within 0.5% of the reference, and the adapters' own effect within 2.7%.
  - Two EP ranks, and two MoE-TP shards, each sum to the full layer.
  - CUDA graph replay matches eager mode.
- Negative controls:
  - Without the V-width fix, every qkv case fails on both backends.
  - Without the EP fix, the EP case faults.
  - Before the SM100 fix, GB300 refuses the Marlin path.

**Serving, 4-layer MiMo-V2.6-Flash (both GPUs).** Logprob differences are prompt-token mean |d|.
- BF16 + LoRA: a zero adapter is bitwise equal to base.
- LoRA vs the same adapter merged into the weights: 0.020, at the level of the batch-composition noise (0.015–0.018).
- FP8 + MXFP4 + Marlin LoRA: zero adapter vs base 0.0095, against a same-request repeat of 0.009. EP4 vs EP1 adapter effect: cosine 0.97–0.98.
- `auto` resolves to Marlin, and `flashinfer_mxfp4` with expert LoRA is refused at startup.
- CSGMV (the default; logs say "Using csgmv" on every TP rank) with decode CUDA graphs:
  - A nonzero attention-only adapter matches the same adapter merged into the weights to 0.020 on prompt tokens and 0.024–0.032 on decode steps. Its effect is 0.12 (prompt) and 0.14–0.18 (decode).
  - An adapter on every target matches to 0.020 / 0.033–0.044. For comparison, the Triton backend: 0.020 / 0.022–0.030.
- MiMo prefill runs eagerly in this build, with or without LoRA: prefill CUDA graphs are off for multimodal models, and `--language-model-only` does not support `MiMoV2ForCausalLM`.

**Full checkpoints, TP4.** GSM8K, 200 questions, 5-shot, greedy:

| | no LoRA | LoRA, no adapter | zero adapter | EP4 |
|---|---|---|---|---|
| Flash, H200 | 171 | 174 | 175 | 174 |
| Flash, GB300 | 174 | 177 | 171 | 179 |
| Pro, GB300 | 189 | 187 | 181 | – |

- **MiMo without LoRA, base vs this PR (GB300):** bitwise-identical prompt logprobs and all 200 answers the same, for both Flash and Pro.
- **Attention-only adapters from `--lora-paths` (GB300):** the server keeps `flashinfer_mxfp4`. With no adapter selected, its output is bitwise equal to no LoRA.
- **CSGMV vs Triton, full Flash (GB300):** a strong attention-only adapter gives bitwise the same prompt and decode logprobs on CSGMV (default) as on Triton, and GSM8K is 180/200 on both.
- **Stronger adapters:** the EP4 vs EP1 effect cosine is 0.84 / 0.90 / 0.77, against a same-server repeat of 0.83 / 0.91 / 0.84. A strong MLP-only adapter moves GSM8K to 131/200, so expert LoRA is really applied.
- **Determinism:** the Marlin MXFP4 path is not bitwise repeatable (about 0.012 mean |d| on a repeat), with or without LoRA.

**Other models, base vs this PR (H200).**
- `test_lora_qwen3_8b_logprob_diff`, `test_lora_moe_tp_logprob_diff`, `test_lora_qwen3_5_35b_a3b_logprob_diff` and `test_lora_gpt_oss_20b_logprob_diff` pass on both, with identical printed metrics. The fa4-pinned tests ran with fa3 or triton attention on H200.
- `nvidia/Qwen3-30B-A3B-FP4` with LoRA on Marlin (ModelOpt NVFP4's W4A16 path on Hopper):
  - TP2: base vs this PR 0.0125, against a repeat of 0.012.
  - EP2: base faults (illegal memory access); this PR runs and matches TP2 within that noise.

**MTP loader fix (jybsuper/sglang#35).**
- By @guapisolo: MiMo-V2.6-Flash-RL on four TP2 H200 engines with LoRA (Miles Tinker gateway) and EAGLE (3 steps, top-k 1, 4 draft tokens). The engines start, and greedy decoding of 200 DAPO-Math prompts gives a mean accept length of 2.83 of 4.
- Rechecked on GB300: `test_mimo_v2_fused_qkv_loader` and `test_mimo_v2_lora` pass with the fix. Without it, the new MTP case fails with the `scale_inv` shape mismatch; with only the `mimo_v2_nextn.py` half, it fails on misordered q/k/v. The GPU test `test_mimo_fused_qkv_loader_layout` has the same 3 failures before and after (BF16 at checkpoint TP 8 loaded without a config).

## Not executed
- An adapter exported by Miles (these used synthetic PEFT adapters in the bridge's format).
- The Miles RL loop: weight sync and streamed adapter updates.
- The Llama-based LoRA tests (gated models).
- Throughput benchmarks.
- Prefill CUDA graphs with MiMo (disabled for multimodal models in this build).

## Known limitations
These exist on the base too and are not fixed here:
- The legacy Marlin LoRA core does not pad hidden sizes the stock Marlin path pads, so gpt-oss-20b MXFP4 (2880) fails with a shape error.
- `RedHatAI/Qwen3-30B-A3B-quantized.w4a16` produces garbage on this build even without LoRA.
- The qkv LoRA buffer is slightly over-allocated when TP is larger than the config's KV heads; the result is correct.
