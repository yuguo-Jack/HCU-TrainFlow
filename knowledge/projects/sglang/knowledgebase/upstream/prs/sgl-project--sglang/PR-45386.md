# [Fix] modelopt: Correct NVFP4 TRT-LLM clamps for untied gate/up scales

[Upstream PR](https://github.com/sgl-project/sglang/pull/45386) · state: closed · merged: True

## Original PR description

## Motivation

TRT-LLM applies one GEMM1 clamp to both raw gate/up projections. With unequal NVFP4 global scales, converting the limit using the gate alpha gives the up projection the wrong effective limit: the up limit becomes `L × up_alpha / gate_alpha`, so a configured limit of 7 becomes 28 at a 4× ratio, or becomes stricter when the ratio is below one.

## Modifications

Normalize the effective gate/up alphas to their maximum during the existing TRT-LLM clamp preparation, folding the scale ratio into the smaller-alpha half’s E4M3 block scales. Derive the clamp, beta and output scale from the shared alpha. The fold uses the resolved gate/up alphas and leaves the raw global scales as loaded. Block-scale rows in this backend are `[up, gate]`. The work happens at load time, with no added forward operations.

Extend the existing CPU post-load regression for both halves' effective clamp limits, weight preservation and SiTU behavior, with GPU packing mocked. The GPU regression used in the accuracy tests below was a development-only fixture and is not part of this PR.

## Accuracy Tests

On rebased `main` commit `c1c287a42928495166e14dbcef31b9e1f1dac199` (including #45289), the CPU scale suite passes 20/20 and dispatch suite passes 5/5, with GPU devices hidden. The CPU clamp regression fails on this base with an effective up-half clamp of 28 instead of 7 and passes with the fix.

The GPU and numerical results below were collected before this rebase, against `main` commit `afe3e1df3107b0487258cd4a3d8e625248a8f881` on GB300 with PyTorch 2.14.1+cu130, FlashInfer 0.7.2 and sglang-kernel 0.4.10. GPU runs were not repeated for conflict resolution:

- A development copy of the GPU backend test with a temporary unequal-scale clamp regression passed 5/5 with this fix; the regression fails on the base at cosine 0.9034 against the unchanged 0.99 threshold. That temporary regression is not committed.
- Exact power-of-two controls match tied outputs bitwise, including real GLM expert weights with synthetic activations, routed/non-routed execution, per-token activation, reload and CUDA graph replay. Tied, unclamped, SiTU and sibling-backend controls are preserved.
- All 14 non-binary cases match the unmodified backend loaded with the same normalized weights bitwise, on both execution paths.
- Public prompt check on `nvidia/GLM-5.3-Flash-NVFP4` at revision `da920bb0b9f4a06727223a349e55468e38352348`: the untouched checkpoint gives identical responses before/after. Re-expressing gate globals as ×4 and gate block scales as ÷4 is exact for this checkpoint; the fix’s ÷4 rescaling of the up block scales is exact too. The base then changes its response from 373 to 95 tokens; this fix restores the original content, token strings and logprobs exactly. Each configuration was repeated twice, with separate logprob diagnostics and cache flushes.

All public prompt runs copied the final table correctly and contained no replacement characters; their raw content included reasoning. This checks representation invariance, not reproduction of the reported Unicode failure. The reported finetuned checkpoint was unavailable.

**Rounding tradeoff:** non-binary normalization re-rounds one half's FP8 block scales. In the synthetic sweep, that changed the half's weights by 2.7–3.2% relative L2 and the reference output by 4.7–8.5% with both activation quantization steps included (0.7–3.4% when both were omitted). Every tested case improved over the incorrect clamp. No underflow occurred in these fixtures, but sufficiently small scales can become subnormal or flush to zero, including with power-of-two ratios. This is not a general model-quality evaluation.

## Speed Tests and Profiling

Before this rebase, sequential A/B/A/B CUDA graph measurements covered 52 points: 1–4096 tokens, routed/non-routed, tied/untied scales, 288 experts, hidden size 4096, intermediate size 512 and top-8, with L2 flushed before timing. All output controls passed. Candidate/base latency ratios were 0.9936–1.0031, within the pre-set `max(2%, 2 × baseline run spread)` criterion. The untied post-load step took 97–115 ms versus 90–105 ms on the base, once per 288-expert MoE layer at load time. Profiles confirm the TRT-LLM E2M1 GEMM/SwiGLU kernels.
