# [Fix] [XPU] vision: Keep padded image batches aligned with cu_seqlens in xpu_attn

[Upstream PR](https://github.com/sgl-project/sglang/pull/44670) · state: open · merged: False

## Original PR description

## Motivation

On Intel XPU, `openbmb/MiniCPM-o-2_6` sometimes answers an image question with `!` repeated until the output limit. On POPE, 126 of 9000 answers came back like this. The affected questions change on every server restart, but stay the same within one server.

Cause:
- The Idefics2 vision encoder pads the image slices in a batch to one common length, `(bsz, seq_len)`. `cu_seqlens`, however, holds the real slice lengths.
- `VisionIntelXPUAttention` passed the padded `q/k/v` and those `cu_seqlens` to `flash_attn_varlen_func`.
- So every slice after a padded one attended over the wrong rows. The real rows past `cu_seqlens[-1]` were never written; the kernel output comes from `new_empty`, so they keep leftover memory.
- When that memory holds NaN, the logits become NaN and argmax returns token 0 (`!`).
- The encoded image is cached, so every question on that image fails until the server restarts.

## Modifications

- `VisionIntelXPUAttention.forward`: when `bsz > 1` and the row count differs from `cu_seqlens[-1]`:
  1. gather the real rows,
  2. run the varlen kernel on the packed tensors,
  3. scatter the result back into a zero-initialized padded output.
  `VisionAscendAttention` already handles this layout the same way (see also #43748).
- No other path changes. `bsz == 1` (packed encoders such as Qwen-VL) skips the check entirely. Unpadded batches still make the original single kernel call.
- New test `test_xpu_attn_padded_batch_attends_within_each_image` in `test/registered/xpu/test_vision_backend_selection.py`. It uses slice lengths 1036/1014/1014 and head_dim 72, from a failing MiniCPM-o batch. It fails on main and passes with this change.

Note for reviewers: the `fa3`, `fa4` and `triton_attn` vision backends receive the same padded layout with packed `cu_seqlens`. This PR does not change them.

## Speed Tests and Profiling

Only padded batches of more than one image (`bsz > 1`) take the new path. That path adds one gather/scatter of q/k/v per encoder layer. POPE end to end took about 12 min both before and after (12:11 vs 12:32, on separate server runs).
