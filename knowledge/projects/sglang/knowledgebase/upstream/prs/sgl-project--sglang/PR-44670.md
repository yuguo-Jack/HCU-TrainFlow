# [Fix] [XPU] vision: Keep padded image batches aligned with cu_seqlens in xpu_attn

[Upstream PR](https://github.com/sgl-project/sglang/pull/44670) · state: open · merged: False

## Original PR description

## Motivation

On Intel XPU, `openbmb/MiniCPM-o-2_6` sometimes answers an image question with `!` repeated until the output limit. On POPE, 126 of 9000 answers came back like this. The affected questions change on every server restart, but stay the same within one server.

Cause:
- The Idefics2 vision encoder pads the image slices in a batch to one common length, `(bsz, seq_len)`. `cu_seqlens`, however, holds the real slice lengths.
- `VisionIntelXPUAttention` passed the padded `q/k/v` and those `cu_seqlens` to `flash_attn_varlen_func`.
- So every slice after a padded one attended over the wrong rows. The real rows past `cu_seqlens[-1]` were never written; the kernel output comes from `new_empty`, so they keep leftover memory.
- When that memory holds NaN, the logits become NaN and argmax returns token 0 (`!`).
- The encoded image is cached, so every question on that image fails until the server restarts.

## Modifications

- `VisionIntelXPUAttention.forward`: for `bsz > 1`, describe the padded layout to the kernel instead of the packed one: `cu_seqlens` at each image's padded offset (`seq_len` apart) and `seqused_q` / `seqused_k` with the real lengths. `max_seqlen` is the padded `seq_len`.
  - Each image attends only over its own real rows. The kernel skips the padding rows and returns them as zeros.
  - It is one kernel call over the padded tensor: no host sync, no boolean indexing, static shapes.
- `bsz == 1` (packed encoders such as Qwen-VL) is unchanged.
- New test `test_xpu_attn_padded_batch_attends_within_each_image` in `test/registered/xpu/test_vision_backend_selection.py`. It uses slice lengths 1036/1014/1014 and head_dim 72, from a failing MiniCPM-o batch. It fails on main and passes with this change.

**Depends on sgl-project/sgl-kernel-xpu#583**, which implements `seqused_q` / `seqused_k` in `flash_attn_varlen_func`. The pinned v0.4.0 accepts them but ignores them, so this PR needs a kernel release with sgl-kernel-xpu#583 and a pin bump before it can merge.

Note for reviewers: the `fa3`, `fa4` and `triton_attn` vision backends receive the same padded layout with packed `cu_seqlens`. CUDA FA3 can express it with `seqused_q` / `seqused_k`, which the `fa3` backend does not pass. This PR does not change them.

- desmond-intel · comment · 2026-10-26T22:00:27Z · [source](https://github.com/sgl-project/sglang/pull/44670#issuecomment-6428352461)

@mingfeima @airMeng Reworked so the fix is in the kernel.

- **Root cause.** idefics2 (MiniCPM-V/o, Phi-4-MM) pads the image slices to one length, `(B, Lmax)`, and puts the real lengths in `cu_seqlens`. The varlen backends read that as packed rows, so later images attend over the wrong rows and some real rows are never written. idefics2 is the only caller that sends a padded batch with real lengths.
- **Other devices.** CUDA FA3 handles this layout with padded `cu_seqlens` plus `seqused_q` / `seqused_k`. The `fa3` vision backend does not pass them today, so CUDA has the same misalignment; it just rarely turns into NaN there. NPU gathers and scatters in the backend (#43748).
- **Kernel gap.** sgl-kernel-xpu `flash_attn_varlen_func` accepted `seqused_q` / `seqused_k` but dropped them. sgl-project/sgl-kernel-xpu#583 implements them in the non-paged prefill kernel and returns the padding rows as zeros.
- **This PR** (64394dd258) now only passes the padded offsets and `seqused` for padded batches: no host sync, no mask or indexing, static shapes.
