## Motivation

[Foundry](https://github.com/foundry-org/foundry) is an external general plugin (entry point `foundry` in `sglang.srt.plugins`) that persists CUDA graphs across restarts: the first start (SAVE) archives the captured graphs, their kernels and the device-memory layout; later starts (LOAD) rebuild the graphs from the archive instead of capturing. It runs on unmodified SGLang by wrapping existing functions on their dotted paths and three whitelisted resolution steps. Docs: [docs/sglang](https://github.com/foundry-org/foundry/tree/sglang-registry/docs/sglang).

This PR adds no call sites and no hook API. It closes three gaps:

1. **Silent native start.** With `FOUNDRY_GRAPH_EXTENSION_CONFIG` set but the plugin not loaded, SGLang logs the failure and captures natively; the user asked for LOAD and gets no error.
2. **Unowned surface.** Nothing in the tree records which functions the plugin wraps, so a rename or a caller switched to `from ... import` breaks it without any SGLang test failing.
3. **No behavioral signal.** A change to what a captured graph reads (a new static buffer, a different capture order) shows up only as wrong tokens on a user's LOAD.

**No-op guarantee:** with the env var unset, no runtime path changes; the only addition is one env read in `load_plugins()`.

## Modifications

- **Env var** (`srt/environ.py`): `FOUNDRY_GRAPH_EXTENSION_CONFIG = EnvStr(None)`, documented in `references/environment_variables.mdx` and `hardware-platforms/plugin.mdx`.
- **Fail-fast loader** (`srt/plugins/__init__.py`): `load_plugins()` raises `ValueError` when the variable is set and the `foundry` plugin did not load (not installed, import error, filtered by `SGLANG_PLUGINS` / `SGLANG_PLATFORM`). New case in `unit/plugins/test_load_plugins.py`.
- **Contract test** (`unit/plugins/test_foundry_plugin_contract.py`, CPU, AST-based, no Foundry needed): pins the 10 wrapped functions and their parameter lists, one attribute-dispatching caller of each, the runtime-context names read, the `load_plugins()` call sites and entry-point group, and the three resolution steps in `_OVERRIDABLE_HOOKS`. Each failure message says what to update.
- **E2E test** (`e2e/plugins/test_foundry_graph_persistence.py`, 1 GPU, nightly, runner `1-gpu-large-foundry`; skips without `foundry`): native, then SAVE, then LOAD for `Qwen3.5-2B` (decode graphs; prefill graphs off until #36077 lands, see below) and `Qwen3-1.7B` on flashinfer (prefill + decode graphs). Asserts greedy parity with native, LOAD TPOT not above native, bounded restore time, every archived graph restored and replayed, plugin active with no hook errors, archive written.
- **CI**: `scripts/ci/cuda/ci_install_foundry.sh` installs Foundry with `uv pip install --no-build-isolation --no-deps git+https://github.com/foundry-org/foundry.git@${FOUNDRY_GIT_REF:-sglang-registry}`; runner config `1-gpu-large-foundry` (the `1-gpu-h100` pool); suite `nightly-test-1-gpu-large-foundry`; job `nightly-1-gpu-large-foundry` in `nightly-test-nvidia.yml`.

**Maintainers:** the runners need github.com access and the two models in the HF cache. `FOUNDRY_GIT_REF` has no repository variable yet, so the nightly tracks the Foundry branch `sglang-registry`; tell us whether you prefer a pinned tag as the script default or `${{ vars.FOUNDRY_GIT_REF }}`.

**Follow-ups:** larger nightly tests (Qwen3.5-35B-A3B TP2 / EP2, Qwen3.5-122B-FP8 EP4, DeepSeek-V4-Flash-FP8 EP4; exist in Foundry as `test_sglang_save_load_large.py`); optionally expressing the wraps as `HookRegistry` AROUND hooks (no SGLang change needed).

## Accuracy Tests

No model output or kernel changes, so no GSM8K run. Covered by:

- **E2E greedy parity**: 8 prompts x 64 tokens, temperature 0, one at a time and batched; SAVE and LOAD are token-identical to native. On H200: 12/12 in 3 of 4 runs (the fourth failed only the TPOT check while another job shared the host).
- **Real weights** (Foundry side, sglang `main` `fa090f7755`, Qwen3-30B-A3B-FP8, 20 greedy prompts): native vs LOAD 20/20 on EP4 and TP2.
- **CPU tests**: `test_load_plugins.py` and `test_foundry_plugin_contract.py` pass; a mutation check (wrong parameter list, missing call, renamed method) fails the contract cases as intended.

## Speed Tests and Profiling

The PR does not touch the inference path; the numbers are Foundry's startup effect. Each model is started as native graph engine, Foundry SAVE and Foundry LOAD on the same 4xH200 (sglang `main` `fa090f7755` + plugin unless labelled), and each start is split into stages from rank-0 log timestamps up to the first `/health` 200.

![Cold-start stage breakdown](https://raw.githubusercontent.com/foundry-org/foundry/sglang-registry/docs/sglang/figs/stages_pr.png)

Reading the figure:
- Stages come from log lines: process start (to `Init parallel begin`), distributed init (to `Load weight begin`), weight load, KV pool + attention setup, the graph phase (SGLang's `Capture ... elapsed=`; on LOAD split into restore only, the capture loop's per-shape prep, and bootstraps), and server ready (to the first `/health` 200). Timestamps have 1 s resolution; every bar is one run; the dashed tick is the eager engine (`--disable-cuda-graph`).
- **On LOAD, restore replaces capture**: 0.8-1.7 s per rank for 128 decode graphs (plus prefill graphs where present) against 32-86 s of native capture. LOAD reaches `/health` 2-9 s after the eager engine; process start (17-26 s) is now the largest LOAD stage.
- **Server ready is 1-3 s longer on LOAD** because `/health` generates one token, i.e. the process's first eager forward (native and SAVE already ran the eager path during capture). The faded "/health w/o generate" bars re-run two rows with `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=0`: `/health` then answers within 1 s of `fired up` on every engine (LOAD 40.8 s vs native 90.1 s on 122B; 44.2 vs 80.7 s on 30B) and the first real request pays that forward instead, on LOAD and native alike.

**Pass table.** LOAD served with restored graphs and greedy output equal to native (real weights) or to native's dummy-weight text. "n/a" = plain SGLang cannot capture FULL prefill graphs for that model.

FULL prefill graphs on Qwen3.5 (GDN), DeepSeek-V4, GLM-5.3 and Inkling are an SGLang limitation, not a plugin one. For GDN the blocker is the hybrid backend's graph metadata (#35437), not the kernel; once #36077 or an equivalent lands, the plugin needs no change and we will add the Qwen3.5 prefill rows. Full per-row timings: [validated-configs.md](https://github.com/foundry-org/foundry/blob/sglang-registry/docs/sglang/validated-configs.md).
