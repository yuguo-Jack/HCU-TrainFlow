# [diffusion] Bind each GPU worker to its GPU's NUMA node

[Upstream PR](https://github.com/sgl-project/sglang/pull/43565) · state: closed · merged: True

## Original PR description

## Motivation

srt binds every scheduler process to its GPU's NUMA node by default (`SGLANG_AUTO_NUMA_BIND`, `numa_utils`). sglang-diffusion GPU workers were never bound. On a two-socket host, an unbound worker drifts to the other socket while its first-touch host memory stays behind, so every host-bound op pays remote-memory latency. The same configuration then lands in one of two modes from one run to the next.

GB300 (2x Grace; GPU0/1 on node 0, GPU2/3 on node 1), FLUX.1-dev TP2 eager with no other changes: 6.54, 4.30, 6.14, 6.49 s across runs. With the workers bound, it stays at about 4.0 s.

## Modifications

- `run_scheduler_process` binds the worker to its GPU's NUMA node before CUDA init and model load, so first-touch memory lands on the local node. It reuses srt's `get_numa_node_if_available` and `numa_bind_to_node` (in-process `sched_setaffinity` + preferred memory policy), so detection, `SGLANG_AUTO_NUMA_BIND=0`, permission checks and the failure semantics all match srt.
- srt's spawn-time `numactl` path (`configure_subprocess`) is not reused. `_mp_set_executable` asserts that the **global** multiprocessing start method is spawn, while diffusion launches workers from a local `mp.get_context("spawn")`, so the global method is still `fork` on Linux.
- New `--numa-node N [N ...]` with srt's meaning (the i-th value is for the worker on local GPU i), validated against the local worker count, plus a line in `api/cli.mdx`.

## Accuracy Tests

No numerical change: only CPU affinity and the host memory policy of the worker process change.

## Speed Tests and Profiling

GB300, `sglang serve`, `/v1/images/generations`. Each value is the median of 5 requests after 2 warmups, with a fresh server per arm because placement is decided at startup. Arms are interleaved.

| Case | Unbound (main) | Bound |
|---|---|---|
| Cosmos3-Nano T2I 1280x720, 35 steps, CFG-parallel 2 GPUs, eager | 1.349 / 1.270 s | **0.919 / 0.967 s** (this PR, no numactl) |
| same, on GPUs 2,3 | – | 0.947 s; log: `GPU 0/1 worker bound to NUMA node 1` |
| FLUX.1-dev 1024², 50 steps, TP2, eager | 6.44 / 6.37 / 6.06 s | 3.98 / 4.00 / 3.83 s (`numactl` on node 0 as a stand-in) |

Why it matters there: per-rank torch-profiler traces of the unbound FLUX TP2 run show both ranks' main threads ~100% busy on the CPU side. Rank 1 GPU is 27% busy with 639 ms of gaps per 4 steps, while rank 0 spends 1.3 ms per custom all-reduce waiting for it. The step time is the slower rank's host time, so placement shows up 1:1 in latency.
