# [Perf] R3: Gather DeepEP routed-expert ids once per forward (3/3)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47554) · state: open · merged: False

## Original PR description

Stacked on #47553 (which is stacked on #47552).

## Why?

With a scattered MoE a2a backend (DeepEP), each attention-TP rank holds a slice of the tokens. So capture all-gathered every MoE layer's ids inside the forward: one small collective per layer, on every rank, between top-k and dispatch.

```text
Before (one forward, attn-TP 4, L MoE layers)       After
layer 1: top-k → all-gather → device buffer         layer 1: top-k → local buffer
layer 2: top-k → all-gather → device buffer         layer 2: top-k → local buffer
  ...                                                  ...
layer L: top-k → all-gather → device buffer         layer L: top-k → local buffer → 1 all-gather, all layers
= L collectives on every rank                       = 1 collective
```

## What?

- Each rank writes its own tokens' ids to a local buffer. At this rank's last routed layer, `capture()` all-gathers every layer in one call: the output rank receives into its device buffer, the other ranks into a scratch buffer they ignore. Ranks hold equal, rank-ordered shares, so rows land in the order the per-layer all-gather produced.
- The all-gather runs inside the forward and takes its size from the captured rows, so CUDA graphs record it with the shapes they replay.
- The last routed layer is the highest `TopK.layer_id` with capture enabled on this rank (each pipeline stage finds its own), computed once in `create()`. A capture past it raises, and so does a layer whose row count differs from the first routed layer's. The per-layer all-gather stays when there is no such layer (models that call `capture()` directly) and under decoder SWA bounded replay, whose late layers run on fewer rows.
- Groups outside pp0 / attn-cp0 send nothing. The path needs only attn-TP > 1, with or without DP attention.

[P2] With `--enable-two-batch-overlap`, this row-count check raises in the middle of a forward.

TBO runs `TopK` once per sub-batch on every MoE layer (`op_select_experts` runs per `state`, and `execute_overlapped_operations` alternates `executor_a.next()` / `executor_b.next()`), so `capture()` sees layer 0 of sub-batch A, then layer 0 of sub-batch B, then layer 1 of A, and so on. B's first routed layer resets `_first_layer_rows` to B's row count, and the next capture from A raises whenever the two sub-batches hold different local row counts. That is the common case for prefill and for an odd number of decode requests. It needs `--enable-return-routed-experts`, a scattered a2a backend and attn-TP > 1, which is the setup TBO normally runs with.

The base did not raise in this order, but it already returned wrong rows: B overwrites A's gathered rows, and with unequal shares the buffer keeps a mix of B's rows and A's leftover rows. So this PR turns silently wrong routed experts into a server error.

Repro (CPU, PR code with the all-gather mocked to append a peer share), capturing in TBO order with 3 and 2 local rows per sub-batch:
- this PR (08115fda0e): `RuntimeError: Layer 1 captured 3 routed-expert rows, but layer 0 captured 2.`
- base (b8f6c96e59): no error, rows 0-3 of every layer hold B's share and its peer share, rows 4-5 still hold A's peer rows.

Suggested fix: reject `--enable-return-routed-experts` together with `--enable-two-batch-overlap` at startup, since neither path returns correct rows under TBO today. If you want to keep this PR scoped, pass `routed_layer_ids=None` when TBO is on, as for bounded replay, so TBO keeps the per-layer path and this PR adds no crash.

Not verified: an end-to-end GPU run with TBO.
