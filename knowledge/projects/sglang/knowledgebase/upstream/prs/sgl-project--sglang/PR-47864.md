# [Fix] tool-call: enforce parallel_tool_calls=false for tool_choice=auto

[Upstream PR](https://github.com/sgl-project/sglang/pull/47864) · state: open · merged: False

## Original PR description

## Motivation

With `tool_choice="auto"` and non-strict tools no grammar covers the turn, and `parallel_tool_calls=False` was not applied to the parsed result either. `maxItems: 1` is only attached for `tool_choice="required"` / a named function, so on the auto path the flag had no effect: the model generates freely and the response carries every call it emitted.

Reproduced on Qwen3.8-27B (`--tool-call-parser qwen3_coder`): `What's the weather in Hanoi and Tokyo? Use the tool.` with one `get_weather` tool, `tool_choice="auto"`, `parallel_tool_calls=false` returns 2 tool calls (Hanoi, Tokyo), in both non-stream and stream modes. OpenAI semantics say at most one.

An earlier attempt exists in #37157, which takes the same approach but no longer applies to `main` (`FunctionCallParser` gained `prefix`/`constrained`/`tool_choice`, `serving_chat`/`serving_responses` changed) and has no review yet; this PR re-does it on current `main` and adds the `/v1/responses` paths and tests. #43112 (Anthropic `disable_parallel_tool_use`) is a different endpoint and is not touched.

## Modifications

- `FunctionCallParser(parallel_tool_calls=True)`: non-stream (`parse_non_stream`) keeps only the first parsed call; streaming (`parse_stream_chunk`, `parse_stream_end`) locks onto the first call's `tool_index` and drops items of later calls (`_keep_first_call`).
- Pass `request.parallel_tool_calls` into the parser in chat (non-stream, stream, and the `required` probe path) and in `/v1/responses` (non-stream and stream; `parallel_tool_calls is not False`, the field is Optional there).
- Default `True`, so `parallel_tool_calls` true/unset behaves as before; `required` / named choices already carry `maxItems: 1` and are unaffected.
- Not done here: the model still generates the extra calls and they are dropped afterwards. Stopping generation after the first call would save the tokens and is left for a follow-up.
- Tests: `TestParallelToolCallsFalse` (4 cases, real `qwen25` detector, stream fed in 7-char chunks) in `test_function_call_parser.py`, and one case in `test_serving_chat.py` checking the flag reaches the parser on both paths. 3 of the 4 parser cases and the serving case fail without the change.

## Accuracy Tests

No forward or kernel change. Live check, Qwen3.8-27B NVFP4 + EAGLE, `--tool-call-parser qwen3_coder`, 1×RTX PRO 6000, release/v0.5.23 image with the patch overlaid (this branch is rebased on current `main`, covered by the unit tests only). Two-city prompt above:

| `parallel_tool_calls` | before | after |
|---|---|---|
| `false`, non-stream | 2 calls | 1 call (Hanoi) |
| `false`, stream | 2 calls | 1 call (Hanoi) |
| `true` / unset | 2 calls | 2 calls |

Also run against a production deployment (1×H200, Qwen3.8-27B-FP8, `--attention-backend fa3`, EAGLE, HiCache, 1M context, `--reasoning-parser qwen3 --tool-call-parser qwen3_coder`, release/v0.5.23 with this patch mounted): same results as the table, including the streaming cases.

Known limit: the streaming clamp keys on `tool_index`. Detectors that report an index by tool position rather than call order (`gemma4`) or always 0 (`gigachat3`) cannot be separated this way; the other detectors checked report call order.

## Speed Tests and Profiling

None expected: a slice/filter over the already-parsed calls.
