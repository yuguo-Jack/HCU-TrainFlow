# [Fix] moe: Use single-writer prefixes in ep_scatter

[Upstream PR](https://github.com/sgl-project/sglang/pull/44974) · state: open · merged: False

## Original PR description

## Motivation

Fixes #31929. Follow-up to #31930 by HPC4AI.

#31930 already identifies the stale read and proposes computing the offset directly from the expert counts. It still computes a full `cumsum` and has every program write the entire offset table.

We hit the same crash on GLM-5.3-Flash + DFlash2, TP8 on H20-3e, with SGLang 0.5.22. Disabling CUDA graphs and enabling synchronous launches traced it to `_fwd_kernel_ep_scatter_1`.

## Modifications

Keep the direct prefix sum from #31930, remove the redundant full scan, and let each program store only its own offset. This removes the global read-back and the overlapping full-table writes without adding a kernel launch or buffer.

Add registered tests for poisoned offsets, guard regions, empty experts, tile-boundary counts (`0, 1, B-1, B, B+1`), trailing slack, graph replay, and BF16/FP8 scatter. The current padded-row convention is preserved: live rows carry their expert ID and padding carries `-1`.

## Accuracy Tests

H20-3e, PyTorch 2.14.1+cu130, Triton 3.8.0:

```bash
PYTHONPATH=python python test/registered/kernels/ops/moe/test_ep_scatter.py -v
```

4 tests passed. The same tests passed under `compute-sanitizer --tool memcheck --report-api-errors no --error-exitcode 1`, with 0 memory errors. API-error reporting was disabled for library version probes unsupported by the installed driver.

The patched serving kernel also completed the original 32-request benchmark at concurrency 1 and 32, with CUDA graphs enabled. Full model accuracy evaluation was not run.

## Speed Tests and Profiling

Compared the prefix change in #31930, adapted to the current padded-row kernel, against this PR on the same H20. Both matched CPU-derived offsets and indices.

289 experts, 8 warps, 128-row alignment; synthetic 8-routed + 1-shared counts. CUDA-graph timing, median of three measurements:

| Input tokens | #31930 approach (µs) | This PR (µs) |
| ---: | ---: | ---: |
| 8 | 3.75 | 1.55 |
| 256 | 4.16 | 1.64 |
| 4096 | 6.48 | 4.96 |

These are isolated kernel timings. The end-to-end serving benchmark did not show a material gain over our earlier correctness-only patch.
