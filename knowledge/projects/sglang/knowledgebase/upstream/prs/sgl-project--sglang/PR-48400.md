## Modifications

Pin triton to v3.9.0 (b7ddcf86)

## Accuracy Tests


Triton 3.8 is `3.8.0+git1001b1bc` (triton-lang/triton@76940ad3 plus the revert of triton-lang/triton#10833); Triton 3.9 is v3.9.0 (`b7ddcf86`) without the revert.

| Model | Config | Accuracy (3.8 → 3.9) | Performance (3.8 → 3.9) | Result |
|---|---|---|---|---|
| DeepSeek-V4-Flash | TP8 | GSM8K 0.947 → 0.946 | 914 / 912 → 920 tok/s | Match |
| FLUX.2-dev (with negative prompt) | TP2 CFG parallel, torch.compile | Image PSNR 30.2 dB (3.8 run-to-run: 30.8 dB) | 32.78 → 32.62 s | Match |
| FLUX.2-dev (no negative prompt) | TP2 CFG parallel, torch.compile | Image PSNR 44.1 dB (3.8 run-to-run: 40.0 dB) | 32.02 → 32.14 s | Match |
| gpt-oss-120b W4A8 | TP2, W4A8 backend=triton | GSM8K 0.836 → 0.836, 0.835 → 0.835 | 3558 → 3580 tok/s | Match |
| Wan2.2-T2V-A14B | TP1, 720p, 193 frames, 8 steps | Video PSNR 39.1 dB | 1523 → 1530 s | Match |
| Wan2.2-T2V-A14B | TP2 CFG parallel | Video PSNR 28.3 dB | 977 → 1002 s | Match |

Notes:
- PSNR compares the 3.9 output against the 3.8 output. For FLUX.2, "3.8 run-to-run" is the PSNR between two 3.8 runs, a baseline for same-version nondeterminism.
- DeepSeek-V4-Flash: GSM8K via `run_eval` (5-shot). Benchmark at concurrency 64, 320 prompts, 8K input / 1K output (3.8: 2 runs, 3.9: 1 run).
- gpt-oss-120b:
  - Run with `--disable-custom-all-reduce`, because custom all-reduce crashes during CUDA graph capture on both 3.8 and 3.9.
  - GSM8K is 5-shot completion on all 1319 questions, 2 rounds per version.
  - Throughput is with a warm cache. The cold first round was 1636 → 1520 tok/s, from slightly slower compilation on 3.9.
  - The default gluon W4A8 backend was not tested end to end. aiter's unit tests show 8 failures only on 3.9 in `out_mx_quant` mode.
- Wan2.2:
  - All three environments (3.8, 3.9, and the ROCm 10.0 image `v0.5.23-rocm10-mi45x-20261102`) show the same broken frames: noise in the first ~40 frames and no content in the last ~40. This is not caused by Triton.
