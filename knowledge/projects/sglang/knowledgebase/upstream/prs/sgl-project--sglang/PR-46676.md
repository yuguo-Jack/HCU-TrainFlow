# [Fix] dsv4: Keep a coordinated verify rank out of the decoder-tail idle replay

[Upstream PR](https://github.com/sgl-project/sglang/pull/46676) · state: closed · merged: True

## Original PR description

[by Claude Code]

Fixes #46666.

## Motivation

Two DeepSeek-V4.1 serving features meet in this bug.

- **Decoder SWA bounded replay** (on by default where supported). Layers after 20 keep no compressed KV of their own: they read layer 20's, which layer 20 writes for every row. The only state these late layers leave for later tokens is each layer's 128-token sliding window (SWA). So on a prefill (extend) step, the layers from 20 on (`late_layer_start`) run over only each request's last 128 extend rows, the request's *tail*. #45059 and #45107 replay these tail layers from CUDA graphs, one per padded row count (a multiple of 128). Under DP attention every rank replays the same graph, because the ranks meet at every MoE layer. A rank without a tail joins with zero rows of its own (`DecoderReplayTail.run_idle`), on the assumption that it has nothing to compute.
- **DP spec-prefill coordination** (`SGLANG_ENABLE_DP_SPEC_PREFILL_COORDINATION=1`, #40118). One DP rank runs its speculative verify in the same step as another rank's prefill. Each rank keeps its own batch; the step is marked `is_extend_in_batch`.

On such a coordinated step the verify rank is not idle: it has batch size x verify width rows (6 per request with DSpark block size 5). It has no prefill tail, though, so `DecoderReplayTail.plan` sends it down the idle path. Its outputs of the late layers are then replaced by the replay of the other rank's tail graph, cut to the verify's row count by `RowBucketGraphRunner.run`:

- more verify rows than the bucket (22+ requests against a peer prefilling one request): DFlash verify raises `ValueError: next_token_logits row count mismatch for DFlash verify adjustments. Expected 192, got 128.` and the DP schedulers die;
- fewer: no error, but the verify accepts draft tokens against stale logits.

This PR makes `DecoderReplayTail.plan` return "no tail graph" on coordinated steps, so every rank runs the late layers eagerly on those steps, as all steps did before #45107. Coordination itself is unchanged: the prefill and the verify still run in the same step, each in its own batch. Every rank of a coordinated step carries `dp_spec_prefill_coordination_applied`, so the ranks still agree on skipping the tail graphs' host gather and captures. Uncoordinated steps, including steps with genuinely idle ranks, keep the tail graphs unchanged.

Impact:
- **Correctness (e2e):** DeepSeek-V4.1-Flash, 2x B300, the InferenceX B300 DEP2 recipe under a load that forces
  coordinated steps. Main crashes on its first coordinated step (2 of 2 runs: `Expected 192, got 128` and
  `Expected 186, got 128`). With this PR the same load runs its full 240 s: 231 coordinated steps with 27-39 verifying
  requests, no error.
- **Accuracy:** GSM8K (sgl-eval, 1319 examples, no thinking, real acceptance, coordination on) 96.66% and 97.12% with
  this PR vs 96.29% and 96.44% on main; within noise (about 0.5 points standard error), because GSM8K traffic makes
  only 5-8 coordinated steps per run. The new GPU test pins the wrong-logits case exactly.
- **Performance:** no change on uncoordinated steps. On coordinated steps the tail layers run eagerly, as before
  #45107 (see Speed Tests).

## Modifications

**+5 / -0 runtime code (1 file), +190 tests (1 file).** No kernel changes.

- `DecoderReplayTail.plan` returns `(False, None)` when `forward_batch.dp_spec_prefill_coordination_applied`, before
  the host gather (`python/sglang/srt/models/deepseek_v4_replay_tail.py`).
- New 1-GPU test `test/registered/e2e/model_executor/test_decoder_tail_dp_spec_coordination.py`. It runs the tail
  plan and the model's dispatch for a rank without a tail through the real `RowBucketGraphRunner` and a real CUDA
  graph, with the peer's tail rows patched in (row step 8 standing in for 128), and compares the rank's late-layer
  output exactly with the reference:
  - coordinated verify rank, 10 rows (more than the peer's bucket): fails on main with
    `torch.Size([8, 1, 4]) != torch.Size([10, 1, 4])` (the crash's row cut);
  - coordinated verify rank, 5 rows (fewer than the bucket): fails on main with 20 / 20 elements wrong (the silent case);
  - an idle rank on an uncoordinated step still replays the shared bucket (guards against a fix that drops the
    graphs for idle ranks, whose peers capture behind rank barriers).
- Related: #46526 refactors `DecoderReplayTail` but keeps the same `plan` early return and the `run_idle` dispatch, so
  it does not fix this; the fix applies on top of it unchanged. If it lands first, the test's `late_dp_counts=` keyword
  becomes `late_dp_rows=`.

--num-examples 1319 --num-threads 24 --temperature 1.0 --top-p 0.95 --no-thinking --max-tokens 4096` (sgl-eval 0.1.3,

exactly (all 20 values of the 5 rows wrong on main).

## Speed Tests and Profiling

No change on uncoordinated steps: the new check is one attribute read per tail plan.

On coordinated steps, every rank now runs the tail layers eagerly. Main is not a speed baseline for these steps: there
the verify rank skipped its late layers and crashed or computed wrong logits.

**End to end (estimate, not measured):** compared with a hypothetical correct graph path for coordinated steps, the
cost is the eager launch overhead of the prefill rank's tail layers on coordinated steps only. #45107 measured that
overhead at about 42 ms per eager 8K-token prefill step (GB300, DP2 attention, MegaMoE, encoder replay on: cold 8K
TTFT 208.4 -> 166.2 ms). That is an upper bound here, since the verify rank already runs eagerly on these steps and the ranks meet at every
MoE layer. Letting the verify rank's own rows ride the tail graph would recover it, but it replays TARGET_VERIFY rows
through graphs captured on EXTEND batches; that is left for a follow-up.

Repro of the e2e runs: image `lmsysorg/sglang:nightly-dev-cu13-20261026-8252e3af` with the tree's `python/` first on
`PYTHONPATH`. Server: the InferenceX B300 DEP2 DeepSeek-V4.1-Flash recipe (TP2 DP2 EP2, DP attention, MegaMoE,
DSpark block 5, `--disable-prefill-cuda-graph`, `SGLANG_ENABLE_DP_SPEC_PREFILL_COORDINATION=1`, simulated
acceptance 3.51). Load: one 34,000-token prompt (one full 32K chunk, after which the tail graphs run), then 64
closed-loop greedy generations (1,000 in / 8,000 out) plus one 3,000-token prompt per second, for 240 s.
