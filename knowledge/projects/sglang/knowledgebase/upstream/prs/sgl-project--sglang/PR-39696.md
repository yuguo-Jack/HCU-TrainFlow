# [Performance] Batch Mooncake hybrid-pool metadata and puts

[Upstream PR](https://github.com/sgl-project/sglang/pull/39696) · state: closed · merged: True

## Original PR description

## Summary

Split from #39694 as an independently reviewable Mooncake optimization.

Mooncake hybrid-cache writes now:

- expand all component keys into one logical batch;
- query object existence once across the batch;
- build page-buffer metadata only for missing objects;
- submit scalar and multi-buffer components through one grouped put;
- preserve per-component results, group IDs, and partial-miss behavior.

## Motivation

The previous v2 path repeated existence checks and put submissions per hybrid-cache component. It also constructed buffer descriptors for pages that Mooncake already contained, so high-hit workloads paid scheduler-side metadata overhead that was immediately discarded.

## Validation

- `pre-commit run --all-files --show-diff-on-failure` passes, including Python formatting, registered-test validation, rustfmt, and clippy.
- Existing Mooncake group-semantics coverage is extended with a mixed scalar/multi-buffer case that verifies one existence query, one grouped put, key ordering, pointer/size packing, and group IDs.
- Additional unit cases cover mixed hits across pages (only missing pages' host slots are materialized) and a two-object-per-page pool where one page is partly stored (only the missing object is put, with its own pointer and group ID).
- Measured in isolation on GB300 (DeepSeek-V4-Pro, agentic-coding replay, concurrency 1920 over 48 serving GPUs in a 4P1D disaggregated topology, 3600 s measurement, committed golden acceptance length, KV offload on Mooncake with the unified-cache external linker). Each arm is mainline plus only this change, three repetitions per arm:

| Arm | Runs | Total throughput / GPU | Std. dev. |
|---|---|---|---|
| mainline | 3 | 92,838 tok/s | 1,500 (1.6%) |
| mainline + this PR | 3 | 94,586 tok/s | 1,940 (2.1%) |

  The +1.9% mean difference is 1.2 combined standard errors, so this workload cannot resolve it: run-to-run spread within a single arm is as large as the effect. Read the throughput as unchanged rather than improved.

- The write-path RPC reduction reproduces in every run. Per prefill worker over one measurement window, `batch_put_from_multi_buffers` calls drop from 123,888 to 12.8k-24.8k (-80% to -90%), because each logical write now issues one existence query and one put across all hybrid-cache pools instead of one of each per pool. For the same store state the objects and bytes written are unchanged: mainline already put only the objects reported missing, so the submitted-byte difference observed between arms reflects run-to-run hit-rate differences, not this change. The value of this change is fewer store RPCs and no buffer-descriptor construction for pages the store already holds, not reduced write volume or throughput on this workload.

- A first version of this PR built buffer metadata for every component key before the existence query and filtered afterwards, which left the metadata cost in place at high hit rates; the follow-up commit restores deferred, missing-page-only metadata construction.
