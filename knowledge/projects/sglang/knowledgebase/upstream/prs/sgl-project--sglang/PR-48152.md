# [Perf] [AMD] DeepSeek-V4.1: Shard the HIP prefill indexer rows across attention TP

[Upstream PR](https://github.com/sgl-project/sglang/pull/48152) · state: open · merged: False

## Original PR description

## Motivation

#42968 shards the DeepSeek-V4.1 ratio-1/2 prefill indexer across attention TP (`SGLANG_OPT_DSV4_INDEXER_TP_SHARD`), but only on the CUDA DeepGEMM path. On ROCm, `DeepseekV4HipRadixBackend` overrides `_low_ratio_index_topk` and calls `low_ratio_index_topk_hip_extend`, which never reads `row_shard`. Setting the flag on ROCm does nothing, and every attention-TP rank still scores every prefill row.

Related: #48147 is a draft that outlines the same idea but has no code yet. This PR implements it and includes MI355X results.

## Modifications

Behind the same flag and the same gate as #42968 (`DeepseekV4AttnBackend._indexer_row_shard`: flag on, attn TP > 1, no attn CP, at least 512 rows; default off):

- `deepseek_v4_backend_hip_radix.py`: reuse `_indexer_row_shard` and pass the shard to the HIP extend indexer. Decode and verify are unchanged.
- `low_ratio_backend_hip.py`:
  - The rank's share of rows goes through the existing request-group loop.
  - Each request's rows are clipped to that share. A request cut by the shard boundary uses the existing mid-request row-chunk path.
  - A consumer layer's candidate blocks are sliced to the rank's rows.
  - One int32 all-gather over the attention-TP group (`RowShard.gather`) returns `page_indices`, `raw_indices` and, on the candidate-source layer, the candidate block ids and compact lengths. Every rank then rebuilds the per-request publication.

## Accuracy Tests

GSM8K, 1319 questions, same server, flag off vs on:

| | off | on |
|---|---|---|
| TP4 | 0.907 | 0.906 |
| TP2 | 0.906 | 0.905 |

Exactness check on hardware: a debug build ran each indexer call both replicated and sharded. Over 601 calls per rank (16K-row chunks, 128/256-row late-layer tails, multi-request GSM8K batches), the rows a rank scores itself matched its replicated selection set for set.

Rows owned by other ranks can differ on small calls. That variation already exists in the replicated path today: on small calls the attention-TP ranks compute bit-different indexer head weights (`x` and `q` identical), so their replicated top-k selections already differ from each other. With the shard, all ranks use the same gathered selection.

## Speed Tests and Profiling

MI355X, DeepSeek-V4.1-Flash, DSpark, agentic recipe args, `--chunked-prefill-size 16384`, no DP attention. Single request, random-token prompt, median of 3 interleaved reps per arm:

| context | TP4 off → on | Δ | TP2 off → on | Δ |
|---|---|---|---|---|
| 64K | 0.79 → 0.79 s | −1.0% | 1.10 → 1.10 s | +0.2% |
| 128K | 1.64 → 1.59 s | −2.8% | 2.26 → 2.24 s | −0.8% |
| 256K | 3.47 → 3.25 s | −6.4% | 4.68 → 4.58 s | −2.1% |
| 512K | 7.65 → 6.74 s | −11.9% | 10.07 → 9.53 s | −5.3% |
| 1M | 18.07 → 14.19 s | **−21.4%** | 22.84 → 20.46 s | **−10.5%** |

8K/1K serving (conc 1/4/16):
- TP4 is unchanged.
- TP2 TTFT is about +1% at conc 1 and 4 (148 → 150 ms), with throughput unchanged. That is the cost of the all-gather at short prompts.

These numbers were measured with an earlier revision of this patch that implements the same algorithm. The final code was checked against it on CPU with randomized batches: the shard bookkeeping and the gather reconstruct the replicated indices and publication exactly. A hardware re-run on the final code is in progress, and I will post the results here.

### Suggestions

**1. Size the gather from the padded row count.** The caller cuts each rank's share from `num_tokens = pos.shape[0]` ([low_ratio_backend_hip.py#L693](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/dsv4/low_ratio_backend_hip.py#L693)), but `_gather_shard` sizes the gather from `sum(extend_lens)` ([low_ratio_backend_hip.py#L811](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/dsv4/low_ratio_backend_hip.py#L811)). When a call has padding rows, these counts differ. Then rows land in the wrong place, and the top-k indices are wrong with no error. Eager TP prefill has no padding rows, but graph breaks (point 2) do. In a repro with 1,500 real rows padded to 2,048, 1,124 rows were wrong at TP4, and none with the fix. Fix: pass the count from the caller, and use it in `_gather_shard` in place of `num_rows = sum(extend_lens)`:

```diff
             publish,
+            num_rows=num_tokens,
             published=[
```

**2. Keep breakable prefill graphs unsharded, as #42968 does.** `_low_ratio_index_topk` asks for a shard on every extend call ([deepseek_v4_backend_hip_radix.py#L3515](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/deepseek_v4_backend_hip_radix.py#L3515)). But this indexer also runs inside breakable prefill graphs, as an eager step between captured parts (`_low_ratio_sources_break`, [deepseek_v4.py#L919-L929](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/models/deepseek_v4.py#L919-L929)). #42968 keeps those calls unsharded ([deepseek_v4_backend.py#L4071-L4072](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/deepseek_v4_backend.py#L4071-L4072), [deepseek_v4_backend.py#L4191](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/deepseek_v4_backend.py#L4191)). The rows there are padded, so point 1 hits them. Fix: pass `row_shard=None` when `is_in_breakable_cuda_graph()` is true. We found this in the code; our runs did not use prefill graphs.

**3. Stop serving-time Triton compiles in the prefill schedule.** The schedule prep kernel ([fp4_indexer_schedule_hip.py#L65-L66](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/kernels/ops/attention/dsv4/fp4_indexer_schedule_hip.py#L65-L66)) is a plain `@triton.jit`. So Triton compiles new versions of it as row counts, sizes and buffer offsets change. The buffer offsets move with the row count ([fp4_indexer_schedule_hip.py#L265-L272](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/kernels/ops/attention/dsv4/fp4_indexer_schedule_hip.py#L265-L272)). AITER's `_prefill_cta_info_kernel`, which reads them too, has the same problem. With the shard, each rank schedules only its own rows, so one rank may compile while the others wait. In a short serving run, one rank compiled alone for 1.6 s. P99 TTFT at that point was 1,564 ms, against 784 ms without the shard. Fix: mark the per-call values `do_not_specialize` and the buffer pointers `do_not_specialize_on_alignment`, compile all 9 `BLOCK_T` versions on the first prefill, and align the buffers to 16 bytes. With the fix, no schedule kernel compiled inside the 14 measured points above. The fix also helps without the shard. We'll open it as a separate PR and link it here.

**4. Shard only when the context is long enough.** The gate checks only the row count (512 rows, [deepseek_v4_backend.py#L1086](https://github.com/sgl-project/sglang/blob/6510af844da5cb27b68475721329f5fa1cb0494c/python/sglang/srt/layers/attention/deepseek_v4_backend.py#L1086)). A row at position p sees `(p + 1) // ratio` compressed KV positions. The work the shard saves grows with those positions, while a sharded call costs at least about 0.6-0.8 ms even at short context. At TP4, sharding a 16,384-row call gives 0.57-0.77x (slower) when its rows see 4,096 positions on average, 1.01-1.23x at 12,288 and 2.04-2.20x at 28,672. TP2 needs more context: 0.65x at 12,288 and 1.24x at 28,672. Fix: shard only when the rows see at least 12,288 positions on average at TP4 and above, and 24,576 below TP4. All ranks compute this from the same CPU lists, so they agree. We did not measure TP8.

**5. Add a registered test.** The PR has no unit test yet. Ours, `test/registered/attention/unittests/dsv4/test_dsv41_hip_indexer_tp_shard.py` (1 GPU), runs TP2, TP3 and TP4 in one process on the real kernels. It checks every rank against the unsharded path, including padded rows and a batch with an empty request. Rows compare as sets, because top-k returns them in no fixed order and ties can go either way. It passes with the changes above (9 tests, 99 subtests). The empty-request case needs no code change; it only fills a test gap.
