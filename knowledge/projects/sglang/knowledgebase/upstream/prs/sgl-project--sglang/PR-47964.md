## Motivation

`CustomAllReduceV2` (the JIT custom all-reduce, "carv2") only runs on NVIDIA today. On AMD the custom all-reduce is AITER's (or the legacy AOT one), so ROCm gets neither carv2's Lamport push algorithms nor the push/pull communicator planes the fused collectives are built on.

The push algorithms matter most for decode-sized all-reduces: on 8x MI350X, carv2 `1shot_push` is 20-37% faster than AITER at 4-64 KB, and carv2 matches or beats AITER up to 4 MB (table below).

This PR makes carv2 build and run correctly on ROCm (gfx950) and tunes its launch geometry for MI350X. It does **not** change ROCm dispatch: `dispatch_custom_allreduce` still selects AITER on AMD, so serving behavior is unchanged until a follow-up enables v2 there with tuned thresholds. CUDA behavior is unchanged.

## Modifications

Two commits: the ROCm port, then the MI350X block/thread tuning.

**Symmetric workspace over HIP VMM + POSIX fds** (`srt/utils/hip_vmm_utils.py`, new)
- `HipSymmetricBuffer`: one `hipMemCreate` allocation per rank (`hipMemAllocationTypeUncached`, POSIX-fd handle type), exported as an fd, exchanged with the existing `exchange_posix_fds` (`SCM_RIGHTS`), imported and mapped into every peer, and exposed as per-rank uint8 tensors on the local device. It replaces torch symmetric memory on ROCm and needs no FABRIC handle and no multicast.
- Chunked fallback: some amdgpu/KFD drivers reject a VA-less VRAM allocation whose `[0, size)` overlaps an SVM range, which RCCL init can leave in Python's low brk heap (dmesg: `Address: 0x0 already allocated by SVM`); every later large allocation then fails as out of memory with the GPU nearly empty. On that failure the buffer is built from smaller handles mapped back to back, and the handled error is cleared from `hipGetLastError` so torch does not report it later.
- All ranks agree on allocation success before the fd exchange, so a failure raises everywhere instead of hanging peers.

**JIT kernels under hipcc** (`ptx.cuh`, `custom_all_reduce.cuh`, `utils.cuh`)
- HIP implementations of the `ptx::` vocabulary behind `#ifdef USE_ROCM` (the CUDA PTX is untouched): system-scope `__builtin_amdgcn_global_{load,store}_b128` for peer-visible 16B accesses, `__hip_atomic_*` for flag traffic, `__builtin_amdgcn_fence` for fences, and traps for multimem (no multicast on ROCm).
- The local Lamport poll uses agent scope (`sc1`). The uncached workspace is still L2-cached by its owner, with peer writes over XGMI invalidating the line by probe. A single-thread signal fence keeps the poll in the loop: without it LLVM treats the b128 builtin as a pure read and deletes the spin loop.
- `2shot_pull`: every wave issues a system-scope release before the block barrier. On gfx950 `s_barrier` does not drain a wave's outstanding stores and the signalling thread's release only covers its own wave; without this, graph replays rarely read stale reduced shards (1 bad replay in 200 at TP6).
- `utils.cuh`: add the missing `cudaMemcpyDeviceToDevice` / `cudaGetDevice` HIP aliases.

**`CustomAllReduceV2` on ROCm** (`custom_all_reduce_v2.py`, `configs/custom_all_reduce_v2.py`)
- `_allocate_symmetric_memory` returns `(owner, per-rank views, multicast VA)` and uses `HipSymmetricBuffer` on ROCm; `has_multicast` is False there.
- No graph zero-copy input registration on ROCm (the 2-shot graph path would store into peers' cached input buffers, which XGMI does not keep coherent); captured all-reduces stage through the workspace. `IPCManager` is only built when graph registration can happen.
- ROCm gets its own tuning table instead of falling into the SM90 table because gfx950 reports capability 9.5.
- Gate: on ROCm, `can_use_custom_all_reduce_v2` disables v2 with a warning when the loaded HIP runtime (`hipRuntimeGetVersion` on the `libamdhip64` torch loaded) is older than `MIN_HIP_VERSION = (7, 2)`, the oldest validated. ROCm 10.x ships HIP 7.16+.

**MI350X launch geometry** (second commit). Swept grid size x threads per block x message size at TP2/4/6/8, two runs per point (median run-to-run spread 1.3%):
- `num_pull_blocks = 32` in the ROCm table instead of one block per CU. Each pull block runs its own cross-GPU barrier, so 256 blocks spend most of a pull all-reduce on flag traffic; 32 blocks make `2shot_pull` 39-65% and `1shot_pull` 35-51% (from 1 MB) faster at TP8, and are within a few % of the best grid at TP2/4/6. The existing thread rule stays within ~3% of the best block size at this grid.
- `1shot_push` launches 1024 threads per block from 128 KB on ROCm (TP8 -7 to -11% at 128-256 KB, -8% at 1 MB; TP4/6 -4 to -8%; neutral below 128 KB).
- The push grid stays at one block per CU: `2shot_push`, which covers the mid range, is best or within ~2% there at every world size, and the push grid is bound to the counter array.
- Size thresholds are unchanged (follow-up).

**Tests**
- `test_custom_all_reduce_v2_capability.py`: the HIP runtime gate (7.0/7.1 rejected before topology checks, 7.2/7.17 admitted).
- `test_custom_all_reduce.py`: graph capture uses `capture_error_mode="thread_local"`; the reference NCCL group's watchdog thread queries events during capture, which fails under global capture mode on ROCm.
