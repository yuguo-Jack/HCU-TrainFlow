# [PD] Add Prefill-to-Prefill KV transfer over Mooncake

[Upstream PR](https://github.com/sgl-project/sglang/pull/32478) · state: closed · merged: False

## Original PR description

## Summary

This PR adds an opt-in Prefill-to-Prefill KV transfer path for PD-disaggregated SGLang deployments.

When cache-aware routing moves a request away from the Prefill worker that owns its prefix, the target Prefill can pull page-aligned KV (and supported model state) directly from the source through Mooncake instead of recomputing the whole prefix.

The transfer path is disabled by default and requires `--enable-prefill-p2p-kv-transfer` on participating Prefill workers.

## Design

- Adds a Prefill-to-Prefill control endpoint and OpenAI request-header integration.
- Reuses Mooncake sender/receiver bootstrap rather than introducing a second data plane.
- Supports identical model/KV layouts, including identical TP, PP, and attention-CP topology.
- Uses a stable layout fingerprint to reject unsafe model, dtype, page, or state-layout mismatches.
- Advances Mooncake transfers through a Scheduler-owned pending state machine:
  - `RESERVED -> WAIT_SOURCE -> TRANSFERRING -> CONSENSUS -> COMMIT/FAILED`
  - the peer HTTP request runs off the Scheduler thread;
  - sender/receiver transport is progressed with one nonblocking `poll()` per Scheduler iteration;
  - model-parallel consensus uses ordered asynchronous collectives.
- Keeps reserved KV outside the radix cache until every rank succeeds.
- Falls back to local recomputation on discovery, allocation, transfer, or consensus failure.
- Quarantines target KV after an indeterminate transport timeout instead of risking late writes into reused slots.
- Adds allocator ownership/accounting checks and fail-stop handling for cache-integrity violations.

The first implementation deliberately permits one in-flight P2P transfer per worker to preserve collective ordering.

## Performance

Validated on an isolated 3-worker PD stack on RTX PRO 5000:

- 2 Prefill workers, 1 Decode worker, TP1
- Mooncake TCP + HiCache
- 15 clients / 15 max parallel
- request rate 1.5
- 10K initial prompt, 3K sub-question, 200 output tokens, 5 rounds
- 75/75 successful requests in both runs

| Metric | Synchronous reference | Pending-state implementation | Change |
|---|---:|---:|---:|
| Average TTFT | 1.72 s | 1.03 s | -40.1% |
| P90 TTFT | 4.37 s | 2.06 s | -52.9% |
| Average E2E latency | 2.31 s | 1.77 s | -23.4% |
| P90 E2E latency | 4.77 s | 2.79 s | -41.5% |
| Input throughput | 21,696.81 tok/s | 23,730.70 tok/s | +9.4% |
| Request throughput | 1.26 req/s | 1.38 req/s | +9.5% |

The pending-state run injected 12 remote-KV hints and completed 10 physical target transfers; the other hinted prefixes were already present on the selected target. There were zero P2P fallbacks, cache-integrity errors, or quarantined allocations. A separate 20,315-token smoke test succeeded in both Prefill directions.

This is a focused validation, not a claim of universal performance improvement. Results will vary with topology, transport, prefix length, and load.

## Tests

```text
69 passed, 1 skipped, 4 subtests passed
```

Covered areas include:

- nonblocking source and target Scheduler progress;
- deferred control response delivery;
- bidirectional pair serialization;
- TP/PP/CP rank mapping and consensus;
- model/KV layout fingerprint validation;
- KV and Mamba ownership/duplicate settlement;
- HiCache source load-back;
- failure cleanup and allocator accounting;
- control headers/endpoints and CLI validation.

## Limitations

- Opt-in and disabled by default.
- Mooncake backend only.
- Source and target must use identical model/KV and distributed layouts.
- One in-flight transfer per worker in this first version.
- A source prefix that exists only in HiCache L2 may still require synchronous load-back before Mooncake can read it.
