# [Feat] sgl-router: Add --decode-dispatch-limit to pick decode DP ranks near KV arrival

[Upstream PR](https://github.com/sgl-project/sglang/pull/44402) · state: closed · merged: True

## Original PR description

## Motivation

With `--dp-aware` in PD mode, the router picks a request's decode DP rank on arrival, but decode only starts it after prefill has queued, computed and sent its KV. With long prefill queues, 44–57% of decode's requests are still waiting for KV (#43511), so `least_in_flight` evens out requests per rank while the running batches, which every DP-attention decode step waits on, stay uneven. Picking the rank shortly before the KV lands avoids that.

## Modifications

- `--decode-dispatch-limit N` (PD only; unset keeps today's behaviour): prefill still gets every request on arrival, but at most N per prefill DP rank go on to decode before their first token. The rest wait at the router in arrival order and get their decode rank when sent. A slot frees on decode's first token or when prefill answers. A request that ends first (decode failure, expiry, client gone) frees its slot at once; one whose prefill fails stops waiting.
- Needs prefill `--optimistic-prefill-attempts` above 0, so prefill can start a request before its decode connects.
- A request that expires or loses its client while waiting has its prefill aborted (`/abort_request`). Requests without a router-minted rid (caller-set `rid`, fan-out) skip the wait.
- Native gRPC calls share HTTP's dispatch, so they wait for the same slots, and a streaming call frees its slot on decode's first reply. Their prefill is aborted with `/abort_request` as well; it needs no key, since an engine refuses `--grpc-port` with `--api-key` or `--admin-api-key`.
- New `workers/decode_gate.rs`: one FIFO semaphore per (prefill worker, DP rank). REFERENCE.md: DP-rank routing, linked from the README.

## Testing

- New `dp_rank_routing::decode_dispatch_limit_gates_decode_per_prefill_rank`: with one slot, a second request on the same prefill rank reaches decode only after the first one's prefill answers (non-streaming) or its first token streams (streaming).
- New `dp_rank_routing::a_request_expiring_before_decode_aborts_its_prefill`: the expiring request's prefill was already sent, receives `/abort_request` for its rid, and decode never sees the request.
- New `dp_rank_routing::a_failed_decode_frees_its_slot`: after a decode fails, the next request on that prefill rank does not wait for the first one's prefill.
- New `grpc_routing::decode_dispatch_limit_gates_decode_as_over_http`: the first test's two cases over native gRPC `ChatComplete`.
- Each test fails with its part of the change reverted (no gate, no abort, no release on the first token).
- Passing: `cargo +nightly fmt --all -- --check`, `cargo check`, `cargo clippy -- -D warnings`, `cargo test --release --workspace -- --skip parity_matrix`.

## Benchmark (MI355X)

DeepSeek-V4-Pro, 1 prefill + 1 decode engine with 8 DP-attention ranks each, AgentX trace replay with AIPerf (multi-turn agentic sessions, 96% prefix-cache hit), 1 h per concurrency. Router `--policy sticky --routing-key-header X-SMG-Routing-Key --decode-policy power_of_two --dp-aware` (decode ranks by `least_in_flight`), built at 1e86143bf0: `--decode-dispatch-limit 8` with this change, unset without it (the `least_in_flight` runs of #43511). Both arms used the same recipe, including prefill `--optimistic-prefill-attempts 2` and `--load-balance-method follow_bootstrap_room` (see #44072), and neither had request errors. Measured at 384 and 512, where prefill queues are long (12 and 28 requests per prefill rank).

Unset → `--decode-dispatch-limit 8`, AIPerf:

|---|---|---|---|---|---|---|

| 512 | 589.9 → 601.7 (+2.0%) | 19.16 → 20.33 | 61.18 → 60.29 | 21.81 → 20.17 (-7.5%) | 24.16 → 23.13 (-4.3%) | 47.84 → 47.59 |

|---|---|---|---|---|---|---|
| 384 | 19.08 → 18.73 (-1.8%) | 25.8 → 24.6 | 0.13 → 0.10 | 171 → 171 | 136 → 52 | 14.7 → 5.7 |

Prefill engine, same hour:

| conc | queue per rank | new tokens per forward | new tokens/s | chunked prefills paused (optimistic yield) |
|---|---|---|---|---|
| 384 | 12.8 → 12.3 | 7237 → 7210 | 44.5k → 45.2k | 3 → 282 (0.5% of requests) |
| 512 | 28.1 → 28.6 | 7776 → 7919 | 48.5k → 49.1k | 2 → 391 (0.7% of requests) |

- Decode now receives a request about 6 s before its first token instead of 15–27 s, so what it holds waiting on KV drops 62–78%, and the running batches even out: CV -23% / -32%, and the busiest rank's batch -4% / -10% with the 8-rank total the same or lower. TPOT p50 -3.0% / -7.5%, engine TPOT -1.8% / -4.3%.
- Prefill is not held back: its queue, forward size and throughput match the unset run. The optimistic yields are chunked prefills, about 0.5–0.7% of requests, that paused because their decode had not connected yet while a request with decode connected was waiting; each saved its computed chunks to the radix cache and later resumed from them, and 5 per run paused a second time and then waited for decode. New tokens computed per prefilled request stayed the same (3120 → 3128 at 384, 3160 → 3158 at 512), so the pauses cost no measurable recompute.
- At 512, TTFT p50 rose 1.2 s with prefill queue time (p50 15.3 → 16.3 s), while decode's part of TTFT fell: with concurrency fixed and prefill the bottleneck, users who finish decoding sooner return to the prefill queue sooner. TTFT mean +1.9%, p90 -1.5%, E2E mean -0.5%.
- Holding requests before prefill instead (the same 8 slots per prefill rank) evened decode out about as well (running CV 0.11), but drained prefill's queue to 2.5–3 requests per rank; prefill forwards then carried 6–8% fewer new tokens, output throughput fell 2.3% / 6.8%, and TTFT p50 rose 38% / 46%. That is why this change holds back only decode.

### Per-rank decode load

Same two runs, computed as in #43511: each decode rank's `Decode batch` log lines sampled every second; outstanding = running + waiting on KV transfer (prealloc, retracted and queue stayed 0). Stdevs are across the 8 ranks, p50 over the hour; busiest ÷ mean running excludes the first 5 min of ramp-up. With the limit, requests waiting for a decode slot are at the router, not in decode's outstanding count. Unset → `--decode-dispatch-limit 8`:

| conc | outstanding stdev (req) | waiting-on-KV stdev (req) | running stdev (req) | waiting ÷ outstanding | busiest ÷ mean running, p50 / p90 |
|---|---|---|---|---|---|
| 384 | 0.71 → 0.87 | 2.71 → 2.00 | 2.74 → 2.12 | 44% → 23% | 1.20 / 1.32 → 1.14 / 1.23 |
| 512 | 0.78 → 0.93 | 3.38 → 2.15 | 3.35 → 2.28 | 57% → 23% | 1.21 / 1.36 → 1.13 / 1.22 |

![Per-rank outstanding, waiting-on-KV and running requests at concurrency 512, unset vs --decode-dispatch-limit 8](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-sgl-router/sglr-decode-dispatch-c512-per-rank.png)

![Busiest ÷ mean running, waiting on KV and prefill queue over the hour at concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-sgl-router/sglr-decode-dispatch-c512-over-the-hour.png)

- Under `least_in_flight` alone, the running spread followed the waiting spread (#43511). With decode getting requests close to KV arrival, waiting is 23% of decode's requests at both concurrencies, its spread drops by a quarter to a third, and the running spread drops with it (2.74 → 2.12 and 3.35 → 2.28 requests), even though outstanding requests are slightly less even (0.87–0.93 vs 0.71–0.78 requests).
- The lower busiest ÷ mean holds through the hour, while the prefill queue follows the same course in both runs. No rank stays hot: each rank's mean running batch is within ±1.6% of the 8-rank mean (±2.2–3.1% unset).
