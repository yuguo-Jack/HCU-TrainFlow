## Motivation

Prefill CP for DeepSeek-V4.1 already works on CUDA, but on AMD it's still blocked. 
Long prompts (e.g. 100k) are slow to prefill on plain TP8, this PR turns it on for AMD HIP platform, validated on gfx950.

## Modifications

- `deepseek_v4_hook.py`: stop rejecting V4.1 for prefill CP on HIP, including with `--enable-decoder-swa-bounded-replay` (V4 is still rejected).
- `deepseek_v4_backend_hip_radix.py`:
  - Add a HIP `_forward_low_ratio_sources_cp` instead of previous CUDA version:
    - Compressor: all-gather the prompt and let every rank compress all tokens, so each rank has the full main KV and indexer K. The full extend reuses the same fused kernel as non-CP cases.
    - Indexer: only score this rank's rows.
  - `_low_ratio_index_topk`: drop the assert that rejected `rows_per_request` and pass it down to the HIP indexer.
  - Add `_first_rows`: on gfx950 `q_lora` can be an FP8 activation wrapper that can't be sliced with `[:n]`.
  - Bounded-replay tail under CP:
    - Reuse CUDA's `_late_layer_tail_cp_layout` to build the tail's own CP layout.
    - `init_forward_metadata_prefill` takes an optional `cp_metadata` for the tail: pad `swa_replay_start` and reindex rows with `local_index`.
    - `enter_late_layer_tail` / `exit_late_layer_tail` swap in and restore the CP metadata and DP buffer length, and cut candidate masks by each rank's local tail rows.
- `low_ratio_backend_hip.py`: pass `rows_per_request` into the HIP indexer so it knows how many local rows each request has.
- `deepseek_v4.py`: with HIP CP, put the tail outputs (including DSpark aux) back into the rank's full layout, because the CP runner gathers by that layout.
- `interleave.py`: on HIP, skip CP when a rank would get fewer than 16 tokens. aiter's group32 MXFP8 GEMM returns NaN for `wqkv_a` (N=1792, K=5120) at M=5~8. Left a TODO to drop this once the kernel is fixed.
- Remove the stale "V4.1 is rejected on HIP" case from `test_platform_prefill_cp_deprecation.py`.

- SAXEM1997 · comment · 2026-10-20T15:02:38Z · [source](https://github.com/sgl-project/sglang/pull/43465#issuecomment-6293977244)

**CUDA: prefill CP + decoder SWA bounded replay + DSpark crashes at the first large prefill (tail rows are not scattered back before the CP gather)**

We reproduced a failure on CUDA/SM90 with the combination enabled. The analysis points at the same tail-layout gap that the "Bounded-replay tail under CP" part of this PR closes on HIP.

**Setup**: DeepSeek-V4.1-Flash, 8×H20-3e (SM90), CUDA, sglang v0.5.22, `--tp 8 --ep 4 --enable-prefill-cp --cp-strategy interleave --enable-decoder-swa-bounded-replay --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --chunked-prefill-size 32768` (prefill CUDA graph disabled).

**Symptom**: the server boots, but the first 128K-token prefill kills the scheduler:

```
RuntimeError: Interleave CP gather received an unexpected local token count:
  rank=3, got=16, expected_at_least=4096, total=32768, cp_size=8
  File ".../srt/layers/cp/interleave.py", line 288, in _gather_interleaved_tensor
  File ".../srt/layers/cp/utils.py", line 246, in cp_gather_after_forward
  File ".../srt/model_executor/runner/eager_runner.py", line 405, in _execute_extend_cp
  File ".../srt/speculative/dspark_components/dspark_worker_v2.py", line 650, in _forward_prefill
```

**Analysis**
- With replay, the late layers run over each request's SWA window (128 tokens); after interleave sharding a rank owns 16 of them.
- In `DeepseekV4Model.forward`, the `_scatter_tail_rows(...)` call is guarded by `not capture_dspark`. With DSpark (`capture_dspark=True`), the model returns tail rows (and tail-row aux tensors) un-scattered.
- `eager_runner._execute_extend_cp` then gathers with the full-batch CP metadata (`per_rank_logical_token = 32768 / 8 = 4096`), and `interleave.py:288` raises.

**Launch-time guard gap**: `arg_groups/deepseek_v4_hook.py` only rejects `--enable-decoder-swa-bounded-replay` when `attn_dp_enabled`; a DP=1 pure-CP configuration passes the check and crashes at the first large prefill instead of being rejected at startup. The comment there already says "Attention TP/CP shards need a separate tail padding layout".

**Fix we validated**: in `deepseek_v4.py`, when `is_cp_active(forward_batch)` and a replay tail exists, scatter `hidden_states`, `pre_hc_head` and the DSpark aux tensors back into the rank's full (sharded) layout before the runner gathers (22 lines; non-tail rows zero-filled). With that:
- Cold TTFT 128K / 256K / 512K: **3.37 s / 6.86 s / 15.95 s**, vs 5.41 / 11.71 / 28.66 s for the same CP + DSpark config without replay.
- Greedy outputs on a 5-prompt set are token-identical to the non-CP production config with replay on.
- Decode replay (36 real sessions): c8 ITL p90 **86 ms vs 160 ms** (CP without replay), output throughput **259 vs 176 tok/s**.

Is this the same gap #43465 closes on HIP, and is a CUDA-side counterpart planned? Happy to send the 22-line patch if useful.
