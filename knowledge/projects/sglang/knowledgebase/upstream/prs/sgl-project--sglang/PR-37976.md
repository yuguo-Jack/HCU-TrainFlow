# [Feat] trace: propagate per-request context to mooncake store RPC for end-to-end request tracing

[Upstream PR](https://github.com/sgl-project/sglang/pull/37976) · state: closed · merged: True

## Original PR description

<!-- Thank you for your contribution! Please follow these guidelines to enhance your pull request. If anything is unclear, submit your PR and reach out to maintainers for assistance. Join our Slack community at https://slack.sglang.io to discuss further. -->

## Motivation


  HiCache's KV read/query/writeback paths issue Mooncake store RPCs (`batch_get*`, `batch_exists`, `batch_set*`, …), but those RPCs carry  no request identity. As a result, the Mooncake master cannot attribute a given storage I/O to a specific request, so the `request → store  RPC` trace link is broken and there is no end-to-end request tracing/atrribution on the store path.

  This PR injects a per-request context (`request_id`, plus optional `trace_id` / `span_id` / `parent_span_id`) and propagates it as a  `coro_rpc` attachment on store RPCs. The Mooncake master records it, closing the request→store-RPC trace link.

## Modifications

  Final state carries `request_id` inside `HiCacheStorageExtraInfo.extra_info` without changing any store method signature. 
  - **`mooncake_store.py` (+107/−6)** — `MooncakeBaseStore` gains request-context support:
    - `set_request_context` / `clear_request_context` / `request_context()` context manager, delegating to the underlying
    `MooncakeDistributedStore` Python bindings.
    - Helpers `_extra_info_request_id`, `_request_context_from_extra_info`, and a `_has_request_context_support` `cached_property` guard.
    - The context is held in Mooncake C++ thread-local `g_current_ctx` and attached out-of-band to subsequent store RPCs; it is cleared after
    each request to prevent cross-request interference.
    - `MooncakeStore`, `MooncakeEmbeddingStore`, and `MooncakeDirectLinker` inherit it via `MooncakeBaseStore`.

  - **`cache_controller.py` (+9/−3)** — carry `request_id` in `HiCacheStorageExtraInfo.extra_info` on KV read/query store-RPC paths:
    - `_page_transfer` (`batch_get_v1`, and its KV-derived sidecar `batch_get_v2`);
    - `_storage_hit_query` (`batch_exists`).

  - **`hybrid_cache_controller.py` (+6/−2)** — same `extra_info` propagation:
    - `_storage_hit_query` (`batch_exists` / `batch_exists_v2`) + non-KV sidecar `batch_get_v2`.

  - **Not changed** — store method signatures are untouched (no `request_id` param added; the store reads it from `extra_info`). Write path  (`batch_set*`, backed by `StorageOperation`) carries no `request_id` and is left unchanged; the embedding path has zero net diff.

  - **Backward compatible** — `_has_request_context_support` guards every call; against older Mooncake wheels (no `set_request_context`  binding) it is a no-op (no error, no behavior change).
  
Related mooncake pr: https://github.com/kvcache-ai/Mooncake/pull/3848
