# [Fix] scheduler: Keep PD decode non-idle while deferred KV releases are held

[Upstream PR](https://github.com/sgl-project/sglang/pull/44386) · state: closed · merged: True

## Original PR description

## Motivation

On PD decode, a failed or aborted transfer is held for deferred release (#35049, on by default). Its KV pages, request row, tree lock and metadata slot stay with it until every prefill rank acks that its writes drained, or until the timeout (30 s by default).

`Scheduler.is_fully_idle` never looks at these holds. Its decode branch checks the prealloc, retracted and transfer queues, but a held request has already left the transfer queue. So `flush_cache` runs while a hold is outstanding:

1. The flush clears the tree, the request pool and the allocator. The held pages go back to the free list.
2. When the hold resolves, `_do_release` → `release_kv_cache` frees the same pages again.
3. The allocator now has every one of those pages twice. Two later requests get the same pages and overwrite each other's KV.
4. With the decode radix cache on, the held `req.lock` points at a node of the old tree.
5. If the prefill write was still landing, which is always the case for a room #43719 poisons, it lands on pages that already have a new owner.

RL rollouts hit this without any unusual timing. The flow is abort, `pause_generation`, then `update_weights(flush_cache=True)`. While paused, the decode loop skips `process_decode_queue`, so nothing resolves the holds before the flush.

The idle leak check already knew about these holds and skipped itself while they were pending. Only the flush gate was missing.

## Modifications

- In `is_fully_idle`, the decode branch now requires `has_pending_deferred_releases()` to be False.

The same gate also covers attach / detach of a storage backend and `release_memory_occupation`. The last of these currently drops held entries and pauses KV memory while a prefill write may still be landing.

## Tests

- No new unit test. The existing retracted-queue idle test stubs the transfer queue with a `SimpleNamespace`, which now also needs `has_pending_deferred_releases`.
- `test_decode_queue_cleanup.py` passes (14 tests).
- Allocator-level repro on an H200, with the real `is_fully_idle`, the real `DecodeTransferQueue` defer / resolve and a real allocator. On main, a flush followed by the deferred release raised available pages above the pool total (272 of 256), and one alloc returned 16 pages twice. With this change the flush is refused, and the pool returns to 256 with no duplicates.

Related: #36869 rewrites `is_fully_idle` as `not_idle_reasons()`. When it rebases, this condition becomes one more `require_empty` entry.

Thanks for fixing this. I reproduced the same race on CPU with a script that drives the real `DecodeTransferQueue`, allocators and `flush_cache` (one aborted transfer leaves a deferred release holding two pages), and it confirms the fix:

```
before #44386  is_fully_idle()=True   flush_cache() -> True   the held pages go to the next request and end up freed twice (10 pages free in an 8-page pool)
after #44386   is_fully_idle()=False  flush_cache() -> False  nothing is freed twice, and the PD role switch is refused as well
```

The role switch goes through the same check (`role_switch.py:73`). If a regression test would help, I can send one that aborts a transfer through the real `DecodeTransferQueue` and checks that `flush_cache` and the role switch are refused until the hold resolves.
