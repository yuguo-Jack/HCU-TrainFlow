# [Fix] [Intel] attention: Fall back to intel_xpu for deterministic inference

[Upstream PR](https://github.com/sgl-project/sglang/pull/45533) · state: closed · merged: False

## Original PR description

## Motivation

Deterministic inference picks a CUDA-only attention backend on Intel XPU. With no `--attention-backend`, `_deterministic_attention_backend` falls through the SM100/SM120 check to `fa3`, whose factory asserts `SM>=80 and SM<=90`. `get_device_capability()` returns `(None, None)` on XPU, so the assert fires and the server dies during startup:

```
Attention backend not specified. Falling back to 'fa3' for deterministic inference.
...
AssertionError: FlashAttention v3 Backend requires SM>=80 and SM<=90.
```

Every deterministic run on XPU that does not name a backend is affected, including a plain `--enable-deterministic-inference` launch. `intel_xpu` is already in `DETERMINISTIC_ATTENTION_BACKEND_CHOICES`; nothing selected it.

## Modifications

- `arg_groups/overrides.py`: resolve the deterministic fallback to `intel_xpu` on XPU. The branch only runs when `attention_backend is None`, so an explicitly requested backend is untouched.
- `test/registered/unit/test_model_overrides.py`: cover both directions - the XPU fallback resolves to an XPU-capable backend, and an explicit backend is left alone. The first case fails on pre-fix code (verified), the second passes before and after.

## Accuracy Tests

Intel Arc Pro B60, `sgl-kernel-xpu` built from source.

`test/registered/cuda_graph/breakable/test_bcg_with_lora.py` - unmodified by this PR, and the test that surfaced the bug, since it enables deterministic inference without naming a backend. Before: every case errored at server launch on the fa3 assert. After: **12/12 pass** (`TestBCGLoRACsgmv` 6/6, `TestBCGLoRATriton` 6/6, ~2.5 min per class on one card).

Logs confirm the fix took effect and the test is not passing vacuously: each of the four servers logs `Falling back to 'intel_xpu' for deterministic inference`, and each class records 10 prefill batches served by the breakable CUDA graph (`cuda graph: True`), so the graph-vs-eager prompt-logprob comparison really ran through the graph path.

New unit cases: 2 passed; 1 of the 2 fails when the fix is reverted.

## Speed Tests and Profiling

Not applicable - startup-path config resolution only, no effect on steady-state inference.
