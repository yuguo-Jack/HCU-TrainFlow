# [Fix] tokenizer_manager: Leave room for max_new_tokens and reserved tokens when auto-truncating

[Upstream PR](https://github.com/sgl-project/sglang/pull/48063) · state: open · merged: False

## Original PR description

Closes #21136.

## Motivation

With `--allow-auto-truncate`, `_validate_one_request` cuts an over-long input to exactly `context_len`. The total-token check right below then sees `input + max_new_tokens > context_len` and clamps `max_new_tokens` to 0, so the request returns no output, the opposite of what enabling auto-truncate asks for.

The same branch also drops `num_reserved_tokens` (the output slots EAGLE reserves) from `input_token_num` after truncating, although the check above it had counted them. With EAGLE a truncated request therefore ends `num_reserved_tokens` past the context.

## Modifications

- Truncate to `context_len - max_new_tokens - num_reserved_tokens`, at least one token, and keep the reserved slots in `input_token_num` so both checks agree.
- Read `max_new_tokens` before the input-length check; the later total-token check is unchanged.
- Add `test_tokenizer_manager_auto_truncate.py`: the truncated input leaves room for `max_new_tokens` (with and without reserved slots), keeps the reserved slots in budget when `max_new_tokens` is absent, and keeps one input token when `max_new_tokens` exceeds the context.

Not changed: a request without `max_new_tokens` is truncated only below the reserved slots, since reserving room for the 128 default would change how much of a long prompt survives. Raise it if you want that.

Checked on a Linux host: the 4 cases pass on this branch and all 4 fail with `main`'s `tokenizer_manager.py` (e.g. `AssertionError: 100 != 90`).

The room-for-output rule only runs when input_token_num >= context_len, so prompts just under the limit still get their output clamped away. With context_len=100 and max_new_tokens=50, a 99-token prompt keeps all 99 tokens and gets max_new_tokens clamped to 1, while a 100-token prompt is cut to 50 and keeps all 50. Should the truncation also kick in when input_token_num + max_new_tokens > context_len?


- bzantium · comment · 2026-11-04T16:17:11Z · [source](https://github.com/sgl-project/sglang/pull/48063#discussion_r4470104948)

File: `python/sglang/srt/managers/tokenizer_manager.py` · line 1401

Good catch on the discontinuity — that's real. I deliberately kept the trigger at `input >= context_len` though: when the prompt already overflows, we have to drop tokens anyway, so reserving room for output costs nothing extra. When the prompt fits, truncating it would silently change results for existing users, and it would hit clients that send `max_tokens` close to the context length hard (e.g. 128k context with `max_tokens=127000` would cut a 2k prompt down to 1k). So for prompts that fit, I'd keep the existing behavior: keep the prompt intact and clamp `max_new_tokens`. I added a test pinning that boundary case (`test_prompt_that_fits_is_kept_and_max_new_tokens_clamped`). Happy to extend the trigger if maintainers prefer prioritizing output in all cases.
