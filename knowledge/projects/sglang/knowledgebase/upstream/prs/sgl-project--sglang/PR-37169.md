# [Feat] cuda-graph: Capture allocator history to investigate memory corruption

[Upstream PR](https://github.com/sgl-project/sglang/pull/37169) · state: open · merged: False

## Original PR description

## Motivation

A stale CUDA-graph pointer can overwrite a tensor owned by unrelated code. The later failure identifies the corrupted tensor, not the allocation that the graph originally captured, making the cause difficult to trace.

This PR adds an opt-in way to retain allocator history and save snapshots after graph capture. Investigators can map an affected address to allocation stacks. It is a diagnostic aid, not a memory-corruption fix; #37168 addresses specific captured-tensor lifetime defects.

## Modifications

Set `SGLANG_MEM_FORENSICS_DIR` to start PyTorch allocation-history recording after distributed initialization and save a `ready` snapshot after all scheduler captures complete. Additional tags can be requested by failure handlers. Snapshots have unique rank/PID/timestamp names and use atomic writes; a failed write can be retried.

With `--enable-profile-cuda-graph` and forensics enabled, the capture profiler keeps the forensics recorder configuration instead of switching it to the PyTorch defaults and stopping it, so the history recorded before capture is kept in order and the `ready` snapshot is written; its own capture snapshot then uses the forensics configuration. Without forensics, or once the directory is unset, the capture profiler starts and stops recording as before. If another profiler (for example the torch profiler's `MEM` activity) has stopped recording, which discards the recorded events, the snapshot is still written because live blocks keep their allocation stacks; recording is re-armed with the original configuration and the tag stays open so a later request for it carries history again. The start and dump helpers log failures instead of raising, and do not call CUDA while the directory is unset, including when it is unset after recording started.

## Accuracy Tests

15 CPU tests passed, covering disabled behavior, recorder initialization, snapshot writes, retries, re-arming, an unset directory after start, the capture profiler hooks with and without forensics ownership, and the startup sequence in which the capture profiler (or another profiler) records and stops before the scheduler's single `ready` request, using a recorder model that reproduces PyTorch's ring-buffer capacity and ordering behavior. CUDA snapshot recording has not been tested.

## Speed Tests and Profiling

Disabled by default. Recording allocation stacks consumes history storage; overhead was not measured.
