# [Feat] kv-indexer: Add a shared Valkey placement backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/42447) · state: open · merged: False

## Original PR description

Reopened from #39785. GitHub closed that PR on 2 October when the fork it came from was deleted; its review history is still there.

## Motivation

`sgl-kv-indexer` has one storage backend, an in-process map. That makes the Indexer a single point of failure for cache-aware routing: a restart or deploy blanks the placement index, and hot prefixes that are already resident on workers (system prompts, tool schemas) are never re-emitted, so a fresh Indexer never learns them until they churn. Two Indexer servers cannot share state, so the README's operational contract is "run exactly one".

This adds a second `KvIndexerBackend` over a Valkey (or Redis) keyspace. The server holds no state, so it can be restarted or run active-active over one keyspace behind the Router.

## Modifications

- `sgl-kv-indexer/src/valkey_backend.rs`: `ValkeyKvIndexerBackend` and `ValkeyConfig`. Standalone and cluster mode (cluster requires a hash-tagged prefix so pipelines stay in one slot; the default `{sgl-kv-indexer}:` is one). Data model, consistency and the cycle-detection argument are in the module docs.
- `src/bin/kv-indexer-server.rs`: `KV_INDEXER_BACKEND=memory|valkey`, `KV_INDEXER_VALKEY_URL`, `KV_INDEXER_VALKEY_KEY_PREFIX`, `KV_INDEXER_VALKEY_CLUSTER`. Default stays `memory`; nothing changes for existing deployments.
- `tests/valkey_parity.rs`: the same scenario streams applied to both backends with every response compared, including a 3-seed randomized stream of 300 batches. Spawns `valkey-server` from `PATH` on a unix socket or uses `KV_INDEXER_TEST_VALKEY_URL`; skips cleanly when neither exists, so CI without Valkey is unaffected.
- README: backend selection, Valkey section, operational contract updated.
- New dependency: `redis = 1` with `tokio-comp`, `connection-manager`, `cluster-async`, `tokio-rustls-comp` + `tls-rustls-webpki-roots` (so `valkeys://` works on the same rustls stack as the router's reqwest), and `script` (default features off).
- Client hygiene: per-command response timeout (`KV_INDEXER_VALKEY_REQUEST_TIMEOUT_MS`, default 1000) and connect timeout (`KV_INDEXER_VALKEY_CONNECT_TIMEOUT_MS`, default 5000); transport errors map to `UNAVAILABLE`, everything else to `INTERNAL`; the prune script is loaded once and run by `EVALSHA` with every key it touches declared in `KEYS`.
- Also fixes a bug in the in-memory backend that the parity fuzz exposed: `recompute_worker_subtrees` seeded every dirty block and skipped visited ones, so a batch that revoked a child before its parent (any `CLEAR_ALL_AT_TIER`, whose order comes from a `HashSet`) could leave the child marked prefix-complete under an incomplete parent. The fast path then returned a prefix the worker could not serve (7 blocks where the rule engine said 4). Fix: seed the recompute only from dirty blocks with no dirty ancestor so every pass is top-down; deterministic regression test `prefix_fast_path_recomputes_children_after_parents_on_revoke` fails on the old code and passes on the fix.

Semantics are field for field those of the in-memory backend: prefix answers come from the shared rule engine in `service.rs` over the same placement inputs; a rejected batch leaves the keyspace untouched; a hit count is dropped at the revoke that empties a block even when a later action in the same batch re-reports it; empty block records are pruned upward as children disappear. Cycle detection avoids a network graph walk by storing each block's chain root: a batch can only attach a block whose parent was unknown, so a cycle through existing state means a planned parent's root is itself in the batch.

Measured on two SGLang workers behind `sgl-router --cache-prefix-provider indexer`, with the Indexer server killed and restarted one second later under load (a rolling deploy). 8 tenants with ~7.8k-token system prompts, working set above one worker's KV pool: the in-memory Indexer took the workers' prefix hit ratio from 0.99 to 0.70 in the restart window, TTFT p50 from 56 ms to 492 ms, p90 to 1,056 ms, throughput in the window to 39 requests from about 130, and the router made 161 decisions without a cache candidate. The Valkey-backed Indexer held 0.90, p50 63 ms, 93 requests in the window, 25 blind decisions, all inside the one-second outage. The index for that fleet was 2,461 keys and 1.65 MB in Valkey.

## Benchmarking and Profiling

Not a hot-path change for the Router. Indexer query latency over a local unix socket stayed under the Router's 100 ms deadline throughout the runs above; no timeouts or fallbacks were recorded outside the outage window.

## Limits

- An accepted batch is pipelined, not one transaction, so a concurrent query can see it partly applied. REPORT can only under-report a prefix; a REVOKE is visible one round trip later.
- Cluster mode keeps every key in one slot via the hash-tagged prefix, since pipelines cannot cross slots. The index is about a hundred bytes per placement, so this is a capacity fit; cluster buys failover, not sharding.
- No worker liveness TTL, same as the in-memory backend: a dead worker keeps its placements until something clears them. That needs a bridge heartbeat and is the follow-up in #42449.
- The parity tests skip with a message when no `valkey-server` is on PATH, so this PR does not change what the CI matrix executes. #42449 makes the router job install one.
