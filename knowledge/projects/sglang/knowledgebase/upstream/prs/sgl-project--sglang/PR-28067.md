# [scheduler] Keep stop-the-world GC pauses off the batch critical path

[Upstream PR](https://github.com/sgl-project/sglang/pull/28067) · state: closed · merged: False

## Original PR description

## Motivation

CPython's automatic generation-2 garbage collection is a stop-the-world pause that costs O(live heap) and fires at arbitrary allocation sites. In a tensor-parallel deployment, a pause in **one** scheduler rank stalls **all** ranks: the paused rank stops launching kernels while the peer GPUs spin at 100% inside a collective that needs its next launch. If anything in the process slowly accumulates live objects (we hit a leaking dependency — flashinfer#2139-family behavior in the fused-MoE entry points), pause duration grows with uptime until it exceeds the 20s `/health_generate` window; the liveness probe then kills the pod mid-pause. The resulting signature is the well-known silent hang report (`Health check failed. Server couldn't get a response from detokenizer...`, e.g. #22511) with no traceback — even though the process would have recovered on its own.

Measured on 8×B300 TP=8 serving [`deepseek-ai/DeepSeek-V3.1-Terminus`](https://huggingface.co/deepseek-ai/DeepSeek-V3.1-Terminus)-class models with such a leak:

- scheduler heap reached **74.8M tracked Python objects** in 6.5h;
- a single gen-2 `gc.collect()` on the live rank measured **41.17s and freed 0 objects** (pure traversal of live objects);
- stall duration grew linearly with uptime: 7s @1h → 23s @3.5h → 46s @6.5h;
- py-spy at stall time shows the victim rank GIL-held mid-collection at an arbitrary allocation site, victim rotating across ranks, while the other seven GPUs spin in a collective;
- pods were recycled several times per day by the liveness probe.

This PR makes the scheduler structurally robust to this failure class: GC pauses happen only when they cannot stall in-flight batches, regardless of which dependency grows the heap.

## Modifications

New `python/sglang/srt/managers/scheduler_gc_manager.py` (`SchedulerGCManager`), constructed in `Scheduler.__init__` and hooked into the idle housekeeping path (`on_idle`). Three env knobs registered in `environ.py`. Behavior (default on):

1. **Defer automatic gen-2 collections**: raise the gen-2 threshold (`SGLANG_SCHEDULER_GC_GEN2_THRESHOLD`, default 10000). Deferred, not disabled — automatic gen-2 remains as a fallback under never-idle load; gen-0/gen-1 collection is untouched and keeps handling short-lived cycles.
2. **One-time startup-heap freeze**: on the first fully-idle tick (i.e. right after warmup — weights loaded, CUDA graphs captured, autotuning done), run one full collect, then `gc.freeze()` the startup heap into the permanent generation so no future collection ever traverses it again (measured: ~954k objects frozen in ~1s, once).
3. **Collect only at idle**: periodic `gc.collect()` from `on_idle()` (`SGLANG_SCHEDULER_IDLE_GC_INTERVAL`, default 300s), i.e. only when `is_fully_idle()` — exactly when a pause cannot stall in-flight work, and (since TP ranks run the same batches) when the peer ranks are idle too. This reclaims reference cycles, e.g. evicted radix-tree nodes, whose parent↔child links refcounting alone cannot free.
4. **Leak canary**: an idle collect taking >0.1s logs its duration — a growing value is an hours-early warning that something in the process is accumulating tracked objects.
5. **Deliberately no periodic re-freeze**: an object frozen while alive is never collected if it later becomes cyclic garbage, so a naive "freeze every N minutes" policy would convert ordinary radix-cache churn into a true permanent leak. Freezing only the startup heap is safe because it lives for the process lifetime by construction.

Kill-switch: `SGLANG_ENABLE_SCHEDULER_GC_MANAGEMENT=0` restores stock behavior exactly (thresholds untouched, no freeze, no idle collects). The existing `/freeze_gc` endpoint is untouched and composes with this.

## Accuracy Tests

Not applicable — no kernel or model-forward changes; this only changes *when* Python GC runs in the scheduler process.

## Speed Tests and Profiling

8×B300, TP=8, public `deepseek-ai/DeepSeek-V3.1-Terminus` (fp8, default backend resolution: `attention_backend=trtllm_mla`, `moe_runner_backend=flashinfer_trtllm`), sustained multi-turn load (6 concurrent ~15k-token conversation streams + sparse single requests + mid-stream client aborts) with a 4s `/health_generate` probe:

- With this PR: **0 log-silence gaps ≥6s and 554/554 health probes OK** across the soak; gen-2 collections occurred only at idle; unfrozen working set stayed at ~15–47k objects; `Initial post-warmup GC freeze: collected 0, froze 954,447 objects (0.42s)` on all 8 ranks.
- Causality control on a deliberately-leaking build: ranks with the startup heap frozen ran stall-free for an hour while a single unfrozen control rank produced exactly one 56s GC stall (py-spy caught it GIL-held mid-collection while the other GPUs spun at 100%).
- Steady-state overhead: none measurable — idle collects are ms-scale against the small unfrozen set and run only when the scheduler is fully idle.

- debo3 · comment · 2026-06-14T21:49:23Z · [source](https://github.com/sgl-project/sglang/pull/28067#issuecomment-4703184397)

Thanks @Swipe4057: jemalloc is a great tip and we'll likely adopt it for the RSS side. Worth being precise about what it does and doesn't address here, though, since they're orthogonal: 
  
jemalloc operates at the C allocator level fragmentation and returning freed pages to the OS (your 20→50GB, day-long-delay RSS symptom). It changes how malloc/free manage physical memory.

This PR is about the duration of CPython's gen-2 garbage collection, which is stop-the-world and scales with the number of tracked Python objects, not with heap fragmentation. The 41s gc.collect() we measured is the GC walking the object graph (tp_traverse over every container) to find reference cycles — that traversal costs the same regardless of the underlying allocator. Because it's GIL-held and on the scheduler's critical path, in a TP group one rank's pause wedges all ranks and trips the health check.

So jemalloc would help your RSS/fragmentation, but it wouldn't shorten a gen-2 pause or prevent the TP-wide stall + pod kill that this PR targets ; they're complementary. (And the heap growth itself, in our case, was an upstream flashinfer TuningConfig leak — flashinfer#2139-family; fixing that stops the accumulation at the source, after which jemalloc keeps RSS tidy.)
