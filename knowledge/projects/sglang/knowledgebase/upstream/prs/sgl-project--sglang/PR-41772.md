# [Fix] disaggregation: Keep a PD rebootstrapped request's cached_tokens from its first handoff

[Upstream PR](https://github.com/sgl-project/sglang/pull/41772) · state: open · merged: False

## Original PR description

## Motivation

On a PD decode worker, a request that is rebootstrapped reports the wrong `usage.prompt_tokens_details.cached_tokens`, and after a second rebootstrap it can report more cached tokens than prompt tokens. Two things rebootstrap a request today: `pause_generation(mode="retract")` followed by `continue_generation` (the RL weight-update loop), and a DSV4.1 + DSPARK memory retraction.

For a rebootstrap, the prefill worker recomputes prompt + generated tokens and reports the cache hit **of that recompute**. `DecodeTransferQueue._commit_transfer_to_req` copies it over the request's usage fields:

- `cached_tokens` and `already_computed`;
- the device/host/storage breakdown;
- the multimodal token counts.

Example with a 1000-token prompt, driven through the real `_commit_transfer_to_req`, `MetadataBuffers` and `Req`:

```
after first handoff  : cached_tokens=0
after rebootstrap    : cached_tokens=1000   (the recompute's hit on prefill's radix)
after 2nd rebootstrap: cached_tokens=1299 > prompt_tokens=1000
```

The aggregated path counts cached tokens once (`retracted_stain`), and `prepare_for_prebuilt` already skips its own update for retracted requests. The PD handoff was the one place that re-counted. This is the same class of issue as #41380 (`queue_time` after a PD-decode retraction): the PD path did not follow a retraction invariant that the aggregated path relies on.

Found while checking the other fields `_commit_transfer_to_req` writes after #41380, which fixed `queue_time` at the same PD retraction boundary.

## Modifications

`python/sglang/srt/disaggregation/decode.py`, `_commit_transfer_to_req`: commit the prefill's usage numbers (cached tokens and breakdown, `already_computed`, mm token counts) only when `decode_req.is_rebootstrap` is false. Both rebootstrap entry points set that flag. A rebootstrap is always of a request that already committed its first handoff, so the kept values are the original ones. `already_computed` stays at 0 from `reset_for_retract`, and every reader of it is gated by `retracted_stain`.

Output ids, the replayed boundary token, logprobs and sampling masks are unchanged.
