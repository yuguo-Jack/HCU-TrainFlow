# [Feat] bench: Add timed-trace replay to sglang-bench

[Upstream PR](https://github.com/sgl-project/sglang/pull/47050) · state: open · merged: False

## Original PR description

## Motivation

`sglang-bench` (#43950) has no trace replay: its datasets are `random`, `random-ids` and `sharegpt`. The Python client's `mooncake` dataset reads a Mooncake-format trace but replays only its *timing*: each `hash_ids` entry becomes placeholder text through the chat template, so the served prompt lengths are the tokenizer's rather than the trace's `input_length`, and the block-aligned prefix structure that drives prefix-cache reuse is lost. Benchmarks whose gates are exact token counts and cache hit rates (agentic traces, SLA settlement) cannot be replayed that way, and the Python client is also the component that caps throughput at high stream concurrency, the reason the Rust client exists.

vLLM's benchmark client has `timed_trace` (vllm-project/vllm#55937): hash chunks expand to token ids and requests fire at the trace's arrival timestamps. This PR adds it to `sglang-bench` as `--dataset-name timed-trace`, with vLLM's flag names. It is the token-exact counterpart of `mooncake --use-trace-timestamps`: same schedule, exact prompts.

## Modifications

- `rust/sglang-bench/src/timed_trace.rs` (new): JSONL loader (file order, `--num-prompts` cap, remappable field names via `--timed-trace-label-*`, u64 hash ids, float-encoded lengths accepted, non-finite offsets refused with the row named), chunk expansion with a per-(hash, size) cache seeded from the hash (`--timed-trace-chunk-hash-size` ids per hash, last chunk partial so the prompt is exactly `input_length`), and `arrival_offsets` anchored on the first row as the Python client's `get_request` does (negative offsets clamp to 0).
- `src/args.rs`: the dataset and its flags (`--timed-trace-chunk-hash-size`, `--timed-trace-sec-multiplier`, `--timed-trace-label-{timestamp,input-length,output-length,hash-ids}`); `--vocab-size` covers it since the prompts are ids by construction; `--request-rate`, `--disable-ignore-eos` and chat backends are refused for it rather than silently overridden, in line with the crate's existing policy for flags that would report a benchmark nobody ran.
- `src/dataset.rs`: `DatasetRow.timestamp`; `src/run.rs`: `dispatch` sleeps to each row's absolute offset from the dispatch start instead of a Poisson gap when a schedule is present, so a late dispatch does not shift the rest.
- `README.md`: a "Trace replay" section; the dataset is Rust-first (the `serving.py --rust-client` route and its allowlist are untouched, `python -m sglang.benchmark.rust_client` reaches it).
- `--cache-report` (second commit): the Python client's flag, ported. `request.rs` records the prefix-cache hits the engine attributes to each request (`meta_info.cached_tokens` and `cached_tokens_details` on `/generate`, over HTTP and gRPC; `sglext.cached_tokens_details` on the OpenAI routes), `None` where nothing is reported; `metrics.rs` sums them over successful requests by tier and writes the `Cache Hit Details` block, the `cache_report` result key and the `cached_tokens` / `cached_tokens_details` columns under `--output-details`, with the Python client's labels and keys; `rust_client.py` forwards the flag instead of refusing it. A replay needs this per request: it is what lines the engine's hits up against the trace's prefix structure.

Tests (`cargo test -p sglang-bench`, 10 new): exact lengths incl. the partial chunk and scaled offsets; a shared hash prefix yields a shared token prefix; reload is bit-identical; `input_length` is bounded by the hashes (no over-allocation on a corrupt row); `--num-prompts` cap in file order; a missing remapped field names its flag; exporter encodings (u64 hashes, `16.0` lengths); non-finite offset rejected; first-row anchor and negative clamp; the flag refusals.

## Accuracy Tests

Not applicable. Replay fidelity was measured against a live SGLang deployment: Kimi-K3 behind the SGLang router in PD mode (1 prefill + 2 decode workers on B300, `--page-size 64`, hierarchical cache on), no warmup. Served counts are the client's; engine counts are the prefill worker's `sglang:prompt_tokens_total` / `sglang:cached_tokens_total` deltas over the run.

**Mooncake `conversation_trace.jsonl`** ([kvcache-ai/Mooncake FAST'25 release](https://github.com/kvcache-ai/Mooncake/blob/main/FAST25-release/README.md)) as the reference traces dataset. Due to prefill capacity at this deployment, only the first 300 s (= 927 requests, 512-token hash chunks with arrivals replayed 4× slower (`--timed-trace-sec-multiplier 0.004`)) were used:

| quantity | trace value | achieved |
|---|---|---|
| requests completed | 927 | 927 |
| input tokens (Σ `input_length`) | 12,538,685 | 12,538,685 served; engine prompt counter +12,538,685 |
| output tokens (Σ `output_length`) | 326,942 | 326,942 |
| per-request input and output lengths | each row's values | all 927 exact |
| arrival span | 1,200 s (slowed) | run duration 1,210.1 s |
| prefix-cache hits, infinite-cache prefix match on the trace at page 64 | 2,626,048 tokens (20.9 %) | 1,963,200 (15.7 %): GPU tree 584,576, CPU-memory tier 1,325,184, Mooncake L3 53,440 |

The trace value is under infinite cache, meaning it is an upper bound of what the theoretical max cache hit could be with no eviction.

With `--cache-report` the same quantity is available from the client's own record.
