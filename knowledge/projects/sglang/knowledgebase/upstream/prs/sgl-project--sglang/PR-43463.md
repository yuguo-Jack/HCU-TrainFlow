# [QSA] Bound the decode indexer's work by the context length

[Upstream PR](https://github.com/sgl-project/sglang/pull/43463) · state: open · merged: False

## Original PR description

## Motivation

For Qwen3.8-Flash-Next B200 BF16 (TP4, NEXTN MTP 3/1/4) the QSA decode indexer takes about 3 ms of a 28.75 ms bs64 decode step. It costs that much even at short contexts, where QSA selects every block anyway. Three pieces of it scale with the max context instead of the live one:

- `tilelang_qsa_mqa_decode` launches a `(rows, max_pages / 4)` grid. The CUDA-graph page table is sized for the max context: 262144 tokens are 65536 compressed tokens, which is 4096 pages of 16, or 1024 CTAs per row. At bs64 verify (256 rows) this launches 262K CTAs per layer, almost all of which exit immediately. Each call takes 137 us, 1.78 ms per step.
- For a row whose compressed length fits the k = 512 top-k, `fast_topk` writes `0..len-1` without reading its scores. So the scoring work on that row is thrown away, and so is the `-inf` pre-fill of the whole `rows x max_model_len` logits matrix, since `fast_topk` never reads past a row's length.
- `_qsa_fused_kv_prepare` writes every row's full packed width: 2112 tokens of K and V at 256 dims, zero-filling the part past the valid count. `trtllm_decode` reads each row only up to `valid_counts`. At 256 rows this writes 537 MB per call, 76 us per call and 1.06 ms per step.

## Modifications

- `qsa/mqa.py`:
  - The decode kernel now takes `ctas_per_row`, chosen as 1, 16 or 256 by row count so the grid covers about four waves; the three levels bound the number of TileLang specializations. Each row's CTAs stride over its 64-token groups up to `context_len` in a dynamic loop.
  - `min_scored_len` skips rows at or below that length.
  - `tilelang_qsa_mqa_decode(..., min_scored_len=)` leaves those rows, and the columns past each row's length, unset (`torch.empty`). The default of 0 keeps the previous fully `-inf`-filled output.
- `qsa/qsa_indexer.py`: `select_decode_tokens` passes `min_scored_len=block_topk` only on the `fast_topk` (k = 512) path. That path writes `0..len-1` for rows that fit k without reading their scores, and never reads past a length. Every other top-k path keeps the full `-inf` fill.
- `qsa/fused_kv.py`: `fused_kv_prepare(..., visible_page_size=)` applies on the block-index path (`compress_ratio > 1`). A packed tile at or past the row's valid count, rounded up to the page, returns before loading or storing. The count uses the same formula as the `COUNTS` tile.
- `qwen_sparse_attn_backend.py`:
  - The trtllm sparse decode passes `visible_page_size=64`, the trtllm page.
  - The packed scratch is allocated with `torch.zeros`, so bytes that are never written cannot be NaN. The allocation happens once, at full graph capacity during the eager warmup before capture.
- Tests:
  - `test_qsa_indexer.py`: the decode grid scores every group at 256, 16 and 1 CTAs per row, checked against the torch reference. With `min_scored_len`, `fast_topk` returns the same selection; the unset logits are NaN-poisoned through the caching allocator.
  - `test_qsa_fused_kv_prepare.py`: with `visible_page_size`, the visible pages are bitwise equal to the full write and nothing past them is written (NaN sentinel), for counts at and around page edges and widths 1 and 4.

## Accuracy Tests

- `test_qsa_indexer.py` and `test_qsa_fused_kv_prepare.py`: 187 passed. `test_qsa.py`: 49 passed, 1 skipped. All run on B200.
- GSM8K through `sglang.test.run_eval` (chat, 5-shot, 200 questions, greedy, max 4096 tokens), Qwen3.8-Flash-Next BF16, TP4, MTP: 0.985 with this PR, 0.98 on main.
- Needle in a haystack: a 4-digit code planted at 10/50/90% depth in natural text of 1.1K, 4K, 16.6K, 35K and 70K tokens, chat API, greedy. 15/15 pass. Above 2048 tokens QSA's sparse selection is active, so these runs exercise the restructured scoring path.

## Speed Tests and Profiling

Setup:
- 8x B200, two servers built from the same commit: main `5cbf949839` on GPUs 4-7 and this PR on GPUs 0-3.
- Both use the cookbook B200 BF16 low-latency flags.
- Load: closed bursts of chat requests with `ignore_eos`, 1536 output tokens each.
- Step time = running × accept_len / gen_throughput, taken as the median over the steady-state `Decode batch` log lines.

| Concurrency | main | this PR |
|---|---:|---:|
| 1 | 6.29 ms | 6.22 ms |
| 16 | 16.55 ms | 15.77 ms (-4.7%) |
| 64 | 28.75 ms | 26.54 ms (-7.7%) |

Torch profile, bs64 decode, TP0, 10 steps. The main-side profile is from `fba3ad4b1f`, whose QSA files are identical to `5cbf949839`.

| Kernel, per step | main | this PR |
|---|---:|---:|
| TileLang decode scoring | 1.778 ms (137 us/call) | 0.041 ms (3.2 us/call) |
| `_qsa_fused_kv_prepare` | 1.060 ms (76 us/call) | 0.317 ms (22.6 us/call) |
| logits fill | 0.165 ms | 0.036 ms |
| Total | 3.03 ms | 0.42 ms |

Long contexts do not regress. Scoring plus `fast_topk` for 256 rows over a 64K-token context takes 365 us on main and 333 us with this PR. This is an eager measurement including launch overhead, and its 287 MB compressed cache is larger than L2.

Trade-off: up to three TileLang decode-scoring specializations are compiled per head configuration, where main compiled one.
