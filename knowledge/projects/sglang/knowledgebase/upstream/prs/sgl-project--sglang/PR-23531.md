# [Quant] Fix NVFP4 MoE input scale EP sharding in generic post-load path

[Upstream PR](https://github.com/sgl-project/sglang/pull/23531) · state: closed · merged: False

## Original PR description

## Summary

Under `--quantization modelopt_fp4` with expert parallelism (`--ep > 1`) and a non-flashinfer MoE runner backend (e.g. `--moe-runner-backend triton`), server startup crashes in `process_weights_after_loading` with:
```
RuntimeError: The size of tensor a (384) must match the size of tensor b (24)
at non-singleton dimension 0
```

Reproduces on `nvidia/Kimi-K2.5-NVFP4` with `--tp 16 --ep 16 --moe-runner-backend triton --quantization modelopt_fp4` (384 routed experts, 24 local per rank).

## Root cause

In `ModelOptNvFp4FusedMoEMethod`, `w13_input_scale` and `w2_input_scale` are registered with `_sglang_require_global_experts = True`, so the weight loader brings all `num_experts` (384) scales onto every rank. `process_weights_after_loading` is responsible for reducing them down to the rank's local-expert range.

Three backend branches exist in that function:

| branch | reduction | correct under EP? |
|---|---|---|
| `flashinfer_cutlass` / `flashinfer_trtllm` | `.max()` → scalar | yes (scalar broadcasts) |
| `flashinfer_cutedsl` | explicit `_slice_scale` to `[num_local_experts]` | yes |
| else (generic / triton / cutlass) | `.max(dim=-1).values` → `[num_experts]` | **no, never sliced** |

Downstream in the same function, `w13_weight_scale_2` / `w2_weight_scale_2` are
already per-local-expert (size `num_local_experts`). The elementwise multiply
`w13_input_scale * w13_weight_scale_2` then sees `[num_experts] × [num_local_experts]`
and raises.

## Changes

- `python/sglang/srt/layers/quantization/modelopt_quant.py`
  - In the generic `else` branch of `process_weights_after_loading`, slice `w13_input_scale` and `w2_input_scale` to this rank's local expert range when `moe_ep_size > 1`. Mirrors what `flashinfer_cutedsl` already does via `_slice_scale`.
