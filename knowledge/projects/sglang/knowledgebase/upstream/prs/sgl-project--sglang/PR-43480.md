# [Perf] [AMD] DSV4.1: Fuse wo_b's GEMM with its all-reduce via mori cco on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/43480) · state: open · merged: False

## Original PR description

## What

`wo_b` in DeepSeek-V4.1-Flash is a `RowParallelLinear`: an mxfp8 GEMM followed
by an all-reduce of the `[M, hidden]` result. The two can overlap.
`mori.ops.gemm_ar`'s fused kernel writes each destination's row band straight
into a symmetric window and hands it to the SDMA copy engines as soon as that
band's tiles are done, so the transfer runs *inside* the GEMM instead of after
it. The reduce and all-gather still run as their own kernels.

**Opt-in and ROCm gfx950 only.** `fused_wo_b()` returns `None` for everything it
does not serve — decode, small or ragged `M`, a layer neither mxfp8 route
prepared, no SDMA queues — and disables itself for the process on any failure,
so the ordinary path is the fallback rather than an error.

Supersedes #40757, which could not be reopened after its branch was
force-pushed. Same branch, rebased onto current `main`; the first commit is that
PR's content and the second takes it to V4.1-Flash.

## Two switches, and they are not interchangeable

| | TTFT, TP2 | TTFT, TP4 | numerics |
|---|---:|---:|---|
| `SGLANG_OPT_FUSED_WO_B_AR=1` | **−2.4%** | **−2.0%** | relL2 **7.5e-3 – 8.2e-3** |
| ` + ..._FP8_GATHER=1` | **−5.8%** | **−7.0%** | relL2 **1.87e-2** |

The fp8 gather sends the all-gather leg as e4m3 with a per-row scale. It is
worth more than the fusing itself — and it is the half that costs accuracy, so
it stays off by default.

2x and 4x MI355X, DeepSeek-V4.1-Flash, 16384 in / 64 out, concurrency 1, the
MI355X cookbook's flags unchanged (including `--fp8-gemm-backend aiter`).
Medians over six fresh server instances per arm, arms interleaved. 48 instances,
24 pairs, every pair agreeing in sign.

### Numerics, measured where the path engages

`SGLANG_DEBUG_FUSED_WO_B_AR=1` reports two things per fused call: the op against
the unfused path, and the op against *itself* on the same inputs immediately
again. 42 samples per arm at M=16384:

**Corrected after review** (thanks @hubertlu-tw). This section claimed the bf16
wire was bit-identical on the cookbook flags. It is not, and the claim was the
wrong half of a real distinction: exactness needs `wo_a` to hand `wo_b` an
`Fp8GridActivation`, which `wo_b_takes_fp8_grid()` only returns for the gfx950
*native* mxfp8 route. The MI355X recipes pin `--fp8-gemm-backend aiter`, where
`wo_b` receives a plain bf16 tensor and the fused and unfused paths each
quantise it themselves.

Re-measured at M=16384, 4x MI355X, TP4, cookbook flags otherwise unchanged:

| | vs unfused | vs itself |
|---|---|---|
| bf16 wire, `--fp8-gemm-backend aiter` | 7.48e-3 .. 8.20e-3 | 0 |
| bf16 wire, `--fp8-gemm-backend auto` | 7.48e-3 .. 7.56e-3 | 0 |
| fp8 wire | 1.844e-2 .. 1.899e-2 | 0 |

The earlier **0** could not be reproduced on either backend value, and the
native route it would require is not one these flags select, so treat it as
withdrawn rather than conditional. The second column staying zero is the part
that holds: the collective is deterministic, without which "lossy but
deterministic" and "non-deterministic" would look the same.

The fp8 wire's spread is 3% of its own value, which is what a fixed mantissa
width looks like rather than a numerical hazard. **What it does to downstream
quality is not measured here**: GSM8K cannot answer it — its 5-shot prompts give
a padded M of ~512 against a floor of 8192, so every arm runs the same code, and
two passes of that same code scored 0.906 and 0.898, which puts its resolution
above 1% anyway.

## Worth a reviewer's attention

* **Both gfx950 mxfp8 routes are served, and the weight's shape cannot say which
  one ran.** The native route rebinds the weight to a shuffled
  `[N/16, K/128, 2048]`; the aiter route — which `--fp8-gemm-backend aiter`
  takes, and which the MI355X cookbook pins — leaves the checkpoint's `[N, K]`.
  `mxfp8_aiter_ready` records it, because reading one layout as the other
  returns an uncorrelated result rather than failing. mori's own `preshuffle_b`
  is defined on exactly what the aiter route leaves, so only the B conversion
  branches.

* **The operand the gfx950 `wo_a` fork emits decides whether this can serve the
  call at all.** An `Fp8GridActivation` unwraps to the bf16 underneath, but an
  `Mxfp8Activation` is already quantised with no bf16 left and the op does its
  own quantisation, so that form keeps the ordinary path. Only decode produces
  it, which the M floor declines anyway.

* **The window is VMM memory outside torch's allocator**, sized from
  `get_schedule().chunked_prefill_size` and unable to grow afterwards (560-640
  MiB at these shapes), so a run that enables this wants a correspondingly lower
  `--mem-fraction-static`. It is taken from the chunked-prefill limit rather
  than the first request seen, so a short prompt arriving first cannot leave a
  window too small for a later full chunk.

* **The thresholds are on the SGLang side on purpose.** `_MIN_FUSED_M` (8192 on
  the bf16 wire, 2048 on the fp8 one) answers "is fusing *worth* it against
  what the model runs today", which is not a property of the kernel;
  `mori.ops.gemm_ar.supports()` answers the separate question of whether the
  shape is expressible.

* **The MORI pin moves to `066fd10e`** so that `export BUILD_CCO_SDMA=ON` can
  come out of the Dockerfile and the CI install script: ROCm/mori#710 made the
  cco SDMA path the default and normalised `1`/`TRUE`/`yes`, which previously
  built a host library with SDMA and JITted a device wrapper without it. The
  guard in `_FusedWoB` stays — a build can still opt out, and the failure mode
  it catches is a collective that moves no bytes and therefore measures
  *faster*.

## How these were measured, because a single pair does not resolve them

Instance-to-instance spread on these boxes is the same order as the effect,
while repeats inside one server instance land within ~1%. An earlier three-pair
run of the same comparison came out at −0.1% with two of its three pairs landing
on the baseline; six pairs of fresh instances put it at −5.8% with all six
agreeing. So: interleave the arms, take the median across instances, keep both
arms in one lease on one node, and record a signal that each arm is what it
claims to be (`window` present, `declines` zero) rather than trusting the switch.

Per-layer timings are deliberately **not** quoted. That harness synchronises
every call, so the transfer sits on the critical path with no neighbouring work
to hide behind — it cannot show an overlap benefit by construction, and its
baseline is the native route rather than the aiter one the server takes. On a
contended node it also inflates the NCCL baseline ~48% while leaving the SDMA
path untouched, which flips the sign.

## Not in this PR

* **The standalone mxfp8 GEMM.** mori's GEMM without a collective attached is
  ~25-30% faster than aiter's at these shapes and serves layers this has nothing
  to fuse with, but it belongs in aiter rather than behind an SGLang switch, and
  is going there instead.
* **Tests.** The perf harnesses this was derived with are not included.
* **V4-Pro.** #40757 measured V4-Pro, whose `wo_b` is a 128x128 block-scale
  linear preshuffled by the aiter block-fp8 route. V4.1-Flash quantises at
  32-wide ue8m0 and takes a gfx950 mxfp8 route, so the second commit replaces
  that path rather than adding to it — those numbers describe the first commit,
  not this PR's head.

### 1. DP attention: wrong reduction group, possible hang

You're right on both counts, and the second one follows from the first. The gate was on `defer_all_reduce`, which is a different question — everything that made *that* false reached the fused path, including `attn_tp_size == 1` and `1 < attn_tp_size < tp_size`. The env var's comment said "TP-only" and nothing enforced it.

Rather than gate at the call site I put it in `fused_wo_b`, as `_reduces_over_tp_group(layer)`, using `RowParallelLinear.forward`'s own conditions read off the layer — `reduce_results and tp_size > 1`, not `use_decode_attn_tp`, not `use_dp_attention_reduce`, and `tuple(layer.tp_group.ranks) == tuple(get_tp_group().ranks)`. The call site is where this went wrong once; restating the rule there would leave two places to keep in agreement. `should_skip_mlp_all_reduce()` is in the per-forward half of it, which you'll also recognise as a case the old code let through: it made `defer_all_reduce` false, so the fused path performed a reduce the split path would have skipped.

Not gated: `quantize_communications`, which would make the split path's reduce numerically different — `validation_hook.py:263` rejects it on anything but NPU.

Verified end to end: TP2 with `--attn-dp-size 2` (so `attn_tp_size == 1`), switch on, an 8401-token prompt that is eligible on the TP-only run. **Zero** `mori fused wo_b` lines — it declines before constructing anything — and the model answers correctly. Plus a unit check of all six group configurations.

That also closes the hang, since eligibility can only diverge across ranks under DP attention, which no longer reaches `_eligible`.

### 2. A rank-local disable deadlocks the TP group

Agreed, and the architecture was wrong rather than the handler. Construction is now collective: `_construct_collectively` attempts it on every rank, agrees the outcome over `tp.cpu_group`, and the ranks that *succeeded* tear their communicator down when a peer did not — otherwise they hold the window's reservation for a path nothing can use.

After construction there is no fallback left. An OOM in `pad_rows`/`quantize_packed` is rank-local and `run` is collective, so returning None from either is exactly the silent hang you describe; dying is visible. Every remaining reason to decline is an explicit check above that point, and each reads the same on all ranks.

Verified with fault injection under torchrun, both `--fail-rank 0` and `--fail-rank 1`:

```
rank 0: constructed=False  disabled=True  state_kept=False  torn_down=True
rank 1: constructed=False  disabled=True  state_kept=False  torn_down=False
all ranks agree: True
```

### 3. Construction `ValueError` retried every call

Same root cause — one `try` over both construction and the per-call work, with a handler written for the latter. Construction is attempted once and a failure is permanent (and collective).

### 4. Lazy second copy of each `wo_b` weight

`prepare_wo_b_weight` now runs at load time. Worth noting that my first attempt at this **didn't work and the measurement caught it**: I hooked `post_load_weights`, which `loader.py:856` runs *before* `process_weights_after_loading`, so `mxfp8_ready` was false and it returned without allocating — KV cache and available memory came out byte-identical to the switch-off run. It is now in `precompile_kernels_after_loading`, which runs after the layout exists and before the pool is sized.

TP2, identical args, `max_total_num_tokens`:

| | tokens |
|---|---:|
| switch off | 34,249,728 |
| switch on | 33,768,960 |

−480,768 tokens. With four MLA KV source layers that is roughly 1.1 GB, against 40 × 21 MiB ≈ 840 MiB of extra weight — the right order, and the point is that the profiler now sees it at all.

### 5. Window sizing without chunked prefill

Switched to `max_prefill_buffer_tokens()` with `max_prefill_tokens` as the fallback, which is what the other buffer-sizing callers here use and also covers PP dynamic chunking's 1.25× probe. Added the one-line warning when a call exceeds the window.

Verified with `--chunked-prefill-size -1 --max-prefill-tokens 20480`, first eligible request M=8401:

```
mori fused wo_b: window 700 MiB, tp=2, M<=20480, N=5120, K=4096, gather=bf16
```

Sized from the ceiling, not from that first request — which under the old code would have pinned it at ~8448 and declined everything larger for the life of the process.

### 6. Raw `os.environ`

Both go through the `EnvField` API now, and `os` is no longer imported. Your sub-point was the sharper half: `SHAPE_LOG=true` was silently ignored and `override()` did nothing, since it was compared against `"1"` at import time. Checked both in the unit test.

### 7. Duplicated ue8m0 scale rule

The quantiser calls `fp8_grid_quant` and keeps only the packed store. You're right that they are not the same function — `fp8_grid_quant` takes the exponent off the IEEE bits and is exact at powers of two, where `ceil(tl.log2(.))` can land above the integer and pick one exponent higher.

Verified rather than reasoned: operands with whole groups placed on exact powers of two of 448, comparing against `fp8_grid_quantize`. Exponents and fp8 codes are now byte-identical; 0 differing groups.

### 8. Hot-path overhead

The switch is memoised (`_disabled` stays dynamic and is checked first, so the off path is one bool), and `m_pad` is computed once per call instead of three times. I left the call-site caching alone — it's a model-file change for what is now a memoised read.

Nothing on the tensor moves, so the cache cannot be made to notice. **The update has to be refused**, which is what sglang already has a mechanism for and I should have found before inventing a key: `_unsupported_derived_weight_cache_error` walks the modules for `_derived_weight_cache_error`, and all four update paths check it before writing. Its docstring describes this exact case — "derived weight splits that in-place loader writes do not refresh" — and requires the constraint be startup-determined and rank-uniform, which `_can_ever_fuse` is.

So building a fused copy now publishes it and releasing clears it. The `(id, _version)` key is gone rather than kept as a second line of defence, since a key that cannot work is worse than none.

Verified against the updater's own function rather than by reading:

```
ok  clean model allows updates
ok  a fused copy blocks updates
ok  the reason says what to turn off
ok  the cache is indeed blind to a .data write   <- the premise, asserted
ok  releasing lifts the constraint
ok  a rebuild after release sees the new weight
```

The fourth line is deliberate: it asserts the failure mode still exists, so if a future torch makes `.data` writes observable the test says so instead of silently protecting nothing.

Your `id`-reuse point is moot now — there is no key — but it was correct.

@hubertlu-tw @bmullick-amd Thanks for the detailed measurements. I think this is a known environment issue rather than something in the kernels or the integration. **Both of your hosts run Linux 5.15, and the stock Ubuntu 22.04 5.15 kernel is built without `CONFIG_DMABUF_MOVE_NOTIFY`.**

**What happens.** mori cco allocates its symmetric window through the HIP VMM API. `hipMemSetAccess` imports that memory into each peer as a dma-buf. On a kernel without move-notify support, amdgpu won't pin the buffer in VRAM: `amdgpu_dma_buf_pin()` drops the VRAM domain and pins it in **host system memory** instead. After that, every write into the window goes to host DRAM over the writing GPU's PCIe link, at roughly one link's bandwidth. Nothing errors, and results stay correct. It's documented in mori's known issues, Issue 1:
https://github.com/ROCm/mori/blob/main/.claude/skills/known-issues/SKILL.md (from ROCm/mori#595, where EPv2 dropped ~9x for the same reason).

**Why it matches your numbers**
- `gemm-only` writes C (16384×5120 bf16 = 168 MB) straight into the window. 168 MB / 3.3 ms ≈ 51 GB/s, which is about one link. That's also why the time stays flat from K=2048 to K=4096: the cost is the store, not the math.
- The reduce, gather and LSA phases all read and write the window too, so `split-sdma` and `fused-sdma` degrade far more than the GEMM alone.
- `validated=True` and normal relL2 are expected: the data is right, it just lives in the wrong place.
- torch GEMM, RCCL and peer copy don't use VMM-shared memory, so they're unaffected. Our hosts run Ubuntu's 6.8 HWE kernel, which has both options enabled, so the same images run normally there.

This also rules out the JIT-recompilation idea I raised earlier: graph replay doesn't recompile, and 3.3 ms is GPU time.

**How to check (no GPU needed):**
```bash
grep -E 'CONFIG_(PCI_P2PDMA|DMABUF_MOVE_NOTIFY)=' /boot/config-$(uname -r)
```
Both must print `=y`. On one of our boxes, the leftover 5.15 config shows the problem:
```
/boot/config-5.15.0-151-generic:  # CONFIG_DMABUF_MOVE_NOTIFY is not set
/boot/config-6.8.0-65-generic:    CONFIG_DMABUF_MOVE_NOTIFY=y
```
For a direct runtime check, `vmm_peer_probe.cpp` in the same skill directory reports `VERDICT: AFFECTED` if granting peer access moved the buffer out of VRAM.

**Fix.** Install the HWE kernel (`sudo apt install linux-generic-hwe-22.04`, which is 6.8), or rebuild 5.15 with `DMABUF_MOVE_NOTIFY` and `PCI_P2PDMA` enabled. The doc also has a one-line amdgpu DKMS patch. There's no application-level workaround: cco needs a flat symmetric VA across processes, and that only comes from VMM.

def _kernel_config_error() -> RuntimeError | None:
    """The running kernel's config, if readable, rules out a VRAM window."""
    import gzip
    import platform

    sources = ((f"/boot/config-{platform.release()}", open), ("/proc/config.gz", gzip.open))
    for path, opener in sources:

def _vram_used_bytes() -> int | None:
    """This rank's GPU VRAM in use, from amdgpu's sysfs counter."""

Reviewed the whole diff, with a focus on correctness of the gating and on the question of whether any non-gfx950 platform can reach this path.

Overall this is careful work — the collective-agreement staging in `_construct_collectively`, the bounded `self_test`, and the "disable on every rank or none" discipline all address failure modes that are easy to get wrong and hard to debug. The three-layer test split (host gating / mori contract / cross-rank) is the right shape. Below are the things I think are worth acting on.

## Correctness

### 1. `sp_active` is not excluded, and under SP `wo_b` does not all-reduce

`RowParallelLinear.forward` has a branch *before* the all-reduce:

```python
if (
    get_forward().sp_active
    and tp_size > 1
    and not skip_all_reduce
    and output_tensor is None
):
    output = layernorm_sp.row_parallel_gbar_matmul(self, input_parallel, bias_)
    output_bias = self.bias if self.skip_bias_add else None
    return output, output_bias
```

With Megatron SP active, this layer performs a **reduce-scatter** and returns an output that is sharded along the token dim for the next SP LayerNorm region. The fused path performs a full all-reduce and returns an unsharded `[M, N]`, so both the semantics and the shape are wrong.

`_reduces_over_tp_group()` reads only static layer attributes, and `_substitutes_layer_all_reduce()` adds only `should_skip_mlp_all_reduce()`; neither can see this per-forward flag. DSV4 does reach SP — the sibling `wo_b` optimisation in the same method already guards on it:

```python
fuse_mxfp8_quant = self.use_flashinfer_mxfp8_wo_b and not get_forward().sp_active
```

Suggest adding `if get_forward().sp_active: return False` to `_substitutes_layer_all_reduce()`, which is already the home for per-forward flags. `sp_active` is rank-uniform, so this introduces no rank divergence.

Everything else in `_reduces_over_tp_group` checks out against `RowParallelLinear.forward`: once `use_dp_attention_reduce` and `use_decode_attn_tp` are excluded and the rank tuples match, the layer reduces over the global TP group whether it takes the `parallel_group == "tp"` branch or `tensor_model_parallel_all_reduce`. The `attn_tp` subgroup case is declined conservatively, which is correct.

### 2. `mxfp8_shape()` overstates N when N is not a multiple of 32

`mxfp8_shape()` derives `(sn * 32, sk * 32)` from the scale, but `weight_scale_mx_e8m0` has `ceil(N / 32)` rows. That non-divisible case is expected elsewhere in this file — `_prepare_flydsl_mxfp8` does `layer.weight_scale_mx_e8m0.repeat_interleave(32, dim=0)[:n]` precisely to handle it.

The consequence is that `mori_weight()`'s `w.reshape(n, k)` raises, and since `prepare_fused_wo_b` is deliberately not best-effort, that is a startup failure rather than a fallback. K is protected by the `w_k != k` comparison against the activation; N has no equivalent.

DSV4.1-Flash's `wo_b` emits `hidden_size`, which divides, so this is not reachable today. But the aiter route leaves the weight as `[N, K]`, so `layer.weight.shape[0]` is available directly; alternatively `mxfp8_route()` could require `n % 32 == 0 and k % 32 == 0` and return `None` otherwise. Given how defensive the rest of the module is, this gap stands out.

### 3. `prepare_fused_wo_b` allocates copies for layers it will then decline

The window takes `(n, k)` from `candidates[0]`, but `mori_weight(layer)` is then called for *every* candidate. `fused_wo_b` later declines any layer where `n != _state.n or k != _state.k`, so a mismatched layer's full weight copy is never read. Filtering candidates by `(n, k)` before the `mori_weight` loop would close it.

## Worth discussing

**The returned view lives longer than the docstring suggests.** The comment says the caller consumes it in the residual add of the same layer. In practice `attn_boundary.finish()` passes it to `ResidualStream.record()`, which explicitly records the contribution *without applying the residual update*; it is applied at `ffn_boundary.prepare()` inside `op_mhc_post_attn_pre_mlp`. That is still within the same layer and before the next `wo_b`, so it is safe today — and TBO is safe too, because neither DSV4 prefill op list has a `YieldOperation` between `op_attn` and `op_mhc_post_attn_pre_mlp`. But the safety rests on an op schedule this module does not own, and prefill TBO is exactly the large-M regime where fusing engages: a yield inserted between those two ops would make two microbatches overwrite each other's window silently. Worth stating as an invariant in the module docstring, or checking under the debug flag.

**Enabling this flag disables online weight updates.** `_UPDATE_UNSUPPORTED` lands on every `wo_b`. That is a real trade-off for RL / online-update users and probably deserves a mention beyond the env comment. Minor related nit: `release_mori_weight` sets `_derived_weight_cache_error = None` rather than restoring a prior value. The only other writer is the Hopper-only path in `fp8.py`, so there is no collision on ROCm today.

**The `--mem-fraction-static` requirement is only in the env comment and the PR body.** A 560–700 MiB/rank window plus ~840 MiB of weight copies is enough that the first attempt to enable this will OOM for most users; it would help to have it in the docs.

**Bias is silently dropped.** The fused path ignores `layer.bias`. `wo_b` is constructed with `bias=False`, so this is not live, but an explicit `layer.bias is None` check would match the defensive style of the rest of the module.

**LoRA would fail at startup.** With a LoRA adapter, `wo_b` becomes `RowParallelLinearWithLoRA` and the attributes move under `base_layer`. `_reduces_over_tp_group` reads `layer.tp_group` / `layer.reduce_results` directly and `_can_ever_fuse` does not wrap it, so this raises `AttributeError`. Only affects runs that opt in, and one `hasattr` guard covers it.

## Platform reachability

I checked whether anything other than ROCm gfx950 can reach the fused path. The answer is no, but the guarantee is implicit rather than stated in code.

`fused_wo_b_available()` checks only `_disabled`, the env switch, and that `mori.ops.gemm_ar` imports — there is no `is_hip()` or arch check anywhere in the module. What actually excludes other platforms is the `mxfp8_route(layer)` / `weight_scale_mx_e8m0` test, via this chain: those markers are set only in `fp8_hip.process_dense_weights`, which is called only from the `backend.is_gfx95()` branch of `_process_mxfp8_linear_weight_scale`, and the `GFX95_*` backends are selected only under `_is_hip and _is_gfx95_supported` in `resolve_block_fp8_mxfp8_backend()`.

Per platform:

- **NVIDIA / CPU / XPU**: mori is a ROCm-only package, so the import fails, `_mori_has_gemm_ar()` sets `_disabled` and warns once. Even with mori somehow present, no layer carries `weight_scale_mx_e8m0` and every call stops at the `hasattr`.
- **NPU**: the markers are never set, and NPU has its own `use_npu_arch35_mxfp8_wo_a` route.
- **gfx942 / MI300X**: the closest case, because the ROCm image *does* ship mori, so `fused_wo_b_available()` returns True. `_is_gfx95_supported` is False, so no mxfp8 marker exists, `_can_ever_fuse` returns False and no window is allocated. Behaviour is correct; the cost is one attribute lookup per call.

So nothing is broken, but I would still add `is_gfx95_supported()` (already in `sglang/srt/utils/common.py`) to `fused_wo_b_available()`. The concern is not today's behaviour: the gate is currently "does this attribute exist" rather than "what hardware is this", so if any future backend reuses the `weight_scale_mx_e8m0` / `mxfp8_aiter_ready` names — a later gfx revision, or a CUDA mxfp8 route — this path becomes eligible silently and fails inside mori's device-side barriers.

Imports are fine: `deepseek_v4.py` imports `mori_gemm_ar` unconditionally at module scope, which pulls in `triton` and `mxfp8_amd_gfx95`, but that module depends only on torch/triton/msgspec and `deepseek_v4.py` already imports several triton kernel modules at top level.

That rank then falls back to `self.wo_b(...)`, i.e. an NCCL all-reduce, while its peers keep calling the mori op. mori's `drain` / `gather` phases end in device-side cross-rank barriers (`kernels_sdma.build_sdma_phases`), so the peers spin on the GPU waiting for a rank that never arrives: no timeout, no error, just a hung server.

Rank-local failures are realistic here: an OOM in `pad_rows` / `quantize_packed` / `mori_weight` (see the comment on `mori_weight`), or `alloc_mem` failing on one rank inside `_FusedWoB.__init__` while the others have already entered `self_test()`, which is itself a collective.

The enable/disable decision needs to be collective. E.g. agree on the outcome of construction across `tp.cpu_group` (all-gather a success flag) before any rank uses the op, and treat failures after construction as fatal rather than silently falling back on one rank.
