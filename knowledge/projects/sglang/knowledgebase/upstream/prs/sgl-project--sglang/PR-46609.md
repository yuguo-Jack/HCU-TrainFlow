# [Perf] [AMD] moe: Raise the small MoE sort's pair limit from 256 to 1024

[Upstream PR](https://github.com/sgl-project/sglang/pull/46609) · state: open · merged: False

## Original PR description

## Motivation

The small MoE sort (#36559, #44004, #42498) is limited to 256 (token, expert) pairs, so it turns off at 32 decode tokens with top 8. Speculative decoding reaches that limit quickly. A DFLASH verify step has 8 tokens per request, so at top 8 it covers only 4 requests (256 pairs); 8 requests need 512 pairs and 16 requests 1024. Past the limit every MoE layer goes back to aiter's two-kernel sort followed by a separate stage-1 quant launch.

The 256 limit was set in #36559 without a stated reason, and #41900/#44004 benchmarked only up to 256 pairs. Measured above it, the sort is still faster than aiter's sort plus quant at every point up to 1024 pairs, and slower from 1536 on (tables below). This PR raises the limit to 1024. On one MI355X, the MoE layer gets 2 to 5 % faster between 257 and about 900 pairs, and is unchanged at and above 1024. In serving MiMo-V2.6-Pro-RL with DFLASH, throughput rises 1.3 % with 8 concurrent requests and is unchanged with 16 (same-node A/B below).

Why the crossover sits there: the sort (the bitonic kernel from #44004, with #42498's fused quant) runs in one CTA over `next_pow2(pairs)` lanes, so its time steps up at each power of two: 5.3 us up to 256 pairs, 7.3 to 7.6 us up to 512, and 10 us up to 1024. At 1536 pairs it pads to 2048 lanes and takes 18 us. aiter's sort plus quant grows only from 9.5 to 11.7 us between 256 and 1024 pairs (masked, block 32). Beyond 1024 pairs, the sort also nears Triton's limit of 2^20 elements per tensor for `PAD_POW2 = next_pow2(pairs * block_size)`; in this sweep it failed to compile at block 128 with 16k pairs and at block 64 with 32k.

Related PRs:
- This PR requires #44009, which in turn requires #42498. Only the last two commits are new (see the review note under Modifications).
- It applies cleanly to main.
- No open PR depends on the 256 limit or conflicts with raising it:
  - #43822 (@kevin-mii) and #41871 (@Jacob0226) edit the same gate, and they already conflict textually with #44009 and #42498. This commit adds no new conflict.
  - #41871 emits MXFP4 from the compact kernel and the distributed kernel, not from the bitonic one. Measured up to 1024 pairs, its output is bitwise equal to aiter's, but past 256 pairs its distributed kernel is slower than aiter: 20.4 against 9.7 us at 512 pairs and 36.4 against 10.3 us at 1024 (Qwen3-30B-A3B shape, block 32). If both land, that emit path should keep its 256 limit. The raised limit belongs to the bitonic kernel only.
  - #44987 and #44988 (drafts) hand off to aiter's `moe_sorting` and do not touch the limit.

## Accuracy Tests

This PR changes which batches take the small sort, not the sort itself. So accuracy comes down to one question: for the newly admitted batches (257 to 1024 pairs), does the small sort give stage 1 the same input that aiter's `moe_sorting` plus quant gives it? If it does, stage 1's output is unchanged.

"The same input" means aiter's sort contract:
- `num_valid_ids`, `sorted_expert_ids` and the padding are identical.
- Each expert block holds the same (token, slot, weight) pairs. Their order inside a block is not part of the contract: stage 1 computes each row on its own and writes it to that pair's (token, slot) position.
- With the fused quant, each token's fp8 row and the e8m0 scales of each pair's row are identical, byte for byte.

`TestMoeSortingSmallPast256Pairs` checks this over the whole new range. It uses MiMo-V2.6-Pro's shape (384 experts, top 8, hidden 6144) and DeepSeek-V4.1's (385 experts with the fused shared expert, top 7, hidden 5120), at blocks 16, 32, 64 and 128, with no mask, with each EP8 rank's mask, and with a random mask:
- **Sort:** every row count from 257 to 1024 pairs with uniform routing. Every 8th row count also runs with a few hot experts, with every token on the same experts, and, under a mask, with every pair on another rank. All 11,604 cases match aiter.
- **Fused quant:** every 6th row count, with uniform and hot routing. All 2,960 cases match aiter byte for byte.
- **Stage 1:** aiter's a8w4 `fused_moe` (MXFP4 weights) with the small sort, against stock aiter, in 26 cases: MiMo EP8 ranks 0 and 5, and DeepSeek-V4.1 with no mask and with rank 2. The stage-1 output is bitwise equal at every (token, slot) the rank computes. One row past the limit (129 rows at top 8, 147 at top 7), the wrapper does not fuse the quant and aiter does the sort, as intended.
- **Determinism:** 192 cases, three calls each. The sort and quant outputs are bitwise equal across calls, including the order inside blocks.
- **Gate:** at four expert counts, with and without a mask and at every block size, the largest row count within 1024 pairs is admitted and the next is not. Exactly 1024 pairs is admitted and 1025 is not.

On one MI355X (image `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261025`, Triton 3.8.0, torch 2.11.0+rocm10.0.0, with this branch's `python/` ahead of the image's sglang), all 15 tests in `test_moe_sorting_small.py` pass at `659a7f79`, none skipped, in 119 s.

The test stops at stage 1 because aiter's stage 2 is not deterministic: two stock runs of the same layer (random MXFP4 weights) differ by up to 4 in the bf16 output's maximum absolute difference. The pair order inside a block can change the order in which stage 2 adds up a token's experts, and that falls within the same run-to-run variation. This is also why the layer runs under Speed Tests are not bitwise equal to stock.

I did not rerun GPQA or other end-to-end evals. The serving runs below are a speed check only.

Between 257 and 1024 pairs, the 1024 limit was faster than or equal to the 256 limit at all 12 points measured. At 256 pairs or fewer, and past 1024, both limits run the same code; they agree within 1.5 % below 256 and within 0.2 % above 1024. Under the EP8 mask, the kernel saving falls from 3.4 us at 320 to 512 pairs to 1.2 to 1.7 us at 640 to 1024, and at 1024 pairs it no longer shows in the layer time. For MiMo at 264 to 512 pairs (DFLASH with 5 to 8 requests), the 2.3 to 3.3 us saved per layer comes to about 0.2 ms per decode step over its 69 MoE layers.

Serving: MiMo-V2.6-Pro-RL MXFP4, TP8/EP8, DFLASH with 8 draft tokens, on one MI355X node.
- **Baseline:** our current best MiMo image, `amdsiloai/sglang:v0.5.21-rocm10-mi35x-20261011-mimo-aiter-tuned-p0-ep8sort-pfused-pr41573`. Its small sort is the 2026-10-12 version of #42498 + #44009.
- **This PR:** the same image with this PR's two `<= 256` checks raised to 1024.
- **Method:** random dataset at ratio 0.8, with identical prompts and seeds. Both arms ran on the same node, one sweep each, the PR arm first.
- **Points:** only the four whose pair counts this PR moves. A verify step puts 64 pairs per request through the sort (8 tokens × top 8), so 5 to 16 requests means 320 to 1024 pairs. At 4 requests or fewer the small sort already runs, and at 32 or more the batch is past 1024.

| 8k / 1k | 8 | 1756.9 / 1780.0 | +1.3 % | -1.2 % | -1.8 % |
| 8k / 1k | 16 | 2309.5 / 2318.2 | +0.4 % | +0.4 % | -0.3 % |
| 60k / 600 | 16 | 354.5 / 356.5 | +0.6 % | -0.7 % | -0.3 % |
| 128k / 1k | 16 | 229.3 / 229.6 | +0.1 % | -2.3 % | -0.6 % |

An earlier, preempted run of this PR's arm on the same node repeated 8k/8 and 8k/16 within 0.3 % throughput. The 8-request gain is about four times that spread, and it matches the about 0.2 ms per verify step expected from the layer numbers. At 16 requests the batch reaches 1024 pairs, where the layer time is unchanged, so those points stay within run-to-run noise.
