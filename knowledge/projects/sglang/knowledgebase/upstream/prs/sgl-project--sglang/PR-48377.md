# [Perf] qsa: CUDA-graph-safe fused resolve for the QSA K/V host offload (2/N)

[Upstream PR](https://github.com/sgl-project/sglang/pull/48377) · state: open · merged: False

## Original PR description

> **Stacked on #48376 (1/N).** This branch includes #48376's commits; the change to review here is the commits after `d7ac615487` ([compare](https://github.com/esarafian/sglang/compare/qsa-kv-host-offload-store...qsa-kv-host-offload-fused)). I will rebase once #48376 merges.

## Motivation

#48376 (1/N) added host offload of the QSA K/V for Qwen4-Exp. It keeps the full-attention K/V in pinned host memory and a per-request GPU cache of the selected blocks, and it works with the radix cache. Its resolve (selected positions → GPU rows, swapping missing blocks in from the host) is an eager torch reference with host synchronizations, so it needs `--disable-cuda-graph` and costs about 63 ms per decode step at 61K-token contexts on a 300 W RTX PRO 6000 (measured in PR 1/N).

This PR adds a fused Triton resolve that keeps every table on the GPU and needs no host synchronization, so decode and target verify run inside CUDA graphs. It is the default on CUDA.

**Series.** Stacked on PR 1/N and must merge after it. On its own merits it replaces the eager resolve with a CUDA-graph-safe one; it adds no other feature.

## Modifications

- **`mem_cache/qsa_kv_offload_kernels.py` (new):**
  - `_resolve_kernel`: one program per request. It does the tail-ring bookkeeping, takes the unique selected blocks, keeps an exact per-request LRU (double-buffered order list), and refreshes stale blocks: a block is reused only while `req_to_token` still maps its positions to the slots it was filled from. It also writes the copy plan and the per-column device rows.
  - `_copy_plan_kernel` and `_ring_load_kernel` read the planned host rows through their pinned UVA addresses. `_write_through_kernel` copies new rows to the host.
  - Requests past `num_real` (CUDA-graph padding) are skipped.
  - A complete block leaving the tail ring is not copied into the LRU from its ring rows. The backend stores the new token before the resolve runs, so those rows may already be overwritten. The block is loaded from the host on its next miss instead: at most one 4-token block per request and layer every 4 decode tokens.
  - A selected column that resolves to no device row should not happen. It is counted on the device and raises at the next eager forward (an async pinned copy, no host sync), so attention never silently skips a token.
- **`mem_cache/qsa_kv_offload.py`:**
  - The fused resolve is the default on CUDA (not HIP: it reads the host store through raw UVA pointers). `SGLANG_ENABLE_QSA_KV_OFFLOAD_TORCH_RESOLVE=1` selects the eager reference (A/B, debugging).
  - Under the fused resolve the torch tables are not allocated.
  - The verify mode's checks accumulate on the device, so they also run inside CUDA graphs, and leave out CUDA-graph padding rows, which the resolve gives no device row (`real_rows`). In verify mode the offload reads one snapshot of `req_to_token` per forward (`snapshot_mapping`), so its resolve and the full-pool reference read the same mapping even when the scheduler rewrites it mid-forward. They are read back on every eager forward (one host read of two counters, in verify mode only) and at shutdown; any mismatch raises, and progress is logged at most every 10 s. Serving itself reads the live table; a mapping rewritten mid-forward is handled there by the resolve's staleness check, not by the verify mode.
- **`layers/attention/qwen_sparse_attn_backend.py`:** binds the offload at graph capture and sets `num_real` on every eager forward and graph replay.
- **`arg_groups/qsa_kv_offload_hook.py`:** decode CUDA graphs are allowed. Prefill CUDA graphs stay off, because the prefill context gather is built from host-side lengths.
- **Tests:** `test_qsa_kv_offload.py` runs both resolves and adds a CUDA-graph test: the resolve captured once and replayed with new positions, new `req_to_token`, radix remaps and padded requests. Padded rows must be -1 and leave every table unchanged. PR 1/N's backend-level test `test_qsa_kv_offload_backend.py` (offload on vs off through `QwenSparseAttnBackend`, bitwise) runs with both resolves.
- **Docs:** `environment_variables.mdx` row for the torch-resolve switch, and a Qwen3.8-Flash-Next cookbook section: when to use the offload, the launch line, host and GPU costs, and incompatible features.

## Accuracy Tests

The offload stays bit-exact.

- **Unit tests** (`test/registered/kernels/ops/attention/qsa/test_qsa_kv_offload.py`): for both resolves (fused and torch) × BF16, FP8→BF16 and FP8→FP8 packing × decode and 4-row verify, the packed decode scratch from the offload's row table is bit-identical to upstream's gather through `req_to_token` on the full pool. The scenarios include eviction at the minimum hot-cache size, radix remaps and verify rejections. The fused error counter stays 0. **13 pass**, plus PR 1/N's backend-level test with both resolves (2 pass).
- **End to end, inside CUDA graphs:** `SGLANG_DEBUG_QSA_KV_OFFLOAD_VERIFY=1` with decode CUDA graphs on, the same 24-request mix as PR 1/N, H = 512 blocks, RTX PRO 6000 Blackwell Server Edition (600 W). At this PR's head, **15 runs, 0 mismatches** (27,552-29,544 checks each; 4 of them with every decode batch size 1-8 captured). Earlier commits passed too: ≥ 24,516 checks on an RTX PRO 6000 Blackwell (300 W) and 29,448 at 600 W.
  - Two verify false positives were found and fixed while gating; serving output was not affected by either.
  - **CUDA-graph padding.** A decode batch padded to the next captured size (3 requests in the size-4 graph) reported mismatches in every padded step. The resolve leaves padding rows unattended by design, but the verify reference still gathered them. The reference now leaves them out.
  - **Mapping rewritten mid-forward.** About one run in eight reported 2 differing tensors, i.e. K and V of one check. The diagnosed case was one decode row of 4, in the first QSA layer only, with 280 of 2,050 columns differing, at prompt positions (e.g. 20,268 of 20,370) during the shared-prefix concurrent phase. Mechanism (code): the scheduler rewrites a running request's `req_to_token` rows (radix dedup in `RadixCache.checkpoint`) on its own stream while the next forward runs. The old and new rows point at K/V of the same tokens, so attention is equally valid with either, as it is on `main`. But the resolve and the reference could read different rows within one layer. Verify mode now copies the mapping once per forward, and both read that copy; serving still reads the live table.
- **Token identity vs `main` on GB200, inside CUDA graphs**, where deterministic inference runs for this model: one GB200, TP1, `--enable-deterministic-inference --attention-backend flashinfer`, decode CUDA graphs on (`--disable-prefill-cuda-graph`), offload on with in-server verify, the same 24 requests. **24/24 outputs are token-identical** to `main` with the same arguments; verify ran 27,900 checks with 0 mismatches.
- Token identity vs `main` is not gated on SM120, for the reasons in PR 1/N: `main` is not run-to-run deterministic for this model there, and deterministic mode needs more shared memory than SM120 has.
- **gsm8k** (`sgl-eval run gsm8k --num-examples 200 --temperature 0 --max-tokens 4096`). Serving args as in the speed test, with `--context-length 20480` and decode CUDA graphs on. Hardware: RTX PRO 6000 Blackwell Server Edition (600 W).

  | Run | Offload off | Offload on |
  |---|---|---|
  | `main` vs this PR, separate allocations | 97.5% | 96.5% |
  | this PR off then on, one allocation | 97.5% | 96.0% |
  | this PR off, on, off, one allocation | 96.0% / 96.5% | 97.0% |

  The spread is run-to-run noise. In the off-on-off run, the two **offload-off** runs produce different text for 194 of 200 questions, and off vs on differ on 188-192. Correctness changes on 2-3 questions in every pair. Mean: 96.9% off vs 96.5% on (± 1.2 pp standard error per run).

## Speed Tests and Profiling

Setup: `main` and this PR on the same GPU and image; decode CUDA graphs on and `--disable-prefill-cuda-graph` on both sides.
- Common args: `--tp 1 --quantization modelopt_fp4 --mem-fraction-static 0.93 --max-running-requests 32 --chunked-prefill-size 4096 --context-length 65536`.
- This PR adds `--enable-qsa-kv-offload --qsa-kv-offload-host-size 60 --qsa-kv-offload-hot-blocks 1024`.
- Load: `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random-ids --random-input-len 61440 --random-output-len 1024 --random-range-ratio 1.0 --num-prompts 16 --max-concurrency 16`, three runs per arm (seeds 1-3) on one server. Shown as median [min-max].

**RTX PRO 6000 Blackwell Server Edition (600 W)**, this PR's resolve as reviewed (commit `a7751467da`):

| Arm | KV tokens | Max running | Output tok/s | Median TTFT | Median TPOT | Duration |
|---|---|---|---|---|---|---|
| `main` | 308,416 | 4 (KV-bound) | 139.5 [126.5-145.3] | 44.8 s [36.3-58.1] | 15.3 ms [15.3-17.2] | 117.4 s |
| this PR | 2,441,280 | 11 (GDN-state cap) | **165.1** [148.0-177.8] | 39.5 s [39.4-46.7] | 23.6 ms [22.8-24.4] | 99.2 s |

- **Output throughput +18%**, and the ranges do not overlap. With 61K-token sessions the offload runs 2.75× the concurrent sessions (4 → 11) at the default GDN-state budget.
- The fused resolve costs about 8 ms per decode step at 11 running vs `main` at 4 (TPOT 23.6 vs 15.3 ms), against about 63 ms for PR 1/N's eager resolve.
- Prefill gathers the whole context from the host for every chunk after the first. A follow-up could gather only the rows the top-k reads.

**RTX PRO 6000 Blackwell (300 W)**, same args and load, at earlier commits of this PR (`0f7be68f88`, `eb5e54a7e5`), before the review changes to the resolve and PR 1/N's sizing change; the sizing of both rows is the same at the final head:

| Arm | KV tokens | Max running | Output tok/s | Median TTFT | Median TPOT | Duration |
|---|---|---|---|---|---|---|
| `main` | 306,624 | 4 (KV-bound) | 126.9 [114.9-132.7] | 48.8 s [44.4-67.0] | 16.4 ms [15.5-18.6] | 129.1 s |
| this PR | 2,441,280 | 11 (GDN-state cap) | **143.8** [133.5-161.4] | 55.3 s [44.4-58.1] | 21.3 ms [20.6-29.8] | 114.0 s |

- Output throughput +13%, though the ranges only just separate.
- Single runs, not claimed (same setup, 256 output tokens): 61K × 24 prompts, `main` 42.8 tok/s with 4 running vs this PR 41.8 tok/s with 11 running (this load is prefill-bound); 16K × 48 prompts, `main` 127.2 vs this PR 123.0 tok/s, both at 11 running.
- In-server verify gate wall time, same 24 requests: 72.9 s with this PR's resolve vs 190.6-201.1 s with PR 1/N's eager resolve. Not a serving benchmark.
