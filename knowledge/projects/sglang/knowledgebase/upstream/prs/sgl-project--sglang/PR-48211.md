# [Fix] openai: do not render a null tool-level defer_loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/48211) · state: open · merged: False

## Original PR description

## Motivation

`Function` drops a null `strict` / `defer_loading` and keeps the client's key order (#46133), so chat templates see the tool schema as the client sent it. Function-level `defer_loading` itself came with #22702. `Tool` has no serializer, though. `serving_chat.py` renders request tools with `item.model_dump()`, so every tool reaches the chat template with an extra tool-level `"defer_loading": null` that the client never sent and that `apply_chat_template` does not render.

Qwen/Qwen2.5-0.5B-Instruct, one user message and two tools (`get_weather`, `run_python`). Served `usage.prompt_tokens` vs `tokenizer.apply_chat_template(messages, tools=<client JSON>)`:

| | main | this PR | HF render |
|---|---|---|---|
| with 2 tools | 241 | **231** | 231 |
| no tools | 38 | 38 | 38 |

The 10 extra tokens on main (5 per tool) are the `"defer_loading": null` entries.

## Modifications

- `Tool` gets a wrap serializer, like `Function`'s: it drops `defer_loading` when it is `None`. An explicit `true` or `false` is kept, at both the tool and the function level.
- Every plain `Tool.model_dump()` now omits the null field:
  - the chat-template render (`serving_chat.py`, request tools and the `tool_choice`-filtered list);
  - the DSV3.2 encoder's `messages[0]["tools"]`. That encoder reads only `tool["function"]`, so its prompt does not change;
  - the tool dicts built by `function_call/base_format_detector.py` and `function_call/beam_detector.py`. Neither reads `defer_loading`. The one reader of tool dicts (`parser/glm53_chat_template.py`) treats a missing key like null.
- Dumps with `exclude_unset=True` (system-message tools, response-format paths) were already unaffected.

## Accuracy Tests

- sgl-eval gsm8k/mmlu prompts carry no tools, so this change cannot reach them; no accuracy eval was run.
- This intentionally changes the prompt for chat requests that carry tools: it now matches the client JSON and the HF render. Requests without tools are unchanged.
- Same GPU, `--enable-deterministic-inference`, greedy, 64 tokens:
  - the no-tools request gives byte-identical text on main and this PR;
  - the tools request gives the same tool call (`get_weather` with `{"city": "Paris"}`) on both.

## Speed Tests and Profiling

No runtime change beyond 5 fewer prompt tokens per tool (in this example).
