# [Fix] HiSparse: check logical capacity for speculative decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/48334) · state: open · merged: False

## Original PR description

## Motivation

An admitted paged HiSparse speculative request already owns persistent device buffers and speculative scratch. `alloc_for_spec_decode` grows logical token positions, while target verification reuses that reserved physical workspace.

The inherited decode-capacity check uses `min(logical_free, physical_free)`. Consequently, a full device working-set pool can trigger retraction even when the next logical allocation fits. One regression models eight running requests requiring 512 logical slots with 1,189,888 logical slots free but only 64 unassigned physical slots.

## Modifications

Override `HiSparseTokenToKVPoolAllocator.check_decode_capacity()` only for paged speculative decoding with configured scratch. Reclaim/check logical slots against the next-step demand. Keep the existing physical gate for new admission (`available_size()`), page-size-one allocation, non-speculative decoding and allocators without configured scratch.

This PR does not change request-length limits or implement/alter terminal PD retraction handling.

## Accuracy Tests

Running the seven new regressions against unmodified upstream allocator code yields **5 failures and 2 passes**. With this change, the capacity/allocator/coordinator suites yield **22 passed, 3 subtests passed**:


Coverage includes scheduler demand, exact logical boundaries, reclaimable logical pages, genuinely exhausted logical capacity, legacy fallbacks, and real CPU paged allocators with all physical pages occupied.

## Speed Tests and Profiling

No throughput benchmark. The intended behavior is to avoid unnecessary retraction without relaxing the logical capacity bound.
