# [Perf] Cache tool-schema meta-validation across requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/46818) · state: open · merged: False

## Original PR description

## Motivation

`OpenAIServingChat._validate_request` runs `Draft202012Validator.check_schema` per tool per request. The jsonschema library re-resolves the meta-schema on every call with no memoization — measured ~0.9 ms for a two-property schema, ~17 ms for a realistic 20-property one with `$defs`. For agentic clients carrying large tool sets this is pure repeated CPU on every request:

- 177 tools × medium schema ≈ **3.1 s per request**, before templating, tokenization, or any engine work.

## Fix

Cache the validation result by canonical schema JSON (sorted keys, via orjson) in a new `check_json_schema` wrapper in `function_call/utils.py`, and call it from `_validate_request` in place of `Draft202012Validator.check_schema`. Semantics are unchanged: same input schema → same validation outcome; `SchemaError` still propagates for invalid schemas (failures are not cached, they re-raise). `lru_cache(maxsize=1024)` bounds memory.

Measured with 177 distinct medium tool schemas: first request ~3.1 s (each schema validated once, unavoidable), subsequent identical request **~1.2 ms**.

## Tests

- `TestCheckJsonSchemaCached`: a repeated schema (including a key-reordered variant, which must hit the same cache entry) triggers exactly one underlying `check_schema` call; an invalid schema still raises `SchemaError`.

Independent of #46810; touches the same validation loop but different lines.

This looks right to me, and the gain is real. On a real server, TTFT fell from 52-55 ms to 14 ms with 18 tools and from 284-287 ms to 38 ms with 81 tools. I left one optional note inline about the size limit.

Tested head 6a172b3e15 merged onto main e152f531d9 and compared with that main, on one B200 GPU with Llama-3.2-1B-Instruct (`--tool-call-parser llama3`), using streamed chat completions with `max_tokens` 1 and generated tool sets.

Median TTFT in ms, pass 1 / pass 2. Idle rows are 30 requests each after warm-up. Concurrent rows are 8 threads with 15 requests each.

| Workload | main | this PR |
| --- | --- | --- |
| No tools | 8.2 / 8.5 | 8.8 / 8.8 |
| 18 tools (31.8 KB) | 52.1 / 54.8 | 14.1 / 14.2 |
| 81 tools (204.8 KB) | 283.8 / 286.6 | 38.6 / 37.5 |
| 18 tools, concurrent | 353.2 / 349.6 | 45.9 / 42.5 |
| 81 tools, concurrent | 2166.4 / 2173.1 | 157.3 / 161.2 |
| 18 tools, schema changes on every request | 72.2 / 72.7 | 73.4 / 73.7 |

The last row is always a miss, so a miss costs about 1 ms more than main. The no-tools path has no tool loop, so I read its gap as run-to-run noise.

Accept/reject results and status codes matched main, both in a differential fuzz of mutated schemas (bad keyword values, NaN, Infinity, big integers, lone surrogates, shuffled keys) and on the server over chat, `/v1/tokenize`, `/v1/messages` and gRPC. Breaking each branch of `check_json_schema` in turn made at least one new test fail, so those branches are protected. There is no new dependency, since orjson is already declared and main already imports jsonschema.

Only one of this and #43274 should land. The tradeoff as I measured it: this PR keeps the same validator and adds no dependency, while #43274 adds a pinned compiled package to five pyprojects and also speeds up new schemas. On a miss this PR still pays 36 ms for 18 tools and 234 ms for 81, against 0.125 ms and 0.825 ms for the #43274 validator form. A hit here costs 0.068 ms and 0.427 ms, and the two match on TTFT when a client repeats the same tools.

My results for #43274 are in a separate review on that PR.

I closed #42213, which targeted the same check, in favor of this PR and #43274.

- bvolpato · comment · 2026-11-02T23:48:17Z · [source](https://github.com/sgl-project/sglang/pull/46818#discussion_r4449164051)

File: `python/sglang/srt/function_call/utils.py` · line 196

Optional note, not a blocker. A schema whose sorted JSON is over 64 KiB never reaches the cache, so a structure-heavy one still pays full `check_schema` on every request. This is no regression from main, and the limit looks deliberate since `test_large_schema_is_not_retained` covers it.

In-process, a 110 KB structural schema took 136.7 ms per call against 136.9 ms for plain `check_schema`, while a 46.6 KB one went from 59.1 ms to 0.113 ms. Cost follows subschema count, not bytes, so being over the limit is not always slow: a 198 KB schema with 97 properties costs about 15 ms either way.

The limit does bound memory. 1,500 distinct 63 KB schemas stopped at 1024 entries and grew RSS by 77 to 127 MB depending on shape, so I would mention the limit in the PR body next to `lru_cache(maxsize=1024)`.

If large tools turn out to matter, keying on a SHA-256 of `schema_json` (collision resistant, since the client controls the input) removes the limit. A prototype with a 1024-entry `OrderedDict` took 0.832 ms on a repeated 110 KB schema, still raised `SchemaError` on an invalid one, and grew RSS by 1.3 MB on 1,500 distinct 256 KB schemas. It needs a small dict in place of `lru_cache`, because a miss still has to validate the schema, and I did not check its thread safety.
