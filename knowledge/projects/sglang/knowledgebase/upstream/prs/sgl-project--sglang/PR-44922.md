# [Perf] SenseNova-U1: BSHD q/k/v, fused MLP gate_up + SiLU, RoPE table…

[Upstream PR](https://github.com/sgl-project/sglang/pull/44922) · state: open · merged: False

## Original PR description

## Motivation

Part of #37742. At 2048x2048 the NEO-Unify denoise forward runs 42 layers x 2
CFG branches per step over 4096 image tokens, so per-layer bookkeeping that is
neither GEMM nor attention adds up. An 8-step `--profile-all-stages` trace on
main shows three sources of it:

- **Layout copies.** Generation q/k/v are built in `[B, H, S, D]` and then
  transposed back to `[B, S, H, D]` (with `.contiguous()`) right before the
  attention call, which consumes BSHD. The bit-exact fused RoPE kernel from
  #40374 also works in BSHD, so on the BHSD path each of its six calls per layer
  (q and k, three axes) transposes in and out of it as well.
- **Unfused MLP activation.** `act_fn(gate_proj(x)) * up_proj(x)` runs two GEMMs,
  a SiLU kernel and a separate multiply kernel.
- **RoPE tables rebuilt in every layer.** Each of the 42 layers recomputes the
  same temporal, height and width cos/sin tables from the same positions, about
  ten tiny kernels per table. Their GPU time is small, but the ~20k launches per
  8 steps are paid on the CPU, and the denoise loop has little CPU headroom.

All three can be removed without changing a single output bit.

## Modifications

In `runtime/models/sensenova_u1/neo_unify/modeling_qwen3.py`, plus a load-time
packing call in `runtime/models/sensenova_u1/loader.py`. The cookbook's Ascend
note said the fused MLP packs its weights on first use; it now says they are
packed once at load time.

**1. Build generation q/k/v directly in BSHD.**

- The q/k/v construction in `Qwen3Attention.forward_gen` moves into a new
  `_build_qkv_gen(hidden_states, indexes, bshd)`. With `bshd=True` the
  projections, the per-head RMSNorms, the 3-axis (t/h/w) RoPE and the head-dim
  concat all stay in `[B, S, H, D]`, and the `transpose(1, 2).contiguous()` of
  q, k and v before attention disappears.
- New `apply_rotary_pos_emb_bshd(q, k, cos, sin)`: the same
  `fused_rope_rotate_half_bitexact` kernel and the same eager fallback as
  `apply_rotary_pos_emb`, on BSHD inputs. Both layouts share one eligibility
  check (`_use_fused_rope`) and one kernel call (`_fused_rope_bshd`), so the
  two cannot drift apart. The eligibility conditions are #40374's, unchanged for
  the BHSD caller; they only gain the sequence dimension as a parameter.
- `forward_gen` decides the layout before building q/k/v. It keeps `[B, H, S, D]`
  for the three consumers that read that layout: the eager (dense-mask)
  fallback, the NPU BNSD flash cache, and the `Cache.update` path. Those paths
  are unchanged.

**2. One gate_up GEMM plus a fused SiLU that rounds like eager.**

- `Qwen3MLP` already packed gate/up into one weight for the NPU `npu_swiglu`
  path, re-pointing both `nn.Linear` weights at slices of the packed buffer so
  the weights are stored once and `state_dict()` is unchanged. That helper is
  generalized (`_pack_npu_gate_up_weights` -> `_packed_gate_up_weight`) and
  reused on CUDA: one GEMM produces `[*, 2 * I]`, then
  `silu_and_mul_with_activation_rounding` does the activation.
- That kernel variant is what keeps this bit-exact. Its `kRoundActivation` path
  rounds `silu(gate)` to bf16 before the multiply and rounds the product once,
  which are exactly the two rounding points of eager `F.silu(gate) * up`. The
  plain `silu_and_mul` keeps the product in fp32 and would change the output.
- The CUDA path is taken in inference mode only (no grad, eval, bf16, `silu`,
  `intermediate_size % 16 == 0`, not under `torch.compile`); everything else
  falls through to the original code.
- Packing happens once, at load time: after `model.to(device)` the loader calls
  `Qwen3MLP.pack_gate_up_weight()` on every MLP and then empties the allocator
  cache. Packing lazily in the first forward instead left every freed 96 MiB
  gate/up pair reserved, since two of them cannot hold the next 192 MiB packed
  buffer: +13.8 GB peak reserved memory on H200 (36378 -> 50228 MB) with the
  same allocated memory.
- The packed weight is a view of the storage the two parameters share, not a
  cached tensor. Sleep mode (`release_memory_occupation`) moves parameters and
  buffers only, so a cached reference would keep ~13.5 GiB per GPU alive while
  asleep. Weights rebound to new storage (wake-up, weight update) are repacked
  on their next forward, which also empties the allocator cache for the same
  fragmentation reason; that happens once per MLP after such an event.

**3. Build the RoPE tables once per forward.**

- Every layer's `rotary_emb` / `rotary_emb_hw` is built from the same config,
  so their tables depend only on the positions and the dtype.
  `Qwen3Model.forward` builds the three `(cos, sin)` pairs once, after `indexes`
  is final (the single-token decode path rebuilds it inside the forward), and
  passes them down as `rope_tables`. The existing `**kwargs` plumbing carries
  them through the decoder layer; only `Qwen3Attention.forward_und` /
  `forward_gen` name the parameter.
- `Qwen3Attention.build_rope_tables` returns the shared tables when their dtype
  matches the layer's input and rebuilds otherwise. The tables are cast to the
  activation dtype, and a layer's input can differ from the embedding dtype
  (fp32 norm weights promote a bf16 input), so reusing them blindly would change
  the RoPE rounding. Called without tables (direct callers, tests), it behaves
  as before.
- This is the step before #40374's: that PR fused *applying* the tables
  (`q * cos + rotate_half(q) * sin`) into one kernel; this one stops
  *recomputing* them in every layer. The two compose.

## Accuracy Tests

The output is **bit-identical** to main, not merely close: 12 runs (4 main, 4
this PR, 4 this PR with per-layer RoPE tables) on H200 at 2048x2048 / 50 steps /
guidance 4.0 / seed 42 all produce a PNG with md5
`b95d2e9f57b48dc4e91fa20de8deca74`. Items 1 and 2 were also checked with the FA3
attention change from the follow-up PR stacked underneath (both builds give
`ca5f3dc015ac07a3b31a46cc822a3e42`).

The paths the default command does not reach are byte-identical to main as well:

| Path | Setup | Result |
|---|---|---|
| 1024x1024 | cookbook command at 1024x1024, 8 runs (4 main, 4 PR) | one md5, `c7017ed1` |
| Dynamic batching (cookbook 5.1) | `--batching-max-size 2 --batching-delay-ms 100`, two concurrent requests with different prompts and seeds, 1024x1024 / 20 steps, 2 rounds | both images identical to main; the two responses finish within 1 ms of each other, so they ran as one B=2 batch (per-sample KV compaction, batched RoPE tables) |
| `think_mode=True` | Python API, 1024x1024 / 20 steps (exercises the single-token decode path, where `indexes` is rebuilt inside the forward) | identical to main, `92f43736` |

Not run on Ascend NPU. The NPU paths keep the `[B, H, S, D]` layout, but the
`npu_swiglu` MLP now uses the load-time packed weight.

Unit tests, `python/sglang/multimodal_gen/test/unit/test_sensenova_u1.py`:
84 passed on H200; 81 passed, 3 skipped (CUDA-only) on CPU. Three cases are new:

- `test_sensenova_u1_gen_qkv_bshd_matches_bhsd`: the BSHD q/k/v build equals the
  BHSD build exactly. On CPU and on CUDA, where 128 tokens with 128-dim heads put
  the t/h/w RoPE on the fused kernel.
- `test_sensenova_u1_cuda_fused_mlp_keeps_eager_rounding`: the fused MLP output
  equals eager `down_proj(silu(gate) * up)` bit for bit.
- `test_sensenova_u1_shared_rope_tables_match_per_layer`: a 2-layer model through
  prefill, single-token decode and denoise matches the per-layer-table build
  exactly, and builds each table once per forward. Its denoise step feeds bf16
  embeddings to fp32 weights, so the dtype rebuild is exercised.

Each was checked to fail on a mutated build: swapping in plain `silu_and_mul`;
swapping `cos`/`sin` in the BSHD kernel call; and, for the RoPE tables, dropping
the dtype check, never reusing the shared tables, or building them before the
decode path rebuilds `indexes`. The existing NPU fused-MLP
test also asserts that the module holds no tensor outside its parameters and
buffers (a cached packed tensor would survive sleep mode).

Memory, 1x H200, cookbook command, `Max peak` reserved: main `bab9c81fea`
36542 MB, this PR 36446 MB (the first version, which packed lazily, measured
50228 MB).

Sleep mode on a 2-GPU server (with the CFG-parallel PR), `nvidia-smi` per GPU:
38.8 GB awake, 4.8 GB after `release_memory_occupation`, 38.6 GB after
`resume_memory_occupation`, 38.9 GB after the first request following wake-up,
which repacks every MLP (54.8 GB when the repack did not empty the cache). The
image is unchanged across the cycle.

## Speed Tests and Profiling

Environment: 1x H200 (driver 595.71.05), Xeon Platinum 8558, torch
2.13.0+cu130, triton 3.7.1; main `bab9c81fea`; local copy of
`sensenova/SenseNova-U1.5-8B-MoT`. GPU clocks were logged during the profiles:
1.87 GHz mean SM clock under load, power-cap throttling only.

1x H200, local checkpoint, the cookbook single-GPU command
(`docs/cookbook/diffusion/SenseNova/SenseNova-U1.5-8B-MoT.mdx` §3.1),
`--warmup-mode request`, reading the `(with warmup excluded)` line, runs
interleaved on one GPU. The middle row is this PR with item 3 disabled (each
layer builds its own tables), to separate its effect:

```bash
sglang generate --model-path <SenseNova-U1.5-8B-MoT> \
  --prompt "A cinematic mountain lake at sunrise, realistic photography." \
  --width 2048 --height 2048 --guidance-scale 4.0 --num-inference-steps 50 \
  --seed 42 --warmup-mode request
```

| Build | Wall time, 4 runs (s) | Median | Delta vs main |
|---|---|---|---|
| main (`bab9c81fea`) | 16.20 / 16.21 / 16.22 / 16.18 | 16.21 s | — |
| this PR, per-layer RoPE tables (items 1-2) | 15.63 / 15.65 / 15.62 / 15.65 | 15.64 s | -3.5% |
| this PR (items 1-3) | 15.37 / 15.36 / 15.35 / 15.36 | 15.36 s | **-5.2%** |

At 1024x1024, where the per-step GPU work is a quarter of the above and launch
overhead weighs more, same worker, interleaved:

| Build | Wall time, 4 runs (s) | Median | Delta |
|---|---|---|---|
| main | 5.49 / 5.32 / 5.14 / 5.29 | 5.30 s | — |
| this PR | 3.72 / 3.73 / 3.74 / 3.73 | 3.73 s | **-29.7%** |

8-step profile (`--profile-all-stages`) at 2048x2048, both builds on the same
worker:

| | main | this PR |
|---|---|---|
| copy / cat / index | 87.2 ms | **11.9 ms** |
| elementwise / activation | 335.0 ms | **259.5 ms** |
| kernel busy total | 2563.2 ms | 2456.3 ms (-4.2%) |
| kernel launches | 57,166 | **33,712 (-41%)** |
| GPU busy share of the profiled window | 66.5% | 91.3% |

GPU kernel time drops 4.2%, yet wall time drops 5.2% at 2K and 29.7% at 1K:
the rest comes from launching 41% fewer kernels. With fewer launches the GPU
stops waiting on the host. The busy share is measured under the profiler, which
inflates host cost, so it overstates how idle main's GPU is in a normal run.

Main resolves attention to torch SDPA here; the follow-up FA3 PR changes that.
Measured before item 3 was added, items 1-2 were worth -3.9% with FA3 stacked
underneath (14.23 s -> 13.66 s).

The merged gate_up GEMM picks a different nvjet tile config than the two
separate GEMMs, at comparable efficiency; the GEMM column moves a few percent
between profiles, so the 50-step wall time is the number to trust.
