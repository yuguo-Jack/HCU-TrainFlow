# [Feat] gemma4: per-layer attention backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44399) · state: open · merged: False

## Original PR description

## Motivation

Gemma-4-31B has two kinds of attention layer:
- 50 sliding-window layers with head_dim 256;
- 10 full-attention layers with head_dim 512.

FA3 cannot run head_dim 512, so on SM90 the whole model runs on `fa4` today. On the 256-dim layers, FA3 is faster than FA4 for small-batch decode. This PR lets Gemma-4 run with `--attention-backend fa3`. The 256-dim layers stay on FA3 and the 512-dim layers run on FA4.

## Modifications

- `FlashAttentionBackend._ver_for(layer)` picks the kernel per layer. On the `fa3` backend it returns FA4 when `max(head_dim, v_head_dim) > 256` or the batch has image masks (FA4-only). Otherwise it returns the backend's own version. MLA and the `fa4` backend are unchanged.
- Every kernel call and FA4-only guard in `forward_extend` and `forward_decode` uses this per-layer `ver` in place of `self.fa_impl_ver`.
- When FA4 layers are present, init rejects a KV cache that is not BF16 and the embedding no-KV-cache path (`fa_skip_kv_cache`), and skips the FA3 scheduler-metadata precompute, which FA3 cannot size for head_dim 512.
- `fa3` is added to Gemma-4's accepted backends.

Usage:

```bash
python -m sglang.launch_server --model-path RedHatAI/gemma-4-31B-it-FP8-block \
  --attention-backend fa3
```

## Accuracy

GSM8K, full test set (1,319 questions), 5-shot, greedy, parallel 8, `sglang.test.few_shot_gsm8k`. Model: RedHatAI/gemma-4-31B-it-FP8-block on 1× H200, TP1, BF16 KV cache, same serving settings as the benchmark below.

| config | Accuracy | Invalid |
|---|---:|---:|
| `fa4` (baseline) | 0.796 | 0.005 |
| `fa3` (hd256 on FA3, hd512 on FA4) | 0.797 | 0.002 |

## Benchmark

`--attention-backend fa4` vs `--attention-backend fa3`, measured with `sglang.bench_serving` on `RedHatAI/gemma-4-31B-it-FP8-block`, 1× H200, TP1. Both backends run from the same image.

Common serving settings:

    --tp-size 1
    --dp-size 1
    --dtype bfloat16
    --kv-cache-dtype auto
    --context-length 16384
    --chunked-prefill-size 8192
    --max-running-requests 64
    --cuda-graph-max-bs-decode 64
    --mem-fraction-static 0.85

Benchmark settings:

- Random dataset with tokenized prompts and fixed input/output lengths: 1024/1024, 8192/128, 8192/1024.
- Concurrency: 1 (single request, the decode-latency case this PR targets).
- Requests per cell: 32.
- Eight warmup requests per cell.
- Request rate: unlimited.
- Random-length ratio: 1; seed: 42.
- Cache flushed before each cell.

At concurrency 1, `fa3` cuts TPOT by about 11 % and raises output throughput by 9–13 %; TTFT is unchanged.
