## Motivation

Transformers v5 may drop `add_bos_token` and `add_eos_token` settings when
loading a tokenizer backed by `tokenizer.json`. It assumes that the serialized
tokenizer post-processor already handles BOS/EOS insertion, but that is not true
for every tokenizer configuration.

SGLang already compensates for this behavior in `get_tokenizer()` by reading
`tokenizer_config.json`, restoring the supported flags, and rebuilding the
tokenizer post-processor.

SGLang has two related loading entry points:

- `get_tokenizer()` returns a tokenizer directly and is typically used by
  text-only loading paths.
- `get_processor()` returns a multimodal processor that owns a tokenizer in
  addition to image, audio, or other preprocessing components.

Both entry points ultimately tokenize the text portion of a request, so their
tokenizer compatibility behavior should be consistent. Before this change,
only the direct `get_tokenizer()` path applied the Transformers-v5 BOS/EOS
repair. The tokenizer embedded in a processor bypassed it.

This does not affect every model. The compatibility helper is limited to
tokenizer classes that supported these flags before Transformers v5, currently
including Llama, Code Llama, Gemma, and Cohere tokenizers. It is a no-op for
other tokenizer classes and for configurations whose values are already
correct.

Multimodal models commonly load the same tokenizer through `get_processor()`.
That path extracts the processor-owned tokenizer and applies several post-load
fixes, but it does not apply the existing BOS/EOS compatibility repair. The same
checkpoint can therefore tokenize a prompt differently depending on which
loading entry point is used. For affected Gemma tokenizers, the processor path
can omit the expected BOS token.

This change does not alter Transformers itself or introduce a new compatibility
policy. It applies SGLang's existing policy consistently to the tokenizer owned
by a processor.

## Modifications

- Apply the existing `_fix_v5_add_bos_eos_token()` helper to the final tokenizer
  selected by `get_processor()`.
- Keep the compatibility policy in one place rather than duplicating it in the
  processor loader.
- Add a CPU-only regression test that loads a local Gemma tokenizer
  configuration through the processor path and verifies that `add_bos_token`
  is restored and the tokenizer post-processor is rebuilt.

The helper already limits restoration to tokenizer classes that supported
these flags before Transformers v5. Unsupported tokenizer classes and
tokenizers with correct settings remain unchanged.
