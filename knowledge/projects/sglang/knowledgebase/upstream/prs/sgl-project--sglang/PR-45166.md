# [Feat] [NVIDIA] fp8: Add an H20-3e block-32 FP8 GEMM for DeepSeek-V4.1-Flash decode

## Motivation

DeepSeek-V4.1-Flash ships its dense weights in FP8 with a fixed `[32, 32]` quantization block, so every dense projection is a blockwise FP8 GEMM (Triton `w8a8_block_fp8_matmul_triton`, with a DeepGEMM fast path on Hopper). That Triton kernel tiles only M and N, never K. At decode-sized M the grid is almost empty: `M=1, N=1792, K=5120`, `BLOCK_M=16, BLOCK_N=32` gives `grid = (ceil(1/16)*ceil(1792/32), 1, 1) = (56, 1, 1)`, and each of those 56 CTAs walks the full K loop. H20-3e has 78 SMs, so most of the device idles and this GEMV sits in the mid-30 us range.

H20-3e has no MXFP8 hardware path, so the block-32 FP8 GEMM itself has to fill the GPU. Splitting K across CTAs fixes the occupancy. Baseline: **94.1 tok/s** aggregate decode at M=1 on 8x H20-3e, DeepSeek-V4.1-Flash, TP8/EP8.

## Modifications

- `python/sglang/kernels/jit/csrc/gemm/fp8_block32_sm90.cuh` — SM90 WGMMA block-[32, 32] FP8 GEMM. WGMMA atom K is 32; stock CUTLASS SM90 scales only after four atoms (K=128), this kernel multiplies the fp32 group scale after **every** atom, matching Triton.
  - One CTA owns 64 output rows x 8 tokens. `choose_split_k` returns the largest divisor of `k/32` that is `<= min(~8 grid-waves, k/128, k/32)`, so a split is always a multiple of the 32-element scale group and keeps >= 128 K elements.
  - Split-K partials are summed by a second reduce kernel.
  - Example `N=1792, K=5120, M=2`: 160 scale groups, 28 CTAs unsplit, target `ceil(78*8/28)=23`, largest divisor of 160 below 23 is 20 -> `grid (28, 20, 1)`, 560 CTAs at 256 K each.
  - A 64x128 variant (`fp8_block32_sm90_large`) exists for prefill-sized M; the serving dispatch caps at M <= 32, so the serving path uses only the 8-token split-K variant.
- `python/sglang/kernels/ops/gemm/fp8_block32_sm90.py` — JIT wrapper, `fp8_block32_gemm`, `_is_h20_3e` gate, `use_fp8_block32_gemm` eligibility check. `.../gemm/__init__.py` exports it.
- `python/sglang/srt/layers/quantization/fp8_utils.py`:
  - DeepGEMM fallback redirects to the new kernel at M <= 8.
  - Triton backend redirects to the new kernel at M <= 32.
  - Both require: NVIDIA H20-3e, batch-invariant mode off, `weight_scale.dtype == float32`, `output_dtype == bfloat16`, `block_size == [32, 32]`, `input_scale is None`. Everything else is unchanged.
- Tests: `test/registered/kernels/ops/gemm/test_fp8_block32_sm90.py` (vs Triton, M/K sweep, split-K path) and `test/registered/kernels/ops/quantization/test_fp8_block_gemm_configs.py` (dispatch coverage).

End-to-end (evalscope):

| Case | Output tok/s | Total tok/s | Avg TTFT ms | Avg TPOT ms |
|---|---|---|---|---|
| 1024->4096, p1 baseline | 92.95 | 22.65 | 197.39 | 10.71 |
| 1024->4096, p1 this PR | **105.66** (+13.7%) | **25.74** (+13.6%) | **193.71** (-1.9%) | **9.42** (-12.0%) |
| 32768->512, p1 baseline | 43.64 | 2790.73 | 6219.58 | 10.79 |
| 32768->512, p1 this PR | **46.24** (+6.0%) | **2956.76** (+5.9%) | **6220.73** (+0.0%) | **9.50** (-12.0%) |

| 32768->512, p30 this PR | **76.70** (+1.3%) | **4905.38** (+1.3%) | **94096.02** (-1.2%) | **207.61** (-1.4%) |

Single-stream improves most (decode TPOT ~-12%); at p=30 decode is bound elsewhere.

Profiling: NCU on `M=1, N=1792, K=5120` shows much higher compute utilization in the main kernel; the K split turns 56 serial CTAs into 560 CTAs (`grid (28,20,1)`, 256 K per split, ~8 waves on 78 SMs) and device time drops from the mid-30 us range to about **10 us**. The reduce kernel costs one fp32 pass over `split_k x M x N` and is not visible end-to-end.

Rejected alternative - Triton `SPLIT_K=16` (raises occupancy but is slower than this kernel and ~equal to baseline):

| M | Baseline | Triton `SPLIT_K=16` | This PR |
|---|---|---|---|
| 1 | 94.12 | 93.67 | 107.03 |
| 2 | 169.29 | 168.78 | 184.74 |
| 4 | 297.12 | 296.58 | 317.38 |
| 8 | 497.05 | 499.60 | 535.82 |
| 16 | 745.86 | 750.74 | 800.88 |

`SPLIT_K` only accepts powers of two, so it cannot land near 8 waves while dividing the 160 scale groups; `choose_split_k` picks 20. It also pays a full fp32 partials buffer plus a reduce without folding the group scale into the mainloop.
