# [Perf] [XPU] usp: Enable packed Ulysses QKV all-to-all

[Upstream PR](https://github.com/sgl-project/sglang/pull/39989) · state: closed · merged: True

## Original PR description

The packed-QKV input exchange was gated to CUDA by `is_cuda` checks in the relayout kernel and in both eligibility predicates, so XPU silently fell back to three separate collectives per attention layer and never populated the A2A staging cache.

Nothing on this path is CUDA-specific: the pack is an in-tree Triton kernel and the exchange is `all_to_all_single`. Relax those gates to a device-type set; "cuda" also covers ROCm, where `is_cuda` is True, so ROCm is unchanged.

Two CUDA-only calls on the same path had to move to `torch.get_device_module()`, which is exactly `torch.cuda` for a CUDA device:

- `_a2a_staging_buffer` called `torch.cuda.is_current_stream_capturing()`, which raises `RuntimeError: Tried to instantiate dummy base class` on an XPU-only build rather than returning False. It was unreachable only because the `device.type != "cuda"` test short-circuited ahead of it, so relaxing the device gate alone would have crashed.
- `drop_a2a_staging_buffers` guarded its synchronize on `torch.cuda.is_available()`, so on XPU it cleared the cache without waiting for collectives that may still be reading those buffers. Dormant until this change populated the cache on XPU. Its call site in `gpu_worker.py` already excludes only CPU/MPS and calls `torch.get_device_module().empty_cache()`.

Tests: resolve the accelerator once per module instead of hardcoding `device="cuda"`, so the six cases run on XPU as well; CUDA is probed first so a CUDA host keeps identical coverage. Add
`test_packed_path_issues_one_collective` -- the unpacked fallback is also bit-exact, so the equivalence test passes whether or not the packed path was selected, and only the collective count pins the device gate.
