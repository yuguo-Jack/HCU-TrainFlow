# [Perf] kvcache: Fuse ordinary FP8 KV stores with shared conversion

[Upstream PR](https://github.com/sgl-project/sglang/pull/31652) · state: open · merged: False

## Original PR description

## Motivation

With `--kv-cache-dtype fp8_e4m3`, ordinary MHA writes on main `4eb606b2a` still quantize eagerly in `MHATokenToKVPool.set_kv_buffer`: `div_` on K and V, two casts and then the store, which is five launches with scales and three without. #40785 fused this conversion into the prefix-valid commit kernel, and #30815 was closed after it, but ordinary `set_kv_buffer` FP8 stores were left on the eager path.

## Modifications

1. Extract the prefix-valid writer's conversion into `_quantize_kv_fp8`. Ordinary and prefix-valid writes share this helper, but not their indexing schedules.
2. Add `kvcache.store_cache_fp8` (Triton, registered for CUDA SM89+) and use it for ordinary dense NHD writes on CUDA SM89+. It handles independent K/V widths and token strides, host, None or scalar FP32 device scales, and the reserved padding slot zero. Tensor scales keep source-rounded division, and host scales keep reciprocal multiplication, as in #40785 and #42982.
3. Out-of-range slots still fail fast. The launch keeps Triton's `debug=True`, so the slot `tl.device_assert` raises, matching the always-on device `assert` in the `store_cache` JIT kernel (`kvcache.cuh:75`). The timings below include it.
4. Other layouts, DCP masks and unsupported dtypes or scale forms keep their existing writers. The base pool's eager E4M3 conversion now uses `saturate_to_fp8_range`, matching the prefix-valid overflow policy. This aligns the policy; it does not claim that every backend overflowed identically before.
5. Fused writes do not mutate K/V, but the fallbacks still may, so callers keep their defensive copies.
6. Tests: a kernel numerical test (`test/registered/kernels/ops/kvcache/test_store_cache_fp8.py`), a CI microbenchmark (`test/registered/kernels/benchmark/kvcache/bench_store_cache_fp8.py`), pool-level tests in `test_asymmetric_mha_pool.py`, and the registry capability check in `test_kernels_namespace.py`.

## Accuracy Tests

Rebased onto main `4eb606b2a` as `10f5f9f73`. Apart from the new kernel test and benchmark, the diff differs from the previous head `e42753125` only in a docstring reflow and keyword arguments at the two new call sites.

On `10f5f9f73`, on an RTX PRO 6000 Blackwell Max-Q (SM120) with Torch 2.14.1+cu130, Triton 3.8.0, Transformers 5.19.0, sglang-kernel 0.4.10 and FlashInfer 0.7.2:

```bash
python -m pytest -q \
  test/registered/kernels/ops/kvcache/test_store_cache_fp8.py \
  test/registered/unit/mem_cache/test_asymmetric_mha_pool.py \
  test/registered/unit/mem_cache/test_prefix_valid_fp8_pool.py \
  test/registered/kernels/ops/kvcache/test_prefix_valid_fp8.py \
  test/registered/unit/kernels/test_kernels_namespace.py
```

108 passed, none skipped: 6 in the new kernel test, 16 in the pool test, 7, 3 and 76. The kernel test compares the whole cache byte for byte, including untouched slots, against the shared eager oracle in `sglang.test.kernels.prefix_valid`. It covers BF16, FP16 and FP32 sources, padded token strides, int32 and int64 indices, host, device and absent scales, asymmetric widths, FP8 limits and NaN, every BF16 and FP16 bit pattern under host and device scales, skipping of slot zero, and empty indices.

On `e42753125` (main `7d4426990`), with the same kernel and pool code: real Qwen3-0.6B serving with FP8 KV and Triton attention, three serial prompts, 24 generated tokens each, in eager and CUDA graph modes. Baseline and candidate gave identical output tokens and text, with zero output-token logprob difference. Negative and upper-bound slots raised the device assertion. This is a bounded serving check, not a full model-accuracy evaluation or a batch-invariance claim. Physical SM89, Hopper and ROCm execution are untested locally.

## Speed Tests and Profiling

Kernel-level rows from the new benchmark on `10f5f9f73`, same RTX PRO 6000 (SM120), with no other process on the GPU when the job started (the device was not reserved):

```bash
python test/registered/kernels/benchmark/kvcache/bench_store_cache_fp8.py                     # full sweep
SGLANG_IS_IN_CI=1 python test/registered/kernels/benchmark/kvcache/bench_store_cache_fp8.py   # CI sweep
```

`marker.do_bench` replays CUDA graphs with a cold L2 and reports the median time per call. `eager` is main's writer (divide, cast, `store_cache`) and `fused` is `store_cache_fp8`. Both use BF16 sources, an E4M3 cache of 1M slots, and FP32 device scales (`tensor`) or no scales (`none`). The full sweep covers `num_kv_heads x head_dim` in {1x128, 2x128, 8x128, 8x64, 4x256} and batch sizes 1 to 16384 (powers of two).

| Shape | Scales | Batch | eager (us) | fused (us) | fused / eager |
| --- | --- | --- | --- | --- | --- |
| 8x128 | tensor | 1 | 11.22 | 2.54 | 0.226 |
| 8x128 | tensor | 16 | 11.84 | 2.77 | 0.234 |
| 8x128 | tensor | 256 | 12.33 | 3.17 | 0.257 |
| 8x128 | tensor | 4096 | 37.70 | 14.32 | 0.380 |
| 8x128 | tensor | 16384 | 178.56 | 58.82 | 0.329 |
| 8x128 | none | 1 | 5.00 | 2.33 | 0.467 |
| 8x128 | none | 16 | 5.43 | 2.54 | 0.468 |
| 8x128 | none | 256 | 6.08 | 2.97 | 0.488 |
| 8x128 | none | 4096 | 17.92 | 13.29 | 0.742 |
| 8x128 | none | 16384 | 64.18 | 55.13 | 0.859 |

Over the full sweep, the fused/eager geometric mean is 0.274 with tensor scales (75 rows, range 0.208 to 0.617) and 0.534 without scales (75 rows, range 0.439 to 0.958). The CI sweep (8x128, tensor scales, batch 16 and 4096) gives 0.240 and 0.382.

End to end on `e42753125`: unprofiled Qwen3-0.6B `Engine.generate`, FP8 KV and Triton attention, eager mode, overlap and radix cache off, serial requests, 48 generated tokens, ABBA source order with two boots per source. Median request latency was 629.35 -> 593.82 ms (short capital question) and 617.65 -> 597.39 ms (repeated gravity prompt), 3.3% to 5.6% lower, and all recorded output tokens matched. No device was reserved, and no general throughput or graph-mode serving claim is made.
