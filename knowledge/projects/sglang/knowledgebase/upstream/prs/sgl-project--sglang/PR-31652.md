# [Perf] Fuse ordinary FP8 KV stores with shared conversion

[Upstream PR](https://github.com/sgl-project/sglang/pull/31652) · state: open · merged: False

## Original PR description

## Motivation

Addresses the ordinary FP8 KV-store overhead in #30815. With `--kv-cache-dtype fp8_e4m3`, ordinary MHA writes perform separate scaling, conversion and storage operations: five launches with scales, three without.

This replaces the earlier C++ implementation with an ordinary scatter writer that shares the conversion policy accepted in #40785 and #42982. My previous claim that removing source-dtype rounding made the result "more accurate" was unsupported as a model-accuracy claim. It also did not preserve the accepted conversion contract. The replacement retains source rounding and preserves NaNs.

## Modifications

1. Extract the prefix writer's conversion into `_quantize_kv_fp8`. Ordinary and prefix-valid writes share this helper, not their different indexing schedules.
2. Fuse ordinary dense NHD writes on CUDA SM89+, including independent K/V widths and token strides, scalar FP32 device scales, padding slot zero and bounds errors. Tensor scales retain source-rounded division; host scales retain reciprocal multiplication.
3. Keep other layouts, DCP masks and unsupported forms on their existing writers. Base-pool eager E4M3 conversion uses the existing saturation helper to match the prefix overflow policy. This is explicit policy alignment, not a claim that every backend's previous overflow behavior was identical.
4. Keep caller defensive copies: eligible fused writes do not mutate inputs, but fallbacks still may. Register the hardware requirement and test fallback/layout ownership.

## Accuracy Tests

Candidate `e427531250d5048d885e078640236473730349d4`, tested against main `7d44269907e1e82be6bbab9277c0f1df78b852ea`. RTX PRO 6000 SM120, Torch 2.14.1+cu130, Transformers 5.19.0, sglang-kernel 0.4.9.

```bash
python -m pytest -q \
  test/registered/unit/mem_cache/test_asymmetric_mha_pool.py \
  test/registered/unit/mem_cache/test_prefix_valid_fp8_pool.py \
  test/registered/kernels/ops/kvcache/test_prefix_valid_fp8.py \
  test/registered/unit/kernels/test_kernels_namespace.py
```

103 tests and 168 subtests pass. Additional pool checks cover all 65,536 BF16/FP16 source bit patterns with None, host 0.1 and device 0.1 scales: no value/NaN mismatches against source-dtype division, saturation and conversion. Negative and upper-bound slots propagate device assertions.

Real Qwen3-0.6B serving with FP8 KV and Triton attention: three serial prompts, 24 generated tokens each, both eager and CUDA graph modes. Baseline and candidate have identical output tokens/text and zero output-token logprob difference. Each candidate trace contains 2,016 fused stores and 4,032 fewer GPU launches. An initial uncontrolled batched comparison diverged; it is not counted as equivalence evidence or a batch-invariance claim.

These are bounded numerical and serving checks, not a full model-accuracy evaluation. Physical SM89/Hopper and ROCm/FNUZ execution remain untested locally; mocked SM80 tests establish eligibility, not execution on that hardware. PageInterleave's separate writer is unchanged.

## Speed Tests and Profiling

Unprofiled Qwen3-0.6B `Engine.generate`, FP8/Triton, eager mode, overlap and radix cache off, serial requests, 48 generated tokens. ABBA source order, two independent boots per source, two warmups and six samples per prompt per boot. Existing caller copies and dispatch remain included. All recorded output token sequences match.

| Short capital question | 629.35 ms | 593.82 ms |
| Repeated gravity prompt | 617.65 ms | 597.39 ms |

Median request latency was 3.3–5.6% lower in these fixtures. Boot medians varied: short baseline 634.52/615.58 ms versus candidate 584.31/600.84 ms; long baseline 628.49/609.66 ms versus candidate 586.04/601.79 ms. No exclusive-device reservation or general throughput claim; no graph-mode serving latency win is claimed.

L2-rotated CUDA-graph pool measurements include two caller clones and GPU scalar scales, with five warmups and 100 replays using the repository benchmark marker. At width 1024, main/candidate GPU times were 9.73/3.99 us (B=1), 13.27/5.47 us (B=16), 14.40/6.31 us (B=256), and 51.98/24.67 us (B=4096). At B=4096 and width 4096: 199.87/99.82 us. These GPU timings exclude Python dispatch; the serving measurements above include it.
