# [sglang-miles] LoRA/MoE/KDA: decode fast paths for colocated LoRA RL rollout

[Upstream PR](https://github.com/sgl-project/sglang/pull/44617) · state: open · merged: False

## Original PR description

> Developed by the **CAKE team**. These opt-in decode paths make Kimi-K3 LoRA RL rollout **4.6× faster** (387 → 85 s per step, on 16×4 GB300, together with radixark/miles#4127), at matching accuracy.

- **Decode step is 2.8× faster:** 59.4 → 20.9 ms. Measured on one TP16 engine at batch 8 with an r16 adapter.
- **Accuracy is on par:**
  - Kernels are bit-equal or within 2 bf16 ulp of stock.
  - Over 10 end-to-end GRPO steps, the rollout/trainer KL averages 0.0033 in both arms.
  - AIME 2024 avg@16 is 0.500, against 0.510 stock.
- **Everything is opt-in:** each path is behind an `SGLANG_OPT_*` flag that defaults to off. With all flags off, the code runs the stock paths.

## Motivation
One Kimi-K3 decode step takes 63 ms on GB300. That is TP16 over 4 trays, MXFP4 MoE through Marlin, an r16 all-linear LoRA, batch 8. The time breaks down as:
- **41 % `_fused_moe_lora_kernel`.** It expands the shared LoRA A to all 896 experts and pads each expert to 64-row blocks.
- **22 % NCCL ring all-reduce.** Custom AR v2 refuses multi-node without a VMM allocator, and torch_memory_saver has none.
- **9 % Marlin.** It is instruction-bound at decode.
- **6 % LoRA launch chains.**

The weight sync also had problems. It stashed the whole streamed adapter on every TP rank (about 24 GB at r16), then installed experts one copy at a time, taking about 10 s per sync.

## Modifications
| `SGLANG_OPT_…` | change | batch-8 decode step |
|---|---|---|
| `LORA_SHARED_OUTER_MOE_DECODE` | Shared-A / shared-B MoE-LoRA decode: one shrink per token, then per-(token, expert) expand. Stock rounding points. | 59.4 → 41.3 ms |
| `CUSTOM_ALL_REDUCE_V2_ALLOW_NON_VMM` | Custom AR v2 across trays with a non-VMM allocator. The NVLink clique check is kept. | 41.3 → 28.1 ms |
| `LORA_DECODE_FUSED_LAUNCHES` | Split-K LoRA-A, fused shrink+expand, and LoRA-A on a side stream. | 28.1 → 24.0 ms (split-K); 23.8 → 21.7 ms (rest) |
| `LORA_ROW_PARALLEL_FUSED_ALL_REDUCE` | One all-reduce over [base \| lora_a] for row-parallel layers. | 24.0 → 23.8 ms |
| `MXFP4_MOE_DECODE_GEMM` | MXFP4 decode GEMM that reads Marlin-packed weights in place. | 23.8 → 22.1 ms |
| `K3_FUSED_KDA_DECODE_TP16` | Fused KDA decode at TP16 (6 local heads). | 22.1 → 20.9 ms |
| `LORA_FAST_STREAMED_LOAD` | TP-sharded stash and batched install for streamed MoE adapters. | sync 12.3 → 2.2 s; stash is 1/16 |

## Accuracy Tests
- **Kernel tests**, on GB300 at this head:

  | test | passed | what it checks |
  |---|---|---|
  | `test_shared_outer_moe_lora.py` | 18 | bit-equal to an fp64 reference that uses the stock rounding, m = 1..32 |
  | `test_lora_decode_fused.py` | 46 | fused paths bit-equal to the split-K chain; split-K within 2 ulp of stock |
  | `test_mxfp4_moe_decode_gemm.py` | 21 | within 2 ulp of Marlin on at least 99.998 % of outputs |
  | `test_kda_fused_decode_tp16.py` | 19 | within 2 ulp of the unfused chain on more than 99.9 % of outputs |
  | `test_lora_row_parallel_fused_all_reduce.py` | 3 + 3 | bit-equal on 2 and 4 GPUs |
  | `test_lora_fast_streamed_load.py`, plus the custom-AR capability and stream-update tests | 38 (CPU) | |

- **End to end** (Kimi-K3 LoRA GRPO, 10 steps, same prompts in both arms):

  | | flags on | stock |
  |---|---:|---:|
  | `train_rollout_kl` | 0.0020–0.0045 (mean 0.0033) | 0.0018–0.0043 (mean 0.0033) |
  | reward | 0.655 | 0.662 |

- **AIME 2024**, one TP16 engine, 16 samples per problem at T = 1.0, 480 samples per arm: 0.500 with the flags on, 0.510 stock. The difference is within the sampling noise, which is about ±0.03.

## Speed Tests and Profiling
- **End-to-end RL step**, on 16×4 GB300 over 10 rollouts:
  - Rollout drops from 387 to 85 s, and the whole step from 558 to 112 s, measured together with radixark/miles#4127.
  - That run also doubles the rollout concurrency, which the trainer-side changes make room for.
- **Decode step**: the per-flag numbers are in the table above. They come from the engine's decode-batch logs (one TP16 engine, rollout-only mode); the breakdown in Motivation is from a torch-profiler trace.
