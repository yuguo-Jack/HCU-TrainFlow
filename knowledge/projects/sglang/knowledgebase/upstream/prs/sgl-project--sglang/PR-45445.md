# [Fix] http_server: Make SageMaker /ping reflect server readiness

[Upstream PR](https://github.com/sgl-project/sglang/pull/45445) · state: closed · merged: True

## Original PR description

## Motivation

`GET /ping` (the SageMaker health check) returns a static 200, so SageMaker treats the container as healthy during warmup, after a failed PD warmup, and during SIGTERM drain. The AWS inference container contract says a 200 "indicates to SageMaker AI that the container is ready to accept inference requests", and recommends meaningful health checks over a static 200; the `/ping` request timeout is 2 seconds ([docs](https://docs.aws.amazon.com/sagemaker/latest/dg/your-algorithms-inference-code.html)).

## Modifications

- Add `TokenizerManager.is_healthy()`: not shutting down and `server_status == Up`. `is_ready()` becomes `not is_pause and is_healthy()`, and the gRPC `RuntimeHandle.health_check()` returns `is_healthy()`. Neither changes behavior (`ServerStatus` has three values, so `not in (Starting, UnHealthy)` equals `== Up`).
- `/ping` returns 200 with an empty body when `is_healthy()`, otherwise 503.
  - It stays an O(1) flag check. It is deliberately not an alias of `/health`: with the default `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=1`, `/health` runs a generation probe that takes 1-20s and mutates `server_status`, which does not fit the 2s timeout.
  - A paused server still answers 200, matching the gRPC `health_check`, so an intentional pause (e.g. a weight sync) does not get the instance replaced. `/ready` still returns 503 while paused.
- `checkpoint_engine/update.py` (package and example): `check_sglang_ready` treats a 503 from `/ping` as "listening". With `--checkpoint-engine-wait-weights-before-ready`, warmup waits on the weights these scripts push, so waiting for 200 would stall startup until `SGLANG_WAIT_WEIGHTS_READY_TIMEOUT`.
- Docs: `/ready` and `/ping` under Health Check; a SageMaker note on `ContainerStartupHealthCheckTimeoutInSeconds`.
- Tests: `/ping` for Up (200, empty body), paused (200), Starting, UnHealthy, and graceful exit (503).

**Behavior change:** `/ping` now returns 503 during warmup, during SIGTERM drain, and while `UnHealthy`. The HTTP server only starts listening after model load, so startup only grows by the warmup time.

**Known limitations (unchanged by this PR):**
- `UnHealthy` is set by a PD warmup failure or a `/health_generate` timeout and stays until a later `/health_generate` succeeds; this now also shows on `/ping` (documented).
- `/ping` is not exempt from `--api-key` auth (`utils/auth.py`); I plan a separate PR.
- Node ranks >= 1 keep the static dummy `/ping` (`utils/common.py`), which is what the checkpoint-engine script expects there.
- The Rust server has no `/ping`; see #41462.

- shijie-lyu · comment · 2026-10-21T06:24:21Z · [source](https://github.com/sgl-project/sglang/pull/45445#issuecomment-6309554635)

GPU end-to-end run on 1x NVIDIA L4 (g6.12xlarge), `Qwen/Qwen2.5-0.5B-Instruct`, default server args. Script: launch the server, poll `/ping` every 0.2s and log each status change, then start a 2000-token `/generate` request and send SIGTERM while it is in flight. `000` = connection refused (HTTP server not listening yet / exited).

**This PR (886ece207f)**
```
   0.01s /ping -> 000
  79.70s /ping -> 503
  88.61s /ping -> 200
  88.62s server: The server is fired up and ready to roll!
  89.63s sending SIGTERM
  89.64s /ping -> 503 (draining)
request http=200
 101.05s /ping -> 000 (draining)
 102.10s server exited
```

**Base main (f0b6590722)**
```
   0.01s /ping -> 000
  60.69s /ping -> 200          <- uvicorn up at 06:03:59; "fired up" logged at 06:05:24
  61.71s sending SIGTERM
  61.73s /ping -> 200 (draining)
request http=200
 156.22s /ping -> 000 (draining)
 157.27s server exited
```

- On main, `/ping` returned 200 as soon as uvicorn started, ~85s before warmup finished, and stayed 200 for the whole ~95s SIGTERM drain.
- With this PR, `/ping` is 503 from uvicorn start until warmup completes, flips to 200 at the "fired up" log line, and returns 503 within 10ms of SIGTERM. The in-flight request still completed (HTTP 200).
