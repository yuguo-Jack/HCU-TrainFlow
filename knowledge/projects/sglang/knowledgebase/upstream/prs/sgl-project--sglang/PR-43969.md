## Motivation

`write_through_selective` can lose a reusable prefix before HiCache copies it to host memory. This causes a large cache-hit and throughput regression under GPU KV-cache pressure.

#### Root cause

#41520's final PR body says that "`write_through_threshold` defaults to 1 for both write-through policies, keeping the first-finished-request backup timing of `write_through_selective`."

However, commit [21f8950063](https://github.com/sgl-project/sglang/commit/21f895006377868ed28ccbc65a877ac869e287dd) changed both initialization and runtime policy switching from threshold 1 to `1 if policy == "write_through" else 2`. The same commit replaced documentation saying that selective write-through backs up a prefix "once the first request using it finishes" with "after the access frequency exceeds a threshold." The merged implementation therefore gives `write_through_selective` threshold 2, which contradicts the final PR body.

The first finished request therefore raises a prefix to `hit_count == 1` without backing it up. If the GPU cache evicts that prefix before a second request finishes, the prefix never reaches host memory. In the Qwen3.5 AgentX concurrency-80 replay, host KV use fell to 32%, cache hit rate fell to 51%, and output rate fell to 646 token/s.

## Modifications

- Set `write_through_threshold` to 1 for both `write_through` and `write_through_selective` during HiCache initialization.
- Apply the same threshold when the write policy changes through runtime storage attachment.
- Keep the `write_back` threshold at 2.
- Add a CPU regression test for initialization and runtime policy switching.

- chuyeh · comment · 2026-10-13T03:48:32Z · [source](https://github.com/sgl-project/sglang/pull/43969#issuecomment-6137792053)

@hnyls2002 Can you help review this PR? This is a follow-up to #41520. I'd like to check which `write_through_selective` behavior you intended, because the merged code and the #41520 description seem to disagree.

**What I see**

- Before #41520, selective used threshold 2 and, as I read the old code, a request counted a node twice (prefill checkpoint + finish), so a prefix was backed up when the first request using it finished.
- #41520's description says threshold 1 for both write-through policies, "keeping the first-finished-request backup timing", and [fe542dc](https://github.com/sgl-project/sglang/commit/fe542dce8ba3a22eaa535c4102241de659c48d50) / [dfe5e08](https://github.com/sgl-project/sglang/commit/dfe5e0814fccb3930fbf0b696937c29e4aed4a7c) set exactly that.
- [21f8950](https://github.com/sgl-project/sglang/commit/21f895006377868ed28ccbc65a877ac869e287dd) then counted each node once per request (at its first insert, including checkpoints) and restored threshold 2 and the "hot data" docs.

Net effect on main: selective backs up a prefix only when a second request uses it. On Qwen3.5-397B-A17B-FP8 AgentX (TP4 MI355X, concurrency=80), most prefixes are evicted before that:

| | main (threshold 2) | this PR (threshold 1) |
|---|---:|---:|
| Output rate | 646 tok/s | 2,584 tok/s |
| Cache hit rate | 51% | 94% |
| Host KV use | 32% | 100% |

Under the new counting, threshold 1 backs up at the first insert, which is the same timing as `write_through`. So this PR makes the backup mechanism of two policies identical.

**Which behavior do you want for `write_through_selective`?**

1. Back up only on reuse (current main). Then I'll close this PR and switch our recipe to `write_through`.
2. Back up when the first request finishes (the #41520 description). Threshold 1 alone doesn't give that; selective would need to count hits only at the finishing insert. I can send that instead.
3. Same as `write_through`. Then this PR is enough.

Many thanks!
