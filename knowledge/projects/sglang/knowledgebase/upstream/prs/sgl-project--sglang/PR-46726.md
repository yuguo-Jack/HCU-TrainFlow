# [Feat] metrics: expose effective request capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/46726) · state: open · merged: False

## Original PR description

A hybrid model may cap `--max-running-requests 32` below the requested value because of its state-cache capacity. `/server_info` exposes that effective limit, but Prometheus has no matching capacity gauge for dashboards comparing running and queued requests.

Export `sglang:max_running_requests_effective` from the scheduler's final worker-provided limit at startup. Keep the existing rank labels and document how to select one TP/PP representative per DP worker before summing capacity.

This is the metrics portion of #38846. The API alias proposed in #38931 remains separate; admission and model execution are unchanged.

## Validation

Validated exact head `7ed56ff94704a9024a9c28cd73df1c4011eff4cb` through normal
SGLang package imports and a real single-GPU HTTP server on an NVIDIA L20
(TP=1), using cached Qwen3-0.6B configuration/tokenizer and dummy weights.

- Requested `--max-running-requests 32` with a 32-token KV pool, context 32,
  prefill chunk 16 and page size 1. The real worker reduced capacity to 16.
  The startup log and `/server_info` effective capacity both reported 16,
  while `/server_info` retained the requested value 32.
- `/metrics` exposed exactly one `sglang:max_running_requests_effective` sample
  with value 16 before and after a completed one-input/eight-output-token
  `/generate` request. Its labels were `model_name=Qwen/Qwen3-0.6B`,
  `engine_type=unified`, and TP/PP/MoE-EP ranks 0. No `dp_rank` label was emitted
  for this single-worker configuration.
- A fresh normal-package collector probe confirmed that omitting the optional
  value emits no false zero, then preserved supplied values 9/4 and all supplied
  labels, including `dp_rank=2`. No AST loading or import stubs were used.
  The earlier source-isolated Prometheus HTTP/multiprocess checks also remain
  applicable: both modified production files have unchanged hashes.

The serving fixture used Triton attention, the PyTorch sampler, disabled CUDA
graphs, and `--skip-server-warmup`; generation still ran through the real CUDA
model, allocator, scheduler and HTTP path. The startup background `/freeze_gc`
request logged a connection-refused exception before HTTP readiness. The server
subsequently became ready and passed the probe; this was not a warning-free run.

Not yet validated: a hybrid/Mamba state-cache cap, distributed TP/PP/DP
aggregation, the full registered MFU metrics test, CUDA graphs, trained-weight
quality or performance. This remains a draft pending the motivating hybrid case.
No throughput or latency improvement is claimed.

Prepared with Codex assistance.
