# [Feat] diffusion: abort queued rollout requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/44953) · state: open · merged: False

## Original PR description

## Motivation

RL trainers that use `/rollout/generate` (for example miles) oversample: they send more rollout requests than they need, and once enough groups pass their reward filter the rest are useless. Today there is no way to stop those requests, so the engine keeps generating them and the next rollout or weight sync waits behind work nobody will read.

This adds a way to abort rollout requests that are still queued.

## Modifications

- `POST /rollout/abort` takes `request_ids` or `abort_all`.
- `/rollout/generate` accepts an optional client `request_id`, so the client can refer to it later. It is limited to `[A-Za-z0-9_-]{1,128}` because the id can end up in file names (profiler traces).
- New `AbortReq` control message. It fans out to every replica, since the request may be queued on any of them.
- The scheduler handles `AbortReq` as soon as it is received instead of queueing it, so it does not wait behind the requests it cancels. Matching requests in `waiting_queue` are removed and each caller gets an `OutputBatch` with `error="Request aborted"`. Warmup requests are never aborted.
- An aborted rollout returns 499 instead of 500, so clients can tell it apart from a real failure.

## Limitations / follow-ups

- Only queued requests are aborted. A request already denoising runs to completion. Stopping it mid-loop would need a cancel flag checked per denoising step.
- The scheduler reads new messages between batches, and fan-out contacts replicas one after another, so under load an abort can wait for the current batch on each replica.
- `num_aborted` in the reply comes from the first replica only, because fan-out replies are merged by taking the first.
- Only the monolithic scheduler loop is wired. Disaggregated roles are not.

## Tests

New `test/unit/test_rollout_abort.py`:
- only matching ids are dropped, survivors keep FIFO order, and unknown ids are a no-op
- the abort never enters the queue
- `abort_all` spares warmup requests; a grouped request is matched by its first req
- `AbortReq` is in the fan-out list
- an aborted rollout maps to 499 and the client id reaches `build_sampling_params`
- unsafe request ids are rejected, and an abort with neither ids nor `abort_all` returns 400
