# [Perf] [AMD] dsv41: Shard the prefill indexer rows across TP ranks on HIP

[Upstream PR](https://github.com/sgl-project/sglang/pull/48147) · state: closed · merged: False

## Original PR description

## Motivation

In DeepSeek-V4.1 prefill, every TP rank runs the sparse-attention indexer (logits and top-k) for all rows of the chunk, so at TP4 three quarters of that work repeats on every rank. #42968 shards these rows across the TP ranks behind `SGLANG_OPT_DSV4_INDEXER_TP_SHARD`, but only in the CUDA backend (`deepseek_v4_backend.py` and `dsv4/v41_indexer`). The HIP backend's low-ratio indexer (`DeepseekV4HipRadixBackend._low_ratio_index_topk`, which calls `low_ratio_index_topk_hip_extend`) still scores every row on every rank. In our long-prompt benchmark on MI355X at TP4, the prefill indexer is about 8% of prefill kernel time.

This is a draft opened before the code, so the plan can be discussed first.

## Modifications

Planned (no code in this draft yet):

- Behind the same flag as #42968 (`SGLANG_OPT_DSV4_INDEXER_TP_SHARD`, off by default), the HIP prefill indexer scores `ceil(rows / tp)` rows on each rank and all-gathers the selected indices over the attention TP group, following #42968's `RowShard` and its minimum row count.
- Decode and verify steps are unchanged.

## Accuracy Tests

Not run yet. Plan: the selected top-k indices equal to the unsharded path for every layer kind, then GSM8K and long-context NIAH with the same server config, with and without the flag.

## Speed Tests and Profiling

Not run yet. Plan: indexer kernel time per prefill chunk, and long-prompt TTFT and output throughput at TP4 on MI355X, with and without speculative decoding.
