# [Perf] dsv41: Serve token-interleaved V4.1 KV caches with sgl-flash-mla

[Upstream PR](https://github.com/sgl-project/sglang/pull/45893) · state: closed · merged: True

## Original PR description

> (auto generated by Claude)

## Motivation

FlashMLA's 2026.09.30 V4.1 kernels read a token-interleaved KV cache and are faster at decode. They ship in the `sgl-flash-mla` wheel (release workflow #45651), which also carries every pre-release kernel sglang uses behind `use_legacy=True`. This moves all CUDA FlashMLA calls to that wheel and adds the interleaved layout as an opt-in, so existing deployments are unchanged.

Supersedes the serving side of #45635 (co-authored), keeping the block-split `v41` layout so gfx950 / aiter_sparse keeps working.

## Modifications

- New `SGLANG_DSV4_KV_LAYOUT=v41_new` (`KVLayout.V41_NEW` / `V41_FP4_NEW`): the V4.1 bytes interleaved per token, unpadded. `v41` keeps the block-split layout. Writers, dequant and the request-window copy address both through `row_addressing`; the PD layout string names the arrangement, so mismatched prefill / decode pairs are refused.
- `sglang.kernels.ops.attention.flash_mla_interface` wraps the wheel with the call signatures of the former `sgl_kernel.flash_mla` / `flash_mla_mega` ops. Old kernels default to `use_legacy=True`; only `V41_NEW` uses the current kernels. The V3/R1 dense, V3.2 DSA and DSv4 backends import from it; HIP / XPU keep their sgl-kernel ops.
- Decode skips the schedule precompute when the current kernel does not split the KV (`topk + extra_topk <= 640`).
- `KVLayout` properties are `functools.cached_property`.
- Adds `sgl-flash-mla` to the dependencies.

## Accuracy and speed

DeepSeek-V4.1-Flash, 4x B200, TP4 / EP4 / DSpark, sgl-eval with temperature 1.0 / top_p 0.95:

| | v41 | v41_new |
|---|---|---|
| gsm8k (1319) | 96.66 | 96.51 |
| ruler2 64K (240 x 3) | 86.31 / 87.03 (two servers) | 87.57 |
| decode TPOT, 8K in / 1K out, concurrency 16 | 2.50 / 2.46 ms | 2.41 / 2.35 ms |

Greedy ruler2 outputs agree as often across layouts (65.0%) as across two v41 servers (66.7%). On the same tokens the current and legacy V4.1 sparse decode kernels give bitwise-identical outputs.

Reviewed against the published `sgl-flash-mla` 1.0.0 wheel on GB300 (4 GPUs, nvcc 13.0 image, driver 13.1). Three commits pushed to the branch, no behaviour change in the first two.

**1. `test_flashmla_sched_meta.py` failed on the wheel, fixed in 45aeb50550.** Four `test_extra_cache_schedule` cases (fp4 extra cache, `topk + extra_topk > 640`) failed with the wheel while all 41 pass on main with sgl-kernel's FlashMLA on the same node. Cause: sgl-project/FlashMLA#12 (in 1.0.0) stopped the legacy scheduler reading one entry past `first_block_idx_shared` when filling the partitions after the last request, so their `begin_block_idx` is now 0 instead of the aliased `last_block_idx_shared[0]`; sglang's `flashmla_sched_meta.cuh` reproduced that read on purpose. Decode outputs are bitwise identical either way: old pin vs wheel with each kernel's own schedule across six shapes, and the wheel with the precomputed schedule in all six extra-cache test cases. The fix writes 0 for idle partitions and updates the boundary test's expectation; the file passes 41/41 on GB300 afterwards.

**2. Lint**: isort and ruff-format wanted changes in 13 files; pushed as ea11ee15ed and ce7fec3e02. The earlier runs' GPU failures were the fail-fast cascade from lint, not test failures.

**3. Title**: nothing under `python/sglang/kernels/aot` changes, so sgl-kernel still builds and ships `flashmla_ops`; sglang just stops importing it. "drop sgl-kernel's FlashMLA" should wait for the sgl-kernel follow-up, or the title should say "stop using".

Checked and fine: the HIP and XPU paths never import the wheel (`is_hip()` branches / `TYPE_CHECKING`); the wheel's `torch>=2.14.1` agrees with sglang's pin; `SPLIT_KV_MIN_TOPK = 641` matches the fork's `topk + extra_topk <= 640`; the default stays block-split `v41` so existing deployments are unchanged and `v41_new` is opt-in.
