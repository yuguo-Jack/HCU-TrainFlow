## Motivation

SGLang's optional Metal extension currently maintains custom logic for
C++/Metal compilation, nanobind linking, and library staging.

MLX 0.32.4 provides native `MetalExtension` and `BuildExtension` helpers.
Using them removes duplicated build logic while preserving the existing
`setup_metal.py install` entry point.

## Modifications

- Replace the custom extension builder with MLX's `MetalExtension` and
  `BuildExtension`.
- Require MLX >= 0.32.4 for building the optional Metal extension and ensure
  the required build dependencies are available.

## Accuracy Tests

Validated locally on Apple M4 with Python 3.12.13, MLX 0.32.4, and
nanobind 3.1.0.

- Built and installed the extension , and confirmed that the Metal library loaded successfully.
- Checked RoPE results, KV-cache writes, skipped negative slots, and
  untouched cache entries.
- All output arrays were bitwise identical to the previous custom
  builder's outputs.

File: `python/sglang/kernels/aot/setup_metal.py` · line 101

Yes. The explicit `-ffast-math` preserves the previous build's settings, the old direct `xcrun metal -O3` command enables fast math by default, while MLX's build helper explicitly adds `-fno-fast-math`. This flag overrides that setting.

I also checked this locally with Metal 32023.883, corresponding to Xcode 26.6 and also another metal compiler in Xcode 27. For this shader, the default settings, explicit `-ffast-math`, and `-fno-fast-math -ffast-math` all produced identical IR.

I checked the nanobind docs, and it says that the internal ABI versions must match for modules to share domains. However, nanobind’s internal ABI version is independent of its semantic version, meaning that multiple releases may share the same internal ABI version. Therefore, the easiest approach is to pin kernels' binding to the same version.
