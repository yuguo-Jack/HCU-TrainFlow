# [Perf] [AMD] diffusion: bound MIOpen find for the Conv2d VAE path

[Upstream PR](https://github.com/sgl-project/sglang/pull/46289) · state: open · merged: False

## Original PR description

### Motivation

`SGLANG_USE_ROCM_VAE_CONV2D` rewrites a 3x3x3 causal `Conv3d` as a temporal-unfolded
`Conv2d`: the temporal taps are folded into the channel dimension, so a 256-channel
kernel becomes `C_in = 768` at full frame resolution. Those shapes are new to MIOpen,
and MIOpen's default find mode enumerates **every** solver for each of them.

On gfx1151 (Radeon 8060S, MIOpen from ROCm 7.2.4) the cost lands entirely on the
first decode of a given (resolution, frame count):

| Wan2.2-TI2V-5B, 832x480 / 21 frames / 8 steps, `--vae-decode-precision bf16` | decode |
|---|---|
| Conv2d path, **cold cache** (fresh `MIOPEN_USER_DB_PATH`), default find | **1378.01 s** |
| Conv2d path, cold cache, `MIOPEN_FIND_MODE=FAST` | **34.2 s** |
| Conv2d path, warm cache, default find | 25.09 s |
| no rewrite (3D Conv3d, MIOpen naive fallback) | 200.19 s |

So the flag is a 8.0x win once warm, but a 6.9x **regression** on the first request of
a new shape — which is exactly what a user sees when they try the flag. Heuristics
cost ~1.4x of the steady state (34.2 vs 25.09 s) and remove the multi-minute stall.

The same effect reproduces on RDNA4 (gfx1201, 64 KiB LDS), reported in this
thread for Wan2.1-T2V-1.3B at 832x480 / 17 frames / 10 steps, each run in a
fresh container: the 3D path costs 444 + 161 s, the same rewrite under the
default find mode 216 + 5 s / 247 + 5 s, and under `FAST` 13 + 5 s / 6 + 5 s. The stall is
therefore a property of MIOpen's find on the unfolded Conv2d shapes, not of one
GPU family. (The two columns are `DecodingStage` plus the gap to the request
wall clock; the gap includes one-time startup and load.)

### Modifications

- `multimodal_gen/runtime/platforms/rocm.py`: in `optimize_vae`, when the Conv2d
  path is enabled and the user has not set `MIOPEN_FIND_MODE`, default it to `FAST`
  and log the reason. The user's own setting always wins.
- `docs/docs/sglang-diffusion/environment_variables.mdx`: document
  `SGLANG_USE_ROCM_VAE_CONV2D` and `SGLANG_USE_ROCM_VAE_CONV2D_BF16` (both were
  undocumented) and the find-mode interaction.
- `multimodal_gen/test/unit/test_rocm_vae_conv2d_rewrite.py`: the rewrite had no
  test. Pin the properties a "looks equivalent" edit would break: fold order,
  bias, temporal stride, the causal-cache front-pad offset, `skip_bias` /
  `residual` contracts, and that pointwise / grouped convs are skipped.

### Accuracy Tests

- The unit test compares `_conv3d_as_batched_conv2d` and the installed `forward`
  against `F.conv3d` on CPU tensors: `max |diff| <= 1e-5` (fp32) for all five cases.
  It runs on CUDA and ROCm CI (flat file under `multimodal_gen/test/unit/`, per
  `gpu_cases.py::_discover_unit_tests`).
- End to end, Wan2.2-TI2V-5B at 832x480 / 81 frames / 40 steps with the rewrite
  (plus bf16 decode and dense SDPA operands) matches the fp32-decode baseline at
  PSNR 34.96 dB / SSIM 0.9765 over the first 48 frames, i.e. the rewrite adds no
  measurable error beyond the precision change itself.

### Speed Tests and Profiling

`rocm/sgl-dev:v0.5.21-rocm724-gfx1151-20261008` (torch 2.9.1+rocm7.2.4, MIOpen
bundled), Ryzen AI Max+ 395 / Radeon 8060S (gfx1151), `SGLANG_DIFFUSION_SYNC_STAGE_PROFILING=1`,
seed 42. Cold and warm arms are separated with independent, empty
`MIOPEN_USER_DB_PATH` directories so the production cache is never touched.

| arm | decode | note |
|---|---|---|
| no rewrite | 200.19 s | MIOpen falls back to `naive_conv` for 3D NCDHW (0.1 TF) |
| rewrite, cold, default find | 1378.01 s | fresh cache dir; 23 min stall |
| rewrite, cold, `MIOPEN_FIND_MODE=FAST` | 34.2 s | this PR's default |
| rewrite, warm, default find | 25.09 s | best steady state |

A larger shape confirms the same picture. At 1280x704 / 121 frames, the rewrite
turns a decode that had not finished after 85 min on the 3D path into 266.77 s;
that run used a fresh `(C_in=768, 364x644)` shape, i.e. the find mode this PR
defaults was in effect on a cold cache.

The default is also observable in the log, before MIOpen is initialised:

```
[10-24 06:59:02] Set MIOPEN_FIND_MODE=FAST: MIOpen's full find costs minutes per new Conv2d VAE shape on the first decode
```

Profiled with SGLang's built-in torch profiler (`--profile-all-stages`): without the
rewrite, 78.5% of the decode is five calls of
`naive_conv_ab_nonpacked_fwd_ncdhw_ushort_double_ushort` (66 GFLOP/s = 0.2% of peak);
with it, the Conv2d path runs at 7.8-14 TF on the same shapes.

### Rebase re-test (2026-11-03)

Rebased onto `upstream/main` at `4709a3a24e` (head `72edb7d67b`); the diff is
unchanged (`+147 / -0` across 3 files). On gfx1151:

- `test_rocm_vae_conv2d_rewrite.py`: `5 passed` in 0.14 s.
- Cold-cache A/B with independent empty `MIOPEN_USER_DB_PATH` directories:
  default (this PR applies `FAST`) **20.84 s** vs forced
  `MIOPEN_FIND_MODE=NORMAL` **1378.14 s**, i.e. 66x. The `NORMAL` arm reproduces

reproduced exactly.

- Woody-Hu · comment · 2026-11-03T08:33:12Z · [source](https://github.com/sgl-project/sglang/pull/46289#issuecomment-6598996708)

Thanks — this is exactly the cross-part evidence I could not produce myself, and it
matches what I see on gfx1151. Two things I want to confirm and one correction to my
own earlier accounting:

**1. The stall is find, not kernel.** On gfx1151 (Radeon 8060S, MIOpen from ROCm
7.2.4), the Conv2d rewrite creates shapes MIOpen has never seen (`C_in` becomes
`Kt*C_in` at full frame resolution: a 256-channel 3x3x3 becomes `C_in=768`). With the
default find mode every new shape pays the full solver enumeration *once*. The FLOPs
of the winning solver are identical either way — the warm decode is unchanged — so
the multi-minute number is solver search, not a regression in the kernel itself.
Your Conv3d rows show the same mechanism from the other side: the 3D path never got a
fast solver at all, so FAST only moves it from ~605 s to ~250 s, while the rewrite
gets it to ~11-18 s.

**2. Your stage split is the right way to read it, and it also applies to my numbers.**
`SGLANG_DIFFUSION_SYNC_STAGE_PROFILING` is what makes `DecodingStage` drain the device
queue at its own exit. Without it, the queued kernels surface at whichever call blocks
next — here the tensor materialisation before `Output saved`, which is your steady
~161-169 s gap on the 3D path. So cold arms should be compared on the sum (stage +
remainder); with the flag set the whole decode lands in the stage line. That is what I
used for the numbers below, and it is why I keep quoting 1378 s vs 34.2 s on gfx1151
rather than the 948 s the stage timer alone reports for the default arm.

**3. Re-run after rebasing onto current `upstream/main`** (head moved from `d80b96b` to
`72edb7d67b`; only the three files of this PR, `+147/-0`):

- `multimodal_gen/test/unit/test_rocm_vae_conv2d_rewrite.py`: **5 passed in 0.14 s**
  (Python 3.12.3, pytest 9.0.3, torch 2.9.1+rocm7.2.4, gfx1151). Same result you got on
  gfx1201, and it confirms the ruff-format follow-up commit did not disturb the cases.
- pre-commit on the touched files: all hooks pass (ruff 0.15.1 / isort 7.0.0 /
  ruff-format / codespell / check-merge-conflict / detect-private-key / ...).
- Cold-cache A/B, fresh `MIOPEN_USER_DB_PATH` per arm, Wan2.2-TI2V-5B, 832x480 /
  21 frames / 8 steps, `--vae-decode-precision bf16`, `SGLANG_USE_ROCM_VAE_CONV2D=1`,
  `SGLANG_DIFFUSION_SYNC_STAGE_PROFILING=1`:

| arm | `MIOPEN_FIND_MODE` | `DecodingStage` | log evidence |
|---|---|---|---|
| this PR, env unset | set to `FAST` by `optimize_vae` | **20.84 s** | `Set MIOPEN_FIND_MODE=FAST: ...` printed before the pipeline starts |
| same rewrite, forced | `NORMAL` | **1378.14 s** | no such line (user setting wins) |

The unset arm is the behaviour change this PR introduces: nothing in the environment,
the default lands in the log before MIOpen initialises, and the first decode of a new
shape stays in seconds instead of minutes. The forced-`NORMAL` arm is the pre-PR
equivalent on the same container and shape — 66x slower, and it reproduces the 1378.01 s
I measured before the rebase to within 0.1 %, so the cliff survives the rebase
unchanged. Denoise (2.8879 vs 2.9238 s/step) and text encoding (12.76 vs 12.21 s) do not
move in a direction attributable to find mode: that path never calls the VAE
Conv2d, so no find-mode claim is made there. The two output videos are
bit-identical (same md5), so FAST changes solver selection only, not the result.

**4. FAST vs NORMAL, stated plainly.** FAST is not free: on a warm gfx1151 cache the
same decode was 25.09 s with the default find and 34.2 s with FAST (~1.36x). What it
buys is bounding the *first* decode of every new (resolution, frame count) from
~23 min to ~34 s. Because that trade is a preference, the patch only sets the default
when `MIOPEN_FIND_MODE` is absent — anyone who wants the steady-state best can export
`MIOPEN_FIND_MODE=NORMAL` (or whatever they use) and the environment wins untouched.
If maintainers would rather not touch process-wide env at all, the alternative is a
launcher-level default or a dedicated `SGLANG_ROCM_VAE_CONV2D_FIND_MODE`; say the word
and I will rework the patch that way.

**5. On denoise.** Agreed — I would not attribute anything there either. My 8-step
runs land at 2.89 / 2.92 s per step, and the find mode is not on that path.

The checks last ran on `d80b96b`; the rebased head `72edb7d67b` needs a fresh `run-ci`.
Nothing in the rebase touches the diff.
