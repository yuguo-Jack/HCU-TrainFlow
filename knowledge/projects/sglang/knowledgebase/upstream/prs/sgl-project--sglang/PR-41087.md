# [OpenAI] Forward request priority through /v1/responses

[Upstream PR](https://github.com/sgl-project/sglang/pull/41087) · state: open · merged: False

## Original PR description

## Motivation

`/v1/responses` accepts `priority` but never hands it to the engine, so with `--enable-priority-scheduling` every Responses request is scheduled as if it had none, whatever the client sent. Chat and completions already pass it through.

Fixes #41089.

## Modifications

- Pass `priority=request.priority` to the `GenerateReqInput` in `create_responses`.
- Default `ResponsesRequest.priority` to `None` instead of `0`, like the other request models. Otherwise every request without a priority would be sent at `0`, which skips `--default-priority-value` and gets aborted under `--abort-on-priority-when-disabled`.
- Keep the priority on the follow-up turns of built-in tool calls, and drop the `orig_priority - 1` that was computed there but never used. I didn't wire that `- 1` up: it comes from vLLM, where a lower value always runs first, but here the direction depends on `--schedule-low-priority-values-first`. Happy to do it in a follow-up if you want it.

`x-override-priority` still only applies to chat; I left that as is.

## Tests

Three unit tests in `test_serving_responses.py`: an explicit priority reaches the engine, an unset one stays `None`, and a tool-call follow-up keeps the request's priority. The first and the last fail on `main`, and the `None` one fails (`0 is not None`) if you only add the forwarding line without the default change.

All Responses unit tests pass locally (123 across the four test files) and `pre-commit` is clean on the changed files. No accuracy or speed impact: this only forwards request metadata.
