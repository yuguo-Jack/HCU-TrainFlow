# [Fix] [AMD] deterministic: Run block-FP8 linears through Triton on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/47412) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-deterministic-inference` on ROCm, block-scale FP8 checkpoints (Qwen3-FP8, Qwen3.8-FP8, DeepSeek FP8) are not deterministic: `--fp8-gemm-backend auto` runs their linears through AITER, which picks kernels and split-K settings by the number of tokens, so a request's result depends on its batch. On MI350X, Qwen3.8-27B-FP8 in deterministic mode gives 2 different outputs for 50 identical requests, up to 6 outputs per prompt in the prefix test, and identical logprobs in only 289 of 1,275 responses; Qwen3-8B-FP8 up to 5 per prompt.

SGLang's Triton block-FP8 GEMM uses one tile configuration per weight shape and no split-K, so its result for a row does not depend on the other rows. This PR selects it in deterministic mode on ROCm when the backend is `auto`, the same way deterministic mode already resolves other batch-dependent backends.

**Which models this affects.** Every block-scale FP8 checkpoint served on ROCm in deterministic mode: Qwen3.8-27B-FP8, Qwen3-8B-FP8 and Qwen3-30B-A3B-FP8 (tested below), and the DeepSeek FP8 family's dense linears. FP8 MoE experts need the companion change (`rocm-deterministic-fp8-moe-triton`).

## Modifications

- `arg_groups/overrides.py`: new post-process pass `_deterministic_rocm_fp8_gemm_backend`: with `--enable-deterministic-inference` on ROCm and `--fp8-gemm-backend auto`, resolve to `triton` (with a warning). An explicit backend is kept; normal mode and CUDA are unchanged.
- `arg_groups/attention_hook.py`: run the pass in `handle_deterministic_inference` next to the deterministic sampling pass.
- `test/registered/unit/test_model_overrides.py`: the pass (auto -> triton on HIP in deterministic mode; explicit choice, normal mode and CUDA unchanged) and a resolution-level test through `_construct` + `resolution_result` on a HIP platform.

## Accuracy Tests

MI350X (gfx950), ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`, deterministic mode (`--enable-deterministic-inference`) together with the other open MI350X deterministic-mode changes (the same in every run). Checks: `python3 -m sglang.test.test_deterministic` (`single`, `prefix`, `prefix --return-logprob`, `radix_cache`, 50 trials) plus a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response). GSM8K through sgl-eval, 1,319 questions, temperature 0.

| model, TP | before | with this PR |
| --- | --- | --- |
| Qwen3.8-27B-FP8, 1 | single 2, prefix up to 6 per prompt, bitwise logprobs 289 / 1,275 | every check passes on 3 / 3 fresh servers; GSM8K 95.98% (normal mode 95.83%) |
| Qwen3.8-27B-FP8, 4 | | every check passes; GSM8K 96.13% |
| Qwen3-8B-FP8, 1 | prefix up to 5 per prompt, prefix logprobs differ | every check passes on 3 / 3 fresh servers; GSM8K 93.18% (before 93.56%) |
| Qwen3-30B-A3B-FP8, 1 / 2 / 4 (with the FP8 MoE change) | single 19-21 | every check passes (2 / 2, 2 / 2, 1 / 1 servers); GSM8K 95.38% (TP1), 94.92% (TP2) |

The server logs `FP8 GEMM backend is set to triton for deterministic inference on ROCm.` and no flag is needed.

## Speed Tests and Profiling

Deterministic mode, `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-range-ratio 1.0 --request-rate inf`, 1k in / 1k out, output throughput before -> after:

| model, TP | before (not deterministic) | with this PR | normal mode |
| --- | --- | --- | --- |
| Qwen3-8B-FP8, 1 | 4,168 | 3,835 (-8.0%) | |
| Qwen3-30B-A3B-FP8, 2 (with the MoE change) | 8,035 | 6,792 (-15%) | 13,775 |
| Qwen3.8-27B-FP8, 1 | 3,024 | 2,017 (-33%) | 3,090 |

This is the cost of correct results: before this PR deterministic mode was faster but not deterministic for these checkpoints. Per GEMM, the Triton block-FP8 kernel is 1.3-2.9x the AITER path at 1,024+ rows on Qwen3.8-27B's shapes (e.g. gate_up 34,816 x 5,120 at 4,096 rows: 1,887 vs 667 us), which explains the larger cost on the dense 27B model. A faster batch-invariant FP8 GEMM (a fixed-configuration AITER/CK kernel) can replace it later without changing this switch. Normal mode is unchanged.
