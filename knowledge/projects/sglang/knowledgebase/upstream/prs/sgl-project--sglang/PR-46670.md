# [Perf] model_loader: Fault mmap'd safetensors views in on the CPU on integrated GPUs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46670) · state: open · merged: False

## Original PR description

## Motivation

On integrated GPUs (DGX Spark / GB10 and similar unified-memory parts) weight loading is dominated by the host-to-device copy itself: both safetensors iterators hand out mmap views, and a copy taken straight from an unmapped file-backed view pays its page faults inside the driver copy. Measured on a DGX Spark with the real shards of `nvidia/Llama-3.1-8B-Instruct-NVFP4` (1027 tensors, 5.61 GiB), fresh process per variant, page cache dropped before each:

| source of the copy | total | per tensor |
|---|---|---|
| mmap view (current iterators) | 34.3 s | 33 ms |
| mmap view, page cache pre-warmed | 33.6 s | 33 ms |
| `.clone()` of the view | 0.12 s | 0.12 ms |
| view with one byte per page touched first | 0.11 s | 0.11 ms |

The page cache does not matter; the cost is the fault-in during the copy. vLLM hit the same thing (vllm-project/vllm#58726) and fixed it by touching the pages before the copy (vllm-project/vllm#58868). On a smaller unified-memory laptop part the same checkpoint took 1882 s to load.

## Modifications

`_fault_in_mmap_view()` touches one byte per page of each `get_tensor` view before it is yielded, in both `safetensors_weights_iterator` and `buffered_multi_thread_safetensors_weights_iterator`, when the current CUDA device reports `is_integrated`. The pages stay file-backed and reclaimable, so no extra host memory is used; discrete GPUs are unchanged. `--weight-loader-disable-mmap` stays as a user knob (it reads each shard into anonymous memory: 3.99 s here, at +2.6 GB of transient host memory).

Complementary to #46128, which warms the page cache sequentially before the multi-thread loader maps a shard: that removes the 4 KiB-at-a-time read; this removes the fault-in during the copy, which the warm-cache row above shows is a separate cost.

## Accuracy Tests

No numerical change: the same tensors are yielded in the same order. The new unit test (`test/registered/unit/model_loader/test_fault_in_mmap_views.py`) forces the integrated-GPU gate on, checks that every page of a shard's mapping is resident after each yield (`/proc/self/smaps` Rss), and that the tensors are byte-identical; it also checks the helper is a no-op when the gate is off and accepts 0-d, empty, non-contiguous and bf16 tensors. CI has no integrated GPU, so this is the only coverage of the touch path.

## Speed Tests and Profiling

DGX Spark (GB10, CUDA 13), `nvidia/Llama-3.1-8B-Instruct-NVFP4`, `--quantization modelopt_fp4 --mem-fraction-static 0.5`, page cache dropped before each run, "Load weight" from the server log:

| | Load weight |
|---|---|
| main | 31.04 s / 30.62 s |
| this PR | **0.94 s** |
| `--weight-loader-disable-mmap` on main | 3.99 s (+2.6 GB host RAM) |
