# [Fix] [AMD] ci: Rebuild AITER when the image's AITER commit differs from the Dockerfile pin

[Upstream PR](https://github.com/sgl-project/sglang/pull/47374) · state: closed · merged: False

## Original PR description

## Motivation

When a change moves the gfx942/gfx950 AITER pin in `docker/rocm.Dockerfile`, CI jobs that run on an image built before that change still test the image's old AITER. `[CI-AITER-CHECK]` is supposed to catch this, but it never rebuilds.

The image reports a pip version like `v0.1.26.dev144+g285579b62.d20261027`. That never equals the full commit hash in `AITER_COMMIT_DEFAULT`, and the next branch (`dev` or `+g<hash>`) matches every image. So the job always logs "Dev/patched version detected → skipping rebuild".

Example: scheduled `pr-test-amd` run 38779037426, job 116574211696 (2026-10-15). The Dockerfile pin was `2bb549102`, the image had `+ge7d2453f2`, and the rebuild was skipped. Nothing else covers this: no workflow builds the image from the PR's Dockerfile, and `AITER_COMMIT_OVERRIDE` is only set by manual inputs.

## Modifications

All changes are in `scripts/ci/amd/amd_ci_install_dependency.sh` and apply only to gfx942/gfx950 images. gfx1250 keeps its current behavior and rebuild steps.

- **Decide:** take the short hash after `+g` and check whether the Dockerfile pin starts with it. If it does, skip. If not, rebuild, and log both commits and why. Dev versions without a hash are still left alone.
- **Rebuild the way the Dockerfile does:** clone and `checkout -f` the pin, apply the two v4 fp4 indexer `sed` fixes, update submodules and install `requirements.txt`, copy the ROCm/aiter#5195 `mla_v4` `.co` from the checkout, do the editable install with `GPU_ARCHS` set to the image's gfx arch, then apply the torch.Stream patch. The old rebuild path left out the `sed` fixes and the `.co`.
- **Kernels are not prebuilt.** The Dockerfile's `PREBUILD_KERNELS=1 build_ext` step took 7061s for gfx942-rocm1000 and 8082s for gfx950-rocm1000 in the 2026-10-29 image build (release-docker-amd-rocm10, jobs 123577549671 / 123577549656). That is longer than the AMD CI job timeouts, and each GPU job would repeat it. Kernels JIT-compile on first use instead, as in the old rebuild path. The comment and the log line say so.
- Log the installed AITER version and how long the rebuild took.

What the rebuild has to reproduce was checked on `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261022`:
1. `git status` in `/sgl-workspace/aiter` shows only three changes: `pa_mqa_logits_fp4_prefill.py` (the `sed`), `csrc/cpp_itfs/torch_utils.py` (the torch.Stream patch), and `hsa/gfx950/mla_v4/*.co`. The rebuild covers all three.
2. The container keeps the stage's environment: `GPU_ARCH=gfx950-rocm1000`, `GPU_ARCH_LIST=gfx950`, `BUILD_AITER_ALL=1`, `BUILD_LLVM=0`, `AITER_USE_SYSTEM_TRITON=1`, empty `SETUPTOOLS_SCM_PRETEND_VERSION`, and `PIP_CONSTRAINT=/etc/sglang/constraints/torch-rocm.txt`.
3. AITER's `requirements.txt` does not pin torch or triton. On the finished image, `pip install -r requirements.txt --dry-run` would only install PyYAML 6.0.3 and ninja 1.13.0, and `PIP_CONSTRAINT` also protects torch.

## Testing

On an MI355 machine, I ran the real image-detection and `[CI-AITER-CHECK]` sections of the script in a separate container:
- `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261028`: image AITER `g285579b62` matches the pin, so the rebuild is skipped (3s).
- `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261019`: image AITER `g2bb549102` differs from the pin `285579b62`, so AITER is rebuilt. The rebuild took **94s** and installed `0.1.26.dev144+g285579b62.d20261030`.
- After the rebuild, `op_tests/test_rmsnorm2d.py` passed. Its first run, including JIT compilation, took 60s on one GPU.

I also ran the decision block locally with sample versions for gfx942, gfx950 and gfx1250. gfx1250 with a different hash still skips, as before. `bash -n` passes, and the gfx1250/other rebuild block is byte-identical to `main`.
