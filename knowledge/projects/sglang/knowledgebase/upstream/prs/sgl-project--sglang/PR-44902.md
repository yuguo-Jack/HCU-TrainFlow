# [Fix] speculative: Count proposals from completed adaptive rounds

[Upstream PR](https://github.com/sgl-project/sglang/pull/44902) · state: open · merged: False

## Original PR description

## Motivation

With adaptive spec decoding, the verify width can change while a request is running. But proposed drafts are counted as `verify_count × width`: request metadata uses the width at startup, and scheduler logs use the current width. Both are wrong once the width changes. For example, 127 zero-step rounds on a server started with 2 steps are reported as 254 proposed drafts, which makes the acceptance rate meaningless.

## Changes

- Each completed `GenerationBatchResult` records the width it actually ran with, and each request adds up its proposed drafts from those.
- The total travels with token/string outputs and through multi-tokenizer routing. Scheduler log intervals add up the same way.
- A request with zero proposals now reports a null acceptance rate (native and OpenAI) instead of a made-up number. Scheduler logs keep their numeric 0.
- Accept-length semantics are unchanged, and nothing on the model or sampling path changes.

## Tests

The new `test_spec_proposal_accounting.py` covers a static width; 2→0→0→2; 127 zero-step rounds; a callback switching the config before the result settles; inactive and no-verify requests; UNO's output stride; and interval metrics. The related managers tests pass (40 in total).

I also ran it end-to-end on an H20 with Gemma-4-12B, on my Frozen-KV adaptive branch (#44914). For 115 requests, the reported proposal totals matched per-round snapshots exactly: 976 proposals over 3,453 rounds, including a 0→2 switch inside one request.

The fix isn't specific to Frozen-KV, so it also applies to adaptive under PP (#41801). cc @hnyls2002, since #23962 set up these counters.
