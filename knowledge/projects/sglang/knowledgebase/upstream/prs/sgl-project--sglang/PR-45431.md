# [Feat] rust-server: Let the launcher set the default max_new_tokens for /generate

[Upstream PR](https://github.com/sgl-project/sglang/pull/45431) · state: closed · merged: True

## Original PR description

## Motivation

A `/generate` request that omits `max_new_tokens` gets 128 tokens from the Rust frontend: the JSON schema bakes `SamplingParams`'s default in at deserialization, and nothing at launch time can change it. The Python `TokenizerManager` leaves the same default, but a launcher that subclasses `RustServer` (the way `_health_generate_headers` and `_resolve_multimodal` already let it) has no hook to pick a different default, for example "no limit" when `--context-length` is set, which the scheduler then clamps to the room the prompt leaves in the window.

## Modifications

- `ServerArgs.default_max_new_tokens: Option<i64>` (Rust) is the launch-time default for an omitted `max_new_tokens`. `/generate` merges `{"max_new_tokens": <default>}` beneath the request's own value and beneath `preferred_sampling_params`, with the same merge the preferred params already use, so the precedence is request value > preferred sampling params > launch default. `None` arrives as an explicit `null`, which the schema decodes as "no limit"; the frontend's input-plus-output 400 already skips a `null` cap, and the scheduler clamps it to the context window.
- `RustServer._default_max_new_tokens(scheduler)` returns `SamplingParams().max_new_tokens` (128) and is passed to `_build_server_args(..., default_max_new_tokens=...)`. Default behaviour is unchanged; a subclass may return `None` or another value.
- gRPC `Generate` is untouched: protobuf cannot express "no limit", so it keeps the schema default.

## Accuracy Tests

N/A: no model numerics change. An omitted `max_new_tokens` still asks for 128 tokens by default.

## Speed Tests and Profiling

N/A for speed: one JSON merge of a single key per `/generate` request, on the same path the preferred sampling params already take.

Tests run:

- `rust/`: `cargo fmt --all -- --check`, `cargo clippy --locked -p sglang-server --all-targets -- -D warnings`, and `cargo test --locked -p sglang-server`: 366 passed.
  - `omitted_max_new_tokens_takes_the_launch_default`: an omitted value takes the launch default (a number, or `None` = no limit); the preferred sampling params and the request's own value win over it.
  - `omitted_max_new_tokens_under_a_context_length_passes_a_near_limit_prompt`: with a `None` default, a 990-token prompt under a 1000-token window passes the frontend check untouched; a fixed 128 or an explicit 1000 is a 400.
- Python: `test/registered/unit/entrypoints/test_rust_server_dp_ports.py` and `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py` (the launch now passes `default_max_new_tokens=128`): 29 passed.
- Not run here: a live server. The default (128) is unchanged, so the end-to-end behaviour of an omitted `max_new_tokens` is what the existing CI already checks.
