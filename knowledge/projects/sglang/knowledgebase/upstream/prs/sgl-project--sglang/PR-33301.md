# [AMD] Enable DSpark speculative decoding on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/33301) · state: closed · merged: False

## Original PR description

## Motivation

DSpark block-diffusion speculative decoding was silently falling back to greedy decoding on AMD ROCm. The sampler kernels (`top_k_renorm_prob`, `top_k_top_p_sampling`, etc.) were only imported when `is_cuda() or is_musa()`, so on ROCm the import was skipped and DSpark produced greedy output with no error or warning.

## Modifications

`python/sglang/srt/speculative/dflash_utils.py`: Add `is_hip()` to the sampler kernel import guard so the kernels are loaded on ROCm.

## Accuracy Tests

DSpark accept rate and output quality on Kimi-K3 verified correct on MI355X (gfx950) after this fix. Previously accept rate was 0% (greedy fallback); after fix matches CUDA behavior with expected accept rates.

## Speed Tests and Profiling

N/A — correctness fix. DSpark throughput gains (~3x) now apply on ROCm identically to CUDA.

## Repro Steps

**Hardware:** AMD MI355X (gfx950), ROCm 7.x

- stefanskiasan · comment · 2026-08-12T17:35:48Z · [source](https://github.com/sgl-project/sglang/pull/33301#issuecomment-5270251673)

We can confirm this fix from production use. We have been running DSpark speculative decoding with Kimi-K3 on an 8x MI350X node (gfx950, TP8, `--speculative-dspark-block-size 4`, `--speculative-num-draft-tokens 5`) for several days, with the same `is_hip()` guard applied locally in `dflash_utils.py`. With the guard in place, accept length is ~2-5 depending on content/context length, and single-stream decode throughput improves accordingly — matching the CUDA behavior this PR describes. Without it, the silent greedy fallback is indeed invisible in logs, which made this painful to diagnose independently.

Two operational data points from production on ROCm that may be useful for reviewers:

- DSpark composes fine with TP8 + fp8 KV cache (`kv_cache_dtype=fp8_e4m3`) and full CUDA-graph decode on gfx950.
- Combining DSpark with MoE EP hits an unrelated per-rank mamba state pool sizing limit in the current tree, so DSpark+EP should not be considered covered by this PR's testing — TP-only is the well-trodden path.

Thanks for upstreaming this — it removes a nasty silent-fallback foot-gun.
