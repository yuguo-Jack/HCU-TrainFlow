# [DeepGEMM] Pre-compile FP8 einsum to avoid cold-start JIT stalls

[Upstream PR](https://github.com/sgl-project/sglang/pull/42821) · state: open · merged: False

## Original PR description

## Motivation

`deep_gemm.fp8_einsum` is the only DeepGEMM GEMM that SGLang calls directly instead of through `deep_gemm_wrapper`, so it bypasses `deep_gemm_execution_hook` and is never JIT pre-compiled at startup. Two call sites use it:

- DeepSeek-V4 attention output projection `wo_a` (`"bhr,hdr->bhd"`, recipe `(1, 1, 128)` on Blackwell, `(1, 128, 128)` on Hopper)
- Dots3 absorbed-MLA BMM (`_absorbed_bmm`, default recipe `(1, 128, 128)`)

On a cold DeepGEMM cache, the first request that needs each new einsum config therefore compiles it on the CPU mid-request, adding ~1.7 s to that request's TTFT on B200. With DeepSeek-V4-Pro (TP8, B200) a 30-min agentic trace replay showed 9–12 such TTFT spikes, all in the first ~10 minutes after server start; profiling one showed a 1.78 s GPU-idle gap inside the prefill step right before the first launch of the `wo_a` einsum kernel.

This is a warmup coverage / cold-start fix, in the same spirit as #26238 and #27986 (DSv4 MHC prenorm): every DeepGEMM kernel on the serving path should be compiled at startup, not on a user request. It does not change steady-state performance.

## Modifications

- `deep_gemm_wrapper/entrypoint.py`: new `einsum_bhr_hdr_bhd_f8f8bf16(lhs, rhs, out, recipe)` entrypoint that wraps `deep_gemm.fp8_einsum("bhr,hdr->bhd", ...)` in `deep_gemm_execution_hook`, like the other entrypoints.
- `deep_gemm_wrapper/compile_utils.py`:
  - new `DeepGemmKernelType.EINSUM_BHR_HDR_BHD_F8F8BF16` with a warmup executor that builds inputs from `(m, n, k, num_groups, recipe)` only, and its memory requirement;
  - `deep_gemm_execution_hook` takes an optional `recipe` that becomes part of the pre-compile key (the recipe selects the kernel). Existing kernel types do not pass it and behave as before.
- `models/deepseek_v4.py`, `models/dots3_common/modeling.py`: call the new entrypoint instead of `deep_gemm.fp8_einsum`. No other behavior change.
- Both models can select the FP8 einsum with JIT DeepGEMM disabled (`SGL_USE_DEEPGEMM_BMM` for Dots3, `SGLANG_OPT_FP8_WO_A_GEMM` for DSv4), where the wrapper never imports `deep_gemm`; the entrypoint then keeps the previous direct, un-warmed call.

The warmup stays lazy: it runs only for models that reach this entrypoint, once per `(shape, recipe)`, on the first rank of each node, and its cubins are cached in `SGLANG_DG_CACHE_DIR` like other DeepGEMM kernels, so warm-cache restarts pay ~nothing.

## Accuracy Tests

No numeric change: the call sites run the same `deep_gemm.fp8_einsum` with the same inputs and recipe. Verified on B200 that the entrypoint output is bitwise identical to a direct `deep_gemm.fp8_einsum` call for recipes `(1, 128, 128)` and `(1, 1, 128)`, that it pre-compiles once per `(shape, recipe)`, and that with `ENABLE_JIT_DEEPGEMM=False` (and no module-level `deep_gemm`) it falls back to the direct call without invoking the warmup.

## Speed Tests and Profiling

**Warmup coverage (B200, DSv4 `wo_a` shape G=2, N=1024, K=4096, recipe `(1, 1, 128)`, empty DeepGEMM cache).** First call at each serving size, using DSv4's own UE8M0 activation quantizer and transformed weight scales:
