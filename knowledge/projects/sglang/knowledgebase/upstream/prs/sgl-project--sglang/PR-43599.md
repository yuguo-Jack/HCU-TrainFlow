# [Spec] Kimi-K3 EAGLE3 MLA draft under DCP + HiCache: draft routing, aux capture, physical draft KV pools

[Upstream PR](https://github.com/sgl-project/sglang/pull/43599) · state: open · merged: False

## Original PR description

## Motivation

We wanted to run Kimi-K3 with the EAGLE3 MLA draft ([lightseekorg/kimi-k3-eagle3.1-mla](https://huggingface.co/lightseekorg/kimi-k3-eagle3.1-mla)) on a DCP + HiCache deployment. Main does not support EAGLE3 under DCP at all yet (there is no attention routing for the draft's verify / extend phases), so the first commit picks that routing from the `yanbo/pd-k3-rebase-0919` branch (602578ab49 by @yhyang201, co-author trailers kept) and adds the K3 override. Once it runs, the draft's KV pools have two real problems:

1. **The draft pools are 8x too big.** Under DCP the MLA draft only ever touches row `loc // dcp_size`, but both its device pool and its HiCache host copy are sized for the full logical token count. On TP8/DCP8 with `--hicache-size 100` that is 9.95 GiB of GPU memory and 27.84 GB of host memory per rank, and 7/8 of it can never be written.
2. **Restores from the host tier land in the wrong rows.** Under DCP the draft keeps each token's KV at row `loc // dcp_size`. The draft's host (HiCache) copy was built without that rule, so when a prefix is evicted to host and later restored to the GPU, the data is written back at the undivided `loc`, i.e. into the wrong rows. The draft then reads other tokens' KV while guessing, so its guesses get worse. The output text is still correct, because the target model checks every draft token and rejects the bad ones, but fewer draft tokens are accepted per step: accept length 2.06 -> 1.45 (slower decoding).

Fixing the pools alone is not enough to actually deploy this, so the series also includes the handful of smaller things we hit along the way: the right attention mode for EAGLE3 under DCP, the draft model's loader config, how a physical-row draft pool is transferred in PD, EAGLE3 aux capture when the prefill is pipelined (PP), two things that stop a TP1 pipelined K3 prefill from booting, and a KDA prefill routing fix for packed one-token batches (#43615, also proposed on its own in #43629).

## Modifications

1. **attention: run an EAGLE3 MLA draft under DCP and on a pipelined K3 prefill** (core routing from 602578ab49 on `yanbo/pd-k3-rebase-0919` by @yhyang201, plus the K3 override). `draft_extend_v2` joins the DCP MLA decode phase; cutedsl_mla gets a real draft prefill backend; trtllm_mla handles DCP for any dense draft window (fp8 KV on draft-extend too), refuses a padded window, and picks the cute-dsl runner for `64 < q_heads < 128` (a TP1 K3 stage) where trtllm-gen has no MLA decode kernel; the eager runner skips the prefill DCP gather for MLA target verify; the K3 override forces `speculative_attention_mode=decode` for EAGLE3 as for DSPARK. Unit test: EAGLE3 under DCP resolves to the decode mode.
2. **kimi_k3: EAGLE3 aux capture, including across pipeline stages** (port of 51010f6085 onto the current `residual_batch` / `attn_bank` forward). `capture_layer_ids` gives DSPARK and EAGLE3 one shared index set; on the bank path EAGLE3 snapshots the plain prefix stream while DSPARK keeps the AttnRes aggregate; captures are banked per PP stage and forwarded on the PP proxy; the validation hook admits EAGLE3 behind a PD prefill like DSPARK. Unit tests: id mapping, EAGLE3 bank path, PP proxy sizing.
3. **hicache/dcp: size the MLA draft KV pool and its host sidecar in physical rows.** `KVCacheConfigurator.draft_mla_rows_are_physical` names the case; `loc_space_scale` and the unified-allocator draft override keep physical rows; the host sidecar gets `dcp_size`/`dcp_rank` with a physical/physical ratio; the HiCache+DCP gate admits EAGLE3; `topk > 1` with an MLA draft under DCP raises. MHA drafts unchanged (`test_dcp_logical_capacity.py` fixture updated and asserts MLA-physical vs MHA-logical capacities).
4. **model loader: draft load format and the PP draft embedding re-open.** `--model-loader-extra-config` reaches the draft only when its resolved load format equals the target's; the PP draft embedding re-opens a runai_streamer target that is a local safetensors directory with AUTO and no extra config.
5. **disaggregation: transfer a DCP-collapsed MLA draft pool with the target's row mapping.** `KVCache.rows_are_dcp_collapsed` names the layout, the decode registers it (one trailing frame on the Mooncake and NIXL registration messages; absent means the old layout), and the DCP transfer plan maps a collapsed draft with the target's owner rows and a physical-page item length. Unit test.
6. **kda: keep packed one-token prefill batches off the FlashInfer recurrent kernel** (#43615; the same routing is proposed standalone in #43629). `num_tokens <= num_sequences` batches go to the Triton kernel; the tracked-state check asks the dispatcher with the same sequence count. GPU regression cases `(1,1)` / `(2,0)` with an FP32-state assertion.
7. **About the PP8 crashes we hit while testing.** On main 234ccba7f6 the PP8 prefill with a host tier kept dying at 32-48 concurrency with an `ack_load_queue.pop(0)` IndexError on one of the later stages: later stages pop as many HiCache load acks as PP0 reports complete, and one stage had issued one load fewer than PP0. The previous revision carried a small guard for this. The real cause turned out to be #41593: the waiting queue's prefix-recency refresh ran on a per-rank 0.5 s wall-clock timer, so PP stages refreshed at different moments, evicted different prefixes and then issued different host loads. #43479 (2026-10-11) made that refresh deterministic across ranks, and #38217 (2026-10-11) additionally makes every stage wait for its own load-back before reading KV. Checks: the crash itself is not a reliable yardstick on the old base (3/3 crashes one day, 0/2 on a re-run of the same ladder), so we counted, per PP stage, how many host loads each stage issued. With the refresh on, the stages disagreed within two rounds in every run; with it off (`SGLANG_ENABLE_WAITING_PREFIX_REFRESH=0`) there were zero mismatches across 13k requests, and a v0.5.21 build, which predates #41593, shows zero as well. On main e6072935, which has both fixes, the crash never reproduced in several hours of PP8 load, with or without the guard. So the guard is gone from this series, and every number below was measured on main e6072935 with this 6-commit series and no guard.

## Accuracy Tests

Setup: Kimi-K3 + kimi-k3-eagle3.1-mla on GB300, main e6072935 + this series, TP8 / DCP8, HiCache `--hicache-size 100`, EAGLE3 steps 3 / topk 1 / draft tokens 4; target via runai_streamer, draft via `auto`. Main cannot run EAGLE3 under DCP at all, so "before" here means: only commits 1, 2 and 4 applied (just enough to make it run, draft pools still sized the old way). "after" is the whole series.

How much smaller the draft pools get (per rank, DCP8):

| pool | before | after | change |
|---|---|---|---|
| draft device KV | 9,273,856 rows / 9.95 GiB | 1,159,232 rows / 1.24 GiB (= target rows) | 8x smaller, 8.7 GiB freed per GPU |
| draft host sidecar | 24,162,816 tokens / 27.84 GB | 3,020,352 tokens / 3.48 GB | 8x smaller, 24 GB host freed per rank |
| target device KV | 1,159,232 rows / 29.85 GiB | same | - |
| target host KV | 3,020,288 tokens / 83.50 GB | same | - |

Device numbers are from the PD decode on this base (before = r34 image, after = full series). The host sidecar "before" is from the previous base: on this base the "before" build does not get past the HiCache + DCP gate (commit 3 is what admits EAGLE3 there), so the row shows the old-base measurement, which is simply 8x the after.

Does the draft still work after a prefix comes back from the host tier? Same 15k-token document, first served cold, then again with its prefix still on the GPU ("device"), then pushed out to host by 69 other 17.6k prompts (1.2M tokens) and requested again so it is restored from host ("host", 14,848 cached tokens, `cache_source=host` in the metrics):

| | cold accept_length | device recall | host recall |
|---|---|---|---|
| after (this base) | 3.08 | 3.00 | **3.00** (same number of verify steps) |
| before (previous base, same kind of probe) | - | 2.06 | **1.45** |

The "before" row is on the previous base for the same reason as above (the before build cannot boot HiCache + DCP + EAGLE3 here). The point is the last column: before, a host restore cost a third of the accept length; after, host recall equals device recall.

DSpark (MHA draft) regression check with the same pool-sizing hunks: draft pools unchanged (5,513,216 device rows, 55.32 GB host per rank), no configurator assert.

PD disaggregation (EAS LLMGateway, sglang-mooncake, 1P1D, 2 nodes per role, decode DCP8 with the EAGLE3 draft, `--max-running-requests 16`), measured after a warm-up (the first request after boot pays Mooncake buffer and RDMA setup, 40-80 s). GSM8K: 100 questions, 8-shot, greedy, every record checked, 100/100 correct for every layout with EAGLE3 on both sides.

Accept lengths are the same within 0.2 across the layouts with EAGLE3 on both sides, so the DCP8 decode draft reads the KV that a TP8, TP4+PP2 or PP8 prefill transferred into the collapsed pool, and the PP prefill's cross-stage capture matches TP8. DCP8 costs nothing against plain TP8 in this context range (<= 17.6k) at batch <= 16. The mixed load saturates the decode at its 16-request limit; the PP8 prefill wins only when the prefill itself is the bottleneck (16 x 16k prompts: 38.7k vs 22.7k tok/s) and loses about 28% on the mixed load at the decode limit (569 vs 788 tok/s) because a single long prefill occupies the whole pipeline (single-stream TTFT 2.4x TP8, TTFT p50 3.5 s vs 1.4 s at 16 streams). A prefill without the draft leaves the decode draft with no prompt KV and no aux hidden state (accept 3.5 -> 2.0 on GSM8K, 2.6 -> 1.5 on 12k prompts) and does not prefill faster. Decode with attention DP does not fit K3's weights on a 288 GB GB300 (255.9 GB per GPU at attn-dp 8).

## Speed Tests and Profiling

No kernel changes. Per rank under DCP8 the series frees about 8.7 GiB of device memory and about 24 GB of host memory that the draft pools reserved but could never use.
