# [Feat] kimi_k3: Run the EAGLE3 MLA draft under DCP with a physical draft KV pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/43599) · state: open · merged: False

## Original PR description

## Motivation

We wanted to run Kimi-K3 with the EAGLE3 MLA draft ([lightseekorg/kimi-k3-eagle3.1-mla](https://huggingface.co/lightseekorg/kimi-k3-eagle3.1-mla)) on a DCP deployment. Main does not support EAGLE3 under DCP at all yet (there is no attention routing for the draft's verify / extend phases), so the first commit picks that routing from the `yanbo/pd-k3-rebase-0919` branch (602578ab49 by @yhyang201, co-author trailers kept) and adds the K3 override. Once it runs, the draft's device KV pool has a real problem:

**The draft device pool is 8x too big.** Under DCP the MLA draft only ever touches row `loc // dcp_size`, but its device pool is sized for the full logical token count. On TP8/DCP8 that is 9.95 GiB of GPU memory per rank, and 7/8 of it can never be written.

The matching HiCache fix (the draft's host sidecar, which also lacked the `loc // dcp_size` rule so host-tier restores landed in the wrong rows) is split out into #45731, a standalone PR on main. Until it lands, the HiCache + DCP gate keeps rejecting EAGLE3, so this PR never builds a host sidecar for a collapsed draft.

Fixing the pool alone is not enough to actually deploy this, so the series also includes the handful of smaller things we hit along the way: the right attention mode for EAGLE3 under DCP, the draft model's loader config, how a physical-row draft pool is transferred in PD, EAGLE3 aux capture when the prefill is pipelined (PP), and two things that stop a TP1 pipelined K3 prefill from booting.

## Modifications

1. **attention: run an EAGLE3 MLA draft under DCP and on a pipelined K3 prefill** (core routing from 602578ab49 on `yanbo/pd-k3-rebase-0919` by @yhyang201, plus the K3 override). `draft_extend_v2` joins the DCP MLA decode phase; cutedsl_mla gets a real draft prefill backend; trtllm_mla handles DCP for any dense draft window (fp8 KV on draft-extend too), refuses a padded window, and picks the cute-dsl runner for `64 < q_heads < 128` (a TP1 K3 stage) where trtllm-gen has no MLA decode kernel; the eager runner skips the prefill DCP gather for MLA target verify; the K3 override forces `speculative_attention_mode=decode` for EAGLE3 as for DSPARK. Unit test: EAGLE3 under DCP resolves to the decode mode.
2. **kimi_k3: EAGLE3 aux capture, including across pipeline stages** (port of 51010f6085 onto the current `residual_batch` / `attn_bank` forward). `capture_layer_ids` gives DSPARK and EAGLE3 one shared index set; on the bank path EAGLE3 snapshots the plain prefix stream while DSPARK keeps the AttnRes aggregate; captures are banked per PP stage and forwarded on the PP proxy; the validation hook admits EAGLE3 behind a PD prefill like DSPARK. Unit tests: id mapping, EAGLE3 bank path, PP proxy sizing.
3. **dcp: size the MLA draft KV pool in physical rows.** `KVCacheConfigurator.draft_mla_rows_are_physical` names the case; `loc_space_scale` and the unified-allocator draft override keep physical rows; `KVCache.rows_are_dcp_collapsed` marks the layout for the PD transfer (and for the HiCache sidecar in #45731); `topk > 1` with an MLA draft under DCP raises. MHA drafts unchanged (`test_dcp_logical_capacity.py` fixture updated and asserts MLA-physical vs MHA-logical capacities; `test_hicache_dcp_host_pool.py` covers `rows_are_dcp_collapsed`).
4. **model loader: draft load format and the PP draft embedding re-open.** `--model-loader-extra-config` reaches the draft only when its resolved load format equals the target's; the PP draft embedding re-opens a runai_streamer target that is a local safetensors directory with AUTO and no extra config.
5. **disaggregation: transfer a DCP-collapsed MLA draft pool with the target's row mapping.** `KVCache.rows_are_dcp_collapsed` names the layout, the decode registers it (one trailing frame on the Mooncake and NIXL registration messages; absent means the old layout), and the DCP transfer plan maps a collapsed draft with the target's owner rows and a physical-page item length. Unit test.
6. **About the PP8 crashes we hit while testing.** A PP8 prefill with a host tier on main 234ccba7f6 died at 32-48 concurrency with an `ack_load_queue.pop(0)` IndexError, because PP stages refreshed waiting-queue prefix recency on per-rank timers (#41593) and issued different host loads. #43479 and #38217 fix that on main, so this series carries no guard for it.

The KDA packed one-token prefill routing fix this series used to carry (#43615) landed separately as #45018 and is no longer part of this PR.

## Accuracy Tests

Setup: Kimi-K3 + kimi-k3-eagle3.1-mla on GB300, main e6072935 + the series at the time (these commits, the HiCache follow-up now split into #45731, plus the KDA routing fix now upstream as #45018), TP8 / DCP8, HiCache `--hicache-size 100`, EAGLE3 steps 3 / topk 1 / draft tokens 4; target via runai_streamer, draft via `auto`. Main cannot run EAGLE3 under DCP at all, so "before" here means: only commits 1, 2 and 4 applied (just enough to make it run, draft pool still sized the old way). "after" is the whole series.

How much smaller the draft device pool gets (per rank, DCP8):

|---|---|---|---|

PD disaggregation (measured with the full series including #45731; EAS LLMGateway, sglang-mooncake, 1P1D, 2 nodes per role, decode DCP8 with the EAGLE3 draft, `--max-running-requests 16`), measured after a warm-up (the first request after boot pays Mooncake buffer and RDMA setup, 40-80 s). Accept lengths are the same within 0.2 across the layouts with EAGLE3 on both sides, so the DCP8 decode draft reads the KV that a TP8, TP4+PP2 or PP8 prefill transferred into the collapsed pool, and the PP prefill's cross-stage capture matches TP8. DCP8 costs nothing against plain TP8 in this context range (<= 17.6k) at batch <= 16. The mixed load saturates the decode at its 16-request limit; the PP8 prefill wins only when the prefill itself is the bottleneck (16 x 16k prompts: 38.7k vs 22.7k tok/s) and loses about 28% on the mixed load at the decode limit (569 vs 788 tok/s) because a single long prefill occupies the whole pipeline (single-stream TTFT 2.4x TP8, TTFT p50 3.5 s vs 1.4 s at 16 streams). A prefill without the draft leaves the decode draft with no prompt KV and no aux hidden state (accept 3.5 -> 2.0 on GSM8K, 2.6 -> 1.5 on 12k prompts) and does not prefill faster. Decode with attention DP does not fit K3's weights on a 288 GB GB300 (255.9 GB per GPU at attn-dp 8).

## Speed Tests and Profiling

No kernel changes. Per rank under DCP8 this frees about 8.7 GiB of device memory that the draft pool reserved but could never use (the ~24 GB host-memory saving is in #45731).

[P1] Migrate or reject MoRI before shrinking the draft pool

This changes every eligible MLA DCP draft to physical pool and page sizes, but MoRI still uses the widened draft layout. Its registration schema has no collapsed-layout field, and `MoriKVManager.send_kvcache_dcp` in `disaggregation/mori/conn.py:1480` calls `build_dcp_token_transfer_plan` without `draft_rows_collapsed`, so it defaults to `False`. The DCP backend allowlist includes MoRI and the K3 DCP override permits aiter.

For physical page size 2, DCP size 4, rank 2, source pages `[5,2,11,4]`, destination page `[7]`, and 8 tokens, the actual MoRI plan call produces draft destination rows `[56,57,58,59,60,61,62,63]`; the collapsed plan requires `[14,15]`. With physical capacity 32, the old widened capacity 128 contained those indices, but the newly shrunk pool does not. Registration skips draft destination-width validation by passing `None` for those entries.

Please propagate the layout through MoRI's registration and existing transfer-plan API, as Mooncake/NIXL do, or reject this combination before allocation. I reproduced the mapping with the source-extracted call; real ROCm DMA behavior was not tested.
