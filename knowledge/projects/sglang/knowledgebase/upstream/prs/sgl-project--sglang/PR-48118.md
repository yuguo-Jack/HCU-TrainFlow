# [Perf] [AMD] gdn: Add an aiter backend for linear-chain target verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/48118) · state: open · merged: False

## Original PR description

## Motivation

With MTP (NEXTN), the GDN layers of Qwen3-Next / Qwen3.5 run `target_verify` on every verify step, not `decode`. On ROCm that step has only Triton kernels: the recurrence goes through `TritonGDNKernel.target_verify` (`fused_sigmoid_gating_delta_rule_update`) and the conv1d update through Triton `causal_conv1d_update`, and `--linear-attn-verify-backend` has no AMD option. aiter (main's ROCm pin `285579b6`) ships FlyDSL kernels written against SGLang's verify contract for both: `flydsl_gdr_mtp_sglang` (pool slot per request, per-draft snapshots into the intermediate buffer, `disable_state_update`) and `causal_conv1d_update_sglang_flydsl` (same signature as SGLang's `causal_conv1d_update`, including the deduplicated conv-window view).

## Modifications

- `--linear-attn-verify-backend aiter`: new `LinearAttnKernelBackend.AITER`. The default is unchanged (Triton).
- New `AiterGDNKernel` (`kernels/gdn_aiter.py`): linear-chain `target_verify` on `flydsl_gdr_mtp_sglang`, reading the q/k/v views in place (`supports_strided_target_verify_qkv`). Decode and extend stay on Triton, and tree verify (topk > 1) keeps going to the Triton kernel through the existing `tree_verify_kernel` route.
- `GDNKernelDispatcher` builds it only on ROCm with `SGLANG_USE_AITER=1` and raises otherwise; with this backend the verify conv1d update in `forward_extend` uses `causal_conv1d_update_sglang_flydsl`.
- `--enable-linear-replayssm-spec` replaces the recurrent verify with its own kernels, so combining it with `--linear-attn-verify-backend aiter` is rejected at startup. KDA models reject the value through the existing "Unsupported KDA verify backend" error.
- Tests: new `test/registered/attention/unittests/gdn/test_aiter.py` (AMD CI). `GDNAttentionCase` gains a `linear_attn_verify_backend` field so the attention unittest kit can run verify on a chosen backend.

## Accuracy Tests

MI355X (gfx950), torch 2.11.0+rocm10.0.0, sglang-kernel 0.4.10, aiter `285579b6`, `SGLANG_USE_AITER=1`, base is main `11d687870f`. Qwen3-Next-80B-A3B-Instruct-FP8, TP2, `--speculative-algorithm NEXTN --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.

**Unit tests.** `test_aiter.py` runs EAGLE chain, EAGLE tree, frozen_kv_mtp, dflash and ngram verify, eager and CUDA graph, against the kit's pure-PyTorch gated-delta reference, and checks that chain verify calls both aiter kernels and never the Triton recurrence. It fails on main (no `aiter` backend), and on deliberately broken copies of this PR each assertion fails where it should: dropping the conv routing fails the dispatch and kernel-call tests, dropping the `SGLANG_USE_AITER` or ReplaySSM checks fails the matching policy test, and `use_qk_l2norm=False` fails every chain case. `test_triton.py`, `test_torch_native.py`, `test_gdn_noncontiguous_stride.py` and `test_kda_helion_dispatcher.py` still pass.

**Kernel output** against the Triton kernels, Qwen3-Next TP2 shapes, 6 draft tokens, batch 1 to 128 including padded (`-1`) slots: recurrence output max abs diff 6.1e-5 (output magnitude ~0.06), per-draft intermediate state 3e-7 with an fp32 state and 2e-3 with a bf16 state, pool untouched by both. Conv output within one bf16 ulp; conv state and conv window identical.

**GSM8K** (`python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --max-tokens 4096`, 3 runs each):

| | main | This PR |
|---|---|---|
| Accuracy | 0.9642 / 0.9604 / 0.9635 (mean 0.9627) | 0.9604 / 0.9665 / 0.9642 (mean 0.9637) |

Per question, two main runs give the same verdict on 98.73% of questions and main vs this PR on 98.88%.

## Speed Tests and Profiling

Kernel time per call, CUDA graph, Qwen3-Next TP2 shapes (8 k heads, 16 v heads, K=V=128, conv dim 4096, width 4), 6 draft tokens, fp32 state:

| Batch | Recurrence Triton → aiter (µs) | Conv update Triton → aiter (µs) |
|---|---|---|
| 1 | 16.6 → 6.6 (2.54x) | 3.95 → 2.22 (1.78x) |
| 4 | 18.7 → 8.0 (2.33x) | 3.99 → 2.26 (1.77x) |
| 16 | 27.6 → 21.4 (1.29x) | 4.19 → 2.60 (1.61x) |
| 32 | 41.2 → 43.0 (0.96x) | 4.67 → 2.96 (1.58x) |
| 50 | 78.7 → 66.8 (1.18x) | 6.25 → 3.73 (1.68x) |
| 64 | 94.3 → 78.4 (1.20x) | 6.70 → 3.95 (1.69x) |

With a bf16 state the recurrence is 1.65x at batch 1, even at 32 and 0.89-0.93x at 50-64. At Qwen3.8-Flash-Next TP1 shapes (16 k heads, 48 v heads) it is 1.14-2.28x with an fp32 state and 0.94-1.48x with a bf16 state; the conv update is 1.6-1.8x in every case.

`python -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 1024 --random-output-len 1024 --random-range-ratio 1.0` (ShareGPT text), `--num-prompts` 4x the concurrency (32 at concurrency 1), same server args as above plus `--max-running-requests 64 --cuda-graph-max-bs-decode 64`. Blocks of 4 runs in the order main, PR, PR, main, a fresh server per block; the first run of each block is dropped and each block reports the median of runs 2-4. Main and PR are the means of their two blocks; noise is the second main block vs the first. Runs during which another tenant's job was active on the host's other GPUs are excluded, except at concurrency 1, where all four such runs are on the PR side and keeping them gives the smaller gain.

| Concurrency | Output throughput, main → PR (tok/s) | Median TPOT, main → PR (ms) | Noise, throughput / TPOT |
|---|---|---|---|
| 1 | 530 → 553 (+4.4%) | 1.48 → 1.41 (−4.8%) | 2.8% / 0.3% |
| 16 | 3224 → 3321 (+3.0%) | 3.72 → 3.60 (−3.3%) | 3.8% / 1.2% |
| 32 | 4577 → 4723 (+3.2%) | 5.38 → 5.20 (−3.3%) | 0.1% / 0.4% |
| 50 | 5473 → 5567 (+1.7%) | 7.14 → 6.95 (−2.7%) | 0.8% / 0.7% |
| 64 | 6155 → 6388 (+3.8%) | 8.18 → 7.85 (−4.1%) | 1.9% / 1.5% |

Median TTFT moves by at most 2% except at concurrency 32 (148 → 124 ms); accept length is 4.30-4.42 in every block of both builds. By the kernel table, the two kernels save ~19 µs per GDN layer at batch 64, 0.7 ms per verify step over the 36 GDN layers.
