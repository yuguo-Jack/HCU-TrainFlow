# [Fix] scheduler: Do not request input logprobs again when re-prefilling a retracted request

[Upstream PR](https://github.com/sgl-project/sglang/pull/47298) · state: open · merged: False

## Original PR description

## Motivation

A retracted request asks its re-prefill for input logprobs it already has.

A `return_logprob=True` request without `logprob_start_len` (output logprobs only, the default RL rollout shape) gets `logprob_start_len = len(origin_input_ids)` at intake, so its first prefill scores no input positions. When the request is retracted (KV pool full in `retract_decode`, or `pause_generation(mode="retract")` during a weight sync), it re-prefills prompt + generated tokens. `logprob_start_len` still points at the prompt end, so `compute_extend_logprob_start_len` asks for input logprobs over every generated token:

- The logits processor computes full-vocab logits for those rows (`extend_return_logprob` becomes True).
- Their target ids are padding (0), because `extend_input_logprob_token_ids` reads only `origin_input_ids`.
- `add_input_logprob_return_values` then drops them ("The input logprob has been already computed. It only happens upon retract."). The output logprobs already returned stay on the req and are never recomputed.

So the work is pure waste, and it grows with response length (e.g. ~3.5k generated tokens × vocab per retracted RL sample). On a backend that cannot serve input logprobs, the request is fatal: on sglang-torchtpu the compiled forward rejects it, and every retraction under `return_logprob` traffic killed the engine (fixed there in sgl-project/sglang-torchtpu#1836).

## Modifications

- `compute_extend_logprob_start_len` takes `input_logprobs_finalized`. When the req's input logprobs are already finalized (`req.logprob.input_token_logprobs_val is not None`, the same marker `add_input_logprob_return_values` uses), it returns `extend_len`, so no input positions are requested.
- The per-request target ids move into `compute_extend_input_logprob_token_ids`, which returns exactly one id per requested row. A finalized request therefore adds no ids, and the batch's flat `extend_input_logprob_token_ids` stays aligned. Without this, a retracted request that asked for prompt logprobs (`logprob_start_len=0`) would add ids for rows nobody computes and shift the targets of every later request in the batch. Requests that do score input positions get the same ids as before.
- A request retracted mid-prompt (a chunked prefill with prompt logprobs not yet finalized) still computes them.
- New unit test `test/registered/unit/managers/test_retract_input_logprobs.py` covers an output-only retracted request, a retracted prompt-logprob request, and a request retracted mid-prompt.

## Accuracy Tests

No change to returned values; the removed rows were discarded. On H200 with Qwen3-4B (`sglang-miles` 6136e6d, same code), stock vs patched engines side by side, 64 × 1024-token greedy `return_logprob` requests:

| Scenario | Stock | Patched |
|---|---|---|
| `SGLANG_TEST_RETRACT=1` (forced `retract_decode`), 2 runs | 113 retractions, 0 errors | 113 retractions, 0 errors |
| `pause_generation(retract)` + `flush_cache`, 8 pauses | 0 errors | 0 errors |

Every response had all 1024 output logprobs, finite. Stock vs patched greedy sequences agree at the same rate as patched vs a rerun of itself (10/64 vs 8/64 identical with retract pauses; 52/64 without retraction), i.e. within run-to-run nondeterminism.

Prompt-logprob alignment (H200, `sglang-miles` with the same change, Qwen3-4B, 96 staggered greedy requests, half with `logprob_start_len=0`, `SGLANG_TEST_RETRACT=1`, ~350 retractions): all 48 prompt-logprob requests returned input logprobs identical to a no-retraction reference (max diff 0.0). With the row-count check removed, 1 of 48 came back with wrong input logprobs (off by up to 0.12) and no error.

Unit tests: `test/registered/unit/managers/test_retract_input_logprobs.py` (CPU) fails on main. Removing either the finalized check or the empty-list return fails the case that guards it. The rest of `test/registered/unit/managers/` shows the same results with and without the fix. (Two failures and two collection errors are the same in both runs; they come from the devbox environment.)

## Speed Tests and Profiling

Requests that are never retracted take the same path as before. On H200 at these lengths the removed logits were within noise (forced retraction: 8.8–9.5k vs 9.2–9.5k tok/s). The saving scales with generated length per retracted request.
