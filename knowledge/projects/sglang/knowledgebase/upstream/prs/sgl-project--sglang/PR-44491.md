# [Perf] qwen3: Fuse SiLU*mul with the NVFP4 quantization of down_proj in Qwen2MLP

## Motivation

Qwen3.5's dense MLP runs SiLU*mul and the NVFP4 quantization of the down_proj input as one FlashInfer kernel. Qwen3 uses `Qwen2MLP`, which lacks that path, so its NVFP4 W4A4 MLPs write the activation in 16 bits (`act_and_mul`) and read it back (`fp4_quantize`).

## Modifications

- Move the fused call and its enabling check from `Qwen2MoeMLP` / `qwen3_5.py` to `models/utils.py` and give `Qwen2MLP` the same branch, enabled only by `Qwen3DecoderLayer` when both projections use ModelOpt NVFP4 W4A4. Other `Qwen2MLP` users are unchanged.
- Keep it off for NVFP4 AWQ, whose `pre_quant_scale` the fused kernel skips (#38864 adds the same check to the Qwen3.5 copy), and, per forward, under sequence parallelism or with a LoRA-wrapped down_proj, which read the activation tensor (as `DualGemm.can_run` does). Without the LoRA check, a Qwen3 NVFP4 server with a down_proj adapter fails at startup.
- CPU unit tests for the three gates.

## Accuracy Tests

- The fused FP4 data and block scales are bit-identical to the two-kernel path (M = 128 to 40960, intermediate size 9728).
- `Qwen3-Embedding-4B` NVFP4 on 60 questions each of Ko-StrategyQA / MIRACL-ko: Recall@10 0.876 / 0.767 and the distance to BF16 scores are identical to main.
- `Qwen3-Reranker-4B` NVFP4 as a causal LM (CUDA graphs on), and `Qwen3-Reranker-0.6B` NVFP4 with a down_proj LoRA adapter: greedy outputs match main.
- `test_qwen3_5_modelopt_fp4.py`: 12 passed.

## Speed Tests and Profiling

| 320 tokens | 455.6 ms | **419.0 ms** (-8.0%) |
