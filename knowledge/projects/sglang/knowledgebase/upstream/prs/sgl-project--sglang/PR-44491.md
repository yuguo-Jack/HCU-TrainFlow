# [Perf] qwen3: Fuse SiLU*mul with the NVFP4 quantization of down_proj in Qwen2MLP

## Motivation

Qwen3.5's dense MLP runs SiLU*mul and the NVFP4 quantization of the down_proj input as one FlashInfer kernel. Qwen3 uses `Qwen2MLP`, which lacks that path, so its NVFP4 W4A4 MLPs write the activation in 16 bits (`act_and_mul`) and read it back (`fp4_quantize`).

## Modifications

- Move the fused call and its enabling check from `Qwen2MoeMLP` / `qwen3_5.py` to `models/utils.py` and give `Qwen2MLP` the same branch, enabled only by `Qwen3DecoderLayer` when both projections use ModelOpt NVFP4 W4A4. Other `Qwen2MLP` users are unchanged.
- Keep it off where down_proj cannot use the fused output. Qwen3.5's dense MLP shares these checks, so it gets them too.
  - NVFP4 AWQ: the fused kernel skips `pre_quant_scale` (#38864 adds the same check to the Qwen3.5 copy).
  - The Marlin FP4 GEMM backend, the default on SM80-SM90: it takes a floating-point input.
  - A down_proj K that is not a multiple of 64: the fused kernel leaves the padded scale columns unwritten.
  - Per forward, sequence parallelism or a LoRA-wrapped down_proj: both read the activation tensor (as `DualGemm.can_run` does). Without the LoRA check, a Qwen3 NVFP4 server with a down_proj adapter fails at startup.
- CPU unit tests for each gate, and that the fusion turns on for W4A4.

## Accuracy Tests

- The fused FP4 data and block scales are bit-identical to the two-kernel path (M = 128 to 40960, intermediate size 9728).
- `Qwen3-Embedding-4B` NVFP4 on 60 questions each of Ko-StrategyQA / MIRACL-ko: Recall@10 0.876 / 0.767 and the distance to BF16 scores are identical to main.
- `Qwen3-Reranker-4B` NVFP4 as a causal LM (CUDA graphs on), and `Qwen3-Reranker-0.6B` NVFP4 with a down_proj LoRA adapter: greedy outputs match main.
- On an L4 (SM89, `auto` picks Marlin), greedy outputs and logprobs match main (`Qwen3-Reranker` 0.6B and 4B NVFP4).
- `test_qwen3_5_modelopt_fp4.py`: 15 passed.

While re-checking the handoff I found one more case. When down_proj's K is not a multiple of 64, the FP4 scales are padded, and the fused kernel leaves the padding unwritten (fp4_quantize zeroes it). In a kernel test with K = 1376 and 608, a NaN byte left there turned the whole GEMM output into NaN. 47dcb3e4 keeps the fusion off for such K; every Qwen3 size at TP <= 8 is a multiple of 64. 8b512342 moves the kill switch into `Envs` and logs the enable message once.
