# [DeepSeek V4.1] Support SM120 candidate fallback and extra KV pages

[Upstream PR](https://github.com/sgl-project/sglang/pull/39914) · state: open · merged: False

## Original PR description

## Summary

- restore a dense Torch candidate-block fallback when the sparse DeepGEMM kernel is unavailable (notably SM120)
- keep the SM100 DeepGEMM sparse fast path for block size 8
- split the extra SM120 KV cache into 64-token pages with an independent grow-only buffer for both prefill and decode

## Why

The candidate-indexer API can be present on SM120 even though the underlying sparse DeepGEMM attention kernel rejects non-SM100 devices (`attention.hpp:301: device.get_arch_major() == 10`). After falling back to dense paged logits, long-input prefill then exposed a second mismatch: the primary cache was split to page size 64, while the extra cache stayed at page size 128 and FlashInfer rejected the configuration.

## Validation

- `python test/registered/unit/layers/attention/test_dsv41_candidate_torch.py` (4 passed)
- `python test/registered/unit/test_flashinfer_sparse_mla.py` (5 passed)
- Ruff 0.15.1 selected checks and format check passed
- Pro5000 / SM120 runtime: DeepSeek-V4.1-Flash completed 80/80 requests at 32768 input tokens after these fixes; a short generation also returned coherent output

### Where it stands against `main`

Checked at 40a64e1b5. The PR is CONFLICTING, and not only from line drift: `python/sglang/srt/layers/attention/dsv4/candidate_indexer.py` no longer exists — #41125 moved this code into `dsv4/v41_indexer/` — and three of the six names `candidate_torch.py` imports have no definition anywhere in the tree now (`IndexerInputs`, `CandidateMasks`, `mask_topk_scores`; the two backends now speak `publish_prefill` / `consume_prefill` / `publish_decode` / `consume_decode` over `PrefillInputs` and `DecodeInputs`, types.py:153 and :163). The `flash_mla_sm120.py` half does still apply, offsets aside, which matches what @bhavicp wrote on 30 Sep.

The failure itself is live and the chain is unchanged. `is_sm100_or_newer()` is `capability[0] >= 10` (`v41_indexer/__init__.py:45-48`), so SM120 enters the candidate path; `DEEPGEMM_PAGED_SPARSE_MQA_LOGITS` short-circuits on `DEEPGEMM_BLACKWELL = ENABLE_JIT_DEEPGEMM and get_platform().is_sm100` before it ever probes for the symbols (`deep_gemm_wrapper/configurer.py:57` and `:64-78`), so `__init__.py:108-112` raises.

On our host that raise sits on the default startup path rather than behind an opt-in: the V4.1-Flash checkpoint carries `candidate_topk_blocks=2048` and `candidate_block_size=8` in `text_config`, and neither has a CLI or env override, so all eight TP ranks fail in attention-backend init. We hit it on 26 Oct and reproduced it on a clean tree on 28 Oct, so I do not think the gate needs more argument.

### Why I would not carry the new indexer file

`make_candidate_indexer` already constructs the dense backend before it consults the gate and already returns `(dense_blocks, dense_blocks)` for the non-SM100 case (`__init__.py:92-102`). Replacing the raise with that return is about four lines and gives the semantics you describe, and the torch scoring you wrote into `candidate_torch.py` already exists inside `DenseBlocksBackend` (`_torch_publish_prefill` / `_torch_consume_prefill`, dense_blocks.py:187 and :218). Two PRs opened after yours do exactly this: #42371 (+47, on four GB10/SM121 nodes) and mine, #47209 (+9/-2, on this same 8xRTX PRO 5000) — disclosing that because it is a conflict of interest in a review like this one.

If you keep a separate torch indexer, one defect to fix on rebase: `_scores` passes `metadata.deep_gemm_metadata` into `deep_gemm_fp4_paged_mqa_logits`, which forwards it positionally to `deep_gemm.fp8_fp4_paged_mqa_logits` with no None guard (`kernels/ops/attention/dsv4/index_logits.py:127-152`). On SM120 the model hook sets `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=True` (`arg_groups/model_hook.py:506-507`) and `dsv4/metadata.py:204-208` then nulls exactly that field, so the new path would be handed the None schedule it was written to avoid. That is the same producer/consumer mismatch as `make_full_topk_indexer`'s `use_deep_gemm_decode=is_sm100_or_newer()` (`__init__.py:76`), which never reads the env, and it is what we hit next: `TypeError: Mismatched type on argument #6 ... Expected DLTensor* but got None` out of `FullTopKIndexer.topk_decode` (full_topk.py:61-65). Worth stating for anyone evaluating this PR on hardware: a candidate-only patch does not make SM120 start, it moves the failure later. Ours went from about 242 s to about 487 s, but that clock tracks weight loading (the same crash reappeared at 179-192 s once the page cache was warm), so identify it by the frame chain, not the elapsed time.

### The half that is still missing, and one question about it

Verified on `main`: the prefill leg splits the primary cache (`flash_mla_sm120.py:236`) and passes `extra_kv_u8` through untouched (line 261), while the decode leg assigns `extra_kv_64 = extra_kv_u8` (line 631). DSV4 pins the page size at 256 (`arg_groups/model_overrides/deepseek_v4.py:51`, asserted at `deepseek_v4_backend.py:1308` and `dsv4/metadata.py:290`) and the SWA pool follows it (`kv_cache_configurator.py:1940-1942`), so the extra cache does reach FlashInfer at 256-token pages while the primary is at 64.

Two notes supporting the patch as written. `buf_key_suffix` is load-bearing, not cosmetic: `_split_kv_pages_to_64` keeps one grow-only buffer per device under `key = f"flash_mla_sm120_split:{dev}"` (line 504), so a second call inside the same forward returns a view of the same storage and the second kernel launch overwrites the first output — the extra leg needs its own buffer. And passing `extra_idx` unremapped is right for the reason the module already documents: "Token indices are invariant under page-split (identity mapping)" (line 600).

The question is which leg actually failed for you. Today's decode leg hands the unsplit 256-page extra buffer to the same `_sparse_mla_sm120_paged_attention` entry point the prefill leg uses; your description justifies the change by a prefill rejection only, while the patch edits both. If FlashInfer's prefill kernel rejects a non-64 extra page size and its decode path accepts that layout, fine, but the asymmetry belongs in the description. If the decode path is consuming it today without complaining, then this PR also closes a silent correctness gap at decode, which is a larger claim than the prefill crash and is worth putting up front. I did not exercise either leg on our tree, so I cannot tell you which it is.

For whoever rebases: #46986 (merged 28 Oct) added `SGLANG_OPT_SM120_DIRECT_SWA_KV` (`environ.py:1356-1359`, default False), which allocates the SWA pool at 64-token physical pages so no per-call split happens at all (`deepseek_v4_memory_pool.py:1173-1187`). That is a second, pool-side answer to your second half; I think the maintainers' actual choice is between those two, not about your indexer code.

Minor: `block_size == 8` overlaps an existing assert — `SparseTableBackend.__init__` already requires `candidate_block_size == CANDIDATE_BLOCK_SIZE` (sparse_table.py:128, with the constant at candidate_table.py:22, whose comment says DeepGEMM accepts 8 or 16). Branching on it instead of asserting means SM100 with a block size of 16 quietly takes the torch path where it used to fail loudly. Probably intended; just not in the description.
