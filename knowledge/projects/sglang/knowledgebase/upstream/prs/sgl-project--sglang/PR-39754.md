# [Fix] managers: Preserve trailing [SEP] when auto-truncating encoder embedding inputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/39754) · state: open · merged: False

## Original PR description

Split out of the XPU model-enabling PR #35304 so this shared `managers/` change is
reviewed on its own. Not gated behind any backend.

## Modification

**Encoder embedding truncation preserves the trailing separator** (`managers/`)
Encoder embedding models (BERT / RoBERTa / ModernBERT / NomicBERT) rely on the
trailing `[SEP]`; a plain head-slice on over-length inputs drops it and shifts the
pooled embedding.
- `managers/utils.py`: the auto-truncation helper takes an optional
  `preserve_last_token_id`; re-append it after the head-slice if the input ended with it.
- `managers/scheduler.py`: resolve `sep_token_id` once (only when `not is_generation`)
  and pass it through.
- `managers/tokenizer_manager.py`: same preservation on that truncation path.
Gated on `not is_generation`, so generation models are unaffected.

- ShaiShmuel · comment · 2026-09-24T14:45:02Z · [source](https://github.com/sgl-project/sglang/pull/39754#issuecomment-5816365892)

The qk_norm fix here is also needed on plain CUDA with default flags. Since piecewise CUDA graph became the default (#16331, first shipped in v0.5.10), every HunYuan v1 checkpoint with `use_qk_norm: true` fails at startup on NVIDIA GPUs.

**Repro:** `tencent/Hy-MT2-1.8B` (`HunYuanDenseV1ForCausalLM`) on SGLang v0.5.10.post1, launched with `python -m sglang.launch_server --model-path tencent/Hy-MT2-1.8B` and no extra flags. The piecewise CUDA graph warmup fails at `self.o_proj(attn_output)` in `hunyuan.py`:

```
RuntimeError: mat1 and mat2 shapes cannot be multiplied (64x128 and 2048x2048)
```

That is 4 warmup tokens × 16 heads, one head wide. It happens on L4 with flashinfer and with triton, and on H100 with fa3, flashinfer and triton.

**Why CUDA hides it only sometimes:** flashinfer and fa3 return `o.view(-1, heads * head_dim)`, which masks the per-head shape of `q`. The piecewise CUDA graph extend path in `radix_attention.py` allocates `output = torch.empty_like(q)`, so the broken shape reaches `o_proj` on every backend. The triton backend also does `empty_like(q)`, so it never masked the bug.

**What we verified on v0.5.10.post1:**
- **Unpatched, default backend, `--disable-piecewise-cuda-graph`:** the model serves correctly. Tested on L4 with flashinfer and on H100 with fa3, on 32 WMT24++ rows each. Prompt token counts match Transformers on every row, and chrF++ is within noise of a direct Transformers decode.
- **This PR's two-line reshape, triton backend, `--disable-piecewise-cuda-graph`:** loads and serves correctly on L4.

Related: #21127, the same crash on HY-MT1.5-7B, was closed as stale without a fix. #21128 was also closed as stale.

The hunyuan.py change is independent of the encoder truncation change. Could it be split into its own PR so it can be reviewed separately? A small startup smoke test on a HunYuan v1 checkpoint (for example Hy-MT2-1.8B) with piecewise CUDA graph on would also guard against regressions. As far as we can tell, no current test loads one.
