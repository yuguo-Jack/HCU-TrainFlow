# [Perf] [NVIDIA] attention: Add opt-in optimized LiteTopK fused indexer top-k for GLM-5.2 DSA prefill on SM100

[Upstream PR](https://github.com/sgl-project/sglang/pull/46434) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.2's DSA indexer runs its prefill top-k in `Indexer._get_topk_ragged`:

1. DeepGEMM `fp8_mqa_logits` writes a `[rows, keys]` fp32 logits matrix, row-chunked to the logits budget.
2. A top-k transform picks each row's 2048 keys. GLM-5.2 on B200 takes the PAGED transform (KV slots through the page table): its default recipe auto-selects an FP8 KV cache and `trtllm` prefill. Only a non-default prefill backend (`flashmla_sparse`, `flashmla_sparse_q8` or `triton_sparse_mla` on an FP8 KV cache) takes the RAGGED one.

At long context this is the indexer's dominant cost and its largest temporary buffer.

This PR adds an opt-in optimized LiteTopK fused indexer top-k (`SGLANG_ENABLE_DSA_FUSED_MQA_TOPK=1`, CUDA SM100):

- One persistent kernel scores every visible key (FP8, 32 index heads x 128) and selects each row's top-2048 in a single launch.
- It writes the transformed indices directly (PAGED, and RAGGED for the non-default backends) and never materializes the logits.
- The result is the exact top-k up to ties at the 2048-th score.

**Speed vs SGLang's current implementation (B200, real GLM-5.2 data).**

Baseline: `Indexer._get_topk_ragged` with the flag off, i.e. DeepGEMM logits chunked to the static logits budget for `--mem-fraction-static 0.85` (5.35 GiB), then SGLang's PAGED top-k transform. Speedup = dense time / fused time of one single-request prefill chunk (cold L2; the times are under [Speed Tests](#speed-tests-and-profiling)).

Crossover (where the fused path starts to win):

- Keys: with 1024 or more rows it already wins at 24K keys, the shortest length compared with the dense path. The worst such cells are layer 0 with 1024 rows: re-measured over two 60-round processes, the layer-0 dump is 1.08-1.11x and the layer-0 capture 1.13-1.14x (1.17x in the table above). So the crossover lies below 24K keys; 20481-24575 keys were not compared, and the op does not take 20480 keys or fewer.
- Rows: below 1024 rows layer 0 loses at short lengths. With 512 rows it loses up to 64K keys (0.82-0.91x) and breaks even near 256K (1.03x on the capture, 1.53x on the layer-0 dump); with 256 rows it loses up to 256K (0.75-0.86x) and wins at 1M (1.51x). Layers 1 and 6 win from 24K keys even with 512 rows (1.20x and 1.06x).
- So SGLang takes the fused path for chunks of at least 1024 rows whose longest row sees at least 24576 keys. From there the speedup grows with the length: at 1M keys 2.8-3.8x on layer 0, 1.9-3.0x on layer 6 and 4.4-5.3x on layer 1 (1024 to 16384 rows).

**Scope.** To reduce the code diff and make review easier, this PR only covers GLM-5.2 (32 index heads x 128, `index_topk` 2048, FP8 index K cache). Our DeepSeek adaptation is also prepared and will be sent as a follow-up PR.

**Credit.** This kernel is an optimized LiteTopK kernel. [LiteTopK](https://github.com/Heisenberg-Yin/LiteTopK) ([paper](https://arxiv.org/abs/2607.11976), vLLM [#48726](https://github.com/vllm-project/vllm/pull/48726)) first proposed fusing the indexer scoring and top-k into one kernel. It uses a sample-filter-select framework: sample each row's scores to set a gate, keep only the keys that pass the gate, and select the top-k among them. vLLM PR [#60618](https://github.com/vllm-project/vllm/pull/60618) (head `ca75fe8043`) by **Roberto L. Castro (@LopezCastroRoberto)** improved it in two ways:

- A persistent kernel. One CTA per SM claims 8-row blocks from a global counter and runs each block's sample and scan tiles through one continuous pipeline. The separate seed-logits launch is gone, the workspace is a small fixed pool per SM, and every chunk up to 16384 rows and 1M keys, including multi-request chunks, takes one launch. LiteTopK fused only single-request chunks of fixed size.
- A threshold-prediction algorithm. The kernel predicts each row's threshold (the gate) from a sampled quantile of the row's own scores, with no host calibration. The row's candidate count verifies the prediction: a block whose count leaves the exact range is rescanned densely, so the result is the exact top-k up to ties at the k-th score.

For these improvements, **Roberto L. Castro** is a co-author of this PR. **Ziyi Xu (@DarkSharpness)** independently came up with the persistent-kernel idea and discussed it with me, so **Ziyi Xu** is also a co-author. Thanks to **Yuan Luo (@yuan-luo)** for the early SGLang adaptation of LiteTopK in #32094; **Yuan Luo** is also a co-author. #32094 ports the original three-launch kernel: a dense-logits seed on a KV prefix, then a scan, then a select, with a per-request host calibration loop.

## Differences from vLLM PR #60618

This PR keeps #60618's persistent fused scoring/top-k design, sampled gating, and exact-rescan recovery. The main changes are:

- **GLM-5.2 gating:** per-row gate bins avoid excessive rescans on layer 1.
- **Pipeline efficiency:** ballot-compacted candidate staging, streaming selection, and improved pipeline overlap.
- **SGLang integration:** B200 tuning, a corrected rescan scheduler for large row counts, and direct RAGGED/PAGED index output.
- **Focused scope:** top-2048, 20481 to 2^20 keys, built for `sm_100f`; smaller-key paths are omitted.

On the measured B200 kernel benchmarks with real GLM-5.2 data, speedups over the #60618 head kernel are **1.35-2.19x on layer 0**, **4.46-5.54x on layer 1**, and **1.52-1.68x on layer 6**. Results below 64K keys are outside vLLM's default fused dispatch range.

## Modifications

- The kernel and its README (see above).
- `kernels/jit/csrc/dsa/fused_mqa_topk.cuh` and `kernels/ops/attention/dsa/fused_mqa_topk.py`: the JIT op `fused_mqa_topk_prefill`, registered as `attention.fused_mqa_topk_prefill` for SM100.
    - It holds the op's coverage predicate.
    - It builds the module for `sm_100f` instead of the JIT default `sm_100a` (see the kernel README).
    - It keeps one workspace per (device, stream): about 296 MiB on 148 SMs plus 4.5 bytes per query row, allocated on the first call per stream; only a call with more rows than any before it regrows the per-row part (at least twofold), and graphs captured before keep the old one. The kernel leaves its claim counter zeroed, so other calls neither allocate nor synchronize and can be graph-captured.
- `srt/layers/attention/dsa/dsa_indexer.py`: when the flag is set and the call is covered, `_get_topk_ragged` writes `topk_result` with the fused op.
    - It keeps the dense path's index contract for the same metadata:
        - fused RAGGED transform: `(key - row start) + topk_indices_offset`;
        - fused PAGED transform: `page_table_1[request, key - row start]`;
        - unfused top-k: row-relative;
        - `-1` padded in every case.
    - Every DSA prefill top-k of GLM-5.2 goes through this method, either eagerly or from the PCG/BCG prefill split op. (GLM-5.2 sets no `index_kpool`.)
    - Covered: CUDA SM100 with nvcc >= 12.9 for the JIT (`sm_100f`), 32 index heads x 128, `index_topk` 2048, FP8 e4m3 index K, 20481 to 2^20 keys, 16-byte aligned contiguous operands.
    - Excluded:
        - deterministic inference (ties at the 2048-th score resolve in atomic order);
        - index init/local tokens;
        - prefill context parallelism;
        - stream capture.
    - The fused path is taken only where it was not slower on B200 for single-request chunks (thresholds below). For both transforms the chunk needs at least 1024 query rows. The longest row must see at least 32768 keys for RAGGED and the unfused top-k, or at least 24576 keys for PAGED (the dense PAGED transform is slower). An import-time assert keeps both key bounds at or above the op's minimum of 20481 keys.
    - With the flag off nothing changes.
- `SGLANG_ENABLE_DSA_FUSED_MQA_TOPK` (default off) in `environ.py`.

## Accuracy Tests

The fused top-k is exact up to ties at the 2048-th score.

- **Coverage:** RAGGED/PAGED outputs, boundary sizes, CUDA graphs, workspace growth, fallback paths, and dispatch thresholds.
- **Real data:** 135 GLM-5.2 runs; all sampled rows passed tie-aware FP32 checks, with set recall >= 0.99953. An additional kernel harness checked 164 cases.
- **Not run:** end-to-end GLM-5.2 serving accuracy. Validation is at the indexer level.

## Speed Tests and Profiling

Measured on B200 through `Indexer._get_topk_ragged`, against SGLang's dense PAGED path with cold L2.

- **Indexer speedup:** 2.76-3.54x on layer-0 captures at 1M keys (1024-16384 rows), and 3.00-5.33x on multi-layer dumps at 1016K keys (8192 rows).
- **Memory:** removes the logits temporary buffer, which can reach 5.35 GiB per call.
- **Minimum dispatch:** 1024 rows; 24K keys for PAGED, 32K for RAGGED/unfused top-k. Smaller calls keep the dense path.
- **Scope:** single-request timings; mixed-request performance was not benchmarked.
