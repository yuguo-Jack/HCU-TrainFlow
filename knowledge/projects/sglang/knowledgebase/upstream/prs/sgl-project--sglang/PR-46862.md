# [Feat] RL: [sglang-miles] WeightBridge weight receiver driven by the scheduler loop

[Upstream PR](https://github.com/sgl-project/sglang/pull/46862) · state: open · merged: False

## Original PR description

> Companion PR: https://github.com/radixark/miles/pull/4461, the trainer side that drives these receivers.

## Motivation

This adds [WeightBridge](https://github.com/harvard-cns/weightbridge) (`pip install wbridge`) as a trainer→rollout weight-transfer mode for disaggregated Megatron + SGLang runs. Its key properties:

- **No redundant transfer.** Every trainer rank sends only its own live shards, with no trainer-side gather, directly to the rollout ranks that need them, and each replicated tensor crosses the network only once.
- **Balanced transfer at high rollout DP.** Each rollout replica receives only a share of the weights from the trainer and the rollout workers exchange the rest among themselves, so trainer egress does not grow with the number of rollout replicas.
- **Adapts to different models and parallelism automatically.** WeightBridge infers each side's weight layout by probing the framework's own `load_weights`, so no per-model or per-parallelism mapping code is needed.

On real RL deployments from 16B to 1T parameters, WeightBridge cuts the GPU stall time per weight transfer by **16.6×–29.4× against Miles' NCCL broadcast** and **5.4×–42.0× against Miles' P2P transfer**, and training is unchanged: in deterministic mode a WeightBridge run is bitwise identical to a broadcast run.

## Modifications

### How it works

**Startup.** Each SGLang engine started with `--enable-weightbridge-receiver` builds a WeightBridge receiver on every worker at startup (engine rank 0 also spawns the per-engine coordinator). Each receiver infers its weight layout by probing the engine's own `load_weights`. On the trainer, each rank builds a sender by probing Megatron-Bridge's HF→Megatron import, then connects once through the coordinators.

**Per update.**

1. Trainer: `send_weights(metadata={"weight_version": v})` on every rank, then waits until every engine has loaded it (or returns after packing with `--weightbridge-async-delivery`).
2. Engine: every scheduler polls its receiver once per loop pass, before receiving that pass's requests. Engine rank 0 sees the trainer's data-ready flag and broadcasts GO over WeightBridge's own control hub; the hub is a barrier, so every TP/PP rank acts on it at the same pass.
3. On GO, every rank applies the same pause semantics as Miles' HTTP session: finish the batch in flight on the GPU, retract (or, with `--pause-generation-mode abort`, abort) every request, and synchronize the device. Then WeightBridge writes the weights, the KV/radix cache is flushed, the weight version is set to the trainer's version (carried as WeightBridge update metadata), and generation resumes.

**Pipeline parallelism.** Under PP, the quiesce first runs one loop round that launches nothing new, so micro-batches already in flight finish exactly as in an idle pass and every stage-to-stage send keeps its matching receive; then all live requests are retracted/aborted on every stage.

**Topologies.** TP, PP, attention DP, and engines spanning several nodes (the control hub becomes a TCP endpoint on rank 0's host). Rejected: separate data-parallel replicas (`--dp-size > 1`), PD disaggregation, speculative decoding with PP, colocated placement, LoRA, and `--fully-async`.

### Usage

```bash
pip install 'wbridge[cuda]'   # plus a Mooncake transfer engine build matching your CUDA version
python -m sglang.launch_server ... \
  --enable-weightbridge-receiver \
  --weightbridge-pause-mode retract       # or abort
  # multi-node engines: --weightbridge-hub-addr tcp://<rank-0 host>:<port>
```

The trainer side (`SenderAdapter.send_weights`) lives in the companion miles PR; any trainer that connects to the engine's coordinator (HTTP port + 1717) works.

WeightBridge's transfer path has been verified with 5D parallelism on the trainer (TP, PP, DP, EP, CP) and 3D parallelism on the rollout side (TP, DP, EP), in the experiments behind the real-workload results under Speed Tests. Attention DP within an engine is supported and tested. Rollout PP is supported but not yet tested. Engines with several DP replicas (`--dp-size > 1`) and rollout PD disaggregation are not supported and are rejected in this PR. The accuracy comparison under Accuracy Tests was run on 8 GPUs only.

## Accuracy Tests

### Training is unchanged

![Training reward by step and by wall-clock time](https://github.com/SwiftSeal03/miles/blob/weightbridge-pr-assets/step-time-reward.png?raw=true)

Qwen3-8B-Base on GSM8K, disaggregated `train_async.py` on 2 nodes × 4 H100 (trainer TP4 on one node, two TP2 SGLang engines on the other), identical hyperparameters and code, 1 hour each, deterministic mode (`--deterministic-mode` with SGLang deterministic inference); only `--update-weight-transfer-mode` differs. The two runs are bitwise identical: every training reward over steps 0–115 (the steps both runs reached), every GSM8K eval, and every rollout's tokens and log-probs match. Before training, a `--check-weight-update-equal` run confirms the first WeightBridge transfer reproduces every rollout tensor byte for byte (291/291 on all 4 rollout ranks).

**Why the wall-clock gain is modest here.** Each update is 3.0× faster with WeightBridge (median 0.14 s vs 0.42 s), but on this 8B model the update is only ~1.4% of a ~21 s step. Deterministic inference makes rollout about 1.75× slower. The gain is larger for MoE models because they transfer all experts but activate only a few per token.

Setup: the Miles disaggregated RL pipeline (Megatron-LM trainers, SGLang rollout engines) on DAPO-Math, BF16 checkpoints, on an H100 cluster with 8× H100 80GB per node (NVLink/NVSwitch) and 32× 100 Gbit/s RDMA NICs per node (400 GB/s aggregate). Broadcast pays for gathering to one rank and sending replica-redundant data through a global collective; P2P for trainer-side gathering and CPU staging, plus a single-source fan-out when rollout GPUs outnumber trainer GPUs. WeightBridge routes each shard directly to the rollout workers that need it, exchanges replicated shards between rollout workers, and pipelines conversion, RDMA, and reconstruction.
