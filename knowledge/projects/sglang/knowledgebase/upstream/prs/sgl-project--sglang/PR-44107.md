# [Fix] glm: Bound tool argument pairs and handle unserializable values

[Upstream PR](https://github.com/sgl-project/sglang/pull/44107) · state: open · merged: False

## Original PR description

## Motivation

Two bugs in GLM tool calling lose a call that the model tried to make. The cookbook uses `glm47` for GLM-4.7 through GLM-5.3.

**Repeated argument keys.** With the `glm47` or `flint` parser, one tool call can repeat argument keys until `max_tokens`, so the request returns no usable call. Any request with non-strict tools and `tool_choice` `auto` or `required` can reach this. On public GLM-4.7-Flash with a synthetic prompt, 234 of 432 requests hit the 4000-token limit on main and 0 of 432 with this PR. The prompt demands an argument that the schemas lack, and how often clients send this shape is not measured. In a smaller run of 160 requests, the loop needed the system prompt and history together: 20 of 32 on main with both, and 0 of 128 on main in the other scenarios. An ordinary prompt in that run also lost queries: in 4 of 32 requests to search five terms, the non-stream parser kept only the last of 5 or 6, and this PR returned 6 separate calls.

**Unserializable literals.** When a GLM model writes a tool argument as a Python set, bytes, or complex literal, main returns raw markup instead of the tool call. Chat completions streams end with no finish reason or `[DONE]`, and the server logs `TypeError: Object of type set is not JSON serializable`. `glm45` and `iquest_q1` can reach this on any non-string-typed parameter, because `tool_choice` auto has no grammar. `glm47` reaches it through a schema the grammar leaves free, such as `$ref`, or a client constraint. Every run prompted or forced the literal, so unprompted frequency is unmeasured and may be low. An issue search found no user report.

I found no other open PR that bounds these pairs or fixes this crash. #46672 bounds the text preamble. #43270 and #43264 conflict with this PR over a separate tuple bug. The second to land keeps both changes, with `json.dumps` before the tuple branch.

## Modifications

- Limit the argument pairs in each call to the number of keys in a complete schema. Keys stay optional and in any order. A closed schema with no keys allows no pairs.
- Check the literal result with `json.dumps` in the `glm45` and `glm47` parsers. If that fails, keep the original argument text, as the Poolside parser does. `iquest_q1` and `ling3` inherit this check.

Limits:

- With parallel tool calls on, repeated whole calls stay accepted.
- Incomplete or free-form schemas keep the unbounded rule.
- A repeated key can push out a later key.
- Requests with a strict tool skip this grammar.
- Where values stream verbatim, a Python literal still gives invalid JSON deltas: array, object, and boolean with `glm47`, and declared non-string types with `glm45`. Fixing this needs buffering. Open #43275 changes these `glm47` deltas.
- `{'a': 1e999}` gives non-standard `Infinity`.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Cap arguments for complete zero-key schemas**

When a no-argument tool declares `{"properties": {}, "additionalProperties": false}`, `_glm_has_complete_properties()` regards it as complete but `all_props` is empty, so this new bounded rule is skipped and the fallback `(...)*` still accepts arbitrary repeated argument pairs. Such GLM47 calls can therefore still run to `max_tokens`, precisely the production loop this change is meant to prevent; distinguish a complete empty schema from an unresolved/free-form schema and emit zero argument pairs.
