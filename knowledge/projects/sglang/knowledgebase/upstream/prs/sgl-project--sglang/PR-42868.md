# [Feat] lora: Shared hooks for the LoRA MoE and dense engines (01/21)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42868) · state: closed · merged: False

## Original PR description

Part 01 of 21 of the LoRA runtime stack (branch `lora-stack-00-shared-hooks`, base `main`). The stack is cut from the development branch of #42284.

## What this part adds

Add the hooks the LoRA engines need in shared code, with no effect unless a
lora_* MoE runner or the triton_v2 LoRA backend is selected:
- MoeRunnerBackend gains LORA_CUTEDSL, LORA_TRITON and LORA_MARLIN with the
  is_lora() and is_lora_marlin() predicates.
- FusedMoE keeps DeepGEMM's resident weight layout for lora_* runners, and the
  NVFP4 routed-scaling decision treats the LoRA Marlin vendor like Marlin.
- ModelOptNvFp4FusedMoEMethod prepares Marlin weights for lora_marlin, rejects
  the other lora_* runners, and leaves execution to the LoRA wrapper.
- post_reorder_deepgemm accepts an optional per-pair lora_delta added before
  the route weights and routed scaling.
- The decode-graph "lora"/"nolora" label becomes the capture_lora_variant()
  context manager, so later captures cannot inherit it.
- The decode-graph batch-info init is renamed init_decode_cuda_graph_batch_info
  on LoRAManager, every backend and the decode runner's call, matching the
  prefill one.
- Both graph runners call LoRAManager.reset_routing_cache() before each
  capture; the backend default is a no-op until a backend caches routes.

Tests: the existing chunked SGMV CUDA-graph and speculative-verification
batch-info suites are updated to use `init_decode_cuda_graph_batch_info`.
The runner-extension tests are unchanged.

Files outside the LoRA owners' paths: `python/sglang/srt/layers` (MoE utils, fused_moe_triton layer), `srt/layers/quantization` (ModelOpt NVFP4), `python/sglang/kernels` (ep_moe post-reorder), `srt/model_executor` (graph runners, capture mode).
