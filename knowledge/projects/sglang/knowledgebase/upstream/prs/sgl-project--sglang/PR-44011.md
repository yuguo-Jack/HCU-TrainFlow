# [MemCache] Reclaim orphan Full KV in hybrid unified cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/44011) · state: open · merged: False

## Original PR description

## Motivation

Hybrid attention/Mamba models can evict recurrent State independently from Full KV. This can leave a Full-KV-only subtree that no longer reaches any reusable recurrent-state boundary. Keeping such a subtree consumes device cache, but matching it cannot produce an executable hybrid prefix.

This PR adds an opt-in, pressure-driven reclamation path for those orphan Full-KV subtrees.

## Modifications

- Add `SGLANG_OPT_UNIFIED_CACHE_RECLAIM_ORPHAN_FULL_KV` (default: disabled).
- Before the normal Full-KV eviction walk, find maximal hybrid-cache subtrees that contain no device or host Mamba State.
- Treat runtime and storage dependencies as anchors: device/host locks, session references, host copies, external-cache copies, and pending write-through/load-back operations all prevent reclamation.
- Reclaim eligible subtrees in LRU order and stop after satisfying the requested Full-KV pressure target.
- Keep the Python and Rust TreeCore implementations behaviorally aligned.

The optimization changes cache retention only. It does not change model kernels, scheduling order, or generated-token logic.

## Algorithm, fallback, and example

The reclamation path is a priority layer in front of SGLang's existing Full-KV eviction, not a replacement for it:

1. It runs only when a Full-KV allocation is under pressure and the opt-in flag is enabled.
2. TreeCore performs a post-order traversal. A subtree is anchored if any node in it has a device/host Mamba State or a live dependency such as a lock, session reference, host/external copy, or pending transfer.
3. The remaining maximal unanchored roots are the orphan candidates. Selecting maximal roots avoids double-counting descendants and lets TreeCore detach a structurally complete subtree.
4. Candidates are ordered by their oldest access time. Whole candidates are reclaimed until the Full-KV target is reached or no candidate remains.
5. The controller consumes the returned tensor frees and adds them to the same eviction tracker used by the existing allocator path.
6. If orphan reclamation is insufficient, execution falls through to the unchanged SGLang Full-KV eviction walk, which frees additional ordinary eligible KV. Allocation fails only if the combined orphan and normal eviction paths still cannot satisfy the allocator.

In simplified form:

```text
if Full-KV allocation is under pressure and orphan reclaim is enabled:
    reclaim maximal orphan subtrees in LRU order
    apply those frees to the allocator and eviction tracker

if the allocation target is still not reached:
    run the existing SGLang Full-KV eviction walk
```

Consider this hybrid radix tree, where sizes denote Full-KV token slots:

```text
root
├── A: 7K Full KV and reusable State            anchored, preserve in Stage 1
├── B: 3K Full KV, no State                    oldest orphan root
│   └── B1: 1K Full KV, no State               part of B's 4K subtree
├── C: 5K Full KV, no State, active lock       dependency-protected
└── D: 6K Full KV, no State                    newer orphan root
```

For an 8K Full-KV pressure target, the policy reclaims B (4K) and then D (6K), releases 10K, and stops. A remains because its subtree contains a reusable State; C remains because its active lock is a live dependency. Reclaiming 10K for an 8K target is intentional: a maximal subtree is the atomic structural unit, so the final reclaim can overshoot the requested token count.

For a 12K target on the same tree, all eligible orphan subtrees provide only 10K. The controller then continues into SGLang's existing eviction walk to obtain the remaining space from ordinary unlocked Full KV. If that path also has less than 2K available, the allocator reports the same failure it would report without this optimization.

If a later request needs B or D, the removed suffix is recomputed from the nearest preserved recurrent-State boundary, or from the root when no such boundary exists. The policy therefore spends recomputation only on prefixes that could not form an executable hybrid-cache hit after their State was lost, while preserving every branch with a current runtime or storage dependency.

## Speed Tests and Profiling

### Latest standalone Stage-1 revalidation (2026-10-08)

Protocols 406/407 isolate Stage 1 on an RTX 5080 with Qwen3.5-0.8B (18 GDN + 6 full-attention layers). Application hints, capture, checkpoint leases, QCCC, queue/component cuts, State-aware Full eviction, and the generic Full-only fallback are disabled. The only added mechanism is coverage-debt tracking plus dependency-safe pressure reclamation.

The natural Exgentic experiment contains 43 requests and 247,404 input tokens, generates 16 tokens per request at concurrency 8, and reports the second round after cache construction. Each arm uses three independent server restarts.

| Metric | All off | Stage 1 only | Change |
|---|---:|---:|---:|
| Recomputed tokens | 65,260 | 60,076 | **-7.94%** |
| Median throughput | 7.056 req/s | 7.446 req/s | **+5.53%** |
| Median mean E2E | 3.348 s | 3.025 s | **-9.65%** |
| Median P95 E2E | 6.074 s | 5.756 s | **-5.24%** |
| Median peak HBM | 7,472 MiB | 7,506 MiB | +34 MiB (noise range) |

Recomputation was identical across all three restarts in each arm, and Stage 1 throughput was higher in every paired restart. Three of 43 warm-cache outputs differ from the control, at stable request indices, so these results do not claim bitwise equivalence to a different warm-cache execution path.

Protocol 406 measures physical reclamation with 28 dead branches plus 8,192-token one-shot fillers:

- Control succeeds with 19 fillers but fails at 20 with `Can not alloc mamba cache`.
- Stage 1 completes 34 fillers in **3/3** independent restarts with exact forced-output replay and a healthy server.
- Verified effective workload capacity increases from 19 to at least 34 fillers: **+78.95%**, or **1.406 GiB** of additional Full-KV content within the fixed preallocated pool.
- Each run performs 62 pressure-triggered collections over 6,019 radix nodes and reclaims 385,216 Full-KV token slots.
- Maximum physical reclamation in one collection is **95.25 MiB**; cumulative reclaimed-and-reused Full KV is **4.408 GiB**.
- Peak digest-ghost metadata is about **94 KiB**.

These are the latest complete standalone Stage-1 measurements. They were collected on the research implementation containing coverage debt, dependency-safe pressure reclamation, and digest ghosts. This PR is the current-main extraction of the reclamation core; an exact current-commit A/B will be added before merge.
