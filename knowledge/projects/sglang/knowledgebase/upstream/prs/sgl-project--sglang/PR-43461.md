# [srt] Allow mixed chunk prefill on the Full prefill CUDA graph backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/43461) · state: closed · merged: True

## Original PR description

## Motivation

Starting a server with `--enable-mixed-chunk` and the Full prefill CUDA graph backend fails in `PrefillCudaGraphRunner.__init__`, which asserts that mixed chunk prefill is served by the Breakable backend only. That guard was written when Breakable was the only padded prefill topology. Full now captures a padded EXTEND topology on both the token and request axes and refreshes the live attention metadata before every replay, and `MIXED` forwards already replay the EXTEND-captured graphs on both backends (the runner maps `MIXED` to `EXTEND` before the replay lookup). Nothing on the mixed path is Breakable-specific any more, so the guard only blocks a working configuration.

Mixing prefill chunks with running decode rows under Full prefill graphs lets a serving deployment that prefers Full's static request-axis shape keep decode rows moving while prefills arrive, instead of choosing between the two.

## Modifications

- `python/sglang/srt/model_executor/runner/prefill_cuda_graph_runner.py`: the startup guard accepts `Backend.FULL` as well as `Backend.BREAKABLE`. Defaults are unchanged: mixing stays opt-in and every other backend is still rejected with the same assertion. Shapes the Full backend cannot replay (more requests than captured slots, uncapturable prefix chunks, and so on) fall back to eager execution exactly as before; this change touches only the constructor check.
- `test/registered/unit/model_executor/test_prefill_cuda_graph_runner.py`: a CPU case constructs the runner with mixed chunk enabled on the Full backend, with base initialization patched to raise a sentinel, and checks that the sentinel is reached. It fails on the previous guard with `Mixed chunk prefill requires the breakable prefill CUDA graph backend; got 'full'`.

## Accuracy Tests

Not applicable to default configurations: the change is a constructor check and is a no-op unless `--enable-mixed-chunk` is set with the Full backend. On that configuration the forward path is the existing Full EXTEND replay with refreshed attention metadata, which is already exercised by non-mixed Full prefill; decode rows in a mixed batch take the same padded slots they would in a Breakable mixed batch.

## Speed Tests and Profiling

Not applicable: no kernel or runtime path changes. Mixed chunk prefill interleaves prefill and decode for better decode concurrency in mixed workloads, trades prefill completion latency for it, and remains opt-in.
