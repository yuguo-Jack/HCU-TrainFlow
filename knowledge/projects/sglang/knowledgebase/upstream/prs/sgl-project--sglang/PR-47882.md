## Motivation

Some Qwen4-Exp compressed-tensors checkpoints, such as `intel-ai/Qwen3.8-Flash-Next-MXFP4-BF16Attn-MXFP8MTP-PLEMXFP8-CT-AutoRound`, quantize the PLE n-gram embedding table to MXFP8. Each `shard_N.weight` is fp8 e4m3, with a `shard_N.weight_scale` tensor holding one uint8 (E8M0) scale per 32 columns.

The PLE path only knew two table formats:
- a bf16 table;
- an fp8 table with one scalar `weight_scale`.

An MXFP8 checkpoint therefore failed to load: the scale shard tripped the scalar-scale assertion. Even with that bypassed, a lookup would have returned fp8 values without applying the group scales.

## Modifications

- Table detection:  _ple_table_is_mxfp8  reads the compressed-tensors target map and matches an fp8, 8-bit, group-size-32 weight target for the table's prefix.
- `Qwen4ExpMxfp8Embedding`:
  - It stores the fp8 table plus a uint8  weight_scale  buffer of shape  [rows_per_partition, dim // 32] . The buffer starts at 127, which is a scale of 1.
  - Lookup gathers the fp8 values and the scales. It computes  value * 2^(scale - 127)  per group of 32 and returns  output_dtype , bf16 here.
  - Rows owned by other TP ranks are zeroed, as in  VocabParallelEmbedding .
  - The gather runs on  uint8  views, so it doesn't depend on fp8  index_select  support.
  - It raises  ValueError  if the embedding dim is not a multiple of 32.
- `Qwen4ExpNGramEmbedding`:
  - It selects the new class when MXFP8 is detected.
  - It skips the scalar  weight_scale  buffer and the  * weight_scale  multiply.
  - It raises  NotImplementedError  together with  ple_offload_embedding .
- Loader:
  -  shard_N.weight_scale  shards are copied into  weight_scale  with the same row placement as the weight shards.
  - Scale shards no longer trigger the fp8 "downcasting is lossy" warning.
  - The  copy_ple_rows_to_tp_embedding  helper gained an optional  target  for this.
- Non-MXFP8 checkpoints are unaffected. The new code is only reached when the target map says MXFP8.

**Limitations**

- The MXFP8 table is not supported with  ple_offload_embedding , and that case raises. Where offload is on by default, such a checkpoint needs  --ple-offload-embedding false .
- The dequantization is plain torch, not a fused kernel.

**Tests**

New file `test/registered/unit/models/test_qwen4_exp_ple_mxfp8.py`, 13 CPU tests:
- table detection, with positive and negative cases;
- lookup against a torch dequantized reference;
- a TP shard that zeroes foreign rows;
- the scale-buffer default and the dim-multiple check;
- the loader through the real  load_weights , with out-of-order shards, a TP rank slice and a short last shard;
- no downcast warning for scale shards.

The existing PLE table and decode-comm tests still pass.

The tests are CPU-only because the implementation is pure Python with standard torch ops.
