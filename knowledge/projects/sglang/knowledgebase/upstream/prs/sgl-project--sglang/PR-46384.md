# [Perf] unified-memory: Clear Mamba slots without a host sync

[Upstream PR](https://github.com/sgl-project/sglang/pull/46384) · state: open · merged: False

## Original PR description

Stacked on #46379 ([Feat] unified-memory: Admit fa4 for EAGLE and DFLASH), which itself is stacked on #46378; only the last commit is new here.

## Motivation

`UnifiedMambaPool.clear_slots` (whole entries) and `UnifiedDraftMambaPool.clear_slots` (a fused draft's state block) zeroed slots as `view[idx] = 0`. With device indices that is `index_put_` with a 0-dim host value, which copies the value to the device from pageable memory: a `cudaMemcpyAsync` plus a `cudaStreamSynchronize` per view. A fused draft clears its block after every prefill's draft extend, once per draft runner and state view. Inkling-Small's MTP draft fuses 8 runners of 6 conv state streams each, so every admitting forward stalled the scheduler about 48 times, and serving traces on the unified pool showed about four times the default pool's stream synchronizes, nearly all of them here.

## Modifications

- Both clears now zero with `index_fill_` (a device-side scalar fill; indices cast to int64 where they are not already), which writes the same bytes: strided views, whole-entry uint8 rows, int32 and duplicate indices, and an empty temporal stream behave as before (`mem_cache/unified_memory_pool.py`, `mem_cache/unified_draft_pool.py`). The slot siblings' own resets are unchanged. The default `MambaPool` already zeroes without a host value.

Test (CUDA), `test/registered/unit/mem_cache/test_unified_handout_zeroing.py`: `TestMambaSlotClearStaysOnDevice` clears a fused host and draft state pool under `torch.cuda.set_sync_debug_mode("error")`, which raises on a synchronizing operation, and checks the cleared and the spared slots. The old `view[idx] = 0` path raises there. The existing CPU tests of these slot ops pass unchanged.

## Accuracy Tests

Not applicable: the clears write the same bytes as before (see the test).

## Speed Tests and Profiling

SM90, `thinkingmachines/Inkling-Small`, TP 8, `--attention-backend fa4`, `--speculative-algorithm EAGLE --speculative-draft-model-path thinkingmachines/Inkling-Small --enable-multi-layer-eagle --speculative-num-steps 8 --speculative-eagle-topk 1 --speculative-num-draft-tokens 9 --speculative-use-rejection-sampling`, radix cache, overlap scheduler, CUDA graphs on, on top of #46379 and #46376. `--enable-unified-memory` against the default pool on the same build; a second default-pool server bounds the default pool's run-to-run noise.

| load | unified req/s, before / after | req/s gap to the default pool, before / after | median TTFT gap, before / after |
|---|---|---|---|
| 200 requests of 4096 input / 64 output tokens, concurrency 64 (admission-heavy) | 6.48 / 7.45 | -13.0% / -3.5% | +16.4% / -0.3% |
| 192 requests sharing a 4096-token prefix + 128 tokens, 2048 output tokens, concurrency 192 | 0.97 / 0.96 | -10.1% / -10.5% | +12.7% / +10.7% |

The default-pool servers varied by up to 4.6% between themselves on the admission-heavy load; the unified server's own throughput rose 15%. Decode at equal batch size is unchanged, as expected: the clears run only when requests are admitted. The remaining decode gap on this stack comes from the draft's per-step graphs, which the follow-up "[Perf] unified-memory: Stage a fused draft's draft-extend metadata once per draft cycle" addresses. That change alone also closes the admission-heavy gap on this setup; the two gains overlap and do not add, and this PR's gain on top of it was not measured.
