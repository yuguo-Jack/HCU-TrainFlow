# [Fix] disaggregation: wait for the prefill forward before sending KV chunks under PP

[Upstream PR](https://github.com/sgl-project/sglang/pull/45524) · state: open · merged: False

## Original PR description

## Motivation

On a disaggregated prefill server with pipeline parallelism, `process_prefill_chunk` sends the KV of a chunked request's non-final chunk at the start of the next scheduler iteration. At that point the chunk's forward has only been launched on `forward_stream`, and the PP event loop does not wait for it before the page indices are handed to the KV sender.

With the default PP comm path and the default `--pp-async-batch-depth 0`, this happens to be safe. After launching a batch, each stage issues a P2P send for it (proxy tensors on non-last stages, outputs on the last stage) that makes the schedule stream wait on that forward's event. The page-index copy in `send_kv_chunk` is issued on that stream after the wait, so it completes only after the forward: v0.5.22 blocks on it with `.cpu()`, and on main the Mooncake transfer worker synchronizes on its `indices_event`. Three settings break this ordering:

- `--pp-async-batch-depth N` with N > 0: the last stage sends the outputs of the micro-batch launched N iterations earlier, before it launches the current one, so what holds its scheduler back now refers to that older forward. The last stage hands each non-final chunk to the KV sender while the chunk's forward is still running.
- `SGLANG_PP_COMM_OVERLAP=1`: the wait is issued on the dedicated PP comm stream instead, so on the non-last stages nothing orders the KV read after the forward anymore.
- `SGLANG_PP_SKIP_PURE_CHUNKED_OUTPUT_COMM=1`: the last stage skips the output send for a batch that holds a single non-final chunk, and the wait goes with it. #47074 reports this case and restores the wait in the scheduler.

In all three cases the transfer engine can read KV pages that are still being written, and decode runs on partially stale KV.

The cached-prefix early send is not affected. Under PP it runs inside `run_batch`, which `_pp_launch_batch` calls under `forward_stream_ctx`, so its page-index copy is already ordered after the previous forward on that stream. The radix-cache runs below confirm this, so this PR leaves that path unchanged.

To confirm the race, I temporarily instrumented the Mooncake transfer worker to call `wait_event.query()` when it dequeues a non-final chunk (debug only, not part of this PR). On a PP2 prefill server, the counts of non-final chunks whose producing forward was still running at that moment, over 8 requests (24 for the last row):

| PP comm | `--pp-async-batch-depth` | First stage | Last stage |
| --- | --- | --- | --- |
| default | 0 | 0/80 | 0/80 |
| default | 1 | 0/80 | 80/80 |
| default | 2 | 0/80 | 80/80 |
| `SGLANG_PP_COMM_OVERLAP=1` | 0 | 80/80 | 0/80 |
| `SGLANG_PP_SKIP_PURE_CHUNKED_OUTPUT_COMM=1` | 0 | 0/216 | 216/216 |

## Modifications

- `process_prefill_chunk`: when `pp_size > 1`, record an event on `forward_stream` and attach it to the sender before sending a non-final chunk.
- The event goes through the existing `_early_send_wait_event` → `TransferKVChunk.wait_event` path that the cached-prefix early send already uses. The transfer worker synchronizes on it before the RDMA read, so the scheduler thread is never blocked. Mooncake and Mori already honor this event, and #43299 adds the same wait to NIXL; other backends ignore it, as before.
- Add `test/registered/unit/disaggregation/test_prefill_pp_kv_send_wait.py`. Its PP case fails without this change.

## Accuracy Tests

Tested on v0.5.22 with this patch applied; `process_prefill_chunk` is identical on main.

Setup: Qwen3-4B-Instruct-2507 on one 8xH200 node. Prefill runs TP1 per stage, `--chunked-prefill-size 8192` and `--disable-radix-cache`. Decode runs TP1. KV transfer uses Mooncake, behind sglang-router.

Test: passcode retrieval over ~87K-token prompts of random words, with a 7-digit passcode at evenly spread depths. Greedy decoding, `max_tokens=16`, one request at a time.

| Prefill PP | PP comm | `--pp-async-batch-depth` | Before | After |
| --- | --- | --- | --- | --- |
| 4 | `SGLANG_PP_COMM_OVERLAP=1` | 0 | 18/24 | 24/24 |
| 4 | default | 0 | 24/24 | 24/24 |
| 2 | default | 1 | 5/24 | 24/24 |
| 2 | default | 2 | 5/24 | 24/24 |

Before the fix, wrong answers are truncated or have wrong digits, e.g. `2719` for `2378845` and `9468399` for `9468339`. The first token is sampled on the prefill server and is always right; every later token reads the transferred KV.

**With radix cache enabled.** Same model and test, PP2 prefill without `--disable-radix-cache`, and two decode servers behind sglang-router with round-robin. Each pair sends a ~76K-token prompt A, which computes 10 chunks, and 0.8 s later the same prompt as B. B matches 73,731 cached tokens, early-sends them and joins A's last chunk. In 16 of the 24 pairs the passcode sits in the last cached chunk, the one written by the forward just before B's early send.

| PP setting | Before: A | Before: B | After: A | After: B |
| --- | --- | --- | --- | --- |
| `SGLANG_PP_COMM_OVERLAP=1` | 24/24 | 24/24 | 24/24 | 24/24 |
| `--pp-async-batch-depth 1` | 0/24 | 24/24 | 24/24 | 24/24 |
| `SGLANG_PP_SKIP_PURE_CHUNKED_OUTPUT_COMM=1` | 1/24 | 24/24 | 24/24 | 24/24 |

B is right in every run. On the stage that races, each of B's early sends was issued while the previous forward was still running (24/24 per setting), and by the time `send_kv_chunk` returned that forward had finished in every case, because the page-index copy runs on `forward_stream`. With PP2 the comm-overlap setting did not corrupt A in this run, although its first stage still handed 215 of 216 non-final chunks to the sender before their forward had finished. The PP4 run above shows that failure.

Unit tests: the new test passes. The existing `test_prefill_result_polling.py`, `test_mooncake_transfer_batching.py` and `test_prefill_complete_integration.py` under `test/registered/unit/disaggregation/` still pass.

## Speed Tests and Profiling

Same PP4 setup, `python3 -m sglang.bench_serving --backend sglang --dataset-name random-ids --random-input-len 16384 --random-output-len 128 --random-range-ratio 1 --num-prompts 96 --max-concurrency 8`, one run each:

| Prefill PP comm | `--pp-async-batch-depth` | Version | Req/s | Input tok/s | Mean TTFT (ms) | P99 TTFT (ms) | Mean TPOT (ms) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| default | 0 | before | 5.24 | 85,859 | 600 | 1,128 | 7.05 |
| default | 0 | after | 5.24 | 85,860 | 603 | 1,286 | 7.06 |
| default | 1 | before | 5.19 | 85,092 | 596 | 1,133 | 7.23 |
| default | 1 | after | 5.15 | 84,454 | 609 | 1,221 | 7.19 |
| `SGLANG_PP_COMM_OVERLAP=1` | 0 | before | 5.24 | 85,867 | 595 | 1,113 | 7.13 |
| `SGLANG_PP_COMM_OVERLAP=1` | 0 | after | 5.23 | 85,622 | 599 | 1,134 | 7.13 |

The wait happens on the transfer worker thread, so the scheduler is never blocked. With `--pp-async-batch-depth 0` throughput and mean latency are unchanged: the event has normally completed by the time the worker reaches it. With `--pp-async-batch-depth 1` the last stage's worker now waits on every non-final chunk (see the counters above). In this single run, the fixed version has about 1% lower request throughput and 13 ms higher mean TTFT. P99 TTFT over 96 requests varies from run to run.
