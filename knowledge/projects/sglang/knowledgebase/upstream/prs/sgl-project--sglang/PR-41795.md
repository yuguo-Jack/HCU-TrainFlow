# [Fix] Preserve launcher identity for worker failure signals

[Upstream PR](https://github.com/sgl-project/sglang/pull/41795) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #41539. If a launcher dies while a spawned worker is importing modules, the worker can be reparented to PID 1 before it records its error-notification target. A later startup failure then sends SIGQUIT to init instead of the original launcher.

The parent-selection approach comes from #40596, separated into this focused fix following [the author's suggestion](https://github.com/sgl-project/sglang/issues/41539#issuecomment-5895127517).

## Modifications

- Resolve the original launcher through `multiprocessing.parent_process()` in scheduler, detokenizer, data-parallel controller, multi-detokenizer router, and watchdog startup.
- Capture the psutil process identity, then check the multiprocessing parent sentinel. A dead launcher raises `NoSuchProcess` instead of falling back to an adoptive parent; the ordering also rejects an already-reused launcher PID.
- Preserve the existing OS-parent fallback outside multiprocessing and allow a legitimate PID-1 launcher to receive notifications.
- Add five CPU regression/compatibility tests, including real `spawn` and `forkserver` notification delivery. Register them in `base-a-test-cpu`.

## Accuracy Tests

Linux CPU container, based on current main `fc9bdc8a3e`:

```text
python test/registered/unit/utils/test_parent_process.py -v

```

Restoring the old `psutil.Process().parent()` lookup makes three regression cases fail (forkserver targeting, missing launcher, and PID reuse), while PID-1 and non-multiprocessing compatibility still pass. Moving the sentinel check before process-identity capture also makes the PID-reuse case fail.

Separately ran 12 lifecycle scenarios in disposable Linux containers with private PID namespaces: both entrypoints, three scenarios, on baseline and patched code.

| Scenario | Main | This patch |
| --- | --- | --- |
| Launcher exits before worker startup captures its parent | Scheduler and detokenizer send SIGQUIT to PID 1 | Both raise `NoSuchProcess`; no signal attempted or received |
| Live launcher outside PID 1 | Launcher receives SIGQUIT | Preserved |
| Legitimate launcher at PID 1 | Launcher receives SIGQUIT | Preserved |

These runs used the real imported detokenizer startup with an intentionally missing local tokenizer, and the real imported scheduler entrypoint with model/config dependencies stubbed and a real closed startup pipe producing `BrokenPipeError`. No GPU inference or full serving validation was run.

All applicable pre-commit checks and `git diff --check` passed.
