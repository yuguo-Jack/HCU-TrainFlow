# [Fix] disagg: Size the decode reserve by what a request can still decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/46269) · state: open · merged: False

## Original PR description

## Motivation

On a PD decode server, a request within `--num-reserved-decode-tokens` (default 512) of the decode KV pool size passes every intake check and then never fits, even when the pool is empty. There are two ways to get there:

1. **Fresh prompt.** `pop_preallocated` never preallocates it and stops at it, so every request queued behind it waits as well.
2. **Retracted request.** A request that has decoded most of its `max_new_tokens` and then gets retracted never resumes. `pop_preallocated` also subtracts its reservation from every fresh request's budget, so nothing is admitted after it. The decode server stalls until the requests time out or are aborted. This case does not need a long prompt: a 64-token prompt that has generated close to its limit is enough.

The decode server runs the normal intake. `init_req_max_new_tokens` clamps `max_new_tokens` so the prompt plus its output fits the pool, and `validate_input_length` and `_check_if_req_exceed_kv_capacity` accept the request. `_required_admission_tokens` (preallocation) and `_prealloc_required_tokens` (retracted resume, and the retracted reservation charged in `_allocatable_token_budgets`) then add the full `num_reserved_decode_tokens` on top of the request's KV. That is up to 512 tokens more than the request can still decode.

This is reachable whenever the decode pool holds fewer tokens than `context_len`, so that the pool bounds intake. That is common for long-context models on decode nodes with a small KV budget.

## Modifications

- New `DecodePreallocQueue._decode_reserve_tokens(req)` returns `min(num_reserved_decode_tokens, max_new_tokens - len(output_ids) + 1)`, which is the decode slots the request can still use, including the pending token. Both `_required_admission_tokens` and `_prealloc_required_tokens` use it for the request's own reservation, and the SWA side follows the full side as before. The reservations kept for other active requests (`num_reserved_decode_tokens * n_active`) are unchanged.
- New CPU test `test/registered/unit/disaggregation/test_decode_prealloc_admission.py`, with page sizes 1 and 16. It takes the decode limits from `TpModelWorker.get_worker_info` and the request from `init_req_max_new_tokens` and `validate_input_length`, and uses a real token allocator. The KV receiver, the final `_pre_alloc` copy and `restore_kv_cache` are stubbed, as in the existing prealloc queue tests.
  - `test_longest_accepted_prompt_is_preallocated_on_an_empty_pool`: the longest prompt the intake accepts must be preallocated.
  - `test_retracted_request_near_its_length_limit_resumes_on_an_empty_pool`: a retracted request one token short of its `max_new_tokens` must resume.
  - On `main`, all 4 subtests fail.

I also ran the new test and the existing CPU tests that drive the prealloc queue (`test_priority_scheduling_disaggregation.py`, `test_decode_radix_lock_ref.py`, `test_decode_retraction_backup.py`, `test_mamba_capacity.py`, `test_prefill_complete_integration.py`, `test_unified_memory_move_gate.py`, `test_decode_queue_cleanup.py`, `test_admission_abort_not_enqueued.py`) on both trees. The only failures specific to `main` are the 4 new subtests, and nothing fails only on this branch. The other failures are the same on both trees. All of them are in `test_decode_retraction_backup.py` and need CUDA, which my machine does not have.

I also ran a scheduler-level check. A CPU driver runs the real `Scheduler` in decode mode with the fake transfer backend and the decode radix cache on, so requests go through `process_decode_queue`, preallocation, the fake transfer, the commit of the synthetic handoff token, and decode. On `main`, all 30 seeds stopped making progress: the prealloc queue held dozens of requests while the pool was completely free, for example `prealloc 57 … free 256` on a 256-token pool. With this change all 30 seeds finished. One caveat: the driver's pools are small (160–512 tokens), so the default 512-token reserve alone exceeds the pool and every request is affected. On a production-sized pool, only requests close to capacity hit it.

I have not run an end-to-end PD deployment.
