# [sgl-router] Enable broader Dynamo rendering and token forwarding

[Upstream PR](https://github.com/sgl-project/sglang/pull/40533) · state: closed · merged: False

## Original PR description

## Motivation

HF-template models already render locally, but SGLang parity gates prevent forwarding tokens for tools, reasoning, text arrays, and continuations. Allow Dynamo-rendered text requests to use router-generated `input_ids` without requiring SGLang behavior parity.

Stacked on #40532; review this branch against `codex/router-deepseek-v41-parity`.

## Modifications

- Remove parity-only forwarding gates across routing policies and enable Dynamo's native Inkling formatter.
- Retain original messages, caller IDs, the forwarding opt-out, and worker processing for media, template overrides, and rendering failures.
- Reuse compact forwarding tests and simplify the documentation; net removal of 213 lines.

## Accuracy Tests

Passed: 714 library tests, 23 input-ID proxy tests, and 7 tokenizer component tests, including existing DeepSeek/Kimi fixtures. Inkling's native prompt and HF-template tools, reasoning, text arrays, and continuations are covered.

`cargo clippy --locked --workspace --all-targets -- -D warnings`, nightly formatting, and `git diff --check` passed. No live-model generation evaluation.

- ShangmingCai · comment · 2026-09-21T13:00:03Z · [source](https://github.com/sgl-project/sglang/pull/40533#discussion_r4062329223)

File: `experimental/sgl-router/src/server/routes/chat/preparation.rs` · line 496

forwarding `reasoning_effort` and `chat_template_kwargs` means we own the whole reasoning-control table, and `template_kwargs` implements three generic kwargs.

hunyuan is the concrete one. `normalize_hunyuan_reasoning_effort` (`parser/hunyuan_reasoning.py:17`, called at `serving_chat.py:1295`) folds `medium|high|xhigh|max` to `high` and `minimal|low` to `low` before rendering, so `reasoning_effort: "max"` renders `high` on the engine and `max` here. it then pops `reasoning_effort` out of `chat_template_kwargs`, so top-level wins there, while our `or_insert` lets `chat_template_kwargs` win — precedence is inverted, not just the value. the template consumes the kwarg directly (detection keys on `reasoning_effort` + `reasoning_mode_token` + `no_think`, `template_detection.py:187`), so both are prompt-visible, and the engine 400s on an effort outside that set where we render it.

nemotron-3-super is the other row: `effort_kwarg="low_effort"` (`template_detection.py:213`) sets `low_effort=True` for `reasoning_effort: "low"`, we don't.

both need `--reasoning-parser hunyuan` / the matching template on the worker, which isn't visible from here. that's the argument for keeping these two fields gated rather than chasing rows.

- ShangmingCai · comment · 2026-09-21T13:00:03Z · [source](https://github.com/sgl-project/sglang/pull/40533#discussion_r4062329244)

File: `experimental/sgl-router/src/server/routes/chat/preparation.rs` · line 590

dynamo rewrites messages for templates its probes see raising — demotes non-leading system, coalesces consecutive users (`formatters.rs:63`). the engine doesn't rewrite, it 400s, so these requests stop erroring and start generating off a prompt the engine never built.

and `demote_nonleading_system` is `nonleading_system || mid_after_assistant`, so for a template that takes `[sys,user,sys]` but rejects it after an assistant turn the rewrite also applies to the shape the engine renders fine. no shipped template in hand that hits that, but the mechanism is there.

File: `experimental/sgl-router/src/tokenizer/chat_formatter.rs` · line 64

inkling can't forward as-is. `_encode_messages` calls `render_inkling_messages(..., add_generation_prompt=False)` (`serving_chat.py:596`) and the renderer only appends `<|message_model|>` under that flag (`inkling_renderer.py:172`), while `should_add_generation_prompt` is hardcoded true — one extra token on every request.

two more on that path: the engine's inkling branch never calls `_handle_last_assistant_message`, so a trailing assistant turn stays a closed model turn instead of becoming a user turn, and its continuation prefix is `MESSAGE_MODEL + CONTENT_TEXT + text` (`serving_chat.py:604`) where we append bare text. routing-only is fine here, forwarding isn't.
