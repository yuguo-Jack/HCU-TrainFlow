# feat(Qwen3.8-Flash-Next): avoid padded PLE prefill activations

[Upstream PR](https://github.com/sgl-project/sglang/pull/43032) · state: open · merged: False

## Original PR description

## Summary

This PR fixes Qwen3.8/Qwen4Exp PLE prefill temporary activation amplification for mixed-length batches.

The current PLE short-conv prefill path materializes packed tokens as a dense tensor:

```text
[num_requests, max_query_length, ple_channels]
```

This means short requests are padded to the longest request in the batch. For skewed mixed-length batches, the temporary activation memory scales with:

```text
num_requests × max_query_length × ple_channels
```

instead of:

```text
sum(query_lengths) × ple_channels
```

This can allocate several GiB of temporary tensors and cause OOM even when KV cache utilization is still low.

This PR adds a packed varlen Triton path for ordinary PLE prefill so short-conv memory and compute scale with the actual scheduled tokens.

## Changes

- Add a packed varlen PLE prefill short-conv Triton kernel.
- Add a separate state-writeback kernel for main and radix-tracking short-conv states.
- Preserve the existing decode and MTP target-verify paths.
- Preserve the existing PyTorch path as a fallback.
- Add live `query_start_loc` metadata for breakable prefill CUDA Graph replay.
- Enable the fused path only for supported NVIDIA CUDA BF16 inputs.
- Add direct correctness tests for mixed-length, equal-length, empty rows, chunked prefill, radix tracking, FP32 state storage, fallback, and graph live metadata.

The change is limited to five files and does not modify the scheduler, cache ownership, MTP state-commit protocol, N-gram logic, or PLE gate logic.

## Correctness

The packed implementation was compared against the existing padded PyTorch path using real Qwen3.8 PLE dimensions:

```text
channels = 10240
kernel size = 4
dilation = 3
state length = 9
dtype = BF16
GPU = NVIDIA H20
```

Covered cases include:

- mixed-length batches
- equal-length batches
- chunked prefill
- empty request rows
- radix state tracking
- FP32 state storage with BF16 materialization semantics

All tested cases produced element-wise identical outputs and final states:

```text
output max absolute error = 0
state max absolute error  = 0
torch.equal(output)       = True
torch.equal(state)        = True
```

Service-level validation also covered ordinary mixed-length prefill, NEXTN MTP3, decode CUDA Graph, breakable prefill CUDA Graph, and target-verify CUDA Graph. Baseline and feature outputs had identical hashes, and NEXTN MTP3 preserved `accept length = 4.0` and `accept rate = 1.0`.

## PLE short-conv performance

The packed varlen path reduces PLE prefill short-conv latency by removing dense padding, transpose/concatenation, packed-output gathering, and separate PyTorch state updates.

The following H20 BF16 results compare the existing padded prefill short-conv path with the packed varlen convolution and state-writeback kernels. Both sides exclude the common SiLU operation.

| Query lengths | Padded path | Packed varlen | Speedup |
|---|---:|---:|---:|
| `[8192, 1, 1, 1]` | 11.84 ms | 0.70 ms | 16.85x |
| `[4096, 2048, 1024, 512]` | 6.57 ms | 0.66 ms | 9.94x |
| `[2048, 2048, 2048, 2048]` | 4.11 ms | 0.70 ms | 5.86x |
| Chunked prefill, `8192` as `4 × 2048` | 4.34 ms | 0.84 ms | 5.14x |
| Radix state tracking, `[4096, 2048, 1024, 512]` | 6.59 ms | 0.67 ms | 9.81x |

## Memory results

For the most skewed kernel workload:

```text
query lengths = [8192, 1, 1, 1]
```

| Metric | Padded path | Packed varlen |
|---|---:|---:|
| Incremental peak allocated memory | 2081.5 MiB | 160.1 MiB |
| Mean short-conv latency | 11.84 ms | 0.70 ms |

In the mixed-length serving matrix, process-level GPU peak memory changed from:

```text
97,039 MiB -> 90,097 MiB
```

This reduced the observed peak by approximately 6.8 GiB.

The padded implementation also OOMed at `--mem-fraction-static 0.85` in the tested mixed-length workload because of a roughly 3 GiB short-conv temporary allocation. The packed implementation completed successfully.

## End-to-end check

For a mixed-length workload:

```text
[L, L/8, L/32, L/256, L/1024, 8]
```

with TP8 + EP8, `--chunked-prefill-size 32768`, and 64 output tokens:

| Maximum input length | Input throughput change | Median E2E change |
|---:|---:|---:|
| 32K | +7.32% | -6.91% |

This PR is primarily a memory/OOM fix, not a general long-context throughput optimization.

## Usage

No new command-line option is required.

The packed varlen path is selected automatically for supported Qwen3.8/Qwen4Exp PLE ordinary prefill batches on NVIDIA CUDA with BF16 inputs.

Example:

```bash
python3 -m sglang.launch_server \
  --model-path <Qwen3.8-Flash-Next-model-path> \
  --tp 8 \
  --enable-ep-moe \
  --ep-size 8 \
  --chunked-prefill-size 32768
```

The existing fusion switch can be used to force the original fallback path for debugging:

```bash
SGLANG_ENABLE_QWEN4_PLE_FUSION=0 \
python3 -m sglang.launch_server \
  --model-path <Qwen3.8-Flash-Next-model-path> \
  --tp 8
```

Unsupported devices, dtypes, state layouts, and convolution configurations automatically use the existing PyTorch fallback.
