# [Fix] sampling: Count the stop_regex window bound in UTF-8 bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/47280) · state: open · merged: False

## Original PR description

## Motivation

A `stop_regex` can miss its match when the matched text is split into more tokens than the regex bound allows for. The request then runs to `max_new_tokens`, while the same text passed as `stop` stops in the right place.

The bound comes from `get_max_seq_length()`. It counts every literal, character class and `.` as one token, and the comment above it says one buffered character is one token in the worst case. That stops being true when a byte-level BPE or SentencePiece byte-fallback tokenizer spends one token per UTF-8 byte on a rarer character. For a request that only has a `stop_regex`, `Req.tail_str()` decodes the last `stop_regex_max_len + 1` tokens, so `停止` (bound 2) gets a window of 3 tokens. On TinyLlama `停` is three byte tokens `<0xE5> <0x81> <0x9C>` and `止` is one token. The window holds the last two bytes of `停` plus `止`, and `re.search` never sees the match.

I drove the real `Req.update_finish_state` one token per step with HF tokenizers on main (68e57f4), comparing `stop` and `stop_regex` on the same text.

```
TinyLlama-1.1B-Chat-v1.0, "思考过程很长。停止 后面不该输出" (23 tokens)
  stop='停止'          finished at token 16/23
  stop_regex='停止'    NOT finished after all 23 tokens (stop_regex_max_len=2)

gpt2, "Done 🛑 trailing text" (6 tokens)
  stop='🛑'            finished at token 4/6
  stop_regex='🛑'      NOT finished after all 6 tokens (stop_regex_max_len=1)
  stop_regex='[🛑⛔]'  NOT finished after all 6 tokens (stop_regex_max_len=1)

Qwen2.5-0.5B-Instruct, "Done 🫠 trailing text" (6 tokens)
  stop='🫠'            finished at token 4/6
  stop_regex='🫠'      NOT finished after all 6 tokens (stop_regex_max_len=1)

Qwen2.5-0.5B-Instruct, "思考过程很长。龘龘 后面不该输出" (13 tokens)
  stop='龘龘'          finished at token 8/13
  stop_regex='龘龘'    NOT finished after all 13 tokens (stop_regex_max_len=2)
```

It only happens when a character costs more tokens than the bound gives it. On Qwen2.5 `停止` is a single token and `stop_regex='停止'` already stops at token 5/10, and `é` works on gpt2. Emoji and rarer CJK characters are the usual way to hit it, current tokenizers included.

## Modifications

The bound is now counted in UTF-8 bytes. A literal counts its UTF-8 length. A class made only of literals and ranges counts its widest member, taking the upper end of each range. `.`, negated classes and the categories `\d`, `\w` and `\s` count 4, since for str patterns they also match non-ASCII characters. `NOT_LITERAL` (a lone `[^a]`) stays on the existing unbounded fallback.

Patterns made only of ASCII literals and ASCII ranges keep their bound, so `[a-z]{3}` is still 3. Patterns with `.`, a category or a negated class get a wider window. `\d{6}` goes from 6 to 24 and `.{40}` from 40 to 160, because `\d` matches fullwidth and other non-ASCII digits too. The cost of that is in the speed section below.

The Rust server sizes the same window in `rust/sglang-server/src/utils/regex.rs`, and the scheduler skips the Python `normalize()` for requests that arrive already normalized. It already counted literals in bytes, but `HirKind::Class(_)` was 1, so `.` and `[🛑⛔]` undercounted there in the same way. It now uses `Class::maximum_len()` from regex-syntax. The admission corpus in that file stores measured Python bounds in `py_max_len` and checks that every admitted pattern's Rust bound is at least that. I re-measured every row against the new `get_max_seq_length()` and 11 rows change. With only the Python side fixed, the corpus test fails with `UNDER-estimate` on `\d{6}`, `[\d\s]{2}` and `(?i)\d{4}-\d{2}`, so the two sides have to move together. Where a row's `rust_bound` changes with the new Class arm I updated it too, and the pinned `\d{6}` and `\d{3}` bounds in the Rust tests go from 6 and 3 to 24 and 12.

One gap is left on the Python side. Under `(?i)` a letter can also match a wider case variant, for example `k` matches the Kelvin sign U+212A (3 bytes), and the bound still counts it as 1. regex-syntax folds case into the class, so Rust already gives 3 for `(?i)k`. Doing the same in Python needs an inverse case table, and it only matters if the model emits one of a handful of characters like U+212A or U+017F, so I wrote it down in the comment instead.

In `test_sampling_params.py` I added bound cases and updated two existing expected values, `.` is now 4 and `(foo|bar)\d{2}` is now 11. `test_stop_str_speculative.py` gets a Req-level regression with a fake tokenizer that emits one token per UTF-8 byte, and checks that `停止` and `[🛑⛔]` stop at the right `finished_len`. `regex.rs` gets `class_bound_counts_utf8_bytes`.

#36728 fixes the same kind of bug for plain `stop` strings and only touches `stop_str_max_len`, so the two changes are independent. #30933 and #38598 make `NOT_LITERAL` count as 1 in the same block, so whichever lands second needs a small rebase. After this change `NOT_LITERAL` should count 4, otherwise `[^a]` undercounts on non-ASCII output. #46346 adds corpus rows to `regex.rs` with `py_max_len` measured by the old function (`\d{1, 3}` is 7 there and 10 with this change), so those rows need re-measuring whichever lands first.

## Accuracy Tests

Not a model forward change. With the fix, the same script gives this.

```
TinyLlama   stop_regex='停止'    finished at token 16/23
gpt2        stop_regex='🛑'      finished at token 4/6
gpt2        stop_regex='[🛑⛔]'  finished at token 4/6
Qwen2.5     stop_regex='🫠'      finished at token 4/6
Qwen2.5     stop_regex='龘龘'    finished at token 8/13
```

Each one now stops at the same token as the matching `stop` string. I also ran it with 3 and 8 tokens per step, as speculative decoding does, and `finished_len` matches `stop` in every case.

Python unit tests, CPU only.

```
python -m pytest test/registered/unit/sampling/test_sampling_params.py \
  test/registered/unit/managers/test_stop_str_speculative.py \
  test/registered/unit/entrypoints/openai/test_matched_stop.py \
  test/registered/unit/api/v1/test_parity.py
103 passed, 3 warnings, 67 subtests passed
```

With the new tests and main's `sampling_params.py`, `test_sampling_params.py` gives 6 failed, 75 passed and `test_stop_str_speculative.py` gives 2 failed, 10 passed. Running each file directly with `python3 <file>` also passes (81, 12, 1 and 9 tests).

For Rust I compiled `regex.rs` on its own against regex-syntax 0.8.11 and ran its tests, 13 passed. With the old Class arm and the re-measured corpus, 5 fail, including the three `UNDER-estimate` rows above. I could not build the whole workspace offline on this machine, so the two updated numbers in `message/sampling.rs` are only checked against the same function and CI will be the first full run. The pre-commit hooks pass on all five files, except the workspace clippy hook, which needs the same full build.

## Speed Tests and Profiling

Only patterns with `.`, a category or a negated class get a wider window, and the part that grows is decoding the tail on each step. With HF fast tokenizers, decoding 7 tokens against 25 (the `\d{6}` window before and after) takes 1.5 us against 4.6 us on Qwen2.5 and 2.8 us against 8.2 us on TinyLlama. For `.{40}`, 41 tokens against 161 takes 6.4 us against 21.2 us and 12.3 us against 45.8 us. That is per decode step, and only for requests that set such a `stop_regex`.
