# [MoE] Add out-of-tree expert executor selection

[Upstream PR](https://github.com/sgl-project/sglang/pull/41635) · state: open · merged: False

## Original PR description

## Motivation

MoE model implementations such as Gemma4 own their routing semantics: they compute router logits, choose the top-k experts, and pass a `TopKOutput` to an expert executor. Today, `get_moe_impl_class()` only chooses between SGLang's built-in executor classes from process-wide MoE settings.

An out-of-tree platform may need to provide a complete expert executor because its parameter ownership, dispatch, and combine lifecycle do not fit inside a built-in `FusedMoE` runner core. SGLang already lets OOT platforms optionally provide subsystem classes such as full graph backends while preserving an upstream fallback. This change applies the same platform-factory pattern to MoE expert executors.

The platform decision is integrated into the existing `get_moe_impl_class()` selector, rather than adding a second selector. Model context keeps an override scoped to compatible models, while callers that do not pass context retain the existing behavior.

## Modifications

- Add `MoeExpertExecutorContext`, which describes the model family, layer and expert dimensions, activation/reduction behavior, quantization, checkpoint prefix, redundant experts, and TP/EP sizes used during executor selection.
- Add the optional `SRTPlatform.get_moe_expert_executor_cls(context)` factory. Its default implementation returns `None`.
- Extend `get_moe_impl_class(quant_config, *, context=None)` to consult the OOT platform when model context is available. If the platform returns `None`, the existing `DeepEPMoE` versus `FusedMoE` selection remains unchanged.
- Pass context from `Gemma4MoE` into the existing selector. Gemma4 continues to construct its own `TopK` router and passes the resulting `TopKOutput` unchanged to the selected executor.
- Keep `context` optional and keyword-only, so every existing MoE model caller retains its current behavior.

## Accuracy Tests

No numerical kernels or routing formulas are changed. Added CPU unit coverage verifies:

- selection is scoped by model context;
- an out-of-tree platform can decline the override;
- declining an override preserves the existing `DeepEPMoE` backend selection;
- in-tree platforms retain the existing default executor;
- Gemma4 forwards model, quantization, checkpoint-prefix, and parallel context;
- the selected executor receives the existing constructor contract; and
- Gemma4 produces the routing output before passing that exact object to the executor.
