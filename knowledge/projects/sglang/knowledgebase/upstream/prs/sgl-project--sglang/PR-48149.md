# [Fix] dwdp: Retry local VMM allocation after CUDA OOM

[Upstream PR](https://github.com/sgl-project/sglang/pull/48149) · state: open · merged: False

## Original PR description

## Motivation

DWDP local weight conversion can run out of memory while completed source shards are reclaimable. Resizing their storage to zero can leave memory in the PyTorch allocator cache, while `cuMemCreate` allocates directly through the CUDA driver. The helper currently clears the cache only after copying every shard.

Clear cached memory when local physical allocation runs out of memory, then retry once per shard. Refs #41077; follows the reporter's cache-release work in #41086 and #41093.

## Modifications

- Classify local `cuMemCreate` OOM with a `RuntimeError` subclass, preserving `check_drv` and other error handling.
- On this exception, enter the allocation device context, clear the PyTorch cache, and retry once in the existing VA reservation with the same size and properties. Other allocation stages and copy failures do not trigger a retry. Keep the final cache clear.
- Register mapped handles before copying and release owned resources on failure. Attempt all cleanup steps while preserving the primary exception. Add registered CPU regression tests for recovery, failure boundaries, and handle ownership.

Failure recovery cannot restore released source storage; driver cleanup errors may leave resources allocated. Native cache clearing may also affect other devices' allocator caches. This patch targets current main and overlaps the `VmmBackend` refactor in #40763.

## Accuracy Tests

**Linux ARM64 CPU:** all eight tests pass with zero skips:

```bash
python test/registered/unit/layers/moe/dwdp/test_transport.py -v
```

The fixture models CUDA calls and isolates unrelated MoE initializers, exercising the production modules with real CPU tensor storage. The baseline raises `RuntimeError: cuMemCreate(local): 2` on injected physical OOM. Fresh-process imports of transport and VMM also pass. Environment: Python 3.12.9, Torch 2.14.1+cpu, Transformers 5.19.0, Triton 3.8.0.

**L4 OOM recovery test:** the source contains 96 shards of 128 MiB (12 GiB total), with a separate 12 GiB target. Both versions encounter CUDA OOM on the 79th physical allocation. The original helper propagates the error; the patched helper clears 9.75 GiB of released-source cache, retries successfully, and completes all 12 GiB of byte-for-byte readback. After target teardown, tracked resources are zero and driver-free memory returns to its pre-test level. Environment: Torch 2.11.0+cu130, CUDA bindings 13.0.3, native allocator.

[Reproduction scripts, versions, and raw results](https://github.com/user-attachments/files/34315338/sglang-dwdp-oom-evidence.zip). The GPU-tested candidate and submitted production code have identical Python ASTs; only formatter-required line wrapping differs.

GPU validation covers the single-device component. Full-model, multi-rank, GPU rollback-fault, and Torch 2.13 runs were not performed.
