# [Fix] [AMD] triton-moe: Clamp SwiGLU on HIP

[Upstream PR](https://github.com/sgl-project/sglang/pull/44543) · state: open · merged: False

## Original PR description

## Motivation

A model with `swiglu_limit` set (DeepSeek V4, GLM-5.3-Flash) crashes on the Triton MoE runner when every expert is local (TP only, no expert parallelism):

```
AssertionError: fused silu_and_mul_clamp kernel is CUDA/XPU only; HIP must disable SWIGLU_CLAMP_FUSION
```

`silu_and_mul_clamp` exists only for CUDA and XPU. The expert-filtered path is unaffected, because `act_and_mul_triton` applies the limit itself. HIP has no way through the non-filtered branch.

Related: #41136 carries this same clamp together with a different mHC change. This PR is only the clamp.

## Modifications

In `_fused_moe_kernel_sequence`, the HIP non-filtered path clamps the gate half from above and the up half to `±limit`, in place, then runs the regular `silu_and_mul`. That is the contract of the CUDA fused kernel and of the model's `swiglu_clamped`. The CUDA/XPU path still calls `silu_and_mul_clamp`.

## Accuracy Tests

On GLM-5.3-Flash BF16 RL, the same 4 steps with this clamp (Triton MoE) and without it (aiter MoE, which does not apply the clamp) agreed to three decimals on `train_rollout_logprob_abs_diff`: 0.087, 0.085, 0.061, 0.094. Pre-activations almost never exceeded the limit of 10 on this checkpoint, so the clamp is required for the kernel contract and did not move the logprob gap.

## Speed Tests and Profiling

The clamp is two in-place elementwise ops on the first GEMM output, and only on the HIP path that previously asserted. The Triton MoE run that applied it was slower than tuned aiter MoE (132–183 s vs 114–157 s per rollout step) for unrelated kernel reasons. The RL recipe keeps aiter MoE; this change is so the Triton runner can serve the same model on HIP.
