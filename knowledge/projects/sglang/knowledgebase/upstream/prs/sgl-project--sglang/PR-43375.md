# [HiCache] Fix host-pointer handling on WSL2

[Upstream PR](https://github.com/sgl-project/sglang/pull/43375) · state: open · merged: False

## Original PR description

## Motivation

I hit a CUDA illegal-memory-access error on WSL2 while HiCache was backing up Mamba state to host memory. The stack went through `transfer_kv_mamba_lf_pf` and `submit_device_to_host`; the CUDA watchdog reported the error while flushing pending backups.

I looked at the host pointers on the same RTX 5090 system. The CUDA capability query said registered host memory was supported, but `cudaHostGetDevicePointer` returned a device address different from the host address for a `cudaHostRegister` buffer. With PyTorch-pinned memory, the addresses matched, and a small CUDA kernel write to that buffer worked. This points to a host-pointer compatibility issue on this WSL2 setup, though I have only verified it on this machine.

The relevant setup was a Qwen3.8-family 27B NVFP4 target with a matching DFlash2 NVFP4 draft, FP8 KV cache, and HiCache configured with `page_first`, `write_through_selective`, and the `kernel` I/O backend. The run used ModelOpt FP4 quantization, `--max-total-tokens 175064`, `--max-mamba-cache-size 10`, Mamba `bfloat16` with the `extra_buffer` radix strategy, page size `64`, chunked prefill `4096`, and at most two running requests. At the time, `--mem-fraction-static` was `0.89` and `SGLANG_HICACHE_HOST_ALLOC` was unset. The original log showed 151,488 KV tokens; the memory fraction was later lowered to `0.78`. Before the fix, I saw the crash with different request contents, so it does not appear to depend on a particular prompt.

The relevant excerpt from the incident log is:

```text
2026-10-09T08:04:03Z INFO: "POST /v1/chat/completions HTTP/1.1" 200 OK
2026-10-09T08:04:04Z Decode batch, #full token: 19200, Mamba usage: 0.30
2026-10-09T08:04:08Z Prefill batch, #new-token: 4096, Mamba usage: 0.30
2026-10-09T08:04:09Z Prefill batch, #new-token: 4096, Mamba usage: 0.80
2026-10-09T08:04:09Z Process group watchdog: CUDA error: an illegal memory access was encountered
2026-10-09T08:04:09Z CUDA kernel errors might be asynchronously reported at some other API call.

File sglang/kernels/ops/mamba/transfer_mamba.py, line 74, in transfer_kv_mamba_lf_pf
File sglang/srt/mem_cache/pool_host/mamba.py, line 587, in _copy_tensor_all_layers_lf_pf
File sglang/srt/mem_cache/pool_host/mamba.py, line 729, in backup_from_device_all_layer
File sglang/srt/mem_cache/pool_host/base.py, line 433, in backup_from_device_all_layer_physical

File sglang/srt/managers/cache_controller.py, line 842, in start_writing
```

The `200 OK` is logged before the CUDA error; it does not mean the generation finished successfully. CUDA also warns that errors may surface asynchronously, so this stack identifies the path involved but not necessarily the exact faulting instruction.

## Modifications

When `SGLANG_HICACHE_HOST_ALLOC=auto` (the default), use PyTorch-pinned host allocations on WSL and keep `cudaHostRegister` on other platforms. `SGLANG_HICACHE_HOST_ALLOC=pin` and `register` allow users to override the choice.

The pinned allocator needs HiCache pinning enabled and the default host allocator. It raises a clear error for shared-memory or external/custom allocators rather than silently substituting a different allocation strategy. I added unit coverage for the selection logic and these unsupported cases, and documented the setting.

`test_hicache_host_register.py` passed all 19 tests using its `unittest` entry point. Registered-test lint and `git diff --check` passed. Pre-commit formatting and the full code-style checks were not run locally.

On the rebuilt image, the default `auto` setting selected PyTorch pinned memory on the WSL2 kernel. The serving test used `SGLANG_HICACHE_HOST_ALLOC=pin`. A controlled overlap test ran a 19,199-token prompt that generated 2,048 tokens, then submitted a second 4,099-token prompt 8 seconds later; it generated 128 tokens. Both chat-completion requests returned HTTP 200, the service remained healthy, and the logs contained no CUDA illegal-memory-access error. Mamba usage peaked at 0.60, below the 0.80 shown in the incident log. Since applying the change, I have also been able to run long-chain agent turns normally and have not seen the illegal-memory-access error again. The full project suite and upstream CI have not been run.

The incident log came from Python 3.12 and showed FlashInfer `0.7.0.post1` on SM120. The post-change runtime used PyTorch `2.14.1+cu130`, FlashInfer `0.7.0.post1`, and `sglang-kernel 0.4.9+cu130`. I did not capture the original runtime's immutable image digest or NVIDIA driver version, so these details should not be read as a complete lockfile for the failing run.
