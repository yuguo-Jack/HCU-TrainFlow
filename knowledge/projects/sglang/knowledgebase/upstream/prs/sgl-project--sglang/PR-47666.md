# [WIP][Perf]dsv41: Accelerate SM90 compact FP4 candidate scoring with CUDA 

[Upstream PR](https://github.com/sgl-project/sglang/pull/47666) · state: open · merged: False

## Original PR description

> **WIP — Draft PR.** This work will receive further updates. It is not ready to merge; the known numerical difference and remaining validation are documented below.

## Motivation

DeepSeek-V4.1 consumer indexer layers rescore the candidate blocks selected by a source layer before selecting their own attention indices. On SM90, the compact Triton scorer remains a significant decode cost: in the batch-64 measurement below, candidate scoring takes 21.18 ms of a 107.35 ms GPU decode round.

This PR adds a CUDA implementation of `fp4_index_logits_candidates` for SM90. It reads the existing paged FP4 cache directly and produces scores in the existing compact candidate order. In the measured Triton 3.6 configuration, candidate scoring is 4.50× faster and the complete GPU decode round is 15.89% shorter. Against Triton 3.7.1, CPU-observed steady decode round intervals fall by a median 6.24% across three batch-32 pairs and by 9.03% in one batch-64 pair. Output throughput also depends on speculative acceptance and serving load.

This work continues the existing candidate-block workflow: source layers publish candidate blocks, and consumer layers score only those blocks. SM100 already uses this workflow through its DeepGEMM sparse backend. Building on [#40860](https://github.com/sgl-project/sglang/pull/40860), which provides compact Triton candidate scoring on SM90, this PR adds a dedicated SM90 CUDA scorer to reduce candidate-scoring overhead during decode/verify.

The rebased #40860 dependency is kept in a separate commit; the CUDA implementation and tests are another commit. Once the upstream base contains the dependency, the remaining change should be the CUDA increment. All performance comparisons below already include the rebased #40860 implementation in the Triton baseline.

## Modifications

- Add a JIT-compiled CuTe/CUDA scorer for SM90 BF16 queries with 32 heads, head dimension 128, and compression ratios 1 and 2, with Triton fallback for unsupported configurations.
- Score compact candidates directly from the existing paged FP4 cache, using natural D128 BF16 MMA, optimized FP4 decoding, Q/weight reuse, and register-based head reduction.
- Preserve the existing input/output and candidate-selection interfaces, and add numerical, masking, layout, dispatch, downstream top-k/finalizer, and CUDA Graph replay tests.

The CUDA path preserves the existing BF16 rounding sites and scale flush-to-zero behavior. Natural D128 accumulation changes the floating-point accumulation order relative to the parity-split Triton implementation; bitwise-identical scores and selections are not guaranteed for every input.

The numerical reference decodes the same quantized inputs independently with CPU PyTorch FP64, preserves the specified BF16 conversions, and propagates fixed FP32 accumulation bounds through the dot product and head reduction. It checks finite scores against those bounds and checks masks exactly. Top-512/top-1024 checks cover selection cutoffs and the actual downstream consumer/finalizer; they are separate from score-error checks.

In a separate migration check on Torch 2.9.1+cu129/Triton 3.5.1, six fixtures comprising 18,336 scores matched the original CUDA implementation through `65f7b9f` bit for bit. The real downstream top-k/finalizer produced identical final indices for CUDA and Triton on those six fixtures. This establishes the checked migration behavior, not universal CUDA/Triton equivalence.

**Known numerical difference:** an earlier saved fixture, case 065, has a one-candidate replacement in the actual top-1024 selected set relative to the frozen historical Triton baseline. It remains unresolved and was not rerun as part of the 227-test post-rebase suite. Case 058 has a strict `torch.topk` diagnostic difference but matching actual consumer selected sets. The historical 66-shape/594-state sweep was not repeated during integration. Separate diagnosis of five score outliers located their differences at BF16 dot-product rounding boundaries; those five inputs had matching final indices, but do not clear case 065.

No model task-accuracy or log-probability equivalence result is claimed. The known selection difference needs a numerical-acceptance decision supported by model-level validation, or an implementation change, before merge.

## Speed Tests and Profiling

**Setup:** DeepSeek-V4.1-Flash, 8×H20, TP8, Torch 2.13.0+cu129/CUDA 12.9. Humming, DSpark block size 5 with adaptive speculation disabled, overlap scheduling, bounded replay, and decode CUDA Graphs remain enabled. Workloads use random token IDs, 24,576 input tokens and 500 output tokens per request, seed 42, temperature 0, and `ignore_eos`.

For each A/B pair, the Triton and CUDA variants use matching inputs, launch parameters, and shared runtime adaptations. Serving traces separately confirm that the intended scorer runs on all eight ranks. Benchmark revisions are A=`8a18da3b9f` and B=`a3f3ed6694`; their source difference is the nine-file CUDA increment. The shared legacy MLA compatibility and FlashInfer runtime-library selection fix are benchmark-environment adaptations, outside that increment.

The performance measurements below were collected on base `2d44b55010`, before rebasing the submission onto main `8368f86fd7`. End-to-end performance has not been remeasured on that new base.

### GPU attribution on Triton 3.6.0

Same host, batch 64, alternating A1 → B1 → A2 → B2, with a fresh server process for each capture. GPU measurements use a fixed 30-round decode window per capture, validated across all ranks for constant batch/request membership, graph execution, and no prefill, completion, or retraction in the selected window. Values below are rank-0 averages across the two captures per variant.

| Metric | Triton | CUDA | Change |
|---|---:|---:|---:|
| Candidate GPU kernel time per decode round, four calls | 21.181 ms | 4.709 ms | **4.50× faster** |
| Complete GPU decode-round period | 107.354 ms | 90.293 ms | **−15.89%** |
| CPU launch interval in separate unprofiled controls | 106.957 ms | 90.168 ms | **−15.70%** |

Candidate kernels save 16.47 ms per round, compared with 17.06 ms saved over the complete GPU round. Measured overlap between candidate kernels and other GPU work is approximately 0.001 ms per round. This supports candidate scoring as the main observed source of the round-time reduction. The unprofiled control uses CPU timestamps and is not a GPU-runtime measurement.

The median paired throughput change is −0.08%; the marked +2.32% in the table is the ratio of per-variant medians and does not establish a consistent throughput gain. All runs are retained; the current result is an observed reduction in decode round intervals, with unstable throughput and acceptance.
