# [Feat] hicache: Add KVCR storage backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/45647) · state: open · merged: False

## Original PR description

## Motivation

Add [KV Cache Runner (KVCR)](https://github.com/ai-dynamo/kvcr) as an optional L3 storage backend for HiCache. This enables local DRAM caching and router-guided KV reuse between workers through SGLang's existing host-staged storage path.

## Modifications

- Add `--hicache-storage-backend kvcr` with storage lookup, backup and restore operations.
- Forward request-scoped source hints and cache-key namespaces through HiCache prefetch and storage operations.
- Publish actual KVCR store and eviction events separately from GPU/HiCache host-cache events, allowing Dynamo to identify KVCR-owned source blocks correctly.
- Add backend documentation and regression coverage for storage operations, rank coordination and inventory publication.

Build and usage guide: [KVCR #114](https://github.com/ai-dynamo/kvcr/pull/114).

## Accuracy Tests

- Storage unit tests: **46 passed**, plus **78 subtests**.
- Qwen3-0.6B BF16: **eight same-host TP1/TP2 cases** passed across Python and Rust radix cores. HiCache-only prefixes produced no KVCR peer hint; KVCR-only prefixes produced genuine router hints and restored **192/256 tokens** with matching transfer-byte digests and output token IDs.
- Quick-start serving and request checks: cold reuse **0/2048**, destination reuse **1984/2048**, **16 matching output token IDs**, and successful delivery of **31 blocks / 62 spans / 227,540,992 source bytes**. No failed or partial transfers were observed in these functional tests.

## Speed Tests and Profiling

Not benchmarked. Validation covers same-host functionality, not performance, cross-host RDMA, hybrid models or disaggregated P/D.

Dynamo reads this `dp_rank` as the worker's DP rank and expects one source per rank in `0..dp_size * attn_dp_size`. `_generate_storage_config` sets it to `attn_dp_rank`, or to `0` when DP attention is off. With `--dp-size 2` and no attention DP, both replicas report `dp_rank: 0`, and `control_address()` gives them the same control port. Dynamo then rejects the incomplete rank map and the worker fails to register; past that, the second replica's lazy `_start()` would fail to bind. With `dp_size > 1` plus attention DP, `attn_dp_rank` restarts at 0 in each replica, so the same applies.

Could KVCR use the global DP rank for both the reported source and the port offset? If DP replicas are out of scope for now, rejecting them at KVCR startup with a clear error would also work.

[by Claude Code] **Severity: perf | Confidence: Medium**

**Issue**

This loop does not stop when the scheduler revokes the prefetch during confirmation. `is_terminated()` only sets `accepted[0]` to 0, so the loop moves to the next smaller boundary and calls `confirm_lookup` again. For KVCR, each call fetches the trailing Mamba/SWA checkpoint from the peer and takes a new claim, and each step adds one all-reduce. The prefetch query thread stays busy the whole time.

**Example**

I marked a Mamba operation with 8 legal boundaries as terminated and ran `_sync_prefetch_hit_query` on CPU. It called `confirm_lookup` 8 times (pages 8 down to 1) and then returned 0.

**Fix**

Add an `int(not operation.is_terminated())` slot to `accepted`, and `break` when it reduces to 0. On a rank whose operation is already terminated, skip the local `confirm_lookup` call but still join the all-reduce.
