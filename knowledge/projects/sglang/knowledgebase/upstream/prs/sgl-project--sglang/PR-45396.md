# [Perf] vision: Run SDPA per sequence instead of with a patch mask

[Upstream PR](https://github.com/sgl-project/sglang/pull/45396) · state: open · merged: False

## Original PR description

## Motivation

`VisionSdpaAttention` (the `sdpa` multimodal attention backend, and the default on several non-CUDA platforms) always builds a `[1, 1, s, s]` boolean mask from `cu_seqlens` and passes it to `F.scaled_dot_product_attention`:

- For a **single image** the mask is all-True, so it does nothing except keep SDPA off its flash kernels.
- For **several images**, or window attention (`flatten_batch=True`), the mask is block-diagonal. The masked kernel still does O(s²) work across the off-diagonal blocks.
- Every layer also syncs `cu_seqlens` to the host, rebuilds or looks up the mask, and copies it host-to-device.

#13883 measured the single-image case on an RTX 5090: the mask makes SDPA pick mem-efficient over FA-2 (1.47 ms vs 0.71 ms), and the mask H2D copy costs another 1.9 ms. That PR was auto-closed as stale, not rejected, and its CI had passed. This PR covers that case and also the multi-sequence case.

I hit this on Intel XPU (Arrow Lake iGPU, `--device xpu --encoder-only`, Qwen3.5-arch vision tower) while serving an encoder-only EPD node. There, the mask more than doubles per-layer attention time.

## Modifications

`python/sglang/srt/layers/attention/vision.py`, `VisionSdpaAttention` only:

- `_maskless_seq_lens()` returns the per-sequence lengths when the mask would be all-True or block-diagonal:
  - `bsz == 1`
  - `cu_seqlens` starts at 0 and ends at `s`
  - a single sequence, or `flatten_batch=True`

  Otherwise it returns `None`. Zero-length segments are dropped.
- `_sdpa_per_sequence()` runs one unmasked SDPA per sequence and concatenates the results. The output layout `[s, h, head_size]` is unchanged.
- `forward()` takes this path only when no `attention_mask` was passed in. These cases keep the existing masked path unchanged:
  - padding masks (`bsz > 1`, or non-flatten multi-sequence)
  - `cu_seqlens` that don't cover `s`
  - `softmax_in_single_precision`
  - GQA (`num_kv_heads != num_heads`)
  - caller-provided masks

No new flags or env vars. `generate_patch_attention_mask` and its cache are untouched, since other code paths still use them.

Tests are added to `test/registered/unit/layers/attention/test_vision_backend_selection.py` (CPU):

- `test_per_sequence_sdpa_matches_masked` checks that the per-sequence path equals the original masked forward for a single sequence (flatten and non-flatten), several sequences, and a zero-length segment.
- `test_mask_kept_when_not_block_diagonal` checks that the mask is kept when `cu_seqlens` doesn't cover a padded tail and for non-flatten multi-sequence. A mutation check confirms that dropping the `flatten_batch` condition turns this case red.

## Accuracy Tests

End-to-end on the encoder-only server (`nvidia/Qwen3.8-27B-NVFP4` vision tower, BF16, Intel Arrow Lake iGPU via `--device xpu`). Embeddings pushed over `zmq_to_scheduler` were compared with an FP32 CPU reference of the same tower (HF transformers `Qwen3_5VisionModel`, same weights). The input was a 1536×838 image, which the processor resized to a 52×96 patch grid: 4992 patches, 1248 output tokens.

| | mean cosine | p1 cosine | min cosine | rel. L2 |
|---|---|---|---|---|
| before (stock v0.5.22) | 0.99994 | 0.99921 | 0.99472 | 0.0156 |
| after (this diff) | 0.99992 | 0.99883 | 0.98315 | 0.0191 |

The math is the same, but masked and unmasked SDPA dispatch to different XPU kernels with a different BF16 accumulation order, so the results are not bit-identical. Both are well within BF16 noise. For scale, a CPU BF16 run of the same tower against the FP32 reference, measured on a 1024 px image, gives mean 0.99946, min 0.92346 and rel. L2 0.049.

Unit tests: `test/registered/unit/layers/attention/` gives 271 passed with this change vs 265 on `main`. The 6 extra passes are the new cases. The 4 failures and 1 collection error (`test_llada2_cfg_flashinfer_backend.py`, which needs flashinfer) are identical on `main` in this CPU/XPU environment.

## Speed Tests and Profiling

**Intel Arrow Lake iGPU (Core Ultra 9 285K, 64 EU), torch 2.14.0+xpu, sglang v0.5.22 with this diff applied.** These are end-to-end `/encode` latencies on an `--encoder-only` server, median of 3 warm runs:

| image max side | tokens (patches) | before | after | speedup |
|---|---|---|---|---|
| 448 | 112 (448) | 0.40 s | 0.36 s | 1.1x |
| 1024 | 544 (2176) | 2.60 s | 1.89 s | 1.38x |
| 1536 | 1248 (4992) | 10.80 s | 6.26 s | 1.73x |

Before the change, py-spy put about 68% of encoder busy time on the `cu_seqlens.cpu().tolist()` line in `generate_patch_attention_mask`. That line is the per-layer host sync, so the samples there are the CPU waiting for the masked attention kernels to finish.

Isolated SDPA, `[1, 16, s, 72]` bf16 on the same iGPU (ms per call):

| case | masked | this PR |
|---|---|---|
| 1 sequence, s=4992 | 261.7 (all-True mask) | 99.8 |
| 2 images, 2176 + 2176 | 138.3 | 61.1 |
| 8 images × 544 | 138.5 | 17.5 |
| 1 image, 78 windows of 64 | 147.3 | 8.5 |
| 1 image, 312 windows of 16 | 184.4 | 32.5 |

The many-small-windows rows matter because one SDPA call per window could, in principle, lose to a single masked call on launch overhead. On XPU it doesn't, even at 312 windows.

**I have not measured CUDA or ROCm.** The asymptotics are the same there (O(Σ l²) vs O(s²)), and #13883 shows the single-sequence win on a 5090. Even so, numbers from a reviewer for a window-attention model on `--mm-attention-backend sdpa` (e.g. Qwen2.5-VL) would be welcome before merging.
