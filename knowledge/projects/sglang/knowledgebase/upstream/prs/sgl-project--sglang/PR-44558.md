# [sgl-router] Add an opt-in toktier tokenizer backend (session-delta encoding)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44558) · state: open · merged: False

## Original PR description

## Motivation

Router tokenization sits on the TTFT path, and every turn re-encodes the full rendered chat. #41268 added `--tokenizer-backend fast` and the L1 prefix cache to cut that work. This PR adds a third backend, opt-in, built on [toktier](https://crates.io/crates/toktier). toktier keeps the transcript of each session, and when a new turn's rendered prompt extends it, toktier re-tokenizes only the appended tail and repairs the BPE boundary exactly. The backend changes how much text is tokenized again and nothing else: on every route the ids are the ones the reference `tokenizers` engine returns for the same text. The method and its measurements are in [Delta Tokenizer](https://arxiv.org/abs/2610.19801) (arXiv:2610.19801, session deltas and segment parallelism on multicore CPUs) and [TokTier](https://arxiv.org/abs/2607.29678) (arXiv:2607.29678, the exactness certificate the crate ships with each tokenizer family).

It is a backend and not a cache in front of one because the L1 cache reuses tokens only up to a special-token boundary and re-encodes the tail turn whole, while toktier's session store repairs at any byte position. A turn that appends 400 characters to a 100K-token context therefore tokenizes about 400 characters' worth of text, whether or not a special token happens to sit at the cut.

On this branch, a session turn that appends about 400 characters to a 109K-character rendered transcript takes 0.41 ms for Qwen3-8B and 0.39 ms for Llama-3.1-8B, against 22.3 ms and 16.7 ms for the router's `hf` encode of the same prompt. The one case that does not get faster, a chat prompt the store has not seen, is described under Speed Tests and Profiling.

## Modifications

Everything is behind a new Cargo feature, `toktier`, which is off by default and builds against toktier 0.3.0 from crates.io. A default build compiles none of the new code and none of the new crates, and differs only by `Cargo.lock` entries. `--tokenizer-backend` keeps `hf` as its default.

- `Cargo.toml`: feature `toktier = ["dep:toktier"]` and the optional dependency `toktier = { version = "0.3", default-features = false, features = ["serving"], optional = true }`. This is CPU only, with no prebuilt CUDA kernels and no SQLite persistence.
- `config/types.rs`: `TokenizerBackend::Toktier` (`--tokenizer-backend toktier`), present only with the feature. `config/cli.rs`: one line of flag help; the CLI plumbing test accepts `toktier`.
- `tokenizer/toktier.rs` (new): `ToktierTokenizer`, an implementation of `dynamo_tokenizers::traits::Tokenizer`. Encode takes the first route that applies:
  - a session route when a session id is bound on the calling thread: `session_repair` when the stored transcript is a byte-exact prefix of the prompt, `session_seed` when the prompt replaces it;
  - a content lookup when no id is bound (`content_lookup`). The store indexes sealed 4096-character blocks, so it finds transcripts at least that long;
  - toktier's admitted whole-prompt route otherwise (`full`).

  Anything toktier declines falls back to the Hugging Face encoder (`fallback_hf`). Decode, `has_unstable_suffix`, `vocab_size`, `token_to_id`, `special_token_ids` and `num_special_tokens_added` delegate to the Hugging Face tokenizer loaded from the same `tokenizer.json`. `validate_prefix_cache` returns `Err`, so `--tokenizer-l1-cache-mb` does not stack on it. Idle sessions are bounded (LRU, 512 per process, below toktier's own store capacity of 1024) and deleted on eviction. At startup the backend logs the family, the certification label and the admitted backends, and it warns if toktier admitted no accelerated engine on the build.
- `tokenizer/adapter.rs`: one arm in `encoder()`. A `tokenizer.json` whose SHA-256 is not one of the 15 artifacts toktier ships certification data for stays on HF and is reported as `toktier_fallback_hf`, the same way `fast` reports files fastokens cannot load. When a backend refuses the prefix cache, `build()` now reports `L1State::DisabledByBackend` with a warning instead of failing. This applies to any backend that refuses it.
- `server/routes/chat.rs`: the affinity `--session-id-header` value (default `x-session-id`, available under `--policy session_aware`) is bound in a thread-local `SessionScope` around the synchronous request preparation of the OpenAI routes and `/generate`. The binding never crosses an `.await`. This is the simplest shape that needs no change to the `dynamo-tokenizers` trait; a keyed `encode` on the trait would be the cleaner long-term home (question 1 below). `/v1/messages` and `/v1/tokenize` are not bound and use the content lookup.
- `tokenizer/stats.rs`: `EncodeBackend::{Toktier, ToktierFallbackHf}`, `L1State::DisabledByBackend`, and `sgl_router_tokenizer_toktier_encodes_total{route=session_repair|session_seed|content_lookup|full|fallback_hf}` on `/metrics`, rendered only when the backend is toktier.
- README: one bullet next to the `fast` and L1 bullets.

Session repair, session seed and overwrite, content lookup and whole-prompt encodes are exact by construction. A content-lookup hit is verified byte for byte before reuse, and a whole prompt takes toktier's admitted route, which is the reference engine wherever the fast engine does not apply. The existing backends still handle `tokenizer.json` files outside toktier's shipped families, `.model` tiktoken files (unchanged tiktoken path), `encode_segments` (default `Err`, so Kimi stays on its path) and any toktier error.

### Building

```bash
cd experimental/sgl-router
cargo build --release --features toktier
```

toktier's build script records the facts its certification label depends on. Among them are the dependency versions this build resolves, which it reads from the consumer's `Cargo.lock`; it finds that file by walking up from Cargo's `OUT_DIR`. With the default `target/` under `experimental/sgl-router`, as in this repository's CI, the walk reaches this crate's lockfile. When `CARGO_TARGET_DIR` points somewhere else, name the lockfile explicitly:

```bash
cd experimental/sgl-router
TOKTIER_CARGO_LOCK="$PWD/Cargo.lock" cargo build --release --features toktier
```

Without the variable, a build with an outside target directory finds no lockfile. Its `doctor` report then says `dependency_closure: unlocated` and `core_closure: unlocated` and has no resolved reference versions to compare. The label (`Supported`) and the admitted backends (`[FastCpu, HuggingFace]`) are the same as with the variable, and every route stays exact either way. A build with the default `target/` and no variable gives a `doctor` report byte-identical to one with the variable set. The variable only changes what the build report can say about this lockfile, and we suggest keeping it in any build recipe or CI job that enables the feature.

Build cost (rustc 1.92.0, release profile):

- The feature adds 30 crates to a from-scratch build (353 to 383). From scratch with 8 jobs, the build with the feature took 1 m 30.9 s; the added crates compile beside the router's own critical path.
- `target/release/sgl-router` is 40,034,560 B with the feature against 33,719,016 B for the default build (+6,315,544 B, +18.7%).
- `Cargo.lock` grows by 37 entries. None are removed and no existing entry changes version, because toktier 0.3.0 takes its third-party dependencies on caret ranges, which resolve to the versions this lockfile already holds. New: the five toktier crates, sonic-rs/winnow/rkyv and their helpers, eyre, blake2b_simd, fs2, tar. Second copies beside existing ones: `tokenizers 0.22.2` (dynamo-tokenizers stays on 0.21.4), `sha2 0.11` with its digest/block-buffer/crypto-common, and `indicatif 0.18`/`console 0.16` (pulled in by tokenizers 0.22's default progress-bar feature). These entries are in the lockfile whether or not the feature is enabled; the default binary is unchanged.

### The certification label a maintainer will see

At startup with Qwen3-8B the router logs:

```
toktier tokenizer loaded ... family="qwen3_8b" certification=Supported backends=[FastCpu, HuggingFace] reasons=[]
```

toktier's `doctor` gives the same label and backends for Llama-3.1-8B.

`Supported` is toktier's `supported_untested` label. By source identity, the fast CPU engine compiled into this binary is the one toktier's exactness campaign judged (`doctor` reports `source_identity_judged true`), so the default policy admits it. toktier reports three reasons why the label stops short of `certified_source`. They decide the label only; routing is the same:

- the compiler is the router's pinned rustc 1.92.0, while the judged builds used rustc 1.93.1;
- the feature set is `serving`, while the judged builds used `default,prebuilt-gpu,serving,sqlite`;
- this graph resolves `icu_properties` 2.3.0 (Unicode 17 data; `dynamo-tokenizers =3.1.0` reaches `icu_normalizer`, which requires `~2.3.0`), while toktier's certified reference versions list 2.0.2, so its `doctor` reports `reference_certification_reason: uncertified_reference`. This blocks nothing, and the note goes away when toktier adds 2.3.x to its certified reference versions.

toktier's `toktier-rust verify-local --engine cpu` compares the two engines on a machine's own text and relabels the route `locally_verified`. This draft did not use it; the router tests below make the same kind of comparison against the router's own HF backend.

## Accuracy Tests

Router-side unit tests in `src/tokenizer/toktier.rs` compare every id against the inner `tokenizers` crate (`create_tokenizer_from_file`) on real `tokenizer.json` files, resolved from `SGL_ROUTER_TOKTIER_FIXTURES=<dir>` (`qwen3_8b-*`, `llama_3_1_8b-*`, `bert_cased-*`). A cell whose file is absent is skipped with a note; the tiny-fixture cells always run.

- `full_encodes_match_hf` (Qwen3-8B, Llama-3.1-8B): prose, whitespace, chat-template text with special tokens, CJK, a ~200 KB text, and `encode_batch`.
- `session_append_matches_hf_from_scratch`: 20 growing chat turns under one session id, each equal to a from-scratch HF encode, with counters at 1 seed + 19 repairs. A prompt that does not extend the transcript, and a shorter one, overwrite it and stay exact.
- `unkeyed_content_lookup_matches_hf`: a stored transcript found by content without a session id.
- `declined_session_route_keeps_ids_exact`: a session id toktier rejects (over 1024 bytes) encodes without a session, ids unchanged.
- `concurrent_sessions_stay_exact`: 8 threads, six of them sharing two session ids and two unkeyed; all 48 encodes equal HF.
- `foreign_tokenizer_passes_through_to_hf` (BERT) and `tiny_fixture_passes_through_to_hf`: `toktier_fallback_hf`, ids equal to HF.
- `l1_cache_is_inert_on_toktier`: `L1State::DisabledByBackend`, ids exact, L1 counters at zero.
- `session_scope_nests_and_restores`; the CLI plumbing test accepts `toktier`; the existing L1 `cache_tests` loop now includes the toktier backend on the tiny fixture (HF answers, L1 applies); the metrics render test covers the new series.

This build admits toktier's fast engine, so these tests compare the fast engine and its session repair with HF id for id, in addition to the reference engine against itself.

Results with toktier 0.3.0 from crates.io (rustc 1.92.0 from `rust-toolchain.toml`, release profile, fixtures for Qwen3-8B, Llama-3.1-8B and BERT-cased present):

- `cargo test --release --features toktier --lib -- tokenizer:: config::cli::tests::tokenizer_backend_and_l1_cache_are_plumbed`: 67 passed, 0 failed (1026 filtered out).
- `cargo test --release --features toktier --lib`: 1093 passed, 0 failed.
- `cargo clippy --release --all-targets -- -D warnings`, with and without the feature: clean.
- `cargo fmt --all -- --check` with the pinned toolchain, and `cargo +nightly fmt --all -- --check` as CI runs it: clean.
- `cargo build --release`, with and without the feature: 0 warnings.

Outside the unit tests, a probe binary built inside this workspace encoded fresh 100K-, 400K- and 1M-character prompts on both families (a mixed text of prose, code, CJK and numbers, and real prose from Project Gutenberg novels), plus a 20-turn session sequence. Across 160 processes every id equalled the router's HF encode. A live run of the binary (`--tokenizer-backend toktier --policy session_aware`, Qwen3-8B, unreachable worker) answers `/v1/tokenize` with the same ids an earlier build of this branch returned when toktier ran only its reference engine. After two chat turns under one `x-session-id`, it reports `session_seed 1, session_repair 1` on `/metrics`.

## Speed Tests and Profiling

The probe is built inside this workspace against the same toktier. Each process times one encode, so neither engine has seen the text, and each cell is the median of five processes. `RAYON_NUM_THREADS=1`, with memory bound to the local NUMA nodes on a dual-socket AMD EPYC 9115. `inner` is the router's own HF backend (`tokenizers` 0.21.4 through `dynamo-tokenizers`).

| ms, toktier / inner (speedup) | Qwen3-8B | Llama-3.1-8B |
|---|---|---|
| session turn: ~400 characters appended to a ~109K-character rendered chat transcript (median of 20 turns) | 0.41 / 22.3 (54x) | 0.39 / 16.7 (43x) |
| whole prompt, 100K characters of prose | 1.49 / 29.0 (19.5x) | 1.54 / 18.1 (11.8x) |
| whole prompt, 400K characters of prose | 3.83 / 101.6 (26.5x) | 3.41 / 79.2 (23.2x) |
| whole prompt, 1M characters of prose | 24.65 / 272.4 (11x) | 6.74 / 233.7 (35x) |
| whole prompt, 100K characters of prose wrapped in the model's chat template (one process each) | 28.1 / 27.5 (0.98x) | 18.5 / 17.5 (0.95x) |

The table was measured on a snapshot of toktier's 0.3.0 release branch whose source identity is the published crate's. On the crates.io build, the session and 1M-prose rows were measured again with the same protocol (30 processes, every id equal): session turn 0.37 / 22.5 ms (Qwen3-8B) and 0.39 / 16.5 ms (Llama-3.1-8B); 1M characters of prose 23.9 / 272.8 ms and 7.0 / 239.9 ms.

Prose is the input text of 20 LEval `narrative_qa` items (Project Gutenberg novels), five windows per size at different offsets. For Qwen3-8B the fast engine's cost depends on whether a window holds any non-ASCII character: at 1M characters the all-ASCII windows took about 6.5 ms and the others about 25 ms. Both tiers are exact, and both are about ten times faster than HF or more. Llama-3.1-8B shows no such split.

On toktier's serial whole-prompt route, a prompt that contains an added-token literal goes whole to the reference engine. Every prompt rendered from a chat template contains such literals, so a chat request that is new to the store (no session id bound, and no stored transcript found by content) costs what `hf` costs, as the last row shows. So does the first turn of a session, which seeds the store (Qwen3-8B: 31.0 ms for a 100K-character rendered seed). Later turns are not affected, because a repair re-encodes only the appended tail, and text that carries no template literals (raw `/generate` text, for example) takes the fast engine. Segmenting the serial route at added-token literals, as the chunked route already does, is on toktier's roadmap for 0.3.1.

toktier 0.3.0 also has chunk-parallel encoding, `Tokenizer::chunked()`, admitted under the default policy for Qwen3-8B, Llama-3.1-8B, DeepSeek-V3 and gpt-oss-120b. It cuts at added-token literals and keeps the fast engine for the rest, so long chat-templated prompts do benefit from it. On a 1M-character prose window with 8 workers started in advance (and warmed on the same text), it took 3.96 ms for Qwen3-8B and 0.98 ms for Llama-3.1-8B, with ids equal in all 15 processes per family. This PR does not use it. A follow-up PR adds the router switches: a character threshold, the worker count, and a one-time warm-up at startup, since starting the workers costs about 0.2 s for Qwen3-8B on first use.

## Related RFC and PRs

This is roadmap item 4 of RFC #44374, the Rust front end: the same library with the same admission and fallback rules, in the router's tokenizer path instead of the Python tokenizer manager. It does not depend on the Python PRs, and they do not depend on it. #44373 adds `--tokenizer-backend toktier` to the Python server (session route and chunked encoding through the `toktier` wheel, also 0.3.0). #44382 stacks on it and adds toktier's worker pool behind one awaited hook. #44392 is independent of toktier and extends #41259's intra-message cuts to the Qwen2/Qwen3, o200k and DeepSeek-V3/V4 pipelines. A deployment gets the same ids whether it tokenizes in the router or in the engine.

## Questions for maintainers

This is a draft, and these questions come first.

1. Is the thread-local binding acceptable, or would you rather see a keyed `encode` added to `dynamo-tokenizers`?
2. Where should the session id come from: affinity's `--session-id-header` only (as in this draft), or also sticky's header or a body field?
3. Should the backend exclude `--tokenizer-l1-cache-mb` (this draft leaves L1 inert with a warning), or should the two stack?
4. Is a second `tokenizers` copy (0.22.x beside dynamo's 0.21.4) acceptable behind a feature until dynamo-tokenizers moves?
5. CI builds only the default feature set today. Would you like a job that runs `cargo clippy` and the tokenizer tests with `--features toktier` (with `TOKTIER_CARGO_LOCK` set as above), and if so, with which fixtures?
