# [Fix] openai: Scrub server source paths from validation error responses

[Upstream PR](https://github.com/sgl-project/sglang/pull/47081) · state: open · merged: False

## Original PR description

## Motivation

Fixes #47076.

A malformed request to an OpenAI endpoint (e.g. `messages: "not-a-list"` on
`/v1/chat/completions`) returns HTTP 400 with the server's absolute source
path, line number, and endpoint function name in the response message, because
the `RequestValidationError` handler built the client message from
`str(exc)`, and FastAPI's exception string carries the dispatching endpoint's
context. The same body sent to `/v1/messages` returns a concise field
validation message, because the Anthropic branch already renders from
`exc.errors()`.

This change makes every non-systemone validation branch render the
client-facing message the same way: a short `loc: msg` digest built from the
structured field errors only. Status codes and response envelopes are
unchanged, and the full error (minus the client input echo) is now logged
server-side with `logger.warning`, where diagnostics belong.

## Modifications

- `python/sglang/srt/entrypoints/http_server.py`:
  - The `RequestValidationError` handler no longer uses `str(exc)` /
    `str(exc.errors())` for the client message. It now renders
    `_anthropic_validation_message(exc.errors())` for the OpenAI envelopes
    (`/v1/chat/completions`, `/v1/completions`, `/v1/responses`, and the
    default `ErrorResponse` branch), reusing the scrubbed digest the
    `/v1/messages` branch already used.
  - Added a server-side `logger.warning` with the path and the field errors
    (input values stripped, matching the `/v1/systemone` branch's treatment).
  - `/v1/messages` behavior is unchanged; `/v1/systemone` still returns its
    documented 422 detail list with the input echo dropped.

Example before/after for `messages: "not-a-list"` on `/v1/chat/completions`
(status stays 400):

- Before: `1 validation error: {...} File ".../http_server.py", line 1702,
  in openai_v1_chat_completions ...`
- After: `messages: Input should be a valid list`

## Tests

No GPU is available on this machine, and FastAPI/pydantic are not installed
here, so a full server run was not possible. Instead, the real handler and
message helper were executed via AST extraction against stubbed response
types, with the issue's recorded error dicts and leaked message string
(harness kept in the contributor workspace, not in this PR). All 14 checks
pass:

- `/v1/chat/completions`: 400, message exactly
  `messages: Input should be a valid list`, no source path, endpoint name, or
  input echo; legacy `ErrorResponse` envelope preserved.
- `/v1/responses`: 400 with the same scrubbed message in the nested
  `error.message` field.
- `/v1/messages`: Anthropic envelope byte-identical to before.
- `/v1/systemone`: still 422 with the documented detail list, input dropped.
- Multi-error bodies join as `messages: ...; temperature: ...`; empty error
  lists fall back to `Invalid request`.
- Static check: the handler contains no `str(exc)` call, so no endpoint
  context can reach the client through this path regardless of how FastAPI
  builds the exception string.

Lint on the touched file: `ruff check --select F401,F821,F823,UP037` passes,
`ruff format --check` passes, `python3 -m py_compile` passes,
`git diff --check` passes.

Existing unit test `test_validation_errors_are_422_on_this_route_only`
(`test_serving_decisions.py`) asserts only the status code for the
non-systemone branch, so it is unaffected by the message change; it could not
be run here (it needs the full server test dependencies).
