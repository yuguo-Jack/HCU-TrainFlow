# [Feat] weight-sync: let one serialized payload serve every TP rank

[Upstream PR](https://github.com/sgl-project/sglang/pull/48241) · state: open · merged: False

## Original PR description

## Motivation

`update_weights_from_tensor` indexes `serialized_named_tensors` by `tp_rank`, so an HTTP caller has to send one identical copy of the payload per rank. For a trainer that pushes a LoRA adapter to external engines over HTTP every step, that multiplies the request by the engine's TP size (base64 inside JSON on top), and rank 0 also forwards the whole request to the other ranks.

Measured with miles' http-lora transport (radixark/miles#3690) on GLM-5.3 744B with the GLM LoRA cookbook's full MoE LoRA (4.1 GB adapter), rollouts on MI355X, trainer on B300:

| rollout engines | copies per request | sync per step |
|---|---|---|
| 2 engines × TP4 | 4 | 409 s |
| 1 engine × TP8 (dp-attention) | 8 | > 600 s (hit the 600 s weight-update timeout) |
| 1 engine × TP8 (dp-attention), this PR + miles sending one copy | 1 | **127 s** (103 s of it the POST) |
| 1 engine × TP8, this PR + miles sending one copy | 1 | **84 s** |

The per-rank copies are only needed for CUDA-IPC payloads (the in-process `Engine` path), where a rank must not open another rank's handles. HTTP callers ship plain CPU tensors, which carry no handles.

## Modifications

- `BaseTpWorker.deserialize_own_rank`: with a single entry, every rank deserializes entry 0; a per-rank list is indexed by `tp_rank` as before.
- Backward compatible: per-rank lists behave exactly as today, and a single entry on a multi-rank engine used to raise `IndexError`, so no working caller changes behaviour. In-process callers (`Engine._serialize_tensors_per_rank`, CUDA-IPC) keep sending per-rank lists.

Source: 1 file, +5/-4.

## Accuracy Tests

- `test/registered/unit/managers/test_tp_worker_shared_tensor_payload.py`: 2 cases (per-rank list reads its own entry on ranks 0-3; a single shared entry is read by ranks 0-3). Fails without the change on the shared case, passes with it. `test/registered/unit/model_executor/test_weight_update_tensor_rank.py` still passes, in either order.
- End to end: GLM-5.3 744B LoRA, miles fully-async with http-lora tensors mode sending one copy per engine, one TP8 engine on 8× MI355X: the 4.1 GB adapter syncs in 84 s every step (v0-v2: 84.2 / 84.1 / 84.9 s) and the engine serves it; trainer vs rollout log-prob diff 0.036 → 0.033, KL 5.4e-3 → 4.6e-3 over the first two steps (fp8 rollout, bf16 train, within the GLM LoRA cookbook's documented fp8-rollout range).
