# [Feat] weight_cache: Add the vmm_fd transport

[Upstream PR](https://github.com/sgl-project/sglang/pull/46953) · state: open · merged: False

## Original PR description

Co-authored with @Shunkangz and @mohammedabdulwahhab.

## Motivation

The weight cache daemon (#27139) shares weights with engines through `torch_ipc`, which uses CUDA IPC handles. The `vmm_fd` backend in `weight_cache/transport.py` is still a placeholder that raises `NotImplementedError`; #33522 and #27310 (§4.2, phase 1) both plan it.

With CUDA VMM, the engine reserves its own virtual address range and maps the daemon's allocations into it. With `cudaIpcOpenMemHandle`, the caller cannot choose the address. That difference gives:

1. **In this PR:** a daemon exit no longer kills the engine. CUDA frees a `cuMemCreate` allocation only after every mapping and handle to it is released, so an attached engine keeps valid weights, and the SIGKILL watchdog is only needed for `torch_ipc`.
2. **Follow-ups:** release the weights and map them back later at the same addresses, so that pointers captured in CUDA graphs stay valid. This would allow weight release/resume with the cache on (rejected today by `_assert_weight_cache_inactive`), the roadmap's epoch handoff, and engine snapshots that re-attach the node's resident weights instead of reading them from the checkpoint (#43965, #40736; a proposed design, not tested here). In this PR the engine maps once and does not re-map.

The KV cache needs no new transport: with `--enable-memory-saver`, torch_memory_saver already allocates it with CUDA VMM and keeps its addresses across pause and resume.

## Modifications

- `--weight-cache-transport {auto,torch_ipc,vmm_fd}`, the flag named in #33522. On the daemon, `auto` keeps `torch_ipc` for now; on an engine, `auto` accepts whatever the daemon serves, while a named transport refuses a daemon serving the other.
- Daemon: after loading, pack each rank's tensors into a few large exportable allocations (new `weight_cache/vmm_layout.py`), freeing each original as it goes. Aliases and tied weights keep sharing storage.
- Protocol: `fetch_state` sends the layout, then one fd per allocation over `SCM_RIGHTS`. `_recv_fd` takes every delivered fd before any check, closes them on error, refuses truncated ancillary data and uses `MSG_CMSG_CLOEXEC`.
- Engine: reserve one address range, import and map each allocation, and pass the tensors to the existing `_set_module_tensor` path. Mappings are kept until the process exits, because a parameter can outlive the model object.
- With `vmm_fd`, a daemon exit is logged and the engine keeps serving. The watchdog stays for `torch_ipc`.
- `preloaded_weights_bytes` reports the packed allocations. `expandable_segments` is allowed in a `vmm_fd` daemon.
- `IpcModelLoader` is renamed to `WeightCacheModelLoader`, since it now serves both transports. The module name `ipc_loader.py`, the internal `ipc_cache` load format and the "Loaded model via IPC" log text stay as they are.
- Tests: CPU unit tests in `test_weight_cache_vmm_fd.py`, and a `vmm_fd` variant of each of the five GPU test classes in `test_weight_cache_daemon.py`.

Not done yet: loading straight into exportable memory, read-only mappings, docs, and in-tree byte-level parity checks.

Follow-ups, in separate PRs: release and re-attach the weights at the same addresses; the epoch handoff (#33522); release and re-attach the KV cache together with the weights; refresh PD KV-transfer registrations after a re-attach; engine snapshots (#43965 / #40736).

## Known limitations

- POSIX file descriptors only, so the engine and the daemon must be on the same node. ROCm stays on `torch_ipc`.
- The existing quantization allowlist (unquantized and block-wise FP8) applies to both transports.
- Export fails if a model tensor is not on this GPU, for example a CPU buffer. `torch_ipc` handles that.
- As with `torch_ipc`, objects that the model derives after loading and keeps as plain attributes are not exported, for example DeepSeek MLA's `w_kc` / `w_vc` (from reading the code). A tensor that is still referenced outside the parameters and buffers stays alive in the daemon as an extra copy.
- Mappings stay until the process exits. SGLang does not load a second model with the cache on, because weight updates are refused.
- The shared weights are writable: an in-place write in one engine changes every engine's copy. EPLB rebalancing does this, for `torch_ipc` too; #45341 addresses it. The EP tests here never rebalance.
- On SM100, DeepGEMM's UE8M0 repack of block-FP8 scales and BF16 Qwen3-MoE's default `flashinfer_trtllm` runner change weights after loading, which a meta-initialized engine cannot reproduce. This affects `torch_ipc` too. The runs above used `SGLANG_ENABLE_JIT_DEEPGEMM=0` for FP8 and `--moe-runner-backend triton` for MoE. `CacheConfig` does not record the MoE runner, so the daemons and the engine must use the same one.
- Mixed builds (from reading the code): an engine from before this PR fails against a `vmm_fd` daemon, without falling back to disk. Upgrade daemons and engines together, and keep `auto` while a node runs both builds.

**Loading approach**

What drove the choice to load normally and relocate the final weights, rather than using a custom MemPool that directly loads into VMM backing? 

From reading this change, it seems re-location is quite an involved technique requiring a correct impl across the following concerns:
- Correctly (and efficiently) packing tensor storages
- Correctly determining allocation granularity/alignments for the planned layout.
- Free-ing references to old storage tensors (from the ordinary allocator) so they are reclaimed
- Re-wiring model tensors to point to the new storage. Handling views, aliases, and other special cases.

It seems that we have it working for now, but I'd like to seriously vet the alternative (directly loading into VMM backing using a [CudaPluggableAllocator](https://docs.pytorch.org/docs/2.15/generated/torch.cuda.memory.CUDAPluggableAllocator.html)) to see if we avoid implementing some of these concerns.

Thanks for raising this. We compared relocation with our own allocate-at-load prototype (a torch `MemPool` backed by a `CUDAPluggableAllocator` that creates one POSIX-fd-exportable VMM allocation per segment) on GLM-5.2-FP8 (TP8, 8x B200) and Qwen3-30B-A3B (TP8).

**What we measured**

- The prototype exports one VMM allocation per caching-allocator segment containing exported storage: 362 per rank on GLM-5.2 versus 151 with relocation (125 versus 8 on Qwen3-30B). Each attach sends one fd per allocation, which the client imports and maps. Median per-rank attach (fetch, import and map, rebuild the tensors; not a full engine start) is 0.57 s with relocation versus 1.0 s with the prototype, or 0.23 s versus 0.54 s with cached fds (28 ms versus 386 ms on Qwen3-30B).
- On GLM-5.2, the unpruned pool also keeps 0.57 GiB per GPU in allocations that hold no exported storage, plus 0.27 GiB outside the exported storages inside exported allocations. `preloaded_weights_bytes` is 89.3 GiB per GPU versus 88.8 GiB with relocation.
- Relocation pays once per daemon load: about 0.22 s of packing per rank on GLM-5.2, and about 1.01 GiB of extra memory per GPU at the 1 GiB cap.

**On the concerns you listed**

- *Packing and granularity/alignment*: `vmm_layout.py` puts shared or overlapping storages in one slot, aligns slots to 512 bytes, and rounds allocations to the driver's granularity; the CPU tests cover these cases. Allocate-at-load skips the packing but still rounds every allocation to the granularity.
- *Freeing old storages*: the plan keeps tensor names, not tensors, and each copied tensor is repointed before the next allocation; `empty_cache()` then returns the segments that are fully free. That is where the transient above comes from. After the pack, no copied original was still live (rank-0 allocator trace).
- *Re-wiring, views and aliases*: in this version, repointing the model's tensors is what releases the originals during packing. Views and aliases share one slot, and each tensor's dtype, shape, stride and offset are sent; the client needs that metadata under either approach.
