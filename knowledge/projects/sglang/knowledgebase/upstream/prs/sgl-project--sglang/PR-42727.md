# perf(kimi-k3): prepare native MXFP4 expert-tile routing in the fused route+quant launch

[Upstream PR](https://github.com/sgl-project/sglang/pull/42727) · state: closed · merged: False

## Original PR description

## Motivation

For Kimi-K3 MXFP4 decode on Blackwell, the fused route+quant launch (`route_quant_fused`) already produces the packed top-k ids and the MXFP8 activations. The trtllm-gen routed MoE body then runs its own routing-preparation kernel (`routingIndicesBlockKernel`) to turn those ids into expert-tile metadata. At M ≤ 8 that metadata is cheap to emit from the routing CTAs we already launch, which removes one kernel per MoE layer from the decode critical path.

## Modifications

- **`jit/csrc/moe/route_quant_metadata.cuh`** (new): a variant of the fused route+quant kernel. For M ≤ 8 it also writes FlashInfer's native eight-token-tile routing metadata (`total_num_padded_tokens`, `expanded_idx_to_permuted_idx`, `permuted_idx_to_token_idx`, expert weights, `cta_idx_xy_to_batch_idx`, `cta_idx_xy_to_mn_limit`, `num_non_exiting_ctas`). At M = 1 the radix-selected experts are already in ascending order. At M > 1 the last routing CTA to finish lays out every token's routes. Routing and quantization stay bit-identical to `route_radix` + `per_token_group_quant`.
- **`ops/moe/trtllm_prepared_fp4.py`** (new): `try_prepared_k3_mxfp4` runs FlashInfer's `MoERunner` with `do_preparation` skipped, supplying the prepared metadata (`da_routing_metadata`) and a cached body workspace. A Triton `prepare_expert_tile_metadata` kernel is the fallback when no prepared metadata was handed off. It covers only the K3 shape (896 experts, top-16, hidden 3584, intermediate 384, no EP offset) on SM100/103/107, tile 8, M ≤ 8. Anything else returns `None` and the runner uses `trtllm_fp4_block_scale_routed_moe` unchanged.
- **`ops/moe/moe_route_quant_fused.py`**: `metadata_available()`, `allocate_metadata()`, and a `metadata=` argument on `route_quant_fused` that selects the metadata kernel. The existing M ≤ 64 cap is unchanged.
- **`route_quant_handoff.py`**: allocate metadata for M ≤ 8 when supported, publish it with the packed ids, and `take_metadata(routing)` to consume it only for the exact packed-id tensor that produced it.
- **`flashinfer_trtllm.py`** (MXFP4 SiTU routed path): try the prepared path first, otherwise fall back to the existing call.

No model code changes. Requires FlashInfer ≥ 0.7.0 (`TrtllmMoERoutingMetadataSlot`); the pinned 0.7.0.post1 has it.

## Accuracy Tests

B300 1×8 (SM103), TP8, `moonshotai/Kimi-K3` MXFP4, the cookbook B300 Unified Low-Latency recipe (`--tp-size 8 --mem-fraction-static 0.85`, backends auto-resolved).

**Kernel level:**
- `route_quant_fused` with and without metadata is bitwise identical to `route_radix` + pack + `per_token_group_quant` (weights, ids, packed ids, x_q, x_s) for M ∈ {1…9, 16, 64, 65, 128, 512, 1024, 4096}.
- The fused metadata is byte-identical to the Triton `prepare_expert_tile_metadata` reference for every M = 1…8.
- `test_route_quant_prerequisites.py` and `test_mxfp4_flashinfer_activation_prep.py`: 8 passed.

**GSM8K** (`sglang.test.few_shot_gsm8k`, 5-shot):

| Run | main | this PR |
|---|---|---|
| 1319 questions, `--parallel 64` | 0.949 | 0.955 |
| 1319 questions, `--parallel 8` (decode batches ≤ 8) | 0.956 | 0.953 |
| first 250, `--parallel 1` (batch size 1) | 0.980 | 0.988 |

## Speed Tests and Profiling

Same setup. `bench_one_batch_server`, input 8192, output 1024. Three runs per arm on separate server launches in alternating order (output throughput, tok/s):

| Batch size | main | this PR | Δ |
|---|---|---|---|
| 1 | 119.32 / 119.64 / 119.66 | 123.75 / 123.58 / 123.52 | **+3.4%** |
| 2 | 213.51 / 213.62 / 213.74 | 218.30 / 218.84 / 218.80 | **+2.3%** |
| 4 | 387.95 / 387.82 / 383.72 | 388.87 / 386.80 / 386.83 | +0.2% |
| 8 | 607.42 / 605.23 / 606.87 | 646.82 / 644.22 / 644.17 | **+6.4%** |

These three runs used a build that also lifted the M ≤ 64 cap (see below). Decode batches never exceed 64 tokens, so the decode path is identical to this PR. One run of this exact PR (cap kept) gave 123.17 / 218.38 / 390.66 / 646.84 tok/s at batch sizes 1 / 2 / 4 / 8, with TTFT 0.40 / 0.76 / 1.64 / 2.70 s vs main's 0.40–0.43 / 0.70–0.81 / 1.36–1.54 / 2.69–2.79 s. Prefill takes the same kernels as main: a batch-size-8, 8192-input profile shows 2274.2 ms (main) vs 2273.1 ms (this PR) of GPU kernel time on TP0.

Per MoE layer at batch size 1 (TP0 torch-profiler trace): `route_quant_metadata_kernel` at 5.64 µs replaces `route_quant_fused_kernel` (4.11 µs) plus FlashInfer's `routingIndicesBlockKernel` (4.96 µs).

Not included: an experiment that also dropped the M ≤ 64 cap on the fused route+quant launch, so prefill would use it. Decode was the same, but TTFT rose 3–10% at batch sizes 1–8 (all-reduce wait grew on TP0, so the fused launch was slower on the other ranks at prefill sizes), so the cap stays.
