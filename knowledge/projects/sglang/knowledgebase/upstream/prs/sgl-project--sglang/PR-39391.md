# [Spec] Tolerate draft configs that fail to parse during algorithm resolution

[Upstream PR](https://github.com/sgl-project/sglang/pull/39391) · state: closed · merged: False

## Original PR description

### Motivation

`_resolve_speculative_algorithm_alias` eagerly loads the draft model's HF config to detect Gemma4 assistant drafts (which promote NEXTN/EAGLE to FROZEN_KV_MTP). The `get_config(...)` call is unguarded, so any draft config that `AutoConfig` cannot parse makes the whole engine fail at argument resolution — before weights load, before any useful error about the draft itself.

The generic AutoConfig path requires a `model_type` key, which speculators-style draft configs (e.g. DFLASH's `DFlashSpeculatorConfig` with no `model_type`) do not carry. The probe's only purpose is Gemma4 detection: a config that fails to parse is never a Gemma4 assistant draft, so a parse failure simply means "not a Gemma4 draft" and resolution should proceed with a logged reason.

### Modification

Wrap the draft-config probe in try/except:

- on failure, log the path and the reason at INFO level and treat the draft as non-Gemma4 (`cfg = None`; the existing `getattr(cfg, "architectures", None) or []` already handles None);
- every config that parses behaves exactly as before — including both Gemma4 architectures (`Gemma4AssistantForCausalLM`, `Gemma4UnifiedAssistantForCausalLM`) and the EAGLE3 hard-reject path;
- only previously fatal third-party draft configs become servable.

### Test plan

- New CPU unit test `test/registered/unit/arg_groups/test_speculative_draft_config_tolerance.py` (3 cases, `register_cpu_ci(est_time=5, suite="base-a-test-cpu")`):
  1. unparseable draft config (load raises) → resolution returns the algorithm unchanged;
  2. parseable Gemma4 draft → FROZEN_KV_MTP promotion preserved;
  3. parseable non-Gemma4 draft (e.g. `DFlashDraftModel`) → pass-through preserved.
- Local run: **3 passed** (pytest, this commit's tree).
- Existing behavior guard: the Gemma4-draft promotion and EAGLE3 rejection logic are covered by cases 2 and 3.

### CI expectation

- No dependency/lockfile changes; docs untouched.
