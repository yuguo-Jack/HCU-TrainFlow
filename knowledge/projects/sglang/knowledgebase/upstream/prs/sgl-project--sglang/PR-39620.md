# [Feat] kv-events: Include the removal reason in BlockRemoved

[Upstream PR](https://github.com/sgl-project/sglang/pull/39620) · state: open · merged: False

## Original PR description

## Motivation

Refs #39604. `BlockRemoved` says which blocks left a tier but not why, so a consumer cannot tell capacity eviction from a demotion that left the content readable in a lower tier. That is the difference between a cache miss meaning pressure and a miss that is still servable, and today it has to be inferred from timing and unrelated scheduler state.

The issue asks for the event semantics to be settled before implementation, so the first half of this description is what the call sites actually say. The vocabulary below is derived from them, not proposed from outside, and I am happy to rename any of it.

### What the removal paths actually are

#40313 removed the SWA and Mamba radix caches and #40787 removed HiRadixCache while this PR was open, so after merging `main` there are 5 `kv_events.record_remove(...)` call sites, in `radix_cache` and `unified_tree_core`. Grouped by what is true of the content afterwards:

| cause | call sites | after the event, the content is |
| --- | --- | --- |
| capacity eviction | `radix_cache.evict`, `unified_tree_core._release_all_component_layers`, `unified_tree_core._evict_host_leaf` | gone |
| demotion | `unified_tree_core._demote` | on host |
| duplicate reclaim | `unified_tree_core._release_full_host_duplicate` | still on device |

Three of the five collapse to one reason. The Rust tree core, the default backend, has the same paths and emits the same reasons: `release_all_component_layers_` and `evict_host_leaf_` (evicted), `demote_` (demoted), `release_coexisting_host_value_` (duplicate reclaim).

**Two of the four candidate values in the issue have no emitting call site.** `request_finished` and `aborted` do not appear, because finishing or aborting a request only drops a lock reference; the blocks stay in the tree until one of the causes above removes them. Emitting them would mean inventing removals that do not happen, so this PR leaves them out. `AllBlocksCleared` stays the representation of an explicit global clear, as the issue suggests.

### Compatibility

`KVCacheEvent` is a tagged msgpack **map** with `omit_defaults=True`. Only `EventBatch` is `array_like`, and it is untouched. So an optional field left unset is absent from the payload, and a consumer that does not know the key never sees it. `BlockStored` already gained `cache_salt` and `session_id` this way.

The in-repo Rust consumer confirms it rather than assumes it. `sgl-kv-indexer`'s bridge decodes `BlockRemoved` by looking up the keys it routes on and ignores the rest, and the `KvCacheEvent` doc comment in the router's `wire` module already says exactly that about `BlockStored`: "Keys the gateway does not route on (`cache_salt`, `session_id`) are ignored." Nothing in the KV-event path uses `deny_unknown_fields`; the only uses of it in the router are on config and tokenize types. No Rust change is needed, and none is included.

## Modifications

```python
class BlockRemoved(KVCacheEvent):
    block_hashes: list[int]
    medium: Optional[str] = None
    reason: Optional[str] = None
```

- `RemovalReason(str, enum.Enum)` next to `StorageMedium`, mirroring how `medium` is already typed: a documented vocabulary, carried on the wire as a plain string. Values: `evicted`, `demoted`, `duplicate_reclaimed`.
- The wire default is `None`, not `evicted`. "Not stated" and "evicted" are different claims, and an unset field keeps today's byte shape.
- `KVCacheEventRecorder.record_remove` takes `reason` as a keyword defaulting to `RemovalReason.EVICTED`, the way `medium` already defaults to `StorageMedium.GPU`. Only the three non-eviction sites pass anything, which keeps the diff to the paths whose meaning actually differs.
- The coalescing predicate now compares `reason` as well as `medium` (point 4 of the issue). Merging removals with different causes would report demoted blocks as evicted.
- Rust tree core: `KvCacheEvent::BlockRemoved` carries a `RemovalReason` (`as_str()` gives the Python values), set at the four `record_remove_event_` sites. `enqueue_kv_event_` coalesces removals only when the reason matches as well. The binding appends the reason to the `block_removed` tuple, so the existing indices stay where they are, and `rust_tree_core/adapter.py` passes it to `BlockRemoved`.

Deliberately not included: `cache_salt` on `BlockRemoved` (question 3 in the issue). It is a separate change with its own symmetry argument, and folding it in here would blur what this PR is asking to agree.

## Unit tests

Extended the two files that already own this surface, `test/registered/unit/disaggregation/test_kv_events.py` (wire contract) and `test/registered/unit/mem_cache/test_radix_cache_unit.py` (recorder and coalescing).

| test | what it stops |
| --- | --- |
| an old consumer decodes an event carrying each reason | the field breaking existing subscribers |
| a new consumer reads an event emitted without one, and sees `None` | a missing reason being read as `evicted` |
| omitting the reason leaves exactly `{type, block_hashes, medium}` | the wire shape changing for emitters that state nothing |
| `reason` is a named field, and survives a mixed batch | the value being dropped in transit |
| removals with different reasons do not coalesce | the merge that would relabel demotions as evictions |
| removals with the same reason still coalesce | the guard defeating the batching it sits in |
| `record_remove` defaults to `evicted` and carries an explicit reason | the recorder silently dropping the argument |

- sohom-cs · COMMENTED · 2026-10-25T01:15:35Z · [source](https://github.com/sgl-project/sglang/pull/39620#pullrequestreview-5640902497)

The reason is only set in the Python tree core. On main, with the default tree core (`SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND` is `rust`; Python is the fallback), a removal goes through `record_remove_event_` (`rust/sglang-radix-tree/src/unified_tree_core.rs:3713`), which carries the hashes and the medium only, and the adapter turns that tuple into `BlockRemoved(block_hashes=..., medium=...)` (`python/sglang/srt/mem_cache/rust_tree_core/adapter.py:145`). So on that path every event has `reason=None`, including the Rust counterparts of the two paths labelled here, `demote_` and `release_coexisting_host_value_`. The new tests exercise the recorder and the wire format, not either core's eviction paths.

Should the reason go through the Rust `KvCacheEvent::BlockRemoved` and the binding tuple in this PR, or should the description name the Rust core as a follow-up?
