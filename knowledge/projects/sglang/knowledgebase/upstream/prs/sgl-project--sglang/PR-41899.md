## Motivation

This is a ROCm performance change. With `--enforce-shared-experts-fusion` the
BF16 shared expert of a Quark MXFP4 checkpoint is quantized to MXFP4 at load and fused into
the routed grouped GEMM (general matrix multiply), instead of running as a separate BF16
MLP (multi-layer perceptron). On `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` over 8x MI355X at TP8
that is worth **+4.5% output throughput and -4.6% mean ITL (inter-token latency)**, as a
geomean across a 12-point serving sweep.

There is currently no Qwen3.8-2.4T-A95B checkpoint in which the shared expert is FP4
quantized, so shared-expert fusion is unavailable for this model family on MXFP4.

`amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` quantizes the routed experts to MXFP4 but lists the
shared-expert body in the Quark quantization config's `exclude` list, so
`gate_proj`/`up_proj`/`down_proj` of the shared expert ship in BF16. Shared-expert fusion
works by appending the shared expert as one more routed expert at slot `num_experts`, so
that a single grouped GEMM serves top-k routed experts plus the shared one. That requires
every slot in the fused weight to have the same dtype, so today
`QuarkConfig.can_fuse_shared_expert()` sees the format mismatch and refuses, and the model
falls back to running the shared expert as a separate BF16 MLP alongside the routed grouped
GEMM. Rather than wait for a new checkpoint, this PR quantizes the BF16 shared expert at
load time so the existing checkpoint can use the fused path.

The feature is **off by default** and gated behind the existing
`--enforce-shared-experts-fusion` server argument, which already means "fuse the shared
expert even where the gate would normally refuse". In the fused path the shared expert goes
through the routed experts' W4A4 grouped GEMM, so its weights *and* its input activations
are quantized to MXFP4, where the standalone path it replaces ran BF16 x BF16. That is a
real precision trade and should be an explicit choice rather than something a checkpoint
opts into silently.

### Reproduction

Run inside `lmsysorg/sglang:v0.5.21-rocm10-mi35x` with this branch reinstalled in full over
the stock SGLang:

```shell
SGLANG_USE_AITER=1 \
AITER_USE_FLYDSL_MOE_SORTING=1 \
ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
SAFETENSORS_FAST_GPU=1 \
SGLANG_WARMUP_TIMEOUT=10000 \
python3 -m sglang.launch_server \
  --model-path amd/Qwen3.8-2.4T-A95B-Quark-MXFP4 \
  --tp-size 8 \
  --trust-remote-code \
  --reasoning-parser qwen3 \
  --tool-call-parser qwen3_coder \
  --attention-backend aiter \
  --kv-cache-dtype fp8_e4m3 \
  --mamba-ssm-dtype bfloat16 \
  --page-size 64 \
  --chunked-prefill-size 16384 \
  --max-prefill-tokens 16384 \
  --max-running-requests 256 \
  --disable-radix-cache \
  --mem-fraction-static 0.9 \
  --model-loader-extra-config '{"enable_multithread_load": true}' \
  --watchdog-timeout 12000 \
  --enforce-shared-experts-fusion
```

Dropping `--enforce-shared-experts-fusion` gives the baseline: the shared expert stays BF16
and runs unfused.

The split is deliberate: the decision of *whether* to convert lives with the quantization
config, the ROCm-only kernel call lives with the MXFP4 scheme, and the copy into the fused
slot lives with `FusedMoE` alongside the FP8 hook that already solves the same problem.

Rebased onto `main` at `11bfd868` of 2026-10-11. The change depends on
[#40754](https://github.com/sgl-project/sglang/pull/40754)
(`e2f4fed`, merged 2026-09-24), which is in `main`. That PR gave the text-only
`Qwen3_5MoeForCausalLM` the shared-expert fusion weight remapping its multimodal sibling
already had, `mlp.shared_expert.* -> mlp.experts.{num_experts}.*`. Without it those weights
were silently dropped and the fused slot left uninitialized. The remap is what makes the
shared-expert tensors arrive at the fused slot at all, and the loader hook added here
intercepts them at that slot and converts them on the way in. #40754 covered checkpoints
whose shared expert already matches the routed-expert dtype (FP8), so no conversion was
needed; this PR extends the same path to the Quark MXFP4 checkpoint, where the shared expert
is BF16 and the conversion is the missing piece.

### The path through the code

The whole flow for one MoE layer on the path where the conversion does happen, with the
reasoning the diff cannot show attached to the step it belongs to. **Bold** is added by this
PR, *italic* is updated by it, and plain is untouched code the feature rides on.

1. *`QuarkConfig.__init__`*, `quark.py` - parses the checkpoint's quant config; this PR adds
   the `model_type` capture.
2. `_qwen3_5_shared_experts_fusion_disable_reason`, `models/qwen3_5.py` - asks whether
   fusion is possible at all.
3. *`can_fuse_shared_expert`*, `quark.py` - used to refuse on the dtype mismatch, and now
   also answers yes when the online conversion is available.
4. **`shared_expert_online_mxfp4_supported`**, `quark.py` - requires
   `--enforce-shared-experts-fusion`, a ROCm build,
   `SGLANG_USE_AITER`, gfx95x, a prequantized checkpoint, one of the Qwen3.5 MoE
   `model_type`s, and that the layer-0 MoE config resolves to MX-FP4 rather than to the W4A8
   or FP8 scheme. The `model_type` restriction is deliberate, and it carries more weight now
   that the opt-in is `--enforce-shared-experts-fusion`, which the DeepSeek-V4 recipes pass
   as a matter of course: `can_fuse_shared_expert()` is also reached from
   `quant_blocks_shared_experts_fusion()` in `models/deepseek_common/utils.py`, so without
   the restriction a DeepSeek-family Quark MXFP4 checkpoint excluding its
   `mlp.shared_experts.*` would silently start quantizing it on a model family that was
   never measured.
5. **`shared_expert_excluded_from_quant`**, `quark.py` - confirms the shared-expert body is
   in `exclude`, so it really is BF16.
6. **`_non_mxfp4_moe_layer_overrides`**, `quark.py` - scans `layer_quant_config` up front,
   because layer 0 answers for layer 0 only while the fused slot lives in every MoE layer.
   Empty here, so no fallback. Any refusal in steps 4 to 6 instead calls
   **`_warn_online_mxfp4_unavailable`** to name the unmet condition and falls back to a
   standalone shared expert; without the warning that fallback is silent, and it is only
   reachable once the flag was genuinely asked for.
7. `FusedMoE.__init__`, `layer.py` - sets `_has_fused_shared` and `_num_local_routed`, and
   sizes the buffers with one extra slot.
8. *`get_quant_method`*, `quark.py` - this PR adds the guard here rather than in
   `get_moe_scheme()`, because block-FP8 MoE layers are dispatched straight to
   `Fp8MoEMethod` earlier in this function and never reach the scheme lookup. A mixed
   checkpoint would otherwise fuse a BF16 shared expert into an FP8 buffer without the guard
   ever being consulted.
9. **`shared_expert_online_mxfp4_for_layer`**, `quark.py` - `isinstance(layer, FusedMoE)`
   and `layer._has_fused_shared` and the model-wide answer. The per-layer question is
   separate because fusion can be off for this layer through
   `--disable-shared-experts-fusion`, a DeepEP / DeepEP-v2 / MoRI a2a backend, a
   shared-expert intermediate size that differs from the routed one, or per-rank shared
   slots at `moe_ep_size > 1`. Nothing is copied into a fused slot then, so neither the
   guard nor the scheme's warning should fire.
10. **`shared_expert_needs_online_mxfp4`**, `quark.py` - the model-wide answer. Nothing here
    is cached, so step 8 computes the step 9 result once and passes it to step 12 rather
    than letting the chain run twice per MoE layer.
11. `_find_matched_config`, `quark.py` - resolves this layer's spec to MX-FP4, so the
    `NotImplementedError` backstop in step 8 is not taken.
12. *`get_moe_scheme`*, `quark.py` - this PR adds the `quantize_shared_expert_online`
    parameter, so the decision from step 9 is passed in rather than recomputed.
13. *`QuarkW4A4MXFp4MoE.__init__`*, `quark_w4a4_mxfp4_moe.py` - stores the flag and emits
    the one-time warning that the shared expert's weights and input activations are both
    being quantized.
14. *`create_weights`*, `quark_w4a4_mxfp4_moe.py` - this PR adds the rejection of a hidden
    size or a per-partition intermediate size that is not a multiple of 32, naming which
    dimension and why, so an unsupported TP size fails at startup rather than part way
    through loading.
15. `Qwen3_5MoeForCausalLM.load_weights`, `models/qwen3_5.py` - remaps
    `mlp.shared_expert.{gate,up,down}_proj` to `mlp.experts.{num_experts}.*`, which is what
    #40754 added and what this PR depends on.
16. `FusedMoE.weight_loader`, `layer.py` - turns the checkpoint's logical id into the
    physical slot `_num_global_routed + shared_expert_id`.
17. `_weight_loader_physical`, `layer.py` - `_map_global_expert_id_to_local_expert_id`
    narrows that to this rank's local slot.
18. *`_weight_loader_impl`*, `layer.py` - computes `shard_dim`; this PR adds the call to the
    hook below.
19. **`_maybe_load_bf16_shared_expert_as_fp4`**, `layer.py` - the hook. It runs here, after
    the id mapping, so it can compare against `_num_local_routed`, which keeps it correct
    when EPLB (expert-parallel load balancing) adds redundant physical experts and the
    logical id the checkpoint carries diverges from the physical slot count.
20. **`quantize_shared_expert`**, `quark_w4a4_mxfp4_moe.py`.
21. `dynamic_mxfp4_quant`, aiter - packed uint8 weight plus E8M0 scales for the whole
    unsharded tensor. Quantizing whole and sharding afterwards gives the same bytes as
    sharding first, because MX blocks run along K: the hidden size for `w1`/`w3`
    (`gate_proj`/`up_proj`, never split by TP) and the intermediate size for `w2`
    (`down_proj`, which TP does split, but only at multiples of the 32-element block size,
    enforced in step 14).
22. `_load_model_weight_or_group_weight_scale`, `layer.py` - for the packed weight.
23. `_load_w13` or `_load_w2`, `layer.py` - narrows by `moe_tp_rank` and copies into the
    fused slot.
24. `_load_model_weight_or_group_weight_scale`, `layer.py` - again, for the scales.
25. `_load_w13` or `_load_w2`, `layer.py` - same narrowing, same slot, scale buffer.
26. `process_weights_after_loading`, `quark_w4a4_mxfp4_moe.py` - shuffles weights and scales
    for the grouped GEMM, fused slot included.
27. `apply_weights`, `quark_w4a4_mxfp4_moe.py` - at inference, one W4A4 grouped GEMM over
    top-k routed experts plus the shared slot.

Steps 1 to 6 run once per model, 7 to 14 once per MoE layer, 15 to 25 three times per MoE
layer (`gate_proj`, `up_proj`, `down_proj`), and 26 to 27 once per layer after loading.

Steps 15 to 18 and 21 to 27 are untouched. The conversion inserts itself at exactly two
points, one decision site in `get_quant_method()` and one interception in the weight loader,
and reuses the routed experts' narrowing, padding and shuffling for everything after. That
is why tensor-parallel narrowing, aiter's intermediate padding, `use_presharded_weights` and
the gate/up ordering within `w13` need no special handling for the fused slot.

### Why `--enforce-shared-experts-fusion` rather than a new flag

An earlier revision of this PR added a dedicated `SGLANG_FUSE_SHARED_EXPERTS_ONLINE_MXFP4`
environment variable. That is gone. The opt-in is the existing
`--enforce-shared-experts-fusion`, which already means "fuse the shared expert even where
the gate would normally refuse", and a BF16 shared expert on an MXFP4 checkpoint is exactly
such a refusal. Reusing it keeps the opt-in in `server_args` logging, beside
`--disable-shared-experts-fusion`, which it is already mutually exclusive with, and leaves
`environ.py` and the environment-variable reference untouched.

The cost is that on one checkpoint family the flag now also changes numerics, which is why
`_ONLINE_SHARED_EXPERT_MXFP4_MODEL_TYPES` restricts the new behaviour to the Qwen3.5 MoE
`model_type`s: the DeepSeek-V4 recipes pass `--enforce-shared-experts-fusion` routinely and
must not start quantizing anything. Happy to split the two decisions back into separate
arguments if maintainers would rather have them apart.

### Documentation

The `--enforce-shared-experts-fusion` help text in `arg_groups/fields/exec_.py`, and the
matching row in `docs/docs/advanced_features/server_arguments.mdx`, gain a sentence on what
the flag additionally does to a Quark MXFP4 Qwen3.5/Qwen3.8 checkpoint that excludes its
shared expert from quantization. The AMD GPUs bullet of the Qwen3.5 cookbook says the same.
All three state that the shared expert's weights and input activations end up at MXFP4, so
accuracy should be validated.

### Tests

Both files are CPU-only and registered with `register_cpu_ci` in the `base-a-test-cpu`
suite: no model loading, no GPU, no aiter.

`TestSharedExpertOnlineMxfp4Gate` in `test_quark_config.py` covers the gating decision
above, one test per condition, including that a layer without a fused shared slot is
neither told to convert nor rejected. Every pre-existing test in the file is unchanged; the
only edits outside the new class are the suite's `est_time` estimate and the
`unittest.mock` import line.

`test_quark_shared_expert_online_mxfp4_loader.py` is new and covers the loader hook:
placement within `w13` and `w2`, sharding at TP2 and TP8 at every rank, aiter's intermediate
padding, and the cases the hook has to decline. It borrows the real `_load_w13` and
`_load_w2` and drives them with position-encoding bytes, so the placement logic under test
is the one the routed experts use.

## Accuracy Tests

gsm8k, 5-shot, run through `lm_eval`'s `local-chat-completions` against the served model at
temperature 1.0 with the model's own chat template, N = 1319 questions per run. Ten runs: five
fusion ON / OFF pairs. Both arms of a pair share one image and one config and differ only in
`--enforce-shared-experts-fusion`, verified across every logged server parameter.

Two images were measured, to separate the feature from the aiter underneath it:

| Image | aiter | Pairs |
| --- | --- | --- |
| stock aiter | the base image's, ROCm/aiter `acf8fdf93` of 2026-09-12 | concurrency 4, 32, 64 |
| rebuilt aiter | `amd-sriram/aiter` `e8f6cf54` | concurrency 32, 64 |

### Reading these two tables together

**Fusion costs about 4 pp of strict-match, and that result is solid.** All five pairs move the
same way, on two different aiter builds, and pooling gives P around 1e-06 and 5e-05. The
concurrency-32 stock-aiter pair at P = 0.061 is the weakest of the five; it is not the whole
picture.

**It costs nothing measurable on flexible-extract.** Pooled, the two images give +0.10 pp and
−0.08 pp, with P of 0.78 and 0.86. The model is still solving the problems at the same rate; it
is labelling the answer differently.

The difference between the two filters is the entire effect. strict-match scores a reply zero
unless it contains a literal `#### N`; flexible-extract takes the last number regardless. Pulling
the generated text out of the server logs for the concurrency-32 stock-aiter pair, replies with no
marker rose from 150 of 1289 parsed (11.64%) with fusion off to 189 of 1293 (14.62%) with it on, a
rise of 2.98 pp that accounts for the 2.58 pp of strict-match lost at that point.

Nothing was truncated. Every single marker-less reply in both arms ended with
`finish_reason: stop`, `matched: <|im_end|>` — a natural end of turn, not a stop string and not
`max_gen_toks`. A representative case, correct to the cent and scored zero by strict-match:

```
QUESTION: Kyle bought last year's best-selling book for $19.50. This is with a 25% discount
          from the original price. What was the original price of the book?

REPLY:    Let the original price be \(x\).
          Since Kyle paid with a 25% discount, he paid 75% of the original price:
          \[ 0.75x = 19.50 \]
          \[ x = \frac{19.50}{0.75} = 26 \]
          The original price of the book was **$26.00**.
```

Two further observations. Across three fusion-OFF runs at concurrency 4, 32 and 64 the
marker-omission rate was 11.64%, 11.64% and 11.72%, a spread of 0.08 pp, while the Jaccard overlap
between any two of those runs' missing sets was only 0.12 to 0.16 — at temperature 1.0 *which*
questions lose the marker is largely resampled each run even though the rate is highly
reproducible. And the variance sits on the fusion side: fusion OFF scored 0.8620 / 0.8658 / 0.8620
and 0.8650 / 0.8650 across the five pairs, while fusion ON ranged from 0.8052 to 0.8400.

Independently, sglang's own `run_eval` gsm8k on the same image, whose grader also takes the last
number, found no fusion effect at all: 0.9825 against 0.9825 at 4 threads and 0.9802 against
0.9810 at 32. That agrees with flexible-extract and is the behaviour to expect if answer
correctness is untouched.

### Post-rebase spot checks

The gsm8k pairs above were measured on the pre-rebase `01c9a620`, already gated on
`--enforce-shared-experts-fusion`. The rebased branch at `abddcd87` was then re-measured end to
end on 2026-10-11, and two further evals ran inside each of those two serving sweeps, in the
first sweep point of both arms and so against the same server instance that produced the speed
numbers below:

| Eval | fusion ON | fusion OFF |
| --- | ---: | ---: |
| GPQA via sglang `run_eval`, temperature 1.0, top-p 0.95, thinking enabled | 0.9242 | 0.9192 |
| RULER `niah_single_2` at 65536 via `lm_eval` | 1.0 | 1.0 |
| RULER `niah_single_2` at 131072 via `lm_eval` | 1.0 | 1.0 |

GPQA is +0.50 pp with fusion on, against per-sample standard deviations of 0.265 and 0.273.
GPQA's question sets run to a few hundred, which puts the standard error near a point, so a
half-point difference is no change rather than a gain. Retrieval is exact in both arms at 64K
and at 128K, which is worth stating separately from gsm8k because the fused slot participates
in every MoE layer and a long-context regression would not show on a short-prompt eval.

### The aiter rebuild is not a factor

Pooled strict-match loss is 3.97 pp on the stock-aiter image and 4.06 pp on the rebuilt one, and
flexible-extract is flat on both. This was checked because [amd-sriram/aiter#10](https://github.com/amd-sriram/aiter/pull/10)
adds a fallback for ROCm/aiter#4383, which made `dynamic_mxfp4_quant` default to a gfx950 Gluon
kernel. Inspecting the running container, the base image's aiter is `acf8fdf93` of 2026-09-12 and
its `dynamic_mxfp4_quant` contains no Gluon branch at all, so there is nothing for that fallback to
repair and both images take the same Triton quantization path.

### Limits of this evidence

These runs establish that fusion degrades output *formatting* on gsm8k and leave answer
correctness indistinguishable at this sample size. flexible-extract at roughly 0.975 is close
enough to saturation that a sub-point correctness regression would not show; the pooled 95%
confidence interval on the flexible-extract difference spans about ±0.7 pp. The mechanism behind
the formatting shift is also not established — a small weight perturbation changing stylistic
preference is consistent with the data but is not demonstrated by it.

All runs were at TP8, and `w2` (`down_proj`) is the projection whose K dimension TP splits, so
other TP sizes exercise shard boundaries these numbers do not cover. A greedy-decoding pass at
temperature 0 would make the comparison paired per question, permit a McNemar test and show which
questions flip; top-1 agreement and mean KL of teacher-forced next-token logprobs over a fixed
prompt set would be more sensitive still, at a fraction of the cost.

**On TTFT.** Median TTFT improves at all 12 points, by −1.53% on geomean. Mean TTFT is −0.71%,
better at 11 of 12, and P99 TTFT −0.30%, better at 10 of 12. The three exceptions are all
tail statistics on short request counts. P99 TTFT is worse at ISL 8192 concurrency 4 (+1.71%,
32 requests completed) and at ISL 128000 concurrency 16 (+0.42%, 96 completed), so each P99 is
a single sample; both points' medians move the other way, at −1.89% and −0.54%. Mean TTFT is
worse only at ISL 60000 concurrency 16 (+2.17%), where the median is −0.64%.

An earlier sweep of this branch on the v0.5.20 base showed P99 TTFT slightly worse at all 12
points. That no longer reproduces on v0.5.21, where it is now marginally better on geomean, so the
prefill side is best described as unchanged to slightly improved rather than as a cost.

The decode side is where the change pays, and the gain is largest where the shared expert is the
biggest share of the work: +10.38% output throughput at ISL 8192 with 4 concurrent, falling to
+1.13% at ISL 60000 with 64 concurrent. Fusing the shared expert removes a separate GEMM and its
per-layer launch overhead, which matters most when the routed-expert work is not already
saturating the GPUs. Mean ITL and mean TPOT both improve by about 4.6% on geomean at all 12
points.

The reason to keep the feature opt-in is the precision trade on the shared expert and the gsm8k
formatting regression documented above, not a latency cost.
