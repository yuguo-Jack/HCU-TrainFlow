# [Perf] [AMD] quark/Qwen3.8: Quantize the BF16 shared expert of Quark MXFP4 checkpoints to MXFP4 while loading for shared-expert fusion

[Upstream PR](https://github.com/sgl-project/sglang/pull/41899) · state: open · merged: False

## Original PR description

 

## Motivation

This is a ROCm performance change. With `--enforce-shared-experts-fusion` the
BF16 shared expert of a Quark MXFP4 checkpoint is quantized to MXFP4 at load and fused into
the routed grouped GEMM (general matrix multiply), instead of running as a separate BF16
MLP (multi-layer perceptron). On `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` over 8x MI355X at TP8
that is worth **+4.5% output throughput and -4.6% mean ITL (inter-token latency)**, as a
geomean across a 12-point serving sweep.

There is currently no Qwen3.8-2.4T-A95B checkpoint in which the shared expert is FP4
quantized, so shared-expert fusion is unavailable for this model family on MXFP4.

`amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` quantizes the routed experts to MXFP4 but lists the
shared-expert body in the Quark quantization config's `exclude` list, so
`gate_proj`/`up_proj`/`down_proj` of the shared expert ship in BF16. Shared-expert fusion
works by appending the shared expert as one more routed expert at slot `num_experts`, so
that a single grouped GEMM serves top-k routed experts plus the shared one. That requires
every slot in the fused weight to have the same dtype, so today
`QuarkConfig.can_fuse_shared_expert()` sees the format mismatch and refuses, and the model
falls back to running the shared expert as a separate BF16 MLP alongside the routed grouped
GEMM. Rather than wait for a new checkpoint, this PR quantizes the BF16 shared expert at
load time so the existing checkpoint can use the fused path.

The feature is **off by default** and gated behind the existing
`--enforce-shared-experts-fusion` server argument, which already means "fuse the shared
expert even where the gate would normally refuse". In the fused path the shared expert goes
through the routed experts' W4A4 grouped GEMM, so its weights *and* its input activations
are quantized to MXFP4, where the standalone path it replaces ran BF16 x BF16. That is a
real precision trade and should be an explicit choice rather than something a checkpoint
opts into silently.

### Reproduction

Run inside `lmsysorg/sglang:v0.5.21-rocm10-mi35x` with this branch reinstalled in full over
the stock SGLang:

```shell
SGLANG_USE_AITER=1 \
AITER_USE_FLYDSL_MOE_SORTING=1 \
ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
SAFETENSORS_FAST_GPU=1 \
SGLANG_WARMUP_TIMEOUT=10000 \
python3 -m sglang.launch_server \
 --model-path amd/Qwen3.8-2.4T-A95B-Quark-MXFP4 \
 --tp-size 8 \
 --trust-remote-code \
 --reasoning-parser qwen3 \
 --tool-call-parser qwen3_coder \
 --attention-backend aiter \
 --kv-cache-dtype fp8_e4m3 \
 --mamba-ssm-dtype bfloat16 \
 --page-size 64 \
 --chunked-prefill-size 16384 \
 --max-prefill-tokens 16384 \
 --max-running-requests 256 \
 --disable-radix-cache \
 --mem-fraction-static 0.9 \
 --model-loader-extra-config '{"enable_multithread_load": true}' \
 --watchdog-timeout 12000 \
 --enforce-shared-experts-fusion
```

Dropping `--enforce-shared-experts-fusion` gives the baseline: the shared expert stays BF16
and runs unfused.

The decision of *whether* to convert lives with the quantization
config, the ROCm-only kernel call lives with the MXFP4 scheme, and the copy into the fused
slot lives with `FusedMoE` alongside the FP8 hook that already solves the same problem.

The change depends on #40754
(`e2f4fed`, merged 2026-09-24), which is in `main`. That PR gave the text-only
`Qwen3_5MoeForCausalLM` the shared-expert fusion weight remapping its multimodal sibling
already had, `mlp.shared_expert.* -> mlp.experts.{num_experts}.*`. Without it those weights
were silently dropped and the fused slot left uninitialized. The remap is what makes the
shared-expert tensors arrive at the fused slot at all, and the loader hook added here
intercepts them at that slot and converts them on the way in. #40754 covered checkpoints
whose shared expert already matches the routed-expert dtype (FP8), so no conversion was
needed; this PR extends the same path to the Quark MXFP4 checkpoint, where the shared expert
is BF16 and the conversion is the missing piece.
