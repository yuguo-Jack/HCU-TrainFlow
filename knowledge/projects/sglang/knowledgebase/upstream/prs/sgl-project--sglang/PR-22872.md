# [Fix][Perf] Improve Elastic EP fault tolerance with direct controller routing and async active-rank snapshots

[Upstream PR](https://github.com/sgl-project/sglang/pull/22872) · state: closed · merged: False

## Original PR description

## Motivation

This PR improves the Elastic EP fault-tolerance path in four areas: active-rank control-plane routing, GPU-to-CPU synchronization overhead, correctness of async fault detection under overlap scheduling, and coverage of non-overlap scheduling.

Previously, active-rank updates were routed through tokenizer output handling. In multi-tokenizer mode this is unreliable because `ActiveRanksOutput` is an internal control-plane message and has no request-associated `http_worker_ipc`, so it can be dropped by tokenizer routing. Active-rank updates should bypass tokenizer routing and be delivered through a control-plane path.

The original fault-tolerance path also synchronously read GPU active-rank state on the forward path, which introduced an observed ~2ms GPU/CPU synchronization bubble. This PR replaces that hot-path sync with async pinned-CPU snapshots, reducing snapshot submission overhead to roughly ~2us in the overlap path.

Simply making the snapshot async is not enough: with overlap scheduling, a stale forward result can be committed before the next forward observes the fault. This PR moves detection to the scheduler-side result synchronization point, before generated tokens are committed to `req.output_ids`, and uses retract-based recovery so clients can continue transparently when possible.

Finally, the original detection path was wired only into the overlap event loops. This PR extends the same scheduler-side detection to the non-overlap loops so elastic EP can be enabled without `--enable-overlap-schedule`.

## Modifications

### 1. Route active-rank updates through a control-plane publisher

- Added a dedicated Scheduler -> DataParallelController control-plane channel.
- `Scheduler` no longer sends `ActiveRanksOutput` through tokenizer output handling.
- Added a lightweight `ElasticEPStatusPublisher` abstraction with a single `publish_committed_active_ranks` entry point.
- `ControllerElasticEPStatusPublisher` owns the DPC-specific conversion from TP active masks to DP worker active status and sends `ActiveRanksOutput`.
- The default publisher is a no-op, so non-DP or unsupported control-plane configurations do not perform unnecessary conversion or routing.
- Publishing is now driven only from the committed-snapshot path, removing an earlier instantaneous-view publishing branch in `run_batch` that disagreed with the scheduler's own committed (sticky-latched) view of active ranks.

This keeps scheduler logic independent from the DPC wire format while preserving the current DP behavior, and ensures DPC sees the same sticky-latched view that the scheduler uses for its own retract decisions.

### 2. Use async active-rank snapshots and scheduler-side detection

Overlap scheduling already synchronizes `result.copy_done` before processing the previous batch result. Since `submit_active_snapshot` and `copy_done.record()` are issued on the same `forward_stream`, synchronizing `copy_done` also guarantees the async active-rank D2H copy has completed, without adding another GPU sync.

Changes:

- `ModelRunner.forward` submits active-rank snapshots at the end of forward.
- `ElasticEPState.submit_active_snapshot()` accepts a `non_blocking` flag so the same call site serves both overlap (async pinned-CPU staging) and non-overlap (synchronous staging valid on return).
- `ElasticEPState.commit_active_snapshot()` consumes the oldest staging slot and advances the committed sticky mirror under a CPU `all_reduce(MIN)`.
- `ElasticEPState.is_stale_snapshot()` is now a pure CPU comparison against the last handled snapshot.
- Detection lives in `_handle_elastic_ep_result_boundary` (overlap: `popleft -> copy_done.synchronize -> commit -> publish -> check stale -> retract or commit`; non-overlap: same flow without the `copy_done` step, since the staging buffer is already synchronously valid).
- Staging buffers are initialized to healthy state to avoid startup false positives.

#### Cost / benefit of the per-iteration consensus

The main per-iteration cost added by this design is a CPU `all_reduce(MIN)` over the TP CPU group inside `commit_active_snapshot`, on a tensor of `world_size` bytes. This collective is what gives all ranks a single, consistent committed view of active ranks: without it, each rank would only see its own local AND of (device active mask, pg snapshot, pg active mask), and ranks could disagree about who is alive in the fault window. Disagreement here directly causes "collective drift" — some ranks entering retract while others enter the next forward's MLP `all_gather` or `broadcast_pyobj` — which is the failure mode we are trying to prevent.

In overlap mode this barrier sits inside `pop_and_process`, which runs concurrently with the next forward's CPU prepare, so its visible cost is largely hidden. In non-overlap mode the barrier is on the critical path, but the payload is tiny (typical CPU TP collective is tens of µs at intra-node scale), and non-overlap already pays for stream synchronization on the result CPU copies anyway.

Beyond avoiding collective drift, this consensus has two other benefits worth calling out:
- The same committed view drives both internal retract decisions and the external DPC `status` view, so they cannot disagree (see §1).
- The sticky-dead latch is now consistent across ranks, so a rank cannot be considered dead by one peer and alive by another between the fault and the next consensus.

### 3. Retract-based transparent recovery

On a newly detected fault, the scheduler clears any in-flight overlap result queue, drains GPU work, retracts in-flight requests, runs EPLB rebalance, and marks the snapshot as handled.

Retracted requests are requeued and resumed by existing scheduling infrastructure. If a request exceeds `SGLANG_ELASTIC_EP_MAX_RETRACTION`, it falls back to an abort with `ElasticEPRankFault`.

The retract path covers both `running_batch` and `cur_batch`. This matters because when `cur_batch` is a freshly launched prefill batch, its reqs have already been allocated KV by `prepare_for_extend` but are not yet merged into `running_batch` (the merge runs at the next `get_next_batch_to_run`, which never arrives after fault). Without draining `cur_batch`, those requests' KV would leak. Draining is dedup'd by object identity (`cur_batch is self.running_batch`), since for a decode batch `cur_batch` and `running_batch` are the same object — a second `release_req` on the same `Req` would crash on freed-`req_pool_idx`.

This prevents poisoned tokens from being committed while still allowing normal client streams to pause briefly and continue after recovery.

### 4. PD-disagg decode support

The same scheduler-side detection pattern is applied to overlap PD-disagg decode and to its non-overlap counterpart. The existing PD retract path handles KV offload/load and requeueing, so decode-side in-flight requests can also recover transparently.

### 5. Non-overlap scheduling support

The detection pattern is wired into `event_loop_normal` and `event_loop_normal_disagg_decode` so elastic EP works with `--disable-overlap-schedule` as well. To make `_handle_elastic_ep_result_boundary` mode-agnostic, the snapshot staging is made synchronous on the non-overlap path via `submit_active_snapshot(non_blocking=False)`. The retract function uses `if self.enable_overlap: self.result_queue.clear()` to avoid touching `result_queue` from non-overlap loops where it is not initialized.

PD-disagg prefill and pipeline-parallel loops are intentionally not covered here.

## Correctness Notes

- Fault detection happens before `process_batch_result_decode`, so poisoned tokens do not enter `req.output_ids`.
- Retract length is based on committed `output_ids`, so poisoned KV positions are not preserved.
- Non-elastic EP paths are unchanged because the boundary check is gated on `self.server_args.elastic_ep_backend is not None` and the snapshot branch is skipped when `ElasticEPStateManager.instance()` is `None`.
- DPC-specific TP-to-DP aggregation is isolated inside the controller publisher, not scheduler logic.
- Drain order in retract is dedup'd by object identity rather than by `req.rid` / set membership — this exploits the existing scheduler invariant (also used in `abort_request` at scheduler.py:3527) that `cur_batch is self.running_batch` iff they share reqs, avoiding a per-req hash lookup.
- Publishing is consolidated to the committed (sticky-latched) view, so the controller's `status` and the scheduler's retract decisions are derived from the same source of truth.

## Tests

Tested non-disaggregated and PD-disaggregated serving with Elastic EP enabled, including multi-tokenizer mode, in both overlap and non-overlap scheduling modes.

Fault tolerance was tested by killing a scheduler process during serving:

```bash
pkill -f sglang::scheduler_DP7_TP7_EP7
```

Verified active-rank updates reach DPC, failed DP workers stop receiving new requests, EPLB rebalance is triggered, in-flight requests retract and resume transparently (including requests that were freshly launched as a prefill batch and not yet in `running_batch`), repeated failures hit the configured abort fallback, and normal serving continues without injected faults.

The async snapshot path removes the previous blocking GPU-to-CPU active-rank sync from the hot path of overlap scheduling, with observed improvement around the previous ~2ms bubble. The non-overlap path uses synchronous staging for the snapshot, which has no measurable perf impact since non-overlap already pays for stream synchronization on result CPU copies.

- KMSorSMS · comment · 2026-05-07T10:02:00Z · [source](https://github.com/sgl-project/sglang/pull/22872#issuecomment-4396136235)

Thanks for the review!

Two design points from this PR that may be useful context if you do start a follow-up for the control-plane integration:

**1. Scheduler ↔ upper-layer reporting is fully decoupled via a small publisher abstraction.**

The scheduler no longer knows anything about DPC's wire format. It only calls into `ElasticEPStatusPublisher` (`python/sglang/srt/managers/elastic_ep_status.py`):

```python
class ElasticEPStatusPublisher:
    def publish_committed_active_ranks(
        self, committed_active_ranks: torch.Tensor
    ) -> None:
        pass


class ControllerElasticEPStatusPublisher(ElasticEPStatusPublisher):
    """DPC-specific: aggregates TP active mask -> per-DP status, sends ActiveRanksOutput."""
    ...


def create_elastic_ep_status_publisher(
    server_args, send_to_controller
) -> ElasticEPStatusPublisher:
    if (
        server_args.enable_dp_attention
        and server_args.elastic_ep_backend is not None
        and server_args.dp_size > 1
    ):
        return ControllerElasticEPStatusPublisher(
            send_to_controller, server_args.dp_size
        )
    return ElasticEPStatusPublisher()  # no-op default
```

Today the only concrete upper layer is DPC, but plugging in a different consumer (a different control plane, an external scheduler, a metrics sink, etc.) just means subclassing `ElasticEPStatusPublisher`, overriding `publish_committed_active_ranks`, and selecting it in the factory. The scheduler side does not need to change. So whichever direction the follow-up goes, the integration surface is already this one method.

**2. The per-iteration `all_reduce(MIN)` in `commit_active_snapshot` is not just a perf detail — it also fixes a real correctness issue on the recover path.**

Before this PR, each rank's view of "who is dead" was its own local AND of (device active mask) ∩ (pg observation). These can diverge in the fault window — rank A may already see rank C as dead while rank B has not yet observed it. With that inconsistency, when the recovery path eventually enters its `peer_state` collective (itself an all_reduce), some ranks participate and some don't, and the collective hangs.

The new `commit_active_snapshot` consolidates both the EP-side and PG-side views and then forces consensus across the TP group:

```python
self.committed_active_ranks_cpu.bitwise_and_(snapshot)              # EP-side
self.committed_active_ranks_cpu.bitwise_and_(global_pg_snapshot)    # PG-side
self.committed_active_ranks_cpu.bitwise_and_(global_pg_active_ranks_cpu)
torch.distributed.all_reduce(
    self.committed_active_ranks_cpu,
    op=torch.distributed.ReduceOp.MIN,
    group=consensus_cpu_group,
)
```

`MIN` makes every rank converge to the same committed view (any rank seeing a peer as dead → all ranks see it as dead). That stable view is then both:

- Used by the scheduler for the retract/recover decision, so the recovery-path collective is entered consistently across ranks (no more "some ranks miss the all_reduce" hang).
- Reported up via the publisher, so DPC sees exactly the same view the scheduler is acting on — no skew between routing decisions and the scheduler's own state.

The cost is one CPU collective over `world_size` bytes on the TP CPU group; in overlap mode, it sits inside `pop_and_process` and overlaps with the next forward's CPU prepare.

For what it's worth, I've also tested this on a 2-node setup (both fault tolerance and recovery) and under PD-disaggregated serving (fault tolerance), and both pass cleanly. 

Happy to discuss the publisher abstraction further if you want to extend it for the follow-up control-plane work.

The `event_loop` implementation results in a tight busy loop when no requests are pending from either the tokenizer or the scheduler. Since both `recv_from_tokenizer` and `recv_from_scheduler` use `zmq.NOBLOCK` and the loop immediately restarts after the inner loop breaks, this will cause 100% CPU utilization on the controller process. Following PEP 8 and general best practices for asynchronous I/O, it is recommended to use a `zmq.Poller` to wait for events on either socket with a small timeout, or at least include a small `time.sleep` when no data is drained to yield the CPU and reduce resource consumption.
