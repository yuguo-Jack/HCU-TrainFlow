# [Fix] diffusion: Count reclaimable page cache as available inside a cgroup cap

[Upstream PR](https://github.com/sgl-project/sglang/pull/48418) · state: open · merged: False

## Original PR description

## Motivation

Inside a memory-capped cgroup, `physical_host_memory_available_bytes()` took the cgroup's `memory.current` as used. That number includes the page cache charged to the cgroup, which the kernel reclaims under the cap. Outside a cgroup the same function uses psutil's `available` (MemAvailable), which counts that cache as available. So the two paths disagreed.

Seen on an RTX 5090 desktop with 60 GB RAM, MiniMax-H3 T2VA 480p, run in `systemd-run --user --scope -p MemoryMax=56G` right after another engine ran in the same scope:

| | host memory log | DiT layers pinned | denoise |
|---|---|---|---|
| no cgroup | 41.5 GiB available | 32 / 50 | 4.55 s/it |
| 56G scope | 17.6 GiB available (cap 56.0, in use 38.4) | 12 / 50 | 5.12 s/it |

A container started with `--memory` hits the same thing, since the checkpoint it reads at load is charged to it as cache. The Ascend server-test conftest evicts stale model cache before each case to work around the same reading.

## Modifications

- Inside a cap, usage now excludes the file LRUs: `active_file + inactive_file` on v2, and `total_active_file + total_inactive_file` on v1 (v1 `usage_in_bytes` covers the subtree; the unprefixed keys do not). This matches what MemAvailable counts. shmem/tmpfs stays counted as used. It is in v2's `file` and v1's `cache`, which the old shared-pool path subtracted, but only swap can reclaim it.
- `shared_pool_available_bytes()` became identical to the physical reading, so it is removed and its one caller uses `physical_host_memory_available_bytes()`.
- The startup line now shows how much of the cgroup usage is reclaimable cache.

Why not subtract only `inactive_file` (the kubelet working set):
- Which list a page is on depends on how it was accessed and on the LRU implementation. MGLRU reports the young generations as active, and the classic LRU lets the active list grow to about sqrt(10 * GB) times the inactive one. Cold leftover cache can therefore sit on the active list, and the bug would stay.
- `page_cache_cannot_hold()` would count a hot, already-cached mapping as used. A courier rebuilt after LoRA would then switch to O_DIRECT reads for a mapping the cache already holds.

Counting a mapping's own cached pages as available does not let a placement evict the mapping it streams from:
- The planner leaves a layer on its mapping only when the copies do not fit. Each byte pinned out of the mapping is then a byte the mapping no longer needs cached.
- The readings that size anonymous or pinned memory (pin budget, layer plan, loader, AdaLN host tier) all run at load or configure time, before any mapping streams.

## Tests

`test_host_memory_budget.py` has a new `TestCgroupPageCache` that fakes `memory.max`, `memory.current` and `memory.stat`:
- cache left in a capped cgroup counts as available (the bug)
- a mapping the cache already holds on the active list is room for itself (rules out the inactive-only rewrite)
- shmem charged to the cgroup is not available (rules out a rewrite to `file`)
- v1 subtracts subtree totals

All four fail on main and pass here. I also checked each guard by mutation: inactive-only, `file`/`cache`, and v1 local keys are each caught. The whole file passes locally (36 tests, CPU). The layerwise offload, weight snapshot and component residency tests stub these functions; they need the full kernel stack, so CI runs them.

Not rerun. The 5090 host went offline before the scoped A/B. The expected result is the uncapped numbers above (about 41 GiB available, about 32 pins).
