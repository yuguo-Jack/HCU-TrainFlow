# [AMD][DSv4] Tuned decode moe kernels for mori-EP backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/41119) · state: closed · merged: False

## Original PR description

## Motivation

On DSv4 EP8, prefill and decode send tokens to very different experts: decode concentrates on a few hot experts, while prefill spreads almost evenly. The same MoE shape therefore wants different kernels in each case. aiter can't tell them apart, because its tuned-config lookup uses only the padded token count, and prefill and decode fall into the same size buckets. Whichever resolves a bucket first fixes the kernel for both, and with CUDA graphs that is always decode. As a result, a decode-tuned table cannot be enabled without also forcing those kernels onto prefill.

This PR adds the sglang side of a per-regime contract with aiter. An aiter that has the regime API reads one tuned table per regime, from `AITER_CONFIG_FMOE_PREFILL` and `AITER_CONFIG_FMOE_DECODE`.

Corresponding aiter PR : https://github.com/ROCm/aiter/pull/5821

## Summary of changes

- **`layers/moe/aiter_moe_regime.py` (new):**
  - Maps each `ForwardMode` to a regime. `DECODE`, `IDLE` and `TARGET_VERIFY` count as decode. `EXTEND`, `MIXED` and draft-extend count as prefill.
  - Adds `pin_decode_moe_regime()` for use during graph capture.
  - Both do nothing on non-HIP builds or on an aiter without the regime API, so the behaviour there is unchanged.
- **`ModelRunner.forward`:** sets the regime on every forward pass. This is a single delegating call, because `model_runner.py` is frozen.
- **`DecodeCudaGraphRunner.capture`:** pins the decode regime during capture. A replayed graph never re-enters `forward()`, so the kernel chosen at capture time is the one decode keeps using.
