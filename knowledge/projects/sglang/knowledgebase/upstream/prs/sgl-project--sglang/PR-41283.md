# [Perf] EAGLE rejection sampling on each row's top-k support

[Upstream PR](https://github.com/sgl-project/sglang/pull/41283) · state: open · merged: False

## Original PR description

## Motivation

With `--speculative-use-rejection-sampling`, every verify step builds the dense target distribution for all `bs * num_draft_tokens` rows. That means a full-vocab softmax, `top_k_renorm_probs`, `top_p_renorm_probs`, and then `chain_speculative_sampling_triton`, whose residual resample walks the whole vocab twice with one program per request.

When the requests use a top-k, only the top-k tokens of each row can carry target mass. Qwen's recommended `top_k=20` is one such case. Almost all of that work then reads and writes zeros. On large vocabularies this costs 0.29 ms at bs=1 and 1.2 ms at bs=32 on every verify step (248K vocab for Qwen3.5/3.6; RTX PRO 6000 numbers below).

## Modifications

- **`chain_speculative_sampling_topk_triton`** (in `kernels/ops/speculative/reject_sampling.py`) is the same chain rejection sampler, but it takes each row's sorted top-k logits instead of dense probabilities.
  - It applies temperature, top-k, softmax and top-p on that support, and keeps the dense chain's semantics. Top-k runs first. Top-k keeps every logit tied with the k-th one, like `top_k_renorm_probs`. Top-p keeps every probability tied with its pivot, like `top_p_renorm_probs`.
  - It then runs the same accept rule and residual resample as `speculative_sampling_classic_kernel`. Off the support p = 0, so max(p - q, 0) = 0, and the support holds everything the residual needs.
  - The final CDF is walked in token-id order, the same order as the dense kernel's vocab scan. So the two samplers pick the same token for the same coin.
- **`topk_support_width`** sets how many candidates to fetch: `next_power_of_2(max_top_k + 16)`, capped at the vocab size. The extra room holds logits tied with the k-th one, which are common with bf16 logits (see below).
- **`eagle_sample`** gets a new branch, taken only when all of these hold:
  - rejection sampling is on;
  - the platform is CUDA;
  - every request has `top_k <= 128` (`_SPARSE_TOP_K_LIMIT`, shared with UNO);
  - no request uses min_p.

  It gets the support with `flashinfer.top_k(..., deterministic=True)` and calls the new kernel. Every other case keeps the dense path. The draft-probs check moved into `_check_rejection_draft_probs` so both paths use it.
- **Degenerate residual:** if q >= p on the whole support, the new kernel falls back to sampling from p. The dense kernel returns token `vocab_size - 1` in that case.

## Accuracy Tests

**Kernel test.** The new `test_chain_topk_sampling_matches_dense` runs both samplers with the same bf16-rounded logits, draft probs and coins. It requires identical `predicts`, `accept_index` and `accept_token_num`. It covers:
- a single request;
- mixed per-request top-k (1/5/20/64) in one batch;
- no top-p.

**Wider randomized check** (not in CI, RTX PRO 6000). All 144 settings were identical to the dense `eagle_sample` path on every draw:
- bs 1 and 3;
- int32 and int64 ids;
- T / top-k / top-p in {1.0/20/0.95, 0.7/20/0.8, 1.0/40/off, 1.3/5/0.9, 0.6/128/0.95, 1.0/1/off};
- three logit scales, each in fp32 and bf16-rounded;
- 100 draws per setting, with fresh drafts and coins each time.

So were 200 draws of a mixed-top-k batch. Up to 2.33 of 3 drafts were accepted per request on average.

With bf16-rounded logits at vocab 248,320 and top-k 20, 1,750 of 3,840 rows (46%) have a tie at the k-th logit. All 24,000 row draws matched the dense path.

**End to end.** Setup:
- Qwen/Qwen3.6-35B-A3B-FP8;
- NEXTN: 3 steps, topk 1, 4 draft tokens;
- `--speculative-use-rejection-sampling`;
- one RTX PRO 6000.

GSM8K test set (1,319 questions), chat API, non-thinking, T 0.7 / top-p 0.8 / top-k 20:
