## Original PR description

# [Fix] kimi-k3: Reuse the attention-residual bank across forward passes

## Motivation

On MI350X, a TP8 Kimi-K3 server ends a long benchmark with 15.0–16.6 GiB more memory in use on each GPU than right after startup, and the amount differs by up to 1.6 GiB between GPUs. At `--mem-fraction-static` 0.91 and 0.93 the server ran out of memory during an ~8K-token prefill, each time on a different set of GPUs.

The difference between GPUs comes from timing. Every rank runs the same steps, but each one keeps a slightly different set of large cached segments, depending on which step sizes it saw and when its buffers were freed. A GPU that holds a few more segments has less memory left for allocations outside PyTorch, such as RCCL kernel scratch, and PyTorch cannot free its cache to make room for those. So a server with a few GiB of headroom per GPU can run out of memory on some GPUs while others still have room.

The cache grows because of two buffers that are sized by each step's token count and allocated fresh on every step. The caching allocator reuses a free segment only if it is large enough and never merges segments, so every new, larger size leaves another segment behind, and nothing calls `empty_cache()` while serving. The two buffers are:

1. The MoE stage-2 reduce target in aiter's `_flydsl_v2_stage2_wrapper` (112 KiB per token, 1.75 GiB at 16,384 tokens). [ROCm/aiter#7363](https://github.com/ROCm/aiter/pull/7363) fixes it there.
2. The attention-residual (AttnRes) bank in SGLang, which this pull request fixes. `AttnResidual.__init__` allocates the `[num_tokens, block_num, hidden_size]` snapshot bank on every forward:

```python
self.block_residual = hidden_states.new_empty(
    (num_tokens, block_num, hidden_size)
)
```

For Kimi-K3 (H = 7168, up to 8 banked blocks, bf16) that is up to 112 KiB per token, the same as the aiter target: 1.75 GiB for a 16K-token prefill chunk.

vLLM measured both buffers on Kimi-K3 TP8 on MI355X and needed both fixed. With only its bank fix ([vllm-project/vllm#63838](https://github.com/vllm-project/vllm/pull/63838)), the aiter target still drove minimum free memory to 0.12 GiB. With both, free cached segments stayed flat at about 6.3 GiB and the run finished.

## Modifications

`AttnResidual` takes its bank from one grow-only buffer per (device, stream), the same scheme as aiter#7363, and views it to each forward's shape:

```python
def _bank_scratch(shape, dtype, device) -> torch.Tensor:
    if device.type != "cuda" or torch.cuda.is_current_stream_capturing():
        return torch.empty(shape, dtype=dtype, device=device)
    nbytes = math.prod(shape) * dtype.itemsize
    key = (device, torch.cuda.current_stream(device).cuda_stream)
    buf = _BANK_SCRATCH.get(key)
    if buf is None or buf.numel() < nbytes:
        _BANK_SCRATCH.pop(key, None)
        buf = torch.empty(nbytes, dtype=torch.uint8, device=device)
        _BANK_SCRATCH[key] = buf
    return buf[:nbytes].view(dtype).view(shape)
```

- **Correctness:** the bank is a prefix of the buffer along the first dimension, so it stays contiguous, which the kernels need. Every forward writes a bank row before any read of it, so contents left by an earlier step are never read.
- **CUDA graphs:** a captured graph records the bank's address, and a buffer that later grows would free that memory. During capture the bank is allocated as before, from the graph's own pool.
- **Pipeline parallelism:** a rank that is not the last one sends its bank to the next rank (`proxy_tensors.tensors["attn_res_bank"]`), so the bank outlives the forward. `KimiK3LinearModel.forward` opens it with `reuse=self.pp_group.is_last_rank`, so those ranks allocate per forward as before. The last rank copies the inherited rows into its reused bank, also as before.
- **Streams:** the key includes the current stream, so forwards on different streams never share a bank. Forwards on one stream are ordered, so a forward can only overwrite the bank after the previous forward's kernels have read it.
- **Other devices:** non-CUDA devices (CPU tests, NPU) allocate as before.

`AttnResidual` and `AttnBank.open` gain a `reuse` argument that defaults to `True`. Other callers that open the bank, such as out-of-tree plugins that replace the layer loop, therefore reuse it without changes.

Memory: the buffer stays at the largest size seen for the life of the process, the same on every rank. A per-forward bank already needed that much at the peak, so the peak does not rise. When the buffer grows, the smaller one goes back to PyTorch's cache.

## Unit Tests

`test_attn_residual_bank_reuse.py` checks that:

- consecutive banks of 64, 16, 64 and 1 tokens share the same storage, each with the requested shape and contiguous, and a 65-token bank grows the buffer;
- a bank on another stream, and a bank with `reuse=False`, get their own storage;
- a bank opened during CUDA graph capture does not use or create the shared buffer;
- a reused bank that was filled with NaN by a larger step gives bit-identical aggregation results to a freshly allocated bank, over three blocks of writes and reads.

Not run yet.
