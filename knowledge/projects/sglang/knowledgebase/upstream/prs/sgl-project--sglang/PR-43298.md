# [Scheduler] Requeue preempted requests when admission admits nothing

[Upstream PR](https://github.com/sgl-project/sglang/pull/43298) · state: closed · merged: True

## Original PR description

## Motivation

With priority scheduling and preemption on, admission can preempt running requests to make room for a higher-priority waiting request, then fail to admit that request (it no longer fits the prefill budget, the prefill delayer holds it, or its storage prefetch is still running). `PrefillAdder.preempt_to_schedule` has already released the preempted requests and removed them from the running batch, but the no-admit early return in `_get_new_batch_prefill_raw` only requeued them on the admitting path. They end up in no queue: they never finish and their clients never get a response.

## Modifications

- On the no-admit return, requeue `adder.preempt_list` with `_add_request_to_queue`, as the admitting path already does.
- `test/registered/scheduler/test_priority_scheduling.py`: the request ordering, abortion and rejection tests sent all requests at once and assumed the first one reached the scheduler first. When they arrived in the same receive pass, admission took the highest priority and aborted the intended holder. They now send the holder first and each later group in its own wave (`_send_in_waves`), and compare finish times (send offset + e2e latency).

## Checks

- End to end, Qwen3-0.6B on one H200, `--enable-priority-scheduling --enable-prefill-delayer --max-running-requests 4`. Each round fills the running batch with four low-priority (`priority=0`) 2500-token requests, then sends one high-priority (`priority=100`) request 1.5 s later. Admission preempts a low-priority request, and the prefill delayer then rejects the pass because fewer slots are free than the recent prefill batch size, so nothing is admitted:

| branch | server | rounds | requests returned (reqs) |
|---|---|---|---|
| main | reused | 3 | 15 / 18, one preempted request lost per round |
| main | fresh | 3 | 16 / 18 (the delayer skips its first delay once per server) |
| this PR | fresh, two runs | 6 | 36 / 36 |

  - On `main`, the lost requests time out on the client after 90 s while `/health` and new requests keep succeeding.
- `test_priority_scheduling.py` on 1-gpu-5090: 5 / 5 runs pass with the wave sends; 0 / 5 passed before them.
