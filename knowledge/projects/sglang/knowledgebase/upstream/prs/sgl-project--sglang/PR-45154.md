# [Feat] glm-5.3: Render GLM-5.3 and GLM-5.3-Flash chat prompts with a Python chat template

[Upstream PR](https://github.com/sgl-project/sglang/pull/45154) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.3 and GLM-5.3-Flash ship a `chat_template.jinja` that is costly to evaluate: tool results are matched to `tool_calls` by id with list rebuilding and sorting in Jinja, and every content part goes through macro calls. This PR renders both models' prompts with a Python port of the same template (adapted from the GLM team's reference implementation). It produces byte-identical prompts and renders 4.7-17x faster.

## Modifications

- **`parser/glm53_chat_template.py`**: one renderer for both models. GLM-5.3-Flash differs only in its multimodal block (image/video/audio parts emit `<|begin_of_image|><|image|><|end_of_image|>`-style tokens where GLM-5.3 emits a text-only reminder) and in stringifying non-string tool-call names (`~` instead of `+`). Malformed input fails where the template fails (`ValueError` for Jinja's `UndefinedError`, the same `TypeError`), so the API still answers 400.
- **`parser/python_chat_template.py`**: `PythonChatTemplate` declares the features sglang otherwise derives from the Jinja source (content format, always-on reasoning, tool-result reordering, inline system messages, `glm45` / `glm47` parsers) and installs the renderer as the serving tokenizer's `apply_chat_template` with transformers' calling convention, so the request pipeline (content normalization, tool-result canonicalization, `continue_final_message`, the render cache) is unchanged.
- **Selection** (`TemplateManager`):
  - By default, the Python template replaces the checkpoint's when the architecture is `GlmMoeDsaForCausalLM` / `Glm5NextForConditionalGeneration` and the checkpoint template is a GLM-5.3 one whose multimodal block matches the architecture. GLM-5 / 5.1 / 5.2 share the architecture but not the template, so they keep Jinja.
  - `--chat-template glm-5.3` / `--chat-template glm-5.3-flash` forces it and needs no Jinja template.
  - `--chat-template <checkpoint>/chat_template.jinja` keeps the Jinja path exactly as before.
- **Auto parsers**: `--reasoning-parser auto` / `--tool-call-parser auto` resolve to the template's declared parsers when the Python template renders the prompts, as for the other non-Jinja encoders (DeepSeek-V4, Kimi-K3). A built-in template name resolves them without loading the tokenizer.

## Accuracy Tests

- **Differential fuzzing** against both checkpoints' `chat_template.jinja`, compiled the way transformers compiles it: ~490k randomized conversations (tools, parallel tool calls with out-of-order / duplicate / missing ids, `tool_reference`, reasoning history, `clear_thinking`, `reasoning_effort`, media parts, malformed messages). Every successful render is identical, and every failure fails on both sides with an error the API answers with 400 (never a 500).
- **Serving level**: `OpenAIServingChat._process_messages` with the real tokenizers gives identical prompts, prompt ids, media data and stops for 23 requests per model, on the default path, with `--chat-template glm-5.3[-flash]` and no Jinja template in the checkpoint, and with `--chat-template <jinja path>`.
- **Online A/B** (this branch vs. `main`, greedy decoding; GLM-5.3-Flash TP4 and GLM-5.3 TP8 on B200 with EAGLE MTP): identical `prompt_token_ids` and outputs for chat, `reasoning_effort`, multi-turn reasoning, `clear_thinking`, tools (`auto` / `required` / named / `none`), out-of-order tool results, inline system messages, `continue_final_message`, images, video, streaming, `/v1/responses` and `/v1/messages`, also with `--reasoning-parser auto --tool-call-parser auto`.
- **Unit tests**: `test/registered/unit/parser/test_glm53_chat_template.py`. Set `SGLANG_TEST_GLM53_CHECKPOINT` / `SGLANG_TEST_GLM53_FLASH_CHECKPOINT` to a model directory to also compare against its Jinja template.

## Speed Tests and Profiling

Median latency with the GLM-5.3 tokenizer, prompts under 32,768 characters (below `SGLANG_PARALLEL_PROMPT_ENCODE_MIN_CHARS`, so the prompt is encoded with a single tokenizer call). Both implementations produce identical prompts and token ids in every row.

| Scenario | Prompt chars / tokens | Render, ms | Render + encode, ms | Request preprocessing, ms |
|---|---|---|---|---|
| chat, 1 turn | 115 / 21 | 0.029 → 0.003 (9.1x) | 0.072 → 0.034 (2.1x) | 0.111 → 0.072 (1.5x) |
| chat, 20 turns with reasoning | 25,084 / 4,745 | 0.341 → 0.034 (10.1x) | 7.95 → 7.57 (1.05x) | 8.41 → 8.05 (1.04x) |
| 8 tools, 1 turn | 2,532 / 662 | 0.178 → 0.038 (4.7x) | 1.12 → 0.88 (1.3x) | 1.55 → 1.29 (1.2x) |
| agent: 8 tools, 18 tool-call rounds | 28,675 / 5,385 | 2.92 → 0.17 (17.1x) | 12.13 → 9.24 (1.3x) | 13.27 → 10.42 (1.3x) |
| agent: 8 tools, 8 rounds × 3 parallel calls | 31,556 / 5,921 | 2.60 → 0.16 (16.0x) | 12.54 → 9.94 (1.3x) | 13.71 → 11.14 (1.2x) |
| GLM-5.3-Flash, 8 images | 505 / 72 | 0.056 → 0.009 (6.3x) | 0.162 → 0.098 (1.7x) | 0.387 → 0.306 (1.3x) |

Longer prompts are encoded by `parallel_prompt_encode`, which takes the rendered string, so it applies to both implementations unchanged and saves the same encode time on both paths. Rendering then becomes the dominant remaining cost, and the Python template's gain in request preprocessing grows to 2.3x (GLM-5.3, identical token ids):

| Scenario | Prompt chars / tokens | Single-call encode (`SGLANG_PARALLEL_PROMPT_ENCODE=0`), ms | Parallel encode (default), ms |
|---|---|---|---|
| agent: 8 tools, 50 tool-call rounds | 73,404 / 13,449 | 32.20 → 25.16 (1.28x) | 12.72 → 5.45 (2.33x) |
| agent: 8 tools, 200 rounds × 3 parallel calls | 705,303 / 127,661 | 270.90 → 214.22 (1.26x) | 98.63 → 42.33 (2.33x) |

Together with parallel encode, request preprocessing for these prompts is 5.9x / 6.4x faster than Jinja with a single-call encode.

- Render is `tokenizer.apply_chat_template(..., tokenize=False)`, what sglang calls; render + encode adds `tokenizer.encode(add_special_tokens=False)`; request preprocessing is the whole `OpenAIServingChat._process_messages` (message normalization, render, encode), with the render cache cleared each iteration.
- GLM-5.3-Flash renders at the same speed; its request preprocessing also decodes the prompt for the multimodal processor, which adds up to ~1.9 ms on both sides.
- Rendering runs in Python under the GIL in the tokenizer manager (the Rust tokenizer releases it while encoding), so the saved render time also stops contending with other requests' processing.
- Environment: Intel Xeon 6960P, Python 3.12.15, transformers 5.19.0, jinja2 3.1.6, tokenizers 0.23.2.
