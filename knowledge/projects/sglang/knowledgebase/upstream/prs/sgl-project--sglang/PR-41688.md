# [diffusion] perf: row-shard MiniMax-H3's TP=2 residual behind DeepGEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/41688) · state: open · merged: False

## Original PR description

## Motivation

At TP=2, each MiniMax-H3 DiT block does two bf16 all-reduces: one after `attn.out_proj` and one after `mlp.fc2`. Nothing overlaps them. On two RTX 5090s over PCIe they are a large share of a block's non-attention time.

Everything between a row-parallel GEMM's reduction and the next column-parallel GEMM works one row at a time: the gated residual, RMSNorm, the AdaLN scale/shift and the block-FP8 quantization of the next GEMM's input. So each rank can do the following instead of the all-reduce:

1. reduce-scatter and keep only its half of the residual rows;
2. run that row-local stretch on half the rows;
3. all-gather the next GEMM's **already-quantized** input, i.e. FP8 rows plus packed UE8M0 scales. That is about half the bytes of the bf16 rows an all-reduce returns.

The rows are also cut into up to 4 chunks, so each chunk's collective runs on a side stream underneath the next chunk's GEMM.

The result is **bit-exact** against the all-reduce path.

## Modifications

**`minimax_h3_row_shard.py` (new)**
- Row bookkeeping: `shard_rows` / `unshard_rows`. A rank holds its half of every chunk, back to back.
- `CommLane`: one side stream for the collectives. Every buffer is allocated on the compute stream and none is recorded on the side stream, so the caching allocator never sees a tensor on two streams.
- `row_chunks`: decides whether the path is eligible and how many chunks to use.
- `gemms_beside_collectives`: sets `configure_deep_gemm_num_sms(num_sms - NCCL_MIN_NCHANNELS)`. DeepGEMM is persistent, so without this its CTAs on the SMs NCCL holds would wait for NCCL. The count changes which SM computes a tile, not what the tile holds.

**`minimax_h3.py`**
- `MiniMaxH3DiTBlock.forward(..., row_chunks=0)` dispatches to `_forward_row_sharded`. It chains chunked gathers, the QKV GEMM into rows of one buffer, attention on the full rows, a chunked reduce-scatter of `out_proj`'s partial sums, the gated residual, gather, fc1 → SiLU → fc2, and reduce-scatter.
- `MiniMaxH3Attention.forward` is split into `_split_qkv` + `attend` so the row-sharded path can reuse the attention body.
- `MiniMaxH3DiTModel.forward` shards the hidden rows before the block loop and unshards them after it, before the spectrum record.

**Kernel: `diffusion.indexed_scale_shift_block_fp8` (new, Triton, `kernels/ops/diffusion/quantization/block_fp8_triton.py`)**
- Fuses the indexed AdaLN modulation (`indexed_scale_shift_bf16_`) with `sglang_per_token_group_quant_fp8(..., scale_ue8m0=True)`, bit for bit.
- Its scales are row-major `[rows, ceil(groups/4)]` int32 rather than MN-major, so gathering rows also gathers their scales.

**`fp8_utils.deepgemm_w8a8_block_fp8_linear_with_fallback`**
- Accepts a pre-quantized input with packed UE8M0 int32 scales, row-major or already MN-major, via a new `deepgemm_ue8m0_mn_major`.
- Takes an `out=` buffer, so each chunk's GEMM writes straight into its rows.
- The assert that `weight_scale` is int32 on this pre-quantized branch is removed, so fp32 power-of-two weight scales are accepted too. DeepGEMM checks the pow2 requirement itself.
- Existing callers are unchanged: `out` defaults to `None`, and the pre-quantized fp32 path (`SGLANG_OPT_MOE_QUANT_ONCE`) is untouched.

**`GroupCoordinator` (multimodal)**
- Adds `reduce_scatter(input_, output=None)` and `all_gather_into(output, input_)`.

**When the path is taken.** Anything else keeps the existing all-reduce path. All of these must hold:
- `tp_size == 2`, with no SP (Ulysses/Ring).
- CUDA, eager: not under `torch.compile`, not during stream capture, no cache-dit.
- Every block is a plain `MiniMaxH3DiTBlock`: no VDN hybrid attention, no `to_gate_compress`.
- `qkv_proj` / `fc1` are bias-free `ColumnParallelLinear` layers with block-FP8 `[128,128]`, no Marlin, and a runner of DeepGEMM with `DEEPGEMM_SCALE_UE8M0`. LoRA-wrapped layers are not a `ColumnParallelLinear`, so they fall back.
- `out_proj` / `fc2` are plain bias-free `RowParallelLinear` layers.
- Eligibility reads `output_size_per_partition` / `input_size_per_partition`, not `weight.shape`, because under layerwise offload a layer that is not resident holds a placeholder weight.

**Why only TP=2.** At TP=2, a reduce-scatter and an all-reduce both sum each element once (a + b), so the result is the same. With more ranks, NCCL chooses the summation order, and it can differ between the two collectives.

## Accuracy Tests

The path is bit-exact by construction and tested on bits, not with a tolerance.

- `test/registered/kernels/ops/diffusion/test_block_fp8_triton.py`: the fused kernel against `indexed_scale_shift_bf16_` + `sglang_per_token_group_quant_fp8(scale_ue8m0=True)`. Cases are normal, heavy-tailed, zero/tiny (the 1e-10 floor) and ±inf. It checks fp8 bytes and scale words with `torch.equal`, that the input is not modified, and that inputs the unfused path would not fuse are refused.
- `python/sglang/multimodal_gen/test/unit/test_minimax_h3_row_shard.py`:
  - CPU: shard/unshard ordering, chunk selection, and ineligible layers falling back.
  - Two SM120 GPUs: a block-FP8 DiT block at TP=2 with per-rank weight shards. Row-sharded with chunks 1/2/4 under `gemms_beside_collectives`, compared with `torch.equal` against the all-reduce block. The test also checks that an offload placeholder weight does not change eligibility.
- End to end, H3 FL2VA (config below): all 4 videos per attention backend are byte-identical, 2 runs before and 2 after.

  - sage_attn: `a7bf39928542db1e…`

## Speed Tests and Profiling

2× RTX 5090 (PCIe), sgl-deep-gemm 0.2.0, DeepGEMM runner, `NCCL_MIN_NCHANNELS` default (8).

**Block microbenchmark, no attention**: GEMMs plus communication plus row-local ops only. H3 dims, 112,000 rows, block-FP8, median of 10:

| | all-reduce (main) | row-sharded | saved |
|---|---|---|---|
| per block | 144.5 ms | 106.9 ms | −37.6 ms (−26.0%) |
| per step (50 blocks, incl. shard/unshard) | 7.23 s | 5.36 s | −1.86 s (−25.8%) |

**End to end**: H3 FL2VA, first frame at 1344×768, 362 frames, 8 steps, seed 0, `--tp-size 2 --ulysses-degree 1 --performance-mode memory --layerwise-offload-components dit,text_encoder --dit-offload-prefetch-size 1 --dit-layerwise-resident-layers 0 --enable-torch-compile false`. DiT: FP8 FL2VA transformer; text encoder: bf16 Qwen3-VL-32B. One discarded warm-up request, then two measured runs per build; the numbers are the mean of the two runs.

**Request E2E**: client-side wall time for the generation request.

| attention | metric | main | this PR | saved |
|---|---|---|---|---|
| sage_attn | Request E2E | 188.7 s | 178.8 s | −9.9 s (−5.2%) |
| SDPA | Request E2E | 370.9 s | 359.8 s | −11.2 s (−3.0%) |

Steady-state denoise step, the mean of timed steps 2–7:

| attention | main | this PR | saved |
|---|---|---|---|
| sage_attn | 23.72 s | 22.32 s | −1.40 s (−5.9%) |
| SDPA | 49.73 s | 48.21 s | −1.52 s (−3.1%) |

The saving per step is about the same with either attention backend, because only the GEMM/communication stretch changes. Peak memory is essentially unchanged.

**Not verified here:** SM100 (B200), where DeepGEMM also scales in UE8M0 and the kernel test's CI runner lives. All numbers above are from SM120.
