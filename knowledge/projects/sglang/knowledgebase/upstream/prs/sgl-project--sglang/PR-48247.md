# [Fix] http_server: skip the sglang launcher re-import in spawned uvicorn workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/48247) · state: open · merged: False

## Original PR description

## Motivation

With `--tokenizer-worker-num > 1`, uvicorn starts the HTTP/tokenizer workers with the `spawn` start method. Before a spawned worker unpickles its target, `multiprocessing` re-runs the parent's main module in it. For `python -m sglang.launch_server` that main module imports `sglang.srt.server_args`, `sglang.srt.utils` and therefore torch and transformers. All of this runs before uvicorn's health-check (ping) thread exists in the worker.

On a CPU-oversubscribed host this import takes longer than `SGLANG_UVICORN_WORKER_HEALTHCHECK_TIMEOUT` (10 s). The supervisor then kills the worker as unresponsive and spawns a new one, which pays the same import again.

Re-import time of `sglang.launch_server` as `__mp_main__` (what each spawned worker runs before it can answer a ping). Fresh interpreter, 16 CPUs (`taskset`) of an AMD Threadripper PRO 7965WX, N busy-loop processes on the same CPUs, median of 3:

| busy loops on 16 CPUs | 0 | 24 | 48 | 96 |
|---|---|---|---|---|
| `python -m sglang.launch_server` main re-import | 2.19 s | 6.78 s | 8.82 s | **18.99 s** |
| with this PR (uvicorn imports only) | — | — | 0.19 s | — |

**Scope of the problem on current main.** It needs heavy CPU oversubscription and the `python -m sglang.launch_server` entrypoint:
- At 3x oversubscription (48 busy loops on 16 CPUs) the re-import stays just under the 10 s timeout, and no worker is killed.
- At 6x (96 busy loops) it takes 19 s, and workers are killed on start-up and on respawn (see below).
- The `sglang serve` console script re-runs only `sglang.cli.main` (0.83 s at 48 busy loops), so the recommended entrypoint is much less exposed.

The fix is still worth having: `python -m sglang.launch_server` is supported and widely used in scripts and tests. With the fix, a worker answers health checks after only the uvicorn imports (0.19 s), however slow the launcher module is. It covers sglang's own launchers only; a user's launcher script is still re-run in every worker, as on main.

**Related: #47838** (open) addresses the same kill-and-respawn loop from another cause: under `CUDA_MODULE_LOADING=EAGER`, the CUDA init during the worker's `import sglang` outlasts the health check. That `import sglang` still happens with this PR, because the worker imports the app module, so the two fixes are complementary and neither covers the other. They edit different hunks of `http_server.py`, and this branch merges cleanly with #47838's head.

## Modifications

- `python/sglang/srt/entrypoints/uvicorn_worker_spawn.py`: `skip_main_reimport_in_spawned_workers()` is a context manager. When the server was started by sglang's own entrypoint (`python -m sglang.launch_server`, or the `sglang` console script), it drops `init_main_from_name` / `init_main_from_path` from `multiprocessing.spawn.get_preparation_data()` while it is active. A uvicorn worker unpickles only uvicorn objects and imports the app from an import string (`SGLANG_HTTP_SERVER_APP_PATH`), so it needs nothing from `__main__`. The original function is restored on exit.
- A user's own launcher script (e.g. `if __name__ == "__main__": launch_server(...)` after module-level model registration or patches) is still re-run in every worker, exactly as on main.
- `http_server.py`: the multi-worker uvicorn supervisor (`uvicorn.run` and the `--enable-http-worker-reuseport` supervisor) runs inside that context. Health-check timeouts are unchanged, so a frozen live worker is still killed.
- `init_multi_tokenizer()` calls `suppress_noisy_warnings()`. Workers no longer run the launcher module that applied these warning filters at import.
- The single-tokenizer path and the Granian HTTP/2 path are unchanged.

## Accuracy Tests

No model-output change. Exactness gate: same GPU, same image, `--enable-deterministic-inference --tokenizer-worker-num 2`, Qwen/Qwen2.5-0.5B-Instruct, 4 greedy prompts x2 plus a batch of 4 through the HTTP workers. Generated text is byte-identical between main (`8d4e1ce4c7`) and this PR.

## Speed Tests and Profiling

No steady-state serving change: this only affects how workers are spawned. Worker respawn under CPU saturation, CPU only:
- A uvicorn supervisor with 2 workers, started from a module that imports `sglang.launch_server` at top level, as the real launcher does.
- Each worker app imports `sglang.srt.entrypoints.http_server`.
- `timeout_worker_healthcheck=10`, 16 CPUs.
- Once both workers serve, one is SIGKILLed. Run length 180 s.

3 runs per arm, 96 busy loops / 16 CPUs, same machine. The "main" arm runs upstream main (`8d4e1ce4c7`). The "this PR" arm runs this branch; its harness marks itself as the sglang launcher, since it stands in for `python -m sglang.launch_server`.

| arm | health-check kills per run | respawn after the injected kill serves after (s) |
|---|---|---|
| main | 4, 10, 7 | 48.8, never, never |
| this PR | 0, 0, 0 | 53.4, 47.5, 36.4 |

- Not counted above: each run also has 1 injected SIGKILL.
- "never": the respawned worker was still being killed by the health check when the 180 s run ended.
- Times are host-specific. On a second host (16 CPUs of an 8x H100 server node, same busy loops) the re-import took longer: 30.5 s at 96 busy loops. There, main also had repeated health-check kills, and the PR had none.

At 48 busy loops, main was not killed by the health check: the re-import (8.8 s) stays just under the 10 s timeout.
