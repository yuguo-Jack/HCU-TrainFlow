# [Feat] openai: Render DeepSeek-V4/V4.1 chat prompts with deepseek-recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/45315) · state: closed · merged: True

## Original PR description

DeepSeek-V4 and V4.1 chat prompts are rendered and tokenized by [deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe) 0.2.0, DeepSeek's official encoder library, through the `dsv4` / `dsv41` chat encoding adapter. SGLang's copies of the checkpoint encoders (`encoding_dsv4.py`, `encoding_dsv41.py`) are removed.

## Changes

- `parser/deepseek_recipe_renderer.py`: translates the request for recipe (`developer` -> `system`, object tool-call arguments -> JSON, `continue_final_message` -> `prefix`, `required` and named `tool_choice` -> `auto` because SGLang's grammar enforces the choice, `structural_tag` left to the grammar), then renders and tokenizes with the served checkpoint's fast tokenizer. It adds the two SGLang extensions recipe does not model: quick instruction `task`s and V4.1 numeric effort budgets.
- `serving_deepseek_recipe.py`: the adapter. Only the prompt goes through recipe; thinking, `reasoning_effort`, sampling (`n`, `temperature`, `top_p`, `max_tokens`) and the trailing-assistant rule of `_handle_last_assistant_message` follow SGLang's request handling. An unset effort falls back to `SGLANG_DSV4_REASONING_EFFORT` / `SGLANG_DSV41_REASONING_EFFORT`, then to recipe's default. A bad default effort fails at startup.
- Adapter protocol: `encode_messages` takes the handler's `thinking` decision, and adapters declare `strict_tool_call_arguments`.
- Output parsing is unchanged: the DeepSeek reasoning and tool-call parsers still parse model output.
- `encode_simple_chat` (offline tools) renders DeepSeek-V4 / V4.1 through recipe as well.
- `deepseek-recipe==0.2.0` is a dependency in every `pyproject*.toml` (wheels for Linux x86_64 / aarch64 and macOS).

## Behavior changes

DeepSeek-V4 / V4.1 prompts follow deepseek-recipe wherever the removed encoders differed:

- Reasoning effort
  - V4 follows DeepSeek's official effort profile. The preview profile and its `dsv4_reasoning_effort_profile` override are gone, so `high` and `max` render the official prompts on every checkpoint.
  - V4 `medium`, `xhigh` and `ultra` map to recipe's tiers instead of being ignored.
  - With thinking on, an unset or `none` effort renders recipe's default effort prompt on V4, where nothing was rendered before.
  - A numeric `reasoning_effort` (integer or float) on V4 returns 400 instead of being ignored.
  - V4.1 `minimal` maps to `low` (budget 50) instead of falling back to the default budget 75.
- Tools
  - V4 tool schemas render in OpenAI field order, without the `strict` default.
  - A tool without a description renders `"description": ""` (V4 rendered `null`, V4.1 omitted the field).
  - A named `tool_choice` renders only the chosen tool, as SGLang does for other models.
  - History tool calls with non-object `arguments` are accepted instead of returning 400.
  - A `tool` message that answers no preceding tool call returns 400.
- Messages
  - `developer` messages render as system messages instead of user turns.
  - A mid-conversation system message on V4 moves to the start of the prompt instead of rendering in place.
  - A trailing `latest_reminder` renders before the generation header.
  - V4 joins multiple text parts with a blank line instead of a space, and renders an image part as `[Unsupported Image]` instead of dropping it.
  - Special-token strings in message text are encoded as plain text. V4 used to turn them into special tokens; V4.1 rejected the image token.
  - `continue_final_message` in thinking mode continues the answer after `<think></think>` instead of inside the reasoning block.
- Response format: `json_object` and `json_schema` requests get the official response-format instruction in the prompt.

Other models:

- `reasoning_effort` accepts `ultra` for every model. Models whose encoders do not map it keep their own handling: gpt-oss falls back to its default effort, and Inkling and Hunyuan reject it.
- Assistant messages accept `prefix`, which used to be dropped. Chat templates that read it (such as the DeepSeek-V3.1 / V3.2 tool templates under `examples/chat_template/`) now see it.

The Rust processor (`rust/sglang-processor`) still renders DeepSeek with its own encoder, and its parity fixtures are unchanged.

## Tests

- `test/registered/unit/parser/test_deepseek_recipe_renderer.py`: request translation, numeric effort budgets, every task with thinking on and off (token ids), and the effort-line rewrite.
- `test/registered/unit/entrypoints/openai/test_serving_deepseek_recipe.py`: adapter construction and startup checks; through the chat handler, the thinking default, request effort over the server default, `temperature` and `max_tokens` left to SGLang, numeric effort and `task` reaching the prompt, and the trailing-assistant rules.
- `test/registered/unit/function_call/test_deepseekv41_detector.py` renders its fixtures with deepseek-recipe.
