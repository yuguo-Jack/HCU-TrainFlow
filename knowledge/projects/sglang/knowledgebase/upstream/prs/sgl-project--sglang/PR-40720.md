# [Fix] [XPU] weight_sync: stage serialized XPU tensors through host shared memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/40720) · state: open · merged: False

## Original PR description

## Motivation

`Engine.update_weights_from_tensor()` crashes on Intel XPU, so online RL training (GRPO/RLHF through verl and similar trainers) cannot push weights into a colocated engine after each `optimizer.step()`. Inference is unaffected.

PyTorch has no XPU tensor IPC: `UntypedStorage` has `_share_cuda_` but no `_share_xpu_`, and `torch.multiprocessing.reductions.reduce_tensor` has only CUDA and meta branches ([intel/torch-xpu-ops#1678](https://github.com/intel/torch-xpu-ops/issues/1678)). An XPU tensor falls through to the CPU storage path:

```
File "torch/multiprocessing/reductions.py", in reduce_storage
    fd, size = storage._share_fd_cpu_()
RuntimeError: _share_fd_: only available on CPU
```

Under Ray it fails instead with `AuthenticationError: digest received was wrong`, because fd passing needs an authkey that a trainer actor and an `mp.spawn`-ed scheduler never share.

## Modifications

**Transport** (`python/sglang/srt/utils/xpu_tensor_shm.py`). Each serialized XPU tensor is staged through a POSIX shared-memory segment. The producer copies device → host, the payload carries only the segment name (174 B regardless of tensor size), and each scheduler copies host → its own device. There is no fd passing, so no authkey dependency. `posix_fallocate` turns an exhausted `/dev/shm` into `ENOSPC` instead of `SIGBUS`.

**Segment lifetime** follows who can observe the readers. Each scheduler reads `payload[tp_rank]`, so a payload has one reader per pipeline stage (DP replicas are already rejected for this API, `tokenizer_control_mixin.py:565`). Stage 0's TP0 replies only after its TP group has loaded: `SchedulerWeightUpdaterManager.update_weights_from_tensor` ends on a TP barrier. Stage *k*, however, reads only after stage *k*−1 has finished and relayed the request (`event_loop_pp` processes, then relays). So later stages load after the call has returned.

| Producer | Who unlinks | Host copies per call |
|---|---|---|
| `Engine.update_weights_from_tensor`, `load_lora_adapter_from_tensors`, `HttpServerEngineAdapter`, PP = 1 | the producer, on return (`staged_xpu_segments(pp_size=1)`) | **1** (a tensor serialized once per TP rank is staged once) |
| the same, PP > 1 | the reader on the last pipeline stage | `tp_size` |
| hand-off producers that return before the request does (`weight_sync.utils.update_weights` on its non-root ranks) | the reader on the last pipeline stage | one per rank |

**Security.** `_rebuild_xpu_tensor_from_shm` is allowlisted in `SafeUnpickler.ALLOWED_GLOBALS`, and it accepts only the segment-name shape `make_shm_name("xputensor")` produces. The name arrives in the pickle that `POST /update_weights_from_tensor` takes. That route is `ADMIN_OPTIONAL`, so it's unauthenticated by default, and an unchecked name would read and unlink any `/dev/shm` segment the scheduler's uid owns. That is the channel `SafeUnpickler` was narrowed for in CVE-2025-10164.

**Patch installation.** `monkey_patch_xpu_tensor_reductions()` is installed at engine startup (`_set_envs_and_config`) and on scope entry. The new call sites install only that patch, not `monkey_patch_torch_reductions()`, so CUDA producers' payloads are unchanged.

**`_reduce_tensor_modified` fix** (`patch_torch.py`). It rewrote argument index 6 into a device UUID on every reduction, but only the CUDA-IPC payload carries a device there. A CPU tensor reduces to 3 arguments and died with `IndexError`. A meta tensor reduces to 7, where index 6 is `requires_grad`, so the UUID was written over it. The rewrite is now keyed off the rebuild function.

**Docs.** `docs/docs/hardware-platforms/xpu.mdx` gains an RL weight-sync section covering `/dev/shm` sizing, cost, what callers that serialize their own payloads must do, and how to clear a leak.

### Notes for review

- A review asked that the synchronous producers own the unlink so `--pp-size 2` works. That alone is not safe: the call returns when stage 0 replies, and with the producer unlinking on return, stage 1 found its segment gone and crashed the server. It reproduced deterministically on hardware. A barrier inside the handler can't fix it either, because stage 0 relays the request only after its handler returns. PP > 1 therefore uses the last-stage rule, which is sound for the ordering reason above.
- The same review also found that rejected requests leaked their staging, and that a process-wide registry could unlink a bucket the caller had pre-serialized for its next call. Both are fixed by the per-call scope.
- **Behavior on other platforms:** no change on CUDA, ROCm or NPU. The new install calls and `staged_xpu_segments` are no-ops off XPU. The only shared-path change is the `_reduce_tensor_modified` short-circuit for non-CUDA-IPC payloads. Those payloads previously crashed (CPU) or were corrupted (meta), and the CUDA-IPC rewrite itself is untouched; the existing 2-GPU CUDA case in `test_patch_torch.py` still covers it.

### Known limitations

- Producer and consumer must be on the same node, as with CUDA IPC.
- With PP > 1, a request rejected before loading (outside a weight-update session) leaves its staging, since no stage reads it. For hand-off producers, a crash between staging and loading does the same. Both are documented, with `rm /dev/shm/sgl_shm_xputensor_*` as the remedy.

## Accuracy Tests

Not applicable: this is a transport-only change. Weights arrive bit-exact; the unit tests compare raw bytes across bf16, fp8, int64, 0-d, empty and transposed tensors.

## Speed Tests and Profiling

Measured on Arc Pro B60, torch 2.14.0.dev+xpu:

- Staging runs at ~1 GiB/s device → host and ~2.2 GiB/s host → device (256 and 512 MiB tensors). A pinned intermediate buffer was not consistently faster and doubles host memory, so the copy goes straight into the segment.
- `update_weights_from_tensor` for one 32 MiB `up_proj` on Llama-3.2-1B takes 0.041–0.060 s at TP=1, TP=2 and PP=2.
- At PP=1, a call stages one host copy per tensor instead of `tp_size`.

## Tests

`test/registered/utils/test_xpu_tensor_shm.py` (registered for `stage-b-test-1-gpu-xpu`) guards one failure mode per case:
- round trip is bit-exact (dtype, shape, contiguity, `Parameter`);
- a payload survives an unrelated producer process exiting, with no shared authkey;
- foreign segment names are refused, and the segment survives;
- one segment serves every TP rank's reader;
- **PP > 1: only the last stage unlinks**;
- the scope reclaims payloads nobody read;
- the scope leaves pre-serialized payloads alone;
- a tensor written in place between serializations is restaged rather than served stale.

`test/registered/rl/test_patch_torch.py` adds CPU and meta tensors through the patched reducer, including `requires_grad=True` leaves.

End-to-end on 8× Arc Pro B60, inside a `begin_weight_update()` / `end_weight_update()` session:

| Config | Model | Result |
|---|---|---|
| TP=1 | Llama-3.2-1B-Instruct | `(True, 'Success')`, readback 1.5, generation OK, 0 segments left |
| TP=2 | Llama-3.2-1B-Instruct | same |
| PP=2 | Llama-3.1-8B-Instruct | `(True, 'Success')`. Zeroing `layers.31.down_proj`, which lives on stage 1, changes greedy output, so stage 1 loaded it; 0 segments left |
| no session | Llama-3.2-1B-Instruct, TP=1 | rejected before deserializing, 0 segments left |

The previous head of this PR, on the PP=2 case, returned `(True, 'Success')` and then crashed stage 1 with `Shared-memory segment ... is gone`.

PP=2 on Llama-3.2-1B crashes during generation with `'PPMissingLayer' object has no attribute 'quant_method'`. That also happens on unmodified `main` with no weight update: tied embeddings put `lm_head` on stage 0. It is unrelated to this PR, which is why the PP=2 row uses the 8B model.
