# [Feat] sgl-router: Route prefill buckets by uncached tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/45103) · state: open · merged: False

## Original PR description

## Motivation

Prefill buckets match a request on its input length. In agentic workloads most of a long context is usually cached: a 130k-token turn may need only a few hundred new tokens of prefill, yet it lands in the long-prompt bucket, while cache-aware candidates ignore bucket ranges altogether.

## Modifications

`--route-by-uncached-tokens` (with `--policy cache_aware` and `--bucket-config`), off by default:

1. Warm requests: match prefill buckets on E, the input beyond the longest prefix any prefill worker can reuse according to the KV indexer. The request uses the buckets that hold E, and cache candidates outside them are dropped.
2. Cold requests (nothing reusable, or no answer from the indexer) are not matched to a bucket: the existing load-based selection picks among all prefill workers. This avoids stalling the warmup of an agentic benchmark, where every session's first turn is a long uncached prompt: matched on input length, all of them would queue on the long-prompt bucket while the other workers sit idle.
3. Idle spill: when every DP rank of every worker in E's buckets has pending prefill work, send a warm request to another worker with an idle DP rank. A rank's pending work is its queued requests plus the uncached tokens it still has to prefill, so a rank chunking a long prompt (empty queue) is not idle.

## Speed Tests and Profiling

DeepSeek-V4-Pro (FP4), MI355X, agentic coding traces, 192 concurrent sessions, 1 prefill node + 1 decode node (TP8/DP8 attention), shared UMBP host pool, same code and nodes for both rows:

| Prefill node | tok/s/GPU | TTFT p50 / p90 / p95 (s) | P90 interactivity |
|---|---|---|---|
| one TP8/EP8 DP-attention worker | 47,646 | 4.17 / 12.02 / 18.46 | 74.7 |
| TP4 worker (E > 8192) + DP4-attention worker (E ≤ 8192), this PR | 50,778 | 3.80 / 9.89 / 15.02 | 71.4 |

Interactivity is lower for two reasons. With faster prefill, more sessions are decoding at once (decode step time +1.8%), which accounts for about 40% of the gap. Both runs also use `--pd-stream-after-prefill` (https://github.com/sgl-project/sglang/pull/45102), which counts decode output produced before the prefill request completes in TTFT instead of ITL; requests prefilled on the less loaded TP4 worker reach the client sooner, so less decode time lands in TTFT (0.69 s vs. 0.87 s per request on average), which accounts for about 55%.
