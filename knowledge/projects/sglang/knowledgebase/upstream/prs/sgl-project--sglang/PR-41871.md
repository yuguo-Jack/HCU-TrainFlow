# [AMD][gfx95] GLM-5.3-Flash MXFP4 MoE decode: small-M kernel and sort-fused FP4 quant

[Upstream PR](https://github.com/sgl-project/sglang/pull/41871) · state: open · merged: False

## Original PR description

## Summary

At small decode batches, the routed experts of a GLM-5.3-Flash MXFP4 MoE layer take **five** kernels. A sort groups tokens by expert, and each of the two expert GEMMs needs an FP4 quant first. The sort and the two quants cost half as much as the GEMMs. Both changes are on by default:

1. SGLang already has a gfx950 small-batch MoE kernel. It reads BF16 activations directly, so it needs no sort and no quant. GLM-5.3-Flash now uses it.
2. For somewhat larger batches, the sort also writes the first FP4 quant, bit-exact with aiter. This removes one quant kernel.

| Routed MoE, decode batch 4 | baseline (µs) | this PR (µs) |
| --- | --- | --- |
| sort | 4.40 `_moe_sorting_small_kernel` | — |
| stage-1 + stage-2 FP4 quant | 3.88 + 3.88 `fused_mx_quant_moe_sort_kernel` | — |
| gate/up + SiLU | 15.38 moe1 | 14.78 `smallm_p1_i512_c16` |
| down | 7.98 moe2 | 10.26 `smallm_p2_i512_s8` |
| **per layer (×42)** | **5 kernels, 35.52** | **2 kernels, 25.04** |

## Scope

gfx950 MXFP4 MoE on the aiter runner, decode only. CUDA and other AMD GPUs do not change. The small-batch kernel adds one shape: per-GPU intermediate 512 with 8 or 9 top-k slots (top-8, plus the fused shared expert), up to decode batch 16. Larger batches and other shapes stay on aiter. The sort change needs batch × top-k ≤ 256 and a hidden size divisible by 2048: batch 17 to 28 with 9 slots, 17 to 32 with 8. It covers any MXFP4 MoE with SiLU or GELU and separate gate/up. `SGLANG_ROCM_SMALLM_MOE=0` still turns off the small-batch kernel.

- Raiden-Makoto · comment · 2026-10-06T16:09:34Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4197690378)

`_workspace()` caches `hbuf`, `acc`, and `cnt` by `(device, slots, inter)`, but these are mutable buffers shared by the two asynchronous kernel launches. Two forwards on different streams or graph instances can have one phase-1 overwrite `hbuf` while the other phase-2 is still reading it. The new inter=512 dispatch exposes GLM to that existing assumption, and the graph test only covers one prewarmed stream. Can this use a stream/graph-specific workspace lease, or otherwise serialize access?

- Raiden-Makoto · comment · 2026-10-06T16:09:48Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4197692908)

File: `python/sglang/kernels/ops/moe/smallm_moe_gfx950/__init__.py` · line None

GLM-5.3 sets `swiglu_limit=10.0`, but this dispatch only receives `activation_is_silu`. `p1_body` computes plain `silu(gate) * up`; it does not apply `gate = min(gate, 10)` and `up = clamp(up, -10, 10)` as the AITER path does. The explicit clamp-boundary test uses top-k 1, which `DISPATCH_SLOTS[512]` rejects, so that case falls back to AITER and never exercises this kernel. Please implement the clamp and test top-k 8/9 values beyond the boundary, or leave clamped models on AITER.

- Raiden-Makoto · comment · 2026-10-06T16:09:49Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4197693163)

The `hidden_states.shape[-1] % 2048 == 0` gate above also enables this path for H=2048, while the bit-exact test hard-codes H=4096. In the current MI355X run, the patch is active for `Qwen3-30B-A3B-Instruct-2507-FP8` (H=2048), and its GSM8K check scored 0.916 and then 0.906 against the required >0.92. The new H=4096 sort test did not run because that failure stopped the shard. Please restrict dispatch to the validated width, or add H=2048 bit-exact coverage and resolve the accuracy failure.

- Jacob0226 · comment · 2026-10-07T03:11:52Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4202691465)

File: `python/sglang/kernels/ops/moe/smallm_moe_gfx950/__init__.py` · line None

Good catch, confirmed: GLM-5.3-Flash ships `swiglu_limit=10.0`, it reaches `quant_info.swiglu_limit`, and the smallm dispatch ignored it. Fixed in f80f614486: the limit is passed into the kernel (the spare `Args` int is now a float, so the kernarg stays 104 bytes) and p1 computes `silu(min(gate, L)) * clamp(up, -L, L)`, matching the AITER path. The new `test_swiglu_limit_clamp` covers top-k 8/9 at 1/4/16 tokens with gate/up crossing ±10. With the limit dropped (the old behavior), rel L2 vs the clamped reference is 1.8–4.3; with it, ≤ 1.2e-4.


- Jacob0226 · comment · 2026-10-07T03:11:54Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4202691612)

File: `python/sglang/kernels/ops/moe/moe_sorting_small.py` · line 554

The patch is active for Qwen3-30B (H=2048), but this GSM8K check is also flaky on main without this PR: scheduled main runs score 0.908–0.932 on the first try, and run [37223521301](https://github.com/sgl-project/sglang/actions/runs/37223521301) failed the same way (0.908, then 0.920 on retry, vs `> 0.92`). H=2048 is a supported width by design (the emit splits columns into 2048-wide chunks), and f80f614486 adds `(E=128, topk=8, H=2048)`, up to batch 32, to the bit-exact test, now also checking the scale tensor shape. Passes on MI355X alongside the GLM shapes.


- Jacob0226 · comment · 2026-10-07T03:11:56Z · [source](https://github.com/sgl-project/sglang/pull/41871#discussion_r4202691735)

File: `python/sglang/kernels/ops/moe/smallm_moe_gfx950/__init__.py` · line 38

Each call launches p1 and p2 back to back on the current stream, so they are stream-ordered, and graph replays are serialized on the forward stream. In the DeepSeek/GLM dual-stream MoE, only the shared expert (a dense MLP) runs on `alt_stream`; routed experts, and therefore smallm, stay on the main stream. A per-stream workspace would make the captured pointers depend on the stream and complicate graph capture, so f80f614486 documents this invariant on `_workspace()` instead. Happy to add a guard if you know of a path that runs two MoE calls concurrently.
