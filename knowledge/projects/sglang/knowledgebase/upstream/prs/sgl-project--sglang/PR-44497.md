# [AMD] Add MiniMax-M3 dense MXFP8 FlyDSL GEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/44497) · state: open · merged: False

## Original PR description

## Motivation

MiniMax-M3 dense MXFP8 on gfx95 stores the weight in the MX-scale preshuffle layout, with per-1x32 E8M0 scales. With `--fp8-gemm-backend=aiter` and `SGLANG_USE_AITER=1`, an exact TP4 signature can run that layout through AITER `gemm_mxscale_preshuffle`. That entry is ROCm/aiter#5817. The default gfx95 runner stays on `dot_scaled`.

## Modifications

- Native MXFP8 on gfx95 selects `gfx95_mxfp8_flydsl` only when the runner backend is AITER. `is_gfx95()` does not include that value, so the existing gfx95 weight and apply path is unchanged.
- Block-fp8 served as MXFP8 still resolves to `gfx95_mxfp8_aiter` when the runner backend is AITER.
- For the seven TP4 shapes below, load time shuffles the weight with `shuffle_weight(..., (16, 16))` and the scale with `shuffle_scale_a16w4` when every tuned M for that N×K is present. Any other N×K keeps the checkpoint tensors.
- Apply uses the shuffled tensors only for an exact `(M, N, K)` row, a bf16 activation, and, when `M <= 64`, a batch size inside the captured decode graph. Otherwise the call uses `dot_scaled` on the checkpoint tensors. Split-K uses a caller-owned fp32 workspace so the graph address stays fixed.

Shapes: `(2304, 6144)`, `(2560, 6144)`, `(6144, 2048)`, `(6144, 6144)`, `(6144, 3072)`, `(1536, 6144)`, `(6144, 768)`.

## Accuracy Tests

`test/registered/unit/layers/quantization/test_minimax_m3_mxfp8_aiter.py`: 8 passed.

- The default gfx95 runner resolves to `dot_scaled`.
- `--fp8-gemm-backend=aiter` on gfx95 resolves native MXFP8 to FlyDSL and block-fp8-as-MXFP8 to `gfx95_mxfp8_aiter`.
- An N×K with no tune keeps the checkpoint weight.
