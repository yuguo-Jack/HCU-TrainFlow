# [Perf] [AMD] batch-invariant: Segmented split-K bf16 matmul for gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45599) · state: open · merged: False

## Original PR description

## Motivation

In deterministic mode, SGLang replaces `aten::mm` with a batch-invariant Triton matmul, so a token's result does not depend on how many other tokens share its batch. That kernel launches one program per output tile and loops over all of K in each, so at decode sizes (a few to a few hundred tokens) it launches few programs and leaves most of an MI350X idle. On gfx950 the decode GEMMs run at well below `torch.mm` speed, and they are a large part of deterministic mode's remaining cost after #44045.

This PR adds a segmented split-K matmul for bf16 on gfx950. K is split into 4 fixed segments, each reduced in 64-wide blocks, and the 4 segment sums are added in a fixed order, at every batch size. Up to 1,024 tokens (128 for layers wider than 8,192 outputs), the segments run in separate programs (fp32 partial sums, then a fixed-order reduce), so decode and small-prefill GEMMs launch 4 times as many programs. Larger batches run all segments in one program. Both orders are the same, so the output bits are the same whichever path or tile is chosen, and the launch can be picked by M and N for speed without breaking batch invariance. Matmuls with K up to 256 keep the persistent kernel: there each segment is a single 64-wide block, and the compiler folds the segment sums into one accumulation when all segments run in one program, so the split and unsplit launches would round differently.

One pitfall, found while testing: when one program loops over all segments with software pipelining (`num_stages` 2 or 3) across the segment loop, the output was not run-to-run deterministic for some K on MI350X (only seen with 2 segments, but the cause is not understood). This kernel therefore never pipelines that loop (`num_stages` 1 when not split), and a unit test keeps it that way. Pipelining within one segment, as in the split path, was deterministic in every test.

**Impact**
- Who: `--enable-deterministic-inference` on gfx950 (MI350X/MI355X), bf16 models, in the linear layers that go through the batch-invariant matmul.
- Effect: deterministic-mode throughput +12% at 1k/1k, +12% at 4k/512 and +3% at 8k/1k on Qwen3-8B; +12% / +14% on Qwen3.8-27B; +14% / +14% / +5% on Phi-4 (table below); bitwise batch invariance unchanged.
- Numerics: the reduction order changes (fixed 4 segments, BLOCK_K 64), so deterministic-mode outputs on gfx950 differ in the last bits from before this PR, as with any change of the batch-invariant kernel; accuracy is unchanged (GSM8K below).
- Unchanged: deterministic mode off; other GPUs, including MI300 (gfx942) and NVIDIA; fp16 and fp32 matmuls; bf16 matmuls with a non-bf16 output dtype (they keep the persistent kernel and #44045's preset).

**Dependency:** stacked on #44045 (gfx950 preset for the persistent kernel): this branch contains its commits, and the gains below are measured on top of it.

## Modifications

- `batch_invariant_ops.py`:
  - `_segmented_matmul_kernel` (Triton): per output tile, sums 4 fixed K segments in order; `SPLIT` runs one segment per program and stores fp32 partials, otherwise one program loops over all 4. Bias is added after the segment sum. int64 offsets.
  - `_segment_reduce_kernel`: adds the 4 partials in order (and the bias) and casts to the output dtype.
  - `_segmented_matmul_launch(M, N)`: tile, warps, `num_stages` and split by M and N, measured on MI350X over the bf16 linear shapes of Qwen3-8B, Qwen3.8-27B, Qwen3-30B-A3B and gpt-oss-20b (M = 1-8192). Split up to M = 1,024 (M = 128 when N > 8,192); unsplit launches use `num_stages` 1.
  - `matmul_persistent`: on gfx950, bf16 inputs with bf16 output and K above 256 (`_SEGMENT_MIN_K`) go to `_matmul_segmented_triton`.
- Tests:
  - `test/registered/unit/batch_invariant_ops/test_segmented_matmul.py` (gfx950, registered on the MI35x per-PR suite): bitwise equality of each row across batch sizes 1-4096 (with and without bias), run-to-run equality, the same bits for every launch configuration in the table and for split vs unsplit, and relative error against fp32 below 1%; shapes include K = 2,880 (not a multiple of the segment size) and N = 32. A short-K test checks that rows at K = 96-512 do not depend on the batch size through `matmul_persistent`.
  - `test_matmul_persistent_configs.py` (CPU): the segment constants, and that unsplit launches are never pipelined.

## Accuracy Tests

MI350X, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261018` (ROCm 7.2.4), this PR's `batch_invariant_ops.py` over the image's SGLang together with the other open deterministic-mode fixes MI350X needs (#43788, #34543, #44489). Server:

```
SGLANG_USE_AITER=1 python3 -m sglang.launch_server --model-path <model> --tp <N> \
  --attention-backend triton --prefill-attention-backend triton --decode-attention-backend aiter \
  --enable-deterministic-inference
```

Checks: `python3 -m sglang.test.test_deterministic --test-mode {single,prefix,radix_cache} --n-trials 50` (prefix also with `--return-logprob`), and a bitwise comparison of 1,275 responses (the same prompt in batches of 1-50, token IDs and log-probabilities) against batch size 1. Long context (Qwen3-8B with YaRN x4): a 64k and a 120k prompt alone vs next to other requests; a 100k prompt split at different chunk boundaries by other requests; 30k-token cached prefixes.

| Model | TP | single | prefix (logprobs) | radix_cache | bitwise |
| --- | --- | --- | --- | --- | --- |
| Qwen3-8B | 1, 2, 4, 8 | 1 unique | identical | pass | 1,275/1,275 |
| Qwen3-30B-A3B | 1 | 1 unique | identical | pass | 1,275/1,275 |
| Qwen3.8-27B | 2, 8 | 1 unique | identical | pass | 1,275/1,275 |
| Phi-4 | 1 | 1 unique | identical | pass | 1,275/1,275 |
| gpt-oss-20b (with ROCm/aiter#6583's deterministic MoE) | 1 | 1 unique | identical | pass | 1,275/1,275 |

The kernel's split and unsplit paths compute the same segment sums in the same order, so moving the split threshold does not change any output bit (checked on 200 shape and batch-size points, and for every launch in the table by the new unit test); the final launch table was re-checked end to end on Qwen3-8B TP1 (all of the above, and the long-context checks below).

Long context, Qwen3-8B TP1: 64k/120k 8/8 identical, chunk boundaries 12/12, cached 30k prefix 12/12.

GSM8K (1,319 questions, greedy), Qwen3-8B deterministic mode: 93.18% before, 93.33% after.

Unit tests on MI350X (this branch's tree on `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261020`): `test_segmented_matmul.py` and `test_matmul_persistent_configs.py` 10 passed (259 subtests), existing `test_batch_invariant_ops.py` 6 passed, 1 skipped.

Short K: before the fix in the latest commit, `torch.mm` in batch-invariant mode gave rows that depended on the batch size at K = 96, 128, 192 and 256 (N = 2,048-5,120, rows of batches of 1-1,024 vs the same rows in a batch of 4,096); this showed up end to end as a TP4 difference in Kimi-Linear, whose shared-expert down projection has K = 256 per rank. With the fix every audited shape (K = 96-2,304) is batch-invariant, the same as the persistent kernel on main.

- aarnetalman · comment · 2026-10-25T07:54:01Z · [source](https://github.com/sgl-project/sglang/pull/45599#issuecomment-6395099493)

I found a batch-invariance bug in this PR and pushed a fix (bb91ae091a, together with a merge of current main).

When K is 256 or less, each of the 4 segments is just one 64-wide block. In that case the unsplit launch (used for large batches) rounds differently from the split launch (used for small batches), so a row's result could change with the batch size. I ran into it with Kimi-Linear at TP4: its shared-expert down projection has K = 256 per GPU, and the prefix determinism test failed.

The fix keeps matmuls with K <= 256 on the persistent kernel, the same as without this PR. Larger K is untouched, so the numbers in the description still hold. I also added a test for short K (96-512).

Checked on MI350X: no batch-size differences at any shape I tested (K from 96 to 2,304), the unit tests pass, and Kimi-Linear TP4 now passes every determinism check (prefix gives one output per prompt, before 1/2/1/2; 1,275/1,275 bitwise identical).
