# [Fix] function_call: Infer number for schemas that allow integer or number

[Upstream PR](https://github.com/sgl-project/sglang/pull/48151) · state: open · merged: False

## Original PR description

> Stacked on #48143. The first commit here is #48143; please review only the second commit, **"Infer number for schemas that allow integer or number"**. I will rebase once #48143 is merged.

## Motivation

`infer_type_from_json_schema` picks one type per parameter, and Qwen3-Coder, GLM-4.5/4.7 and Kimi K2 detectors convert values with it. For schemas that allow both integers and decimals it picks the wrong one, so a decimal value comes back as a string:

| Schema | Inferred before | Qwen3-Coder result for `2.5` |
|---|---|---|
| `{"type": ["integer", "number"]}` | `integer` | `{"x": "2.5"}` |
| `{"anyOf": [{"type": "integer"}, {"type": "number"}]}` | `integer` | `{"x": "2.5"}` |
| `{"anyOf": [integer, number, null]}` | `integer` | `{"x": "2.5"}` |
| `{"enum": [1, 2.5]}` | `string` | `{"x": "2.5"}` |

The type-array branch returns the first non-null type, the `anyOf`/`oneOf` branch falls back to the first type, and the `enum` branch treats any mix of value types as `string`. `{"enum": [1.5, 2.5]}` is already inferred as `number`, so only the mixes are wrong.

I did not open an issue for this; I found it while working on #48143. Open PRs that mention `infer_type_from_json_schema` (#46038, #45840, #43389, #36835, #43018, #46565) do not change how it merges types. #43018 adds an unrelated helper next to it in `utils.py`.

## Modifications

- `function_call/utils.py`: a small `_unify_scalar_types` helper ignores `null` and returns `number` when the remaining types are exactly `integer` and `number`, or the single remaining type otherwise. The type-array, `anyOf`/`oneOf` and `enum` branches use it before their existing fallbacks, so every other schema is inferred as before.
- `qwen3_coder_detector.py`: the `number` branch now tries `int()` first for literals without `.` or `e`. Without this, `integer | number` schemas, which previously went through the `integer` branch, would start rounding integers above 2**53 (`9007199254740993` became `9007199254740992`). Plain `number` parameters get the same fix.

Side effect: a nullable enum such as `[1, null]` is now inferred as `integer` instead of `string`, so `1` is returned as a number. A literal `null` value is still returned as `None` in all three detectors.

## Testing

CPU only (ARM Neoverse-N1), Python 3.12. Added `test_integer_or_number_parameters_keep_decimal_values` to `TestQwen3CoderDetector`. It checks the four schemas above with `2.5` and `9007199254740993`, in one-shot parsing and streaming at several chunk sizes, through the existing `_check_structured_union_value` helper.

- Without the change, 15 subcases fail, e.g. `AssertionError: {'value': '2.5'} != {'value': 2.5}` and `{'value': '9007199254740993'} != {'value': 9007199254740993}`.
- With the change, `test_function_call_parser.py` gives 254 passed. The 9 failures are all in `TestDeepSeekV32Detector` and fail the same way on `main` in my environment because `torchvision` is not installed.
- The other callers' suites still pass: `test_glm47_schema_types.py` (11), `test_k2_v3_detector.py` (18), `test_json_schema_constraint.py` (18).
- For `integer | number` schemas, `inf`, `nan` and `Infinity` stay strings, thanks to #48143.

`pre-commit run --files` passes on the changed files.

AI assistance was used to help find the issue and draft the change; I reviewed the change and ran the tests above.
