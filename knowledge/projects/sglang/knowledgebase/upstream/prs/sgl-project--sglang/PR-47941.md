# [Fix] sampler: Avoid a host read in the torch top-k / top-p / min-p sampler

[Upstream PR](https://github.com/sgl-project/sglang/pull/47941) · state: open · merged: False

## Original PR description

## Motivation

`top_k_top_p_min_p_sampling_from_probs_torch` zeroes the filtered probabilities by assigning through a boolean mask (`probs_sort[mask] = 0.0`, three sites: top-k, top-p, min-p). That form is a composite that calls `nonzero` and then `item`, because the number of selected elements is data-dependent, so every call sends a size and a value back to the host:

```
CPU: aten::item, aten::_local_scalar_dense
XPU: aten::nonzero, aten::item, aten::_local_scalar_dense
```

(`torch.profiler` over one call of each form; `masked_fill_` reports none on either device.)

That costs twice:

1. **A host read cannot be recorded in a device graph**, so a decode graph that samples through this path fails to capture. On Intel XPU it raises `level_zero backend failed with error: 44 (UR_RESULT_ERROR_UNSUPPORTED_FEATURE)` at the first of the three sites.
2. **In eager mode the read waits for the queued work to drain.** At the sampler's own shape (4 x 3072), issued behind ten queued matmuls the way a decode step would issue it, the boolean form holds the host **2.72 ms** against **0.007 ms** for `masked_fill_`. The absolute number tracks the queue depth, not the mask; the point is that the sampler pays a full drain on every step instead of none.

This path is not exotic: it is what the `pytorch` sampling backend runs, and the only backend that honours per-request sampling seeds, since the `flashinfer` and `intel_xpu` backends assert `sampling_seed is None`. A concrete casualty is the Qwen3-Omni talker in sglang-omni, which pins `sampling_backend="pytorch"` for seeded sampling: its decode graph cannot capture on XPU, so the speech pipeline has to run the talker eagerly.

## Modifications

- `python/sglang/srt/layers/sampler.py`: the three boolean-mask assignments become `masked_fill_`, which is the same operation with a fixed shape and no host read. The Ascend path in the same file already uses `masked_fill_`, as does the top-p renorm a few lines above.
- `test/registered/xpu/test_sampler_graph_capture_xpu.py`: captures the sampler in an XPU graph and checks the replay against eager, both with per-request seeds (token ids) and with min-p (filtered weights, since min-p excludes seeds and `torch.multinomial` is not deterministic).

I kept the change unconditional rather than gating it on XPU: the host read is in the device-agnostic composite, it is observable on CPU as well, and `masked_fill_` has no downside on any backend.

## Accuracy Tests

- The new test passes with this change and fails without it, raising the error above (Arc Pro B60, torch 2.14.0+xpu).
- Seeded tokens replayed from the captured graph are bit-identical to eager (`rtol=0, atol=0`).
- Qwen3-Omni speech end to end on 8x Arc Pro B60 (sglang-omni, thinker TP=4 + talker + Code2Wav): round-trip WER through Qwen3-ASR is 1.9% with the talker decode graph this change makes capturable, against 1.6% with the eager talker, over the same 24 prompts (8 vs 7 word errors out of 429).

## Speed Tests and Profiling

Micro, the sampler's own shape (4 x 3072 probabilities, top-k 50 / top-p 0.8), host time per call, issued behind ten queued matmuls:

| | host time |
|---|---|
| `probs_sort[mask] = 0.0` | 2.717 ms |
| `probs_sort.masked_fill_(mask, 0.0)` | 0.007 ms |

End to end, Qwen3-Omni speech on 8x Arc Pro B60 (thinker TP=4 plus talker plus Code2Wav), 5 s read-aloud prompts. RTF is generation time ÷ audio length; lower is better. Capturing the talker's decode graph, which this change makes possible, is a 3.8x end-to-end speed-up and takes the pipeline from slower than realtime to 3.9x faster than realtime.

| Talker decode | RTF, 1 concurrent | RTF, 4 concurrent | First audio, 1 concurrent |
|---|---|---|---|
| eager (graph cannot capture today) | 0.960 | 1.080 | 0.99 s |
| XPU graph (this change) | **0.254** | **0.337** | **0.45 s** |

I have no CUDA host, so the CUDA effect of removing the host read is not measured here; the dispatch above is device-agnostic and the CPU profile shows the same `item` / `_local_scalar_dense` pair.
