# [CI] [AMD] spur: Run AMD CI suites on MI35x nodes scheduled through Spur

[Upstream PR](https://github.com/sgl-project/sglang/pull/44538) · state: open · merged: False

## Original PR description

## What

Lets AMD CI suites run on MI35x nodes scheduled through Spur, with a runner on the cluster's login node instead of an ARC pod on each GPU host. This PR adds a dispatch-only smoke-test workflow running the stage-a 1-GPU suite; wider suites can follow once the path is proven.

## Why

The `linux-mi35x-gpu-*` jobs assume an ARC pod. The GPU arch comes from a `linux-<arch>-gpu-N` hostname, and the persistent cache lives at `/home/runner/sglang-data`. A Spur node has neither. Without a fix, the scripts silently fall back to the mi30x image and to a container-local cache.

The DI nightly already runs on Spur through `launch_mi355x.sh`, but that launcher is built around multi-node disaggregation (RDMA, MORI, model staging). Single-node suites need none of that, so this adds a small launcher instead of extending it.

## Changes

- **`scripts/ci/amd/*`:** two optional overrides, both unset on ARC runners, so their behaviour is unchanged.
  - `AMD_CI_GPU_ARCH` is checked before the hostname.
  - `AMD_CI_CACHE_HOST` relocates the `/sgl-data` cache and turns the mount on by default.
- **`launch_amd_ci_mi35x.sh`** (runs on the runner) submits one whole-node job and streams its log into the step output. It handles the Spur behaviours found in #40113 and #41025:
  - jobs that are cancelled or held before they start are resubmitted;
  - one empty state reading is not taken as "finished";
  - a two-field time limit is rejected.
- **`amd_ci_job_mi35x.sh`** (runs on the node) runs the same steps as the ARC jobs: `ensure_vram_clear` → start container → install → `run_suite.py`.
  - The checkout is copied to node-local scratch first, because the root-run container writes into its bind mount and an NFS home with root squash refuses that.
  - The node is held `--exclusive`, because `ensure_vram_clear.sh` stops every GPU container on the host.
- **Runner environment:** cluster settings (`SLURM_PARTITION/ACCOUNT/QOS`, `CI_NODE_SCRATCH`) come from the runner's `.env`, the same way the DI nightly runner gets its cluster settings.

## Test plan

- Ran `launch_amd_ci_mi35x.sh --suite stage-a-test-1-gpu-small-amd --rocm-version rocm10` from a Spur login node against an MI355X node, the same command the workflow step runs.
  - `AMD_CI_GPU_ARCH` selected the mi35x image (`rocm/sgl-dev:v0.5.21-rocm10-mi35x-20261014`), and `/sgl-data` was mounted from node-local scratch.
  - The job's log streamed into the launcher output, and the launcher exited with the job's exit code.
  - The node's checkout copy and the `ci_sglang` container were removed afterwards.
- Suite result: 6 of 7 tests pass. `test_basic_sanity_eagle3.py` fails with a 401 on the gated `meta-llama/Llama-3.1-8B-Instruct`, because the manual run had no `HF_TOKEN`. The runner needs `HF_TOKEN` in its environment, as the ARC runners have.
- ARC path (both variables unset): [PR Test (AMD) run 38781829386](https://github.com/sgl-project/sglang/actions/runs/38781829386), attempt 2, uses the hostname parse and `/home/runner/sglang-data` as before. 20 MI300 stage jobs pass, e.g. [stage-a-test-1-gpu-small-amd](https://github.com/sgl-project/sglang/actions/runs/38781829386/job/116593083497) and [stage-b-test-1-gpu-small-amd (0)](https://github.com/sgl-project/sglang/actions/runs/38781829386/job/116599937121).
  - The one failure is `test_kda_kernels.py` in [stage-b-test-1-gpu-large-amd (2)](https://github.com/sgl-project/sglang/actions/runs/38781829386/job/116599936452). It fails the same way on `main` ([scheduled run](https://github.com/sgl-project/sglang/actions/runs/38734250959/job/116419462469)), so it isn't caused by this change.
  - The MI35x jobs are still queued.
- The workflow itself can't run until a runner with label `linux-sglang-mi35x-spur` is registered. Not yet verified.
