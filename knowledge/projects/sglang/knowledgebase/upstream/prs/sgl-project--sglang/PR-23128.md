# fix: clamp dA_cumsum differences to prevent Inf in Mamba2 SSD kernels

## Motivation

Clamp `dA_cumsum` differences to non-positive before exponentiation in Mamba2 SSD Triton kernels to prevent `Inf` → `NaN` propagation.

When a Mamba2 model has large `|A|` values, `dA_cumsum` reaches magnitudes where float32 ULP exceeds safe range. The parallel prefix scan (`tl.cumsum`) introduces rounding errors that can make `(dA_cs_last - dA_cs_k)` slightly positive instead of the mathematically guaranteed `≤ 0`. When this positive value is fed into `tl.exp()`, it overflows to `Inf`, which propagates through the SSM state and produces `NaN` in subsequent decode steps, corrupting outputs.

This mirrors:
- Upstream Mamba training-path fix: [state-spaces/mamba#713](https://github.com/state-spaces/mamba/pull/713)
- vLLM inference-path fix: [vllm-project/vllm#37501](https://github.com/vllm-project/vllm/pull/37501)

SGLang carries the same unguarded pattern in its Mamba2 SSD kernels, so the same correctness fix applies.
## Modifications

Added `tl.minimum(..., 0.0)` as a guard before `tl.exp()` at every call site where the exponent is a difference of `dA_cumsum` values.

Since `dA_cumsum` is a cumulative sum of non-positive values (`A ≤ 0`, `dt ≥ 0`), it is monotonically non-increasing, so any difference `dA_cumsum[i] - dA_cumsum[j]` with `i > j` is mathematically `≤ 0`. The clamp is a no-op in exact arithmetic and only takes effect on the float32 rounding edge cases that would otherwise overflow `exp()` to `Inf`.

Call sites guarded:
- `_chunk_scan_fwd_kernel` in `ssd_chunk_scan.py`
  - `cb *= tl.exp(dA_cs_m[:, None] - dA_cs_k[None, :])`
  - `scale_m = tl.exp(dA_cs_m - dA_cs_m_boundary)`
- `_chunk_state_fwd_kernel` in `ssd_chunk_state.py`
  - `scale = tl.exp(dA_cs_last - dA_cs_k) * dt_k` (both branches of `HAS_SEQ_IDX`)
- `_chunk_state_varlen_kernel` in `ssd_chunk_state.py` (SGLang-specific kernel; not present in vLLM)
  - `tl.exp(dA_cs_last - dA_cs_k) * dt_k`
  - `scale = tl.exp(dA_cs_last - dA_cs_boundary)`

Call sites intentionally left unchanged: `tl.exp(dA_cs_m)` at lines 271 and 277 in `ssd_chunk_scan.py`. These apply `exp` to a single `dA_cumsum` value rather than a difference, and since `dA_cumsum ≤ 0` by construction, `exp(·) ≤ 1` is already bounded.

This goes slightly beyond the vLLM port ([vllm-project/vllm#37501](https://github.com/vllm-project/vllm/pull/37501)) by also guarding the `_boundary` call sites, which carry the same arithmetic pattern and therefore the same float32 overflow risk.

Example (before → after):
```python
# before
cb *= tl.exp(dA_cs_m[:, None] - dA_cs_k[None, :])
# after
cb *= tl.exp(tl.minimum(dA_cs_m[:, None] - dA_cs_k[None, :], 0.0))
```

No behavior change for inputs where the subtraction is actually `≤ 0` (always true in exact arithmetic).

## Accuracy Tests

This fix was originally validated in the vLLM port of these kernels during RL training on a Mamba2-based LLM, where the unguarded pattern caused intermittent `NaN`s in rollout outputs. 

On the vLLM side:
- Before fix: 32 / 224 samples contained `NaN` (65,504 `NaN` tokens)
- After fix: 0 / 224 samples, 0 `NaN` tokens

See [vllm-project/vllm#37501](https://github.com/vllm-project/vllm/pull/37501) for the detailed numbers.

The SGLang kernels carry the identical arithmetic pattern, so the same correctness argument applies. Happy to add an SGLang-specific regression test if the maintainers would like one.

## Speed Tests and Profiling

No meaningful performance impact expected. The fix adds a single `tl.minimum` per `tl.exp` call site inside kernels that already perform multiple arithmetic ops per iteration. `tl.minimum` compiles to a single fused instruction and does not change memory access patterns or block layout.
