# [Perf] streaming: Coalesce queued tokenizer output notifications

[Upstream PR](https://github.com/sgl-project/sglang/pull/48310) · state: open · merged: False

## Original PR description

## Motivation

When detokenizer outputs queue behind the tokenizer manager, waking every request after every output spends CPU on stream chunks that can already be coalesced by the response consumer. This limits throughput for high-concurrency streaming.

## Modifications

- Drain already-queued outputs through nonblocking reads, preserving control-message order, and notify each affected request once at the end of the pass.
- Bound each pass by output count and row count, and yield throughout the pass so HTTP intake can progress.
- Preserve incremental and cumulative output handling, avoid empty wakeups when a slow consumer has already taken its outputs, and track request-state identity when request IDs are reused.
- Normalize nonpositive notification batch sizes. Retain the original per-output behavior for custom workers that override `_handle_batch_output`, including its original method signature.
- Enable the drain by default with `SGLANG_ENABLE_TOKENIZER_OUTPUT_DRAIN=0` as the opt-out. Hoist the weight-version lookup out of the per-request loop.

Related [#46372](https://github.com/sgl-project/sglang/pull/46372) optimizes metadata scans inside the existing consumer coalescer; this changes socket draining and notification scheduling upstream of that consumer.

## Speed Tests and Profiling

Historical same-host H100 measurements supplied with the patch; these were not rerun during this PR preparation. Two base and two patch repetitions, decode CUDA graph ceiling 512 in both arms, two benchmark clients for c512.

| Model / native streaming workload | Base output tok/s | Patch output tok/s | Change |
| --- | ---: | ---: | ---: |
| Qwen3-0.6B / 256-in, 512-out, c512 | 15,761 | 33,581 | +113.1% |
| Qwen3-0.6B / 512-in, 128-out, c512 | 14,560 | 21,027 | +44.4% |
| Qwen3-0.6B / 256-in, 512-out, c64 control | 18,385 | 18,379 | ~0% |
| gpt-oss-20b / ShareGPT, 1024-out, c512 | 12,561 | 22,172 | +76.5% |

On the first workload, median TTFT fell from 1,933 to 410 ms and median TPOT from 28.40 to 14.44 ms.

Tradeoffs: the first notification waits for the drain pass, and overloaded streams can contain more tokens per chunk even at stream interval 1. A row budget can be exceeded by the final whole output batch; very large batches still defer that output's notifications. Tool/reasoning parsers and clients must support multi-token deltas, as they already can receive from slow-client coalescing. Distributed serving and production parser combinations need broader CI coverage. Custom handler overrides retain the previous notification path.

To reproduce the primary workload, start the server on the base or patch checkout:

```bash
python -m sglang.launch_server --model-path Qwen/Qwen3-0.6B \
  --port 30000 --cuda-graph-max-bs-decode 512
```

In a separate Bash terminal, run two concurrent clients (3,072 total requests, total maximum concurrency 512) and keep both output files. Repeat both arms twice, alternating their order; leave the drain environment override unset.

```bash
pids=()
for i in 1 2; do
  python -m sglang.benchmark.serving --backend sglang \
    --model Qwen/Qwen3-0.6B --host 127.0.0.1 --port 30000 \
    --dataset-name random --random-input-len 256 --random-output-len 512 \
    --random-range-ratio 1.0 --num-prompts 1536 --max-concurrency 256 \
    --seed "$((1000 + i))" --output-details \
    --output-file "client-${i}.jsonl" > "client-${i}.log" 2>&1 &
  pids+=("$!")
done
for pid in "${pids[@]}"; do wait "$pid"; done
```

Check each client's successful-request and generated-token totals before aggregating throughput, and ensure neither client is CPU-saturated.
