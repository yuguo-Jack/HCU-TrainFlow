# [Perf] request_logger: don't walk omitted or truncated fields during watermark redaction

[Upstream PR](https://github.com/sgl-project/sglang/pull/44683) · state: closed · merged: False

## Original PR description

## Motivation

#37577 (Aaronson-Gumbel text watermarking) made `_dataclass_to_string_truncated` and `_transform_data_for_logging` call `redact_watermark_secrets` on the whole request **before** truncation and **before** `skip_names` filtering. Redaction is key-based, but it walks every element, so every request-log call is now O(prompt length), even for fields the log never prints.

With `--log-requests --log-requests-level 1` (`max_length = 1 << 30`, and `input_ids` / `output_ids` in `skip_names`, so they are never printed), each call walks the full `input_ids` list. The tokenizer manager's event loop pays for this on receive, before the request is dispatched to the scheduler, so it adds directly to TTFT. It pays again on finish.

Measured on our deployment (DeepSeek-V4.1-Flash on 4×B300, replaying production traffic with a mean prompt of ~84k tokens), the API server's received→dispatched time went from ~3 ms to ~25 ms per request compared with a pre-#37577 build.

## Modifications

`python/sglang/srt/utils/request_logger.py`:
- New helper `_redact_fields_for_logging(values, max_length, skip_names)`, used by the dict and dataclass branches of both formatters in place of redacting the whole object:
  - Fields in `skip_names` are never redacted. The log omits them anyway.
  - Lists and tuples longer than `max_length` outside the watermark-bearing fields (`watermark`, `watermark_key`, `watermark_key_b`, `watermark_config`, `sampling_params`, `preferred_sampling_params`) skip the whole-object walk. Everything else is redacted exactly as before.
- In `_transform_data_for_logging`, the truncated-list branch now redacts the printed head and tail halves, as `_dataclass_to_string_truncated` already did. Secrets in a long list are still redacted wherever they are printed.

Log output does not change at any `--log-requests-level` (0–3).

## Tests

New `test/registered/unit/utils/test_request_logger_redaction.py` (CPU, `base-a-test-cpu`):
- Watermark secrets are redacted in both formatters, for short and 100k-token requests, at level 1 and inside a long `sampling_params` list.
- The longest list handed to `redact_watermark_secrets` is bounded at each level's real `(max_length, skip_names)` (levels 0–2; level 3 prints every id).
- Truncated output keeps its head and tail.

Results with the installed tree copied to a scratch dir and only `request_logger.py` swapped:
- `upstream/main` `request_logger.py`: **1 failed, 5 passed**. `test_redaction_walk_is_bounded_at_every_log_level` fails with `AssertionError: 100000 not less than or equal to 2048 : level=0 _dataclass_to_string_truncated`.
- This PR: **6 passed**.

**Output equivalence.** I compared old and new output for both formatters at levels 0, 1, 2 and 3, using each level's `RequestLogger(...).metadata`. The inputs were `GenerateReqInput` with 16 / 3k / 100k `input_ids` (with and without watermark params), text input, batched input, a long `sampling_params` list, `EmbeddingReqInput`, finish `out` dicts (16 / 5k `output_ids`), and OpenAI-style dicts (the `log_openai_received_request` path, no `skip_names`). The output was byte-identical in 72/72 cases (text and JSON), and no secret appeared in any output.

**Microbenchmark.** Per log call at `--log-requests-level 1`, plain `sampling_params`, mean of 30 calls, single-threaded on a dev-box CPU:

| `input_ids` | formatter | before (ms) | after (ms) |
|---|---|---|---|
| 30k | `_dataclass_to_string_truncated` (text) | 6.87 | 0.057 |
| 30k | `_transform_data_for_logging` (json) | 6.89 | 0.051 |
| 80k | `_dataclass_to_string_truncated` (text) | 18.43 | 0.057 |
| 80k | `_transform_data_for_logging` (json) | 18.40 | 0.051 |
| 120k | `_dataclass_to_string_truncated` (text) | 27.56 | 0.057 |
| 120k | `_transform_data_for_logging` (json) | 27.73 | 0.051 |

After this PR the cost no longer depends on prompt length.
