# [Fix] speculative: Restore DFLASH draft graph replay metadata

[Upstream PR](https://github.com/sgl-project/sglang/pull/47262) · state: open · merged: False

## Original PR description

## Motivation

DFLASH V2 manually constructs the draft `ForwardBatch` instead of using the normal scheduler-to-forward-batch initialization path. As a result, the draft batch did not inherit the scheduler's CUDA-graph eligibility votes or initialize the token-count metadata used by TP/DP synchronization.

The draft graphs were captured successfully at server startup, but runtime draft steps retained the default graph state and executed eagerly. Profiles showed roughly 100 individual kernel launches per draft step and no `hipGraphLaunch`, while target verification replayed its graph normally.

## Modifications

- Copy `can_run_decode_cuda_graph`, `can_run_dp_draft_cuda_graph`, and `is_extend_in_batch` from the scheduler batch into the hand-built draft `ForwardBatch`.
- Initialize MLP synchronization metadata with `is_draft_worker=True` so request counts are converted to draft-token counts correctly.
- Add CPU unit coverage for:
  - graph eligibility without DP synchronization metadata;
  - scaling a four-request count to 32 draft tokens for an eight-token block;
  - draft-specific DP counts and preservation of a negative graph vote.

The patch does not force graph replay: an unsafe scheduler/DP vote remains false and uses the eager path.

## Accuracy Tests

The change does not alter model math, sampling, or KV-cache contents.

- Acceptance length remained matched:

## Speed Tests and Profiling

After the fix, each draft step contains one `hipGraphLaunch` instead of approximately 100 eager launches.

| Workload | Draft before | Draft after | Change |
|---|---:|---:|---:|
| 60k/c16 | 7.700 ms | 1.996 ms | **-74.1%** |
| 128k/c4 | 6.876 ms | 1.488 ms | **-78.4%** |

Target-verification time was effectively unchanged. Same-node serving impact:

| Workload | Output throughput | Mean ITL |
|---|---:|---:|
| 8k/c4 | **+23.99%** | **-16.85%** |
| 8k/c16 | **+9.64%** | **-7.86%** |
| 60k/c16 | **+0.93%** | **-4.02%** |
| 128k/c4 | **+2.50%** | **-7.73%** |

The four-point throughput geomean is **+8.90%**. In the canonical 12-point ratio-0.8 sweep, all points improved and throughput geomean increased **5.75%**.

### Reproduction

Use the official `XiaomiMiMo/MiMo-V2.6-Pro-RL` checkpoint and set `DRAFT_PATH` to its `dflash` directory.

```bash
python -m sglang.launch_server \
  --model-path XiaomiMiMo/MiMo-V2.6-Pro-RL \
  --served-model-name XiaomiMiMo/MiMo-V2.6-Pro-RL \
  --tensor-parallel-size 8 \
  --expert-parallel-size 8 \
  --attention-backend aiter \
  --moe-runner-backend aiter \
  --page-size 1 \
  --max-running-requests 256 \
  --cuda-graph-max-bs-decode 256 \
  --cuda-graph-backend-prefill disabled \
  --chunked-prefill-size 32768 \
  --max-prefill-tokens 65536 \
  --speculative-algorithm DFLASH \
  --speculative-draft-model-path "$DRAFT_PATH" \
  --speculative-num-draft-tokens 8 \
  --speculative-draft-attention-backend triton \
  --enable-mixed-chunk \
  --disable-hybrid-swa-memory \
  --mem-fraction-static 0.7 \
  --port 8018
```

Run a warmup, then compare `main` and this branch with the same seeds:

```bash
python -m sglang.bench_serving \
  --backend sglang --dataset-name random \
  --model XiaomiMiMo/MiMo-V2.6-Pro-RL \
  --host localhost --port 8018 --request-rate inf \
  --random-range-ratio 0.8 \
  --random-input-len 8192 --random-output-len 1024 \
  --max-concurrency 16 --num-prompts 96 --seed 3
```

Repeat for `60k/600 c16` (`num-prompts=96`, seed 9) and `128k/1k c4` (`num-prompts=32`, seed 11). For profiling, confirm that `step[DRAFT ...]` contains `hipGraphLaunch` on this branch and eager kernel launches on `main`.
