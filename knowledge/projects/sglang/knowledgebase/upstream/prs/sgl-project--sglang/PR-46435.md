# [Feat] mem_cache: Optionally zero KV pages on free

[Upstream PR](https://github.com/sgl-project/sglang/pull/46435) · state: open · merged: False

## Original PR description

## Motivation

A freed KV page keeps the previous request's KV until something overwrites it. If a bug ever lets a request read a page it does not own (a stale index, a transfer into the wrong pages), it reads another request's KV. This adds an opt-in flag that zeroes pages when they are freed, so such a bug reads zeros instead.

## Modifications

- New flag `SGLANG_ENABLE_ZERO_KV_ON_FREE` (off by default).
- On CUDA with page size > 1, every free path in `PagedTokenToKVPoolAllocator` (`free`, `free_segment`, `free_page_ids`, `free_group_end`) ends in `_release_page_ids`. This PR hooks in there. `clear()` zeroes the whole pool.
- `KVPageZeroer` (`mem_cache/kv_page_zeroer.py`) zeroes every page-indexed buffer in a single Triton launch, using a table of buffer pointers (`zero_pages_multi` in `kernels/ops/kvcache/zero_pages.py`). It covers the target pool's KV, the DSA index-K buffers, and the draft model pools, which share the target allocator's page ids. Only `MLATokenToKVPool` and `DSATokenToKVPool` are supported for now. Any other pool or allocator raises an error at startup.
- Timing:
  - The zero runs on a side stream that first waits for the current stream and the forward stream. With overlap scheduling, the forward pass that is already running can still write the last token of a request whose pages are being freed, so zeroing at free time would miss that write.
  - Freed pages sit in a `zeroing_pages` list together with a CUDA event. They move to the free list only after the event has completed. Allocations check this without blocking, and only wait when the free list runs short.
  - Zeroing later (for example, just before the next forward pass) would be unsafe. The page could already have been handed to a writer that does not run on the forward stream, such as a PD KV transfer or a HiCache load, and the late zero would wipe its data.
- `available_size()` and `get_all_free_pages()` count pages that are still being zeroed, so the scheduler's capacity math does not change.

## Accuracy Tests

No change when the flag is off. With the flag on, only freed pages are touched.

## Speed Tests and Profiling

Not measured yet. Estimate: zero traffic roughly equals KV write traffic, plus one extra kernel launch and one event per free call.

## Tests

- `test/registered/unit/mem_cache/test_paged_allocator_zero_on_free.py` (CPU): freed pages are zeroed, kept pages are untouched, enabling the flag zeroes the pool, and pages stay out of the free list until their event completes (blocking only when the free list is short).
- `test/registered/unit/mem_cache/test_kv_page_zeroer_cuda.py` (CUDA): the fused kernel matches a torch reference across MLA-like and index-K-like buffers, and the zero is ordered after pending forward-stream writes.

Draft: the CPU tests pass locally, but the CUDA test and an end-to-end run have not been run on a GPU yet.
