# [Fix] scheduler: Reject disk weight updates while weight memory is released

[Upstream PR](https://github.com/sgl-project/sglang/pull/44928) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44834.

`update_weights_from_disk` can reach the loader while weight memory is released, killing the scheduler. A release can also overtake an update waiting for the tokenizer's writer lock.

## Modifications

- Check the scheduler's `offload_tags` before invoking either weight loader. Return the existing unsuccessful response, which the HTTP handler exposes as HTTP 400, with instructions to resume weight memory.
- Keep disk updates available when only KV-cache or CUDA-graph memory is released.
- Extend the existing CPU tests with side-effect checks and a deterministic queued-update interleaving using the real tokenizer method and reader/writer lock. Extend the existing Blackwell reload test to check rejection before resuming weights.

## Accuracy Tests

Matched runs on one RTX 3050 (8 GiB), Qwen3-0.6B BF16, upstream base `3b34d9f8b6edc23216f29c1edf02d1ff0306f9de`, PyTorch 2.14.1+cu130, FlashInfer 0.7.2, torch-memory-saver 0.0.10:

| Case | Baseline | Fix |
| --- | --- | --- |
| Release, then disk update | Connection dropped; scheduler died in `weight_loader` with CUDA invalid argument / allocation not found | HTTP 400 for all-region and weights-only release, with `flush_cache` both true and false |
| Update queued before release, dispatched afterward | Same scheduler failure | HTTP 400; valid reload after weight-memory resume succeeded |

The sequential baseline used the reporter's unmodified client. The GPU race check used test-only endpoints to hold the real tokenizer reader lock, observed one waiting writer from an actual disk-update HTTP request, released memory, then released the reader. No production lock behavior was changed.

After valid reloads, greedy output for the same prompt was unchanged and `/health` returned 200. Reloading while only KV memory was released also succeeded. This is lifecycle validation, not a task-accuracy evaluation.

Local checks:

- Weight-update CPU test file: **23 passed, 8 subtests passed**. The CI entry point (`python test/registered/unit/managers/test_scheduler_weight_version_tracking.py -f`) also passed with zero visible CUDA devices. Both new rejection cases failed before the fix.
- Both added executable production lines (the guard condition and rejection return) covered; coverage started after native imports because import-time instrumentation crashed locally.
- Changed-file pre-commit hooks and `git diff --check`: passed.

Limitations: single GPU, Python radix-tree backend, prefill graphs disabled, full decode graphs enabled through batch size 32. The four-GPU Blackwell suite and live speculative/draft-model execution were not run locally; CPU coverage checks that neither target nor draft loader is invoked on rejection.

## Speed Tests and Profiling

No model-forward changes. No throughput benchmark was run.
