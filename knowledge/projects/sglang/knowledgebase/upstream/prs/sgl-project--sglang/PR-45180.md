# [Feat] diffusion/minimax-h3: Add an online FP8 video VAE decoder

[Upstream PR](https://github.com/sgl-project/sglang/pull/45180) · state: open · merged: False

## Original PR description

## Motivation

The MiniMax-H3 video VAE decode is dominated by its 36 ViT decoder blocks: 144 FP16 linears (`attn.to_qkv`, `attn.to_out`, `ff.w1`, `ff.w2`) run over every tile of every window, and there is no quantized checkpoint for the VAE. On 4x RTX PRO 5000 the decode stage takes 3.26 s of a 30 s five-step 768p request.

This PR converts those 144 linears to W8A8 FP8 once at load behind `--component-quantizations.video_vae fp8`: per-output-channel weight scales, dynamic per-token activation scales and the shared `apply_fp8_linear` dispatch, the recipe the DiT's online `--quantization fp8` already uses. The decode stage drops by 40% at a worst-frame PSNR of 51 dB against the FP16 decoder. It is a lossy, deployment-level option outside the quality levels: opt-in by flag, it changes the output at every level including `exact`, and the docs say so.

Stacked on #45179: until that merges the base is `pr/minimax-h3-vae-fast-path` and the diff shows its commit too; this PR's own change is the last commit. The FP8 decoder runs on #45179's batched decode and output kernels.

## Modifications

Shared FP8 linear (`runtime/layers/quantization/online_fp8_linear.py`):

- `OnlineFP8Linear.from_linear` quantizes a prepared FP16/BF16 CUDA `nn.Linear` with `per_token_group_quant_fp8(weight, in_features)` (per-output-channel e4m3 weights, the online recipe of `Fp8LinearMethod`), keeps the bias and runs `apply_fp8_linear` with dynamic per-token activation scales (CUTLASS / tuned-Triton dispatch). `forward_quantized` takes rows a fused producer already quantized (`input_scale`, `pre_quant_output_dtype`). Inference-only; dtypes are pinned across `.to()`.

H3 install (`minimax_h3_video_vae/fp8.py`, `loader/component_loaders/vae_loader.py`, `models/vaes/minimax_h3.py`, `configs/pipeline_configs/minimax_h3.py`):

- The flag reaches `MiniMaxH3VideoVAE.quantize_decoder_fp8` from the VAE loader before `optimize_vae`. `install_fp8_block_linears` validates the released 36-block / 144-linear scope (shapes and biases) before replacing anything, requires resident prepared FP16 weights, swaps the linears and decides once (`structure_reject_reason`) whether the blocks can run on the fused producers. Only those four linears per block change: the encoder, the patch embedding, the norms, the attention core (weightless Q/K RMSNorm + RoPE and SDPA) and the decoder output projection `proj_out` keep their precision. No other VAE accepts the option.
- Startup validation: `fp8` only; `--component-quantization-ignored-layers.video_vae` is rejected instead of silently ignored; CUDA SM100+, the FP16 decode autocast recipe (no `--component-precisions.video_vae`, no `--disable-autocast`) and a resident video VAE are required. The validated `quality: "high"` fingerprint gains `video_vae_quantization=None`, so a server started with the flag rejects `high` requests at admission.

Fused producers (JIT, SM100+; `kernels/jit/csrc/diffusion/minimax_h3_vae_residual_norm.cuh`, `silu_mul_quant_fp8.cuh`):

- `minimax_h3_vae_residual_rmsnorm_fp8` (FP32 residual update + RMSNorm + dynamic per-token e4m3 quantization), `minimax_h3_vae_rmsnorm_fp8` for the decoder input, `minimax_h3_vae_residual_layernorm` (the last residual folded into the output LayerNorm) and `silu_mul_quant_fp8` under `kernels/ops/diffusion/quantization/` (`silu(gate) * up` quantized without the 16-bit round trip). The quantization epilogue follows `per_token_quant_fp8`.
- `fused_decoder.block_forward` feeds each block from these and reuses `fused_inplace_qknorm_rope` for the weightless Q/K RMSNorm+RoPE. The producers run whenever the FP8 decoder is installed, at every quality level; per-call admission looks only at tensors (device, FP32 3-D input, rope table, no mask, no grad / compile / stream capture) and otherwise falls back to the eager FP8 path. The attention runs on the block's configured backend (`torch_sdpa` by default); it does not go through the cuDNN SDPA rebinding of the FP16 `lossless` path, so pass `--component-attention-backends video_vae=torch_cudnn_sdpa` to keep it on cuDNN.

Runtime weight updates and the decode-dtype store:

- `MiniMaxH3VideoVAE.validate_weight_update_source` rejects `/update_weights_from_disk` and `/update_weights_from_tensor` requests that include `video_vae` while the FP8 decoder is installed, before any weight is written: the updater's in-place copy would overwrite the e4m3 payload and leave the per-channel scales stale while reporting success. `WeightsUpdater` now runs the weight-update hooks on any module that defines them (previously `BaseDiT` only); without FP8 the VAE keeps taking updates.
- Applies to every MiniMax-H3 resident start, FP8 or not: `vae_loader._hold_decoder_weights_in_decode_dtype` writes and adopts the file-backed decode-dtype store only while the component's parameters live on the host. A store left by a host start (`--performance-mode auto` below 120 GiB) was otherwise adopted by a later resident start, which moved the CUDA FP16 decoder weights back to host mappings and failed the FP8 install; resident starts also no longer write an empty store.

Docs: cookbook section "Advanced: online FP8 video VAE decoder (deployment-level, lossy)" and the deployment-details bullet; the CLI reference rows for `--component-quantizations`; kernels README; `existing-fast-paths.md`; performance skill.

Tests:

- GPU (SM100+): `test/registered/kernels/ops/diffusion/test_minimax_h3_vae_fp8_decoder.py`: `OnlineFP8Linear` against the dequantized math and `forward_quantized` against `forward` on pre-quantized rows; two real decoder blocks fused vs eager FP8 on `TORCH_SDPA` and `TORCH_CUDNN_SDPA` (relative RMS < 1%, cosine > 0.99995); the installer swaps exactly the 144 linears and keeps `proj_out` / `x_embedder` FP32, and the installed decoder refuses a `WeightsUpdater` tensor update with payload and scales untouched. `test_minimax_h3_vae_fp8_producers.py`: against an eager reference (`F.rms_norm` / `F.layer_norm` / `F.silu`, then the dynamic per-token e4m3 quantizer), scales within fp32 rounding (rtol 3e-6), >= 99.9% identical e4m3 bins and a half-ulp bound on the dequantized values (shared `discrete_flip_rate` helper); FP32 residual / LayerNorm outputs within atol 4e-6 / rtol 3e-5.
- CPU: `test_server_args.py` (fp8 only, ignored layers rejected, SM100 / FP16-autocast / resident requirements), `test_vae_loader.py` (only the H3 video VAE admits the override, quantized before `optimize_vae`; with a CUDA device of any SM, a host-start store does not pull the FP8 decoder to the host), `test_vae_decoder_store.py` (a resident start neither adopts nor writes a store), `test_minimax_h3_vae_fp8_weight_update.py` (tensor and disk updates rejected before any write, a decoder without FP8 keeps taking updates).
- `test/registered/kernels/benchmark/diffusion/bench_minimax_h3_vae_fp8_producers.py`.

## Accuracy Tests

Not bit-identical by design. Setup as in #45179: 4x RTX PRO 5000 (SM120), TP2 + Ulysses2, t2va 768p 16:9 5 s, 5 steps, seed 1101, default `torch_sdpa` for the video VAE; the reference is `main` (62cee1b15c, the rebase base) at the same quality level, so the DiT trajectory is identical and only the VAE differs. ffmpeg PSNR / SSIM on the decoded frames, audio compared as a hash. Two or three runs per row produced identical outputs.

| Decoder | Request | worst frame PSNR | mean PSNR | SSIM min | Audio |
|---|---|---:|---:|---:|---|
| FP8 | `lossless` (default) | 51.4 dB | 51.9 dB | 0.995 | identical |
| FP8 | `exact` | 51.3 dB | 51.8 dB | 0.995 | identical |
| FP16, #45179 | `lossless` | 52.1 dB | 52.6 dB | 0.995 | identical |

On this clip the FP8 decoder costs about 0.7 dB on top of the FP16 batched decode; the fused producers (both FP8 rows) and the tile batching (the `lossless` row) do not add to it. On fl2va (first-frame conditioning) the previous revision of this branch measured a worst frame of 44.0 dB, next to 44.2 dB for its FP16 decode against the same reference; that clip's VAE-only difference is larger for both decoders.

Runtime weight update, live 4x SM120 server: before the fix, updating `video_vae` with the checkpoint's own weights reported success and the next request decoded at 26.8 dB worst-frame PSNR (SSIM min 0.52) against the pre-update output; with it the request is rejected before any write and the frames are bit-identical. Decode-dtype store: a `--performance-mode auto` start followed by an FP8 resident start now loads and decodes in the same time as a store-disabled run (before, the loader aborted).

Tests on SM120: `test_minimax_h3_vae_fp8_decoder.py` + `test_minimax_h3_vae_fp8_producers.py` + `test_minimax_h3_vae_output.py` + `test_model_fast_paths.py -k "minimax_h3 or h3_vae or fp8_linear"`, 45 passed. The MiniMax-H3 and VAE unit files pass on CPU (387 cases, with a CUDA device visible for the two store cases). No CI case compares the FP8 decoder with the FP16 decoder's output yet; the fidelity numbers above come from the end-to-end runs. The kernel tests are registered on the `4-gpu-b200` lane, so this PR's CI is their first run on SM100.

## Speed Tests and Profiling

Environment and protocol as in #45179 (4x RTX PRO 5000 72 GB SM120 PCIe, torch 2.14.1+cu130, CUDA 13.0, sgl-kernel 0.4.9, flashinfer 0.7.1; TP2 + Ulysses2, t2va 768p 5 s, 5 steps, blocks interleaved, `SGLANG_DIFFUSION_SYNC_STAGE_PROFILING=1`). Decode = `MiniMaxH3DecodingStage` duration; peak = runtime peak reserved.

| Decoder | Request | decode ms, median (min–max) | vs `main` same level | vs FP16 #45179 same level | peak reserved |
|---|---|---:|---:|---:|---:|
| FP16, `main` | `lossless` | 3258 (3252–3264), n=2 | | | 58120 MB |
| FP16, #45179 | `lossless` | 3158 (3147–3162), n=3 | −3.1% | | 58120 MB |
| FP8 | `lossless` | 1931 (1931–1937), n=3 | −40.7% | −38.9% | 56192 MB |
| FP16, `main` | `exact` | 3404 (3402–3406), n=3 | | | 58120 MB |
| FP16, #45179 | `exact` | 3400 (3391–3409), n=3 | within noise | | 58120 MB |
| FP8 | `exact` | 1998 (1989–2007), n=2 | −41.3% | −41.2% | 56190 MB |

Numbers are on the rebase base 62cee1b15c; `main`'s `exact` decode is slower than its `lossless` one there because #44690 dropped the Triton QK RMSNorm+RoPE the ViT attention ran at every level (see #45179). The `exact` row is the FP8 GEMMs plus the fused producers; `lossless` adds the tile batching (−3%). The previous revision gated the producers by quality level, and its `exact` row (FP8 GEMMs with the eager producers) measured 2098 (2096–2107) ms on 57db5089c2, so the producers are worth about 100 ms, or 5% of the FP8 decode time. End to end, the five-step `lossless` request moves from 30.2–30.3 s to 29.0 s (`exact`: 30.5–30.6 s to 29.2 s).

Kernel microbenchmarks (`bench_minimax_h3_vae_fp8_producers.py`, one SM120 GPU, width 2048 / FFN 8192; `split` is the eager FP32 chain followed by `per_token_quant_fp8`):

| rows | op | split µs | fused µs |
|---:|---|---:|---:|
| 1792 | residual_rmsnorm_fp8 | 45.5 | 20.3 |
| 1792 | residual_layernorm | 42.6 | 20.4 |
| 1792 | rmsnorm_fp8 | 21.9 | 14.2 |
| 1792 | silu_mul_quant_fp8 | 66.1 | 50.8 |
| 7168 | residual_rmsnorm_fp8 | 261.7 | 132.1 |
| 7168 | silu_mul_quant_fp8 | 489.3 | 244.6 |

Not measured on the other SM100+ hardware the option accepts (B200 / B300, GB200 / GB300, RTX 5090 and the other SM120 cards); Hopper is rejected at startup. The benchmark file is registered on the `1-gpu-large` lane, where every row skips.
