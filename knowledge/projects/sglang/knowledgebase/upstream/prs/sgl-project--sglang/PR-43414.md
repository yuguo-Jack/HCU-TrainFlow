# [diffusion] Make warmup preload components and margin configurable

[Upstream PR](https://github.com/sgl-project/sglang/pull/43414) · state: open · merged: False

## Original PR description

## Motivation

Closes #41126 (follow-up to #40761). Which components stay on device after warmup is hard-coded through `preferred_ready_after_request`, and the warmup preload budget check uses a fixed 1 GiB margin. Users can't turn the preload off, pick the components, or leave more room for the first real request's activations.

## Modifications

- `--warmup-preload-components` (`auto` default | `none` | comma-separated component names). Applied in `ComponentResidencyManager.finish_request` for warmup batches only; regular requests keep the pipeline hints. Explicit `--component-residency` still wins, and the single-DiT rule is unchanged. Names that warmup never used log a warning.
- `--warmup-preload-margin-gib` (default 1.0) replaces `_WARMUP_PRELOAD_MARGIN_BYTES`. It reaches the strategy through `ResidencyState.warmup_preload_margin_bytes`.
- Validation: no empty names in the list, margin must be finite and non-negative (`nan` / `inf` are rejected with the other CLI errors), `AUTO`/`NONE` are case-insensitive.
- Defaults keep the current behavior.
- Docs: both flags are described in the Component Residency section of the diffusion CLI docs.

Not in scope: reserving activation/workspace memory automatically (the issue's last point). A larger margin is the manual knob for that for now.

## Accuracy Tests

No change to model outputs.

## Speed Tests and Profiling

No change with the defaults.

## Tests

New CPU unit tests in `test/unit/test_component_residency.py` (15 cases):
- the margin threshold in `ComponentOffloadStrategy.finish_request`
- each policy's effect on `preferred` for warmup vs. regular requests
- the margin reaching the request state
- CLI parsing and validation

Ran on ubuntu with CPU torch: all new cases pass. On main, 11 of them fail; the other 4 check that the default behavior is unchanged. The four `test_warmup_*_peaks` tests in that file also fail on untouched main in this CPU-only environment, so they're unrelated to this change.
