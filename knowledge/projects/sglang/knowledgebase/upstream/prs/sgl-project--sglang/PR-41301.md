# [Perf] [NVIDIA] quantization: Add tuned W8A8 block-FP8 GEMM configs for H20

[Upstream PR](https://github.com/sgl-project/sglang/pull/41301) · state: open · merged: False

## Original PR description

## Motivation

`python/sglang/kernels/ops/gemm/configs` already treats H20 as a supported device
(26 config files for `[128,128]` blocks and channelwise FP8), but the block-`[32,32]` W8A8 path
has only the ten `NVIDIA_H200` entries for these shapes. On H20, `get_w8a8_block_fp8_configs` therefore misses
for every shape and each call falls back to the default tile config:

```python
config = {
    "BLOCK_SIZE_M": 64, "BLOCK_SIZE_N": block_size[0], "BLOCK_SIZE_K": block_size[1],
    "GROUP_SIZE_M": 32, "num_warps": 4, "num_stages": 3,
}
```

With `BLOCK_SIZE_K == block_k == 32` the K loop is fully serial, and at the small M this kernel
actually sees (decode M≈6, speculative-verify M=384, prefill M≤8192) the grid has too few CTAs to
fill the machine. The fallback is not silent — it logs a warning on every miss:

```
Using default W8A8 Block FP8 kernel config. Performance might be sub-optimal!
```

On our 8×H20 deployment that warning fired 80 times per server start before this change.

## Modifications

Adds ten new config files, one per (N, K) shape, each covering 27 M tiers (`M = 1 … 8192`):

```
configs/N={512,576,1280,1536,1792,4096,5120,25600},K={288,1024,1280,5120,6144,15360},
device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[32, 32].json
```

The ten tables are purely additive: deleting them restores the previous behaviour. One existing
file is touched — `kernels/ops/gemm/fp8_kernel.py` — so that enabling these tables cannot break
deterministic inference (see *Deterministic inference* below). Schema is identical to the existing
`NVIDIA_H200` files for the same shapes, including the use of `SWAP_AB` / `SPLIT_K` where they win.

Produced with the in-tree tuner:

```bash
python -m benchmark.kernels.quantization.tuning_block_wise_kernel \
    --block-n 32 --block-k 32 --input-type fp8 \
    --save-path python/sglang/kernels/ops/gemm/configs
```

### When is this table read?

On SM90, block-`[32,32]` W8A8 GEMMs take the native DeepGEMM path by default since
#42604 (merged 2026-10-10, after this PR was opened):

- `dispatch_w8a8_block_fp8_linear` (`srt/layers/quantization/fp8_utils.py`) returns
  `deepgemm_w8a8_block_fp8_linear_with_fallback` when `weight_block_size == [32, 32]`,
  `SGLANG_ENABLE_JIT_DEEPGEMM` is on (the default), and the backend is `auto` or `deep_gemm`.
- `_deepgemm_block_fp8_supported` accepts any `[32, 32]` shape with `n % 8 == 0 and k % 32 == 0`
  on SM90. All ten shapes here satisfy that.

So the tables are read when the **Triton block-FP8 backend** is in use: with
`--fp8-gemm-backend=triton`, with `SGLANG_ENABLE_JIT_DEEPGEMM=0`, when DeepGEMM is unavailable
for the build, or when its runtime fallback triggers. The Triton backend is the default on
non-SM90 hardware and on any SM90 build without DeepGEMM.

This matters for reading the numbers below: they are Triton-backend numbers, measured on the
default at the time this PR was opened. On today's H20 default path this PR changes nothing that
runs — the same is true of the ten `NVIDIA_H200` block-`[32,32]` tables already on `main`.

One case reaches these tables without an explicit backend choice: `triton_w8a8_block_fp8_linear`
deliberately bypasses its bf16-weight expansion when `is_batch_invariant_mode_enabled()`, which
`--enable-deterministic-inference` turns on (`model_runner.maybe_enable_batch_invariant_mode`).
Under that flag the block-32 path runs the Triton matmul, reads this table, and therefore needs
the guard described next.

### Deterministic inference

`enable_deterministic_inference` promises batch-invariant ops. The lookup picks an entry by nearest
`M`, and in these files the reduction strategy changes with `M` — e.g. for `(N,K)=(1536,5120)`,
`M=96` uses `SPLIT_K=4` while `M=168` uses a single accumulator — so the same row would accumulate
K in a different order depending on the batch it ran in.

`w8a8_block_fp8_matmul_triton` now drops `SPLIT_K` and `SWAP_AB` from the selected entry when
deterministic inference is enabled. `BLOCK_SIZE_K` is constant (32) across every entry of each file
added here, so once the reduction meta-parameters are gone every `M` dispatches to the same
single-accumulator kernel and a row's result is independent of its batch. The check reads
`exec.deterministic` only when the `exec` namespace is published, so standalone callers (tools, unit
tests) keep their previous behaviour instead of raising
`ValueError("config namespace 'exec' not published")`.

**Which kernel path each tier takes.** Of the 270 entries, 77 set `SWAP_AB` (10) or `SPLIT_K > 1`
(67) and so dispatch to `_w8a8_block_fp8_matmul_hopper`; the remaining 193 set neither and stay on
`select_w8a8_block_fp8_matmul_kernel`. No entry sets both. This mirrors how #39657 populates the
H200 tables: the transpose/split-K variants are used only where they measure faster, not uniformly.

## Accuracy Tests

1. **fp64 reference.** An independent microbenchmark dequantizes the same fp8 operands with the same
   fp32 block scales and matmuls in fp64, so each candidate is checked for *accuracy*, not merely for
   agreement with the deployed default.
2. **Numerically lossless end-to-end.** `accept_len` — the speculative-decode accept length, a
   sensitive end-to-end correctness signal — is unchanged at 2.66–2.67 across all three arms measured
   (no configs / M≤64 configs / 27-tier configs).
3. **Candidate-vs-deployed parity.** For the 27-tier tables, 38 candidate configs were compared against
   the deployed configuration: **35 bit-identical, 3 differing by 1 bf16 ulp**.
4. **Caveat, stated plainly.** The 67 entries with `SPLIT_K > 1` accumulate K in separate fp32
   partials, so they are not bit-identical to the single-accumulator kernel by construction; this is
   why (1) and (2) exist. The remaining 203 entries use a single accumulator. The H200 files use
   `SPLIT_K` / `SWAP_AB` in the same way.

No model-output regression is claimed beyond the above.

The CPU config-table test from the first revision
(`test/registered/cpu/quant/test_w8a8_block_fp8_configs.py`) has been removed at review request; it
is not part of this PR.

## Speed Tests and Profiling

8× NVIDIA H20 (SM90, 96 GB), `torch 2.11.0+cu130`, `triton 3.6.0`,
`torch.cuda.get_device_name()` = `NVIDIA H20`, DeepSeek-V4.1-Flash at TP=8 / EP=8.
Workload: `vllm bench serve`, sharegpt 100 prompts, seed 42, temperature 0, closed-loop concurrency.
These figures come from one deployment, not a general claim.

**Microbenchmark, per shape, M=1** (CUDA-graph capture+replay timing): 4.3–6.7×; 3258 → 989 µs summed
over the ten shapes.

**End-to-end, before → after (output tok/s):**

| concurrency | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| default fallback | 127.53 | 204.86 | 316.27 | 458.63 | 586.42 | 757.83 | 999.78 |
| with H20 tables | **172.79** | **258.46** | **368.74** | **507.44** | **640.63** | **814.80** | **1133.32** |
| delta | +35.5% | +26.2% | +16.6% | +10.6% | +9.2% | +7.5% | +13.4% |

Extending the tables from `M ≤ 64` to 27 tiers (`M ≤ 8192`) moved the high-concurrency tier further,
where the lookup had been picking a small-M config for large-M calls:

| | concurrency 64 | `ttft_p50` |
|---|---:|---:|
| `M ≤ 64` table | 1048.83 tok/s | 1539.4 ms |
| 27-tier table | **1133.32 tok/s** (+8.1%, median of 7 samples) | **1052.2 ms** (−31.7%) |

The other six concurrency tiers moved within ±1.5% of the pre-extension values.

**Runtime confirmation.** After the change the server logs `Using configuration from ... NVIDIA_H20 ...`
for all ten shapes and the "default config / sub-optimal" warning count drops from 80 to 0 per start.

## Relation to other open PRs

#41098, #41035 and #39306 add block-`[32,32]` tables for `device_name=NVIDIA_H20-3e`. Those keys are
disjoint from `NVIDIA_H20` — the config filename is an exact-match lookup on
`torch.cuda.get_device_name()`, so neither set is reachable from the other's hosts. This PR adds the
`NVIDIA_H20` set and touches no file those PRs touch.

If you would rather have a single table keyed by one name, say so and I will fold this in; the two
are otherwise independent.

Worth flagging for whoever reviews them: all three write to
`python/sglang/kernels/ops/quantization/configs/`, which does not exist on `main` and has no reader.
The block-FP8 tables are loaded from `python/sglang/kernels/ops/gemm/configs/` — see
`get_w8a8_block_fp8_configs` at `kernels/ops/gemm/fp8_kernel.py:553`, which joins
`os.path.dirname(os.path.realpath(__file__))` with `"configs"` (`:576`). Files placed under the old
path would never be opened.

