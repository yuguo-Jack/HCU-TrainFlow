# [NPU] MLA pool: index-K elision on A3, DCP pool fixes, short-pool warning

[Upstream PR](https://github.com/sgl-project/sglang/pull/42976) · state: open · merged: False

## Original PR description

## Motivation

Three small fixes to the NPU MLA KV pool, found while serving GLM-5.2 with 1M-token contexts on Ascend A3.

1. **Index-K is allocated for every layer on A2/A3, but only some layers own an Indexer.** The compact
   indexer layout (index-K only for layers that have an Indexer) was gated on `is_npu_arch35()`. Which
   layers own an Indexer depends on the model config, not on the chip, and a layer without one never
   writes index-K on any hardware. On non-arch35 chips the memory was allocated and never used.
2. **DCP on NPU: the allocator page and the index-K bound.** `_alloc_page_size` did not ask the NPU allocator, whose page is
   `page_size * dcp_size` (CUDA and HIP already do). That only changes behaviour at `--page-size 1`, which
   DSA on Ascend cannot run today (the Lightning Indexer needs a block size that is a multiple of 16), so it
   is a latent bug. Index-K writes also had no bounds check against the widened index range.
3. **A pool that cannot hold one full-length request fails late.** When the pool is smaller than
   `--context-length`, nothing is logged at startup. Long requests are refused or truncated at serving time.

## Modifications

- `kv_cache_configurator.py`, `pool_configurator.py`: drop the `is_arch35` gate on the compact indexer
  layout and on `allocate_all_layers`.
- `memory_pool_npu.py`: `set_index_k_buffer` checks writes against the widened index range (async
  out-of-bounds check, active with `SGLANG_ENABLE_ASYNC_ASSERT=1`).
- `allocation.py`: `_alloc_page_size` returns the NPU allocator's page size under DCP, as on CUDA/HIP.
- `KVCacheConfigurator._warn_if_pool_cannot_hold_context`: a startup warning when the pool holds fewer
  request tokens than `--context-length`. It counts request tokens (`logical_token_capacity`), not per-rank
  rows, so a DCP pool is not flagged for its smaller per-rank row count. It skips the draft worker.
- `pool_configurator.py`: a comment on why the indexer term scales with `dcp_size`.

**Behaviour change for users without DCP:** item 1 has no flag. On A2/A3, DSA models now allocate
index-K only for the layers that own an Indexer. Everything else in this PR is DCP-only or a warning.

## Accuracy Tests

No forward-path change. Index-K for layers without an Indexer was never read, so outputs are unchanged.

## Speed Tests and Profiling

No speed change. The gain is memory. For GLM-5.2 (78 KV layers, 21 with an Indexer, bf16 index-K
128 × 2 B per token per layer), index-K drops from 19,968 B to 5,376 B per token, and total KV per token
from 109,824 B to 95,232 B. At the same memory, the pool holds about 15% more tokens. This is arithmetic
from the pool layout, not a served A/B.

## Tests

- `test/registered/unit/mem_cache/test_npu_index_k_elision.py` (CPU): on A2/A3 the memory budget and the
  pool count the same Indexer layers. Fails if either side's `is_arch35` gate comes back.
- `test/registered/unit/mem_cache/test_pool_context_warning.py` (CPU): the warning fires when the pool is
  short, and a DCP pool is measured in request tokens, not per-rank rows.
