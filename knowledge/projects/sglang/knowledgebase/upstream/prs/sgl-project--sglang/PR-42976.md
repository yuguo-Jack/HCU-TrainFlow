# [Fix] [NPU] mla-pool: DCP allocator page and index-K bound, short-pool warning

[Upstream PR](https://github.com/sgl-project/sglang/pull/42976) · state: closed · merged: True

## Original PR description

## Motivation

Small fixes to the NPU MLA KV pool, found while serving GLM-5.2 with 1M-token contexts on Ascend A3.

1. **DCP on NPU: the allocator page and the index-K bound.** `_alloc_page_size` did not ask the NPU allocator,
   whose page is `page_size * dcp_size` (CUDA, HIP and XPU already do). This only changes behaviour at
   `--page-size 1`, which DSA on Ascend cannot run today (the Lightning Indexer needs a block size that is a
   multiple of 16), so it is a latent bug. Index-K writes also had no bounds check against the widened index range.
2. **A pool that cannot hold one full-length request fails late.** When the pool is smaller than
   `--context-length`, nothing is logged at startup. Long requests are refused or truncated at serving time.

This PR first also removed the `is_arch35` gate on the compact index-K layout. #44436 has since made the same
change on main, so that part is gone from this diff. Only a test that both sides agree is left (see Tests).

## Modifications

- `allocation.py`: `_alloc_page_size` returns the NPU allocator's page size under DCP, as on CUDA/HIP/XPU.
- `memory_pool_npu.py`: `set_index_k_buffer` checks writes against the widened index range (async
  out-of-bounds check, active with `SGLANG_ENABLE_ASYNC_ASSERT=1`).
- `TpModelWorker.get_worker_info`: a startup warning when the served `kv_capacity` is below `--context-length`.
  It is checked there because that is the final served value, so DCP and page-interleave widening are counted.
- `kv_cache_configurator.py`, `pool_configurator.py`: comments on why the NPU DCP allocator is widened and why
  the indexer term scales with `dcp_size`.

**Behaviour change for users without DCP:** none, except the new warning when the pool is short.

- OrangeRedeng · comment · 2026-10-13T15:09:43Z · [source](https://github.com/sgl-project/sglang/pull/42976#discussion_r4260409160)

File: `python/sglang/srt/mem_cache/kv_cache_configurator.py` · line None

For hybrid  sliding-window attention with `--enable-unified-memory`, the warning uses `sizes.max_total_num_tokens`, which is a sizing estimate rather than the effective serving capacity.

`ModelRunner` uses `hybrid_swa_token_capacity()` based on `allocator.size_full`, optionally capped by `max_total_tokens`. This mismatch can produce a false warning.

For example, with an estimated capacity of 80K tokens, an effective capacity of 130K, and `context_len=100K`, the warning incorrectly reports insufficient KV memory.

**Suggested fix:** Use the initialized allocator's effective capacity, consistent with serving, while preserving DCP/KV-sharding scaling and draft-worker exclusion.
