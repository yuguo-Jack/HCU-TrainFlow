# [NOT READY][Feat] [NVIDIA] speculative: Opt-in CUDA graphs for the EAGLE post-verify step and the GDN prefill extend

[Upstream PR](https://github.com/sgl-project/sglang/pull/45436) · state: closed · merged: False

## Original PR description

## Motivation

Two parts of SGLang's serving step still run outside CUDA graphs:
- After the EAGLE target-verify graph replays, the verify's post-section runs eagerly every round: sampling and acceptance, the commit outputs and, on hybrid models, the mamba state commit.
- On hybrid models with GatedDeltaNet (GDN) layers, such as Qwen3.5, breakable prefill CUDA graphs break at every GDN layer. KDA layers are already captured (`linear/kda_prefill_graph.py`).

This PR adds SGLang's own CUDA graphs for both. Each sits behind an environment variable that is off by default:
- `SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH`: the EAGLE verify's post-section in CUDA graphs.
- `SGLANG_ENABLE_GDN_PREFILL_GRAPH_EXTEND`: the GDN extend inside breakable prefill CUDA graphs.

With both off, nothing changes. Nothing here needs a megakernel. The NVIDIA megakernel binding for Qwen3.5, a separate PR stacked on this one, runs its entries inside these graphs.

## Modifications

**1. Post-verify CUDA graphs for the EAGLE verify (`speculative/eagle_post_verify_graphs.py`, new; `eagle_worker_v2.py`, `eagle_worker_common.py`, `eagle_utils.py`, `spec_utils.py`, `frozen_kv_mtp_worker_v2.py`)**
- With `SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH=1`, `EAGLEWorkerV2` creates `EaglePostVerifyGraphs` in `init_attention_backends`, and so do the standalone and frozen-KV MTP workers built on it. The verify hands every round to the graphs through `run_eagle_verify(post_verify_graphs=...)`.
- The switch is ignored, with a warning, where the graphs cannot run: without CUDA, for a tree draft (top-k above 1), and under DP attention. Each key is captured at its own first rounds, which attention-DP ranks do not reach together, and a capture may end in a collective over the TP group.
- The graphs capture sampling and acceptance (`eagle_sample`), the commit outputs (`prepare_verify_commit_outputs`) and, on a side stream, the mamba state commit (`commit_mamba_states_after_verify`). The worker joins the side stream once the draft extend is enqueued.
- There is one set of graphs per key: batch size, sampling mode, forced acceptance, tracking, draft token count, tree depth and the verify logits buffer. Two slots alternate per key, so one round's outputs stay valid while the host reads them. A key's first four rounds run eagerly as warm-up, and each slot is captured after that. At most 64 keys are kept; a batch past them runs eagerly.
- A batch a graph cannot reproduce runs SGLang's eager path: grammar, penalties, logit bias, per-request seeds, min-p, watermarks, HiSparse, rejection sampling, or a target verify that ran without a CUDA graph. A KV pool whose rejected c128 draft states the eager verify clears (DeepSeek-V4) always takes the eager path.
- The forced acceptance length (`SGLANG_SIMULATE_ACC_LEN`) is one stream. With the graphs on, the worker seeds a generator from the server seed, and the graphs and the eager verify both draw from it, once per round. Every rank therefore forces the same lengths, whatever else uses its global RNG, and a run whose rounds mix graph and eager paths forces the lengths of an all-eager run. In the graphs, the length reaches the device through a pinned ring, and `eagle_sample(simulated_acc_len=)` applies it with `generate_simulated_accept_index_device`, which writes what the host-length version writes. With the graphs off, the eager verify draws from the global CPU RNG, as before: `run_eagle_verify`, `eagle_sample` and `generate_simulated_accept_index` pass the generator through, and `None` keeps the global RNG.

**2. The GDN extend in breakable prefill CUDA graphs (`linear/gdn_backend.py`, `linear/gdn_prefill_graph.py`, new; `fla/chunk.py`, `fla/chunk_o.py`, `fla/gdn_prefill_graph_track.py`, new; `linear/kernels/gdn_triton.py`)**
- The FLA chunk kernels take optional, caller-built chunk tables, and the Triton GDN extend passes them through. Without them the eager path is unchanged.
- `gdn_prefill_graph.py` holds a captured bucket's static tables, refilled before each replay by one host-to-device copy. `gdn_prefill_graph_track.py` takes the prefix-cache snapshots of conv windows and SSM states inside the graph, converting a BF16 chunk state before the store.
- With `SGLANG_ENABLE_GDN_PREFILL_GRAPH_EXTEND=1`, `GDNAttnBackend.supports_prefill_graph_extend()` holds where the setup can run the extend on static tables, as KDA's does. Breakable prefill graphs then capture each GDN layer's extend instead of breaking at it.
- Only the target's extend is captured. A draft model's prefill graphs keep their eager path; Qwen3.5's MTP draft has no GDN layer, so it would only refill the tables.
- Any other setup keeps breaking at every layer: a platform other than CUDA, a GDN kernel other than Triton, multi-item scoring, a mamba chunk size other than the delta rule's, non-contiguous state pools, or captured buckets that change `chunk_fwd_o`'s block size.

Both switches are environment variables in `environ.py`, next to comparable experimental toggles: `SGLANG_ENABLE_METADATA_GLUE_GRAPH`, and KDA's `SGLANG_DISABLE_KDA_PREFILL_GRAPH_EXTEND`. They are separate because the GDN extend does not need speculative decoding.

### Known limits

- Only `EAGLEWorkerV2` and its subclasses use the post-verify graphs. The multi-layer EAGLE and UNO workers keep the eager verify.
- The post-verify graphs are captured while serving, after the KV pool is sized, so their memory comes from what the pool left free: up to 64 keys, with two slots each. A capture synchronizes the device and empties the allocator cache, so each new key stalls serving once.
- A capture that fails raises; there is no eager fallback.
- On a model without mamba state the side-stream commit graph is empty, and each replay still records its two events.

## Accuracy Tests

With both switches off, the default, no new path runs. The post-verify graphs and the forced-length generator exist only with `SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH`, and GDN layers keep breaking prefill graphs unless `SGLANG_ENABLE_GDN_PREFILL_GRAPH_EXTEND` is set.

CPU tests, one per behaviour:
- the post-verify switch turns the graphs on for every verify of a setup they can run, and leaves them off without CUDA, for a tree draft and under DP attention;
- only batches a graph can reproduce take the graphs, and a KV pool with c128 draft states never reaches them;
- with the graphs on, graph rounds and eager rounds draw one forced-length stream, the same on every rank; with them off, the eager draws equal the global RNG's and leave it in the same state;
- the GDN switch captures the target's extend only where the setup supports it, and never a draft's.
