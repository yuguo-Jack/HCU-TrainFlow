# [Scheduler] Throttle waiting-prefix refresh by forward count, not wall time

[Upstream PR](https://github.com/sgl-project/sglang/pull/43512) · state: closed · merged: False

## Original PR description

## Motivation

The waiting-prefix refresh from #41593 throttles on each rank's own `time.monotonic()` (0.5 s). Ranks on opposite sides of the 0.5 s mark refresh on different calls, so their radix-tree LRU order, and later their evictions, diverge. This caused two failures:

- `test_unified_radix_cache_hicache_pp_kl.py` (TP2 + PP2, HiCache, 4-gpu-h100): the rank consensus checker caught PP0 evicting 27 tokens and PP1 48. Reproduced on 8x H200 with a per-rank refresh log: PP0 and PP1 disagreed at calls 93 and 94, and about 16 s later the checker fired with CI's exact tokens and hashes. Forcing PP1 never to refresh also trips the checker; `SGLANG_ENABLE_WAITING_PREFIX_REFRESH=0` ran clean 4/4.
- `TestInklingSmallCacheConsistencyNightly` (TP8, 8-gpu-b200) hung: it passed in the 10-07 nightly and hung on 10-09, the first nightly with #41593. Reproduced on 8x B300 with a per-rank refresh log: ranks disagreed on 495 of 7561 calls while seeing the same queue length, starting before the test's jitter is on. The last disagreements split the ranks {TP1, TP5} vs the rest, the same split as the hang dump (12-request batch vs 1).

## Modifications

- Throttle on `Scheduler.forward_ct`, which is identical on every rank: at most one refresh per 32 forwards. `forward_ct=None` skips the refresh.
- `@rank_consensus` on `UnifiedRadixCache.touch_prefix`, so a divergence is reported at the touch itself.
- The static refresh checks are computed once in `__init__`; the decode-mode check stays per call because a PD role switch can change it. Two test files now publish the runtime context.
- Regression test: the same calls, made back to back and 0.6 s apart, must refresh identically.

- mmangkad · comment · 2026-10-11T07:33:43Z · [source](https://github.com/sgl-project/sglang/pull/43512#issuecomment-6106718875)

Closing this since #43479 landed first and fixes the same divergence.

Just leaving this here for the record: the two PRs count differently. #43479 refreshes every 32 `calc_priority` calls, this one every 32 forwards. When the server is saturated, calls get sparse, so the call-based refresh barely runs. I ran a quick `bench_serving` comparison (`generated-shared-prefix`, 4k shared prefix, 128 output, Qwen3-4B on 1x H200, 4 running slots, 64k-token KV pool, avg of 2 seeds):

| Requests | Refresh | Cache hit | Duration | Mean TTFT |
|---|---|---|---|---|
| 128 | off | 27.9% | 23.7 s | 11.6 s |
| 128 | every 32 calls (#43479) | 30.8% | 23.5 s | 11.5 s |
| 128 | every 32 forwards (this PR) | 51.8% | 21.7 s | 10.8 s |
| 512 | off | 16.0% | 97.4 s | 48.6 s |
| 512 | every 32 calls (#43479) | 17.6% | 96.9 s | 48.4 s |
| 512 | every 32 forwards (this PR) | 39.6% | 89.9 s | 45.1 s |

So under load, the call-based version behaves pretty much like refresh off, while counting forwards gets ~21 points more cache hit and ~7% more throughput. It only matters when things are backed up, but it might be worth a small follow-up at some point.
