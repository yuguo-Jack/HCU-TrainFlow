# [Fix] session: Keep a retracted streaming turn in flight

[Upstream PR](https://github.com/sgl-project/sglang/pull/46275) · state: open · merged: False

## Original PR description

## Motivation

`retract_decode` releases a streaming-session turn through `claim_kv_row` → `StreamingSession.try_cache_finished_req`. That keeps the turn's record in the session slot, which is intended, but it also calls `Session.finish_req` as if the turn had finished. The turn is still in flight: it goes back to the waiting queue and resumes later. This has two consequences.

1. **The in-flight guard is lost.** `finish_req` clears `_inflight`, so `create_req` stops rejecting new turns ("Streaming session already has an active request"). A new turn on that session is accepted while the retracted one is still pending. Streaming turns share their token arrays, so it extends them in place: the retracted turn's `origin_input_ids` changes underneath it, and the two turns then run on the same slot.
2. **An aborted turn becomes the rollback point.** `finish_req` also moved `req_nodes` and the `committed_*` lengths to the retracted turn. If that turn is aborted afterwards (client cancel, timeout), the next turn's history keeps the aborted turn's prompt and partial output. A turn aborted while running is rolled back and re-prefilled from the last finished turn instead, as the `try_cache_finished_req` docstring describes.

A deterministic reproduction on `main` (efc9849520): a real `Session` with a real `UnifiedRadixCache` on a CPU fixture. Turn 1 = 8 prompt tokens plus 3 outputs, finished. Turn 2 = `[20, 21]`, decodes 2 tokens, then gets retracted.

```
A  concurrent turn while t2 is retracted: ACCEPTED, t2 prompt rewritten to 16 tokens (was 13)
B  turn 3 history: LEAKED aborted turn: [20, 21, 201, 202, 30]
```

With this PR:

```
A  concurrent turn while t2 is retracted: rejected
B  turn 3 history: rolled back to turn 1
B  sanity_check passed
```

## Modifications

- `try_cache_finished_req` calls `Session.finish_req` only when the request has finished. A retracted turn keeps the record in the slot as before, and the slot remembers it in `SessionSlot.retracted_rid`.
- New `StreamingSession.release_retracted_turn(req)`, also exposed on `UnifiedRadixCache`. When the aborted request is the turn the slot holds as retracted, it drops the slot with `release_session`, so the next turn re-prefills from the last finished turn. It is called from both places that abort a waiting turn: `Scheduler._release_aborted_request`, and the pre-abort branch of `find_active_slot`.
- Tests in `test_streaming_session_unit.py`:
  - `test_retracted_turn_stays_in_flight`: retraction must not call `finish_req`.
  - `test_aborted_retracted_turn_drops_its_record[scheduler_abort|preabort_match]`: the slot is released and its row and KV are freed.
  - On `main`, all 3 fail. With this PR, `test_streaming_session_unit.py` and `test_session_token_share_unit.py` pass (19 tests).

## Benchmarking and Profiling

Not applicable. The extra work is a dict lookup on the abort path.

I found this with a CPU scheduler driver. It runs the real `Scheduler`, `UnifiedRadixCache` and `SessionController` with random multi-turn streaming sessions, uses `SGLANG_TEST_RETRACT=1` to force retraction, and checks that the token fed at each position matches the sequence, that every prefix slot holds the right token, and that `out_cache_loc` matches `req_to_token`. Over 60 seeds each in normal and overlap scheduling on `main`, it saw:

- 36 runs fed the wrong token;
- 5 runs had a prefix slot holding another sequence's token;
- 2 runs had an `out_cache_loc` mismatch;
- 2 runs crashed with "KV page use-after-free".

With this change and #46273 (the dfs-weight crash, which this driver also hits), all of these went to 0 on the same seeds. Both trees still show the hold-and-wait stalls from session-pinned KV, the problem described in #27024, which this PR does not address.

I have not run an end-to-end streaming-session deployment.
