# [Perf] dspark: Refresh Mamba tracking once per verification step

[Upstream PR](https://github.com/sgl-project/sglang/pull/47494) · state: closed · merged: True

## Original PR description

## Codex notes

### Motivation

Every non-idle DSpark decode step calls `prepare_mamba_track_for_verify` in the worker and again in `DFlashVerifyInput.prepare_for_verify`. With Mamba prefix-cache tracking enabled, this prepares the same tracking indices twice before the target forward.

### Modifications

Remove the worker's earlier call and its unused import (two production-line deletions). Ordinary and compact verification both reach `prepare_for_verify`, which refreshes tracking before `ForwardBatch.init_new` and before graph loading or eager metadata initialization. No intervening consumer needs the earlier refresh.

This benefits DSpark targets using radix caching with `extra_buffer` or `extra_buffer_lazy`. Eligible architectures include Kimi Linear/K3, Qwen3-Next/3.5, Nemotron-H, Falcon-H1, Granite hybrid and Inkling, when used with a compatible DSpark draft. With tracking disabled, the removed call only performed an early return.

### Accuracy tests

Fresh [B200 CI on `c617e09210`](https://github.com/sgl-project/sglang/actions/runs/41483413993) passed the registered Nemotron 3.5 NVFP4 DSpark test: **192/200 GSM8K answers correct (96%)**, zero request errors, and two responses truncated at the 16,384-token limit. This uses the published target and matching DSpark draft.

Removed the mocked verification-preparation harness. The full-model smoke and GSM8K results below were collected before this test-only cleanup; the two-line production change is unchanged.

A full-model GB300 smoke completed on head `6d6fa068e3` and main `5008726431` using NVIDIA Nemotron-3.5-Lightning-30B-A3B-NVFP4 and its matching DSpark draft, `extra_buffer` tracking, TRTLLM MHA draft attention, and full verify CUDA graphs. Both completed 19 requests at batch sizes 1, 2, 4, 8, 3, 1 with 32 output tokens each. However, two outputs differed at batch 8. A repeat of the unchanged baseline also changed two outputs at batch 3, so this run does not establish output parity or identify the cause of the differences.

Local runtime: PyTorch 2.11.0/CUDA 13.2, FlashInfer 0.7.2, CuTe DSL 4.8.0, and installed sgl-kernel 0.4.6.post1 with `SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1` (upstream expects 0.4.9). Target MoE used CuTeDSL W4A16 and draft MoE used Marlin. This was a smoke test, not an accuracy evaluation or throughput benchmark.

A subsequent 64-question GSM8K comparison with sgl-eval 0.1.3 completed on candidate `6d6fa068e3` and original base `5008726431`: **64/64 correct on candidate, 63/64 on base**. The base had one response truncated at the 8,192-token limit; candidate had none. Both had zero request errors. Each server ran on one GB300 GPU with the same Nemotron 3.5 NVFP4 target and DSpark draft, `extra_buffer` tracking, full verify graphs (maximum batch 8), disabled overlap scheduling, Triton target attention, TRTLLM MHA draft attention, CuTeDSL W4A16 target MoE, and Marlin draft MoE. Context length was 16,384. The evaluator used temperature 1.0, top_p 0.95, seed 42, and concurrency 8; reasoning was enabled by the model template. This is a small accuracy comparison, not proof of output parity, a statistically established improvement, or a throughput benchmark. The local runtime/version limitation above still applies.

### Speed tests and profiling

A GB300 microbenchmark on head `6d6fa068e3` measures the real tracking helper with CUDA mappings at batch sizes 1, 8, 32, and 128. Two calls take 112–160 µs versus 55–80 µs for one call with ordinary tracking; lazy tracking takes 89–129 µs versus 46–64 µs. These are medians of three 200-iteration measurements per variant in an alternating order, with CUDA synchronization around each measurement block. The runtime mode accessor is supplied by the harness and the optional index-reuse cache is disabled. This measures tracking preparation only, not model throughput.
