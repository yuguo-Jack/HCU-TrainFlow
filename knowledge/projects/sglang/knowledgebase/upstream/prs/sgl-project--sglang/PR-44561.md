# [Fix] [Intel] qwen4_exp: only import qwen4_decode on CUDA

[Upstream PR](https://github.com/sgl-project/sglang/pull/44561) · state: open · merged: False

## Original PR description

## Motivation

Since #42175, `Qwen4ExpLayerExtensionMixin.__init__` imports `sglang.srt.layers.moe.qwen4_decode` unconditionally. That module imports `custom_all_reduce_v2`, which imports `tvm_ffi`. The XPU install (`pyproject_xpu.toml`) does not provide `tvm_ffi`, so Qwen4Exp (Qwen3.8-Flash-Next) models fail during layer construction on Intel GPUs:

```
File ".../sglang/srt/layers/moe/qwen4_decode.py", line 15, in <module>
    from sglang.srt.distributed.device_communicators.custom_all_reduce_v2 import (
File ".../sglang/srt/distributed/device_communicators/custom_all_reduce_v2.py", line 35, in <module>
    from sglang.kernels.ops.communication.all_reduce import (
File ".../sglang/kernels/ops/communication/all_reduce.py", line 7, in <module>
    import tvm_ffi
ModuleNotFoundError: No module named 'tvm_ffi'
```

`prepare_qwen4_decode_comm` already returns `None` unless the device is CUDA SM10, so the import is not needed on other platforms.

## Modifications

Gate the import and the `prepare_qwen4_decode_comm` call on `is_cuda()`. CUDA behaviour is unchanged. The second import in `_run_ffn_stage` is only reached when `_decode_moe_comm` is not `None`, so it needs no change.

## Accuracy Tests

No change to model outputs on CUDA. The non-CUDA path was already `_decode_moe_comm = None`.

## Speed Tests and Profiling

Not performance-related. Tested on 1x Intel Arc Pro B70 (torch 2.14.0+xpu, sglang-kernel-xpu 0.4.0) with a 4-layer dummy-weight Qwen3.8-Flash-Next config (`--load-format dummy --device xpu --attention-backend intel_xpu`). Before this change, the server failed at model construction with the error above. After it, the server starts and serves eager decode at C1/C2/C4.
