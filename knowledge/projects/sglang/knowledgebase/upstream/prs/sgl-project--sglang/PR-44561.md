# [Fix] [Intel] qwen4_exp: only import qwen4_decode on CUDA; run the qwen4 PLE tests on XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/44561) · state: open · merged: False

## Original PR description

## Motivation

Since #42175, `Qwen4ExpLayerExtensionMixin` imports `sglang.srt.layers.moe.qwen4_decode` unconditionally. That module imports `custom_all_reduce_v2`, which imports `tvm_ffi`. The XPU install (`pyproject_xpu.toml`) does not provide `tvm_ffi`, so Qwen4Exp (Qwen3.8-Flash-Next) models fail during layer construction on Intel GPUs:

```
File ".../sglang/srt/layers/moe/qwen4_decode.py", line 15, in <module>
    from sglang.srt.distributed.device_communicators.custom_all_reduce_v2 import (
File ".../sglang/srt/distributed/device_communicators/custom_all_reduce_v2.py", line 35, in <module>
    from sglang.kernels.ops.communication.all_reduce import (
File ".../sglang/kernels/ops/communication/all_reduce.py", line 7, in <module>
    import tvm_ffi
ModuleNotFoundError: No module named 'tvm_ffi'
```

`prepare_qwen4_decode_comm` already returns `None` unless the device is CUDA SM10, so the import is not needed on other platforms.

Enabling the existing qwen4 tests on XPU (as asked in review) also showed that the PLE prefetch stream was a `torch.cuda.Stream`, so a Qwen4Exp model with `ple_offload_embedding` could not be built on XPU either.

## Modifications

1. `[Fix] [Intel] qwen4_exp: only import qwen4_decode on CUDA`: a small helper, `_prepare_decode_moe_comm(mlp)`, imports `qwen4_decode` and calls `prepare_qwen4_decode_comm` only on CUDA for a `Qwen2MoeSparseMoeBlock`; otherwise `None`, which is what the non-CUDA path got before. The second import in `_run_ffn_stage` is only reached when `_decode_moe_comm` is not `None`, so it needs no change. New `test/registered/unit/models/test_qwen4_exp_decode_comm.py` (CPU and XPU CI) fails any import of `qwen4_decode` and checks that a MoE layer off CUDA, and a dense layer anywhere, never import it.
2. `[Intel] qwen4_exp: device-agnostic PLE prefetch stream; run the PLE offload test on XPU`: the four PLE prefetch-stream calls use `torch.get_device_module()` (the `torch.cuda` module on CUDA, so CUDA is unchanged). `test/registered/kernels/ops/embeddings/test_qwen4_ple_offload.py` takes its device from `torch.accelerator` (CUDA or XPU), uses `torch.accelerator` memory stats, and is registered with `register_xpu_ci(est_time=45, suite="stage-b-test-1-gpu-xpu")`. The file-backend cases stay CUDA-only (they check host page-table access through the CUDA runtime) and skip on XPU as before.

## Accuracy Tests

No change to model outputs on CUDA: the CUDA branch of the helper runs the same calls as before, and `torch.get_device_module()` is `torch.cuda` there.

On 1x Intel Arc Pro B70 (torch 2.14.0+xpu, sglang-kernel-xpu 0.4.0, this branch on main fdc2dd0d05):

```
pytest test/registered/unit/models/test_qwen4_exp_decode_comm.py \
       test/registered/kernels/ops/embeddings/test_qwen4_ple_offload.py \
       test/registered/unit/models/test_qwen4_exp_ple_table.py \
       test/registered/unit/layer_boundary/test_qwen4_exp_ple_rows.py
32 passed, 6 skipped
```

The 6 skips are the existing CUDA-only checks (file backend, pinned memory through the CUDA runtime). Before the stream change, `test_qwen4_ple_offload_avoids_device_table` failed on XPU with `RuntimeError: torch.cuda.Stream requires CUDA support` (`qwen4_exp.py:1109`). With `_is_cuda` forced on and a MoE block, the new test's import guard does catch the `qwen4_decode` import, so it would catch a regression.

End to end, 4-layer dummy-weight Qwen3.8-Flash-Next config (`--load-format dummy --device xpu --attention-backend intel_xpu`), same card: main fdc2dd0d05 fails at model construction with `ModuleNotFoundError: No module named 'tvm_ffi'`; this branch starts and serves eager decode at C1/C2/C4 (512-token random prompts, 256 new tokens).

Not run: CUDA (no NVIDIA GPU here; CUDA behaviour is unchanged by construction, and CI will cover it).
