# [Perf] hybrid-swa: Detect hybrid SWA models from layer_types

[Upstream PR](https://github.com/sgl-project/sglang/pull/45295) · state: closed · merged: True

## Original PR description

## Motivation

Gemma 2, Gemma 3, EXAONE 4 and Olmo 3 mix sliding-window and full-attention layers, but sglang serves them from a single KV pool: their model overrides turn hybrid SWA memory off unconditionally, so every sliding-window layer keeps KV for the whole context. Hybrid SWA detection is an architecture allowlist with a layer rule per architecture, so each such model needs its own change (#41143, #41013, #41012). This PR replaces them with one rule: a config that sets `sliding_window` and whose `layer_types` mixes `sliding_attention` and `full_attention` layers is hybrid SWA, split by `layer_types`.

## Modifications

- `is_hybrid_swa_model()` falls back to that rule after the allowlist and the `is_hybrid_swa` opt-in, and `get_hybrid_layer_ids()` splits by `layer_types` after the existing branches, so listed architectures keep their rules. `ModelConfig.is_layer_types_hybrid_swa` marks models that came in through the new rule.
- For those models, `ModelRunner` checks the split against the `RadixAttention` layers it built: a layer in the SWA pool must have a window and a layer in the full pool must not. A mismatch, from model code that does not read `layer_types`, fails at startup and points to `--disable-hybrid-swa-memory` instead of silently dropping context. It fails rather than falling back so that every pipeline stage keeps the same pool layout.
- Gemma 2/3, EXAONE 4 and Olmo 3 no longer opt out. The opt-outs that stay: Gemma 3n and ExaoneMoE (not supported), and Gemma 3 on fa3 (#9123) until NVIDIA/FA3 validation covers SWA page allocation, freeing and reuse under long-context memory pressure; removing it is left for a separate PR.
- On the aiter backend, models detected through `layer_types` keep the single pool. With the SWA pool aiter switches to unified attention, which loses a passkey 32K tokens back on Gemma 3 (below). Listed models are not affected.
- Speculative drafts stay on the listed rules. Their workers size draft KV pools themselves: FROZEN_KV_MTP gives `Gemma4AssistantForCausalLM` (3 sliding layers, 1 full) a single-pool dummy config, which the `layer_types` rule would leave without SWA pool sizes.

Models whose behavior changes: Gemma 2, Gemma 3 (text and VL), EXAONE 4 (EXAONE-4.0-1.2B has no window), Olmo 3, and the other models whose code already takes its windows from `layer_types`: Cohere2 (Command R7B, Command A), Cohere2-MoE, AFMoE and Granite SWA.

## Accuracy Tests

1x MI325X (gfx942), ROCm 7.2.2, main at `a90e9c5d` against this PR, TP 1, `--attention-backend triton --mem-fraction-static 0.85`. GSM8K is `sglang.test.few_shot_gsm8k` (8-shot, 512 new tokens, 1319 questions).

| model | window | KV tokens, main → PR | GSM8K, main / PR | passkey, main / PR | greedy probes equal to main |
|---|---|---|---|---|---|
| Gemma 3 12B it | 1024 | 529,157 → 634,988 | 0.906 / 0.908 | 15/15 / 15/15 | 12/12 |
| Gemma 2 9B it | 4096 | 623,152 → 692,391 | 0.851 / 0.845 | 5/5 / 5/5 | 12/12 |
| Olmo 3 7B Instruct | 4096 | 416,256 → 489,712 | 0.352 / 0.356 | 5/15 / 5/15 | 12/12 |
| EXAONE 4.0 32B | 4096 | 643,632 → 757,214 | 0.906 / 0.908 | 15/15 / 15/15 | 12/12 |

- Probes: 48 greedy tokens on prompts of window - 1, window, window + 1 and 2 x window tokens, and on a 2 x window prefix extended by 512 tokens, each sent cold and again with a radix-cache hit. All 12 outputs per model are token-identical to main.
- Passkey: a 5-digit key in the first sentence, plain filler, the question at the end; 5 keys at 2 x window, 4 x window and the context limit (Gemma 2: 8128 tokens only). Olmo 3 7B misses the same keys in both arms.
- `--enable-hierarchical-cache` with the hybrid pool (Gemma 3): GSM8K 0.904, passkey 15/15, probes 12/12, so it needs no opt-out.
- Command R7B (Cohere2): main fails at the first forward on the triton backend (`layer 0 is a sliding-window layer but this forward built no window_kv_indices`). With the hybrid pool it runs: GSM8K 0.798, passkey 5/5 at 8128 tokens.
- aiter: Gemma 3 with the hybrid pool forced on gets GSM8K 0.901 but passkey 10/15, missing all five keys at 32,704 tokens that triton retrieves. On main, Gemma 2/3 do not start on aiter at all (`aiter paged decode cannot honor sliding-window attention`), and this PR keeps that.
- Speculative drafts: `test_frozen_kv_mtp.py` (Gemma 4 E4B with its assistant draft), main merged, MI300X with the AMD CI environment: GSM8K 0.715 / 0.705 at topk 1 / 3 (threshold 0.65). Without the draft rule the server fails at startup.

## Speed Tests and Profiling

`sglang.benchmark.serving --dataset-name random-ids`, output tok/s and running requests at the peak, same setup:

| model | 12288 in, 2048 out, 128 prompts at concurrency 128 | 16384 in, 512 out, 256 at 256 |
|---|---|---|
| Gemma 3 12B it | 670 → 766 (+14%), 36 → 43 running | 317 → 321, 30 → 36 running |
| EXAONE 4.0 32B | 521 → 519, 44 → 52 running | 157 → 158, 37 → 44 running |
| Gemma 2 9B it | | 590 → 606 (7168 in, 512 at 512), 77 → 86 running |
| Olmo 3 7B Instruct | | 270 → 286, 23 → 27 running |

The default `--swa-full-tokens-ratio` (0.8) gives the full-attention layers 11-20% more tokens, and concurrency grows by the same factor. A smaller ratio gives more: at 0.2, Gemma 3 runs 108 requests at 870 tok/s (+30%) in the decode-heavy run. The window pool must still hold window x running requests: EXAONE 4 at 0.2 (322K window tokens for 69 x 4096) retracts requests and loses 17%. EXAONE 4 32B on one GPU is compute-bound at 44-52 running requests, so its extra capacity does not raise throughput there.
