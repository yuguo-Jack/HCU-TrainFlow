# [Fix] disaggregation: Preserve Qwen EAGLE state across retraction

[Upstream PR](https://github.com/sgl-project/sglang/pull/48384) · state: open · merged: False

## Original PR description

## Motivation

Fixes [#48356](https://github.com/sgl-project/sglang/issues/48356).

A retracted Qwen PD decode request can resume with EAGLE draft state received from prefill, even after decode has generated additional tokens. In a forced-retraction test with Qwen3.8-Flash-Next and NIXL GPU buffers, some responses repeated digit fragments without producing the requested code.

## Modifications

- Wait for pending overlap results before retracting affected requests, retaining the running batch while those results are processed.
- Before releasing a request slot, save the latest draft top-k probabilities and indices, hidden state when present, and proposal distribution when used. Restore the saved state when decode resumes.
- Add regression tests for relay state, request-slot reuse and scheduler ordering.

The change applies to Qwen3.5 and Qwen3.8 EAGLE PD decode.

## Accuracy Tests

Tested Qwen3.8-Flash-Next FP8 on one H20 host, with prefill TP2/EP2 and decode TP2/EP2 in the same container. Both workers used NEXTN (3 steps, top-k 1, 4 draft tokens), overlap scheduling, FP32 recurrent state and regular NIXL GPU buffers. UCX was configured with `UCX_TLS=tcp,cuda_copy,cuda_ipc,self` and `UCX_ACC_DEVICES` unset. CUDA graphs were disabled because the container's FlashMLA binary was incompatible with its PyTorch version.

Each round sent eight concurrent prompts asking the model to repeat a six-digit code. A response passes if it contains the requested code after removing whitespace; the check does not require 100 exact repetitions. Forced-retraction runs set `SGLANG_TEST_RETRACT=1` and `SGLANG_TEST_RETRACT_INTERVAL=4` on decode.

| Configuration | Round 1 | Round 2 | Round 3 | Total retractions |
| --- | --- | --- | --- | ---: |
| [Base `b27a5e80a0`](https://github.com/sgl-project/sglang/commit/b27a5e80a0836e073db63fef53eddf94eacb71ed), no forced retraction | 8/8 | — | — | 0 |
| Base, forced retraction | 7/8 | 7/8 | 7/8 | 187 |
| This PR, forced retraction | 8/8 | 8/8 | 8/8 | 174 |

The three failing baseline responses repeated digit fragments without producing the requested code.

For a broader accuracy check, the [upstream Qwen3.8 PD GSM8K recipe](https://github.com/sgl-project/sglang/blob/6393e66b8649b4e6e22f2d94a933e69059192900/test/registered/e2e/disaggregation/test_qwen4_exp_pd_prefill_cp.py) uses 200 questions, 32 client threads, thinking enabled and a 16,384-token output limit. With `sgl-eval`, the same 200 questions scored 194/200 (97.0%) on the base and 195/200 (97.5%) with this PR. There were no request errors. One response in the PR run reached the output limit and remained in the score; none did on the base. Both exceed the reference test's 94% threshold; the reference uses an NVFP4 checkpoint, while this test uses FP8.

Twelve targeted unit tests and pre-commit passed. The model tests did not cover Qwen3.5, cross-node deployment or CUDA graphs.

## Speed Tests and Profiling

Using `python -m sglang.benchmark.serving` on the same host and model, each case ran three times serially with random token IDs (seed 42), 1,024 input tokens, 256 output tokens, concurrency 8, 16 warmup requests and 64 measured requests. Each run completed 64/64 requests and generated 16,384 output tokens. CUDA graphs were disabled. Normal runs used a 32,768-token context and 98,304-token KV pool; forced-retraction runs used 16,384 and 32,768 respectively. Each pair used matching settings.

| Configuration | Output tokens/s | Median TTFT (ms) | Median TPOT (ms) | Retractions per run* |
| --- | ---: | ---: | ---: | --- |
| Base | 120.63 | 626.53 | 57.02 | 0 / 0 / 0 |
| This PR | 115.07 | 642.39 | 59.55 | 0 / 0 / 0 |
| Base, forced retraction | 102.46 | 630.72 | 64.63 | 262 / 260 / 254 |
| This PR, forced retraction | 112.60 | 616.83 | 59.81 | 237 / 252 / 248 |

The throughput and latency columns are the medians of the three run-level values. *Retraction counts include warmup requests. Normal-run throughput was 4.6% lower with the PR in this serial comparison; the cause was not isolated. Forced-retraction counts differ, and the baseline can generate incorrect output under that load, so those rows do not isolate the snapshot cost or establish a performance improvement.
