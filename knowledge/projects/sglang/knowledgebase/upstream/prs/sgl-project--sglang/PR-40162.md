# [Feature] Extend Candidate Compact Scoring to DeepSeek-V4.1 DSpark Target Verification on Hopper

## Motivation

baseline PR: https://github.com/sgl-project/sglang/pull/38798

DeepSeek-V4.1 uses a hierarchical sparse indexer in its decoder:

- Layer 20 performs a full-context index scan and publishes up to 16,384 candidate positions.
- Layers 24, 28, 32, and 36 reindex within those candidates.

PR #38848 optimizes ordinary decode on Hopper by reusing candidate slots across Reindex layers. However, DSpark primarily runs the target model in `TARGET_VERIFY` mode, where each request contributes multiple verification rows. The existing optimization therefore does not improve the main DSpark verification path.

## Proposed Changes

Extend candidate compact scoring to both static and ragged `TARGET_VERIFY`:

1. Have the Full indexer publish per-verification-row:
   - Logical candidate positions
   - Physical KV slots
   - Valid candidate counts
2. Reuse the published candidate state in all subsequent Reindex layers.
3. Score only the candidate pool instead of rescanning the full allocated context.
4. Preserve both output contracts:
   - Physical slots consumed by sparse attention
   - Logical indices used by metadata and debugging paths
5. Support eager execution and decode CUDA Graph capture/replay.

## Hopper-Specific Optimizations

The implementation should avoid materializing a dense `[verify_rows, context_capacity]` slot matrix.

Instead:

- Resolve `req_to_token` mappings directly inside the SM90 FP4 scoring kernel.
- Fuse FP4 scoring with candidate block-max generation.
- Use the existing Hopper-optimized TopK v2 kernel for full and candidate Top-K selection.
- Reuse one candidate Top-K plan across all Reindex layers.
- Fuse candidate block sorting, validity filtering, logical-to-physical mapping, and output writes into dedicated kernels.
- Ensure score storage has a physical row stride aligned to four elements, as TopK v2 uses 16-byte vectorized loads.

## Expected Execution

```text
Layer 20:
  Full-context FP4 scoring
  + candidate block reduction
  -> Top-2048 blocks
  -> 16,384 candidate positions and physical slots

Layers 24/28/32/36:
  Score only the 16,384 published candidate slots
  -> Top-512 sparse-attention slots
```

## Expected Benefits

For long-context DSpark workloads:

- Reduce each Reindex layer from `O(verify_rows * context_capacity)` to `O(verify_rows * 16K)`.
- Avoid multi-gigabyte temporary slot tensors at 1M context.
- Reduce CUDA Graph memory consumption.
- Remove unnecessary PyTorch elementwise, sorting, masking, and gather launches from the verification hot path.
- Improve target-verification latency and end-to-end speculative throughput on H20/H100.

- songkuan-zheng · comment · 2026-09-20T09:10:57Z · [source](https://github.com/sgl-project/sglang/pull/40162#issuecomment-5748870229)

Corroborating from a service-level A/B on 8 x H200 (SM90), TP4, DSpark k=5 (`--speculative-dspark-block-size 4`, so 5 draft tokens), `--max-running-requests 8`. This is the mode our production traffic actually runs in, so if there is a place where TARGET_VERIFY needs the compact-scoring treatment, it is the dominant path rather than a corner.

One interaction worth writing down, because it makes the two problems compound rather than add:

The layer-20 full-context scan is charged **per row**, and DSpark multiplies rows by (1 + k). At bs=8 that is up to 48 verify rows against a capacity-sized column count — so whatever the full indexer costs per row gets paid ~6x per scheduled request. Measured on our box, per-request decode at bs=8 is 2.68x worse at `--context-length 1048576` than at 131072, while at bs=1 it is only 1.50x — i.e. the cost is strictly proportional to rows x configured width, linear in both (halving the configured width halves the saving, 10.91 : 5.52 ms at n=8).

That also means the fix ordering matters: #40431 removes the arithmetic on invisible columns, this PR removes the need to re-score rows at all for the reindex layers, and the residual is the grid itself plus the width (separate issue). Extrapolating sglang's decode step to zero indexer capacity leaves ~20-25% of the gap to vLLM at the same operating point unattributed, which is roughly the size of the prize here if TARGET_VERIFY is where most of the rows come from.

No action requested — just flagging that the payoff for extending this to verify should be larger than the ordinary-decode case, and that a row-multiplying speculative configuration is the realistic setting to validate at.
