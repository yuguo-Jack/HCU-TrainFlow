# [Perf] [NVIDIA] deepseek-v4.1: Fuse BF16 prefill indexer score epilogue

[Upstream PR](https://github.com/sgl-project/sglang/pull/45807) · state: open · merged: False

## Original PR description

## Motivation

The DeepSeek V4.1 Torch prefill indexer materializes full-size BF16 intermediates for ReLU and head-weight multiplication before reducing scores across heads. This introduces substantial memory traffic and kernel-launch overhead.

This change fuses the score epilogue for the supported 32-head CUDA BF16 path while retaining the existing GEMM.

## Modifications

- Add a Triton kernel that fuses ReLU, head-weight multiplication, head reduction, and FP32 output conversion.
- Preserve BF16 rounding after multiplication and reduction, and follow the CUDA Torch 32-head accumulation order used in validation.
- Pass context-dependent score-row and score-head strides as runtime parameters to avoid per-length specialization of these strides.
- Retain the Torch fallback for unsupported devices/dtypes, non-32-head inputs, and widths of at most one.

## Accuracy Tests

Local validation on DeepSeek V4.1 Flash:

- 20 CP request-row mapping cases passed.
- 24 scoring and epilogue checks passed with exact agreement.
- Epilogue stress tests covering 18 shapes and 100 seeds per shape passed with exact agreement, including BF16 rounding boundaries.
- 8 Prefill integration cases passed with exact raw-index and KV-slot writeback agreement.
- 8 synthetic arithmetic/retrieval probes at approximately 32K and 64K context lengths passed.

GSM8K, 1,319 examples per run:

| --- | ---: | ---: |
| Baseline A/A, run 1 | 96.74% | 0% |

The baseline A/A runs show run-to-run variation. These results do not establish bitwise equivalence of complete generated outputs or replace representative long-context quality evaluation.

The validation scripts were run locally and are not yet included as CI-registered tests in this patch.

> (from Claude) Why `width <= 1`? Is it because Torch uses a different reduction order at width 1? A one-line reason here would stop someone from removing it.

Our actual measurement has confirmed that under the current Torch/CUDA environment, when width=1, the head dimension becomes a continuous reduction dimension. The reduction order used by Torch is different from the four-way accumulation in the fusion kernel. The floating-point addition order will affect the result. Therefore, it is necessary to retain the Torch fallback.
