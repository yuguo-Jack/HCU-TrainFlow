# [Fix] disaggregation: Send decode transfer destinations to prefill only after the in-flight forward

[Upstream PR](https://github.com/sgl-project/sglang/pull/46373) · state: closed · merged: True

## Original PR description

## Motivation

When decode reuses a finished request's KV pages while its last forward is still in flight, publishing the new destination immediately lets prefill write into pages that the old forward can still overwrite. #45328 orders the normal deferred-publication path; this PR closes the remaining device-destination paths under overlap scheduling, including staging, HiSparse, and configurations with the WAR barrier or deferred publication disabled.

PP currently disables overlap, so it keeps its existing synchronous publication behavior. Host destinations keep their existing H2D fencing.

## Modifications

- Hold inline device metadata behind an event recorded on the forward stream. Publish only after every rank agrees that its event is complete and its receiver has not failed, using a MIN reduction. This prevents partial publication across TP ranks during cancellation.
- Publish held destinations before the retraction and polling gates, and again after newly allocated requests enter the transfer queue. A retracted request cannot indefinitely delay an unrelated ready destination.
- Release unpublished failed destinations without waiting for drain acknowledgements that cannot arrive. If a peer requires a collective hold, the unpublished rank participates with zero required acknowledgements.
- For early-policy rebootstrap requests, submit prefill recomputation after the held metadata is actually sent, preserving the existing ordering and avoiding an abort before the receiver is armed.
- Initialize `chunk_staging_infos` in `CommonKVReceiver.__init__`, so staging cleanup is safe before `send_metadata`.

The existing deferred-publication and host-destination paths retain their ordering. Tests cover event readiness, agreement across ranks, retraction gating, failed receivers, acknowledgement accounting, staging cleanup, and recompute submission order. The delayed-conclusion test is defensive coverage; it does not claim that PP currently enables overlap.

## Motivation

On a PD decode server with overlap scheduling, a request that finished at step k−1 is still a row of forward k, because forward k was launched before the scheduler processed step k−1's results. `process_batch_result` frees that request's KV pages while forward k is still in flight. On the next iteration, `process_decode_queue` can preallocate those pages for a new request, and `DecodePreallocQueue._send_kv_metadata` sends them to prefill right away.

The prefill then writes the pages by RDMA, and no CUDA stream orders that write. If the RDMA lands before forward k writes the finished row's KV, forward k overwrites part of the new request's transferred KV. The new request then decodes from wrong KV, and nothing reports an error.

Two other paths already guard against this by waiting for the forward stream before they reuse pages:
- prebuilt requests (`get_new_prebuilt_batch`);
- retraction restore and write-through (#42701, #42702).

The prealloc → transfer path is the one that remains, and `wait_stream` cannot order a remote RDMA write.

Each hit corrupts one position per finished row with plain decode. With speculative decoding it corrupts one verify window, and that window can fall on a page beyond the request's committed length. Hits need a nearly full decode pool, so that a freed page is reused at once, and a prefill that is already waiting for decode memory, so that its RDMA lands within one forward.

## Modifications

When overlap scheduling is on and the destination is on the device:
- `DecodePreallocQueue._send_kv_metadata` records an event on the forward stream after allocating, instead of calling `send_metadata` right away. The event covers every forward enqueued so far. The `send_metadata` arguments are kept on the request in a new field, `DecodeRequest.pending_metadata`.
- `DecodeTransferQueue.pop_transferred` sends the held metadata once its event completes, after it polls and filters the queue, so only requests still queued send it.
- Nothing blocks. A request dropped from the transfer queue drops its held metadata with it.

The send is delayed by at most the forward in flight, about one decode step, and only while that forward is still running. Host destinations are unchanged, because the H2D copy that follows already waits for the forward.

Every transfer backend gets the fix, since they all receive destinations through `_send_kv_metadata`. That includes the staging path, whose scatter runs on its own stream.

The unit test stand-ins for `DecodeRequest` and the scheduler get the new fields (`pending_metadata=None`, `enable_overlap=False`).

## Accuracy Tests

The corruption is silent, so it was found with a KV integrity checker. The checker seals each transferred page with a checksum on prefill and verifies it when decode accepts the transfer.

The setup was PD 1P1D with overlap scheduling and a decode pool small enough to force retractions, with 4096-token prompts and 2048-token outputs at concurrency 32.

Before this change, with and without speculative decoding:
- Transferred pages failed their checksum at accept, while the page identity in the tag still matched.
- Debug output showed the forward for requests that had just finished writing into those pages after the transfer landed.

After this change: no mismatches over repeated runs (8–10 retractions and about 475 accepted transfers each), with `cpu_tensor` and `host_pool` retraction backups, with and without speculative decoding. GSM8K was unchanged.

## Follow-ups in this revision

Two fixes found in review of the first revision:

- `CommonKVReceiver.__init__` creates `chunk_staging_infos = []`, so a staging `release_room` works for a request that failed or was aborted before its held `send_metadata` ran. Before, the list was created by `send_metadata`, and cleanup of such a request raised and leaked the decode pool pages it had reserved.
- The held send moves from the top of `DecodeTransferQueue.pop_transferred` to after the poll and queue filtering, so only requests still in the transfer queue send their destination. A request that failed or was aborted while its destination was held never tells prefill where to write, and `_defer_release` awaits no drain acknowledgement for it.

New unit tests: `test_receiver_connection_pool.py::TestCommonReceiverLifecycle.test_staging_release_before_send_metadata` and `test_deferred_decode_kv_release.py::TestFailedTransfersDeferOnEveryFailure.test_held_destination_is_sent_only_by_queued_requests`.
