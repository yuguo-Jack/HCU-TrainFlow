# [Feat] [AMD] monokernels: one runtime switch for vendor monokernel plugins

[Upstream PR](https://github.com/sgl-project/sglang/pull/44353) · state: closed · merged: True

## Original PR description

## Motivation

Persistent "monokernels" run most of a decoder layer, including its TP all-reduce, in one or two launches, which removes the launch gaps and collective latency that dominate small-batch decode. RFC #43949 proposes one framework for them. This PR is that framework, with the kernels themselves living outside SGLang in vendor plugins: AMD's are in [sgl-project/sgl-amd-mono](https://github.com/sgl-project/sgl-amd-mono) (DeepSeek-V4.1-Flash and its DSpark draft on MI350X / MI355X).

## Modifications

- Add `--monokernel-backend <name>` in `exec.kernel`, an experimental feature, disabled by default; selecting a backend logs that its kernels, coverage and plugin API may change. General plugins (`sglang.srt.plugins`) register a backend's spec per architecture through `sglang.srt.monokernels.spec.register`; specs load lazily and declare the API version they target (`MONOKERNEL_API_VERSION`, bumped on any breaking change, like `SERVE_BACKEND_API_VERSION` for `sglang serve` backends).
- Validate the selected target spec in the configuration pipeline (`guards.handle_monokernel`) and align configured decode capture sizes with its supported widths. A spec states what it needs as data (`Requirements`: dtype, decode-phase attention backend, server arguments, HF config fields, SGLang environment variables), checked the same way for every spec; an optional `config_disable_reasons` covers the rest. Observe checkpoint tensors before model-specific conversion (`runtime.monokernel_weights_iterator`) so plugins can retain required weight copies, and refuse a spec that keeps copies when the load path skipped the observer.
- Build the selected spec after weight loading, before KV sizing (`runtime.install_monokernel_forward`), and install a full-forward dispatcher that preserves the model's signature. Every built width of the model's step (decode, or verify on a speculative server at any token count) uses the plugin's forward; other shapes use the original forward. Models with derived weight copies refuse online weight updates.
- Decide alike on every TP rank: the ranks exchange spec lookups (outcome, registration, reason, spec name and API version) before branching, so an unregistered draft keeps its forward everywhere, and a broken or mismatched spec on any rank fails startup on every rank. Supported graph keys are fixed at install and compared across ranks; routing reads only a step's graph key. Before the plugin's first forward, with or without CUDA graphs, the switch checks the decode attention backend that step runs on, since a draft runner may override the one the launcher checked.
- Check coverage against the graphs the runner actually captured (alignment and request-pool limits can drop configured sizes): a capture hook fails startup when no captured graph runs the plugin, and logs the captured and eager steps that run the monokernels.
- Type the plugin API (`BuiltMonokernels` with `forward`, the spec callbacks' signatures, `Plan`) and state the forward's obligations: the model forward's arguments and outputs, the KV cache and auxiliary hidden-state writes of the standard path for every row, padded rows included, and CUDA-graph capturability. Keep framework code in `python/sglang/srt/monokernels/`; vendor kernels and model-specific forwards remain in their plugin packages.
- Pin sgl-amd-mono in the `srt_hip` extras of `pyproject_other.toml`, so AMD installs (and SGLang's ROCm images) include the plugin; `--monokernel-backend amd` stays opt-in. Add the server-argument documentation row.
- Register CPU tests for spec lookup, validation (every requirement kind, including decode-backend overrides), graph-size alignment, forward routing/signatures, step modes (a one-token draft block is a verify step), the per-step backend check, per-step state, rank-uniform lookup and spec identity, captured and eager coverage, weight observation and a load path that skips it, deadlines, the runtime's reads of a published config, and the SGLang names the framework reads off GPU-only objects. Vendor kernel and serving tests live in the plugin repository.

## Accuracy Tests

DeepSeek-V4.1-Flash, MI350X, TP4, 04fcb04e34 with sgl-amd-mono 8f1bff3 (on the DSpark server, target and draft both on monokernels). Each server steps past the largest covered width and back as its batch fills and drains:

| | DSpark (verify steps) | Decode (no speculation) | Bound | Normal path |
| --- | --- | --- | --- | --- |
| GSM8K, 200 questions, 8-shot | 0.920 | 0.875 | > 0.85 | 0.88 to 0.91 |
| Mean KL of the covered steps' tokens vs the normal prefill path (8 LongBench-v2 prompts) | 0.0118 | 0.0119 | < 0.03 | about 0.007 |

A fault injected on one rank stops every rank, and no token of the failed step reaches the client. CPU tests: `test/registered/unit/monokernels` 17 passed; the plugin's serving tests (above) 9 passed. Not executed: MI355X, and AgentX at TP2 (in progress).

## Speed Tests and Profiling

Per-user decode tok/s, real DSpark acceptance (mean accept length 3.72 off, 3.69 on), monokernels off -> on: 1 request 444.1 -> 776.0 (+75%), 4 requests 362.8 -> 441.4 (+22%), 8 requests 267.4 -> 327.5 (+22%). Measured at 05e333df70 with sgl-amd-mono 905f61b; the later commits change startup checks and logging, not the step path.

AgentX (the published MI355X agentic recipe, run on MI350X, TP4, DSpark, 1 concurrent user for 900 s, forced acceptance 3.51): P90 410.3 -> 543.8 tok/s/user (+32.5%), P50 438.6 -> 591.5 (+34.9%), 117 -> 132 requests. Both arms ran with the simulated-acceptance fold, a separate PR that keeps sampled verify steps on the CUDA graph under forced acceptance. Measured with sgl-amd-mono 8faf602, before its K2i indexer kernel; not rerun since.
