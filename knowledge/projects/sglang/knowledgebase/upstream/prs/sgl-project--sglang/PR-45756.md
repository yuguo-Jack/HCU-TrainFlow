# [Feat] muse_spark: Pipeline parallelism with DFLASH speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/45756) · state: closed · merged: False

## Original PR description

## Motivation

Muse Spark builds every decoder layer on every rank, and DFLASH rejects `pp_size > 1`. So the model cannot span nodes with speculative decoding. On 8×H100 80 GB, Muse-Spark-Open-816B-A42B-NVFP4 with the DFlash2 draft leaves a ~311k-token GPU KV pool. That rejects the 330k–480k-token inputs of long agentic traces, and a higher `--mem-fraction-static` OOMs the MoE in warmup. Running TP8 × PP2 across two nodes gives each stage a 6.35M-token pool. This PR adds pipeline parallelism to Muse Spark and lets DFLASH run on the existing PP spec relay (`SGLANG_ENABLE_PP_SPEC`).

## Modifications

**Muse Spark** (`models/muse_spark.py`, `models/muse_spark_omni.py`)
- Each stage builds only its own layers (`PPMissingLayer` elsewhere) and skips other stages' layer weights.
- Pre-attention norms fuse only within a stage. The stage's last layer takes the unfused tail, as the model's last layer already does.
- The fp32 residual stream crosses stages as a bf16 head plus its bf16 rounding error, so it reconstructs to about fp32 precision. It fits the `hidden_states` / `residual` proxy buffers that the PP runtime and the decode CUDA graphs already allocate.
- Earlier stages relay their DFLASH target-layer taps in the existing `dspark_hidden_states` proxy slot, the one Kimi K3 uses. The last stage prepends them to its own taps.
  - `set_dflash_layers_to_capture` already runs on every stage's target runner, so `get_pp_proxy_dspark_hidden_size` derives the width from `layers_to_capture`.
- Later omni stages skip embedding and multimodal routing.
- Layernorm SP stays single-stage and raises under PP.

**DFLASH under `SGLANG_ENABLE_PP_SPEC`**
- The last stage holds the draft:
  - It verifies the relayed block without drafting it again. Selector and LiLiCorr heads still draft, because their accept step reads the draft's samples.
  - It accepts, then tail-drafts the next block from the post-accept state, and relays that block with the accept results.
- Earlier stages run their half of the same 8-token verify from the relayed tokens (new `speculative/dflash_pp.py`).
- `scheduler_pp_mixin`: DFLASH relays a chain, so no tree topology and no EAGLE `topk_p` / hidden-state tensors ride with it.
- `spec_utils`: relayed batches carry no DFLASH draft state, so they take the generic decode KV reservation. It reserves the same 2 × block size.
- `dflash_worker_v2`: the draft worker reuses the target's broadcast seed. `draft_pp_context()` hides `pp_size`, so `TpModelWorker` would otherwise skip its PP+spec branch and enter a WORLD broadcast that earlier stages never join.
- `speculative_hook` / `validation_hook`: allow DFLASH with `pp_size > 1` only when `SGLANG_ENABLE_PP_SPEC=1`.

`SGLANG_PP_LAYER_PARTITION` works unchanged (`get_pp_indices`), and the single-stage draft ignores it.

## Accuracy Tests

Setup: Muse-Spark-Open-816B-A42B-NVFP4 with the `RadixArk/Muse-Spark-Open-DFlash2` draft and 8 draft tokens, using `--moe-runner-backend marlin --fp4-gemm-backend marlin --attention-backend fa3 --kv-cache-dtype fp8_e4m3`. Acceptance is real, not simulated. The H100s are 80 GB HBM3, with NCCL over sockets between the two nodes.

`python -m sglang.test.few_shot_gsm8k --num-questions 400 --parallel 16` (greedy):

| Config | Accuracy | Mean accept length |
|---|---|---|
| TP8, 1 node | 0.960 | 5.19 |
| TP8 × PP2, 2 nodes | 0.963 | 5.04 |

In InferenceX CI ([run 39735574615](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/39735574615)), lm-eval gsm8k on TP8 × PP2 at concurrency 16 scored 0.980 ± 0.004 (1,319 questions). Mean accept length on the last stage was 5.49 with real acceptance.

The ~3% lower acceptance under PP is mostly a known cost of the relay design. A request's first decode after prefill verifies the sampled token plus 7 placeholders, because the first block is drafted only at the end of that round. That costs one round per request.

## Speed Tests and Profiling

Agentic-coding trace replay on TP8 × PP2 (two H100 nodes, inputs up to ~480k tokens, 1-hour runs), from InferenceX CI [run 39735574615](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/39735574615). Acceptance is pinned at 4.05 with `SGLANG_SIMULATE_ACC_LEN` so that results are comparable across hardware.

| Concurrency | Output tok/s per GPU | Median tok/s per user | TTFT p50 (s) |
|---|---|---|---|
| 1 | 6.03 | 148 | 1.08 |
| 2 | 7.39 | 125 | 0.73 |
| 4 | 9.56 | 113 | 0.73 |
| 8 | 12.85 | 56 | 0.68 |
| 16 | 8.17 / 8.79 | 23 / 29 | 27.5 / 15.0 |

Concurrency 16 saturates this setup, so it varies from run to run; the two values are the run's first attempt and a rerun of that point. An earlier CI run got 10.19 tok/s per GPU and an 8.65 s TTFT p50 there, and c1–c8 matched this run. Across the three c16 runs, throughput tracks the prefix-cache hit rate (49%, 54% and 63%), with KV usage under 50% in each.

At concurrency 1 a round takes 27.4 ms against 18.5 ms on a single H200 node, which is close to the HBM bandwidth ratio. That suggests the relay adds little; this is an estimate, not a profile.

The last stage also runs the draft, the LM head and sampling. An uneven split (`SGLANG_PP_LAYER_PARTITION`) is the obvious tuning knob; these results use the even 31/31 split.

**Test scope:** the hardware runs used `lmsysorg/sglang:dev-muse-spark-open` with the equivalent change applied as a patch. This PR ports it onto `main`:
- The scheduler, relay and hook changes applied to `main` unchanged.
- The model and draft-worker hunks were re-applied by hand, because `main`'s `muse_spark.py` has no expert-TP wrapper.
- The CI run above applies the same change to the image as a patch. This exact branch has not run on hardware.
