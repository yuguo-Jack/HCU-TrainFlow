# [Fix] metrics: Correct MFU/MBU bandwidth overcounting and GraniteMoE AutoTokenizer fallback

[Upstream PR](https://github.com/sgl-project/sglang/pull/47416) · state: open · merged: False

## Original PR description

## Motivation

This PR bundles three independent, hardware-validated fixes found during P1 perf/accuracy CI triage, all in the MFU/MBU analytical estimator and tokenizer loading path.

**1. MFU/MBU estimator overcounts read bandwidth.** With `--enable-metrics --enable-mfu-metrics`, the estimated decode read-bandwidth (and therefore any peak-bandwidth-normalized MBU%) comes out several times too high once concurrency is above a handful of requests. Reproduced on real hardware with `baidu/ERNIE-4.5-0.3B-PT` at concurrency≈100 (TP=1, no tensor parallelism involved):

| Platform | read BW reported | MBU (vs. peak HBM bandwidth) |
|---|---|---|
| NVIDIA RTX PRO 6000 Blackwell | ~7342 GB/s | ~410% |
| Intel Arc Pro B60 | ~2088 GB/s | ~458% |

A GPU physically cannot sustain more than 100% of its own memory bandwidth, so this is clearly wrong, not just "slightly off."

**2. `AutoTokenizer` fails to load granitemoe-family models.** `ibm-granite/granite-3.0-3b-a800m-instruct` (and likely sibling `granitemoe`/`granitemoehybrid`/`granitemoeshared` models) fails to load with:

```
ValueError: Couldn't instantiate the backend tokenizer from one of:
(1) a `tokenizers` library serialization file,
(2) a slow tokenizer instance to convert or
(3) an equivalent slow tokenizer class to instantiate and convert.
You need to have sentencepiece or tiktoken installed to convert a slow tokenizer to a fast one.
```

Root cause: this model's `config.json` has `model_type: "granitemoe"`, which transformers v5 maps to the generic `TokenizersBackend` in `TOKENIZER_MAPPING_NAMES`. The model's own `tokenizer_config.json` declares `tokenizer_class: "GPT2Tokenizer"` (it ships `vocab.json`/`merges.txt`, no `tokenizer.json`). transformers' `AutoTokenizer.from_pretrained` only honors a hub-declared `tokenizer_class` override when the model_type's *registered* class is concrete — since `granitemoe`'s registered class is itself `TokenizersBackend`, the override is skipped and the bare generic backend is instantiated instead, which can't build a tokenizer from `vocab.json`/`merges.txt` alone and raises.

sglang already has `_resolve_tokenizers_backend()` to work around this general class of transformers v5 regression, but it only triggers when `AutoTokenizer.from_pretrained` *succeeds* and returns a `TokenizersBackend` instance. In this case construction raises instead of returning an object, so that fallback path is never reached.

**3. MFU/MBU estimator overcounts FLOPs for hybrid Mamba/attention/MLP architectures.** `_init_estimated_perf_constants` in `metrics_reporter.py` scales both the attention-FLOPs term and the MLP-FLOPs term by `num_attention_layers`, which `ModelConfig` sets equal to `num_hidden_layers` for hybrid models like NemotronH (no hybrid-Mamba special case exists there). In practice only a small fraction of layers are true attention layers; the rest are Mamba-mixer-only or MLP-only layers with no attention sublayer and, for Mamba layers, no MLP sublayer either. This inflates the estimated prefill TFLOPS by roughly an order of magnitude for mostly-Mamba stacks. Concretely, on `nvidia/Nemotron-H-4B-Instruct-128K` (52 layers: 4 attention, 24 Mamba, 24 MLP-only), live on H200 (`SGLANG_ENABLE_METRICS_DEVICE_TIMER=1`, bench_serving, 1536-in/512-out, 500 prompts, concurrency 128), the device-timer-weighted ground-truth prefill TFLOPS was 1631.1 TFLOPS/s — 165% of H200's 989 TFLOPS/s physical peak, which is impossible.

## Modifications

**MFU/MBU estimator** — two independent overcounting bugs in `SchedulerMetricsReporter`'s analytical FLOPs/bytes estimator (pure Python math from model config + batch shape, no device-specific branching — both bugs affect every backend identically):

1. **`_estimate_prefill_perf` / `_estimate_decode_perf`**: the whole-model weight-read byte count (`_weight_read_bytes_per_token`) was multiplied by the batch's token count, as if every concurrent sequence independently re-reads the entire model from HBM. A batched decode step reads each weight matrix from HBM once and reuses it across every row of the GEMM, so this inflated read bandwidth by roughly the batch size. Fixed by charging it once per forward pass instead of once per token (KV-cache bytes are untouched — those genuinely are per-sequence).
2. **`_init_estimated_perf_constants`**: `num_attention_heads`/`num_kv_heads` are already divided by `tp_size`, but `intermediate_size` (the MLP/FFN dimension, also sharded under tensor parallelism) was left unsharded, overcounting MLP FLOPs/bytes by `tp_size` for every TP>1 run.

**Tokenizer fallback** — in `_auto_tokenizer_from_pretrained`, when `AutoTokenizer.from_pretrained` raises the `Couldn't instantiate the backend tokenizer` `ValueError`, fall back to the existing `_load_tokenizer_by_declared_class()` helper, which loads the tokenizer directly via the class `tokenizer_config.json` declares (`GPT2Tokenizer` here), bypassing `AutoTokenizer`'s resolution entirely. If that fallback also can't improve on `AutoTokenizer` (returns `None`), the original `ValueError` propagates unchanged.

**Hybrid Mamba/attention/MLP FLOPs split** — in `_init_estimated_perf_constants`:
- Read `hf_text_config.layers_block_type` (the per-layer type list the model builder itself reads at construction time, e.g. `models/nemotron_h.py`) when available, and derive separate `num_attn_layers` (count of `"attention"`) and `num_mlp_layers` (count of `"mlp"` + `"moe"`) instead of using a single shared `num_layers` for both.
- Falls back to the existing `full_attention_layer_ids`-based attention-layer count (with `num_mlp_layers = num_layers`) when `layers_block_type` isn't present, preserving current behavior for non-hybrid architectures.
- Scale `attn_linear_flops` by `num_attn_layers`, `mlp_flops` by `num_mlp_layers`, and `_attn_dot_flops_coeff` by `num_attn_layers` (previously all three were scaled by the same `num_layers`).
- Mamba/SSM-layer compute itself is intentionally left uncosted (not estimated) rather than guessed at — a conservative gap that, if anything, slightly under-reports FLOPs/MFU for heavily-Mamba models rather than over-reporting.

All three only affect the analytical FLOPs/bytes estimator used for `--enable-mfu-metrics` telemetry; none change model execution.

## Accuracy Tests

- MFU/MBU bandwidth and TP-sharding estimator fixes: N/A — these only change a diagnostic metrics estimator, not model computation or outputs.
- Tokenizer fallback: validated on real XPU hardware against `lmsysorg/sglang:v0.5.21-xpu`. Before fix: server crashes at tokenizer init with the `ValueError` above, every run. After fix: tokenizer loads via `GPT2Tokenizer`, model loads as `GraniteMoeForCausalLM`, server starts successfully, and a gsm8k eval (5 examples, `lm_eval`) completes with exit code 0 (`exact_match` 0.6, both `flexible-extract` and `strict-match` filters).
- Hybrid Mamba FLOPs split: N/A — this only changes the `est. prefill/decode TFLOPS/s` telemetry estimator, not model forward computation.

## Speed Tests and Profiling

Hardware-validated before/after on both platforms (`baidu/ERNIE-4.5-0.3B-PT`, TP=1, 4096/1024 in/out, 100 prompts, concurrency≈100). Real served throughput is unchanged (this only touches the metrics estimator):

| Platform | MBU before | MBU after |
|---|---|---|
| NVIDIA RTX PRO 6000 Blackwell | ~410% | ~64% |
| Intel Arc Pro B60 | ~458% | ~72% |

Also hardware-validated bug 2 (`intermediate_size` TP sharding) specifically, which only manifests at TP>1: same model at TP=2 on Intel Arc Pro B60 (2 GPUs), before/after on the decode-loop's self-reported per-GPU numbers:

| | read BW (per GPU) | real served throughput |
|---|---|---|
| Before | ~1090 GB/s | 1971 tok/s |
| After | ~110-130 GB/s | 2050 tok/s |

Real throughput is within noise of the TP=1 run and unaffected by the fix, as expected — only the estimator's self-reported bandwidth number drops to a physically plausible range.

Hardware-validated the hybrid Mamba FLOPs split live on an H200 GPU running `nvidia/Nemotron-H-4B-Instruct-128K` with `SGLANG_ENABLE_METRICS_DEVICE_TIMER=1 --enable-metrics --enable-mfu-metrics`, using `sglang.bench_serving` (`--dataset-name random --random-input-len 1536 --random-output-len 512 --num-prompts 500 --max-concurrency 128`):

| Stage | Ground-truth prefill TFLOPS/s | % of H200 peak (989 TFLOPS/s) |
|---|---|---|
| Before fix (all 52 layers costed as attention) | 1631.1 | 165% (impossible) |
| After fix (4 attention, 24 MLP, 24 Mamba layers split correctly) | 933.3 | 94.4% |

Unit tests added in `test/registered/unit/observability/test_forward_pass_metrics.py`:
- `TestEstimatedPerfConstantsTpSharding` — weight-read bytes no longer scale with batch size/token count, and MLP FLOPs/bytes scale down with `tp_size`.
- `TestEstimatedPerfConstantsHybridMambaSplit` — `layers_block_type` splits attention/MLP/MoE layer counts and leaves Mamba-only layers uncosted; the `full_attention_layer_ids` fallback still costs MLP for every layer; and the no-hybrid-metadata path preserves prior behavior (every layer costed as attention+MLP).

Unit tests added in `test/registered/unit/tokenizer/test_auto_tokenizer_declared_class_fallback.py`:
- Recovery via `_load_tokenizer_by_declared_class` when `AutoTokenizer` can't instantiate a backend tokenizer.
- The original `ValueError` propagates unchanged when that fallback also can't help.

All new tests confirmed to fail against their respective pre-fix code and pass against the fix.
