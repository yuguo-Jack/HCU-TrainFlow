## Motivation

Add MSCCL++ latency-mode expert parallelism to SGLang as an additional MoE
dispatch/combine backend.

The integration provides two layouts:

- **Rank-major**
- **Expert-major**

The goal is to reduce expert-parallel communication overhead while preserving
CUDA Graph compatibility, correctness, and the existing SGLang MoE
dispatch-run-combine abstractions.

## Modifications

- Added the MSCCL++ latency-mode dispatcher and combine integration.
- Added rank-major dispatch support for the FlashInfer CUTLASS runner.
- Added expert-major dispatch support for the Triton runner.
- Added shared communicator/resource reuse with graph-stable runtime buffers.
- Added prefill and decode capacity handling based on the active attention
  tensor-parallel geometry.
- Added MSCCL++ mode/layout configuration and combine routing-weight plumbing.
- Added runner pre/post-permute adapters and dispatcher format/type guards.
- Added `bench_mscclpp_ll_ep.py` for correctness and CUDA Graph performance
  comparisons:
  - Rank-major MSCCL++ performance and correctness comparation with FlashInfer.
  - Expert-major MSCCL++ correctness comparation with Triton.
  - Separate dispatch, expert compute, combine, and unclassified kernel timing.
  - Deterministic globally balanced routing with invariant validation.
  - User-configurable `--atol` and `--rtol` for either layout.

## Accuracy Tests

### Test configuration

This benchmark models the forward pass of a distributed Mixture-of-Experts (MoE) layer. It generates token activations, top-k expert assignments, and routing weights, then uses either the MSCCL++ low-latency expert-parallel backend or the FlashInfer backend to dispatch tokens to the GPUs that own the selected experts. A FusedMoE implementation performs the local expert GEMM computation, after which the backend combines the expert outputs and returns them to the tokens' original ranks. The benchmark validates the resulting output and reports the latency of the dispatch, expert GEMM, combine, and complete MoE pipeline, allowing the communication backends and MSCCL++ data layouts to be compared under the same representative MoE workload.

- Nodes: 2, 4, and 8.
- GB200 GPUs: 4 ranks per node, up to 32 ranks.
- Data type: BF16.
- Hidden size: 7168.
- Intermediate size: 2048.
- Top-k: 8.
- Experts per rank: 8 and 16.
- Tokens per rank: 16, 32, 64, and 128.
- Routing: deterministic balanced routing.
- Every run verified:
  - Equal aggregate routes per global expert.
  - No duplicate top-k expert for any token.

## Summary

The PR adds an MSCCL++ latency MoE A2A backend with rank-major (FlashInfer CUTLASS) and expert-major (Triton) layouts, shared communicator reuse, and a CUDA-graph benchmark. The dispatch/combine plumbing and runner adapters are directionally right, but production capacity handling does not match the MSCCL++ tensor contract: rank-major will raise on any batch smaller than the allocated max, expert-major (the default layout) never shrinks the padded GEMM, and dispatcher init uses raw `chunked_prefill_size`. There is also a real regression in `require_mlp_tp_gather` for speculative draft A2A.

**[bug]** Rank-major dispatch always passes the full-capacity buffer from `get_dispatch_output_buffer()` while also passing a possibly smaller `runtime_max_tokens_per_rank=active_capacity`. MSCCL++ `RequestBuilder._dispatch_buffer` exact-shape-checks that `output_buffer` against `dispatch_shape(..., active)`, which is `(num_ranks, active, hidden)` for rank-major. The cached buffer is `(num_ranks, allocation_capacity, hidden)`. The kernel benchmark hides this because it sizes `chunked_prefill_size` to the measured token count, but a real server allocates `max(prefill_capacity, decode_capacity)` once and then captures/runs CUDA-graph buckets with far fewer tokens. Those forwards will raise inside `mscclpp.ep` before any expert GEMM. The same path also forwards `active_capacity=0` for an idle/empty batch (`max(dp_global_num_tokens)==0` or `hidden_states.shape[0]==0`); the native API requires a positive capacity.

**Suggestion:** Do not pass the full-capacity tensor into `dispatch` when `active_capacity != allocation_capacity`. For rank-major, pass `output_buffer=None` (or `get_dispatch_output_buffer(runtime_max_tokens_per_rank=active_capacity)`) so the runtime returns an active-sized view of the same storage, and reject or clamp a 0-token active capacity the way FlashInfer A2A already allows empty payloads.

**[bug]** Expert-major always passes `runtime_max_tokens_per_rank=None`, so every dispatch uses the full `allocation_capacity`. The Triton pre-permute then flattens `hidden_states` to `num_local_experts * num_ranks * allocation_capacity` rows and runs `moe_align_block_size` / fused MoE over that padded table, skipping only `-1` slots. `_select_active_capacity` is computed and stored but not applied. Default `--mscclpp-ep-layout` is `expert_major`, so a decode step on a DeepSeek-scale config (for example 32 local experts, 8 ranks, prefill capacity 2k–16k) processes hundreds of thousands to millions of padded slots per layer. The advertised CUDA-graph decode path is therefore either extremely slow or large enough to OOM; the benchmark never sees this because its allocation equals the measured batch.

**Suggestion:** Pass `runtime_max_tokens_per_rank=active_capacity` for expert-major too. The native API already views the runtime dispatch buffer at the active shape when `output_buffer` is omitted; prefer that (or an active-shaped view) over a separately allocated full-capacity `torch.empty`, and keep one static allocation only as backing storage.

**[bug]** Prefill capacity is `ceil(chunked_prefill_size / attn_tp_size)` with no guard for non-positive values. Decode-only disaggregation sets `chunked_prefill_size == -1`, which hits `_resolve_capacity_per_attention_tp`'s `num_tokens must be non-negative` check and fails dispatcher construction. FlashInfer A2A already treats non-positive chunk size as 0 via `max_prefill_buffer_tokens()` and then takes `max(prefill, decode, 4096)`. This path also ignores PP dynamic chunking, which can grow a chunk to `max(max_prefill_tokens, 1.25 * chunked_prefill_size)`; those forwards will later raise `MSCCL++ active capacity exceeds the shared allocation`.

**Suggestion:** Mirror FlashInfer: derive prefill tokens from `max_prefill_buffer_tokens()` (so `-1`/0 and PP dynamic chunking are handled), then `max` with the decode-graph token budget, and keep a positive floor. Fail at init with a clear error if the resolved capacity is still 0.
