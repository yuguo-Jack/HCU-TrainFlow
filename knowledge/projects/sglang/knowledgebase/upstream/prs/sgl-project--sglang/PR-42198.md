# [Perf] [AMD] custom-all-reduce: Select the fused AR+RMSNorm 1-stage kernel by token count and read volume

[Upstream PR](https://github.com/sgl-project/sglang/pull/42198) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, `GroupCoordinator.fused_allreduce_rmsnorm` uses AITER's 1-stage fused AR+RMSNorm kernel only up to a 128 KiB payload, a cutoff that only fits TP=8; this PR bounds the kernel's read volume (`payload × world_size`) and token count instead, so TP=2/4 decode batches get the faster 1-stage kernel.

Each 1-stage rank reads every peer's full payload, so cost grows with `world_size × payload`; at bf16, hidden 6144, the fixed cutoff is hit at 10 tokens.

## Modifications

- Select 1-stage when `token_num <= 80` and `payload * world_size <= 8 * 128 KiB`. The budget is today's TP=8 cutoff and where 1-stage stops winning at TP=4. 80 is the 1-stage grid size (`kMaxBlocks`); the cap only binds when `hidden × world_size ≤ 6472` (bf16).
- TP=8 is unchanged. At hidden 6144, batches of 11–42 tokens (TP=2) and 11–21 tokens (TP=4) move to 1-stage.
- `SGLANG_USE_1STAGE_ALLREDUCE` still overrides; `fused_allreduce_rmsnorm_quant_per_group` keeps its own rule (#24651).
- `test_aiter_allreduce_fusion_amd.py`: `TestFusedArRmsStageSelection` (CPU) pins the selection at TP=2/4/8, the token cap and the env override.

AITER's own `CudaCommunicator` already scales this cutoff with world size (ROCm/aiter#3745); SGLang calls `custom_fused_ar_rms` directly, with a lower budget (1 MiB of reads, not 1.75 MiB). GLM-5.x enables the fusion for decode by default on ROCm; other models reach it at TP=2/4 with `--enable-aiter-allreduce-fusion`.

## Accuracy Tests

GSM8K 5-shot, greedy, 1319 items, `lm_eval`, `num_concurrent=16` (decode batches in the new window), strict-match. 8× MI355X, main `0072e2cc08` on sglang build `0.5.21.dev20261002+gedee4308bc`, amd-aiter `0.1.23.dev183`.

| model | TP | main | PR |
|---|---:|---|---|
| GLM-5.3 (FP8) | 4 | 0.9271 (0.9189–0.9310, 5 runs) | 0.9253 (0.9212–0.9287, 5 runs) |
| Qwen3.8-2.4T-A95B MXFP4 (control, same kernel) | 8 | 0.8355 / 0.8415 | 0.8393 |

- GLM-5.3: every PR run is inside main's range; per-sample verdict agreement is 95.1–96.7 % main vs. PR and 95.5–96.5 % main vs. main.
- Same inputs through both kernels (TP=4, hidden 6144, m = 8–20): residual is bit-identical; normed output differs in ~6 per million elements by 1 bf16 ulp.
- Test file on 2× MI355X (main `b960aa903a`, amd-aiter `0.1.26.dev144`): 15 passed, 1 skipped (8-GPU benchmark); the new selection tests fail on main.

## Speed Tests and Profiling

Same build, torch `2.11.0+rocm10.0.0`. Arms run in blocks of 4, first run discarded, two blocks in opposite order; e2e uses a fresh server per run.

Micro, `benchmark_fused_ar_rms_amd.py`, graph-mode p50, block-minimum gain per shape:

| TP | switched shapes | median gain | range | unchanged |
|---|---:|---:|---:|---:|
| 2 | 13 | **+17.2 %** | +13.7 … +23.2 % | −0.1 % ¹ |
| 4 | 14 | **+5.7 %** | +0.8 … +14.6 % | −0.5 … +0.1 % |
| 8 | 0 | — | — | −1.6 … +0.6 % |

¹ 131 × 6144; 3 × 6144 (8 µs) reads −2.3 % / +0.5 % across blocks.

At TP=4 the gain falls to +0.8 … +2.8 % at the edge of the read budget. At TP=2, with `use_1stage` forced, 1-stage is faster at every size measured (+15.6 % at 43 × 6144, +8.1 % at 81 × 2048, +7.8 % at 1024 × 7168), so the bounds are conservative.

Median TPOT −1.04 % / −1.56 %; TTFT −2.05 … +0.45 %, within spread. Only graph bs 12 and 16 switch kernel; 156 fused calls per decode step × 0.7–1.5 µs is 0.1–0.23 ms per step, consistent with TPOT.
