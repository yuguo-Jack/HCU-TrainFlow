# [Perf] disaggregation: Add the just_in_time decode allocation policy

[Upstream PR](https://github.com/sgl-project/sglang/pull/48205) · state: open · merged: False

## Original PR description

> Depends on #45337. This PR's own change is its last commit, `[PD] Add the just_in_time decode allocation policy`.

## Motivation

TL;DR Instead of allocating decode memory immediately under policy early (which wastes decode memory), or waiting until prefill completes under policy prefill_complete (which adds latency to kv-transfer), we should allocate decode memory precisely such that it aligns with kv-transfer start. This PR does so with policy just_in_time.

`--disaggregation-decode-allocation-policy prefill_complete` (#40703) makes decode reserve a request's KV slots only after prefill finishes, so a request does not hold decode memory while it waits for and runs prefill. The cost is that decode's reservation handshake runs after prefill instead of overlapping it: prefill signals readiness, decode admits the request and allocates, and decode's destination indices travel back (under PP, through the stage-0 consensus poll) before prefill may write the KV. `early` overlaps that handshake with prefill but reserves decode memory for the whole prefill.

`just_in_time` keeps the deferred reservation but starts the handshake while the request still prefills, timed so that decode's destination arrives about when prefill finishes: decode memory is reserved for roughly one handshake longer than under `prefill_complete`, and the handshake no longer adds to TTFT (time to first token).

On a GLM-5.2 deployment at 0.8 req/s, with #45337 applied, `prefill_complete` still trails `early` by 0.12-0.15 s of mean TTFT with a PP4 prefill. `just_in_time` closes that gap, and with a DEP4 prefill it saves another 0.24-0.36 s. At 0.8 req/s decode reserves 3.4x (PP4) and 23x (DEP4) less KV for not-yet-decodable requests than under `early`.

## Modifications

Prefill signals readiness at the last scheduling round whose predicted remaining prefill time R still covers the handshake latency H, i.e. `R >= H > R - t` for round interval t. R counts the request's unscheduled chunks at t each, plus the measured lead from scheduling a chunk to processing its result, which spans the pipeline under PP. A request whose whole prefill is shorter than H, or that arrives before any measurement, signals before its first forward. Completion of prefill stays the fallback signal.

- `DecodeReadinessPacer` (`disaggregation/decode_readiness.py`; stage 0 under PP) sees each scheduled prefill batch before launch in the normal, overlap and PP loops. It refreshes a tracked request's schedule time every round and recounts its remaining chunks until it signals, using the dynamic chunk sizer under PP dynamic chunking.
- t and the lead are medians of recent windows (the first requests after startup also pay compilation and would skew a mean).
- H runs from the readiness message to the arrival of decode's destination indices, both timestamped in `DeferredBootstrap` rather than observed by a scheduler poll. Readiness signaled before decode registered waits there, and that wait is not part of H. The estimate is the p90 of the last 64 handshakes, excluding the first with each decode endpoint (it also sets up connections) and, under PP, handshakes whose decode registration reached stage 0 after its final result, where another stage's readiness admitted the room first.
- Decode behaves exactly as under `prefill_complete`. Every `prefill_complete` check becomes a check against `DEFERRED_DECODE_ALLOCATION_POLICIES`, and `mark_prefill_complete` is renamed `signal_decode_readiness`.
- sgl-router treats `just_in_time` as a deferred policy for `--decode-dispatch-limit`.
- Docs describe `just_in_time`.

**Tests**

## Accuracy Tests

No accuracy eval was run. The change touches no model or kernel code; it changes when prefill signals readiness, so decode's destination can arrive while the request still prefills. `TestJustInTimeAllocation` checks that a request whose destination arrived mid-prefill returns the same tokens and logprobs as an unslowed repeat, with a single-GPU prefill, a PP2 prefill and an attention-DP2 + EP2 prefill.

## Speed Tests and Profiling

Same setup and client as #45337: GLM-5.2 NVFP4 with random weights on GB300, 8 GPUs per run, one prefill node (TP1 x PP4 with the PP scheduler, or DEP4 = TP4, attention DP4, EP4 with the overlap scheduler) and one DEP4 decode node, Mooncake over NVLink, MTP with simulated acceptance, a Dynamo frontend with KV routing, chunked prefill 16384. Prompts of 8k-40k random words (about 37-40k tokens at p50), 128 output tokens, Poisson arrivals in 180 s phases at 0.25 / 0.5 / 0.8 req/s, the same seed in every run. Each arm ran twice; every run completed with 0 errors. "Before" is `prefill_complete` with #45337; "after" is `just_in_time` on the same code.

**TTFT.** Mean paired difference (same request), ranges over the run pairings, ms, at 0.25 / 0.5 / 0.8 req/s:

| prefill | after vs before | after vs `early` | `early` vs `early` (noise) |
|---|---|---|---|
| PP4 | -38...+5 / -57...-76 / -119...-126 | +5...+43 / -24...+5 / -1...+28 | +16 / -12 / -26 |
| DEP4 | -144...-313 / -193...-437 / -243...-363 | -303...+108 / -269...+31 / -79...-43 | -278 / -170 / -20 |

With a PP4 prefill, `just_in_time` matches `early` within `early`'s own run-to-run spread. With a DEP4 prefill the saving is larger; these runs do not break down where the handshake spends its time in that topology. `early` keeps the default `--optimistic-prefill-attempts 0` in these runs (its requests wait for decode's allocation before prefill), and its run-to-run spread under DEP4 is large, so the DEP4 comparison against `early` is approximate.

**Decode KV reserved before the KV arrives.** Per request, decode's `transfer_duration` from `--enable-request-time-stats-logging` (destination allocated to KV arrived); "held" is input length x that duration summed over the phase and divided by its length. At 0.25 / 0.5 / 0.8 req/s, both runs:

| prefill | arm | mean hold (ms) | held tokens |
|---|---|---|---|
| PP4 | `early` | 1552-1562 / 1939-1962 / 2550-2590 | 14k / 37k / 79-81k |
| PP4 | before | 256-259 / 507-509 / 708-713 | 2.6k / 9.3k / 21.5k |
| PP4 | after | 474-494 / 603-605 / 759-762 | 4.4k / 11.6k / 23.7k |
| DEP4 | `early` | 2839-3136 / 3348-3502 / 4399-4437 | 27-30k / 68-71k / 145-146k |
| DEP4 | before | 139-150 / 222-225 / 283-301 | 1.4k / 4.0k / 8.7-9.4k |
| DEP4 | after | 387-580 / 127-133 / 205-211 | 3.0-4.4k / 2.3-2.5k / 6.3k |

With a PP4 prefill, decode reserves about 10% more than before (the transfer still starts only when every stage finishes), and 3.4x less than `early`. With a DEP4 prefill it reserves less than before at 0.5 and 0.8 req/s: the destination arrives before prefill ends, so finished chunks transfer during prefill as under `early`. At 0.25 req/s the first requests, before any handshake is measured, signal at their first chunk by design, which raises the mean hold.

A PP2 x DEP2 prefill (each stage TP2, attention DP2, EP2) also ran `just_in_time`: 0 errors, mean TTFT 1536 / 1824 / 2579 ms, mean hold 305 / 323 / 401 ms.

**ITL and throughput** are unchanged: ITL p50 6.7-7.1 ms in every phase of every run, output throughput about 30 / 58 / 94 tokens/s.

**Issue**

This test fails at the PR head. It never adds `req` to `scheduler.prefill_launched_reqs`, but `process_batch_result_disagg_prefill` now calls `move([req], self.prefill_launched_reqs, self.disagg_prefill_transfer_queue)` before it reaches the pacer. The call raises `RuntimeError: Requests ['aborted-prefill'] are not in PREFILL_LAUNCHED`, so `base-a-test-cpu` will fail once CI runs.

**Fix**

Add `scheduler.prefill_launched_reqs.join([req])` before the `with patch(...)` block, as `test_ready_observes_accepted_token_and_speculative_sidecars` does. With that one line, the test passes locally on CPU.
