# [Perf] hicache: Enable async ready-count sync by default

[Upstream PR](https://github.com/sgl-project/sglang/pull/45795) · state: open · merged: False

## Original PR description

Adapt based on @nvrohanv 's draft.
## Motivation

With `--enable-hierarchical-cache`, the scheduler calls `check_hicache_events` every step. It counts each rank's completed write-back (D→H) and load-back (H→D) acks and MIN-all-reduces the counts over the attention-TP CPU group. That way every rank consumes the same acks and the radix trees stay identical. The all-reduce is a **blocking gloo collective on the critical path of every step, decode included**.

The overlap scheduler hides it while the GPU step is long. Once the GPU step is short, as with fast decode kernels or small or sparse models at low concurrency, the CPU loop becomes the critical path. That one collective then adds directly to every decode step.

## Modifications

Async ready-count sync, **on by default**. `--disable-hicache-async-ready-sync` restores the blocking per-step sync, which is what stock main does, for example when debugging.

In the results below, **flag on** is this PR's default and **flag off** is `--disable-hicache-async-ready-sync`, which is identical to stock main. The data was collected while the flag was still opt-in; the code paths are the same.

- The ready-count all-reduce is issued with `async_op=True` on a **dedicated gloo group** in step N and consumed in step N+1.
- Safety rests on two invariants:
  1. Acks complete in queue order, and queues only grow at the tail. So a prefix that was ready on every rank in step N is still ready in step N+1.
  2. In step N each rank remembers the ack object that ends its ready prefix. In step N+1 it pops up to and including the agreed one. If a blocking write-back drain consumed it in between, it pops nothing, so there is no double consumption.
- The duplicate-reclaim digest check rides along and fires one step later.
- There is one async op per step on its own group, issued in the same order on every rank, so no new collective ordering is introduced.
- **Scope:** host-cache path with more than one attention rank and no storage backend, PP or attention CP. Other setups keep the synchronous sync and log the reason once at info level.
- **Runtime storage attach:** if a storage backend is attached later via the admin API, the in-flight sync is settled and the cache falls back to the synchronous path for good. The storage queues are only drained on that path. This fallback is added in this PR.
- **Cost:** the forward pass and TTFT are not delayed, because loaded KV is ordered by CUDA events, not by the ack. What moves one step later is the bookkeeping: finished load-back and write-through nodes are unlocked, and become evictable, one step later. Under tight device memory, slightly fewer tokens are evictable for that step. The cache also holds one extra gloo group per attention TP group.
- **Validation scope:** GB200, single node, TP4. PD decode, multi-node TP and non-NVIDIA backends are not yet covered; `--disable-hicache-async-ready-sync` is the escape hatch.

Files:
- `python/sglang/srt/mem_cache/unified_radix_cache.py`: deferred-sync logic, roughly 130 lines.
- `arg_groups/fields/memory.py`, `field_order.py`: the `--disable-hicache-async-ready-sync` flag.
- `docs/.../server_arguments.mdx`, `hicache_best_practices.mdx`: docs. The server-args docs-coverage test requires the row.

## Accuracy / correctness

Setup: GB200 NVL4, TP4, HiCache `write_through` with a 64 GB host pool. The device KV pool is capped at 65,536 tokens. 8 conversations × 4 turns of about 12K tokens each are visited round-robin, so revisits require host backup and load-back. Decoding is greedy with a fixed `--random-seed`.

| model setup | output token ids, flag on vs off | `cached_tokens`, flag on vs off |
|---|---|---|
| GLM-5.2 geometry, 12 layers (dummy) | 32 / 32 identical | 32 / 32 identical |
| GLM-5.2 geometry, 40 layers (dummy) | 32 / 32 identical | 32 / 32 identical |
| GLM-5.3-NVFP4, full 78 layers (dummy) | 32 / 32 identical | 32 / 32 identical |
| GLM-5.3-Flash-NVFP4, real weights + MTP (hybrid linear-attn) | not deterministic run-to-run (see note) | not deterministic run-to-run (see note) |

- Turn 1–3 hits are 11968, 12288 and 12544 tokens, which confirms load-back is exercised.
- With the flag on, every rank logs that the deferred ready-count sync runs on its own gloo group over ranks [0, 1, 2, 3]. With it off, none does.
- Unit tests (CPU, 2 simulated ranks with a fake async MIN all-reduce) cover these cases:
  - consume-count edge cases;
  - the result is consumed exactly one step later;
  - lockstep under rank skew, with new acks appended at the tail;
  - no double consumption after a blocking drain;
  - the digest-divergence assert;
  - the storage-attach fallback;
  - pending-sync drop on reset.
- **GSM8K on GLM-5.3-Flash-NVFP4, real weights + MTP** (EAGLE 3/1/4; full 1319 questions, 5-shot, parallel 64; one boot per mode, 3 passes per boot; invalid answers 0 % throughout):

  | | pass 1 | pass 2 | pass 3 | mean |
  |---|---|---|---|---|
  | flag off (stock) | 0.917 | 0.923 | 0.911 | 0.917 |
  | **flag on** | 0.915 | 0.925 | 0.922 | **0.921** |
  | HiCache disabled | 0.930 | 0.920 | 0.924 | 0.925 |

  All three overlap within pass-to-pass noise of about ±0.6 points, so the flag has no measurable accuracy effect. An earlier 500-question pass suggested a 2-point gap (on 0.906/0.912 vs. off 0.932/0.926). It did not hold at full size. MTP accept length was 3.50–3.62 in every boot.
- **Note on GLM-5.3-Flash:** token-exact comparison is not meaningful for this model. Two stock (flag-off) boots match each other on only 7/32 outputs and 28/32 `cached_tokens`, the same level as flag on vs. off (7/32 and 29/32). NVFP4 + MTP + hybrid linear attention is not run-to-run deterministic.

## Benchmark

All runs: GB200 NVL4, TP4, HiCache with a 64 GB host pool, and `--load-format dummy`. Dummy weights keep the kernels and step time real while letting the FP8 geometry fit on 4 GPUs.

The "12 layers" and "40 layers" setups are **the same `zai-org/GLM-5.2-FP8` architecture** with `num_hidden_layers` overridden (the real model has 78). They are not different models. 12 layers stands in for a short GPU step, as from fast decode kernels or a small model. 40 layers is the largest depth that fits. `nvidia/GLM-5.3-NVFP4` runs at its full 78 layers.

Each request uses a distinct 4K random prefix and 256 output tokens. Medians are of client-side streaming inter-token intervals, with no profiler attached.

**Short GPU step, CPU-bound (GLM-5.2 geometry, 12 layers): the sync is on the critical path.**

| | flag off (stock) | **flag on** | HiCache disabled (reference) |
|---|---|---|---|
| bs=1 decode step (8×4-turn trace, revisited ctx) | 2.18 ms | **1.79 ms (−18 %)** | 1.71 ms |
| ITL, concurrency 1 | 2.19 ms | **1.79 ms (−18 %)** | 1.69 ms |
| ITL, concurrency 8 | 2.27 ms | **1.85 ms (−19 %)** | 1.76 ms |
| ITL, concurrency 32 | 2.43 ms | **2.02 ms (−17 %)** | 1.94 ms |

HiCache's per-step overhead drops from 0.47 ms to 0.08 ms, so the flag removes about 83 % of it. The bs=1 gap reproduced across two independent server boots (2.15 → 1.80 ms and 2.18 → 1.79 ms).

**Real weights: `nvidia/GLM-5.3-Flash-NVFP4` + MTP (EAGLE 3/1/4): no reproducible latency change.** Two server boots per mode:

| | flag off #1 | flag off #2 | flag on #1 | flag on #2 |
|---|---|---|---|---|
| bs=1 decode iteration | 5.89 ms | 5.87 ms | 5.57 ms | 5.89 ms |
| ITL, concurrency 1 / 8 / 32 | 6.12 / 8.50 / 10.47 | 5.94 / 8.35 / 10.46 | 5.50 / 8.11 / 10.26 | 5.81 / 8.81 / 10.09 |

The first flag-on boot was faster, but the second matched flag off, so that gap is boot-to-boot variance.

**Long GPU step, GPU-bound: the sync is already hidden. There is no gain and no regression.**

| | flag off | flag on | HiCache disabled |
|---|---|---|---|
| GLM-5.2 geometry, 40 layers: bs=1 step | 4.48 ms | 4.48 ms | 4.48 ms |
| 40 layers: ITL, concurrency 1 / 8 / 32 | 4.44 / 4.78 / 4.96 | 4.43 / 4.78 / 4.96 | 4.43 / 4.78 / 4.96 |
| GLM-5.3-NVFP4, 78 layers: bs=1 step | 6.95 ms | *6.60 ms (boot variance, see note)* | 6.95 ms |
| 78 layers: ITL, concurrency 1 / 8 / 32 | 6.82 / 7.56 / 8.41 | *6.48 / 7.11 / 8.20 (boot variance)* | 6.82 / 7.56 / 8.41 |

On GLM-5.3 flag off equals HiCache off, so the sync is fully hidden there. The flag-on boot was faster than even HiCache off. Its trace shows that run's *GPU kernels* were about 0.2 ms per step faster: it was the first boot and ran a fresh FlashInfer autotune, while the others used the cache. That makes it boot-to-boot kernel variance, not this flag. The same pattern appeared on GLM-5.3-Flash, where a repeat flag-on boot matched flag off, so this row is treated as boot variance.

The flag pays off where the host is on the critical path, which matches the original internal measurements. When the GPU step is long, the overlap scheduler already hides the sync.

@YAMY1234 It isn't specific to write-through. With `--enable-hierarchical-cache`, `check_hicache_events` → `_sync_hicache_ready_counts` runs the MIN all-reduce on every scheduler step, whatever `--hicache-write-policy` is set to. The policy only changes when backups are issued (on insert for write-through, on eviction for write-back). That changes how many acks are queued, not whether the collective runs. In the traces above, the blocking sync costs about 0.53 ms per step during steady bs=1 decode, when there are almost no new write acks. So the cost is the gloo round-trip itself, not the ack volume. It isn't agg-only either: the PD decode path calls the same `check_hicache_events` (`disaggregation/decode.py`).

What is specific is the regime. It shows end-to-end only when the scheduler loop is on the critical path, i.e. low concurrency or a short GPU step, as in the 12-layer rows. In GPU-bound setups (40 and 78 layers) the overlap scheduler hides it. Happy to add a write-back run to the tables if that would help.
