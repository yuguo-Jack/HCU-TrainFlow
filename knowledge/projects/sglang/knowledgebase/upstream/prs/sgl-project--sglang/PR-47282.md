# [PD] Start bootstrap server before launching prefill schedulers

[Upstream PR](https://github.com/sgl-project/sglang/pull/47282) · state: open · merged: False

## Original PR description

## Motivation

With `RayEngine` (or `--use-ray`) and `--disaggregation-mode prefill`, every PD request fails with `Decode handshake failed ... KVTransferError: Aborted by AbortReq.` The prefill's bootstrap server answers every decode lookup with `503 Prefill server not fully registered yet (0 workers registered).`, and this never recovers.

Prefill schedulers register to the PD bootstrap server synchronously while they initialize (`CommonKVManager.__init__` -> `register_to_bootstrap()`). They retry for about 12-15 s, then log an error and give up for good. The server itself was created by `TokenizerManager.init_disaggregation` (or `MultiTokenizerRouter`), which `Engine._launch_subprocesses` only builds after `_launch_scheduler_processes` returns:

- **Plain `Engine`:** `_launch_scheduler_processes` returns right after spawning, and the wait happens later in `wait_for_ready()`. Registration only works because scheduler startup is slower than tokenizer manager startup.
- **`RayEngine`:** `_launch_scheduler_processes` blocks on `ray.get(actor.get_info.remote())` until every `SchedulerActor.__init__` has finished, and registration happens inside `__init__`. So it always hits a closed port, and nothing re-registers. The Ray DP path (`RayDataParallelController`) has the same ordering.

Seen in a Ray Serve SGLang PD release test (NIXL backend). The run hit the 1 h job timeout with no error naming the cause: `RayEngine` defaults to `log_level="error"`, which hides the per-attempt registration warnings.

## Modifications

**Start the bootstrap server before the schedulers** (`engine.py`)
- `Engine._launch_subprocesses` starts the PD bootstrap server before `_launch_scheduler_processes`, on node rank 0. Python mode uses `start_disagg_service()`. Rust-server mode uses `start_disagg_service_for_rust_server()`, which previously ran after scheduler launch.
- The launcher owns the handle through `SchedulerInitResult.disaggregation_bootstrap_server`. This replaces the write-only `kv_bootstrap_server` field.
- `TokenizerManager` and `MultiTokenizerRouter` no longer create the server.

**Release the port on failure and shutdown**
- If startup fails after the server is up, an `ExitStack` closes it. On success, ownership passes to the caller.
- `Engine.shutdown()` closes it through `SchedulerInitResult.stop_disaggregation_bootstrap_server()`, and calling it twice is safe.
- `start_disagg_service()` closes its listener if creating the Ascend config store fails.
- `CommonKVBootstrapServer` creates its event loop before starting its thread and stops on a shutdown event, so `close()` works even before the thread runs.

**Fail loudly when registration never succeeds** (`common/conn.py`)
- `_register_topology_row` raises `RuntimeError` once its retries run out, instead of logging and returning. The message includes the URL and the last failure (HTTP status, or the root-cause exception such as `connection refused`), so the cause shows up even at `log_level="error"`. Retry count and backoff are unchanged.
- At startup this surfaces as a scheduler process or Ray actor init error, so the launch fails instead of serving. During a runtime PD role switch, `handle_pd_role_switch` already treats an exception from `init_disaggregation()` as fatal and marks the instance unhealthy.
- Updated the comment in `Scheduler.init_disaggregation` that described the old "retries ~60s then logs" behavior.

**Interface change for forks**
- The `start_pd_bootstrap_service` keyword is removed from `TokenizerManager.__init__` and `TokenizerManager.init_disaggregation`.
- The unused `TokenizerManager.bootstrap_server`, `MultiTokenizerRouter.disaggregation_bootstrap_server` and `SchedulerInitResult.kv_bootstrap_server` attributes are gone.
- The `init_tokenizer_manager_func` hook is unchanged, so custom tokenizer manager factories keep working and don't start a second server.

## Tests

`test/registered/unit/disaggregation/test_register_to_bootstrap.py` (CPU only, 18 tests):
- **Launch order:** runs the real `Engine._launch_subprocesses` in prefill mode, in both Python and rust-server mode. The patched scheduler launch registers a prefill rank (PUT `/route`) against the real bootstrap server. Both tests fail on `main` with `['connection refused'] != [200]`. They also check that the server outlives a successful launch.
- **Cleanup:** the port is released when startup fails (scheduler, tokenizer and readiness stages), when the config store fails, on shutdown (including a second shutdown), and on a close that comes before the server thread starts.
- **Registration:** exhausting the retries raises, and the error names the HTTP status or the root cause. The existing backoff and jitter tests now expect the raise.

I also ran 167 unit test files under `entrypoints/`, `managers/` and `disaggregation/`, plus launcher-adjacent files, one process per file, on this branch and on `main`. Pass/fail is identical on both. Files that fail locally fail the same way on `main` for environment reasons (macOS, CPU-only, older torch).

Not run: an end-to-end Ray + GPU PD deployment.
