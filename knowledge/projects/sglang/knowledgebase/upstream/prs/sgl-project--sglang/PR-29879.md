# [Feat] metrics: Add forward-pass decode interference metrics

[Upstream PR](https://github.com/sgl-project/sglang/pull/29879) · state: open · merged: False

## Original PR description

## What changed

This PR adds three per-step histograms. Each batch is sampled by exactly one scheduler rank: attention TP rank 0 and attention CP rank 0 on the final PP stage. That is the same predicate the FPM publisher uses (`_is_forward_pass_metrics_rank()`). With `--enable-dp-attention`, each attention DP group runs its own batch and emits its own series under its `dp_rank` label.

- `sglang:forward_pass_duration_seconds`: device-measured time of the batch's own forward segments. When one batch launches several segments (e.g. speculative draft + verify), their times are added. Labels: `phase`, `prefill_tokens_bucket`, `decode_reqs_bucket`.
- `sglang:decode_step_latency_seconds`: the same measurement, limited to passes with decode requests. Labels: `phase` (`decode_only` / `mixed`), `co_scheduled_prefill_bucket`, `decode_reqs_bucket`.
- `sglang:schedule_to_result_latency_seconds`: wall time from the start of batch selection to the end of result processing. Under overlap it includes the next batch's selection and launch, so it measures an engine step, not forward time.

**Attribution under overlap.** `run_batch` stamps each batch with the `[begin, end)` range of device-timer segments it launched (`DeviceTimer.num_started`). Result processing claims exactly that range. `event_loop_overlap` launches n+1 before it processes n, and n+1's forward is never charged to n. A step is skipped if it launched no timed segment, or if one of its segments has not finished. The metric never waits on the device.

**Enabling.**
- `--enable-metrics` alone exports only `schedule_to_result_latency_seconds`, on unified, PP and PD-disaggregated schedulers.
- The two forward-pass series also need the device timer: `SGLANG_ENABLE_METRICS_DEVICE_TIMER=1` or `--enable-forward-pass-metrics`. Without either, they stay empty.

**Other changes.**
- Labels come from an O(1) count on the batch (`prefill_stats`, `decoding_reqs`). They never read `seq_lens_cpu`, which spec-v2 overlap can leave as `None`. A decode batch that DP attention runs as a 1-token extend counts as decode.
- `fpm_start_time` is stamped on every batch selection, at the cost of one `time.monotonic()` call. This includes the PD-disaggregation decode and prefill selectors and the PP disaggregated prefill loop.
- FPM behavior change: the FPM publisher now also requires `attn_cp_rank == 0`. Before, every CP rank of a DP group started a publisher on the same `{base}.{dp_rank}` endpoint.
- Docs: `docs/docs/references/production_metrics.mdx`. It covers how to read the metrics, rank and DP semantics, and PromQL examples.

**Known limits.**
- With `--pp-size`, the forward-pass value is the final stage's forward, not full-model latency.
- FPM (ZMQ) `wall_time` still drains the device timer in bulk. #38711 addresses FPM timing ownership.
- Tested on CPU only (see Validation).

## Why

The production symptom this targets is: decode requests are streaming normally, then a long prompt/prefill request joins the scheduler batch, and existing decode streams suddenly see a p99 inter-token latency / TPOT spike. Request-level TPOT and ITL metrics are useful for user-visible latency, but they aggregate over a whole request. They do not tell us whether the slow decode token was delayed specifically by a long prefill that was co-scheduled in the same scheduler/model forward pass.

In production, this commonly shows up with mixed traffic:

- A chat workload has many short streaming decode requests already running.
- A retrieval or agent request arrives with a very large prompt, for example a 32k-100k token context assembled from documents, tool traces, or conversation history.
- The scheduler admits that prefill alongside active decode work in a mixed batch.
- Users on unrelated decode streams observe one or more slow token intervals, but the completed-request TPOT metric only says those requests had a bad tail. It does not identify the interfering engine step.

The right diagnostic unit is the scheduler/model forward pass, not the completed request. This PR records the device-measured time of each forward pass. Separately, it records decode-step latency for passes that include decode requests, and a schedule-to-result interval that also covers scheduling and launch cost. The labels intentionally stay low-cardinality: phase, bucketed co-scheduled prefill token count, and bucketed decode request count.

With these metrics, operators can compare:

- decode-only p99, where no prefill work was co-scheduled;
- mixed prefill+decode p99;
- mixed p99 grouped by co-scheduled prefill token buckets such as `16k_64k` and `64k_plus`.

A practical production diagnosis becomes possible: if `sglang:decode_step_latency_seconds` p99 for `phase="mixed"` and `co_scheduled_prefill_bucket="16k_64k"` or `"64k_plus"` is repeatedly much higher than `phase="decode_only"`, long prefill co-scheduling is likely contributing to decode ITL/TPOT tails. That gives an actionable signal for tuning chunked prefill, mixed batching, prefill throttling, or prefill/decode disaggregation.

This metric is intentionally not a replacement for completed-request TPOT. It is a forward-pass-level interference signal. Speculative decoding, stream interval, and two-batch-overlap can make one forward pass only an approximation of one visible token interval, so the metric should be interpreted as an engine-step latency proxy.

## Supporting data point: forward-pass granularity is also what engine-stall forensics needs

A recent production incident we root-caused (on vLLM, but the lesson is
engine-agnostic: vllm-project/vllm#37729,
[trigger analysis](https://github.com/vllm-project/vllm/issues/37729#issuecomment-5018012967))
is a strong argument for exactly the framing this PR takes — that the
scheduler/model forward pass, not the completed request, is the right unit of
observation.

**The incident**: a flashinfer <= 0.6.13 Blackwell GDN prefill kernel hangs
permanently depending on **batch composition** — a forward pass whose varlen
batch had >= 5 rows with any row length not a multiple of 128 could wedge the
engine forever. No request-level metric could have localized this: the failure
was a property of which prefills the scheduler co-scheduled into one pass, not
of any individual request. We only found the trigger by instrumenting per-pass
batch shapes — effectively hand-rolling a crude version of what this PR
provides as standing metrics.

**Second, the detection angle.** During the wedge, every aggregate signal
failed in practice: the health endpoint stayed 200, and in one captured wedge
the running-requests gauge read 0 because the hang landed before the gauge
update, so gauge-based alerting misclassified a dead engine as idle.
Per-forward-pass metrics give the cleanest liveness signal we know of:
`rate(forward_pass_duration_seconds_count) == 0` while work exists cannot be
faked by a stale gauge.

One caveat worth designing for: a *hung* pass never completes, so the histogram
observation never fires — the stall is visible only as an absence of samples. A
tiny extension would make it a positive signal: also count pass *starts* (or
expose a last-pass-started timestamp). Then `started - completed > 0` sustained
for N seconds is an unambiguous mid-pass stall signature, distinguishable from
"no traffic" without reference to any gauge. That is precisely the signal our
incident needed and none of the existing metrics provided.

Happy to share the batch-shape instrumentation or the incident's forensic data
if useful as a validation scenario.

That makes the number wrong in the specific direction that matters here: the metric exists to attribute decode slowdown, and this construction folds scheduling work into what a reader will interpret as forward time, so it would mislead exactly during the incident it is meant to explain. Your `disable_overlap_for_batch` observation is a good confirmation — that branch has the selection delay but not the launch delay, which is precisely the asymmetry you'd expect if the interval is bounded by the wrong event.

`_forward_pass_composition` counts decode requests as `len(batch.decoding_reqs)`, and `decoding_reqs` is set only when `mix_with_running` merges the running batch into the prefill batch. Without mixed chunk, `get_next_batch_to_run` runs the prefill batch first and the running decode batch waits a whole step. That step is recorded as `forward_pass_duration_seconds{phase="prefill_only", decode_reqs_bucket="0"}` and never reaches `decode_step_latency_seconds`.

So the check in the docs (`mixed` p99 against `decode_only` p99) shows no interference while prefill is stalling streams. Mixed chunk is off by default on current `main`, and some configurations (diffusion LLMs, HiSparse, several speculative decoding setups) turn it off or reject it, so enabling it doesn't always work around this.

I measured this client-side with Qwen3-8B on one H100, SGLang v0.5.21, defaults (mixed chunk off, chunked prefill 8,192). The load was 8 short streaming requests/s, alone and then with one 3,118-token prompt per second added:

| | alone | with long prompts |
|---|---|---|
| inter-token gaps over 50 ms, per minute | 27 | 361 |
| replies with such a gap | 5% | 48% |
| p99 inter-token gap | 20 ms | 23 ms |
| p99.9 inter-token gap | 33 ms | 84 ms |
| longest gap | 108 ms | 255 ms |

724 of the 739 gaps over 30 ms began within 0.15 s of a long prompt arriving. Each long prompt fits in one 8,192-token chunk, so these gaps are prefill-only steps (one, or a few back to back) while the decode batch waits.

A possible fix: `prefill_stats` already carries `num_running_reqs` for the batch that waits. For an extend pass without `decoding_reqs`, record the pass in `decode_step_latency_seconds` under its own phase, e.g. `phase="prefill_blocking"`, with `decode_reqs_bucket` from that count. The docs would then compare `mixed|prefill_blocking` against `decode_only`. I'm happy to send this as a commit on your branch or as a follow-up PR, whichever you prefer.
