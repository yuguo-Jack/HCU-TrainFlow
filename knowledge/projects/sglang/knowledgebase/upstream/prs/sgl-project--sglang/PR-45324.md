# [Perf] [AMD] diffusion: Fuse the FLUX.2 SwiGLU into its FP8 quantize and drop the concatenation

[Upstream PR](https://github.com/sgl-project/sglang/pull/45324) · state: closed · merged: False

## Original PR description

## Motivation

**What goes wrong**
In the FLUX.2 single transformer block on gfx1250, the output projection's input is built in two full passes over HBM that exist only to satisfy the shape of the GEMM that follows. `Flux2ParallelSelfAttention.forward` applies the SwiGLU to the `[4112, 36864]` gate/up projection and writes the `[4112, 18432]` activation back as bf16, concatenates it with the attention output into a `[4112, 24576]` bf16 tensor, and only then quantizes that tensor to FP8 for the GEMM. The concatenation exists because one GEMM takes one activation operand with one per-token scale, so the two halves have to be made adjacent and put on a shared scale first. That shared scale is also a numerical cost: whichever half has the larger magnitude sets the row's exponent and crushes the other.

**Where it shows up**
Every gfx1250 run that serves FLUX.2 with online FP8, which is the path #45304 adds; the 48 single blocks account for 288 of these per profiled capture. MI300X and MI355X do not reach it -- the branch is gated on `Fp8LinearMethod.use_gfx1250_triton_fp8`, which requires `is_gfx1250_supported()`, so every other device and NVIDIA keep the existing concatenate-then-GEMM path byte for byte. The dual blocks also keep it: they have no concatenation to remove.

**How to fix**
Quantize the activation directly out of the gate/up projection so the bf16 activation never reaches HBM, and pass the attention output and the activation to the GEMM as two separately scaled K segments so the concatenation is not needed at all.

## Modifications

- `kernels/ops/gemm/fp8_gfx1250.py`: `swiglu_quant_fp8_gfx1250` computes `silu(gate) * up` and quantizes it to FP8 with a per-row scale in one kernel. It reads strided rows natively, because the gate/up operand is a column slice of the fused qkv+mlp projection and copying it to make it contiguous costs more than the fusion saves.
- `kernels/ops/gemm/fp8_gfx1250.py`: `gfx1250_fp8_scaled_mm_2seg` multiplies `concat(a1, a2) @ b` without materializing the concatenation, with an independent per-token scale per segment. Both segments share one accumulator; one tile multiply at the seam rebases it from the first segment's scale onto the second's, which costs far less than the second `BLOCK_M x BLOCK_N` accumulator a two-scale sum would need. Both quantizers map an all-zero row to a scale of 1.0, so the ratio is always finite.
- `multimodal_gen/.../quantization/fp8.py`: `try_flux2_gfx1250_fp8_swiglu_linear` wires the two together and returns `None` for any shape the tiles do not cover, leaving the caller on its existing path.
- `multimodal_gen/.../models/dits/flux_2.py`: the single block takes that path when `_enable_gfx1250_fp8_token_cat` is set, alongside the existing ModelOpt FP8 and NVFP4 token-cat hooks.

## Accuracy Tests

No accuracy harness applies to an image diffusion model; the gate is the rendered image, and this change does not alter it visibly. At the kernel level the fused path is **more** accurate than the one it replaces, which the test asserts rather than assumes:

| path | relative error vs fp32 |
|---|---|
| concatenate then GEMM (shared row scale) | baseline |
| fused, independent per-segment scales | **<= the above, asserted** |

`test_matches_cat_then_linear` scores both against an fp32 reference and fails if the fused path is the worse of the two. The two FP8 paths cannot be compared to each other directly -- they differ by ~3.5% on synthetic data purely because they quantize differently -- so comparing them to each other would have been a meaningless assertion.

12 tests / 21 subtests: strided and contiguous gate/up slices, ragged M (4111), small N, bias and no bias, all-zero rows, two segments with a 3x magnitude gap (a shared scale would visibly degrade one of them and fail the test), and rejection of shapes the K loop cannot cover.

## Benchmarking and Profiling

FLUX.2-dev, 720p, 100 denoise steps, seed 42, one gfx1250, `--quantization fp8 --enable-torch-compile true --attention-backend aiter`. Three repetitions each, serialized on one idle GPU, warm compile cache, no profiler attached. Base is this PR's parent (#45304 head).

| | rep 1 | rep 2 | rep 3 | mean |
|---|---|---|---|---|
| base (#45304) | 0.5234 | 0.5288 | 0.5211 | **0.5244 s/step** |
| + this change | 0.5263 | 0.5139 | 0.5171 | **0.5191 s/step** |

**-1.0%, inside the repetition spread** (1.0% and 2.4%). A matched pair of profiles -- same step count, same GPU, same runner -- scores the pointwise region at **+15 ms of GPU time over three steps**, i.e. slightly negative. The two disagree in sign and both are small: the honest reading is neutral.

Per kernel, the fusion does what it was designed to do and it is still not enough:

| | before | after |
|---|---|---|
| SwiGLU + concatenate (`cat_mul_silu_slice`) | 207 us | - |
| quantize `[4112, 24576]` | 104 us | - |
| fused SwiGLU + quantize | - | 330 us |
| extra attention-side quantize | - | 34 us |
| **total per block** | **311 us** | **364 us** |

It moves strictly fewer bytes -- 379 MB against 858 MB -- and is slower anyway, because it cannot stream them as well: ~1.15 TB/s against the 2.76 TB/s the two kernels it replaces achieve, against a 2.93 TB/s measured HBM ceiling. The cost is the two-pass row re-read. Reaching the per-row amax of a 18432-wide activation in one pass needs the row resident in registers, which spills on this target (266.7 us against 149.6 us for streaming it twice), and splitting the amax across the grid with `tl.atomic_max` on f32 is roughly 30x slower still (5.2-8.4 ms against 0.19 ms). Both alternatives are recorded here so the next person does not re-derive them.

Where this could still be worth having: the traffic reduction scales with M while the bandwidth penalty is a property of this kernel and this compiler, so a part with less bandwidth headroom, a larger batch, or a Triton release that stops spilling the single-pass form would move it into positive territory. On this part today it does not.
