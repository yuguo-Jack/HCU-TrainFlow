# [Feat] parser: Add Beam reasoning, tool calls and response templates (5/7)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45257) · state: closed · merged: True

## Original PR description

## Motivation

Split #44747 into reviewable parts. This is the parser and response templates part, position 5 of 7 in the merge order below. It also adds the Beam E2E test, which needs both the model and these parsers.

## Modifications

Beam reasoning and tool-call parsing, built on #40479's response-template adapters, across Chat Completions, Responses and Messages:
- **Parsers.** `--reasoning-parser beam` and `--tool-call-parser beam` (also auto-detected from the chat template) use Beam's response template; checkpoint `response_template` metadata takes precedence over the built-in fallback.
- **Grammars.** Structural tags are derived from the template for required, named and strict tool choice. Unconstrained turns get a turn grammar that holds Beam's trained format, reasoning followed by tool calls or an answer, never both (`SGLANG_ENABLE_RESPONSE_TEMPLATE_TURN_GRAMMAR`, on by default with the XGrammar backend; set `0` to turn it off). A JSON `response_format` is framed as Beam's answer, which the model may replace with tool calls; it never writes calls followed by an answer in one turn.
- **Answer text stays text.** While Beam's grammar constrains the turn, tool extraction stops at the answer opener, including with `separate_reasoning=false` and when the prompt already opened the answer. Template markup inside the answer stays answer data, and answer or call openers quoted inside the reasoning stay reasoning.
- **Responses.** The `shell` tool (`environment: {type: local}`) maps to the `bash` tool the chat template declares; namespace tools are flattened for Beam and returned with separate `namespace` and `name`.
- **Messages.** Tool `strict`, `disable_parallel_tool_use` and `output_config.format` (also in `count_tokens`); invalid requests found while converting a request (`ValueError`) return HTTP 400 instead of 500.
- **`/tokenize`** with chat `messages` takes `add_generation_prompt` to render them exactly as given, and then honours `add_special_tokens` (default `false`); this needs a Jinja chat template (documented in `native_api.mdx`).

Where Beam differs from #40479's defaults:
- Strict tools and `parallel_tool_calls=false` with automatic tool choice are enforced through Beam's structural tag instead of being rejected; the response-template tool detector's `validate_structure_constraint_request` returns that tag.
- With a JSON `response_format`, tools stay callable: Beam's grammar admits tool calls instead of the answer, and they are parsed until the answer opens. Other response-template models keep #40479's behaviour of applying the schema and parsing no calls.
- Beam's grammar admits declared tool names only; parsing follows `SGLANG_FORWARD_UNKNOWN_TOOLS`, as in #40479.

Behaviour changes outside Beam:
- Response-template argument coercion: when the schema allows a string and other types, text converts to one of the others only when it is exactly that type's JSON (`"7"` becomes `7`; `"007"` and `"123_456"` stay strings); a value written as a JSON string stays a string when the schema allows strings; integer text parses without float rounding; and parameters declared through a local `$ref`, a single `allOf` or `enum`/`const` are coerced to their type.
- Responses: named tool-choice echoes keep `custom` and `namespace`; non-Harmony lifecycle events echo the request's tools; tool definitions keep fields SGLang does not model (the shell tool's `environment` needs this); non-streaming reasoning items report `status: "completed"`, also for native chat encoders; replay attaches a reasoning item to the assistant message that follows it, even when that message carries a `phase`. `shell` is now a known tool type that models other than Beam reject with HTTP 400 (before, it failed schema validation).
- Messages: the options above apply to every model. With a response-template reasoning parser and a Jinja chat template that reads `reasoning_content`, earlier thinking blocks are passed to the template as `reasoning_content` instead of being wrapped into the content.
- `/tokenize`: the formatting options above apply to every model with a Jinja chat template.

Adds `test/registered/e2e/models/test_beam_10_b200_pd.py`, a nightly test on the 8-GPU B200 runner (per-commit CI has no 8-GPU B200 job), modelled on Muse Spark's B300 1P1D test: prefill TP4 and decode TP4 over Mooncake with DFlash2, the full GSM8K set through sgl-eval with Beam's recommended sampling (temperature 0.7, top_p 0.99), a decode-side accept-length check and the single-request speed check. It uses the cookbook B300 NVFP4 low-latency flags except `--enable-unified-memory`, which PD rejects together with speculative decoding over Mooncake.

The Responses shell tool needs OpenAI 2.8.0 (#45291, merged); this part changes no pyproject.

Its branch merges #45256, which should land first; its dependencies #40478, #43941 and #40479 have merged into main, so its diff is Beam's own changes: **42 files (+6,950 / -413)**: 26 source and doc files and 16 test files (6 new, including the E2E test). The split commit carries the 8 `Co-authored-by` trailers of the Beam commits that touched these files.

## Validation

- On 8×H200 with the public `reflection/Beam-1.0-501B-A23B-FP8` checkpoint and the cookbook H200 FP8 low-latency recipe (TP8, DFlash2), this branch + #43216:
  - the [Beam Verifier](https://github.com/reflection-oss/beam-verifier) at `dfa85fe771` passes its required suites 133/133: 131 cases at its defaults and the 2 recall cases at temperature 0. The optional suites and evals did not run;
  - chat reasoning, streaming, chat tool calls (streaming and not), Responses text, a Responses function call, a full Responses shell round trip, a Messages tool call and `/tokenize` all pass;
  - the required suite is not always 131/131: in repeated runs (18 runs, 36 `python_repl_sqrt` requests at the verifier's temperature 0.7), that case ran to `max_tokens` 4 times; no other case did. See the residual risk below.
- All 71 CPU-registered unit test files under `test/registered/unit/{parser,function_call,constrained,entrypoints}` (69) plus `beam_search/test_output_decode.py` and `managers/test_trim_matched_stop.py` pass on Linux; the Beam E2E file collects; pre-commit passes on every changed file.
- This revision moves the Beam E2E test from the per-commit 8-GPU B300 runner to the nightly 8-GPU B200 runner. It has not run on B200 yet; Beam's cookbook lists NVFP4 for B300 and GB300 only. When the stack was published it passed on two 4×GB300 nodes (prefill TP4 on one, decode TP4 on the other, Mooncake over multi-node NVLink, in place of the test's single-node 8-GPU layout): GSM8K 96.51–96.89% at temperature 0.7 over three runs, decode accept length 4.53–4.55, and single-request accept length 4.92 at about 750 tok/s. Its GPU workload was not rerun here.
- Residual risk: under the turn grammar, a strict text argument can only end with its exact closer (`\n</rfl:parameter>`), and stop tokens are masked inside it. If the model slips inside such a value (for example `">` right after the code in a `Python_REPL(query)` call), it cannot stop and writes until `max_tokens`; the output is unusable and the call is dropped. Letting a call closer also end the value removed the runaway, but the model then often skipped `</rfl:parameter>` on ordinary calls and those calls were dropped (14 of 22 repeated required-suite runs failed instead of about 3 of 11), so the forced closer is kept. Clients should set `max_tokens`.
- Not measured: the decode cost of the default-on turn grammar. Beam's grammars were tested with XGrammar only. Without the turn grammar (turned off, or another grammar backend), a call opener quoted in a text answer or in unseparated reasoning is parsed as #40479 parses it, which drops an unclosed call together with the text after it.

## Merge order

Each part is based on the one before it in the stack. Merge bottom-up; after each part merges, the next part is retargeted to `main` and `main` is merged into it. #44747 stays open, unchanged, as the full reference. Merge in this order:

1. #45253 — Beam CUDA Docker image (merged)
2. #45291 — OpenAI SDK 2.8.0, needed by the Responses shell tool in #45257 (merged)
3. #45254 — Kernels
4. #45256 — Attention, memory and DFlash DP support, and the Beam model (#45255 folded in; also after #43216)
5. #45257 — Beam reasoning, tool calls, response templates and the Beam E2E test (#40479, #40478 and #43941 are merged)
6. #45290 — `nvidia-cuda-tileiras`, needed by #45361
7. #45361 — cuTile BF16x3 router GEMM (optional: without it Beam uses the cuBLAS router)

#45292 (Dynamo and `grpcio-tools` pins for the Beam image) is not in the merge order for now.
