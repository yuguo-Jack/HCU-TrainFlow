# [mm] Release multimodal features at consumption (opt-in) to bound host memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/37473) · state: open · merged: False

## Original PR description

## Motivation

Multimodal CPU feature tensors are retained until a request fully finishes. Under high-concurrency vision serving with long decodes (and multi-turn clients that resend image history each turn), the retained pool grows with live requests × images and can exhaust host memory on the serving node.

Once an image's features have been consumed into the multimodal embedding for prefill, the CPU-side tensor is no longer needed for that request: with radix caching enabled, a retracted request re-prefills from the retained prompt KV, not from the features. This PR releases each feature at that point instead of at request finish, bounding host memory by in-flight prefill rather than in-flight requests.

## Modifications

- New opt-in flag `SGLANG_ENABLE_MM_RELEASE_AT_CONSUMPTION` (default off; documented in `environment_variables.mdx`). Policy helper `should_release_mm_features` additionally requires radix caching (retract re-prefill reads the retained prompt KV) and `pp_size == 1` (only the first PP stage consumes features).
- `mm_utils.release_consumed_mm_features`: releases each mm item (tensor- or list-backed) once its token span is fully covered by the prefilled/matched prefix, using per-item offsets vs. the chunk end.
- Retraction keeps the prompt: when a request whose features were released is retracted, `release_req` takes a tree lock on its prompt node, so it re-prefills from the cached prompt KV. The hold is dropped once the request is admitted again or aborted from the queue. This means such a retraction frees only the request's decode tokens.
- If the prefix is still missing at readmission, the request is aborted with a retryable 503 (`_abort_mm_req_with_released_features`) instead of recomputing with missing features. This also covers a later session turn whose cached history was evicted.

With the flag off (default), feature retention behavior is unchanged; the only addition on that path is the policy check.

## Accuracy Tests

`test/registered/unit/managers/test_mm_release_at_consumption.py` (5 CPU tests included in this PR) covers:

- release/re-prefill offset boundaries of `release_consumed_mm_features`,
- the enablement policy truth-table (flag × radix × pp_size),
- the released-feature abort: retryable 503, remaining features released, beam group retired,
- the same abort for a session turn whose released history was evicted,
- retraction holding the prompt KV in a `RadixCache` through eviction until the hold is released.

## Speed Tests and Profiling

Opt-in and off by default. Enabled, the release check is per-chunk bookkeeping over the request's mm items and their offsets on the scheduler CPU path.

### 1. Retracted requests always fail with 503 under real KV pressure

Setup: Qwen3-VL-8B-Instruct, TP1, `--chunked-prefill-size 512 --max-total-tokens 40000 --mem-fraction-static 0.8 --schedule-conservativeness 0.05`. 128 concurrent requests, one 896x896 image each (801 prompt tokens), a long-story prompt, `max_tokens=4096`, temperature 0. The retractions are normal "KV cache pool is full" ones, not `SGLANG_TEST_RETRACT`.

| code | flag | retracted | 200 / 503 | scheduler RSS during load |
|---|---|---|---|---|
| this PR as is (ede5d34216) | on | 27 | 101 / 27 | 2948 -> 3031 MiB |
| rebased + patch below | on | 27 | 101 / 27 | 2995 -> 3032 MiB |
| rebased + patch below | off | 29 | 128 / 0 | 3802 -> 4096 MiB |

Every retracted request failed. All 503s came in one scheduling pass, about 350 s after the requests were sent.

What happens:
- `release_req` does not put the retracted request's KV back into the tree (see the TODO there), and it calls `evict_from_tree_cache` right away.
- The request goes back into the queue with a new `wait_queue_entry_time`, so with FCFS it waits behind everything already queued (about 100 requests here).
- The check in `get_new_batch_prefill` only runs when the loop reaches the request. By then the prompt KV has been evicted, so `has_released_items_beyond_prefix` is true and the request is aborted.

So on main, a retracted request usually cannot re-prefill from the retained prompt KV. And retraction is most likely under exactly the load this flag is meant for. Some options:
- When retracting a request whose features were released, keep its prompt prefix locked in the tree until it is scheduled again, and only free the decode part.
- Or decide at retraction time: if the prefix can't be kept, abort right away instead of after minutes in the queue.
- When choosing which requests to retract, prefer ones that still hold their features.

Without retraction the flag works well. With 64 concurrent requests and no retraction, outputs at temperature 0 matched flag-off exactly, and scheduler RSS growth dropped from +629 MiB to +58 MiB.

### 2. Overlap with #43475

#43475 (merged on 10-11) added `Req.release_mm_inputs_on_abort()` and calls it from `_release_aborted_request`. That covers queue-limit rejection, priority preemption, queued abort, and the new 503 path. For session requests it releases only the current turn's media and keeps the history.

After the rebase, the `release_features()` calls this PR adds on those paths are either no-ops (`multimodal_inputs` is already None) or a second release. `test_terminal_release_spares_session_features` calls `_abort_on_queued_limit` directly, so it misses the release that `_add_request_to_queue` does right after. Main's `test_multimodal_abort_cleanup.py` already covers these cases.

### 3. Smaller points

- `release_consumed_mm_features` doesn't skip session requests. With the flag on, a later session turn whose history prefix was evicted gets a 503 instead of re-encoding. That is probably fine as a trade-off, but it should be documented.
- The release runs after the host-offload loop in `prepare_mm_inputs`, so fully consumed CUDA features are first copied to CPU and then dropped. Releasing before the loop (after `record_stream`) avoids that copy.

The patch below covers 2 and 3. It does not fix 1. It applies on top of this PR rebased onto d88d5c325a. The only rebase conflict is in `test_scheduler_timeouts.py`; keep main's version.

- klshuster · comment · 2026-10-13T17:07:43Z · [source](https://github.com/sgl-project/sglang/pull/37473#issuecomment-6150941902)

@yhyang201 thanks for the thorough repro and the patch. I applied the patch as-is in 6fa88f724e (credited to you) and rebased on main.

For the retraction problem I went with your first option, in 7e7e7b2741. When a request whose media was released is retracted, `release_req` locks its prompt node in the tree right after dropping the request's own lock, so neither the immediate `evict_from_tree_cache` nor later evictions can take the prompt. The hold is dropped once the request is admitted again (after admission has locked the prefix it matched), or when it is aborted from the queue via `_release_aborted_request`. Decode disaggregation is excluded since it rebootstraps instead of re-prefilling. The 503 check stays as a fallback.

The trade-off is that retracting such a request now frees only its decode tokens, so under pressure a pass may retract a few more requests.

The new test drives `release_req` against a `RadixCache`: the prompt survives a full evict while the hold is in place and becomes evictable after it is released. It fails without the change.

I couldn't rerun your end-to-end benchmark here. Would you mind rerunning it on 7e7e7b2741?
