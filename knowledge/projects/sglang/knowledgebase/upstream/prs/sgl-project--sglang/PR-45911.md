# [Fix] [NVIDIA] jit: Build sm_100f on CC 10.7 until the bundled CUTLASS supports SM107

[Upstream PR](https://github.com/sgl-project/sglang/pull/45911) · state: closed · merged: True

## Original PR description

## Motivation

On CC 10.7 devices, SGLang JIT kernels are built for `sm_107a`, but they include FlashInfer's bundled CUTLASS (`flashinfer/data/cutlass`, 4.5.0). That CUTLASS has no SM107 support (`struct Sm107` and the `CUTLASS_ARCH_MMA_SM107A_ENABLED` gates arrive in CUTLASS 4.8). Against it, an `sm_107a` build compiles cleanly but loses features:

- `CUTE_ARCH_TMA_SM90_ENABLED` is undefined, so every cute TMA copy compiles to `CUTE_INVALID_CONTROL_PATH` and asserts at runtime.
- `CUDA_CTA_RECONFIG_ACTIVATED` is off, so `warpgroup_reg_alloc/dealloc` (`setmaxnreg`) become no-ops.

This is reachable today. DeepSeek-V4.1 with DP attention and `--dsv4-attn-backend trtllm` runs the DeepSelect top-k JIT kernels. On a CC 10.7 device, the first request fails with:

```
cute/arch/copy_sm90_tma.hpp:189: static void cute::SM90_TMA_LOAD_3D::copy(...): Assertion `0 && "Trying to use tma without CUTE_ARCH_TMA_SM90_ENABLED."` failed.
```

FlashInfer handles the same situation for its own JIT kernels: `flashinfer.compilation_context.cutlass_supports_sm107()` checks its bundled CUTLASS for `struct Sm107`, and builds the `sm_100f` family target when it is missing.

## Modifications

`python/sglang/kernels/jit/utils/arch.py`: on CC 10.7, when FlashInfer's `cutlass_supports_sm107()` (present in the pinned 0.7.2) is false, the JIT target becomes `10.0f`. The import stays inside the CUDA 10.7 branch, because ROCm and MUSA installs don't provide that function. This gives `-gencode=arch=compute_100f,code=sm_100f` and `SGL_CUDA_ARCH=1000`, so the binary and the arch macro the kernels branch on stay consistent. The `sm_100f` family binary runs on SM107.

Every other architecture is unchanged. On 10.7, the JIT goes back to `sm_107a` automatically once FlashInfer bundles a CUTLASS that declares `Sm107`. The JIT cache key includes the target, so stale `sm_107a` builds are not reused.

## Accuracy Tests

On a CC 10.7 device: DeepSeek-V4.1-Flash, TP4 / DP4 / EP4 with DP attention, `--moe-a2a-backend megamoe`, `--dsv4-attn-backend trtllm` and DSpark. GSM8K (200 questions, `sglang.test.run_eval`):

- Before: the DeepSelect top-k kernels assert on the first request and the server dies.
- After: 0.985. The JIT cache shows the DeepSelect builds targeting `sm_100f`.

## Speed Tests and Profiling

No speed claim. This trades an `sm_107a` build with TMA and `setmaxnreg` compiled out for a working `sm_100f` build.
