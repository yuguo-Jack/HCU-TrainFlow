# [NPU] Add MindIE-SD FIA and EQBSA attention backends

[Upstream PR](https://github.com/sgl-project/sglang/pull/40580) · state: open · merged: False

## Original PR description

## Motivation

Enable Ascend NPU diffusion pipelines, including MiniMax-H3, to select MindIE-SD FIA FP8 attention or EQBSA sparse attention through `--attention-backend fia_attn` and `--attention-backend eqbsa_attn`.

## Modifications

- Register the FIA and EQBSA backends with the NPU platform.
- Use MindIE-SD `quant_attention` in FP8 `HIGH_PRECISION` mode for FIA, dispatching to `fused_infer_attention_score_v2`, including independent batch and packed-sequence execution.
- Add EQBSA through `sparse_attention(sparse_type="rf_v3")`, with configurable sparsity, dense warmup steps, and `bf16`, `mix`, `fp8`, or `mxfp4` precision.
- Carry `txt_len`, exact video token grids, and `video_spans` with physical offsets through MiniMax-H3 packed layouts and Ulysses metadata. Text, audio, images, and alignment segments remain outside the sparse video spans.
- Build EQBSA step metadata for the resolved transformer backend, including component-specific overrides, while preserving existing Cube/VSA metadata handling.
- Keep the MiniMax-H3 Qwen3-VL text encoder on SDPA when FIA or EQBSA is selected globally for the transformer; preserve explicit text-encoder overrides.
- Add CPU contract tests for dispatch, precision options, packed-sequence isolation, video-span validation, MiniMax-H3 metadata, and backend routing.

FIA requires MindIE-SD `quant_attention` and `fused_infer_attention_score_v2`. EQBSA requires a MindIE-SD build whose `rf_v3` implementation supports `video_spans` and forwards the selected precision mode; older implementations accepting and ignoring those keyword arguments are insufficient. EQBSA supports head sizes 64 and 128, with sparse `mix` mode restricted to head size 128. Causal attention, dropout, and ring rotation are unsupported.

### Feature request: dense fallback for the tail steps of the EQBSA schedule

Currently the EQBSA backend only supports a dense **warmup prefix**: `skip_first_steps` (default 10) runs dense attention for the first N steps, and every step after that runs rf_v3 sparse — the dispatch condition in `eqbsa_attn.py` is just `current_timestep < skip_first_steps -> sparse_type=None`.

Many sparse attention methods (SVG, SageAttention-style schedules) additionally fall back to dense attention for the **last** few denoising steps, because late steps shape high-frequency details and are the most sensitive to sparse approximation. It would be great if EQBSA supported a tail dense fallback as well, e.g.:

- `dense_last_steps: int` — run dense (`sparse_type=None`) when `current_timestep >= total_steps - dense_last_steps`; or more generally
- `sparse_step_ranges: list[[start, end]]` — an explicit per-step sparse schedule.

Implementation-wise this looks small: add the field to `EQBSAAttentionMetadata` + validation in `EQBSAAttentionMetadataBuilder`, extend the dense-fallback condition in `EQBSAAttentionImpl.forward`, and thread the config through both `pipelines_core/stages/denoising.py::_build_attn_metadata` and `minimax_h3/stages/denoising.py::_forward_dit` (both already read `skip_first_steps` from `attention_backend_config`).

[Category] Code design / Logic design

[Issue] The EQBSA backend contract does not match its actual operator selection. This validation accepts bf16, mix, fp8, and mxfp4 and forwards them to the generic RFv3 API. However, only mix dispatches to eagle_quant_block_sparse_attention; the other modes use the BSA path, including the default bf16 mode. Selecting eqbsa_attn therefore does not ensure that EQBSA is used, and this mode-based dispatch does not explicitly report the actual alternative operator. This makes it difficult to attribute accuracy and performance results to the intended operator. See the MindIE-SD dispatch implementation: https://github.com/Ascend/MindIE-SD/blob/f56b2f4490f143021988553dd38918fd0e6271b3/mindiesd/layers/flash_attn/sparse_flash_attn_rf_v3.py#L752

[Suggestion] Please define the backend's scope explicitly. If it is intended to integrate EQBSA only, restrict the accepted precision modes and validate dtype/shape constraints against EQBSA's actual capabilities, ensuring that supported inputs dispatch to EQBSA. If alternative operators are intentionally retained as fallbacks, first check whether EQBSA supports the input, then explicitly select the fallback and log its reason, actual operator, and precision once. Avoid broadening precision validation and relying on the lower-level API to switch operators implicitly.

- coderYJY · comment · 2026-10-12T11:25:22Z · [source](https://github.com/sgl-project/sglang/pull/40580#discussion_r4247464106)

File: `python/sglang/multimodal_gen/runtime/layers/attention/backends/eqbsa_attn.py` · line 237

[Category] Non-style code issue / Parameters, return values, and operator precedence

[Issue] This call always passes block_size=128, but MindIE-SD RFv3 defaults block_size_kv to 256 for precision="fp8" and "mxfp4". When video_spans is supplied (as in the MiniMax-H3 path) and execution reaches the sparse phase, RFv3's wrapper requires equal Q/KV block sizes and raises ValueError, aborting generation. This is a wrapper-level check, not a claim that block_size=128 is inherently invalid for EQBSA. See the checked MindIE-SD dev implementation: https://github.com/Ascend/MindIE-SD/blob/f56b2f4490f143021988553dd38918fd0e6271b3/mindiesd/layers/flash_attn/sparse_flash_attn_rf_v3.py#L646

[Suggestion] Please select compatible Q/KV block sizes for each precision mode. Either of the following approaches could be evaluated:

- Use block_size=256 for FP8/MXFP4 to match the default KV block size. Update layout checks that assume 128, including the filler calculation at line 210, and validate rearrangement, mask construction, and native operator execution.
- If the target operator supports Q/KV block sizes of 128, add block_size_kv forwarding to the public sparse_attention() API and explicitly pass block_size_kv=128. The current full-FP8 path documents a KV block-size requirement of a multiple of 256, so this option cannot be applied to it without validation; MXFP4 can be evaluated separately.

Please add parameter-forwarding coverage and native operator validation for the chosen approach, rather than relying only on mocks that accept the arguments.
