# [Fix] [AMD] aiter: Use the layer's softmax scale in MHA prefill and decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/46833) · state: closed · merged: True

## Original PR description

## Motivation

With the aiter attention backend (the default for MHA models on ROCm), a model whose softmax scale is not `head_dim**-0.5` produces garbage, with a bf16 KV cache too. The default decode passes the backend-wide `self.scale = 1 / sqrt(head_dim)` to `paged_attention_ragged`, and the NHD prefill (`mha_batch_prefill_func`, plus the two vectorized-5D prefill calls in `aiter_utils.py`) passes no `softmax_scale`, so aiter falls back to `head_dim**-0.5`. #38754 moved the `unified_attention` calls to `layer.scaling`; these four sites were left as they were.

Measured below: Granite 3.x (`attention_multiplier` 1/64 or 1/128, 8-11x below `head_dim**-0.5`) and Granite 4.0 (`GraniteMoeHybridForCausalLM`). By the same code path, also GraniteMoE, Phi-3-small (`1 / head_dim`) and models served through the Transformers fallback with a custom scaling. Models with sliding-window layers (Gemma 2/3/4 and others) take the unified path and are not affected.

On main, `ibm-granite/granite-3.3-2b-instruct` continues "The capital of France is" with " a fascinating number of times. The first time I visited a federal circuit..."; with `--attention-backend triton` it answers " Paris.".

## Modifications

- `aiter_backend.py`: pass `layer.scaling` to `paged_attention_ragged` in decode and as `softmax_scale` to `mha_batch_prefill_func` in the NHD extend; remove `self.scale`, which has no other reader.
- `aiter_utils.py`: pass `softmax_scale=layer.scaling` to both `mha_batch_prefill_func` calls in `forward_extend_vectorized_5d`.
- `test_aiter_fp8_kv_scales_paths.py`: the `paged_attention_ragged` decode and NHD prefill cases also run at `layer.scaling = 1 / head_dim`, and a new case runs both SHUFFLE 5D prefill paths (fresh prompts, and a cached prefix gathered from the 5D pool) with a bf16 cache, through `AiterAttnBackend` with the real aiter kernels against an fp32 reference. On main the `1 / head_dim` prefill cases fail (relative L2 error 2.1 to 6.1) and decode fails because the backend still reads `self.scale`; with this PR all pass.

For models whose scale is `head_dim**-0.5` nothing reaching the kernels changes: the prefill passes the expression aiter defaults to, and the decode kernel takes a 32-bit `float`, in which `1 / sqrt(d)` and `d ** -0.5` are bitwise equal for every head_dim from 8 to 1024.

## Accuracy Tests

MI355X (gfx950), main 132b0f0ae7, bf16 KV cache, `SGLANG_USE_AITER=1`, CUDA graphs on. GSM8K with two harnesses: `python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --max-tokens 4096` (chat API, greedy, 1314 questions), and lm_eval 0.4.13 5-shot completion (greedy, 1319 questions, strict-match):

| Model | Harness | `--attention-backend triton` | aiter, main | aiter, this PR |
|---|---|---|---|---|
| ibm-granite/granite-3.3-2b-instruct | run_eval | 0.2268 ± 0.0116 | 0.0122 | 0.2397 ± 0.0118 |
| | lm_eval | 0.6293 ± 0.0133 | 0.0023 | 0.6187 ± 0.0134 |
| ibm-granite/granite-4.0-350m | run_eval | 0.3478 ± 0.0131 | 0.0145 | 0.3425 ± 0.0131 |
| | lm_eval | 0.2654 ± 0.0122 | 0.0023 | 0.2691 ± 0.0122 |
| Qwen/Qwen3-0.6B (default scale) | run_eval | | 0.6218 ± 0.0134 | 0.6225 ± 0.0134 |
| | lm_eval | | 0.4230 ± 0.0136 | 0.4200 ± 0.0136 |

The two harnesses score the models differently in absolute terms, but agree that main collapses Granite and that this PR matches triton within one standard error. In the lm_eval runs, each site breaks Granite on its own: on main, aiter prefill with triton decode scores 0.0000 and triton prefill with aiter decode 0.0008. With `SGLANG_USE_AITER_UNIFIED_ATTN=1 --page-size 16`, whose kernels already receive `layer.scaling`, main scores 0.6194.

Unit tests: the new cases pass; the existing aiter attention tests (`test_aiter_asm_prefill_gather`, `test_aiter_cross_layer_kv_guard`, `test_aiter_fp8_q_unified_attention`, `test_aiter_gluon_h12_fp8`, `test_aiter_swa_kv_pool_resolver`, `test_fused_fp8_kv_write`, `test_asm_context_prefill_gather_indices`) pass, 53 tests. gfx942 is not tested.

## Speed Tests and Profiling

No kernel, launch or argument change for models whose scale is `head_dim**-0.5` (see above), so no speed change is expected; not measured.

One thing I noticed but left out of this PR: with an fp8 pool, the 5D gather path still casts q with `q.to(fp8_dtype)` and passes `layer.k_scale` as `q_descale`, which #46528 replaced on the NHD path (k_scale is calibrated for K, not q, and `.to(fp8)` turns out-of-range values into NaN on e4m3fnuz). That's why the 5D cases here use a bf16 cache. It looks like a separate fix, so I kept it out of this PR.
