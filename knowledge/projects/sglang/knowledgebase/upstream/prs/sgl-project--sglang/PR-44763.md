# [Feat] dwdp: Support MTP speculative decoding on DWDP prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/44763) · state: open · merged: False

## Original PR description

## Motivation

`handle_dwdp` rejects every `--speculative-algorithm`, so a DWDP prefill server cannot run an MTP draft. MTP can still be enabled on the decode server alone, but then decode gets neither the draft KV of the prompt nor the first-step draft input (top-k and hidden state), which the prefill server normally produces with its draft extend. That costs accept length, mostly at short outputs, where the first decode round has no draft input. With DWDP8 prefill, GLM-5.3-Flash gets 1.81 instead of 2.95 at 8 output tokens and 3.92 instead of 4.53 at 1024; Qwen3.8-Flash-Next gets 1.87 instead of 2.37 and 2.64 instead of 2.67; MiMo-V2-Flash gets 1.41 instead of 1.70 and 2.76 either way (tables below).

Letting the prefill server run the draft takes more than dropping the assert:

1. **The MTP layer's MoE is computed from 1/N of the routed experts.** Under DWDP, sparse MoE runs on DP-local tokens and `post_experts_output_is_complete()` is True, so no sum follows the experts. The target's MoE layers still see every expert through the prefetch pipeline. The draft runner, however, returns early from `maybe_init_dwdp`, so the draft's `FusedMoE` keeps its EP shard (36 of 288 experts for GLM-5.3-Flash on DWDP8) and silently drops the other experts' contributions.
2. **Draft forwards trigger the target's prefetch.** `ModelRunner.forward` calls the global manager's `prefetch_first_layers()` for every runner, so each draft forward copies the target's first two MoE layers from peers (~12 GiB of NVLink traffic for GLM-5.3-Flash) that no forward consumes.

Related:
- #22084 tracks DWDP. #29778 added DWDP for MoE prefill together with the `handle_dwdp` check ("DWDP does not support speculative decoding") that this PR relaxes.
- #39802 (open) fixes the same mn-major scale layout in the target's `_allgather_small_params` that `_all_gather_experts` keeps here. The two PRs change different functions in `dwdp_manager.py`, and #39802's diff applies cleanly on top of this one. Once both land, the two gathers could share one helper.
- I found no open PR on DWDP with speculative decoding.

cc @yhyang201, who added DWDP and this check in #29778.

## Modifications

- `dwdp_manager.replicate_routed_experts(model)`: for every EP-sharded `FusedMoE` in `model`, all-gathers `w13_weight` / `w2_weight` and the expert-sharded side tensors (`named_per_expert_tensors`, e.g. quant scales) over the MoE EP group, then binds them with EP collapsed to 1. The gather runs in memory order, so a permuted layout such as DeepGEMM's mn-major scales keeps its strides. Fused shared experts raise `NotImplementedError`.
- `FusedMoE.bind_full_expert_weights(..., *, prefetched=True)`: `prefetched=False` keeps a fully resident layer out of DWDP's `wait_prefetch` / `record_compute_and_prefetch_next` hooks. The DWDP manager's call is unchanged.
- `ModelRunner`:
  - `maybe_init_dwdp`: the draft runner calls `replicate_routed_experts(self.model)` instead of returning.
  - `forward`: skips `prefetch_first_layers()` on the draft runner.
- `handle_dwdp`: accepts `EAGLE` / `NEXTN` on `--disaggregation-mode prefill`. Other algorithms and null mode are still rejected (see "Why prefill only" below).
- Tests (CPU, both fail before this change):
  - `test_moe_runner_config_placement.py`: replication gathers weights and scales in global expert order and in their memory layout (an mn-major scale keeps its strides), collapses EP and leaves the layer out of the prefetch.
  - `test_server_args.py`: `handle_dwdp` accepts EAGLE/NEXTN on prefill and rejects EAGLE3, DSPARK and null mode.

Cost: one MoE layer's experts per draft layer. For GLM-5.3-Flash (FP8, 288 experts) that is ~6.75 GiB per rank instead of the ~0.84 GiB EP shard. The draft weights are counted in the KV budget, so in the setup below the prefill KV pool went from 1,048,576 (the `--max-total-tokens` cap) to 419,840 tokens per rank. For Qwen3.8-Flash-Next (FP8, 512 experts) it is ~2.34 GiB instead of ~0.29 GiB, and the KV pool stayed at the cap.

## Accuracy Tests

Setup:
- GLM-5.3-Flash (FP8), PD over two 8x H20 nodes, mooncake over RoCE.
- Prefill: `--tp-size 8 --dwdp-size 8 --chunked-prefill-size 65536 --load-balance-method total_tokens --mm-enable-dp-encoder`.
- Decode: TP8.
- MTP on both sides: `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.
- Image: nightly 2026-10-14 (684fea8a). Its DWDP files and the touched `fused_moe_triton/layer.py` are byte-identical to `main` 4e85e8e, and the `model_runner.py` / `parallel_hook.py` hunks match. This change was mounted on the prefill side. Two sessions: the first predates the prefill-only condition in `handle_dwdp` (its runs satisfy it), the second ran the final version of this change.
- GLM-5.3-Flash under DWDP also needs the shared-expert TP1 condition from #39802, which is mounted in every DWDP run here and is not part of this PR.

GSM8K (20-shot, 200 questions) and a ~53k-token needle test (16 prompts), through the router:

| Prefill | GSM8K | Needle |
|---|---|---|
| DWDP8, no MTP | 0.940 / 0.960 | 15/16 |
| DWDP8, MTP on decode only | 0.965 / 0.960 | - |
| DWDP8 + MTP (this PR) | 0.955 / 0.955 / 0.955 | 13/16 |
| DWDP8 + MTP, assert dropped only | 0.940 / 0.945 / 0.960 | - |
| TP8 + MTP | 0.950 / 0.940 / 0.955 | 15/16 |

Up to three runs per row for GSM8K, one for the needle test. Every needle miss is a refusal: the model treats the planted code as an injected instruction, and the missed depths differ between runs.

Accept length per stage (ShareGPT text truncated to exact lengths). The decode server is flushed before each stage, which resets its speculative counters, and its `avg_spec_accept_length` is read afterwards; `bench_serving` alone prints the average since the decode server started. Second session:

| Prefill | GSM8K | p64k (48 x 64k, out 8) | p2k (200 x 2k, out 8) | d2k (200 x 2k, out 1024) |
|---|---|---|---|---|
| TP8 + MTP | 3.76 | 2.10 | 2.99 | 4.53 |
| DWDP8, MTP on decode only | 3.29 | 1.66 | 1.81 | 3.92 |
| DWDP8 + MTP (this PR) | 3.80 | 2.13 | 2.95 | 4.53 |
| DWDP8 + MTP, assert dropped only | 3.75 | 2.12 | 2.94 | 4.51 |

MTP on decode only loses 22-39% at 8 output tokens, where the first decode round has no draft input, and still 13% at 1024 and on GSM8K. Most of the gain comes from the prefill server running the draft at all: dropping the assert alone stays within 1.3% of this PR in PD. The MTP layer's attention runs before its MoE, so the draft KV that prefill ships is correct either way; only the first decode round's draft input comes from the partial expert sum, and decode runs every later draft step itself with all experts. The assert-only build still computes that input from 1/8 of the experts and pulls the target's prefetch on every draft forward.

### Qwen3.8-Flash-Next

Qwen3.8-Flash-Next (FP8, `Qwen4ExpForConditionalGeneration`; 512 routed experts, top-10, plus a shared expert) is a second MoE MTP model, built from different model code: its one MTP layer is a full-attention layer with a `Qwen2MoeSparseMoeBlock`. `replicate_routed_experts` gathers all 512 experts of `mtp.layers.0.mlp.experts`. Both sessions used the final version of this change.
- Spec flags: `--speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`.
- Model flags, as in the cookbook's FP8 config: `--linear-attn-prefill-backend flashinfer --linear-attn-decode-backend flashinfer --linear-attn-verify-backend triton --mamba-ssm-dtype bfloat16`. Same nodes, image and harness as above.
- Decode and the non-DWDP prefill use TP8 with `--ep-size 8`: the FP8 128x128 weight blocks cannot split the 640-wide experts 8 ways.
- The DWDP prefill sets `SGLANG_USE_ATTN_TP_NGRAM=1`. Without it the model's n-gram embedding refuses to start under DWDP's DP attention.
- Under DWDP, `Qwen2MoeSparseMoeBlock` keeps the shared expert TP-sharded (it is replicated only with an a2a backend), the same problem #39802 fixes for DeepSeek-V2. A one-line local fix is mounted in every DWDP run here and is not part of this PR.
- GSM8K uses the chat API, 5-shot, thinking disabled, 200 questions. With the 20-shot completion prompt the model stops after one token.

First / second session; accept length per stage, from the second session:

| Prefill | GSM8K | Accept GSM8K / p64k / p2k / d2k | p64k input tok/s | p2k input tok/s | d2k output tok/s |
|---|---|---|---|---|---|
| DWDP8, no MTP | 0.980 | - | 52,738 | 56,889 | 2,391 |
| DWDP8, MTP on decode only | 0.990 / 0.990 | 3.30 / 2.11 / 1.87 / 2.64 | 60,090 / 52,434 | 57,874 / 56,214 | 3,249 / 3,253 |
| DWDP8 + MTP (this PR) | 0.990 / 0.990 | 3.55 / 2.76 / 2.37 / 2.67 | 57,349 / 65,018 | 53,765 / 54,833 | 3,220 / 3,333 |
| TP8 / EP8 + MTP | 0.980 / 0.980 | 3.51 / 2.80 / 2.39 / 2.70 | 20,755 / 20,816 | 22,504 / 22,528 | 3,349 / 3,314 |

- Accept length matches the non-DWDP prefill within 1.5% on every stage, and DWDP keeps 2.4-3.1x its prefill throughput.
- MTP on decode only loses 21-24% at 8 output tokens and 7% on GSM8K, but only 1% at 1024, so d2k output throughput is about the same (3,220 / 3,333 vs 3,249 / 3,253 tok/s). The missing prompt draft KV matters much less here than for GLM.
- The draft extend adds ~4% to the prefill time of a 64k request (8.10 → 8.40 / 8.43 s in the prefill server's `ReqTimeStats`). The p64k input throughput is set by the busiest DP rank and differs by 13-15% between sessions of the same config. At 2k, prefill with the draft is 2-7% below the arms without one.

### MiMo-V2-Flash

MiMo-V2-Flash (FP8, 256 routed experts, no shared experts) has three dense MTP layers, so `replicate_routed_experts` has nothing to gather. The run covers the rest of the change, with several draft runners under multi-layer EAGLE.
- Spec flags, as in `test_mimo_v2_flash.py`: `--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 --enable-multi-layer-eagle`.
- Model flags: `--attention-backend fa3 --page-size 64`. Same nodes and harness as above.
- Decode and the non-DWDP prefill use `--attn-dp-size 8` (attention TP 1, as on a DWDP prefill). MiMo's FP8 QKV block scales cannot be split for attention TP 8. Also, decode at attention TP 2 behind a DWDP prefill returned garbage (GSM8K 0.000) with or without MTP, and matching the attention TP avoided it.

First / second session; accept length per stage from the second session, averaged over the decode server's 8 DP ranks:

| Prefill | GSM8K | Accept GSM8K / p64k / p2k / d2k | p64k input tok/s | p2k input tok/s | d2k output tok/s |
|---|---|---|---|---|---|
| DWDP8, no MTP | 0.705 | - | - | 27,103 | - |
| DWDP8, MTP on decode only | 0.695 / 0.700 | 2.90 / 1.41 / 1.41 / 2.76 | 27,124 / 27,155 | 27,772 / 26,654 | 4,555 / 4,585 |
| DWDP8 + MTP (this PR) | 0.750 / 0.730 | 2.95 / 1.73 / 1.70 / 2.76 | 26,111 / 29,414 | 28,798 / 30,064 | 4,584 / 4,529 |
| Attention DP 8 + MTP | 0.700 / 0.725 | 2.94 / 1.75 / 1.67 / 2.79 | 12,480 / 12,721 | 24,727 / 25,746 | 4,680 / 4,807 |

Accept length matches the non-DWDP prefill within 2%, and DWDP keeps 2.1-2.3x its 64k prefill throughput. MiMo's MTP layers attend over a 128-token window, so the prompt's draft KV stops mattering after the first decode steps: MTP on decode only loses 17-19% at 8 output tokens and nothing at 1024.

### Why prefill only

DWDP also allows `--disaggregation-mode null`. There the draft runs decode steps too, and under DWDP they run eagerly. In those steps every row of the draft MoE input arrives masked as padding: on a 1-row draft batch, 8 of 8 expert ids were -1.

- With this PR, the replicated layer's Triton runner treats every id as local (`filter_expert` is off once `num_local_experts == num_experts`). It faults with an illegal memory access in `invoke_fused_moe_kernel`.
- With the assert dropped only, the EP-sharded layer filters the -1 ids, so its draft decode steps compute no routed experts at all. It still reached accept length 4.25 and GSM8K (100 questions) 0.970.
- DWDP null mode without speculative decoding is unaffected: the target's decode batches carry the right non-padded count.

Fixing the draft-decode padding count is a separate change, so this PR enables speculative decoding only on PD prefill servers, where the draft only runs extend.

## Speed Tests and Profiling

GLM-5.3-Flash, same setup, first / second session:

| Prefill | p64k input tok/s | Prefill time per 64k request | p2k input tok/s | d2k output tok/s | d2k mean TPOT |
|---|---|---|---|---|---|
| DWDP8, no MTP | 30,429 | 14.64 s | 29,514 | 1,842 | 28.9 ms |
| DWDP8, MTP on decode only | - / 35,054 | - / 14.64 s | 29,672 / 28,978 | 3,060 / 3,056 | 16.5 / 16.4 ms |
| DWDP8 + MTP (this PR) | 29,341 / 29,388 | 15.04 / 15.07 s | 29,677 / 28,393 | 3,375 / 3,605 | 14.5 / 13.7 ms |
| TP8 + MTP | 13,435 / 13,431 | - | 20,043 / 20,045 | 3,796 / 3,791 | 13.4 / 13.6 ms |

- With this PR a DWDP prefill node keeps 2.2x TP8's prefill throughput at 64k and 1.4-1.5x at 2k, and runs the draft for decode. At d2k that gives 10% / 18% more output throughput than MTP on decode only (TPOT 16.5 → 14.5 ms and 16.4 → 13.7 ms), and 83% more than no MTP.
- The draft extend adds 2.8% to the prefill time of a 64k request (14.64 → 15.04 / 15.07 s; 14.96 s with the assert dropped only). This is the prefill server's `ReqTimeStats` forward duration minus the KV transfer tail. The p64k throughput itself is set by the busiest DP rank: with 48 requests on 8 ranks, a session in which one rank serves 7 of them instead of 6 takes ~1/6 longer, which is why the decode-only row reached 35.1k in the second session.
- With short prompts at c64, TP8 prefill still gives lower TTFT (d2k mean / median 1.39 / 0.39 s vs 2.49 / 1.50 s with this PR). DWDP runs one prefill per rank, which is the existing DWDP trade-off and is unchanged here.
