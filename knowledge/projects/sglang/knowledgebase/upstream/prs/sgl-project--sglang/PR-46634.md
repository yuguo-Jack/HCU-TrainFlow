# [Fix] [MUSA] fa3: Compute scheduler metadata from the calling backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/46634) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #46508.

On MUSA with `--attention-backend fa3` and speculative decoding, the second request whose prefix hits the radix cache hangs. `MusaFlashAttentionBackend` stored itself in a module-level `_CURRENT_BACKEND` when it was constructed, so the last backend built won. The draft backend is built after the target, so every target-model `flash_attn_with_kvcache` call computed MATE `scheduler_metadata` from the draft backend's layer, `max_seqlen_k` and refresh decision, and replayed the draft's cached metadata. Every `flash_attn_with_kvcache` call (cached-prefix prefill, target verify, decode) gets this metadata. The reported hang starts at the second request's prefill, which hits the cached prefix; the first request's prefill has no cached prefix and runs through `flash_attn_varlen_func`, which takes no scheduler metadata.

Two-batch overlap hits the same override without speculative decoding. `TboAttnBackend.init_new` builds a primary and two child `MusaFlashAttentionBackend` instances, so calls on the primary and the first child read the second child's state.

## Modifications

- `flash_attn_with_kvcache` takes the calling backend as a keyword-only `backend` argument. All 11 call sites in `MusaFlashAttentionBackend` pass `backend=self`.
- Removed `_CURRENT_BACKEND` and its assignment in `__init__`.
- New CPU test, `test/registered/unit/hardware_backend/musa/attention/test_flashattention_backend.py` (`base-a-test-cpu`). It builds a target backend, then a draft backend, runs two draft decode layers and then a target decode. It checks the metadata on every kernel call: both draft calls get the draft's head count and `max_seqlen_k`, and the target's call gets the target's.

This is the explicit-backend variant the reporter named as the cleaner alternative to their validated two-line patch, which re-pointed the global in `_set_current_state`. On every current call path the two behave the same, because each wrapper call follows `self._set_current_state(...)` on the same instance.

Unchanged: the CUDA/ROCm FA3 backends, the MLA workspace logic, `_MATE_NO_MLA_SCHEDULER_METADATA_DICT`, and the DSpark device check in `speculative_hook.py`.

## Accuracy Tests

No kernel or model math changes. The fix only picks which backend's state builds the metadata. Not run on MUSA hardware (see Not covered).

## Speed Tests and Profiling

N/A. This fixes a hang and makes no speed claim. It adds no work on the hot path; the wrapper now receives the backend as an argument instead of reading a module global.

## Not covered

- Not run on MUSA hardware; I don't have an MTT S5000. The reporter validated the equivalent two-line fix on one (Qwen3-4B with a DSpark draft: the second cached request completes). A MUSA run of the repro in #46508 would confirm this version.

## Notes for reviewers

`_MATE_NO_MLA_SCHEDULER_METADATA_DICT` is keyed by prefix alone and shared by every backend instance. With this fix each backend's first layer refreshes the entry, so sequential target and draft forwards are fine. Two cases can still reuse another backend's entry: a draft whose first `layer_id` is above its computed start layer, and the two TBO children, whose stages alternate. I left that out of scope and can follow up separately if you want it keyed per backend.
