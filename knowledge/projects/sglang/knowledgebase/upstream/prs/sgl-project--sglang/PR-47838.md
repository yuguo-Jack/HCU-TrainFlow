# [Fix] http_server: Start HTTP workers with lazy CUDA module loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/47838) · state: open · merged: False

## Original PR description

## Motivation

With `CUDA_MODULE_LOADING=EAGER` and `--tokenizer-worker-num > 1`, the HTTP/tokenizer workers never all come up. The server log prints `Waiting for child process [pid]` / `Child process [pid] died` every few seconds, indefinitely, and `ps` shows a single `sglang::tokenizer_worker` next to a queue of `spawn_main` processes at 100% CPU.

Cause:

- uvicorn starts the workers with the spawn context, so each worker re-imports `sglang`. Platform detection at import (`torch.cuda.is_available()`, plus the module-level `is_cuda()` checks) initializes CUDA in the worker.
- Under `EAGER`, that CUDA init loads every kernel module up front. We measured ~2 min of CPU and several GB of RSS per worker for `torch.cuda.is_available()` alone, against ~1–2 s with `LAZY`.
- uvicorn pings each worker with `timeout_worker_healthcheck` (`SGLANG_UVICORN_WORKER_HEALTHCHECK_TIMEOUT`, default 10 s), and the worker's pong thread only starts after the import finishes. Every fresh worker misses the healthcheck, is killed, and is respawned into the same state.

Raising `SGLANG_UVICORN_WORKER_HEALTHCHECK_TIMEOUT` hides the loop, but each worker still pays minutes of CPU and GBs of memory for a CUDA init it does not use.

## Modifications

- `http_server._use_lazy_cuda_module_loading_for_http_workers()`: if `CUDA_MODULE_LOADING` is `EAGER`, set it to `LAZY` in the parent's environment and log it. Called at the top of the multi-tokenizer branch of `_setup_and_run_http_server`, so it covers the uvicorn, SO_REUSEPORT and Granian multi-worker paths, plus workers that uvicorn later respawns.
- Scheduler processes are not affected. `launch_server` only reaches `_setup_and_run_http_server` after `Engine._launch_subprocesses` has returned, so the schedulers, detokenizer and DP controller are already running. They keep the environment they were spawned with, and CUDA reads `CUDA_MODULE_LOADING` at init in each process.
- No-op when `EAGER` is not set, with `--tokenizer-worker-num 1`, on the Rust server path, and on `node_rank >= 1`.
- Test: `test/registered/unit/entrypoints/test_http_server_worker_cuda_module_loading.py` (CPU). It checks the env mapping (`EAGER`/`eager` → `LAZY`, `LAZY` and unset unchanged), and that a spawn-context child sees `EAGER` before the call and `LAZY` after it.
