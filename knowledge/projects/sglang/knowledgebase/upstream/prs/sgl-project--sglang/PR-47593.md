# [Fix] scheduler/MiniMax-M3.1-Flash: Bound a chunked prefill continuation by the allocatable KV

[Upstream PR](https://github.com/sgl-project/sglang/pull/47593) · state: open · merged: False

## Original PR description

## Motivation

At high concurrency a chunked prefill continuation can kill the scheduler with `RuntimeError: Prefill out of memory. Try to lower your batch size.` We hit it serving MiniMax-M3.1-Flash on GB300 (DSpark, attention DP 2 + EP 2, MegaMoE, HiCache `write_back`, `--chunked-prefill-size 32768`, `--prefill-decode-interval 16 --schedule-policy shortest-prefill-first`) under SemiAnalysis' AgentX trace replay: at 48 and 56 concurrent sessions the scheduler died 9.2 and 20.6 minutes into the run.

In both runs DP0 was chunk-prefilling a very long request (`#pending-token` 1,348,240 and 833,015 just before the crash) while 12 and 11 decodes grew on the same rank. Its token usage reached 1.00 with nothing evictable, and the next chunk asked for 16,384 and 12,800 tokens against `Available full tokens: 13824` and `6528` (`full_evictable_size_=0` in both). The other DP rank sat at 0.91 and 0.63.

Cause: `PrefillBudget.available_chunk_tokens` sizes a continuation from `remaining_total`: free + evictable minus the pages already handed out this pass and the running decodes' reserved growth. When that reserved growth exceeds the pool, it returns the whole chunk so that the continuation keeps making progress ("Single-pool continuation must make progress to release its KV"). The allocator cannot back a chunk larger than the free pages and raises. Prefill is scheduled before decode in the step, so decode retraction never gets the chance to free pages.

## Modifications

- `PrefillBudget.available_chunk_tokens` (`mem_cache/prefill_budget.py`): when the budget is spent, return what the pool can back now (`remaining_current`, which carries no future-growth reservation) in whole pages with one page spare, instead of the whole chunk. When nothing is allocatable, return `None` if the caller can wait, otherwise keep the previous attempt.
- `PrefillAdder.add_chunked_req` (`managers/schedule_policy.py`): passes `can_wait=True` when a running decode batch exists, since those requests can finish or retract and free pages; the continuation then skips one step instead of crashing. With no running decode the behaviour is unchanged, so a real out-of-memory is still reported rather than hung.
- `ChainPrefillBudget` forwards the flag; `SWAPrefillBudget` accepts and ignores it (it already returns `None` for a continuation without room).
- New CPU test `test/registered/unit/mem_cache/test_prefill_budget_chunked_continuation.py`, built on the crash numbers (16,384-token chunk, 13,824 free, reserved growth past the pool). Without the change all four cases fail. The existing `test_prefill_memory_budget.py` (16 tests) and `test_prefill_adder.py` (55 tests) pass.

## Speed Tests and Profiling

Same deployment, flags and trace replay (AIPerf agentx-harness 1.0.12, 1,200 s window, simulated acceptance length 4.04), GB300, image `lmsysorg/sglang:nightly-cu134-20261030-e371881`, with and without this change:

| 56 | scheduler died at 20.6 min (`Prefill out of memory` on DP0) | completed, valid: 1,824 requests, 0 errors, peak token usage 1.00, 0 out-of-memory; 61.8 tok/s/user, 100,153 total tok/s per GPU, p90 TTFT 8.1 s |

![KV token usage per DP rank, main vs this PR](https://raw.githubusercontent.com/thanhhao98/sglang/htphan/pr-assets-chunked-continuation/chunked-continuation-main-vs-pr.png)

KV token usage per DP rank over each run; the dashed line marks where main's scheduler died. The first ~9.5 minutes are server warm-up and the replay's warm-up requests; the measured window follows. With this PR both ranks repeatedly reach the pool limit and the run completes.

A second MiniMax-M3.1-Flash deployment hit the same crash on the stock image `lmsysorg/sglang:nightly-cu134-20261027-3927a73`: DFlash2 speculative decoding, attention DP 4 + EP 4 with MegaMoE, HiCache `write_back`, `--chunked-prefill-size 32768` (8,192 per DP rank), `--prefill-decode-interval 16 --schedule-policy shortest-prefill-first --enable-dp-attention-local-control-broadcast`, AgentX trace replay at 128 concurrent sessions over the 3,600 s window. On the image as shipped the scheduler died 2,626 s into the run (`Prefill out of memory. Try to allocate 8192 tokens. Available full tokens: 7552 (full_available_size=7552 + full_evictable_size_=0)` on DP0; error rate 0.10, run invalid). With this change backported onto the image's commit the run completed and is valid: 15,664 requests, error rate 0.0003, peak token usage 1.00, 0 out-of-memory; 81.3 tok/s/user (1000 / p90 ITL), 132,840 total tok/s per GPU, p90 TTFT 4.0 s. The backport is this PR's change applied to 3927a73, where `PrefillBudget.available_chunk_tokens` has the same fallback; the PR's unit test plus `test_prefill_memory_budget.py` and `test_prefill_adder.py` pass on that tree.
