# [Fix] moe: Fix flashinfer TRT-LLM BF16 expert weight reload on refit

[Upstream PR](https://github.com/sgl-project/sglang/pull/33743) · state: open · merged: False

## Original PR description

## Motivation

BF16 MoE expert weights are converted to the FlashInfer TRT-LLM BlockMajorK
layout on cold load. The inverse restore previously ran only for the routed
backend, although both `flashinfer_trtllm` and `flashinfer_trtllm_routed` use
the transform. A subsequent checkpoint-format copy into a blocked parameter
can therefore fail with:

```
The size of tensor a (64) must match the size of tensor b (2048) at
non-singleton dimension 2
```

A shape-only restore is insufficient: unchanged expert values must also be
returned to checkpoint order before the next pack, or repeated refits can
silently scramble them.

Fixes #27787

## Modifications

1. Gate the inverse on `use_flashinfer_trtllm_moe`, matching the transform for
   both routed and non-routed BF16 backends.
2. Restore both the canonical shape and values in place, preserving parameter
   storage and rejecting non-bijective row permutations or wrong element counts.
3. Implement `restore_weights_before_loading` so `begin_weight_update` restores
   both expert parameters for direct tensor and P2P/RDMA writes that bypass
   model weight loaders. Retain loader-side restoration for disk reloads,
   which do not open a weight-update session.
4. Shape-guard the post-load pack: canonical weights are converted to kernel
   layout, while already-blocked weights remain unchanged. The existing
   `end_weight_update` finalizes once per session, not once per bucket, using
   the existing LoRA-aware model-loader traversal. No new updater/base hook or
   per-bucket `finally` callback is introduced.

Files changed relative to main:
`python/sglang/srt/layers/quantization/unquant.py` and
`test/registered/unit/layers/quantization/test_flashinfer_trtllm_bf16_moe_reload.py`.

## Accuracy Tests

The CPU-registered unit file contains 10 test methods. It covers exact layout
round trips, bucketed tensor/flattened/distributed updates, mixed
canonical/blocked parameters, unchanged and inactive-backend behavior, invalid
permutations and element counts, LoRA-wrapped traversal, and three successive
loader-free refits through both direct tensor updates and simulated P2P flat
copies. Runtime topology is scoped with `get_parallel().override(tp_rank=0)`.
Loader-free tests assert exact cold-load byte equality and unchanged storage
pointers, while forbidding any call to the model weight loader.

October 5 validation of commit `493fab0f593649c3c22a19302bab1b597a70aada`,
including main `70f0b7351e74b372cc928db533824d3993d65922`: all 10 methods and
5 format subtests pass, plus 22 nearby session/cache-guard methods. Controls
reproduce the three pre-fix TP-rank failures and fail the new loader-free case
in both formats when only the production restore hook is removed. Native XML,
exact source hashes and terminal accounting were independently checked;
all applicable pinned pre-commit hooks pass.
FlashInfer's layout entry points are deterministic, order-changing CPU
stand-ins; this is not on-device kernel accuracy, real RDMA transport, or
end-to-end RL validation.

## Speed Tests and Profiling

No speed benchmark is claimed. Forward kernels are unchanged. Canonical restore
and pack are paid once per weight-update session; disk reloads retain their
existing load/postprocess lifecycle. This fixes representation correctness,
not rollback of partially written weight values.

I completed an end-to-end before/after verification of this change using the original BF16 MoE RL weight-refit workload.

#### Test configuration

- Qwen3-30B-A3B
- BF16 MoE
- Non-routed `flashinfer_trtllm` MoE backend
- Single-node, 8× B200/SM100
- Bucketed RL weight synchronization through `update_weights_from_tensor`
- Same pinned model, training configuration, and dependency set for the reproduction and fixed runs

#### Failure reproduction

The failure was first reproduced on this PR's parent commit, `2adb2e8485210b94198301df24ae6cdaa211b0e8`.

The update reached:

```text
update_weights_from_tensor
  -> Qwen3MoeForCausalLM.load_weights
  -> FusedMoE._load_w13
  -> expert_data.copy_
```

and failed with the original error:

```text
RuntimeError: The size of tensor a (64) must match the size of tensor b (2048)
at non-singleton dimension 2
```

This confirms that the verification exercised the original non-routed `flashinfer_trtllm` failure rather than a synthetic approximation of it.

#### Fixed result

I then ran the same workload with commit `522980ec4b3f4bfbd3e95b2542bf6d43e59430f6` from this PR.

The run completed successfully:

- 5 complete rollout/training steps
- 6 complete hot-update rounds
- 115 weight-update buckets per round
- 690 successful `update_weights_from_tensor` requests in total
- 6 automatic post-update repacks
- 6 successful generation continuations after the updates
- 0 occurrences of the 64-vs-2048 mismatch
- 0 failed weight-update requests
- No legacy post-processing request was needed; SGLang performed the repack through the new hot-update lifecycle

The observed correctness signals remained finite and stable throughout the run:

| Signal | Observed range |
| --- | ---: |
| Raw reward | 0.1035–0.2236 |
| Truncation fraction | 0.3359–0.4102 |
| Train/rollout KL | 0.00325–0.00368 |
| Gradient norm | 0.1133–0.1510 |

#### Conclusion

This end-to-end result confirms both halves of the fix:

1. The BlockMajorK representation is genuinely inverted before canonical checkpoint tensors are copied, so the original shape mismatch is removed.
2. The expert parameters are repacked after every hot-update bucket, allowing subsequent inference/generation to continue using the kernel-required layout.

This is important because widening the restore gate alone would make the copy succeed but could leave the parameter in canonical layout, or corrupt untouched expert slots across a bucketed update. The inverse-plus-repack behavior in this PR avoids both cases.

The exact tested commit was `522980ec4b3f4bfbd3e95b2542bf6d43e59430f6`. It is still an ancestor of the current PR head, `b20933008d065bd859a5082d4785cc4c8657bf74`; the later commit merges `main` into the feature branch. I did not separately rerun that merge commit, so the end-to-end result is formally attached to `522980ec`.

From the original failure's perspective, this PR is verified and ready to land.
