# [Fix] dsv41: Preserve rejected tool calls in history

[Upstream PR](https://github.com/sgl-project/sglang/pull/44464) · state: open · merged: False

## Original PR description

## Motivation

A client can reject a malformed generated tool call and send its parse error back
to the model. With the `dsv41` chat encoding, replaying that history currently
returns HTTP 400 (`Assistant tool call function.arguments must be valid JSON.`)
instead of allowing the model to recover. Removing the generic validation alone
is insufficient: the V4.1 renderer also calls `json.loads` unconditionally.

For example, the following history fails before generation:

```json
[
  {"role": "user", "content": "Run the lookup."},
  {
    "role": "assistant",
    "content": null,
    "tool_calls": [{
      "id": "call_1",
      "type": "function",
      "function": {"name": "lookup", "arguments": "{\"key\":\"alpha"}
    }]
  },
  {
    "role": "tool",
    "tool_call_id": "call_1",
    "content": "failed to parse function arguments: unexpected EOF"
  }
]
```

This follows the malformed-history recovery precedent for Kimi K3 in #33025,
while retaining the default validation introduced by #28035.

## Modifications

- Allow the `dsv41` encoder to handle malformed historical argument strings.
- Preserve those strings verbatim inside the historical DSML invoke body, next
  to the client's tool-error result. Do not repair arguments, invent parameters,
  or execute a rejected call.
- Keep ordinary DSML parameter rendering for valid JSON objects. Valid JSON
  arrays, scalars and null remain rejected; other encodings retain their
  existing validation behavior.
- Add serving-path regression tests covering malformed/empty arguments, valid
  object rendering, non-object rejection, error-result retention, request
  immutability, and strict default Jinja validation.

This is a history-rendering fix, not an output-parser change. The original raw
model output was not captured, so this PR makes no claim about whether the
initial malformed arguments originated in generation or parsing.

## Accuracy Tests

Tested against main at `f7ad4345b86d147a1c3095a3cebabca9a33ebaa1`:

- Negative control: the new V4.1 test fails on unpatched main for all three
  malformed argument cases; its valid/non-object cases and the strict-default
  regression pass.
- `python -m unittest test_serving_chat`: **158 tests passed**.
- `python -m unittest test_protocol test_responses_protocol test_serving_responses test_serving_responses_stream test_responses_custom_tools`:
  **143 tests passed**.

These CPU unit tests imported the current-main source in an existing SGLang
deployment dependency image; current main was not GPU-runtime-qualified here.
The equivalent patch on our pinned deployment was also verified end-to-end via
direct Chat Completions (streaming and non-streaming), and through LiteLLM with
streaming Chat Completions and Responses: a replayed malformed call plus parse
error produced a valid replacement call and then a final answer after a tool
result. On that deployment, 256 valid-history prompts were byte-identical before
and after the patch.
