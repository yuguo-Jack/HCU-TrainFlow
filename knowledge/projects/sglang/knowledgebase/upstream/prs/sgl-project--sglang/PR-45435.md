# [Fix] mamba: Keep prefill rows' checkpoint tracking through mixed chunked prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/45435) · state: closed · merged: True

## Original PR description

## Motivation

With `--enable-mixed-chunk` and the `extra_buffer` / `extra_buffer_lazy` Mamba radix cache, a prefill chunk that runs in the same forward as running decodes (a MIXED step) saves no Mamba state, but the radix cache still stores its checkpoint:

1. `prepare_for_extend` claims the request's next ping-pong slot and stamps `mamba_last_track_seqlen` for every extend row whose chunk reaches the checkpoint grid.
2. `mix_with_running` -> `merge_batch` resets every `mamba_track_*` field to `None`, and nothing rebuilds them.
3. The linear-attention backends gate the extend-side state copy on the track mask, so the MIXED forward never writes the claimed slot.
4. The slot is donated anyway at the stamped depth. A later request that resumes from that prefix restores whatever the slot held before. The output is wrong with no error.

## Modifications

- `ScheduleBatch.mix_with_running` saves the prefill rows' track tensors and host lists before `merge_batch` and restores them after it. The running decode rows are appended as untracked rows (`mask=False`, `seqlen=-1`, index `-1`); decode tails were never tracked in a mixed step, so their behavior is unchanged.
- Lazy strategy: `prepare_for_decode` may already have handed a decode row at a track boundary its next ping-pong slot (`mamba_lazy_prealloc_at_boundary`). A mixed forward writes no decode track state and its result path never frees that slot, so the new `mamba_lazy_undo_prealloc_at_boundary` frees it and restores the row's next index first.
- The row remembers the decode batch in which it rode a mixed step (`ReqKvInfo.mamba_untracked_decode_batch_idx`). In `_handle_finish_state_updated_req`, the lazy "boundary write was in place, skip the radix insert" shortcut no longer fires for a request that finished one step before that boundary, because no in-place write happened.
- `merge_batch` is unchanged; the post-forward running-batch merge must keep dropping tracking, `prepare_for_decode` rebuilds it.
- Production change: `python/sglang/srt/managers/schedule_batch.py` (+49) and `python/sglang/srt/managers/scheduler_components/batch_result_processor.py` (+1).

## Tests

`test/registered/unit/managers/test_mix_with_running_mamba_track.py` (`base-a-test-cpu`, ~5 s). It drives the real `_mamba_radix_cache_v2_req_prepare_for_extend`, `mix_with_running` and `MambaAttnBackendBase._init_track_ssm_indices_from_cpu` with stub requests and a stub pool:

- `test_mixed_batch_tracks_prefill_rows_into_the_donated_slot` (both strategies): after the mix the batch is MIXED, the prefill rows keep their mask / seqlen / slot, the decode rows are untracked, and the slot the backend's eager track plan writes is exactly the slot the tracked prefill row will donate. Fails on main (`mamba_track_mask` is `None`).
- `test_lazy_decode_tails_give_back_the_boundary_slot`, `test_lazy_undo_keeps_the_slot_when_the_prealloc_failed`, `test_non_lazy_decode_tails_keep_their_slots`: slot bookkeeping around the undo.
- `TestLazyFinishBeforeMixedBoundary`: a request that finishes at grid - 1 while its overlapped boundary step is mixed still releases with `checkpoint=True`; the in-place case still skips. Fails if the result-processor condition is removed.

`test_schedule_batch_out_of_place.py` now stubs the mamba settings `mix_with_running` reads; it and `test/registered/unit/layers/test_mamba_prefill_track_metadata.py` pass unchanged otherwise (15 passed, 96 subtests).

Not run for this PR: GPU end to end. The change is scheduler bookkeeping only (three tensor concatenations and two host-list extensions per mixed step, no kernel changes).
