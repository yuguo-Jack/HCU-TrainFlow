# [Fix] moe: Apply swiglu_limit in the FlashInfer CuTe DSL NVFP4 MoE runner

[Upstream PR](https://github.com/sgl-project/sglang/pull/47080) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4 experts use a clamped SwiGLU, with `swiglu_limit` = 10.0 in the DeepSeek-V4-Pro config. The clamp is `gate = min(W1 x, 10)` and `up = clamp(W3 x, -10, 10)`, followed by `silu(gate) * up`. `DeepseekV2MoE` passes the value into `FusedMoE` (`deepseek_v2.py:766`), so it reaches `MoeRunnerConfig.swiglu_limit`.

`--moe-runner-backend flashinfer_cutedsl` drops it on both of its paths:

1. Standard path, `--moe-a2a-backend none` or `flashinfer`. `ensure_cutedsl_wrapper` builds `CuteDslMoEWrapper` without SwiGLU parameters (`flashinfer_cutedsl.py:353`), so FlashInfer uses its default `swiglu_limit`, the float32 maximum. The routed experts run without the clamp.
2. DeepEP low-latency path, `--moe-a2a-backend deepep`. `flashinfer_cutedsl_moe_masked` applies the activation with `silu_and_mul_scaled_nvfp4_experts_quantize` (`flashinfer_cutedsl_moe.py:167`), which has no clamp parameter.

`flashinfer_trtllm` (#39920) and `flashinfer_cutlass` (#39939) already apply `swiglu_limit`.

FlashInfer's wrapper supports the clamp. `CuteDslMoEWrapper.__init__` takes `swiglu_alpha`, `swiglu_beta` and `swiglu_limit` in 0.7.2 (the pinned version) and in 0.7.1. The SM100 GEMM1 epilogue (`blockscaled_contiguous_gather_grouped_gemm_act_fusion.py` and the W4A16 kernel) computes:

- `gate = min(acc * alpha, limit)`
- `up = clamp(acc * alpha, -limit, limit)`
- `out = gate * sigmoid(swiglu_alpha * gate) * (up + swiglu_beta)`

Here `alpha` is the per-expert `w1_alpha` (times the per-token scale when one is used), so the clamp acts on dequantized values. With the defaults `swiglu_alpha=1` and `swiglu_beta=0`, this is the DeepSeek-V4 activation, so `swiglu_limit` can be passed through unchanged. TRT-LLM divides the limit by `g1_alphas`; this path does not need that.

**Impact**

- DeepSeek-V4-Pro-NVFP4 (and DeepSeek-V4 NVFP4 checkpoints) with `--moe-runner-backend flashinfer_cutedsl`: the routed experts run an unclamped SwiGLU. The shared expert is not affected: CuteDSL turns off shared-expert fusion, so it runs through `DeepseekV2MLP`, which applies the clamp.
- Any other NVFP4 model that sets `MoeRunnerConfig.swiglu_limit` takes the same code path on this runner. I checked only DeepSeek-V4.
- I did not measure how often real DeepSeek-V4 activations exceed ±10. CuteDSL needs SM100, and the model does not fit on the GPU used here.

## Modifications

- `ensure_cutedsl_wrapper`: when `moe_runner_config.swiglu_limit` is set, pass `swiglu_limit=float(...)` to `CuteDslMoEWrapper`. `swiglu_alpha` and `swiglu_beta` keep FlashInfer's plain-SiLU defaults. Models without a limit build the wrapper exactly as before.
- `ModelOptNvFp4FusedMoEMethod.create_moe_runner`: on the CuteDSL DeepEP (masked) path, raise a `ValueError` when `swiglu_limit` is set. The message names `--moe-a2a-backend none` or `flashinfer`. `create_moe_runner` runs from `FusedMoE.__init__`, so the server stops before it loads weights. This follows the existing refusals for configurations a runner cannot serve, such as `hpc_ops` with `swiglu_limit`, and `flashinfer_cutedsl` with per-token activation under DeepEP in `moe_hook.py`.

Not covered: `gemm1_alpha`, `gemm1_beta` and `gemm1_clamp_limit` (the GPT-OSS-style parameters). This runner still ignores them, as it did before. `materialize_swiglu_params_for_cutlass` shows how they would map onto the same three wrapper arguments, but I have not tested that mapping on this runner.

This change will conflict textually with #44148 and #46687 (SiTU on the CuTe DSL MoE), which also add kwargs to the same `CuteDslMoEWrapper(...)` call. The two changes are compatible: SiTU uses `situ_beta` / `situ_linear_beta`, and DeepSeek-V4 uses `swiglu_limit`.

The code, the tests and this description were drafted with an AI coding agent (Claude Code).

## Accuracy Tests

**Unit tests (CPU)**

Two tests are added to `test/registered/unit/layers/quantization/test_modelopt_nvfp4_moe_scales.py`, next to `test_trtllm_post_load_activation_parameters`:

- `test_cutedsl_wrapper_gets_swiglu_limit`: runs `ensure_cutedsl_wrapper` with FlashInfer's `CuteDslMoEWrapper` mocked with `autospec=True`, so the kwargs are checked against FlashInfer's real signature.
  - With `swiglu_limit=10.0`, the wrapper must receive `{"swiglu_limit": 10.0}` and no other `swiglu_*` kwargs.
  - With no limit, it must receive none.
- `test_cutedsl_deepep_rejects_swiglu_limit`: `create_moe_runner` with `flashinfer_cutedsl` must raise for DeepEP plus `swiglu_limit=10.0`. It must still accept DeepEP without a limit, and `--moe-a2a-backend none` with the limit.

Results:

- On main both tests fail: `AssertionError: {} != {'swiglu_limit': 10.0}` and `AssertionError: ValueError not raised`.
- With the fix, all 22 tests in the file pass.
- With the kwarg misspelled as `swiglu_clamp_limit`, the first test fails with `TypeError: got an unexpected keyword argument 'swiglu_clamp_limit'`.

These related CPU tests pass before and after: `test_modelopt_nvfp4_moe_dispatch.py` (5), `test_flashinfer_cutlass_swiglu_params.py` (5), `test_modelopt_nvfp4.py` (7).

**Kernel test (SM100)**

`test_flashinfer_cutedsl_swiglu_limit` is added to `test/registered/unit/layers/quantization/test_nvfp4_moe_backends.py` (4-gpu-b200 suite). It runs the real `FusedMoE` with NVFP4 shards and `swiglu_limit=0.25` against the existing dequantized torch reference, with the DeepSeek-V4 clamp added to the reference. For these weights |gate| has a std of about 0.3, so the limit binds on about a fifth of the gate values. The test first checks that the clamped and unclamped references differ (cosine < 0.99), so a runner that ignores the limit cannot pass.

I ran this test on one B300 (sm_103):
- Image: `lmsysorg/sglang:nightly-dev-cu13-20261028-586355a8`, with torch 2.14.1+cu130 and FlashInfer 0.7.2. Its `pyproject.toml` and Dockerfile are identical to main 5cc9c933.
- Main: main 5cc9c933's `python/` with this PR's test files. `test_flashinfer_cutedsl` passes. `test_flashinfer_cutedsl_swiglu_limit` fails with `AssertionError: 0.8254664540290833 not greater than 0.99`. The kernel's output matches the unclamped reference (cos 0.9965), not the clamped one.
- With this PR: 5cc9c933 with this PR's four files. Both tests pass. The cosine is 0.9977 with the clamped reference and 0.8257 with the unclamped one.

I have no B200 (sm_100) run. On sm_120, the real `CuteDslMoEWrapper` is built with `swiglu_limit=0.25` without error, but `wrapper.run` fails before any GEMM in FlashInfer's `moe_sort` JIT build with `RuntimeError: No supported CUDA architectures found for major versions [9, 10]`. `test_flashinfer_cutedsl` fails the same way on main. The 0.25 limit and the cosine guard were chosen with a torch-only simulation of the same shapes and weight statistics (`limit_choice_sim.py`). At a limit of 0.25, 21.6% of gate values exceed the limit, and the cosine between the clamped and unclamped outputs is 0.83, well below the test's 0.99 threshold.

Environment: torch 2.14.1+cu130, flashinfer 0.7.1, nvidia-cutlass-dsl 4.8.0, RTX 5070 Ti (sm_120). I ran everything above on main at 5bb7ecc. I reran the CPU tests (new and related) on 5cc9c933, the base of this PR, with the same results.

## Speed Tests and Profiling

Not benchmarked. Models without `swiglu_limit` build the same wrapper as before.

- W4A4 kernel: the SwiGLU epilogue (FlashInfer 0.7.1) already runs the `fmin` clamps with the default limit, the float32 maximum, so a finite limit only changes a compile-time constant.
- W4A16 kernel (`SGLANG_FLASHINFER_CUTEDSL_NVFP4_W4A16=1`): a non-default limit selects its parameterized SwiGLU epilogue.
- In both cases FlashInfer compiles one more kernel variant, because the limit is part of its kernel cache key.
