# [Perf] [NVIDIA] moe: Add L20 block-FP8 Triton configs for Qwen4-Exp

[Upstream PR](https://github.com/sgl-project/sglang/pull/36993) · state: open · merged: False

## Original PR description

## Motivation

Qwen3.8-Flash-Next-FP8 (`Qwen4ExpForConditionalGeneration`) falls back to the default Triton MoE configuration on NVIDIA L20 for the TP4/EP4 shape: 128 local experts, hidden size 2560, intermediate size 640, top-k 10, and FP8 blocks `[128, 128]`. Current `main` still has no matching L20 configurations.

## Modifications

Add separate gate-up and down JSON configurations for M=1, 2, 4, 8, 16, 32, 64, 128, 256, 512, and 1024. There are no kernel or loader changes and no dependency on another PR.

The two files retain their original Triton 3.7.1 tuning directory. The current Triton 3.8.0 loader's version fallback was exercised with both files. Rebased onto `fd5c52588ff2`; tested head `8a8aceb2cc59` includes the required `6a39ddf1f2e0` CI baseline.

## Accuracy Tests

October 26 revalidation on one NVIDIA L20:

- **77/77 cases bitwise equal** to the current automatic heuristic, including eager and CUDA Graph output checks. Inputs are BF16, weights are FP8, and per-block weight scales vary independently in `[0.01, 0.05)`.
- Every M bucket covers synthetic all-local routing and three held-out real-model routing-ID tensors mapped to EP local ranks 0 and 3. Nonlocal expert IDs are `-1`. Activations, weights, and router weights are synthetic; this does not test checkpoint accuracy.
- The native loader resolves both files and all 11 buckets. Isolated CPU checks additionally cover 22 JSON records, 15 nearest-bucket lookups, version fallback, and deterministic-mode bypass.

## Speed Tests and Profiling

Source `8a8aceb2cc59`, torch `2.14.1+cu130`, Triton `3.8.0`, FlashInfer `0.7.2`, sglang-kernel `0.4.10`. The changed native-path packages were installed in an isolated overlay over the October 13 experiment environment.

Measure the full local `fused_moe` call, including the same input clone in both arms. After warmup, capture eight calls per CUDA Graph, replay 20 times per timing, and take medians from six paired trials in alternating A/B and B/A order. The table averages the six held-out routing/rank cases at each M; speedup is default/configured minus one.

| M | Default (us) | Configured (us) | Speedup |
| ---: | ---: | ---: | ---: |
| 1 | 54.892 | 19.656 | +179.27% |
| 2 | 62.411 | 24.406 | +155.72% |
| 4 | 72.089 | 35.247 | +104.53% |
| 8 | 85.429 | 53.211 | +60.55% |
| 16 | 141.284 | 111.685 | +26.50% |
| 32 | 229.650 | 207.050 | +10.92% |
| 64 | 278.164 | 253.380 | +9.78% |
| 128 | 333.733 | 318.734 | +4.71% |
| 256 | 409.431 | 396.834 | +3.17% |
| 512 | 502.963 | 488.649 | +2.93% |
| 1024 | 680.404 | 677.427 | +0.44% |

Across the 66 held-out routing-ID cases, the ratio of equally weighted latency sums gives **10.21% speedup**. This is not a serving-batch-weighted result. Across all 77 cases, **0 cases exceed a 2% latency regression**; worst observed median latency change is +0.55%.

These are single-GPU, local-expert microbenchmarks at the TP4/EP4 tensor shape. They exclude expert communication, checkpoint execution, and serving overhead. **No end-to-end throughput claim is made.** The previous Triton 3.7.1 GEMM-only measurements are superseded here by this explicitly scoped current-head validation.
