# [Fix] server-args: Treat YAML null as unset in --config files

[Upstream PR](https://github.com/sgl-project/sglang/pull/47702) · state: open · merged: False

## Original PR description

## Motivation

A null or empty value in a `--config` YAML file reaches argparse as the literal string `None`, because `ConfigArgumentMerger._convert_config_to_args` passes it through `str()`. String flags accept that silently, and int flags stop the server with an error that does not point at the config file.

Results from `prepare_server_args(["--config", ...])` on `main` and on this branch:

| `config.yaml` line | `main` | This PR |
| --- | --- | --- |
| `api-key: null` or `api-key:` | `api_key='None'` | `api_key=None` |
| `tokenizer-path: null` | `tokenizer_path='None'` | `tokenizer_path=None` |
| `chat-template: ~` | `chat_template='None'` | `chat_template=None` |
| `context-length: null` | exits with `argument --context-length: Invalid integer value: 'None'` | `context_length=None` |

The `api-key` row matters most. Someone who writes `api-key: null` to leave auth off gets auth turned on with the key `None`: a request with no key is rejected, and `Authorization: Bearer None` is accepted.

I checked the open PRs that touch this file, and none of them handle null values.

## Modifications

- `_convert_config_to_args` skips null values, so the flag behaves as if it were not in the file and keeps its default. Unsupported keys are still checked first, so they raise as before.
- Add a regression test next to the existing `--config` test in `test_server_args.py`. It covers string and int flags, all three YAML spellings of null, and a flag with a non-null default.
- Document the behavior in `server_arguments.mdx`.

This only changes top-level values. A null inside a list is unchanged, and nested mappings already go through `json.dumps`.
