# [Perf] diffusion: Defer full GC collections while importing the runtime

[Upstream PR](https://github.com/sgl-project/sglang/pull/44606) · state: closed · merged: True

## Original PR description

## Motivation

A diffusion scheduler process imports about ten thousand modules before it builds its pipeline. Imports create long-lived modules, classes and functions and very little garbage, yet CPython runs a full collection every time the surviving heap has grown by a quarter, and each one traces every tracked object again. A scheduler process runs 12 of them during startup, which together take about 1.6 seconds of CPU, with or without compiled bytecode.

Where those collections fall also depends on the import order rather than on the work done. Moving an import, for example to load a module on first use, can add or remove a whole-heap collection inside a given span of startup, which makes import time changes hard to judge.

## Modifications

- `runtime/utils/process.py` gains `defer_full_gc_for_imports()`, a context manager that raises the third GC threshold so that no automatic full collection runs inside the block. Young collections keep running, so short-lived cyclic garbage is freed as usual. Restoring the original thresholds lets automatic full collections resume after the block. On CPython 3.14.0–3.14.4, which uses incremental GC and ignores the third threshold, the context manager is a no-op.
- On exit it restores the thresholds it found, also when the block raises. Nested and concurrent blocks restore them when the last one exits, a child forked inside a block restores them at fork, and the collector's enabled state is never changed, so a process that disabled the collector keeps it disabled.
- It is used where diffusion processes import their runtime in bulk, in the activation phase of `bootstrap_scheduler_process` (platform initialization through the `gpu_worker` import), the activation phase of `bootstrap_http_server_process`, and pipeline and config discovery in the registry. Pipeline discovery enters the block only on its first run, so the registry lookups that return early touch nothing.
- No new option, and nothing changes for srt.

Two simpler forms were measured first and not used. `gc.disable()` over the same blocks saved the same CPU, but it also stops young collections, so about 7 MB of short-lived cyclic garbage (frames of caught exceptions, closures, package metadata structures) stayed alive until the block ended, which showed up as 8 MiB more anonymous memory in the HTTP server child. `gc.freeze()` after the imports would keep import-time objects out of every later collection, but frozen objects are never collected again, so it changes steady-state serving memory, and freezing after warmup is the existing pattern for that.

## Accuracy Tests

No output path changes. Only the timing of garbage collections during startup imports changes.

`test_process.py` checks that full collection is deferred where the collector supports threshold2, that incremental GC is left unchanged on CPython 3.14.0–3.14.4, and that nesting, exception exits with GC disabled, and forked children restore the correct state. The file passes on CPython 3.11.16, 3.12.15, 3.13.15, 3.14.0, 3.14.4, and 3.14.5; only the threshold2-specific collection assertion is skipped on 3.14.0–3.14.4. The earlier CPU diffusion-unit comparison had the same per-test outcomes as the base, apart from the added GC coverage.

## Speed Tests and Profiling

Measured on a CPU-only host with scripts that start each process the way it starts in a server, without touching a device. A scheduler child runs through `bootstrap_scheduler_process` up to the point where `build_pipeline` would construct the pipeline, and the `--webui` HTTP child runs through `bootstrap_http_server_process` up to `create_app`. After each run, the same process allocates 100,000 objects so that any collection this change postpones is paid inside the measurement. Each process ran once with compiled bytecode present, as in an installed package, and once with every module compiled from source.

The comparison ran as eight counterbalanced pairs with a local Cosmos3 Nano checkpoint, then eight fresh pairs with a local Wan2.1 T2V 1.3B checkpoint as an independent confirmation, each beside an A/A control that compared two separate copies of the base. A gain is listed only where both sets established it at 1 percent or more and the A/A control showed no difference. The table gives the mean change with this PR and its 95 percent interval over the pairs, for the Cosmos3 Nano and the Wan2.1 pairs.

| Process | Backend | Bytecode | CPU time | Wall time |
|---|---|---|---|---|
| scheduler child | auto | compiled | -2.9 % [-3.3, -2.6] and -2.8 % [-3.5, -2.2] | -5.8 % [-6.5, -5.0] and -5.2 % [-6.4, -4.0] |
| scheduler child | auto | from source | -2.5 % [-2.6, -2.3] and -2.5 % [-2.9, -2.2] | -4.5 % [-5.1, -3.9] and -4.5 % [-5.5, -3.6] |
| scheduler child | sglang | compiled | -2.8 % [-3.5, -2.0] and -3.0 % [-3.2, -2.8] | -5.2 % [-6.6, -3.7] and -5.5 % [-6.2, -4.8] |
| scheduler child | sglang | from source | -2.7 % [-3.2, -2.2] and -2.8 % [-3.2, -2.4] | -4.8 % [-6.0, -3.6] and -5.2 % [-6.3, -4.1] |
| HTTP child (`--webui`) | auto | compiled | -2.2 % [-2.7, -1.6] and -2.9 % [-3.4, -2.4] | -4.7 % [-6.0, -3.5] and -5.6 % [-6.7, -4.6] |
| HTTP child (`--webui`) | auto | from source | -2.8 % [-3.2, -2.3] and -2.6 % [-3.0, -2.2] | no claim |

In absolute terms the scheduler child uses about 0.7 s less CPU, out of about 26 to 28 s, and reaches the point where it would build its pipeline 0.7 to 0.8 s sooner. It runs 8 full collections instead of 12 in every run, and spends about 0.8 s less in garbage collection. The HTTP child wall time from source has no claim because the A/A control of the Wan2.1 pairs read a difference of -0.53 % [-1.05, -0.02] on that metric.

No performance claim for the launcher and HTTP frontend process, where no full collection falls inside the blocks this change covers. In every process measured, including the launcher, anonymous memory (`Pss_Anon`), peak RSS (`VmHWM`), minor page faults and the number of full collections read no worse than without this change.

### Additional real-server check

Compared base `b234b5c32e0d` with `04c42400522d` on one H200 (143771 MiB), Xeon Platinum 8558P, driver 595.71.05, Python 3.12.15, PyTorch 2.14.1+cu130, Transformers 5.19.0, and Diffusers 0.37.0. The native SGLang backend used FA3, speed mode, GPU-resident components, and no torch.compile or CUDA graphs.

Model: `Wan-AI/Wan2.1-T2V-1.3B-Diffusers`, revision `0fad780a534b6463e45facd96134c9f345acfa5b`. Server warmup: 256×256, 9 frames, one step. First API request: the same shape, two steps, seed 42, CFG 5, prompt “A small red boat floating on a calm lake.” We timed readiness via `/health` and the first completed `/v1/videos` job, polling every 100 ms. Checkpoint download and kernel priming were excluded. A/B/B/A order, two measured starts per revision; means below:

| Measurement | Base | This PR |
|---|---:|---:|
| Process start → server ready | 41.97 s | 41.47 s |
| Process start → first request completed | 42.28 s | 41.78 s |
| First request after readiness | 0.309 s | 0.309 s |

All four output MP4s were byte-identical. This small sample observed about 0.50 s (1.2%) lower complete startup latency, not a general speedup guarantee. It does not establish a steady-state inference speedup. The scheduler and HTTP bootstrap ordering tests also passed.
