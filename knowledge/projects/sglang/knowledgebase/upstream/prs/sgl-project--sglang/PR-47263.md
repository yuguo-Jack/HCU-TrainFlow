# [DeepEP] Give each TBO sub-batch its own normal-mode buffer

[Upstream PR](https://github.com/sgl-project/sglang/pull/47263) · state: closed · merged: False

## Original PR description

### Problem

`MaybeTboDeepEPDispatcher` creates one inner dispatcher per TBO sub-batch, but the
DeepEP branch lets both of them share a single process-wide `Buffer`, while the
mori branch already hands each inner dispatcher its own instance:

```python
# python/sglang/srt/batch_overlap/two_batch_overlap.py
if get_moe_a2a_backend().is_deepep():
    self._inners = [
        DeepEPDispatcher(runner_backend=runner_backend, **kwargs)
        for _ in range(num_inner_dispatchers)
    ]                                                  # <-- shared buffer
...
elif get_moe_a2a_backend().is_mori():
    self._inners = [
        MoriEPDispatcher(instance_id=i, **kwargs)      # <-- per-sub-batch instance
        for i in range(num_inner_dispatchers)
    ]
```

`DeepEPBuffer` is explicitly one-per-process (its own docstring says so):

```python
class DeepEPBuffer:
    """Managing facade for the process-wide DeepEP comm buffer; the state
    itself lives on ``ctx.resources`` (one entry per process)."""
```

At the same time, the DeepSeek-V4 prefill TBO strategy added in #29362 ships
`tbo_delta_stages=0`, which means both sub-batches have a `dispatch -> combine`
transaction in flight simultaneously:

```python
# python/sglang/srt/batch_overlap/operations_strategy.py  (_compute_moe_deepseek_v4_prefill)
layer.mlp.op_dispatch_a, YieldOperation(), layer.mlp.op_dispatch_b,
layer.mlp.op_experts, layer.mlp.op_combine_a, YieldOperation(),
layer.mlp.op_shared_experts, layer.mlp.op_combine_b, ...
# OperationsStrategy(tbo_delta_stages=0, ...)
```

So with DeepEP + TBO the two sub-batches interleave as
`dispatch(A) -> dispatch(B) -> combine(A) -> combine(B)` on **one** buffer.
Whether that is safe depends entirely on whether the underlying DeepEP
implementation keeps per-transaction layout state. The existing FIXME in the
dispatcher acknowledges the same fragility:

```python
# python/sglang/srt/layers/moe/token_dispatcher/deepep.py
# FIXME: `handle` should be transmitted with tokens from dispatch to combine.
# However, doing this would incur an unknown synchronization error, but keeping
# `handle` as a member variable works.
```

### What this PR does

Key the `DeepEPBuffer` process state by a `slot` id and let each inner dispatcher
own a slot, mirroring what the mori path already does with `instance_id`.
Defaults keep `slot=0`, so single-batch (non-TBO) behaviour is byte-identical and
low-latency mode is untouched (it keeps one buffer; its hook-based API is already
designed to be in flight).

Net effect: with TBO enabled, the two sub-batches no longer share normal-mode
buffer state.

### Why it matters

On a backend whose DeepEP normal-mode buffer keeps only the *last* dispatch's
layout, the shared-buffer path is not merely slower — it is incorrect, and in our
case it aborts. We hit this on Kunlunxin P900 (`sglang-kunlun` OOT plugin):
3 of 8 ranks abort in the first prefill batch of the shipped V4 prefill strategy:

```
deep_ep.cpp:207 'recv_num_tokens >= 0 and "bkcl_notify_dispatch_standard failed"'
  op_dispatch_b -> dispatch_b -> _dispatch_core -> buffer_v2.py:545
```

With the per-slot buffer the same workload runs. We cannot say whether any CUDA
DeepEP build is affected — on that backend the shared buffer evidently works
today, which is why this is proposed as a robustness/symmetry fix rather than a
bug report against the CUDA path.

### Measurements (Kunlunxin P900, 2 nodes x 4 cards, TP8/EP8/DP8)

**Both columns below have TBO enabled** and differ only in buffer ownership, i.e.
this is a shared-buffer vs per-sub-batch-buffer comparison, not a TBO on/off one.

Pure-prefill throughput, real-text corpus, 512 requests @ concurrency 64,
input 2048 tokens; 5 cells per round, first cell discarded (cold), mean of the
remaining 4; `fail=0`, `retract=0`:

| node pair | shared buffer | per-sub-batch buffer | delta |
|---|---|---|---|
| A | 18582 in-tok/s | 19655 | **+5.78%** |
| B | 19487 (spread 2.4%) | 21306 (spread 2.0%) | **+9.33%** |

Energy, sampled at 1 Hz per card over exactly the same windows:

| node pair | shared buffer | per-sub-batch buffer | delta |
|---|---|---|---|
| A | 0.0832 J/in-tok | 0.0808 | **−2.9%** |
| B | 0.0801 J/in-tok | 0.0769 | **−4.0%** |

Accuracy (GSM8K via evalscope, 200 items, batch 64, temperature 0):
TBO off 98.5% / TBO on + shared buffer 99.0% / TBO on + this PR 98.5%
— i.e. one item out of 200, no regression.

### Caveats

- Measured on an out-of-tree Kunlunxin backend, on a vendor branch based on
  0.5.17. Not measured on CUDA hardware — we have no NVIDIA DeepEP setup.
- Extra memory: one additional normal-mode buffer per extra sub-batch. On our
  setup both fit in a 2 GiB symmetric heap with all 8 ranks constructing
  successfully, and the second buffer costs nothing when idle
  (−0.27%, within noise, measured with `tbo_delta_stages=2`).
- The size of that extra buffer depends on `deepep_mode`: under
  `DeepEPMode.NORMAL` it is a normal-mode buffer only, while under
  `DeepEPMode.AUTO` the extra slot is also constructed with
  `low_latency_mode=True`, so its `num_rdma_bytes` is maxed against the
  low-latency hint. The numbers above are from the normal-mode path.

Closing this: wrong target repository on my side.

The behaviour this change addresses — a shared normal-mode DeepEP buffer keeping only the last dispatch's layout — is a property of the **Kunlunxin DeepEP port**, not something we can demonstrate on a CUDA DeepEP build (we have no NVIDIA DeepEP environment). Asking upstream to carry a change whose only evidence comes from an out-of-tree backend isn't the right call, so I'm re-filing it against the Kunlun plugin repo (`baidu-baige/sglang-kunlun`), where the affected code actually lives.

Apologies for the noise. The upstream `mori` path already gives each inner dispatcher its own instance (`MoriEPDispatcher(instance_id=i, ...)`), so if a CUDA-side DeepEP issue is ever observed, that precedent and this patch are a starting point.
