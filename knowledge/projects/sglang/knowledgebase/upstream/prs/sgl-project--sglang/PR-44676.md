# [Feat] dflash: Serve SpecForge MLA drafts through the target MLA attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/44676) · state: open · merged: False

## Original PR description

Serve SpecForge DFlash MLA drafts (`dflash_config.attention_mode: "mla"`, SpecForge #758) with the target's DeepSeek MLA attention. SpecForge exports DeepSeek's MLA parameterization: the same projection names, an optional `q_lora_rank`, `rope_interleave` and `mscale_all_dim` scaling. The draft layer is therefore a thin `DeepseekV2AttentionMLA` subclass. It runs the target's absorbed-MLA forward and backend dispatch, and stores one latent row plus one RoPE key per token in `MLATokenToKVPool`.

Only the DFlash-specific parts are new:

- `DeepseekV2AttentionMLA` takes `attn_type` and `sliding_window_size`. The defaults are unchanged.
- `DFlashMLAAttention`:
  - sets the layer's DFlash causality (bidirectional by default, causal with `is_causal=true` and `layer_types`);
  - loads SpecForge's separate `q_a_proj` / `kv_a_proj_with_mqa` into the fused down projection;
  - absorbs `kv_b_proj` into `w_kc` / `w_vc` when that weight loads;
  - projects target-context latents for the worker.
- `ModelConfig` routes an MLA draft through the existing MLA branch.
- Each MLA layer writes its own target-context KV with `DFlashMLAAttention.write_context_kv`: latent rows through `set_mla_kv_buffer`, and accepted-prefix commits through the new masked `MLATokenToKVPool.set_mla_kv_buffer_prefix_valid`. The DFlash worker and DSpark's context-KV writer both call it, so DFlash, DFlash2, Domino and DSpark drafts share one MLA path. DSpark already builds the same layers, and its fused GQA write paths are skipped for MLA drafts.
- The draft backend goes through the existing DFlash resolution: `--speculative-draft-attention-backend` if set, otherwise the target's backend, otherwise the platform fallback.
  - Two backends serve only one attention layout, and each falls back with a warning when it doesn't match the draft: `tokenspeed_mla` serves only MLA drafts, and `trtllm_mha` only non-MLA drafts.
  - A draft worker never inherits `tokenspeed_mla` from the target; it gets it only when named, which the DFlash hook does for MLA drafts. DSpark resolves its backend outside that hook and applies the `trtllm_mha` rule itself.
  - MLA backends take the draft's mask from the layer's `attn_type`. FlashInfer MLA fixes it once per batch, using the same helper the draft layers use.
  - `triton`, `flashinfer` and `tokenspeed_mla` are validated as MLA draft backends, and only `triton` serves sliding MLA layers.

The following are rejected at load or launch:

- quantized draft weights;
- `attention_bias`;
- attention sinks and value scaling;
- RoPE types other than `default`, `yarn` and `deepseek_yarn` (the target layer serves scaling as DeepSeek YaRN);
- MLA mixed with GQA/MHA layers;
- `--dcp-size > 1`.

Each backend checks its own kernel limits, such as TokenSpeed's FP8 KV and page size.

For a BF16 MLA draft, add one of these to the DFlash launch:

```bash
# FlashInfer
--speculative-draft-attention-backend flashinfer \
--speculative-draft-kv-cache-dtype bf16

# TokenSpeed, with tokenspeed_mla installed
--speculative-draft-attention-backend tokenspeed_mla \
--speculative-draft-kv-cache-dtype fp8_e4m3 \
--page-size 32
```

Validation on one GB300 (SM103), TP1, BF16 models. Image: sglang nightly cu13 2026-10-06 (PyTorch 2.14.1+cu130, FlashInfer 0.7.0.post1, sglang-kernel 0.4.9, TokenSpeed MLA 0.1.8, Transformers 5.17.0).

At `080fb0bd70`:

- **Draft MLA tests:** `test_dflash_mla_backends.py` and `test_dflash_mla.py` passed with no skips.
  - The GPU backend test runs real `triton`, `flashinfer` and `tokenspeed_mla` kernels, with bidirectional and causal masks, eagerly and after one CUDA graph replay with changed prefixes. The reference is independent FP32 SpecForge math.
  - The GPU bounds are relative L2 below 1.2% plus element-wise tolerance 0.025 for BF16 KV, and relative L2 below 5% for TokenSpeed's FP8 KV.
  - The CPU unit test checks:
    - SpecForge reference numerics through the target MLA forward, for both Q parameterizations and both RoPE conventions;
    - loading the split checkpoint and absorbing `kv_b_proj`;
    - compressed KV pool sizing.
- **CPU:** the unit tests and the arg-hook tests pass; ruff, isort and codespell are clean.

The source at `080fb0bd70` is identical to `1663e55397`, where these broader checks ran:

- **Maximum relative L2 against FP32:**

  | Backend / KV | Max relative L2 |
  | --- | ---: |
  | triton BF16 | 0.48% |
  | flashinfer BF16 | 0.50% |
  | triton FP8 | 4.23% |
  | tokenspeed_mla FP8 | 4.52% |

- **Target MLA regressions:** the FlashInfer MLA and TokenSpeed MLA suites, Triton eagle-verify in eager and CUDA-graph modes, and the DFlash hook and draft-config tests gave 26 passed and 12 skipped (skips declared by the suites).
- **Real Engine smoke, one per draft backend:** a Qwen3 MHA target with an MLA draft checkpoint in SpecForge's split `q_a_proj` / `kv_a_proj_with_mqa` layout. Each run checked:
  - three rounds of 24 tokens: single, batch 2, and a repeated batch 2 with prefix-cache hits;
  - target and draft CUDA graph replay at batch sizes 1 and 2;
  - batched prefix commits into `[slots,1,576]` MLA pools, FP8 for TokenSpeed.

  The checkpoints are deterministic random weights, so this validates integration only, not acceptance rate or quality. The triton-draft smoke used a triton target, because this image's FlashInfer 0.7.0.post1 is below the Engine's 0.7.1 minimum for a FlashInfer target.

Later commits, each validated on GB300 as well:

- **`a4f342b3cb` (generic draft-backend resolution and the `--dcp-size` check):** launch-time logic only; its CPU tests pass.
- **`b1d3760dec` (masked prefix commit) and `a36ebf0c0b` (`write_context_kv`):** the GPU backend test passes. Engine smokes for the triton, flashinfer and tokenspeed_mla drafts produce greedy output tokens identical to the earlier runs.
- **`ed0eb908ce` (DSpark MLA drafts):** 31 unit tests pass (38 subtests). Engine smokes with a tiny DSpark MLA draft pass on triton (static and compact ragged verify), flashinfer and tokenspeed_mla.
- **`4e62995d8e` (layout guards for draft workers):**
  - With a `trtllm_mha` target, an MLA DSpark draft builds flashinfer whether its backend is inherited or set to `trtllm_mha`.
  - An explicit triton draft keeps triton.
  - A unit test shows a draft worker no longer inherits a target's `tokenspeed_mla`.

Not yet validated: multi-rank TP, HIP, sliding MLA layers on triton, long-context RoPE scaling, and trained-checkpoint acceptance.

Compressed storage holds `kv_lora_rank + qk_rope_head_dim` values per token and layer, instead of per-head K and V. For latent 512, RoPE 64, 32 heads and K/V widths 192/128, that is 17.78x smaller. Measured on the previous revision: 3,203 MiB vs 180 MiB in BF16 for 32,768 tokens and five layers.

Reproduction:

```bash
python -m pytest -q \
  test/registered/unit/spec/test_dflash_mla.py \
  test/registered/unit/spec/test_oot_dflash_hooks.py \
  test/registered/attention/test_dflash_mla_backends.py
```
