# [Feat] dflash: Serve SpecForge MLA drafts through the target MLA attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/44676) · state: closed · merged: True

## Original PR description

Serve SpecForge DFlash MLA drafts (`dflash_config.attention_mode: "mla"`, SpecForge #758) with the target's DeepSeek MLA attention. SpecForge exports DeepSeek's MLA parameterization: the same projection names, an optional `q_lora_rank`, `rope_interleave` and `mscale_all_dim` scaling. The draft layer is therefore a thin `DeepseekV2AttentionMLA` subclass. It runs the target's absorbed-MLA forward and backend dispatch, and stores one latent row plus one RoPE key per token in `MLATokenToKVPool`.

Only the DFlash-specific parts are new:

- `DeepseekV2AttentionMLA` takes `attn_type` and `sliding_window_size`. The defaults are unchanged.
- `DFlashMLAAttention`:
  - sets the layer's DFlash causality (bidirectional by default, causal with `is_causal=true` and `layer_types`);
  - loads SpecForge's separate `q_a_proj` / `kv_a_proj_with_mqa` into the fused down projection;
  - absorbs `kv_b_proj` into `w_kc` / `w_vc` when that weight loads;
  - projects target-context latents for the worker.
- `ModelConfig` routes an MLA draft through the existing MLA branch.
- Each MLA layer writes its own target-context KV with `DFlashMLAAttention.write_context_kv`: latent rows through `set_mla_kv_buffer`, and accepted-prefix commits through the new masked `MLATokenToKVPool.set_mla_kv_buffer_prefix_valid`. The DFlash worker and DSpark's context-KV writer both call it, so DFlash, DFlash2, Domino and DSpark drafts share one MLA path. DSpark already builds the same layers, and its fused GQA write paths are skipped for MLA drafts.
- MLA drafts run on the default MLA draft backends: `flashinfer` on CUDA (SGLang's default MLA backend on Blackwell), `triton` on ROCm and XPU. The draft backend goes through the existing DFlash resolution: `--speculative-draft-attention-backend` if set, otherwise the target's backend, otherwise that default.
  - A target's MLA-only backend (`trtllm_mla`, `cutedsl_mla`) is not a draft backend, so an MLA target's draft falls back to the default.
  - `trtllm_mha` serves only non-MLA drafts. An MLA draft that would get it falls back to the default MLA draft backend, not to `fa4`, which main now picks for non-MLA drafts on SM100. DSpark resolves its backend outside the DFlash hook and applies the same `trtllm_mha` rule itself.
  - FlashInfer MLA fixes the mask once per batch, using the same helper the draft layers use. Triton takes it from each layer's `attn_type`, and only `triton` serves sliding MLA layers.

The following are rejected at load or launch:

- quantized draft weights;
- `attention_bias`;
- attention sinks and value scaling;
- RoPE types other than `default`, `yarn` and `deepseek_yarn` (the target layer serves scaling as DeepSeek YaRN);
- MLA mixed with GQA/MHA layers;
- `--dcp-size > 1`.

A BF16 MLA draft needs no extra flags on CUDA. To pin the backend and the draft KV dtype explicitly:

```bash
--speculative-draft-attention-backend flashinfer \
--speculative-draft-kv-cache-dtype bf16
```

### Validation

Rebased onto main `d0a7565436` as two commits: the PR as it was (11 commits, squashed) and the switch from `tokenspeed_mla` to the default MLA backends, since main removed `tokenspeed_mla` in #44803.

At `28405e8424`, on one GB300 (TP1, BF16), with torch 2.14.1+cu130, FlashInfer 0.7.2, sglang-kernel 0.4.10 and Transformers 5.19.0 (main's pins):

- **Draft MLA tests:** `test_dflash_mla_backends.py` (2 passed, 4 subtests, no skips) and `test_dflash_mla.py` with the hook tests (9 passed).
  - The GPU backend test runs real `triton` and `flashinfer` kernels, with bidirectional and causal masks, eagerly and after one CUDA graph replay with changed prefixes. The reference is independent FP32 SpecForge math, within relative L2 1.2% and element-wise tolerance 0.025.
- **Target MLA regressions:** the FlashInfer MLA suite and Triton eagle-verify in eager and CUDA-graph modes gave 8 passed and 1 skipped. The skip is main's known SM10.3 FlashInfer EAGLE-graph failure.
- **Real Engine smoke, one per draft backend:** a Qwen3 MHA target with a tiny MLA draft checkpoint in SpecForge's split `q_a_proj` / `kv_a_proj_with_mqa` layout.

  | Target backend | Draft backend flag | Draft backend built |
  | --- | --- | --- |
  | `flashinfer` | `triton` | `TritonAttnBackend` |
  | `triton` | `flashinfer` | `FlashInferMLAAttnBackend` |
  | `trtllm_mha`, page 32 | none | `FlashInferMLAAttnBackend`, after the `trtllm_mha` fallback warning |

  Each run checked:
  - three rounds of 24 tokens: single, batch 2, and a repeated batch 2 with prefix-cache hits;
  - target and draft CUDA graph replay at batch sizes 1 and 2;
  - batched prefix commits into a `[slots,1,576]` BF16 MLA pool.

  The checkpoints are deterministic random weights, so this validates integration only, not acceptance rate or quality.

- **CPU:** the unit tests and the arg-hook tests pass; ruff, isort and codespell are clean. The new resolver case fails on the pre-switch commit, where an MLA draft leaving `trtllm_mha` lands on `fa4`.

Before the rebase, the same draft math was validated on GB300 against independent FP32 SpecForge math (max relative L2 0.48% for triton BF16 and 0.50% for flashinfer BF16), together with Engine smokes for DSpark MLA drafts on triton and flashinfer.

Not yet validated: multi-rank TP, HIP, `fa3` / `fa4` as MLA draft backends, sliding MLA layers on triton, long-context RoPE scaling, and trained-checkpoint acceptance.

Compressed storage holds `kv_lora_rank + qk_rope_head_dim` values per token and layer, instead of per-head K and V. For latent 512, RoPE 64, 32 heads and K/V widths 192/128, that is 17.78x smaller. Measured on an earlier revision: 3,203 MiB vs 180 MiB in BF16 for 32,768 tokens and five layers.

```bash
  test/registered/unit/spec/test_dflash_mla.py \
  test/registered/unit/spec/test_oot_dflash_hooks.py \
  test/registered/attention/test_dflash_mla_backends.py
```
