# Fix SGLANG_DEFAULT_THINKING ignored by dsv4/dsv32 reasoning parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/28288) · state: open · merged: False

## Original PR description

## Motivation

For the DeepSeek V4 / V3.2 custom encoder path, `SGLANG_DEFAULT_THINKING` is only read on the **prompt-encoding** side (`_apply_jinja_template`, `serving_chat.py:648`). The **reasoning parser** side (`_get_reasoning_from_request`) never consults the env.

As a result, when an operator sets `SGLANG_DEFAULT_THINKING=1` and the client does **not** pass `chat_template_kwargs={"thinking": true}`:

- the prompt is built in thinking mode (ends with `<｜Assistant｜><think>`), so the model **does** think;
- but `_get_reasoning_from_request` returns `False` (dsv4 has no chat template → `reasoning_config=None` → the `explicit_thinking` branch only returns `True` when the request explicitly sets `thinking=True`);
- so `is_force_reasoning=False`, and since the model output does not re-emit a leading `<think>` (it's already in the prompt), the detector treats nothing as reasoning.

Net effect: the leading reasoning text **and the literal `</think>` marker leak into `content`**, while `reasoning_content` comes back empty. This is confusing — the env appears to "half-enable" thinking.

## Modification

Make the resolved thinking decision a **single source of truth**: after resolving `thinking_requested` (request value, falling back to the env), persist it back onto `request.chat_template_kwargs` so the reasoning parser agrees with the prompt we actually built.

- Scoped to the dsv4/dsv32 custom encoder path (`chat_encoding_spec in ("dsv4", "dsv32")`) — the only path the env actually drives. Jinja-template models are unaffected.
- Uses `setdefault`, so an explicit `thinking` value in the request still wins over the env default.

## Tests

Added three unit tests in `test_serving_chat.py`:
- env default ON + request silent → request normalized to `{"thinking": True}` and parser agrees (`reasoning` enabled);
- env default OFF + request silent → `{"thinking": False}`, parser stays off;
- explicit `thinking=False` in request + env ON → explicit value wins.

> Note: I was unable to run the suite locally due to unrelated dependency-version mismatches in my local env (`openai` / `huggingface_hub` / `datasets`). Relying on CI for full verification.

## Code Review

This pull request addresses an issue where the reasoning parser and prompt template disagree on the thinking mode for DeepSeek v4/v32, which can cause </think> tags to leak into the output. It resolves this by persisting the resolved thinking decision back onto the request's chat_template_kwargs and adds unit tests to verify the behavior. However, the review feedback correctly points out that performing this normalization inside _apply_jinja_template is too late in the pipeline, as _process_messages evaluates the thinking mode beforehand and can bypass _apply_jinja_template entirely. It is recommended to move this logic to the beginning of _process_messages.
