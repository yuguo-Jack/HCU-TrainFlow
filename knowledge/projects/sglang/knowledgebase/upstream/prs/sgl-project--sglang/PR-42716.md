# [Fix] [AMD] hicache: Serve encoder-replay prefix hits with a paged DSpark draft SWA

[Upstream PR](https://github.com/sgl-project/sglang/pull/42716) · state: closed · merged: True

## Original PR description

## Motivation

DeepSeek-V4.1 with DSpark and `--enable-encoder-swa-bounded-replay` keeps the target's SWA state in a per-request window (`DeepSeekV4TokenToKVPool.request_window`), which replay rebuilds on admission. Since #44673 the CUDA DSpark draft keeps its SWA in a per-request ring, so on CUDA the radix tree has no SWA component under encoder replay. On HIP the draft still addresses a paged SWA pool through the target's allocator, so the tree keeps an SWA component that only the draft uses. `SWAComponent.create_match_validator` and the Rust tree core's validator skip the SWA gate only for the per-request SWA ring (`is_swa_req_ring`). With HiCache on and no SWA host pool, every host-only node fails that check: `host_hit_length` stays 0 and `load_back` never runs, so the host tier fills up but never serves a hit. Device nodes whose draft SWA was evicted are rejected the same way, although replay rebuilds the target window in both cases.

Measured before #44673, while the CUDA draft still used paged SWA: DeepSeek-V4.1-Flash, TP4 on 4x RTX PRO 6000 Blackwell (SM120), DSpark, encoder SWA replay, HiCache ratio 2: send a 54K-token prompt, then about 2.74M tokens of unrelated prompts to evict it from the 2.64M-token device pool, then the same prompt again. I measured this with an earlier revision of this fix, on an older upstream base; this exact diff was not benchmarked.

| | host-hit tokens | TTFT after eviction (cold) |
|---|---|---|
| before | 0 | 4.98 s (7.43 s) |
| after | 53,760 | 0.72 s (7.30 s) |

Both runs recovered the passkey from the prompt.

#42446 changes the same Python gate for HiCache without an SWA host pool. This PR also covers the Rust tree core and request windows with HiCache off, and keeps the SWA match gate for paged allocators without a request window.

## Modifications

- `CacheInitParams.swa_gates_prefix_match` declares whether tree-held SWA gates prefix matching. `kv_cache_builder` sets it to `False` for a per-request SWA ring, and for paged SWA beside the target's encoder-replay `request_window`, which only the draft then uses (after #44673, on HIP only). The tree no longer inspects the allocator or the pool.
- `SWAComponent`'s validator reads the flag, and `RustUnifiedTreeCore` passes it to the Rust core's existing `swa_req_ring` gate flag. No Rust change; the ring check `is_swa_req_ring` moves from the validator into the builder.
- `test_rust_tree_core_integration.py`, parameterized over both tree cores with stand-in request windows:
  - `test_swa_match_ignores_tombstones_with_a_request_window`, with and without HiCache: an SWA tombstone no longer truncates the reusable device prefix.
  - `test_swa_host_only_prefix_matches_with_a_request_window`: a backed-up prefix demoted to host, with no SWA host pool, is a host hit (`host_hit_length == 8`) with a request window and still a miss with paged SWA.
  - All request-window cases pass with this change.

Note for reviewers: without an SWA host pool, host load-back does not restore the DSpark draft's paged SWA history. Encoder replay rebuilds the target window; ordinary prefill injects draft state for uncached tokens. Whether the missing draft history lowers initial acceptance is unmeasured. Draft tokens are verified against the target logits.
