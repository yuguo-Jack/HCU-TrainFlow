# [AMD] Run Quark MXFP4 MoE as W4A16 via triton_kernels on RDNA (gfx1151)

[Upstream PR](https://github.com/sgl-project/sglang/pull/41389) · state: open · merged: False

## Original PR description

## Motivation

Quark MXFP4 MoE checkpoints (e.g. `amd/Qwen3.5-35B-A3B-MXFP4`) cannot run correctly on RDNA GPUs such as gfx1151 (Radeon 8060S / Strix Halo), which have neither FP4 hardware nor an AITER FP4 MoE kernel:

- Without `SGLANG_USE_AITER=1`, the server crashes after weight loading with `NameError: name 'e8m0_shuffle' is not defined`, because `process_weights_after_loading` calls `e8m0_shuffle` on every non-gfx1250 GPU while the import is gated on `_use_aiter`.
- With `SGLANG_USE_AITER=1`, the server starts, but the output is garbage (GSM8K 8%, chat echoes the question). The scales are preshuffled into the gfx950 `e8m0_shuffle` layout while the weights are not shuffled (`_is_shuffle_moe_mxfp4` is gfx95-only), and aiter's `fused_moe` falls back to its "2stage default" kernel on gfx1151.

`triton_kernels`' `matmul` can already upcast MXFP4 weights inside the kernel with bf16 activations, and it computes correctly on gfx1151, so this PR uses it as a W4A16 path for these GPUs.

## Modifications

All changes are in `python/sglang/srt/layers/quantization/quark/schemes/quark_w4a4_mxfp4_moe.py`:

- Add `_use_triton_w4a16`, enabled on HIP when the GPU is neither gfx95x nor gfx1250 (opt out with `SGLANG_QUARK_MXFP4_MOE_W4A16=0`). gfx950 and gfx1250 keep their existing AITER paths unchanged.
- `create_weights`: don't apply AITER MoE padding when the W4A16 path is active.
- `create_moe_runner`: skip the AITER runner requirement on the W4A16 path.
- `process_weights_after_loading`: on the W4A16 path, swizzle the packed MXFP4 weights and e8m0 scales with the existing `_swizzle_mxfp4` helper, build `PrecisionConfig`s (`b_microblock_size=32`, fp32 output for w2), and drop the original loaded tensors. The AITER preshuffle (and the `e8m0_shuffle` call) is no longer reached on these GPUs.
- `apply_weights`: on the W4A16 path, build expert-major ragged routing from the standard `topk_ids` / `topk_weights` entirely on device (`argsort` + `scatter_add_`, no `bincount`, so it's CUDA-graph capturable). Then run gate_up `matmul` (gather) → `silu_and_mul` → down `matmul` (scatter + router weights), and reduce the scattered `num_tokens * top_k` rows over `top_k`.
- The path asserts a serialized MXFP4 checkpoint and `silu` activation, so unsupported configurations fail loudly instead of computing wrong results.

Activations stay in bf16 (W4A16) rather than being quantized to MXFP4 as on gfx950, so accuracy is at least as good as the W4A4 path.

## Accuracy Tests

Model `amd/Qwen3.5-35B-A3B-MXFP4` on 1x gfx1151 (Radeon 8060S, 96 GB VRAM carve-out), `--attention-backend triton --context-length 8192`, sglang at `172b1b4825` in the `rocm/sgl-dev:v0.5.20-rocm724-gfx1151-20260923` image (ROCm 7.2.4, torch 2.9.1, triton 3.7.0). The file touched here is unchanged between that commit and current `main`. Reference: `Qwen/Qwen3.5-35B-A3B` (BF16) on the same machine and flags.

| Model | Path | MGSM-en (100, chat, thinking off) | GSM8K 5-shot (200) |
|---|---|---|---|
| Qwen3.5-35B-A3B BF16 | unquantized | 0.98 | 0.945 |
| Qwen3.5-35B-A3B-MXFP4 | before, `SGLANG_USE_AITER=1` | — | 0.080 (50 q) |
| Qwen3.5-35B-A3B-MXFP4 | before, default | crash (`NameError: e8m0_shuffle`) | — |
| Qwen3.5-35B-A3B-MXFP4 | **this PR** | **0.97** | **0.970** |

Kernel-level check on real layer-3 weights: the W4A16 MoE output vs. an fp32 reference built from the dequantized MXFP4 weights (`_dequant_mxfp4_to_bf16`) gives a relative error of 0.41–0.43% for m = 1 … 256 tokens.

## Benchmarking and Profiling

Same setup as above.

| Model | Path | Decode bs=1 (in 512 / out 256) | Median TPOT | Throughput, 16 concurrent (MGSM) |
|---|---|---|---|---|
| Qwen3.5-35B-A3B BF16 | unquantized | 9.38 tok/s | 103.5 ms | 46.8 tok/s |
| Qwen3.5-35B-A3B-MXFP4 | **this PR** | 8.37 tok/s | 118.2 ms | 79.7 tok/s |

The W4A16 path uses the default `triton_kernels` opt flags (`num_warps=8`) with no gfx1151 tuning yet. Single-request decode is slightly slower than BF16, while batched throughput is 1.7x BF16. Weight loading takes 15.6 s (vs. 63.5 s for BF16), and CUDA graph capture works.
