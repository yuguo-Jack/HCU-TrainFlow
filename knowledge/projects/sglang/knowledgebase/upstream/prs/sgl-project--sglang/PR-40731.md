# [Fix] disaggregation: Pin a retract rebootstrap to the prefill DP rank the receiver is bound to

[Upstream PR](https://github.com/sgl-project/sglang/pull/40731) · state: open · merged: False

## Original PR description

Fixes #40730
Refs #39357

## Motivation

Follow-up to #39357 (`5c2de3f355`), which made `build_rebootstrap_payload`
carry `routed_dp_rank` so a PD true-retraction recompute goes back to the
prefill DP that served the request. It reads `Req.disagg_prefill_dp_rank`,
which is only set when the client or the router supplied the rank on the
original `/generate`. In every other deployment the field is `None`, the
recompute request carries `routed_dp_rank: null`,
`DataParallelController.maybe_external_dp_rank_routing` returns `False`, and
the recompute is dispatched by the prefill's normal load balancer.

That matters because the decode receiver is not rebuilt for a rebootstrap.
`CommonKVReceiver.init(prefill_dp_rank)` fetches the bootstrap infos of exactly
that prefill DP rank's TP/PP/CP ranks and calls `_register_kv_args()`, which
registers this decode rank's kv_args with those ranks only; nothing re-resolves
it afterwards. When the recompute lands on a different DP, that DP bootstraps
for the room with no decode peer registered while the bound receiver waits for
a transfer nobody starts. Both sides only unblock on their 300 s timeouts and
the request fails. The wrongly-routed prefill also re-registers the
`bootstrap_room -> dp_rank` entry on the bootstrap server, since without
`disagg_prefill_dp_rank` its `CommonKVSender` takes the
`_register_prefill_dp_rank()` branch.

With `--load-balance-method auto` a PD prefill defaults to
`follow_bootstrap_room`, where the DP controller re-derives the same rank from
the unchanged `bootstrap_room`, so the omission is invisible. It bites as soon
as prefill DP routing is load-aware (`round_robin`, `total_requests`,
`total_tokens`) -- exactly the case where decode has to resolve the rank
through `CommonKVReceiver.query_prefill_dp_ranks` and the resolved rank has
nothing to do with `bootstrap_room % dp_size` -- and also with
`SGLANG_DISAGGREGATION_FORCE_QUERY_PREFILL_DP_RANK=1`.

The rank is known on the decode side; it just was not kept anywhere the payload
builder could read it.

## Modifications

**`python/sglang/srt/disaggregation/decode.py`** - all three
`decode_req.kv_receiver.init(...)` call sites in `DecodePreallocQueue` (the
fake-transfer shortcut, the cache-only fast path in `add`, and the
`_resolve_pending_reqs` slow path) now go through one helper:

```python
def _init_kv_receiver(self, decode_req: DecodeRequest, prefill_dp_rank: int) -> None:
    decode_req.req.pd_resolved_prefill_dp_rank = int(prefill_dp_rank)
    decode_req.kv_receiver.init(prefill_dp_rank)
```

so the bound rank cannot drift from what the receiver was actually initialised
with. Fake transfer records 0 because that is the rank it binds to.

**`python/sglang/srt/managers/schedule_batch.py`** - `Req` gains
`pd_resolved_prefill_dp_rank: Optional[int] = None`, and
`build_rebootstrap_payload` prefers it over the client hint:

```python
prefill_dp_rank = self.pd_resolved_prefill_dp_rank
if prefill_dp_rank is None:
    prefill_dp_rank = self.disagg_prefill_dp_rank
if prefill_dp_rank is not None:
    prefill_dp_rank = int(prefill_dp_rank)
...
"routed_dp_rank": prefill_dp_rank,
"disagg_prefill_dp_rank": prefill_dp_rank,
```

Notes on the details:

- `int(...)` because a rank resolved through `query_prefill_dp_ranks` can be a
  numpy integer and the payload is JSON-encoded.
- `disagg_prefill_dp_rank` in the payload gets the same value, so the prefill
  `CommonKVSender` keeps skipping `_register_prefill_dp_rank()` and the
  bootstrap server's `bootstrap_room -> dp_rank` table is left as decode
  expects it.
- The payload shape is unchanged: both keys are still always present and still
  `None` when no rank is known, which keeps the pre-#39357 behaviour for a
  request that was retracted before its rank was ever resolved, instead of
  sending a rank the DP controller would reject.
- The resolved rank is deliberately **not** re-validated against `dp_size`
  before the POST. `TokenizerManager` already rejects an out-of-range
  `routed_dp_rank` (`tokenizer_manager.py:868-877`) with HTTP 400, and
  `CommonKVManager._run_prefill_recompute` already turns any `status_code >= 400`
  into `_fail_prefill_recompute` -> `KVPoll.Failed`, so a bad rank surfaces as a
  clean request failure rather than a silent mis-route. Adding a second check
  here would only duplicate that.

Nothing changes for the configurations that already worked: with
`follow_bootstrap_room` or a client-supplied rank, the resolved rank is the
same value #39357 was already sending.

**Tests** - `test/registered/unit/managers/test_pd_rebootstrap_dp_pinning.py`
(new, registered CPU test, `suite="base-a-test-cpu"`), 10 cases in two classes:

- payload: pins `routed_dp_rank` to the bound rank; the bound rank wins over a
  stale client hint; the client hint is still used when no rank was resolved;
  both keys stay `None` when nothing is known; a numpy rank is coerced to a
  plain `int` and the payload stays `json.dumps`-able; a real `Req` defaults to
  `None` (the payload builder reads the attribute directly, not via `getattr`).
- queue: `_init_kv_receiver` records the rank *and* still calls
  `kv_receiver.init`; the fast path in `add()` records the resolved rank; fake
  transfer is pinned to 0; a request that cannot be resolved yet stays in
  `pending_reqs` with no rank recorded.

Two existing fixtures are updated for the new attribute /helper:
`test_priority_scheduling_disaggregation.py` (`pd_resolved_prefill_dp_rank=None`
on its `_new_req`) and `test_admission_abort_not_enqueued.py`
(`_init_kv_receiver` mock on its queue double).

## Accuracy Tests

Not applicable: routing-only change, no kernel, model forward or sampling code
is touched. The recompute itself is the same request the prefill would have run
either way; only which DP rank runs it changes.

## Speed Tests and Profiling

No steady-state impact: the changed code runs only on the true-retraction
rebootstrap path. The effect it does have is removing a 300 s
`SGLANG_DISAGGREGATION_WAITING_TIMEOUT` stall plus a failed request per
retracted request in the affected configurations.

GPU validation was done on a v0.5.17-based 2P2D PD deployment (prefill and
decode both dp=4) carrying this same change, with true retractions forced on
the decode workers via `SGLANG_TEST_RETRACT=1` / `SGLANG_TEST_RETRACT_INTERVAL=50`.
Without the pin, 53 of 100 recomputes in a run stalled until the KV waiting
timeout and the other 47 landed on the right DP by chance. With it, 1190 of
1194 forced recomputes completed, and for all 1190 the prefill DP rank in the
recompute submission, the DP that actually ran it, and the DP the decode
receiver was bound to were the same. The remaining 4 failed on a
`bootstrap_room` reuse race at the retract instant that is unrelated to the pin.
The port to current `main` is covered by the CPU unit tests below; it has not
been re-run on a GPU against `main`.
