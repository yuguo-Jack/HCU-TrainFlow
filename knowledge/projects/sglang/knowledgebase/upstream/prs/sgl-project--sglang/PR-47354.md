# [Perf] [NVIDIA] glm5: Route small-M BF16 GEMMs to FlashInfer warp split-K with PDL on SM107

[Upstream PR](https://github.com/sgl-project/sglang/pull/47354) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

On SM107 (Vera Rubin NVL72), GLM-5 TP4 decode with EAGLE runs its dense BF16 GEMMs on 1 to 20 tokens per step: o_proj, fused_qkv_a, the DSA indexer's fused wk + weights_proj, and the shared expert's gate_up and down. Today they go to the CuTe DSL TGV kernel, to cuBLAS (for the shared expert and the indexer often a split-K GEMM plus a separate reduce kernel), or, for fused_qkv_a at M <= 16, to SGLang's fused_a JIT kernel. At these sizes each GEMM takes a few microseconds and mostly streams weights, so how much of its start-up overlaps the previous kernel matters as much as the kernel body.

FlashInfer's warp split-K BF16 GEMM, which main already runs for its Muse Spark keys in `_BF16_WARP_SPLITK_TUNED_TACTICS`, launches with PDL (programmatic dependent launch): it starts while the previous kernel is still finishing, issues its weight loads, and waits for the previous kernel only before it reads the activations. With PDL it is faster per call than the current route at all of these shapes; without PDL it is slower than TGV at o_proj (tables below).

This PR, on SM107 only:
- adds 16 GLM-5 TP4 decode keys `(M, N, K)` to the warp split-K table, so these GEMMs take main's existing split-K route (`pdl=True`, FlashInfer's default tactic per key). M = 1, 4, 5, 20 are the draft and verify sizes at batch 1 and 4 with EAGLE 4-1-5 (verify M = 5 x batch);
- moves fused_qkv_a at M = 1, 4, 5 off the fused_a JIT kernel onto that route (q_b_proj keeps fused_a);
- compiles the 16 tactics before CUDA graph capture in `GlmMoeDsaForCausalLM.precompile_kernels_after_loading`, as Qwen4-Exp does for its keys.

Other GPUs, other shapes and the kernel itself are unchanged. Like main's table, the keys match on shape alone, so on SM107 any model whose BF16 GEMMs have exactly these shapes takes the same route. `SGLANG_ENABLE_BF16_SPLITK_GEMM=0` still turns the whole split-K route off, including the fused_qkv_a move.

**Impact**
- **Performance:** AgentX GLM-5.3-NVFP4 TP4 c1 on Vera Rubin NVL72 (low-latency point, EAGLE 4-1-5): per-request decode time per output token **-2.51%** [95% CI -2.80%, -2.16%]; the two base/PR pairs gave -2.54% and -2.47%, A/A noise +/-0.14%. Interactivity (1000 / p90 ITL) +2.6%, within this run's noise (A/A +/-2.5-2.9%); TTFT unchanged within noise. About 1 point of the -2.51% comes from the fused_qkv_a move (estimate, not measured separately: its share of the main-stream per-call savings, weighted by calls per decode cycle).
- **Per call** (decode profile on Vera Rubin NVL72; main stream timed from the previous kernel's end to the GEMM's end, side stream by kernel time): o_proj M=5 5.79 -> 4.93 us, fused_qkv_a M=5 4.51 -> 3.55 us, indexer wk M=5 4.48 -> 2.88 us on the main stream; shared expert gate_up M=5 8.35 -> 4.10 us and down M=5 4.10 -> 2.82 us on the side stream.
- **Accuracy:** GSM8K (sgl-eval, 300 questions, with a superset of these keys) 98.00% -> 98.00%; with `--max-running-requests 1`, so every decode step runs on the new keys, 98.33% -> 98.33%. All 16 keys match an FP32 reference within BF16 tolerance, with PDL on and off.
- **Accuracy (GPQA-Diamond, GB300 proxy):** 90.40% -> 91.92%, paired difference +1.52 points [95% CI -1.52, +4.55], within a 5-point non-inferiority margin set before the run (it rules out gross breakage only; details below).

## Modifications

**+74 / -8 runtime code (3 files), +234 tests (1 file).** No kernel changes.

- `_BF16_SM107_WARP_SPLITK_TUNED_TACTICS` (16 keys) is added to the active warp split-K table when split-K is enabled and `get_platform().device_sm == 107`: `initialize_bf16_gemm_config` rebinds `_active_warp_splitk_tactics` (the base table, or the base table plus these keys on SM107), which `use_bf16_splitk_gemm`, `_bf16_splitk_gemm_out` and `precompile_splitk_tactics` read; neither table is modified (`layers/quantization/unquant.py`). A key was kept only where FlashInfer with PDL beat the current route per call in a decode profile (table below); the indexer's wq_b (no gain at M=5; at M=20 it shares its shape with q_b_proj, which got 12.5% slower) and shared expert down at M=20 (+8.7%) keep their current routes. Each key uses FlashInfer's default tactic: an in-situ sweep over the 88-110 valid tactics per shape, at M = 1 and 5, found none more than 1.5% faster.
- `prefer_bf16_splitk_over_fused_a()` (`unquant.py`) and its call in `DeepseekV2AttentionMLA.prepare_qkv_latent` (`models/deepseek_v2.py`): fused_qkv_a at M = 1, 4, 5 (N=2624, K=6144) runs through the linear layer, and so through the split-K route, instead of the fused_a JIT kernel. It returns False unless the SM107 keys are active, so other GPUs never reach the shape check.
- `precompile_splitk_tactics(keys=...)` takes an optional key subset; `precompile_sm107_splitk_tactics()` compiles only the SM107 keys and is called from `GlmMoeDsaForCausalLM.precompile_kernels_after_loading` (`models/glm4_moe.py`), so GLM does not compile the Muse Spark and GB300 tables.
- `test/registered/unit/layers/quantization/test_unquant_sm107_splitk.py` (CPU): the routing on SM107 vs SM100/SM103, the fused_qkv_a condition, and the `prepare_qkv_latent` call site (Accuracy Tests).

## Speed Tests and Profiling

**Pareto point:** the low-latency end (c1 with EAGLE). The change only touches GEMMs on at most 20 tokens, that is batch <= 4 with EAGLE 4-1-5; larger batches keep their routes. These decode steps are dominated by small, weight-streaming kernels and launch gaps, which is where PDL overlap pays.

**Why AgentX:** the kernel effect depends only on batch shape, so a static workload isolates it (static results below), but the deployment this targets is the AgentX GLM-5 c1 configuration, so the deciding run used AgentX traffic (multi-turn requests with prefix-cache hits and varying context lengths).

**Setup:** one Vera Rubin NVL72 compute tray (4 GPUs), GLM-5.3-NVFP4, TP4, AgentX GLM-5 TP4 c1 configuration: `--bf16-gemm-backend cutedsl`, `--disable-shared-experts-fusion` (so the BF16 shared expert runs as its own GEMMs), EAGLE (4 steps, top-k 1, 5 draft tokens), HiCache, FP8 KV cache, `--max-running-requests 8`, simulated acceptance length 3.33 in both arms (draft tokens are real, acceptance is matched to the recipe's expected length). Base: main 86f72e5; PR: the same main plus an earlier revision of this change with the same 16 keys, tactics and routing. This branch is that revision rebased onto current main and simplified (no override env var; the fused_qkv_a check sits in its caller instead of the fused_a helper); it launches the same kernels and was not re-measured. Order base, PR, PR, base, 900 s each, 125 requests paired across all four runs. Every PR server compiled the 16 tactics before graph capture, and no kernel compiled during serving.

**Known issue (pre-existing, not changed here).** FlashInfer's warp split-K kernel, which main already runs with PDL for the Muse Spark keys, has three synchronization orderings that the PTX memory model does not guarantee (output stores under PDL, the shared-memory stage release, and loader exit with copies in flight). None depends on this PR or showed up in the checks above. Reported in flashinfer-ai/flashinfer#8080, fixed in flashinfer-ai/flashinfer#8081 (outputs bit-identical; per-call cost within about +-1% at most of these shapes).
