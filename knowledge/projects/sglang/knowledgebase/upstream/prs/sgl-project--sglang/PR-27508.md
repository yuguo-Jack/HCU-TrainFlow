# [Feat] speculative: adaptive spec anti-oscillation

[Upstream PR](https://github.com/sgl-project/sglang/pull/27508) · state: open · merged: False

## Original PR description

## Summary

This PR adds a small anti-oscillation guard for adaptive speculative decoding and simplifies the policy:

- add failed-upshift backoff after a failed 3 -> 7 probe
- restrict upshift to the next candidate step
- use one uniform `down_hysteresis` instead of step-specific `down_hysteresis_by_step`
- reduce bs=1 backoff window from 192 to 64 to be closer to throughput-optimal behavior
- add focused unit coverage for ping-pong backoff and uniform down-hysteresis behavior

## E2E Validation

Setup:
- `Qwen/Qwen3.6-27B`, MTP/NEXTN, topk=1
- TP=4 on GPUs 0-3
- default adaptive config vs same config with only `failed_upshift_backoff_window=0`
- each workload ran 3 times; table uses averages

### Anti-oscillation

| config | total switches | 3 -> 7 | 7 -> 3 | avg switches / run |
|---|---:|---:|---:|---:|
| with anti-oscillation | 22 | 11 | 11 | 7.3 |
| no backoff | 94 | 47 | 47 | 31.3 |

Result: anti-oscillation reduces adaptive step switching by about 77%.

### Performance

| workload | with anti-oscillation tok/s | no backoff tok/s | delta |
|---|---:|---:|---:|
| high_c1 | 331.0 | 340.8 | -2.9% |
| high_c8 | 2001.3 | 1962.1 | +2.0% |
| low_c8 | 1554.5 | 1572.4 | -1.1% |
| transition_c8 | 1777.9 | 1790.0 | -0.7% |
| long_low_c4 | 933.7 | 929.9 | +0.4% |

Result: switch churn is much lower. Performance stays close on the mixed suite; the remaining tradeoff is a small hit on pure single-concurrency high-acceptance traffic, where probing 7 more aggressively can help.

Using `assert` statements for runtime configuration validation is discouraged because assertions can be globally disabled in Python when run with optimization flags (e.g., `python -O`). If assertions are disabled, a negative backoff window could be accepted, leading to unexpected behavior. It is safer to raise a `ValueError` instead.

```python
        if self.failed_upshift_backoff_window < 0:
            raise ValueError("failed_upshift_backoff_window must be >= 0")
```

While using boolean subtraction `(target > old_steps) - (target < old_steps)` is a clever way to compute the sign of the difference, it is less readable and can be confusing for other maintainers. Using a standard `if/elif/else` block is much clearer and more maintainable.

```suggestion
        if target > old_steps:
            direction = 1
        elif target < old_steps:
            direction = -1
        else:
            direction = 0
```

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Reset failed-probe tracking after stable windows**

When the controller stays on the higher tier (`direction == 0`), `_last_switch_direction` remains positive indefinitely, so a later downshift after many stable recompute windows is still treated as an immediately failed upshift and starts the full backoff. In workloads that legitimately run at step 7 for a while and then have a brief low-acceptance phase, this blocks re-entering step 7 for 192 policy windows even though the previous upshift was not a failed probe; clear or age `_last_switch_direction` on no-change windows so only an actual immediate upshift→downshift sequence is penalized.
