## Motivation

Backends with one window rail asked for "the window" by the sliding-window role, and the role became a sub-pool name in three places (the chain allocator's id spaces, a fused draft runner's id spaces and `RunnerIds`). A fused draft's window layers routed under the role name "swa" rather than their host sub-pool, so two window hosts would have collided. The Triton backend kept one window's rail in its own metadata fields and every further window in a separate map built by a second builder. This PR resolves the role in one place and builds every window rail the same way.

## Modifications

- Draft window routes: a fused draft runner routes each window layer to its host sub-pool by name, with that sub-pool's window; the runner's router maps the sliding-window role to the window host (the longest when its layers span several), as the target's router maps it to its primary window. The draft runner's window sub-pools are listed, so binding a backend that reads fewer window rails than the runner's layers use is refused, as for the target.
- Role resolution: id spaces are keyed by sub-pool name only; `mem_cache/kv/alloc/runner_ids.py::RunnerIds.sub_pool_name` resolves a role, and `RunnerIds.window_storage` names the sub-pool a one-rail backend reads and writes its window layers through (replacing `window_kv_kind` and `window_kv_sub_pool`). The KV checksum and the decode offload manager take the sub-pool their pool's router names for the role.
- Triton window rails: every window rail is one `WindowRail` in `ForwardMetadata.windows`, keyed by the sub-pool its window layers read (`TritonAttnBackend.window_lengths`), built by one builder (`_window_rails`) in every mode (eager decode, extend incl. the deterministic tile-aligned rail, target verify, draft extend, dLLM extend) and their CUDA-graph buffers. Modes that serve one window still build one rail; unused decode window kv-split counts are removed. Model code that stores window layers itself reads the one rail's write ids through `ForwardMetadata.swa_out_cache_loc`.
- Tests: the fused-draft window metadata test is rebuilt over a real storage plan (FlashInfer, TRT-LLM and aiter read tests now reach their checks); the write-location golden (reads, writes and routes for one and several windows, eager and graphs, deterministic, static pools and a fused draft) is unchanged except the draft layer's route name.

**Behavior change:** a fused draft runner whose window layers span more window sub-pools than its attention backend can read is refused at binding, as the target already was. Reads, writes and window kinds are otherwise unchanged.
