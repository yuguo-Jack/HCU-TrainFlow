# Reject API keys in multi-tokenizer mode where auth is not enforced

[Upstream PR](https://github.com/sgl-project/sglang/pull/29658) · state: open · merged: False

## Original PR description

## Motivation

The API-key auth middleware is only installed in single-tokenizer mode
(`tokenizer_worker_num == 1`, see `launch_server`). When
`--tokenizer-worker-num > 1`, a configured `--admin-api-key` (or `--api-key`)
is never wired into the request path, so admin-tagged management routes become
reachable without credentials. The worker init already rejected `api_key`, but
it did not reject `admin_api_key`, and only failed after startup rather than at
config-validation time.

## Modifications

- `ServerArgs.check_server_args()` now rejects a configured `api_key` /
  `admin_api_key` when `tokenizer_worker_num > 1`, failing fast at startup
  with a clear message (set `tokenizer_worker_num=1` to use API-key auth).
- Added `TestMultiTokenizerApiKeyRejected` covering: admin key rejected,
  normal key rejected, and single-worker + both keys allowed.

No changes to model/kernel/forward code or any inference path.

N/A — this is a startup config-validation change and does not affect model outputs.

`check_server_args()` at launch.

## Code Review

This pull request introduces a validation check to reject API key configurations (`api_key` or `admin_api_key`) when running in multi-tokenizer mode (`tokenizer_worker_num > 1`), as the authentication middleware is only supported in single-tokenizer mode. It also adds corresponding unit tests to verify this behavior. The reviewer suggested using truthiness checks (`not self.api_key` and `not self.admin_api_key`) instead of explicit `None` checks to robustly handle cases where empty strings are passed as arguments.

Runtime confirmation from a full-server PoC (sglang 0.5.21, PyPI, CPU device), in case it helps this get merged:

- Started with `--tokenizer-worker-num 4 --admin-api-key SECRET123` → the server boots normally to /health=200 (no fail-fast), and an **unauthenticated** `POST /flush_cache` (ADMIN_OPTIONAL route) returns **200 "Cache flushed."**; unauthenticated `GET /server_info` also returns 200 with the plaintext key in `launch_command`.
- Control on the same build: single-tokenizer with the same `--admin-api-key` → unauthenticated `POST /flush_cache` returns **401 Unauthorized`, and the same request succeeds with `Bearer SECRET123` — isolating the bypass to the `tokenizer_worker_num == 1` middleware-install condition exactly as described here.

Also worth noting while this is unmerged: in the multi-tokenizer configuration the three hicache endpoints that "check" the admin key pass for any caller, because their check only tests that the config value exists (`if not get_serving().admin_api_key: 403`, http_server.py ~:1111/:1143/:1167), not the request credentials.

Harness (localhost-only, both modes + controls) available on request.

Checking `self.api_key is None` and `self.admin_api_key is None` can cause unexpected assertion failures if these arguments are passed as empty strings (e.g., `--api-key ""` or `--admin-api-key ""`), which are functionally treated as disabled/unset in `auth.py` (using `if api_key:`). \n\nUsing `not self.api_key` and `not self.admin_api_key` is more robust and aligns with how truthiness is checked in the authentication middleware.
