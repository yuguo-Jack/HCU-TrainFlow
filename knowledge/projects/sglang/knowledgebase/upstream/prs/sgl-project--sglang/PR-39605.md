# [Feat] all-reduce: host-staged all-reduce for two GPUs without peer access

[Upstream PR](https://github.com/sgl-project/sglang/pull/39605) · state: open · merged: False

## Original PR description

**Problem.** On consumer cards (no NVLink, no PCIe P2P — `nvidia-smi topo`
says `SYS`, `--disable-custom-all-reduce` is required) NCCL uses its SHM
transport. Its kernels read host memory over PCIe a cache line at a time:
on two RTX 5070 Ti (PCIe 4.0 x16, 26 GB/s per direction measured) a
20 MB all-reduce — `[2048, 5120]` bf16, one TP=2 prefill chunk — takes
10.9 ms, 1.9 GB/s, under `NCCL_PROTO=LL`, `Simple` and `LL128` alike.
A 2048-token prefill chunk of a 64-layer model does 128 of them: 733 ms of
an 802 ms step in the torch profiler. `NCCL_SHM_USE_CUDA_MEMCPY=1` brings
the 20 MB case to 12.5 GB/s but doubles the latency of the 10 KB decode
all-reduces (39 -> 81 µs, 130 per token), so it costs decode.

**Change.** An opt-in communicator (`SGLANG_HOST_STAGED_ALLREDUCE=1`) for
messages of at least `SGLANG_HOST_STAGED_ALLREDUCE_MIN_BYTES` (1 MiB)
outside CUDA-graph capture; smaller messages and captured graphs keep the
existing path, so decode is untouched. Two ranks share a `/dev/shm` file
(rank 0 names it, the gloo group carries the name at init), registered
Portable|Mapped. Each rank DMAs its input into its region in 4 MB pieces on
a D2H stream and publishes a monotonic piece counter with
`cuStreamWriteValue32`; the peer's H2D stream `cuStreamWaitValue32`s on
that counter, DMAs each piece back as it lands and adds once at the end.
Slots are double-buffered with a "read back" counter guarding reuse. The
CPU never blocks (an earlier host-synchronising version lost 1-3 ms per
all-reduce to the exposed kernel-launch time of the next layer). The sum
is `a + b` on both ranks, so the result is bit-identical to NCCL's.

**Numbers** (dual RTX 5070 Ti, EPYC host):

| message | NCCL SHM | this |
|---|---:|---:|
| 20.97 MB | 10 859 µs | 1 494 µs |
| 12.90 MB | — | 946 µs |
| 1.31 MB | — | 142 µs |
| 62.9 MB | — | 4 385 µs |

Qwen3.8-27B (dense, ModelOpt NVFP4, TP=2, `--attention-backend triton`):
3308-token prompt TTFT 2.55 s -> 0.56 s, 8169 tokens 6.36 s -> 1.10 s,
2174 tokens 1.73 s -> 0.51 s; decode 67 tok/s unchanged; the 3308-token
greedy answer byte-identical before and after. On a KT hybrid MoE
(Qwen3.8-Flash-Next) it removes 0.5 s per 2048-token chunk.

**Scope.** `world_size == 2` only (the layout generalises, the sum does
not); CUDA only; env-gated. `test/manual/test_host_staged_allreduce.py`
(torchrun, 2 GPUs) checks bit-exactness against NCCL for the prefill
shapes, the size threshold and the capture guard, and prints the 20 MB
timing.

**Not this PR.** Making it the default when P2P is absent, a server arg
instead of the env, and >2 ranks.

- 05yuki · comment · 2026-09-25T04:54:38Z · [source](https://github.com/sgl-project/sglang/pull/39605#issuecomment-5826973147)

Pushed a second commit that covers the other half of the same problem: decode-sized all-reduces.

The host-staged path deliberately leaves messages under 1 MiB and CUDA-graph captures alone, so decode on these two cards still goes through NCCL's SHM transport. For a 4096-element bf16 all-reduce that is 22–25 µs per call inside a graph (~41 µs eager), and a decode step makes dozens of them (88 on a 43-layer MoE).

`SGLANG_LL_ALLREDUCE=1` adds a one-kernel path for bf16 messages up to `SGLANG_LL_ALLREDUCE_MAX_BYTES` (64 KiB, decode up to batch 8). Each rank writes its vector into pinned host memory that both GPUs map, in NCCL's LL form: every 8-byte store carries two bf16 values plus the call's sequence number, so data and flag land together. It then spins on the peer's words until they carry the same number and adds. No copy engine, no CPU thread, and it is capturable in a CUDA graph. The two size ranges don't overlap, so the host-staged path is untouched.

Two things that went wrong on the way, noted in the kernel: a separate flag word raced ahead of its data over PCIe (hence LL), and a non-volatile load in the spin got hoisted out of the loop.

`test/manual/test_ll_allreduce.py` (two GPUs, `torchrun --nproc_per_node=2`):
- bit-exact against `dist.all_reduce` at 2048 / 4096 / 7168 / 8×4096 elements
- routing: fp32, odd length and > 64 KiB go elsewhere
- 88 calls captured in one CUDA graph and replayed three times, bit-exact
- timing: `4096 x bf16 all-reduce: LL 6.5 us, NCCL 41.5 us` (eager)

End-to-end decode on the same two cards (graphs on, TP=2): Qwen3.5-35B-A3B 64.7 → 71.0 tok/s (+10%), a DeepSeek-V4-Flash vision variant +4–6%, and ±0 on a model whose decode is bound elsewhere.

Happy to split this into its own PR if you'd rather review the two separately.


- 05yuki · comment · 2026-09-26T12:57:36Z · [source](https://github.com/sgl-project/sglang/pull/39605#issuecomment-5846455591)

Pushed a fix for a race in the host-staged path (904dea8).

`all_reduce` added the peer's pieces into `src` in place on the h2d stream after waiting only for the peer's counter, not for this rank's own D2H copies of `src`, and the caller waited on h2d only. When the peer's counter arrived first, the peer DMA'd a half-summed input, and the caller's next kernels could also overwrite `src` while it was still being copied. The result was wrong sums that differ from run to run.

It showed up on our two RTX 5070 Ti (no P2P) as served input logprobs that were not reproducible between identical requests once a prompt crossed the 1 MiB threshold (224+ tokens at hidden 2560): median |Δ logprob| 0.1 nat, max 2–5 nat, while 20–192-token prompts were bit-identical. With the fix, 224–320-token prompts are bit-identical too.

The fix makes h2d wait for d2h before the add; the copies still overlap. The new manual test `test_own_copy_lags_peer` holds rank 0's D2H stream back with a sleep kernel and compares against NCCL: it fails on the previous commit and passes now. The 20 MB all-reduce time is unchanged (1504 vs 1506 µs).
