# [Fix] replay_ssm: Reject unflushed ReplaySSM cache checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/43749) · state: open · merged: False

## Original PR description

## Motivation

ReplaySSM updates the convolution state every decode step but only folds pending updates into the temporal state on a ring flush. When a request finished mid-ring, the cache shortened its key to the last flush boundary and donated the live slot. The convolution state still represented the longer prefix, so a later cache hit could change the next-token distribution.

For example, with a 16-step ring and no speculative decoding, generating 24 tokens and then continuing the same token IDs produces warm/cold KL of 0.0871 / 0.0551 for the count/story cases.

## Modifications

- Decline finished ReplaySSM checkpoint donation while the ring has pending updates. Existing component cleanup releases the slot and KV normally; safe prompt checkpoints remain reusable.
- Preserve fully flushed checkpoint donation and update its pool documentation.
- Add full-vocabulary warm/cold KL coverage for mid-ring and fully flushed finishes, plus normal/int8 resource-lifecycle coverage. Share the existing KL request/distribution helpers without changing the lazy regression configuration.

This is independent of #43387: it reproduces without speculative decoding and changes the cache component rather than the speculative finish guard.

## Accuracy Tests

GB300, Qwen/Qwen3.5-0.8B revision `2fc06364715b967f1860aea9cf38778875588b17`, `no_buffer`, ReplaySSM ring length 16, greedy decoding. Each warm/cold pair uses identical probe token IDs and the full vocabulary; threshold is KL < 0.005.

| Case | Before | After |
| --- | ---: | ---: |
| count, 24 tokens (partial ring) | 0.0871493503 | 0.0000268408 |
| story, 24 tokens (partial ring) | 0.0550937731 | 0.0006480758 |
| count, 33 tokens (fully flushed) | 0.0012804768 | 0.0012804768 |
| story, 33 tokens (fully flushed) | 0.0014460154 | 0.0014460154 |

The same regression ran three times on each version: all six pre-fix partial-ring cases failed the KL assertion, all six pre-fix flushed controls passed, and all twelve fixed cases passed. A fresh fixed server launch passed all four cases again. No runtime errors occurred in these comparison runs.

Targeted unit tests verify cache contents and KV/active/checkpoint slot accounting for pending vs. fully flushed rings with normal and int8 checkpoint storage. The two pending-ring subcases fail before the fix; all three related test methods pass after it on both CPU and GPU.

The existing lazy in-place KL regression also passes after sharing the helpers (KL = 0, cached prefix = 128 tokens).

Reproduction:

```bash
python test/registered/radix_cache/test_mamba_cache_kl.py TestMambaReplaySSMFinishedKL
python test/registered/unit/mem_cache/test_unified_radix_cache_unittest.py TestMambaReplaySSMFinishedCheckpoint TestMambaFinishedOvershootCheckpoint TestUnifiedRadixCacheInt8MambaCheckpoint
```

## Speed Tests and Profiling

No throughput benchmark. The fix reads the same cursor as before and adds no kernel or synchronization point. Mid-ring finishes retain less generated-prefix cache; fully flushed and existing prompt checkpoints remain reusable.
