# [Test] [AMD] diffusion: Skip the Kandinsky6 FA dispatch test on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/44421) · state: open · merged: False

## Original PR description

## What

`test_kandinsky6_bf16_dtype.py::test_attention_backend_dispatch_and_repeated_forward[*-FA]` (added in #42743) fails on the scheduled AMD run (`multimodal-gen-test-1-gpu-amd`). Test-only fix, no runtime changes.

Failing run: https://github.com/sgl-project/sglang/actions/runs/38563492873/job/115850314797

## Why

On ROCm the FA backend resolves to Torch SDPA (FA3 is CUDA-only, and `flash_attn` is not in the image), so the "must not silently fall back" assert fails. The test already skips FA on SM12.x for the same reason; this adds the same skip for ROCm.

This PR originally also fixed `test_server_args.py::test_fasth3_selects_vsa_h3_for_the_transformer` on ROCm. Main has since fixed that upstream (the shared CUDA mock now pins `is_rocm`), so the merge with main takes main's version of that file.

## Test plan

- MI300: the FA cases skip and the TORCH_SDPA cases pass ([job](https://github.com/sgl-project/sglang/actions/runs/38755083928/job/116491534135)).
- CUDA: the multimodal unit suite passes ([job](https://github.com/sgl-project/sglang/actions/runs/38820876644/job/116731184729)).

- stayinalive181 · comment · 2026-10-15T17:12:29Z · [source](https://github.com/sgl-project/sglang/pull/44421#issuecomment-6197884956)

Some MI355X data in support of keeping `aiter` as FastH3's transformer default on ROCm. Setup: `lmsysorg/sglang-rocm:v0.5.21-rocm10-mi35x-20261014`, 1× MI355X.

- **The kernel itself works on gfx950.** The in-tree VSA-H3 Triton forward passes `test_vsa_h3_attention.py` (12 passed).
- **It is slower than dense aiter at 10% block density.**

  | Tokens (24 heads, head 128) | VSA-H3 Triton | Dense aiter |
  | --- | ---: | ---: |
  | 64k | 69.4 ms | 42.5 ms |
  | 32k | 17.6 ms | 10.6 ms |

  The VSA-H3 numbers use `num_stages=2, waves_per_eu=2, matrix_instr_nonkdim=16`. The pinned Hopper/Blackwell launch (`num_warps=4, num_stages=5`) is slower still, at 91.3 ms for 64k.
- **End to end it would need more work.** Routing `video_sparse_attn_h3` on ROCm stops in `flash_attention_v3.flash_attn_varlen_func` with `No module named 'flash_attn'`.
- **The aiter default works.** FastH3 V2 t2va at 1344×768, 5 s, 8 steps takes 34.8 s on one MI355X.

So the CUDA-only VSA-H3 default looks like the right call for ROCm today.
