# [AMD] Keep the FP4 varctx schedule test off AITER's 2048-row compile

[Upstream PR](https://github.com/sgl-project/sglang/pull/41793) · state: closed · merged: True

## Original PR description

## Motivation

The scheduled [PR Test (AMD) run 36568058787](https://github.com/sgl-project/sglang/actions/runs/36568058787) on `main` included #40546 and #41464. In it, `stage-b-test-1-gpu-small-amd-mi35x (rocm10, linux-mi35x-gpu-1)` passed 46 of 49 files, then hit the 30-minute `Run test` step timeout ([job log](https://github.com/sgl-project/sglang/actions/runs/36568058787/job/109404903720)).

Most of the overrun came from `test_fp4_indexer_hip.py`, which took 578s against an estimate of 60s. 551s of that was spent in one case, `test_decode_schedule_matches_aiter_varctx_schedule[1536]`. With 1536 rows, AITER's `compute_varctx_schedule` reference launches `_varctx_cta_info_kernel` with `BLOCK_B = next_power_of_2(1536) = 2048`. The kernel holds a `[256, 2048]` tile and unrolls a 32-step search over the 2048-row vector. On the ROCm 10 image that Triton compile is very slow. On the rocm720 and rocm724 lanes of [run 36606581500](https://github.com/sgl-project/sglang/actions/runs/36606581500), the whole file takes 40s.

## Modifications

`test_decode_schedule_matches_aiter_varctx_schedule` now uses 200 rows instead of 1536, and monkeypatches `_DECODE_ROW_BLOCK` from 1024 to 64 for the test. The test still covers what the large case was there for:
- The in-tree prep kernel carries prefix sums across four row blocks, and the last block is partial (200 = 3×64 + 8).
- `_decode_cta_count(200, 65536)` is 1024, so the cta_info kernel still spans four 256-slot programs.
- Every 7th row still has zero length.

AITER's reference tile drops to `[256, 256]`. The production code is unchanged.

## CI results

`test_fp4_indexer_hip.py` passes in **36s**, against the 60s estimate and the 578s that caused the timeout: [`stage-b-test-1-gpu-small-amd-mi35x` part 0 of run 38208231513](https://github.com/sgl-project/sglang/actions/runs/38208231513/job/114676475958).

That run is a `workflow_dispatch` of this stage on the PR head with `continue_on_error`, because on a normal PR run the part stops at its first failing file and never reaches this one. `test_fp4_indexer_hip.py` is file 10 of 29 in part 0, behind `e2e/quantization/test_quark_mxfp4.py` (file 1) and `kernels/ops/attention/test_fused_kda_conv_recurrent_verify.py` (file 5), both of which fail on `main`.

With the parts run to completion, each fails on exactly one file, and both also fail on `main` ([run 38189648453](https://github.com/sgl-project/sglang/actions/runs/38189648453)):

| 1 | 30/31 | `kernels/ops/attention/dsv4/test_compact_attention_hip.py` |

The other red lanes on this PR are pre-existing on `main` as well: `attention/test_kda_kernels.py` in `stage-b-test-1-gpu-large-amd (…, 2)` and `observability/test_tracing.py` in `stage-b-test-1-gpu-small-amd (…, 12)`. On the NVIDIA side, `base-b-test-1-gpu-large (0)` fails `e2e/radix_cache/test_mamba_extra_buffer_spec_grammar.py`; every other red `base-b` job is a fail-fast skip off it and ran no test. The `PR Test (Xeon)` parts failed before running anything, on a runner storage fault (`failed to export layer`, `no space left on device`). The `PR Test Extra` checks are red only because this PR carries `run-ci` without `run-ci-extra`.
