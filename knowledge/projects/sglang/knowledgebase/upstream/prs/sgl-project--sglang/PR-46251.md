# [Perf] sgl-router: Encode tiktoken models with fastokens under --tokenizer-backend fast

[Upstream PR](https://github.com/sgl-project/sglang/pull/46251) · state: closed · merged: True

## Original PR description

## Motivation

`--tokenizer-backend fast` only applied to a `tokenizer.json`. A `tiktoken.model` (Kimi-K3) silently stayed on tiktoken-rs, which runs at about the speed of Python tiktoken: 8 to 9 MB/s per core, so a 128k-char K3 prompt costs about 15 ms of router CPU on the TTFT path. dynamo-tokenizers 3.1.0 already ships `FastTikTokenTokenizer`, which loads the same ranks, BPE pattern and special tokens from the same `tiktoken.model`, `config.json` and `tokenizer_config.json`.

fastokens encodes exactly one input differently from the engine: U+017F (long s) directly after an apostrophe. tiktoken's `(?i:'s)` case-folds `'ſ` into the contraction and keeps ` I'ſ` as one pretoken; the fastokens scanner ends the word before the apostrophe. A sweep of every BMP codepoint through nine apostrophe and contraction contexts (571,104 inputs) against tiktoken-rs and Moonshot's `tokenization_kimi.py` found no other divergence, and the 135-case corpus below (chat, code, tool JSON, Chinese, 32k to 512k-char prompts, 60k-char base64 runs crossing the 25k split, markers typed by users) matched id for id.

## Modifications

- `adapter.rs`: for a non-json tokenizer path under `fast`, build `FastTikTokenTokenizer` and keep the tiktoken-rs tokenizer. A small wrapper routes any input whose bytes contain `C5 BF` (U+017F) to tiktoken-rs and everything else to fastokens, for both plain and segmented encodes. Load failure falls back to tiktoken-rs with a warning, as the json path does with HF.
- `stats.rs`: new `fast_tiktoken` encode backend label for the startup log.
- `REFERENCE.md`: document the tiktoken case for `--tokenizer-backend fast` and mention it in the Kimi-K3 section.
- `tests/component/tokenizer/kimi.rs`: the Kimi parity fixtures now run under both `hf` and `fast`. A second test builds a vocabulary with a merge across an apostrophe and checks that the `fast` backend matches tiktoken-rs on `'ſ` while bare fastokens does not, so the fallback can be dropped once fastokens folds the contraction.

The L1 prefix cache is unaffected: it is never built for a `.model` path (no boundary tokens are read from it), and Kimi-K3 encodes per segment anyway.

## Accuracy Tests

`cargo test -p sgl-router kimi` and `cargo test -p sgl-router --lib tokenizer::` pass; clippy with `-D warnings` is clean. On the real `moonshotai/Kimi-K3` vocabulary (revision f831ab66), the guarded fast backend produced 0 id mismatches against tiktoken-rs and the Python reference on the 135-case corpus and on the 571,104-input codepoint sweep.

## Speed Tests and Profiling

Measured on an m7i.8xlarge (Xeon 8488C), Kimi-K3 vocabulary, each stack in its own process. Per-request latency pinned to one core, first encode of each input (cold caches):

| input | tiktoken-rs (before) | fast (this PR) |
|---|---|---|
| short chat, ~190 chars | 35 us | ~4 us |
| medium chat, ~2k chars | 315 us | ~26 us |
| Python file, ~20k chars | 2.42 ms | ~150 us |
| 128k-char prompt | 15.4 ms | ~0.9 ms |
| 512k-char prompt | 61 ms | ~2.6 ms |

Aggregate encode throughput, all cores busy: 134 Mchars/s before, 2742 Mchars/s after (32 threads); 7.9 vs 185 Mchars/s on one core. Steady-state RSS after traffic: 69 MB before, about 340 MB after, of which the retained tiktoken-rs fallback is about 30 MB. Load time 60 ms before, about 0.8 s after.
