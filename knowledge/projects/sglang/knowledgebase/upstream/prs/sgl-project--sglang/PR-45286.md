# [Fix] marlin_moe: Load grouped zero points at group boundaries

[Upstream PR](https://github.com/sgl-project/sglang/pull/45286) · state: open · merged: False

## Original PR description

## Motivation

While reproducing #44999 with a synthetic two-layer checkpoint generated from the reporter's probec reproducer on an RTX 3090, the first Marlin MoE GEMM intermittently produced incorrect AWQ results with correct inputs and routing metadata.

When a quantization group spans multiple K tiles, the kernel reloads its zero point from shared memory for each tile. A slower warp's redundant read can overlap the next asynchronous copy into that shared slot. For the observed group128/K64 configuration, this can substitute group g+2's zero point while retaining group g's scale. The resulting offsets match the captured incorrect outputs, including 384 and 416.

## Modifications

- Read grouped zero points into registers only at group boundaries, matching the existing scale-load cadence. Keep the group's raw zero point in registers for its remaining tiles. Apply the same condition to both grouped zero-point load branches.
- Add a BF16/FP16 integer-zero-point property test through the public repack, alignment and GEMM operators: group-dependent affine offsets representing a zero matrix must still produce exactly zero, including when the output buffer initially contains NaNs.

All engine requests completed with exactly 256 output tokens. The checkpoint, inputs, engine options and sampling options were identical between the two engine runs. These model-level results use the locally generated synthetic checkpoint ([probec](https://github.com/DiaaAj/probec), commit `d7cfa22752bcf705ba128d77fb888f5ae20042cf`).

```
python -m pytest -q test/registered/kernels/ops/moe/test_moe_wna16_marlin.py \
  -k 'moe_wna16_marlin_gemm or groupwise_zero_point_translation' -rA
```

On the patched checkout: **2 passed, 24 skipped, 11 deselected**. The 24 existing JIT/AOT comparisons were skipped because this environment's sglang-kernel does not expose the AOT MoE GEMM operator. The new tests run independently of AOT availability.

Supplemental validation replayed all 24 original configurations, retaining their input generation, routing and call flags, against CPU Float64 matrix multiplication of the test helper's dequantized weights, rounded to the output dtype. **24/24 passed**. The predeclared gates were relative MAE < 0.04 and elementwise absolute error <= 0.05, following existing numerical-test conventions. Observed maximum absolute errors were 0.000244140625 for FP16 and 0.0009765625 for BF16; the largest relative MAE was 0.000213345. This was separate numerical validation; the original AOT comparisons remain skipped.

The added case is an exact arithmetic property test; it does not force a particular tile configuration or race interleaving. The intermittent failure was checked separately using the bounded replays above. GPU tests cover integer zero points; the floating-zero-point branch is not currently instantiated by the JIT dispatcher.
