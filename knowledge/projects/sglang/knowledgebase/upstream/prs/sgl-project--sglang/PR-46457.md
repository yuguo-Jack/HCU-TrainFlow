## Original PR description

# [Perf] paged-experts: fuse slot lookup into decide

## Motivation

This PR aims to increase decode tok/s.

Currently, Paged Experts (#42557) runs 21 graph nodes per paged MoE layer in captured decode. 11 of them are small torch ops that turn the decide kernel's result into the runner's inputs: index the slot of each routed entry, mask padding, mask its weight. On Qwen3-30B-A3B-GPTQ-Int4 at batch size 1 they take 0.44 ms per step, about 9% of decode.

The decide kernel already knows each routed expert's slot when its eviction loop ends. This PR has it write the runner's inputs directly: the slot and router weight of each routed entry, with slot 0 and weight 0 for padding. The layer's paged part of the graph is then decide plus gather, **10 nodes instead of 21**, and the runner reads its inputs straight from the decide kernel's output.

## Modifications

`paged_experts.cuh`, `paged_experts.py`, `executor.py`:
- After its eviction loop, the decide kernel also writes each routed entry's slot and router weight. Padding entries, and ids outside `[0, E)`, get slot 0 and weight 0.
- The device executor passes these straight to the base method. A paged layer's part of the captured step is now decide plus gather: 10 nodes instead of 21.
- Router weights are passed to the kernel as float32. If they come in another dtype, they are converted back, which is exact.
- `paged_experts_decide` gains `topk_weights`, `run_ids` and `run_w`; it has no other callers. The host-planned (eager) path is unchanged.

## Accuracy Tests

**Kernel test.** Over 200 random routing steps with padding, the decide kernel's runner inputs equal the reference: each entry's slot from the LRU reference, and its weight, with 0 for padding. Ids outside `[0, E)` count as padding.

**Paged vs unpaged, 4-layer test models** (E=32, top-4, K=8; prompt and greedy decode logprobs; RTX 5070 Ti; main 2d3de82633 and this PR in one run):

| model | runner | this PR | main |
|---|---|---|---|
| Qwen3-MoE bf16 | triton | identical | identical |
| AWQ int4 | Marlin | decode max 0.014 | decode max 0.014 |
| compressed-tensors NVFP4 | Marlin | median max 0.076, unpaged floor 0.055 | median max 0.059, unpaged floor 0.063 |

Marlin is not run-to-run reproducible, so the Marlin formats are judged against the spread of two unpaged servers (the floor); bf16 on triton is bit-identical. Each check has a negative control that must fail (a perturbed RMSNorm eps on bf16 and AWQ, unnormalized top-k weights on NVFP4), and all three do.

**GSM8K (200 questions), Qwen3-30B-A3B-GPTQ-Int4, K=92:** main 0.950 / 0.935, this PR 0.945.

## Speed Tests and Profiling

Same machine as #42557: RTX 5070 Ti 16 GB (PCIe 5.0 x16, 62 GB RAM), Qwen3-30B-A3B, 10,240 KV tokens and 4 slots, prefix caching off, 16 ShareGPT warm-up requests discarded. Decode tok/s is `1000 / median TPOT` over 8 ShareGPT prompts sent one at a time (256 output tokens each); TTFT and ITL are from the same requests. 4 requests: 16 ShareGPT prompts from 4 clients at once (output tok/s). 2k TTFT: 4 natural ~2,048-token prompts. main (upstream 2d3de82633) is measured first and last in the same run as this PR; both values are shown, and a difference inside their spread is no difference.

| config | decode tok/s | TTFT p50 / p99 | ITL p50 / p99 | 4 requests: out tok/s | 2k TTFT p50 | peak VRAM |

| int4, K=92: this PR | **234.1** (+10.3%) | 50 / 82 ms | **4.27 / 4.90 ms** | **418** (+4.2%) | 248 ms | 14.7 GiB |
| FP8, K=40: main | 90.3 / 90.3 | 213 / 301, 218 / 301 ms | 10.51 / 20.74, 10.51 / 20.76 ms | 100 / 99 | 427 / 424 ms | 13.4 GiB |
| FP8, K=40: this PR | **94.2** (+4.3%) | 219 / 300 ms | **10.04 / 20.26 ms** | 101 | 425 ms | 13.4 GiB |
