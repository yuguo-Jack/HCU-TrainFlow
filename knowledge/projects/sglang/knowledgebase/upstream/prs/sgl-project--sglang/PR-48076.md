# [Feat] scheduler: Add the UniBoost schedule policy

[Upstream PR](https://github.com/sgl-project/sglang/pull/48076) · state: open · merged: False

## Original PR description

## Motivation

UniBoost (*Beyond Prediction: Tail-Aware Scheduling for LLM Inference*, ICML 2026, [project page](https://yl3469.github.io/uniboost-icml26/#cite), [arXiv:2606.18431](https://arxiv.org/abs/2606.18431)) is a prediction-free, tail-aware schedule policy. A waiting request `r` is served in ascending

```
phi(r) = A(r) - b_gamma(q(u(r)))      b_gamma(w) = -ln(1 - exp(-gamma * w)) / gamma
```

where `A(r)` is its arrival stamp, `u(r)` its uncached prefill work and `q()` a geometric quantization at bin size `k`. Small work gets a large boost and large work almost none, and no boost exceeds `b_gamma(k)`. So a newcomer can only overtake requests that arrived less than `b_gamma(k)` earlier: large `gamma` converges to FCFS, small `gamma` to shortest-uncached-work-first, and every request's wait has a bound.

The existing policies sit at the two ends. `fcfs` bounds waits but ignores work; `lpm` and `shortest-prefill-first` favor cheap requests with no starvation bound; `hrrn` ages by waited tokens. UniBoost interpolates between them with one knob and an explicit bound.

This PR adds the policy as `--schedule-policy uniboost` with a fixed `gamma`. The follow-ups below add the paper's adaptive gamma and two serving-side extensions.

**UniBoost series** (each PR builds on the previous one; review in order):
1. #48076: the policy (`--schedule-policy uniboost`)
2. #48077: adaptive gamma from the response-time tail
3. #48078: bounded waits for requests that share a prefix
4. #48079: decode time-slicing for first-token-starved waiters

All four target `main`, so #48077 to #48079 also carry the commits of the PRs before them; each PR's own change is its last commit.

## Modifications

- `managers/uniboost.py` (new): the boost `b_gamma` (paper Eq. 2), the geometric bin `q` (Eq. 8), uncached work `u(r)` (input plus generated tokens minus the matched prefix), and the queue sort.
  - **Clock** (`--uniboost-clock`): `tokens` (the paper's clock: prefill tokens processed by this scheduler) or `wall` (arrival in seconds, with work converted to seconds at the measured prefill token rate, an EMA in `TokenClockRate`). Under `wall`, `gamma` is in 1/s and its meaning does not drift with the cache hit rate.
  - Arrival stamps are taken the first time the policy sees a request and survive retraction, so a retracted request keeps its seniority.
  - Sort key: priority first when `--enable-priority-scheduling` is on, then `phi`. In-batch prefix-dedup followers sort last, as under the other cache-aware policies. Ties break on `A(r)`, then rid.
- `managers/schedule_policy.py`: `CacheAwarePolicy.UNIBOOST`, dispatched from `calc_priority`.
  - Without a prefix cache it falls back to `fcfs` with a warning, like the other cache-aware policies.
  - It keeps its order on long queues, whereas `lpm` and `hrrn` switch to `fcfs` above 128 waiting requests: a bounded wait that disappears under load would defeat the policy.
- `managers/scheduler.py`: passes the knobs to `SchedulePolicy`.
- `managers/schedule_batch.py`: two `Req` fields for the arrival stamps.
- `arg_groups/`: `--uniboost-gamma` (unset means 1e-4 per token, or 0.1 1/s under `wall`), `--uniboost-bin-size` (256) and `--uniboost-clock` (`tokens`), with validation. `uniboost` is allowed with `--enable-priority-scheduling`.
- `docs/.../server_arguments.mdx`: the new choice and flags.

## Accuracy Tests

The policy only changes the order in which waiting requests are admitted. Model forward, KV cache contents and sampling are untouched, so each request's output is unchanged.

No GPU accuracy run on main yet. The KV path this series touches is limited to #48079 (released decodes are checkpointed and resume from the radix cache); a gsm8k check with forced releases can be added on request.

The uniboost row is the complete series (#48076 to #48079) in the configuration `--schedule-policy uniboost --uniboost-bin-size 256 --uniboost-clock wall --uniboost-adaptive-gamma --uniboost-adaptive-max-jump-s 50 --uniboost-preempt-wait-s 30 --uniboost-preempt-quantum-tokens 512 --uniboost-preempt-max-per-req 2`. It was measured on a port of this series to sglang v0.5.21 (flag prefix `--boost-` there; the policy logic is the same). Two things in that build are not part of this series: a 60 s cap on how long an in-batch prefix-dedup follower is held back (`--in-batch-prefix-caching-max-pin-s 60`, applied to lpm, hrrn and uniboost), and a guard that re-queued a prefill batch whose KV allocation failed (it fired 3 times in the uniboost run and never in the others; see the note in #48079).
