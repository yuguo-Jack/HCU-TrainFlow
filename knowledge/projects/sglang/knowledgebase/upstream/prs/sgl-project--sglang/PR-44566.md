# [Perf] [AMD] Qwen3-Next: consume the fused AR+norm+quant output

[Upstream PR](https://github.com/sgl-project/sglang/pull/44566) · state: open · merged: False

## Original PR description

# [AMD] Qwen3-Next: consume the fused AR+norm+quant output

**Depends on #39140** (the Gluon kernel) and **#44565** (the FFN-side wiring).
It targets `main` independently rather than stacking: until those land the
declarations here are inert rather than harmful — the attention side falls
through to the existing aiter path and the FFN read is ignored.

Last of three. This is the PR that changes behaviour for a model, and the only
one with end-to-end numbers.

## What this does

Declares the quantized read on the Qwen3-Next decoder layers so the boundary
hands down `(bf16, fp8, scale)` instead of a tensor, and routes the pieces to
the consumers that can take them:

* `declare_attn(read=NormQuantReadout(...))` on both decoder layers —
  `Fp8Input.TUPLE_AND_BF16` for the GDN layer, whose small `in_proj_ba` gating
  projection needs bf16 alongside the quantized `in_proj_qkvz`, and
  `Fp8Input.TUPLE` for the attention layer.
* `_forward_input_proj` and the `qkv_proj` sites unpack the tuple, giving each
  linear the member it can consume.
* `Qwen3NextSparseMoeBlock` routes the MLP side, keeping `qwen2_moe.py` —
  shared by several models — byte-identical to upstream.

Every declaration is conditional on the consuming projection actually accepting
an FP8 tuple, so a build whose projections are not block-quantized keeps the
plain AR+RMSNorm path.

## The FFN read is not installed unconditionally

`declare_ffn` defaults to `NORM_READOUT`, and `NormQuantReadout` is not a
drop-in substitute: on an empty batch `NormReadout` keeps the previous residual
while `NormQuantReadout` returns `hidden_states` as the residual. `_ffn_read()`
therefore returns `NORM_READOUT` unless `_use_aiter` is set **and** the MoE
block can consume an `(fp8, scale)` pair, so no other backend sees a changed
declaration.

The attention side needs no equivalent: `declare_attn` already defaults to
`NORM_QUANT_READOUT`, the same type, so `fp8_input=None` there is the default.

## Scope

The kernel serves `M ∈ {1, 2, 4, 8, 16}` at hidden 2048, TP4, eps 1e-6, on
gfx950 with `SGLANG_USE_AITER`. Above M=16, aiter's
`allreduce_fusion_kernel_1stage_per_group` is as fast or faster, so
`is_supported()` declines and the existing path serves the shape. Anything
outside the envelope — other architectures, other TP sizes, CUDA — is
unaffected.

## Results

4× MI355X (gfx950), TP4/EP1, `Qwen3-Next-80B-A3B-Instruct-FP8`, ISL/OSL
1024/1024, un-profiled, shared-expert fusion at its default (on). Baseline is
the same commit with none of these three PRs applied. Output tok/s:

| C ≈ decode batch | stock | this PR | |
|---|---|---|---|
| 1 | 227.5 | 235.4 | **+3.5%** |
| 2 | 434.7 | 446.3 | **+2.7%** |
| 4 | 843.7 | 869.2 | **+3.0%** |
| 8 | 1641.0 | 1682.6 | **+2.5%** |
| 16 | 2989.9 | 3077.7 | **+2.9%** |
| 32 | 4769.5 | 4822.0 | **+1.1%** |
| 64 | 7327.0 | 7508.3 | **+2.5%** |

GSM8K 1319q: **0.946**, `Invalid: 0.000`, against 0.948 for stock — within
run-to-run spread (readings across arms ranged 0.941–0.948).

The two PRs below this one are measured as no-ops on the same hardware: the
kernel alone is within ±0.1% of stock at every concurrency, and the wiring
within ±0.5%. The gain appears only when a model declares the read, which is
what this PR does.

Measured with #42483 cherry-picked, because Qwen3-Next does not currently start
on `main` without it; this branch does not carry that commit.

## Test plan

* GSM8K 1319q against stock at the same commit.
* Output-throughput sweep at C = 1, 2, 4, 8, 16, 32, 64.
* Kernel-vs-aiter isolation arm, to attribute the delta between the kernel and
  the declarations.

## Hardware

gfx950 (MI355X), TP4, `SGLANG_USE_AITER=1`.
