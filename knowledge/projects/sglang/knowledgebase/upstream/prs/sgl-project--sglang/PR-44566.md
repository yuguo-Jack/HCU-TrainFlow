# [Perf] [AMD] Qwen3-Next: consume the fused AR+norm+quant output

[Upstream PR](https://github.com/sgl-project/sglang/pull/44566) · state: open · merged: False

## Original PR description

On gfx950 with TP4, Qwen3-Next runs its attention-input all-reduce + RMSNorm and then a separate per-group FP8 quant for its FP8 projections, because the model never declares a quantized read. The fused all-reduce + RMSNorm + quant path exists, and with #39140 and #44565 it reaches a faster Gluon kernel on this shape, but Qwen3-Next never asks for it. This PR makes Qwen3-Next ask.

It is the only one of the three that changes behaviour for this model, and the only one with end-to-end numbers: **+2.8% to +3.6% output tok/s at C1–C16, +1.4% to +2.1% at C32–C64, with GSM8K unchanged.**

Last of three:

1. #39140 — the Gluon kernel
2. #44565 — lets the norm module reach it
3. **this PR** — the Qwen3-Next opt-in

Targets `main` independently rather than stacking. Landing order matters for what runs: on its own and with `--enable-aiter-allreduce-fusion`, this PR moves Qwen3-Next onto aiter's fused all-reduce + RMSNorm + quant kernel, and the Gluon kernel takes over at batch 1–16 once #39140 and #44565 are in. The numbers below are for all three together.

## What this does

Declares the quantized read on the Qwen3-Next decoder layers, so the boundary hands down `(bf16, fp8, scale)` instead of a tensor, and routes the pieces to the consumers that can take them:

* `declare_attn(read=NormQuantReadout(...))` on both decoder layers: `Fp8Input.TUPLE_AND_BF16` for the GDN layer, whose small `in_proj_ba` gating projection needs bf16 alongside the quantized `in_proj_qkvz`, and `Fp8Input.TUPLE` for the attention layer.
* `_forward_input_proj` and the `qkv_proj` sites unpack the tuple, giving each linear the member it can consume.

Each declaration is conditional on `_use_aiter` **and** on the consuming projection accepting an FP8 tuple. A build whose projections are not block-quantized, and every non-aiter backend including CUDA, keeps the plain tensor. There is no environment variable and no constructor flag; selection is by hardware capability alone.

## The MLP side is left alone

Only the attention input is declared; the FFN stage keeps the default read and `qwen2_moe.py` is not touched. An earlier revision also declared a quantized FFN read, consumed by a `Qwen3NextSparseMoeBlock` subclass. It was removed because on Qwen3-Next's default configuration it never engaged:

* `shared_expert_intermediate_size == moe_intermediate_size == 512`, so shared-expert fusion is on by default and there is no separate FP8 shared expert to feed.
* aiter's tuned Qwen3-Next MoE config (`qwen3next_80b_fp8_tuned_fmoe.csv`, `xbf16=1` on every row) selects a kernel that quantizes activations inside the MoE, so there is no separate quant launch to remove.

Instrumenting a running server showed the FFN read plain at all 192 sites, and removing the subclass measured within ±0.5% at every concurrency, with GSM8K unchanged.

## Scope

The Gluon kernel serves `M ∈ {1, 2, 4, 8, 16}` at hidden 2048, TP4, eps 1e-6, on gfx950 with `SGLANG_USE_AITER`. Above M=16, aiter's kernel is as fast or faster, so `is_supported()` declines and aiter serves the shape. Anything outside the envelope — other architectures, other TP sizes, CUDA — is unaffected.

## Results

4× MI355X (gfx950), TP4/EP1, `Qwen3-Next-80B-A3B-Instruct-FP8`, ISL/OSL 1024/1024, shared-expert fusion at its default (on), image `v0.5.20-rocm724-mi35x`, `--attention-backend aiter --moe-runner-backend aiter --enable-aiter-allreduce-fusion`. "This stack" is `main` 6d6c9cd4ae with the three PRs merged, file-for-file identical to what they now carry. The baseline is that same `main` with none of them. The arms are separate builds, not a runtime switch, run back to back in one session with at least 8 prompts per concurrency (16 at C1). C1 and C16 were repeated after restarting each server. Output tok/s:

| C ≈ decode batch | stock | this stack | |
|---|---|---|---|
| 1 | 227.6 / 227.4 | 235.3 / 235.6 | **+3.5%** |
| 2 | 433.7 | 445.8 | **+2.8%** |
| 4 | 841.2 | 871.8 | **+3.6%** |
| 8 | 1629.3 | 1681.8 | **+3.2%** |
| 16 | 3000.0 / 2996.1 | 3096.8 / 3071.1 | **+2.9%** |
| 32 | 4806.4 | 4873.6 | **+1.4%** |
| 64 | 7564.1 | 7726.3 | **+2.1%** |

C32 and C64 are above `SUPPORTED_M`, so the Gluon kernel declines and aiter serves those shapes; the gain there comes from the fused read itself, not from the Gluon kernel.

GSM8K 1319q (`python -m sglang.test.few_shot_gsm8k`, 5-shot): **0.944**, `Invalid: 0.000`, against 0.942 for stock, within run-to-run spread (σ ≈ 0.0065 at n=1319).

Instrumenting plan construction on the running server confirms where the gain comes from: the attention read is quantized at all 192 sites (48 layers × 4 ranks; `Fp8Input.TUPLE_AND_BF16` on the 36 GDN layers, `Fp8Input.TUPLE` on the 12 attention layers).

Qwen3-Next does not currently start on `main` on ROCm (`Capture cuda graph failed: expected scalar type BFloat16 but found Float`), independently of these PRs. All arms, stock included, were measured with the call-site fix from #46161 applied. This branch does not carry it.

## Test plan

* `test/registered/unit/layer_boundary/test_qwen3_next_fused_ar_read.py` (CPU): the attention declaration is gated on `_use_aiter` at both decoder layers (the test requires finding both, so it cannot pass vacuously; verified to fail when the gate is removed), and non-tuple inputs pass through to the projections untouched.
* GSM8K 1319q against stock at the same commit.
* Output-throughput sweep at C = 1, 2, 4, 8, 16, 32, 64, with C1 and C16 repeated.

## Hardware

gfx950 (MI355X), TP4, `SGLANG_USE_AITER=1`, ROCm >= 7.2.

Two things changed besides formatting. `Qwen3NextSparseMoeBlock` and the FFN quantized read are removed (details in the inline reply), so the PR is now `qwen3_next.py` plus one test file, +136/−9. And the numbers: +2.8% to +3.6% at C1–C16, +1.4% to +2.1% at C32–C64, GSM8K 0.944 vs 0.942.

I looked into your question about why `Qwen2MoeSparseMoeBlock` and it wasn't required, so it's removed in c883cbea.

`Qwen3NextSparseMoeBlock` differed from `Qwen2MoeSparseMoeBlock` only in that `forward` accepted a `(bf16, fp8, scale)` tuple, so a separate FP8 shared expert could take the quantized activations. We confirmed it on a running server: the FFN read was plain at all 192 sites, so the subclass only ever delegated to the parent. Removing it measured within ±0.5% at every concurrency, with GSM8K unchanged.

On NVIDIA: it never ran there either, since the FFN read was gated on `_use_aiter`. Now that it's removed, the MoE path is `Qwen2MoeSparseMoeBlock` on every backend, unchanged from `main`.
