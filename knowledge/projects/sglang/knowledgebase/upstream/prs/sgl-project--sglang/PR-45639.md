# [Fix] attention: Bound FP8 KV-cache reads in FlashInfer MLA prefill and decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/45639) · state: open · merged: False

## Original PR description

## Motivation

Addresses the FlashInfer MLA portion of [#35291](https://github.com/sgl-project/sglang/issues/35291).

Paged prefill and decode cast the entire per-layer FP8 KV pool to the query dtype on every forward, including unused slots. Conversion work and temporary memory therefore scale with allocated pool capacity. This change reads the rows referenced by the attention plan when that reduces the temporary allocation. The separate FA3 path remains outside this PR's scope.

## Modifications

- Eager paged prefill/decode gather referenced rows as bytes, convert the compact copy, and plan FlashInfer over consecutive compact IDs. Row order and duplicate IDs are preserved; piecewise and breakable prefill use this path.
- Select compact gathering only when `3 * num_kv_ids <= 2 * pool_rows`. This accounts for both the FP8 gather and its BF16/FP16 output. Above that threshold, retain physical IDs and use the existing full-pool cast.
- Captured decode refreshes referenced physical rows in one persistent query-dtype shadow. A fixed-grid Triton kernel reads the live row count from device metadata, so replay follows updated indices and sequence lengths.
- Share the shadow across layers and the primary/child TBO backends, whose attention calls execute serially on the compute stream. Each backend retains its own attention metadata.
- Preserve the existing E4M3 graph path below SM89, and the existing paths for non-FP8 caches, speculative decoding/verification, DCP and ragged prefill. KV writes and scaling semantics are unchanged.

**Issue**

`_refresh_mla_kv_shadow_kernel` gets the pool as `torch.float8_e4m3fn`, which Triton types as `fp8e4nv`. Triton allows `fp8e4nv` only on SM89+, so on SM80/SM86 this kernel fails to compile. The old path used torch `.to()`, which works on any GPU. The KV write path passes `uint8` views to Triton for the same reason.

**Example**

On A100 with `--attention-backend flashinfer_mla --kv-cache-dtype fp8_e4m3` and CUDA graphs on, decode graph warmup raises `ValueError: type fp8e4nv not supported in this architecture`.

**Fix**

Set `is_graph_decode` (`flashinfer_mla_backend.py:968`) only on SM89+ or for an E5M2 pool, and keep the full-pool cast otherwise. `use_fp8_e4b15_for_e4m3fn` in `sglang/kernels/ops/quantization/fp8_utils.py` already encodes this cutoff.

**Issue**

Each `FlashInferMLAAttnBackend` builds its own `_Fp8KvRowReader`, and each reader keeps its own pool-sized query-dtype shadow for the life of the process. With `--enable-two-batch-overlap`, `TboAttnBackend.init_new` builds a primary and two children, and each one runs captured decode. That gives up to three persistent shadows. The old in-graph `.to()` used one transient that the graph pool reused.

**Example**

A per-layer pool of 1M rows x 576 gives a 1.15 GB BF16 shadow. TBO then holds about 3.5 GB instead of about 1.15 GB.

**Fix**

Share one shadow between the TBO primary and its children, whose attention calls run in order on one stream; for example, give the children the primary's reader. Otherwise, state the extra memory in the PR.
