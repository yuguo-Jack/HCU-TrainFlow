# [Fix] managers: Keep the reserved token budget after auto-truncation

[Upstream PR](https://github.com/sgl-project/sglang/pull/46069) · state: closed · merged: False

## Original PR description

`_validate_one_request` counts the per-request output slots (`num_reserved_tokens`, non-zero only with EAGLE) when it decides the input is too long:

```python
input_token_num = len(input_ids) + self.num_reserved_tokens
if input_token_num >= self.context_len:
```

but the auto-truncate branch then drops them again:

```python
del input_ids[_max_req_len:]
input_token_num = len(input_ids)          # reserved slots gone
```

So the `max_new_tokens` clamp below it budgets the whole context for input + output, and the request still carries `num_reserved_tokens` on top. With `--enable-auto-truncate` on an EAGLE model, a long prompt ends up `num_reserved_tokens` past the context instead of at it.

Reproduced with a `TokenizerManager` built by `__new__` (`context_len=1024`, `num_reserved_tokens=4`, the values the new test uses):

```
# before
$ python -m pytest test/registered/unit/managers/test_tokenizer_manager_auto_truncate.py
AssertionError: 1028 not less than or equal to 1024   (input 1023 + 4 reserved + 1 new)
AssertionError: 1028 not less than or equal to 1024   (input 1024 + 4 reserved, no max_new_tokens)
2 failed

# after
$ python -m pytest test/registered/unit/managers/test_tokenizer_manager_auto_truncate.py
2 passed
```

The fix truncates to `context_len - num_reserved_tokens` and keeps the reserved slots in `input_token_num`, so the two checks agree. Without EAGLE `num_reserved_tokens` is 0 and nothing changes.

The numbers above are from a checkout of `main` (`25ba24e9a`); the unit test needs no server, GPU, or model. `ruff check` / `ruff format --check` pass on both files.

- nankingjing · comment · 2026-11-02T15:05:55Z · [source](https://github.com/sgl-project/sglang/pull/46069#issuecomment-6580507999)

Two things worth recording before anyone spends time reviewing this.

**Prior art: #24128.** @bzantium opened the broader version of this in April, and @hnyls2002 closed it on 2026-08-19 with "The fix looks well-tested, so @bzantium please reopen if you'd like to land it." That PR touches the same file and even the same test path, and it also reserves `max_new_tokens`. I only found it after opening this, and not citing it was a mistake on my part.

This PR is deliberately the narrower half. #24128 changes two things — keep the reserved-slot budget, and hold back `max_new_tokens` room — and it is the second one that has kept it from landing: reserving output room for every request changes how much of a long prompt gets through, which is a behaviour decision, not a bug fix. The reserved-slot half has no such ambiguity: `input_token_num` already adds `self.num_reserved_tokens` three lines above, so truncating to `_max_req_len` and then resetting `input_token_num` to `len(input_ids)` drops exactly the budget the check above just enforced. With EAGLE that ends at `context_len + num_reserved_tokens`, which is what the test reproduces:

```
unpatched main: AssertionError: 1028 not less than or equal to 1024   (2 failed)
with this diff: 2 passed
```

If you would rather have both halves, #24128 is the one to reopen and this one should be closed as its subset — I have no attachment to the PR number.

One limitation stated plainly: I checked the negative-slice case (`del input_ids[_max_req_len - num_reserved_tokens:]` when `num_reserved_tokens >= context_len`) and did not guard it. `compute_num_reserved_tokens()` returns `max(eagle_topk * eagle_steps, max_draft_tokens)`, so it is a single-digit number against a `context_len` in the thousands; a guard would be dead code and I would rather keep the diff at three lines. Say the word if you want it anyway.

I also have not run `base-a-test-cpu` — every `PR Test` job is parked at `Require run-ci label`, so the test in this PR has never executed in CI, only locally.

- bzantium · comment · 2026-11-03T04:02:29Z · [source](https://github.com/sgl-project/sglang/pull/46069#issuecomment-6595127705)

Thanks for the write-up and for checking prior art.

The reserved-slot half is right, but on its own it leaves the main symptom of #21136. After truncating to `context_len - num_reserved_tokens` and adding the reserved slots back, `input_token_num` equals `context_len`. The total-token check below then clamps `max_new_tokens` to `max(0, context_len - input_token_num) = 0`, so the request still produces no output. The new test passes because it only asserts `used <= CONTEXT_LEN`, which `max_new_tokens=0` satisfies.

I've opened #48063 against current `main`. It is the #24128 approach, rebased: truncate to `context_len - max_new_tokens - num_reserved_tokens` (at least 1) and keep the reserved slots in `input_token_num`. Its tests assert that `max_new_tokens` survives truncation. It also covers what yours does, so this one can be closed as a subset, as you suggested.
