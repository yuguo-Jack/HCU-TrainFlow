# [diffusion] fix: keep MiniMax-H3 VAE fused norms off ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/43350) · state: open · merged: False

## Original PR description

## Motivation

Since #41906, `minimax_h3_ref2va_video_audio_2gpu_h100` fails on AMD MI300 in the scheduled PR Test (AMD) runs on main. `MiniMaxH3DecodingStage` returns a video that is entirely NaN: 331,333,632 NaN values in a `[1, 3, 107, 768, 1344]` tensor ([example job](https://github.com/sgl-project/sglang/actions/runs/37709475489/job/113091795394)).

In the scheduled AMD runs on main:

- **Before #41906 merged (10-05 09:30 UTC):** this case either passed or failed with a server startup timeout, never with NaN.
- **After the merge:** every run that reached the case (7 runs, 10-06 to 10-09) failed with the all-NaN decode.

#41906 enables its fused Triton kernels (block RMSNorm, scale-add-RMSNorm, and the QK RMSNorm+RoPE) when the tensors satisfy `is_cuda`. On ROCm, `tensor.is_cuda` is also true, so MI300 takes the fused path.

## Modifications

- `vae_vit._fused_blocks_available` and `attention._try_fused_qk_rmsnorm_rope` now also require `current_platform.is_cuda()`, which is true only on NVIDIA. ROCm keeps the unfused fp32-norm path. NVIDIA behavior is unchanged.
- The fused-vs-unfused unit test now runs only on NVIDIA.
- A new unit test simulates a non-NVIDIA platform and checks that neither fused kernel is called.

Re-enabling the fused path on ROCm needs a separate root-cause fix on AMD hardware.

## Validation

- On an RTX 5090, `test_minimax_h3_vae_parallel_modes.py` passes (15 tests). The new test fails if the gate is removed.
- To confirm on MI300: PR Test (AMD) should run `minimax_h3_ref2va_video_audio_2gpu_h100` without the NaN decode.

### issue_comments

- mickqian · comment · 2026-10-10T07:46:52Z · [source](https://github.com/sgl-project/sglang/pull/43350#issuecomment-6095267306)

Thanks for the fix. Adding the root cause, two AMD failures that are still in this file, and an end-to-end check on AMD.

**Root cause.** `_scale_add_rmsnorm_kernel` calls `mul_rn_f32` from `sglang/kernels/numerics.py`, which is `tl.inline_asm_elementwise` with NVIDIA PTX (`mul.rn.f32`, constraints `"=f,f,f"`). The AMD Triton backend cannot allocate the `f` constraint (`error: could not allocate output register for constraint 'f'`), and the kernel output is all NaN: calling `h3_vae_scale_add_rmsnorm` directly on gfx950 returns NaN for every element. So re-enabling the fused path on ROCm needs a HIP implementation of that helper. `h3_vae_qk_rmsnorm_rope` has no inline asm, but gating it together with the block path keeps ROCm on the configuration that `MINIMAX_H3_VAE_DECODER_FUSED_NORM=0` already runs. The other users of the PTX helpers (`try_fused_scaled_residual_add_exact`, `rmsnorm_scale_shift_bitexact`, kda `layernorm_modulate_triton`) already gate on `current_platform.is_cuda()`, so this decoder path is the only gap.

**Two tests in this file still fail on MI300** in this PR's AMD run ([job](https://github.com/sgl-project/sglang/actions/runs/37926880974/job/113807955184)): `test_vit_fast_path_is_gated_and_matches_reference` and `test_vit_rope_batched_tiles_match_per_tile`. Their `requires_cuda` marker checks `torch.cuda.is_available()`, which is also true on ROCm, and the qk-norm RoPE JIT kernel they exercise does not compile under HIP. Switching the marker to the platform fixes both, and `test_fused_decoder_matches_unfused_forward` can reuse it:

```python
requires_cuda = pytest.mark.skipif(
    not current_platform.is_cuda(), reason="fused VAE kernels need CUDA"
)
```

**End-to-end on AMD.** 2x MI350X (gfx950), `lmsysorg/sglang:v0.5.21-rocm10-mi35x`, MiniMax-H3 FL2VA T2VA with `--attention-backend aiter`, `SGLANG_USE_AITER=1`, `--ulysses-degree 2`, 50 steps, 1344x768, 124 frames, `MINIMAX_H3_VAE_DECODER_FUSED_NORM` unset:
- main: warmup and the request both fail with `StageVerificationError` (383,975,424 NaN in the `[1, 3, 124, 768, 1344]` decode)
- with the same platform gate: warmup and the request complete, and the MP4 (124 frames plus audio) looks correct

With the gate and the marker change, `test_minimax_h3_vae_parallel_modes.py` passes on MI350X (CUDA-only tests skipped) and on B300.
