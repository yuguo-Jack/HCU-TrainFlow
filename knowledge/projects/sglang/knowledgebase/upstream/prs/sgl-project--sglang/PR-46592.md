# [Fix] eplb: Warm default-group P2P transports on multi-node layouts

[Upstream PR](https://github.com/sgl-project/sglang/pull/46592) · state: closed · merged: True

## Original PR description

## Motivation

#42026 warms EPLB's default-group NCCL P2P transports before KV-cache sizing, but only on a single node. On multi-node full-EP layouts, the first rebalance still creates the cross-node connections to the peers it exchanges with lazily (in our runs, all of them). By then the KV pool has already been sized to the free memory, so the transport buffers come out of memory the pool was counting on. The first rebalance also stalls while it connects.

Measured on GB300, DeepSeek-V4.1-Flash MegaMoE decode with DSpark and `--enable-eplb --ep-num-redundant-experts 32`, stock main:

| decode layout | first rebalance | steady rebalance | free memory lost at the first rebalance, per rank |
|---|---|---|---|
| 2-node DEP8 | 3.21 s | 1.01-1.04 s | 4.38 GiB, of which 3.24 GiB is P2P transports |
| 4-node DEP16 | 6.6-6.7 s | 0.85 s | 7.0 GiB |

That memory comes out after KV sizing, so a high `--mem-fraction-static` risks an OOM at the first rebalance, the failure #42026 addressed for single-node layouts. We have not hit that OOM in any run at 0.85; on 1-node DEP4 the ranks still had 52-57 GiB free before each rebalance. This is a stability fix, not a throughput change.

## Modifications

- Drop the `nnodes == 1` gate from the EPLB P2P warmup. The other gates are unchanged: CUDA with NCCL, `--enable-eplb` without an elastic EP backend, PP=1, and EP=TP>1.
- After the per-peer send/recv, run one 4 MiB all-reduce on the default group. Each rebalance all-reduces the recorded expert counts on that group. The warmup only sets up the NCCL algorithm and protocol picked at 4 MiB; the rebalance all-reduces the whole `logical_count` buffer (over 100 MB with a 3000-pass window), which NCCL may run with another algorithm. On GB300 MNNVL the warmup covered what the rebalance used (the first-rebalance loss drops to the staging cache, below); IB-only fabrics are not validated.

The all-reduce also runs on single-node layouts, so single-node memory accounting changes slightly (numbers below).

The warmup's KV cost grows with world size (~0.45 GiB per peer, measured on MNNVL); stock pays the same transports later, at the first rebalance. The warmup posts all peers in one batch, unlike the rebalance P2P, which is chunked; it has only run at W <= 8.

## Accuracy Tests

Not applicable: a startup-only change with no effect on model outputs.

## Speed Tests and Profiling

GB300, SGLang main at 65633129, InferenceX AgentX trace, MegaMoE decode with DSpark and dynamic EPLB (+32 redundant experts).

2-node DEP8 decode, rebalance every 3000 passes, c512, 14 rebalances per arm:

| | stock | this PR |
|---|---|---|
| first rebalance | 3.21 s | 1.06 s |
| later rebalances | 1.01-1.04 s | 1.01-1.06 s |
| free memory lost at the first rebalance, per rank | 4.38 GiB | 1.14 GiB |
| warmup at startup | - | 1.65 s, 3.24 GiB per rank (before KV sizing) |
| KV pool per rank | 87.64M tokens | 85.87M tokens (-2.0%) |
| OOM / request errors | none | none |

The remaining 1.14 GiB is the staging cache that every rebalance grows in both arms.

End-to-end throughput was not compared, and none is expected: the PR saves about 2 s once per server lifetime (the first rebalance at DEP8), and later rebalances take the same time in both arms. The 0.5-2.0% smaller KV pool could cost slightly when the KV pool is the limit.

1-node DEP4 decode, where #42026 already warms the P2P transports and this PR adds only the all-reduce. Rebalance every 1000 passes, c256, 5-6 rebalances per arm:

| | stock | this PR |
|---|---|---|
| warmup | 0.93 s, 1396 MiB | 1.08 s, 1780 MiB |
| KV pool per rank | 42.99M tokens | 42.79M tokens (-0.5%) |
| first rebalance | 2.06 s | 1.80 s |
| free memory lost at the first rebalance, per rank | 2.45 GiB | 2.08 GiB |

Not validated:
- The KV cost and startup time with this PR on 4-node DEP16. Only stock DEP16 was measured; the numbers above are from stock.
- HIP, and multi-node layouts over IB only. All runs used GB300 NVL72 racks with NCCL defaults, so cross-node traffic could use MNNVL.
