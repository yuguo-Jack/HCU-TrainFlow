# [diffusion] fix: give the scheduler hop its own host

[Upstream PR](https://github.com/sgl-project/sglang/pull/42435) · state: open · merged: False

## Original PR description

## Motivation

The scheduler's ZMQ endpoint was built from `host`, the address the HTTP server binds and advertises. Once `host` is routable — needed whenever the HTTP server must be reached from another process or machine, e.g. RL rollouts — `is_local_endpoint` treats the in-tree scheduler hop as remote. The scheduler still spills reply tensors to `CudaIpcRef`, but the client only materializes them on local endpoints, so the ref leaks to callers:

```
TypeError: 'CudaIpcRef' object is not subscriptable
```

`/generate` and `/rollout/generate` both index `OutputBatch.output` and fail this way. It also exposed the scheduler socket, which unpickles whatever it receives, on that routable address.

## Modifications

- Add `scheduler_host` / `--scheduler-host` (default `127.0.0.1`) and build the scheduler endpoint from it instead of `host`, as `disagg_p2p_hostname` already does for the P2P transport.
- Gate the reply-side `spill_cuda_tensors` on `is_local_endpoint` of this replica's own endpoint, like the file-ref spill next to it, so both ends of the hop apply the same condition.

Unchanged when `host` is `None`, `localhost` or `127.0.0.1`. With a routable `host`, request-side IPC (`update_weights_from_tensor`) now turns on too. A remote `DiffGenerator(local_mode=False)` must set `--scheduler-host` on both ends: the server no longer exposes the scheduler socket just because `host` is routable, and the connection error now says so.

## Tests

One test in `test/unit/test_ipc_array.py`, collected by the `unit` suite: with a routable `host`, a reply round trip through `Scheduler.return_result` and the client's receive path hands the caller a tensor, over IPC on a local hop and over pickle on an explicitly remote one. Not run yet; draft until verified.
