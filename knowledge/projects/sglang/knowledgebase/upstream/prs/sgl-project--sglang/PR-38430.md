# [Feat] glm: Enable compact NoPE KV storage with native FlashInfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/38430) · state: open · merged: False

## Original PR description

## Motivation

With compact-aware FlashInfer kernels, the same memory budget for GLM NoPE KV rows can hold 24.2% more token slots: each row uses 528 rather than 656 bytes, with the same FP8 values and FP32 scales. That provides more room for long prompts or cached request context without reducing precision. This is the row-capacity gain before allocator padding; other memory pools and configured context limits still apply.

This PR makes that capacity available to SGLang by integrating FlashInfer's native GLM NoPE attention backend on SM120 and selecting compact rows when supported. The existing RoPE entry point cannot serve GLM's NoPE query and sparse-candidate geometry. Gabriel Wu’s merged [FlashInfer #5075](https://github.com/flashinfer-ai/flashinfer/pull/5075) provides the canonical compact payload, runtime row strides and masked-read correction, including my eight-head decode and layout-validation fixes. His subsequent [FlashInfer #5197](https://github.com/flashinfer-ai/flashinfer/pull/5197) refactors native SM120 execution, runtime dispatch and calibration. Both are merged upstream and first ship in the FlashInfer 0.7.1 release line (0.7.1rc1 and later). No isolated serving speedup is claimed.

Related to #36830 for the SM120 native-backend path; this PR does not add SM90 support.

## Dependency

The native GLM NoPE path requires FlashInfer 0.7.1 or newer, which is currently published only as release candidates (0.7.1rc1 and later). The current pin, 0.7.0.post1, exports `SparseMLASm120Wrapper` and `supported_sparse_mla_sm120_configs` but reports 656-byte `glm53_nope` rows without the #5075 fixes. This PR does not change the pin; SGLang pins final FlashInfer releases, and moving to 0.7.1 belongs to the regular FlashInfer upgrade together with the cubin and JIT-cache images. Until then the native path is opt-in: SGLang selects `flashinfer_sparse_mla` automatically only for `GlmMoeDsaForCausalLM` (GLM with RoPE, `qk_rope_head_dim=64`), which keeps using the existing FlashInfer API and the 656-byte layout on any pinned version. A GLM NoPE model reaches the native path only when `--dsa-prefill-backend` and `--dsa-decode-backend` select `flashinfer_sparse_mla` explicitly. With an older FlashInfer, that fails at backend construction with an error naming the required and installed versions.

## Modifications

Use a persistent native FlashInfer wrapper for GLM NoPE and recognize the Glm5Next architectures. Pad 2,051 candidates to 2,176 columns and bound each row by its last valid column, preserving valid tail entries after missing groups. Size the runner buffers for mixed prefill/decode/verify batches and the scheduler's final whole-prompt admission when chunking is disabled. Allow this backend with multiple KPool index groups. When either attention phase selects the native backend, require both phases to select it; preserve other backend pairs for their existing validation paths.

Allocate one FP32 LSE buffer with the runner's token and head capacity and pass a slice of it as `out_lse` on every call. Without a caller-provided `out_lse`, the FlashInfer wrapper allocates and keeps a separate `[tokens, heads]` LSE buffer for every distinct call shape, so serving variable eager prefill lengths would keep accumulating GPU memory (about 8 GiB for every length from 65 to 8,192 tokens at 64 heads). The shared buffer is `max_num_tokens * num_heads * 4` bytes; SGLang does not read the LSE values.

Select compact 528-byte FP8 KV rows from FlashInfer’s model-specific canonical payload metadata. Native GLM NoPE runner construction requires this capability; the earlier padded-only native API is rejected. Both layouts contain the same 512 FP8 values and four FP32 scales. Compact rows remove 128 unused RoPE bytes per cached token per affected layer without requantization. This applies to GLM NoPE, not models that store RoPE values in those bytes.

Runner construction requires `supported_sparse_mla_sm120_configs()["glm53_nope"].bytes_per_token == 528`. That check excludes older payload metadata, but does not independently verify correctness fixes; partial cherry-picks of compact-row support are unsupported. The compact-capable kernels accept both 528- and 656-byte inputs. The separate open PR #37625 addresses finite top-k selection; this adapter also handles `-1` holes without dropping subsequent valid candidates. The existing RoPE API remains available. The native GLM NoPE path does not support skip-softmax thresholds: leave `SGLANG_SKIP_SOFTMAX_DECODE_THRESHOLD_SCALE_FACTOR` and `SGLANG_SKIP_SOFTMAX_PREFILL_THRESHOLD_SCALE_FACTOR` unset.

## Accuracy Tests

`test/registered/unit/test_flashinfer_sparse_mla.py`: 23 CPU tests and 23 subtests passed with each of FlashInfer 0.6.18, 0.7.0.post1 and 0.7.1rc4 installed. They cover backend selection, payload/layout checks, mixed-batch workspace sizing, candidate holes and empty rows, LSE buffer reuse across variable token counts, and an unmocked check that the installed FlashInfer either advertises compact `glm53_nope` rows (0.7.1 and newer) or makes runner construction fail with the version requirement.

`test/registered/kernels/ops/attention/test_flashinfer_sparse_mla_glm_nope_sm120.py` runs the real kernels through the SGLang adapter on SM120. It compares 528- and 656-byte rows against a dequantized PyTorch reference for 8 and 64 heads in decode and prefill form, with interior holes, valid K-pool tails, a tail-only row, an empty row and a poisoned cache slot 0. Queries and KV have unit variance so attention is far from uniform; the test requires under 4% aggregate and 10% per-row relative error and checks that references with a zero, halved or doubled softmax scale differ by at least 15%. It also replays a captured CUDA graph after a short row and an empty row are extended, and checks that the result differs from one limited to the lengths seen at capture. A third test checks that a sweep of distinct eager prefill lengths does not retain LSE allocations. It is registered for the SM120 kernel-unit runner and skips unless the GPU is SM 12.x and the installed FlashInfer advertises compact `glm53_nope` rows, so with the current pin CI collects it and reports skips; it exercises the kernels once FlashInfer 0.7.1 is installed. These GPU tests and Compute Sanitizer have not been run yet. On RTX PRO 6000 Blackwell (SM120), torch 2.14.1+cu130, Triton 3.8.0 with FlashInfer 0.7.1 (main d4b19b87, which reports 528-byte `glm53_nope` rows), all 11 tests in this file passed, as did the 23 unit tests in `test/registered/unit/test_flashinfer_sparse_mla.py`.

## Speed Tests and Profiling

KV rows decrease from 656 to 528 bytes: 128 bytes saved per cached token per affected layer, or 19.5% less row storage. The same row-storage budget holds 24.2% more token slots before allocator padding. Serving throughput was not benchmarked.
