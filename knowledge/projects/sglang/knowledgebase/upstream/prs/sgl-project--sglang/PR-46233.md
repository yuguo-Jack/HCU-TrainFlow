# [Feat] [NPU] eplb: enable dynamic expert load balancing on Ascend

[Upstream PR](https://github.com/sgl-project/sglang/pull/46233) · state: closed · merged: False

## Original PR description

## Motivation

Support `--enable-eplb` on Ascend with valid sender-route statistics, reuse of the existing TP device group, and migration of internal-format expert weights.

## Modifications

- Reuse upstream direct sender-route counting. Isolate ordinary NPU draft forwards and full-graph capture from target statistics through one entry guard, without modifying model definitions.
- Reuse TP's device group and communication options. TP must cover WORLD in rank order because shared statistics and migration use WORLD ranks. Prewarm statistics and all-peer P2P channels during non-elastic target initialization.
- Keep weight-format staging, chunk validation and migration participation checks under the NPU backend. Stage internal-format and strided ND weights into contiguous migration storage, then write back in place to preserve model addresses and strides. Allocate receive buffers on the first participating layer and reuse them within the chunk; idle ranks allocate none.
- Aggregate statistics windows before mapping and communication for supported policies and object output. Preserve full windows for file output and policies requiring per-step loads.
- Retain upstream scheduling, thresholds and the shared migration algorithm. Batched-route statistics, auxiliary packing, custom count kernels, replay-time statistics state, static-dispatch changes and the earlier 64-step initial policy are excluded.

Six production files differ from the comparison base: three NPU files and three shared integration files. GPU forward and the common recorder lifecycle retain their upstream implementations. Shared EPLBManager, placement metadata, model definitions and the decode graph runner are unchanged.

Generic breakable prefill graph capture is outside this adapter's draft-isolation coverage.

## Validation

Earlier hardware checks, using a dedicated group, covered imports, mixed-format migration, in-place writeback, communicating graph replay, and a short non-speculative PD ON startup/rebalance smoke check. They do not establish shared-TP HCCL service correctness.

Targeted CPU checks cover strided-ND wire ordering, original-storage writeback, deferred allocation and unchanged senders; the wire-order model is not an HCCL hardware result.

The TP-reuse and entry-guard changes passed local source-extracted checks, bounded single-NPU format/writeback and synthetic-graph checks, and CPU/Gloo migration checks. Each check's scope is recorded in the validation note. Complete shared-TP service validation, generic prefill/draft graph coverage, GPU regression, and matched PD throughput/accuracy validation remain pending. No serving-throughput or model-accuracy improvement is claimed.

No new test files are included; the existing NPU graph fixture supplies worker identity. See the [concise validation note](https://github.com/AkiYangDev/sglang/blob/f6ad2f4f922d0df111dc66153f543a453267455c/test/manual/ep/reports/ascend_dynamic_eplb_upstream_20261024.md). Detailed diagnostics, scripts and performance materials remain outside the PR.

- AkiYangDev · comment · 2026-10-27T02:26:31Z · [source](https://github.com/sgl-project/sglang/pull/46233#discussion_r4384516506)

File: `python/sglang/srt/eplb/expert_distribution.py` · line None

Yes, you are right about backend selection. I traced the initialization path: SGLang already initializes the default process group with HCCL on NPU. Passing a separate group is not necessary just to select HCCL.

The dedicated EPLB group uses explicit HOST expansion and a 32 MiB buffer, and is also used for weight migration. Those settings alone do not establish that statistics need this group. Also, `dist.group.WORLD` and the separately created TP/MoE groups are distinct communicators even when their rank membership matches, so sharing ranks does not establish a conflict with the forward graph's communicator.

I checked the CANN 9.1.0 HCCL/HCOMM source as well. Ordinary AIV mode is distinct from ONLY_AIV mode; the legacy Reduce path selects non-AIV algorithms, and the explicit rejection of non-AIV algorithms is conditional on ONLY_AIV. Therefore, the absence of Reduce from the AIV support table is not sufficient evidence that the default group cannot run these statistics collectives.

Based on this, I agree that the statistics path should be simplified to reuse the default group, while keeping migration-specific communication separate. This group change is not implemented yet. Default-group `reduce`/`all_reduce`/`broadcast` interleaved with NPU graph execution still need hardware validation on the deployed stack; the source inspection is not a runtime validation result.
