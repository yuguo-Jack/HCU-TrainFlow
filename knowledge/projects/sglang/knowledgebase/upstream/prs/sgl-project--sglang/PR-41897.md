# [Perf] [XPU] flux2: Bit-exact FLUX.2-klein op substitutions

[Upstream PR](https://github.com/sgl-project/sglang/pull/41897) · state: open · merged: False

## Original PR description

## Motivation

On Intel XPU, FLUX.2-klein pays for copies and kernel choices the backend doesn't need:

- RMSNorm copies every strided Q/K head view of the packed QKV (Qwen3 text encoder) before the kernel;
- the dual-block SwiGLU reaches a fused kernel, but the wrong one for these shapes: #41940 enabled the Triton `_packed_silu_mul_kernel` on XPU, where `sgl_kernel.silu_and_mul` is **1.3-1.4x faster**;
- the single-block tail materializes the eager SwiGLU output, then copies it again into `cat([attn, mlp])` — and the single-block tensor is strided, which is exactly where the Triton kernel stops paying for itself.

This PR removes all three on XPU. Every change is bit-exact, so no quality gate is needed. CUDA/ROCm behaviour is unchanged.

**What the two block types actually see.** Probed on a live klein-4B 1-step run at 1024x1024, by wrapping `_flux2_swiglu` / `_flux2_cat_swiglu` from a `sitecustomize.py` (so it reaches the spawned GPU workers) and aggregating by shape:

| caller | shape | row stride | contiguous | calls/step |
|---|---|---|---|---|
| double blocks, image stream | `[1, 4096, 18432]` | 18432 | yes | 5 |
| double blocks, text stream | `[1, 512, 18432]` | 18432 | yes | 5 |
| single blocks | `[1, 4608, 18432]` | **27648** | **no** | 20 |

So 20 of the 25 SwiGLU sites per step are **strided**, and they are the ones commit 3 serves. This is why the contiguity check in commit 2 is not a conservative limitation — it is the predicate that routes the single blocks into commit 3.

## Modifications

Three commits, each reviewable on its own:

1. **`RMSNorm.forward_xpu` reads packed-QKV head views in place.** It passes the strided 3-D view to `sgl_kernel::rmsnorm` instead of `reshape`-copying it. The output is bitwise identical, and it saves 72 copies per request.
2. **FLUX.2 SwiGLU goes through `can_use_fused_packed_silu_mul()`.** On XPU that routes contiguous inputs to `sgl_kernel.silu_and_mul`: bit-exact, **1.427x** over main's Triton kernel at the 4096-token shape and **1.304x** at the 512-token shape. Strided inputs are rejected by the predicate, because `sgl_kernel`'s packed kernel copies a strided input first; they are served by commit 3 instead, which beats both main and eager there.
   - The CUDA-graph capture guard asks `torch.get_device_module(x.device)` instead of `torch.cuda`, which raises off CUDA. It stays behind `can_fuse and not verified`.
   - `srt`'s `is_device_stream_capturing` is not used, because it returns False mid-capture on ROCm.
3. **The single-block eager SwiGLU writes straight into the `to_out` input.** `_flux2_cat_swiglu` allocates the `[attn | mlp]` buffer once and writes `silu(gate) * up` into its right half. The GEMM input is identical to the cat's. **This is the larger of the two optimizations: 14.24 ms of the 15.78 ms/step total**, because it fires on all 20 single blocks.
   - It returns `None`, keeping the cat, in these cases:
     - off XPU;
     - when the fused kernel applies;
     - under `torch.compile`;
     - on a dtype or shape mismatch.
   - For klein-4B at 1024x1024 the fused kernel never applies at a single block (the input is strided), so in practice this path is taken on every one of them.
   - FP8/NVFP4 paths are untouched.
   - `mlp_act_fn.forward` is bypassed on this path, so forward hooks on it (e.g. layerwise NVTX markers) don't fire.

New tests:
- `test/unit/xpu/layers/`:
  - `test_xpu_rmsnorm.py`: the head-view predicate (CPU, so it also runs in the H100 unit suite) and bit-exactness vs the contiguous path;
  - `test_xpu_packed_silu_mul.py`: bit-exactness vs eager;
  - `test_xpu_flux2_cat_swiglu.py`: bit-exactness vs the cat, and each fallback case.

  The H100 unit suite walks `test/unit/` recursively, where the XPU-only tests skip. `pr-test-xpu.yml` does not run them yet; wiring them in, as `pr-test-musa.yml` does for MUSA, is a follow-up PR.
- `test_model_fast_paths.py::test_flux2_cat_swiglu_is_xpu_only`: checks that CUDA and CPU keep the cat.

## Benchmarking and Profiling

Intel Arc Pro B60, 1 card, torch 2.14.0+xpu, sglang-kernel-xpu 0.4.0, bf16. Both arms are this branch (`1e290129ea`) and its base (`dc81f17b90`) in the same env on the same card, minutes apart — all three commits are pure Python, so the arms are a `git checkout` apart with no rebuild. 50 timed reps after 10 warmup, `torch.xpu.synchronize()` either side, on the probed shapes above.

**Double blocks — contiguous, 5 calls/step each shape:**

| shape | eager | main (Triton) | this PR (`sgl_kernel`) | vs main |
|---|---|---|---|---|
| `[1, 4096, 18432]` | 1.097 ms | 0.956 ms | **0.670 ms** | **1.427x** |
| `[1, 512, 18432]` | 0.134 ms | 0.090 ms | **0.069 ms** | **1.304x** |

**Single blocks — strided `[1, 4608, 18432]`, 20 calls/step.** Measured as the whole `to_out`-input preparation, which is the comparable unit: main does `swiglu -> torch.cat`, this PR fuses the mul into the cat buffer.

| path | time | vs eager |
|---|---|---|
| eager swiglu + cat | 2.467 ms | 1.000x |
| **main**: fused (Triton, strided) + cat | **2.512 ms** | **0.982x — slower than eager** |
| **this PR**: `_flux2_cat_swiglu` | **1.800 ms** | **1.371x** |

On the shape 20 of 25 sites see, main's Triton path is a **net loss** once the `cat` it forces is counted; this PR is **1.396x** faster than main there. In isolation that kernel does gain on strided input (1.011x at T=4096, 1.595x at T=512 vs eager), but the separate output buffer it writes has to be copied again by the `cat`, which erases it.

**Per step**, weighted by the probed call counts:

| | main | this PR | saving | saving % | % of the 485 ms step |
|---|---|---|---|---|---|
| 5 double blocks (image + text) | 5.230 ms | 3.695 ms | 1.535 ms | 29.35 % | 0.32 % |
| 20 single blocks | 50.240 ms | 36.000 ms | 14.240 ms | 28.34 % | 2.94 % |
| **total** | **55.47 ms** | **39.70 ms** | **15.78 ms/step** | **28.43 %** | **3.25 %** |

Against a measured klein-4B denoise step of **485.0 ms** (`sglang serve --enable-torch-compile --component-residency dit=resident,text_encoder=layerwise-offload`, `bench_serving --dataset vbench --num-prompts 20 --num-inference-steps 4` at 1024x1024, 20/20, 2.4915 s mean latency, 10430 MB peak), that is **3.25 % of denoise**.

**Caveat:** the per-step figures are built from isolated microbenchmarks on synthetic tensors of the probed shapes. They predict ~500 ms/step for an end-to-end run on `dc81f17b90` against this branch's measured 485.0 ms/step; that end-to-end arm has not been run, so the 3.25 % is a projection, not a measured delta.

## Accuracy Tests

All three changes are bit-exact by construction and asserted with `torch.equal` in the new tests.

- **XPU**, Arc Pro B60, torch 2.13.0+xpu. The new layer tests were run one file per command, then as a directory: 3 + 2 + 3 passed, and 8 passed.
- **XPU bit-exactness at the real shapes**, torch 2.14.0+xpu: every fused result in the benchmark above compared `torch.equal`-identical to the eager reference — on both arms, at all three shapes (contiguous 4096 / 512, strided 4608), including `_flux2_cat_swiglu`'s full `[1, 4608, 12288]` `to_out` input against `cat([hs, silu(gate) * up])`.
- **CUDA**, A100-SXM4-40GB, torch 2.13.0+cu130. `test/registered/kernels/ops/diffusion/{test_model_fast_paths,test_activation,test_sites,test_norm}.py` were run on this branch and on the base:

  | | base | this PR |
  |---|---|---|
  | test_model_fast_paths | 65 passed, 1 failed, 21 skipped | 66 passed, 1 failed, 21 skipped |
  | test_activation | 11 passed | 11 passed |
  | test_sites | 24 passed | 24 passed |
  | test_norm | 171 passed, 1 failed | 171 passed, 1 failed |

  The two failures are identical on the base, so they already exist on main:
  - `test_hunyuan_quality_qknorm_matches_rmsnorm`: CuTe-DSL NVVM compile error;
  - `test_cutedsl_norm_scale_shift_shapes[dtype1-shape0-layer-True]`: 4 of 353,894,400 elements out of tolerance.
- **CUDA-graph capture** (A100), run under a real `torch.cuda.graph` capture:
  - inside a capture, the guard keeps `_flux2_swiglu` eager and unverified, and the replay is bit-exact;
  - outside a capture, the fused kernel runs and is bit-exact;
  - a re-capture after that is bit-exact too.
