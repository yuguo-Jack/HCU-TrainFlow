# [Fix] hicache: Key MLA Mamba state per TP rank in the file backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/41907) · state: closed · merged: True

## Original PR description

## Motivation

MLA shares KV storage keys across TP ranks, but Mamba checkpoints are sharded. Give file-backend Mamba keys a TP rank/size suffix so one rank cannot overwrite another rank's checkpoint. Keep existing keys for other pools. Same fix as #43594 for NIXL; SeaweedFS and HF3FS have the same bug and are fixed in #43816 and #43817.

## Modifications

- `HiCacheFile._get_suffixed_key` gives Mamba component keys (`<key>.mamba`) the TP rank/size suffix (`tp_config_suffix`); other pools keep their existing keys. Public `get/set/exists` signatures are unchanged.
- `LRUFileEvictor` takes `owned_suffixes` instead of MLA flags: every rank owns its TP-sharded files, and MLA rank 0 also owns the shared files. With file eviction enabled, MLA ranks > 0 can now store their own Mamba state, while replicated KV is still created by rank 0 only.
- On MLA models `max_size` now applies per rank to that rank's own files, as it already did on non-MLA models, so a shared directory can exceed one cap.

Old unranked Mamba files are not reused because their owning rank is ambiguous; rank 0 owns them and evicts them through LRU.

## Validation

- GLM-5.3-Flash TP4 with file L3, L3-only restore of a 16K prefix: 408/544 wrong-rank Mamba payloads on main, 544/544 correct with per-rank keys (earlier revision of this patch; key format unchanged since).
- New unit tests (two-rank Mamba round trip, MLA rank 1 creating its own Mamba file under eviction) fail on main and pass with this PR; the file-backend unit test modules pass.
