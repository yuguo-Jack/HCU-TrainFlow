# [Fix] lora: Clear the embed_tokens/lm_head slot before loading a partial embedding adapter

[Upstream PR](https://github.com/sgl-project/sglang/pull/44924) · state: open · merged: False

## Original PR description

## Motivation

When a LoRA slot is reused, `load_lora_weight_to_buffer` only zeroes the `embed_tokens` / `lm_head` buffers for adapters that have no embedding weights at all. If the incoming adapter has some of them (say just `lm_head`), the zeroing is skipped, so the slot keeps whatever the evicted adapter left in the rest. The next request then runs with another adapter's weights and nothing complains.

It needs `--max-loras-per-batch` smaller than the number of adapters in use, so slots actually get reused, plus adapters that carry embedding / `lm_head` LoRA weights.

I came across this reading `mem_pool.py` and checked it on a live server (Qwen3-0.6B, `--max-loras-per-batch 1`). Adapter X only changes `lm_head`. Adapter Y has `embed_tokens` weights with a zero B matrix, so it should behave exactly like the base model:

| request | before | after |
|---|---|---|
| base | ` Paris. The capital of Italy is Rome...` | same |
| X | garbage (`항ICK鐘 addrYa...`) | same, as expected |
| Y | the same garbage as X | ` Paris. The capital of Italy is Rome...`, equal to base |

## Modifications

- In `LoRAMemoryPool.load_lora_weight_to_buffer`, moved the existing zeroing block (the one the `else` branch already had) in front of the `if lora_adapter.embedding_layers:` check, so it runs for every adapter. No new logic.
- As a side effect it also clears the rank / vocab tail that a smaller adapter doesn't overwrite, which had the same stale-data problem.
- One regression test, added to the existing `test_mem_pool_ep_unit.py`: a rank-4 slot reused by a rank-2 `lm_head`-only adapter. It fails on main (32 stale values left in `embed_tokens`) and passes with the change. `test/registered/unit/lora` is 114 passed.

I checked the overlap-loading path too: the whole load, including this zeroing, runs inside the same stream context, so the order against the weight copies is unchanged.

If you'd rather see the rank-tail clearing as a separate change, I'm happy to split it out.

## Accuracy Tests

Only affects outputs in the reuse case above, where they were wrong before; the table is the check. No model or kernel code changed.

## Speed Tests and Profiling

One extra `zero_()` on the slot's embedding / `lm_head` buffers per adapter load, on buffers the load already writes into. By my arithmetic that is a few MB at rank 8 and about 40 MB at rank 64. I haven't measured it; I expect it to be lost next to the weight copy.
