# [Fix] diffusion: report the port each scheduler actually bound to its clients

[Upstream PR](https://github.com/sgl-project/sglang/pull/42332) · state: open · merged: False

## Original PR description

## Motivation

Diffusion servers starting together on one host can pick the same scheduler port: it is guessed as `5555 + randint(0, 100)` and checked by a probe that releases it. The loser's scheduler then binds `port + 42`, but its HTTP side still connects to the guessed port, so its requests are served by the other server's scheduler and GPU.

We hit this as an intermittent RL CI failure, caught by the UUID check from #32685:

```
no payload was exported from this worker's GPU 47b7c7e8-..., got ['05a0fd7c-...']
```

## Modifications

- Each scheduler reports the port it actually bound in its ready message (`dp_replica`, `actual_scheduler_port`); the launcher records it in `server_args.scheduler_ports` before any client connects. A scheduler that moved off a taken port is now reached on its new port.
- The scheduler also records the bound port in its own `server_args`, so the metrics `replica` label matches the real endpoint.
- `--strict-ports` now fills `scheduler_ports` as well, so the list is always set.

- AgainstEntropy · comment · 2026-10-22T18:22:56Z · [source](https://github.com/sgl-project/sglang/pull/42332#issuecomment-6348090892)

seems #43732 fixed the same issue the opposite way: the scheduler binds with `same_port=True`, so it never moves, and the server that loses the race fails at startup.

However I believe in RL case (and most other cases), the losing server should still start, bind a free port and report it faithfully as this PR does.
(except for explicit `--scheduler-port` or `--strict-ports`, where `same_port=True` so port should never be moved)
