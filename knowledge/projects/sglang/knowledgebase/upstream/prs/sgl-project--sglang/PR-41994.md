# [AMD] Faster DSpark scheduling and per-step verify width for DeepSeek-V4.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/41994) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1-Flash with DSpark on MI355X loses throughput in three places on main after #41308:

- **Batch 1 to 64 decode.** With overlap scheduling and speculative decoding on HIP, `FutureMap.resolve_seq_lens_cpu` and `resolve_mixed_spec_tails` block the host on the previous forward's publish event (`publish_ready.synchronize()`), so the GPU idles between the DSpark verify and the next draft. The host sync exists because `Event.wait()` on the separate schedule stream is slower still: a device wait pending in another HIP queue while the forward graph runs slows every dispatch of that graph.
- **Bursts at `max_running_requests`.** `MinFreeSlotsDelayer`, auto-enabled for DSpark, holds fresh prefills until `min(4, max(2, (max_running_requests + 5) // 6))` slots are free. A burst of 256 requests on the High-Throughput cell settles at 253 running with 3 queued, and those 3 wait for the whole decode of the running batch (75 s maximum TTFT).
- **Batch 64 to 256 decode.** DSpark verifies `gamma + 1` tokens per request at every batch size. Past batch 8 the verify cost grows with verify tokens faster than the tail draft positions add accepted tokens, so a narrower verify commits more tokens per second.

## Modifications

- `perf(amd): keep speculative overlap scheduling on the forward stream`. On HIP with overlap scheduling, speculative decoding and no pipeline parallelism, the scheduler runs on the forward stream (`Scheduler.schedule_on_forward_stream`, decided once in `init_overlap`), and `FutureMap(same_queue_publish=True)` waits on the publish event in-queue with `Event.wait()` instead of blocking the host. Stream order carries the forward-to-schedule dependencies. Without speculation there is no publish wait, so the separate schedule stream stays. CUDA is unchanged; on HIP this applies to every speculative algorithm.
- `fix(scheduler): stop the min-free-slots delay once every waiting request fits`. `MinFreeSlotsDelayer.should_delay` takes the number of waiting requests and delays only while the free slots are fewer than both the threshold and the waiting requests. With at least `threshold` requests waiting, nothing changes. The new unit case covers 254 running with 2 free: 2 waiting are admitted, 3 still wait.
- `feat(spec): pick the DSpark static verify width per step`, off by default.
  - `SGLANG_DSPARK_VERIFY_WIDTHS` (extra widths below `gamma + 1`, e.g. `3,4`) plus a diagonal SPS table (`--speculative-dspark-sps-table-path`, from `python -m sglang.benchmark.dspark_sps_profiler`) enables it. `SGLANG_DSPARK_FORCE_VERIFY_WIDTH` pins one captured width for A/B runs.
  - After the full-width graphs, the worker builds a target attention backend, decode graphs and a verify epilogue for each extra width under a scoped `get_spec().override(speculative_num_draft_tokens=w)`, and swaps them onto the target model runner only around the verify forward. `model_runner.py` is unchanged.
  - A step at width `w` verifies the anchor plus the first `w - 1` drafts of the unchanged proposal. Accept, commit and the folded epilogue run at width `w`, and the result carries `w` as its output row stride.
  - The width maximizes predicted committed tokens per second: the expected accept length from decayed per-position acceptance, times the SPS table's steps per second at `bs * w` verify tokens, with a 2% switch margin. Acceptance counts come from a device histogram read with a fixed lag, so every TP rank picks the same width. The full width runs until every draft position is measured, and every 64th step after.
  - Grammar, logprob and sampling-mask steps keep the full width. Unsupported setups fail at startup: non-static verify modes, attention DP, PP, mamba targets, simulated acceptance and the DSpark debug observers.
  - Enabling it needs an SPS table for the deployment, so the cookbook is unchanged here.

## Accuracy Tests

- GSM8K, full test set (1319 questions, natural EOS, concurrency 128), High-Throughput cell, two fresh servers per arm: main 97.19% and 96.97%, this PR 96.97% and 96.97%. Two main servers agree on 1307 answers, a main and a PR server on 1301-1307, so the differences are server-to-server variation.

- Verify width off vs auto (`3,4`), 64 GSM8K questions per server: 63 and 63 off, 63 and 62 auto.
- Because the forward-stream scheduling covers every speculative algorithm on HIP, the speculative AMD CI tests were also run locally on MI355X with `scripts/ci/amd` and the `rocm/sgl-dev:v0.5.20-rocm10-mi35x-20260930` image: `test_basic_sanity_eagle3`, `test_dflash`, `test_eagle_dp_attention` (4 GPUs), `test_frozen_kv_mtp`, `test_spec_standalone_extra`, `test_eagle_worker_v2_topk1_fastpath`, `test_build_eagle_tree` and `test_resolve_swa_kv_pool` pass. `test_adaptive_speculative` is flaky on main as well: it passed 11 of 12 runs on this PR and 10 of 11 on main, and both failures were the same `Never downshifted` check. `mock_model/test_e2e_spec_eagle` fails with a memory fault in `ck_tile::FmhaBatchPrefillWithPagedKVCacheKernel` at the same prefill on main as well.

@kpham-sgl

**Conclusion.** We split this PR into three PRs, as you asked. Together they are the same change as this PR. For part 1, we kept the forward-stream change, because `needs_cpu_seq_lens = False` does not remove the batch < 64 cost on HIP.

1. #42279: batch < 64, speculative overlap scheduling on the forward stream (HIP)
2. #42280: `MinFreeSlotsDelayer`
3. #42281: DSpark per-step verify width, batch >= 64

**Data.** For DeepSeek-V4.1 on HIP, `needs_cpu_seq_lens` is already False. #41308 sets it from `SGLANG_OPT_USE_ONLINE_COMPRESS`, which is off by default. We ran the Low-Latency DSpark cell on main `dcf4e18283` with a print-only probe. Both the target and the draft `DeepseekV4HipRadixBackend` report `needs_cpu_seq_lens=False`. But `resolve_seq_lens_cpu` still calls `publish_ready.synchronize()`, and it does no seq_lens D2H. These code paths are the same on current main.

**Analysis.** On HIP, the host sync occurs before the code reads `needs_cpu_seq_lens`, so the flag cannot remove the sync. This host sync is the batch < 64 cost. A device `Event.wait()` on the separate schedule stream removes the sync, but it makes the verify graph 1.21 ms slower (the #26672 regression). The forward-stream change removes the sync without this regression.

**What we think.** #42279 is the correct fix for batch < 64. Its description has the details. This PR stays open until you agree with the split.
