# [Refactor] scheduler: Route every step launch through one hook and count in-flight steps

[Upstream PR](https://github.com/sgl-project/sglang/pull/43900) · state: closed · merged: True

## Original PR description

Every step launch now goes through one hook, and each request counts the launched steps carrying it whose results are not processed yet. Nothing reads the count yet; it is what a request's memory release can wait on, since those steps may still use its KV.

- `Scheduler._on_step_launch(batch)` holds the bookkeeping of every launch: `forward_ct` / `forward_iter`, `launch_ts`, the idle-gap flag, the profiler predicate, `batch.add_inflight_step()` and `_join_launched_reqs`. `run_batch` and the MLX overlap launch (`_prepare_mlx_launch`) both call it instead of keeping their own copies.
- `Req.inflight_steps`: `ScheduleBatch.add_inflight_step()` records the step's requests as `launched_reqs` (a tuple, carried by `copy()`) and adds one for each at launch; `drop_inflight_step()` subtracts one over the same tuple in `Scheduler._on_step_processed(batch)`, the processing-side counterpart of the launch hook, which `process_batch_result` now ends with (it also holds the running list's `leave_finished`). The PD decode + PP loop, which skips processing a prebuilt micro-batch, still calls `_on_step_processed` for it.
- `SchedulerInvariantChecker.maybe_check_batch_consistency` (under `SGLANG_ENABLE_RUNNING_REQS_CHECK`, on by default in CI) raises if a step is processed with requests other than the ones it was launched with: a launched step's requests do not change.
- Tests: launch and processing counts through the real `run_batch` and `process_batch_result`, and the check rejecting a step processed without its launch (`test_scheduler_running_reqs.py`); unit fakes that reach the hook get the fields it touches.

No behavior change.
