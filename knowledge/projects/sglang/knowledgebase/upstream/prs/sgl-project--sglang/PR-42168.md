## What changes

**Who sees it:** users who run a PD (prefill/decode disaggregation) decode server with `--enable-hisparse`. This includes a decode whose GPU pool holds fewer tokens than one request.

**Before this PR:** the decode rejects any request that is longer than its GPU pool, even though the host-backed pool holds many more tokens. Example: a 105,000-token device pool (104,960 after page rounding) rejected a 117,624-token prompt.

```
Input length (117624 tokens) exceeds the maximum allowed length (104954 tokens)
```

In PD, the rejection also leaves the prefill waiting for the KV transfer until the bootstrap timeout. The run hangs.

**After this PR:** a PD HiSparse decode admits requests up to the size of its host-backed logical pool (`max_token_pool_size`). In the same setup, all 9 turns of a 206K-token session completed.

**Conditions:** the change applies only to a PD decode role with HiSparse. Prefill, aggregated HiSparse and non-HiSparse servers keep the old limit. An aggregated HiSparse server keeps the device limit because its prefill extends take one device slot for each token. The DCP-aware limit of [#39731](https://github.com/sgl-project/sglang/pull/39731) is unchanged for those roles.

Speed is not measured for this PR.

## Background

A PD HiSparse decode receives each request's KV into its host-backed logical pool. The size of this pool is the device token count times `host_to_device_ratio`. The GPU keeps only a fixed hot buffer for each request. `DecodePreallocQueue` already admits requests against the logical capacity. But `max_req_len`, `max_req_input_len` and the `max_new_tokens` clip still came from the device pool. [#39731](https://github.com/sgl-project/sglang/pull/39731) made them the DCP-aware logical capacity of the device pool. That is not the host-backed pool.

## Implementation

- `ModelRunner.request_token_capacity` returns the host-backed logical pool on a PD HiSparse decode. It returns `effective_logical_max_total_num_tokens` in all other cases.
- `TpModelWorker` uses it for `max_req_len` and `max_req_input_len`. This covers startup validation and `get_worker_info`.
- The scheduler uses it, as `Scheduler.request_token_capacity`, for the `max_new_tokens` memory clip.
- A PD role switch of a HiSparse server recomputes these limits for the new role (`Scheduler._refresh_request_length_limits`).
- The scheduler's `max_total_num_tokens`, the hot-buffer budget and all other pool accounting are unchanged.

## Tests

`test/registered/unit/mem_cache/test_hisparse_max_token_pool_size.py` has 8 new tests:

- The logical bound on a PD HiSparse decode.
- The device bound for aggregated HiSparse, prefill HiSparse and non-HiSparse decode.
- The worker's `max_req_len` and `max_req_input_len` for each role.
- The `max_new_tokens` clip beyond and within the device pool.
- The refresh of the limits on a PD role switch in both directions.

Six of the tests fail without this change. Two are regression guards that also pass on the parent.

## Measured

On a GLM-5.2 PD run on MI355X, a TP2 decode with a 105,000-token device pool rejected turns of 117,624 tokens, and the run hung. With this PR, all 9 turns of a 206K-token session completed.

Not run: a PD HiSparse decode on a GPU whose device pool is smaller than one request, in the CI test suite.
