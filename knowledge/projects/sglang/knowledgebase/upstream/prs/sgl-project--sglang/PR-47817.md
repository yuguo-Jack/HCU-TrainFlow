# [Perf] moe: Skip compiled TopK postprocess when metadata is absent

[Upstream PR](https://github.com/sgl-project/sglang/pull/47817) · state: open · merged: False

## Original PR description

## Motivation

`_biased_grouped_topk_postprocess` is invoked by participating MoE layers during model forwards. It performs two optional operations:

- **Logical-to-physical expert ID remapping**, controlled by `expert_location_dispatch_info`.
- **Padded-token masking**, controlled by `num_token_non_padded`.

When both arguments are `None`, neither operation is required. The remapping and masking functions leave `topk_ids` unchanged, but the current implementation still enters the `torch.compile`-decorated wrapper, introducing unnecessary host-side dispatch overhead.

This no-op case can occur in TP-only MoE configurations where expert remapping and padding masking are not needed.

The overhead accumulates across MoE layers and repeated model forwards. Avoiding it can benefit eager execution and Python forwards during CUDA Graph warmup/capture, as well as breakable-graph execution paths that invoke this helper.

Full CUDA Graph replay does not re-execute this Python helper, so no direct steady-state full-graph replay improvement is expected.

## Modifications

- Rename the existing compiled implementation to `_biased_grouped_topk_postprocess_compiled`, preserving its original `torch.compile` decorator and logic.
- Keep `_biased_grouped_topk_postprocess` as the caller-facing entry point without a compilation decorator.
- Add a lightweight Python guard that immediately returns the original `topk_ids` tensor when both metadata arguments are `None`.
- Delegate all other cases (remap-only, mask-only, and remap + mask) to the original compiled implementation.

The change preserves the existing routing behavior and does not modify tensor layouts, expert selection, or CUDA kernel launch parameters.

## Accuracy Tests

The new unit test covers all four combinations of optional metadata and verifies that the compiled implementation is invoked exactly three times.

| Case | Expert dispatch info | Non-padded token count | Expected behavior |
|---|---|---|---|
| Both absent | `None` | `None` | Return the original `topk_ids` object without compiled-wrapper dispatch |
| Remap only | Present | `None` | Preserve expert ID remapping |
| Mask only | `None` | Present | Preserve padded-token masking |
| Remap + mask | Present | Present | Preserve both operations |

The no-op case verifies tensor object identity, while the remaining cases verify the expected output values and delegation behavior.

## Speed Tests and Profiling

### Environment

- **Date:** 2026-11-01
- **GPU:** NVIDIA H100 80GB
- **CUDA:** 13.0
- **PyTorch:** 2.14.1+cu130

### 1. No-op postprocessing microbenchmark

This benchmark compares the original compiled entry point against the new Python guard when both metadata arguments are `None`.

Neither path performs useful GPU computation in this case. The measurement isolates host-side wrapper dispatch overhead rather than end-to-end inference performance.

| Batch size | Compiled wrapper (µs) | Python guard (µs) | Saved (µs) | Reduction |
|---|---:|---:|---:|---:|
| 1 | 4.641 | 0.046 | 4.595 | 99.0% |
| 64 | 4.654 | 0.045 | 4.609 | 99.0% |
| 1024 | 4.618 | 0.045 | 4.574 | 99.0% |
| 8192 | 5.931 | 0.053 | 5.879 | 99.1% |

The approximately 99% reduction applies only to the measured no-op helper overhead, **not overall model latency or throughput**.

### 2. DSV4-shaped eager decode scenario

A synthetic host-side benchmark models repeated postprocessing calls for a DSV4-Flash-shaped eager decode workload:

- Tokens per forward: 64
- Top-k: 6
- Participating MoE layers: 40
- Metadata: Both arguments set to `None`

| Implementation | Time per forward (ms) | Time per layer (µs) | Time per 1,000 forwards (ms) |
|---|---:|---:|---:|
| Original compiled wrapper | 0.1831 | 4.578 | 183.11 |
| New Python guard | 0.0010 | 0.026 | 1.03 |

**Observed reduction in the isolated benchmark:** approximately 0.182 ms per modeled forward, equivalent to approximately 0.18 seconds over 1,000 forwards.

For a Full256 CUDA Graph capture configuration with 36 captured shapes and three Python forwards per shape, this corresponds to an estimated **19.7 ms reduction in cumulative host-side postprocessing overhead**, assuming all 40 relevant layers take the no-op path in each forward.

This capture-time figure is an extrapolation from the microbenchmark, not a directly measured end-to-end CUDA Graph capture-time improvement.

### Limitations

- These measurements isolate Python-side postprocessing overhead and do not represent full-model inference latency or throughput.
- The benefit depends on how often both metadata arguments are `None` in the actual deployment.
- The DSV4-shaped scenario models repeated helper calls; it is not an end-to-end DSV4 serving benchmark.
- The no-EPLB/no-padding condition should be verified against the exact production server configuration before claiming a deployment-wide improvement.
- No direct full-graph replay speedup is expected.
