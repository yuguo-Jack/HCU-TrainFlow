# [Fix] multimodal: bound image preprocessing GPU memory; reject decompression bombs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46646) · state: open · merged: False

## Original PR description

## Motivation

Kimi GPU image preprocessing runs in the tokenizer process on GPU 0, alongside TP rank 0's static pools.
- A many-image request batched every same-size image into one fp32 tensor. A 48-image request exhausted GPU 0 and returned a 500 CUDA OOM.
- Each tokenizer worker's caching allocator kept its peak buffers. After hours of image traffic, GPU 0 had about 1 GB free vs about 13 GB on the other ranks, and large image requests OOMed.
- PIL's `DecompressionBombError` surfaced as a 500.

## Modifications

- Each NaViT size group is processed in sub-batches of at most `SGLANG_MM_GPU_PREPROCESS_CHUNK_BYTES` (default 512 MiB) of fp32 pixels.
- The GPU cache is released after each preprocessing call. On OOM it is retried once, then the request falls back to CPU preprocessing.
- Sources above 4096x4096 are resized on the CPU with the same antialiased bicubic kernel.
- `DecompressionBombError` maps to the existing "Could not decode image" `ValueError`, which returns a 400.

## Accuracy Tests

7 new tests fail on `main` and pass with this PR (`test_mm_process_config.py`, `test_kimi_k3_gpu_preprocess.py`, `test_common.py`). Chunked and CPU outputs match single-batch GPU output. 2 `midashenglm` tests fail on `main` too.
End to end on Kimi-K3 MI355X: requests with 96 and 128 images return 200, decompression bombs return 400, and GPU 0 stays level with the other ranks.

## Speed Tests and Profiling

A request whose images fit in one sub-batch takes the same path as before.

The 512 MiB limit appears to count each image only after it has been resized. Several large photos below the 4096×4096 limit can still be moved to the GPU and joined together before that resize. Could that joined batch use more GPU memory than the limit accounts for?

- aryatsc · comment · 2026-10-28T15:15:06Z · [source](https://github.com/sgl-project/sglang/pull/46646#discussion_r4402390592)

File: `python/sglang/srt/multimodal/processors/kimi_k25.py` · line None

Good catch, thanks. The budget only counted the resized fp32 output, so several large originals with a small target could exceed it. Chunks are now sized per image by the original's bytes, its copy in the joined batch and its fp32 resize input, plus the fp32 output. A new test covers large originals with a small target.
