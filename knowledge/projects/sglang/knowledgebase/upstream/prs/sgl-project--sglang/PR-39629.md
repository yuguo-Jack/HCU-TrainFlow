# fix(loader): let the unbalanced-loading barrier timeout be configured

[Upstream PR](https://github.com/sgl-project/sglang/pull/39629) · state: closed · merged: False

## Original PR description

## What

Read `UNBALANCED_MODEL_LOADING_TIMEOUT_S` from the environment instead of hardcoding it. Default stays 480, so nothing changes unless the variable is set.

## Why

```python
UNBALANCED_MODEL_LOADING_TIMEOUT_S = 480  # leave more time for post data processing
```

480 s is generous for a local disk and short for a shared one. Four nodes pulling the same 539 GB bf16 checkpoint off one NFS export move about 2.1 TB between them; on a cold page cache one TP group did not reach `dist.monitored_barrier` inside the eight minutes, and the group was SIGQUIT'd with

```
TP rank 1 could finish the model loading, but there are other ranks that
didn't finish loading
```

That message reads like a hang or an OOM and is neither — the node still had **2430 GB of its 3023 GB free** at the time. It was only slow.

The failure is also biased towards the configurations that need the loader most: the same checkpoint in FP8 is 274 GB and never came close to the limit. Only the bf16 path, which is what you fall back to when a quantised path is unavailable, hits it.

## Behaviour

| unset | 480 s, exactly as today |
|---|---|
| `SGLANG_UNBALANCED_MODEL_LOADING_TIMEOUT_S=3600` | four-node 539 GB cold load completes |

Once the page cache is warm the same load takes 290 s, well inside the default. The cold path is the one that decides whether the run starts at all.

## Test

* Default (unset): behaviour identical to before.
* `SGLANG_UNBALANCED_MODEL_LOADING_TIMEOUT_S=3600`: four-node DeepSeek-V4-Flash BF16 load completes on cold NFS cache.
