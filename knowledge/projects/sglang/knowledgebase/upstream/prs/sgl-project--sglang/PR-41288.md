# Fix/compressed tensors mxfp4 marlin

[Upstream PR](https://github.com/sgl-project/sglang/pull/41288) · state: open · merged: False

## Original PR description

## Motivation

Stacks on #40022, which added weight-only **NVFP4** dense linear support on
pre-Blackwell via FP4 Marlin and deliberately excluded **MXFP4**, because MXFP4
needs CUDA kernel work rather than pure Python. This is that follow-up: a
compressed-tensors `mxfp4-pack-quantized` checkpoint now loads and runs on SM80+.

MXFP4 dense linears had no path at all — they fell through to the NVFP4 branches.
Unlike NVFP4, this is not a pre-Blackwell fallback: no native MXFP4 dense-linear
kernel exists on any architecture, so both `mxfp4a16` and the w4a4 variant are
served weight-only everywhere.

Three separate things blocked MXFP4 in the dense FP4 Marlin path:

1. **No `group_size=32` kernel instantiation.** `FP4_GET_IF` only emitted
   `group_blocks == 1`, so a gs=32 call computed `group_blocks = 2`, missed every
   branch, and fell back to the no-op `MarlinDefault`, surfacing as a generic
   "no kernel found" error.
2. **The dense template could not decode E8M0 scales.** It called the
   unparameterized `dequant_fp8_scales<scalar_t2>` — the E4M3 decoder. The
   `kFE8M0fnu` specialization exists only on the `s_type`-parameterized overload.
   The MoE kernel already threads `s_type`; dense did not.
3. **Dense made `weight_global_scale` mandatory for all FP4.** MXFP4 has none —
   its E8M0 scales are absolute powers of two — and `marlin_template.h`
   dereferenced `scale2_ptr[0]` unconditionally. Since the Python binding maps a
   `None` global scale to an *empty* tensor, that was an out-of-bounds read, not
   just a wrong value.

## Modifications

**Kernel** (`python/sglang/kernels/jit/csrc/gemm/marlin/`), following the MoE
kernel, which had already solved all three:

- Thread `s_type_id` through the dense template, deriving `S_TYPE` inside
  `_GET_IF` from `W_TYPE` + `GROUP_BLOCKS`. All seven `*_GET_IF` families funnel
  through that one macro, so no call site changes and `MarlinFuncPtr` is
  untouched — `s_type_id` is a template parameter, not a runtime argument.
- Guard the global-scale **load** and **apply** sites on
  `w_type == kFE2M1f && s_type == kFE4M3fn`, and narrow `dequant_skip_flop` from
  `!is_int_type` to MoE's explicit enumeration. `is_int_type` covers exactly
  `{kU4, kU8, kU4B8, kU8B128}` and the only non-int weight types reaching here
  are `kFE4M3fn` and `kFE2M1f`, so this is a strict refinement: identical for
  everything except MXFP4, where it must be false.
- Add `MXFP4_GET_IF` (`group_blocks == 2`), dispatched under a bf16 guard.
  That guard is load-bearing, not stylistic: `dequant.h` provides `kFE8M0fnu`
  for `nv_bfloat162` only, so a `half` instantiation would reference a declared-
  but-undefined specialization and fail to compile. MXFP4 is therefore bf16-only,
  matching the MoE kernel's own guard, and fp16 is rejected on the host with an
  actionable message rather than falling into `MarlinDefault`.
- Add the two host `RuntimeCheck`s dense lacked (`group_size ∈ {16, 32}`, and
  gs=32 implies bf16) and relax the global-scale requirement to gate on
  `group_size == 16`.

**Python:** parameterize the two genuine group-size sites in
`marlin_utils_fp4.py`, add `prepare_mxfp4_layer_for_marlin`, widen
`weight_global_scale` to `Optional`, and add `CompressedTensorsW4A16Mxfp4` plus
the `_is_mxfp4_linear` predicate. One scheme serves both `mxfp4` and `mxfp4a16`:
their weight blocks are byte-identical and they differ only by the presence of
`input_activations`.

MXFP4 scales arrive as raw U8 bytes holding E8M0 exponents with no float8 dtype
attached. The existing `_normalize_scale_tensor` already reinterprets that
container correctly, so the dense path reuses it rather than adding a second
conversion.
`mxfp4_pack_quantized` is added to `_ACTIVATION_QUANTIZATION_FORMATS` because the
`input_activations` parse is gated on that list, so w4a4 MXFP4 checkpoints were
silently discarding theirs. Audited across 130 local checkpoints: inert for
scheme selection, recovers 18 `input_activations` parses.

### Note for reviewers on one file

The diff includes `test_compressed_tensors_fp4_linear_numeric.py`, which
otherwise belongs to #40022. It adds `is_sm100_supported()` to that file's skip
guards. The pre-existing guards admitted SM8X/SM9X/SM120 but not SM100, so on
datacenter Blackwell every test skipped while pytest exited 0 — a green run
asserting nothing. It is carried here because this PR is what made the omission
observable.

## Accuracy Tests

- **SM90 (H100 80GB):** granite-4.2-30b `mxfp4a16` and `mxfp4`, both generating
  coherent text. Coherent text is asserted, not merely a clean load — the NVFP4
  work established that a scale-bias error yields `inf` logits and token 0
  forever, which a load-only check passes.
- **SM100 (GB200):** 8 numeric tests passed (3 mxfp4 + 5 nvfp4), 0 skipped —
  versus 8 skipped before the guard fix. 16 scheme tests + 4 subtests.
- **No regression:** int4 `pack-quantized` and fp8 re-verified, since
  `dequant_skip_flop` and the `s_type` threading touch code paths all FP4 *and*
  FP8 weights flow through.

## Speed Tests and Profiling

No benchmark run. The path is weight-only: activations stay bf16 and the kernel
is the existing FP4 Marlin GEMM, so throughput should match the NVFP4 weight-only
path at equal shapes. No new kernel is introduced — only added template
instantiations, which cost per-shape JIT latency, not binary size (dense FP4 goes
from 30 instantiations to 45).

There is a bias correctness issue in the new dense MXFP4 preparation path.

[`prepare_mxfp4_layer_for_marlin`](https://github.com/sgl-project/sglang/blob/5308ebaa44996f05f302cbf1cc690a8738a562e1/python/sglang/srt/layers/quantization/marlin_utils_fp4.py#L286-L290) applies `marlin_permute_bias()`, but [`apply_fp4_marlin_linear`](https://github.com/sgl-project/sglang/blob/5308ebaa44996f05f302cbf1cc690a8738a562e1/python/sglang/srt/layers/quantization/marlin_utils_fp4.py#L111-L136) does not pass bias into the kernel. It adds it afterwards with `output.add_(bias)`, where the output is in normal channel order. That gives each channel the wrong bias.

I reproduced the Python-side mismatch using the exact function bodies from this head, with the CUDA repack/workspace calls stubbed and GEMM returning the mathematically expected zero product for zero input:

```text
N = K = 128, BF16, x = 0, bias = arange(128)
expected: [0, 1, 2, 3, 4, 5, ...]
actual:   [0, 1, 8, 9, 16, 17, ...]
96 / 128 channels differ
```

This is a CPU-only isolation of bias handling; I have not run the CUDA kernel. Bias-free Granite runs would not catch it, and the dense Marlin numerical test currently does not create or pass bias.

Could we preserve `layer.bias` in logical channel order and length, and add it after cropping the GEMM output to logical N? Keeping the logical length also matters for `skip_bias_add=True`, where the linear layer returns `layer.bias` to its caller. Please cover bias with both aligned and padded N, plus `skip_bias_add`.

The older NVFP4 helper has the same pattern; this PR carries it into the new MXFP4 path.
