# [Feat] metrics: expose detokenizer worker processing time

[Upstream PR](https://github.com/sgl-project/sglang/pull/47877) · state: open · merged: False

## Original PR description

## Motivation

#43304 asks for per-stage metrics on the multi-tokenizer / multi-detokenizer
IPC path so a saturated stage can be identified from metrics instead of
out-of-tree tracing. Its proposed metric 4 calls for per-message processing
time histograms in `MultiDetokenizerRouter` and in each detokenizer worker.
The router half is covered by #45036; the detokenizer worker half is not
covered by any open or merged PR (#43323 router CPU, #44390 router
throughput, #44524 per-process CPU labels, #46596 scheduler-to-router
delivery latency cover the other proposals).

This PR adds the detokenizer-side processing-time histogram, mirroring the
semantics of the router histogram in #45036 so the two stages can be
compared directly: which stage's processing time grows is where the work
piles up.

## Modifications

- `python/sglang/srt/managers/detokenizer_manager.py`: when
  `--enable-metrics` is on, `DetokenizerManager` now creates a
  `sglang:detokenizer_processing_seconds` histogram next to the existing
  CPU monitor start, using the same bucket set as the router histogram in
  #45036, and wraps dispatch plus send in the timing context defined on
  the mixin. The receive wait stays outside the timed section, so
  queueing delay in the ZMQ socket is excluded.
- `python/sglang/srt/managers/multi_tokenizer_mixin.py`: defines the `_timed_processing` context manager on the
  mixin (a no-op that never reads the clock when no histogram is set,
  and it records an observation even when handling raises), and the
  multi-http-worker event loop (the shape used with
  `--detokenizer-worker-num > 1`) wraps its dispatch and fan-out in it,
  so both detokenizer loops report the metric.
- `docs/docs/references/production_metrics.mdx`: documents the new
  histogram, its semantics, and a p99 promql example.
- `test/registered/unit/managers/test_multi_tokenizer_mixin.py`: CPU unit
  tests driving both event loops with fake sockets: one observation per
  message, an observation is recorded when the handler raises, the
  disabled path still dispatches without observing, and the
  multi-worker loop records processing time.

## Accuracy Tests

Not applicable: this change only adds observability. It does not touch
tokenization, detokenization, or model output logic; with metrics disabled
the event loops run the same code as before.

## Speed Tests and Profiling

No server benchmark run. With `--enable-metrics` off, the added cost per
message is one attribute check in a context manager. With metrics on, it
is two `perf_counter` reads and one histogram observation per message,
the same pattern #45036 applies to the router loop. The detokenizer is
not the throughput-critical path this issue is about; the saturated stage
in the reported case was the router, whose identical instrumentation was
accepted as cheap enough there.
