# [Perf] [NVIDIA] attention: Add opt-in LiteTopK decode top-k for DSA and DeepSeek-V4.1 on SM100

[Upstream PR](https://github.com/sgl-project/sglang/pull/40764) · state: open · merged: False

## Original PR description

@DarkSharpness could you take another look? This revision follows sgl-project/DeepGEMM `dev` after deepseek-ai/DeepGEMM#462, where SM100 paged MQA logits are BF16-only. It is stacked on #44350 (zcnrex), which moves the DSA / DSV4 indexers onto that API. Until #44350 lands, this branch also carries #44350's two commits (rebased onto `main` 3671503e44); this PR is the last commit.

## Motivation

DSA models (GLM-5 family, DeepSeek-V3.2) and DeepSeek-V4.1's ratio-1/2 index layers score every KV position of each decode / verify token with DeepGEMM's paged MQA kernel, then pick the top-k (2048 for DSA, 512 for V4.1) in a separate kernel. With #44350, the kernel writes BF16 logits and SGLang widens them to FP32 for `topk_transform_paged_v2`. topk v2's first pass over the scores only builds a coarse histogram.

With sgl-project/DeepGEMM#94, the scoring kernel counts that histogram while it writes the scores. LiteTopK reads the histogram, finds the bin holding the k-th score, takes everything above that bin, and ranks the bin exactly, all in one pass over the BF16 scores. Nothing is widened.

**The selection is exact**, with ties going to the lower physical slot. If the histogram disagrees with the scores, or the crossing bin is too large, LiteTopK falls back to an exact radix select.

## Changes since the last revision

- **Rebuilt for BF16-only logits.** 15 files, +2864 / -18 on top of #44350.
- **Selector:** `Fp32Top2048` is removed. The new `Bf16Top2048` (64-slot pages) serves DSA. `Bf16Top512` (V4.1) is unchanged, and its 4 kernels have the same SASS as before.
- **DSA:**
  - The histogram is passed through #44350's adapter. When a histogram is given, the adapter returns DeepGEMM's BF16 logits unwidened.
  - LiteTopK requires #44350's UE8M0 index cache.
  - Any number of draft tokens is served (`DSA_MAX_NEXT_N` is removed).
- **V4.1:**
  - Uses `dev`'s `fp8_fp4_paged_mqa_logits(..., indices=, histogram=)`.
  - Decode reuses the forward's DeepGEMM schedule.
  - Verify schedules the tokens of a request as one request, so their KV is read once.
- **DeepGEMM detection:** the wrappers must declare `indices` and `histogram`, and must not declare `logits_dtype`. Builds without DeepGEMM#94 (including the pinned 0.2.2) and the previous #94 revision are refused with one warning.
- **Kept from the last revision:** grids follow the device's SM count, the causal verify-length fix (`.clone()`), and the class default of `paged_mqa_causal_ctx_lens`.

## Modifications

- `kernels/jit/csrc/litetopk_decode/select.cuh`: one selector templated over `Bf16Top2048` and `Bf16Top512`.
  - Rows of up to 16384 scores are selected from registers by one CTA; longer rows are split across CTAs.
  - The scratch returns to zero after every call, so CUDA graphs need no reset kernel. PDL is on.
- `kernels/ops/attention/litetopk_decode.py`: configs, storage / plan, device and DeepGEMM API detection, and `select(...)`, which writes physical KV slots (padded with `-1`).
- `srt/layers/attention/litetopk_decode.py`: per-process selector buffers, grown only outside graph capture.
- Serving is opt-in with `SGLANG_OPT_LITETOPK_DECODE=1` (default off):
  - **DSA** (`dsa/dsa_indexer.py`, `dsa_backend.py`, `deep_gemm_mqa_logits.py`): decode and target verify, for 32 index heads of dim 128 and top-2048. Verify tokens get causal lengths.
  - **DeepSeek-V4.1** (`dsv4/v41_indexer/*`, `deepseek_v4_backend.py`, `dsv4/metadata.py`): FullTopK and SparseTable decode / verify.
  - Everything else keeps the default top-k.

## Accuracy

- **Kernel test (B200): 23 / 23.** Both configs are checked against an exact (score, lower slot) reference, with SM counts forced to 7 / 63 / 148 / 296 and rows of up to 1M scores. The cases cover:
  - ties, ±0 and infinities;
  - stale histograms and the overflow fallback;
  - graph replay;
  - with DeepGEMM#94: the DSA MXFP8 chain (the histogram equals the reference, and the BF16 logits equal the default path's widened logits) and the V4.1 routes inside a CUDA graph.
- **CPU unit test:** 14 / 14. Together with the related CPU tests of `main` / #44350: 201 passed (#44350 alone: 187).
- **`main` / #44350 GPU tests (11 files), flag off:** the same results on #44350's head and on this branch. Flag on: `test_dsa_metadata_replay.py`, `test_dsa_metadata.py`, `test_dsa_kpool_metadata_fusion.py` and `test_dsa_indexer.py` pass.
- **Serving smoke** on one B200, eager and CUDA graph, with DeepGEMM#94. Models: truncated GLM-5.2 (8 layers, with and without MTP) and DeepSeek-V4.1 (6 layers). 18 runs, all 256 / 256 tokens.
  - Flag on: all 203,202 LiteTopK selections equal the exact top-k of the same BF16 logits (197,746 eager rows + 5,456 after graph replays). Every histogram row sum equals the row's live count.
  - Verify rows are causal: 18,944 / 18,944 eager and 3,968 / 3,968 replayed.
  - V4.1: LiteTopK's logits are bit-identical to the default route's on all live columns, and its picks equal `topk_v2`'s by value on 1,008 / 1,008 rows.
  - Flag off: routes and call counts match #44350 in all 6 configurations.
  - For reference: on the same GLM workload, `topk_transform_paged_v2` on the widened logits returned picks below the true 2,048th score on 92 of 992 decode rows (long rows, its cluster path).

## Speed (kernel level, B200)

What is timed: indexer scores + top-k of one layer per decode / verify step.
- **Method:** each arm is a single-call CUDA graph replayed after a 1 GiB flush (cold L2), timed by CUPTI from its first to its last kernel. Arms are interleaved, with an A/A arm.
- **Checks:** every cell is checked for exactness before and after timing. No other process was on the GPU.
- **Data:** real captures only. GLM-5.2 index layers 0 and 38, converted to MXFP8 the way #44350 does; DeepSeek-V4.1 layer 20 in MXFP4.
- **Baseline:** #44350 with the flag off, i.e. DeepGEMM `dev`'s producer → `to_fp32_logits` → `topk_transform_paged_v2`. Speedup = baseline / LiteTopK.

### GLM-5.2 (DSA), top-2048

Grid: B 1-128 × L 8K-~1M × `next_n` 1-4, 383 cells.

- **vs #44350: geomean 2.934×.** LiteTopK is faster in all 383 cells (minimum 1.191×). Within one rank's KV pool (287 cells) the geomean is 3.048×.
- **Why the gain is this large:** #44350 widens the whole BF16 logits buffer to FP32 on every call.
  - Under CUDA-graph decode that buffer is as wide as the page table (1M tokens here), so the copy costs 92-95 µs whatever L is.
  - The speedup therefore falls with L: 5.67× at 8K, 1.29× at ~1M.
  - At B 1, ~1M: 41.6 vs 59.5 µs (1.43×).
- **Selector alone, on identical BF16 logits:** 1.623× against `topk_transform_paged_v2` on a pre-widened FP32 copy. LiteTopK is faster in 378 of 383 cells.
- **DeepSelect BF16 top-2048, for reference** (SGLang does not route DSA to it): LiteTopK is 1.317× faster.
  - It is slower in 44 cells, all at 8K / 16K. The worst is 0.870× (layer 38, B 16, 16K: 24.32 vs 21.22 µs).
  - On layer 38, every score falls in a unit bin, with 76-136-way ties at the k-th value.

### DeepSeek-V4.1, top-512

Grid: 1-6 tokens per request × B {1, 16, 64} × L {4K, 16K, 64K, 256K, ~1M} = 90 core cells, plus 52 extra cells (DSpark, high batch, DeepSelect tier boundaries). Every cell is averaged over two runs.

- **vs #44350 (FP32 widen + topk v2): 4.515×** on the core cells. LiteTopK is faster in all 142 cells.
- **vs DeepSelect on BF16 logits (#44051): 1.395×** on the core cells.
  - This is `main`'s opt-in route; on #44350 it is unreachable, because #44350 widens.
  - **Within the KV pool it is 1.134× (62 cells).** The headline is carried by the cells beyond the pool, where the speedup is 2.203×.
  - LiteTopK is slower in 28 of 142 cells, all within the pool at L ≤ 64K. The worst is 0.821× (5 tokens, B 16, 4K: 17.02 vs 13.98 µs).
  - Most of those losses come from the histogram's cost in the producer.
- **Isolating the parts:**
  - At ≥ 2 tokens per request, part of the gain is the request-grouped schedule (one KV pass per request). With the same producer feeding DeepSelect instead, the speedup is 1.051×.
  - Selector alone: 1.433× against DeepSelect, and 2.012× against topk v2 on pre-widened logits.

## Notes

- **Dependencies:** this needs #44350 and an sgl-deep-gemm release that contains sgl-project/DeepGEMM#94. Without such a release, the flag only logs a warning.
- **Histogram cost:** the producer pays for the histogram, and it is included in every chain number above.
  - GLM: +2.28 % geomean.
  - V4.1: +1.25 % at 1 token per request and +14 % at 5-6 tokens, until DeepGEMM's 6-token Q tile returns in a follow-up.
- **Scope:** measured on B200 only. Other SM100-family GPUs get SM-count-derived grids, unmeasured. All speed numbers are kernel-level. V4.1 target verify, TP > 1, DP attention, DCP and TBO were not served.
