# [Perf] diffusion: opt-in Wan UMT5 padding trim (SGLANG_DIFFUSION_WAN_TEXT_PADDING)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46328) · state: closed · merged: True

## Original PR description

Draft: the output is not bit-identical (see Results), and MOVA is only covered by the existing tests so far.

## Summary

Wan padded every prompt to 512 tokens, ran UMT5 over all 512, then sliced the padding off in `t5_postprocess_text` and zero-padded back to 512. This tokenizes with `padding="longest"` on `WanT2V480PConfig`, so UMT5 only runs over the real tokens. Typical prompts are 10 to 150 tokens.

The DiT still gets 512 long, zero-padded embeddings. `t5_postprocess_text` now returns a `TextConditioningOutput` with a 512 long mask and the real lengths, because the pipeline checks the mask length against the embedding length and `padding="longest"` alone fails that check.

## Results

A100-80GB, real `TextEncoderLoader.load` of the UMT5 encoder from `Wan-AI/Wan2.1-T2V-1.3B-Diffusers`, median of 20 runs, ABBA order:

| Prompt | Real tokens | Encode ms before | Encode ms after | Max abs diff | Cosine |
|---|---|---|---|---|---|
| short | 11 | 324 | 31 to 33 | 2.0e-5 | 0.99999994 |
| long | 75 | 328 | 70 | 2.2e-5 | 1.0 |
| negative prompt | 62 | 330 | 48 | 5.4e-6 | 1.0 |
| batch of 2 | 11 and 75 | 617 | 117 | 1.8e-5 | 1.0 |

Each request encodes a positive and a negative prompt, so the saving is about 0.3 to 0.6 s per request. That is small next to a full generation.

End to end (Wan2.1-T2V-1.3B, one prompt, seed 42, 480x832, 33 frames, 20 steps, through `sglang generate`):

| Comparison | PSNR |
|---|---|
| base vs base | identical |
| this branch vs this branch | identical |
| base vs this code with padding kept at 512 | identical |
| base vs this branch | 30.3 dB mean, 28.5 dB min |

So the mask and output type change is faithful, and the difference comes only from the shorter padding. The embeddings differ by about 1e-5, but the different matrix shapes change the bf16 rounding and 20 denoising steps amplify it. The video is a different but valid sample. I did not judge which one is better.

## Tests

CPU, one case in the existing `test_wan_pipeline_config.py`: the config trims padding, and the postprocess keeps 512 long embeddings, a matching mask and the real lengths. I also ran `test_text_encoding_cache.py` and `test_wan_pipeline_config.py` on base and on this branch: 50 passed on base, 51 on this branch (the new case). `test_wan_streamed_encode.py` fails at collection on both.

## Not done

- MOVA reuses `t5_postprocess_text` and now gets the same `TextConditioningOutput`. It keeps its 512 padding. I have not run MOVA end to end.
- Only one prompt was generated end to end, and memory was not measured.
- Other Wan configs inherit the change through `WanT2V480PConfig`. Only the 1.3B T2V model was run.
