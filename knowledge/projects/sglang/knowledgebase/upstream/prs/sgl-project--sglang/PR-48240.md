# [Perf] hybrid: drop residual host syncs from GDN extend

[Upstream PR](https://github.com/sgl-project/sglang/pull/48240) · state: open · merged: False

## Original PR description


## Motivation

#45472 moved most of the hybrid (GDN) extend preparation off the host-device sync path. A sync census of upstream main serving Qwen3.8-Flash-Next with MTP (torch sync debug mode, counted per scheduler stage and call site) still finds about 6 host syncs in every eager GDN extend, outside the attention backend:

| Call site | Syncs per extend (RTX PRO 6000 / GB300) |
|---|---|
| `fla/index.py` `prepare_chunk_indices` (`.tolist()` + H2D at the first GDN layer) | 2 / 2 |
| `fla/index.py` `prepare_chunk_offsets` (`new_tensor([0])`) | 1 / 1 |
| `mem_cache/ple_state_pool.py` `reset_slots` (scalar assignment through a device index) | 1.97 / 1.94 |
| `hybrid_linear_attn_backend.py` `_init_track_conv_indices` (`clamp` against a device scalar) | 0.98 / 0.97 |

Each one makes the host wait for the GPU queue to drain before it can keep launching the extend. With this PR, these call sites drop to 0.02-0.14 syncs per extend (0.02-0.05 on RTX PRO 6000, 0.05-0.14 on GB300); what remains is the FLA derivation of extends under 64 tokens. The census ran with both this PR and a separate QSA change applied; their call sites are disjoint and the numbers here count only the rows above.

## Modifications

- `layers/attention/linear/gdn_backend.py`: the eager Triton extend builds the FLA `chunk_indices` / `chunk_offsets` once per forward from `extend_seq_lens_cpu`. It calls the same FLA helpers on a host copy of `cu_seqlens` and uploads the results pinned and non-blocking. The tables are cached on the forward metadata, so every GDN layer shares them, and they reach the kernel through the existing `chunk_indices` / `chunk_offsets` arguments that the prefill CUDA-graph path already uses. Batches below one 64-token chunk keep FLA's own derivation, because the output kernel then uses a smaller chunk; so outputs stay bit-identical.
- `layers/attention/mamba/mamba2_metadata.py`: an `extend_chunk_tables` field on `ForwardMetadata` for that cache.
- `layers/attention/hybrid_linear_attn_backend.py`: `_init_track_conv_indices` takes the host token count (already computed as `logical_num_tokens`) for its clamp.
- `layers/attention/hybrid_linear_attn_backend.py` + `mamba2_metadata.py`: `ForwardMetadata.host_extend_lens_trusted` records the existing condition under which `extend_seq_lens_cpu` is trusted (one entry per request, no two-batch-overlap split). Host tables are built only then, only when that count equals the forward's token rows, and only for the CUDA Triton extend kernel (the CPU and NPU chunk kernels take no tables).
- `mem_cache/ple_state_pool.py`: `reset_slots` uses `index_fill_`, which has the same result and needs no host value copy. This file has its own CODEOWNERS (`srt/mem_cache/`); it can be split into a two-line companion PR if preferred.
- Tests: `test/registered/unit/layers/attention/test_hybrid_extend_host_syncs.py` (new, `1-gpu-small`). Each piece runs under `torch.cuda.set_sync_debug_mode("error")` and is compared with the device-derived result: the tables (values and dtypes), the sub-chunk skip, the track indices and both PLE resets.

## Accuracy Tests

The change is exact by construction: same values and dtypes, same kernels.

- `test/registered/kernels/ops/attention/test_gdn_prefill_graph.py` compares the CUDA-graph GDN extend with the eager `GDNAttnBackend.forward_extend` bit for bit (output, conv/SSM pools, track slots). The eager side now takes the host tables, and the test passes on RTX PRO 6000. `test_mamba_track_state_dtype.py` and `test_gdn_prefill_layout.py` also pass.
- End to end, deterministic greedy vs upstream main on the same GPU: `nvidia/Qwen3.8-Flash-Next-NVFP4`, 1× GB300, TP 1, `--enable-deterministic-inference --attention-backend flashinfer --mem-fraction-static 0.80 --mamba-ssm-dtype bfloat16 --chunked-prefill-size 4096 --disable-prefill-cuda-graph` (so every extend takes the eager path that uses the host tables), NEXTN MTP 3/1/4. 8 prompts of 63 to 14,420 tokens, each sent twice: 16/16 responses identical to main in tokens and logprobs. RTX PRO 6000 ran the module tests above only.

## Speed Tests and Profiling

Host syncs at the call sites this PR touches (Motivation table) go from about 6 per extend to 0.02-0.14 (0.02-0.05 on RTX PRO 6000, 0.05-0.14 on GB300). Decode is already sync-free on upstream.

Same-GPU pairs, `python -m sglang.benchmark.serving`, Qwen3.8-Flash-Next NVFP4 (GB300: `nvidia/Qwen3.8-Flash-Next-NVFP4`; RTX: `RadixArk/Qwen3.8-Flash-Next-NVFP4`) + NEXTN MTP (3/1/4), TP 1. Arms alternated main / PR × 2; each arm is a fresh server.

GB300 (defaults, `max_running_requests` 48):

| Workload | main (2 runs) | this PR (2 runs) |
|---|---|---|
| multi-turn: GSP 16 groups × 4, 2048-token system + 512 question, 256 out, 3 turns, concurrency 16; output tok/s | 1339 / 1341 | 1351 / 1351 |
| same, duration s | 36.71 / 36.67 | 36.39 / 36.37 |
| shared prefix: GSP 8 × 8, 4096 + 256, 8 out, 2 turns, concurrency 4; duration s | 8.25 / 8.03 | 8.03 / 8.03 |
| prefill: random 2048 in / 1 out × 64, concurrency 4; duration s | 3.87 / 3.89 | 3.92 / 3.84 |

RTX PRO 6000 Blackwell Max-Q 300 W (`--quantization modelopt_fp4 --ple-offload-embedding --mem-fraction-static 0.93 --chunked-prefill-size 4096 --cuda-graph-max-bs-prefill 4096`). In this configuration (no mamba-specific pool flags) the mamba state pool gets 10 slots, and with MTP (5 slots per request) that caps `max_running_requests` at 2, so every RTX step is low-concurrency:

| Workload | main (2 runs) | this PR (2 runs) |
|---|---|---|
| multi-turn, output tok/s | 181.1 / 181.3 | 182.3 / 179.2 (neutral) |
| shared prefix, duration s | 45.86 / 48.56 | 45.29 / 46.75 |
| prefill, duration s | 11.75 / 11.81 | 11.80 / 11.73 |

No end-to-end throughput change is claimed. An independent GB300 re-measurement at this head (A-B-B-A, 6 warm runs per arm) gave main 1351.1 tok/s (range 1327-1364) vs this PR 1328.2 (1077-1343), and on an otherwise idle node main 1334.0 (n=4) vs this PR 1331.8 (n=8); median ITL 5.43-5.44 ms and accept length 2.42-2.44 on both arms. Main's own warm run-to-run spread is 1.9-2.7%, so the 2-run difference in the table above is within noise. The change removes host syncs from the extend path (counts above); on the 2-request RTX engine it is also within noise.
