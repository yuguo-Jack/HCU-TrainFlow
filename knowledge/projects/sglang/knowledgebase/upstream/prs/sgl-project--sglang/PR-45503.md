# [Fix] distributed: Prevent unavailable PyNccl enablement

[Upstream PR](https://github.com/sgl-project/sglang/pull/45503) · state: closed · merged: True

## Original PR description

## Motivation

`PyNcclCommunicator` tracks two related states:

- `available` indicates whether its NCCL communication resources are available.
- `disabled` indicates whether the communicator is currently allowed to handle collectives.

An available communicator may be temporarily enabled during device-graph capture and disabled afterward. An unavailable communicator, however, must always remain disabled.

Before this change, `change_state(enable=True)` could produce the invalid state `available=False, disabled=False`. Subsequent collectives could then enter a partially initialized PyNccl path and access resources that were never created.

This change makes availability a hard prerequisite for enablement, preventing the invalid state while preserving existing behavior for available communicators.

During device-graph capture, an unavailable `PyNcclCommunicator` could be temporarily enabled by calling `change_state(enable=True)`.

When NCCL initialization is unavailable, the communicator is only partially initialized and has `available=False`. Enabling it set `disabled=False`, causing subsequent collectives to enter the PyNccl path and access attributes that were never initialized.

An unavailable communicator must always remain disabled.

## Modifications

- Reject explicit attempts to enable an unavailable `PyNcclCommunicator` with a descriptive `RuntimeError`.
- Centralize PyNccl capability checks in `GroupCoordinator`:
  - Return the communicator only when it initialized successfully.
  - Provide a fail-fast helper for operations that require PyNccl.
- Update graph capture and collective-selection paths to use the centralized availability check.
- Preserve existing alternate collective paths when PyNccl is not selected.
- Make PyNccl-required operations fail clearly when the communicator is unavailable.
- Audit direct PyNccl consumers, including bootstrap, symmetric-memory, DSA broadcast, MiniMax indexer, and page-interleave paths.
- Add CPU-only regression coverage for:
  - Explicit enablement of an unavailable communicator.
  - Available communicator enablement and state restoration.
  - Exception-path restoration.
  - `GroupCoordinator` availability semantics.
  - Graph capture skipping unavailable PyNccl.
  - Existing pure-eager collective routing.

@alexnails keeping the following [PyNcclCommunicator](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/distributed/device_communicators/pynccl.py#L65-L76) initialization in mind.

```python
        # if world_size == 1, no need to create communicator
        if self.world_size == 1:
            self.available = False
            self.disabled = True
            return
        try:
            self.nccl = NCCLLibrary(library_path)
        except Exception:
            # disable because of missing NCCL library
            # e.g. in a non-GPU environment
            self.available = False
            self.disabled = True
            return

```

For a multi-rank graph-capture case (i.e. world_size > 1) on non-NCCL backend it would simply initialize an unavailable `PyNcclCommunicator` which can not be enabled and the construction is doing the right thing by setting `available = False` and `disabled=True`.  However, its [enabled back again during graph_capture](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/distributed/parallel_state.py#L682).

So, `use_pynccl` is currently a request to attempt initializing `PyNcclCommunicator`, and not necessarily a proof that `PyNccl` is usable. When initialization fails, `GroupCoordinator` still retains a non-None communicator with `available=False`, while several selection paths interpret non-None as available.

Graph-capture in `GraphCoordinator` would just **enable** any initialized communicator **unconditionally** (regardless if its available or not) [`pynccl_comm = self.pynccl_comm`](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/distributed/parallel_state.py#L677). The current implementation of GraphCoordinator's graph_capture is making a strong assumption that an initialized `PyNcclCommunicator` is usable, which might not be the case always?

For a multi-rank pure-eager case (i.e. world-size > 1) we would never run into this issue because the PyNcclCommunicator is initialized but its **disabled**.

There are couple of options we can go about fixing this in a more robust manner:
1. Keep `use_pynccl` as initialization intent.
2. Retain the communicator in `GroupCoordinator` only when `PyNcclCommunicator` initialization reports `available=True`; otherwise store `None`.
3. Keep the defensive `change_state` availability guard for direct users outside `GroupCoordinator`. Are there any?

Let me know your thoughts.
