# [Fix] systemone: Abort scoring requests when the client disconnects and honor a caller-supplied rid

[Upstream PR](https://github.com/sgl-project/sglang/pull/45957) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45842.

On SGLang 0.5.22, a `/v1/systemone` request whose client disconnects is not aborted: requests already queued or running keep running to completion. Chat (`/v1/chat/completions`) requests are aborted on disconnect as expected. Observed on GB10 with four concurrent ~15.6k-token requests: after the clients were killed, the remaining requests still ran (~3.4 s each) and `sglang:num_running_reqs` + `sglang:num_queue_reqs` only reached 0 after 10.3 s. A proxy in front of SGLang cannot stop abandoned decision requests today, so a burst of them keeps the GPU busy for their full length.

Root cause: the systemone handler's scoring requests are **short and non-streaming**, and the generic non-streaming wait only polls the client connection every `SGLANG_REQUEST_STATE_WAIT_TIMEOUT` (4 s) seconds — a request that finishes inside one poll interval is never checked. (Chat survives because streaming responses get the `create_abort_task` background abort, and non-streaming chat generations usually outlive the poll interval.) Additionally, the rid is generated inside the request pipeline and invisible to the caller, so `/abort_request` cannot target these requests either.

## Modifications

Both asks from the issue:

**1. Caller-supplied rid** — `SystemOneRequest` gains an optional `rid` field, like `/v1/chat/completions`:
- joint-schema path: the single `EmbeddingReqInput` carries the rid as-is;
- Kev pointer path: per-question rids derived as `"<rid>_<i>"`;
- score/decider path: the rid threads through `OpenAIServingDecisions._score` → `score_prompts` → `score_request`. For `GenerateReqInput` the scalar rid is passed through and expanded by the existing `_normalize_rid` (`"{rid}_{i}"`); `EmbeddingReqInput` only accepts rid lists, so the mixin expands it the same way. Multi-item-scoring-fused requests label the single sequence `{rid}_0`.
- `/abort_request` matches by rid prefix, so aborting with the base rid stops the whole request. When the caller supplies no rid, one is generated (current behavior, now also used as the abort handle).

**2. Disconnect abort** — the handler wraps each internal wait (joint, pointer, and score paths) in a guard that polls `raw_request.is_disconnected()` every `_DISCONNECT_POLL_SECONDS` (1 s) and aborts via the base rid as soon as the disconnect is observed; the disconnect then surfaces as a 400 whose message names the aborted rid, the same shape the OpenAI handlers produce. The guard cancels the in-flight generator on abort, which routes through `_generate`'s existing exception path and releases request state. Engine-internal calls (no HTTP request object) skip the guard entirely.

## Accuracy / Regression Tests

`test/registered/unit/entrypoints/systemone/test_joint_schema.py` (new `TestRequestIdAndDisconnectAbort`, reusing the file's `HeadManager` fixture):

- caller-supplied rid reaches the internal request; generated rid when absent
- a disconnected client aborts the request with exactly the request's rid, and the 400 message names it
- a connected client is unaffected (full 200 answer body)

`test/registered/unit/test_token_scoring.py` (new cases, existing `ScoringManager` harness):

- scalar rid expands per request on the generation path (`proxy-rid_0/1`)
- embedding path gets the same expansion from the mixin
- MIS-fused requests label the single sequence `proxy-rid_0`
