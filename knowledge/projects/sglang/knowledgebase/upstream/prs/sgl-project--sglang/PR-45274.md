# [Perf] [NVIDIA] DSA: Pick any divisor of the tile count for the TileLang sparse decode split

[Upstream PR](https://github.com/sgl-project/sglang/pull/45274) · state: open · merged: False

## Original PR description

Co-authored-by: @HanHan009527

## Summary

**TL;DR: This PR lets the CUDA TileLang FP8 sparse decode split each query's top-k tiles into groups of any size that divides the tile count, not only halvings of it, as long as the GPU stays busy. For GLM-5.3-Flash, whose 2051-wide top-k pads to 66 tiles, attention DP8 decode with MTP 1/1/2 at 128 concurrent requests now splits each query into 6 groups instead of 33.** Fewer groups mean fewer partial results to write and merge. Splits are unchanged for power-of-two tile counts (top-k 2048, as in DeepSeek-V3.2 and GLM-5 to GLM-5.2) and on ROCm.

- **Performance** (GLM-5.3-Flash on H200, FP8 KV cache): with attention DP8, steady decode throughput is **up to 4.3% higher** (MTP 1/1/2 at 256 concurrent requests; 2.5% at 128, 1.2% at 64), and with MTP 5/1/6 the decode step is **up to 3.3% shorter** (64 concurrent requests). At 128 concurrent requests with MTP 1/1/2, the sparse decode attention kernels take **27% less GPU time** per call (1.36× faster). Per kernel call, across 8 to 64 heads per GPU and 4 to 200 query rows, this PR takes **8–27% less time** wherever it changes the split, and never more. With TP8 attention and MTP 5/1/6, the decode step is up to 1.2% shorter at 2 to 8 concurrent requests. On H20, per kernel call, this PR takes 16–20% less time where it changes the split; with attention DP8 and MTP 1/1/2, the mean time per output token is 1.1% lower at 64 concurrent requests and 1.3% lower at 128.
- **Accuracy:** **unchanged** end to end: GSM8K 97.04% with this PR and 97.35% on main, within one standard error (0.44 points), and the same MTP accept length. The kernel error at the new splits stays within what main already accepts: below that of main's splits for 66 or more rows.
- **Cost:** a one-time ~35 s at the first start with an empty TileLang kernel cache, to compile the kernels for the new group sizes; later starts take the same time as main. Choosing the group size is a short integer loop on the host.

## Motivation

**Earlier DSA models select 2048 KV tokens per query; GLM-5.3-Flash selects 2051, so its tile count is no longer a power of two, and for decode-sized calls the split search, which only tries halvings, falls back to many small groups.** Its indexer appends up to 3 not-yet-pooled tail tokens (KPool) to the 2048 selected ones, and `_forward_tilelang` pads the 2051 columns to the next multiple of 64, 2112: 66 tiles of 32 on CUDA instead of 64.

#42957 added the FP8 KV cache to the TileLang DSA backend on CUDA through the partial + combine path of `tilelang_sparse_fwd`, which serves both prefill and decode. That path splits the `ni` top-k KV tiles of each query into `ni / inner_iter` groups, computes one partial result per group, and merges them with a combine kernel. `_pick_inner_iter` picks `inner_iter`, the number of tiles per group, and tries only `ni, ni // 2, ni // 4, ...`. For 64 tiles these are all the divisors, but halving 66 gives 33, 16, 8, 4 and 2, of which only 33 and 2 divide 66, so the search never tries 3, 6, 11 or 22.

The search also keeps at least one block per SM: `seq * ni / inner_iter >= cu * block_per_cu`, where `seq` is the number of query rows in the call and `block_per_cu` is 1 on CUDA. On a 132-SM GPU this allows at most `seq / 2` tiles per group. So for 4 to 65 query rows the search falls back to 2 tiles per group: 33 partial results per query, each written out and read back by the combine kernel, although 11 tiles per group (6 groups) fits the same limit at 32 rows. With MTP 1/1/2 (multi-token prediction with `--speculative-num-steps 1 --speculative-eagle-topk 1 --speculative-num-draft-tokens 2`, so one draft token), each decoding request contributes 2 query rows, so 128 concurrent requests on attention DP8 (16 per GPU) give 32 rows per GPU. This PR lets the search also take those other divisors (Modifications).

## Modifications

- **`python/sglang/kernels/ops/attention/dsa/tilelang_kernel.py`**: `_pick_inner_iter` gets `any_divisor` and `head_blocks` options. With `any_divisor`, it also tries the divisors of `ni` larger than the existing pick, within the same work limit, and takes the largest one that passes the fill check below. Only the CUDA FP8 call in `tilelang_sparse_fwd` turns it on. The ROCm calls (FP8 and BF16 KV in `tilelang_sparse_fwd`, and DeepSeek-V4's `dpsk_v4_fp8_attention_fwd`) keep the default search.
- **`test/registered/unit/layers/attention/test_tilelang_dsa_decode_split.py`** (new, `base-a-test-cpu`): checks the picks for 66 tiles on 132 SMs, that power-of-two tile counts pick as before, and that the default search is unchanged. Removing any condition of the new search fails a case.

Design notes:

- **Fill check: a larger group is taken only if the GPU stays busy.** Fewer groups launch fewer thread blocks (`seq * head_blocks * ni / inner_iter`: one per 16 heads, query row and group), and each SM runs two of these blocks at once. The existing work limit only guarantees one block per SM, so with few heads per GPU the largest divisor within it can leave slots idle (8 heads at 44 rows: 22 tiles per group gives 132 blocks, one per SM). The check takes a divisor only if its blocks fill at least 80% of the two slots per SM in each wave they need. With it, this PR is at least as fast as main in every case of the kernel test below, and so would be any threshold from 75% to 100%.
- No new flags or environment variables, and no kernel change: the kernels only need `ni % inner_iter == 0`, and main already runs splits that are not powers of two (33 and 66 tiles per group).
- The pick never has fewer tiles per group than main's, which is its fallback, and differs from it only when the tile count is not a power of two and `seq < cu * block_per_cu`.

## Accuracy Tests

**Unchanged: GSM8K and the MTP accept length match main, and the kernel error at this PR's splits stays below that of main's splits for 66 or more rows.** Each group rounds its softmax probabilities to FP8 against its own running maximum, so a larger group rounds more coarsely; main already uses groups of 33 and 66 tiles for 66 or more rows.

- **GSM8K** (attention DP8 server below; sgl-eval 0.1.2, all 1,319 questions, temperature 0, up to 32,768 tokens, thinking mode): 97.04% with this PR and 97.35% on main, within one standard error (0.44 points).
- **MTP accept length** (TP8 low-latency command below, MTP 5/1/6): +0.0% to +0.5% vs main at 1, 4 and 8 concurrent requests; main's own spread between server restarts is 1.5–1.8%.
- **Kernel error** against an fp32 reference (q cast to FP8 as the wrapper does), for every split of the 66 tiles, 8 and 64 heads, 12 and 48 rows, and scores from flat to peaked: the same for every split with flat scores (2.3–2.4% mean relative error, from the FP8 inputs). With peaked scores it grows with the tiles per group, and this PR's split stays below main's 33- and 66-tile splits in every case:

| Mean relative error, peaked scores (lower = closer to the fp32 reference) | main's split (2 tiles) | this PR's split | 33 tiles (main, 66–131 rows) | 66 tiles (main, 132+ rows) |
|---|---|---|---|---|
| range over 16 cases | 0.13–0.74% | 0.13–1.00% | 0.17–1.23% | 0.16–1.35% |
| per case, relative to main's 2-tile split | 1× | 1.0–1.5× | 1.3–2.2× | 1.2–2.6× |

  All outputs are finite, and CUDA graph replay is bit-identical to eager.

## Speed Tests and Profiling

**Attention DP8, end to end.** This measures the layout of the TL;DR. **Result: steady decode throughput is 2.5% higher at 128 concurrent requests and 1.2% higher at 64, and the MTP accept length is unchanged (1.90–1.91 tokens per step, including the bonus token).** Setup: GLM-5.3-Flash on 8×H200; this PR on main `c5a5bf0` (the PR has since been rebased onto `71ee2dc` with the same diff), with #44262 (needed for attention DP with MTP on this model) applied to both versions; torch 2.14.1, FlashInfer 0.7.1, CUDA 13.0. Configuration: the command below (TP8/EP8, attention DP8 with 64 heads per GPU, FP8 KV with TileLang DSA prefill and decode, MegaMoE with DeepGEMM, MTP 1/1/2, radix cache off). Workload: 64 or 128 prompts of about 8.2k tokens (LongBench-v2 documents) with 1,024 output tokens each, sent at once, so every GPU decodes 8 or 16 requests with no new arrivals. Steady decode throughput is read from each GPU's decode log lines while all of its requests decode, and summed over the 8 GPUs; ITL comes from the benchmark client. Server restarts alternate between the two versions; the tables show medians.

**Attention DP8 with MTP 5/1/6, and with MTP 1/1/2 at 256 concurrent requests, end to end.** These runs put more query rows into each call while staying in the range where the split changes (up to 65 rows per GPU with 64 heads): MTP 5/1/6 gives 6 query rows per request in each verify call, and 256 concurrent requests with MTP 1/1/2 give 64 rows per GPU. **Result: with MTP 5/1/6 the decode step is 3.3% shorter at 64 concurrent requests and 2.0% shorter at 32; with MTP 1/1/2 at 256 it is 4.0% shorter, and steady decode throughput is 4.3% higher (14,733 → 15,370 tok/s).** Setup: as above, with `--enable-dp-attention-local-control-broadcast` added for both versions (it removes an all-rank sync on every scheduler iteration), and for MTP 5/1/6 also `--enable-linear-replayssm-spec` (commands below); 32 to 256 prompts sent at once.
