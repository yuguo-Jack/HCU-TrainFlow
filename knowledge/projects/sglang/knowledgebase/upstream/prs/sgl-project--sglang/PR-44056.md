# [diffusion] feat: enable Qwen-Image 2.1 Triton fast paths on Ascend NPU

Part of #43519 (roadmap item: *Qwen-Image-2.1 — adapt the existing SGLang Diffusion pipeline for Ascend*).

## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Qwen-Image-2.1's fused fast paths are all guarded by `is_cuda`, so on Ascend NPU the
model silently runs the eager path everywhere. Four of those paths are plain Triton
(no PTX / no `.cuh`), and three of them turn out to be **bit-exact on Ascend as well**.
This PR widens their guards so NPU can use them, with no behavioural change on CUDA.

## Modifications

<!-- Detail the changes made in this pull request. -->

Three fused paths, each with the same three-part change:

| Path | Fusion kernel |
|---|---|
| complex RoPE | `fused_complex_rope` |
| QK RMSNorm + complex RoPE | `qknorm_complex_rope` |
| SwiGLU `silu(gate) * up` | `fused_silu_mul_bitexact` |

1. **Model guards** (`qwen_image21.py`): `(_is_cuda and x.is_cuda)` →
   `((_is_cuda and x.is_cuda) or (_is_npu and x.is_npu))`. CUDA stays first; the CUDA
   branch is unchanged.
2. **Kernel input validation**: accept `is_npu` tensors alongside `is_cuda`.
3. **Device context**: `with torch.cuda.device(x.device):` →
   `with torch.cuda.device(x.device) if x.is_cuda else contextlib.nullcontext():`
   (NPU Triton launches target the tensor's own device; the CUDA path is byte-identical).

## Verification

Ran end-to-end on Ascend A3 (`Ascend910_9362`, CANN 9.1.0, torch_npu 2.10.0.post6,
triton-ascend 3.2.2), at commit `991a29d0ad`:

sglang generate --model-path Qwen/Qwen-Image-2.1
  --prompt "Doraemon is eating dorayaki" --num-inference-steps 40
  --guidance-scale 1 --height 1024 --width 1024 --seed 42 --num-gpus 1 --save-output

* exit code 0, image produced normally
* **no `BitExactFusionGate` fallback warning** for any of the three paths, i.e. all
  three passed their first-sight `torch.equal` check against the NPU eager chain and
  are mounted.
