## Zero-SM KV-Shard Gather

The sharded pool's per-layer prefix allgather previously used NCCL ring/LL kernels. When overlapped with attention and GEMMs, these kernels competed for SMs and HBM bandwidth.

`SGLANG_ENABLE_KV_SHARD_ZERO_SM_GATHER` enables **zero-SM** gathering and is on by default. The gather communicator is created with `NCCL_CTA_POLICY_ZERO`, allowing NCCL to run the in-place allgather on copy engines instead of SM kernels.

### Memory Allocation

Both scratch slots are carved from a single `ncclMemAlloc` buffer registered as a symmetric window. Each slot uses a 4 KiB-aligned offset that is identical across all ranks.

- `_scratch_tensor_specs` returns a mapping of `name -> (shape, dtype)`.
- The mixin handles allocation.
- The buffer is deregistered and freed when its last tensor view is destroyed.

### Activation and Fallbacks

The engine defaults `NCCL_CUMEM_ENABLE=1` when zero-SM gathering applies to a single-node deployment.

The pool retains Torch allocation when any of the following applies:

- `SGLANG_ENABLE_KV_SHARD_ZERO_SM_GATHER` is disabled.
- A memory saver or custom memory pool is active.
- The NCCL version is older than 2.28.
- The shard group spans multiple nodes. NCCL would use its hierarchical inter-node RMA path in this case, which remains unverified.

If window registration returns a `NULL` window because NCCL cuMem is disabled, the pool logs one warning and gathering remains on SM kernels.

### NCCL 2.30 Race Workaround

With NVLS enabled, NCCL 2.30 lazily builds the multicast team during the first copy-engine collective's synchronization, without a barrier. This race can cause the first gather to hang.

The pool works around the race by building the multicast team during registration and issuing a barrier afterward.

### GPU Test Coverage

The GPU test profiles a batch of gathers and verifies that:

- No NCCL kernels are launched.
- Peer copies occur.

A gather communicator that loses `NCCL_CTA_POLICY_ZERO` therefore fails the test.
