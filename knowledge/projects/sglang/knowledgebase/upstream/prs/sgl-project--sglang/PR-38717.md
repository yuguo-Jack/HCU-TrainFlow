# [Fix] Size routed expert capture buffers for speculative verification

[Upstream PR](https://github.com/sgl-project/sglang/pull/38717) · state: open · merged: False

## Original PR description

## Motivation

Speculative verification produces multiple token rows per request. The routed-expert capture buffer was sized by request count, so verification batches larger than the prefill chunk could overflow it.

## Modifications

Size the buffer from the maximum aligned eager/graph request capacity and maximum verification width, including adaptive configurations. Apply DP scaling once when allocating the capture buffer.

Add a regression that writes the complete route tensor for ordinary decoding, fixed/adaptive verification, eager/graph padding, and DP concatenation.

- esarafian · comment · 2026-11-03T15:45:14Z · [source](https://github.com/sgl-project/sglang/pull/38717#issuecomment-6608296793)

This is still reproducible on current main (`8d4e1ce4c7`), in case it helps move the PR along.

Setup: 2× RTX PRO 6000 Blackwell, TP2, public `RadixArk/Qwen3.8-Flash-Next-NVFP4` (top-k 10), image `lmsysorg/sglang:nightly-dev-20261103-797af717`.

```
python -m sglang.launch_server --model-path RadixArk/Qwen3.8-Flash-Next-NVFP4 --tp 2 \
  --moe-runner-backend flashinfer_cutlass --mamba-ssm-dtype bfloat16 \
  --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 4 --enable-return-routed-experts \
  --chunked-prefill-size 64 --max-running-requests 32
```

With 32 × 4 = 128 verify rows against a capture buffer of `max(64, 32) = 64` rows, the server dies during startup:

```
File ".../srt/layers/moe/topk.py", line 2629, in capture_routed_experts_if_allowed
File ".../srt/state_capturer/routed_experts.py", line 128, in capture
File ".../srt/state_capturer/base.py", line 50, in capture
RuntimeError: The expanded size of the tensor (64) must match the existing size (128) at non-singleton dimension 0.  Target sizes: [64, 10].  Tensor sizes: [128, 10]
```

The values above are deliberately small to make it easy to trigger. Any deployment where `max_running_requests × num_draft_tokens` exceeds `chunked_prefill_size` hits the same thing, for example 1024 running × 4 drafts with a 2048-token chunk. We measured a similar change in a downstream build (buffer sized by `max_running_requests × num_draft_tokens`): its R3 probes on GB300 showed no capture problems.

The branch now conflicts with main in `model_runner.py` and `routed_experts.py`, so we did not run the PR head itself. Happy to rerun this repro on a rebased head.
