# [Feat] [NVIDIA] modelopt: Opt-in Online block-FP8 dense layers for NVFP4 checkpoint

[Upstream PR](https://github.com/sgl-project/sglang/pull/45694) · state: open · merged: False

## Original PR description

## Motivation

ModelOpt NVFP4 checkpoints such as `nvidia/GLM-5.2-NVFP4` keep attention projections, shared experts and dense MLPs in BF16. This PR adds opt-in, load-time block-FP8 conversion for user-selected BF16 linears, so these layers can use FP8 GEMMs without exporting a separate checkpoint.

## Modifications

- **New option `--nvfp4-ckpt-fp8-dense-modules <module-or-pattern> ...`**, unset by default. It replaces the earlier boolean flag in this PR. Selected eligible BF16 linears are converted after loading to E4M3 with 128×128 weight blocks and dynamic per-token-group activation quantization. Layers the checkpoint already quantizes keep their configured method.
- **Selection reuses existing matching.** Literal module names and dotted paths use SGLang's module-path matching. `*` patterns use ModelOpt's checkpoint exclusion-pattern compiler. Fused projections must be selected through all of their checkpoint parts (for example `gate_proj up_proj`, not `gate_up_proj`); a partial fused selection is an error. Startup logs the rank-local count and warns about selectors that matched nothing.
- **Implementation stays in `modelopt_quant.py`.** `ModelOptOnlineBlockFp8LinearMethod` reuses the existing FP8 compute path and stores power-of-two scales when the selected DeepGEMM path needs UE8M0. `linear.py` registers its loader. There are no changes to `fp8.py` or to model implementations, and no model-specific defaults.
- **Draft/MTP and `lm_head` are not converted.** Draft construction is detected through the existing build scope, not layer names. Independent draft quantization options keep their behavior.
- **Online weight updates are rejected while the option is set**, on every pipeline stage, including stages with no matches. Begin/end update sessions check every selected runner before any restore or post-processing. This prevents writing BF16 values into FP8 storage under stale scales.
- **Docs:** server arguments, the ModelOpt quantization guide, and a GLM-5.2 cookbook example.

### Usage

The GLM-5.2 selection measured below:

```bash
--nvfp4-ckpt-fp8-dense-modules q_a_proj kv_a_proj_with_mqa q_b_proj o_proj wq_b gate_proj up_proj down_proj
```

A bare module name matches that module in every layer, so this selects the same 411 modules as the equivalent `'*.q_a_proj' '*.kv_a_proj_with_mqa' ...` patterns; the runs below used both forms. Patterns are for narrower selections, such as `'model.layers.*.self_attn.o_proj'`, and need quoting in the shell. This is an example to measure on your own GPU and parallelism, not a universal default. It leaves `kv_b_proj`, the indexer `wk`/`weights_proj`, and the draft model unconverted.

The option only touches linears the checkpoint leaves in BF16, that is, modules matched by `exclude_modules` in `hf_quant_config.json`. For `nvidia/GLM-5.2-NVFP4` (78 decoder layers: 3 dense, 75 MoE, plus MTP layer 78), this selection does the following to each excluded group:

| Checkpoint `exclude_modules` entry (BF16 in the checkpoint) | Converted to FP8 | Stays BF16 |
| --- | --- | --- |
| `model.layers.0*`, `model.layers.1.*`, `model.layers.2.*` (dense layers) | `fused_qkv_a_proj_with_mqa`, `q_b_proj`, `o_proj`, `indexer.wq_b`\*, `mlp.gate_up_proj`, `mlp.down_proj` | `kv_b_proj`, `indexer.wk_weights_proj`\* |
| `model.layers.{3..77}.self_attn*` (75 entries) | `fused_qkv_a_proj_with_mqa`, `q_b_proj`, `o_proj`, `indexer.wq_b`\* | `kv_b_proj`, `indexer.wk_weights_proj`\* |
| `model.layers.{3..77}.mlp.shared_experts*` (75 entries) | `gate_up_proj`, `down_proj` | none |
| `model.layers.78*` (MTP / NextN draft layer) | none | all of it: draft layers are never converted |
| `lm_head` | none | `lm_head`: never converted |
| `model.embed_tokens` | none | embedding (not a linear layer) |
| Not excluded: routed experts in layers 3–77 | none | already NVFP4, unchanged |

\* Only the 21 layers with their own DSA indexer. Fused names are SGLang's: `q_a_proj` + `kv_a_proj_with_mqa`, `gate_proj` + `up_proj`, `wk` + `weights_proj`. In total, 411 linear modules are converted, the same count on every rank, as checked by a full-model load audit.

**Small-batch trade-off.** Converting the fused A projection or `q_b_proj` makes them ineligible for SGLang's BF16 min-latency GEMM, so decode can be slower at small batches. An earlier measurement with the boolean flag showed ITL p90 6.28 → 7.02 ms at concurrency 1. Users can leave those modules out, or select them only on prefill workers.

**Note for reviewers: `SGLANG_NVFP4_CKPT_FP8_GEMM_IN_ATTN`.** This PR does not change that existing variable or its docs. The variable converts only `q_b_proj`, and only for DeepSeek-family models. For the main model, this option covers the same case (list `q_b_proj`) and more. The one difference is the MTP / NextN draft layer: the variable also converts its `q_b_proj`, while this option leaves draft layers at checkpoint precision. If both are set, the variable gives `q_b_proj` its own FP8 config, which bypasses the ModelOpt hook, so nothing is converted twice; in that case `q_b_proj` in the option's list matches nothing and logs a no-match warning. Whether to deprecate the variable in favor of this option is a separate follow-up.

## Accuracy

GLM-5.2-NVFP4 on 8×B300, native TP8 with the model-card launch command (no DP-attention, no MTP). The two arms differ only in the option. CIs are paired 95% bootstrap intervals over problems.

Settings follow the model card: temperature 1.0, top_p 0.95, max tokens 100K for GPQA and 64K for the rest.

| --- | ---: | ---: | ---: | ---: | ---: |

| NVFP4, NVIDIA model card | 89.39 | 75.81 | 70.13 | 98.25 | 49.04 |

- **GPQA Diamond:** sgl-eval 0.1.3, 198 questions × 8 repeats, pass@1. Its prompt and answer extraction are the same as NeMo-Skills' Artificial Analysis (AA) prompt.
- **IFBench:** official harness, 300 prompts, one sample. Prompt-level accuracy is shown as strict / loose; AA reports loose.
- **AA-LCR:** v1.0 dataset and prompts, 100 questions × 2. The equality checker is Qwen3-235B-A22B-Instruct-2507-FP8 at temperature 0, which is AA v1.0's judge model.
- **τ²-Bench Telecom:** base split, 114 tasks × 3 trials, max 100 steps, pass^1. The user simulator is the same Qwen model, which matches AA's methodology.
- **SciCode:** official prompts with scientist background, 65 problems / 288 subproblems × 3 repeats, sub-problem accuracy (AA's headline metric). Generated code ran in a network-isolated sandbox with a 300 s per-step timeout (SciPy 1.13.1). Main-problem accuracy, which needs every step of a problem to pass, was 15.90 off and 12.31 on (−3.59 [−8.21, +0.51]); with 65 problems it is noisy. As a check of the grader, the public validation split's own reference solutions passed 48 of 50 steps. The two misses are dataset issues that affect both arms the same way: one reference picks its timestep from wall-clock timing and produces a different trajectory length than the stored target, and one differs numerically on a single case.

The AA-LCR gain (+7.0) is the only interval that excludes zero, out of eleven comparisons in this PR. With 100 questions it may be chance, and we don't present it as an improvement. NVIDIA ran four of these benchmarks on vLLM, and its exact harness configs are not public, so its rows are references rather than matched controls.

## Performance

16 B300 GPUs, prefill/decode disaggregated: two TP4/DP4 prefill workers (EP4) and one TP8/DP8 decode worker (EP1), with DP-attention and MTP. AIPerf 0.12.0 traffic: 124K input tokens (58K shared prefix plus 66K unique), 7K output tokens, streaming, temperature 0, `ignore_eos`. Each point sends traffic for 1,200 s, with up to 300 s to drain. Off and on use the same seed and identical input bytes at each point. One run per point.

**Request rate (Poisson):**

| Offered req/s | Completed / sent (off, on) | TTFT p50 off → on | TTFT p90 off → on | ITL p90 off → on |

Every request completed in both arms. Up to 1.08 req/s, both configurations keep up with the offered load and the option lowers TTFT by 14–18% at p90. ## Limitations

- Concurrency 1–16 decode was not re-measured on this revision; see the small-batch trade-off above.
- Tested on B300 (SM103) only. A selection that pays off here may not on SM90 or under other parallelism, which is why there is no default.
- The CUDA tests cover a single-rank DCP replica, not multi-rank DCP.
- Online weight updates are rejected rather than supported.

[by Claude Code] **Severity: functional | Confidence: Medium**

**Issue**

After the first load, `layer.weight` is the same Parameter but holds FP8 data. An online weight update (`update_weights_from_disk` / `update_weights_from_tensor`) loads BF16 checkpoint values into it again. The row-parallel and merged-column loaders cast them straight to E4M3 with `copy_`, and this re-entry branch then treats them as already quantized with the old `weight_scale_inv`. The column-parallel loader (`copy_with_check`) instead raises "Downcasting not allowed" partway through the update.

**Example**

After a reload, `o_proj` serves raw E4M3 casts of the BF16 values times the stale block scales. The outputs are wrong and nothing reports an error.

**Fix**

Set `layer._derived_weight_cache_error` here so the weight updater rejects online updates with a clear message, or implement `restore_weights_before_loading` to bring back a BF16 weight.
