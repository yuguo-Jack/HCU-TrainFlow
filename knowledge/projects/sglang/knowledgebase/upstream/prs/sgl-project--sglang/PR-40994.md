# [Fix] function_call: Flush pending tool calls at end of stream in the Llama 3.2 detector

[Upstream PR](https://github.com/sgl-project/sglang/pull/40994) · state: open · merged: False

## Original PR description

## Motivation

`Llama32Detector.parse_streaming_increment` emits **at most one unit per delta**:
a tool name with empty parameters, then that call's argument diff, then the next
call. A delta that carries one or more *complete* tool calls therefore leaves
work pending for the following delta, and when that delta was the last one
nothing ever picks it up. On `main`, streaming a call that completes inside a
single delta loses data that `detect_and_parse` returns:

```python
from sglang.srt.function_call.llama32_detector import Llama32Detector

text = (
    '<|python_tag|>{"name": "get_weather", "parameters": {"city": "Paris"}}'
    ';{"name": "get_tourist_attractions", "parameters": {"city": "Paris"}}'
)
d = Llama32Detector()
d.parse_streaming_increment(text, tools)   # -> name "get_weather", parameters ""
d.finish(tools)                            # -> nothing
# observed: one call, with EMPTY arguments, and the second call missing entirely
# expected: both calls with {"city": "Paris"}  (what detect_and_parse returns)
```

This is reachable whenever a tool call completes inside one delta: multi-token
deltas from speculative decoding / MTP, `stream_interval > 1`, or a call short
enough to be produced in a single step. The client either receives an unusable
`tool_call` with empty `arguments`, or no second call at all.

## Modifications

`finish()` now re-runs the incremental parser with an empty delta until a round
yields neither calls nor text, which releases everything the last delta left
pending. This is the pattern `GigaChat35Detector.finish()` already uses.

- `python/sglang/srt/function_call/llama32_detector.py`: +34
- `test/registered/unit/function_call/test_function_call_parser.py`: +46

The drain loop is bounded (`_MAX_FINISH_DRAIN_ROUNDS`) because each round
releases at most one unit, and it stops early once a round is empty, so a stream
that was already fully flushed returns nothing and no existing behavior changes.

### Scope

Other detectors defer the same way; I kept this PR to the Llama 3.2 detector
because it is the case I could validate end to end. A deliberately broader
attempt (draining inside `BaseFormatDetector.finish()`) was discarded: it
surfaces format-specific leftovers such as Mistral's array tail and a stray
`</tool_call>` as visible text, which needs per-format handling rather than a
blanket default (`Spark25Detector` and `KimiK3Detector` already drop such
residue in their own `finish()`).

**Reviewer note — why the drain sits in `finish()` and not in the base class.**

There is an open base-class fix for part of this defect class (#32167, "Fix streaming tool calls losing arguments when completed in the final delta"). It does not cover this detector, and the reason is worth recording before anyone has to ask:

- The shared flush path is `FunctionCallParser.parse_stream_end()` -> `detector.finish()`, and **both** streaming entrypoints call it (`serving_chat.py:3030`, `serving_responses.py:2399`). The flush that #32167 extends, `_check_for_unstreamed_tool_args`, exists only in `serving_chat.py` (defined at 3115, used at 945); `serving_responses.py` has no equivalent.
- `BaseFormatDetector.parse_streaming_increment` processes exactly **one** JSON object per call — there is no loop between the `bot_token` search and the Case 1 / Case 2 returns. A delta carrying several complete calls therefore leaves the rest buffered, and registering the single object that was parsed does not recover them; the drain here re-runs the parser until it yields nothing, which does.
- `Llama32Detector.parse_streaming_increment` is an override that delegates parsing to `super()` (line 23), so a base-class change does reach this detector's *parsing* — but not the pending-call recovery, for the entrypoint reason above.
