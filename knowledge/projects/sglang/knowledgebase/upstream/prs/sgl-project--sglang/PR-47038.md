# [Perf] [AMD] dcp: Gather the target-verify query in fp8 for the aiter asm cprr kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47038) · state: open · merged: False

## Original PR description

## Motivation

- With decode context parallelism (DCP) on ROCm, MLA target verify runs on the AITER asm cp round-robin (cprr) kernel (`AiterAttnBackend._forward_verify_asm_cprr`, already on main).
- That kernel takes the query only as unit-scale fp8 (`q.view(n_rows, -1).to(fp8_dtype)`, `q_scale = 1`) and reads the verify window from the KV cache, so it never uses `k_window`.
- The model still does bf16 work on every verify step, every layer:
  - all-gathers `q_nope_out` and `q_pe` in bf16 across the DCP group;
  - runs `torch.cat` to build the full `[rows, H * dcp, nope + rope]` query;
  - runs `torch.cat` on `k_nope`/`k_pe` to build a `k_window` the cprr route ignores.
- The cast is elementwise and the all-gather is a byte copy, so casting local heads to fp8 before the gather gives the same bytes, moves half the data, and skips the full-width cat.

## Modifications

- `layers/dcp/comm.py`: new `all_gather_q_fp8_for_mla_verify`.
  - Each rank writes `q_nope_out`/`q_pe` into one fp8 `[H, B, nope + rope]` symmetric-memory buffer, gathers along heads, and returns a contiguous fp8 `[B, H * dcp, nope + rope]`.
  - The custom all-gather moves only 16/32-bit floats, so the buffer goes on the wire as bf16 (uint8 for an odd row width).
- `AttentionBackend.takes_fp8_dcp_verify_q()` (default `False`): whether DCP MLA target verify wants that fp8 query and no window K/V.
  - `AiterAttnBackend` returns `forward_metadata.use_asm_cprr_verify`.
  - `HybridLinearAttnBackend`, `HybridAttnBackend` and `TboAttnBackend` forward it to the backend that runs target verify.
- `forward_mla_rocm.py`: the DCP verify query and window follow the table below.

| Condition (DCP decode phase, target verify) | Query gather | `k_window` / `v_window` |
|---|---|---|
| `_use_aiter`, backend `takes_fp8_dcp_verify_q()`, no `llama_4_scaling` | fp8 gather, passed straight to `attn_mqa_for_dcp_decode` | skipped |
| Backend `takes_fp8_dcp_verify_q()`, `llama_4_scaling` set | bf16 gather + cat (backend casts) | skipped |
| Any other case (non-cprr verify, DSA triton) | `all_gather_q_for_mla_decode` as before | built as before |

## Accuracy Tests

- The kernel gets the same fp8 query bytes as before, and the cprr route never read `k_window`, so outputs should not change.
- Unit test `test/registered/unit/layers/test_dcp_fp8_q_gather.py` (CPU, `base-a-test-cpu`):
  - 8 thread "ranks" share a byte-copy all-gather set as the DCP group via `get_parallel().override`.
  - For e4m3fn and e4m3fnuz, at 5 and 260 tokens, the fp8 gather is byte-identical to bf16 gather + cat + cast, including values past the e4m3 range and below its subnormals.
  - Swapping the head order of the rope half makes all 4 subtests fail.

End to end: 8x MI355X, `Kimi-K3-Quark-MXFP4-AttnFP8`, TP8, DCP8, DSpark block 4 with real acceptance (target verify on the asm cprr route).
