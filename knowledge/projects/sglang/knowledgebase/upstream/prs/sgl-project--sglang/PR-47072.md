# [Feat] scheduler: Add typed per-token and per-request customized_info values

[Upstream PR](https://github.com/sgl-project/sglang/pull/47072) · state: closed · merged: True

## Original PR description

## Motivation

`LogitsProcessorOutput.customized_info` is a dict of one value per request, and `_maybe_collect_customized_info` appends `v[i]` to the request's list on every commit, cloning tensor elements so a request does not keep the batch alive. That shape gives a producer no safe way to publish device tensors and no way to say what one of its values means:

- A producer that publishes a view of a CUDA-graph or persistent buffer sees the next forward rewrite it before the scheduler reads the result, and a graph replay hands back its capture-time dict.
- A value that describes each emitted token has no stated width, so a speculative step's draft positions cannot be told from its accepted ones.
- A value that describes the whole request is appended again on every commit, and a re-prefill after retraction or a running request in a mixed batch records it a second time.

## Modifications

- `TokenCustomizedInfo` and `RequestCustomizedInfo` (`logits_processor.py`): typed `customized_info` values. A token value holds `[batch_size, width]` rows, one value per emitted token stored at that token's output position; a speculative step stores its accepted tokens' values. A request value holds `[batch_size]` rows, one value per request, recorded once at the request's first output. Both carry an optional ready event recorded after their rows' copy to the host.
- `LogitsProcessorOutput.own_customized_info`: copies each typed value's rows to the host with `async_d2h` behind one ready event, into a new dict, so a producer may hand out buffer views. `ModelRunner.forward` calls it right after the forward, next to the expert-distribution metrics.
- `materialize_typed_customized_info` (`batch_result_processor.py`): called once per batch from prefill and decode result processing, after `materialize_sampling_mask_output`. It waits on the ready event and turns the rows into host lists, again into a new dict, so a graph's capture-time dict is left as is.
- `_maybe_collect_customized_info` takes `num_new_tokens`, the number of tokens the request just committed (`_handle_finish_state_updated_req` passes the decode step's accept length; prefill keeps the default of 1). Token values are stored at their output positions and cut to the visible output length, with a `RuntimeError` on a row shorter than the committed tokens or a write past an existing position. Request values are recorded once, only when the request is at its first output. Untyped values keep today's path, and with no typed values nothing extra runs per request.
- Two unit-test fakes follow: the fake logits output in `test_batch_result_processor_hidden_states.py` gains `customized_info=None`, and the collector stub in `test_mix_with_running_mamba_track.py` takes the new argument.

## Accuracy Tests

Not applicable: no kernel or model forward change. No in-tree model publishes a typed value yet, so the new code runs only for a producer that opts in.

## Speed Tests and Profiling

Not applicable: with no typed value in `customized_info`, `own_customized_info` and `materialize_typed_customized_info` return at the first check, and the per-request collector takes the same path as before.
