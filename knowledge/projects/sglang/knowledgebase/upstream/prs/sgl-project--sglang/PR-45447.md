# [Perf] prefill-cuda-graph: Replay the prefill graph for 1-token extends so full prefix-cache hits are no longer slower than cold requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/45447) · state: open · merged: False

## Original PR description

## Summary

**Resending exactly the same prompt is slower than sending it the first time.** When a prompt is fully covered by the radix prefix cache, SGLang still recomputes its last token, so the request becomes a **1-token extend**. That extend can never replay the prefill CUDA graph and falls back to an eager forward that is bound by per-layer kernel launches. On H100, a cache hit therefore has a *higher* TTFT than a cold request — up to 5x higher on an MoE model.

This PR lets such tiny extends replay the smallest prefill graph bucket. Cache-hit TTFT drops to the level of (or below) a cold request, with bit-identical outputs:

| Model (official bf16, H100) | Cold request | Cache hit, `main` | Cache hit, this PR | Speedup |
|---|---|---|---|---|
| Qwen3-30B-A3B-Instruct-2507 (MoE), TP=2 | ~17 ms | 91.9 ms | **14.0 ms** | 6.6x |
| Qwen3-8B, TP=1 | ~14 ms | 29.8 ms | **13.7 ms** | 2.2x |
| Muse-Glimmer-30B (dense VLM), TP=1 | ~29 ms | 45.8 ms | **27.8 ms** | 1.65x |

Numbers are single-request, short-prompt (~20 tokens) TTFT medians, i.e. the cost of the 1-token extend step itself; the absolute saving is 16–78 ms per cache-hit request. Under load the extend is batched with other requests and the effect is smaller.

## Motivation

Sending the same prompt again is common: client retries and re-runs, evaluation harnesses, or applications that first warm the prefix cache with a prefill-only request and later send the identical prompt to generate. Users reasonably expect the second request to be the fast one, because its whole KV is already cached.

Why it is slow on `main`:

1. On a full prefix hit the radix cache still leaves the last prompt token to be recomputed (its logits are needed for the first output token), so the forward is an extend of **1 token**.
2. The smallest default prefill CUDA graph bucket is **4** tokens (`arg_groups/cuda_graph_hook.py`, `range(4, 33, 4)`).
3. `PrefillCudaGraphRunner.can_replay_locally` rejects any replay whose padded size exceeds `num_tokens * _MAX_PREFILL_CUDA_GRAPH_PADDING_FACTOR` (2, added in #31487). Padding 1 → 4 is 4x, so the request runs eagerly.
4. A 1-token eager forward does almost no GPU work but launches every kernel of every layer from the CPU. The profile of such a step on `main` (`EXTEND bs=1 toks=1`, `eager_runner._execute_extend`) is dominated by launch overhead. MoE models suffer most because each layer launches more kernels (router, top-k, expert dispatch/combine).

## Modifications

- Move the padding check in `can_replay_locally` into a static helper, `PrefillCudaGraphRunner._padding_within_budget(num_tokens, padded_num_tokens, capture_num_tokens)`.
- Keep the existing 2x cap, with one exception: an extend may replay the **smallest captured bucket when that bucket is itself tiny** (`<= _MAX_PREFILL_CUDA_GRAPH_TINY_BUCKET = 16` tokens). With the default buckets this lets 1-token extends replay the 4-token graph — at most 3 padded tokens of extra work instead of a launch-bound eager forward.
- Sparse large bucket lists keep the existing behaviour: with e.g. `[2816, 3072, 8192]` (the configuration #31487 was written for), small extends still run eagerly instead of replaying a 2816-token graph.

### Alternatives considered

- **Capture a 1-token prefill bucket by default.** This also helps the default configuration (passing `--cuda-graph-bs-prefill 1 2 3 4 ...` gave a similar cache-hit TTFT reduction in an earlier check on v0.5.21), but it adds graph captures and memory to every deployment; with DP-attention gathered buffers, two-batch overlap or attention CP the capture sizes are rounded up to an alignment (`get_cuda_graph_batch_size_alignment`), so a 1-token bucket would not stay 1 there; and it does not help user-specified bucket lists. The rule here needs no extra capture.
- **Allow a fixed number of padded tokens (e.g. ≤ 16 extra) regardless of bucket.** This would also replay e.g. 5 → 16 with buckets `[4, 16]`, which #31487's tests intentionally reject. Restricting the exception to the smallest bucket keeps every existing decision above the smallest bucket unchanged.

### Why 16

The limit only matters for custom bucket lists whose smallest bucket is 5–16 (the default smallest bucket, 4, is always within it). Up to 16 tokens of padded work is negligible: at this size the linear layers are memory-bound (on H100 a 4096x6656 block-FP8 GEMM takes ~13–15 µs from M=16 to M=128) and the attention adds a handful of query rows, while the eager fallback costs tens of milliseconds. A smaller limit would not make the default case safer, only exclude some custom configurations.

### Safety / scope

- **Long prompts.** The breakable prefill graph has no context limit by default (`max_context_size` is only set by `--cuda-graph-prefill-max-context`), so cache hits on long prompts benefit as well; above a user-set limit they stay eager as before.
- **DP consistency.** The schedule-time DP vote (`scheduler_components/dp_attn.py`, `_local_prefill_cuda_graph_vote`) calls the same `can_replay_locally`, so all DP ranks apply one rule.
- **DP attention, decode → extend conversion (behaviour change).** A decode rank votes with its 1-token-per-request extend view (`num_tokens = batch_size`). A rank decoding a single request used to vote eager (1 → 4 > 2x), which — the vote being min-reduced — sent the whole DP group to eager prefill for that step. It now joins the graph replay exactly like ranks decoding 2 or 3 requests already did. Covered by unit tests; not benchmarked end to end.
- **Context parallel.** With CP prefill graphs, `can_run_graph` still selects buckets via `select_replay_bucket_for_batch(..., max_padding_factor=2)`, so CP behaviour is unchanged and `load_batch` never sees an unfitted batch.
- **Unaffected paths.** Target-verify (speculative decoding), multimodal, LoRA, logprob, mixed batches and the context-length bounds all return before the padding check.
- **Hybrid linear-attention models are unaffected.** For Qwen3.5-35B-A3B-FP8 the mamba radix cache only matches at `mamba_track_interval` checkpoints (256), so resending a short prompt hits 0 cached tokens and a long one leaves up to 256 tokens to extend; a 1-token extend does not occur. Measured cache-hit TTFT is unchanged (35.7 vs 34.0 ms) and outputs are identical.

## Tests

- `test/registered/unit/model_executor/test_prefill_cuda_graph_runner_helpers.py` — `test_padding_budget_allows_tiny_extends_below_smallest_bucket`: default-shaped buckets let 1–4 tokens replay the smallest bucket; the 2x cap still rejects 5 → 16 and 100 → 512; with `[2816, 3072, 8192]`, 1 → 2816 and 100 → 2816 are rejected and 1500 → 2816 is allowed.
- `test/registered/unit/model_executor/runner/test_prefill_cuda_graph_padding.py` — `test_accepts_single_token_padding_to_tiny_smallest_bucket`, `test_rejects_tiny_extend_into_large_smallest_bucket`, and the DP vote through `_local_prefill_cuda_graph_vote` with a real runner: `test_single_request_decode_rank_joins_graph_replay`, `test_single_request_decode_rank_keeps_eager_for_large_buckets`.
- These two files plus `test/registered/unit/managers/scheduler_components/test_dp_attn.py`: 57 passed. Against unmodified `main`, exactly the new 1-token / bs=1 checks fail; the large-bucket checks pass on both, i.e. that behaviour is unchanged.

## Accuracy Tests

Greedy outputs are identical between `main` and this branch for all test prompts (cold and cache-hit requests) on every model.

GSM8K (few-shot, 200 questions, `python -m sglang.test.few_shot_gsm8k --parallel 128`):

| Model | main | this PR |
|---|---|---|
| Qwen3-8B (bf16, TP=1) | 0.950 | 0.945 |
| Qwen3-30B-A3B-Instruct-2507 (MoE, bf16, TP=2) | 0.945 | 0.960 |
| Muse-Glimmer-30B (dense, bf16, TP=1) | 0.945 | 0.940 |

(Differences are within the noise of 200 questions.)

## Speed Tests and Profiling

Setup: H100 80GB, `main` @ afe3e1df31 vs this branch (same venv, back to back on the same GPUs), `--mem-fraction-static 0.85`, default prefill CUDA graph settings, official bf16 checkpoints. Each of 3 short chat prompts is sent once (cold) and then 10 more times with exactly the same text; the server log shows `#new-token: 1, #cached-token: 18–22` for the repeated requests. Streaming `/generate`, greedy, 32 output tokens, TTFT measured at the client; medians over the 30 repeated requests.

| Model | Cold TTFT (ms) | Cache-hit TTFT, `main` (ms) | Cache-hit TTFT, this PR (ms) |
|---|---|---|---|
| Qwen3-8B, TP=1 | 14.3 | 29.8 | **13.7** |
| Qwen3-30B-A3B-Instruct-2507 (MoE), TP=2 | 16–17 | 91.9 | **14.0** |
| Muse-Glimmer-30B (dense VLM, 52 layers), TP=1 | 29–30 | 45.8 | **27.8** |
