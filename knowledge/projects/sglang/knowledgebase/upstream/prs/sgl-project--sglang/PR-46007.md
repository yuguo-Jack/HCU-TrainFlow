# [Perf] diffusion: Wait on the socket when the scheduler is idle

[Upstream PR](https://github.com/sgl-project/sglang/pull/46007) · state: closed · merged: True

## Original PR description

## Motivation

With nothing to run, the diffusion scheduler's event loop received from its socket with `zmq.NOBLOCK` and looped again at once, so an idle server kept one CPU core fully busy, between requests as well as during long idle periods. The loop already waits on its poller while a dynamic batch fills and while outputs are being saved, but not when it is simply idle.

## Modifications

- Add `--sleep-on-idle`, disabled by default to match SRT and preserve the existing busy-polling latency policy.
- When enabled, an idle single-rank monolithic replica waits on its existing socket poller. Messages wake it immediately; each wait is bounded by one second or the pending allocator-cache release deadline, whichever is sooner.
- `release_cache_if_idle` returns how long that release still has to wait, so the release happens when it did before.
- A replica that relays requests to other ranks keeps the old loop, because those ranks time their own cache release by its cadence.

## Accuracy Tests

```bash
pytest python/sglang/multimodal_gen/test/unit/test_idle_cache_release.py
```

`test_idle_scheduler_wait_policy` covers default busy polling, opt-in bounded waits, multi-rank fallback, and timely allocator-cache release. The scheduler, metrics, output save, pi05 segment, warmup, port and client unit tests pass as on main.

`nvidia/Cosmos3-Nano` served with its defaults through every Cosmos3 modality (text, image and video to video, with and without sound, and the action modes), 636 requests per arm in fresh servers. Every output is byte for byte the output before the change.

In one run each of a native server on this branch and on main, the scheduler process used 20.2 CPU seconds in a 20 second idle window on main and 0.08 here, both requests returned the same bytes, the allocator cache still went back to the driver about one second after each request, and SIGINT stopped the server in the same time.

## Speed Tests and Profiling

The measurements below were collected before the opt-in follow-up, with idle waiting enabled. They are not new measurements of the current head; the default now retains busy polling. Blocking waits can add idle-to-active wake-up latency, so latency-sensitive deployments should benchmark their low-QPS tail latency before enabling the flag.

One GPU per server, a fresh server per run, the same workload in each, eight paired runs and four more on fresh prompts, seeds and source media.

| Measure | Before | After | Change |
| --- | --- | --- | --- |
| Server CPU while idle, CPU seconds per minute | 65.5 | 0.25 | -99.6% |
| Server CPU per request, text to video | 7.58 s | 7.07 s | -6.7% |
| Server CPU per request, video to video | 8.08 s | 7.56 s | -6.4% |
| Server CPU per request, image to video with sound | 8.11 s | 7.54 s | -6.9% |
| Server CPU per request, forward dynamics | 2.90 s | 2.37 s | -18.1% |
| Server CPU per request, policy | 1.97 s | 1.58 s | -19.7% |
| Server CPU per request, two text to video requests at once | 7.54 s | 7.23 s | -4.1% |

The busy loop also ran between back to back requests, which is where the per request savings come from. Latency, throughput, GPU time and energy per request, device and host memory, startup, first requests and shutdown show no measurable difference in either set of runs. A request waiting in an idle loop reaches it within about 10 us of when a spinning loop would see it.
