# [Fix] [AMD] deterministic: Use one partition in the MiniMax Gluon sparse prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/46786) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-deterministic-inference`, MiniMax-M3 on MI350X at TP4 gives different outputs for the same prompt depending on whether part of it came from the radix cache: `test_deterministic --test-mode radix_cache` fails (a cached prefill and an uncached prefill of the same prompt give different logprobs), and the prefix test returns many different outputs per prompt. TP2 passes.

At TP4 each rank holds one KV head, and with one KV head the ROCm sparse prefill runs AITER's Gluon paged-attention kernel (`gluon_sparse_prefill`). It sizes its context split count from the number of query tokens in the forward (`get_recommended_splits(total_q, 1)`). A request extended over a cached prefix has fewer query tokens in its forward than the same request prefilled from scratch (and a request prefilled next to other requests has more), so the attention partials are combined in a different order and the output changes. An op-level comparison confirms it: the first op whose inputs (the queries and every K/V row they read) are bitwise equal but whose outputs differ is the attention of the first sparse layer, on every rank. With more than one KV head per rank (TP2) the model already uses the Triton sparse prefill, which does not depend on the query count.

This PR uses one partition (no context split) in the Gluon prefill in deterministic mode, so a row's attention is computed in the same order whatever else is in the forward. It costs nothing measurable. Normal mode is unchanged.

## Modifications

- `kernels/ops/attention/minimax_sparse/prefill/gluon_prefill.py`: the split count moves into `_max_part_num()`. In deterministic mode it is 1 for every forward; otherwise it is `get_recommended_splits(total_q, 1)` as before. The deterministic flag is read once from the runtime config.
- New CPU test `test/registered/unit/layers/attention/test_minimax_gluon_prefill_splits.py`: recommended split counts in normal mode, one partition in deterministic mode.
- Unchanged: normal mode, other models, MiniMax-M3 with more than one KV head per rank (Triton sparse prefill), the indexer and decode.

## Accuracy Tests

MI350X, ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`, MiniMax-M3 (MXFP4), TP4, deterministic mode, together with the other MiniMax-M3 deterministic-mode changes it needs on this image (batch-invariant sparse decode #46397, a deterministic MXFP4 MoE path and the fp32 router gate; not part of this PR). Default server settings (CUDA graphs and overlap scheduling on).

`python3 -m sglang.test.test_deterministic` (`single`, `prefix`, `prefix --return-logprob`, `radix_cache`, 50 trials), a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response), and a cached-prefix check (a 772-token prompt alone, after one of its own shorter prefixes, and next to other prompts, 24 comparisons with its first run):

| | before | this PR |
| --- | --- | --- |
| `single` | 1 output | 1 output |
| `prefix` (4 prompts, outputs per prompt) | 1 / 79 / 46 / 87 | 1 / 1 / 1 / 1 |
| `prefix --return-logprob` | logprobs differ | identical |
| `radix_cache` | fails | passes |
| bitwise batch-size check | 1,275 / 1,275 | 1,275 / 1,275 |
| cached-prefix check | 16 / 24 differ | 24 / 24 identical |

Switching the Gluon prefill off through `SGLANG_OPT_USE_MINIMAX_GLUON_PREFILL=0` gives the same results. GSM8K (sgl-eval 0.1.2, temperature 0, 1,319 questions), TP4, deterministic mode with this PR: 95.98%. The new unit test passes (`2 passed`).

## Speed Tests and Profiling

Deterministic mode, MiniMax-M3 TP4, `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-range-ratio 1.0 --request-rate inf`, output throughput (one round each):

| workload | before | this PR | change |
| --- | --- | --- | --- |
| 1k in / 1k out, 256 prompts, concurrency 256 | 4,868.7 tok/s | 4,886.2 tok/s | +0.4% |
| 8k in / 1k out, 128 prompts, concurrency 64 | 1,300.4 tok/s | 1,299.7 tok/s | -0.1% |

One partition costs nothing measurable here. For comparison, keeping the Triton sparse prefill instead costs 1.5% at 1k/1k and 10.1% at 8k/1k, and pinning the split count to 4 or 8 costs 0.8-5.4%.

Normal mode is unchanged.
