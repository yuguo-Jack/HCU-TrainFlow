# [Feat] rust-server: Apply the x-override-* request headers

[Upstream PR](https://github.com/sgl-project/sglang/pull/44312) · state: closed · merged: True

## Original PR description

Follows #44207 (`extra_key` on the Rust frontend's `/generate`), which shared the proto and scheduler-header lines; now that #44207 is merged this branch is rebased onto `main` and carries only this change.

## Motivation

A router in front of the server can leave the `/generate` body opaque and send the fields it computes as `x-override-*` headers: `rid`, the PD `bootstrap_host` / `bootstrap_port` / `bootstrap_room`, `routed_dp_rank`, `disagg_prefill_dp_rank`, `priority` and `conversation_id`. The Python server applies them on `/generate` when `SGLANG_ENABLE_REQUEST_HEADER_OVERRIDES` is set (`python/sglang/srt/entrypoints/request_headers.py`). The Rust frontend ignored them, so in Rust mode the router's request ids, PD pairing and DP placement were silently lost.

## Modifications

- `rust/sglang-server/src/api_server/http/request_headers.rs` (new): the port of `request_headers.py`. With the env var on, each present `x-override-*` header overrides the body field of the same name before the body is decoded, typed as Python casts it (`str` or `int`); an unparsable value is a 400 naming the header. `native_api.rs` applies it on `/generate`. The flag reaches the server as `ServerArgs.enable_request_header_overrides` (`message/config.rs`), set from `envs.SGLANG_ENABLE_REQUEST_HEADER_OVERRIDES` in `python/sglang/srt/rust_server/config.py`.
- `priority` becomes a `GenerateRequest` schema field (proto tag 24; `api_types.py`, `sglang.api.v1.rs` and `sglang.api.v1.serde.rs` regenerated with `cargo gen-api`) and is carried in its scheduler-header slot (`message/io_struct.rs`), one value for every batch item as in Python. It leaves the pinned list of Python-only request fields (`test_parity.py`, `json_parity.json`, the `unported_generate_req_input_fields_are_ignored` test).
- When priority scheduling is on, an unset priority takes `default_priority_value` at intake (`to_scheduler_validation.rs`, via `ServerArgs.default_priority_value`), as Python's `TokenizerManager._set_default_priority` does. Without that, a request that sends no priority would arrive as `None`, which the scheduler ranks lowest, so any request carrying `x-override-priority` would outrank, preempt and abort it. `rust_server/config.py` passes the default only when `enable_priority_scheduling` is set.
- `conversation_id` is accepted and dropped: nothing past Python's TokenizerManager reads it. The OpenAI routes are out of scope here.
