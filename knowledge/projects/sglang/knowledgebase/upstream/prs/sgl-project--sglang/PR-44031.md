# [Feat] [AMD] DeepSeek-V4.1: FP8 unified KV for the ratio-1/2 layers, with DSpark, PD and the UMBP linker

[Upstream PR](https://github.com/sgl-project/sglang/pull/44031) · state: open · merged: False

## Original PR description

## Motivation

On ROCm (MI355X), the FP8 unified KV layout (`SGLANG_DSV4_UNIFIED_KV_FP8`) only covers the DeepSeek-V4 compress ratios 4 / 128, and the hook rejects it for DeepSeek-V4.1, which uses ratios 1 / 2 with several layers sharing one kv_source. This PR makes FP8 unified KV work for DeepSeek-V4.1-Flash, including DSpark speculative decoding, PD transfer and the UMBP external linker.

The unified layout replaces the paged SWA pool, which is sized up front from `--swa-prefix-tails`, with one SWA ring per layer, so the memory goes to full-context tokens instead; how much this adds depends on that reservation (see Speed Tests). DSpark is the only speculative decoding DeepSeek-V4.1 has (its `mtp.*` weights are the DSpark draft), and the InferenceY deployment of DeepSeek-V4.1-Flash runs with it, so the unified layout has to work with DSpark to be usable there. DeepSeek-V4 already runs fp8 unified KV with DSpark (#38901: the target on the fp8 rings, the draft on a bf16 ring of its own); this PR reuses that split for V4.1.

UMBP with DSpark also relies on the UMBP direct linker accepting the packed DSpark draft layer mappings (#44929, merged).

## Modifications

1. **FP8 unified KV for the ratio-1/2 kv_source groups**: one compressed region per kv_source group and one SWA ring per layer (`compress_row_base`); the c1 / c2 two-pool store (fp8 nope + bf16 rope); low-ratio decode streams; a packed fp8 query without q-norm (V4.1 has none); the hook admits the fp8 unified layout for V4.1. The FlyDSL v4 nm decode keys its split plan by stream kind; the ratio-1/2 streams (SWA prefix plus a top-k tail) take the CSA plan.
2. **Decode on par with paged KV**: RoPE inside the fp8 query packer, with the query pack and the ring K store in one launch (two launches on parallel streams where the layer overlaps them); one decode stream per ratio-1/2 index source with metadata in two launches; on the asm decode, the inverse RoPE folded into the split merge, which loads all splits at once (the FlyDSL decode merges in its own launch and takes the inverse RoPE as a separate pass, or fused with the wo_a quant).
3. **Decoder SWA bounded replay and prefill CP**: the late layers' SWA floor (`pf_swa_floor`) in the prefill metadata; with the prefill CP of #44730, CP rows taken by the layout's `local_index`. Since #45339 the tail starts at the last kv_source layer, whose compressed KV `write_tail_source_kv` writes for every row through the same c1 / c2 stores; the floor covers that layer's ring like the later ones.
4. **Kernel tests** for the ratio-1/2 unified path, byte-for-byte against paged KV.
5. **PD / linker**: with the unified layout the ratio-1 and ratio-2 groups share one compressed region, so each group is registered once and its PD transfer and external-linker mapping start at `compress_row_base`; the C1 / C2 rope side pools join the low-ratio regions (the nope half alone restores stale rope); the C4 / C128 rope regions are skipped when the model has no such layers; the two new rope pool names are registered in the Rust radix tree core like the C4 / C128 ones; the hook admits unified + PD for V4.1.
6. **DSpark**: the hook admits DSpark with the unified layout on V4.1 (static verify). The target verifies through the fp8 decode streams, and its c1 / c2 compressors write the rows of the verified tokens through the same fused stores as paged KV; the draft keeps the bf16 ring of #38901. The V4.1 draft block attends to its request's last 128 committed positions and the whole block (bidirectional inside the block, as the paged draft's `BuildDsparkSwaPageIndices` does), while V4's draft reads a causal window: under the unified layout the backend now builds the V4.1 block window over the draft ring instead of falling back to the causal one, which would not fail but would lower acceptance. No grouped HCA verify streams are built for a model without ratio-128 layers. Tests: a c2 verify that rejects part of its draft and verifies again leaves the pool, the outputs and the pair-state ring exactly as a token-by-token decode of the accepted tokens; the draft block streams match `BuildDsparkSwaRingIndices` row for row; the hook cases.
7. **Verify metadata**: under DSpark every target step is a verify, so the target-verify metadata goes through the two-launch V4.1 builder too (a verify row is a decode row at its own position), with the grouped verify streams shared between both paths as V4 builds them.
8. **DSpark under PD**: the target and draft SWA rings already ship as two `SWA_RING` state components (the draft ring as in V4's PD); the DeepSeek-V4.1 DSpark PD layout handshake now accepts them instead of demanding two paged SWA states, the hook drops the unified + DSpark + PD rejection, and MoRI joins Mooncake and NIXL as a DSpark PD transfer backend, for paged and unified KV alike (the same one-line allowance as #42457). A paged side and a unified side still fail the handshake, since the state types are part of the layout.

## Supported scope and limitations

- How it is turned on: this PR adds no environment variable and no server flag. The layout is enabled by the two existing switches `SGLANG_HACK_FLASHMLA_BACKEND=unified_kv_triton` and `SGLANG_DSV4_UNIFIED_KV_FP8=1`, both off by default; their gate already limits the unified layout to ROCm and the fp8 layout to gfx95, so CUDA never reaches the new code. With them unset, CUDA and ROCm behave as on main: every new path in the shared DSV4 backend, the model, the pools and the kernels sits behind that gate, and the new hook rejections only apply with the unified layout. The one change outside the gate is the MoRI allowance for DeepSeek-V4.1 DSpark PD (item 8), which applies to paged KV as well.
- Validated only on ROCm gfx950 (MI355X).
- Unified KV on V4.1 is fp8 only. The hook rejects the bf16 unified layout, encoder SWA bounded replay and HiCache with the unified layout. The external cache linker was run with the MoRI UMBP backend only (the Mooncake linker shares the same region mapping but was not run). With DSpark it also rejects compact ragged verify (`SGLANG_RAGGED_VERIFY_MODE=compact`; the default `static` is supported). DSpark under PD disaggregation needs static verify and Mooncake, NIXL or MoRI on both sides, with the same unified KV setting on prefill and decode. PD was run on one node and across two MI355X nodes, prefill TP up to 4 with CP4. DeepSeek-V4.1 DSpark PD needs the same TP size on both servers (a check on main). With paged KV, PD over MoRI on current main can answer long prompts wrong when OPUS sparse prefill (`SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL`) is on; that is an issue on main outside the PD transfer, which this PR does not touch, and fp8 unified (no OPUS) is not affected. The paged PD runs below keep OPUS off.
- The image used here ships FlyDSL 0.4.0 with the v4 nm decode, so the unified decode below ran on FlyDSL (the default); the unified kernel tests pass on it, including the FlyDSL cases (278, none skipped).
- On HIP, V4.1 unified KV does not support the breakable prefill CUDA graph; the backend rejects it with `NotImplementedError`, and all runs use `--cuda-graph-backend-prefill disabled`.
- Decode with TP8 and no DP attention is blocked by the aiter fp8 decode kernel (no gqa=8 instance).
- The CP key dedup of #43806 is not included, so UMBP capacity and sharing across CP layouts are not guaranteed.

## Accuracy Tests

Setup: MI355X, DeepSeek-V4.1-Flash, image `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261025` with the branch's whole `python/sglang` mounted over the image's, this PR on main `d19f19d68`, model default context (1M). Results marked † are from an earlier revision of this PR on main `30dc2f943` (image `-20261023`, with the one-line q_lora fix that main has since merged as #46151); since then the PR was rebased without conflicts, got a cleanup without functional change (direct field access instead of defensive getattr, unused helpers and fields removed) and registers the C1 / C2 rope pool names in the Rust radix tree core. Unified environment: `SGLANG_HACK_FLASHMLA_BACKEND=unified_kv_triton SGLANG_DSV4_UNIFIED_KV_FP8=1`. Each comparison runs both servers on one node at the same time with the same command line except the two env vars. sgl-eval 0.1.3 GSM8K with the settings of `test_deepseek_v41_flash_gb300.py` (`--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash --max-tokens 4096 --num-threads 64`), all 1319 questions. Every server below also answered the internal greedy set (21 prompts) and the 50 concurrent long needles (31k–186k tokens, incl. prefix-cache hits) right, unless noted.

**Without speculative decoding** (TP4, `--fp8-gemm-backend aiter --kv-cache-dtype fp8_e4m3 --cuda-graph-backend-prefill disabled --prefill-decode-interval 32 --swa-prefix-tails 2048 --enable-decoder-swa-bounded-replay --max-running-requests 64 --mem-fraction-static 0.86`):

| KV layout | GSM8K |
|---|---|
| paged FP8 | 96.29% |
| fp8 unified | 95.91% |

**With DSpark**, the InferenceY DeepSeek-V4.1-Flash TP4 recipe (`--speculative-algorithm DSPARK --speculative-dspark-block-size 5`, `--enable-decoder-swa-bounded-replay`, `--prefill-decode-interval 96`, `--swa-prefix-tails 1024`, `--max-running-requests 32`, `--mem-fraction-static 0.70`, INT8 quick reduce, OPUS sparse prefill). Acceptance length is the server's `accept len`, averaged over the GSM8K run:

| KV layout | GSM8K | Acceptance length |
|---|---|---|
| paged FP8 | 96.21% | 3.47 |
| fp8 unified | 96.44% | 3.48 |

With the InferenceY TP2 concurrency-64 settings (`--swa-prefix-tails 4096`, `--mem-fraction-static 0.85`, `--max-running-requests 128`, `--chunked-prefill-size 4096`, `--prefill-decode-interval 4`) and DSpark: paged FP8 96.51% / 3.52, fp8 unified 96.29% / 3.51; with `--chunked-prefill-size 16384` (long extends through the replay tail) paged FP8 96.66% / 3.44 and fp8 unified 96.59% / 3.48 (on both, one of the 50 long needles, 186k tokens in its third send, ran out of the 1024 output tokens while still reasoning); fp8 unified together with #44730 (CP2 + decode-attention TP) 96.66% / 3.43 †.

**DSpark under PD**, 1P1D over MoRI, on one node (through the NIC loopback) and across two nodes, both servers with fp8 unified KV and `--speculative-algorithm DSPARK --speculative-dspark-block-size 5 --cuda-graph-backend-prefill disabled --fp8-gemm-backend aiter --kv-cache-dtype fp8_e4m3 --max-running-requests 32 --mem-fraction-static 0.70` (static verify, no decoder replay); acceptance length on the decode server, averaged over the GSM8K run:

| Prefill / decode | Nodes | GSM8K | Acceptance length |
|---|---|---|---|
| TP2 / TP2 | one | 96.51% | 3.50 |
| TP4 + CP4 (#44730) / TP4 † | one | 96.29% | 3.49 |
| TP4 / TP4 | two | 96.59% (96.21% on a second pair) | 3.46 (3.50) |
| TP4 + CP4 (#44730) / TP4 † | two | 96.13% | 3.49 |

The acceptance length matches the non-PD servers (about 3.5 above): a wrong draft ring would lower it while GSM8K stays put, so this is the check that the draft ring arrives intact. For reference, paged FP8 KV with DSpark under PD (TP2 / TP2, one node, OPUS off) gives 96.21% / 3.47 †.

**UMBP external linker with DSpark under PD** (one node, TP2 / TP2 over MoRI, a standalone UMBP server as the prefill's external store, the decode without UMBP): after flushing the prefill's device tree, re-sent prompts of 5.7k / 28.5k / 85.5k tokens read their whole prefix back from UMBP (`cached_tokens_details` all on the host tier) and answer right, 9/9; with it GSM8K 96.29% and acceptance length 3.48, and the same check on paged FP8 KV is 9/9 too (96.66% / 3.43 †).

No server faults or NaN in any run.

Unit tests: the kernel cases and the new pool / linker / DSpark / PD cases pass. The other failures in the touched test files (`TestDSparkDraftRingWithEncoderReplay`, 3 cases) fail the same way on main.

## Speed Tests and Profiling

`bench_serving`, random token ids, 5 x concurrency requests (at least 16), the radix cache flushed before every run (random-ids prompts of one seed are prefixes of each other across runs, so an earlier run would otherwise warm the next one). Each point is a single run.

**KV capacity** (`max_total_num_tokens`): the paged layout reserves its SWA pool up front from `--swa-prefix-tails`, while the unified rings are sized by the request slots only, and a full-context token costs a little more in the unified layout; the gain therefore grows with `--swa-prefix-tails`, and with small tails the unified layout can hold fewer tokens than paged KV.

| Setting | paged FP8 | fp8 unified |
|---|---|---|
| TP4, no spec, tails 2048, mem 0.86 | 76.71M | 82.37M (+7.4%) |
| TP4, DSpark, tails 1024, mem 0.70 | 50.17M | 52.56M (+4.8%) |
| TP2, DSpark, tails 4096, mem 0.85 | 28.46M | 48.86M (+72%) |

**Without speculative decoding**, the servers of the first GSM8K table. Output tok/s and mean TPOT:

| Input / output | Concurrency | paged FP8 | fp8 unified |
|---|---|---|---|
| 8k / 1k | 1 | 183.4, 5.31 ms | 183.4, 5.31 ms |
| 8k / 1k | 16 | 1625.2, 8.82 ms | 1658.3, 8.64 ms |
| 8k / 1k | 64 | 3165.1, 16.93 ms | 3187.0, 16.83 ms |
| 64k / 1k | 1 | 155.7, 5.39 ms | 147.0, 5.40 ms |
| 64k / 1k | 4 | 383.1, 7.95 ms | 379.6, 8.00 ms |

Both layouts decode at the same speed: TPOT is within 2% at every point. The 64k / 1k concurrency-1 throughput gap comes from the unified run's TTFT (one slow first request, P99 TTFT 5.8 s vs 1.2 s), not from the decode.

**With DSpark**, the servers of the second GSM8K table. Output tok/s, mean TPOT and mean TTFT:

| Input / output | Concurrency | paged FP8 | fp8 unified |
|---|---|---|---|
| 8k / 1k | 1 | 609, 1.51 ms, 0.13 s | 635, 1.44 ms, 0.14 s |
| 8k / 1k | 16 | 1842, 2.02 ms, 6.22 s | 1825, 1.98 ms, 6.30 s |
| 64k / 1k | 1 | 437, 1.29 ms, 1.02 s | 429, 1.29 ms, 1.07 s |
| 64k / 1k | 4 | 403, 1.45 ms, 8.10 s | 474, 1.61 ms, 6.40 s |

With DSpark the throughput follows the acceptance of the generated text, so single runs are noisy (two runs of the same unified server differed by 5–20% in the previous revision). Here the unified TPOT is between -5% (8k / 1k concurrency 1) and +11% (64k / 1k concurrency 4) of paged KV, and equal at 64k / 1k concurrency 1; at 64k / 1k concurrency 4 the paged run had a slow TTFT instead (P99 12.5 s vs 7.4 s), so its throughput is the lower one.

**TP2, DSpark**, the InferenceY TP2 concurrency-64 settings above; output tok/s and mean TPOT:

| Input / output | Concurrency | paged FP8 | fp8 unified | fp8 unified + #44730 (CP2) † |
|---|---|---|---|---|
| 8k / 1k | 32 | 2390, 9.50 ms | 2398, 9.73 ms | 2409, 9.15 ms |
| 8k / 1k | 64 | 2489, 9.29 ms | 2432, 9.65 ms | 2409, 9.72 ms |
| 64k / 1k | 8 | 451, 6.30 ms | 440, 6.07 ms | 439, 6.06 ms |

Here the unified layout stays within 3% of paged KV in throughput (TPOT -4% to +4%) and holds 72% more KV.
