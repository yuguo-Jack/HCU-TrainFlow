# [Feat] [AMD] DeepSeek-V4.1: FP8 unified KV for the ratio-1/2 layers, with DSpark, PD and the UMBP linker

[Upstream PR](https://github.com/sgl-project/sglang/pull/44031) · state: open · merged: False

## Original PR description

## Motivation

On ROCm (MI355X), the FP8 unified KV layout (`SGLANG_DSV4_UNIFIED_KV_FP8`) only covers the DeepSeek-V4 compress ratios 4 / 128, and the hook rejects it for DeepSeek-V4.1, which uses ratios 1 / 2 with several layers sharing one kv_source. This PR makes FP8 unified KV work for DeepSeek-V4.1-Flash, including DSpark speculative decoding, PD transfer and the UMBP external linker.

The unified layout replaces the paged SWA pool, which is sized up front from `--swa-prefix-tails`, with one SWA ring per layer, so the memory goes to full-context tokens instead; how much this adds depends on that reservation (see Speed Tests). DSpark is the only speculative decoding DeepSeek-V4.1 has (its `mtp.*` weights are the DSpark draft), and the InferenceY deployment of DeepSeek-V4.1-Flash runs with it, so the unified layout has to work with DSpark to be usable there. DeepSeek-V4 already runs fp8 unified KV with DSpark (#38901: the target on the fp8 rings, the draft on a bf16 ring of its own); this PR reuses that split for V4.1.

### Relation to #42197

The first commit is #42197 unchanged (author @AMD-yanfeiwang, head `ff4fa016`): the UMBP direct linker builds the C4 / C128 regions only when the model has those layers and registers the C1 / C2 pools. The PD / linker part of this PR builds on it, and the commit drops out on rebase once #42197 merges. **Please review only the last seven commits.**

## Modifications

1. `[Unified Cache][UMBP] Support DeepSeek-V4.1 and packed draft layers in the UMBP direct linker`: #42197, unchanged.
2. **FP8 unified KV for the ratio-1/2 kv_source groups**: one compressed region per kv_source group and one SWA ring per layer (`compress_row_base`); the c1 / c2 two-pool store (fp8 nope + bf16 rope); low-ratio decode streams; a packed fp8 query without q-norm (V4.1 has none); the hook admits the fp8 unified layout for V4.1. The FlyDSL v4 nm decode keys its split plan by stream kind; the ratio-1/2 streams (SWA prefix plus a top-k tail) take the CSA plan.
3. **Decode on par with paged KV**: RoPE inside the fp8 query packer, with the query pack and the ring K store in one launch; one decode stream per ratio-1/2 index source with metadata in two launches; on the asm decode, the inverse RoPE folded into the split merge, which loads all splits at once (the FlyDSL decode merges in its own launch and takes the inverse RoPE as a separate pass, or fused with the wo_a quant).
4. **Decoder SWA bounded replay and prefill CP**: the late layers' SWA floor (`pf_swa_floor`) in the prefill metadata; CP rows taken by the layout's `local_index`.
5. **Kernel tests** for the ratio-1/2 unified path, byte-for-byte against paged KV.
6. **PD / linker**: with the unified layout the ratio-1 and ratio-2 groups share one compressed region, so each group is registered once and its PD transfer and HiCache / linker mapping start at `compress_row_base`; the C1 / C2 rope side pools join the low-ratio regions (the nope half alone restores stale rope); the C4 / C128 rope regions are skipped when the model has no such layers; the hook admits unified + PD for V4.1.
7. **DSpark**: the hook admits DSpark with the unified layout on V4.1 (static verify, no PD yet). The target verifies through the fp8 decode streams, and its c1 / c2 compressors write the rows of the verified tokens through the same fused stores as paged KV; the draft keeps the bf16 ring of #38901. The V4.1 draft block attends to its request's last 128 committed positions and the whole block (bidirectional inside the block, as the paged draft's `BuildDsparkSwaPageIndices` does), while V4's draft reads a causal window: under the unified layout the backend now builds the V4.1 block window over the draft ring instead of falling back to the causal one, which would not fail but would lower acceptance. No grouped HCA verify streams are built for a model without ratio-128 layers. Tests: a c2 verify that rejects part of its draft and verifies again leaves the pool, the outputs and the pair-state ring exactly as a token-by-token decode of the accepted tokens; the draft block streams match `BuildDsparkSwaRingIndices` row for row; the hook cases.
8. **Verify metadata**: under DSpark every target step is a verify, so the target-verify metadata goes through the two-launch V4.1 builder too (a verify row is a decode row at its own position), with the grouped verify streams shared between both paths as V4 builds them.

## Supported scope and limitations

- Validated only on ROCm gfx950 (MI355X). The unified KV changes, including those in the shared DSV4 backend, only take effect with the unified layout.
- Unified KV on V4.1 is fp8 only. The hook rejects the bf16 unified layout, encoder SWA bounded replay and HiCache with the unified layout; with DSpark it also rejects compact ragged verify (`SGLANG_RAGGED_VERIFY_MODE=compact`; the default `static` is supported) and PD disaggregation (the draft ring of a ratio-1/2 model is not transferred yet).
- The image used here ships an aiter without ROCm/aiter#6377, so the FlyDSL v4 nm decode is unavailable and every run below took the asm decode; the FlyDSL path is covered only by the existing kernel tests.
- On HIP, V4.1 unified KV does not support the breakable prefill CUDA graph; the backend rejects it with `NotImplementedError`, and all runs use `--cuda-graph-backend-prefill disabled`.
- Decode with TP8 and no DP attention is blocked by the aiter fp8 decode kernel (no gqa=8 instance).
- The CP key dedup of #43806 is not included, so UMBP capacity and sharing across CP layouts are not guaranteed.

## Accuracy Tests

Setup: MI355X, DeepSeek-V4.1-Flash, image `rocm/sgl-dev:v0.5.21-rocm720-mi35x-20261015` with the branch's whole `python/sglang` mounted over the image's, this PR on main `617c8b67b`, model default context (1M). Unified environment: `SGLANG_HACK_FLASHMLA_BACKEND=unified_kv_triton SGLANG_DSV4_UNIFIED_KV_FP8=1`. Each comparison runs both servers on one node at the same time with the same command line except the two env vars. sgl-eval 0.1.3 GSM8K with the settings of `test_deepseek_v41_flash_gb300.py` (`--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash --max-tokens 4096 --num-threads 64`), all 1319 questions.

**Without speculative decoding** (TP4, `--fp8-gemm-backend aiter --kv-cache-dtype fp8_e4m3 --cuda-graph-backend-prefill disabled --prefill-decode-interval 32 --swa-prefix-tails 2048 --enable-decoder-swa-bounded-replay --max-running-requests 64 --mem-fraction-static 0.86`):

| KV layout | GSM8K |
|---|---|
| paged FP8 | 96.36% |
| fp8 unified | 96.29% |

**With DSpark**, the InferenceY DeepSeek-V4.1-Flash TP4 recipe (`--speculative-algorithm DSPARK --speculative-dspark-block-size 5`, `--enable-decoder-swa-bounded-replay`, `--prefill-decode-interval 96`, `--swa-prefix-tails 1024`, `--max-running-requests 32`, `--mem-fraction-static 0.70`, INT8 quick reduce, OPUS sparse prefill). Acceptance length is the server's `accept len`, averaged over the GSM8K run:

| KV layout | GSM8K | Acceptance length |
|---|---|---|
| paged FP8 | 95.98% | 3.48 |
| fp8 unified | 96.51% | 3.53 |

The same recipe together with #44730 (`--enable-prefill-cp --cp-strategy interleave --enable-cp-decode-attn-tp`, CP4), paged FP8 vs fp8 unified: GSM8K 96.51% / 96.29%, acceptance length 3.51 / 3.50.

No server faults or NaN in any run.

Unit tests: the kernel cases and the new pool / linker / DSpark cases pass. Other failures in the touched test files are the same on main.

## Speed Tests and Profiling

`bench_serving`, random token ids, 5 x concurrency requests (at least 16), the radix cache flushed before every run (random-ids prompts of one seed are prefixes of each other across runs, so an earlier run would otherwise warm the next one).

**Without speculative decoding**, the servers of the first GSM8K table.

**KV capacity**: `max_total_num_tokens` 60.48M (paged FP8) vs 68.54M (fp8 unified), +13% (this node reports about 27 GB less free memory per GPU than our other nodes, which lowers both). The paged layout reserves its SWA pool up front from `--swa-prefix-tails`, while the unified rings are sized by the request slots only, and a full-context token costs a little more in the unified layout; the gain therefore grows with `--swa-prefix-tails`, and with small tails the unified layout can hold fewer tokens than paged KV. With the InferenceY TP2 concurrency-64 settings (`--swa-prefix-tails 4096`, `--mem-fraction-static 0.85`, `--max-running-requests 128`, `--chunked-prefill-size 4096`, `--prefill-decode-interval 4`) and DSpark, paged FP8 KV holds 26.0M tokens, while fp8 unified together with #44730 (CP2 + decode-attention TP) holds 44.8M (+72%); GSM8K 96.29% / 96.59%, acceptance length 3.52 / 3.45, and per verify step the two are within 3% at 8k / 1k concurrency 32 and 64 and 64k / 1k concurrency 8.

Output tok/s and mean TPOT:

| Input / output | Concurrency | paged FP8 | fp8 unified |
|---|---|---|---|
| 8k / 1k | 1 | 179.5, 5.31 ms | 177.4, 5.38 ms |
| 8k / 1k | 4 | 541.5, 6.56 ms | 621.2, 6.11 ms |
| 8k / 1k | 16 | 1649.3, 8.75 ms | 1672.4, 8.60 ms |
| 8k / 1k | 64 | 3162.9, 16.98 ms | 3169.6, 16.93 ms |
| 64k / 1k | 1 | 155.4, 5.36 ms | 152.9, 5.45 ms |
| 64k / 1k | 4 | 376.6, 8.05 ms | 343.4, 7.94 ms |
| 64k / 1k | 16 | 529.1, 13.74 ms | 566.9, 12.86 ms |

A single request decodes 1–2% slower on the unified layout (TPOT 5.38 vs 5.31 ms at 8k / 1k, 5.45 vs 5.36 ms at 64k / 1k); from concurrency 16 on it is on par or ahead (64k / 1k concurrency 16: +7% throughput, -6% TPOT). Two points are pulled by a few slow first requests: paged KV at 8k / 1k concurrency 4 (P99 TTFT 5.7 s vs 0.9 s) and fp8 unified at 64k / 1k concurrency 4 (P99 TTFT 9.8 s vs 4.4 s). Each point is a single run.

**With DSpark**, the servers of the second GSM8K table: `max_total_num_tokens` 49.5M (paged FP8) vs 52.6M (fp8 unified), +6% at `--swa-prefix-tails 1024`. Output tok/s, mean TPOT and the mean acceptance length over the run:

| Input / output | Concurrency | paged FP8 | fp8 unified |
|---|---|---|---|
| 8k / 1k | 1 | 577, 1.59 ms, 4.44 | 664, 1.36 ms, 5.24 |
| 8k / 1k | 16 | 1559, 2.33 ms, 4.96 | 1773, 2.21 ms, 5.04 |
| 64k / 1k | 1 | 365, 1.39 ms, 5.13 | 419, 1.35 ms, 5.37 |
| 64k / 1k | 4 | 481, 1.54 ms, 5.46 | 461, 1.62 ms, 5.34 |

With DSpark the throughput follows the acceptance of the generated text, which differs between the two layouts on random prompts. Per verify step (TPOT x acceptance length) the unified layout is within 1–3% of paged KV (8.65 vs 8.41 ms at 64k / 1k concurrency 4, 11.14 vs 11.57 ms at 8k / 1k concurrency 16); its mean TTFT at 64k / 1k concurrency 1 is 1.06 s vs 1.38 s. With #44730 on top (CP4 + decode-attention TP), the per-step time is 1.6–2.2% above paged KV across the same four points.
