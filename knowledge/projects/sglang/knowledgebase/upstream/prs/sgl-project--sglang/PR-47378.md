# [Feat] diffusion: Support Pika-Labs/Pika-H3-Flex (MiniMax-H3 + 6-step LoRA)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47378) · state: closed · merged: True

## Original PR description

## Motivation

Add [Pika-Labs/Pika-H3-Flex](https://huggingface.co/Pika-Labs/Pika-H3-Flex) to SGLang Diffusion.

Pika H3 Flex is not a new checkpoint. It is MiniMax-H3 plus two FP32 LoRA adapters (rank/alpha 128): `fl2va` covers t2va/fl2va and `ref2va` covers ref2va. The adapters were post-trained for a fixed six-step sampler:

- knots `1000/750/500/250/100/40`, shifted per modality (video 12, audio 3)
- a re-noising update: predict x0, then re-noise to the next sigma with fresh noise

`--model-path Pika-Labs/Pika-H3-Flex` serves t2va/fl2va, and `--model-variant ref2va` serves ref2va. It runs on the native MiniMax-H3 pipeline, so the existing H3 kernels, caches and parallelism apply.


https://github.com/user-attachments/assets/cc36c135-3b78-4886-9af2-42206e42434a


## Why not a plain distilled LoRA

The adapters are ordinary PEFT LoRAs and are applied through the existing LoRA path. A plain `--lora-path` recipe, like the Larry/LightX2V Turbo LoRAs in the H3 cookbook, is still not enough:

| | Plain distilled LoRA recipe | Pika H3 Flex |
|---|---|---|
| Launch | `--model-path MiniMaxAI/MiniMax-H3 --lora-path … --lora-weight-name …` | `--model-path Pika-Labs/Pika-H3-Flex [--model-variant ref2va]` |
| Schedule | `num_inference_steps` on the uniform `linspace(1, 0)` grid | fixed knots `1000/750/500/250/100/40`, shifted per modality |
| Update rule | Euler blend | re-noise: x0, then fresh noise to the next sigma |
| Adapter choice | the user picks the file and must match it to the partition | the overlay pairs `fl2va`→FL2VA and `ref2va`→Ref2VA, pins the base revision, and verifies sha256 |

Neither the schedule nor the update rule can be expressed on the request today. Loading the adapter with `--lora-path` and `num_inference_steps: 6` runs uniform-grid Euler, which Pika's README calls "not equivalent". Both are therefore opt-in fields in `model_index.json._minimax_h3`. Base H3, FastH3 and existing LoRA recipes are unaffected.

## Modifications

The sampler follows diffusers `modular_pipelines/pika_h3_flex` and `MiniMaxH3Scheduler(stochastic_sampling=True)`, at the commit pinned by Pika's examples (`d0b9b1b5`). Each commit is one item:

1. **Overlay + partition subfolder fix.** `--model-subfolder` / `--model-variant` skipped overlay resolution: the raw source repo was downloaded with a subfolder pattern and never materialized. This affects any partitioned overlay. The fix resolves the overlay root first, for a registered overlay id or a local overlay dir.
2. **Re-noising sampler.** `x0 = x + σ·v` from the grid sigma, then `x_next = (1-σ')·x0 + σ'·noise` for both modalities, with video noise drawn first. The terminal `σ' = 0` step returns x0.
   - The noise comes from a per-output device generator seeded with `plan.seed`, so each output of an expanded request gets its own stream. The stream stays independent of the CPU generators that use the same seed for the initial and condition noise.
   - Off by default.
3. **Release metadata.** `model_index.json._minimax_h3` can declare two new fields, both validated:
   - `stochastic_sampling`, which requires `dmd_denoising_steps`; the existing field already carries the knots.
   - `lora_adapter`, a relative `.safetensors` loaded as the startup LoRA. `--lora-path` cannot replace it.
4. **Pika registration.**
   - Adds `PikaH3FlexPipeline` / `PikaH3FlexSamplingParams` (fixed 6 steps) / `PikaH3FlexPipelineConfig`, plus tests.
   - Adds the [`Niehen6174/Pika-H3-Flex-overlay`](https://huggingface.co/Niehen6174/Pika-H3-Flex-overlay) overlay, pinned to `2d8d5e4d`. It downloads only the two adapters (~5.5 GB) and checks each one's sha256 and sampling contract against Pika's manifest. It then links the base `FL2VA/` and `Ref2VA/` partitions from `MiniMaxAI/MiniMax-H3` at the revision the adapters pin (`42ed227e`).
   - The PEFT keys map through the existing H3 LoRA mapping, covering 208/208 layers (52 blocks × qkv/out/fc1/fc2).
5. **Docs.** A "Pika H3 Flex: six-step adapters" subsection in the MiniMax-H3 cookbook's LoRA chapter, and a model-catalog entry.

## Accuracy / Validation

Setup: 1×H200, `--model-path Pika-Labs/Pika-H3-Flex` through the published overlay, default memory policy, seed 42. Inputs are the official examples in `Pika-H3-Flex/examples/assets`.

| Task | Canvas | Frames | Gen (cold) | Gen (warm) | Denoise (6 steps) | Decode |
|---|---|---|---|---|---|---|
| t2va | 1344×768 | 124 (5 s) + stereo audio | 38.3 s | 37.1 s | 26.8 s | 4.3 s |
| fl2va (first frame) | 1344×768 | 124 (5 s) + stereo audio | 42.3 s | – | – | – |
| ref2va (2 images + 1 video w/ audio) | 1344×768 | 124 (5 s) + stereo audio | 284.0 s | 260.4 s | 183.2 s | 4.3 s |
| t2va | 864×480 | 124 (5 s) + stereo audio | 13.5 s | 11.5 s | – | – |

- **Quality:** outputs are visually coherent at 6 NFE and follow their conditions.
  - fl2va starts on the given frame and follows the multi-shot prompt with hard cuts.
  - ref2va reproduces the character sheet and the environment, and takes its motion from the reference video.
- **ref2va latency:** the packed sequence is long (a 10 s reference video plus two 2048-px reference images), so denoise runs at about 30 s/step.
- **Unit tests:** `test_minimax_h3_pika_flex.py` (5 tests) passes. The rest of `test_minimax_h3_*.py`, `test_comfyui_h3.py`, `test_lora_format_adapter.py` and `test_server_args.py` pass on H200 (594 passed, 3 xfailed, 204 subtests).

## Known differences from the Pika package

- **RNG:** noise streams differ from diffusers, so a seed does not reproduce the diffusers sample bit-for-bit. The sampler math is the same. The knot grid is shifted in float32 rather than float64, about 1e-8 apart.
- **Canvas:** 768p at 21:9/16:9/4:3/1:1/3:4/9:16 matches Pika's buckets.
  - Pika caps area per tier: its 480p 16:9 bucket is 832×480, where H3 gives 864×480.
  - Pika's 3:2/5:4/4:5/2:3/9:21 buckets are not in H3's aspect-ratio list.
  - ref2va image references are encoded at 2048 short edge at every tier, where Pika uses 1024 below 768p.
  - A tiered canvas policy is planned as a follow-up PR because it changes H3 geometry.
- **fl2va conditioning:** Pika rounds keyframe latents through bf16 and center-crops keyframes to the canvas aspect. H3 keeps fp32 latents and stretches the first keyframe. With the default auto aspect the canvas follows the keyframe, so the fit differs only by rounding.
- **ref2va limits:** each reference must be 2–15 s, with totals ≤ 15 s. These follow H3's existing validation rather than Pika's package checks.
