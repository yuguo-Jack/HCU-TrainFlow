# Implemented MXFP8 quant lightning indexer for DSA

[Upstream PR](https://github.com/sgl-project/sglang/pull/40591) · state: open · merged: False

## Original PR description

## Motivation

On Ascend NPU, the DSA Lightning Indexer (LI) already runs quantized when the KV cache is FP8, but it quantizes **per token** (one FP32 scale per token) and calls `torch_npu.npu_quant_lightning_indexer` (v1).

This PR moves the quantized indexer to **MXFP8** (microscaling FP8: one E8M0 scale per 32-element block) and to the v2 kernel from CANN ops-transformer. Block scales lose less accuracy than one scale per token, so the quantized indexer gets faster without the accuracy drop (see results below).

The v2 kernel is two ops:

1. `torch.ops.cann_ops_transformer.quant_lightning_indexer_metadata` plans the load balance (a task list) from the batch shape only. That plan is the same for every indexer layer, so it runs **once per forward**, not once per layer.
2. `torch.ops.cann_ops_transformer.quant_lightning_indexer` does the indexer computation using that plan.

MXFP8 (`quant_mode=3`) in the v2 kernel is supported on Ascend 950 only.

## Modifications

**`hardware_backend/npu/attention/ascend_backend.py`**
- New `_plan_quant_indexer_metadata`, called from `init_forward_metadata`. It builds `cu_seqlens_q` (int32, 0-prefixed, `(b+1,)`), `seqused_k` (int32, `(b,)`) and the metadata tensor, and stores all three on `ForwardMetadata` for every indexer layer to reuse.
- Planning is skipped when the quant indexer is off, and for context-parallel extend, which takes a different indexer path and never calls the v2 kernel.

**`layers/attention/dsa/dsa_npu_indexer.py`**
- `_quantize_npu_indexer_activation` now uses `npu_dynamic_mx_quant` and returns E8M0 block scales shaped `(..., d/64, 2)`, the descale layout the v2 kernel expects.
- The v1 `npu_quant_lightning_indexer` call is replaced by the v2 `quant_lightning_indexer` call (`layout_k` `PA_BSND` → `PA_BBND`, `cu_seqlens_q` / `seqused_k` / `metadata` arguments, `weights` cast to fp32).
- If the backend did not pre-plan the metadata (for example under graph capture), the indexer computes it inline.
- New `_check_quant_lightning_indexer_constraints`: `PA_BBND` requires a page size in `[16, 1024]` that is a multiple of 16. A wrong page size now fails with a clear message (use `--page-size 64`) instead of an error inside the kernel.
- Imports `cann_ops_transformer` on NPU so the `torch.ops.cann_ops_transformer` namespace is registered.

**`hardware_backend/npu/memory_pool_npu.py`**
- The index-K scale cache changes from one FP32 value per token to MX scales: `uint8` storage, per-token shape `(k_n, d/64, 2)`. Each token still takes 4 bytes per indexer layer, so KV pool capacity does not change.
- `get_index_k_scale_buffer` returns a `float8_e8m0fnu` view of that storage. `set_index_k_scale_buffer` writes whole per-token scale rows and asserts that the scale is 1 byte per element.

**`mem_cache/pool_host/mla.py`** (HiCache)
- The host mirror of the scale cache takes its shape and dtype from the device pool, so the two match byte for byte. The size per token is still 4 bytes, so host pool sizing and page pointer arithmetic do not change. Only the comments are updated.

**Tests**
- `test_npu_ascend_backend.py`: per-forward metadata planning for plain extend and decode, int64 → int32 cast, and the CP-extend and disabled cases are skipped.
- `test_npu_quant_lightning_indexer.py` (new): page-size constraint check, MX quantization shapes, dtypes, empty input and dequant round-trip, and smoke tests for the metadata op and the full kernel.
- `test_npu_dsa_index_k_scale_pool.py` (new): scale-cache layout, E8M0 view, set/get round trip across pages, per-layer slot isolation, and that the HiCache host mirror matches the device pool.
