# Stack Overview: Token-Space Multimodal Processing in SGLang

This post explains the multimodal processor after a six-PR stack ([#43420](https://github.com/sgl-project/sglang/pull/43420), [#43421](https://github.com/sgl-project/sglang/pull/43421), [#43422](https://github.com/sgl-project/sglang/pull/43422), [#43423](https://github.com/sgl-project/sglang/pull/43423), [#43963](https://github.com/sgl-project/sglang/pull/43963), [#43964](https://github.com/sgl-project/sglang/pull/43964)). The goal is a clear mental model: what the new pieces are, how one request moves through them, and where they connect to the processor code that already existed.

## Why change the processor

A vision-language prompt contains a few **placeholder tokens**. A placeholder token stands for one media item, such as one image or one video. A **media item** is a single image, video or audio clip in a request.

The model cannot use a single placeholder. It needs one token per visual patch (or per audio frame). Replacing each placeholder with the right number of tokens is called **expansion**. An image that produces 224 patches turns one `<|image_pad|>` into 224 of them.

Today SGLang does expansion inside the Hugging Face (HF) processor. The call looks like `processor(text=prompt, images=...)`. The HF processor expands placeholders **in the prompt string** and then tokenizes the whole string again.

This works well for plain chat serving. It is a poor fit for two other callers:

- **RL rollout and multi-turn agents.** These callers already hold the exact token IDs of the conversation. Turning the IDs back into text and tokenizing again can change them.
- **Training.** The trainer must see the same image features that serving produced. Today the feature code lives inside serving classes that need a full server to construct.

The stack adds a second way to process multimodal input. It works directly on token IDs, so we call it **token space**: expansion edits the `input_ids` list, not the prompt string. We call the existing approach the **legacy route** and the new approach the **token-space route**. The legacy route stays the default and is unchanged in behavior.

## Building blocks

The token-space route is made of a few small parts. We introduce them one at a time, then put them together in the next section.

### BatchFeature

`BatchFeature` is the HF container that a processor returns. It holds `input_ids`, `attention_mask` and the media tensors, such as `pixel_values` and `image_grid_thw`. The token-space route produces a `BatchFeature` with the same fields and values as the HF processor. A trainer can use it directly.

### The strategy: `TokenSpaceProcessStrategy`

A strategy holds the model-specific logic. It has no threads, no caches and no server state. Every method is a plain function of its inputs:

| Method                                            | What it does                                                 |
| ------------------------------------------------- | ------------------------------------------------------------ |
| `process_image`, `process_video`, `process_audio` | Run the HF media processor on **one** media item, with no prompt text |
| `merge_media`                                     | Combine the per-item results into one set of media features, in request order |
| `get_mm_token_expansion_spec`                     | List the replacement rules: which token sequence to find, and which token sequence replaces it for each media item |
| `expand_media_tokens`                             | Apply those rules to `input_ids`                             |
| `build_processor_output`                          | Assemble the final `BatchFeature`                            |

The Qwen family uses `QwenTokenSpaceProcessStrategy` (`token_space/qwen_vl.py`). Other models add their own subclass.

Each media item is processed alone. As a result, the output for an image never depends on which other images arrived in the same request.

### Expansion spec and partial expansion

The **expansion spec** is the output of `get_mm_token_expansion_spec`. It is a list of replacement rules, one per modality. Each rule is a pair:

- a **pattern**: the placeholder token sequence to find in `input_ids`;
- a list of **fragments**: the token sequence that replaces the pattern, one fragment per media item of that modality, in request order.

For Qwen3-VL the spec looks like this:

```text
[
  ([<image_pad>], [ fragment for image 1, fragment for image 2, ... ]),
  ([<video_pad>], [ fragment for video 1, ... ]),
]

fragment for an image  = <image_pad> × (patches / merge_size²)
fragment for a video   = for each frame group:
                         "<t seconds>" tokens, <vision_start>, <video_pad> × N, <vision_end>
```

A fragment is a full token sequence, not just a count. This is why one mechanism covers both cases: the image fragment repeats one token, and the Qwen3-VL video fragment also inserts timestamp tokens and frame boundaries.

`expand_media_tokens` scans `input_ids` from left to right. Each time a pattern matches, it writes the next fragment of that rule in place of the pattern. Inserted tokens are never scanned again. The expansion only reads `input_ids` and the spec; it never decodes tokens back to text.

The request can also carry `mm_token_expansion_start_len`. Expansion leaves the first `start_len` tokens untouched and only expands placeholders after that point. A multi-turn caller uses it to keep an already-expanded history as it is:

```text
turn 1   start_len = 0
  in : <user> <vision_start><image_pad><vision_end> describe ... <assistant>
  out: <user> <vision_start><image_pad>×224<vision_end> describe ... <assistant>

turn 2   start_len = length of turn 1 output + response
  in : [turn 1 tokens, kept as is] <user> <vision_start><image_pad><vision_end> and this one?
  out: [turn 1 tokens, unchanged ] <user> <vision_start><image_pad>×196<vision_end> and this one?
```

The request still sends every media item, so every rule still holds one fragment per media item in the whole conversation. When the expansion finds k patterns of a rule after `start_len`, it uses the last k fragments of that rule. The request fails with an error if a rule finds more patterns than it has fragments. With `start_len = 0`, the two counts must be equal.

### The mixin: `MultimodalProcessorMixin`

The strategy computes, but it does not schedule work. The mixin does. It lives in `media_processor.py` and owns:

- media loading (`_load_media_lists`, `fast_load_mm_data`) on an IO worker pool;
- the processor worker pool, where `process_media_async` runs one task per media item;
- the token-space pipeline itself (`load_and_process_token_space_async`), which calls the strategy methods in order.

The mixin does not import `ServerArgs` or any serving module. Its loading and pool code was moved out of `BaseMultimodalProcessor` without changes, so the legacy route runs the same code as before.

### `MultimodalProcessorConfig`

Before the stack, the processor read its settings from `ServerArgs`. A trainer has no `ServerArgs`. `MultimodalProcessorConfig` is a small frozen dataclass with only the settings a processor needs at init:

| Field                                                        | Meaning                            |
| ------------------------------------------------------------ | ---------------------------------- |
| `image_processor_backend`, `disable_fast_image_processor`    | Which HF image processor to use    |
| `mm_process_config`                                          | Per-modality processor kwargs      |
| `mm_processor_worker_num`, `mm_io_worker_num`, `cpu_worker_num`, `cpu_process_start_method` | Worker pool sizes and start method |
| `allowed_media_domains`, `media_url_max_file_size_mb`        | Media URL policy                   |
| `keep_mm_features_on_device`                                 | Whether features stay on the GPU   |

Serving fills it from `ServerArgs`. A trainer builds it directly.

### Hosts: who owns the mixin and the strategy

A **host** is a class that inherits the mixin and holds a strategy. There are two:

- `StandaloneTokenSpaceProcessor` is the training host. It is the mixin plus a strategy and nothing else. It can be imported without starting SGLang serving.
- `TokenSpaceMultimodalProcessor` is the serving host. It also inherits `BaseMultimodalProcessor`, which adds serving state: the preprocess cache, the hash executor and the transport to the scheduler.

Both hosts run the same mixin code and hold the same strategy class. Given the same devices and config, they produce the same `BatchFeature`.

### The output builder: `MultimodalProcessorOutputBuilder`

The scheduler does not consume a `BatchFeature`. It consumes a `MultimodalProcessorOutput`, which adds padded `input_ids`, per-item offsets and, for Qwen, M-RoPE positions. The output builder turns one into the other. The Qwen family uses `QwenVLMultimodalProcessorOutputBuilder`.

The output builder is serving-only. A trainer never needs it.

The legacy `QwenVLImageProcessor` used to compute this tail inline. The stack moved that code into the output builder. Now the legacy route and the token-space route call the same builder, so serving output is assembled in one place.

## Putting it together: one request

<img width="2320" height="2080" alt="token-space-pipeline" src="https://github.com/user-attachments/assets/a5a58291-9514-4722-909a-4603547b5784" />


The figure shows one request from input to output. Each box carries a tag for the part that owns it (mixin, strategy, output builder or `TokenSpaceMultimodalProcessor`) and a badge for the PR that added it.

1. **Inputs.** The caller passes `input_ids`, an optional `mm_token_expansion_start_len` and the raw media. In serving, the tokenizer manager passes token IDs instead of text, because the token-space processor sets `prefer_tokenized_input = True`.
2. **Load.** The mixin loads every media item with `_load_media_lists` on the IO pool.
3. **Process each item.** `process_media_async` starts one task per media item. Each task calls the strategy's `process_image`, `process_video` or `process_audio`.
4. **Merge.** `merge_media` combines the per-item results into one set of media features.
5. **Expand.** `get_mm_token_expansion_spec` reads the media features and returns the expansion spec. `expand_media_tokens` applies it to `input_ids`, after `start_len`.
6. **Build.** `build_processor_output` combines the expanded `input_ids` and the media features into an HF-shaped `BatchFeature`.

Steps 2 to 6 are shared by training and serving. After step 6 the two callers split:

- **Training** takes the `BatchFeature` from `StandaloneTokenSpaceProcessor` and feeds the model, for example through the Megatron bridge.
- **Serving** continues in `TokenSpaceMultimodalProcessor.sglang_post_process`. It collects the media items, binds each item to its offset in `input_ids`, then calls `output_builder.build`. The result is a `MultimodalProcessorOutput` for the scheduler.

The boundary is simple. The strategy decides *what* the `BatchFeature` contains. The output builder decides *how* serving packages it for the scheduler.

## Where the stack connects to existing code

<img width="2320" height="1600" alt="token-space-classes" src="https://github.com/user-attachments/assets/52a0f71d-e714-4b7d-aa85-c4c8902f1a19" />


On the left is the old structure. `BaseMultimodalProcessor` read `ServerArgs` directly, and `QwenVLImageProcessor` called the HF processor with text and media together.

On the right is the new structure. Read it from top to bottom:

- **Shared pieces.** `modality.py` (PR1) holds `Modality` and `MultimodalInputFormat`, which both routes import. `MultimodalProcessorConfig` (PR2) replaces direct reads of `ServerArgs`. `MultimodalProcessorMixin` (PR3, PR4) holds loading, pools and the token-space pipeline.
- **Training.** `StandaloneTokenSpaceProcessor` (PR4) inherits only the mixin and holds `QwenTokenSpaceProcessStrategy`.
- **Serving base.** `BaseMultimodalProcessor` (PR2, PR3) now inherits the mixin and keeps only serving state.
- **Legacy route.** `QwenVLImageProcessor` still calls the HF processor on the prompt string. Its only structural change is that it holds a `QwenVLMultimodalProcessorOutputBuilder` (PR5) instead of computing the output inline.
- **Token-space route.** `TokenSpaceMultimodalProcessor` (PR4) is the serving host. `QwenVLTokenSpaceProcessor` (PR5) subclasses it for Qwen. It holds the same strategy class as the training host and the same output builder class as the legacy route. The dashed lines in the figure mark these shared classes.

Two places decide which route a request takes:

- **`get_mm_processor_cls` (PR6)** runs at startup. It returns the token-space processor only when `--enable-token-space-processor` is set and the model is supported. Otherwise it returns the legacy processor, as before. Token-space processors are registered in a separate `TOKEN_SPACE_PROCESSOR_MAPPING`, so they never replace a legacy processor.
- **`TokenizerManager` (PR6)** passes token IDs to a token-space processor. It rejects `mm_token_expansion_start_len` when the selected processor is on the legacy route.

Every move of existing code is a mechanical move: a separate commit that only relocates code. Each one ships a script that replays the move on the parent commit and reproduces the commit's tree byte for byte.

## Adding a model

1. **Strategy.** Subclass `TokenSpaceProcessStrategy`. Implement `process_image`, `process_video` or `process_audio`, the matching `merge_*_features` and `get_mm_token_expansion_spec`. This is all a trainer needs: `StandaloneTokenSpaceProcessor(hf_config, hf_processor, MyStrategy)`.
2. **Output builder, only if needed.** Subclass `MultimodalProcessorOutputBuilder` when the model needs extra serving output, such as M-RoPE positions.
3. **Serving processor.** Subclass `TokenSpaceMultimodalProcessor` and set the model list, the strategy class and the output builder class. It is registered in `TOKEN_SPACE_PROCESSOR_MAPPING` only.
4. **Parity test.** Compare the legacy route and the token-space route bit for bit on the processor output.
