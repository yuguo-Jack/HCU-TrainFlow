# feat(diffusion): parallelize heavy component loading with ThreadPoolExecutor

[Upstream PR](https://github.com/sgl-project/sglang/pull/44127) · state: closed · merged: False

## Original PR description

## Summary

Fixes #19092

Diffusion server launch is bottlenecked by sequential module loading (`load_modules` ~63s / 77s total), where `text_encoder` (~33s) and `transformer` (~30s) dominate and are independent during instantiation and weight-loading.

This PR parallelizes the heavy component loading using `concurrent.futures.ThreadPoolExecutor`.

## Changes

In `composed_pipeline_base.py`, the sequential load loop is split into two phases:

1. **Small helpers** (`vae`, `tokenizer`, `scheduler`, `image_processor`, ...) -> keep serial (sub-second each, no bottleneck).
2. **Heavy models** (`transformer*`, `text_encoder*`, `transformer_2`) -> load in parallel via `ThreadPoolExecutor(max_workers=2)`.

Thread safety: each worker thread explicitly sets the correct device (`cuda:{LOCAL_RANK}` etc.) because CUDA/NPU `current_device` is thread-local and worker threads do not inherit the main thread's selection.

Single heavy-component pipelines gracefully fall back to serial loading (no thread-pool overhead).

## Expected impact

- Launch time should drop from ~63s to ~max(33s, 30s) ≈ **33s** on typical pipelines like Qwen-Image.
- Only one file changed; no CUDA/C++ touched; pure Python.

## Risk / Notes

- Peak CPU memory doubles during the heavy phase (two state dicts resident simultaneously). We keep `max_workers=2` to bound this.
- Only verified conceptually; a real benchmark on a GPU runner would confirm the end-to-end speedup.
