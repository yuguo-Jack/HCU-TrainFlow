# [Fix] hicache: vote the prefetch timeout once per tick, not per admission poll

[Upstream PR](https://github.com/sgl-project/sglang/pull/47620) · state: open · merged: False

## Original PR description

## Motivation

Under `--hicache-storage-prefetch-policy timeout` (the default) the per-request deadline verdict is agreed by a collective issued from inside the admission loop: `check_prefetch_progress` calls `_can_terminate_prefetch`, which on main does one `_all_reduce(MAX)` per call (`python/sglang/srt/mem_cache/unified_radix_cache.py:2480-2490` on `1ad0149814`). The scheduler issues that call once per waiting request with a live prefetch per scheduling pass (`python/sglang/srt/managers/scheduler.py:4543`), and the loop's exits around it (`batch_is_full` from `get_num_allocatable_reqs`, `scheduler.py:4406-4411` and `4528-4540`) are evaluated by each rank on its own. That is the shape reported in #30760 (TP=4, no PP): one rank examined one more candidate than its peers before its own `batch_is_full` tripped, called the collective one more time, and waited in it forever while the others had moved on to `recv_requests`. #44614 centralized the per-request budget (`_StoragePrefetchWait`, started at the first blocked poll, `_prefetch_deadline_expired`, `_mark_prefetch_deadline_expired`) but left the vote in the poll; #36425 had moved the vote into `_can_terminate_prefetch`; #33029 and #44340 (both closed, not merged) proposed a once-per-tick vote, and this PR reuses that part of #44340.

This PR removes the per-poll collective that #30760 reported and makes the remaining rank-consistency premise (every rank polls the same requests) fail loud in the same tick on every rank instead of hanging. Even when the counts match, the per-poll vote costs one gloo all_reduce per waiting request per pass (prior measurements: roughly 60-80 us at TP2 and 0.6-0.9 ms at TP8), paid for every request parked behind a slow storage lookup.

## Modifications

All in `python/sglang/srt/mem_cache/unified_radix_cache.py`; no new flags, no new collective.

- `_vote_prefetch_deadlines` (lines 2492-2520) runs once per scheduler tick from `check_hicache_events`, after the storage drain, under storage only (lines 3985-3987). It packs one int per live prefetch, in `ongoing_prefetch` insertion order, evaluated on PP rank 0 with the existing `_prefetch_deadline_expired` (a wait that has not started yet contributes 0), does ONE `_all_reduce(MAX)` (line 2516: TP MAX on PP0, relayed along PP by `_pp_sync`, lines 428-462 (`_all_reduce` and `_pp_sync`)), and for every 1 calls the existing `_mark_prefetch_deadline_expired` and `cache_controller.terminate_prefetch` (lines 2519-2520), so every rank records the same verdict in the same tick and the transfer worker and the hit drain stop spending on the cut span at once (the drain already handles a terminated operation: `is_terminated()` at lines 3279 and 3402, with the `deadline` reason at 3407 and no retry at 3416). With no live prefetch no rank issues a collective. The vote runs only under policy `timeout`; `best_effort` and `wait_complete` never vote.
- `_can_terminate_prefetch` under `timeout` (lines 2482-2489) returns the recorded verdict (`wait.expired`) and issues no collective. It keeps `@rank_consensus(same_results=True)`: the verdict is rank-agreed by the vote. Since the vote also terminates, a poll on an expired operation normally takes the existing `is_terminated()` path (line 2631); retirement (`terminate_prefetch`, the `deadline` reason, `revoke_pending_prefetch` / `_handle_prefetch_result`, lines 2638-2647) is unchanged and still happens at the poll, or at the lockstep drain when the hit or the final ack lands first (lines 3402-3419 and 3440-3459). A parked hit cut by the vote is finished with the `deadline` reason before its revoke (lines 3279-3283), as the poll would.
- `check_prefetch_progress` is now collective-free for all three policies: `best_effort` returns True (line 2477), `wait_complete` returns False (line 2481), `timeout` reads the verdict (line 2489). The only collective reachable from an admission poll is the PP ticket path's own MAX in `_check_pp_prefetch_progress` (line 2556), left as is. The remaining `_all_reduce*` call sites in the file are the tick's own syncs (`_sync_hicache_ready_counts` lines 3700/3702, `writing_check`, `loading_check`, the linker round), the synchronous hit query helper (line 2254) and `drain_storage_control_queues`, which only the GPU test kits call.
- Rank consistency of the vote's shape, made fail-loud: `ongoing_prefetch` is filled by `prefetch_from_storage` (`@rank_consensus`, line 2260) and emptied by the lockstep drain and by the admission polls. The polls retire per rank, so the number and length of the packed vote would depend on the premise that every rank polls the same requests (#30760's maintainer position: `get_num_allocatable_reqs`, hence the poll sequence, is identical across TP ranks). `_hicache_sync_digest` (lines 2522-2540) folds the live prefetch set (rids and attempt ids in insertion order, crc32) into the digest the ready-count MIN sync already carries as `[digest, -digest]` (line 3674; asserts at 3682-3685 for the shm path and 3705-3708 for the gloo path, which also covers PP stages through the relay). A divergent set therefore raises on every rank at the start of the next tick, before any vote is issued, instead of one rank blocking in a vote its peer never issues or the two voting on tensors of different length. The row width is unchanged, so the shm fast path (8-slot table) is unaffected; the fold is active only when the vote would read the dict (storage on, policy `timeout`, non-empty). Main is exposed to the same premise one step earlier (the poll's own collective) and hangs; other policies keep main's behavior.
- In PP ticket mode (`buffer_only`, PP > 1) no entry is ever kept in `ongoing_prefetch`: PP > 0 returns at line 2283 (`get_prefetch_submission` returns an empty submission, `hybrid_cache_controller.py:1102`) and PP0 returns at line 2415 (`submit_prefetch` returns `decision=True`, `hybrid_cache_controller.py:1173`), so the vote never runs there and the PP relay of `_all_reduce` is only exercised in cache-mode PP.

Behavior changes to be aware of: a request whose budget ran out is cut on every rank at the next tick's vote instead of at its own poll, so the cut can land up to one tick later than before; between the vote and the poll the operation is terminated but still listed, so a hit or final ack landing in that window is settled by the drain (same outcome accounting path as a controller-terminated query: `revoked` outcome plus `deadline` reason) rather than by the poll.

Companion note for downstream forks that subclass the tick (prod_inference's Meta subclass runs its own packed buffer-mode vote and per-poll agreement before calling `super().check_hicache_events()`): after this change that subclass should either override `_vote_prefetch_deadlines` to a no-op in buffer mode or drop its own vote in favor of this one, to avoid two packed collectives per tick; both feed the same `_mark_prefetch_deadline_expired` / `wait.expired` state, so they agree either way.

## Accuracy Tests

No model-output change: the policy's verdict is the same `_prefetch_deadline_expired` evaluation, agreed by the same MAX, read by the same poll.

CPU unit tests, `test/registered/unit/mem_cache/test_storage_prefetch_lifecycle.py`, `TestStoragePrefetchTimeout` (line 444):

- `test_polls_never_reduce_and_the_tick_votes_once` (line 445): five live prefetches, four polled in one pass issue 0 collectives; the tick issues exactly one MAX over `[0,0,0,0,0]`; at a time long past the budget the four polls still return False and issue nothing, the next tick votes `[1,1,1,1,0]` (the never-polled request's wait never started), the four voted operations are terminated by the tick and the parked one is not, every polled request is then cut by its poll with no retry armed; `best_effort`, `wait_complete` and an empty `ongoing_prefetch` issue no collective.
- `test_expiry_is_agreed_even_before_a_peer_starts_waiting` (line 499, two-rank gloo, `_two_rank_prefetch_deadline` line 250): only rank 0 started the wait and only its clock ran out; rank 0 polls (returns False, no collective) while rank 1 does not poll; the tick marks the operation expired on both ranks with one collective each; the poll on both returns True; neither rank re-issues the prefetch. Adapted from main's version, which asserted that the poll itself returned True on both ranks: that assertion pinned the per-poll vote this PR removes, so the agreement is now asserted after the tick, and the polls are asserted not to reduce.
- `test_uneven_polls_before_a_verdict_issue_no_collective` (line 510, two-rank gloo, `_two_rank_uneven_polls` line 287): #30760's trigger before any verdict; both ranks start two waits, then rank 0 polls two requests and rank 1 one; no collective is issued by the polls, the tick votes `[1,1]` once on each rank, and both ranks retire both requests with the same verdicts. Against the old per-poll vote (main's `_can_terminate_prefetch` body patched in) it fails at its first uneven poll, which votes and cuts by itself.
- `test_divergent_live_prefetch_sets_raise_on_every_rank_in_the_same_tick` (line 520, two-rank gloo, `_two_rank_divergent_live_sets` line 324): #30760's shape after a verdict; after an agreed `[1,1]` vote rank 0 polls two requests and rank 1 one, so the live sets differ by one entry; the next tick's ready-count sync raises the digest assertion on both ranks (checked with `all_gather_object`), and the sequence of collectives is identical on both (`MIN, MAX, MIN`: no vote was issued with mismatched lengths). With the fold removed from `_hicache_sync_digest` (scratch negative control) the same worker fails differently: rank 0 issues no vote and the peer waits alone in its one-element MAX until the gloo timeout (`Timed out waiting 30000ms for send operation to complete`).
- `test/registered/unit/mem_cache/test_hicache_pp_sync_drain.py`: `test_pp_relays_the_deadline_vote_after_the_counts` (line 90) runs the tick on a cache-mode PP0 and a PP1 stage, each with one live prefetch: PP0 reads its own clock, issues the counts (8-slot MIN) and then the vote `[1]` (MAX), marks and terminates; PP1 contributes `[0]`, never evaluates `_prefetch_deadline_expired`, receives `[1]` second on the same path and marks and terminates the same way. The fixture (lines 32-35) now carries `prefetch_stop_policy` and an empty `ongoing_prefetch`; the two existing cases are unchanged, and the buffer-mode follower's `_all_reduce.assert_not_called()` now also pins that an empty vote issues nothing.

## Speed Tests and Profiling

Collectives per scheduling pass with N waiting requests under `timeout`: main 1 (ready-count sync) + N; this PR 2 (ready-count sync + one packed vote), 1 when no prefetch is live. The digest fold adds a crc32 over the live rids per tick on every rank (no extra slot, no extra collective). Not re-measured on GPU for this revision; the per-request gloo cost quoted in Motivation (60-80 us at TP2, 0.6-0.9 ms at TP8) is a prior measurement, not one from this revision.

Not run: GPU serving, PP > 1 end to end, PD disaggregation, mooncake/hf3fs/nixl backends. The repository CI was not triggered.
