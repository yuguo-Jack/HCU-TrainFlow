# [Feat] rust-server: Carry customized_info through the native /generate frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/46949) · state: closed · merged: True

## Original PR description

## Motivation

A model can attach per-token values to a request's output through `customized_info` (`Req.customized_info`). In Python mode the TokenizerManager gathers each key's values and reports them in native `/generate` `meta_info`: the running list by default, or the frame's own slice under `--incremental-streaming-output`. In rust-server mode, `push_generation` never sent the column, so the values were lost with no error.

## Modifications

The Rust frontend now carries `customized_info` the way Python does.

- **Egress** (`output_streamer.py`, `rust_server/server.py`). Each step's values go to the frontend as one more optional header column: each request's values for its new output tokens, padded with `None` for a request without the key. The column is a single JSON text, encoded the way Python's responses encode it (orjson with the response options), so numpy values become lists and NaN becomes null. A value orjson can't serialize is sent as its `str`. As a result, a model's values can't fail the scheduler step, and they can't fail the frame's decode either: a batch whose text can't be encoded (for example an int wider than 64 bits) or read loses only its `customized_info`, with a log line.
- **Native `/generate`** (`native_api.rs`, `message/response.rs`, `core/frame.rs`).
  - A frame reports the keys its own scheduler output carried, as Python's frames take the keys of their own batch, so a prefill or scheduler-abort frame without them reports none. A cumulative-stream frame re-reports every key surfaced so far, as the TokenizerManager does since #43772 and #44537; a key a hook consumes never surfaces, so it is never re-reported.
  - Values are the running list by default and the frame's own values in an incremental stream. A unary response reports the full lists. The running lists are shared, so a cumulative frame doesn't copy them.
  - The OpenAI and gRPC paths never report `customized_info` and don't accumulate it; the api.v1 gRPC schema doesn't model it.
- **Hooks** (`generate_hook.rs`).
  - `GenerateFrameInfo::customized_info` gives a `GenerateHook` each frame's new values. Every value appears on exactly one frame, and cumulative and incremental streams show the same values.
  - `GenerateHook::consumes_customized_info_key` lets a hook claim keys. Frames don't report those keys, and the frontend keeps only their values since the last frame.

Differences from Python mode, and known costs:

- **Incremental streams.** Python slices an incremental frame's list at the request's output-token offset. Once a frame's batch lacked the key, the list falls behind the token count and those slices lose values, so whether values reach the client depends on batch composition (the usual case is a prefill frame without the key). The Rust frontend reports each frame's own values instead. That Python behaviour is out of scope here; the fixture records Python's output for that case as `python_incremental`.
- **Repeated keys.** A `customized_info` key that repeats a schema key (`id`, `prompt_tokens`, ...) or a key a hook writes is dropped, with a one-time warning; the schema and hook keys win, where Python would overwrite them.
- **Key order.** `customized_info` keys come after the schema's keys and before a hook's. Python's insertion order differs in places.
- **Odd value types.** `bytes` and torch values fail Python's response serialization (a 500). The Rust frontend reports their `str`.
- **Known cost.** A batch with `customized_info` boxes a `ChunkExtras` for every row; there is no cost without it. A leaner layout (metadata split from the boxed logprob and hidden-state part, or one Arc'd column per frame) is a follow-up.
- **Error message.** The existing refusal of streamer-added customized_info (`has_additional_customized_info`) now says why: that info needs TokenizerManager hooks the Rust frontend doesn't run.

Rebased on the chat-layer changes from #45449 and #45659: `drain_unary_frame` returns its frame in `Ok(..)` and `RequestState` keeps its `pub(super)` visibility; nothing else differs from the change as developed.

## Test

- `rust/`: `cargo fmt --all -- --check` passed; `cargo clippy --locked -p sglang-server --all-targets -- -D warnings` clean; `cargo test --locked -p sglang-server`: 399 passed. New tests:
  - `customized_info_matches_python` replays `testdata/customized_info.json`, generated by `sglang.test.rust_customized_info.build_rust_customized_info_fixture` from `push_generation` / `push_abort` headers and the TokenizerManager's own `update_request_meta_info` and `_slice_streaming_output_meta_info`, through cumulative and incremental streams and unary responses, with and without a hook that consumes a key. The fixture covers a prefill frame without the key, a batch without `customized_info` in the middle of a request, a scheduler abort, and a frame that also carries output logprobs.
  - `coalesced_frames_catch_up_on_customized_info`: a coalesced cumulative frame with a hook.
  - `repeated_customized_info_keys_give_way`, which also pins the schema key list.
  - `customized_info_text_never_rejects_the_frame`: malformed JSON, wrong shapes and a short column.
- Python: `test/registered/unit/managers/test_output_streamer_customized_info.py` and `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py` (the fixture regenerates and compares equal; each step sends only its new values; the JSON encoding of numpy, NaN, non-string keys and `bytes`; a batch orjson can't encode is still sent): 24 passed, 7 subtests passed.
- Not run here: a gRPC check (gRPC doesn't carry the column) and a live-server check.
