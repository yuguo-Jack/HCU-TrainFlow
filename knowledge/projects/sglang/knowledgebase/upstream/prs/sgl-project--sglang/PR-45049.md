# [Fix] speculative: Refresh shared_read_done_event after post-verify KV cache compaction

[Upstream PR](https://github.com/sgl-project/sglang/pull/45049) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44997

When running speculative decoding (`--speculative-algorithm NEXTN` / `NGRAM`, or `EAGLE` with `topk > 1`) with CUDA graphs enabled and the overlap scheduler active, `DecodeCudaGraphRunner.execute` publishes `model_runner.shared_read_done_event` inside or immediately at the end of the target verify CUDA graph replay (`SharedReadEnds.PRE_REPLAY` for Triton, `SharedReadEnds.IN_REPLAY` for FlashInfer via `in_graph_metadata_prep_done`, or `SharedReadEnds.POST_REPLAY`).

However, after `target_worker.forward_batch_generation(..., is_verify=True)` returns, `NGRAMWorker.forward_batch_generation` (and `run_eagle_verify` when `topk > 1` via `_finalize_accept_tree_path`) launches `move_accept_tokens_to_target_kvcache` on `forward_stream`. `move_accept_tokens_to_target_kvcache` runs `assign_extend_cache_locs`, which reads `batch.req_to_token_pool.req_to_token[batch.req_pool_indices, batch.seq_lens : batch.seq_lens + num_correct_drafts + 1]` into `tgt_cache_loc`, and then copies KV cache entries from `accept_out_cache_loc` into `tgt_cache_loc`.

Because `shared_read_done_event` was not refreshed after `move_accept_tokens_to_target_kvcache`, `scheduler._apply_war_barrier()` only fenced `schedule_stream` behind the target verify graph's early `shared_read_done_event`. When a request finishes on a stop token (or by length when speculative pre-stop is disabled) in `batch_t`, it still participates in `batch_{t+1}`'s verify step before `pop_and_process(batch_t)` runs:
1. While `batch_{t+1}`'s target verify forward is still executing on `forward_stream`, `_apply_war_barrier()` on `schedule_stream` immediately passes (since `PRE_REPLAY` / `IN_REPLAY` already fired).
2. `pop_and_process(batch_t)` calls `release_kv_cache`, freeing the finished request's `req_pool_idx`.
3. The next iteration admits a new request into that same `req_pool_idx` and executes `alloc_for_extend` -> `write_cache_indices` on `schedule_stream`, overwriting `req_to_token[req_pool_idx, :prefix_len + extend_len]` with the new request's radix-cached prefix KV slot indices **before** `batch_{t+1}`'s `move_accept_tokens_to_target_kvcache` executes on `forward_stream`.
4. `batch_{t+1}`'s `move_accept_tokens_to_target_kvcache` then reads `tgt_cache_loc` from the overwritten `req_to_token[req_pool_idx]` (pointing to the shared radix-cached prefix KV slots) while `accept_out_cache_loc` holds the finishing request's old over-allocated draft KV slots, corrupting the shared radix-cached prefix KV cache in-place.

## Modifications

- Add `refresh_shared_read_done_event(model_runner, device_module=None)` in `python/sglang/srt/model_executor/runner_utils/shared_read_event.py` to record and publish a fresh `shared_read_done_event` on `forward_stream` when an earlier event was published during the forward pass.
- Call `refresh_shared_read_done_event(self.model_runner)` in `NGRAMWorker.forward_batch_generation` (`python/sglang/srt/speculative/ngram_worker.py`) after post-verify `move_accept_tokens_to_target_kvcache` (and `compute_spec_logprobs`).
- Call `refresh_shared_read_done_event(target_worker.model_runner)` in `run_eagle_verify` (`python/sglang/srt/speculative/eagle_worker_common.py`) after `_finalize_accept_tree_path` when `finalize_tree_path and not batch.forward_mode.is_idle() and topk > 1`.
- Add unit tests in `test/registered/unit/model_executor/runner/test_prefill_shared_read_done.py` covering `refresh_shared_read_done_event`, `NGRAMWorker` target verify event refresh ordering, and `run_eagle_verify` tree compaction event refresh ordering.

### GB10 exact-oracle GPU validation of the NGRAM fence

I tested a narrow Python backport of `13ef17a8292d9ba7c4f14b42ca936d3ed0a61267` on one DGX Spark GB10 (aarch64, CUDA 13), using SGLang 0.5.21 container digest `sha256:b1259f3ea3275f66237c498ea388919729018bc9f01c3d638391e06e2cf3f469`. The backport adds the helper and the NGRAM/tree call sites without replacing other engine sources or native extensions. This validates the backported NGRAM fence, not a build of the current complete PR head.

The exact-oracle checkpoint is a synthetic Qwen3-0.6B-shaped twin (28 layers, hidden 1024, 16 attention / 8 KV heads), generated with probec `d7cfa22752bcf705ba128d77fb888f5ae20042cf`, recall program and no scale check. The public reproducer currently imports `sgl_ngram_investigate.py`, which that commit deletes; I restored the unchanged helper from `1c40c6644e8d06ad169aecca9362995a5d8dfccc` via a separate read-only import path.

Workload: all 192 seeded requests queued, 56 shared-prefix requests, prompt lengths 149–14,495, up to 256 output tokens, per-request oracle-derived stop token, temperature 0. Limits: 32 active requests, context 16,512, static memory fraction 0.30, FlashInfer attention, NGRAM draft length 4, default overlap/radix caching/CUDA graphs.

Baseline: no-spec matches all 192 oracle answers; NGRAM has 3 wrong requests (148, 174, 179). Request 174 first diverges at output index 44; request 179 reports 1,923 cached tokens from its 1,946-token prompt extending request 174’s 1,924-token prompt, and first diverges at index 6. Request 148 similarly reports 1,147 cached tokens while extending request 89. All three miss their stop token and produce 256 tokens instead of 15/57/190. With the backported fence, no-spec and NGRAM both match all 192 oracle answers. The stop token is included in returned IDs in every baseline reference request.

Disabling overlap on the unchanged baseline gives 0/192 oracle errors. The baseline length-ending control also has 3/192 NGRAM errors (109, 173, 182), while its no-spec reference is exact; this is consistent with the older 0.5.21 behavior, not evidence that stop tokens are the sole trigger. Patched length-ending execution was not tested. A separate patched allocation audit is also exact (0/192 errors). In the reproducer’s sequential no-spec and NGRAM runs, each actual request pool has capacity 32 and records 192 allocations, 192 matching frees and 160 freed-slot owner reassignments. The NGRAM pool has 109 cached-prefix matches against previously admitted prompts; across both pools, 83 matches span at least 1,024 tokens. This host-metadata-only audit reads no device tensor contents and introduces no GPU synchronization, but file writes can change scheduling, so it supplements the uninstrumented comparison. It does not identify the exact internal radix node supplying every hit. EAGLE tree execution is not validated: the synthetic target has no compatible local EAGLE draft, and the existing 27B DFlash2 checkpoint is not a compatible draft for this 0.6B-shaped synthetic target. Ordinary real-model output comparisons would not establish exact correctness here.


All five valid runs complete with unchanged frozen sources and checkpoint identities. Whole-machine usage peaks at 46.124 GiB, with at least 75.564 GiB available (250 ms sampling). No throughput claim is intended. The shared reference identity over full oracle answers, prompt lengths and shared-prefix mapping is `91cf2be42b2bbec94ce857a3ac546eb8815819bf0176fb1f7c017822c60c1054` (sorted-key JSON SHA256). Full raw dumps are retained locally; the reference engine is independently checked against the oracle, rather than merely compared against NGRAM.

AI assistance was used for investigation and test implementation; the reported results were checked against the saved request/source evidence.
