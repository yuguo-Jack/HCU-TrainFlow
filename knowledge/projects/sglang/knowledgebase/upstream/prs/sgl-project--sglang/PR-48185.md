# [Fix] llguidance: Accept special tokens in tool tags

[Upstream PR](https://github.com/sgl-project/sglang/pull/48185) · state: closed · merged: False

## Original PR description

## Motivation

With `--grammar-backend llguidance`, finishing a tool call gives HTTP 500. A legacy structural tag spells special tokens such as `</tool_call>` as forced text. llguidance tokenizes that text into the special token, allows only that token, and then rejects it:

```text
Grammar accept_token failed: Parser Error: token "�[151658]" doesn't satisfy the grammar; forced bytes: got '<'; applying 'ÿ'
```

This reaches `hermes`, `qwen`, `qwen25`, `trinity`, `apertus2509`, `deepseekv3` and `deepseekv31` on tokenizers that define these tokens as special.

The Rust schema for one tool has no `"type": "object"`, so named and one-tool `required` calls accept `["abc"]`. #48116 fixes the Python copy, so this PR leaves it.

## Modifications

The llguidance backend now writes each structure as a Lark grammar that references special tokens by ID. The Rust schema now sets `"type": "object"`.

A text trigger now fails at 667 tools, where main works up to 1990. Among served parsers, only `mistral` has one, and a user `structural_tag` can use one. The compile limit also falls for both trigger kinds.

This PR does not fix:

- `--reasoning-parser` (#33061, #25700). Merge this first: at `d59bb5520d`, #33061 alone killed the server on the first finished call, and #33061 with this fix did not.
- `at_least_one`, which llguidance ignores on legacy tags. Most no-call responses are empty: the mask blocks `<think>`, the model's first choice, so the model can stop at once.
- `mistral`, native tags, and `glm47` with non-strict tools (see the table).
