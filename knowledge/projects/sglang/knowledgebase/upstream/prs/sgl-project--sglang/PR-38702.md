# [DSpark] Support PP verify with stage-local draft owners

[Upstream PR](https://github.com/sgl-project/sglang/pull/38702) · state: closed · merged: False

## Original PR description

## Motivation

Pipeline-parallel target verification can reduce cross-node MoE communication for DeepSeek-V4 deployments. However, running all DSpark draft work on the last pipeline stage creates an additional bottleneck and leaves bubbles on other stages.

This PR introduces an experimental PP2 DSpark mode where:

- Each PP stage hosts a complete TP draft model replica.
- Every request is assigned to one stable draft owner.
- Draft work is distributed across PP stages instead of duplicated on every stage.
- Draft generation for one microbatch can overlap with target verification of another microbatch.
- Only projected target context and draft proposals are transferred between stages.

## Modifications

- Add `--speculative-dspark-pp-replicated-draft`.
- Add `--speculative-draft-scheduling-policy={tail,bubble}`.
- Support DSpark decode with PP2 under PD disaggregation.
- Assign each request to a deterministic PP draft owner based on `rid`.
- Store and update draft KV state only on the owning stage.
- Generate next-round proposals after accepted target context has been committed.
- Relay owner proposals through the existing PP output ring.
- Optionally batch the bidirectional PP2 result relay with `SGLANG_PP_DSPARK_BATCHED_RESULT_RELAY=1`, removing odd-rank recv-before-send serialization.
- Validate request lifecycle with request ID, PD bootstrap generation, retraction generation, and speculative round.
- Relay projected target context instead of full raw hidden states.
- Initialize owner-local draft context during PD prefill.
- Disable PP output skipping for replicated DSpark chunked prefill.
- Reject unsupported request-level stochastic sampling before it reaches the scheduler loop.
- Add tests for owner assignment, proposal packing, lifecycle validation, owner-only KV commits, PP result relay, PD wire behavior, DP attention, and argument validation.

Current constraints:

- PP size 2 with PD disaggregation on both prefill and decode servers.
- A bundled DeepSeek-V4 DSpark checkpoint.
- Greedy sampling and no rejection sampling.
- `SGLANG_RAGGED_VERIFY_MODE=static`.
- Decode radix cache disabled; radix-backed draft context is supported on prefill.
- Prefill CUDA graph disabled; decode CUDA graphs are supported.
- `--pp-async-batch-depth 0`.
- Attention CP size 1 and no mixed chunked prefill.
- DP attention requires `attn_dp_size == tp_size` and uses built-in TP MoE (`--moe-a2a-backend none`).

The first decode round uses a deterministic warm-up proposal. Subsequent rounds use proposals produced by the assigned owner.

## Speed Tests and Profiling

Serving benchmark: 1,024 generated-shared-prefix requests, request rate 128, max concurrency 256, seed 43, input lengths 3,500 + 64, output length 1,500. Both variants used the same PP2/TP8/DP8 deployment, Humming runtime overlay, and:

```bash
SGLANG_DP_USE_REDUCE_SCATTER=1
SGLANG_DISABLE_CUSTOM_REDUCE_SCATTER=1
```

The relay variant changed only the scheduler/environment files from commit `fc30ffb6e5` and added:

```bash
SGLANG_PP_DSPARK_BATCHED_RESULT_RELAY=1
```

| Variant | Run | Output throughput | Mean TPOT | P95 TPOT | P99 TTFT |
|---|---:|---:|---:|---:|---:|
| Original branch (`e85a8ac463`) | 1 | 8,999.64 tok/s | 24.80 ms | 27.06 ms | 5,132.76 ms |
| Original branch (`e85a8ac463`) | 2 | 8,673.10 tok/s | 25.03 ms | 27.52 ms | 4,376.28 ms |
| Original branch (`e85a8ac463`) | 3 | 8,695.34 tok/s | 25.04 ms | 27.51 ms | 4,626.23 ms |
| Original branch median | - | 8,695.34 tok/s | 25.03 ms | 27.51 ms | 4,626.23 ms |
| Batched result relay | 1 | 8,997.20 tok/s | 24.58 ms | 26.45 ms | 5,015.96 ms |
| Batched result relay | 2 | 8,939.93 tok/s | 24.97 ms | 27.28 ms | 6,886.75 ms |
| Batched result relay | 3 | 8,614.30 tok/s | 24.76 ms | 26.81 ms | 4,503.99 ms |
| Batched result relay median | - | 8,939.93 tok/s (+2.81%) | 24.76 ms (-1.08%) | 26.81 ms (-2.54%) | 5,015.96 ms (+8.42%) |

The clean original-branch run reproduced the previous 8,994.45 tok/s result with 8,999.64 tok/s. Mean throughput improves by 0.70% and mean TPOT improves by 0.75% across the three runs, while median throughput is noisy because the metric includes final request drain.

Steady-state weighted DSpark accept length differs by less than 0.5% between runs. The low-throughput runs instead end with a single low-acceptance DP straggler (accept length 2.55-3.02 versus approximately 5.8 in steady state), extending benchmark makespan by 6-8 seconds. The stable signal from this A/B is the TPOT reduction; the end-to-end throughput delta should be interpreted with the drain variance.

All runs completed 1,024/1,024 requests. Both PP nodes remained healthy with no Python traceback or CUDA/NCCL runtime error.
