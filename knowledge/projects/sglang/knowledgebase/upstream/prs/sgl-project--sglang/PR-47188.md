# [Fix] marlin: keep one block per SM in the MoE kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47188) · state: open · merged: False

## Original PR description

Fixes #44999.

## Motivation

`moe_wna16_marlin_gemm` intermittently returns wrong rows on pre-Hopper GPUs. Reported by #44999
on sm86; reproduced here on sm89 (RTX 4090) with synthetic AWQ W4A16 MoE weights
(E=128, K=2048, N=768, group 128, topk 8): 4-6% of probe launches differ from the majority output,
3-4 of 64 tokens are wrong (|delta| up to 5.0) and every other row is bit-identical. The Triton
WNA16 path is exact, which is how the report distinguishes it from a numerics issue.

`determine_exec_config()` sizes the launch by an occupancy estimate (`allow_count`), so the kernel
can run two or three blocks per SM. The split-K reduction chains those blocks through a global lock
array (`barrier_acquire`/`barrier_release`), and that chain is only correct with a single resident
block per SM.

## Modifications

- `determine_exec_config()` keeps computing the per-SM shared-memory/register budget for thread
  config selection, but no longer raises `blocks_per_sm` above 1, so the kernel always launches
  with `sms` blocks.

## Verification

Determinism harness: fixed probe input (M=64, top-8) run 300 times, each launch preceded by a call
with a random batch size (M in [1, 900]) to perturb scheduling. Outputs are compared bitwise.

| config | distinct outputs | mismatch rate | worst element delta |
|---|---|---|---|
| before | 13-18 | 4-6% | 4.0-5.0 |
| after | 1 | 0 / 300 | 0 |

Per-gemm check: `moe_wna16_marlin_gemm` called directly for the gate/up and the down projection is
independently nondeterministic before the patch and deterministic after it.

Cost (same weights, 100 reps, ms/call):

| M | before | after |
|---|---|---|
| 1 | 0.297 | 0.287 |
| 16 | 0.325 | 0.324 |
| 64 | 0.376 | 0.392 |
| 256 | 0.416 | 0.437 |

i.e. the multi-block occupancy path buys nothing measurable for MoE shapes.

New test: `test/registered/unit/layers/quantization/test_marlin_moe_determinism.py`
(repeated calls with the same input must be bitwise identical, including decode-shaped M=1 calls).
It fails without this patch and passes with it.

## Notes

What was ruled out while narrowing this down (all verified on sm89 with instrumented kernels):
work-item coverage and lock arrival counts are exact; the C_tmp accumulator handoff is byte-exact;
the A/B/scale/zero-point operands fed to the MMA are bitwise identical across good and bad launches;
compute-sanitizer memcheck is clean. The corruption therefore needs several blocks of this kernel to
co-reside on one SM, which is exactly what this patch removes.

Could we keep this to pre-Hopper? On H200 it slows Marlin down a lot, and the barrier chain from your comment doesn't run for NVFP4 there, since `fused_marlin_moe` sets `use_atomic_add` on SM90 (`marlin_template.h:1904`).

1x H200, `fused_marlin_moe` at the MiniMax-M3.1 TP8 rank shape (E=128, K=6144, N=384, top-4), cold weights, CUDA graph, main vs one block per SM:

| M | main (us) | one block per SM (us) |
|---|---|---|
| 1 | 21.5 | 26.4 |
| 8 | 61.8 | 79.0 |
| 64 | 190.1 | 253.4 |
| 128 | 216.4 | 290.3 |

TP4 (N=768) is +11% to +21%.

Distinct outputs in 120 runs at that shape, main vs one block: M=1 120 vs 120, M=8 120 vs 1, M=64 and M=256 1 vs 1. Main's differences are at most 3 bf16 ulps (22 on values up to 1496), so I think that's the atomicAdd order from #39456, separate from the wrong rows you found on sm89. `test_single_token_decode_is_bitwise_identical` from this PR fails on H200 too, 3 of 3 runs at d3a0ed38cd, so it would need a skip on SM90+.

MXFP4 does take the barrier path on H200. At DSv4.1's TP8 gate/up shape (K=5120, n=640, top-6), main gave one output in 150 runs for M up to 32, including the 2-block config at M=1.

```suggestion
#if SGL_CUDA_ARCH < 900
    // The split-K reduction chains blocks through a global lock array
    // (barrier_acquire/barrier_release in marlin_template.h). That protocol is
    // only correct with a single resident block per SM: with more than one, the
    // accumulation of the partial sums is nondeterministic and a few output rows
    // are silently corrupted (sgl-project/sglang#44999).
    allow_count = 1;
    (void)sms;
#else
    if (thread_m_blocks > 1) {
      int problem_blocks = prob_n / th_config.thread_n * prob_m * top_k * 4;
      if (problem_blocks < sms * allow_count) {
        allow_count = max(problem_blocks / sms, 1);
      }
    }
#endif
```
