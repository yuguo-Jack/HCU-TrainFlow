# [Refactor] Simplify RadixCache.total_size() to O(1) using existing size counters

[Upstream PR](https://github.com/sgl-project/sglang/pull/37067) · state: closed · merged: False

## Original PR description

## Motivation
`RadixCache.total_size()` currently uses `_total_size_helper()` to perform an $O(N)$ depth-first search traversal over all tree nodes on every call.
In production servers with thousands of multi-turn requests and deep branching trees, frequent calls to `total_size()` (e.g. from monitoring, logging, or metric scrapers) can cause avoidable CPU latency spikes and GIL contention on the scheduler thread.
Since `RadixCache` already maintains `self.evictable_size_` and `self.protected_size_` in $O(1)$ across all mutating operations (insert, split, lock, unlock, evict), `total_size()` can be calculated directly in $O(1)$ time via `self.evictable_size_ + self.protected_size_`.
## Modifications
1. Refactored `RadixCache.total_size()` to return `self.evictable_size_ + self.protected_size_` ($O(1)$).
2. Removed unused `_total_size_helper()`.
3. Added `test_total_size_o1_consistency` in `test/registered/unit/mem_cache/test_radix_cache_unit.py` verifying size invariant across inserts, splits, reference locking/unlocking, and evictions.
## Checklist
- [x] Code passes unit tests.
- [x] Non-breaking performance optimization.

Hi @alphabetc1, you're completely right that in the current scheduler hot loop, `evictable_size()` and `protected_size()` are queried directly rather than `total_size()`. 

The motivation for this change was mainly **code hygiene, API consistency, and future-proofing**:
1. **Consistency**: `evictable_size()` and `protected_size()` are already $O(1)$. Having `total_size()` return `evictable_size_ + protected_size_` brings it into parity with the other size methods.
2. **Code Simplification**: It eliminates the 11-line stack-based DFS helper (`_total_size_helper`) entirely.
3. **Safety for External Callers**: For session trackers (e.g. in `streaming_session.py`), testing, or future telemetry scrapers calling `total_size()`, having it be $O(1)$ ensures it will never inadvertently block the GIL on large trees.

Happy to keep it as a clean refactor/hygiene improvement, or close if you'd prefer to leave it as-is!

Thanks for the follow-up. I don't think we should merge this, for two reasons:

1. `total_size()` has no production caller. The only real use is `pretty_print()`, so the O(1) version doesn't speed anything up.
2. It weakens the existing tests. `_split_node` is the only mutating op that doesn't touch the size counters. The new test has the same problem: it checks `total_size() == evictable_size() + protected_size()`, and that is now just the definition.
