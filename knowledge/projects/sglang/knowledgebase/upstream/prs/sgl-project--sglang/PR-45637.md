# [Perf] [KDA] muse_spark: use BLOCK_M 240 for BF16 MegaMoE prefill shards

[Upstream PR](https://github.com/sgl-project/sglang/pull/45637) · state: closed · merged: True

## Original PR description

## Motivation

This PR is powered by [KDA](https://github.com/NVlabs/kda) team. MegaMoE is the largest prefill cost in the BF16 TP8/EP8 deployment: about 68 ms of a 131 ms 8K-token TTFT on rank 0. For BF16 prefill shards DeepGEMM's heuristic picks BLOCK_M 192 (`2,192,48,128,2`), sized for uniformly spread routing. Muse Spark routing is skewed, and on GB300 `2,240,40,128,2` is faster for these shards. DeepGEMM reads `DG_MEGA_MOE_TILES` on every MegaMoE launch; an empty value keeps its heuristic.

## Modifications

- `srt/layers/muse_spark/muse_spark_megamoe.py`: `_tile_override` asks DeepGEMM's `get_block_m_for_mega_moe` for the launch's tile (LRU-cached); only when it returns 192 for `bf16xbf16` does `_megamoe_tiles` set `DG_MEGA_MOE_TILES=2,240,40,128,2` around that one launch and reset it afterwards, including on exceptions
- NVFP4, decode and small prefill shards (smaller heuristic tiles) and a user-set `DG_MEGA_MOE_TILES` are left alone
- `test_muse_spark_megamoe_tiles.py` (new): the override rules and env scoping on any GPU; on SM100 it pins the installed heuristic, checks that DeepGEMM honours the override and that BF16 output is bitwise identical with either tile. Registered on H100 and B200

## Accuracy Tests

- BLOCK_M only changes how rows are split into tiles, not the K-loop order, epilogue or combine; the registered test checks bitwise-identical output with 192 and 240
- GSM8K (sgl-eval, 1319 questions, BF16 TP8/EP8, 8 runs per side): 93.71% vs 93.55% (-0.16 pt, 95% CI [-0.41, +0.08]); Low Latency recipe -0.08 pt (4 runs per side); greedy replay identical to main

## Speed Tests and Profiling

Kernel on GB300, EP4, 256 experts, top-k 8, expert popularity lognormal (sigma = skew), rank-max time, two jobs:

| Tokens per rank | Skew | BLOCK_M 192 | BLOCK_M 240 | Speedup |
| --- | --- | --- | --- | --- |
| 2048 | 1.2 | 1933 us | 1788 us | 1.081x / 1.083x |
| 2048 | 0.7 | 1772 us | 1664 us | 1.065x / 1.066x |
| 2048 | uniform | 1763 us | 1769 us | 0.996x / 0.998x |
| 1024 | 0.7 | 1177 us | 1124 us | 1.048x / 1.048x |

BF16 model vs main (2x GB300, TP8/EP8, cookbook GB300 High Throughput recipe, 64 requests per point, two pairs):

| Point | Pair 1 | Pair 2 |
| --- | --- | --- |
| 8K C1 TTFT | 1.035x (131.3 -> 126.9 ms) | 1.024x (130.4 -> 127.4 ms) |
| 8K C8 TTFT | 1.043x | 1.021x |
| mixed C1 / C8 TTFT | 1.037x / 1.041x | 1.025x / 1.022x |

- Rank-0 MegaMoE time per 8K request: 68.1 -> 63.7 ms and 67.3 -> 64.5 ms
- Decode ITL within 0.3% of main; no serving point regresses
- Low Latency recipe (DFlash, one pair): 8K C1 TTFT 1.034x [1.032, 1.037] (145.6 -> 140.8 ms), verify-step time 1.002x-1.032x, accept lengths unchanged
- NVFP4 is unchanged (the override only applies to `bf16xbf16`)
- Measured on GB300 only. The override also applies to B200 and B300 BF16 (same EP8 shards); B200 speed is untested, and the gain depends on skewed routing (uniform routing is 0.2-0.4% slower in the kernel table above)
- Happy to limit it to SM103 (B300/GB300) if reviewers prefer, or keep it on B200 if someone can measure there
