# [Fix] deepseek-v4.1: Start the PD decode draft SWA window at the prefill draft valid-from

[Upstream PR](https://github.com/sgl-project/sglang/pull/45037) · state: closed · merged: True

## Original PR description

- With encoder SWA bounded replay on a PD prefill worker, the DSpark draft ring restarts at the cached prefix, but PD sends the draft's last SWA window from its start. After a prefix hit whose extend is shorter than the 128-token window, decode's paged draft SWA held rows the prefill never wrote for that request, and the draft attended over them. Lossless, but it lowers acceptance.
- The draft pool keeps that mark per request slot (`swa_valid_from`), and PD sends it as a new `REQUEST_ROW` state component: one item per request slot, sent slot to slot by Mooncake and NIXL, registered after the draft's SWA. Decode receives the prefill ring's mark in its own draft pool. Every DSpark draft on CUDA keeps the mark, ring or paged, in the custom mem pool like the pool's other transferred buffers, so both PD roles register it; it stays 0 unless the ring restarts or PD writes it.
- `ComputeDsparkWindowGather` takes an optional `valid_from` (torch and triton), so the paged window stops there, as `BuildDsparkSwaRingIndices` does for the ring.
- The ring's `swa_req_ring_valid_from` / `reset_swa_req_ring` become `swa_valid_from` / `set_swa_valid_from`: one per-slot mark for both storages.
- Tests: paged indices with a valid-from match the ring's; a DSpark draft keeps the mark for either storage and registers it as a `REQUEST_ROW` component after its SWA, while other drafts keep none; triton matches torch with a valid-from.

Checked on GB300 with DeepSeek-V4.1-Flash: one DEP2 prefill worker (encoder replay on) and one DEP2 decode worker on one node, DSpark block 5, MegaAttention, MegaMoE, Mooncake, greedy.

| Workload | main: accept length (tokens) | This PR: accept length (tokens) |
|---|---:|---:|
| 2048-token cached prefix + 43-token question, 64 new tokens, round 1 (128 requests) | 3.16 | 3.85 |
| same, round 2 | 2.87 | 3.80 |

This workload leaves an 85-row gap on every hit. GSM8K (sgl-eval, 1,319 questions, thinking off) behind a shared 8-shot prefix, whose prompts hit at a page boundary that leaves no gap: 97.12% and 96.89% on main over two passes, 96.74% with this PR. Zero KV transfer failures. These runs predate moving the mark's allocation to one place; that move does not change the DSpark PD path. Not run with a Mooncake custom mem pool (`SGLANG_MOONCAKE_CUSTOM_MEM_POOL`).

Known limit: with a decode-side prefix cache that holds more of the window than the prefill, the mark also hides those decode-local rows (acceptance only).

Behavior change: PD workers with a DSpark draft on CUDA register one more state component, and decode's draft window stops at the prefill's mark. A DSpark draft without PD keeps the mark at 0, so its window gather adds one clamp that leaves the values unchanged; nothing else changes.
