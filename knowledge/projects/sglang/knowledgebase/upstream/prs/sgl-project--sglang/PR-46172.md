# [Perf] diffusion: Encode Cosmos3 video while it decodes

[Upstream PR](https://github.com/sgl-project/sglang/pull/46172) · state: closed · merged: True

## Original PR description

Branch: mick/cosmos3-encode-while-decoding (on main 005333d029), commit f86dd52e1d

Merge note: this PR and #46173 both edit the decode call in `Cosmos3DecodingStage.forward`; whichever lands second needs a trivial rebase.

## Motivation

For causal VAEs, the generic `DecodingStage` passes each run of finished frames to the MP4 encoder while the rest of the clip is still decoding (`EncodeWhileDecoding` over `CudaVideoEncoder`). Only the last frames and the ffmpeg flush are left after the decode.

Cosmos3 runs its own `Cosmos3DecodingStage`, which never set that up. Every Cosmos3 video was decoded to a float32 `[1, 3, T, H, W]` clip (2 GB at 720p and 189 frames) and handed to the worker, and only then encoded. On 4xB300, Cosmos3-Nano T2V 720p 189 frames spent 1.13-1.16 s after the decode stage before the request completed. That was the largest piece of its post-denoise tail.

## Modifications

- `stages/model_specific_stages/cosmos3.py`:
  - `Cosmos3DecodingStage._encode_while_decoding` opens the shared encoder (`streamed_video_output_path` + `EncodeWhileDecoding`) for plain video outputs, using the stage's own `[-1, 1] -> [0, 1]` postprocess as `finish_frames`.
  - The decode passes the encoder as the Wan VAE's `on_frames`. On success the stage returns `OutputBatch(output=None, output_file_paths=...)`, as the generic stage does.
  - An encoder failure falls back to the old save-after-decode path.
  - Outputs that need the decoded frames are not streamed: guardrails, sound, action predictions and transfer displays.
- `test_cosmos3.py`:
  - `TestCosmos3EncodeWhileDecoding.test_streamed_frames_equal_the_saved_output`: a frame-by-frame VAE feeds the encoder frames that are bitwise equal to the clip the non-streamed path returns, and the stage returns the file path.
  - `test_outputs_that_need_the_frames_are_not_streamed` covers guardrails, sound, action and transfer.

## Accuracy Tests

The encoder gets the same values per frame, converted by the same `CudaVideoEncoder` with the same ffmpeg command line, so the MP4 is unchanged. Cosmos3-Nano T2V 720p 189 frames, 4xB300: the base and this change produced byte-identical MP4s (md5 a494ab96ce / 80597a2763 for two requests, default x264 settings).

## Speed Tests and Profiling

Cosmos3-Nano T2V 720p 189 frames, 4xB300 (CFG 2 x Ulysses 2, 4-rank spatial-parallel VAE decode), synchronized stage timers, two requests per build:

| | client e2e | decode stage | after decode |
|---|---|---|---|
| base | 24.251 / 24.300 s | 1.818 / 1.815 s | 1.134 / 1.156 s |
| + this PR + "Gather spatial-parallel decode heights on the host" | 23.076 / 23.062 s | 1.717 / 1.730 s (now includes the encode) | 0.022 / 0.041 s |

Each change on its own, same setup:

| | client e2e | decode stage | after decode | MP4 md5 |
|---|---|---|---|---|
| base | 24.251 / 24.300 s | 1.818 / 1.815 s | 1.134 / 1.156 s | a494ab96ce / 80597a2763 |
| this PR alone | 23.290 / 23.247 s | 1.919 / 1.920 s (incl. encode) | 0.032 / 0.031 s | same |
| "Gather spatial-parallel decode heights on the host" alone | 24.053 / 24.069 s | 1.619 / 1.621 s | 1.121 / 1.138 s | same |

This PR alone saves 0.96 / 1.05 s per request. The encode now overlaps the decode, and only about 0.1 s of it (the last frames and the ffmpeg flush) is left after the decode.
