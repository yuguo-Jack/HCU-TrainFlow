# [Perf] [AMD] GLM5: Skip redundant -inf pre-fill of KPool MQA-logits

[Upstream PR](https://github.com/sgl-project/sglang/pull/44824) · state: open · merged: False

## Original PR description

## Motivation

This affects prefill serving of GLM-5.3-Flash, which uses the pooled DSA `IndexerKPool`.

`IndexerKPool._kpool_topk_by_row_chunks` calls `fp8_mqa_logits` with `clean_logits=True`, which initializes the full `[query rows x concatenated pooled KV rows]` FP32 logits buffer to `-inf` before the scorer writes each row's valid range. The buffer can be several GiB at long context.

The downstream KPool top-k already receives `row_starts` and `pool_lens` and reads only `score[row, row_start : row_start + pool_len]`. Initializing positions outside those ranges is therefore redundant. This is the KPool equivalent of the non-pooled indexer optimization merged in #28757.

## Modifications

- `python/sglang/srt/layers/attention/dsa/dsa_indexer_kpool.py`: pass `clean_logits=False` to the ragged KPool MQA-logits call. Valid logits are unchanged; positions outside each row's declared range remain uninitialized and are not read by KPool top-k.
- Extend the gfx950 real-kernel test to compare `clean_logits=True` and `False` through the production KPool top-k transform at GLM-5.3-Flash geometry (`32 x 128`, KPool 4, token top-k 2048).
- Make KPool chunking unit tests require `clean_logits=False` on both ROCm/AITER and CUDA/DeepGEMM paths.

## Accuracy Tests

TP4 used context 65,536, 1,319 GSM8K questions, 64 threads, and max output 32,768. TP8 used context 131,072, 1,319 questions, 1,200 threads, and max output 4,096.

## Speed Benchmarks

MI355X/gfx950, image `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261013`, SGLang `84bd7ab1884cee885fafce9c94f5c9ad80a4f0b8`, AITER `e7d2453f25e5aaeea72a3a40b284ba453e026624`, PyTorch `2.11.0+rocm7.2`, Triton `3.7.0`. FP8 MQA scorer GPU-event medians after warmup, seven measurements per cell, `H=32`, `D=128`.

| query rows | concatenated KV rows | clean=True (ms) | clean=False (ms) | delta |
|---:|---:|---:|---:|---:|
| 128 | 4,096 | 0.048 | 0.042 | -11.3% |
| 1,024 | 16,384 | 0.129 | 0.119 | -7.2% |
| 4,096 | 65,536 | 1.547 | 1.203 | -22.2% |
| 8,192 | 131,072 | 7.120 | 6.353 | -10.8% |

A separate concurrency-64-shaped segmented case used 64 requests, 128 query rows and 2,048 pooled KV rows per request (`8,192 x 131,072` output, 4 GiB). Skipping initialization reduced scorer time from 2.605 ms to 1.960 ms (**-24.8%**) and produced identical KPool top-k selections.

These are component timings only; no end-to-end performance improvement is claimed.
