# [Benchmark] Fix prompt token accounting and harden OpenAI dataset loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/32492) · state: closed · merged: False

## Original PR description

## Motivation

SGLang's benchmarking toolchain (`sglang.benchmark`) has four distinct issues regarding OpenAI-format dataset loading and metric calculation, leading to ‌reports containing inaccurate data:

1. **Confused prompt token definitions**: In `calculate_metrics`, the `total_input` value relies on the client-side tokenizer's estimate (`input_requests[i].prompt_len`) rather than the actual value measured by the server. Although request functions can retrieve `prompt_tokens` from the response, they do not write this back to `output.prompt_len`; consequently, throughput statistics use the estimated value, and the difference between client-side and server-side measurements remains unobservable.

2. **Lack of context length filtering**: `OpenAIDataset` lacks an option to filter requests based on context length.

3. **Incorrect parsing of `apply_chat_template` return values**: When calculating `prompt_len`, `len()` is called directly on the result of `tokenizer.apply_chat_template(messages, tokenize=True, add_generation_prompt=True)`. However, since the result is a `BatchFeature` dictionary, `len()` returns the number of keys (typically 1–3) rather than the token count. This causes the `prompt_len` for OpenAI-format requests to be severely underestimated (resulting in single-digit values) and distorts throughput statistics.

4. **`max_completion_tokens` not recognized**: `sample_openai_requests` only reads `max_tokens`, whereas newer OpenAI APIs and reactive client traces have switched to using `max_completion_tokens`.

## Modifications

- **`python/sglang/benchmark/serving.py`**
- Added logic to request functions (`async_request_openai_completions`, `async_request_openai_chat_completions`, `async_request_truss`, `async_request_sglang_generate`) to parse `prompt_tokens` from the response and write the value back to `output.prompt_len`: for OpenAI interfaces, it retrieves `usage.prompt_tokens`, while for the native `/generate` endpoint, it retrieves `meta_info.prompt_tokens`. 
- In `calculate_metrics`, updated `total_input` to use `outputs[i].prompt_len` (server-side measured value) and added a `total_input_client` metric for the client-side estimate; corresponding fields were added to `BenchmarkMetrics`. - The report now prints two values: `Total input tokens (client)` and `Total input tokens (server)`.

- **`python/sglang/benchmark/datasets/openai_dataset.py`**
- Added a `context_len` parameter to `OpenAIDataset` and `sample_openai_requests` (reusing the existing `args.sharegpt_context_len`); requests where `prompt_len + output_len > context_len` are skipped. Original behavior is maintained if the parameter is not provided. 
- Fixed `prompt_len` calculation: now takes the length (`len()`) of the `["input_ids"]` field from the return value of `apply_chat_template(...)`. 
- Added compatibility for `max_completion_tokens`: the code now recognizes both `max_tokens` and `max_completion_tokens` fields.

## Accuracy Tests

This PR modifies only the benchmarking toolchain (dataset loading and metric calculation); it does not involve model forward passes or kernels, nor does it affect model output accuracy.

## Speed ​​Tests and Profiling

This PR does not affect inference speed. Below is a comparison of benchmark reports before and after the changes, demonstrating improved metric calculation accuracy:

**Before changes** (OpenAI format dataset, single request):
```
Total input tokens:           2          # ← Length of the dictionary returned by apply_chat_template; highly inaccurate
```

**After changes**:
```
Total input tokens (client):  1428       # ← Estimated by local tokenizer (after fixing input_ids parsing)
Total input tokens (server):  1432       # ← prompt_tokens returned by the server; close to the client value
```

Observations:
- Before the change, `Total input tokens` was a single-digit number (representing the count of dictionary keys). After the fix, the client value represents the actual token count and aligns closely with the server's measured value; the slight discrepancy arises from factors like tool token estimation, which is expected.
- The basis for calculating throughput (tokens/s) has shifted from an estimated value to the server's measured value, providing a more accurate reflection of actual costs.
