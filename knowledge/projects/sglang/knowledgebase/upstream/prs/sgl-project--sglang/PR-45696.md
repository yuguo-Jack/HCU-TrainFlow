# [Fix] sgl-router: Do not abort forwarded requests on reqwest's default 30 s TCP_USER_TIMEOUT

[Upstream PR](https://github.com/sgl-project/sglang/pull/45696) · state: closed · merged: True

## Original PR description

## Motivation

The router's forwarding client is a default `reqwest` 0.12 client. On Linux, `reqwest` sets `TCP_USER_TIMEOUT` to 30 s on every connection unless told otherwise (`reqwest-0.12.28/src/async_impl/client.rs:307`). If an engine reads none of a forwarded request's body for 30 s, the kernel aborts the router's send with `ETIMEDOUT`. That can happen when the engine's HTTP process is busy with a burst of long prompts and stops reading request bodies. The router then answers 504 `upstream_timeout` after about 30.5 s, regardless of `request_timeout`.

We hit this in agentic trace replays: about 1,000 new 100K-token prompts arrive at once, and the engine's single HTTP process falls behind. Every send still in flight failed together about 30.7 s after the burst, and the client aborted the run. The error chain was `hyper::Error(Io, Os { code: 110, kind: TimedOut })` at `SendRequest`, and the `TCPAbortOnTimeout` counter rose with it. sgl-model-gateway, which `sglang_router.launch_router` installs, uses the same `reqwest` default.

## Modifications

- `sgl-router/src/proxy/mod.rs`, `build_client`: call `.tcp_user_timeout(None)` on Linux/Android/Fuchsia, the targets where reqwest sets the option. `request_timeout` and the stream idle and stale limits still bound a request.
- `sgl-router/tests/proxy/timeout.rs`: add `request_survives_worker_that_reads_nothing_for_over_30s`. A worker accepts the connection, reads nothing for 40 s, then reads the whole 16 MiB request and answers 200; the test expects a 200. It is Linux-only and `#[ignore]` because it takes about 40 s. Run it with `cargo test --test proxy -- --ignored reads_nothing`.
