# [Fix] kda: Align graph tracking branch dtype with the recurrent state pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/44886) · state: closed · merged: True

## Original PR description

## Motivation

KDA graph tracking can read an FP32 chunk-boundary snapshot or a recurrent-state pool entry. With a BF16 state pool, these branches produce different Triton types, causing compilation to fail before the final store cast.

Observed during GLM-5.3-Flash prefill BCG initialization with BF16 recurrent state:

```text
triton.compiler.errors.CompilationError: at 19:4:
    stride_h_row,
    numel,
    BLOCK: tl.constexpr,
):
    r = tl.program_id(0)
    mode = tl.load(track_mode + r)
    if mode == 0:
        return
    dst = tl.load(track_dst + r).to(tl.int64)
    offs = tl.program_id(1) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < numel
    if mode == 1:
    ^
AssertionError("Mismatched type for val between then block (<['1024'], bf16>) and else block (<['1024'], fp32>)")
```

A cast after the `if/else` cannot resolve this error: Triton requires matching types for `val` when merging the branches, before compiling the subsequent cast.

## Modifications

Cast the snapshot to the state-pool element type before the branches merge. The stored dtype is unchanged, and FP32 state pools retain their existing behavior.

## Accuracy Tests

Validated in GLM-5.3-Flash PD serving on 8 × H200 with BF16 recurrent state and MTP516: GSM8K, 1,314 examples × 2 rounds, scored **95.4% / 95.9%**. These results are from the existing integration configuration containing this fix and the separate Decode RadixCache changes, not a new full-model run on this rebased PR branch.
