# [Feat] gdn: run DFLASH and DSPARK verify on the ReplaySSM spec ring

[Upstream PR](https://github.com/sgl-project/sglang/pull/46185) · state: open · merged: False

## Original PR description

This is component 2 of the DFlash adaptive-verification series. Original implementation and component-only review: https://github.com/jianc99/sglang/pull/2. Integration and full-system results: https://github.com/sgl-project/sglang/pull/46182.

Updated onto upstream `main` (6a319e7b). All applicable pre-commit checks passed on this branch. The GPU tests and benchmark results below were run previously on the original source branch; they have not been rerun after this upstream update. Submission preparation used AI assistance.

---

## Motivation

On Qwen3.5/3.8 GDN targets, DFLASH and DSPARK verify by writing a full SSM state snapshot per draft token (FlashInfer MTP or the Triton recurrent verify) and scatter the accepted one afterwards. `--enable-linear-replayssm-spec` avoids those snapshots with a compact per-request ring, but it was refused for DFLASH/DSPARK on non-KDA models: their commit, `HybridLinearAttnBackend.update_mamba_state_after_mtp_verify`, only knew the KDA ring and would have scattered snapshots that ReplaySSM does not allocate.

Wiring the GDN ring into that commit also turned up problems that affect every algorithm on the GDN spec ring:

- the ring length was never checked: a draft window longer than the ring was silently truncated, and a ring shorter than 16 failed at the first verify;
- the cursor advance and the other three ring kernels disagreed on which rows are live;
- a non-finite value at a rejected draft could reach the accepted outputs and the committed state;
- the verify replayed empty history for every row, even though DSPARK, DFLASH and the commit of a bf16 state fold every step.

Separately, nothing refused DSPARK's compact verify on GDN targets. Compact verify packs per-request verify lengths into one token list, but GDN target verify views a dense `[batch, draft tokens]` window, and eager compact verify on Qwen3.6 has been reported to hit an illegal memory access.

## Modifications

Fixes first, then the feature and the speedup, then two follow-up fixes:

1. **[Fix] gdn: check the ReplaySSM ring length and advance cursors by state slot.** When the GDN spec ring is allocated, `MambaPool` requires a power-of-two `--linear-replayssm-cache-len` of at least 16 that holds the draft window, and the flag's help says so. A ring of 8 used to pass startup and then fail to compile the compact commit at the first verify. The cursor advance skips rows without a state slot, as the verify, commit and finish kernels already do.
2. **[Fix] gdn: refuse compact verify on GDN targets.** `GDNAttnBackend` raises at startup when the target's speculative algorithm builds ragged layouts and `SGLANG_RAGGED_VERIFY_MODE=compact`. Static and cap-accept verify (cap-accept verifies the dense window and only trims acceptance), draft workers and other algorithms are unchanged. This commit is independent of the others; see "Related upstream work" for how it interacts with sgl-project/sglang#38897.
3. **[Fix] gdn: keep rejected drafts out of ReplaySSM spec outputs and state.** The verify selects its causal terms with `tl.where` instead of multiplying by zero. The commit masks its ring loads to the committed history.
4. **[Feat] gdn: commit ReplaySSM spec state for DFLASH and DSPARK.** The cursor advance, the fold of the accepted window and the conv rollback move into one helper, `commit_gdn_replayssm_after_verify`. The generic spec commit and the backend commit (DFLASH/DSPARK) both call it. The backend commit folds every accepted window whatever the state dtype, as the KDA fold in the same function does, so `temporal` is the committed state after each step and radix donation and state copies read the slot directly. Only the lazy fold needs the draft length (for its early flush), so the helper takes `max_spec_len` only without `fold_every_commit`. The configurator refusal is removed, and an assert before the snapshot scatter checks that snapshots exist.
5. **[Perf] gdn: skip the ReplaySSM verify history replay for rows without history.** The history terms run only when `write_pos > 0`, and they are built after the K loop.
6. **[Fix] gdn: keep the fused multiply-adds in the ReplaySSM spec verify selects (0d3649d36).** Commit 3 wrote each masked term as `tl.where(m, a * b, 0)` and added it to the accumulator, so the multiply and the add no longer fused and the `(I + A)^-1` row update, `D = R T^T` and the output `D F` rounded differently from main. The `(I + A)^-1` reduction now masks the operand, and the other two select the fused update, `tl.where(m, tl.fma(a, b, acc), acc)`, never the product alone. An implicit `acc + a * b` inside the select is not enough: at a window of 16 the compiler still splits some of them. Rejected positions still never reach the result.
7. **[Fix] test: key the GDN compact verify refusal test on supports_ragged_verify (bf3c6b7a5).** Test only. The refusal test used to name the algorithms that build ragged layouts; it now uses an algorithm stub with the case's `supports_ragged_verify()` value, so it keeps passing when another algorithm gains ragged verify.

No new flags or environment variables.

Behavior changes:
- A ring that cannot hold the draft window, or is shorter than 16, now fails at startup, for any algorithm on the GDN spec ring. For example, EAGLE or NGRAM with more than 16 draft tokens at the default ring of 16 now needs `--linear-replayssm-cache-len 32`.
- GDN plus DSPARK with `SGLANG_RAGGED_VERIFY_MODE=compact` now fails at startup.

Memory: the ring replaces the per-draft snapshots. At TP1 with 128 requests on Qwen3.8-27B it takes 3.04 GB instead of 72.6 GB of snapshots, and the KV cache grows from 1.13M to 2.03M tokens. DFLASH and DSPARK fold every commit, so their ring never holds more than one window, but 16 is already the smallest ring the compact commit supports (it reduces over the whole ring with `tl.dot`), so the default fits drafts of up to 16 tokens without waste.

## Accuracy Tests

Validated on GB300 (SM100) only, upstream image `lmsysorg/sglang:v0.5.21` with this tree mounted. The GPU test's numeric bounds are relative to the Triton snapshot verify, which runs on every GPU; it has not been run on SM90 yet.

- `test/registered/unit/spec/test_gdn_replayssm_dflash_commit.py` (new, CPU) covers:
  - the ring-length errors;
  - routing of the DFLASH/DSPARK backend commit, including padding rows, PP rows and track slots;
  - that the generic commit passes the state slots to the cursor advance;
  - the snapshot assert;
  - the compact refusal, and that static and cap-accept pass.
- `test/registered/attention/unittests/gdn/test_gdn_replayssm_direct_commit.py` (new, GPU) runs `GDNAttnBackend.forward_extend` and `update_mamba_state_after_mtp_verify` at Qwen3.8 head shapes (HV/H = 3, K = V = 128, block 8, ring 16) for bf16 and fp32 states:
  - a 256-step verify/commit chain against a float64 sequential GDN reference with conv, bounded at 1.25x the error of the Triton snapshot verify on the same inputs. Measured ratios: outputs 1.05 (bf16) and 1.03 (fp32), states 0.97 and 1.00;
  - a 128-step lazy-fold chain (fp32, ring 32), where verifies replay up to 16 history records (ratio 1.05);
  - track slots. The active fold may differ by 1 ulp when the track path is compiled in;
  - NaN/Inf injected at rejected drafts leaves outputs, state, conv and cursors bit-identical, for bf16 and fp32 states with the fold every commit and for the lazy fold of the generic (EAGLE/MTP) commit, which runs four steps with committed history in the ring before the second poisoned window;
  - rows without a state slot keep their cursors;
  - CUDA graph replay matches eager.
- With item 6, the two new files give 16 passed and 13 subtests.
- Existing tests pass unchanged: `test_ngram_mamba_verify_update.py` and `test_linear_attn_config.py`, and a regression set of `test_replayssm_ring_accounting.py`, `test_mamba_unittest.py`, `test_linear_replayssm_decode.py`, `test_mamba_track_state_dtype.py`, `test_gdn_prefill_backend_policy.py`, `test_gdn_mis_metadata.py` and `test_gdn_cutedsl_ring_verify.py` (53 passed on this branch and on main). Every commit passes the tests that exist at that commit.
- compute-sanitizer: memcheck reports no device errors on the non-chain tests and on the lazy-fold chain that replays history; racecheck on the non-chain tests reports 0 hazards.
- Bit-exactness of item 6 against main's verify kernel, with both kernels loaded in one process: 12 chained verify + commit steps at Qwen3.8-27B shapes, batch 16, comparing outputs, ring records, states and cursors by raw bits.
  - With commits 1–4 plus item 6, every field is bit-identical to main on finite inputs for draft windows 4, 8 and 16, bf16 and fp32 states, the fold every commit and the lazy fold (8 configurations).
  - On the full branch the bf16 configurations are bit-identical; fp32 differs only through commit 5's TF32 rounding (see Numerics below).
  - Before item 6, a bf16 state differed from main on 52 of 4.7M outputs at window 4, 235 of 9.4M at 8 and 619 of 18.9M at 16, along with the ring records and states folded from them.
  - With NaN/Inf at the rejected drafts, no accepted output, state or cursor changes; main turns them all into NaN.

  - Acceptance length matches: c1 3.83 (snapshot) vs 3.77 (ReplaySSM); c8 3.88–3.90 vs 3.88–3.89.
  - Both paths are deterministic at c1 (16/16 identical across two runs each). ReplaySSM matches the snapshot path exactly on 4/16 requests and diverges after 47% of the text on average. All 12 divergences, and 36 of 38 at c8, start at a near-tie: the top-2 logprob gap is under 0.05 (median 0.008).

With an fp32 state in both paths, ReplaySSM matches the snapshot path on 5/16, acceptance 3.86 vs 3.94, and all 11 divergences start at a top-2 gap of 0.024 or less.
  - TP2 greedy (ReplaySSM, c1 and c8) serves without errors, acceptance 4.09 and 3.92.
  - The final branch reproduces the greedy outputs of the revision measured above: 16/16 at c1, and 48/48 against one of its two c8 runs (those two runs agree on 21/48, because batching changes the rounding).

These serving checks predate item 6.

## Speed Tests and Profiling

Setup: Qwen3.8-27B (48 GDN + 16 attention layers), DFlash2 block-8 draft, GB300, TP1, `--max-running-requests 128`, bf16 mamba state, radix cache off, overlap scheduling on. Client: SPEED-Bench first turns, T=1, top_p 0.95, top_k 20, up to 4096 output tokens.

Decode tok/s = per-request decode rate (output tokens after the first / time after the first token), times concurrency; c1 is the single-request decode rate.

| decode tok/s | snapshot verify (main) | ReplaySSM (this PR) | change (means) |
|---|---|---|---|
| c128 | 6967 / 6921 / 6994 | 7730 / 7714 / 7672 / 7686 | +10.6% |
| c64 | 5881 / 5933 / 5988 | 6591 / 6412 / 6731 / 6476 | +10.4% |
| c32 | 4809 | 5151 | +7.1% |
| c8 | 2058 | 2239 | +8.8% |
| c1, 16 requests | 348 | 327 | -5.9% |
| c1, 48 requests | 335 | 333 | -0.5% |
| c1 greedy, 48 requests | 365 | 372 | +2.0% |

The fourth ReplaySSM run at c64 and c128 is the final branch before item 6; the first three ran an earlier revision with the same kernels. No run in this table includes item 6 (the end-to-end numbers in https://github.com/sgl-project/sglang/pull/46182 do, on the merged stack); its verify kernel time is in the last table.

At c128 the running cap equals the concurrency, so about one request waits in the queue. https://github.com/sgl-project/sglang/pull/46182 shows that this setup reads 7-15% higher at that level than a larger cap, on both sides, so compare c128 only within this table.

Acceptance length is unchanged from c8 to c128: 3.55–3.69 for main and 3.55–3.70 for this PR.

At c1 acceptance is dominated by which trajectories the requests take: 3.67 for main vs 3.53 for this PR on the first 16 requests at T=1, 3.57 vs 3.53 on 48 requests, and 3.96 vs 4.05 greedy. The verify step rate, decode tok/s divided by acceptance length, is within 1% on 48 requests: 93.7 vs 94.3 steps/s at T=1 and 92.2 vs 92.0 greedy (95.0 vs 92.9 on the first 16 requests).

Numerics on finite inputs:
- Commit 3 changes the rounding of a few sums: with a bf16 state, 1e-5 to 3e-5 of the outputs differ over 12 chained steps, by up to 4e-3 of the largest output. Item 6 removes this difference.

## Related upstream work

- **sgl-project/sglang#38897 (conflicts with commit 2).** It declares ragged-verify graph support on `GDNAttnBackend` for every GDN verify path (`supports_ragged_verify_graph = True`), so compact verify runs on GDN without ReplaySSM. Commit 2 refuses exactly that configuration at startup. Its conv changes handle packed rows (a varlen kernel for CUDA chain verify, a dense scratch otherwise), but it does not change the FlashInfer GDN verify kernel (`gdn_flashinfer.py`), which still views the verify tokens as `[bs, seq_len // bs]`; with `--linear-attn-verify-backend flashinfer` (the verify default whenever the decode backend is flashinfer) a packed batch would be read as uniform. What to do: if sgl-project/sglang#38897 lands first, drop commit 2 or narrow it to the verify kernels that cannot read packed rows; if this PR lands first, sgl-project/sglang#38897 needs to lift the refusal for the paths it makes safe. https://github.com/sgl-project/sglang/pull/46189 is our version of that lift, for the ReplaySSM path only.
- **sgl-project/sglang#42688 (same change as part of commit 3).** It masks the compact commit's ring loads to the committed history, the same five load masks as commit 3. It also masks the keys and updates past the tracked prefix before the track products, which this PR does not do. It does not touch the verify kernel. What to do: whichever lands second drops its copy of the history-load masks; the verify selects in commit 3 (with item 6) stay either way, and the track-prefix masking comes from sgl-project/sglang#42688.
- **sgl-project/sglang#36683, sgl-project/sglang#35725, sgl-project/sglang#42209 (alternatives to commit 4).** All three connect DFLASH (the first two also DSPARK) to ReplaySSM on GDN through the fold-every-commit path, the last one behind a new environment variable. This PR uses the circular ring the GDN pool already allocates, shares one commit helper between the generic and backend commit paths, and adds the ring-length, cursor and NaN fixes. Reviewers should pick one approach. The latest head of sgl-project/sglang#35725 also declares GDN ragged-graph support and sends ragged batches to the Triton varlen verify, so it conflicts with commit 2 the same way sgl-project/sglang#38897 does.
- **sgl-project/sglang#35413** reported the eager compact-mode illegal memory access on Qwen3.6 that commit 2 refuses.
