# [Fix] qwen2_moe: Replicate the shared expert under DWDP

[Upstream PR](https://github.com/sgl-project/sglang/pull/44828) · state: open · merged: False

## Original PR description

## Motivation

Under DWDP (#29778), sparse MoE runs on DP-local tokens and `post_experts_output_is_complete()` is True, so `reduce_moe_output` skips the all-reduce after the experts. `Qwen2MoeSparseMoeBlock` replicates its shared expert only for the a2a backends. Under DWDP it stays TP-sharded with `reduce_results=False`, so each rank adds 1/TP of the shared expert's output for its own tokens, and nothing sums the shards.

Shared-expert fusion is wrong under DWDP too: DWDP prefetches only the routed experts, and the fused shared slot's routing weight is pre-scaled by 1/ep_size for the post-experts all-reduce that DWDP skips. Qwen3-Next enables this fusion on CUDA.

This affects every model built on `Qwen2MoeSparseMoeBlock` with a shared expert: Qwen1.5/Qwen2 MoE, Qwen3-Next, Qwen3.5 MoE and Qwen3.8 (`qwen4_exp`). Qwen3 MoE has no shared expert. #39802 fixes the same problem for DeepSeek-V2.

## Modifications

- `Qwen2MoeSparseMoeBlock`, under DWDP:
  - The shared expert is built with `parallel_group="replicated"`, as for the a2a backends.
  - Shared-expert fusion is turned off with a warning, so the block falls back to the separate (now replicated) shared-expert MLP. The loaders read the decision from the built layer (`num_fused_shared_experts`), as for the existing per-rank-slot fallback.
- Test (CPU, fails before this change): `TestQwen2MoeSharedExpertUnderDwdp` in `test_shared_experts_fusion_gates.py` builds the block on a DWDP layout and checks that the shared expert holds its full weights and stays out of the fused MoE. The same topology without DWDP keeps the TP shard and the fusion.

Cost: the shared expert's weights in full on every rank. At load, Qwen3.5-35B-A3B goes from 12.78 to 12.99 GB per rank and Qwen3.8-Flash-Next from 24.13 to 24.54 GB (its FP8 checkpoint keeps the shared experts in BF16).

## Accuracy Tests

Setup:
- One node, 8x H20. DWDP: `--tp-size 8 --dwdp-size 8 --chunked-prefill-size 65536 --load-balance-method total_tokens --mm-enable-dp-encoder` in the default `--disaggregation-mode null`, no speculative decoding.
- The non-DWDP baseline is plain TP8. Qwen3.8 adds `--ep-size 8`: its FP8 128x128 blocks cannot split the 640-wide experts 8 ways.
- GSM8K: chat API, 5-shot, thinking disabled, 200 questions.
- Image: nightly 2026-10-14 (684fea8a). Its `qwen2_moe.py` is byte-identical to `main` a038a0d, and the fixed arm mounts this PR's file.
- Qwen3.8 also runs with its cookbook GDN flags and, under DWDP, `SGLANG_USE_ATTN_TP_NGRAM=1` (as in #44763).

| Model | Shared expert | TP8 | DWDP8, main | DWDP8, this PR |
|---|---|---|---|---|
| Qwen3.5-35B-A3B (BF16) | separate MLP | 0.975 | 0.170 | 0.975 |
| Qwen3.8-Flash-Next (FP8) | separate MLP | 0.975 | 0.915 | 0.985 |
| Qwen3-Next-80B-A3B-Instruct (BF16) | fused on CUDA | 0.965 | fails at startup | 0.970 |

- On `main`, Qwen3-Next fails in DWDP setup with `cuMemcpyDtoD: CUDA_ERROR_INVALID_VALUE` in `_copy_local_weights_to_handles`: each rank's expert tensors carry the fused shared slot on top of the routed shard that DWDP sized its handles for. With this PR every rank logs the fusion-off warning and the model serves.
- The separate-MLP models run on `main` but lose accuracy, more for Qwen3.5 than for Qwen3.8.

No speed numbers: this is a correctness fix, and DWDP's prefill throughput is covered in #29778 and #44763.

Related: #22084 tracks DWDP. #39802 (open) fixes the same shared-expert sharding for DeepSeek-V2. The Qwen3.8 runs in #44763 (DWDP + MTP) mounted this fix.
