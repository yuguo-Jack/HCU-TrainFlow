# [Perf] [NVIDIA] muse-spark: column-split the pooler and small-M unpooler on Hopper

[Upstream PR](https://github.com/sgl-project/sglang/pull/44921) · state: closed · merged: False

## Original PR description

## Motivation

Follow-up to #44666. This draft targets its branch so the diff shows only this change. I'll retarget it to main once #44666 merges.

On Hopper, Muse Spark runs the pooler (8192 -> 4096) and unpooler (4096 -> 8192) as replicated BF16 GEMMs on every TP rank. At decode sizes these are weight reads: each rank reads 128 MB per layer for the two projections, and all 8 ranks of the H200 TP8 recipe read the same bytes.

`gemm_ag` already column-splits these on SM103, and it runs fine on SM90 (multimem stores need SM90+). Today SM90 only uses it for the unpooler at M <= 8.

## Modifications

- `gemm_ag.projection_max_tokens`: on SM90 with TP4/8, split the 4096-wide pooler up to 512 rows (same as SM103) and the 8192-wide unpooler up to 64 rows. SM103 and other archs are unchanged.
- SM90 has no cluster boundary to defer the unpooler gather into, so the gather runs inline. Past 64 rows the 8192-wide gather costs more than the GEMM saves.
- The pooler call site and the push-workspace reservation accept SM90. The reservation is sized per projection width (4 MB per slot on SM90).
- New multi-GPU test: the gathered output equals each rank's slice GEMM side by side, at M = 1 and at the arch bound, with the reserved push space.

## Accuracy Tests

The split output differs from the replicated GEMM by at most 2 bf16 ulp per element (cuBLAS picks a different kernel for the narrow slice), and is bit-exact for M >= 1024. No accuracy eval with real weights yet.
