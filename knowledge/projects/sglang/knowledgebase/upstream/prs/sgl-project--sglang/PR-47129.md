# [Perf] [NVIDIA] muse-spark: Add B200 runtime optimizations

[Upstream PR](https://github.com/sgl-project/sglang/pull/47129) · state: open · merged: False

## Original PR description

## Changes

Bring the distinct, reviewable parts of the Muse Spark B200 AutoResearch B1 candidate to main:

- Admit the existing fused projection/all-gather path on SM100 at TP8 for BF16 projections with 4096/8192 output columns and up to 128 token rows. Existing multicast, workspace, layout and dtype checks still apply.
- With the experimental opt-in enabled and no explicit prefill/decode interval, allow one DFlash verification step between consecutive prefill batches. Synchronized DP scheduling is excluded; empty and prefill-only running batches do not block admission.
- Scan paged-allocation prefixes in fixed256-request blocks with a runtime loop above256, avoiding batch-size-dependent compilation variants, and avoid value specialization of the last-location kernels' runtime batch/stride arguments. Update both paged and current chain allocator call sites. Masked prefix/sequence-length loads explicitly use `other=0`, giving inactive lanes the additive identity before the extend-kernel reductions; the decode scan also explicitly zero-fills inactive lanes.

**Changed defaults**

- `SGLANG_MUSE_B200_OPTIMIZATIONS` is new and defaults to **false**. It controls B200 projection eligibility and DFlash interleaving; the existing projection/scheduling policies remain in effect when unset. It is process-wide: the interleaving branch applies to DFlash without synchronized MLP scheduling when explicitly enabled, and is not a general cross-model performance recommendation.
- Paged extend/decode kernels now use fixed256-request scan blocks with explicitly zero-filled masked lanes; last-location kernels avoid runtime value specialization. These shared JIT-policy changes are unconditional. The separate request-to-token assignment scan retains its minimum64 policy. Current-head numerical and compilation-growth coverage is listed below; source-bound isolated-cost and cross-model checks are preserved in the evidence archive.

To opt in, prefix an existing launch command with `SGLANG_MUSE_B200_OPTIMIZATIONS=1`. This flag does not change numerical generation settings, memory fraction, or the model configuration.

Duplicate/scope audit: the DFlash FC-split implementation is excluded because #45895 already proposes that mechanism. Current main already has dynamic small-copy specialization controls, so the historical tuple-encoding workaround is excluded. The B1 hardcoded FlashInfer tactic pin and graph-bucket changes are also excluded. This is not the geometric compaction policy in #46739, and it contains no RMSNorm changes from #46622. No `doc/` or `docs/` files are changed.

**Above 64 requests the alloc kernels still recompile while serving**

This PR stops the mid-serving recompiles of `alloc_extend_kernel` and `alloc_decode_kernel` only for batches of up to 64 requests. `bs_upper` is still a constexpr, so with `max_running_requests` above 64 both kernels compile again each time the running batch first reaches 128, 256, … requests: about 120 ms per width on MI355X (86–94 ms `alloc_extend_kernel`, 28–33 ms `alloc_decode_kernel`).

Otherwise the change works on AMD (gfx950): `test_paged_allocator.py` passes and kernel time matches main (within ±2 %; two noisy cases at −4.9 % and +3.1 %).

**Proposed fix:** sum the prefix in fixed 256-request blocks, so that each kernel compiles once for every batch size. The first block is straight-line; the loop only runs above 256 requests:

```python
BLOCK_BS: tl.constexpr = 256
first = tl.arange(0, BLOCK_BS)
first_seq_lens = tl.load(seq_lens_ptr + first, mask=first <= pid, other=0)
first_pre_lens = tl.load(pre_lens_ptr + first, mask=first <= pid, other=0)
extend_lens = first_seq_lens - first_pre_lens
num_new_pages = (first_seq_lens + page_size - 1) // page_size - (
    first_pre_lens + page_size - 1
) // page_size
for block_start in range(BLOCK_BS, pid + 1, BLOCK_BS):
    load_offset = block_start + tl.arange(0, BLOCK_BS)
    mask = load_offset <= pid
    seq_lens = tl.load(seq_lens_ptr + load_offset, mask=mask, other=0)
    pre_lens = tl.load(pre_lens_ptr + load_offset, mask=mask, other=0)
    extend_lens += seq_lens - pre_lens
    num_new_pages += (seq_lens + page_size - 1) // page_size - (
        pre_lens + page_size - 1
    ) // page_size
```

`alloc_decode_kernel` takes the same form with `pre_lens = tl.where(mask, seq_lens - 1, seq_lens)`, and the callers stop passing `batch_scan_width(bs)`.

Cost of the proposed fix: at most 0.14 µs per launch of a ~2 µs kernel. Against this PR that is +0.6 to +2.0 % at 129–256 requests, and up to +6.9 % at 64 or fewer, where this PR's 64-wide scan reduces within one warp. The indices are identical.

A test that each kernel compiles once at batch sizes 1–300 and matches the non-Triton allocator fails on main (7 variants) and on this PR (3), and passes with the proposed fix.
