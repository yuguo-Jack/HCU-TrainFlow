# fix(gemma4): stop array parser hanging on nested arrays with brackete…

[Upstream PR](https://github.com/sgl-project/sglang/pull/46367) · state: open · merged: False

## Original PR description

## What

`_parse_gemma4_array` could loop forever on a tool call whose nested array contains a `]` inside a `<|"|>`-delimited string.

The nested-array branch balanced brackets without skipping string contents (every other scanner in the file — the nested-object branch, the array branch in `_parse_gemma4_args`, and `_find_matching_brace` — skips them). A `]` inside a string closed the inner array early, and the leftover bare `]` landed in the bare-value branch, whose scan stops at `]` without consuming it. The element loop then made zero progress and spun on that request forever.

## Fix

- Skip `<|"|>`-delimited string contents while balancing nested arrays, matching the other scanners in the file.
- Guard the bare-value branch against zero progress so malformed output terminates instead of hanging the parser.

## Reproduction

Before the fix this input never returns:

```python
_parse_gemma4_args('paths: [[<|"|>a]b<|"|>, <|"|>c<|"|>]]')
```

After the fix it returns `{"paths": [["a]b", "c"]]}`. The hang also reached `Gemma4Detector.detect_and_parse` and `parse_streaming_increment` on `<|tool_call>call:f{paths: [[<|"|>a]b<|"|>, <|"|>c<|"|>]]}<tool_call|>`.

## Tests

Added `test/registered/unit/function_call/test_gemma4_detector.py` (8 cases): the hang case, open/close brackets inside strings, deep nesting, stray-bracket termination, and unchanged behavior for plain nested arrays, flat strings, one-shot and streaming parses. The added tests pass with the fix; the hang cases do not terminate without it.
