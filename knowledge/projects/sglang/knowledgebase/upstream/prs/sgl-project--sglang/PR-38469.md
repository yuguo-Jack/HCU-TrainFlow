# fix: bound the DSA kpool ragged MQA logits allocation

[Upstream PR](https://github.com/sgl-project/sglang/pull/38469) · state: closed · merged: False

## Original PR description

The kpool indexer's ragged extend path builds one dense fp32 logits tensor whose two dimensions are both summed over the whole batch, while each q row may only read its own request's column window. Peak memory is therefore quadratic in the request count and each row's useful area is ~1/B of the allocation, so long-context traffic with prefix-cache hits kills every TP rank inside deep_gemm.fp8_mqa_logits.

The non-kpool indexer already had a memory budget for the same tensor, but the kpool path carried a dead, drifted copy of the predicate and never called it. Move the policy to one module both flavors import, and split the kpool computation per request and then per q-row chunk under that budget. The single-call fast path is preserved unchanged when the dense tensor fits.

Fixes #37712

## Modifications

  - New `dsa/mqa_logits_budget.py` — single home for the budget policy, since both indexer flavors need it and they are not in a subclass relationship. A second copy is how the kpool path drifted in
  the first place.
  - `dsa_indexer.py` — drop the class constants and the three budget methods, import the module functions instead.
  - `dsa_indexer_kpool.py` — delete the dead duplicate; consult the shared budget, and when the dense tensor does not fit, split per request (`plan.ragged_groups`) and then per q-row chunk. Every
  column index rebases into the sliced K window. The single-call fast path is preserved unchanged when it fits.
  - `kpool_plan.py` — add `RaggedGroup` and `KPoolExtendPlan.ragged_groups`, the host-side geometry of the ragged concat layout, built from CPU lists already computed in the plan so there is no
  device→host sync.

## Accuracy Tests

GLM-5.3-Flash on 8× B300-class GPUs, serving shape from the issue.

  Chunking must not change which KV tokens the indexer selects. 4 passkey-retrieval prompts (~72 K tokens, needles at four depths, greedy), sent serially so batch composition is fixed, with
  `SGLANG_DSA_MQA_LOGITS_FREE_MEM_FRACTION` large (dense path) vs `0.001` (~32 q-row chunks per step):

  | | result |
  |---|---|
  | dense | 4/4 |
  | chunked | 4/4, byte-identical output text |

## Speed Tests and Profiling

  12 × 132096-token contexts in one batch (18.14 GiB dense, i.e. above the budget so the fix does chunk), warm repeats with `/flush_cache` between each:

  | | wall |
  |---|---|
  | chunked | 0.6 / 0.6 / 0.7 s |
  | dense (budget raised) | 0.6 / 0.6 / 0.6 s |

  No measurable cost. Note the *first* long-context batch after server start is 3–20× slower from deep_gemm JIT; only warm repeats are comparable.
