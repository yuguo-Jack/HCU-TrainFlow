# [Perf] [NVIDIA] fused_moe: Add H20-3e configs for GLM-5.3-Flash TP8/TP4

[Upstream PR](https://github.com/sgl-project/sglang/pull/48314) · state: open · merged: False

## Original PR description

## Motivation

With plain tensor parallelism (`--tp 8` or `--tp 4`, no `--ep`), GLM-5.3-Flash runs its routed experts through the Triton fused MoE. The serving lookups are:

- `E=289` for the target layers, because the shared expert is fused into the routed experts by default.
- `E=288` for the NextN/MTP draft layer, and for any run with `--disable-shared-experts-fusion`.

#45089 added configs for these shapes under `device_name=NVIDIA_H20` (the 96 GB H20). The 141 GB H20-3e reports `NVIDIA H20-3e`, so it has no config for them: every MoE layer logs `Config file not found at .../E=289,...,device_name=NVIDIA_H20-3e,...` and `Using default MoE kernel config.`, and runs the block-FP8 default (`BLOCK_SIZE_M=64`, `BLOCK_SIZE_N=128`, `BLOCK_SIZE_K=128`, `GROUP_SIZE_M=32`, 4 warps, 3 stages, no TMA) for both GEMMs.

## Modifications

Eight Triton 3.8.0 configs (main pins torch 2.14.1, which ships Triton 3.8.0), an up-projection and a down-projection (`_down`) config per shape:

| Files | Used by |
| --- | --- |
| `E=289,N=256,device_name=NVIDIA_H20-3e,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP8, target layers |
| `E=288,N=256,device_name=NVIDIA_H20-3e,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP8, MTP draft layer / shared-expert fusion disabled |
| `E=289,N=512,device_name=NVIDIA_H20-3e,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP4, target layers |
| `E=288,N=512,device_name=NVIDIA_H20-3e,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP4, MTP draft layer / shared-expert fusion disabled |

How they were tuned (the same procedure as the H20 `_down` PR, #48313):

- `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton_sep.py` with `--enable-tune-up-tma`. Round 1 tunes the down GEMM. Round 2 tunes the up GEMM, writing its output in the layout the chosen down config reads (sorted when the down config uses TMA).
- Routing from `--topk-ids-dir`: top-k ids captured from GLM-5.3-Flash serving (TP4 on H20, 3 ShareGPT prompts of about 8k tokens, all 42 MoE layers, 126 files of shape `[T, 9]`, of which the tuner reads 100; column 9 is the fused shared expert). The routing depends on the model and the prompts, not on the GPU. The `E=288` shapes use the first 8 columns.
- Full default search space (1,280 configs after the `BLOCK_SIZE_K` filter) and the default 18 batch sizes, each batch size in its own process on one GPU. The script's single-GPU path neither applies the `BLOCK_SIZE_K` filter nor writes files, so I called its `tune()` per batch size with the filtered space and wrote the files with its `save_configs_sep()` on an H20-3e.
- To get `E=289`, I applied #43647's one-line `common_utils.py` change locally, as for #45089. Without it the tuner writes only `E=288`. This PR leaves the tuner alone.

The result uses TMA for the down GEMM in all 72 entries and for the up GEMM in 70 (not at M=4096 for `N=256`). `BLOCK_SIZE_M` is 16 for M ≤ 512 and 32 for M = 1024–3072. At M=4096 it is 64, except 32 for `E=288,N=512`. Each `_down` entry has the same `BLOCK_SIZE_M` as its up entry, which the loader requires.

## Setup

- Image `lmsysorg/sglang:nightly-dev-cu13-20261031-a2cafa56` (torch 2.14.1+cu130, Triton 3.8.0), with `PYTHONPATH` set to a source tree. The "main" arm is main `ea2fda7` (no H20-3e file for these shapes); the "this PR" arm adds the eight files. The two trees differ only in these files. Between `ea2fda7` and the base of this branch (`57bfde9f2c`), the Triton fused-MoE kernel (`fused_moe_triton_kernels.py`) and `triton_utils/` (config loader, `fused_moe.py`) are unchanged.
- One 8× H20-3e 141 GB node. Its GPU 1 overheats under sustained load: 86–87 °C with software thermal slowdown, and a per-case median SM clock of 660–840 MHz during TP8 serving. The other seven GPUs stay at 1980 MHz.
  - The six batch sizes first tuned on GPU 1 were re-tuned on the other GPUs; for M ≥ 48, GPU 1's best times had been 1.4x–1.7x slower. All six picks changed, in four files.
  - The kernel benchmark uses GPUs 0, 2, 3, 4. TP4 serving uses GPUs 4–7.
  - TP8 serving needs all eight GPUs, so both TP8 arms include GPU 1. The TP8 absolute numbers are low for that reason; the two arms run on the same GPUs.

## Kernel benchmark

This benchmark calls the runtime `fused_moe` (the serving entry point, including the `_down` lookup) with random FP8 weights and scales and the captured routing. For each M, a CUDA graph holds 10 calls, one per captured routing file (MoE layers 10–13, the first M rows of each), with top-k 9 for `E=289` (the fused shared expert included, as in serving) and 8 for `E=288`. The graph is replayed 100 times and the time per call is recorded. The two arms alternate on the same GPU in ABBA order for 6 rounds, and the tables show the median of each entry. Speedup = main / this PR. Main uses the default config here.

## Serving

The two arms of each pair use the same node, image and flags, and differ only in the source tree on `PYTHONPATH` (see Setup). The main arm's server log shows `Config file not found` for the up and `_down` files and `Using default MoE kernel config.`; this PR's shows `Using MoE kernel config from` for both files of each shape it runs. Other settings are the same as #45089:

- Triton MoE (auto-selected), BF16 KV cache, default DSA backends, radix cache off.
- `--reasoning-parser glm45 --tool-call-parser glm47`.
- MTP: `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.
- Load: `sglang.bench_serving --dataset-name random-ids --tokenize-prompt --random-range-ratio 1.0 --request-rate inf --seed 42`, with 4× concurrency prompts (8 at concurrency 1), after one warm-up run per server start.

Some runs below used the first merge of these files, made before the six re-tuned batch sizes replaced the GPU 1 results. It differs from the final files only in:

- `E=288` entries, which only the MTP draft layer reads (TP8: M=8 and 4096; TP4: M=48, 256 and 2048).
- One `E=289` entry: TP8 `_down` at M=4, `GROUP_SIZE_M` 64 → 32. The tuner timed the old and new picks at 30.8 and 31.0 us.

So the runs without MTP measure the final target-layer configs, apart from that one TP8 entry.

## Accuracy

GSM8K 20-shot, 500 questions (`sglang.test.run_eval --eval-name gsm8k --api completion --num-shots 20 --num-examples 500 --max-tokens 512`; 128 client threads without MTP, 16 in the MTP runs above):

| Layout | Mode | Files | Main | This PR |
| --- | --- | --- | --- | --- |
| TP4 | no MTP | final | 0.922 | 0.926 |
| TP8 | no MTP | first merge | 0.930 | 0.934 |
| TP4 | MTP (runs above) | first merge | 0.930 / 0.930 | 0.924 / 0.934 |
| TP4 | MTP (runs above) | final | 0.932 / 0.942 | 0.932 / 0.936 |

The differences go both ways and are at most 1.0 point, against a standard error of about 1.1 points for one 500-question score at this accuracy.

Numerics (main `57bfde9f2c` vs this branch, GPU 0): with fixed random FP8 weights and captured routing (M from 1 to 2048), the `fused_moe` outputs of the two arms differ by at most 1.1e-3 (relative L2) on all four shapes. Against a float32 reference (dequantized weights, unquantized activations, M ≤ 64), both arms have a relative error of 4.2e-2 to 4.6e-2, and the two arms' errors differ by at most 2e-5. The reference does not quantize activations, which both arms do, so neither arm matches it exactly; their errors are the same.
