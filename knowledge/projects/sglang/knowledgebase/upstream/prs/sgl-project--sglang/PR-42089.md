# [AMD] Enable mixed wave32/wave64 ROCm AOT kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/42089) · state: closed · merged: False

## Original PR description

# [AMD] Enable mixed wave32/wave64 ROCm AOT kernels

## Summary

Enable `sgl_kernel` builds for `gfx1100` and `gfx1201`, including mixed CDNA/RDNA binaries.

The optimized MoE TopK launchers previously used wave64 in ROCm host code while gfx11/gfx12 device code used wave32. This made host launch geometry disagree with the compiled kernel. This PR builds explicit 32- and 64-lane variants and selects the correct one from the current device at runtime.

## Changes

- Add `gfx1100` and `gfx1201` to the `setup_rocm.py` target allowlist. Existing semicolon-separated `AMDGPU_TARGET` handling produces the fat binary.
- Read the current device's cached `warpSize` through `at::cuda::getCurrentDeviceProperties()`.
- Template softmax and sigmoid TopK kernels, constants, launch bounds, grid calculations, and block dimensions on `WARP_SIZE_PARAM`.
- Dispatch `<32>` on wave32 devices and `<64>` on wave64 devices. CUDA keeps its existing 32-lane path.
- Compile QuickReduce placeholders on gfx11/gfx12 while preserving the real implementation on CDNA. Runtime QuickReduce remains restricted to gfx94/gfx95.
- Keep custom and deterministic all-reduce compiled and registered for mixed binaries.

## Additional changes (rebased onto current `amd_march`)

- `setup_rocm.py`: `gfx1151` (RDNA3.5 / Strix Halo, also wave32) is added to the supported targets alongside `gfx1100` and `gfx1201`.
- `kvcacheio/transfer.cu`: block size on ROCm now uses the device wave size (`get_current_warp_size()`) instead of the host-side `WARP_SIZE`, which is always 64.
- Removed `docker/patches/sgl-kernel-gfx1151.sh` and its step in `docker/rocm-gfx1151.Dockerfile`. The patch lifted the arch gate and forced `WARP_SIZE=32` for gfx1151; both are now handled in-tree (allowlist + runtime wave-size dispatch).
- The MoE TopK fix also applies to `gfx1250`, which is wave32 and already a supported target.

Multi-arch (fat-binary) builds come from #44308. This PR's runtime wave-size dispatch works with it. Whichever merges second needs to add the RDNA targets to #44308's `supported_archs` list.

## Why runtime and compile-time selection are both needed

HIP builds one architecture-neutral host library and one device code object per `--offload-arch`. The host must inspect the executing GPU at runtime, while values used in `__launch_bounds__` and row-partition calculations must remain compile-time constants.

For example:

```text
gfx950  -> HIP selects gfx950 code object  -> warpSize=64 -> launch <64>
gfx1201 -> HIP selects gfx1201 code object -> warpSize=32 -> launch <32>
```

Using one `WARP_SIZE_PARAM` for both host geometry and device calculations keeps them consistent.

## Scope

This PR enables BF16/FP16 AOT operation and wave32 MoE routing on consumer RDNA. It does not enable native FP8 or DeepSeek-V4 FP8 support on gfx1100.

The existing `FP8_TYPE` compatibility block in `utils.h` is unchanged. Its type aliases describe FP8 representation for existing code; they are not a declaration that gfx1100 supports native FP8 computation. Native-FP8 kernels must continue to use their existing architecture capability gates or software fallbacks.
