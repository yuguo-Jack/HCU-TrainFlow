# [Fix] scheduler: don't crash with --max-queued-requests 0 and priority scheduling

[Upstream PR](https://github.com/sgl-project/sglang/pull/45827) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-priority-scheduling --max-queued-requests 0`, the server's own
warmup request crashes the scheduler instead of being rejected:

```
Scheduler hit an exception: Traceback (most recent call last):
  ...
  File ".../sglang/srt/managers/scheduler.py", line 2699, in _abort_on_queued_limit
    idx, candidate_req = max(enumerate(self.waiting_queue), key=key_fn)
ValueError: max() arg is an empty sequence
```

`_abort_on_queued_limit` reaches the priority-preemption branch because
`len(waiting_queue) + 1 <= max_queued_requests` is false for a zero limit,
but there is no waiting request to preempt, so `max()` over the empty queue
raises `ValueError` and terminates the scheduler process tree.

Fixes #45510.

## Modifications

- `python/sglang/srt/managers/scheduler.py` (`_abort_on_queued_limit`):
  only enter the priority-preemption branch when the waiting queue is
  non-empty (`if self.enable_priority_scheduling and self.waiting_queue:`).
  With an empty queue there is no candidate to preempt, so the incoming
  request is rejected with the standard 503 "The request queue is full.",
  matching the non-priority path. Also fixed a comment typo ("aboritng").
- `test/registered/unit/managers/test_scheduler_timeouts.py`: added
  `test_zero_limit_empty_queue_rejects_incoming_without_crash`
  (priority on/off x zero limit with empty queue: no exception, 503 with
  "The request queue is full.") and
  `test_zero_limit_nonempty_queue_still_preempts_lower_priority`
  (priority preemption still engages when a waiter exists under a zero limit).
