# [Fix] [NVIDIA] moe: Pick a supported runner for auto-detected ModelOpt NVFP4 MoE on SM110/SM120

[Upstream PR](https://github.com/sgl-project/sglang/pull/45520) · state: open · merged: False

## Original PR description

## Motivation

ModelOpt NVFP4 MoE checkpoints crash at warmup on SM120 with the default `--moe-runner-backend auto`. On one RTX PRO 6000 Blackwell (SM120), main `4eb606b2a` fails this way for `nvidia/Qwen3-30B-A3B-NVFP4` (NVFP4 experts) and for `nvidia/Qwen3.6-35B-A3B-NVFP4` (MIXED_PRECISION with W4A16_NVFP4 experts):

```
python -m sglang.launch_server --model-path nvidia/Qwen3.6-35B-A3B-NVFP4 --tp 1 --context-length 32768 --mem-fraction-static 0.85 --disable-radix-cache
...
AttributeError: 'FusedMoE' object has no attribute 'g1_scale_c'
```

The SM110/SM120 rule never sees the checkpoint's quantization. #41765 extended an existing SM120 rule to SM110; it resolves `auto` to `flashinfer_cutlass` for `modelopt_fp4`, but it compares `--quantization`, which stays unset when the quantization comes from the checkpoint, as in the usual launch. So `ModelOptNvFp4FusedMoEMethod.create_moe_runner` resolves `auto` to FLASHINFER_TRTLLM for every capability 10.0 and up, while the weight preparation follows the global backend (still `auto`) and never creates the TRT-LLM scales.

## Modifications

- On SM110/SM120, with `--moe-runner-backend auto` and `--quantization` not given, `_moe_runner_backend_quant_constraints` now uses the quantization `ModelConfig` resolved from the checkpoint.
- A `modelopt_mixed` checkpoint whose experts are `W4A16_NVFP4` gets `marlin`, which the Nemotron-H override and the SM100 Qwen3 MoE override already pick for W4A16 MoE layers under `auto`. `modelopt_fp4` keeps `flashinfer_cutlass`, and a `modelopt_mixed` checkpoint whose experts are `NVFP4` now gets it too. The log line names the backend and quantization it picked.
- `get_mixed_precision_moe_quant_algos` moves from `model_overrides/qwen3_moe.py` to `utils/common.py`, so the Qwen3 MoE override and this rule use the same function.
- `test_sm1xx_modelopt_nvfp4_moe_auto_avoids_trtllm_gen` in `test_model_overrides.py` covers mixed W4A16 experts, mixed NVFP4 experts and plain NVFP4, with the platform flag set to SM120 and to SM110.

An explicit `--quantization modelopt_mixed` is handled by the same branch, and an explicit `--quantization modelopt_fp4` keeps `flashinfer_cutlass`. The platform flag `is_sm120` matches every capability 12.x (with CUDA 12.8 or newer), so SM121 takes the same path. I have no SM110 device; the rule is shared with SM120 and the test runs both flags.

Known limits:
- Generic `--quantization modelopt` stays on `auto`, as on main. The FlashInfer Cutlass check in `handle_moe_kernel_config` accepts only the specific ModelOpt names, so resolving the generic flag needs that check changed too.
- Explicit method flags are taken as given: a mixed W4A16 checkpoint launched with `--quantization modelopt_fp4` keeps `flashinfer_cutlass`, as on main.
- A `modelopt_mixed` checkpoint that declares its expert algorithms only in `hf_quant_config.json` stays on `auto`; the shared helper reads `config.json`'s `quantization_config`, as the Qwen3 MoE and Nemotron-H overrides do.
- Plain `W4A16_NVFP4` checkpoints resolve to `modelopt_fp4` and get `flashinfer_cutlass`; I have no such MoE checkpoint to test.
- Neither checkpoint I ran has mixed NVFP4 experts, so that branch is covered by the unit test only.

Related PRs:
- #35617 adds `modelopt_mixed` to the same check. It helps only an explicit `--quantization modelopt_mixed` and sends W4A16 experts to `flashinfer_cutlass`.
- #39807 changes the fallback inside `create_moe_runner` to FLASHINFER_CUTLASS on SM12x and makes `enable_flashinfer_cutlass_moe` follow its resolved backend, but leaves the global backend at `auto`.

## Accuracy Tests

Both checkpoints now start on `auto`, and GSM8K is unchanged within noise against main with the same backend passed explicitly (one RTX PRO 6000 Blackwell Max-Q, TP1, sgl-eval 0.1.3):

| checkpoint | main, `auto` | this PR, `auto` | main, explicit backend | right on one side only (main, PR) |
| --- | --- | --- | --- | --- |
| nvidia/Qwen3.6-35B-A3B-NVFP4 | fails at warmup (crash command above) | marlin, 0.930 (186/200) | marlin, 0.935 (187/200) | 8, 7 |
| nvidia/Qwen3-30B-A3B-NVFP4 | fails at warmup (crash command above with this model) | flashinfer_cutlass, 0.955 (191/200) | flashinfer_cutlass, 0.945 (189/200) | 3, 5 |

The last column counts the questions only one side answered correctly. Server logs, per-run backend checks, sgl-eval outputs and the scripts are in https://gist.github.com/waynehacking8/a3fb1c44b09958b10998fe5b7c210e40.

```
python -m sglang.launch_server --model-path nvidia/Qwen3.6-35B-A3B-NVFP4 --tp 1 --disable-radix-cache --reasoning-parser qwen3 --mem-fraction-static 0.8 --moe-runner-backend {auto,marlin}
python -m sglang.launch_server --model-path nvidia/Qwen3-30B-A3B-NVFP4 --tp 1 --disable-radix-cache --reasoning-parser qwen3 --moe-runner-backend {auto,flashinfer_cutlass}
sgl-eval run gsm8k --base-url http://127.0.0.1:<port>/v1 --num-examples 200 --temperature 0.7 --top-p 0.8 --max-tokens 32768 --seed 0 --chat-template-kwarg enable_thinking=false
```

The MoE layers ran on the backend in the table: a probe recorded `ModelOptNvFp4FusedMoEMethod` with that backend at runner creation and in the forward for every run, and only this PR's `auto` runs log the rule's `Use ... as MoE runner backend on SM110/SM120` line.

Settings that differ from the cookbook (the Qwen3.6 RTX Spark recipe already pins `--moe-runner-backend flashinfer_cutlass`; these runs test the backend choice itself):
- Kept: the reasoning parser and `--mem-fraction-static 0.8`.
- Dropped: `--tool-call-parser qwen3_coder` and `--mamba-radix-cache-strategy extra_buffer`; the runs use `--disable-radix-cache`.
- Qwen3-30B: the Qwen3 page has no NVFP4 recipe.
- All runs set `SGLANG_FLASHINFER_AUTOTUNE_CACHE=0`, and the eval does not apply Qwen3.6's recommended `presence_penalty` 1.5.

The GPU runs used this library change as one commit on main `4eb606b2a`. The branch is rebased onto `956b9a24ee`; its `python/` changes have the same patch-id, and it adds the mixed NVFP4 test case. On that base, the unit tests pass (115 run, 1 skipped).

```
PYTHONPATH=python python -m unittest test/registered/unit/test_model_overrides.py
```

- With only the test file added to `956b9a24ee`, the new test fails with `AssertionError: 'auto' != 'marlin'`.
- With the platform reported as SM120 and `--quantization` unset, the two checkpoints resolve to `marlin` and `flashinfer_cutlass`, against `auto` on main. The explicit-flag cases in the known limits were checked the same way.

## Speed Tests and Profiling

No kernel changes: `auto` now resolves to backends that already exist. Decode TPOT at c=1, accuracy launch above:

| checkpoint, backend | main, explicit backend | this PR, `auto` | change |
| --- | --- | --- | --- |
| Qwen3.6, marlin | 3.23 ms | 3.33 ms | +3.1% |
| Qwen3-30B, flashinfer_cutlass | 4.63 ms | 4.78 ms | +3.1% |

TPOT on this PR's `auto` runs is 3.1% higher than main's explicit runs in both rows, one server boot per cell. The diff only changes server-arg resolution, which runs once at startup, and both arms resolve to the same server args apart from the random seed, so the MoE runner path is the same. For Qwen3.6 the gap is within what I saw between main boots: a separate main boot with the crash command's flags (table below) gave 3.33 ms. For Qwen3-30B it isn't: all five of this PR's prompts (4.777 to 4.787 ms) are slower than all ten from main's two flashinfer_cutlass boots, this table's and the crash-flags boot below (4.257 to 4.669 ms). This PR's boot came first in both pairs, so boot order is one candidate; I haven't found the cause. I can run three boots per arm in alternating order if a reviewer wants it settled.

Backend comparison on main `4eb606b2a` with the crash command's flags and the backend passed explicitly, one boot each:

| checkpoint | marlin | flashinfer_cutlass |
| --- | --- | --- |
| Qwen3.6 (W4A16 experts) | 3.33 ms | 3.93 ms |
| Qwen3-30B (NVFP4 experts) | 4.19 ms | 4.66 ms |

flashinfer_cutlass also runs Qwen3.6, which ships expert input scales, but marlin decodes faster, so `auto` picks marlin. For NVFP4 experts this PR keeps the SM120 rule's existing flashinfer_cutlass choice. Marlin also runs Qwen3-30B on main and decodes faster here; I left that choice alone because this PR is about the crash, and it may be worth a separate look.

TPOT is the median over 5 random 512-token prompts, measured through `/generate`. Each prompt's value is:

```
(latency at 257 tokens - latency at 1 token) / 256
```
