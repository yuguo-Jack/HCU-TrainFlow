# [HF3FS] Snapshot free pages under the metadata lock

[Upstream PR](https://github.com/sgl-project/sglang/pull/42081) · state: open · merged: False

## Original PR description

## Motivation

A periodic HF3FS metadata save copies the key-to-page mapping under the rank lock but retains a reference to the mutable free-page list. If an HTTP deletion releases a page before JSON serialization, the file can mark that page both free and assigned. After restart, allocating another key can give both keys the same page. A concurrent reservation can instead remove capacity from the saved snapshot without recording its new owner.

## Modifications

Copy the free-page list while holding the existing rank lock. Each saved rank then contains a consistent free-list/mapping snapshot without holding locks during file I/O. The persistence format and ordinary allocation behavior stay unchanged.

## Accuracy Tests

- Two deterministic regressions fail before the fix: an actual HTTP deletion during persistence creates conflicting page ownership after reload, and a concurrent reservation removes a free page from the captured snapshot. Both gate the real JSON serializer and join the saving thread before checking results.
- A roundtrip control preserves free pages, key order, and separate rank/pool namespaces.
- All 3 tests and all matching pre-commit hooks pass. The actual HTTP/delete/save/reload/allocation reproduction now restores distinct pages for the old and new keys.

CPU validation uses actual metadata classes, FastAPI TestClient, JSON files, reload, and allocation. The local harness excludes GPU/backend import initialization; no GPU or native HF3FS I/O is claimed. This change ensures internal metadata-snapshot consistency, not atomic persistence with ongoing storage-file writes.

Prepared and independently reviewed with AI assistance (Codex).

## Speed Tests and Profiling

No throughput claim. The change copies the free-page list once per metadata save while the existing rank lock is held.
