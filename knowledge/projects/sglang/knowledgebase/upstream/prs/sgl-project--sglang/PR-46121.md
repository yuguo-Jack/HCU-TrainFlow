# [Fix] disaggregation: Raise the transfer engine init deadline to 240s

[Upstream PR](https://github.com/sgl-project/sglang/pull/46121) · state: closed · merged: False

## Original PR description

## Motivation

`SGLANG_DISAGGREGATION_ENGINE_INIT_TIMEOUT` (#37874) bounds the transfer engine init call so a wedged RDMA stack fails startup with a clear error instead of sitting until the scheduler watchdog kills the process. Its default of 60 s is below the time a healthy NIXL prefill worker legitimately needs.

The prefill worker asks NIXL for 8 progress threads, and NIXL opens one UCX worker per thread plus one shared worker. Each worker builds receive memory pools for every RDMA transport (rc, dc, ud) on every device in `UCX_NET_DEVICES`, so the init time grows linearly with the thread count. Measured inside the CI runner container on `h200-gmi-wk03` (NIXL 1.3.0, `UCX_NET_DEVICES=mlx5_0:1,mlx5_6:1,lo`, box idle):

| num_threads | create_backend('UCX') |
| --- | --- |
| 0 (decode) | 3.7 s |
| 1 | 11.5 s |
| 4 | 31.8 s |
| 8 (prefill) | 49.5 s |
| 8, concurrent with a decode worker | 48.4 s |

Raw `ibv_reg_mr` of a 40 MB buffer takes 10 ms on the same host, so this is UCX pool setup per worker, not a stuck driver. A passing run of the same test on `h200-sci-71-12` shows the same shape: decode 6 s, prefill 29 s.

Under a real CI job the prefill side crosses 60 s and `test_disaggregation_decode_radix_cache_swa.py` fails in `setUpClass`:

```
RuntimeError: NIXL create_backend('UCX', {'num_threads': '8'}) did not return within 60s on radixark-wk03
RuntimeError: Server process exited with code -9
```

Example: https://github.com/sgl-project/sglang/actions/runs/39977798414/job/120497020607 (the three Mooncake tests in the same partition passed on the same runner).

## Modifications

- `SGLANG_DISAGGREGATION_ENGINE_INIT_TIMEOUT` default 60 s -> 240 s. That is about 4x the slowest measured host and still 60 s under the 300 s scheduler watchdog, so a real hang still reports here first with the host name.
- `run_with_deadline` logs how long the bounded call took on success, so the next slow host shows up in the server log instead of only as a timeout.

No behavior change for deployments that already set the env var. The unit test in `test_nixl_backend_basic.py` pins the value to 5 s and is unaffected.
