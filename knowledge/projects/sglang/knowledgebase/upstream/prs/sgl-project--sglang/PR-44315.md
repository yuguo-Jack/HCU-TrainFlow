# [Feat] rust-server: Attach configured metadata headers to a healthy /health_generate

[Upstream PR](https://github.com/sgl-project/sglang/pull/44315) · state: closed · merged: True

## Original PR description

## Motivation

The embedded Rust server's `/health_generate` is status-only: a healthy probe answers a bare 200. The Python server can attach extra response headers to it through its extension points, and the Rust frontend had no equivalent, so a subclass could not add any. This adds optional response headers to a healthy `/health_generate`, validated at startup, with an empty default.

## Modifications

- `ServerArgs` gains `health_generate_headers: BTreeMap<String, String>`, handed over from Python like every other field. `ServerArgs::validate` rejects an entry that is not a valid HTTP header name or value at startup, so a bad configuration fails at boot instead of being silently dropped per probe.
- A healthy (200) `/health_generate` carries the configured headers. `/health` keeps the same deep probe when `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION` is on but does not add them; 503 responses never carry them.
- `RustServer._health_generate_headers(scheduler)` is the Python-side hook, in the same style as `_load_extension` / `_resolve_multimodal`: it returns `{}` by default, and a model package subclass overrides it. `launch` passes its result to `_build_server_args`, which has a matching `health_generate_headers` keyword.

Default behavior is unchanged: with no override the map is empty and the responses are byte-identical to before.
