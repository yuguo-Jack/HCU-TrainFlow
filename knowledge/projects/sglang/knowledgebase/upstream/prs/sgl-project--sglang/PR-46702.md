# [Feat] linear-attn: Bole spec-verify for GDN (drop per-draft SSM snapshots)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46702) · state: open · merged: False

## Original PR description

## Motivation

Speculative target verify on GDN (gated delta rule) hybrid models snapshots the full
recurrent state after every draft step into `MambaPool.intermediate_ssm`, so that the
commit can copy back the state of the accepted step. The buffer is
`(max_running_requests + 1) x num_draft_tokens x state_size_per_layer x num_gdn_layers`
and is reserved for the whole lifetime of the server. For Qwen3.8-27B (48 GDN layers,
TP2) with DFLASH block 8 it is **3.66 GB per GPU at `--max-running-requests 12`**, taken
straight out of the KV pool, and it grows linearly with the concurrency cap.

ReplaySSM spec-verify (RFC #28511) removes this buffer for MTP-style verify, but with
DSPARK/DFLASH it currently requires a KDA model
(`--enable-linear-replayssm-spec with DSPARK/DFLASH requires a KDA model`), so GDN models
served with DFLASH (e.g. Qwen3.8-27B + DFlash2) still pay the full snapshot cost.

## Modifications

Bole keeps only the low-rank factors of each draft step and rebuilds the accepted state
on commit. Starting from the same state `S_0`, the state after `a` steps of the gated
delta rule is

$$S_a = p_a S_0 + \sum_{j \le a} \frac{p_a}{p_j} k_j u_j^\top$$

where `p` is the cumulative decay, `k_j` the L2-normalized key and `u_j` a correction
vector obtained from a `T x T` unit lower-triangular system. Verify stores `p`, `k`, `u`
(about `T x 128` values per head instead of `T x 128 x 128`), and the commit writes
`S_a` back into the request slot.

- `kernels/ops/attention/linear/bole_spec_verify.py` (new): three Triton kernels
  - `bole_factor_kernel`: per (request, head) cumulative log-decay, beta, normalized k,
    and the `T x T` k-k / q-k interaction matrices.
  - `bole_solve_kernel`: solves for `u`, writes the verify output (reads `S_0` from the slot).
  - `bole_commit_kernel`: rebuilds the accepted step's state in place for every layer.
  FP32 factors, TF32x3 dot products.
- `srt/layers/attention/linear/bole_spec.py` (new): `BoleSpecVerifier`, one factor
  workspace per CUDA-graph batch size, optional numerical audit (`SGLANG_BOLE_AUDIT=1`,
  eager only) against the recurrent kernel.
- `MambaPool`: with Bole on, the draft-step axis of `intermediate_ssm` is 0 (the tensor
  stays non-None for code that reads its layout); conv windows are unchanged.
- `KVCacheConfigurator._handle_max_mamba_cache`: does not reserve the SSM snapshot part,
  holds back `--linear-bole-workspace-mb` instead.
- `GDNAttnBackend.forward_extend`: Bole branch next to the ReplaySSM branches.
- `HybridLinearAttnBackend.update_mamba_state_after_mtp_verify`: rebuild via Bole, then
  the existing conv-window scatter and PLE side-state update; radix track slots
  (`extra_buffer`) are rebuilt from the request slot's prefix state before it is overwritten.
- New flags `--enable-linear-bole-spec`, `--linear-bole-workspace-mb` (default 384),
  appended to `POSITIONAL_FIELD_ORDER` and documented in `server_arguments.mdx`.
  Validation: linear draft chain only (`--speculative-eagle-topk` in {None, 1}),
  triton verify backend, fp32/bf16 SSM dtype, not with ReplaySSM spec-verify, not with PD
  disaggregation, GDN models only.

Off by default; with the flag off the code paths are unchanged.

Not supported yet (rejected at startup or asserted): EAGLE tree verify, PD
disaggregation, PP stable rows, unified memory pool, KDA models.

## Accuracy Tests

- Unit test `test/registered/attention/unittests/gdn/test_gdn_bole_spec_verify.py`:
  verify output and committed state vs. the recurrent kernel with per-draft snapshots,
  fp32 and bf16 state, with and without a radix track slot, padded rows and untouched
  slots unchanged. Relative-L2 bounds: output 2e-3, state 2e-4 (fp32) / 1e-2 (bf16).
- End to end, RadixArk/Qwen3.8-27B-NVFP4 + incoai/Qwen3.8-27B-DFlash2, TP2, greedy,
  thinking off, GSM8K test first 200 questions, concurrency 8:

  | | Off | Bole |
  | --- | --- | --- |
  | Accuracy | 92.5% | 93.0% |
  | Accept length | 6.19 | 6.17 |

  Outputs are not bit-identical (different floating-point order), the differences go
  both ways.
- Earlier validation of the same kernels on an internal Qwen3.8-27B-based model (1,110
  questions over HumanEval, MATH-500, GPQA-Diamond, AIME 2025, LooGLE) showed no
  significant accuracy difference vs. the snapshot path (80.7% vs 80.8%), with equal accept
  lengths; on code/math (HumanEval+, MATH-500, GSM8K, thinking off) accept length stays at
  6.1–7.4 with Bole, the same as without it.

## Speed Tests and Profiling

Same model and draft, 2x RTX 5090 (TP2), `--max-running-requests 12`,
`--max-mamba-cache-size 48`, fp8 KV, page 256, `--mem-fraction-static 0.85`.

Memory (per GPU):

| | Off | Bole |
| --- | --- | --- |
| SSM verify snapshots | 3.66 GB | 0 |
| KV pool (tokens) | 378,368 | 542,208 (+43.3%) |

Long-context multi-turn, `benchmark/hicache/bench_multiturn.py` (16 clients x 5 rounds,
40k-token first turn, +5k per later turn, 1k output, ShareGPT tokens, seed 42), HiCache L2
40 GB/GPU write-through, `--mamba-max-states-per-path 3`. Mean of 3 runs; Bole and Off ran
at the same time on two identical GPU pairs, swapped between runs.

| max-parallel | | output tok/s, mean (min–max) | vs Off | TTFT P50 / P90 (s) | TPOT (ms) | accept len | cache hit |
| --- | --- | --- | --- | --- | --- | --- | --- |

| 4 | Bole | 362.9 (351.6–369.3) | -1.6% | 0.90 / 4.02 | 8.8 | 3.66 | 76.8% |
| 8 | Off | 411.3 (402.9–420.0) | | 5.15 / 9.82 | 12.1 | 3.61 | 76.8% |

| 10 | Off | 410.4 (407.8–414.5) | | 9.40 / 16.83 | 12.2 | 3.61 | 76.8% |
| 10 | Bole | 450.2 (447.4–453.8) | **+9.7%** | **3.08** / 12.23 | 15.8 | 3.75 | 76.8% |
| 12 | Off | 421.0 (405.9–430.9) | | 11.97 / 22.16 | 11.9 | 3.80 | 76.8% |
| 12 | Bole | 436.0 (431.2–442.3) | +3.5% | 5.92 / 20.65 | 16.2 | 3.34 | 76.8% |

- Best level vs best level: Off 421.0 tok/s (max-parallel 12) vs Bole 450.2 tok/s
  (max-parallel 10), **+6.9%**. At max-parallel 8 and 10 every Bole run beats every Off run.
- With the larger KV pool more sessions run concurrently instead of queueing, so TTFT P50
  drops 5.5x at max-parallel 8 and 3x at max-parallel 10. TPOT is higher because the decode
  batch is larger (more requests in flight).
- At max-parallel 4 the KV pool is not the bottleneck and the two are within noise.

Cost: verify does two extra small `T x T` products and a rebuild per step; on short
prompts where KV is not the bottleneck Bole is a few percent slower (GSM8K c8: 1285.6 vs
1363.9 tok/s, -5.7%). The gain shows up when the KV pool is the bottleneck (long shared
prefixes, many long multi-turn sessions, higher concurrency caps).

```bash
python -m sglang.launch_server --model-path RadixArk/Qwen3.8-27B-NVFP4 --tp-size 2 \
  --speculative-algorithm DFLASH --speculative-draft-model-path incoai/Qwen3.8-27B-DFlash2 \
  --speculative-dflash-block-size 8 --speculative-num-draft-tokens 8 \
  --linear-attn-verify-backend triton --enable-linear-bole-spec \
  --max-running-requests 12 --max-mamba-cache-size 48 --kv-cache-dtype fp8_e4m3 --page-size 256
```
