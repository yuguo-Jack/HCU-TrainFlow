# [Perf] dsa: Route the k-pool indexer top-k through the top-k v2 kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/43775) · state: closed · merged: True

## Original PR description

## Motivation

The GLM-5.3-Flash k-pool indexer selects its top-k pooled groups with `kpool_topk_transform`, which runs one thread block per row. At decode time there is one row per request, so a single block scans the whole pooled history while the rest of the GPU idles. At 1M context this costs about 84 us per DSA layer per decode step, which is most of the decode slowdown from short to long context.

The top-k v2 kernel already splits long rows across thread-block clusters. This PR routes the k-pool indexer through it, with pool expansion, tail append and the output transform fused into the same kernel.

## Modifications

- **Fused k-pool mode in top-k v2** (`TopKMode::KPOOL`, `transform_kpool`): selection over pooled scores plus pool expansion, tail append and page-table or offset mapping in one launch, on every dispatch route (register, streaming, cluster, persistent cluster). The launch dispatch is shared with `transform_paged` through `launch<kMode>()`.
- **Ragged k-pool entry point** (`transform_kpool_ragged`): per-row windows (`row_starts`, `page_table_row_index`) for prefill and for any caller without a plan. Its select-then-transform body is shared with the ROCm `topk_packed_kernel` through `ragged_select_transform`.
- **Plans live in metadata**: decode and verify metadata build the top-k v2 plan once per forward, before the logits kernel, and refresh it on CUDA-graph replay. Rows without a matching plan take the ragged path.
- `topk_from_pooled_history_logits` dispatches to the planned path, then the ragged path, then the existing kernels. `SGLANG_OPT_USE_TOPK_V2=0` keeps the existing kernels.

## Accuracy Tests

- Kernel parity against the existing fused kernel: every output mode (no transform, page table, page table with row index, offsets), with and without tail columns, aligned and unaligned `row_starts`, short and zero-length rows. All selections match, up to exact score ties at the cut-off.
- CUDA-graph replay with the plan refreshed between replays, batch 1 to 300, covering every cluster dispatch route including the persistent cluster: 0 mismatches.

Could we handle threshold-bin overflow before enabling the cluster path for k-pool?

This launch newly routes long k-pool rows through `TopKCluster`, which [still truncates an overflowing threshold bin](https://github.com/sgl-project/sglang/blob/c31b9b1efe9c0ae7539b93d2cb7ce798bf95a63c/python/sglang/kernels/jit/include/sgl_kernel/deepseek_v4/topk_impl.cuh#L847-L850). It retains at most `kMaxNumTie = 2048` candidates in arrival order, then selects from that subset. If the bucket contains distinct FP32 scores, this can discard genuinely higher-scoring pools, rather than just reorder equal-score ties.

The [existing k-pool selector rescans overfull bins using exact keys](https://github.com/sgl-project/sglang/blob/c31b9b1efe9c0ae7539b93d2cb7ce798bf95a63c/python/sglang/kernels/jit/csrc/dsa/kpool_topk_transform.cuh#L130-L186), so enabling this dispatch introduces a selection-correctness regression for those inputs. Register/streaming v2 already have overflow refinement; cluster does not.

A targeted case is batch 1, 65536 pools, pool size 4, and 512 selected pools, with shuffled scores `1 + i * 2**-23`. All 65536 scores are distinct FP32 values but map to the same 10-bit coarse bucket. That exceeds the candidate buffer even though the requested top-k fits.

<details>
<summary>Minimal regression probe for a cluster-capable H100/B200/B300</summary>

```python
import torch
from sglang.kernels.ops.attention.dsv4.topk import (
    plan_topk_v2,
    topk_transform_kpool_v2,
)

torch.manual_seed(1234)
n, pool_size, group_k = 65536, 4, 512
lengths = torch.tensor([n], device="cuda", dtype=torch.int32)
plan = plan_topk_v2(lengths)
scores = (
    1.0 + torch.randperm(n, device="cuda").float() * 2.0**-23
).view(1, n)
out = torch.empty(
    (1, group_k * pool_size), device="cuda", dtype=torch.int32
)

topk_transform_kpool_v2(scores, lengths, out, pool_size, plan)
groups = out[:, ::pool_size].long() // pool_size
expected = scores.topk(group_k, dim=1).indices

torch.testing.assert_close(
    groups.sort(dim=1).values,
    expected.sort(dim=1).values,
    atol=0,
    rtol=0,
)
```

The device must have schedulable clusters; a single-block fallback would mask the issue. I verified the single-bucket input condition on CPU, but have **not run this probe on a GPU**, so I do not have a measured mismatch count.

</details>

The existing narrow-distribution v2 test [explicitly skips possible cluster shapes](https://github.com/sgl-project/sglang/blob/c31b9b1efe9c0ae7539b93d2cb7ce798bf95a63c/test/registered/kernels/ops/attention/test_topk_v2.py#L382-L397), and the k-pool overfull-bin test calls the legacy kernel directly. Could we add coverage through the new planned entry point, comparing it with the legacy/ragged paths, and either refine overflowing cluster bins or fall back to an exact path?
