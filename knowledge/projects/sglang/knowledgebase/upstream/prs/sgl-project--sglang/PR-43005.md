# fix(openai): preserve zero cached tokens when cache reporting is enabled

[Upstream PR](https://github.com/sgl-project/sglang/pull/43005) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-cache-report`, zero means reporting was enabled and no prompt tokens came from cache. The current OpenAI-compatible usage path filters that valid value into `prompt_tokens_details: null`, making it indistinguishable from disabled reporting:

```diff
-"prompt_tokens_details": null
+"prompt_tokens_details": {"cached_tokens": 0}
```

The [OpenAI Responses SDK model](https://github.com/openai/openai-python/blob/v2.21.0/src/openai/types/responses/response_usage.py#L8-L15) represents `cached_tokens` as an integer, and [SGLang's Responses serializer](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/protocol.py#L2138-L2152) already emits an explicit zero when no cache details are present. Preserving zero when cache reporting is enabled makes the existing Chat Completions and Completions usage behavior unambiguous and consistent with that Responses behavior.

This distinction matters for workload-level metrics such as AgentX: its [run-level cache-read percentage](https://github.com/SemiAnalysisAI/agentx-harness/blob/56a0cf70f4c0359454ee4bd15a17770b541a3e3e/src/aiperf/metrics/types/usage_total_metrics.py#L320-L362) includes cache observations across requests, its [trace accounting includes zero-hit first turns](https://github.com/SemiAnalysisAI/agentx-harness/blob/56a0cf70f4c0359454ee4bd15a17770b541a3e3e/tests/unit/dataset/loader/test_weka_trace.py#L978-L993), and it [distinguishes an explicit zero from missing cache reporting](https://github.com/SemiAnalysisAI/agentx-harness/blob/56a0cf70f4c0359454ee4bd15a17770b541a3e3e/src/aiperf/metrics/cache_reporting_hint.py#L35-L45). Filtering zero therefore turns a valid cold observation into missing telemetry.

Credit to @EazyReal for identifying the issue and implementing the original fix in #28801. This PR reapplies only the zero-value fix on current `main`; the separate legacy Completions continuous-usage change remains out of scope.

## Minimal Reproduction

Start a server with cache reporting enabled and the radix cache disabled. Disabling the cache makes the zero-hit case deterministic.

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 30000 \
  --enable-cache-report \
  --disable-radix-cache
```

Then issue one non-streaming Chat Completions request:

```bash
curl -s http://127.0.0.1:30000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [{"role": "user", "content": "Reply with OK."}],
    "temperature": 0,
    "max_tokens": 1
  }' | jq '.usage.prompt_tokens_details'
```

Before this fix:

```json
null
```

After this fix:

```json
{
  "cached_tokens": 0
}
```

The same presence rule applies to buffered and final streaming usage.

## Modifications

- Gate cache details on `enable_cache_report`, not on whether the count is positive.
- Apply the same rule to buffered, final-stream, and existing Chat continuous-usage paths.
- Add focused CPU coverage for zero, positive, and disabled-reporting cases.

This does not enable cache reporting on paths that do not already provide it, and it does not change cache accounting, scheduling, model execution, or model output.
