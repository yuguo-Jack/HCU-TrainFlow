# [Perf] glm5: Fuse KDA output norm during target verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/43659) · state: closed · merged: False

## Original PR description

## Motivation

GLM-5.3-Flash runs a separate gated RMSNorm after each KDA layer. The `nv_cutedsl` verify kernel can apply it, as for Kimi K3.

## Modifications

On target verify, the model passes the `o_norm` weight, epsilon and gate to the backend, and skips the separate norm when the kernel takes them.

The backend trims MoE padding from the gate, as for qkv, a and b. Kimi K3 shares this line.

`o_norm.weight` becomes FP32 on every path, with bitwise equal separate-norm output on B200. Only verify on `nv_cutedsl` uses the fused norm.

Deliberate limits:

- An attention exception leaves the handoff set, because the server stops on it.
- CPU tests do not pin `o_norm` to FP32, because the kernel rejects BF16.

These limits are deliberate. Do not add code for them without a real input that reaches the case.

## Accuracy Tests

Server runs used 4 B200s with GLM-5.3-Flash FP8 weights. Base is main `a2029238de`. PR is `a80677798c` merged with it.

The `test_glm53_flash_b200` recipe (TP4, EAGLE 5/1/6, FP8 KV, trtllm DSA, flashinfer_trtllm MoE) ran on three server instances per arm:

```text
# sgl-eval 0.1.3
sgl-eval run gsm8k --num-examples 200 --temperature 1.0 --top-p 0.95 --max-tokens 32768 --thinking
```

PR scored 100%, 98.5% and 98.0%. Base scored 97.5%, 98.0% and 98.0%.

On the PR, the padded TP4/EP4 command from #43271 starts and serves at concurrency 1, 3, 7 and 19. Accuracy was not measured. The padded regression subcase protects against this warmup failure without the trim:

```text
RuntimeError: shape '[1, 6, 16, 128]' is invalid for input of size 16384
```

Kimi K3 weights, B300 and DFlash2 were not run.

## Speed Tests and Profiling

No server-level speed gain is measurable at TP4 on B200 on this head.

`bench_serving` ran the same recipe with random prompts, temperature 0 and 7 sweeps per arm.

| Concurrency (4096 input, 256 output tokens) | PR median tok/s (range) | Base median tok/s (range) |
| ---: | ---: | ---: |
| 1 | 565.9 (556.7 to 583.3) | 567.0 (527.1 to 577.0) |
| 16 | 1897 (1171 to 1921) | 1642 (1209 to 1916) |

At concurrency 16 the ranges are wide and overlap, so the medians show no gain.

Per-layer kernel measurement only: graph replay at H=16 saved 2.3 to 4.1 us per layer per verify.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Refresh the cached norm copy when weights are reloaded**

When a BF16/FP16 GLM model is updated through the supported online weight-loading APIs after startup, this tensor remains the FP32 copy made on the first forward: `Glm5NextForConditionalGeneration.load_weights` updates `o_norm.weight` in place but neither refreshes/invalidates `_fused_onorm_args` nor declares it as an unsupported derived-weight cache. The nv_cutedsl target-verify path therefore keeps normalizing with the old weight while prefill and fallback paths use the new one, producing silently inconsistent logits; even recapturing graphs does not help because the `getattr` guard reuses the stale tuple.
