# [Perf] glm5: Fuse KDA output norm during target verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/43659) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.3-Flash runs a separate sigmoid-gated RMSNorm after each KDA layer. Apply it inside the `nv_cutedsl` target-verify kernel, which already supports the Kimi K3 norm handoff.

## Modifications

Keep `o_norm` in FP32 and pass its current weight and epsilon to verify. Clear the per-call handoff after attention, including on errors, and apply the existing norm if the backend does not consume it.

Decode and extend keep their existing routing. The shared adapter retains Kimi K3 compatibility, and verify reads the model parameter directly so weight updates need no copied-buffer refresh.

## Accuracy Tests

Before the base update, targeted CI passed on `44b2975d`: [GLM-5.3-Flash on B200](https://github.com/sgl-project/sglang/actions/runs/38719395318), [GLM-5.3-Flash on H200](https://github.com/sgl-project/sglang/actions/runs/38719411271), [Kimi K3 on B300](https://github.com/sgl-project/sglang/actions/runs/38719426628), and the [CPU model unit suite](https://github.com/sgl-project/sglang/actions/runs/38719428189). The serving runs cover registered accuracy and speculative-decoding checks. B200 and B300 logs confirm `nv_cutedsl` verification.

After the base update, the CPU model unit suite and scoped formatting pass. The linked GPU results predate this update. Run model unit suites with `python -m pytest` and GPU suites through the registered CI runner.

## Speed Tests and Profiling

Earlier v0.5.20 backport measurements used GLM-5.3-Flash FP8 on TP8 B200, EAGLE 4/1/5 with rejection sampling, cached 60K-token prompts and 1,536 output tokens:

| Verify backend | 1 request | 4 requests | 16 requests |
| --- | --- | --- | --- |
| Triton | 7.201 ms | 9.434 ms | 13.700 ms |
| CuTe | 7.245 ms | 9.431 ms | 13.518 ms |
| CuTe with fusion | 7.160, 7.157 ms | 9.292, 9.269 ms | 13.376, 13.426 ms |

Fusion saved about 0.085 ms per verify step with one request. These measurements predate the current handoff simplification and have not been repeated on this PR commit.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Refresh the cached norm copy when weights are reloaded**

When a BF16/FP16 GLM model is updated through the supported online weight-loading APIs after startup, this tensor remains the FP32 copy made on the first forward: `Glm5NextForConditionalGeneration.load_weights` updates `o_norm.weight` in place but neither refreshes/invalidates `_fused_onorm_args` nor declares it as an unsupported derived-weight cache. The nv_cutedsl target-verify path therefore keeps normalizing with the old weight while prefill and fallback paths use the new one, producing silently inconsistent logits; even recapturing graphs does not help because the `getattr` guard reuses the stale tuple.
