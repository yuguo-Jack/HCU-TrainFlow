# [GLM-5.3-Flash] Fold the KDA output norm into the nv_cutedsl verify kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/43659) · state: open · merged: False

## Original PR description

## Motivation

With `--linear-attn-verify-backend nv_cutedsl`, the target-verify kernel of the KDA layers (`fused_kda_decode_mtp_dspark`) owns all 128 value channels of a head, so it can apply the sigmoid-gated RMSNorm of the KDA output inside the recurrence. Kimi K3 hands the kernel its output-norm gate. GLM-5.3-Flash uses the same `FusedRMSNormGated(activation="sigmoid")` output norm, but it still runs `o_norm` as a separate kernel after every linear-attention layer: 34 extra launches per verify step on GLM-5.3-Flash.

## Modifications

- `glm5_next.py` (`Glm5NextLinearAttention.forward`): in target verify, offer the output-norm gate, the fp32 norm weight and eps through the same attempt-and-verify handoff that Kimi K3 uses (`_k3_onorm_gate`, `_k3_fused_decode_args[5:7]`, `_k3_onorm_consumed`). The handoff is set only around the verify call and cleared after it, so decode and extend are unchanged. If the backend does not consume the gate (another verify backend, or a shape the CuTe kernel does not cover), the model applies `o_norm` as before.
- The fp32 copy of the norm weight is built on the first forward, which is eager, so no allocation happens inside a CUDA graph capture.

## Accuracy Tests

The fused norm in the kernel is covered by `test_kda_decode_mtp.py::test_output_norm`. End to end, on GLM-5.3-Flash (an FP8 fine-tune), TP8 on B200, v0.5.20 with this change and the gate reshape of #40607 backported:

| Verify path | Decode vs prefill log prob of the same tokens, mean abs diff (p99) | Greedy tokens equal to the prefill argmax |
| --- | --- | --- |
| triton | 0.0214 (0.31) | 98.2% |
| nv_cutedsl with this change | 0.0195 (0.28) | 98.7% |

The check greedy-generates 768 tokens after each of 8 real prompts (8 requests in flight, so decode runs batched through verify and state commits), then scores prompt plus output with one prefill. A wrong decode state would make the decode-time log probs drift from the prefill ones.

Prompt log probs of 8,922 sampled tokens (prefill only, so this only checks that nothing else changed): mean NLL 0.2351 with this change; 0.2355 to 0.2369 in five other runs of the same server with other decode-only changes.

## Speed Tests and Profiling

Same setup, MTP with EAGLE 4/1/5 and rejection sampling, 16 prompts of 60K cached tokens, 1,536 output tokens. Time per verify step (ms) with 1, 4 and 16 requests in flight:

| Verify path | 1 | 4 | 16 |
| --- | --- | --- | --- |
| triton | 7.201 | 9.434 | 13.700 |
| nv_cutedsl | 7.245 | 9.431 | 13.518 |
| nv_cutedsl with this change (two runs) | 7.160, 7.157 | 9.292, 9.269 | 13.376, 13.426 |

The change removes 0.085 ms per step with one request, the time of the 34 `o_norm` kernels. Against the triton verify path it is 1.006x, 1.015x and 1.024x.
