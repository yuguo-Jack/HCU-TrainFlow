# [Fix][Qwen-VL] Don't count literal <image> text as an image placeholder

[Upstream PR](https://github.com/sgl-project/sglang/pull/43369) · state: open · merged: False

## Original PR description

## Motivation

#39278 added `|<image>` to Qwen-VL's `image_token_regex`. Chat-template prompts already carry the image as `<|vision_start|><|image_pad|><|vision_end|>`, so a literal `<image>` in the question text (common in MMMU, e.g. `"This Roman portrait mummy <image> ..."`) is counted as a **second** image slot for **one** image. `legacy_load_mm_data` then hits an unhandled `StopIteration` and the request fails with HTTP 500 (`An exception occurred while loading multimodal data`), which breaks every such MMMU request.

Repro (any Qwen-VL server): a chat request with one `image_url` and text `"What is shown in <image>?"` returns 500.

## Modifications

`python/sglang/srt/multimodal/processors/qwen_vl.py`:

1. Revert `image_token_regex` to match only the native placeholder, as before #39278.
2. In `_normalize_prompt_for_fast_path`, rewrite `<image>` to the native placeholder only when the prompt has no `<|vision_start|>`. This keeps the raw `/generate` behavior #39278 added without breaking chat-template prompts.

```diff
             image_token_regex=re.compile(
-                r"<\|vision_start\|>(?:<\|image_pad\|>)+<\|vision_end\|>|<image>"
+                r"<\|vision_start\|>(?:<\|image_pad\|>)+<\|vision_end\|>"
             ),
@@ def _normalize_prompt_for_fast_path(self, input_text, expected_image_count: int)
         native = self.mm_tokens.image_token
+        # sglang's <image> sentinel marks an image only in raw prompts;
+        # next to native vision tokens it is literal text (e.g. MMMU questions).
+        if "<|vision_start|>" not in input_text:
+            input_text = input_text.replace("<image>", native)
         normalized, count = self.mm_tokens.image_token_regex.subn(native, input_text)
```

## Tests

New CPU unit test `test/registered/unit/multimodal/test_qwen_vl_image_sentinel.py` (registered in `base-a-test-cpu`), using a real `QwenVLImageProcessor`:

- Chat prompt with literal `<image>` plus one native placeholder and 1 image: resolves to 1 image with the prompt unchanged. On `main` this raises `RuntimeError`.
- Raw `<image>` prompt with 1 image: stays on the artifact fast path and is rewritten to the native placeholder, as in #39278. A plain revert of the regex fails this test.

Both pass locally. The existing `test_qwen3_vl_feature_materialization.py`, `test_media_artifact_processor.py` and `test_processor_async_call_sites.py` also pass. Hot-path cost is one substring check. No end-to-end MMMU run is attached yet.

- bornmw · comment · 2026-10-11T01:45:08Z · [source](https://github.com/sgl-project/sglang/pull/43369#issuecomment-6104313939)

Reproduced on v0.5.21 (latest release, 2026-09-29) + transformers 5.12.1, Qwen3.8-VL, CUDA — in a real-world agentic scenario, which is a bit nastier than the single-request MMMU case:

Our multi-turn session history contained literal `&lt;image&gt;` in assistant text (script usage lines: `find-cursor.sh &lt;image&gt; &lt;cropw&gt; ...` and `find_cursor.py &lt;image&gt; [roi ...]`). The first request after those messages hit the unhandled `StopIteration` in `legacy_load_mm_data` and 500ed with `An exception occurred while loading multimodal data` — and **every subsequent turn failed too**, because the full history (including the literal tokens) is re-sent each turn. So a single model output containing `&lt;image&gt;` (common in code: usage strings, placeholder examples) permanently breaks a growing conversation.

Count mismatch exactly as described: 23 `image_url` parts + 3 literal `&lt;image&gt;` occurrences = 26 placeholder tokens vs 23 data items → `Mismatch: More 'IMAGE' tokens found than corresponding data provided` → `StopIteration`.

Worked around it by rewriting the literal strings in history (one-off, storage-level). The server-side fix in this PR is the durable fix — happy to help test it on a Qwen3-VL NVFP4 server.

- bornmw · comment · 2026-10-11T03:40:34Z · [source](https://github.com/sgl-project/sglang/pull/43369#issuecomment-6105106176)

Follow-up datapoint correction: in our repro the literal in the text was `<image_path>` (the legacy Qwen placeholder, as in script usage lines like `find_cursor.py <image_path> [roi ...]`), not `<image>`.

Verified against the v0.5.21 code:

1. `QwenVLImageProcessor.image_token` is the expanded native token (vision-start + one image-pad + vision-end, single pad), so the exact-match branch in `get_modality_of_token` never fires for a literal.
2. `image_token_regex` is `vision-start(?:image-pad)+vision-end | <image>` — and `re` cannot match the `<image>` alternative inside the string `<image_path>` (the closing bracket is absent there; the prefix is `<image_`). So the regex branch never fires either.

Nevertheless, literal `<image_path>` in chat history breaks Qwen3-VL requests on v0.5.21 + transformers 5.12.1: 23 `image_url` parts + 3 literal `<image_path>` occurrences in assistant text produced `Mismatch: More 'IMAGE' tokens found than corresponding data provided` followed by an unhandled `StopIteration` in `legacy_load_mm_data` (HTTP 500). Rewriting the literals to a non-token string fixed it — so the counting is real, it just does not go through the branches above.

Suspected source: the model's own tokenizer maps the legacy `<image_path>` surface form to the image-pad token id during chat-template rendering, inflating the placeholder count before sglang's string-level checks ever see it. The fix here covers the `<image>` sentinel; the `<image_path>` surface form looks like a sibling case worth handling in the same place. Happy to provide the full request/traceback pair on request.
