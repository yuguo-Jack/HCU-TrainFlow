# [Perf] [AMD] kimi-k3: Run the merged MoE front through AITER tuned BF16 GEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/44360) · state: open · merged: False

## Original PR description

## Motivation

- Kimi-K3 decode on MI355X is latency-bound at small batches. Every MoE layer starts with the merged front GEMM (`shared gate-up | router | latent down`, N=6016, K=7168 at TP8).
- That GEMM goes through `F.linear`, so hipBLASLt picks the kernel. For this shape at 1-192 tokens its choice is slow; AITER's tuned BF16 table (ROCm/aiter#6411) has faster FlyDSL kernels.
- Goal: run the front through AITER's tuned GEMM where rows exist, as an opt-in switch, without touching other shapes or targets.

## Modifications

- `kimi_k3_rocm_moe.py`: `build_tuned_front_gemm` decides once, at weight-merge time, whether the tuned GEMM applies. Forward then checks only the token count.
- `KimiK3MoE._forward_fused` calls `tgemm.mm` for batches inside the window and keeps `_k3_bf16_gemm` otherwise.
- At load, the AITER row is checked for every batch size in the window (once per process), so a partial AITER cannot silently run untuned kernels.

| Env var | Default | Effect |
|---|---|---|
| `SGLANG_OPT_HIP_K3_TUNED_MOE_FRONT` | `false` | Run the merged MoE front on AITER's tuned BF16 GEMM (needs `SGLANG_USE_AITER=1`) |
| `SGLANG_OPT_HIP_K3_TUNED_MOE_FRONT_MIN_TOKENS` | `1` | Smallest batch (tokens) that takes the tuned GEMM |
| `SGLANG_OPT_HIP_K3_TUNED_MOE_FRONT_MAX_TOKENS` | `192` | Largest batch (tokens) that takes the tuned GEMM; AITER's last tuned row for this shape |

| Condition | Result |
|---|---|
| Switch on, BF16 TP8 front (6016, 7168), gfx950 with 256 CUs, batch in window | AITER tuned GEMM |
| Batch outside the window | Default GEMM |
| Other TP size, dtype, arch, or CU count | Warning, default GEMM |
| `--enable-deterministic-inference` | Warning, default GEMM (AITER picks kernel and split-K by batch size) |
| AITER lacks `tgemm` or a tuned row for any batch in the window | Load fails with an error naming ROCm/aiter#6411 |
| `MIN_TOKENS > MAX_TOKENS` or `MIN_TOKENS < 1` | Load fails |

|---|---|
| GSM8K, 1,319 questions, switch on, 3 runs | 97.19%, 97.42%, 97.12%; no truncation |
| GEMM max relative error vs FP32 | default 1.8e-3 to 3.6e-3; tuned 2.1e-3 to 6.8e-3 |

- All runs are within sampling noise (single-run stderr ~0.45 pp at temperature 1.0).
- Setup: 8x MI355X, `Kimi-K3-Quark-MXFP4-AttnFP8`, AgentX c16 recipe (TP8/DCP8, HiCache, DSpark block 4, decode graphs bs 1-32), simulated acceptance off; only the switch differs. Build: `k3-agentx-pr-stack` @ `39d944c57d`, ROCm/aiter stack @ `f9b5308b2`.
- One earlier OFF run hung after 1215 answers (97.53% so far): every rank waited in `FutureMap.resolve_seq_lens_cpu` on an event that never fired, with the GPUs idle. The retry above did not hang, and no ON run hung, so the hang is on the default (switch off) path and not in this PR.
- Unit tests: `test/registered/unit/models/test_kimi_k3_rocm_quant.py` (CPU, fake AITER) and `test/registered/unit/models/test_kimi_k3_rocm_moe_gfx950.py` (real AITER on MI355X): 13 passed.

## Speed Tests and Profiling

- Setup: 8x MI355X, TP8, `Kimi-K3-Quark-MXFP4-AttnFP8`, integration build that includes other open K3 PRs.
- Workload: 8,192 input / 1,024 output tokens, radix cache off, 3 alternating runs per configuration.

| Concurrency | TPOT off (ms) | TPOT on (ms) | Change |
|---:|---:|---:|---:|
| 1 | 13.43 | 12.86 | -4.2% |
| 4 | 15.83 | 15.25 | -3.7% |
| 8 | 18.55 | 18.00 | -3.0% |
| 16 | 23.43 | 23.54 | +0.5% |
| 32 | 31.78 | 31.51 | -0.8% |
| 64 | 47.12 | 45.92 | -2.5% |

- TPOT drops 2.5-4.2% at concurrency 1-8 and 64. Concurrency 16 is 0.5% slower in every run; concurrency 32 is within noise. TTFT is unchanged.
- GEMM microbenchmarks: 6-49% lower latency on the sampled tuned batches. M=160 had no tuned row in the AITER used for the microbenchmark and showed no gain. Some of the larger gains come from poor default kernel choices.
