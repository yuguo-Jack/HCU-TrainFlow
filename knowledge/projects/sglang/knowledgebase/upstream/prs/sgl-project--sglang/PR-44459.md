# [Perf] [AMD] mla: Fuse RoPE, concat and KV-cache write for MLA decode on gfx1250

[Upstream PR](https://github.com/sgl-project/sglang/pull/44459) · state: open · merged: False

## Original PR description

## Motivation

On gfx950, aiter MLA decode runs RoPE, the q/k concat and the KV-cache write in one `fused_qk_rope_cat_and_cache_mla` kernel. On gfx1250 these are still separate: native RoPE, two `torch.cat` and `set_kv_buffer`, more than a dozen elementwise kernels per layer. This PR extends the gfx950 fused branch to gfx1250.

## Modifications

With `SGLANG_USE_AITER=1` on gfx1250, MLA decode with the aiter or triton backend skips the standalone RoPE and takes the fused branch, as aiter MLA does on gfx950. gfx950 is unchanged.

- As on gfx950, the gate is evaluated per call: decode, the aiter or triton backend, no DSA, one DCP rank, a rope module of exactly `RotaryEmbedding` or `DeepseekScalingRotaryEmbedding`, and a bf16 or FP8 KV pool. The pool check reads the pool's dtype, so an fp16 pool, which the kernel rejects, stays on the unfused path.
- sglang's rope keeps cos and sin in one `cos_sin_cache`; the kernel gets the two halves as strided views.
- Q keeps `q_nope_out`'s dtype, which is bf16 on gfx1250: MLA decode there takes an unquantized Q even over an FP8 KV cache.
- Prepare's rope-skip condition moves into `_applies_rope_in_prepare`, so the unit test can check that prepare skips RoPE exactly when core fuses it.
- CPU unit tests are added to `test/registered/unit/models/test_rocm_mla_absorb_fusion_gate.py`.

Requires ROCm/aiter#5501, which both ROCm Docker pins in `docker/rocm.Dockerfile` already contain. On main, gfx1250 MLA decode runs the triton backend, which the gate covers, and the first set of numbers below is main with the triton decode backend. With #44458's aiter decode backend the same fused branch applies; the second table measures that.

Validated on gfx1250 with Kimi-K2-Thinking-MXFP4 at TP8, with the triton decode backend on main and the aiter decode backend from #44458.

## Accuracy Tests

The fused kernel matches the unfused path (q and the written KV rows) for bf16 and FP8 KV, batch 1 to 128.

GSM8K, 8-shot, 1319 questions, triton decode backend on main:

| | KV cache | Runs | Accuracy |
|---|---|---|---|
| Before | FP8 | 4 | 0.942 (0.950, 0.939, 0.939, 0.939) |
| After | FP8 | 4 | 0.940 (0.942, 0.938, 0.934, 0.945) |
| Before | bf16 | 1 | 0.947 |
| After | bf16 | 1 | 0.938 |

Unchanged main moves by 0.011 between server launches (0.950 and 0.939), so the single bf16 run is within that spread.
