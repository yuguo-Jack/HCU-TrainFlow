# [Perf] dsv4: Restore sparse prefill for request-window rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/45573) · state: closed · merged: True

## Original PR description

- `_use_sparse_prefill` no longer rejects a batch whose KV pool has a request window, so encoder SWA bounded replay rows above the sparse threshold take sparse prefill again instead of the paged decode kernel. #42273 admitted them; #38603 brought the old clause back while reworking the call-site condition, and #37958 moved it into `_use_sparse_prefill`. The decoder tail (`late_layer_tail`) still stays dense.
- The chunk cache already builds from the request-window layout (`_build_sparse_prefill_chunk_cache`), and a request-window batch still publishes no prefill read-done (`_snapshot_prefill_shared_reads` returns `UNKNOWN`), so the cache is built in the first layer behind the whole-forward barrier.
- DeepSeek V4.1 Flash on GB300, DEP4, encoder replay on, 131,072-token context with 4,096 new tokens per request, one run per arm: 79,375 -> 86,987 tok/s/GPU at 32K tokens per rank (+9.6%; attention kernels 83.2 -> 46.7 ms per step) and +5.3% at 64K. GSM8K (sgl-eval, 200 examples, with `SGLANG_OPT_FLASHMLA_SPARSE_PREFILL=1` so smaller extends take the sparse path too): 98.99% over the 198 answered before an unrelated crash, vs 98.50% on main.

Changes behavior only when encoder SWA bounded replay is on.
