# [Doc] [NPU] cookbook: add A3 deployment scenarios to GLM-5.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/45655) · state: open · merged: False

## Original PR description

## Motivation

Refs Ascend/sglang#1209.

The GLM-5.1 cookbook has no Ascend NPU option, although the [Ascend NPU GLM-5.1 best practice](https://docs.sglang.io/docs/hardware-platforms/ascend-npus/model-deployment/best-practices/glm_5_1) documents measured multi-node recipes. This PR adds the two scenarios the task asks for, so you can pick a deployment on **Atlas 800I A3** and get the command for it:

- **PD Mixed on 2 × A3** (32 dies, one server across two nodes)
- **1P1D PD disaggregation on 4 × A3** (64 dies, each role is a two-node server)

## Modifications

### Page layout

The GPU generator on this page is still the legacy `glm-51-deployment.jsx`. Instead of extending that component, the Ascend section renders the shared `Deployment` engine with an A3-only config (`configs/zai-org/glm-5.1-ascend.jsx`), the same approach as #38800 (Qwen3-Next). The GPU widget and its commands are untouched.

This keeps the diff to data plus one MDX section. The A3 config uses the same format as a config-driven page, so if this page is ever moved onto the shared template, the three cells drop straight into its config and the second widget goes away.

### Recipes

| Deployment | Source (Ascend best practice) | Key flags |
|---|---|---|
| PD Mixed | `W4A8 16P IN3K5 OUT1K5 50ms` | `--tp-size 32 --dp-size 16`, DeepEP auto, NEXTN 3-1-4 |
| PD Disagg · Prefill | `W4A8 1P1D 32P IN16K OUT1K 50ms` | `--tp-size 32`, interleave prefill CP across all 32 ranks, DeepEP normal, graph capture off |
| PD Disagg · Decode | same | `--tp-size 32 --dp-size 32 --ep-size 32`, DeepEP low_latency, NEXTN 3-1-4 |

- Every cell sets `nnodes: 2`, so the engine injects `--nnodes 2 --node-rank --dist-init-addr`. The selector id is `pdMode`, so the engine gives the roles their own serving ports (prefill 30000, decode 30100). The router command is in the page text.
- Checkpoint: `Eco-Tech/GLM-5.1-w4a8` (msModelSlim W4A8, 420 GB; `--quantization modelslim`). Its `quant_model_description.json` stores the MTP layer (layer 78) as FLOAT, so the recipes pass `--speculative-draft-model-quantization unquant`.
- `dockerImages.a3` is `quay.io/ascend/sglang:v0.5.22-cann9.1.0-a3`. v0.5.22 (2026-10-13) is the first release carrying both features these recipes need — NPU prefill CP (#39427) and `--attn-dp-size` (#41818) — and all three generated commands resolve against that release's `server_args` as well as against `main`. The rolling `main-cann9.1.0-a3` tag the Ascend docs use works too, but it moves.

### Differences from the best-practice scripts

The recipes are transcribed as written, including the prefill role's context parallelism (`--enable-prefill-cp --cp-strategy zigzag --attn-cp-size 8`), which NPU supports again after #39427. The remaining changes are spelling updates that current `main` requires:

- Recipes follow the 2026-10-15 revision of the best practice (#44432, the CANN 9.1.0 update), and `dockerImages.a3` pins that page's CANN 9.1.0 line to the `v0.5.22` release image.
- `--dp-size N --enable-dp-attention` → `--attn-dp-size N` (deprecated in #41818), `--disable-cuda-graph` → `--cuda-graph-backend-{decode,prefill} disabled`, `--moe-dense-tp` → `--moe-dense-tp-size`.
- `SGLANG_ENABLE_SPEC_V2` is dropped (removed on `main`, only logs a warning) and so is `SGLANG_SPEC_ENABLE_OVERLAP_REFLOW` (nothing reads it). `--served-model-name glm-5` is dropped so the cURL example's model name matches.
- The best practice's 64k and 128k 1P1D entries drive prefill CP through `--enable-nsa-prefill-context-parallel` / `--nsa-prefill-cp-mode`, which #38293 removed; this PR ships the 16k entry, whose `--enable-prefill-cp --cp-strategy zigzag` form is the supported one. (The NPU CI cases under `test/registered/npu/*/glm5_1/` still carry the removed flags and the pre-#39427 skip reason, so they stay disabled — worth a follow-up by the NPU CI owners.)

All three cells are marked `verificationStatus: "in-progress"`, like the Kimi-K3 A3 cell in #35508.

### Notes against the cookbook review checklist

- **Parsers are baked into the cells.** The checklist keeps `--reasoning-parser` / `--tool-call-parser` in the Playground, but this page has no Playground (the GPU half is still the legacy generator), so a parser left out of the cell is a parser the reader never gets. The merged Kimi-K3 A3 cells do the same, and the legacy GPU generator on this page emits both parsers by default. Both ids are registered on `main` (`glm45`, `glm47`).
- **No `playgroundFeatures` and `showPlaygroundLink: false`**, same as #38800: this widget only renders the deployment matrix.
- **`matchDims` instead of the legacy five dimensions** (`quant` x `pdMode`, with `nnodes` on the cell), following `kimi-k3.jsx`. Each PD role needs `--nnodes 2`, which a `nodes` dimension cannot express.
- **The router listens on 30000**, the port the cookbook convention asks for. The engine assigns the roles 30000 (prefill) and 30100 (decode), so the page notes that the router needs a node other than the prefill head, or a free port there.

## Accuracy Tests

**Not measured in this PR.** The recipes are transcribed from the Ascend GLM-5.1 best practice, which publishes its own measurements; this PR does not re-run them. A3 full nodes (2 x and 4 x, 16 dies each) were not available to me — the HiDevLab allocation I can claim is a single 8-card 910B4 node (32 GiB/die, 256 GB total), and the W4A8 checkpoint alone is 391 GB.

All three cells therefore ship as `verificationStatus: "in-progress"`, the same state the merged Kimi-K3 A3 cell (#35508) has, and the page says so in its Verification status note. Once someone runs them on A3, the numbers go into a `glm-5.1-ascend-benchmarks.jsx` and the cells flip to verified. I have a runbook with the exact commands the page emits, pass criteria and the logs to collect, and I'm happy to hand it over or fill in the results.

## Speed Tests and Profiling

**Not measured in this PR**, same reason. The best-practice entries each table row links to carry the published TPOT target of 50 ms for both workloads (3.5k+1.5k and 16k+1k), which is what a verification run should compare against.
