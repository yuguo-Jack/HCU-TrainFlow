# Fix EVS for NemotronH_Omni_Reasoning_V3

[Upstream PR](https://github.com/sgl-project/sglang/pull/42933) · state: closed · merged: True

## Original PR description

## Motivation

EVS on `NemotronH_Omni_Reasoning_V3` breaks outside the single-video case:

- Image + video in one request crashes the scheduler (`AssertionError` in EVS redistribution).
- Multiple videos with `video_temporal_patch_size=2`: tubelets span video boundaries (shape mismatch with EVS, wrong embeddings without).
- A 1-2 frame video crashes the scheduler (`AttributeError: 'EVSEmbeddingResult' object has no attribute 'reshape'`): it takes the per-image path, which expects a tensor.

## Modifications

- Processor: videos sent with dynamic-res images now get EVS metadata; video items carry `frames_per_video`.
- Model: encode temporal tubelets per video; always store padded ids in `pre_chunked_input_ids` so EVS redistribution keeps image pad values.
- EVS: return unpruned features when every video is a single frame/tubelet (nothing to prune).
- Match the HF tubelet label format (`Frame N ... and frame M`).
- Unit tests for each fix; each fails on the old code.

## Accuracy Tests

TP4 H100, `video_pruning_rate` 0.7 and 0.0: single video, odd-frame video, image + video, two videos, and a video crossing the chunked-prefill boundary all run and give correct answers. Before this PR, image + video crashed the server.

TP2 B200, `video_pruning_rate` 0.7: a 1-frame video crashed the server before the single-frame fix and now answers correctly; single video, two videos, and image + video still pass.

[by Claude Code] **Severity: functional | Confidence: Medium**

**Issue**

`get_video_feature` still concatenates the pixels of all items (line 283) before it splits them per video. On CUDA, `_batch_encode_per_image_misses` sends the one-tubelet videos of every request in a prefill batch to one call. With `video_target_num_patches > 0`, `video_to_pixel_values` keeps each video's aspect ratio, so frame sizes can differ and `torch.cat` crashes the scheduler.

**Example**

Request A sends a 1-frame 16:9 video and request B sends a 1-frame 4:3 video in the same batch. On CPU, this call fails with a `torch.cat` size error at `video_pruning_rate` 0.0 and 0.7.

**Fix**

Split each item's own feature, and flatten each output because callers already reshape to `[tokens, hidden]`:

```python
return torch.cat([
    self.extract_video_feature_temporal(video, video.shape[0]).flatten(0, 1)
    for item in items
    for video in item.feature.split(item.frames_per_video)
])
```
