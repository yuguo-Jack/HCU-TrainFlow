# [Perf] sdar: Prototype KV refresh and next-block denoising pairing

[Upstream PR](https://github.com/sgl-project/sglang/pull/44652) · state: open · merged: False

## Original PR description

## Motivation

SDAR predicts a completed block from masked or partially committed inputs. Its cached KV therefore describes the inputs, not the newly selected tokens. A separate refresh rebuilds that KV before the next block can use it.

This draft tests whether the refresh and the next block's first denoising pass can share linear-layer execution. It preserves both blocks' arithmetic and the attention dependency. Larger linear operations may reduce repeated weight reads and launch overhead at low batch sizes.

**Status: experimental model-execution prototype. This PR does not enable a production serving feature or claim a measured speedup.**

## Modifications

- Add `FlashInferBlockPairBackend` for dense SDAR, LowConfidence decoding, BF16 model/KV, full attention, page size one, and TP=PP=1.
- Pack `[completed block A, masked block B]` for shared linear operations. Within each layer, refresh A with stock FlashInfer attention, then process B using A's refreshed KV.
- Preserve request row order, block-causal attention, and cache write locations during graph replay.
- Add CPU tests and a portable benchmark with separate stock forwards, paired forwards, and a Qwen AR control.
- Add optional CPU/CUDA profiling after clean timing trials. Save traces, operator summaries, and separate prefill/generation/refresh measurements.

There are no FlashInfer library changes. The backend is intentionally not registered as a server option. Scheduler integration depends on correctness and performance evidence.

## Accuracy Tests

Passed locally against main `e5274752a8960796178c4054efc789edca713f32`, with CUDA hidden:

- Four backend tests: heterogeneous prefixes, request ordering, cache dependency, block masks, and invalid layouts.
- Three decoding-driver tests: native selection, exact output IDs, progress counts, terminal refresh, and CPU-only execution.
- Six existing FDFO KV-reuse tests.

The A100 benchmark checks checkpoint logits, retained KV, selected tokens, and graph/eager equivalence before timing. A timing pair is admitted only when full output token IDs match. Those GPU checks are pending. Threshold zero is a cost diagnostic, not a quality result.

## Speed Tests and Profiling

Prepared comparison: SDAR B16/B32 and Qwen3-8B; BF16; fixed batches 1, 4, and 16; 128 input tokens and 256 output tokens. SDAR thresholds are 0, 0.5, and 0.95. Five trials alternate separate and paired execution. Both arms use model CUDA Graphs and include planning, selection, and terminal refresh.

The first A100 experiment uses pinned SGLang `e00930c5489053f26d86b179cee0d087f846acbb` and FlashInfer 0.6.18. The backend logic is identical to this draft. Current-main GPU qualification remains a separate requirement. The experiment waits for an existing serial allocation; no candidate GPU results are claimed here.

For `G` output blocks at threshold zero, generation calls change from `2G` to `G+1`. Each paired call processes two blocks. B16 with 256 output tokens changes 32 calls to 17; B32 changes 16 to 9. These are call counts, not speedups. At high thresholds, repeated denoising remains unchanged.

The benchmark excludes HTTP, admission, and production scheduler costs. Qwen produces one token during prefill and takes 255 later decode steps; SDAR produces all 256 tokens during generation. Report these scopes explicitly.

See `benchmark/dllm/refresh_denoise_pair.md` for commands and limitations.
