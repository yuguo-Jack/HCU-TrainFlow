## Original PR description

# [AMD] Qwen3-Next: route GDN decode at AITER's fused gfx950 kernel

> **Requires AITER ≥ `dd6b8907`** — [ROCm/aiter#5520](https://github.com/ROCm/aiter/pull/5520)
> (*[Triton/Gluon] Fused Qwen3-Next GDN decode op for gfx950*) **merged
> 2026-10-06** and added `fused_gdn_decode_qkvz` /
> `fused_gdn_decode_qkvz_supported` to `aiter.ops.triton.gated_delta_net`.
> This PR only consumes them.
>
> With the env var unset (the default) this PR does not import AITER at all.

## Motivation

Qwen3-Next's Gated DeltaNet decode step runs four kernels per layer, per step,
across 36 GDN layers:

```
fused_qkvzba_split_reshape_cat  ->  causal_conv1d_update
  ->  fused_recurrent_gated_delta_rule_packed_decode  ->  gated RMSNorm
```

AITER ships a single Gluon kernel that does all four and consumes the packed
`qkvz`/`ba` projections directly. This wires Qwen3-Next to it.

**+4.7% to +8.6% output throughput** on 4x MI355X / TP4, no accuracy
regression. Off by default; opt in with
`SGLANG_QWEN3_NEXT_GDN_FUSED_BACKEND=aiter`.

Note the fused proj+Conv1D path that already exists in the GDN backend
(`fused_qkvzba_causal_conv1d_update_contiguous`) is **Qwen3.5-only** —
`_gdn_decode_fused_proj_conv` appears in `qwen3_5.py` and nowhere else — so
Qwen3-Next still runs the full unfused chain today.

## Modifications

The fusion spans SGLang's model/backend boundary, which is why this is not a
one-line dispatch change. `Qwen3GatedDeltaNet.forward` owns the qkvz split
(stage 1) and the gated RMSNorm (stage 5); `GDNAttnBackend.forward_decode` owns
the conv and recurrence (stages 2-4) and the state pools. Neither side holds all
the inputs: the backend receives post-split `mixed_qkv` and never sees `z` or
the norm weight, while the model never touches the mamba pools.

This follows the **attempt-and-verify stash** that Kimi-K3 already uses for its
fused KDA decode (`kimi_k3.py` / `kda_backend.py`): the model offers the
output-norm weight on the attention layer, the backend consumes it only if a
covered kernel engages, and the model applies its own norm when the stash comes
back unconsumed. Purely additive — no signature changes, and it fails safe.

New:
* `kernels/ops/attention/gdn_fused_decode_aiter.py` — fail-closed adapter:
  `enabled()` (env), `available()` (platform, AITER import, Triton Gluon),
  `covered()` (per-call contract) and `run()`. `covered()` delegates the tensor
  contract to AITER's own `fused_gdn_decode_qkvz_supported()` so the two cannot
  drift, and adds the one thing AITER cannot see — the model's output-gate
  activation, which the kernel hard-codes to SiLU.

* `test/srt/test_gdn_fused_decode_aiter.py` — the opt-in, the capability probe
  and every decline path. The decline cases need neither a GPU nor AITER, which
  is the point: they are exactly what CI can check on any runner.

Modified:
* `srt/layers/attention/linear/gdn_backend.py` — `_try_aiter_fused_gdn_decode()`
  inside the existing `isinstance(mixed_qkv, tuple)` branch. Returns post-norm
  output and sets the consumed flag, or `None` to fall through to today's chain.
  Logs once on engage and once on reject-with-reason.
* `srt/models/qwen3_next.py` — the decode-only stash and fast path,
  `_gdn_fused_decode_ready` (static gate: platform, opt-in, head ratio, head
  dims, conv width), and `_prepare_gdn_fused_decode()` called from
  `load_weights` to publish the bf16 norm weight before graph capture. A zero
  conv bias is pre-allocated at init for models without one, so nothing is
  allocated inside a captured decode graph.

The backend's tuple input `(projected_qkvz, projected_ba)` already exists for
Qwen3.5's fused path; Qwen3-Next simply had not opted in. No new mechanism.

## Scope

**The CUDA path is unaffected.** The fused path requires `is_hip()` and gfx950,
and with the env var unset the probe returns `False` before AITER is imported,
leaving the existing chain byte-identical. Every gate degrades to the current
behaviour:

| gate | on failure |
|---|---|
| env var unset (default) | stock chain |
| not HIP / not gfx950 | stock chain |
| AITER or Triton Gluon unavailable | stock chain, logged once |
| Triton < 3.8 (see below) | stock chain, logged once with the reason |
| shape/dtype not covered | stock chain, logged once with the reason |
| output-gate activation is not SiLU | stock chain |

Following `_can_fuse_accept_state`'s framing in `kda_backend.py`: this is a
capability, not a mode — falling short of the contract falls back rather than
raising.

SGLang authors no Gluon; this only *consumes* AITER's, and Gluon availability is
probed rather than pinned, as `aiter_mla_gluon.py` does.

### A note on Triton 3.7 images

Some ROCm builds ship Triton **3.7** carrying a backported Gluon that *imports
cleanly* but miscompiles the layout ops this kernel uses. AITER therefore gates
on `triton >= 3.8` rather than on an import probe. On such an image this feature
declines and falls back — correct, but inert. Concretely, of the 2026-10-12
nightlies, `rocm724` ships Triton 3.7.0 and `rocm10` ships 3.8.0.

Standard error at n=1319, p~0.94 is 0.0065, so this is "no detected

### Raised graph cap

AITER's op carries a second decomposition above batch 128, which only fires when
`--cuda-graph-max-bs-decode` exceeds its default of 64. Same two arms at a cap
of 256:

| conc | baseline tok/s | this PR tok/s | delta | baseline TPOT | this PR TPOT |
|---|---|---|---|---|---|
| 128 | 21701.42 | 22863.24 | **+5.4%** | 11.05 ms | 10.44 ms |
| 256 | 31343.49 | 32821.80 | **+4.7%** | 14.98 ms | 14.25 ms |

The gain narrows at the top of the range, as expected — the decode kernel is a
smaller share of step time once the batch is large enough to be bandwidth-bound.

At this cap SGLang captures **36** decode graph sizes and the op covers all of
them; selection inside AITER is a range check, not a shape table.

### Methodology notes

Both arms were run with an idle-GPU assertion (no server processes, <3% VRAM)
before each arm, not just between them. An earlier ladder produced a spurious
-80% baseline result from contention with a stale server; it reproduced within
that session, which is precisely why the guard now runs per arm.

Absolute throughput here is **not comparable** to the figures previously quoted
in this PR: those came from a ROCm 7.0 image with Triton 3.8 installed manually,
these from ROCm 10 with native 3.8 — a different compiler and a different
absolute scale. The arm-vs-arm deltas are the like-for-like comparison, and they
are unchanged across that move and a ~1700-commit jump in main.

## Known gaps

* **The FP8 epilogue is not wired up.** The AITER op can emit per-head group-128
  FP8 activations that a block-FP8 `out_proj` consumes directly, removing a
  further `dynamic_per_group_scaled_quant` launch per GDN layer. This PR calls
  it with `quant_dtype=None`. Measured against an out-of-tree reference
  implementation that does use it, that leaves roughly **2 percentage points**
  of throughput on the table. It is deferred because no linear-attention backend
  currently returns an `(fp8, scales)` tuple into a `Linear`, and it deserves its
  own gate and its own review.

```bash
docker run --rm -it --device /dev/kfd --device /dev/dri --network host \
  --group-add video --ipc host --shm-size 32g \
  -v $HF_HOME:/hf lmsysorg/sglang-rocm:v0.5.21-rocm10-mi35x-20261012

# The image's AITER predates #5520; install one that contains it.
pip install -U "git+https://github.com/ROCm/aiter.git@main"   # >= dd6b8907

export SGLANG_USE_AITER=1
export SGLANG_QWEN3_NEXT_GDN_FUSED_BACKEND=aiter   # omit for the baseline arm

python3 -m sglang.launch_server \
  --model-path Qwen/Qwen3-Next-80B-A3B-Instruct-FP8 \
  --tensor-parallel-size 4 --ep-size 1 \
  --dtype bfloat16 --quantization fp8 --kv-cache-dtype fp8_e4m3 \
  --attention-backend aiter --moe-runner-backend aiter \
  --enable-aiter-allreduce-fusion \
  --disable-radix-cache --disable-shared-experts-fusion \
  --mem-fraction-static 0.80 \
  --context-length 8192 --chunked-prefill-size 16384 \
  --cuda-graph-max-bs-decode 64 \
  --port 8888 --trust-remote-code
```
