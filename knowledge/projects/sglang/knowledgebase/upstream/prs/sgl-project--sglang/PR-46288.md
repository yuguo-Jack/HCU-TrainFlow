# [Fix] RL: Read output store parts straight into caller memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/46288) · state: closed · merged: True

## Original PR description

## Summary

Read output store parts straight into caller memory instead of Mooncake's local buffer.

## Symptom & Reproduction

- **Symptom:** Miles GLM-5 4-layer indexer replay at 256 samples per rollout (`--use-output-store`, Mooncake over TCP, 16gb local buffer) failed its first train step with `output store part not found: .../indexer_topk`, right after Mooncake logged `Failed to allocate buffer for key`. The objects were stored.
- **Reproduction, buffer:** on a live Mooncake 0.3.13.post1 master, `read_many` of 7 `indexer_topk` fields of 129 MiB through a 1000 MiB local buffer raised `KeyError`.
- **Reproduction, lease:** two readers, each reading 128 fields of 122-134 MiB with a 16 GiB budget, lost 119-121 parts each to `LEASE_EXPIRED`.

## Root Cause

1. `MooncakeBackend.get_many` reads with `batch_get_buffer` into the client's local buffer.
2. `OutputStore.read_many` sizes chunks by stored bytes against `buffer_bytes`.
3. Mooncake's `OffsetAllocator` rounds each part up a size class: 130 MiB takes 144 MiB.
4. A full chunk outgrows the buffer; parts without room come back `None`.
5. `get_many` reports every `None` as a missing part.
6. One `batch_get_buffer` per chunk outlasts the 10 s read lease over TCP.

## Fix

`MooncakeBackend.get_many` allocates one array for the requested parts, registers it with `register_buffer`, reads each part with `get_into` from 4 threads, and unregisters it. Nothing is rounded, chunked or copied, each call stays far inside the lease, and `get_into` tells a missing part (-704) from a failed read, so the backend raises `KeyError`, `ValueError` (size differs from the ref) or `RuntimeError` without another call.

`OutputStore` keeps one read path: `read_many` drops `buffer_bytes`, and the view-returning `get_many` goes, since its views were the reason for the buffer. Puts still use the local buffer, so a client that only reads can set `local_buffer_size` to 0. Miles' reader moves with it in radixark/miles#4267.

Four threads matched one `batch_get_into` over RDMA; more only shared the bandwidth. A single part whose transfer alone outlasts the lease (15 GiB over TCP) still fails.

## Verification

- `radix_transfer_plugins/tests`: 34 passed (fake Mooncake); read tests new or rewritten.
- Live Mooncake 0.3.13.post1, one host, two concurrent readers of 128 fields of 122-134 MiB:
  - `read_many` per reader: RDMA 12.6 GiB/s (before 3.2), TCP 1.42 GiB/s (before 0.94); client setup 0.59 s (before 1.41) without the 16 GiB buffer.
  - A never-written part raises `KeyError`; a ref 4 KiB off either way raises `ValueError`.
- Miles GLM-5 4-layer, 256 samples, 5 rollouts each way, with the radixark/miles#4267 reader: both runs trained; the read stage per rollout took a median 24 s (before 39 s, range 27-94); train/rollout log-prob diff 0.0446-0.0553 (before 0.0445-0.0560).

## Review Focus

- `MooncakeBackend._read_into`: the registration covers the whole array and is undone in `finally`; `_raise_failed_reads` maps the results to exceptions.
- `_READ_THREADS = 4`: measured on one host over RDMA and TCP; cross-host TCP is not measured.
