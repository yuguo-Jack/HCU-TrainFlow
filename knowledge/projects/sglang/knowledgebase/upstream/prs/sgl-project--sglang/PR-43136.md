# [Perf] dcp: Slice gathered MHA prefixes with host offsets

## AITER prerequisites

None. The prefix offsets are computed on the host in SGLang. This change does not call an AITER kernel.

## Motivation

With DCP, MHA prefill over a cached prefix all-gathers the prefix KV and then interleaves it with the new tokens' KV, one request at a time. `all_gather_kv_cache_for_mha_extend` computed the slice bounds with `torch.cumsum` on the GPU. Slicing a tensor at a GPU-scalar bound forces a blocking device-to-host copy, so each prefill step paid 4 syncs per request per MLA layer. The same lengths are already on the host in `forward_batch.extend_prefix_lens_cpu` and `forward_batch.extend_seq_lens_cpu`.

## Modifications

- `all_gather_kv_cache_for_mha_extend` (`layers/dcp/comm.py`) computes the per-request offsets on the host with `itertools.accumulate` over `extend_prefix_lens_cpu` and `extend_seq_lens_cpu`.
- The device cumsum path is removed. Every `ForwardBatch` path that sets `extend_prefix_lens_cpu` also sets `extend_seq_lens_cpu` and pads both to the batch size, and the caller already depends on `extend_prefix_lens_cpu`.
- The unused `seq_lens`, `extend_prefix_lens`, and `extend_seq_lens` arguments are dropped. The two callers, `forward_mha.py` (CUDA) and `forward_mha_rocm.py`, now pass `extend_seq_lens_cpu`.

Outputs do not change: the offsets have the same values, now computed on the host. I checked the old and new interleaving on CPU against 500 random batches, including extend KV with trailing padded rows, and they match exactly.

## Speed Tests and Profiling

Mean TTFT is 3.5% lower and median TTFT is 4.6% lower. TPOT and the prefix cache hit rate do not change.

<details>
<summary>Setup</summary>

- Hardware: MI355X x8.
- Model: Kimi-K3, Quark MXFP4 MoE with FP8 attention.
- Server: the cookbook's MI355X configuration. TP8, `--dcp-size 8 --dcp-comm-backend a2a`, AITER prefill and decode attention, FP8 KV cache, radix cache on, `--chunked-prefill-size 8192`.
- Workload: `python -m sglang.benchmark.serving --dataset-name generated-shared-prefix`, with 32 groups x 8 prompts, a 16384-token shared prefix, a 1024-token question, 256 output tokens, and concurrency 16. The cache was warmed with a different seed and flushed before the measured run.
- Both sides set `SGLANG_AITER_FP8_PREFILL_ATTN=0`. On `main`, the FP8 prefill kernel `_mla_fp8_prefill_attn_ps` tries to allocate about 1.2 TiB for a cached prefix under DCP8 and runs out of memory. That bug is unrelated to this PR.
- The numbers were measured on the previous revision of this PR. That revision used the same host-offset slicing and still had the device fallback, which this run never reached.
