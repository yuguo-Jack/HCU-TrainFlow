# [diffusion] Serve the LLaDA-Image Turbo FP8 checkpoint on one GPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/43654) · state: open · merged: False

## Original PR description

## Motivation

inclusionAI publishes a pre-quantized FP8 checkpoint of LLaDA-Image Turbo, `inclusionAI/LLaDA-Image-Turbo-FP8`. sglang refuses it at startup today. With this PR it serves on one GPU from its own quantization metadata, with lower latency and about 18.6 GiB less device memory than BF16 Turbo at matching quality.

It follows the BF16 LLaDA-Image support of #37907.

## Modifications

- The DiT loads its FP8 weights through the native FP8 linear method from the checkpoint's `quantization_config`. Only serialized FP8 weights in 128x128 blocks with dynamic activation scales are accepted, and any other declared quantization fails at startup with the declared config named.
- The FP8 DiT stays resident on the GPU when the automatic memory policy would offload it. An explicit transformer offload fails at startup with the flags named.
- The text encoder's `llada_fp8_experts` metadata maps to a standard FP8 config that quantizes only the routed experts. Attention, shared experts, and the dense MLPs keep their BF16 weights.
- The LLaDA2 loader expands the fused per-expert block scales into `weight_scale_inv`. Every other tensor keeps its name, and none of the 96 public LLaDA2 repositories checked carries the fused scale names, so they load as before.
- The FP8 Base checkpoint `inclusionAI/LLaDA-Image-FP8` stays refused at startup, with a message that points to BF16 Base (see Accuracy Tests).
- The `--quantization` refusal now points to the Turbo FP8 checkpoint.

## Reproduction

```bash
sglang serve --model-path inclusionAI/LLaDA-Image-Turbo-FP8 --revision 664a975e4b4980fb750fd47b2f87e1874bb14bd7 --trust-remote-code --port 30000
```

Requests are the same as for BF16 Turbo in #37907, with `"num_inference_steps":4` and `"guidance_scale":1.0`.

## Accuracy Tests

Turbo FP8 against Turbo BF16 at 1024x1024 with the same prompts, seeds, settings, and evaluators. GenEval uses 553 prompts with seeds 42 to 45. LongText-Bench uses 160 English and 160 Chinese prompts with seeds 42 to 45. CVTG-2K uses 2000 prompts with seed 42 and reports OCR word accuracy. Turbo uses 4 steps with CFG 1.

| Benchmark | Turbo BF16 | Turbo FP8 |
| --- | ---: | ---: |
| GenEval | 0.8250 | 0.8175 |
| LongText English | 0.8974 | 0.8983 |
| LongText Chinese | 0.9228 | 0.9160 |
| CVTG-2K word accuracy | 0.8236 | 0.8225 |

The FP8 Base checkpoint scores 0.7493 CVTG-2K word accuracy against 0.7805 for BF16 Base. Its FP8 DiT weights, dequantized to BF16 and run through the BF16 path, still score 0.7547, so the loss comes from the published weights and not from the FP8 kernels. Base therefore keeps its BF16 checkpoint.

New unit tests cover which text encoder layers stay BF16, the fused scale names in the LLaDA2 loader, and the Turbo-only FP8 startup check. On GPU, BF16 Base and Turbo produce byte-identical images to the base branch on the same requests.

## Speed Tests and Profiling

Median client wall latency on one H200 at 1024x1024, one request at a time. Each cell pools 40 measured requests from four fresh server processes, each running two warmups and then ten measured requests. The BF16 and FP8 servers alternated in one run on the same GPU.

| Task | Turbo BF16 | Turbo FP8 |
| --- | ---: | ---: |
| T2I | 0.5791s | 0.4900s |
| Edit | 1.4271s | 1.1925s |
| Peak device memory | 51,793 MiB | 32,751 MiB |

## Known Limitations

- An FP8 server compiles its DeepGEMM kernels at startup. It takes about 13 minutes to become ready with empty kernel caches and about 10 to 11 minutes with filled caches, against 1 to 2 minutes for BF16 on the same GPU.
- The FP8 Base checkpoint is refused at startup, as described above.
- FP8 weights must stay on the GPU, so an explicit transformer offload is refused.
- Sequence parallelism is not served by this PR and is refused at startup.
