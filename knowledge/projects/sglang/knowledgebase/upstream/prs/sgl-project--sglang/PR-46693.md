# [Feat] [AMD] minimax: Support MiniMax-M3.1-Flash on MI350X / MI355X (gfx950)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46693) · state: open · merged: False

## Original PR description

> Part of the MiniMax-M3.1-Flash AMD series that replaces #45936 (closed with its base branch `minimax-m3.1-flash`): kernel PRs #46690 (attention), #46691 (MoE / GEMM) and #46692 (quick all-reduce), now merged; #47862 (one shared folder of in-tree AITER tuned rows); this PR with the M3.1 call sites, stacked on #47862; then #46694 (indexer CP). Until #47862 merges, this diff includes its six files (`utils/aiter_tuned_tables.py`, `model_runner.py`, `environ.py`'s switch comment, DeepSeek-V4's module and CSV, `test_aiter_intree_tune.py`). It follows the DeepSeek-V4.1 AMD layout (#41018-#41021, then #41308).

## Motivation

Run MiniMax-M3.1-Flash on AMD Instinct MI350X / MI355X (gfx950) with DSpark speculative decoding, at TP 4 per server. AMD's Quark MXFP4 export of the model shares the target-model paths; the DSpark draft's Triton verify optimizations and the tuned `lm_head` key on the NVFP4 checkpoint.

## Modifications

- **Model override** (`model_overrides/minimax_m3_hip.py`): gfx950 defaults for the NVFP4 checkpoint and the Quark export.
  - Attention runs on the Triton backend, and the DSpark draft on Triton.
  - The MoE runner is AITER, with page size 128.
  - The KV format defaults to NVFP4 under DSpark.
  - The quick all-reduce level is set here too.
  - Guards: M3.1 NVFP4 on ROCm requires gfx950 (elsewhere the override would pick CUDA-only backends) and refuses TP above 4 (TP8 with attention DP produced runaway whitespace in GSM8K answers), and attention TP above the KV head count, which returned garbage on ROCm.
- **Weights**
  - Routed experts are requantized from NVFP4 to MXFP4 at load and run on AITER's FlyDSL fused MoE, with tables tuned for the M3.1 TP4 shapes.
  - The MXFP8 attention, dense and shared-expert projections are converted to FP8 at load and run on AITER GEMMs with tuned block-scale and rowwise tables. Up to 128 tokens they use a per-channel copy; above that, block scaling.
- **KV cache and attention**
  - Under DSpark, the cache is the packed NVFP4 KV and indexer-K pool (MSA-v1 layout, as on Blackwell); the QK-norm / RoPE kernel quantizes and stores it.
  - Sparse decode runs on a gfx950 Gluon kernel. Prefill runs on a Gluon kernel from 2048 tokens and on AITER's Gluon paged attention below that. Indexer scoring is Triton.
  - `SGLANG_MINIMAX_M3_AMD_KV_FORMAT=fp8` selects an FP8 cache instead, which is the default for the Quark export.
  - HiCache copies of the packed pages run on HIP.
- **Fusions**
  - QK-norm, RoPE and the KV-cache write run as one kernel.
  - RMSNorm and SwiGLU write the FP8 input of the next GEMM directly, and the sparse attention hands the `o_proj` its FP8 input.
  - The shared-expert output folds into the MoE reduction.
  - Up to 16 rows a step (decode, or DSpark verify of up to two requests at 7 drafts), sgl-amd-mono's M3.1 FFN monokernel (`--enable-amd-monokernel`, not in this PR) runs everything after attention as one launch per layer.
- **All-reduce:** AITER custom all-reduce handles messages up to 2.4 MiB. Above that, at TP 4, a JIT-built quick all-reduce takes over: bitwise equal to sgl-kernel's at the level it runs. With `ROCM_QUICK_REDUCE_QUANTIZATION` unset the model sets INT4 (`SGLANG_ENABLE_MINIMAX_M3_AMD_QUICK_REDUCE_INT4=0` leaves it unset); a level already set, including the ROCm images' INT8, stays. An INT4 request runs INT8 below `SGLANG_ROCM_QUICK_REDUCE_INT8_BELOW_MB` (64). Other GPUs, world sizes, levels and dtypes fall back to sgl-kernel.
- **DSpark**
  - Draft attention runs on the Triton backend; its grouped-head verify serves the draft's sliding window, reads the draft K/V through their strides and packs only the window's KV indices, and its KV store skips the defensive clone.
- **AITER integration:** `aiter_moe_addend` (from #46691) folds the shared-expert output into AITER's stage-2 reduction, applied only if AITER's function signature matches and otherwise left unpatched with a log line.
  - M3.1's tuned rows are four CSVs in #47862's folder, `utils/aiter_tuned_configs/<table>/minimax_m31_tp4*.csv` (block-scale and rowwise fp8 GEMMs, bf16 GEMMs including `lm_head` and the DSpark `fc`, and the MXFP4 fused MoE). #47862's installer applies them; this PR adds no table code.

- ROCm code lives in `_hip` modules or behind `is_hip` / gfx950 checks, so CUDA paths are unchanged.
- The kernels these callers use are on `main` (#46690, #46691, #46692).

## Removed in this revision
Each change below was turned off alone in the on/off table further down; the fast configuration (TP4 NVFP4 with DSpark and the FFN monokernel) no longer runs it.
- **Fused decode routers** (`m31_router`, `m31_shared_router`, the presorted-sort handoff, router GEMV's public split-K partials and the SwiGLU fused into their launch, `moe_fused_gate`'s partials input, and the small-M fp8 GEMM's M3.1 shared-expert shape). The routers served only 1-16 rows, which the monokernel now takes; above that they measured within noise (+1.5% / -0.1% / +0.8% at 8 / 32 / 64 requests).
- **The deferred host seq-lens pull** (`overlap_utils_hip.py`, `dspark_hip.py`, and their hooks in `FutureMap`'s publish, the scheduler's overlap step and the DSpark worker's decode). It queued the gfx950 DSpark draft before the host waited for the previous step's sequence lengths: +8.2% TPOT at 1 request, +2.8% at 8 and 32 (borderline against the noise), none at 64. That was too much change to the shared overlap path for the gain; the overlap path is main's again. Not re-measured on the current stack, where the monokernel's shorter 1-2 request steps may make the loss at 1 request larger.
- **The asm split-K GEMM launched into the norm's zeroed output** (`aiter_asm_blockscale`, the norm's zero fill, hipcc's 2-D grid). It measured within noise end to end; ROCm/aiter#6786 adds `out_zeroed` to AITER's own launcher.
- **Tests**: those of the removed code, plus three model-override cases that restated assignments or a three-line check, and a JIT-cutoff test folded into one table.
- Not re-measured after the removal: serving throughput with the monokernel on against the stack that had the fused routers. The c1 FFN step measured 8.05 -> 7.56 ms with the monokernel when it was added (sgl-project/sgl-amd-mono#56).

## Speed Tests and Profiling

Four MI350X GPUs, TP 4, NVFP4 KV, **DSpark acceptance simulated at 3 tokens per step** (`SGLANG_SIMULATE_ACC_LEN=3`, `match-expected`, `real-draft-token`). Real-acceptance throughput was not measured for this PR.

Decode throughput is output tokens/s per server, median over 2 crossed rounds × 2 GPU sets with 3 repeats each. Every column uses 150K-token distinct contexts, except 64 requests, which uses 64K.

| Concurrent requests | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Output tok/s | 376 | 640 | 1,016 | 1,629 | 2,515 | 3,978 | 5,765 |

Prefill is the latency of one extend on a cached prefix, median of 9 repeats over 2 crossed rounds × 2 GPU sets:

| Cached prefix + new tokens | 0 + 32K | 100K + 2K | 100K + 8K | 200K + 8K | 100K + 32K |
|---|---:|---:|---:|---:|---:|
| Latency (ms) | 551 | 91 | 191 | 220 | 630 |

These numbers were measured on #45936's stack, before this series dropped four changes that measured within run-to-run noise (see Changes measured on and off); they describe this stack's throughput, not gains attributable to individual changes.

Also, from the same stack: for the Quark export at TP4 on MI355X the Triton MXFP8 GEMMs alone halve batch-1 decode (94 vs 206 tok/s at 8K input). From about 1 MB the JIT quick all-reduce's INT8 is faster than aiter's bf16 custom all-reduce (#46692), so aiter's custom AR now stops at 2.4 MiB instead of 64 MiB; messages from 2.4 to 64 MiB are therefore reduced in INT8 rather than exact bf16, which the GSM8K results above include.
