# [Perf] dflash: Add opt-in compact CUDA graph buckets

[Upstream PR](https://github.com/sgl-project/sglang/pull/46739) · state: closed · merged: False

## Original PR description

## Changes

Split the DFlash capture policy from the Muse Spark RMSNorm change in #46622. Add process-wide opt-in `SGLANG_DFLASH_COMPACT_CUDA_GRAPHS=1` to retain geometrically spaced automatic target-verification buckets after alignment/capacity filtering. Preserve the smallest/largest eligible buckets and the published configuration.

**Changed defaults: none.** The new flag defaults to **false**, so every DFlash model keeps main's dense capture policy. Explicit batch-size lists, draft workers, non-DFlash models, no-padding mode, non-full graph backends, two-batch overlap, non-CUDA paths and missing configuration provenance retain the original policy even when enabled.

Opt-in example: `SGLANG_DFLASH_COMPACT_CUDA_GRAPHS=1 python -m sglang.launch_server ...`. With max batch size 64 this retains `[1,2,4,8,16,32,64]`; intermediate batches can do more padded verification work.

### reviews

- db-ol · COMMENTED · 2026-10-27T20:19:07Z · [source](https://github.com/sgl-project/sglang/pull/46739#pullrequestreview-5672607702)

Thanks for splitting this out, keeping the default dense and measuring c10, c24 and c48. That addresses the scope and measurement requests from my review on #46622.

On AIME the paired results are small either way. Across problem and seed pairs, 2 are right only on main and 1 only on the PR (GSM8K 24 and 27), so they neither show a regression nor rule one out. Main solved `source_index` 21 in both c24 seeds, while the PR missed it twice (once at the length cap, once with a wrong answer), and the PR solved problem 29 in seed 42 where main did not. Since the quality requests run at temperature 0, extra seeds mainly vary the batching, so paired c24 repeats that log the verification bucket each request used would be more informative. A run at batch 1 could serve as a control, though both policies keep bucket 1, so it would not exercise the changed padding.

The evidence also shows `max_total_num_tokens` at 1764480 on main and 1791616 with the flag in both seeds, about 1.5 percent more KV capacity. That fits KV sizing after graph capture absorbing the freed graph memory, would explain the flat peak, and could go in the Costs table.

My main question is when someone should turn this on. Throughput is lower at all three concurrencies, while the gains are about 24 s of startup and about 1.5 percent more KV tokens. Which workloads are meant to benefit? One measurement where faster startup or the extra KV capacity matters would help maintainers judge whether the flag is worth carrying.
