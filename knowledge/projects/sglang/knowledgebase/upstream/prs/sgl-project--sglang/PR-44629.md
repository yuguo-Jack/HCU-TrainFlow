# [Perf] [AMD] GLM5: Add opt-in W8A16 KDA decode projections on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/44629) · state: open · merged: False

## Original PR description

## Motivation

Depends on #38764.

With the #38764 PTPC selector enabled, GLM-5.3-Flash KDA decode still runs the first-stage `[qkv | beta | f_a | g_a]` projection as a fused BF16 GEMM, and that GEMM reads the full BF16 weight on every decode step. #38764 already keeps a per-channel FP8 copy of the same weight for prefill.

This change adds an opt-in W8A16 decode path that reads that existing FP8 weight with BF16 activations. Beta's rows are packed into the same FP8 weight, so one decode GEMM produces qkv, beta, and f/g. No second quantized copy is stored, and no activation quantization runs on the decode path. The decode GEMM reduces its split-K partials inside the same launch.

## Modifications

- Add the default-off `SGLANG_OPT_GLM53_KDA_W8A16_DECODE` selector and reject it unless `SGLANG_OPT_GLM53_KDA_PTPC_MODULES` is also set.
- Add `sglang.kernels.ops.gemm.gfx95_a16w8_preshuffle`, a gfx950 Triton GEMM with BF16 activations against the (16, 16)-preshuffled per-channel FP8 PTPC weight. It is used for decode token counts covered by the tuned table (`M<=64`), reuses the weight as a zero-copy view, and applies the existing per-row scale once to each reduced tile.
- Reduce split-K partials in the GEMM. The last CTA of each output tile sums the partials in split order and writes BF16, so there is no separate reduce launch and results do not depend on CTA arrival order. Splits of a tile share a program id modulo 8, so gfx950's round-robin dispatch places them on one XCD and the hand-off stays in one L2 behind a relaxed device-scope counter. A device-scope release per CTA would write back L2 and cost more than the reduce launch it replaces. Each layer owns a non-persistent tile-counter buffer, which every call leaves zeroed.
- When the selector is set, pack the first-stage FP8 weight as `[qkv | f_a | g_a | beta]`, padded to a multiple of 16 rows. Decode returns qkv, beta, and f/g views from one GEMM instead of running a separate BF16 beta GEMM. PTPC prefill reads only the unchanged qkv/f/g prefix and keeps BF16 beta.
- Add static per-`(N, K)` decode configs for TP4 (`N=6416`) and TP8 (`N=3344`), `K=4096`, from MI355X cold-cache sweeps of this kernel. Token counts above the table, and unsupported shapes, stay on fused BF16. The default PTPC path is unchanged when the selector is unset.
- Keep `o_proj` decode in BF16. In-situ decode profiles of the two-launch W8A16 path showed its GEMM plus split-K reduction was slower than the BF16 GEMM.
- Add CPU contracts for selector validation, table dispatch, tile-counter registration, and the packed beta split. Add gfx950 suites for the GEMM at every table row and bucket boundary, including single-split configs, 50 bitwise-repeat launches, counter reset, and CUDA-graph replay, and for the W8A16 decode projection against the dequantized FP32 reference. Extend the PTPC prefill test to the beta-packed layout.

Enable with:

```bash
SGLANG_OPT_GLM53_KDA_PTPC_MODULES=qkv_proj,f_a_proj,g_a_proj,o_proj
SGLANG_OPT_GLM53_KDA_W8A16_DECODE=1
```

## Accuracy Tests

Focused validation passed **26 CPU contracts and 7 gfx950 tests (129 subtests)**. Coverage includes TP4/TP8 packed shapes with and without beta, every decode table row and bucket boundary against the dequantized FP32 reference (relative error < 5e-3), BF16 cosine similarity, bitwise repeatability, split-K counter reset, PTPC prefill numerics, selector failures, finite outputs, and CUDA-graph replay.

Full GLM-5.3-Flash MXFP4 TP4 GSM8K on snapshot `b5688f25491202978c19c4d036eef579f61bbe07`: 1,319 examples, 64 evaluator threads, 32,768 maximum output tokens, thinking enabled, temperature 1.0, top-p 0.95, sampling seed unset.
