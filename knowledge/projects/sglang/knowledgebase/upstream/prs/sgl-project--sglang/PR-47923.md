# [Feat] [AMD] tokenizer: Install fastokens in the ROCm image

[Upstream PR](https://github.com/sgl-project/sglang/pull/47923) · state: open · merged: False

## Original PR description

��## Motivation

fastokens turns the prompt text into token ids. It is faster than the Hugging Face tokenizer SGLang uses by default. The package lives at [crusoecloud/fastokens](https://github.com/crusoecloud/fastokens). SGLang can already select it with `--tokenizer-backend fastokens`. That flag landed in [#23753](https://github.com/sgl-project/sglang/pull/23753), and the same change added a `fastokens` extra to the CUDA dependency file. The CUDA image installs the `all` extra, which includes that package, so a CUDA container can turn the flag on.

The ROCm image is built from a different file, `python/pyproject_other.toml`. It installs the ROCm serving extra (`srt_hip`, `srt_hip_rocm724`, or `srt_hip_rocm101`) rather than `all`. Those lists never included fastokens. On a ROCm container the flag fails with an import error until someone installs the package by hand after the container has started. This pull request puts the package in the ROCm image. The serving code does not change.

## Modifications

The CUDA file already pins `fastokens>=0.3.2`. This adds the same extra to the ROCm dependency file, includes it in `all_hip`, `all_hip_rocm724`, and `all_hip_rocm101`, and adds `fastokens` to the package list the ROCm Dockerfile installs for every ROCm version it builds.

Models that use the default chat template (for example Qwen) hit an `AttributeError` with fastokens on chat prompts of 32,768+ characters until #45459 merges. DeepSeek-V4.1 is not affected, because its chat requests use the dsv41 encoder.

## Accuracy Tests

GSM8K, 1314 examples, same server as the speed test. Only the tokenizer changed.

| Tokenizer | Correct | Score |
| --- | ---: | ---: |
| Hugging Face | 1280 | 0.974 |
| fastokens | 1273 | 0.969 |

## Speed Tests and Profiling

The benchmark is SGLang's built-in `generated-shared-prefix` dataset, the same family [#23753](https://github.com/sgl-project/sglang/pull/23753) used. The benchmark writes the prompts itself.

- One group of 16 prompts
- Shared prefix of 79,872 tokens
- Each prompt adds its own question of 12,288 tokens
- Output length 128
- Prefix cache on, cleared before each concurrency
- Concurrency 1, then concurrency 4

The server was DeepSeek-V4.1-Flash on four MI355X GPUs, tensor parallel 4, with the prefix cache on, DSpark on, shared-expert fusion off, and prefill graphs off. fastokens 0.3.2 was installed with pip into the current ROCm image. That install is the step this pull request removes. The baseline is the Hugging Face tokenizer.

| | Conc 1 | Conc 4 | Conc 4 rerun | Conc 4 rerun, second pass |
| --- | ---: | ---: | ---: | ---: |
| Median TTFT | 57.5% faster | 58.3% faster | 48.0% faster | 27.6% faster |
| Mean TTFT | 32.5% faster | 2.6% faster | 26.0% faster | 13.5% faster |
| Total token throughput | 37.1% higher | 8.1% lower | 7.8% higher | 3.8% higher |

- amd-pedghazi · comment · 2026-11-04T06:12:11Z · [source](https://github.com/sgl-project/sglang/pull/47923#issuecomment-6624005348)

Thanks, this is the right fix and the smallest one: same pin as the CUDA extra, in all_hip* and in every ROCm
srt_extras, and fastokens has no runtime dependencies, so the torch/transformers constraints are not touched.

One related fix to mention: on main, _build_plan in
`python/sglang/srt/entrypoints/openai/parallel_prompt_encode.py` calls
backend.post_processor.num_special_tokens_to_add(False), which the fastokens post-processor does not have, so
with fastokens every chat prompt of 32,768+ characters on the default chat-template path raises
AttributeError: 'builtins.PostProcessor' object has no attribute 'num_special_tokens_to_add' (#45459 fixes it;
I reproduced the error with fastokens 0.3.5, the newest release). DeepSeek-V4.1 is not affected, because its chat
requests use the dsv41 encoder and never reach parallel_prompt_encode: a 60k-token chat prompt through
/v1/chat/completions returned 200 on the ROCm image with fastokens and without #45459. So this PR does not depend
on #45459 for DeepSeek, but other models served with fastokens on ROCm would need it; a line in the description
would help.

Two small points: `docker/rocm-gfx1151.Dockerfile` also installs srt_hip and does not get fastokens (fine if
intended; worth a line). In the speed table, the c4 row (total throughput -8.1% with only the tokenizer changed, and
mean TTFT -2.6% against median -58.3%) looks like run-to-run noise from one 16-prompt run; a repeat or a note would
help. GSM8K shows 1,314 examples rather than the usual 1,319; is there a reason?

- mustafa-khalid · comment · 2026-11-04T14:45:13Z · [source](https://github.com/sgl-project/sglang/pull/47923#issuecomment-6633627596)

Thanks for your comments @amd-pedghazi.

- I've added a note in the description about other models needing #45459 for chat prompts of 32,768+ characters.
- I've also added a note that `docker/rocm-gfx1151.Dockerfile` is not included in this install. That could be another PR, with a test on gfx1151 hardware.
- About concurrency 4: I repeated it, as you suggested. In the original fastokens pass, a Triton kernel took about 1.5 s to compile, and that cost throughput. I reran the row twice on the same node. Each rerun had three warm-up points and then five scored seeds. `fastokens` gets better results than the baseline in both reruns. Both reruns are now in the table as the last two columns.
- GSM8K asks for 1,319 examples. The first 5 are the five-shot prompt, so the score is on 1,314. Both tokenizers scored 1,314.
