# [Spec] Support --speculative-token-map with a vocab-sharded target lm_head (TP>1)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43249) · state: open · merged: False

## Original PR description

## Motivation

Fixes #42397.

`--speculative-token-map` (reduced "hot" draft vocab) crashes at `--tp-size > 1`. `init_lm_head` in `eagle_worker_v2.py` indexes the shared target lm_head with **global** vocab ids. Under vocab-parallel TP each rank only holds `vocab / tp` rows, so this either:
- reads out of bounds, giving a device-side assert in `vectorized_gather_kernel`, or
- silently picks the wrong rows on rank ≥ 1.

#42424 makes this fail fast. This PR makes it work instead. If #42424 lands first, its guard can be dropped.

## Modifications

New `slice_hot_token_head(hot_token_id, target_lm_head)`. It is pure index math, run once at init.

1. Each rank keeps the hot ids inside its own shard and converts them to local row indices.
2. The draft logits are all-gathered along the vocab dim, so every rank must contribute the same width. Shorter blocks are padded with ids from the same shard that are not in the hot set. These are distinct real tokens, so top-k never sees duplicate candidates.
3. The function returns the global id of every gathered column, in rank order, as the new `hot_token_id`. The existing `hot_token_id[topk_index]` mapping therefore stays exact.

Unchanged:
- TP=1 behaves exactly as before.
- The rejection-sampling path still rejects a reduced draft vocab (existing FIXME).

## Accuracy / tests

CPU unit tests are in `test/registered/unit/spec/test_hot_token_head_tp.py`:
- TP=2 with unbalanced shards.
- TP=4 with an empty shard.
- An uneven last shard.
- TP=1 passthrough.
- A shard too small for the padded width.

Each case checks that the gathered columns are exactly the declared global ids, that every hot id is present, that no column is duplicated, and that all ids are real tokens.

End-to-end setup:
- Hardware: 2× DGX Spark (GB10, sm_121), TP=2 over RoCE.
- Model: Qwen3.8-Flash-Next NVFP4.
- Speculative decoding: NEXTN 3/1/4 with a 65,536-id map.

The map splits 32,768 / 32,768 across the two ranks, so the padding path was not exercised end to end. It is covered by the unit tests. These runs used main@7be5e347 with the equivalent patch:

| | Before | With this PR |
|---|---|---|
| Server start with `--speculative-token-map` at TP=2 | device-side assert in `init_lm_head` | starts |
| Acceptance length, short structured-JSON task | 4.00 (no map) | 4.00 |
| Our CN/JP structured-extraction regression suite | 36/36 | 36/36 |
| GSM8K, full 1319, thinking on, T=0.6 (author protocol) | — | 97.42% (checkpoint author: 97.27%) |

The GSM8K run had this PR and the sm_121 skinny-GEMM PR enabled together. With both PRs vs neither, single-stream decode went:

| Task | Without | With both |
|---|---|---|
| Short JSON | 64.2 tok/s | 77.8 tok/s |
| CN prose | 31.4 tok/s | 38.4 tok/s |
| JP prose | 34.7 tok/s | 39.0 tok/s |

The draft head shrinks from 124,160 to 32,768 rows per rank. We did not isolate this PR's share of the gain.

This PR was rebased onto current main. The unit tests were re-run on the rebased code, but the end-to-end run was on the commit above.

- xin-osaka-u · comment · 2026-10-10T03:19:39Z · [source](https://github.com/sgl-project/sglang/pull/43249#issuecomment-6093237354)

Thanks @jvzibro for the careful comparison in #43347. Two follow-ups from our side.

**1. Quantized lm_head: fixed here (c89d16c).** You are right that plain row indexing is wrong for a block-quantized head. Our end-to-end run used Qwen3.8-Flash-Next-NVFP4, whose lm_head stays BF16, so we never hit it. This PR now raises a `ValueError` at startup when the shared lm_head weight is not floating-point, at any TP size, instead of binding packed bytes. A unit test covers it.

**2. The two designs fit different cases.** I agree with your table. For reviewers, the trade-off in one place:

| | Sharded hot head (this PR) | Replicated hot head (#43347) |
|---|---|---|
| Draft lm_head rows per rank | `H / tp` for a balanced map | `H` |
| Per-step collective | the existing vocab-dim all-gather of draft logits | none |
| Candidate set vs TP=1 | same for a balanced map; a skewed map adds fill tokens (real, distinct, same shard) | always the same |
| Best fit | large maps on memory-bandwidth-limited ranks, where the lm_head read dominates | maps used as a hard restriction of the draft vocabulary; fast GPUs where the gather is the larger cost |

Our case is the first column: a 65,536-id map on two GB10 nodes (unified memory, roughly 200 GB/s). At hidden 2560 in BF16, each draft step reads about 168 MB of head weights per rank with the sharded head and about 336 MB with the replicated one, while the gathered logits are 32,768 values per token per rank. That is arithmetic, not an A/B: I have not benchmarked #43347 on our hardware. The numbers in this PR's description are from the sharded design only.

On `use_attn_tp_group`: this PR takes the shard layout from the lm_head module itself (`tp_size`, `shard_indices`, `num_embeddings_per_partition`) and passes through when that `tp_size` is 1. I have not tested dp-attention with a token map.

I have no preference on which design lands. If the maintainers prefer the replicated head for exactness, I'm happy to close this one and test #43347 on GB10 TP=2. If the sharded layout is worth keeping for bandwidth-limited hardware, it could also be an option on top of #43347.

@xin-osaka-u Thanks for the quick fix — I checked c89d16c and the dtype guard + test look right to me. Good to know the Flash-Next NVFP4 checkpoint keeps its lm_head in BF16; that explains why this never surfaced on your side.
