# fix: default Inkling to fa4 on Hopper

[Upstream PR](https://github.com/sgl-project/sglang/pull/35292) · state: closed · merged: True

## Original PR description

## Motivation

A bare `python -m sglang.launch_server --model-path thinkingmachines/Inkling-Small-NVFP4 --trust-remote-code` dies at startup on Hopper.

The Inkling model override defaults the attention backend to `fa4` only on SM100 and to `triton` everywhere else, while `apply_inkling_prefill_cuda_graph_default` unconditionally opts Inkling into FULL prefill CUDA-graph capture. `TritonAttnBackend` cannot capture EXTEND, so capture fails with:

```
ValueError: Invalid forward mode: forward_mode=<ForwardMode.EXTEND: 1> for CUDA Graph replay.
```

Both defaults date from the original Inkling support (#31681). Users following the cookbook never hit it because the H200 recipe passes `--attention-backend fa4` explicitly: fa4 runs on SM90, so the triton fallback on Hopper was never needed.

## Modifications

- `model_overrides/inkling.py`: when every attention-backend flag is unset, default to `fa4` on SM90 and SM100 (was SM100 only) and `triton` elsewhere (SM120/GB10, ROCm), written as an inline platform branch like the other model overrides.
- `apply_inkling_prefill_cuda_graph_default`: opt into FULL only when prefill runs on fa4, i.e. an explicit `--prefill-attention-backend` / `--attention-backend` of `fa4`, or no backend flag on SM90/SM100. Otherwise the generic prefill-graph default applies, which triton captures fine.
- Net effect: Hopper now matches the cookbook (fa4 + FULL prefill graph); an explicit `--attention-backend triton` boots instead of crashing; Blackwell is unchanged.

## Accuracy Tests

2x H200, `thinkingmachines/Inkling-Small-NVFP4`, TP2, cookbook H200 flags without `--attention-backend` (TP2 with `--max-mamba-cache-size 1024 --max-total-tokens 1572864` instead of TP8). Probes: 5 prompts (arithmetic, factual, code, Chinese, listing) x `reasoning_effort` none/high, greedy. GSM8K: `few_shot_gsm8k`, 200 questions.

| tree | extra flags | attention / prefill graph | boot | probes | GSM8K | output tok/s |
|---|---|---|---|---|---|---|
| main | - | triton / full | `ValueError ... EXTEND` | - | - | - |
| this PR | - | fa4 / full | OK | 10/10 | 0.840 | 2407 |
| this PR | `--attention-backend triton` | triton / breakable | OK | 10/10 | 0.850 | 1904 |

No tracebacks in any server log; GSM8K invalid rate 0 in both arms.

## Speed Tests and Profiling

Startup argument resolution only. On H200 the new fa4 default is faster than the triton fallback (2407 vs 1904 output tok/s on the GSM8K run above; single runs, noisy).

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Honor the split prefill backend when gating graphs**

When a user sets a base backend and overrides only prefill, such as `--attention-backend triton --prefill-attention-backend fa4`, this returns the base `triton` even though `attention_backends_of()` makes the effective prefill backend `fa4`. `_apply_inkling_prefill_cuda_graph_default()` consequently skips Inkling's FULL graph opt-in, after which the generic multimodal compatibility rule disables the default breakable graph and runs prefill eagerly. This regresses a supported FA4 prefill configuration that previously received FULL capture; resolve the effective prefill backend by preferring `prefill_attention_backend` over the base backend.
