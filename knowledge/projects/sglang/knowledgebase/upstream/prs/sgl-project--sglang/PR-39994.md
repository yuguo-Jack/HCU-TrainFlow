# [Perf] [AMD] MiniMax-M3: Remove small kernel launches from the sparse KV cache write

[Upstream PR](https://github.com/sgl-project/sglang/pull/39994) · state: open · merged: False

## Original PR description

## Motivation

On MiniMax-M3-MXFP8 (TP4/EP1, MI355X/gfx950), small elementwise, cast and copy kernels cost 1.79 ms per decode step (12.6% of decode kernel time): 433 launch-bound launches of about 4 us each, mostly one or two per sparse layer. Some do nothing (dividing K and V by 1.0); others split one job across launches (two fp8 casts, then a scatter).

This PR removes **228 launches per decode step** (433 → 205, 1.79 → 0.84 ms). The profiled decode step is 9.2% shorter, output throughput is 1.9% to 8.0% higher at concurrency 4–64, and GSM8K is unchanged (mean 0.978 in both arms).

## Modifications

- **A. Skip work with no effect (A1):** −114 launches/step.
- **B. Fuse or replace kernels (B1, B2):** −114 launches/step, all from B1.

**A1. Skip dividing K/V by a unit scale** (`memory_pool.py`). The MiniMax sparse backend passes `layer.k_scale_float` and `layer.v_scale_float`, which are `1.0` when the checkpoint has no KV scales, so every sparse layer ran `div_(1.0)` on K and V. `_kv_scale_divides()` skips a host `1.0` at all seven scale-divide sites; a device scale still divides, since reading it would break CUDA-graph capture. −114 `MulFunctor<float>` launches. **Bit-exact on every non-NaN value.** A negative NaN now keeps its sign, which dividing by 1.0 cleared: on gfx950, the 127 negative bf16 NaNs store `0xFF` in a `float8_e4m3fn` cache instead of `0x7F`, and `float8_e4m3fnuz` is unchanged.

**B1. Fold the bf16 → fp8 KV cast into the paged write** (`memory_pool.py`, `cache_ops.py`, `hisparse_memory_pool.py`). `store_kv_fused_cast()` casts and scatters K and V in one `reshape_and_cache_flash` launch: −114 `float8_copy_kernel_cuda` launches. `_has_dense_kv_rows()` admits the strided `dim=-1` QKV slices (the kernel takes the token stride) but requires the exact token count; anything else takes the old path. Like `store_cache`, it skips reserved slot 0 (new `skip_slot_zero`, default off) and bounds slots by `size + page_size` (new `size_limit`, default off). Where `store_cache` device-asserts on an out-of-range slot, the fused store skips it, since Triton has no always-on device assert; with `SGLANG_ENABLE_ASYNC_ASSERT=1`, `maybe_detect_oob()` still fails loudly. `HiSparseMHAMainPool` opts out, and its `store_kv_fused_cast()` raises. Bytes match `.to(fp8)` + scatter wherever ATen's cast is finite (|x| ≤ 464 for `float8_e4m3fn`; every bf16 value tested on gfx950 and gfx942, for `float8_e4m3fnuz` too); where ATen overflows to NaN, the fused store may write the saturated maximum instead (±448 for `float8_e4m3fn`).

**B2. Replace the index-K `index_put` with a row scatter** (`cache_move.py`, `memory_pool.py`). `MHATokenToKOnlyPool.set_k_buffer` ended in `k_buffer[loc] = src`; it now always calls `store_k_slots`, a Triton row scatter that skips any slot outside `[0, size + page_size)`. A source that fails `_has_dense_kv_rows()` is made contiguous first; the MiniMax-M3 index-K source is already dense. The two paths differ only on slots a correct caller never passes, since padded rows target slot 0: ATen asserted on a too-large slot and wrapped a negative one, and `store_k_slots` skips both. Same launch count, **4.9 → 4.1 us/layer**.

### Impact on CUDA and on Other AMD Architectures

Only B1 checks the architecture, and only on CUDA; otherwise dispatch conditions decide:

| change | reaches CUDA and gfx942 when |
| --- | --- |
| A1 | a host `1.0` scale is passed (bit-exact except a NaN's sign) |
| B1 | MiniMax-M3's sparse store casts bf16 K/V into an fp8 cache on gfx942 or on CUDA sm89 and newer, passes `can_store_kv_fused_cast()`, and is not taken first by the fused K/V/index store from [#46135](https://github.com/sgl-project/sglang/pull/46135) |
| B2 | a MiniMax-M3 index-K store passes `_has_dense_kv_rows()` |

`can_store_kv_fused_cast()` requires HIP or CUDA sm89 and newer, since Triton's CUDA backend casts to `float8_e4m3fn` only from sm89, as well as nhd layout, a `uint8`-stored non-quantized `float8_e4m3fn` or `float8_e4m3fnuz` cache, a flat 3-D buffer, `head_dim == v_head_dim`, unit scales and dense, equal-shape K/V; anything else keeps today's path. E5M2 is left out so that an overflow stays infinite, as ATen makes it, instead of saturating. The AITER backend's own `launch_reshape_and_cache_flash()` calls keep the defaults (no slot-0 skip, no `size_limit`). For every caller, the kernel now computes destination offsets in int64 and the launcher asserts a contiguous `slot_mapping`; neither changes those calls, which already pass contiguous int64 slots. B1 and B2 have only been benchmarked on gfx950, and their tests have not run on CUDA. On CUDA (`float8_e4m3fn`) and gfx942 (`float8_e4m3fnuz`), B1 swaps ATen's fp8 cast for Triton's; the `float8_e4m3fnuz` byte test passes on gfx942, where Triton converts in hardware, as well as on gfx950, where it converts in software.

### Unit Tests

```bash
pytest test/registered/kernels/ops/kvcache/test_store_cache.py
```

These check `store_k_slots` and `set_k_buffer` against ATen indexing, `store_kv_fused_cast` against `.to(fp8)` on every bf16 value (also for `float8_e4m3fnuz` on ROCm), that `set_kv_buffer` leaves K/V untouched for a host `1.0` scale and divides by host and tensor scales on every bf16 value, that every bounded store skips out-of-range slots with `SGLANG_ENABLE_ASYNC_ASSERT` off, and each guard's accept and reject cases. On a real `MiniMaxSparseKVPool`, they check the main K/V and index-K cache bytes that `set_fused_kv_index_buffer` writes through the fused cast and through `set_kv_buffer`, including a `[N, 1, D]` source whose head stride is 1. All pass on MI355X. On MI300 the file passed before the real-pool test and the `[N, 1, D]` cases were added, which have run only on MI355X. `test/registered/attention/test_fused_fp8_kv_write.py` passes on MI355X.

# Status after merging `main`

Merging `main` removed much of the tail on its own; this PR's own commits in between add no launches.

| | before merging `main` | 2026-10-06 | 2026-10-26 |
| --- | --- | --- | --- |
| tail launches/step | 946 → 319 (−627) | 433 → 205 (−228) | 433 → 205 (−228) |
| tail ms/step | 4.05 → 1.39 | 1.83 → 0.86 | 1.79 → 0.84 |
| baseline decode step | 21.55 ms | 14.29 ms | 14.15 ms |
| output throughput | +8.6% to +11.8% | +2.4% to +6.6% | +1.9% to +8.0% |

- [#36574](https://github.com/sgl-project/sglang/pull/36574) moves this model's MXFP8 MoE to aiter's fused kernels, with the sorting kernel from [#36559](https://github.com/sgl-project/sglang/pull/36559). That took the Triton MXFP8 runner's clamp, zero-fills, combine and copies out of the baseline (570 launches, 2.42 ms/step), including everything the former A2 and A3 removed, so both were dropped.
- [#36549](https://github.com/sgl-project/sglang/pull/36549) stores the index-K cache in fp8 on gfx95, adding the cast behind the 57 remaining `float8_copy_kernel_cuda` launches.
- [#46135](https://github.com/sgl-project/sglang/pull/46135) adds a CUDA-only store that writes K/V and index K in one launch, with the same bf16 → fp8 cast. It runs before B1 when both caches use the same fp8 dtype (Hopper with `fp8_e4m3` KV, or fp8 attention-GEMM mode); B1 covers HIP and the other CUDA cases.

The faster MoE also shrank the step, so the tail's share fell from 18.8% to 12.8%. Between the first two measurements, `--fp8-gemm-backend aiter`, `SGLANG_USE_AITER_MOE_GU_ITLV=0` and `SGLANG_MINIMAX_INDEXCACHE_*` were added and `ROCM_QUICK_REDUCE_QUANTIZATION=INT4` was dropped. That doesn't affect the tail rows, but those two columns' step and throughput rows compare configurations as well as trees; the 2026-10-26 run kept the 2026-10-06 settings.
