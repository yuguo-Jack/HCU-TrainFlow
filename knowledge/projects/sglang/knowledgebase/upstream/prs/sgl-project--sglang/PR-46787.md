# [Fix] [AMD] deterministic: Batch-invariant channel-wise FP8 linears and experts on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/46787) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-deterministic-inference` on ROCm (gfx950), compressed-tensors FP8 models with per-channel weight scales are not deterministic. `RedHatAI/*-FP8-dynamic` is the common example. For `RedHatAI/Qwen3-8B-FP8-dynamic` at TP1 with every other deterministic-mode fix in place:
- `single` returns 3 different outputs in 50;
- `prefix` returns 19-22 per prompt;
- a bitwise batch-size check keeps the same tokens in only 890 of 1,275 responses.

Two paths cause it:

- **Linears:** AITER per-token quantization plus the CK `gemm_a8w8_bpreshuffle` kernel, which picks its kernel by the number of tokens.
- **Experts (MoE):** AITER's fused MoE, where a token's result depends on the other tokens in its batch.

## Modifications

Depends on #46791 (first two commits: experts preshuffled only for the AITER runner; K taken from the tensors on the Triton runner). This PR's own changes are the last two commits:

- **Linears:** `fp8_utils.py` adds `apply_fp8_channel_linear_batch_invariant` and `compressed_tensors_w8a8_fp8.py` uses it for channel-wise linears in deterministic mode on ROCm. The weight stays unshuffled, and `triton_scaled_mm` runs with a fixed tile that depends only on N (`_batch_invariant_fp8_channel_tile`: 128x256x64 from N >= 16,384, else 128x128x128). One program per output tile loops over K, so every row is reduced in the same order at any batch size.
- **Experts:** `compressed_tensors_w8a8_fp8_moe.py` makes the automatic runner choice pick the Triton MoE runner in deterministic mode, and the experts stay unshuffled for it. The Triton runner uses one fixed config in deterministic mode. An explicitly requested runner is kept.
- **Tests:** the CPU test from #46791 gets a deterministic-mode case.
- **Unchanged:** normal mode, CUDA, and block-scaled FP8.

## Accuracy Tests

## Speed Tests and Profiling

Deterministic mode, `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-range-ratio 1.0 --request-rate inf`. Output throughput, before vs this PR; 1k/1k is 256 prompts at concurrency 256, 8k/1k is 256 prompts at concurrency 128:

| Model | TP | 1k in / 1k out | 8k in / 1k out |
| --- | --- | --- | --- |
| Qwen3-8B | 1 | 4,265 -> 4,084 tok/s (-4.3%) | 945 -> 917 tok/s (-3.0%) |
| phi-4 | 1 | 3,415 -> 3,287 tok/s (-3.8%) | 681 -> 662 tok/s (-2.8%) |
| Llama-3.1-8B-Instruct | 1 | 3,194 -> 3,106 tok/s (-2.8%) | 957 -> 931 tok/s (-2.7%) |
| Qwen3-32B | 2 | 3,391 -> 3,193 tok/s (-5.8%) | 761 -> 728 tok/s (-4.3%) |
| Qwen3-30B-A3B (MoE) | 1 | 5,043 -> 4,657 tok/s (-7.7%) | 1,182 -> 1,081 tok/s (-8.6%) |

The cost comes from `triton_scaled_mm` and the Triton MoE runner replacing CK and AITER kernels. For Llama-3.3-70B TP4, starting the larger tile at N >= 12,288 instead of 16,384 was slower end to end (-3.6% at 1k/1k, -1.6% at 8k/1k), so the threshold stays.
