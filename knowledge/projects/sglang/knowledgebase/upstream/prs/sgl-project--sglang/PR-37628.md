# [unified-memory] Fuse the draft model's KV into the target's page envelope (mechanism)

## Motivation

A speculative draft model owns a KV pool of its own, separate from the target's.
That means a second allocator, a second id space, a second set of page tables, and
memory reserved up front for the draft that the target can never use.

Under `--enable-unified-memory` the target's slot entries already have room. This
PR puts the draft's K/V rows **inside** the host entry, after the host's own parts:

```
[ K_0 | V_0 | ... | K_n | V_n | dK_0 | dV_0 | ... | dK_m | dV_m | pad ]
  \___________ host ___________/ \_________ draft _________/
```

One slot id then addresses both. One allocation, one free, and one whole-page
relocation carry the target's KV and the draft's together — a compaction move gets
the draft bytes for free instead of needing a second, separately-indexed move.

**This PR builds that mechanism and leaves it unreachable.** The admission gate is
untouched — `speculative_algorithm in (None, "DSPARK")` — and the fuse decision
additionally requires an EAGLE-family algorithm, which DSPARK is not. Admitting the
algorithms that can fuse is #40491's job, which keeps this PR reviewable as
mechanism and the behavior change it enables in a diff of its own.

## Modifications

**Layout and pool.** `DenseDraftRegion` describes the draft's K/V geometry as two
more parts of the host entry at `draft_offset_in_entry()`, and
`UnifiedDraftKVPool` presents those parts to the draft as an ordinary KV cache
whose write doors take physical ids only (`requires_physical_write_loc`). The unit
of the region's layer dimension is a **lane**, not a layer, because the two draft
head shapes place runners oppositely: a replicated head gives every runner all the
draft's layers and so needs a range each (3 runners × 2 layers = 6 lanes), while a
per-depth head gives each runner one depth (8 layers across 2 runners = 2 lanes).
The runners' ranges must tile the region exactly, in runner order, which
`FusedDraftPlacement.__post_init__` asserts.

**Id space.** The fused-draft disposition on `KVIndexTranslator`: a fused draft
runner translates through the **target's** v2p table, exactly as the target does.
A dense fused draft has no second id space, so its window index table falls back
to the one dense table.

**Multi-step draft decode.** `generate_draft_decode_kv_indices` translates the ids
it copies when handed the runner's v2p table (`KVIndexTranslator.full_flat_v2p()`),
in all four multi-step containers; a negative id lands on the page-0 sink, as
`translate_kv_loc` does. Static pools pass `None` and keep the raw copy.

**Boot.** The target resolves the placement from the draft's config read in draft
mode (`SpecAuxHiddenStateConfig.draft_model_config` / `draft_kv_num_layers`).
That reading feeds only the fused decision: a private draft pool keeps its
historical size, so a path-less MTP deployment's token budget is unchanged. The
pool solve prices the exact fused entry — host rows plus draft rows plus alignment
pad, through the same spec the pool factory builds — in the cell size and in the
bytes the unified pool is handed, for both the ratio solve and the SWA chunk-cap
solve. `_init_pools` runs twice per server: the target pass stores the placement on
the `UnifiedKVPool`, the draft pass reads it back and binds the draft worker to the
region.

## Scope: full-attention draft KV only

The fused region is dense and full-attention. `place_fused_draft` declines, with
the reason logged, and the draft keeps its private pool over the unified virtual
id space, whenever the draft needs something the dense region cannot express:

| draft shape | status here |
|---|---|
| full-attention K/V, symmetric rows | **fused** |
| asymmetric K/V rows (`head_dim != v_head_dim`) | declines to a private pool |
| sliding-window layers of its own | declines to a private pool |
| recurrent / Mamba state layers of its own | declines to a private pool |
| K/V rows not a multiple of the 16-B part alignment | declines to a private pool |
| explicit `--speculative-draft-kv-cache-dtype` unlike the host's | declines to a private pool |

A draft whose `auto` KV dtype resolves unlike the host's is only known once the
draft runner loads; it then fails the bind with a message naming the flag, instead
of reading the host's rows as another dtype.

## Accuracy Tests

Because no draft can fuse on this branch, this tests the claim that the machinery
is **dormant**: the host entry layout changed and the translator gained a
disposition, and both run on every forward regardless.

H20, the pre-rebase revision of this PR: GSM8K at n=200, unified against the same
build without it on the same model, backend and configuration — **26 matched
pairs, median +0.25 pt, sd 2.18 pt**. The two pairs more than 2.9 pt (the measured
run-to-run floor) below baseline are both gpt-oss-20b, whose baseline alone spans
6.5 pt in the same run; excluding it, 22 pairs, median +0.75 pt, worst −1.5 pt.

B200, this head: a path-less MTP deployment off the unified pool keeps main's
token budget — Qwen3.5-0.8B, EAGLE (3 steps, topk 1, 4 draft tokens), flashinfer,
`--mem-fraction-static 0.5`: `max_total_num_tokens` 5,233,400 here against
5,253,582 on main, the difference being the two runs' free memory at load
(176.97 vs 177.58 GB); GSM8K 0.330 on both.

B200, greedy parity, this head: Qwen3.5-4B on flashinfer, spec-off on the unified
pool and MTP on the static pool, temperature 0, 24 prompts × 128 tokens one at a
time — identical tokens and logprobs to `main` (max |Δlogprob| 0), and the same
`max_total_num_tokens` (1,381,150 / 1,592,686).

## Speed Tests and Profiling

H20, the pre-rebase revision: median inter-token latency, unified against the same
build without it, speculative decoding off — **20 matched pairs, median +0.48%**,
every measurement between −1.9% and +2.2%. That is the unified pool's standing
overhead on this matrix, not a cost this PR adds.

B200, adjacent heads, the same unified spec-off configuration (Qwen3.5-4B,
flashinfer, interleaved on one GPU): median inter-token latency with one request in
flight 2.53 ms on `main`, 2.54 ms on #37627, 2.53 ms here.

## Notes for reviewers

**Nothing on this branch can reach a fused draft, deliberately.** The new code
paths are exercised here by unit tests — geometry, placement tiling, translator
disposition, boot-time pricing, the draft-worker binding, and the translated
multi-step kernel — and end to end by #40491's GPU runs.

**Lane count is not layer count**, in either direction, and the two draft head
shapes disagree about which way. The module docstring in
`mem_cache/layout/fused_draft.py` states the convention; `lanes_for(runner)` is per
runner, which is what makes `len(full_ids) == len(full_lanes)` hold at bind.
