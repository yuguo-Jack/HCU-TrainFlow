# [Refactor] dsv4: Keep only the two-level V4.1 indexer in the prefill graph

[Upstream PR](https://github.com/sgl-project/sglang/pull/45783) · state: closed · merged: True

## Original PR description

- The prefill CUDA graph captures the DeepSeek-V4.1 ratio-1/2 indexer only with two-level candidates (`SparseTableBackend`), the path released checkpoints take on SM100: `low_ratio_prefill_graph` now means exactly that and absorbs `_prefill_graph_two_level`. Any other config runs the ratio-1/2 sources as one eager break, as SM90 already does.
- Remove what served the other path: the captured full top-k (`FullTopKIndexer.topk_prefill_captured`, `topk_transform_paged_torch`) with its candidate-window assert, and the c1/c2 paged indexer metadata every replay built for it (full-width page tables, row chunks, DeepGEMM schedules). The captured consumer read only the index page size from that metadata, now `CapturedPrefillInputs.index_page_size`; `refresh_for_breakable_cuda_graph_replay_` drops `two_level`, and `PagedIndexerMetadata` drops `row_chunk`.
- Remove `SGLANG_DSV41_TORCH_PREFILL_INDEXER`, a development switch that forced the torch prefill indexer on SM100; SM90 keeps the torch indexer. HIP states `low_ratio_prefill_graph = False` instead of borrowing the CUDA property, which reads the CUDA backend's candidate indexer.

No behavior change for released checkpoints: DeepSeek-V4.1-Flash and DeepSeek-V4.1-Flash-1017 set `candidate_topk_blocks: 2048`, so SM100 already runs the two-level path and SM90 the eager break; a replay just no longer builds metadata that nothing reads. Supersedes #45073.
