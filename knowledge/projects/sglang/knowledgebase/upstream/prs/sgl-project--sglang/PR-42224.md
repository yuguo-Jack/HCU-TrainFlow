# [Perf] [NPU] dsa: Add INT8 LightningIndexer to accelerate indexing on A2/A3

[Upstream PR](https://github.com/sgl-project/sglang/pull/42224) · state: open · merged: False

## Motivation

A2 and A3 NPUs do not support FP8 LightningIndexer, so FP16 is the only practical precision for the indexer. This makes the indexer a bottleneck for long-context workloads. This PR adds an int8 quantization option for the NPU LightningIndexer. It stores the indexer key cache as int8 and uses the NPU-native npu_quant_lightning_indexer kernel, delivering a 2× indexer speedup and reducing end-to-end TTFT on Ascend A2/A3.

The feature is opt-in via SGLANG_NPU_INDEXER_INT8=True and is disabled by default, preserving existing FP16/FP8 behavior.

## Modifications

- python/sglang/srt/environ.py

Adds SGLANG_NPU_INDEXER_INT8 = EnvBool(False) as the feature flag for int8 indexer mode.

- python/sglang/srt/hardware_backend/npu/memory_pool_npu.py


Adds indexer_kv_store_int8 and selects index_k_store_dtype = torch.int8 and index_k_scale_dtype = torch.float16 when the flag is enabled.

Creates the scale buffer for both FP8 and int8 modes, using index_k_scale_dtype (FP16 for int8, FP32 for FP8).


- python/sglang/srt/layers/attention/dsa/dsa_npu_indexer.py

 _quantize_npu_indexer_activation now accepts a scale_type argument instead of hardcoding torch.float32 for the scale tensor.

forward_npu passes pool.index_k_store_dtype and pool.index_k_scale_dtype into the quantizer.

When index_k_store_dtype == torch.int8, the indexer weights are cast to FP16 before calling npu_quant_lightning_indexer, because the int8 kernel requires FP16 weights.

- TamirBaydasov · COMMENTED · 2026-10-22T15:40:34Z · [source](https://github.com/sgl-project/sglang/pull/42224#pullrequestreview-5616862877)

Thanks for this PR. We tested the INT8 indexer's accuracy on GLM-5.2 (A3, tp8) with long
prompts (6k–26k tokens). Short prompts like gsm8k cannot test it: with 2048 tokens or fewer,
the indexer selects every token, so even a broken kernel gives the same answer.

| indexer | copy a long random list | find a value among 650–2100 similar records (15 questions) |
|---|---|---|
| FP16 | 100% | 15 / 15 |
| INT8 (this PR) | 100% | 15 / 15 |
| deliberately broken (control) | 0–19% | 0 / 15 |

In this setup INT8 gives the same results as FP16. We found three other setups that break
when the flag is on. Each inline comment below explains one of them and proposes a fix.
With these fixed, turning the flag on can no longer break DeepSeek-V4, and setups with
prefill CP or an FP8 KV cache keep their current indexer.

Longer term, we would like this to be the default on A2/A3. Before that we plan to check
three more things: the same test at 128k–1M tokens with the usual production launch
flags, one standard long-context benchmark, and no slowdown on short prompts. These three
fixes come first either way.

File: `python/sglang/srt/hardware_backend/npu/utils.py` · line None

**Problem.** When the flag is on, `custom_ops` is never imported. Other code needs it:
DeepSeek-V4 on NPU calls `torch.ops.custom.*` ops (`ascend_dsv4_backend.py`, `dsv4_rope.py`,
`npu/moe/topk.py`). Those ops then do not exist, so DeepSeek-V4 cannot run with the flag on. This also means the
flag can never become the default without breaking DeepSeek-V4 on NPU.

**Why the crash happened.** `import custom_ops` copies every `torch.ops.custom.*` op onto the
`torch_npu` module. After the import, `torch_npu.npu_quant_lightning_indexer` is the custom
version, not the original one, and the INT8 call needs the original.

**Proposal.** Always import `custom_ops` (remove the two `if` blocks) and call the original op
by its full name. The import replaces names on the `torch_npu` module only, and
`torch.ops.npu` is not touched:

```python
# dsa_npu_indexer.py, INT8 branch
topk_indices = torch.ops.npu.npu_quant_lightning_indexer(
    query=query,
    key=past_key_states,
    ...  # same arguments as today
)
```

Please check on your setup that its return value is the same as
`torch_npu.npu_quant_lightning_indexer`'s before `custom_ops` is imported.

- TamirBaydasov · comment · 2026-10-22T15:40:35Z · [source](https://github.com/sgl-project/sglang/pull/42224#discussion_r4350393164)

File: `python/sglang/srt/layers/attention/dsa/dsa_npu_indexer.py` · line None

**Problem.** With the flag on and prefill CP enabled (`attn_cp_size > 1`), the server starts
normally and then crashes with this `RuntimeError` on the first prefill that uses CP. A crash
in the middle of serving is much harder to diagnose than a clear message at startup.

**Proposal.** Decide once, when the memory pool is created, and fall back to the current
indexer with a warning instead of crashing (`memory_pool_npu.py`, around line 709):

```python
want_int8 = index_head_dim is not None and envs.SGLANG_NPU_INDEXER_INT8.get()
self.indexer_kv_store_int8 = want_int8 and get_parallel().attn_cp_size <= 1
if want_int8 and not self.indexer_kv_store_int8:
    logger.warning("INT8 indexer does not support prefill CP yet; using the default indexer.")
```

The `RuntimeError` here then cannot be reached; it can stay as an `assert`. Adding INT8
support to `do_npu_cp_balance_indexer` can come later in a separate PR.

- TamirBaydasov · comment · 2026-10-22T15:40:35Z · [source](https://github.com/sgl-project/sglang/pull/42224#discussion_r4350393179)

File: `python/sglang/srt/hardware_backend/npu/memory_pool_npu.py` · line 712

**Problem.** The flag switches the indexer cache to INT8 even when the KV cache is FP8
(`dsa_kv_cache_store_fp8`, used on A5 / Ascend 950). That setup already has its own FP8
indexer, and the motivation of this PR is A2/A3, which have none. A user who sets the flag
on A5 silently replaces a working FP8 indexer with an INT8 one that nobody has tested there.

**Proposal.** Use INT8 only when the indexer would otherwise be FP16/BF16. Together with
inline 2:

```python
want_int8 = index_head_dim is not None and envs.SGLANG_NPU_INDEXER_INT8.get()
self.indexer_kv_store_int8 = (
    want_int8
    and not self.dsa_kv_cache_store_fp8
    and get_parallel().attn_cp_size <= 1
)
```

It would also help to log one line at startup with the indexer cache dtype that was chosen
(int8 / fp8 / bf16), so users can see which path they are on.
