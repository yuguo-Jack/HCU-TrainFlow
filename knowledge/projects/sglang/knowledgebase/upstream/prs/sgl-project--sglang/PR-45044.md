# [Fix] Drop STAGING_RSP for chunks this engine never requested

[Upstream PR](https://github.com/sgl-project/sglang/pull/45044) · state: open · merged: False

## Original PR description

Fixes #45014.

## Motivation

The prefill rank socket accepts unauthenticated ZeroMQ control messages. In `handle_staging_rsp` (shared by the Mooncake and NIXL connectors), an attacker-controlled `chunk_idx` drove `StagingTransferInfo.set_chunk`, which grows three Python lists to `chunk_idx + 1` entries with no bound. A peer that first registers a normal-looking transfer (so the room and session resolve to a real `TransferInfo`) can then name any index; the issue measured 12.23 GiB of host memory growth on a two-host run of 0.5.15.post1.

## Modification

`handle_staging_rsp` now takes the engine's `prefetch_requested` set and drops any response whose `(room, chunk_idx, session_id)` key was never requested, before touching the lists. The set is the exact keyspace of legitimate chunks: `prefetch_staging_reqs` adds each key before its STAGING_REQ goes out, and room teardown purges the keys together with the transfer infos, so a late response for a finished room drops the same way. Both connectors pass their staging context's set; no protocol change, and a legit decode side cannot tell the difference.

This bounds the index without a policy cap: the largest acceptable `chunk_idx` is the transfer's own chunk count, which is what the requested set encodes.

## Tests

Three CPU-only cases in `test_nixl_backend_basic.py::TestNixlStaging`:

- a requested chunk applies (offsets grow to the requested index and record the values),
- a plausible-looking but never-requested chunk (index 0 on a live room) drops without touching staging state,
- the issue's exact attack shape (fake room created by a normal registration, then `chunk_idx` 50,000,000) grows nothing.

The two drop cases go red if the membership check is removed (mutation-verified); the apply case stays green. Full file: 56 passed + 6 subtests. `ruff check` and `ruff format` clean on all four touched files.

One adjacent observation for a follow-up, not this PR: a short or malformed message on this socket (fewer than 7 parts) raises `IndexError` out of `handle_staging_rsp` inside the bootstrap thread, which has no guard around the handler call. Worth hardening separately.

## Verification scope

Local verification is the CPU unit path above; the two-host RDMA repro belongs to the issue's environment. CI covers the connector integration lanes.
