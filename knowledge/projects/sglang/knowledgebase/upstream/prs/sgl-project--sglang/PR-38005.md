# [3/N] Quantization Refactor: pin the package's public import surface

[Upstream PR](https://github.com/sgl-project/sglang/pull/38005) · state: closed · merged: False

## Original PR description

## Motivation

The quantization refactor moves implementations between modules and leaves re-export shims behind, so that the paths callers already use keep resolving. 497 import statements in this tree point into the seven modules that series will split: `base_config` (258), `fp8_utils` (70), `unquant` (50), `utils` (46), `fp8` (35), `modelopt_quant` (27), `mxfp4` (11). Forget one symbol in one shim and one of those paths dies.

Nothing currently fails loudly when that happens, which is the gap this test closes:

- **The failure lands far from the change.** A moved symbol breaks an import in a model file that only executes on a GPU with a particular checkpoint, so the split PR's own tests stay green.
- **Not every caller is an import.** The kernel registry addresses its implementation as a string: `target="sglang.srt.layers.quantization.fp8_utils:bmm_fp8"`. No linter, type checker or import scan sees that, and it fails at kernel-selection time on hardware that has the backend installed.
- **Not every caller is in this repo.** `base_config` and the package-root `*Config` exports are taught by `docs/docs/developer_guide/quantization_contribution_guide.mdx`, so downstream code imports them too, and no grep here can find those call sites.

## Modifications

Adds `test/registered/unit/layers/quantization/test_import_shims.py`. No source changes. It runs on CPU with no model, in about 7 seconds, and asserts that the public surface resolves rather than that any internals work:

- `base_config`'s five exported symbols, the path 258 statements across 252 files use.
- The 33 config classes the package root re-exports, plus the four non-class root names (`QUANTIZATION_METHODS`, `BASE_QUANTIZATION_METHODS`, `CPU_QUANTIZATION_METHODS`, `get_quantization_config`). Each config name must resolve to a class actually called that, which catches a shim wired to the wrong class rather than merely a missing one.
- The `from <module> import <names>` form specifically, because that is what the call sites use and a module-level `__getattr__` has to serve that form too.
- Submodule imports still falling through, which requires `__getattr__` to raise `AttributeError` and nothing else.
- Every `KernelSpec` whose `target` string addresses this package. The list is derived from the kernel registry rather than hardcoded, so a future spec pointing here is covered automatically; today only `gemm.bmm_fp8` does. The attribute may sit behind an optional third-party import, so a definition visible in the source counts, which keeps the case meaningful on a machine without flashinfer.

`LEGACY_IMPORT_PATHS` is the registry a later shim PR appends its old path to. Entries should only ever be added; a path stops needing to resolve when the gated shim-removal phase removes it, not when someone moves a symbol.

This is based on the `quant-refactor/string-spec-registry` branch to keep the series in one line of review. The test itself does not depend on it: it passes unchanged against both the current eager package `__init__` and the lazy `__getattr__` one, which is deliberate, since a compatibility test that encodes one implementation stops being a compatibility test.

## Accuracy Tests

Not applicable: this adds a test and changes no source.

The assertions were checked against mutations rather than assumed to work. Each of the following turns the suite red, and it returns to green when reverted:

| mutation | effect |
| --- | --- |
| drop a config from the registry spec table | 2 cases fail |
| a shim re-exports the wrong class under the name `Fp8Config` | 1 case fails |
| `__getattr__` raises `KeyError` instead of `AttributeError` | 1 case fails |
| rename the `bmm_fp8` target string | 1 case fails |

One earlier mutation attempt is worth recording, because it did not fire: repointing the `"fp8"` registry key at `W8A8Fp8Config` left the suite green. That is a registry-mapping bug rather than a re-export bug, `Fp8Config` still resolved correctly through another entry, and the registry tables are covered elsewhere. The mutation above targets the failure mode this file is actually responsible for.

Result: 5 cases, 76 subtests, passing. The quantization unit directory goes from 186 to 191 passing with the same pre-existing failure set.
