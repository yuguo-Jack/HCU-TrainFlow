# [Fix] Inkling: frame constrained output in native message tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/44716) · state: closed · merged: True

## Original PR description

## Motivation

With `--reasoning-parser inkling`, `response_format` / `regex` / `ebnf` constraints do not follow Inkling's wire format: Inkling frames every message with native tokens (`<|message_model|><|content_text|>…<|end_message|>`), but on `main` the constraint neither waits for the real think-end token nor admits the answer frame. Live on `thinkingmachines/Inkling-NVFP4` @ `06b81b120e`: the answer header is missing, prose or extra data surrounds the JSON, whitespace runs to `max_tokens`, regex payloads repeat (`Yesyes`), and `continue_final_message` + constraint fails 54/54.

## Modifications

Inkling's format knowledge lives with its reasoning detector: `BaseReasoningFormatDetector.get_answer_frame()` returns `None` by default; Inkling's returns an `InklingAnswerFrame` (`parser/answer_frame.py`) owning the framed constraint types, framing token IDs, open-text-block check, the frame's structural tag and the canonical auto-tool tag. `ReasonerGrammarBackend` only composes a detector's frame with the payload grammar; detectors/backends without a frame keep their existing dispatch.

- **Native think-end** (contains #40894): the reasoning-deferred grammar takes think-end IDs from the detector, so Inkling's native `<|end_message|>` (200010) ends thinking; the canonical auto-tool tag skips deferral.
- **Whole-turn frame**: `json` / `regex` / `ebnf` constraints compile into one token-level structural tag — optional thinking message, answer header, payload, `<|end_message|>`. With `continue_final_message`, the payload starts inside the already-open text block.
- **Strict thinking**: the frame caps thinking at the request's `thinking_budget`, else the server's `SGLANG_MAX_THINK_TOKENS` (request overrides server). Distinct budgets compile distinct frames, cached under a normalized key (negatives → unlimited, server value → default key), bounded to 32 variants.
- **xgrammar backend**: framed grammars compile on an uncached `GrammarCompiler` — the cached one mixes token-level structural tags of different shapes (fixed upstream by mlc-ai/xgrammar#943, unreleased; [reproducer](https://github.com/mlc-ai/xgrammar/issues/951#issuecomment-6159764165)). Framing token IDs are reserved from matching text in the framing compiler only.

Split out of #42844, which moves Inkling prompt rendering and output parsing to `tml-renderers` and builds on this change. Works with `main`'s existing Inkling renderer and parsers.

Devbox: 4x GB300, `thinkingmachines/Inkling-NVFP4`, cookbook GB300 NVFP4 TP4 recipe plus `--reasoning-parser inkling --tool-call-parser inkling` (strict rows add `--enable-strict-thinking` with `SGLANG_MAX_THINK_TOKENS=48`).

\* The 6 misses are effort-high `ebnf` `[0-9]+` answers that keep adding digits (`426`) — a digits-only grammar cannot end the sentence, a grammar/prompt mismatch, not framing.

Unit tests (xgrammar 0.2.7): `unit/constrained/` + `unit/function_call/` 775 passed; recipe incl. `test_serving_chat.py` 271 passed @ `4c0c9a0530`. The detector-ownership refactor at that head is behavior-identical to the pre-refactor head: compiled grammars, dispatch and per-step token masks match on 200 probe cases (Inkling and Qwen3 detectors, strict on/off, `json`/`regex`/`ebnf`/`structural_tag`, plain and continuation prompts, five budgets).

Unconstrained requests without strict thinking do not take the changed paths.

## Speed Tests and Profiling

Not performance-related. Framed grammars compile once per distinct constraint (and budget variant); the compiled grammar is cached as before.
