# [DSv4.1] Run the candidate indexer on SM12x through the paged decode path

[Upstream PR](https://github.com/sgl-project/sglang/pull/42371) · state: open · merged: False

## Original PR description

Fixes #42364.

## Motivation

DeepSeek-V4.1 does not start on SM12x. `make_candidate_indexer` sends every GPU with compute capability >= 10 down the SM100 branch, and that branch requires DeepGEMM's paged sparse MQA logits. Those are SM100-only (`DEEPGEMM_PAGED_SPARSE_MQA_LOGITS` needs `DEEPGEMM_BLACKWELL`), so on SM120/SM121 the attention backend raises at init. The traceback is in #42364. I hit it on four DGX Spark (GB10, SM121) nodes running TP4.

Hopper already has what SM12x needs. It gets the dense-blocks scheme for prefill and decode, and since #41251 its decode scores the index-K pool with the Triton `fp4_index_logits_paged` kernel, builds the candidate mask once at the source layer and selects with the JIT top-k v2. None of that is Hopper-specific. SM12x also already uses the same 64-slot index-K pages, because `dsv41_index_page_size()` returns 64 whenever the sparse API is missing.

SM12x is one more backend for #40574; it was not on that list.

## Modifications

- `dsv4/v41_indexer/__init__.py`: when DeepGEMM's paged sparse MQA logits are missing and the platform is SM12x, `make_candidate_indexer` returns the dense-blocks backend for prefill and decode instead of raising. SM100 without the sparse API still raises as before.
- `dsv4/v41_indexer/scoring.py`: `decode_scores` takes the paged path on SM12x as well as on SM90.

The second line matters for speed. Without it SM12x starts, but every candidate layer scores all compressed positions up to the CUDA-graph capacity on each decode step. The numbers are under Speed Tests.

Prefill does not change. SM12x already ran prefill through the dense-blocks scheme with DeepGEMM's flattened-K logits (`_use_deep_gemm_prefill()` is true there).

Tests:

- `test/registered/unit/layers/test_dsv41_candidate_blocks.py`, new `TestCandidateIndexerGating` (CPU): SM12x without the sparse logits gets the dense-blocks backend, and SM100 without them still raises. The SM12x case fails on main with the RuntimeError from #42364.
- `test/registered/kernels/ops/attention/test_fp4_indexer.py`: `test_hopper_indexer_backends_replay` is renamed to `test_paged_indexer_backends_replay` and now also runs on SM12x. It captures the full top-k, source and consumer decode in one CUDA graph, checks that all three go through the paged scorer, and compares pages and raw indices against a torch reference while lengths and mappings change between replays.

## Accuracy Tests

Hardware: four DGX Spark (GB10, SM121), TP4 over a QSFP ring, driver 595.84, CUDA 13.0. The GPU clocks are locked to 300-2000 MHz on all four nodes (`nvidia-smi -lgc 300,2000`; GB10 can boost to 3003 MHz), so absolute tok/s will be lower than on a stock box. Both arms below ran at the same clocks. Image: `lmsysorg/sglang:nightly-dev-cu13-20261003-65f75914` with the python tree replaced by this branch.

Kernel tests on one GB10, plain SGLang:

| tree | `test_paged_indexer_backends_replay` | `TestCandidateIndexerGating` |
|---|---|---|
| main (00bcc25f6c) | fails (ratio 1 and 2) | fails (RuntimeError) |
| this PR | passes | passes |
| this PR, `scoring.py` line reverted | fails (ratio 1 and 2) | passes |

All of `test_fp4_indexer.py` with this PR on GB10: 99 passed, 36 skipped (the SM100-only vectorized prefill cases), 0 failed.

End to end, DeepSeek-V4.1-Flash, TP4 on the four GB10s. One thing about this stack: the model does not fit four GB10s on plain SGLang (it needs NVMe-offloaded Engram tables, among other things), so it runs through a local serving recipe, MiaAI's DGX Spark TP4 recipe. Its adapters patch weight loading, the MoE path (b12x) and DSpark verify. I turned off every adapter that pins engine sources. The kernel tests above do not go through the recipe.

- main: the server dies at backend init (#42364).
- This PR (together with #42368, see the note at the end):
  - GSM8K, all 1319 (`sgl-eval 0.1.2 run gsm8k --no-thinking --temperature 0 --seed 42 --max-tokens 2048 --num-threads 16`): 1276/1319 (0.9674), 1 truncated, 0 errors. #41251 reports 1276 to 1278 on H200 and 1277 to 1279 on GB300 at the same cap.
  - RULER2 at 64K (`--ruler2-seq-len 65536 --ruler2-dataset-size 10 --no-thinking --temperature 0 --seed 42`, all 12 subtasks): 91.11, 0 errors, 0 truncated (average input 62,426 tokens). At 64K the context is longer than the 16,384 compressed positions (2048 blocks x 8) the candidates cover, so the consumers really select inside the candidate blocks.

## Speed Tests and Profiling

Decode on the same stack and the same prompts: code text with a fresh first line for every request, 512 output tokens, greedy, thinking off. "Non-paged" is this PR with the `scoring.py` line reverted, so SM12x runs the dense-blocks scheme on the non-paged dense scores.

Single request, server freshly started for each arm, two runs per length. Decode is the mean of the two runs, TTFT the second run.

| input | decode tok/s, this PR | decode tok/s, non-paged | TTFT s, this PR | TTFT s, non-paged |
|---|---|---|---|---|
| 16K | 66.1 | 46.1 (+43%) | 4.4 | 4.1 |
| 64K | 65.8 | 48.1 (+37%) | 16.4 | 16.2 |
| 128K | 57.9 | 44.6 (+30%) | 34.9 | 36.0 |

TTFT is the same in both arms, as expected: the change does not touch prefill.

## Note on #42368

With the FlashInfer version main pins (0.7.0.post1), DeepSeek-V4.1-Flash on SM12x with attention TP > 1 also fails at decode CUDA graph capture, for an unrelated reason: #42367, fixed in #42368. The end-to-end runs above include that fix. The kernel tests do not need it.
