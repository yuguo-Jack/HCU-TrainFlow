# [PD] Fix pd_dcp_gather grid.y overflow and vectorize pack gather to 8-byte lanes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43782) · state: open · merged: False

## Original PR description

## Motivation

- **Crash:** `copy_mla_rows_into_pack` launches its gather kernel with
  `grid=(num_layers, cdiv(n*max_item_len, 1024))`, putting the n-dependent
  dimension on `grid.y` (hardware cap 65,535). Any pack above **58,253
  rows** (at 1152 B/row) fails launch with
  `RuntimeError: Triton Error [CUDA]: invalid argument`, killing the
  mooncake transfer worker thread silently and stalling cross-node KV
  transfer with zero error logs. This makes chunked-prefill-size 65536
  unusable while 16384 works, for reasons unrelated to model or memory.
- **Throughput:** the upstream kernel moves **one byte per lane**; measured
  ~510-550 GB/s on B300 — far from memory-bound, so the pack step
  needlessly inflates PD transfer latency for large windows.

## Modifications

- **Swap grid dims:** blocks on `grid.x` (limit 2^31-1), layers on
  `grid.y` (a few dozen at most). Kernel logic unchanged; no div/mod.
- **Vectorize to 8-byte lanes:** when every `item_len` and
  `src_item_len` is 8-aligned (MLA item lengths are 1152 B — the common
  case), gather through an int64 view of the pack buffer. Non-8-aligned
  item lengths fall back to the (dim-swapped) byte path, preserving
  original behavior.
- **Opt-in int64 addressing:** enabled only when the launch size actually
  approaches 2^31, avoiding int64's cost in the common case.
- Merged with the upstream `src_row_stride` / `src_token_item_lens`
  parameters (strided source rows are honored by both paths).

## Accuracy Tests

- `test/registered/kernels/test_pd_dcp_gather.py` (CUDA, registered
  `base-b-kernel-unit` / `1-gpu-large`): byte-exact pack vs a reference
  gather at n = 1,000 / 58,253 / 100,000 / 300,000 rows (2 layers x
  1152 B); strided-source case (`src_item_len=1536`); byte-path case with
  `item_len=1001` (non-8-aligned); a direct-launch case compiling and
  running the `USE_INT64=True` branch. All 7 cases pass. The upstream
  kernel crashes at n=100,000 with the exact production signature,
  validating the test.
- Production validation: full-model (93-layer Kimi-K3) PD+DCP rounds at
  chunk 65536 (2x 30-min, c32, 2,436 requests, 0 errors, 0 transfer
  failures) with this kernel in the transfer path, plus a 12-question
  gsm8k probe afterwards (acc=1.000, invalid=0.000).

## Speed Tests and Profiling

**Setup.** B300 GPU, 2 layers x 1152 B/row (production MLA shape),
CUDA-event `do_bench`, min over 50 reps, idle GPU, 5 repeated rounds per
point.

| rows | original (upstream) | this MR (vec8) | vs original |
|---|---|---|---|
| 16,384 | ~509 GB/s | 1,872-1,887 | **+268%** |
| 32,768 | ~538 | 2,262-2,311 | **+327%** |
| 58,253 | ~549 | 2,577-2,591 | **+372%** |
| 100,000 | **CRASH** (grid.y=112,500) | 2,786-2,792 | — |
| 300,000 | **CRASH** (grid.y=337,500) | 3,004-3,005 | — |

Block-size sweep for the vec8 path: 512 elements/block wins (2,369 /
**3,005** / 2,336 GB/s at 300K rows for 256/512/2048). Grid-swap-only
(V2) lands at ~488-528 GB/s, i.e. correctness without the throughput
gain; 1D-flatten variants measured -12~-14% vs original in earlier
rounds.
