# [Perf] [Intel] gemma4: Fuse BF16 PLE residual add and layer scale

[Upstream PR](https://github.com/sgl-project/sglang/pull/44925) · state: open · merged: False

## Original PR description

## Motivation

Gemma4's per-layer-input (PLE) tail stores a BF16 residual-add result before reading it again for the layer-scalar multiply. Fuse those two operations while retaining the BF16 add rounding and both existing norm calls.

Stacked on #44919, parent `ea813bd72eb6a14b988311d5b778371bdf848050`. Review the six-file child diff: [parent → this head](https://github.com/sgl-project/sglang/compare/ea813bd72eb6a14b988311d5b778371bdf848050...a3c379de38ffa12a31c94c07b2a9f88c28f263f6).

## Modifications

- Add the lazy public XPU operator `sglang.kernels.ops.elementwise.bf16_add_then_scale`. It casts the add to BF16 before multiplying by the current BF16 `[1]` scalar; the fixed Triton kernel uses 1,024 elements and four warps.
- Select it for the unquantized Gemma4 dense PLE path on B70 at TP1, only for contiguous BF16 `4096 × 1536` activations and PLE width 256 under no-grad. Keep the existing module calls, norm hooks/delegated methods, shared LUT owner, and unsupported-shape/dtype/backend/grad fallbacks.
- Add registered operator/namespace tests and an actual decoder-tail integration test. No native-kernel or parent-stack implementation changes.

## Accuracy Tests

- **75 namespace tests passed** on the actual featureful XPU environment, including lazy import and backend capability checks.
- **3 operator tests and 40 subtests passed**: all 65,536 BF16 input patterns with finite, signed-zero, subnormal, infinity and NaN operand/scalar cases; required intermediate rounding; fullgraph; poisoned replay with changed inputs and the same scalar storage; contract rejection cases. Finite values, signed zeros and infinities match bitwise; NaN classification matches without a NaN-payload guarantee.
- **1 actual decoder-tail test passed**, using the pinned Gemma4 E2B config and synthetic weights: exact eager/fullgraph output, changed-input/scalar graph replay, norm hooks/delegation, and backend/grad/shape/dtype fallbacks.
- Pre-commit passed on all six changed files.
- A separate whole-stack sanity check compared baseline `797dbef` (before the prefill optimization stack) with this head using official `sgl-eval 0.1.3`, GSM8K-200, temperature 0 and seed 42. Both scored **160/200**, with three truncated generations each; 187 generations were identical, with one correctness loss and one win. All 400 request payloads matched the same 200 pinned cases. This comparison includes the earlier prefill changes, does not isolate PLE, and does not specifically exercise the 4,096-row specialization.

## Speed Tests and Profiling

An untimed CPU+XPU trace of the actual `M=4096` decoder tail shows **11 → 10 device kernels**: exactly the final BF16 add and scalar multiply become one `_bf16_add_then_scale` kernel. Both RMSNorms, all three GEMMs, native gate/up, GELU and PLE gating-multiply counts are unchanged. Outputs match bit-for-bit.

One captured cold microbenchmark on B70, `4096 × 1536`, no-grad with inference mode disabled, compares the actual Torch BF16 add followed by the BF16 `[1]` scalar multiply against the public fused operator:

| Operator | Mean device time |
|---|---:|
| Torch add then multiply | 137.042344 µs |
| Fused add then scale | 72.669434 µs |

**46.973% lower device time**, with all six mirrored rounds favoring the fused operator. The run rotates 32 physical banks with 768 MiB of disjoint input/residual storage, preserves every backend/bank output, and validates poisoned replay after independent input, residual and scalar changes. Source and actual mapped libraries were verified after timing. This is one microbenchmark process and seed, without a repeat or tuning sweep.

Actual Gemma4 E2B serving was then compared in **one A/B run**, parent `ea813bd7` versus this `a3c379de` head, on the same B70 at TP1/BF16 with NEXTN and the full graph backend. Both arms used the same native sidecar and original featureful wheel; this is production-source sidecar validation, not a full-wheel-serving claim. Global and request seeds were 42. Each workload had four warmups and 24 measured samples per arm, with an uncached 4,096-token prompt and one generated token per request.

| Serving workload | Parent mean | This head mean | Observed reduction |
|---|---:|---:|---:|
| 1 × 4,096-token prompt | 184.395361 ms | 182.885776 ms | 0.818668% |
| 4 queued × 4,096-token prompts | 726.265363 ms | 720.257784 ms | 0.827188% |

Separate actual-server preflights, retired before timing, prove **0 → 35 fused PLE kernels** and removal of 35 BF16 adds plus 35 scalar multiplies, with the exact removed CPU shapes. All other device-kernel name counts match, including the existing 20-wide/15-narrow native MLPs, norms, GELU and PLE gating. All 120 paired timed completions match text/IDs; all 16 compatibility cases match text/IDs and every returned logprob field. Source, sidecar, all 89 mapped native-library records and process cleanup were verified.

The c8 control reported mean TPOT 6.262457 → 6.222039 ms, with 58/64 generated texts identical, 128 output tokens per request and zero errors. **No decode gain is attributed to this change.** This is a single A/B observation, without B/A, a repeat or a control-self drift estimate. An earlier interrupted partial control is excluded; results use only the complete A/B run. The passed preflights were reused with hash-bound raw-trace verification rather than replayed.

**Draft limitation:** model-quality parity for this change is not established; the parent stack's long-context quality uncertainty remains unresolved. The numerical tests, short serving comparisons and equal GSM8K sample scores do not establish universal generation equivalence or quality parity.
