# [Perf] disaggregation: Send deferred-allocation Success from the transfer worker

[Upstream PR](https://github.com/sgl-project/sglang/pull/48204) · state: closed · merged: False

## Original PR description

> Depends on #45337 (`prefill_complete` with a pipeline-parallel prefill). This PR's own change is its last commit, `[PD] Deferred allocation: send Success from the transfer worker`.

## Motivation

`--disaggregation-decode-allocation-policy prefill_complete` (#40703) makes PD (prefill/decode) disaggregated decode reserve a request's KV slots only after prefill finishes. Under it, prefill tells decode that a KV transfer succeeded only from `sender.clear()`, when the prefill scheduler releases the request. That ordering exists so decode never reuses a bootstrap room that prefill still holds: after a true retraction, decode resumes the request by asking the same prefill server to recompute it under the same bootstrap room.

With a PP (pipeline parallelism) prefill (#45337), the release waits for the stages' consensus poll, and with attention DP (data parallelism) for the scheduler's next synchronized iteration. Decode cannot start decoding until it hears Success, so the release delay lands in TTFT (time to first token), and decode holds the request's KV slots for that time without using them. Under `early`, the transfer worker sends Success as soon as the transfer ends.

On a GLM-5.2 deployment with a PP4 prefill at 0.8 req/s, `prefill_complete` adds 0.82-0.87 s to mean TTFT relative to `early`. This PR removes 0.70-0.72 s of that and halves the decode KV reserved for requests whose KV has not arrived yet. The remaining 0.12-0.15 s is decode's reservation handshake, which `prefill_complete` runs after prefill; #48205 overlaps it with prefill.

## Modifications

The transfer worker now sends Success when the transfer ends, as under `early`, for the deferred policy too. Decode may then retract the request and resume it, reusing its bootstrap room, before prefill has released it. Prefill keeps that safe (`disaggregation/common/bootstrap.py`, `common/conn.py`, `prefill.py`):

- `DeferredBootstrap.conclude()` commits the room's success under the room lock before Success goes out. It fails when a failure or cancellation already won; the worker then sends nothing, and the winner notifies decode.
- A decode registration that arrives while the room is concluded belongs to the room's next request. It is kept and applied when the sender releases the room.
- A recompute that reaches prefill before that release waits in `PrefillBootstrapQueue.room_waiters` and is enqueued once the room is free. Under PP every stage releases and admits in the same loop iteration, so the stages' queues agree. An `AbortReq` retires matching waiters; the waiters are listed in `Scheduler.request_lists()` (so a waiting recompute keeps the worker from being idle for a cache flush or weight update), and the load snapshot counts them as bootstrapping.
- A failure after Success concerns a request decode already holds: it neither notifies decode nor cancels the room's next request. Decode's ABORT goes through the new `DeferredBootstrap.cancel()`, which on a concluded room cancels the next request, the only one decode can still abort.
- The sender releases a concluded room only after the transfer worker's room cleanup, including after an abort that caches `Failed`, so the old worker cannot erase a recompute's transfer state.
- Docs: the PD disaggregation page describes the new Success timing.

## Accuracy Tests

No accuracy eval was run. The change touches no model or kernel code; it changes when decode learns that a KV transfer finished. The GPU e2e cases compare outputs: a multi-chunk request returns identical tokens and logprobs on a repeat, and a request retracted three times through `pause_generation(mode="retract")` never rewrites tokens or logprobs it already emitted. They pass with a PP2 prefill and with an attention-DP2 + EP2 prefill.

## Speed Tests and Profiling

**Setup.** GLM-5.2 NVFP4 with random weights (`--load-format dummy`) on GB300, 8 GPUs per run: one prefill node (TP1 x PP4 with the PP scheduler, or DEP4 = TP4 with attention DP4 and EP4 with the overlap scheduler) and one DEP4 decode node, Mooncake over NVLink, MTP with simulated acceptance, a Dynamo frontend with KV routing, chunked prefill 16384. An open-loop client sends prompts of 8k-40k random words (about 37-40k tokens at p50) with 128 output tokens, as Poisson arrivals in three 180 s phases at 0.25, 0.5 and 0.8 req/s, with the same seed in every run, so request i of a phase is the same request in every run. Each arm ran twice. "Before" is #45337 alone; "after" adds this PR. Every run completed with 0 errors.

## Known limitations

- A retraction recompute that reaches prefill before prefill has finished streaming the original request's output is rejected as a duplicate rid (`TokenizerManager` still tracks the original), and decode then aborts the resumed request. `early` already has this window, since its Success also comes from the transfer worker; this PR gives `prefill_complete` the same window, which with a PP prefill lasts until the stages' release consensus. Under the deferred policy it takes a `pause_generation(mode="retract")` followed by `continue_generation` within that window: the deferred policies reject the DeepSeek-V4 KV pools, the other source of recomputing retractions. Giving the recompute its own rid (derived from the original, so prefix-matched aborts still reach it) closes the window; that is left to a separate PR.
- The speed results are from one model and topology family at low decode load.
