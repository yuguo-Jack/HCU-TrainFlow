# [WIP][Feat] dflash: Serve MoE FFN drafts from the config's HF MoE fields

[Upstream PR](https://github.com/sgl-project/sglang/pull/47181) · state: open · merged: False

## Original PR description

## Motivation

SpecForge ([sgl-project/SpecForge#1031](https://github.com/sgl-project/SpecForge/pull/1031)) trains DFlash-family drafts (DFlash, DFlash2, DSpark) whose FFN is a mixture of experts. The export stacks the experts as `experts.gate_up_proj` [E, 2I, H] / `experts.down_proj` [E, H, I] and may ship a trained router bias (`gate.expert_bias`, DeepSeek-style: it shifts which experts are picked, never their weights).

SGLang's draft classes only build the dense `DFlashMLP`, and `DFlashDraftModel.load_weights` ignores unknown tensors, so such an export starts a server whose draft FFNs are uninitialized. This PR makes the DFlash family's FFN config-driven: a draft config with routed experts, in the HF conventions the Qwen, DeepSeek and Mixtral families share, is served by the existing classes (`DFlashDraftModel`, `DFlash2DraftModel`, `Qwen3DSparkModel`, ...) with no new architecture names and no dependency on a SpecForge model family.

## Modifications

`python/sglang/srt/models/dflash.py`:

- `parse_dflash_moe_spec(config)`: the MoE FFN the config describes, or `None` for a dense draft. Fields: `num_experts` / `n_routed_experts` / `num_local_experts`, `num_experts_per_tok`, `moe_intermediate_size` (falls back to `intermediate_size`), `hidden_act` (silu), `scoring_func` (softmax or sigmoid), `norm_topk_prob`, `n_group` / `topk_group` / `topk_method` (group-limited top-k), `routed_scaling_factor`, and `shared_expert_intermediate_size` (Qwen's sigmoid-gated shared expert) or `n_shared_experts` (DeepSeek's summed ones).
- `DFlashMoE`: `ReplicatedLinear` router, SGLang's `TopK` for that routing, `get_moe_impl_class(quant_config)` (`FusedMoE`) for the experts, `Qwen2MoeMLP` as the shared expert, one TP all-reduce over the routed and shared partial sums. The router bias is decided by the checkpoint alone: `gate.expert_bias` or `gate.e_score_correction_bias` loads into an fp32 buffer and re-creates the `TopK` with it as `correction_bias`; with plain softmax scores the biased top-k runs in torch via `custom_routing_function`, because the fused softmax routers (`moe_fused_gate`) keep softmax routing bias-free. No bias in the checkpoint means SGLang's unbiased top-k.
- `build_dflash_ffn` picks `DFlashMoE` over `DFlashMLP` when the config has routed experts; `DFlashDecoderLayer` builds its FFN through it, so DFlash2's conv wrapping and DSpark inherit it unchanged.
- Loading: `DFlashDraftModel.load_weights` hands `layers.{i}.mlp.*` of MoE layers to the block. Stacked and per-expert expert names go through `FusedMoE.weight_loader` (TP/EP sharding stays its job); `shared_expert.*` and `shared_experts.*` both map to the shared expert. It refuses MoE tensors aimed at a dense layer, a shared expert or gate the config does not describe, shape mismatches, and (`check_loaded`) a partially loaded FFN.
- Guards: `--moe-a2a-backend` other than `none` (the draft runs the standard dispatcher), `flashinfer_trtllm_routed` together with a router bias (in-kernel routing would drop it), non-silu experts.

Tests:

- `test/registered/unit/spec/test_dflash_moe_ffn.py` (CPU): the spec from Qwen-style and DeepSeek-style fields, the dense/MoE switch, stacked vs per-expert vs `model.`-prefixed loading against `FusedMoE`'s own loader, the DeepSeek names, the DSpark path, every refusal, the biased softmax routing math.
- `test/registered/unit/spec/test_dflash_moe_ffn_cuda.py` (nightly, 1 GPU): the block against a torch reference: biased and plain softmax top-k, sigmoid top-k with the DeepSeek bias, gated and summed shared experts.

## Speed Tests and Profiling

Dense drafts build the same modules as before. MoE drafts run `FusedMoE` (the Triton runner under `--moe-runner-backend auto` for bf16; no tuned config exists yet for `E=8,N=1536` on H200, the log says so).

Width-8 concurrency sweep on one H200 (Qwen3-8B target, `--speculative-dspark-block-size 8`, `--max-running-requests 256`, graphs captured up to bs 256, 4x concurrency requests of 256 tokens each), time per verify step from each request's `e2e_latency / spec_verify_ct`:

| concurrency | 1 | 8 | 32 | 64 | 128 | 256 |
|---|---|---|---|---|---|---|
| dense 12288 draft (step 39000), ms/step | 8.2 | 11.0 | 18.1 | 27.5 | 45.3 | 81.6 |
| MoE 8x1536 top-1 draft (step 43000), ms/step | 8.1 | 11.2 | 18.0 | 26.8 | 43.9 | 78.9 |
| dense, total tok/s | 693 | 3564 | 8389 | 11607 | 14349 | 16207 |
| MoE, total tok/s | 694 | 3472 | 8418 | 11669 | 14834 | 16730 |

At matched acceptance length (6.54 vs 6.60 on this prompt set) the MoE draft's step time and total throughput match the dense draft's at every concurrency (within 3%); the FFN is a small part of a step dominated by the target's verify, so the MoE FFN costs nothing extra in this path.
