# [Fix] kda: Keep FlashInfer prefill off its grouped kernel's bf16/flat-dt_bias contract

[Upstream PR](https://github.com/sgl-project/sglang/pull/45018) · state: closed · merged: True

## Original PR description

## Motivation

Serving Kimi-K3 with `--linear-attn-prefill-backend flashinfer` (the default on SM100/SM103) and the radix cache enabled crashes the scheduler in two ways, both coming from the same place: FlashInfer's `recurrent_kda` picks its **grouped recurrent kernel** instead of the flash prefill kernel whenever no sequence in the packed batch extends more than one token. That kernel has a stricter tensor contract than the flash prefill kernel, and SGLang's wrapper did not honor it.

1. **`dt_bias` layout.** The grouped kernel binds `dt_bias` as a flat `[H*K]` tensor with a unit leading stride (`mark_layout_dynamic(leading_dim=0)`). The wrapper passed a `[H, 128]` view, so the first extend that reused a cached prefix failed at compile time:
   ```
   RuntimeError: Expected strides[leading_dim] == 1, but got 128.
   ```
2. **State pool dtype.** The grouped kernel loads the recurrent state pool into bf16 registers. The KDA pool is fp32, so a packed batch where every sequence extends exactly one token (retracted requests re-entering with a fully cached prefix, as happens under memory pressure with long inputs) fails at compile time:
   ```
   NotImplementedError: autovec_copy only supports equal source and destination element type bit widths, got Float32 and BFloat16
   ```
   Multi-token extends take the flash prefill kernel, which accepts the fp32 pool, so short-prompt workloads never see this. The existing reroute to Triton only covered a single one-token sequence (`T == 1`).

Neither issue is addressed by the flashinfer-python 0.7.2 bump: its grouped kernel keeps both the flat `dt_bias` binding and the bf16 state load.

## Modifications

- `kda_flashinfer_prefill.py`: pass `dt_bias.reshape(-1)` (flat `[H*K]`) to `recurrent_kda`. Same values, same order; only the view changes.
- `kda_backend.py`: `KDAKernelDispatcher.effective_extend_kernel` takes the packed sequence count and routes any batch with `num_tokens <= num_seqs` to the Triton KDA kernel (generalizing the previous `num_tokens <= 1` rule). Both call sites (`extend` and the track-snapshot capability check in `KDAAttnBackend.forward_extend`) pass `query_start_loc.numel() - 1`.
- `test/registered/unit/layers/attention/linear/kernels/test_kda_flashinfer_prefill.py` (new, `base-a-test-cpu`): three CPU cases.
  - `dt_bias` reaches the kernel flat, unit-stride, float32, values in the layer's order. The `recurrent_kda` stand-in enforces the grouped kernel's leading-stride contract, so the pre-fix `[H, 128]` view fails with the production error.
  - A packed batch of four one-token sequences dispatches to Triton; FlashInfer is not called.
  - A batch where one sequence extends two tokens stays on FlashInfer (guards against the reroute widening into a blanket Triton fallback).

  Verified red on the pre-fix code (dt_bias case: `Expected strides[leading_dim] == 1, but got 128`; one-token case: FlashInfer called instead of Triton) and green on the fix.

## Accuracy Tests

Both bugs are hard crashes, so the fix is accuracy-neutral by construction: the flat `dt_bias` is a view of the same parameter, and one-token-per-sequence batches now run on the same Triton kernel that already served the `T == 1` case. 

## Speed Tests and Profiling

No impact on ordinary prefill: the FlashInfer flash prefill kernel is still selected whenever any sequence extends more than one token. The reroute only affects batches consisting solely of one-token extends, which previously crashed.
