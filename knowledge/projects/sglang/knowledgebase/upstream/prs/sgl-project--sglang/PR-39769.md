# Skip fully-masked KV tiles in sliding-window extend attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/39769) · state: closed · merged: True

## Original PR description

## Motivation

On a sliding-window layer, the stage-2 loop in `_fwd_kernel` sweeps the extend KV from 0:

```python
for start_n in range(0, extend_end, BLOCK_N):
```

The window mask inside that loop keeps `(q, kv)` only when `q <= kv + SLIDING_WINDOW_SIZE`, so every tile lying entirely below `cur_block_m * BLOCK_M - SLIDING_WINDOW_SIZE` is fully masked and contributes nothing.

Those tiles do not read K/V and do not run the dot — `SKIP_TILE` already guards that. What they still pay, once per tile, is the cost of establishing that they contribute nothing: building `final_mask` (the causal compare, the window compare, the `&`), and then the `[BLOCK_M, BLOCK_N]` cross-wave `tl.max` reduction that computes `SKIP_TILE` itself.

On a long extend with a small window that is the majority of the loop. At `extend_len = 8192` and `W = 127`, the last M block's floor sits at roughly `8192 - 127`, so almost every iteration is spent proving that the tile is empty.

### Where this kernel runs by default

The Triton backend is the default attention backend, without any flag, for:

- **Gemma 4** (`Gemma4ForConditionalGeneration`): its model override selects `triton` whenever `--attention-backend` is unset, on ROCm and on CUDA other than SM100 (which gets `trtllm_mha`). The server logs `Use triton as default attention backend for Gemma4`. 25 of the 30 layers of `gemma-4-26B-A4B-it` are sliding-window layers (`W = 1024`, `head_dim = 256`).
- **OLMo 3** (served as `Olmo2ForCausalLM`) and **EXAONE 4.0** checkpoints with a sliding-window pattern (e.g. `EXAONE-4.0-32B`): `triton` by default on ROCm and on CUDA below SM80.

It also runs for any sliding-window model served with `--attention-backend triton`.

## Modifications

Start the loop at the `BLOCK_N`-aligned tile that contains the window floor:

```python
extend_start = 0
if SLIDING_WINDOW_SIZE > 0:
    extend_start = (
        tl.maximum(cur_block_m * BLOCK_M - SLIDING_WINDOW_SIZE, 0) // BLOCK_N
    ) * BLOCK_N
for start_n in range(extend_start, extend_end, BLOCK_N):
```

The bound is derived from the mask predicate rather than estimated. The kernel returns early when `cur_block_m * BLOCK_M >= cur_seq_len_extend`, so `offs_m = 0` is always a live row and the smallest query index in the block is exactly `m0 = cur_block_m * BLOCK_M`. A skipped tile satisfies `start_n + BLOCK_N <= floor_aligned <= m0 - W`, hence its largest key index `start_n + BLOCK_N - 1 < m0 - W`, so the window mask is false for every one of its elements.

It is also tight at tile granularity: the preceding tile would need `floor_aligned >= m0 - W + 1` to hold a surviving element, which contradicts `floor_aligned <= m0 - W`. Nothing that can contribute is skipped, for any `BLOCK_M`/`BLOCK_N`.

`SLIDING_WINDOW_SIZE` is a `tl.constexpr`, so a full-attention layer loses the branch at trace time and its loop is unchanged. `extend_start` is a multiple of `BLOCK_N`, so `tl.multiple_of(start_n, BLOCK_N)` stays valid. A custom mask or the non-causal path only adds conjuncts, which narrow the mask further, so the bound remains sound there. Under the HIP compact grid `cur_block_m` is still the per-sequence tile index, so the derivation is unaffected.

`test/registered/attention/unittests/swa/test_triton.py` gains three cases with extend lengths above `BLOCK_M` and windows below it — no prefix; a prefix with a window that is not a tile multiple; a window landing exactly on a tile boundary — so some query tile starts past the window and the bound takes effect. Every pre-existing SWA extend case keeps the extend length under `BLOCK_M`, where the loop always starts at tile 0.

## Accuracy Tests

MI355X (gfx950, 256 CU), ROCm 7.2.0, torch 2.9.1, Triton 3.7.0. sglang `main` @ `7ff3a11284` with `sglang-kernel` 0.4.9 built from the same tree and transformers 5.19.0.

**Unit tests.** `test/registered/attention/unittests/swa/test_triton.py` and `.../dense/test_triton.py`: 15 passed, 2 skipped, 58 subtests passed.

**Kernel output is bitwise identical.** 21 configurations (12 sliding-window, 4 full-attention, 5 where the bound never fires) at `B=32, H_Q=64, H_KV=8, D=128`, bf16, causal. Each run hashes its inputs as well as `o_extend`, so the output comparison is only accepted when the inputs provably matched: **21/21 inputs identical, 21/21 outputs bitwise identical.**

**End to end, `gemma-4-26B-A4B-it`, default server args** (no `--attention-backend`; the server resolves `triton`):

- Greedy parity: 32 chat requests sent one at a time to a `main` server and a server with this PR, prompts of 3,968–18,164 tokens (all longer than the 1024-token window, so the bound fires), 128 output tokens, temperature 0. **Outputs identical: 32/32.**
- GSM8K, `python -m sglang.test.run_eval --eval-name gsm8k` (chat API, 5-shot, greedy), all 1319 questions, two runs per server:

| | Run 1 | Run 2 |
|---|---|---|
| `main` | 0.960 | 0.959 |
| This PR | 0.954 | 0.956 |

The per-question standard deviation is 0.20, so the standard error of one run is about 0.0055 and the gap is within run-to-run noise. Concurrent batches change the numerics of other kernels between runs; the parity check above runs one request at a time and shows identical outputs.

## Speed Tests and Profiling

### Kernel

`triton.testing.do_bench(warmup=100ms, rep=500ms, return_mode="median")`, minimum over 7 repetitions, one idle GPU. Inputs come from `_build_batch` in `benchmark/kernels/sliding_window_attention_triton/bench_triton_swa_kernel.py`; `extend_attention_fwd` is called the way `triton_backend` calls it, including `extend_seq_lens_cpu`, so the HIP compact ragged grid is exercised. (That file's own `_run_triton` predates the `k_scale`/`v_scale` parameters, and `sglang.benchmark.bench_utils` imports `flashinfer`, which has no ROCm build.) `gemma-4-26B-A4B-it`, `python -m sglang.bench_one_batch` with default server args (the attention backend resolves to `triton`), `--output-len 4`, one MI355X. Minimum of 4 alternating runs per arm.

|---|---|---|---|---|
| 1 | 2048 | 0.0505 | 0.0496 | −1.7% |

| 1 | 16384 | 0.5389 | 0.4952 | **−8.1%** |

### Reproduce

```bash
MODEL=google/gemma-4-26B-A4B-it

# prefill latency
python -m sglang.bench_one_batch --model-path $MODEL \
  --batch-size 1 4 --input-len 2048 8192 16384 --output-len 4

# serving
python -m sglang.launch_server --model-path $MODEL --port 30000
python -m sglang.bench_serving --backend sglang --port 30000 --model $MODEL \
  --dataset-name random-ids --random-input-len 16384 --random-output-len 16 \
  --random-range-ratio 1.0 --num-prompts 16 --max-concurrency 1

# accuracy
python -m sglang.test.run_eval --port 30000 --eval-name gsm8k --num-examples 1319
```

Only MI355X was measured. The change is not ROCm-specific, so CUDA runs of the Triton backend take the same bound; their correctness is covered by the unit tests above in CI.
