# [Fix] Honor --max-total-tokens for unified Mamba memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/42678) · state: open · merged: False

## Original PR description

## Motivation

Fixes #42652.

With unified memory enabled for hybrid Mamba models, the shared byte pool can expose far more FULL-token capacity than the configured `--max-total-tokens`. The scheduler used that physical view for admission and `/v1/loads`, so active FULL KV usage could exceed the configured logical limit (52,639 tokens observed with a limit of 16,384).

## Modifications

- Keep the allocator's existing physical shared-byte budget for coordinating FULL KV and Mamba state allocations.
- Add a separate DCP-aware logical FULL-token capacity derived from `--max-total-tokens`.
- Enforce the logical budget during prefill admission, running-request headroom accounting, decode capacity checks, and allocation-time eviction.
- Report logical capacity and usage through pool statistics and validate it in scheduler leak invariants.
- Add focused regressions for logical-vs-physical accounting, ignore-EOS headroom, decode capacity, DCP widening, and stats/invariant behavior.

## Accuracy Tests

Not applicable to model-output accuracy: this changes scheduler admission and memory accounting, not model forward code or kernels.

Serving correctness was exercised on an NVIDIA A100-SXM4-40GB with `ibm-granite/granite-4.0-h-tiny`: all 48 concurrent long-generation requests completed with HTTP 200, with no traceback, scheduler-invariant, memory-leak, or CUDA-error signatures.

After rebasing onto `ed75fe67f1`, the same 48-request workload was repeated on an NVIDIA A10. All 48 requests completed with HTTP 200, zero of 1,589 load samples exceeded the configured cap, and the server reported no error signatures.

Focused CPU tests on the GPU host:

- Changed scheduler/allocator test modules: **159 passed, 702 subtests passed**.
- Existing DCP logical-capacity and unified-byte-budget tests: **9 passed, 11 subtests passed**.

## Speed Tests and Profiling

No inference-speed claim is made; this is a correctness fix that intentionally limits concurrency when the configured token cap is the active constraint.

Using the issue's 48-request workload with `--max-total-tokens 16384 --enable-unified-memory`:

| Result | Upstream baseline | This change |
|---|---:|---:|
| Successful requests | 48/48 | 48/48 |
| Peak `num_used_tokens` | 52,639 | 15,040 |
| Samples over configured max | 495/785 | 0/391 |
| Peak running requests | 35 | 10 |
| Workload wall time | 160.2 s | 79.8 s |

The wall time is included to characterize the validation run, not as a controlled performance benchmark.

Post-rebase A10 validation was also run. The A10's memory-derived Mamba pool limited serving concurrency to 3; the workload completed in 321.8 s with peak FULL usage of 4,512/16,384 tokens and zero cap violations. This result is a correctness check, not a cross-GPU performance comparison.
