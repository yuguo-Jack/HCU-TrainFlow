# [DeepEP] Ship static-FP8 W4AFP8 normal dispatch in a BF16 view

[Upstream PR](https://github.com/sgl-project/sglang/pull/41840) · state: closed · merged: False

## Original PR description

## Motivation

For W4AFP8 MoE on the DeepEP **normal**-dispatch path, activation quantization
and the all-to-all are separate stages (unlike low-latency dispatch, where
DeepEP fuses its own per-token-group quantization into the transport). The
current flow is:

```
sender:   hidden(BF16) ------------------ a2a (BF16, 2 bytes/elem) ---------->
receiver: hidden(BF16) -> per_tensor_quant_fp8(static ckpt scale) -> W4A8 GEMM
```

This pays BF16 bandwidth for the all-to-all and then re-quantizes on the
receiver with the checkpoint's **static per-tensor** scale. Worse, the only
FP8 transport option the normal dispatcher offered was DeepEP's per-token
group(128) quantization (`sglang_per_token_group_quant_fp8`), whose scales do
not match the per-tensor granularity the W4A8 kernel consumes — using it meant
an additional lossy per-token → per-tensor conversion on the receiver.

Since the W4AFP8 activation scale is a **single static scalar** from the
checkpoint, quantizing on the sender is bit-identical to quantizing on the
receiver. We can therefore quantize *before* the all-to-all and ship FP8:

```
sender:   hidden(BF16) -> per_tensor_quant_fp8(static ckpt scale)
                         -> view as BF16 -- a2a ("BF16", 1 byte/elem) ------>
receiver: view back to FP8 -> W4A8 GEMM (no requantization)
```

The FP8 payload is carried in a **BF16 view** (`[M, K] fp8` ≡ `[M, K/2] bf16`),
so DeepEP stays on its plain, well-tested BF16 all-to-all path — no DeepEP FP8
machinery, no per-token scale side-channel, no dtype negotiation. Traffic is
halved and the receive-side requantization kernel disappears.

## Modifications

- **`token_dispatcher/deepep.py`** — `_DeepEPDispatcherImplNormal` learns a
  `normal_static_fp8_scale` quant-config entry (injected via the existing
  `set_quant_config`, so no dispatcher interface change):
  - `dispatch_a`: when the scale is present, per-tensor quantize the hidden
    states to `float8_e4m3fn` and ship a BF16 *view* of the FP8 buffer. The
    DeepEP-DeepGEMM per-token-group FP8 branch is untouched and still applies
    when no static scale is configured.
  - `dispatch_b`: symmetrically restore the FP8 view; `hidden_states_scale`
    stays `None` (there are no per-token scales to propagate).
- **`quantization/w4afp8.py`** — `W4AFp8MoEMethod.process_weights_after_loading`
  hands the collapsed static `w13_input_scale` to the dispatcher when running
  on a DeepEP a2a backend (other backends are unchanged).
  `apply_deepep_normal` now accepts either BF16 (legacy flow) or a statically
  quantized FP8 payload (new flow), and still rejects anything else.
- **`cutlass_w4a8_moe.py`** — `cutlass_w4a8_moe_deepep_normal` detects the FP8
  payload and permutes it through a BF16 view — the *exact same* 2-byte
  element-copy triton path as the BF16 flow — then restores the FP8 view and
  skips the receive-side `per_tensor_quant_fp8`. The BF16 flow is byte-for-byte
  unchanged.
- **Tests** — `test_w4afp8_deepep_dtype.py`: dispatcher quant-config contents
  (DeepEP vs non-DeepEP), `dispatch_a` quantize+view contract, `dispatch_b`
  view restoration, and a bit-exact quantize→view→restore roundtrip.
  `test_w4afp8_deepep_post_reorder.py`: BF16 vs static-FP8 payloads (requant
  call count 2 vs 1) and a check that the FP8 payload is permuted via the BF16
  view and reaches the first GEMM as full-width FP8.

No changes to `ep_moe/layer.py`, TBO, or any other dispatcher backend: the
feature is entirely driven by the quant-config key only W4AFP8 sets.

## Relation to #34694

#34694 (`Use static FP8 communication for W4AFP8 normal dispatch`) implements
the same optimization by sending a real FP8 tensor and threading a
`static_scale` argument through the dispatcher call chain. This PR takes a
different route that keeps the patch surface minimal:

| Aspect | #34694 | This PR |
|---|---|---|
| Transport | FP8 tensor through DeepEP | FP8 bytes in a **BF16 view**; DeepEP stays on its BF16 path |
| Scale plumbing | new `static_scale` arg on `dispatch()`/`dispatch_a()` (incl. TBO wrapper) | injected once via existing `set_quant_config`; **zero** call-site changes |
| Receive-side permute | FP8 triton path | reuses the proven BF16 2-byte copy path via view |
| `ep_moe/layer.py` | modified | untouched |

Happy to align either direction with the maintainers of #34694.

## Accuracy Tests

CPU regression suite (`base-a-test-cpu`), torch 2.13:

```
test_w4afp8_deepep_dtype.py        10 passed
test_w4afp8_deepep_post_reorder.py  2 passed (+2 subtests)
full test/registered/unit/layers/moe suite: 135 passed
  (1 pre-existing failure in test_fused_moe_native, also fails on unmodified main)
```

The roundtrip test asserts bit-exact equality between sender-side quantization
and the FP8 tensor recovered on the receiver, and the post-reorder test asserts
the GEMM-facing contract (no requant for FP8 payloads).

## Speed Tests and Profiling

Expected wins, by construction:

- **Dispatch all-to-all volume: 2× reduction** (`2 bytes/elem → 1 byte/elem`)
  on every W4AFP8 MoE layer in normal (prefill) mode.
- **One less full-width quantization kernel** (`per_tensor_quant_fp8` over the
  permuted `[num_assignments, hidden]` buffer, ~`2 * num_assignments * hidden`
  bytes of traffic) per MoE layer per forward.

No host-side overhead is added: one `torch.empty` + one elementwise quant
kernel on the sender (previously paid on the receiver), and two dtype views
which are metadata-only. GPU end-to-end numbers on an EP cluster to follow in
CI / a follow-up comment.
