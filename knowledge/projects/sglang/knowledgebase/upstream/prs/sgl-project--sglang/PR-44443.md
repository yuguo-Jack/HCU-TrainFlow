# [Fix] [AMD] mhc: Bound the Triton fused post+pre buffer cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/44443) · state: closed · merged: True

## Original PR description

## Motivation

`_get_fused_hc_post_pre_buffers` caches one set of `mhc_post_pre` buffers per distinct `num_tokens` and never evicts them. The cache was added together with the `num_tokens <= _FUSED_HC_POST_PRE_M_THRESHOLD` (64) gate in #26383, so it stayed small. Since #36871, gfx1250 runs the Triton fused post+pre for every batch size, so each distinct prefill size adds a set that is never freed. For DeepSeek-V4-Pro (hidden 7168, `hc_mult` 4), one set is about 160 KB per token, or about 330 MB at 2048 tokens; over half of that is the fp32 `acc_partial`.

On gfx1250, a DeepSeek-V4-Pro prefill server (TP4, `--chunked-prefill-size 2048`) running a multi-turn agentic workload kept growing until it hit `torch.OutOfMemoryError` about an hour in. Live-tensor scans showed a growing set of `(896, M, 24)` fp32 buffers, one for each distinct M.

## Modifications

- Cache buffers only for `num_tokens <= _FUSED_HC_POST_PRE_M_THRESHOLD`, the bound the cache was designed for. The bound applies to every caller.
- Larger calls allocate their buffers per call; they go back to the caching allocator after use. Small (decode) batches keep using cached buffers.
- Today only gfx1250 runs this path above the threshold, so that is the only place behavior changes:
  - gfx95 enters it only for up to 64 tokens, when the aiter HIP kernel declines;
  - GLM-5-Next calls the boundary only for up to 16 tokens;
  - other platforms never reach it.
- Add a CPU regression test, `TestAmdFusedMhcBufferCache`. It fails on main (sizes 65 and 2048 stay cached) and passes with this change.

## Accuracy Tests

Outputs are not expected to change. The kernel and the buffer shapes are the same; for `num_tokens > 64` the buffers are just no longer reused across calls.

## Speed Tests and Profiling

Not benchmarked separately. Calls above 64 tokens make six extra caching-allocator allocations, and small batches are still served from the cache.

End-to-end memory on gfx1250: DeepSeek-V4-Pro, PD disaggregation 1P (TP4) + 1D (TP4), multi-turn agentic benchmark at concurrency 64, `--mem-fraction-static 0.82`. The run used a downstream build whose `deepseek_v4_fused_mhc.py` matches main, with an env-gated variant of this change that caches up to 512 tokens.

| Prefill server | TP0 `torch.cuda.memory_allocated` | Result |
|---|---|---|
| main | 427 GiB at failure (432 GiB device) | OOM about 58 min into the benchmark |
| bounded cache | 362.6 GiB -> 363.0 GiB over 2 h 11 min | benchmark completed (3,042 requests, 0 errors) |
