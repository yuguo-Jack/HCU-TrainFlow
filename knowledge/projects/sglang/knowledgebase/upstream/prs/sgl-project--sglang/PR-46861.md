# [Fix] [AMD] memory_pool: Keep K and V in separate allocations on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/46861) · state: closed · merged: True

## Original PR description

## Motivation

This ROCm bugfix, with no speed change, turns off the fused K/V allocation from #32272 on ROCm, because with it the MI35x PD disaggregation test `test_disaggregation_basic.py` returns garbage on every AMD PR.

#32272 changed `MHATokenToKVPool` to store each layer's K and V as block-aligned halves of one allocation, so `v_buffer[i]` now starts inside the allocation of `k_buffer[i]`. Only the trtllm_mha fmha_v2 prefill on CUDA reads that layout, but the allocation change has no platform gate. The test serves Qwen3-8B with Mooncake, prefill and decode on one MI35x node. The decode server now returns nonsense with no transfer error:

```
FAIL: test_gsm8k (__main__.TestDisaggregationAccuracy.test_gsm8k)
AssertionError: 0.005 not greater than 0.7
```

The MI35x 8-GPU disaggregation job ran on many PRs on 2026-10-27. Grouped by the main commit each run merged onto:

| main base | jobs | `test_disaggregation_basic.py` |
| --- | --- | --- |
| `db90f584d2`, `2b36c718cb`, `e4d4a9a7de` (before #32272) | 9 | passed in all 9 ([example](https://github.com/sgl-project/sglang/actions/runs/40464519661/job/122061186617)) |
| `1a120754e0` (#32272) and every later base seen (`d3a157a2f2`, `61a676125a`, `449617bc94`, `3927a73a34`, `8a455f1b90`, `a6f5bd397b`) | 9 | failed in all 9, GSM8K accuracy 0.0 to 0.01 ([first](https://github.com/sgl-project/sglang/actions/runs/40468145469/job/122072975234)) |

Seven of the nine earlier jobs failed in `test_disaggregation_pp.py`, which also fails on main's scheduled runs. `test_disaggregation_basic.py` passed in each of them.

Three other commits sit between `e4d4a9a7de` and `1a120754e0`. They are #31286 (removes an unused HiCache field), #46366 (gfx1250 diffusion GEMM) and #33743 (flashinfer TRT-LLM MoE weight reload). None of them touches the KV pool or PD. Every job ran on a different runner, so one bad machine does not explain it.

Mooncake's HIP transport carries the same-node transfer. It registers each KV buffer with its own `hipIpcGetMemHandle` and maps peer addresses as `dest - entry.addr + shm_addr`. With the fused layout, both handles of a layer point into one allocation. I did not find which step then puts V at the wrong address, so the evidence here is the bisect, not a mechanism.

## Modifications

- In `memory_pool.py`, the fused allocation now also needs `not _is_hip`. ROCm gets back the two `torch.zeros` per layer it had before #32272.
- In `test_mha_pool_fused_kv_layout.py`, a new CPU test patches `_is_hip` and checks that K and V do not share storage. The existing fused-layout test still runs on the CPU runner, where `_is_hip` is false. Both tests build the pool with a shared `_make_pool` helper.

Off ROCm this change does nothing. On ROCm nothing reads the fused layout, because fmha_v2 runs only on CUDA, so the only effect there is the allocation from before #32272.
