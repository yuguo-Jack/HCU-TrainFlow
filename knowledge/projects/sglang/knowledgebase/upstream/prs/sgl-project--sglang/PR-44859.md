# [Fix] multimodal: Clear the embedding cache in Scheduler.flush_cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/44859) · state: open · merged: False

## Original PR description


Clears the multimodal embedding cache when the scheduler flushes its caches. Before this, a server
whose weights were updated kept answering an image it had seen before with the embeddings of the
old vision encoder.

#36468 by @yuanlehome proposed the same change first. This pull request adds a regression test in
the existing flush test file and checks the fix on nine models (images, video and audio) against
fresh servers, bitwise. Happy to work with the author on either pull request, or for the
maintainers to merge whichever they prefer.

## Motivation

The scheduler keeps the vision encoder's output for an image or a video in
`mm_schedule.embedding_cache`, keyed by a hash of the input. `Scheduler.flush_cache()` resets the
radix cache, the KV pools and the grammar cache, but not this cache, and nothing else clears it.

`update_weights_from_disk`, `update_weights_from_tensor`, `update_weights_from_distributed` and
`update_weights_from_ipc` all end in `flush_cache()`. So do `/flush_cache` and
`release_memory_occupation` when it releases the KV cache. After a weight update the radix cache
is empty, but an image the server has seen before still gets the old encoder's embeddings, and the
model answers it as if the vision weights had not changed. A new image already gets the new ones.

The cache is on by default for most VLMs (`SGLANG_VLM_CACHE_SIZE_MB`, 100 MiB). Qwen3-VL on large
Hopper GPUs and `--rl-on-policy-target` turn it off unless the variable is set.

The memory is not returned either: `flush_cache()` empties the allocator cache while the cached
tensors are still referenced.

## Reproduction

Environment:

- GPU: NVIDIA H100 80GB HBM3, one GPU
- Base: upstream `abf92826ee54`, with and without this change
- Model: `Qwen/Qwen3-VL-4B-Instruct`, default server arguments and `SGLANG_VLM_CACHE_SIZE_MB=512`
  (set because Qwen3-VL turns the cache off on this GPU)
- Updated weights: a copy of the checkpoint with `model.visual.merger.linear_fc2.weight` set to
  zero. The language model is unchanged, so a different answer to an image prompt can only come
  from different image embeddings.
- Requests: two synthetic 448x448 images (image 1: a red circle and a blue square; image 2: a green
  triangle and an orange bar), "Describe this image in one sentence.", greedy, 48 tokens

On each server: ask about image 1, call `/update_weights_from_disk` with the changed checkpoint,
ask about image 1 again and about image 2 for the first time. A fresh server started on the
changed checkpoint gives the reference answers.

| Server | Image 1, before the update | Image 1, after the update | Image 2, after the update |
|---|---|---|---|
| Base | ... a red circle and a blue square on a white background. | ... a red circle and a blue square on a white background. | A green triangle sits atop a solid orange rectangle against a plain white background. |
| With this change | ... a red circle and a blue square on a white background. | ... a red circle and a blue rectangle against a plain white background. | A green triangle sits atop a solid orange rectangle against a plain white background. |
| Fresh server, changed checkpoint | | ... a red circle and a blue rectangle against a plain white background. | A green triangle sits atop a solid orange rectangle against a plain white background. |

Every answer to image 1 begins with "The image displays a simple composition of".

On the base server image 1 keeps its old answer after the update, although the radix cache was
flushed (the server log shows the request after the update prefilling all 213 prompt tokens, none
cached). Image 2 matches the fresh server on both, so the weights themselves were updated. With
this change image 1 matches the fresh server too.

The same holds with the ViT CUDA graph and with `/update_weights_from_tensor`, the path RL
trainers use (upstream `a8aaf95b58e0`, same model and images; the tensor update sets the same
weight to zero):

| ViT | Update | Base: image 1 after the update | With this change: image 1 after the update |
|---|---|---|---|
| eager | `update_weights_from_disk` | old answer | identical to the fresh server |
| eager | `update_weights_from_tensor` | old answer | identical to the fresh server |
| `SGLANG_VIT_ENABLE_CUDA_GRAPH=1` | `update_weights_from_disk` | old answer | identical to the fresh server |
| `SGLANG_VIT_ENABLE_CUDA_GRAPH=1` | `update_weights_from_tensor` | old answer | identical to the fresh server |

"Identical" means the same tokens with the same log probabilities, compared with a fresh server
on the changed checkpoint (with the same ViT mode) that flushed its cache before the request, as
the updated server just did. The ViT graph is captured before the update and replayed after it;
its answer equals that of a graph captured with the new weights. Without the flush, a fresh
server's first request takes 4 prompt tokens from the radix cache left by its warm-up, and its log
probabilities differ by up to 0.12.

The same check on eight more models, each with the last layer of its own projector set to zero and
compared bitwise with a fresh server (two H200): Qwen2.5-VL-7B-Instruct and InternVL2.5-2B (each
also with its ViT CUDA graph), GLM-4.1V-9B-Thinking, Kimi-VL-A3B-Instruct, DeepSeek-VL2-tiny,
Pixtral-12B, Qwen2-Audio-7B-Instruct with an audio input, and LLaVA-OneVision-0.5B; and on
Qwen3-VL-4B-Instruct with a video input. Every model that goes through the embedding cache gave the
old answer on the base server and the fresh server's answer with this change. LLaVA-OneVision
encodes in its own forward and was not affected.

## Modifications

- Add `clear_mm_embedding_cache()` to `mm_schedule`, next to `init_mm_embedding_cache()`.
- Call it in `Scheduler.flush_cache()` before the allocator cache is emptied, so the memory is
  returned as well.
- Add `test_flush_cache_drops_cached_mm_embeddings` to
  `test/registered/unit/managers/test_scheduler_flush_cache_after_retract.py` (CPU): a bare
  `Scheduler` flushes with a real `MultiModalStaticCache` holding one entry, which must be gone
  afterwards.

Not covered here: Kimi-VL's vision tower keeps its own cache of interpolated position embeddings
per image grid, which also survives a weight update; that needs a change in the model and is left
to a separate pull request.

Nothing else holds encoder output across a flush. The tokenizer's preprocessing cache stores
processor output, not encoder output, and is already cleared on `/flush_cache` and after weight
updates. The encoder server of encoder disaggregation has its own embedding cache, but no
weight-update endpoint, so its weights cannot change while it runs.

## Accuracy Tests

No model, kernel or forward code changes.

```bash
python3 test/registered/unit/managers/test_scheduler_flush_cache_after_retract.py -v
```

Without the change, the new case fails (`AssertionError: 1 != 0`: the cached entry is still
there) and the six existing cases pass. With the change all seven pass. The existing cases
flush without an embedding cache, which covers the `None` check.

```bash
pytest test/registered/unit/managers test/registered/unit/multimodal \
  test/registered/chunked_prefill/test_mm_chunked_embedding_unit.py
```

| Tree | Result |
|---|---|
| upstream `a8aaf95b58e0` | 2 failed, 1190 passed, 43 skipped |
| with this change | 2 failed, 1191 passed, 43 skipped |

The two failures are the same on both trees and unrelated: two cases of
`test_mm_process_config.py` set `tp_size=8` in a single process and stop on
`ValueError: parallel topology is inconsistent`. The extra pass is the new case.

`pre-commit run --files` on the three changed files passes.

## Speed Tests and Profiling

Serving is not affected: the new call runs only when the caches are flushed. After a flush or a
weight update, an input that was cached is encoded once more. On Qwen2.5-VL-7B (one H200, a
448x448 image, 10 runs) the first token after a flush takes 64.1 ms instead of 40.6 ms.
