# [Feature] Extend set_internal_state to hot scheduler knobs

[Upstream PR](https://github.com/sgl-project/sglang/pull/37661) · state: open · merged: False

## Original PR description

## Motivation

`set_internal_state` already fans out to every scheduler rank, but its allowlist admits only five niche keys. The settings operators actually tune, concurrency cap, queue limit, prefill chunk size, prefill budget, schedule policy, are read by the event loop on every step and are plain Python state, yet changing one means killing the server and reloading the weights. On the machines below that is one to seven minutes per change.

This widens the existing route to those knobs. No new endpoint, no new transport, no kernels, no architecture-specific code.

| knob | accepted values | where the loop reads it |
|---|---|---|
| `max_running_requests` | 1 to the boot allocation | scheduler.py 2274, 2302, 3626 |
| `max_queued_requests` | 0 or more | scheduler.py 3077 |
| `chunked_prefill_size` | above 0 | scheduler.py 3600 |
| `max_prefill_tokens` | 1 to `max_total_num_tokens` | scheduler.py 3621 |
| `schedule_policy` | any `SchedulePolicy`, via `_validate_and_adjust_policy` | schedule_policy.py 257, 294, 297 |
| `schedule_conservativeness` | above 0, rebuilds the watermarks as `from_config` does | scheduler.py 3620, 3890 |
| `log_level` | DEBUG, INFO, WARNING, ERROR | every log call |

`get_internal_state` reports the live values and the boot ceilings under a `trimtab` key. `SetInternalStateReq.server_args` widens to allow `str` for the two string knobs. Unknown keys fall through to the existing allowlist untouched, so the five upstream keys behave exactly as before.

## Modifications

- `python/sglang/srt/managers/scheduler.py`: `_trimtab_apply_hot_knobs` applies and validates the knobs, called at the top of `set_internal_state`; `get_internal_state` reports them.
- `python/sglang/srt/managers/io_struct.py`: `server_args` accepts `str` values.
- `test/registered/unit/managers/test_trimtab_hot_knobs.py`: new, CPU only.

The in-place KV pool reinit that was in the first version of this PR has been split out. It is the risky half, it deserves its own review, and it will follow once this lands.

## Accuracy Test

No model behaviour changes. These are scheduler admission and batching settings; the sampling path is untouched.

## Benchmark and Profiling

Measured on H100, RTX PRO 6000 and B200 with Qwen3.8-27B-FP8 under 32-thread load: 20 of 20 changes applied, p50 16 to 22 ms round trip, zero failed requests across every run. The same settings changed by restart cost 56 to 86 s warm and 141 to 391 s cold on the same machines.

Hi @numinousmuses, we're planning PRs that make `chunked_prefill_size` and `prefill_max_requests` writable through `set_internal_state`, built on the handler table that #41950 added in `scheduler_components/internal_state.py`. That overlaps with your PR on `chunked_prefill_size`, so I wanted to coordinate before opening anything.

Our design, in case it's useful for yours: validators per knob, applied together after all of them pass; a launch-value ceiling for `chunked_prefill_size` (so a write can't grow past the sizing of startup buffers); `bool` rejected as an int; and refusals for dynamic chunking and for the prefill delayer's queue trigger.

Are you still working on this PR? If you plan to rebase onto the handler table, happy to review or send suggestions. If not, we'll send narrower PRs for these two knobs and leave the rest of your list (`max_prefill_tokens`, `max_running_requests`, `schedule_policy`, `schedule_conservativeness`) for a follow-up on top of ours.
