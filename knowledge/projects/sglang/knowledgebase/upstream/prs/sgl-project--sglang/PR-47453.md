# [AMD] Write the Kimi-K3 shared-down GEMM through AITER when out is set

[Upstream PR](https://github.com/sgl-project/sglang/pull/47453) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, module-level bf16 GEMMs go through Aiter's tuned `tgemm` when `SGLANG_USE_AITER` is set. Kimi-K3's shared-expert down GEMM does not: `_k3_bf16_gemm` is called with `out=` pointing at the fused `[latent | shared]` all-reduce slice, and that path still uses `torch.mm`.

So the GEMM already has the right destination, but it misses the tuned kernels. Routing it through Aiter needs `tgemm.mm(..., out=)`, which is on Aiter main via [ROCm/aiter#6833](https://github.com/ROCm/aiter/pull/6833). Without that Aiter build, this PR falls back to `torch.mm` and nothing changes.

The fused front GEMM (`out is None`) is a separate change (#41867 / #44360). This PR only touches the shared-down path.

Replaces closed #44294 (same branch, rebased after the head branch was recreated).

## Modifications

In `_k3_bf16_gemm` (`python/sglang/srt/models/kimi_k3.py`):

- When `out is not None`, HIP, and `SGLANG_USE_AITER` is set, call `tgemm.mm(..., out=out)`.
- Skip when `unquant._skip_aiter_unquant` is set (gfx95 deterministic), matching `UnquantizedLinearMethod`.
- If the installed Aiter has no `out` argument, or rejects the layout (`ValueError`), keep using `torch.mm`.
- Leave the `out is None` (front GEMM) path alone.

## Accuracy Tests

No model-math change when Aiter writes the same buffer `torch.mm` would.

Paired with Aiter main / #6833: result pointer matches the passed `out`, values match `F.linear`. With `_skip_aiter_unquant=True`, the helper returns False and leaves the buffer untouched.

Full-model gsm8k / serving accuracy still to run against that Aiter build.

## Speed Tests and Profiling

Not measured yet. Expected effect: shared-down uses the tuned Aiter kernel and writes straight into the all-reduce slice (no allocate + copy).
