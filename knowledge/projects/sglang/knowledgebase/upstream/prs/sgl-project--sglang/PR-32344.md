# [Bugfix] Emit cached token metric before first cache hit

[Upstream PR](https://github.com/sgl-project/sglang/pull/32344) · state: closed · merged: False

## Original PR description

## Summary

- emit `sglang:cached_tokens_total{cache_source="total"} 0` after a completed request with no cache hit
- keep the cached-token label set available for PromQL vector arithmetic before the first positive cache hit
- extend the existing metrics integration test to verify the cold-request zero series

Without an explicit zero series, queries such as `prompt_tokens_total - cached_tokens_total` drop the entire label set until a cache hit occurs.

- gnanirahulnutakki · comment · 2026-07-24T19:26:17Z · [source](https://github.com/sgl-project/sglang/pull/32344#discussion_r3647690927)

File: `python/sglang/srt/observability/metrics_collector.py` · line 1695

The added zero series still cannot participate in the unmodified subtraction described in the PR. `prompt_tokens_total` is declared with only the base labels, while every `cached_tokens_total` child—including this one—also has `cache_source`; [PromQL's default one-to-one matching requires the exact same labels](https://prometheus.io/docs/prometheus/latest/querying/operators/#one-to-one-vector-matches), so `prompt_tokens_total - cached_tokens_total` continues to drop the series. Please either expose a separate aggregate counter with the base label set, or update the consumer query to aggregate this dimension first (for example, `prompt_tokens_total - sum without(cache_source) (cached_tokens_total)`). The test should cover that query-level behavior or at least assert the intended label compatibility; checking that a cached-token sample exists and sums to zero does not catch this mismatch.
