## Original PR description

# [AMD] Enable GPT-OSS MXFP4 with Triton kernels on ROCm

## Summary

Enable serialized GPT-OSS MXFP4 checkpoints on ROCm systems where AITER is disabled by routing MoE execution through `triton_kernels`.

## Changes

- Register `mxfp4` on RDNA when `triton_kernels` is available, while preserving the existing native gfx95 path.
- Allow `Mxfp4Config` on that ROCm software backend and report a clear error when neither native support nor Triton-kernels is available.
- For GPT-OSS MXFP4 on HIP with EP size 1, select:
  - Triton attention when AITER is disabled;
  - `moe_runner_backend="triton_kernel"` when the package is available.
- Pass `b_microblock_size=32` with MXFP4 scales, as required by the Triton 3.8 `PrecisionConfig` API. MXFP4 stores one scale per 32 weight values.

## Dependency

This path requires compatible Triton 3.8 and `triton-kernels` packages. SGLang does not vendor them.

## Validation

Completed:

- GPT-OSS resolves to Triton attention and `triton_kernel` MoE on ROCm with AITER disabled.
- MXFP4 weights load successfully on gfx1100 and gfx1201.
- GPT-OSS runs successfully with passing gsm8k accuracy test

Hardcoding b_microblock_size=32 breaks Triton 3.7. PrecisionConfig doesn't have this field there, so this raises TypeError, for example on the gfx942/gfx950 rocm720 images, which build Triton 42270451. This path is shared with CUDA (H100 GPT-OSS) too. Upstream fixed this in #38641 with _mx_block_kwargs(), which only passes the field when it exists.
