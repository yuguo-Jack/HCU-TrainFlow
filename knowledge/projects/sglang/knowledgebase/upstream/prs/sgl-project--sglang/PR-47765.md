# [Perf] dflash: Fuse the simulated-acceptance overwrite into one kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47765) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

`SGLANG_SIMULATE_ACC_LEN` is a benchmark mode that forces the speculative acceptance length. For DFlash, each verify step runs the real accept first and then overwrites its outputs (accept and commit lengths, bonus token, committed block) with the forced length (`apply_dflash_simulated_acceptance`). That overwrite is simulation-only work, and it was eager:

- `fixed` token mode: 4 small launches (`fill_` x 4).
- `real-draft-token` mode: 6 launches (fills, zero, slice copies, casts).
- On the sampling and selector verify branches, which do not produce the target argmax, `real-draft-token` mode also ran a full-vocabulary argmax over all `bs x block_size` verify rows, then read only one row per request (the row at the forced length).
- On the greedy branch the Triton accept already writes `new_seq_lens`; under simulation the caller threw it away and recomputed `prefix_lens + commit_lens` (2 more launches).

This PR does that overwrite in one small JIT CUDA kernel and takes the argmax of the forced row only. Outputs are byte-identical to the eager code, including the memory around strided outputs and the CPU RNG state after the call. The real accept is untouched and still runs first, and nothing changes when `SGLANG_SIMULATE_ACC_LEN` is unset.

It follows the rule in #46840 (now in `environ.py`): simulation changes only the accepted length, every operation real serving runs still runs at real cost, and only work that the simulation alone adds may get cheaper. #46840 did the same for the EAGLE simulated bonus sample, which drew over all rows and kept one. #41169 is the EAGLE precedent for the fusion itself: it fused EAGLE's simulated-acceptance ops into one kernel, with the forced length passed as a scalar, on by default and with no new flag. This PR is the DFlash counterpart. cc @weireweire @YAMY1234

**Why a JIT CUDA kernel and not Triton.** The first version of this PR used a Triton kernel, like #41169. At batch 1-8 this overwrite is bound by host launch cost, not GPU time, and a Triton launch with this many arguments costs about as much host time as 4 `fill_` calls. On the sampling branch, where there is no `new_seq_lens` recompute to remove, the Triton version was 16-38 us per round slower than main at bs 1-8, though its GPU time was lower. A JIT CUDA op through `sglang.kernels.jit` costs about one `fill_`. Host cost per call, B200, bs 1, 3000 back-to-back launches per sync (median of 7, two processes):

| op | us per call |
|---|---|
| torch `fill_` | 2.9 |
| Triton kernel with this PR's argument list (8 pointers, 13 ints) | 12.3-12.5 |
| existing JIT op `add_constant` (2 tensors) | 2.3 |
| this PR's JIT op, in the 4 argument shapes it is called with | 3.3-3.8 |

With the JIT op every measured case is faster than main (table below), so there is no gate or size threshold: the fused path runs on every CUDA call. Other devices keep the eager ops.

**Impact**

- **Accuracy:** byte-identical. A unit test compares against a frozen copy of main's eager implementation in 938 cases on B200 (both token modes, both length methods, bs 1-64, block 4-16, int32/int64 mixes, ids past 2^31, strided and sliced outputs, with and without `new_seq_lens`, logits with tied maxima and NaN rows at vocab 32,000 and 128,256 in fp32/bf16/fp16). The accept-region benchmark below also dumped every output and the CPU RNG state from main and from this PR: 480 of 480 comparisons equal.
- **Performance (accept region, B200, V = 128,256, block 10):** cheaper than main in every cell measured (2 branches x 2 token modes x bs 1/8/16/32/64), by 2.9-63.9 us per round, each by more than its noise; the smallest margin is `fixed` / sampling at bs 1, -9.2 ±4.9 us. GPU time and kernel count also drop in every cell. The fused kernel itself takes 1.9-2.6 us of GPU time.
- **End to end:** real serving is unchanged; simulated runs move closer to real cost. The saving is tens of us per decode step, under 1% of a step, which an end-to-end run cannot resolve (measured on the Triton version: about 4.3 ms per step either way, with about 12 us between two launches of main).

## Modifications

**+292 / -13 runtime code (5 files), +474 tests (1 file).** One new JIT CUDA kernel.

- `dflash_simulated_accept` (`kernels/jit/csrc/speculative/dflash_simulated_accept.cuh`, wrapper `kernels/ops/speculative/dflash_simulated_accept.py`, registered as `speculative.dflash_simulated_accept`, `KernelBackend.JIT`, CUDA only): one thread per `out_tokens` element. It writes the committed row; column 0 also writes `num_correct_drafts = n - 1`, `num_accept_tokens = n`, the bonus and, when given, `new_seq_lens = prefix_lens + n`.
  - `n` and the fixed token are scalar arguments, so a new forced length needs no rebuild.
  - `fixed` mode writes the fixed token to the bonus and every column; it stays an argument (`fixed_token_id=100` default unchanged).
  - `real-draft-token` mode writes `candidates[:, 1:n]`, the bonus at column `n - 1` and zeros after it, with the same two casts as before (target dtype -> bonus dtype -> output dtype).
  - Every tensor is int32 or int64 with any strides. The width is a runtime field per tensor, so one build covers every dtype mix. Shape, dtype, device and range checks are in the C++ launcher (`TensorMatcher`, `CHECK_HOST`); the Python wrapper passes its arguments through.
- `apply_dflash_simulated_acceptance` (`srt/speculative/dflash_utils.py`):
  - Draws the forced length first: the same `sample_simulated_acc_len` call on the same CPU generator, once per round. Moving it before the argmax does not change the RNG stream (the argmax draws nothing).
  - When `target_predict` is None, takes `torch.argmax` of row `n - 1` of each request only, so the tie rule (first NaN, else the lowest index of the max) is torch's, as before.
  - Uses the kernel on CUDA; other devices keep the eager ops.
  - New optional `prefix_lens` / `new_seq_lens`: when the greedy Triton accept wrote `new_seq_lens`, the kernel rewrites it from the forced length and the function returns it; otherwise it returns None and the caller recomputes as before.
- `DFlashWorkerV2._accept_block` (`srt/speculative/dflash_worker_v2.py`): passes `prefix_lens` and `new_seq_lens` through and keeps what comes back. The three real accept branches and their TP syncs are unchanged.
- No env var, no docs change, no CUDA-graph change (the DFlash accept tail is eager on main).

## Accuracy Tests

**Unit test** (`test/registered/unit/spec/test_dflash_simulated_accept.py`, B200, `torch.equal`, integer outputs so the tolerance is exact). The expected values come from `_eager_reference`, a verbatim copy of main's eager body (at c757c4bb7c), never from the new code. A hand-built case pins both the reference and the new path to literal values. Each case runs 4-6 rounds on one CPU RNG stream; every round poisons each output's backing buffer, runs the reference, restores the RNG state, runs the new path, then compares the RNG state and every backing buffer in full (tail rows and stride gaps included). `prefix_lens` is always passed, as the worker does, and every other case passes `new_seq_lens=None` (the sampling-branch call).

| test | cases |
|---|---|
| `test_reference_hand_built` | literals, CPU and CUDA |
| `test_eager_fallback_matches_reference` | 160, CPU (the non-CUDA path, forced-row argmax included) |
| `test_matches_reference` | 640: token mode x method x {`target_predict`, logits with ties and NaN rows} x 5 means (reaching length 1, `block_size` and an interior length) x bs {1, 2, 7, 64} x block {4, 5, 8, 16}, cycling fresh / sliced / strided outputs |

**Issue**

This PR is based on c757c4bb7c, and main has since changed these lines. #47512 replaced this `torch.argmax` with `sampling_argmax` (a JIT kernel that never picks NaN). #48298 added `generator=` to this function, to the `sample_simulated_acc_len` call at line 963, and to the call in `DFlashWorkerV2._accept_block`, so every TP rank draws the same forced length. The PR now conflicts with main, and keeping this side of the conflict drops both changes.

**Fix**

When rebasing, take the forced row's argmax with `sampling_argmax` and pass `generator` through. Then update `_eager_reference` in the test to main's new body, including the NaN rule that `test_argmax_ties_at_real_vocab` expects.
