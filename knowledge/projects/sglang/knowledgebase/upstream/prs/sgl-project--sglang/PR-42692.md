# perf(kimi-k3): fold BS1 shared-expert all-reduce into the deferred-finalize push

[Upstream PR](https://github.com/sgl-project/sglang/pull/42692) · state: closed · merged: False

## Original PR description

## Motivation

At batch size 1 on the Kimi-K3 TP8 fused MoE path, the shared-expert output gets its own low-SM pull all-reduce on the side stream. The latent then goes through the deferred-finalize push all-reduce + RMSNorm. Both collectives move tiny tensors, and the push all-reduce has headroom for the shared rows. This PR folds the shared-expert partials into the finalize push so both ride one collective, which removes one all-reduce launch per MoE layer per decode step.

## Modifications

- `ar_fusion.cuh`, `finalize_push_norm`: in the finalize variant, stage 1 finalizes the leading latent rows from the trtllm-gen deferred-finalize triple. Any trailing rows are staged from `out` as rank-local partials. Only the latent rows are RMSNormed. The host accepts either a latent-only `[T * 3584]` output or a flattened `[latent | shared]` `[3T * 3584]` output, and sizes the row-cluster grid from the total row count.
- `kimi_k3.py`, `_forward_fused`: when the deferred finalize is active, `num_tokens == 1`, and three rows fit the push window, skip the side-stream `all_reduce_low_sm` on `shared_output` and pass the whole `[latent | shared]` symmetric buffer to `finalize_all_reduce_push_norm`.
- Docstrings updated in `all_reduce_residual.py` and `k3_ar_fusion.py`.

The path is gated on the existing deferred finalize (`flashinfer_mxfp4` + SiTU, the Blackwell default), so it is active on B200/B300 TP8 MXFP4. Other batch sizes are unchanged.

## Accuracy Tests

B300 1×8, TP8, `moonshotai/Kimi-K3` MXFP4, the cookbook B300 Unified Low-Latency recipe (`--tp-size 8 --mem-fraction-static 0.85`, attention/MoE backends auto-resolved). GSM8K (`sglang.test.few_shot_gsm8k`, 1319 questions, 5-shot):

| Run | main | this PR |
|---|---|---|
| Full set, `--parallel 64` | 0.951 (invalid 0.001) | 0.951 (invalid 0.001) |
| First 250, `--parallel 1` (batch size 1, exercises this path) | 0.988 (247/250) | 0.980 (245/250) |

The batch-size-1 delta is 2 questions out of 250, within one standard error (~0.9 pt) at this sample size. Reduction order for the shared rows changes (summed inside the push all-reduce instead of a separate pull all-reduce), so greedy outputs can diverge in a few places. A full 1319-question batch-size-1 run is still to do before this leaves draft.

## Speed Tests and Profiling

Same setup. `bench_one_batch_server`, batch size 1, input 8192, output 1024, three repetitions per arm on the same server:

| Output throughput (tok/s) | rep 1 | rep 2 | rep 3 |
|---|---|---|---|
| main | 118.72 | 119.28 | 119.17 |
| this PR | 119.58 | 119.46 | 119.50 |

Decode is +0.2–0.3% on B300 (main's rep 1 includes first-request warmup). The gain is small on B300 because the separate shared-expert all-reduce already ran on the side stream, overlapped with the routed experts. What this PR saves is one launch and one synchronization per layer.

Kernel counts from a TP0 torch-profiler trace (batch size 1, 1024 input, 5 profiled steps):

| Kernel | main | this PR |
|---|---|---|
| `all_reduce_pull_res_kernel` | 553 | 185 (−368, one per MoE layer per decode step) |
| `all_reduce_push_norm_cluster_kernel` | 368 × 8.14 µs | 368 × 8.06 µs (now also carries the shared rows) |
| Total kernels | 11393 | 11025 |
