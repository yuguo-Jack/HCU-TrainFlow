# [sgl-router] Render Kimi-K3 through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/43608) · state: open · merged: False

## Original PR description

> [!NOTE]
> **Stack 2/3**, merge in order: #43625 (GLM-5.3) → #43608 (Kimi-K3) → #43689 (Qwen3.8). This PR is based on #43625 (`kan/sgl-router-glm53`), so its diff shows only the Kimi-K3 commit. After #43625 merges it gets rebased onto `main`.

Adds Kimi-K3 to sglang-processor and renders it there in the router, so every text Kimi-K3 chat forwards the same `input_ids` SGLang would build. This follows #43000 (DeepSeek-V4.1).

## Modifications

- **Render:** `ChatFormatter::KimiK3` (`render/models/kimi_k3.rs`). `render_request` builds the request the way `serving_chat.py` calls the checkpoint's encoder (`_prepare_kimi_k3_messages` and the `kimi_k3` branch of `_encode_messages`), then renders it with Dynamo's `KimiK3Formatter`:
  - **Messages:** the pydantic message dump keeps only text and image parts, neutralizes the image placeholder, and turns developer turns into system turns. String tool arguments are parsed into objects.
  - **Tools:** dumped as `exclude_unset` does. A system turn with tools renders only its declaration.
  - **Thinking:** kwargs win, then `reasoning`/effort, then the server's defaults; on by default.
  - **`thinking_effort`:** the kwarg, else a `low`/`high`/`max` request effort, else `max`.
  - **`tool_choice`** (`required`/`none`) and **`response_format`** (including the legacy `schema` and the kwargs `response_schema`) render as SGLang renders them.
  - **Continuation:** the `continue_final_message` prefix is returned on its own, since SGLang tokenizes it separately.

  `render_request` now returns a `RenderedPrompt`, so K3 keeps its special-token segments. `render_prompt` keeps Dynamo's K3 request semantics, which typed hosts rely on, so sglang-renderer is unchanged.
- **Left to the engine:** where the pinned formatter would render differently, `render_request` returns an error and hosts send the request to the engine:
  - a null `thinking_effort` with thinking on;
  - whitespace-only reasoning history;
  - string tool arguments that are not a JSON object;
  - numbers serde_json prints differently from Python (`1e-06`, integers beyond 64 bits, `-0`);
  - tokenizer arguments in `chat_template_kwargs`;
  - tool declarations Dynamo rejects.
- **Router:**
  - Kimi-K3 renders through the processor. The router's own `kimi::normalize` is gone; the chunked tiktoken encode stays.
  - Every text chat forwards `input_ids` (`AllText`).
  - Kimi chats are never lowered to `/generate` (outcome `kimi_k3_openai_layer`). SGLang's OpenAI layer special-cases K3 (reported prompt tokens, `skip_special_tokens`, non-strict `json_schema`), and `lower_chat` doesn't reproduce that.

## Checks

- **Render:** 109 cases match SGLang's prompt text and token ids at `moonshotai/Kimi-K3@f831ab66`, using the real tiktoken vocab. 13 are known gaps that the processor leaves to the engine. `generate_parity.py` records the template text for a spec that tokenizes inside `apply_chat_template`.
- **End to end:** the real `sgl-router` binary runs in front of SGLang's Python OpenAI layer: `OpenAIServingChat` with the K3 tokenizer and the `kimi_k3` reasoning and tool parsers, with only the model forward stubbed. Each of 130 requests is sent both to the engine and through the router. The cases are the fixture's, plus streaming, usage, sampling and long inputs (including a 30k-character run).
  - The recorded `GenerateReqInput`s and the OpenAI responses are identical for all 130.
  - 111 requests carry router `input_ids`.
  - Both hold with `--default-chat-template-kwargs` set to `{"reasoning_effort":"low"}` and to `{"thinking":false}`.
  - On `main`, the router forwards 24 of the 130, and one of them (a `json_schema` response format with a legacy `schema`) arrives with wrong ids.
- The proxy test covers the `/generate` gate: workers report OpenAI settings with no parsers, and Kimi chats still take the engine's route.
- `cargo test` and `cargo clippy -D warnings` pass for `rust/` and `experimental/sgl-router`.

There was no live GPU run. Serving Kimi-K3 chats through `/generate` would need the `kimi_k3` reasoning and tool parsers plus K3's OpenAI-layer behavior; that is a follow-up.
