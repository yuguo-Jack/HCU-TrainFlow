# [Fix] hicache: Recover storage worker collectives and expose storage liveness

[Upstream PR](https://github.com/sgl-project/sglang/pull/44342) · state: open · merged: False

## Original PR description

## Motivation

The Python HiCache storage pipeline runs one query, one transfer, one sync and one backup daemon thread per rank, and the query thread and the sync thread each rank-reduce their result with a gloo `all_reduce` on dedicated storage sync groups (`cache_controller.py` `_sync_prefetch_hit_query`, `_reduce_prefetch_ack`; `hybrid_cache_controller.py` overrides; since #43344 the PP ticket thread issues the same hit reduction). Those collectives are outside every `try/except`, and nothing on the scheduler thread checks whether the workers are alive. So when one rank's backend call hangs (slow `exists()`/`get()`, a stuck RPC) the peers block in the collective, and once the group timeout fires the collective raises and **kills the worker thread on every rank** (the healthy rank with `Timed out waiting ... for recv operation`, the hung rank with `Connection closed by peer` when it finally enters the collective). From then on no query or ack is ever published on any rank: under `wait_complete` every later L3-hit request waits forever, under `timeout` every one of them pays the full deadline and recomputes, and the only operator remedy (`/flush_cache`, detach) raises out of the scheduler. #43550 only guards the backend call, not the collective. The same strand happens when a worker thread dies for any other reason on one rank: its peers' collectives never complete.

Two-rank CPU reproduction (gloo, rank 1 hung in `batch_exists`, 3 s group timeout): rank 0's query thread dies at 3.0 s, rank 1's at 5.0 s the instant its call returns, nothing is published, every later query stays queued — on upstream main as well as with #43550.

This PR makes the worker collectives recoverable and gives the scheduler a rank-agreed liveness signal, so a collective failure or a dead worker degrades to "L3 unavailable" instead of silently stranding every rank.

## Modifications

**Worker threads (`cache_controller.py`, `hybrid_cache_controller.py`)**

- Every worker-thread collective goes through `HiCacheController._storage_sync_all_reduce`: on a `RuntimeError` (gloo timeout, connection closed) it logs one ERROR with the traceback, sets the controller-level `storage_sync_failed` flag and returns `False`; the caller publishes the operation as FAILED on this rank (hit query -> 0 hits with no pool verdict, transfer ack -> 0 completed tokens, sidecar ack -> all-zero pool hits) and **the thread stays alive**. Every later collective is still entered: gloo keeps a timed-out pair closed, so a broken group raises at once on every rank (measured 0.00-0.01 s), whereas skipping it would strand a peer on a group that did not fail (the hits and completion groups are distinct gloo groups even on TP2). The publication sequence stays exactly one per query and one ack per transfer batch, which is what the scheduler's MIN-of-queue-sizes drain relies on.
- The PP ticket thread (`pp_prefetch_command_thread_func`) runs the hit query and its MIN itself since #43344, so the guarded `_sync_prefetch_hit_query` covers the ticket path; an unexpected ticket failure records the same sync failure before the thread exits (the broadcast is the PP agreement itself). `is_pp_prefetch_ready` no longer raises for a dead ticket thread under the default policy (the health bit retires the ticket instead; `raise` keeps the old fail-loud behaviour), and `take_ready_pp_prefetch` waits in 1 s slices and raises when the local ticket thread is dead instead of blocking the scheduler forever on a ticket PP0 declared ready.
- `storage_workers_healthy()` / `storage_health_reason()`: rank-local liveness = no sync failure and every **started** storage worker thread (plus the PP ticket thread when present) alive. A controller whose storage I/O runs outside these Python workers has none to watch and reports healthy on their account.
- Two keys in `--hicache-storage-backend-extra-config`, popped and validated at the top of `attach_storage_backend` before any side effect (that entry point also covers the decode offload manager, which bypasses `parse_storage_backend_extra_config`): `storage_failure_policy` (`"disable"` default, `"raise"`) and `storage_sync_timeout` (seconds, **default 300**; torch's gloo default is 30 minutes). The timeout is plumbed through a new optional `timeout` argument of `create_custom_parallel_group` into `torch.distributed.new_group` for the groups the controller builds in `_create_sync_groups` and for the PP ticket broadcast group, which is now created when the storage workers start — after attach has applied the timeout — instead of before the config is parsed (`reset()` restarts the threads and keeps the group). `mla_host_dedup._prebuild_prefetch_sync_groups` builds a second, currently unused set with torch's default.

**Scheduler thread (`unified_radix_cache.py`)**

- The health bit is folded into the collectives the drain already issues: `_sync_hicache_ready_counts` and `drain_storage_control_queues` append `int(cc.storage_workers_healthy())` to the MIN-reduced count tensor, read after the queue sizes (see below), on both the gloo reduce and the shared-memory count exchange (`_shm_count_exchange`; its `hicache` row grows from 8 to 9 words so the no-extra-pool layout keeps taking the shm path, `get_shm_exchange` gains a `width` argument for that). In buffer-only PP>1 *without* PP tickets every stage issues its own prefetch and `check_prefetch_progress` must cut on one value, so PP0's verdict is relayed with the existing `_pp_sync` (one recv per tick on PP>0, the coupling cache-mode PP already has); with PP tickets PP0 decides per request through the existing MAX, so stages keep their own bit and nothing new touches the PP group.
- `_apply_storage_health`: when the agreed bit drops (once): ERROR log with the reason (this rank's, or "reported by a peer rank"), `sglang:hicache_storage_healthy` gauge -> 0 (also set to 0 on detach, 1 on attach), then the policy. `disable` sets `storage_unavailable` and logs a WARNING once a minute while degraded; `raise` raises `RuntimeError` out of the scheduler.
- Under `storage_unavailable`: `prefetch_from_storage` and `query_storage_hit_length` return immediately, `write_backup_storage` / `enqueue_backup_intent` enqueue nothing new, `check_prefetch_progress` cuts every in-flight prefetch through the `deadline_expired` machinery of #44614 (no retry re-arm, no belief learning, no miss accounting) and reports it under a new `storage_unavailable` reason of `sglang:storage_prefetch_unfulfilled_tokens_total`, a PP ticket is retired on every rank through the PP0-decided MAX (verdict 0 pending / 1 ready / 2 retire), the drain reads every popped hit as a miss and applies no further transfer progress (completion still releases each operation's tail at the last agreed progress), and `_invalidate_absent_from_hit_query` learns nothing. Re-attaching the backend (fresh threads and groups) clears the flag; `/flush_cache` restarts the workers but keeps the groups, so it logs that L3 stays disabled.

**Why the degrade is rank-consistent.** After the first failure every collective on the broken group fails on every rank, but the failing collective itself can end differently per rank: a peer whose data arrived just before the timeout may complete while the other rank raised. The design therefore never trusts a value published around the failure: a worker sets `storage_sync_failed` *before* it publishes the failed item, and the scheduler reads the queue sizes *before* the health bit, so any round that counts (and thus pops) a possibly-asymmetric publication is a round in which the agreed bit is already 0 on every rank (MIN), and in such a round every rank discards the hit, freezes transfer progress and skips belief healing identically. Items drained in earlier rounds were reduced successfully on all ranks. The frozen progress is conservative (a batch that every rank did complete may be dropped) but identical everywhere; the prefix that was already agreed is still used.

**Why `disable` is the default.** The OSS default stack has no supervisor that restarts a crashed server, and a degraded L3 (one ERROR, a gauge at 0, a WARNING per minute, cold TTFT) is strictly better than today's strand or a crash of the whole engine; fleets that alert on crashes rather than logs can opt into `raise`. Happy to flip the default if maintainers prefer fail-loud.

**Why 300 s.** The group timeout only bounds how long a healthy rank waits for a peer that is stuck in its backend; tripping it degrades L3 until re-attach, so it must stay far above any healthy batch call (128 pages per call) and above the 60 s idle ticket broadcast, while noticing a hung peer in minutes rather than after 30. A per-call bound that turns a hung call into a single miss without touching the group is a separate PR (#44343).

**Known limits** (pre-existing behaviour, called out for reviewers): the health bit is agreed over the ranks that share a scheduler drain, so in every PP>1 shape a PP>0 stage's own worker failure reaches PP0 only once a cross-stage sync collective fails or times out (folding PP>0 bits needs a reverse message per tick; follow-up). A worker stuck inside a backend call (not a collective) is still only released by that call returning or by a per-call bound (#44343); the health bit covers thread death and collective failure. `/flush_cache`/detach while a worker is still inside a hung backend call still fail their 10 s join (flush raises out of the scheduler, pre-existing; #44348); once the call returns both succeed. A worker that dies loses the acks it had not published, so its in-flight operation's host tail stays allocated until re-attach; under a dead backup thread, cache-mode `ongoing_backup` host locks and already-queued buffer-mode write staging stay pinned until re-attach (only new work is gated).

**Rebase note.** The branch was brought up to date with a merge of `main`; the conflicts were #43344 (the scheduler-thread PP reduce this branch guarded no longer exists), #44614 (the degrade cut now rides `deadline_expired`) and the shared-memory count exchange (health bit split out there too). The GPU runs below were done on the first revision of this PR; the rebased code was validated on CPU (below).

## Speed Tests and Profiling

Healthy path (Qwen2.5-1.5B-Instruct, TP2, `file` backend, `buffer_only`, `write_through`, page 64, 16 prompts x 6-8k tokens, seed / flush / replay; first revision):

| policy | replay full hits | replay TTFT p50 / p90 / max | gauge |
|---|---|---|---|
| `timeout` | 16/16 (99.0 % cached) | 0.128 / 0.191 / 0.244 s | 1 on both ranks |
| `wait_complete` | 16/16 (99.0 % cached) | 0.129 / 0.203 / 0.245 s | 1 on both ranks |

(0 ERROR lines.) The health bit adds one int to an existing all-reduce (or one column of the shared-memory row) per scheduler tick; no new collectives on the healthy TP path.

Wedge path (`wait_complete`, `storage_sync_timeout: 20`, rank 1's `batch_exists` hangs 90 s on the first query; first revision): the faulted request completes after 20.09 s and the eight L3-hit requests queued behind it after 10.1-10.2 s (they were released by the same rank-agreed cut), short prompts 0.03 s throughout; both ranks log `HiCache storage sync failed ... Timed out waiting 20000ms` / `HiCache storage pipeline unhealthy ...` once, `sglang:hicache_storage_healthy` drops to 0 on both ranks, `/health` stays 200; a second wave 60 s later is served cold at 0.04-0.16 s TTFT; once the hung call had returned, `/flush_cache` succeeded and both query threads were idle at `queue.get`. Before this change the identical fault stalls every L3-hit request forever and `/flush_cache` crashes both ranks.

Unit tests (CPU, rebased head): `test/registered/unit/mem_cache/test_hicache_storage_sync_recovery.py` (one two-rank gloo spawn running the hit-query timeout, ack-alignment and dead-worker cases through the production `check_hicache_events` round; knob parsing/validation and timeout plumbing; the PP ticket group receives the timeout; a controller without started Python workers reads healthy while an exited worker reads dead). The two-rank case fails on the pre-fix source (the query thread dies) and on the first revision of this PR (the cross-group ack is skipped on one rank and blocks the other for the healthy group's timeout). Existing suites rerun on the rebased head together with the new one: `test_buffer_mode_sidecar`, `test_hicache_pp_sync_drain`, `test_pp_prefetch_ticket`, `test_storage_prefetch_lifecycle`, `test_unified_hicache_regressions`, `managers/test_scheduler_hicache_events` — 53 passed, 3 skipped (47 subtests). `test_pp_prefetch_ticket::test_file_attachment_enables_pp_tickets` now drives the group creation through `_start_storage_threads`, where the group is built. Not run: AMD/NPU lanes, PP>1 (no PP2 buffer-only step-time check; the relay is limited to the ticket-less shape) and mooncake/hf3fs/nixl e2e.
