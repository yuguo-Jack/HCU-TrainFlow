# [AMD] Add JIT cooperative DSA top-k

[Upstream PR](https://github.com/sgl-project/sglang/pull/39673) · state: closed · merged: False

## Original PR description

## Summary

- add an in-tree cooperative HIP DSA top-k kernel compiled through `sglang.kernels.jit`
- specialize on the requested top-k at first use and support every width from 1 through 4096, including K=2028
- support raw rows, compact page tables with optional raw-index output, page-size-1 tables, and ragged offsets
- default DSA and DSV4 models on wave64 ROCm GPUs to this path while honoring an explicit `SGLANG_OPT_USE_TOPK_V2` setting
- retain the existing kernels as fallback on unsupported HIP architectures and unsupported top-k values

This is based directly on `main` and is independent of #39631. The `sgl-kernel` AOT sources are unchanged.

## Performance

MI355X steady-state graph-replay microbenchmark, legacy DSV4 kernel / cooperative HIP kernel speedup, averaged over batches 1, 8, 32, and 128:

| score length | K=512 | K=1024 |
|---:|---:|---:|
| 8,192 | 1.01x | 1.06x |
| 32,768 | 1.15x | 1.18x |
| 65,536 | 1.46x | 1.43x |
| 100,500 | 1.76x | 1.94x |
| 131,072 | 2.04x | 2.24x |

JIT compilation is a one-time warmup cost and is excluded from these steady-state numbers. At the smallest 8K/K=512/batch=1 point, the cooperative path is about 12% slower; the average at that length is neutral.

## Validation

- MI355X JIT kernel suite: 9 passed
- widths K=256/512/1024/2028/2048/4096
- 1,048,576-score row with K=2028: exact selected-score multiset match against `torch.topk`; all 2,028 output indices were unique and in range
- `seq_len < topk`, zero-length rows, and row-split execution
- CUDA graph capture with compact page tables and `raw_indices`
- page-size-1 and ragged transforms
- environment-variable default and explicit-priority tests: 3 passed, 2 subtests passed
- pre-commit on all changed files

- tianxiaojiang4 · comment · 2026-09-18T04:56:17Z · [source](https://github.com/sgl-project/sglang/pull/39673#issuecomment-5725371692)

This also fixes a silent **correctness** bug, which isn't visible from the PR title or body — worth stating explicitly, since it changes how this should be prioritized. Right now it reads as a 1.0–2.2x perf change, and the defect is only described inside the new header comment.

`topk_transform_paged` is the entry point the DeepSeek-V4.1 low-ratio HIP indexer reaches for its final selection (`low_ratio_backend_hip.topk_transform_paged_sorted` → `topk_transform_paged`), so the dispatch this PR adds moves that path off `radix_topk` as well. We measured that kernel on MI355X / gfx950 independently of this PR, and it reproduces the failure your header describes for GLM-5.2.

**The kernel in isolation** — k=512, 8 rows, 30 runs on identical inputs, comparing the selected *score multiset* against `torch.topk` so that a different pick among equal scores counts as correct:

| candidates in the threshold bin | distinct selected sets / 30 | rows with a wrong score multiset |
|---:|---:|---:|
| 4,096 | 1 | 0 / 240 |
| 5,119 | 1 | 0 / 240 |
| 5,120 | 1 | 0 / 240 |
| 5,121 | 6 | 42 / 240 |
| 6,144 | 30 | 240 / 240 |
| 16,384 | 30 | 240 / 240 |

The cliff is exactly `SMEM_INPUT_SIZE`, and nothing else changes across it.

**On real DeepSeek-V4.1-Flash decode scores** — 12,008 tokens of context, the indexer's top-k inputs tapped and frozen to disk, then the kernel re-run 20x on those bytes so the scorer is out of the loop entirely:

| row | threshold-bin population | recall of true top-512 | distinct sets / 20 |
|---|---:|---:|---:|
| L20 | 2,360 | 1.0000 | 1 |
| L24 | 11,573 | 0.9395–0.9609 | 13 |
| L24 (bs8) rows 0,1,5,6 | 600–1,382 | 1.0000 | 1 |
| L24 (bs8) row 2 | 7,753 | 0.8789–0.9004 | 15 |
| L24 (bs8) row 3 | 6,332 | 0.9609–0.9746 | 6 |
| L24 (bs8) row 4 | 8,198 | 0.8965–0.9199 | 11 |
| L24 (bs8) row 7 | 6,663 | 0.9805–0.9883 | 8 |

Overflow ⟺ wrong and unstable, with no exceptions across the ten rows. Every affected row also has exactly one score equal to the k-th, so this is not tie-breaking — the kernel is dropping candidates it never ranked. For comparison on the same rows, `fast_topk` (the existing coop kernel, at its own k=2048) returns recall 1.0000 and a single distinct set on all ten, including the overflowing ones.

One caveat on representativeness: our capture used a synthetic prompt (a single sentence repeated), which plausibly concentrates the indexer scores more than real traffic would. So these numbers establish the mechanism and the cliff, not a production hit rate — your GLM-5.2 capture is the better evidence on frequency.

Separately, and relevant because it decides where the cliff sits: the two ROCm build systems disagree on `SGL_TOPK_DYNAMIC_SMEM_BYTES` for gfx950. `python/sglang/kernels/aot/setup_rocm.py` gives it 40 KiB (5,120 entries); `3rdparty/amd/wheel/sgl-kernel/CMakeLists_rocm.txt` gives it 128 KiB (16,384). Our wheel came from the former, which is why our cliff is 5,120 while #36807 quotes 16,384 for gfx95x. Same source, different answer depending on which build produced the wheel.

Happy to re-run any of the above against this branch on MI355X if that would help move it along.
