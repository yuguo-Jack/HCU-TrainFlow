# [Perf] scheduler: Spread finished-request KV releases over decode steps

[Upstream PR](https://github.com/sgl-project/sglang/pull/43638) · state: open · merged: False

## Original PR description

## Motivation

When many requests finish in the same decode step (multi-turn traffic finishes in waves), the step's result processing runs `release_kv_cache` for every one of them before the next batch can be scheduled and launched. The overlap loop only hides one decode forward of CPU work, so the GPU waits for the rest.

Measured with CUDA events on the forward stream around each launch (no torch profiler), Inkling-Small-NVFP4 TP4 on GB300 with 128 multi-turn lanes: ordinary decode steps have no idle before the next launch (p99 3 us), but a step that releases >= 8 finished requests leaves the GPU idle for 8-16 ms on average, ~360 ms per run in total. A release is mostly per-request tree work (checkpoint insert, Mamba state hand-off), about half a millisecond of CPU each, so a wave of 32 does not fit in one forward.

## Modifications

Finished requests are queued on the result processor (`deferred_kv_releases`) instead of released inline, and drained oldest-first:

- at most 8 per decode step (`_KV_RELEASES_PER_DECODE_STEP`), so a wave spreads over the next few steps and each step stays inside the headroom the overlap loop has;
- all of them before deciding to retract (`update_running_batch` re-checks decode memory after draining, so deferred KV never causes a retraction);
- all of them on idle, and `is_fully_idle` is false while any are deferred (flush_cache / pause / weight updates see a drained pool);
- before prefill admission, the deferred requests that a waiting request may continue (its input starts with the finished request's tokens; a cheap necessary check, a false positive only releases early), so a next turn always finds its previous turn in the tree.

Every decision depends only on state that is identical across TP ranks (the deferred queue, the waiting queue, decode memory), so ranks release the same requests in the same order.

This is independent of #43600, which makes each release cheaper; this PR moves releases off the step that would otherwise stall. They compose.

## Accuracy / correctness

No change to what is cached; prefix hit rate unchanged in the benchmark below.

- New `test_deferred_kv_release.py`: per-step cap releases the oldest first; uncapped drain; only a continued turn is released early (shorter, diverging, or empty waiting lists release nothing); `update_running_batch` drains before retracting and does not retract when that frees enough; `is_fully_idle` is false while releases are deferred. Removing each mechanism (cap, early release filter, retract drain, idle check) fails its test.
- Scheduler unit-test stubs built with `Scheduler.__new__` get an empty `batch_result_processor` stub (and `waiting_queue` where `get_next_batch_to_run` runs).
- Unit suites (mem_cache, managers, disaggregation, dllm) and the Rust-core unified suite: same failures as main (pre-existing, unrelated), nothing new.

## Benchmark

Inkling-Small-NVFP4, TP4, `--kv-cache-dtype mxfp8`, `--max-total-tokens 2097152`, `--max-mamba-cache-size 1024`, 4x GB300, 128 multi-turn lanes, 16 timed turns, L1 only, rounds interleaved with main.

| | tok/s (3 rounds) | mean |
|---|---|---|
| main | 13155 / 13128 / 13129 | 13138 |
| this PR | 13276 / 13259 / 13298 | 13277 (**+1.06%**) |
| this PR + #43637 | 13430 / 13434 / 13394 | 13419 (+2.15%) |

Forward-stream idle in the steps that release >= 8 requests, measured together with #43637: ~364 ms -> ~29 ms per run.
