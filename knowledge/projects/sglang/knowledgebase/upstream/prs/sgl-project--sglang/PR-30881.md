# fix(reasoning): guard continue_final_message against non-string assistant content

[Upstream PR](https://github.com/sgl-project/sglang/pull/30881) · state: closed · merged: False

## Original PR description

## Motivation

An assistant message's `content` is typed `Union[str, List[ContentPart], None]` (see `ChatCompletionMessageGenericParam` in `protocol.py`), but `ReasoningParser.__init__` forwards it verbatim as `previous_content` when `continue_final_message` is set:

```python
kwargs["previous_content"] = request.messages[-1].content
```

`BaseReasoningFormatDetector.__init__` then treats that value as a string:

```python
self.previous_count = len(previous_content)          # len(None) -> TypeError
if self.think_start_token in self.previous_content:  # "<think>" in None -> TypeError
```

So a valid request with `continue_final_message=true` whose last assistant turn has `content: null` (a tool-only turn) crashes with `TypeError: object of type 'NoneType' has no len()`. On the non-streaming path this is caught and surfaced as an HTTP 500 (`serving_chat.py`, reasoning branch); on the streaming path the parser is constructed lazily inside `_process_reasoning_stream` with no guard, so the exception propagates mid-stream. A multimodal list `content` does not raise but silently miscomputes the reasoning state (`previous_count` becomes the number of parts and the `<think>` membership check is meaningless).

`serving_chat._apply_continue_final_message` already handles this exact value with an `isinstance(last_content, str)` guard and explicitly "ignores multimodal content (lists)". The reasoning-parser construction path just omitted the same guard.

This is independent of #30193 / #30000, which address a different defect (Glm45Detector not accepting the `continue_final_message` kwarg). That fix touches only `Glm45Detector.__init__`; this one touches `ReasoningParser.__init__` and adds a separate test method.

Repro before the fix:

```python
req = ChatCompletionRequest(
    model="test",
    messages=[
        ChatCompletionMessageUserParam(role="user", content="Hi"),
        ChatCompletionMessageGenericParam(role="assistant", content=None),
    ],
    continue_final_message=True,
)
ReasoningParser("qwen3", request=req)
# TypeError: object of type 'NoneType' has no len()
```

After the fix the same request constructs cleanly with `continue_final_message=False` and `previous_content=""`; a normal string `content` is unchanged.

## Modifications

- `python/sglang/srt/parser/reasoning_parser.py`: only forward `continue_final_message` / `previous_content` when the last assistant message's `content` is a `str`, mirroring `serving_chat._apply_continue_final_message`. Non-string content falls back to the detector's default (no continuation).
- `test/registered/unit/parser/test_reasoning_parser.py`: add `test_continue_final_message_non_string_content` covering `content=None` and a multimodal list, asserting no crash and the safe default. The case fails on the pre-fix code (TypeError for `None`) and passes with the fix.
