# [sglang-miles] [Diffusion] Support distributed weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/42854) · state: closed · merged: True

## Original PR description

## Motivation

This ports #38540 from `sglang-miles-h3` to `sglang-miles`. miles-diffusion's docker image and CI now build from `sglang-miles`, which has no diffusion endpoints for distributed weight updates. The async (one-step-off) DiffusionNFT trainer in radixark/miles_diffusion#232 runs the trainer and the rollout engines on separate GPUs. It needs these endpoints to broadcast new weights to the engines over NCCL instead of round-tripping through disk or CUDA IPC.

## Modifications

The diffusion engine gets the same NCCL weight-sync flow that the LLM engine (srt) already has:

- `POST /init_weights_update_group`: each engine rank joins a custom process group at `rank_offset + world rank`. The trainer is rank 0. DP replicas share one torch world, so these ranks are unique.
- `POST /update_weights_from_distributed`: each engine rank allocates tensors from `names/dtypes/shapes` and receives the trainer's broadcast. It then loads them through the existing `WeightsUpdater.update_weights_from_tensor`, so `target_modules`, `weight_update_mode="lora_merge"`, `lora_alpha` and `lora_rank` behave exactly as they do for `/update_weights_from_tensor`.
- `POST /destroy_weights_update_group`.
- The scheduler runs each of these ops on every rank and all-gathers each rank's `(success, message)` over the world CPU group, so the request fails if any rank failed. An op that raises is reported as a failure instead of propagating, so every rank still reaches the all-gather.
- `AsyncSchedulerClient` sends these three requests to all DP replicas **concurrently**. Every replica takes part in the same collective, so the sequential control-request fan-out would deadlock.

**Fix in `srt/utils/common.py:init_custom_process_group`.** When the default process group is bound to a device (`init_process_group(device_id=...)`, which the diffusion engine does), torch builds every new NCCL group by splitting the default communicator. A group spanning processes from other worlds then silently ends up with each process in a group of its own: the broadcast "succeeds" and the receiver keeps uninitialized memory. The helper now builds the group as if the default PG were unbound, and restores the binding afterwards. This covers both lazy and eager (`device_id=`) groups. srt's default PG is not bound, so this is a no-op for the LLM engine. Two processes reproduce the bug, each with its own device-bound world-size-1 default PG broadcasting through `init_custom_process_group`:

| default PG | group init | before | after |
|---|---|---|---|
| bound | lazy | rank 1 keeps its own data | ok |
| bound | eager (`device_id`) | rank 1 keeps its own data | ok |
| unbound | lazy | ok | ok |

Porting notes (relative to #38540): the only textual conflict was the import block in `scheduler.py`. Beyond the port, this PR also does the following:
- moves the `split_from` workaround into `init_custom_process_group`, where it covers eager groups too; the original post-construction reset did not;
- drops request validation that srt does not have, and that cannot prevent a sender hang anyway, because the trainer broadcasts while the request is in flight;
- drops the sync client's collective branch, which had no caller.

## Tests

- `test/unit/test_distributed_weight_update.py` covers concurrent fan-out to DP replicas, propagation of a non-primary rank's failure to the HTTP result, and a raising rank still joining the all-gather. 3 passed.
- `test/single_test_file/test_update_weights_from_distributed.py` (one engine GPU plus one sender GPU, both with device-bound default PGs). For full weights and for `lora_merge`, the transformer checksum after an NCCL update equals the checksum after the same update through `update_weights_from_tensor`. This holds across repeated updates, and the group is destroyed and re-created between cases. It also guards the `init_custom_process_group` fix: a split group would leave the engine with garbage, so the checksums would not match. The file is registered in `STANDALONE_FILES`.
- `pre-commit run` on the changed files is clean.

Local run on this branch (B200; one engine GPU plus one sender GPU, sharing the GPUs with another job), model `black-forest-labs/FLUX.2-klein-base-4B`:
