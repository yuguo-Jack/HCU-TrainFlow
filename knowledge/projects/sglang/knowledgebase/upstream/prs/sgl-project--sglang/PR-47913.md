# [Perf] [NVIDIA] trtllm_mla: Build fp8 chunked-prefill Q/K/V in one launch

[Upstream PR](https://github.com/sgl-project/sglang/pull/47913) · state: open · merged: False

## Original PR description

## Motivation

With `--attention-backend trtllm_mla --kv-cache-dtype fp8_e4m3`, MLA chunked prefill (`MHA_CHUNKED_KV`, which every
eager extend takes on `trtllm_mla`) feeds the TRT-LLM ragged fp8 kernel through several passes:

- `_concat_and_cast_mha_k` builds K = [k_nope | k_pe] in bf16. When the per-rank head count is not a power of two
  (12 heads, for example), this falls back to aten slice copies.
- `_quantize_fp8_qkv` then casts K and V to fp8 with strided copies, for the current chunk and again for every
  cached-prefix chunk.
- The same bf16 Q is cast to fp8 once per ragged launch: once for the causal pass, plus once per prefix chunk.

The pieces to fix this are already in the tree:
- `forward_mha` already has backend hooks for it (`pack_prefix_chunk_kv`, `prepare_chunked_prefill_qkv`).
- The fused `mla_kv_pack_quantize_fp8` kernel already exists, and `CuteDslMLAPrefillBackend` already uses it.
- `TRTLLMMLABackend` implements neither hook, so the default SM100 DeepSeek deployment keeps the slow path.

Related PRs:
- #41716 packs the prefix chunks behind a default-off env flag. This PR makes the pack the default, also covers the
  current chunk, and casts Q once.
- #33950 casts Q once through a new base-class hook. Here the existing `prepare_chunked_prefill_qkv` does it.

## Modifications

- `TRTLLMMLABackend.pack_prefix_chunk_kv`: packs each prefix chunk's K/V into contiguous unit-scale fp8 with
  `mla_kv_pack_quantize_fp8`, in one launch.
- New hook `pack_extend_kv`, called from `forward_normal_prepare`: the same pack for the current chunk. It returns
  None under the flashinfer fallback, which reads bf16.
- `TRTLLMMLABackend.prepare_chunked_prefill_qkv`: casts Q to fp8 once per layer.
- `_quantize_fp8_qkv` passes K/V that are already fp8 through at unit scale.
- Without an fp8 KV cache, or with `qk_rope_head_dim == 0`, the hooks are hidden in `__init__` (as the Triton
  backend does), so bf16 KV keeps the existing path.
- Unit test `test/registered/unit/layers/attention/test_trtllm_mla_fp8_prefill_pack.py`.

**Numerics.** The pack computes bf16 → fp32 → e4m3 (RNE) at unit scale. That is what `.to(torch.float8_e4m3fn)`
produced, so Q/K/V and the attention output are bit-identical. The MHA prefill layer (`attn_mha`) never loads
checkpoint KV scales, because they map to `attn_mqa`. So its k/v scales are 1.0, and the unit-scale pack is the same
quantization the stock path used.

## Accuracy Tests

**Setup.**
- Model and GPU: DeepSeek-V2-Lite-Chat (real weights) on 1× B200, v0.5.22 (`lmsysorg/sglang:v0.5.22`). It has the
  same per-GPU MLA geometry as DeepSeek-V3 at TP8: 16 heads, kv_lora 512, rope 64.
- Server flags: `--attention-backend trtllm_mla --kv-cache-dtype fp8_e4m3 --disable-prefill-cuda-graph
  --chunked-prefill-size 16384 --mem-fraction-static 0.85`.
- Each A/B runs stock and this PR on the same GPU, in one job, with the same flags.
- Why `--disable-prefill-cuda-graph`: at the default setting, extends of 2048 tokens or fewer run the absorbed path
  inside the prefill CUDA graph and never reach this code. DeepSeek-V3 has that graph off by default.

**Unit test.** The test checks that the pack matches stock bitwise for 12, 16 and 128 heads, and that the ragged
prefill kernel output matches bitwise on SM100. It passes on B200, together with the existing
`test_mla_kv_pack_quantize_fp8.py` (9/9).

**End-to-end bit-exactness.**
- Run: greedy 32-shot GSM8K at batch size 1, on 150 questions.
- The shared ~6.6k-token few-shot prefix is served from the radix cache, so every request after the first runs the
  prefix pass.

| pair | identical greedy text | same final answer |
|---|---|---|
| stock vs stock | 150/150 | 150/150 |
| stock vs this PR | **150/150** | 150/150 |

**Batched evals.** These run 128 requests concurrently, so batch composition varies from run to run. Given the
bit-exact result above, the differences here are that noise. All evals are accuracy, so higher is better (↑).

| eval | before | this PR |
|---|---|---|
| GSM8K (`sgl-eval`, 1319) ↑ | 59.3% | 57.7% |
| MMLU (`sgl-eval`, 2000) ↑ | 34.4% | 35.1% |
| 32-shot GSM8K (1319, ~6.6k-token prompts) ↑ | 66.4% | 66.2% |
| 400-shot GSM8K (300, ~79k-token prompts) ↑ | 65.7% | 63.7% |



## Speed Tests and Profiling

Arrows give the better direction: ↓ = lower is better, ↑ = higher is better. A Δ is an improvement when its sign
matches the arrow.

### DeepSeek-V2-Lite-Chat, 1× B200 (real weights)

Same server as above. The client is `bench_serving --dataset-name random-ids --tokenize-prompt --random-range-ratio 1.0
--flush-cache`. Arms alternate inside each round (stock, PR, stock, PR), and each value is the mean over the runs.
This change acts only on prefill chunks, and gains grow with the cached prefix each chunk re-reads.

| workload | runs per arm | metric | before | this PR | Δ |
|---|---|---|---|---|---|
| 6 × 128k → 1, concurrency 1 | 2 | mean TTFT ↓ | 2219 ms | 2115 ms | **−4.7%** |
| 8 × 64k → 1, concurrency 4 | 2 | mean TTFT ↓ | 3144 ms | 3026 ms | **−3.8%** |
| 16 × 32k → 1, concurrency 1 | 4 | mean TTFT ↓ | 399.8 ms | 389.7 ms | **−2.5%** |
| 128 × 8k → 32, concurrency 128 (no prefix) | 2 | mean TTFT ↓ | 5340 ms | 5271 ms | −1.3% |

The spread is small: for 32k, the stock runs are 398.7–401.5 ms and the PR runs 389.2–389.9 ms.


**Profile** (torch profiler, one 40k-token prompt, 4 forward steps, every MLA layer):

| kernel | before | this PR |
|---|---|---|
| `concat_and_cast_mha_k_kernel` launches ↓ | 108 | **0** |
| fused pack (`mla_kv_pack_quantize_fp8`) launches | 0 | 162 |
| GPU time in concat + bf16→fp8 cast + pack kernels ↓ | 21.9 ms | 8.0 ms |

- **Low end of the gain:** V2-Lite has 16 heads per rank, which already takes the fast Triton concat. At 12 heads per
  rank, the concat falls back to aten slice copies, so the gain is larger (next section).
