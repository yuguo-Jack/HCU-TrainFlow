# [Perf] beam: Add optional cuTile BF16x3 router GEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/45361) · state: open · merged: False

## Original PR description

## Motivation

Beam's router multiplies BF16 hidden states by an FP32 gate in each of its 49 MoE layers. #45256 runs it with the tiny FP32 GEMM, the GEMV and the cuBLAS BF16x3 GEMM. This part adds the cuTile BF16x3 router GEMM from #44747 and makes it Beam's default router on Hopper and SM10x Blackwell.

It's optional: without it, Beam serves on the cuBLAS router. It needs the `tileiras` compiler, which is #45290. Position 7 of 7 in the merge order below. It is based on #45290's branch (`beam-stack-deps-tileiras`), so its diff shows only this part.

## Modifications

- `kernels/ops/gemm/router_gemm_cutile.py`: BF16 activations × FP32 router weights → FP32 logits. It uses a three-part BF16 split of the weight prepared at load time, and combines K tiles with explicit FP32 rounding. Small batches use split-K plus a reduction.
- `models/beam.py`:
  - `BeamRouterLinearMethod` refreshes the split weight in place after weight loading, so captured graphs see updated weights.
  - Above the tiny FP32 GEMM's 16 tokens, the router uses cuTile.
  - FP8 and NVFP4 checkpoints also keep the tiny FP32 GEMM when cuTile is on.
- Shared splitter ownership: Beam and the cuBLAS wrapper import `split_fp32_to_bf16x3` from `ops.quantization.bf16x3_split`, registered as `quantization.split_fp32_to_bf16x3`. The old inline splitter, GEMM inventory entry and shared split scratch are removed. This branch carries the canonical module from #45254 until its later restack; the existing `out=parts` use is unchanged.
- `SGLANG_BEAM_ROUTER_BACKEND` chooses `cutile` (default), `cublas` or `torch`.
- The kernel is registered in the kernel inventory as `gemm.router_gemm_bf16x3`, with a new `cutile` `KernelBackend` provenance value (and the matching `forward_cutile` stub in `BaseFusedOp`), for SM90 through SM10x.

This part adds no test code. The recorded GB300 serving runs below belong to earlier revisions.

This part changes **9 files (+340 / -64)** relative to its #45290 base branch.

## Validation

**The splitter migration in `4a8c0cde40` has not been reverified, as requested.** No tests, lint, pre-commit, import/compilation smoke, GPU checks or benchmarks were run for that update. CuTile arithmetic and model dispatch are unchanged; this was a targeted ownership migration, not a full stack restack.

### Historical results

The results below come from earlier revisions, before `4a8c0cde40`. They do not establish verification of the latest update.


- Synced with main: the branches fast-forward from their previous heads and merge into main `b57b5e2286` without conflicts (#45257 merges that main, which includes #40478; the others are on `6efdd33d07`).
- No upstream code is copied into the stack any more. The cherry-picks of #42930, #43168 and #43170 (merged), #43169 (closed) and #43216 (open) are reverted, and #40479 and #43941 come in as merges of those PRs in #45257 (#40478 has since merged into main).
- On 4×GB300 with the public `reflection/Beam-1.0-501B-A23B-NVFP4` checkpoint and the cookbook GB300 NVFP4 low-latency recipe, serving main `6efdd33d07` + #43216, #40478, #43941 and #40479 + this stack:
  - With #45290 and #45361: GSM8K 96.44–96.59% over three server runs (sgl-eval 0.1.3, 1,319 questions, temperature 0), with zero request errors. Chat reasoning, streaming, a chat tool call, Responses text, a Responses function call, a full Responses shell round trip and `/tokenize` all pass. A profiler trace shows the cuTile router kernel running.
  - Without #45290 and #45361: GSM8K 96.51% in both of two server runs, with zero request errors, and the same checks pass.
- The Beam E2E test in #45257 passes on two 4×GB300 nodes (prefill TP4 on one, decode TP4 on the other, Mooncake over multi-node NVLink, in place of the test's single-node 8-GPU layout): GSM8K 96.51–96.89% at temperature 0.7 over three runs, decode accept length 4.53–4.55, and single-request accept length 4.92 at about 750 tok/s.
- Main's existing GPU tests for the code the stack changes pass unedited on GB300: TRT-LLM MHA (dense, graph metadata, encoder-only, stride parity), SWA FlashInfer, tiny GEMM, collectives, Triton MoE and the DFlash buffer and kernel tests. pre-commit passes.
- On GB300 the registered kernel matches an FP64 reference at Beam's router shape with a mean absolute error of 1.6–2.7e-7 for 1 to 2,048 tokens over two runs, and importing `sglang.kernels.ops` does not import `cuda.tile`.
- Earlier measurements from #44747, unchanged by this sync:
  - Router latency per call at Beam's shape (N=256, K=5120, CUDA graphs), against the cuBLAS path: the same up to 16 tokens; from 32 to 2,048 tokens, 2–5 µs faster on GB300 and 4–9 µs faster on H200.
  - Mean absolute error against FP64: 1.6–2.8e-7 for cuTile, against 1.9–6.2e-6 for cuBLAS BF16x3.
- `tileiras` must share its major.minor with `nvidia-cuda-nvcc` and `nvidia-nvvm`. cuda-tile rejects mismatched wheels, and the router then fails at startup.
