# [Intel GPU] Map the generic profiler activity to XPU on Intel GPUs

[Upstream PR](https://github.com/sgl-project/sglang/pull/38267) · state: open · merged: False

## Original PR description

Before this change, a default profile request on an Intel GPU recorded no device kernels, because `GPU` always meant the CUDA activity.
Now `GPU` means the XPU activity on XPU, and both profiler paths use one shared resolver that also removes duplicate activities.
On CUDA the default request resolves as before. Two things change there: repeated names now collapse to one activity, and the v2 path now passes an explicit `XPU` to torch.

## Motivation

Requesting a profile with the generic `GPU` activity on an Intel GPU produced a trace that opened fine, had a plausible size, and contained **no device kernels**. The profiler appeared to work and the data was empty of the thing being profiled.

Two independent code paths each built the same name-to-activity map by hand, and both hardcoded `GPU` to the CUDA activity:

`srt/managers/scheduler_components/profiler_manager.py` (scheduler path):
```python
        activity_map = {
            "CPU": torch.profiler.ProfilerActivity.CPU,
            "GPU": torch.profiler.ProfilerActivity.CUDA,
        }
        if current_platform.is_out_of_tree():
            if hasattr(torch.profiler.ProfilerActivity, current_platform.get_torch_profiler_activity_str()):
                activity_map[...] = current_platform.get_torch_profiler_activity()
        if hasattr(torch.profiler.ProfilerActivity, "XPU"):
            activity_map["XPU"] = torch.profiler.ProfilerActivity.XPU
```

`srt/utils/profile_utils.py`, `_ProfilerTorch.start()` (v2 path) has the same map, without the `XPU` key and without the `hasattr` guard on the out-of-tree name.

The `CUDA` activity collects nothing on XPU, so the request resolved to a tracer with nothing to record. A caller who passed `XPU` explicitly could get device events from the scheduler path but not from the v2 path. The generic name `GPU` is in the default list of the profile endpoints. It was broken on both paths.

## Modifications

Replace both hand-written maps with one shared resolver in `profile_utils.py` and route both implementations through it:

- `get_torch_profiler_activity_map()`: on XPU, **both** `GPU` and `XPU` map to `ProfilerActivity.XPU`. Off XPU, `GPU` stays `CUDA`, and the explicit `XPU` key is still offered when the build exposes that activity.
- `resolve_torch_profiler_activities(activities)` turns names into activities in request order. It drops unknown names and **collapses duplicates**.

Three side effects of folding the copies together, all intentional:

**1. The v2 path gains the `hasattr` guard the scheduler path already had.** An out-of-tree platform naming an activity this torch does not expose is now skipped instead of raising an `AttributeError` from `get_torch_profiler_activity()`. `test_missing_out_of_tree_activity_is_ignored` covers it, and asserts the platform hook is not even called.

**2. The v2 path gains the explicit `XPU` key.** Under `SGLANG_PROFILE_V2=1`, a request that names `XPU` now reaches `torch.profiler` whenever the torch build exposes `ProfilerActivity.XPU`. Before, the v2 path dropped the name with no error. The scheduler path already passed it. `test_explicit_xpu_key_survives_on_a_non_xpu_platform` covers the key off XPU, and the added assertion below covers it on XPU.

**3. Duplicate collapsing changes behaviour on every platform, not only XPU.** It has to, because on XPU two names now resolve to one activity. `torch.profiler.profile` does not tolerate that on current torch. The behaviour differs by version:

```
# torch 2.11.0+cpu (what python/pyproject.toml:78 pins)
torch/profiler/profiler.py:162:  self.activities = set(activities) if activities else supported_activities()
>>> torch.profiler.profile(activities=[A.CPU, A.CPU])   # accepted, silently deduped

# torch 2.13.0+xpu (the image these measurements ran on)
>>> torch.profiler.profile(activities=[A.CPU, A.CPU])
ValueError: Activity ProfilerActivity.CPU specified more than once
```

So on the XPU image this is not forward-looking hygiene. Without the collapse, a `["CPU", "GPU", "XPU"]` request is a hard failure today. Removing `dict.fromkeys` and running the resolver in that container shows it:

```
torch 2.13.0+xpu
NO-DEDUP resolved: [<ProfilerActivity.CPU: 0>, <ProfilerActivity.XPU: 1>, <ProfilerActivity.XPU: 1>]
profile() RAISED: ValueError: Activity ProfilerActivity.XPU specified more than once
```

Collapsing in the resolver keeps an explicit both-names request working on either version instead of depending on which one is installed.

**Behaviour on CUDA.** The default request `["CPU", "GPU"]` resolves to `[CPU, CUDA]` on both paths, as before. `current_platform.is_xpu()` and `current_platform.is_out_of_tree()` are both false on CUDA. So the out-of-tree guard has no effect there, and `GPU` still resolves to `CUDA`. Only two things differ on CUDA. A repeated name now collapses before it reaches the constructor, which the constructor did itself on torch 2.11. And under `SGLANG_PROFILE_V2=1`, an explicit `XPU` now reaches `torch.profiler`. The v2 path dropped it before. The scheduler path already passed it.

I checked the v2 path with the platform mocked as CUDA and `torch.profiler.profile` patched to record its `activities` argument (torch 2.14.0+cu130):

```
request                  9fea3e9bb2           this PR
["CPU", "GPU"]           [CPU, CUDA]          [CPU, CUDA]
["CPU", "GPU", "XPU"]    [CPU, CUDA]          [CPU, CUDA, XPU]
["CPU", "CPU"]           [CPU, CPU]           [CPU]
```

On a host with no XPU device, torch accepts the extra `XPU` activity. It warns `XPU is not available, disabling XPU profiling` and continues. I ran that check on a host with no GPU, not on a CUDA GPU.

## Accuracy Tests

No model output changes. This change touches only how requested profiler activity *names* become torch activities.

`test/registered/unit/utils/test_profile_utils.py` (new, 6 tests, `register_cpu_ci(est_time=1, suite="base-a-test-cpu")`):

| test | asserts |
| --- | --- |
| `test_legacy_profiler_routes_generic_gpu_to_xpu` | the scheduler path passes `[ProfilerActivity.XPU]` for a `["GPU"]` request on XPU |
| `test_v2_profiler_routes_generic_gpu_to_xpu` | the v2 path does the same |
| `test_aliased_names_collapse_to_one_activity` | `["CPU","GPU","XPU"]` on XPU yields `[CPU, XPU]`, not `[CPU, XPU, XPU]`. `["CPU","XPU"]` on XPU yields `[CPU, XPU]` |

## Speed Tests and Profiling

**No speed claim.** This changes what the profiler records, not how the model runs. The resolver runs once per profile start.

I verified on hardware (eight Intel Arc Pro B70 at TP8, DeepSeek-V4-Flash-0731) that the trace now contains device work. A generic `GPU` request produced eight traces, one per rank, 37.0 to 51.6 MB each. A full scan of one trace found:

| category | events |
| --- | --- |
| `kernel` | 1,936 |
| `ac2g` (correlation arrows) | 12,128 |
| `gpu_memcpy` | 45 |

**An earlier version of this evidence was retracted and should not be reintroduced.** It cited host-side `xpu_driver` and `xpu_runtime` records as proof the fix worked. Those appear whether or not the fix is present, because the CPU activity collects them. So they prove nothing. Only the device-side categories in the table above distinguish the two states.

## Limits of the evidence, and what to check hardest

- **The duplicate-collapsing change is not Intel-only** and deserves a look from whoever owns the profiler paths. It is intentional. On the pinned torch 2.11 it has no effect, because the constructor deduplicated anyway. But the resolver, not torch, now owns that behaviour.
- **A third copy of the same mapping remains** at `srt/disaggregation/encode_server.py:2539`. Deliberately out of scope so this change stays to the two paths the scheduler uses, and so it does not pull in another owner group. It is called out in the commit message too.
- **The exact torch version where the `ValueError` was introduced is not pinned down.** Observed: 2.11.0 accepts a duplicate, 2.13.0 raises. 2.12 was not tested. The fix does not depend on which of the two it was.
- **`request-order preservation` is the resolver's own contract, not an observable torch behaviour on the pinned version.** The 2.11 constructor does `set(activities)`, which discards order regardless. The test guards the resolver so a future refactor cannot quietly start reordering.
- **Stopping the profile returned an internal server error** on the hardware run, although all eight traces were written correctly. That was not chased and is not known to be related to this change.
- **CI stops at the maintenance gate on this PR.** Both failed runs in the CI States block stop at the `check-maintenance` step. The gate (issue #21065) needs a `MIN_BASE_SHA` that `intel_dev` does not contain. No CI lane runs XPU tests on `intel_dev`, because `pr-test-xpu.yml` triggers only on `main`. Merges to `intel_dev` do not need green CI. At 297f7af357, pre-commit on the 3 changed files, both registration checks, `git diff --check` and the 6 unit tests pass locally (torch 2.14.0+cu130).

One of several small, independent changes split out of a larger DeepSeek-V4 XPU enablement branch. This one depends on none of the others.

File: `python/sglang/srt/utils/profile_utils.py` · line 39

Good question — passing `XPU` explicitly does work today on the default profiler path, and it keeps working after this. Three things it does not cover.

**The default collects nothing on Intel GPU.** `--profile-activities` defaults to `["CPU", "GPU"]`, and `"GPU"` mapped to `ProfilerActivity.CUDA` on every platform. On the pinned XPU wheel `torch.profiler.supported_activities()` is `['CPU', 'XPU']`, so a CUDA request can never produce device rows there. Measured on hardware rather than reasoned about: with the old mapping `/start_profile` produced traces containing no XPU events at all, and with the device-aware mapping the same request produces them, with a same-session control unaffected (ITL 31.19 ms against 30.93 ms, within noise). Mapping the generic `GPU` to the XPU activity is what makes the default command useful without the operator knowing to add anything.

**Explicit `XPU` resolved in only one of the two paths.** `profiler_manager.py` already carried `if hasattr(torch.profiler.ProfilerActivity, "XPU")`, so on the default profiler the name resolved. `_ProfilerTorch.start()` in `profile_utils.py` did not, so under `SGLANG_PROFILE_V2=1` it fell through `if a in activity_map` and was dropped with no error. The two copies of the map had drifted apart; this replaces both with one resolver so they cannot drift again.

**`GPU XPU` together becomes a duplicate, and torch stopped tolerating it.** Before this change `GPU` meant CUDA and `XPU` meant XPU, so the collision was unreachable; the aliasing introduces it.

| torch | behaviour on a duplicated activity |
|---|---|
| 2.11.0 (`python/pyproject.toml`) | `set(activities)` — silently deduplicated |
| 2.13.0+xpu (`python/pyproject_xpu.toml`) | `ValueError: Activity ProfilerActivity.XPU specified more than once` |
| 2.14.0 | same `ValueError` |

I ran the 2.13 on the pinned XPU build. Since the aliasing is what creates the collision, the deduplication has to land with it rather than separately.

So the short version: passing `XPU` by hand stays valid; this makes it unnecessary by default, consistent across both paths, and safe to combine with `GPU`.

I am glad to clarify this. Here is a shorter version of my earlier answer, plus one new test assertion.

`--profile-activities XPU` worked on the default profiler path before this PR, and it still works. The flag alone does not fix two cases:

1. The default `["CPU", "GPU"]` recorded no device events on XPU, because `GPU` mapped to `ProfilerActivity.CUDA` on every platform. On XPU, `GPU` now maps to `ProfilerActivity.XPU`.
2. With `SGLANG_PROFILE_V2=1`, the v2 map had no `XPU` key and dropped an explicit `XPU` with no error. Both paths now use one resolver.

The mapping does create one new case: `GPU` plus `XPU` now gives the same activity twice. torch 2.13 and 2.14 raise `ValueError` on a duplicate activity, so the resolver removes the duplicate.

Commit 297f7af357 adds an assertion that `["CPU", "XPU"]` on XPU resolves to `[CPU, XPU]`, which is the case you asked about. Before it, a change that removed the explicit `XPU` key on XPU passed all 6 tests. With it, that change fails 1 of the 6 tests.
