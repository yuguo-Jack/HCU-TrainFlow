# [Perf] IPC: add opt-in ZeroMQ frame buffers for MessagePack

[Upstream PR](https://github.com/sgl-project/sglang/pull/45097) · state: open · merged: False

## Original PR description

## Motivation

Reduce host copies for large MessagePack IPC messages. Keep the change optional because frame buffers add overhead for small messages.

## Modifications

- Add `SGLANG_ENABLE_MSGPACK_ZERO_COPY`, disabled by default.
- With the flag enabled, send MessagePack with `copy=False` and decode directly from received frame buffers.
- Apply the flag to all shared MessagePack socket helpers.
- Keep pickle IPC and the wire format unchanged. Tensor decoding still allocates owned storage.

```bash
SGLANG_USE_PICKLE_IPC=0 SGLANG_ENABLE_MSGPACK_ZERO_COPY=1 python -m sglang.launch_server ...
```

## Accuracy Tests

- **76 local tests passed**, with no skips, in the CUDA serving container.
- Text, token IDs, and expert bytes match between flag settings, including streaming and concurrent requests.
- Control operations, request abort, and pickle serving passed.

## Speed Tests and Profiling

### Native SGLang serving

**Model:** `PrimeIntellect/qwen3-moe-tiny`. **Hardware:** one NVIDIA B200, TP=1, BF16.
FlashInfer attention and CUTLASS MoE. Prefix caching and CUDA graphs disabled.
AIPerf uses native `/generate`, without Dynamo or the sidecar.

Results compare flag off → on, using medians of three runs per setting.
Each setting uses a separate loaded engine. Only one engine receives requests at a time.
Each run has 32 warmup requests. Runs issue requests for 30 seconds, except concurrency 128 runs, which measure 128 requests.

| Input / output tokens | Return experts | Concurrency | Requests/s, off → on | Host CPU/request change |
|---|---|---:|---:|---:|
| 128 / 16 | No | 512 | 342.732 → 339.102 | +0.1% |
| 128 / 16 | Yes | 512 | 336.334 → 329.885 | -2.7% |
| 16,000 / 1 | Yes | 16 | 15.356 → 15.336 | -7.1% |
| 16,000 / 1 | Yes | 128 | 15.167 → 15.244 | -9.2% |

Host CPU sums the HTTP/tokenizer and detokenizer processes, including their I/O threads.
The concurrency 128 case reaches 2.048M input tokens in flight. Engine capacity remains 131,072 tokens.
Large replies use less host CPU. Short expert replies lose 1.9% throughput, so the flag remains opt-in.

### CPU replay with larger batches

Intel Xeon Platinum 8568Y+, one sender and receiver, and one message in flight.
Real output structs carry synthetic int32 indices: 24 layers and four experts per layer.
CPU time sums both processes across the tensor and base64-string IPC hops, including serialization and decoding.
It excludes model inference, base64 conversion, HTTP, and Dynamo.

| Batch × sequence tokens | Messages/run | Copied CPU | Frame CPU | Reduction |
|---|---:|---:|---:|---:|
| 1 × 131,072 | 8 | 0.346 s | 0.239 s | 31% |
| 1 × 1,048,576 | 3 | 4.195 s | 2.747 s | 35% |
| 32 × 131,072 | 1 | 14.817 s | 8.745 s | 41% |

Results compare copied MessagePack with frame buffers, using medians of three runs after one warmup per run.
All full-value comparisons passed, including the 2 GiB base64 batch. These replays do not test million-token model inference.
Small control replies use 4.5% more CPU with frames.
