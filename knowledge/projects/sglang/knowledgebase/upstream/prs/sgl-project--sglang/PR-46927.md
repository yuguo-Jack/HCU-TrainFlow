# [Feat] clover: Add native serving and self-speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/46927) · state: open · merged: False

## Original PR description

## Motivation

Add native SGLang serving support for [Diffuspace/Clover-35B-A3B-Preview](https://huggingface.co/Diffuspace/Clover-35B-A3B-Preview), using a shared model for parallel draft generation and autoregressive verification.

Clover generates a block of draft tokens through its preview pathway, verifies the proposals through the autoregressive pathway, and commits the accepted prefix for the next decoding step.

## Modifications

- Register `CLOVER` as a speculative-decoding algorithm and add `CloverMoeModelLM` support.
- Implement Clover draft generation, verification, and accept-token bookkeeping.
- Manage KV cache and recurrent state across preview and verification passes.
- Integrate preview attention through `CloverPreviewFlashInferBackend` and the Clover linear-attention backend.
- Support CUDA-graph execution for Clover decoding.
- Add `--speculative-clover-accept-rule {threshold,exact}`: threshold remains the default; exact matches drafts against the penalty-adjusted verify argmax and stops at the first mismatch. 
- Add configurable threshold parameters and Clover sampling penalties.
- Validate model compatibility, draft width, launch configuration, and unsupported request options.
- Document Clover launch configuration, acceptance semantics, sampling defaults, and platform limitations in the speculative-decoding guide.

## Changes to shared SGLang infrastructure

- Add configuration and dispatch hooks for the Clover model and worker.
- Integrate Clover request validation and decoding results with the scheduler.
- Keep Clover preview attention adaptation in its dedicated backend subclass.

Apart from the review, I have a question:
[Question: should penalty counts include earlier drafts in the same block?]
It looks like every row in a verify block uses the same committed_counts, built only from committed output_ids. If I'm reading this right, when a draft repeats a token proposed earlier in the same block, that second occurrence isn't penalized. Token-by-token AR decoding would penalize it at that position.

Is this intentional, e.g. to keep the penalty computation block-parallel or to match how the checkpoint was evaluated? If so, it might be worth stating in the docs, since Clover enables presence_penalty=0.9 and repetition_penalty=1.05 by default. Under those defaults, exact acceptance wouldn't be equivalent to penalized greedy AR, and the gap would grow with verify position.
