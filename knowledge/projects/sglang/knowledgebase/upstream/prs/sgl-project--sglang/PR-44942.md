# [Fix] openai: Forward replayed reasoning to gpt-oss thinking field (#44931, #44932)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44942) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44931 and #44932.

1. **Multi-turn reasoning history is silently dropped for `gpt-oss` and other templates reading `message.thinking` (`#44931`)**:
   - `OpenAIServingChat._apply_jinja_template()` and `process_content_for_template_format()` populate `reasoning_content` on the processed message dict, whereas `gpt-oss` Jinja templates read `message.thinking` (`{%- if "thinking" in message %}`).
   - As a result, prior-turn reasoning replayed via `reasoning_content`, `thinking`, or structured `{"type": "thinking", ...}` content blocks was omitted from the rendered prompt.

2. **Anthropic `/v1/messages` multi-turn thinking on `gpt-oss` fails with HTTP 500 (`#44932`)**:
   - `OpenAIServingChat.supports_native_reasoning_history()` only checked `chat_encoding.spec_owns_reasoning_history()`, returning `False` for Jinja-based templates like `gpt-oss`.
   - `AnthropicServing._convert_to_chat_completion_request()` therefore fell back to `wrap_reasoning_history()`, splicing `<|channel|>analysis<|message|>...<|end|>` into `content`, which triggers `raise_exception("You have passed a message containing <|channel|> tags in the content field...")` in the `gpt-oss` template.

## Modifications

- **`python/sglang/srt/parser/jinja_template_utils.py`**:
  - Added AST-based `_jinja_template_reads_field()`, `template_reads_reasoning()`, and `template_reads_thinking()` (built on `_try_extract_ast()`, inspecting `Getattr`, `Getitem`, `Call(get)`, `Compare(in, notin)`, and `Filter(map, rejectattr, selectattr)`), and refactored `jinja_template_may_reorder_tool_results()` to share `_jinja_template_reads_field()`.
  - Updated `process_content_for_template_format()` to extract and join `thinking_parts` (`"\n".join(thinking_parts)`) once across both `"openai"` and `"string"` content formats into `new_msg["reasoning_content"]` without mutating the caller's `msg_dict` in place.
- **`python/sglang/srt/entrypoints/openai/protocol.py`**:
  - Added `thinking` alias normalization to `reasoning_content` on `ChatCompletionMessageGenericParam` (`exclude=True`).
- **`python/sglang/srt/entrypoints/openai/serving_chat.py`**:
  - In `_apply_jinja_template()`, copy `reasoning_content` to `thinking` on assistant messages when the template reads `thinking` and not `reasoning_content`, and gate the `tool_calls` + `content` -> `thinking` merge on `self.is_gpt_oss`.
  - Extended `supports_native_reasoning_history()` to return `True` when the tokenizer's Jinja template natively reads `reasoning_content` or `thinking`.

This detects field usage by substring matching on the template text, which is wrong in both directions:

- **False positive**: `{# reasoning_content #}` in a comment, or `{{ 'message.thinking' }}` as a string literal, sets `supports_native_reasoning_history()` and changes Anthropic history handling for no reason.
- **False negative**: `message.get('thinking', '')` is a common idiom and is not matched, so the history is still dropped.

This module already has `_try_extract_ast()` (used by `jinja_template_may_reorder_tool_results()` and `detect_jinja_template_content_format()` ten lines above). Walking `Getattr` / `Getitem` / `Call(get)` / `Compare(in, notin)` / `Filter(selectattr, map)` gives the same answer without either problem, and keeps this file consistent.

This merge is not scoped to gpt-oss, so it fires for **any** template that reads `thinking` but not `reasoning_content`. For those templates the visible assistant text is moved into the reasoning channel and `content` is emptied.

Minimal repro — template `{% for m in messages %}{{ m.thinking }}|{{ m.content }}{% endfor %}`, message:

```json
{"role": "assistant", "reasoning_content": "analysis", "content": "visible", "tool_calls": [ ... ]}
```

renders `analysis|` instead of `analysis|visible`.

The merge is only needed because the real gpt-oss template raises `Cannot pass both content and thinking in an assistant message with tool calls!`. Since that is model-specific, please gate it on `self.is_gpt_oss` and let other templates keep their own content channel.

Two issues here:

1. The assignment is guarded by `msg_dict.get("reasoning_content") is None` **inside** the content loop, so only the first `thinking` part is kept.
