# perf(xpu): promote MXFP4 MoE bias to fp32 at load, not per forward

[Upstream PR](https://github.com/sgl-project/sglang/pull/40029) · state: open · merged: False

## Original PR description

## Motivation

On XPU, `Mxfp4MoEMethod.create_weights()` allocates `w13_weight_bias` / `w2_weight_bias` in bf16, but sgl-kernel-xpu's W4A16 grouped GEMMs take the bias as fp32. `fused_experts` therefore casts both biases on **every forward**: 72 elementwise-copy launches per decode step on gpt-oss-120b tp=4.

The bias is a static weight, so this PR promotes it once at load. The `_use_aiter` and CPU-AMX branches of the same method already do this. bf16 → fp32 is exact, so outputs are bit-identical.

Pairs with sgl-kernel-xpu [#496](https://github.com/sgl-project/sgl-kernel-xpu/pull/496). That PR first memoized this cast kernel-side, but the cache served a stale bias after `param.data.copy_`, so it was removed. **This PR is now the only place the cast is avoided.**

## Modifications

`python/sglang/srt/layers/quantization/mxfp4.py`, `_is_xpu` branch of `process_weights_after_loading()`:

| Change | Detail |
|---|---|
| Promote bias at load, in place | `bias.data = bias.data.to(torch.float32)` for `w13_weight_bias` / `w2_weight_bias`, skipped if absent or already fp32. Same pattern as the `_use_aiter` branch. |
| Keep the `Parameter` object | Rebinding `.data` preserves the `weight_loader` attrs from `create_weights()`. An earlier revision re-wrapped the bias in a new `Parameter`, which dropped them and made `update_weights_from_disk` raise `TypeError` in `default_weight_loader` and kill the scheduler. Fixed in `04403a4`. |
| Comment fix | The block comment said the launcher promotes the bias; it now describes the load-time promotion. |

Weight updates stay correct: `FusedMoE.weight_loader` writes with an in-place `copy_`, which casts into the fp32 storage. `fused_experts` skips its cast when the bias is already fp32.

## Accuracy Tests

gpt-oss-20b, tp=1, B60, with this PR plus sgl-kernel-xpu #496 @ `5e64996`:

| Check | Result |
|---|---|
| `fused_experts`, fp32 vs bf16 bias, M = 1, 2, 7, 64, 257 | bit-identical |
| Bias params after load | fp32, same `Parameter`, `weight_loader` kept |
| `update_weights_from_tensor`: perturb a bias, then restore | output changes, then returns exactly to baseline |
| `update_weights_from_disk` | succeeds, output unchanged |
| GSM8K, 200 questions, bare server | 0.560 |

## Speed Tests and Profiling

gpt-oss-120b, B60, TP=4, `intel_xpu`, MXFP4 W4A16, `bench_serving` random 4096/1024, concurrency 1, n=1. Count of `UnrolledElementwiseKernel<...CopyScalarFunc<c10::BFloat16>...>` launches, TP-0 device self-time:

| | launches/step | ms/step |
|---|---:|---:|
| Before | 73 | 0.633 |
| After | 1 | 0.009 |
| **Delta** | **−72** | **−0.624** (0.91% of TPOT) |

The remaining launch is `logits.float()` in `logits_processor.py`. That's device time for one bucket, not an end-to-end speedup claim. The table above predates the in-place fix and the #496 cache removal. On the current heads, 120b decode shows 1.000 launch/step on all four ranks (the `logits.float()`), with 0 inside MoE.

### gpt-oss-120b graph arm: without vs with both PRs (joint)

This measures the **combined effect of this PR and sgl-kernel-xpu [#496](https://github.com/sgl-project/sgl-kernel-xpu/pull/496)**; neither is isolated. Same base, same flags, graphs captured in both arms, n=1 per arm. Without PRs: kernel `e11219e` + sglang `9a53f75124`. With PRs: `5e64996` + `04403a4`. B60, TP=4, `intel_xpu`, MXFP4 W4A16, random 4096/1024, concurrency 1.

| Metric | Projection | without PRs | with PRs | Δ |
|---|---:|---:|---:|---:|
| **median ITL (ms)** | 3.503 | 9.37 | **8.15** | **−1.22 (−13.0%)** |
| P99 ITL (ms) | — | 9.86 | 8.60 | −1.26 (−12.8%) |
| P99 TPOT (ms) | — | 9.37 | 8.15 | −1.22 (−13.0%) |
| Output tok/s | 266.42 | 102.29 | 116.87 | +14.3% |
| TTFT (ms) | 259.868 | 403.40 | 402.72 | −0.68 (−0.2%) |
| P99 TTFT (ms) | — | 403.40 | 402.72 | −0.68 (−0.2%) |

With `--num-prompts 1`, P99 TPOT and P99 TTFT are the single request's value, so they equal the mean. Only the ITL percentiles are distributions (1023 decode steps).

From the eager profiled arms, decode device time (four-rank mean, comms excluded) drops from 7.560 to 6.433 ms/step (−1.127). The two levers account for −0.81 ms/step of that: bias casts 73 → 1 launches/step (−0.624 ms) and MoE bookkeeping 144 → 36 launches/step (−0.185 ms). The remaining −0.32 ms comes from kernels that run in both arms but were slower without the PRs (mostly `gemm_kernel`). That part is unexplained and may be a session effect. There is one run per arm, so the −13% has not been tested for repeatability.

<details><summary>Reproduce</summary>

```bash
export SGLANG_USE_SGL_XPU=1 ZE_AFFINITY_MASK=4,5,6,7
python3 -m sglang.launch_server --model-path openai/gpt-oss-120b --device xpu --tp 4 \
  --attention-backend intel_xpu --mem-fraction-static 0.8 --context-length 8192 \
  --max-total-tokens 32768 --max-running-requests 8 --disable-radix-cache \
  --chunked-prefill-size -1 --max-prefill-tokens 8192 --port 8000 \
  --model-loader-extra-config '{"enable_multithread_load": false}' --weight-loader-disable-mmap
python3 -m sglang.bench_serving --backend sglang --port 8000 --dataset-name random \
  --random-input-len 4096 --random-output-len 1024 --random-range-ratio 1.0 \
  --num-prompts 1 --max-concurrency 1 --profile --profile-activities XPU --profile-num-steps 10
```
`--weight-loader-disable-mmap` and single-thread load avoid a host-RAM OOM at 120b tp=4.
