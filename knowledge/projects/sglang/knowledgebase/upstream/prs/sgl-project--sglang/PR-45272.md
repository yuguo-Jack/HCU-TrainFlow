# [Fix] qwen3_coder: don't constrain non-strict tools under tool_choice="auto"

[Upstream PR](https://github.com/sgl-project/sglang/pull/45272) · state: open · merged: False

## Original PR description

Thank you @cmlccie for the extraordinarily detailed report and root-cause analysis — the GPU-free grammar reproducer made this very actionable.

## Summary

Under `tool_choice="auto"`, a single tool with `"strict": true` put **every** tool under the model-native structural tag, including non-strict ones (`function_call_parser.py`: `any(tool.function.strict ...)`). For `qwen3_coder`, that tag cannot produce the chat template's own zero-argument form (`<function=NAME>\n</function>`), and a non-strict tool compiles to an open parameter zone — so the model invents arguments for non-strict zero-argument tools (4/4 runs in the report).

A structural tag is triggered per tool call and lists every allowed tool name, so it cannot enforce per-tool strictness. This PR constrains under `"auto"` only when **every** tool is strict (or `SGLANG_TOOL_STRICT_LEVEL >= FUNCTION`, which is documented as "constraints for all tools"). A mixed set now leaves generation unconstrained, exactly like the no-strict case — matching OpenAI's per-tool `"strict"` semantics. Trade-off, as noted in the issue: in a mixed set, the strict tool's schema is not enforced under `"auto"` (it still is under `"required"`/named `tool_choice`, which is unchanged).

## Change

- `python/sglang/srt/function_call/function_call_parser.py`: `should_constrain_auto` now requires `all(...)` instead of `any(...)` for the tool set (with an empty-tools guard preserving prior behavior); comment documents the rationale and trade-off.
- `test/registered/unit/function_call/test_function_call_parser.py`: 3 new tests covering the mixed-strict scenario from this issue (`qwen3_coder` and `kimi_k2` auto → no constraint; all-strict auto → structural tag).

## Before / after (copy-paste-runnable, xgrammar==0.2.7, no GPU)

This drives the **real** `FunctionCallParser.get_structure_constraint` from this repo against `xgrammar.get_model_structural_tag(model="qwen_3_coder", ...)` with the issue's exact tool set (`get_schema`: no args, `strict: false`; `query_database`: required `sql`, `strict: true`):

```
=== FunctionCallParser.get_structure_constraint('auto'), mixed strict set ===
BEFORE (any strict -> constrain):  ('structural_tag', <StructuralTag>)   # the buggy tag
AFTER  (all strict required):       None                                  # unconstrained, = no-strict control

=== Grammar acceptance of the tag SGLang requested BEFORE the fix ===
  template-native zero-arg  "<tool_call>\n<function=get_schema>\n</function>\n</tool_call>"  accepted=False
  invented <parameter=sql>  "<tool_call>\n<function=get_schema>\n<parameter=sql>\n\n</parameter>\n</function>\n</tool_call>"  accepted=True
```

Unchanged behavior, verified against the real code:
- `all strict + auto` → `('structural_tag', <StructuralTag>)`
- `no strict + auto` → `None`
- `mixed + required` → `('structural_tag', <StructuralTag>)` (strict schemas still enforced for required/named calls)

## Tests

- New unit tests in `test/registered/unit/function_call/test_function_call_parser.py::TestGetStructureConstraint` (mixed → `None` for `qwen3_coder`/`kimi_k2` under `auto`; all-strict `qwen3_coder` under `auto` → `structural_tag`): 3 new + 4 neighboring existing assertions pass.
- The GPU-free grammar reproducer above reproduces the reported acceptance table for the pre-fix tag.

Fixes #45235.
