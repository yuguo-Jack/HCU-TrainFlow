# [Fix] moe: Use flashinfer_trtllm_routed when routed experts are returned

[Upstream PR](https://github.com/sgl-project/sglang/pull/47524) · state: open · merged: False

## Original PR description

## Why?

- On SM100, BF16 Qwen3 / Qwen3.5 MoE auto-selects `--moe-runner-backend flashinfer_trtllm`.
- That runner computes top-k inside the kernel and never hands the top-k ids back. `TopK` returns `BYPASSED` and never calls the routed-experts capture hook.
- So with `--enable-return-routed-experts`, routing replay silently records nothing. Responses carry no routed experts, and RL training that replays routing has nothing to replay.

## What?

- New post-process pass `_moe_runner_routed_experts_capture`. When routed-experts capture is on and `flashinfer_trtllm` is selected, it switches to `flashinfer_trtllm_routed` and logs a warning. The routed variant computes top-k in SGLang and runs the same expert GEMMs.
- Quantizations the routed runner doesn't support get a clear error that names the flag to change.
- The supported-quantization set (`_FLASHINFER_TRTLLM_ROUTED_QUANTIZATIONS`) is now shared with the existing assert in `moe_hook.py`, so the two can't drift.
- An explicitly chosen non-TRT-LLM backend, such as `triton`, is left alone.

## Verification?

```text
Qwen3 MoE BF16 on SM100, --enable-return-routed-experts

Before: backend = flashinfer_trtllm → TopK returns BYPASSED → capture never runs → no routed experts
After:  backend = flashinfer_trtllm_routed (warning logged) → top-k ids captured → routed experts returned   (expected)
```

## Test?

- `test/registered/unit/test_model_overrides.py::TestGoldenModelOverrides::test_routed_experts_capture_selects_routed_trtllm`: resolves a Qwen3 MoE config on SM100 with and without capture, plus an explicit `triton` backend and an unsupported quantization. **Pending CI** (not run locally).
- `pre-commit run` on the changed files: **observed** passing.
- GPU end-to-end with routing replay: **pending**.

Reviewer note: `experimental_sgl_trtllm` also bypasses `TopK` and is not switched here.

- esarafian · comment · 2026-11-03T15:44:27Z · [source](https://github.com/sgl-project/sglang/pull/47524#issuecomment-6608271088)

We tested this on GB300, since `flashinfer_trtllm` is the default MoE backend there for Qwen3.8-Flash-Next.

**Setup.** One GB300 per server, TP1, public `nvidia/Qwen3.8-Flash-Next-NVFP4`, image `lmsysorg/sglang:nightly-dev-20261103-797af717`. We compared main `8d4e1ce4c7` with this PR merged onto it (no conflicts).

```
--tp 1 --mem-fraction-static 0.85 --mamba-ssm-dtype bfloat16 --max-running-requests 32 \
--enable-return-routed-experts [--enable-deterministic-inference]
```

**Check.** For each of 8 prompts, we generated 64 greedy tokens with `return_routed_experts`. We then sent prompt + output back as one prefill (`max_new_tokens=1`) and compared the sorted top-10 sets per (token, layer).

| server | MoE backend | expert id 0 share | prompt rows = prefill | decode rows = prefill |
|---|---|---:|---:|---:|
| main | `flashinfer_trtllm` (auto) | 100% (all zeros) | n/a | n/a |
| main + `--moe-runner-backend flashinfer_trtllm_routed` | routed | 0.16% | 100% | 56% |
| this PR | `flashinfer_trtllm_routed` (auto, warning logged) | 0.16% | 100% | 56% |

- On main, every returned id is 0, which is the silent failure this PR targets. With the PR, the ids are real, and greedy outputs match the explicit `flashinfer_trtllm_routed` server token for token (8/8).
- The decode-vs-prefill agreement is per (token, layer) set equality over 48 layers × top-10 of 512 experts. Decode and prefill numerics flip near-tied router logits, so we read 56% as numerics, not a capture bug. Prompt rows agree 100%.

**Two side effects worth noting in the warning or docs:**
1. Turning on routed-experts capture now changes the model's outputs relative to the same server without capture. Under `--enable-deterministic-inference`, greedy outputs matched without capture in 0 of 8 prompts, diverging after 5–68 tokens, because routing moves from inside the TRT-LLM kernel to SGLang's top-k. For RL users, that means the rollout policy differs slightly between R3-on and R3-off runs.
2. Decode cost. In the same random-ids bench (1024 in / 512 out, 16 concurrent, 96 prompts, two runs each), median TPOT went from 7.52 ms to 8.35–8.45 ms, and output throughput from 1937/2044 to 1622–1823 tok/s.

We measured a similar change in a downstream build. There, recomputing top-k with `torch.topk` for capture disagreed with the kernel's own selection on about 23% of layer-rows, because of exact bf16 ties at rank k/k+1. So taking the ids from the routed kernel, as this PR does, seems preferable to recomputing them.
