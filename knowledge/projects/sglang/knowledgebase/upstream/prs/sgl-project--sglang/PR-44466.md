# [Fix] attention: Keep shared-KV verify split partials in FP32

[Upstream PR](https://github.com/sgl-project/sglang/pull/44466) · state: open · merged: False

## Original PR description

## Motivation

The shared-KV verify kernel in `verify_mla.py` stores each split's partial output (`Att_Out`) in BF16 and merges the splits afterwards. When the splits cancel each other out, the true result is a small residual, and the rounding before the merge can be as large as that residual.

Minimal repro: uniform attention over a prefix whose V values sum to 1.75, so the exact output is 1.75/n. At head_dim 256 the kernel returns 0. With real Gemma-4 Q/K/V I get 0.0530 where the FP64 reference is 0.0763.

The per-head split-KV verify kernel and Triton's split-KV decode both keep their partials in FP32. This PR does the same here.

## Changes

- `Att_Out` scratch is FP32. Q/K/V, output and LSE dtypes are unchanged, as are dispatch and tiling.
- New regression test in `test_verify_shared_kv.py` (head_dim 64 and 256, scratch growth, CUDA graph replay). It fails on main (max error 3.4e-3, tolerance 5e-5) and passes with this change. The whole file passes 8/8 on H20.

## Cost

FP32 partials cost some speed. Isolated kernel time on H20, bs 128, Q16/KV1, 3 query tokens:

| head_dim | prefix 256 | prefix 4096 |
|---|---|---|
| 256 | +2.5% | +0.1% |
| 512 | +4.7% | +3.1% |

Scratch memory doubles: 256 → 512 MiB at head_dim 512.

## Question for reviewers

#33981 chose BF16 partials on purpose to save scratch bandwidth, and today this kernel is only dispatched on gfx95, which I can't measure. @1am9trash @chuyeh, is this trade-off acceptable on MI35x? If not, I can keep BF16 on HIP and use FP32 only on the CUDA path (#44830), or make it configurable.
