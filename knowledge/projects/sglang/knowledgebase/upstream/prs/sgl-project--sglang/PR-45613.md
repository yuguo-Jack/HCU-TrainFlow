The branch is rebased onto main `6cac4dc3fe`.

## Motivation

On Hopper, `--moe-a2a-backend megamoe` covers FP8 checkpoints only. FlashInfer flashinfer-ai/flashinfer#6343 and flashinfer-ai/flashinfer#6517 add `flashinfer.megamoe`, an SM90 MegaMoE kernel for NVFP4 weights with FP8 activations (dispatch, both expert GEMMs, SwiGLU and combine in one persistent kernel, with a split variant for large batches). This PR wires it into the existing `megamoe` path for ModelOpt NVFP4 checkpoints, starting with `nvidia/DeepSeek-V4-Flash-NVFP4`.

On 8x H200 and 8x H20, TP8 / attention-DP8 / EP8, it is faster than DeepEP + DeepGEMM FP8 (W8A8) in prefill and decode (H200: 1.34x prefill TTFT, 1.13x decode ITL; H20: 1.27x / 1.42x) and at parity with the SM90 FP8 MegaMoE path while using NVFP4 weights.

## Modifications

1. **SM90 NVFP4 MegaMoE path** (`layers/moe/mega_moe_sm90_fi_nvfp4.py`, `layers/moe/mega_moe.py`, `layers/moe/fused_moe_triton/layer.py`):
   - Converts the ModelOpt expert weights at load into the format `transform_nvfp4_weights_for_mega_moe` expects (Marlin nibble order, one global scale per expert, local scales rebalanced into the kernel's range without changing the dequantized values).
   - Forward: DeepGEMM's SM90 pre-dispatch writes FP8 activations into the FlashInfer buffer, then `commit_staged()` and `nvfp4_mega_moe`. Under DP attention every rank launches with the same padded token count, as FlashInfer requires.
   - Prewarms the FlashInfer JIT modules before CUDA-graph capture; rejects EPLB and FlashInfer builds without flashinfer-ai/flashinfer#6517.
2. **ModelOpt NVFP4 MoE method** (`layers/quantization/modelopt_quant.py`): on SM90 with `--moe-a2a-backend megamoe`, builds the experts through the module above.
3. **Environment variables** (`environ.py`, `environment_variables.mdx`): `SGLANG_FLASHINFER_MEGAMOE_SM90_PREWARM`, `SGLANG_FLASHINFER_MEGAMOE_SM90_KERNEL_FAMILY`.
4. **Tests**: weekly 8x H200 e2e test (cookbook launch + sgl-eval GSM8K), skipped when FlashInfer lacks flashinfer-ai/flashinfer#6517.
5. **Docs**: DeepSeek-V4 cookbook note with the launch command and a fixed-revision FlashInfer install.
6. **Prefill CUDA graphs** (`layers/dp_attention.py`): when the FI path is captured into a prefill graph it latches the shared-bucket flag, so every DP rank replays one MAX_LEN bucket (FlashInfer needs the same token count on every rank) and batches with an idle rank fall back to eager.

**Local CPU validation** on the branch in the CI image without GPUs: the `layers/moe`, `layers/quantization` and `server_args` unit suites show no new failures against main `6cac4dc3fe` (the same 17 GPU-dependent cases fail on both); pre-commit passed for all changed files.

**Test environment**: one host, 8x NVIDIA H200 141 GB (NVLink); image `lmsysorg/sglang:nightly-dev-cu13-20261021-c1c287a4` with this branch on top of `6cac4dc3fe`; FlashInfer built from `main` `da992ed` as a wheel (`pip wheel "flashinfer-python @ git+https://github.com/flashinfer-ai/flashinfer@da992ed..."`) and installed into the image, with no `PYTHONPATH` overlay and no disabled version checks; model `nvidia/DeepSeek-V4-Flash-NVFP4`; sgl-eval 0.1.3. Unless noted: `--tp 8 --dp 8 --enable-dp-attention --moe-a2a-backend megamoe`.

**Review update (rebased onto main `ca4bedfffa`).** The prefill-graph change was checked on 8x H200 (image `nightly-dev-cu13-20261025-65633129`, FlashInfer `da992ed`) with uneven DP bursts: one long request with 7 idle ranks, mixes crossing the 256-token fused/split boundary, alternating 120/600 and 150/450-token prefills one per rank, and 7 short + 1 long. Default config (eager prefill) and `--cuda-graph-backend-prefill breakable`, before and after the change: no hang, GSM8K answers unchanged within noise. `--cuda-graph-backend-prefill full` does not start on DeepSeek-V4 (its attention backend does not capture EXTEND), with or without this PR.

**Dependency compatibility.** With the image's released FlashInfer `0.7.2` wheel (no `flashinfer.megamoe`), selecting this path raises the expected load-time error naming flashinfer-ai/flashinfer#6343 / flashinfer-ai/flashinfer#6517, the new e2e test skips (8 skipped), and the unit suites above behave as on main.

## Scope and Limitations

- SM90 only, opt-in through `--moe-a2a-backend megamoe` with ModelOpt NVFP4 experts. The integration is not DeepSeek-V4-specific: it uses the generic MegaMoE hook, and FlashInfer plans any legal geometry (tuned for DeepSeek-V4-Flash, DeepSeek-V4-Pro and MiMo-V2.5-Pro). It needs a model with a SwiGLU limit (the kernel's clamped SwiGLU) and has been validated only on `nvidia/DeepSeek-V4-Flash-NVFP4`.
- Against DeepEP + Humming W4A8 with humming-kernels 0.1.18 on H200, prefill is faster (1.41x TTFT) but decode above 4 tokens per rank is 3-9% slower.
- EPLB is not supported on this path.
- A coordinated FlashInfer dependency update is required before out-of-box use.

[P1] Uneven DP prefill CUDA graph replay violates FlashInfer’s cross-rank contract
_rank_invariant_tokens() returns the local graph’s token count during capture. However, prefill_graph_tolerates_sum_len() still allows MegaMoE ranks to replay different prefill graph buckets. For example, ranks replaying 128-token and 512-token graphs would launch the fused and split kernel families respectively, while FlashInfer requires all ranks to use the same token count and matching kernels. This mismatch can cause collective hangs or incorrect execution.

Please enforce a shared prefill graph bucket across all EP ranks for this backend, or temporarily reject this configuration. Regression coverage should include uneven token counts, idle ranks, and buckets crossing the fused/split boundary.

- ouershua2299 · comment · 2026-10-25T12:26:31Z · [source](https://github.com/sgl-project/sglang/pull/45613#issuecomment-6397619021)

@Fridge003 Thanks for the review. We could not reproduce a hang or wrong output from uneven prefill graph replay on DeepSeek-V4-Flash, but the concern is valid against FlashInfer's contract (same token count on every EP rank), so we changed it as you suggested in 232e96a466:

- While the FI NVFP4 MegaMoE path is captured into a prefill graph, it now latches the existing shared-bucket flag (the same one a captured DP gather sets, via a new `note_shared_bucket_in_prefill_graph()` in `dp_attention.py`). `prefill_graph_tolerates_sum_len()` then returns False, so every DP rank replays one MAX_LEN bucket, and batches with an idle rank fall back to eager, where this path already pads to the gathered max token count. Decode graphs already replay one shared bucket on all DP ranks, and the default config (prefill graphs disabled) is unchanged.

Test setup: 8x H200, branch rebased onto main `ca4bedfffa`, image `nightly-dev-cu13-20261025-65633129`, FlashInfer `da992ed`, `nvidia/DeepSeek-V4-Flash-NVFP4`, cookbook flags. The client sends concurrent GSM8K prompts padded to different lengths so DP ranks get uneven token counts in the same step: 1 long request with 7 idle ranks, 3 / 8 / 20 mixed lengths crossing the 256-token fused/split boundary, 120/600 and 150/450 tokens alternating one per rank, 7 short + 1 long, and 1 short request.

| Prefill graph | Before (5e5c94985e) | After (232e96a466) |
| --- | --- | --- |
| disabled (default) | pass, 2 rounds | pass, 2 rounds, same answers |
| `--cuda-graph-backend-prefill breakable` | pass, 2 + 5 rounds, ranks replay per-rank buckets | pass, 2 + 5 rounds, all ranks log the shared MAX_LEN bucket |
| `--cuda-graph-backend-prefill full` | fails at startup | fails at startup |

"pass" means no request timed out (no cross-rank hang) and greedy GSM8K answers stayed within noise (e.g., 150/450 alternating: 13-16/16 before, 14-16/16 after). With `full`, DeepSeek-V4's attention backend raises `NotImplementedError: unsupported forward_mode=EXTEND` during prefill graph capture, before the MoE runs, so `breakable` is the reachable prefill-graph path for this model. Our guess for why the old behavior did not fail: in the observed steps the ranks replaying graphs mostly landed above 256 tokens, where they select the same split plan even with different M.
