# [Refactor] dsv41: Shard Engram tables on hash-column boundaries

[Upstream PR](https://github.com/sgl-project/sglang/pull/42787) · state: closed · merged: True

## Original PR description

> (auto generated by Claude)

Each engram table is 24 column segments (3 n-gram sizes x 8 heads), one per hash column, laid out back to back: hash column `c` produces ids in `[bounds[c], bounds[c+1])` by construction. This PR cuts the TP row shards on those boundaries whenever `tp_size` divides the column count (2/3/4/6/8/12/24), so a rank owns whole per-head subtables. Any other world size keeps today's equal-row split.

Why: a shard boundary that never cuts a hash column makes the owning rank a pure function of the column index and gives every rank exactly `24 / tp_size` gathers per token, which upcoming sharded-table kernels rely on. Exactly one rank owns each row under either split, so the zero-fill + all-reduce lookup output is bitwise unchanged; checkpoints, configs and the host-table layouts are untouched (the shard is still one contiguous row range, per-rank sizes now differ by the prime gaps, ~0.005%).

Changes:
- `EngramLayout.column_bounds()`: the per-layer segment prefix sums, in the hash's column order.
- `shard_range()`: column-aligned split with the equal-row fallback for non-dividing world sizes; `EngramEmbedding` consumes it, everything downstream already keys off `row_start`/`rows`.
