# [Kernel][MoE] Add a CUTLASS MXFP4 x BF16 grouped-GEMM MoE backend for SM90, improving long-context prefill by up to 20%

[Upstream PR](https://github.com/sgl-project/sglang/pull/38884) · state: open · merged: False

## Original PR description

## Motivation
This PR adds an SM90 mixed-input CUTLASS grouped GEMM that feeds the MXFP4 nibbles to `wgmma` directly, keeps activations in BF16, and is selected with `--moe-runner-backend cutlass_mxfp4`.
The target came from an `nsys` capture of a live W4A16 server (128 concurrency, three isolated `#new-token: 16384` chunked-prefill forwards, 604 ms/forward):

|Category|ms/forward|Share|Instances|
|-|-|-|-|
|**MoE marlin W4A16 GEMM**|**209.1**|**34.65%**|86 = 43 layers x 2|
|Sparse attention `sparse_attn_fwd`|81.3|13.48%|43|
|Dense GEMM (deep_gemm fp8 + cuBLAS)|75.1|12.45%|539|
|NCCL AllReduce|47.5|7.87%|87|
|DSA indexer `sm90_fp8_mqa_logits`|46.9|7.77%|21|
|everything else|144.2|23.78%|—|

* **The MoE GEMM is the top entry at 34.65%**, 2.6x the next one.
* It is the only entry far below the hardware: 1.237 TFLOP per layer per GPU in 4.863 ms is **254 TFLOPS, 25.7% of H100 BF16 peak**, while reading 856 MB/layer, i.e. 176 GB/s, **5.3% of HBM3**.
* It is issue-bound, not bandwidth-bound: the SASS inner loop spends 64 of 220 instructions per 32-K step on `HMMA`, the rest on dequant, scale and pack.
* The attention-side alternatives are already near their limits on the same capture: the DSA indexer runs at ~50% of fp8 peak, AllReduce at 82% of one-way NVLink
* `flashinfer_mxfp4` is slower than marlin on this model;
`--flashinfer-mxfp4-moe-precision fp8` is 12% faster than that and still slower.

**Why activations stay BF16.** A gate experiment on the vendored SM90 mixed-input
collective, single layer, single GPU, 1.237 TFLOP:

|Configuration|ms/layer|TFLOPS|vs marlin|
|-|-|-|-|
|marlin MXFP4 W4A16 (production nsys)|4.863|254.4|1.00x|
|CUTLASS W4A8, grouped GEMM only|3.411|362.7|1.43x|
|CUTLASS W4A8, full MoE (permute + quant + silu-quant + unpermute)|4.134|299.2|1.18x|

The 0.72 ms/layer of glue gives back half the win and puts activation quantization on 61440-token prefills. Changing `MmaType` from `float_e4m3_t` to `bfloat16_t` removes the glue entirely and leaves the MoE operator boundary, the
weight-loading path and the memory footprint identical to marlin's.



## Modifications
### Kernel
`mxfp4_a16_grouped_mm_sm90.cuh` instantiates the mixed-input collective:

* `MmaType = bfloat16_t`, `QuantType = float_e2m1_t`, per-element `uint8` scale operand, tile `<128, kTileTokens, 128>` on `KernelPtrArrayTmaWarpSpecializedCooperative`.
* It computes `D^T = B^T A^T`, so per-expert problem sizes are `(2*intermediate, rows, hidden)` for GEMM1 and `(hidden, rows, intermediate)` for GEMM2.
* Weight nibbles are consumed in the checkpoint layout; scales are TMA-loaded as `Array<uint8_t, TileK/32>`.

**The mainloop change that makes group-32 possible.** Upstream keeps one
`intermediate_array` accumulator per scale group, so register cost scales with
chunks per K tile:

|Configuration|chunks|registers|Outcome|
|-|-|-|-|
|g128 / TileK=256|2|64|usable|
|g128 / TileK=512|4|128|collapses to 149.5 TFLOPS, ptxas reports `(C7511) wgmma.mma_async instructions are serialized due to insufficient registers`|
|**g32 / TileK=256**|**8**|**256**|**over the 255 limit -- does not compile at all**|

Backing off to TileK=128 is not a fix either: 7% slower by itself, landing at
1.23x marlin, below the 1.356x that +10% end-to-end requires. So the scale is
folded into the A fragment instead:

* One accumulator, dequant per element in `convert_A_kblock_scaled`, register cost independent of group size.
* `ScaleGroupSize` derived as `TileK / PackedScalesNum` instead of a global define, so the group-128 W4A8 kernel and the group-32 MXFP4 kernel share one mainloop; it evaluates back to exactly 128 for W4A8.
* Every new branch sits behind `UsePerElementScale`, false for W4A8's `Array<bfloat16_t, N>` scales, so the pre-existing path compiles out unchanged.

**Three device primitives** in `mixed_input_utils.hpp`; SM90 has no usable
equivalent for any of them:

* `convert_e2m1_kblock` -- places E2M1 bits into BF16 by hand without renormalizing, since CUTLASS's fp16 path needs Blackwell's `cvt.rn.f16x2.e2m1x2`. The result is the fp4 value scaled by `2^-126`, subnormals included; the missing `2^126` is folded into the scale byte offline.
* `apply_exponent_scales` -- builds `2^(e-127)` directly in the BF16 exponent field with one `prmt`, multiplying via `mul.rn.bf16x2` because the fp32 round trip under `-use_fast_math` flushes every E2M1 code below 1.0.
* `convert_A_kblock_scaled` -- fuses conversion and scale folding in one pass.

### Runtime
* **Load-time scale repack**: `[E, N, K/32] -> [E, K/128, N*4]` so a 128-wide Ktile's four scale groups are adjacent, +126 added per byte, each `_inv` parameter freed before the next operand (doing both first costs 2.16 GB of peak). Exponents above 128 are rejected (byte 255 is Inf/NaN in BF16). Weight nibbles are untouched.
* **Token-tile dispatch**: four instantiations (16/32/64/128 tokens) picked from average rows per expert. Same `kTileK` in all four, so one weight/scale layout serves every width at no extra memory. This is not a micro-optimization -- the fixed decode regression was -39.9%.
* **Fused metadata kernel** (`mxfp4_moe_grouped_metadata.cu`) replaces `torch.sort` + `compute_src2dst` + `compute_problem_sizes` + `compute_expert_offsets`: one CTA builds an expert histogram in shared memory,
block-scans it into offsets, writes both problem-size tables, then reuses the histogram as write cursors for the row permutation. **0.061 -> 0.008 ms/layer** against a 0.7 ms decode layer.
* **Python orchestration**: `cutlass_mxfp4_moe.py` runs metadata -> gather -> GEMM1 -> `silu_and_mul` -> GEMM2 -> scatter with one pooled buffer for GEMM1's A and GEMM2's D. `Mxfp4CutlassMoEMethod` registers scales as
`w13/w2_weight_scale_inv` exactly like marlin, so the weight-loading path is untouched.
* `Fp8Config.get_quant_method`** gains a **`cutlass_mxfp4`** branch.** Without it the DSV4-Flash fp4 experts fall through to a bare `Fp8MoEMethod` with `self.runner is None` and crash during decode graph capture.
* **Architecture gate, three layers**: `validate_cutlass_mxfp4` rejects non-SM90, `ep_size != 1` and `moe_a2a_backend != none` **before weight loading** and overrides `--speculative-moe-runner-backend`; `Mxfp4CutlassMoEMethod.__init__` raises for offline construction; `is_sm90_supported()` guards direct kernel calls.
* **Build**: the five `cutlass_extensions` headers move from `kernels/aot/csrc/` to `kernels/jit/include/` so AOT and JIT share one copy (the wheel prunes `kernels/aot/**`, and the JIT kernel must find them at runtime); three have real
changes, two are pure moves. The builder gains a SFINAE shim for the stage-count template order that CUTLASS 4.5 swapped, since AOT pins 4.2 and JIT compiles against FlashInfer's 4.5.


## Accuracy Tests
```bash
python3 -m pytest -q test/registered/unit/test_cutlass_mxfp4_scale_layout.py \
                     test/registered/quant/test_mxfp4_a16_moe_mm.py
```
* `test_mxfp4_a16_moe_mm.py` (6 cases, CUDA) diffs the grouped GEMM against a BF16-dequantized reference built from the same nibbles and scale bytes, so the tolerance is set by BF16 rounding rather than quantization error. It covers
uniform rows, a ragged tail with an empty expert, and **all four token-tile widths** -- prefill only ever reaches the 128-wide one.
* The same file covers the metadata kernel: both problem-size tables, out-of-range ids dropped without consuming a row,
`num_experts == kMetadataBlock`, and the permutation checked as a bijection onto the rows the GEMM will visit (nothing downstream can detect a wrong permutation on its own).
* `test_cutlass_mxfp4_scale_layout.py` (3 cases, CPU) pins the repack, the +126 bias and both rejection paths.

**Kernel level**, single layer, single GPU, 1.237 TFLOP, marlin = 4.863 ms
(GEMM1 + GEMM2, ms):

|Iteration|GEMM1|GEMM2|Total|vs marlin|rel err|
|-|-|-|-|-|-|
|i4 + bf16 g128 (accumulator scaling, the W4A8 mechanism)|2.084|1.564|3.648|1.33x|1.9e-3|
|i4 + E8M0 g128 (A-fragment scaling)|2.260|1.589|3.849|1.26x|1.6e-3|
|i4 + E8M0 g32|2.266|1.617|3.883|1.25x|2.2e-3|

* The first four rows are everything the quantization format alone can buy, and real MXFP4 is the slowest of them: fp4 decode costs 7.6% more than int4, 21 vs 13 ops per 8 elements.
* The last row is the turning point: **register pressure and tile shape were worth 0.41 ms in one step**, more than every format choice combined.

* Four extra kernels (metadata / gather / silu / scatter) cost ~0.065 ms/layer, a fixed ~15% at low concurrency even if the mainloop matched marlin's bandwidth.

**The decode regression that produced the token-tile dispatch.** The first integrated version regressed decode by **-39.9%** (4503 -> 2707 output tok/s, mean TPOT 5.14 -> 8.48 ms) with accept length unchanged at 5.64 vs 5.57, so it was not a speculation artifact. ### When to use which backend
Given the decode performance regression at low concurrency (< 128), we recommend PD-disaggregated deployment for production serving.

|Workload|Recommended|Evidence|
|-|-|-|
|Long context / RAG / document understanding (input >= 30K, output <= 2K)|`cutlass_mxfp4`|+10% to +16% total throughput, mean TTFT -14% to -22%|
|High-concurrency online serving (conc. >= 64, in:out >= 4:1)|`cutlass_mxfp4`|+7% to +8% total throughput, P99 TTFT -19%|
|High-concurrency long generation (conc. >= 128, in:out <= 1:4)|`cutlass_mxfp4`|throughput level, P99 TTFT -41%, TPOT cost only +5%|
|Low-concurrency long generation (conc. <= 16, output >= input)|`marlin`|the only regression band: -12.9% throughput, TPOT +18.7%|
|PD-disaggregated|`cutlass_mxfp4` prefill + `marlin` decode|wins all 6 scenarios, +1.1% to +22.3%|

Both backends coexist in one build and `--moe-runner-backend` is per process, so
a PD deployment picks per role; `marlin` stays the decode default.

## Limitations
* **SM90 only** (H100 / H800); the validator refuses to start elsewhere. The `mma.m16n8k32.e4m3` finding does not apply to `sm_89` / `sm_120+`.
* **Standard (non-EP) MoE dispatch only**; `ep_size != 1` or an enabled a2a backend is rejected before weight loading.
* Hidden size and per-rank intermediate size must be multiples of 128. DSV4-Flash satisfies this; GPT-OSS's 2880 does not.
* **Decode below ~30 routed tokens per step is ~15% slower than marlin**, and it is structural: the instruction count would have to fall another 2.5x to become bandwidth-bound, and there are no registers left (168/thread, 1 CTA/SM). Keep marlin for low-concurrency decode. Getting both the prefill win and no decode loss would require marlin to read the checkpoint MXFP4 layout so one weight copy serves both; carrying two layouts today costs 43 x 768 MiB = 32 GiB per rank, so that is separate work.
* Row order within an expert is not a stable sort (the metadata kernel's cursors are atomics). Nothing downstream depends on it today.
* **Due to limited machine resources, the experiments above were conducted on a single H100 *8 and H20 * 8  only. We were therefore unable to explore large-scale TP-parallel deployments, nor to validate on other Hopper-architecture hardware such as H200,  or H800.**
