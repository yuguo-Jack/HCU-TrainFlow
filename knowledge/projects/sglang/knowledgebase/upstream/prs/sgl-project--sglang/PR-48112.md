## Motivation
Every rank chooses its radix TreeCore on its own. The default Rust core is used only if the rank's probe passes (`_rust_fallback_reason`: platform, PyTorch, device, and `cargo --version` / `rustc -vV` with a 10 s limit); otherwise the rank falls back to the Python core. Nothing makes the ranks of one tree agree.

The probe is not reliable across ranks: `rust/rust-toolchain.toml` pins 1.92, which the current images do not ship, so the first probe installs it, and ranks that start together race on that install. In practice one rank of a worker gets the Rust core and its peers get the Python core.

The two cores are not interchangeable inside one tree. With HiCache `write_back`, `_sync_hicache_ready_counts` checks that every TP/PP rank reclaimed the same host duplicates by all-reducing a digest, and the cores fold it differently (Python: `d * 1000003 + id + 1`; Rust: `d * 1000003 + (id + 1) * 3 + component_idx`). Once the host tier fills, the first reclaim fails `write_back duplicate-reclaim victims diverged across PP/TP ranks` and the scheduler exits.

## Modifications
The cache builder settles the backend for the ranks that share a prefix tree: the TP (DP-TP), attention-TP, attention-CP and PP cache groups, i.e. the groups the HiCache syncs use. Attention-DP ranks keep separate trees and are not tied together.

- `agree_tree_core_backend(params)`, called in `build_kv_cache` before the cache factory, on every rank: one MIN all-reduce of `[runtime probe ok, crc32(request), -crc32(request)]`.
  - Ranks requesting different backends fail startup.
  - If any rank's runtime probe fails, every rank uses the Python core; the result is stored in `CacheInitParams.peers_can_use_rust_tree_core`.
  - Only Rust requests probe.
- `UnifiedRadixCache` reuses that verdict: `select_tree_core_backend` then only checks the cache's own configuration (session cache, tree slots, custom components), and `create_tree_core(..., resolve=False)` skips the second rank-local probe the cache used to run.
- `check_tree_core_backend_matches(params, tree_cache)`, called right after the cache factory, on every rank: fails startup if the built backends still differ (the configuration half is decided per cache, after the factory fills the slots). Ranks whose cache has no TreeCore, such as `PureSWARadixCache` on a PP stage holding only SWA layers, take part with a neutral value.
- `_rust_fallback_reason` is split into `_rust_config_fallback_reason` and `_rust_runtime_fallback_reason`; the checks are unchanged.
- `UnifiedRadixCache.tree_core_backend` exposes the chosen backend.

Both calls run on every rank, whichever cache class it builds, so the collectives line up even when PP stages build different cache classes. Without `torch.distributed`, or with single-rank groups, nothing is communicated and behavior is unchanged. Caches built outside the builder keep the old local resolution.

Net effect: ranks that share a tree run one backend, or startup fails with a message naming the mismatch, instead of failing later during HiCache reclaim.
