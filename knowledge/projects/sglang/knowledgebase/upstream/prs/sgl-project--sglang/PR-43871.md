# [Fix] glm4v: Clamp request video budgets to the deployment limit

[Upstream PR](https://github.com/sgl-project/sglang/pull/43871) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #43705.

GLM-V video requests could raise `fps`, `max_frames`, `max_tokens_per_frame`, and `max_image_tokens` above the deployment budget before frames were decoded. A large request could then make the worker decode far more frames, at higher resolution, than the default config allows.

## Modifications

- Clamp each request knob to the deployment limit, so a request can only tighten the budget. Omitted knobs stay unset, so an `fps`-only request does not inject `max_frames` and bypass the HF sampler.
- The `max_frames` limit comes from the processor's `max_frames`, or from `--mm-process-config`. GLM-4.1V/4.5V/4.6V processors have no `max_frames`; their HF sampler stops at `max_duration * fps` (600 by default), so that value is the limit there. It follows a server `fps` override.
  - Note: GLM-4.6V's own HF sampler allows up to 640 frames, so a request asking for 601-640 frames now gets 600. This is deliberate: the limit stays at or below what the default config samples.
- At decode time, drop a request `max_tokens_per_frame` when its total pixels (`cap * 28^2 * frame_count`) exceed the shared presize budget. The frames then go through the shared presize path. A server-configured per-frame cap keeps per-frame mode.
- On the DP encoder path, make that decision with the full clip length, so every shard picks the same resizer.
- Reject non-positive, non-numeric, and non-finite values. `ChatCompletionMessageContentVideoURL` now declares `gt=0` (and `allow_inf_nan=False` for `fps`), so OpenAI-path requests get a 400 before batching. The processor keeps the same check for the native `/generate` path.
- Log a one-time warning when a request value is clamped.
- Docs: `multimodal_language_models.mdx` now says GLM-V request knobs can only tighten the budget, and operators raise the limits with `--mm-process-config`.

## Accuracy Tests

No model-forward or kernel change. Tests in `test/registered/unit/multimodal/test_glm4v_mixed_offsets.py` build budgets with the real `glm_processor_video_config`. They cover:
- per-knob clamps, including the server-raised limit and the GLM-4.xV `max_duration * fps` limit;
- a 1-hour clip where a request can no longer sample more frames than the default HF sampler;
- the pixel-based per-frame drop and the DP full-clip count;
- the server per-frame mode;
- rejected values at both the processor and the API schema.

The GLM-4.xV frame-limit, per-frame pixel, and schema tests fail on the previous head and pass now.

## Speed Tests and Profiling

No inference-speed change. The clamp bounds decode work that a request could otherwise raise.
