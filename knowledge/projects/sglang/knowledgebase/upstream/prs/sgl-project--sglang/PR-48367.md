# [Perf] speculative: Fuse the draft proposal's Gumbel-max sample into one pass

[Upstream PR](https://github.com/sgl-project/sglang/pull/48367) · state: open · merged: False

## Motivation

With `--speculative-use-rejection-sampling`, every EAGLE/MTP draft step samples its proposal with the exponential-race form of Gumbel-max (`spec_utils.fast_sample`, unseeded path):

```python
q = torch.empty_like(probs, dtype=torch.float32).exponential_(1.0)
q.clamp_min_(torch.finfo(torch.float32).tiny)
scores = probs.float() / q
sample_index = sampling_argmax(scores)
```

Each step reads and writes a `[bs, vocab]` FP32 tensor three times after the draw (`clamp_min_`, the division into a new `scores` buffer, the argmax). A chain with `--speculative-num-steps N` samples N times per verify cycle. With 150K-250K vocabularies and many running requests, that is a visible slice of the cycle.

Upstream already has the one-pass building block: `sglang.kernels.ops.speculative.row_argmax.div_argmax`, a Triton row-wise `(x / divisor).argmax(-1)` with IEEE division, used by the Gemma 4 diffusion sampler for the same exponential race.

## Modifications

- `div_argmax(x, divisor, *, divisor_min=None, ignore_nan=False)` gains two keyword options. The defaults keep today's behaviour:
  - `divisor_min` applies `divisor.clamp_min(divisor_min)` inside the kernel, with `clamp_min`'s rule (a NaN divisor stays NaN);
  - `ignore_nan` makes a NaN quotient never win. That is the rule of the CUDA `sampling.argmax` kernel `fast_sample` uses today (strict `>` scan from -inf, lowest index on ties, index 0 for a row with nothing above -inf). By default NaN wins, as in `torch.argmax`.
- `fast_sample`, unseeded path, `num_samples == 1` (every caller in the tree), on CUDA with a contiguous FP32 `probs` of at least 2^23 elements (bs × vocab): after the unchanged `exponential_` draw, it calls `div_argmax(probs, q, divisor_min=tiny, ignore_nan=True)`. The path is taken only where `sampling_argmax(scores)` would run its CUDA kernel (`can_argmax`); elsewhere, and for `num_samples > 1`, the torch ops are unchanged. The sampled index, `q(X)` and the RNG stream are identical to the old path for every input.
- Tests:
  - `test/registered/kernels/ops/speculative/test_draft_sampling.py`:
    - `div_argmax` with the new options vs `sampling_argmax` / `torch.argmax` of `p / q.clamp_min(tiny)`, on random rows, rows with planted 0 / -0 / NaN / ±inf / subnormal / `tiny` / 3e38, and edge rows: all NaN, all -inf, ±0 ties, duplicate maxima;
    - default `div_argmax` unchanged;
    - `fast_sample` vs the old code under the same seed, including an unaligned vocabulary that takes the torch path;
    - `sample_draft_proposal` under CUDA graph capture/replay vs the old code.
  - `test/registered/kernels/benchmark/speculative/bench_draft_sampling.py`: fused vs torch, `marker.do_bench`.

## Accuracy Tests

No output change: for every input, the fused path returns the same index as the three ops it replaces, and the RNG draw is untouched.

**Op level** (`test_draft_sampling.py`, 4 tests; pass on RTX PRO 6000 Blackwell and GB300):
- `div_argmax(p, q, divisor_min=tiny, ignore_nan=True)` returns the same index as `sampling_argmax(p / q.clamp_min(tiny))`, and the default-NaN variant matches `torch.argmax`, on:
  - random rows;
  - rows with planted 0 / -0 / NaN / ±inf / subnormal / `tiny` / 3e38;
  - edge rows: all NaN, all -inf, ±0 ties, duplicate maxima.
- `fast_sample` matches the old code under the same seed, at sizes that take the fused path (64 × 151,936, 65 × 248,320) and at sizes that do not (small tensor, unaligned vocabulary).
- `sample_draft_proposal` captured in a CUDA graph at 64 rows matches the old code captured the same way.

Unchanged and passing: `test_deterministic_fast_sample.py`, `test_speculative_sampling.py`, and the tests of the other `div_argmax` user (`test_gemma4_renoise.py`, `test_gemma4_sampling_cuda.py`).

**End to end vs main (`8d4e1ce4c7`).** Same GPU, both builds in one container, rejection sampling on, server `--random-seed 1234`. 8 prompts are sent one at a time at `temperature=0.7, max_new_tokens=160`, plus the same 8 greedy, and `output_ids` are compared. Servers launch main, PR, PR, main, so main-vs-main and PR-vs-PR show the comparison is sensitive.

| Model | Launch | GPU | Sampled / greedy tokens | main vs PR | main vs main | PR vs PR |
|---|---|---|---|---|---|---|
| Qwen/Qwen3.5-9B (MTP) | `--speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 --speculative-use-rejection-sampling` | RTX PRO 6000 Blackwell 300 W | 1,076 / 1,163 | identical | identical | identical |
| Qwen/Qwen3.5-0.8B (MTP) | same with `--speculative-num-steps 6 --speculative-num-draft-tokens 7 --cuda-graph-max-bs-decode 256 --max-running-requests 256` | RTX PRO 6000 Blackwell 300 W | 1,114 / 851 | identical | identical | identical |
| nvidia/Qwen3.8-Flash-Next-NVFP4 | `--tp-size 4`, NEXTN 3 steps, rejection sampling, the flags of `test_qwen4_exp_models.py` | 4× GB300 | 902 / 979 | identical | identical | — |

These one-at-a-time requests reach `fast_sample` with one row, so they take its unchanged branch. They show that nothing else moved. The fused branch needs ≥ 2^23 elements (≥ 34 rows at this vocabulary), and concurrent sampled requests are not token-reproducible on main itself: 64 prompts in one request, or one request with `n=64`, differ between two main runs. That branch is therefore covered by the bitwise tests above, not by an e2e token gate.

`--enable-deterministic-inference` is deliberately not used here. In that mode every request carries a `sampling_seed`, so `fast_sample` takes its seeded hash path and never reaches this code.

Accuracy evals (GSM8K etc.) were not run: the sampled index is unchanged by construction.

On small tensors the split-vocab launch does not beat the three ops on every GPU (down to 0.78×), so `fast_sample` sends a step to `div_argmax` only from 2^23 elements (bs × vocab): ≥ 34 rows at a 248K vocabulary, ≥ 256 rows at 32K. In that range it is 1.51-2.32× on RTX PRO 6000 Blackwell and 1.03-1.60× on GB300. A chain with `--speculative-num-steps N` samples N times per verify cycle (N − 1 draft steps plus the post-verify draft extend).

**Serving:** `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random-ids --random-input-len 128 --random-output-len 1024 --random-range-ratio 1.0 --temperature 0.7 --seed 1 --num-prompts 512 --max-concurrency 256`, rejection sampling on, same GPU.
- Main and PR alternate per rep (main first, then PR first); each launch is followed by a discarded warmup run.
- Change = PR / main − 1 per rep, mean and 95% t-interval.
- Median ITL is the time between streamed chunks, about one verify cycle.

| Model, setup | GPU | Reps | Output tok/s, median main → PR | Output tok/s change | Median ITL change |
|---|---|---|---|---|---|
| Qwen3.5-0.8B, MTP 6, 256 running | RTX PRO 6000 Blackwell 300 W | 3 | 14,728 → 15,468 | +4.6% [−1.3, +10.4] | **−4.2% [−4.5, −3.9]** |

Accept length is unchanged within run-to-run spread (main 5.53-5.69, PR 5.57-5.61). Throughput varies more than ITL because concurrent batching changes the sampled tokens, and hence the accept length, from run to run. The saving is a fixed number of µs per draft step, so it shows end to end only when draft sampling is a visible share of the cycle: a large vocabulary, many running requests, a small or fast target.
