# [Feat] hicache: Support file storage with MLA host dedup

[Upstream PR](https://github.com/sgl-project/sglang/pull/45168) · state: open · merged: False

## Original PR description

> Part of the HiCache MLA host-dedup series (see umbrella). This is `[4/N]`. Depends on `[3/N]` (#45141 — L2 dedup **and** the shared-CPU-read path), `[2/N]` (#43798), and `[1/N]` (#43795); also builds on two already-merged upstream fixes — #41907 (rank-sharded `file` storage keys) and #43550 (storage workers survive backend exceptions).

## Motivation

With host dedup enabled, the duplicated MLA KV is stored as a single shared `file` L3 object, while rank-private state keeps per-rank keys (provided by #41907). Non-owner TP ranks hold a **dummy** host pool with no physical buffer, so having every rank issue the file read is both redundant and unsafe — it would target a buffer that does not exist.

This PR makes the `file` L3 read path dedup-aware: the owner rank performs the physical read once, dummy ranks skip it while still taking part in hit/completion synchronization, and rank-private state (Mamba/KDA, MHA draft) continues to be read per rank. Host→device distribution reuses the broadcast path from #45141 (`[3/N]`). This PR targets **broadcast**-mode dedup only; the shared-CPU-memory restore path also lives in #45141 and deliberately keeps storage attach rejected (*"Shared MLA host restore currently supports L2 cache only"*), so `file` L3 and `shared` mode are mutually exclusive for now.

## Modifications

- **Skip physical I/O for dummy pools.** `_skip_storage_pool_io()` filters the file→host read for a deduplicated KV pool and its derived sidecars when the host pool is a dummy (`_is_dummy`), while rank-private state still performs real reads. The shared-KV file format and key naming are unchanged.
- **Keep dummy ranks in the sync protocol.** A rank that skips the read publishes an optimistic hit count (`len(batch_hashes)`, or all-`True` sidecar results) that is reduced with the owner's actual result through the existing cross-pool `min`, so progress is published at the shortest prefix restorable across the owner and every required state.
- **Own the prefetch sync-group lifecycle.** `_create_sync_groups()` prebuilds the dedicated gloo groups via `_prebuild_prefetch_sync_groups()` under dedup; `_take_or_create_sync_groups()` transfers ownership on attach (clearing the context field), and detach / startup-failure destroys them — so a later attach always creates fresh groups and a destroyed group is never reused.
- **Allow dedup + `file`, reject the rest.** `handle_hicache` and storage attach now accept the `file` backend (error text: *"MLA host dedup currently supports only file storage"*), replacing the previous hard *"requires the file L3 integration"* rejection; non-`file` backends and `file` + rank-sharded MHA draft pools remain rejected (*"does not yet support rank-sharded MHA draft pools"*). The `shared`-mode guard that restricts restore to L2 (from #45141) is left untouched, so `file` L3 applies to broadcast-mode dedup.

## Accuracy Tests

**Component regressions: 92 passed, 69 sub-checks passed.** Cases added by this PR cover the sync-group handoff (`test_storage_group_handoff_does_not_reuse_or_double_destroy`, `test_reattach_replaces_groups_after_detach_or_startup_failure`), attach-time rejection before any mutation (`test_storage_attach_rejects_unsupported_pools_before_mutation`), and the dummy-read skip matrix (`test_dummy_reads_skip_only_deduplicated_pools`, `test_dummy_trailing_sidecars_keep_logical_hits_and_read_real_state`, `test_all_dummy_pools_leave_storage_reads_to_owner`).

**End-to-end (GLM-5.2 FP8 TP4):** 16 prefixes of 5000 tokens each are written to two separate file directories, the server is stopped (files retained) and restarted, then the marker questions are replayed. Both groups give 16/16 correct answers, 16 real file-L3 restores, 67,008 storage tokens each, device = host = 0, and identical input/generated token IDs.

The combination with layer-wise broadcast was additionally verified on B300 TP8: a four-stage 32/32 correct-answer run, restoring 8 requests / 21,504 storage tokens per group after restart. This is a correctness regression, not a new performance result.

### Repro

The two groups use different file directories; all other args are identical. The dedup group adds `--enable-mla-hicache-host-dedup`. First write 16 distinct marker prefixes, then stop the server (retain files), restart, and replay the appended marker questions. Both groups reuse the same token IDs and chat template; confirm `cached_tokens_details.storage > 0` per request, then compare answers and read counts.

```bash
python -m sglang.launch_server --model-path /path/to/GLM-5.2-FP8 \
  --tp-size 4 --port $PORT --trust-remote-code --enable-cache-report \
  --max-total-tokens 65536 --context-length 8192 \
  --chunked-prefill-size 512 --kv-cache-dtype bfloat16 \
  --dsa-prefill-backend flashmla_sparse --dsa-decode-backend flashmla_sparse \
  --enable-hierarchical-cache --hicache-ratio 1 \
  --hicache-write-policy write_through --hicache-io-backend direct \
  --hicache-mem-layout page_first_direct \
  --hicache-storage-backend file \
  --hicache-storage-prefetch-policy wait_complete \
  --hicache-storage-backend-extra-config '{"file_storage_path":"/path/to/this-mode-files"}' \
  --random-seed 42
```

When constructing requests, write a distinct `CEDAR-000` … `CEDAR-015` marker at the start of each session prefix, then pad to 5000 tokens. The write phase only needs this prefix to land in file L3; the restore phase appends "What is this session's unique marker? Answer with the marker only." after the same token prefix, keeping the model chat template's assistant start marker. Both groups must reuse the same token IDs and the same file-write/restart steps, so a template-truncated continuation is not mistaken for the answer.
