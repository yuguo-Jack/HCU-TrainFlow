# [Deterministic][Speculative][GDN] Add Decode-Verify-Rollback

[Upstream PR](https://github.com/sgl-project/sglang/pull/33291) · state: open · merged: False

## Original PR description

## Motivation

RL rollout systems recompute generated-token logprobs in the trainer. SGLang's batch-invariant target kernels make this computation reproducible, but deterministic one-token decode is much slower than the standard decode path. Gated DeltaNet (GDN) models add another challenge because prefill and recurrent decode follow different numerical paths.

Decode-Verify-Rollback (DVR) accelerates target execution without changing its scoring semantics. A fast provisional path proposes several tokens, the deterministic target verifies them in one prefill-style pass, and rejection sampling preserves the target distribution. Only accepted tokens and their corresponding state are committed.

This provides two practical benefits:

- DVR is faster than deterministic decode. In the 10,000-token tests below, self-draft DVR is 1.58x-2.65x faster at single-request decode.
- DVR supports GDN target verification while keeping recurrent state and target logprobs aligned with deterministic prefill recomputation.

DVR complements SGLang's true-on-policy alignment work but does not modify the trainer. End-to-end trainer/generator logprob parity additionally requires the training engine to implement and validate the same numerical contract.

## Modifications

- `DECODE_VERIFY_ROLLBACK` with target self-draft.
- `DECODE_VERIFY_ROLLBACK_EAGLE` with EAGLE or built-in MTP proposals.
- `DECODE_VERIFY_ROLLBACK_DFLASH` with DFlash block proposals.
- DVR is opt-in. When selected, extra memory for proposals and GDN state is accounted for before cache pools are sized.
- One target verification, rejection sampling, rollback, and state update path shared by all three draft backends.
- GDN state recovery across 64-token boundaries, including Radix reuse.
- Dedicated self-draft and target-verify CUDA graphs. Target prefill and verify retain the existing deterministic attention, MoE, and collective policies.
- Startup validation, focused tests, and manual launch and correctness tools.

Shared-path changes are limited to algorithm registration, cache sizing and request release hooks, two CUDA Graph extension points, exposing the existing CustomAllReduceV2 topology result, and correcting the Triton target-verify mask bound. Non-DVR defaults remain unchanged.

### Design

Every draft backend uses the same adapter to prepare its input, propose tokens, and update its draft cache. The common worker verifies the proposal and updates the target cache and GDN state:

```text
DecodeVerifyRollbackWorker
  |-- DVRDraftBackend
  |     |-- SelfDraftBackend
  |     |-- EagleDraftBackend  -> upstream EagleDraftWorker
  |     `-- DFlashDraftBackend -> upstream DFlashWorkerV2
  |-- sampling.py              -> rejection sampling
  `-- DVRStateLifecycle        -> rollback, state updates, and Radix
        `-- DVR GDN backend, when the target contains GDN layers
```

At runtime, the common worker executes:

```text
fast draft
  -> deterministic target verify
  -> rejection sampling
  -> discard rejected changes
  -> keep accepted tokens and state
```

Self-draft replays a fast single-token decode graph. EAGLE/MTP and DFlash reuse their existing workers through the adapter above. The target verifier decides which proposed tokens are returned and added to cache.

For GDN targets, DVR saves recurrent state at each 64-token boundary and replays the accepted suffix during verification. Draft state is kept separate from verified target state. Radix stores only exact boundary checkpoints, so the suffix is recomputed after a cache hit.

The provisional draft is an optimization and may use faster, batch-dependent kernels. DVR's numerical contract applies to target execution: for a fixed accepted token sequence, DVR target decode and deterministic target prefill produce matching target logprobs. Draft differences may change the sampled trajectory, while rejection sampling preserves the target distribution.

### Usage

Sync scheduling is the recommended DVR configuration:

```bash
python -m sglang.launch_server \
  --model-path /models/Qwen3.5-35B-A3B \
  --enable-deterministic-inference \
  --speculative-algorithm DECODE_VERIFY_ROLLBACK \
  --speculative-num-steps 15 \
  --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 16 \
  --page-size 64 \
  --attention-backend triton \
  --linear-attn-backend triton \
  --disable-overlap-schedule
```

Use `DECODE_VERIFY_ROLLBACK_EAGLE` with an EAGLE/MTP draft checkpoint, or `DECODE_VERIFY_ROLLBACK_DFLASH` with a DFlash draft checkpoint. The checked-in manual launcher documents the supported arguments and correctness test.

The initial supported configuration is NVIDIA CUDA, pipeline parallel size one, chain proposals with `--speculative-eagle-topk 1`, and Triton or FA3 target attention. Self-draft requires CUDA Graph. Supported GDN targets additionally use Triton linear attention, page size 64, and FP32 recurrent state. Online weight updates must keep tensor shapes unchanged and cannot recapture CUDA Graphs.

## Validation

### Sampling Semantics

DVR uses rejection sampling so published tokens follow the deterministic target model's output distribution even though proposals come from a faster draft path.

### Target Logprob Parity

Tests used Qwen3.5-35B-A3B at TP1 and Qwen3-Next-80B-A3B-Instruct at TP2. Sampling was non-greedy: temperature 1.0, top-p 0.95, and top-k 20 for 35B; temperature 0.7, top-p 0.8, and top-k 20 for 80B. Every request used seed 2026 and `ignore_eos=true`.

For every listed configuration, selected-token original logprobs had `maxdiff=0` for repeated deterministic target prefill, DVR target decode versus DVR target prefill, and DVR target decode versus ordinary deterministic target prefill.

These gates validate serving-side target computation. Cross-engine trainer/generator parity requires a matching training-side implementation and is outside this PR's test scope.

Additional tests covered prompt lengths 1/63/64/65, 512/1,024-token generation, 8,000-token prompts, Radix reuse, CUDA Graph batch sizes, request cleanup, weight updates, and sustained serving.

### Decode Performance

The tables report single-request decode throughput in tokens/s, computed as `1000 / median_TPOT_ms` and excluding TTFT. Prompts came from the ShareGPT Vicuna unfiltered dataset. Each row used one discarded 10,000-token warmup followed by three 10,000-token measured generations on NVIDIA H20-3e GPUs.

## Known Limitations

- FlashInfer full attention is not supported.
- Pipeline parallelism greater than one is not supported.
- Grammar constraints and dynamic frequency, presence, repetition, and `min_new_tokens` penalties are not supported.
- ReplaySSM is incompatible with DVR's GDN path; DVR already limits GDN state rebuild to the suffix after the latest 64-token boundary.
- Streaming sessions are not supported for GDN targets.
- KDA is not supported by this initial implementation.
- Non-chain EAGLE trees are not supported; DVR requires `--speculative-eagle-topk 1`.
