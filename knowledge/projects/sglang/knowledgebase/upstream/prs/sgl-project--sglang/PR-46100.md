# [Perf] diffusion: Hash large conditioning-cache keys in parallel chunks

[Upstream PR](https://github.com/sgl-project/sglang/pull/46100) · state: open · merged: False

## Original PR description

## Motivation

The conditioning cache keys every encoder call by a SHA-256 of its inputs, and computes the key before it knows whether the call will hit. For an image-conditioned request every key misses on new inputs, so hashing is pure request-path cost. One Qwen-Image-2.1 edit with a 1024x704 reference (resized to 1248x864) hashes three copies of the image:

| key | bytes | time, before |
|---|---|---|
| VAE input (`AutoencoderKLQwenImage21.encode`, after a GPU→CPU copy) | 8.6 MB | 10.1 ms |
| text encoder outer key (the resized PIL image) | 4.3 MB | 3.6 ms |
| vision tower (`_get_flat_visual_features`, processor output after a GPU→CPU copy) | 25.9 MB | 19.9 ms |

(1xH200, server timings around each key.) These run on the host before the vision tower is launched, while the GPU has only the VAE encode to do, so they add almost one to one to the request. Single-threaded `hashlib.sha256` runs at about 1.45 GB/s on the host CPU.

The cache is kept. It is exact, and it serves repeated inputs: the same reference with a new prompt reuses the VAE latents and the vision features, and the same request with a new seed skips the encoders. Only the key gets cheaper.

## Modifications

`runtime/cache/conditioning.py`: `_digest` hashes a buffer of at most 2 MiB with SHA-256 as before. A larger buffer is hashed as SHA-256 over its length and the SHA-256 digests of its 2 MiB chunks. The chunks are hashed on a module-level thread pool of up to eight threads; `hashlib` releases the GIL while it hashes. The digest still covers every byte and keeps SHA-256's collision resistance. Tensors (dense and sparse block paths), PIL images and NumPy arrays use it.

Measured on one host core vs eight threads: a 25 MB buffer takes 16.9 ms with one SHA-256 and 2.3 ms chunked.

Tests: `test_conditioning_cache.py::test_chunked_input_digest_covers_every_byte` sends inputs larger than a chunk through the real cache (a VAE encode and a PIL image key): an equal copy hits; a change in the first byte, at a chunk boundary, in the last element, or in the length misses.

## Accuracy Tests

Keys change format, values do not: a hit returns the stored output as before, and a miss computes it as before.

## Speed Tests and Profiling

Qwen-Image-2.1 edit 1024 with the harness's request (distinct inputs per request, so every key misses), measured inside one server that switches between chunked and single-threaded hashing request by request (interleaved rounds; an A/A pair in the same rotation stays within 5 ms):

| | single-threaded keys | this PR | difference |
|---|---|---|---|
| 1xH200, 8 rounds | 5.177 s | 5.155 s | −22 ms |
| 1xB300, 6 rounds | 2.624 s | 2.603 s | −17 ms |

With this PR, turning the whole conditioning cache off saves only another 13 ms on H200 (it was 39 ms on main), which is what repeated-input users now pay for their hits.
