# [Fix] rust-server: Check only a client-sent max_new_tokens against the context window

[Upstream PR](https://github.com/sgl-project/sglang/pull/45460) · state: closed · merged: True

## Original PR description

Stacked on #45431 (branch `oss-sync-d5268b39ae`): this branch is based on it and edits the `/generate` max_new_tokens tests it adds, so the diff against `main` includes that PR until it merges.

## Motivation

When `--preferred-sampling-params` sets `max_new_tokens` as large as the context length (a preferred `{"max_new_tokens": N}` under `--context-length N`, so that an omitted value means "as much as the window allows"), the Rust frontend returns 400 `Requested token count exceeds the model's maximum context length` for every `/generate` request that leaves `max_new_tokens` out, while the Python frontend serves them. A client that omits `max_new_tokens` on purpose, so the server's defaults apply, cannot use such a launch in Rust mode at all.

The cause is ordering. The Rust HTTP and gRPC adapters fill the preferred params (and, since #45431, the launch default) in beneath the request before decoding, and `check_total_tokens` then validates the filled value as if the client had asked for it. Python's `TokenizerManager._validate_one_request` checks only the request's own `sampling_params["max_new_tokens"]` and merges the preferred params afterwards, so a preferred or default value is never context-checked; the scheduler clamps it to the room the prompt leaves.

## Modifications

- `message/wire.rs`: `ClientMaxNewTokens` reads, before any fill, which requests of a `/generate` body sent their own `max_new_tokens`: one answer for a single or absent `sampling_params` object (applied to every item), one per object for a list; for gRPC, whether the protobuf field is set. A present JSON key counts, even an explicit `null`.
- `api_server/http/native_api.rs`, `api_server/grpc/service.rs`: each `generate` adapter takes that reading first, and after `into_requests` fans the body out marks the requests that did not send one.
- `message/request.rs`: `GenerateRequest::max_new_tokens_defaulted`, set by the adapters (the decoded request no longer shows which keys the client sent).
- `tokenizer_manager/to_scheduler_validation.rs`: `check_total_tokens` skips the input-plus-output check for a defaulted value, which reaches the scheduler as is and is clamped there, as in Python.

Unchanged: the input-alone check (an over-long prompt is still a 400); the rejection, or the `allow_auto_truncate` clamp, of a value the client sent; the precedence of an explicit request value (even `null`) over the preferred params and the launch default; the OpenAI endpoints. As in Python, an omitted `max_new_tokens` with no preferred params (the schema default of 128) is no longer context-checked either.

## Accuracy Tests

N/A: no model numerics change. The only requests that behave differently are the ones the frontend used to reject with a 400 although the scheduler would have clamped them.

## Speed Tests and Profiling

N/A for speed: one read of the `sampling_params` key(s) per `/generate` request, before the JSON decode that already walks the body.

Tests run (`rust/`, toolchain 1.92):

- `cargo test --locked -p sglang-server`: 368 passed. New or extended:
  - `defaulted_max_new_tokens_is_left_to_the_scheduler`: a defaulted cap as large as the whole window is neither rejected nor clamped, with and without `allow_auto_truncate`; an over-long prompt is still rejected.
  - `over_context_request_deregisters_unless_its_cap_is_defaulted`: end to end through `drive`, the same `max_new_tokens: 64` under a 4-token window is a 400 when the client sent it and reaches the scheduler unchanged when it is defaulted.
  - `generate_marks_each_max_new_tokens_the_client_omits` (HTTP): omitted, other keys only, no preferred params, explicit, explicit `null`, a per-item list, and one object broadcast to a batch.
  - `omitted_max_new_tokens_takes_the_launch_default` and the gRPC `preferred_sampling_params_fill_unset_fields` / `unset_protobuf_sampling_fields_take_schema_defaults` now also assert the defaulted flag.
  - With the gate in `check_total_tokens` and the HTTP marking disabled, the three new tests fail.
- `cargo fmt --all -- --check` and `cargo clippy --locked --workspace --all-targets -- -D warnings`: clean.
- Not run here: a live server (unit tests only). A client-sent value and the input-alone check keep their existing end-to-end coverage.
