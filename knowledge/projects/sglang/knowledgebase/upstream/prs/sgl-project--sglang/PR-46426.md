# [Perf] [NVIDIA] GLM-5.3-Flash: Add opt-in FP8 for the BF16 KDA projections

## Summary

**TL;DR: This PR adds an experimental opt-in environment variable, `SGLANG_OPT_GLM53_KDA_PTPC_MODULES`, that runs GLM-5.3-Flash's BF16 KDA (linear attention) projections in FP8 on NVIDIA Hopper GPUs, plus H200 and H20 tile tables for their FP8 GEMMs.** The FP8 checkpoint leaves these projections in BF16, so every decode step reads their full BF16 weights. With the variable set, SGLang quantizes them to FP8 at load time, reusing its existing FP8 linear layer and kernels: no new kernel, and the variable is off by default.

- **Performance** (H200, this PR vs main): attention DP8 (data-parallel attention on 8 GPUs) decode step time is **up to 10.0% lower** (5.0–10.0% without MTP speculative decoding, 2.3–8.3% with MTP 1/1/2 to 5/1/6, at 8 to 128 concurrent requests), its KV cache holds **7.5–13% more tokens**, and its time to first token (TTFT) is 2.1–4.5% lower. TP4 prefill median TTFT is **3.0–3.8% lower** on prompts of 8k tokens or more. In the cookbook's H200 TP8 configurations, with the input projections only, TTFT is 1.0–1.4% lower on 16k–64k-token prompts and decode step time up to 0.8% lower. Per layer, the KDA projections run **1.62× faster** in attention DP decode (38% less time).
- **Accuracy:** on H200, every GSM8K and RULER2 difference below is within measurement error, and the MTP accept length stays within 1%; on H20 (@QNan0513), GSM8K is 92.1% with this PR against 93.1% and 92.2% on two main servers. Accuracy is not validated across all workloads, so the variable is experimental and not a recommended configuration.
- **Cost:** load time unchanged. Against main, no end-to-end slowdown in the measured configurations except one: at TP4 without prefill CUDA graphs, TTFT for 1k-token prompts sent one at a time is 2.5% higher (host time per projection call). At TP8, adding `o_proj` to the input projections costs a little: on H200 decode step time without MTP is 0.3% higher, so the TP8 measurements use the input projections only; on H20 median TPOT with one request is 0.3% higher without MTP and 0.8% higher with MTP (accept length fixed at 4).

## Motivation

**GLM-5.3-Flash's FP8 checkpoint keeps the KDA input projection and `o_proj` of its 34 KDA (linear attention) layers in BF16, and in attention DP8 decode these two GEMMs take about 11% of a decode step at 16 requests per GPU:** 80 µs per layer per step, 2.7 ms of a 25 ms step (MTP 1/1/2, profile below). At decode batch sizes they are bound by reading their weights (BF16 reads them at about 3.5–3.7 TB/s there, near H200's 4.8 TB/s; [microbenchmark](#per-layer-speed)): the fused input projection `[q|k|v|b|f_a|g_a]` is 24896 × 4096 per GPU with attention DP and `o_proj` is 4096 × 8192, 258 MiB of BF16 per layer. FP8 weights halve those bytes.

SGLang already has the pieces: online FP8 quantization of BF16 weights and the CUTLASS FP8 GEMM. What it lacks is a way to apply them to only these projections of an FP8 checkpoint, which this PR adds. Applied as is, three things get in the way, and the PR handles each: at TP8 the input projection's 3336 rows per GPU push its GEMM off CUTLASS, the freed BF16 memory does not reach the KV cache, and at 96–384 tokens CUTLASS's SM90 tile choice is slower than BF16 at these shapes (the tile tables recover most of that range; TP8's input projection stays 5–11% slower at 256–384 tokens, see Per layer speed).

## Modifications

**Nothing changes unless `SGLANG_OPT_GLM53_KDA_PTPC_MODULES` is set**, except new H200 and H20 tile tables (the `configs/` bullet below), which other per-channel FP8 GEMMs of the same shapes on those GPUs also use.

- **`python/sglang/srt/environ.py`**: adds the experimental `SGLANG_OPT_GLM53_KDA_PTPC_MODULES`, a comma-separated list of the KDA projections to run in FP8: `qkv_proj`, `f_a_proj`, `g_a_proj`, `o_proj`. Empty by default.
- **`python/sglang/srt/models/glm5_next.py`**: the listed projections use `_KdaFp8LinearMethod`, a subclass of the online `Fp8LinearMethod` (per-channel weight scales, per-token activation scales; the quantization `--quantization fp8` applies to a BF16 checkpoint). It adds:
  - **Padding to a multiple of 16 rows**, so TP8's 3336-row input projection runs on CUTLASS, which needs both weight dimensions divisible by 16, instead of the Triton fallback. The output is cut back to 3336 columns.
  - **A CUDA memory pool per BF16 weight** (`torch.cuda.MemPool`), so the memory freed by quantization reaches the KV cache. Without it, an unrelated small tensor shares each BF16 weight's allocator segment and the segment is never returned. KV cache tokens at attention DP8: +7.5% with the pool, +4.2% with only a per-layer `torch.cuda.empty_cache()`.
  - **A direct call to the kernels `apply_fp8_linear` would pick** (per-token quantization, then the tuned Triton tile or the GEMM `fp8_scaled_mm` selects), skipping its per-call branching, whose host time prefill pays on every projection outside CUDA graphs. The output is bit-identical on H200. Where no tuned tile applies, it calls the CUTLASS kernel `sgl_kernel.fp8_scaled_mm` directly below 8192 tokens; at 8192 tokens or more, with a forced fused-op backend or on an out-of-tree platform, it calls `fp8_scaled_mm`, as `apply_fp8_linear` would; with `USE_TRITON_W8A8_FP8_KERNEL` or a bias (these projections have none) it falls back to `Fp8LinearMethod.apply` (`apply_fp8_linear`).
- **Startup checks** make a setup this path does not support fail at launch with a `ValueError`, instead of being silently ignored or computing wrong values:
  - an unknown name (it would otherwise be ignored), or a partial input-projection list (the three are one fused GEMM);
  - a GPU other than Hopper (SM90): it is measured on H200 and H20, and its GPU test runs on H100, H200 and H20;
  - LoRA, or an input projection that the quant config leaves unfused;
  - an `o_proj` the checkpoint already stores quantized (this path only quantizes BF16 weights);
  - `SGLANG_FORCE_FP8_MARLIN` (it forces the weight-only Marlin kernel instead of the FP8 GEMMs this path is tuned and measured for);
  - `--load-format remote_instance`, `sharded_state`, `presharded` or `remote` (they copy a seed's or a saved model's processed tensors into parameters built from the checkpoint), and a transfer-engine seed (`--remote-instance-weight-loader-start-seed-via-transfer-engine`, which serves its FP8 tensors to such peers);
  - `--elastic-ep-backend` (without an expert backup, it reloads lost experts with a weight update these projections refuse, and does not check the refusal);
  - `--enable-deterministic-inference` (the FP8 path picks its kernel by token count, so outputs would change with the batch).

  Each GPU worker process logs a warning at model load that the variable is experimental. Online weight updates and weight export (sending weights to another instance, `save_remote_model`, `save_sharded_model`, `get_weights_by_name`) are refused through the guards `nemotron_h` also uses, because the projections are quantized at load; `end_weight_update`, which reruns post-load processing, leaves the FP8 weights as they are. The weight cache (`--weight-cache-mode`) is refused too, see `protocol.py` below.
- **`python/sglang/kernels/ops/gemm/configs/`**: six H200 `fp8_w8a8_channelwise` tile tables for the projection shapes, `N=24896/6416/3344, K=4096` (input projection at attention TP 1/4/8) and `N=4096, K=8192/2048/1024` (`o_proj`), which `apply_fp8_linear` already reads (#34331, on by default). A Triton tile is used only at batch sizes where it measured faster than CUTLASS: 2–16 and 41–64 tokens for the attention DP input projection, and some batch sizes between 81 and 384 tokens for the other shapes (one `o_proj` shape also at 768); this recovers most of the 96–384-token range where CUTLASS's SM90 tile choice is slower than BF16 (TP8's input projection stays 5–11% slower at 256–384 tokens); null entries keep CUTLASS everywhere else. Other per-channel FP8 GEMMs of these shapes on H200 use the tables too; the one measured, Qwen3-8B with `--quantization fp8` at TP4 (`o_proj` 4096 × 1024), has 0–1.1% lower decode step time. Six H20 tables for the same shapes, tuned on H20 by @QNan0513, keep a tile only where it beat CUTLASS by more than 3%; other models were not measured on H20.
- **`python/sglang/srt/weight_cache/protocol.py`**: the weight cache's quantization check (`check_ipc_quant_support`) rejects `SGLANG_OPT_GLM53_KDA_PTPC_MODULES`. A weight-cache client builds the projections from the checkpoint's BF16 shapes, so it cannot map the FP8 weights a daemon would export; the daemon stops before it loads weights and the client before it fetches them. The check reads only the variable, so the weight cache is refused for any model while it is set.
- **`test/registered/kernels/ops/gemm/test_glm53_kda_fp8_projection.py`** (new, GPU: H100 in `base-b-test-1-gpu-large`, H200 in `base-c-test-8-gpu-h200`, H20 in `base-c-test-8-gpu-h20`): runs the real load-time quantization and padding and the real kernels. It checks the model's projection modules and weight loaders against the BF16 projections; each per-rank shape against the GEMM recomputed from its FP8 operands and both scales, at 1, 8191 and 8192 tokens and, on GPUs whose tables load (H200 and H20; the log says whether they were checked), at every distinct tile of that GPU's tables; which kernel each case runs, including a forced fused-op backend and an out-of-tree platform, and the tile's launch parameters; CUDA graph replay; a second post-load pass through `end_weight_update` and the guards that refuse updates and export; and that the BF16 weight memory is released.
- **`test/registered/unit/models/test_glm5_next_bfg_fusion.py`** (CPU): the startup checks above, the experimental warning, and which projections take the FP8 method (all four, the input projection only, `o_proj` only) without a quant config, and all four with GLM-5.3-Flash's FP8 checkpoint config. **`test/registered/unit/model_loader/test_weight_cache_protocol.py`** (CPU): the weight-cache rejection.

**Measured results by projection list** (experimental, not a recommended configuration; H200 from the measurements below, H20 from @QNan0513's [H20 results](https://github.com/sgl-project/sglang/pull/46426#issuecomment-6494394614)):

### Per layer speed

**Decode profile** (attention DP8, MTP 1/1/2, 16 requests per GPU): the two projections take 49.1 µs per layer per step instead of 79.7 µs (1.62×), with BF16's split-K reduction and FP8's activation quantization included; over 34 layers that is 1.04 ms, close to the 0.93 ms by which the end-to-end decode step time drops in this configuration (24.92 → 23.99 ms).

**Microbenchmark** (one H200, one CUDA graph per row, weights read from HBM; FP8 times include the activation quantization, BF16 times cuBLAS's split-K reduction). With attention DP, BF16 reads the two weights at about 3.5–3.7 TB/s from 1 to 64 tokens (H200's HBM peak is 4.8 TB/s), so the projections are bound by weight reads. In FP8 they take 18–43% less time with attention DP and 6–39% less at TP4 at every batch size.
