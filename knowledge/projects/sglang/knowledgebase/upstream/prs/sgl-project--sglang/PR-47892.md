# [Fix] quantization: Store --quantization-param-path KV scales the way checkpoint KV scales are stored

[Upstream PR](https://github.com/sgl-project/sglang/pull/47892) · state: open · merged: False

## Original PR description


## Motivation

`--quantization-param-path` loads per-layer KV cache scales from a JSON file through the models' `load_kv_cache_scales` (13 model files, including Llama, Qwen2 and Qwen3). They assign a Python float to `attn.k_scale` / `attn.v_scale` and leave `k_scale_float` / `v_scale_float` as None. The attention backends expect what `BaseKVCacheMethod` stores for checkpoint scales: `k_scale` as a device tensor and `k_scale_float` as its host value. So on main, a server with `--kv-cache-dtype fp8_e4m3 --quantization-param-path <json>` fails during startup. The aiter backend fails in `reshape_and_cache_flash`:

```
ValueError: Unsupported ptr type triton.language.float32 in `tl.load`
```

and `--attention-backend triton` fails in `decode_attention_fwd`:

```
TypeError: unsupported operand type(s) for *: 'float' and 'NoneType'
```

#37446 converts the scales for Qwen3.5 only and keeps the tensors on CPU, where the aiter and FA3 kernels cannot read them.

## Modifications

- `load_model_utils.load_kv_cache_scales`, the only caller of the models' loaders, now runs `_kv_cache_scales_to_tensors` after them: every `RadixAttention` whose scale is a float gets a 0-dim float32 tensor on the runner's device, and the float is kept in `k_scale_float` / `v_scale_float`. The model loaders are unchanged.
- `ModelRunner` passes `device=self.device`.
- New CPU test `test/registered/unit/model_executor/model_runner_components/test_load_kv_cache_scales.py` (`base-a-test-cpu`) checks the tensor, its host copy, and that a layer without a loaded scale is left as None. On main, after `load_kv_cache_scales` the layer still holds `k_scale = 0.25` as a float and `k_scale_float = None`.

## Accuracy Tests

MI355X (gfx950), image `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025` (torch 2.11.0+rocm10, aiter `285579b6`), CUDA graphs on, KV cache `fp8_e4m3`. Llama runs use `meta-llama/Llama-3.1-8B-Instruct` with the repo's `test/manual/quant/kv_cache_scales_llama3_8b.json` (per-layer scales 0.04 to 0.18) and `python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --max-tokens 4096` (chat API, greedy). "x0.01" is the same JSON with every scale multiplied by 0.01: K/V then overflow the e4m3 range unless the loaded scale is actually applied, so it shows whether the kernels read the JSON scales.

Qwen3-8B uses 5-shot completion GSM8K (`python -m sglang.test.few_shot_gsm8k --num-questions 1319`), because the chat API makes Qwen3 think at length. Its JSON sets 0.05 for every layer (not calibrated), which caps K/V at 0.05 x 448 = 22.4; that file costs about 1.3 points, while the all-1.0 JSON matches the run without one, so the loading path itself does not change accuracy.

With calibrated scales every path scores within the run-to-run spread of the fp8 cache without scales, and scaling them by 0.01 breaks every path, so the loaded scales reach the kernels on aiter (both decode paths), triton, TP1 and TP2.

At TP>1 the JSON must give scales for every TP rank. The repo's `kv_cache_scales_llama3_8b.json` only has rank 0, so at TP2 the schema validation fails and `kv_cache_scales_loader` logs an error and falls back to 1.0 while the server starts normally (behavior on main, unchanged by this PR). The TP2 rows above use the same scales copied to ranks 0 and 1.

The JSON schema defines e4m3fn scales, while gfx942 stores the fp8 KV cache as e4m3fnuz (max 240); `BaseKVCacheMethod` doubles checkpoint scales there. On MI325X (gfx942), torch 2.11.0+rocm10.0.0, aiter `285579b62`, main `cb55d77d37` with this patch, doubling the JSON scales makes no measurable difference, so this PR loads them as given:

| Attention backend | JSON as given | JSON scales x2 |
|---|---|---|
| aiter | 0.8113 / 0.8158 | 0.8151 / 0.8196 |
| triton | 0.8166 | 0.8158 |

For reference on the same machine: aiter fp8 KV without JSON 0.8227, bf16 KV 0.8326.

Not tested: NVIDIA backends (FA3, FlashInfer). They already read checkpoint KV scales stored as a device tensor plus host float, which is the form this PR now gives JSON scales too.
