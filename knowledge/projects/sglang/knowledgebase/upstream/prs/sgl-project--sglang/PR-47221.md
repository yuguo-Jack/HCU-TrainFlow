# [Perf] dsa: Elide shared-layer index-K under HiSparse decode to raise batch size

[Upstream PR](https://github.com/sgl-project/sglang/pull/47221) · state: open · merged: False

## Original PR description

Allow DSA index-K elision under HiSparse decode to reclaim GPU memory and raise batch size.

## Motivation

DeepSeek-DSA's IndexShare lets most layers share a single top-k selection: these
"shared" layers reuse a preceding producer layer's top-k and never read or write
their own index-K. GLM-5.2 has 78 layers, of which only 21 are producers and 57
are shared.

The device pool already allocates 0 index-K pages for the shared layers via
`skip_topk_layers`, but `_should_elide_dsa_index_k()` still refused elision under
HiSparse on a PD decode engine, so the 57 shared layers held device buffers for
nothing. This commit opens elision on that path and returns the memory to the KV
pool.

## Modifications

- `kv_cache_configurator.py`: allow `_should_elide_dsa_index_k` to elide on a
  HiSparse PD decode engine. The prefill peer runs the indexer on every layer and
  writes its own index-K, so only the decode engine can drop these rows; a single
  engine (`disaggregation_mode == "null"`) and prefill still keep the full set.
- `pool_configurator.py`: drop the `or enable_hisparse` short-circuit so the
  sizing path and the allocation path read the same predicate. Previously sizing
  priced all 78 layers while allocation already saved 21, so
  `max_total_num_tokens` did not reflect the reclaimed memory.
- Under HiSparse, index-K resides on device at logical capacity ×
  `host_to_device_ratio`, so the saving is multiplied by the same factor.
- Kill switch: `SGLANG_DISABLE_DSA_INDEXK_ELISION=1`.

No PD transfer-protocol change is needed: a shared layer's buffer is 0 bytes, so
`_registerable_regions()` skips the zero-length region (Mooncake rejects a zero
length memory region) and the sender's `is_elided_entry` drops the matching
transfer entry. The hierarchical-cache host (L2) index-K pool is likewise packed:
one host layer per index-K-owning device layer.

## Accuracy Tests

GLM-5.2 NVFP4, 8× RTX PRO 6000 (SM120), TP8/PP1, PD disaggregation with HiSparse
on the decode engine, 5-shot GSM8K, temperature=0, `--parallel 16`. Each arm
fully restarts PD and changes only the kill switch; after restart the decode-side
`max_total_num_tokens` is 206144 (off) / 402752 (on), confirming the two arms are
different pools.

| num-questions | elision | Accuracy | Invalid |
|---|---|---|---|
| 200  | off | 0.960 | 0.000 |
| 200  | on  | 0.940 | 0.000 |
| 1000 | off | 0.949 | 0.000 |
| 1000 | on  | 0.946 | 0.000 |

At n=1000 the two arms differ by 0.3pp (3/1000 questions), within the 1%–5%
variance CONTRIBUTING documents for this script; the n=200 gap of 2.0pp (4
questions) is too small a sample to be meaningful. This matches the structural
argument: shared layers never read their own index-K (`dsa_layer_skips_topk()`
plus the existing `skip_topk_layers` path), so not allocating it is a no-op and
does not change model outputs.

## Benchmarking and Profiling

GLM-5.2 NVFP4, 8× RTX PRO 6000 (SM120), TP8/PP1, PD disaggregation with HiSparse
on the decode engine, `host_to_device_ratio=10`, `device_buffer_size=4096`,
shared-index prefetch off, decode `--mem-fraction-static 0.90` / prefill `0.80`,
128K input, O=2000, full prefix hit on the prefill side. Batch size is the
largest concurrency the decode pool admits without retraction. Latencies are
sampled after the client's initial burst has drained.

| Arm | Device pool tokens | Batch size | Output tput | Per-GPU | TPOT |
|---|---|---|---|---|---|
| elision off | 206,144 | 15 | 325.7 tok/s | 40.7 tok/s | 45.5 ms |
| elision on  | 402,752 | 30 | 436.5 tok/s | 54.6 tok/s | 67.1 ms |

The device pool grows 1.954×, matching the per-token cost ratio 154,128/78,888
(78 × 656 B latent KV plus 132 B per indexer layer × ratio). Doubling concurrency
(batch 15 → 30) trades latency for throughput: aggregate throughput +34.0%
(325.7 → 436.5 tok/s) and per-GPU +34.2% (40.7 → 54.6 tok/s), at the cost of TPOT
+47.5% (45.5 → 67.1 ms). Latency-sensitive deployments can fall back to the
smaller pool via the kill switch. Both arms show `err=0`, `#queue-req: 0`,
`#retracted-req: 0`.
