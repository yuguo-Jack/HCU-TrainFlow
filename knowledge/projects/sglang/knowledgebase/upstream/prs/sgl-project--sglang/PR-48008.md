## Motivation

Previous PRs plan one window sub-pool per window length and refuse, at binding, a runner whose layers span more window sub-pools than its backend serves (every backend serves one). This PR lets the Triton backend serve any number of window sub-pools, each through its own rail, and carries write locations by sub-pool name.

## Modifications

- Triton (`layers/attention/triton_backend.py`): one rail per window sub-pool in eager extend, eager decode and decode CUDA graphs (window length, read indptr and indices, graph buffers, write ids). With one window sub-pool nothing changes (no extra rail, same buffers, kernels and graph shapes). Triton serves several window sub-pools without speculative decoding, decode context parallelism, deterministic windows, dLLM, MLA or a shared indptr buffer; otherwise one.
- Write locations: `KVWriteLoc.window_locs` carries every window's write ids keyed by sub-pool name; `swa_loc` is removed and the fields after `loc` are keyword-only. All attention backends (CUDA, AMD aiter, Intel AMX, torch native, XPU, MUSA, NPU) and the CP strategies take `window_locs`; DFlash and DSpark draft writers key them by layer route (`mem_cache/kv/router.py`, `routed_cache.py`, `memory_pool.py`, `swa_memory_pool.py`).
- Tests: `test/registered/unit/layers/attention/test_triton_several_windows.py`, `test_window_write_locations.py` with a recorded golden of the rows every attention layer writes and reads (`window_write_locations_golden.json`, regenerate with `SGLANG_REGEN_WINDOW_WRITE_GOLDEN=1`), `test/registered/unit/models/test_draft_sliding_window_rules.py`, plus updates to backend, draft placement and NPU tests.

**API change for backend implementers:** `KVWriteLoc.swa_loc` is gone; read a window's write ids from `window_locs[sub_pool]`. No serving behavior change for current models: the production configurator declares one target window.
