# [Bug] Reject dynamic LoRA updates when tokenizer-worker-num > 1

[Upstream PR](https://github.com/sgl-project/sglang/pull/41399) · state: open · merged: False

## Original PR description

## Motivation

Fixes #31084.

With `--tokenizer-worker-num > 1`, each tokenizer worker process owns its own `LoRARegistry` / `lora_ref_cache`. Dynamic `/load_lora_adapter`, `/load_lora_adapter_from_tensors`, and `/unload_lora_adapter` only update the worker that handled the HTTP request. Requests routed to other workers then fail with `"Got LoRA adapter that has never been loaded"`, and a retry on another worker can mint a new id and hit `"already loaded"` on the backend.

Adapters seeded at startup via `--lora-paths` are unaffected (every worker loads them at init).

Related earlier attempts: #31724, #36487 (same fail-fast direction; this PR targets current `get_serving()` / runtime-context APIs).

## Modifications

- Add `_validate_dynamic_lora_supported()` in `tokenizer_control_mixin.py` and call it from the three dynamic LoRA handlers before any backend / registry mutation.
- Document the `--tokenizer-worker-num 1` requirement under Dynamic LoRA loading in `docs/docs/advanced_features/lora.mdx`.
- Add CPU unit coverage in `test/registered/unit/managers/test_dynamic_lora_multi_tokenizer_guard.py`:
  - all three endpoints reject with `tokenizer_worker_num > 1` (no communicator call, no registry mutation)
  - guard still fires when dp-attention allows `dp_size > 1`
  - single-worker load path still succeeds
