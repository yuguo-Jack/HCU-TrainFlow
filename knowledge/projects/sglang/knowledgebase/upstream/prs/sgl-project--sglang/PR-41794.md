## Motivation

On ROCm, Quark-quantized Kimi-K3 (`Kimi-K3-Quark-MXFP4-AttnFP8`) stores attention weights as per-channel FP8. Two of those layers miss the FP8 kernels at decode:
- The KDA input projection runs as three separate linears (`[q,k,v,g]`, `f_a`, `b`).
- The MLA absorb dequantizes `kv_b` to BF16 and runs BF16 BMMs.

## Modifications

**`5e57539a9c` run the Quark per-channel FP8 KDA in-proj and MLA absorb on FP8 kernels on ROCm**
- Merge the Quark per-channel FP8 [q,k,v,g | f_a | b] KDA in-projection into one FP8 linear for decode.
- Pad the merged output to a multiple of 64 so it keeps AITER's preshuffled FP8 GEMM.
- Serve the Quark FP8 f_b from a BF16 copy so it uses the tiny GEMM and the fused KDA decode.
- Take the single in-proj GEMM path whenever the merged layer exists, not only when _bfa_w is set.
- Requantize the Quark per-channel FP8 kv_b to per-tensor FP8 so the MLA absorb BMMs run AITER a8w8.
- Gate the absorb requantization behind SGLANG_OPT_HIP_K3_MLA_ABSORB_FP8, on by default.
- Register SGLANG_OPT_HIP_K3_KDA_FUSED_BACKEND and keep SGLANG_ROCM_K3_KDA_FUSED_BACKEND as a deprecated alias.

Switch: none (`SGLANG_OPT_HIP_K3_MLA_ABSORB_FP8` is on by default). Everything is ROCm only; CUDA and other checkpoints keep the existing path.

@BowenBao Yes, I think it makes sense for shared experts.

### Storing shared experts in BF16

- Shared experts always run in BF16 in our recipe, so storing them as MXFP4 only adds a quantize-then-dequantize step at load.
- BF16 storage would remove that step. The `SGLANG_ROCM_QUARK_MXFP4_LINEAR_ACT` flag would then not be needed for these layers.
- Tradeoff: the checkpoint gets larger and uses more memory. Shared experts and layer-0 are a small part of total weights, so I expect the cost to be small.
- I'd keep the load-time dequantization path so existing MXFP4 checkpoints still work.

### Why the env var exists (internal harness)

- Harness: `sglang.test.few_shot_gsm8k`, 5-shot, 512 tokens.
- Dense linears with BF16 activations: 94.7%.
- Dense linears with FP4 activations: 90.8%.
- This ~4-point gap is why we added `SGLANG_ROCM_QUARK_MXFP4_LINEAR_ACT=bf16`. The default is `bf16`.

### HF page test (separate harness, not comparable to the numbers above)

- Published vLLM: 96.36%.
- Our SGLang implementation: 96.3609% (1271/1319).
- The full SGLang recipe matches the published score.

### vLLM vs SGLang implementation

- vLLM uses the generic Quark / `FusedMoEFactory` path.
  - Routed experts are A16W4 by default, and A4W4 with `VLLM_ROCM_USE_AITER_MOE_SITUV2=1`.
- SGLang uses K3-specific post-load transforms and the AITER MXMoE runner.
  - Transforms include merged KDA projections, MLA absorb, MoE layouts, and selected MXFP4 dequantization.
  - It also uses FP8 KV cache and INT4 quick-reduce.

### Why A4W4 for routed experts

- Routed experts dominate compute and weight traffic, so FP4 activations help most here.
- A4W4 keeps both operands in MXFP4, and the AITER MXMoE path quantizes BF16 input inline, so it needs no separate A16W4 path.
- It matches vLLM's A4W4 mode and keeps the HF accuracy.

### Discussion

- Routed experts: A4W4.
- Shared experts and layer-0 dense: BF16.
