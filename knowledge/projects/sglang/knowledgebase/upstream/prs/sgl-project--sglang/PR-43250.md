# [Perf] sm_121 (GB10 / DGX Spark) skinny BF16 GEMM for decode projections and lm_head

[Upstream PR](https://github.com/sgl-project/sglang/pull/43250) · state: open · merged: False

## Original PR description

## Motivation

On sm_121 (DGX Spark / GB10), cuBLAS handles small-M BF16 GEMMs with SM80 WMMA kernels (`cutlass_80_wmma_tensorop_bf16_s161616gemm…`, one warp per CTA). These reach about 125–205 GB/s of the 273 GB/s available. For Qwen3.8-Flash-Next, everything outside the NVFP4 experts is BF16, and in our decode profile those GEMMs were the largest single cost. The same finding was reported for vLLM in vllm-project/vllm#59605. vLLM fixed it with a CuTe-DSL skinny GEMM plus an SM121 plan table (vllm-project/vllm#59632). This PR ports that to SGLang.

## Modifications

- **`kernels/ops/gemm/_sm121_skinny_kernel.py`**: vLLM's `CuteSkinnyGemm`, verbatim (Apache-2.0, attribution in the header).
- **`kernels/ops/gemm/sm121_skinny_gemm.py`**:
  - Dispatch and plan table. The base is vLLM's SM121 table (TP=1 and TP=2 rows).
  - We added rows measured on GB10 for SGLang-specific fused shapes:
    - Packed GDN `in_proj` (8240, 2560).
    - (10240, 2560), (2560, 2560), HC (336, 10240) and (320, 2560).
    - The M=3 rows used by NEXTN verify.
  - We also dropped rows that lost to cuBLAS in our profiler.
  - A shape runs here only if (N, K, M) has a measured plan and M ≤ 16. Everything else keeps cuBLAS.
- **Hooks**:
  - `UnquantizedLinearMethod.apply`, `apply_with_addend` and `apply_into`.
  - `_bf16_gemm_dispatch_impl`.
  - The lm_head matmul in `LogitsProcessor`.
- **Warmup**: every plan whose (N, K) matches a BF16 weight in the model is compiled and launched once in `init_cuda_graphs`, before capture. Graphs then record only plain launches. Compiling takes a few seconds.
- **Gating**:
  - Only exact capability (12, 1).
  - Requires `cutlass-dsl` and `quack`, which are already dependencies.
  - Skipped under batch-invariant mode and inside `torch.compile`.
  - `SGLANG_SM121_SKINNY_GEMM=0` disables it, and `SGLANG_SM121_SKINNY_GEMM_PDL=1` enables PDL. Both are declared in `environ.py`.

Numerics: BF16 in/out with FP32 accumulation, the same precision class as cuBLAS. The reduction order differs, so results are not guaranteed bit-identical. In isolated tests on GB10, 99.9–100% of outputs matched cuBLAS bit for bit.

## Accuracy / tests

- **`test/registered/unit/kernels/test_sm121_skinny_plans.py`** (CPU): structural invariants for every plan row.
- **`test/registered/kernels/ops/gemm/test_sm121_skinny_gemm.py`**:
  - Compares against an fp32 reference on representative shapes and every planned M, including the residual and `out=` paths.
  - Checks the fallback for unplanned shapes and for M > 16.
  - Skips unless running on sm_121. It passes on GB10 on the rebased branch.
- **End to end**: 2× DGX Spark, TP=2, Qwen3.8-Flash-Next NVFP4, NEXTN 3/1/4, run on main@7be5e347 with the equivalent patch:
  - Our CN/JP structured-extraction regression suite stays at 36/36.
  - GSM8K full 1319 (author protocol: thinking on, T=0.6, max 8192) scored **97.42%**. The checkpoint author reports 97.27%, with a BF16 band of 97.12–97.50.

## Speed (GB10)

- **Isolated kernels**: the large projections ran 1.3–2.3× faster than cuBLAS, and the lm_head at M=1 ran 1.43× faster.
- **Rank-0 decode profile**: the cuBLAS WMMA share fell from 25% to 6% of GPU time.
- **In-service overlap**: when these kernels overlap with other streams, they take longer than in isolation. For example, (8240, 2560) at M=4 took 194 µs in service vs 106 µs isolated, with cuBLAS at 200 µs. So the end-to-end gain is smaller than the micro-benchmarks suggest.
- **End to end** (single stream, T=0, 3 runs each), with this PR together with #43249 (TP-aware `--speculative-token-map`) vs neither:

| Task | Without | With both |
|---|---|---|
| Short CN JSON | 64.2 tok/s | 77.8 tok/s |
| CN prose | 31.4 tok/s | 38.4 tok/s |
| JP prose | 34.7 tok/s | 39.0 tok/s |

TTFT was unchanged (180–270 ms). We did not isolate this PR alone.

This PR was rebased onto current main. The unit and GPU tests were re-run on the rebased code, but the end-to-end numbers come from the commit above.
