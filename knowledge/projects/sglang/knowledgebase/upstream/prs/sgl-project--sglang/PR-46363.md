# [Perf] hicache: Let the PP-sync channel run the pipeline's depth ahead, not one round (#45351)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46363) · state: open · merged: False

## Original PR description

Fixes #45351. Related: #45357 (hang in the same wait; this does not fix a rank that never posts its recv, see below), #42433 (removes the channel in cache mode on the old bootstrap ring), #28916 (the single-round drain).

## Motivation

`UnifiedRadixCache._pp_sync` posts one gloo `isend` per `_all_reduce` to the next PP rank, and `_drain_async_work` waits on all of the previous round's sends at the start of every `check_hicache_events`. A gloo send completes only when the receiver posts the matching `recv`, and rank r+1 posts it inside its own HiCache step, after its forward launch, result processing and the other PP receives. So rank r's round k+1 cannot start until rank r+1 reached round k's HiCache step: the pipeline runs in lock-step on this channel and `--pp-async-batch-depth` cannot let PP0 run ahead. #45351 measured ~20% of PP0's loop in that wait on a PP8 prefill server with runnable work queued.

Measured with the same gloo calls on CPU (torch 2.14.1): `isend()` returns in 0.2 ms, eight back-to-back sends issue in 3 ms, every send completes exactly when the receiver posts its recv, and `Work.is_completed()` never turns true on its own, only `wait()` reports completion. That last point is why the pre-#28916 non-blocking reap never reaped, and why a window has to be counted rather than polled.

## Modifications

- `unified_radix_cache.py`: `work_list` becomes `work_rounds`, a deque of per-round send lists. `_bound_async_work` (replacing `_drain_async_work`) opens the new round and waits out the oldest round only while more than `pp_sync_window = pp_size + pp_async_batch_depth` rounds are outstanding, i.e. the PP loop's own `pp_loop_size`. Window 1 is byte-for-byte the previous behaviour. Receivers consume in FIFO order on the one tag, so nothing changes in what they see; the list stays bounded, which keeps the #28916 leak fix.
- `cache_init_params.py`, `kv_cache_builder.py`: `pp_async_batch_depth` travels through `CacheInitParams` like `pp_rank` / `pp_size`, so the cache constructor reads no runtime context (unit tests build the cache without a published parallel namespace).

## Effect

4-rank gloo model of the loop (`isend` to r+1, blocking `recv` from r-1, the drain at the start of each round), follower rounds of 10 ms with a 200 ms burst every fifth round, leader with 45 ms of own work per round, 60 rounds:

| policy | leader blocked in the drain | leader's last round issued at | round p50 / p90 |
|---|---|---|---|
| single-round drain (main) | 1.17 s | 4.10 s | 50 ms / 154 ms |
| window 8 (this PR) | 0.00 s | 2.91 s | 49 ms / 50 ms |

Hardware: 2x B200, Qwen3-1.7B, PP2 x TP1, HiCache write_through (`--hicache-ratio 2`, `--max-total-tokens 200000`), chunked prefill 4096, no CUDA graph, not disaggregated (the channel is the same in every PP loop). Per server launch: 600 requests of 300..3000 random tokens at 8 req/s, then 3 x 400 requests at once, 16 output tokens each; six launches (the depth-0 pair twice). Time PP0's scheduler spent inside the drain / window wait, measured with a timing wrapper around the two functions over the ~170 s load window:

| config | PP0 inside the wait | whole HiCache step on PP0 | outstanding sends (max) |
|---|---|---|---|
| main, `--pp-async-batch-depth 0` (2 launches) | 12.1-12.6% of wall | 16.0-16.6% | 1 |
| this PR, depth 0 (2 launches) | 0.2% | 2.7% | 2 = pp_size |
| main, depth 2 | 11.5% | 15.2% | 1 |
| this PR, depth 2 | 0.2% | 2.7% | 4 = pp_size + depth |

Greedy outputs for 32 fixed prompts are identical across main and this PR at both depths; no error in any server log. Throughput is unchanged at this scale: saturating input throughput (3 samples per launch) is 45.6k / 49.7k tok/s for the two main launches vs 48.2k / 48.9k for this PR at depth 0, and 42.1k vs 43.1k at depth 2; with 3000 short prompts (128..256 tokens) 31.5k vs 30.5k at depth 0 and 17.6k vs 17.8k at depth 2; two launches of the same build differ by more than any main-vs-PR gap. The loop runs ~350 rounds/s here, most of them without a batch, so this 1.7B model is GPU-bound and PP0's blocked time is off the critical path. The reporter's case (16k chunks, PP8, 20% of PP0 in the wait with runnable work queued) is where the run-ahead should show up in throughput; this run verifies the mechanism and the bound, not that gain.

Not reproduced at the reporter's scale (PP8 Kimi-K3 PD prefill on two GB300 nodes).

## Tests

`test/registered/unit/mem_cache/test_hicache_pp_sync_drain.py` (CPU):
- `TestPPSyncWindow`: rounds inside the window are not waited; the oldest round is waited in full and the deque stays bounded at the window; window 1 is the single-round drain.
- `TestPPSyncWindowGloo`: two gloo processes, rank 1 sleeps 1 s before its first recv. With window 1 rank 0's second round blocks for more than 0.5 s (the lock-step); with window 4 rank 0 issues four rounds in under 0.5 s.
- The existing batching cases carry the new fields instead of mocking the drain.

## On #45357

PP0 to PP3 blocked in this wait means each waits for the next rank's recv, so the chain is stuck at PP4 or later, before PP4's HiCache recv. The window lets PP0 to PP3 tolerate a slow PP4 for `pp_loop_size` rounds, but a rank that never posts its recv still stalls the pipeline; the PP4 to PP7 stacks are needed for that one.
