# [Perf] hicache: Space out write_back eviction waits with a bounded reserve

[Upstream PR](https://github.com/sgl-project/sglang/pull/47650) · state: open · merged: False

## Original PR description

## Motivation

With `--hicache-write-policy write_back`, a device eviction backs its victims up to host and blocks on that copy (`writing_check(write_back=True)` -> `ack.finish_event.synchronize()`). The D2H stream is fenced on the forward stream (#44800), so every eviction pass waits for the whole in-flight forward.

On a saturated prefill instance the device pool is full, so nearly every scheduling step evicts exactly its shortfall and pays that wait. The scheduler loses its one-step lookahead every step. Under DP attention the peer rank waits for it in the DP-attention all-gather, and the GPU idles between forwards. In a PD prefill trace this was 14-15% GPU idle, almost all of it between forwards.

#46884 removed an earlier form of this wait (the coarse WAR barrier behind the write-back index copy). The eviction ack wait remains. #41690 adds a reserve at some allocator call sites. This PR instead puts the reserve inside `UnifiedRadixCache.evict()` and `evict_for_alloc()` without a predicate, which stay exact-shortfall today. Those are reached by the paged allocator's eviction, HiCache load-back and the linker LOAD path.

## Modifications

- New opt-in `SGLANG_OPT_HICACHE_WRITE_BACK_EVICTION_HEADROOM_TOKENS` (default 0: unchanged).
- Under write_back, `UnifiedRadixCache.evict()` and the no-predicate branch of `evict_for_alloc()` grow a nonzero Full / SWA shortfall by the reserve, capped by the evictable size.
- The predicate branch is unchanged: the allocator owns its stop condition.
- Eviction order is unchanged; freed slots return to the ordinary free pool.
- Where it applies: prefill and decode eviction through these two entry points when write_back is active (allocator `evict_to_free_tokens`, decode prealloc reclaim and capacity checks, HiCache load-back, linker LOAD). It does not apply to write_through, to caches without HiCache, or to the ChainAllocator paths that pass a reclaim predicate.
- Trade-off: the coldest reserve tokens are demoted to host earlier, so a later hit on them loads back from host. Prefix hit was unchanged at the point below (0.9647 vs 0.9646); a much larger reserve would trade device hits for fewer stalls.
- With #41690: separate env names. If both are set, their reserves stack (each capped by the evictable size); setting one is enough.

## Accuracy Tests

GSM8K (sgl-eval 0.1.3, 1319 examples, model preset, 1P1D PD with write_back HiCache): 96.66%, 0% truncated / errors. Same-build baselines without the reserve: 96.51-96.97%.

## Speed Tests and Profiling

DeepSeek-V4.1-Flash PD disaggregation on GB300: 6 prefill instances (DP-attention, 2 ranks each, write_back HiCache), 1 DEP16 decode. Agentic multi-turn trace at a prefill-heavy mid-curve operating point, 20 minutes, metrics from minutes 8-20. Reserve 262144 tokens (~0.3% of the prefill device pool). Both arms ran concurrently on the same image with #46884.

| | without reserve | with reserve |
|---|---|---|
| Output tput/GPU (min 8-20) | baseline | +0.5% |
| Output tput/GPU (whole run) | baseline | +1.0% |
| p90 interactivity (tok/s/user) | 191.8 | 190.6 |
| TTFT p90 / p50 | 8.45 s / 2.28 s | 7.89 s / 2.16 s (-6.6% / -5%) |
| Prefill steps/s per rank | 3.01 | 3.21 (+6.6%) |
| Prefill queue p50 | 11 | 6 |
| Prefix cache hit | 0.9646 | 0.9647 |
| Decode accept length | 3.51 | 3.51 |

The throughput change is within run-to-run noise at this point: prefill has spare capacity there, so the faster prefill shows up as lower TTFT and a shorter queue. Trace of the same mechanism with the reserve applied at the allocator call sites: prefill GPU idle 15.1% -> ~6%, and eviction stalls every 4-5 forwards instead of every forward. The remaining per-stall cost is the once-per-victim wait inside a larger pass, which #46930 addresses.
