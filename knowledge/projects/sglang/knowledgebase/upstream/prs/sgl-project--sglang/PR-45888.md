# [Feat] rust-server: Serve /abort_request from the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/45888) · state: closed · merged: True

## Original PR description

## Motivation

Python's HTTP frontend serves `POST /abort_request` (`AbortReq` body: `rid`, `abort_all`) and answers 200 with an empty body once the abort is handled. Clients and routers that cancel a request this way (for example a prefill/decode router aborting a paired decode request after a failed prefill) got a 404 from the Rust frontend, so the aborted request kept its slot until it finished or timed out on its own.

## Modifications

- `rust/sglang-server/src/api_server/http/info.rs`: add `POST /abort_request`. The handler reads Python's body (`rid`, default `""`; `abort_all`, default `false`) and cancels through the core's existing cancellation registry (`CoreHandle::abort`, the same primitive the gRPC `Abort` RPC uses): `abort_all` cancels every live generation, otherwise every live generation submitted under the public rid (all items of a batch sent under it). The response is Python's: 200 with an empty body whether or not anything matched. As in `TokenizerManager.abort_request`, an empty rid without `abort_all` is ignored rather than matching every request. A malformed body is a 400 with the native error body.
- The aborted request ends the way an explicit cancellation already does on the Rust frontend: the runtime is told to abort it and the client's stream ends with the cancelled error.
- Test `abort_request_cancels_the_named_generations` covers a rid match, `abort_all`, a rid nothing runs under, the ignored empty rid, an empty object, and a malformed body.
