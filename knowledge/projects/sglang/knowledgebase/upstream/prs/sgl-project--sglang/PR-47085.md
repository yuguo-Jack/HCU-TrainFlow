File: `python/sglang/srt/arg_groups/kv_cache_hook.py` · line 440

🔴 Operators who combine `--enable-prefill-weight-versions` with `--enable-lmcache` can crash the scheduler when a prompt reuses KV loaded from LMCache. The new guard rejects `enable_hierarchical_cache`, because restored KV has no weight version. LMCache restores KV into device slots in the same way, without a forward pass, yet it passes the guard. Fix: reject every KV source that fills slots without a model forward, including `enable_lmcache` (and `enable_unified_cache_external_linker` if it loads KV), next to the hierarchical-cache check.

<details>
<summary>Why this was flagged</summary>

With `--enable-lmcache`, the scheduler loads prefix KV from LMCache straight into device KV slots (scheduler.py:3415/4317 paths). No ModelRunner.forward runs for those slots, so `KvWeightVersionRecord` never records them and `_slot_version_ids` stays at `_UNWRITTEN_VERSION_ID` (-1). When that request's prefill finishes, `fill_req_prefill_weight_versions` reads the req_to_token slots of the prompt, and `_lookup_spans` raises `ValueError("KV slots without a recorded weight version were looked up: ...")` inside the scheduler loop, which kills the server. Without the new flag LMCache works on the base branch. The check at kv_cache_hook.py:399-411 covers only `enable_hierarchical_cache` and `disaggregation_mode`, and its own message gives the reason LMCache shares ("KV restored from the host or storage tiers carries no weight version").

**Verification:** The new guard at kv_cache_hook.py:399-411 rejects only `enable_hierarchical_cache` and disaggregation mode. `_start_external_load` (lmcache_unified_radix_cache.py:537) fills fresh slots through `lmcache_connector.submit_load(...)` with no model forward. `_lookup_spans` then raises `ValueError("KV slots without a recorded weight version were looked up: ...")`, so the scheduler crashes.

</details>

File: `python/sglang/srt/managers/scheduler_components/batch_result_processor.py` · line 412

🟡 (optional) With the flag on, every decoding request in a mixed or DP-converted extend batch re-runs the prompt-span lookup. Each lookup costs several GPU syncs, which slows those steps. Decode requests go through `process_batch_result_prefill` with `inflight_middle_chunks <= 0`, so they reach `fill_req_prefill_weight_versions` on every such step. Fix: compute the spans once per prefill and skip requests in `batch.decoding_reqs` or whose `prefill_weight_versions` is already set. `reset_for_retract` clears that field, so retracted requests still refill. Batch the lookups for a prefill batch into one gather and one D2H copy.

<details>
<summary>Why this was flagged</summary>

Two cases hit this path. With `--enable-mixed-chunk`, `mix_with_running` appends every running request to `batch.reqs` (schedule_batch.py:3987) and the batch is processed as an extend. Under DP attention, `maybe_convert_decode_to_extend` (dp_attn.py:807) turns a whole decode batch into EXTEND whenever a peer rank prefills. In both cases each running request passes the `continue` check and enters `if req.inflight_middle_chunks <= 0`. There batch_result_processor.py:358-359 calls `fill_req_prefill_weight_versions(req)` again, even though its prompt slots have not changed. `_lookup_spans` (kv_weight_version_tracker.py:122-145) does a GPU gather of the whole prompt, a `.any()` host sync, a `nonzero()` and two `.tolist()` syncs per request. So a 256-request running batch adds about a thousand blocking device syncs to the scheduler loop on each such step, and the result is identical every time. On the base branch this path does no per-request device work. The result is not wrong, only slower, and only while the opt-in flag is on.

**Verification:** With --enable-prefill-weight-versions and --enable-mixed-chunk or DP attention, an unfinished decode request has `inflight_middle_chunks <= 0`, so it passes the skip at batch_result_processor.py:348-354 and reaches `fill_req_prefill_weight_versions` at lines 356-359. Nothing checks `batch.decoding_reqs` or whether `req.prefill_weight_versions` is already set. Each lookup forces several device-to-host syncs. The expensive per-request lookup is new in this change.

</details>

File: `python/sglang/srt/mem_cache/kv_weight_version_tracker.py` · line 94

🔴 Hybrid-SWA servers using `--enable-unified-memory` with the new flag can hit a CUDA index-out-of-bounds device assert, which kills the scheduler. The tracker is sized as `allocator.size_full + allocator.page_size`. On a window `ChainAllocator`, `size_full` is only the admission cap, but the virtual KV ids in `out_cache_loc_virtual`/`req_to_token` cover the owner band's whole arena. Fix: size the tracker from the request-token id space, the way the routed-experts capturer does with `runner_ids.capture_token_capacity(max_token_pool_size)` (model_runner.py:1267), or reject `--enable-unified-memory`.

<details>
<summary>Why this was flagged</summary>

The trigger is a hybrid-SWA model started with `--enable-unified-memory --enable-prefill-weight-versions`. kv/build.py:252 then builds a `ChainAllocator` with a window role. `handle_cache_compatibility` (kv_cache_hook.py:399-435) never checks `enable_unified_memory`. The tracker only unwraps `SWATokenToKVPoolAllocator`, so it takes `ChainAllocator.size_full`. That is `_WindowPolicy.size_full` (interim.py:291), which returns the legacy `full_max_total_num_tokens` cap that kv/build.py:247 passes. The owner `Band`'s virtual ids come from `free_virtual_ids = arange(min_page_index, num_pages)` (band.py:495), with `num_pages` derived for the whole arena (arena.py:144). Pages are taken from the front and freed ones go to the back, so ids rise past `size_full + page_size` after enough churn. `record` and `_lookup_spans` then index past the end of the tensor, raise a CUDA device-side assert, and crash the server. On the base branch the flag does not exist.

**Verification:** Severity: normal. `KvWeightVersionTracker.maybe_create` (kv_weight_version_tracker.py:86-95) only unwraps `SWATokenToKVPoolAllocator`, so the tracker uses `num_slots=allocator.size_full + allocator.page_size`. `record` (line 108) does `self._slot_version_ids[slot_indices] = ...` on a CUDA tensor. An out-of-range index there raises a CUDA device-side assert, which corrupts the context and kills the scheduler.

</details>
