# [Feat] decisions: `--decision-config`, per-type default temperatures for ordinary chat models

[Upstream PR](https://github.com/sgl-project/sglang/pull/47790) · state: open · merged: False

## Original PR description

Adds an opt-in `--decision-config <file>` that sets default temperatures for `choice`, `noul` and `score` questions when an ordinary generation model answers on `/v1/systemone` and `/v1/decisions`. System One SDK clients can then get calibrated label probabilities without a `temperature` field, which that API doesn't have. Without the flag nothing changes.

- `/v1/systemone` keeps its request schema and still refuses `temperature`. On `/v1/decisions`, a request that sets `temperature` overrides the file.
- The file is the temperature part of a decision checkpoint's `decision_config.json`: `format_version`, scalar `temperature`, `temperature_by_type`. A type without an entry uses `temperature`, then 1.
- Decision checkpoints refuse the flag; they carry their own calibration.

## Why

On main, a decision checkpoint gets its trained temperature from `decision_config.json`, a file read only for a bare `Qwen3_5Model` backbone with a trained readout (`configs/model_config.py`). An ordinary chat model served for decisions has no equivalent: `/v1/systemone` scores it at 1.0, and `/v1/decisions` takes one temperature per request for all question types.

The right temperature differs by question type and is far from 1. Stock Qwen3.8-27B NVFP4 on `/v1/systemone`, fitted on the Typed Decisions `train` split: `choice` 2.58, `noul` 3.28, `score` 2.62. A fit pooled from other text datasets lowers Typed Decisions KL from 0.541 to 0.219, but it makes CIFAR-10H (image `choice`) worse, from 0.264 to 0.386. Typed Decisions gold is a teacher model's distribution, so its KL measures agreement with that teacher, not correctness. Values belong to one model and workload, so the PR ships no defaults; operators fit their own.

## Design

```json
{"format_version": 1, "temperature_by_type": {"choice": 2.5, "noul": 3.3, "score": 2.6}}
```

- `temperature_by_type` uses the key, type names and value rules (finite, above 0) of #45621; `yes_no` questions use `noul`, as there. `format_version` must be 1, as for checkpoints.
- Any other key (`codes`, `token_ids`, `attention_mode`, `pooling`, ...) is refused at launch with a message that it needs a decision checkpoint.
- The file is keyed by question type, not modality. Fits also vary by dataset and modality within a type (above), which a per-deployment file handles.
- Scoring stays one `score_prompts` call. With the flag set, each question's probabilities are taken from the raw label log-probabilities the scoring path already returns; without it the code path is unchanged.

## Tests

- CPU, added to `test_serving_decisions.py`, through the real handlers and score mixin with fixed log-probabilities: per-type temperatures on both routes, scalar fallback, request override on `/v1/decisions`, no file means 1, checkpoint refusal, and file validation (version, readout keys, unknown types, non-positive or non-numeric values). Local run of that file plus `unit/server_args`: 501 passed, 1 unrelated failure (`TestMultimodalFeatureTransport::test_default_transport_is_cpu_for_unsupported_multinode_model`, which also failed without this change in the same combined run and passes alone).
- Live server (RTX PRO 6000, `nightly-dev-cu13-20261101-cda284e4` with this commit, stock Qwen3.8-27B NVFP4): `/v1/systemone` answers with the file equal a flagless server's answers rescaled by each type's T, to 1.1e-16 on three requests; `/v1/decisions` uses the file only without a request `temperature`; `/v1/systemone` with `temperature` still returns 422; a file with `codes` is refused at launch; chat works.
