# [Fix] Preserve Falcon-H1 tied embedding dtype

[Upstream PR](https://github.com/sgl-project/sglang/pull/41674) · state: open · merged: False

## Original PR description

## Motivation

Fixes #41463.

With `tie_word_embeddings=True`, Falcon-H1 aliases `lm_head` to the input embedding module. Calling `.float()` on that shared module also converts the input embedding to FP32, causing the first fused RMSNorm to fail on BF16 models during server warmup.

## Modifications

- Keep the shared embedding/head in the model dtype and use the existing `LogitsProcessor.use_fp32_lm_head` path for FP32 logits.
- Preserve the existing FP32 head behavior for untied models.
- Add a registered CPU regression test covering tied/untied BF16, FP16, and FP32 weights, shared parameter identity, checkpoint loading, embedding output dtype, and LM-head numerical results. The test mocks backbone/distributed initialization but exercises the actual constructor, weight loader, and LM-head computation.

## Accuracy Tests

- The regression test fails on the original code for tied BF16/FP16 weights and passes with this fix. Final tests passed on CPU, CUDA, and with GPUs hidden (`CUDA_VISIBLE_DEVICES=99`).
- LM-head logits match an explicit FP32 matrix multiplication reference; tied weights retain their original dtype and identity after computation.
- Real `tiiuae/Falcon-H1-Tiny-90M-Instruct` (revision `e6389502a0b12cd8da894b395ba5bf7436873b16`): warmup plus single-input and two-input batch generation pass with all CUDA graphs disabled, and with only prefill graphs disabled while decode graphs remain enabled. All three greedy outputs (16 tokens each) match across these modes. These are functional/numerical checks, not a dataset accuracy evaluation.

Commands:

```bash
python test/registered/unit/models/test_falcon_h1_tied_embeddings.py
CUDA_VISIBLE_DEVICES=99 python test/registered/unit/models/test_falcon_h1_tied_embeddings.py
python -m sglang.launch_server \
  --model-path tiiuae/Falcon-H1-Tiny-90M-Instruct \
  --mem-fraction-static 0.4 --max-running-requests 8 \
  --context-length 1024 --cuda-graph-max-bs-decode 4 \
  --cuda-graph-backend-prefill disabled
```

Validation environment: RTX 4090 D (24 GB), driver 570.124.06, Python 3.12.12, PyTorch 2.13.0+cu129, Transformers 5.12.1, FlashInfer 0.6.18, and `sglang-kernel==0.4.6.post1+cu129`. This used `SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1`: the current 0.4.7 wheel requires CUDA 13, which was not validated on this host.

**Separate prefill graph limitation:** default prefill CUDA Graph replay still encounters an illegal memory access in this environment. An unmodified Falcon-H1 implementation with an untied control checkpoint (a cloned output head with the same weight values) reproduces that failure, so it does not require this patch. Synchronous CUDA execution locates the failure in model-body graph replay before the LM head. A separate diagnostic eager boundary around Mamba fixes the tested cases, but is deliberately outside this PR. This PR does not claim to fix the prefill graph issue.

## Speed Tests and Profiling

No throughput benchmark or performance improvement is claimed. A before/after serving comparison is unavailable because the original tied model fails warmup. This reuses the existing FP32-output LM-head path and leaves the untied path unchanged.
