## XPU: SYCL vs Triton `build_tree_kernel_efficient` — validation & performance

**TL;DR**
- **Correctness:** the SYCL kernel's output is bit-identical to the Triton kernel's. End-to-end accuracy matches, and with `--enable-deterministic-inference` all 200/200 MMLU generations are byte-identical.
- **Performance:** no measurable end-to-end change. `build_tree` is ~0.05% of a decode step's GPU time, and its host work is fully overlapped with GPU execution.
- **Default:** kept opt-in. `SGLANG_ENABLE_SPEC_OPTIMIZED=1` selects SYCL; the default stays Triton.

**Setup**
- **Hardware/software:** Intel Arc Pro B60, single GPU (TP=1), torch 2.13+xpu, `sglang-kernel-xpu` 0.3.0 wheel.
- **Model:** Llama-3.1-8B-Instruct BF16 + `lmsys/sglang-EAGLE3-LLaMA3.1-Instruct-8B`, EAGLE3 `--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`.
- **Serving:** `--attention-backend intel_xpu --page-size 64`, XPU decode graph on (`--cuda-graph-backend-decode full`). The Triton attention backend was also checked.
- **Note:** on XPU, `build_tree_kernel_efficient` runs for topk=1 too. The CUDA chain fast path requires `seq_lens.is_cuda`.

### Correctness

- **Kernel parity:** 592 configs (topk 1/2/4/8, steps 1–5, bs 1–32, `FULL_MASK` + `QLEN_ONLY`, int64/int32 `seq_lens`). `tree_mask`, `positions` and `retrive_*` are all bit-identical.
- **Unit test:** `test/registered/xpu/test_spec_build_tree_sycl.py` covers parity through `build_tree_kernel_efficient`, a regression for the uint8 verify-mask buffer, and env-flag routing.
- **Bug found end-to-end and fixed:** the Triton attention backend preallocates the verify mask as `uint8` (`maybe_create_verify_mask(dtype=torch.uint8)`), and the SYCL op requires `bool`. The SYCL branch now passes `tree_mask.view(torch.bool)`, which is zero-copy with the same 0/1 bytes.
- **MMLU** (sgl-eval 0.1.2, `MMLUSanityMixin` settings: 200 examples, 64 threads, temperature 0, max_tokens 1024):

| Config | Triton build_tree | SYCL build_tree |
|---|---|---|
| intel_xpu attention | 0.675 | 0.690 |
| Triton attention | 0.700 (repeat 0.690) | 0.705 |
| Triton attention + `--enable-deterministic-inference` | 0.695 | 0.695 (**200/200 generations byte-identical**) |

All scores are within the ±3.2 pp standard error. Without deterministic inference, two *Triton-vs-Triton* runs share only 82/200 identical generations, because XPU batching is nondeterministic. So text identity is only meaningful in deterministic mode.

### Performance (intel_xpu attention, graph on, bs=1, fixed 6 × 384-token workload)

| | Triton build_tree | SYCL build_tree |
|---|---|---|
| Step time (no instrumentation) | 43.04 / 43.04 ms | 43.06 / 43.16 / 43.10 ms |
| Throughput | 52.85 tok/s | 52.7 tok/s |
| Accept length | 2.274 | 2.274 |

With Triton attention (GSM8K, 2 runs per kernel), throughput also matched: bs=1 28.25 vs 28.25 tok/s, and conc 8 70.23 vs 70.41 tok/s (±0.5% run-to-run noise).

<summary>Per-step breakdown (intel_xpu, graph on, bs=1)</summary>

Host time comes from `perf_counter` wrappers (adds +0.3 ms/step). GPU time comes from XPU events in a separate run. Step time comes from runs with no instrumentation.

| Stage | Host, Triton | Host, SYCL | GPU, Triton | GPU, SYCL | Share of step GPU |
|---|---|---|---|---|---|
| Draft (draft-decode graph: 2 draft forwards) | 0.69 ms | 0.63 ms | 4.55 ms | 4.52 ms | 10.6% |
| ├ draft attention metadata | 0.18 | 0.18 | 0.50 | 0.48 | 1.1% |
| └ **build_tree** | **0.19** | **0.12** | **0.023** | **0.022** | **0.05%** |
| Verify (target-verify graph: 32 layers × 4 tokens, then accept) | 0.78 | 0.81 | **35.93** | **35.93** | **83.7%** |
| Draft extend (draft-extend graph) | 0.63 | 0.66 | 2.15 | 2.15 | 5.0% |
| **Whole step** (`forward_batch_generation`) | **2.21** | **2.19** | **42.93** | **42.81** | 100% |

The host queues the whole step in ~2.2 ms and then waits. The GPU is busy ~42.9 ms of a ~43.0–43.1 ms step, so it's idle less than 1% of the time. Target verify (84%) is the bottleneck: it streams ~15 GB of weights per pass at ≈420 GB/s, near the B60's 456 GB/s peak.

</details>

<details>
<summary>Inside build_tree (in-server GPU kernels per call)</summary>

| Kernel | Triton path | SYCL path |
|---|---|---|
| Tree-mask `fill_` + draft-token `cat` + init `fill_` | 5.3 + 4.4 + 1.7 µs | 5.1 + 4.5 + 1.7 µs |
| Seq-len `cumsum` + `sub` | 4.2 + 3.3 µs | — |
| Tree kernel | 5.1 µs (`sgl_build_tree_kernel_efficient_triton`) | 12.3 µs (`BuildTreeKernel`) |
| **Total GPU** | **24.0 µs (6 kernels)** | **23.6 µs (4 kernels)** |
| **Host** | **0.19 ms** | **0.12 ms** |

Standalone micro-benchmark per call: Triton 43–58 µs eager versus SYCL ~13 µs. That gap is mostly host launch overhead. Measured GPU time is 7.6–8.3 µs vs 4.0–6.4 µs. In-server, the SYCL kernel runs longer (12.3 µs), but it also removes two launches, so the GPU total is the same.

**Why there's no end-to-end gain:** SYCL saves ~70 µs of host time per step, which overlaps with the 4.5 ms draft already running on the GPU, and the GPU time is unchanged. Injecting extra host delay at the `build_tree` call site showed ≥1.5 ms (intel_xpu) to ≥4 ms (Triton attention) of host slack there.

</details>

<details>
<summary>Measurement notes</summary>

- XPU torch-profiler (PTI) traces don't record kernels that run inside XPU graph replays. A replay appears as one `zeCommandListImmediateAppendCommandListsExp` call. Getting kernel-level splits requires a graph-off trace.
- Profiler Python stack tracing inflates host time roughly 10x. Kernel durations are still accurate, since they come from device timestamps.
- On intel_xpu, recording timing events sits on the host critical path. sglang's `SGLANG_ENABLE_METRICS_DEVICE_TIMER=1` adds ~3 ms/step (43.1 → 46.1 ms). So host times above come from `perf_counter` only, device times from a separate event run, and step times from uninstrumented runs.

</details>

**Repro (server)**
```bash
SGLANG_ENABLE_SPEC_OPTIMIZED=1 \
SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 \
python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct \

```
Set `SGLANG_ENABLE_SPEC_OPTIMIZED=0` (or leave it unset) for the Triton path. `SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1` is needed because the EAGLE3 draft config declares a 2048-token context.

## Update: SYCL `verify_tree_greedy` on XPU (same flag)

**TL;DR**
- **What's new:** `SGLANG_ENABLE_SPEC_OPTIMIZED=1` now enables **both** SYCL kernels on XPU: `build_tree_kernel_efficient` and `verify_tree_greedy`. The default is unchanged (Triton for both).
- **Correctness:** the SYCL verify kernel is bit-identical to Triton. With `--enable-deterministic-inference`, MMLU generations are 200/200 byte-identical.
- **Performance:** no measurable end-to-end change. The verify kernel is ~10 µs of a ~43 ms decode step, and its host cost is overlapped with GPU work.

**Change** (`python/sglang/srt/speculative/eagle_utils.py`, `verify_tree_greedy_func`)
- When the flag is set, XPU takes the existing `sgl_kernel.verify_tree_greedy` branch, the one MUSA already uses, with the same `retrive_*` argument names. With the flag off, the Triton path is unchanged.
- Note: on XPU, EAGLE verify is always greedy (`_verify_uses_greedy` includes `is_xpu`), so this kernel runs for every speculative request.

### Correctness

- **Kernel parity:** 592 configs (topk 1/2/4/8, steps 1–5, bs 1–32, 0–5 accepted drafts per request). `predicts`, `accept_index` and `accept_token_num` are all bit-identical.
- **Dtype contract:** the SYCL op requires `candidates`, `retrive_*` and `target_predict` to share one dtype, while Triton accepted mixed dtypes. The server path passes int64 for all of them, which is the same contract the CUDA kernel enforces, so no cast is added. A mismatch raises a clear error rather than failing silently.
- **Unit tests** in `test/registered/xpu/test_spec_build_tree_sycl.py`:
  - added `test_sycl_verify_matches_triton`, bit-parity through `verify_tree_greedy_func`;
  - extended `test_flag_selects_kernel` to assert both SYCL kernels are routed when the flag is on, and neither when it's off;
  - result: 6 tests / 14 subtests pass.
- **Correction to my earlier `build_tree` comment.** The test's random draft-tree generator used independent scores at each depth. For topk>1 that produced **disconnected** trees: `retrieve_next_token` was all -1, so verify could never accept anything.
  - The generator now uses cumulative path scores (child = beam × p) and selects beams by top-k, matching `select_top_k_tokens`.
  - Re-validated on connected trees: `build_tree` is **1184/1184** bit-identical (592 configs × `FULL_MASK` / `QLEN_ONLY`), and verify is 592/592.
  - The topk=1 results and the earlier end-to-end checks were unaffected.

**MMLU** (sgl-eval 0.1.2, `MMLUSanityMixin` settings: 200 examples, 64 threads, temperature 0, max_tokens 1024). The in-server profiler confirmed which kernels ran in each leg.

| Config | Triton (build_tree + verify) | SYCL (build_tree + verify) |
|---|---|---|
| intel_xpu attention | 0.690 | 0.675 |
| Triton attention + `--enable-deterministic-inference` | 0.695 | 0.695 (**200/200 generations byte-identical**) |

The intel_xpu gap is within the ±3.2 pp standard error. The earlier `build_tree`-only pair came out the other way round: 0.675 vs 0.690.

### Performance (intel_xpu attention, XPU graph on, bs=1, fixed 6 × 384-token workload)

| | Triton path | SYCL path |
|---|---|---|
| Step time (no instrumentation) | 43.48 / 43.01 ms | 43.41 / 43.32 ms |
| `verify_tree_greedy` per step: GPU / host | 10 µs / 53 µs | 9 µs / 32 µs |
| `build_tree` per step: GPU / host | 23 µs / 175 µs | 22 µs / 109 µs |
| Whole step: host / GPU | 2.02 / 42.98 ms | 1.97 / 42.85 ms |

<details>
<summary>Why there's no end-to-end gain</summary>

- **Standalone, per call:** Triton verify takes ~32–37 µs and SYCL ~19 µs, back-to-back including output allocation. That gap is mostly host launch overhead.
- **In the server:** both SYCL kernels together save ~44 µs of host time per step. The host queues the entire step in ~2 ms while the GPU works for ~43 ms, so the saving is hidden behind GPU execution.
- **Device side:** the two kernels are ~32 µs of a 42.9 ms GPU step (<0.1%). The step is dominated by target verify (~36 ms, 84%), which streams weights near the B60's memory-bandwidth limit.

</details>

<details>
<summary>Measurement notes</summary>

Host times come from `perf_counter` wrappers around each stage, which add ≤0.4% to step time. GPU times come from XPU events recorded in a separate run. Step times come from runs with no instrumentation. Torch-profiler and `SGLANG_ENABLE_METRICS_DEVICE_TIMER` timings are not used, because on intel_xpu they perturb the host critical path (device timer: +3 ms per step).

</details>
