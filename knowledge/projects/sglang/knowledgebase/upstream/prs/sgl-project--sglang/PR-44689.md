# [Feat] sgl-model-gateway: Add --decode-dispatch-limit to pick PD decode workers near KV arrival

[Upstream PR](https://github.com/sgl-project/sglang/pull/44689) · state: closed · merged: True

## Original PR description

## Motivation

In PD mode the gateway picks the decode worker (the DP rank with `--dp-aware`) on arrival, but decode starts only after prefill has queued, computed and sent the KV, so under long prefill queues running batches stay uneven across ranks. #44402 makes the same change in `experimental/sgl-router`.

## Modifications

- `--decode-dispatch-limit N` (PD only; unset keeps today's behaviour): prefill gets every request on arrival; at most N per prefill worker (DP rank with `--dp-aware`) go on to decode until decode answers or prefill finishes, and the rest pick their decode worker when sent. Needs prefill `--optimistic-prefill-attempts` above 0.
- `decode_gate.rs`: a FIFO semaphore per prefill worker. `pd_router.rs`: prefill first, then gate, select and send decode; a disconnect or `--request-timeout-secs` ends the wait. Plus config, CLI, bindings, docs.

## Testing

- New `pd_routing_tests::test_pd_decode_dispatch_limit_holds_decode_not_prefill`: with one slot, prefill receives both requests at once and the second decode request arrives only after the first one's slot frees (~600 ms). With the gate bypassed, both decode requests arrive within ~1 ms and the test fails.
- Passing: `cargo clippy --workspace --all-targets --all-features -- -D warnings`, nightly rustfmt on the touched files, `cargo test --lib`, `--test routing_tests` and `--test reliability_tests` (apart from `redis_test_server`, which needs a local `redis-server`), and `test_arg_parser.py` / `test_pyo3_binding.py` after `maturin develop`.

## Benchmark (MI355X)

DeepSeek-V4-Pro, 1 prefill + 1 decode engine with 8 DP-attention ranks each, AgentX trace replay with AIPerf (multi-turn agentic sessions, 96% prefix-cache hit), 1 h per concurrency. Gateway `--pd-disaggregation --policy consistent_hashing --dp-aware --decode-policy power_of_two --request-timeout-secs 14400`, built at 1e86143bf0 with #42027, #43483's `SGLANG_ROUTER_P2C_LOAD_METRIC=least_requests` (decode goes to the rank with the fewest router in-flight requests), and this change (read from an environment variable at the time). Both arms ran the same build and recipe, including prefill `--optimistic-prefill-attempts 2`, and neither had request errors.

- Decode now receives a request about 6 s before its first token instead of 15–32 s, so what it holds waiting on KV drops 62–80%, and the running batches even out: CV -24% / -33%, busiest rank's batch -6% / -4%. TPOT p50 -3.2% / -1.3%, p90 -4.9% / -3.3%.
- At 512 decode also ran 3% more requests at the same engine TPOT, and output throughput rose 4.0% with prefill new tokens/s up 2.3%. At 384 throughput rose 1.5% with prefill unchanged.
- Prefill is not held back: its queue, forward size and throughput match the unset run. The optimistic yields are chunked prefills that paused because their decode had not connected yet while a request with decode connected was waiting; they resume from the radix cache.
- TTFT changed with prefill queue time (p50 -3.8% / -0.3%, p90 -7.3% / -2.2%), which varies between runs.

### Per-rank decode load

Same runs, computed as in #43511: each decode rank's `Decode batch` log lines sampled every second; outstanding = running + waiting on KV transfer (prealloc, retracted and queue stayed 0). Stdevs are across the 8 ranks, p50 over the hour; busiest ÷ mean running excludes the first 5 min of ramp-up. With the limit, requests waiting for a decode slot are at the gateway, not in decode's outstanding count. Unset → `--decode-dispatch-limit 8`:

| conc | outstanding stdev (req) | waiting-on-KV stdev (req) | running stdev (req) | waiting ÷ outstanding | busiest ÷ mean running, p50 / p90 |
|---|---|---|---|---|---|
| 384 | 0.78 → 0.87 | 2.78 → 1.97 | 2.74 → 2.05 | 44% → 23% | 1.20 / 1.32 → 1.14 / 1.22 |
| 512 | 0.78 → 0.97 | 3.27 → 2.18 | 3.20 → 2.28 | 62% → 24% | 1.23 / 1.40 → 1.14 / 1.23 |

![Per-rank outstanding, waiting-on-KV and running requests at concurrency 512, unset vs --decode-dispatch-limit 8](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-sgl-router/gateway-decode-dispatch-c512-per-rank.png)

![Busiest ÷ mean running, waiting on KV and prefill queue over the hour at concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-sgl-router/gateway-decode-dispatch-c512-over-the-hour.png)

- As with #44402: waiting drops to 23–24% of decode's requests, its spread by 29–33%, and the running spread with it (-25% / -29%), while outstanding requests are slightly less even.
