# [Fix] batch-invariant: deterministic mode runs fp32 matmuls in TF32 (Gemma 3 breaks past 2k tokens)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47800) · state: open · merged: False

## Original PR description

## Motivation

with `--enable-deterministic-inference` (or `--rl-on-policy-target`), the persistent mm/bmm kernels in `batch_invariant_ops.py` (#10695, #12000) call `tl.dot` with no precision, so fp32 inputs run in tf32 on nvidia even when torch has tf32 off. gemma 3 builds its rope angles with an fp32 bmm, so every position above 2048 gets rounded to 11 bits (2049 -> 2048, 4097..4099 -> 4096) and long prompts fall apart: passkey at ~6.8k tokens is 1/40 in deterministic mode vs 40/40 by default.

## Modifications

use `"ieee"` for fp32 `tl.dot` unless torch allows tf32 (`torch.backends.cuda.matmul.fp32_precision == "tf32"`), matching `aten::mm` and `fla/kda.py`. bf16/fp16 calls and `--enable-tf32-matmul` models (Glm4Moe, MiniMaxM2) compile to the same code as before.

## Accuracy Tests

H100 (google/gemma-3-1b-it), repro: https://gist.github.com/EvanZhuang/a4fd70fa2388e7493e85baf7cbc1b29a (`python3 repro.py --engine google/gemma-3-1b-it`):

|Check|default|deterministic (main)|deterministic (+ patch)|
|---|---|---|---|
|RoPE wrong angles in 0..8191 (n=1,048,576)|0|1,044,353|0|
|Gemma3RotaryEmbedding mismatched positions (n=8,192)|0|8,191|0|
|fp32 mm/bmm max error vs fp64 (K=1536)|7.1e-5|0.115 / 0.132|1.9e-4 / 3.0e-4|
|Gemma-3-1B-it passkey at ~6,800 tokens (n=40)|40/40|1/40|40/40|

tests: `pytest test/registered/unit/batch_invariant_ops/` (16 passed across 4 files; 2 new tests in `test_batch_invariant_ops.py` fail on main) and `test_qsa_determinism.py` (4 passed).

## Speed Tests and Profiling

on H100 (`do_bench`, cold L2), gemma 3's rope bmm is unchanged (11.5 -> 10.7 us at N=2048, 11.5 -> 11.0 us at N=8192), as is end-to-end gemma-3-1b-it prefill (0.237 s) and decode (0.893 s). the one cost is fp32 gate matmuls in models that never enabled tf32 now run at ieee speed in deterministic mode (e.g. 76 us -> 1.02 ms for [64,5120]x[5120,160]), same precision as default mode; models with `--enable-tf32-matmul` keep tf32 (75.7 vs 75.6 us).
