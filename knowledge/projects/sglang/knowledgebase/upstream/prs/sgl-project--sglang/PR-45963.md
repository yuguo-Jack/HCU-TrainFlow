# [Fix] trtllm_mha: include draft-extend-v2 in the native-FP4 forward_extend gate

[Upstream PR](https://github.com/sgl-project/sglang/pull/45963) · state: open · merged: False

## Original PR description

## Motivation

`--kv-cache-dtype nvfp4` combined with speculative decoding crashes in the draft-prefill step of the verify loop (#36010).

`_forward_extend_uses_native_fp4` gates the physical-NVFP4 read on `is_target_verify()` only, but the sibling batch-metadata dispatch in this same file already groups both roles as decode (`is_decode_mode = is_target_verify() or is_draft_extend_v2()`). When a hybrid backend routes the draft-extend-v2 (spec-v1 draft-prefill) role to the decode child, the gate mismatch sends that batch into the BF16 dequant workspace path where `extend_prefix_lens_cpu` is `None` — the `TypeError` reported in #36010. Treating the gate as an omission, not a design: it must match the dispatch next to it.

A full field report with production numbers (SM120 TP2 rig, 224 K-token NVFP4 pool × NEXTN × HiCache, accept length up to 2.7) is in https://github.com/sgl-project/sglang/issues/36010#issuecomment-6357159017.

## Modifications

One term added to the decode branch of `_forward_extend_uses_native_fp4` (`or forward_batch.forward_mode.is_draft_extend_v2()`), docstring updated to name both routed roles and cross-reference #36010.

## Behavior

Pure relaxation of a branch that today hard-crashes: configs that worked before take exactly the same paths (the term can only flip `False → True` for `DRAFT_EXTEND_V2` batches on a native-FP4 decode child, which are the crashing ones). No effect on any non-NVFP4 or non-speculative configuration — `uses_trtllm_gen_native_fp4` short-circuits first.
