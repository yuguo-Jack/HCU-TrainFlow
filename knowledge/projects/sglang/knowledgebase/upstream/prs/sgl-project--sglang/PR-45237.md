# [Perf] diffusion: Fold the Cosmos3 audio tokenizer weight norm at load

[Upstream PR](https://github.com/sgl-project/sglang/pull/45237) · state: open · merged: False

## Original PR description

## Motivation

The Cosmos3 audio tokenizer wraps every convolution in `torch.nn.utils.weight_norm`. That hook recomputes each weight from `weight_g` and `weight_v` at every forward and keeps the result on the module. After the first sound request the device therefore holds a second copy of every tokenizer weight, allocated inside that request's transient memory. The worker releases the allocator cache after each request, but a segment that still holds one of those weights cannot be returned, so the memory a later request sees depends on which requests ran before it, and a server that has decoded sound keeps up to about 1.5 GiB more reserved than it needs.

## Modifications

- After the checkpoint is loaded, each weight norm is folded into its convolution with `remove_weight_norm`. The fold runs on the device that runs decode, so the folded weights are exactly the ones the hook computed, and each folded weight is written back into the storage that held `weight_v`, so the parameter layout of the load is unchanged.
- The fold's temporaries are released once at load.
- Decode no longer recomputes the weights and no longer leaves copies on the device. Outputs are unchanged.

## Accuracy Tests

```bash
pytest python/sglang/multimodal_gen/test/unit/test_cosmos3.py python/sglang/multimodal_gen/test/unit/test_vae_loader.py
```

The new `test_load_folds_weight_norm` fails on main, where every `weight_g` survives the load, and passes here. Both files pass as on main otherwise.

`nvidia/Cosmos3-Nano` served with its defaults through every Cosmos3 modality (text, image and video to video, with and without sound, and the action modes), 636 requests per arm in fresh servers. Every output is byte for byte the output before the change.

## Speed Tests and Profiling

One H200 per server, a fresh server per run, the same workload in each, eight paired runs and four more on fresh prompts, seeds and source media. Sampled device memory while each request kind runs, MiB, mean of the eight paired runs.

| Request kind | Before | After | Change |
| --- | --- | --- | --- |
| Text to video | 39598 | 38168 | -1430 |
| Video to video | 39568 | 38150 | -1418 |
| Text to video with sound | 39566 | 38146 | -1420 |
| Image to video with sound | 39680 | 38146 | -1534 |
| Video to video with sound | 39622 | 38148 | -1474 |
| Inverse dynamics | 34716 | 33510 | -1206 |
| Video to video with sound, two at once | 39720 | 38152 | -1568 |
| Idle between requests | 34382 | 32730 | -1651 |

Peak memory over a whole run is 16 MiB lower and readiness memory is unchanged. Latency, throughput, GPU time and energy per request, host CPU and memory, startup and shutdown show no measurable difference in either set of runs.
