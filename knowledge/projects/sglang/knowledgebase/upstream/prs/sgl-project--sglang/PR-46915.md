# [Fix] [AMD] layernorm: call vLLM fused_add_rms_norm with its in-place signature

[Upstream PR](https://github.com/sgl-project/sglang/pull/46915) · state: open · merged: False

## Original PR description

## Motivation

On ROCm without aiter (`SGLANG_USE_AITER` unset, which is the normal setup on RDNA) and with vLLM installed, `layernorm.py` binds `fused_add_rms_norm` from `vllm._custom_ops`. vLLM's signature is the four-argument in-place one:

```
fused_add_rms_norm(input, residual, weight, epsilon) -> None
```

But `RMSNorm.forward_hip` and `GemmaRMSNorm.forward_hip` call it with the six-argument out-of-place form. So the first forward with a residual, i.e. the second decoder layer of every model, fails:

```
TypeError: fused_add_rms_norm() takes 4 positional arguments but 6 were given
```

This is not RDNA-specific. CDNA with aiter turned off hits it too. I reproduced it on gfx950 with vLLM 0.30, and on gfx1100 with vLLM 0.16 and 0.31. Part of the RDNA plan in #46900; the same fix applies to `main`.

## Modifications

- `RMSNorm.forward_hip` and `GemmaRMSNorm.forward_hip` (vLLM branch):
  - Call `fused_add_rms_norm(x, residual, weight, eps)` in place and return `(x, residual)`, as `forward_cuda` already does with sgl-kernel's in-place kernel.
  - `residual` is made contiguous first, since vLLM's kernel requires it.
- Empty batches go to `forward_native`. The vLLM kernels fail to launch with an empty grid (`hipErrorInvalidConfiguration`), which I also hit on gfx1100.
- The aiter branches are unchanged.

**Regression test:** `test/registered/unit/layers/test_layernorm_hip_vllm.py` (CPU suite).
- It patches in a reference with vLLM's exact signature and in-place semantics, and checks `forward_hip` against `forward_native` for both classes, including an empty batch and `post_residual_addition`.
- It fails on the current code (`5 failed`, all `TypeError`) and passes with this change.

## Accuracy Tests

**Real vLLM kernel, gfx1100.** Radeon PRO W7900D, vLLM 0.31.0, torch 2.13, `SGLANG_USE_AITER=0`. Each case compares `forward_hip` to `forward_native` (fp32 reference math) for `(out, residual)`:

| case | `amd_march` | this PR: max abs err (out / residual) |
|---|---|---|
| RMSNorm bf16 [33, 4096] | TypeError | 3.1e-2 / 0 (1 bf16 ulp) |
| RMSNorm fp16 [33, 4096] | TypeError | 3.9e-3 / 0 |
| RMSNorm bf16 [2, 17, 4096] | TypeError | 3.1e-2 / 0 |
| RMSNorm bf16, non-contiguous residual | TypeError | 3.1e-2 / 0 |
| RMSNorm bf16, `post_residual_addition` | TypeError | 3.1e-2 / 6.3e-2 (summation order, same as `forward_cuda`) |
| RMSNorm empty batch | TypeError | OK |
| GemmaRMSNorm, same six cases | TypeError | same as RMSNorm, residual exact |

The same fix on `main`, checked on gfx950 (MI355X, vLLM 0.30.0, aiter off), gives the same numbers.

**Unit test** (CPU):

| tree | result |

**End to end, gfx1100.** Qwen/Qwen3-8B bf16, TP1, default args (Triton attention, decode CUDA graph), vLLM 0.31 installed, no aiter. Applied on top of #46914, which makes the quark imports work without aiter. `sgl-eval==0.1.2` gsm8k, 200 examples, `enable_thinking=false`, temperature 0.7, top_p 0.8: **0.955**. Without this change the scheduler dies on the first request with the `TypeError` above.

gfx1201 (R9700): the vLLM build I have for gfx1201 doesn't register the `_C` RMSNorm ops at all (`'_OpNamespace' '_C' object has no attribute 'rms_norm'`), so this path can't be exercised there. The CPU unit test covers the call shape, and the gfx1201 end-to-end run in #46914 uses `forward_native`.
