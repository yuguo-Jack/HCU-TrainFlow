# [Fix] [AMD] ct-fp8-moe: Mark the pre-shuffled CT FP8 MoE weights is_shuffled

[Upstream PR](https://github.com/sgl-project/sglang/pull/47870) · state: open · merged: False

## Original PR description

## Motivation

`CompressedTensorsW8A8Fp8MoE.process_weights_after_loading` already pre-shuffles
the expert weights for AITER. The shuffle was introduced in #17503 (2026-02-16)
and later narrowed to the AITER runner in #45486; `is_shuffled` has never been
set in this file:

```python
layer.w13_weight = torch.nn.Parameter(
    shuffle_weight(layer.w13_weight.data, (16, 16)), requires_grad=False)
layer.w2_weight  = torch.nn.Parameter(
    shuffle_weight(layer.w2_weight.data,  (16, 16)), requires_grad=False)
```

but it never sets the `is_shuffled` marker that AITER reads to pick a kernel.
`aiter/fused_moe.py` resolves the flag with

```python
is_shuffled=getattr(w1, "is_shuffled", False) and getattr(w2, "is_shuffled", False)
```

so the default `False` wins and **AITER has no way to know the weights are
already in its shuffled layout.** The sibling Quark scheme
(`quark/schemes/quark_w8a8_fp8_moe.py`) performs the identical shuffle *and*
sets the marker; this path is the only AITER MoE scheme that shuffles without
tagging.

**Two consequences:**

1. *Today, silently:* AITER dispatches the `preshuffle_off` CK instance for
   weights that **are** shuffled — kernel and data layout disagree. Visible in
   the log as
   `module_moe_ck2stages_f8_f8_preshuffle_off_b16_silu_per_token_mulWeightStage2`.
2. *With a newer AITER:* [ROCm/aiter#6736](https://github.com/ROCm/aiter/pull/6736)
   added `_require_shuffled_gfx950_fp8`, which rejects an unshuffled-looking
   `per_Tensor`/`per_Token` fp8 MoE call on gfx950. Because this path reports
   `is_shuffled=False`, the call now raises:

```
RuntimeError: gfx950 fp8 CK MoE reads the shuffle_weight() layout on both w1
and w2; unshuffled per_Tensor and per_Token weights are unsupported
```

This is how the problem surfaced: it fails
`test/registered/unit/layers/quantization/test_compressed_tensors_fp8_moe_layout.py::test_aiter`
on all three ROCm flavors in the AMD AITER Scout run that pins AITER to
`bd4ff1c70`, and it blocks advancing the AITER pin past `285579b62`.

The AITER-side guard is behaving correctly — it caught a real mislabel on our
side. Tagging the tensors is the fix.

## Modifications

Set `is_shuffled = True` on `w13_weight` and `w2_weight` immediately after the
existing `shuffle_weight()` calls, matching
`quark_w8a8_fp8_moe.process_weights_after_loading`. No change to the shuffle
itself, to the quantization, or to any non-AITER path — the block is already
gated on `strategy == CHANNEL and _use_aiter and runner_backend.is_aiter()`.

## Accuracy Tests

Offline on MI355X (gfx950), one GPU, container
`rocm/sgl-dev:v0.5.23-rocm724-mi35x-20261030`, SGLang tree pinned to the Scout's
`01fde5cb6`. Every AITER pin verified three ways (`aiter/_version.py`,
`git rev-parse HEAD`, `importlib.metadata`) before each run.

| AITER | this patch | `test_compressed_tensors_fp8_moe_layout.py` | CK instance AITER loaded |
|---|---|---|---|
| `285579b62` (current pin) | no | ✅ OK (2 tests) | `…preshuffle_**off**…` |
| `bd4ff1c70` (Scout candidate) | no | ❌ **FAILED** — the RuntimeError above | — (guard raises) |
| `bd4ff1c70` (Scout candidate) | **yes** | ✅ **OK** | `…preshuffle_**on**…` |
| `285579b62` (current pin) | **yes** | ✅ OK | `…preshuffle_**on**…` |

The kernel name is the point: the weight bytes are identical in every row, only
the marker changes, and AITER switches to the instance that matches the layout
this scheme already produces. Row 4 shows the patch is safe on the currently
pinned AITER — it is not coupled to the pin bump.

Also verified: reverting only `44b4fea64` (the aiter#6736 commit) on the
candidate restores the pass without this patch, confirming the attribution.

## Speed Tests and Profiling

Not measured. The change selects the CK instance that matches the data layout
rather than the mismatched one, so a throughput difference is plausible; this PR
does not claim one.

## What this does not cover

The shuffle block is gated on `QuantizationStrategy.CHANNEL`. A **TENSOR**-strategy
CT FP8 MoE still reaches AITER with genuinely unshuffled weights, and on a newer
AITER would hit the same guard legitimately. That case needs either a shuffle for
the tensor-strategy path or an explicit non-AITER route; it is out of scope here
and no regression is introduced for it.
