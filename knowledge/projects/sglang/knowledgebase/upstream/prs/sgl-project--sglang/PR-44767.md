# [Feat] rust-server: Serve /v1/tokenize and /v1/detokenize from the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44767) · state: closed · merged: True

## Original PR description

## Motivation

The Rust frontend answers 404 on `/v1/tokenize` and `/v1/detokenize`, which Python serves through `OpenAIServingTokenize` and `OpenAIServingDetokenize`. A client that counts tokens before sending a prompt, or decodes ids it received, cannot use a Rust-mode server.

## Modifications

Serve `/v1/tokenize` and `/v1/detokenize`, plus the unversioned `/tokenize` and `/detokenize` aliases, from the Rust frontend with Python's request and response shapes:

- `/v1/tokenize` takes `prompt` (a string or a list of strings) or chat `messages`, and `add_special_tokens` (default true). It returns `tokens`, `count` and `max_model_len`. Messages render through the chat template and encode without auto-added specials, as on the chat path.
- `/v1/detokenize` takes `tokens` (a list, or a list of lists) and `skip_special_tokens` (default true), and returns `text`.
- Errors use Python's flat `ErrorResponse` body. A malformed body, or both or neither of `prompt` and `messages`, is a 400 of type `Bad Request`. A rejected input is a 400 `BadRequestError`; other failures are a 500 `InternalServerError`.

How it is wired:

- Encoding runs on the tokenizer pool as a new `RequestKind::Tokenize`, which the pool answers through the request's own sink with a `ResponseItem::TokenIds`; intake does not register it with a detok shard.
- Decoding reuses the detok shards' `RequestKind::Detokenize`, which now carries `skip_special_tokens`. The `/v1/completions` echo path still decodes with it set.
- `max_model_len` is the Python tokenizer's `model_max_length`, or the context length when that is not a 64-bit integer, derived at launch the way `OpenAIServingTokenize` derives it (the `getattr` mirrors that code; the tokenizer is `None` under `skip_tokenizer_init`) and stamped into the Rust `ServerArgs` as `tokenizer_model_max_length`.
- A dropped tokenize or detokenize call (client gone, or `try_join_all` dropping the rest of a list after one failure) releases only its Rust-side state through a new `AbortSource::Local`. It never reached the scheduler, so it queues no scheduler `AbortReq`; otherwise a cancelled list of thousands of prompts would push thousands of aborts ahead of generation requests.
- `ChatRequest` in `openai/chat.rs` becomes `pub(super)` so the tokenize route can render `messages` with the same parser; its PD routing fields are accepted and ignored there.

Differences from Python, on purpose:

- Negative token ids are a 400 here (validated before decoding); Python fails inside the tokenizer with a 500.
- Media in `messages` is rejected, as on the Rust chat route.

This PR is independent of #44533 and #44532: it touches neighbouring lines of `ServerArgs` and `rust_server/config.py` but shares no hunk with either.
