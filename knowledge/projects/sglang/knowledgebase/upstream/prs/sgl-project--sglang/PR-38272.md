# [Intel GPU] Add opt-in decode graph capture widths for DSV4 on XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/38272) · state: open · merged: False

## Original PR description

## Motivation

- The DSV4 indexer sizes its paged gather and logits buffer from `MAX_SEQ_LEN_FOR_CAPTURE`. On `intel_dev` that is the full configured context. At `--context-length 262144 --page-size 256` it is 262148, because the pool adds padding (`deepseek_v4_backend.py:558`).
- Graph capture freezes that width. So a short conversation does full-context indexer work on every decode step.
- CUDA has the same cost: #40441 measured 2.68x faster per-request decode at `--context-length 131072` than at 1048576 (8x H200, DeepSeek-V4.1-Flash with DSpark).

## Modifications

- **Opt-in widths, XPU only.** `SGLANG_DSV4_DECODE_GRAPH_SEQ_LENS` (default empty, so off) lists narrower capture widths. On a device other than XPU, a non-empty value raises an error (`deepseek_v4_backend.py:509`).
- **One graph per width.** The backend advertises the widths and always appends the full context as the last width. The runner captures one graph per width and replays the smallest width that fits the batch. The graph key carries the width. The shared runner code names no backend.
- **Bad combinations fail at startup.** `validate_deepseek_v4_decode_graph_widths` (`deepseek_v4_hook.py:198`) rejects the variable together with any of these:
  - speculative decoding (`speculative_algorithm`)
  - diffusion decoding (`dllm_algorithm`)
  - two-batch overlap (`enable_two_batch_overlap`)
  - PDMux (`enable_pdmux`)
  - a decode graph backend other than `full`
- **Eager forward passes use the full context.** A narrowed width belongs to a graph replay only. Since 2340f8c401, eager decode metadata uses the full context (`deepseek_v4_backend.py:1465`). At 3c0dbe0052, it could use the width of the last replay. Then a long eager batch would lose its trailing pages.
- **Off means unchanged.** With the variable unset, the runner captures one graph per batch size, with the same graph keys as before. `AttentionBackend` and `DecodeCudaGraphRunner` carry class-level `None` defaults. So the draft runners that skip `super().__init__()` still work.
- **The XPU gate stays.** I did not measure this code on CUDA. I think a device-neutral version belongs on `main`, based on #38993.

## Limits

- I found the eager-path defect by reading the code. No device run checked the fix.
- I measured this PR's code at 1024 in / 1024 out only. The gain should shrink as prompts grow toward the full context.
- I want a second opinion on one point. `can_run_graph` builds its graph key with the width label of the previous replay (`decode_cuda_graph_runner.py:526`). I found no wrong replay, because capture records every batch size x width combination.
- CI does not run on this PR, for three reasons:
  - The PR has no `run-ci` label.
  - The XPU lane runs only for pull requests to `main`.

Thanks all for the comments!

**@jianan-gu on scope.** Agreed this should not stay XPU-only, and I do not have evidence that CUDA is unaffected. The mechanism is shared code: `MAX_SEQ_LEN_FOR_CAPTURE` feeds `make_core_attn_metadata(max_seq_len=...)` and on into `BuildPageTablePositions.execute(...)`, which sizes the page-table and paged-gather buffers, and capture then freezes that width for every replay. Nothing in that chain is XPU-specific.

The plumbing is already backend-neutral: the lines this PR adds to `decode_cuda_graph_runner.py` carry no XPU, DSV4 or DeepSeek reference, and a backend opts in purely by advertising `decode_graph_widths`. The restriction is one guard, at `deepseek_v4_backend.py:508`. So the gate reflects where I could measure — +13.4% tok/s/user and 11.8% lower ITL at 1024/1024, concurrency 1, on 8xB70 — rather than a claim about CUDA. I will try to run the same A/B test on Nvidia GPU(s). If the effect reproduces I would rather relax that guard in this PR than leave it as a follow-up; if it does not, the gate stays and I will say so here either way. If anyone already has a box free and gets there first, I am glad to take their numbers instead.

**@CaoE and @unrahul on memory.** The KV half is settled in source, and @unrahul's reading matches mine with one addition: `post_capture_kv_sizing_planned()` returns False three separate ways for this configuration — `device != "cuda"`, MLA enabled, and `is_deepseek_v4(hf_config)`. So the KV budget is sized from free memory and `mem_fraction_static` before capture with no graph term, and `max_total_num_tokens` cannot move.

The capture-headroom half is a fair question. `reserve_for_graph_mb()` adds `max_bs * 2` MB with no width term, so the reserve stays flat while graph count multiplies by the number of widths. The one thing that softens it is that the added graphs are the narrow ones, whose page-table and logits buffers are smaller than the full-context graph already being captured, so the marginal cost per width sits below the existing one rather than equal to it. That is reasoning, not a number.

**Two things I will do.**

1. @unrahul's three-arm experiment: one image, one source tree, identical arguments, changing only the variable — unset, then `8192,32768`, then `8192,32768,65536` — reporting `max_total_num_tokens`, capture wall time and peak memory during capture for each arm. I will post the table here.

2. @CaoE's coverage point, which is a real gap rather than a covered one. The current tests pin the pure helpers with the feature off: the resolver returns `()` for an empty configuration, and `_compose_graph_width_variant("lora", None, 8192)` returns `"lora"` unchanged. What is missing is the runner itself with a backend that advertises nothing — that `capture_widths` collapses to `(None,)`, that `_make_graph_key` is identical to before, and that `can_run_graph` never consults the new check. - inteljerry · COMMENTED · 2026-09-11T06:16:43Z · [source](https://github.com/sgl-project/sglang/pull/38272#pullrequestreview-5175232407)

Experiment results are summarized below, including follow-ups for the two failure modes @CaoE raised: graph capture failing, and runtime OOM on workloads whose activation memory peaks near the limit. 
25 server launches on 8x Arc Pro B70, TP8. Same image, same source tree, same arguments, with `SGLANG_DSV4_DECODE_GRAPH_SEQ_LENS` as the only variable. Arms were run round-robin instead of one block per arm, so any drift over the hour is spread across all three.

Configuration: `--page-size 256 --context-length 262144 --mem-fraction-static 0.85 --max-running-requests 8 --chunked-prefill-size 8192 --max-prefill-tokens 16384 --attention-backend dsv4 --kv-cache-dtype fp8_e4m3`, decode graphs full at `bs=[1,2,4,8]`, prefill graphs disabled. `--max-total-tokens` is intentionally not passed, so the token budget is derived from free memory and can move between arms.

### @unrahul: the three experiments

3 repeats per arm, mean (min-max):

| metric | unset (4 graphs) | `8192,32768` (12) | `8192,32768,65536` (16) |
|---|---|---|---|
| `max_total_num_tokens` | 518912 (518656-519168) | 518827 (518656-519168) | 518997 (518656-519168) |
| capture elapsed, TP0 | 19.64 s (19.35-19.95) | 23.26 s (23.08-23.61) | 24.84 s (24.71-25.06) |
| capture retained, TP0 | 2.26 GB | 2.27 GB | 2.27 GB |
| capture retained, TP1-7 | 0.74 GB | 0.75 GB | 0.75 GB |
| free after capture, TP0 | 2.09 GB | 2.08 GB | 2.08 GB |
| time to ready | 100 s | 105 s | 108 s |

`max_total_num_tokens` covers the same range in all three arms and the means are non-monotonic in graph count, so there is no arm effect above a one-page (256 token) jitter.

TP0 is quoted throughout because it is the binding rank: it retains roughly 3x what TP1-7 do (2.26 vs 0.74 GB). An 8-rank average would report 0.93 GB and understate the worst rank by 2.4x.

Resolved ladders, taken from each arm's own log: `(8192, 32768, 262148)` and `(8192, 32768, 65536, 262148)`.

### Establishing a slope for the memory cost

The memory deltas above sit at the log's resolution. `mem usage` prints GB to two decimals, so 0.01 GB is one least-significant digit, and at 12 and 16 graphs that is the entire delta. Three points at the resolution floor do not determine a slope, so longer ladders were captured:

| widths | graphs | retained TP0 | capture elapsed |
|---|---|---|---|
| 1 | 4 | 2.26 GB | 20.01 s |
| 4 | 16 | 2.27 GB | 24.84 s |
| 6 | 24 | 2.28 GB | 29.19 s |
| 7 | 28 | 2.29 GB | 30.08 s |

That is 0.03 GB across six added widths, or approximately **5 MB of retained device memory per added width, per rank**. Capture time is 10.1 s across 24 added graphs, or **0.42 s per added graph**, which agrees with the marginals computed independently from the three-arm table above (0.45 and 0.40 s/graph).

For scale, the 4-graph baseline retains 2.26 GB on TP0, so each additional rung adds roughly 0.2% on top of it.

### @CaoE: can graph capture fail?
Capture failure is determined by the peak, so the cliff was measured directly by raising `--mem-fraction-static` until capture breaks:

| `mem_fraction_static` | `max_total_num_tokens` | free at capture begin | unset | 4 rungs |
|---|---|---|---|---|
| 0.85 | ~518,000 | 4.53 GB | ready | ready |
| 0.89 | ~686,000 | 3.31 GB | ready | ready |
| 0.93 | ~854,000 | 2.09 GB | ready, 0.02 GB free after | ready, 0.02 GB free after |

At 0.93 the binding rank completes capture with 20 MB remaining, and the 4-rung ladder survives the same point. It retained slightly less there than the baseline (1.89 vs 1.90 GB) and obtained marginally more KV tokens (854,528 vs 853,760), so the difference is below run-to-run variation even at the edge.

The pool appears to size itself against available memory instead of requesting a fixed amount: TP0 retained 2.26 GB at 0.85 but 1.90 GB at 0.93 for the same four graphs. Additional graphs are absorbed into the same budget, and the cost surfaces as capture time.

### @CaoE: can activation peaks cause a runtime OOM?

Concurrency 8 (= `max_running_requests`), 8000-token inputs, sampling all eight devices for the duration of the run:

| arm | peak device memory | peak util | min free | tok/s/user |
|---|---|---|---|---|
| unset | 32655 MiB | 100.0% | 3 MiB | 17.67 |
| `8192,32768` | 32655 MiB | 100.0% | 3 MiB | 25.17 |
| `8192,32768,65536` | 32655 MiB | 100.0% | 3 MiB | 25.31 |

The peak is identical across all three arms, and the arm with the feature disabled already reaches 100%. The KV pool is sized from free memory so that it fills the device, so 100% is the expected steady state here and not a consequence of this change.

One limit on that measurement: at 100% with 3 MiB free it cannot resolve a 5-30 MB difference. It establishes that the ladder does not raise the peak. It cannot determine whether it consumes a small amount of slack, because no arm has any.

The activation ceiling in this configuration is set by `chunked_prefill_size` and `max_prefill_tokens`, and prefill graphs are disabled so prefill runs eagerly against those caps. This PR modifies neither, so the ladder shifts the floor by its retained cost and leaves the peak unchanged.



On lowering `mem_fraction_static` as a workaround: it does not appear necessary at this scale, since the configuration that barely survives with the feature disabled survives equally with four rungs. That holds for the shape measured here and should not be extrapolated further. If there is a specific memory-constrained configuration worth testing, the harness takes an argument list and the runs are inexpensive.

- CaoE · comment · 2026-09-08T08:47:41Z · [source](https://github.com/sgl-project/sglang/pull/38272#issuecomment-5582045835)

One concern is the memory overhead introduced by adding multiple context-width variants. Since the full-context graph is still captured, configuring additional widths adds more graphs rather than replacing the original one. Because graph count scales roughly with batch_size × width_variants × other variants, this could increase both capture time and persistent device memory usage.

On memory-constrained devices, could this reduce the available KV-cache capacity, max_total_num_tokens, or max_running_requests, or even cause graph capture to fail with OOM? The PR reports decode performance improvements, but it would be helpful to include measurements of the additional memory usage and its impact on maximum context capacity and concurrency, comparing the default configuration with one or more width configurations.

Although the new logic is intended to be inactive when decode_graph_widths is unset, do we need to add regression coverage to verify that the existing capture and replay behavior remains unchanged for backends that do not advertise width variants ?

- CaoE · comment · 2026-09-09T08:24:13Z · [source](https://github.com/sgl-project/sglang/pull/38272#issuecomment-5598728551)

@inteljerry I think we may be discussing two different effects. I agree that max_total_num_tokens, mem_fraction_static, and the KV-cache allocation remain unchanged for this configuration. My concern is that the additional width-specific graphs still consume device memory themselves.

Therefore, even if the default configuration fits within the existing KV and static-memory budget, adding more graphs may reduce the remaining headroom for activations and other runtime work. This could potentially cause XPU graph capture to fail, or lead to runtime OOMs for workloads whose activation memory peaks near the limit.

In that case, users might need to lower `mem_fraction_static` to leave more device-memory headroom for graph allocations and runtime workspaces, at the cost of reducing KV-cache capacity.
