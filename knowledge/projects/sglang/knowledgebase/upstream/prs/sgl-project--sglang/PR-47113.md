# [Fix] rust-server: Fix the metrics flush race and the default-priority label

[Upstream PR](https://github.com/sgl-project/sglang/pull/47113) · state: closed · merged: True

## Original PR description

Stacked on #47108: this branch is based on `oss-sync-3af1aca65b`, and the new test's `CoreConfig` fixture uses the `multimodal` field that pull request adds. Only the last commit is this change.

## Motivation

Two small bugs in the Rust frontend's request metrics.

1. **Flush race.** `FrontendMetrics::flush()` snapshotted every counter and histogram family before taking the `written` lock. A `/metrics` scrape flushes too, so it could race the periodic flusher: the flush holding the older snapshot could take the lock second and write it over the newer multiprocess file, and a scrape would then see counters go down as if they had reset.
2. **Default-priority label.** `CoreHandle` picked a request's metrics label series before scheduler intake applied `--default-priority-value`. With `--enable-priority-scheduling`, a request that sent no priority was scheduled at the default but counted under `priority=""`, while an explicit request at the same priority was counted under `priority="<n>"`. The Python frontend does not have this split: `_set_default_priority` runs at the top of `generate_request`, before `collect_metrics` reads the priority.

## Modifications

- `core/metrics.rs`: `flush()` takes the `written` lock before the snapshot and holds it through the write, so two concurrent flushes cannot write an older snapshot over a newer one.
- `handlers/handle.rs`: `CoreMetadata` carries `default_priority` from `ServerArgs::default_priority_value`.
- `handlers/generate.rs`: `CoreHandle` applies it to a request with no priority in `generate`, `generate_internal` and `generate_batch`, i.e. for single, internal and batch generations, before the metrics series is picked.
- `tokenizer_manager/to_scheduler_validation.rs`, `to_scheduler_types.rs`, `to_scheduler_tests.rs`: the intake-side copy of the default is removed, with its `Limits::default_priority` field and the `unset_priority_takes_the_default` test. Every generation reaches intake through `CoreHandle`, so the priority the scheduler sees is unchanged.
- New test `unset_priority_takes_the_default_before_metrics` in `handlers/generate.rs`: sends a generation without a priority through `CoreHandle` with metrics on and a default of 5, and checks both the priority handed to intake and the `priority="5"` label on `sglang:num_requests_total`. It fails without the fix.

Out of scope: there is no test for the flush race itself. Making it deterministic would need hooks inside `flush()`, and a sleep-based test would be flaky.
