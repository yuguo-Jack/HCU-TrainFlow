# [NVIDIA][MegaMoE] Use persistent top-k reduce to eliminate decode latency overhead

[Upstream PR](https://github.com/sgl-project/sglang/pull/39832) · state: open · merged: False

## Original PR description

## Motivation

In MegaMoE decode, the separate CuTe-DSL top-k reduce launches a static grid sized from the workspace capacity. A 256-token decode step therefore pays for the full-capacity launch. FlashInfer https://github.com/flashinfer-ai/flashinfer/pull/5666 adds a persistent finalize mode that reads the live token count from device memory, so the reducer scales with the actual batch.

## Modifications

- **Persistent finalize:** The NVFP4 and MXFP8 MegaMoE configs request `FinalizeMode.AUTO` and pass a `num_valid_tokens_tensor`.
  - `AUTO` keeps FlashInfer's CAKE reducer eligible where it supports the problem, and otherwise uses the persistent finalize that reads the tensor. Forcing `PERSISTENT` displaced CAKE on hidden=4096/top_k=6 at capacities 256 and 4096.
  - `DeepGemmMegaMoeConfig` is untouched.
- **Shared tensor:** One int32 `(1,)` CUDA tensor is shared by all layers (`get_buffer`, created at layer build, outside CUDA graph capture). FlashInfer pools workspaces keyed on this tensor's identity, so every layer must hold the same object. The layer stores it, and it reaches `run_flashinfer_megamoe` through the new `FlashInferMegaMoeQuantInfo.num_valid_tokens` field. Nothing reads FlashInfer's private `_megakernel_config`.
- **Per-forward refresh:** The tensor is filled with `x.shape[0]` before a MegaMoE launch. `DeepseekV4Model.forward` enters `megamoe_forward_scope()`, which keeps the row count last written in a per-forward flag, so the layers of one forward with the same row count share a single fill. The flag is reset when the scope exits and keyed on the row count, so a CUDA graph replay between two forwards, or two overlapped sub-batches of different sizes, cannot leave the kernel a stale count. Outside a scope (every other model) each call still fills. Inside a CUDA graph the fill is a captured node that replays the value baked for that capture shape (the padded row count, not the true token count); with the scope the capture holds one fill, at the first MoE layer.
- **Rename:** `apply_topk_in_fc1` becomes `apply_routing_weights_before_fc2` (the [#5666](https://github.com/flashinfer-ai/flashinfer/pull/5666) name).
- **Env var:** `SGLANG_FLASHINFER_MEGAMOE_TOPK_REDUCE_PERSISTENT` (default `True`; `0` restores the static reducer). It is documented in `environment_variables.mdx`.
- **Autotune:** `MegaMoeTunedForward._geometry_key` now serializes enum config values by name. Without this, startup autotune fails on the `FinalizeMode` enum. `_valid_native_cache` now compares the cache `version` with FlashInfer's `KNOB_CACHE_VERSION` instead of a hard-coded 1: FlashInfer `main` writes version 2, so a successful tune was rejected as "did not record its selected tactic".

## Dependency and compatibility

This requires FlashInfer https://github.com/flashinfer-ai/flashinfer/pull/5666 (`FinalizeMode`, `num_valid_tokens_tensor`, `apply_routing_weights_before_fc2`). Older wheels, including the pinned 0.7.2, fail at layer build with `ImportError` or `TypeError`. No released FlashInfer wheel includes it yet (`v0.7.2` and `v0.7.2.post1` do not), so this PR cannot merge until a FlashInfer release includes https://github.com/flashinfer-ai/flashinfer/pull/5666 and the pin is bumped. There is no fallback for older wheels.

On `main`, the MegaMoE decode path (dp-attention plus `flashinfer_megamoe`) failed at decode CUDA graph capture with `transport finalize owes an undeclared sum group` (https://github.com/sgl-project/sglang/issues/46316), independent of this PR. The fix, https://github.com/sgl-project/sglang/pull/46365, is merged and included in this branch.

## Results

DeepSeek-V4-Flash-NVFP4, 4x GB200, TP4 + DP4 with dp-attention, `--moe-runner-backend flashinfer_megamoe --moe-a2a-backend flashinfer_megamoe`. This is a deliberately MegaMoE-specific setup, not the cookbook default (`flashinfer_trtllm_routed`, TP8), so these numbers describe the MegaMoE path only.

Measured on this branch at `81cc57d009` (merged with `main` at `638374c389`) with the fix from https://github.com/sgl-project/sglang/pull/46365 applied as an uncommitted local patch, FlashInfer `main` at `27c62fdf0` (includes #5666), `SGLANG_FLASHINFER_MEGAMOE_MAX_TOKENS_PER_RANK=2048`. "OFF" is `SGLANG_FLASHINFER_MEGAMOE_TOPK_REDUCE_PERSISTENT=0`.

**Benchmark** (`sglang.bench_serving`, random 1024 in / 1024 out, 1024 prompts, request rate inf, max concurrency 8192, seed 43; one warm-up run, then one measured run per mode):

| | OFF (static reducer) | ON (this PR) | Change |
|---|---|---|---|
| Total token throughput (tok/s) | 19749.07 | 19975.48 | +1.1% |
| Benchmark duration (s) | 52.10 | 51.51 | -1.1% |
| Mean TPOT (ms) | 117.98 | 114.84 | -2.7% |
| Median TPOT (ms) | 65.23 | 63.28 | -3.0% |
| Mean ITL (ms) | 60.91 | 59.48 | -2.3% |
| P99 ITL (ms) | 108.76 | 103.00 | -5.3% |
| Mean TTFT (ms) | 8383.94 | 8407.91 | +0.3% |
| Max ITL (ms) | 14420.97 | 14575.84 | +1.1% |

These are single runs and the differences are small; treat them as directional, not as a measured speedup.

**Trace** (torch profiler, TP0, 10 decode steps in steady state, 430 MegaMoE launches = 43 layers x 10 steps). The window is at about 120 to 250 running requests per DP rank, and the same in both modes because the seed and the trigger are the same.

| | top-k reduce kernel | median | MegaMoE main kernel (median) |
|---|---|---|---|
| OFF | `reduce_static_..._TopkReduce` | 10.3 us | 187.1 us |
| ON | `reduce_persistent_..._TopkReduce` | 3.9 us | 187.1 us |

- With `FinalizeMode.AUTO`, FlashInfer used the persistent finalize here; no CAKE reducer kernel appears in the trace.
- The saving is about 6.4 us per layer per step, roughly 0.28 ms per decode step over 43 MoE layers. The main kernel does not get slower.
- An earlier measurement of this PR on an older FlashInfer build had the static reducer at 24.0 us. I have not isolated why it is faster now, so the saving is smaller than first reported.
- Once-per-forward fill (`76aa5082c2`), same setup on this branch's head after merging `main` (which includes #46365): the extra `FillFunctor` kernels in the 10-step window went from 430 (one per layer per step) to 10 (one per step). The reducer is unchanged (`reduce_persistent`, 3.8 us) and GSM8K is 0.980 (400 questions, single run). End-to-end throughput stays within single-run noise.
- Every measurement above uses `--disable-flashinfer-autotune`. With startup autotune on (4x GB200, DeepSeek-V4-Flash-NVFP4 with dummy weights, FlashInfer `main`), `RuntimeError: MegaMoE autotune did not record its selected tactic` was the version mismatch above, and it failed the same way with the persistent finalize on and off. With the fix all 12 capacities (1 to 2048) tune, but the server still does not come up: after the first MegaMoE forward it has 3.5 GB free, against 6.4 GB with autotune disabled (where it comes up), and the indexer warmup then fails with `torch.OutOfMemoryError` (a 2 GiB allocation). The extra 2.9 GB is taken during the per-capacity tuning: device free memory drops by 0.05 GB at capacity 16 up to 0.78 GB at 2048, while PyTorch's allocator grows by only 1.4 GB in total, so most of it is outside torch's allocator. I have not found what holds it, and I did not run real weights. `main` at `638374c389` without this PR and the FlashInfer 0.7.2 wheel fails earlier in the startup autotune with `ValueError: compute(output=None) is incompatible with knobs='auto'`. Which reducer runs with autotune enabled is not measured.

## Tests

- every layer receives the same tensor object;
- an env-off run requests nothing;
- the tensor the quant info holds is refreshed on every call outside a forward scope;
- inside a forward scope, layers with the same row count share one fill, and nothing carries over to the next forward;
- the autotune key serializes the enum. This test fails without the fix;

## Validation on FlashInfer #5666 (DeepSeek-V4-Flash-NVFP4, MegaMoE)

  I rebased this branch onto `main` (`ff3f8c348c`) and validated it against FlashInfer #5666 (`1181a77eb`, built from source
  as 0.7.2). The branch now adapts to the #5666 API: `use_persistent_finalize_kernel` plus a shared
  `num_valid_tokens_tensor`, and `apply_routing_weights_before_fc2`.

  **Setup**
  - DeepSeek-V4-Flash-NVFP4, 4x GB200, TP4 + DP4 with dp-attention, `--moe-runner-backend flashinfer_megamoe
  --moe-a2a-backend flashinfer_megamoe`
  - Workload: random, 1024 in / 1024 out, 1024 prompts, `--request-rate inf`, `--max-concurrency 8192`
  - Torch profiler, 10 decode steps in steady state (~170-180 running requests per DP rank, CUDA graph), 43 MoE layers, all
  4 ranks agree
  - The only thing changed between runs is the env var: `SGLANG_FLASHINFER_MEGAMOE_TOPK_REDUCE_PERSISTENT=0/1` and
  `SGLANG_FLASHINFER_MEGAMOE_IN_KERNEL_FC2_REDUCE=1`

  ### 1. Kernel time per MoE layer per decode step (median, from the torch trace)

  | Mode | MegaMoE main kernel | Top-k reduce kernel | Total per layer | Reduce kernel in trace |
  |---|---|---|---|---|
  | Persistent OFF (static `TopkReduce`) | 222.1 us | 24.0 us | 246.1 us | `reduce_static_..._topk_reduce` |
  | **Persistent ON (this PR, default)** | 221.6 us | **3.8 us** | **225.4 us** | `reduce_persistent_..._topk_reduce` |
  | In-kernel fc2 reduce | 220.6 us | none | 220.6 us | none (0 reduce-like kernels) |

  - The reduce kernel is ~6.3x faster with the persistent kernel (24.0 -> 3.8 us). This saves ~20.7 us per layer per step,
  i.e. ~0.89 ms per decode step over 43 layers.
  - The MegaMoE main kernel time is unchanged (222.1 vs 221.6 us), so the saving comes only from the reducer.
  - The static reducer sizes its grid from the workspace capacity, so a ~170-token decode batch pays the full-capacity
  launch. The persistent kernel reads the live token count from device memory. In prefill steps the same persistent kernel
  averaged ~22 us, so it does scale with the token count.
  - The persistent flag has no effect when `IN_KERNEL_FC2_REDUCE=1`; no persistent kernel shows up in that trace, which
  matches FlashInfer's `not in_kernel_fc2_reduce` condition.

  ### 2. Accuracy: GSM8K, 400 questions (`sglang.test.run_eval`, default settings)

  | Mode | Score | Std. err. | Diff vs. persistent OFF |
  |---|---|---|---|
  | Persistent OFF | 0.9725 | 0.0082 | - |
  | **Persistent ON (this PR)** | 0.9700 | 0.0085 | -0.25 pp (0.2 sigma) |
  | In-kernel fc2 reduce | 0.9775 | 0.0074 | +0.50 pp (0.45 sigma) |

  No accuracy difference is detected between modes (all differences are well within the noise).

  ### Notes and limitations
  - One run per mode, 10 profiled decode steps each. The kernel-level numbers are consistent across ranks; I am not claiming
  an end-to-end throughput number from these runs (differences there are within run-to-run noise).
  - Batch size here is ~170-180 requests per rank, smaller than the ~329 tokens/rank in the original description, so the
  absolute saving may differ at larger batch.
  - In-kernel fc2 reduce is documented by FlashInfer as having non-deterministic accumulation order; only GSM8K was checked
  for it.
  - Only the NVFP4 MoE path was exercised here (MXFP8 and DeepGemm paths were not run). `DeepGemmMegaMoeConfig` is left
  unchanged.
  - This is the experimental MegaMoE path, not the cookbook default for this checkpoint (`flashinfer_trtllm_routed`).
  - This PR now requires a FlashInfer build with #5666 (older wheels do not have the new fields). I'll keep it as Draft
  until #5666 is merged/released.
  - Startup log (`max_total_num_tokens`, `available_gpu_mem`) is identical across the three modes, so I do not see a memory
  difference from in-kernel reduce in this setup.

Done in 76aa5082c2. The fill now happens once per forward for DeepSeek-V4: `DeepseekV4Model.forward` enters `megamoe_forward_scope()` (next to `mega_gate_forward_scope`), which keeps the row count last written to the shared tensor in a per-forward flag, and layers with the same row count skip the fill. I did not cache the previous value across forwards: a CUDA graph replay overwrites the tensor with the count baked at capture time, so a host-side cache could skip a fill that the next eager forward needs. The flag is reset when the scope exits and keyed on the row count, so overlapped sub-batches of different sizes still refill. A unit test covers the stale-across-forwards case.

CUDA graphs: the fill takes a Python int, so in a capture it is baked into the graph node with the (padded) capture batch size and re-executed on each replay. With this change the capture holds one fill, at the first MoE layer.

Measured on 4xGB200 (TP0, 10 decode steps, 43 MoE layers): the extra FillFunctor kernels went from 430 to 10, the reducer is still `reduce_persistent` at 3.8 us, GSM8K (400, legacy run_eval) is 0.980. End-to-end throughput is within single-run noise, as expected for about 40 us per step.
