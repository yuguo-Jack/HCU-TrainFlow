# [NVIDIA][MegaMoE] Use persistent top-k reduce to eliminate decode latency overhead

[Upstream PR](https://github.com/sgl-project/sglang/pull/39832) · state: open · merged: False

## Original PR description

## Motivation

In MegaMoE decode, the separate CuTe-DSL top-k reduce launches a static grid sized from the workspace capacity. A 256-token decode step therefore pays for the full-capacity launch. FlashInfer #5666 adds a persistent finalize mode that reads the live token count from device memory, so the reducer scales with the actual batch.

## Modifications

- **Persistent finalize:** The NVFP4 and MXFP8 MegaMoE configs request `FinalizeMode.PERSISTENT` and pass a `num_valid_tokens_tensor`.
  - The mode is explicit because `AUTO` would pick FlashInfer's CAKE reducer wherever it supports the problem.
  - `DeepGemmMegaMoeConfig` is untouched.
- **Shared tensor:** One int32 `(1,)` CUDA tensor is shared by all layers (`get_buffer`, created at layer build, outside CUDA graph capture). FlashInfer pools workspaces keyed on this tensor's identity, so every layer must hold the same object. The layer stores it, and it reaches `run_flashinfer_megamoe` through the new `FlashInferMegaMoeQuantInfo.num_valid_tokens` field. Nothing reads FlashInfer's private `_megakernel_config`.
- **Per-call refresh:** Before each MegaMoE launch the tensor is filled with `x.shape[0]`. Inside a CUDA graph that fill is a captured node that replays the value baked for that capture shape. This is the padded row count, not the true token count.
- **Rename:** `apply_topk_in_fc1` becomes `apply_routing_weights_before_fc2` (the #5666 name).
- **Env var:** `SGLANG_FLASHINFER_MEGAMOE_TOPK_REDUCE_PERSISTENT` (default `True`; `0` restores the static reducer). It is documented in `environment_variables.mdx`.
- **Autotune:** `MegaMoeTunedForward._geometry_key` now serializes enum config values by name. Without this, startup autotune fails on the `FinalizeMode` enum.

## Dependency and compatibility

This requires FlashInfer #5666 (`FinalizeMode`, `num_valid_tokens_tensor`, `apply_routing_weights_before_fc2`). Older wheels, including the pinned 0.7.1, fail at layer build with `ImportError` or `TypeError`. The PR stays **Draft** until a FlashInfer release includes #5666 and the pin is bumped. There is no fallback for older wheels.

## Results

DeepSeek-V4-Flash-NVFP4, 4x GB200, TP4 + DP4 with dp-attention, `--moe-runner-backend flashinfer_megamoe`. This is a deliberately MegaMoE-specific setup, not the cookbook default (`flashinfer_trtllm_routed`, TP8), so these numbers describe the MegaMoE path only.

Decode steady state, 10-step windows, about 170-180 running requests per DP rank, 4 ranks agree, single run per mode:

| mode | MegaMoE main kernel (median) | top-k reduce (median) | per layer per step | GSM8K (400) |
|---|---|---|---|---|
| persistent OFF (static reducer) | 222.1 us | 24.0 us | 246.1 us | 0.9725 (SE 0.0082) |
| persistent ON (this PR) | 221.6 us | 3.8 us | 225.4 us | 0.9700 (SE 0.0085) |
| in-kernel FC2 reduce (not part of this PR) | 220.6 us | none | 220.6 us | 0.9775 (SE 0.0074) |

- Persistent saves about 20.7 us per layer per step, roughly 0.89 ms per decode step over 43 MoE layers. The main kernel does not get slower.
- GSM8K differences are under 0.7 sigma, so no accuracy difference was detected.
- End-to-end throughput in these runs (10312 vs 10112 tok/s) is single-run and within noise, so it is not claimed as a result.

## Tests

`pytest test/registered/unit/layers/moe/test_flashinfer_megamoe.py`: 19 passed. The tests cover:
- every layer receives the same tensor object;
- an env-off run requests nothing;
- the tensor the quant info holds is refreshed on every call;
- the autotune key serializes the enum. This test fails without the fix.

All FlashInfer classes in these tests are fakes.

## Validation on FlashInfer #5666 (DeepSeek-V4-Flash-NVFP4, MegaMoE)

  I rebased this branch onto `main` (`ff3f8c348c`) and validated it against FlashInfer #5666 (`1181a77eb`, built from source
  as 0.7.2). The branch now adapts to the #5666 API: `use_persistent_finalize_kernel` plus a shared
  `num_valid_tokens_tensor`, and `apply_routing_weights_before_fc2`.

  **Setup**
  - DeepSeek-V4-Flash-NVFP4, 4x GB200, TP4 + DP4 with dp-attention, `--moe-runner-backend flashinfer_megamoe
  --moe-a2a-backend flashinfer_megamoe`
  - Workload: random, 1024 in / 1024 out, 1024 prompts, `--request-rate inf`, `--max-concurrency 8192`
  - Torch profiler, 10 decode steps in steady state (~170-180 running requests per DP rank, CUDA graph), 43 MoE layers, all
  4 ranks agree
  - The only thing changed between runs is the env var: `SGLANG_FLASHINFER_MEGAMOE_TOPK_REDUCE_PERSISTENT=0/1` and
  `SGLANG_FLASHINFER_MEGAMOE_IN_KERNEL_FC2_REDUCE=1`

  ### 1. Kernel time per MoE layer per decode step (median, from the torch trace)

  | Mode | MegaMoE main kernel | Top-k reduce kernel | Total per layer | Reduce kernel in trace |
  |---|---|---|---|---|
  | Persistent OFF (static `TopkReduce`) | 222.1 us | 24.0 us | 246.1 us | `reduce_static_..._topk_reduce` |
  | **Persistent ON (this PR, default)** | 221.6 us | **3.8 us** | **225.4 us** | `reduce_persistent_..._topk_reduce` |
  | In-kernel fc2 reduce | 220.6 us | none | 220.6 us | none (0 reduce-like kernels) |

  - The reduce kernel is ~6.3x faster with the persistent kernel (24.0 -> 3.8 us). This saves ~20.7 us per layer per step,
  i.e. ~0.89 ms per decode step over 43 layers.
  - The MegaMoE main kernel time is unchanged (222.1 vs 221.6 us), so the saving comes only from the reducer.
  - The static reducer sizes its grid from the workspace capacity, so a ~170-token decode batch pays the full-capacity
  launch. The persistent kernel reads the live token count from device memory. In prefill steps the same persistent kernel
  averaged ~22 us, so it does scale with the token count.
  - The persistent flag has no effect when `IN_KERNEL_FC2_REDUCE=1`; no persistent kernel shows up in that trace, which
  matches FlashInfer's `not in_kernel_fc2_reduce` condition.

  ### 2. Accuracy: GSM8K, 400 questions (`sglang.test.run_eval`, default settings)

  | Mode | Score | Std. err. | Diff vs. persistent OFF |
  |---|---|---|---|
  | Persistent OFF | 0.9725 | 0.0082 | - |
  | **Persistent ON (this PR)** | 0.9700 | 0.0085 | -0.25 pp (0.2 sigma) |
  | In-kernel fc2 reduce | 0.9775 | 0.0074 | +0.50 pp (0.45 sigma) |

  No accuracy difference is detected between modes (all differences are well within the noise).

  ### Notes and limitations
  - One run per mode, 10 profiled decode steps each. The kernel-level numbers are consistent across ranks; I am not claiming
  an end-to-end throughput number from these runs (differences there are within run-to-run noise).
  - Batch size here is ~170-180 requests per rank, smaller than the ~329 tokens/rank in the original description, so the
  absolute saving may differ at larger batch.
  - In-kernel fc2 reduce is documented by FlashInfer as having non-deterministic accumulation order; only GSM8K was checked
  for it.
  - Only the NVFP4 MoE path was exercised here (MXFP8 and DeepGemm paths were not run). `DeepGemmMegaMoeConfig` is left
  unchanged.
  - This is the experimental MegaMoE path, not the cookbook default for this checkpoint (`flashinfer_trtllm_routed`).
  - This PR now requires a FlashInfer build with #5666 (older wheels do not have the new fields). I'll keep it as Draft
  until #5666 is merged/released.
  - Startup log (`max_total_num_tokens`, `available_gpu_mem`) is identical across the three modes, so I do not see a memory
  difference from in-kernel reduce in this setup.
