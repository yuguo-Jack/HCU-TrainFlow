# [Feat] qwen4: --ple-offload-token-embedding keeps embed_tokens in host memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/48252) · state: open · merged: False

## Original PR description

## Motivation

On a single 96 GB RTX PRO 6000, `nvidia/Qwen3.8-Flash-Next-NVFP4` leaves only a few GB for the KV cache once its weights are resident, so serving is KV-bound. That holds even with `--ple-offload-embedding` moving the 47.7 GiB PLE n-gram table to host memory (the cookbook cells run 78k–170k-token pools). The token embedding (`embed_tokens`, 248,320 x 2,560 BF16 = 1.27 GB) still sits on the GPU. It is only read row-by-row: one gather per input token. That is exactly the access pattern the existing zero-copy PLE gather kernel serves from pinned host memory.

## Modifications

- New opt-in server arg `--ple-offload-token-embedding` (default off), next to `--ple-offload-embedding` in `ExecOffload`. The table is always page-locked host memory, whatever `--ple-offload-backend` is, and on unified-memory devices (e.g. GB10) the flag frees nothing; the help text and the docs row say so. It is plumbed into the Qwen4-Exp text config like the other PLE offload settings, and is rejected for non-Qwen4-Exp models and together with `--cpu-offload-gb` / `--offload-group-size`, like `--ple-offload-embedding`.
- `Qwen4ExpModel._build_embed_tokens`: with the flag, the embedding is built on the meta device and wrapped in the existing `Qwen4ExpPinnedHostEmbedding`, so its table is allocated only in pinned host memory and never on the GPU. Rows are gathered by the existing Triton kernel (bitwise-equal rows, CUDA-graph safe). Models with tied word embeddings are rejected, because the `lm_head` reads the same table on the device.
- `Qwen4ExpPinnedHostEmbedding`:
  - takes an optional `host_table` to share an existing pinned table;
  - tolerates sources without a `weight_scale` (the token embedding has none).
- `Qwen4ExpForCausalLMMTP.set_embed_and_head`: when the target's embedding is a host table, the MTP draft gathers from the same table instead of keeping its own GPU copy.
- Docs: `server_arguments.mdx` row. Tests:
  - the server-arg conflict test is parametrized over both PLE flags;
  - a kernel test checks that `_build_embed_tokens` allocates nothing on the device and gathers bitwise-equal to `F.embedding`, and that `Qwen4ExpForCausalLMMTP.set_embed_and_head` makes the draft gather from the target's host table (same pointer, same rows);
  - mismatched shared tables and tied embeddings are rejected.

## Accuracy Tests

The gather is bitwise identical to `F.embedding` (`assert_close(rtol=0, atol=0)` in the new kernel test; `test_qwen4_ple_offload.py`: 12 passed, 3 skipped on RTX PRO 6000).

No token-identical end-to-end gate is possible for this model on SM120. Main is not repeat-deterministic there: two passes of the same prompt on one server give different prefill logprobs, and `--enable-deterministic-inference` is unsupported for the QSA indexer top-k. Model-level accuracy therefore uses GSM8K: `sgl-eval run gsm8k --num-examples 200 --num-threads 32 --temperature 0 --max-tokens 2048 --chat-template-kwarg enable_thinking=false`, `sgl-eval==0.1.3`, against the server launched as in the next section on one RTX PRO 6000:

| | main `8d4e1ce4c7` | this PR, `--ple-offload-token-embedding` |
|---|---|---|
| GSM8K, no MTP | 96.00% (5/200 truncated) | 96.50% (4/200 truncated) |
| GSM8K, MTP (settings as in the MTP table below) | 97.00% (4/200 truncated) | 96.00% (5/200 truncated) |

The differences (+0.5 and −1.0 points, in opposite directions) are within the run-to-run variation of a 200-example GSM8K run (binomial standard error ≈ 1.3 points at 96%), as expected from bitwise-equal embedding rows.

With the flag off, the KV pool (140,928 tokens) and memory figures equal main's.

**Token-identical gate on GB200.** Deterministic inference does work for this model on GB200 (SM100), so the end-to-end gate runs there. One GB200 node, TP2, `nvidia/Qwen3.8-Flash-Next-NVFP4` with the server arguments of the next section plus `--tp-size 2 --enable-deterministic-inference --attention-backend flashinfer`, CUDA graphs on. 7 greedy text prompts, each sent twice, plus one image chat. Output token ids are identical to main for all 7 prompts and the image chat, both with the flag off and with `--ple-offload-token-embedding`, and every arm is repeat-identical.

Tested at TP1 (RTX PRO 6000) and TP2 (GB200). Not tested: PP, DP attention, and online weight updates of the embedding.

## Speed Tests and Profiling

`python -m sglang.launch_server --model-path nvidia/Qwen3.8-Flash-Next-NVFP4 --ple-offload-embedding --json-model-override-args '{"text_config": {"ple_embedding_dtype": "float8_e4m3fn"}}' --moe-runner-backend flashinfer_cutlass --mem-fraction-static 0.85 --cuda-graph-max-bs-prefill 2048 --disable-radix-cache [--ple-offload-token-embedding]`, RTX PRO 6000 Blackwell Max-Q (300 W), same GPU for every arm:

| | main `8d4e1ce4c7` | this PR, flag off | this PR, `--ple-offload-token-embedding` |
|---|---|---|---|
| Weights on GPU | 80.742 GB | 80.742 GB | 79.561 GB |
| Free after weight load | 13.43 GB | 13.43 GB | 14.61 GB |
| **KV cache tokens** | **140,928** | 140,928 | **163,648 (+16.1%)** |
| Pinned host memory of the server (RssShmem) | 68,763,598,848 B | 68,763,574,272 B | 70,911,082,496 B (+2 GiB) |

The host side grows by 2 GiB rather than 1.27 GB because torch's pinned allocator rounds the table up to a power of two. Allocating the host table at its exact size is a separate change.

`python -m sglang.benchmark.serving --backend sglang --dataset-name random-ids --random-input-len 1024 --random-output-len 128 --random-range-ratio 1.0 --num-prompts 80 --max-concurrency 16 --seed 1`, 3 runs per arm on the same GPU; median (range):

| | Output tok/s | Median TTFT (ms) | Median TPOT (ms) |
|---|---|---|---|
| main | 490.93 (490.62–494.32) | 1306.6 (1303.3–1315.4) | 22.40 (22.26–22.53) |
| this PR, flag on | 493.64 (487.55–496.07) | 1304.0 (1298.0–1315.4) | 22.46 (22.26–22.69) |

Gathering 2,560 BF16 values per token from host memory does not change throughput or latency at this load: the arms overlap in every column. An earlier single-run pair showed a 2.2% TTFT gap that does not reproduce in these repeats.

With the in-checkpoint MTP head (`--speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 --mem-fraction-static 0.94 --chunked-prefill-size 4096 --max-running-requests 8 --max-mamba-cache-size 40`, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, otherwise as above), the draft shares the host table:

| | main | this PR, `--ple-offload-token-embedding` |
|---|---|---|
| Weights on GPU (target + draft) | 81.346 GB | 80.178 GB |
| **KV cache tokens** | **22,656** (0.536 GB) | **69,824** (1.650 GB): +47,168 tokens, 3.1x |
