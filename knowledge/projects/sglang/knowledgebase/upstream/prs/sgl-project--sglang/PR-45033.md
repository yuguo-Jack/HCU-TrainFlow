# [Fix] [Intel] spec: Fix XPU nightly dflash stop_regex and DSpark capture check

[Upstream PR](https://github.com/sgl-project/sglang/pull/45033) · state: open · merged: False

## Original PR description

## Motivation

The Intel kernel-main nightly ([run 39063278229](https://github.com/sgl-project/sglang/actions/runs/39063278229)) failed in two jobs:

- **1-GPU**: `test_dflash_intel_xpu.py` → `TestDFlashIntelXPUOverlap.test_finish_stop_regex_str`: `Expected finish_reason: stop, but got: length` (on the first try and on the retry).
- **2-GPU**: `test_dspark_intel_xpu.py` → `TestBasicSanityDSparkXpuIntelXpuDecodeGraph` `setUpClass`: `Capture cuda graph failed: Tried to instantiate dummy base class _cuda_isCurrentStreamCapturing`.

## Modifications

Fix 1 is a scheduler fix and applies to every backend. Fix 2 is gated on `is_xpu()`, and the disable is an XPU-only CI registration.

**1. Speculative stop_regex misses an end-anchored match on a token accepted mid-step** (`schedule_batch.py`)

`Req._check_str_based_finish` runs `stop_regex` once per step, against the decoded tail ending at the *last* accepted token. If a step accepts several tokens, a pattern like `[.!?]\s*$` that matches after an earlier token in the step never matches the full window, so the request can run to `max_tokens`. When the full window doesn't match and the step accepted more than one token, the accepted prefixes are also checked: `_locate_str_stop_finished_len(..., full_window_matched=False)` returns `None` if no prefix matches. `test_stop_str_speculative.py` gets a regression case that checks the request finishes at the mid-step match (`finished_len == 2`).

**2. DSpark draft sampler uses a CUDA-only capture check** (`dspark_draft_sampler.py`)

`_step_logits` asserted `torch.cuda.is_current_stream_capturing()`, which raises on XPU (`_cuda_isCurrentStreamCapturing` is a dummy there) and aborts draft graph capture. It now uses `torch.xpu.is_current_stream_capturing()` on XPU and keeps `torch.cuda.is_current_stream_capturing()` everywhere else. This assert came in with #43790 (10-12), so the XPU DSpark test added in #33739 (10-14) has never passed.

**3. Disable `test_dspark_intel_xpu.py` in the XPU nightly registry** (`register_xpu_ci(..., disabled=...)`)

With fix 2 in place, every DSpark XPU class starts, but `TestBasicSanityDSparkXpuIntelXpuDecodeGraph.test_fwd_occupancy` still fails: under `--cuda-graph-backend-decode full` with `--tp 2`, every draft is rejected (accept length ~1.0, vs ~3.3 eager). Accuracy tests still pass because the target verify runs eagerly. Evidence from debugging:

- The draft graph's attention metadata (`cache_seqlens`, `cu_seqlens_q/k`, page table, write slots) is identical to eager for the same step, and the prefix KV is injected eagerly in both modes.
- In eager mode the two TP ranks' draft hidden states are identical. **After graph replay the two ranks differ**, so the TP reduction isn't taking effect inside the replayed XPU draft graph.
- Not caused by the attention backend (triton gives the same 1.0), the in-graph draft TP broadcast (`SGLANG_SPEC_TP_SYNC=all,-dspark-draft`), the sampler (`SGLANG_DSPARK_USE_GREEDY_DRAFT=1`), the folded proposal (`SGLANG_DSPARK_FOLDED_PROPOSAL=0`), or L0 copy offload.

XPU defaults to no decode graph, so nothing else in XPU CI runs a decode graph with TP>1. The file is disabled for XPU only. Tracked in #45034, which should re-enable it.

## Accuracy Tests

Verified on the Intel CI runner with `intel/sglang-dev:latest-kernel-main` (sglang `8dee3f6bd`, sgl-kernel-xpu 0.4.0, torch 2.14.0+xpu) and a test checkout at the same commit:

| Check | Without fix | With fix |
|---|---|---|
| `test_stop_str_speculative.py` (new mid-step case) | new case fails | 10/10 pass |
| DFlash `[.!?]\s*$` request (greedy, same prompt) | stopped after **217** tokens, past several sentence ends | stopped at the **first** sentence end, **38** tokens |
| `test_dflash_intel_xpu.py` full file | `test_finish_stop_regex_str` fails in CI | regex test passes in every class |
| `test_dspark_intel_xpu.py` | `DecodeGraph` `setUpClass` crash (same error as CI) | 95 tests run; only `DecodeGraph.test_fwd_occupancy` fails (accept length 1.0, see item 3) |

In the full dflash run, two classes (`BackendPage256`, `BackendOverlapPlanStream`) hit `UR_RESULT_ERROR_OUT_OF_RESOURCES` in target prefill after about 70 minutes and ~15 server launches on one GPU. Re-run on their own, `BackendPage256` passes 20/20 both with and without this patch, so that's unrelated.

`run_suite` registry check: `nightly-xpu-kernel-main-2-gpu` now lists `test_dspark_intel_xpu.py` as disabled, and the other four files still run.

The XPU-gated revision was re-checked on XPU hardware: `TestDFlashIntelXPUOverlap.test_finish_stop_regex_str` OK (the sentence regex stops at 38 tokens), and `TestBasicSanityDSparkXpuIntelXpuDecodeGraph.test_health` OK (graph capture succeeds).
