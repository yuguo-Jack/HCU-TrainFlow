# LoRA support for LFM2 and LFM2-MoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/27813) · state: closed · merged: False

## Original PR description

## Motivation

Part 2 of splitting #25528 (as discussed there with the maintainers; part 1 is #27381). Enables full LoRA support for LFM2 (dense) and LFM2-MoE: attention, MLP, MoE experts (per-expert), MoE router (`gate`), and ShortConv (`in_proj`/`out_proj`). All LFM2-specific logic lives in the two model files.

## Modifications

**Model files (LFM2-specific):**
- **`models/lfm2.py`** — the dense MLP used module names `w1/w3/w2`, but adapter normalization renames those weights to `gate_proj/up_proj/down_proj` and stacks them into `gate_up_proj`, so dense MLP LoRA landed in buffers no module consumes and was silently never applied. Aligned the MLP with `lfm2_moe.py`'s fused naming (`MergedColumnParallelLinear gate_up_proj` + `down_proj`, `SiluAndMul`). Added `get_hidden_dim` (LoRA buffers must use LFM2's *actual* FF dim — `block_auto_adjust_ff_dim` means e.g. `intermediate_size=12288` in config but 8192 in the modules) and `get_stacked_multiply` (ShortConv `in_proj` packs 3 partitions: B/C/x).
- **`models/lfm2_moe.py`** — `get_hidden_dim` (incl. router `gate`: hidden → num_experts; `in_proj`: hidden → 3·hidden) and `get_stacked_multiply`. The router is a `ReplicatedLinear`, handled by the existing `ReplicatedLinearWithLoRA`.

**Core files (generic/additive):**
- **`lora/lora.py`** — generic normalizer: tile a single-rank `lora_A` for adapters trained against a merged multi-partition `in_proj` as one Linear (partition count from the model's `get_stacked_multiply`; weights already stacked by the Mamba/GDN normalizers are shape-guarded out). Same pattern as the existing `in_proj_qkvz` handling.
- **`lora/utils.py`** — `gate` added to known modules; `w1/w3/w2` entries in target-name normalization, mirroring the existing `_rename_expert_w_to_proj` weight rename.
- **`utils/common.py`** — `out_proj`, `in_proj`, `gate` added to the CLI whitelist.
- **`lora/mem_pool.py`** — `has_shared_experts` extended for `num_dense_layers > 0` so hybrid MoEs with leading dense MLP layers (LFM2-MoE: layers 0–1) get their non-MoE 3D buffers alongside the 4D `*_moe` ones. (DeepSeek hybrids already work because they set `n_shared_experts > 0`.)

## Accuracy Tests

Teacher-forced top-k logprob comparison vs HF+PEFT running the same adapters (greedy, bf16):

| Run | ROUGE-L | Prefill mean/max Δlogprob | Decode mean/max |
|---|---|---|---|
| Dense base vs base (noise floor) | — | 0.12 / 0.49 | 0.09 / 0.25 |
| **Dense + LoRA** | **1.00 (token-identical)** | 0.14 / 0.44 | 0.17 / 0.43 |
| MoE base vs base (noise floor) | — | 0.37 / 1.50 | 0.40 / 1.75 |
| **MoE + LoRA** | **1.00 (token-identical)** | 0.22 / 0.77 | 0.28 / 0.87 |

With LoRA applied, divergence from HF is at or below each model's no-LoRA kernel-noise floor, and 32-token greedy generations are byte-identical.

**Reproducing — dense (LFM2.5-1.2B-Instruct), adapter [`LiquidAI/LFM2.5-1.2B-Instruct-smoltalk-LoRA`](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct-smoltalk-LoRA):**

```bash
sglang serve \
    --model-path LiquidAI/LFM2.5-1.2B-Instruct \
    --enable-lora --max-lora-rank 8 \
    --lora-paths "smoltalk=LiquidAI/LFM2.5-1.2B-Instruct-smoltalk-LoRA" \
    --lora-target-modules q_proj k_proj v_proj out_proj gate_proj up_proj down_proj in_proj \
    --lora-strict-loading
```

**Reproducing — MoE (LFM2-8B-A1B), adapter [`LiquidAI/LFM2-8B-A1B-smoltalk-LoRA`](https://huggingface.co/LiquidAI/LFM2-8B-A1B-smoltalk-LoRA):**

```bash
sglang serve \
    --model-path LiquidAI/LFM2-8B-A1B \
    --enable-lora --max-lora-rank 8 \
    --lora-paths "smoltalk=LiquidAI/LFM2-8B-A1B-smoltalk-LoRA" \

```

**[P0] Adding `"gate"` to `_KNOWN_LORA_TARGET_MODULES` breaks `--lora-target-modules all` for every other MoE model whose router is a `ReplicatedLinear` named `gate`** (qwen2_moe, qwen3_moe, mixtral, olmoe, ...).

`auto_detect_lora_target_modules` collects `LinearBase` leaf names and intersects with this set. Before this PR, `gate` was filtered out by the intersection; now it survives. `LoRAMemoryPool.init_buffer` then calls `get_hidden_dim("gate", ...)`, and since those models don't implement `get_hidden_dim`, the default fallback raises `NotImplementedError("get_hidden_dim not implemented for gate")` during memory-pool init — server fails to start on configurations that worked before this PR. (Models whose gate is a plain `nn.Module`, e.g. GLM4-MoE / DeepSeek `MoEGate`, are unaffected because auto-detect only picks up `LinearBase` leaves.)

Suggestion: only keep `gate` from auto-detect when the base model actually supports it (e.g. probe `base_model.get_hidden_dim("gate", 0)` / check for the method), or add a generic `gate` branch to the default `get_hidden_dim` fallback using `config.num_experts`.

**[P0] `--lora-target-modules all` crashes for LFM2 because `get_hidden_dim` has no `embed_tokens`/`lm_head` branches.**

Once a model defines `get_hidden_dim`, `lora/utils.py` dispatches *all* module-shape queries to it — bypassing the default fallback that does handle embeddings — and `--lora-target-modules all` unconditionally force-adds the embedding names. So `init_embedding_buffer → get_embedding_lora_A_shape → base_model.get_hidden_dim("embed_tokens", 0)` hits this `raise` at startup. The repro commands in the PR description only work because they enumerate target modules explicitly.

Same defect in `Lfm2MoeForCausalLM.get_hidden_dim` (`lfm2_moe.py`). Suggestion: add `embed_tokens`/`lm_head` branches, or delegate unknown names to the default util instead of raising.

**[P1] These `w1`/`w3`/`w2` mappings turn a loud failure into silent output corruption for models whose live modules are literally named `w1`/`w2`/`w3`** (e.g. InternLM2's `self.w2`).

For such a model, an adapter with `target_modules=["w2"]` now normalizes to `down_proj`: validation passes, buffers get allocated, and the renamed weights load without any skip warning — but module wrapping matches module basenames against the *normalized* target set, and basename `w2` is not in `{down_proj}`, so the module is never wrapped and the down-proj LoRA delta is silently dropped (wrong generations). Before this PR the same adapter failed loudly.

The rename is only correct for models whose runtime modules are actually named `gate_up_proj`/`down_proj` (LFM2 after this PR). Consider gating the normalization on the base model (mirroring how the weight-side `_rename_expert_w_to_proj` is scoped) rather than applying it globally.

**[P1] This allocates dense 3D `gate_up_proj`/`down_proj` LoRA buffers for *every* layer, but hybrid models only have a dense MLP on the first `num_dense_layers` layers.**

**[P1] This conflates attention `out_proj` (`head_dim * num_heads → hidden`) with ShortConv `out_proj` (`hidden → hidden`) and ignores `layer_idx`.**
