# [Fix] tokenizer_manager: Skip watermark redaction in request dumps when watermarking is disabled

[Upstream PR](https://github.com/sgl-project/sglang/pull/46518) · state: open · merged: False

## Original PR description

## Motivation

Without `--enable-watermark`, the dump paths in `TokenizerManager` still redact watermark secrets on every dump. `_dump_data_to_file` runs on the tokenizer event loop each time `dump_requests_threshold` finished requests accumulate, and `redact_watermark_secrets` recursively walks the whole request list — every request's `input_ids` and output ids. Measured on `main`: ~3 ms per dump for 64 × 8192-token requests, ~64 ms for 1000 × 4096-token (Xeon 8124M, CPU microbenchmark), spent on a feature that is off.

#46207 gated the request logger the same way; the dump paths were missed.

## Modifications

Gate all redaction in the dump paths behind `get_exec().features.enable_watermark`, mirroring the existing `_server_args_for_dump`:

- `_redact_for_dump(data)`: pass-through when watermarking is off, `redact_watermark_secrets(data)` when on. Covers `config_updates` and `requests` in `_dump_data_to_file` and `dump_requests_before_crash`, plus `_dump_config_snapshot`.
- `_launch_command_for_dump()`: plain `" ".join(sys.argv)` when off, `redact_watermark_command_line(...)` when on.
- README: per-surface breakdown of what is redacted where.

Skipping redaction with watermarking off drops no server-side secret: `--watermark-config` is rejected at startup, so no server key exists. Client-supplied `watermark` fields are kept as-is (same as request logs after #46207) — note a crash dump can still hold a client's key from a request that crashed before validation. With `--enable-watermark`, dump payloads are byte-identical to `main`.

## Accuracy Tests

Dump-path-only change; inference is untouched.

- Unit: `test_tokenizer_config_updates.py`, `test_tokenizer_manager_rid_cleanup.py`, `test_request_logger_redaction.py` — 65 passed.
- One-off parity harness (not committed), driving both dump paths with a 100k-token request:
  - Watermark on: pickled payloads byte-identical to `main`, secrets redacted in both.
  - Watermark off: 0 redaction calls (7 on `main`); only payload diff is the snapshot fields `watermark_config`, `watermark_key`, `watermark_key_b` keeping `None` instead of `"<redacted>"`.

## Speed Tests and Profiling

Removes the per-dump redaction walk when watermarking is off (~3 ms @ 64 × 8k tokens, ~64 ms @ 1000 × 4k tokens per dump). The watermark-on path is unchanged.
