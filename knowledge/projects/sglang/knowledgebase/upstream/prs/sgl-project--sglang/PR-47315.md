# [Perf] activation: Add a JIT CUDA xIELU kernel for Apertus

[Upstream PR](https://github.com/sgl-project/sglang/pull/47315) · state: open · merged: False

## Original PR description

> Apertus-v1.5-8B is not in upstream SGLang yet (#32979), so its rows below were measured with this same change on [swiss-ai/sglang-apertus `apertus-1-5`](https://github.com/swiss-ai/sglang-apertus/pull/4), with transformers [swiss-ai@3797303](https://github.com/swiss-ai/transformers/tree/3797303dda74844e3d1f8977ff5518bb91f818b4) as pinned by the model card. Apertus-8B-Instruct-2509 rows are on upstream `main`.

## Motivation

Apertus's MLP is `up_proj -> xIELU -> down_proj` on a `[tokens, 21504]` tensor (8B). Today `XIELU` runs one of two paths:

- If the optional [nickjbrowning/XIELU](https://github.com/nickjbrowning/XIELU) package is installed, its CUDA kernel. It is not a dependency, has to be built from source (on torch 2.14 it also needs `-std=c++20`, and its CMake sets no CUDA architecture), and SGLang calls it with `with_vector_loads=False`.
- Otherwise a bf16 `torch.where` expression of about ten elementwise kernels.

Both evaluate in bf16 with bf16 coefficients. With the checkpoints' large layer-0 coefficients (`softplus(alpha_p) ≈ 166`, `alpha_n ≈ 41` in Apertus-8B-Instruct-2509) the negative branch cancels near `x ≈ -0.024`, and about half of all outputs are not correctly rounded.

## Modifications

- `kernels/jit/csrc/elementwise/xielu.cuh`, `kernels/ops/activation/xielu.py`: a JIT xIELU kernel (fp16/bf16). It evaluates the fp32 expression with explicitly rounded operations (no FMA contraction), in the order of the torch reference, and rounds once. The launcher picks the widest vector (up to `kMaxVecBytes`) that both buffers are aligned to and that still leaves `SM count x 512` threads: at decode sizes the per-element `expm1f` is latency-bound, so fewer elements per thread wins. A thread past the last vector handles the tail. PDL as in the other activation kernels. Registered as `activation.xielu`, and as a custom op so `torch.compile` sees it as opaque.
- `XIELU`: the effective coefficients `[softplus(alpha_p), beta + softplus(alpha_n), beta, eps]` live in a non-persistent fp32 buffer `_coeffs`, derived with torch ops by `update_coefficients()` and read by the kernel on device. This keeps the layer constructible on the meta device (zero-copy IPC loading), lets the IPC daemon's exported buffers carry the loaded values, and lets captured CUDA graphs follow in-place weight updates. Inputs other than fp16/bf16 (e.g. `--dtype float32`) and non-contiguous inputs use the native fp32 expression. The optional external package path, its 3-D reshape warning and the dynamo special case are removed.
- `ApertusForCausalLM`: calls `update_coefficients` after `load_weights` and from `post_load_weights`. This also replaces the old path's `beta`/`eps` scalars, which were cached at construction rather than from the checkpoint.

## Note on the removed package path

`with_vector_loads=True` on the package makes Apertus-8B-Instruct-2509 return empty completions (GSM8K 0.000), and the scalar path SGLang uses is matched end to end by this kernel with correctly rounded outputs. So I removed the optional import rather than keeping it as a fallback; happy to keep it behind a flag if you prefer.
