# [Fix] mem_cache: Count unified-cache hits only on the finishing insert

[Upstream PR](https://github.com/sgl-project/sglang/pull/44893) · state: open · merged: False

## Original PR description

## Motivation

#41520 states that only the finishing insert bumps `hit_count` and that checkpoints do not. The `cache_inserted_len` watermark it landed with also bumps hits on checkpoint inserts, so with `write_through_threshold=1` the HiCache write-through / external-linker offload fires once per prefill chunk instead of once per request. With the UMBP linker on a PD prefill this roughly doubles the number of offload batches and slows decode steps by ~2 ms at 1e86143b.

## Modifications

`UnifiedRadixCache.checkpoint_into_tree`: pass `inserted_len=0` for a finished request (each node on the path counts once) and the full key length for a checkpoint (no node counts). Prompt-split re-inserts and `RadixCache` are unchanged.

## Accuracy Tests

N/A: only changes when hit counters are bumped (and thus when write-through/offload is triggered); the model forward and the inserted KV are unchanged.

## Speed Tests and Profiling

DeepSeek-V4-Pro FP4, 1P1D on MI355X: prefill TP8/EP8 with the UMBP linker (`write_through`), decode TP8 with DP attention, DSPARK, agentic workload at concurrency 256, 3600 s. Each column uses one fixed node pair. Decode step time in ms, regressed to 16 running req/rank and 220k context.

Prefill prefix-cache hit rate unchanged (96.5%). Output throughput +1.2% (A) / +1.4% (B) vs the mean of the 1e86143b runs (61.1k / 61.0k tok/s). Runs used an equivalent sentinel (`1 << 62`) for the checkpoint `inserted_len`.

The existing `test_scripted_core_1gpu` hit-count tests expect every node to be hit exactly once after the request finishes, which still holds (not run locally).
