# [Fix] moe: Make Marlin MoE deterministic under --enable-deterministic-inference

[Upstream PR](https://github.com/sgl-project/sglang/pull/48268) · state: open · merged: False

## Original PR description

## Motivation

Fixes #48150. `fused_marlin_moe` never reads `--enable-deterministic-inference`, so a MoE model on the Marlin runner gives different bits for identical calls with the flag on. Two sources vary between calls:

- atomic-add reductions in the Marlin GEMM, which decide the result at decode sizes;
- the order in which `moe_align_block_size` places each expert's entries, which decides which entries share a GEMM block at prefill sizes.

#26627 turns off the atomic adds under the flag for Kimi-K2.5. This PR includes that and adds the entry order, which is the larger source at prefill sizes on current main (ablation below). It reads the flag through `get_exec()`, since `get_global_server_args()` has been retired. #26627's dual-stream change in `deepseek_v2.py` is a separate concern and isn't included here. If maintainers would rather land this through #26627, I'm happy to close this one.

## Modifications

- `fused_marlin_moe.py`: under the flag, `use_atomic_add` is false, and after `moe_align_block_size` each expert's entries are sorted ascending with padding last (`_order_entries_within_experts`).
  - The sort keys on runs of equal block expert ids instead of the ids themselves, so it doesn't depend on `expert_ids` being sorted (the expert-parallel path doesn't certify that). It handles the `-1` blocks and the `[padded_tokens, inactive_blocks]` count from #45462.
  - Tensor ops only (`cumsum`, gather, stable `argsort`), so CUDA graphs capture it.
  - The single-token `moe_align_single_token` path isn't sorted: its top-k ids are distinct, so each expert holds one entry.
- `test_moe_wna16_marlin.py` and the manual `bench_mxfp4_sm90_kernels.py` call `fused_marlin_moe` without a server. `get_exec()` raises when no config is published, so both now publish a dummy config, as `test_marlin_moe.py` already does.
- `test_marlin_moe.py`: `test_fused_marlin_moe_deterministic_inference_repeats_bitwise`. Int4 GPTQ weights in fp16, with and without expert parallelism (dispatcher-style local ids, `-1` for non-local experts). It checks that five calls under the flag match to the bit and that the result matches the default path within `1e-3`.

Nothing changes with the flag off.

## Accuracy Tests

Kernel level, on an RTX 5060 Ti (SM120), torch 2.14.1+cu130, sglang-kernel 0.4.10. The NVFP4 case is the issue's shape (random weights through `prepare_moe_nvfp4_layer_for_marlin`, 256 experts, hidden 4096, width 1024, top-6, bf16). Counts are calls identical to the first, out of 10:

| Case | Flag off | Flag on | Max abs difference, flag on vs off |
|---|---:|---:|---|
| NVFP4, 1 token | 0 | 10 | 0.0625 (one bf16 step at that magnitude) |
| NVFP4, 512 tokens | 0 | 10 | 0.0625 |
| NVFP4, 2,700 tokens | 0 | 10 | 0.0625 |
| int4 fp16, 512 tokens, 64 experts | 0 | 10 | 1.5e-5 |
| int4 fp16, 512 tokens, expert parallel (8 of 16 local) | 0 | 10 | 1.5e-5 |

Ablation on current main, flag on, identical out of 10:

| Case | Atomic adds off only | Entry sort only | Both |
|---|---:|---:|---:|
| NVFP4, 512 tokens | 5 | 10 | 10 |
| NVFP4, 2,700 tokens | 1 | 10 | 10 |
| int4 fp16, 256 tokens | 0 | 10 | 10 |

At 1 token, the single-token path doesn't sort, and turning off atomic adds takes it from 0/10 to 10/10.

A CUDA graph captured with the flag on replays identically to eager (5 of 5).

I didn't run a server-level eval; the issue reports the server-level effect (TP2/TP4, 48 of 48 identical pairs) for the equivalent change.

## Speed Tests and Profiling

`marker.do_bench` with CUDA graphs, same NVFP4 shapes and GPU. The weights (~1.6 GB) far exceed L2 (32 MB), so argument cloning is skipped. Times are per `fused_marlin_moe` call:

|---:|---:|---:|---:|

Only runs with `--enable-deterministic-inference` pay this.
