# [MoE] Serve tiny-batch moe_align on the pair axis, at any expert count

[Upstream PR](https://github.com/sgl-project/sglang/pull/34131) · state: closed · merged: False

## Original PR description

> Generated by Claude.

## Motivation

`bs=1` decode aligns a handful of (token, slot) pairs over hundreds of experts, but every kernel we had scaled with the **expert** axis rather than the pair axis:

- the AOT/JIT small-batch kernel caps at 64 buckets (its shared histogram is `O(threads x experts)`),
- the wider paths zero and scan 1024 shared counters no matter how small the batch.

So the cheapest case paid the most fixed cost. PR #32395 added a triton kernel for exactly this corner; this PR moves that idea into the JIT kernel, makes it ~2-3x faster, and lifts the expert-count limit entirely.

## What this does

Two single-CTA kernels that never touch the expert axis. Warp `w` owns a pair, its lanes hold every pair, and three warp reductions over the resulting 32x32 relation give each pair

- its bucket's population,
- its rank within that bucket,
- the count of pairs in strictly smaller buckets.

That last one is the *unpadded* prefix, and it is strictly increasing across distinct non-empty buckets — so it doubles as a dense key. A bucket's leader adds its block count into every `s_cumsum[k]` with `k >= rank`, and a pair then reads its own bucket's start at `s_cumsum[rank]`. A second kernel gives each warp two pairs to reach 64. Nothing is sized by the bucket count, so **both accept any number of experts**.

### Measured (B200, CUDA graph replay)

| shape | new | triton (#32395) | JIT v1 |
|---|---|---|---|
| `topk=7  E=257 blk=128 bs=1` | **0.87us** | 2.58us | 3.24us |
| `topk=16 E=896 blk=128 bs=1` | **1.03us** | 2.75us | 3.50us |
| `topk=7  E=257 blk=128 bs=5` | **1.27us** | 5.48us | 3.08us |
| `topk=16 E=896 blk=128 bs=4` | **1.63us** | 5.65us | 3.53us |

An empty single-block launch measures 0.56us on the same harness, so the smallest shapes are now within ~0.3us of the launch itself.

## Also in here

- **One entry for v1 and v2.** The JIT wrapper picks v2 wherever it runs and falls back to v1 for what it cannot take (wide expert counts on the bucket-scanning paths, non-int32 ids, odd block sizes, unaligned input). `version=` pins one, which the benchmark uses to compare them.
- **`ignore_invalid_expert` becomes a template parameter** of v2 instead of a runtime bool, so only the variant a caller asks for is compiled and ptxas can unswitch the histogram loop (~2x on that loop body).
- **v1 gets PDL**, conservatively: the wait ahead of every kernel's first global access, the trigger at the end of each block's work.
- **Call sites unified.** `moe_align_block_size` now has a single implementation under `sglang.kernels.ops.moe`, reached through the registry; the three private copies under the LoRA paths are gone.
- **`sorted_token_ids` allocation.** Both align kernels clear it with `ceil(len / VEC_SIZE)` `int4` stores, so an exact-length buffer was being written up to 3 `int32`s past its end. The buffer is now reserved rounded up to `VEC_SIZE` while still exposed at its exact length, so `shape[0]` is unchanged for consumers that derive a block count from it by floor division.
- **The triton kernel leaves the runtime dispatch** now that the JIT covers its corner faster. Its source stays, and the benchmark still measures it.

## Compatibility

The public signature is unchanged. Verified against the previous implementation on B200 over ~5800 configurations (experts 1..9000, block sizes 4..256, numel 0..8192, int32/int64, with EP `-1` sentinels and `ignore_invalid_expert`): identical `num_tokens_post_padded`, identical `expert_ids`, identical `sorted_token_ids` contents and shapes.

## Tests

`test/registered/kernels/ops/moe/test_moe_align_v2.py` replaces `test_moe_align_small_numel.py`. The oracle is a plain-torch implementation of the contract, so it does not depend on any other kernel's shape support; the AOT wheel is cross-checked on top of it to back the drop-in claim. Parametrisations land deliberately on each of the three kernel shapes, and `test_tiny_batch_takes_any_expert_count` sweeps 64..65535 experts at `numel` 1 and 64 — re-introducing a bucket bound on that path turns it red.
