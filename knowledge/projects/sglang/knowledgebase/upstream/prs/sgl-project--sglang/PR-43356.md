# fix: make FlashInfer NVFP4 speculative decoding graph-safe

[Upstream PR](https://github.com/sgl-project/sglang/pull/43356) · state: open · merged: False

## Original PR description

## Motivation

NVFP4 KV cache with FlashInfer speculative prefill needs a dequantized workspace during target verification and draft extend. The prompt-prefill path relies on CPU request/length metadata and a contiguous dequant page table, which do not describe these fixed-width speculative forwards and cannot follow CUDA Graph replay metadata.

This supersedes #36045, which was auto-closed by the idle-PR bot. It refreshes the fix against `888de24cc8a5c919ec952be938c319a36442edbb` and responds to the [SM120 Qwen NVFP4 + MTP report](https://github.com/sgl-project/sglang/pull/36045#issuecomment-6078220276).

## Modifications

- Add a capture-stable Triton kernel that reads GPU request indices and lengths, dequantizes cached NVFP4 K/V into their physical FP8 workspace slots, and copies current speculative K/V. Replay can change requests and prefix lengths; padded requests leave reserved slot 0 untouched.
- Route target verification and NVFP4 draft extend through this workspace. Use the current `KVWriteLoc`/`KVLocPlan` APIs and preserve ordinary non-quantized draft-prefill behavior.
- Account for the independent draft pool's full dequant workspace, including implicit MTP. Respect draft KV dtype overrides and the allocator's actual buffer recipe without changing the existing speculative-layer resolver semantics.
- Add CUDA replay tests for 1/2/4 local KV heads, six CPU routing/API-contract tests, and five pool-sizing tests with 15 subcases. Register the GPU test in the Blackwell kernel suite with an executable pytest entry point.

- New FlashInfer routing/API-contract tests with all GPUs hidden: **6 passed**.
- Repository pre-commit checks passed for all changed files.
- Local `qwen38-27b-nvfp4-modelopt` checkpoint (`Qwen3_5ForConditionalGeneration`, 64 layers) with integrated one-layer MTP, implicit draft path, independent target/draft pools: **all 6 short request groups passed in both graph and eager modes, with exact output-token parity**. This includes repeated BS1/BS2 64-token generation and three simple answer probes. Logs confirm actual CUDA Graph replay at both batch sizes; eager logs show no graph replay.

@AppNetDeveloper your data is exactly why we shipped #43471 last night — same SM120 platform, same Qwen3.8-27B-NVFP4 + MTP stack. It may change the tradeoff you backed away from.

To be precise about what it does *not* touch: your mid-length decode regression (~134→106 tok/s at 1–2 running) is on the trtllm_mha/XQA **decode** path + page-64 reuse, and #43471 doesn't move decode kernels — your conclusion holds there. What #43471 removes is the FP8 dequant **workspace** from the prefill path entirely: NVFP4 prefill now goes through FlashInfer's native packed-FP4 paged prefill (`run(..., kv_cache_sf=...)`, kernel-side tile dequant), so the per-chunk gather→bf16→fp8 re-dequant of the whole cached prefix is gone — along with its two structural taxes:

- **Transient memory**: on our 2× RTX 5060 Ti 16 GB (TP2) rig, a ~45K-token cold prefix OOM-killed the scheduler *in production* via `dequantize_prev_kv` temporaries under the workspace route. With #43471, back-to-back cold 45K/100K/150K prefill rounds run with GPU memory **flat to the MiB** across all rounds (no per-layer spikes at all).
- **Fixed + per-token pool cost**: `dq_k/dq_v` were allocated per pool-row (~146 MiB/rank) *and* charged 1024 B/token into `compute_cell_size`. Both vanish → cell size 10816→**9792 B/token**, i.e. **+10.5% same-budget pool capacity**, and boot headroom rose 0.88→2.6 GB/rank at our 180K config, which let us raise both pool and mamba-slot budget.

Reference numbers (same rig, native-FP4 prefill, greedy, cold disjoint prefixes — full A/B vs the workspace route running as I type; these are the absolute values):

| metric | 2×5060 Ti 16GB TP2 (chunk 2048) |
|---|---|
| 45K cold prefill TTFT | 12.4 s |
| 100K cold | 35.5 s |
| 150K cold | in-flight (180K pool, usage ~0.83) |
| decode (NEXTN 2/1/3 MTP) | 70–90 tok/s single-stream, accept 2.1–3.0, HiCache kernel+`#43240` battery green |

Notes for a trial on your rig:
- #43471 is `main`-based and env-gated: `SGLANG_NVFP4_NATIVE_PREFILL=0` restores the old workspace route for a clean A/B with no re-deploy.
- It expects FlashInfer's NVFP4 `kv_cache_sf` prefill support (present in 0.6.18; worth a quick check on your 0.7.0.post1 before wiring).
- Expect a minor rebase conflict against #43356 — both touch the same forward path, but #43356's spec-extend workspace kernels and this route are orthogonal (spec verify/draft-extend still rides trtllm native decode). Happy to help resolve a combined tree.
- Your chunked-prefill 16384 already shrinks the workspace route's quadratic re-dequant tax (fewer chunks), so the prefill *time* delta may be modest for you; the OOM-class removal and the +10.5% capacity / headroom are the parts that don't depend on chunk size.

If the decode side is what keeps you on FP8 KV, one data point worth having on your radar: on SM120 the decode loss looks like an XQA/page-size property of the NVFP4 route, not of the KV format's arithmetic — if FP8-KV decode at page 64 ≈ page 16 on your harness, the mid-length story may be fixable independently of this.
