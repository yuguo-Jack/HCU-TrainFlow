# [Fix] diffusion: keep ZMQ ingress sockets on their configured port

[Upstream PR](https://github.com/sgl-project/sglang/pull/43732) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #43731.

The scheduler ingress ROUTER and the disagg orchestrator's frontend/result sockets are bound with `get_zmq_socket`'s default retry policy, which moves to `port + 42` when the configured port is taken. Their peers keep connecting to the configured endpoint, so with two instances starting at the same time the second instance's request is executed by the first instance and the second one hangs.

## Modifications

- `Scheduler`: bind the ingress with `same_port=True`, i.e. retry on the configured port (TIME_WAIT) and fail with `EADDRINUSE` instead of moving.
- `DiffusionServer` orchestrator: same for the frontend ROUTER and the encoder/denoiser/decoder result PULL sockets. Pool workers already did this.
- `get_zmq_socket`: the final error log printed a `+42` port even in `same_port` mode; it now prints the endpoint actually tried.
- New CPU unit test `test_zmq_bind_port.py`: the same-port helper fails/succeeds as expected, and the scheduler requests `same_port=True`. The scheduler test fails on `main`.

The race in `settle_port` (checked at parse time, bound later) is not addressed here. After this change, the instance that loses the race fails with a clear error and does not steal or lose requests.

## Tests

- `pytest test_zmq_bind_port.py test_scheduler_client.py test_dp_routing.py`: 18 passed.
- End to end, MiniMax-H3 TP2, two concurrent `sglang generate` with `--scheduler-port 7000`:
  - `main`: instance 2 rebinds to 7042, instance 1 executes both requests (its log shows instance 2's `output_file_path`), instance 2 hangs until killed.
  - this PR: instance 1 retries 7000 for about 9 s, then exits with `ZMQError: Address already in use (addr='tcp://127.0.0.1:7000')`. Instance 2 finishes normally.
