# [Fix] Abort only the request a rid names, not every rid it prefixes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43476) · state: open · merged: False

## Original PR description

## Motivation

`POST /abort_request {"rid": "job-1"}` also aborted every in-flight request
whose rid has `job-1` as a prefix: `job-10`, `job-11`, ... It aborted them
part-way through with `finish_reason: "abort"`, even though the caller never
named them.

Caller-supplied rids are a documented request field (`rid` on `/generate` and
on the OpenAI endpoints), and sequential ids or a per-tenant/per-session shared
prefix are the ordinary way to choose them, so one abort silently cancelled
unrelated requests. The cost is not just a wrong response: each wrongly aborted
request had already been scheduled, so it held KV cache and a
`--max-running-requests` slot that no longer had a consumer.

Reproduction on v0.5.21 (4x RTX 4090, TP=4, long generations):

```
POST /generate              {"rid": "probe-a",  "sampling_params": {"max_new_tokens": 2500}}
POST /generate              {"rid": "probe-ab", "sampling_params": {"max_new_tokens": 2500}}
POST /abort_request         {"rid": "probe-a"}   -> 200

probe-a   finish_reason=abort  completion_tokens=309   (expected)
probe-ab  finish_reason=abort  completion_tokens=332   (unexpected: should run to length)
```

## Modifications

Abort targets are now matched by `matches_abort_rid(req_rid, abort_rid)`
(`python/sglang/srt/managers/io_struct.py`), which accepts the named rid
exactly, plus the sub-request ids the engine itself derives from it --
`GenerateReqInput._normalize_rid` expands a parent rid to `f"{rid}_{i}"` for
batch requests and parallel sampling, so those children stay abortable through
the parent rid.

All 11 prefix-match sites are converted:

* `Scheduler.abort_request`: chunked req, waiting queue, prefill bootstrap
  queue, prefill inflight queue, decode prealloc queue, decode transfer queue,
  retracted queue, inflight batches
* `GrammarManager.abort_requests` (grammar queue)
* `MMReceiverBase.abort_waiting_requests` (encoder / EPD waiting list)
* `DllmManager.pop_aborted_reqs` (dLLM queues)

`abort_all` is untouched. An `AbortReq` for a rid the engine does not know
stays a no-op, and an empty rid (which would previously prefix-match every
request) now matches nothing, consistent with the `TokenizerManager` guard
that already refuses empty ridded aborts.

## Accuracy Tests

No model, kernel or forward-pass change.

Before/after on 4x RTX 4090, Qwen3.5-27B-FP8, TP=4, EAGLE:

| action | before | after |
| --- | --- | --- |
| `abort("probe-a")` while `probe-a` and `probe-ab` are decoding | both `finish_reason=abort` | `probe-a` aborts, `probe-ab` runs to `length` |
| `abort("batchprobe")` for a parent rid of `batchprobe_0/_1` | children abort | children still abort |
| `abort("ghost-rid")` for an unknown rid | HTTP 200, no-op | HTTP 200, no-op |
