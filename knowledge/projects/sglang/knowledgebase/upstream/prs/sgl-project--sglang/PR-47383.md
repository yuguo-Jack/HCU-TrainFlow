# [Feat] [NPU] attention: Add native LIM and CopySFA KV offload

[Upstream PR](https://github.com/sgl-project/sglang/pull/47383) · state: open · merged: False

## Original PR description

## Motivation

Add bounded native KV offload for Ascend DSA serving with LIM selection and full-visible CopySFA attention. This follow-up removes unnecessary resident-staging work from long requests without changing the existing Host KV publication or CopySFA resident-refresh path.

## Changes

- Replace history address/mask materialization followed by a generic copy with a native short-history restore operator. Long rows skip the history-position loop using the actual device lengths.
- Fuse current-KV destination calculation, resident-cache writes, and extent commits into one Triton kernel. Historical restoration reads immutable old extents and writes separate next extents before current-KV processing.
- Keep the target's bounded resident-cache policy and the draft worker's native KV policy. Preserve short, long, mixed, padding, request-reuse, and graph-replay behavior.
- Expose the native restore through the lazy `sglang.kernels.ops.kvcache` namespace and add a reproducible manual staging A/B benchmark.

The native operator is supplied by the companion [sgl-kernel-npu PR #909](https://github.com/sgl-project/sgl-kernel-npu/pull/909). The candidate requires a wheel containing `npu::restore_short_kv_history`.

## Validation

- Complete A3 wheel build: exit 0. Native graph/bounds validation: 1 passed. Framework staging validation: 18 passed, covering Q=1/2/3/4/5/8/14 in eager/graph mode, request reuse, physical mapping changes, C-1/C/C+1, invalid indices, padding, and feature tails.
- KV payload and extent checks use independent expected values and exact comparisons (`atol=0`, `rtol=0` or `torch.equal`). These are staging numerical checks, not model-task accuracy results.
- Staging A/B: B16, Q4, C12288, BF16, 576 features, context limit 67584. Both implementations used the same candidate wheel and deterministic input in the same process. Each side used 10 warmups and 30 timed samples. All eight eager/graph cases matched numerically and had lower median latency.
- Long-request staging, int32/first stride 1: eager 554.81 -> 143.67 us; graph 492.55 -> 66.45 us.
- Separate long-request follow-up with int64 metadata and `positions[B,Q][:,0]` first-position stride 4: eager 557.97 -> 160.69 us; graph 487.14 -> 61.95 us. Both cases matched the independent oracle and baseline exactly, exit 0.
- Publication checks include Ruff, Ruff formatting, isort, syntax/whitespace checks, and isolated lazy-registry/argument-forwarding smoke validation. The complete namespace suite was not run in the Windows host environment.

The NPU results were collected on the frozen core implementation before adding the thin in-tree facade and the portable benchmark CLI; the numerical kernel bodies are unchanged. Native NPU tests were run explicitly on A3 rather than inferred from generic PR CI.

## Reproduce the staging benchmark

With the companion kernel wheel installed, place the candidate framework's `python` directory first in `PYTHONPATH`, preserving the existing value. Run `test/manual/kernels/bench_npu_resident_staging.py` with `--baseline` and `--candidate` pointing to the two `npu_kv_residency.py` files, and an `--output` JSON path. Use `--layout int32-stride1` for all eight cases or `--layout int64-stride4` for the long-request follow-up. Redirect stdout/stderr to a persistent log.

The measurements cover `stage_resident_kv`; the required Host KV publication is outside that timed subchain. End-to-end TPOT, serving throughput, and model-task accuracy have not been measured for this update. Analytical TPOT estimates are not presented as benchmark results.
