# [DSv4.1] Add opt-in LiteTopK decode top-512 path for SM100

[Upstream PR](https://github.com/sgl-project/sglang/pull/42351) · state: closed · merged: False

## Original PR description

@DarkSharpness could you take a look at the speedup table below when you have a chance? Thanks to @TKONIY for the collaboration on this work.

## Motivation

DeepSeek-V4.1 selects top-512 index-K slots in its ratio-1/2 index layers during decode and target verify. This PR adds an opt-in SM100 path that produces BF16 scores with an exact per-score histogram, then selects the top-512 physical slots in one LiteTopK selector launch.

Exactness is defined over the BF16 producer's scores. BF16 reduction and rounding can change the selected set relative to the default FP32 producer; this change does not claim identical model outputs or speculative acceptance rates.

## Changes

- Add `Bf16Dsv41DecodeStorage` and `Bf16Dsv41DecodePlan`, with a JIT-compiled BF16 selector under `bf16_exact/`. Outputs are unordered int32 physical slots, padded with `-1`; equal ordered BF16 keys prefer the lower physical slot. The selector clears histogram/candidate scratch for reuse and uses an exact whole-row fallback for stale counts or candidate overflow.
- Route `FullTopKIndexer.topk_decode` and `SparseTableBackend.publish_decode` through this plan when `SGLANG_OPT_DSV41_LITETOPK_DECODE=1`. The flag is off by default. Unsupported devices, missing producer APIs, raw-index consumers and unsupported geometry retain the existing dispatch.
- Build the matching schedule once per forward/ratio from live request IDs and lengths. Decode uses CPU hint 1; target verify uses `spec_info.draft_token_num`. Graph replay updates live metadata, and storage remains alive for captured graphs when later eager calls grow the current allocation.
- Allow candidate-block selection to read BF16 scores and produce FP32 block keys. Add dispatch/storage/metadata unit tests and BF16 selector/serving GPU tests.
- Add a local `bf16_exact/.clang-format` using the existing SGLang JIT rules. This preserves the selector's formatting after removing the standalone FP32 module.

## Dependencies and code sources

Build and install [sgl-project/DeepGEMM #96](https://github.com/sgl-project/DeepGEMM/pull/96). It provides `get_paged_mqa_logits_bf16_metadata` and `fp4_paged_mqa_logits_bf16`, including the histogram-enabled producer and its matching schedule. Producer kernels, bindings and producer tests belong to that PR. Its BF16 arithmetic/core is adapted from [deepseek-ai/DeepGEMM #462](https://github.com/deepseek-ai/DeepGEMM/pull/462), merge `057ca5964aae0879ff2e0eb71ee05a3cb0ba3df7`.

The selector builds on the LiteTopK design in [SGLang #40764](https://github.com/sgl-project/sglang/pull/40764). This BF16 path runs independently of that PR's standalone FP32 module and does not require [DeepGEMM #94](https://github.com/sgl-project/DeepGEMM/pull/94)'s generic FP32 histogram API. Those FP32 files, examples and tests are excluded from this change.

The diff against main is **16 files, +3,435 / −49**: 2,221 added lines in the BF16 implementation/documentation/format configuration, 662 in BF16/serving tests, and 552 in serving/candidate integration. The BF16 selector accounts for 1,820 lines.

## Scope

SM100/B200, MXFP4 Q/KV, H32/D128, 128-slot index-K pages, top-512, CPU hints 1–6 and at most 16,384 score rows. Hints 1–4 use Q4 / three TMEM stages; 5–6 use Q6 / two stages, with histogram XOR swizzle for hint 6. Schedule and producer must receive matching hints, IDs and lengths. Adjacent rows with equal request IDs share page tables and have nondecreasing causal lengths. Prefill keeps its existing path.

Histogram counts every live non-NaN BF16 score once. NaN-free rows are selected exactly by ordered BF16 key, with `+0` above `-0`. Omitting NaNs from the histogram does not guarantee their exclusion from selection: short rows return every live slot, and longer nonfinite rows can take the raw-key fallback. Shared storage is about 70 KiB per row; serial calls reuse it, while concurrent calls need separate storage.

`SGLANG_DEBUG_DSV41_LITETOPK_CHECK[_FILE]` compares selection against the existing top-k on the same BF16 scores widened to FP32. This checks selector behavior, not agreement with the independent default FP32 producer.

## Speed Tests and Profiling


The primary comparison follows #40764: **default SGLang** = unchanged dev FP32 `fp8_fp4_paged_mqa_logits` + `topk_transform_paged_v2`; **this PR** = #96 BF16 `fp4_paged_mqa_logits_bf16(..., histogram=)` + BF16 LiteTopK. Both return physical slots. This ratio includes producer arithmetic, score precision and KV-sharing changes as well as selection.

Separate same-score baselines use the upstream #462 BF16 producer: **naive** copies/masks the live scores, runs BF16 `torch.topk`, converts indices and maps slots; **DeepSelect** runs full-width and causal-max-sliced forms, then maps slots. Best DeepSelect uses the faster variant in each cell. DeepSelect revision: `bfa4507d935f17ebfc3d0f00ff7d3c9a4d0e5c18`.

Cold-cache measurements use NVIDIA B200 (148 SMs), Torch `2.13.0+cu130`, CUDA `13.0`, and PDL enabled. Comparisons within each cell run on the same GPU; n=1–3 use GPU4 and n=4–6 GPU6. The matrix is n=1–6 × B={1,16,64} × L={4096,16384,65536,262144,1048342}: 90 cold cells. B counts requests, R=B×n score rows, and L compressed KV positions.

Inputs are captured DeepSeek-V4.1 layer-20 MXFP4 Q/KV and BF16-rounded head weights, extended to each shape with randomly permuted physical pages and each query row's causal length. The default FP32 producer receives one independent page-table/length row per query, as the serving path does; the paired BF16 producer can reuse KV among adjacent equal request IDs. L is the live context, while score allocation retains the captured ~1M-column maximum window; only live columns are defined.

Each cell uses 80 randomized paired blocks. A 1 GiB buffer is zeroed before every single-call CUDA graph replay to evict the preceding cache contents. The flush is outside the timed span; CUPTI measures each chain from its first kernel start to its last kernel end. Outputs and scratch are reused. Physical-slot mapping, histogram consumption and scratch cleanup are included. Q projection/packing, schedule/plan construction, serving weight conversion and CPU launch overhead are outside this matrix.

Clocks and power settings are unchanged. Idle gates and per-process monitoring reject affected cells with a 10 s / 6 s margin, including their preparation and profiling window. Raw samples, kernel launch signatures, clocks, rejected attempts and source/binary hashes accompany the results.

> ## Scope
> SM100/B200, MXFP4 Q/KV, H32/D128, 128-slot index-K pages, top-512, CPU hints 1–6 and at most 16,384 score rows. Hints 1–4 use Q4 / three TMEM stages; 5–6 use Q6 / two stages, with histogram XOR swizzle for hint 6. Schedule and producer must receive matching hints, IDs and lengths. Adjacent rows with equal request IDs share page tables and have nondecreasing causal lengths. Prefill keeps its existing path.
> 
> Histogram counts every live non-NaN BF16 score once. NaN-free rows are selected exactly by ordered BF16 key, with `+0` above `-0`. Omitting NaNs from the histogram does not guarantee their exclusion from selection: short rows return every live slot, and longer nonfinite rows can take the raw-key fallback. Shared storage is about 70 KiB per row; serial calls reuse it, while concurrent calls need separate storage.
> 
> `SGLANG_DEBUG_DSV41_LITETOPK_CHECK[_FILE]` compares selection against the existing top-k on the same BF16 scores widened to FP32. This checks selector behavior, not agreement with the independent default FP32 producer.

> ## Speed Tests and Profiling
> The primary comparison follows #40764: **default SGLang** = unchanged dev FP32 `fp8_fp4_paged_mqa_logits` + `topk_transform_paged_v2`; **this PR** = #96 BF16 `fp4_paged_mqa_logits_bf16(..., histogram=)` + BF16 LiteTopK. Both return physical slots. This ratio includes producer arithmetic, score precision and KV-sharing changes as well as selection.
> 
> Separate same-score baselines use the upstream #462 BF16 producer: **naive** copies/masks the live scores, runs BF16 `torch.topk`, converts indices and maps slots; **DeepSelect** runs full-width and causal-max-sliced forms, then maps slots. Best DeepSelect uses the faster variant in each cell. DeepSelect revision: `bfa4507d935f17ebfc3d0f00ff7d3c9a4d0e5c18`.
> 
> Cold-cache measurements use NVIDIA B200 (148 SMs), Torch `2.13.0+cu130`, CUDA `13.0`, and PDL enabled. Comparisons within each cell run on the same GPU; n=1–3 use GPU4 and n=4–6 GPU6. The matrix is n=1–6 × B={1,16,64} × L={4096,16384,65536,262144,1048342}: 90 cold cells. B counts requests, R=B×n score rows, and L compressed KV positions.
> 
> Inputs are captured DeepSeek-V4.1 layer-20 MXFP4 Q/KV and BF16-rounded head weights, extended to each shape with randomly permuted physical pages and each query row's causal length. The default FP32 producer receives one independent page-table/length row per query, as the serving path does; the paired BF16 producer can reuse KV among adjacent equal request IDs. L is the live context, while score allocation retains the captured ~1M-column maximum window; only live columns are defined.
> 
> Each cell uses 80 randomized paired blocks. A 1 GiB buffer is zeroed before every single-call CUDA graph replay to evict the preceding cache contents. The flush is outside the timed span; CUPTI measures each chain from its first kernel start to its last kernel end. Outputs and scratch are reused. Physical-slot mapping, histogram consumption and scratch cleanup are included. Q projection/packing, schedule/plan construction, serving weight conversion and CPU launch overhead are outside this matrix.
> 
> Clocks and power settings are unchanged. Idle gates and per-process monitoring reject affected cells with a 10 s / 6 s margin, including their preparation and profiling window. Raw samples, kernel launch signatures, clocks, rejected attempts and source/binary hashes accompany the results.
