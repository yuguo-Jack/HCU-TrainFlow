# [Fix] diffusion: Reject requests and report unhealthy after an unrecoverable device error

[Upstream PR](https://github.com/sgl-project/sglang/pull/45065) · state: open · merged: False

## Original PR description

## Motivation

Fixes #38167.

When a diffusion forward fails with a CUDA error other than OOM (a driver error, a device-side assert, a caching-allocator assert), the device or its allocator can no longer be trusted. The worker logged the error, called `empty_cache()` and kept serving. So every later request either ran on the broken device or failed, and `/health` still returned `{"status": "ok"}`, which means no orchestrator would restart the server.

In #38167 the trigger is PyTorch's expandable-segments allocator: when a driver call fails with a non-OOM status during `ExpandableSegment::map()`, the half-created handles are not released, and every later allocation into that range hits `!handles_.at(i) INTERNAL ASSERT FAILED` (pytorch/pytorch#188008, pytorch/pytorch#166234; the report is on WSL2 with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`). That needs a PyTorch fix. This PR makes the server fail cleanly instead of staying up broken.

## Modifications

- `gpu_worker.py`: classify forward errors that leave the device unusable (`torch.AcceleratorError`, `CUDA driver error:`, `CUDA error:`, `HIP error:`, caching-allocator asserts, also through `__cause__`/`__context__`; anything mentioning "out of memory" is excluded). On the first one, record it, log the restart guidance (with the expandable-segments note), set `OutputBatch.device_unrecoverable`, and skip `empty_cache()`, which raised again from inside the error handler on a broken device. OOM keeps its current recover-and-continue behavior.
- `scheduler.py`: once the worker is flagged, `_handle_generation` rejects generation requests with "Device is in an unrecoverable state after an earlier error (...); restart the server." without running a forward (one reply per request, one per request group). The two dynamic-batch error paths carry the flag through.
- `scheduler_client.py` / `http_server.py`: the async client records the first flagged reply, and `/health` returns 503 `{"status": "unhealthy", "error": ...}` from then on. `/liveness` is unchanged.
- `schedule_batch.py`: new `OutputBatch.device_unrecoverable` field.

Not changed: an over-budget request still fails. It now fails without taking the server down silently. With DP > 1, `/health` goes 503 when any replica is flagged. With multi-rank TP/SP, each rank tracks its own state, so a rank that did not see the error behaves as before.
