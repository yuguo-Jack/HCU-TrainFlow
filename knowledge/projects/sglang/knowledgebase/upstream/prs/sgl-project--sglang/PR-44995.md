# [CI] Docker: reuse Hugging Face kernel download cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/44995) · state: open · merged: False

## Original PR description

## Motivation

Source changes invalidate the final editable-install layer, rerunning `kernels lock` and `kernels download`. The current layer filesystem cannot reuse downloads from its previous execution, even when the required kernel artifacts are unchanged.

## Modifications

- Add a BuildKit cache mount for Hugging Face kernel downloads, separated by target architecture and CUDA version, with `sharing=locked`.
- Set `HF_HOME` only for the editable-install RUN.
- Copy cached downloads to the existing runtime cache location before the RUN ends, because cache-mount contents are not exported in image layers.

The existing metadata resolution, retry behavior, and runtime-stage copy paths remain in place. This is the download-cache subset of a downstream build improvement; it does not add a pinned kernel lock.

## Production build and deployment evidence

The downstream build improvement has successfully produced the image used by our production inference deployment. It includes both kernel metadata pinning and download caching; this PR extracts only the reusable download-cache portion.

On 2026-10-18, read-only checks confirmed the published base image manifest (HTTP 200 and a matching content digest). The deployed Dockerfile and kernel-lock input metadata matched the downstream release by SHA256. The runtime deployment snapshot showed all 14 related service pods Running and Ready with zero restarts.

These results establish a successful downstream build and deployment. The upstream extraction retains online metadata resolution, so it does not claim to fix metadata-fetch timeouts. No matched cold/warm build timing or speedup percentage is claimed.

## Validation

- `git diff --check` passed.
- The changed RUN's shell body passed `sh -n`.
- A local cache-materialization fixture confirmed that `cp -a` preserves Hugging Face-style relative snapshot symlinks and that they resolve after copying.

The shared cache retains older snapshots. Copying it can grow the runtime cache as kernel revisions accumulate; architecture/CUDA-specific cache IDs avoid combining incompatible target caches.

## Related work

#22160 already optimized Docker dependency layering and source-copy placement. This builds on that structure by reusing kernel downloads when the source-sensitive layer must rerun.
