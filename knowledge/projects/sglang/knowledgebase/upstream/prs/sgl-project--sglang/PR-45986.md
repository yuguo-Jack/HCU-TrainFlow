# [Perf] mem_cache: build non-Triton extend bookkeeping on the host

[Upstream PR](https://github.com/sgl-project/sglang/pull/45986) · state: open · merged: False

## Original PR description

## Motivation

On backends where `support_triton(backend)` is False, two pieces of the extend (prefill) bookkeeping issue device ops whose shapes are set by each request's prompt length:

1. `compute_position_torch` (`model_executor/forward_batch_info.py`) builds `torch.cat([torch.arange(p, p + n, device=...) for ...])` on the device, one `arange` per request.
2. The non-Triton branch of `write_cache_indices` (`mem_cache/allocation.py`) loops over requests and calls `req_to_token_pool.write((req_idx, slice(...)), tensor)`: one slice copy per request with a prompt-length-dependent shape, plus four `.item()` calls per request (its own comment pointed this out).

On backends that compile per shape, every new prompt length compiles a new program on the serving path. We hit this on AWS Trainium through the out-of-tree Neuron platform plugin. A compile tracer in the plugin traced the remaining serving-time compiles to exactly these two places:

- `aten::copy_((2048,))` and `aten::copy_((1314,))` from `ReqToTokenPool.write` <- `write_cache_indices` <- `alloc_for_extend` <- `prepare_for_extend`
- `aten::cat` and `aten::arange.start_out` from `compute_position_torch` <- `compute_position` <- `ForwardBatch.init_new`

The plugin currently monkeypatches both functions. This PR moves the fix upstream in a backend-neutral form, so other non-Triton backends also get a constant number of device ops per batch in place of O(batch size).

## Modifications

- **`compute_position`** takes two new optional arguments, `extend_prefix_lens_cpu` and `extend_seq_lens_cpu`. On the non-Triton branch, when both are given, the new `compute_position_host` builds `positions` and `extend_start_loc` on the CPU with a vectorized ragged arange (`arange(total) + repeat_interleave(prefix - start, lens)`). It then copies each result to the device once (pinned memory and `non_blocking` when available). Output dtypes are unchanged: `positions` is int64 and `extend_start_loc` keeps the dtype of `extend_seq_lens`. Without the mirrors, it falls back to the old `compute_position_torch`, which is left in place.
  - Call sites that pass the mirrors: `ForwardBatch.init_new`, using the `ret.extend_{prefix,seq}_lens_cpu` it already fills from the host lists, and the TBO child split, using `child_b.extend_{prefix,seq}_lens_cpu`. In the `gpu_only` path these mirrors are `None`, so that path keeps the old behavior. The DFlash and DSpark callers are unchanged.
- **`write_cache_indices`**: the non-Triton branch now calls the new `write_cache_indices_torch`. That function builds the flat destination indices (`row * width + col`, every prefix first and then every extend range) on the host from the CPU mirrors `alloc_for_extend` already passes (`req_pool_indices_cpu`, `prefix_lens_cpu`, `extend_lens_cpu`). It copies those indices to the device once and does a single `req_to_token.view(-1).index_put_((idx,), cat(prefixes..., out_cache_loc))`. `out_cache_loc` is already the request-order concatenation of the extend slots, so the values need no device-side reordering. Values are moved to the table's device first, so a host-resident `req_to_token` with device-resident slots still works (the old slice assignment tolerated that). `index_put_` rather than `index_copy_` because it is the op more backends lower to a dynamic-shape scatter (torch-neuronx lists `_index_put_impl_` among its dynamic NKI kernels). Empty prefixes are skipped, which includes the CPU `_EMPTY_PREFIX` placeholder. Nothing is read back from the device.
- **No shape bucketing.** The total-token-count shape of the single copy is still dynamic. Padding it to fixed buckets needs a backend-specific scratch cell to absorb the padding writes, so that stays in the platform plugin. Upstream only removes the per-request, per-prompt-length ops.
- **Triton paths (`compute_position_triton`, `write_req_to_token_pool_triton`) are untouched.**

## Accuracy Tests

This change only reorganizes bookkeeping. The new code writes the same positions, start offsets and `req_to_token` contents as the per-request code it replaces.

New `test/registered/unit/mem_cache/test_host_extend_bookkeeping.py` (registered with `register_cpu_ci`):
- `compute_position_host` against `compute_position_torch` for several `(prefix, extend)` cases: zero prefix, a single request, several requests with mixed prefixes, a zero-length extend inside a batch, and int32 and int64 length dtypes. It checks both values and dtypes.
- `compute_position(... "torch_native", ..., prefix_cpu, seq_cpu)` dispatches to the host path, and without the mirrors it still falls back to the torch path.
- `write_cache_indices_torch`, and the public `write_cache_indices` with a non-Triton prefill backend, against a copy of the old per-request writer on a real `ReqToTokenPool`. The cases cover no prefix, prefix greater than 0 (so `prefix_tensors` are written), several requests with mixed prefixes on non-contiguous rows, a full row, and a request with zero extend. The table starts filled with `-1` so any stray write shows up.
- A host-resident table with `out_cache_loc` and prefixes on an accelerator. It runs when CUDA or MPS is present and is skipped on CPU-only CI. Without the `.to(device)` on `out_cache_loc` it fails (segfault on MPS, device-mismatch error on CUDA).

## Speed Tests and Profiling

There is no change on Triton backends, since the code there is untouched. On non-Triton backends, the extend bookkeeping now issues a constant number of device ops per batch (two H2D copies for positions, one H2D copy, one cat and one `index_put_` for `req_to_token`) where it used to issue O(batch size) ops shaped by prompt length. The per-request `.item()` calls are also gone. On Trainium (GLM-5.2, TP64), the same approach as an out-of-tree patch removed every serving-time compile that the tracer attributed to these two call sites.
