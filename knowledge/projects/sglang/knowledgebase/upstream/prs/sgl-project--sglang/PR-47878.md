# [Perf] attention: Run dense causal prefill when QSA block selection is exhaustive

[Upstream PR](https://github.com/sgl-project/sglang/pull/47878) · state: open · merged: False

## Original PR description

## Motivation

A QSA indexer keeps `block_topk = indexer_budget / indexer_compress_ratio` compressed
blocks per query row, and prefill attention then runs over the selected blocks plus each
row's causal remainder. A query at logical position `p` has `(p + 1) // compress_ratio`
complete blocks behind it, so **once a request is no longer than
`block_topk * compress_ratio` tokens, every candidate block fits the budget and top-k
keeps all of them** — `qsa_fast_topk` returns `min(candidates, topk)` entries. The
attended key set is then every complete block plus the `0 .. compress_ratio - 1` token
remainder, which is exactly the full causal prefix.

On that input the sparse pipeline is doing dense causal attention the expensive way: it
scores and gathers a selection that is already complete, then walks a fixed
`budget`-wide inner loop that the causal mask would have halved. For the shipped Qwen4-Exp
profile (`indexer_budget=2048`, `indexer_compress_ratio=4`) this covers every request up
to 2048 tokens, which includes most short requests and every prefix-cache hit that lands
under the budget.

This PR detects that condition from host metadata and runs dense causal attention
instead. The selection math is unchanged for anything longer, and the indexer still
writes its compressed-K and RoPE buffers, so decode's sparse selection is untouched.

## Relationship to #37570

This PR does **not** depend on #37570 and does not block it.

- **CUDA:** no interaction. Every change #37570 makes to `qsa_fast_topk`,
  `expand_qsa_block_indices` and `QSAIndexer` is behind an `if _is_npu:` branch, and its
  `forward_extend` change is `if not q.is_cuda:` → `if _is_npu or not q.is_cuda:`. The
  dense path added here runs before all of it.
- **Textual overlap:** one hunk. The call added to `forward_extend` sits immediately above
  the line #37570 rewrites, so whichever lands second needs a one-line rebase.
- **NPU, once #37570 lands:** eligible batches would reach this dense path before
  `_npu_sparse_attention`. That is where the measured win comes from, but it also means the
  equivalence argument then rests on `sgl_kernel_npu`'s `fast_topk` and `expand_blocks`
  honoring the contract #37570's docstring states, namely that all candidates are kept when
  `candidates <= topk`. `SGLANG_QSA_ASSERT_DENSE_PREFILL=1` is the check for that, and
  `_dense_prefill_keys` returns `None` for the rank-4 paged and FIA cache layouts
  #37570's `_flatten_qsa_kv_cache` describes, so the dense path stays off those pools
  until someone adapts it deliberately.

## Modifications

- New `python/sglang/srt/layers/attention/qsa/dense_prefill.py` holding the rule and the
  device-agnostic pieces:
  - `exhaustive_prefill_budget(profile)` — `block_topk * compress_ratio`, `0` when there
    is no QSA profile.
  - `is_prefill_selection_exhaustive(...)` — host-only predicate. It rejects the **whole
    batch** unless every request qualifies, so a batch is never half dense, and it
    rejects batches whose `extend_seq_lens` do not sum to the query row count (DP padding
    and speculative layouts stay on the sparse path).
  - `dense_causal_prefill_reference(...)` — varlen dense causal GQA for the non-CUDA
    backend, bottom-right aligned to match `flash_attn_varlen_func(causal=True)`.
  - `gather_packed_sequence_kv(...)` — device-agnostic counterpart of
    `pack_qsa_prefill_kv`, which keeps the CUDA path.
  - `visible_prefix_counts(...)` + `assert_prefill_selection_exhaustive(...)` — the debug
    assertion described below.
- `qwen_sparse_attn_backend.py`:
  - `__init__` computes `_dense_prefill_budget` and `_assert_dense_prefill` once, so the
    forward pass does no per-layer config work.
  - `_try_dense_causal_prefill(...)` returns `None` for anything not provably exhaustive,
    which leaves the existing code path byte-for-byte unchanged.
  - `_dense_prefill_keys(...)` reuses `pack_qsa_prefill_kv` on CUDA and the torch gather
    elsewhere.
  - `forward_extend` gains a seven-line call ahead of the sparse dispatch.

Kill switches, both read once at construction:

| Variable | Effect |
|---|---|
| `SGLANG_QSA_DISABLE_DENSE_PREFILL=1` | Disables the dense path; the sparse pipeline runs as before. |
| `SGLANG_QSA_ASSERT_DENSE_PREFILL=1` | Per-row assertion naming the offending row. Reads the comparison back, so it is a debug switch, not a default. |

The default path adds **no** device-to-host read: eligibility comes from
`extend_seq_lens_cpu` / `seq_lens_cpu`, which the backend already consumes.

### What the dense path deliberately refuses

Each of these keeps the existing sparse path, because the dense path would otherwise make
a claim this PR cannot support:

- **Batch-invariant (deterministic) mode.** The QSA top-k and attention kernels have
  batch-invariant variants; FA varlen does not. `is_batch_invariant_mode_enabled()`
  short-circuits the dense path rather than silently breaking determinism.
- **SM121 and ROCm.** `_resolve_flash_attn_varlen_func` returns `qwen38_qsa_sm121_varlen`
  on SM121 and aiter's CK varlen on ROCm. Both are sparse-*decode* kernels, never
  exercised over dense full-length K/V at prefill row counts. The dense path uses a
  narrower resolver, `_resolve_dense_prefill_varlen_func`, which returns `None` on those
  platforms and when `flash_attn` is absent, so prefill keeps the sparse Triton kernels
  there instead of routing through something unvalidated.
- **Rank-4 KV caches.** Paged and FIA pools expose rank-4 caches that need a layout
  adapter before a physical-slot gather means anything, so `_dense_prefill_keys` returns
  `None` for them.
- **fp32 queries**, and any batch whose `extend_seq_lens` do not sum to the query row
  count (DP padding, speculative layouts).

### The one invariant checked by default

The dense path ignores `topk_indices` and recomputes the full causal prefix. If a top-k
kernel ever stopped keeping all candidates, the dense result would stay mathematically
correct while longer requests and every decode step used the sparse selection: a quiet
inconsistency rather than an error. To close that without a hot-path synchronization, the
CUDA branch asserts

```python
torch._assert_async((topk_indices >= 0).sum() == total_visible_tokens(...))
```

This is sound and complete, not a heuristic: a row's selected entries are distinct and
causal, so each row contributes at most its own prefix size, and the batch total is
reachable only when every row is covered exactly. One device reduction, no host read,
following the `torch._assert_async` pattern already used in `_qsa_write_plan`. It stays
off on non-CUDA devices, where `_assert_async` falls back to a CPU check and synchronizes.

## Accuracy Tests

New `test/registered/unit/layers/attention/test_qsa_dense_prefill.py`, 10 cases, 1.9 s on
CPU, registered to `base-a-test-cpu`. It does not mock the selector: it drives the real
`qsa_fast_topk` and `torch_expand_qsa_block_indices` from `qsa/kernel.py`, so if the
selection semantics ever change the test fails rather than the runtime going quietly
wrong.

- `test_selection_covers_the_causal_prefix_within_budget` — for sequence lengths
  1, 2, 3, 4, 5, 7, 8, `budget-1`, `budget`, the selected token set of **every row**
  equals `{0 .. p}`. This is the equivalence claim, checked against upstream's own code.
- `test_selection_is_incomplete_past_the_budget` — at `budget + ratio` the last row no
  longer covers its prefix, so the boundary is tight and not merely conservative.
- `test_guard_accepts_exactly_the_provable_cases` — ten eligibility cases including
  `budget` vs `budget + 1`, a mixed batch where one request is too long, continuation
  chunks, DP padding, empty and decode-shaped batches, and malformed metadata.
- `test_dense_matches_sparse_for_a_full_chunk` and
  `test_dense_matches_sparse_for_a_continuation_chunk` (extend lengths 1, 3, 4, 16 inside
  a `budget`-token sequence) — dense output matches
  `qsa_sparse_attention_reference` over the real selection to `rtol=atol=1e-5` in fp32.
- `test_dense_handles_a_multi_request_batch` — per-request varlen packing, each request
  checked against the sparse reference.
- `test_assertion_rejects_an_under_selected_row` — the debug assertion names the offending
  row when a selection is damaged.
- `test_packed_gather_matches_a_slot_by_slot_gather`, `test_budget_comes_from_the_profile`,
  `test_disabled_budget_never_takes_the_dense_path`.

**Scope of what the test proves.** It drives the reference implementations inside
`qsa_fast_topk` and `expand_qsa_block_indices`. The production CUDA kernels behind the
same two entry points (`sglang.kernels.ops.attention.fast_topk` and `sgl_kernel`'s
`fast_topk_v2`) are assumed to honor the same contract: when a row has no more candidates
than `topk`, all of them are kept. That is what a correct top-k does and what the
fixed-width `-1`-padded output implies, but this PR adds no kernel-level test for it. The
default-on `torch._assert_async` above is what actually holds those kernels to it at
runtime.

End-to-end evidence from a prototype of the same rule (see the caveat in the next
section): 22/22 prompts and 176/176 generated tokens identical to the sparse path, with
`max_abs_logprob_delta = 1.95e-3`.

## Speed Tests and Profiling

**There is no benchmark of this patch on any upstream-supported platform. That is the
reason this is a draft, and it is the main thing I need help with.** The numbers below are
from a prototype that applied the same rule through a vendor-local NPU prefill module.
They are what motivated the change. They are not a measurement of the code under review,
and the `[Perf]` title is a statement of intent until someone replaces them.

Platform: Ascend 910, 2 chips, TP2, 24 layers, **dummy weights**, CANN 9.1,
torch_npu 2.10, chunked prefill 16384.

Device trace, rank0, per 2048 input tokens:

| Stage | Baseline | With dense prefill | Delta |
|---|---:|---:|---:|
| QSA sparse pipeline | 26.63 ms | 0.00 ms | −26.63 |
| Dense causal attention | 0.00 ms | 1.02 ms | +1.02 |
| **Total attention** | **26.63 ms** | **1.02 ms** | **−25.61** |

−25.61 ms against a 169.90 ms baseline compute budget, i.e. 15.1% of total device compute.
Isolated throughput ablation at that step: 13,618 → 15,213 input tok/s (+11.7%, single
round of 128 requests at concurrency 32, roughly ±1% noise).

Single-operator check: `torch_npu.npu_fusion_attention` (BSH, `sparse_mode=3`) at
1024×12×256 costs 89.2 µs and lands `relative_l2 = 2.12e-3` against an fp32 dense causal
reference.

**Not yet measured, and the reason this is a draft:**

1. **No CUDA benchmark.** The win should carry over — FA2 varlen with `causal=True` does
   half the score work of a fully selected sparse row and skips the gather — but I have no
   NVIDIA numbers. If a reviewer with a Qwen4-Exp CUDA setup can run a prefill sweep, I
   will fold the results in; otherwise I will get access to a card first.
2. **Continuation chunks are unit-tested, not benchmarked.** Every NPU number above was
   taken with `prefix_len == 0`. The bottom-right causal alignment for `prefix_len > 0` is
   covered by `test_dense_matches_sparse_for_a_continuation_chunk`, which is why that case
   is in the patch rather than excluded, but it has no end-to-end timing.
4. **SM121 and ROCm are excluded on purpose**, see above. If a maintainer confirms
   `qwen38_qsa_sm121_varlen` and aiter's CK varlen are safe over dense full-length K/V,
   widening the resolver is a one-line follow-up.
3. **Dummy weights only.** Token-identity against the sparse path is the strongest
   accuracy claim here; there is no real-weight eval.

One implementation note worth recording, because the first version of this check was
silently wrong: an earlier exhaustiveness check used `scatter_` with invalid slots clamped
to index 0. `scatter_` with duplicate indices is last-write-wins, so a clamped invalid slot
erased a real hit and the check reported a complete selection as incomplete. The version
here counts valid entries per row instead, which is sound because a row's entries are
distinct and causal: complete blocks do not overlap, and the remainder only covers the
incomplete block, which is never a top-k candidate.

## Review and Merge Process

Opening as a **draft**, because the fast path has no benchmark on a platform upstream
actually ships. Three questions:

1. **Can someone with a Qwen4-Exp CUDA setup run a prefill sweep?** That is the one thing
   blocking this. If the dense path does not win on CUDA, the right outcome is to close
   this and keep the rule as an NPU-side change instead.
2. Is the equivalence argument acceptable as stated, given that the attended key set is
   identical and only the summation order differs? The alternative is to default the dense
   path off and make it opt-in, which I am happy to do.
3. Would you rather the eligibility predicate derive its bound on device from
   `row_ends - row_starts` instead of from `seq_lens_cpu`? That is strictly more robust if
   the metadata construction changes, at the cost of one device-to-host read per layer.
   The current version keeps the hot path synchronization-free and leans on the unit test
   plus the default-on `_assert_async` to catch a drift.
