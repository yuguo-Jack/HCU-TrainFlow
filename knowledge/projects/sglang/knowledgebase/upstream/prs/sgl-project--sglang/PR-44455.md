# [Perf] [AMD] lm_head: Use aiter tgemm for the bf16 lm_head on gfx1250

[Upstream PR](https://github.com/sgl-project/sglang/pull/44455) · state: closed · merged: True

## Original PR description

## Motivation

On gfx1250 the unquantized bf16 lm_head goes through `torch.matmul`, which lands on hipBLASLt and is several times slower than aiter's GEMM at decode batch sizes.

## Modifications

With `SGLANG_USE_AITER=1` on gfx1250, a 2D bf16 lm_head matmul uses `aiter.tuned_gemm.tgemm.mm`, as `unquant.py` already does for linear layers on HIP. Other dtypes, shapes and devices keep the existing path. A CPU unit test covers the gate.

## Setup

Kimi-K2-Thinking-MXFP4, TP8, MI455X (gfx1250), image `rocm/sgl-dev:v0.5.22-rocm10-mi45x-20261019` with sglang 36978d6c4d and aiter 2bb549102 plus Kimi-K2 GEMM configs.

Server: `--tp 8 --attention-backend aiter --prefill-attention-backend aiter --decode-attention-backend aiter --page-size 64 --kv-cache-dtype fp8_e4m3 --disable-radix-cache --disable-custom-all-reduce --chunked-prefill-size 8192 --cuda-graph-max-bs-decode 128 --max-running-requests 128 --mem-fraction-static 0.8`.

## Accuracy Tests

The lm_head output is bit-identical to `torch.mm` at batch sizes 1, 4, 32 and 128.

GSM8K with `few_shot_gsm8k` (8-shot, 1319 questions, `max_new_tokens` 512, the settings of sglang's AMD Kimi accuracy tests):

| | Accuracy | Invalid |
|---|---|---|
| Before (two runs) | 0.939 / 0.945 | 0.000 / 0.000 |
| After | 0.944 | 0.000 |

## Speed Tests and Profiling

lm_head of Kimi-K2 at TP8 (vocab shard 20480 x 7168, 293 MB of weights, far larger than L2), MI455X, CUDA-graph replay:

| batch | torch.mm (ms) | tgemm.mm (ms) |
|---|---|---|
| 1 | 0.131 | 0.070 |
| 4 | 0.129 | 0.062 |
| 32 | 0.285 | 0.074 |
| 128 | 0.986 | 0.232 |

End to end, TP8, 8k input / 1k output, concurrency 4, `bench_serving`:

| | Output tok/s | Median TTFT (ms) | Median TPOT (ms) |
|---|---|---|---|
| Before | 137.42 | 414.54 | 27.90 |
| After | 142.08 (+3.4%) | 414.09 | 26.92 (-3.5%) |

At batch 4 the kernel saves about 0.07 ms per decode step, so most of the end-to-end difference is run-to-run variance (the two before runs differ by 2.1%); the saving grows with batch size (0.75 ms per step at batch 128).
