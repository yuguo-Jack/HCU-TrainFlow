# Pass uniform_q_len to the FlashInfer target-verify plan for EAGLE speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/44115) · state: open · merged: False

## Original PR description

## Motivation

EAGLE target verify gives every request exactly `num_tokens_per_req` (= `draft_token_num`) query rows: `EagleVerifyInput` builds `qo_indptr` as a constant-stride arange. FlashInfer's FA2 CUDA-graph planner cannot see that from the ragged CSR alone, so it sizes its query tile for the worst case (`total_rows - bs + 1` rows per request). For a typical verify batch (32 q-heads, TP8, 4 draft tokens) that means running a 64-row tile on a 16-packed-row problem.

[flashinfer-ai/flashinfer#6144](https://github.com/flashinfer-ai/flashinfer/pull/6144) added a `uniform_q_len` keyword to `BatchPrefillWithPagedKVCacheWrapper.plan()`: a host-side promise that every request has exactly that many query rows, letting the planner size the tile for `uniform_q_len * gqa_group_size` packed rows. The same hint is the dispatch key for FlashInfer's specialized SM90 fp8-KV verify kernel from that PR.

## Modifications

One wiring change in `flashinfer_backend.py`: `call_begin_forward` adds `uniform_q_len=num_tokens_per_req` to the paged plan kwargs for EAGLE verify batches (`SpecInputType.EAGLE_VERIFY`; DFLASH / NGRAM verify and draft extends keep the stock plan).

Capture fixes the verify kernel's query tile from the hint, so every plan through a captured verify wrapper must carry the same hint: the hint is passed on both plan paths, the real `plan()` and the `SGLANG_OPT_FLASHINFER_VERIFY_HOST_PLAN` sync-free replay (`fast_prefill_plan`, which previously pinned the argument to 0).

**Requires the FlashInfer >= 0.7.2.post1 pin (#46926), the first release with the `plan(uniform_q_len=...)` keyword; this PR should land after it.** An earlier revision carried an `inspect.signature` capability probe to tolerate older FlashInfer; per review it is dropped.

Adds a CPU unit test for the gating (only EAGLE verify batches are hinted, unset `num_tokens_per_req` is not a promise).

## Benchmarks

Qwen3.5-397B-A17B-FP8, TP8/EP8 on 8x H200, EAGLE (`steps 3 / topk 1 / draft 4`), 256k-context agentic workload at 10 concurrent sessions, 1 h steady state per arm. Reported metric: **normalized interactivity** (output tokens/s per request over each request's own decode, so it isolates decode speed from TTFT and queueing). Each arm is compared against a production run of the same day on the same hardware; cross-day control drift was 1.8% at p50 and 3.7% at p90.

| configuration | p50 | p90 |
|---|---|---|
| baseline (no hint, same-day control per arm) | 113.5 / 115.5 tok/s | 63.6 / 65.9 tok/s |
| `uniform_q_len` hint (planner tile only) | 130.5 tok/s (**+15.0%**) | 71.0 tok/s (**+11.6%**) |
| hint + FlashInfer's SM90 fp8-KV verify kernel (dispatches behind the same hint) | 136.1 tok/s (**+17.8%**) | 73.6 tok/s (**+11.7%**) |

Corresponding ITL p50: −15.0% and −19.4%. Output tok/s +6%, accept length unchanged (3.30 vs 3.28), output lengths unchanged, GSM8K accuracy at parity (197 vs 196 / 200 correct, paired).

**Issue**

The docstring says a wrong hint "degrades to the stock plan rather than failing". That is true for one plan, but not for a CUDA-graph wrapper. FlashInfer fixes `CTA_TILE_Q` and the grid size from `plan_info` at capture (`DISPATCH_CTA_TILE_Q` in `csrc/batch_prefill.cu`). If the hint holds at capture and is dropped at a later replay, the replay plan's tiles no longer match the captured kernel. EAGLE verify keeps the same stride at capture and replay today, so this is not a live bug, but the comment points future callers at an unsafe fallback.

**Fix**

Replace the four-line docstring with one line that states the contract, for example: `# Every plan through a captured verify wrapper must have the same per-request q length.`

**Issue**

On current main, EAGLE verify graph replays use `fast_prefill_plan` when `SGLANG_OPT_FLASHINFER_VERIFY_HOST_PLAN=1` (#44518, #45082). Capture calls the real `plan()` with `uniform_q_len=N`, but replay skips this branch, and `fast_prefill_plan` passes a hard-coded `0`. So the replay plan does not match the captured kernel. FlashInfer 0.7.2.post1 has the keyword, and #46926 bumps main to it. The comment above is also out of date.

**Example**

Llama-3.1-8B, TP1, H100, 4 draft tokens, graph bs=40: capture plans 16-row tiles and `padded_batch_size=40`; replay plans 128-row tiles and 44. The workspace index arrays move, but the captured kernel reads the old offsets.

**Fix**

Add a `uniform_q_len` argument to `fast_prefill_plan` and pass it instead of `0`. Compute the hint before the `uses_fast_prefill` check and pass it on both paths.
