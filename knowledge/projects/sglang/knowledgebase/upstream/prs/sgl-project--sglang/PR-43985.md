# [AMD][DI][CI] kimik26 2p1d-ep16: capture CUDA graph on decode (eager decode is slow)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43985) · state: closed · merged: True

## Original PR description

## What
In the two kimik26 `2p1d-ep16` recipes, replace `--disable-cuda-graph` on decode with `--cuda-graph-bs-decode 1..64` (`1..128` for `-mtp`).

For `-mtp`, the decode MORI settings also change, from 64 / 332 / 128 to 512 / 2048 / 1024. These are the values the dsv4pro and glm52 `-mtp` recipes use: capture needs batch size x 4 draft tokens to stay within the dispatch limit. The comment in the `-mtp` recipe that said to revisit CUDA graph once the test is green is updated.

## Why
Both tests are green but slow, about 1 h 20 min (plain) and 40 min (`-mtp`) a night, because decode runs eagerly.

This changes what the tests measure: throughput will be higher than the eager baseline.

## Validation
On pit2 (4 nodes), main `6a7abcf`, same image as the nightly. Each run once. Decode logs show `cuda graph: True`, no capture errors, no timeouts, 7 of 7 result files.
- plain: 25 min, GSM8K 0.936.
- `-mtp`: 18 min, GSM8K 0.934.
