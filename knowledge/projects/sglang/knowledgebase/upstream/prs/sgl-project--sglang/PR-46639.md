# [Perf] speculative: Rotate multi-layer EAGLE prefill input_ids 4096 ids per trip, not 8

[Upstream PR](https://github.com/sgl-project/sglang/pull/46639) · state: closed · merged: True

## Original PR description

## Motivation

In short: `rotate_input_ids` shifts each request's `input_ids` left by one in place for the multi-layer EAGLE draft. On the prefill path it moves only 8 ids per loop trip, so a 16384-token chunk takes 2048 serial trips with two CTA barriers each. This PR uses the 4096-id block that the decode path already uses. The output is bit-identical. On an H100 PCIe one prefill call goes from 824 to 6.4 us at 16384 tokens, and inside a server from 763 to 6.0 us per launch.

Details:

`rotate_input_ids` (`python/sglang/kernels/ops/speculative/multi_layer_eagle.py`) runs one program per request. Each loop trip loads `BLOCK_SIZE` ids, hits `tl.debug_barrier()`, stores them one slot to the left, and hits a second barrier. The launcher picks `BLOCK_SIZE = 4096 if select_index is not None else 8`. `select_index` is set on the decode calls and is `None` on the prefill calls, so prefill gets 8. Both values came in with the day-0 MiMo-V2-Flash support in #15207, with no stated reason for 8.

In `multi_layer_eagle_worker_v2.py` the prefill draft extend calls it once before the first draft step and once after every step, so a prefill chunk pays `speculative_num_steps + 1` calls. Each call takes `max request length / 8` trips. Measured on an H100 PCIe that is about 0.40 us per trip, so 0.82 ms per call at 16384 tokens and 1.65 ms at 32768.

Recipes that reach it, from the cookbook (MTP on, which sets `--enable-multi-layer-eagle`). The chunk is per attention-DP rank, since DP attention divides `--chunked-prefill-size` by `--attn-dp-size`:

| recipe | prefill chunk per rank | draft steps | calls per chunk |
|---|---|---|---|
| MiMo-V2-Flash (DP 2 by default) | 8192 | 3 | 4 |
| MiMo-V2.5 | 8192 on Hopper (DP 2), 16384 on Blackwell; V2.5-Pro 16384 | 3 | 4 |
| Step-5-Preview | 16384 (8192 in the DP 2 rows) | 3 | 4 |
| Step-3.5, Step-3.7-Flash (MTP opt-in) | default: 8192 on H200, 16384 on B200 and MI300-class | 3 | 4 |
| Inkling, Inkling-Small | default: 8192 on H200, 16384 on B200/B300 | 8 | 9 |

## Modifications

In short: `BLOCK_SIZE = 4096` for both paths. One line, plus a test.

Why any block size gives the same bytes: each trip reads `[off + 1, off + B + 1)` and writes `[off, off + B)`. All loads of a trip complete before the barrier, and the stores come after it. The next trip reads only ids past every slot written so far. So no trip reads an id that an earlier store overwrote, for any `B`. (The decode path already uses 4096, but its windows are 4-9 ids, so it never runs more than one trip.)

`num_warps` stays at the default 4. I swept `BLOCK_SIZE` 1024-8192 x `num_warps` 4/8/16. 8192 x 16 warps is 1.1-2.4 us faster for one request of 16384-32768 tokens (5.31 vs 6.40 us at 16384, 9.02 vs 11.39 us at 32768), which is small next to the 0.8-1.6 ms saved. So I kept the decode path's 4096 x 4 and left one config for both paths.

New test `TestRotateInputIds.test_in_place_shift_across_blocks` in `test_boundary_kv_fix_kernels.py` (the GPU test file for the multi-layer EAGLE kernels; there was no GPU test for this kernel). It compares against a torch reference for one batch with request lengths 0, 1, 2, 4095, 4096, 4097 and 8197: 4097 shifts exactly one full block, and 8197 runs three trips, so later trips must read ids that earlier trips did not overwrite. Sentinel slots between requests catch writes outside a request's window. It runs with `select_index` `None` and set.

Not a duplicate: no open PR changes this kernel. #46385 moves draft-proposal sampling into the per-step draft-extend graphs and patches in a Python reference of the rotate for its unit test; it does not touch the Triton kernel. #43052 changes the draft-extend buffer prep kernel in the same file, not `rotate_input_ids`.

## Accuracy Tests

The output is bit-identical to main, so model accuracy can't change. Checked at the kernel level and in a server:

- Bitwise vs main 9f6678aa3d, CPU-seeded inputs, whole `input_ids` buffer hashed: **192 of 192 identical**. Lengths 1-32768 (including 7, 8, 9 and 4095, 4096, 4097), with 1, 4 or 32 requests, or a random split with an empty and a 1-id request; int32 and int64 index tensors; `select_index` `None` and set. All 192 also match a torch reference.
- Every swept `BLOCK_SIZE` x `num_warps` config vs `BLOCK_SIZE` 8 on the same 192 cases: 2304 of 2304 identical.
- `test_boundary_kv_fix_kernels.py`: 2 passed (6 subtests). I checked the new test fails on 5 broken kernels (mask `<=`, a short loop bound, a write for an empty request, `select_index` ignored, read offset +2).
- Registers: 113 per thread at 4096 x 4 warps, 0 spills.
- In a server: `thinkingmachines/Inkling` revision `test` (the 4.4 GB checkpoint with 2 MTP heads from `TestUnifiedHybridMTPBitExact`), its server args (deterministic inference, `--enable-multi-layer-eagle`, 2 steps, `--chunked-prefill-size 16384`). 6 greedy prompts of 7 to 25206 tokens, 64 new tokens: output ids and `spec_accept_length` identical on 6 of 6.

## Speed Tests and Profiling

H100 PCIe (350 W limit, 310 W default), driver 595.71, torch 2.14.1+cu130, triton 3.8.0, main 9f6678aa3d. `sglang.kernels.jit.benchmark.marker.do_bench` (CUDA graph, `input_ids` copies rotated so L2 is cold), median of 3 rounds that interleave all configs in one process. "main" is the same kernel launched with `BLOCK_SIZE=8`, the only difference in the diff. Contiguous requests, int32 index tensors.

| prefill shape | main | this PR | speedup |
|---|---:|---:|---:|
| 1024 tokens, 1 request | 52.56 us | 2.17 us | 24x |
| 4096 tokens, 1 request | 207.02 us | 2.60 us | 80x |
| 8192 tokens, 1 request | 412.52 us | 3.86 us | 107x |
| 16384 tokens, 1 request | 824.10 us | 6.40 us | 129x |
| 16384 tokens, 4 requests | 213.70 us | 2.82 us | 76x |
| 16384 tokens, 32 requests | 31.51 us | 2.42 us | 13x |
| 32768 tokens, 1 request | 1646.03 us | 11.39 us | 145x |

Over 18 prefill shapes (1024-32768 tokens, 1, 4 or 32 requests): geomean 23.3x, range 1.44x (1024 tokens in 32 requests) to 145x. The decode calls run the same 4096 x 4 config on main and this PR (2.29-2.78 us at batch 1-256, width 4 and 9).

When one request fills the chunk, that is 0.41 ms saved per call at 8192 tokens and 0.82 ms at 16384. Per chunk:

| chunk per rank | 3 draft steps (4 calls) | 8 draft steps (9 calls) |
|---|---:|---:|
| 8192 | 1.6 ms | 3.7 ms |
| 16384 | 3.3 ms | 7.4 ms |

These are H100 PCIe per-call times x calls per chunk, not measured on those models.

In a server, same Inkling test checkpoint and args as above, torch profiler over 8 requests of 16000 input tokens: 24 `rotate_input_ids_kernel` launches (8 chunks x 3 calls), median 763 -> 6.0 us per launch, total 18.09 -> 0.14 ms, 4.15% -> 0.03% of GPU kernel time. This checkpoint is small, so I expect that share to be lower on the full models. The per-launch time depends on the GPU and the longest request in the chunk, not on the model weights.

`sglang.benchmark.serving`, random 16000 in / 1 out, 64 prompts, request rate inf, 3 interleaved rounds:

| round | main input tok/s | this PR input tok/s |
|---|---:|---:|
| 1 | 269588 | 294714 |
| 2 | 286508 | 292351 |
| 3 | 285938 | 295081 |

Rounds 2-3: 286.2k -> 293.7k tok/s (+2.6%). All rounds: 280.7k -> 294.0k (+4.8%). Main round 1 was the first server launch on the box (240 s to start vs 50 s for the others), which is why I quote rounds 2-3.

Not tested: NPU. The Ascend MiMo recipes run this Triton kernel too, and the decode calls in the same worker already use 4096 there.
