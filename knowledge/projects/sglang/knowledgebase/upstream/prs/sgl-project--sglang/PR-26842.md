# fix(gateway): clean up stale service discovery workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/26842) · state: closed · merged: False

## Original PR description

## Motivation

Kubernetes service discovery can leave stale workers in the gateway registry when a previously registered pod is later reported with different pod metadata, or when it no longer matches the configured discovery selectors.

One concrete production-style case is PD disaggregation deployed with LeaderWorkerSet:

1. The router discovers the LWS leader pod and registers its pod IP as a prefill/decode worker.
2. The LWS group restarts or is rescheduled, and the leader/worker roles or labels change.
3. The old worker URL can remain reachable and may still pass the router's `/health` probe, but the pod no longer satisfies the service discovery selector that originally made it a routable worker.
4. Because service discovery does not deregister that old entry, routing policies can continue selecting the stale URL and send requests to the wrong pod.

This is a correctness bug: router health checks only tell us whether an HTTP endpoint is alive, not whether the Kubernetes pod is still part of the discovered worker set.

This PR supersedes the stale cleanup issue described in #22019 and adds coverage for an additional removal failure caused by matching the full `PodInfo` value.

## Root cause

There were two related failure modes.

### 1. Selector mismatch events were dropped too early

The watcher filtered pod events before they reached the reconciliation handler:

```rust
if PodInfo::should_include(&pod, &config_inner) {
    Some(Ok(pod))
} else {
    None
}
```

If a tracked pod later stopped matching `--selector`, `--prefill-selector`, or `--decode-selector`, the update was discarded. The handler never got a chance to queue `RemoveWorker`, so the stale worker stayed in the registry.

### 2. Removals depended on exact `PodInfo` equality

Tracked pods were stored as `HashSet<PodInfo>`, and deletion used the incoming event's full `PodInfo` as the removal key.

A pod can be tracked while ready/running, then later emit a deletion or terminal update with different fields:

| Field | Tracked pod | Incoming event |
|---|---|---|
| `name` | `prefill-pod` | `prefill-pod` |
| `ip` | same IP | same IP |
| `status` | `Running` | `Failed` / terminating |
| `is_ready` | `true` | `false` |
| `pod_type` | `Prefill` | possibly changed / no longer matched |

With `HashSet<PodInfo>`, `tracked.remove(pod_info)` requires all fields to match. If readiness/status/type changed, removal missed the tracked entry and the original worker URL remained registered.

## Fix

- Track discovered pods by stable Kubernetes pod name: `HashMap<String, PodInfo>`.
- When removing a pod, remove by pod name and use the stored `PodInfo` to compute the original worker URL/type.
- Let events for already-tracked pods pass through the watcher even if they no longer match discovery selectors.
- Add `handle_selector_mismatch()` and share removal logic through `handle_pod_removal()`.
- Record selector-mismatch deregistration with a dedicated `selector_mismatch` metric label.
- Add regression tests for:
  - deletion after pod status/readiness changed;
  - tracked pod no longer matching service discovery selectors.

## Expected effect

After this change, service discovery deregisters workers when:

- the pod is deleted after status/readiness changed;
- the pod remains present but no longer matches the configured selector;
- the incoming Kubernetes event no longer has the exact same `PodInfo` fields as the registration event.

This prevents the gateway from continuing to route requests to stale pod IPs that are no longer part of the discovered worker set.

## Code Review

This pull request refactors service discovery in the model gateway by changing the tracking of pods from a `HashSet` to a `HashMap` keyed by pod name. This allows the system to correctly deregister stale workers when a pod's status changes or when it no longer matches service discovery selectors. A new helper function `tracked_pods_summary` and a common `handle_pod_removal` function are introduced, along with corresponding unit tests. The reviewer suggested a code modification to `handle_selector_mismatch` to improve how it delegates to `handle_pod_removal`.

Update `handle_selector_mismatch` to delegate to the updated `handle_pod_removal` function.

```rust
async fn handle_selector_mismatch(
    pod_info: &PodInfo,
    tracked_pods: Arc<Mutex<HashMap<String, PodInfo>>>,
    app_context: Arc<AppContext>,
    port: u16,
) {
    warn!(
        "Pod no longer matches service discovery selectors, removing tracked worker if present: name={} ip={} worker_url={}",
        pod_info.name,
        pod_info.ip,
        pod_info.worker_url(port)
    );

    handle_pod_removal(
        &pod_info.name,
        Some(pod_info),
        tracked_pods,
        app_context,
        port,
        metrics_labels::DEREGISTRATION_SELECTOR_MISMATCH,
    )
    .await;
}
```
