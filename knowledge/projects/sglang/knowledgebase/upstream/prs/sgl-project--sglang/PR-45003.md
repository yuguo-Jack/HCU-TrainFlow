# [Perf] mooncake: Reduce KV transfer descriptor construction overhead

[Upstream PR](https://github.com/sgl-project/sglang/pull/45003) · state: open · merged: False

## Original PR description

## Motivation

Mooncake's generic KV transfer path splits paired page indices into Python lists, builds a `(src, dst, length)` tuple for every layer and contiguous run, then unpacks those tuples into the three lists consumed by `batch_transfer_sync`. Fragmented page maps make this CPU work grow with the number of transfer descriptors.

Build the descriptor columns directly to reduce preparation overhead. Related to the PD transfer-efficiency work in #43699.

## Modifications

- Represent contiguous runs by their source start, destination start, and length, without materializing each page list. A discontinuity on either side ends the run.
- Construct the three engine input lists directly. Use scalar arithmetic for a single run and NumPy broadcasting across layers and runs for fragmented transfers. Use unsigned address arithmetic to preserve pointers with bit 63 set.
- Preserve descriptor ordering, transfer boundaries, and failure propagation across MHA/MLA, state buffers, mixed host/device destination maps, bounded batches, and custom-pool transfers. Existing tuple-list callers remain supported.

## Accuracy Tests

- Six affected disaggregation suites: **134 passed, 159 subtests passed**. Added byte-copy coverage checks the selected destination pages and untouched guards across layouts, strides, high-bit addresses, mixed destination maps, and batching modes. Existing PP and deferred-release coverage also passes.
- Qwen3-32B-FP8 local PD: **2,048/2,048 timed requests succeeded**. A separate run with `--disaggregation-enable-kv-checksum` passed **352/352 requests**; decode verified the actual transferred KV pages against prefill checksums. Checksum runs are excluded from performance numbers.
- Both versions answered **32/32 addition sanity-check questions** correctly. Full generated sequences are not bitwise identical; repeated baseline runs also differ. These checks do not constitute a full model accuracy evaluation.

## Speed Tests and Profiling

Baseline: `a3abea35609eeeff7e165486dd614963af211161`; patched runs use the same revision plus this change. Hardware: **2 × H100 PCIe 80 GB with NVLink**, one prefill GPU and one decode GPU. PyTorch `2.14.1+cu130`, Mooncake `0.3.13.post1` (CUDA 13). All timing runs have profiling disabled. Results cover intra-node NVLink, not inter-node RDMA.

**Real GPU transfer benchmark.** Each trial sends 32 logical requests through the same live engine and registered GPU buffers, with 32 flat buffers, 256 pages/request, and 512 bytes/page/buffer: **128 MiB total**. Six measured trials per version alternate execution order after warmup. Both versions submit the same 32 engine calls and the same descriptors and bytes for each page map; every transferred byte and untouched guard is checked.

| Contiguous pages per run | Outside-engine time, baseline → PR | Total time, baseline → PR | Total reduction |
| --- | ---: | ---: | ---: |
| 256 | 2.07 → 1.29 ms | 5.74 → 5.03 ms | 12.3% |
| 64 | 2.45 → 1.46 ms | 13.10 → 12.15 ms | 7.2% |
| 1 (fragmentation stress case) | 81.52 → 15.52 ms | 582.78 → 514.52 ms | 11.7% |

Values are medians. Outside-engine time is the measured send duration minus time inside `batch_transfer_sync`, calculated per trial. In the fragmentation stress case it falls by **81%**, while median engine time is essentially unchanged (**501.00 → 498.96 ms**). This isolates the benefit to descriptor preparation; it does not imply an 81% serving speedup.

**Concurrent PD serving.** 32 closed-loop clients, 64 warmup requests per fresh server pair, identical seeded synthetic workloads and server settings within each comparison. Prompt lengths are sampled from 512/1024/1536/2048/3072 tokens and output lengths from 32/64/128/192 tokens; `temperature=0`, `ignore_eos=True`. Throughput counts output tokens only. Startup, compilation, and warmup are excluded.

| Model | Measured requests per run; order | Baseline output tok/s | PR output tok/s | Difference |
| --- | --- | ---: | ---: | ---: |
| Qwen3-0.6B BF16 | 256; A/B/B/A | 5,079.1 | 5,362.0 | +5.57% |
| Qwen3-0.6B BF16 | 2,048; B/A, one pair | 4,028.6 | 4,711.8 | +16.96% |
| Qwen3-32B-FP8 | 512; A/B/B/A | 597.9 | 602.2 | +0.72% |

A is baseline; B is this change. A/B/B/A rows report the arithmetic mean of the two runs per version. The 0.6B short runs last about five seconds, and its longer result is only one pair, so neither establishes a general serving speedup.

For 32B, the individual results are **590.83 / 594.35 / 610.06 / 605.00 tok/s** in A/B/B/A order. The +0.72% mean difference is smaller than the within-version run-to-run spread (~2.4–2.6%), and P99 TTFT does not improve. **This workload does not establish a stable end-to-end throughput gain.** Separate CPU/GPU traces show GEMM dominating 32B GPU time, consistent with limited impact from reducing CPU descriptor work.

- `--mem-fraction-static 0.65` for 0.6B, `0.8` for 32B; identical between baseline and PR for each model. The 32B checkpoint uses FP8 block-128 weights with dynamic activation quantization and BF16 KV cache.
- A custom asynchronous client sends paired prefill/decode `/generate` requests with the same bootstrap room. Decode is streamed; a client starts its next request after both responses complete. Workload seed: 43699; warmup uses a separate seed and prompt set.
- CPU/GPU traces were captured separately with torch profiler for six scheduler steps on each role. Transfer-only traces also cover the CPU preparation and `batch_transfer_sync` regions.
