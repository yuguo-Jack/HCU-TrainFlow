# [Fix] disaggregation: Fail parked prefill requests when their decode goes away

[Upstream PR](https://github.com/sgl-project/sglang/pull/47100) · state: open · merged: False

## Original PR description

Related: #43699 (KVCache liveness). Follows up #40703.

## Motivation

With `--disaggregation-decode-allocation-policy prefill_complete`, a request keeps its KV on prefill until decode is ready for it:

1. Decode sends `BOOTSTRAP(room, ip, port)` to prefill.
2. Prefill runs the request and sends `WaitingForInput` to decode over its ZMQ status socket.
3. When decode has free KV, it sends destinations; prefill transfers the KV and frees it.

If decode dies between 2 and 3, prefill never notices, because liveness is only checked from decode to prefill. The parked requests hold their KV until `SGLANG_DISAGGREGATION_BOOTSTRAP_TIMEOUT` (default 300 s) fires, and prefill accepts almost no new work meanwhile.

The status socket's monitor sees the disconnect within about 1 ms, but it is only read on the next send to that decode, and nothing is sent while its requests are parked. Separately, if decode is already dead at the first connect, the socket reports `EVENT_CLOSED`, which the monitor did not watch. The readiness message then sits in a socket that never delivers.

The timeout cannot be tuned around this. A short one fails requests that are legitimately waiting for a busy but healthy decode (second table below); a long one strands KV for minutes when decode dies. This PR does not depend on the timeout: it reacts to the lost connection itself.

## Results

Two nodes, one prefill and one decode instance (TP 1 each), Mooncake over RDMA, `deepseek-moe-16b-chat`, `sglang-router` 0.3.2, main at 286e018. 128 requests (3000 input and 1000 output tokens) are sent at once. A 512-token probe every 10 s shows when prefill accepts new work.

Decode killed 20 s in, default 300 s timeout:

| | Prefill KV after the kill | Prefill accepts new work |
|---|---|---|
| main | 99% for about 290 s, until the timeout. Then 44%: the 26 queued requests are prefilled and parked again for the dead decode | 287 s after the kill |
| this PR | 0% within 2.2 s (first metrics sample) | 0.4 s after the kill |

In both runs the parked requests fail, since their decode is gone. The difference is how long prefill holds their KV.

Decode stays healthy, nothing killed:

| | Bootstrap timeout | Requests that succeed |
|---|---|---|
| this PR | 300 s (default) | 128 of 128 |
| main | 20 s (lowered as a workaround) | 72 of 128 |

## Modifications

- New `CommonKVManager.check_decode_connections()`. At most once per second, it drains the monitors of the cached status sockets and fails every request still waiting on a lost decode: one that is `Bootstrapping` or has no sender yet. Requests that already received destinations are left to the transfer path. The decode is not notified, because that connection is the one that was lost.
- It is called from `CommonKVSender._poll_with_status` for `Bootstrapping` senders, only under `prefill_complete`. Requests in the waiting queue are polled too (`resolve_waiting_queue_bootstrap`), so they fail before running prefill.
- The monitor also watches `EVENT_CLOSED`. The drain-and-drop code moves from `_connect` into `_drop_if_disconnected` so both callers share it.

There is no wire format change, so mixed prefill and decode versions keep working.

Limitations:
- A dead decode process is detected at once. A lost host is detected only after TCP keepalive gives up, about 45 s.
- These cases still rely on the timeout: a decode that hangs with its connection open, and requests whose `BOOTSTRAP` never reached prefill.

## Tests

Two cases in `test/registered/unit/disaggregation/test_prefill_complete_integration.py` use real ZMQ sockets on loopback. Both fail on main and pass with this PR. The whole file passes (23 tests), and so does `pre-commit` on the changed files.
- `test_lost_decode_fails_its_rooms_before_bootstrap_timeout`: decode disconnects after readiness. Its parked and queued requests fail, while a request bound to another, live decode keeps waiting.
- `test_decode_gone_before_first_ready_fails_room`: decode is already gone at the first readiness message.
