# [Fix] hicache: storage workers survive, fail loud when dead, stop without querying the backlog

[Upstream PR](https://github.com/sgl-project/sglang/pull/47617) · state: open · merged: False

## Original PR description

## Motivation

HiCache's four storage worker threads (prefetch query, prefetch IO, prefetch sync, backup) are started per rank in `HiCacheController._start_storage_threads` (`python/sglang/srt/managers/cache_controller.py:493`) and nothing watched them. Three problems follow from that.

1. A worker could die silently. `prefetch_io_aux_func` ran `_page_transfer` under `try/finally` with no `except`, so any exception that escaped the hybrid transfer outside its inner guards (the host layout lease raising on release in `pool_host/unified.py`, `_sync_trailing_keys` or `_resolve_sidecar_nonkv_derived_pool_transfers` raising before the sidecar ack) published the final ack and killed the thread. From then on the hit path kept allocating host bounces that only this thread's acks free: the host pool filled, hits parked forever, and `wait_complete` requests never admitted. No log line said why. In the hybrid controller the sidecar ack was also skipped on that path, so the per-operation ack sequence differed between the failing rank and its peers and the sync thread's next collective paired with the wrong ack.
2. No rank could tell that a worker on another rank had died. The MIN-counted drains in `check_hicache_events` simply stopped making progress.
3. Stopping with a backlog called the backend. The prefetch worker's loop keeps draining `prefetch_queue` after the stop event and ran a live `_storage_hit_query` for every queued operation; the backup worker finished every 128-page batch of its current operation. During a backend slowdown the fixed 10 s join in `_stop_storage_threads` then failed and `reset()` (flush) raised after the tree had already been wiped.

## Modifications

Worker survival, rank-safe by construction: the per-operation ack sequence is the same on every rank.

- Invariant: for every prefetch operation each rank publishes `ceil(len(hash_value) / STORAGE_BATCH_SIZE)` batch acks, then the sidecar ack when the operation carries `pool_transfers` (hybrid controller), then the `completed_req` ack; the sync thread reduces each one with the peers' ack of the same position. Every batch and sidecar ack now goes through `_put_transfer_ack`, which counts them on the operation together with the completed prefix the last one carried (`cache_controller.py:1374-1398`; `PrefetchOperation.published_transfer_acks` / `published_transfer_tokens`, `cache_controller.py:317-320`, `hybrid_cache_controller.py:166-169`).
- `prefetch_io_aux_func` catches `Exception` around `_page_transfer`, logs it with the request id, publishes the acks the transfer did not reach (`_publish_missing_transfer_acks`, `cache_controller.py:1405-1417`: the missing batch acks carry the prefix this rank last published, never less, because the scheduler drain asserts the reduced prefix is monotone; the hybrid override adds the sidecar ack with empty `pool_hits` when it was not reached, `hybrid_cache_controller.py:1694-1703`), and still publishes the `completed_req` ack in `finally` (`cache_controller.py:1470-1489`). The request finishes with the prefix this rank really has; the worker stays up.
- Hybrid `_page_transfer_sidecar` guards the whole sidecar section, including `_sync_trailing_keys` and `_resolve_sidecar_nonkv_derived_pool_transfers`, and publishes the sidecar ack with empty `pool_hits` on failure (`hybrid_cache_controller.py:1646-1692`). The MIN in `_reduce_prefetch_ack` turns that into zero hits on every pool for every rank, the same outcome the existing `batch_get_v2` failure path already produced.
- `prefetch_thread_func` is restructured so everything before the hits reduce is inside one guard; an exception anywhere before `_sync_prefetch_hit_query` answers 0 hits and still joins the collective and publishes the operation (`cache_controller.py:1555-1591`). Exceptions inside the reduce itself propagate and kill the thread; the liveness check below reports that.
- Sync thread and backup thread: no change. The sync thread's only non-`Empty` exception path is the collective itself, which cannot be retried rank-safely. The backup thread already survives backend errors through `_page_backup_or_log` (`cache_controller.py:1663-1669`).

Liveness, agreed on every rank that reduces the counts.

- `HiCacheController._storage_worker_threads()` returns the started, not yet stopped workers; `dead_storage_workers()` names the ones that exited; `storage_workers_alive()` is true when none did (`cache_controller.py:532-562`). The thread attributes are explicit (`None` in `__init__`, `cache_controller.py:386-391`; set back to `None` after a successful stop, `cache_controller.py:620-624`), so a controller that started no workers (a native controller whose `_start_storage_threads` returns None) reports alive. Threads carry names (`hicache-prefetch`, `hicache-prefetch-io`, `hicache-prefetch-sync`, `hicache-backup`; the PP ticket thread is `hicache-pp-ticket`) so messages can say which one is meant.
- A worker that finished while the stop event is set is not dead (`cache_controller.py:545-556`). A stop that hit its bound on one rank (`_stop_storage_threads` raised, `StorageAttachment.detach` returned the error, `storage_attachment.py:215-221`) leaves the stop event set and the threads in the started set by design; when they then finish their last call and exit, the next tick must not report a death on every rank. The retried detach joins them and clears the set. The stop event is set and cleared only on the scheduler thread, so the word reads the same on every rank in a tick (a rank whose stop succeeded has an empty set; a rank whose stop failed has the event set; both say alive).
- The PP ticket thread is deliberately not in the liveness set (`hybrid_cache_controller.py:309-313`). On a flush PP0 stops it inside its own `reset()` one relay step before PP1+ processes the same request, and PP1+'s copy exits on PP0's None ticket while PP1+ still ticks its current iteration; in buffer_only the tick reduces per stage, so counting it would raise falsely on PP1+. The existing `is_pp_prefetch_ready` check on the request path keeps covering that thread (`hybrid_cache_controller.py:1269-1277`). Its stop uses the same bounded join as the workers (`hybrid_cache_controller.py:294-303`).
- `UnifiedRadixCache._sync_hicache_ready_counts` folds one word, 1 alive / 0 dead, into the per-tick count exchange as a MIN, both the gloo tensor and the shm row: `[write_acks, load_acks, workers_alive, *storage_queue_sizes, digest, -digest]` (`unified_radix_cache.py:3607,3631`). When the agreed word is 0, every rank in the reducing group raises `RuntimeError("HiCache storage worker thread(s) exited on this rank: <names>" | "... on a peer rank")` in the same tick (`unified_radix_cache.py:3661-3666`). No health or degrade state: fail loud is the contract.
- The shm row width for the `hicache` exchange grows from 8 to 9: `get_shm_exchange` takes a `width` and `_shm_count_exchange` passes `_HICACHE_COUNT_ROW_WIDTH = 9` (`shm_tag_exchange.py:263-301`, `unified_radix_cache.py:153-156,3685-3687`). Rows with extra host pools still fall back to the gloo reduce as before.

Stop without live backend calls.

- Once the stop event is set, the prefetch worker answers every remaining queued operation as a miss without calling the backend but still runs the hits reduce and publishes it (`cache_controller.py:1566-1583`). This is rank-safe: every rank still joins the collective; a rank whose worker queried before it saw the stop is outvoted by the MIN.
- The backup worker stops issuing new batches after the stop event and acks with what completed (`cache_controller.py:1641-1644`); the hybrid backup returns before its sidecar write, the one backend call the base loop's check does not see (`hybrid_cache_controller.py:1726-1731`).
- The join bound is the module constant `STORAGE_STOP_JOIN_S = 60.0` (`cache_controller.py:280`), applied through `_join_storage_threads` (`cache_controller.py:564-582`), which logs every `STORAGE_STOP_LOG_EVERY_S = 10.0` s which threads are still running and the call each is inside (`_describe_thread`, `cache_controller.py:284-300`, reads the thread's current frame: the innermost `sglang` frame and the innermost frame). It still raises at the bound. 60 s is one slow backend call: after the stop event a worker only finishes the call it is already inside, not a queue, and the slowest single call we tolerate (a 128-page batch get/set against a stalled remote backend with the backends' own timeouts) sits well under a minute; a worker still inside a call after that is stuck, and the raise is the right outcome.

No new configuration knob. `STORAGE_STOP_JOIN_S`, `STORAGE_STOP_LOG_EVERY_S` and `_HICACHE_COUNT_ROW_WIDTH` are module constants.

Known limits with PP > 1 (unchanged by this PR; a reverse PP collective is out of scope). The word is agreed within the group that reduces the counts (`unified_radix_cache.py:3601-3606`): all TP ranks in every mode. In buffer_only with PP > 1 the tick reduces per PP stage (`_all_reduce_attn_groups`, `unified_radix_cache.py:3649-3652`), so a death on stage k raises on stage k only and the other stages hang in the next PP collective instead of raising. In cache mode with PP > 1, `_all_reduce` reduces across PP0's attention groups and then broadcasts down the pipeline (`unified_radix_cache.py:431-442`), so PP1+ ranks' own words are overwritten by PP0's and a worker death on PP1+ still shows up only as PP0's prefetch thread blocking inside the hits reduce.

Tests adapted because the contract they pinned changed: `test_hicache_pp_sync_drain.py` pins the tick row layout (`[1, 2, 0, 0]` becomes `[1, 2, 1, 0, 0]`); `test_shm_tag_exchange.py` pins the shm row width (9 now; the no-extra-pool row goes through shm, the rows with extra pools take gloo, exactly as before); `test_hicache_storage_registration_hook.py`'s bare controller fixture sets the four explicit thread attributes attach now reads.

## Accuracy Tests
