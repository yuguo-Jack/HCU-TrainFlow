# [Fix] rust-server: Constrain DeepSeek-V4.1 tool choices and gate them on reasoning

[Upstream PR](https://github.com/sgl-project/sglang/pull/45660) · state: closed · merged: False

## Original PR description

Stacked on #45659.

- `tool_constraint`: for `deepseekv41`, `required` and named `tool_choice` get xgrammar's `deepseek_v4_1` structural tag (previously a 400, since Dynamo does not know the parser). `auto` is constrained only once a tool is strict. A non-strict tool's arguments stay free (`json_schema: true`), and a strict tool's schema types are normalized, as in SGLang. The tag keeps xgrammar's think excludes only without a reasoning parser.
- The typed chat handler sets `require_reasoning` in thinking mode, so the tool constraint starts after the reasoning.
- `lower_chat` gets a tokenizer for logprob token text and bytes, so `logprobs` requests stay on the processor path and report `reasoning_tokens`.
- The DeepSeek-V4.1 renderer normalizes DB-style tool schema types (`"varchar"` to `"string"`), as SGLang does.
- `select_chat_formatter` no longer logs the error it returns, which was logged twice.
- `sglang-processor`'s schema-type normalization moves to the crate root, so the tool constraint in `parser/` builds without the `render` feature.

Not covered: `SGLANG_TOOL_STRICT_LEVEL` is not read by the Rust tool constraints, for any parser.

## Tests

- Unit: the tag equals Python's `get_structure_constraint` output for `required`, named and strict `auto` choices; a V4.1 `varchar` tool renders and constrains like `string`; logprob tokens, values and byte-level bytes are served by the processor. `sglang-processor` builds with `parser`, `render` and `render,openai` only.
- Live (same setup as #45659): 54 of 54 replayed requests match Python, including logprob tokens, bytes and values. gsm8k on c1ba2549d4: Rust 98.0%, Python 96.0%. Both were measured before the strict-tool, think-exclude and feature-gate fixes, which have unit tests only.
