# [MiniMax-M3] Fix EAGLE3 verification on CUDA

[Upstream PR](https://github.com/sgl-project/sglang/pull/43804) · state: open · merged: False

## Original PR description

## Motivation

MiniMax-M3 with an EAGLE3 draft does not start on CUDA. TARGET_VERIFY reaches the sparse layers' `forward_extend`, which
builds prefill metadata from `extend_seq_lens`. Verify batches carry none, so the startup warm-up's first TARGET_VERIFY
forward fails. On GB300 with `lmsysorg/sglang:nightly-dev-cu13-20261012-e6072935` and `Inferact/MiniMax-M3-EAGLE3-GQA`
(`--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`, `SGLANG_DISABLE_MSA=1`):

```
  File "python/sglang/srt/layers/attention/minimax_sparse_backend.py", line 1504, in forward_extend
    cu_seqlens, seq_lens, prefix_lens = self._resolve_extend_meta(
  File "python/sglang/srt/layers/attention/minimax_sparse_backend.py", line 1425, in _resolve_extend_meta
    1, dtype=torch.int32, device=forward_batch.extend_seq_lens.device
AttributeError: 'NoneType' object has no attribute 'device'
```

#41497 fixed ROCm by running a linear draft chain through the unchanged sparse decode kernels, one causal row per draft
token. Every gate it added is `is_hip`, so CUDA still takes the prefill path.

## Modifications

- The linear-verify path of #41497 runs on every non-NPU GPU. `init_forward_metadata_in_graph` builds the per-row
  metadata (`seq_lens + arange(1..ndt)`, `req_pool_indices.repeat_interleave(ndt)`), and `forward_extend` hands verify to
  `forward_decode` on a shallow copy, so the dense layers keep their per-request metadata and the `bs * ndt` draft KV is
  stored once. `_init_rocm_linear_verify_metadata` becomes `_init_linear_verify_metadata`.
- The draft guard is `draft_is_chain_layout`, already used by the ROCm indexer CP: EAGLE chains (`topk == 1`) only, so
  tree drafts and other algorithms raise `NotImplementedError` at startup instead of running with chain lengths.
- Graph capture bound. On CUDA the TARGET_VERIFY capture took `_max_seqlen_k` from the 1-token dummy lengths, so the
  graph baked a one-column score buffer that `_decode_score_kernel` overruns at replay. Verify capture now takes the
  context-length bound on every platform, and the eager bound counts the draft rows (the last row reads `prefix + ndt`
  tokens, one more 128-token block whenever the window crosses a block boundary).
- Rows past the context length are clamped to it. They predict positions that are never committed (the scheduler caps
  `max_new_tokens` below the context length and trims over-accepted drafts), and the clamp keeps the verify bound at the
  context length instead of `context + ndt`. At 1M context that keeps the decode top-k in its 8192 register bucket: one
  extra block moves it to the 16384 bucket, measured at +3.3–3.9 µs per call at 4–128 rows and +22 µs at 512 rows on
  GB300 (57 sparse layers per step).
- Verify rows stay on the Triton kernels when MSA decode is enabled. The MSA plan is prepared for decode batches only, so
  with `--disable-cuda-graph` the rerouted rows would raise "MSA decode metadata missing". MSA with the decode graph and
  speculative decoding is still refused at startup, as before.

## Accuracy Tests

MiniMax-M3-NVFP4 on 4x GB300, TP4, `--context-length 1048576`, thinking enabled, `SGLANG_DISABLE_MSA=1`,
`lmsysorg/sglang:nightly-dev-cu13-20261012-e6072935` with this patch. EAGLE3: `Inferact/MiniMax-M3-EAGLE3-GQA`,
`--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4
--speculative-draft-model-quantization unquant`, real verification.

| same build, one tray each | no spec | EAGLE3 |
|---|---|---|
| GSM8K 1319 q (5-shot) | 0.861 | **0.864** |
| GSM8K 40 q at `--parallel 1` (bs=1 decode graph) | 0.800 | 0.875 |
| passkey retrieval at 131K / 524K / 990K prompt tokens | pass | pass |
| mean acceptance length (GSM8K / long-context probe) | – | 2.81 / 2.90 |

`test/registered/kernels/ops/attention/test_minimax_linear_verify.py` (new, CUDA) drives the backend's verify entry with a
stub KV pool and compares against the same rows decoded alone, on private copies of the cache that hold only the tokens
each row may see:
- eager verify of prefixes 1000 and 5118 (the second crosses a block boundary): bit-exact;
- a verify graph captured on 1-token dummies, replayed with one request two tokens short of a 64K context: rows inside
  the context match, rows past it are clamped;
- MSA decode is switched on in the fixture, so both cases also pin that verify rows run on Triton.

On GB300, dropping the draft-token term from the eager bound fails both eager cases (the rows that cross the block
boundary differ), and dropping the clamp fails both replay cases. `test_minimax_decode_topk.py` (160),
`test_minimax_decode_topk_page_table.py` (38) and `test_minimax_sparse_decode_paged_tile.py` (4) pass on GB300 with the
patch. The ROCm test only follows the rename.

## Speed Tests and Profiling

Same build, one GB300 tray per arm, bs=1 decode right after the prompt is cached, 256 output tokens, real acceptance
(mean time per output token):

| prompt tokens | no spec | EAGLE3 | speedup |
|---|---|---|---|
| 8K | 4.34 ms | 2.23 ms | 1.95x |
| 131K | 6.00 ms | 3.40 ms | 1.76x |
| 524K | 9.78 ms | 5.43 ms | 1.80x |
| 990K | 13.88 ms | 8.30 ms | 1.67x |

`bench_serving` random 8K/1K, 16 concurrent, 64 prompts: output 1485 → 2387 tok/s (+61 %), median TPOT 9.31 → 5.53 ms.

AgentX results on GB300 (InferenceX methodology, EAGLE3 against no spec on the same build) will be added here when the
canonical sweep finishes.

## Not in this PR

- DP attention: `prepare_mlp_sync_batch` can still turn TARGET_VERIFY into one-token EXTEND rows, which this path does
  not see. TP is what this PR covers.
- Each draft row scores the index-K prefix on its own; a per-request packed scorer (as NPU's `pack_verify` and the ROCm
  indexer CP do) would cut verify indexer traffic at long context.
