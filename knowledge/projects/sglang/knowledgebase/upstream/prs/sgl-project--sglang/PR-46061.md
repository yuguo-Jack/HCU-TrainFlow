# [Perf] dsv4: Pass a persistent multi-CTA counter buffer to trtllm-gen attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/46061) · state: closed · merged: False

## Original PR description

[by Claude Code]

**At a glance:** removes 40 memset graph nodes per DeepSeek-V4/V4.1 trtllm-gen decode step. A graph of 40 attention calls gets 34-46 us faster on B200 (-5% to -10%). Outputs are bitwise equal. Not measured end to end on its own.

## Motivation

With `--dsv4-attn-backend trtllm`, DeepSeek-V4 / V4.1 attention runs on FlashInfer's trtllm-gen kernels (the
attention kernels generated by TensorRT-LLM). When a batch has few query rows, the kernel splits each row's keys
across several thread blocks (CTAs). Those blocks coordinate through a small buffer of counters, which must be zero
when the kernel starts; the kernel sets them back to zero before it exits.

If the caller passes no counter buffer, FlashInfer allocates and zeroes a new one on every call. In a captured CUDA
graph, that adds a zeroing node before every attention kernel, one per layer per step.

SGLang tried to avoid this: `_install_persistent_trtllm_semaphores` monkeypatched
`flashinfer.mla._core._get_trtllm_gen_multi_ctas_kv_counter_buffer` to return one shared buffer. Since FlashInfer
0.7.1, `trtllm_batch_decode_sparse_mla_dsv4` gets its buffer through `flashinfer.utils`, which calls its own copy of
that function, so the patch has no effect. SGLang pins FlashInfer 0.7.2, so every call zeroes a fresh buffer.
FlashInfer now accepts a caller-owned buffer (`multi_ctas_kv_counter_buffer=`), which is what the old patch's
docstring said it was waiting for.

## Modifications

In `python/sglang/srt/layers/attention/deepseek_v4_trtllm_backend.py`:

- Allocate one zeroed counter buffer per process through `get_buffer`, like the existing 128 MiB workspace. It is
  sized with FlashInfer's `get_trtllm_gen_multi_ctas_kv_counter_bytes` for the existing query-row bound
  (`_trtllm_query_row_capacity`, unchanged) and `max(64, num_attention_heads)` heads, since a launch passes either
  the per-GPU heads or the 64-head padding. That is 4 bytes per row and head, e.g. 4 MiB at 16384 rows and 64 heads.
- Pass it as `multi_ctas_kv_counter_buffer=` to both `trtllm_batch_decode_sparse_mla_dsv4` calls (decode / verify /
  draft-extend, and prefill).
- `_check_trtllm_query_rows` now compares the bytes a launch needs with the buffer's size. It still raises
  `RuntimeError`.
- Remove the dead monkeypatch and its module globals.

**Why one buffer is safe to reuse:** the kernel resets the counters at the end of every launch (FlashInfer's
contract), and all trtllm attention launches of this backend run in order on the forward stream, which the shared
workspace already relies on. The removed patch used the same one-shared-buffer design.

**Related:** the trtllm MLA and DSA backends already pass a persistent counter buffer (#31927, #39175 by
@mmangkad); this does the same for DeepSeek-V4. #36652 (same author, open) edits the same file but keeps the old
patch. The two are independent: whichever merges second resolves two small conflicts (and, if this one is second,
drops two arguments that #36652 removes from the new test's calls).

Tests:

- New `test/registered/kernels/ops/attention/test_dsv4_trtllm_counter_buffer.py` (B200 runner), calling the
  backend's real decode and prefill methods:
  - Decode, 36 query rows x 16 heads, 4 layers: the eager run and 3 CUDA-graph replays with fresh inputs are bitwise
    equal to FlashInfer with its own per-call buffer, and the counters are all zero after each step. The captured
    graph has exactly one node fewer per attention call.
  - Prefill, 2 requests of 3 and 9 query rows, run twice: bitwise equal, the counters are back to zero, and the
    FlashInfer call receives the backend's buffer. (Prefill is not graph-captured, and a dropped buffer would not
    change its output, so the test checks the call itself.)
  - Removing `multi_ctas_kv_counter_buffer=` from the decode call fails the decode test; removing it from the
    prefill call fails the prefill test.
- The capacity test in `test_deepseek_v4.py` and the manual `test_dsv4_trtllm_prefill.py` use the new helpers.

## Accuracy Tests

Outputs are bitwise identical to FlashInfer's per-call buffer, so no model eval was run.

| Check | B200 |
|---|---|
| `test_dsv4_trtllm_counter_buffer.py` | 2 passed, 0 skipped |
| `test_deepseek_v4.py` | 25 passed (34 FlashMLA subtests skipped: no `flash_mla` in the image) |
| `test_dsv4_trtllm_prefill.py` (manual) | 1 passed, 4 subtests |
| Shared vs per-call buffer at 12 decode and prefill shapes, 3 reuses each | bitwise equal, counters zero after every launch |

With the counters pre-filled with non-zero bytes, the kernel hangs on B200 at 8, 36 and 64 decode rows and at
three of the four prefill shapes, including both shapes the new test uses. So these shapes do exercise the
counters, and a buffer left non-zero would hang rather than silently change outputs.

## Speed Tests and Profiling

Microbenchmark on one GPU: one CUDA graph of 40 attention calls (each packs the sparse indices, then calls
`trtllm_batch_decode_sparse_mla_dsv4`), with 16 heads, as in DeepSeek-V4.1-Flash decode with tensor parallelism
(TP) 4. Before: no buffer passed (FlashInfer zeroes one per call). After: one shared buffer. Outputs are checked
bitwise equal before timing. Times are us per graph replay, the median of 9 trials of 50 replays. The A/B script is
not part of this PR; it is available on request.

| | B200 |
|---|---|
| 36 query rows | 643.7 -> 609.9 (-33.8) |
| 1 query row | 457.3 -> 411.6 (-45.7) |
| Graph nodes per replay | 120 -> 80 |
| Software | torch 2.14.1, CUDA 13.0, FlashInfer 0.7.2 |

Across three B200 runs on two nodes, 36 rows saved 23-42 us and 1 row saved 26-47 us.

This change was not measured end to end on its own.
