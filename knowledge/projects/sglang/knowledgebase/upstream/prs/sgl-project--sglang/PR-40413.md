# [Fix] tracing: end span when mismatched slice discarded

[Upstream PR](https://github.com/sgl-project/sglang/pull/40413) · state: open · merged: False

## Original PR description

## Motivation

`TraceReqContext.trace_slice_end` discards a slice without ending its span when
the slice name or level does not match the top of the stack, so that span is
never exported.

On `main` (`dd83b54611897a5f80f4df59e69756bd2fb4b8ab`),
`python/sglang/srt/observability/trace.py` L665-672:

```python
        # check if slice_name matching and level matching
        # unlikely path, excepting error API usage
        if cur_slice.slice_name != name or cur_slice.level != level:
            logger.warning(
                f"Slice name mismatch: {name} != {cur_slice.slice_name} or level mismatch: {level} != {cur_slice.level}"
            )
            self.thread_context.cur_slice_stack.pop()
            return
```

The slice is popped, but `cur_slice.span` is never ended. After the pop nothing
holds a reference to that span, so it stays recording for the life of the
process and the span processor never sees it. The matching path ends the span
at L692 before popping at L694, and `abort()` at L797-800 ends every slice span
it discards:

```python
        while len(self.thread_context.cur_slice_stack) > 0:
            if self.thread_context.cur_slice_stack[-1].span:
                self.thread_context.cur_slice_stack[-1].span.end(end_time=ts)
            self.thread_context.cur_slice_stack.pop()
```

So this branch is the only place in the file that drops a slice span without
ending it.

The parent span is still ended by `abort()`/`trace_req_finish`, which is why
this shows up as a silently missing child span rather than a broken trace: the
request trace is exported with one slice absent, and the `SLICE_START` timing
for that slice is lost.

## Modifications

`trace.py`: end the span before popping in the mismatch branch, guarded by
`if cur_slice.span:` to match the existing style in `abort()`.

`test_trace.py`: two regression tests. The existing
`test_trace_slice_end_name_mismatch` asserts only that the stack was popped,
which is true both before and after this change, so it cannot see the leak. The
new tests assert the discarded span is no longer recording, and cover both
halves of the condition (name mismatch and level mismatch).

## Accuracy Tests

Not applicable — tracing only, no change to model outputs.

## Speed Tests and Profiling

Not applicable. The added work is one `span.end()` on a branch the comment

## Verification

Against the unmodified file at `dd83b5461189`, driving the real
`TraceReqContext` with an SDK tracer provider:

| case | before | after |
|---|---|---|
| matching name (normal path) | 1 span exported | 1 span exported |
| mismatched name | **0 spans exported**, span still recording | 1 span exported, ended |
| mismatched level | **0 spans exported**, span still recording | 1 span exported, ended |

Running the two new tests against the pristine file fails both with
`the discarded slice's span must be ended, not left recording`; the
pre-existing `test_trace_slice_end_name_mismatch` and the normal-path test pass
in both states, so the failure isolates the defect.

`ruff format` reports both files already formatted, `ruff check
--select=F401,F821,UP037` passes, and `isort --check-only` with the repo's
`.isort.cfg` passes.
