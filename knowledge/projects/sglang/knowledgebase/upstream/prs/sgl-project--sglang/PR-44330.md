# [Fix] tokenizer_manager: Reject prompts that tokenize to zero tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/44330) · state: open · merged: False

## Original PR description

## Motivation

One request can take a server down:

```bash
curl -s http://127.0.0.1:30000/generate -H 'Content-Type: application/json' \
  -d '{"text": "", "sampling_params": {"max_new_tokens": 2}}'
```

`GenerateReqInput` rejects an empty `input_ids` list with a 400 (#4481), but a `text` prompt is tokenized later, and on a tokenizer that adds no BOS token (Qwen2.5 here) `""` becomes zero tokens. Nothing checks the token count after tokenization, so the request reaches the model and the scheduler dies:

```
  File ".../sglang/srt/models/qwen2.py", line 226, in forward
    q, k = self.rotary_emb(positions, q, k)
  File ".../sglang/srt/layers/rotary_embedding/base.py", line 400, in forward_cuda
    q_rope = query.view(batch_size, -1, self.head_size)
RuntimeError: cannot reshape tensor of 0 elements into shape [0, -1, 64] because the unspecified dimension size -1 can be any value and is ambiguous
[...] SIGQUIT received. signum=None, frame=None. It usually means one child failed.
```

A batch with one empty prompt (`"text": ["hi", ""]`) crashes the same way whenever the scheduler prefills the empty request on its own; when it shares a prefill batch with a non-empty request, the server survives and returns output for a prompt of zero tokens.

Embedding servers are affected through the OpenAI-compatible endpoint. `/v1/embeddings` validates strings and flat token-id lists, but not a batch of token-id lists, so this kills a `BAAI/bge-base-en-v1.5 --is-embedding` server with a CUDA device-side assert:

```bash
curl -s http://127.0.0.1:30000/v1/embeddings -H 'Content-Type: application/json' \
  -d '{"model": "BAAI/bge-base-en-v1.5", "input": [[101, 7592, 102], []]}'
```

The other OpenAI endpoints return 400 for an empty prompt at their own layer.

## Modifications

- `TokenizerManager._validate_one_request` raises `ValueError` when the request has zero input tokens. This runs after tokenization and multimodal processing for both the single and the batch path, and for generation and embedding requests alike, so it covers `text`, `input_ids` and multimodal inputs, and the HTTP layer turns it into a 400 like the existing context-length errors. A session request with a session id is still allowed to leave its prompt to the session history, matching the `input_ids` check in `GenerateReqInput`.
- `EmbeddingReqInput.normalize_batch_and_arguments` rejects an empty `input_ids` list like `GenerateReqInput` does. `/encode` with `"input_ids": []` indexed `input_ids[0]` while deriving the batch size and returned a 500.
- Regression tests:
  - CPU: `test_tokenizer_manager_input_validation.py` checks that a zero-token generation prompt and a zero-token embedding input are rejected, that `/encode` with empty `input_ids` is rejected before batching, and that a session request with an empty prompt still passes.
  - Server: `test_request_length_validation.py` sends `""` and `["hi", ""]` to `/generate`, expects 400 for both, and then checks that a normal request still succeeds. This file already holds the other `/generate` 400 cases that used to crash the scheduler.
