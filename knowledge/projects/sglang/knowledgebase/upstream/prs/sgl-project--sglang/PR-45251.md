# [Perf] deepseek-v4.1: Score a request's verify rows as one request in the full-scan indexer

[Upstream PR](https://github.com/sgl-project/sglang/pull/45251) · state: closed · merged: True

## Original PR description

## Motivation

Under DSpark target verify the ratio-1 and ratio-2 DeepSeek-V4.1 indexers call DeepGEMM's paged logits kernel with every draft row as its own request, so each row streams its request's whole index-K cache: six times per request with block 5. On a DEP16 decode at 64 requests per rank and 128K contexts the four full scans take 1.27 ms of a 22.6 ms DSpark cycle.

## Modifications

- `PagedIndexerMetadata.rows_per_request`: the draft block for static verify, 1 for ragged verify and everywhere else. The DeepGEMM schedule is planned over the lengths viewed `[requests, block]` (the JIT planner flattens them, so grouped rows use DeepGEMM's).
- `DeepGEMMDecodeData.paged_logits_args` views `q` as `[requests, block, heads, 64]`, the lengths as `[requests, block]`, and takes one page-table row per request. Both full-scan callers use it: `FullTopK._deep_gemm_decode` and the candidate-source `publish_decode`.
- No kernel change: `fp8_fp4_paged_mqa_logits` already schedules `next_n` rows per request in blocks of `128 / heads`, so six rows read the cache twice instead of six times.
- The logits tensor, the per-row lengths and page table handed to top-k are unchanged, so the bf16 DeepSelect top-k, top-k v2 and the paged top-k all see the same input as before.

## Validation

DeepSeek-V4.1-Flash, one DEP16 worker on 4x4 GB300 (DP attention 16, EP16, MegaMoE, `flashmla_mega`, DSpark block 5, static ragged verify, bf16 index logits, decode graphs at batch 64), 1,024 random-id prompts of 128K tokens held at 64 per rank, golden acceptance 3.51, main `49766a74f9` against this branch, one run each. Step time from the scheduler's `Decode batch` lines over the steady window; kernel times from a torch trace of 20 steps.

| 64 per rank, 128K contexts | main | this PR |
|---|---:|---:|
| Full scans, layers 2 / 8 / 14 (ratio 2) / 20 (ratio 1), us | 249 / 259 / 246 / 516 | 96 / 96 / 97 / 183 |
| Four scans per verify step, ms | 1.27 | 0.47 |
| DSpark cycle (draft + verify), ms | 22.57 | 21.57 |

Other kernels unchanged within 1%. GSM8K at native acceptance on one DEP2 node (5 shots, 1,314 examples, temperature 0): 97.56% main, 97.11% this branch, inside the run-to-run spread, as the check below shows.

Kernel-level check on one GB300 (DeepGEMM v0.2.2, bf16 logits): the same `fp8_fp4_paged_mqa_logits` call on identical random inputs, per row (`next_n` 1) and grouped six per request (`next_n` 6), on three batches: 64 x 6 rows at 128K slots with two seeds, and 16 x 6 at 64K. Every logit a row scores inside its own length is bit-equal (78M values, max abs diff 0), so the per-row top-k is identical on all three. The fp32-logits output type was not run.
