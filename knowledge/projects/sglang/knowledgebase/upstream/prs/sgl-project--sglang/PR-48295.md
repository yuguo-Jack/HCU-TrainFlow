# [Feat] modelopt: Quantize block-FP8 MTP draft experts to NVFP4 for MIXED_PRECISION checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/48295) · state: open · merged: False

## Original PR description


## Motivation

`--speculative-draft-model-quantization modelopt_fp4` converts the MTP draft's MoE experts to NVFP4 while they load when a serialized NVFP4 checkpoint ships them in BF16 (`_resolve_explicit_draft_quant_config`). ModelOpt MIXED_PRECISION exports such as `nvidia/Qwen3.8-Flash-Next-NVFP4` ship the MTP experts as block FP8 instead (`mtp.layers.0.mlp.experts`: `FP8_BLOCK_SCALES`, group size 128). The draft resolves to `modelopt_mixed`, the explicit request is ignored, and the 512 draft experts stay block FP8 on the triton FP8 MoE path. On a single 96 GB GPU, where this checkpoint is tight, the extra draft bytes come straight out of the KV pool.

## Modifications

- `ModelOptMixedPrecisionConfig.convert_block_fp8_experts_to_nvfp4()` routes block-FP8 FusedMoE layers to upstream's existing online FP8-to-NVFP4 loader (`make_modelopt_fp4_online_config_from_fp8`, the path `--quantization modelopt_fp4` already uses for FP8 checkpoints), with the checkpoint's block size.
- `_resolve_explicit_draft_quant_config` calls it for a MIXED_PRECISION draft when the user explicitly passed `--speculative-draft-model-quantization modelopt_fp4`. Inherited target quantization, other explicit draft quantizations, and the target model are unchanged.
- Unit tests in `test/registered/unit/model_loader/test_modelopt_loader.py`: the explicit request routes the MTP experts to `ModelOptNvFp4OnlineFusedMoEMethod` with an FP8-serialized, `[128, 128]`-block online config; inherited and other explicit requests keep `Fp8MoEMethod`.
- Cookbook: the RTX PRO 6000 notes for `nvidia/Qwen3.8-Flash-Next-NVFP4` (`docs/cookbook/autoregressive/Qwen/Qwen3.8-Flash-Next.mdx`) describe the flag and its measured effect.

Supported GPUs: verified on RTX PRO 6000 (SM120, `flashinfer_cutlass`) and GB200 (SM100, `flashinfer_trtllm`). On GPUs without native NVFP4 MoE kernels, such as H100, the flag now builds NVFP4 draft experts where it used to be ignored for these checkpoints; that configuration is untested.

## Accuracy Tests

Setup: 1x RTX PRO 6000 Blackwell Server Edition (SM120), `nvidia/Qwen3.8-Flash-Next-NVFP4`, main = `8d4e1ce4c7`, both arms on the same node with the same flags:

```bash
python3 -m sglang.launch_server --model-path nvidia/Qwen3.8-Flash-Next-NVFP4 \
  --ple-offload-embedding --json-model-override-args '{"text_config": {"ple_embedding_dtype": "float8_e4m3fn"}}' \
  --moe-runner-backend flashinfer_cutlass --disable-radix-cache --cuda-graph-max-bs-prefill 2048 \
  --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 \
  --mem-fraction-static 0.94 --chunked-prefill-size 4096 --max-running-requests 8 --max-mamba-cache-size 40 \
  --speculative-draft-model-quantization modelopt_fp4
sgl-eval run gsm8k --base-url http://127.0.0.1:<port>/v1 --num-examples 200 --num-threads 32 \
  --temperature 0 --max-tokens 2048 --chat-template-kwarg enable_thinking=false
```

| | main | this PR |
|---|---|---|
| GSM8K (200) | 97.0% | 96.5% |
| Avg spec accept length (after GSM8K) | 3.50 | 3.50 |

The target model's weights and quantization are untouched; only the draft experts change. Greedy verification keeps the target's choice, but a different draft accepts different tokens per verify step, so the target computes the same sequence in different verify-step groupings. On this model that grouping can move the target's logprobs slightly on long decodes (see the GB300 paragraph below), so outputs are identical to main except where a changed acceptance pattern tips a near-tie. Accuracy and mean acceptance are unchanged; the GSM8K gap is one question of 200.

On the RTX PRO 6000, where this model is not repeat-deterministic on main, greedy outputs agree with main as often as main agrees with itself: 32 prompts x 3 runs, 64 new tokens, same GPU, 48/288 cross pairs identical against 16/96 main-vs-main pairs (mean common prefix 30.3 vs 29.6 tokens).

On 1x GB200 (`--moe-runner-backend flashinfer_trtllm --mem-fraction-static 0.85`, otherwise the same flags), greedy outputs on 32 short prompts are token-identical to main: 3 runs per arm, 64 new tokens, 288/288 cross pairs identical (main itself is repeat-deterministic there, 96/96).

| GB200 | main | this PR |
|---|---|---|
| GSM8K (200) | 96.5% | 97.0% |
| Avg spec accept length | 3.46 | 3.47 |

On 1x GB300 with `--attention-backend flashinfer --enable-deterministic-inference` (otherwise the GB200 flags), every arm is repeat-identical, GSM8K is 97.0% on both and accept length 3.43 on both, and the draft load drops from 4.79 to 3.75 GB.
- The 32 short prompts (64 new tokens) are token-identical to main: 288/288 cross pairs.
- A mixed set of 8 chats (128 new tokens) matches on 7. The 8th has a 14,420-token prompt. It matches main through token 59 bit for bit, logprobs included. From token 60 the logprobs drift, and token 67 flips on a near-tie: at that position the top token has only about 25 % probability in every arm (" First" on main, " So" with this PR).

Streaming the per-step accepted tokens shows why. The two drafts first group tokens differently at token 14 (one verify step accepts 4 tokens with the fp8 draft and 2 with the NVFP4 draft), while logprobs stay identical for another 46 tokens.

The same thing happens without this PR's flag and with no change to the draft weights. Running this branch without the flag (the same code path as main; its `3/4` run equals main bit for bit) with `--speculative-num-steps 2 --speculative-num-draft-tokens 3` instead of `3/4` groups the tokens differently from token 4, and its logprobs drift from token 48 (tokens still identical through 128).

So on this long prompt the target's numerics depend on how earlier tokens were grouped into verify steps. Any draft change exposes that, including main's own draft-length setting. This PR is no exception.

| GB300, 14,420-token prompt, 128 tokens | main (fp8 draft, 3/4) | this PR (NVFP4 draft, 3/4) | main (fp8 draft, 2/3) |
|---|---|---|---|
| verify steps | 46 | 45 | 52 |
| first token where verify-step grouping differs from main 3/4 | | token 14 | token 4 |
| first logprob different from main 3/4 | | token 60 | token 48 |
| first token different from main 3/4 | | token 67 | none |

The "main" columns ran this branch without `--speculative-draft-model-quantization`, which loads the fp8 draft exactly as main does. Its output matched main's run of the same request bit for bit, logprobs included. Tokens per verify step come from streaming: one chunk per verify step, checked against `spec_verify_ct`.
