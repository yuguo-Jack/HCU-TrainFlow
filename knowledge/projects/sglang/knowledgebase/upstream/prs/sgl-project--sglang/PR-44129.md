# [Fix] mm: encode a multimodal item once per request in chunked prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/44129) · state: open · merged: False

## Original PR description

Fixes repeated video encoding in chunked prefill. A long video was run through the vision encoder once per chunk, so two or three times per request. Now it is encoded once.

## Motivation

When a prompt is longer than `chunked_prefill_size`, prefill runs in chunks. Each chunk looks for the encoder output in the embedding cache. If it is not there, the chunk runs the encoder again on the whole video, not only on the part it needs.

For a long video it is usually not there:

- The cache is 100 MiB by default. The encoder output of a long video is bigger than that, so it is never stored.
- Qwen3-VL on a Hopper GPU with 60 GiB or more runs with the cache off.
- An entry can be evicted between two chunks of the same request.

So a request with 3 chunks runs the encoder 3 times. A large image or an audio clip that is cut by a chunk boundary has the same problem.

I found this while profiling Qwen3-VL video requests: the vision encoder ran twice for one 16.5 s clip.

## Reproduction

## Modifications

- When the first chunk runs the encoder, keep the part of its output that later chunks still need, in a table in `mm_schedule` (`_prefill_rows`). The key is the item's hash and its positions in the prompt.
- Read the kept rows in later chunks before looking at the cache. In `_get_chunked_embedding_full` the cache is asked only when nothing is kept, so later chunks no longer touch its LRU order.
- Drop the part already read, so only the unread part stays in memory.
- Remove an entry after the item's last chunk. The scheduler also empties the table whenever no request is between two prefill chunks: at the start of `get_new_batch_prefill`, in the dLLM branch of `get_next_batch_to_run` while no context prefill is part-way (`DllmManager.any_context_in_progress()`), when a dLLM request is aborted, and in `pause_generation`, `flush_cache` and `release_memory_occupation`.
- Add `MultiModalStaticCache.peek()`, which reads an entry without changing the LRU order.
- `MultiModalStaticCache.set()` refuses an entry larger than the whole cache before evicting anything, so a long video no longer empties the cache for every other request. #42062 makes the same change.
- Check that the kept rows cover the chunk before slicing them.
- Cover the three chunked paths: `_get_chunked_embedding_full`, `_batch_encode_per_image_misses` and `_get_chunked_embedding_by_item`.
- Add unit tests for the three paths, EVS, a cache entry evicted between two chunks, an encoder that reuses its output buffer, a restarted prefill, items shared by session requests, the same image twice in one prompt, every place the scheduler empties the table, and an entry larger than the cache.

No new flag or config. A request that fits in one chunk takes the same path as before. `schedule_batch.py` is not changed, and nothing is stored in `model_specific_data`.

What is kept is a copy of the unread part, not the encoder output itself. The output can be a slice of a larger batch tensor, and keeping the slice would keep the whole batch alive. The copy is made again only after half of it has been read, so a video with many chunks is not copied once per chunk. If the cache holds the same tensor, it is kept by reference and nothing is copied; when `set()` stored a clone of the output, the clone is read and kept instead.

Requests with the same items at the same positions share an entry (session requests, identical prompts). That is safe because the rows depend only on the content, and a request reads an entry only from the position where its unread rows begin. The positions are part of the key because the same image twice in one prompt has the same hash; with the hash alone, the second copy would read rows of the first.

Where the table is emptied: `get_new_batch_prefill` is reached by every prefill loop after an abort, a disagg bootstrap failure or an optimistic yield has dropped the chunked request, and before a new request becomes the chunked one. Outside dLLM only the chunked request keeps rows into the next step, so the table holds the items of one request.

Making the cache bigger with `SGLANG_VLM_CACHE_SIZE_MB` does not fix this. The cache is shared and evicts the least recently used entry, so a request can still lose its entry between two chunks.

A precomputed embedding that is too short now fails at the new check instead of later in `_adjust_embedding_length`.

Not changed here: models that run the encoder inside their own `forward` (the legacy LLaVA family) have the same problem and need a separate change.

The retention mechanism is the right shape for this bug, and the evidence package (encoder-call counts, logprob-exact parity, peak-memory tables) is thorough. Details in the line comments; three things that don't anchor to this diff:

1. `MultiModalStaticCache.set()` evicts before checking whether the entry can ever fit (`mem_cache/multimodal_cache.py:115-119`): an oversize entry — exactly the long-video case here — flushes the *entire* cache and then returns `False`. Every first chunk of a long video therefore still wipes every other request's cached embeddings under this PR. `if data_size > self.max_size: return False` before the eviction loop fixes it; worth landing here or immediately after, since this workload is the PR's motivation.
2. The EVS path is unit-tested only per the PR description. Please run one EVS model on a GPU before merge.
3. Pre-existing gap this workload makes visible: nothing ever clears the embedding cache on `flush_cache`, so it can serve stale embeddings after a weight update. Separate-PR material, mentioning it here only because kept-rows work is adjacent.
