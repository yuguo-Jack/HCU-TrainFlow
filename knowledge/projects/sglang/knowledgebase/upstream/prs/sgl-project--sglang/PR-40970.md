# [GLM47] Reduce full-assistant grammar overhead: batched masks, thinking fast path, shared metadata

[Upstream PR](https://github.com/sgl-project/sglang/pull/40970) · state: open · merged: False

## Original PR description

## Summary

Reduce GLM47 full-assistant grammar overhead while preserving the default-on constraint introduced by #38890. On the original benchmark, that constraint reduced decode throughput by roughly 18–20% at concurrency 64 on an 8×B200 allocation (TP4/EP4).

- Fill eligible xgrammar mask rows through its native matcher pool, with four workers and a minimum batch size of 16; retain per-row handling for other grammar objects.
- Add `SGLANG_ENABLE_GLM47_FULL_ASSISTANT_CONSTRAINT=0` as an explicit opt-out, applied consistently to request constraints and tool parsing. The default remains enabled.
- Reuse the thinking-phase mask and skip matcher updates for tokens proven safe for the canonical GLM47 thinking grammar. Atomic thinking-end tokens switch to the generation matcher; other boundary/partial-token cases use the full matcher for exact behavior.
- Share immutable thinking metadata across schemas under a backend lock. Keep schema-dependent generation contexts and sparse mask-word overrides for tokens that cross into generation.
- Cover speculative tree rollback, partial UTF-8 and boundary tokens, request retraction, and metadata sharing against full-matcher masks.

Rebased onto `943621c3364de6948fc02ee13c55b4f1cdf97f3a` (2026-10-08); current head: `f539271102cc83a9b1436efcf8b889ac3f1aeea0`. That rebase had one conflict in `serving_chat.py` (upstream's tool-bearing gate on `glm_constraint` merged with this PR's env opt-out) and passed pre-commit + 178 CPU unit tests (+112 subtests). Earlier validation below references older bases/heads; the 2026-10-01 rebase (`99c59a2ea62f32fd5497eceaf2ed18cad33389db`, head `a114d4df7cb5fc3b6b7ac68c21281e5d99b09a5b`) applied with zero conflicts and re-passed the live smoke gate (tool replay 64/64 `tool_calls`, accept 2.7588; GSM8K N256 96.875% / 100% stop, accept 2.7738). The 2026-10-08 head is validated by the same static gates plus CI; no new live smoke was run for it.

## Validation

All changed files pass pre-commit. The two constrained test modules and the complete `test_serving_chat.py` pass: **163 tests and 79 subtests**. GPU visibility was disabled for these tests using a nonexistent ordinal (`CUDA_VISIBLE_DEVICES=999`, verified `torch.cuda.device_count() == 0`), because an existing test helper indexes the first character of this variable and cannot collect with an empty value.

Historical evidence on base `6b33338242f8ce85cd66bac96a396a4ddf05da9e`:

- Non-speculative GLM-5.3-Flash tool replay, high reasoning effort, N512/c64: **974.9 → 1183.3 output tok/s (+21.4%)**; repeat **998.0 → 1166.6 (+16.9%)**. This used an 8×B200 allocation with TP4/EP4. It is not a speculative-decoding speedup measurement.
- Real-tokenizer bitmask parity: **24 cases / 794 token steps**, including tool-choice/parallel modes, UTF-8, and boundary tokens; masks were bitwise equal to full xgrammar. Mixed batches also matched across 32 rows and 15 steps. Additional review exercised 72 real-tokenizer speculative tree traversals and 2,500 randomized accept/rollback steps.
- Full GSM8K with NEXTN 3/1/4 and grammar enabled: **1282/1319 correct (97.19%)**, **1318/1319 stop (99.92%)**, acceptance **2.9031**, **810.14 output tok/s**.

Refreshed validation on the rebased head, fresh 4×B200, NEXTN 3/1/4 and grammar enabled:

| Full GSM8K accuracy | 1282/1319 (97.19%) | **1284/1319 (97.35%)** |

The refreshed tool replay passes **64/64 `tool_calls`** at c16/high effort, with acceptance **2.7265** and **514.92 output tok/s**. The serve log contains zero grammar/matcher errors, crashes, or OOMs before intentional shutdown. No compilation/warmup messages occurred inside either measured workload interval. GSM8K has zero request errors or truncated responses.

The 20.1% throughput drop is observed drift. Quality and stopping remain in the requested band, and acceptance is slightly higher. The new run generated 23.0% fewer tokens and completed 3.7% sooner; the old run included one token-capped response. Different output lengths, separate reservations, workload history, and intervening upstream changes prevent attributing this single-run difference to the grammar optimization.

**Follow-up controlled A/B (2026-09-24, one fresh 4×B200, A1→B1→B2→A2, fresh server per leg, full discarded warmup before every measured pass, fixed seeds):** A = upstream/main `4e60d70ba4`, B = this branch `ec1bf54389`, both grammar-default-on with NEXTN 3/1/4. Full GSM8K 1319 output tok/s: B/A **+3.04% / −1.89%**, pooled **+0.49%** — the A and B ranges overlap (within-A spread 2.15%). Tool replay N64/c16: B/A **+97.20% / −6.55%**, but A's own repeat spread is ~50%, so neither a speedup nor a regression is established there either; B is not consistently slower in both repeats for either workload. Zero grammar errors/crashes across all four server lifetimes, and zero compilation/warmup log lines inside any measured interval. **The −20.1% gap above is not reproduced as a branch regression by this controlled comparison.**


## Reproduction

Model: public `zai-org/GLM-5.3-Flash` FP8 checkpoint, revision `eb9eb208eb0d988989d07a6a12d0fdeb5f52574a`. The refreshed validation uses a fresh 4×B200 box, `lmsysorg/sglang:latest`, and a Python source overlay of the tested head. Pin the downloaded model to this revision and set `MODEL_PATH` to its directory.

```bash
GITHUB_BASE_REF=upstream/main pre-commit run --files $(git diff --name-only upstream/main HEAD)
CUDA_VISIBLE_DEVICES=999 PYTHONPATH=python SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1 \
python3 -m pytest -q \
  test/registered/unit/constrained/test_xgrammar_thinking_mask.py \
  test/registered/unit/constrained/test_xgrammar_batched_mask.py \
  test/registered/unit/entrypoints/openai/test_serving_chat.py

export PYTHONPATH="$PWD/python"
export SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1
export CUDA_VISIBLE_DEVICES=0,1,2,3
unset SGLANG_ENABLE_GLM47_FULL_ASSISTANT_CONSTRAINT
python3 -m sglang.launch_server \
  --model-path "$MODEL_PATH" --served-model-name zai-org/GLM-5.3-Flash \
  --tp-size 4 --ep-size 4 --kv-cache-dtype fp8_e4m3 \
  --moe-runner-backend deep_gemm --reasoning-parser glm45 --tool-call-parser glm47 \
  --speculative-algorithm NEXTN --speculative-num-steps 3 \
  --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 \
  --max-running-requests 64 --mem-fraction-static 0.8 \
  --host 0.0.0.0 --port 30000 --enable-metrics
```

With `sgl-eval==0.1.2`, run the full dataset:

```bash
sgl-eval run gsm8k --base-url http://localhost:30000/v1 \
  --model zai-org/GLM-5.3-Flash --num-threads 16 \
  --max-tokens 16384 --temperature 1 --top-p 0.95 --seed 0 \
  --chat-template-kwarg enable_thinking=true --out-dir gsm8k-results
```

The tool-trace gate uses 64 requests at concurrency 16 after 24 discarded warmup requests, high reasoning effort, streaming, temperature 1, top-p 0.95, seeds starting at 1000, and a 16,384-token cap. The trace is not included in this patch. Acceptance is calculated from workload-bracketing metrics as `(Δgeneration_tokens_total − Δnum_requests_total) / Δspec_verify_calls_total`; health probes run outside measured workloads.

## Limitations

- Live top-k>1 speculative decoding with paged DSA remains untested: the existing framework guard rejects that configuration. It still exists on the rebased head. CPU tree tests do not substitute for that live coverage.
- Performance under speculative decoding remains mixed and is not fully established. Prior warmed on/off repeats varied by workload and run; the refreshed grammar-on gate is a correctness check, not a new controlled speedup comparison.
- Schema-dependent generation contexts and the pre-existing unbounded grammar cache still grow with schema cardinality. The fixed thinking payload is now shared: the previous real-tokenizer probe found 174,240 bytes per backend instead of that payload per schema. The prior 2,000-schema soak still showed scheduler RSS growth; this does not make total memory use constant.
- The replay uses non-strict tools. A `tool_calls` finish does not establish that every argument satisfies its tool's JSON schema.
