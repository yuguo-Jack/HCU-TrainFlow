# [Fix] multimodal: expand2square must return RGB for every PIL mode

[Upstream PR](https://github.com/sgl-project/sglang/pull/45195) · state: open · merged: False

## Original PR description

## What breaks

`expand2square` is used by LLaVA, Janus Pro and `process_images`. It only converted `L` images to RGB, and that conversion sat **after** the square-input early return, so:

| input | before |
|---|---|
| `L`, square | returned mode `L` (conversion skipped) |
| `LA`, `I;16`, `1`, non-square | `TypeError: color must be int or tuple` from `Image.new` |
| `P` | returned the palette image; the three-channel normalize fails later |
| `RGBA`, `CMYK` | returned a 4-channel image; same downstream failure |

Measured over 8 PIL modes x {square, non-square}: only non-square `L` worked.

Impact per caller:

- `processors/llava.py` feeds the result straight to `image_processor(image.convert("RGB"))`, so it only suffers the `TypeError` paths;
- `configs/janus_pro.py` does `np.transpose(x, (2, 0, 1))` assuming `[H, W, 3]`, so L/P/I;16 produce a wrong-shaped array;
- `mm_utils.process_images` passes the result to `image_processor.preprocess` with no conversion, so the non-RGB modes fail at normalize.

## Fix

```python
-    if width == height:
-        return pil_img
-    if pil_img.mode == "L":
-        pil_img = pil_img.convert("RGB")
+    if pil_img.mode != "RGB":
+        pil_img = pil_img.convert("RGB")
+    if width == height:
+        return pil_img
```

Any non-RGB mode is converted before the early return. `convert("RGB")` matches what `llava.py` already did explicitly; for `LA`/`RGBA` the alpha channel is dropped, which is the pre-existing behaviour of that call site. `smart_to_rgb` would composite against a sampled background instead — happy to switch if you prefer that.
