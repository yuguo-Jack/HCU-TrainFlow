# [Feat] [NPU] quantization: :sparkles: Support online W4A4 MoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/32602) · state: open · merged: False

## Original PR description

## Summary

Extend Ascend `--quantization mxfp4` to online FusedMoE with single-level packed MXFP4 expert weights and FP4 activations. Surrounding online Linear layers retain dual-level MXFP4; ignored or locally unaligned Linear layers remain unquantized. Offline ModelSlim packed weights are never requantized.

## Dependency and review scope

**This PR now depends on #43739.** On 2026-10-30, the W4A4 increment was rebased onto #43739 while retaining the existing main synchronization (`52604e1d46`). The subsequent ordinary merge consumes #43739 head `c0e0fab8e6`; current W4A4 head: `831438498f`. Base remains `main`; the diff against main includes the prerequisite until #43739 lands.

The inherited completion-tracked loader and lazy dynamic-op lookup are not independently reimplemented. General local-K/per-matmul fixes now belong to #43739 and were also synchronized to its separate #36426 validation branch. This PR inherits them via an ordinary merge; W4A4-specific functionality/shared refactors remain here, and #36426 is not included.

## Changes addressing the October 27 review

- **1 / 8 — loading and reload:** W4A8 and W4A4 online methods share an MXFP4 base and the existing `NPUOnlineMoEWeightLoader`. Sources start on meta, materialize lazily, and convert when each logical W13/W2 is complete. Registered loader attributes and source release/reload checks are retained. This still stages complete logical W13/W2 tensors, not individual experts.
- **2 — weight policy and dtype:** shared online MoE FP4 weight conversion explicitly uses `round_mode="rint", scale_alg=2, dst_type_max=7.25`. Unsupported sources fail clearly. Activation policies and dual-level Linear quantization are unchanged.
- **3 — shared preparation and explicit cast policy:** online/offline weights now use `prepare_mxfp4_moe_weight` with checked scale pairing and transpose views. W4A4 explicitly retains packed-byte casting (`customize_dtype=None`); the existing W4A8 entry preserves its FP4 unpack/cast arguments. The production default layout is unchanged. The user-reported Ascend 950 results below support retaining this policy rather than applying W4A8 cast requirements to W4A4.
- **4 / 7 — fusion boundaries:** online W4A4 explicitly opts in, only for plain bias-free SiLU on the no-A2A path. ModelSlim explicitly remains unfused. W2 allocates no fused component; runner construction and execution both consult W13 for the fusion decision. Preserve current-main MXFP8 clamp behavior and explicit rejection of unsupported W4A4 `swiglu_limit`.
- **5 — TP alignment:** both online MXFP4 configs share the block-size constant and check the bound group's local K before weight creation. Column/replicated layers do not divide K by TP.
- **6 — shared execution:** W4A8/W4A4 share the fused call body and `fused_matmul` naming, preserving scheme-specific dtypes and input-scale handling. Existing COUNT/CUMSUM wrapper behavior remains unchanged. MXFP8 is not migrated into this helper.
- **9 — duplicate lazy-op change:** inherited from #43739, with no separate W4A4 patch.

**Problem**

There are two issues in the online weight quantization:

1. `_quantize_weight_online` (L435) calls `npu_dynamic_mx_quant(..., round_mode="round")` and leaves `scale_alg` and `dst_type_max` at their defaults. For online FP4 weights, #43739 settled on `round_mode="rint", scale_alg=2, dst_type_max=7.25`, the #43367 settings. With both PRs merged, online W4A8 and online W4A4 would round FP4 weights differently.
2. The online/offline switch is `dtype in (float16, bfloat16)`, and every other dtype goes down the offline branch. With `--dtype float32`, for example, loading then fails with an `AttributeError` on `w13_weight_scale`, which the online path never creates.

**Fix**

```python
    @staticmethod
    def _quantize_weight_online(weight: torch.Tensor, fp4_dtype) -> Tuple[torch.Tensor, torch.Tensor]:
        """Return packed FP4 experts and paired [E, N, K/64, 2] block scales."""
        if not weight.is_npu:
            weight = weight.to(f"npu:{torch.npu.current_device()}")
        return torch.ops.npu.npu_dynamic_mx_quant(
            weight,
            dst_type=fp4_dtype,
            round_mode="rint",
            scale_alg=2,
            dst_type_max=7.25,
        )
```

Then key the branch on the offline checkpoint dtype, the way MXFP8 does:

```python
        weight = getattr(layer, f"{weight_prefix}_weight")
        # ModelSlim W4A4 stores packed uint8; anything else is an online source.
        online = weight.data.dtype != torch.uint8
```

With the loader from comment 1, unsupported source dtypes are already rejected in `create_weights` with a clear message. If W4A4 is meant to use a different rounding policy, could you document why and show its accuracy against BF16?

**(3/9)**

**Problem**

The weight and scale preparation here re-implements what the W4A8 path already shares, and it leaves out two safeguards that path has:

- `npu_format_cast(weight.data)` receives the online `float4_e2m1fn_x2` tensor with no `customize_dtype`/`input_dtype`. `_is_nz_aligned` lets unknown dtypes through, so the op runs without being told the data is FP4. `prepare_w4a8_mxfp_weight` passes `input_dtype=fp4`, and the dual-level Linear path uses `view(torch.int8)` plus `customize_dtype`.
