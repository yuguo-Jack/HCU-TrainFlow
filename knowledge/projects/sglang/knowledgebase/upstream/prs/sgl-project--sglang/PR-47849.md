# [Perf] kimi-k3: Reduce latent-up weight memory on TP8 decode workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/47849) · state: open · merged: False

## Original PR description

## Motivation

Kimi-K3 keeps the BF16 latent MoE up-projection replicated on every TP rank. For the 92 MoE layers with a `[7168, 3584]` weight, storing only one eighth on each TP8 rank saves **4,136,108,032 parameter bytes (3.852 GiB) per GPU**. Memory-constrained decode workers can use the freed budget for KV cache.

This is a memory optimization with a communication cost. The measured projection tail is slower at most batch sizes. Exact-version full-model and matched service experiments are now complete: code alone changes output throughput by **+2.24%** at MRR512 on the fixed 64K/1K workload below, with a latency tradeoff.

**This PR is open for review and CI; numerical acceptance remains unresolved.** The complete GSM8K evaluation passes the experiment's predeclared noninferiority criterion, but the stricter common-prefix logprob/top-1 gate fails. Numerical diagnosis isolates BF16 projection rounding after changing the GEMM output width. Performance results characterize the unchanged candidate; they do not resolve numerical acceptance or establish merge readiness.

## Modifications

- Use `ColumnParallelLinear` and its checkpoint loader for physical output-column sharding. Reuse `MultimemAllGatherer` to return the complete output on each rank; one workspace is shared across layers and keyed by the TP group.
- Enable the layout for CUDA decode workers with TP8, BF16 unquantized latent projections, hidden/latent widths 7168/3584, shared experts, no MoE A2A, no attention DP or layernorm SP, and the existing multicast-capable K3 fusion. Other configurations retain replicated weights. No new configuration flag.
- Keep the existing small-batch `gemm_ag` arithmetic. Its host entry accepts either the replicated weight or a local `[896, 3584]` shard and selects the local pointer before launch. The producer/consumer arithmetic and tail additions are unchanged.
- Larger batches use the existing gatherer's NCCL fallback. Keep ordinary prefill/mixed servers on the replicated layout because the gather cost is substantial for those batches.
- Extend the existing collective and parallel-placement tests.

Related work: #47075 and #44985 compute row slices of replicated up-projection weights on AMD; #45126 shards the latent **down/front** projection; #46474 tunes SM107 small-batch kernels and touches the same `gemm_ag` files. This PR changes physical up-weight storage on CUDA decode workers. Concurrent edits to the GEMV interface will need coordination.

### Matched service experiments (same exact commits)

Four groups, two fresh services each: A=reference512, B=candidate512, D=reference272, C=candidate272, where the number is both MRR and maximum decode graph batch. Order A1/B1/B2/A2 then D1/C1/C2/D2. Each run has 512 warmup requests and 2048 formal requests, both at concurrency 512. Total 16,384 formal requests; warmup excluded.

aiakperf 1.6.3: fixed 65,536 input/1,024 output tokens, 16 client processes, seed 42, temperature 0, ignore EOS, streaming. Random input content does not mean random lengths. Common MF 0.97, context 69632, output reservation 1024, TP8/DCP8/fi_a2a, BF16 KV/Mamba, Radix disabled, extra slots 16, tokenizer/detokenizer 32. Fake-prefill decode throughput excludes real prefill and P/D network transfer.

All arms start with byte-identical complete baseline-only FlashInfer tactic caches, isolated writable/JIT caches, and the same input fingerprints. Cache hashes remain unchanged through measurement. A task-local aiakperf copy sets deterministic request IDs/bootstrap rooms and records input hashes before timing; upstream fake handoff hashes request IDs, so matching token lengths alone would not match requests. All 32 tokenizer workers are ready before formal timing. No profiling or diagnostic model hooks.

The combined gain is measured directly, not a sum of individual percentages. Capacity/combination pairs span the two temporal blocks and do not have the same interleaving as the within-block code comparison. Two repetitions support this hardware/workload only; they are not a broad statistical performance guarantee.

The exact saved parameter bytes were also verified in the full model. At MRR512, logged loaded weights decrease 195.81→191.96 GiB/GPU and logical KV capacity increases 14,364,672→15,559,680 tokens (+8.32%); per-GPU KV storage increases 46.24→50.08 GiB. Under DCP8, log allocation slots are per-GPU, while `max_total_num_tokens` is logical aggregate capacity. Thus memory savings permit a larger running batch, but do not remove the projection/communication latency cost.

All eight runs complete without request failure, OOM, CUDA/scheduler error, or KV retraction. Latency must be assessed alongside throughput; the strict numerical gate remains unresolved. These exact-version results replace the earlier prototype evidence and do not inherit its +10.93% claim.
