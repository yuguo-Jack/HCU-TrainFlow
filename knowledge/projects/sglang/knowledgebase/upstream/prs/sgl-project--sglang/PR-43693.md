# [AMD][Diffusion] Sol-Attn: run on ROCm gfx1201 with aiter's Sol kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/43693) · state: open · merged: False

Depends on the gfx1201 Sol-Attn op in aiter (parts 3-4 of the series: previews Shan2L/aiter#2 HIP kernel, Shan2L/aiter#3 code object), which follows ROCm/aiter#6390. ## Motivation

`SOL_ATTN` (NVlabs Sol-Attn, block-sparse attention with a dense guard for the first steps / layers) is rejected on ROCm, because its only kernel is the CUDA `sol_attn` package. aiter is adding `aiter.gfx1201_sol_attention` for Radeon RDNA4 (gfx1201: Radeon AI PRO R9700 / R9600D, Radeon RX 9070 series). It takes the same arguments as `sol_attn.sol_attn` with `thresh_type="diag"` (per-query-block routing on `tau`, plus sink tokens), and runs Sage-style INT8 QK^T / FP8 PV on the selected blocks.

## Modifications

- **Platform.** On ROCm, `SOL_ATTN` is selected when the GPU is gfx1201 and the installed aiter provides `gfx1201_sol_attention`. Otherwise it raises an explicit error, as before but with the requirement in the message.
- **Sparse path.** On ROCm, `SolAttnImpl` calls `aiter.gfx1201_sol_attention` with the configured `tau`, `sink_tokens`, `sink_start` and the layer's `softmax_scale`. Only `thresh_type="diag"` is supported (anything else raises); `kv_splits` is a CUDA scheduling knob and is not used.
- **Dense guard.** `dense_backend` gains an `aiter_sage` option, the default on ROCm. It reuses `AITERSageImpl` (so `gfx1201_sage_attention` with #43687), including the packed trailing-padding handling of `forward_varlen`.
- **Import.** `flash_attn_varlen_func` is imported lazily, so the module loads on ROCm.
- **Docs.** `attention_backends.mdx` lists gfx1201 support and the new `dense_backend` value.

CUDA behaviour is unchanged: the default dense backend stays `fa`, and the CUDA path still calls `sol_attn`.

Unit tests are in `test/unit/test_sol_attn_backend.py` and use stubbed `aiter` / platform, so they need no GPU. They cover platform selection and its errors, the arguments passed to `gfx1201_sol_attention`, the `thresh_type` check, and the `aiter_sage` dense guard for `forward` and `forward_varlen`.

## Accuracy and speed

MiniMax-H3, with the case parameters of `minimax_h3_t2va_2gpu_h100`: t2va, 1344x768, 4 s, 8 steps, seed 42, TP2, on 2x R9700 (PyTorch 2.11 / ROCm 7.15), same flags as that case. Sol rows: `--attention-backend sol_attn --attention-backend-config dense_steps=3 --component-attention-backends text_encoder=torch_sdpa,transformer=sol_attn` (default `tau=1.0`, dense layers `0,1`; `dense_steps` lowered from the default 10 because the case has 8 steps). Video PSNR and audio cosine are against the `torch_sdpa` run.

| attention | denoise stage | vs BF16 SDPA | video PSNR / audio cos vs SDPA run |
|---|---|---|---|
| `torch_sdpa` (BF16) | 152.3 s | 1.00x | - |
| `torch_sdpa`, K/V token order reversed (rounding-only noise floor) | 152.3 s | - | 34.41 dB / 0.991 |
| `aiter_sage` (#43687, aiter part 2) | 94.2 s | 1.62x | 32.14 dB / 0.897 |
| `sol_attn`, this PR, aiter part 3 (HIP kernel) | 91.2 s | 1.67x | 32.14 dB / 0.948 |
| `sol_attn`, this PR, aiter part 4 (code object) | 89.4 s | 1.70x | 32.30 dB / 0.946 |

At this short sequence (4 s video), 3 of 8 steps and 2 of 50 layers run dense, so Sol gains little over dense Sage. The sparse kernel pays off at longer sequences and more steps: on the 15 s / 362-frame ref2av case (29 steps) in LightX2V with its shipped MiniMax-H3 Sol config, the same kernels give 211.6 -> 63.7 s (part 3) / 60.8 s (part 4) per DiT step, against 89.1 s for dense Sage (part 2).

The R9700 runs used `sgl-kernel` built for gfx1201 (#43679), and the custom all-reduce was disabled because R9700s connect over PCIe (#43676).

- Shan2L · comment · 2026-10-11T23:35:18Z · [source](https://github.com/sgl-project/sglang/pull/43693#issuecomment-6115163826)

Note on run-to-run variation in the quality numbers above.

Repeating the same 8-step config (same seed, same tree) gives slightly different videos. For example, the asm path measured 32.84 dB in one run and 32.14 dB in another. We traced this down and it does **not** come from the attention kernels:

- `gfx1201_sage_attention` (asm and HIP) is bitwise deterministic: repeated calls on dirty memory, and 60 calls under concurrent side-stream load, give identical outputs.
- Hashing every DiT module across runs, the first divergence is in two **FP32 GEMMs** that are not part of this PR: the TimeEmbedder `proj_in` (`[1,256] x [2688,256]^T`) and the final-layer `video_out` (`[32704,5376] x [48,5376]^T`). Inputs, weights and bias are bitwise identical across runs, and recomputing in the same process gives the same result. Across processes, however, hipBLASLt/Tensile sometimes picks a different solution for the same shape, e.g. `MT16x8x64` vs `MT64x64x16`. In 12 runs, the output groups matched the kernel-name groups exactly. The 1-ulp difference is then amplified by the 50 DiT blocks over 8 steps.

So expect about ±0.7 dB PSNR jitter between identical runs on this stack, for every attention backend including SDPA. Only differences larger than that are meaningful. We are reproducing the per-process kernel choice standalone to report it to hipBLASLt.


- Shan2L · comment · 2026-10-12T01:01:16Z · [source](https://github.com/sgl-project/sglang/pull/43693#issuecomment-6115895828)

Follow-up: the per-process kernel choice is a hipBLASLt bug. For untuned shapes, the heuristic falls back to a solution list ordered by host pointer value, so the kernel that runs depends on the heap layout. It is fixed on rocm-libraries `develop` (ROCm/rocm-libraries#11340) but not in any TheRock release yet. Reported with a standalone repro in ROCm/rocm-libraries#13476, with a backport to 10.1 in ROCm/rocm-libraries#13477.
