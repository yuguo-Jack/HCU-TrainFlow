# Sampler: gather sampled-token logprobs before log

[Upstream PR](https://github.com/sgl-project/sglang/pull/41111) · state: closed · merged: False

## Original PR description

With `return_logprob` and no top-k or token-id logprob requests, the standard sampling path built `torch.log(probs)` over `[bs, vocab]` and clamped the whole tensor in place, only to gather one value per row. Gather the sampled entries first and apply the same log and clamp to them. Values are bitwise identical; other logprob requests keep the full-tensor path.

## Motivation

When only sampled-token logprobs are requested, the full `[bs, vocab]` log-probability tensor is unnecessary. We only need one probability per sampled token.

The existing path performs a full-tensor `torch.log(probs)` followed by an in-place clamp, then gathers the sampled entries. This introduces several `[bs, vocab]` memory passes and a full-tensor allocation.

This change gathers the sampled probabilities first, then applies `log` and `clamp` only to the resulting `[bs]` tensor.

## Modifications

- In the standard sampling path, keep a reference to `probs` instead of computing `torch.log(probs)` when:
  - `return_logprob` is enabled.
  - `SGLANG_RETURN_ORIGINAL_LOGPROB` is not enabled.
  - `logprobs_via_logsoftmax_kernel` is `None`.
  - No request in the batch requires top logprobs or token-id logprobs.
- In the `return_logprob` path, compute:
  `torch.log(probs.gather(1, ids)).view(-1).clamp_(min=finfo.min)`
- Keep `compute_logprobs` and the existing full-tensor path unchanged for all other cases.

## Accuracy Tests

Compared baseline and candidate using identical logits and PyTorch seeds across:

- Batch sizes: 1, 8, 64, 256
- Sampling modes: top-p/top-k filtered, simple, min-p
- Sampled-token logprobs with `top_logprobs=0`
- Top logprobs and token-id logprobs, which use the unchanged path

Sampled token IDs and `next_token_logprobs` are `torch.equal()` across both arms. Top-logprob and token-id outputs are also equal.

`test_sampling_mask.py::TestSamplingMaskCapture` parity was verified, along with the CPU sampling test suite.

The log and clamp operations are applied to the same sampled probability values in the same order, so the resulting token logprobs are bitwise identical.

## Speed Tests and Profiling

Measured `sampler_logprob_forward_us` using CUDA events on NVIDIA B300 SXM6 PC x1.

8 trials per arm after 2 warmup trials, interleaved ABBA. Lower is better.

| Arm | n | Median |
| --- | ---: | ---: |
| Baseline | 8 | 865.28 us |
| Candidate | 8 | 715.74 us |

This is a **17.28% reduction** in `Sampler.forward` time for the measured workload (`0.8272x` baseline).

The benchmark targets `bs=256` with sampled-token logprobs and no top-k/token-id logprob requests.

The optimization removes the full `[bs, vocab]` `log` and clamp work and avoids the corresponding full-tensor intermediate for this case.

The gain does not apply to greedy batches, deterministic mode, `SGLANG_RETURN_ORIGINAL_LOGPROB`, or batches containing requests that require top or token-id logprobs.
