# [Perf] paged-experts: exact size pinning

## Motivation

This PR aims to decrease memory footprint.

Currently, the Paged Experts Feature (#42557) keeps every expert of the model in page-locked host memory. torch's pinned allocator rounds each allocation up to a power of two, so **a 402 MB `w13` tensor pins 512 MiB**. Across a model this pins about a third more than the experts need on Qwen3-30B-A3B, and 85% more on gpt-oss-20b. Pinned memory cannot be swapped, and it is often what decides whether a model fits: WSL2, for example, caps it at about half of RAM.

## Modifications

`store.py`:
- The pinned host store allocates through HiCache's host allocator (`alloc_with_host_register` with `HostTensorAllocator`). That maps exactly the tensor's size (huge pages with `SGLANG_HUGEPAGE_SIZE`), pre-faults it and registers it with CUDA.
- The gather kernel reads it through `cudaHostGetDevicePointer` as before.
- A store only staged for a repack stays pageable, as before.

## Accuracy Tests

The experts' bytes are unchanged; only their allocation differs.

**Kernel test.** The store pins exactly its size, and the gather kernel reads it.

**Paged vs unpaged, 4-layer test models** (E=32, top-4, K=8; prompt and greedy decode logprobs; RTX 5070 Ti; main 2d3de82633 and this PR in one run):

| model | runner | this PR | main |
|---|---|---|---|
| Qwen3-MoE bf16 | triton | identical | identical |
| AWQ int4 | Marlin | decode max 0.014 | decode max 0.014 |
| compressed-tensors NVFP4 | Marlin | median max 0.078, unpaged floor 0.059 | median max 0.059, unpaged floor 0.063 |

Marlin is not run-to-run reproducible, so the Marlin formats are judged against the spread of two unpaged servers (the floor); bf16 on triton is bit-identical. Each check has a negative control that must fail (a perturbed RMSNorm eps on bf16 and AWQ, unnormalized top-k weights on NVFP4), and all three do.

## Speed Tests and Profiling

Same machine as #42557: RTX 5070 Ti 16 GB (PCIe 5.0 x16, 62 GB RAM), Qwen3-30B-A3B, 10,240 KV tokens and 4 slots, prefix caching off, 16 ShareGPT warm-up requests discarded. Decode tok/s is `1000 / median TPOT` over 8 ShareGPT prompts sent one at a time (256 output tokens each); TTFT and ITL are from the same requests. 4 requests: 16 ShareGPT prompts from 4 clients at once (output tok/s). 2k TTFT: 4 natural ~2,048-token prompts. main (upstream 2d3de82633) is measured first and last in the same run as this PR; both values are shown, and a difference inside their spread is no difference. Pinned host memory is `Shmem` in `/proc/meminfo` once serving (the new allocator maps the store shared; torch's pinned allocator counted there too).

Decode, TTFT and throughput are unchanged; the store pins a quarter less on all three formats (power-of-two rounding cost a third more than the experts need). Pre-faulting the exact-size mapping adds about 6 s to FP8's weight load (27 GiB of store); the 45.2 s is one slow boot of main.

HiCache pairs this allocator with explicit unregister calls in `HostKVCache.destroy()`, while `HostExpertStore` has no equivalent cleanup.

Please pair registration with unregister before releasing the mapping, after outstanding GPU reads have finished. Tie cleanup to the actual buffer lifetime: the new test retains `host` after its temporary `HostExpertStore` is gone, so a store destructor alone would be too early. One focused allocation/release regression test should be enough.

Thanks, good catch! Fixed in a32258a322, and the allocation is simpler for it:

- Each pinned store tensor is now shared memory of exactly its size (`memfd` + `torch.UntypedStorage.from_file`), registered with CUDA in place, as multimodal_gen's layerwise offload pins its stores. It no longer goes through HiCache's allocator: that allocator pairs with an explicit `destroy()`, and the tensor it returns releases its mapping itself, with no point to unregister before that. Tying the unregister to the buffer's lifetime on top of it took a second tensor over the same pages, only to have an object whose death we could hook. With memory we allocate and register ourselves, the finalizer sits on the one storage that owns the pages, so the registration and the memory share a single lifetime.
- A `weakref.finalize` on the storage ties the registration to the buffer's lifetime: it runs when the last tensor or view on the storage is freed, synchronizes the device so queued page-in copies and gather reads have finished, and unregisters the pages while they are still mapped; then torch releases them. A failed unregister is logged.
- New kernel test `test_store_unregisters_its_pages_once_the_last_tensor_is_freed`: a slice that outlives its `HostExpertStore` keeps the pages registered (with a non-blocking copy still queued); once it is freed, `cudaHostUnregister` on the address fails because nothing is registered there anymore.
