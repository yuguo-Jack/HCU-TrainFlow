#  [NPU][Quant] Fix ModelSlim W8A8 loading for Qwen3.8-27B-W8A8: resolve fused in_proj_qkvz scheme, quantize vision encoder, flatten 3-D inputs in NPU W8A8 kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/36426) · state: open · merged: False

## Original PR description

Summary
ModelSlim W8A8_DYNAMIC checkpoints of Qwen3.5 (GDN hybrid, e.g. Qwen3.8-27B-w8a8) load incorrectly on Ascend NPU: the fused linear-attention projections and the whole vision tower silently fall back to unquantized loading
(int8 weights copied raw into bf16 params → garbage output, with only not found in params_dict warnings), and once quantized, the first vision-tower matmul crashes the server at warmup with an ACL parameter error.
Three independent bugs are fixed:
1. Unresolved fused-GDN scheme — the model side fuses in_proj_qkv + in_proj_z into in_proj_qkvz (and in_proj_b + in_proj_a into in_proj_ba) while the ModelSlim checkpoint records the unfused per-projection names.
   ModelSlimConfig._quant_prefix_candidates() now maps the fused names onto their shards, so in_proj_qkvz resolves to W8A8_DYNAMIC instead of falling through to UnquantizedLinearMethod (48 layers × missing
   weight_scale/weight_offset).
2. Vision encoder forced unquantized — Qwen3VLForConditionalGeneration hardcoded quant_config=None for Qwen3VLMoeVisionModel, but ModelSlim checkpoints quantize the vision tower (attn.qkv/attn.proj/mlp.linear_fc1 are
   W8A8_DYNAMIC). The config is now forwarded when isinstance(quant_config, ModelSlimConfig) (same gating as kimi_vl_moonvit.py); GPTQ/AWQ/BitsAndBytes paths keep quant_config=None exactly as before.
3. NPU W8A8 kernels reject 3-D input — the vision tower feeds linears (seq, 1, hidden) activations (x.unsqueeze(1) in Qwen3VLMoeVisionModel.forward); the bf16 path broadcasts fine but
   npu_dynamic_quant/npu_quantize/npu_quant_matmul only accept 2-D (ACL error 161002). Both NPUW8A8Int8LinearMethod and NPUW8A8Int8DynamicLinearMethod.apply now flatten leading batch dims into m for the NPU ops and restore
   the layout afterwards. 2-D inputs (all language-model layers) are byte-identical.

Changes
python/sglang/srt/layers/quantization/modelslim/modelslim.py
_quant_prefix_candidates(): add fused-GDN candidates (in_proj_qkvz → in_proj_qkv/in_proj_z, in_proj_ba → in_proj_b/in_proj_a) and model.visual. ↔ visual. prefix variants.
python/sglang/srt/models/qwen3_vl.py
Forward quant_config to Qwen3VLMoeVisionModel when it is a ModelSlimConfig.
python/sglang/srt/hardware_backend/npu/quantization/linear_method_npu.py

Regarding the first bug described in this PR, **“Unresolved fused-GDN scheme”**, thanks for identifying and fixing the issue. I added temporary debug logging around `packed_modules_mapping` and the ModelSlim quantization lookup to provide some additional runtime information.

For the Qwen3.8-27B-W8A8 checkpoint on NPU, the raw mapping received by ModelSlim currently has the following mixed structure:

```jsonc
{
  // From Qwen3_5ForCausalLM.packed_modules_mapping
  "qkv_proj": [
    "q_proj",
    "k_proj",
    "v_proj"
  ],
  "gate_up_proj": [
    "gate_proj",
    "up_proj"
  ],
  "in_proj_qkvz": [
    "in_proj_qkv",
    "in_proj_z"
  ],
  "in_proj_ba": [
    "in_proj_b",
    "in_proj_a"
  ],

  // Appended to the same mapping by the NPU loader
  "visual": {
    "qkv_proj": [
      "qkv"
    ],
    "gate_up_proj": [
      "gate_proj",
      "up_proj"
    ]
  },
  "vision_model": {
    "qkv_proj": [
      "q_proj",
      "k_proj",
      "v_proj"
    ],
    "proj": [
      "out_proj"
    ]
  },
  "model": {
    "qkv_proj": [
      "q_proj",
      "k_proj",
      "v_proj"
    ],
    "gate_up_proj": [
      "gate_proj",
      "up_proj"
    ],
    "fused_qkv_a_proj_with_mqa": [
      "q_a_proj",
      "kv_a_proj_with_mqa"
    ],
    "index_qkv_proj": [
      "index_q_proj",
      "index_k_proj"
    ]
  }
}
```

This mapping is used by ModelSlim to resolve an SGLang runtime fused-module name to the corresponding checkpoint-side entry in `quant_model_description.json`. ModelSlim then uses the resolved checkpoint entry to select the quantization scheme, such as W8A8/INT8 or FLOAT.

The mixed mapping is constructed from two sources:

1. The Qwen3.5 model class declares a flat model-specific mapping, including:

   ```python
   "in_proj_qkvz": ["in_proj_qkv", "in_proj_z"],
   "in_proj_ba": ["in_proj_b", "in_proj_a"],
   ```

   Source: [`Qwen3_5ForCausalLM.packed_modules_mapping`](https://github.com/sgl-project/sglang/blob/cebbaacae45ebf669101dde3aac4817ecbb038e0/python/sglang/srt/models/qwen3_5.py#L1303-L1311)

2. On NPU, the loader retrieves that model-class mapping and appends the nested `"model"`, `"visual"` and `"vision_model"` mappings.

   Source: [`_get_quantization_config()` NPU mapping injection](https://github.com/sgl-project/sglang/blob/cebbaacae45ebf669101dde3aac4817ecbb038e0/python/sglang/srt/model_loader/loader.py#L218-L251)

The resulting object therefore mixes two different value types:

```text
Dict[str, List[str] | Dict[str, List[str]]]
```

while the original `packed_modules_mapping` contract is a flat:

```text
Dict[str, List[str]]
```

The current ModelSlim implementation selects only one nested subgroup:

```python
key = "model"
if "vision_model" in prefix:
    key = "vision_model"
elif "visual" in prefix:
    key = "visual"

packed_modules_mapping_subset = self.packed_modules_mapping.get(key, {})
```

Source: [`ModelSlimConfig.get_quant_method()`](https://github.com/sgl-project/sglang/blob/cebbaacae45ebf669101dde3aac4817ecbb038e0/python/sglang/srt/layers/quantization/modelslim/modelslim.py#L266-L285)

For a language-model layer, this means ModelSlim uses only:

```json
{
  "qkv_proj": [
    "q_proj",
    "k_proj",
    "v_proj"
  ],
  "gate_up_proj": [
    "gate_proj",
    "up_proj"
  ],
  "fused_qkv_a_proj_with_mqa": [
    "q_a_proj",
    "kv_a_proj_with_mqa"
  ],
  "index_qkv_proj": [
    "index_q_proj",
    "index_k_proj"
  ]
}
```

The model-declared outer mappings for `in_proj_qkvz` and `in_proj_ba` are still present in the raw object, but become invisible after the `"model"` subgroup is selected.

Consequently, ModelSlim cannot resolve:

```text
in_proj_qkvz -> in_proj_qkv / in_proj_z
in_proj_ba   -> in_proj_b / in_proj_a
```

before querying `quant_model_description.json`. This causes incorrect downstream handling of the W8A8 `in_proj_qkvz` projection and the floating-point `in_proj_ba` projection.

At least three potential fix directions appear possible:

1. Add `in_proj_qkvz` and `in_proj_ba` to the NPU loader’s hard-coded `"model"` subgroup.
2. Add Qwen3.5 GDN fused-name aliases inside ModelSlim, as proposed in this PR.
3. Teach ModelSlim to understand the existing mixed mapping structure by retaining the model-declared outer flat mappings and applying the selected NPU subgroup as a scoped override.

I am providing this mainly as runtime debug information related to the first bug. The preferred fix likely needs discussion because these alternatives have different compatibility and maintenance trade-offs.


- fishAndShrimp · comment · 2026-08-26T14:07:00Z · [source](https://github.com/sgl-project/sglang/pull/36426#issuecomment-5426520562)

Regarding the second bug described in this PR, **“Vision encoder forced unquantized”**, I noticed a possible compatibility issue in the new prefix-handling logic in `_quant_prefix_candidates()`.

Previously, every candidate that did not start with `language_model.` would also get a `language_model.` version:

```python
if candidate.startswith("language_model."):
    candidates.append(candidate.removeprefix("language_model."))
else:
    candidates.append(f"language_model.{candidate}")
```

The PR changes this to:

```python
if candidate.startswith("language_model."):
    candidates.append(candidate.removeprefix("language_model."))
elif candidate.startswith("model.visual."):
    candidates.append(candidate.removeprefix("model."))
elif candidate.startswith("visual."):
    candidates.append(f"model.{candidate}")
```

The new `model.visual.*` / `visual.*` handling is needed for the quantized vision encoder. However, changing the original `else` into `elif` also means that ordinary candidates no longer get the old `language_model.` fallback.

For example, for this input:

```text
model.layers.0.mlp.down_proj
```

the old code generated these candidates:

```text
model.layers.0.mlp.down_proj
model.layers.0.block_sparse_moe.down_proj
language_model.model.layers.0.mlp.down_proj
language_model.model.layers.0.block_sparse_moe.down_proj
```

With the code in this PR, only these candidates are generated:

```text
model.layers.0.mlp.down_proj
model.layers.0.block_sparse_moe.down_proj
```

Therefore, these two candidates disappear:

```text
language_model.model.layers.0.mlp.down_proj
language_model.model.layers.0.block_sparse_moe.down_proj
```

The `language_model.` fallback was added for checkpoints whose quantization metadata keeps that outer prefix, so removing it may affect those checkpoints.

I confirmed the candidate-list difference through static code analysis, but I have not reproduced an actual runtime failure. Would it be safer to keep the language-model prefix handling and the vision prefix handling as two independent operations? For example:

```python
for candidate in list(candidates):
    if candidate.startswith("language_model."):
        candidates.append(candidate.removeprefix("language_model."))
    else:
        candidates.append(f"language_model.{candidate}")

    if candidate.startswith("model.visual."):
        candidates.append(candidate.removeprefix("model."))
    elif candidate.startswith("visual."):
        candidates.append(f"model.{candidate}")
```

This keeps the new vision-prefix support while preserving the previous `language_model.` fallback behavior.

### Also required for the `W8A8_MXFP8` path

Confirming this PR is needed beyond the int8 `W8A8_DYNAMIC` case in the issue. We hit the same failure with a ModelSlim **`W8A8_MXFP8`** checkpoint of Qwen3.5-27B on Ascend 950, served through the offline ModelSlim path (`--device npu --tp 1`, scheme auto-detected from `quant_model_description.json`).

**Before this PR**, every GDN layer lost its scheme and then its scales:

```
Unsupported Linear modelslim scheme: [''] in layer: model.language_model.layers.0.linear_attn.in_proj_qkvz
Unsupported Linear modelslim scheme: [''] in layer: model.language_model.layers.0.linear_attn.in_proj_ba
Parameter model.layers.0.linear_attn.in_proj_qkvz.weight_scale not found in params_dict
```

repeated for every linear-attention layer, plus the vision tower (`visual.blocks.*.attn.qkv_proj`, `attn.proj`, `mlp.linear_fc1`, `mlp.linear_fc2`, `visual.merger.*`). The server started and answered, but the output was garbage.

**Why this is not int8-specific.** Three of the four changes here are naming/mapping fixes that run *before* scheme dispatch:

- `loader.py`: `in_proj_qkvz -> [in_proj_qkv, in_proj_z]`, `in_proj_ba -> [in_proj_b, in_proj_a]`
- `modelslim.py::get_quant_method`: redirect to the unfused component name the checkpoint actually stores
- `modelslim.py::_quant_prefix_candidates`: `model.visual.` <-> `visual.`

The lookup fails before `get_linear_scheme()` ever chooses between `ModelSlimW8A8Int8` and `ModelSlimMXFP8Scheme`, so the scheme string in the checkpoint is irrelevant: it returns `None`, the layer becomes `UnquantizedLinearMethod`, and the float8 weights are copied raw into bf16 parameters. Only the fourth change (folding 3-D vision inputs to 2-D in the W8A8 int8 kernels) is int8-specific; `NPUMXFP8LinearMethod` already reshapes to 2-D, so MXFP8 needs nothing there.

**After this PR**: no `Unsupported Linear modelslim scheme` warnings, no `not found in params_dict`, and generation is correct again.

**One caveat for MXFP8, separate from this PR.** Once the vision tower receives the ModelSlim config, `ModelSlimMXFP8Scheme.create_weights` sizes the weight-scale placeholder as `K // 32`, one column short for the vision MLP down projection. A ModelSlim `W8A8_MXFP8` export of Qwen3.5-27B stores it as:

```
model.visual.blocks.0.mlp.linear_fc2.weight        [1152, 4304]   W8A8_MXFP8
model.visual.blocks.0.mlp.linear_fc2.weight_scale  [1152,  135]   W8A8_MXFP8
```

`ceil(4304 / 32) = 135` while the placeholder allocates 134, so the parameter fails to load; 135 is also odd, which the `reshape(n, k // 2, 2)` pair layout in `process_weights_after_loading` cannot consume. Rounding up and padding the odd scale count is in sgl-project/sglang#32745. It is independent of this PR and does not block it -- the same block's `linear_fc1` has `K=1152` with 36 scales and is unaffected.
