# [Fix] [NVIDIA] trtllm_mla: Reject prefill and skip the decode counter on SM12x

[Upstream PR](https://github.com/sgl-project/sglang/pull/28837) · state: open · merged: False

## Original PR description

## Motivation

On SM120 (RTX PRO 6000, RTX 50 series; SM121 from the code), `trtllm_mla` fails today:

1. Decode fails on SM12x because the backend passes a counter buffer that FlashInfer's XQA kernel rejects. Since v0.5.17 (#31927), `TRTLLMMLABackend` always passes `multi_ctas_kv_counter_buffer` for its default `trtllm-gen` backend without naming a `backend`, so FlashInfer's `auto` picks XQA off SM10x ([`mla/_core.py:4205-4210`](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/mla/_core.py#L4205-L4210)), and XQA rejects the counter ([`_core.py:4291-4294`](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/mla/_core.py#L4291-L4294)). With CUDA graphs the server never becomes ready; without them the first decode fails.
2. Prefill: the TRTLLM MLA prefill kernel is SM10x only. With prefill CUDA graphs off (the default for DeepSeek-V3/R1 with `trtllm_mla` prefill), the first prefill fails with `Unsupported architecture` (#24633). With the default breakable prefill graph on other MLA models, the backend falls back to FlashInfer's MLA prefill inside the graph, and requests succeed (on main, 8- and 6,000-token prompts with `--prefill-attention-backend trtllm_mla --decode-attention-backend triton`).

Fixes #24633 for server launches, with the clearer startup error proposed there. Default MLA launches on SM12x use `triton` and don't change. One behavior change to weigh: the new prefill check also refuses those prefill-graph launches that work on main (question 1).

## Modifications

1. `TRTLLMMLABackend` skips the counter when `is_sm120_supported()` (SM120 and SM121). SM10x keeps it; nothing else in the decode call changes. SM11x is left as is: `auto` picks XQA there too, but XQA's MLA kernel exists only for SM120 and SM121 ([`xqa.py:633-634`](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/xqa.py#L633-L634)), so decode fails on SM11x with or without the counter.
2. `_mla_kv_cache_dtype_checks` keeps main's Blackwell and KV dtype checks (now also accepting the documented `bfloat16` alias) and adds one: `trtllm_mla` as the resolved prefill backend off SM10x fails at startup with "TRTLLM MLA prefill requires SM10x (datacenter Blackwell). Please use a different prefill backend, such as --prefill-attention-backend flashinfer." On SM11x and SM12x this refuses `--attention-backend trtllm_mla` without a prefill override and `--prefill-attention-backend trtllm_mla`.
3. New test `test/registered/attention/test_trtllm_mla_sm120_decode.py` (`1-gpu-small`, the RTX 5090 runner, in `base-b`). It starts servers with FlashInfer prefill, `trtllm_mla` decode and CUDA graphs, with BF16 and `fp8_e4m3` KV, and checks that `--attention-backend trtllm_mla` is refused. The model is `DEFAULT_MLA_MODEL_NAME_FOR_TEST` with dummy weights, cut to 2 layers and 128 heads through `--json-model-override-args`.
4. Docs (`attention_backend.mdx`): on SM12x, TRTLLM MLA is decode only, with exactly 128 query heads per rank (XQA's requirement, so DeepSeek-V3/R1 needs `--attn-dp-size` equal to `--tp`), BF16 or `fp8_e4m3` KV, and the default `--speculative-attention-mode prefill`.

#35807 (open) edits the same code and keeps the counter for dense decode; a merge that keeps its decode block brings the SM12x failure back. I'm happy to rebase onto it if it lands first.

Questions (if nobody has a preference, the PR stays as is):

1. Should the prefill check allow `trtllm_mla` prefill while the prefill CUDA graph is on, since it then runs FlashInfer's kernel anyway? I refused it so the error names the kernel that actually runs.
2. Would a startup check for the 128-head limit help? Today it fails at graph capture.

## Accuracy Tests

One RTX PRO 6000 (SM120), main's pins (torch 2.14.1, FlashInfer 0.7.2). The head `cb802d42a6` is this PR rebased onto main `03a27e2a17`; the conflict was in `test_server_args.py` only.

- On the GPU: `test_trtllm_mla_sm120_decode.py` passes both tests (both servers, BF16 and `fp8_e4m3` KV, with CUDA graphs, 253 s), and `test_sm12x_decode_omits_trtllm_gen_counter` passes, with nothing skipped.
- On CPU: `test_server_args.py`, 357 passed.
- With main's code (before the rebase), both decode servers exit at graph capture, the refusal case gets no error, and the 4 new-behavior `TestTrtllmMlaArchGuard` tests fail.
- Servers (DeepSeek-V2-Lite config, dummy weights, 2 layers, 128 heads), measured on an earlier head with the same backend change:

| setup | main | this PR |
| --- | --- | --- |
| `--attention-backend trtllm_mla`, graphs off | first prefill fails | refused at startup |
| FlashInfer prefill, `trtllm_mla` decode, BF16 or FP8 KV, graphs off | first decode fails | serves every request |
| the same with CUDA graphs | never ready | serves every request |

Dummy weights only show that decode completes, so I replayed the recorded decode call against an fp32 reference: relative L2 error 2.2e-3 with BF16 KV and 2.3e-2 with FP8 KV (XQA rounds the softmax weights to e4m3), and references with a deliberate mistake score at least 3 times worse.

In CI, the registered test jobs, including the new `base-b` test, need a maintainer to add the `run-ci` label. Not run: SM100, SM11x and SM121 GPUs, attention DP, speculative decoding, PD. Details: https://gist.github.com/waynehacking8/a858496a37383dd4a6a93258f8a0d5d8
