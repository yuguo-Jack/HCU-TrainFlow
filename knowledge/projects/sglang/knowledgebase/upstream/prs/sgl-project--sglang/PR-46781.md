# [Perf] spec: Avoid blocking H2D for MRoPE delta in spec decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/46781) · state: open · merged: False

## Original PR description


## Motivation
`ForwardBatch.compute_spec_mrope_positions` builds the per-step MRoPE position tensor for multimodal requests by stacking each request's `mrope_position_delta` on host and shipping it to device with `.to(device=device)`. The source (`torch.stack`'s output) is pageable, so PyTorch appends a `cudaStreamSynchronize` to that H2D copy — the driver cannot let the DMA proceed asynchronously because the OS could swap the source page mid-transfer. The host blocks until every kernel already queued on the stream has retired.

This function runs every step of speculative decode (both target verify and draft extend call it), so the queued work behind the sync is the whole in-flight draft/verify window. On an MTP (NEXTN) deployment (TP8), this turned an 8-byte copy into a multi-millisecond stall per call — profiling showed two such stalls per decode step (~1.4ms and ~7.7ms), each draining the stream and then starving the GPU while the host re-issued kernels one at a time instead of running ahead on a primed queue.
<!-- Describe the purpose and goals of this pull request. -->

## Modifications
Stage the stacked delta tensor through pinned host memory before the H2D, so `non_blocking=True` actually applies (it only takes effect when the source is pinned):

```python
stacked = torch.stack(deltas, dim=0)
if stacked.device.type != "cpu" or not is_pin_memory_available(device):
    return stacked.to(device=device)
staging = torch.empty(stacked.shape, dtype=stacked.dtype, pin_memory=True)
staging.copy_(stacked)
return staging.to(device=device, non_blocking=True)
```

CUDA's per-stream ordering still guarantees the copy completes before any kernel that reads `mrope_delta_tensor` executes — only the host-side wait is removed.

- Falls back to the original blocking `.to(device=device)` when `is_pin_memory_available(device)` is `False` (CPU-only / unsupported accelerators), so no behavior change there.
- Value, dtype, device and shape of the result are unchanged.
- Extra host allocation is a `[batch_size, 1]` int64 tensor per step (a few hundred bytes); PyTorch's caching host allocator reuses the pinned block across steps, so there's no unbounded pinned-memory growth.
- Does not touch the text-only fast path (batch has no multimodal requests), which already returns before this tensor is built.
- No new env var / flag — this always applies when pinned memory is available, matching how `non_blocking=True` H2D is already handled elsewhere in this file (e.g. `_compute_mrope_positions_decode`).
<!-- Detail the changes made in this pull request. -->

## Accuracy Tests
This change only replaces how the host→device transfer is performed; the value, dtype, device and shape of `mrope_delta_tensor` are identical to before.

`test_spec_mrope_positions_graph` in `test/registered/kernels/ops/speculative/test_next_verify_prep.py` already calls `compute_spec_mrope_positions` end to end with `mixed=True` (the exact branch this PR touches) and asserts the output against a reference computation, under both eager and CUDA-graph replay. That test passes unmodified against this change, which is expected since the output values are unaffected.

## Speed Tests and Profiling
Measured on an MTP (NEXTN) deployment, TP8, Qwen3.5-VL-class model, `livingroom_planner` multimodal workload, steady-state decode:

| Metric | Before | After | Change |
|---|---:|---:|---:|
| Per-step GPU utilization (busy time summed across all CUDA streams used by draft/verify/draft-extend) | 65.6% | 81.2% | **+15.6 pp** |

| Blocking `cudaStreamSynchronize` time inside one decode step | 9119 us | 5517 us | **-3602 us** |

The two target stalls (`[[1,1],[1,1]]`-shaped pageable H2D copies inside target-verify and draft-extend, ~1.4ms and ~7.7ms respectively) no longer appear in the trace after this change.

|---|---:|
| Original (pageable, blocking) | ~250 ms |
| This PR (pinned, non_blocking) | ~0.2 ms |
