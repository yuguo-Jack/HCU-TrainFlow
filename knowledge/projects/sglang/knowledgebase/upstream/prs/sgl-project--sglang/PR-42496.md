# [Perf] [AMD] deepseek-v4: Fuse the shared expert by default on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/42496) · state: closed · merged: False

## Original PR description

## Motivation

On MI355X, DeepSeek-V4.1 decodes faster when its shared expert runs together with the routed experts (TP4: median time per token 2.0 to 6.6 % lower at 10 of 13 points, slower at none), and every MI355X DeepSeek-V4.1 recipe in the cookbook already turns this on with --enforce-shared-experts-fusion. A server started without that flag still takes the slower path. This PR makes the faster path the default in that case and keeps every existing way to turn it off.

In detail: DeepSeek-V4 runs its shared expert apart from the routed experts in every MoE layer unless the flag is set. On gfx950 with the aiter MoE and MXFP4 routed experts, the fused path has been correct since #42011. This changes model output and speed, so it comes with the accuracy and speed results that the contribution guide and the PR template ask for, and with unit tests for the new rule.

## Modifications

- `python/sglang/srt/models/deepseek_v4.py`, `DeepseekV4ForCausalLM.shared_experts_fusion_disable_reason`: fuse by default when `SGLANG_USE_AITER` is set on gfx950, the routed experts are MXFP4 (not dequantized to FP8), the checkpoint has exactly one shared expert, and no all-to-all MoE backend is set. The FP8 shared expert is then requantized to MXFP4 at load and runs as one more routed expert (DeepSeek-V4.1-Flash: 385 experts, top 7, instead of 384, top 6).
- Unchanged: `--disable-shared-experts-fusion` still wins, because the loader checks it before the model (`resolve_shared_experts_config`). The expert-parallel and precision vetoes still apply. A checkpoint with more than one shared expert stays unfused (with `--enforce-shared-experts-fusion` it still raises).
- DSpark draft models use the same check and fuse by default too (129 experts, top 4); so do MTP (NextN) drafts, which were not run. With an all-to-all MoE backend (MegaMoE, MoRI or another DeepEP-class backend) the default stays off, because none of them was measured; `--enforce-shared-experts-fusion` still turns fusion on there. The check takes the quantization config as an `Fp8Config`, which every DeepSeek-V4 FP4 checkpoint uses.
- `test/registered/unit/models/test_deepseek_v4_shared_expert_fusion.py`: 6 new CPU test methods.

Risk: vllm#61345 (merged 2026-10-19) requires explicit opt-in for this fusion on DeepSeek-V4-Pro with AITER MegaMoE at DEP4 on MI355X; it reports GSM8K 0.9469 ± 0.006 fused versus 0.9545 ± 0.006 unfused. With this PR that setup stays unfused unless the flag is set.

## Accuracy Tests

Setup: DeepSeek-V4.1-Flash (revision `dba1be0a40`), image `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261015` (AITER `2bb549102`), SGLang main `b6d3b7e163` with this PR's rule, `SGLANG_USE_AITER=1`, `AITER_BF16_FP8_MOE_BOUND=0`, no fusion flag in either arm, one run per arm. No all-to-all backend in any run, so the all-to-all and `Fp8Config` checks, added after these runs, do not change a measured path. GSM8K and GPQA Diamond use `python -m sglang.test.run_eval` (GSM8K: 2,048 max tokens; GPQA: thinking on, 32,768 max tokens), NIAH uses lm-eval. The server logs confirm each path: main looks up aiter MoE kernels for 384 experts / top 6, this PR for 385 / top 7.

TP4 on 4 x MI355X (`--mem-fraction-static 0.87 --chunked-prefill-size 16384 --context-length 135168 --enable-decoder-swa-bounded-replay --cuda-graph-max-bs-decode 256 --max-running-requests 256`):

| NIAH single_2, 64k and 128k (500 samples each) | 1.0 | 1.0 |

With `--disable-shared-experts-fusion`, this PR's TP4 server stays unfused (aiter lookups for 384 experts / top 6 only). With the monokernel plugin (`--monokernel-backend amd`, TP2 with DSpark), the fused default starts and runs: GSM8K 1280 / 1314, against 1274 / 1314 for the recipe as published at `b6d3b7e163`, with `--disable-shared-experts-fusion` (main's recipe now sets `--enforce-shared-experts-fusion`).

Unit tests (CPU): 14 of 14 pass. Without this change (at 4b83f215f4), the 3 cases of the new default fail and the other 11 pass. This PR is rebased on 4b83f215f4; the GPU runs used b6d3b7e163.

This PR is faster at 10 of the 13 points (median TPOT 2.0 to 6.6 % lower) and slower at none. 1k / 64 users is left out: a Triton kernel compiled during the measured run of 7 of the 8 sessions. At 1k / 4 users this happened in one session per arm, so that row uses 3 sessions per arm. Median TTFT is within noise at 12 of the 13 points (-3.5 to +2.3 %) and 7.1 % lower at 8k / 2 users. Geometric mean over the 13 points, this PR against main: output throughput +3.8 %, median TPOT -3.7 %, median TTFT -1.4 % (within noise).

TP2 without DSpark (2 sessions per arm, 1k and 8k input, 1 to 16 users): median TPOT is 5.8, 11.9 and 5.9 % lower at 1, 2 and 8 users with 1k input; the other 7 points are the same. With DSpark and with the monokernel plugin (one session per arm, 1k input), median TPOT is 6.5 to 18.5 % and 15.9 to 23.1 % lower; these single runs also differ in accept length by up to 0.35 tokens.
