# [Rust] Serve scheduler metrics on the Rust frontend's /metrics

[Upstream PR](https://github.com/sgl-project/sglang/pull/43942) · state: closed · merged: True

## Original PR description

Stacked on #43924 (`oss-sync-a915eb8795`): the `metrics_listener` argument sits next to the `http_layer` argument that PR adds to `app::serve` and `runtime::start`. Only the last commit is this change.

## Motivation

A Rust-frontend engine started with `--enable-metrics` answers `GET /metrics` with 404: the Rust server has no such route. The schedulers still record everything (they write prometheus_client's multiprocess files under `PROMETHEUS_MULTIPROC_DIR`, exactly as in Python mode), but nothing reaches a scraper, and any test that reads a scheduler histogram from `/metrics` fails in Rust mode.

## Modifications

- The Rust server merges the multiprocess files itself. `utils/prometheus.rs` ports the three prometheus_client pieces the Python `/metrics` relies on: the `MmapedDict` file format, `MultiProcessCollector`'s merge (counters and histograms summed, gauges per `multiprocess_mode`, cumulative buckets, a derived `_count`), and `generate_latest`'s text rendering including `floatToGoString` and label escaping. The merge runs on a blocking thread and never takes the GIL. Collecting under the GIL from the scheduler process would stall the scheduler loop for the whole merge on every scrape, and the cost grows with ranks and series.
- `api_server/http/metrics.rs` mounts `/metrics` (and its subpaths, as Python's mount does) only when metrics are enabled; without `--enable-metrics` there is still no route, as in Python. The route answers Python's `text/plain; version=0.0.4` content type; a missing directory is a 500, as Python's collector raises.
- `ServerArgs` gains `metrics: Option<MetricsConfig>`; `rust_server/config.py` passes the multiprocess directory when metrics are on.
- Only the node's base listener (port offset 0) serves `/metrics`. A DP rank's offset listener answers 404: every listener would render the same node-wide files, so a scraper of each port would count them N times. One port per node matches Python's per-node `/metrics`.
- A fixture written by prometheus_client itself (`rust/sglang-server/testdata/prometheus_multiprocess.json`) pins the format: two processes, every metric type and gauge mode, help and label escapes, unicode, and `le` bounds that need Go-style exponents. The Rust side renders it byte for byte, and a Python test fails if prometheus_client's files or rendering drift from the committed fixture.

Differences from Python's `/metrics`: the text format is always 0.0.4 (no OpenMetrics negotiation, gzip or `name[]` filters), and a file Python's collector cannot parse fails Python's scrape with a 500 where the Rust server skips it with a warning.
