# [Doc] diffusion: validate convrot_int8 on Wan2.2 A14B (T2V & I2V), Wan-Animate-2 (base & distilled)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46048) · state: open · merged: False

## Original PR description


## Motivation

This PR validates ConvRot INT8 (`--quantization convrot_int8`) for:
- Wan2.2 (T2V-A14B and I2V-A14B)
- Wan-Animate-2 14B (base and distilled)

Measured speed, memory and quality on GB200 and H100 for all four, plus two smoke cases for Wan2.2 in the B200 1-GPU suite (no CI case for Wan-Animate-2).

TL;DR (ConvRot INT8 against BF16, same seed and same layout; see below for more details):

- Recipe: `--quantization convrot_int8 --quantization-ignored-layers proj_out` on the stock BF16 checkpoints. No calibration data, no quantized checkpoint, no code change; the quantization page lists no other quantized path for I2V-A14B.
- Wan2.2 T2V and I2V on GB200 (832x480, 81 frames, 30 steps): 1.17x at 1 GPU, 1.17x to 1.19x at 2 and 4 GPUs; 1.23x (T2V) and 1.20x (I2V) on one H100 NVL 94 GB.
- Peak VRAM at 1 GPU reduced from 87.5 to 60.6 GiB (T2V) and from 88.1 to 61.8 GiB (I2V); about 27 GiB less per GPU at every layout.
- Same-seed PSNR to BF16: 21.4 dB (T2V) and 28.1 dB (I2V) at 1 GPU. For scale, BF16 against itself moves by 24.0 to 24.8 dB (T2V) and 28.2 to 29.9 dB (I2V) when only the parallel layout changes, so ConvRot sits below that spread on T2V (by 0.6 to 3.4 dB across the 1-, 2- and 4-GPU layouts) and at its lower edge on I2V, 10 dB or more above the two-seed floor.
- Wan-Animate-2 base: 1.07x and peak VRAM from 86.5 to 71.9 GiB at 1 GPU, 29.4 dB; distilled: 1.07x / 1.06x / 1.04x at 1 / 2 / 4 GPUs, peak VRAM from 65.3 to 50.7 GiB at 1 GPU, 33.9 dB.

Why:

- Wan2.2 I2V-A14B has no published ModelOpt FP8/NVFP4 transformer (the validated ModelOpt transformers on the quantization page cover T2V-A14B only), and producing one needs a calibration set of first-frame/prompt pairs; ConvRot INT8 is data-free and works on the stock checkpoint.
- For T2V-A14B it is an alternative to the ModelOpt FP8 transformer with no conversion step and no extra artifact.
- `convrot_int8` already runs on these models, but the quantization page scopes its quality claims to an explicit list (MiniMax-H3, Qwen-Image, Qwen-Image-Edit); this PR extends that list with the same kind of evidence the existing entries have, smoke-tested in CI and quality-validated offline. Based on main as of 2026-10-22 (`24e45961c6`), which includes #44085, the native support for the distilled Wan-Animate-2 checkpoint.

### Supported features
- The recipe `--quantization convrot_int8 --quantization-ignored-layers proj_out` on the stock checkpoints `Wan-AI/Wan2.2-T2V-A14B-Diffusers`, `Wan-AI/Wan2.2-I2V-A14B-Diffusers`, `Wan-AI/Wan2.2-Animate-2-14B-Diffusers` and `Wan-AI/Wan2.2-Animate-2-14B-Distilled-Diffusers`; no behaviour change.
- Layouts measured: 1 GPU; 2 GPUs `--enable-cfg-parallel`; 4 GPUs `--enable-cfg-parallel --ulysses-degree 2` (Wan2.2 and Animate-2 base); `--ulysses-degree 2` / `4` (Animate-2 distilled, which rejects CFG parallelism). CFG-parallel and Ulysses replicate the DiT on every rank, so the per-GPU memory saving carries over.
- Both backends stay selectable (`SGLANG_DIFFUSION_CONVROT_INT8_BACKEND`); every number here is the `jit` backend (number of quantized layers: `jit 400, comfy_kitchen 0` per expert in every Wan2.2 load log, `jit 480, comfy_kitchen 0` on Animate-2).

### Notes on model-specific parameters
- Both A14B experts (`transformer`, `transformer_2`) are quantized at load, 400 of the 401 eligible linears each (26.17 -> 13.09 GiB per expert). Wan-Animate-2 has one expert, 480 of 481 linears (30.08 -> 15.04 GiB), so its per-GPU saving is about 15 GiB instead of the A14B's 27 GiB.
- `--quantization-ignored-layers proj_out` keeps the output head in BF16 (it matches module paths in both experts); on the hardest T2V prompts this adds 2 to 4 dB (dancer 21.0 -> 24.6 dB, night street 17.0 -> 18.9 dB) at no measurable cost in speed or memory, so the docs recommend it on every layout.
- The fused INT8 kernels JIT-compile once per machine (about 50 s on CC 10.0, 96 s on CC 9.0; needs nvcc) and run on CC 9.0 (H100/H200), 10.0 (B200/GB200) and 12.0 / 12.1 (RTX PRO 6000 Blackwell, RTX 50 series, DGX Spark); with a warm cache ConvRot loads in BF16's time, and the load peak (BF16 weights staged on the GPU before quantization) stays below the runtime peak.

### Rejected at startup
- CC 10.3 (B300 / GB300) is refused by the JIT backend by design (`REFUSED_CAPABILITY_REASONS` in `convrot_int8_jit.py`: Blackwell Ultra's INT8 tensor-core rate makes W8A8 a slowdown); with `auto` the config then resolves to the `comfy-kitchen` INT8 kernels when installed (0.86x on MiniMax-H3) and otherwise fails with the install hint. The cookbooks say so; there T2V-A14B has the ModelOpt FP8/NVFP4 transformers and I2V-A14B no validated quantized path.
- If the JIT probe sees no CUDA device at load (observed once as a host transient), `auto` falls back to `comfy_kitchen` the same way; `SGLANG_DIFFUSION_CONVROT_INT8_BACKEND=jit` turns that into an explicit error.


## Accuracy Tests

Protocol: same seed, same prompt, ConvRot INT8 against the BF16 video of the same GPU layout; PSNR and SSIM over all
frames, LPIPS (AlexNet) on every fourth frame; sharpness is the Laplacian variance and flicker the mean frame-to-frame
pixel difference, both quoted as the ConvRot / BF16 ratio.

Wan2.2: 832x480, 81 frames, 30 steps, CFG 5, seed 42, default negative prompt, one warmup plus six measured requests (one per prompt) per cell.

Wan-Animate-2: `size` 640x800, `clip_len` 37, audio off; base checkpoint 40 steps, CFG 3; distilled checkpoint 10 steps, guidance 1.0 (DPM-Solver++ 2M, `log_scale` -1.3) on the native support merged in #44085.

On every build used here the pipeline is bit-exact across reruns, GPU slots and nodes (BF16 vs BF16 and ConvRot vs ConvRot: PSNR inf, SSIM 1.000), so each row is a single number with no run-to-run band.

## Speed Tests and Profiling

Protocol: 1, 2 and 4 GPUs of 4x GB200 nodes (189 GB per GPU) and one H100 NVL 94 GB (PCIe, 310 W power cap, aarch64
host); sglang main `c5bf3aaf` (the distilled Animate-2 rows on the #44085 head) with torch 2.15.0a0 (pre-release
build), CUDA 13.5, cuDNN 9.27 and the default `dynamic_cudnn_sdpa` attention backend (CUDA 13.0 driver on the H100
node); the accuracy rows above come from the same stack. E2E is the mean of the measured requests after one warmup,
loading excluded; peak is the sglang runtime peak per GPU. The 1- and 2-GPU rows are same-time BF16/ConvRot pairs
averaged over two rounds with the GPU slots swapped (slots on one tray differ by about 10 percent for the same cell, so
a single un-swapped pair can read anywhere from 1.07x to 1.29x at 1 GPU); the 4-GPU rows are BF16 then ConvRot, two
rounds. Outputs were bit-identical across rounds, GPU slots and nodes. The H100 NVL node caps the board at 310 W
(sustained SM clock 700 to 820 MHz of 1785), so its absolute times are higher than what an uncapped part would give;
BF16 fits resident on the 94 GB part.

- 1.17x at 1 GPU for T2V and I2V on GB200, 1.17x to 1.19x on the 2- and 4-GPU layouts; 1.23x (T2V) and 1.20x (I2V) on the H100 NVL. The denoising step moves the same way, 3741 -> 3180 ms (T2V) and 3564 -> 3020 ms (I2V) at 1 GPU on GB200.

### Wan-Animate-2 (base and distilled)

Workload: cookbook defaults (640x800 budget, `clip_len` 37, audio off), the 3-clip input, seed 42; base checkpoint 40 steps, CFG 3; distilled checkpoint 10 steps, guidance 1.0. The base 1-GPU row is the mean of two GPU-swapped rounds of three requests with everything resident; the distilled 1-GPU row uses the same protocol with the text encoder CPU-offloaded (the cookbook's distilled recipe). The 2- and 4-GPU rows use the cookbook's parallel presets
with the text encoder CPU-offloaded, one warmup plus two requests per cell, two rounds each.

Speedups:
- 1.07x on the base checkpoint at 1 and 2 GPUs and 1.08x at 4; 1.07x, 1.06x and 1.04x on the distilled checkpoint. The steady-state denoising step moves 3171 -> 2963 ms (base) and 1776 -> 1679 ms (distilled) at 1 GPU; on the 7-clip input (one request each, text encoder offloaded) the step-time ratio is the same 1.07x / 1.06x.
- ConvRot INT8 reduces peak VRAM on the 3-clip input from 86.5 to 71.9 GiB with the text encoder resident and from 65.3 to 50.7 GiB with it offloaded; the drop is the single expert's weights (about 15 GiB), so it is smaller than the A14B's 27 GiB. At 2 and 4 GPUs it reduces peak VRAM per GPU from 58.6 to 44.5 GiB and from 48.2 to 32.8 GiB (base), from 48.3 to 33.6 GiB and from 41.3 to 26.3 GiB (distilled): CFG-parallel and Ulysses replicate the DiT on every rank, so the per-GPU saving stays at the expert's 14 to 15 GiB (runtime peaks; `nvidia-smi` reports 6 to 10 GiB more per GPU). With the text encoder resident as well, the distilled 1-GPU peak goes from 86.4 to 71.9 GiB, matching the base checkpoint's 86.5 to 71.9.
- The distilled checkpoint on Ulysses drops to 1.06x / 1.04x, consistent with sequence parallelism cutting the per-rank token count of every linear (21,504 -> 5,376 queries per rank at degree 4) while the all-to-all and flex-attention time is unchanged by quantization; CFG-parallel keeps the full sequence per rank and does not show it. Parallel efficiency is the same for both precisions (base: 1.91x at 2 GPUs, 3.38x / 3.39x at 4 GPUs over the respective 1-GPU time).
- The gain is 1.07x rather than 1.17x-1.23x (as seen on Wan2.2) with the same recipe: Animate-2's in-context self-attention (21,504 queries against 41,088 keys per call, Triton flex attention at about 117 ms per call in the autotune log) takes a larger share of the step than the dense A14B attention, and ConvRot only accelerates the linears.

### Recommended parallelism config

- `--quantization convrot_int8 --quantization-ignored-layers proj_out` on every layout (the `proj_out` note above).
- 1 GPU: BF16 needs about 88 GiB resident, ConvRot about 62 GiB, so ConvRot should be the resident path on 80 GB parts (inferred from the 94 GB H100 NVL measurement, not measured on an 80 GB part).
- 2 and 4 GPUs: the same flags on top of `--enable-cfg-parallel` and `--enable-cfg-parallel --ulysses-degree 2`; 1.17x to 1.19x and the same 26 to 27 GiB per-GPU reduction.
- Wan-Animate-2: the same flags on top of the cookbook's 2-GPU CFG-parallel and 4-GPU CFG-parallel x Ulysses 2 presets (1.07x / 1.08x, 14 to 15 GiB less per GPU); on the distilled checkpoint, which runs Ulysses instead of CFG parallel, expect 1.06x at degree 2 and 1.04x at degree 4 with the same per-GPU saving, so there it is a memory recipe.
- Hardware: CC 9.0, 10.0 and 12.0 / 12.1 with nvcc for the one-time compile (the GPU note above); CC 10.3 is refused by design (see "Rejected at startup").



## Known limitations and follow-ups

- Approximate: same-seed outputs are not bit-exact with BF16, so the cases run with consistency and component-accuracy checks off, like the ModelOpt smoke cases.
- The `b200.json` entries are GB200-generated placeholders with a `timing_tolerance` of 1.5 (the E2E and load guards run regardless of `run_perf_check`); regenerate them on the first B200 CI run and drop the tolerance then. The tolerance also covers a cold runner, which pays the one-time JIT compile (about 50 s) inside the load window.
- The cases live in the B200 suite next to the other Wan2.2 quantization cases; the H100 shard is not extended (the kernels run there, so the cases can move if maintainers prefer). The recipe itself is measured on H100 NVL above.
- CC 10.3 (B300 / GB300): refused by design, see "Rejected at startup".
- Speedups on the test node depend on which GPU slot a cell lands on (about 10 percent between slots); every 1- and
2-GPU row is averaged over GPU-swapped same-time pairs, so quote the table values rather than any single pair.
- On the base Animate-2 checkpoint, long chained-clip requests diverge after about four clips under any numerical perturbation (INT8, or a different PyTorch build in BF16): per-clip PSNR drops from 31 to 36 dB on clips 1 to 4 to 19 to 26 dB on clips 5 to 7, so the quality rows for that input are comparable on clips 1 to 4 only. The 3-clip input and the distilled checkpoint do not show this.
- No Animate-2 ConvRot CI case. The existing `wan2_2_animate_2_14b_ref2v` cases cover BF16 with the CI reference video on the H100 lanes; a Wan-Animate-2 quantized variant is left to a follow-up if maintainers would like it.
- Quality under tensor parallelism and the `comfy_kitchen` backend on these models were not measured.
