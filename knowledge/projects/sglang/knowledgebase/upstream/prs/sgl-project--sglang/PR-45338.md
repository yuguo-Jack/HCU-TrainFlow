# [Feat] mooncake: Enable the failed-session probe by default with backoff and idle pruning

[Upstream PR](https://github.com/sgl-project/sglang/pull/45338) · state: closed · merged: True

## Original PR description

## Motivation

When a Mooncake KV send fails, prefill blacklists that decode session (`failed_sessions`). Later requests to it fail fast instead of each one waiting out the transfer timeout. The blacklist is cleared only when the decode re-registers (on restart) or when `SGLANG_ENABLE_FAILED_SESSION_PROBE` sees the session answer again.

The probe has been off by default. So a decode that stays up after a transient network failure is never un-blacklisted: every request routed to it fails until someone restarts it, and `/health` stays green the whole time. #35823 reports a ~4h outage of this kind.

#35823 proposed a TTL that sends real traffic to the session again after 120s. A retry to a dead peer blocks its transfer queue until the transfer timeout, and every queue is shared by several decodes. The probe handles this case off the transfer path, on its own thread.

Turning the probe on as it was would cause a different problem under rolling updates. A restarted decode comes back under a new session ID: Mooncake's P2P handshake picks a fresh RPC port on every start. So the old ID never re-registers and stays blacklisted, and every rollout would add dead IDs that are probed every 30s forever, each failed connect logging a Mooncake error.

## Modifications

- `SGLANG_ENABLE_FAILED_SESSION_PROBE` now defaults to `true`. Set it to `false` to restore the old behavior.
- **Backoff:** after each failed probe, a session's probe interval doubles, starting from `SGLANG_FAILED_SESSION_PROBE_INTERVAL_S` (30s) and capped by the new `SGLANG_FAILED_SESSION_PROBE_MAX_INTERVAL_S` (300s). A successful probe un-blacklists the session as before.
- **Idle pruning:** a blacklisted session that no request has targeted for the new `SGLANG_FAILED_SESSION_IDLE_TIMEOUT_S` (600s) is dropped. Each request that hits a blacklisted session (on the existing early-exit path) refreshes this timer, so a live decode that is partitioned but still being routed to stays blacklisted and keeps being probed.
  - If a request later arrives for a dropped session, it is treated as a fresh session: a real send, re-blacklisted if it fails.
- Re-registration, probe success, and pruning all clear a session's state through one helper.
- A probe that raises now counts as a failure and backs off, instead of being retried on the next pass.
- Startup validates `0 < interval <= max interval` and `idle timeout > 0`.
- Documented the new env vars and updated the existing ones.

## Cost

- **No blacklisted sessions (the normal case):** the probe thread wakes every 30s and finds nothing to do. No Mooncake call, no network traffic.
- **Per probe:** one TCP connection to the decode's handshake port and a few hundred bytes of JSON. The binding releases the GIL (`gil_scoped_release`, Mooncake 0.3.13.post1). Connect is bounded by `MC_HANDSHAKE_CONNECT_TIMEOUT` (5s).
- **Rollout simulation:** 100 dead session IDs, the real `_run_one_probe_pass` on a 30s loop, over one hour:

| | Probes in 1h | Probes in last 10 min | Still blacklisted after 1h |
|---|---|---|---|
| Probe on, without this PR | 12000 | 2000 | 100 |
| This PR | 400 | 0 | 0 |
