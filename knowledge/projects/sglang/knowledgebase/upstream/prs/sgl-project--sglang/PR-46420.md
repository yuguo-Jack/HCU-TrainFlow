# [Fix] jit: Link libcudart from the pip CUDA toolkit layout

[Upstream PR](https://github.com/sgl-project/sglang/pull/46420) · state: open · merged: False

## Original PR description

base_link_flags() always linked `-L$CUDA_HOME/lib64 -lcudart`. The pip CUDA wheels (site-packages/nvidia/cu13) ship lib/libcudart.so.13 with no lib64/ and no unversioned libcudart.so, so every JIT module with device code failed to link there with `cannot find -lcudart`.

Look in lib64/ then lib/, and link the versioned soname by name when the unversioned link is missing. Toolkit installs keep exactly the old flags, so existing build keys are unchanged.

## Motivation

Fixes #46418.

When `CUDA_HOME` points at the pip CUDA toolkit (`site-packages/nvidia/cu13`), every JIT module with device code fails to link with `cannot find -lcudart`. `base_link_flags()` always emits `-L$CUDA_HOME/lib64 -lcudart`, but the pip wheels ship only `lib/libcudart.so.13`: no `lib64/` and no unversioned `libcudart.so`. With an FP8 model the server exits at startup, during prefill CUDA-graph capture. #43591 pins this toolkit for JIT use and lists the link layout as out of scope.

## Modifications

- `python/sglang/kernels/jit/utils/compile/toolchain.py`: `base_link_flags()` gets its libcudart flags from a new `_cudart_link_flags(cuda_root)`. It looks in `lib64/` and then `lib/`. If `libcudart.so` exists it links `-lcudart` as before; otherwise it links the versioned soname by name (`-l:libcudart.so.13`, the shortest match, not `libcudart.so.13.0.96`). With neither present, it falls back to the old flags, so the linker error is unchanged.
- **Toolkit installs keep byte-identical flags**, so existing JIT build keys and caches are unaffected.
- `test/registered/unit/kernels/test_jit_cache.py` gets two cases next to the existing link-flag test, both going through `ninja.generate()` with only `cuda_home` patched:
  - `test_pip_cuda_toolkit_links_the_versioned_cudart`: the regression case. **It fails on current `main`** (`-L…/lib64 -lcudart`) **and passes with the fix.**
  - `test_cuda_toolkit_link_flags_are_unchanged`: guards the toolkit flags. A toolkit's `lib/` must not win over `lib64/`, because the flags are part of the build key.

Not changed: `cuda_stubs_dir()` (`lib64/stubs`, used by a few driver-API modules). The pip wheels ship no `libcuda.so` stub, so that path needs a separate decision. FlashInfer's JIT makes the same `lib64` assumption; that's for its own repo.

## Testing

On an RTX 4070 Ti SUPER (SM89), WSL2 Ubuntu 26.04, with this branch's code and the pip CUDA 13.0 toolchain (no system toolkit), `CUDA_HOME=<venv>/nvidia/cu13`:

- `test/registered/unit/kernels/test_jit_cache.py`: 44 passed, via `pytest` and via direct execution as CI runs it. The new regression case fails against the unmodified `toolchain.py` from `main`.
- **End to end**, plain pip layout (no symlinks), `--attention-backend triton --sampling-backend pytorch`, `Qwen/Qwen3-8B-FP8`:
  - the server starts;
  - greedy, top-k/top-p and 8 concurrent sampled requests all return 200, and so does `/health_generate`;
  - the freshly built `per_token_group_quant` module's `build.ninja` has `-L<venv>/nvidia/cu13/lib -l:libcudart.so.13`, and its `NEEDED` entry is `libcudart.so.13`, the same soname a toolkit build records.
- Caveat: this machine has glibc 2.43, where CUDA 13.0's `crt/math_functions.h` clashes on `rsqrt` (#45066). For the end-to-end run only, I backported CUDA 13.4's `noexcept(true)` declarations into the venv's header. That's unrelated to this change, and the unit tests don't need it.
- `pre-commit run` on the changed files passes.
