# Rainj me/rust bench

[Upstream PR](https://github.com/sgl-project/sglang/pull/43950) · state: closed · merged: True

## Original PR description

## Motivation

The Python benchmark client (`sglang.benchmark.serving`) drives every request and parses every response stream on one asyncio thread, and opens a fresh aiohttp session, and so a fresh connection, per request. On wide-EP deployments the client becomes the bottleneck before the server does, and the benchmark reports the client's limit. It also cannot benchmark a server launched with `--skip-tokenizer-init` at all: it counts a token only where it sees text, so a token-id-only response scores as a failure, and it has no way to reach the Rust server's gRPC service.

This PR adds `rust/sglang-bench`, a Rust port of the client that parses each stream on its own Tokio worker, shares a pooled HTTP client, counts tokens from ids when there is no text, and speaks the Rust server's `sglang.api.v1` gRPC service as a transport option. It keeps the Python client's flags, report, and result keys, so existing command lines and `.jsonl` readers keep working.

## Modifications

**New crate `rust/sglang-bench`** (PyO3 extension, loaded as `sglang.srt.rust_extensions._bench`, discovered by `setup.py` through `[package.metadata.sglang]` like the other extensions; `pyo3` is a plain dependency as in `sglang-server`).

- Backends: `sglang` / `sglang-native` (`/generate`), `sglang-oai`, `vllm`, `lmdeploy` (`/v1/completions`), `sglang-oai-chat`, `vllm-chat`, `lmdeploy-chat` (`/v1/chat/completions`), streaming and not. Datasets: `random`, `random-ids`, `sharegpt`. Poisson pacing, concurrency cap, warmup, cache flush, profiler toggling, readiness probe, `--extra-request-body`, custom headers, API-key auth.
- Metrics follow NumPy (linear-interpolated percentiles, population std) so the numbers line up with the Python client's; the per-second peak-throughput and peak-concurrency windows are reproduced.
- **Token ids on both ends.** `--tokenize-prompt` sends `input_ids`; the response side reads progress from `meta_info.completion_tokens`, falling back to the `output_ids` a frame carries, so a `--skip-tokenizer-init` server measures the same as a decoding one. `--vocab-size N` with `random-ids` loads no tokenizer at all, so the client needs no model files; retokenized totals then report 0.
- **`--protocol {http,grpc}`**, orthogonal to `--backend`. `grpc` sends the native-API request over `sglang.api.v1` (`Generate`, `GetModelInfo`, `GetServerInfo`); default port is `--port + 10000`, matching the server's `--grpc-port`. The request is the same schema the `/generate` route decodes, built once and deserialized into the generated type, and each streamed frame is fed to the same accounting as an SSE frame through its JSON form, so the two transports differ only in wire and are directly comparable. The result line gains a `protocol` key, the one key the Python client does not write, so both kinds of run stay apart in a shared file. gRPC is rejected for the OpenAI-shaped backends, which have no gRPC service; cache flush and the profiler are HTTP-only controls and a gRPC run says so and skips them.
- Additions over the Python flags: `--protocol`, `--worker-threads`, `--disable-retokenize`, `--vocab-size`.

**Python**

- `python/sglang/benchmark/rust_client.py`: `python -m sglang.benchmark.rust_client` forwards argv to the Rust client (clap owns the flags, `--help` works, no model-tooling imports), and `run_rust_benchmark(args)` runs an already-parsed namespace in process.
- `serving.py`: `--rust-client` routes the run to the Rust client, with `--rust-worker-threads`; an unsupported backend/dataset/option is a usage error rather than a silent drop.

**Not covered** (flags absent rather than ignored): `trt`, `gserver`, `truss`, embedding backends; `image`, `mmmu`, `mooncake`, `agentic-trace`, `generated-shared-prefix`, `custom`, `openai`, `longbench-v2`, `speed-bench` datasets; trace replay, multi-turn, LoRA distributions, `--cache-report`, `--plot-throughput`, PD-separated profiling.

## Benchmark Scripts

```bash
SGLANG_RUST_SERVER=1 \
SGLANG_DEEPEP_V2_NUM_MAX_DISPATCH_TOKENS_PER_RANK=4096 \
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
sglang serve /mnt/shared/weights/GLM-5.3 \
  --tp 4 --moe-a2a-backend deepep_v2 --deepep-v2-mode direct \
  --skip-tokenizer-init --grpc-port 20000 --port 30000 \
  --mem-fraction-static 0.75 --cuda-graph-max-bs-decode 256

python -m sglang.benchmark.rust_client \
  --host 127.0.0.1 --backend sglang \
  --dataset-name random-ids --tokenize-prompt --vocab-size 154880 \
  --num-prompts 256 --random-input-len 1024 --random-output-len 256 \
  --random-range-ratio 1.0 --max-concurrency 128 --warmup-requests 2 \
  --protocol grpc --port 20000 \
  --output-file glm53-grpc.jsonl --disable-tqdm

python -m sglang.benchmark.rust_client \
  --host 127.0.0.1 --backend sglang \
  --dataset-name random-ids --tokenize-prompt --vocab-size 154880 \
  --num-prompts 256 --random-input-len 1024 --random-output-len 256 \
  --random-range-ratio 1.0 --max-concurrency 128 --warmup-requests 2 \
  --protocol http --port 30000 \
  --output-file glm53-json.jsonl --disable-tqdm
```

## Accuracy Tests

Not applicable; no model or kernel code changes. Counted quantities match the Python client exactly: against one mock server with `--random-range-ratio 1.0` (fixed lengths, so the two clients' different RNG draws do not matter), both report identical `completed`, input/output token totals, retokenized totals and `accept_length`, with identical result-key sets (plus `protocol`).

Tests: 41 unit tests (wire parsers against recorded frame sequences incl. ids-only frames, NumPy-definition statistics, dataset sampling, argument and config validation) and one end-to-end test that hosts a tonic mock of the api.v1 service and runs the client through its public entry point with ids on both ends and no tokenizer. CI runs them through the workspace `cargo test`.

## Speed Tests and Profiling

**Against a real server**: GLM-5.3 fp8, TP4, DeepEP v2, `--skip-tokenizer-init`, Rust frontend, GB300. 256 prompts × (1024 in, 256 out), concurrency 128, token ids in and out, no client tokenizer. Two samples per cell; a distinct seed per run keeps the prefix cache cold (the Rust frontend has no `/flush_cache`).

| | gRPC | HTTP |
|---|---|---|
| Output throughput | 2377, 2386 tok/s | 2399, 2391 tok/s |
| Median TTFT | 2059, 2055 ms | 2059, 2020 ms |
| P99 TTFT | 3095, 3083 ms | 3067, 3028 ms |
| Mean ITL | 45.7, 45.7 ms | 45.1, 45.5 ms |

Transport makes no measurable difference at this scale (every pair within ~1%); decode sets the pace. The Python client cannot run this workload at all (token-id-only responses).

**Client scaling, mock server** (Python `ThreadingHTTPServer` on the same host, so a direction rather than a specification): 96 output tokens/request at concurrency 256. At 500 requests the two clients are even (1.8 s vs 1.7 s); at 2500, Python takes 106.8 s (2.2k tok/s) against Rust's 13.2 s (18.2k tok/s), with Python's per-request CPU comparable, i.e. blocked rather than compute-bound, consistent with its session-per-request connection churn. Measure on your own server before quoting.
