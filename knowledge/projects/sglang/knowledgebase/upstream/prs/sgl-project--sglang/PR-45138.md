# [Feat] sglang-processor: render Inkling as TMLv0

[Upstream PR](https://github.com/sgl-project/sglang/pull/45138) · state: open · merged: False

## Original PR description

## Motivation

`rust/sglang-processor` rendered Inkling with Dynamo's native formatter (`dynamo-renderer` 7.1.1 `InklingFormatter`). Its output differs from the TMLv0 format that tml-renderers defines and that SGLang's Python path renders through (#42844):

- the tool declaration comes before the system prompt instead of after it;
- a `<|message_model|>` generation header is appended, while Inkling samples its own header;
- `{"type": "thinking"}` content parts are rejected;
- message text has no special-token boundary, so text such as `<|end_message|>` in a user message tokenizes as a control token instead of ordinary text.

## Modifications

- `src/render/models/inkling.rs`: renders an SGLang request body the way `serving_inkling.py` renders it through tml-renderers:
  - system messages first, then `tool_declare`, then the effort message before the first non-system message;
  - no generation header;
  - tool declarations flattened to `description`/`name`/`parameters`/`type`, keys sorted, schema types normalized;
  - call arguments and declarations re-serialized as TMLv0 does, including its float printing: ryu digits; serde_json's default (inexact) float parser applied once to arguments and twice to declarations; declarations write `e+NN`;
  - `reasoning_content` and thinking parts render as thinking messages; tool results take their name from `name` or the matching call id;
  - effort from `reasoning_effort`, `reasoning`, `chat_template_kwargs`, the server's default kwargs, or `SGLANG_INKLING_DEFAULT_REASONING_EFFORT`, quantized as TMLv0 does (both roundings half-to-even in `f64`);
  - `continue_final_message` leaves an open model text block.

  The prompt is segmented: control tokens may tokenize as specials, message text may not.
- `render/mod.rs`, `selection.rs`: `inkling_mm_model` selects a new `ChatFormatter::Inkling` (`render_request` and `render_prompt`).
- Values the processor cannot tell apart once parsed render on the engine:
  - `-0` (Python prints `0`) versus `-0.0`;
  - integer literals beyond 64 bits versus integral floats at or above 2^63.
- `tests/fixtures/parity/inkling-nvfp4.json`: 192 cases, including the 14 tml-renderers golden prompts.
- `tests/parity.rs`: segmented prompts encode with fastokens on `tokenizer.json`, because Dynamo's Hugging Face backend has no segmented encoding.
- `generate_parity.py`: builds the serving spec adapter and records Inkling prompts by decoding their ids.

The fixture is generated from the Python path in #42844, so this PR should merge after it. Hosts that tokenize with Dynamo's Hugging Face backend cannot encode the segmented prompt. They still send Inkling chats to the engine, as sgl-router already does.

## Accuracy Tests

Rendering only; no model forward change.

- `cargo test -p sglang-processor --locked` with the checkpoint's tokenizer cached passes:
  - Inkling, 159 rendered cases: prompt text and token ids match the Python path. Token ids are checked with fastokens.
  - 25 cases are rejected by both.
  - 8 are marked `known_gap` for the ambiguous numbers above.
- The Python fixture matches tml-renderers' golden input ids for all 13 text-only golden prompts.
- Against the Python path, outside the fixture, through `render_request`:
  - 3,253 floats (random bit patterns, magnitudes 1e-8 to 1e17, short decimals), each in call arguments and in a tool declaration: all match.
  - 12,901 effort values in [0, 0.99]: all match.
- `cargo clippy -p sglang-processor --all-targets --locked -- -D warnings` and `cargo check -p sglang-processor --no-default-features --features render,tokenizer --locked` pass.
