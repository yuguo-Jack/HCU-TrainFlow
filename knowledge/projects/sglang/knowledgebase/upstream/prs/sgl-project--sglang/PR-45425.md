# [CI] [AMD] pr-test-amd: Cut redundant shards, tag fetches and non-AMD test runs

[Upstream PR](https://github.com/sgl-project/sglang/pull/45425) · state: closed · merged: False

## Original PR description

## Motivation

Follow-up to #42148. After that change, the remaining low-hanging GPU-time waste in AMD PR CI comes from four places: shards that pay a full ~3-4.5 min setup to run only a few files, a `git fetch --tags` that pulls every branch head (~30 s per job) just to read one tag name, and PRs whose only changes are tests no AMD suite runs, which still trigger every AMD GPU stage. No test is dropped from PR coverage.

### Expected savings

Measured against AMD CI for the week after #42148 merged (Oct 15-22: all four AMD workflows, all retry attempts, a random sample of ~4,000 of 16,729 runs scaled up per workflow). AMD CI currently uses about **19,700 runner-hours / 45,700 GPU-hours per week**. GPU-hours weight each job by its runner's GPU count, so the 8-GPU changes count for more there.

Updated after merging `main`: #46084 moved the tests in CUDA's extra tier to the AMD extra workflow and already reduced the stage-b shards (1-GPU small / 1-GPU large / 2-GPU large) from 14 / 3 / 2 to 12 / 2 / 1. The stage-b rows above count only the jobs this PR removes on top of that (per-job savings unchanged from the original measurement).

| Change | Runner-h/week | GPU-h/week | Basis |
| --- | ---: | ---: | --- |
| stage-b 1-GPU small: 12 → 8 shards | 292 | 292 | measured setup per job (~3.2 min) × removed jobs |
| stage-b 1-GPU large: 2 → 1 job | 76 | 76 | same |
| stage-b 2-GPU large: already one job on `main` | 0 | 0 | timeout and `--continue-on-error` only |
| stage-c 8-GPU: MI300 4 → 2, MI35x 3 → 1 | 154 | 1,232 | same (~3.4 min MI300, ~4.3 min MI35x) |
| `git ls-remote` instead of `git fetch --tags` | 285 | 484 | ~29 s (local test) × ~35,000 GPU jobs/week |
| Skip AMD stages for non-AMD test-only PRs | ~100-300 | ~170-700 | earlier estimate, not re-measured |
| **Total** | **~910-1,110** (5-6%) | **~2,250-2,780** (5-6%) | |

## Modifications

- **Change detection:** skip the AMD GPU stages when every changed `main_package` file is a test no AMD suite runs: a `test_*.py` without `register_amd_ci`, a test under another hardware's directory (`npu`, `xpu`, `musa`, `mps`, `mlx`, `cpu`, `gb300`), or `test/manual/`. Suites are collected only from files that call `register_amd_ci`, and no AMD test imports another `test_*.py`. Deleted files and non-test helpers still count as relevant. Source changes are unaffected. (~100-300 runner-h, ~170-700 GPU-h/wk)
- **stage-c 8-GPU shards:** MI300 4 → 2, MI35x 3 → 1. The MI35x third shard only existed because one file's `est_time` (4800 s) is far above its ~250 s runtime. Timeouts 120 → 150 and 60 → 90. (~154 runner-h, ~1,230 GPU-h/wk; stage-c only runs when stage-b passes)
- **stage-b-test-1-gpu-small-amd:** 12 → 8 shards (14 before #46084). The partitions were very uneven (7-42 min of test); stage-b wall time doesn't grow, since 1-gpu-large stays the critical path. Step timeout 75 → 120. (~290 runner-h = GPU-h/wk, scaling with PR volume)
- **stage-b 1-gpu-large and 2-gpu-large:** one job each. 1-gpu-large goes from 2 shards to one job; 2-gpu-large is already one job on `main` since #46084. They were already serialized by `max-parallel: 1`, so this only removes setups. Timeouts raised (1-gpu-large 60 → 200, 2-gpu-large 120 → 170). (~76 runner-h = GPU-h/wk)
- **Container start:** resolve the image tag with `git ls-remote --tags` instead of `git fetch --tags`, using the same PEP 440 ordering as `get_version_tag.py`. The installed sglang version string is unchanged (the shallow checkout already falls back), and a failed lookup falls back to the default tag as before. (~285 runner-h, ~485 GPU-h/wk)

The merged single-job suites (stage-c and stage-b large) run with `--continue-on-error`, so one failing file no longer hides the rest; the job still fails. `wait-for-stage-b-amd`'s expected counts are updated to 8 / 1 / 1.

## Speed Tests and Profiling

Validated locally:
- In a simulated CI depth-1 checkout, the `ls-remote` lookup resolves the same tag (`v0.5.22`) as the current fetch in ~1 s instead of ~30 s.
- The relevance step gives the expected result for non-AMD-only, AMD-registered, deleted, source, mixed and helper-file changes.

The new timeouts cover the slowest projected merged job in each of the past five weeks (summed shard times per clean run, minus the removed setups), with some headroom; late September ran 30-60% longer than recent weeks.

`pr-test-amd` on this PR ([run 39586039975](https://github.com/sgl-project/sglang/actions/runs/39586039975)): every MI300 job passed within its new timeout (1-gpu-large 86 / 200 min, 2-gpu-large 68 / 170, stage-c 8-GPU 62 and 83 / 150, 1-gpu-small shards 21-51 / 120). The MI35x failures are unrelated to this PR, which only changes CI files:
- **ImportError `_check` from `smallm_moe_gfx950`** (1-gpu-small-mi35x shard 0, stage-c 8-GPU MI35x, both DSv4 jobs): a gfx950-only import breakage on `main` (Oct 21), fixed by #45676 on Oct 22.
- **`test_dsv4_hip_bcg_metadata`: no attribute `swa_req_ring_size`** (1-gpu-small-mi35x shard 1): the test lagged a `main` change; fixed by #45507 on Oct 22.
- **disaggregation (8-GPU fabric) out of memory:** this job failed in ~80% of PR runs Oct 15-22.

The merged MI35x stage-c job (90 min timeout) still needs a clean run after the fix.

- michaelzhang-ai · comment · 2026-10-25T17:23:17Z · [source](https://github.com/sgl-project/sglang/pull/45425#issuecomment-6400763417)

Thanks for this, the measurements were useful. #46084 and #46085 have since landed, so I compared this PR against the current main and against AMD PR runs from the last few days:

- **Stage-c shard counts** (MI300 4 → 2, MI35x 3 → 1) are already on main through #46085, and the 4800 s file moved to nightly. So the 154 runner-h/week row and the MI35x third-shard explanation no longer apply here.
- **Always-on `--continue-on-error`** for 1-gpu-large, 2-gpu-large and both stage-c jobs drops fail-fast on PRs. A run with an early failure keeps its runner until the timeout, which works against the GPU savings. Could these keep the `continue_on_error` output?
- **Timeouts** were sized before #46084/#46085 moved about half of these suites out. Measured medians on main are about 57 min for 1-gpu-large in total, 38 min for 2-gpu-large and 23 min for stage-c MI35x. A hang under the new 200 / 170 / 90 min limits would hold the runner 3–4× longer than the job needs.
- **Merging 1-gpu-large into one job** saves one setup, about 4 min. But it puts about 58 min on stage-b's longest path, where #46086 instead runs the two shards in parallel at about 30 min each.

The ls-remote tag lookup, the non-AMD test skip and 12 → 8 small shards all look right to me. I checked that `--tag-only` already picks the global max, so ls-remote returns the same tag. I also checked that no AMD-registered test on main imports a non-AMD `test_*.py`.

To keep things moving, I put those three pieces in #46453 with a few changes:
- The tag listing lives in `get_version_tag.py --remote` instead of an inline one-liner in both container scripts.
- The relevance check is a script that also counts non-AMD tests imported by AMD tests, so a future sibling import can't silently skip AMD CI.
- The 1-gpu-small timeout is 90 min on MI300.

The two PRs overlap and will conflict. Would you be OK closing this in favor of #46453? cc: @bingxche
