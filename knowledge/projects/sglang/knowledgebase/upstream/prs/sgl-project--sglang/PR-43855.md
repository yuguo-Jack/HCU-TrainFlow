# [AMD][V4.1] Cheaper mHC reduce + sinkhorn row, bitwise unchanged

[Upstream PR](https://github.com/sgl-project/sglang/pull/43855) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, DeepSeek-V4.1's mHC boundary defers its reduce + sinkhorn into the next RMSNorm launch: one extra program per row runs `_hc_mix_reduce_sinkhorn_row` beside the norm rows. At decode batch 1 that program is the critical path of every hosted norm, about 86 launches per target forward. The row was slower than it needed to be in two ways:

- **Loads between reductions.** Each `tl.sum` ends in a barrier, and the row issued its next global loads only after it: the partials one reduction at a time, then `hc_base` / `hc_scale` after the scratch reload. Every reduction therefore waited on another global round trip.
- **Full IEEE division in the sinkhorn.** Triton's `/` lowers to `v_div_scale`, `v_rcp`, two Newton steps, `v_div_fmas` and `v_div_fixup`, about 40 times per row. The scale and fixup steps only act on zeros, infinities, NaNs, denormals and extreme exponent gaps, which the sinkhorn's operands after the first division never are.

## Modifications

All in `python/sglang/kernels/ops/layernorm/mhc_boundary_hip.py`; outputs are bitwise unchanged.

- Issue every load (`hc_scale`, `hc_base`, all partials) before the first reduction. Tiles, layouts and reduction trees are unchanged.
- `_sinkhorn_div(n, d)`: `v_rcp_f32` plus the same Newton steps as `/`, without the scale and fixup. It replaces `/` for every sinkhorn division except the first, where `exp` may underflow.
  - After the first division entries stay in [~1e-12, 1] and divisors in [eps, ~hc], so the quotient bits are those of `/`.

## Accuracy Tests

- `test/registered/kernels/ops/layernorm/test_hc_boundary_hip.py` (gfx950): 7 passed, in about 8 s against its registered `est_time=15`.
  - New `TestSinkhornDivision`: 1M log-uniform operand pairs in the sinkhorn's range against correctly rounded fp64. Replacing the helper with a reciprocal-multiply (`n * rcp(d)`) fails it.
  - The existing tests still pass: torch / fp64 references, hosted vs standalone bitwise, batch invariance.
- Whole-row bitwise check during development, not kept as a test: `pre`, `post` and `comb` were compared with `torch.equal` against main's row. It covered 1-320 rows, every hosting norm (fp8 grid, MXFP8, plain) plus the standalone launch, with and without a pending `hc_post`, and mixing scales up to 1e3. It was dropped because it carried an 80-line copy of main's kernel in the test file.
- Division sweep: 2^30 random pairs in the same range, 0 mismatches against `/`.
- End to end, DeepSeek-V4.1-Flash TP4 with DSpark and real acceptance, on main 166b4ae7fc with #43821 and #43822: correct answers (391 / Paris / 42) and 0 NaN / error lines.
