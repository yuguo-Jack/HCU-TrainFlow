# [Feat] [AMD] mori: Run MORI EPv2 dispatch/combine on AsyncLL kernels for TBO

[Upstream PR](https://github.com/sgl-project/sglang/pull/44492) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #40666 (MORI EP V2). MORI is adding an **AsyncLL** kernel family for EPv2 (ROCm/mori#768) that splits each dispatch/combine into a send half and a receive half, with an `sdma` (copy engine) or `lsa` (peer store) transport. This PR lets SGLang's EPv2 dispatcher drive those kernels so that, with two-batch overlap, the sibling micro-batch computes while a transfer drains.

Opt-in only (default off); nothing changes for existing EPv1/EPv2 users.

**Draft because it depends on unmerged MORI work:**
- ROCm/mori#768 (AsyncLL kernels), and
- a fix on top of it for the received topk weights: [ChengYM5685/mori@`f9ae1c4d`](https://github.com/ChengYM5685/mori/commit/f9ae1c4da3af4d52e2668a9564b7266012354da1). Without it, `dispatch_recv()` (and any rank with zero local tokens) leaves the recv weights zeroed, every routed expert contributes nothing, and the model outputs garbage.

## Modifications

- `environ.py`: `SGLANG_MORI_EPV2_ASYNC_LL` (bool, default `false`) and `SGLANG_MORI_EPV2_ASYNC_LL_TRANSPORT` (`sdma` | `lsa`, default `sdma`).
- `arg_groups/moe_hook.py`: `MORI_ENABLE_SDMA=1` no longer forces EPv1 when AsyncLL is on (EPv2 uses SDMA only through AsyncLL).
- `token_dispatcher/moriep.py` (EPv2 normal dispatcher only):
  - `dispatch_a` / `combine_a` call `dispatch_send` / `combine_send`; `dispatch_b` / `combine_b` call `dispatch_recv` / `combine_recv`. The DSV4 prefill TBO yields fall between the halves; without TBO they run back to back.
  - No comm stream and MORI's own launch geometry under AsyncLL (it derives grids from the CU count).
  - fp4 dispatch and quantized combine fall back to bf16 with a warning (AsyncLL has neither).
  - Keep the full receive view (the AsyncLL layout is not checked against `SGLANG_MORI_RECV_BOUND`).
  - Size the cco window from MORI's `asyncll_regions` (the AsyncLL arena is larger than the intranode one).
  - Each TBO child keeps its own `MoriEPDispatcher(instance_id=i)` / op, so pending send/recv state never mixes.
- Docs: the two new variables.

**Second commit (separate fix, independent of AsyncLL):** `[Fix] dsv4: Keep compressor prefill plan pinned buffers alive until copied` (`compress.py`). `CompressorPrefillPlan.generate*` builds the plan in a pinned host buffer and copies it with a raw `cudaMemcpyAsync`, which torch's host caching allocator does not track; once the plan is dropped, the block can be reused by the next same-sized plan and overwritten before the queued copy reads it. The TBO two-chunk split (two same-sized plans back to back) makes this likely and is the cause of the `flash_c128_prefill` page fault below. The fix records an event behind each copy and keeps the buffer until it completes (skipped under graph capture). It is needed by any DSV4 + TBO run with the default `--tbo-token-distribution-threshold`, with or without AsyncLL.

## Accuracy Tests

MI455 (gfx1250, SPX, one node), DeepSeek-V4-Flash, `--tp 4 --attn-dp-size 4 --ep-size 4 --moe-a2a-backend mori --deepep-mode normal`, eager, `--tbo-token-distribution-threshold 0`, MORI #768 + the fix above:

- MORI level: native EPv2 vs AsyncLL `sdma` / `lsa` on the same inputs (EP4, one rank sending 0 tokens) give bit-identical received hidden / topk ids / topk weights and combine output. MORI's `test_asyncll.py` passes for both transports (default shapes + hidden 4096 / top-k 6 / 64 experts per rank / 4096 tokens).
- Server level: greedy outputs of 4 prompts × 2 rounds (covering all 4 DP ranks) with AsyncLL `sdma` + TBO and `lsa` + TBO are token-identical to native EPv2 + TBO.
- AgentX (aiperf `agentx` scenario, CONC=2, session-sticky DP routing), AsyncLL `sdma` + TBO, 20 min: 25 requests, 0 errors, prompt cache hit 93.8%.

## Speed Tests and Profiling

Prefill-only load (random ids, ISL 4096, OSL 1, 128 requests at once, `--chunked-prefill-size 16384`), eager, same setup:

| Config | Input tok/s | Mean TTFT |
|---|---|---|
| EPv2 native | 22.1k | 12.7 s |
| EPv2 native + TBO | 21.1k | 13.3 s |
| EPv2 AsyncLL sdma + TBO | 18.3k | 15.1 s |
| EPv2 AsyncLL lsa + TBO | 17.3k | 16.0 s |

AsyncLL is not faster yet in eager mode; this PR wires the path up so it can be tuned (CUDA graph, TBO split policy, MORI kernels).

## Known issues (not caused by this PR)

- ~~DSV4 TBO with the default `--tbo-token-distribution-threshold` (two-chunk split) page-faults in `flash_c128_prefill` on gfx1250 under load, with native EPv2 too; `0` avoids it.~~ Fixed by the second commit: with the default threshold (0.48), AsyncLL `sdma` + TBO ran AgentX c16 for 20 min (200 requests, 0 errors, no fault; before the fix it faulted within 1–2 min), and mean TTFT went from 1.49 s (threshold 0) to 1.32 s.
- AsyncLL fails on DPX-partitioned nodes (sdma hangs, lsa combine mismatches) in MORI's own test; SPX is fine.
