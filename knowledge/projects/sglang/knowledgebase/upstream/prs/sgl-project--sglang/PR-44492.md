# [Feat] [AMD] mori: Run MORI EPv2 dispatch/combine on AsyncLL kernels for TBO

[Upstream PR](https://github.com/sgl-project/sglang/pull/44492) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #40666 (MORI EP V2). Two things kept two-batch overlap (TBO) from paying off for DeepSeek-V4 on AMD with MORI EPv2:

1. **Communication occupied the compute units.** MORI's AsyncLL kernels (ROCm/mori#768, merged) split each dispatch/combine into a send and a receive half and move data with the copy engine (`sdma`) or peer stores (`lsa`). This PR lets the EPv2 dispatcher drive them, so one micro-batch computes while the other's transfer drains. Both micro-batches stay on one compute stream.
2. **TBO silently did nothing with DSpark.** DSV4 turned TBO off whenever DSpark captured aux hidden states. This PR captures them per micro-batch, so TBO runs with DSpark.

AsyncLL is opt-in through the existing switches (`--deepep-mode low_latency` or `MORI_ENABLE_SDMA=1`); default EPv1/EPv2 behavior is unchanged.

**Related MORI PR:** ROCm/mori#892 gives each AsyncLL op its own SDMA queue (opt-in); this PR turns it on when MORI supports it. Without it, results are correct but TBO prefill is about 11% slower.

## Modifications

**MORI EPv2 AsyncLL** (`moriep.py`, `moe_hook.py`)
- `low_latency` sends in `*_a` and receives in `*_b`; `normal` + SDMA sends and receives back to back. With either switch EPv2 runs AsyncLL instead of falling back to EPv1 (EPv1 only if the MORI build lacks AsyncLL).
- fp4 dispatch falls back to MXFP8 (bf16 on gfx1250), combine to bf16, since AsyncLL has no fp4 or quantized-combine kernels.

**MORI dispatcher under TBO**
- TBO-only transfer settings (comm stream, full receive buffer) apply only to TBO micro-batches, no longer to every forward once TBO is enabled.
- `SGLANG_MORI_RECV_BOUND` also bounds TBO micro-batches (each by its own per-rank rows) and AsyncLL.
- `SGLANG_MORI_NUM_MAX_DISPATCH_TOKENS_PER_RANK` defaults to the per-rank chunked prefill when unset (at least 4096).

**DSV4 + DSpark + TBO**
- TBO runs together with DSpark's aux hidden state capture.
- Fixes for DSV4 + TBO: a pinned-buffer race in the compressor prefill plan (page fault), DSpark verify batches that TBO cannot split (crash), and DSpark draft steps losing their CUDA graphs under TBO.

Also a hang fix in MORI's LSA probe, docs, CPU unit tests, and TBO/AsyncLL modes in the manual 8-GPU dispatcher test.

## Accuracy and Speed Tests

**gfx950** (8x MI355X, DeepSeek-V4-Pro, TP8/DP8/EP8 + DP attention, DSpark, mxfp8 dispatch, `SGLANG_MORI_RECV_BOUND=1`, TBO, eager prefill; random 8k input / 1 output, 1024 requests at c256):

| | input tok/s | gsm8k (200 q) |
|---|---|---|
| native EPv2 | 81.4k | 0.975 |
| AsyncLL `low_latency` + SDMA, shared SDMA queue | 70.6k | — |
| AsyncLL `low_latency` + SDMA, per-op queue (#892) | 79.7k | 0.965 |
| same, decode with CUDA graphs | 79.7k | 0.980 |

Unit tests and the 8-GPU manual dispatcher test (7 configs) pass.

**gfx1250** (DeepSeek-V4-Flash, single node, DSpark):
- AsyncLL `sdma` / `lsa` vs native EPv2: bit-identical dispatch/combine outputs at the MORI level, token-identical greedy outputs at the server level; gsm8k with TBO: native 0.960, AsyncLL 0.950 / 0.965; AgentX c64 for 1 h, 0 errors.
- DSpark + TBO vs no TBO (3 runs each): gsm8k 0.935–0.965 vs 0.920–0.940; prefill +3.8% with 8192 tokens per rank.

## Known issues (not caused by this PR)

- TBO still costs decode throughput when short prefills interleave with decode; for decode-heavy serving, leave `--enable-two-batch-overlap` off.
- AsyncLL fails in MORI's own test on DPX-partitioned gfx1250 nodes; SPX is fine.

- Duyi-Wang · comment · 2026-10-27T06:37:12Z · [source](https://github.com/sgl-project/sglang/pull/44492#discussion_r4385780706)

File: `python/sglang/srt/environ.py` · line None

Could we remove `SGLANG_TBO_MIN_EXTEND_TOKENS` and the associated threshold check from this PR, keeping the existing TBO eligibility policy? Although the default of 0 preserves current behavior, setting a positive threshold disables TBO for small prefills without switching the configured EPv2 AsyncLL dispatcher back to the normal kernels: dispatcher selection still follows `deepep_mode` / `MORI_ENABLE_SDMA`, independently of the per-batch TBO decision. This can leave the batch using AsyncLL without the intended cross-microbatch overlap. A token-based policy would be better evaluated separately with benchmarks for both overlapped AsyncLL and non-overlapped normal kernels, plus consistent graph capture/replay handling. It does not seem necessary for enabling EPv2 AsyncLL/TBO support here.
