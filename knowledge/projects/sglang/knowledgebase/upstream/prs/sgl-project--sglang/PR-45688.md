# [Feat] scheduler: Add a skip-join MLFQ policy with cache-aware placement and a prefill gate

[Upstream PR](https://github.com/sgl-project/sglang/pull/45688) · state: open · merged: False

## Original PR description

## Motivation

SGLang runs a prefill batch of waiting requests before the running batch's next decode step, and the scheduling policy only orders the waiting queue: it decides which prompt is prefilled next, not whether a prefill runs now. Under agent-style traffic, long prompts with short answers and many returning turns, that step model pauses every running request for every newcomer's prefill. On an A100 a fresh 50k-token prompt is seven chunks of 0.6 to 2.9 s each, about 6.8 s back to back, while a decode step takes 40 ms; a 30-token tool-call answer that needs 1.2 s of decode spends most of its life waiting for other requests' prefills. Measured under fcfs on the Mooncake tool-and-agent trace (Kimi production traffic, FAST'25), the mean time per output token was 646 ms against a 40 ms step: each decode step waited fifteen times its own compute. No queue order fixes that: fcfs, lpm, shortest-prefill-first and an MLFQ without a gate landed within 4% of each other on this trace.

`--schedule-policy sj-mlfq` is FastServe's skip-join multi-level feedback queue (Wu et al., arXiv:2305.05920) adapted to a prefix-caching engine, with the one decision SGLang's step model allows: whether a prefill starts now. A request joins the queue level its predicted first iteration fits, priced from the uncached suffix it must prefill on top of its cached prefix, not from the whole prompt (cache-aware placement). It drops a level each time it uses up a level's quantum and is promoted back after 3 s without service. The level is stored as the request priority, so the existing priority retraction policy follows it. The prefill gate holds a new prefill while the head of the queue is less urgent than the most urgent running request; the step is then a decode step. That is FastServe's iteration-level preemption expressed through SGLang's own "no batch, run a decode step" path.

On the trace with Qwen3-8B on one A100: mean JCT 12.3 s against 17.5 s for fcfs and 15.5 s for the best SGLang-native configurations, at the same throughput, with no retraction and the p99 of long answers unchanged. Nothing changes unless the policy is selected.

## Modifications

- New module `python/sglang/srt/managers/skip_join_mlfq.py`: `SkipJoinMlfq` (placement, re-pricing of waiting requests that have not run, charging and demotion, starvation promotion, the gate level) and `OnlinePrefillCostModel` (a seed cost shape; two scale factors fitted by ridge least squares with forgetting from the prefill batches the scheduler runs, so no hardware profile is needed).
- `SchedulePolicy`: `sj-mlfq` joins the cache-aware policies. `calc_priority` hands the queue to `SkipJoinMlfq.order`, which places new requests, re-prices waiting ones, promotes starved ones and sorts by (level, level entry time); SGLang's in-batch prefix set still defers duplicate prefixes for one ordering. Two methods for the scheduler, `prefill_gate_level(running_reqs)` and `gate_blocks(req, gate_level)`, so the scheduler's lines read as calls.
- `Scheduler._get_new_batch_prefill_raw`: after `calc_priority`, if no chunked prefill is in progress and the queue head is held by the gate, the pass returns no batch and the event loop runs a decode step. Inside the admission loop, the first waiting request the gate holds ends the loop, the queue being in level order. A chunked prefill already started continues regardless.
- `SchedulerBatchResultProcessor._charge_mlfq`: once a batch's outputs are on the host (after `copy_done.synchronize()`, prefill and decode batches alike), the rank that sources the request stream measures the batch's elapsed time since `launch_ts` and its end timestamp, both are broadcast with `attn_cp_tp_broadcast_pyobj` (a no-op at TP 1), the policy charges the batch's requests, and prefill batches feed the online model.
- `Req`: five fields (`mlfq_level`, `mlfq_runs`, `mlfq_service_s`, `mlfq_level_entry_time`, `mlfq_last_service_time`). They survive retraction, so a returning request keeps its level.
- Flags: `--schedule-policy sj-mlfq`; `--sj-mlfq-cost cache-aware|prompt` (default `cache-aware`; `prompt` is FastServe's whole-prompt rule, kept so the ablation can be reproduced); `--sj-mlfq-base-quantum-ms` (default 10, FastServe's value). Validation: sj-mlfq requires `--enable-priority-scheduling` with the default higher-values-first order and the radix cache (it raises without it, as shortest-prefill-first does). Docs: the three rows in the server arguments page; `hrrn` and `shortest-prefill-first` added to the `--schedule-policy` choices cell, which lacked them.

The configuration measured below is `--schedule-policy sj-mlfq --enable-priority-scheduling --retraction-policy priority --disable-priority-preemption`, which the help text recommends. FastServe's other mechanisms, proactive swap-in of the next requests' KV and an eviction order by queue level, were ported and measured and are not in this PR: needed KV is almost never evicted at these pool sizes (host hits are zero on the natural pool and 3 to 4% of prefill input on the pinned pool), so neither had a measurable effect.

### Analysis of results

- **The mean and median gains come from not pausing short answers.** Half of the requests generate at most 30 tokens. Under fcfs they took 12.2 s on average, 7.2 s of it waiting for their own prefill behind others; with the gate they take 3.8 s. A short answer is now paused only when the head of the queue is more urgent than the most urgent running request, so it runs its decode steps back to back instead of pausing around every prefill. The time per output token shows the same thing: 646 ms under fcfs, 69 ms here, within a factor of two of a decode step.
- **Time to first token improves less than under shortest-prefill-first, and that is the trade.** Shortest-prefill-first admits short prefills at once, even when they are less urgent than the running answers. It reaches a TTFT of 3.8 s against 5.1 s here, but each admitted prefill pauses every decoder, so its time per token is 62% worse than fcfs and its mean JCT gain stops at 12%.
- **SGLang's two timing flags each fix one metric.** `--prefill-decode-interval 8` reaches the same time per token as this policy (64 ms against 69 ms) by forcing eight decode steps after every prefill, but it delays every prefill alike, so TTFT is 19% worse than fcfs and the mean gain is 5%. Mixed chunks halve the time per token because decodes ride along with every prefill, but a 30-token answer still takes 30 steps, each lasting as long as a prefill chunk (0.6 to 2.9 s) rather than 40 ms, so the mean gain is 12%. The gate decides per step whether a prefill should run at all, which is what neither flag can do.
- **Returning turns carry the cache-aware gain.** Of the 1,738 requests, 1,019 are returning turns. Their TTFT is 7.2 s under fcfs, 4.4 s with FastServe's whole-prompt placement and 2.7 s with cache-aware placement, with the gate and everything else identical between the last two; their JCT follows, 13.2 s to 6.9 s to 5.2 s. A 60k-token turn with 55k tokens cached costs about 1.2 s to prefill, not the 9 s of a fresh prompt; pricing it as a fresh prompt puts it two levels too low. Fresh prompts are unchanged (23.8 s to 22.5 s).
- **Long answers are not worse off.** Their prefill may start later while short answers finish, but once running their decode steps are no longer paused either: p99 JCT 73.0 s against 74.2 s, and the mean of answers over 200 tokens 24.6 s against 25.9 s.
- **Throughput is equal by construction under capacity**, so the equal 0.48 req/s is not by itself evidence of zero capacity cost. The saturation run is: at 11x slowdown on the same pinned windows (arrivals at 0.69 req/s against 0.63 completed), mean JCT is 40% below fcfs with throughput still equal and p99 unchanged; shortest-prefill-first is 31% below, lpm with mixed chunks 24%, fcfs with mixed chunks 8% above. This policy loses one of the four saturated windows, window 25, to shortest-prefill-first by 6% (21.4 against 20.2 s), reported as measured.
- **More concurrency, more gain.** On the natural 393k-token pool more requests run at once, so each prefill under fcfs pauses more of them: mean JCT 41% below fcfs on windows 10 and 25 (13.1 against 22.3 s), where the best native row (interval 8) reaches 25%.
- **The workload shape sets the size of the gain.** Removing the pauses helps most where short answers share the server with long prefills. On the Mooncake conversation trace (window 10, natural pool), where the median answer is 350 tokens, the gain is 16% on mean JCT, 24% on TTFT and 62% on TPOT, where lpm with mixed chunks is 1% worse than fcfs. Uniform request lengths leave placement nothing to distinguish and the gate little to hold; the policy then degrades to fcfs with better per-token time.

**Reproduction:** Benchmarks used Qwen3-8B on an A100 80GB with a 160k-token KV pool, replaying one-minute windows at minutes 10, 25, 40 and 55 of the Mooncake tool-and-agent trace at 15× slowdown. The server configuration and results are documented above. PR #45687 also fixes SGLang's built-in Mooncake dataset to preserve the trace's original prompt lengths and shared prefixes.

## Where it also applies

- **Newer GPUs.** The pause the gate removes is a prompt's prefill time; faster hardware shortens it, but it also shortens the answers that suffer from it, and what matters is the ratio. Prefill is compute-bound and decode is bandwidth-bound: an H100 has about three times the A100's bf16 compute but about 1.7 times its memory bandwidth, so prefill speeds up roughly twice as much as decode and the relative pause roughly halves; Blackwell raises both by similar factors and keeps that ratio. A 60k-token prompt still pauses every running answer for one to two seconds on an H100 against decode steps of a few tens of milliseconds. The gain shrinks with the ratio; it does not go away. The 2x RTX PRO 4500 run below is the one Blackwell datapoint so far.
- **Larger KV pools and larger models.** More memory means more concurrent requests, and every prefill pauses all of them: the natural pool's 41% against the pinned pool's 30% is this effect, and an H200 or B200 pushes further that way. Model size scales prefill and decode time together, so the ratio holds, and the online cost model refits its scale to the model within the first few dozen prefill batches.
- **Prefill-decode disaggregation.** On the prefill node, placement and queue order apply as described: returning turns are priced by their cached prefix and prefilled ahead of fresh long prompts, which is the TTFT part of the gain; the gate has nothing to protect there, since no decode runs on that node. On the decode node there is no prefill to pause anything, so the policy is inactive and retraction keeps SGLang's default order. The policy is additive to disaggregation, not in conflict with it; the gate's part of the gain is specific to colocated serving, which is how most deployments run.
- **Tensor parallelism.** Every attention-parallel rank runs its own scheduler and must build the same batch; demotion is a threshold on charged time and placement comes from a fitted model, so the ranks must see the same timings. The policy never reads the wall clock itself: the source rank's elapsed time and end timestamp are broadcast, and the policy keeps that timestamp as its clock (unit-tested: the same charged sequence gives the same state however much wall time passes). Run at TP 2 on 2x RTX PRO 4500 Blackwell (pinned 160k pool, window 10, host cache pool 40 GB): all 438 requests completed, mean JCT 10.7 s, p50 5.0 s, p99 55 s, TTFT 3.7 s, TPOT 56 ms, no retraction, matching TP 1 on the A100 on the same window (12.4 s); TP 1 on a single 4500 is compute-bound on this window (21.0 s).
- **Not measured:** data-parallel attention (each DP rank gates its own queue; a rank that builds no batch still takes part in the prefill delayer's negotiation through `finalize`), speculative decoding (a verify step is charged as one pass), Mamba and SWA models, TP above 2. Each is read from the code.

## Design notes for reviewers

- The level lives in `req.priority`, so under sj-mlfq a priority sent with a request is validated as today and then replaced by the level. The help text says so; a client priority as an offset or tie-break is a possible follow-up.
- The charged time runs from `launch_ts` to the outputs being on the host, which under the overlap scheduler includes the wait behind the previous batch, so it overstates a pass by about one level of earlier demotion. Levels are logarithmic and the gain above was measured with the overlap scheduler on, so it is left as is.
- The 10 ms base quantum is a flag with FastServe's value as the default; the help text says to set it to about one decode step. The seed cost (Qwen3-8B on an A100) only sets the starting scale of the online model.
- Starved requests are promoted every 1,000 orderings after 3 s without service (FastServe's values). A demoted long request behind a steady stream of short arrivals could wait tens of seconds; the trace's bursty arrivals did not produce it.
- The policy relies on priority retraction, not preemption. With the gate, an urgent arrival that does not fit in memory waits for a running answer to finish, which is quick; preempting instead costs the victim its place and a reload and paused everyone else, and measured at thresholds 0 and 3 it raised long answers' p99 from 196 s to 336 s. The recommended configuration therefore disables preemption, and the final rows have zero retractions.
- The gate is unconditional because the policy without it, placement and demotion only, was within 4% of fcfs, lpm and shortest-prefill-first.

## Tests

- `test/registered/unit/managers/test_skip_join_mlfq.py` (CPU): cache-aware placement prices the uncached suffix (level 3 against level 6 for the whole prompt); the level is the log2 of cost over quantum; order is level then level entry time; in-batch prefix siblings go to the back for one ordering; demotion after the level quantum; the same charged sequence gives the same state however much wall time passes; starvation promotion follows the charged clock; a waiting request is re-priced only down and only before it runs; the gate level is the most urgent running level and None with nothing running; the online cost model starts from the seed and learns a doubled scale within 15%.
- `test/registered/unit/managers/test_schedule_policy.py` (CPU): sj-mlfq requires priority scheduling, orders by predicted prefill time, sets the priority, and gates on the running levels.
- `test/registered/scheduler/test_sj_mlfq_scheduling.py` (1 GPU): MMLU through `run_sgl_eval` with the policy, priority retraction, 512-token chunks, forced retraction and the strict memory check on, at the 0.64 threshold `test_retract_decode.py` uses for the same model.

Run on an A100 pod with this branch installed at upstream main `da7b97a737`: the 12 CPU cases and the docs-coverage test pass, and the MMLU test passes with Qwen2.5-7B-Instruct standing in for the gated CI model (score 0.746 against the 0.64 bar). CI has not run yet (draft).

## Accuracy Tests

The policy decides when a request runs, not what it computes; the retraction order changes only which request is retracted. GSM8K through the sgl-eval CLI on Qwen3-8B, 200 examples, non-thinking (`--temperature 0.7 --top-p 0.8 --max-tokens 2048 --no-thinking --chat-template-kwarg enable_thinking=false`), same server settings as the speed runs: 94.5% without the policy, 93.5% with `--schedule-policy sj-mlfq --enable-priority-scheduling --retraction-policy priority --disable-priority-preemption`, inside the 1 to 5% variance the contribution guide gives for this check. The MMLU test above is the CI check.
