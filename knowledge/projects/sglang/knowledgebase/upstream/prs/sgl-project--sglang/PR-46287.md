# [Fix] lora: Skip LoRA release for requests rejected before adapter acquire

[Upstream PR](https://github.com/sgl-project/sglang/pull/46287) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-lora`, a `/generate` request that is rejected before its adapter is acquired still schedules a LoRA release.
`_release_lora_once` treats `lora_path` as the sign that a request holds an adapter reference, but `lora_id` is only set by a successful `LoRARegistry.acquire`.
When `_resolve_lora_path` rejects the request first (an adapter name that was never loaded, or more unique adapters than `--max-loaded-loras`), the cleanup in `_release_req_states_on_failure` calls `lora_registry.release(None)` once per request state.
Each of those tasks raises `TypeError: lora_id must be either a string or a list of strings.`, and asyncio logs `Task exception was never retrieved` with a full traceback.
The counters stay correct, so the impact is noise, but every rejected LoRA request with `n=3` writes three tracebacks to the server log, which reads like a crash to operators.

Reproduced on `main` (406786fd9) with a live server (tiny Qwen3, `--enable-lora --max-lora-rank 8 --lora-target-modules all --max-loaded-loras 2`):

```bash
curl -s localhost:30000/generate -H 'content-type: application/json' \
  -d '{"text":"x","lora_path":"nope","sampling_params":{"max_new_tokens":4,"n":3}}'
# 400, and the server log shows 3x:
# Task exception was never retrieved
# future: <Task finished name='Task-309' coro=<LoRARegistry.release() done ...> exception=TypeError(...)>
# TypeError: lora_id must be either a string or a list of strings.
```

In our probe, two rejected requests (unknown adapter with `n=3`, and three adapters over `--max-loaded-loras 2` with `n=2`) produced 9 tracebacks.
#33300 (against `sglang-miles`) describes the same ownership rule ("treat the acquired `lora_id`, rather than `lora_path`, as the ownership signal ... avoids `release(None)`"); this PR is the minimal fix for `main`.

## Modifications

- `TokenizerManager._release_lora_once`: release only when the state has an acquired `lora_id` (as well as `lora_path`). One condition, so every caller (normal finish, abort echo, error, failed dispatch) gets the fix.
- `test_tokenizer_manager_rid_cleanup.py`: regression test `test_unknown_adapter_rejection_releases_nothing` (single request and `n=3`) asserting that no release task is scheduled, no state leaks, and the registered adapter's counter stays at 0.

Requests that did acquire an adapter are unchanged: `lora_id` is set by `acquire` and propagated to sub-requests, so their release still happens exactly once.

## Test plan and results

SGLang's suite is large, so only the relevant tests were run (CPU, Python 3.12, torch 2.14.1+cu130):

- New test on `main` without the fix: `2 failed, 1 passed, 48 deselected` (both `n=1` and `n=3` subtests fail on the pending `LoRARegistry.release()` tasks).
- With the fix: `test/registered/unit/managers/test_tokenizer_manager_rid_cleanup.py` `49 passed, 43 subtests passed`.
- `managers/test_lora_update_result_merge.py`, `managers/test_tokenizer_manager_rid_cleanup.py`, `entrypoints/test_server_info.py`: `84 passed, 61 subtests passed`.
- `pre-commit run --files` on both changed files: all hooks pass (isort, ruff, ruff-format, codespell, registered-test checks).
- End to end on an RTX 5070 Ti with a live server and a random LoRA adapter on a tiny Qwen3: an 8-scenario LoRA hot-load probe (client disconnect mid-stream and mid-batch with `n=4`, unload during an in-flight request, reload after unload, duplicate load, eviction past `--max-loaded-loras`, pinned adapter, unknown adapter with `n>1`, then `/health_generate` and SIGTERM). All HTTP results are identical before and after the fix; the `TypeError` tracebacks go from 9 to 0.

## Limitations

- `GenerateReqInput.lora_id` is still a dataclass field that a client can set in the JSON body. This PR does not change how a client-supplied `lora_id` is handled; it only stops releases for requests whose `lora_id` is still `None`.
