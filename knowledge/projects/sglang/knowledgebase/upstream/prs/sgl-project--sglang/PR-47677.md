# [Perf] [NVIDIA] dspark: Stage draft DP-MoE token counts through persistent buffers

[Upstream PR](https://github.com/sgl-project/sglang/pull/47677) · state: open · merged: False

## Original PR description

## Motivation

Under DP-MoE sync, `DraftBlockProposer._fill_dp_moe_sync_metadata` builds two fresh pinned `torch.tensor`s each decode step and copies them H2D: the draft's `global_num_tokens_gpu` and `global_num_tokens_for_logprob_gpu`. The draft ForwardBatch also gets a fresh `global_num_token_non_padded` H2D twice, once when it is built and once in the fill.

On DSV4.1-Flash GB300 disagg DEP16, this host work costs `P.dp_meta` 0.23-0.26 ms and `P.fwdbatch` 0.21 ms. It sits on the host path between the DP agreement and the draft graph launch.

## Related PRs

One of four DSV4.1 attn-DP decode host-path changes that cut the host work between the DP agreement and the draft graph launch. They are independent in code and were measured together: #47676 (padded metadata glue), #47677 (persistent DP-MoE counts), #47678 (bulk decode-prep fill) and #47685 (KV page top-up, measured on top of the other three).

## Modifications

- Under DP-MoE sync (MoE draft with attention DP, idle-rank participation included), both count rows go into a two-slot pinned `[2, 2, dp]` host buffer, written through its numpy view, and one H2D copies them into a matching device buffer. `global_num_tokens_gpu` and `global_num_tokens_for_logprob_gpu` are views into the current device slot.
- Every DSpark draft step that uses `num_token_non_padded` (EP > 1, DP gather, a custom A2A backend, DP attention with TP MoE) passes the persistent `_num_token_non_padded` as `global_num_token_non_padded`, instead of a fresh H2D of the same value. The fill already writes that count into it. Later writers rebind the field, except the idle dummy-extend `fill_` in `prepare_mlp_sync_batch`, which writes the same value (0) that is already there.
- The per-step fresh-tensor path and `_make_num_token_non_padded` are removed. There is no env switch: the new path writes the same values and has no configuration in which the old one is better.

Why reusing the slots is safe:
- Device slot: it is rewritten two fills later. The fills and every consumer run on the same stream, so the rewrite is ordered after the earlier readers. `prepare_mlp_sync_batch` still writes `global_num_tokens_gpu` in place, now into the current slot.
- Pinned host slot: each slot records an event after its H2D, and the event is synchronized before the CPU rewrites the slot, so a copy still in flight is never overwritten. There is one fill per step, and with overlap scheduling the GPU is already past that copy two fills later, so the synchronize returns at once.

All runs: GB300, DSV4.1-Flash, on a 2026-10-30 nightly.

## Accuracy Tests

- GSM8K, 1P1D DEP16 with real DSpark acceptance, together with the two sibling host changes (#47676, #47678): 96.82% vs 96.89%; accept length 3.50 vs 3.49-3.51.
- TP4 c1 agg: T=1 GSM8K 97.33% vs 97.33%, long-context needle retrieval at 20K-160K tokens 48/48 vs 48/48 (greedy) and 24/24 vs 24/24 (T=1), accept length 3.591 vs 3.598.

**Issue**

These new GPU-count assertions cannot catch a row mix-up in `_stage_dp_meta`. Here both counts are `[0, 3 * width, 0]`, so the two rows hold the same values. Each test also builds a fresh proposer and fills once, so the two-slot reuse never runs.

**Example**

I changed `_stage_dp_meta` to `return dev[0], dev[0]`. All 13 tests in the three test files listed in the PR still pass.

**Fix**

In `test_preserves_unscaled_request_counts_for_cuda_graph_admission`, the counts differ (`[6, 18, 0, 12]` vs `[1, 3, 0, 2]`), so assert both GPU tensors there. Then fill three times with different counts on one proposer. Check that each call's tensors hold its own counts and that the third call reuses the first call's storage.
