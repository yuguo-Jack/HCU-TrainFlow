# [Perf] [AMD] triton: Scale KV cache writes out of place and drop the extend K/V clones

[Upstream PR](https://github.com/sgl-project/sglang/pull/47909) · state: open · merged: False

## Original PR description

## Motivation

`TritonAttnBackend.forward_extend` clones K and V before every scaled KV write only because the MHA pools' `set_kv_buffer` divides the caller's `cache_k`/`cache_v` by the scale in place; this PR makes the pools scale out of place and drops the two clones, removing two full K/V copies per extend call with identical KV cache bytes.

The clone runs for non-MLA triton extend whenever `layer.k_scale` is set, which FP8/Quark/ModelOpt checkpoints do (1.0 when they ship no KV scale), so it also runs with the default bf16 KV cache. On ROCm the default MHA backend is aiter, so with default flags only MiniMax-M3 reaches it (its override selects triton on HIP), on dense layers 0-2 of 60. The saving there is 2-20 us per call. Other models reach it with `--attention-backend triton` and a quantized checkpoint.

Related: #42181 (closed, unmerged) removed the clones by dividing on the triton side and leaving the pool in place. That also divides when the KV cache is bf16, where the pool skips scaling: in the micro below it is 13-61% slower than main on that case, and it changes the stored KV when the layer scale is not 1. #31652 (open) fuses the FP8 store on CUDA sm89+ but keeps the eager `div_` and the clones.

## Modifications

- `MHATokenToKVPool.set_kv_buffer`, `MHATokenToKVPoolFP4.set_kv_buffer`, `MHAView.set_kv_buffer` and the eager fallback of `_set_mha_kv_buffer_prefix_valid` use `torch.div(x, scale, out=torch.empty_like(x))` instead of `x.div_(scale)`. `out=` keeps the input dtype, so aiter's shape-[1] fp32 scale does not promote bf16 to fp32 and the result matches `div_`.
- Triton extend passes K/V without cloning; the MLA branch divides out of place instead of `clone().div_()`.
- Tests: a CPU case in `test_unified_mha_views.py` writes scaled FP8 K/V through the plain pool and the unified view, and checks that the caller's tensors are unchanged and the cache holds `(k / scale).to(fp8)`. `test_prefix_valid_fp8_pool.py::test_eager_fallbacks` asserted that the eager fallback mutates its inputs; it now asserts the opposite.

Cost: callers that never cloned (triton decode, FlashInfer/FA, aiter's SWA fallback, all with an opt-in FP8 KV cache) now allocate the scaled copy. Their device time is flat except at the largest point measured (8 KV heads, 30727 tokens): -10.6% / -11.8%. Eager wall-time medians are -5% to -12%, against a -6% noise floor.

## Speed Tests and Profiling

Micro: the `forward_extend` KV-save block into the real `set_kv_buffer`, HIP-graph device time on MI355X, main@d9521615b7 (the touched files are unchanged on main@b45a36531c). Four runs per arm, first discarded, median [min-max]; a reverse-order repeat agreed. MiniMax-M3 shape (4 KV heads x 128, 64 q heads), bf16 KV cache, `k_scale` 1.0:

| tokens | main (us) | this PR (us) | speedup |
|---:|---:|---:|---:|
| 37 | 10.01 [9.90-10.05] | 7.70 [5.88-7.76] | +29.9% |
| 2053 | 11.39 [11.38-11.68] | 7.56 [6.32-7.70] | +50.6% |
| 6151 | 16.65 [16.50-16.73] | 7.66 [6.96-7.99] | +117.5% |
| 30727 | 41.58 [41.13-41.64] | 21.20 [21.15-21.33] | +96.2% |

Medians over 3 shapes x 6 token counts: bf16 KV extend +87%, FP8 KV extend +30%, direct pool callers -0.5%. KV cache bytes match main at all 72 points.
