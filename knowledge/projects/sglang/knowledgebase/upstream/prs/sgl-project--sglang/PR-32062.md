# [FlashInfer] Plan wrappers from layer-local attention metadata

[Upstream PR](https://github.com/sgl-project/sglang/pull/32062) · state: closed · merged: False

## Original PR description

## Motivation

FlashInfer's metadata updaters currently derive `num_qo_heads` and sliding-window trim/window metadata from model-wide server arguments. That is not sufficient for models whose existing attention wrapper groups have different layer-local metadata.

Laguna-S-2.1 is one such model: full-attention layers use 48 query heads while sliding-window layers use 72. Both groups were planned with the global 48-head value, and all wrappers shared one ragged prefill planner. On ragged prefill, the last plan overwrote the shared planner state, so execution could use metadata from the other wrapper group.

This PR makes the backend contract generic: metadata may differ **between existing FlashInfer wrapper groups**, but it must remain uniform **within each group**. Laguna only needs a small model hook to normalize Hugging Face's inclusive `sliding_window=512` value to SGLang/FlashInfer's exclusive `window_left=511` convention.

This is the SGLang counterpart of the same root-cause fix previously implemented in vLLM ([vllm#41651](https://github.com/vllm-project/vllm/issues/41651), [vllm#42650](https://github.com/vllm-project/vllm/pull/42650)). I did not find an existing SGLang PR that resolves mixed query-head counts at FlashInfer wrapper-planning time.

## Modifications

- Resolve `num_qo_heads` and `window_left` from the instantiated `RadixAttention` layers assigned to each existing wrapper group.
- Validate that those values are uniform within a wrapper group and report an actionable error when they are not.
- Keep the existing global values as a compatibility fallback for pipeline partitions, mocks, and backends that inherit initialization without using the base FlashInfer planner.
- Give each wrapper group its own ragged prefill wrapper instead of sharing mutable plan state.
- Thread per-wrapper query-head counts through decode, prefill, speculative/DFlash, cross-attention, and CUDA-graph planning. Size the full-CUDA-graph workspace for the largest wrapper-group head count.
- Preserve current-main's path-specific window behavior:
  - ragged sliding-window prefill plans and executes with the finite window;
  - normal paged sliding-window prefill plans with the finite window;
  - speculative custom-mask and multi-item-scoring paged paths remain unwindowed at planning time;
  - decode keeps the existing trimmed-index/unwindowed-plan behavior.
- Add Laguna's `get_attention_sliding_window_size()` implementation, returning `config.sliding_window - 1`.
- Add CPU unit coverage for per-wrapper metadata resolution, validation, planner isolation, compatibility fallback behavior, and Laguna window normalization.
- Extend registered GPU coverage with an above-window default-ragged prefill case; run it together with the existing paged and DFlash eager/CUDA-graph cases.

The change intentionally does **not** claim arbitrary per-layer FlashInfer geometry. KV-head count, head dimensions, and decode tensor-core selection remain model-global; this PR only makes query-head count and window metadata local to the wrapper groups that SGLang already constructs.

<summary>Investigation notes (not all addressed by this PR)</summary>

### Root cause and differential analysis

- Laguna-S-2.1's full-attention layers instantiate 48 query heads and its sliding-window layers instantiate 72. The stock FlashInfer backend planned both groups from the global 48-head server argument.
- The two groups also shared a single ragged wrapper. Because `plan()` mutates wrapper state, the later group's plan replaced the earlier group's metadata before execution.
- Hugging Face expresses Laguna's sliding window as an inclusive token count (`512`), while the SGLang attention metadata and FlashInfer `window_left` use the exclusive-left value (`511`). Laguna already normalized this at the layer level; the runner/global pooling path still exposed `512`.
- An early port propagated the finite window to every paged plan. Differential testing against an untouched current-main worktree showed that current-main intentionally plans DFlash/custom-mask paged verification unwindowed. Keeping finite windows on ragged and ordinary paged SWA paths, while leaving custom-mask plans at `-1`, made both the baseline behavior and the missing ragged-window correctness case hold.
- A broad experimental branch also touched MoE/router, protocol, YaRN, and other model behavior. It was discarded. Reproducing the problem from a clean lineage isolated the required fix to attention planning plus Laguna's window metadata hook.

### Prior art and adjacent SGLang work

- vLLM diagnosed the same model/backend mismatch in [vllm#41651](https://github.com/vllm-project/vllm/issues/41651) and merged the generic group-local solution in [vllm#42650](https://github.com/vllm-project/vllm/pull/42650) ([commit](https://github.com/vllm-project/vllm/commit/c7624bea5ebba1c688eb4c216bd4ede7a94f2a82)). It reads instantiated attention-layer head counts and enforces uniformity inside each attention group. This PR follows that design at SGLang's wrapper-group boundary.
- The community [DGX Spark / RTX PRO 6000 recipe](https://github.com/MiaAI-Lab/Laguna-S-2.1-DGX-Spark-RTX-6000-PRO) succeeds with vLLM 0.25.1 because that release already contains the generic vLLM fix; the recipe does not need a model-specific source patch.
- [sglang#24204](https://github.com/sgl-project/sglang/pull/24204) introduced Laguna's per-layer head construction and layer-level window normalization. [sglang#29446](https://github.com/sgl-project/sglang/pull/29446) added Laguna DFlash support. Neither changes FlashInfer's model-global planner inputs.
- [sglang#31501](https://github.com/sgl-project/sglang/pull/31501) correctly adds finite plan-time windowing for ordinary paged SWA; it does not address mixed query-head counts or shared ragged-planner state, and this PR preserves its speculative/custom-mask behavior.
- [sglang#31918](https://github.com/sgl-project/sglang/pull/31918) and [sglang#29884](https://github.com/sgl-project/sglang/pull/29884) document FlashInfer/DFlash trouble and a TRTLLM workaround, but not this planner-metadata fix.
- Open PR [sglang#24198](https://github.com/sgl-project/sglang/pull/24198) proposes the independently identified FP8 cached-prefix K/V-scale fix, so it is intentionally excluded here.
- [sglang#31927](https://github.com/sgl-project/sglang/pull/31927) proposes FlashInfer `0.6.15.post1`; [sglang#31625](https://github.com/sgl-project/sglang/pull/31625) reverted an earlier 0.6.15 bump for performance. Upgrading FlashInfer changed neither the caller-provided head count nor shared wrapper state, so this PR does not bundle a FlashInfer dependency bump.

### Runtime findings outside this patch

- On SM121/TP=1, TRTLLM MHA's decode guard accepted the architecture. Relaxing the separate prefill gate reached the kernel, which then reported `Unsupported architecture`; the observed TP=1 failure is therefore distinct from the documented TP>=4 rejection and is not solved by widening a Python guard.
- DFlash's `speculative_num_steps=16` yields 15 draft proposals plus the verifier/bonus position. Setting it to 15 to obtain 15 proposals was an off-by-one configuration change and was reverted.
- The tested SGLang release exposed one global KV-cache dtype. A target FP8 KV cache combined with a BF16 drafter cache was therefore not representable in that runtime; BF16/BF16 was the qualified configuration.
- DFlash currently rejects grammar/structured-output constraints and logprob requests. Those limitations are independent of wrapper planning.
- The deployment was qualified at 32K context, not the model's advertised 262K maximum.
- Enabling `fix_mistral_regex=True` changed case-preserving coding tokens adversely in this tokenizer and was not used.
- A cached-prefix discrepancy led to the independently discovered FP8 K/V-scale omission, but open PR [sglang#24198](https://github.com/sgl-project/sglang/pull/24198) proposes the same two-scale fix.
- Target-only and DFlash runs produced the same *set* of greedy variants. Comparing only one output hash initially looked like corruption, but repeated output-set comparison did not support that conclusion.
- The deployed models were downloaded through the standard Hugging Face cache and mounted read-only; no model-specific cache directory was required.

### Full-model follow-up: this attention fix is necessary, but not sufficient by itself

Correction: the earlier version of this comment mixed results from different SGLang source lineages, including one run against the wrong checkout. That table is superseded by the exact-build comparisons below.

We now have a **local current-main workbranch that runs the Laguna target and DFlash drafter correctly within our present test regime** on a DGX Spark (GB10/SM121, TP=1). The passing build contains three pieces:

1. this PR, exactly as submitted;
2. the FlashInfer 0.6.15.post1 upgrade from #31927; and
3. a local SM12x compressed-tensors NVFP4 MoE patch that dispatches to FlashInfer b12x and prepares the checkpoint weights and scales for that kernel.

With all three pieces present:

- the target-only server and the target+DFlash server both load and capture CUDA graphs;
- all 12 repeated chat/raw semantic tool-call checks pass;
- the clean target-reference token hashes match;
- DFlash is active, and all speculative proposal/acceptance counter checks pass.

These are strong correctness checks for the exercised prompts and runtime paths, but they are not a claim of exhaustive model accuracy or maximum-context qualification.

We also rebuilt the same passing image with **only this PR reverted**. The server still loaded, captured graphs, and ran DFlash, but every semantic check failed and every clean-reference hash changed. That establishes that this attention PR is part of the working Laguna configuration; the local MoE patch does not make it redundant.

The local MoE patch is known-good within this test regime, but it is not ready to submit upstream as-is. Before opening a separate PR, we need to reduce it to the smallest upstream-appropriate change and distinguish kernel-contract requirements from compatibility workarounds for the current FlashInfer b12x API. That work should remain separate from this PR so this PR can stay focused on its generic wrapper-local attention-planning fix.
