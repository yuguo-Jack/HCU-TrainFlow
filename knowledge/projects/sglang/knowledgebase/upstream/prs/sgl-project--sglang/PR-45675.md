# [Test] [AMD] deepseek-v4.1: Check the HIP breakable graph metadata at the graph width

[Upstream PR](https://github.com/sgl-project/sglang/pull/45675) · state: closed · merged: False

## Original PR description

## What
`test_dsv41_bcg_hip.py` now asks the backend for the breakable graph's context width (`_graph_metadata_max_seq_len`) and checks the captured page table and the eager reference at that width, instead of assuming the capture batch's own width when no `max_seq_len` override is set.

## Why
`TestHipBreakableGraphCaptureReplay.test_capture_replay_matches_eager` has failed on every `stage-b-test-1-gpu-small-amd-mi35x` partition 0 run since Oct 19, on rocm10, rocm724 and rocm720:

```
File ".../test_dsv41_bcg_hip.py", line 168, in _capture_replay_matches_eager
    self.assertEqual(
AssertionError: 2 != 1
```

Example: https://github.com/sgl-project/sglang/actions/runs/39599109770/job/119218874753

Since #43733, `_graph_metadata_max_seq_len` falls back to `prefill_cuda_graph_default_max_seq_len` (16k for the V4.1 1/2 layout) instead of `None` when `cuda_graph_config[prefill].max_seq_len` is unset. Capture therefore builds at 16k, and `page_table_from_req_to_token` caps that at the fixture's `req_to_token` width (512), giving 2 pages. The test still expected `ceil(96 / 256) = 1`. Replay rebuilds the live metadata at that same width, so the eager reference the test compares against has to be built at it too. The `max_context_size` branch of the test already did this; it now covers the default path.

Test-only change.
