# [Feat] [AMD] attention: Enable ring attention on the AITER backend

## Motivation

<!-- Describe the purpose and goals of this pull request. -->
Currently ring attention cannot run with the AITER backend on ROCm.

This PR makes AITER backend ring-compatible and returns LSE on request. 

This PR also changes the default ROCm backend selection when using ring. AITER is the default backend when ring attention is selected.

Note: this PR previously also reworked `USPAttention` to handle replicated prefix/suffix tokens under ulysses+ring. #33327 has since solved that properly via `USPAttention._replicated_kv_attention`, which LSE-merges the replicated KV with the ring-sharded KV, so that work has been dropped and this PR has been rebased and trimmed to the AITER/ROCm half.

## Modifications

<!-- Detail the changes made in this pull request. -->
-  `AITerImpl.forward` takes `return_softmax_lse` and returns the BF16 kernel's LSE, and `AITerBackend.supports_ring_rotation()` declares the capability. The FP8 FMHA ASM path has no LSE output, so it yields to the BF16 kernel when an LSE is requested.
-  Adds `aiter` to `RING_CAPABLE_ATTENTION_BACKENDS`, the name-level admission list that gates before backend classes are importable on every platform.
- Returns AITER as backend by default when using ring and no attention backend is specified
-  Drops the AMD/ROCm ring skip in the server test fixture, and extends `test_ring_admission.py` with a ROCm-gated case pinning the name list to the backend capability.

I think this padding is not numerically safe. The padded K/V rows are still visible to the attention softmax, so they consume probability mass even though V is zero. For `num_rep` values that are not divisible by `total_sp_size`, this will silently change outputs rather than just making the replicated tokens shardable. Please either reject this case for now (`num_rep % total_sp_size == 0`) until masking is wired through, or pass a valid-token mask/length into the ring path so padded K/V tokens are excluded from attention.
