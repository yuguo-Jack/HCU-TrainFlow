# [Feature] Exaone4: size sliding-window layers from the hybrid SWA pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/41013) · state: closed · merged: False

## Original PR description

## Motivation

The Exaone override disables the hybrid SWA KV pool whenever `sliding_window_pattern` is set, and `Exaone4ForCausalLM` is not on the hybrid-SWA allowlist, so every sliding-window layer of EXAONE-4.0-32B (48 of 64, window 4096) is allocated a full-context KV pool. The window is still applied in attention, so this costs capacity, not correctness.

## Modifications

- **`configs/model_config.py`**
  - `Exaone4ForCausalLM` joins the hybrid-SWA allowlist, but only counts as hybrid when both `sliding_window` and `sliding_window_pattern` are set: with a pattern and no window, `models/exaone4.py` gives no layer a window. EXAONE-4.0-1.2B has neither (`Exaone4Config` loads its null pattern as `0`) and keeps the single pool.
  - `get_hybrid_layer_ids` applies the per-layer rule `models/exaone4.py` uses, `(layer_id + 1) % len(sliding_window_pattern) != 0`, rather than `layer_types`, so the pool split cannot drift from the layers the model actually windows.
- **`arg_groups/model_overrides/exaone.py`**: keeps the pool disabled for `ExaoneMoEForCausalLM` (it passes its window without the -1 Exaone4 applies and has an MTP draft; not validated here) and under the hierarchical cache (not validated with this change).
- **Tests**
  - `test_model_overrides.py`: the golden test that expected Exaone4 to disable the pool now expects it kept; new tests cover ExaoneMoE (still disabled) and the hierarchical cache.
  - `test_model_config.py`: the layer split, the model rule taking precedence over `layer_types`, the window/pattern guard (including the 1.2B's loaded values), and ExaoneMoE staying single-pool.

## Accuracy Tests

`LGAI-EXAONE/EXAONE-4.0-32B`, 2x MI325X, TP 2, `--attention-backend triton` (the Exaone4 hook accepts fa3/triton/trtllm_mha; triton is the one available on ROCm), `--mem-fraction-static 0.80 --context-length 18432`. The two GPUs also held an idle resident service using ~49% of their memory, so absolute numbers are not representative; before and after ran under identical conditions.

GSM8K via lm-eval (`local-chat-completions` with the chat template, 5-shot, all 1319 questions, greedy), strict match:

| radix cache | before | after |
|---|---|---|
| on | 0.939 ± 0.007 | 0.938 ± 0.007 |
| off | 0.938 ± 0.007 | 0.933 ± 0.007 |

Greedy `/generate` outputs (48 tokens) for prompts of window-1, window, window+1 and 2x window tokens, each sent twice so the second reuses the radix cache, plus a 2x window prompt extended by 512 tokens: 12/12 token-identical between before and after, with the radix cache on and off.

Negative control, EXAONE-4.0-1.2B (no sliding window), radix cache on: both arms run the same single pool (1,670,089 tokens), 12/12 identical probe outputs, GSM8K 0.707 vs 0.701. The code path is identical there, so that 0.6-point spread is the run-to-run noise of this eval.

## Speed Tests and Profiling

| | before | after |
|---|---|---|
| KV pool (tokens) | 530,224 (single pool) | full 623,792 + SWA 499,033 |

`bench_serving --dataset-name random-ids`, after a warmup round:

| workload | radix cache | output tok/s, before -> after | peak running requests |
|---|---|---|---|
| 384 x (8192 in, 1024 out), conc 128 | on | 726.2 -> 746.1 (+2.7%) | 58 -> 69 |
| 256 x (16384 in, 1024 out), conc 256 | on | 377.1 -> 384.1 (+1.8%) | 31 -> 36 |
| 384 x (8192 in, 1024 out), conc 128 | off | 747.9 -> 731.6 (-2.2%) | 56 -> 73 |
| 256 x (16384 in, 1024 out), conc 256 | off | 383.4 -> 380.5 (-0.8%) | 30 -> 37 |

Both workloads are KV-bound on this setup. With the default `--swa-full-tokens-ratio 0.8` the full pool admits 17.6% more tokens and 16-30% more concurrent requests, but output throughput only moves between -2% and +3%: median TPOT rises with the larger batches (e.g. 46 -> 70 ms with the radix cache off at conc 128), so on the triton backend the extra concurrency does not turn into throughput at these sizes.

Long context, 64 prompts of 32768 input / 1024 output tokens at concurrency 64 (`--context-length 34816`, otherwise the same setup), radix cache on:

| | KV pool (tokens) | output tok/s | median TTFT | median TPOT | peak running |
|---|---|---|---|---|---|
| before | 530,224 (single pool) | 186.9 | 170 s | 38.7 ms | 15 |
| after, default ratio 0.8 | full 623,792 + SWA 499,033 | 192.4 (+2.9%) | 157 s | 41.5 ms | 18 |
| after, `--swa-full-tokens-ratio 0.2` | full 1,325,559 + SWA 265,111 | 212.8 (+13.8%) | 140 s | 74.1 ms | 39 |

With a 4K window and 32K prompts the sliding layers need far less than 0.8x the full pool; at 0.2 the full pool is 2.5x the single pool, and 2.6x the concurrency turns into 13.8% more throughput.

These runs used upstream `a1b4ec02ae` with this diff applied (plus two local fp8-kernel patches that are not on this bf16 path); the diff applies unchanged to current `main`, where the unit tests were rerun.

Side note, not changed here: because `Exaone4Config` loads the 1.2B's null `sliding_window_pattern` as `0`, the Exaone4 hook's `sliding_window_pattern is not None` check still demands an explicit fa3/triton/trtllm_mha backend for that checkpoint, which has no sliding layers.
