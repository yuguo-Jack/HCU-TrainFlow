# [Feat] frozen-kv: Support adaptive steps and zero-step target decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/44914) · state: open · merged: False

## Original PR description

## Motivation

Frozen-KV MTP (Gemma 4) isn't connected to the adaptive spec controller, so it runs the same number of steps at every batch size. At large batch this costs a lot: on H20 with Gemma-4-12B, fixed 2-step is 24% slower than plain decode at bs 24 and 30–36% slower at bs 32–128. Even at 0 steps, Frozen-KV still pays for a width-1 target verify.

## Changes

- Frozen-KV draft backends and graphs are built as adaptive runtime states, and the existing `AdaptiveController` switches between them. There is no new policy.
- Opt-in `SGLANG_FROZEN_KV_ZERO_DECODE=1`: at 0 steps, run the ordinary target DECODE CUDA graph instead of a width-1 verify. Three things needed care:
  - the bonus token carried over from the last spec round has to be consumed at the right KV position;
  - the hidden seed is copied out before the graph reuses its storage;
  - Frozen-KV has no draft-extend forward, so the scheduler's write-after-read fence now waits on the target runner's read-done event, including across consecutive 0-step rounds.
- Grammar, logprobs and HiSparse stay on width-1 verify, and a verify batch is never replayed through the DECODE graph.
- Scope: CUDA, PP=1, Triton attention, topk=1. The adaptive docs are updated.

## Results

H20, Gemma-4-12B BF16, TP1, Triton attention.

The example policy uses 2 steps below padded batch 16 and 0 steps from 16 up. I chose the boundary after looking at the decode and static 2-step runs, so treat it as an example rather than a tuned default.

Fixed batch, 256-token prompts, 128 output tokens, 2 servers × 3 samples each:

| batch | decode | static 2-step | adaptive | adaptive vs decode |
|---|---|---|---|---|
| 1 | 106.2 | 137.1 | 137.0 | +29.0% |
| 8 | 651.5 | 703.1 | 703.0 | +7.9% |
| 16 | 1040.9 | 894.9 | 1033.7 | −0.7% |
| 32 | 1422.4 | 1000.5 | 1407.6 | −1.0% |
| 128 | 1699.7 | 1088.6 | 1674.9 | −1.5% |

At large batch, adaptive recovers almost all of what static 2-step loses. The remaining ~1% gap is the cost of the zero-step path compared with plain decode.

Under changing load (concurrency 4 → 64 → 8, 30 s per phase, no drain between phases), average throughput over the 90 s is 1415.7 / 886.3 / 1484.6 tok/s for decode / static 2-step / adaptive. That is +67.5% over static 2-step and +4.9% over decode. The last phase (concurrency 8) shows no clear gain over decode.

Accuracy on GSM8K, 300 questions, temperature 0: decode 293, static 2-step 291, adaptive 291. Static 2-step and adaptive agree on every question. At switch points, 22k checks of hidden state, bonus token and sequence length matched between graph and eager.

Upstream reports the wrong acceptance *rate* under adaptive until #44902 lands, so I only report accept length here. Tests: 44 unit tests covering state construction and switching, zero-step frontier and seed handling, graph-mode guards and scheduler fencing.

<details><summary>Benchmark setup</summary>

- Run order: decode → static 2-step → zero → adaptive → adaptive → zero → static 2-step → decode, with batch order reversed in the second half. Profiler and debug checks are off.
- Throughput is HTTP wall time and includes prefill.
- One adaptive run under changing load was discarded because the disk filled partway through; it was rerun from scratch.

</details>
