# [Perf] [NVIDIA] deepseek-v4.1: Zero the MegaAttention packed query once per forward, not per layer

[Upstream PR](https://github.com/sgl-project/sglang/pull/46062) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

On SM100/SM103 (B200/B300), DeepSeek-V4.1 Flash can run attention through FlashMLA MegaAttention
(`--dsv4-attn-backend flashmla_mega`, FP8 KV cache), whose kernels take the query packed as
`(tokens, 32, padded_heads, 16)` with the heads padded to 64. With attention TP > 1 each GPU holds fewer heads (16 of
64 at TP4), and `pack_query` rebuilt the packed tensor in each of the 40 attention layers: a zero-fill of the whole
padded tensor, three quarters of it padding at TP4, then a copy of the real heads. This PR keeps one zeroed buffer
per attention metadata and writes only the real heads into it, so the zero-fill runs once per forward (or once at
capture, for CUDA graphs that keep their metadata) instead of once per layer. The packed values are bitwise
identical and no kernel changes. An eager forward frees its buffer when it ends, and the decoder tail graphs (CUDA
graphs of the late layers that eager prefill chunks replay) keep packing into zeros of their own, as on main, so no
graph pins a forward's buffer. On current main, MegaAttention with attention TP > 1 is the default in PD prefill and
decode servers; aggregated servers with attention TP > 1 default to `flashmla` since #46263 and use this path with
`--dsv4-attn-backend flashmla_mega`.

**Impact**

- **Accuracy:** the packed query is bitwise equal to the old pack (B200 unit tests: eager, CUDA graphs, and graph
  replays after the freed memory is reused), and both MegaAttention kernel sets leave q unchanged. sgl-eval GSM8K
  (200 questions) on 4x B200 TP4: 97.0% and 97.5% with the PR's first revision, 97.5% on main.
- **Performance, microbenchmark:** per 40-layer forward with 16 heads padded to 64: decode of 8 tokens 137 -> 96 us
  on B200 and 125 -> 84 us on VR200; an 8K-token prefill chunk 11.5 -> 6.1 ms on B200.
- **Performance, end to end (the PR's first revision):** 4x B200 TP4 low-latency recipe on MegaAttention, 32K-token
  prompts at concurrency 1: TTFT 285.0 -> 275.5 ms (-3.3%); decode TPOT no regression.
- **End to end for this head (estimate, not measured):** the tail-graph change gives back about 0.11 ms of the
  9.4 ms saved per 32K-token prompt (two 16K-token chunks, 55.6 us each, measured below), so about -3.3% still.
- **Memory:** 4x B200 TP4, 32K-token prompts, rank 0: torch-allocated memory between forwards and after decode equals
  main (-1 MiB); the peak during a 16K-token chunk is +1,023 MiB (that chunk's buffer lives through the forward).
  PyTorch's reserved memory and nvidia-smi memory.used are +2.3 GiB per GPU, the same as the first revision. The KV
  pool is unchanged.

## Modifications

**+82 / −6 runtime code (3 files), +594 / −5 tests (2 files).** No kernel changes.

- `pack_query(q, padded_heads, out=None)` (`deepseek_v4_mega_backend.py`): given `out`, it writes only the real
  heads' slots. Without `out` it works as before.
- `MQALayer._forward_mega` (`deepseek_v4.py`) gets `out` from the new `MQALayer._zero_packed_q`. It follows the
  scheme of `_zero_padded_q`, which serves `q_pad_buffer` on the FlashMLA (non-mega) path and is unchanged: one
  zeroed buffer per attention metadata, grown only when a forward needs more rows, with an assert if the buffer
  would grow after a CUDA graph captured it.
- `DSV4Metadata` (`deepseek_v4_backend.py`) gets two fields, `q_mega_pad_buffer` and `q_mega_pad_captured`.
  MegaAttention needs a buffer of its own because its packed layout puts real heads where `q_pad_buffer` holds
  padding.
- **Graphs that keep their metadata share one buffer.** A breakable prefill CUDA graph keeps one metadata per
  captured shape for the server's lifetime, so one buffer per metadata would add up (58 shapes up to 8,192
  tokens). `DeepseekV4AttnBackend._share_q_mega_pad_buffer` starts each kept metadata from the buffer of the one
  kept before it. It covers prefill graph shapes and early verify graphs (`SGLANG_OPT_DSV41_TARGET_METADATA_EARLY`,
  off by default). Prefill shapes are captured largest first, so they all share one buffer. A shape that needs more
  rows gets a larger buffer, and the graphs captured before it keep theirs.
- **The late layers reuse the forward's buffer.** With decoder SWA bounded replay (on by default on CUDA), the late
  layers switch to a tail metadata that covers a subset of the rows. `enter_late_layer_tail` hands it the forward's
  buffer.
- **An eager forward frees its buffer when it ends.** An eager forward builds its metadata anew, and the backend
  keeps that metadata until the next forward. `DeepseekV4Model.forward` therefore drops the buffer from the forward
  and tail metadata when the forward ends (`DeepseekV4AttnBackend.release_q_mega_pad_buffer`). The buffer is still
  allocated and zeroed once per eager forward; only the time it is freed changes. A buffer that a CUDA graph
  captured stays, and a graph's warmup (capture mode) keeps its buffer for the capture that follows. The release
  runs only when `DeepseekV4Model.use_mega_attention` is set (the condition under which the backend is
  `DeepseekV4MegaAttnBackend`), and it asserts that backend type, so a wrapper backend fails instead of skipping it.
- **The decoder tail graphs pack into their own zeros.** These row-bucket graphs of the late layers
  (`deepseek_v4_replay_tail.py`) capture on first use, inside an eager prefill, and keep the tail metadata they
  captured with. Packing into that metadata's buffer would keep the forward's buffer (1 GiB per GPU for a 16K-token
  chunk at TP4) for the server's lifetime. While `in_replay_tail_graph()` is true, `_forward_mega` therefore packs
  into fresh zeros, as main does; the zero-fill stays inside those graphs, over the bucket's 128 to 2,048 rows. Its
  cost is measured below.
- `test_early_verify_metadata.py`: its stub backend gets the packed-query buffer chain. Without it the CPU test
  fails with `AttributeError: '_share_q_mega_pad_buffer'`.

**Why the padding stays zero.** The buffer is zeroed when it is allocated, and nothing writes its padding after
that:

- `pack_query` writes only `[:, :, :heads]`.
- The MegaAttention kernels only read q. sgl-flash-mla 1.0.0 has two kernel sets: the legacy one, and the one for
  the token-interleaved V4.1 cache added in #45893. Both load q into registers with `ld.global.nc` and never store
  to it (`core_attn/kernel.cuh`). The SM100 test now checks this on both kernel sets.
- Every layer of a model has the same head count, so the pad positions never move.

The same facts make sharing safe: graphs replay one at a time, and each layer writes every real head it reads.

**Buffer lifetime.**

- Eager forwards hold the buffer while they run and free it when they end.
- Decode and verify graphs that build their metadata inside the capture hold it for one forward. A graph of that
  kind zeroes it once per replay: one memset per step instead of one per layer.
- Prefill graphs (and early verify graphs) hold one shared buffer for the server's lifetime. It is allocated and
  zeroed in warmup, so the graphs contain no memset. Its size is tokens x padded heads x 1 KiB: 512 MiB at the
  8,192-token cap and TP4.
- The decoder tail graphs own their packed query in their graph memory pool, sized to the bucket, as on main. They
  never use or mark a forward's buffer, so the end of the forward frees it.
- `DSV4Metadata.copy_` and the breakable-graph refresh leave the buffer alone.

**Related:** `pack_query` comes from #43922, and the grow-only `q_pad_buffer` scheme reused here comes from #45301.

Tests, in `test/registered/kernels/ops/attention/dsv4/test_mega_attention.py`:

- A new class, `TestMegaPackedQueryBuffer`, runs on any CUDA GPU.
  - **The packed query equals the old fresh-zeros pack bitwise**, over 3 layers per token count. Heads: 8, 16, 32
    and 64 padded to 64, and 128 padded to 128. Token counts shrink and grow, from 1 to 64 for decode and from
    1,000 to 8,192 for extend.
  - **A CUDA graph with the buffer allocated before capture:** the address does not change, three replays with new
    inputs are bitwise equal, and growing the buffer after capture asserts.
  - **A CUDA graph with the metadata built inside the capture:** before each replay the buffer is filled with NaN,
    and every replay is still bitwise equal.
  - **Kept metadata share one buffer:** four prefill-graph shapes are captured the way the prefill graph runner
    does it: largest first, eager warmup first, early layers and then the late-layer tail through the backend's
    `enter_late_layer_tail`. The first three shapes and their tails share one buffer, and a larger fourth shape gets
    its own. The graphs then replay in mixed order with new inputs, bitwise equal every time.
  - **An eager forward leaves nothing allocated:** a forward through `DeepseekV4Model.forward` (early layers, then
    the tail) packs bitwise equal to the old pack, and `torch.cuda.memory_allocated` is back to its value before the
    forward. Without the release it is 64 MiB higher (the 1,024-token buffer).
  - **The end of a forward keeps a graph warmup's buffer and a captured one:** a warmup under capture mode keeps its
    buffer for the capture, and an idle eager forward that ends while the backend still holds the captured
    metadata does not free it. The captured graph then replays bitwise equal, with the warmup stream's freed memory
    filled with NaN.
  - **The end of a forward fails under a wrapper backend:** with a `TboAttnBackend` around the MegaAttention
    backend, `DeepseekV4Model.forward` asserts instead of skipping the release.
  - **A decoder tail graph leaves the forward's buffer to the forward:** inside an eager forward through
    `DeepseekV4Model.forward`, the late layers capture 256-, 192- and 128-row graphs through the real
    `RowBucketGraphRunner` (only its distributed pieces are stubbed). When the forward ends, exactly the forward's
    buffer is freed (1,024 x 64 x 512 x 2 B = 67,108,864 B), while the runner still holds its graphs and their
    metadata. After that memory is reused (filled with NaN), two replays with new inputs still pack bitwise equal to
    the old pack.
- `TestMegaAttention.test_mega_kernels_leave_q_unchanged` (SM100): `flash_mla_mega_decode` and
  `flash_mla_mega_prefill`, legacy and current kernel sets, 16 -> 64, 64 -> 64 and 128 -> 128 heads, and decode
  without an extra cache (`extra_kv=None`, the call the model makes on its compress_ratio 0 layers): q is bitwise
  the fresh-zeros pack after every call.
- `test_early_verify_metadata.py`: a later early verify graph holds the buffer the first one allocated.

Each new assertion was checked against a broken version of the code on B200, and each broken version fails exactly
the tests named here:

- Removing the release call, releasing nothing, or releasing only the forward's or only the tail's metadata: the
  eager-forward test and the tail-graph test fail (64 MiB still allocated).
- Releasing captured buffers, or releasing during capture mode: the warmup/captured test fails.
- Looking the release up with `getattr` and skipping a backend that lacks it: the wrapper-backend test fails.
- Storing the buffer under a misspelled field name: every buffer test except the wrapper-backend test fails.
  Setting a misspelled captured flag: the four tests that capture a graph over the buffer fail.
- The tail graphs packing into the forward's buffer again: the tail-graph test fails (0 of 67,108,864 B freed).
- That, plus releasing captured buffers, so the tail graph writes memory the forward freed: the tail-graph test
  fails on its replay check, and the warmup/captured test fails.
- Each of 6 kernel-write mutants (a kernel that stores to q) fails exactly its own 3 subtests of
  `test_mega_kernels_leave_q_unchanged`, and three wrong versions of `_share_q_mega_pad_buffer` fail the early
  verify sharing test.

## Accuracy Tests

The packed query is bitwise identical and the kernels do not change. To check the integration, B200 TP4 servers ran
the DeepSeek-V4.1 Flash cookbook low-latency recipe on main (535aeae2a7) and on this PR's first revision, when TP4
servers defaulted to MegaAttention: TP4, EP4 (the experts split over the same 4 GPUs), DSpark speculative decoding
(DeepSeek-V4.1's bundled draft model) and decode CUDA graphs.

DeepSeek-V4 leaves prefill CUDA graphs off by default, so a second pair of servers added the prefill graph flags of
the DeepSeek-V4.1 CI tests:

```
--cuda-graph-backend-prefill breakable --cuda-graph-max-bs-prefill 8192 --cuda-graph-max-seq-len-prefill 16384
--chunked-prefill-size 8192
```

All servers started and captured every graph without errors or the "grew after a CUDA graph" assert.

| sgl-eval gsm8k, B200 TP4 | main | this PR (first revision) |
|---|---|---|
| Cookbook low-latency recipe (prefill graphs off) | 97.5% | 97.0% |
| Same, plus breakable prefill graphs | 97.5% | 97.5% |

- Harness: sgl-eval 0.1.3 in its own virtualenv, with the DeepSeek-V4.1 CI settings (`dsv41_flash_common.py`):
  200 examples, 64 threads, `max_tokens` 4096, thinking off (no chat template kwargs), temperature 0.0, top_p 0.95.
- With prefill graphs on, 74 of 76 prefill batches on main and 71 of 72 with this PR replayed a graph.
- Outputs are not deterministic from run to run at 64 concurrent requests, because batch composition changes.
  Only 67 of the 200 generations matched between the two cookbook-recipe runs, and the 0.5-point gap is one
  question.
- A later run of the first revision (rebased on main 55f23a8b59) scored 98.0% with breakable prefill graphs plus

## Speed Tests and Profiling

**Where on the Pareto curve, and why a static workload.** The change removes a zero-fill per attention layer whose
size is rows x padded heads x 1 KiB, so its saving depends only on how many rows a forward has, not on the request
mix. It is largest in prefill chunks and matters most where a chunk's time is the latency: long prompts at low
concurrency (TTFT at the low-latency end). In decode it saves about 1 us per layer. A static workload measures that
directly; the end-to-end check below is the low-latency end of the 4x B200 TP4 recipe.

**Microbenchmark** on one GPU: the old `pack_query` against the new `MQALayer._forward_mega`, in one process, on the
same inputs.

- **Exact checks first.** They run before any timing, eagerly and on CUDA-graph replays, and all passed.
- **The forward.** Each forward packs 40 layers, the number of these memsets per decode step in a VR200 profile of
  DeepSeek-V4.1. There are 16 heads, padded to 64.
- **What is timed.** The forward is captured in one CUDA graph, with the metadata built inside it. Times are us per
  forward, the median of 5 interleaved rounds.

| Shape | B200 | B300 | VR200 (Rubin, SM107) |
|---|---|---|---|
| decode, 8 tokens | 137.4 -> 96.3 | 126.5 -> 90.1 | 124.6 -> 83.7 |
| verify, 48 tokens (8 requests x 6 speculative tokens) | 163.9 -> 108.5 | 151.5 -> 100.6 | 140.4 -> 90.2 |
| extend, 8K-token chunk | 11,459 -> 6,145 | 11,201 -> 5,897 | 8,699 -> 6,332 |

- B200 ran this PR's first revision (`e4db5a2527` on main 535aeae2a7); B300 and VR200 ran the same change on earlier
  main trees (b008ec3de6, 306ccf6f57). The release and tail-graph commits do not touch this path (next two tables).
- **Saved per layer:** 0.9-1.4 us at 8 and 48 tokens, and 59-133 us for an 8K-token chunk.
- **Sizes:** the 8-token decode pack is 8 x 64 x 512 x 2 B = 0.5 MiB per layer and the 48-token verify pack 3 MiB,
  so both stay in L2 when the 40 packs replay back to back; in serving, the MoE and GEMM kernels between layers
  evict them. The 8K extend pack (512 MiB per layer) is far larger than L2.

**Freeing the buffer when the forward ends costs nothing measurable.** A second B200 run sends every forward through
`DeepseekV4Model.forward`, where the release happens. It compares main's per-layer pack, this PR without the release,
and this PR with it (same process, median of 5 interleaved rounds; the graph forwards here are warmed before
capture, so they contain no memset):

| B200, us per 40-layer forward | main's pack | without the release | with the release |
|---|---|---|---|
| decode, 8 tokens, CUDA graph | 145.4 | 98.3 | 98.3 |
| decode, 8 tokens, eager | 541.5 | 462.6 | 464.2 |
| extend, 8K-token chunk, CUDA graph | 11,350 | 5,904 | 5,904 |
| extend, 8K-token chunk, eager | 11,554 | 6,126 | 6,125 |
| memory held between eager forwards (8K chunk) | 0 | 512 MiB | 0 |
| peak memory during a forward (8K chunk) | 512 MiB | 512 MiB | 512 MiB |

The tail-graph commit adds nothing outside the tail graphs: the same benchmark on the commit before it and on this
head, on one B200 in the order before, head, head, before, gives head / before = 1.000 for decode and extend in CUDA
graphs and for eager extend. Eager decode is CPU-bound and varied by up to 8% between runs of the same code
(before: 485.6 and 522.5 us; head: 474.5 and 475.5 us).

**What the tail-graph commit costs.** The decoder tail graphs zero-fill per layer again, as on main. One B200, the
model's 20 tail layers of packs captured in one CUDA graph, us per tail, median of 5 interleaved rounds of 200
replays (exact check first):

| Tail rows (bucket) | fresh zeros (this PR, main) | shared buffer (first revision) | cost per tail | per layer |
|---|---|---|---|---|
| 128 | 139.4 | 83.9 | 55.6 | 2.8 |
| 512 | 415.0 | 224.8 | 190.2 | 9.5 |
| 2,048 | 1,491.8 | 760.0 | 731.9 | 36.6 |

- A one-request 16K-token chunk has a 128-row tail, so the commit gives back about 0.06 ms of the ~4.8 ms the PR
  saves per such chunk end to end (below). A full 2,048-row bucket (16 or more requests in a chunk) gives back about
  0.73 ms. Against main it costs nothing: main zero-fills every layer, early and late. These per-chunk figures are
  estimates from the microbenchmark, not end-to-end measurements.

**End to end (the PR's first revision).** 4x B200, the cookbook low-latency recipe (TP4, EP4, DSpark, decode CUDA
graphs, chunked prefill 16,384), on main 55f23a8b59, when TP4 servers defaulted to MegaAttention (on current main,
add `--dsv4-attn-backend flashmla_mega`). Main and the PR on one node in the order main, PR, PR, main:

```

  --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64

python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-input-len 32768 \
  --random-output-len 1 --random-range-ratio 1.0 --tokenize-prompt --num-prompts 16 --max-concurrency 1 --seed 1
# TPOT
python3 -m sglang.benchmark.serving --backend sglang --dataset-name sharegpt --num-prompts 256 \
  --sharegpt-output-len 512 --max-concurrency 8 --seed 1
```

| | PR / main, pair 1 | PR / main, pair 2 | second main / first main |
|---|---|---|---|
| TTFT, 32K-token prompts (median of 16, concurrency 1) | 0.967 | 0.967 | 1.001 |
| TPOT, ShareGPT 256 requests at concurrency 8 | 0.955 | 0.980 | 0.950 |

- TTFT is 284.8 / 285.1 ms on main and 275.3 / 275.7 ms with the PR: 9.4-9.5 ms per 32K prompt, about 4.8 ms per
  16K-token chunk. That is about half of what the 1-GPU benchmark predicts (5.3 ms saved per 8K chunk).
- Decode: no regression. The first main arm was the slow outlier (1,106 tok/s against 1,820-1,829 in the other
  three), so the decode gain is not resolved.
- Zero-fill kernels per decode step in a profile: 45 on main, 6 with the PR.
- **This head (estimate, not measured):** the release costs nothing measurable (table above), and the tail graphs
  give back 2 x 55.6 us per 32K prompt (two one-request 16K-token chunks), so about 9.3 of the 9.4 ms remain: still
  about -3.3% TTFT on this recipe.
- The memory run below is not used for speed: it timed only 6 prompts per server, and its main commit (01759f0a68)
  logs a DSpark draft-metadata glue-graph fallback that later main commits fix (#46891, #46897, #46777).

### Memory

In this recipe every 16K-token prefill chunk runs eagerly, and its packed query is 16,384 x 64 x 512 x 2 B = 1 GiB
per GPU. Main allocated it per layer and freed it after the layer.

4x B200 TP4, the recipe above plus `--dsv4-attn-backend flashmla_mega` (main 01759f0a68 defaults TP4 aggregated
servers to `flashmla`), one node, a fresh server per run, in the order main, this PR, first revision, first
revision, this PR, main. A hook in every scheduler records `torch.cuda` memory once a second and resets the peaks at
each phase. Phases: 6 x 32K-token prompts at concurrency 1 (`--num-prompts 6`, as above), a few seconds idle,
ShareGPT 64 x 512 at concurrency 8, idle. Rank 0, MiB:

| | main | first revision | this PR | this PR - main |
|---|---|---|---|---|
| torch allocated after start-up | 145,518 | 145,517 | 145,517 | -1 |
| peak allocated during the 32K prefills | 150,498 | 152,545 | 151,521 | +1,023 |
| allocated a few seconds after the prefills | 147,042 | 149,089 | 147,041 | -1 |
| peak allocated during the decode phase | 147,824 | 149,089 | 147,970 | +145 |
| allocated after the decode phase | 146,848 | 147,885 | 146,847 | -1 |
| reserved after the prefills | 156,724 | 159,038 | 159,066 | +2,342 |
| nvidia-smi memory.used, peak during the prefills | 161,311 | 163,617 | 163,645 | +2,334 |

- Each value repeats within 2 MiB between the two servers of its tree. Ranks 1-3 are within 6 MiB of rank 0
  (allocated) and 30 MiB (reserved). Every server served 6/6 and 64/64 requests and resolved `flashmla_mega`; the
  KV pool is 1,481,216 tokens in all six.
- **Between forwards and after decode, this PR holds what main holds.** The first revision held +2,048 MiB between
  forwards and +1,037 MiB after decode (two and one 1 GiB chunk buffers); the release and tail-graph commits remove
  both.
- **Peak +1,023 MiB:** one chunk-sized buffer lives through the forward, where main's per-layer copy lived only
  through attention. The decode phase's peak is +145 MiB; that phase also prefills its ShareGPT prompts eagerly.
- **Reserved and nvidia-smi memory.used stay +2.3 GiB**, the same as the first revision (+28 MiB apart). The extra
  is cached by PyTorch's allocator and free for later PyTorch allocations; it does not come out of the KV pool,
  which is sized at start-up. We have not attributed it to specific allocations.
- With breakable prefill graphs (first revision), the prefill graph capture took 7.33 GiB on main and 7.43 GiB with
  the PR (14.36 GiB with an earlier version that gave each kept metadata its own buffer).

**Issue**

`_zero_padded_q` now takes field names as strings and uses `getattr(meta, buffer_attr, None)`, `getattr(meta, captured_attr, False)`, and `setattr(meta, ...)` inside `try/except (AttributeError, TypeError)`. The repo does not allow defensive `getattr` (`.claude/rules/no-getattr-defensive.md`), and string field names hide mistakes from type checks.

**Example**

`DSV4Metadata` is a plain `@dataclass`. If `buffer_attr` were misspelled, `setattr` would add a new attribute and caching would still work. But `release_q_mega_pad_buffer`, `_share_q_mega_pad_buffer`, and `enter_late_layer_tail` read the real field, so they would silently do nothing.

**Fix**

In `_forward_mega`, narrow with `isinstance(meta, DSV4Metadata)` and access `q_mega_pad_buffer` and `q_mega_pad_captured` directly. For example, pass `_zero_padded_q` a small typed holder (buffer plus captured flag) instead of two strings.

[by Claude Code] **Severity: style | Confidence: High**

**Issue**

`getattr(get_attn_backend(), "release_q_mega_pad_buffer", None)` is a defensive `getattr`, which `.claude/rules/no-getattr-defensive.md` does not allow. It runs on every CUDA DeepSeek-V4 forward, even with MegaAttention off, and it skips the release without an error when the backend is the wrong object.

**Example**

With `--enable-two-batch-overlap` on DeepSeek-V4, `get_attn_backend()` returns a `TboAttnBackend`, which has no `release_q_mega_pad_buffer`, so the release is skipped silently. This is harmless today only because MegaAttention is V4.1-only and V4.1 rejects TBO.

**Fix**

Set a flag in `__init__` (for example `self.use_mega_attention`) and call the method directly:

```python
if self.use_mega_attention and not get_is_capture_mode():
    backend = get_attn_backend()
    assert isinstance(backend, DeepseekV4AttnBackend)
    backend.release_q_mega_pad_buffer()
```

`DeepseekV4AttnBackend` is imported only under `TYPE_CHECKING` here, so it needs a runtime import.
