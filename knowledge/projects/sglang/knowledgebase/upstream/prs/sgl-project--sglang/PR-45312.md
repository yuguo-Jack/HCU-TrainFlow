# [Fix] multimodal: Keep the processor's single text unpadded so the shared tokenizer is not reconfigured

[Upstream PR](https://github.com/sgl-project/sglang/pull/45312) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45310. Upstream lock-order bug: crusoecloud/fastokens#84.

With `--tokenizer-backend fastokens` and fastokens 0.3.3 or later, the HTTP/tokenizer process can deadlock. It happens when an image, audio or video request arrives while a text request is being tokenized. Once it happens, `/health` stops answering and the process never recovers.

Two pieces of SGLang meet in the same tokenizer object:

- `serving_base.py:93-97` (#39771) encodes text requests on default-executor threads.
- `base_processor.py:916-921` calls the HF processor with `padding=True` on the event-loop thread. The processor's tokenizer is the TokenizerManager's tokenizer (`get_tokenizer_from_processor`).

Padding a batch of one text adds no tokens. It still makes transformers reconfigure the backend:

- `enable_padding` for the processor call;
- `no_padding` on the next plain encode.

In fastokens ≥0.3.3, `encode_batch` holds its state read lock across `allow_threads`, so it takes the GIL back while still holding that lock. `enable_padding` and `no_padding` take the write lock with the GIL held. The two threads then wait on each other forever. The issue has the stacks, line references and a CPU repro.

This PR removes the write from SGLang's side, so a multimodal request no longer reconfigures the shared tokenizer. The underlying lock-order bug is reported to fastokens in crusoecloud/fastokens#84.

## Modifications

`python/sglang/srt/multimodal/processors/base_processor.py`:

- `process_mm_data` no longer passes `padding=True`. It builds its padding kwargs with a new helper, `_single_text_padding_kwargs()`:

| request | processor | before | after |
|---|---|---|---|
| no audio | any | flat `padding=True` | flat `padding=False` |
| with audio | shipped with transformers | flat `padding=True`, which reaches both the tokenizer and the audio feature extractor | `text_kwargs={"padding": False}` and `audio_kwargs={"padding": True, ...}` |
| with audio | remote code or SGLang's own | flat `padding=True` | unchanged |

Notes on the table:

- **Why an explicit `False`.** Leaving the kwarg out is not enough: Gemma 4's processor pads text by default (`"padding": True` in its `_defaults`).
- **Why the audio case is split per modality.** In `ProcessorMixin._merge_kwargs`, a flat `padding` reaches every modality that accepts it. So the old flat `True` also set the audio feature extractor's padding. For example, it overrode GLM-ASR's `"max_length"` audio default, which GLM-ASR passes on to `WhisperFeatureExtractor`.
- **Why not send `False` flat plus `True` for audio.** transformers raises `ValueError` ("passed two times") when the same key is given flat and in `audio_kwargs`. So for those processors, the text value and the audio value go in their modality dicts.
- **Why other processors keep `padding=True` when there is audio.** We cannot tell where they route a flat `padding`. For example, SGLang's `Qwen3ASRProcessor` reads text options from flat kwargs and passes `audio_kwargs` straight to `WhisperFeatureExtractor`. Adding `padding` there would change its features from 3000 frames to the clip length.
- **How the split is decided.** `_splits_kwargs_by_modality()` treats a processor as splitting kwargs if it is a `ProcessorMixin` defined in a `transformers.*` module.

`test/registered/unit/multimodal/test_base_processor_tokenizer_padding.py` (new, `base-a-test-cpu`). CPU only, with no network and no weights. It builds real transformers processors on an in-memory word-level tokenizer:

- `TestImageRequest` / `TestAudioRequest` (with a real `Gemma4Processor`):
  - after `process_mm_data`, the shared tokenizer's `backend_tokenizer.padding` is still `None`;
  - `input_ids` match the old `padding=True` call exactly;
  - for a two-clip audio request, `input_features` match too.
- `TestAudioKwargsRouting`:
  - for `GlmAsrProcessor`, `_merge_kwargs` yields the same `audio_kwargs` and `text_kwargs` as the old flat `padding=True`, except for text `padding`;
  - SGLang's `Qwen3ASRProcessor` still gets 3000-frame features.

**Not covered by this PR.** These cases still reconfigure the tokenizer on a multimodal request. They stay exposed until fastokens is fixed:

- `ernie45_vl.py` and `midashenglm.py`, which call their own processors with `padding=True`. Both use remote-code processors that we could not test.
- Calls that pass no `padding` to a processor whose defaults pad text, for example `transformers_auto.py:123`.
- Audio requests to processors outside transformers.

### Why this fix and not the alternatives

- **Cap fastokens below 0.3.3 in `pyproject.toml`.** This would remove the mechanism for installs that use the extra. But:
  - 0.3.2 encoded Gemma 4 prompts 2.4x to 3x slower (7k–14k tokens);
  - 0.3.2 holds the GIL while it encodes, so an encode on an executor thread would block the event loop again, which is what #39771 set out to avoid;
  - it drops the 0.3.3 and 0.3.4 changes, including the fixes in crusoecloud/fastokens#78;
  - it does nothing for users who install fastokens themselves.

  The lock-order fix belongs in fastokens. Once that fix is released, no SGLang dependency change is needed. If maintainers want a stopgap in the meantime, `fastokens>=0.3.2,!=0.3.3,!=0.3.4` is a one-line follow-up.
- **Serialize tokenizer use with a lock, or keep all tokenization on one thread.**
  - A Python lock around every tokenizer call is correct. But it is unfair: in our repro, the thread that toggles padding got only 44 toggles through in 10 s against a tight encode loop. In SGLang that thread is the event loop.
  - Moving encodes back onto the loop would revert #39771. Open PRs such as #44502, #39716 and #41031 move more tokenization off the loop, not less.
- **This change.**
  - It costs nothing at runtime and does not change the ids.
  - It removes the writer from the path most multimodal models use.
  - It can be unit tested on CPU.

## Accuracy Tests

No change to model inputs is expected. Padding a batch of one text adds no tokens. The new unit tests check this with Gemma 4's processor:

- image request: identical `input_ids`;
- two-clip audio request: identical `input_ids` and `input_features`.

We did not run a model eval such as MMMU.

## Speed Tests and Profiling

None expected. The change removes two backend reconfigurations per multimodal request (`enable_padding`, then `no_padding`). We did not benchmark it.
