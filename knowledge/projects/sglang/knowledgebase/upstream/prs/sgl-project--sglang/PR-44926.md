# [Fix] gemma: Reject input_embeds requests for Gemma 3n and Gemma 4

[Upstream PR](https://github.com/sgl-project/sglang/pull/44926) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44895. For an `input_embeds` request, the scheduler fills in placeholder `input_ids` (`[1] * len(input_embeds)`) and the model runner passes both to the model. Gemma 3n and Gemma 4 check that exactly one of `input_ids` and `inputs_embeds` is given, so the check raises inside the scheduler and the server goes down. Their per-layer embeddings (always on in Gemma 3n, optional in Gemma 4) also need the real token ids, so these models can't run from embeddings alone.

## Modifications

- `models/gemma3n_causal.py`, `gemma3n_mm.py`, `gemma4_causal.py`, `gemma4_mm.py`: add `supports_input_embeds = False` to `Gemma3nForCausalLM`, `Gemma3nForConditionalGeneration`, `Gemma4ForCausalLM` and `Gemma4ForConditionalGeneration` (`Gemma4UnifiedForConditionalGeneration` inherits it). Same pattern as `supports_cuda_vmm_feature_transport`; other models default to supported.
- `model_loader/utils.py`: `supports_input_embeds(model_config)`, next to `supports_cuda_vmm_feature_transport`.
- `managers/tokenizer_manager.py`: `_tokenize_one_request` rejects an `input_embeds` request for such a model with a `ValueError`, which the HTTP server returns as a 400 (`input_embeds is not supported by this model's architecture (Gemma4ForConditionalGeneration). Send text or input_ids instead.`). The model class is resolved on the first `input_embeds` request and cached, so servers that never get one don't import it in the tokenizer process (the same lookup `_validate_cuda_vmm_feature_transport_support` already does there). Every `input_embeds` request (HTTP, `Engine`, gRPC, batch, multi-tokenizer workers) goes through `_tokenize_one_request`; the Rust server doesn't accept `input_embeds`.

### Open question: other multimodal models

As described in the issue, the other models that go through `general_mm_embed_routine` don't crash, but they don't use `input_embeds` either: `prepare_mm_inputs` computes embeddings from the placeholder ids and copies them over `forward_batch.input_embeds`, so the model generates from token id 1 repeated. This PR only covers the crash. If you'd like those models rejected too, I can add the flag to them here or in a follow-up; supporting embeddings properly in the multimodal path would be a separate change.

## Validation

- New `test/registered/unit/managers/test_input_embeds_support.py` (CPU): 5 passed, 14 subtests. Covers the flag for all five Gemma 3n/4 architectures, Llama and Gemma 3 still supported, the request rejected in `_tokenize_one_request`, and the architecture resolved only once.
- Same request on main vs. this branch (CPU, tokenizer manager only): on main the Gemma 4 `input_embeds` request passes validation and goes on to the scheduler; with this PR it is rejected with the message above.
- `test_tokenizer_manager_rid_cleanup.py` and `test_io_struct.py`: 110 passed, same as main.
- `pre-commit run` on the changed files passes.

I did not run a Gemma 4 server on a GPU; the crash path itself is the one @riversky0014 reproduced in the issue.
