# [Perf] deepseek-v4: Avoid unused Torch hc_pre wrapper in capture mode

[Upstream PR](https://github.com/sgl-project/sglang/pull/47819) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek V4 `hc_pre` defines and decorates the Torch fallback helper before checking the NPU, empty-input, XPU, FlashInfer, TileLang, HIP, and DeepGEMM paths. `@compile_in_capture_mode` performs its work when the local function is defined, not when it is called. In capture mode it evaluates `torch.compile(hc_pre_torch_impl)` and returns the compiled wrapper.

Optimized paths such as TileLang and DeepGEMM return without invoking that wrapper, so the construction is pure host work that is discarded. DSV4-Flash-0731 selects the TileLang branch by default. `hc_pre` is called twice per DSV4 layer per forward (attention and FFN), or 86 times per forward for 43 layers, so this discarded work repeats throughout graph capture.

## Modifications

- Move the local `hc_pre_torch_impl` definition below the DeepGEMM dispatch and into the fallback `else` branch where it is actually called.
- Keep the same helper body, decorator, inputs, and output calculation.
- Keep capture-mode compilation behavior for the Torch fallback.
- Do not change tensor math, layout, norm, routing, Sinkhorn, or kernel parameters.
- Add CPU tests with fake mHC ops to verify that unused branches do not construct or compile the helper, while the fallback still compiles in capture mode.

## Speed Tests and Profiling

Benchmark in capture mode with a TileLang-path stub. It models the DSV4-Flash-0731 topology: 43 layers with two `hc_pre` calls per layer, or 86 calls per forward.

```text
scenario: capture mode + TileLang mHC-pre, tokens=64, hc_pre_calls_per_forward=86
implementation,ms_per_forward,us_per_call
baseline,41.855,486.681
patched,0.931,10.828
```

The patch removes `40.924 ms` of host work per capture-mode forward, a 97.8% reduction for this path. On a Full256 decode grid with 36 captured shapes and the current three forwards per shape, the saving is about `4.42 s` (`108 * 40.924 ms`).

The stub removes actual TileLang kernel execution from the comparison. Both implementations call the same stub, so the delta isolates the unused `torch.compile` wrapper construction; real kernel time would be common to both. This is not an end-to-end model throughput result, and full real-model capture/startup validation is still pending.
