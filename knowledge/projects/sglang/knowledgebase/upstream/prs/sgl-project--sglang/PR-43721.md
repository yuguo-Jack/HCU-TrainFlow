# [MemCache] Split the SWA mapping move out of locked-full recovery as `RecoverEvictedSWA`

[Upstream PR](https://github.com/sgl-project/sglang/pull/43721) · state: closed · merged: True

## Original PR description

## Motivation

`RecoverSWAWithLockedFull` bundles three steps in one `SWAComponent` handler: move the incoming request's SWA mapping onto the node's kept Full ids, free the incoming Full ids, and publish the recovered value on the node. Only the first step is the same for every SWA component. Whether the handler may free the incoming Full ids or write the node depends on who owns them at that point in the tree walk, so a tree core that frees duplicate Full ids and publishes nodes itself cannot reuse the recovery as it stands, and a component with its own mapping layout has to re-implement the whole handler to change the mapping step.

## Modifications

- `python/sglang/srt/mem_cache/unified_cache/components/swa.py`: the mapping move becomes `SWAComponent._set_swa(kept_full, incoming_full)`, which returns the recovered SWA value and keeps both existing recipes: the page-ownership rebind through `_transfer_swa_pages` on the unified pool, and the `full_to_swa` clear-then-set writes on a static allocator. `RecoverSWAWithLockedFull` calls it and then, as before, frees only the incoming Full side (through the composite on the unified pool, through `free_full_segment` otherwise) and stores the value on the node. The new `RecoverEvictedSWA` branch runs `_set_swa` alone.
- `python/sglang/srt/mem_cache/unified_cache/cache_action.py`: `RecoverEvictedSWA(component_type, kept_full, incoming_full)`, the mapping-only component action. Its `component_type` has no default, since it is addressed to whichever SWA-style component owns the mapping; Full cleanup and tree publication stay with the caller.
- `test/registered/unit/mem_cache/test_swa_locked_full_recover_unified.py`: two cases for the new action, on the unified composite and on the static recorder, checking that the node's ids adopt the incoming SWA pages while no Full id is freed and no device value is published. They guard against folding either step back into the shared helper, which would double-free under a caller that still owns them. The existing locked-full cases are unchanged and still pass.

## Accuracy Tests

Not applicable: no model or kernel path changes. Locked-full recovery performs the same allocator calls as before in both the unified and the static branch; the existing handler tests in `test_swa_locked_full_recover_unified.py` and `test_unified_radix_cache_unittest.py` cover both.

## Speed Tests and Profiling

Not applicable: the handler issues the same allocator operations in the same order relative to the free; only the publication now happens through a shared code path.
