# [Fix] openai: Accept replayed assistant reasoning

[Upstream PR](https://github.com/sgl-project/sglang/pull/44109) · state: closed · merged: False

## Original PR description

## Motivation

SGLang declares only `reasoning_content`, so assistant reasoning replayed as `reasoning` is silently dropped and the next prompt loses it. Clients using that name, which vLLM reads, hit this (listed in RFC #47763), but I have no captured request. A client echoing SGLang's reply sends `reasoning_content` and is unaffected. In a Qwen3-0.6B tool loop (one B200, cookbook parsers, main `ba1ed00dfe`), main builds a 199-token prompt from that replay, identical to no reasoning, and this PR builds 307, identical to `reasoning_content`, with matching next output.

#47271 (Mistral-Large-4, not run here) adds the same Python validator for assistant messages, but no router or Rust change, so the `Router from main` column would still apply. If both merge, one validator can go. #44942 targets the `thinking` key and #47175 changes responses only.

## Modifications

A string `reasoning` fills a missing or null `reasoning_content`. Explicit `reasoning_content` wins, and a non-string `reasoning` stays ignored.

- Python and `rust/sglang-processor` apply this rule, so DeepSeek-V4, V4.1, GLM-5.3, Kimi-K3 and Qwen3.8 render the same prompt everywhere. MiniMax-M3 and M3.1, newer than this head, share that code and should too.
- For other models, the sgl-router guard sends the request to the engine.

Limits:

- For those models, routing tokens omit the alias, which can change the chosen worker and router token count, but not the prompt.
- The Rust server's typed parse covers those models and requests the lowered `/generate` route declines, such as `tool_choice: required`. On Qwen3-0.6B it gives 35 for `reasoning` alone, but returns 400 for both fields, `reasoning` with a null `reasoning_content`, or an object `reasoning`. No captured client request reaches this, and #47175 adds it only for a Python reply replayed to a Rust server.
