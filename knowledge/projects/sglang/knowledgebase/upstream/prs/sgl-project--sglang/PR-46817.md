# [Fix] [NVIDIA] flashinfer_mla: Fall back to FA2 ragged prefill for head dims CUTLASS lacks

[Upstream PR](https://github.com/sgl-project/sglang/pull/46817) · state: open · merged: False

## Original PR description

## Motivation

On SM100/SM103 (B200, B300), `FlashInferMLAAttnBackend` always builds its ragged (MHA) prefill wrapper with `backend="cutlass"`. FlashInfer's SM100 CUTLASS FMHA only has kernels for head dims (64, 64), (128, 128) and (192, 128). Any MLA model with other dims crashes on its first prefill.

GLM-4.7-Flash is one example: `qk_nope_head_dim + qk_rope_head_dim = 192 + 64 = 256` and `v_head_dim = 256`. With `--attention-backend flashinfer` on a B300, the server dies during warmup:

```
File ".../flashinfer/data/csrc/fmha_cutlass_sm100.cu", line 113, in FMHACutlassSM100Run
RuntimeError: Check failed: (dispatched) is false: Unsupported head dimensions: head_dim_qk=256, head_dim_vo=256
```

The MHA FlashInfer backend (`flashinfer_backend.py`) already guards against this with a supported-dims check and an FA2 fallback. The MLA backend never got the same check.

I did not find an existing issue for this.

## Modifications

- `flashinfer_backend.py`: move the CUTLASS head-dim set into a module constant, `SM100_CUTLASS_FMHA_HEAD_DIMS`. The MHA backend's behavior is unchanged.
- `flashinfer_mla_backend.py`: on SM100, use `cutlass` only when `(qk_nope + qk_rope, v_head_dim)` is in that set. Otherwise use `fa2`. Non-SM100 GPUs still use `auto`. The same `fmha_backend` also feeds the MHA chunked-prefix wrappers, so those paths are fixed too.
- DeepSeek-style models (192, 128) still use CUTLASS, as before.
- `mla/test_flashinfer.py`: new test `test_ragged_prefill_head_dims_without_cutlass_kernel`. It builds the backend for (256, 256) head dims, runs its ragged prefill wrapper, and compares the result to `F.scaled_dot_product_attention`. It fails on main on SM100 with the error above and passes with this change.

## Accuracy Tests

Hardware: 1x NVIDIA B300 SXM6 (SM 10.3), driver 580.159.03, CUDA 13.0, torch 2.14.1+cu130, flashinfer-python 0.7.2. SGLang base: `c43abd6d9e`.

Server command:

```bash
python -m sglang.launch_server --model-path zai-org/GLM-4.7-Flash --tp 1 \
  --attention-backend flashinfer --mem-fraction-static 0.5 \
  --disable-prefill-cuda-graph --disable-radix-cache
```

Eval command (sgl-eval 0.1.3):

### Known remaining limitation (not fixed here)

With the radix cache on, GLM-4.7-Flash on the FlashInfer backend still fails on requests that hit a short cached prefix. Those requests go through the absorbed MLA paged prefill. FlashInfer 0.7.2 refuses that plan when `num_heads` (20 here) does not divide the query tile:

```
fa2 MLA causal tile boundary is unsupported: request 0, num_heads=20, query=38, key=64, native KV tile=64
```

This check lives in FlashInfer (`_validate_fa_causal_tile_bound` in `mla/_batch_mla/_backends/_fa_common.py`), and it also covers the fa3 path. It is separate from the startup crash fixed here, which happens before any request is served. I think it needs a FlashInfer fix or a separate routing change in SGLang, so I left it out of this PR.

## Speed Tests and Profiling

No kernel changes. DeepSeek-style models (192, 128) keep the CUTLASS path. Models that used to crash now run on FA2, so there is no before number to compare against.
