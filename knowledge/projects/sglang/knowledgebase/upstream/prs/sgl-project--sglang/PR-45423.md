# [Feat] disaggregation: Let PD decode servers prefill requests marked disagg_local_prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/45423) · state: open · merged: False

## Original PR description

## Motivation

Phase 1 of #45416 (PPD: prefill on the decode worker). In multi-turn and agentic traffic, the decode worker that served turn N already holds turn N's prompt and output in its radix cache, so turn N+1 needs only a short prefill. Today that short prefill still goes through a prefill worker, a bootstrap handshake and a KV transfer. This PR lets the router mark such a request with `disagg_local_prefill: true` and send it to the decode worker alone, which prefills it with chunked prefill and decodes it in the same running batch as PD requests. Router support (`experimental/sgl-router`) is phase 2.

## Modifications

- **Flag and request field.** New `--disaggregation-decode-enable-local-prefill`, and a request field `disagg_local_prefill` on `/generate` and the OpenAI and Anthropic endpoints, appended as a defaulted tail field of `TokenizedGenerateReqInput`. A server without the flag rejects marked requests with 400. A marked request needs no bootstrap fields.
- **Queues.** With the flag on, `waiting_queue` holds only requests this decode server prefills, so the aggregated prefill path keeps its meaning. Transferred requests wait in the new `Scheduler.disagg_decode_prebuilt_queue`. With the flag off, the attribute stays `None` and transferred requests stay in `waiting_queue`, so existing PD behavior does not change.
- **Scheduling.** `get_next_disagg_decode_batch_to_run` merges transferred requests as before, then calls the aggregated `get_next_batch_to_run`, which merges the last prefill batch and runs the next chunk or a decode step. Prebuilt admission counts local requests that join the running batch later in the same step, so the running batch stays within `--max-running-requests`.
- **Memory.** Decode preallocation reserves the remaining chunks of the in-flight local prefill. Local admission uses the aggregated `PrefillAdder` budget.
- **Retraction, pause and abort.** A locally prefilled request has no prefill peer. When it is retracted, the server skips the host backup and prefills it again locally. `pause_generation(retract)` re-queues it locally instead of rebootstrapping it. Abort, idle checks, waiting timeouts, weight-version stamping and load reports cover both queues. A queued local request owns no KV, so abort does not release any.
- **Server args.** A decode server with local prefill counts as one that runs prefill forwards (`runs_prefill_of`). It keeps prefill CUDA graphs, reserves their memory, sizes the activation reserve and the SWA request cap for a prefill chunk, and passes the post-capture sizing check. Without prefill CUDA graphs, a 332-token local prefill of Qwen3-30B-A3B took 55 ms TTFT instead of 18 ms.
- **Validation.** The late hook `validate_decode_local_prefill` rejects pipeline parallelism, DP attention, MoE all-to-all backends, HiSparse, decode host KV buffering and disabled chunked prefill for now.
- Local requests are timed as aggregated requests and return input logprobs.
- Docs: a "Decode local prefill" section in `pd_disaggregation.mdx` and a row in `server_arguments.mdx`.

## Accuracy and performance

All runs below used one 4x GB300 node and the Mooncake TCP transport. Unless noted, prefill (GPU 0) and decode (GPU 1) served Qwen3-30B-A3B at TP1. Decode ran with `--disaggregation-decode-enable-radix-cache --disaggregation-decode-enable-local-prefill --chunked-prefill-size 512`. Requests were greedy, and correctness was measured as KL(ref ‖ got) over the top-20 output logprobs, averaged per request over 128 tokens.

**Correctness, Qwen3-30B-A3B, 8 conversations.** Turn 1: a 4000-token prompt and 128 output tokens through PD. Turn 2: turn 1 plus a 300-token suffix. Two identical turn-1 caches were kept in separate `cache_salt` namespaces, so the local arm and the PD arm hit the same decode-side prefix (4096 tokens) and differ only in where the suffix is prefilled.

| comparison | mean KL |
|---|---:|
| local prefill vs PD with the same decode hit | 0.0121 |
| PD with decode hit vs cold PD (existing cache-hit noise) | 0.0086 |
| local prefill vs cold PD | 0.0161 |
| cold PD vs cold PD | 0.0 |

The local path adds no error beyond the numerical difference that a decode radix hit already has on main.

**TTFT, Qwen3-30B-A3B.** A 4128-token history, cached on both prefill and decode, plus a 300-token suffix, generating 16 tokens. Each arm ran 16 requests, alternating.

| path | median TTFT | mean TTFT |
|---|---:|---:|
| PD | 39.5 ms | 39.4 ms |
| decode local prefill | 17.8 ms | 19.1 ms |

Both arms ran on one node, where KV crosses Mooncake TCP on loopback; across nodes the PD arm also pays the network.

**Robustness, Qwen3-30B-A3B.**

| scenario | result |
|---|---|
| 256 requests at concurrency 32, half local and half PD, suffixes of 64–3000 tokens (up to 6 chunks) | 256/256 OK |
| `--max-total-tokens 30000`, all local | 256/256 OK |
| `SGLANG_TEST_RETRACT=1`, all local (273 effective retractions) | 256/256 OK |
| 8 local streams closed mid-prefill or after the first token | decode healthy |

After every run, the decode server passed its idle memory check, with no leak and no traceback.

**DeepSeek-V4.1-Flash.** Recipe: the cookbook's GB300 low-latency flags (DSPARK block 5, `--cuda-graph-max-bs-decode 64`, mem 0.8), with these differences: prefill TP2/EP2 on GPUs 0–1, decode TP2/EP2 on GPUs 2–3, page 256, `--max-running-requests 8`, local prefill chunk 1024. Decode radix cache for DeepSeek-V4 is CUDA-gated on main, so local requests prefilled the whole prompt (no decode hit). This run checks the DSPARK, SWA-cap and `max_running_requests` paths.

- Correctness, 16 requests of 2000 + 128 + 300 tokens: KL(cold PD ‖ local) has median 0.026 and mean 0.111. Two cold PD runs give median 0.021 and mean 0.090, because DeepSeek-V4 is not deterministic.
- Mixed stress (256 requests, half local) passed 256/256, and the abort test passed. The running batch peaked at 8. Before the admission fix it reached 10 and crashed the DSPARK draft forward.

**Unit tests.**
- New file `test/registered/unit/disaggregation/test_decode_local_prefill.py` has 15 tests. Each production hunk it covers was reverted once, and the matching test failed every time (10 hunks).
- New pool-sizing test in `test_pool_configurator.py`.
- I ran `unit/managers`, `unit/disaggregation`, `unit/server_args`, `unit/observability`, `test_pool_configurator.py` and the decode cache tests on main and on this PR. This PR adds no failures. Existing mocks that now need the new fields were updated.
- New GPU e2e test `test/registered/disaggregation/test_disaggregation_decode_local_prefill.py` (Llama-3.1-8B, 2 GPUs, mini-lb) passed 3/3. It covers decode-cache reuse with first-token KL < 0.05 against cold PD, mixed local and PD traffic, and the prefill server's rejection of marked requests.

**Note on Mooncake TCP.** Under `--max-total-tokens 30000` with all-PD traffic, both main and this PR (flag off) sometimes failed a burst of PD transfers. Each time, the prefill worker logged `TCP lane queue-full rejection` followed by `Session ... failed`. In 7 alternating runs, each side hit this 3 times. It comes from the TCP transport, not from this change.

## Limitations and follow-ups

- Phase 2 is the router: the decode-side prefix lookup, the local-prefill decision, and decode affinity in `experimental/sgl-router`.
- Phase 1 does not support DP attention, DeepEP or other all-to-all backends, pipeline parallelism, HiSparse, or decode host KV buffering.
- DeepSeek-V4 decode radix cache on CUDA, without which PPD on DSV4 gets no decode-side hit.
- The Rust server and processor do not plumb `disagg_local_prefill` yet.
