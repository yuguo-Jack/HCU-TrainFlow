## Original PR description

The Qwen3.8-27B MXFP4 (Quark W4A4) changes for MI355X that touch the same Qwen3.5 GDN layer, its MXFP4 GEMM inputs and
the gated RMSNorm + MXFP4 kernel, in one PR (19 commits plus one merge):

1. Fused GDN prefill prologue (Conv1D, state update, gating) and gated RMSNorm + MXFP4 output epilogue, with the
   strided `in_proj` views. This was the original PR.
2. Ratio-3 fused qkvzba split on AITER/HIP, which the strided views need. Was #43381.
3. GDN `in_proj_qkvz` + `in_proj_ba` packed into one AITER ASM MXFP4 GEMM. Was #43785.
4. Bit-exact fusion of the MXFP4 input quantization into the preceding add + RMSNorm, SiLU-and-mul and attention output
   gate, and the packed `in_proj` at prefill sizes. Was #47154 (which had already absorbed #47155).
5. The GDN output norm + MXFP4 quantization per part of the pipelined chunk scan. Was #47777.

Stacked on #47774, merged in as one merge commit (`651bdf421c`): Part 5 needs #47774's pipelined chunk scan. Review only
the commits listed below; the #47774 commits drop out of this diff once #47774 merges and this branch is rebased.

### Part 1 (original #39912): fused GDN prefill prologue and MXFP4 output epilogue

#### Summary

- Fuse the Qwen3.8 TP1 GDN prefill producer’s causal Conv1D, state update, raw contiguous Q/K/V emission, and raw A/B to FP32 g/beta preparation on gfx950.
- Keep Q/K raw at the producer boundary and preserve the existing chunk scan’s `use_qk_l2norm_in_kernel=True` path for exact BF16 behavior.
- Fuse per-head gated RMSNorm with MXFP4 activation quantization before `out_proj`, supporting row-major EVEN output for Triton and native shuffled RoundUp output for the AITER ASM consumer.
- When the prefill prologue is on, read the GDN `in_proj` outputs as strided views (as CUDA already does) instead of unpacking them into contiguous `mixed_qkv` / `z` / `b` / `a` copies, since the prologue and the gated RMSNorm read them in place.
- Keep all additions fail closed: unsupported architecture, topology, dtype, stride, execution mode, state layout, or quantization contract retains the existing path.

#### Modifications

- `qwen3_5.py`: `use_strided_prefill_z` is now also true on ROCm when the new `Qwen3_5GatedDeltaNet._uses_qwen38_prefill_views` holds, so prefill takes `qwen3_5_gdn_prefill_projection_views` instead of `fused_qkvzba_split_reshape_cat_contiguous`. The check is a conservative mirror of the prologue's eligibility:
  - prologue enabled (AITER, gfx95, `SGLANG_QWEN38_GDN_PREFILL_PROLOGUE_FUSION=1`);
  - attention TP 1 with the Qwen3.8-27B GDN head layout (16 QK heads, 48 V heads, head dim 128);
  - extend without speculation, without multi-item scoring and without a mamba track mask;
  - not deterministic inference and not page-major KV layout;
  - no DP padding.

  Every other ROCm batch keeps the contiguous unpack, and CUDA behavior is unchanged. If the prologue still declines a batch at runtime, the views go to the stride-aware fallbacks: the Triton `causal_conv1d_fn` (channel-last), `fused_gdn_gating` and the gated-norm kernels. No new env var. The values read are the same, only through views, so the math is unchanged.

#### Dependency and scope

[#39598](https://github.com/sgl-project/sglang/pull/39598) has merged; this PR extends its Quark AITER ASM FP4 GEMM input contract.

The prefill producer targets Qwen3.8 TP1 GDN extend layers on gfx950 and is opt-in through `SGLANG_QWEN38_GDN_PREFILL_PROLOGUE_FUSION=1`. Decode, target verification, MIS, page-major state pools, DP padding, tracked-state batches, deterministic inference, and the model’s softmax-attention layers retain their existing paths.

The strided-views change needs #43381 (ratio-3 fused qkvzba split on AITER) to take effect: without it, the Qwen3.8-27B layout (ratio 3) does not reach the fused-unpack branch on ROCm and the change is a no-op. Overlap: #41683 and #47128 switch every ROCm extend to strided views; this PR switches only the batches the Qwen3.8 prologue consumes.

The producer emits raw BF16 post-Conv Q/K because the existing scan’s Q/K L2Norm reduction order is part of the exact numerical contract. V, FP32 g/beta, Conv state updates, packed-varlen boundaries, initial-state behavior, scheduler tails, and scan normalization remain unchanged.

#### Update: Conv1D bias is optional

Qwen3.8 checkpoints have no GDN Conv1D bias, so the earlier eligibility check rejected every real prefill and the fused producer never ran on the target model. The producer now accepts `bias=None` and selects the existing `HAS_BIAS=False` kernel variant, and rank 0 logs once whether the prologue is enabled, or why not. New tests: bias-free output is bit-exact against `causal_conv1d_fn`, and bias shape/dtype/stride mismatches are rejected.

A/B of this fix, MI355X TP1, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`, 5 serving rows, same image with and without it: throughput +0.43% geomean, TTFT −8.39% (8K c4 −34.6%), TPOT +0.18%. The performance sections below predate this fix and will be re-measured.

### Part 2 (was #43381): ratio-3 fused GDN qkvzba split on AITER/HIP

#### Motivation

Qwen3.8-27B (and other dense Qwen3.5-architecture hybrids) use 48 v-heads over 16 k-heads in their GDN layers, a v/k head ratio of 3. #34859 taught `fused_qkvzba_split_reshape_cat_contiguous` to handle non-power-of-two groups through a per-head walk, and enabled ratio 3 on CUDA. The AITER tuple in `qwen3_5.py` was left at `(1, 2, 4, 8)`. On ROCm, every GDN layer of these models therefore still takes the unfused fallback on every forward pass: `torch.split`, two `.contiguous()` copies, and a `torch.cat`.

The kernel itself has no CUDA-specific code on this path, and the existing ratio-3 unit test is already registered for AMD CI.

#### Modifications

- `python/sglang/srt/models/qwen3_5.py`: add `3` to `_GDN_FUSED_QKVZBA_RATIOS` when `_use_aiter` is set (`(1, 2, 4, 8)` -> `(1, 2, 3, 4, 8)`), and update the comment. CUDA, CPU and non-AITER HIP are unchanged.

#### Accuracy Tests

The fused kernel is pure data movement. `test/registered/attention/test_gdn_fused_split_head_ratios.py` checks it bit-exactly against plain slicing for ratios 1, 2, 3 and 4. On MI355X (ROCm 7.x, torch 2.11.0+rocm, `SGLANG_USE_AITER=1`), with this branch's source:

### Part 4 (was #47154): bit-exact RMSNorm / SiLU-and-mul + MXFP4 quant fusion

#### Motivation

On MI355X (gfx950), Quark W4A4 MXFP4 Qwen3.5/3.8 dense checkpoints run `qkv_proj`, the dense MLP `gate_up_proj` and `down_proj`, and the packed GDN `in_proj` on the AITER ASM FP4 GEMM (`SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM=1`). Each of these GEMMs gets its FP4 input from a separate `per_1x32_f4_quant(shuffle=True)` that reads back the bf16 tensor the previous op just wrote:

- `qkv_proj`, `gate_up_proj` and GDN `in_proj` quantize the output of the Gemma add+RMSNorm in front of them;
- `down_proj` quantizes the output of SiluAndMul.

That costs one extra kernel launch and one extra round trip of the activation per projection per layer, which is significant at decode batch sizes. This PR moves the quantization into the producing kernel for both cases, without changing a single bit of the GEMM input.

Bit-exactness is deliberate. AITER already has a fused `act_mul_and_mxfp4_quant`, but by default it quantizes the fp32 `silu(gate) * up` with even-rounded scales. That is valid MXFP4, but it is not the input the unfused path produces; this and a non-bit-exact norm+quant producer we tried first matched only 98.2-99.5% of the fp4 bytes, and on Qwen3.8-27B at TP2 that was enough to move GSM8K (see Accuracy).

#### Modifications

##### Add + RMSNorm + MXFP4 quant (`qkv_proj`, `gate_up_proj`, GDN `in_proj`)

- `gemma_fused_add_rmsnorm_mxfp4_quant` (`sglang/kernels/ops/layernorm/minimax_m3_rmsnorm.py`): the existing ROCm Triton Gemma add+RMSNorm kernel with an MXFP4 epilogue.
  - It rounds the normed row to bf16, then quantizes it the way `per_1x32_f4_quant` does: RoundUp E8M0 scale, 1e-10 amax floor, E2M1 round-to-nearest-even via `v_cvt_scalef32_pk_fp4_f32`.
  - It writes fp4x2 codes, plus E8M0 scales in the shuffled, 256-row padded layout that the ASM GEMM reads.
- `gemma_rms_norm_uses_rocm_triton()` in `layernorm.py`: true when `GemmaRMSNorm.forward_hip` runs that Triton kernel. That is the bf16 path the fused producer must match bit for bit.
- `qwen3_5.py`:
  - `_GemmaRMSNormMXFP4Quant` and `_gemma_rms_norm_for` replace `input_layernorm` / `post_attention_layernorm` only when all of these hold:
    - AITER on gfx950, with the ROCm Triton Gemma norm;
    - hidden size a multiple of 256 and at most 8192;
    - the consumer is a Quark W4A4 MXFP4 linear.
  - Whether a batch takes the fused path is decided per batch, because the ASM GEMM is selected after weight loading. The fused path requires that the consumer actually runs the ASM GEMM for that batch, and it is never taken under torch.compile, sequence parallelism or DP attention. Otherwise, and for the first layer (no residual), the regular bf16 norm runs.
  - The `(fp4x2, E8M0)` pair is routed to ASM FP4 linears (`_select_fused_ar_input_for_linear`) and to the packed GDN `in_proj` (64 rows eager, 256 under graph capture, same caps as #43785).

##### SiLU-and-mul + MXFP4 quant (`down_proj`)

- `Qwen2MoeMLP._silu_mxfp4_quant_fused` calls `act_mul_and_mxfp4_quant(gate_up, "silu", scaling_mode="roundup", shuffle=True, round_to_input_dtype=True)`:
  - `round_to_input_dtype` makes the kernel quantize `bf16(bf16(silu(gate)) * up)`, which is the tensor SiluAndMul writes;
  - `"roundup"` uses `per_1x32_f4_quant`'s E8M0 scale.
  - The result goes to `down_proj` as `_AsmShuffledMxfp4Input` (from #39912), and `down_proj` validates it before calling `gemm_a4w4`.
- `Qwen2MoeMLP.forward` takes the fused path only for 2-D, non-empty batches when `down_proj.use_aiter_asm_fp4_gemm` is set (decided after weight loading). Every other case keeps SiluAndMul followed by the normal quant.
- `_maybe_enable_silu_mxfp4_quant_fusion` (qwen3_5) turns it on for dense MLPs on ROCm only when both `gate_up_proj` and `down_proj` use `QuarkW4A4MXFP4`, and the installed AITER kernel accepts `round_to_input_dtype`. If the AITER kernel cannot reproduce the unfused bytes, the fusion stays off.

##### Common

- No new env var or kill switch. Both paths are only reachable with the existing opt-in `SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM=1`, and they need no separate switch because the GEMM input is bit-identical to the unfused path.

- Norm: fp4 codes, E8M0 scales and the residual output are byte-identical to `GemmaRMSNorm` (ROCm Triton) followed by `per_1x32_f4_quant(shuffle=True)`, so the GEMM sees exactly the same input as before. They are byte-identical to the unfused add + RMSNorm + `per_1x32_f4_quant_hip` in all 30 cases tested: M 1-16,384, hidden size 5,120; unit, large, tiny and all-zero inputs.

### Part 5 (was #47777): GDN output norm + MXFP4 quant per part of the pipelined scan

#### Motivation

With `SGLANG_GDN_CHUNK_PIPELINE=1` (#47775), the GDN chunk scan of a long prefill runs in parts: `chunk_h` of part i runs on
the calling stream while a side stream runs the per-chunk kernels of the parts before and after it. The layer's output then
goes through the gated RMSNorm + MXFP4 quantization (the out_proj input, #39912). That kernel ran over all rows after the
scan, alone on the calling stream: 117 us per layer for a 16384-token chunk on MI355X, 48 GDN layers in Qwen3.8-27B. It is
bound by bandwidth and VALU work (the precise sigmoid takes ~11 VALU instructions per element), and launch shapes gain at
most 4%. So the lever is overlap: the rows of a part are final as soon as the side stream has written that part's output,
while `chunk_h` still runs the next part.

#### Modifications

- `chunk_gated_delta_rule(..., epilogue=None)`: `epilogue(o, start, end)` runs on output rows [start, end) once they are
  final. In the pipelined scan it runs on the side stream after each part's output kernel; the last part (and any padded
  rows after the sequence) runs on the calling stream after the scan. In one pass it runs once over all rows.
- The Triton GDN extend kernel passes `epilogue` on and declares `supports_extend_epilogue`. `GDNAttnBackend` takes
  `linear_attn_epilogue` in `forward_extend` and refuses it for target verify, MIS metadata or kernels without support.
- `RadixLinearAttention`: the owning layer sets `output_epilogue`. A call passes the epilogue's tensors as
  `epilogue_inputs`, and they reach the backend as arguments of the breakable CUDA graph's eager break, like the attention
  inputs (under a breakable prefill graph only the break runs at replay, so the model code cannot hold them between
  breaks). After a padded batch's tail is zeroed, the epilogue covers those rows too.
- Qwen3.5 GDN layer: with the pipelined scan on, the strided prefill views, and an out_proj scheme that takes the fused
  gated-norm input (`QuarkW4A4MXFP4.prepare_fused_rmsnorm_gated_rows`), the layer allocates the out_proj input up front,
  passes (z, FP4 codes, scales) as epilogue inputs and feeds the buffers to out_proj after attention. Otherwise nothing
  changes.
- `rmsnorm_gated_mxfp4_quant_rows` writes token rows [start, end) with the launch of the full row count (same rows per
  program), so the bytes are the same as one launch over all rows. With the ASM-shuffled scale layout a range starts at a
  32-token scale tile.

#### Accuracy Tests

- Bit-identical by construction (the same kernels with the same per-row launch parameters, run on rows once they are
  final). Microbenchmark: FP4 codes, ASM-shuffled scales, the attention output and the final state are bit-identical to the
  current scan + norm at 16384, 12596, 8192 and 16000-in-16384 (padded) tokens.
- New unit tests: the epilogue sees every row once, after it is final (4 parts, 3 parts, padded tail, one pass, two
  sequences; output and state unchanged with and without it); the row writer in any order and from inside a scale tile,
  both scale layouts, bytes equal to one launch; the attention layer hands the inputs to the epilogue and covers padding,
  also through the eager break; the layer only takes the path with the pipeline, a supporting backend and scheme. MI355X,
  this branch: `test_chunk_gated_delta_rule.py` 37 passed, 1 skipped; `test_rmsnorm_gated_mxfp4.py` 7 + 12 passed;
  `test_quark_mxfp4_asm_prequantized.py` 8; `test_qwen3_5_gdn_mxfp4.py` 8; `test_radix_linear_attention.py` 8;
  `test_qwen38_gdn_prefill_prologue.py` 10; `test_mamba_prefill_track_metadata.py` 11.
