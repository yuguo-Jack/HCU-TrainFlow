# [Perf] spec-decode: Add candidate-pruned DSpark Markov sampling

[Upstream PR](https://github.com/sgl-project/sglang/pull/40513) · state: open · merged: False

## Original PR description


## Summary

DSpark computes a Markov correction across the draft vocabulary at each proposal step. This PR adds an opt-in candidate union: base-logit Top-K plus the previous token's static Markov Top-K. It evaluates the correction only for that union, then passes the same FP32 masked logits through the existing `MarkovSampleStep`, proposal storage, and rejection verification.

- Use one option, `--speculative-dspark-markov-topk`, for both sets. The default `0`, or K covering the full draft vocabulary, uses the dense path. Candidate pruning currently supports an ordinary VanillaMarkov head on NVIDIA CUDA with TP=1; other configurations retain the dense path.
- Precompute only candidate IDs in bounded chunks. Compute their bias values online; preserve overlapping candidates as one outcome, draft-to-target vocabulary mapping, and negative/zero logit scale.
- Reuse the existing per-step loop, Philox sampling and dense proposal probabilities. There is no separate candidate sampler, fused walk kernel, sparse proposal cache, or verifier-normalization change.
- Retain the Qwen3 Speculators checkpoint adapter, checkpoint-owned embedding/head and hidden-size projection needed by the tested checkpoint path. Preserve bucketed and direct weight updates, refreshing candidate IDs in place.

The simplification follows the request to isolate the candidate-set change in [the related review](https://github.com/vllm-project/vllm/pull/56694#issuecomment-6269712362). Unrelated PP-stage test coverage is restored. The previous standalone benchmark targeted the removed fused implementation and has been removed.

## Validation

Current implementation: [`a720a45705`](https://github.com/sgl-project/sglang/pull/40513/commits/a720a45705c3018901666ca058904a647c3d9108).

- Python AST, Ruff checks and formatting, whitespace checks, and registered-test lint checks pass locally.
- Three focused CPU regressions in the existing `test_dspark_draft_block.py` pass when executing the actual production classes/methods through an AST harness: candidate union/mapping/scale, disabled/full-vocabulary fallback, and bucket/direct weight updates with stable ID-table storage. The weight-update regressions also fail against the old implementations.
- Additional CPU checks of the actual block loop and `MarkovSampleStep.torch` cover FP16/BF16/FP32, positive/negative/zero scale, padded anchors, mixed temperatures, stored proposal logits and RNG-offset advancement.
- Full pytest collection is blocked in the local environment by missing `triton.backends`. GPU correctness, CUDA graph capture/replay, and throughput have **not** been rerun for this simplified implementation.

## Current GPU validation recipe

Use the same checkpoint and workload on the same commit, comparing `--speculative-dspark-markov-topk 0` with `--speculative-dspark-markov-topk 32`. There is no longer a `--speculative-dspark-markov-bias-topk` option or checkpoint-derived candidate budget.

```bash
python -m sglang.launch_server \
  --model-path /personal/model/Qwen3-4B \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path /personal/model/dspark_qwen3_4b_block7 \
  --speculative-dspark-block-size 8 \
  --speculative-dspark-markov-topk 32 \
  --disable-radix-cache \
  --port 30012
```

For the 4B model, start with one GPU and concurrency 1/8/64. Report output tokens/s, TPOT, accepted length, task accuracy, initialization time and memory, at temperatures 0 and 1; include a high-entropy workload. Record the exact commit, checkpoint, GPU/runtime versions and raw results. Multi-GPU/DP measurements can then be reported separately.
