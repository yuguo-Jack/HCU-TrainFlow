# [Perf] disaggregation: Batch prefill KV-send page-id readback across a batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/47472) · state: open · merged: False

## Original PR description

> Stacked on #47426 (shares its deferral predicate and `kv_to_page_indices(non_blocking=)`). Until that merges, review the last commit only.

## Motivation

A PD prefill worker computes every KV send's page ids one request at a time:

- **Early cached-prefix send** (`run_batch`, `SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX`): `maybe_send_cached_prefix_chunk` runs per request, and each call does its own `req_to_token` row gather, D2H copy and early-send event record.
- **Last-chunk send** (`process_batch_result_disagg_prefill`): each finished request does its own gather and D2H copy inside the result loop.

With many cache-hit requests per batch, for example agentic multi-turn traffic, this is per-request host and launch work on the scheduler thread, and it grows with batch size. A blocking sender also pays one device sync per request.

## Modifications

- `_batched_page_indices(reqs, ends)` reads the page ids of every request's next send `[start_send_idx, end)` with one index upload, one gather and one host copy, then splits them per request.
  - Deferring senders (`supports_host_tensor_indices`) get the copy in flight through `to_host_nonblocking`. Each send's indices event is recorded later on the same stream, so it covers that copy.
  - Blocking senders get one `.cpu()` for the whole batch.
  - It returns None, and each send keeps computing its own ids, for: a single request; staging or a sender transfer cap (multi-segment sends); a non-identity `translate_kv_indices_for_transfer` (virtual-id pools); rank-local CP storage (`is_cp_sharded_padded`); and a batch that mixes deferring and blocking senders.
- Early send: `send_cached_prefix_chunks(reqs, allow_send)` replaces the per-request `maybe_send_cached_prefix_chunk`.
  - Eligibility, in `_cached_prefix_send_end`, is unchanged: page-aligned device-resident prefix, the staging snapshot, `pending_bootstrap`, and the HiCache load-back gate from #44081.
  - Under overlap, one `device_module` event recorded on `forward_stream` covers every early send in the batch. Before, each request recorded its own event at the same point.
- Last-chunk send: the result loop collects the finished requests, and `_send_last_kv_chunks` sends them after the loop with batched page ids. Each send still follows its own request's cache insert, which rewrites only that request's row.
- `send_kv_chunk` / `_send_kv_chunk` take optional precomputed `page_indices`, used only on a single-segment send.

## Accuracy Tests

The model forward is unchanged. The page ids each send ships are asserted to be the same as the per-request path, in the unit tests and in the benchmark below.

## Speed Tests and Profiling

Scheduler-thread time of one batch's early cached-prefix sends on one B300. The benchmark runs the real `SchedulerDisaggregationPrefillMixin` send path against a sender that only records its arguments, so it measures the scheduler's index work and not the transfer. `page_size=64`. In the deferred rows, a 200 ms kernel is in flight on the stream, standing in for the forward. Every run checks that the shipped page ids match `req_to_token`.

Two runs, each the median of 5 iterations after 2 warmups:

| sender | batch size | cached prefix | per request (ms) | batched (ms) | speedup |
|---|---:|---:|---:|---:|---:|
| deferred | 8 | 16,384 | 0.458 / 0.403 | 0.389 / 0.446 | ~1× (noise) |
| deferred | 32 | 16,384 | 1.229 / 1.214 | 0.728 / 0.667 | 1.7–1.8× |
| deferred | 64 | 8,192 | 2.169 / 2.134 | 1.127 / 0.977 | 1.9–2.2× |
| deferred | 128 | 4,096 | 4.426 / 4.218 | 1.744 / 1.791 | 2.4–2.5× |
| blocking | 8 | 16,384 | 0.350 / 0.382 | 0.309 / 0.292 | 1.1–1.3× |
| blocking | 32 | 16,384 | 1.153 / 1.205 | 0.414 / 0.425 | 2.8× |
| blocking | 64 | 8,192 | 2.453 / 2.252 | 0.561 / 0.548 | 4.1–4.4× |
| blocking | 128 | 4,096 | 4.307 / 4.419 | 0.695 / 0.727 | 6.1–6.2× |

Small batches see no measurable gain. The saving grows with the number of cache-hit requests per batch.

The last-chunk send uses the same helper. I have not run an end-to-end PD serving benchmark for this PR.

## Tests

- `test/registered/unit/disaggregation/test_prefill_batched_page_indices.py` (new):
  - Batched ids equal the per-request reads: partial last page, a resumed send, nothing left to send, input shorter than the extend range, start past the end, and early-send ends.
  - Every unbatchable case falls back to the per-request path.
  - A precomputed id list is shipped as is, with no row gather of its own.
  - With a kernel in flight, the deferred ids land correctly (CUDA).
- `test_prefill_abort_result_cleanup.py`:
  - One early-send event, created by the scheduler's device module, covers every eligible request. Ineligible requests get no event and no send.
  - A batch with a pending HiCache load-back sends nothing.
