# [CI] workflows: Don't cancel in-flight post-merge runs on main

[Upstream PR](https://github.com/sgl-project/sglang/pull/44833) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #44832.

In `pr-test-{npu,xpu,xeon,musa,rust}.yml`, every `push` to `main` lands in the same concurrency group (`...-refs/heads/main`) with `cancel-in-progress` enabled. Each merge therefore cancels the previous merge's in-flight post-merge run. Recent data: NPU had 39 of its last 60 `main` push runs cancelled, Xeon 18 of 30, XPU 11 of 31. As a result, breaking commits can reach `main` without a completed run on these backends, and the culprit range grows when something finally fails.

## Modifications

In these five workflows, change only `cancel-in-progress`. The concurrency groups are unchanged.

```yaml
cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

- **`pull_request`:** unchanged. A new push to a PR still cancels that PR's older run.
- **`push`, `schedule` and `workflow_dispatch` on `main`:** runs queue instead of cancelling the run in progress. GitHub keeps at most one pending run per group, and a newer pending run replaces an older one. Runner cost is therefore bounded at one running plus one queued run per workflow, not one run per commit.
- **`workflow_call` callers** (`release-branch-cut.yml`, `bot-bump-sglang-version.yml`): still never cancelled. The old `!= 'workflow_call'` check could never match, because a reusable workflow sees the caller's `event_name`.
