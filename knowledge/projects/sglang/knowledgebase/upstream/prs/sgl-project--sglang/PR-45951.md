# [Perf] LoRA: improve throughput and GPU memory usage for multi-LoRA serving under PP

[Upstream PR](https://github.com/sgl-project/sglang/pull/45951) · state: closed · merged: True

## Original PR description

## Motivation

Pipeline-parallelism is a foundational paradigm for serving large models efficiently. However, currently, multi-LoRA serving does not handle PP in the most efficient way possible, both in terms of throughput and GPU memory usage.

#### Example

Consider PP=2, with 4 slots on each GPU. Microbatch A uses 2 adapters, and the scheduler is building microbatch B from requests for 3 other adapters. Both microbatches pass through both GPUs, but each GPU only considers the adapters of its own microbatch. Since B's 3 adapters fit in 4 slots on their own, the scheduler admits all of B's requests, even though A and B together need 5. Every GPU then evicts and loads adapters on every step as A and B take turns. With this PR, each GPU keeps the adapters of all in-flight micro-batches loaded, and the scheduler only admits a request if its adapter fits alongside them. B gets 2 of its 3 adapters, and the request for the third waits until a slot frees up.

```
main
  Stage 0 │▒ load ▒▒█ run A █│▒ load ▒▒█ run B █│▒ load ▒▒█ run A █│▒ load ▒▒█ run B █│
  Stage 1 │                  │▒ load ▒▒█ run A █│▒ load ▒▒█ run B █│▒ load ▒▒█ run A █│▒ load ▒▒█ run B █│

branch
  Stage 0 │▒ load ▒▒█ run A █│▒ load ▒▒█ run B █│█ run A █│█ run B █│
  Stage 1 │                  │▒ load ▒▒█ run A █│█ run B █│█ run A █│█ run B █│

█ compute   ▒ load adapters
```

## Modifications

There are two main modifications that I made:
- `LoRAManager`s on a given PP stage should prioritize keeping adapters that are needed in other stages in the memory pool. Previously, `LoRAManager`s were only aware of the adapters needed for their own next microbatch.
- Each stage's LoRA memory pool only allocates adapter weights for the layers that stage uses, which reduces the GPU memory per adapter slot by a factor of the PP size.

#### Throughput Results

| Metric | `main` | PR | Change |
|---|---:|---:|---:|
| Benchmark duration (s) | 2,370.2 | 420.1 | **−82.3%** |
| Output throughput (tok/s) | 44.3 | 250.2 | **5.6×** |
| Mean E2E latency (ms) | 187,553 | 31,353 | **−83.3%** |
| Median E2E latency (ms) | 189,043 | 30,307 | **−84.0%** |
| P99 E2E latency (ms) | 404,723 | 79,866 | **−80.3%** |
| Mean TPOT (ms) | 709.4 | 77.0 | **−89.1%** |
| Median TPOT (ms) | 722.3 | 77.0 | **−89.3%** |
| P99 TPOT (ms) | 928.4 | 87.8 | **−90.5%** |
| Mean TTFT (ms) | 2,601 | 11,196 | +330% |
| Median TTFT (ms) | 854 | 2,341 | +174% |
| P99 TTFT (ms) | 33,987 | 47,861 | +41% |

The scheduler now admits a request only when its adapter fits alongside those of in-flight micro-batches, instead of evicting adapters that are still in use. Thus, new requests may wait longer for a slot (resulting in higher TTFT), but no longer cause reloads on every decode step, resulting in a much lower TPOT.
