# [Perf] [AMD] frontend: Encode long Qwen3.5-family chat prompts in parallel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47778) · state: open · merged: False

## Original PR description

## Motivation

`parallel_prompt_encode` (#41259) cuts a long rendered chat prompt at added tokens and, for the GLM / Llama-3
pre-tokenizer only, at pre-token boundaries inside long gaps, then encodes the pieces with `encode_batch`.
Qwen3.5-family tokenizers (Qwen3.5 / Qwen3.6 / Qwen3.8: NFC normalizer + the Qwen3.5 split regex) get neither benefit
for a single long message:

- the intra-gap cuts are refused (different regex, and a normalizer is present), so a 100k-token message is one piece;
- these models are multimodal, and SGLang sets `TOKENIZERS_PARALLELISM=false` for them, so `encode_batch` runs serially
  anyway and the CPU-time probe switches the helper off for the process.

On a 100k-200k token chat request, tokenization alone then takes 0.15-0.32 s on the request path before prefill starts.

Related: #44392 (open) extends the intra-gap cuts to the Qwen2 / Qwen3, Qwen3.5, o200k and DeepSeek-V3 pre-tokenizers
under NFC, with the same regex and the same NFC argument as the first item below. It does not have the thread pool, so on
Qwen3.5-family models (multimodal, `TOKENIZERS_PARALLELISM=false`) the pieces are still encoded one after the other. The
measured gain needs both parts: the cuts make the pieces and the pool encodes them in parallel. If #44392 lands first, I'll
rebase this PR onto it and keep only the thread pool.

## Modifications

- Accept the Qwen3.5 split regex (letter runs include combining marks, single digits) and an NFC normalizer for the
  intra-gap cuts. The cut points ("letter|space letter", "\n|letter") are pre-token boundaries for this regex for the
  same reasons as for the GLM regex, and NFC never composes a space or an ASCII letter with a preceding character, so
  normalizing both sides of a cut separately gives the normalized whole. Added tokens matched on normalized text could
  straddle a cut, so a normalizer together with such tokens keeps only the added-token cuts.
- When the tokenizers thread pool is off in the process, encode the pieces one per `encode_batch` call from a small
  thread pool (`encode_batch` releases the GIL). The existing CPU-time probe still turns the helper off when this does
  not actually run in parallel. A forked child creates its own pool.

## Accuracy Tests

- Unit tests (`test/registered/unit/entrypoints/openai/test_parallel_prompt_encode.py`, CPU): a Qwen3.5-shaped tokenizer
  built in memory (NFC + Qwen3.5 regex + ByteLevel + BPE): edge cases, NFC-rewritten text (combining marks, Hangul
  jamo, singletons, non-ASCII digits) on both sides of every cut point, and fuzzed texts give the ids of a single
  `encode` at every cut point; the normalized-added-token refusal; the thread-pool path (one call per piece, identical
  ids, a new pool after fork). 32 passed, 21 subtests; dropping either the refusal or the thread pool fails the new
  tests.
- Real tokenizer (Qwen3.8-27B, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`): ids identical to `tokenizer.encode` on 110 texts
  (33.8M characters, including adversarial Unicode); served `prompt_tokens` identical with and without the change.
- Greedy output ids of four reference prompts (100k-200k tokens and a short one) identical with and without the change.

## Speed Tests and Profiling

Qwen3.8-27B MXFP4 (`amd/Qwen3.8-27B-Quark-AWQ-MXFP4`), one MI355X, TP1, chunked prefill 16384, FP8 KV cache.
`python3 -m sglang.bench_serving --backend sglang-oai-chat --dataset-name random --random-range-ratio 1.0
--random-output-len 1 --max-concurrency 1 --request-rate inf --num-prompts 32 --warmup-requests 1 --flush-cache`, one
seed per input length. Same GPU, runs in the order before / after / after / before; mean of each side's two median
TTFTs (the two runs of a side differ by at most 0.5%):

| input tokens | median TTFT before (s) | after (s) | change |
|---|---|---|---|
| 100000 | 2.968 | 2.893 | -75 ms (-2.5%) |
| 120000 | 3.730 | 3.632 | -98 ms (-2.6%) |
| 140000 | 4.555 | 4.418 | -138 ms (-3.0%) |
| 160000 | 5.456 | 5.307 | -149 ms (-2.7%) |
| 180000 | 6.358 | 6.171 | -188 ms (-3.0%) |
| 200000 | 7.390 | 7.200 | -190 ms (-2.6%) |

Tokenization of one prompt in the server process: 0.15 / 0.15-0.22 / 0.28-0.32 s at 100k / 131k / 200k tokens before,
13 / 19 / 33 ms after.
