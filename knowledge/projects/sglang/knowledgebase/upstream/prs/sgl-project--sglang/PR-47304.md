# [Perf] dsv41: Drop per-layer routing glue under simulated routing with EPLB

[Upstream PR](https://github.com/sgl-project/sglang/pull/47304) · state: closed · merged: True

## Original PR description

## Motivation

DSV4.1 decode baselines run with `SGLANG_SIMULATE_ROUND_ROBIN_EXPERTS=1` plus EPLB (`--ep-num-redundant-experts 64 --ep-dispatch-algorithm dynamic`). In that setup every MoE layer ran six small kernels between MegaGate and MegaMoE that production never runs:

`randint` → `triton_poi_fused_index_randint_remainder` → `_fill_padded_rows` → int32 `direct_copy` → routed-scale `Mul` → `mega_moe_pre_dispatch`

`run_mega_gate` dropped the in-buffer routing path whenever simulation and EPLB were both on, because the simulation wrote logical ids. So the benchmark overstated decode step time.

Separately, `_physical_dispatch_maps` cast the int64 EPLB maps to int32 on every call. That is 2 cast kernels per MoE layer per step, on the production path too.

## Modifications

1. **Simulation writes physical ids.** `_simulate_balanced_routing_kernel` optionally maps logical ids to physical slots with MegaGate's replica pick (`(ep_rank + token * 23333) % logical_count`). `run_mega_gate` passes the maps and keeps `in_buffer` under simulation. `moe_ep_rank` is read only when a map is passed.
2. **Cached int32 dispatch maps for MegaGate.** `ExpertLocationMetadata.mega_gate_maps(algorithm)` builds MegaGate's int32 `(physical map, replica count)` once per dispatch algorithm, on first use and outside graph capture. `update()` refreshes the cached maps in place, so captured CUDA graphs see rebalances. When MegaGate is on, `ExpertLocationDispatchInfo` carries this layer's slice in one `mega_gate_maps` field. Without it, for example when another backend is in use or in existing tests, the gate still casts per call. Nothing is allocated unless MegaGate and a static/dynamic dispatch algorithm are both enabled.

## Accuracy Tests

No numerics change in production. (1) only touches the benchmark-only simulation path, and (2) replaces casts with identical int32 values.

## Benchmarking and Profiling

DSV4.1-Flash, DEP16 (4 nodes × 4 GPUs), DSpark spec with simulated acceptance 3.25, round-robin simulated routing, 64 redundant experts with dynamic dispatch.

Same job, baseline vs. this PR, bs256 per rank, 2k-token prefix:

| | base | this PR |
|---|---|---|
| step time | 19.09 ms | 18.50 ms (−3.1%) |
| kernels / step (rank 0) | 1155 | 913 |
| elementwise kernels / step | 324 | 122 |

Removed per step (×40 layers each): `mega_moe_pre_dispatch` (302 µs), `triton_poi_…randint…` (101 µs), `randint` (95 µs), `direct_copy` (80 µs), `Mul` (57 µs), `_fill_padded_rows` (52 µs). Each layer now runs MegaGate → simulation → MegaMoE.

At a 126k prefix (commit 1 only, vs. an earlier baseline run): bs8 8.09 → 7.84 ms, bs64 10.15 → 9.83 ms, bs256 19.91 → 19.45 ms.

## Tests

- Existing tests passed on GPU with this change: `test_round_robin_ep_balance.py`, `test_mega_gate.py`, `test_topk_routing_inputs.py`, `test_dispatch_dtype_preservation.py`, `test_expert_location_weight_loading.py`, `test_hash_topk.py`, `test_flashinfer_dispatcher.py`, `test_mega_moe_deepgemm_api.py`.
- Checked end to end with the bs256 decode profiles above: no glue kernels, and no int32 cast kernels before MegaGate.
