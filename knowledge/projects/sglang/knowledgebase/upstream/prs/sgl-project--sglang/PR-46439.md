# [Perf] diffusion: Quantize video frames to uint8 before the host copy

[Upstream PR](https://github.com/sgl-project/sglang/pull/46439) · state: closed · merged: False

## Original PR description

## Motivation

Public video frames are uint8, but two return paths move the full FP32 clip to the host and quantize it afterwards:

- `LTX2AVDecodingStage._postprocess_video` copies the FP32 clip into a pinned host buffer, one bounded chunk at a time.
- On the default array return (no `return_frames`), the worker hands the FP32 CUDA video `[B, C, T, H, W]` to the scheduler. The scheduler copies it to the host to spill it, and the client quantizes it in `_sample_to_uint8_frames`.

The host copy therefore carries four times the bytes it needs. For a 121-frame 960x544 clip that is 758,292,480 bytes instead of 189,573,120.

## Modifications

- `decoding_av.py`: the pinned buffer is uint8. Each bounded chunk is clipped to `[0, 1]`, scaled by 255 and truncated before the copy, which is the same policy the client applies to these frames.
- `gpu_worker.py`: for video requests (`req.data_type == DataType.VIDEO`), `_return_frames_from_worker` also routes a multi-frame CUDA video on the default array return through the existing worker-side frame conversion. That conversion is `(x * 255).clamp(0, 255).to(torch.uint8)`, the same formula as the client's `_sample_to_uint8_frames`, now applied before the copy.
- `return_frames` keeps its meaning. Other data types, frame interpolation, upscaling, latents, NCHW images and one-frame tensors keep their current path.

**Behavior change:** on the affected paths, `GenerationResult.samples` now holds the uint8 frames instead of the FP32 sample, as it already does with `return_frames=True`. `frames`, saved files and server responses are unchanged.

## Accuracy Tests

The final frames are computed with the same formulas as before, only on the GPU before the copy:

- `TestLTX2VideoPostprocess` asserts exact equality with the host clip-scale-truncate policy on CUDA, across bf16/fp16/fp32, normalization and channels-last inputs.
- On a 124-frame video model, the returned video and audio arrays matched the previous client-side conversion.
- For LTX-2.5, the saved MP4 in every request is one of the same two byte sequences with or without this change. The unpatched runtime itself alternates between those two across requests.

Closing after measuring where this pays off: 1x/4x B200, main d2cf2371b0 vs main + #46436 + this PR, ABBA order.

| Path | main | this PR |
| --- | --- | --- |
| HTTP `/v1/videos`, MP4 saved: LTX-2.5 960x544 121f, 1 GPU | 2.665 / 2.651 s | 2.667 / 2.668 s |
| HTTP `/v1/videos`, MP4 saved: LTX-2.5 two-stage 1920x1088, 4 GPUs | 3.257 / 3.272 s | 3.283 / 3.266 s |
| HTTP `/v1/videos`, MP4 saved: FastH3 V2 124f, 4 GPUs | 5.220 s | 5.218 / 5.216 s |
| Offline `generate(save_output=True)`, LTX-2.5 1 GPU | 2.651 / 2.659 s | 2.648 / 2.654 s |
| Offline `generate(save_output=False)`, LTX-2.5 1 GPU | 2.933 / 2.990 s | 2.476 / 2.500 s |

Why only the last row moves:
- The HTTP server and saved outputs already quantize to uint8 on the GPU before the host copy (`_sample_to_uint8_frames`). LTX-2 over HTTP also encodes while decoding.
- Only the offline array return copies FP32 to the host, and that case gains 0.47 s (16%).

The routing condition also matches requests that need the FP32 output:
- The `/rollout/generate` API (`save_output=False`, video `data_type`) would get a list of uint8 arrays, and `_build_response` reads `result.output.shape`.
- The disagg decoder would pass numpy arrays to `send_tensors`, which accepts tensors only.

If the offline array path matters later, it should be an explicit opt-in that only `DiffGenerator` sets.
