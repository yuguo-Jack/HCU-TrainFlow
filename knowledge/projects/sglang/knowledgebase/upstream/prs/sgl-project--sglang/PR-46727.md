# [Perf] deepseek-v4.1: Feed encoder-only decode tails through DSpark verify steps

[Upstream PR](https://github.com/sgl-project/sglang/pull/46727) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

Stacked on #45265 (encoder-only prefill for DeepSeek-V4.1 PD). Until that merges, this diff also contains its two commits; the change here is the last commit, `50bc63b0ef`.

In #45265 the prefill server stops 128 tokens short of the prompt end. Decode then runs those last tokens (the "tail") through all 40 layers before it samples the first token. #45265 runs each tail as an extend step that alternates with decode steps. With decode DP attention every rank joins that step, so a steady stream of new requests costs every running request extra steps. At c160 the tail extends raised decode ITL p50 from 11.0 to 15.8 ms.

This PR runs the tail inside the speculative verify steps that decode performs anyway:
- A transferred request joins the running batch with its KV at the tail start.
- Each DSpark verify step feeds the request's next 6 prompt tokens as forced drafts. Their logits rows are one-hot, so the normal accept takes exactly those tokens.
- A 128-token tail therefore rides about 22 verify steps instead of separate extend steps.
- Late layers floor their sliding window at the tail start, so each tail row attends to the same keys as in the extend.
- Prompt tokens never reach the output or the speculative metrics.

The path is behind `SGLANG_DSV41_FUSED_TAIL=1` (default off). Without it, #45265's extend path is unchanged.

**Impact**
- **Accuracy:** GPQA diamond (`sgl-eval`): split with fused tails 90.6% (358/395) vs stock PD + prefill HiCache 91.9% (362/394), within the ~2-point standard error. GSM8K (400 questions): fused 0.900, stock 0.900.
- **Performance, decode cost of the tail** (GB300, DP2 decode, real acceptance): ITL p50 / p90 +7% / +4% over stock PD, against +10% / +11% for time-batched tail extends (`SGLANG_DSV41_TAIL_HOLD_MS=500`, #45265). Under a burst of 4.8 new requests/s per rank, decode throughput drops 3.1-3.9% vs 10.1-11.3%.
- **Performance, end to end:** the max-throughput point in #45265 (GB300, 10 prefill workers + DEP16 decode, AgentX c6400) runs with this PR. There the split ties stock PD (906k vs 909k tok/s/GPU) at the same P/D ratio; layouts with fewer prefill workers are being measured.

## Modifications

**+458 / −8 runtime code (14 files), +408 tests (1 file).** No kernel changes.

- `SGLANG_DSV41_FUSED_TAIL` (`environ.py`). The decode server requires DSpark with `SGLANG_RAGGED_VERIFY_MODE=static`: fed tails ride the uniform verify rows (`deepseek_v4_hook.py`).
- **Admission** (`disaggregation/decode.py`, `decode_schedule_batch_mixin.py`, `disaggregation/utils.py`):
  - A transferred request whose DP rank already runs decode joins the running batch.
  - Admission keeps running plus fed requests within the largest captured decode CUDA graph. A fed request holds a batch slot for ~22 steps. Without the cap, decode left its graphs and throughput fell 72% in a test with graph max batch 192 under a 200-request running cap.
  - Ranks with nothing running, short prompts, grammar requests and re-bootstrapped requests keep the extend path.
- **Verify** (`dspark_verify.py`, `dspark_worker_v2.py`):
  - The request's next prompt tokens are forced as its drafts, and those logits rows are one-hot, so the unchanged accept takes them.
  - Steps carrying fed tails use the eager accept.
  - Fed rows keep their forced accept under `SGLANG_SIMULATE_ACC_*`; otherwise simulated acceptance would replace prompt tokens.
- **Attention** (`deepseek_v4_backend.py`, `models/deepseek_v4.py`): late layers floor their SWA window at each fed tail's start. The floors live in one persistent per-request buffer that eager steps, graph capture and graph replay all read.
- **Results** (`batch_result_processor.py`, `output_streamer.py`, `managers/utils.py`, `schedule_batch.py`): the prompt part of each accepted run is committed to the KV cache but kept out of `output_ids`, streaming, throughput and accept-length metrics.
- **Engram** (`ngram_embedding_manager.py`): a fed request hashes the history ending at its tail position.

## Accuracy Tests

**GPQA diamond** (`sgl-eval`, the model's preset sampling: temperature 1.0, top_p 0.95, thinking, high effort), GB300 1P1D. The split rows also carry an experimental CUDA graph over the whole tail step that is not in either PR. Unanswered questions are generations still running at the eval timeout.

| Arm | Base | Score |
|---|---|---|
| stock PD + prefill HiCache | #45265's earlier base | 91.9% (362/394) |
| split, fused tails | same | 90.9% (358/394) |
| split, fused tails | main c1c287a4 | 90.6% (358/395) |

The GPQA runs sample at temperature 1.0, so they also exercise fed tails under non-greedy sampling.

**GSM8K** (`few_shot_gsm8k`, 400 questions, parallel 64, one GB300 node, decode DP2 + DSpark): fused 0.900, #45265's extend path 0.905 and 0.885 on two starts, stock PD 0.900.

**Greedy agreement**: 17 prompts from 8 to 131,201 tokens, 64 output tokens.
- First output tokens match the extend path within 3e-5 in logprob at 4224, 4225, 30001, 65665 and 131201 tokens.
- Mean |Δ logprob| over matched tokens, fused vs extend: 0.012-0.014, the same as stock vs extend (0.012).
- The largest |Δ logprob| is higher than between two runs of the same path: 0.45-0.61 vs 0.38-0.46. A tail spans ~22 verify steps of varying batch composition, so near-tied tokens flip more often.

**Speculative acceptance** (real, DSpark block 5, AgentX c160, one GB300 node, weighted by running requests): fused tails averaged 3.39 accepted tokens per verify step in two runs, against 3.44 for stock PD and 3.44 for #45265's extend path with `SGLANG_DSV41_TAIL_HOLD_MS=500`.

**Unit tests**: `test/registered/unit/disaggregation/test_dsv41_fused_tail.py`, 13 tests.

## Speed Tests and Profiling

**Decode cost per tail strategy** (one GB300 node). Decode DP2 with the published decode flags: cap 40 running per rank, CUDA graphs to 40, MegaMoE, DSpark block 5. Load: Poisson arrivals at 5 requests/s per rank. Each request is a cached prefix plus 5,000 new tokens, with OSL 1000. Acceptance is real; random prompts make outputs repetitive, so it is high (~5.2) in every arm. Window 60-180 s, single runs.

| Decode tail | Running per rank | Accept length | Step (median) | ITL p50 / p90 | TTFT p50 / p90 |
|---|---|---|---|---|---|
| stock PD (no tail) | 18.6 | 5.25 | 19.9 ms | 3.65 / 4.79 ms | 0.45 / 0.59 s |
| split, fused tails | 22.9 | 5.24 | 24.4 ms | 3.90 / 4.99 ms | 0.84 / 1.11 s |
| split, extend with 500 ms hold | 21.2 | 5.22 | 22.6 ms | 4.02 / 5.34 ms | 0.59 / 0.82 s |

**Burst of arrivals** (one GB300 node, decode DP2). 180 running requests per rank, then 4.8 new 64k-prefix requests/s per rank for 90 s. The metric is decode tok/s in the arrival window vs a quiet window.

| Arm | Decode throughput change | TTFT p50 |
|---|---|---|
| stock PD | +0.6% | 0.58 s |
| split, extend with 500 ms hold | −10.1%, −11.3%, −10.6% | 0.61-0.63 s |
| split, fused tails | −3.9%, −3.1% | 1.73-1.75 s |

Fused tails cost decode less than tail extends, at the price of TTFT: a tail takes ~22 verify steps. Both tables were measured on #45265's earlier base, before the admission cap was added. There the extend path also had an experimental CUDA graph over the whole tail step, which favors the hold arm. The end-to-end result at GB300 max throughput is in #45265's Speed Tests.

## Known gaps

- Steps carrying a fed tail use the eager accept instead of the in-graph (folded) accept. Moving the one-hot rows into the graph would restore it; its cost was not measured.
- The decode tail adds 0.4-1.1 s of TTFT at the measured loads.
- Stacked on #45265: rebase after it merges.
