# [Fix] attention: Pad the TileLang sparse MLA prefill output back to the padded extend batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/44262) · state: closed · merged: False

## Original PR description

Merged in #46424

## Summary

**TL;DR: This PR extends #42896's output padding to the `[1, rows, heads, dim]` layout of the TileLang sparse MLA prefill kernel, so padded extend batches on that path run instead of crashing.** #42896, now on main, pads the attention output back to the padded batch only when rows are in the output's first dimension. The TileLang kernel's output therefore keeps only the real rows, and the next layer fails on the row count. This PR pads that layout as well. Other output layouts keep main's code path: the fa3 and triton attention backends give bit-identical outputs with and without this PR.

- **Enables:** GLM-5.3-Flash on its H200 cookbook pairing (BF16 KV + TileLang) now runs with an all-to-all MoE backend (MegaMoE) or with DP attention + MTP; on main both crash within 30 s of a gsm8k run. DeepSeek-V3.2 with DeepEP and TileLang prefill runs as well.
- **Accuracy:** on setups where main crashes, gsm8k now runs to the end: **91.9%** on GLM-5.3-Flash, in line with main's default `flashmla_sparse` prefill on that setup (91.8%); **91.7%** on GLM-5.3-Flash with DP attention + MTP; **95.8%** on DeepSeek-V3.2 with DeepEP.
- **Cost:** for this layout, one copy of the output into the padded output buffer, the same copy other backends' outputs already take. Only padded extend batches reach this code, and main crashes on them with this layout. No new flags or environment variables.

## Motivation

#42896 runs attention on the real rows of a padded extend batch and then pads the output back to the batch's rows. MLP sync can pad the batch when an all-to-all MoE backend (`--moe-a2a-backend megamoe` or `deepep`) runs at attention TP > 1, or under DP attention. The padding step in `_attention_on_real_rows` (`python/sglang/srt/layers/attention/graph_utils.py`) expects rows in the output's first dimension. `tilelang_sparse_fwd` runs its kernel on `q.unsqueeze(0)` and returns `[1, rows, heads, dim]`, so the output is not padded and the next layer gets fewer rows than the batch:

- `ValueError: input tensor must be the same size as output size times world size` in the attention-TP reduce-scatter (GLM-5.3-Flash with MegaMoE);
- `ValueError: Mismatched mR.shape[0]` in the fused residual add-RMSNorm (GLM-5.3-Flash's MTP draft extend under DP attention, and DeepSeek-V3.2 with DeepEP).

v0.5.22, released on 2026-10-19, includes #42896 but not this fix.

It takes three things:
- `--dsa-prefill-backend tilelang`;
- a padded extend batch on the sparse path: on H200, one whose longest sequence is over 2,048 tokens, in the target model or in the MTP draft model;
- a batch that runs outside a captured prefill CUDA graph: by default for MLA models, any batch over 2,048 tokens, or every batch with `--cuda-graph-backend-prefill disabled`.

On ROCm, `--dsa-prefill-backend triton` (`triton_sparse_mla_fwd`) returns the same layout and takes the same new branch; we have not run it on ROCm.

GLM-5.3-Flash's H200 cookbook command uses BF16 KV with TileLang, so adding an all-to-all MoE backend, or DP attention with MTP, to it reaches this crash.

Repro (8x H200; on main every rank raises the first error above):
```bash
sglang serve --model-path zai-org/GLM-5.3-Flash --trust-remote-code --tp-size 8 --ep-size 8 \
  --moe-a2a-backend megamoe --moe-runner-backend deep_gemm --kv-cache-dtype bfloat16 \
  --dsa-prefill-backend tilelang --dsa-decode-backend tilelang --mem-fraction-static 0.70 \
  --disable-overlap-schedule --disable-shared-experts-fusion --max-running-requests 32 \
  --max-prefill-tokens 8192 --chunked-prefill-size 8192 --context-length 131072
python3 -m sglang.test.run_eval --eval-name gsm8k --num-shots 20 --num-examples 1319 --num-threads 32 \
  --max-tokens 512 --api completion
```

Our local fix (`b17da53725`) pads the token dimension and removed that crash. It also carried CPU regression coverage for the tensor/tuple result forms; please retain coverage of an auxiliary LSE result where that contract applies.

This is historical crash evidence, not a fresh GPU test of your head. Other DP2×DCP2 graph outputs remained garbled and unbisected, so eliminating this shape failure does not certify the whole DCP stack. Historical performance used simulated MTP acceptance; no stack throughput claim is made here. This generic padding fix should be evaluated independently of the ROCm DCP enablement in #44322.
