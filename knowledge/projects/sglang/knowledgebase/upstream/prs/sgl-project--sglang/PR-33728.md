# [4/N] elastic-ep: Scale at DP-attention replica granularity

[Upstream PR](https://github.com/sgl-project/sglang/pull/33728) · state: open · merged: False

## Original PR description

## Summary

This PR follows the Elastic EP CUDA graph recapture PR
[#33723](https://github.com/sgl-project/sglang/pull/33723) and removes the
scale-up topology restriction `dp_size == tp_size == ep_size`.

Scale-up now admits complete DP-attention replicas. For example, with fixed
`attn_tp_size=2`, a deployment can scale from **DP2/TP4 to DP3/TP6 to
DP4/TP8**, adding two physical EP ranks and one logical DP replica per step.

The scale API continues to use physical EP sizes. The scheduler, DP controller,
and tokenizer use the corresponding logical DP size.

## Changes

- Derive the replica width as `attn_tp_size * attn_cp_size` and track the live
  DP size as `elastic_ep_size / replica_width`.
- Size scheduler workers, DPC capacity, joiner offsets, and tokenizer routing
  in logical DP units.
- Keep scale targets and Mooncake/NIXL membership in physical EP-rank units.
- Admit and health-check complete replicas instead of individual ranks.
- Handle the newly exercised MLP synchronization, empty embedding batch, and
  DCP KV-padding paths.

## Configuration

Primary and joiner groups must use the same fixed topology:

```text
attn_tp_size
attn_cp_size
dcp_size
moe_dense_tp_size=1
```

The target EP size must be divisible by `attn_tp_size * attn_cp_size`.

## Known Limitations

- Attention TP, attention CP, and DCP sizes cannot change during scale-up.
- This PR does not negotiate topology between the primary and joiners.
- `moe_dense_tp_size == attn_tp_size` cold launch is outside this PR;
  `moe_dense_tp_size=1` remains required.
- The scale-direction and recovery limitations of the existing Elastic EP
  scale-up path are unchanged.

## Test Plan

The eight-GPU test adds one complete two-rank attention replica per step:

| Stage | Physical topology | Logical DP size |
| --- | --- | ---: |
| Launch | DP2 / TP4 / EP4 | 2 |
| First scale | DP3 / TP6 / EP6 | 3 |
| Second scale | DP4 / TP8 / EP8 | 4 |

It uses fixed `attn_tp_size=2`, `dcp_size=2`, `attn_cp_size=1`, and
`moe_dense_tp_size=1`.

```bash
python -m pytest -v -s \
  "test/manual/ep/test_elastic_scale.py::TestElasticScaleUpDP2TP4ToDP4TP8::test_scale_up_on_demand"
```

Validated results:

- Eager DP2/TP4 -> DP3/TP6 -> DP4/TP8: passed, GSM8K **63.28%**.
- FULL decode CUDA graphs on the same topology: passed, GSM8K **64.45%**.
- Existing width-one EP4/DP4 -> EP5/DP5 -> EP6/DP6: passed, GSM8K
  **64.06%**.
- Existing width-one EP4/DP4 -> EP5/DP5 with CUDA graphs: passed, GSM8K
  **62.50%**.
- Focused topology, process-group, utility, and embedding tests: **37 passed**.

The unit split is consistent at every consumer I traced. Physical EP covers the scale API and Mooncake membership; logical DP covers the scheduler, DPC and tokenizer:

- The WORLD MLP-sync all-reduce lays rows out (dp, cp, tp), so `tp0_info[:, 0]` picks one row per replica.
- `dp_gather_width()` and `dp_gather_slot()` agree.
- The DPC slots, `routed_dp_rank`, load snapshots and control fan-out all read the logical width. Local control broadcast is forced on under scaling, so `control_message_step` is 1.
- The recaptured decode-graph buffers size from the logical `dp_size`.
- `attn_tp_size` keeps its publish-time value after `dp_size` is overridden.

Three inline comments, none blocking:
1. A joiner with a different replica width passes every check and fails in the first post-scale gather, not at admission.
2. `moe_dense_tp_size=1` is listed as required but is only enforced for single-rank joiners.
3. The replica width is re-derived at nine call sites.

Two notes outside the diff:
- "Create fixed attention and DCP groups for joiners using their global rank offset" is already on main (`rank_offset` in `parallel_state.py`). Nothing here changes group creation, so the description could drop that bullet.
- #33111 (scale-down) builds its shrink `ElasticScaleUpdateReq` slots and the tokenizer's `retired_ranks` from physical EP sizes. It also still assumes `dp_size == tp_size`. Whichever of the two lands second has to convert those to DP slots, and retire whole replicas.

- julienmancuso · comment · 2026-08-18T20:12:26Z · [source](https://github.com/sgl-project/sglang/pull/33728#issuecomment-5333511044)

This physical-EP/logical-DP distinction matches the abstraction we are proposing for the Dynamo Kubernetes autoscaling target in [Dynamo DEP #13121](https://github.com/ai-dynamo/dynamo/issues/13121):

```text
replica_width = attn_tp_size * attn_cp_size
physical_ep_target = logical_size * replica_width
logical_size = physical_ep_size / replica_width
```

Keeping SGLang's native scale API in physical EP units makes sense. Could SGLang also expose the resolved mapping as machine-readable status or capabilities—for example `logical_dp_size`, `replica_width`, target granularity, effective/max physical EP size, and a fixed-topology/configuration fingerprint?

That would let an external orchestrator validate targets and launch complete compatible joiner cohorts without duplicating SGLang's topology arithmetic or inferring it from CLI flags. It would also give a clear error boundary when the requested logical target is not representable.

The broader orchestrator lifecycle discussion is in [#35376](https://github.com/sgl-project/sglang/issues/35376).

A joiner whose replica width differs from the primary's passes every check here and in `handle_elastic_ep`.

Example: `--tp 2 --dp 2 --dcp-size 1` (attn_tp 1) joining a `--tp 4 --dp 2` primary (attn_tp 2) at offset 4, target 6:
- Both sides satisfy `live_dp_size * attn_replica_size == effective_ep_size` in `_resolve_elastic_world_dp_size`.
- The MLP-sync all-reduce has the same numel on both sides: 3×2 rows on the primary, 6×1 on the joiner.
- But the primary reads 3 DP slots and the joiner reads 6. `global_num_tokens`, and with it the size of the DP gather buffer, then differ across WORLD, so the first post-scale forward hangs or mixes rows.

`ScaleCohort` already carries `cuda_graph_enabled` for exactly this kind of mismatch, and the primary rejects it in `waiting_for_cohort` via `fail_scale`. Could it also carry `attn_tp_size` (and `attn_cp_size`)? A mismatched cohort would then fail with a clear error, and the "no topology negotiation" limitation becomes a checked one.
