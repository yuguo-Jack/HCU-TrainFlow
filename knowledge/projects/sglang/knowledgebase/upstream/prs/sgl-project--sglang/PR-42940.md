# [LoRA] Support GPT-OSS MXFP4 experts with Marlin

[Upstream PR](https://github.com/sgl-project/sglang/pull/42940) · state: closed · merged: False

## Original PR description

## Motivation

`openai/gpt-oss-20b` cannot currently use expert LoRA through the Marlin MXFP4 path: the LoRA wrapper rejects `Mxfp4MoEMethod`. Allowing the type alone is insufficient because the existing Marlin LoRA runner assumes ordinary SiLU, unpadded dimensions, and a different accumulation mode.

This adds expert LoRA while keeping the base expert weights in MXFP4. Attention and LM-head adapters remain enabled.

## Modifications

- Expose the existing Marlin quant-info builder from `Mxfp4MoEMethod`.
- Keep adapter gate/up rows in the split order used by Marlin's repacked weights.
- Apply GPT-OSS's clamped, alpha-scaled SwiGLU between the gate/up and down LoRA updates.
- Remove tile padding before applying adapters, then restore it for the base GEMMs.
- Use the stock MXFP4 runner's FP32 split-K reduction instead of BF16 atomics. Without this, even zero-adapter results differ from the base runner.
- Allocate LoRA CUDA-graph metadata on the backend's device without assuming quant info exposes an unpacked `w13_weight`.
- Reject TP layouts whose logical intermediate shard is not a multiple of 32. The checkpoint loader shards MXFP4 groups differently from LoRA in those layouts.

Example:

```bash
python -m sglang.launch_server \
  --model-path openai/gpt-oss-20b \
  --dtype bfloat16 --tp-size 1 --moe-runner-backend marlin \
  --enable-lora --lora-target-modules all --max-lora-rank 32
```

## Accuracy Tests

Added a GPU regression test covering padded hidden/intermediate dimensions, GPT-OSS activation clipping, expert biases, two nonzero adapters, and CUDA-graph buffer initialization.

H200 results:

- Zero-adapter runner output matches the stock MXFP4 runner exactly.
- Nonzero-adapter relative L2 error against a dequantized reference is below 0.8%.
- [Spindle's integration draft](https://github.com/modal-projects/spindle/pull/33) uses its Miles backend to train two rank-32 clients for two optimizer updates each, then exported and published three versions per client. The MXFP4 server loaded all six versions and generated 16 tokens per request.
- Zeroing only the trained expert LoRA B tensors changes input-token log-probabilities by up to 0.276, confirming expert updates are used.
- Against the existing BF16 serving implementation with the same trained adapters, mean absolute input-token log-probability differences are 0.0153 / 0.0176; maxima are 0.0482 / 0.0604.

GPU validation uses a [backport onto Spindle's pinned SGLang revision](https://github.com/modal-projects/sglang/compare/d050d06437d96196fc68d5b4e5c246408790d537...9e565a1d757998d4e9ca7d867a33c5e97cfebbdf). The numerical runner changes are the same; the older revision also needs logical dimensions when allocating its intermediate CUDA-graph buffers. Upstream-head CI has not been run. Full-model validation passes with decode CUDA graphs enabled (captured batch sizes 1–32), a 64K server context setting, and eight adapter slots. The validation prompts are 12/14 tokens with 16 generated tokens; this is not a 64K-sequence test.

With graphs enabled, mean absolute trainer-versus-sampler input-token log-probability differences are 0.0146 / 0.0156 (maxima 0.0831 / 0.0453). Mixed-adapter batches compared with same-sized single-adapter batches have mean differences 0.0121 / 0.0254 and maxima 0.0447 / 0.1078. The existing BF16 path is batch-invariant for this comparison; the MXFP4 path is not. Unadapted MXFP4 single-versus-batched requests also differ (maxima 0.0478 / 0.0616).

The tested inference topology is TP1 on one H200 with BF16 activations and MXFP4 expert weights. GPT-OSS TP4/TP8 are intentionally rejected by the new shard check; they need matching checkpoint/adapter sharding work. This is a short functional validation, not a model-quality evaluation.

## Speed Tests and Profiling

No throughput benchmark. SGLang reports 14.00 GiB of model weight memory for the original MXFP4 checkpoint. Batch composition produces small numerical differences in the Marlin path; these results do not claim bitwise batch invariance.
