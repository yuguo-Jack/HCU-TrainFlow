# [AMD] gfx950 small-batch MoE: expert-count gate for the small sort and FP8 block-scale small-M kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/41982) · state: closed · merged: True

## Original PR description

## Motivation

Qwen3.5-397B-A17B-FP8 on MI355X is slower than B200 at low concurrency in the AgentX benchmark ([InferenceX PR #3602](https://github.com/SemiAnalysisAI/InferenceX/pull/3602)). One factor is the MoE sort from #36559: past its compact range, its distributed kernel scans every 64-expert chunk per pair, so with Qwen3.5's 513 experts it is slower than AITER's sort for mid-size decode batches (6 to 23 tokens). At TP8 with 16 verify tokens, going back to AITER's sort saves 1.7 ms per decode cycle.

This PR does two things:

1. Fix the slowdown: past the compact range, #36559's distributed kernel is only used up to 256 experts, and larger models go back to AITER. MiniMax-M3 (129 experts), which the kernel was written for, keeps it because it is faster there.
2. Add FP8 block-scale support to the #40204 small-M MoE kernel, which needs no sort and is much faster at small batches but only supported MXFP4.

With this PR, the interactivity improves by about 20% at concurrency 1 and 4.

## Modifications

- `moe_sorting_small.py`: past the compact kernel's range (`min(64, 2 * block_size)` (token, expert) pairs), the distributed kernel only runs for up to 256 experts; above that, the sort and the fused MXFP8 quantization go back to AITER (+13 / -3).
- `smallm_moe.hip`: `p1_body` / `p2_body` take an `F8` template flag. Shuffled FP8 weights have the same byte layout as fp4x2, so the load path is shared. e4m3 is converted to bf16 at scale 1.0 and each 128x128 block's fp32 scale is applied to the partial sum (`cvt_scalef32_pk_bf16_fp8` only applies the scale's exponent). New kernels cover TP4 (intermediate 256) and TP8 (intermediate 128); the MXFP4 kernels are unchanged.
- `smallm_moe_gfx950/__init__.py`: takes the FP8 path for shuffled `float8_e4m3fn` `w13` / `w2` with contiguous fp32 block scales, up to 20 tokens at TP4 and 48 at TP8. `SGLANG_ROCM_SMALLM_MOE=0` still turns the kernel off.
- `moe_runner/aiter.py`: passes `w13_scale` / `w2_scale` to `smallm_moe_supported` (+2 lines).
- Tests (MI35x suite): `TestSmallMMoeFp8Gfx950` checks both shapes against a dequantized reference at 1 / 3 / 8 tokens and the cap, and that cap+1, per-channel or non-contiguous scales, and unshuffled weights fall back. New `test_moe_sorting_small.py` compares the sort and the fused MXFP8 quant with AITER on the compact path (Qwen3.5 shape) and the distributed path (MiniMax-M3 shape, 13 to 51 tokens), and checks the fallback at 513 experts.

## Accuracy Tests

All runs use image `rocm/sgl-dev:v0.5.20-rocm720-mi35x-20260927` (same image as `lmsysorg/sglang-rocm` with that tag), InferenceX recipe flags, GSM8K 1319 questions.

| Model | Setup | Baseline | This PR |
|---|---|---:|---:|
| `Qwen/Qwen3.5-397B-A17B-FP8` | TP4, real draft acceptance, `sglang.test.few_shot_gsm8k` | 0.933 | 0.941 |
| `amd/Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2` (sort change) | TP2, lm-eval 5-shot, thinking off | 0.977 | 0.979 |

The FP8 kernel's rel L2 against the dequantized reference is at most 7.4e-4 over 5 seeds in the unit test. The sort output matches AITER's layout in every path, so the sort change only affects speed.

### AgentX benchmark

Setup:

- Hardware: MI355X, TP4.
- Model and recipe: `Qwen/Qwen3.5-397B-A17B-FP8` with the InferenceX recipe `qwen3.5-fp8-mi355x-sglang-agentic`, image `rocm/sgl-dev:v0.5.20-rocm720-mi35x-20260927`.
- Server flags: as in the recipe. FP8 KV cache, EAGLE 3 / 1 / 4 with simulated acceptance 3.39, admission and decode CUDA graph batch at 2x concurrency.
- Client: the CI AgentX command, `aiperf profile --scenario inferencex-agentx-mvp` on `semianalysis_cc_traces_weka_062126_256k`, 3600 s per run.
- Order: one run at a time on the same GPUs (this PR c1, baseline c1, baseline c4, this PR c4).

Baseline is the image as shipped: AITER's FP8 MoE with #36559's sort (`SGLANG_ROCM_SMALLM_MOE=0`). With this PR, every decode batch at these concurrencies runs the FP8 small-M kernel and skips the sort, so the gain here comes from the kernel.
