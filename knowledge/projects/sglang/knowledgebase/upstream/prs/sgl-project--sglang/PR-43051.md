# [AMD] Add SGLANG_KV_CACHE_FAKE_QUANT=mxfp4 for KV-cache quantization accuracy studies

[Upstream PR](https://github.com/sgl-project/sglang/pull/43051) · state: closed · merged: False

## Original PR description

## Motivation

The LMSYS NVFP4 KV-cache post (2026-09-16) measured NVFP4 KV accuracy on NVIDIA hardware. We want the same measurement for **MXFP4 KV cache on AMD** before anyone writes FP4 attention kernels for it. This PR adds an opt-in **fake-quant (QDQ)** mode. It keeps a BF16 KV cache, but every value stored in it is first rounded to the MXFP4 grid. This gives the exact MXFP4 numerical error while reusing the existing attention kernels.

## Modifications

- `environ.py`: new `SGLANG_KV_CACHE_FAKE_QUANT` (default `""` = off). The only supported value is `mxfp4`; any other value raises at import time.
- `layers/radix_attention.py`: `RadixAttention.forward` dispatches to `_forward_kv_fake_quant` when the flag is set. The original body is now `_forward` and is unchanged.
  - The QDQ is AMD Quark's `qdq_mxfp4(x, "even")`: blocks of 32 along `head_dim`, an E8M0 scale per block ("even" scale rounding), and round-to-nearest-even onto E2M1. K is quantized after RoPE. The QDQ can be captured in a CUDA graph.
  - **Semantics match real quantized-KV kernels: the current chunk attends to its raw K/V, and every cache read sees MXFP4.**
    - Decode: the QDQ'd K/V are written to the cache, and attention reads them from there.
    - Extend: the backend runs normally with raw K/V (some backends read the current chunk back from the cache). The chunk's cache slots are then overwritten with the QDQ values, so later chunks and decode read MXFP4.
  - The hook lives at the `RadixAttention` level, not inside `set_kv_buffer`. This keeps it independent of the attention backend's various cache-write paths (e.g. aiter's fused or shuffled layouts).
  - Requires a BF16/FP16 cache (`--kv-cache-dtype auto`); this is asserted. Quark is imported only when the flag is set. Layers without a KV cache (linear-attention/GDN, cross-attention) and idle batches are left untouched.
- `benchmark/kv_cache_fake_quant/README_zh.md`: a Chinese write-up of the method, the per-stage semantics, the correctness checks, and BF16 / FP8 / MXFP4 results on Qwen3.8-27B-FP8.

Usage:
```bash
SGLANG_KV_CACHE_FAKE_QUANT=mxfp4 python -m sglang.launch_server --model-path <model> --kv-cache-dtype auto ...
```

## Accuracy Tests

**QDQ kernel.** `qdq_mxfp4_hip` matches a pure-PyTorch reference (even scale + RNE) bit-for-bit on a random 8192×2×256 BF16 tensor.

**Semantics check.** Qwen3.8-27B-FP8, MI355X, 1067-token prompt, greedy decoding, radix cache disabled. The table shows the logprobs of the first 3 output tokens.

| KV | chunked_prefill_size | tok1 | tok2 | tok3 |
|---|---|---|---|---|
| BF16 | 8192 | -0.02455 | -1.00951 | -0.25823 |
| BF16 | 128 | -0.02455 | -1.00951 | -0.25823 |
| MXFP4 | 8192 | **-0.02455** | -1.18503 | -0.37080 |
| MXFP4 | 128 | -0.02232 | -1.10742 | -0.32116 |

- Single-chunk prefill: token 1 is identical to BF16, which shows the current chunk sees raw K/V. Decode tokens differ, which shows the cache holds MXFP4.
- Chunked prefill: token 1 differs too, because the prefix is read back as MXFP4.

**Evals.** Qwen3.8-27B-FP8, MI355X, TP1. Sampling and server flags follow the LMSYS post: temperature 0.6, top_p 0.95, top_k 20, radix cache disabled, max 81920 new tokens. `±` is the standard error over repeats.

| KV | GSM8K (8-shot) | GPQA-Diamond pass@1 (×4) | AIME25 pass@1 (×8, xhigh) |
|---|---|---|---|
| BF16 | 97.33 | 89.77 ± 0.73 | 95.00 ± 1.41 |
| MXFP4 (fake quant) | 97.79 | 90.53 ± 0.13 | 94.58 ± 0.88 |

MXFP4 is within noise of BF16 on all three. Mean reasoning length is about 7% longer on GPQA and about 11% longer on AIME25 with MXFP4 KV.

These results were produced on the v0.5.21 release branch, where the same patch applies. On `main` I verified import and dispatch only (flag off, `mxfp4`, invalid value) and the QDQ op itself. I did not rerun the end-to-end evals.

## Speed Tests and Profiling

Off by default, and there is no change when the flag is unset. This is an accuracy-study tool. When the flag is on, there is one QDQ per K/V per layer, plus one extra `set_kv_buffer` per layer during extend. There is no memory or speed benefit.
