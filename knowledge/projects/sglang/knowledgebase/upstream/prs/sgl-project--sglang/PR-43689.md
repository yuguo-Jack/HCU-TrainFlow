# [Feat] sgl-router: Render Qwen3.8 (Max, 27B, Flash-Next) through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/43689) · state: closed · merged: True

## Original PR description

> [!NOTE]
> **Stack 3/3**, merge in order: #43625 (GLM-5.3) → #43608 (Kimi-K3) → #43689 (Qwen3.8). This PR is based on #43608 (`kan/sgl-router-kimi-k3`), so its diff shows only the Qwen3.8 commits. After the PRs below merge it gets rebased onto `main`.

Adds Qwen3.8 to sglang-processor and serves it from sgl-router end to end: Qwen3.8-Max (`Qwen/Qwen3.8-2.4T-A95B`), Qwen3.8-27B and Qwen3.8-Flash-Next. With the cookbook's `qwen3` and `qwen3_coder` parsers, the router renders, tokenizes and parses every text chat and talks to the engine through `/generate`.

## Modifications

- **Render:** `ChatFormatter::Qwen38` (`render/models/qwen38.rs`), picked in `from_tokenizer_config` by its template. SGLang renders Qwen3.8 with `apply_chat_template` (no encoding spec), so the processor builds the template context `_process_messages` and `_apply_jinja_template` build and renders it with Dynamo's Jinja formatter:
  - messages, tools and tool calls as the pydantic dumps give them (`Tool.type` as sent, `Tool`'s null `defer_loading`, `FunctionResponse`'s null `arguments`);
  - content in the template's content format: Max's text-only template gets strings (text parts joined with spaces), the vision template of 27B and Flash-Next gets parts lists, which it concatenates;
  - kwargs over the request effort, then the server's default kwargs; reserved kwargs and `documents` are checked after the defaults merge in, as for GLM-5.3.

  Where Dynamo departs from Python, the processor fails rather than render differently, so hosts leave the chat to the engine: a later system turn (Dynamo demotes it, the template raises), media, text whose `trim` differs (U+001C..U+001F), and numbers serde_json prints unlike Python.
- **Parsing:**
  - `think/models/qwen3.rs`: `Qwen3Detector`, the base detector over `<think>` with `<tool_call>` ending the reasoning.
  - `tool_call/models/qwen3_coder.rs`: `Qwen3CoderDetector`, streaming and one-shot. Argument values are typed by the request's tool schemas as `_convert_param_value` types them (`int()`, `float()`, `json.loads`, and the JSON-like subset of `ast.literal_eval`). Tool detectors now take the request's tools rather than their names, and the `parser` feature's stream gives an id and name only to a named call item, as Python does.
  - **sglang-server**, whose parser registry these ports also serve: `qwen3` starts in reasoning when the prompt ends in a prefilled `<think>` (as it already did for DeepSeek-V4), and `parallel_tool_calls=false` keeps every delta of the first call, which `qwen3_coder` streams as a name and argument fragments (the response processor too).
  - `ChatModel.reasoning_toggle`: the template's toggle (`enable_thinking`, on by default for all three checkpoints), which `_get_reasoning_from_request` reads. The template prefills `<think>\n`, so this decides `require_reasoning` and the forced reasoning split.
- **Router:** renders Qwen3.8 through the processor, so every text chat forwards `input_ids` (`AllText`), and with the cookbook's parsers lowers it to `/generate`. `required`, named and strict tool choices, media and `sglext` fields such as `return_meta_info` keep the engine's route.

Left as known differences, where Python itself fails or the case is out of reach:
- tool argument literals `json.dumps` cannot serialize (sets, bytes, complex numbers) stay strings; Python drops the call in unary responses and raises mid-stream;
- `\N{...}` escapes and lone surrogates in literal-typed arguments stay strings.

## Checks

- **Render:** 136 cases per checkpoint match SGLang's prompt text and token ids at the pinned revisions; 5 per checkpoint are `known_gap`s the processor leaves to the engine (trim separators, exponent floats, huge integers).
- **Parsers (fixtures from SGLang's Python):** `reasoning_parity/qwen3.json` (88 cases) and `tool_parity/qwen3_coder.json` (45 outputs, 50 chunkings, covering schema typing, Unicode decimal digits, Python-literal fallbacks including parenthesized signed numbers, the 200-bracket nesting limit and key merging, truncation, marker splits). A throwaway randomized comparison also matched Python on 60,000 typed values and 50,000 chunked streams (apart from an empty function name, which is served identically).
- **OpenAI layer:** `openai_parity/qwen3.8-27b.json`, 13 cases recorded from `OpenAIServingChat` against a live Qwen3.8-27B engine (thinking on/off/effort, truncation, continuation, tools with and without thinking, typed arguments, unary and streaming, `tool_choice: none`, and `required` left to the engine); generic OpenAI-layer behavior is covered by the other models' fixtures and the live run below: the `/generate` body and the OpenAI response match.
- **Live, Qwen3.8-27B on one B300** (cookbook GB300 BF16 cell with its default overlays, plus `--log-requests-level 3`); each chat was sent to the engine directly and through the real `sgl-router` binary, flushing the cache before each:

  | Check | Result |
  |---|---|
  | Router chats served via `/generate` | 50 / 61 |
  | Identical engine-side `GenerateReqInput` on those | 50 / 50 |
  | Identical responses on those | 48 / 50 |
  | GSM8K (1314, chat API, `reasoning_effort=low`, greedy) | engine 0.977, router 0.979, every router request via `/generate` |

  The two differing responses are a seeded-sampling request that also varies between runs on the engine alone, and an `n=2` stream whose choices interleave differently with the same per-choice text. The 11 chats on the engine's route are `required`/named/strict tools, an image, and rejected requests, which return the same 400 on both paths.
- `cargo test`, `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` pass for `rust/` and `experimental/sgl-router`, as do `cargo check -p sglang-processor --no-default-features --features render,tokenizer` and `--features render,openai`.
