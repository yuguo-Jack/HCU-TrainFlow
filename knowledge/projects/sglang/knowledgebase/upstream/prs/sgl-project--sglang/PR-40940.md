# [bugfix] chunked prefill req counted as a new waiting req in calculating batch_is_full

## Motivation
In Prefill procedure, chunked reqs, 


Under the combination of chunked prefill + DP attention, when max_running_requests > 1 and chunked_prefill_size is internally divided by dp_size along the dp-attention path, the per-rank running batch gets stuck at max_running_requests - 1 in steady state: 
- Each DP rank is expected to admit up to max_running_requests // dp_size requests in flight (e.g., 16). 
- In practice, each DP rank holds at most 15 (or max - 1) consistently. 
- The under-utilization persists through the entire steady state; it only briefly recovers when a request finishes and triggers a batch shrink. 
- Reducing chunked_prefill_size or disabling chunked prefill avoids the bug. 
- Increasing concurrency or shortening output_len does not help — as long as "a chunked_req is in flight" AND "the waiting queue is non-empty" both hold, the bug fires.

The admission check len(adder.can_run_list) >= get_num_allocatable_reqs(...) compares two quantities with mismatched scopes. adder.can_run_list includes the in-flight chunked request that add_chunked_req just appended for its next chunk — that request already holds a req_to_token_pool row from its initial prefill, so appending it here is bookkeeping, not a new admission. get_num_allocatable_reqs() counts how many new requests can fit; it uses pp_max_micro_batch_size - running_bs and req_to_token_pool.available_size(), both of which have already subtracted the chunked request's row. 

When bs = max - 1 with a chunked request in flight, both sides evaluate to 1, so 1 >= 1 flips batch_is_full to True and breaks out of the admission loop before any waiting request is examined. Since batch_is_full only resets when a request finishes, the running batch is pinned at max - 1 for the rest of steady state.

As an example, in Ascend 910 NPU environment, TP8+DP8+DP Attention+EP8, Qwen3.5 122B A10B, chunked-refill-size 32768, adjust men-fraction-static and schedule-conservativeness to ensure max-request 16 per rank. Sending 128 reqs of (2k to 32k) by bench serving will trigger this problem.

## Modifications
Admission gate in _get_new_batch_prefill_raw: track whether add_chunked_req appended to can_run_list (via length diff) and subtract that count from the left side of the gate.

File: `python/sglang/srt/managers/scheduler.py` · line None

has_chunked is assigned only when self.chunked_req is not None, but the waiting-queue loop uses it unconditionally. On the first ordinary request, self.chunked_req is None, so the admission check raises UnboundLocalError. This also affects configurations with chunked prefill disabled. Initialize has_chunked = 0 before the branch.

- WayneLuo-HW · comment · 2026-09-24T03:21:59Z · [source](https://github.com/sgl-project/sglang/pull/40940#discussion_r4089463731)

File: `python/sglang/srt/managers/scheduler.py` · line None

get_num_allocatable_reqs() returns the minimum of the remaining PP microbatch capacity and the available request-pool slots. A continuing chunked request reuses its pool slot, but still occupies microbatch capacity. Subtracting it from the count used against both limits can therefore admit an extra waiting request. For example, with a microbatch limit of 2, 1 running request, 1 chunked request completing its final prefill chunk, and sufficient free pool slots, the new condition evaluates to 1 - 1 >= 1, which is false. Another request is admitted, bringing the total to 3. Check total microbatch occupancy separately from requests requiring new pool slots.
