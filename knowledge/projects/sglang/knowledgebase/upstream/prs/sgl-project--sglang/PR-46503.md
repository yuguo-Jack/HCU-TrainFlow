# [Feat] spec: Add a topk=1 chain target-only sampling kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/46503) · state: open · merged: False

## Original PR description

Related: #12562 (Task 2), #45616, #45704, #34140

## Motivation

Part of #12562, which asks for a more efficient kernel for the `topk=1` special
case of target-only speculative sampling.

The target-only tree verify kernel never needs a real draft distribution in that
case. Every caller passes `torch.zeros_like(target_probs)`, a
`[bs, num_draft_tokens, vocab]` fp32 buffer allocated and zeroed on every verify
step, even when the draft tree degenerates to a linear chain with no siblings.
With `draft_probs` all-zero at `topk == 1`, rejection sampling degenerates to
plain residual resampling: the buffer carries no information, yet the kernel
still reads all of it back. At bs 32, 16 draft tokens and a 152064 vocab that is
297 MiB per step.

A chain has no siblings to walk. It needs one top-down pass with a running
residual, which a single launch can do with the rejected token masked in
registers, so the buffer never has to exist.

The tree kernel keeps its `draft_probs` parameter; dropping it is #45616 / Task 1.
The HIP greedy gate and the `dflash_utils` ROCm binding belong to #45704 and
#34140. Where the chain op is unavailable, routing falls back to the tree path.

## Modifications

- `kernels/ops/speculative/reject_sampling.py`: new
  `speculative_sampling_target_only_chain_kernel` plus the wrapper
  `chain_speculative_sampling_target_only_triton`. One Triton launch runs the
  `topk=1` chain verify and the residual resampling. The rejected token is kept
  in registers and masked inline in both final passes, which is element by
  element what the tree kernel achieves by writing `target_probs[rejected]` into
  `draft_probs` and reading `relu(q - p)` back. There is no `draft_probs`
  argument, so callers allocate nothing. `BLOCK_V` is raised to 8192 in this
  kernel only; the tree wrappers keep 4096. The kernel's fallback path compares
  `found == 0` explicitly, because Triton promotes `found` to an int32 scalar
  inside a runtime `if`, where `not found` asks for a bitcast to int1 and fails
  to compile.
- `kernels/ops/speculative/__init__.py`: register the new op in
  `_TRITON_KERNELS`.
- `kernels/ops/speculative/verify_sampling.py`: export the chain op on CUDA and
  MUSA. The NPU kernel still takes `draft_probs`, so its entry is `None` and
  routing leaves NPU on the tree path.
- `srt/speculative/eagle_utils.py`: route `tree_topk == 1` with
  `use_rejection_sampling` off to the chain op and pass `draft_probs=None`
  instead of allocating the buffer.
- `srt/speculative/dflash_utils.py`: DFlash is always `topk == 1`, so its
  sampling verify prefers the chain op, with the tree kernel plus zeros kept as
  a fallback.
- `test/registered/kernels/ops/speculative/test_speculative_sampling.py`: seven
  new cases, and the eagle and DFlash graph-pool tests patch the new kernel.

Seven files, +490 / -21.

## Accuracy Tests

Setup: one RTX 3080 Ti (sm_86, 80 SMs, 12 GB), torch 2.14.1+cu130, CUDA 13.0,
Python 3.12.3, `sglang-kernel` 0.4.10, `SGLANG_JIT_CACHE_DIR` per build.
Kernel tests (`pytest test/registered/kernels/ops/speculative/test_speculative_sampling.py`):

```
this PR   14 passed  (7 pre-existing + 7 new)
```

The new cases cover zero-mass draft with `coin == 0` and `threshold == 0`,
zero-mass with the default threshold, the interior boundary
`coin == p / threshold_acc` rejected under strict `<`, the lower endpoint
`coin == 0` accepted, the upper endpoint `coin -> 1.0` accepted and then sampled
from the next row, and two bitwise comparisons against the CUDA tree kernel via
`torch.equal`.

Randomized equivalence against the tree path. 200 cases over `bs`, chain length,
`vocab`, `threshold_single` and `threshold_acc`, seeded, replayed on both
kernels with identical coins: **200 of 200 cases are bit-identical**, 718 requests
in total.

A 500-case sweep recomputes every differing row in `float64`, using the
semantics both kernels actually implement: sample from row `accept_num`, mask
the *rejected* draft, which lives in slot `accept_num + 1` because slot 0 is the
root, and mask nothing when every draft was accepted (`k == ndt - 1`). 499 cases
are bit-identical. The single case that differs produces one differing row.

| seed | configuration | slot | accept_num | float64 ref | old | new | margin at old | p_old |
| ---: | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 251 | bs=8 ndt=16 v=151936 | 64 | 0 | 88173 | 88174 | **88173** | 1.94e-06 | 1.89e-06 |

That row is a rejection case (`accept_num = 0` of 15 drafts), and the new kernel
agrees with the `float64` reference while the tree path does not. The competing
token probabilities are `1.89e-06` and `6.05e-07`, so this is the float32
last-ulp boundary, not a semantic difference.

`margin_sweep.py --selftest` pins the reference rules on hand-computed CPU cases
with no GPU and no kernels: the resampling row, the mask slot, the all-accepted
case, and a hard error when a 1-D buffer is passed in.

The mask itself is not a semantic change. A synthetic case (`bs=1, ndt=2,
vocab=8`, target row `[0.70, 0.10, ...]`, draft token 0 rejected,
`coin_final = 0.10`) shows the tree kernel with zero `draft_probs` refusing to
re-pick the rejected token as well: priming `draft_probs[row][rejected] = p`
zeroes its residual and reproduces the old output bit for bit. The chain kernel
implements that existing behaviour in registers.

Caller level. Half of this change is routing, so kernel-only tests would miss it.
A harness runs the real `eagle_sample` and the real DFlash verify twice on
identical inputs and identical coins: once with the chain op available, once with
it patched to `None` so routing falls back to
`tree_speculative_sampling_target_only` plus `torch.zeros_like`, which is pre-PR
behaviour.

Over seeds 0 to 49 (100 cases, 50 seeds across eagle and DFlash) every case is
identical, 182 tokens accepted. Seeds 50 to 99 (another 100 cases) turn up four
cases that differ:

| kind | seed | differing tensor | index | old | new |
| :--- | ---: | :--- | ---: | ---: | ---: |
| eagle | 52 | `predict` | 0 | 84128 | 84127 |
| dflash | 52 | bonus token | 0 | 84128 | 84127 |
| eagle | 64 | `predict` | 12 | 129071 | 129072 |
| dflash | 64 | bonus token | 6 | 129071 | 129072 |

Accept lengths, `accept_index` and `correct_len` agree element for element in all
four, so only the final bonus token moves, by one id, on adjacent tokens. These
are the same float32 tie class as the row above.

Running the `float64` reference on these four settles which side is right: a spy
around the chain kernel captures the exact `target_probs` (already temperature and
top-k / top-p normalised), `candidates` and final coin the kernel was fed, and the
selection is recomputed in `float64` with the same rules.

```
rows_total                   4
rows_new_matches_float64     4
rows_old_matches_float64     0
```

All four rows have `accept_num = 0`, i.e. the first draft was rejected and the
rejected draft in slot 1 is the masked one, so these rows also check that the mask
covers the rejected draft and not the root token. Every difference observed in
this PR is a float32 tie on which the new kernel agrees with the `float64`
reference and the tree path does not. Both kernels are float32 and the side they
land on depends on the accumulation order, so this is a statement about the ties
above rather than about accuracy in general.

Not measured:

- End-to-end serving throughput or latency with a real EAGLE or DFlash model.
- Any other GPU, including datacenter parts. Everything here is from one
  RTX 3080 Ti.
- NPU hardware. That path keeps the tree kernel unchanged.

## Speed Tests and Profiling

GPU: one RTX 3080 Ti (sm_86, 80 SMs), torch 2.14.1+cu130, CUDA 13.0, 50 warmup and
300 timed iterations per variant, p50 reported.

Method. Three variants separate the allocation from the kernel work, and the
variants are interleaved with the order rotated every iteration so thermal drift
hits all of them equally. Every timed call sits between CUDA events after a
`torch.cuda._sleep` that keeps the GPU busy while the host enqueues the call, so
the interval is GPU time without launch gaps. Outputs are compared before
anything is timed: identical across variants in all 18 configurations.

- old step: `torch.zeros_like(target_probs)` plus the tree kernel, which is what
  `eagle_sample` and DFlash verify run on every verify step
- old kernel: the tree kernel alone, with one zero buffer reused across calls
- new step: this PR, the chain kernel with `draft_probs=None`

The 18-configuration grid was run end to end three times; the per-row step
speedup moved by at most 4.5% between runs. The table quotes the last run and
all three raw files are published. One baseline sample in an earlier pass read
29.7 us against 24.6 us elsewhere; repeated measurement and the later runs
returned 24.6 us.

- The verify step is 1.07x to 4.74x faster at p50, and every one of the 18
  shapes is ahead of the old step. The headline row (`vocab=152064, bs=32,
  ndt=16`) goes 471.0 us to 99.3 us: p10 470.02 / p50 471.04 / p90 472.06
  against 98.30 / 99.33 / 110.59.
- Memory: `torch.cuda.max_memory_allocated` grew by the buffer size for every
  old step and by 0 bytes for every new step, 0.5 MiB to 297 MiB per verify step
  in this grid.
- The gain grows with batch size. Both wrappers launch `grid = (batch_size,)`,
  so at `bs=1` the whole GPU runs a single CTA that cannot saturate bandwidth;
  the `draft_probs` read this PR removes was never the bottleneck there, while
  the per-block work sits on the only critical path available. That gives
  1.07x-1.37x at `bs=1`, 1.24x-2.14x at `bs=8` and 2.04x-4.74x at `bs=32`.
- `old step` and `old kernel` measure within 1% of each other, so on this GPU the
  allocation is already amortised by PyTorch's caching allocator. The win is
  bandwidth, not allocation.

`BLOCK_V` is raised to 8192 in the chain wrapper. At `vocab=152064`, 4096 means
38 serialized block reductions per pass, 76 in total, with a single CTA and
nothing to hide them behind. A sweep at `bs=1`, chain length 4, 8 and 16:

```
times in microseconds, p50, new step
 ndt | BV=4096 | BV=8192 | BV=16384 | BV=32768
   4 |   111.6 |    91.1 |    103.4 |    180.2
   8 |   107.5 |    88.1 |    101.4 |    185.3
  16 |    72.7 |    63.5 |     73.7 |    300.0
```

`16384` loses the gain and `32768` spills registers down to 0.29x. The kernel
ships 8192; at 4096 two of these three shapes are slower than the old path
(0.89x and 0.88x), so the tiling change is what puts all 18 shapes ahead.

The measurement harness follows the three-variant split, interleaved rotation,
input digest and caller-level A/B of the harness published for #45616's Task 1:
https://gist.github.com/Eliaaazzz/a1fe153a87446b6d7b3b23f5e9be24a5 . Every
number above is backed by raw artifacts -- the three benchmark passes, the 200-
and 500-case sweeps with their float64 verdicts, the caller-level sweep and the
full run log -- which are available on request. The harness scripts that
produced them are published at
https://gist.github.com/xingfendy/085ce2e70f842018f5099f48517f7b50 .
