# [Fix] [AMD] mhc: Enable AITER kernels on gfx942

[Upstream PR](https://github.com/sgl-project/sglang/pull/44544) · state: open · merged: False

## Original PR description

## Motivation

aiter mHC pre/post is gated to gfx95. On gfx942 (MI300X / MI325X) the fused mHC post/pre boundary therefore selects `mhc_fused_post_pre`, whose TileLang kernel uses `tl.get_lane_idx()`. TileLang's HIP codegen cannot lower that op on gfx942, so CUDA-graph capture dies with:

```
tvm.error.InternalError: Unresolved call Op(tl.get_lane_idx)
Exception: Capture cuda graph failed: Unresolved call Op(tl.get_lane_idx)
```

aiter's mHC kernels do run on gfx942 with their default config for that CU count. Using them, instead of the unfused torch fallback, is what made GLM-5.3-Flash decode on MI300X fast enough for RL rollout.

#41136 avoids the TileLang crash by turning the fused boundary off for all HIP. This PR takes the other route on gfx942: run aiter, and only skip the TileLang kernel that cannot compile there. gfx95 and gfx1250 are unchanged.

## Modifications

- `_use_aiter_mhc()` and `_is_aiter_gfx95_mhc_available()` also accept gfx942, so pre, post, and `mhc_fused_post_pre` use aiter when `SGLANG_USE_AITER=1`.
- `_is_fused_mhc_post_pre_enabled()` returns false on gfx942, after the gfx1250 early return, so the TileLang fused kernel is never chosen there.

## Accuracy Tests

MI300X, GLM-5.3-Flash BF16, TP8, aiter mHC, decode CUDA graphs. The server completes graph capture and serves. Teacher-forced logprobs against the trainer, after the separate routing-bias fix, match the previous rollout build (`train_rollout_logprob_abs_diff` 0.06–0.09 over 4 RL steps). With routing replay the gap was 0.022–0.029.

## Speed Tests and Profiling

Decode throughput, 512 output tokens per request, TP8, one MI300X node:

| Concurrency | Previous build, torch mHC | This branch, aiter mHC |
|---|---|---|
| 16 | 945 tok/s | 1031 tok/s |
| 64 | 1914 tok/s | 2349 tok/s |
| 128 | — | 3000 tok/s |

At concurrency 128 the GPU spends about 35 ms per decode step. The pure-torch mHC fallback had been the largest CPU-side cost in the previous build (about 46% of scheduler samples).

Thanks for flagging. The two are compatible.

`_is_fused_mhc_post_pre_enabled()` only gates the TileLang fallback in `apply_mhc_post_pre_boundary`. The aiter fused kernel is tried before that and is gated by `_is_aiter_gfx95_mhc_available()`, which this PR extends to gfx942. So with both PRs, gfx942 with `SGLANG_USE_AITER=1` still gets aiter pre/post and the aiter fused boundary, and without it runs the unfused sequence. Neither path reaches TileLang. #41136's HIP guard covers the gfx942 return added here.

Both PRs add their early return at the same spot after the gfx1250 branch, so whichever merges second will have a textual conflict. No need to hold this one for #41136. Once it lands I'll rebase #41136 on top, fold the gfx942 branch into the HIP guard, and update the #41136 test comment that says gfx942 has no aiter kernel.
