# [Fix] dsv41: Load MXFP4-packed Engram tables by widening them to the FP8 table

[Upstream PR](https://github.com/sgl-project/sglang/pull/47880) · state: closed · merged: False

## Original PR description

## Motivation

[nvidia/DeepSeek-V4.1-Flash-1017-NVFP4](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-1017-NVFP4) stores the two Engram lookup tables (`layers.{1,14}.engram.embed.weight`) as packed MXFP4: `uint8 [rows, 128]`, two E2M1 values per byte with the even column in the low nibble, next to the unchanged per-32 ue8m0 `.embed.scale`. SGLang allocates the table as e4m3 `[rows, 256]`, so `EngramEmbedding._load_rows` fails on the shape mismatch and the checkpoint cannot load. Everything else in the checkpoint already loads: the NVFP4 routed experts take the existing hybrid FP8 + NVFP4 path, and the DSpark draft keeps its MXFP4 experts. Keeping the table packed and decoding in the gather (as vllm-project/vllm#61530 does) would halve the table memory; that is a larger follow-up.

## Modifications

- `EngramEmbedding._load_rows`: when the loaded rows are `uint8` and the table is e4m3, widen this rank's rows into the e4m3 table instead of copying them. The widening runs in 1M-row chunks on the table's device and handles both the per-rank and the shared (row-slice) placements.
- Every E2M1 value (0, 0.5, 1, 1.5, 2, 3, 4, 6 and their negatives) is exact in e4m3 and the scale tensor is unchanged, so the dequantized table is identical to an MXFP4 decode. The lookup, staging, host-table and peer-shard paths are unchanged, and the table keeps the FP8 checkpoint's memory.

## Accuracy Tests

GB300, TP4, one node, SGLang nightly 2026-10-30 plus this change, GSM8K via sgl-eval 0.1.3 (300 questions, temperature 1, top_p 1). Both checkpoints ran back to back on the same node.

| checkpoint | plain | DSpark (block 5) | DSpark accept length |
|---|---:|---:|---:|
| nvidia/DeepSeek-V4.1-Flash-1017-NVFP4 | 98.00% | 98.33% | 3.48 |
| deepseek-ai/DeepSeek-V4.1-Flash (FP8) | 98.00% | 97.33% | 3.57 |

The logs show the hybrid FP8 + NVFP4 checkpoint detection and the `flashinfer_trtllm_routed` MoE runner for the NVFP4 checkpoint. GPU memory after load is 77.3 GB per GPU vs 99.9 GB for the FP8 checkpoint.

Load-path checks (CPU): the widened table matches a reference `decode_e2m1 * 2^e8m0` decode bit for bit, and its fp8 bytes equal torch's fp32 -> e4m3 cast. Cases: all 256 byte values with random scales, 100003 random rows across chunk boundaries, an empty shard, a row-slice destination, and 8 real 4096-row ranges of both tables. Swapping the nibble order fails the check, which confirms the low-nibble-first layout.

## Speed Tests and Profiling

Load only. Widening runs at about 3.8 GB/s on 16 CPU threads, about 6 s per TP4 rank shard of a table when the table lives in host memory.
