# [Perf] unified-memory: Stage a fused draft's draft-extend metadata once per draft cycle

[Upstream PR](https://github.com/sgl-project/sglang/pull/46386) · state: open · merged: False

## Original PR description

## Motivation

A multi-layer EAGLE draft replays one CUDA graph per draft step. When the draft is fused into the unified pool (`--enable-unified-memory`), its FlashAttention backend translates KV ids and so could neither record its draft-extend metadata in the graph nor stage it: every step's replay rebuilt the metadata eagerly first. The steps of a chain extend the same window, so all of those rebuilds produced the same tables: lengths, prefix sums, the translated full and sliding-window page tables, and the sliding-window write ids. In a traced Inkling-Small MTP run on fa4 (TP 8, SM90), the unified pool's draft-extend host time per cycle was twice the default pool's.

## Modifications

- A translating FlashAttention backend now stages the draft-extend metadata once per cycle from the cycle's plan (`layers/attention/flashattention_backend.py`). One launch fills the lengths and prefix sums; the page tables come from the plan's read table, which the first step backend builds in place and the others copy; the sliding-window write ids come from the plan, as before. A backend whose reads stay virtual has no plan table to stage from, so it reports no staging support.
- The multi-layer runner stages through an explicit `stage_draft_extend_metadata` entry (`layers/attention/base_attn_backend.py`), which Inkling's short-conv wrapper now exposes too (`layers/attention/linear/inkling_sconv_backend.py`).
- With staging available, these drafts can take the single combined draft graph, as on the default pool (unless `SGLANG_ENABLE_SINGLE_CG_DRAFT=0`).
- On a translating pool the chain stages after verify, not before it (`speculative/multi_layer_eagle_worker_v2.py`). Staging before verify would move the scheduler's write-after-read fence to the target's read end, but this pool still translates after verify: Inkling's draft graph maps its checkpoint slots through the live table, and a widened window binds its own plan. A request freed once that fence passes would unmap a slot the draft is about to write.

Tests:
- CUDA (SM90), `test/registered/unit/layers/attention/test_flashattention_graph_metadata.py`: staging fills exactly the tables the per-step rebuild did, at page sizes 1 and 128, with and without a sliding-window pool; one plan serves every step backend with one build per table; a captured step reads each cycle's staging in place, including after pages move. The staging capability for static, translating, DCP and topk > 1 backends.
- CPU, `test/registered/unit/spec/test_draft_extend_metadata_staging.py`: staging backends get one staging call per cycle and no per-step rebuild; others keep the rebuild; the wrapper stages its attention tables, then its slot indices. A unified chain is not staged before verify and keeps the draft's fence, while a static pool's chain is staged early and its replay reads checkpoint slots as staged.

## Accuracy Tests

SM90, `thinkingmachines/Inkling-Small`, TP 8, `--attention-backend fa4`, `--speculative-algorithm EAGLE --speculative-draft-model-path thinkingmachines/Inkling-Small --enable-multi-layer-eagle --speculative-num-steps 8 --speculative-eagle-topk 1 --speculative-num-draft-tokens 9 --speculative-use-rejection-sampling`, radix cache, overlap scheduler, on main `669292bacc` with this PR and the other open unified-memory PRs applied. sgl-eval GSM8K, all 1314 test questions, `--temperature 0 --max-tokens 2048`. Default pool against `--enable-unified-memory`; median accept length from the scheduler logs. The unified-memory servers ran with `SGLANG_DEBUG_POISON_POOL=1`, so a read of a never-written pool row shows up as a wrong answer.

| CUDA graphs | GSM8K (default / unified) | one pool only right (default / unified), p | accept length (default / unified) |
|---|---|---|---|
| off | 0.9543 / 0.9482 | 12 / 4, p = 0.08 | 3.88 / 3.88 |
| on | 0.9543 / 0.9543 | 9 / 9, p = 1.00 | 3.88 / 3.92 |

Neither row's difference is significant at 0.05, which does not by itself establish equivalence. An earlier run on main `259f0131c9` gave 0.9543 / 0.9521 with graphs off and 0.9551 / 0.9513 with graphs on, also not significant. The unified pool's score is equal or slightly lower in all four runs.

## Speed Tests and Profiling

Same setup on main `259f0131c9`, CUDA graphs on, with #46376 in both builds so both pools run 14 requests at once. `--enable-unified-memory` against the default pool on the same build, before and after this PR; a second default-pool server gives the run-to-run spread in parentheses.

| load | req/s gap, before / after | mean TTFT gap, before / after | mean ITL gap, before / after | decode step gap at equal batch size, before / after |
|---|---|---|---|---|
| 24 requests of 512 input / 2048 output tokens, one at a time | -12.6% / -1.3% (1.8) | +2.8% / +1.4% (0.4) | +14.9% / +1.3% (1.9) | +12.6% / +1.4% |
| 100 requests of 512 input / 4096 output tokens, concurrency 128 | -7.9% / -1.0% (1.6) | +7.3% / +1.1% (2.0) | +7.9% / +0.9% (1.3) | +8.2% / +0.7% |
| 192 requests sharing a 4096-token prefix + 128 tokens, 2048 output tokens, concurrency 192 | -7.8% / -1.2% (2.0) | +8.2% / +0.8% (3.5) | +11.3% / +1.3% (2.7) | +10.9% / +2.3% |

Before this PR the unified server logs that it cannot refresh its metadata for a combined graph and falls back to per-step draft graphs; after it, it captures the combined graph. That combined graph already samples the rejection-sampling proposal in the graph, so #46385's gain on unified fa4 does not add to this one: with both applied, unified fa4 runs this path.
