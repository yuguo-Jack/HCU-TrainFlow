# [Feat] rust-server: Let a multimodal processor check and fetch media during admission

[Upstream PR](https://github.com/sgl-project/sglang/pull/46206) · state: closed · merged: True

## Original PR description

## Motivation

The Rust frontend resolves a request's I/O-backed media on the API runtime before multimodal dispatch (`core::prefetch`), but it only knows `http(s)://`, `file://` and absolute paths. Any other string counts as inline base64, so a request naming its media by some other URI scheme (`custom://bucket/key`, for example) reaches the MM worker as "base64", fails to decode there, and the client gets a 500 (`encode failed`) rather than a 400. An external `MmProcessor` also has no way to refuse media it cannot encode (an unsupported modality, say) before the request is fetched and queued to the scheduler.

## Modifications

`MmProcessor` gains two default-off hooks, run during admission for the processor the MM pool was started with:

- `check_media(&MmData) -> Result<(), String>` refuses a request's media before any byte is fetched; `Err` is a 400.
- `fetch_media(source, modality, budget) -> Result<Option<Bytes>, MediaError>` sees each I/O-backed source before the built-in fetcher. It runs on the blocking pool and charges the request's byte budget. `Ok(None)` leaves the source to the built-in fetcher.

`CoreHandle::set_mm_processor` installs the pool's processor once, when `Runtime::spawn_mm_pool` starts the workers (after the listeners are up, before startup warmup marks the server ready). Prefetch takes it as an `Option` so every existing call site and test runs unchanged with `None`.

Behaviour changes for every Rust-mode engine, with or without an external processor:

- `is_io_source` treats every `scheme://` URI as an I/O source, scanning only a bounded 32-byte prefix (a multi-megabyte inline base64 payload no longer pays a full scan on the async API worker). A scheme that no processor and no built-in path serves is a 400 during prefetch (`media fetch: unsupported URI: custom://...`) instead of a base64 decode failure on the worker.
- Media failures carry their class through a new `MediaError`, mirroring the Python loader contract: `Client` is a 400 (`ValueError` in Python) and `Server` a 500 (any other exception). The built-in fetch errors stay 400; a panicking fetch is now a 500 (it was a 400).

The permit of the global fetch cap stays with the blocking fetch (`run_blocking_bounded`), so an abandoned fetch cannot escape the bound while a processor's fetch, which may take longer than a plain download, shares it.

Files: `rust/sglang-server/src/multi_modality/worker.rs` (hooks, `MediaError`), `api_server/core/prefetch.rs` (modality-tagged plan, processor fetch, error classes), `api_server/core/handle.rs` (processor slot, 400/500 mapping), `multi_modality/payload.rs` (`is_io_source`), `utils/runtime.rs` (install on pool start), `lib.rs` (re-exports `MediaError` and `MediaByteBudget` for external processors).

## Accuracy Tests

Not applicable: no model forward or kernel code changes. Unit coverage in `cargo test -p sglang-server`:

- `prefetch::tests::processor_hooks_check_and_fetch_media`: a processor's `custom://` sources resolve in request order beside base64 and local-file sources; its `Client` and `Server` failures keep their class; `other://` with the processor and `custom://` without it are 400 "unsupported URI"; a panicking fetch is a `Server` error; `check_media` refuses before any fetch starts.
- `handle::tests::processor_media_failures_keep_their_status_class`: through `CoreHandle::generate`, a `Client` failure is HTTP 400 and a `Server` failure HTTP 500, neither request reaches intake, and a second `set_mm_processor` is refused.
- `payload::tests::io_sources_use_prefetched_bytes`: any well-formed `scheme://` counts as an I/O source; bare base64, `data:` URLs, malformed prefixes and a scheme-alphabet run past the 32-byte bound do not.
- The existing prefetch tests assert the `MediaError` class; `cancelled_caller_does_not_release_blocking_permit_early` is unchanged.
