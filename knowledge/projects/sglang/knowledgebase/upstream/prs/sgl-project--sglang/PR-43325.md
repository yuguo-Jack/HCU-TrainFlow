## Motivation

MiMo-V2-Flash has asymmetric K/V rows: 192-wide K heads and 128-wide V heads, on its full-attention and its sliding-window layers alike. `--enable-unified-memory` refuses any such model at boot ("does not yet admit asymmetric K/V rows"), so MiMo serves only on the default pool. That pool splits its memory between the two layer kinds at boot, and under long decodes it retracts requests while the other kind's memory still has room.

## Modifications

Backend rejection reports the applicable allowed set without incorrectly attributing symmetric or MLA failures to asymmetric KV rows.

1. **Admit asymmetric K/V rows on the backends that carry `v_head_dim`** (`8523eb5e81`). The unified pool stores each token's K and V rows side by side in one per-token entry, each at its own offset, so a V row narrower than K needs no pool-level refusal. What remains is a backend property: whether the kernel is told the V width at all. FlashInfer's `paged_kv_t` keeps separate K and V strides but one `head_dim` for both tiles, and sglang's MHA plan path never passes `head_dim_vo`; trtllm_mha refuses unequal QK/V dims. For a model with asymmetric rows, the attention backends that `--enable-unified-memory` accepts therefore narrow to `ASYMMETRIC_KV_BACKENDS`: triton, fa3 and fa4, which pass `layer.v_head_dim` through. fa4 is the resolved default for an asymmetric-K/V model on SM100, so leaving it out would make such a model unbootable in its own default configuration; it also runs on SM90, and the accuracy table below includes it. A speculative draft whose KV is fused into the target's pages follows the same rule (it fuses only when the target's and the draft's backends all carry `v_head_dim`), its share of each entry is sized with the draft's own `v_head_dim`, and the check that every row is 16-byte aligned covers the V row as well as the K row.
2. **Build pools from the actual full/SWA head geometry** (`2aaa913354`). Both hybrid-SWA factories and fused FULL host sizing share `_unified_swa_head_geometry`, so the bytes priced at startup match the entries allocated. The GPU path reads ModelConfig's full/SWA KV-head counts and K/V widths; the NPU compress path retains its HF-config geometry. Non-SWA Mamba/full hosts also carry their actual V width. This removes duplicated geometry decisions and covers asymmetric rows outside the compress-model list.

Tests (CPU): `TestUnifiedSWAHeadGeometry` runs both factories on a model outside the compress list whose sliding-window layers have 8 KV heads against 4 and 128-wide V rows against 192-wide K, and checks the head geometry each hands its pool constructor: `(4, 192, 192, 4, 192, 192)` before this change, `(4, 192, 128, 8, 192, 128)` after it. The test stubs for models with both Mamba-style state and sliding-window layers gain the SWA head fields and `v_head_dim`.

SM90, MiMo-V2-Flash, TP4, no speculation, radix cache, overlap scheduler, CUDA graphs on. Default pool against `--enable-unified-memory`. GSM8K, all 1314 test questions, 5-shot, greedy:

With CUDA graphs off, fa4 scores 0.844 on the default pool and 0.830 on the unified pool. In the fa4 runs the unified pool filled every byte that is never written with NaN (`SGLANG_DEBUG_POISON_POOL=1`), so a read of a slot nobody wrote would show up as lost accuracy. Over 1314 questions one run's score has a sampling error of about one point, so both fa4 pairs are within noise.

On both layer kinds, the unified pool stores MiMo's K and V rows at their real 192 and 128 widths, in entries of the size the startup memory sizing computes.

The triton and fa3 MiMo runs used the head of the next PR in this stack, which changes what a speculative draft binds and leaves a run without a draft as it is in this PR.

## Speed Tests and Profiling

The measurements in this section are historical results from before this rebase, at the revisions/configurations stated below. Current combined-stack validation is linked above.

The same MiMo configuration under two load tests: 100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests that share a 4096-token system prompt, each with a 128-token question and 2048 output tokens, at concurrency 192. Every request completed on every server, and no server reported an error.

| attention backend | requests × input / output tokens | default pool req/s | unified req/s | change |
|---|---|---|---|---|
| triton | 100 × 512 / 4096 | 0.615 | 0.896 | +45.6% |
| triton | 192 × (4096 shared + 128) / 2048 | 0.867 | 1.259 | +45.2% |
| fa3 | 100 × 512 / 4096 | 0.611 | 0.874 | +43.2% |
| fa3 | 192 × (4096 shared + 128) / 2048 | 0.824 | 1.156 | +40.3% |

The gain is capacity: from the same memory, the unified pool lets either layer kind take the bytes the default pool splits between them at boot, so it retracts fewer requests.

A model this PR does not admit is unaffected: Qwen3.5-9B without speculation (200 requests of 2048 input / 512 output tokens at concurrency 64), run back to back on one host with and without this PR, keeps its unified-vs-default-pool req/s gap at −0.4% (fa3), −0.5% (triton) and −0.4% (trtllm_mha), against −0.3%, −0.2% and −0.5% without it. The default pool runs twice per configuration, and its two runs differ by at most 0.2%.
