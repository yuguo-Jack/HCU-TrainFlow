# [Fix] disaggregation: Reject PD pairs whose DSA KV rows differ in width

[Upstream PR](https://github.com/sgl-project/sglang/pull/46406) · state: open · merged: False

## Original PR description

## Motivation

PD transfers KV rows byte for byte, so the prefill and decode pools must store the same row layout. With a DSA model (DeepSeek-V3.2, GLM-5.x) on SM100+, `--kv-cache-dtype auto` resolves to FP8, and the two roles choose different DSA backends:

- a HiSparse decode defaults both DSA backends to `flashmla_kv`, which uses FlashMLA's packed FP8 row (656 B per token for kv_lora 512 + rope 64);
- a prefill without HiSparse defaults to `trtllm` on Blackwell FP8, which uses the raw row (576 B).

Each role sizes its pool from its own backend (`kv_cache_configurator.py`), and the PD handshake compares only page size and KV dtype. The decode therefore reads misaligned rows and produces garbage silently. The deployment in `hisparse_guide.mdx` reaches this directly: it says the prefill instance needs no changes, and the DeepSeek-V3.2 / GLM-5.x cookbook pages point to it for PD decode with HiSparse. `test_dsa_glm52_hisparse.py` already works around it by adding `--dsa-prefill-backend flashmla_kv --dsa-decode-backend flashmla_kv` to the prefill, but neither the defaults nor the guide changed.

#45075 added a `kv_layout` field to the PD handshake, but only `DeepSeekV4TokenToKVPool` reports one.

## Modifications

- `DSATokenToKVPool.pd_kv_layout()` reports the MLA row width (`dsa_mla_row:<kv_cache_dim>`). `get_pd_kv_layout` also returns it for a DSA pool, including the DSA full pool of a hybrid pool. A DSA pair whose rows differ is now rejected at the existing handshake check instead of exchanging misaligned KV. Pairs with equal rows are unaffected.
- The handshake error names the DSA backend flags.
- `hisparse_guide.mdx`: on SM100+ with FP8 KV, the prefill instance needs `--dsa-prefill-backend flashmla_kv --dsa-decode-backend flashmla_kv`. The decode backend flag is needed because startup autotune runs a decode forward on the prefill too. Also drop the "transparent to prefill" claim.

The mismatch raises in `try_ensure_parallel_info` like the existing DeepSeek-V4 layout check. That stops the decode process on its first request from a mismatched prefill; turning it into a per-request rejection is left for a separate change.

## Accuracy Tests

8x B300 (SM100), `nvidia/GLM-5.2-NVFP4`, 1P1D over Mooncake. Prefill runs TP4. Decode runs TP4 with `--attn-dp-size 4 --enable-hisparse --hisparse-config '{"top_k":2048,"device_buffer_size":4096,"host_to_device_ratio":5}'`, the same config as `test_dsa_glm52_hisparse.py`. KV dtype is the default `auto`. GSM8K uses sgl-eval 0.1.3 with temperature 1.0, top_p 0.95 and `--thinking`; max_tokens is 16384 instead of the recommended 200000 so the broken arm finishes.

| Tree | Prefill flags | Decode | Result |
|---|---|---|---|
| main | none (as the guide said) | HiSparse | output is garbage after the first token (`"17*23?" -> "39!!!!!!..."`); GSM8K 0.00% (200 questions, measured on an earlier main) |
| this PR | none | HiSparse | rejected at the handshake: `KV layout mismatch: prefill server has kv_layout=dsa_mla_row:576, but decode server has kv_layout=dsa_mla_row:656` |
| this PR | `--dsa-prefill-backend flashmla_kv --dsa-decode-backend flashmla_kv` | HiSparse | GSM8K 98.00% (200 questions); probes answer correctly |
| this PR | none | plain (no HiSparse) | GSM8K 98.00% (100 questions); no false rejection |
