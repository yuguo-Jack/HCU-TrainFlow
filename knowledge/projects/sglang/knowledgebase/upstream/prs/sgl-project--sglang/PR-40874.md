# [Feat] dsv41: Support encoder-only prefill for PD disaggregation

[Upstream PR](https://github.com/sgl-project/sglang/pull/40874) · state: open · merged: False

## Original PR description

## Motivation

Add an opt-in encoder-only Prefill mode for text-only DeepSeek-V4.1 P/D disaggregation. Prefill loads the encoder layers and final global-cache producer; Decode reconstructs its local state and samples the first output token. This reduces Prefill work and resident weights; this revision makes no throughput or capacity claim.

Closes #39963.

## Implementation

For an effective input of N tokens, Prefill processes `[0, S)`, where `S = max(0, N - 128)`, and transfers prefix Main-KV/Indexer-K, the encoder SWA history, and the pending ratio-2 compressor pair. Decode reuses its preallocated slots for a real `[S, N)` extend. Encoder layers read transferred history; decoder layers retain bounded-replay floors. Inputs of at most 128 tokens use a metadata-only Prefill handoff.

The flag `--dsv41-encoder-only-prefill` is required on both roles. The supported envelope is CUDA, text-only 40-layer V4.1 with KV sources `[2,8,14,20]`, a 128-token window, Mooncake, PP1/DP1/CP1, paged SWA, and Prefill CUDA Graph disabled. Decode-local DSpark is allowed; its draft state is reconstructed on Decode. Unsupported request features, including logprobs and auxiliary captures, fail explicitly.

The change preserves first-token ownership, cache accounting, overlap replay suspension/restoration, and rebootstrap boundary tokens. It also handles metadata-only transfer failure without releasing unallocated KV, ignores stale cache-only metadata in fake health transfers, and validates the normalized sliding-window configuration. The unused admission prefix clone and ForwardBatch marker are removed, and ordinary SWA capacity handling follows main.

This PR does not add replay Graph machinery, kernel tuning, Indexer host-layout paths, or Router changes. The existing exact split and pending-pair protocol are retained.

- akhilg-nv · comment · 2026-10-15T23:49:53Z · [source](https://github.com/sgl-project/sglang/pull/40874#issuecomment-6204692867)

@HanHan009527 Thanks for driving this. I'm working on supporting this feature from NVIDIA's side and would like to collaborate. I'd like to suggest one design change before more is built on the current handoff. 

[Following description is mostly written by claude code. The tldr is we should only compute up to tokens N-128 on the encoder/prefill worker, and we need to also pass the encoder SWA for last 128 tokens to the decode worker]
                                                                   
It seems like in the current design, decode's layers 0–19 are approximate. Every layer reads its own 128-token SWA window. Decode currently receives only Main-KV/Indexer-K, so when it replays [N−128, N) through L0–19, those layers have no SWA history before N−128. Their outputs feed L20–39, so the error from bounded replay hits both halves of the model. Collocated `--enable-decoder-swa-bounded-replay` only truncates L20–39. So the current PD output is not equivalent to the collocated path, and nothing can be parity-tested against it. GSM8K at this sample size (p=0.109) can't detect a gap like this.                                                   

I'd instead propose the following approach (which follows what was shipped in NVIDIA/TensorRT-LLM#19727 as `bounded_replay_on_generation`):
1. Prefill processes only `[0, max(0, N−128))` through L0–19 plus the L20 KV/indexer path. For N ≤ 128 it skips the forward, as the RFC describes.                                               
2. Transfer Main-KV + Indexer-K for that prefix, **plus L0–19 SWA for the last 128 prefix positions** and the ratio-2 compressor state at the boundary. L20–39 SWA is not transferred. This is about 1.5 MB per request.
3. Decode runs the tail [N−128, N) through all 40 layers as it does today, but:
     - L0–19 read the transferred SWA with no floor, so the encoder half is **exact**, exactly like the next chunk of a chunked prefill;                                                         
     - L20–39 are floored at N−128, the same as collocated decoder bounded replay;
     - the tail writes its own Main-KV/Indexer-K for [N−128, N), instead of the cache-only/state-only rebuild.
                                                                   
This makes the PD output match collocated decoder bounded replay, so we can gate on logprob/KL parity against it. It also removes the duplicated L0–19 compute on [N−128, N). Most of the decode-side replay and scheduling work in this PR carries over unchanged.
  
**Question on the current code:** on decode, the request window is disabled and paged SWA is used. As far as I can tell, the `swa_replay_start` floor in `make_core_attn_metadata` is only applied in the request-window branch, and the main `init_forward_metadata_prefill` call doesn't pass one. If so, L0–19 tail rows may read SWA slots for positions < N−128 that were never written on decode. Could you confirm? Poisoning decode's SWA pool with NaN at startup would show it quickly. I may be misreading. The proposal above makes this moot for L0–19, but L20–39 still need the floor.
                                                                   
Happy to help implement this, either as PRs against your branch or as a separate upstream PR, whichever you prefer. @zooeyQAQ, this changes the transfer payload and the decode attention metadata, so it may be worth syncing before you go deep on the SM120 decode path.

- akhilg-nv · comment · 2026-10-20T08:26:05Z · [source](https://github.com/sgl-project/sglang/pull/40874#issuecomment-6286758335)

[by Claude Code] Thanks @HanHan009527, glad the new handoff (prefix + encoder SWA) is in. FYI, we built the same design independently in #45265 and have tested it on GPUs (GB300, prefill TP2 + decode TP2, Mooncake over MNNVL). In short:

**Correctness**
- The output matches a single-server run that splits the prompt at the same point: identical tokens for tails of 128 and 129 tokens, and logprob differences no bigger than ordinary run-to-run noise.
- GSM8K stays at parity with DSpark on decode, DP attention on prefill, DP attention + DSpark on decode, and forced retraction.

**One design difference:** we round the split point down to an even number of tokens. That way no half-filled ratio-2 pair is left at the boundary, so no per-request compressor state needs to be transferred, and prefill and decode can use different ring sizes (e.g. DSpark on decode only).

**Performance (AgentX, 1P1D, 160 concurrent sessions)**
- At this load, stock prefill runs out of KV cache. The split's larger prefill cache fixes that: cache hit rate 89.7% → 94.6%, p90 TTFT 13.7 s → 2.0 s.
- But overall throughput is lower, because decode now runs each request's last 128 tokens as an eager (no CUDA graph) extend, about 150 ms per step, and decode stalls while it runs. We're working on making that step cheap.

Happy to consolidate the two PRs. Which parts of each would you like to keep?
