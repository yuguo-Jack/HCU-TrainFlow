# [Perf] diffusion: Accelerate conditioning hashing with GPU BLAKE3

[Upstream PR](https://github.com/sgl-project/sglang/pull/46603) · state: open · merged: False

## Original PR description

## Motivation

This PR follows up on [#46028](https://github.com/sgl-project/sglang/pull/46028), extending the GPU hash optimization introduced for Cosmos3 to other diffusion models with suitable conditioning workloads.

Profiling shows that hashing large visual conditioning tensors adds substantial device-to-host transfers and CPU SHA-256 work before VAE or vision encoding. Reusing the existing GPU [BLAKE3](https://github.com/BLAKE3-team/BLAKE3) implementation keeps tensor-content hashing on the GPU and returns only the 32-byte digest to the CPU.

## Modifications

- Add `use_gpu_conditioning_hash()` to select GPU hashing within an existing conditioning-cache scope. CPU tensors use the original digest, and nested scopes restore the previous policy on exit, including exceptions.
- Reuse `gpu_tensor_blake3` from `python/sglang/kernels/ops/memory/gpu_tensor_hash_blake3.py`. Keep `_fingerprint`'s signature and container recursion; select the digest only in its Tensor branch.
- Enable the policy at these conditioning paths:

| Path | Models |
| --- | --- |
| Ref2VA VAE and vision-encoder inputs | MiniMax-H3, FastH3-Omni |
| Control/reference-video VAE inputs | Cosmos3 Transfer, Cosmos3 multiview and Simulation, Wan2.2-Animate-2 including Distilled |
| Multiple reference images | FLUX.2/Klein and Qwen-Image-Edit through the shared image-VAE stage; Qwen-Image-2.1 VAE and vision encoding; GLM-Image VAE |
| Video-clip memory VAE inputs | JoyAI-Echo |

**Workload selection matters.** The shared `ImageVAEEncodingStage` opts in only when `num_frames == 1 and len(images) > 1`. These are multiple reference images without padded zero frames; images are still hashed and encoded individually. Ordinary I2V inputs contain one image followed by zero frames, and the original digest already filters nonzero blocks on the GPU to avoid transferring the padding. Single-image requests keep the default policy in this stage.

The scoped policy can be reused at other conditioning-cache call sites. Further single-image or model-specific adoption should be based on the actual tensor size, sparsity, and measured hash cost.

## Accuracy Tests

- All 11 completed comparisons for newly adapted workloads produced **bitwise-identical decoded RGB frames and audio samples where present**. The existing Cosmos3 V2V reference comparison also passed.
- GPU digests matched the standard CPU BLAKE3 implementation for the tested conditioning tensors.
- Current cache, model-boundary, and text-encoding regressions: **130 passed, 1 skipped**. Coverage includes CPU fallback, content changes, nested scopes, exception restoration, and posterior sampling/RNG. Pre-commit passed.
- Full-model validation remains pending for JoyAI-Echo, Qwen-Image-Edit-2511, Qwen-Image-2.1-Turbo, and GLM-Image. They are integrated but excluded from the performance table below.

## Speed Tests and Profiling

RTX PRO 6000 Blackwell Server Edition 96GB; Xeon Platinum 8480+ with 16 logical CPUs; SGLang Docker `b1259f3ea327`.

Each mode runs in a separate process on the same GPU: one complete warmup followed by one measured request, using different visual inputs and prompts to avoid warmup cache hits. The baseline retains the original digest, including GPU zero-block filtering; other settings are identical within each pair.

Hash timing includes tensor-content hashing and required transfers with inputs ready, and excludes VAE encoding and upstream waits. E2E includes generation and output saving, excluding model loading. Speedup is original time divided by GPU-hash time.

Outputs: MiniMax/FastH3 896×512, 107 frames; Wan-Animate 576×1024 with a requested 37-frame clip; Cosmos3 832×480, 45 frames per view; Klein 1024×1024. MiniMax uses layerwise offload with 20 DiT layers resident; FastH3 uses Torch SDPA on SM120.
