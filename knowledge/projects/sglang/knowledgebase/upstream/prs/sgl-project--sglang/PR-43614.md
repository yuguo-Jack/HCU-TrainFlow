# [Perf] Apply min_new_tokens penalties with compact stop-token updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/43614) · state: open · merged: False

## Original PR description

## Summary

### Motivation

`min_new_tokens` masks a few EOS/stop IDs, but currently prepares a batch × vocabulary penalty tensor and runs dense where/add operations on every decode step. Keep compact padded stop IDs and use one Triton update on CUDA; use compact Torch scatter_add on other devices.

### Modifications

```diff
 prepare
-  penalties[batch, vocabulary]
+  stop_ids[batch, max_stops], penalties[batch, max_stops]
 apply
-  dense where + vocabulary-wide add
+  update active stop entries
```

Preserve pinned metadata transfers, EOS union/deduplication, additive semantics, length counters, filter/merge and teardown. Validate IDs on CPU before direct CUDA addressing; skip zero padding to avoid token-0 races. Add registered CPU/GPU tests, including graph replay and different stop-list widths.

## Evidence

### Speed Tests and Profiling

- **Before:** A100, Qwen3-0.6B BF16, greedy 64-token generation with min_new_tokens=64: 17,094.84 tokens/s at batch128; 27,626.55 at batch512.
  **After:** 17,596.94 (+2.94%) / 29,429.45 (+6.53%). Each comparison uses ABBA, 10 timed groups per variant, identical inputs/settings within the pair. Throughput counts all completion tokens over client time to receive the full response, including prefill and HTTP/SSE overhead. The min=0 controls change -0.96% / +0.53%. Batch512 disables radix cache on both sides; it uses a larger token pool and is a separate experiment.
- **Before:** Production apply at B128/V151936/two stop IDs: 302.17 μs.
  **After:** 27.35 μs (11.05×). CUDA events around repeated host launches; this is an operator measurement, not an end-to-end speedup.
### Accuracy Tests

- 105 pytest tests and 23 subtests pass; 24 microbenchmark shapes and 65 additional CUDA differential checks match the dense reference. Covers FP32/FP16/BF16/FP64, strided logits, padding/empty/ragged stops, graph replay, invalid IDs, nonfinite values and merge/filter. 27,560 timed model responses plus 32 naturally EOS-terminated responses match token IDs, text and finish reasons exactly. Pre-commit passes.
### Limitations

- Small/streamed workloads show no consistent gain: final single-request throughput -1.03%, SSE -1.89%, cached batch32 SSE -1.11%; SSE TTFT worsens 1.29% / 1.41%. A separate same-process diagnostic finds batch128 +4.07% and single SSE +0.09%. Do not infer a general TTFT benefit.

Baseline: 234ccba7f625e12639e621044496bcc6197c3758. Patch: fcdd5e12ac1865c94f73807a9dc5370518608e0c. Model revision: c1899de289a04d12100db370d81485cdf75e47ca. Torch 2.14.1+cu130 / Triton 3.8.0. Full settings, scripts and raw outputs: [benchmark evidence](https://github.com/davidliuk/sglang/tree/d2abd339976589225c3ffa9d9cbc90382c2ac6c1/benchmark_evidence/sparse-min-new-tokens-20261010), [detailed report](https://github.com/davidliuk/sglang/blob/d2abd339976589225c3ffa9d9cbc90382c2ac6c1/benchmark_evidence/sparse-min-new-tokens-20261010/REPORT.md), [machine-readable summary](https://github.com/davidliuk/sglang/blob/d2abd339976589225c3ffa9d9cbc90382c2ac6c1/benchmark_evidence/sparse-min-new-tokens-20261010/summary.json). ## Merge Danger

**Door:** two-way

No format/API migration; reverting restores the dense implementation.

**Blast Radius:** sampling

Affects batches using min_new_tokens, including their EOS/stop handling and metadata merge/filter. Other penalties and the min=0 path are unchanged. Tested on one A100 and CPU; AMD/NPU, other GPU architectures, TP and real model speculative decoding remain untested. The main timed workload reaches the length limit; natural EOS is checked separately for correctness, without claiming short-output performance gains.
