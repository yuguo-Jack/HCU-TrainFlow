# [GDN] Add --enable-linear-lossless-verify: bit-exact tuple replay for spec verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/42388) · state: open · merged: False

## Original PR description

<!-- Title: [GDN] Add --enable-linear-lossless-verify: bit-exact tuple replay for spec verify -->

## Motivation

**How it works today.** On hybrid GDN models (Qwen3.5 / 3.6 / 3.8, Qwen3-Next), speculative target-verify runs the recurrent kernel with `disable_state_update=True` and writes a full `[HV, V, K]` SSM snapshot for every draft position into `intermediate_ssm`. After acceptance, `scatter_mamba_states_after_mtp_verify` copies two snapshots back into the persistent pool: the last accepted position, and, with the `extra_buffer` radix strategy, the position that crossed a mamba-track boundary. Every linear-chain algorithm goes through this path: EAGLE/MTP, DFLASH and DSPARK.

**The problem.** That buffer is large, and it grows with the draft width. On Qwen3.6-35B-A3B one snapshot is 60 MiB (30 GDN layers × 32 heads × 128 × 128 × fp32), so each request needs `60 MiB × D`. `_handle_max_mamba_cache` reserves this for every request slot before the KV pool is sized, so all of it comes out of KV capacity:

| setup (1× H100) | `intermediate_ssm` |
|---|---|
| Qwen3.6-35B-A3B-FP8, MTP D=4, 25 requests | 6.09 GB |
| Qwen3.6-35B-A3B-FP8, DFLASH block 16, 8 requests | 8.44 GB |
| Qwen3.8-27B-FP8, DFlash2 / DSpark D=8, 8 requests | 10.12 GB |

In the first setup the KV pool ends up at 498,880 tokens. That is not enough for 25 concurrent 26k-token requests, so 7 of them sit in the queue.

`--enable-linear-replayssm-spec` already gets rid of these snapshots, but it changes how verify is computed: a frozen checkpoint plus a compact ring, a causal-masked window, and compensated materialization. Its results are therefore not bit-identical to the default verify. On Qwen3.6-35B-A3B with MTP (measured on v0.5.21), greedy outputs diverged from the default path after 23–143 tokens on 8 of 8 prompts. Many deployments can live with that. Some cannot: evals, A/B rollouts and regression testing all need the outputs to match the default path exactly.

**The idea.** Each recurrent step is

```
h_t = exp(g_t) * h_{t-1} + k_t ⊗ u_t,    u_t = beta_t * (v_t - (exp(g_t) * h_{t-1})^T k_t)
```

The verify kernel already computes `u_t`, the l2-normalized `k_t` and `g_t`. And `h_0` is still in the pool, because verify does not update state. So instead of keeping every `h_t`, we can keep `(u_t, k_t, g_t)` and rebuild the accepted `h_t` at commit time. That costs `HV * (V + K + 1)` floats per step instead of `HV * V * K`, which is 63.8× less at K = V = 128.

The rebuild has to round exactly the way the verify kernel does. Inside the kernel the decayed state `h * exp(g)` is used twice, by the delta reduction and by the update. So the compiler keeps it as a separately rounded multiply and folds the update into a single FMA: `fma(k, u, round(h * exp(g)))`. The replay writes out the same two instructions. A naive replay written as one expression lets the compiler contract a different multiply and drifts by 1–2 ULP. The tests include that case, to show they would catch it.

## Modifications

Everything sits behind a new flag, `--enable-linear-lossless-verify`, off by default. With the flag off, no code path and no memory reservation changes.

**Verify kernel** (`fused_sigmoid_gating_recurrent.py`, `gdn_triton.py`)
- New optional `u_states_buffer` / `k_states_buffer` / `g_states_buffer` arguments and a `CACHE_U_TUPLES` constexpr. For each draft step, the kernel stores `u` (after the beta scaling), the l2-normalized `k`, and `g`, at the row given by `intermediate_state_indices`. `k` and `g` do not depend on the V tile, so only the `i_v == 0` program writes them.
- The per-request pitch comes from the buffer shape, so it stays correct under `--speculative-adaptive`.
- The tuple path picks the same launch config as the dense verify (`target_verify=True`, which includes the SM90 `BV=4` tile). Verify outputs are therefore identical by construction, not just in testing.

**Verify call site** (`gdn_backend.py`)
- When the pool has a tuple ring, the ring is passed to the kernel instead of `intermediate_ssm`.
- A one-time check that the dispatcher picked the Triton verify kernel. The FlashInfer verify kernel accepts `**kwargs`: it would silently ignore the buffers, and the commit would replay zeros.
- An assert that no tree metadata (`retrieve_parent_token`) reaches the tuple path.

**Commit** (`hybrid_linear_attn_backend.py`, `mamba_state_scatter_triton.py`)
- `_recon_kernel` replays all GDN layers of a batch in one launch, starting from `ssm_states[slot]` and stopping at the accepted step.
  - On CUDA, the rounding is pinned with `mul.rn.f32` / `fma.rn.f32` inline PTX.
  - PTX does not exist on ROCm: the AMDGPU backend rejects the `f` register constraint. HIP builds instead use a plain multiply feeding `tl.fma`, which the compiler cannot contract.
  - Both forms are bit-exact against verify.
- Rows with a negative step, or an out-of-range slot or row index, are skipped. This is the same validity rule `fused_mamba_state_scatter_with_mask` uses.
- **Order matters.** The mamba-track replay runs before the in-place replay of the accepted state, because both must start from the pre-verify state. If the in-place replay runs first, the track replay starts from the already-advanced state and stores a wrong prefix-cache state. This bug does not show up in throughput benchmarks. It shows up as the second turn of a conversation diverging from the default path; the server-level test below covers it.
- Conv windows still go through the existing scatter. `scatter_mamba_states_after_mtp_verify` gets a `skip_ssm` argument, so the SSM half is left to the replay.
- PP spec stable rows (`SGLANG_ENABLE_PP_SPEC`) work: the replay reads the same rows verify wrote to (`src_indices_raw`).

**Pool and memory accounting** (`memory_pool.py`, `kv_cache_configurator.py`, `disaggregation/decode.py`, `unified_memory_pool.py`)
- `MambaPool.SpeculativeState` gets `intermediate_ssm_u` / `_k` / `_g`, shaped `[layers, spec_slots + 1, D, HV, V | K | -]`. In this mode `intermediate_ssm` is `None`.
- The ring is always fp32, whatever `--mamba-ssm-dtype` is, so bf16 state pools stay exact too.
- The ring is excluded from state transfer, like the other spec-only buffers.
- `spec_intermediate_bytes_per_req` computes the scratch size from the same shapes `MambaPool` allocates: the tuple ring plus the deduplicated conv window.
- With the flag on, `_handle_max_mamba_cache` reserves exactly that in all three sizing branches, including the joint solve for `max_mamba_cache_size`. The freed memory becomes KV cache instead of an idle reservation. With the flag off, the existing formula is used unchanged.
- The flag is plumbed through `HybridReqToTokenPool` and the PD decode pool. The unified memory pool rejects it.

**Gating** (`attention_hook.py`, `pipeline.py`)

The replay walks one linear chain, so the flag requires `--speculative-eagle-topk 1`. This is enforced in three places:
- **At startup:** `validate_linear_lossless_verify` runs right after `handle_speculative_decoding`. It cannot live in `handle_linear_attn_backend`, because that runs earlier, before DFLASH and DSPARK pin topk to 1.
  - Accepted: EAGLE/MTP with topk 1, DFLASH, DSPARK.
  - Rejected with a clear message: tree EAGLE (topk > 1), NGRAM, no speculative decoding, either ReplaySSM flag, a non-Triton verify backend, `--enable-unified-memory`, and any `SGLANG_RAGGED_VERIFY_MODE` other than `static`.
- **In the pool:** `MambaPool` rejects topk ≠ 1 and KDA layers, and the KV cache configurator rejects non-GDN models.
- **At runtime:** `forward_extend` asserts that no tree metadata reaches the tuple path.

**Tests**: `test/registered/attention/unittests/gdn/test_gdn_lossless_verify.py`, registered for CUDA and AMD CI. Details below.

Not changed: the default verify path, KDA, tree verify, and ReplaySSM.

## Accuracy Tests

**Unit tests** (`test_gdn_lossless_verify.py`, 8 tests). They drive the real `MambaPool`, the real verify kernel and the real commit entry point (`HybridLinearAttnBackend.update_mamba_state_after_mtp_verify`), and require `torch.equal` against the snapshot verify for:
- verify outputs, every SSM slot, every conv slot and every mamba-track slot, for D ∈ {2, 3, 4, 8, 16} and heads (16, 32) and (4, 16);
- a bf16 state pool;
- PP stable request rows;
- out-of-range rows, which must be left untouched;
- the PTX and portable replay forms (CUDA);
- the scratch-size helper against the real allocation, byte for byte;
- rejection of tree verify;
- a control: replaying the accepted state before the track state gives a wrong track state, so the ordering above is actually exercised.

On H100 these 8 pass, and so do the existing GDN tests: `test_triton.py`, `test_gdn_replayssm_spec_fold.py`, `test_fused_verify_triton_gdn.py`, `test_gdn_noncontiguous_stride.py`.

**Server-level, greedy.** Stock `main` (d75d5b33f) against this branch with `--enable-linear-lossless-verify`, same flags otherwise (`--max-running-requests 8 --max-mamba-cache-size 40 --kv-cache-dtype bf16 --page-size 64`), 1× H100. Each workload runs twice per server, with a cache flush in between, so the server's own run-to-run determinism is measured too:
- **single:** 8 prompts, one at a time, 300 tokens each.
- **multi-turn:** turn 1 decodes 700 tokens, crossing the 256 and 512 mamba-track boundaries. Turn 2 is turn 1 plus a follow-up, so its prefill resumes from the state tracked during turn-1 decode (`cached_tokens = 512`). This is the workload that catches a wrong track state.
- **batched:** the 8 prompts in one request, so the batch composition is fixed.

| speculative setup | single | multi-turn (turn 1 · turn 2) | batched |
|---|---|---|---|
| EAGLE/MTP 3/1/4, Qwen3.6-35B-A3B-FP8 | 8/8 | 4/4 · 4/4 | 8/8 |
| DFLASH, Qwen3.6-35B-A3B-FP8 + z-lab/Qwen3.6-35B-A3B-DFlash (D=16) | 8/8 | 4/4 · 4/4 | 8/8 |
| DFLASH with a DFlash2 draft, Qwen3.8-27B-FP8 + z-lab/Qwen3.8-27B-DFlash2 (D=8) | 8/8 | 4/4 · 4/4 | 8/8 |
| DSPARK, Qwen3.8-27B-FP8 + RadixArk/Qwen3.8-27B-DSpark (D=8) | 8/8 | 4/4 · 4/4 | 8/8 |

Every cell matched stock on both runs. When the same 8 prompts are fired from 8 threads instead, outputs occasionally differ in 2 of 8. Stock differs from itself in exactly the same way between runs, because arrival order changes how requests are batched; it is not specific to this change.

**ROCm.** The same kernels and commit logic, backported to v0.5.21 and run on an MI325X (gfx942, ROCm 7.15, Triton 3.8):
- A standalone harness passed 144 of 144 exact checks with the portable replay.
- Server-level, with `--enable-deterministic-inference --attention-backend triton` and `SGLANG_USE_AITER=0`, all four workloads matched stock on both runs.
- With the default aiter backends, stock itself is not reproducible from run to run (even bs=1 greedy differs), so that configuration cannot be compared. Accept length was the same (2.852 vs 2.850).
- gfx950 has not been tested yet.

## Speed Tests and Profiling

**End to end.** Qwen3.6-35B-A3B-FP8, MTP 3/1/4, 1× H100, with `--mem-fraction-static 0.8 --kv-cache-dtype bf16 --page-size 64 --max-running-requests 25 --max-mamba-cache-size 150 --enable-hierarchical-cache`. `bench_serving` on the random dataset, 25 requests × (26k in / 2k out), concurrency 25:

| | verify scratch | `max_total_num_tokens` | max running | duration | output tok/s | accept length |
|---|---|---|---|---|---|---|
| main | 6.09 GB | 498,880 | 18 | 36.75 s | 1,360.6 | 3.51 |
| this PR, flag on | 0.10 GB | 788,224 (+58%) | 24 | 33.03 s | 1,513.7 (+11%) | 3.45 |

Accept length is within run-to-run noise: it ranged from 3.45 to 3.51 across repeated runs of both configurations. That is expected, since the outputs are bit-identical.

**Memory with other algorithms** (8 requests, 40 mamba slots, so the absolute numbers are not comparable with the table above):

| setup | verify scratch | `max_total_num_tokens` |
|---|---|---|
| MTP, Qwen3.6-35B-A3B-FP8 (D=4) | 2.11 → 0.03 GB | 1,007,680 → 1,107,776 (+10%) |
| DFLASH, Qwen3.6-35B-A3B-FP8 (D=16) | 8.44 → 0.13 GB | 390,208 → 591,040 (+51%) |
| DFlash2, Qwen3.8-27B-FP8 (D=8) | 10.12 → 0.16 GB | 176,640 → 302,464 (+71%) |
| DSpark, Qwen3.8-27B-FP8 (D=8) | 10.12 → 0.16 GB | 178,944 → 304,832 (+70%) |

**Per-step kernel cost.** Microbenchmark on the Qwen3.6-35B-A3B GDN geometry (30 layers, 16/32 heads, 128 × 128), H100, CUDA events, about 25% of rows crossing a track boundary. The verify kernel gets cheaper, because it writes `HV * (V + K + 1)` instead of `HV * V * K` floats per step. The replay is cheaper than the scatter at D=4 and costs a little more at D=8 and D=16, where it walks a longer chain. Net, every configuration is faster per verify step:

| requests × draft tokens | verify, per GDN layer | commit, 30 layers | net per verify step |
|---|---|---|---|
| 25 × 4 | 99.7 → 53.9 µs | 1868 → 1489 µs | −1.75 ms |
| 8 × 4 | 41.0 → 41.8 µs | 605 → 413 µs | −0.17 ms |
| 8 × 8 | 64.9 → 42.0 µs | 527 → 548 µs | −0.67 ms |
| 8 × 16 | 120.9 → 60.3 µs | 470 → 690 µs | −1.60 ms |
