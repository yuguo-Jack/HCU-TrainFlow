# [Feat] qsa: host offload of the MTP draft model's QSA K/V (3/N)

[Upstream PR](https://github.com/sgl-project/sglang/pull/48378) · state: open · merged: False

## Original PR description

> **Stacked on #48377 (2/N), which is stacked on #48376 (1/N).** This branch includes both; the change to review here is the commits after `a3a1c2c452` ([compare](https://github.com/esarafian/sglang/compare/qsa-kv-host-offload-fused...qsa-kv-host-offload-mtp-draft)). I will rebase as the base PRs merge.

## Motivation

PR 1/N keeps the full-attention K/V of Qwen4-Exp's QSA layers in pinned host memory, with a per-request GPU cache of the blocks the indexer selects; PR 2/N makes that resolve CUDA-graph-safe. Both offload the target model only. With MTP speculative decoding (`--speculative-algorithm NEXTN`), the draft model has a QSA layer of its own, and its pool keeps the full K/V of every logical token on the GPU.

Once the target's K/V is on the host, that draft K/V is most of what a logical token still costs on the GPU. With a BF16 KV cache on Qwen3.8-Flash-Next, the pool configurator charges 27,456 B per token with MTP: 24,576 B of target K/V, 768 B of target index, and a 2,112 B draft share. Target offload leaves 2,880 B on the GPU, of which 2,048 B is draft K/V.

This PR adds `--qsa-kv-offload-draft`, which offloads the draft pool the same way, leaving 832 B per token on the GPU (the two indices).

**Series.** Stacked on PR 2/N (`qsa-kv-host-offload-fused`, whose verify mode already leaves CUDA-graph padding rows out) and must merge after it. Off by default; with the flag off, behaviour is unchanged.

## Modifications

- **`arg_groups/fields/memory.py`, `field_order.py`, `qsa_kv_offload_hook.py`:** `--qsa-kv-offload-draft` (bool, default off). Validation: it needs `--enable-qsa-kv-offload` and an MTP draft (`--speculative-algorithm NEXTN` or `EAGLE`). The startup layout check also covers the draft decode rows (below).
- **`mem_cache/kv_cache_configurator.py`:** the draft worker's `QSATokenToKVPool` gets the offload layout when the flag is on. A draft pool without a QSA profile is refused, since the sizing already moved its K/V to the host.
- **`model_executor/pool_configurator.py`:** the offload budget adds the draft's layers. Its K/V bytes per token move from the GPU cell to the host, and one more hot cache per request slot is charged. `--qsa-kv-offload-host-size` now covers both pools.
- **`layers/attention/qwen_sparse_attn_backend.py`, `layers/attention/qsa/kv_offload_attention.py`:**
  - The draft's three forward kinds run on its offloaded pool (the backend lets `DRAFT_EXTEND_V2` through to the offload paths):
    - EXTEND after a prefill: stored through the scratch rows and written through to the host; the context is gathered from the host.
    - `DRAFT_EXTEND_V2`: a fixed-width window of rows per request, resolved like a target verify.
    - The multi-step decode.
  - `QwenSparseMultiStepDraftBackend` sets the offload's real request count before every draft-decode graph replay. Its fast replay path does not go through `_replay_cuda_graph_metadata`, which sets it for the other forwards.
- **`mem_cache/qsa_kv_offload.py`, `qsa_kv_offload_kernels.py`:**
  - Draft decode steps reuse the draft-extend selection: its expanded top-k and the capture position's partial block, plus the positions drafted since (`QSAMTPSharedSparseIndices`). Once a step crosses a block boundary, those trailing single-position columns lie before the tail ring.
  - The layout gets `extra_columns` (draft pool: `compress_ratio - 1 + speculative_num_steps + 1`), and the hot-cache check requires room for one row's blocks plus them.
  - The fused resolve adds the blocks of such columns to its needed-block set (a constexpr `XT` branch; `XT = 0` for the target pool, whose kernel is unchanged). The torch reference resolve already handles any column.
  - The layout reserves room for several plain query rows per request or one row with extra columns, not both, so the fused resolve refuses that combination (no current forward produces it) and sizes its tables for the larger case.
- **`managers/scheduler.py`:** releases the draft pool's pinned host store at shutdown too.
- **Docs:** `server_arguments.mdx` row; the Qwen3.8-Flash-Next cookbook offload section explains the MTP case.
- **Tests:**
  - `test_qsa_kv_offload.py` (GPU): a draft-decode test for both resolves. The selection is captured at an earlier position, and the decode steps cross block boundaries and are rewound by verify rejections. The packed decode scratch must stay bit-identical to upstream's gather.
  - `test_qsa_kv_offload_unit.py` (CPU): the flag's validation, the layout's extra-column rule, and the torch resolve on draft decode rows.
  - `test_qsa.py`: the step-backend fake in the MTP CUDA-graph padding test gets `_kv_offload = None`, like `QwenSparseAttnBackend` (a class attribute, set from the pool in `__init__`). The draft backend now reads it before a graph replay.

## Accuracy Tests

The offload stays bit-exact.

- **Unit tests** (`test_qsa_kv_offload.py`, both resolves): the draft-decode rows (captured selection plus drafted positions, block crossings, verify rewinds, a capture shorter than the top-k) pack decode scratch bit-identical to upstream's gather through `req_to_token` on the full pool. With the series' `test_qsa_kv_offload_backend.py`, 17 GPU tests pass on RTX PRO 6000 Blackwell 600 W and on H100 (300 W at an earlier revision). The CPU tests (flag validation, layout rule, torch resolve on draft decode rows) pass 19/19.
- **End to end, verify mode, inside CUDA graphs** (`SGLANG_DEBUG_QSA_KV_OFFLOAD_VERIFY=1`, RTX PRO 6000 Blackwell Server Edition):
  - Setup: MTP (NEXTN, 3 steps, 4 draft tokens) with `--qsa-kv-offload-draft`, decode and draft CUDA graphs and overlap scheduling on, minimum hot cache (H = 2048).
  - Load: the 24-request mix of PR 1/N (long prompts up to 29K tokens, multi-turn radix hits, a shared 20K prefix, concurrent batches).
  - Result, with every decode batch size captured: **0 mismatches** in >= 10,236 target-pool and >= 2,421 draft-pool checks. All 24 requests were served, with accept length 3.76.
- **End to end, verify mode, on 8x H100 80GB HBM3** with the public `Qwen/Qwen3.8-Flash-Next-FP8` at `--tp 8 --ep-size 8`, the same MTP settings, `--qsa-kv-offload-draft`, H = 2048 and decode and draft CUDA graphs: all 24 requests served, **0 mismatches** on every TP rank in >= 8,508 target-pool and >= 2,021 draft-pool checks per rank; accept length 3.81.
- **gsm8k** (`sgl-eval run gsm8k --num-examples 200 --temperature 0 --max-tokens 4096`, same GPU, MTP on, target offload on): `--qsa-kv-offload-draft` off **96.00%**, on **96.50%**. MTP accept length 2.98 in both arms (mean over the server's decode log lines).
- Token identity vs `main` is not gated on SM120 (see PR 1/N).

## Speed Tests and Profiling

Public `nvidia/Qwen3.8-Flash-Next-NVFP4` with its MTP head, same GPU (RTX PRO 6000 Blackwell Server Edition, 600 W), one server per arm, run back to back. Both arms have MTP on and the target offload on; arm B adds `--qsa-kv-offload-draft`. Common flags: `--tp 1 --quantization modelopt_fp4 --mem-fraction-static 0.93 --disable-prefill-cuda-graph --chunked-prefill-size 4096 --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 --mamba-ssm-dtype bfloat16 --mamba-radix-cache-strategy extra_buffer_lazy --enable-qsa-kv-offload --qsa-kv-offload-host-size 80 --qsa-kv-offload-hot-blocks 2048` (decode CUDA graphs on).

**Capacity** (`--max-running-requests 8 --context-length 131072 --max-mamba-cache-size 32`, startup logs):

| | Draft K/V on the GPU | `--qsa-kv-offload-draft` |
|---|---|---|
| `max_total_num_tokens` | 1,110,336 (GPU-bound) | 3,004,736 (host-bound; the GPU alone allows 3,618,572) |
| GPU bytes per logical token | 2,880 | 832 |

**KV-bound serving** (`--max-running-requests 12 --context-length 131072 --max-mamba-cache-size 48`; `python -m sglang.benchmark.serving --dataset-name random-ids --random-input-len 102400 --random-output-len 1024 --random-range-ratio 1.0 --num-prompts 12 --max-concurrency 12`, 2 repeats per arm, median [min-max]):

| | Draft K/V on the GPU | `--qsa-kv-offload-draft` |
|---|---|---|
| `max_total_num_tokens` | 173,056 | 292,224 |
| Requests decoding at once | 1 | 2 |
| Output throughput (tok/s) | 70.6 [68.3-72.9] | **86.7 [82.6-90.8]** (+23%) |
| Benchmark duration (s) | 174.3 [168.6-179.9] | 142.0 [135.3-148.7] |
| Median TPOT (ms) | 5.93 [5.69-6.17] | 14.53 [14.25-14.80] |
| MTP accept length (median of decode log lines) | 3.00 (206 lines) | 3.16 (101 lines) |

With the draft K/V on the GPU, the pool holds one 100K-token session at a time; with it on the host, two. The TPOT rises because two requests share each decode step; the throughput gain comes from that concurrency.

When the pool is not the limit, the flag costs little: at 61K x 8 (concurrency 8, 512 output tokens) a single run per arm gave 78.9 vs 81.0 output tok/s, and at 123K x 8 (256 output tokens) 21.1 vs 20.9 tok/s.
