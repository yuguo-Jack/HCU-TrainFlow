# [Fix] dsv4: Mirror SGLANG_DEFAULT_THINKING between prompt and reasoning parse sides

[Upstream PR](https://github.com/sgl-project/sglang/pull/45804) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45614.

Serving a DeepSeek V4.x model with the cookbook's agentic recipe env `SGLANG_DEFAULT_THINKING=1`, a `/v1/chat/completions` request that carries **neither** `reasoning_effort` **nor** `chat_template_kwargs.thinking` returns the model's raw thinking text merged into `content`, with `reasoning_content: null`. Adding `reasoning_effort` (any value other than `none`) makes the split work, which points at a prompt-side vs parse-side disagreement about the *default* thinking state:

1. **Prompt side** — `_apply_jinja_template` resolves `thinking_requested = (request.chat_template_kwargs or {}).get("thinking", envs.SGLANG_DEFAULT_THINKING.get())` and passes the resulting `ThinkingMode` to the dsv4/dsv41/dsv32 encoders. With the env set and no kwarg, the encoder appends the thinking opener: the prompt **is** in thinking mode.
2. **Request mapping** — `protocol.py` only writes `chat_template_kwargs["thinking"]` when `reasoning_effort` (or `reasoning.enabled`) is present, so a bare request leaves it unset.
3. **Parse side** — `_get_reasoning_from_request` for the `explicit_thinking` detectors (`deepseek-v41`/`deepseek-v4`/`deepseek-v3`) returned `True` only for an explicit `thinking=True` kwarg and never consulted `SGLANG_DEFAULT_THINKING`, so the reasoning parser was built with `force_reasoning=False`.
4. With the opener consumed by the prompt, the output contains no think-start token, so the detector emitted everything — thinking text, the think-end token, and the answer — as normal `content`.

The Responses API path has the same disagreement: `OpenAIServingResponses._is_thinking_enabled_for_request` returned `False` for explicit-thinking parsers while its prompts (shared via `_process_messages`) were env-defaulted into thinking mode.

## Modifications

- **`chat_encoding.py`**: new `spec_prompt_reads_default_thinking_env(spec)` — answers whether the encoder for a spec builds the prompt's thinking mode from the `thinking` kwarg with an `SGLANG_DEFAULT_THINKING` fallback. True for `dsv4`/`dsv41`/`dsv32` (the DeepSeek native encoders); `kimi_k3`/`inkling`/jinja templates don't consume the env default, so they stay `False`.
- **`serving_chat.py`** (`_get_reasoning_from_request`): for those specs, resolve the read side from the same source as the prompt — an explicit `thinking` kwarg wins, otherwise `SGLANG_DEFAULT_THINKING`. Placed after the parser special cases, before the template-config logic.
- **`serving_responses.py`** (`_is_thinking_enabled_for_request`): same fallback, after the explicit-toggle and `force_reasoning` checks.
- **Jinja-template models are intentionally untouched**: their prompts never apply the env default (template kwargs stay verbatim), so the read side keeps following the template's own `ReasoningToggleConfig` default. This also means the reverse case is now consistent — `SGLANG_DEFAULT_THINKING=0` with a template whose `default_enabled=True` no longer matters for dsv4x, since the encoder (not the template) owns those prompts and both sides follow the env.

## Accuracy / Regression Tests

Two unit tests in `test/registered/unit/entrypoints/openai/test_serving_chat.py` (CPU suite, no server needed):

- `test_dsv41_reasoning_mirrors_default_thinking_env` — with spec `dsv41`: env=1 + no kwarg → reasoning enabled (the reported bug); explicit `thinking=True`/`thinking=False` still win over the env in both env states; env unset → disabled.
- `test_jinja_explicit_reasoning_ignores_default_thinking_env` — guard that the jinja path (spec `None`, `deepseek-v3` detector) keeps ignoring the env for explicit-thinking parsers, while an explicit `thinking=True` still enables.
