# [Fix] [Intel] layers: Guard torch.compile calls against XPU in vocab/rotary embeddings

[Upstream PR](https://github.com/sgl-project/sglang/pull/46318) · state: closed · merged: False

## Original PR description

## Motivation

`VocabParallelEmbedding.get_masked_input_and_mask` (`vocab_parallel_embedding.py`) and `apply_rotary_pos_emb_native` (`rotary_embedding/utils.py`) are both `@torch.compile`-decorated without an XPU guard. torch.compile/Inductor codegen on Intel XPU under tensor parallelism is unreliable for these functions, causing either:

- a scheduler watchdog timeout (stuck in Inductor's compile-worker subprocess, visible in a thread dump under `torch/_inductor/compile_worker/subproc_pool.py`), or
- a hard crash: `RuntimeError: level_zero backend failed with error: 20 (UR_RESULT_ERROR_DEVICE_LOST)` or `error: 40 (UR_RESULT_ERROR_OUT_OF_RESOURCES)`, surfacing at the next CPU/GPU sync point (e.g. a `.item()` call in an unrelated function further down the call stack), which makes the crash site misleading relative to the actual cause.

This affects any TP>1 model on `intel_xpu` that routes position-embedding lookups through `VocabParallelEmbedding`/`ParallelLMHead`, or that calls `apply_rotary_pos_emb` from `rotary_embedding/utils.py` (used directly by some vision towers and `gemma3_causal.py`, separate from the `RotaryEmbedding` class in `rotary_embedding/base.py`, which already has proper XPU handling via a dedicated fused kernel).

`sglang/srt/speculative/spec_utils.py` already guards an identical `torch.compile` pattern with `disable=_is_npu or _is_xpu` — these two call sites were simply missed when XPU support was added elsewhere in the codebase.

## Modifications

- `python/sglang/srt/layers/vocab_parallel_embedding.py`: add `_is_xpu = is_xpu()`, change `get_masked_input_and_mask`'s decorator from `disable=_is_npu` to `disable=_is_npu or _is_xpu`.
- `python/sglang/srt/layers/rotary_embedding/utils.py`: add `_is_xpu = is_xpu()`, change `apply_rotary_pos_emb_native`'s decorator from no `disable` argument to `disable=_is_xpu`. (Left NPU behavior here untouched — this decorator previously compiled unconditionally, including on `apply_rotary_pos_emb_npu`'s fallback path for shapes it doesn't support, and I haven't validated disabling compile there, so I didn't bundle an NPU behavior change into an XPU fix.)

## Accuracy Tests

Validated on real hardware (4x Intel Arc Pro B60, TP4, `intel_xpu` backend) running a vision-language model whose vision tower hits both call sites (position-embedding lookup via `VocabParallelEmbedding`, and rotary embeddings via `apply_rotary_pos_emb` in the vision attention path):

- Before fix: crashed on the very first vision-embedding lookup (0% progress), every run.
- After the `vocab_parallel_embedding.py` fix alone: progressed much further, but a full-dataset accuracy run still crashed partway through (~20%) with the same `UR_RESULT_ERROR_DEVICE_LOST` signature, now originating from the second, previously-unidentified `apply_rotary_pos_emb_native` compile site.
- After both fixes together (plus a request-concurrency cap to stay within available device memory, unrelated to this change): a full accuracy run completed end to end with zero crashes across multiple runs (300 and 5349 examples), accuracy scores in the expected range for the task and model.

Also added `test/registered/xpu/test_vocab_rotary_torch_compile_xpu_guard.py`, run on the same hardware:
- Direct regression check that `torch.compile` is actually disabled on XPU for both functions (checks for the absence of `_torchdynamo_orig_callable` -- `torch.compile(fn, disable=True)` returns `fn` itself, unwrapped). Verified these two assertions fail if the `_is_xpu` guard is reverted, so they'd catch a future regression without needing to reproduce the original multi-GPU TP hang/crash.
- Functional correctness of both functions on an XPU device, parametrized over dtypes/shapes.
- All 12 tests pass with the fix in place.

## Speed Tests and Profiling

Not applicable — this change only disables `torch.compile` for the XPU device path (no effect on CUDA/CPU/NPU), replacing an unreliable/crashing compiled kernel with the existing eager fallback. No speed comparison was run since the XPU path did not previously complete.
