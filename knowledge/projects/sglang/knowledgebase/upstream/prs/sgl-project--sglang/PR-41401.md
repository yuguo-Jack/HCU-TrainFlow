# [Perf] [XPU] diffusion: Use the AOT SYCL fused residual-norm-scale-shift kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/41401) · state: open · merged: False

## Original PR description

## Motivation

On XPU, `ScaleResidualLayerNormScaleShift.forward_xpu` runs a triton kernel that blocks regional `torch.compile` of a Wan2.2 DiT block. Inductor re-lowers the kernel and Intel triton fails to compile the result:

```
triton/backends/intel/compiler.py: make_llir -> RuntimeError: PassManager::run failed
```

This happens in the first denoise step, so compiled Wan2.2 cannot run on XPU today. sgl-kernel-xpu ships an AOT SYCL kernel for the same op (sgl-project/sgl-kernel-xpu#497), in the `sglang-kernel-xpu` 0.4.0 wheel already pinned in `pyproject_xpu.toml`. It is a registered custom op, so inductor keeps it opaque and compiled regions call it unchanged.

## Modifications

- `kernels/ops/diffusion/norm/scale_residual_norm_scale_shift_sycl.py` (new): the SYCL backend, exported through the `ops.diffusion` facade.
  - `can_use_fused_scale_residual_norm_scale_shift_sycl` reuses the triton eligibility check for shape, device and contiguity, and adds the kernel's dtype rule. Gate, weight and bias must share one dtype. Scale and shift are cast to it only when the cast is exact (same dtype, or an upcast to fp32); any other mix stays on triton.
  - `fused_scale_residual_norm_scale_shift_sycl` calls `torch.ops.sgl_kernel` directly, so operands are validated once by the op's C++ checks.
  - A `register_fake` companion lets Dynamo trace the op, since sgl-kernel-xpu registers only the XPU implementation.
- `layernorm.py`: `forward_xpu` prefers the SYCL kernel, then triton, then `forward_native`. The import sits in the existing `_is_xpu` block next to `fused_inplace_qknorm_rope`, so other platforms never load it.

No model code changes. Wan's self-attention site passes bf16 1-element null shift/scale next to an fp32 gate and fp32 affine parameters. The exact upcast keeps that site on the SYCL path, so other devices see no change.

## Speed Tests and Profiling

Wan2.2-I2V-A14B, TP=4 on 4x Arc Pro B60, 832x480 resolution, 21 frames, 20 steps, warm caches, first run of the session discarded:

```bash
CCL_ZE_IPC_EXCHANGE=pidfd sglang generate \
  --model-path Wan-AI/Wan2.2-I2V-A14B-Diffusers --num-gpus 4 --tp-size 4 \
  --text-encoder-cpu-offload --pin-cpu-memory \
  --image-path <i2v_input.JPG> --prompt "<prompt>" \
  --height 480 --width 832 --num-frames 21 --num-inference-steps 20 --seed 42 \
  [--enable-torch-compile --regional-compile]   # SGLANG_TORCH_COMPILE_MODE=default
```

| Mode | Denoise before (s) | Denoise after (s) |
|---|---|---|
| eager | 100.43 / 100.10 | 100.10 / 100.05 |
| regional compile | fails at step 0 | 82.74 / 82.74 |

- Eager is unchanged. Both kernels cost about 1.8 ms per call on the GPU at the Wan shape, and the host queues all steps well ahead of the device.
- Regional compile now runs, and its denoise time is 17% below eager (1.21x).
- Compiled end-to-end time is still higher than eager because `--enable-torch-compile` also compiles `vae.decode`. That is unrelated to this PR.
