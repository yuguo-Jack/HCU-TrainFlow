# [Perf] GGUF: merged linear shards as flat views, no per-forward weight copy

[Upstream PR](https://github.com/sgl-project/sglang/pull/43430) · state: open · merged: False

## Original PR description

## Motivation

`GGUFLinearMethod` packs the shards of a merged layer (`QKVParallelLinear`, `MergedColumnParallelLinear`) into one zero-padded 2D block `[sum(rows), max(row_bytes)]`, and `apply()` cuts each shard out on every forward:

```python
qweight[start:end, :offset].contiguous()
```

When all shards share one GGUF type this slice covers full rows and `.contiguous()` is free. When they don't (different row widths, which is common in i-quant and mixed GGUFs, e.g. `q` in IQ3_S and `k`/`v` in a wider type), the slice is not contiguous and every decode step copies every such weight. In an nsys trace of one decode step this showed up as a `direct_copy` elementwise kernel plus the cat, ~20 us per layer.

## Modifications

`python/sglang/srt/layers/quantization/gguf.py`, `GGUFLinearMethod` only (the Ascend method pre-dequantizes and is untouched):

- `_create_padded_weight_param` -> `_create_merged_weight_param`: the shards are laid end to end in one flat 1D buffer, without padding, in the same logical order as before (`_ordered_gguf_shard_ids`). The shard map is now `shard_flat_map: {shard_id: (offset, rows, row_bytes)}` (replaces `shard_offset_map`).
- `apply()`: each shard is `qweight[offset : offset + rows * row_bytes].view(rows, row_bytes)`, a contiguous view with no copy. The views are cut from `layer.qweight` on every call, so nothing that could go stale is cached. Neighbouring shards with the same GGUF type and row width (adjacent in the buffer) run as one GEMM: one activation quantization and one launch instead of several, and fewer pieces to concatenate. With a single group the `torch.cat` is skipped.
- Side effect: the zero padding of the merged block is no longer allocated.
- `test/registered/expert_pack/test_kimi_k3_gguf.py`: the existing logical-order test is updated to the flat layout (`shard_flat_map` on a 1D buffer, buffer order deliberately different from the logical order).

The weight bytes fed to each kernel are the same as before; only the layout of the merged parameter and the number of calls change. The buffer is allocated once at load time and the views have static addresses, so CUDA graph capture is unaffected.

## Accuracy Tests

- Greedy decode output is unchanged with this patch on a mixed-type IQ3_S GGUF (dense weights kept in their GGUF types), TP2.
- CPU self-check (not part of the PR): the old and new `GGUFLinearMethod` code is executed on fake merged layers with a recording stand-in for `fused_mul_mat_gguf`. For qkv with mixed widths, gate_up with one type, four shards with alternating widths, and same type with different widths, the per-shard bytes handed to the GEMM are byte-identical to the loaded shards, each new view shares storage with `layer.qweight` (no copy), and the layer outputs are identical. Calls per forward: qkv mixed 3 -> 2, gate_up 2 -> 1. Merged buffer size: e.g. 544 -> 416 bytes for the mixed qkv case (padding gone).
- Grouping only concatenates rows of the same type and width. In the decode case (small batch, MMVQ) each output row is computed independently, so results are bitwise the same. One thing to note for reviewers: `fused_mul_mat_gguf` picks MMVQ vs. MMQ/dequant by batch size with a threshold that depends on `qweight.shape[0] > 5120`, so a grouped call can cross that threshold for batch sizes between the two limits (3-6, or 9-16 for i-quants). That is the same choice an unsharded layer of the grouped size would get; batch 1-2 is unaffected. For larger batches the MMQ / dequant + GEMM paths see a wider N, which can change accumulation order at the float rounding level only.

## Speed Tests and Profiling

Mixed-type IQ3_S GGUF, dense weights kept in their GGUF types, TP2 on 2x RTX 5070 Ti (routed experts on CPU, so absolute tok/s reflects that setup; the A/B below changes only this patch, same launch otherwise). nsys per decode step:

| | before | after |
|---|---|---|
| shard copies (`direct_copy` + cat) | ~20 us / layer | 0 |
| decode forward | 15.19-15.60 ms | 14.15-14.63 ms |
| decode throughput | 59.7-61.7 tok/s | 63.8-64.5 tok/s |

Same-type grouping on top of the flat views: forward median 14.05 -> 13.87 ms.

For single-type GGUFs the old slice was already contiguous, so they only gain the grouping (one launch for gate_up / qkv instead of two or three).
