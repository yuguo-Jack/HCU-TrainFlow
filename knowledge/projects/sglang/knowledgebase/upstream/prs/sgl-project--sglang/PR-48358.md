# [Perf] [Intel] kv-canary: Add an on-device XPU fallback for plan/verify/write

[Upstream PR](https://github.com/sgl-project/sglang/pull/48358) · state: closed · merged: False

## Original PR description

## Motivation
On XPU the kv-canary plan/verify/write ops fall back to the Python references (`*_ref.py`), which copy `req_to_token` to host and loop per token. Decode drops to 2-3 tok/s with the canary on, and all 11 kv_canary e2e tests time out on XPU.

## Modifications
- `kernels/ops/kv_canary/_tensor_fallback.py` (new, XPU only): vectorized on-device plan entries, verify and write, with no host sync. Plan reuses the existing Triton offsets kernel.
- `plan/api.py`, `verify.py`, `write.py`: dispatch to it when `device.type == "xpu"`. CUDA keeps the JIT kernels; other devices keep the references.
- `test/kv_canary/e2e_base.py`: use `--attention-backend intel_xpu` on XPU (the default Triton backend is too slow for the ~7k-token workload).
- `test_tensor_fallback.py` (new, XPU CI): 120 differential tests, byte-equal against the Python references (plan, verify, write; MHA/SWA, all real-KV hash modes, duplicate slots, ring overflow).

## Accuracy Tests
Byte-equal to the references: 120/120 pass. kv_canary e2e on Arc Pro B60, 11/11 pass (baseline MHA/SWA, perturb_real_kv_used x3, perturb_real_kv_unused_cache x3, perturb_req_to_token x2, pr_25015). Perturbation tests still report the expected violations.

## Speed Tests and Profiling
Qwen3-0.6B, 8 requests, canary on, Arc Pro B60:

| | Decode |
|---|---|
| Python reference | 2-3 tok/s |
| This PR | ~220 tok/s |

With only the attention-backend change the tests still time out (2.96 tok/s); the reference ops were ~99% of each decode step.
