# [Sampler] Sort only the max(top_k) leading columns in the torch sampler

[Upstream PR](https://github.com/sgl-project/sglang/pull/43346) · state: closed · merged: True

## Original PR description

## Motivation

`top_k_top_p_min_p_sampling_from_probs_torch` sorts the whole vocabulary on every decode step and then zeroes every column at rank `>= top_k`:

```python
probs_sort, probs_idx = probs.sort(dim=-1, descending=True)
...
probs_sort[torch.arange(0, probs.shape[-1], ...).view(1, -1) >= top_ks.view(-1, 1)] = 0.0
```

On ROCm this is the default sampler, not a fallback: `is_flashinfer_available()` requires CUDA, so `sampling_backend` resolves to `pytorch`. Any request with a finite `top_k` takes this path. Through the OpenAI-compatible endpoints the model's `generation_config` supplies one by default, e.g. `top_k=20` for the Qwen3 / Qwen3.5 / Qwen3.8 families. With vocabularies of 152k–248k tokens the full sort dominates the sampler.

## Modifications

- When every row has a finite `top_k`, sort only the `max(top_k)` leading columns with `torch.topk(..., sorted=True)`. Every column past each row's `top_k` is zeroed afterwards anyway, so the leading `max(top_k)` columns hold all the mass that survives: the top-p cumulative sum, the min-p threshold (`probs_sort[:, 0]`) and the sampled token are unchanged.
- The bound is a host-side field, `SamplingBatchInfo.max_top_k`, built from the request params next to `npu_top_k_top_p_eligible`, so the sampler adds no device-to-host sync. It is `None` when any row samples from the whole vocabulary. `merge_batch` takes the max (or `None`); `filter_batch` keeps it unchanged, since any upper bound stays exact. `SamplingBatchInfo` objects built elsewhere (e.g. the EAGLE draft CUDA graph) leave it `None` and keep the full sort.
- Two paths keep the full sort:
  - The seeded path (deterministic inference). The bound is batch-wide, and the order `topk` gives tied probabilities may depend on `k`; deterministic results must not depend on batch composition.
  - `return_filtered_probs=True`, whose sorted tensors are handed to the sampling-mask capture.

Related: #33539 (open) changes this function to keep tokens tied with the k-th probability. Those can sit past rank `max(top_k)`, so if both land, the bound needs to cover the tie set.

## Accuracy Tests

- `test/registered/unit/sampling/test_torch_sampling_top_k_bound.py` (new, CPU): with `torch.multinomial` replaced by argmax, the bounded sort yields the same tokens and exactly the same weights as the leading `max(top_k)` columns of the full sort, and the full sort's remaining columns are all zero. It covers mixed per-row `top_k`, top-p and min-p, plus `return_filtered_probs` and a bound at the vocabulary size keeping the full width.
- `test_sampling_batch_info.py`: `max_top_k` construction, merge and filter.
- `test/registered/unit/sampling/`: 216 passed.

End to end on MI355X (gfx950), ROCm 7.2.0, torch 2.9.1, Triton 3.7.0; sglang `main` @ `3ab142adc4` with a `sgl-kernel` build from the same tree and AITER `e7d2453f` (pinned in `docker/rocm.Dockerfile`). Qwen3.5-35B-A3B, TP1, default server args (`sampling_backend=pytorch`).

GSM8K, all 1319 questions, chat API, `temperature=0.7, top_p=0.95, top_k=20`:

| | GSM8K | Output tok/s during the eval |
|---|---|---|
| `main` | 0.482 | 4392 |
| This PR | 0.496 | 5703 |

The difference is within sampling noise (std ≈ 0.014). The absolute score is low because the model thinks by default and the eval's 2048-token cap truncates many answers; both runs use the identical harness.

Serving, Qwen3.5-35B-A3B (vocab 248320), `bench_serving --backend sglang --dataset-name random-ids --random-input-len 1024 --random-output-len 512 --random-range-ratio 1.0`, `num_prompts = 4 × concurrency`, sampling params `temperature=0.7, top_k=20, top_p=0.95`:
