# fix(openai): honor tool_choice=none in DeepSeek encoders

[Upstream PR](https://github.com/sgl-project/sglang/pull/43006) · state: open · merged: False

## Original PR description

## Motivation

OpenAI defines `tool_choice: "none"` as generating a message without calling any tool. SGLang's [shared prompt-building path](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/serving_chat.py#L1386-L1400) already leaves active `tools` unset for this value, and its [response path disables tool-call parsing](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/serving_chat.py#L1015-L1025). However, the [custom DeepSeek branch](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/serving_chat.py#L1590-L1602) bypassed the shared input decision by reading `request.tools` directly and rendered the tool schema plus [DSML call instructions](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/encoding_dsv41.py#L76-L92) into the model prompt.

The custom DSV4.1 encoder was introduced in [#39665](https://github.com/sgl-project/sglang/pull/39665), which preserves client-supplied tool fields and ordering and validates the encoding against the V4.1 reference. This PR leaves that serialization unchanged; it only withholds the tool payload when SGLang's shared active-tool decision is `none`.

That mismatch can expose the model to DSML tool-call instructions while the response path treats its output as ordinary text. On DeepSeek-V4.1-Flash, the minimized failure had this shape:

```text
request.tool_choice = "none"
response.message.tool_calls = null
response.message.content contains a raw <｜DSML｜ calls> invocation
response.finish_reason = "stop"
```

Minimal HTTP reproduction:

```bash
curl http://localhost:30000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "deepseek-ai/DeepSeek-V4.1-Flash",
    "messages": [{"role": "user", "content": "Solve 100 divided by 7."}],
    "tools": [{
      "type": "function",
      "function": {
        "name": "calculator",
        "parameters": {
          "type": "object",
          "properties": {"expression": {"type": "string"}},
          "required": ["expression"]
        }
      }
    }],
    "tool_choice": "none",
    "temperature": 0
  }'
```

Expected: a normal assistant message with no tool call and no DSML tool-invocation syntax in `content`.

This restores SGLang's existing input/output decision for `none`, while preserving the observable [OpenAI Chat Completions contract](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create): the model does not call a tool and instead generates a message.

## Modifications

- Reuse `_process_messages`' normalized active-tool decision when populating the custom DeepSeek encoder input.
- Omit tool schemas from `dsv4`, `dsv32`, and `dsv41` prompts when `tool_choice` is `none`.
- Preserve the existing typed payload and prompt behavior for active tool modes.
- Add a CPU unit test covering `none` and `auto` for all three DeepSeek encoding specifications.

This PR does not change tool parsing, detector behavior, tool schema serialization, or inference kernels.

## Accuracy Tests

This is a request-contract fix, not a model-forward change. The registered CPU test covers `none` and `auto` across `dsv4`, `dsv32`, and `dsv41`. Pre-commit, `py_compile`, and `git diff --check` passed for all changed files. The unit test and an end-to-end `none`/`auto`/`required` canary remain for hosted CI because the local source environment lacks PyTorch.

## Speed Tests and Profiling

Not applicable. This PR does not change model execution, scheduling, or kernels. Requests using `tool_choice: "none"` render a shorter prompt because unused tool definitions are omitted.

## Compatibility and Merge Danger

- **Door and blast radius:** Two-way; limited to OpenAI-compatible chat requests using `dsv4`, `dsv32`, or `dsv41` encoders.
- **Intentional behavior change:** `tool_choice: "none"` no longer exposes tool schemas or tool-call instructions to the model.
- **Preserved behavior:** Active modes retain the original typed payload, including DSV4.1 serialization.\n
