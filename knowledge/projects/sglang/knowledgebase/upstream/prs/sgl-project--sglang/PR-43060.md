# [Feat] [XPU] distributed: Enable symmetric-memory one-shot all-reduce

[Upstream PR](https://github.com/sgl-project/sglang/pull/43060) · state: open · merged: False

## Original PR description

## Motivation

On Intel XPU, tensor-parallel all-reduce always goes through `XpuCommunicator`, a plain `dist.all_reduce` over oneCCL. The latency-oriented paths other platforms have (custom AR v1/v2, quick AR, mscclpp, PyNCCL) are CUDA/ROCm-only. At decode, each all-reduce is a few KiB to a few tens of KiB, so oneCCL's fixed cost (about 17 µs at 4 ranks and 31 µs at 8 on Arc Pro B60) dominates.

torch-xpu-ops already ships `XPUSymmetricMemory`: an allocator, IPC rendezvous over `syclexp::ipc_memory`, signal pads and a barrier. It registers none of the `symm_mem::*` reduce ops, though, and Xe reports no multicast, so `TorchSymmMemCommunicator` disables itself on XPU. This PR adds the missing reduce behind the existing `--enable-torch-symm-mem` flag. Under XPU graph replay it is 1.25-2.2x faster than oneCCL for decode-sized payloads, and oneCCL keeps every case where it is not clearly faster.

## Modifications

- **`device_communicators/xpu_symm_mem.py`**: `XpuSymmMemCommunicator`. Each call does three steps:
  1. stage the input in this rank's symmetric buffer;
  2. one barrier;
  3. a Triton kernel reads every rank's staged input and sums it in fp32 in ascending rank order, so every rank gets a bitwise-identical result.
- **One barrier per call:** the buffer holds two staging halves, and calls alternate between them. The half is chosen by a call counter kept on the device, so captured graphs alternate halves on every replay. A rank restages a half only after the next call's barrier, which every peer reaches only after it has read that half.
- **`hardware_backend/xpu/kernels/comm/one_shot_all_reduce.py`**: the stage and reduce kernels, with 256-element blocks and 4 warps. On B60, 8 elements per thread stalled the peer reads at 6 ranks.
- **`device_communicators/symm_mem_workspace.py`**: `SymmMemWorkspace` does the setup:
  - allocation and rendezvous;
  - the backend, world-size and single-node checks (via `in_the_same_node_as`);
  - the peer pointer table (via `make_ptr_table`).

  `all_ranks_agree` reduces the go/no-go decision over the group. A follow-up MoE all-to-all (`--moe-a2a-backend symm_mem`) builds on the same workspace.
- **`device_communicators/all_reduce_utils.py`**: `XPU_SYMM_MEM_ALL_REDUCE_MAX_SIZES`, the per-world-size payload ceiling: the largest size where the path clearly beat oneCCL on both hosts measured below. Other world sizes keep the path off.

  | World size | Ceiling |
  |---|---|
  | 2 | 32 KiB |
  | 4 | 16 KiB |
  | 6 | 16 KiB |
  | 8 | 8 KiB |
- **`environ.py`**: `SGLANG_XPU_SYMM_MEM_MAX_BYTES` (unset by default) overrides the ceiling, for systems whose peer bandwidth differs from B60 over PCIe, such as Xe Link.
- **`parallel_state.py`**: `GroupCoordinator.xpu_symm_mem_comm`, read only by `_all_reduce_in_place`.
  - The path is used only while an XPU graph is being captured. In eager mode its two Triton launches cost more host time than one oneCCL call at every size.
  - `torch_symm_mem_comm` is unchanged, so the Inkling kernels and the outplace path still see the CUDA communicator and fall back on XPU as before.
- **`scripts/ci/xpu/xpu_ci_start_container.sh`**: starts the CI container with `--cap-add SYS_PTRACE`. Rendezvous imports peer allocations with `pidfd_getfd`, which Docker's default seccomp profile blocks without it.
- **Docs:** `--enable-torch-symm-mem` in `server_arguments.mdx` and its help text; `SGLANG_XPU_SYMM_MEM_MAX_BYTES` in `environment_variables.mdx`.

Behaviour and guards:

- **Off by default:** without `--enable-torch-symm-mem`, nothing changes on any platform.
- **Fallback to oneCCL:** eager calls, payloads above the ceiling, dtypes other than bf16/fp16/fp32, non-contiguous inputs, and sizes that aren't a multiple of 4 bytes.
- **Self-disabling:** the communicator turns itself off with a warning if:
  - the backend isn't `XPU`;
  - the group has more than 8 ranks or spans hosts;
  - rendezvous fails;
  - a kernel fails to build.

  Both kernels are pre-built for every supported dtype without any cross-rank wait, and the decision is agreed on every rank before the first barrier runs. A rank that is slow or fails in setup therefore can't leave the others spinning in a device barrier.
- **Ptrace exposure:** torch-xpu-ops calls `prctl(PR_SET_PTRACER, PR_SET_PTRACER_ANY)` during rendezvous, so with the flag on, any process of the same user can ptrace the server.
- **Determinism:** `--enable-deterministic-inference` still turns `--enable-torch-symm-mem` off, as on CUDA. The kernel is order-deterministic, but choosing an algorithm by payload size is not batch-invariant.

## Accuracy Tests

`python test/registered/xpu/test_xpu_symm_mem_all_reduce.py` relaunches itself under torchrun on 2 XPUs (registered in `nightly-xpu-kernel-main-2-gpu`). All 4 cases pass on both hosts below with torch 2.14.0.dev20260720+xpu, and on bmg17690 also with the torch 2.13.0+xpu (oneAPI 2026.0) and 2.14.0+xpu (oneAPI 2026.1) releases:

- **Exact results:** bitwise exact (`atol=0, rtol=0`) against an fp32 sum over ranks in ascending order. Covered: bf16, fp16 and fp32 at 128, 3584 and 131072 elements, out of place and in place.
- **Fallbacks:** ineligible inputs return `None`, so the caller falls back.
- **Lagging peer:** a peer that lags between the barrier and its read still sees this call's data. This case fails, with 87.5% of elements wrong, if the two halves stop alternating.
- **Routing through `GroupCoordinator`:** `all_reduce` keeps eager calls on oneCCL, and a captured call takes the one-shot path and returns the correct sum on replay.

Also checked outside the test file:

- **Graph replay:** a captured call replayed 200 times back to back, with fresh inputs and no host sync, had 0 mismatches at 2, 4, 6 and 8 ranks.
- **Not run yet:** a model-level accuracy eval. The fp32 ordered sum reduces in a different order from oneCCL, so outputs can differ from the default path in the last bits.

## Speed Tests and Profiling

How this was measured:

- **Workload:** per-call latency of one all-reduce of `tokens x 4096` bf16, against `dist.all_reduce` over the XCCL group.
- **Graph replay:** 20 calls captured in one `torch.xpu.XPUGraph`, replayed 30 times.
- **Host A, emr816610:** 8x Arc Pro B60, all PCIe Gen5 x8, dual-socket Xeon 8592+ (GPUs 0-3 on socket 0, 4-7 on socket 1).
- **Host B, bmg17690:** 8x Arc Pro B60. One card trained its PCIe link at Gen2, so host B runs used only the Gen5 cards, and there is no 8-rank row for it.

Graph replay, µs per all-reduce, one-shot / oneCCL. Bold values are inside the default ceiling, which is where the one-shot path is used.

**Host A, emr816610:**

| Payload | 2 ranks | 4 ranks | 6 ranks | 8 ranks |
|---|---|---|---|---|
| 8 KiB | **7.2** / 9.4 | **8.5** / 16.6 | **13.1** / 23.9 | **14.3** / 30.9 |
| 16 KiB | **7.5** / 9.9 | **10.6** / 17.0 | **18.7** / 24.9 | 35.2 / 30.4 |
| 32 KiB | **8.7** / 11.1 | 16.9 / 17.0 | 30.0 / 25.0 | 76.7 / 30.5 |
| 64 KiB | 11.6 / 11.7 | 25.4 / 19.2 | 47.8 / 26.1 | 142.0 / 31.0 |

**Host B, bmg17690:**

| Payload | 2 ranks | 4 ranks | 6 ranks |
|---|---|---|---|
| 8 KiB | **8.0** / 10.0 | **9.3** / 17.8 | **12.9** / 26.0 |
| 16 KiB | **8.4** / 10.6 | **12.1** / 17.7 | **16.4** / 26.4 |
| 32 KiB | **9.7** / 12.1 | 16.4 / 18.0 | 24.3 / 27.2 |
| 64 KiB | 11.5 / 12.2 | 23.7 / 19.7 | 40.4 / 27.3 |

- **Why the ceiling shrinks as ranks grow:**
  - Each rank reads (world_size - 1) x payload from its peers, so the total traffic is world_size x (world_size - 1) payloads. oneCCL's total is about 2 (world_size - 1) payloads.
  - Total peer-to-peer throughput across all cards stayed near 36-45 GB/s on both hosts, regardless of rank count, and crossing sockets made no difference at 4 ranks.
  - So the one-shot path loses once the transfer is bandwidth-bound, earlier at more ranks: from 16 KiB at 8 ranks.
- **What dominates at small sizes:** the barrier, 4.3 µs at 2 ranks up to about 11 µs at 7. One cross-card signal alone takes about 4.2 µs one way.
- **Eager mode,** which is the XPU default since decode graphs are opt-in, is not used. It takes 50-60 µs against 17-31 µs for oneCCL, because each Triton launch costs about 12-19 µs of host time on XPU, about 12 µs even when the compiled kernel is launched directly.
- **Not measured yet:** end-to-end throughput.

**Known issue, outside this PR (XCCL under graph capture):** with the torch 2.14.0+xpu release, whose wheels pin oneCCL 2022.1.1, a `dist.all_reduce` over XCCL issued during XPU graph capture is silently dropped.
- It does not run at capture time, and replay leaves the tensor unchanged.
- With oneCCL 2022.0.0 under the same torch it is captured correctly, as it is on torch 2.13.0+xpu and the 2.14 nightly above.
- This affects the default XPU all-reduce in decode graphs at TP > 1, and this PR's fallback above the ceiling. The one-shot path itself is captured correctly on 2.14.0.

**Known issue, outside this PR (rendezvous hang):** on emr816610 (compute runtime 26.18), torch-xpu-ops' own `torch.distributed._symmetric_memory.rendezvous` hangs about 1 start in 3, at 4 ranks as well as 8.
- One rank stays in Level Zero `appendUSMMemcpy` while the others wait in the CPU-side collective.
- A bare script with only `symm_mem.empty` and `rendezvous` reproduces it, so with `--enable-torch-symm-mem` server startup on that host can hang the same way.
- It will be reported to torch-xpu-ops.
