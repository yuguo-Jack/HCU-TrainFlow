# [bench] Fix warm-cache benchmark under-counting streaming output tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/40555) · state: open · merged: False

## Original PR description

## Motivation

`benchmark/hicache/bench_warm_cache.py` can silently under-report **output token throughput** under high concurrency / long streaming requests: some requests finish with HTTP 200 but are recorded as `success` with `output_len == 0`, so `Total generated tokens` ends up an exact multiple of `output_len` short of `completed * output_len` and `output_throughput` is deflated — even though the server actually generated the tokens (engine `gen throughput` logs confirm generation). This is a **benchmark-only** measurement bug; no serving/runtime code is involved.

Root cause in `async_request_sglang_generate`:
1. The token count is only updated inside `if "text" in data and data["text"]:`. A request whose chunks never hit that branch (chunk-boundary / cumulative-text handling under load) keeps `output_len == 0` and never reads `meta_info.completion_tokens`.
2. Any HTTP 200 is marked `output.success = True` regardless of whether tokens were received, so 0-token streams are silently counted into the denominator.

Observed on a 32K-input / 1K-output / 75%-shared-prefix run: at concurrency 10, ~1/3 of runs reported e.g. `Successful requests: 30` but `Total generated tokens: 27648` (= 27×1024) — a few "successful" requests contributed 0 tokens.

## Modifications

- Read `meta_info.completion_tokens` on **any** chunk that carries it (monotonic max), decoupled from whether `text` is non-empty; keep TTFT on the first counted token and distribute ITL over new tokens.
- If a 200 response yielded **0** counted tokens, mark it `success = False` with an explicit error so it surfaces in the `WARNING x/y requests failed` line instead of silently deflating throughput.
- Only `benchmark/hicache/bench_warm_cache.py` is changed.
