# [Fix] anthropic: Accept thinking.type=enabled without budget_tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/45364) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-style Anthropic clients (for example DeepSeek Harness) call `/v1/messages` with `thinking={"type": "enabled"}` and no `budget_tokens`; they carry the reasoning strength in `output_config.effort` instead. `AnthropicThinkingParam` rejects these requests with a 400 (`thinking.budget_tokens is required when thinking.type is 'enabled'`), so these clients cannot use a DeepSeek-V4.1 SGLang server at all.

The budget has no effect here: the local backend has no hard-cap knob, and `serving.py` only logs it as "not enforced". Requiring it only breaks clients and gives them nothing in return. We ran DeepSeek-V4.1-Flash behind such a client by patching this check locally, and this PR moves that fix upstream.

## Modifications

- `anthropic/protocol.py`: `budget_tokens` is optional on `type="enabled"`. When it is given, it must still be `>= 1024`. The `disabled` and `adaptive` rules are unchanged. The docstring now records the deviation from the SDK and the reason for it.
- `anthropic/serving.py`: the comment describing the protocol shape is updated to match.
- `test_serving.py`: `test_request_thinking_enabled_requires_budget_tokens` is replaced by `test_request_thinking_enabled_without_budget_tokens_is_accepted`. The new test asserts that the request parses, reasoning is enabled, and no unenforced-budget warning is logged. The existing `< 1024` rejection test and the "with budget, logs warning" test still pass unchanged.

Marking this explicitly: relaxing the required `budget_tokens` deviates from the Anthropic API contract — the real Messages API 400s on `thinking.type=enabled` without it, and `budget_tokens` is a required field in the SDK's `ThinkingConfigEnabled`, so official-SDK clients can't even construct the request this PR now accepts. It's an accept-superset relaxation aimed at non-SDK clients, consistent with this endpoint's accept-and-log stance (the budget is unenforced even when provided), so I think it's the right call — but if we ever move toward strict API mirroring, or later implement a real budget hard-cap, this relaxation needs to be revisited.
