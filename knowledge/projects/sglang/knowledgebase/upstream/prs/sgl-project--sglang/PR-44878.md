# [Perf] moe: apply the routed scaling factor inside the fused gate for FP8 MegaMoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/44878) · state: closed · merged: False

## Original PR description

## Motivation

In a DeepSeek-V4.1-Flash DEP2 prefill step on GB300 (MegaMoE all-to-all backend, FP8 expert method, eager prefill), every MoE layer runs one `vectorized_elementwise_kernel` of 2 µs right before `mega_moe_pre_dispatch`: `topk_weights_in * routed_scaling_factor` in `run_mega_routed_experts`. 40 launches per 16K-token step, each costing 40 to 65 µs of dispatch on the eager path for 2 µs of GPU work.

The multiply exists because `_fuses_routed_scaling_factor_in_topk` returns False for `Fp8MoEMethod` unless the runner is CUTLASS or FlashInfer TRT-LLM routed, so the top-k config gets `apply_routed_scaling_factor_on_output=False`, the fused gate leaves the weights unscaled, and the MegaMoE runner scales them afterwards.

## Modifications

- `fused_moe_triton/layer.py`: `_fuses_routed_scaling_factor_in_topk` also returns True for `Fp8MoEMethod` when the MoE all-to-all backend is MegaMoE. The model then builds its top-k with `apply_routed_scaling_factor_on_output=True`, the fused gate multiplies the selected weights by the factor in registers (`_router_triton_kernel`, `APPLY_SCALE`), and `run_mega_routed_experts` takes its existing `routed_scaling_factor=1.0` branch. The FlashInfer MegaMoE and FlyDSL MegaMoE paths read the same flag and already skip their own multiply when it is set.
- `test_mega_moe_deepgemm_api.py`: the flag is True for an FP8 method under MegaMoE and False under the plain all-to-all backend.

Numerics: the same fp32 weights, scaled inside the gate after renormalization instead of in a separate kernel after it; fused shared-expert slots are not used on this path (`num_fused_shared_experts` is 0 with MegaMoE).

## Measured

GB300, DEP2 (TP2 + DP attention, EP2), MegaMoE, Mega-mHC, decoder bounded replay, eager prefill, 16K-token prefill budget per rank, same node, on top of #44875 (job 3487) against that plus this change and #44879 together (job 3488; the two landed in the same run because the cluster worktree is a live mount).

| Rank 0, cold 16K chunk, profiled step | before | after |
|---|---:|---:|
| Kernel launches | 1,407 | 1,303 |
| `topk_weights * routed_scaling_factor` launches | 40 | 0 |
| Launches removed by the page-slot kernel of #44879 | | 64 |

| Unprofiled, median of 3 (ms) | before | after |
|---|---:|---:|
| 1 x 16K cold chunk per rank | 191 | 190 |

GPU kernel time is unchanged; the gain is dispatch on the eager path. GSM8K on GB300 (DEP2, DSpark with real acceptance, greedy, 1,314 examples): 0.9741 with all three of #44875, #44878 and #44879 applied (job 3495) and 0.9741 on the same stack without them (job 3496), the same 1,280 correct.

## Is the gain significant?

Marginal. It removes 40 launches of 2 µs each per 16K step, about 2 ms of dispatch on the eager path and nothing inside a graph; the step-time change is below what one run can resolve. It is a one-line consistency fix, the gate already had the code path, and it is worth taking for that reason rather than for speed.
