# [Fix] diffusion: float32 Plucker rays for bf16 camera poses

[Upstream PR](https://github.com/sgl-project/sglang/pull/45638) · state: closed · merged: True

## Original PR description

Part of #43875 (item 25). Split out of #44888 as requested in review so it can be validated on its own.

## Commits and the bugs they fix

### 1. Plucker rays built in float32 (`811661cc89`, item 25)
- **Bug:** rays were built in bf16 when the poses were bf16. bf16 cannot represent pixel coordinates above 256, so neighbouring pixels of a wide frame shared a ray.
- **Fix:** `get_plucker_embeddings` computes in float32 (or wider). LingBot-World builds its poses and intrinsics in float32.
- **Test:** `test_camera_geometry.py`, bf16 poses on a 640-wide frame give the same rays as float32.
- **Behavior change:** conditioning values change slightly. On CPU at 832x480 (float64 as truth), the old path differs in 74% of values (max 0.032). The new path matches float64 after the final bf16 cast.

### 2. Fused QKV made a copy and ignored LoRA and weight updates (`37e49c88a1`)
- **Bug:** `fuse_qkv_projection` stored a registered `nn.Parameter` copy of `to_q/to_k/to_v` (about +6.3 GB at TP=1 across 40 blocks). After that, `_project_qkv` always used the copy, so in-place LoRA merges and weight copies on the original layers never reached the forward. The model also did not override `refresh_weight_derived_caches`, so a weight swap left the copy stale.
- **Fix:** the layers now alias one packed buffer, so no second copy is kept and in-place updates land in the fused GEMM. `repack_qkv_projection()` re-packs after a loader replaces `.data`. The model's `refresh_weight_derived_caches` calls it for every block. The fused path is skipped while a dynamic LoRA (`BaseLayerWithLoRA.lora_active`) is active, since that delta is applied inside each layer's forward.
- **Tests:** shared storage and in-place update visible in the fused output; repack after `.data` replacement; model refresh hook repacks. On `main`, all 3 fail.
- **Not covered by a test:** the dynamic-LoRA skip branch.

### 3. Causal attention applied RoPE twice on the no-cache path (`37e49c88a1`)
- **Bug:** on CUDA, flashinfer RoPE rotates `q/k` in place. The `kv_cache is None` branch then passed those already-rotated tensors to `super().forward`, which applies RoPE again. The model forward always passes a KV cache, so this is latent today.
- **Fix:** the no-cache early return runs before RoPE, so the base attention applies RoPE once. The sequence-shard `NotImplementedError` on that branch was unreachable (sequence sharding needs a cache) and is removed.
- **Test:** monkeypatched CUDA path; the q/k the base forward receives are the originals. On `main`, it fails.

### 4. Uneven sequence splits hang or corrupt ring and kv-gather strategies (`37e49c88a1`)
- **Bug:** `kvgather_replicated`, `kvgather_sharded` and `ring` assume equal per-rank chunks (plain all-gathers, `current_start // world_size`, equal P2P buffers). Nothing checked the splits, so uneven splits could hang or corrupt the KV cache. `ulysses` already handles uneven splits and is unchanged.
- **Fix:** `_check_sequence_split_strategy` raises `NotImplementedError` for those three strategies when the splits are not uniform.
- **Test:** the helper rejects uneven splits for the three strategies and accepts uniform ones and `ulysses`. On `main` the helper does not exist, so this fails.

## Validation

- OnePunchMonk · comment · 2026-10-25T16:41:27Z · [source](https://github.com/sgl-project/sglang/pull/45638#issuecomment-6400312297)

Tested another idea:

**The idea:** `LingBotWorldTransformerBlock` (bidirectional) calls `cam_conditioner(hidden, c2ws_plucker_emb)` in every block, every forward. That runs `compute_scale_shift(c2ws_plucker_emb)`, which is the `cam_injector` MLP plus `cam_scale_layer` and `cam_shift_layer`, producing a per-block scale and shift of shape S x d. The camera input is the same for both CFG branches, so the same result gets recomputed. The idea was to compute it once per request per block and reuse it across the CFG branches. The causal path already does per-request caching of this (`_prepare_cam_conditioner_scale_shifts`). The bidirectional path does not.

**Measured on one H100, 14B shape, 480p 81 frames (S = 32760):**
- Camera scale/shift is about 8.5 ms per block. The full camera path is about 9.3 ms, against about 85 ms for a block proxy (self-attn QKV/out and FFN). So the camera path is about 10% of a block, not the 14% we first estimated. The proxy leaves out cross-attention and norms, so the real share is probably a little lower.
- The saving only comes from sharing across CFG branches. If the bidirectional pipeline runs two forwards per step, that saves about 4.5% of a CFG step. Without CFG there is no saving. We have not checked how the pipeline runs CFG.
- Keeping the scale/shift for all 40 blocks for the whole request is about 2 x S x d per block, about 27 GB at this shape. That is too much on top of a 14B model.

**Why it is not in this PR:** the saving is small and the memory cost is large. Also, the only registered LingBot pipeline configs on `main` are the two causal DMD configs, so nothing currently serves the bidirectional model.

Writeup and benchmark script (no model change) are in the fork: https://github.com/OnePunchMonk/sglang/pull/19
