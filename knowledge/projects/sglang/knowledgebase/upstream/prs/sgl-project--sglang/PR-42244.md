# [Spec] Keep the speculative lookahead within context_len at the length cap

[Upstream PR](https://github.com/sgl-project/sglang/pull/42244) · state: open · merged: False

## Original PR description

## Motivation

With EAGLE speculative decoding and the overlap scheduler, a request that runs all the way to the context limit kills the scheduler. On current releases the crash looks like this, and it happens right after the request itself returns `finish_reason: length`:

```
Scheduler hit an exception: Traceback (most recent call last):
    ...
    scheduler.event_loop_overlap()
    pop_and_process()
    self.process_batch_result(tmp_batch, tmp_result)
    self.batch_result_processor.process_batch_result_decode(batch, result)
    result.copy_done.synchronize()
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
```

We first hit this on v0.5.14 with `Qwen/Qwen3.6-35B-A3B-FP8`, EAGLE 3/1/4, FA3, `--page-size 64` and `--context-length 131072`. On v0.5.14 the same overflow tripped a host-side check in the FA3 draft-decode path (`flashattention_backend.py`, `assert_buffer_fits(..., "FA3 draft-decode page_table")`):

```
AssertionError: FA3 draft-decode page_table: used 2049 > capacity 2048
```

That check is gone since v0.5.15. #29343 moved the FA3 page-table build onto the GPU, so the same overflow now shows up as an illegal memory access somewhere later. I reproduced it on v0.5.21 and checked that `main` has the same code. The trigger is just one request reaching the cap, either without `max_tokens` or with `max_tokens` close to the limit. It needs neither grammar nor concurrency. The repro below uses a plain prompt and a single request.

### What goes wrong

Three things line up.

1. **The length budget has no room for speculation.** `init_req_max_new_tokens` clamps `max_new_tokens` to `max_req_len - input_len - 1`, so a request can reach `context_len - 2` tokens in total. When the client sends `max_tokens`, the tokenizer checks `input + max_tokens + num_reserved_tokens <= context_len`, where `num_reserved_tokens` is `compute_num_reserved_tokens()`, the draft slots EAGLE needs. When `max_new_tokens` is `None`, nothing applies that reservation. The Responses API had the same hole for its default `max_tokens`, and #18932 fixed it there by subtracting `num_reserved_tokens`.
2. **A spec step can accept past the cap.** Verify accepts up to `num_draft_tokens` tokens regardless of the remaining budget. The extra tokens are trimmed on the CPU (`finished_len`), but `seq_lens` on the GPU is not.
3. **Overlap runs the finished request one more time.** The next batch is built before the previous result is processed, so a request that finished in batch N is still in batch N+1. The code acknowledges this ("Under overlap a finished row reappears for one overshoot tick"). That tick does a full draft, verify and draft-extend.

Let `B = input + max_new_tokens` be the cap and `D = num_draft_tokens`. The last step that still sees the request as unfinished starts at `seq_lens <= B - 2`, because the request has at most `B - 1` tokens and `seq_lens` does not count the bonus token, whose KV is not written yet. That step accepts up to `D`, and then the overshoot tick verifies `D` more. So the tick reads KV up to:

```
B + 2D - 2
```

With EAGLE 3/1/4 and `B = context_len - 2`, that is `context_len + 4`. At 128K context with page size 64 it needs 2049 pages, and FA3's page table has 2048.

### Why this turns into an illegal memory access

The FA3 page table is sized `ceil(context_len / page_size)` per row. The builders (`normal_decode_set_metadata`, `build_trtllm_mha_page_table`) only write the pages that fit in that width. `cache_seqlens` is passed to `flash_attn_with_kvcache` unclamped, though, so the kernel reads one page id past the end of the row:

- In the CUDA-graph buffers, that slot is column 0 of the next row: another request's page, or a stale one.
- In the eager `DRAFT_EXTEND_V2` path, `seq_lens_cpu` is `None` under spec v2, so the page table is a fresh `[bs, max_context_len / page_size]` tensor. For the last row the extra slot is past the end of the tensor. If it holds garbage, the page id points outside the KV pool and the kernel faults.

The outputs the client sees are still correct. Causal masking keeps the queries that matter from attending to the extra page. The problem is the out-of-bounds read itself.

FA3 is not the only thing affected. Those positions also go to RoPE, and `cos_sin_cache` has `max_position_embeddings` rows. For most models that number equals `context_len`.

## Modifications

The fix is in the scheduler: keep the speculative lookahead inside `context_len` when clamping `max_new_tokens`.

- `managers/utils.py`: new `compute_spec_context_reserve(enable_overlap)`. It returns `compute_num_reserved_tokens()` with overlap off, and twice that with overlap on: one window for the accept overshoot and one for the overshoot tick. It returns 0 when spec is off or the algorithm is not EAGLE-family, same as `compute_num_reserved_tokens()`.
- `managers/scheduler.py`: compute it once in `init_model_worker`, right after `max_req_len` arrives, and subtract it in `init_req_max_new_tokens`. That single clamp covers both the `None` path and the explicit-`max_tokens` path. There is also a class-level default of 0, the same pattern as `kv_shard_widening`, so tests that build the scheduler with `__new__` keep working.
- `test_scheduler_init_req_max_new_tokens.py`: the existing rule check now includes the reserve. A new regression case runs EAGLE 3/1/4 and 5/1/6, each with `max_new_tokens=None`, a huge value, and the largest value the tokenizer accepts, and asserts that the overshoot tick's KV length stays within `context_len`. Plus a check that the reserve is 0 without spec.

```diff
+def compute_spec_context_reserve(enable_overlap: bool) -> int:
+    """Context slots kept free past a request's length cap for spec lookahead.
+    ...
+    """
+    return compute_num_reserved_tokens() * (2 if enable_overlap else 1)

         ) = self.tp_worker.get_worker_info()
+        self.spec_context_reserve = compute_spec_context_reserve(self.enable_overlap)
 ...
-                self.max_req_len - input_len - 1,
+                self.max_req_len - input_len - 1 - self.spec_context_reserve,
```

After the fix, `B <= context_len - 2 - 2R` with `R >= D`, so the overshoot tick reads at most `context_len - 4`.

**What users see.** A request that runs into the context limit gets up to `2R` fewer tokens, 8 with EAGLE 3/1/4, and still ends with `finish_reason: length`. Tokenizer validation does not change, so no request that used to be accepted gets rejected now. With spec off, `R = 0` and nothing changes.

### Why `2R` and not `num_draft_tokens`

The minimum extra headroom is `2D - 4`. That comes from `B + 2D - 2 <= context_len` with `B = context_len - 2 - reserve`. It equals `D` only when `D = 4`. So reserving `num_draft_tokens` once is exactly tight for EAGLE 3/1/4 and too small for anything with more draft tokens. I measured both on v0.5.21. To make sure the last accept landed at every possible offset from the cap, I swept the prompt length one token at a time:

| config | extra reserve | cap B | bound `B + 2D - 2` | max KV measured | result |
|---|---|---|---|---|---|
| EAGLE 3/1/4 | 0 (today) | 4094 | 4100 | 4098 | illegal memory access |
| EAGLE 3/1/4 | 4 (`D` once) | 4090 | 4096 | 4096 | survives, exactly at capacity |
| EAGLE 3/1/4 | 8 (this PR) | 4086 | 4092 | 4091 | survives |
| EAGLE 5/1/6 | 6 (`D` once) | 4088 | 4098 | 4098 | over capacity, illegal memory access on the 2nd run |
| EAGLE 5/1/6 | 12 (this PR) | 4082 | 4092 | 4092 | survives, 12/12 |

Every measured maximum matches the bound. I went with `2R` over the exact `2D - 4` on purpose. The exact form depends on four separate off-by-ones in different places: `max_req_len = context_len - 1`, the clamp's own `- 1`, a request counting as unfinished below its cap, and `seq_lens` excluding the bonus token. The last one isn't written down anywhere. If any of them changes, the exact form silently lets the crash back in. `2R` uses the reservation the tokenizer already applies, costs at most 4 slots more than the minimum for a chain, and keeps that margin.

### Why not widen the attention metadata instead

#29665 (FA3) and #29696 (all backends) proposed sizing page tables from `req_to_token.shape[1]` instead of `context_len`. Both were closed without review. DSA got the same treatment in #30274. That removes the page-table fault, but the positions still go past `context_len`. I tested an FA3-only widening on v0.5.21 with `max_position_embeddings` overridden to 4096, so the RoPE cache has 4096 rows. The server no longer crashes, but the overshoot tick's TARGET_VERIFY and DRAFT_EXTEND_V2 run at position 4096, one row past the RoPE table. That is the same kind of failure as the DSpark RoPE crash in #33454 / #33963. Keeping the budget inside `context_len` fixes it once, for every attention backend and for RoPE, without touching any of them.

### Scope

- The change is backend- and vendor-agnostic. ROCm keeps the overlap scheduler on, so AMD gets `2R` too. On AMD the aiter backend keeps a flat `kv_indices` buffer with `num_draft_tokens` of slack per row, so the page-table side probably doesn't fault there; the RoPE side is the same as on NVIDIA. I could only test on H100.
- Out of scope: DFLASH, DSPARK and NGRAM, where `compute_num_reserved_tokens()` is 0. Their boundary issues are tracked in #33579 and #33963.
- Not verified: pipeline parallelism. If PP can keep more than one batch in flight past a finished request, the overshoot could be more than one tick.

## Accuracy Tests

This doesn't change model outputs below the cap. It only moves where requests stop. The end-to-end checks below are about crashes and KV lengths.

**Setup:** 1x H100 80GB, v0.5.21 with this diff applied (it applies cleanly; only line offsets differ), `Qwen/Qwen3.6-35B-A3B-FP8`:

```
python -m sglang.launch_server --model-path Qwen/Qwen3.6-35B-A3B-FP8 \
  --context-length 4096 --page-size 64 --attention-backend fa3 \
  --speculative-algorithm EAGLE --speculative-num-steps 3 \
  --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 \
  --mamba-radix-cache-strategy extra_buffer --mem-fraction-static 0.8
```

The context is small so a request hits the cap in about 10 seconds instead of minutes. Each request is a counting prompt that the model continues until the cap. The KV lengths come from a wrapper around the FA3 metadata init that logs `cache_seqlens` near the limit. It was loaded through `sitecustomize`, so sglang itself is untouched.

| case | v0.5.21 | with this PR |
|---|---|---|
| no `max_new_tokens` | total 4094, overshoot verify KV 4098 (65 of 64 pages), illegal memory access (2/2 runs) | total 4086, alive |
| `max_new_tokens = 4096 - 4 - input` (largest the tokenizer accepts) | cap 4092, GPU seq 4094, KV 4098, illegal memory access | total 4086, alive |
| `json_schema`, no `max_new_tokens` | total 4094, KV 4097, illegal memory access | total 4086, alive |
| 4 concurrent requests, no `max_new_tokens` | not run (one request is enough) | all 4086, alive |

Across the 8 requests with the fix, the longest KV that FA3 was asked to read was 4091.

The instrumentation log from the failing case:

```
OVERFLOW mode=TARGET_VERIFY   seq_lens=[4094] max_cache_seqlens=4098 pages_needed=65 max_num_pages=64
OVERFLOW mode=DRAFT_EXTEND_V2 seq_lens=[4098] max_cache_seqlens=4098 pages_needed=65 max_num_pages=64
```

**FA3 reads past the row.** A standalone call to `flash_attn_with_kvcache` with page size 64, a 2-column page table viewed out of a 2-row buffer, and `cache_seqlens = 2 * 64 + 2`:

| value in the slot right after row 0 | last query output (sum) | first query output (sum) |
|---|---|---|
| 3 | 10.610926 | 4.543498 |
| 4 | 13.119022 | 4.543498 |
| 3 (again) | 10.610926 | 4.543498 |
| 50,000,000 | `cudaErrorIllegalAddress` | |

The last query depends on memory outside its row. The first query doesn't, because of the causal mask. A garbage page id there faults.
