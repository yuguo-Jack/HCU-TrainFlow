# [Perf] pd: Poll finished KV transfers while the prefill loop waits for a forward result

[Upstream PR](https://github.com/sgl-project/sglang/pull/47015) · state: closed · merged: True

## Original PR description

## Motivation

In the PD prefill overlap loop, a request whose KV transfer completes during a long forward step is noticed only after that step ends. While a forward result is pending, the loop blocks in the oldest result copy's `synchronize()` and calls `process_disagg_prefill_inflight_queue()` once per pass, so a transfer that finishes early in a step is retired only when the step is over:

```text
                 step N                       step N+1
GPU:   |========================|==================================|
                                ^ request's prefill done
                                post KV send, poll: Transferring
                                |-- transfer --|                    ^ poll: Success
                                               (done, unobserved)     KV released, output streamed
                                |<------ handoff = length of step N+1 ------>|
```

A short request that finishes behind a long prompt therefore waits for the whole following step before its KV cache is released and its output is streamed, even though the transfer itself took a small fraction of that time. On the decode side the first token is already out; this delay reaches the client only where the client waits for the prefill response (for example when it asks for prefill-side logprobs), but it always delays the prefill engine's KV release and metadata-slot reuse.

## Modifications

Add `SGLANG_DISAGG_PREFILL_POLL_TRANSFERS_WHILE_WAITING` (default off). When it is on and a transfer is in flight, the loop waits for the oldest result through the existing non-blocking readiness poll (the one continuous input polling uses) and calls `process_disagg_prefill_inflight_queue()` on every waiting pass, so finished transfers retire as soon as they complete:

```text
                 step N                       step N+1
GPU:   |========================|==================================|
                                ^ post KV send
                                poll  poll  poll: Success -> KV released, output streamed
                                |<- transfer ->|
```

- **Intake during the wait.** New requests and batches are taken while waiting only with `SGLANG_ENABLE_DISAGG_PREFILL_CONTINUOUS_INPUT_POLLING`. With only this flag, the loop takes no input until the result is ready, exactly as the blocking wait did; pause and shutdown requests land on the next pass.
- **Shared support check.** Both flags use one `_supports_result_wait_polling()` check: attention DP=CP=1, non-speculative, autoregressive generation, no dLLM. Under it the oldest result's copy is always submitted and the inflight queue is identical on all TP ranks; readiness is MIN-reduced, so every rank issues the same collectives in the same order and leaves the wait on the same pass. With attention DP or CP > 1, shards keep different inflight queues, so one shard could leave the wait while another enters the TP-wide readiness all-reduce; there the flag logs a warning once and the blocking wait stays.
- **Barrier order.** When the WAR barrier is deferred, finished transfers retire before the pending barrier is applied, matching the ordering of the regular result path.
- **Default path.** With the flag off, the loop is unchanged: the only new work is the flag read at loop entry.

Retiring a transfer while a forward runs (releasing its KV cache and metadata slot, streaming its output) already happens at the end of every step today; this change only moves the poll earlier.

## Accuracy Tests

Not applicable: no change to model forward or sampling. The flag is off by default.

Unit tests in `test/registered/unit/disaggregation/test_prefill_result_polling.py` cover the new behaviour on CPU:

- transfers are polled during a result wait only when the flag is on, with and without continuous input polling;
- a blocking wait becomes a polling wait only when a transfer is in flight, and the result is processed exactly once;
- pause and shutdown ordering is preserved in both loops;
- the flag needs a supported loop (attention DP, CP, speculative, embedding and dLLM configurations warn and keep the blocking wait);
- under TP=2 (gloo), ranks whose copies finish on different passes still leave the wait on the same pass, with a collective asserted on every poll;
- a transfer that finishes while a result is pending is retired exactly once, its metadata slot is reused by the next admission, and a failed admission still retries only after the result;
- the deferred WAR barrier is applied after the transfer poll.

## Speed Tests and Profiling

With the flag on, the time from a request's KV transfer completing to its KV release and output stream drops from "the rest of the current forward step" to roughly one polling pass, which matters for short requests that finish behind a long prompt. No end-to-end numbers are included in this PR; the flag is opt-in and the default path is unchanged.
