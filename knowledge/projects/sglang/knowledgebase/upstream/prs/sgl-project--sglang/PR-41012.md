# [Bugfix] Olmo3: size sliding-window layers from the hybrid SWA pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/41012) · state: closed · merged: False

## Original PR description

## Motivation

Olmo3 checkpoints are served as `Olmo2ForCausalLM` (`Olmo3Config` rewrites the architecture), and `_olmo2_overrides` sets `disable_hybrid_swa_memory=True` unconditionally, with a FIXME pointing at #7367. Olmo3 interleaves sliding-window and full-attention layers 3:1 (24 of the 7B's 32 layers are `sliding_attention`, window 4096), so every sliding layer is allocated a full-context KV pool. The window is still applied in attention, so this costs capacity, not correctness.

Removing the unconditional disable on its own would not help: `Olmo2ForCausalLM` is not on the hybrid-SWA allowlist in `is_hybrid_swa_model`, so the model would silently stay on a single full-size pool.

## Modifications

- **`configs/olmo3.py`**: `Olmo3Config` derives `hybrid_layer_pattern` (1 = sliding, 0 = full) from `layer_types` and sets `is_hybrid_swa` only when there is a real window and a genuine mix of layer kinds. These are the generic opt-in hooks `is_hybrid_swa_model` and `get_hybrid_layer_ids` already read, so the allowlist is unchanged and genuine Olmo2 checkpoints (loaded through `Olmo2Config`, no sliding layers) are untouched.
- **`arg_groups/model_overrides/olmo2.py`**: keeps the hybrid pool disabled when that marker is absent (genuine Olmo2) or when the hierarchical cache is on. The hierarchical cache supports FULL+SWA trees (#23391), but this change was not validated with it, so that combination keeps today's single pool.
- **Tests**
  - `test_model_config.py`: an Olmo3 config opts in and `get_hybrid_layer_ids` returns its split through the generic pattern fallback; configs without a window, all-full, or all-sliding do not opt in; genuine Olmo2 is not hybrid.
  - `test_model_overrides.py`: golden resolution of an `olmo3` config keeps the hybrid pool; the hierarchical cache still disables it; the marker is also read from `text_config`.

## Accuracy Tests

`allenai/Olmo-3-7B-Instruct`, 8x MI325X, TP 8, bf16 KV cache, default attention backend (the Olmo2 override picks triton on ROCm), `--mem-fraction-static 0.90 --context-length 11264`. GSM8K via lm-eval (`local-chat-completions` with the chat template, 5-shot, all 1319 questions, greedy), strict match:

| radix cache | before | after |
|---|---|---|
| on | 0.905 ± 0.008 | 0.911 ± 0.008 |
| off | 0.908 ± 0.008 | 0.911 ± 0.008 |

## Speed Tests and Profiling

Same setup. `bench_serving --dataset-name random-ids`, 384 prompts of 8192 input / 1024 output tokens, max concurrency 128, after a warmup round.

| | before | after |
|---|---|---|
| KV pool per rank (tokens) | 3,653,481 (single pool) | full 4,298,213 + SWA 3,438,570 |
| output tok/s, radix cache on | 3249.2 | 3229.4 (-0.6%) |
| output tok/s, radix cache off | 3160.6 | 3129.9 (-1.0%) |
| median TPOT (ms), radix on / off | 32.4 / 32.6 | 32.7 / 32.8 |

With the default `--swa-full-tokens-ratio 0.8` the full-attention pool holds 17.6% more tokens. At this operating point (TP 8, 256 GB per GPU) the workload is not KV-bound, so throughput is flat within run-to-run noise; the gain is capacity for longer or more concurrent requests.

Long context on one GPU, where the pool is the limit: TP 1 on a separate MI325X host whose GPUs are shared with a resident service (arms back to back), `--mem-fraction-static 0.80 --context-length 40960`, 48 prompts of 32768 input / 1024 output tokens at concurrency 48, three runs per arm:

| | KV pool (tokens) | output tok/s | peak running |
|---|---|---|---|
| before | 172,745 (single pool) | 132.3 / 129.3 / 129.3 | 4-5 |
| after, default ratio 0.8 | full 203,230 + SWA 162,584 | 108.6 / 108.7 / 108.6 | 5 |
| after, `--swa-full-tokens-ratio 0.2` | full 431,863 + SWA 86,372 | 155.4 / 155.4 / 155.3 (+17% to +20%) | 12 |

The default-ratio drop is not the pool. At equal concurrency the decode step takes the same time with and without this change (3 running: 23.5 vs 23.7 ms; 5 running: 36.9 vs 37.5 ms). What changes is the CUDA-graph bucket: decode graphs are captured at bs 1, 2, 4, 8, 12, ..., so 3 or 4 requests run the bs-4 graph at about 23.5 ms per step and 5 requests are padded into the bs-8 graph at about 37 ms. The larger pool moves this workload from 4 to 5 concurrent requests, across that step. On the unpatched tree at a fixed concurrency of 5, a token takes 36.8 ms with the default graphs and 27.1 ms with `--cuda-graph-bs-decode 1 2 3 4 5 6 7 8 12 16 24 32` (4 requests: 24.0 ms). For long prompts it is a lower ratio that turns the capacity into throughput. The padding cost itself is filed as #41151 and addressed in #41229.

These runs used upstream `a1b4ec02ae` with this diff applied (plus two local fp8-kernel patches that are not on this bf16 path); the diff applies unchanged to current `main`, where the unit tests below were rerun.
