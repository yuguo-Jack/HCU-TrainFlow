# fix(dspark): isolate draft MoE from target expert recorder

[Upstream PR](https://github.com/sgl-project/sglang/pull/37947) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #34974. With EPLB enabled, DSpark's draft MoE calls the target model's shared expert recorder without a target layer context. The stat gatherer indexes with `layer_idx=None`, and `scatter_add_` fails during draft CUDA graph capture.

DSpark stages have independent NextN weights and zero-based stage IDs. Assigning those IDs to the target recorder would mix draft traffic into unrelated target layers.

## Modifications

- Wrap only the draft MoE call in `DSparkV4Stage._run_ffn` with the existing recorder's `disable_this_region()` context, matching other MTP paths.
- Add registered CPU tests for target-count/output preservation, eager/capture-active hook paths, exception restoration, and nested disabled regions.

The target recorder, expert mapping and MoE arithmetic are otherwise unchanged. The separate draft expert-dispatch mapping work in #34846 is not included.

## Accuracy Tests

On upstream base `06b874980`, the regression invokes the real DSpark FFN method, recorder hook and stat gatherer, substituting only expensive MoE computation. Before the patch, eager and capture-active cases both produce the reported `scatter_add_` dimension error. After the patch:

```bash
python test/registered/unit/spec/test_dspark_expert_distribution.py -v
# 3 tests passed

python test/registered/unit/spec/test_dspark_target_hidden_projection.py -v
# 2 tests passed
```

A manual A100 CUDA graph capture/replay check at the same recorder seam also passed: target counts remained exactly `[[0,0,0,0],[2,0,4,0]]`, the draft output was preserved, and recorder state was restored. It used substituted MoE arithmetic, not the full model. Environment: NVIDIA A100 80GB PCIe, PyTorch `2.13.0+cu130`.

Full 8xH20 DeepSeek-V4-Flash server startup, end-to-end accuracy, speculative acceptance and live expert migration were not tested. Those need matching full-model CI; the seam tests do not establish complete EPLB/DSPARK compatibility.

## October 4 update and community validation

Synced current `main` and initialized `_expert_location_metadata` in the test gatherer fixture, following [@Frank-whw's October 2 report](https://github.com/sgl-project/sglang/pull/37947#issuecomment-5950938296). The three registered CPU recorder regressions pass on the updated branch (Python 3.12, PyTorch 2.11.0); GPU visibility was disabled for this CPU run.

The same report provides independent full-model startup evidence for **DeepSeek-V4.1-Flash on 8 H200s**, TP8/EP4/DP1, CUTLASS W4A16 and DSpark block 5. Before the guard, all eight ranks failed during capture with `layer_idx=None`. With the production guard applied, startup and three rounds of eight cold 8192-token requests succeeded. The reported recorder counts were 8192 × top-k 6 for layers 0–20 and 128 × 6 for layers 21–39, identical across all ranks with identity placement. This is community validation, not an author-run serving benchmark; speculative acceptance and live expert migration are still unverified.

No speedup is claimed and no serving benchmark or profile was run. This is a recorder-ownership fix for a startup/capture failure.

Results:

- **With the change**: full 8-rank startup completes, and 3 rounds of 8 cold 8192-token requests (1 output token each) produced valid per-pass counts:

  - layers 21–39: exactly `128 x topk(6)` each,
  - per-layer histograms identical across all 8 TP ranks, physical→logical map identity.
- So the isolation does not merely stop the crash here; it restores output that EPLB statistics depend on.

One thing that will affect CI: **the registered test as written no longer runs against current `main`.** `_SelectExpertsSinglePassGatherer.on_select_experts` now bounds ids with `self._expert_location_metadata.num_physical_experts` (`srt/eplb/expert_distribution.py:622`), but the test constructs the gatherer via `__new__` and sets only `_data`, so it errors with:

```
AttributeError: '_SelectExpertsSinglePassGatherer' object has no attribute '_expert_location_metadata'
```

Adding one fixture line makes all 3 tests pass against current `main`:

```python
self.gatherer._expert_location_metadata = SimpleNamespace(num_physical_experts=4)
```

I did not otherwise modify the test. Happy to push that as a small fixup if useful.
