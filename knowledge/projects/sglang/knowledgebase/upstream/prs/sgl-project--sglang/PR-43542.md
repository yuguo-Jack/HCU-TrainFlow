# [Fix] speculative: Resolve the SWA KV pool for the FA backend under FROZEN_KV_MTP

[Upstream PR](https://github.com/sgl-project/sglang/pull/43542) · state: open · merged: False

## Original PR description

## Motivation

Gemma-4 with the FA backend (`--attention-backend fa4`) and the `google/gemma-4-31B-it-assistant` draft (promoted to `FROZEN_KV_MTP`) crashes on the first request with `CUDA error: an illegal memory access was encountered`.

**This is a latent bug in `FlashAttentionBackend`, not a regression from #42019.** The FA backend never resolved the SWA KV pool for a frozen-KV draft. It stayed hidden because Gemma-4 could not select the FA backend on Hopper: the SM90 FA4 kernel did not support the head dimension 512 of Gemma-4's global-attention layers, so Gemma-4 ran on Triton. #42019 ("Enable Gemma4 FA4 on SM90 with head-dim 512 support") makes `--attention-backend fa4` selectable for Gemma-4 (opt-in; Triton stays the default). That opens the FA backend to the Gemma-4 SWA + frozen-KV MTP draft combination for the first time, and exposes the bug. Without this fix, `--attention-backend fa4` + MTP on Gemma-4 crashes on `main`.

Root cause: the FROZEN_KV_MTP draft has no KV of its own and reads the target's KV, but its `ModelRunner.token_to_kv_pool` is a plain (non-SWA) pool. `FlashAttentionBackend.__init__` derived `use_sliding_window_kv_pool` from that pool, so it was `False` for the draft. Full-pool page-table slots were then never translated to SWA slots, and the smaller SWA buffer was indexed out of bounds.

`flashinfer`, `trtllm_mha` and `aiter` already resolve the SWA pool from the allocator for frozen-KV drafts (`_resolve_swa_kv_pool`). The FA backend was the odd one out.

## Modifications

`python/sglang/srt/layers/attention/flashattention_backend.py`
- Add `FlashAttentionBackend._resolve_swa_kv_pool`, mirroring the flashinfer/trtllm_mha resolver: use the active pool if it is a `SWAKVPool`; for a draft worker, only FROZEN_KV_MTP falls back to the allocator's SWA pool (other EAGLE drafts keep their own separate pool and still get `None`).
- Store the result in `self._swa_kv_pool`, derive `use_sliding_window_kv_pool` from it, and use it at every place that calls `translate_loc_from_full_to_swa` / reads `full_to_swa_index_mapping` (previously `self.token_to_kv_pool`).
- For every non-frozen-KV case the resolved pool is the same object as before, so behavior is unchanged.

`test/registered/unit/spec/test_resolve_swa_kv_pool.py`
- Register the FA backend resolver in the existing `_RESOLVERS` table.

## Accuracy Tests

The change only selects which pool the page table is translated against; it does not touch kernels or model code, so accuracy with MTP should equal accuracy without it.

Setup: lm-eval GSM8K, 5-shot, chat template, greedy, `max_tokens=4096`, 32 concurrent requests, full test set. 1x H200, `RedHatAI/gemma-4-31B-it-FP8-block`, `--attention-backend fa4`, server flags as under Speed Tests.

**On `main` + this PR**

| Config | flexible-extract | strict-match | accept length | accept rate | `illegal memory access` in server log |
|---|---|---|---|---|---|
| no speculative decoding | 0.9712 ± 0.0046 | 0.9719 ± 0.0045 | - | - | 0 |
| MTP4 (FROZEN_KV_MTP) | 0.9712 ± 0.0046 | 0.9719 ± 0.0045 | 4.26 | 0.814 | 0 |
