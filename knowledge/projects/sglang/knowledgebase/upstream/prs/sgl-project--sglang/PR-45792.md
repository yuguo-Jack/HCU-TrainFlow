# [Feat] [NPU] multimodal: Add independent V1 JPEGD + VPC image decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/45792) · state: open · merged: False

## Original PR description

## Motivation

Add Ascend JPEGD decoding and VPC RGB conversion while keeping GPU and NPU image-decoding policies independent. This implements the JPEG decoding item in the [Ascend multimodal roadmap](https://github.com/sgl-project/sglang/issues/43519).

## Changes

- Keep `gpu_image_decode`, including its existing defaults, model overrides and CUDA `nvjpeg_fancy` behavior. Add a separate keyword-only `npu_image_decode` policy, defaulting to false in the shared loader and base processor. Verified Qwen2.5-VL, Gemma3 and GLM4v processor/configuration combinations opt in.
- Select the NPU route using the processor's actual serving device and independent NPU policy. Bind ordinary loading and snapshot loading to the configured NPU, and include the effective policy in preprocessing cache fingerprints.
- Add `SGLANG_DISABLE_NPU_IMAGE_DECODE=1` as a service startup override. Its default is false; it can disable an eligible processor's NPU decoding but cannot enable an ineligible processor, device or input. It takes effect when processors are constructed. Low-level explicit loader calls retain their caller-supplied policy.
- Use **V1 JPEGD + VPC** for eligible baseline 8-bit YCbCr 4:2:0 JPEGs: 32–4096 pixels per dimension, at most 32 MiB. Convert NV12 to full-range BT.601 RGB and return synchronized, Torch-owned, contiguous NPU `uint8 [3, H, W]` tensors. Odd dimensions use a private SOF copy and output cropping.
- Unsupported inputs, including PNG/progressive JPEG and EXIF/ICC-bearing inputs, use PIL. Ascend 950 and unknown devices take the PIL path before unsupported V1 resources are constructed. This PR adds neither V2 nor PNG hardware decoding.
- Preserve visible device execution failures. Keep GLM patch extraction on CPU and stage device tensors for PIL preprocessing. Reuse per-thread/per-device decoders, preserve caller context, and retain potentially in-flight resources when synchronization fails rather than freeing them prematurely.

## Validation on the submitted source

Hardware: **Ascend910_9362**, CANN 9.1, HDK 25.5.1. The submitted tree is the frozen R5 tree; publishing does not change or rebase the tested source.

- Seven processor/configuration chains, each with 16 single-image inputs plus a JPEG/PNG pair, in separately started enabled/disabled processes: **119 complete-output comparisons passed**. Eligible enabled JPEGs asserted actual JPEGD/VPC calls; disabled runs asserted zero calls. Chains cover Qwen 3B, Gemma 4B, GLM torchvision, GLM explicit PIL, GLM auto parameters with an actual PIL backend, Qwen 72B processor, and quantized GLM processor.
- Qwen 3B/72B processor `max_pixels` configurations passed their additional 18 groups each. Real cache miss/hit, effective-policy fingerprint separation, features, tokens, MRoPE and offsets were checked.
- Eight independent SGLang smoke-test processes covered both startup settings for Qwen 3B, Gemma 4B, GLM torchvision and GLM PIL. Each completed naturally, matched its counterpart's answer and exhibited the expected observed decode route. These are smoke tests, not dataset accuracy measurements.
- **110 CPU tests passed**, plus six simulated CPU/CUDA routing-policy combinations with both startup settings. Applicable pre-commit hooks and `git diff --check` passed. The final 20 changed files were checked against the tested source hashes.

## Earlier R4 accuracy and component measurements

These results belong to the recorded R4 patch `265fcad946489f8e72e0b232e5e144106a75c1431759e186952545375786ad91`, not an R5 rerun. R5 adds the startup override, documentation and tests without changing R4's default decode/processing implementation.

Qwen2.5-VL-3B-Instruct/BF16, original MMBench DEV EN v1.1: 1,292 base question groups, fixed option order, concurrency 1, `temperature=0`, `seed=42`, up to 64 naturally generated tokens; both arms infer on NPU. This is not CircularEval.

| Image decoding | Correct / 1292 | Accuracy |
| --- | ---: | ---: |
| CPU/PIL | 1077 | 83.36% |
| V1 JPEGD + VPC | 1077 | 83.36% |

All 1,292 options and full answer texts matched, with no failed, invalid or truncated responses. R4 also checked 1,250 original images: 1,229 NPU decodes and 21 PIL fallbacks, all RGB outputs byte-identical to PIL; device/thread lifecycle tests included same-process cross-device loading.

R4 component benchmark: 24 original JPEGs plus three synthetic JPEGs; three warmups, then three rounds of five observations per cell with backend order rotated. Both paths start with in-memory JPEG bytes and end at a synchronized, owned, contiguous NPU CHW RGB tensor. Allocation, transfers and layout are included; disk, first-use initialization, model preprocessing and inference are excluded.

| Synthetic dimensions | CPU/PIL + upload median ms | V1 median ms |
| --- | ---: | ---: |
| 128×64 | 0.31 | 0.73 |
| 640×480 | 2.55 | 1.39 |
| 1920×1080 | 18.08 | 5.28 |

These are measurements from a four-CPU container on a shared host. NPU medians were lower on 24 of 27 inputs and higher on three small inputs. They do **not** establish an end-to-end serving speedup.

## Remaining validation limits

- No physical GPU or Ascend 950 validation in this run. GPU simulations do not establish GPU end-to-end behavior; 950 uses PIL and has no hardware-decode claim.
- Only Ascend910_9362 was hardware-tested. Other qualified A2/A3 names and some general descriptor API product-specific details still need stronger evidence.
- Qwen 72B and quantized GLM rows load processors/configurations only, not their model weights.
- The tested baseline is `af5731cca609df9a11ada39382d65751e8ab7905`. A later main was checked for textual merge conflicts; merged-main service behavior and final-commit project CI remain separate validation work.
