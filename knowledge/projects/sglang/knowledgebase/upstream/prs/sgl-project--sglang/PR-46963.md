# [Feat] rust-server: Report the scheduler's per-request stats in native /generate meta_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/46963) · state: closed · merged: True

## Original PR description

Stacked on #46961 (cached tokens by cache tier in the Rust frontend), which sits on #46949 (customized_info through the Rust frontend); this PR's own change is its last commit, and its diff against #46961 is the 10 files below.

## Motivation

In Rust frontend mode, native `/generate` responses were missing the per-request stats that Python's TokenizerManager reports in `meta_info`:

- `num_retractions`;
- with `--enable-metrics`: the scheduler timings `queue_time`, `forward_entry_time`, `prefill_finished_time`, `storage_prefetch_wait` and `storage_staging_wait`, plus `decode_throughput`;
- with speculative decoding: `spec_accept_rate`, `spec_accept_length`, `spec_num_correct_drafts`, `spec_num_proposed_drafts`, `spec_verify_ct`, `spec_cap_length`, `spec_block_accept_length`, `spec_correct_drafts_histogram` and `spec_cap_lens_histogram`.

A client that reads these keys from a Python-mode server got nothing from a Rust-mode one. After this change the Rust frontend reports the same keys, under the same conditions, with the same values.

## Modifications

- **Scheduler** (`scheduler_components/output_streamer.py`): for each finished request, `get_request_stats` builds a `request_stats` map keyed by the `meta_info` names, using the helpers TokenizerManager uses: `SchedulerReqTimeStats.convert_to_output_meta_info` and the speculative-decoding computation. That computation moves out of `TokenizerManager._calculate_spec_decoding_metrics` into `speculative/spec_decoding_metrics.py` (`populate_spec_info`) with no behavior change, and TokenizerManager now calls it. The map travels as a new optional trailing `request_stats` column of the Rust egress batch header (`rust_server/server.py`); it is built only in Rust frontend mode and only for finished rows.
- **Rust frontend** (`message/response.rs`, `core/frame.rs`): the column decodes into `ChunkExtras.request_stats` (a `RequestStats` JSON map); a finished request's stats ride its terminal output. Native `/generate` (`http/native_api.rs`) writes the entries into the terminal frame's `meta_info` after the schema's keys and before the `customized_info` and hook keys, with no per-key Rust code, so a new Python stat needs no Rust change. A `customized_info` key that repeats a stats key gives way, as it already does for schema and hook keys, so `meta_info` never has a key twice.
- **`decode_throughput`** comes from frontend timing, so the frontend computes it as Python's `get_decode_throughput` does (one over the time per output token after the first), when metrics are on, and appends it after the scheduler's stats.
- **Timing fix:** a request whose first output is also its terminal output (for example a non-streaming request on a PD decode server) now has zero decode latency, as in Python, which reuses that output's arrival time as the finish time. Before, the frontend measured the gap between two clock reads, so `decode_throughput` could come out in the hundreds of millions of tokens per second where Python omits it.
- **Frequency:** Python repeats `num_retractions` and the scheduler timings on every streamed frame and reports the speculative stats and `decode_throughput` only on the final one. The Rust frontend reports all of them on the terminal frame only, which keeps the scheduler from building a dict per row on every decode step.
- **Compatibility:** the column travels only inside one server process, between the scheduler and its embedded frontend. A frame without the column renders exactly as before. A request the scheduler aborts outside the output stream carries no stats, as in Python's `_handle_abort_req`. api.v1 gRPC frames are unchanged: their `meta_info` is typed, so these keys reach native HTTP `/generate` only.

## Beyond the original change

Two lines are adapted to #47166 (typed scheduler timing reports), which landed on main after this change was written and removed the API it called:

- `get_request_stats` (`output_streamer.py`), under the same metrics flag as before, reads the scheduler timings through `req.time_stats.to_output_time_stats()` and, when that is not `None`, adds `.to_meta_info()`; before #47166 it called `req.time_stats.convert_to_output_meta_info()`. Same keys, same gating.
- `build_rust_frame_metadata_fixture` (`test_rust_server_extension.py`) reads the Python-mode batch output's `time_stats[0].to_meta_info()` and no longer unpickles the column, since #47166 sends typed reports instead of a pickle.

Eight more lines are adapted to #47178 (per-request output stats sent only when changed), which landed after that:

- The accumulator field that carries the Rust frontend's per-row stats is `rust_request_stats` (three lines: its declaration, the write in `accept`, and the `push_generation` argument), because #47178 added a `request_stats` field of its own to `_GenerationStreamAccumulator` for the Python-mode `RequestOutputStats` rows. The egress header column keeps its name.
- The scheduler-side test class is `TestOutputStreamerRustRequestStats`, because #47178 added a `TestOutputStreamerRequestStats` to the same file.
- `build_rust_frame_metadata_fixture`'s request fake gains `request_stats_retraction_count` and `take_request_stats_due` (the `Req` method, imported), which #47178's Python-mode accumulator now reads, and the Python-mode comparison reads the retraction count and time stats from `request_stats[0]` instead of the removed `retraction_counts` and `time_stats` columns.

Nothing else differs from the change as originally tested.

## Accuracy Tests

Not applicable: no model numerics change. The speculative-decoding computation is moved, not changed; the new unit tests pin its outputs against the Python path on the same batch output.

## Speed Tests and Profiling

Not run. The scheduler builds one small dict per finished request (not per decode step), and the frontend copies its entries into the terminal frame's `meta_info`.

## Testing

- `testdata/frame_metadata.json` gains a `request_stats` case, regenerated with `build_rust_frame_metadata_fixture`: `frame_metadata_matches_python` decodes it and checks the Rust-decoded stats, keys in order, against the `meta_info` that `TokenizerManager._handle_batch_output`'s code builds from the same requests' Python-mode batch output (cap-accept mode, storage waits and every spec key). A running request, a frame without the column, and the abort carry none.
- `generate_hook_keys_reach_every_frame` now covers stream and unary, single and batch, incremental and cumulative, metrics on and off: stats reach the terminal frame only, after the schema's keys and before the hook's, with `decode_throughput` = 4.0 for two tokens 0.25 s apart; a terminal output without stats reports neither.
- `repeated_customized_info_keys_give_way` covers a `customized_info` key repeating a stats key; `native_frame_keeps_the_schema_keys_first` checks key order; `request_timing_records_ttft_once_and_e2e_on_finish` checks the zero decode latency; `decode_throughput_needs_two_tokens_and_a_decode_latency` pins the throughput rule.
- `test_rust_frames_carry_finished_requests_stats` pins explicit values and gating on the scheduler side, and asserts that no stats key collides with an api.v1 `GenerateMetaInfo` field.
- Ran locally: `cargo fmt --check`, `cargo clippy -p sglang-server -p sglang-api-types --all-targets -- -D warnings`, `cargo test -p sglang-server -p sglang-api-types`, and pytest of `test_output_streamer_customized_info.py` and `test_rust_server_extension.py`.
