# [Feat] clef: Honor an explicit prefill CUDA graph backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/45692) · state: open · merged: False

## Original PR description

## Motivation

A Clef checkpoint serves one whole prompt as a single extend and never decodes, so the joint-head
hook declares **both** CUDA graph phases disabled. A declared resolution outranks raw CLI input, so
`--cuda-graph-backend-prefill` is silently overridden for these checkpoints and the prefill graph is
unreachable. `/v1/systemone` therefore runs fully eager: on a short prompt the launch train between
~1000 tiny kernels costs more wall time than the GPU work (A100, clef-flash-int8: 70.9 ms per
request, GPU busy 30.7%).

The prefill body is graph-eligible: BCG captures the transformer stack and replays the outer tail
eagerly, and the `EmbeddingGemma` branch in the same file already uses BCG prefill in embedding mode,
so this is not a new contract. Opting the phase in also exposed a bug in the breakable runner, fixed
by the first commit of this PR.

## Modifications

1. `prefill_cuda_graph_runner.py` (`load_batch`): the static `ForwardBatch` is rebuilt field by field
   and the tail then runs eagerly on the replayed hidden states, so the prefill-only readout metadata
   it consumes must survive the rebuild. Forward `decision_layouts` (a joint schema head raises
   `the joint schema head did not score this request` -> HTTP 500 without it) and
   `token_indices_to_pool` (setwise readout; forwarding it keeps the rebuild faithful rather than
   silently falling back to standard pooling if the runner's guard is ever relaxed -- today that
   guard keeps setwise batches off the graph).
2. `model_hook.py`: keep disabling the decode phase (nothing to capture), but stop overriding a
   prefill backend the caller selected explicitly -- the same `_cuda_graph_config_locked` check the
   DeepSeek-V3 and `EmbeddingGemma` paths use. BCG is CUDA-only, so non-CUDA platforms stay eager.
   Without an explicit selection the behaviour is unchanged: both phases stay disabled. (Note:
   `--cuda-graph-backend-prefill full` remains unusable for this stack -- the hybrid GDN backend
   crashes while capturing -- so `breakable` is the working mode.)
3. `test/manual/systemone/test_decision_layouts_prefill_graph.py`: reproduction (see below). A CI
   unit test is not practical here -- the bug needs CUDA graph capture plus a joint-head checkpoint,
   which the CPU CI cannot construct.

Reproduction (needs a Clef checkpoint and a GPU):

    python -m sglang.launch_server --model-path <clef-flash> \
        --mem-fraction-static 0.85 --cuda-graph-backend-prefill breakable
    python3 test/manual/systemone/test_decision_layouts_prefill_graph.py \
        --base-url http://127.0.0.1:31510 --model <clef-flash>
    # add --expect-status 500 on the parent commit

## Accuracy Tests

- With the prefill backend selected explicitly, the parent commit fails the server's own startup
  warmup (`warmup POST /v1/systemone` -> 500, `the joint schema head did not score this request`);
  this PR serves `cuda_graph={prefill=51.61, decode=0.00}` and 3/3 `/v1/systemone` calls return 200
  with bit-identical decisions across warm runs. Without the flag the log still reports
  `cuda_graph={prefill=0.00, decode=0.00}` and the eager path answers 200 as before.
- The graph-on configuration was A/B'd against the eager path on the Decision Index 0.3 suite (2638
  rows, same edition): no row flips; scores stay within the noise band (+0.11 pp on clef-flash-int8,
  -0.11 pp on the 27B). Those runs used our full local stacked configuration, not this patch alone.

## Speed Tests and Profiling

Measured with a small stdlib probe (not `bench_serving`), A100-80GB, clef-flash-int8, 306-token
prompt, C=1: **70.5 ms eager -> 46.9 ms** with the prefill graph. Profiling of the eager path shows
the gap comes from the host launch train between ~1000 short kernels, not from GPU work.

Note on the default: we keep the phase off unless it is requested explicitly. On the 27B (BF16)
checkpoint the same phase is neutral on short/1k prompts and **regresses ~10k-token single requests
by 3-6%** (bucket padding dominates the saved launch overhead), so deployments opt in per model size.
