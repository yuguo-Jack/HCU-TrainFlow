# [Test] [NPU] radix-eviction: Add e2e test for --radix-eviction-policy-config

[Upstream PR](https://github.com/sgl-project/sglang/pull/39938) · state: open · merged: False

## Original PR description

## Motivation

`--radix-eviction-policy-config` passes tuning parameters to the radix cache eviction policy (currently only `slru`, e.g. `protected_threshold`). The parameter is decoupled from the hardware backend, but there was no NPU e2e coverage for it. This PR adds an NPU e2e smoke test that verifies `slru` + `protected_threshold` starts and works correctly on Ascend NPU, improving NPU parameter coverage.

## Modifications

- Added an NPU e2e test `test/registered/npu/basic_function/HiCache/test_npu_radix_eviction_policy_config.py`:
  - Launches the server with `--radix-eviction-policy slru` + `--radix-eviction-policy-config '{"protected_threshold": 4}'` (`--attention-backend ascend`, `--disable-cuda-graph`, `--tp-size 1`).
  - Test 1: verifies the config is parsed correctly and the server returns a successful response (no TypeError).
  - Test 2: verifies the radix cache prefix cache is still reused under the SLRU policy (second request with the same long prompt has `cached_tokens > 0`), driving `hit_count` for the protected/probationary scoring.
  - Scaffolding and registration follow the existing `test_npu_radix_cache.py` (`register_npu_ci`).

You're right -- the previous hit_count=6 satisfied both >= 4 and >= 2, so it couldn't distinguish the configured threshold from the default. Fixed: the shared prefix is warmed 4 times (hit_count reaches 4, the configured
protected threshold, and survives), while the victim prefix is cached exactly once (hit_count == 2 < 4, so it is evicted).
On the "3 hits" suggestion: the victim must be a long prompt to survive page-aligned matching (Ascend page_size=128; anything shorter is floored to an empty key). For such a prompt each finished request walks the radix tree twice -- once on prefill (cache_unfinished_req) and once on release (cache_finished_req) -- each incrementing hit_count, so hit_count advances in steps of 2 (1 request -> 2, 2 -> 4, 3 -> 6) and never takes 3. Using 2 is therefore the tightest reachable value below 4 and still uniquely proves the configured threshold drives eviction: under the default 2, a hit_count of 2 is protected and survives, so the victim's eviction can only happen with the configured value.

The "hit_count == 2 after one request" premise held for this branch's base (Sep 17), but #41520 ("count cache hits only when a request finishes", merged Oct 1) changed the semantics: cache_unfinished_req / cache_finished_req no longer exist, and the inserted_len guard in _insert_helper (radix_cache.py:728) prevents a request's own nodes from being re-counted at release. On current main, hit_count advances by 1 per finished request (1 request → 1), not by 2.
With the victim requested once, hit_count = 1 on merged main: 1 < 2 and 1 < 4, so the victim is evicted under both the configured threshold 4 and the SLRU default 2. 
The victim-boundary design is right; just recalibrate the request count. Request the victim twice (hit_count = 2 on current main, exactly at the default threshold boundary):
threshold 4: 2 < 4 → evicted → cached == 0 passes;
threshold 2 (config dropped): 2 ≥ 2 → protected → survives → cached == 0 fails.
The shared prefix at 4 requests (hit_count = 4) already catches thresholds > 4. Please also update the phase-2 comment (the "walks the tree twice" explanation describes the pre-#41520 behavior) .
