# [DSA] Prefill indexer: TP row split and per-request page-table rows (opt-in)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42006) · state: open · merged: False

## Original PR description

> **Draft for code review.** Combines #41976 and #41977 into one PR, as suggested in review. Rebased onto current `main` (`efb62ce269`). Flags and defaults are unchanged, and with every flag off behavior matches `main` exactly. The chunk decision now goes through `mqa_logits_should_chunk` (#39095), and the split reads the group via `get_parallel()` (#40068).

## Motivation

For DSA models in long-context prefill, the sparse-attention indexer dominates the cost of long prefill chunks, and decodes waiting behind those chunks stall for that long. Profiling showed two sources of waste: every attention-TP rank computes the indexer logits and top-k for all rows of the extend (the same work repeated on every rank), and the chunked paged top-k builds a per-token copy of page-table rows, copying the same request's row once per token.

## Modifications

Three commits, each off by default (with them off the code path is unchanged):
1. `SGLANG_DSA_DEDUPE_CHUNK_GATHER=1`: the chunked paged top-k in `Indexer._get_topk_ragged` passes one `page_table_1` row per request (a view) plus per-request `cu_seqlens_q` instead of the per-token copy `page_table_1[token_to_batch_idx[start:end]]`. Same fused prefill transform, same scores, lengths and row starts. CUDA only: ROCm's packed v2 top-k (#37889) already reads rows through `token_to_batch_idx` without the copy.
2. `SGLANG_DSA_INDEXER_TP_SPLIT=1`: when an extend has at least `SGLANG_DSA_INDEXER_TP_SPLIT_MIN_ROWS` rows and attention TP > 1, each rank computes logits and top-k for a contiguous slice of rows (balanced by KV length), then the top-k indices are gathered with one `all_gatherv`.
3. `SGLANG_ENABLE_DSA_TP_SPLIT_IN_GRAPH=1`: also allows the split when the indexer runs as the eager break op during `BreakableCUDAGraph.replay()`. Capture, warmup, model capture mode and stream capture keep the replicated path, so no collective enters a captured segment.

## Accuracy and performance

All GPU numbers below were measured on this PR's head (`b0d70e705a`), applied to the SGLang nightly at `f3fe7534`. That nightly includes #42038. Every arm uses the same build.

**Setup**
- **Model and serving:** GLM-5.2 FP8 on one 8-GPU node, with EAGLE (3 steps, top-k 1, 4 draft tokens).
- **HiCache L2:** `write_back`, direct I/O, `page_first_direct`.
- **Prefill and memory:** 8192-token chunked prefill; `mem-fraction-static` 0.92; max running requests = 2 × concurrency.
- **Workload:** agentic-coding trace replay, with a 20-minute measurement window per arm.
- **Noise:** one run per arm, so treat differences under about 5% as noise.

**Arms**
- **a:** TP8, split off (control).
- **b:** TP8 with `SGLANG_DSA_INDEXER_TP_SPLIT=1`, `SGLANG_DSA_DEDUPE_CHUNK_GATHER=1` and `SGLANG_ENABLE_DSA_TP_SPLIT_IN_GRAPH=1` (this PR).
- **c:** prefill CP, with `--enable-prefill-cp --cp-strategy interleave --attn-cp-size 8`.
- **e:** CP2 × attention-TP4, with `--attn-cp-size 2`.

Relative numbers are against arm a at the same concurrency.

- **Prefill CP vs this PR:** on this workload, the split (b) beats every runnable prefill-CP arm on tok/s per GPU at c16 and c32; CP is 5.9–10.1% lower. At c16 CP is also 12.6–22.3% lower on p90 per user. At c32, CP2 × TP4 is within noise of b on p90 (−1.0%) but 9.2% lower on tok/s per GPU, with worse TTFT.
- **Why:** CP has the fastest long-context prefill (CP8 is flat at about 300 ms per chunk). But decode is slower on replicated attention weights (+2% to +48% per step), and the KV pool is 1.6–7.5% smaller. The split keeps decode and the KV pool unchanged and makes chunk time nearly flat in cached context.
- **`--enable-cp-decode-attn-tp` (CP8)** crashes at startup with the default DeepGEMM FP8 path. The per-CP-rank slice of the packed `q_b_proj` weight scales leaves a stride DeepGEMM rejects; the fix is in open #43972.
  - With a non-default FlashInfer dense FP8 GEMM backend it runs. Against the split on the same backend at c32: p90 30.02 vs 29.43 (+2.0%), tok/s per GPU 10,443 vs 10,849 (−3.7%), TTFT p90 26.93 vs 22.85 s, decode step +30%, 256K+ chunk 342 vs 529 ms.
  - That backend alone costs the split 7.2% tok/s per GPU against DeepGEMM.
- **Higher load:** the gain grows with prefill pressure. At c64, past the knee for both arms (about 23 requests running, TTFT p90 of 7–12 minutes), b vs a is 8.74 vs 2.84 p90 tok/s per user, and 5,007 vs 2,113 tok/s per GPU.
- **How these were measured:** chunk times are the wall time between consecutive prefill log lines on rank 0, with cached context reconstructed by chaining chunks. Decode step time is a proxy from decode log lines. The KV pool size is from the startup log.

**Engagement**
- **b:** the "split across attn-TP", in-graph and dedupe log lines appear on all 8 ranks in every run. 130 (c16) and 168 (c32) in-graph-eligible graphed prefills per 20 minutes.
- **c, e:** the CP-enabled line appears, the breakable graph is disabled, and the prefill graph backend is `disabled`, with 0 graphed prefills.

**Bit-exactness (CPU)**
- Commit 1 matches the per-token path: same inputs to the same kernel.
- In commit 2 each row's logits and top-k are computed exactly as before, just on one rank, so the gathered result is identical to the replicated path.
- Commit 3 matches the replicated path in a multi-process simulation of capture and replay, with the same gather order and sizes on every rank.
- On current `main`, the equivalence checks pass for all three commits: 81/81, 200/200 and 29/29.
