## Motivation

Whether the prefix cache reclaims an allocation's demand jointly or evicts each pool's shortfall, and who drives "evict, then check", was decided by reading `pools_share_memory` in every capacity entry point, in `evict_for_alloc` and in the decode queue. Under `--radix-eviction-policy joint_lru`, an allocation's reclaim walked the cache's own victim order rather than the joint order. Pools without unified memory presented a fresh `StaticKVStorage` on every `kv_storage_of` call. This PR decides the discipline once, applies joint LRU to allocation reclaim, restores `main`'s window-first reclaim where it applies, and keeps one static storage per pool.

## Modifications

- `mem_cache/capacity.py::discipline` reads the declaration once and returns the discipline (pools sharing one memory, or pools of their own) that answers every capacity question, `evict_for_alloc` and whether windows share the owner's memory. A cache reclaims jointly (`reclaim_jointly`) or evicts shortfalls (`evict_pool_shortfalls`); allocators answer the token pool's room themselves (`owner_available_size`).
- Window-first reclaim: `capacity.windows_reclaimed_first` is true with a HiCache storage backend attached or on a PD decode node (read on every reclaim); the cache's reclaim then takes window entries before token entries, keeping FULL prefixes, as `main` does.
- Joint LRU: under `joint_lru`, with compaction able to run, an allocation's reclaim takes every reclaimable token and window entry in the joint access order and stops at the first victim after which the allocation fits. Other policies keep the cache's order.
- One static storage per pool: built the first time it is asked for and kept by the pool; the step's prefix cache and batch are passed to `take_extend` / `take_decode`; pool shape and the PD draft pool are bound once (`bind_shape`, `bind_transfer_draft`); the window's retention lives on the storage (`BaseTokenToKVPoolAllocator.window_retention` is removed).
- Tests: joint-LRU allocation reclaim evicts a prefix of the order a full eviction takes and fits afterwards; window-first predicate per configuration and the first sub-pool evicted from (`test_multi_ended_allocator.py`, `test_unified_joint_allocation_eviction.py`).

**Behavior changes (unified memory):**
- With a HiCache storage backend attached or on a PD decode node, allocation reclaim evicts window entries first (`main`'s rule; heads #48010–#48024 of this stack evict token entries first in every mode).
- Under `--radix-eviction-policy joint_lru`, allocation reclaim follows the joint LRU order.
