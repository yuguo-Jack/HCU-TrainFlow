# [Feat] [NPU] unlimited-ocr: Support Unlimited-OCR on Ascend NPUs

[Upstream PR](https://github.com/sgl-project/sglang/pull/44391) · state: open · merged: False

## Original PR description


## Motivation

Make Baidu Unlimited-OCR (`PaddlePaddle/Unlimited-OCR`) servable on Ascend NPUs. The upstream GPU implementation (#29186) relies on prefill-aware sliding-window attention, a paged reference-SWA cache with prompt protection, and the model's no-repeat n-gram logit processor — none of which had an Ascend path. This PR ports all three to the Ascend backend and validates end-to-end OCR quality against the published numbers.

Contributes to the Ascend multimodal workstream in the NPU roadmap: #43519 (Unlimited-OCR item, "adapt and validate document OCR on Ascend").

## Modifications

**Reference-SWA attention on Ascend**
- Prefill-aware SWA in the Ascend attention backend: decode attends over the protected prefill range (prompt + image tokens) plus the recent sliding window, via a paged layout; eager decode serves through native SDPA (`run_sdpa_forward_decode` with per-request reference lengths), which tracks the reference implementation's rounding most closely.
- Re-prefill that appends generated tokens beyond the original prompt is routed through the native SDPA extend path; full-prompt prefill keeps the regular FIA path.
- ACLGraph decode (full-graph, bs 1/2/4) works alongside the paged SWA cache with a model-specific graph policy.

**Paged reference-SWA cache**
- Per-request evict floor in the SWA token allocator protects prompt/image tokens from sliding-window eviction; reference lengths are preserved across retraction.
- Ascend SWA KV pool wiring in the KV cache configurator (including the spec-decode KV-copy configuration the generic hybrid path already had).
- Multi-page chunked prefill is disabled for this model on Ascend until the chunked reference window semantics are validated (single-page chunked prefill is supported and validated).

**Vision / model plumbing**
- Preserve bundled page axes in vision encoding and expose the page axis for spatial crop splitting, so multi-page documents keep per-page ordering.
- MoE model variant registration and model-specific serving overrides (graph policy, chunked prefill).

**NGRAM speculative decoding on Ascend**
- Linear-time NGRAM draft/verify for this model (`ngram_npu`), with the spec-decode KV move routed to native advanced indexing for NPU paged pools (which do not build tiled-copy strides) and an fp4-scale-move guard for pools without native scale buffers.

**General Ascend fixes**
- `ascend_fuseep` EP backend no longer crashes on BF16 (unquantized) MoE layers: weight scales are now optional (empty scale + `quant_mode=0` per the deep_ep contract), with an explicit error for `fuseep_mode=2`, which the kernel does not support in BF16.

**Overlap-safe sampling for custom logit processors (generic scheduler fix)**
- Under overlap scheduling, a custom logit processor rebuilt its history from `req.output_ids` one step behind: the previous batch's sampled tokens were not yet committed when the current batch sampled, so the stale-view ban never landed on the true next token and any period ≥ 2 loop survived the model's `NoRepeatNGramLogitProcessor` (affects all backends, not just Ascend).
- Fix: extend the existing delayed-sampling condition in `TpModelWorker.forward_batch_generation` to batches carrying a custom logit processor, reusing the grammar path's delay mechanism — the k-th token is now sampled only after the first k−1 tokens are committed to `req.output_ids`. Forward overlap is preserved; grammar, prefill-only, and explicit delay-sampling behavior are unchanged.

**Tests**: unit tests for image input handling, the MoE variant, the Ascend native SDPA backend, NPU NGRAM, the model overrides, and a scheduler-level delayed-sampling regression for custom logit processors under overlap (deterministic phase-sequence cases fail on the old code, pass on the fix; covers overlap on/off, mixed batches, first-token/prefill→decode boundaries, and grammar/prefill-only pass-through).

## Usage

Single-card launch (validated configuration):

```
python3 -m sglang.launch_server --model-path PaddlePaddle/Unlimited-OCR \
  --device npu --attention-backend ascend --page-size 128 \
  --context-length 32768 --max-total-tokens 65536 \
  --enable-custom-logit-processor
```

`--enable-custom-logit-processor` enables the model's `DeepseekOCRNoRepeatNGramLogitProcessor` (ngram 35, window 128), as in the reference recipe. The request shape (chat completions with `images_config` / `image_mode`) is unchanged from #29186. TP2 and attention-DP deployments are also validated.

## Accuracy Tests

Full official [OmniDocBench v1.5](https://github.com/opendatalab/OmniDocBench) run — all 1355 pages, official `end2end_dataset` + `quick_match` scoring (CDM with XeLaTeX rendering), greedy decoding, gundam image mode, single Ascend NPU (64GB):

| Metric | This PR (Ascend) | Published (paper, GPU) |
| --- | --- | --- |
| Text Edit Distance ↓ | 0.0384 | 0.038 |
| Formula CDM ↑ | 0.9249 | 0.9261 |
| Table TEDS ↑ | 0.8529 | 0.9093 |
| Table TEDS-S ↑ | 0.8971 | 0.9407 |
| Reading order Edit ↓ | 0.0452 | 0.045 |
| Overall ↑ | 91.31 | 93.23 |

Text, reading order, and formula CDM match the published values (Δ ≤ 0.001); the gap is concentrated in table TEDS. 1353/1355 pages completed with a clean stop; 2 dense newspaper pages hit the 32K context budget (`finish_reason=length`) and were scored with their truncated output. A length stop alone does not establish that the source document genuinely requires that many tokens; the Chicago control below reproduces erroneous repetition on the GPU reference path as well.

Also validated on **OmniDocBench v1.6** (the 1651-page release adding the 296-page hard subset; evaluation code at commit `147cd5a`, MGAM matching + pure-Python CDM), same recipe and hardware:

| Metric | This PR (Ascend) | Published (paper, GPU) |
| --- | --- | --- |
| Text Edit Distance ↓ | 0.0969 | 0.042 |
| Formula CDM ↑ | 0.9502 | 0.9579 |
| Table TEDS ↑ | 0.8573 | 0.9016 |
| Table TEDS-S ↑ | 0.8974 | 0.9332 |
| Reading order Edit ↓ | 0.1338 | 0.129 |
| Overall ↑ | 90.35 | 93.92 |

Formula CDM and reading order are close to the published values (Δ ≤ 0.008); the gap concentrates in text edit distance and table TEDS, consistent with the repetition-loop pages and the hard-subset's denser content. 1647/1651 pages completed with a clean stop; 4 pages hit the 32K context budget. The failing outputs include degenerate repetition that escaped the model's `NoRepeatNGramLogitProcessor` under default overlap scheduling due to the upstream scheduler timing issue described above (the processor read `req.output_ids` one step behind, so the ban never landed on the true next token). Unit tests and an A/B image test verify the processor's intended behavior when it receives the committed history.

With the overlap-safe sampling fix in this PR, re-running the 4 degenerate pages under the default (overlap-enabled) configuration heals 2 of them outright (both now finish cleanly instead of looping to the 32K context budget). The 2 dense newspaper pages still repeat through patterns permitted by the current 35-gram / 128-token-window rule: Chicago generates changing years, while Washington includes exact paragraph repetitions with a 137-token period, beyond the rule's effective search range. These residual failures do not establish that the history-timing fix failed. Re-scoring v1.6 with the 2 healed pages replaced:

| Metric | This PR (Ascend, overlap fix) | Before fix | Published (paper, GPU) |
| --- | --- | --- | --- |
| Table TEDS ↑ | 0.8608 | 0.8573 | 0.9016 |
| Overall ↑ | 90.47 | 90.35 | 93.92 |

All other metrics are unchanged; the entire gain comes from table TEDS.

### Chicago GPU/NPU reference control

We additionally compared the Chicago Tribune page 015 on an NVIDIA A100 40GB and Ascend using the checkpoint's original Hugging Face implementation. The GPU environment uses PyTorch 2.10.0+cu128, torchvision 0.25.0, and Transformers 4.57.1; the NPU reference also uses PyTorch 2.10.0 and Transformers 4.57.1. The downloaded GPU weights match the NPU checkpoint byte-for-byte by SHA-256. Reference code/configuration, tokenizer, image, prompt, gundam tiles, and decoding settings are shared: 3557 prompt tokens, 32 tiles, BF16, greedy, ngram 35 / window 128. All five input tensors were verified equal against the official GPU `infer()` preprocessing.

| GPU reference path | Output analyzed | Result |
| --- | ---: | --- |
| Token-by-token HF forward, without autocast | First 6500 tokens | County Clerk phrase repetition followed by incrementing years through 2227; no EOS |
| AutoModel with the official CUDA BF16 autocast setting | 6500 tokens | Repeated phrases and repeated second notice; no EOS |
| Official `AutoModel.infer()` → `generate()` | 6500 tokens | All token IDs identical to the autocast observation path; no EOS |

To compare scores without conflating different generated histories, we also replayed three fixed prefixes token by token on GPU and NPU (1800, 5000, and 600 steps), preserving the original protected prompt and generated-token ring cache. At output index 1192 of the saved Chicago trajectory, after `Check with the County Clerk`, the image requires ` as`, but both devices prefer the incorrect ` to` before any n-gram ban:

| Reference implementation | Incorrect ` to` logit | Correct ` as` logit | EOS logit |
| --- | ---: | ---: | ---: |
| NPU HF | **20.250** | 17.250 | 9.625 |
| GPU HF, without autocast | **20.375** | 18.250 | 10.000 |
| GPU HF, with autocast | **20.250** | 18.250 | 10.0625 |

At index 4682, the GPU processor correctly bans the repeated `201` token, but `202` still scores 16.875 versus EOS at 9.625; the next digit completes `2020`. NPU and GPU autocast controls make the same choice. Across the three GPU/NPU fixed-prefix comparisons, EOS is never the post-processor argmax. Thus, suppressing exact repetition does not necessarily make EOS the preferred continuation.

These controls reproduce the failure in the official GPU reference path, supporting that the Chicago issue is not exclusive to Ascend or the SGLang scheduler. They do not establish numerical equivalence: GPU/NPU post-processor argmax differs at 14/1800, 36/5000, and 4/600 steps under identical histories. The free-generation comparisons use a 6500-token diagnostic scope; they are not a complete 32K termination test or a new benchmark run. No corresponding GPU control was run for Washington, and this single-page result does not explain the full published-score gap or uniquely identify a training, architecture, or operator cause.

### Other accuracy checks

For v1.5, ablations rule out scoring-recipe causes for the remaining TEDS gap: the ModelScope-commented `remove_det` variant (which drops each page's last block) scores worse (Overall 89.23 vs 91.31), and re-running the 63 lowest-TEDS pages (107 tables with TEDS < 0.8) in base image mode (1024 whole-page, no tile cropping) lowers overall TEDS (85.29 → 83.95), so the official 90.93 cannot be explained by tile cropping or post-processing either. Our pipeline cross-checks cleanly: DeepSeek-OCR's published TEDS (84.97) matches our reproduction (85.29) on the same evaluation stack.

Feature matrix validated on real weights before the benchmark (single-page gundam/base, 18-row long output, repeat determinism, 8-way concurrency as gates): ACLGraph decode (bs 1/2/4), chunked prefill (chunk 256, single-page), TP2, attention-DP (TP2 + attn-DP2), batch-16 capacity, and NGRAM speculative decoding (accepted length 2.6–4.7; long outputs identical to non-speculative).

Not enabled on Ascend: EP (`ascend_fuseep` kernels are INT8-weight-only; BF16 checkpoints are rejected by the CANN operator).
