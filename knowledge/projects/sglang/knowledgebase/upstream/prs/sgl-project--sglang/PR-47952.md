## Motivation

<!-- Describe the purpose and goals of this pull request. -->

MSCCL++ (`--enable-mscclpp`) has been part of SGLang's distributed runtime since #6277, was reworked in #22734 (which also added it to the Docker image) and extended to 8-node and NVLS algorithms in #37442. However, no registered CI test exercises it, and the `mscclpp` package is not installed in the CUDA CI environment. `pymscclpp.py` has since been touched by several SGLang-wide refactors (e.g. #23906, #30493, #33013) with nothing to catch a regression.


This PR turns the existing `benchmark/kernels/all_reduce/benchmark_mscclpp.py` into a CI correctness check for the MSCCL++ all-reduce path in the TP group, runs it through a thin registered test, and lets CI install MSCCL++.

No GitHub workflow (`.github/workflows/*.yml`) changes.

- **`test/registered/kernels/ops/communication/test_mscclpp_wrapper.py`** (new): thin wrapper. Runs `benchmark_mscclpp.py --mscclpp-algorithms all --expect-graph-backend mscclpp` under `torchrun` at world sizes 4 and 8 (skipped if the machine has fewer GPUs), over 2 KiB–8 MiB, and fails if it exits non-zero. bf16 per PR; fp16/bf16/fp32 nightly via `get_ci_test_range`. Registered `extra-b` and `nightly` on `8-gpu-h200`.
- **`benchmark/kernels/all_reduce/benchmark_mscclpp.py`**:
  - Fails fast with a clear error if the MSCCL++ communicator is unavailable, so a missing or broken `mscclpp` cannot pass.
  - Checks every timed path against an untimed NCCL all-reduce bit-exactly (`atol=0, rtol=0`; inputs in {0, 1} keep sums exact in every dtype).
  - New check: replays one captured MSCCL++ graph three times on new input and compares each result with NCCL, as serving does every decode step. The timing loop reuses the same input, so a replay returning stale data (e.g. from scratch-buffer or flag reuse) would pass there unnoticed.
  - `--backends`: choose which of the existing timed paths to run (`torch-eager`, `mscclpp-eager`, `mscclpp-graph`, `pynccl-graph`; default all).
  - `--mscclpp-algorithms`: `tuned` (default, previous behavior), `all`, or algorithm names. Forces each MSCCL++ all-reduce algorithm over the sizes it supports instead of only the one tuning picked on that machine, so CI covers every kernel regardless of which wins on the runner.
  - `--expect-graph-backend mscclpp`: the results table the benchmark prints at the end of a run now also reports which backend `GroupCoordinator.all_reduce` dispatched to, in eager mode and under CUDA graph capture (via spies on each communicator's entry point), and checks a graph captured through it against NCCL. This flag fails the run if the graph-mode backend is not MSCCL++. Results stay correct if SGLang silently falls back to another backend, so this is the only check that catches a dispatch regression.
  - `--dtypes`, `--min-bytes`, `--max-bytes`; adds `dtype`, `mscclpp algorithm` and dispatch columns to the results table. With no options (bf16, 2 KiB–1 MiB, tuned algorithm, all four paths) it times the same paths as before; the only additions are the extra columns and checks.
- **`benchmark/kernels/all_reduce/README.md`**: documents the checks and options.
- **`scripts/ci/cuda/ci_install_dependency.sh`**: new `install_mscclpp` step, run when `INSTALL_MSCCLPP=1`. MSCCL++ is not published on PyPI (the Dockerfile also builds it from source), so the step builds it at the tag pinned by `docker/Dockerfile` (`MSCCLPP_VERSION`) with the Dockerfile's CMake arguments. CI therefore tests what the image ships and follows future pin bumps. The build is cached per tag in the persistent CI venv.
- **`scripts/ci/cuda/ci_install_dependency_mscclpp.sh`** (new): wrapper that sets `INSTALL_MSCCLPP=1`.
- **`scripts/ci/runner_configs.yml`**: `8-gpu-h200` uses the wrapper; `install_timeout` 20 → 40 to cover the one-time build on a fresh runner. No other runner config changes.

**What the test catches:**
- **If MSCCL++ returns wrong results**, we would know because every MSCCL++ call (eager, CUDA graph, graph replayed on new input, and through `GroupCoordinator.all_reduce`) is compared bit-exactly with NCCL on the same input, for every message size, dtype and MSCCL++ algorithm. Any mismatch fails the test.
- **If SGLang stops choosing MSCCL++**, we would know because the benchmark records which backend `GroupCoordinator.all_reduce` actually called under CUDA graph capture, and `--expect-graph-backend mscclpp` fails the test if it was anything else. Results would still be correct after such a fallback, so the output comparisons alone could not catch it.
- **If `mscclpp` is missing or fails to initialize**, we would know because the benchmark exits with "MSCCL++ communicator unavailable" instead of skipping.

Open for maintainers: the runner choice (`8-gpu-h200` follows `test_custom_all_reduce.py` / `test_symm_mem_all_gather.py`; `4-gpu-h100` would be cheaper but only covers 4 ranks), and whether `install_mscclpp` should run on all CUDA runners instead of only those that run MSCCL++ tests.

## Speed Tests and Profiling

<!-- If this pull request impacts inference speed, provide benchmarking and profiling results. -->

No inference-path change. For context, `benchmark_mscclpp.py --mscclpp-algorithms all` on 4× GB200 (one node), µs, tuned algorithm per size:

| Message | MSCCL++ algorithm (tuned) | torch eager (NCCL) | MSCCL++ eager | **MSCCL++ graph** | PyNCCL graph |
|---|---|---|---|---|---|
| 2 KiB | nvls_packet | 90.1 | 19.0 | **6.5** | 18.1 |
| 64 KiB | nvls_packet | 85.1 | 16.9 | **7.4** | 19.8 |
| 512 KiB | packet | 83.0 | 17.9 | **10.6** | 21.0 |
| 1 MiB | packet | 84.5 | 18.3 | **12.6** | 22.7 |
| 8 MiB | rsag_zero_copy | 84.6 | 458.1 | **31.5** | 49.1 |

The table also shows why testing every algorithm matters: the non-tuned ones are correct but can be much slower at sizes they support (e.g. `nvls_packet` at 512 KiB: 179 µs graph), so tuning never selects them on this machine, and they would otherwise go untested.

CI cost measured through `rerun-test.yml`: `install_mscclpp` takes 279–333 s on a runner's first run and 1–2 s afterwards (cached per pinned tag). The test step took 1–1.75 min on 4 GPUs (all algorithms, dispatch check included; ~1–1.5 min per world size), mostly MSCCL++ start-up tuning.

**Out of scope, reported separately:** MSCCL++ all-gather is only registered for multi-IPC-domain topologies (`_MULTI_NODE_IPC_DOMAIN_COUNTS`), so it is not exercised on single-node runners; and on multi-node GB200 (one NVLink domain), the zero-copy all-reduce fails for messages ≥ 2 MiB on PyTorch-allocated tensors. Neither affects single-node CI.
