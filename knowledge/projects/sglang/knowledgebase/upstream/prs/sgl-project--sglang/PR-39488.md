# [weight_cache] Add Prometheus `/metrics` endpoint to the daemon

[Upstream PR](https://github.com/sgl-project/sglang/pull/39488) · state: closed · merged: False

## Original PR description

## Motivation

Related to #33522 Ops & reliability.

Second slice of the "daemon status command + Prometheus metrics" item. **Stacked on #39256** (the `status` request): this PR's diff includes that commit until #39256 merges, after which it will be rebased. Review only the second commit (`d5b67fbef9`).

The weight cache daemon is a standalone process that outlives the engine in `client` mode, so it cannot share the engine's `/metrics`. This PR gives each daemon its own scrape endpoint.

## Modifications

- New `--metrics-port` flag on the daemon launcher. Each daemon serves `/metrics` from a background thread. When the launcher starts several daemons, `gpu_id=N` listens on `port+N`; a single-daemon launch uses the port as given. Off when omitted.
- `weight_cache/metrics.py`: a custom `prometheus_client` collector on a private registry that re-reads `_status_snapshot()` on every scrape. The `status` CLI and Prometheus therefore report identical numbers, and adding a snapshot field is the only step needed to expose it. Every series carries `gpu_id` / `tp_rank` / `pp_rank`; an `_info` metric holds the static identity; `None` fields (still loading, never served) emit no sample rather than a fake zero.
- The server starts before `load()` so a scrape mid-load sees `loaded=0`.
- `_status_lock` serializes the serve loop's counter and client-PID updates against the scrape thread's snapshot.

Exposed metrics (prefix `sglang:weight_cache_daemon_`): `info`, `loaded`, `preloaded_weights_bytes`, `num_tensors`, `load_seconds`, `uptime_seconds`, `live_clients`, `last_served_timestamp_seconds`, `fetch_state_total{result=hit|mismatch}`.
