# [Fix] dsv41: Open the assistant turn when a conversation has only a system message

[Upstream PR](https://github.com/sgl-project/sglang/pull/46072) · state: closed · merged: False

## Original PR description

## Motivation

On the DeepSeek-V4.1 chat-encoding path (`chat_encoding_spec == "dsv41"`), a request whose `messages` hold only a system message gets no generation prompt. The prompt ends right after the system text, without `<｜Assistant｜>`, so the model continues the system text instead of answering it. The request still returns HTTP 200, often with an empty reply.

`render_message` in `encoding_dsv41.py` writes the `<｜Assistant｜>` opener after a user or developer message, or after a system message at `index > 0`. A leading system message is not followed by one, and when nothing comes after it, nothing ever opens the turn:

```
messages = [{"role": "system", "content": "You are a poet. Write a haiku about rain."}]
chat:     <｜begin▁of▁sentence｜><｜System｜>You are a poet. Write a haiku about rain.
thinking: <｜begin▁of▁sentence｜><｜System｜>Reasoning Effort: ...\n\nYou are a poet. Write a haiku about rain.
```

The encoder renders a leading system message followed directly by a final assistant message the same way. On the serving path, however, `_handle_last_assistant_message` first turns that request into a case above. A string final assistant message becomes a user message. With `continue_final_message`, it is removed and used as the continuation prefix, which leaves a system-only conversation, and this PR covers that.

This rendering matches DeepSeek's reference `encoding/encoding.py` in the model repo, which also has no generation prompt for this shape. An OpenAI-compatible `/v1/chat/completions` request always asks for a reply, though, and nothing else in the serving path adds one for this shape. In the end-to-end test below most replies are empty or continue the system text. vLLM made the same change for DeepSeek V4 in vllm-project/vllm#51262 (merged) and proposes it for V4.1 in vllm-project/vllm#62459 (open).

## Modifications

- `encoding_dsv41.py`: a leading system message also opens the assistant turn when the conversation has no user or developer message (`find_last_user_index` returns -1). This is the same opener that a user message gets: `<｜Assistant｜>` followed by `<think>` or `</think>`, depending on the thinking mode. Conversations that contain a user or developer message render exactly as before. Before / after renders of 12 conversation shapes with a user or developer turn (system + user, multi-turn, tool calls and results, developer, inline system), each in chat and thinking mode and with `drop_thinking` on and off, are identical (48 / 48).
- A user message that holds only tool results does not count as a user turn (`find_last_user_index` skips it). So `[system, assistant(tool_calls), tool]` also changes: a conversation that starts with only a system prompt, where the model calls a tool first. It now gets the opener between the system text and the assistant message. Before, the assistant message was glued to the system text, and in thinking mode there was a stray `</think>` (`...S</think>\n\n<｜DSML｜ calls>...` becomes `...S<｜Assistant｜><think></think>\n\n<｜DSML｜ calls>...`). The same conversation with a user turn before the tool call renders as before.
- Test: `test_dsv41_system_only_conversation_opens_assistant_turn` checks three things. A system-only conversation ends in `<｜Assistant｜><think>` (thinking) or `<｜Assistant｜></think>` (chat), with exactly one opener. `[system, assistant(tool_calls), tool]` has the opener right after the system text. system + user renders as before.

## Accuracy Tests

Setup: DeepSeek-V4.1-Flash on 4×H200, `lmsysorg/sglang:v0.5.21` and `lmsysorg/sglang:v0.5.22`. Their `encoding_dsv41.py` is byte-identical, and the diff applies cleanly to both and to `main`. Server flags: `--tp-size 4 --ep-size 4 --reasoning-parser auto --tool-call-parser auto --chunked-prefill-size 2048 --max-running-requests 128 --mem-fraction-static 0.75`. "Before" is the image as is; "after" is the image with this PR.

Requests go to `/v1/chat/completions` with `max_tokens` 1024 and three thinking settings: `chat_template_kwargs.thinking` not sent (server default), `true`, `false`. Each cell is 1 greedy (T = 0) + 4 sampled (T = 1.0, top_p 0.95) requests (v0.5.22: 1 + 2). The table counts empty `content` per cell for not sent / `true` / `false`:

| messages | v0.5.21 before | v0.5.21 after | v0.5.22 after |
|---|---|---|---|
| system only: "You are a poet. Write a haiku about rain." | 1 / 2 / 0 of 5 | 0 / 0 / 0 of 5 | 0 / 0 / 0 of 3 |
| system only: "Translate into French: Good morning, how are you today?" | 5 / 5 / 4 of 5 | 0 / 0 / 0 of 5 | 0 / 0 / 0 of 3 |
| system only: "Be a helpful assistant" | 0 / 2 / 0 of 5 | 0 / 0 / 0 of 5 | 0 / 0 / 0 of 3 |
| system + user (control) | 0 / 0 / 0 of 5 | 0 / 0 / 0 of 5 | 0 / 0 / 0 of 3 |

- Before, the non-empty replies continue the system text rather than answer it. For the haiku prompt the greedy reply starts with ` (No markdown, plain text only)\n---\n` and then writes the haiku. For "Be a helpful assistant" (thinking not sent / `false`) the greedy reply starts ` that answers questions about the<blockquote> <p>Be a helpful assistant that answers…` and repeats until `max_tokens`; with thinking `false`, 2 of 5 replies contain other chat templates' markers such as `<|im_start|>user` / `<|im_end|>`.
- After, every reply answers: the haiku, the French translation, and for "Be a helpful assistant", e.g. `I'd be happy to help! What can I assist you with today?`. No reply is empty, none stops at `max_tokens`, and with thinking on the reasoning is in `reasoning_content` in every case.
- The control (system + user) gives the same greedy replies before and after.
- v0.5.22 "before" was not run separately: its encoder file is identical to v0.5.21's, so its rendering is the same.

Unit tests, in the v0.5.22 image with this PR applied:

- `test/registered/unit/entrypoints/openai/test_serving_chat.py` of that image: 156 passed (113 subtests).
- The new test only calls `encoding_dsv41.encode_messages` and does not depend on the other tests, so I ran it from `main`'s test file against the image. Its system-only part passes (2 subtests). Run against the unchanged encoder, it fails in both subtests.
- The tool-call cases were added after that run. I checked the full test method by running it on its own against the encoder: it passes with this change, and fails in all 4 subtests with the unchanged encoder.

## Notes

- I found no SGLang PR or issue for this. #43549 (open) changes how inline (non-leading) system messages are hoisted on the Anthropic path; #45411 (open) changes how `find_last_user_index` is computed. Neither changes this case; whichever lands second needs only a one-line rebase.
- dsv4 and dsv32 have the same shape: their encoders open the turn only after a user or developer message. They are left out to keep this PR to the encoder I tested end to end; happy to extend them in a follow-up.
- Not covered: a leading system message followed by an assistant message and then a user turn (an assistant greeting before the first user message). It still renders without an opener between the system and assistant text, as the reference encoder does. vllm-project/vllm#62459 also opens the turn in that case; I can align this condition with it if preferred.
- Behavior change: a client that sent only a system message and relied on the model continuing that text now gets a reply instead. Plain text continuation belongs on `/v1/completions`.
