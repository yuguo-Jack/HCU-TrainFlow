# [Fix] function_call: Accept more Harmony call shapes in GptOssDetector

[Upstream PR](https://github.com/sgl-project/sglang/pull/44780) · state: open · merged: False

## Original PR description

## Motivation

Fixes #41315.

`--tool-call-parser gpt-oss` only recognizes a call written exactly as `<|start|>assistant<|channel|>commentary to=... <|constrain|>json<|message|>...`. Three other valid Harmony shapes are not parsed in non-streaming responses:

- **The call is the first message of the completion.** The generation prompt already ends with `<|start|>assistant`, so a call emitted without an analysis message first starts with `<|channel|>commentary to=...`. `has_tool_call()` only looks for `bot_token = "<|start|>assistant<|channel|>commentary"`, finds nothing, and the raw Harmony markup is returned as `content`. The streaming path parses the same text, so the two paths disagree.
- **The call has no `<|constrain|>json`.** The Harmony format treats `<|constrain|>` as optional, but `tool_extract_pattern` requires `<|constrain|>json<|message|>`. The call is dropped and `content` is empty, so the request returns neither a tool call nor text.
- **The recipient is in the role header** (`<|start|>assistant to=functions.X<|channel|>commentary ...`). The Harmony spec allows it, and openai-harmony renders history this way. The whole call comes back as `content`.

Repro, CPU only:

```python
from sglang.srt.entrypoints.openai.protocol import Function, Tool
from sglang.srt.function_call.gpt_oss_detector import GptOssDetector

tools = [Tool(type="function", function=Function(name="get_weather", parameters={
    "type": "object", "properties": {"city": {"type": "string"}}}))]
call = '<|channel|>commentary to=functions.get_weather<|message|>{"city": "Paris"}<|call|>'
res = GptOssDetector().detect_and_parse(call, tools)
print(res.calls, repr(res.normal_text))
```

Before this change: `[] '<|channel|>commentary to=functions.get_weather<|message|>{"city": "Paris"}<|call|>'`. After: one `get_weather` call with `{"city": "Paris"}` and empty content.

## Modifications

- `python/sglang/srt/function_call/gpt_oss_detector.py`:
  - `has_tool_call()` also matches a `<|channel|>commentary` header that carries a recipient (`to=`), and a role header `<|start|>assistant to=functions.`. The existing `bot_token` check stays, so previously detected text is unchanged. A recipient outside `functions.` in the role header, such as `to=browser.search`, is still not treated as a function call.
  - `tool_extract_pattern` makes `<|constrain|>json` optional and accepts the `<|channel|>commentary` header between the recipient and the message, so the three shapes above reach `json.loads` the same way as the common shape.
- `test/registered/unit/function_call/test_gpt_oss_call_shapes.py`: new CPU tests for the shapes above (detector only, the forced channel-first payload from #41747, and after the gpt-oss reasoning parser), a streaming increment without `<|constrain|>`, and plain text that must stay content.

Streaming: a call without `<|constrain|>` that arrives in one increment is now parsed too, because the streaming path uses the same extraction pattern. This PR does not change the streaming buffering logic, so per-token streaming and the recipient-in-role-header shape in streaming are not covered here.

Overlap: #41826 changes the same `has_tool_call` line. Its pattern (`<|channel|>commentary\s+to=`) is the first alternative of `tool_start_pattern` here, so this change covers it. The channel-first payload in #41747 (`tool_choice: "required"`) takes the same path, and the detector now parses it. #41045 and #43243 rework the streaming path, which this change does not touch.
