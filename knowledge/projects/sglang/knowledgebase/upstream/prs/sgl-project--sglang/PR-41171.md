# [qwen 3.8 next] Fuse hybrid speculative state commits across state pools

[Upstream PR](https://github.com/sgl-project/sglang/pull/41171) · state: open · merged: False

## Original PR description

## Motivation

Target verification commits accepted GDN, convolution, and PLE states through multiple launches. Combine compatible state pools and active/tracking writes while preserving tracking overwrite precedence.

## Modifications

Cache validated state geometry with storage/layout invalidation, preserve integer state bits and strided convolution windows, and retain unsupported-path fallbacks.

This PR is independently based on `main`. QSA KV preparation is tracked separately in #40972.

- puncsky · comment · 2026-10-20T16:43:39Z · [source](https://github.com/sgl-project/sglang/pull/41171#issuecomment-6296113027)

A bounded GB10 baseline that may help scope the state-commit optimization here. **I did not run this PR**, and these numbers do not estimate its fused-pool gain; they test only whether increasing the existing SSM copy tile is sufficient.

Environment: DGX Spark GB10 / SM121, CUDA 13, pinned SGLang 0.5.21 image `lmsysorg/sglang@sha256:b1259f3ea3275f66237c498ea388919729018bc9f01c3d638391e06e2cf3f469`, source `e00930c5489053f26d86b179cee0d087f846acbb`. We changed only the SSM tile constant from 1024 to 4096/8192/16384; all other Python AST nodes match. Actual Qwen3.8-27B geometry is 48 recurrent layers, 48 × 128 × 128 FP32 SSM elements per entry, four speculative positions, batch 1/8/16.

| Tile | b1 live copy ms | b8 live copy ms | b16 live copy ms | b16 all-masked tracking ms |
| --- | ---: | ---: | ---: | ---: |
| 1024 | 1.3795 | 11.1239 | 22.5202 | 0.3180 |
| 4096 | 1.3968 | 11.0705 | 22.1420 | 0.0908 |
| 8192 | 1.3930 | 11.0604 | 22.0708 | 0.0639 |
| 16384 | 1.3888 | 10.9900 | 21.9492 | 0.0619 |

Each cell is a 25-sample CUDA-event median for the operation, not HTTP latency. The largest tile improves b16 live copy by 2.54%, while b1 regresses by about 0.67%. FP32/BF16 exact state and convolution-window checks passed for all four variants, including invalid/freed slots, partial/all accepted indices, checkpoint crossings, changing request generations, envelope strides and tail masks. This is copy-semantics coverage, not recurrent-engine integration validation. Variant order is fixed, so this is a candidate screen rather than repeated server A/B.

A separate historical b16 trace has 499.840 ms of live scatter and 6.246 ms of tracked scatter within an 8251.581 ms GPU span. Logical live read+write traffic is 101,770,592,256 bytes, about 203.6 GB/s. Actual tracking masks were not retained, so physical tracked traffic is unknown. Under a conditional 273 GB/s streaming-bandwidth assumption, even zero-cost tracking plus that live-copy roofline would save only about 1.64% of the historical span. This is not a hardware traffic-counter bound, cache-aware proof or universal limit on a layout/fusion rewrite.

We therefore rejected tile-only tuning without running serving/quality gates. The evidence distinguishes a bandwidth-heavy live-state path from launch/tracking consolidation; it does **not** reject the architectural work in this PR. The newer upstream verify scratch-row mapping is absent from this old image, so any current-main port also needs that correctness contract preserved. No claimed end-to-end gain or regression bound follows from this screen.
