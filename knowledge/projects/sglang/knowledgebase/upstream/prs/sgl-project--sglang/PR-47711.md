# [Fix] multi-tokenizer: Record an abort that arrives before any worker holds the rid

[Upstream PR](https://github.com/sgl-project/sglang/pull/47711) · state: open · merged: False

## Original PR description

> **Stacked on #47693.** Until it merges, the diff here also shows its commit
> (`multi-tokenizer: Broadcast a non-owner's abort to the owning worker`); please review
> the two commits of this PR. I will rebase onto main once #47693 lands.

## Motivation

Second follow-up to #47546, on top of #47693. The broadcast of #47693 reaches the owning
worker only after it has registered the rid. Under an abort storm with congested workers
the owner can enter `generate_request` seconds after the abort arrived — we measured the
abort preceding scheduler admission by p50 0.1 s / p90 1.3 s / max 26 s on a production
1P1D decode with tens of tokenizer workers. The broadcast then finds no owner, the
scheduler drops the forwarded abort, and the request runs unaborted; on a PD decode
server its preallocated KV is held until the transfer timeout. In our incident replay,
3,402 such rids (of 75,210) leaked enough transfers to fill the decode KV pool: the
deployment stopped serving and did not recover while idle.

## Modifications

Commit 1 — `MultiTokenizerRouter` keeps a pending-abort table for forwarded aborts:

- record before broadcasting (a claim racing back must find the entry); rebroadcast at
  1 s / 3 s / 8 s while unclaimed — the owner registers on entering `generate_request`,
  well before its dispatch, so rebroadcasts cover the registration lag without a new
  false-abort class;
- any abort from a worker that holds the rid (`forward=False`) claims the entry, and the
  broadcast handler sends that claim even when `abort_sent` already deduplicates the
  local abort;
- any output for the rid clears the entry;
- a recorded rid's generate passing the router is forwarded and then aborted with a
  follow-up `AbortReq` on the same socket (refire, one-shot) — the scheduler takes it
  through its normal queued-abort path and the echo routes back by the generate's
  `http_worker_ipc`;
- entries expire after 30 s (must outlive abort → generate-passes-router, measured up to
  26 s); expiry falls back to today's behavior, so the TTL is a benefit knob, not a
  correctness one. The router logs a periodic counters summary.

Commit 2 — the single-tokenizer analog: an abort for an unregistered rid used to be a
silent no-op; `abort_request` now records it for 30 s and registration consumes the
record, marking the state `abort_sent` so the #47546 skip-dispatch path finishes it.

Scope notes: refire covers `TokenizedGenerateReqInput` and its batch; embedding requests
fall back to expiry (they hold no PD KV). A late abort killing a reused rid exists today
at millisecond scale; the table widens that window to its TTL for rids nobody held, and
the one-shot entry, the claim and the output-clear paths bound it to at most one wasted
retry.

## Validation on the incident workload

Replaying the same 8,132-request production window against a 1P1D test deployment
(decode: 32 tokenizer workers, DP8):

| | #47693 only | + this PR |
|---|---|---|
| successful requests | 1,075 | 4,697 |
| served after the storm minute | 0 (wedged) | every minute, 86–96% cache hit |
| decode transfer/prealloc residue per rank | 18–31 / 202–244 | 0 / 0 |
| prefill bootstrap timeouts | 4,658 | 20 |
| recovery when idle | none (perpetual 429) | first probe 200 in 0.55 s |

Router counters over the run satisfied `recorded = claimed + refired + expired` exactly
(97,799 = 35,198 + 21,141 + 41,460); the 41k expired entries were attempts the gateway
tore down before their decode-side generate completed (they hold no KV).
