# [CI] [NVIDIA] gb300: Run DSV4.1-Flash tests on 2 GPUs with engram host tables

[Upstream PR](https://github.com/sgl-project/sglang/pull/45294) · state: closed · merged: True

## Original PR description

Moves the DeepSeek-V4.1-Flash GB300 tests onto half a GB300 node, so each node can be split into two 2-GPU runners.

## Why

GB300 per-PR testing (base-c) is backed up. There are only two `4-gpu-gb300` runners, and the four `test_deepseek_v41_flash_gb300_*` tests make up about 2,400 of the stage's ~2,680 seconds of estimated test time. Each test loads the 510 GB model at TP4. Splitting each node into two 2-GPU runners would double the slots, but DeepSeek-V4.1-Flash barely fits on 2 GPUs:

| | per GB300 GPU (277.5 GiB usable, from `nvidia-smi` on our runners) |
|---|---|
| DSV4.1-Flash weights at TP2 | ~237 GiB, leaving ~40 GiB |
| ...of which the engram tables (2 × ~384M rows × 264 B, FP8 + scales) | ~94 GiB (~189 GiB in total) |
| **TP2 with engram tables in host memory** | **~143 GiB of weights, ~134 GiB headroom** |

`SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE` keeps the engram tables in host memory (pinned, `cudaHostRegister`) and gathers the rows each step needs over NVLink-C2C, instead of splitting the tables across HBM. GB300 nodes have 955 GiB of host RAM, so two runners per node would use about 378 GiB for the tables.

## What

- **`python/sglang/test/dsv41_flash_common.py`:** `--tp 2`, the engram host table turned on through the recipe's existing `server_env` hook, and `TP4_EP4_ARGS` → `TP2_EP2_ARGS`.
- **The four `test_deepseek_v41_flash_gb300_*` tests:** `runner_config="2-gpu-gb300"`, and EP / DP-attention sizes 4 → 2. `…_tp4ep4.py` / `…_dp4ep4.py` and their classes are renamed to `…_tp2ep2.py` / `…_dp2ep2.py` (`TestDSV41FlashTP2EP2DSpark`, `TestDSV41FlashDP2EP2DSpark`).
- **New `2-gpu-gb300` runner config** (`scripts/ci/runner_configs.yml`), a row in the base-c aarch64 matrix (`.github/workflows/pr-test.yml`), and the suite name in `test/run_suite.py`.
- `compute_partitions.py` locally gives `base-c-test-2-gpu-gb300` 2 shards (the 4 DSV4.1 tests) and leaves `base-c-test-4-gpu-gb300` 1 shard (disaggregation, CUDA-VMM transport, NUMA). Those stay on 4 GPUs.

## Not done yet

- **No runner has the `2-gpu-gb300` label**, so the new base-c rows will queue until one does. To try this without splitting a node, a GB300 runner can temporarily carry the `2-gpu-gb300` label: the tests run at TP2 on GPUs 0–1 of a 4-GPU runner, which is enough to check memory and accuracy.
- **What the tests cover changes:** TP2 / EP2 / DP-attention 2 with host-memory engram tables, instead of TP4 / EP4 / DP4 with tables in HBM. The test owners should decide whether that's acceptable for base-c, or whether some TP4 coverage should stay (e.g. in nightly).
- **Timing:** engram rows come over NVLink-C2C instead of HBM, so per-test runtime may change. Compare against the current ~600 s per test.
- Memory numbers are calculated from the model config and `layers/engram.py`, not measured.

### Validated on the new 2-GPU GB300 runners

I split one 4-GPU GB300 runner (CoreWeave node `s3ptq4n4`) into two 2-GPU runners, then ran this PR's four DSV4.1-Flash tests on **both runners at the same time**, at this PR's head (`28eb455`).

**What was done**
- Drained and deregistered `gb300-s3ptq4n4` (4-GPU), then deleted its pod. `gb300-shhq3nb4` keeps `4-gpu-gb300` and was not touched.
- Created two pods on `s3ptq4n4` from the same manifest with `nvidia.com/gpu: 2` each. Each pod sees exactly 2 distinct GB300s.
- Registered them as `gb300-s3ptq4n4-a` and `gb300-s3ptq4n4-b` (runner 2.338.0, ARM64). After the runs below passed, both got the `2-gpu-gb300` label.
- Downloaded `deepseek-ai/DeepSeek-V4.1-Flash` (476 GB) and `MMMU/MMMU_Pro` into each pod's local cache before the tests. Each took about 2.5 min.

**Results:** all passed. Each test runs 2 cases (GSM8K, MMMU-Pro).

| Test (run order) | `gb300-s3ptq4n4-a` | `gb300-s3ptq4n4-b` |
|---|---|---|
| `tp2ep2` | ✅ 1399 s | ✅ 1409 s |
| `dp2ep2` | ✅ 701 s | ✅ 718 s |
| `encoder_bcg` | ✅ 669 s | ✅ 681 s |
| `trtllm_bounded_bcg` | ✅ 572 s | ✅ 588 s |
| Job | [run 39699970988](https://github.com/sgl-project/sglang/actions/runs/39699970988/job/119566671158) | [run 39699973756](https://github.com/sgl-project/sglang/actions/runs/39699973756/job/119566697917) |

- The first test is slow because the pods were fresh and kernel compile caches were cold. With warm caches, tests take 9.5–12 min, close to `est_time=600`.
- **Engram host tables work as intended.** Node shared memory rose by about 189 GiB per server (18 → 396 GiB with both servers up), and each GPU held about 168 GB.
- **Two runners on one node have enough host RAM.** With both DSV4.1 servers running, peak node usage was 567 / 955 GiB, and at least 387 GiB stayed available.

**Notes**
- #45313 touches the `encoder_bcg` and `trtllm_bounded_bcg` test files, which this PR also changes, so whichever merges second needs a rebase.
- After `4-gpu-gb300` is retired, `shhq3nb4` can be split the same way.
