# [Perf] dsv4: Keep V4.1 image rows inside the Engram gate kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/45904) · state: closed · merged: True

## Original PR description

- After each Engram layer, DeepSeek-V4.1 put the pre-Engram residual back on image-token rows with a separate full-width `torch.where` over the residual stream. It ran on every forward, including text-only batches where it selected nothing, and allocated a second residual-sized output.
- The Engram gate kernel now takes the layer's input ids and the image token id, and stores the unchanged residual for image rows in the same pass. The `torch.where` and its extra output are gone.
- `Engram` now takes `image_token_id`, as `EngramHasher` already does. It is set only for V4.1 checkpoints with a vision tower, and both read it from one helper, `_engram_image_token_id`. Other models pass no ids and run the kernel unchanged.
- The ids are the model's prepared input ids (multimodal pad ids already mapped to the image token id), the same tensor the old select read. Under the breakable prefill graph, the kernel reads them from the captured buffer at replay.
- The torch fallback path applies the same select after its gate.

Output is bitwise identical to before, for text rows and image rows, in eager mode and in graph replay.

Verification:
- The fused kernel matches the old gate + `torch.where` bit for bit. This covers several batch sizes, bf16 and fp32 activations and weights, int32 and int64 ids, and no, some, or all image rows. A captured CUDA graph reads the live ids at replay.
- A micro benchmark with DeepSeek-V4.1-Flash shapes on B300 and GB300 shows the fused kernel well ahead of the old gate + select at every prefill size tested, with and without image rows.
