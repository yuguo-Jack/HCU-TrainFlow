# [Fix] [NVIDIA] kvcache: Gate fused FP8 prefix-valid commit kernel on SM89+

[Upstream PR](https://github.com/sgl-project/sglang/pull/45488) · state: open · merged: False

## Original PR description

Motivation

set_kv_buffer_prefix_valid_tiled_fp8 (added by #40785) fuses FP8 KV-cache quantization into the prefix-valid commit kernel used by DFLASH speculative decoding. It compiles fp8e4nv inside a Triton kernel, which only works on SM89+ (Ada / Hopper). On SM86 (Ampere, e.g. RTX 3090) the Triton codegen rejects fp8e4nv:


ValueError: type fp8e4nv not supported in this architecture.
The supported fp8 dtypes are ('fp8e4b15', 'fp8e5').


The dispatch in MHATokenToKVPool.set_kv_buffer_prefix_valid only checks the KV cache dtype and the resolved K/V scales — it does not inspect the compute capability — so an SM86 box is sent straight into the fused kernel and crashes on startup. The pre-#40785 eager path (PyTorch-layer quantization + the generic byte-copy Triton kernel) is left untouched below the fused branch, so the fix is to fall back to it on pre-SM89 GPUs.

This is the prefix-valid writer specifically. #31652 gates the ordinary set_kv_buffer FP8 stores on SM89+ but leaves the prefix-valid dispatch ungated, and #42982 (SM89 NaN-saturation) does not add a capability guard either.

Modifications

- Add a module-level _FP8_FUSED_OK that is True only on CUDA SM89+ (torch.cuda.get_device_capability() >= (8, 9)).
- Add and _FP8_FUSED_OK to the fused-branch condition in MHATokenToKVPool.set_kv_buffer_prefix_valid, so pre-SM89 GPUs take the existing eager-quantization fallback (the pre-#40785 path) instead of the fused fp8e4nv kernel.

SM89+ keeps the fused fast path unchanged; SM86 / SM80 and other pre-SM89 arches fall back to eager quantization, which is exactly what worked before #40785.

Accuracy Tests

No numeric change. The eager fallback's overflow policy (saturate_to_fp8_range) already matches the fused kernel (aligned in #42982), so for in-range inputs both paths write identical KV bytes. SM89+ is untouched (still the fused kernel). SM86 now takes the same eager path it used before #40785, so behavior matches the pre-#40785 reference. A per-arch capability gate cannot be unit-tested without hardware of each arch; validated on-die on dual RTX 3090 (SM86) and reviewed against the SM89+ fused path.

Speed Tests and Profiling

No speed impact on SM89+ (the fused kernel is taken exactly as before). On SM86 the fallback adds the two eager quantization launches plus a cast per layer — this is the pre-#40785 cost, and it is the only path that compiles on SM86 (the fused kernel cannot be built there), so there is no regression relative to a working SM86 baseline.

- michaelzhang-ai · CHANGES_REQUESTED · 2026-10-26T16:59:25Z · [source](https://github.com/sgl-project/sglang/pull/45488#pullrequestreview-5655902139)

Thanks, the diagnosis is right: Triton only lowers `fp8e4nv` on SM89+, and the prefix-valid dispatch is the one FP8 store path that isn't gated. Two problems with the gate as written:

1. `_is_cuda and ...` also disables the fused path on ROCm. This dispatch is reachable on HIP (the guard above is `_is_cuda or _is_hip`), and the fused kernel runs there with the fnuz/OCP fp8 types. The `saturate_to_fp8_range` docstring relies on that. With this change, MI300/MI355 would silently drop to the eager fallback.
2. Calling `torch.cuda.get_device_capability()` at module scope initializes CUDA at import time, which breaks fork-based startup (see the comment in `get_device_sm()`).

Evaluating it lazily fixes both:

```python
@lru_cache(maxsize=1)
def _fp8_fused_prefix_valid_supported() -> bool:
    # Triton lowers fp8e4nv only on SM89+; ROCm fp8 types are unaffected.
    return _is_hip or get_device_sm() >= 89
```

and `and _fp8_fused_prefix_valid_supported()` in the dispatch condition. By the time this runs, the pool is already on the device, so the check costs nothing after the first call.
