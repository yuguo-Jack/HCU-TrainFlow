# [diffusion] Share Qwen-Image 2.1 prefix KV across outputs of one prompt

[Upstream PR](https://github.com/sgl-project/sglang/pull/40489) · state: closed · merged: False

## Original PR description

## Motivation

Qwen-Image 2.1 prefills the condition prefix (text + reference-image latents) once per request and reuses its per-layer KV for every denoising step. With `num_outputs_per_prompt = n`, the encoding stage gives each output its own cache even though all `n` outputs of a prompt share the same encoder hidden states, layout and condition latents. The prefix is therefore prefilled `n` times and its KV is stored `n` times. The prefix is read-only after prefill, so the copies are redundant.

## Modifications

- `QwenImage21EncodingStage` builds one cache per prompt and hands the same object to every output of that prompt. Different prompts and the two guidance branches keep separate caches.
- `QwenImage21Transformer2DModel.forward` lets the first sample holding an empty cache prefill it; later samples holding the same cache skip the text projection and per-block prefix work and read the populated KV.
- Cookbook sentence on multi-output caches updated.

Scope: this only applies where one request keeps `n` outputs together, i.e. the HTTP image endpoints. Offline `sglang generate` expands `n` outputs into `n` single-output requests before the pipeline, so it is unaffected (measured: identical memory and latency). Requests crossing the disaggregation boundary rebuild independent caches, because the extras codec does not preserve object identity; that keeps today's behavior.

## Accuracy Tests

- New tests fail on main's implementation (3 failed) and pass here (3 passed); `test_qwen_image21.py` + `test_qwen_image21_cuda.py` pass in full (41 passed). The CUDA test asserts bitwise-equal output and KV versus independent caches and one prefill instead of two. pre-commit passes.
- Full checkpoint, `/v1/images/edits`, 1024x1024, 40 steps, seed 42, n in {1,2,4}, CFG off and CFG 4: all 14 output images are pixel-identical to main (max abs diff 0) on RTX PRO 6000; the same holds for the 10 images of the 5 configs main can run on RTX 5090, and for the same 10 on RTX 4090.

## Speed Tests and Profiling

Protocol for every row: `/v1/images/edits`, one 1024x1024 reference image, 1024x1024 output, 40 steps, seed 42, fresh `sglang serve` per config, one warm request, peaks from `perf_dump_path` (`runtime_peak`, which is cumulative over the server's life and so includes the warm request of the same config). CFG rows use guidance 4 with a negative prompt. Latency is quoted per card; the cards are not comparable with each other.

Which stage owns the request peak depends on where the DiT lives during decode, so the effect differs by deployment.

**RTX 5090 32 GB, default flags** (auto policy: encoders and VAE layerwise-offloaded, `dit_cpu_offload`, so the DiT is off the GPU during decode and denoising is the peak). Two timed requests.

| config | peak allocated main -> here (MB) | latency main -> here (s) |
|---|---|---|
| CFG off, n=1 | 17653 -> 17653 | 16.86 / 16.94 -> 16.72 / 16.79 |
| CFG off, n=2 | 20256 -> 18068 | 32.78 / 32.59 -> 32.09 / 32.22 |
| CFG off, n=4 | 25469 -> 18967 | 65.27 / 65.37 -> 64.24 / 64.35 |
| CFG 4, n=1 | 19713 -> 19713 | 32.73 / 32.83 -> 32.75 / 32.84 |
| CFG 4, n=2 | 24374 -> 20129 | 63.85 / 63.99 -> 63.18 / 63.28 |
| CFG 4, n=4 | **OOM** -> 21030 | - -> 126.80 / 126.94 |

main fails in the first denoising step: `Tried to allocate 384.00 MiB ... 26.89 GiB is allocated by PyTorch`, capacity 31.36 GiB. `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` does not remove it: main fails the same way with 28.14 GiB allocated and 1.21 GiB reserved but unallocated. These runs do not separate a pure capacity shortage from a residual allocation limit. A per-stage probe on main confirms denoising is the request peak on this card (17653 / 20255 / 25467 MB for n=1/2/4, against 16311 MB for conditioning and 4850 / 8023 / 14371 MB for decode).

**RTX 4090 24 GB, cookbook multi-output recipe** (`--performance-mode manual --dit-layerwise-offload true --text-encoder-cpu-offload true`, FlashAttention). One timed request.

| config | main | here |
|---|---|---|
| CFG off, n=1 / 2 / 4 latency (s) | 25.35 / 48.55 / 96.33 | 25.35 / 48.01 / 94.35 |
| CFG 4, n=1 / 2 latency (s) | 49.85 / 96.20 | 49.82 / 95.69 |
| CFG 4, n=4 | **OOM** | 187.11 s |

Recorded peak allocated is 18650-18669 MB in every successful config on both sides. A per-stage probe on main shows why: the conditioning stage peaks at 18650 MB for every n, above denoising (4397 / 7000 / 12211 MB for n=1/2/4) and decode (4094 / 7267 / 13615 MB).

main's OOM is again in the first denoising step, with `16.70 GiB allocated ... 5.48 GiB reserved but unallocated` of 23.52 GiB. This one is an allocator-fragmentation failure, not a capacity limit: with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` main completes the same request (189.63 s). This change avoids it under the default allocator by keeping the denoising footprint smaller. On the RTX 5090 that setting did not help, as noted above.

**RTX PRO 6000 96 GB, default flags** (everything resident, so the batched VAE decode is the peak without CFG). Two timed requests.

| config | peak allocated main -> here (MB) | peak reserved main -> here (MB) | latency main -> here (s) |
|---|---|---|---|
| CFG off, n=2 | 22002 -> 22002 | 31216 -> 28720 | 18.93 / 19.07 -> 18.77 / 18.84 |
| CFG off, n=4 | 28352 -> 28352 | 46510 -> 39470 | 37.97 / 38.25 -> 37.34 / 37.61 |
| CFG 4, n=2 | 25019 -> 22002 | 36402 -> 31410 | 37.53 / 37.77 -> 37.06 / 37.32 |
| CFG 4, n=4 | 34346 -> 28353 | 55746 -> 41776 | 75.24 / 75.45 -> 74.13 / 74.21 |

n=1 is unchanged everywhere. On this card the allocated peak only drops under CFG; without CFG the decode peak (about 3.17 GB per output) hides it. Decoding one sample at a time (#40493) removes that peak there: n=4 goes 28352 -> 19613 MB (CFG off) and 34346 -> 21677 MB (CFG 4) with both changes, versus 26115 / 34346 with #40493 alone.

In these samples end-to-end latency for n>1 was 0.5-2.1% lower with this change (two timed requests per config on RTX PRO 6000 and RTX 5090, one on RTX 4090; variants were run in a fixed order, not interleaved). Skipping the repeated prefills is the expected source, but prefill time was not measured separately.
