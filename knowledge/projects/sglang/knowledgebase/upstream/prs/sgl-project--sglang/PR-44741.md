# [Perf] logprob: Keep input top-k and token-ids logprobs off the host sync path

[Upstream PR](https://github.com/sgl-project/sglang/pull/44741) · state: open · merged: False

## Original PR description

## Motivation

Input top-k and token-ids logprobs (`return_logprob` with `logprob_start_len >= 0` plus `top_logprobs_num` or `token_ids_logprob`) blocked the overlap scheduler on the in-flight forward once per prefill (and per logprob chunk):

- **Top-k:** results only went through async pinned copies when graph-pool borrowing was on (off by default). Otherwise they were read back with `.tolist()`.
- **Token-ids:** the GPU logprobs were indexed with a Python list, an implicit synchronous H2D copy.

This affects `/v1/completions` with `echo` + `logprobs`, `/generate` prompt scoring, and setwise scoring in the Score API.

## Modifications

- `layers/logprob_processor.py`: on CUDA, top-k / token-ids results always leave the device as async pinned copies with a copy-done event; borrowing now only decides where the scratch memory lives. The token-ids index is staged through `async_h2d`.
- `finalize_input_logprobs()` already converts the pinned spans before every consumer reads them (prefill, disagg prefill, PP). Multi-item scoring and non-CUDA devices are unchanged.
- `test_logprob_fast_input.py`: the test helper finalizes results the way the scheduler does.

## Accuracy Tests

Values are computed exactly as before; only the D2H transport changes.

- `test_logprob_fast_input.py` + `test_logprob_chunk_stitching.py`: 16 passed on H200.
- `test/registered/core/test_srt_endpoint.py`: 20 passed, including all logprob tests.

## Speed Tests and Profiling

Qwen3-0.6B, 1x H200, TP=1 bf16 with default flags, `main` vs this PR. 64 concurrent `/generate` requests with random prompts, `logprob_start_len=0`, 1 output token. Fresh server per run; two rounds each, numbers are the mean.

| Workload | Before (req/s) | After (req/s) | Change | p50 latency |
|---|---|---|---|---|
| top-k=5, 1024-token prompt | 166 | 252 | +52% | 385 -> 252 ms |
| top-k=5, 256-token prompt | 571 | 744 | +30% | 111 -> 85 ms |
| token-ids (10 ids), 1024-token prompt | 187 | 236 | +26% | 342 -> 270 ms |
| token-ids (10 ids), 256-token prompt | 602 | 685 | +14% | 106 -> 93 ms |
| no logprobs (control) | 1683 | 1671 | ~0 | - |

With 256-token decode traffic sharing the server, top-k scoring throughput goes from 525 to 683 req/s (+30%).

The gain grows with prompt length (the removed `.tolist()` covered every prompt position) and is largest when the forward is short.
