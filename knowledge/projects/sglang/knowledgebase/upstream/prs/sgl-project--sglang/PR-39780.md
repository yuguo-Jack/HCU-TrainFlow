# [Fix] dpsk-v4: c128 online prefill plan IMA and EP scatter-1 bug

[Upstream PR](https://github.com/sgl-project/sglang/pull/39780) · state: open · merged: False

## Original PR description

## Motivation

Two intermittent memory-safety bugs, both reachable only under production-shaped load.

### 1. Online-compress c128 prefill plan: the plan builder is captured inside the decode CUDA graph

`CompressorPrefillPlan.generate_online` fills a pinned host staging buffer, and the C++ plan builder then issues a raw `cudaMemcpyAsync` out of it.

On the decode side, the speculative-decoding target-verify path builds this plan **inside the decode CUDA graph**. That raw H2D copy is therefore captured as a graph node with the *host pointer* baked in. The staging buffer was allocated per call with `torch.empty(..., pin_memory=True)` and freed as soon as the plan was dropped, so every replay re-read freed — and possibly reused — host memory and handed it to stage 1 as the plan: `read_page_0` lands outside `[0, batch_size)` and indexes `req_pool_indices` out of bounds → CUDA IMA.

The out-of-range read is only the visible part: in-range entries carry another allocation's bytes too, so even when it does not fault the plan is wrong — which is why the spec accept rate was depressed (see Accuracy Tests below).

Notes for reviewers:

- The prefill path already refuses to build the online c128 plan in prefill cuda-graph mode (`init_forward_metadata_prefill`: *"Online c128 uses a different planner that cannot be created in prefill cuda-graph mode"*). The target-verify path reaches `create_paged_compressor_data` directly and was missing that rule.
- We first tried enforcing that rule there (`use_prefill_cuda_graph=False`), but it breaks the decode graph runner: `replay_cuda_graph_metadata_from` does `chosen_metadata.copy_(temp_metadata)` and the plan shapes no longer match (`[1, 16]` vs `[0, 16]`). The padding is required for shape stability, so the fix keeps the capture and makes the host buffer persistent instead.
- Forcing a synchronous H2D (`SGLANG_DEBUG_C128_ONLINE_SYNC_H2D=1`, verified active in the server process) does **not** suppress it: the capture is independent of the copy's sync-ness; the replay re-reads the baked-in host pointer either way.

### 2. EP scatter-1 kernel: cross-warp offset read-back

`_fwd_kernel_ep_scatter_1` finalized each expert's offset by having every program store the whole prefix-sum array to `expert_start_loc` and then read its own slot back. That read-back depends on the visibility of a vector store issued across the block's warps, so a program could observe a stale value, compute a garbage base pointer, and fault in the `m_indices` store loop.

## Reproduction

DeepSeek-V4-Flash, PD disaggregation, `SGLANG_OPT_USE_ONLINE_COMPRESS=1` + `SGLANG_EXPERIMENTAL_ONLINE_C128_MTP=1`, multi-turn, long context.

- Bug 2: crash at ~25 min, hundreds of `DeepGEMM grid sync timeout` asserts, `Xid 31 MMU Fault (ACCESS_TYPE_VIRT_READ)`, then `CUDA error: unspecified launch failure`.
- Bug 1: the decode side died with `CUDA error: unspecified launch failure` in **4 of 5 runs** (within 2-11 min). Instrumenting the plan bounds check logged entries whose four `CompressPlan` fields were four consecutive int32 of an unrelated array, e.g. `seq_len=54775 ragged=54776 read_page_0=54777 read_page_1=54778` — i.e. the staging buffer held foreign bytes.

## Modifications

- `python/sglang/kernels/ops/attention/dsv4/compress.py`: keep the online c128 prefill staging buffer per `(device, num_q_tokens)` when the plan is built for cuda-graph use, so the pointer captured in the graph stays valid; stage 0 refills it each forward. The eager path still allocates per call, so the cache stays bounded by the graph's bucket count.
- `python/sglang/kernels/jit/csrc/deepseek_v4/c128_online_v2.cuh`: the `num_batch` bounds check now fails loudly (`printf` + `__trap()`, HIP `__builtin_trap()` fallback) instead of writing `CompressPlan::invalid()`, which would silently drop the chunk and turn this into an accuracy regression.
- `python/sglang/kernels/ops/moe/ep_moe_kernels.py`: each program selects its own offset from the in-register `cumsum` (`tl.sum(tl.where(offset_cumsum == cur_expert, cumsum, 0))`), removing the cross-warp read-back. The `m_indices` tail mask is kept as hardening — all current callers pad the per-expert counts to `BLOCK_E`, so the partial tail block is not reachable — and the launcher/kernel comments are reworded accordingly.
- `test/registered/kernels/ops/moe/test_ep_scatter_1.py` (moved from `test/manual/`): unit tests for `_fwd_kernel_ep_scatter_1`, registered for `base-b-kernel-unit` on 1 GPU.

## Accuracy Tests

Neither change alters numerics: the plan change only affects host memory lifetime, and `expert_start_loc` still holds the same exclusive prefix sum, now computed in-register.

Indirectly, the fix removes silent wrongness. On the same config the decode-side spec accept rate goes from `[0.69, 0.39, 0.26]` (plan captured, stale) to `[0.73, 0.42, 0.28]`.

## Speed Tests and Profiling

No measurable cost: keeping the staging buffer alive removes a per-call pinned allocation on the captured path, and the plan is still built at the same point. Same config: **79.95 req/s** with the fix vs **78.94 / 79.01 req/s** in clean pre-fix runs.

- yhyang201 · comment · 2026-10-12T14:30:47Z · [source](https://github.com/sgl-project/sglang/pull/39780#issuecomment-6126336757)

Thanks for tracking these down! A couple of thoughts:

**1. Bounds guard in `plan_c128_online_prefill_kernel`**

I'm not sure the out-of-range `batch_id` can come from stage 0 itself. `_plan_prefill_partial` always writes `i < batch_size`, and `seq_lens` / `extend_lens` / `req_pool_indices` share the same `B` in the `TensorMatcher` checks. So if stage 1 sees an out-of-range value, the device-side plan probably wasn't produced by this call's stage 0.

One possible cause is the pinned staging buffer. `generate_online` allocates `pin_buffer` with `torch.empty(..., pin_memory=True)` on every call. The H2D copy, however, is a raw `cudaMemcpyAsync` in C++, so PyTorch's caching host allocator doesn't record an event for it. Once the plan object is released, the pinned block can be handed to the next batch. That batch's stage 0 can then overwrite it before the previous copy has actually run. This is easier to hit with the overlap scheduler, since the CPU runs one batch ahead.

If that's what is happening, the out-of-range entries are only the visible part. The in-range entries would also carry another batch's `seq_len` / `ragged_id` / slots. Turning them into `invalid()` would make the downstream kernels silently skip those chunks, so the crash would become an accuracy issue.

Could you try reproducing with `SGLANG_DEBUG_C128_ONLINE_SYNC_H2D=1`? If the IMA goes away, that would confirm it. A fix could then be one of these:
- Do the H2D on the Python side with `plan_c_dev.copy_(plan_c_pin, non_blocking=True)` (and the same for `plan_w`), so the host allocator tracks the pinned buffer.
- Keep `pin_buffer` alive until the copy has finished, e.g. by recording a CUDA event after it.

The guard itself might work better as a device-side assert than as a silent `invalid()`.

**2. Tail mask in `_fwd_kernel_ep_scatter_1`**

As far as I can tell, all current callers pad the per-expert counts to a multiple of `BLOCK_E`:
- `pad_expert_counts` in `deep_gemm.py`
- DeepEP with `expert_alignment=128`
- `counts_aligned` in `deep_gemm_sm120.py`

The launcher comment around L1171 also relies on this alignment. So the tail overrun shouldn't be reachable in practice. The mask is fine to keep as hardening, but could you reword the description so it isn't presented as a cause of the IMA, and update that launcher comment as well?

Thanks for the careful read — you were right that the out-of-range `batch_id` cannot come from this call's stage 0, and that the pinned staging buffer is the place to look. The mechanism turned out to be a bit different from the two options you listed, so here is what we found.

**Root cause.** The plan builder issues a raw `cudaMemcpyAsync` out of the pinned staging buffer, and on the decode side the spec target-verify path builds this plan **inside the decode CUDA graph**. That copy is therefore captured as a graph node with the *host pointer* baked in. `generate_online` allocated the buffer per call with `torch.empty(..., pin_memory=True)` and it is freed as soon as the plan is dropped, so every replay re-reads freed (and possibly reused) host memory and hands it to stage 1 as the plan.

Instrumenting the bounds check showed exactly that: entries whose four `CompressPlan` fields were four consecutive int32 of an unrelated array (`seq_len=54775 ragged=54776 read_page_0=54777 read_page_1=54778`), and the decode side died with `CUDA error: unspecified launch failure` in 4 of 5 runs.

This also explains why `SGLANG_DEBUG_C128_ONLINE_SYNC_H2D=1` does not suppress it — we verified the flag is active in the server process. The capture is independent of the copy's sync-ness; the replay re-reads the baked-in host pointer either way.

On your two suggestions: (b) holding the buffer until the copy has finished is not enough — it has to live as long as the *graph*, not just the capture-time copy. And (a) doing the H2D from Python with `copy_` has the same problem, since the copy is still inside the captured region.

We also tried the obvious alternative — enforcing the existing "cannot be created in prefill cuda-graph mode" rule on the target-verify path (`use_prefill_cuda_graph=False`) — but that breaks the decode graph runner: `replay_cuda_graph_metadata_from` does `chosen_metadata.copy_(temp_metadata)` and the plan shapes no longer match (`[1, 16]` vs `[0, 16]`).
