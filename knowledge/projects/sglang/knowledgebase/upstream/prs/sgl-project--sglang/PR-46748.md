# [Fix] rust-server: Serve decode_allocation_policy and enable_kv_cache_sharding from the bootstrap registry

[Upstream PR](https://github.com/sgl-project/sglang/pull/46748) · state: open · merged: False

## Original PR description

## Summary

The Rust `/route` bootstrap registry (`rust/sglang-server`, `SGLANG_RUST_SERVER=1`) dropped two `PrefillServerInfo` keys that the Python decode consumes:

- `decode_allocation_policy`: decode compares it against its own policy in `CommonKVReceiver` and errors on mismatch.
- `enable_kv_cache_sharding`: decode branches on it when computing the transfer layout.

Decode builds `PrefillServerInfo(**data)` with dataclass defaults, so the missing keys silently read as `"early"` / `False`. Today that affects the two keys differently:

- **`enable_kv_cache_sharding` is a live bug.** Nothing stops a Rust-server prefill from running with `--enable-kv-cache-sharding`. Decode then reads `False` and computes its transfer layout as if the prefill weren't sharded.
- **`decode_allocation_policy` is groundwork.** `_validate_prefill_complete` currently refuses `prefill_complete` under `SGLANG_RUST_SERVER` ("does not yet support the Rust bootstrap registry"). With the default `early` on both sides, the missing key reads correctly. The registry needs to serve it before that guard can go; without it, decode would raise a false policy mismatch.

This ports the Python `CommonKVBootstrapServer` semantics:

- PUT parses both keys; the policy defaults to `"early"`.
- A disagreeing policy after the first registration gets the same 400 `Inconsistent prefill allocation policies`, checked after the dsv41 layout gate as Python does. A rejected PUT stores nothing.
- `enable_kv_cache_sharding` is first-wins.
- The `-1` sentinel GET serves both keys.

Split out of #46745.
