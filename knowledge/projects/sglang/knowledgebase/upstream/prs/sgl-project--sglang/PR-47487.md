# [Feat] rust-server: Keep a /generate request abortable while an HTTP layer prepares it

[Upstream PR](https://github.com/sgl-project/sglang/pull/47487) · state: closed · merged: False

## Original PR description

Stacked on #47321 (`oss-sync-7ef70da4f4`). This change builds on the `AbortEnding` / `Cancellation` rework that #47321 introduces, so it is based on that pull request's branch. Review only the top commit.

## Motivation

An `HttpLayer` (the hook an extension package uses to wrap the Rust frontend's axum app) can do work on a `/generate` request before the handler runs, for example waiting on a remote dependency for the request's inputs. A rid enters the core's cancellation registry only when `/generate` calls `CoreHandle::generate`. So an `/abort_request`, an `abort_all`, or a gRPC `Abort` that arrives during that work matches nothing, and the request runs anyway once the work finishes.

## Modifications

- `abortable_before_generate(extensions, rid, work)` (new public API, `http/pre_generate.rs`): registers `rid` in the cancellation registry while the layer's `work` runs, and races the work against an explicit cancellation.
  - When an abort wins, it returns at once with `Aborted { ending, abort_all }`. The layer may answer the request itself or pass it on. If it passes the request on, `/generate` ends it the way the abort says, without submitting it: an abort finish reason for `/abort_request`, or 499 for the gRPC `Abort`.
  - When the work finishes, the registration passes to `/generate` as a request extension, so an abort that lands between the layer and the handler ends the request the same way.
  - The request takes the held internal rid. An abort that has already detached the entry therefore still names the rid that is submitted.
  - A request that arrives under a different rid registers afresh, logs a warning, and keeps any cancellation the hold already saw.
  - Dropping the request before `/generate` unregisters it. Outside a server's app, `work` just runs.
- `handlers/generate.rs`:
  - `CoreHandle::hold_generation` and `generate_pending`, and the new `PendingGeneration` type (`claim`, `cancelled`).
  - A cancellation now also records whether it came from an abort of all generations.
  - `Generations::abort` is split into `detach` and `notify`.
  - `AbortEnding` becomes public, next to a new public `Aborted`.
- `http/app.rs`: the `HttpLayer` is applied through `pre_generate::apply`, which adds the core as a request extension.
- `http/native_api.rs`: a single (non-batch) `/generate` claims a held generation.
- `Cargo.toml` and `lib.rs`: a new `test-support` feature exports `test_support::pre_generate_app`, which lets an extension package test its layer without a running server. `lib.rs` also exports `AbortEnding`, `Aborted` and `abortable_before_generate`.

Scope: `/abort_request` on this frontend aborts only the listener's own generations; there is no cross-DP-listener abort forwarding. The tests therefore cover the client-facing abort paths only.

- `cargo test --locked -p sglang-server`: 436 passed in a run where the known flake below did not trigger, and in 3 of 3 runs with `--test-threads=1`. The new tests:
  - `pre_generate::tests::an_abort_before_generate_ends_the_request_unstarted`: covers a rid abort and `abort_all`, unary and streaming, and an abort during the layer's work or after it but before `/generate`. In each case the request ends on the abort output, nothing reaches the scheduler, and nothing stays registered.
  - `pre_generate::tests::a_held_request_runs_or_disconnects_cleanly`: a held request that is not aborted runs under its own rid, and a later abort still reaches it. A gRPC `Abort` during the work ends `/generate` with 499. A client disconnect during the work leaves nothing behind.
  - `generate::tests::a_claimed_hold_keeps_the_rid_a_detached_abort_names`: covers an abort that detaches the entry before the request is admitted, and the mismatched-rid case.
- `explicit_abort_during_batch_preprocessing_preserves_other_items` fails intermittently in full-suite runs on my machine: it timed out waiting for a media connection after 5 s.
