# [Perf] eplb: Fuse expert-count recording into one kernel on CUDA decode graphs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46497) · state: closed · merged: True

## Original PR description

## Motivation

With `--enable-eplb`, every decode step pays a fixed cost for expert-distribution recording and the logical-to-physical remap. That cost is large enough to cancel the balancing gain on a MegaMoE decode.

`_SelectExpertsSinglePassGatherer.on_select_experts` builds the per-layer count with about eight small elementwise ops: two compares, `&`, `~`, `masked_fill`, two dtype casts and `scatter_add_`. On CUDA the static remap is two more ops (index plus cast). `_on_hook` records whenever a stream is capturing, so all of these go into the decode CUDA graph and run on every replay, even after recording stops.

Measured on GB300, 40 MoE layers in one CUDA graph, 20-120 tokens per rank, extra time over no EPLB:

| path | extra time per forward |
| --- | --- |
| recorder hook only (MegaGate maps in-kernel) | +570 to +720 us |
| torch static remap + recorder hook | +763 to +1069 us |

On DeepSeek-V4.1-Flash DEP32 decode (6x DEP2 prefill, c3018 agentic), dynamic EPLB with 32 redundant experts gave no decode-step gain on an earlier nightly. The placement it computed was near-ideal: the busiest rank carried 1.03-1.07x the mean tokens, against 4.2x with the trivial placement. A matched-batch comparison showed +5.6% step time at 4 running requests per rank and -5.5% at 24: a fixed cost cancelling a load-proportional gain. A static placement computed offline from the same traffic, which runs no recorder, gives the gain.

`eplb_map_and_record_fused` already does the remap and the count in one Triton kernel. It is only reachable on the ROCm prefill-only MegaMoE path, and `get_current_pass_count_buffer` returns `None` during CUDA graph capture, because `_record_current_pass` is only set inside `with_forward_pass`.

## Modifications

- The kernel moves from `srt/eplb/eplb_map_record_fused.py` to `sglang/kernels/ops/moe/eplb_map_record.py` and is registered as `moe.eplb_map_and_record` and `moe.record_physical_counts`. Both entries take tensors only (the dispatch map instead of `ExpertLocationDispatchInfo`). Its GPU test moves to `test/registered/kernels/ops/moe/test_eplb_map_record.py`.
- `eplb_map_record.py`: add `WRITE_IDS` to the histogram kernel. Map+record and the new count-only `record_physical_counts(topk_ids, load_buffer)` share one launch helper. Inputs are made contiguous, since the kernel indexes them flat.
- `expert_location_dispatch.py`: `topk_ids_logical_to_physical_and_record` reads the static dispatch map from the dispatch info and calls the kernel; it returns `None` for non-static algorithms, which keep the torch remap.
- `expert_distribution.py`: `_SelectExpertsSinglePassGatherer.on_select_experts` uses the one-kernel histogram for GPU tensors (CUDA and ROCm) and keeps the torch path for other devices. This covers every recorder caller, including MegaGate's in-buffer path and DeepSeek-V4.1 VL routing. `get_current_pass_count_buffer()` now uses the same gate as `_on_hook` (`_disable_all`, the prefill-only pass check, recording or capturing) on every platform, and returns the recorder's current-layer row, the same row the hook writes. So the fused path is captured into decode graphs.
- `topk.py`: on CUDA, the routed-only branch of `_post_process_topk_ids` uses the fused map+record whenever the recorder exposes a buffer, then applies the usual padded-row mask and skips the separate recorder hook. The ROCm MegaMoE prefill path calls the same helper. All other branches are unchanged.

## Accuracy Tests

The checks below ran on the original revision (aea10915c0). The follow-up commits (kernel move, gate unification, guard removal) were checked by `test_eplb_map_record.py` on 1 GPU and the CPU unit tests at 1da0bdf5d8 only; the last four commits and the ROCm path were not run.

The counts are int32 and must match bitwise. Checked on 1 GPU (GB300) against the previous torch implementation:

- Histogram: 256 cases (T in {1, 7, 20, 60, 120, 144, 1024, 16384}, top-k {6, 8}, 384/416 physical experts, int32/int64 ids, -1 and out-of-range ids, non-contiguous inputs, non-zero initial buffer). 0 mismatches.
- Map + record against remap + padded mask + record: 320 cases (also 256/288 experts, `num_token_non_padded` None/full/T-3/0, padded rows holding -1 or live ids). Output ids and counts are identical in every case. A non-contiguous input gives a contiguous output with identical ids and counts.
- CUDA graph capture with recording started but no forward-pass context: the fused path is captured, and N replays give N times the eager counts. `disable_this_region` and eager-not-recording return `None`.
- Existing tests, identical on base and on this PR: `unit/eplb/test_megamoe_prefill_recorder.py`, `unit/eplb/test_dispatch_dtype_preservation.py`, `unit/layers/moe/test_topk_routing_inputs.py`, `unit/layers/moe/test_mega_moe_deepgemm_api.py`, `moe/test_hash_topk.py` (CPU), and `test_megamoe_prefill_recorder::test_fused_map_record_filters_padding` plus `moe/test_topk_padded_region.py` (GPU; 3 HIP-only skips).
- `torch.compile` bs=1 smoke, DeepSeek-V2-Lite-Chat TP2/EP2, `--enable-torch-compile --torch-compile-max-bs 1`, EPLB +4 rebalancing every 64 passes (about 1,065 rebalances), GSM8K 200 questions: this PR scores 0.045 at parallel 1 and 0.640 at parallel 32, against 0.045 and 0.655 on the base. The low bs=1 compiled score is already there without EPLB on the base (0.105), so it is unrelated to this change.
- `test/manual/test_expert_distribution.py`: 1 passed (5 subtests) on base and on this PR. `test/manual/ep/test_eplb.py`: 4 passed on base and on this PR.
- Server-level count check, DeepSeek-Coder-V2-Lite-Instruct, TP2 with attention DP2, flashinfer a2a + flashinfer_cutlass, +4 redundant experts from a skewed initial placement, static dispatch, stat recorder, decode in CUDA graphs. Traffic: 16 sequential greedy requests at batch size 1, then an 8-request burst (1,057 forward passes). In the same process, the old torch remap + mask + record ran on the same inputs at every call, including inside the captured graphs, and was compared on device: 0 count mismatches and 0 id mismatches over 27,690 fused calls on both ranks. Comparing separate server runs isn't bitwise reproducible even on the base (two base runs on different nodes differ by up to 35 per expert-layer, two runs of this PR by 12), and base against this PR (13) is within that.
- PD GSM8K, DeepSeek-V4.1-Flash, DEP4 decode with dynamic EPLB (+32 redundant, rebalance every 200 passes, 42 rebalances during the eval): 96.51% (1273/1319), against 96.82% for the same deployment without EPLB.

## Speed Tests and Profiling

Extra time over no EPLB per 40-layer forward, in a CUDA graph on GB300:

| T (tokens/rank) | torch remap + record | fused map + record | record only (MegaGate) | fused record only |
| --- | --- | --- | --- | --- |
| 20 | +763 us | +166 us | +570 us | +168 us |
| 60 | +900 us | +143 us | +638 us | +141 us |
| 120 | +1069 us | +146 us | +720 us | +143 us |

End-to-end, DeepSeek-V4.1-Flash, 6x DEP2 prefill + DEP32 decode, GB300, agentic c3018, 1800 s from a cold start:

| arm | decode step at matched batch | ITL p50 | ITL p90 | requests (1800 s) |
| --- | --- | --- | --- | --- |
| no EPLB | baseline | 3.53 ms | 3.97 ms | 176,486 |
| no EPLB, repeat | -0.3% | 3.53 ms | 3.91 ms | 173,033 |
| static placement from an offline recording, +32 | -8.7% | 3.18 ms | 3.54 ms | 174,478 |
| **dynamic EPLB +32, this PR** | **-6.8%** | **3.29 ms** | 3.83 ms | 169,837 |

The matched-batch step is the median step time at each per-rank running-request count, weighted over counts, from 600 s on. From 15 minutes in, dynamic gives -6.3% and static -8.2%.

Dynamic EPLB with this PR recovers about three quarters of the static placement's decode gain, with no offline recording. The remaining gap of about 2 points matches the roughly 0.15 ms per step the fused kernels still add, plus a few transient placements in the first rebalances (1.24-1.47x busiest/mean, settling to 1.04-1.06x).

End-to-end request throughput is not better than the no-EPLB control: 3.8% lower here (the control repeat was 2.0% lower than the control), and below the static arm. TTFT p90 is also higher (24.1 s against 14-21 s). The cause is the blocking rebalance itself: about 20 s for the first one and about 0.57 s for each of the 16 that follow. This PR does not change that; #43754 (stop rebalancing after K rebalances) and #45282 (non-blocking rebalance) address it.

**Issue**

This PR makes `record_physical_counts_fused` and `eplb_map_and_record_fused` the default CUDA recording path, but no CI test runs them. `test_fused_map_record_filters_padding` is in a file registered only with `register_cpu_ci`, so it is always skipped. The new CUDA gate in `get_current_pass_count_buffer` (layer match, capture) is untested too. A wrong count does not crash; it only gives EPLB a worse placement.

**Fix**

Commit a few of the checks from the PR description: a `register_cuda_ci` test comparing both entry points with the torch path on -1, out-of-range, and padded rows, and a CPU test (patch `_is_cuda`) that `get_current_pass_count_buffer` returns `None` on a layer mismatch and in `disable_this_region`.
