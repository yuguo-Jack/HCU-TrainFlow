# [Fix] mamba: End the prefill chunk at the Mamba branching point

[Upstream PR](https://github.com/sgl-project/sglang/pull/45379) · state: closed · merged: False

## Original PR description

## Motivation

With `--mamba-radix-cache-strategy extra_buffer`, a prefill extend snapshots the recurrent state at one position. Normally that is the last checkpoint-grid boundary of the prompt. When the Full-KV match runs past the matched Mamba state, `match_prefix` reports a branching point. If that point lies inside the extend, the one snapshot is moved there, and the prompt end gets no state. The next turn of the conversation extends this prompt, but it can only reuse the branching point. So **turn k+1 hits only turn k-1's length** and recomputes a whole turn. The loss then repeats on later turns.

Example (Kimi-K3, multiturn set below, session 2, grid 64): turn 2 (6,049 prompt tokens) hits 1,984, about turn 0's length. Turn 3 (7,794 tokens) hits 4,032, which is turn 1's length, instead of 6,016 (turn 2's prompt end rounded down to 64). With this PR the hits are 4,032 and 6,016.

Any request whose KV is still cached but whose Mamba state is gone (for example, evicted under state-slot pressure) hits the same path. This is the "only one checkpoint per extend" case reported in #22935.

Related: #41701 and #43135 keep budget-chunked prefill cuts on the checkpoint grid. This PR complements them: it spends the per-extend snapshot on the prompt end rather than the branching point, and its split refuses lengths off `truncation_align_size`, so the changes compose. #38018 adds metrics for this loss.

## Modifications

- `PrefillAdder` ends the prefill chunk at the Mamba branching point (`_mamba_branching_split_len`). That chunk end is checkpointed as before, and the next chunk snapshots the prompt end. This applies to a request's first extend (`add_one_req`) and to the last chunk of a chunked prompt (`add_chunked_req`).
- The split only happens when:
  - the extra-buffer strategy and chunked prefill are on;
  - the extend reaches the prompt end, so no split happens when it is already budget-chunked;
  - `branching - prefix` is on the checkpoint grid, the same predicate as the branching-point snapshot in `ScheduleBatch`, and is aligned to `truncation_align_size` and the KV shard granule;
  - the rest of the extend reaches the next checkpoint;
  - on admission, no other request is mid-chunk, because the scheduler tracks one chunked request.
- Admission no longer lets a second request take the chunked slot in the same pass. Before, a second request could overwrite `new_chunked_req` when an SWA-capped chunk left budget over.
- `SGLANG_OPT_MAMBA_SPLIT_EXTEND_AT_BRANCHING` (default on); `=0` restores the old behaviour.
- Unit tests in `test_prefill_adder.py`.

## Accuracy Tests

Setup: Kimi-K3 (KimiLinear MLA + KDA) on 8x MI355X, `lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261016`, TP8, fp8 KV, chunked prefill 16,384, `extra_buffer`, radix on. The `dcp8` arm adds `--dcp-size 8`. The GPU runs used the first revision of this change, ported onto that image together with the #44660 files. Its code paths are inactive in these arms. The current head also covers the last chunk and adds the budget-chunk and off-grid guards. The multiturn prompts (at most 11.4K tokens, so one chunk, with on-grid prefixes) do not reach those paths.

## Speed Tests and Profiling

### S1. Multiturn prefix hits
Same 48 rows as A2. Each turn appends the next 2,048 tokens of a corpus and a fixed question to the previous turn's text. The table shows `cached_tokens` summed over all rows (287,897 prompt tokens). The ceiling replays the rows through the cache rules with every branching extend split. It stays below the KV ideal because the next turn drops the previous question's tokens, and no prompt-end snapshot covers them.

| Arm | Without fix | With fix | Ceiling | KV ideal | Recovered (of ceiling gap) |
|---|---|---|---|---|---|
| dcp1 | 156,672 (.544) | **176,896 (.614)** | 180,480 (.627) | 204,032 (.709) | 85% |
| dcp8 | 158,208 (.550) | **165,056 (.573)** | 180,480 (.627) | 204,032 (.709) | 31% |

The image as shipped gives the same .544 as the "without fix" dcp1 arm on all 48 rows. With the measured unsplit extends marked, the simulation reproduces every row of both "with fix" arms. dcp1 left 2 extends unsplit and dcp8 left 8, because turns of different sessions arrive together and only one request per pass can split.

### S2. AgentX, dcp8, concurrency 16
InferenceX AgentX client (`semianalysis_cc_traces_weka_062126`), 1,200 s profile. Both servers ran back to back on the same node, n = 1 each.

| Arm | Requests (err) | Device hit (theoretical .957) | tok/s/GPU | TTFT mean / p50 / p90 (s) | TPOT mean / p90 (ms) |
|---|---|---|---|---|---|
| without fix | 200 (0) | .707 | 2,728 | 26.22 / 1.16 / 57.24 | 134.8 / 95.5 |
| with fix | 211 (0) | .716 | 2,838 (+4.0%) | 25.13 / 1.12 / 68.78 | 117.5 / 81.0 |

Hit improves by 1 pp, and tok/s/GPU rises 4%. A single run per arm cannot separate that from noise. On this trace the dominant miss is Mamba state-slot eviction (0 free KDA slots at p25), not the branching case.

Some extends still run unsplit because only one request per pass can split. Keeping two snapshots in one extend would remove that limit, but it needs a second state slot per request; that is left as follow-up.
