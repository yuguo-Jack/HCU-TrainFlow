# [Fix] glm4_moe: bound the text preamble before a required tool call

[Upstream PR](https://github.com/sgl-project/sglang/pull/46672) · state: open · merged: False

## Original PR description

## Motivation

With `tool_choice="required"` or a named function, the GLM grammar is `assistant_turn ::= thinking_block text_block tool_call_blocks` with an unbounded `text_block`. EOS stays masked until `<tool_call>` appears, so a model that keeps writing ordinary text runs to `max_tokens` with no tool call. Seen with GLM-5.3-Flash under conflicting instructions; the reproduction is in #42458. There is no separate GitHub issue for this grammar bug (#13514 was the earlier JSON-grammar variant, fixed in v0.5.6.post2).

Predecessor #42458 removes `text_block` for required selection. Review there noted that GLM models usually emit a short text preamble before the call, so this PR keeps the preamble and bounds it instead.

## Modifications

- `generate_glm_grammar`: when `required and functions`, `text_block ::= ( <sep> [^<]{0,256} )?`, so the call must start within 256 characters. Excluding `<` also keeps every GLM special token out of the preamble.
- `tool_choice="auto"` and requests without tools keep the unbounded `text_block`.
- `test_required_selection_bounds_text_preamble`: 256 characters of text before the call are accepted for auto, required and named selection; 257 are accepted only for auto; thinking on and off.

Known limitation: a literal `<` in the preamble (e.g. `a < b`) is rejected under required selection. It is still allowed inside tool-call argument values.

## Accuracy Tests

Grammar construction only; no model forward or kernel changes. `test/registered/unit/function_call/test_function_call_parser.py -k "Glm47FullAssistantGrammar or Glm4MoeDetector or Glm47MoeDetector"` passes locally, and the new test fails against the current `main` grammar. No end-to-end argument-quality A/B was run.
