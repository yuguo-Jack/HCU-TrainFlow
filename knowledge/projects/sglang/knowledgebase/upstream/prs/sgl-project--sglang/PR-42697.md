# [Fix] hicache: clear the storage backend when a weight update flushes the cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/42697) · state: open · merged: False

## Original PR description

## Motivation

`update_weights_from_disk / _tensor / _distributed` with `flush_cache=True` reaches `flush_cache_after_weight_update`, which resets the tree, the pools and the host tier — but nothing clears L3:

- `Scheduler.flush_cache` calls `tree_cache.reset()`, which never touches the storage backend;
- the only path that calls `storage_backend.clear()` is `clear_storage_backend()`, reachable solely through the separate `ClearHiCacheReqInput` RPC (and PD role switch);
- the key carries no weight version — `storage_model_name` is just the model name plus the host pool's `storage_format_tag`.

So after a weight update the engine keeps prefetching KV computed with the **previous** weights. Silent wrong output, unbounded in time, and the obvious way to hit it is an RL rollout that updates weights between rounds with `--hicache-storage-backend` on.

## Modifications

`flush_cache_after_weight_update` also clears the storage backend, mirroring `clear_hicache_storage_wrapped`'s existing gate (`enable_hierarchical_cache or enable_lmcache`). A backend that cannot be cleared logs a warning rather than failing the update; `clear()` already swallows backend exceptions and takes no collective, and the call runs on every rank exactly as the existing RPC handler does.

`flush_cache=False` is left alone on purpose: the caller is saying the stale pages are theirs to manage, and the device and host tiers keep theirs too.

The existing `test_scheduler_weight_version_tracking.py` stub scheduler gains the two attributes the code under test now reads, rather than the product code defending with `getattr` — a stub that doesn't model the real scheduler is what hid this.

## Accuracy Tests

New CPU test `test/registered/unit/managers/test_weight_update_clears_storage.py` (6 cases, 9 s): a flush clears L3; lmcache counts too; no flush requested and no storage tier are both no-ops; a failed clear does not raise; a `None` scheduler is a no-op. With `test_scheduler_weight_version_tracking.py`: 26 passed.

Negative control: drop the new call → 5 of 6 cases fail. Restored → 6 passed.

Found while re-reviewing the unified radix cache; code-traced, not reproduced on a live engine.

## Open question (why this is a draft)

Clearing is the blunt instrument. With a shared backend (one mooncake cluster behind several engines) this wipes entries other engines are still using correctly — a perf hit for them, not a correctness one, whereas not clearing is a correctness bug here. The alternative is to fold a weight generation into `storage_model_name` so stale entries simply become unreachable and age out, which also keeps a shared backend usable across a rollout. That is the better end state; this PR is the minimal fix. Happy to switch if reviewers prefer the versioned key.
