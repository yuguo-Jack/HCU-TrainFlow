# [Fix] [Intel] diffusion: Restore copy offload for FLUX.2-dev nightly

[Upstream PR](https://github.com/sgl-project/sglang/pull/45725) · state: closed · merged: True

## Original PR description

## Motivation

`TestFlux2DevXPU::test_diffusion_generation[flux2_dev_image_t2i]` in `nightly-xpu-kernel-main-4-gpu` has failed the e2e latency guard every night since 10-19 ([latest run](https://github.com/sgl-project/sglang/actions/runs/39663561647/job/119442565458)):

```
Validation failed for 'E2E Latency'.
  Actual:   83818.7248ms
  Expected: 49699.2100ms
  Limit:    69578.8940ms (rel_tol: 40.0%, abs_pad: 20.0ms)
```

Denoising runs at ~1.6 s/step against a ~0.93 s/step baseline in `xpu_b60.json`.

**Root cause:** #45013 set `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` in `scripts/ci/xpu/xpu_ci_start_container.sh` to work around a first-H2D-copy hang in 1-GPU text-model tests. That keeps all copies on the compute engine. FLUX.2-dev runs with `--dit-layerwise-offload`, which streams ~14.6 GB of pinned weights H2D on every denoise step and relies on the copy engine to overlap those copies with compute. Without copy offload the copies serialize with the DiT compute.

The timing lines up exactly, all on the same runner (`aicf-jf-cicd-06`):

| Nightly | Checkout contains #45013 | FLUX.2 result |
|---|---|---|
| 10-16, 10-17, 10-18 | no | passed (test 133-147s) |
| 10-19, 10-20, 10-21 | yes | failed (~1.6 s/step, test ~165s) |

FLUX.2 never hit the hang that #45013 works around; it passed on all three nights with copy offload on.

## Modifications

- `test/registered/xpu/test_xpu_flux2_dev.py`: set `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=0` in the case `env_vars`, so the FLUX.2 server gets copy offload back. Every other XPU test keeps the #45013 workaround.
  - UR's `getenv_tobool` only treats `y/yes/t/true/1` as true, so `"0"` re-enables copy offload.
  - The diffusion harness applies case `env_vars` on top of the inherited container env (`env.update(self.env_vars)` in `ServerManager`), so the per-case value wins.

The `xpu_b60.json` baseline is unchanged. It reflects the expected performance with copy offload on.
