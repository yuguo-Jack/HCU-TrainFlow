# [Fix] [NPU] gptq: Correct linear zero-point offset sign

[Upstream PR](https://github.com/sgl-project/sglang/pull/47637) · state: open · merged: False

## Original PR description

NPU GPTQ linear layers produce incorrect outputs when the zero point differs from the signed-weight midpoint. For example, a 4-bit layer with weight 10, zero point 9, scale 0.5 and 256 unit inputs returns 384 instead of 128.

The loader shifts both weights and zero points by the midpoint. `npu_weight_quant_batchmatmul` adds `antiquant_offset`, so the converted zero point needs to be negated. Do this once during weight loading, after the GPTQ v1 `+1` adjustment. Symmetric zero points remain zero.

Tested the original and patched loader/matmul on Ascend NPU with torch-npu 2.10.0.post6: 4/8-bit, GPTQ v1/v2, FP16/BF16, symmetric/asymmetric and boundary zero points, random weights, group sizes 64/128, bias, and 2D/3D inputs. Before: 8 passed, 48 failed. After: 56 passed. Reference is FP32 dequantization/matmul cast to the output dtype (`rtol=0.02, atol=0.125`). This is a kernel-level check, not a full-model accuracy run.

[Per-case results](https://github.com/AkiYangDev/sglang/blob/789468d8b4a2fc3fc664a67535d27c3271e057f5/RESULT.json). The screenshot below renders those saved results.
