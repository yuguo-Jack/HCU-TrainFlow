# [HiCache] Support Mamba in buffer-only host memory mode

[Upstream PR](https://github.com/sgl-project/sglang/pull/36345) · state: closed · merged: True

## Original PR description

## Motivation

`--hicache-host-memory-mode buffer_only` rejects any tree with a Mamba component, so hybrid Mamba/GDN models cannot use it. This PR lifts that fence. Part of #34899.

## Changes

On top of #42633, the write path needs no Mamba code: per-pool backups already write a node's Mamba state under its last page hash. What remains is the read path, which this PR moves behind component hooks so the pipeline stays component-agnostic.

- **Component load-back context**: `prepare_buffer_load_back(req, staged)` returns a `BufferLoadBackContext` with additional `load_xfers`, `finalize_allocation(success)`, `get_insert_fields()`, and redundant destinations to free after the transfer ack. Returning `None` defers admission. Required staged state is checked by the owning component.
- **`MambaComponent`**: loads the staged checkpoint into both the published node slot and the request slot through the layer-gated H2D path. Preparation rolls back the request allocation on failure. Successful load-back resets the ReplaySSM cursor and removes the pending CoW/clear; an existing node checkpoint's redundant destination is freed only after the transfer ack.
- **Pipeline and admission**: records staged state in `StagedPrefetchPlan.mamba_slots` and `req.mamba_host_hit_length`. Component hooks handle load-back preparation; the pipeline no longer branches on Mamba to validate the staged state. Shared-pool admission charges both the request state and the staged node checkpoint before allocating either, with bounded deferral when capacity is unavailable. Continuing chunks do not charge an already consumed host checkpoint again.
- **Test**: `TestUnifiedHybridBufferOnlyBitExact` (Inkling, 1 GPU) seeds `P[:512]` into L3, flushes the device tree, then measures `P[:768]`, so every hit comes back through the buffer-mode read path.

Additional GB300 validation (2026-10-10): Inkling-Small-NVFP4, TP4, `buffer_only`, HiCache L3(file), unified memory disabled. The original PR head (`fccd0483225a`) plus the independent main scheduler fix #43479, without #43108, completed 10 minutes of mixed pressure plus drain: 407 requests (386 generations and 21 intentional aborts), 48 L3-hit requests. All 109 scored requests / 34,831 tokens had exact logprob equality and sampled KL=0, including all 48 L3 hits. All 205,441 recorded cache-boundary events agreed across four ranks. Backup, prefetch, and FULL/SWA/Mamba load-back transferred data; the final cache flush succeeded. Sampled KL compares scored token logprobs, not the full vocabulary distribution.

The TP pressure run requires #43479 to avoid main's rank-local waiting-prefix refresh timer causing different LRU eviction decisions. #43108 addresses a separate cancellation race and did not resolve this divergence alone. The independent cache-efficiency fix #43466 is not included in this run. Pressure-induced backup drops and prefetch retry-cap warnings remain recorded for further investigation; this is not a claim that all cache-efficiency issues are resolved.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Reserve both Mamba slots for staged load-back**

When buffer-mode admission has limited Mamba capacity, this reserves only the consuming request's slot, but `_prepare_mamba_handoff` also passes `node_copy` to `cc.load`, which auto-allocates a second device slot for the published tree node. Consequently a request can pass the `rem_mamba_slots` gate with only one recoverable slot, consume it for the request, and then have `cc.load` fail and discard an otherwise valid L3 hit; if the request already owns a slot, this reserves zero despite still needing the node slot. Account for the tree-node allocation as well so staged Mamba hits are not spuriously recomputed under pressure.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Retain the request slot until the queued H2D finishes**

When a staged request passes the initial budget gates but is rejected by a later check in `add_one_req` (for example the post-load input-token or tile gate), this queues an H2D into its Mamba slot before admission is committed. The rejection path in `scheduler.py` immediately returns that slot to `mamba_allocator`, while `ready_to_load_host_cache()` launches the queued copy only afterward (or during a later batch if no request was admitted), so the transfer can overwrite a slot already reassigned to another request and silently corrupt its recurrent state. The destination slot must remain owned until the load is cancelled or its completion is acknowledged.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Reset ReplaySSM cursors after restoring a checkpoint**

When `--enable-linear-replayssm` or its speculative variant is enabled, replacing the deferred `copy_from` with this direct H2D leaves `replayssm_write_pos` and, where present, `replayssm_cache_base`/`replayssm_is_flush` unchanged. Those cursor arrays are not included in the HiCache Mamba transfer, while the ordinary `MambaPool.copy_from` path explicitly resets them when installing a checkpoint; a newly allocated or previously used request slot can therefore interpret stale ring entries on its first decode and produce incorrect output. Reset the ReplaySSM cursor metadata when the staged state supersedes the pending copy.

Useful? React with 👍 / 👎.
