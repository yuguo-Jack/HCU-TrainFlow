# [Docs] Document Qwen3-4B/8B H200 mixed-chunk latency tradeoffs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43551) · state: closed · merged: True

## Original PR description

## Motivation

Qwen3-4B and Qwen3-8B BF16 on one H200 can show high median TTFT with concurrent long prompts even when its prefill and decode kernels are already comparable to vLLM. The cookbook does not mention the existing mixed-chunk option or its latency tradeoff.

## Modifications

Add a Qwen3-4B/8B H200 configuration tip to benchmark `--enable-mixed-chunk`, with an explicit reminder to check TPOT, end-to-end tail latency, and throughput. This is an opt-in deployment recommendation; no runtime default changes.

## Accuracy Tests

Qwen3-8B, full held-out GSM8K: 1,314 cases, five separate few-shot examples, non-thinking mode, temperature 0, top_p 1, seed 42, max_tokens 2048, concurrency 64. The exact prompt hashes and case IDs match across runs.

| Configuration | Run 1 correct | Run 2 correct |
|---|---:|---:|
| Default | 1201/1314 | 1205/1314 |
| Mixed chunk | 1200/1314 | 1203/1314 |

All four runs completed without request errors or truncated responses. Greedy outputs vary across repeated runs of the same configuration (28 and 33 numeric-answer changes respectively). The paired mixed runs lost 10/gained 9 and lost 11/gained 9 answers. These task scores do not establish numerical equivalence or statistical non-inferiority.

Qwen3-4B uses the same held-out cases and sampling settings with max_tokens 4096. Default scores 1153/1314 and mixed scores 1157/1314, with 11 losses and 15 gains and zero request errors. Default case 754 and mixed cases 357/754 hit the token limit and are counted wrong. The same-device vLLM control scores 1157/1314 with one capped case (214). These are different outputs despite similar aggregate scores. An earlier matched 2048-token pair scored 1160/1314 (default) and 1158/1314 (mixed), with no request errors; default case 754 was capped, and the mixed run had no capped responses. Raising the generation limit therefore does not establish a stable accuracy improvement.

## Speed Tests and Profiling

SGLang `e35f60b9bcb51045fd0602d8ed12cff8021c040f`; Qwen3-8B revision `b968826d9c46dd6066d109eabc6255188de91218`; TP1, default FA3 backend, no speculative decoding. Same H200 for all runs. Random ShareGPT-derived prompts, nominal 8192 input/1024 output tokens, seed 42, 320 requests, concurrency 64, request_rate=inf. Per-request retokenized input lengths match; every timed request returned 1024 output tokens. Warmup and prefix-cache flush precede timing. Profiling is a separate run.

| Configuration | Output tok/s | Median TTFT(ms) | Median TPOT(ms) | p99 E2E(ms) |
|---|---:|---:|---:|---:|
| Default, run 1 | 1705.21 | 7195.66 | 30.55 | 38579 |
| Mixed, run 1 | 1703.08 | 969.40 | 36.53 | 51290 |
| Mixed, run 2 | 1704.99 | 968.78 | 36.50 | 51162 |
| Default, run 2 | 1705.79 | 7170.90 | 30.53 | 38569 |

The second pair reverses the order. Mixed chunk lowers median TTFT by about 86.5% with less than 0.13% throughput change, while median TPOT rises about 19.5% and p99 E2E rises about 33%. The initial burst still waits for prefill: p99 TTFT stays around 14 s. This is a workload-dependent tradeoff, not a general tail-latency improvement.

Separate traces show comparable pure decode GPU iterations (about 22.5 ms in SGLang versus 22.7 ms in vLLM on the same machine) and comparable 8K prefill kernels. Mixed-chunk traces verify actual MIXED batches. The median TTFT gap here is primarily a scheduling/workload interaction, rather than evidence that the standalone attention kernel is slow.

Qwen3-4B revision `1cfa9a7208912126459214e8b04321603b3df60c`, the same workload and pinned SGLang source, TP1/default FA3, another H200 with all three controls on its GPU 0:

| Configuration | Output tok/s | Median TTFT (ms) | Median TPOT (ms) | p99 E2E (ms) |
|---|---:|---:|---:|---:|
| SGLang default | 2078.32 | 4484.83 | 26.44 | 31655 |
| SGLang mixed | 2070.73 | 641.94 | 30.20 | 39767 |
| vLLM control | 2076.00 | 954.69 | 29.96 | 39655 |

Exact request records and actual input/output token counts match. An earlier SGLang pair independently reproduces the tradeoff: default/mixed throughput 2079.28/2068.94 tok/s and median TTFT 4482.56/789 ms. The shared configuration tip applies to both dense models: mixed chunk substantially reduces median TTFT, with higher TPOT and end-to-end tail latency than SGLang's default. For 4B, the mixed configuration reaches within 0.25% of the same-device vLLM throughput, with lower median TTFT and similar TPOT/p99.

A separate matched 4B profile finds comparable initial prefill kernel sums (1089.4 ms SGLang versus 1091.6 ms vLLM across eight steps). SGLang initially runs pure EXTEND batches while vLLM mixes decode rows into prefill. The measured intervention is the existing scheduler option; this documentation change does not introduce a new kernel.
