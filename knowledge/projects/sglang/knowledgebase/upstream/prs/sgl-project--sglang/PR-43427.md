# [Performance] GGUF: use MMQ from 2 rows for very large matrices (e.g. lm_head)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43427) · state: open · merged: False

## Original PR description

## Motivation

`fused_mul_mat_gguf` dispatches standard / K-quant GGUF matmuls to MMVQ (`ggml_mul_mat_vec_a8`) when `x.shape[0] <= mmvq_safe`, with `mmvq_safe = 2` for matrices with more than 5120 output rows. MMVQ launches one grid row per input row, so its cost is linear in the number of input rows, while MMQ (`ggml_mul_mat_a8`) has a fixed cost that a very large matrix amortizes. For a large-vocab lm_head this makes the 2-row case (e.g. the verify window of one-step speculative decoding) almost twice as slow as it needs to be.

Q6_K lm_head of a 248K-vocab model under TP2 (124,160 x 2560 per rank), RTX 5070 Ti (sm_120), time per call inside a CUDA graph:

| input rows | MMVQ | MMQ |
|---|---|---|
| 1 | 324 µs | 378 µs |
| 2 | 643 µs | 381 µs |
| 3 | 963 µs | 385 µs |
| 4 | 1284 µs | 387 µs |

A mid-sized matrix behaves differently: an 8192 x 2560 Q6_K is still faster in MMVQ at 2 rows (25.6 µs vs 32.3 µs MMQ). So the existing rule is right for ordinary layers, and the change is a threshold on output rows.

## Modifications

- `python/sglang/srt/layers/quantization/gguf.py`: add a module-level constant `MMVQ_SINGLE_ROW_ABOVE = 32768`. For non-I-Matrix types, a matrix with more than that many output rows uses MMVQ for a single input row only, and MMQ from 2 rows.
- I-Matrix types are unchanged: they have no MMQ kernel, so leaving MMVQ would fall back to dequantization.
- Nothing else in the dispatch changes; batch-size-1 decode still uses MMVQ everywhere.

## Accuracy Tests

MMQ and MMVQ both quantize the activations to q8_1 and accumulate the same blocks, so the lm_head output differs only at bf16 rounding level. On the speculative-decoding run below, the draft acceptance length was unchanged (1.49 before and after), and generated text showed no quality change.

## Speed Tests and Profiling

End to end, measured as an A/B of this one change in our serving tree (SGLang with a KTransformers CPU/GPU hybrid MoE, so not upstream main itself): a Qwen-architecture IQ3_S GGUF model with a Q6_K lm_head (248K vocab), TP2 on 2x RTX 5070 Ti, one-step speculative decoding (2-row verify), Japanese fiction decode probe, mean of 8 runs:

| | decode tok/s (mean) |
|---|---|
| without this change | 77.6 |
| with this change | 80.8 |

Per-call kernel times are in the table above. Without speculative decoding (1 row per step) the dispatch is unchanged.
