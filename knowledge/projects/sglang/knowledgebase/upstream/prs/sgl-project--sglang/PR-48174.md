## What

Re-lands #47784 (the JIT `moe_finalize_fuse_shared`, reverted by #47994) with one fix: the shared-expert row is now read after `PDLWaitPrimary`. The routing tensors still load before the wait when `routing_ready=True`. It also drops the device guard #47784 added around the launch.

cc @hnyls2002 @BBuf

## Why the revert happened

#47994 suspected the early `shared_output` load, and that is the cause. `shared_output` is written by the shared expert on `alt_stream` and joined with `wait_stream` before the finalize. In a CUDA graph, that cross-stream join into a PDL launch is a programmatic edge as well, so a shared expert that triggers its dependents early lets the finalize start before the row is written. Only the PDL wait orders it.

Reproduced on B300 with a shared-expert stand-in on a side stream that triggers at entry and spins 300 us before writing, joined with `wait_stream`, followed by the PDL finalize:

| kernel | eager | CUDA graph | eager, PDL writer | CUDA graph, PDL writer |
|---|---|---|---|---|
| #47784 | 0/20 wrong | 0/20 | 0/20 | 20/20 wrong |
| this PR | 0/20 | 0/20 | 0/20 | 0/20 |

The reproduction needs a purpose-built early-triggering writer kernel, so it is not added as a registered test.

## Performance

B300, hidden 7168, top-k 8, bf16 with fp32 weights, CUDA graph behind a real PDL producer that triggers before its final stores. Finalize cost = pair time minus producer-only time, medians of 2 x 15 replays.

| | this PR vs #47784 | this PR vs the pre-#47784 kernel on main |
|---|---|---|
| warm (the shared row was just written, in L2) | within +-0.04 us at 1-8192 tokens | 1 token -0.65 us, 32-128 tokens -1.5 to -2.9 us, 4096-8192 tokens equal |
| cold (rotated buffers) | +0.12 / +0.23 us at 64 / 128 tokens, about 0 elsewhere | 32-128 tokens -2.6 to -6.5 us |
| without PDL | about 0 | |

Issuing the shared load right after the wait is as fast as or faster than issuing it in use order (after the gathers): for one-wave grids ptxas places it after the gathers either way, and the persistent kernel is up to 0.6 us faster with the early issue.

We are keeping this without a device guard on purpose. The goal is no extra CPU overhead on the decode path and a clean launcher: a guard (or the old launcher's `cudaSetDevice`) costs a host-side device query and switch on every call, for a case that does not occur in SGLang, where each process launches its kernels on its current device. The JIT kernel launchers follow the same rule. A caller that does need another device should set it once around its own region rather than have every kernel do it per call.
