# [Diffusion] Add opt-in pi0.5 completion-boundary action batching

[Upstream PR](https://github.com/sgl-project/sglang/pull/43528) · state: closed · merged: False

## Original PR description

## Motivation

Pi0.5 requests with different denoising budgets currently form separate whole-trajectory batches. This change adds a default-off execution path that retains each request's original Euler grid, latent and prefix state, advances an admitted batch to its next completion boundary, returns completed actions, and re-admits unfinished requests with their original FCFS age.

For example, requests with 3 and 5 remaining steps execute three steps together. The first returns; the second retains two steps and may batch with a new compatible request. The continuation never resamples its noise or substitutes its remaining budget for its original integration grid.

Related to #43522. This is the execution/lifecycle portion of the proposal; dynamic remaining-work bucketing and workload control are deferred.

## Modifications

- Handle action requests without the visual-generation `image_path` field during dynamic admission; a real HTTP request exposed this integration error, now covered by a real-Req regression.

- `enable_segmented_actions=false` preserves the existing path and sampling signatures.
- Opt-in path relaxes only the N signature field, retains other admission checks, and uses rank-zero original-arrival selection.
- Continuations bypass preprocessing/prefix encoding and the fresh-batch accumulation delay. Intermediate placeholders stay inside the scheduler.
- Compatible prefix lengths are padded and masked for collation. Both prefix and action graphs are disabled because graph-owned prefix outputs may be overwritten by later replay.
- Initial scope is monolithic pi0.5 with SP=1, CFG parallelism disabled, and no per-request action-expert offload. Stateful realtime sessions and multi-output groups remain on the ordinary path.

## Accuracy Tests

- [x] 39 new component/regression tests and 46 existing pi0.5 API/cache/runtime tests passed with normal package imports and the upstream unit conftest in a Linux Ascend environment (PyTorch/torch-npu 2.10, Python 3.11).
- [x] Ruff checks, formatting, Python syntax, JSON configuration and diff whitespace checks.
- [x] Focused pi0.5 unit suites in the installed Linux environment; the full upstream suite remains pending.
- [x] Base pi0.5 checkpoint on Ascend, TP=1: fixed-noise HTTP comparison for budgets [3,5,4,8], plus 12 staggered requests with three prompt lengths; all completed and preserved original step counts, with actual continuations observed.
- [x] Real TP=2 on Ascend, SP=1: the same four-request comparison completed with segment counts [1,2,1,3] and maximum absolute error 0.010557 at the same tolerances.
- [ ] Applicable upstream hardware CI, CUDA validation and target TP=8 topology.

The initial isolated CPU runner was supplemented by the normal-import tests and real HTTP checks above. The full-checkpoint checks used bf16, SP=1 and request graphs off; atol=0.01 and rtol=0.01 passed, with maximum absolute action error 0.011049 for the four-request check and 0.008912 for the staggered check. This is a limited synthetic-input comparison, not bitwise equivalence, a robot task-quality result, or CUDA validation. The hardware comparison utility under `examples/usage/pi05_segmented_actions/` checks final actions and original step counts and rejects runs without an observed continuation. No new hardware performance claim is made.
