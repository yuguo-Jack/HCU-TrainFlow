# [Perf] [AMD] diffusion: add a Triton dense attention prefill path for gfx1151

[Upstream PR](https://github.com/sgl-project/sglang/pull/46515) · state: open · merged: False

## Original PR description

## Motivation

`SDPAImpl.forward` transposes the token-major q/k/v to head-major and hands SDPA a
**non-contiguous** view. On gfx1151 (RDNA 3.5, Ryzen AI MAX 395) that view costs
AOTriton a lot: the same
`attn_fwd` kernel runs at 12.4 / 6.7 / 2.06 TF for 4096 / 8192 / 16384 tokens,
versus 12.4 → 18 TF when the operands are dense. Even the dense number leaves
throughput on the table: a plain Triton prefill kernel reaches 31.8 TF at the
same shape, which is the bulk of diffusion prefill cost.

## What this adds

* `python/sglang/kernels/ops/diffusion/attention/flash_attn_dense_triton.py` — a
  non-causal MHA prefill kernel for dense `[B, H, S, D]` operands. It needs no
  masks in the main loop (query length is a multiple of the tile, padding rows of
  K/V are zeroed and their mass is subtracted from the denominator), loads K
  pre-transposed through its strides, and runs `BLOCK_M = BLOCK_N = 64` with 4
  warps and a single pipeline stage. bf16 in, fp32 accumulate, bf16 out; softmax
  keeps the reference's rounding (unscaled q into the WMMA,
  `1/sqrt(D) * log2(e)` on the fp32 scores).
* A gated fast path in `SDPAImpl.forward`: HIP only, `SGLANG_USE_ROCM_TRITON_DENSE_ATTN`
  (default off), bf16, batch 1, equal q/k/v lengths, `head_dim == 128`,
  `seq_len % 64 == 0`, `seq_len >= 4096`, non-causal, no dropout. Everything
  else falls through to the existing SDPA call untouched. Operands are
  materialised head-major once before the kernel sees them; below 4096 tokens
  those copies cost more than the kernel saves, so shorter sequences stay on
  SDPA.

## Numbers (gfx1151, torch 2.9.1+rocm7.2.4, B=1 H=32 D=128 bf16)

All rows below are measured on gfx1151 (Ryzen AI MAX 395, RDNA 3.5).

Same dense head-major operands for both, kernel-only (median of 10, 3 warmups):

| seq | AOTriton SDPA | Triton | speedup | Triton TF |
|---|---|---|---|---|
| 4096 | 16.4 ms | 9.7 ms | 1.70x | 28.5 |
| 16384 | 239.3 ms | 138.5 ms | 1.73x | 31.8 |

The 16384 row uses the shipped one-stage pipeline; the 4096 row predates the
stage sweep and is unaffected by it.

What the flag actually changes end to end, i.e. including the layout
materialisation the kernel needs versus the strided call the backend makes today:

| seq | today (SDPA on the view) | with this PR | speedup |
|---|---|---|---|
| 4096 | 22.2 ms | 16.6 ms | 1.34x |
| 8192 | 163.6 ms | 54.3 ms | 3.01x |
| 16384 | 2131 ms | 183.3 ms | 11.6x |

The 16K row is the interesting one: AOTriton's strided-operand regression grows
faster than the work does, so at 128 head dim the gap widens with sequence
length. Diffusion DiT self-attention at 2048x2048 sits exactly there.

## Kernel resources and scaling

Compiled at S=16384 the kernel uses 256 VGPR per lane (the RDNA3 limit) with
**zero spills** and 16 KiB of LDS, which keeps four CTAs resident per CU. A
second pipeline stage doubles LDS to 32 KiB, halves residency, and measured
146.3 ms instead of 138.5 ms — that is why the shipped configuration uses one
stage. Of 81 swept `BLOCK_M x BLOCK_N x warps x stages` points, 66 compiled and
this one ranked first; `BLOCK_M = 128` with 2-4 warps spills 350-1149 registers
and drops to 3.8-6.7 TF.

Sweeping the sequence length shows where the materialisation stops paying:

| seq | SDPA on the view | this PR | speedup | kernel vs dense AOTriton |
|---|---|---|---|---|
| 1024 | 1.37 ms | 2.10 ms | 0.65x | 1.81x |
| 2048 | 5.39 ms | 5.58 ms | 0.97x | 1.78x |
| 4096 | 21.7 ms | 16.9 ms | 1.29x | 1.70x |
| 8192 | 150.2 ms | 54.2 ms | 2.77x | 1.62x |
| 16384 | 2180.5 ms | 182.4 ms | 11.95x | 1.64x |
| 32768 | 12932.8 ms | 658.6 ms | 19.64x | 1.65x |

The kernel alone wins at every length (1.62-1.81x against dense AOTriton, and
2.1x to 22x against the strided view); what crosses over is the three
materialisations, which are 69% of the call at 1024 tokens and 20% at 16384.
Hence the 4096-token floor.

Numerics against an fp32 reference: max abs diff 1.1e-3, mean 1.9e-5, no element
above 0.05 (bf16 rounding on both sides).

## Tests

* `test/registered/unit/attention/test_sdpa_triton_dense_attention.py` (CPU, no GPU
  needed; the kernel is mocked): env gate, non-ROCm, torch.compile, causal,
  dropout, fp32, `head_dim != 128`, `seq % 64`, short sequences (`seq < 4096`),
  mismatched lengths, kernel refusal → SDPA fallback; operand strides and `scale`
  forwarded to the kernel. `10 passed`.
* `test/registered/kernels/ops/attention/test_flash_attn_dense_triton.py` (AMD CI):
  fp32-reference numerics at 128/256/512 tokens, zero-padded K/V with `kv_pad`,
  predicate rejections. `4 passed` on gfx1151.

Both were run on gfx1151 with `PYTHONPATH` pointed at a patched copy of the
installed package, so they are not compile-only checks.

## Performance across architectures

The kernel-vs-dense comparison above is gfx1151 only. Per-architecture status,
including the reviewer's measurements on other cards:

| arch | device | kernel vs dense AOTriton | status |
|---|---|---|---|
| gfx1151 | RDNA 3.5 (Ryzen AI MAX 395) | 1.73-1.80x (S=4096-32768) | measured here |
| gfx1201 | RDNA 4 | 1.19-1.37x | reviewer A/B, 2026-10-29 |
| gfx1100 | RDNA 3 | 0.82-1.01x | reviewer follow-up on #46065, 2026-10-30 |
| gfx9x | CDNA | — | untested |

So the gain is not RDNA4-only and not `gfx11`-uniform: it holds on gfx1151 and
gfx1201 and is absent on gfx1100 (0.82-1.01x). The fast path should therefore be
gated by architecture, not by the `gfx11` prefix.

## Relation to other work

* #46065 materialises dense SDPA operands; that closes the "strided view" half of
  the gap (AOTriton back to 240 ms at 16K) but not the remaining 1.63x.
* Model-side qkv changes and sparse-attention kernels are out of scope here.

## Caveats

- The default is off. gfx1151 (RDNA 3.5) and gfx1201 (RDNA 4) both show a gain;
  gfx1100 (RDNA 3) is flat at 0.82-1.01x in the reviewer's A/B. gfx9x is
  untested. Gate the fast path per architecture rather than per `gfx11` prefix;
  flip the default once there are numbers for the remaining parts.
- Sequences below 4096 tokens deliberately stay on SDPA. The floor is the
  measured crossover from the table above (gfx1151), not a derived bound: the
  kernel alone is faster at every length, but the three head-major
  materialisations dominate short calls and make the full path a net loss there.
- End-to-end diffusion (Qwen-Image 2.1 at 2048x2048) throughput is not measured
  in this PR; the benchmark above is operator-level.
