# [lora] Support LoRA for the NemotronH_Nano_VL_V2 model family

[Upstream PR](https://github.com/sgl-project/sglang/pull/39798) · state: closed · merged: True

## Original PR description

## Motivation

**1. `should_apply_lora` has no call site.**

#21864 moved the `embed_tokens` / `lm_head` handling above the gate so VL patterns would stop skipping those, but removed the gate instead of re-inserting it below. The comment it left behind still refers to it:

```python
# Handle embed_tokens and lm_head before the should_apply_lora gate,
# since VL models' should_apply_lora patterns only match language
# model layers and would incorrectly skip these.
```

Nine models in tree declare `should_apply_lora` to keep their encoder towers out of LoRA, and none of it has taken effect since. Where a tower nests under `layers.<i>.` and `VisionAttention` exposes `qkv_proj`, a target as ordinary as `--lora-target-modules qkv_proj` also selects vision modules and binds them to the language model's buffers. The first request naming an adapter then aborts the scheduler:

```
AssertionError: LoRA buffer shape torch.Size([2304, 8]) does not match weight shape torch.Size([1024, 8])
```

Nothing in CI covered the call site, which is how the deletion went unnoticed, so this PR adds unit coverage for it.

**2. Restoring the gate regresses Intern-S2-Mobius.**

Intern-S2-Mobius (#33691) landed after #21864, so its guard against routed-expert adapters was written for a loop that had no gate, and it sits inside the `FusedMoE` branch below one. With the gate back, `should_apply_lora` admits only `model.layers.`, so `model.meta_mlp.<bank>.experts` hits `continue` and that `ValueError` becomes unreachable.

Startup then succeeds where it used to fail. The pool still sizes its `*_moe` buffers, because `mem_pool` scans every `FusedMoE` in the model rather than the wrapped set, and `lora_strict_loading` is off by default — so the adapter's routed-expert weights load and are silently dropped.

**3. LoRA support for the `NemotronH_Nano_VL_V2` family.**

`LoRAManager` resolves the text config via `get_text_config()` and looks up `get_hidden_dim()` / `get_stacked_multiply()` on the top-level model.

## Changes

- `lora_manager.py`: restore `should_apply_lora`, after the `embed_tokens` / `lm_head` handling so VL patterns do not skip those.
- `lora_manager.py`: hoist the Intern-S2-Mobius routed-bank rejection above the gate, keeping the layer-id condition so only banks outside the decoder hierarchy are rejected, and drop the now-unreachable copy in the `FusedMoE` branch.
- `test/registered/unit/lora/test_lora_manager_init_modules.py`: three cases pinning the ordering — a vision projection sharing a target name stays out of `lora_modules`, an `embed_tokens` outside the gated prefix is still wrapped, and a routed bank still raises rather than being skipped. Renamed from `test_lora_manager_tied_lm_head.py`, since the file now covers `init_lora_modules` rather than the one tied-head case.
- `configs/nano_nemotron_vl.py`: expose `llm_config` through `get_text_config()`. It is assigned before `super().__init__()`, which validates token ids through that accessor.
- `models/nano_nemotron_vl.py`: declare `supported_lora_modules` and forward `get_hidden_dim()` / `get_stacked_multiply()` to the inner `NemotronHForCausalLM`. Its per-layer geometry is required for the Mamba / MoE / latent projections; the generic fallback sizes those wrongly and raises on `in_proj`, `out_proj` and `fc*_latent_proj`.
- `test/registered/unit/configs/test_nano_nemotron_vl_config.py`: assert `get_text_config()` resolves to `llm_config`. Without the override it returns the VL config itself and the `num_hidden_layers` lookup raises.

## Tests

`python3 -m pytest test/registered/unit/models/test_nano_nemotron_vl.py test/registered/unit/configs/test_nano_nemotron_vl_config.py test/registered/unit/lora/test_lora_manager_init_modules.py` — 15 passed.

Each new case was checked against its unfixed code, one perturbation at a time:

| perturbation | resulting failure |
| --- | --- |
| gate deleted, i.e. the state on `main` | `lora_modules[0]` also holds `vision_model.encoder.layers.0.attn.attn.qkv_proj` |
| gate hoisted above the `embed_tokens` / `lm_head` handling | `embed_tokens_module` is left `None` |
| routed-bank rejection left below the gate | `model.meta_mlp.0.experts` is skipped instead of raising |
| `get_text_config()` override removed | `AttributeError` on `num_hidden_layers` |

Served a Nemotron-H Omni checkpoint on 2 GPUs, TP2, `csgmv` backend, base plus two adapters in a single batch:

| adapter | result |
| --- | --- |
| `lora_B = 0` | output identical to base — the LoRA path leaves the base computation untouched |
| `lora_B ~ N(0, 0.5)` | output changes — the delta is applied |

Both checks fail without these changes. Also verified startup on a second checkpoint, and that non-LoRA serving is unaffected (gsm8k 5-shot unchanged at 91.1% flexible / 85.4% strict).

Run the `model.meta_mlp.` check before the gate, or delete the dead branch and warn when an adapter carries routed-expert weights.
