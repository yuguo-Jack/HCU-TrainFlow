# [Fix] dsa: Refuse the trtllm backend at launch outside SM100/SM103/SM107

[Upstream PR](https://github.com/sgl-project/sglang/pull/47237) · state: open · merged: False

## Original PR description

## Motivation

On CUDA capability >= 10, `_dsa_split_backend_resolution` defaults the `trtllm` DSA
backend (FP8 KV on both phases, BF16 KV on decode). That arm hardcodes flashinfer's
`backend="trtllm-gen"`, which the pinned wheel builds for SM100/SM103/SM107 only:

```python
# flashinfer 0.7.2, mla/_core.py:1300, 1319-1322 (_resolve_dsv4_sparse_mla_backend)
is_sm100_family = cc in ((10, 0), (10, 3), (10, 7))
if requested_backend == "trtllm-gen" and not is_sm100_family:
    raise ValueError(f"backend={requested_backend!r} requires SM100/SM103/SM107, got SM{cc[0]}{cc[1]}")
```

So on SM120/SM121 resolution accepts a configuration that cannot run: the weights load
and the refusal arrives during autotune, CUDA-graph capture or the first forward --
#40558, and #40286 for SM121. Reproduced on an RTX PRO 5000 (cc 12.0) with a
`DeepseekV32ForCausalLM` config and no DSA flag.

## Modifications

- `_check_dsa_backend_constraints` refuses `trtllm` unless `(major, minor)` is in
  `(10, 0), (10, 3), (10, 7)` -- flashinfer's own condition. `major == 10` alone would
  still admit SM101/SM102/SM104 to the same late failure.
- Nothing is re-routed: sparse MLA on SM120/SM121 is what #31481 is building (open) and
  #40286 records no usable DSA backend there, so a new default would be an unvalidated
  target. This only turns "accepted, then crashes" into "refused at startup".
- The gate sits after every device-free rule and skips a tilelang + `trtllm` mix, which
  stays the layout error it already was, so no existing case becomes device-dependent.
- The set tracks the pinned wheel, which `bot-bump-flashinfer-version.yml` moves on its
  own.
- The ROCm hint said "trtllm on Blackwell", now "trtllm on SM10.x Blackwell". HIP skips
  the gate.

## Accuracy Tests

No numerics -- which configurations are accepted changes, no computed value does. One
unit case over accepted and rejected arch triples in the existing DCP constraint file;
the existing golden-resolution file gains the end-to-end shape of #40558 (SM120, no DSA
flag, both KV dtypes). Two pre-existing assertions that paired `trtllm` with an
unsupported device now mock an accepted arch.

Measured on head `65707fcef4` (base `58214f648c`) on an 8xH20 node (cc 9.0) and an
8xRTX PRO 5000 node (cc 12.0), both sglang 0.5.22 / flashinfer 0.7.1 / torch 2.14.1, by
replacing the installed `overrides.py` functions with this branch's, asserting the gate
is in the module the test process imports, then restoring the files:

- SM120 with nothing mocked refuses `trtllm` for FP8 and BF16 KV and accepts a
  non-`trtllm` pair; the golden-resolution method with the new SM120 cases goes
  `ran=1 failures=0` with the patch to `failures=2` without it on both nodes, both on
  `ValueError not raised` at the new sub-tests; the negative control against
  `origin/main`'s checker goes 0 -> 5 failures, all of them the new assertions.
- TileLang FP8 suite 8/8 with the patch on both nodes -- the ordering claim above, on a
  device -- and the device-gate case passes `(10,0)/(10,3)/(10,7)`, refuses
  `(10,1)/(12,0)/(12,1)/(11,0)/(9,0)`.

The two DCP default errors in both arms are the container's `_dsa_dcp_overrides` not
consulting `is_hip`: unrelated to this patch, expected to pass on the CPU lane, which
builds from main. The host's flashinfer 0.7.1 answers `requires SM100/SM103` for
`(10,0), (10,3)`; the set and message here follow the pin's 0.7.2.

- lingxling · comment · 2026-11-02T03:37:36Z · [source](https://github.com/sgl-project/sglang/pull/47237#issuecomment-6568452774)

Data point from an RTX 5090 (SM120, cc 12.0) on the official v0.5.23 image (flashinfer 0.7.2, sgl-flash-mla 1.0.0, tilelang 0.1.12). Config-only DeepseekV32ForCausalLM (V3.2 attention and indexer dims, 4 layers, 16 experts), --load-format dummy, TP1, one 32-token and one 3000-token request (index_topk=2048), 16 decode tokens each:

| KV cache | DSA prefill / decode | result |
|---|---|---|
| fp8_e4m3 (default) | trtllm / trtllm (auto) | dies at startup: `TllmGenFmhaRunner ... Unsupported architecture` |
| bfloat16 | flashmla_sparse / trtllm (auto) | dies at startup: `Sparse Attention Forward Kernel is only supported on SM90a and SM100f architectures` |
| fp8_e4m3 | flashmla_sparse / flashmla_sparse | same FlashMLA error |
| fp8_e4m3 | flashmla_kv / flashmla_kv | `CUDA error: no kernel image is available` (get_decoding_sched_meta) |
| bfloat16 | tilelang / tilelang | `Failed to set the allowed dynamic shared memory size to 231680` |
| fp8_e4m3 | tilelang / tilelang | starts; both requests decode 16 tokens |

So with no DSA flag the launch is accepted and then dies during startup, which matches the motivation here. One addition: on SM120, tilelang for both phases with FP8 KV does start and decode, so the refusal message could point SM12x users to `--dsa-prefill-backend tilelang --dsa-decode-backend tilelang` with FP8 KV. I only checked that it runs (random weights), not its accuracy.


- xulunfan · comment · 2026-11-02T05:36:19Z · [source](https://github.com/sgl-project/sglang/pull/47237#issuecomment-6569937360)

Thanks -- that matrix is the clearest picture of the SM120 backend surface I've seen, and the last row is actionable. Amended it into the PR: the refusal now names `--dsa-prefill-backend tilelang --dsa-decode-backend tilelang --kv-cache-dtype fp8_e4m3` and marks it as unvalidated for accuracy, since only startup and decode were exercised. A test now pins that the combination the message names really passes these checks on SM120, so the pointer cannot drift away from the gate.

Your table also shows the gate is narrower than the crash surface in two ways I would rather not silently widen here: `flashmla_kv`/`flashmla_kv` and the `flashmla_sparse` arms are accepted by these checks on SM120 yet die in your runs, and naming tilelang for only one phase escapes the gate under bf16 KV, because the mixed-layout check returns early on dtype. Happy to track the whole matrix in this PR if maintainers want that; otherwise the scope stays on the auto-selected default, which is what makes a launch with no DSA flag crash.
