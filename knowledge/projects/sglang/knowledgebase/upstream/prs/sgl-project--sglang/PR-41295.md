# [Perf] Skip unused K/V work in Gemma3n shared attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/41295) · state: closed · merged: False

## Original PR description

## Motivation

Gemma3n shared-KV attention layers compute packed Q/K/V and then discard K/V. E2B has ten such consumers. Keep only the useful Q projection and avoid allocating and rotating dummy keys on supported CUDA RoPE kernels.

## Modifications

- Preserve the `qkv_proj` parameter name and split/fused checkpoint interfaces with a model-local column-parallel Q projection. Producer layers, KV owner IDs and cache writes are unchanged.
- Keep packed QKV for quantized models, LoRA, and direct-state checkpoint formats (`sharded_state`, `remote`, `remote_instance`). Their scales, adapter buffers or direct copies rely on the original layout.
- Pass an empty K view to supported NVIDIA RoPE kernels. Other platforms and fallback kernels retain the previous call; the FP32 RoPE cache and partial-RoPE arithmetic are preserved.

This is limited to Gemma3n. Gemma4 Q-only work in #25461 and the separate Gemma3n attention-output fix in #37515 are not included.

## Accuracy Tests

- Pre-commit passes on all changed files. A full-repository run also passed all non-Rust hooks; four Rust hooks could not run because this host has no `cargo`/`rustup`. No Rust files are changed.
- New unit suite: 4 tests passed, including all simulated TP1/2/4 ranks, bias on/off, split/fused weights, producer/consumer and fallback layouts, and FP8 checkpoint scales. TP sharding was tested with CPU tensors; distributed inference was not run.
- New RoPE regression: 8 cases passed (FP16/BF16, partial/full RoPE, eager/CUDA Graph), plus 288 diagnostic exact-parity checks for the E2B head shape, strided inputs and positions through 32767.
- Full checkpoint text-path runs: 16 fresh processes across two H100 allocations, four workloads each. All 64 saved correctness outputs (one per process/workload) have bit-identical logits and generated tokens across baseline/candidate and allocations. All 7,168 decode calls used CUDA Graph.

## Speed Tests and Profiling

H100, BF16, FA3, TP1, full decode graph buckets 1/4, eager prefill, radix cache disabled, max total tokens 8192, memory fraction 0.70. First allocation used upstream `f337f01b80`; second used `cf5df82680` (Gemma3n/linear/RoPE sources unchanged). Torch 2.13.0+cu130, Transformers 5.12.1, sglang-kernel 0.4.7, FlashInfer 0.6.18.

Allocation 007 verifies the final candidate's source hashes. Allocation 005 tested an earlier candidate hash whose exact overlay bytes were not retained; it is supporting evidence, not an exact-source replication of this head.

Each allocation used eight independent checkpoint loads and graph captures, ordered `ABBABAAB` and `BAABABBA`. Each workload had three warmups and twelve timed requests per process. Each request generated eight tokens; its seven-step decode wall time is divided by seven to report milliseconds per decode step. The table uses the median of four process medians per arm. Inputs repeat the tokenized text “The quick brown fox jumps over the lazy dog. Explain what happens next.” to the indicated length.

All workload medians and balanced four-process block differences favor the candidate in both allocations. These are small model-runner gains with uncertain magnitude: three of allocation 007's process-bootstrap intervals include zero, and its slow B06 process is retained. Prefill is noisy and no stable prefill gain is claimed.

Timing includes CPU dispatch, synchronization and token/logit clones; this is not a serving-throughput or production tail-latency claim. An earlier same-runner dual-graph experiment failed with illegal memory access and was excluded; all separately captured process runs completed normally. No profiler was attached to timed runs.
