# [Feat] sgl-router: Continue W3C traces, record and forward request IDs, mark errors on spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/44805) · state: open · merged: False

## Original PR description

## Motivation

- The gateway's `http_request` span always starts a new trace, even when the caller sent a `traceparent`, so the caller's trace and SGLang's are disconnected.
- A request the gateway rejects (no worker, rate limit, bad request) never reaches an engine, so the gateway's span is the only record of it, and that span carries no request ID a caller would know.
- 4xx/5xx responses aren't marked on the span, so samplers and alerts that key on errors can't see gateway failures.

The existing `--request-id-headers` doesn't cover the second point: it picks the first matching header as a single `request_id` (generating one if none is present) for correlation inside the gateway. It doesn't record the raw values of several IDs, and the engine never sees what it picked.

## Modifications

1. **Continue incoming W3C traces and record request IDs.**
   - `RequestSpan` sets the span's parent from an incoming `traceparent` (`extract_trace_context_http`).
   - Request headers named in `SGLANG_TRACE_REQUEST_HEADERS` are recorded on the span as `http.request.header.<name>`, cut to 1024 bytes. This is the same variable, attribute name and limit as the engine (#<request-headers PR>), so one setting covers both. Header values are visible ASCII, so bytes and characters agree.
   - Headers named in `SGLANG_TRACE_REQUEST_HEADERS` or the existing `SGLANG_LOG_REQUEST_HEADERS` are forwarded to workers, so the engine can record or log them too.
   - `ResponseLogger` records an `error` attribute on 4xx/5xx (the router's error code, or the HTTP reason phrase) and sets `otel.status_code=ERROR` on 5xx only, following the OpenTelemetry HTTP conventions for server spans.
2. **Don't forward hop-by-hop and framing headers named in those lists.** If a list names a hop-by-hop header (`host`, `connection`, `transfer-encoding`, `proxy-authorization`, ...) or `content-length` (say, to log it on the engine), copying the client's value onto the request the gateway builds for the worker would misroute or misframe it. Those are skipped with a warning, reusing the hop-by-hop list the gateway already applies to worker responses (`should_forward_header_no_alloc`). Other listed headers are recorded and forwarded as configured.
3. **Docs** in `production_request_trace.mdx`.

### Behavior changes

- `http_request` spans join the caller's trace when a valid `traceparent` is present; before, they always started a new one.
- 4xx/5xx responses record `error`; 5xx responses mark the span as an error.
- With neither header variable set in the gateway's environment, no headers are recorded and forwarding is unchanged.
