# [Fix] hicache: Preserve sparse restore checkpoints under host pressure

[Upstream PR](https://github.com/sgl-project/sglang/pull/46954) · state: open · merged: False

## Original PR description

## Motivation

A hybrid L3 hit can be restorable only at sparse endpoints because it needs both a contiguous KV prefix and a trailing state/window snapshot. A smaller prefix is not necessarily another valid hit.

For example, a query can find complete checkpoints at pages 16 and 32. If host staging has room for only 24 pages, cache-mode partial allocation currently clips the hit to page 24. The subsequent trailing-pool read then targets a checkpoint that the query did not establish. The existing completeness check correctly rejects an incomplete restore, but the usable 16-page checkpoint is lost and KV reads can be wasted.

## Modifications

- Keep the common restorable endpoint set after the existing cross-rank query reduction, rather than keeping only its maximum and leaving a rank-local set behind.
- When partial host allocation is necessary for a trailing-pool restore, select the largest common endpoint that fits the capacity bound before allocating any partial buffers. If no endpoint fits, use the existing host-capacity cleanup path without submitting the read.
- Treat an `assume_stored` trailing hit as proof of its original endpoint only; it cannot establish intermediate checkpoints without a query. Plain KV retains its contiguous-prefix fast path.
- Size cache-mode auxiliary staging from the selected restore length.

This preserves the all-pools completeness check, existing allocation ownership, and the current collective sequence. Full-hit allocation and `allow_partial=False` retain their existing behavior. Buffer-only head trimming continues to preserve the original sidecar endpoint; PP keeps its existing capacity-capped checkpoint vote. No backend/storage format or serving configuration changes are included.

- The existing buffer trim/stage regression also passed its 8 combinations. A separate shared-host real-pool neighbor was blocked by the existing host-memory reserve guard on this Mac, before reaching the behavior under test; it is not counted as passing.

The local macOS CPU process uses the repository's complete `_platform_stubs.py` and `maybe_stub_sgl_kernel()` for GPU-only imports. The MPS availability override is limited to compatibility installation and is restored before importing/running the targets; tensors and assertions run on CPU. This adapter is not part of the patch. New query tests mock the unrelated Linux-only native hash boundary. Target controller/cache methods are imported directly, not copied or AST-extracted.

In a configured Linux development environment, the added tests can be run with:

```bash
python3 test/registered/unit/mem_cache/test_hybrid_storage_sparse_allocation.py -v
python3 test/registered/unit/mem_cache/test_pp_prefetch_ticket.py TestPPPrefetchTicket.test_sparse_checkpoint_vote_does_not_invent_capacity_endpoint -v
```

The tests directly import the production controller/cache methods and use CPU tensors. Host capacity, storage queries, and collective boundaries are controlled test inputs; they do not reproduce a real allocator-pressure history or a multi-process Store deployment.

GPU/model accuracy, the complete CPU suite, and a full Linux integration run have not been performed. No available GPU is required for the added unit tests.
