# [mem_cache] Free a chunked prefill's out-of-window SWA slots before sizing its next chunk

[Upstream PR](https://github.com/sgl-project/sglang/pull/41263) · state: open · merged: False

## Original PR description

## Motivation

On a hybrid-SWA model served with `--disable-radix-cache`, when the SWA pool is sized by `SWARequestCapPoolConfigurator`, a long prompt's chunks shrink after the second one. On MiMo-V2.6-Flash (window 128, `--chunked-prefill-size 4096`, `--max-running-requests 1`, overlap on), the SWA pool is 8,451 tokens. A 127,852-token prompt ran as 2 × 4,096 and then 258 and 3,968 alternating: 60 forwards instead of 32.

The cause is ordering. `PrefillAdder.add_chunked_req` sizes a continuing chunk from `SWAPrefillBudget.available_chunk_tokens`, which is the SWA pool's free count. At that point the previous chunk's out-of-window slots are still held: `ScheduleBatch.maybe_evict_swa` frees them only later, in `alloc_for_extend`. So when chunk 3 is sized, chunks 1 and 2 (8,192 slots) are both still allocated, and 258 is what's left.

`compute_swa_request_cap` already assumes those slots are gone by then. Under overlap it budgets two chunks plus one window (`chunks_in_flight = 2`), which is what is live when chunk N+1 is allocated while chunk N runs, once everything before chunk N's window has been freed. Without overlap it budgets one chunk, and the old order shrinks chunks there too (4096, 258, 3968, …; see the unit test).

## Modifications

- `mem_cache/common.py`: new `free_chunked_swa_before_plan()`. For a chunked request on an SWA cache that does not share prefixes (what `--disable-radix-cache` builds), it calls the cache's `evict_sliding_windows`, the same path `maybe_evict_swa` takes, with the same bound: `prefix_len`, and under overlap one chunk back (`prefix_len − chunked_prefill_size`, nothing before the third chunk), because the chunk in flight still reads the window before its start. It returns early for prefix-sharing caches and for a per-request SWA ring, whose chunks are not sized from the free count (`SWAPrefillBudget.available_chunk_tokens` skips `remaining_swa` for a ring).
- `managers/scheduler.py`: `_get_new_batch_prefill_raw` calls it before building the `PrefillAdder` whenever a chunked request is in progress. dLLM and PD disaggregation are skipped; I have not tested either.
- `environ.py`: `SGLANG_SWA_EVICT_BEFORE_CHUNK_PLAN` (default on). Setting it to 0 restores the old order. Happy to drop the flag if you'd rather not carry it.

So this frees exactly the slots `maybe_evict_swa` would free later in the same step, and that call then has nothing left to do. After a chunk cut short (e.g. by `shortest_prefill_chunk_limit`), that bound trails the chunk in flight, and what it frees is still enough: the slots held are then one chunk plus one window, which is what `compute_swa_request_cap` budgets. The unit test checks both.

## Accuracy Tests

The change moves chunk boundaries, so prompts longer than two chunks no longer get bit-identical output: different tokens share a forward. To check that the schedule is the only thing that changes, I ran a control: the old order with the SWA pool enlarged by one chunk, so the old planner produces the same full chunks. On the 127,852-token prompt the fix and the control gave identical output token ids and identical logprobs for all 64 output tokens, on each of two runs. Prompts that fit in two chunks were identical to the unpatched build.

This was tested end to end on a local build at `542a043` that also carries unrelated out-of-tree changes (a MoE expert offload path). Since then `main` has moved under the branch three times. The port onto `f92199b569` (2026-10-12) was the substantive one: #42822, #42824 and #42825 replaced `extend_range` and `Req.prefix_indices` with `prefix_len` / `extend_end`, and #43201 deleted `ChunkCache`. The latest rebase, onto `2c1e85964e` (2026-10-13), only resolved #43870's switch to `self.get_prefill_adder_class()`. The end-to-end run took the bound from the start of the chunk in flight; with full chunks that equals the bound above, which is what that run had at every step. The end-to-end numbers are from the original base; the unit test below was re-run on the new one.

## Speed Tests and Profiling

MiMo-V2.6-Flash, one RTX PRO 6000 Blackwell, one request, 127,852-token prompt, two runs each:

|---|---:|---:|
| prefill forwards | 60 | 32 |

| end to end (s) | 253.9 / 238.7 | 179.5 / 174.9 |
| decode, short prompts (tok/s) | 32.74 | 32.73 |

This box streams MoE experts from host memory and SSD (out of tree), so the absolute throughput is not representative. The forward count is the part that carries over.

## Unit test

`test/registered/unit/mem_cache/test_swa_evict_before_chunk_plan.py` runs on CPU. It drives one 33,644-token request through the real `SWATokenToKVPoolAllocator`, `UnifiedRadixCache` with `disable=True` (what `--disable-radix-cache` builds for a hybrid SWA model), `PrefillAdder.add_chunked_req` and `ScheduleBatch.maybe_evict_swa`, at the pool size `compute_swa_request_cap` gives (chunk 4096, window 128, page size 1, one running request):

- old order, overlap: 4096, 4096, then 258 and 3968 alternating (the sequence we saw in production);
- this change, with and without overlap: 8 × 4096 + 876, and with the third chunk cut to 1,000 tokens, 4096, 4096, 1000, 5 × 4096, 3972;
- after each early free, every slot the in-flight chunk reads is still mapped in the SWA pool, and the full pool is untouched;
- the `maybe_evict_swa` in `alloc_for_extend` then finds nothing left to free;
- a prefix-sharing cache, an SWA ring, a request without KV, and the first chunk in flight under overlap are each left alone (each case starts from a continuing request, so only the check under test can stop the free).

The test fails for each of eight mutations: no early free; the in-flight chunk's end as the bound; overlap ignored; a bound one chunk further back than `maybe_evict_swa`'s; and each of the four checks above removed. Upstream's unit tests that touch these paths (28 files, 3 of them on CUDA) give the same results as on `main`.

## Not covered

Page size > 1, several concurrent chunked or decoding requests, and the non-overlap path end to end (it is covered by the unit test only). The radix-cache path is unchanged, because the new function returns early for prefix-sharing caches; the scripted SWA chunked-prefill tests (`test_scripted_swa_1gpu.py`) run with the radix cache on, so they don't reach it.
