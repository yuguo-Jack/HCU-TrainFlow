# [Fix] model_loader: Avoid unsafe pickle fallback when loading PyTorch checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/42760) · state: open · merged: False

## Original PR description

## Motivation

`torch.load(weights_only=False)` deserializes with pickle, so a crafted checkpoint can execute code when it is loaded. `_load_pt_file` fell back to it for legacy tar checkpoints, and several loaders called `torch.load` on model files without `weights_only=True`. This is the same class of issue as #35653 (RIFE) and is consistent with the contribution guide's rule against unpickling untrusted data.

## Modifications

- Remove the `weights_only=False` fallback in `_load_pt_file` (`srt/model_loader/weight_utils.py` and `multimodal_gen/runtime/loader/weight_utils.py`). Legacy tar checkpoints now fail with torch's own error and should be converted to safetensors or a zip-format `.pt` offline.
- Pass `weights_only=True` to `torch.load` in `deepseek_ocr.py` (x2), `roberta.py` and `rife_interpolator.py`.
- Add unit tests for `_load_pt_file`: a tensor state dict still loads, and a pickle payload is not executed.
- `srt/debug_utils` is unchanged: it reads developer-written tensor dumps, not model weights.

## Accuracy Tests

Not applicable: only the checkpoint deserialization path changes; no model forward code is touched.

- nvpohanh · comment · 2026-10-13T03:26:21Z · [source](https://github.com/sgl-project/sglang/pull/42760#discussion_r4254390952)

File: `python/sglang/srt/model_loader/weight_utils.py` · line 1400

[by Claude Code] FYI: here is why removing the legacy `.tar` fallback looks safe. This applies to both `_load_pt_file` copies (`srt` and `multimodal_gen`).

**Where it came from**

Commit ceade7498c inside #16529, a CI test migration PR, added the fallback. Its commit message says it fixed the speculative decoding notebook, which "loads EAGLE models with legacy tar format weights". Nobody discussed it in that PR.

**Why that reason does not hold up**

- Every EAGLE draft in the docs and the CI test constants stores `pytorch_model.bin` as a zip file: `lmsys/sglang-EAGLE-llama2-chat-7B`, `lmsys/sglang-EAGLE-LLaMA3-Instruct-8B`, `lmsys/sglang-EAGLE3-LLaMA3.1-Instruct-8B`, `jamesliu1/sglang-EAGLE3-Llama-3.1-Instruct-8B`, `thunlp/LLaMA3-Instruct-8B-FR-Spec`, and `Tengyunw/qwen3_30b_moe_eagle3`. None of these repos has changed since November 2025, so they were zip files in January 2026 too. For a zip file, `torch.load` never reaches the tar code.
- On #16529, the Execute Notebooks job passed at d9e85bac45, the commit just before the fallback was added.
- torch raises the same "legacy .tar format" error for a corrupted file whose first 512 bytes are zero, because `tarfile` reads that as an empty archive. For such a file, the `weights_only=False` retry also fails, with `KeyError: filename 'storages' not found`. So the fallback could not have fixed that failure either. The CI logs have expired, so the real cause cannot be confirmed.

**What changes with this PR**

Only files that `tarfile` accepts behave differently. Real tar checkpoints come only from PyTorch 0.1.9 or older (before 2017). Files saved with `_use_new_zipfile_serialization=False` use the non-tar legacy format, and they still load with `weights_only=True`. I checked both versions of `_load_pt_file` with torch 2.14:

| File | main | this PR |
|---|---|---|
| zip state dict | loads | loads |
| legacy non-zip state dict | loads | loads |
| crafted tar file with a pickle payload | loads and **runs the payload** | `RuntimeError`, payload not run |
| corrupted file, first 512 bytes zero | `KeyError` | `RuntimeError` |

So this PR drops no checkpoint format that users load in practice, and it closes a code-execution path.
