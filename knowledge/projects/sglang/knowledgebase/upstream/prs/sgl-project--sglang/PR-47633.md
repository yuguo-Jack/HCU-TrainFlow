# [Feat] minimax-m3: Serve M3.1 NVFP4 MoE with DeepEP low-latency NVFP4 dispatch and CuteDSL masked GEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/47633) · state: open · merged: False

## Original PR description

## Motivation

MiniMax-M3.1 NVFP4 checkpoints currently serve their MoE layers only through MegaMoE (`--moe-a2a-backend megamoe`) or the routed TRT-LLM kernel. This PR adds a DeepEP expert-parallel path built on FlashInfer CuteDSL:

- DeepEP low-latency dispatch sends **pre-quantized NVFP4 activations with per-token FP32 scales**. That is 4-bit payload on the wire instead of BF16, with no requantization on the receiving rank.
- The FlashInfer CuteDSL **masked grouped GEMM** runs GEMM1 with SwiGLU (including the M3.1 clamped / `swigluoai` variant) and NVFP4 output quantization fused into the epilogue. The intermediate activation never round-trips through BF16 memory.

**Dependencies (this PR must land after them):**
- DeepEP: sgl-project/DeepEP#16. This adds `Buffer.low_latency_dispatch_fp4` with `per_token_scale` and swizzled scale output. A follow-up bumps the `sgl-deep-ep` wheel once it is released.
- FlashInfer: flashinfer-ai/flashinfer#7850 (fused gated activation in the masked grouped GEMM epilogue) and flashinfer-ai/flashinfer#7851 (NVFP4 output quantization in that epilogue).

There is no silent fallback. If the DeepEP build lacks `low_latency_dispatch_fp4`, or the FlashInfer build lacks the fused epilogue, startup fails with an explicit error.

## Modifications

- **`token_dispatcher/deepep.py`**
  - With `nvfp4_per_token_activation`, the LL dispatcher quantizes tokens with `flashinfer.nvfp4_quantize(per_token_activation=True)` (linear block scales, FP32 per-token scale).
  - It then calls `Buffer.low_latency_dispatch_fp4(..., per_token_scale=..., swizzle_scales=True)`.
  - `DeepEPLLDispatchOutput` gains an optional `per_token_scale`.
- **`flashinfer_cutedsl_moe.py`**
  - New `flashinfer_cutedsl_moe_masked_fused_swiglu`. GEMM1 uses `activation_type=Swiglu` with separate gate/up alphas, per-token activation scales and NVFP4 output; GEMM2 is the existing masked GEMM.
  - If an NVFP4 recipe override is set (`FLASHINFER_NVFP4_4OVER6`, disabled fast-math quantization), GEMM1 emits BF16 and a separate grouped quantize runs, so the dispatch and GEMM2 recipes stay consistent.
  - New `supports_masked_gemm_fused_swiglu()` capability probe (SM100/SM103 plus the FlashInfer API).
- **`moe_runner/flashinfer_cutedsl.py`**
  - `CuteDslFp4MoeQuantInfo` carries `w1_alpha_up` and the SwiGLU `(alpha, beta, limit)`.
  - The DeepEP fused function picks the per-token path when the dispatch output carries `per_token_scale`.
- **`quantization/minimax_m3_nvfp4.py`**
  - New CuteDSL weight processing. It reorders W13 to `[up; gate]` and interleaves 64-row halves for the fused epilogue, with block scales permuted the same way and then swizzled.
  - It derives per-expert gate/up alphas from the two W13 global scales and the GEMM2 alpha from the W2 input scale.
  - It builds a `FLASHINFER_CUTEDSL` MoE runner and configures the dispatcher for per-token NVFP4.
- **`arg_groups`**
  - `--moe-runner-backend flashinfer_cutedsl` is accepted for `minimax_m3_nvfp4` with `--moe-a2a-backend deepep`; DeepEP mode resolves to `low_latency`.
  - A startup check rejects configs whose prefill chunk / prefill graph / decode graph exceeds `SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK`. LL dispatch serves prefill too, so without this check the error would be a DeepEP assert during graph capture.
- **Tests**
  - New `test/registered/kernels/ops/moe/test_minimax_m31_nvfp4_cutedsl_moe.py` (single GPU, SM100) runs the full DeepEP-LL-format to CuteDSL MoE path against a dequantized reference. It covers uneven routing, an empty expert, distinct gate/up global scales, a non-unit W2 input scale, and NaN scales in unused rows.
  - Both fused-NVFP4-output and BF16-output GEMM1 are parametrized, plus a rejection test when the fused epilogue is unavailable.

Launch:

```bash
SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK=1024 \
python -m sglang.launch_server --model-path <MiniMax-M3.1 NVFP4> --trust-remote-code \
  --tp-size 8 --ep-size 8 \
  --moe-a2a-backend deepep --deepep-mode low_latency --moe-runner-backend flashinfer_cutedsl \
  --chunked-prefill-size 1024 --cuda-graph-max-bs-prefill 1024
```

## Accuracy Tests

Setup: 8x B200, TP8/EP8, colocated, decode CUDA graph + breakable prefill CUDA graph, FP8 KV cache. Built against DeepEP#16 and FlashInfer#7850 + #7851.

GSM8K (5-shot, 500 questions, greedy):

| MoE path | GSM8K |
|---|---|
| MegaMoE (default) | 0.964 |
| **DeepEP LL NVFP4 dispatch + CuteDSL fused SwiGLU (this PR)** | **0.960** |

Unit test: `test_minimax_m31_nvfp4_cutedsl_moe.py`, 3 passed.

## Speed Tests and Profiling

`bench_one_batch_server`, input 1024 / output 256, same setup:

| bs | MegaMoE (default) out tok/s | This PR out tok/s | MegaMoE TTFT | This PR TTFT |
|---|---|---|---|---|
| 1 | 108.1 | 103.3 | 0.11 s | 0.14 s |
| 8 | 799.7 | 721.5 | 0.12 s | 0.69 s |
| 32 | 2689.5 | 2445.9 | 0.42 s | 2.53 s |
| 64 | 4936.5 | 3410.6 | 0.74 s | 4.88 s |
| 128 | 9140.0 | 8172.6 | 1.48 s | 10.38 s |

On a single TP8 node, MegaMoE stays faster, and it remains the default. This path does not replace it; it adds a DeepEP expert-parallel option for M3.1 NVFP4.

The higher TTFT comes from DeepEP low-latency mode handling prefill: chunks are capped at 1024 tokens per rank, so prefill runs as many small LL dispatches.

Expected follow-ups:
- A DeepEP normal-mode prefill handler for this path.
- Disaggregated / multi-node deployments, where LL NVFP4 dispatch traffic is the bottleneck.
