# [Fix] penaltylib: Replay retained output tokens after retraction

[Upstream PR](https://github.com/sgl-project/sglang/pull/47252) · state: open · merged: False

## Original PR description

## Motivation

Fixes #47245.

`reset_for_retract` keeps a request's `output_ids`, and the re-prefill feeds them back as input. But `prepare_for_extend` builds a fresh `BatchedPenalizerOrchestrator`, so the request's frequency, presence and repetition rows start at zero and its `min_new_tokens` counter restarts at 0. From the retraction point on, the request is penalized as if it had generated nothing. Its output then diverges from an uninterrupted run with no error, and a `min_new_tokens` request can be held past its minimum.

## Modifications

- `penaltylib/orchestrator.py`: add `BatchedPenalizerOrchestrator.cumulate_output_history(rows, output_ids)`. It pads the histories with `vocab_size` and passes them to each prepared penalizer through a new `_cumulate_output_history` hook.
- Frequency, presence and repetition penalizers scatter the history into their rows. Frequency uses `scatter_add_` and the other two use `scatter_`, matching their per-step `_cumulate_output_tokens`. The padding column is dropped. `min_new_tokens` adds the history length to `len_output_tokens`.
- `ScheduleBatch.prepare_for_extend`: after building `sampling_info`, replay `output_ids` for requests that have them when a penalizer is active. For a normal first prefill `output_ids` is empty, so nothing changes. dLLM batches are skipped because they re-extend with `output_ids` on every block and don't sample through penaltylib.

Scope: this covers the regular re-prefill path. The PD decode-side prebuilt path (`prepare_for_prebuilt`) also builds a fresh orchestrator for retracted requests and could get the same treatment in a follow-up. I left it alone because I can't test PD here.

## Accuracy Tests

New `TestCumulateOutputHistory` cases in `test/registered/unit/sampling/test_penaltylib.py`:
- Replaying histories (including repeats) into some rows of a batch with all four penalizers gives the same additive and scaling penalties as cumulating the tokens one step at a time, and rows without history stay untouched.
- Retained tokens count toward `min_new_tokens`, so EOS is unmasked once the minimum is reached.

`pre-commit run` on the changed files passes. I ran CPU-only unit tests. I didn't run a server or the issue's end-to-end retraction repro, and I didn't test on GPU.

## Speed Tests and Profiling

No hot-path change: the replay only runs during prefill for requests that already have `output_ids` (retracted requests) and only when a penalizer is active.
