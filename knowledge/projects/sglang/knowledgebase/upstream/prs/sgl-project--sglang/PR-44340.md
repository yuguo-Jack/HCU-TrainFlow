# [Fix] hicache: Make the timeout prefetch policy rank-agreed and bounded on TP>1

[Upstream PR](https://github.com/sgl-project/sglang/pull/44340) · state: closed · merged: False

## Original PR description

## Motivation

`--hicache-storage-prefetch-policy timeout` is the default, but on TP>1 the Python path implements it in a way that is neither rank-safe nor bounded:

1. **One collective per waiting request per scheduler pass.** `check_prefetch_progress` voted on each polled request's deadline with its own all-reduce from inside the admission loop (`_can_terminate_prefetch`). The number of votes a rank issues depends on where it leaves the loop (`batch_is_full`, PREFILL-mode `available_size`), so ranks can enter different numbers of collectives (the #30760 class). Even when they agree, the cost scales with the queue: with 24 requests waiting on a slow `batch_exists`, py-spy put 26 % of scheduler samples inside that vote.
2. **The clock started at operation construction.** A request that sat behind others for seconds reached admission already expired, and `hash_value` is empty while the query is pending, so the per-token term never applied to a pending query (a flat 1 s).
3. **A cut re-armed a paced re-query with a fresh budget.** For a queued request whose L3 never answers, the default knobs (`retry_poll_interval=8`, `retry_max_attempts=8`) gave 9 issues and 9 cuts, i.e. ~9 x base before the request was admitted.
4. **A cut query healed storage-existence beliefs from fields the worker thread still owns** (`all_hash_values`, `query_pool_hit_pages`, `storage_hit_count`) before the MIN-reduced publication, so TP ranks could end up with different beliefs (one rank `[True, True]`, the other `[False, False]`), which later misaligns the rank-min ack drain. This is the deadline-cut variant of the #43108 class.

## Modifications

The policy now decides once per scheduler tick, in one collective, and the admission polls only read the verdict (`python/sglang/srt/mem_cache/unified_radix_cache.py`):

- `_retire_lapsed_prefetches` (L2200) runs from `check_hicache_events` right after the storage drain (L3639). It packs one `lapsed` flag per ongoing prefetch, in the rank-agreed `ongoing_prefetch` order, into a single MAX all-reduce (same sync shape as `_sync_hicache_ready_counts`: PP0 decides and broadcasts along PP, TP-wide only in PP ticket mode), then retires every lapsed operation on every rank in the same tick: `terminate_prefetch`, then `revoke_pending_prefetch` for a querying/parked operation or `_handle_prefetch_result` for a dispatched one (L2229). The collective count per tick is therefore 1 whenever any prefetch is ongoing, independent of how many requests each rank polls. `best_effort` and `wait_complete` do not run the vote.
- `_can_terminate_prefetch` under `timeout` issues no collective: it starts the attempt's budget at this first blocked poll (`_start_storage_prefetch_wait`, L2181) and returns the stored verdict (L2256). The budget is `prefetch_timeout_base + prefetch_timeout_per_ki_token * requested tokens / 1024`, measured from the first blocked admission poll (queue residence does not count), kept across re-issues of the same attempt (`_StoragePrefetchWait`, L176), and released at admission (`finish_storage_prefetch_admission`, also on the retracted-stain path of `PrefillAdder`), on abort (`release_aborted_request`), at the PD-decode consumer (`pop_prefetch_loaded_tokens`), on `reset`, and on detach.
- After a cut the budget is spent: the cut arms no `poll_miss`, cancels a pending retry, and `prefetch_from_storage` returns without a lookup for that attempt (L2020), so a device-hit-loss re-issue or a paced retry cannot start another storage query; the request is admitted and recomputes.
- A cut operation carries `deadline_expired` (`hybrid_cache_controller.py` `PrefetchOperation`). Neither the cut nor the later drain of its published query heals beliefs (`_invalidate_absent_from_hit_query`, L2781: a cut query's agreed hit may be a MIN over skipped lookups, not a verdict), the all-or-nothing hybrid discard keeps its KV/sidecar beliefs (`_check_hybrid_prefetch_result`, L2472), and the loss is reported under a new `deadline` reason of `storage_prefetch_unfulfilled_tokens_total` instead of `storage_transfer`/`dropped`.
- Docs: `hicache_design.mdx` described a `prefetch_timeout_max` knob and defaults that do not exist; the section now states the real knobs/defaults and the clock semantics above.

Behavior changes to be aware of: the per-token term now also applies while the query is pending (an 8k-token request gets 3.0 s instead of a flat 1.0 s under the defaults); a lapsed request is cut on every rank in the same tick instead of at its own poll; a never-answering lookup costs one budget instead of up to nine.

Relation to other work: this is the Python-path counterpart of the internal Rust-MCS fix (same `_StoragePrefetchWait`, packed vote, retry suppression and `deadline_expired` guards). It is independent of #43108 (belief handling at abort): it applies with or without it, and the two guards compose.

## Speed Tests and Profiling

CPU unit tests (prod_inference venv, upstream tree via `PYTHONPATH`):

- `test/registered/unit/mem_cache/test_storage_prefetch_timeout_policy.py` (new, 5 cases, ~27 s): two-rank gloo (real `prefetch_thread_func` workers on their own sync group): a deadline reached on rank 0 alone cuts the query on both ranks in two interleavings (peer still inside `batch_exists`; peer worker not yet dequeued) with beliefs identical and intact on both ranks after the cut and after the drain, no retry armed, no re-issue; ranks that leave the admission loop at different points (`batch_is_full`) still retire the same operations with exactly one collective each and both suppress the re-issue; single rank with a fake clock: the budget runs from the first blocked poll, a store-miss re-issue keeps it, the cut arms no paced re-query, is counted as `deadline`, and admission releases it; a mid-transfer hybrid (SWA) cut keeps KV and SWA beliefs and counts `deadline`; `best_effort`/`wait_complete` and every admission poll issue no collective; `check_hicache_events` votes once, after the drain.
- Existing suites: `test_storage_prefetch_lifecycle.py`, `test_pp_prefetch_ticket.py`, `test_buffer_mode_sidecar.py`, `test_hicache_pp_sync_drain.py`, `test/registered/unit/managers/test_prefill_adder.py`: 87 passed, 69 subtests; `test_unified_radix_cache_unittest.py -k "prefetch or timeout or storage"`: 89 passed, 137 skipped (GPU-only).

- Slow existence check (`batch_exists` delayed 3 s on every call; 24 L3-resident 6.2k-8.2k-token prompts replayed at once + 4 fresh 1.5k-token and 4 32-token canaries, 3 s py-spy record of TP0 at 100 Hz):

The higher TTFT on this branch is the per-token term now applying to a pending query (`1 + 0.25 * 8199/1024 = 3.0 s`), i.e. the documented formula; base cut at a flat 1 s plus skew.

- Hung transfer (`batch_get` blocks forever on rank 1 for the first replay; 1 + 8 + 6 replays in two waves, canaries, py-spy at 60 s): identical TTFT (2.5-3.0 s cuts, all replays recompute because the wedged rank never transfers again), identical `backuped_tokens`, identical query count (17 `batch_exists` per rank = one per request), `storage_prefetch_unfulfilled_tokens_total{reason="deadline"}` +64320 / +43264 where base reported `storage_transfer`; exactly one `HiCache prefetch deadline` line per replayed request per rank; no tracebacks.

Not run: PP>1, `cache` host-memory mode end to end, mooncake/hf3fs/nixl backends, PD disaggregation, multi-node. The repository CI was not triggered.
