# [Fix] glm-4.5/ling3: Fix quadratic regex scans in the tool-call parsers

[Upstream PR](https://github.com/sgl-project/sglang/pull/42574) · state: open · merged: False

## Original PR description

## Rebase update (2026-10-30)

Rebased onto `main` at `16a3bf3` (head `7afb4aa`). Main already contains a linear complete-block scan and an incremental GLM streaming matcher. This branch keeps both, anchors the matcher at the first opening tag to avoid retrying unclosed calls, retains the Ling3 whitespace guard, and replaces the argument-pair regex with a linear scanner. The existing regression tests remain, including the unclosed-tag case. Focused matcher and argument-scanner checks plus Python syntax checks pass on this head; the full unit module has not been rerun after the rebase.

## Motivation

`Glm4MoeDetector` (parsers `glm`, `glm45`) and its `Ling3Detector` subclass scan model output with patterns that go super-linear when a closing `</tool_call>` never arrives:

1. **Non-streaming:** `detect_and_parse` uses `re.findall(r"<tool_call>.*?</tool_call>")`, which rescans to the end of the text from every opening tag.
2. **Streaming:** `parse_streaming_increment` runs `_STREAMING_PARTIAL_PATTERN.search()` over the whole buffer on every chunk, retrying the same failing scan from each opening tag.
3. **Arguments:** `<arg_key>(.*?)</arg_key>(?:\\n|\s)*<arg_value>(.*?)</arg_value>` rescans to the end of the call from every `<arg_key>` that never gets a value.
4. **Ling3:** both of its patterns start with `<tool_call>\s*(.*?)`, which retries the lazy scan from every split of a whitespace run.

| Input | Parser | Before | After |
|---|---|---|---|
| `<tool_call> ` x 4000 (44 KB), non-stream | glm45 | 2.08 s | < 1 ms |
| same | ling3 | 2.05 s | < 1 ms |
| `<tool_call> ` x 1000, one stream chunk | glm45 | 0.20 s | < 1 ms |
| same | ling3 | 1.18 s | 2 ms |
| `<tool_call>` + 20,000 spaces, **one stream chunk** | ling3 | **19.3 s** | 3 ms |
| valid pair + 20,000 unpaired `<arg_key>a</arg_key>`, non-stream | glm45 | **77.5 s** | < 10 ms |

Tool-call parsing runs synchronously on the tokenizer manager's event loop, so one such response, which a user can elicit through the prompt, stalls every in-flight request. Found with an Atheris fuzzing harness that records per-input parse time.

## Modifications

- `Glm4MoeDetector._iter_tool_call_blocks`: a linear `str.find` scan that yields exactly the blocks `findall` returned. The now-unused `func_call_regex` attribute is removed.
- Streaming: `_STREAMING_PARTIAL_PATTERN.match(text, text.find(bot_token))` instead of `.search(text)`. Every successful match starts at a `<tool_call>`, and whenever a later tag could match the first one does too (the success condition is a suffix condition), so the leftmost match is unchanged.
- `_find_arg_pairs`: a linear scanner returning the same pairs as the argument regex's `findall`. It first records every `</arg_key>` that is followed by a value opener; each key then ends at the first such tag after it, which is exactly where the lazy regex stops. (#42575 adds the equivalent scanner for GLM-4.7; whichever merges second can share it.)
- Ling3: `(?:\s*(?=\S))?` instead of `\s*`. The first attempt is identical. The only matches it can drop have a whitespace-only function name, which the caller already treats the same as "no match" (keep buffering).
- Regression tests in `TestGlm4MoeDetector` (two) and `TestLing3Detector`. On `main` they take 131 s, 77.5 s and 37.7 s; with this change, ~0.01 s.

## Accuracy Tests

Differential test of the `main` vs patched detectors (both `glm4` and `ling3`), comparing `detect_and_parse` output and every `parse_streaming_increment` result under random re-chunking: **0 mismatches** over 60k random inputs plus 40k mutated well-formed tool calls (12.5k of which produced parsed calls).

`_find_arg_pairs` vs the regex's `findall`: identical on 600k random and structured strings (463k matches).

`test/registered/unit/function_call/`: 632 passed.

Not addressed here: the streaming XML-to-JSON state machine appends to `self._xml_tag_buffer` one character at a time, so a call is O(chunk length x buffer length) while waiting for a value. With token-sized stream chunks the per-call cost stays small, so I've left that state machine untouched.

## Speed Tests and Profiling

See the table above. A scaling probe (each token literal and each pair, repeated 2k/4k/8k times) finds no remaining super-linear input for `glm45` or `ling3`.

Related: #42573 (same issue class in the dots parser).
