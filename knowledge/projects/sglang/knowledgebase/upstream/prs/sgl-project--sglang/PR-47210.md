# [Perf] [SM120] fp8: Use native block32 DeepGEMM for DSV4.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/47210) · state: open · merged: False

## Original PR description

## Motivation

#42604 added native block32 DeepGEMM on SM90; #45585 enabled explicit UE8M0
block32 selection on SM100. Extend that explicit route to SM120/SM121 for
DeepSeek-V4.1 dense FP8 weights with `--fp8-gemm-backend deep_gemm`.
The `auto` policy, MoE, attention, and existing SM90/SM100 kernel behavior are unchanged.

## Modifications

- Require explicit DeepGEMM, checkpoint `scale_fmt: "ue8m0"`, `[32, 32]` blocks,
  BF16 output, `N % 8 == 0`, and `K % 32 == 0`. Unsupported cases retain Triton.
- Preserve canonical FP8 weights and FP32 `weight_scale_inv`, including their
  shapes and storage. Pack qualifying normal power-of-two scales (`>= 2^-126`)
  into a non-persistent INT32 `_deepgemm_block32_weight_scale` buffer; this is
  layout-only, not requantization. Subnormal scales retain the Triton route.
  `keep_plain_weight_layout` layers do not create this buffer.
- Call `fp8_fp4_gemm_nt` with `recipe_a=recipe_b=(1, 32)` and
  `disable_ue8m0_cast=True` for packed block32 operands. Unpacked scales and other
  recipes retain `fp8_gemm_nt`; other linear runners read canonical scales.
- Refresh packed buffers with `copy_()` to preserve CUDA Graph addresses; reject
  eligibility/layout transitions. Online tensor/distributed weight updates reject
  this runner before any write because those APIs do not refresh packed scales.
  Use explicit Triton for online updates.
- For sharded-state loading, defer this runner's postprocessing until canonical
  checkpoint tensors have been copied, then rebuild the non-persistent scales.
  Other quantization methods retain their existing pre-copy processing order.
- Unpack MN-major packed scales correctly for singleton rows/columns, including
  contiguous tensors whose last stride is not one; retain block128 fallback behavior.
- Precompile the actual SM120/SM121 packed call and scale transforms. Preserve
  existing SM90/SM100 and block128 warmup calls. Check `fp8_fp4_gemm_nt` availability
  before enabling this route; the existing `sgl-deep-gemm==0.2.3.post2` pin is unchanged.
- Preserve buffer persistence through weight-cache IPC export/import, preventing
  derived scales from entering client sharded checkpoints. Legacy metadata keeps
  its previous registration semantics; payloads and zero-copy transport are unchanged.

### Related work and review scope

- #45391 and #45262 add FlashInfer b12x routes on SM12x. This is a separate explicit
  DeepGEMM route; its native K alignment is 32 rather than b12x's 128. No performance
  comparison against b12x has been run, and this PR does not change backend policy.
- #45632 already supports packed MXFP8 producer inputs for selected projections;
  this change covers explicit dense block32 linears, their lifecycle, and warmup.
- The IPC persistence correction overlaps with #36156 and is isolated in a separate
  commit for reuse or a prerequisite PR, subject to maintainer/author coordination.
  This PR does not broaden IPC quantization admission or establish full-model parity.
- That commit is independent of the quantization change and is the only part of this
  PR that reaches `python/sglang/srt/weight_cache`. If reviewers would rather keep it
  with #36156, dropping that one commit leaves the other three and their tests intact.

## Accuracy Tests

### Regression and lifecycle coverage

Tests cover selection and refusal conditions, canonical storage, bit-exact scale
round-trips, native output with Triton fallback forbidden, pointer-stable refresh,
CUDA Graph replay after scale/input mutation, both eligibility transitions,
non-DeepGEMM readers, `auto`, online-update rejection before writes, and real
Triton fallback. Wrapper tests cover packed/unpacked entrypoints, actual warmup
arguments, memory bounds, and incomplete DeepGEMM APIs.

Follow-up CPU tests exercise the subnormal/normal scale boundary, single-row and
single-column packed layouts, and a real `ShardedStateLoader` round-trip with
`Fp8LinearMethod`; model assembly, platform/rank setup, and the DeepGEMM layout
transform are mocked. GPU tests use real `Fp8Config` selection for checkpoints
without UE8M0, compare RHS recipes `(1, 32, 32)` and `(32, 32, 32)` in the same
process for shape/stride/bytes/unpacking/native output, and rebuild packed scales
from canonical sharded tensors before native execution. The SM120 test guard
independently probes hardware/package APIs and fails, rather than skips, when
compatible APIs exist but production flags are disabled.

The measured tree, based on upstream `8fabf5e65c`, was validated on RTX PRO
5000 72 GB with PyTorch 2.14.1+cu130, CUDA 13.0, and isolated
`sgl-deep-gemm==0.2.3.post2`. All 9016 Python/test source files matched the
measured snapshot; every imported SGLang module came from that tree, not the
host's installed SGLang. CPU runs explicitly confirmed zero visible GPUs. The
backend-file rows date from 2026-10-28. The FP8 utility and CPU rows were
re-measured on 2026-10-29 after the gate tests were consolidated, from the same
snapshot with that one test file hash-verified against the pushed revision.

The branch has since been rebased onto `2c362af4cc`. `git range-diff` reports no
change to the four patch bodies; the hardware numbers above were not re-measured
on the rebased tree, and GitHub CI is what covers the current head. One earlier
head was red on `base-a-test-cpu` for a reason outside this PR: upstream

### Limited full-model accuracy evidence

A matched full-model comparison ran on 2026-10-28/29 with DeepSeek-V4.1-Flash-1017,
8 x RTX PRO 5000 72 GB, TP=8/EP=8. Both arms used the measured tree, the same
checkpoint, the same pinned runtime (`sgl-deep-gemm==0.2.3.post2`,
`flashinfer-python==0.7.2`, `sglang-kernel==0.4.10`, `sgl-flash-mla==1.0.0`,
`deepseek-recipe==0.2.0`), and the same source snapshot hash. Launch arguments
were byte-identical except `--fp8-gemm-backend`, and the launch environment
differed only in the audit harness's run-directory and backend-label variables.
Each arm loaded 210 dense block32 layers on all 8
ranks with no foreign SGLang imports, and both DeepGEMM boots recorded the native
call on every rank with `recipe_a=recipe_b=(1, 32)`, `disable_ue8m0_cast=True`,
and INT32 scales; the Triton boots recorded no native calls.

Full GSM8K test split (1319 questions), plain completion, temperature 0, seed 7,
`max_new_tokens=512`, fixed batch 16, identical question IDs and prompt hashes,
scored on the final number:

| Comparison | Correct | Discordant pairs | Exact two-sided McNemar p |
|---|---|---|---|
| Triton A-A, same engine | 1200 → 1210 | 31 / 41 | 0.289 |
| Triton vs DeepGEMM | 1200 → 1187 | 47 / 34 | 0.182 |

The same-engine A-A round already changes 976 of 1319 response texts and moves
the score by 10 questions, so the DeepGEMM arm's 13-question difference sits
inside that floor; the A/B round changes 1015 texts. This is a task-level paired
comparison on one benchmark, not a proof of equivalence or a full-capability
evaluation. MMLU was not run: in the test environment the dataset archive
transfers at roughly 20 KB/s and the dataset API host is unreachable, so no MMLU
evaluation file exists.

Both arms required one independently isolated prerequisite, applied identically
to each arm and **not part of this PR**: #47209, where on SM120/SM121 the V4.1
candidate indexer reuses the existing dense blocks backend when sparse-table
kernels are absent, and full-topk decode honors the torch schedule flag. Without
it, both arms fail before readiness because SM120 passes the indexer's
`capability[0] >= 10` check while the paged-sparse MQA capability requires SM100.
The results therefore validate the measured tree plus that declared prerequisite.

## Speed Tests and Profiling

Matched interleaved boots on the same host and workload as the accuracy run, in
the order Triton (two measurement runs), DeepGEMM, Triton, DeepGEMM: synthetic
random `input_ids` excluding special IDs, `in1024/out128`, `ignore_eos`,
temperature 0, seed 7, streaming. Output tokens come from
`meta_info.completion_tokens`; the prefix cache was flushed before each warmup
and each measured level, and every measured request reported
`prompt_tokens=1024`, `completion_tokens=128`, `cached_tokens=0`.

| Concurrency | Triton output tokens/s (2 boots, 3 runs) | DeepGEMM output tokens/s (2 boots) | Delta of medians |
|---|---|---|---:|
| 1 | 39.49 / 39.46 / 39.34 | 101.28 / 100.68 | +156% |
| 8 | 341.5 / 338.5 / 341.1 | 457.5 / 449.2 | +33% |
| 96 | 850.7 / 866.8 / 850.6 | 1003.5 / 1031.6 | +20% |

| Concurrency | Triton TPOT p50 | DeepGEMM TPOT p50 | Delta of medians |
|---|---|---|---:|
| 1 | 24.66 / 24.67 / 24.68 ms | 9.20 / 9.19 ms | -62.7% |
| 8 | 18.31 / 18.61 / 18.43 ms | 13.40 / 13.64 ms | -26.7% |
| 96 | 70.22 / 67.32 / 69.57 ms | 59.68 / 59.80 ms | -14.1% |

Same-engine repeats differ by at most 2.8% on throughput (Triton 1.9%,
DeepGEMM 2.8%, both at concurrency 96), so the gaps exceed that spread. These are
synthetic requests on one model and one host, not customer traffic, and
native-kernel and prepack contributions were not separated.

Kernel attribution comes from an earlier pre-rebase candidate on the same model
and hardware, with a different request driver, so it explains where the time goes
but does not validate the final lifecycle/warmup changes. Matched TP-rank-0
traces: 60 scheduler steps, concurrency 8, `in1024/out512`, 200 requests, seed 99;
includes extend work, not decode-only.

| Summed kernel durations (pre-rebase candidate) | Triton | DeepGEMM | Delta |
|---|---:|---:|---:|
| Dense GEMM family | 405.13 ms | 111.34 ms | -72.5% |
| All GPU kernels | 1352.6 ms | 1048.6 ms | -22.5% |

Each arm has 12,600 main GEMMs. The DeepGEMM family includes 2,400 split-K
reductions (10.78 ms); scale transforms/activation quantization are included only
in the all-kernel sum. These sums are not utilization or non-overlapping busy time.
These are not cold-prefix results; the prefix-reusing throughput ladder is
excluded.
