# [Fix] sglang-server: Keep the matched stop token in output_ids

[Upstream PR](https://github.com/sgl-project/sglang/pull/42637) · state: closed · merged: True

## Original PR description

## Motivation

The Rust detokenizer pops a matched stop token from the chunk's token IDs before decoding, so the token disappears from the decoded text and also from `output_ids` in `/generate` and gRPC responses. The Python detokenizer trims the stop token only from the IDs it decodes and passes `output_ids` through unchanged. The two servers therefore return different token IDs for the same request, and clients that count or replay `output_ids` (RL rollouts, token-in/token-out pipelines) see a missing final token in Rust mode.

## Modifications

- The matched stop token is left out of the decode slice only. The scheduler's token IDs, and therefore `output_ids`, stay intact.
- Text trimming, `no_stop_trim` and `completion_tokens` are unchanged, except that a matched stop token id 0 is now trimmed like any other. Python has done so since #41590 (`if matched is None`); the Rust guard predated that change.
- Chunk events record when their last token ID was left out of the text. Chat passes reasoning parsers the IDs without that token (`stop_trimmed_token_ids()`), because the GPT-OSS parser builds content from token IDs and the raw IDs would put the stop token back into chat content. Parsers therefore see the same IDs as before this PR.
- Out of scope: with `--tool-call-parser gpt-oss`, Python keeps `<|call|>` (200012) for the tool parser. Rust mode doesn't support that tool parser yet (it isn't mapped to Dynamo's `harmony` parser), so that exception is left to a follow-up.
- Tests: `stop_token_is_preserved_in_output_ids` replaces `stop_token_trimmed_from_output_ids` and covers stop id 0; `stop_trimmed_token_ids_exclude_only_a_trimmed_stop_token` covers the parser view with and without a trimmed stop token.

## Tests

- In `rust/`: `cargo test -p sglang-server` (334 passed) and `cargo clippy -p sglang-server --all-targets -- -D warnings` is clean.
- `pre-commit run --from-ref origin/main --to-ref HEAD`: all hooks pass.
- Real server on one A100 (Llama-3.2-1B-Instruct, `SGLANG_RUST_SERVER=1`), together with the related Rust-frontend PRs, greedy `/generate` on a chat prompt: `text` is `"No."` and `output_ids` is `[2822, 13, 128009]` with `finish_reason {"type": "stop", "matched": 128009}`, so the stop token now appears in `output_ids` while the text stays trimmed. On current main, the same request returns `output_ids` `[2822, 13]` in Rust mode and `[2822, 13, 128009]` from the Python server; `completion_tokens` is 3 in both, and with `no_stop_trim` both already return the stop token. This ran on the first revision; the review changes (renames and the id-0 case) don't affect it, since this model's stop token is 128009.

Rust mode also can't serve gpt-oss tool calls yet: `dynamo_parser_name` doesn't map `gpt-oss` to Dynamo's `harmony` parser, so requests with tools are rejected with "tool-call parser `gpt-oss` is not supported by Dynamo".
