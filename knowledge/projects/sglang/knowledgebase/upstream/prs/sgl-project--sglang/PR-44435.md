# [NPU] Batch Qwen3-VL vision encoding across requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/44435) · state: open · merged: False

## Original PR description

## Motivation

Cross-request image batching in `mm_schedule.py` merges same-round per-image
cache misses into a single ViT forward, amortizing kernel launch/scheduling
overhead. NPU was fenced off from this path (grouped with HIP/XPU onto the
per-request path); the code comment cites a ROCm regression and a conservative
blanket disable — there is no NPU-specific measurement behind it.

Qwen3-VL is a safe candidate to open up: its `get_image_feature` natively
accepts a list of `MultimodalDataItem` and packs multiple images' `grid_thw`
into one visual forward, so no model-side change is needed. The existing
CUDA-path guarantees carry over: dedup by `(hash, token_count)`, embedding
cache backfill, and `sort_by_req_idx` reassembly keep every request's outputs
attached to its own images.

While validating on NPU we also found the batched encode call has no bound:
every cache miss in a scheduling round goes into one ViT forward, so workspace
scales with arrival burstiness (a wave of large images can spike several GB).
This PR therefore also adds a per-call ViT token budget to cap it.

## Modifications

1. **`mm_schedule.py`: open cross-request batching for NPU + Qwen3-VL.**
   Replace the blanket `_is_hip or _is_npu or _is_xpu` check with
   `_can_batch_cross_request_image_misses()`: CUDA unchanged; HIP/XPU stay on
   the per-request path; NPU is enabled only for
   `Qwen3VLForConditionalGeneration` and `Qwen3VLMoeForConditionalGeneration`
   (dense verified on device; MoE shares the same `get_image_feature`
   interface). `is_per_image` admission and the split/backfill logic are
   untouched.
2. **`environ.py` + `mm_schedule.py`: per-call ViT token budget.**
   New `SGLANG_MM_CROSS_REQUEST_BATCH_TOKEN_BUDGET` (default 4096, `<=0`
   disables). `_chunk_misses_by_token_budget()` greedily splits cache misses
   into groups whose total token count fits the budget and encodes them one
   group per call; an oversized single image forms its own group.
   Dedup/backfill/cache logic is unchanged.
3. Unit tests for the batched path (two requests merged into one call, outputs
   asserted split-per-request and equal to per-request reference).

## Accuracy Tests

- `test/registered/chunked_prefill/test_mm_chunked_embedding_unit.py`:
  **29 passed** (run in-container on Ascend 910).
- End-to-end A/B on Ascend 910 / Qwen3-VL-4B-Instruct (CANN 9.1.0-a3): 8
  fixed-seed image cases, identical inputs across baseline (per-request) and
  treatment (batched), `max_tokens=48`. **No cross-request contamination** —
  every caption describes its own image. 5/8 cases show benign wording drift
  after ~30 tokens ("identifiable/recognizable" level), expected from
  batch-variant numerics (reduction order changes); batching is not
  bit-invariant by design.

## Speed Tests and Profiling

Environment: Ascend 910 (64GB HBM), CANN 9.1.0-a3, Qwen3-VL-4B-Instruct,
`--attention-backend ascend --chunked-prefill-size 8192 --max-running-requests
64`, `mem-fraction-static 0.80` unless noted. Repo-standard
`sglang.bench_serving` with the `image` dataset (unique random JPEG per
request, all cache misses), same seed for A/B rounds; the only difference
between rounds is `mm_schedule.py`.

| Workload | TTFT mean | TTFT p99 | Throughput | E2E mean |
|---|---|---|---|---|
| 448², out=32, c16 | 1190 → 629 ms (**-47%**) | 5143 → 2467 ms (-52%) | 9.19 → 13.83 req/s (**+50%**) | -34% |
| 448², out=32, c32 | 3508 → 548 ms (**-84%**) | 5304 → 644 ms (-88%) | 7.60 → 27.68 req/s (**+264%**) | -73% |
| 1920×1080, out=256, c42 | 7496 → 7356 ms (-1.9%) | 14584 → 12831 ms (**-12%**) | 2.06 → 2.12 req/s (+2.4%) | -2.9% |
| 1920×1080, out=256, c16 | 3007 → 2995 ms (±0.4%) | 4546 → 4529 ms (±0.4%) | 4.64 → 4.67 req/s (+0.6%) | ±0.5% |
| Mixed 448²+1080p (16+16 c), small side | 1069 → 648 ms (**-39%**) | 3819 → 3479 ms (-9%) | 6.21 → 7.28 req/s (**+17%**) | -15% |
| Mixed, large side | 3705 → 3332 ms (-10%) | 6868 → 6235 ms (-9%) | 2.80 → 3.02 req/s (+8%) | -7% |

ViT call count (mechanism evidence):

| Workload | Baseline | Batched |
|---|---|---|
| 1080p c42 | 153 calls, all single-image | 48 calls for 153 images, max 4-in-1 |
| 448² c32 | 128 calls | 16 calls, max **19-in-1** |
| Mixed | 385+192 calls | 75+57 calls, incl. 3 genuine mixed batches (8S+1L ×2, 2S+4L) |

Findings:
- Gains scale with per-image ViT token count (small = more launch overhead to
  amortize), decode share (dilutes prefill gains), and same-round batchable
  images (arrival pattern). Small images + short outputs + high concurrency is
  the sweet spot; large images under steady pressure gain 2~4% with the best
  tail improvement (p99 -12%).
- Mixed workloads: net win with a bounded convoy effect — ~6% of small-image
  requests overlapping a large-image ViT window see TTFT dragged to ~3.5 s
  (one large-image ViT duration, hard-capped; p50 unaffected at 422 ms). The
  baseline per-request path shows the same effect at higher severity (9.4% of
  requests >3 s vs 5.8% batched), so this is not introduced by batching.
- Concurrency <4: no gain (low-concurrency sweep measured; knee between 4–8).

Memory:
- Batched ViT workspace adds ~+0.9 GB (64140 → 65074 MiB, large-image c8).
- At `mem-fraction-static 0.85` the large-image workload OOMs **with or
  without** the token budget — root cause identified via traceback as the
  8192-token prefill chunk's LLM attention workspace
  (`forward_extend` → `_npu_flash_attention_qlens` failing to allocate
  180 MiB with 37 MiB free), not the ViT batch.
- 0.85 + budget + `--chunked-prefill-size 4096` survives the same workload
  (0 OOM, c8 TTFT 1.63 s ≈ 0.80 baseline). Recommended configurations:
  `0.80 + budget` (safe default) or `0.85 + budget + chunk 4096` (reclaims
  ~3.2 GB KV pool).

Token budget cost: none on the hot path (small-image c32 still hits 20-in-1 =
3920 tokens, TTFT within run-to-run variance of no-limit: 617 vs 548 ms with
same-code repeats at 753/617 ms); large-image batches cap at 2-in-1
(3528 tokens), halving per-call workspace with c8 TTFT unchanged.

### Collaboration update: input-patch budget + A2 validation

I have integrated the input-patch budgeting and regression coverage from #44233 into this branch as incremental, signed-off commit `3e50dc742b` (preserving the original commits).

**Configuration and scope**
- Replace the merged-output-token budget with `SGLANG_NPU_VIT_MAX_BATCH_PATCHES`, counting **input patches before spatial merging**. With merge size 2, 16384 input patches correspond to 4096 output visual tokens. Output token counts are still used to split embeddings correctly.
- **Default is 0 (disabled)**; positive values opt in. Nonpositive values disable NPU cross-request batching, rather than removing the limit. This is intentional: the A2 measurements below show workload-dependent throughput regressions.
- Retain the Qwen3-VL Dense/MoE allowlist, with conservative guards for TP=1, unquantized models, no encoder DP, and ViT graphs disabled. Unsupported configurations retain per-request encoding. CUDA batching is unchanged.
- Oversized/unknown-size images run alone; the budget is **not a hard memory cap**. Inputs are moved per group.

**A2 serving performance**

Environment: one Ascend 910B3 64 GB (A2), CANN 9.0.0, PyTorch/torch-npu 2.10.0, Transformers 5.12.1 from the A2 image, Qwen3-VL-8B-Instruct BF16, TP1, eager, chunked prefill 4096, context 8192, max-running-requests 64, mem-fraction-static 0.7. This is a different hardware/software/model setup from the original A3/4B measurements, so the numbers should not be compared directly.

Tool: repository-standard `python -m sglang.bench_serving --backend sglang-oai-chat --dataset-name image`; unique random JPEGs, one image/request, 32 requested text tokens, fixed output length, unlimited request rate bounded by the listed concurrency. Two rounds with matched seeds across arms; server restarted between disabled (0) and enabled (16384). Each arm was warmed by the preceding accuracy pass; per-run benchmark warmup was 0 and prefix cache was flushed. Different seeds avoid repeated-image cache hits between workloads.

Numbers below are the **arithmetic mean of two run-level summaries** (including per-run P99, not a pooled P99). These are measurements on a shared server, not confidence intervals or universal speedup guarantees.
