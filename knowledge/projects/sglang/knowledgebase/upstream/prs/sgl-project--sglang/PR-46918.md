# [Fix] [AMD] mla: Cap the absorb-BMM waves-per-EU budget so gfx950 can compile it

[Upstream PR](https://github.com/sgl-project/sglang/pull/46918) · state: open · merged: False

## Original PR description

Fixes #46829.

## Motivation

On gfx950 (MI355X) the absorb-BMM hand configuration aborts the Triton/LLVM
compiler at M=256, which takes the server down during decode instead of at
load time:

```text
llvm/ADT/Sequence.h: llvm::iota_range<unsigned int>::iota_range(...):
Assertion `Begin <= End && "Begin must be less or equal to End."' failed.
```

The issue correctly notes that `waves_per_eu=4` was a hypothesis rather than a
proven root cause. This PR isolates the trigger and fixes it.

### The trigger is `waves_per_eu`, and it is a compile-time property

`waves_per_eu` is not a launch-time scheduling hint. The Triton AMD backend
turns it into an LLVM function attribute:

```python
# third_party/amd/backend/compiler.py
# "amdgpu-waves-per-eu"="<min>[,<max>]" allows controlling the minimal and
# (optional) maximal number of waves per SIMD. ...
# Specifying "N,N" forces LLVM to focus on a single register budget, simplifies
# some heuristics and may improve scheduling.
if options.waves_per_eu != 0:
    kernel_fn.add_fn_attr("amdgpu-waves-per-eu", f"{options.waves_per_eu},{options.waves_per_eu}")
```

LLVM's `AAAMDWavesPerEU` Attributor picks that attribute up and pins the
register budget for the whole kernel, and the AMDGPU AsmPrinter then compares
the achieved occupancy against the requested minimum:

```cpp
// llvm/lib/Target/AMDGPU/AMDGPUAsmPrinter.cpp
const auto [MinWEU, MaxWEU] = AMDGPU::getIntegerPairAttribute(F, "amdgpu-waves-per-eu", {0, 0}, true);
if (TryGetMCExprValue(OccupancyExpr, Occupancy) && Occupancy < MinWEU) { ... }
```

The abort itself comes from `MCRegisterInfo::regunits_interval`, which builds
an `llvm::iota_range` whose constructor asserts `Begin <= End`:

```cpp
// llvm/include/llvm/MC/MCRegisterInfo.h
iota_range<unsigned> regunits_interval(MCRegister Reg) const {
  return seq<unsigned>(RegUnitIntervals[Reg.id()][0], RegUnitIntervals[Reg.id()][1]);
}
```

So a waves-per-EU budget the register allocator cannot satisfy for this
kernel produces an inverted regunit interval and the assertion fires.

### Why M=256 is the first shape that trips it

For `heads=64, n=512` on an MI355X (304 CUs) the hand config resolves to:

| M | BLOCK_SIZE_M | BLOCK_SIZE_N | waves_per_eu |
|---|---|---|---|
| 2 | 16 | 32 | 1 |
| 16 | 16 | 128 | 1 |
| 48 | 32 | 128 | 2 |
| 64 | 32 | 128 | 2 |
| 128 | 64 | 128 | 2 |
| 200 | 64 | 128 | 2 |
| 256 | 64 | 128 | **4** |

M=128 and M=256 produce configs that are identical in every one of the eight
keys except `waves_per_eu` (2 versus 4). That is the independently varied
input the issue was looking for: the eight keys are `BLOCK_SIZE_M`,
`BLOCK_SIZE_N`, `GROUP_SIZE_M`, `num_warps`, `num_stages`, `waves_per_eu`,
`matrix_instr_nonkdim` and `cache_modifier`.

## Modifications

Cap the requested waves-per-EU budget at two, which is the largest value known
to compile and is what every previously-working shape already asked for.

Because the aiter kernel marks `M` and `N` as `do_not_specialize` and the
`EVEN_K` / `EVEN_MN` heuristics evaluate identically for M=128 and M=256
(K=192 is not a multiple of BLOCK_SIZE_K=128, and both M values are multiples
of BLOCK_SIZE_M=64), the capped M=256 launch compiles the *same binary* as the
M=128 launch that is known to build on the same device.

Two knobs are exposed so the value can be re-tuned without a code change:

- `SGLANG_ROCM_ABSORB_BMM_MAX_WAVES_PER_EU` (default `2`): the cap. `0`
  removes it, which is what the gfx950 team needs to sweep the trigger value.
- `SGLANG_ROCM_ABSORB_BMM_DISABLE_HAND_CONFIG` (default `false`): ignore the
  hand-tuned tile config entirely and let AITER pick its own tuning. Slower,
  but it keeps decode alive if a future ROCm toolkit revokes one of the tuned
  kernels.

This is a scoped configuration fix, not the "disable all absorb-BMM tuning"
workaround the issue asked us to avoid. The hand config stays in place for
every shape that worked before.

## Accuracy Tests

No model output changes: the capped M=256 config selects the same tile shape
and the same kernel binary as the M=128 config that already ran in production.

Unit tests are added in
`test/registered/unit/models/test_rocm_mla_absorb_fusion_gate.py`, covering the
wave cap, the identity between the capped M=256 and the known-good M=128
configs, the fact that no row count in 1..256 exceeds the cap, and both env
knobs. `13 passed, 265 subtests passed` locally.

**Limitation:** this was developed on a machine without an AMD GPU, so the
gfx950 behavior is established from the config arithmetic plus the Triton and
LLVM sources quoted above rather than by running the reproducer on an MI355X.
A run of the issue's reproducer on real hardware would confirm it.

## Speed Tests and Profiling

Not measured on AMD hardware. The capped config is the one M=128 already used,
so the M=256 path inherits a known-good tuning rather than a new one.
