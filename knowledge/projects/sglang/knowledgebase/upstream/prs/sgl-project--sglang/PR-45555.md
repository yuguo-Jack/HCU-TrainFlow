# [Perf] [AMD] vattn-asm: Split small-batch MTP verify attention over all CUs on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45555) · state: closed · merged: True

## Original PR description

## Motivation

At mid concurrency, Qwen3.5-397B-A17B-MXFP4 on MI355X decodes 1 to 4 requests at a time, and the full-attention layers run the MTP verify pass through `vattn_asm`. The kernel uses about 148 KB of LDS, so one workgroup fits on a CU, and it splits each sequence into at most 64 segments. At batch size 1 with one KV head per rank, that is 64 workgroups on 256 CUs: three quarters of the GPU is idle during long-context attention.

Also, the seg-plan cache is keyed on the `seqused_k` tensor, but `aiter_backend` builds `seq_lens + max_q_len` again in every layer. The plan is rebuilt in each full-attention layer instead of once per forward.

This PR extends the length-aware seg plan from [#39172](https://github.com/sgl-project/sglang/pull/39172). It lets small batches use up to one segment per CU and builds `seqused_k` once per forward. On AgentX, against a same-image control that already has #43861 and AR fusion, interactivity improves by 9% (median) and 4% (P90) at TP4 c8, and the gain fades to no measurable change at TP2 c16.

## Modifications

- `vattn_asm_gfx950/__init__.py`:
  - The segment cap goes from 64 to `num_cus` (256 on MI355X), and the seg plan also runs at batch size 1, so the segment count follows the context length.
  - Each segment has at least 16 KV tiles (256 tokens). Shorter segments cost more in fp32 partials than they save.
  - `vred.s` reduces at most 64 segments (one per lane). Above 64, a new Triton kernel `_reduce_triton` reduces with the same contract. For 64 or fewer, `vred.s` still runs.
- `aiter_backend.py`: `ForwardMetadata.verify_seqused_k` caches `seq_lens + max_q_len` per forward, so the seg-plan cache hits after the first layer. In a TP4 profile, plan launches drop from 18 to 4 per decode step.
- Tests: `test_vattn_asm_segment_plan.py` (CPU) bounds the cap by `num_cus` and adds a 2-sequence case. `test_vattn_segplan_mi35x.py` applies the 16-tile floor in the reference, also checks batch size 1, and checks that `_reduce_triton` matches `vred.s` on identical partials.

## Speed Tests and Profiling

### Kernel microbenchmarks

- MI355X, one GPU, CUDA graph replay.
- `mtp_verify_attn_fwd_asm` with 4 query tokens per sequence, 1 KV head, head_dim 256, fp8 page-16 KV cache.
- TP4 has 8 query heads per rank and TP2 has 16.
- The plan cost is spread over the layers of a forward.
- Times are in µs, baseline → this PR.

| Context per sequence | TP4 (8 q heads) | TP2 (16 q heads) |
|---|---:|---:|
| 16k | 14.3 → 13.1 (−9%) | 17.6 → 16.4 (−7%) |
| 64k | 26.7 → 18.6 (−31%) | 31.3 → 25.4 (−19%) |
| 224k | 62.7 → 30.5 (−51%) | 71.1 → 38.2 (−46%) |
| 224k x 2 | 64.1 → 47.7 (−26%) | 73.4 → 54.5 (−26%) |
| 224k + 16k | 63.3 → 33.2 (−48%) | 71.6 → 39.9 (−44%) |
| 128k + 64k + 16k + 4k | 43.5 → 30.7 (−29%) | 49.8 → 39.5 (−21%) |
| 32k x 4 | 24.3 → 23.7 (−3%) | 29.6 → 32.0 (+8%) |

Max absolute difference to the baseline output is 4.4e-4 over all points. The one slower case, four uniform short sequences at TP2 (about +2 µs), picks 128 segments and so runs the Triton reduce instead of `vred.s`.

On the decode path (q_len 1) at batch size 1, this PR is +20% at 16k context, −2% at 32k and −23% to −49% from 64k, with the plan rebuilt on every call.
