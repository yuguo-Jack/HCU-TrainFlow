# [Feat] metrics: count prefill tokens lost to a missing cache component state

[Upstream PR](https://github.com/sgl-project/sglang/pull/48248) · state: open · merged: False

## Original PR description

## Motivation

On hybrid models (linear attention / mamba layers next to full attention, e.g. Qwen3.5/Qwen3-Next/Qwen3.8-Flash-Next), a prefix match stops at the deepest radix node where **every** cache component has state. The request then re-prefills everything past that point, including tokens whose Full KV is still cached on device or host, whenever the recurrent state (or an SWA window) is not available at that depth: never stored there (checkpoint grid) or evicted. Today's metrics (`sglang:prefill_effective_tokens_total`, `cache_hit_rate`) show only the total re-prefill. An operator cannot tell whether the miss came from KV eviction (more KV or HiCache helps) or from missing recurrent state (checkpoint interval, mamba cache size and eviction policy help).

## Modifications

- `mem_cache/common.py` (`match_kv_cache`): store the matched `full_kv_hit_length` on the request, capped like `num_matched_prefix_tokens`. The `MatchResult` already reports it; this PR only keeps it.
- `managers/schedule_policy.py` (`PrefillAdder._account_prefill_cache_admission`): once per admitted request, next to the existing device/host/storage hit attribution, add `full_kv_hit_length - num_matched_prefix_tokens` to `log_state_miss_tokens`. Retracted requests are skipped, like the tier counters.
- `scheduler_components/metrics_reporter.py`, `observability/metrics_collector.py`: new counter `sglang:prefill_state_miss_tokens_total` (scheduler labels), pre-seeded at 0 and updated with the effective-prefill counters. KV misses are the rest of `prefill_effective_tokens_total{mode="input"}`, so no second counter is needed.
- The counter is reported only with `UnifiedRadixCache` (Python or Rust tree core), the only cache whose match fills `full_kv_hit_length`. With any other prefix cache it stays at 0.
- Tests (CPU-registered):
  - `test_prefill_adder.py` covers a state miss, a pure KV miss and a retracted request;
  - `test_match_kv_cache_full_kv_hit.py` checks that `match_kv_cache` records `full_kv_hit_length`, capped like the matched prefix;
  - `test_prefill_state_miss_metric.py` checks that the collector exports the counter at 0 and increments it.

The match, admission and scheduling are unchanged. Counting happens once per admitted request, not per match: queued requests are re-matched every scheduling round and would otherwise be counted repeatedly.

## Accuracy Tests

`Qwen/Qwen2.5-0.5B-Instruct` with `--enable-deterministic-inference --enable-metrics`, same RTX PRO 6000: greedy outputs of 7 prompts (single, repeated twice, and batched) are **token-identical** to main (main is repeat-identical in this config), and the existing prefill counters match (`prefill_effective_tokens_total{mode="input"}` 95,211 on both).

The scheduling path is unchanged. With `--enable-metrics` on `nvidia/Qwen3.8-Flash-Next-NVFP4` (radix cache on, same RTX PRO 6000, same request sequence), main and this PR report identical existing counters: `prefill_effective_tokens_total` input 15,271 and device_hit 80,192. The 3,000-word prompt's greedy output is identical. Short-prompt outputs on this model are not repeat-deterministic on main itself (see the exactness note in the speed section).

## Speed Tests and Profiling

No speed change is claimed: the work is two integer additions per admitted request.

Example on the same server: a long prompt is cached, then two continuations of the whole prompt, then a request reusing only its first 60%:

| Counter | main | this PR |
|---|---|---|
| `prefill_effective_tokens_total{mode="input"}` | 15,271 | 15,271 |
| `prefill_effective_tokens_total{mode="device_hit"}` | 80,192 | 80,192 |
| `prefill_state_miss_tokens_total` | (absent) | 256 |

The partial-prefix request reused 8,192 cached tokens and recomputed 269 (scheduler log `#cached-token: 8192, #new-token: 269`). Its Full KV reached 8,448 tokens, but the deepest recurrent-state checkpoint was at 8,192: the 256 counted tokens.

Exactness note: on this model and GPU, main's greedy short-prompt outputs vary between runs (`--enable-deterministic-inference` is unsupported for its QSA top-k on SM120), so the agreement check is on counters and the long prompt.
