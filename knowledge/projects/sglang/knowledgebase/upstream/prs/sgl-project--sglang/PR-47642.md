# [Quant/GGUF] Fix iq3xs_grid: 146 words must be 0x3c not 0x3e

[Upstream PR](https://github.com/sgl-project/sglang/pull/47642) · state: open · merged: False

## Original PR description

### Problem

`python/sglang/kernels/aot/include/sgl_kernel/quantization/gguf/ggml-common.h`
(the only copy of the table in-tree; `csrc/.../dequantize.cuh` and `vecdotq.cuh`
both reference it) ships an `iq3xs_grid[512]` in which **150 of 2048 bytes
(spread over 146 uint32 words) encode `0x3e` (62) where the value must be
`0x3c` (60)**.

Flat representation = 512 uint32 packed little-endian (2048 bytes):

| state | sha256(flat 2048 B) |
|---|---|
| broken (current main @ fb9846d3) | `5dcc1e0fdef66e1cd695958f68884351d8cf60e7f01659c90cef858d1e410559` |
| fixed (this PR) | `331c6882af71bfd4c70eb44cebb1edf5db2241c7ee7c6557f1cc6652160f8294` |

Every wrong byte is exactly `62` instead of `60`, i.e. amplitude 15 folded as
`15*4 = 62` instead of `60`. IQ3_S amplitudes are odd values `{1,3,…,15}`, so
the legal 4× byte set is `{4,12,…,60}` — **62 is never a legal value**.

### Root-cause chain

1. The table was hand-generated as a 4× fold of `iq3s_grid` in vLLM
   PR **vllm-project/vllm#5191** (commit `360bd67cf0`, 2024-08-06) — the
   generation mis-encoded those 150 bytes.
2. sglang PR **#11019** (commit `8fdcd98e`, 2025-10-12) copied the table from
   vLLM verbatim, inheriting the defect.
3. Independent third-party confirmation of the same 146 words:
   **vllm-gguf-plugin issue #129 / PR #136** (commit `e2b8ad532b8b5ea175100202c30430c1d2b5e6a8`,
   merged 2026-09-24) applies the identical `0x3e → 0x3c` fix.

### Why 4×iq3s_grid is the ground truth

The kernel arithmetic (vecdotq / dequantize IQ3_S paths) treats `iq3xs_grid`
as a lane-wise 4× amplification of llama.cpp's `iq3s_grid`. llama.cpp's
`iq3s_grid` has **never been modified since introduction** — byte-for-byte
identical to this snapshot (sha256 of the same flat 2048 B form:
`bd1af4945a1717c65610b0284e4628b9a1ba3b306fae3a06f6e5f597356e349f`).
The invariant `iq3xs_grid byte == 4 × iq3s_grid byte` therefore either holds
for all 2048 bytes or the table is corrupt.

### Verification

- Programmatic diff of this commit: exactly **146 words / 150 bytes** changed,
  each change is exactly `0x3e → 0x3c`; the file is byte-identical outside the
  `iq3xs_grid` block (`git diff --stat`: 1 file, 50 +/- lines).
- After the fix, **all 2048/2048 bytes satisfy `byte == 4 × llama iq3s_grid
  byte`** against today's llama.cpp master `ggml-common.h` (sha above).
- Every post-fix byte satisfies `b % 4 == 0 && (b // 4) % 2 == 1`.
- GPU: dequantize kernel output is **bit-exact (×5 runs)** vs a golden
  reference implementing llama.cpp semantics (verified in our fork after the
  table swap).

### Suggested regression test (cheap, CPU-only)

```python
def test_iq3xs_grid_is_4x_iq3s_grid():
    for w in iq3xs_grid:                     # 512 uint32 words
        for j in range(4):
            b = (w >> (8 * j)) & 0xFF
            assert b % 4 == 0 and (b // 4) % 2 == 1, "not a 4x odd amplitude"
    # equivalently: flat(iq3xs_grid) == bytes(4 * b for b in flat(iq3s_grid))
```

This would have caught the bug at import time and guards the table against any
future re-generation.

### Scope / risk

Table-only change; no code paths touched. Wrong-grid entries only affect
IQ3_S-dequantized tokens containing those grid words, which currently decode
silently to wrong values (62 vs 60 lane scale), so this is a pure correctness
fix.

_Note: reuses the fix already merged upstream in vllm-gguf-plugin#136._
