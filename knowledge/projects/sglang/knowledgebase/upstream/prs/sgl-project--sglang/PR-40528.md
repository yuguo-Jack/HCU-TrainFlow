# # [Perf] [AMD] Qwen3-Next: fused paged-decode attention with output gate on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/40528) · state: open · merged: False

## Original PR description

# [AMD] Qwen3-Next: fused paged-decode attention with output gate on gfx950
## Motivation

Qwen3-Next's full-attention layers currently run this boundary as **three
launches** (`python/sglang/srt/models/qwen3_next.py:827-840`):

```python
attn_output   = self.attn(q, k, v, forward_batch)   # aiter paged_attention_ragged
attn_output   = sigmoid_gate_mul(attn_output, gate) # separate launch
output, _     = self.o_proj(attn_output)            # quantizes bf16 internally
```

The gate and the activation quant are both elementwise passes over
`[tokens, heads*256]` that the attention kernel could absorb, because it already
performs a split-K merge over exactly that data.a

This PR routes the boundary through a new aiter op —
**[ROCm/aiter#5715](https://github.com/ROCm/aiter/pull/5715)**, which this PR
depends on — that does the attention, the sigmoid gate and the group-128 FP8
quant in **two** launches, on gfx950. The
FP8 output is currently discarded — `o_proj` receives BF16 exactly as today — so
this change is the *fusion* only. Handing `o_proj` the `(fp8, scales)` pair
directly is a separate, larger change and is deliberately not attempted here.

**Where the win is.** Attention is 12 of Qwen3-Next's 48 layers (the other 36 are
GDN linear attention, whose cost does not grow with context). So the boundary is
~3.8% of the decode step at 8K context but ~30% at 64K, and the gain scales with
context accordingly.

## Modifications

| file | change |
|---|---|
| `python/sglang/srt/layers/attention/aiter_backend.py` | capability probe; route the Qwen3-Next decode path to the fused op when supported |
| `python/sglang/srt/models/qwen3_next.py` | call the fused op in place of `self.attn(...)` + `sigmoid_gate_mul(...)`; unchanged otherwise |
| `test/registered/amd/test_paged_attention_output_gate.py` | registered test |

**Gated, and falls back rather than failing.** The op exposes
`paged_attention_output_gate_supported(...) -> (bool, reason)`; anything it
declines (non-gfx950, page_size != 1, head_dim != 256, heads > 16, non-fp8 KV
cache, unsupported strides) takes the existing three-launch path unchanged.

**The CUDA path is unaffected.** This is HIP/gfx950-specific and inert
everywhere else.

## Speed Tests and Profiling

4x MI355X (gfx950), TP4/EP1, `Qwen/Qwen3-Next-80B-A3B-Instruct-FP8`, ROCm 7.0,
Triton 3.8. Un-profiled; idle GPUs asserted before every arm.

**Both arms are the same build.** Baseline is this branch's merge-base on
`origin/main`; the only delta is this PR's commit. Twelve serving arms, run
sequentially (two TP4 servers on one host would share CPU and interconnect, and
that is not a confound worth accepting in an A/B measuring single-digit
percentages). A fresh server per configuration, since `--context-length` is a
launch-time flag.

**Two metrics, because they answer different questions.** Median ITL is decode
latency, which is what this change acts on. End-to-end throughput is that same
effect diluted by prefill, which this change does not touch.

| context | ISL/OSL | conc | median ITL | e2e throughput |
|---|---|---|---|---|
| 8,192 | 1024/1024 | 1 | **-1.94%** | +1.87% |
| 8,192 | 1024/1024 | 8 | **-2.18%** | +2.19% |
| 8,192 | 1024/1024 | 32 | **-1.38%** | +1.27% (n=3) |
| 8,192 | 1024/1024 | 64 | **-1.15%** | +1.19% (n=3) |
| 32,768 | 28000/4096 | 8 | **-3.60%** | +3.34% |
| 32,768 | 28000/4096 | 32 | **-2.92%** | +2.37% |
| 65,536 | 60000/512 | 8 | **-5.47%** | +2.18% * (n=3) |
| 65,536 | 60000/512 | 32 | **-7.68%** | +1.51% * (n=3) |
| 65,536 | 60000/4096 | 8 | **-5.48%** | +4.50% |
| 65,536 | 60000/4096 | 32 | **-7.12%** | +4.81% |
| 131,072 | 120000/512 | 8 | **-8.51%** | +2.05% * |
| 131,072 | 120000/512 | 32 | **-10.78%** | +1.26% * |
| 131,072 | 120000/4096 | 8 | **-7.91%** | +6.01% |
| 131,072 | 120000/4096 | 32 | **-10.78%** | +5.84% |

`*` ISL 60 000–120 000 against OSL 512 makes the input 99% of all tokens, so
"total token throughput" on these rows is close to a pure prefill measurement.
Read the ITL column for them.

`(n=3)` Medians of three repeats, with the arms **interleaved** and the leading
arm **alternating** so neither sits systematically in the same position. Median
ITL reproduced to 0.10–1.72 pp across repeats; e2e throughput at OSL 512 to
2.64 pp — the widest spread in the matrix, for the same reason as the `*`.

**Summary: decode latency improves ~1–2% at 8K context and 5–11% at 64–128K;
end-to-end throughput improves 0.9–6.0%**, the spread driven by output length —
longer outputs put more of the request in decode, which is where the change
acts. The relationship is arithmetic rather than asserted: at 64K / C32 /
OSL 512, decode is 4.80 s of a 26.65 s request (18.0%), and 18.0% x 7.58% =
**1.37% predicted** against **1.35% measured**. At 8K decode is 94–98% of the
request, which is why the two columns nearly coincide.

Every number above was measured on the commit in this PR.

**Kernel level**, for reference — the boundary at real context 8192:

| bs | stock (3 launches) | this PR | speedup |
|---|---|---|---|
| 1 | 17.36 µs | 5.77 | **3.01x** |
| 8 | 18.60 | 8.13 | 2.29x |
| 32 | 39.06 | 22.61 | 1.73x |
| 64 | 63.08 | 41.21 | 1.53x |

Method: a CUDA graph containing one kernel costs ~9.3 µs to replay on this host
regardless of the kernel, so each measurement captures 50 invocations per graph;
live dispatch floor 1.70 µs, and no number above is within 2x of it.

### Numerical note

On the FP8 KV path the existing `paged_attention_ragged` diverges from an fp32
reference by ~14% mean relative error, where the fused op agrees to 0.18–0.27%.
That is a defect in aiter, already fixed in
**https://github.com/ROCm/aiter/pull/5642**, and **the fix is timing-neutral**
(13.49 → 13.51 µs at bs=1; 59.68 → 59.50 µs at bs=64), so the numbers above
stand as measured. It does mean the two columns are not computing the same thing
to the same accuracy until that lands.

## Reproduction

Base image plus one change — Triton upgraded to 3.8, which the Gluon launcher
requires (`llvm_fn_attrs=` does not exist in 3.7 and the first launch fails):

```dockerfile
ARG BASE=lmsysorg/sglang-rocm:v0.5.19-rocm700-mi35x-20260910
FROM ${BASE}
ARG TRITON_VERSION=3.8.0
ARG TRITON_INDEX=https://download.pytorch.org/whl/nightly/rocm7.0
RUN python -m pip install --no-deps --force-reinstall --pre \
      --index-url "${TRITON_INDEX}" "triton==${TRITON_VERSION}"
```

Versions the numbers were taken on: ROCm 7.0.0, torch `2.9.0a0+git7bcbafe`,
triton **3.8.0** (base ships 3.7.0), aiter `4ad99832` + ROCm/aiter#5715,
4x MI355X.

```bash
docker build -t pa-gate:local \
  --build-arg BASE=lmsysorg/sglang-rocm:v0.5.19-rocm700-mi35x-20260910 .

python3 -m sglang.launch_server \
  --model-path Qwen/Qwen3-Next-80B-A3B-Instruct-FP8 \
  --tensor-parallel-size 4 --kv-cache-dtype fp8_e4m3 \
  --context-length 65536 --chunked-prefill-size 16384 --ep-size 1 \
  --dtype bfloat16 --quantization fp8 \
  --attention-backend aiter --moe-runner-backend aiter \
  --enable-aiter-allreduce-fusion --disable-radix-cache \
  --disable-shared-experts-fusion --mem-fraction-static 0.80 \
  --cuda-graph-max-bs-decode 64

python3 -m sglang.bench_serving --backend sglang-oai \
  --dataset-name random --random-input-len 60000 --random-output-len 4096 \
  --random-range-ratio 1 --num-prompts 32 --max-concurrency 32
```

ROCm 7.0 specifically: on >= 7.2 SGLang sets `_use_aiter_bpreshuffle_gfx95=True`
and preshuffles FP8 weights, which this path has not been validated against.
