# [Perf] deepseek_v4: fold the MegaAttention query layout into wq_b for block-FP8-as-MXFP8 checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/44838) · state: closed · merged: True

## Original PR description

## Motivation

`setup_mega_attention` folds the MegaAttention query head layout into `wq_b`'s rows (`interleave_query_rows`) only when `wq_b` is a native MXFP8 linear. DeepSeek-V4.1-Flash ships a `[32, 32]` block-FP8 checkpoint whose dense linears run through the same FlashInfer MXFP8 GEMM via the block-FP8-as-MXFP8 view (`block_fp8_mxfp8_ready`), so `mega_wq_b_permuted` stays false and every layer packs the query at forward time with `pack_query`: a `new_zeros` of the `[tokens, 64, 512]` bf16 query and a strided transpose copy into it.

Measured on GB300, DEP2 (TP2 + DP attention, EP2, MegaMoE, decoder bounded replay, Mega-mHC on), one cold 16,384-token prefill chunk per rank, torch profiler:

| per 16K step, rank 0 | count | per launch | total |
|---|---:|---:|---:|
| `aten::new_zeros` (vectorized fill) | 40 | 141 µs | 5.7 ms |
| `aten::copy_` (strided `direct_copy` elementwise) | 40 | 691 µs | 27.6 ms |

That is 33 ms of a 322 ms step (10%) and 80 launches on an eager step that is dispatch-bound (median inter-kernel gap 41 µs). Per layer it writes ~1.2 GB of zeros and moves ~2.4 GB through a non-contiguous copy.

## Modifications

- `_wq_b_uses_flashinfer_mxfp8` also accepts a block-FP8 `wq_b` served as MXFP8 (`block_fp8_as_mxfp8` on the FlashInfer CUTLASS / CuTe-DSL backend), so `mega_wq_b_permuted` is set for this checkpoint.
- In `setup_mega_attention`, for that case: `interleave_query_rows` moves 16-row groups, so the `[32, 32]` block scale is refined to 16 rows, permuted the same way as the weight, and rebound as `weight_scale_inv` with `weight_block_size = [16, 32]`. The existing post-load pass then builds the swizzled MXFP8 scale from it as for any block-FP8-as-MXFP8 layer. The native MXFP8 path is unchanged.

After this `pack_query` is skipped for the block-FP8 checkpoint exactly as for native MXFP8 ones.

Numerics: the same FP8 bytes and the same e8m0 scales reach the GEMM, only in the row order the attention kernel already consumes; refining a 32-row block scale to 16-row blocks is exact.
