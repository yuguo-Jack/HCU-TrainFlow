# [Fix] diffusion/storage: Join uploads before request cleanup

[Upstream PR](https://github.com/sgl-project/sglang/pull/46068) · state: closed · merged: True

## Original PR description

## Summary

Cancelling a cloud upload cancelled its asyncio wrapper, not the SDK thread. Request cleanup could then delete the source files while boto3 was still opening multipart parts. Concurrent image/video uploads could also return on the first cancelled child while another upload was still using the directory.

- Join the SDK operation before propagating cancellation, including repeated cancellation.
- Wait for every image/video upload before allowing caller cleanup.
- Preserve upload failures and the existing local-output fallback.
- Document shutdown grace-period and remote-object retention boundaries.

No new options, production modules, model changes, or changes to storage retry settings. Production diff: +27/-8 lines across three existing files.

## Validation

- Regression tests on Linux: six failures before the fix; all pass after it. Related standalone tests: **52 passed**.
- Real boto3 1.43.116 against a loopback S3-protocol fixture: successful PUT, HTTP 503 retry, HTTP 403 fallback, and cancellation during 16 MiB multipart initialization. Before the fix the source disappeared and zero bytes were published; afterwards the source remained until upload completion, then request cleanup ran and cancellation propagated.
- Integration with #45919, #46025 and #46057: **119 tests passed**.
- H200 / torch 2.14.1+cu130 / Wan2.1-T2V-1.3B-Diffusers, 512x320, 17 frames, four steps: two real server lifecycles covering persistent and temporary outputs, denied/blocked object storage, multi-output publication, recovery and shutdown during uploads. Health/status polling stayed responsive; unfinished uploads did not report completed. Repeated workload outputs matched decoded-frame hashes after recovery. Owned workers exited.
- Pre-commit passed.

The storage fixture exercises the real SDK and HTTP transport, not AWS service availability. Cooperative cancellation may wait for SDK timeouts/retries; it does not roll back uploaded objects or provide durable job recovery. The race also reproduces on main and is not introduced by #45919.
