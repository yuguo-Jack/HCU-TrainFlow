# [Perf] [NVIDIA] qsa: split-K sparse decode kernel for fp8 KV

[Upstream PR](https://github.com/sgl-project/sglang/pull/48296) · state: open · merged: False

## Original PR description


## Motivation

QSA decode and MTP target verify in Qwen3.8-Flash-Next (`qwen4_exp`) attend each query row to 2,051 selected positions (512 compressed blocks of 4 tokens plus a 3-token tail). On SM120 (RTX PRO 6000 Blackwell), the backend prepares them with `fused_kv_prepare`: it stores the new KV, expands the blocks and packs the selected K/V of every row into a page-strided scratch. FlashInfer's `trtllm_batch_decode_with_kv_cache` then reads that scratch.

On SM120 the scratch is bf16 even when the KV pool is `fp8_e4m3`, the setting every NVIDIA recipe in the Qwen3.8-Flash-Next cookbook pins. The pack therefore writes and re-reads twice the bytes the attention needs, and at 32 or more query rows it is about 4x the cost of the attention itself.

This PR adds a JIT CUDA kernel that reads the selected fp8 K/V rows straight from the KV pool through `req_to_token`. It computes the attention in one split-K pass with no gather and no scratch. It is opt-in behind `SGLANG_ENABLE_QSA_SPARSE_DECODE_CUDA`.

## Modifications

- `python/sglang/kernels/jit/csrc/attention/qsa_sparse_decode.cuh` (new, JIT; no `sglang-kernel` release needed):
  - **Split kernel.** One CTA per (query row, KV head, split), 8 splits, 4 warps. 32-column blocks are loaded through a 2-3 stage `cp.async` pipeline. `q k^T` and `p v` run on bf16 `m16n8k16` tensor cores with an online softmax, and the kernel writes unnormalized partials. A small combine kernel then merges the 8 partials into the bf16 output.
  - **Column validity.** A column is used when `0 <= pos < seq_len` and its slot is `>= 0`. A row with no valid column outputs zeros, and blocks without a valid column are skipped.
  - **FP8 conversion.** e4m3 → bf16 is exact. The fast conversion maps the NaN codes to ±480, so a fragment containing one is converted again with `cvt` and NaN propagates.
  - **Determinism.** A row's output depends only on that row, so it is deterministic and independent of the batch.
- `python/sglang/kernels/ops/attention/qsa_sparse_decode.py` (new): the op wrapper.
  - It picks the pipeline depth per architecture: SM12x uses 2 stages with q in registers. SM10x uses 3 stages, with q in shared memory above 32 rows; the op and its tests also run there.
  - It allocates the partials per call, so it holds no state and is CUDA-graph safe.
- `qwen_sparse_attn_backend.py`: with `SGLANG_ENABLE_QSA_SPARSE_DECODE_CUDA=1`, an `fp8_e4m3` MHA KV pool and SM120, decode and target verify skip the fused pack-for-trtllm path. They store the new KV, expand the block top-k (existing `_expand_block_indices`) and call the kernel. Otherwise nothing changes.
  - **SM100 stays on the default path.** There, upstream already packs fp8 for trtllm. The kernel measured 0.83-0.86x at 16 rows and 1.21-1.60x at 32-384 rows on GB200, so it is not enabled.
- `environ.py` + `environment_variables.mdx`: the new env var, default off, in the "Attention & Kernels" table.
- Tests: `test/registered/kernels/ops/attention/qsa/test_qsa_sparse_decode.py` (`1-gpu-small`, skipped off SM100/SM120):
  - the kernel vs `qsa_sparse_attention_reference` (fp32 softmax): decode and verify rows, short and long contexts, int32/int64 request ids;
  - empty blocks and rows without a valid column;
  - determinism and batch invariance;
  - NaN propagation in K and in V;
  - CUDA-graph replay;
  - backend routing with the flag on and off.
- Benchmark: `test/registered/kernels/benchmark/attention/bench_qsa_sparse_decode.py` (marker `do_bench`, cold L2, CUDA graph). It compares the default path (`fused_kv_prepare` + trtllm) with store + block expansion + this kernel; both lines include the new-token KV store.

## Accuracy Tests

Outputs differ from the trtllm path at bf16 rounding level: max |diff| 9.8e-4 on the benchmark inputs. The unit tests hold the kernel to the fp32 reference at `atol=5e-3, rtol=1e-2`.

End-to-end setup:
- Qwen3.8-Flash-Next NVFP4 with `--tp 1 --quantization modelopt_fp4 --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.93 --chunked-prefill-size 4096`, decode CUDA graphs on.
- Flag off (today's path) vs flag on, on the same GPU in the same container.
- gsm8k command: `sgl-eval run gsm8k --num-examples 200 --num-threads 32 --temperature 0 --max-tokens 4096` (sgl-eval 0.1.3), server with `--max-running-requests 32 --context-length 20480 --disable-prefill-cuda-graph`.

| GPU | Checkpoint | gsm8k off | gsm8k on |
|---|---|---|---|
| RTX PRO 6000 Max-Q (300 W) | `RadixArk/Qwen3.8-Flash-Next-NVFP4` | 97.00% | 97.50% |
| RTX PRO 6000 Server (600 W) | `nvidia/Qwen3.8-Flash-Next-NVFP4` | 95.50% | 97.00% |
| RTX PRO 6000 Max-Q (300 W), MTP (NEXTN 3/4) | `RadixArk/Qwen3.8-Flash-Next-NVFP4` | 98.00% | 97.00% |

Across the three pairs the deltas are +0.5, +1.5 and -1.0 points: no consistent direction, all within GSM8K run-to-run variance.

Greedy outputs:
- **Requests.** 24 greedy requests of 160 tokens on 6K-20K-token prompts.
- **Upstream main is not repeat-deterministic on this model,** so the reference is main's own run-to-run agreement.
- **Without MTP:**
  - 600 W: main vs main 14/24 token-identical; flag on vs off 11/24 and 12/24.
  - 300 W: main vs main 7/24; flag on vs off 5/24 and 9/24.
- **With MTP** (NEXTN, 3 steps, 4 draft tokens; covers target verify and draft decode), 300 W: main vs main 6/24 token-identical; flag on vs off 1/24 and 4/24. On 16/24 requests main itself diverges within the first 5 tokens, so these counts are below the noise floor and do not separate the arms. The sensitive check is MTP acceptance, which is unchanged: mean accept length 2.575 (off) vs 2.569 (on) over A-B-B-A serving runs, with a run-to-run spread of up to ±0.18.

- **No end-to-end throughput gain is claimed at this load:** output throughput moves by less than main's own spread between repetitions. At 11 decode rows the kernel saves about 16 µs per QSA layer per step; the 4x kernel gains start at 32+ rows (larger decode batches, or MTP verify at 4 rows per request).
- **With MTP,** upstream sizes this GPU for 2 running requests (8 verify rows), and throughput moves only with acceptance; no gain is claimed there.
