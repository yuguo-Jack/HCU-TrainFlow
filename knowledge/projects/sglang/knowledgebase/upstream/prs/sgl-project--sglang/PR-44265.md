# [Feat] [AMD] dsv4: Dispatch Mega-mHC prefill to aiter on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/44265) · state: open · merged: False

## Original PR description

## Motivation

`SGLANG_OPT_DSV41_MEGA_MHC_PREFILL` already selects single-pass Mega-mHC prefill on SM100 (DeepGEMM). On gfx950 that flag did nothing: `is_sm100` is false, and the fused HIP mHC boundary (`hc_boundary_fused`) owns the same seam. DeepSeek-V4.1-Flash prefill on MI355X therefore never called aiter's Mega-mHC kernel from [ROCm/aiter#6179](https://github.com/ROCm/aiter/pull/6179) (`flydsl_mega_mhc`).

## Modifications

Opt-in, default off. CUDA behavior is unchanged.

- `_can_use_mega_mhc` accepts gfx950 when the flag is set, `hc_mult == 4`, and `hidden == 5120`. Context-parallel prefill stays excluded.
- On HIP, `_post_fusion` calls `flydsl_mega_mhc` with `out_dtype="bf16"` and packs the next `(pre, post, comb)` the same way DeepGEMM does. If aiter is missing or the launch fails, it warns once and uses the unfused post.
- `hc_boundary_fused` is turned off when the flag is set at layer init, so the fused boundary and Mega-mHC do not both apply the post. The model then takes `forward_hc_pre_from_prev`.

Requires an aiter build that exports `aiter.ops.flydsl.flydsl_mega_mhc` (aiter #6179, tested at `31aef274`). This PR does not bump the ROCm image pin.

bf16 norm output only. Handing MXFP8 straight to the next GEMM is a follow-up: FFN combine has no quantized input, and a local MXFP8 experiment still launched the bf16 Mega kernels.
