# [Feat] [AMD] dsv4: Dispatch Mega-mHC prefill to aiter on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/44265) · state: open · merged: False

## Original PR description

## Motivation

`SGLANG_OPT_DSV41_MEGA_MHC_PREFILL` already selects single-pass Mega-mHC prefill on SM100 (DeepGEMM). On gfx950 that flag did nothing: `is_sm100` is false, and the fused HIP mHC boundary (`hc_boundary_fused`) owns the same seam. DeepSeek-V4.1-Flash prefill on MI355X therefore never called aiter's Mega-mHC kernel from [ROCm/aiter#6179](https://github.com/ROCm/aiter/pull/6179) (`flydsl_mega_mhc`).

## Modifications

Opt-in, default off. CUDA behavior is unchanged.

- `_can_use_mega_mhc` accepts gfx950 when the flag is set, `hc_mult == 4`, and `hidden == 5120`. Context-parallel prefill stays excluded.
- On HIP, `_post_fusion` calls `flydsl_mega_mhc` with `out_dtype="bf16"` and packs the next `(pre, post, comb)` the same way DeepGEMM does.
- With the flag set, each forward step takes either Mega-mHC (`forward_hc_pre_from_prev`) or the fused boundary, never both, so the post is not applied twice. Mega-mHC runs on every step, except with `--enable-amd-monokernel`, where it runs on prefill only. The monokernel refuses layers without `hc_boundary_fused` and its kernels follow the fused boundary, so `hc_boundary_fused` stays as on main and decode and verify steps keep the fused path.

Requires an aiter build that exports `aiter.ops.flydsl.flydsl_mega_mhc` (ROCm/aiter#6179, merged as `31aef274`). `rocm/sgl-dev` images from 20261018 on already include it (aiter `2bb5491`), so this PR does not bump the ROCm image pin.

bf16 norm output only. Handing MXFP8 straight to the next GEMM is a follow-up: FFN combine has no quantized input, and a local MXFP8 experiment still launched the bf16 Mega kernels.

### Reproduce

```bash
# Baseline: SGLANG_OPT_DSV41_MEGA_MHC_PREFILL=0. This PR: =1.
SGLANG_USE_AITER=1 SGLANG_MOE_PADDING=1 AITER_FLYDSL_FORCE_REDUCE=0 AITER_BF16_FP8_MOE_BOUND=0 \
ROCM_QUICK_REDUCE_QUANTIZATION=INT4 SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL=1 \
SGLANG_OPT_DSV41_MEGA_MHC_PREFILL=1 \
sglang serve --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code \
  --tp 4 --ep-size 1 --mem-fraction-static 0.87 \
  --chunked-prefill-size 16384 --max-prefill-tokens 16384 --context-length 135168 \
  --cuda-graph-backend-prefill disabled --enable-decoder-swa-bounded-replay \
  --enforce-shared-experts-fusion --cuda-graph-max-bs-decode 256 --max-running-requests 256
# Monokernel runs add: --enable-amd-monokernel --fp8-gemm-backend aiter

# One point; C = 1, 4, 16, 32, 64. 80k/1k: --random-input-len 80000 --random-output-len 1000.
python -m sglang.bench_serving --backend sglang --model deepseek-ai/DeepSeek-V4.1-Flash \
  --dataset-name random --random-input-len 8000 --random-output-len 2000 --random-range-ratio 1.0 \
  --request-rate inf --max-concurrency $C --num-prompts $((4 * C)) --warmup-requests $((2 * C)) \
  --temperature 0 --flush-cache --seed 1
```

- amd-pedghazi · comment · 2026-10-29T11:54:24Z · [source](https://github.com/sgl-project/sglang/pull/44265#issuecomment-6495946508)

With --enable-amd-monokernel, fused_boundary_this_step() keeps the fused boundary on all decode and verify steps. But _install_forward() in [kernel_plugins/amd/binding.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/kernel_plugins/amd/binding.py) sends every step the monokernel does not support to the normal forward. So this gate never sees monokernel steps, and Mega-mHC could also run on large decode and verify batches:

```
def fused_boundary_this_step(forward_batch) -> bool:
    return not envs.SGLANG_OPT_DSV41_MEGA_MHC_PREFILL.get()
```

hc_boundary_fused is unchanged, so the monokernel still attaches. _amd_monokernel_enabled() goes away. Your 8k/2k c64 results, where decode is too large for the monokernel, suggest a gain: TPOT drops 3.3 % without the monokernel (Mega-mHC on every step) and 0.7 % with it (prefill only).

If this is intended, could the docstring say why? Please also check the DSpark accept length. The benchmarks had no speculative decoding.

- stahtine · comment · 2026-10-29T12:11:39Z · [source](https://github.com/sgl-project/sglang/pull/44265#issuecomment-6496305590)

@amd-pedghazi There's tradeoffs for making the mega-mHC to work on decode when mono kernels are not active:

Trade-offs:
- For: decode steps above the monokernel's limit would get Mega-mHC. In my runs without monokernels showed Mega-mHC on decode improving TPOT, including at concurrency 64.
- Against: within one server, small decode batches would run in the monokernel (fused-boundary arithmetic) and large ones through Mega-mHC. Both compute the same thing, but the results aren't bit-identical. That already happens today between the monokernel and the fused boundary, but it adds a third path. Reviewers or the monokernel owners might object, because it goes against the reason for the plugin's check.

I decided not to go with this approach as this is cleaner solution.

> Please also check the DSpark accept length. The benchmarks had no speculative decoding.

For these general benchmarks I did not include speculative decoding.
