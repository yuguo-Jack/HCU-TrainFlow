# RL: Read byte ranges of output store fields into caller memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/47320) · state: closed · merged: True

## Original PR description

## Summary
Read byte ranges of stored output fields, in one Mooncake call, into a `ReadBuffer` the caller registers once and reuses.

## Motivation
Under context parallelism a Miles trainer rank uses only its own rows of each sample's R3 and indexer top-k, but `read_many` reads whole fields, so every CP rank reads the full field. This adds the read that lets Miles fetch only the local rows; `read_many`, puts and deletes are unchanged. Registering a fresh destination on every read would cost more than the read itself below 4 GiB, where Mooncake faults pages in serially, so the destination stays registered across reads.

## Usage
```python
buf = store.read_buffer(n * row_bytes)  # registered until buf.close()
store.read_ranges(
    [RangeRead(ref=ref, field="indexer_topk", src_offset=r0 * row_bytes, nbytes=n * row_bytes, dst_offset=0)],
    into=buf,
)
rows = np.frombuffer(buf.view, dtype=np.int32)  # rows r0 .. r0 + n - 1; buf is reusable
```

## Design Notes
- **Mental model:** Miles' replay fill picks this rank's rows of each stored field plus their places in a reused `ReadBuffer` → `OutputStore.read_ranges` checks each range against the ref's `FieldSpec` and the buffer → `MooncakeBackend.get_ranges` makes one `get_into_ranges` call into the already registered memory, every range in one Mooncake scatter with the GIL released.
- **`ReadBuffer` owns its memory and its registration together:** `close()` unregisters before the memory can be freed, so a registration never outlives the pages it pins. A caller-facing `register(memoryview)`, or a registration cache keyed by address, would let registered memory be freed and reused. `StorageBackend` gains `register` / `unregister`; `get_many` still registers per call.
- **Allocation:** private anonymous `mmap` with `MADV_HUGEPAGE` on Linux, untouched until registration faults it in (in parallel from 4 GiB up). Without huge pages, registration was 3x slower on hosts where THP is madvise-only; numpy asks for them the same way.
- Before any read, each range is checked, raising `ValueError`: field present; identity codec (only then is a range of stored bytes a range of the array); non-empty range inside the field; destination inside `into`; `into` open and created by this store.
- Failures map separately from `_raise_failed_reads`: −704 → `KeyError`, anything else → `RuntimeError`; after the checks, −600 is Mooncake rejecting a range, not the oversized-part mismatch that function reports for whole reads. A failed read leaves `into` registered and usable.

## Verification
- `radix_transfer_plugins/tests`: 40 passed (34 before) on the fake Mooncake, which implements `get_into_ranges` (−600 outside registered memory, −704 for a missing key). New cases: random ranges across 3 refs equal the numpy slices in one backend call; one registration serves every read until `close()`; a closed buffer, another store's buffer, or any invalid range raises before any backend call; the `KeyError` / `RuntimeError` mapping; a failed registration raises.
- `test/registered/unit/managers/test_output_store.py`: its `_MemoryBackend` gains `register` / `unregister` / `get_ranges` so it still instantiates; not run locally (needs torch and SGLang).
- Live Mooncake 0.3.13.post1 (Miles image), holder and reader on two H200 nodes over 400 Gb/s IB, an indexer-like field with 48 KiB rows. One reader reads one CP rank's zigzag rows at cp 4, or the whole field. Medians, every read checked byte by byte; 4 concurrent readers show the same pattern:

| read | bytes | fresh `ReadBuffer` per read | reused `ReadBuffer` | its one-time registration |
|---|---|---|---|---|
| cp4 rows, one 80k-token sample | 0.92 GiB | 0.135 s | 0.022 s | 0.110 s |
| whole field, one 80k-token sample | 3.66 GiB | 0.522 s | 0.086 s | 0.427 s |
| cp4 rows, two 200k-token samples | 4.58 GiB | 0.210 s | 0.108 s | 0.101 s |
| whole field, two 200k-token samples | 18.31 GiB | 0.774 s | 0.423 s | 0.326 s |

## Review Focus

- `MooncakeBackend.get_ranges`: grouping ranges by part key into the nested argument lists, and the per-range result check.
