# [Fix] lora: Keep per-expert MoE LoRA buffers for experts already wrapped

[Upstream PR](https://github.com/sgl-project/sglang/pull/46894) · state: closed · merged: True

## Original PR description

## Problem
Since #45231, `LoRAMemoryPool._has_moe_module` checks each `FusedMoE` against `should_apply_lora(name)`. The pool is built after `init_lora_modules()` wraps the experts, so the `FusedMoE` is named `<name>.base_layer`, and patterns anchored at `mlp.experts` (gpt-oss, MiMo-V2) reject it. These models then get dense 3D buffers:
- gpt-oss MoE LoRA fails CUDA graph capture with `NotImplementedError: virtual-expert MoE LoRA does not support padded Marlin outputs`
- the MiMo-V2 Tinker LoRA test raises `IndexError: tuple index out of range` at `lora_b_list[0].shape[3]` in `virtual_experts.py`

This broke the miles nightly gpt-oss and MiMo LoRA tests (https://github.com/radixark/miles/actions/runs/40528466754).

## Fix
Match `should_apply_lora` against the name without `.base_layer`. Experts a model keeps out of LoRA, such as DeepSeek-V4's routed experts, are never wrapped, so they stay excluded.

## Tests
- New regression test `TestHasMoeModuleAfterWrapping` in `test_mem_pool_ep_unit.py`: fails before the fix, passes after. All 61 tests in the file pass.
- End to end on 2x H200, miles `tests/e2e/megatron/model_scripts/test_gpt_oss_20b_moe_lora_ci.py`: fails at sglang `b8d46f2`, passes at `8237a5b` (before #45231) and with this fix.
- Miles CI with this PR pinned (`ci-sglang-pr: #46894` on https://github.com/radixark/miles/pull/4484), both tests that failed in the nightly now pass:
  - `test_gpt_oss_20b_moe_lora_ci.py`: PASS in 839s, both the per-expert and the shared-outer + virtual-experts configs (https://github.com/radixark/miles/actions/runs/40602473473)
  - `tests/e2e/lora/test_tinker_mimo_v2_6_4layer.py`: PASS in 233s (https://github.com/radixark/miles/actions/runs/40602452095)
