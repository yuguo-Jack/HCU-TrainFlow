# [AMD][CI][Fix] Guard FP32 LM head mm(out_dtype) fast path on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/34681) · state: closed · merged: False

## Original PR description

## Motivation

`test/registered/rl/test_fp32_lm_head.py` fails deterministically on the AMD `stage-b-test-1-gpu-small-amd` shard (`linux-mi300-1gpu-sglang`, partition 7):

```
RuntimeError: gemm input type at::BFloat16 and output type float is not supported for ROCm
```

The FP32 LM head fast path added in #32370 selects `torch.mm(..., out_dtype=torch.float32)` whenever `hidden_states.is_cuda`:

```python
use_mm_out_dtype = (
    hidden_states.is_cuda
    and hidden_states.dtype == lm_head.weight.dtype
    and hidden_states.dtype in (torch.float16, torch.bfloat16)
)
```

`is_cuda` is `True` on ROCm, but the mixed input/output GEMM is **not** available in the torch build the failing image ships. `rocm/sgl-dev:*-rocm700-*` is based on `rocm/sgl-dev:rocm7-vllm-20250904`, which pins torch `2.9.0a0+git7bcbafe` (upstream commit `7bcbafe`, 2025-08-04). In that source `at::cuda::blas::gemm<at::BFloat16, float>()` rejects unconditionally, before any backend dispatch:

```cpp
template <>
void gemm<at::BFloat16, float>(CUDABLAS_GEMM_ARGTYPES_AND_C_DTYPE(at::BFloat16, float)) {
  #ifdef USE_ROCM
  TORCH_CHECK(false, "gemm input type at::BFloat16 and output type float is not supported for ROCm");
  #else
  ...
  #endif
  gemm_internal<at::BFloat16, float>(...);  // unreachable on ROCm
}
```

pytorch#161540 (`a8d6943d36c1`, 2025-09-02) removed these four unconditional checks — in v2.9.1 the same guard reads `#ifndef USE_ROCM` and only covers the CUDA compute-capability case. The `rocm720` images use `rocm/pytorch:rocm7.2_..._pytorch_release_2.9.1` and so include it. **The dividing line is torch source older than 2025-09-02, not the ROCm version** — `rocm700-mi35x` (gfx950) also ships the old torch, while `rocm720-mi30x` (gfx942) ships 2.9.1, so this does not track gfx942 vs gfx950 either.

On newer torch there is a second, narrower raise site: the Composable Kernel branch inside `gemm_internal`. That one requires an explicit `torch.backends.cuda.preferred_blas_library("ck")` — `blasPreferredBackend()` only ever resolves to `Cublas` or `Cublaslt` from env, and SGLang never calls the setter — so it is not what CI hits. The two are distinguishable by message: the CK branch in `gemm_internal<at::BFloat16, float>` prints `at::Half` (an upstream copy-paste typo, still present in v2.9.1), whereas CI reports `at::BFloat16`, which only the unconditional check emits.

The capability gate below is deliberately agnostic to *which* of these applies. It never probes with a real GEMM: an earlier revision of this PR did, and the hipBLASLt algorithm lookup cost ~700 ms on MI355X without amortizing into the first real LM head GEMM.

This is pre-existing CI debt on `main`, not a regression from any in-flight PR; the same shard fails on scheduled `main` runs.

## Modifications

**`python/sglang/srt/layers/logits_processor.py`**

- Add `_supports_mm_fp32_out_dtype(device_type, dtype)` and make it a conjunct of `use_mm_out_dtype`, so an unsupported build falls back to the pre-existing explicit-FP32-cast `torch.matmul` path instead of raising. It decides from metadata, no GEMM:
  - **ROCm**: gate on `torch >= 2.9.0`, the first release containing pytorch#161540.
  - **CUDA**: BF16 additionally requires compute capability 8.0+, which torch enforces in the `#ifndef USE_ROCM` branch of the very same function. FP16 has no such restriction.

The version comparison is prerelease-aware on purpose. The rocm700 image ships `2.9.0a0+git7bcbafe`, and `utils/common.py`'s existing `torch_release` tuple discards the alpha marker:

| version string | `parse(...) >= parse("2.9.0")` | `.release >= (2,9,0)` |
|---|---|---|
| `2.8.0` | False ✅ | False ✅ |
| `2.9.0a0+git7bcbafe` (**the failing image**) | **False ✅** | **True ❌** |
| `2.9.0` | True ✅ | True ✅ |
| `2.9.1+rocm7.2.0.git7e1940d4` | True ✅ | True ✅ |

Using the `.release` tuple would leave the shard red. There is a regression test pinned to exactly this.

Deliberately **not** a plain `is_hip()` gate. `torch.mm(out_dtype=...)` works fine on ROCm with a current torch (verified on gfx950 / ROCm 7.2), and disabling it there would give up #32370's optimization on hardware that supports it — measured at 5.3× (batch 8) to 8.6× (batch 256) for a 152064x4096 BF16 LM head, plus a 2.32 GiB transient FP32 weight copy per forward. A bare `is_hip` gate would also have missed the CUDA sm80 rule and simply relocated the crash to V100.

**Coverage deliberately dropped**: the Composable Kernel BLAS backend rejects this op on *any* torch version, and the version gate does not catch it. Reaching CK requires an explicit `torch.backends.cuda.preferred_blas_library("ck")`; no env var selects it (`Context.h` maps `TORCH_BLAS_PREFER_{CU,HIP}BLASLT` to `Cublaslt` only) and SGLang never calls the setter.

**`test/registered/rl/test_fp32_lm_head.py`**

- Derive the expected op from the same helper rather than `torch.cuda.is_available()`, which encoded the wrong assumption.
- Add `force_support` to `_run_case`, pinning the helper's answer so **both** selection branches are exercised on every runner, NVIDIA included. Without it the suite is tautological: it asserts against the same predicate production consults, so the assertion holds by construction and the fallback branch is only ever reached on a host that already lacks support.
- Add `TestMMFP32OutDtypeGate` covering the version strings, the ROCm gate, the sm80 rule, and non-CUDA devices. Pure metadata, so it needs no GPU.

## Accuracy Tests

No numerical change on any backend that was already working — where the gate returns `True` the emitted op is byte-identical to before. Where it returns `False` the code takes the explicit-FP32-cast path, which is the same path used before #32370 and which is strictly higher precision than the `bf16`-input GEMM it replaces (both accumulate to FP32; the fallback additionally upcasts the inputs). No accuracy run is attached because on the available hardware (MI355X, ROCm 7.2, hipBLASLt) the gate returns `True` and this PR is a no-op at runtime.

## Speed Tests and Profiling

No steady-state delta, and no added device work anywhere:

- The fused `mm(out_dtype=fp32)` path is preserved bit-for-bit on every build that implements it.
- The gate issues **zero GEMMs**. `_TORCH_HAS_ROCM_MM_FP32_OUT` is a single `packaging.version.parse` at import. `_supports_mm_fp32_out_dtype` is `@lru_cache`d on `(device_type, dtype)`; on ROCm it only reads that bool, and `torch.cuda.get_device_capability()` is reached only on NVIDIA + BF16, once.
- Per forward this is one cached-function call plus a tuple hash (sub-microsecond, host-side), and it is the **last** conjunct of a short-circuiting `and`, so it is not even evaluated unless the three cheap dtype/device checks already passed.
- No CUDA-graph impact: the gate is Python, so it runs at capture time and never during replay.


### Unit tests

`11 passed` (16 subtests) on MI355X / ROCm 7.2 / torch 2.9.1. The suite needs no GPU for the gate tests.

Both branches of the selection are asserted on every runner via `force_support`, and the gate is asserted directly against the real-world version strings including the failing image's `2.9.0a0+git7bcbafe`.

**Mutation checks** — the PR head is green. To show the new tests are not tautological, the fix was broken locally in two ways and reverted; each breakage is caught:

| mutation applied locally, then reverted | caught by |
|---|---|
| drop `and _supports_mm_fp32_out_dtype(...)` from `use_mm_out_dtype` | `test_probe_unsupported_falls_back_to_explicit_fp32_matmul`, for both FP16 and BF16 — the fallback stops being selected and the ROCm raise comes back |
| swap the prerelease-aware `parse()` for a `.release` tuple compare | `test_torch_version_compare_is_prerelease_aware`, on exactly `2.9.0a0+git7bcbafe` — the failing image's torch gets misread as `>= 2.9.0` |

No pre-existing test reacts to the first mutation, which is why the original suite was blind to this regression.

### The trigger is a stale torch in the rocm700 image, not the CK BLAS backend

The failing image (base `rocm/sgl-dev:rocm7-vllm-20250904`) ships `torch 2.9.0a0+git7bcbafe` — upstream commit `7bcbafe`, 2025-08-04. In that source, `at::cuda::blas::gemm<at::BFloat16, float>()` rejects unconditionally on ROCm, *before* any backend dispatch:

```cpp
template <> void gemm<at::BFloat16, float>(...) {
#ifdef USE_ROCM
  TORCH_CHECK(false, "gemm input type at::BFloat16 and output type float is not supported for ROCm");
#else
  ...
#endif
  gemm_internal<at::BFloat16, float>(...);  // unreachable on ROCm
}
```

`gemm_internal` — the function holding the `Cublaslt`/`Ck` branches — is never reached, so `blasPreferredBackend()` is not consulted at all. pytorch#161540 (`a8d6943d36c1`, 2025-09-02) removed these four unconditional checks, and the ROCm 7.2 images use `rocm/pytorch:rocm7.2_..._pytorch_release_2.9.1`, which includes it. The dividing line is "torch source older than 2025-09-02", not the ROCm version.

Three independent points rule out CK:

- **Message fingerprint.** The `Ck` branch in `gemm_internal<at::BFloat16, float>` prints `at::Half` (upstream copy-paste typo, still present in v2.9.1). CI reports `at::BFloat16`, which only the unconditional check emits.
- **`Ck` cannot be the default.** `Context.h` maps `TORCH_BLAS_PREFER_{CU,HIP}BLASLT` to `Cublaslt` only, and `blasPreferredBackend()` resolves to `Cublas` or `Cublaslt`. `Ck` requires an explicit `torch.backends.cuda.preferred_blas_library("ck")`, which SGLang never calls; the job log has no `TORCH_BLAS_*` either.
- **Not arch-gated.** `rocm700-mi35x` (gfx950) also ships the old torch while `rocm720-mi30x` (gfx942) ships 2.9.1, so this tracks the ROCm flavor rather than gfx942 vs gfx950.

Worth noting that forcing `preferred_blas_library("ck")` on 2.9.1 exercises a *different* raise site than CI hits — same symptom, so the fix is still validated, but it isn't a faithful repro.

### Asks

1. **Reword the docstring.** As written it will send the next person debugging this to the wrong place. Suggest something like: older ROCm torch builds (pre-pytorch#161540) reject `gemm<BFloat16,float>` unconditionally; newer ones reject only under the CK backend.
2. **The test is currently tautological.** `_expected_operation` calls the same probe the production code calls, so the assertion holds by construction and the fallback branch is only ever exercised on a host that already lacks support. Patching `_supports_mm_fp32_out_dtype` to force both branches would cover the real regression risk on every runner, including all the NVIDIA ones.
3. **`except (RuntimeError, TypeError)` also swallows `torch.cuda.OutOfMemoryError`**, and `lru_cache` then pins that negative for the process lifetime with no log line — the optimization would silently disappear and be undiagnosable. At minimum, log which path was selected.

Two notes for the record, neither blocking. The `gemm_and_bias` unconditional ROCm rejection is still present in v2.9.1, so extending this fast path to a bias-fused `addmm(out_dtype=fp32)` would break again even on new torch + hipBLASLt. And since the real trigger is a base image pinned ~11 months back, refreshing `rocm7-vllm-20250904` is the more direct fix — worth doing in parallel, as merging only this guard leaves the stale image in place.
