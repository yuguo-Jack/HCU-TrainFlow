# [Fix] patch_torch: rebuild CUDA tensors in processes without the reductions patch

[Upstream PR](https://github.com/sgl-project/sglang/pull/45477) · state: open · merged: False

## Original PR description

## Motivation

After `monkey_patch_torch_reductions()` runs, every CUDA tensor that process pickles for IPC is reduced to `(_rebuild_cuda_tensor_modified, args)`. `_rebuild_cuda_tensor_modified` then calls `reductions._rebuild_cuda_tensor_original`, which only exists in processes that also applied the patch. Any receiver that did not apply it fails while unpickling:

```
  File "/usr/lib/python3.12/multiprocessing/queues.py", line 122, in get
    return _ForkingPickler.loads(res)
  File ".../sglang/srt/utils/patch_torch.py", line 82, in _rebuild_cuda_tensor_modified
    return reductions._rebuild_cuda_tensor_original(*args)
AttributeError: module 'torch.multiprocessing.reductions' has no attribute '_rebuild_cuda_tensor_original'
```

RL frameworks apply this patch in their training process so that they can send weights to SGLang over CUDA IPC (miles does it on every weight update). Other libraries in that process also hand CUDA tensors to their own spawned workers, and those workers know nothing about the patch. One concrete case is Megatron's `--async-save --use-persistent-ckpt-worker`, where the trainer puts the checkpoint request, CUDA tensors included, on a `spawn` queue for the persistent checkpoint worker. In miles runs without `--colocate`, the worker dies on the first save, and training hangs in that save.

## Modifications

- `_rebuild_cuda_tensor_modified` still maps the device UUID back to a local index. It now falls back to torch's `reductions.rebuild_cuda_tensor` when `_rebuild_cuda_tensor_original` is absent. When the receiver has applied the patch, behaviour is unchanged.
- `test/registered/rl/test_patch_torch.py`: the existing sender/receiver test now also runs with a receiver that never calls `monkey_patch_torch_reductions()`. The tensor must still arrive on the receiver's matching device.

## Testing

On 2x MI350X, `rocm/sgl-dev:miles-rocm10-mi35x-20261019` (its `patch_torch.py` is identical to `main`):

- `python -m pytest test/registered/rl/test_patch_torch.py` on 2 GPUs:
  - Without the fix: the new case fails with the `AttributeError` above, and the existing case passes.
  - With the fix: both pass.
- End to end with miles `main` (Qwen3-4B GRPO, 1 trainer GPU + 1 rollout GPU, `--async-save --use-persistent-ckpt-worker --save-interval 2`):
  - Without the fix: the checkpoint worker crashes on the first save (iteration 1). No training step runs after it, `iter_0000001/` stays empty, and no tracker file is written.
  - With the fix: the saves at iterations 1, 3 and 5 complete, and the job exits cleanly. Steps 2-3 and 4-5 train while the iteration 1 and 3 saves are in flight. A resume from the iteration 3 checkpoint (`--ckpt-step 3`, synchronous saves) loads it and trains on.
