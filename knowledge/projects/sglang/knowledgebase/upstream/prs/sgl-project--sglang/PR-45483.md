# [Fix] spec: init the active attention backend for eager IDLE batches

[Upstream PR](https://github.com/sgl-project/sglang/pull/45483) · state: closed · merged: False

## Original PR description

## Motivation

With EAGLE v2 MTP, DP attention and a DSA model (GLM-5.2, `index_share_for_mtp_iteration=true`), the decode worker crashes
with `Memory access fault by GPU node-N ... Reason: Unknown` after 20-100 minutes of load. The faulting kernel is the
DSA top-k (`coop_topk_kernel<2048,...>`) called from `Indexer._forward_cuda_k_only` on an `IDLE` batch.

Chain (file references are upstream main):

1. When a DP rank sees a batch that cannot use CUDA graphs (with index sharing, a batch without a DSA seed sets
   `EagleDraftInput.cuda_graph_compatible = False`), `dp_attn._spec_input_cuda_graph_compatible` min-reduces this over
   DP and every rank runs eager, including padded `IDLE` ranks.
2. `EAGLEWorkerV2._draft_forward_idle` (`eagle_worker_v2.py:881`) runs each draft step under
   `ForwardContext(attn_backend=draft_attn_backend.attn_backends[i])`.
3. `EagerRunner._execute_idle` re-initializes only `model_runner.attn_backend`. For the draft runner that is the
   draft-extend backend, not `attn_backends[i]`.
4. Layers read the forward-context backend, so the DSA indexer sees the `forward_metadata` of an earlier real batch.
   `_should_skip_logits_computation` takes the k-only path, which builds `index_topk`-wide (2048) dummy logits and ranks
   them with the stale lengths (~1e5 in our dumps). The kernel reads past the row: a GPU fault when the next page is
   unmapped, silent garbage otherwise.

## Modifications

In `EagerRunner._execute_idle` (bs > 0), after `model_runner.attn_backend.init_forward_metadata(forward_batch)`, also
init the active forward-context backend when it is a different object. This adds 7 lines and no new import. The
behaviour is unchanged when the two backends are the same object, which covers every non-draft runner.

Unit test `test/registered/unit/model_executor/runner/test_eager_idle_active_backend.py` (CPU):
- the context backend differs → both backends are initialized. This test fails without the fix.
- the same backend → initialized once.
- bs = 0 → no init.

Open points for reviewers:
- The fix lives in `EagerRunner`, which is the one place that knows both the runner backend and the active context.
  An alternative is for `_draft_forward_idle` to init `attn_backends[i]` itself.
- On the `bs == 0` branch only `model_runner.attn_backend.forward_metadata` is cleared; this PR does not change that.

## Accuracy Tests

Not applicable: the change only affects metadata of padded IDLE batches, whose outputs are discarded.

## Speed Tests and Profiling

Validated on the equivalent patch applied to an sglang v0.5.21-based tree. Setup: GLM-5.2-MXFP4, 1P1D on one MI355X
node (P TP4, D TP4/DP4 + DP attention), EAGLE MTP, `index_share_for_mtp_iteration=true`, multi-turn agent workload at
concurrency 56.

| run | fix | result |
|---|---|---|
| 5+ runs | no | GPU memory access fault after 23-100 min each |
| 2 runs with an instrumented top-k call site | no | 12 and 20 out-of-row top-k calls in ~15-20 min, all on `ForwardMode.IDLE` with stale metadata |
| 1 run, same instrumentation | yes | full ~88 min benchmark, 0 bad calls, 0 faults |
| 1 run, no instrumentation | yes | ~170 min, 0 faults; benchmark score 21814 vs 22045 with `index_share=false` on the same node |
