# [DeepSeek-V4.1] Extend norm and MoE fusion batch limits

[Upstream PR](https://github.com/sgl-project/sglang/pull/41628) · state: closed · merged: False

## Original PR description

Continued in #47364 with the remaining fixes adapted to current upstream. GitHub rejected reopening this PR.

## Motivation

DeepSeek-V4.1's MXFP8 input path stops using fused RMSNorm and quantization above eight token rows. Larger batches launch a separate quantizer that reads the BF16 output back from memory. This adds a kernel launch and a read before the next projection.

The fused scale writer also assumes all rows fit in one 128-row tile. Row 128 would write over row 0's scales if we only raised the batch limit. The old eight-row limit kept that bug out of the active path.

## Modifications

Run fused RMSNorm and MXFP8 quantization through 512 rows, including the four-stream hyper-connection (HC) combine. Add the missing row-tile offset and zero unused scale entries on every CUDA graph replay.

Extend HC decode/verification and MoE finalize paths through 1,024 rows, and query RoPE/store through 4,095 rows. Keep the model, backend, dtype and numerical-mode checks around these paths.

Raise the TP4 MoE push slot from 4 MiB to 12 MiB and its counter count from 512 to 1,024:

```text
1,024 rows × 5,120 values × 2 bytes = 10 MiB needed per slot
2 slots × 4 ranks × 12 MiB          = 96 MiB allocated per rank
```

The push workspace grows from 32 MiB to 96 MiB per rank, plus 2 KiB of counters. It is reused across layers. Other TP sizes still check their buffer and counter capacity before using the fused path.

## Accuracy Tests

297 tests and 12 subtests passed on B300: 240 kernel/dispatch tests and 57 TP4 collective cases. The 30 dispatch tests also passed without a GPU; their TP2/TP4/TP8 communicators are mocked. Hardware collective coverage is TP4.

Tests cover partial scale tiles, strided inputs, BF16/FP32 HC coefficients, GEMM consumption of the fused output, RoPE output padding and graph replay with changed inputs. Each collective case runs three eager calls and six replays against NCCL and independent HC arithmetic, using exactly representable synthetic inputs.

RMSNorm comparisons use `rtol=0.008, atol=1e-6`. Quantized values and live scales match standalone quantization of the returned BF16 output exactly. Full-model accuracy and serving-memory validation are pending.

## Speed Tests and Profiling

Operator benchmark on one B300 with PyTorch 2.13.0+cu130, Triton 3.7.1 and FlashInfer 0.6.18. BF16 inputs, FP32 HC coefficients and CuTe-DSL quantization. Five warmups, then five 100 ms CUDA-graph measurements per version in alternating order. Medians below.

The baseline follows dispatch at `b95329a74d26397825ebe55c02706c2e2f5fcc28` using its unchanged component kernels.

| Operator | Input shape | Before | After |
| --- | --- | ---: | ---: |
| RMSNorm + MXFP8 | 128 × 1280 | 3.15 µs | 1.84 µs |
| RMSNorm + MXFP8 | 128 × 5120 | 5.94 µs | 3.70 µs |
| HC combine + RMSNorm + MXFP8 | 128 × 4 × 5120 | 9.88 µs | 6.60 µs |
| RMSNorm + MXFP8 | 512 × 1280 | 8.52 µs | 5.13 µs |
| RMSNorm + MXFP8 | 512 × 5120 | 11.67 µs | 6.92 µs |
| HC combine + RMSNorm + MXFP8 | 512 × 4 × 5120 | 17.09 µs | 11.69 µs |
| Query RoPE + store | 128 × 16 × 512 | 7.59 µs | 3.98 µs |
| Query RoPE + store | 512 × 16 × 512 | 11.97 µs | 9.96 µs |
| Query RoPE + store | 1024 × 16 × 512 | 19.90 µs | 18.49 µs |

At 128 rows, profiling shows RMSNorm/quantization going from two launches to one, HC combine/norm/quantization from three to two, and RoPE/store from two to one. The HC count includes zeroing the scale buffer. These are operator timings; end-to-end TTFT and the MoE speedup still need measurement.
