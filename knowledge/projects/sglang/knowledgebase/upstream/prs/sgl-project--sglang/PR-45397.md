# [Fix] scheduler: Don't idle-sleep while an EPD request waits for encoder embeddings

[Upstream PR](https://github.com/sgl-project/sglang/pull/45397) · state: open · merged: False

## Original PR description

## Motivation

With `--sleep-on-idle` and `--language-only` (encoder transfer backend `zmq_to_scheduler` or `mooncake`), every multimodal request takes about 1 s longer than it should, however small the image.

When the request reaches the scheduler, it waits in `mm_receiver.waiting_list` for its embeddings. Nothing else is runnable, so the event loop calls `maybe_sleep_on_idle()`, which blocks in `IdleSleeper.maybe_sleep()` → `poller.poll(1000)`. That poller only watches `recv_from_tokenizer` and `recv_from_rpc`. The embeddings arrive on the request's own receive socket, which the poller doesn't see, so the request is only picked up when the 1 s poll times out.

## Modifications

- `Scheduler.maybe_sleep_on_idle`: don't sleep while `mm_receiver` has waiting requests. The loop keeps polling the receive sockets until the embeddings land, then sleeps normally once nothing is waiting. Nothing changes when EPD is off (`mm_receiver is None`) or when no request is waiting.
- New CPU unit test `test/registered/unit/managers/test_idle_sleep_epd_wait.py` (`base-a-test-cpu`). It covers the pending-embedding case, which fails on the current code and passes with this change, plus both cases where sleeping must still happen.

## Speed Tests and Profiling

Qwen4Exp language server on one GPU with `--sleep-on-idle --language-only`, plus an `--encoder-only` server on a second GPU. Each request is one image plus a short prompt, about 15 output tokens, end to end. The 512×512 row uses a new image each time; the other rows are the second request for the same image:

| Image | Before | After |
|---|---|---|
| 512×512 | 1.19 s | 0.19 s |
| 1024×1024 | 1.17 s | 0.30 s |
| 1920×1080 | 1.17 s | 0.53 s |

(The encoder took 26 ms to encode the 512×512 image. Before the fix, the scheduler log showed prefill starting about 1 s after `/encode completed`, with a 6 ms `queue_duration`.)
