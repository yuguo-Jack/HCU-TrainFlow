# [Fix] flashinfer: convert base-2 LSE to natural log in _safe_merge_state Triton fallback

[Upstream PR](https://github.com/sgl-project/sglang/pull/46845) · state: open · merged: False

## Original PR description

Fixes #46793.

## Motivation

`FlashInferAttnBackend._safe_merge_state` merges the ragged and paged
prefill halves. Its two branches disagree on the log-sum-exp (LSE)
convention:

- The primary branch, FlashInfer's `merge_state`, takes and returns
  **base-2** LSE, which is what FlashInfer prefill returns.
- The fallback branch, the in-tree Triton `merge_state_triton`, uses
  **natural** log (`tl.exp` / `tl.log` in the kernel).

`_safe_merge_state` passed the same base-2 LSEs to both branches, so on
the fallback path (many query heads per rank, e.g. DP attention with
`attn_tp_size=1`) each half was weighted with `exp(delta / ln 2)`
instead of `exp(delta)`. Nothing errored; the merged attention output
was silently wrong. The issue reports ~0.17–0.20 relative error against
a float64 reference on real FlashInfer partial states.

This is the non-MLA counterpart of the MLA chunked-prefix LSE issue
(#40903 / #46313): those PRs touch the MLA backends and the
`merge_state` wrapper, not this function.

## Modifications

- `python/sglang/srt/layers/attention/flashinfer_backend.py`:
  in the Triton fallback branch of `_safe_merge_state`, convert the
  input LSEs from base 2 to natural log (`* ln 2`) before calling
  `merge_state_triton`, and convert the returned LSE back to base 2
  (`/ ln 2`) so both branches keep the same return convention. The
  shared Triton kernel is untouched: its other callers expect natural
  log. The only caller of `_safe_merge_state` discards the returned
  LSE, but preserving the base-2 convention keeps the function
  correct for any future caller.

## Tests

No GPU or torch is available on this machine, so the fix could not be
run against FlashInfer itself. Instead, the merge math was verified
with a NumPy harness that transcribes the Triton kernel formula
exactly (natural-log merge) and compares against a float64 reference:

- Feeding base-2 LSEs straight into the natural-log merge (the old
  code): relative error ~0.12, the same order as the ~0.17–0.20
  reported in the issue.
- With the `* ln 2` / `/ ln 2` conversion (the new code): merged
  output and returned base-2 LSE both match the float64 reference to
  ~6e-8 across 5 randomized trials.

Also verified: `ruff check --select F401,F821,F823,UP037` passes,
`ruff format --check` passes, `python3 -m py_compile` passes, and
`git diff --check` is clean on the touched file. No existing test
references `_safe_merge_state`, so no test contradicts the change.

The conversion looks right to me. `merge_state_triton` uses `tl.exp` and `tl.log`, and FlashInfer hands back base-2 LSE, so scaling by ln 2 going in and dividing it out coming back is the fix.

A small test would help since this path is hard to hit. You could patch `_merge_state_max_safe_num_heads` to return 0 to force the Triton branch, then check `_safe_merge_state` matches FlashInfer's `merge_state` on the same inputs. That'd catch the next time the two drift.

- AgentHan115 · comment · 2026-10-29T04:07:17Z · [source](https://github.com/sgl-project/sglang/pull/46845#issuecomment-6487635253)

@saitarrun Thanks for picking this up. I validated the fix on SM89 (RTX 4070 Ti SUPER, FlashInfer 0.7.2, Triton 3.8.0, torch 2.14.1+cu130, main at dea05ca16) with real `BatchPrefillWithRaggedKVCacheWrapper.forward_return_lse` states. Each state is a 512-token prefix plus 32 extend tokens, head_dim 128, 8 KV heads, checked against float64 attention over the full KV.

| `_safe_merge_state` path | dtype | main: rel L2 error | this PR: rel L2 error |
|-|-|-|-|
| 32 q heads (FlashInfer branch) | bf16 / fp16 | 0.31% / 0.04% | 0.31% / 0.04% |
| 96 q heads (Triton fallback) | bf16 / fp16 | 16.5–17.0% | **0.31% / 0.04%** |
| 32 q heads, fallback forced, vs `flashinfer.cascade.merge_state` | bf16 / fp16 | max abs 0.09–0.19 | max abs ≤ 1.2e-4, LSE ≤ 1e-6 |

Empty segments (`-inf` LSE on either side) still return the other side exactly, with no NaNs.

**One issue with the new test:** `s_a` and `s_b` are created as `float16`. `merge_state_triton` then fails to compile with `Ternary expression with dynamic condition has inconsistent types fp32 and fp16`, so the test errors out both with and without the fix. FlashInfer returns LSE as fp32, so I'd suggest:

```suggestion
        s_a = torch.randn(num_tokens, num_heads, device="cuda", dtype=torch.float32)
        s_b = torch.randn(num_tokens, num_heads, device="cuda", dtype=torch.float32)
```

With fp32 LSE, the test fails on main (75.6% of elements mismatched, max abs diff 0.34) and passes with this PR, so it works as a regression test.

I'd offered to send this fix in #46793. Since the root cause and analysis come from there, would you add me as a co-author?
