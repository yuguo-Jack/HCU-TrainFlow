# Fix MiniMax M2 non-null arguments in nullable schemas

[Upstream PR](https://github.com/sgl-project/sglang/pull/42058) · state: closed · merged: False

## Original PR description

## Motivation

MiniMax M2 tool arguments with nullable schemas lose valid non-null values. For example, `{"type": ["integer", "null"]}` converts the model's `42` to JSON `null`, in both ordinary and streaming responses. Pydantic-style `anyOf` schemas and enums containing `null` have the same problem.

## Modifications

Only treat the parameter's value as a null marker; allowing `null` in its schema no longer bypasses the existing type converters. Preserve the existing `null`/`none`/`nil` aliases.

Add CPU tests through `FunctionCallParser("minimax-m2")` for nullable scalar/container types, `anyOf`/`oneOf`, enums, explicit nulls, and non-nullable controls. Exercise ordinary parsing and streaming with complete frames, parameter boundaries, and character splits after the atomic tool-start marker.

## Accuracy Tests

- New regression suite: **5 tests and 56 subtests pass**. Before the change, 36 non-null nullable cases fail and 20 control subtests pass.
- Existing function-parser module plus the new suite: **240 tests and 107 subtests pass**; 15 existing DeepSeek tests requiring unavailable Triton-backed tokenizer setup are deselected.
- Tests execute the actual protocol and parser source on CPU, bypassing only GPU-facing package initializers in the local harness. No model/GPU inference was run.

Not applicable: this fixes argument conversion and makes no inference-performance claim.
