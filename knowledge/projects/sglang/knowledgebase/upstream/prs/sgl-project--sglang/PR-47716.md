# [Fix] scheduler: Decide early result processing before scheduling the next batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/47716) · state: closed · merged: True

## Original PR description

Stacks on #43900.

The overlap loops decided whether to process the last result early after the next batch was already scheduled, then processed it before launching that batch. A request the early processing finished was still launched with the batch. Two triggers reach this: `SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP` on consecutive extend steps (including DP-converted decode steps and mixed steps), and spec + grammar for algorithms without grammar overlap (NGRAM), where an EOS or stop finish rides the next decode launch.

- `should_process_last_batch_early(last_batch)` replaces `is_disable_overlap_for_batch` and is decided before scheduling from the only result still pending, so the early processing runs before `get_next_batch_to_run`, whose filter then drops the requests it finished. Used by `event_loop_overlap` and `event_loop_overlap_disagg_decode`; the opportunistic unified-memory flush moves with it.
  - After a prefill, for its TTFT: `SGLANG_DISABLE_OVERLAP_AFTER_PREFILL` is set and `last_batch` is extend (`is_extend_in_batch` under DP, already synced across ranks). This renames `SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP`, which still works as a deprecated alias: the next batch is not built yet, so the rule can no longer require it to be a prefill too.
  - Grammar: `last_batch.grammar_needs_sync()`. `grammar_needs_sync` now includes the non-spec check its only caller applied.
- The NGRAM worker decides per request whether to splice the previous round's accepted tokens: a request whose `inflight_steps` (from #43900) is above one at this launch still has an earlier round unprocessed. It used to infer this for the whole batch from `grammar_needs_sync()`, which no longer matches once the decision is made before scheduling, and which already double-spliced the old decode rows on the first decode after a prefill step under overlap (their previous result was processed one iteration earlier).
- The `not r.finished()` filter in `_join_launched_reqs` is removed: no processing runs between scheduling and launch, so no launched row is already finished.
- `test_scheduler_running_reqs.py` drives the overlap loop with an NGRAM grammar row and asserts on the launched rows (the finished row is launched on main) and on each row's unprocessed-round state at launch; `test_ngram_worker_prompt.py` sets the per-request count.

No behavior change in the default configuration. With `SGLANG_DISABLE_OVERLAP_AFTER_PREFILL` (or the old name) set, the last result is processed early after any extend step, also when the next step is decode or idle; before, only when the next step was a prefill too. With NGRAM and grammar, it is processed early whenever the last batch holds a grammar request, also when the next step is a prefill. NGRAM under overlap no longer splices tokens already in a request's output, which changes its drafts (acceptance only, not outputs).
