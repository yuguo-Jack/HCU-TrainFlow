# [Perf] srt: Record on the host whether an extend batch completes a prompt

[Upstream PR](https://github.com/sgl-project/sglang/pull/45487) · state: closed · merged: True

## Original PR description

## Motivation

Model code that does extra work only on the forward that finishes a request's prompt (a head that reads the last prompt token, an output published once per request) has no host-side way to tell whether the current extend batch contains such a row. The available check is on the device: compare `extend_prefix_lens + extend_seq_lens` with `orig_seq_lens`, then `.any().item()` to decide whether to run or publish anything. That is one blocking device sync per extend forward, paid even when every row is a non-final prefill chunk.

## Modifications

- `ForwardBatch.contains_last_prefill_chunk`: a plain `bool` that `init_new` snapshots from request bookkeeping. For a non-speculative extend batch it is `True` when any request that is not a running decode row ends this chunk at `len(full_untruncated_fill_ids)`, i.e. this forward produces that request's next token. Speculative verify batches and the decode rows mixed into a chunked prefill do not count. The dataclass default stays `True`, so synthetic capture and replay batches built directly by the graph runners keep every gate open.
- `TboForwardBatchPreparer.filter_batch` copies the field to both child batches, like the other forward-level flags.
- `init_new` reads two more `Req` fields, so the stand-in request in the mamba metadata test gains `extend_end` and `full_untruncated_fill_ids`.

Why not reuse `ScheduleBatch.contains_last_prefill_chunk`: that flag is set by the scheduler for pipeline parallelism and is false only for a lone non-final chunk. The new field is derived per request when the forward batch is built, so every builder of an extend batch gets the same answer, including mixed batches and zero-token requests whose prompt-final step is their only output.

`init_new` does not mutate the `ScheduleBatch` for this; it only reads `reqs`, `decoding_reqs` and `forward_mode`.

## Accuracy Tests

Not applicable: no numerics change. The field is a new host-side bool with no reader inside this repository yet; existing behaviour is unchanged.

## Benchmarking and Profiling

Not run: the change adds one Python loop over `batch.reqs` per extend forward and no device work.
