# [Feat] [Intel] disaggregation: Support Intel XPU in the EPD multimodal encoder path

[Upstream PR](https://github.com/sgl-project/sglang/pull/47961) · state: open · merged: False

## Original PR description

[Feat] [Intel] disaggregation: Support Intel XPU in the EPD multimodal encoder path

## Motivation

EPD (encoder / language disaggregation) did not run on Intel XPU. The encoder
server and the language-side receiver hardcoded CUDA: landing buffers and the
`EmbeddingPool` were allocated on `"cuda:{gpu_id}"`, streams came from
`torch.cuda.current_stream`, and the tensor-to-CPU and `/send` synchronize steps
were gated on `is_cuda`. On XPU every image request failed with
`Torch not compiled with CUDA enabled`, and the skipped `/send` synchronize could
let the transfer read embeddings before the device writes landed.

The second commit makes the language server return an error for a request whose
embedding never arrives, instead of exiting.

## Modifications

**1. disaggregation: Support Intel XPU in the EPD multimodal encoder path**

- `encoder/receiver.py`: add `is_epd_accelerator()`, the one place that decides
  which devices EPD treats as accelerators (CUDA and XPU). The RDMA landing buffer
  and `EmbeddingPool` are allocated on the runtime device type. `EmbeddingPool`
  takes keyword-only `device_type`, `gpu_id` and `size_bytes`.
- `encoder/server.py`: `TensorWrapper` copies accelerator tensors to CPU; the
  `/send` synchronize and both embedding-cache synchronizes run through
  `current_device_stream`, on accelerators only.
- `utils/common.py`: add `current_device_stream()`.
- On CUDA and ROCm the calls resolve to the same `torch.cuda` calls; other devices
  keep their existing behaviour.
- New `test/registered/e2e/disaggregation/test_epd_disaggregation_xpu.py`
  (nightly, `nightly-xpu-kernel-main-2-gpu`): an encoder-only and a language-only
  server on two XPUs over the Mooncake encoder transfer backend, answering an image
  chat request. Mooncake runs on TENT with the default protocol, so the embedding
  goes card to card through Level Zero IPC, as in
  `disaggregation/test_disaggregation_xpu.py`. One class lands the embedding in the
  default `EmbeddingPool`, the other disables the pool so each request allocates its
  own landing buffer. Each class also reads the encoder's Mooncake log to check that
  the copy went card to card over Level Zero IPC, not a TCP fallback. Outside CI the
  classes skip with fewer than 2 XPUs; in CI they fail, as does a missing Mooncake
  build.
- Docs: `advanced_features/epd_disaggregation.mdx` gains an "Intel XPU" section with
  launch commands, the requirement that both servers see both cards (for Level Zero
  IPC), and `SGLANG_ENCODER_IMAGE_PROCESSOR_USE_GPU=1` to match colocated image
  embeddings. `hardware-platforms/xpu.mdx` links to it.

**2. disaggregation: Don't crash the language server when an EPD receive fails**

In language-only mode a request's `input_ids` are filled in only when its embedding
arrives. When the receive failed, timed out or could not start, `create_req` built
the abort `Req` from `input_ids=None`, and streaming the abort called
`len(origin_input_ids)` (now in `SchedulerOutputStreamer.build_request_stats`). The
`TypeError` killed the scheduler and every in-flight request. `create_req` now passes
an empty prompt when `input_ids` is `None`, so only the failed request returns an
error. Not XPU-specific; covered by a new case in `test_encode_receiver.py`.


## Accuracy Tests

The question is whether EPD answers like colocated serving on the same hardware, so
colocated serving is the reference.

Setup: Qwen/Qwen2.5-VL-3B-Instruct, `--attention-backend intel_xpu --page-size 64`,
TP 1, decode graphs off (the XPU default), cards 0 and 2. sgl-eval 0.1.3 (own venv),
`mmmu_pro`, first 300 questions,
`--temperature 0.000001 --seed 0 --max-tokens 4096` (top_p 0.95 by default).

| Setup | Cards | MMMU-Pro (300 q) | Hit max_tokens | Errors |
|---|---|---|---|---|
| Colocated | 0 | 29.00% | 3.33% | 0 |
| EPD, encoder preprocessing on CPU (default) | 0 → 2 | 31.00% | 1.33% | 0 |
| EPD, `SGLANG_ENCODER_IMAGE_PROCESSOR_USE_GPU=1` | 0 → 2 | 27.33% | 6.33% | 0 |

Paired against colocated, neither difference is significant (McNemar p = 0.48 and
0.52). Decoding is not reproducible across batch compositions at sgl-eval's
concurrency of 64: only 17 to 33 of the 300 answers are word-for-word identical
between any two runs, and answers diverge a few hundred characters in.

To check that EPD feeds the language model the right image, I dumped the tensors
for one image (grid 1x28x40, 280 tokens) at each stage:

| Comparison | Result |
|---|---|
| Encoder output vs embedding received by the language server (Mooncake P2P) | bit-identical |
| Image embedding, colocated vs EPD encoder, default CPU preprocessing | 10.6% relative difference |
| Image embedding, colocated vs EPD encoder, `SGLANG_ENCODER_IMAGE_PROCESSOR_USE_GPU=1` | bit-identical |

The transfer path this PR adds is exact. The colocated-vs-EPD difference comes from
EPD's default: the encoder preprocesses images on CPU
(`SGLANG_ENCODER_IMAGE_PROCESSOR_USE_GPU=False`), while the colocated tokenizer runs
the fast image processor on the device. That shifts the pixel values by about 0.7%
(same grid), which the vision tower amplifies. This default is not XPU-specific and
is left unchanged here. With GPU preprocessing, the single-request greedy answer for
the probed image matches colocated.

Notes:
- All runs cap answers at `--max-tokens 4096` (about 9x the typical answer length).
  sgl-eval 0.1.3 always sends `repetition_penalty 1.0`; the model recommends 1.05.
- 300-question subset, single run per setup.

## Speed Tests and Profiling

Workload from the Qwen2.5-VL cookbook: `bench_serving --backend sglang-oai-chat
--dataset-name image --image-count 2 --image-resolution 720p --random-input-len 128
--random-output-len 1024`, seed 42, so every setup gets identical requests. Latency
uses the cookbook's 10 prompts at concurrency 1. Throughput uses 200 prompts at
concurrency 32 instead of 1000 at 100, to fit a single B60.

All servers run with decode graphs on (`--cuda-graph-backend-decode full`; they are
off by default on XPU). 


Latency (10 prompts, concurrency 1):

| Setup | Cards | Output tok/s | TTFT p50 | TPOT p50 | E2E p50 |
|---|---|---|---|---|---|
| Colocated | 4 | 53.7 | 626 ms | 17.1 ms | 6.6 s |
| Colocated, `--dp-size 2` | 4, 6 | 54.0 | 631 ms | 16.7 ms | 6.5 s |
| EPD, CPU preprocessing | 4 → 6 | 54.3 | 641 ms | 16.7 ms | 6.5 s |
| EPD, GPU preprocessing | 4 → 6 | 55.5 | 563 ms | 16.6 ms | 6.4 s |

Throughput (200 prompts, concurrency 32):

| Setup | Cards | Output tok/s | TTFT p50 | TTFT p99 | TPOT p50 | E2E p50 |
|---|---|---|---|---|---|---|
| Colocated | 4 | 536.1 | 680 ms | 17.3 s | 53.9 ms | 28.8 s |
| Colocated, `--dp-size 2` | 4, 6 | 802.5 | 647 ms | 9.3 s | 34.4 ms | 19.6 s |
| EPD, CPU preprocessing | 4 → 6 | 723.3 | 769 ms | 11.0 s | 38.4 ms | 21.3 s |
| EPD, GPU preprocessing | 4 → 6 | 733.3 | 678 ms | 9.8 s | 38.3 ms | 21.4 s |

- EPD on two cards gives 1.35x (CPU preprocessing) to 1.37x (GPU preprocessing) the
  throughput of one colocated server, and about 90% of colocated `--dp-size 2` on
  the same two cards: EPD moves vision encoding to the encoder card, while all
  prefill and decode stay on the language card. At concurrency 1 all setups are
  within about 3% of each other. Single runs: concurrency-1 numbers vary by about
  8% run to run.
- All 200 + 10 requests succeeded in every run. Every decode batch replayed a
  captured XPU graph on every server, and every EPD transfer went card to card
  through Level Zero IPC.

Decode graphs on vs off, throughput (200 prompts, concurrency 32; the off runs used
the same B60 model):

| Setup | Graphs off | Graphs on |
|---|---|---|
| Colocated | 444.8 tok/s | 536.1 tok/s |
| Colocated, `--dp-size 2` | 630.2 tok/s | 802.5 tok/s |
| EPD, CPU preprocessing | 601.6 tok/s | 723.3 tok/s |
| EPD, GPU preprocessing | 648.9 tok/s | 733.3 tok/s |

Commands (both servers must see both cards for P2P):

```bash
export MC_USE_TENT=1 ZE_AFFINITY_MASK=4,6 TORCHINDUCTOR_USE_STATIC_CUDA_LAUNCHER=0
COMMON="--model-path Qwen/Qwen2.5-VL-3B-Instruct --trust-remote-code --device xpu \
  --attention-backend intel_xpu --page-size 64 --tp 1 --encoder-transfer-backend mooncake"
python -m sglang.launch_server $COMMON --encoder-only --base-gpu-id 0 --port 32100
python -m sglang.launch_server $COMMON --language-only --base-gpu-id 1 --port 32101 \
  --encoder-urls http://127.0.0.1:32100 --cuda-graph-backend-decode full
```

Environment: 8x Intel Arc Pro B60 , torch 2.14.0+xpu,
oneAPI runtime 2026.1.0, oneCCL 2022.1.2 (torch pins 2022.1.1; only the `--dp-size 2`
runs use oneCCL), Mooncake transfer engine with TENT built with `-DUSE_XPU=ON`.
`TORCHINDUCTOR_USE_STATIC_CUDA_LAUNCHER=0` works around an inductor static Triton
launcher issue on XPU (likely pytorch/pytorch#199511), independent of this PR.
