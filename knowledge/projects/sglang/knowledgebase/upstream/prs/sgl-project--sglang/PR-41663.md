# [AMD][Perf][MiniMax-M3] Fuse the bf16->fp8 main-KV cast into the sparse-layer paged scatter

[Upstream PR](https://github.com/sgl-project/sglang/pull/41663) · state: open · merged: False

## Original PR description

## Motivation

Part of optimizing MiniMax-M3 for **vision-language serving** -- one image per request at 512x512 to 2048x1600, Measurements are on that VL sweep.

On MiniMax-M3 sparse layers the main-KV store writes bf16 into an fp8 pool, which
costs a separate cast pass before the paged scatter. When the pool layout permits,
the cast can be folded into the scatter itself.


## What this does

Adds `_can_fuse_fp8_main_kv_store` / `_store_main_kv_fused_fp8` to the sparse
pool: when the destination is an fp8 pool with a cast available and the layout is
token-major contiguous, the bf16→fp8 cast happens inside the paged scatter rather
than as a preceding pass.

## Test plan

`test/registered/unit/mem_cache/test_minimax_sparse_fp8_kv_store.py` — 18 tests
covering the predicate's accept/reject matrix on CPU plus bitwise-equivalence of
the fused and unfused stores on GPU. The GPU equivalence tests compare the fused
result against the `set_kv_buffer` fallback for identical inputs.

Full set run on MI355X (gfx950), ROCm 7.2.1, torch 2.10.0: **18 passed, 0
skipped** -- the 11 CPU gating tests and all 7 GPU equivalence tests.

### Isolated vs cumulative e2e performance

The sweep above is deliberately narrow -- three VL configs at TP2 -- and it isolates
this one change. It is one of a series of VL-specific optimizations (#41662, #41664, #41665, #41672),
which cumulatively give over 20% uplift over the baseline across a wider 8-row
config sweep at TP2, TP4 and TP8.

The 8-row sweep tests how the proportion of VL input tokens affects inference
performance. It is parameterized by image size, input length and concurrency:

on the same node, tensor-parallel width and device set:

## Compatibility

Scoped to the MiniMax sparse pool. Where the predicate rejects, the code path is
byte-identical to before.
