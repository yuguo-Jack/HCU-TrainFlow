# Implemented MXFP4 quant lightning indexer for DSA

[Upstream PR](https://github.com/sgl-project/sglang/pull/42599) · state: open · merged: False

## Original PR description

> **Stacked on #40591** (MXFP8 quant lightning indexer). Until that merges, this diff also contains its commits. The commits that belong to this PR are `50ba99c` (MXFP4 + `--indexer-kv-cache-dtype`) and `4ffb68d` (test fix after upmerge).

## Motivation

On Ascend, the DSA lightning indexer can run on a quantized key cache. #40591 moves it to the CANN `quant_lightning_indexer` v2 kernel with block-32 MXFP8. This PR adds block-32 **MXFP4** (kernel `quant_mode` 5). At `index_head_dim = 128` that cuts the indexer key cache from 132 to 68 bytes per token per indexer layer, and it makes the indexer faster at long context (see below).

Today the indexer cache dtype is derived from `--kv-cache-dtype`. The main KV cache can't use FP4, so the two have to be configurable separately. This PR adds `--indexer-kv-cache-dtype` for that.

## New flag: `--indexer-kv-cache-dtype`

| Value | `quant_mode` | Key payload | Scale |
|---|---|---|---|
| unset (default) | 3 if `--kv-cache-dtype=fp8_e4m3`, otherwise the quantized indexer stays off (bf16 `npu_lightning_indexer`) | — | — |
| `fp8_e4m3` | 1 | FP8 E4M3 | one FP32 per token |
| `mxfp8` | 3 | FP8 E4M3 | one E8M0 byte per 32 elements |
| `fp4_e2m1` | 5 | FP4 E2M1, packed 2 per byte | one E8M0 byte per 32 elements |

Each of these constraints fails with an explicit error:
- Ascend NPU only, and the model must have a DSA indexer (startup).
- An explicit value requires `--kv-cache-dtype=fp8_e4m3`, because the quantized indexer storage lives in the FP8 DSA cache (startup).
- `fp4_e2m1` needs `torch.float4_e2m1fn_x2` (PyTorch ≥ 2.8) (startup).
- `fp4_e2m1` cannot be combined with hierarchical cache yet: the host mirror can't round-trip packed FP4 pages. Use `mxfp8` or leave the flag unset (startup).
- The kernel's `PA_BBND` layout needs a page size in [16, 1024] that is a multiple of 16 (checked on the first indexer forward).

## Changes

**Indexer** (`dsa_npu_indexer.py`)
- `_quantize_npu_indexer_activation` takes a `quant_mode`: mode 1 uses `npu_dynamic_quant`, modes 3 and 5 use `npu_dynamic_mx_quant`. MX scales are normalized to the kernel's `(d/64, 2)` E8M0 layout.
- The indexer calls `quant_lightning_indexer_metadata` + `quant_lightning_indexer` (`TND` query, `PA_BBND` key) in all three modes.
- On NPU the module now imports `cann_ops_transformer`, which registers `torch.ops.cann_ops_transformer`. That package is now a requirement.

**Metadata once per batch** (`ascend_backend.py`)
- The metadata op only depends on the batch shape, so `init_forward_metadata` computes it once and stores it in `ForwardMetadata`, and every indexer layer reuses it. The indexer falls back to computing it inline when the backend didn't plan it (for example, the spec draft model). CP prefill takes the legacy indexer path and is skipped.

**Cache layout** (`memory_pool_npu.py`, `pool_host/mla.py`)
- MXFP4 keys are stored as `uint8 [..., d/2]`, and `get_index_k_buffer` returns a `float4_e2m1fn_x2` view.
- MX scales are stored as `uint8 (k_n, d/64, 2)` per token, and `get_index_k_scale_buffer` returns a `float8_e8m0fnu` view. Token-wise mode keeps one FP32 per token.
- The host mirror takes the scale shape and dtype from the device pool. Every mode uses 4 scale bytes per token per layer, so hierarchical-cache sizing doesn't change.

**Plumbing**
- The flag is defined in `arg_groups/fields/model.py`. Its validator is in `kv_cache_hook.py` and is registered in `pipeline.py` / `resolution_hooks.py`.
- `kv_cache_dtype.resolve_indexer_quant_mode` maps the flag to a `quant_mode`, and `kv_cache_configurator.py` passes that to the NPU MLA pool.

## Effect on existing configs

- Without `--kv-cache-dtype=fp8_e4m3`: unchanged. The bf16 indexer still runs.
- With an FP8 KV cache and no new flag: MXFP8 on the v2 kernel, which is the behaviour from #40591. Compared with `main`, that replaces token-wise FP8 on `torch_npu.npu_quant_lightning_indexer`. `--indexer-kv-cache-dtype=fp8_e4m3` brings back token-wise scaling, now on the v2 kernel.

## Accuracy Tests

Model: GLM-5.2-w4a8c8. Hardware: Ascend A5. Parallel config: TP8. Benchmark: `benchmark/gsm8k/bench_sglang.py`, all 1319 questions.

| Config | Accuracy | Invalid | Latency (s) | Output throughput (tok/s) |
|---|---|---|---|---|
| Baseline (unquantized KV cache and indexer) | 0.944 | 0.000 | 320.5 | 416.6 |
| KV MXFP8, indexer MXFP4 | 0.945 | 0.001 | 330.8 | 401.0 |

Accuracy is unchanged. GSM8K prompts are short, so the indexer saves nothing here, and throughput is within 4% of the baseline.

## Unit tests

All tests are NPU-only and registered with `register_npu_ci`.
- `test_npu_quant_lightning_indexer.py` (new): page-size check; activation quantization for modes 1/3/5 (shapes, dtypes, empty input, dequant consistency); kernel smoke tests in each mode; rejection of int64 `cu_seqlens_q`.
- `test_npu_dsa_index_k_scale_pool.py` (new): MX scale-pool layout, E8M0 view, set/get round-trip across pages, layer-slot isolation, host mirror matching the device pool.
- `test_npu_indexer_kv_cache_dtype.py` (new): flag resolution (inherited, explicit, error cases); pool layout and round-trips for modes 1 and 5; hierarchical cache rejecting MXFP4.
- `test_npu_ascend_backend.py`: `TestQuantIndexerMetadataPlanning` covers int32 inputs, decode, the CP-prefill skip and the disabled skip.
