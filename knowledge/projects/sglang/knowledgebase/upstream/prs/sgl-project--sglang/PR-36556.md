## Original PR description

## Title

fix(qsa): support SM120/SM121 sparse decode paths

## Description

This is a stacked fix for #36531 on top of #36497. The PR base should be `qwen4-main-squashed`.

## Summary

- enable the existing FlashInfer TRTLLM sparse-decode path on SM120 and SM121
- use SGLang's architecture-owned FA4 dispatcher as the fallback for devices matched by the existing major-12 capability gate
- preserve the existing FA2-first fallback order on non-SM12x GPUs
- add focused resolver tests for the SM12x fast path, SM12x fallback, and non-SM12x behavior

## Why

On SM120, `_resolve_trtllm_sparse_decode()` rejected the architecture even though FlashInfer 0.6.17 supports this QSA decode shape. The code then fell through to the pip `flash_attn.cute.interface` implementation, which fails during warmup for the packed QSA varlen shape.

On SM120 and SM121, the normal path now uses TRTLLM decode. If FlashInfer is unavailable, devices matched by the existing major-12 capability gate use SGLang's architecture-owned FA4 dispatcher instead of the incompatible pip implementation.

The TRTLLM path has been validated on both SM120 and SM121. The SGLang FA4 fallback was directly validated on SM120.

Fixes #36531.
Fixes #36558.

### Contrast with the narrow workaround, same box

This matters because on this hardware the two candidate paths are cleanly distinguishable. As
reported in #36531, routing **only** the FA4 fallback (leaving `_resolve_trtllm_sparse_decode()`

```

```

i.e. correct within exactly one KV page, consistent with that fallback's own docstring

same box is exact at 229.5K. So on SM120 the trtllm-gen decode path is not merely the faster
one — it is the one that is correct past the first page.

### Two flags that are load-bearing alongside this patch

* `--attention-backend triton` has to be passed explicitly. There is a **second**

### The A/B

- **A** = trtllm sparse decode forced on, i.e. functionally hunk 1. (We reached it by
  un-gating `is_sm100_supported()` in `_resolve_trtllm_sparse_decode`, before this PR existed.)
- **B** = trtllm left gated off, varlen fallback repaired instead. Same *shape* as hunk 2,
  though not the same kernel - we used the Triton varlen fallback from
  [MiaAI-Lab/Qwen3.8-Flash-Next-Dual-DGX-Sparks](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Dual-DGX-Sparks),
  not `sglang.kernels.ops.attention.flash_attention_v4`. So this is evidence about hunk 2's
  *direction*, not a validation of its exact implementation.

Single-shot cold prefill, greedy, thinking off, no tools, one request at a time. Verdict is a
run of >=50 consecutive token-0 (`!`) in the output:

| prompt tokens | A (trtllm forced) | B (fallback repaired) |
|---|---|---|
| 120k | **1/4 corrupt** | 6/6 clean |
| 160k | **1/4 corrupt** | - |
| 190k | **2/4 corrupt** | 6/6 clean |
| 210k | **4/4 corrupt** | 6/6 clean |
| 240k | - | 6/6 clean * |

B also stayed clean at 210k with thinking on (4/4) and at 225k with a concurrent second
stream (4/4).

\* 240k needed `--chunked-prefill-size 1024` and `--mem-fraction-static 0.82`. At 0.90/4096
B corrupted 2/6 at 240k - but that is a *resource* failure, not this kernel: the QSA indexer
allocates an `fp32 [chunk x history]` workspace per sparse layer per chunk, ~8-10 GB at chunk
4096 and 240k history, against 8.9 GB free. Raising headroom fixes it. Flagging it so the
240k row is not read as evidence about the decode path.

### Hunk 1 is not buying performance either

The docstring justifies preferring trtllm as "~35% faster for the gather+attention pair". On
SM121 we measure the opposite end to end. Single-stream decode, `running-req=1`, >=100k
context, prefill batches excluded:

| | accept len | accept rate | decode |
|---|---|---|---|
| A (only its *non-corrupt* runs) | 3.18 | 0.73 | 43.5 tok/s |
| B | 3.49 | 0.83 | **56.6 tok/s** |

B is ~30% faster because a correct kernel produces drafts the target accepts. Counting A's
corrupt runs its mean falls to ~35 tok/s, and its *useful* throughput at 210k is zero - every
request there burned 512 junk tokens.

### Why the current tests cannot catch this

The two added tests monkeypatch `is_sm120_supported` and assert the resolver returns a given
function object. They verify dispatch, not numerics, so they pass whether or not the kernel
computes the right thing.

The existing kernel test validates at `kv=[2051,2,256]`. The QSA indexer has
`indexer_budget 2048`, so at that length the sparse selection cannot prune and the failing
path is never entered. Our own probe suite had the same blind spot: its sweep ceiling was
128k, just under where this becomes visible.

Two properties make this easy to miss, and we did miss it - we had this config in front
of developers before a real session surfaced it:

1. **It is stochastic.** At 190k it fires about half the time. Any n=1 rung reads as a pass.
   Every cell above is n>=4.
2. **A liveness canary cannot see it.** Ours (three short greedy prompts) passed 3/3 while the
   same server was corrupting 100% of 210k requests.

### Suggestion

Hunk 2 is the valuable half - it is what makes the engine boot on family-12, and on our
hardware the repaired fallback alone is both correct and faster. Hunk 1 is what we would ask
you to reconsider: as written it routes every family-12 device onto a decode path that is
silently wrong on SM121 at ordinary agent context lengths.

Options, in order of preference from here: keep the trtllm gate at SM100 only; or gate it on
a runtime correctness check; or keep it behind an explicit opt-in flag rather than
architecture detection.

Related, and consistent with this: #36716 reports the same trtllm-gen corruption on SM121 from
a completely different configuration (single Spark, TP=1, fp8 KV), and #36558 is the original
SM121 report. Note also that the SM120 validations in this thread are a different SKU from
SM121 and mostly TP=1 - we have not tested SM120 and are making no claim about it. If a
maintainer wants a specific shape re-run on GB10 with real weights and TP=2, we can do that.
