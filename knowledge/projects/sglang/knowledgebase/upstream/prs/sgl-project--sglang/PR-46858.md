# [Feat] lfm3: Add text, vision, audio and Omni support

[Upstream PR](https://github.com/sgl-project/sglang/pull/46858) · state: open · merged: False

## Original PR description

## Summary

Add native text generation for the LFM3 family in SGLang.

| Model | Inputs | Output |
| --- | --- | --- |
| LFM3 | Text | Text |
| LFM3-VL | Text, images, video | Text |
| LFM3-Audio | Text, audio | Text |
| LFM3-Omni | Text, images, audio, video, including video soundtracks | Text |

Uses stock Transformers with `--trust-remote-code` to load the checkpoint-provided configs and processors.

## Implementation

- Shared LFM3 backbone with gated short convolutions, full/sliding-window attention, and SGLang's hybrid cache integration. Includes CuTe DSL convolution kernels and a PyTorch fallback.
- Vision and audio encoders, projectors, and checkpoint loading. Omni reuses these components and the text backbone.
- Multimodal preprocessing uses the checkpoint's Transformers processors and chat template. Omni supports mixed inputs and video/audio interleaving.
- FlashInfer defaults to paged prefill for correct sliding-window attention.

## Usage

Choose a checkpoint for the input modalities you need:

| Model | Checkpoint |
| --- | --- |
| Text | [LiquidAI/LFM3-1.7B](https://huggingface.co/LiquidAI/LFM3-1.7B) |
| Vision | [LiquidAI/LFM3-VL-2B](https://huggingface.co/LiquidAI/LFM3-VL-2B) |
| Audio | [LiquidAI/LFM3-Audio-2B](https://huggingface.co/LiquidAI/LFM3-Audio-2B) |
| Omni | [LiquidAI/LFM3-Omni-2B](https://huggingface.co/LiquidAI/LFM3-Omni-2B) |

For example, launch Omni:

```bash
sglang serve \
  --model-path LiquidAI/LFM3-Omni-2B \
  --trust-remote-code \
  --reasoning-parser auto --tool-call-parser auto \
  --served-model-name lfm3 \
  --port 30000
```

Send requests through `/v1/chat/completions`. This client works with each model; select supported content below. Replace example media URLs with files reachable by the server.

```python
import base64
from pathlib import Path
from openai import OpenAI

client = OpenAI(base_url="http://localhost:30000/v1", api_key="EMPTY")

def ask(content, **kwargs):
    response = client.chat.completions.create(
        model="lfm3",
        messages=[{"role": "user", "content": content}],
        temperature=0,
        max_tokens=256,
        **kwargs,
    )
    print(response.choices[0].message.content)

# Text
ask("What is the capital of Poland?")

# Image
image = {"type": "image_url", "image_url": {"url": "https://your-host/image.jpg"}}
ask([image, {"type": "text", "text": "Describe this image."}])

# Video
video = {"type": "video_url", "video_url": {"url": "https://your-host/video.mp4"}}
ask([video, {"type": "text", "text": "Describe this video."}])

# Audio
encoded = base64.b64encode(Path("question.wav").read_bytes()).decode("ascii")
audio = {"type": "input_audio", "input_audio": {"data": encoded, "format": "wav"}}
ask([audio, {"type": "text", "text": "Answer the spoken question in text."}])

# Omni: image + spoken question
ask([image, audio])

# Omni: video with its soundtrack
ask(
    [video, {"type": "text", "text": "Summarize what happens and what is said."}],
    extra_body={"use_audio_in_video": True},
)
```

For transcription, launch LFM3-Audio and call the existing endpoint:

```bash
curl http://localhost:30000/v1/audio/transcriptions \
  -F model=lfm3 -F file=@question.wav
```

## Validation

| Text | 4/4 | 4/4 |

### sm120 (consumer Blackwell) check: LFM3-1.7B-NVFP4 text on an RTX 5060

Setup: RTX 5060 8 GB (sm120), CUDA 13.3, torch 2.14.1+cu130, flashinfer 0.7.2, checkpoint `LiquidAI/LFM3-1.7B-NVFP4`, text only. Tested b05dd4a01f, then the conv kernel/tests from b1637c242a.

**1. Conv prefill race: reproduced on sm120, and b1637c242a fixes it**

Harness: fixed random inputs, relaunch `gated_causal_conv1d_prefill` (chunk=256, `has_initial_state`=1) 5000 times per case, compare bit-exact against a torch reference.

| batch (requests x tokens) | b05dd4a01f wrong launches | b1637c242a wrong launches |
|---|---:|---:|
| 7 x 257 | 0 / 5000 | 0 / 5000 |
| 31 x 257 | 4 / 5000 | 0 / 5000 |
| 64 x 257 | 5 / 5000 | 0 / 5000 |
| 128 x 257 | 10 / 5000 | 0 / 5000 |
| 16 x 300 | 0 / 5000 | 0 / 5000 |

In failing launches the final state still matched the reference and only early outputs were wrong (max abs error 6 to 11 in a small-chunk variant of the same harness), which matches the chunk-0 read / last-chunk write path. A 2048-token prefill chunk (the default here) fits at most 7 requests of 257+ tokens, and 7 x 257 never failed, so small GPUs rarely hit it; batches sized for 8k+ prefill chunks do.

We arrived at the same snapshot fix independently; b1637c242a's version is functionally identical. The updated kernel suite passes on sm120 (31/31).

Suggestion: `test_cute_prefill_across_chunk_boundary_with_initial_state` is one launch with two requests, so it checks the multi-chunk math but not the race: against the pre-fix kernel it passed 300/300 runs. A slow-marked case with many >256-token requests (e.g. 128 x 257, a few thousand launches, bit-exact) would guard against regressions.

**2. Idle-CTA grid cost (open item from round 2), measured on sm120**

Same b1637c242a kernel, dim 2048, K 7, bf16. The current grid (`n_chunks` from total T, times B) is compared with a grid sized by the longest request (`chunk >= T`, identical per-CTA work while every request is at most 256 tokens). Times are GPU-only, from CUDA-graph replay, per call:

| batch | CTAs (current / ideal) | current | ideal | extra per forward (13 conv layers) |
|---|---:|---:|---:|---:|
| 8 x 256 | 1,024 / 128 | 127.0 us | 125.9 us | 0.02 ms |
| 64 x 32 | 8,192 / 1,024 | 103.7 us | 100.6 us | 0.04 ms |
| 128 x 16 | 16,384 / 2,048 | 116.6 us | 112.9 us | 0.05 ms |
| 256 x 8 | 32,768 / 4,096 | 147.0 us | 140.9 us | 0.08 ms |
| 128 x 128 | 131,072 / 2,048 | 759.1 us | 723.2 us | 0.47 ms |

So on sm120 the idle CTAs cost 1 to 5% of the conv kernel, under 0.1% of a prefill forward at these sizes, since early-exit CTAs are cheap. It is still worth bounding `n_chunks` by the longest extend length (already on the host via `extend_seq_lens_cpu`, so no device sync), but it does not look urgent.

**3. NVFP4 on sm120 works; parity with the HF reference**

- Loads as `modelopt_fp4`. The default `--fp4-gemm-backend` on sm120 is `flashinfer_cutlass` (W4A4), which works; `flashinfer_cudnn` and `marlin` (W4A16) also work.
- Model-code parity: with the NVFP4 weights unpacked to BF16, SGLang matches the checkpoint's `modeling_lfm3.py` in Transformers. Top-1 agreement is 97 to 100% on prompts up to 3000 tokens, and greedy outputs are identical for 32 tokens on all prompts, including 5.9k-token prompts (three prefill chunks across the 256-token window). Radix/mamba prefix-cache hits reproduce cold logprobs exactly.
- W4A4 serving, `sglang.benchmark.serving` with random token ids:

| scenario | flashinfer_cutlass | flashinfer_cudnn |
|---|---:|---:|
| 1 user, 512 in / 256 out: median TPOT | 5.25 ms (184 tok/s) | 5.64 ms (172 tok/s) |
| 8 users, 1024 / 256: output tok/s | 1082 | 1056 |
| 32 users, 1024 / 256: output tok/s | 2776 | 2741 |
| 4 users, 4096 in / 8 out: input tok/s | 21.3k | 21.4k |

**4. Launch command on the NVFP4 model card**

The card uses `--reasoning-parser qwen3-thinking`. With it, any request with `chat_template_kwargs: {"enable_thinking": false}` returns an empty `content`, and the whole answer lands in `reasoning_content`. For example, "What is 12 + 30?" gives `content=''` and `reasoning_content='12 + 30 = 42\n\n42'`. `--reasoning-parser auto`, as used in this PR's description, handles both modes; it may be worth aligning the card.

**5. Minor, non-blocking**

LFM3 isn't registered as hybrid-SWA (`hybrid_swa=False`), so the 5 sliding-window layers keep full-context KV. That is correct, but only 6 of the 11 attention layers need full context, so a SWA pool would save about 45% of KV memory, which matters on 8 GB cards. Possibly a follow-up.

## Test report: LFM3-1.7B on consumer GPU (RTX 4060 Laptop 8 GB, SM89/Ada, WSL2) — works end-to-end

Tested head `b1637c242a0ed7cf6575bab44a21a1be30a5b19a`. The native `Lfm3ForCausalLM` loads, captures CUDA graphs and generates coherent output; a separate pure-HF BF16 control also generated coherent output. **Go ahead from my side** — details below, including one suggestion for a cryptic failure mode we hit with a hand-quantized checkpoint.

### Environment

- GPU: RTX 4060 Laptop 8 GB (SM89, Ada), WSL2
- torch 2.14.1+cu130, torchvision 0.29.0+cu130 (matching the PR's `torch==2.14.1` pin)
- transformers 5.21.0, `flashinfer_python[cu13]` 0.7.2, `sglang-kernel` 0.4.10 (per `python/pyproject.toml`)
- Install: `uv pip install --no-deps "sglang @ git+https://github.com/tugot17/sglang@lfm3#subdirectory=python"` with `SGLANG_BUILD_RUST_EXTS=none` (no Rust toolchain on this box; the text-only path does not appear to need the Rust extensions) — built and installed cleanly.

### Checkpoint and serving setup

- `LiquidAI/LFM3-1.7B` manually quantized selected linear weights to per-tensor FP8 e4m3 with dynamic activation scaling (`weight_block_size: null`, neuralmagic-style `quant_method: "fp8"`). Kept in bf16: embeddings, `lm_head`, all norms, and the depthwise conv kernels.
- `--quantization fp8 --kv-cache-dtype fp8_e4m3`, 32k context, TP=1, CUDA graphs on.

### Results

- **Loads and serves correctly.** A short greedy smoke test produced coherent text. A separate BF16 Hugging Face control also produced coherent text; this was not a token-by-token comparison or comprehensive correctness validation.
- **CUDA graph capture succeeds** on the native implementation. One graph-enabled request generated 200 tokens in 2.34 s end-to-end (~85 output tokens/s including prefill and HTTP overhead). An earlier graph-disabled 150-token request took about 9.1 s end-to-end; these were not matched benchmark runs and do not establish a speedup.
- The server was configured for 32k context and FP8 KV cache; only short prompts were exercised, not a 32k-context test.

### Issue found: unquantized `self_attn.gate_proj` → cryptic load error

With a checkpoint whose `quantization_config` does not ship `ignored_layers`, `self_attn.gate_proj` (the 16×2048 attention out-gate) is instantiated as an FP8 linear while the checkpoint ships it in bf16, and loading fails with:

```
ValueError: Downcasting not allowed: target.dtype=torch.float8_e4m3fn,
loaded_weight.dtype=torch.bfloat16
```

We traced this via a `load_weights` wrapper to `model.layers.N.self_attn.gate_proj.weight`. Checkpoint-side fix that works:

```json
"quantization_config": {
  "quant_method": "fp8",
  "activation_scheme": "dynamic",
  "fmt": "e4m3",
  "weight_block_size": null,
  "ignored_layers": ["lm_head", "self_attn.gate_proj"]
}
```

Two notes that cost us some time:

1. The ignored-layer matcher is dotted-boundary substring matching (`_module_path_match`), **not** glob — `"*.self_attn.gate_proj"` silently does not match; plain `"self_attn.gate_proj"` does.
2. This is consistent with the official `LiquidAI/LFM3-1.7B-NVFP4` checkpoint, which excludes `self_attn*` per attention layer from quantization — i.e. Liquid themselves ship the attention gates (and attention projections) unquantized.

Suggestion: consider auto-ignoring `self_attn.gate_proj` for LFM3 (or at least raising a clearer error that names the offending module and hints at `ignored_layers`), so hand-quantized checkpoints don't trip over this.

### Context: fallback path is not viable (reinforces this PR)

Before testing the PR we tried the `TransformersForCausalLM` fallback on an older build (0.5.6.post3.dev10571): LFM3 loads and runs there, but generation is corrupted garbage in our attempts with official NVFP4 and manual FP8. The root cause was not isolated; hybrid cache handling is a hypothesis, not a confirmed diagnosis. CUDA graph capture also fails in the fallback. A separate BF16 pure-HF control produced coherent text, but did not test those quantized checkpoints outside SGLang. For anyone on older builds: don't bother with the fallback for LFM3; this PR is what makes it work.

### Verdict

Native implementation verified on SM89 with FP8 weights + FP8 KV cache + CUDA graphs, coherent short-prompt output, preliminary single-stream performance for a 1.7B on an 8 GB card. Thanks for the thorough PR — text-only tested here; VL/Audio/Omni paths still untested on our side.

### sm120 NVFP4 check of the latest commits (head 8f6196da)

**Setup:** RTX 5060 8 GB (sm120), WSL2, torch 2.14.1+cu130, flashinfer 0.7.2, `LiquidAI/LFM3-1.7B-NVFP4` (W4A4, default `flashinfer_cutlass`), cookbook launch flags. A/B is 8f6196da vs its parent 917ed8fe.

**TL;DR:** 8f6196da is correct and a small win. Nothing in the new commits regresses NVFP4 prefill, decode, serving or GSM8K on sm120. Two small changes suggested below.

#### 8f6196da (conv launch bounded by the longest request)

- Bit-exact: across 300 random varlen batches (lengths at 1/255/256/257/512/1024, up to 128 requests, with initial state), outputs and final conv state are identical with `max_seq_len=max(lens)` and with the old total-token bound. - Conv kernel time per prefill inside the model (torch profiler, 13 launches per forward):

| batch (requests x tokens) | conv before | conv after | whole forward (GPU) |
|---|---:|---:|---:|
| 1x2048 (control) | 1600 us | 1600 us | 71 ms |
| 64x32 | 1310 us | 1240 us | 68 ms |
| 128x16 | 1427 us | 1362 us | 69 ms |
| 16x1024 | 9213 us | 9106 us | 610 ms |
| 128x128 | 9845 us | 9224 us | 601 ms |

  That is at most ~0.1% of forward GPU time, so end-to-end prefill moves within noise.
- FYI: LFM3 never runs prefill under a CUDA graph. Both `sglang.benchmark.one_batch` and the server log `Disable prefill CUDA graph because some layers do not apply Standard GQA` (only `nemotron_h` sets `supports_hybrid_prefill_graph`), so every LFM3 prefill is eager and gets this bound.

#### Suggested changes

1. **Test the bound.** `Lfm3ShortConv.forward` now always passes `max_seq_len` (from `extend_seq_lens_cpu`), but `test_cutedsl_gated_conv.py` never does, so the kernel tests only cover the old bound. Suggest parametrizing `test_cute_prefill_across_chunk_boundary_with_initial_state` over `max_seq_len in (None, max(seqlens))` with a batch where the bound shrinks the grid, e.g. `seqlens = [600, 300, 3]` (4 chunks -> 3). With the current `[600, 3]` both bounds launch 3 chunks.
2. **Cookbook precision line is stale.** `docs/cookbook/autoregressive/LiquidAI/LFM3.mdx` says "BF16 (or FP16) checkpoints only — there is no packed-quantization (FP8/FP4) variant", but `LiquidAI/LFM3-1.7B-NVFP4` is public. On sm120 it serves with the generated command unchanged (`--trust-remote-code --reasoning-parser auto --tool-call-parser auto`; `modelopt_fp4` is auto-detected and the default FP4 GEMM is `flashinfer_cutlass`). Please update that line, and consider adding the NVFP4 variant to `lfm3.jsx` for the Blackwell targets you have verified. If that includes consumer cards, two things bit us on an 8 GB / 16 GB-RAM box:
   - With default flags the server captures decode CUDA graphs only for bs <= 8 (`bs=[1, 2, 4, 8]`), so 32 concurrent users drop to ~650 output tok/s; `--cuda-graph-max-bs-decode 64` brings it to ~2050 tok/s.
   - The first load JIT-builds FlashInfer's `fp4_gemm_cutlass_sm120` (17 CUTLASS objects); each `cicc` peaks ~4.2 GB, so the default parallel build is OOM-killed on a 16 GB host (ninja exit 137). Installing the prebuilt `flashinfer-jit-cache` (`flashinfer_jit_cache_sm120f`) or lowering `MAX_JOBS` avoids it.

File: `python/sglang/kernels/ops/mamba/cutedsl_gated_conv.py` · line 263

This launch has an unordered read/write race on the conv-state slot. The chunk-0 CTA reads the initial state from `mss` for the first K-1 positions (the `has_init` branch at 236-239), and the last chunk's CTA writes the final state to the same `mss` here. PDL orders kernels, not CTAs within one launch, so nothing stops the tail CTA from storing first when its chunk is short — a 257-512-token request schedules both CTAs at once and the tail computes one token. First K-1 outputs then come from the freshly written state instead of the initial state. Read the initial state from a snapshot taken before the launch (separate input tensor), or write the final state to a second buffer and commit it in a follow-up op.
