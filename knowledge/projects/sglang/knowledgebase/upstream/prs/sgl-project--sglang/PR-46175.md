# [CI] rust: Publish sglang-api-types on crates.io

[Upstream PR](https://github.com/sgl-project/sglang/pull/46175) · state: open · merged: False

## Original PR description

## Motivation

Clients of SGLang's Rust server currently vendor the `sglang.api.v1` `.proto` files and compile their own bindings. This PR makes `rust/sglang-api-types` publishable on crates.io, so they can depend on a versioned crate instead.

The published crate contains `sglang.api.v1` only. The deprecated `sglang.runtime.v1` bindings move to an internal, unpublished crate.

## Modifications

**1. `Move the runtime.v1 bindings out of sglang-api-types`**
- New internal crate `rust/sglang-runtime-v1-types` holding the generated `sglang.runtime.v1` bindings so they do not get published.
- `cargo gen-api` writes the runtime.v1 target there.
- `sglang-grpc` and `sgl-router` depend on the new crate.

**2. `Publishing to crates.io`**
- `sglang-api-types`: its own version (`0.1.0`), independent of SGLang releases.
-  crates.io metadata (repository, homepage, readme, keywords, categories, `include`)
- New `.github/workflows/release-crate-api-types.yml`:
  - On PRs touching the crate, regenerate the bindings with `cargo gen-api` and fail on any difference.
  - On an `api-types-v<version>` tag in `sgl-project/sglang`, the same checks, plus the tag must match the crate version and `cargo-semver-checks` must pass against the latest release on crates.io.

Releases are manual:
1. Bump `version` in `rust/sglang-api-types/Cargo.toml`.
2. Merge.
3. Push an `api-types-v<version>` tag on that commit.

One-time setup is needed to publish the first version by hand.
