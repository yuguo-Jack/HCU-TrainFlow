# [Perf] hicache: Wait once per write_back eviction walk, not once per victim

[Upstream PR](https://github.com/sgl-project/sglang/pull/46930) · state: closed · merged: True

## Original PR description

## Motivation

With `--hicache-write-policy write_back`, the device-eviction walk in `UnifiedRadixCache` copies each victim to host and blocks on that copy before taking the next victim. Each wait sits behind the write fence, so once the host pool is full the scheduler stalls once per victim while the GPU idles.

This PR queues the walk's copies, submits them together, waits once, then demotes the victims in walk order. Eviction decisions are unchanged: same victims, same order, in both tree cores.

## Speed Tests and Profiling

One GB300, `--enable-hierarchical-cache --hicache-write-policy write_back --hicache-size 100`, `benchmark/hicache/bench_multiturn.py`. The device pool holds ~1/4 of the history and the host pool all of it, so admissions evict but nothing is dropped. Mean (min-max), arms alternated, fresh server per run.

| | main | this PR | |
|---|---|---|---|
| `openai/gpt-oss-20b`, eviction-bound: req/s (5 runs) | 113.0 (109.0-115.6) | 120.5 (117.8-122.4) | +6.6% |
| TTFT p50 / p99 (ms) | 366 / 813 | 308 / 559 | -16% / -31% |
| blocking D->H waits per eviction pass | 3.78 | 0.91 | -76% |
| cache hit rate | 0.874 | 0.874 | same |
| `Qwen/Qwen3-8B` (full attention), eviction-bound: req/s (3 runs) | 83.7 | 86.2 | +3.1%, within noise |
| `openai/gpt-oss-20b`, no eviction: req/s (3 runs) | 150.6 | 149.5 | neutral |

The gain grows with victims per eviction pass (3.8 for gpt-oss-20b, 2.5 for Qwen3-8B). The first copy of each pass still waits for the in-flight forward; batching cannot remove that.
