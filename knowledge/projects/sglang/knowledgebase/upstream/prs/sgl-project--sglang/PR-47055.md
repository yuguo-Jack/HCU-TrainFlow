# [Feat] diffusion/openai: Cancel video jobs on DELETE

[Upstream PR](https://github.com/sgl-project/sglang/pull/47055) · state: closed · merged: True

## Original PR description

## Motivation

`DELETE /v1/videos/{id}` removes the job record, but the job keeps its GPU until it finishes (`# TODO: support aborting a job`). A client that cancels a long video job still blocks the replica for the full run.

This revives #24547 by @qimcis, which was approved but no longer applies to main, with a smaller scope:

- a queued job does not start;
- a running job stops after its current denoising step.

Removing one cancelled request from a running dynamic batch is left for a follow-up.

## Modifications

**Cancel channel.** A replica driver runs the forward on the thread that reads its request socket, so it cannot read a cancel while a job runs. The HTTP server now publishes each cancelled request id on a ZMQ XPUB socket with `XPUB_NODROP` backpressure (`entrypoints/openai/video_cancel.py`). This is the reverse of the progress channel from #45919, with the same deployment limits (monolithic, single node). Each driver subscribes and reads the ids at each check (`managers/request_cancel.py`), and drains them in the scheduler receive loop while idle. DELETE returns a retryable 503 and retains the job if a replica has not subscribed or the transport is full.

**All ranks stop at the same step.** The driver broadcasts its decision on the replica CPU (gloo) group. In #24547 each rank checked a marker file on its own, so with sequence parallelism one rank could stop at step k while the others waited in a collective of step k+1. The broadcast runs on the CPU group, so it adds no GPU sync.

**Check points.**
- Before dynamic merging in the scheduler and before the forward in `GPUWorker`, so observed queued cancellations do not enter a mixed live batch. Explicit request groups retain their single-reply protocol.
- After each denoising step, through `PipelineStage.progress_bar`. Every denoising loop advances it once per step, so no loop needs its own edit. Stages that run on the main rank only get no step check, because the check is a collective.
- The sequential path (multi-output SANA-Video 2.0 jobs, and native grouped requests) runs the first stage once for the group. There the worker checks each request before the group starts and runs only the requests that are not cancelled, so each request keeps its own output. The executor also checks before each output, so after a cancel the outputs that remain stop at once.

**DELETE after a timeout.** DELETE publishes cancellation for unfinished jobs, including jobs that `--scheduler-rpc-timeout` marked failed: the timeout ends the HTTP wait, not the GPU work. Completed jobs can be removed without a cancellation channel. The listener retains a bounded history of cancelled IDs.

**Dynamic batches.** A merged batch is cancellable only when each member is, and it stops only when each member is cancelled. The other members continue. The scheduler checks `OutputBatch.cancelled` before `OutputBatch.error`, in the merged batch and in the native grouped batch, so a stopped batch returns cancelled outputs, not errors.

**Logs.** A cancelled request is logged once at info level (`Stopped request ...`). It is not logged as an error with a traceback on each rank. `OutputBatch.cancelled` lets the HTTP side tell a cancel from a failure. `RequestCancelledError` is in the leaf module `request_cancel_error`, so the logging and profiling utilities import it at module level.

The docs for `DELETE /v1/videos/{id}` are updated.

## Speed Tests and Profiling

Requests other than cancellable `/v1/videos` jobs, and warmup requests, do not run per-step cancellation checks. The driver still drains the control channel in the scheduler receive loop. For a video job, each denoising step adds one non-blocking ZMQ read on the driver and, on a multi-rank replica, one broadcast of one int32 on the gloo CPU group.

Microbenchmark of the per-step check on CPU (Apple M5 Pro, Python 3.14, torch 2.14, 5000 iterations after 500 warmup iterations; local processes over loopback):

| Per-step work | mean | p50 | p99 |
| --- | --- | --- | --- |
| `CancelListener.is_cancelled`, no cancel received | 15 us | 16 us | 25 us |
| gloo broadcast of one int32, 2 ranks | 51 us | 49 us | 97 us |
| gloo broadcast of one int32, 4 ranks | 80 us | 76 us | 151 us |
| gloo broadcast of one int32, 8 ranks | 149 us | 146 us | 238 us |

With 8 ranks the check adds about 0.17 ms per step: 0.02 percent of a 1 s MiniMax-H3 step, 0.3 percent of a 50 ms step. The broadcast also makes the CPU thread of each rank wait for the driver once per step, so no rank can queue more than one step of kernels ahead of the driver. A replica across nodes pays the TCP round trip instead of loopback. These initial measurements did not include a matched GPU end-to-end comparison; see the maintainer follow-up below. In the GPU test below, an 8-step MiniMax-H3 job took 9 s with the change. If a maintainer prefers, the check can run every N steps; it cannot use a time interval, because every rank must call the broadcast at the same step.

## Test

**Unit tests** (`test/unit/test_request_cancel.py`, CPU):
- publisher to listener over ipc, ids of expanded outputs (`job:0`), the size bound of the id set;
- a two-process gloo test: every rank follows the driver's decision, also when its own view differs (this test fails when the broadcast is removed);
- the step check stops a loop through `ReportingTqdm`, and only replicated stages get the check;
- the worker skips the forward of a cancelled request;
- the sequential path: a cancelled request does not start and the other requests keep their outputs, the outputs after a cancel stop at once without an error log, and a merged multi-output result stays cancelled;
- DELETE publishes the cancel, also after a scheduler RPC timeout, and a deleted job is not marked failed;
- the dynamic-batch merge rule, and a stopped merged or native grouped batch returns cancelled outputs with no error log;
- `init_request_cancel`, `cancel_endpoint`, and the lifespan start and stop of the publisher;
- each new module imports first without an import cycle.

**GPU test** (covers the per-step and queued checks, not the sequential path; MiniMax-H3 ref2va, 8 x H100, `--ulysses-degree 8 --quantization fp8`, this branch over `lmsysorg/sglang:nightly-dev-20261026`):

| Case | Result |
| --- | --- |
| DELETE a running 50-step job at 10 percent | All 8 ranks stopped after step 6. The next job started 1.1 s after the DELETE and completed. |
| DELETE a job queued behind another job | It never ran. The next job started 1.0 s after the job ahead of it ended. |
| `/health` after the cancels | 200, no NCCL errors |
| Server log after startup | 0 tracebacks, 0 error lines |

## Limits

- A model whose denoising loop does not advance a progress bar runs to the end after a DELETE.
- Stages after denoising (for example decoding) do not run for a cancelled job. A job deleted after its last denoising step still decodes and saves or uploads its output, but the API does not return it.
- DELETE returns 503 with `Retry-After: 1` when the cancellation transport is full or not all replica drivers are subscribed. Retry with the same job ID; the API record is retained.
- An accepted command is not a worker acknowledgement. Cancellation remains best effort across process failures and eviction from the latest 4096 cancelled IDs. There is no durable cancellation protocol.
- Disaggregated and multi-node serving remain unsupported for cancellation; DELETE there only removes the API record.

## Maintainer follow-up (2026-10-29)

Commit `66320508ee15eee776f6fc8909b81e884386e53c` fixes the two reproduced review issues: queued cancellation before dynamic merging, and silent cancellation loss when PUB/SUB reaches its high-water mark. It also preserves explicit-group and deferred/streaming reply semantics, and drains idle replica listeners to avoid blocking cancellation on active replicas.

Validation on Python 3.12, PyTorch 2.14.1+cu130, diffusers 0.37.0 and pyzmq 27.2.0:

- Six targeted test files: **190 passed, 3 skipped**. The skipped two-GPU output-finalization test was separately rerun on CUDA and passed; the other two skips are inapplicable synchronous-caller variants.
- Real IPC coverage includes a 3500-command burst, accepted-command delivery and rejected-command retry, replica subscription/disconnect, DELETE failure preserving the job, and idle listener draining. Dynamic batching uses the real Wan batching contract with a fake model forward.
- Native Wan2.1 T2V 1.3B on **2 x H200, Ulysses 2**, BF16/resident weights, FA, eager, 832x480, 17 frames, seed 42. Stage-profiling synchronization was disabled. The same warm process alternated cancellation checks off/on in A-B-B-A order, eight samples per arm, with progress reporting and output saving enabled in both arms. Median saved-output E2E: **0.812 s off / 0.816 s on (+0.5%)**. This isolates the check toggle, not the entire branch versus main, and is not a throughput or all-model guarantee.
- A 50-step request cancelled after progress step 20 stopped at step 21 without decode; a pre-cancelled request did not enter the pipeline. The next normal request completed, and all 17 comparable MP4s were byte-identical (SHA-256 `303bbf16219dbff03d36f81a92739fdc446fd9eded0aa85e467fb72c6854c426`).
- GPU validation exercised the real scheduler/process/collective path through a diagnostic SDK harness. DELETE-to-transport integration is covered separately by the IPC tests; this is not an additional live HTTP E2E test. The diagnostic SDK reports cancelled outputs as errors because it is not the public async cancellation API. Shutdown also emitted a CUDA IPC producer-lifetime warning, which is not claimed fixed here.
