# [Feat] hicache: Notify storage backends when the initial host-pool registration burst completes

[Upstream PR](https://github.com/sgl-project/sglang/pull/44030) · state: open · merged: False

## Original PR description

## Motivation

A storage backend learns its host pools from a burst of hooks: the anchor pool through `register_mem_pool_host`, then every pool of the host pool group through `register_mem_host_pool_v2` — but nothing told the backend when the burst was over. A backend that must finalize once the pool set is known (e.g. register the instance with a remote cache manager whose spec cannot be amended after registration) had no correct moment to act and could only defer that work to the first data-path call, paying seconds of setup on the first request and surfacing config errors (manager unreachable, instance conflict) after startup instead of failing it.

## Modifications

- `HiCacheStorage` gains a no-op `on_host_pools_registered()`: fires exactly once per attach, right after the last call of the initial burst; pools registered later (dynamic draft sidecars) arrive through v2 alone and do not re-fire it. Raising fails the attach.
- The burst ends in different places on the two controllers, so each fires the hook at its own end: the base controller right after the anchor pool, `HybridCacheController` — whose per-pool v2 loop runs after `super().attach_storage_backend()` returns — after that loop. A `_registers_host_pools_after_super_attach` flag tells the two apart; no signatures change and no code moves.
- The hook defaults to a no-op, so existing backends are unaffected.
- Documents the registration lifecycle in `hicache_design.mdx`.

## Accuracy Tests

Not applicable (no model output changes).
