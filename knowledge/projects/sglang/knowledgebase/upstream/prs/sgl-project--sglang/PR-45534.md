# [Fix] [NVIDIA] DeepSeek-v4.1: scatter the replay tail before the prefill CP gather with DSpark

[Upstream PR](https://github.com/sgl-project/sglang/pull/45534) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1-Flash on CUDA/SM90 supports prefill context parallelism
(`--enable-prefill-cp --cp-strategy interleave`) and decoder SWA bounded replay
(`--enable-decoder-swa-bounded-replay`), and each works on its own. Enabling both
together with DSpark aborts the first large prefill:

```text
RuntimeError: Interleave CP gather received an unexpected local token count:
  rank=3, got=16, expected_at_least=4096, total=32768, cp_size=8
    .../srt/layers/cp/interleave.py:288 in _gather_interleaved_tensor
    .../srt/layers/cp/utils.py:246 in cp_gather_after_forward
    .../srt/model_executor/runner/eager_runner.py:405 in _execute_extend_cp
    .../srt/speculative/dspark_components/dspark_worker_v2.py:650 in _forward_prefill
```

With replay, the late layers run over each request's 128-token SWA tail; after
interleave sharding a rank owns 16 of those rows. `DeepseekV4Model.forward` puts
the tail rows back into the rank's full layout only when `not capture_dspark`.
With DSpark (`capture_dspark=True`) the model returns the 16 tail rows (and
tail-only aux tensors), `exit_late_layer_tail` has already restored the full-batch
CP metadata, and `_execute_extend_cp` then gathers with the full layout
(`32768 / 8 = 4096` expected rows per rank).

On CUDA, `deepseek_v4_hook.py` does not reject this combination at startup: its
incompatible list covers the prefill CUDA graph and DP attention, not prefill CP,
so a `DP=1 + CP=8` configuration passes the check and crashes at the first large
prefill. With this fix the combination is supported for **eager prefill**
(`--cuda-graph-backend-prefill disabled`); the breakable prefill CUDA graph with
prefill CP is guarded separately by #44141. On HIP, `validate_deepseek_v4_cp`
still rejects replay + CP until #43465 lands.

**Note for maintainers:** #43465 already carries the same tail-scatter block for
HIP, and #44730 builds on it. This PR is intentionally CUDA-only — the author of
#43465 has no NVIDIA hardware to validate this configuration. If you prefer to
land #43465 first, that is fine: merge it (and #44730 if it lands) and we will
rebase this branch on top. The two hunks touch the same lines and collapse into
one `is_cp_active` condition; this PR introduces no second design.

## Modifications

```diff
+def _needs_cp_tail_scatter(tail, forward_batch) -> bool:
+    return _is_cuda and tail is not None and is_cp_active(forward_batch)
...
-        if tail is not None and not capture_dspark:
+        cuda_cp_tail = _needs_cp_tail_scatter(tail, forward_batch)
+        if tail is not None and (not capture_dspark or cuda_cp_tail):
             ...
+            if cuda_cp_tail and capture_dspark:
+                dspark_aux_hidden_states = [
+                    _scatter_tail_rows(..., zero=True)
+                    for aux in dspark_aux_hidden_states
+                ]
```

- Add `_needs_cp_tail_scatter()` so the CUDA/CP gate is explicit and unit-testable.
- `_scatter_tail_rows(..., zero=False)` gains a zero-filled variant. The rows
  outside the tail are never read (`_check_late_layer_tail_readers`; DSpark's
  draft reads tail rows only), but the CP gather moves the whole rank layout, so
  they are zero-filled only as a defensive measure (the all-gather buffer stays
  finite); the fill can be dropped to match #43465 if preferred.
- Scatter `hidden_states`, `pre_hc_head` and every tail-layer DSpark aux tensor
  back into the rank layout before the CP gather. Both tensors are gathered:
  `cp_gather_after_forward` gathers the `(hidden_states, pre_hc_head)` tuple, and
  `pre_hc_head` is only dropped from the logits kwargs after the gather when aux
  is not `None`.
- Scoped to `_is_cuda`: this is the CUDA branch of the hunk already present in
  #43465/#44730. If either lands first, the rebase is one line (drop `_is_cuda`
  and keep `is_cp_active`).
- No CLI or config change: replay under CP still requires the explicit flag (the
  automatic resolution keeps it off).
- Unit test covers `_scatter_tail_rows` (indexed and contiguous tails) and
  `_needs_cp_tail_scatter` (CUDA/CP/tail truth table). The forward path itself is
  covered by the H20 run.

## Speed Tests and Profiling

Cold TTFT, unique random prefix per request (2 runs each, spread ≤0.03 s):

| Config | 128K | 256K | 512K |
| --- | ---: | ---: | ---: |
| CP + DSpark, replay off | 5.405 s | 11.710 s | 28.664 s |
| CP + DSpark + replay (this patch) | **3.369 s** | **6.864 s** | **15.954 s** |
| Speedup | 1.60× | 1.71× | 1.80× |

Decode replay, 36 real sessions, 256 output tokens (3–4 of the 36 runs do not
complete in each config; throughput counts completed sessions):

| Config | c1 ITL p50 | c8 ITL p50 | c8 output throughput |
| --- | ---: | ---: | ---: |
| Non-CP production, replay on (single run) | 11.8 ms | 23.9 ms | 149.3 tok/s |
| CP + DSpark, replay off (single run) | 18.4 ms | 27.4 ms | 176.0 tok/s |
| CP + DSpark + replay (c8 median of 5; c1 from C2bv #1) | 18.4 ms | 27.9 ms | **241.4 tok/s** |

The c1 ITL increase comes from CP decode, not from this change: it is the same
18.4 ms with replay off. c8 ITL p90 is noisy on this workload (157–386 ms across
5 runs), so p50 and throughput are the stable metrics. The replay-off decode
baseline is a single run; treat the +37% as directional.
