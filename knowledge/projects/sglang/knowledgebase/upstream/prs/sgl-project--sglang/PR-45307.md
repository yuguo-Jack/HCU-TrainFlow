# [Perf] [AMD] dsa: Share KV pages across MTP verify rows in the gfx950 indexer logits kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/45307) · state: open · merged: False

## Original PR description

> [!TIP]
> **Pairs with ROCm/aiter#6697** (MoE sort folded into GEMM1). With both PRs on the latest main, GLM-5.2 on the InferenceX agentic-trace benchmark gets **+10.6% median interactivity** (290.9 -> 321.7 tok/s/user) and **-9.6% median ITL** vs main. This PR alone: +4.1%. Details under "Speed Tests and Profiling".

## Motivation

With MTP, GLM-5.2 runs the gfx950 DSA indexer logits kernel (`logits_hist`, node 3 of the fused decode indexer) once per verify step on each of its 21 "full" indexer layers. Each request contributes 6 rows (the draft positions), and all 6 rows read the same KV pages, but `logits_hist_m` loads every page once per row. At small batches with long contexts the kernel is bound by those loads.

This PR reads each shared page once per slot of 3 rows, so a request reads each page twice instead of 6 times. The kernel gets up to 2.67x faster, and median interactivity on the InferenceX agentic-trace benchmark (conc 4) rises 4.1%.

## Modifications

- **`paged_mqa_logits.cuh`** adds `logits_hist_slot`. `logits_hist_m` is unchanged; its machine code is identical to main's.
  - The new kernel takes rows in slots of 3. The blocks of a slot split its pages, and every loaded page is scored for each row of the slot, so a page shared by a request's rows is read once per slot. Rows whose page tables differ stream separately.
  - The per-logit math, masking and histogram binning are `logits_hist_m`'s, so logits and histogram are bit-identical.
  - `PagedMqaLogitsKernel::run` takes a new `share_pages` argument and launches the new kernel only when it is set and the grid has at most 18 rows.
- **Where it is used.** The kernel is faster only at long contexts, and it runs inside the decode CUDA graph, so the host decides per graph:
  - On gfx950, `DsaGraphVariants` for the MTP verify graphs captures a third variant, `sparse_shared_pages`.
  - `select()` replays that variant when the batch has at most 18 verify rows and its longest request holds at least 96k tokens.
  - `dsa_indexer` passes `share_pages` (through `gfx950_fused_indexer.py`) only under that variant. Eager calls apply the same rule from `seq_lens_cpu`.
  - Every other launch, including decode without MTP and other GPUs, is main's path.
- **No new flags.**
- **Tests:**
  - `test_logits_hist_shared_pages_matches_per_row`: shared-page vs per-row kernel bitwise on the same rows, for 13 context mixes from 1k to 600k tokens, mixed requests, a graph-width page table, and partial grids down to 1 row.
  - `test_topk_transform_on_shared_page_logits`: node 4 on the new kernel's histogram matches the standard top-k path.
  - `test_dsa_graph_variants.py` (CPU): labels and selection boundaries.
- **Benchmark:** `benchmark/kernels/deepseek/benchmark_dsa_gfx950_logits_hist.py` times both kernels per setup.

**Combined with ROCm/aiter#6697.** That PR folds the MoE sort into GEMM1 for the same GLM-5.2 decode path. With both PRs applied to the latest main (sglang 574f9cdb, aiter 45d7ef38), the same agentic-trace benchmark gives +10.6% median interactivity (290.9 -> 321.7) and -9.6% median ITL against main. That is one 1800 s run per arm. The two gains compound: 1.041 x 1.064 = 1.108.

**Startup cost.** The third verify-graph variant is captured for every bs, though only bs 1-3 use the new kernel. It adds 2.8 s to the target-verify graph capture (25.3 s -> 28.1 s for bs 1-8) and 0.02 GB of graph memory (1.10 -> 1.12 GB).

**Profile.** Capture traces (`--enable-profile-cuda-graph`, `SGLANG_GRAPH_BATCH_CAPTURE=1`) record the kernel of every launch in every captured verify graph.
- With this PR, the `sparse_shared_pages` graphs for bs 1-3 launch `logits_hist_slot` 21 times (once per full indexer layer) and `logits_hist_m` zero times, on all 8 ranks.
- Every other graph launches `logits_hist_m` 21 times: the dense and sparse graphs at every bs, and the shared-page graphs at bs 4-8, which keep the per-row kernel.
- On main, every graph launches `logits_hist_m`.
- In eager mode, a 120k-token request runs only `logits_hist_slot` on all 8 ranks.

## How to reproduce

Hardware: 8x MI355X (gfx950), ROCm 7.2.0. Image `lmsysorg/sglang-rocm:v0.5.22-rocm720-mi35x-20261018`, whose sglang e9b22a08 matches main for every file this PR touches; for the PR arm, this branch's files are copied over. Model: amd/GLM-5.2-MXFP4.

```bash
python3 test/registered/unit/layers/attention/test_dsa_graph_variants.py
python3 test/registered/amd/test_dsa_gfx950_fused_indexer.py -v          # one gfx950 GPU
python3 benchmark/kernels/deepseek/benchmark_dsa_gfx950_logits_hist.py --ctx 4096 131072 524288
# server (InferenceX CI 37326853365 flags); the SGLANG_SIMULATE_ACC_* variables are dropped for accuracy runs
SGLANG_OPT_USE_TOPK_V2=true SGLANG_SIMULATE_ACC_LEN=3.61 SGLANG_SIMULATE_ACC_METHOD=match-expected \
SGLANG_SIMULATE_ACC_TOKEN_MODE=real-draft-token python3 -m sglang.launch_server --model-path amd/GLM-5.2-MXFP4 \
  --trust-remote-code --kv-cache-dtype fp8_e4m3 --dsa-prefill-backend triton --dsa-decode-backend triton \
  --tool-call-parser glm47 --reasoning-parser glm45 --chunked-prefill-size 32768 --mem-fraction-static 0.85 \
  --speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6 \
  --tensor-parallel-size 8 --max-running-requests 8 --cuda-graph-max-bs-decode 8
python3 -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 400000 \
  --random-output-len 1500 --random-range-ratio 1.0 --max-concurrency 1 --num-prompts 5
sgl-eval run gsm8k --base-url http://127.0.0.1:30000/v1 --num-threads 8 --chat-template-kwarg enable_thinking=false
```

## Known gaps

- The 96k cut-over and the blocks-per-row choices were measured on MI355X for 6-draft-token verify grids. With another draft count the rows-to-batch mapping changes, but the rule is expressed in rows, so it still applies; it was not separately tuned.
- Batches of 1-3 requests whose longest context is under 96k keep main's kernel. The new kernel is slower there, mainly because its larger LDS footprint gives fewer blocks per row.
