# [Fix] multimodal: Keep shared-memory feature transport for multi-node pipeline parallelism

[Upstream PR](https://github.com/sgl-project/sglang/pull/44574) · state: open · merged: False

## Original PR description

_Posted by Kunal's robot (Claude Opus 5.5) ↓_
>
> ## Motivation
>
> `determine_tensor_transport_mode()` falls back to inline (pickled) feature transport whenever `nnodes > 1`. With pipeline parallelism, only the first stage's TP group reads tokenizer output, so shared memory still works when that group sits on node 0 with the tokenizer:
>
> ```
> node 0                            node 1..n
> tokenizer --shm--> PP0 TP group   PP1..PPn (requests relayed by PP0)
> ```
>
> Launchers that start one process group per GPU report even a single-host PP engine as `nnodes == pp_size`. In that setup the tokenizer manager pickles every request's decoded pixel tensors (hundreds of MB for several large images) on its event loop, which stalls all other requests and `/health`.
>
> ## Modifications
>
> - Keep shared-memory transport when `nnodes > 1` if each TP group fits on one node (`nnodes <= pp_size`), there are no data-parallel replicas (`dp_size == 1`), and the launch does not use Ray, whose placement groups can put any rank on any node.
> - Extend `test_tensor_transport_mode.py` with the PP, DP and Ray cases.
>
> The first stage still pickles materialized features when it relays requests to the next stage. That is unchanged by this PR and could be a follow-up.
>
> This PR is independent of #44575 and #44576, which address the same workload.
>
> ## Accuracy Tests
>
> Not applicable: the change only picks the transport for feature tensors.
>
> ## Speed Tests and Profiling
>
> A PP8 prefill server under image traffic for 30 minutes: 0.2 requests per second, 4 images per request, 59k to 74k prompt tokens. Base is `main`; fixed has this PR and #44575 and #44576.
>

> | `/v1/models` max | 1.08 s | 10 ms |
