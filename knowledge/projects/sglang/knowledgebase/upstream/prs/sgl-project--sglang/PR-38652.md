## Original PR description

# Support LMCache in UnifiedRadixCache

## Summary

This PR adds LMCache as an external KV-cache backend for SGLang's `UnifiedRadixCache` path. The integration keeps the existing radix-cache lookup, store, reuse, and flush behavior while allowing reusable KV blocks to be persisted and restored through LMCache.

Overall flowchart:
<img width="1618" height="1310" alt="image" src="https://github.com/user-attachments/assets/8e5ba772-41f5-4b5f-ab02-5f805660e8d1" />


The validation covers:

- prefix reuse across requests;
- repeated warm requests;
- cache flush followed by a cold request;
- accuracy on `gsm8k` and `mixed_prefix_gsm8k`;
- write-path overhead with no cache hits;
- filesystem restore performance with reusable prompt KV loaded from storage;
- comparison with the existing HiCache filesystem path.

## Related PRs
- Design doc: https://github.com/LMCache/LMCache/pull/5041
- `UnifiedLMCacheMPConnector` implemention: https://github.com/LMCache/LMCache/pull/4828

## Accuracy

Evaluation configuration:

- 200 examples;
- 32 threads;
- 5-shot prompting;
- temperature `0`;
- maximum output length `2,048` tokens.

| Model | Evaluation | Baseline | LMCache cold | LMCache warm |
|---|---|---:|---:|---:|
| DeepSeek-V4-Flash | GSM8K | 0.975 | 0.96 | 0.97 |
| DeepSeek-V4-Flash | Mixed-prefix GSM8K | 0.985 | 0.985 | 0.975 |
| Qwen-3.5-27B | GSM8K | 0.745 | 0.73 | 0.75 |
| Qwen-3.5-27B | Mixed-prefix GSM8K | 0.86 | 0.865 | 0.85 |

The observed score variation is at most 1.5 percentage points across the sampled runs, with no consistent degradation between cold and warm LMCache paths.

- curnane-lab · comment · 2026-09-24T02:30:28Z · [source](https://github.com/sgl-project/sglang/pull/38652#issuecomment-5806390478)

Watching this with interest — the linker-mode split (SGLang owns the unified radix tree, the external backend owns remote objects) looks like the right shape, and we noticed the companion POC (#40759 / LMCache#5304) already probed the Mamba-lifecycle corner before being withdrawn.

One semantic we'd like to see the interface make room for, whichever backend lands first: **when a KV prefix is restored but the Mamba/GDN state checkpoint is missing or behind the KV hit, who owns the gap and on what budget?**

Concretely, on hybrid GDN models the tree match can return a full-KV hit at `H` while the nearest usable state checkpoint sits at `C < H`. Today the hit retreats to `C` (or the tail is implicitly re-prefilled by the extend pass and re-captured via `_force_track_h`, cf. `mamba_branching_seqlen`). Neither is a deliberate policy, and an external linker that transfers FULL/SWA KV but not state makes the gap *more* common, not less.

There is an in-tree precedent for making this an explicit short-tail policy: `UnifiedRadixCache.swa_reprefill_tail_tokens` caps the match by one sliding window when the SWA ring is not content-stable, with the scheduler-side cap in `schedule_batch.py`. We think Mamba deserves the symmetric hook — e.g. a `mamba_replay_tail_tokens()` on the cache that the admission path charges against — so that linker backends (LMCache included) can rely on one replay/charge semantics instead of each inventing their own.

We've filed the full RFC with the proposal and offline measurements (GDN state tail-replay fidelity vs. recompute cost on Qwen3-class hybrids) as #40865. Happy to align the interface hook shape with whoever is driving the linker contract — the only hard requirement from our side is that "state-behind-KV" is representable in the transfer result, rather than collapsing the hit at transfer time.
