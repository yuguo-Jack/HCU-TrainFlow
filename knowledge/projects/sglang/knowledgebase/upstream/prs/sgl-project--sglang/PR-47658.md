# [Perf] SM120: honour SGLANG_OPT_DEEPGEMM_HC_PRENORM for the DeepSeek-V4.1 compensated mhc projection

[Upstream PR](https://github.com/sgl-project/sglang/pull/47658) · state: open · merged: False

## Original PR description

## Motivation

On SM120 (Blackwell consumer/workstation, capability 12.0) the DeepSeek-V4.1
hyper-connection pre-norm always runs the batch-invariant split-K projection
(`_hc_mix_stats_partial_kernel`), while SM90/SM100 run the compensated
three-bf16 projection (`_hc_mix_stats_bf16x3_kernel`) for the same shapes.

`_mix_stats_impl()` already enters the fused block on SM120, because
`use_fused_stats` tests `get_platform().is_blackwell`, which covers capability
majors {10, 11, 12}. What SM120 cannot reach is the *compensated* branch:
`use_bf16_projection` needs `bf16_parts`, and `bf16_parts` is only built when
the load-time gate in `deepseek_v4.py` passes, which requires
`(is_sm100 or is_sm90)`.

That gate also requires `envs.SGLANG_OPT_DEEPGEMM_HC_PRENORM`. The env default
is `True`, but `arg_groups/model_hook.py` turns it off for SM120:

```python
if not envs.SGLANG_OPT_DEEPGEMM_HC_PRENORM.is_set():
    envs.SGLANG_OPT_DEEPGEMM_HC_PRENORM.set(False)
```

The `is_set()` guard means a user may opt in explicitly. Today that opt-in is
silently ignored on SM120, because the arch whitelist still rejects it: setting
the env changes nothing, and there is no log line saying so. This PR makes the
existing opt-in work. It does not change any default, on any platform.

## What changes

Three arch conditions across two modules, plus routing SM120 into the branch that
does not need DeepGEMM, plus one test file that runs on this architecture:

- `deepseek_v4.py`: add `is_sm120` to the `bf16_parts` build gate, and to the
  `if get_platform().is_sm90:` branch that builds the bf16 triple directly.
- `deepseek_v4_mhc.py`: add `is_sm120` to the `_mix_stats_impl` gate that reads
  `hc.tf32_parts / hc.bf16_parts`.
- `test/registered/kernels/ops/layernorm/test_mhc_bf16x3_sm120.py`: new, registered
  on `1-gpu-small`, which `scripts/ci/runner_configs.yml` maps to `1-gpu-5090`, so
  the SM120 branch executes in CI rather than skipping on a mismatched card.

SM120 joins the SM90 branch on purpose. The `else` branch also builds tf32 parts
and dispatches `deep_gemm.tf32_hc_prenorm_gemm`, and that kernel does run here --
`sgl-deep-gemm` is a fork and ships `sm120_tf32_hc_prenorm_gemm`, present in the
0.2.2 build we measured and in the 0.2.3.post2 wheel `main` pins. We still take
the pure-Triton SM90 branch, because tf32 is the less accurate of the two on this
card: against an fp64 mirror of the reduce arithmetic it sits 1.61e-05
max-relative at M=1024 where the split-K path SM120 runs today sits 2.15e-06, and
in band bf16x3 is both faster and closer to the reference (6.93e-06 vs 1.65e-05 at
M=4096). The tf32 branch also builds parts at every row count, so taking it would
move rows below 4096 onto that kernel by default -- a change this PR does not
measure. Adding `is_sm120` to the whitelist *without* this routing is a different,
untested change and is not what this PR proposes.

## Mechanism boundary: which calls this actually reaches

Two gates are in series, and both have to hold:

1. load time — arch whitelist (this PR) **and** `SGLANG_OPT_DEEPGEMM_HC_PRENORM`,
   which decides whether `bf16_parts` is built at all;
2. run time — `use_bf16_projection = bf16_parts is not None and
   (hopper_medium or 4096 <= rows <= 65536)`.

`hopper_medium` is SM90-only, so on SM120 the compensated projection is reached
only for row counts inside `[4096, 65536]`. Decode (`rows == 1`) keeps
`hc_mix_stats_sinkhorn` on both arms; long-output and small-batch prefill shapes
are likewise outside the band. Under `--enable-decoder-swa-bounded-replay`, 49%
of the 80 `mix_stats` calls per step land in band (2360 bf16x3 vs 2440 partial
over 60 steps); the out-of-band calls are small-row and already cost 0.020 ms
each. That is why the family saving is 38.5 ms/step rather than the full 50.05
ms/step the projection kernel alone accounts for.

One caveat for anyone reading a per-kernel diff: the two wrappers share
`_hc_mix_reduce_sinkhorn_kernel`. Identical call count (4800 over 60 steps), but
2.72 -> 0.84 ms/step, because the reduce gets cheaper once the projection output
changes shape. A shared kernel is not automatically excluded from the delta.

## Measurements

8x NVIDIA RTX PRO 5000 Blackwell 72GB (SM120, capability (12,0)), PCIe only
(`nvidia-smi topo -m` all PHB, no NVLink), torch 2.14.1+cu130, SGLang 0.5.22 +
sgl-deep-gemm 0.2.2, a `deepseek_v41` MoE checkpoint (hidden_size 5120, 40
layers, hc_mult 4), TP8/EP8, `--chunked-prefill-size 16384`,
`--mem-fraction-static 0.78`, `--enable-decoder-swa-bounded-replay`,
`--context-length 131072`.

Workload: single stream, 60 requests x 8192 input tokens x 1 output token,
prefix cache flushed before each run, profiler started before traffic, window
purity checked from the engine log (`#new-token: 8192` delta == 60).

2x2 over the two conditions (same day, same machine, ms per 8192-token prefill
step):

| arch whitelist | env | projection kernel | GPU busy/step | mhc family | TTFT avg / p50 | max_total_num_tokens |
| --- | --- | --- | --- | --- | --- | --- |
| off | unset (hook -> False) | partial 50.05 | 482.52 | 94.76 | 517.8 / 492.5 | 6,168,576 |
| on  | unset (hook -> False) | partial 50.14 | 490.54 | -      | 526.2 / 492.7 | 6,168,576 |
| off | `=1`                | partial 50.10 | 490.02 | 94.81 | 522.8 / 492.5 | 6,168,576 |
| on  | `=1`                | bf16x3 13.11 | 447.66 | 56.02 | 455.0 / 455.0 | 6,018,048 |

Both single-condition arms are no-ops (p50 492.5 / 492.7 / 492.5, and the
projection kernel stays `_hc_mix_stats_partial_kernel` at 50.05 / 50.14 /
50.10 ms per step): the two conditions are in series, which is the point of the
2x2. With both, GPU busy drops 42.36 ms/step (-8.6%) against the same-day stock
control and 34.86 ms/step (-7.2%) against our production baseline; wall-clock
p8k p50 drops 491.1 -> 455.0 ms (-7.35%), two warm repeats 455.0 / 456.3
(0.3% spread). Cost: the bf16 weight triple is resident, so the KV pool shrinks
6,168,576 -> 6,018,048 tokens (-2.44%).

The first request after boot pays a one-off Triton compile (that run shows TTFT
avg 709.2 / p99 3220.4 ms while p50 is already 457.1); steady-state numbers
above are from warm runs.

Per-kernel census of the same two traces (60 steps each, TP-0) decomposes the
family delta of -38.74 ms/step: `partial` 50.05 -> 0.82, `bf16x3` 0 -> 13.11,
`_hc_mix_reduce_sinkhorn_kernel` 2.72 -> 0.84, post side
(`mhc_post_combine_norm_prefill_kernel<128>` + `mhc_post_tilelang_kernel` +
`_mhc_post_split_h_kernel`) 28.99 -> 28.47. Sum -38.52; the remaining 0.22 sits
in the other small quant/norm kernels in that bucket. No `tf32` kernel is hit in
either window, i.e. SM120 takes the pure-bf16 route and the DeepGEMM tf32 path is
never reached.

Per-call cross-check against a standalone micro-benchmark at M=8192, K=20480,
mix=24: partial 1.403 ms -> bf16x3 0.369 ms (3.80x). In the serving trace the
in-band calls go 1.25 ms -> 0.333 ms (3.8x), so the micro-benchmark ratio
reproduces in the engine.

For reference, the same checkpoint on 8x H20 (SM90) runs bf16x3 by default and
spends 10.8 ms/step in it; the SM120 mhc family was 94.76 ms/step before this
change and is 56.02 after, against H20's 66.23.

## Numerics

Kernel level, M=4096, K=20480, mix=24, checkpoint values `rms_eps=1e-20`,
`hc_eps=1e-6`, `sinkhorn_iters=20`. Both wrappers share
`_hc_mix_reduce_sinkhorn_kernel`, so any difference comes from the projection
kernel alone. Reference is a fp32 torch mirror of the reduce kernel's arithmetic.

| comparison | pre max abs | post max abs | comb max abs | max rel |
| --- | --- | --- | --- | --- |
| bf16x3 vs partial (current) | 1.37e-06 | 3.46e-06 | 6.26e-07 | 1.58e-05 |
| partial vs fp32 reference | 1.40e-06 | 4.59e-06 | 4.77e-07 | 1.32e-05 |
| bf16x3 vs fp32 reference | 1.67e-06 | 6.38e-06 | 8.64e-07 | 1.84e-05 |

The perturbation introduced by the swap is the same order as the deviation the
incumbent path already has from fp32. bf16x3 is not more accurate here, just
different at the 1e-05 relative level.

End to end: 226 generated arithmetic questions, each padded to 5570-5572 prompt
tokens so the prefill lands inside the projection band, padding unique per
question and the cache flushed before the run (`cached_tokens == 0` for all 226,
verified). Greedy, 12 output tokens, first-integer scoring. All three arms score
226/226, McNemar b01 = b10 = 0, exact p = 1.0. Per-question text identity and
logprob drift between the changed arm and the baseline (137/226 identical,
median |dlp| 3.44e-02) are at the level of a same-day A-A control that runs the
identical kernels from a different boot (144/226, median |dlp| 2.79e-02), so the
end-to-end instrument cannot resolve this change; accuracy saturates at 100% on
every arm. The kernel-level table above is the discriminating measurement, and we
are not claiming the end-to-end result as one.

## What we did not measure

Stating these as gaps, not as assurances:

- **Decode and the concurrency ladder were not re-measured.** What the new test
  pins is dispatch, not speed: at 1 and 64 rows the compensated kernel is made to
  raise and the split-K partial kernel is asserted to run, so "decode takes the
  same path as before" is now tested. The claim that decode and higher concurrency
  are unaffected *performance-wise* still rests on the row-band mechanism above
  (`rows == 1` never enters the compensated path), not on data from this branch.
- **SM121 and GB10 are still unmeasured.** The test's guard admits both `sm 120`
  and `sm 121`, but nothing has executed it on 121, so treat the guard as intent
  rather than coverage.
- **What we did not measure about tf32 is the trade below 4096 rows, not whether
  it runs.** `deep_gemm.tf32_hc_prenorm_gemm` does instantiate on SM120, and it is
  reachable from `DeepseekV4DecoderLayerBase.hc_pre` when the env is on and rows
  >= 1024. In the deployment we traced it is never taken -- 0 tf32 kernels across
  a 60-step trace covering ~1000 requests -- so this PR does not depend on it
  either way. What we did not measure is its accuracy and speed for the
  `[32, 4096)` band, which is exactly the range the `else` branch would move onto
  it by default; that is why the tf32 route stays out of this PR.
- **We do not know why SM120 is excluded today.** We report two facts (the hook
  carries an `is_set()` guard, and the tf32 route is both less accurate here and
  unmeasured below 4096 rows) and draw no conclusion about upstream's original
  reason. If there is a known SM120 blocker on the compensated path, this PR is
  wrong and we want to hear it.
- **Unmeasured shapes**: the form without `--enable-decoder-swa-bounded-replay`
  (a different share of calls is in band).
- **The cost is paid as soon as the env is on**, regardless of whether any call
  lands in band, because the weight triple is built at load time: -2.44% KV
  tokens. For a decode-only workload this PR is a pure capacity loss.

@BBuf @DarkSharpness one question about the arch whitelist this PR touches, because the answer decides whether the PR is right.

`arg_groups/model_hook.py` disables `SGLANG_OPT_DEEPGEMM_HC_PRENORM` on SM120 behind an `is_set()` guard, so a user can opt in - and that guard is not unique inside the block. What is unique is that the opt-in cannot work: the arch condition is tested in the very same predicate that reads the env, so the env alone never gets past it, and setting it changes nothing, logs nothing and fails nothing. Three of the neighbouring setters state their reason in a comment (FP8 wo_a, top-k v2, the indexer pair); the prenorm line carries none.

So: is SM120 excluded from `bf16_parts` because of a known blocker on the compensated path, or because nobody has run it there? If it is the former, this PR is wrong and we would like to know which constraint we are missing. If it is the latter, this PR only opens the door that is already there - no default changes on any platform, and only a caller that sets the env pays the resident weight triple.

Two pieces of evidence, since "trust us, we measured" is not much on its own.

1. The second commit adds `test/registered/kernels/ops/layernorm/test_mhc_bf16x3_sm120.py`, registered on `1-gpu-small` - which `scripts/ci/runner_configs.yml` maps to `1-gpu-5090`, so SM120 executes the branch instead of skipping on a mismatched card. It pins three things: the opt-in builds the bf16 triple and never the tf32 one, even with `ENABLE_JIT_DEEPGEMM` on and `deep_gemm.tf32_hc_prenorm_gemm` present; rows inside `[4096, 65536]` reach `hc_mix_stats_sinkhorn_bf16x3` and match an fp64 mirror of the reduce arithmetic at the tolerances the existing Hopper test already uses (`rtol=1e-5, atol=2e-6`); and rows outside that band (1 and 64) are asserted to stay on the split-K partial kernel by making the compensated one raise.

Self-correction on the comment above: we have now verified the thing we called unverified, and the answer changes our rationale, not the patch.

- tf32 sits 1.61e-05 max-relative (pre) at M=1024, where the split-K path SM120 uses today sits 2.15e-06;
