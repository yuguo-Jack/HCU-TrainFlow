# [Fix] tokenizer: Isolate and offload regular fast tokenization

[Upstream PR](https://github.com/sgl-project/sglang/pull/30771) · state: open · merged: False

## Original PR description

## Problem

Long regular HF fast-tokenizer calls in `TokenizerManager._tokenize_texts()` block the asyncio event loop and delay handlers such as `/ping`. Moving the call to a worker is insufficient if loop-side callers still share its native backend: a padding/truncation update can wait on the worker's encode.

Addresses the regular HF fast-tokenizer case in #30770. OpenAI conversion is already offloaded by merged #39771; this PR leaves that implementation in place.

## Changes

- Give regular HF fast tokenization one worker and a separate native backend, cloned once at startup. Pass the tokenizer explicitly to the worker rather than swapping `self.tokenizer` or introducing context-dependent tokenizer properties.
- Shallow-copy the wrapper per call so later wrapper settings are reflected without copying the vocabulary on the request path. Propagate request contextvars.
- Preserve synchronous behavior for slow/custom tokenizers and a tokenizer whose backend has been replaced. Preserve the dynamic-batch branch, cross-encoder/result handling and existing OpenAI conversion parallelism.
- Add registered CPU coverage for loop and real ASGI `/generate` + `/ping` responsiveness, backend separation, current wrapper settings, fallback behavior, serialization and context propagation. HTTP tests substitute model execution.

The backend-isolation direction follows @chromecast56's work and @hnyls2002's [shared-tokenizer review on #39716](https://github.com/sgl-project/sglang/pull/39716#discussion_r4150104467). #39716 and @JianWang97's #44502 both build on this PR; [coordination to choose one merge path](https://github.com/sgl-project/sglang/pull/30771#issuecomment-6561204899) is open. This can remain a small prerequisite or be folded into #39716 with attribution preserved.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Offloading tokenization to a separate thread via `asyncio.to_thread` is a great improvement for event loop responsiveness. However, if the tokenizer is a slow tokenizer (i.e., `not getattr(self.tokenizer, "is_fast", False)`), it is implemented in pure Python and is generally not thread-safe. Running it concurrently in multiple threads can lead to race conditions, corrupted tokenization outputs, or crashes.

Furthermore, since pure Python code does not release the GIL, running multiple slow tokenizations concurrently in separate threads does not provide any CPU parallelization benefits anyway. 

To ensure thread safety for slow tokenizers while keeping the asyncio event loop responsive, we should serialize calls to slow tokenizers using a lock (e.g., a `threading.Lock` initialized on the manager).

```python
            if not hasattr(self, "_tokenizer_lock"):
                self._tokenizer_lock = threading.Lock()

            def tokenize_sync():
                is_fast = getattr(self.tokenizer, "is_fast", False)
                if not is_cross_encoder and not is_fast:
                    with self._tokenizer_lock:
                        return [self.tokenizer.encode(t) for t in tokenizer_input], None

                if not is_fast:
                    with self._tokenizer_lock:
                        encoded = self.tokenizer(tokenizer_input, **tokenizer_kwargs)
                else:
                    encoded = self.tokenizer(tokenizer_input, **tokenizer_kwargs)

                return (
                    encoded["input_ids"],
                    encoded.get("token_type_ids") if is_cross_encoder else None,
                )

            input_ids, token_type_ids = await asyncio.to_thread(tokenize_sync)
```
