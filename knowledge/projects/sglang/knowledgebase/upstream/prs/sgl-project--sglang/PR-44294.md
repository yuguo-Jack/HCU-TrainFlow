# [Perf] [AMD] kimi-k3: Run shared-expert down GEMM through Aiter

[Upstream PR](https://github.com/sgl-project/sglang/pull/44294) · state: closed · merged: False

## Original PR description

## Motivation

On ROCm, module-level bf16 GEMMs go through Aiter's tuned `tgemm` when `SGLANG_USE_AITER` is set. Kimi-K3's shared-expert down GEMM does not: `_k3_bf16_gemm` is called with `out=` pointing at the fused `[latent | shared]` all-reduce slice, and that path still uses `torch.mm`.

So the GEMM already has the right destination, but it misses the tuned kernels. Routing it through Aiter only helps once `tgemm.mm` can take that `out=` — that is [ROCm/aiter#6538](https://github.com/ROCm/aiter/pull/6538). Without that Aiter build, this PR falls back to `torch.mm` and nothing changes.

The fused front GEMM (`out is None`) is a separate change (#41867). This PR only touches the shared-down path.

## Modifications

In `_k3_bf16_gemm` (`python/sglang/srt/models/kimi_k3.py`):

- When `out is not None`, HIP, and `SGLANG_USE_AITER` is set, call `tgemm.mm(..., out=out)`.
- If the installed Aiter has no `out` argument, or rejects the layout (`ValueError`), keep using `torch.mm`.
- Leave the `out is None` (front GEMM) path alone.

## Accuracy Tests

No model-math change when Aiter writes the same buffer `torch.mm` would.

Paired with [ROCm/aiter#6538](https://github.com/ROCm/aiter/pull/6538) on `PYTHONPATH`: result pointer matches the passed `out`, values match `F.linear` within bf16 tolerance.
