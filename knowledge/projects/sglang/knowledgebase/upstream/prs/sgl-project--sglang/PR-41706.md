# Fix CFG normalization to use per-sample norm instead of batch-flattened norm

[Upstream PR](https://github.com/sgl-project/sglang/pull/41706) · state: closed · merged: True

## Original PR description

Fixes #41705

## What

`_apply_cfg_normalization` in `python/sglang/multimodal_gen/runtime/distributed/cfg_policy.py` called `torch.linalg.vector_norm` with no `dim` argument, so the norm was computed over the whole flattened batch. The clamp decision and the rescale factor were shared across every sample in the batch rather than computed per sample.

This changes it to compute per sample norms with `dim=list(range(1, ndim)), keepdim=True`, matching the pattern already used by the sibling function `_rescale_noise_cfg` in the same file. The Python `if` becomes `torch.where` because the comparison is now a tensor rather than a scalar.

## Why it matters here

`runtime/pipelines_core/stages/latent_preparation.py` concatenates independent `Req` objects into a single DiT forward pass (`latents = torch.cat(raw_latents, dim=0)`). With a batch global norm, the clamp decision and rescale factor are shared across the batch, so one request's result depends on which other requests happen to be co-scheduled with it.

Three conditions all have to hold for that to bite, and it is worth being precise about them:

- **Batching above 1 must be enabled.** `batching_max_size` defaults to `1` (`runtime/server_args/server_args.py:542`), so a default deployment never forms a batch larger than one and is unaffected. This needs `--batching-max-size > 1`.
- **The config must actually run CFG.** Z-Image-Turbo sets `guidance_scale=0.0` and `cfg_normalization=False` (`configs/sample/zimage.py:21-22`), so `CFGPolicy.combine` returns at the single-prediction early exit and never reaches this function. The non-Turbo `ZImageSamplingParams` (`configs/sample/zimage.py:44-45`) does: `guidance_scale=5.0` and `cfg_normalization=True`.
- **The batch must be heterogeneous.** If the co-scheduled samples are identical the two norms agree exactly, since the shared `sqrt(N)` factor cancels in `max_norm / new_norm`, and the output is unchanged either way.

Verified on an L40S with `Tongyi-MAI/Z-Image` at default sampling params, no overrides. Instrumenting the function's input shape, two independently submitted requests merged into one forward pass:

```
Dynamic batch dispatch: requests=2, outputs=2/2, stop_reason=config_cap:2
CFGNORM_HIT shape= (2, 16, 1, 128, 128)
Processed dynamic batch of 2/2 request(s)
```

against the same request on its own:

```
CFGNORM_HIT shape= (1, 16, 1, 128, 128)
```

So the path is genuinely reachable with a batch dimension above 1. The divergence itself is a tensor level claim, pinned by the unit tests below. I could not isolate it at the pixel level and do not think that is achievable: a batch 1 forward and a batch 2 forward select different kernels, and same seed generations are not bit reproducible at fixed batch size either, so that noise sits above the effect.

## Relationship to upstream

Both the official Z-Image implementation (`Tongyi-MAI/Z-Image`) and `huggingface/diffusers` (`pipelines/z_image/pipeline_z_image.py`) use the same dim-less norm. This patch is therefore a deliberate divergence from upstream, not a transcription fix.

The mitigation is that behavior at batch size 1 is unchanged, since a global norm and a per sample norm are identical when there is only one sample. That case stays bit identical to the reference, and a test below pins it. The divergence only appears at batch size greater than 1, which is the case upstream does not exercise the way this serving path does.

If maintainers would rather keep this matching upstream exactly, say so and I will close this in favour of documenting the behavior instead.

## Checklist before this is ready for review

Tests to add:

- [x] `test_sample_result_is_independent_of_batch_composition`: run a sample alone and co-batched with an outlier, assert its result is identical. This is the test that encodes the actual claim in #41705 and fails on `main`.
- [x] `test_every_sample_respects_its_own_threshold`: assert every sample's post-clamp norm ratio is `<= cfg_normalization`, not just the batch aggregate.
- [x] `test_batch_size_one_unchanged`: assert batch size 1 behavior is unchanged, pinning reference parity and guarding the divergence argument above. Landed as `test_batch_size_one_matches_global_norm_reference`, comparing against the global-norm reference inline.

Verification still outstanding:

- [x] Run the new tests and confirm they fail on `main` and pass with this patch. On this branch: 5 passed. With `cfg_policy.py` reverted to `main`: 2 failed, and they are the two that encode the claim. `test_every_sample_respects_its_own_threshold` reports per-sample ratios `[1.347, 0.013, 0.013, 0.015]` against a 0.7 threshold, so the first sample is left unclamped by the batch-global norm. `test_batch_size_one_matches_global_norm_reference` passes both ways by design.
- [x] Run the existing `test/unit/test_cfg_policy.py` to confirm no regression. Now observed rather than inferred: `test_cfg_parallel_uses_parallel_arithmetic_order` passes on this branch. It exercises `cfg_normalization=0`, so it does not reach the changed code.
- [x] Confirm the input dtype is preserved for bf16 and fp16 predictions. It was not, and this was a real bug in the first version of the patch, caught in review by @adenzhou1350. The per-sample `scale` is fp32 and shaped `[N, 1, ...]`, so `noise_pred * scale` promoted bf16/fp16 output to fp32. The previous batch-global scale was 0-dim, and a 0-dim operand does not promote a dimensioned one, so `main` was unaffected; the old unclamped path also returned `noise_pred` untouched, while the new one always multiplies. Fixed by casting the product back with `.to(noise_pred.dtype)`, and pinned by a dtype case over fp32/fp16/bf16 across the clamped and unclamped branches.
- [x] Check the other `cfg_normalization` consumers reached through `_apply_cfg_postprocess`. There are two, `CFGPolicy.combine` and `run_cfg_parallel` in `cfg_parallel_utils.py`. Both pass a real tensor and feed the return straight into the next operation, so neither relied on a scalar return or on identity when no clamping occurs. One edge the per-sample change introduces: `dims` is empty for a 1-D prediction, and `torch.linalg.vector_norm(x, dim=[])` still reduces over every element, so 1-D inputs behave exactly as they did on `main`.

Optional, probably not required:

- [x] End to end check on a GPU. Reachability is confirmed and written up under "Why it matters here": the normalization does receive a batch dimension of 2 from two independently scheduled requests on non-Turbo Z-Image at default params. A pixel level comparison is not achievable, since changing the batch size changes kernel selection and same seed output is not bit reproducible, so the tensor level unit tests stand as the evidence for the divergence.
