# [Perf] [NVIDIA] eplb: Rebalance the DSpark draft MoE as its own placement family

[Upstream PR](https://github.com/sgl-project/sglang/pull/48038) · state: open · merged: False

## Original PR description

Depends on #47643; this branch contains its commits, only the last commit belongs to this PR.

## Motivation

The DeepSeek-V4 DSpark draft's MoE stages never get EPLB. FusedMoE drops expert location for every draft layer, DeepseekV2MoE gives DSV4 NextN layers no redundant slots, `ExpertLocationDispatchInfo` returns None for drafts, and the draft forward runs inside `disable_this_region`. The target-sized placement and recorder cannot serve the draft (different expert count, layer ids 0..S-1), so the draft always stays on the trivial layout.

The draft's routing is far from balanced. At bs40 DEP16 the draft MoE window balancedness is 0.28 (per stage 0.49 / 0.20 / 0.14), the busiest rank receives about 4.6x the mean rows, and the draft MoE costs about 0.65 ms per decode step.

## Modifications

Expert placement and recording are keyed by a family (`"target"`, `"draft"`):

- `get/set_global_expert_location_metadata` and the recorder accessors take a family. `Resources` holds the draft's own metadata and recorder.
- FusedMoE, TopK and HashTopK carry `expert_location_family` instead of a boolean. `resolve_layer_expert_location_family` is the one decision: a draft layer follows only the draft family, a target layer only the target's, and None keeps the trivial layout. It drives the redundant slots in DeepseekV2MoE, the weight loader's physical slots, and `ExpertLocationDispatchInfo` (so MegaGate's maps come from the family).
- With `SGLANG_DSPARK_ENABLE_DRAFT_EPLB=1` (default off) and `--enable-eplb`, the draft runner publishes a trivial draft placement from the DSpark stage config (draft routed experts, one layer per stage) with the target's `--ep-num-redundant-experts`, before the draft is built, plus a draft recorder without balancedness metrics (no second Prometheus histogram). It logs and stays off without `--enable-eplb`, for drafts other than DeepSeek-V4 DSpark, off DeepGEMM MegaMoE, under elastic EP, with `lp`/`fake` dispatch, or with a recorder mode other than `stat`. If the draft experts plus the redundant slots do not divide evenly over EP, it raises.
- The draft forward runs in `draft_expert_distribution_scope`: the routing hooks and `get_current_pass_local_count_buffer` (#47643) resolve to the draft recorder by stage index, so MegaMoE's in-kernel recv stats count the draft the same way they count the target. Without the draft family nothing is recorded, as before. Count buffers are allocated before CUDA graph capture and reset in place.
- The DSpark worker registers the draft with the target's `EPLBManager`, so both families share one schedule and one pause. The draft is dumped, solved with `init_by_eplb` on its own model config, and moved in place by the draft runner's `ExpertLocationUpdater`, which now takes the family whose metadata it updates.

## Accuracy Tests

GB300, DeepSeek-V4.1 with DSpark, SGLang nightly 2026-10-30 plus this change. The GSM8K and speed runs used this commit before it was rebased onto the recorder-slice refactor in #47643; the smoke and unit tests below ran on this head. GSM8K via sgl-eval 0.1.3, 1319 questions, 1P1D with a DEP16 decode, real DSpark acceptance, draft EPLB on.

| decode | GSM8K | accept length |
|---|---:|---:|
| draft EPLB on, 6 rebalances during the eval | 96.66% | 3.48 |
| stock (earlier checks) | 96.66-97.04% | 3.49-3.51 |

Each rebalance moved all 3 draft stages in 0.66-0.72 s with no lost experts. All 16 decode ranks logged `Draft EPLB on: 3 stages, 128 experts in 144 slots over EP 16`.

Server smoke on this branch's head (same image, one GB300 node, DEP4 MegaMoE, DSpark block 5, `--enable-eplb --ep-num-redundant-experts 16 --eplb-rebalance-num-iterations 200`, draft EPLB on): all 4 ranks logged `Draft EPLB on: 3 stages, 128 experts in 144 slots over EP 4`. GSM8K (sgl-eval 0.1.3, 400 questions) scored 97.25% with 0 errors and accept length 3.45-3.70 per rank, through 18 rebalances that each moved all 3 draft stages (1.76-1.81 s including the target), with no errors in the server log.

CPU unit tests on this head: test_topk_routing_inputs, the eplb unit directory (incl. test_megamoe_prefill_recorder, test_expert_location_weight_loading), test_mega_moe_deepgemm_api, test_mega_moe_decode_capacity, test_runtime_context, test_deepseek_v4_shared_expert_fusion, test_graph_routing_context, test_megakernel_runtime, test_humming_linear: 332 passed, 2 skipped (SM90-only), 0 failed; after merging main, 340 passed, 2 skipped, 0 failed (main alone: 331 passed, 2 skipped).

## Speed Tests and Profiling

Same image and change.

- DEP16, bs40: draft MoE window balancedness 0.24-0.28 -> 0.75 after the first rebalance; decode step about 0.1 ms faster.
- DEP32 decode with 6x DEP2 prefill, c3018, vs a same-day control, 7 rebalances in each run:

| metric | control | draft EPLB |
|---|---:|---:|
| output throughput per GPU (tok/s) | 407,259 | 408,952 (+0.4%) |
| p90 interactivity | 273.8 | 272.7 |
| E2E-normalized p90 interactivity | 67.1 | 67.6 |
| TTFT p90 | 2.37 s | 2.30 s |
| decode step, 16-23 running per rank | 11.04 ms | 10.78 ms (-0.26 ms) |

The client-side metrics are within run-to-run noise: two identical controls differed by 2.5% in p90 interactivity. The gain is in the decode step time, -0.09 to -0.29 ms (1-2.7%), and grows with the number of running requests per rank. The feature is off by default.
