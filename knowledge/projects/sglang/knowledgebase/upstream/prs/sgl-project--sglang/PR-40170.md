# Fix Sarvam MLA model for FlashInfer TRT-LLM MoE runner and CUDA graphs

[Upstream PR](https://github.com/sgl-project/sglang/pull/40170) · state: open · merged: False

## Original PR description

## Motivation

The Sarvam  105B MLA model  does not run correctly under the FlashInfer TRT-LLM MoE runner with tc-piecewise CUDA graphs, which is the production configuration for this model on B200:

- At batch size 1 the torch.compile fast path swaps in `fused_moe_forward_native`, which cannot unpack `BypassedTopKOutput` (with the TRT-LLM runner, routing is fused inside the kernel) and crashes. Swapping MoE kernels per batch size would also make bs=1 numerics differ from bs>1.
- The FA4 attention backend was selected on GPUs where FA4's absorbed-MLA `qv` argument is not implemented (SM100/SM110 only).
- Released checkpoints carry JSON-null routing values in their HF configs, so the intended BF16-weight/FP32-logit router contract was not selected without command-line overrides.
- The attention value projection materialized a transpose/clone that tc-piecewise graphs and `o_proj` do not need.
- Stream discipline under breakable CUDA graph capture borrowed the process-level side stream instead of owning an alt stream.

This PR makes the model run the documented golden configuration out of the box, with no new user-facing flags.

## Modifications

All changes are confined to `python/sglang/srt/models/sarvam_moe.py` and its unit test file; three commits:

- `e415858fe5` — Support DSpark capture in Sarvam MLA model.
- `50d6b920b7` — Use the Sarvam fused MoE routing contract.
- `6eb70c8664` — Integration fixes:
  - Route experts through `BypassedTopKOutput` when the FlashInfer TRT-LLM MoE runner is selected, calling the graph-safe `experts()` wrapper under tc-piecewise CUDA graphs instead of `forward_impl()`.
  - Keep the FlashInfer TRT-LLM MoE runner active at bs=1. The guard lives on the model side: when the TRT-LLM bypass is active, `SarvamMoESparseMoeBlock` installs an instance shadow of the experts' `quant_method._torch_compile_forward` that returns `None`, so the compiled dispatch is kept instead of the bs=1 native swap.
  - Gate the FA4 attention backend to SM100/SM110: FA4's absorbed-MLA `qv` argument is only implemented there, so older GPUs keep the pre-FA4 concat-RoPE dispatch.
  - Default the router to the BF16-weight/FP32-logit contract (`bf16_fp32`) and treat JSON-null routing values in HF configs as absent.
  - Write the attention value-projection BMM directly into the flattened layout consumed by `o_proj` on SM100/SM110 (fp8 weights and tc-piecewise graphs keep the legacy path), removing a transpose/clone kernel from every attention layer.
  - Stream discipline for graph capture: the model owns its `alt_stream` lifetime instead of borrowing the process-level side stream, the dual-stream MoE path is disabled under breakable CUDA graphs, and attention layers stay on the graph's main stream; `alt_stream` is reserved for shared-expert overlap.

## Accuracy Tests

Teacher-forced NLL on B200 (TP=2, production flags: `trtllm_mla` attention, `flashinfer_trtllm` MoE runner, FA4 prefill, torch.compile + tc-piecewise CUDA graphs): the same 100-prompt panel is echoed through each scorer with per-position `logprobs` captured, and all scorers produce identical token streams, so every row compares the logprob of the same token at the same position. Mean NLL/token is first-named vs second-named scorer, relative is the second scorer's total NLL relative to the first's, the median is the per-position absolute NLL delta in nats, and the signed mean is first minus second per position:

|---|---|---|---|---|---|
| vLLM nightly vs this branch | 466,806 | 3.950269 vs 3.959746 | 0.002399 (0.24%) | 0.017988 | -0.008658 |
| This branch vs HF reference | 411,624 | 3.981151 vs 3.514878 | -0.11712 | 0.444103 | +0.45926 |
| vLLM nightly vs HF reference | 406,571 | 3.973466 vs 3.515187 | -0.115335 | 0.433786 | +0.452462 |

The HF-reference legs cover 94/100 prompts (the six longest exhaust the reference scorer's memory). Both engines sit a comparable distance from the HF bf16 reference (signed offsets +0.459 vs +0.452 nats per token), so the fixes add no measurable accuracy damage on top of normal engine-level bf16 numerics; the engine-vs-engine drift has no systematic direction (per-prompt signed means all within 0.10 nats of zero). An output degeneration screen (vocabulary collapse, repetition loops) found no degeneration.

The previous way to serve this checkpoint was through the DeepSeek-V3 compatibility config (a DeepSeek-named config over the Sarvam weights). The guard affects only the plain non-speculative configuration and is validated separately in the A/B above.

The flattened value-projection BMM additionally removes one transpose/clone kernel launch per attention layer on SM100/SM110; it was not isolated in a separate benchmark.
