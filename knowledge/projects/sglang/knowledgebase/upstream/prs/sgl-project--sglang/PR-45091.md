# [Fix] flashinfer: Keep sliding-window layers off the ragged prefill wrapper

[Upstream PR](https://github.com/sgl-project/sglang/pull/45091) · state: open · merged: False

## Original PR description

## Motivation

With `WrapperDispatch.SLIDING_WINDOW`, the FlashInfer backend plans two paged prefill wrappers (window /
full) but only one ragged wrapper, planned without a window. On a cold prefill (no cached prefix) with
the ragged path enabled, sliding-window layers go through that ragged wrapper:

- the `extend_no_prefix` branch calls `prefill_wrapper_ragged.forward(...)` with no `window_left`, so
  the layer attends the whole prompt;
- the prefix branch passes `window_left` at run time, but FlashInfer selects the kernel at plan time, so
  a run-time window on a wrapper planned without one does not mask.

Text-only models with sliding-window layers (multimodal models already disable ragged) therefore
compute full attention on those layers for prompts longer than the window. We found it serving a model
whose sliding-window output feeds a log-sum-exp merge: teacher-forced top-1 against the HF reference
dropped from ~99.97 % to 99.90 % on 6K-token prompts, with reference margins up to 1.5 at the
disagreeing positions; the fix restores bf16-tie level.

## Modifications

`use_ragged` is False under `WrapperDispatch.SLIDING_WINDOW`; those batches use the per-dispatch paged
wrappers, which are planned with `window_left`. Other dispatch modes are unchanged.

## Accuracy Tests

- New unit test `test/registered/unit/layers/attention/test_flashinfer_swa_ragged_prefill.py`: fails on
  main (ragged chosen under sliding-window dispatch), passes with the fix.
- Model-level effect as described above (6,000-token passage, 99.90 % -> 99.97 % top-1 vs HF).

## Speed Tests and Profiling

Only sliding-window models on FlashInfer change: their cold prefills use the paged wrappers instead of
the ragged one. We have not yet measured prefill throughput before/after on a sliding-window model; we will add it here.

- tonylkc · comment · 2026-10-19T05:24:23Z · [source](https://github.com/sgl-project/sglang/pull/45091#issuecomment-6260317352)

Follow-up on the prefill-throughput TODO in the description. We measured it on Gemma-3-12B-it (text-only, sliding window 1024 on 5 of every 6 layers), FlashInfer backend, bf16, on a single GPU. Baseline is the nightly at b234b5c3, compared with the same tree plus this patch. The command was `python -m sglang.benchmark.one_batch --attention-backend flashinfer --batch-size 1 4 --input-len 2048 8192 12000 --output-len 4 --disable-radix-cache`. Each row is the median of 3 runs. Run-to-run spread was 2% or less.

| batch x input | before (tok/s) | after (tok/s) | change |
|---|---|---|---|
| 1 x 2048  | 24,460 | 24,140 | -1.3% |
| 1 x 8192  | 22,880 | 23,970 | +4.8% |
| 1 x 12000 | 21,500 | 23,060 | +7.3% |
| 4 x 2048  | 25,560 | 24,660 | -3.5% |
| 4 x 8192  | 22,940 | 23,750 | +3.6% |
| 4 x 12000 | 21,480 | 23,030 | +7.2% |

Throughput goes up with prompt length because the sliding-window layers stop attending the full prompt. At 2K tokens the paged prefill path is slightly slower than the ragged one, because at that length the window saves little work.

The correctness side matters more than the speed. We teacher-forced a 12,000-token passage and compared top-1 next-token agreement against the triton backend (which applies the window correctly):

| | positions < 1023 | positions >= 1023 | mean abs dlogprob | KL (top-20) |
|---|---|---|---|---|
| before | 98.34% | 17.05% | 8.34 | 2.89 |
| after | 98.24% | 98.73% | 0.055 | 3.0e-3 |

Without the patch, cold FlashInfer prefill on this model is wrong past the first window. With it, FlashInfer matches triton across the whole prompt.

If the 2K regression matters, we could keep the ragged path when the extend length is at most the window, since the result is identical in that case. We kept the patch minimal for now and are happy to add that if you prefer.
