# [Fix] dsv41: Keep MegaGate out of prefill graphs by gating on the forward mode

[Upstream PR](https://github.com/sgl-project/sglang/pull/45969) · state: closed · merged: True

## Original PR description

## Motivation

`should_use_mega_gate` relied on `get_forward().is_extend_in_batch` to keep DeepGEMM's fused gate on decode and verify. The prefill CUDA graph runner clears that flag before capture (`prefill_cuda_graph_runner.py:866,951`), so with `SGLANG_OPT_DEEPGEMM_MEGA_GATE=1` the gate also ran inside captured prefill graphs of up to 2048 rows. On GB300 (DeepSeek-V4.1-Flash, DP2/EP2 MegaMoE, breakable prefill graphs) that produced an `unspecified launch failure` during prefill capture that disappears under `CUDA_LAUNCH_BLOCKING=1`.

## Modifications

- `should_use_mega_gate` takes the `forward_batch` and admits only `DECODE` and `TARGET_VERIFY`; `None` means no gate.
- Unit test: the admission case now checks decode and target-verify admit, extend with the flag cleared does not, and `None` does not.

| Guard | `CUDA_LAUNCH_BLOCKING` | Prefill graph capture | GSM8K (200, sgl-eval) |

| none (main's `is_extend_in_batch`) | off | `unspecified launch failure` at the 2nd shape, 3 of 3 runs on 3 nodes | not reached |

| this PR, cherry-picked | off | passes | 0.975, accept len 4.22 |

Gate off on the same recipe captures and scores 0.975 every time, so the failure is specific to the gate being reachable during prefill capture. With the guard the gate only runs for `DECODE` and `TARGET_VERIFY` batches, which also keeps it off the DSPARK draft's extend forwards.
