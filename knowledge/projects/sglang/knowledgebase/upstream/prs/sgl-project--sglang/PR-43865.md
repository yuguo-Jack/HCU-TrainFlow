# [Fix] tokenizer_manager: Prevent scheduler crash and has_audio_understanding misreport for audio-declaring models without an audio tower

[Upstream PR](https://github.com/sgl-project/sglang/pull/43865) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #43864

An audio request sent to a model whose multimodal processor defines an audio token but has no audio tower - e.g. `gemma-4-31B-it`, a non-audio variant of the Gemma 4 family whose `config.json` ships `audio_config: null` - is not rejected at the API layer. It reaches the scheduler, where `get_audio_feature()` raises inside `model.forward`, and the whole scheduler process dies.

Two underlying problems, both fixed here:

1. Request validation only checks `is_multimodal`, not per-modality capability, so the audio request passes tokenization/dispatch and fails deep in the scheduler, killing the scheduler process.
2. `ModelConfig.is_audio_understandable_model` used `hasattr(hf_config, "audio_config")`. Because the config key is present with a `null` value, `hasattr` is `True` even though no audio tower exists, and the model is misreported as audio-capable (`/get_model_info`: `has_audio_understanding: true` for `gemma-4-31B-it`).

Scope:

- The crash (problem 1) affects only models whose processor defines an audio token while the model has no audio tower. For all other models the audio never reaches the scheduler: models whose processor defines no audio token drop it in the processor, and text-only LLMs have no multimodal processor at all.
- The misreport (problem 2) is a config-level issue: it affects any model whose `config.json` carries `audio_config` with a `null` value.
- Existing behavior is otherwise unchanged: for models whose processor defines no audio token, requests are handled exactly as before (verified on `glm-5.3-flash`, see Production verification). The only intentional exception is the corner case noted under Limitations.

## Modifications

- `python/sglang/srt/configs/model_config.py`: `is_audio_understandable_model` now requires `audio_config` to be present and non-`None` (top-level and under `thinker_config`) instead of `hasattr`. This makes the capability flag - and the `/get_model_info` report - correct for models with a `null` audio config.
- `python/sglang/srt/managers/tokenizer_manager.py` (`_tokenize_one_request`): reject with a per-request error when a request carries audio data, the model's multimodal processor defines an audio token, and the top-level audio_config is present but explicitly None (audio tower disabled), return 400 with :

  ```
  Audio inputs are not supported by <served_model_name>
  ```
  Limitations:
  - Audio only; the same shape of problem could exist for other modalities but is out of scope here.
  - Corner case : on the native `/generate` path, a request that passes valid `audio_data` for a model whose processor defines an audio token but which has no audio tower, while the prompt carries no audio placeholder, used to succeed (the base processor drops the surplus audio with a warning); it is now rejected with the same 400 error. The OpenAI path is unaffected - it always inserts the placeholder, and those requests previously crashed the scheduler. We keep the broader guard because an explicit error is preferable to silently discarding user-provided audio.

## Accuracy Tests

No model output path is changed (the guard rejects requests that would otherwise crash the engine; the config-flag change only corrects a misreported capability), and existing behavior for models whose processor defines no audio token is preserved. 

Verified on `gemma-4-31B-it` (4x H20): an audio request now returns a clean per-request error instead of killing the scheduler, and the engine keeps serving:

```json
{"object":"error","message":"Audio inputs are not supported by gemma-4-31B-it","type":"BadRequestError","param":null,"code":400}
```

Existing behavior also verified on `glm-5.3-flash` (whose processor defines no audio token): an audio request still returns 200 exactly as before this change.

## Speed Tests and Profiling

Not applicable - no change to the forward path; the only addition is a lightweight per-request validation at tokenization time.
