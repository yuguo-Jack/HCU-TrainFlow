# [Fix] Work around a CPython fork deadlock in the CPU preprocess pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/44143) · state: closed · merged: True

## Original PR description

- Forked `ProcessPoolExecutor` workers inherit the parent's `concurrent.futures.process._threads_wakeups`. Since Python 3.12.8 / 3.13.1 each `_ThreadWakeup` has a lock, and a worker's exit hook (`_python_exit`) takes the lock of every inherited wakeup. If a parent thread held one at fork time, the worker never exits and `shutdown(wait=True)` hangs.
- The multimodal CPU preprocess pool hits this after `_replace_broken_cpu_executor`: the replacement forks its worker while the broken pool's manager thread and the cleanup thread still take that pool's wakeup lock. `test_llava_processor_pool.py::test_replacement_pool_runs_after_real_worker_exit` hung until the 15-minute job timeout in `base-a-test-cpu` on #39730 and #43480 (Python 3.12.15).
- The pool now passes an `initializer` that clears the inherited wakeups in each worker; a worker has no executors of its own.
- This works around a CPython regression from python/cpython#125451 (the fix that added the lock), still present on CPython main; it relies on the private `_threads_wakeups`. Moving the pool off `fork` would avoid it too, at the cost of slower worker startup for everyone.

No behavior change otherwise.

Verification (Linux):
- A stdlib-only replay of the test, 16 processes x 300 rounds: hung in 16/16 on Python 3.12.14 and 0/16 on 3.12.3; with the initializer, 0/16 on 3.12.14. A stuck worker's stack ends in `_ThreadWakeup.wakeup` called from `_python_exit`.
- `test_llava_processor_pool.py` on Python 3.12.14, 400 runs each: main hung 6 times, this PR 0.
