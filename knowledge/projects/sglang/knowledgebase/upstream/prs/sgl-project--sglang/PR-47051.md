# [Fix] QSA: Keep two groups in the pending index-key ring

[Upstream PR](https://github.com/sgl-project/sglang/pull/47051) · state: open · merged: False

## Original PR description

## Motivation

The QSA indexer keeps each request's not-yet-compressed index keys in a per-request ring, at slot `req_pool_idx * ratio + position % ratio`, so the ring holds one group (`ratio = 4`). A speculative verify step writes the ring key of every draft row. When the step does not start on a group boundary, its later rows land in the slots of the group still pending before them, which corrupts that group's compressed key in two ways.

- **Within a step:** verify stores all rows' keys first (`build_pending_ring_slots`) and only then reads the completed group back from the ring. Take `pos0 = 5`, rows 5-8: group 4-7 completes at row 7, but row 8 has already overwritten key 4 in slot 0. The group is compressed from keys 8, 5, 6, 7.
- **Across steps:** nothing restores the ring after acceptance. With rows 7 and 8 rejected, the next step starts at position 7, completes group 4-7, and reads key 4's slot, which still holds rejected key 8.

In both cases the stored compressed key is not the one the QSA definition specifies: RMSNorm(AvgPool(k[p_b : p_b + r - 1])) over the block's own keys (Qwen3.8-Next tech report, Eq. (13)). It stays in the compressed cache for the rest of the request and skews the indexer's block selection. Attention values and the KV cache are not affected. The ring is hit by any verify step that does not start on a multiple of 4, roughly 3 steps in 4.

## Modifications

The ring holds two groups per request: slot `req_pool_idx * 2 * ratio + position % (2 * ratio)`. A verify window of up to `ratio + 1` rows then never shares a slot with a member of the group pending before it. A rejected row's key only sits in the slot of its own position, which is rewritten when that position is processed again, before any group reads it.

- `qsa/metadata.py`: `QSA_RING_GROUPS = 2`. `build_pending_ring_slots` and `build_group_ring_slots` index the ring by `ring = QSA_RING_GROUPS * ratio`. Extend's dump rows become `[0, ring)`.
- `qsa/graph_metadata.py`: the graph row-metadata kernel and the draft graph-metadata kernel take a `RING` constexpr for `state_slots` and `ring_locs`. Compression still uses `RATIO`.
- `mem_cache/qsa_kv_pool.py`: the key-state and RoPE-position buffers have `num_request_slots * QSA_RING_GROUPS * ratio` rows. That is 4 extra rows per request slot: one bf16 128-dim key per row in each QSA layer, plus the RoPE rows.
- `qwen_sparse_attn_backend.py`: the existing limit `speculative_num_draft_tokens <= ratio` is unchanged; only its comment and error text are updated.
- Test: `test_verify_rows_never_overwrite_a_pending_group` (`test_qsa.py`) checks, for every start position 0-7, that a 4-row verify window never writes a slot that holds a member of the pending group. It fails for 6 of the 8 start positions without this change.

## Accuracy Tests

- `test/registered/kernels/ops/attention/qsa/test_qsa.py` (156 passed, 1 skipped), `test_qsa_rocm.py` (4 passed), `test_qsa_fused_kv_prepare.py` (174 passed) on MI355X. `test_qsa_indexer.py` and `test_qsa_determinism.py` fail the same tests with and without this change on this machine.
- End to end, Qwen3.8-Flash-Next (`amd/Qwen3.8-Flash-Next-Quark-MXFP4-AttnFP8-PLEFP8`), 1 x MI355X, TP1, NEXTN 3 steps / topk 1 / 4 draft tokens, with the sgl-amd-mono monokernel (`--enable-amd-monokernel`), which reads the ring layout from the pool: 10/10 requests at C=1, measured accept length 3.26, the same as before the change.
- SGLang's own path (no monokernel), same model and NEXTN setup, `--attention-backend triton`, 16 concurrent requests (sgl-eval), main af21e2b989 without and with this change:

  | | main | main + this PR |
  |---|---|---|
  | GSM8K, 1319 q, thinking off, greedy | 95.00% | 95.15% |
  | AIME25, 30 q x 4, thinking, T 0.6, top-p 0.95, max 32k tokens: pass@1 / pass@4 / maj@4 | 90.00% / 93.33% / 93.33% | 90.00% / 93.33% / 93.33% |
  | Accept length (server average after GSM8K / after AIME25) | 2.99 / 2.89 | 2.99 / 2.87 |

  AIME25's outputs average about 10k tokens, so the indexer selects blocks over the request's own generated tokens. GSM8K mostly stays within the 2048-token budget, where every block is selected.

The change only moves ring addresses; no kernel does more work.

We measured a similar change in a downstream build on a Qwen3.8-Flash-Next-based checkpoint with NEXTN 3/1/4, in real serving on RTX PRO 6000. The share of decode-formed compressed keys that differed from a prefill of the same tokens went from about 82% to 0 of 1.78M. Step time and acceptance were unchanged (95.26 vs 94.98 ms/step at 96 concurrent requests, accept length 3.161 vs 3.151).

For reviewers comparing with #46125, which fixes the same bug: at ratio 4 with up to 5 verify rows, both PRs use an 8-slot ring per request (`2 × ratio` here; the next power of two ≥ `ratio + rows − 1` in #46125). #46125 also adds a 35-case GPU harness (`test_qsa_verify_ring.py`) that checks the compressed cache bit-for-bit against prefill. That harness also passes on SM120 and SM100. It might be worth running it against this layout too, before one of the two is picked.
