# [Doc] layer-boundary/moe: Correct guides and comments that drifted from the code

[Upstream PR](https://github.com/sgl-project/sglang/pull/44896) · state: open · merged: False

## Original PR description

## Motivation

Two developer guides and three comments disagree with the code on `main`. Readers and agents follow them, so each points to the wrong module or describes a path that no longer runs. Every correction below was checked against `main` at 86e67f7d93 and rechecked at b234b5c32e. This PR changes docs and comments only.

Left to other PRs:
- The stale guard tests and resolution helpers named in `.agents/skills/sglang-runtime-context/SKILL.md` are left to #43666, which already edits that file.
- Three shared-experts-fusion texts in `python/sglang/srt/layers/moe/utils.py` still describe the model gates as writers: the `is_shared_experts_fusion_disabled` docstring ("Written (both ways) by each MoE model's gate ..."), the `draft_model_build_scope` docstring ("the gates the draft runs also record their decision"), and the `initialize_moe_config` comment ("each model's gate refines the ACTIVE value"). #44913 rewrites them, so they are left to it to avoid a conflict.

Merge order: this PR should land before #44913. They overlap in one `MoeFlags` comment hunk in `runtime_context.py`, which #44913 resolves on rebase.

## Modifications

**`docs/docs/developer_guide/layer_boundary.mdx`: the module map**
- It omitted `facts.py` (`facts_of()`, the record binding keeps of a pipeline neighbour or a bound producer; added in #43459) and `row_transport.py` (`RowTransport`, `ComputeTransport`; added in #43607).
- It omitted five residual schemes: `residual/post_norm.py` (#41779), `residual/ihc.py` (#42477), `residual/gated.py` (#42478), `residual/attn_bank.py` (#42894) and `residual/short_conv.py` (#43606).
- It listed CP under `adapters/` and kept a "CP adapters" bullet. #42036 removed the CP adapter. `adapters/` now holds `attention.py`, `branch.py`, `lora.py` and `overlap.py`. `boundary.py` now picks the CP row moves as one `contracts.py::CpMoves` per kind of prefill CP:
  - the FFN-input gathers are `prepare.py::_then_attn_cp_gather` and `_then_moe_cp_gather`;
  - the take-backs and the reduce-scatter are in `ops.py` (`attn_cp_take_back_output`, `moe_cp_take_back_output`, `attn_cp_reduce_scatter_output`).

  The `boundary.py` row now says so, citing `CpMoves`, whose docstring describes the three moves. The bullet is gone.

**`docs/docs/advanced_features/expert_parallelism.mdx`: the Extensible EP Framework section**
- The flow diagram called `MoeRunner.forward`. The method is `python/sglang/srt/layers/moe/moe_runner/runner.py::MoeRunner.run`.
- The guide presented pre-permute, runner core and post-permute as the general route. `MoeRunner.run` has three routes:
  - It calls the fused function first, when `FusedOpPool.get_fused_func(a2a, runner)` returns one and LoRA is off. Several backends have only a fused path (`runner_core = None`).
  - Otherwise, a `DispatchMoeRunnerCore` gets `run_from_dispatch(dispatch_output, ...)` and no permutes run. Examples are `lora/lora_moe_runner_marlin.py::MarlinLoraRunnerCore` and any core registered through `register_moe_runner_core`.
  - Otherwise, pre-permute, the runner core and post-permute run.

  In `moe_runner/triton.py`, `fused_experts_none_to_triton` serves `--moe-a2a-backend none`, and the `standard` to `triton` permutes are the fallback, used for example with LoRA.
- `register_fused_func` registers into `FusedOpPool`, not `PermuteMethodPool` (`moe_runner/base.py`).

**`python/sglang/srt/runtime_context.py::MoeFlags`: comments on the shared-experts-fusion leaves**
- The comments credited `speculative_moe_backend_context` with bracketing a draft's build and setting `in_speculative_scope`. `python/sglang/srt/layers/moe/utils.py::draft_model_build_scope` does both. `speculative_moe_backend_context` only swaps `runner_backend`.
- They also said each model's gate (`determine_num_fused_shared_experts`) refines the ACTIVE leaf. Since #33889 the loader's `install_shared_experts_fusion_decision` sets it (`model_loader/loader.py`), and the gates only read it. Inside the draft scope, the draft's decision lands on the speculative leaf when the decision is installed, not on exit.
- The `in_speculative_scope` comment now also says that draft builds read the flag to skip target-only setup. `layer_boundary/fusions/cutedsl.py` builds no workspace for a draft, and `models/mimo_v2.py` turns off expert remap, bypassed top-k and the CuTe DSL fusion for a draft.

**`python/sglang/srt/layers/moe/utils.py::should_use_dp_reduce_scatterv`: docstring**
- The docstring said the reduce-scatterv runs in the standard dispatcher's `combine()`. `StandardDispatcher.combine` reduce-scatters only on the FlashInfer CUTLASS FP4 all-gather path, which this predicate excludes. The predicate is read in `layer_boundary/exit.py::exit_facts`, and `_select_dp_reduce_scatter` returns `ops.py::dp_reduce_scatterv` for the FFN output's attention-DP return. The reduce-scatterv first lived in the layer communicator (#22642), which the boundary package replaced.
- On the stage-boundary path the predicate is necessary but not sufficient: `exit_facts` also needs `output.may_reduce_scatterv`, which `factories.py` sets only when `--boundary-reduction` resolves to `rsv` or `rs+rsv`. `models/deepseek_common/moe_transport.py` uses the predicate alone. The docstring now says "whether the parallel configuration allows" and names the boundary requirement.

**`python/sglang/srt/layers/layer_boundary/residual/add_norm.py`: comments**
- The TODO above `FUSE_ALLREDUCE_MAX_BATCH_SIZE` gave the cap as 128 tokens (one-shot only, from #7864). The value has been 2048 since #9278. #12915 also lowered a separate 4096 bound to 2048 to fix speculative acceptance length. The new comment says what the constant does now: it caps the batch for the non-CuTe-DSL FlashInfer all-reduce fusion, and `base_runner.py::_pre_initialize_flashinfer_allreduce_workspace` uses it to size that fusion's workspace before graph capture. The CuTe DSL fusion is outside both: `flashinfer_ar_fusion_applies` excludes it, and `base_runner.py` returns before sizing the workspace when it is in use.
- The note "flashinfer 0.6.1 caused performance regression on sm100" sat on the line that enables SM100. #17591 re-enabled SM100, measuring the fused kernel as still faster than NCCL even while broken, and left the note in place. The note is removed under the comment-style rule: it is history about FlashInfer 0.6.1, the pin is now 0.7.2, and next to code that enables SM100 it reads as a contradiction.
