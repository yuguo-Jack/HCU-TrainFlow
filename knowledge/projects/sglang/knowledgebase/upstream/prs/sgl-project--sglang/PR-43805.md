# [Kernel] Extend the SM100 swapab decode path to the V4.1 KV layouts

[Upstream PR](https://github.com/sgl-project/sglang/pull/43805) · state: open · merged: False

## Original PR description

# [Kernel] Extend the SM100 swapab decode path to the V4.1 KV layouts

## Motivation

The SM100 small-batch decode path (`swapab_attention`, added in #39674) reads
only the packed **V4** cache: `can_use_swapab_attention` gates on
`kv.shape[-1] == KVLayout.V4.bytes_per_token` (584 B). A V4.1 cache (528 B main,
288 B compressed fp4) therefore never reaches it and falls back to the generic
FlashMLA decode.

Measured on a 4x B300 (sm_103) with DeepSeek-V4.1-Flash, TP4/EP4, single request,
median decode ITL: the same V4.1 cache decodes **~11-19% faster** once it reaches
this path (baseline 4.40 ms -> 3.54 ms at 8k; the gap holds to 512k). The V4
layouts are unaffected.

## Modifications

Three files, all in the DSV4 attention kernels. `_load_v4` and `_combine` are
untouched, and no backend dispatch change is needed -- the gate lives entirely in
`can_use_swapab_attention`.

**`python/sglang/kernels/ops/attention/dsv4/decode_attention_sm100.py`**
- Replace the single `LAYOUT = KVLayout.V4` with `KV_LAYOUTS = (V4, V41, V41_FP4)`
  and add `_layout_of_bytes()`, which resolves a layout from a token row's width.
- `can_use_swapab_attention` now resolves the main and compressed caches from
  their own row widths and admits the pair through `is_valid_kv_layout_pair`,
  instead of the two hard-coded `== 584` checks.
- `swapab_attention` derives `DATA_BYTES` / `SCALE_BYTES` / `TILE` from the
  resolved layouts, and passes `IS_V41` / `IS_FP4` / `E_*` so each cache uses its
  own format.

**`python/sglang/kernels/ops/attention/dsv4/decode_attention_sm100_gluon.py`**
- Add `_load_v41`, the V4.1 page load. V41 is 512 e4m3 values with a ue8m0 scale
  per 32; V41_FP4 is the same 512 values as e2m1 two per byte with an e4m3 scale
  per 16. The fp4 branch upcasts with a single `gl.fp4_to_fp(packed, bf16, 1)`
  and lines the scales up with a `join`, so neither side needs a hand-written
  decode.
- `partial_gluon` dispatches each of its two loads (main K, compressed E) to
  `_load_v41` or `_load_v4` on `IS_V41` / `E_IS_V41`.

**`python/sglang/kernels/ops/attention/dsv4/swapab_gluon_hip.py`**
- Mirror the same dispatch: import `_load_v41` and branch the two loads. The V4.1
  page loads use only plain gluon, so the gfx950 kernel shares them.

## Accuracy

Kernel-level check against an fp64 reference (three layouts single-cache, three
mixed pairs double-cache; the test cache carries a 256 B in-page pad so a wrong
stride shows up): **6/6 pass, error ratio 1.00** on every case.

End-to-end, GSM8K (full test split, 8-shot) and RULER (13 tasks x 3 lengths):

| config | GSM8K | RULER 4k | 8k | 16k |
|---|---:|---:|---:|---:|
| V4 | 91.21% | 84.13 | 80.79 | 80.16 |
| V41-fp8 | 91.66% | 84.68 | 80.42 | 78.76 |

Both within the run-to-run spread of the V4 layout; no regression.

## Performance

4x B300 (sm_103), DeepSeek-V4.1-Flash, TP4/EP4, single request, median ITL (ms):

| length | baseline (no fast path) | V4 | V41-fp8 | V41-fp4 |
|---|---:|---:|---:|---:|
| 8k | 4.40 | 3.59 | 3.54 | 3.61 |
| 32k | - | 3.61 | 3.60 | 3.66 |
| 128k | 4.41 | 3.64 | 3.61 | 3.67 |
| 256k | 4.43 | 3.66 | 3.61 | 3.68 |
| 512k | 4.44 | 3.66 | 3.63 | 3.69 |

The three layouts land within 2.5% of each other; V41-fp8 is fastest and fp4
costs ~1-2%.

## Notes

- The change is against the current path structure; it does not touch
  `deepseek_v4_backend.py` -- `can_use_swapab_attention` already owns the gate.
- The fp4 e2m1 page is read as a packed row and widened with the backend's native
  `fp4_to_fp`; no host-side decode.
- Not covered here: `q.shape[0] > 8` still falls back to the generic FlashMLA
  path, as for V4.
