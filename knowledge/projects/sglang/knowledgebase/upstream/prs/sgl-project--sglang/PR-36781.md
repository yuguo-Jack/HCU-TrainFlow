# [PD] Release PP prefill responses before ring consensus

[Upstream PR](https://github.com/sgl-project/sglang/pull/36781) · state: closed · merged: False

## Original PR description

## Motivation

PP disaggregated prefill currently waits for the release ring to confirm that KV transfer has completed on every pipeline stage before returning the response. Since the ring advances once per scheduler body, a stage can finish its local transfer but still wait for a full pipeline traversal before responding.

```text
Before:

local KV transfer completes
        │
        └── release consensus: PP0 ──> PP1 ──> ... ──> PP7 ──> PP0
                                                               │
                                                               └── return response and release resources

After:

local KV transfer completes ──> return response
        │
        └── retain resources
                    │
                    └── existing release ring confirms all stages
                                      │
                                      └── release resources
```

Returning the response after local transfer completion is safe, but releasing resources locally is not. Different free-space values can make pipeline stages construct different batches. This change separates response completion from physical resource reclamation.

## Modifications

- Complete a prefill response when the local KV transfer reaches a terminal state.
- Keep KV pages, request slots, Mamba state slots, and metadata allocated until the existing release ring confirms completion across all pipeline stages.
- Continue reporting locally completed request IDs through the existing release ring without changing its communication order.
- Require every in-flight entry for the same request ID to be terminal before completing that request locally.
- Release retained resources after ring confirmation or an existing uniform failure.
- Reserve one running batch of additional prefill request and Mamba state slots for transfers that have left the running batch but still own resources.
- Keep the existing behavior as the default. Enable the new path with `SGLANG_PP_PD_LOCAL_RELEASE=1`.

The implementation adds no blocking wait, no collective, and no new PP point-to-point communication.

## A/B Test

The A/B test uses one PP8/TP1 prefill server and one TP8/DCP8 decode server. The image, model, nodes, request order, server arguments, router configuration, and benchmark parameters remain identical between arms.

The baseline was SGLang `main` with the pipeline-aligned admission path from [#36613](https://github.com/sgl-project/sglang/pull/36613). The treatment used the same baseline plus the local response-release path from this PR.

### A: admission PR with existing release-ring behavior

```bash
export SGLANG_PP_PD_ADMIT_FLOW=1
export SGLANG_PP_PD_LOCAL_RELEASE=0
```

The response and physical resources are released after the existing PP release ring reaches consensus.

### B: admission PR with local response completion

```bash
export SGLANG_PP_PD_ADMIT_FLOW=1
export SGLANG_PP_PD_LOCAL_RELEASE=1
```

The response is returned after the local KV transfer completes. Physical resources remain allocated until the existing release ring reaches consensus.

This PR does not require `SGLANG_PP_PD_ADMIT_FLOW` for correctness. The admission PR was enabled in this A/B test to hold the admission behavior constant and isolate the effect of local response completion.

### Benchmark command

The benchmark sends 128 requests with 32K input tokens, one output token, and concurrency 16 through the PD router:

```bash
python3 -m sglang.bench_serving \
  --backend sglang \
  --host <router-ip> \
  --port 30000 \
  --model Kimi-K3 \
  --tokenizer /data/models/Kimi-K3 \
  --dataset-name random \
  --random-input-len 32768 \
  --random-output-len 1 \
  --random-range-ratio 1.0 \
  --num-prompts 128 \
  --max-concurrency 16
```

A PP8 standalone server was measured with the same image, model, input length, output length, request count, concurrency, and pipeline depth to establish the non-disaggregated lower bound.

## Performance Results

| Configuration | Median TTFT | Input throughput |
|---|---:|---:|
| SGLang `main` + admission PR, existing release ring | 23.168s | 22,060 tok/s |
| Same baseline + local response release, repetition 1 | 21.039s | 23,954 tok/s |
| Same baseline + local response release, repetition 2 | 21.036s | 23,950 tok/s |
| PP8 standalone | 19.583s | 25,148 tok/s |
| Local response release versus release ring | −9.2% | +8.6% |

Local response completion removes approximately 2.13 seconds from median TTFT and closes most of the gap to standalone. The remaining gap is approximately 1.45 seconds.

These results show the incremental effect of this PR on top of the same admission baseline: both A and B enable [#36613](https://github.com/sgl-project/sglang/pull/36613), while only B enables `SGLANG_PP_PD_LOCAL_RELEASE`.

The table was collected with the equivalent feature before rebasing this PR onto the latest `main`. A clean-branch A/B rerun is in progress and the numbers will be updated before the PR is marked ready for review.

## Accuracy Tests

The accuracy tests used SGLang `main` with [#36613](https://github.com/sgl-project/sglang/pull/36613) and this local response-release path enabled.

- 6/6 deterministic arithmetic and retrieval checks passed.
- 16/16 long-context checks passed with actual prompt lengths between 31.2K and 31.5K tokens and needle positions covering the full prompt.
- GSM8K scored 39/40, or 97.5%, with no truncated responses, timeouts, or request errors.
- A 32K-input, 256-output-token workload completed 64/64 requests with 20.316s median TTFT, 31.73ms median TPOT, 28.403s median end-to-end latency, and 134.03 output tokens/s.
