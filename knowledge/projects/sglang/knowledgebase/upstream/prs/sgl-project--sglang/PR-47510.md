# [Perf] beam: Pack q/k/v/gate into one projection for FP8 checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/47510) · state: open · merged: False

## Original PR description

## Motivation

Beam's attention projects q/k/v and the output gate from the same hidden states. BF16 checkpoints already run that as one packed `qkv_gate_proj` GEMM. FP8 checkpoints run `qkv_proj` and `gate_proj` separately, so each layer quantizes the same input to FP8 twice and launches two small GEMMs. At decode sizes those calls are launch-bound, so the second pair costs about as much as the first.

FP8 is the only quantized Beam recipe on H200, and also a B300/GB300 recipe. Beam roadmap: #45370.

## Modifications

- `BeamAttention` builds the packed `qkv_gate_proj` with the quant config for FP8 checkpoints. FP8_DYNAMIC is per-channel weights plus per-token activations, so the four shards' weights and scales concatenate along N and one per-token quant feeds all of them.
- It packs only when the scheme targets the `Linear` class (as the Beam FP8 checkpoint does, so the packed name always resolves) and the ignore list leaves both `qkv_proj` and `gate_proj` quantized, the same check main runs for those two layers. Anything else keeps the split path, as do NVFP4 checkpoints, whose attention is BF16. Packing BF16 shards changes cuBLAS's kernel choice at small M on B300 (not bitwise equal to the split pair), so that can follow once it has an accuracy run. Replicated KV (attention TP > 8) is unchanged.
- `BeamForCausalLM.packed_modules_mapping` gets `qkv_gate_proj -> q/k/v/gate_proj`, so the quant config resolves the packed name through its checkpoint shards.
- Loading needs no change: `load_weights` already routes `self_attn.{q,k,v,gate}_proj.*` to `qkv_gate_proj` when that param exists, and `weight_scale` goes through the same per-shard loader as `weight`.
- New CPU test `test/registered/unit/models/test_beam_fp8_attention_packing.py`: FP8 weights and BF16 per-channel scales of q/k/v/gate land at TP8 rank 5's offsets of the packed layer through `load_weights` (fails on main), and ignore entries (fused `qkv_proj`, gate only, all four), name-only targets or NVFP4 keep the split path.

## Accuracy Tests

For FP8 checkpoints the packed projection returns exactly main's `cat(qkv_proj(x), gate_proj(x))`.

- Real weights, projection level: layers 0 (dense), 5 (full attention) and 6 (sliding) of `reflection/Beam-1.0-501B-A23B-FP8`, attention TP8 ranks 0 and 5 and TP1. Main's `BeamAttention` loads the real tensors through main's `load_weights`, the packed one through this branch's. After `process_weights_after_loading`, outputs are bitwise equal at M = 1, 8, 64, 640, 4096 in all 9 cases (1x H200).
- Real weights, end to end: the same checkpoint cut to its first 6 layers (3 dense and 3 MoE; sliding layers 0-4, full attention at layer 5), served at TP1 with `--attention-backend fa3 --page-size 64` from main, then this branch, then main again. 8 random-token prompts, 64 greedy tokens each, one request at a time: output ids and output logprobs are bitwise equal across all three servers (1x H200).
- Synthetic weights: bitwise equal at M = 1, 7, 64, 512, 4096 for all four shapes in the tables below.

## Speed Tests and Profiling

Kernel level. One call = one layer's attention input projection on one rank: per-token FP8 quant plus GEMM, twice on main, once here, built from the same SGLang linear classes and quant config the model uses. Each CUDA graph holds 16 layer copies with different weights, so weights come from HBM. 20 replays per point, the two arms alternate over 3 rounds, median. Up to M = 128 the rounds agree within 1%; at larger M they spread up to 10-15%, and the two arms' ranges overlap only at H200 attn TP1 M = 1024 and 2048. Per-rank shapes come from the cookbook FP8 recipes, K = 5120.

TP8 is the H200 low-latency recipe, TP4 the B300 one, attention TP1 the attention-DP high-throughput recipes. Against the bound (FP8 weight bytes plus BF16 input and output over 4.8 TB/s on H200, 8 TB/s on B300), small-M calls go from 12% to 21% on H200 TP8 and from 13% to 25% on B300 TP4. What's left there is the launch latency of one quant and one GEMM.

End to end on one H200: a dummy-weight server with one rank's shapes from the two H200 FP8 recipes (TP8: 6 Q heads and 1 KV head; attention DP8: 48 Q heads and 8 KV heads), expert width 320 and dense FFN 2560, all 52 layers and all 256 experts, `--attention-backend fa3 --page-size 64`, decode CUDA graph, uniform simulated routing. That is 7-11 us saved per layer on the TP8 shape and 5-8 us on the attention-DP shape, in line with the kernel table. The proxy has no collectives and uses main's MoE configs, so a real step is longer and the relative gain smaller. Prefill wall time (2048 and 8192 tokens) moves by less than the run-to-run spread on the TP8 shape and by -0.8% / -2.1% on the attention-DP shape.

Host side, one fewer linear call per layer: in eager mode the Python time of the input projections goes from 116 to 57 us per layer on the H200 host and from 47 to 23 us on the B300 host (M = 1-64).
