# [Fix] hisparse: Use host-backed logical capacity for request limits

[Upstream PR](https://github.com/sgl-project/sglang/pull/34345) · state: open · merged: False

## Original PR description

## Summary

HiSparse requests longer than the GPU KV pool can pass PD admission but still be clipped to zero output tokens by the worker and scheduler's request limits. For example, with 128 GPU token slots and 256 host-backed logical slots, a 192-token prompt requesting 10 new tokens is currently advertised a 127-token request limit and clipped to zero generation.

Use the existing `max_token_pool_size` for HiSparse when deriving `ModelRunner.logical_max_total_num_tokens`. The worker's request limits and scheduler's generation budget already consume this interface, so both now use the host-backed capacity. Preserve auxiliary-cache capacity limits and the existing non-HiSparse/DCP behavior.

This follows up #28753. The implementation has been updated for current main's logical-capacity and allocator-based generation-budget interfaces.

## Validation

- Added CPU regressions connecting the real runner properties, worker request limits, and scheduler generation budget. Cover input beyond the GPU pool, output clipping at the host boundary, auxiliary-cache limits, and non-HiSparse fallback.
- Ran an isolated source-method harness locally: five checks passed, including reproducing zero output on unmodified main and preserving 10 output tokens after the fix; the page-boundary sweep covers page sizes 1/4/16 and 269 input lengths each.
- Import sorting, repository-selected Ruff checks, Ruff formatting, Python compilation, and `git diff --check` passed.
- Full registered tests were not run locally: this macOS environment has no PyTorch installed. CI is still required.
