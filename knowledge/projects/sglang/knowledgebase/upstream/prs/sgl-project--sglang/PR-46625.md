# [Fix] kernel-plugins: Serve the MSA plugin behind --enable-nvidia-megakernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/46625) · state: closed · merged: True

## Original PR description

## Motivation

#45389 moved the monokernel registry to `sglang.kernels.plugin_kernels.amd.spec`, fixed its backend to `amd` and narrowed `--monokernel-backend` to `amd`. The MSA plugin, which serves MiniMax-M3.1 on NVIDIA Blackwell, registers its specs under `msa` through `sglang.srt.monokernels.spec`. On main the plugin therefore fails to load (`No module named 'sglang.srt.monokernels'`), and the MiniMax-M3.1 B300 / GB300 Low-Latency recipe, which passes `--monokernel-backend msa`, fails at argument parsing.

## Modifications

- `--enable-nvidia-megakernel` also serves the MSA plugin: a model whose architecture the plugin registers (MiniMax-M3 / M3.1 and their DSpark draft) runs through the monokernel binding, and every other model keeps the sgl-nvidia-mega path. The MSA repository needs no change.
- `--monokernel-backend amd|msa` stays as a deprecated alias of `--enable-amd-monokernel` and `--enable-nvidia-megakernel`, on the CLI and in config files, so the published recipes keep working.
- `sglang.srt.monokernels.spec` re-exports the contracts for the MSA plugin pinned by `MSA_COMMIT` in `docker/Dockerfile.cu134`, until the plugin imports the new path.

## Verification

- `test_mono_framework.py` and the monokernel cases of `test_server_args.py`: 22 passed.
- 4x B300, `MiniMaxAI/MiniMax-M3.1-Flash`, MSA at the Dockerfile pin (1e7bf76), the cookbook B300 Low-Latency recipe: an earlier revision of this change, which selected the same monokernel path under its own flag, logged `minimax_m3_msa_v1 on sm_103, widths [8]` and scored 0.955 on sgl-eval GSM8K (200 examples, temperature 1.0, top_p 0.95). The run with `--enable-nvidia-megakernel` and `--monokernel-backend msa` is in progress.
