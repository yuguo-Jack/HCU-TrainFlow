# [Fix] mla: Attend each draft step's own tokens on flashinfer_mla, flashmla and trtllm_mla

[Upstream PR](https://github.com/sgl-project/sglang/pull/46375) · state: open · merged: False

## Original PR description

## Motivation

An EAGLE chain draft writes step i's token at the committed length plus i, and `draft_forward` passes every step the same committed `seq_lens`. So each step of a multi-step draft backend has to read the committed prefix plus its own i + 1 draft tokens, as fa3 (`speculative_step_id`) and triton already do. Three MLA backends read fewer:

- FlashMLA and TRT-LLM MLA (and cutedsl_mla, which inherits from it) gave the kernel the committed length. FlashMLA's block table could also stop a page short.
- FlashInfer MLA's multi-step backend packs the right indices, but neither path planned them. The eager decode never passed the step its `spec_info`, so it packed and planned the committed prefix again. Graph replay planned host lengths and offsets from the committed `seq_lens_cpu`, so each request's window was short and every later request's segment started at the wrong place in the packed indices.

So every draft step left out its own token and the earlier steps' drafts. The target still verifies every draft token, so outputs stay valid; this corrects the draft's attention window. It does not raise acceptance: see Accuracy Tests.

## Modifications

- The draft step id now lives on the FlashInfer MLA backend, which the other three subclass, and their multi-step backends give each step backend its id.
- A draft step's decode adds its tokens to the key lengths, the scheduler metadata, the block-table width and FlashInfer's host plan; FlashInfer's eager step plans the indices its multi-step backend packed. This covers the eager path and CUDA graph replay, including the DCP replay of the TRT-LLM family. Other decodes are unchanged.
- FlashInfer MLA's multi-step draft backend now refuses decode context parallelism: its step backends plan the packed draft indices as built, global rather than sharded to the rank, so under DCP every draft step would read KV rows other ranks own (graph replay already did on main). The TRT-LLM family builds its rank-local draft metadata itself and is still admitted.
- Sail's multi-step draft backend is not changed: it creates its step backends without an id, so they behave as on main. Nothing here ran on Sail.

Files: `layers/attention/flashinfer_mla_backend.py`, `flashmla_backend.py`, `trtllm_mla_backend.py`, `cutedsl_mla_backend.py`.

Tests (the CUDA ones ran on SM90; each fails on main and passes with this PR):
- FlashMLA (CUDA), `test/registered/attention/unittests/mla/test_flashmla.py`: draft steps 0-2 match a reference attention over the committed prefix plus their own tokens, eagerly and from graph metadata, with prefixes around a page boundary.
- FlashInfer MLA (CUDA), `mla/test_flashinfer.py`: the same check through the multi-step backend's eager and graph metadata entry points, with three requests around a page boundary. The existing graph-runner check in that file (draft tokens from graph replay against eager), which fails on main for its FlashInfer MLA chain, passes now.
- TRT-LLM MLA and cutedsl_mla (CUDA), `test/registered/dcp/test_trtllm_mla_family_dcp_metadata.py`: the eager, graph and DCP graph metadata carry each step's lengths and pages.
- MLA draft admission under DCP (CPU): the draft factory refuses a flashinfer_mla draft before it allocates and still builds trtllm_mla and cutedsl_mla drafts.

To test the target directly, 120 of those questions, including all 12 from the first round, were replayed one at a time with logprobs. All 36,954 tokens, their logprobs and their top-2 alternatives are exactly equal between main and this PR, while the draft acceptance histograms differ on 119 of the 120.

Ling-3.0-flash-fp8's score is low on both builds and is not its accuracy at the recommended settings, which have thinking on. With thinking off, on main, 529 answers are at most 20 tokens and 65% right; the other 785 are 95.8% right.

**This PR lowers acceptance on Ling-3.1-flash, and why is not known.** Correctness here comes from the reference-attention tests above, not from acceptance. The fall repeats: the median in the scheduler logs goes from 2.69 to 2.64 on flashmla in both rounds, from 2.66 to 2.63 on flashinfer, and from 2.66-2.67 to 2.62-2.63 across four servers per build on flashinfer before upstream's unified-memory rewrite. fa3 and triton, which already read every draft key, measured 2.62-2.64 on this model on an older main (`76d5b3ce02`), so this PR moves both backends into their range.

The other two models show no clear change. Ling-2.6-flash's interval barely includes zero and has no repeat, so it is not a claimed gain. A fall under about 0.02 would not show in one pair. Ling-3.1-flash also ran at far fewer requests, so these runs do not separate the model from the load. All three models are one family; no other family has been measured.

### Not measured

- TRT-LLM MLA and cutedsl_mla need SM100 to serve and were not run as servers; only their metadata tests above ran, on SM90.
- FlashInfer MLA is the default MLA backend on SM100, and this change has not been served on SM100. On SM90 with CUDA 12.3 or newer the default is fa3, which this PR does not change.

## Speed Tests and Profiling

Not benchmarked: the decode kernels are unchanged; each draft step reads up to three more keys per request. Output throughput from the GSM8K runs above, which are not load tests:

- Ling-3.1-flash, flashmla: 486.8 and 485.9 tok/s on main, 479.3 and 479.4 with this PR, about -1.4%.
- Ling-3.1-flash, flashinfer: 478.3 -> 474.5 tok/s, -0.8%, one pair.
- Ling-3.0-flash-fp8, flashmla: 1380 -> 1383 tok/s, +0.2%, one pair.
- Ling-2.6-flash, flashmla: 2471 -> 2670 tok/s, one pair of runs under three minutes each, too short to read as a gain.
