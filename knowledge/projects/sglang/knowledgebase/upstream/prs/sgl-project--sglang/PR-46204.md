# [Apple] Add opt-in memory diagnostics and document the buffer cache cap

[Upstream PR](https://github.com/sgl-project/sglang/pull/46204) · state: open · merged: False

## Original PR description

## Motivation

On Apple Silicon the MLX scheduler's footprint grows under long prompts and concurrency bursts, and nothing shows which part is allocator cache and which is live allocations. On a 24 GB M4 Pro serving Qwen3 4B 4bit, one long prompt phase took the scheduler from 6.9 GB to 18.4 GB and drove 4.2M swapout pages. `SGLANG_MLX_CACHE_LIMIT_GB` already exists but is undocumented, and without allocator numbers there was no way to tell whether it would help.

This PR adds an opt-in log of MLX allocator state at request lifecycle points and documents the cache cap with measured results. Default behavior does not change.

## Modifications

| File | Change |
| --- | --- |
| `python/sglang/srt/environ.py` | Add `SGLANG_MLX_MEMORY_LOG` (bool, default false). |
| `python/sglang/srt/hardware_backend/mlx/model_runner.py` | Add `log_memory(event)`: active, cache, and peak memory, live requests, and idle request KV lists and bytes. Called at prefill and extend finalize, request release, and before and after the periodic `mx.clear_cache()`. At startup it also prints the cache limit in effect; returns at once when the flag is off. |
| `python/sglang/srt/hardware_backend/mlx/tp_worker.py` | Log once after the cache pools initialize (startup). |
| `test/registered/unit/hardware_backend/mlx/test_mlx_memory_log.py` | Flag off reads no allocator state and logs nothing; flag on logs each lifecycle point with all fields; release reports the parked KV list; the cache cap is set before model load, startup reports the effective limit and restores it; the cache cap is set before model load and rejected when negative. |
| `docs/docs/references/environment_variables.mdx` | Document `SGLANG_MLX_CACHE_LIMIT_GB` and `SGLANG_MLX_MEMORY_LOG`. |
| `docs/docs/hardware-platforms/apple_metal.mdx` | Add a Memory section with the measured effect of a 2 GB cap. |

Sample line:
```
MLX memory [release]: active=9.76 GiB, cache=1.82 GiB, peak=12.30 GiB, requests=1, idle_kv_lists=7, idle_kv=5.06 GiB
```

## Accuracy Tests

Same server and workload, temperature 0, with and without `SGLANG_MLX_CACHE_LIMIT_GB=2`: 138 of 138 sequential outputs match exactly between arms; the 8 burst outputs match as a set. Fixed probes are correct in every arm, before and after load.

Unit tests: the new file (6 tests) and the full `stage-a-unit-test-mlx` lane through `run_suite.py` pass locally (22 files, 264 tests).

## Speed Tests and Profiling

| Metric | No cap | Cap 2 GB |
| --- | --- | --- |
| MLX cache max | 10.06 GiB | 2.05 GiB |
| MLX active max | 10.19 GiB | 10.88 GiB |
| Peak scheduler footprint | 18.4 GB | 14.3 GB |
| Footprint after burst and idle | 18.4 GB | 14.3 GB |
| Swapouts during long prompts (16 KB pages) | 4,227,218 | 278,936 |
| Small p50 / p95, S1 | 445 / 472 ms | 443 / 463 ms |
| Small p50 / p95, S2 | 499 / 511 ms | 558 / 636 ms |
| 4K prompt p50 | 8348 ms | 7583 ms |
| 6K prompt p50 / max | 14008 / 255400 ms | 12880 / 14773 ms |
| 8 x 2K burst p50 / max | 29369 / 36527 ms | 22018 / 29343 ms |
| Errors | 0 | 0 |

Diagnostics overhead: small request p50 is 448 ms with the flag off and 445 ms with it on.
Under memory pressure the cap mostly removes thrash; S2 in the capped arm was 12% slower at p50; phase also had more host page ins, which I have not separated.

## Known Limitations

* The cap bounds only the cache. About 5.06 GiB of active memory after the burst was idle request KV lists kept by `_release_cache`, which upstream keeps without a bound. Separate change.
* One machine, one model, one run per arm; run back to back.
* The log runs at INFO on every prefill and release when enabled; it is meant for local diagnosis, not production.
* #41209 proposes a default cap; this PR makes no claim about the unset case and rebases cleanly either way.
