# [Fix] Preserve large integer tool arguments in Qwen3 Coder

[Upstream PR](https://github.com/sgl-project/sglang/pull/42050) · state: closed · merged: False

## Original PR description

## Motivation

For a tool parameter with JSON Schema `type: "number"`, Qwen3 Coder converts an integer literal through `float` before returning an integer. This silently changes values above 2^53: `9007199254740993` becomes `9007199254740992`. The same path serves `step3p5` and `nanbeige`, including streaming responses, so large IDs and nanosecond timestamps can reach tools with the wrong value.

## Modifications

Try exact integer conversion before the existing float conversion for literals without a decimal point or exponent. Keep the existing float fallback and decimal/exponent behavior.

Add CPU tests through `FunctionCallParser` for all three aliases, unary and chunked streaming, large positive/negative integers, a nanosecond timestamp, nullable number schemas, and ordinary numeric/string/integer controls.

## Accuracy Tests

- New regressions: 72 failing subcases on the original code; all 4 test methods and 156 subcases pass after the fix.
- Existing Qwen3 Coder tests plus new tests: 21 passed.
- Broader existing parser module: 235 passed; 15 DeepSeek V3.2/V4 tests cannot initialize their tokenizer fixtures on this CPU-only environment because `triton` is unavailable.
- Touched-file pre-commit checks passed, including CPU CI registration.

Local tests load the actual parser, protocol and test modules while excluding SGLang's GPU-facing package initializers. No parser implementation is replaced. No GPU/model-output benchmark was run.

## Speed Tests and Profiling

No inference performance claim; this changes numeric argument fidelity.
