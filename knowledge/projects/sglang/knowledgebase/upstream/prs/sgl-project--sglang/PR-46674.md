# [Perf] radix-tree: Keep the GIL for tree-core flag, size and digest reads unless the core is busy

[Upstream PR](https://github.com/sgl-project/sglang/pull/46674) · state: closed · merged: True

## Original PR description

## Motivation

The Python bindings of the Rust tree core (`rust/sglang-radix-tree/src/python_bindings.rs`) released the GIL around every O(1) read the radix cache makes on its scheduler-step paths: the tier config flags (`enable_hicache`, `enable_storage`, `has_swa_host_pool`, `is_write_back`, `write_through_threshold`, `is_host_memory_buffer_only`, `enable_external_cache_linker`), the evictable/protected size counters, `has_ongoing_insert` and the write-back coexist reclaim digest. Each is a single field load under the core mutex, but `py.detach` hands the GIL to any waiting Python thread, so the reader can stall for up to a switch interval (5 ms by default) before it gets the GIL back. The cache reads these per scheduler step, per insert and once per evicted leaf, so next to a busy Python thread the stalls add up.

## Modifications

These 15 getters now lock the core through a new `core_attached(py)` helper built on `pyo3::sync::MutexExt::lock_py_attached`: it takes the lock while still attached to the interpreter when the core is free, and only detaches to block when another thread holds the core. Waiting with the GIL held would not be safe: a native call that holds the core can drop tensors Python still references, and libtorch needs the GIL to release their Python objects, so a `reset()` racing a flag read would deadlock.

Setters, `total_size`, the per-node reads and every other binding method still release the GIL around native work. Return values and the Python adapters are unchanged.
