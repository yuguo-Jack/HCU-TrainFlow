# [Fix] true-on-policy: Cast Qwen2/Qwen3 dense inputs to params_dtype, not the quantized weight dtype

[Upstream PR](https://github.com/sgl-project/sglang/pull/45441) · state: open · merged: False

## Original PR description

## Problem

`[1/42]` (true on-policy) made `Qwen3Attention.forward` and `Qwen2MLP.forward` cast their input to the
projection's weight dtype:

```python
if should_force_bfloat16_dense_tensor_math() or hidden_states.dtype != self.qkv_proj.weight.dtype:
    hidden_states = hidden_states.to(self.qkv_proj.weight.dtype)
```

For a quantized layer the stored weight is not in the activation dtype (FP8 is `float8_e4m3fn`). The bf16
activations are cast to FP8 with no scale before `qkv_proj` and `gate_up_proj`, and the FP8 linear method then
receives an FP8 input with `input_scale=None`. Block-wise and per-tensor FP8 Qwen2/Qwen3 dense models fail during
decode graph capture:

```python
import sglang as sgl
sgl.Engine(model_path="Qwen/Qwen3-4B", quantization="fp8")
# AssertionError: assert input_scale is not None ...   (fp8_utils.apply_fp8_linear)
sgl.Engine(model_path="Qwen/Qwen3-4B-FP8")              # block-wise FP8, ROCm gfx950
# [AITER] quant_kernels.cu:795 dynamic_per_group_scaled_quant_kernel not implemented for dtype fp8
# Fatal Python error: Aborted
```

MXFP8 does not crash, because the gfx950 MXFP8 GEMM re-quantizes its input. But every activation first goes
through a scale-1 E4M3 cast. In a 3-step miles GRPO A/B with unified MXFP8 (Qwen3-4B, 2x MI350X, same seeds, only
`qwen2.py`/`qwen3.py` differing), the mean train/rollout log-prob abs diff is 0.054 without this change and 0.037
with it.

`main` is not affected: it still casts with `.bfloat16()`.

## Change

Compare and cast against the projection's `params_dtype`, the model's activation dtype, which is what the
true-on-policy cast is meant to restore. For unquantized layers `params_dtype == weight.dtype`, so nothing
changes. The dtype is captured in `__init__` because the LoRA wrapper that later replaces `qkv_proj` /
`gate_up_proj` does not expose `params_dtype`.

Happy to have this folded into `[1/42]` at the next rebase instead.

## Testing

`sglang-miles` at 92fec6958d vs this branch, MI350X, TP1, `sgl.Engine(..., mem_fraction_static=0.6)`, greedy,
4 prompts x 64 new tokens. The ROCm image's sgl-kernel predates the fp32 rotary cache, so both trees cast
`cos_sin_cache` to the query dtype on HIP to run:

| Model / args | Before | After |
|---|---|---|
| `Qwen/Qwen3-4B-FP8` | aborts in graph capture | ok |
| `Qwen/Qwen3-4B`, `quantization="fp8"` | AssertionError in graph capture | ok |
| `Qwen/Qwen2.5-0.5B-Instruct`, `quantization="fp8"` | AssertionError in graph capture | ok |
| `Qwen/Qwen3-4B` | ok | identical output |
| `Qwen/Qwen3-4B`, `true_on_policy_contract="qwen3_dense_true_on_policy_v1"`, `rl_on_policy_target="fsdp"`, `attention_backend="triton"` | ok | identical output |
| `Qwen/Qwen3-4B`, `enable_lora=True`, `max_lora_rank=16`, `lora_target_modules=["qkv_proj","o_proj","gate_up_proj","down_proj"]` | ok | identical output |
| MXFP8 Qwen3-4B | ok | ok (outputs change, see above) |

On an Oct 14 `sglang-miles` build with the same two-file change, GSM8K (250 test questions, greedy, 768 new
tokens): BF16 92.0% -> 92.0%, block FP8 aborts -> 92.4%, MXFP8 92.4% -> 92.4%.

Not run on CUDA. The `quantization="fp8"` assertion is in platform-independent code.
