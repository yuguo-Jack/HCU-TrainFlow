# [Fix] scheduler: Exclude accepted storage-tier hits from the waiting prefill load

[Upstream PR](https://github.com/sgl-project/sglang/pull/45158) · state: open · merged: False

## Original PR description

## Motivation

`SchedulerLoadInquirer.get_num_waiting_uncached_tokens` is the prefill-load figure behind `LoadSnapshot.num_waiting_uncached_tokens`, which feeds DP balancing and `/v1/loads`. With per-request prefix matching on, it counts `seqlen - num_matched_prefix_tokens` for every waiting request. That matched length only covers the device and host tiers at match time. A waiting request whose prefix is being fetched from the storage tier through the buffer pipeline still has those tokens counted as work to prefill, although the scheduler will never run them: the prefetch was accepted for exactly that span, and the staged hold keeps it until admission. A rank that is absorbing storage hits therefore reports more prefill load than it will do, and the balancer steers traffic away from the rank that is about to serve cheaply.

## Modifications

- `BasePrefixCache.waiting_storage_span(request)` (`python/sglang/srt/mem_cache/base_prefix_cache.py`): new hook returning the expected storage-hit span of a waiting request as logical token offsets, `None` by default so caches without a storage tier are unchanged.
- `UnifiedRadixCache.waiting_storage_span` (`python/sglang/srt/mem_cache/unified_radix_cache.py`): in buffer mode, an ongoing prefetch that the scheduler has accepted (host indices assigned) reports the accepted logical span `[storage_start, storage_start + storage_hit_count)`, independent of how far the worker has progressed; a completed prefetch held in `staged_prefetches` reports `[matched_len, matched_len + num_tokens)`. A prefetch whose result is still awaiting acceptance, a released hold, and resident mode all report `None`.
- `SchedulerLoadInquirer` (`python/sglang/srt/managers/scheduler_components/load_inquirer.py`): optional `get_waiting_storage_span` provider. With per-request matching, the overlap between the reported span and the uncached suffix `[matched, seqlen)` is subtracted, clipped so a span inside the matched prefix or beyond the prompt removes nothing. The historical hit-rate path is untouched because the measured hit rate already includes admitted storage hits. `Scheduler.init_load_inquirer` wires `tree_cache.waiting_storage_span`.
