# [Feat] lora: Dense LoRA runner and the triton_v2 backend (06/21)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42873) · state: open · merged: False

## Original PR description

Part 06 of 21 of the LoRA runtime stack (branch `lora-stack-05-dense-runner`, base `lora-stack-04-dense-tables`). The stack is cut from the development branch of #42284.

## What this part adds

Add DenseLoraRunner (plan-driven A/B execution, split-K, base/LoRA overlap
on the workspace side stream) and the triton_v2 backend that drives it, and
wire the dense layers through BaseLoRABackend.forward_with_base: embedding,
lm_head, column/row/replicated projections. A dense layer stays on the base
path for a batch with no active adapter except while an adapter-capable graph
is captured. LoRAManager validates replicated-Q targets after the backend's
own target check, clears the route cache at capture boundaries, and reads DSA
indexer fusion from the model's indexers. Server args reject triton_v2 with
attention DP, PD-multiplexing, two-batch overlap, SGLANG_EXPERIMENTAL_LORA_OPTI
and ROCm.

Tests: dense backend and runner numerics (the 47-case bitwise fixture), the
runner's architecture resolution, inactive-batch rules under capture,
forward_with_base ordering, target validation, server-arg guards.
