# [Fix] scheduler: Keep long prefill steps in the busy counter and exclude engine pauses

[Upstream PR](https://github.com/sgl-project/sglang/pull/46127) · state: closed · merged: True

## Original PR description

## Motivation

`Scheduler._record_step_counters` maintains `total_prefill_busy_us` and `total_prefill_uncached_tokens`. Both are published in the engine's load reports, and the router uses their deltas to estimate prefill throughput (uncached tokens per busy second) and, from that, the queue time of the waiting uncached tokens. Today any prefill step whose duration reaches `STEP_MAX_US` (2 s) contributes neither busy time nor uncached tokens, so both cumulative counters omit that work. With long prompts or large chunk sizes a single prefill step can exceed 2 s, and then the busy time an engine reports can be a small fraction of the time it actually spent in prefill forwards, while the throughput estimate is taken from the short steps only.

The cap dates from launch-to-launch prefill timing, where a long gap could be idle time. Prefill steps are now charged from the batch launch, or from the previous prefill's result when the two are back to back, to this step's result, and every idle loop iteration sets `_sched_idled`, which breaks the back-to-back chain. Idle time is therefore already excluded, and the cap only discards real work.

One wait skipped that idle flag: a paused engine. While `_engine_paused` is set the disaggregation prefill loops `continue` before setting `_sched_idled`, and the overlap loop holds an in-flight prefill result until resume. Without the cap, the first prefill after a pause would be charged the whole pause (in the unit test, two 0.125 s prefills around a pause of about 10 s would count about 10.25 s).

## Modifications

- Prefill steps are no longer discarded at `STEP_MAX_US`. The cap still applies to decode and target-verify launch cadence, where a gap that long is a stall and not a cadence sample.
- The scheduler records pause windows, from `pause_generation` to `continue_generation`, and subtracts their overlap from each prefill step, so a pause never counts as busy time:
  - An in-place pause starts its window at the call. A first retract starts its window only after the in-flight result has drained, because draining waits for that forward to finish. A repeated pause keeps the first start.
  - A result processed while the pause is still open (an in-place pause followed by a retract drains the held result before resume) excludes the pause so far.
  - Later prefill steps start at or after the previous step's end, so a closed window is dropped once a recorded step ends after it. `PAUSE_WINDOWS_MAX` (1024) bounds the deque; it would only lose a needed window if more than 1024 pauses happened inside one prefill step.
- Nothing else changes: where prefill steps start and end, the decode cadence cap, the load reports and the router's use of them are untouched.
- Tests: `test_disagg_idle_step_counters.py` gains cases for a long prefill step being charged while a long decode gap is not, a pause between prefills, a result held across a pause, a result processed during an open pause, many pauses inside one step, a pause inside an idle gap, and a repeated pause keeping one window. `test_scheduler_pause_generation.py` checks when a retract starts its window. The two unit-test scheduler stubs gain the new attributes.
