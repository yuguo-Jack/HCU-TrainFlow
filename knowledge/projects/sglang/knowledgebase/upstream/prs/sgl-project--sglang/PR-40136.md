# [Feat] [NPU] domino: Add BF16 GRU fallback for NPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/40136) · state: open · merged: False

## Original PR description

## Motivation

Ascend NPU's `DynamicGRU(V2)` TBE kernel rejects BF16 `weight_hidden`, while the Domino runtime runs in bfloat16. On NPU this makes both `aten::gru_cell` (the feedback-token GRU step) and `nn.GRU` (the prefix projection) fail at the operator level, so DFLASH Domino cannot run on Ascend.

## Modifications

- Add `_gru_cell_manual`, an explicit single-layer GRU cell built from `F.linear` + `sigmoid`/`tanh` with fp32 gate math (for parity with CUDA numerics), casting the result back to the input dtype.
- In `_domino_gru_cell`, fall back to `_gru_cell_manual` on non-CUDA devices instead of `torch.ops.aten.gru_cell.default`.
- In `domino_greedy_rollout`, run the two prefix GRU steps manually on non-CUDA devices instead of `nn.GRU`.
- Allow `npu` through `validate_domino_runtime` (previously only `cuda`).

CUDA behavior is unchanged: every new code path is gated behind `device.type != "cuda"`.

## Accuracy Tests

N/A for CUDA (path unchanged). On NPU, validated by the DFLASH Domino e2e tests (`test_npu_dflash_domino.py`)https://github.com/sgl-project/sglang/pull/43045, which pass.

## Speed Tests and Profiling

N/A. This is a correctness/portability fix — the GRU was previously non-functional on NPU. The replacement uses basic ops on a per-token GRU step inside the proposal loop, with negligible end-to-end impact, and the CUDA path is untouched.
