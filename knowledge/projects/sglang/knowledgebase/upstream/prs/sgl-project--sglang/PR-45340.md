# [Feat] Inkling: render and parse chat via tml-renderers

[Upstream PR](https://github.com/sgl-project/sglang/pull/45340) · state: closed · merged: True

## Original PR description

## Motivation

Stacked on #45300 (merged): the chat-encoding adapter registry landed there; this PR is the tml-renderers integration on top of it.

Inkling's chat wire format (TMLv0: message framing, tool declarations, tool calls, thinking blocks, effort, multimodal placeholders) was hand-reimplemented in sglang on both the prompt and output sides. Thinking Machines publishes the reference implementation as [`tml-renderers`](https://tinker-docs.thinkingmachines.ai/cookbook/inkling/tml-renderers/). This PR delegates both directions to that library, so sglang matches the model's training format by construction. Constrained-output framing is a separate fix, merged as #44716.

## Modifications

**Prompt rendering** (`parser/inkling_renderer.py`): OpenAI messages go through `tml_renderers.chat.OpenAIMessage` and `v0.Renderer`. sglang still owns the `tool_declare` message, the media placeholder IDs the MM processor expands, and the open text block for `continue_final_message`.

**Output parsing** (`parser/inkling_output.py` + `entrypoints/openai/serving_inkling.py`): responses are parsed incrementally from output token IDs with `v0.Parser`, so control tokens are recognized by ID only. Stops are cut in the raw sampled stream; a `max_tokens`-cut message surfaces its payload; stream and non-stream share one parser. Tool-call arguments are rebuilt from the sampled payload with Python `json` (key order, UTF-8 and large integers survive).

**Registry integration**: the Inkling adapter registered in #45300 swaps its legacy inline implementation for this delegation. Chat and Responses take prompt encoding, output parsing and history/media handling from the adapter; other specs keep their existing paths.

**Responses and Anthropic APIs**: Responses items (reasoning, message, `function_call`) parse from token IDs with the same parser. Anthropic Messages reuses the chat path, so `thinking` / `text` / `tool_use` blocks and `stop_reason` come from it. On both, prior reasoning renders as `{"type": "thinking"}` content parts; tool results get their name from the matching `tool_call_id`.

**Dependency**: `pyproject.toml` adds `tml-renderers==0.1.0` for linux x86_64/aarch64 and macOS arm64 (Apache-2.0, cp311-abi3 wheels only, no sdist). Serving Inkling without it fails at startup with an install hint. `--reasoning-parser inkling` and `--tool-call-parser` must each be `inkling` or unset. Startup compares all Inkling control-token IDs and one ordinary-text probe against the served tokenizer.

**Removed**: the hand-written TMLv0 tokenizer and renderer.

### Behavior changes

- A tool result without `name` is now named from `tool_call_id` (main's rule); an unknown id stays empty.
- A top-level `reasoning_content` on assistant history renders as a thinking part on every API.
- With tools and a system prompt, the order is now `system → tool_declare → effort`.
- Control tokens are recognized by token ID only; a literal marker spelling stays text.
- A malformed or truncated tool call surfaces as content text instead of being dropped or half-parsed.
- Audio input is rejected (400) outside user messages, as the library does.

### Known scope limits

- `/parse_function_call` and `/separate_reasoning` take text, so they keep the string detectors. So does the Responses built-in tool loop.
- Responses streaming emits a step's text before that step's tool calls when both land in one engine step.
- `usage.reasoning_tokens` counts up to the first `<|end_message|>`, so a response that skips thinking reports its first message as reasoning tokens.
- Non-16 kHz audio is not compared against the library (it resamples through `librosa`); at 16 kHz sglang's DMel is bit-exact.
- The Rust frontend still renders Inkling through its native formatter; aligning it is a follow-up.
- `/v1/messages` `thinking.display` accepts only `summarized`/`omitted` on `main`, while Claude Code sends `updates` — model-independent, needs its own small fix.

## Speed Tests and Profiling

`sglang.bench_serving`, random 1024/1024, 256 prompts, concurrency 64, `--flush-cache`, 4x GB300: output tok/s 3108/3127 vs baseline 3103/3125; median TPOT 19.33/19.29 ms vs 19.33/19.26 ms. Prompt rendering costs 0.17 ms per request, versus 1.59 ms for the previous HF-template encode.
