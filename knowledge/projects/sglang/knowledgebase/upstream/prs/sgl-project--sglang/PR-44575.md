# [Perf] multimodal: Copy features into shared memory off the event loop

[Upstream PR](https://github.com/sgl-project/sglang/pull/44575) · state: open · merged: False

## Original PR description

_Posted by Kunal's robot (Claude Opus 5.5) ↓_
>
> ## Motivation
>
> `wrap_shm_features()` copies each decoded feature tensor into a POSIX shared-memory segment. It runs on the tokenizer manager's event loop, so a request with several large images holds the loop, and `/health` with it, for the length of the copy.
>
> ```
> before:  loop  [tokenize][===== shm copy =====][send]
> after:   loop  [tokenize]  ...serves others...  [send]
>          pool             [===== shm copy =====]
> ```
>
> ## Modifications
>
> - Run the copy in the default executor, the same way the CUDA VMM transport already publishes features.
> - Unlink the segments if the request is cancelled mid-copy. The unlink hangs on the copy future as a done callback, as the VMM path does, so a second cancellation while the task waits for the copy (a client disconnect cancels through the server's cancel scope) cannot skip it.
> - The copy is one more await before dispatch, so a request aborted during it is dropped and its segments released, the way the abort check after the other awaits drops one (#47546).
> - Any exit from `_send_one_request` before dispatch, a cancellation during the copy included, returns the CUDA IPC leases preprocessing took, since no consumer will acknowledge them.
> - Add five tests to `test_gpu_feature_transport.py`: the loop stays responsive during the copy, cancellation unlinks the segments, a second cancellation still unlinks them, an abort during the copy skips dispatch and unlinks them, and a cancellation during the copy returns the CUDA IPC leases. The last three fail without the matching change.
>
> This PR is independent of #44574 and #44576, which address the same workload.
>
> ## Accuracy Tests
>
> Not applicable: the copied bytes are unchanged.
>
> ## Speed Tests and Profiling
>
> The tensor copy releases the GIL. Copying 40 MB left a 1.4 ms worst-case event-loop gap from a worker thread, against 12 ms on the loop.

When a request is cancelled a second time while the executor is still copying (for example, task cancellation followed by loop shutdown), this unshielded `await future` is interrupted and cancels only the asyncio wrapper; the already-running worker still returns a tokenized object containing named `ShmPointerMMData` segments, but `discard_shm_features` is never called. Those segments deliberately are not unlinked by `__del__`, so repeated cases can fill `/dev/shm` until process exit. Attach cleanup as a done callback or otherwise make it survive subsequent cancellation, as the CUDA VMM publication path does.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Release CUDA IPC leases on cancelled SHM wrapping**

When `--mm-feature-transport=cuda_ipc` is enabled and a client disconnects while this executor job is pending, preprocessing has already replaced GPU tensors with `CudaIpcTensorTransportProxy` leases, but this handler only schedules `discard_shm_features`, which ignores those proxies. `_send_one_request`'s `finally` only cancels VMM and positional transports, and because the scheduler never receives this request no consumer acknowledges the CUDA IPC leases; repeated cancellations therefore permanently occupy the bounded pool and force later requests onto the CPU fallback. Call `_cancel_cuda_ipc_features((tokenized_obj,))` on this cancellation path as the abort path does.
