# [Fix] function_call: Keep every Qwen 2.5 tool call and its arguments at end of stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/41039) · state: open · merged: False

## Original PR description

## Motivation

`Qwen25Detector.parse_streaming_increment` delegates to the base implementation,
which emits at most one unit per increment: a tool name with empty parameters, then
that call's argument diff, then the next call. Whatever a delta leaves pending is
normally picked up by the following delta -- but the detector never overrode
`finish()`, whose documented contract is to release what is still held when the
stream ends, so a delta carrying whole calls loses everything after the first unit.

With four calls in one response, the same input degrades as the delta grows:

```
chunk size  13 -> 4 calls, all arguments present
chunk size  87 -> 3 calls
chunk size 128 -> 3 calls, the last with EMPTY arguments
chunk size 152 -> 2 calls
chunk size 517 -> 1 call with EMPTY arguments      (one delta for the whole response)

detect_and_parse for the same text: 4 calls, all arguments present
```

and for a single call whose whole body lands in the final delta:

```
streamed arguments: ""      <- unusable tool call
expected          : {"city": "NYC", "state": "NY", "unit": "celsius"}
```

This is reachable whenever a call completes inside one delta -- multi-token deltas
from speculative decoding / MTP, `stream_interval > 1`, or a call short enough to
be generated in one step -- and it is worse than a display bug: the client receives
a tool call it cannot dispatch, or never learns about calls the model made.

## Modifications

`python/sglang/srt/function_call/qwen25_detector.py` (+39):

- `finish()` re-runs the parser with an empty delta until a round yields neither
  calls nor text, releasing the pending queue. This follows the pattern
  `GigaChat35Detector.finish()` already uses.
- Text the detector held back because a partial end token could still arrive is
  released as well: the stream is over, so it never will. `</tool_call>` is
  stripped from it, since that token is framing rather than content.

`test/registered/unit/function_call/test_function_call_parser.py` (+91): three
cases in `TestQwen25Detector`, parametrized over the chunk sizes above; two of them
fail on `main`.

## Scope: what this deliberately does not change

- **Text preceding a call is still dropped when the call shares its delta** (for the
  single-call example above, at 48 characters per delta the client sees no prose).
  That happens inside the shared `BaseFormatDetector.parse_streaming_increment`
  path, which stops emitting text as soon as the buffer contains a marker, so it
  affects every detector that delegates there rather than being a Qwen-specific
  bug. #35625 targets that shared path and should own it.
- The non-streaming path numbers every call `tool_index = 0`; streaming numbers
  them 0, 1, 2, 3. That asymmetry is not part of this fix and the regression tests
  compare `(name, arguments)` so they do not depend on it either way.

**Reviewer note — why the drain sits in `finish()` and not in the base class.**

There is an open base-class fix for part of this defect class (#32167, "Fix streaming tool calls losing arguments when completed in the final delta"). It does not cover this detector, and the reason is worth recording before anyone has to ask:

- The shared flush path is `FunctionCallParser.parse_stream_end()` -> `detector.finish()`, and **both** streaming entrypoints call it (`serving_chat.py:3030`, `serving_responses.py:2399`). The flush that #32167 extends, `_check_for_unstreamed_tool_args`, exists only in `serving_chat.py` (defined at 3115, used at 945); `serving_responses.py` has no equivalent.
- `BaseFormatDetector.parse_streaming_increment` processes exactly **one** JSON object per call — there is no loop between the `bot_token` search and the Case 1 / Case 2 returns. A delta carrying several complete calls therefore leaves the rest buffered, and registering the single object that was parsed does not recover them; the drain here re-runs the parser until it yields nothing, which does.
- `Qwen25Detector.parse_streaming_increment` calls `super().parse_streaming_increment(...)` and then post-processes the result, so the parse is shared but the one-unit-per-increment limit is not lifted: the four-calls-in-one-delta case in the description still needs the drain.
