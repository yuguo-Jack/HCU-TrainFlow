# [Fix] sgl-kernel: Support arbitrary expert counts in no-copy-engine transfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/32769) · state: open · merged: False

## Original PR description

## Motivation

Fixes #32507.

CPU OffloaderV2's CPU mode requires the DeepEP expert-count vector to reach
the GPU without using a copy engine. `copy_to_gpu_no_ce` only instantiated
N=32, 64, and 72, so a valid 256-expert/EP16 configuration produced N=16 and
failed during prefill warmup with `RuntimeError: unexpected N`.

This is the same fixed-shape failure class previously addressed for N=32 in
#23550.

## Modifications

- Add an exact N=16 specialization for the reported configuration.
- Preserve the existing compact N=32/64/72 launch paths.
- Add a bounded, by-value fallback for other sizes up to 512, without using a
  copy engine.
- Validate empty and oversized inputs with descriptive errors.
- Cover N=16, a previously unsupported N=17, existing specializations, the
  N=512 boundary, and N=513 rejection.

Compared with the always-generic approach in #32515, the hybrid dispatch keeps
small launch arguments for common expert counts while remaining robust to new
counts.

## Accuracy Tests

The modified CUDA source was compiled and exercised directly on an NVIDIA L40S
with CUDA 12.8 and PyTorch 2.10:

```text
correctness: PASS
sizes: 16, 17, 32, 64, 72, 512
oversized input rejection: 513 PASS
```

The operation is an exact `int32` control-vector copy; it does not alter model
arithmetic.

Local static checks:

```text
python -m py_compile python/sglang/kernels/aot/tests/test_copy.py
clang-format --dry-run --Werror python/sglang/kernels/aot/csrc/elementwise/copy.cu
git diff --check
```

## Speed Tests and Profiling

NVIDIA L40S, CUDA 12.8, PyTorch 2.10, median of 7 repetitions with 20,000
operations per repetition:

| N=16 path | Latency |
| --- | ---: |
| Hybrid exact specialization | 1.831 us |
| Generic MAX_N=512 kernel (#32515 approach) | 1.981 us |
| Pinned-memory H2D copy | 3.477 us |

The exact specialization was 7.6% lower latency than always passing the
512-element generic argument and 47.3% lower latency than the copy-engine
fallback in this microbenchmark.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Launch the fallback on the output tensor's device**

When `output` is on a CUDA device other than the current device, which the input checks currently permit, a fallback-size call such as N=17 obtains the current device's stream and launches there while passing a pointer owned by `output.device()`. This can fail with an invalid-device-pointer error or, when peer access is enabled, perform an unordered cross-device write. Guard `output.device()` before retrieving the stream and launching the kernel.
