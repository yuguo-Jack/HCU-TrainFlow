# [AMD] Keep speculative overlap scheduling on the forward stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/42279) · state: open · merged: False

## Original PR description

Split from #41994 as requested in review: the batch < 64 part. The other parts are #42280 (`MinFreeSlotsDelayer`) and #42281 (DSpark verify width).

## Motivation

With overlap scheduling and speculative decoding on HIP, `FutureMap.resolve_seq_lens_cpu` and `resolve_mixed_spec_tails` block the host on the previous forward's publish event (`publish_ready.synchronize()`, #26672), so the GPU idles between the DSpark verify and the next draft. Event-timed on DeepSeek-V4.1-Flash on MI355X (on the DeepSeek-V4.1 AMD development branch), that idle was 0.65 ms of an 8.9 ms batch-1 cycle.

The host sync exists because `Event.wait()` on the separate schedule stream is slower still: a device wait pending in another HIP queue while a graph runs slows every dispatch of that graph (on MI355X a 512-kernel graph takes 1541 us instead of 853 us with such a wait pending). In the same timing, replacing the sync with that wait alone removed 0.50 ms of the idle but made the verify graph 1.21 ms slower.

`needs_cpu_seq_lens` does not reach this sync. The DeepSeek-V4.1 HIP backend already sets it to False on main (#41308 derives it from `SGLANG_OPT_USE_ONLINE_COMPRESS`, off by default). On the Low-Latency DSpark cell on main `dcf4e18283`, a print-only probe shows `needs_cpu_seq_lens=False` for both the target and the draft `DeepseekV4HipRadixBackend`, and `resolve_seq_lens_cpu` taking the host `synchronize()` with no seq_lens D2H: on HIP the sync runs before the flag is checked. The probed files are unchanged on current main.

## Modifications

On HIP with overlap scheduling, speculative decoding and no pipeline parallelism, the scheduler runs on the forward stream (`Scheduler.schedule_on_forward_stream`, decided once in `init_overlap`), and `FutureMap(same_queue_publish=True)` waits on the publish event in-queue with `Event.wait()` instead of blocking the host. Stream order carries the forward-to-schedule dependencies. Without speculation there is no publish wait, so the separate schedule stream stays. CUDA is unchanged; on HIP this applies to every speculative algorithm.

## Accuracy Tests

- Batch 1, 64 fixed GSM8K questions and 8 retrieval probes per server: every server scored 62/64 and 8/8 in both arms on main `dcf4e18283` (61-63/64 and 8/8 in an earlier session on main `a702970ecb`). Every Low-Latency server scored 63/64.
- Because this covers every speculative algorithm on HIP, the speculative AMD CI tests ran locally on MI355X with `scripts/ci/amd` and the `rocm/sgl-dev:v0.5.20-rocm10-mi35x-20260930` image, on #41994's tree: `test_basic_sanity_eagle3`, `test_dflash`, `test_eagle_dp_attention` (4 GPUs), `test_frozen_kv_mtp`, `test_spec_standalone_extra`, `test_eagle_worker_v2_topk1_fastpath`, `test_build_eagle_tree` and `test_resolve_swa_kv_pool` pass. `test_adaptive_speculative` is flaky on main as well: it passed 11 of 12 runs there and 10 of 11 on main, and both failures were the same `Never downshifted` check. `mock_model/test_e2e_spec_eagle` hits a memory fault in `ck_tile::FmhaBatchPrefillWithPagedKVCacheKernel` at the same prefill on main.
