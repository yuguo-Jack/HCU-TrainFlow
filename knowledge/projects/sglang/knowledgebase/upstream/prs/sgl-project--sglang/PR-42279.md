# [Perf] [AMD] scheduler: Keep speculative overlap scheduling on the forward stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/42279) · state: open · merged: False

## Original PR description

Split from #41994 as requested in review: the batch < 64 part. The other parts are #42280 (`MinFreeSlotsDelayer`) and #42281 (DSpark verify width, closed in favor of compact verify).

## Motivation

With overlap scheduling and speculative decoding on HIP, `FutureMap.resolve_seq_lens_cpu` and `resolve_mixed_spec_tails` block the host on the previous forward's publish event (`publish_ready.synchronize()`, #26672). DSpark publishes after verify and accept, near the end of the step, so the GPU idles while the host prepares the next batch: event-timed on DeepSeek-V4.1-Flash on MI355X, 0.65 ms of an 8.9 ms batch-1 cycle.

The host sync exists because `Event.wait()` on the separate schedule stream is slower still: a device wait pending in another HIP queue while a graph runs slows every dispatch of that graph (on MI355X a 512-kernel graph takes 1541 us instead of 853 us with such a wait pending). In the same timing, replacing the sync with that wait alone removed 0.50 ms of the idle but made the verify graph 1.21 ms slower.

`needs_cpu_seq_lens=False` alone does not remove this sync: on HIP the sync runs before the flag is checked, and the GPU gather of `new_seq_lens_buf` right after it needs the publish ordering in any case. The DeepSeek-V4.1 HIP backend already sets the flag to False (#41308).

## Modifications

On HIP with overlap scheduling and speculative decoding, without pipeline parallelism, and when no attention backend of the step keeps the CPU seq_lens mirror (`needs_cpu_seq_lens=False`), the scheduler runs on the forward stream (`Scheduler.schedule_on_forward_stream`, decided once in `init_overlap`, applied in `run_event_loop`), and `FutureMap(same_queue_publish=True)` waits on the publish event in-queue with `Event.wait()` instead of blocking the host. Stream order carries the forward-to-schedule dependencies.

These cases keep the current path:

- A backend that keeps the CPU mirror, such as aiter (the HIP default): the mirror is pulled with `.cpu()`, which on the forward stream waits for the whole forward (for EAGLE, including draft_extend) instead of the publish. Without this exclusion, Llama-3.1-8B + EAGLE3 on aiter lost 2.35% of batch-1 decode throughput (Table 3).
- Overlap without speculation: it has no publish wait, so the separate schedule stream keeps overlapping batch preparation.
- Pipeline parallelism, which runs its own event loop (`event_loop_pp`) and streams.

CUDA is unchanged.

No new unit test: the change only moves where the publish wait runs, so its observable effect is timing. A CPU test could only restate the gate or assert a mocked `Event` call, which `.claude/rules/unit-test-admission.md` does not admit. The AMD speculative CI tests use the triton backend (`needs_cpu_seq_lens=False`) and run the new path; the aiter EAGLE3 runs below cover the excluded one.
