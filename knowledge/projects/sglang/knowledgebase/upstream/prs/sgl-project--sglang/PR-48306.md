# [Feature] multimodal: Write item feature cache entries behind the request

[Upstream PR](https://github.com/sgl-project/sglang/pull/48306) · state: open · merged: False

## Original PR description

## Motivation

A request waited for its own cache writes before returning its features. On an item whose features run to hundreds of megabytes, e.g. a Qwen3.5 video of 14k visual tokens (about 240 MB), that put the time `torch.save` takes between processing and prefill, and the concurrent misses of one prompt's samples queued on the disk together: in the TimeLens run below the engines' rollout time went up by 1.2 s per step with the cache on.

## Modifications

- `_get_item_features` schedules each miss's write with `loop.run_in_executor` and returns; a failed write is logged. A reader that arrives before the file misses and computes the item itself, as before. `get` is still awaited, in the same thread pool.

## Tests

`test_mm_token_expansion.py`: a request returns with its features while a cache whose `__setitem__` blocks is still writing, and the write lands afterwards; a cache whose write raises only logs. The test helper's `asyncio.run` joins the default executor, so the other cases still see their writes.

Run on the H200 devbox: `test_mm_token_expansion.py`, `test_preprocess_cache.py`, `test_model_overrides.py` pass.

End to end: see #48305, which was measured together with this change.

## Stack

After #48288. The main port of #48304; the patch is byte-identical to it. The tests were run on the sglang-miles stack, not re-run here.
