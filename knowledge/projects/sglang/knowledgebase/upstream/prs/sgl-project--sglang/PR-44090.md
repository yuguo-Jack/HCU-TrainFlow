# [Fix] wan-animate-2: Size the in-context slot from both input grids

[Upstream PR](https://github.com/sgl-project/sglang/pull/44090) · state: closed · merged: True

## Original PR description

## Motivation

`POST /v1/videos` on Wan-Animate-2 at `size=720x1280` with a reference image and a driving video of slightly different aspect ratios (1072x592 and 538x304) fails in the first DiT forward of the first clip, on both checkpoints:

```
RuntimeError: The expanded size of the tensor (3520) must match the existing size (3555) at non-singleton dimension 2
```

**How the inputs are sized.** The requested `size` is a pixel-area budget, not an output resolution. `resize_by_area` fits the reference image and the driving video to that area independently, each at its own aspect ratio, with both sides floored to a multiple of 16. At 720x1280 the two inputs land on different grids:

| Input | Aspect | Canvas | Latent grid | Tokens per frame |
| --- | ---: | --- | --- | ---: |
| Reference image, drives the output | 1.811 | 1280x704 | 80x44 | 3520 |
| Driving video | 1.770 | 1264x720 | 79x45 | 3555 |

The video grid is one latent row taller and one column narrower, and holds 35 more tokens.

**Where it breaks.** The in-context attention lays the generated frames and the reference-video frames side by side in one sequence, with one fixed-size slot per frame. `_InContextLayout` sized every slot from the generation grid alone (3520 here), so the copy that lays each reference-video frame into its slot was asked to place 3555 tokens into 3520 positions. Which input ends up with the larger grid depends on the fractional parts the floor to 16 discards, not on which aspect ratio is larger, so other budgets fail for other input pairs (576x1024 with the same inputs: 2240 against 2268).

## Modifications

`_InContextLayout.max_tokens_per_frame` is now `max(generation tokens per frame, reference-video tokens per frame)`. Everything downstream already keys on that one value: the generation and reference K/V copies, `block_mask_fn`, `_make_score_mod` (the biased keys are still generation frame 1) and the block-mask cache key, so nothing else changes. The official implementation sizes the slot from the budget itself (`width * height // 256`, 3600 here) and so holds either grid; `max(...)` is the tighter bound and needs nothing new passed into the layout.

Three CPU unit tests: the layout slot for the measured grids, with the mirrored and equal-grid cases unchanged; a 5-token reference frame against a 4-token generation frame through `_in_context_attention`, which raises on main; and `resize_by_area` on the measured inputs at 720x1280, giving the two grids and a slot equal to the larger.

No cookbook change here: the output-resolution paragraph is reworded to describe the per-input fit in the distilled Wan-Animate-2 PR (#44085), which touches the same lines.

## Accuracy Tests

Bit-identical for every request that runs today: when the two grids agree, or the video's is the smaller, `max(...)` equals the previous value, so the layout, mask, score bias and every padded tensor are unchanged. The CI case (720x1280 image and 480x832 video at 576x1024: 2304 against 2268 tokens per frame) is in that set, so its pinned ground truth stays valid.

GPU check (one GPU, base checkpoint, 4 steps, `clip_len` 37, the 1072x592 / 538x304 pair): the 720x1280 request that fails on main with the error above completes with this change and returns 237 frames at 1280x704; the same request at the default 640x800 gives a byte-identical MP4 (same md5, per-frame PSNR inf) on main and with this change.
