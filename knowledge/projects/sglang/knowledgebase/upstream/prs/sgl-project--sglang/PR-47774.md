# [Perf] [AMD] fla/gdn: Faster GDN long-prompt prefill on gfx95 (chunk kernels, two-stream chunk scan, no host syncs)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47774) · state: open · merged: False

## Original PR description

Long Qwen3.8-27B prompts (100k-200k tokens) on MI355X spend about 11% of their prefill in the chunked gated delta rule of
`fla/`. This PR makes that path faster in three parts, one commit per change, eight commits in all:

1. Five changes to the GDN chunk kernels (`chunk_fwd_o` launch, tail-row clearing, `chunk_h` MFMA size knob, output into
   the caller's buffer, kkt zero blocks). This was the original PR.
2. An opt-in two-stream pipeline for the chunk scan of one long sequence (`SGLANG_GDN_CHUNK_PIPELINE=1`), plus the gate's
   chunk-local cumsum folded into the kkt + solve kernel. Was #47775.
3. Prefill steps prepared without host reads of device tensors (GDN chunk indices and offsets built from host offsets).
   Was #47776.

All three touch the same `fla/` chunk code and each builds on the one before, so they are now reviewed together.

### Part 1 (original #47774): faster GDN chunk kernels

#### Motivation

A long Qwen3.8-27B prompt on MI355X (TP1, 16384-token prefill chunks, 48 GDN layers) spends a visible share of its
prefill in the chunked gated delta rule of `fla/`. A profile of a 200k-token request shows five costs that do not need
to be there:

1. `chunk_fwd_o` launches two programs per (chunk, head) (`BV=64` for V = 128), and each computes the same `q @ k^T` of
   its chunk: 0.35-0.40 ms per GDN layer and chunk.
2. `chunk_fwd_o` allocates its output with `torch.zeros_like(v)` and then writes every row anyway: a 201 MB fill per
   layer and chunk (~35 us).
3. The `chunk_h` recurrence (~0.6 ms per layer and chunk, latency-bound: each 64-token step waits on its dependent
   dots) has no way to pick the MFMA instruction size; 16x16 is 6% faster than what the compiler picks.
4. In a breakable prefill CUDA graph the Triton GDN kernel returns a new tensor, which
   `_linear_attention_with_output_impl` copies into the graph's static output buffer: 2 x 201 MB per layer and chunk
   (~74 us).
5. `chunk_gated_delta_rule_fwd_intra` fills A (100 MB at 16384 tokens) with zeros before the fused kkt + solve kernel,
   which writes only the blocks on and below the diagonal (~14 us per layer and chunk).

Related: #38806 also retunes the HIP launches of `chunk_fwd_o` / `chunk_h` (and allocates the `chunk_fwd_o` output with
`empty_like`); see commit 2 for the padded-batch rows that then stay unwritten.

#### Modifications

One commit per item, each measured on its own (tables below):

1. `chunk_fwd_o`: on gfx95, one program per (chunk, head) (`BV=128`) with 16x16 MFMA tiles; other GPUs keep the current
   launch. The kernel is unchanged.
2. `chunk_fwd_o`: allocate with `torch.empty_like(v)` and zero only a padded batch's rows past `cu_seqlens[-1]` with a
   small Triton kernel that reads `cu_seqlens[-1]` on the device (no host sync, CUDA-graph safe). Fixed-length batches
   have no padding rows and skip it.
3. `SGLANG_GDN_CHUNK_H_MATRIX_INSTR_NONKDIM` (ROCm only): the MFMA instruction size of the single `chunk_h` config (`16`
   or `32`); the default `0` leaves the choice to the compiler, as today. Same single-config property as the existing
   `SGLANG_GDN_CHUNK_H_BV` / `_NUM_WARPS` / `_NUM_STAGES` knobs.
4. `chunk_gated_delta_rule(..., output=None)`: `chunk_fwd_o` writes into `output` when it is a contiguous tensor of `v`'s
   shape and dtype (otherwise a new tensor is returned, as before). `TritonGDNKernel.extend` passes the `output` the GDN
   backend already hands to every kernel, so the caller's `data_ptr` check skips the copy. Relies on commit 2: a
   caller's buffer gets exactly the rows a new tensor would.
5. The fused kkt + solve kernel also stores the six 16 x 16 blocks above the diagonal as zeros (same block pointers and
   boundary checks), and A is allocated with `torch.empty`.

#### Accuracy Tests

- Commits 2-5 are bit-identical (output, `h`, final state, A / w / u; checked at 16384 tokens in one and in several
  sequences, with and without padding, on NaN-filled fresh memory). Commit 1 differs only by bf16 rounding in a few
  elements (16384 tokens: max abs difference 1.2e-4, under 0.005% of the elements).
- New unit tests in `test/registered/attention/test_chunk_gated_delta_rule.py`: `chunk_fwd_o` against a float64
  evaluation of its formula (ragged sequences, 3 value heads per key head); padded rows are zero after NaN-filled
  blocks were freed; the output buffer is written in place exactly when it is usable (contiguous / padded real rows /
  other dtype / strided); the kkt + solve kernel writes every element of A (fresh memory holding 0, NaN and 7 gives the
  same bits). MI355X, this branch: 33 passed, 1 skipped (K = V = 256, skipped on ROCm before this change), 12 subtests.
- End to end (Qwen3.8-27B MXFP4, TP1), after each commit: greedy output ids identical to before on four reference
  prompts (100k-200k tokens and a short one); needle-in-a-haystack 30/30 at 100k-200k tokens; GSM8K-200
  (`sglang.test.few_shot_gsm8k`) 0.925-0.960, within the 0.920-0.960 run-to-run spread of this stack without the change.

### Part 2 (was #47775): GDN chunk scan pipelined over two streams

#### Motivation

On MI355X the GDN chunk scan takes ~11% of a 100k-200k-token Qwen3.8-27B prefill (48 GDN layers). Per layer, for a
16384-token chunk: `chunk_h` 532-560 us, kkt + solve + w/u 356 us, the output kernel 199 us. `chunk_h` is the serial
recurrence: one program per (head, V block), 192 programs for 48 heads x 4, each walking 256 chunks one after the other.
It is latency-bound and most of the 256 CUs sit idle while it runs; the per-chunk kernels before and after it are
parallel over chunks but wait for it.

#### Modifications

1. `SGLANG_GDN_CHUNK_PIPELINE=1` (off by default): `chunk_gated_delta_rule_fwd` runs the scan of one sequence with at
   least 8192 tokens as up to 4 parts of whole chunks, at most one part per 4096 tokens.
   - The calling stream runs `chunk_h` part after part; the state passes from one part to the next through the pool slot
     in fp32, as it stays in fp32 registers within one launch.
   - A side stream runs the per-chunk kernels beside it: kkt + solve + w/u of part i + 1 and the output of part i - 1
     while `chunk_h` does part i. Events order the parts, and the calling stream waits for the side stream at the end.
   - The single pass stays for batches of several sequences, sequences under 8192 tokens, read-only states
     (`inplace_update=False`) and CUDA graph capture.
   - `chunk_gated_delta_rule_fwd_h` takes an optional buffer for the per-chunk states, so the parts write into one tensor
     of the full scan and callers that read the states (mamba state tracking) get the same tensor as before.
2. With the pipeline, the gate's chunk-local cumsum moves into the fused kkt + solve kernel
   (`chunk_gated_delta_rule_fwd_intra(..., g_out=...)`): the kernel loads the chunk's 64 gate values anyway, takes
   `tl.cumsum` over them as `chunk_local_cumsum` does and stores it for the later kernels. Parts 1-3 then take their
   cumsum on the side stream, off `chunk_h`'s critical path. The one-pass path keeps `chunk_local_cumsum` (without the
   pipeline the fold does not pay: alone on one stream it costs about what the separate kernel did).

#### Accuracy Tests

- Bit-identical by construction: the same kernels on the same per-chunk inputs (the [64] cumsum stays inside one wave64
  in both kernels).
- New unit tests in `test/registered/attention/test_chunk_gated_delta_rule.py`: `test_pipelined_scan_is_bit_identical`
  (GQA 6:2; o, h and the state pool vs one pass at 16384 tokens / 4 parts, 12600 / 3 parts with a part boundary inside
  the last chunk, 8192 / 2 parts, 10000 tokens in 10240 rows with a padded tail; 8000 tokens, two sequences and a
  read-only state keep the single pass), and a cumsum test (with `g_out`, the cumsum, w, u and A equal
  `chunk_local_cumsum` followed by the current kernel, bit for bit, at 4096 and 4000 tokens and for three sequences).
  MI355X, this branch: 34 passed, 1 skipped, 19 subtests.
- Qwen3.8-27B MXFP4 on MI355X with the variable on: greedy output ids identical to the run without it (4 prompts incl.
  100k-200k-token needle prompts), needle-in-a-haystack 30/30 at 100k-200k tokens, GSM8K-200 0.935-0.945 (0.925-0.950 on
  builds without it); a mixed soak (16 prompts of 100k-200k tokens next to 600 chat requests) serves every request.

### Part 3 (was #47776): prefill steps without host reads of device tensors

#### Motivation

With the overlap scheduler the CPU prepares step i + 1 while the GPU runs step i. A long prompt is prefilled in chunks
(16384 tokens per step here), and in a profile of a 200k-token Qwen3.8-27B request on MI355X (TP1, aiter attention,
breakable prefill CUDA graph) the GPU sits idle for 1.2-1.5 ms at the start of every chunk. Running the server with
`torch.cuda.set_sync_debug_mode` shows five host reads of device tensors per prefill step; each one blocks the CPU until
the GPU has drained, so the CPU can no longer queue the next step ahead and the GPU waits for it:

- `AiterIndicesUpdaterPrefill.update_single_wrapper`: slicing `kv_indices` at `kv_indptr[-1]` (removed by #47432);
- `prepare_chunk_indices`: `.tolist()` of the chunk counts, and the copy of the indices to the device;
- the pipelined GDN chunk scan's plan: `cu_seqlens.tolist()` for the sequence length;
- `prepare_chunk_offsets`: `cu_seqlens.new_tensor([0])` (a synchronous host-to-device copy).

The values are all known on the host: the scheduler already has the extend lengths (`extend_seq_lens_cpu`, which
`logical_num_tokens` uses today). The stall only goes away when every read of the step is gone, so this PR and #47432 are
measured together below.

#### Modifications

- `ForwardMetadata.query_start_loc_cpu`: the hybrid linear-attention backend keeps `query_start_loc` on the host when the
  extend lengths are trusted (the same condition as `logical_num_tokens`: lengths for every request, no two-batch-overlap
  split); otherwise it stays `None` and nothing changes.
- The GDN backend hands it to the Triton extend kernel, which passes it to `chunk_gated_delta_rule(cu_seqlens_cpu=...)`.
- `prepare_chunk_indices(cu_seqlens, chunk_size, cu_seqlens_cpu=None)`: with host offsets the indices are built on the host
  and copied in from pinned memory without blocking; the pipelined scan takes its plan from the host offsets;
  `chunk_fwd_o` builds its indices from them too (the same cached indices when its chunk size is 64).
- `prepare_chunk_offsets` pads its leading zero on the device.

#### Accuracy Tests

- Unchanged by construction: the same kernels run on the same index tables.
- Unit tests: chunk indices from host offsets equal the device-built ones (values, dtype, several length mixes); chunk
  offsets equal the previous formula; `chunk_gated_delta_rule` with host offsets gives bit-identical output, per-chunk
  states and final states (one pass with three sequences, pipelined with and without a padded tail, one pass with a padded
  tail) and runs under `torch.cuda.set_sync_debug_mode("error")`; the metadata's host offsets equal `query_start_loc`
  exactly when the lengths are trusted, `None` otherwise (decode, verify, idle, two-batch overlap). MI355X, this branch:
  `test_chunk_gated_delta_rule.py` 36 passed, 1 skipped; `test_mamba_prefill_track_metadata.py` 11 passed, 90 subtests.
- Qwen3.8-27B MXFP4 end to end on MI355X (with #47432): with sync debug mode on, three 100k-token requests log no
  synchronizing call (five call sites before); greedy output ids identical to the run without the change (4 prompts),
  needle-in-a-haystack 30/30 at 100k-200k tokens, GSM8K-200 0.940 (0.930 without it, same harness); a mixed-traffic soak
  (16 prompts of 100k-200k tokens at concurrency 2 next to 600 chat requests of 1-2k tokens at 6 requests/s) completes
  every request with the same greedy output afterwards.
