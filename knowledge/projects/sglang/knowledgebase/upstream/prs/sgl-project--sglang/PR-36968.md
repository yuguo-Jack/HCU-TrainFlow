# [Fix] qsa: Fail early on SM89 without classic FA2

[Upstream PR](https://github.com/sgl-project/sglang/pull/36968) · state: open · merged: False

## Original PR description

## Base and scope

Retargeted to `main` after the model integration landed in #37500 (replacing #36497). Rebased onto `fd5c52588ff2` on October 26; current head `0570f5e17dbf` includes the required `6a39ddf1f2e0` CI baseline. The main-branch resolver still accepts an importable FA4 fallback on SM89 when classic FA2 is missing; this PR keeps its SM89 preflight fix independent of the model-support stack.

## Motivation

Qwen3.8-Flash-Next currently fails late on NVIDIA L20 / SM89 when the image does not contain classic FlashAttention / FA2:

```text
FlashInfer TRTLLM resolver -> unavailable on SM89
classic flash_attn / FA2    -> not importable
flash_attn.cute / FA4       -> importable, so the resolver selects it
first sparse decode         -> CuTe MLIR operation creation failure
```

On four L20s with the released FP8 checkpoint, the server loaded the approximately 173 GB checkpoint and became HTTP-ready before the first generation request failed in the FA4/CuTe path. Importability is therefore not a sufficient compatibility check, and the failure happens after the most expensive part of startup.

## Modifications

- Represent the resolved QSA sparse-decode backend explicitly as `TRTLLM`, `TRITON_ROCM`, `KDA_SM121`, classic `FA2`, or `FA4_CUTE` and use the same result for preflight and runtime dispatch.
- Reject the FA4/CuTe fallback only on exact SM89 when classic FA2 is unavailable, with an actionable error.
- Run the QSA check before `ModelRunner.load_model()` and log the selected backend once on TP rank zero.
- Keep the QSA implementation lazily imported for non-QSA models.
- Preserve the existing TRTLLM route on SM100/SM120, dedicated KDA route on SM121, and import-based policy on SM90. Preserve the current ROCm Triton packed-decode path without requiring FA2/FA4/aiter, and retain the existing aiter varlen helper. The behavioral change is intentionally limited to the hardware reproduced here.

## Independence / related work

- #36806 changes the exact SM120 FlashInfer route; it does not add an SM89 path or preflight.
- Draft #36787 adds SM120 kernels and leaves the existing flash-attn fallback on other architectures, including SM89.
- #36531 and #36558 track SM12x failures, not L20 / SM89.

The October 13 main snapshot still permits the import-based FA4 fallback on SM89. A targeted October 13 search of PR titles/bodies for QSA and SM89 found this PR and the separate L20 MoE-config PR, but no equivalent preflight implementation. This does not exclude other ongoing or unindexed work.

Rebase-only update; the patch is unchanged apart from surrounding main-branch context. The full-startup tests use the real local Qwen3.8-Flash-Next-FP8 checkpoint configuration, TP1, and disabled CUDA graphs. Both stack traces reach `ModelRunner.initialize -> preflight_model_backends -> preflight_qsa_sparse_decode_backend` and raise:

```text
RuntimeError: QSA sparse decode on NVIDIA SM89 requires classic FlashAttention / FA2,
but it is not importable. FlashAttention-4 / CuTe is not a validated QSA fallback
on SM89/Ada. Install a compatible FA2 build before starting SGLang.
```

Neither log contains `Load weight begin`; the model-runner memory baseline is 0.00 GB. An earlier attempt in the old image stopped at its FlashInfer version gate and is not counted as a passing startup test.

FA2 parity mirrors the QSA varlen call: 24 Q heads, 2 KV heads, head dimension 256, one query per row, `causal=True`, and KV lengths `[1]`, `[64]`, `[0,1,17]`, `[31,0,129,257]`. Maximum absolute error against the FP32 reference was **5.49e-4 for FP16** and **4.17e-3 for BF16**. Empty rows and extra packed-buffer capacity are included. Tolerances: FP16 `atol=0.002, rtol=0.005`; BF16 `atol=0.01, rtol=0.01`.

Build disclosure: classic FA2 `2.8.3.post1` was compiled locally with only its two CUDA/C++ build-standard flags changed to C++20, following upstream [#2879](https://github.com/Dao-AILab/flash-attention/pull/2879) / [#2899](https://github.com/Dao-AILab/flash-attention/pull/2899) for newer Torch headers. FA2 kernel sources were unchanged; this experiment-only build adaptation is not part of this SGLang PR.

### Check that newer FA4 has not already removed the failure

FA4 `4.0.0b34` does contain an SM8x forward path, so this is **not a claim that FA4 is universally unsupported on Ada**. Directly exercising the same varlen interface on L20 with the actual QSA head dimension 256 still fails all eight FP16/BF16 × KV-length cases with CUDA launch/configuration errors. Changing only the head dimension to 128 passes all eight numerical-control cases.

Minimal reproduction of the failing QSA shape, in that environment:

```python
import torch
from flash_attn.cute.interface import flash_attn_varlen_func

q = torch.randn(1, 24, 256, device="cuda", dtype=torch.bfloat16)
k = torch.randn(71, 2, 256, device="cuda", dtype=torch.bfloat16)
v = torch.randn_like(k)
cu_q = torch.tensor([0, 1], device="cuda", dtype=torch.int32)
cu_k = torch.tensor([0, 64], device="cuda", dtype=torch.int32)
flash_attn_varlen_func(q=q, k=k, v=v, cu_seqlens_q=cu_q,
                      cu_seqlens_k=cu_k, max_seqlen_q=1, max_seqlen_k=64,
                      softmax_scale=256**-0.5, causal=True)
```

The registered suite covers SM89, SM90, SM100, SM120, SM121, ROCm's no-varlen-dependency path, non-QSA lazy no-op, rank-zero logging, and exception propagation. Other architectures are policy/unit coverage, not hardware validation. Ruff, isort, registered-test taxonomy, and whitespace checks passed.

The [independent RTX 4090 report](https://github.com/sgl-project/sglang/pull/36968#issuecomment-6142214847) supports the original failure and workaround; it is not counted as testing this head. These results validate fail-fast and the selected kernel, **not successful full-model 176B serving, CUDA-graph capture, throughput, or complete upstream CI**.

- aisensiy · comment · 2026-10-13T09:10:02Z · [source](https://github.com/sgl-project/sglang/pull/36968#issuecomment-6142214847)

Validated this fix direction on real hardware: 8x RTX 4090 (sm89), `Qwen3.8-Flash-Next-FP8`, tp4/ep4, 262K context, PLE offload enabled.

Preinstalling classic FA2 `2.8.3.post1` (built from sdist against `torch==2.13.0+cu130`, `FLASH_ATTN_CUDA_ARCHS=80;90;100;120`) makes the exact crash described here disappear: the QSA resolver picks classic FA2, server serves fine, throughput on par with vLLM on the same hardware and checkpoint.

One extra data point for anyone shipping classic FA2 in a shared image: with classic FA2 importable, `_resolve_flash_attn_varlen_func()` also selects it on sm120 (RTX 5090 / RTX PRO 6000), so build the 100/120 archs too (the upstream default arch set already does) or Blackwell machines get an importable-but-kernelless FA2. The sm121/GB10 branch is unaffected.

Without the fail-fast here, users burn a 10-20 minute full weights load before hitting the CuTe error, which is very far from the real cause. Would love to see this merged.
