# [Feat] [AMD] gpt-oss: Mixed W4A8 MoE on gfx1250, Gluon below a token count and FlyDSL above

[Upstream PR](https://github.com/sgl-project/sglang/pull/47398) · state: open · merged: False

## Original PR description

This PR applies Mixed (FlyDSL + Gluon) MoE strategy, with a configurable threshold setting.

## Motivation

On gfx1250, there are **3 apparent lowering paths of W4A8 MoE kernels**: triton, Gluon, FlyDSL.  Profiling them reveals interesting results as below.  Experiment details: Per-layer MoE time, gpt-oss-120b, TP1, layer 18's real weights, the full MoE forward SGLang calls (routing, quant, both GEMMs), inside a CUDA graph, weights streamed from HBM; µs per layer, median of 3 passes.

| tokens | Triton (existing) | Gluon | FlyDSL | fastest | Gluon / FlyDSL |
|---|---|---|---|---|---|
| 1 | 36 | **36** | 77 | Gluon (= Triton) | 0.47 |
| 16 | 222 | **125** | 224 | Gluon | 0.56 |
| 64 | 351 | **229** | 324 | Gluon | 0.71 |
| 128 | 403 | **276** | 345 | Gluon | 0.80 |
| 256 | 599 | **335** | 371 | Gluon | 0.90 |
| 384 | 750 | 394 | 399 | tie | 0.99 |
| 512 | 926 | 462 | **436** | FlyDSL | 1.06 |
| 1024 | 1272 | 608 | **555** | FlyDSL | 1.10 |
| 2048 | 1560 | 1015 | **758** | FlyDSL | 1.34 |
| 3072 | 2150 | 1738 | **1024** | FlyDSL | 1.70 |

- **Gluon** wins below ~320 tokens: 1.4-2.3x faster than FlyDSL below 128.
- **FlyDSL** wins from 1024 tokens on, by 1.7x at a full 3072-token prefill chunk; from 320 to 768 the two are within 6%.
- **Triton** matches Gluon only at a single token; from 4 tokens on it is 1.5-2.3x slower than the faster of the two.
- TP2 (per rank, intermediate 1440): the same picture (Gluon/FlyDSL 0.46 at 1, 0.62 at 128, 1.61 at 3072; within 7% from 320 to 1024). With uniform routing the crossover moves up to ~1024, with all tokens on 4 experts down to ~192.

FlyDSL also costs ~1 ms of CPU per eager call (Gluon and Triton ~0.3 ms), so this pays off with prefill CUDA graphs (`--cuda-graph-backend-prefill breakable`), where that cost is not paid per step.

## Modifications

- `SGLANG_GFX1250_W4A8_FLYDSL=1` (default off: without it nothing changes). At load, `prepare_w4a8_gfx1250_flydsl_weights` puts the experts into FlyDSL's layout: gate/up interleaved, dims zero-padded to 256 (2880 -> 3072; the TP2 intermediate 1440 -> 1536), `moe_shuffle_weight` / `moe_shuffle_scale`, padded scales = e8m0 1.0. These buffers become the layer's parameters.
- Batches of at least `SGLANG_GFX1250_W4A8_FLYDSL_MIN_TOKENS` tokens run `aiter.fused_moe` (FlyDSL a8w4, `gate_mode=INTERLEAVE`, `quant_type=per_1x32`, `quant_dtype_a=fp8`, Swiglu with `swiglu_limit`, bias1/bias2, bf16 router weights).
- Smaller batches run `moe_gemm_a8w4` with `backend="gluon"`, `preshuffled=True`, `swizzle_mx_scale="GFX1250_SCALE"` over `moe_weight_decode_view` of the same storage (zero-copy views).
- The Gluon views are cut to dims rounded up to 128 (2880 -> 2944, activations zero-padded). With `GFX1250_SCALE` the scale descriptor ends at `K // 32` groups while the n32k4 layout stores K in 128-element chunks, so at K = 2880 the last chunk's scales would read as 0. Aligned, the Gluon path is bitwise equal to the Triton path.
- `SGLANG_GFX1250_W4A8_FLYDSL_MIN_TOKENS` defaults to 384. In serving the MoE sees decode batches of at most the decode graph size (64 in the benchmarks below) and prefill buckets of 832-3072 tokens (1k prompts, 3072-token chunks); at most 5% of prefill steps fall between. So any value from 128 to 1024 serves about the same (predicted within 0.6% from the batch census and the per-layer times; measured at 256, 768 and 1024: throughput within the control drift, 768 and 1024 raised one point's median TTFT by ~4%). At 16, decode batches of 16-64 tokens run FlyDSL: -19% throughput (table below).
- The prepared weights are copied into a `torch.cuda.MemPool` of their own. Without it the caching allocator kept 13.6 GiB of reserved-but-free segments after the prep (each pinned by a piece of a padded buffer), which SGLang counted as weight memory and took from the KV pool. Outputs bitwise unchanged.
- Expert parallelism keeps the existing path. `SGLANG_GFX1250_W4A8_KERNEL_GATHER=1` together with the switch is refused (the Gluon path takes preshuffled weights).
- Unit test `test/registered/amd/test_gpt_oss_w4a8_flydsl_moe_gfx1250.py` (stage-b 1-GPU AMD, ~60 s; skips off gfx1250 or without AITER's FlyDSL grouped MoE): synthetic MXFP4 experts at gpt-oss's hidden size 2880 and the TP1/TP2 intermediate sizes, nonzero biases. Covers the dispatch boundary (MIN-1 Gluon, MIN and MIN+1 FlyDSL), Gluon views vs the Triton path (bitwise), FlyDSL vs an fp32 dequantized reference (rel. L2 < 0.03), finite outputs, unchanged weights, and the switch off (stock layout and output). It fails, as it should, with the Gluon views at the real K = 2880 and on an AITER without ROCm/aiter#6663.

## Accuracy Tests

`amd/gpt-oss-120b-w-mxfp4-a-fp8`, gfx1250 (MI450-series), images `rocm/sgl-dev:v0.5.22-rocm101-mi45x-20261027` and `-20261028`, AITER 2bb549102 + #6663 + the decode-store fix. GSM8K: 1319 questions, thinking, on a fresh server **after** fixed-seq 8192/1024 c16 + 1024/1024 c16 load (the protocol that exposed the race above).

- TP1, this PR at `MIN_TOKENS=384`: 0.9636 / 0.9621 / 0.9613 (three servers); with the MemPool commit 0.9613.
- With the AITER decode-store fix: 12 of 12 gate runs pass at TP2 and TP1; on the final stack TP1 0.9591 / 0.9613, TP2 0.9606.
- After each layout of a full benchmark suite, switch off -> this PR: TP1 0.9598 -> 0.9606, 2xTP1 0.9591 / 0.9538 -> 0.9591 / 0.9613, TP2 0.9621 -> 0.9583.

No truncated answers in any passing run. Layer check on real weights (TP1 layers 0/18/35, both TP2 ranks; 1-3072 tokens incl. 63/64/65 and 383/384/385; router and skewed routing): Gluon views vs the Triton path bitwise identical in all 130 rows; FlyDSL vs an fp32 reference rel. L2 0.02-0.07, the same distance as the Triton path; no NaN/Inf; weights unchanged after all calls.

## Known limitations

- **Memory.** The FlyDSL layout pads to 256: with the switch on the weights take 68.9 GB after loading instead of 61.2 GB (TP1; TP2 34.6 vs 30.7 GB per rank), so the TP1 KV pool is 987,776 tokens instead of 1,213,504. Padding to 128 needs AITER's FlyDSL MXFP8 activation quant to accept a feature dim that is not a multiple of 256 (it asserts today).
- **Gluon MoE decode race**: It was captured in TP2 GSM8K test. TP1 GSM8K almost always survive GSM8K full round.  The race can only be detected with finer-grained tests into LDS rows.  The root cause is complex.  [A known fix in LLVM upstream](https://lists.llvm.org/pipermail/llvm-commits/Week-of-Mon-20260803/2001738.html) mitigates this a lot but not cut to zero.  Still need further investigation.
- Off by default; `EP` keeps the existing path.
