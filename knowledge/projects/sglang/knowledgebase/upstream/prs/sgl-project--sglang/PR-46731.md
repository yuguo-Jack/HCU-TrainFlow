# [Perf] [AMD] moe: Add tuned Triton fused MoE config for gemma-4-26B-A4B on MI355X

[Upstream PR](https://github.com/sgl-project/sglang/pull/46731) · state: closed · merged: True

## Original PR description

## Motivation

On MI355X, gemma-4-26B-A4B's Triton fused MoE (`--moe-runner-backend triton`) has no tuned config, so every batch falls back to the heuristic:

```
Using default MoE kernel config. Performance might be sub-optimal! Config file not found at .../moe_runner/triton_utils/configs/triton_3_8_0/E=128,N=704,device_name=AMD_Instinct_MI355X.json
```

The heuristic uses `BLOCK_SIZE_M 64, BLOCK_SIZE_K 32` from batch 256 up. At batch 4096 the fused MoE takes 1303 us; with a tuned config it takes 722 us. `main` has no MI355X fused-MoE config at all.

## Modifications

One new file, no code change: `python/sglang/srt/layers/moe/moe_runner/triton_utils/configs/triton_3_8_0/E=128,N=704,device_name=AMD_Instinct_MI355X.json`, 14 batch buckets (1 to 8192).

- `E=128` is `num_experts` and `N=704` is `moe_intermediate_size` at TP1. Other TP sizes give another `N` and do not use this file.
- `triton_3_8_0` matches the ROCm 10 image (`triton.__version__ == "3.8.0"`). Images with another Triton version reach this file through the newest-first fallback, with a warning. I measured only Triton 3.8.0.
- There is no `_down` file. The down projection then reuses this table (`get_moe_configs` falls back to the up config), and the kernel numbers below time both GEMMs.

### Tuning

`benchmark_config` from `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py` over the default ROCm search space (1600 candidates per bucket, bf16, TP1), one bucket per process. Two candidate groups are excluded:

- `num_warps=1`. On gfx950 with Triton 3.8.x, single-wave kernels race on LDS between a `ds_read` and the direct-to-LDS loads, and write rows that the store mask should drop (llvm/llvm-project#187673, reverted upstream in llvm/llvm-project#208280 but still in Triton 3.8.x's LLVM). This also makes the stock tuner crash with a memory fault at M = 512, 1024, ... .
- `num_warps=2` with `BLOCK_SIZE_N=16` and `BLOCK_SIZE_M>=128`. These intermittently produced wrong elements in the down GEMM in our checks.

Every selected entry uses `num_warps` 2, 4 or 8. The tuning driver is not part of this PR.

## Accuracy Tests

`fused_moe` output with each tuned entry vs the heuristic config, same inputs: max abs diff 0 for all 14 buckets, three reruns identical. A `num_warps=1, BLOCK_SIZE_M=128` control at M=640 shows a mismatch, so the check detects bad configs.

  --moe-runner-backend triton --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.88 \
