# [Fix] speculative: Keep the server alive when verify sampling ops fail to JIT

[Upstream PR](https://github.com/sgl-project/sglang/pull/43884) · state: open · merged: False

## Original PR description

## Motivation

#43412: on pip CUDA bundles without prebuilt flashinfer coverage, the first non-greedy speculative request triggers flashinfer's request-time JIT for the verify renorm ops; the compile fails (bundled cccl vs pip-toolkit headers), the RuntimeError escapes the scheduler event loop, and the whole server is SIGKILLed. The failed build also leaves partial artifacts in the flashinfer cache, so every restart repeats the crash. #43591 pins the toolchain for that environment; this handles the residual the issue's expected-behavior section asks for — a sampling-op JIT failure shouldn't be fatal to the server.

## Modifications

At startup, the spec workers that run eagle_sample's verify path (EAGLE, multi-layer EAGLE, NGRAM, UNO) now prewarm the sampling ops through the existing prewarm_sampling hook: a poisoned flashinfer cache (build.ninja + partial objects, no sampling.so) is cleared first, then the renorm kernels are warmed with small dummy tensors. Without --speculative-sampling-renorm-fallback a compile failure stops startup with the full compiler log; with it, the verify renorm degrades to the in-tree triton kernels HIP already uses at this call site. At request time a renorm failure aborts only the affected requests with a 500 and a hint, and the failed backend is remembered so later requests don't re-run the compile (flashinfer doesn't cache failed builds). --sampling-backend pytorch now reaches the verify renorm on CUDA, which it previously didn't. I left the PD-disagg and pipeline-parallel event loops and DFlash's own verify path out of this and can follow up if wanted.

## Accuracy Tests

No model-output changes on the flashinfer path — same kernels, same call semantics; the degraded path reuses the triton renorm kernels already serving HIP at this exact call site. santanu20 (the issue reporter) has offered to test on the reproducing rig (RTX 4070 Laptop, pip cu13); the new CPU tests cover dispatch, containment, and cache recovery with mocked compile failures (38 tests).

## Speed Tests and Profiling

Not perf-sensitive: the startup prewarm costs one ninja no-op on a warm cache, and the request-time path is unchanged while flashinfer is healthy.

Reviewed from the reporter side of #43412 — the containment design matches what the issue's expected-behavior section asked for, and both scope suggestions from the thread made it in. Findings:

**Correctness — no blockers found:**

- The poison signature (build.ninja or `*.o` present, `sampling.so` absent) matches exactly the failed-ninja-build state reported in #43412.
- Lock-awareness is the load-bearing detail for TP: every rank runs the preflight concurrently, and doing check-then-act under the same filelock flashinfer serializes builds with closes the race where one rank deletes a build another just started. `test_lock_held_means_not_poisoned_and_no_clear` pins it.
- The surgical clear matters in practice — flashinfer's own `clear_cache_dir()` would also drop unrelated working ops; sibling-op survival is tested.
- OOM excluded from the poison path (a retry after a transient OOM would succeed, so the failed-backend flag must not latch) — correct failure-class separation.
- Fail-fast scoped to renorm-needing batches only (temperature-only traffic stays servable), and per-call `resolve_verify_renorm_impls()` replacing the hardcoded flashinfer imports means the degraded path is entered without changing the healthy path's semantics. HIP resolution is unchanged.
- The fallback retry re-runs from the pre-renorm tensor — correct if flashinfer's top_k half-succeeded before top_p threw.
- The overlapped loop correctly suppresses `launch_batch_sample_if_needed` for an aborted batch (`spec_sampling_op_failed`), which would otherwise sample a `None` result.

**Nits (non-blocking):**

- The triton retry block in `_renorm_verify_probs` duplicates the renorm sequence (~25 lines); an inner helper would DRY it, though exception-path explicitness is a defensible trade.
- Flag doc living in `server_arguments_undocumented.txt` matches recent speculative-flag precedent; a docs row would also be fine.

**+1 for the offered follow-ups**, with DFlash's verify path first if possible: `dflash_utils` aliases the same renorm names, so the DFlash lane keeps the original crash-on-affected-environments behavior until then.

Follow-up from the #43412 environment with runtime receipts (flashinfer 0.6.18, no working nvcc for either the system or the bundled toolchain — the issue env):

**What this PR fixes — confirmed live:**

- The startup poison-clear fired as designed: `flashinfer sampling JIT cache is in a partial-build state (failed compile left artifacts without sampling.so); clearing .../cached_ops/sampling so warm-up can retry from scratch`, then the warm-up retry failed, then `flashinfer sampling op preflight failed; degrading speculative verify to the in-tree triton renorm (--speculative-sampling-renorm-fallback)` — and the server reached `The server is fired up and ready to roll!` instead of crash-looping. That is exactly the recovery arc the issue's expected-behavior section asked for.

**Surviving crash path on this env class — scope observation, not something this PR introduced:**

- The first non-greedy request still takes the scheduler down. Traceback chain: `eagle_sample` (eagle_utils.py:1204) → `tree_speculative_sampling_target_only` (kernels/ops/speculative/sampling.py:50) → lazy `load_jit("speculative_sampling", ..., extra_dependencies=["flashinfer"])` → ninja build of `sgl_kernel_jit_speculative_sampling_4_True` fails with the same `cuda_toolkit.h` `#error` → `Scheduler hit an exception` → SIGQUIT.
- The renorm containment covers `resolve_verify_renorm_impls()`, but `sampling_fn` selection (eagle_utils.py:1149-1157) has no JIT-free CUDA alternative for the non-rejection path: `use_rejection_sampling=False` always binds the JIT tree kernel on CUDA, while the triton `chain_speculative_sampling_triton` path requires target-vocab `draft_probs`, which NGRAM drafts don't produce (guarded by the ValueError at eagle_utils.py:1188).

Two possible extensions, for consideration: route the tree kernel through the same startup preflight (warm it or fail it at boot), and/or give the lazy JIT failure the request-level containment the renorm path got — currently the exception propagates out of `forward_batch_generation` and kills the server.

Rig knobs used (env facts for reproduction, not suggestions): `--attention-backend triton` (0.6.18 has no wheel coverage for the branch's prefill attention op — separate gap, consistent with the flashinfer ≥ 0.7.1 assert), `--sampling-backend pytorch` (base `gen_sampling_module().build_and_load()` hits the same 0.6.18 wheel-coverage issue, also outside this PR), `SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1` (the issue env pins 0.6.18).
