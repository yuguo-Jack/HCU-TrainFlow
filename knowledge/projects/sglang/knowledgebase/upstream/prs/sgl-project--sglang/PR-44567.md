# [Fix] openai: a pre-stream abort answers with its HTTP status, not a 200 stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/44567) · state: open · merged: False

## Original PR description

## Motivation

On a **streaming** `/v1/chat/completions` or `/v1/completions` request, every scheduler abort is delivered as an SSE error event inside a `200`, even when the abort arrives before any output was produced:

| abort | status carried | streaming today | non-streaming today |
|---|---|---|---|
| `--max-queued-requests` full | 503 | `200` + `data: {"error": {..., "code": 503}}` | HTTP 503 |
| waiting-queue timeout (`SGLANG_REQ_WAITING_TIMEOUT`) | 503 | same | HTTP 503 |
| priority preemption | 503 | same | HTTP 503 |
| scheduler-side validation (sampling mask, beam) | 400 | same | HTTP 400 |

`_handle_streaming_request` already pulls the first chunk before sending headers so that a validation failure can become a proper HTTP 400 instead of an SSE payload (see the comment there), but it only catches a raised `ValueError`. The scheduler abort comes back through `tokenizer_manager._handle_abort_finish_reason` as an ordinary yielded chunk that `_generate_chat_stream` turns into an error event, so it slips past the pre-read and goes out as a `200`.

This matters for anything in front of the engine: a load balancer or gateway that routes on status cannot tell a queue-full refusal (safe to retry elsewhere, no work was done) from a successful stream without parsing SSE bodies, and `max_queued_requests` loses most of its value as a back-pressure signal for streaming clients, which are the common case for chat.

## Modifications

- `serving_base.py`: `pre_stream_error(first_chunk)` parses the kick-start chunk; if it is an error event carrying an integer status code, it returns `create_error_response` with that message, type and code; otherwise `None`.
- `serving_chat.py`, `serving_completions.py`: after the kick-start, if `pre_stream_error` returns a response, close the generator and return it. A normal first chunk and `[DONE]` are untouched. Mid-stream aborts (headers already out) are unchanged and still arrive in-band.

## Unit test

`test_streaming_abort_before_any_output_answers_with_its_status` drives `_handle_streaming_request` with a queue-full abort as the only output and asserts a 503 response with the abort's message and code. It fails on `main` (`200 != 503`) and passes with the change; `test_streaming_abort_yields_error` (mid-stream abort stays in-band) still passes.
