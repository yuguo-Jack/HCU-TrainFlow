# [AMD] DeepSeek-V4.1: opt-in mono decode launches on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/43497) · state: open · merged: False

## Original PR description

> **Status (2026-10-19):** SGLang now runs DeepSeek-V4.1 monokernels through the sgl-amd-mono plugin (`--monokernel-backend amd`, #44353, merged 2026-10-15). This draft stays open as the record of our in-tree work and is not for merge. The parts the plugin does not have yet are proposed to sgl-amd-mono: <PR links>.


## Motivation

DeepSeek-V4.1-Flash decode on MI355X runs many small kernels and two TP all-reduces in every layer. A monokernel runs a large part of a decoder layer, including its all-reduce, in one persistent launch, so a decode step needs far fewer launches.

This PR moves the two DeepSeek-V4.1 monokernel launches (FFN and K1) onto the plugin layout and API of RFC #43949, behind one switch: `--enable-monokernel`. The switch replaces the env vars `SGLANG_ROCM_MONO_DECODE` and `SGLANG_ROCM_MONO_K1`. The PR is based on main `d4daf52369` and does not depend on #44405-#44408. #44033 (K1 on all layers, and K2) stacks on this PR and is moving to the same plugin.

## Modifications

- New package `python/sglang/experimental/monokernels/` (35 files, RFC layout), plus the `experimental` package marker:
  - `guards.py`, `runtime.py`, `spec.py`: startup refusal, load hooks, staged attach, routing, spans, numerics and the spec registry.
  - `hip/common/`: the shared HIP runtime. Every wait between workgroups or GPUs goes through one guarded wait.
  - `hip/deepseek_v41/`: the DeepSeek-V4.1 spec and its gfx950 kernels, moved with `git mv` from `srt/models/deepseek_common/amd/dsv41_mono/`.
- Two spans per layer. SGLang's attention core runs between them, because its state lives in the attention backend (RFC section 5).
  - `k1` (`layer_in` -> `core_in`): the pending mHC post, the mHC pre, the norm, and the attention front (wqkv_a, q and kv norms, wq_b, RoPE, SWA KV write). It runs on 30 layers in decode: the layers without a compressor or indexer, except layer 0 and the Engram layers. DSpark captures the input of three of them, so a verify step runs `k1` on 27 layers.
  - `ffn` (`attn_partial` -> `layer_out`): the attention all-reduce, the FFN seam, the MoE with the shared expert, and the MoE all-reduce. All 40 layers.
- Decode and DSpark verify graphs of up to 48 rows use the monokernels (up to 48 decode requests, or 8 requests in a verify step). Larger graphs use the normal path.
- Safety (RFC sections 7-9):
  - Startup refuses every unsupported setting and lists all reasons at once (for example DP attention, EP, PP, LoRA, eager or breakable decode graphs, a GPU other than gfx950, TP other than 2 or 4).
  - Every wait has a deadline: half of `--watchdog-timeout`, at most 60 s; a deadline below 5 s is refused. A timeout stops every rank, and no token of the failed step is sent.
  - All ranks agree at each attach stage. All buffers are allocated at attach, none during graph capture or replay.
- SGLang integration: 7 `srt` files, +75/-4: the flag, the config hook, three test env vars, and the load, attach, route and kernel calls in the DeepSeek-V4 model. Plus one CODEOWNERS line. With the switch off, SGLang runs its normal path.
- Tests: CPU unit tests (`test/registered/monokernels/unit`), kernel and fail-stop tests (`kernels`, nightly MI35x), serving tests (`e2e`, nightly MI35x), and `test/manual/monokernels/validate.py`.
- Usage: add `--enable-monokernel` to the DeepSeek-V4.1 MI355X recipe (cookbook section 3.6). Details: `python/sglang/experimental/monokernels/README.md`.
- Credits: `hip/SOURCE.md` lists the code adapted from [ROCm/ATOM](https://github.com/ROCm/ATOM/commit/97359d6df46c59736468168b7be8bc50b482a1a9) (MIT) and vLLM (Apache-2.0), with their licenses. No code is taken from #44406 or #44407.
- Review: the RFC migration is the last six commits, from `32e567e667`. `863fc1caff` and `0b265fdac8` are pure renames. The earlier commits are the first version of this PR and merges of main.

## Accuracy Tests

MI355X, TP4, image `rocm/sgl-dev:v0.5.21-rocm720-mi35x-20261009`, the cookbook section 3.6 recipe (DSpark block 5, Engram host table `per_rank`, `--enforce-shared-experts-fusion`, `--enable-decoder-swa-bounded-replay`), run with `validate.py`. Requests are sent 8 at a time, so every verify step runs on the monokernels.

End to end, switch on against switch off:

| Check | Switch on | Switch off |
|---|---|---|
| GSM8K, 500 questions | 0.898 | 0.890 |
| NIAH, 64k and 128k tokens, 3 depths each | 1.0 | 1.0 |
| KL of decode logprobs | 0.0174 (on vs off) | 0.0123 (switch off, batch 8 vs batch 4) |
| DSpark accept length, 8 requests | 3.32 | 3.39 |

- Pass rules: GSM8K within 1 point of switch off; KL at most twice the switch-off noise plus 0.001 (0.0256); accept length at most 3 % lower (here 2.3 %, from 26 and 25 log lines).
- A separate decode-only run (no DSpark, no host table) scored 0.915 on 200 GSM8K questions with the switch on. It also checked the 48-row limit: 48-row steps ran on the monokernels and larger steps (56 and 64 rows) on the normal path, with the same answer.

GPU kernel and fail-stop tests:

| Test | TP2 | TP4 |
|---|---|---|
| FFN and K1 kernels against the test's reference, 22 widths | Passed | Passed |
| Graph replay: FFN 500 replays with 0 mismatches; K1 bit for bit against eager | Passed | Passed |
| Memory allocated during graph capture and replay | 0 bytes | 0 bytes |
| Fail-stop: a wait stalled on purpose, at each site, in the first and the fourth launch | 2 of 2 (1 site) | 28 of 28 (all 14 sites) |
| Fail-stop while serving: a stall in the last layer | - | Passed |

- The 22 widths are the 15 that a server builds plus 7 odd sizes.
- In the serving fail-stop, the server stops, and all 64 tokens it sent match the answer without the fault.
- Reproduce: `python3 test/manual/monokernels/validate.py --model <path> --tp 4` runs every check above; `--steps` picks a subset.
- These runs used an earlier build of this branch. Its runtime code differs from this head only in the `ffn.residual` bound (2^-7, now 2^-6).
- Pending (we will update this description when they finish):
  - Set the `ffn` output bound against SGLang's normal path (RFC section 10). It is still set against the test's reference.
  - Merge current main, then rerun every check above on that head, with GSM8K on all 1,319 questions. #43607 moved the DeepSeek-V4 layer loop that our model seams use, so two files conflict now.

Thanks @rkarhila-amd good questions!

On the code location: AMD maintainers have been careful with PRs that touch common code, so I kept this self-contained on purpose. Apart from some minor changes in `environ.py` and `deepseek_v4.py`, it's all new code under `deepseek_common/amd/` plus tests, and it's off by default. It's the same layout vLLM merged in vllm-project/vllm#60397. The reusable part is already split out in `dsv41_mono/common/` (from ROCm/ATOM's `atom/mono`). When a second model's mono kernels come to SGLang, we can move it to a shared AMD folder in a small follow-up PR. vLLM is starting to do the same.

On other GPUs: this PR is gfx950 only and stops at startup with a clear error elsewhere, so gfx942 users see no change. gfx942 is possible but needs a port, and vLLM has a draft for it (vllm-project/vllm#60731). With 64 KB of LDS instead of 160 KB, it takes up to 42 rows instead of 48, runs at TP4 only and adds a few kernels. We can bring it over as a follow-up PR. For gfx1250, I'd wait: these kernels are built for fixed shapes and tuned per chip, so a small separate PR once the hardware and FlyDSL support are ready is cleaner.
