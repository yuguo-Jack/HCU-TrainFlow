# [Perf] Check tool parameter schemas with jsonschema-rs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43274) · state: open · merged: False

## Original PR description

## Motivation

The chat endpoint checks each tool's `parameters` against the JSON Schema 2020-12 metaschema on every request, on the API server's event loop. `Draft202012Validator.check_schema` is pure Python and takes about 0.7 ms per tool, so an agent that sends 18 tools adds 12 ms of blocking CPU to each request.

#42213 adds a cache and skips the check for schemas it has already seen. This PR instead makes the check itself about as fast as a cache read, so a new schema is fast too and no cache is needed.

## Modifications

- Check tool parameters with a `jsonschema_rs.Draft202012Validator` built once at import.
- Check `pattern` regexes and `$ref`/`$id`/`$schema` URIs with `check_schema`'s Python format checker.
- Add `jsonschema-rs==0.58.6` (MIT, prebuilt wheels) to every `pyproject`.
- Error messages keep the same form: the failing value, the keyword, and the location in the schema.

## Accuracy Tests

Model inputs and sampling are unchanged. On 41,559 schemas (edge cases, two fuzzers over real agent tool schemas, and nesting up to the HTTP body limit), the new check accepts and rejects the same schemas as `check_schema`, except schemas nested past Python's recursion limit (about 98 levels), which it accepts.

## Speed Tests and Profiling

Checking the 18 tool schemas of a coding agent, median of 5,000 runs on one thread:

| | check_schema | jsonschema-rs |
|---|---|---|
| 18 tools | 12.6 ms | 0.06 ms |

End-to-end: Qwen3-8B on one H100, streamed chat with a cached 11K-token prefix (system prompt and the 18 tools) and 32 output tokens. One server ran both checks, alternating in blocks over 10 rounds per concurrency.

| Concurrency | TTFT p50 before (ms) | TTFT p50 after (ms) | Change |
|---|---|---|---|
| 1 | 58.4 | 34.9 | −40% |
| 4 | 90.8 | 59.8 | −34% |
| 16 | 436.4 | 87.2 | −80% |

At 18 tools and c=1 the saving matches the check cost (about 40 ms). Your Qwen3-8B saving (23.5 ms) is about 2x your 12.6 ms, and I didn't reproduce or explain that.

I fuzzed this against `check_schema` and probed real main and PR servers over HTTP. Beyond the deep nesting you documented, the only HTTP difference I found is that this PR rejects a trailing newline in `$anchor`, `$dynamicAnchor`, `$recursiveAnchor` or `$id`. On the gRPC bridge it also rejects NaN or Infinity in `maximum` or `minimum` and lone surrogates in keys or `pattern`. Invalid schemas still return 400 with the same prefix, and the text after the prefix changes.

On the default 8 MB stack the validator never overflowed at any depth `json.loads` can deliver. On smaller stacks it segfaults where main raises `RecursionError` (5,000 levels at 2 MB, 1,500 at 1 MB). orjson caps HTTP near 1,024 levels, but the bridge has no cap. I found nothing in the repo that shrinks the stack, so I'm only noting it.

Packaging looks fine. 0.58.6 is MIT with no runtime dependencies, and has abi3 wheels for manylinux x86_64, i686 and aarch64, musllinux x86_64 and aarch64, macOS and Windows, plus an sdist. There are no ppc64le, riscv64 or s390x wheels. The aarch64 glibc 2.28 floor isn't new, since the latest tiktoken and llguidance wheels are already at 2.28 and 2.31. It adds 14 MB on disk, 11.6 ms of import and 7.8 MB of RSS.

The chat validation, schema normalization, gRPC bridge and tool-calling server tests found no regressions on the merged tree.

Not checked: a live gRPC client (bridge results come from calling `_validate_request` directly), running anywhere but Linux x86_64 on Python 3.12 (other platforms got wheel listings or `pip download` only), multiple API or tokenizer workers, your Qwen3-8B setup and schema corpus, and the security history of jsonschema-rs or versions after 0.58.6. For #46818 I only measured timing and read the diff.
