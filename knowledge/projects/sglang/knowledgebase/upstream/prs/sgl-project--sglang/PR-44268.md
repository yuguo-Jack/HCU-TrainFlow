# [Fix] moe: Fix --enable-fused-moe-sum-all-reduce outside CUDA and with LoRA hooks

[Upstream PR](https://github.com/sgl-project/sglang/pull/44268) · state: open · merged: False

## Original PR description

## Motivation

`--enable-fused-moe-sum-all-reduce` (#19672) moves the expert sum into the Triton down GEMM. The GEMM
`atomic_add`s every expert's output into `out_hidden_states`, and nothing is written to
`intermediate_cache3`. Two parts of `_fused_moe_kernel_sequence` still assume the unfused layout:

1. **The combine handles the fused case only under `_is_cuda or _is_musa`.** On HIP, XPU and the
   generic fallback, the combine then reduces `intermediate_cache3`, which the fused path never
   writes, over the top of the fused result. The output is garbage.
2. **The eligibility test ignores LoRA.** `hooks.after_down` adds the LoRA down delta to
   `intermediate_cache3`. The fused path never reads that buffer, so the delta is silently
   dropped. This happens **on every platform, CUDA included**.

Reproduction on MI355X, main@`16176278d0`:

```bash
sglang serve --model-path Qwen/Qwen3.6-35B-A3B --moe-runner-backend triton \
  --enable-fused-moe-sum-all-reduce
```

GSM8K is 0.00 %, and every answer runs to `max_tokens`:

```
"fh's朔zzeNUSNUS instant Freeman发现NU S instantNG__os__NGNG永康时刻NU..."   # Qwen3.6-35B-A3B
"!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!..."      # Kimi-Linear-48B-A3B
```

**Who hits it.** The flag is off by default, so default deployments are unaffected. With the flag
on, ROCm breaks every MoE layer that runs the generic Triton path with `topk > 2`:

- **The flag alone is enough** when the Triton runner is picked automatically. The bf16
  aiter CK MoE needs `intermediate_size / TP` to be a multiple of 128. gemma-4-26B-A4B
  (I = 704) therefore always runs Triton, and the cookbook's MI355X command is the plain
  `sglang serve --model-path google/gemma-4-26B-A4B-it`. The same applies whenever
  `SGLANG_USE_AITER=0`.
- **With `--moe-runner-backend triton`.** On dummy weights the broken combine was reached by
  Qwen3.6-35B, Kimi-Linear-48B, GLM-5.3 (fp8), MiniMax-M2.7 (fp8), Qwen3-Next-80B-FP8 and
  Qwen3.8-Flash-Next-FP8.
  - With `SGLANG_USE_AITER=1`, the block-fp8 checkpoints in that list produce garbage on main
    under `--moe-runner-backend triton` *even with the flag off*. `Fp8MoEMethod` pre-shuffles the
    expert weights for aiter whenever aiter is enabled, whatever the runner. Open #41636 fixes that
    separately.
  - The real-weight runs below therefore use `SGLANG_USE_AITER=0` for the fp8 flagships. There
    `auto` already picks the Triton runner, so the flag alone triggers this bug.
- **Not affected:**
  - layers on the aiter runner (the default for the other checkpoints probed);
  - Quark MXFP4, which refuses the Triton runner;
  - MXFP8 on gfx950, which uses `fused_experts_mxfp8` and never reads the flag.

For the LoRA half: MoE LoRA runs on the Triton runner, and since #39798 gemma-4's `moe.experts`
are LoRA targets.

## Modifications

`python/sglang/srt/layers/moe/moe_runner/triton_utils/fused_moe.py`:

- **The fused case is handled before the platform dispatch,** so no platform runs a combine
  over `out_hidden_states` once the down GEMM has summed into it.
  - Routed scaling stays whatever that platform's own combine did. The CUDA/MUSA, XPU and
    non-aiter HIP combines multiply by `routed_scaling_factor`.
  - aiter's `moe_sum` does not, because on the aiter path the router has already folded the
    factor into `topk_weights`. That contract is spelled out in `topk.py` (see #40584 and
    #41357).
  - CUDA/MUSA behaviour is unchanged: their branch is the same code, moved up.
- **The fusion is disabled when `hooks.after_down` is set.** The test is on the callback, not
  on `hooks` being truthy. `build_lora_hooks` returns an empty `LoRAHooks()` whenever no adapter
  is active, and in that case the fusion must stay on.

`test/registered/moe/test_fused_moe.py` gains `TestFusedMoeSumAllReduce`, which is already
registered for CUDA and AMD CI:

- Flag-on output must match the flag-off output on the same platform.
- The matrix covers routed scale None / 2.5, no hooks / empty hooks / an `after_down` hook, and
  token counts 5 / 37 / 333.
- It also asserts whether the fused down GEMM actually launched.

**What this PR does not change: speed.** On gfx950 the fused path is slower than the unfused one
it replaces (see below), so turning the flag on remains a bad trade on ROCm. That is a separate
question, and the PR leaves it alone. One option is `sem="relaxed"` on the epilogue atomic:
op-level it brings the path to parity, but it needs a CUDA measurement first. Another is to
refuse the flag on HIP, as the closed #19840 proposed. Whichever is chosen, the flag should not
silently return garbage.

Known gap: the generic fallback branch's `vllm_ops.moe_sum` does not apply the routed scale, but
the fused branch does. The Triton fused MoE is not expected to run on that fallback.

## Speed Tests and Profiling

**e2e, default flag-off path:**

- Model and command: gemma-4-26B-A4B-it with the cookbook command, TP=1 on one MI355X. Triton
  MoE was auto-selected, confirmed in the server log.
- Benchmark: `python -m sglang.benchmark.serving --dataset-name random --random-input-len 1937
  --random-output-len 389 --random-range-ratio 0.8 --num-prompts 307 --max-concurrency 61
  --seed 20261014`.
- Each arm ran as a consecutive block of 4 runs with a fresh server per run, in the order main →
  this PR flag-off → this PR flag-on. Run 1 of each block is discarded; the tables give the
  median of runs 2–4, with spread = (max − min) / median.
- Peak host load was ≤ 22.4 on 236 cores.

| metric | main | ± | this PR, flag off | ± | Δ |
|---|---:|---:|---:|---:|---:|
| Total tok/s | 13870.9 | 0.83 % | 13935.4 | 0.79 % | +0.47 % |
| Mean TTFT (ms) | 296.8 | 20.8 %¹ | 295.7 | 1.4 % | −0.4 % |
| Median TTFT (ms) | 112.8 | 1.5 % | 113.7 | 5.7 % | +0.8 % |
| Mean TPOT (ms) | 24.14 | 0.91 % | 24.20 | 0.79 % | +0.25 % |
| Median TPOT (ms) | 24.82 | 0.28 % | 24.86 | 0.76 % | +0.16 % |

¹ main's run 4 had a TTFT tail (P99 2053 ms vs ~1735 ms in the other runs); median TTFT is flat.

No regression on the path everyone runs. Op level, with the flag off, this PR matches main to
within ±0.07 % at every shape and is bit-exact.

**With the flag on (for the record, not a goal of this PR).** Same benchmark, this PR:

- 5589 tok/s, −59.7 % against flag-off.
- Median TPOT 62.7 ms (+152 %), median TTFT 280 ms (+148 %).

Op level (`fused_moe`, Qwen3.6 shape E=257 H=2048 N=1024 topk=9 bf16, T = 5 … 3300):

- The fused path is 2.9–6.0× slower than unfused, and 1.6–2.2× slower on the GLM-5.3 block-fp8
  shape.
- The compiled gfx950 ISA shows why. The packed `atomic_pk_add_bf16` is fine, but the default
  `acq_rel` semantics bracket it with a `buffer_wbl2` and a `buffer_inv` of the L2 in every
  workgroup.

On ROCm this flag should stay off until that is addressed.
