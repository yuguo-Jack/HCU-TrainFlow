# [Fix] function_call: Reject complete invalid Qwen JSON tool calls

[Upstream PR](https://github.com/sgl-project/sglang/pull/47986) · state: open · merged: False

## Original PR description

## Motivation

A complete tool call can disappear when the model emits invalid JSON under `--tool-call-parser qwen` / `qwen25`. Non-streaming parsing logs the JSON error and drops the call; streaming treats it as unfinished input. The OpenAI layer can consequently report a successful stop with no tool call, leaving an agent's requested action undone.

This was found during a **synthetic OpenCode deployment experiment**, not a production-user trace.

<details>
<summary>Deployment evidence and reduced reproduction</summary>

Environment: SGLang 0.5.21, one RTX PRO 6000 Server Edition 600W, `ProCreations/Nanbeige4.3-33B-NVFP4-A16`, DFlash draft, FP8 KV cache, 524288 context limit. The selected parser was `qwen`; chat-template options included `tool_call_format="json"` and thinking enabled. Tool grammar constraints were disabled.

In the 2026-11-02 21:06 UTC synthetic test, OpenCode 2.0.30 completed two reads, performed no edit or shell check, emitted zero error events, and exited 0. The fixture assertions failed. Its second parsed response contained:

```json
{
  "content": "Both files are read. Now I'll edit `greeting.py` to implement the required behavior",
  "tool_calls": [],
  "finish_reason": "stop",
  "done": true
}
```

A **separate native-generation replay of the captured prompt** produced a complete XML-style `edit` call despite the JSON template setting. This is a separate generation, not a byte-identical capture of the parsed response above. It motivates the deterministic reproduction; it does not prove that the original generation contained exactly the same bytes.

Reduced synthetic payload, included in the tests:

```text
I'll edit the file.
<tool_call>
<function=edit>
<parameter=text>synthetic payload</parameter>
</function>
</tool_call>
```

With an `edit` tool declared, current upstream silently returns no call for this payload. The patch raises `ToolCallParseError`. The same behavior is checked with malformed JSON and valid JSON followed by trailing garbage, so the fix is not specific to XML or Nanbeige.

The original replay artifact has SHA-256 `d1420e8c86eba9545bd1958e51a1ed58f8ccbe50b592309f78da349b408d9447`. Only the reduced synthetic fixture and aggregate observations are shared; no deployment endpoints, credentials, or user transcripts are included.

</details>

## Modifications

- Reject JSON decoding failures only when both tool-call delimiters have arrived. Unterminated calls keep their existing truncation behavior.
- Validate streaming fragments independently of the base parser's consumable buffer. This catches trailing garbage even after valid arguments have already been emitted, without repeatedly joining the accumulated payload.
- Propagate a typed parser error through Chat Completions and Responses. Non-streaming requests return HTTP 500; Chat streams emit an error and `[DONE]`, and Responses streams emit `response.failed`, without a successful terminal event.
- Keep generated arguments out of the error message. Do not reinterpret XML, repair JSON, or change sampling/grammar settings.
- Add CPU-registered parser and API regressions, including every two-chunk split, one-character streams, mixed closing forms, literal tags and escaped quotes/backslashes inside arguments, a malformed call after a valid call, and valid/truncated controls.

Already emitted streaming deltas cannot be retracted. Clients should treat the error as a failed response; this change does not provide transactional tool execution.

Related: #26793 proposes accepting Qwen XML via a different parser. This PR instead makes a complete payload that violates the selected JSON format an explicit error. #41039 addresses flushing valid calls at stream end; this PR leaves `finish()` unchanged.

The newline-free closing-tag regression raised in [review](https://github.com/sgl-project/sglang/pull/47986#discussion_r4448311934) is addressed in `7cf0b005d`. The validator recognizes both supported streaming closing forms while tracking JSON string/escape state across chunks. The mixed-closing regression fails on `33f63cb` and passes with the follow-up fix.

When a streamed Qwen call closes with `</tool_call>` immediately after its JSON (a form this detector explicitly handles via `end_token_without_newline`), this state machine waits only for `self.eot_token` (`\n</tool_call>`), so `_validation_parts` stays open. If another valid standard-form call follows, its closing tag causes the concatenation of both calls and the intervening tags to be passed to `json.loads`, producing `ToolCallParseError` and failing an otherwise valid response; the validator needs to recognize the alternate closing form while avoiding delimiter-like text inside JSON strings.
