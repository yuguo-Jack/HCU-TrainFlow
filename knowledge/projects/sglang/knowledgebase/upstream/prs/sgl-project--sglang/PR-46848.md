# [Fix] [Apple] mlx: Reject LoRA at startup

[Upstream PR](https://github.com/sgl-project/sglang/pull/46848) · state: closed · merged: False

## Original PR description

## Motivation

The MLX backend has no LoRA support: `MlxModelRunnerStub.initialize()` never calls `maybe_init_lora_manager`, so `model_runner.lora_manager` stays `None`. But `--enable-lora` (or `--lora-paths`) is still accepted on MLX. The server starts, and the first LoRA request reaches `Scheduler.can_schedule_lora_req`, which calls `self.tp_worker.model_runner.lora_manager.validate_lora_batch(...)` and crashes the scheduler with an `AttributeError` on `None`.

## Modifications

- Add a `validate_mlx_server_args` resolution step next to `handle_hardware_runtime_validation`. When MLX is enabled and LoRA is requested, it raises a `ValueError` that points to the standard Torch MPS path, which does support LoRA for dense models.
- It runs before the dummy-model return, like the other model-independent checks, and is added to the overridable hook list.
- `--enable-lora False --lora-paths ...` still passes, since the paths are ignored in that case.

## Accuracy Tests

Apple M2 Max:

- New `test_lora_is_rejected_at_startup` in `test/registered/unit/hardware_backend/mlx/test_runtime.py` covers `--enable-lora` and `--lora-paths`. It fails on `main` and passes with this change.
- `SGLANG_USE_MLX=1 pytest test/registered/unit/hardware_backend/mlx`: 227 passed.
- `test/registered/unit/server_args/test_resolution_hook_registry.py` passes.

I traced the crash from the code above rather than by launching a LoRA server on MLX.
