## Motivation

This PR implements part of https://github.com/sgl-project/sglang/issues/38902; rebase from https://github.com/sgl-project/sglang/pull/39944, https://github.com/sgl-project/sglang/pull/43851.

The companion storage PR persists DeepSeek-V4.1 C1/C2 Main KV in the 384-byte packed E2M1 layout requested in [#38902](https://github.com/sgl-project/sglang/issues/38902). This PR adds a Hopper consumer that reads those bytes directly inside FlashMLA's SM90 sparse decode kernel, alongside the existing SWA FP8 cache.

Enable the path explicitly with:

```bash
--dsv41-main-kv-layout packed_fp4 \
--dsv41-main-kv-consumer direct
```

The default `auto` configuration continues to use the existing layout and consumer.

<!-- Describe the purpose and goals of this pull request. -->

## Modifications

- Add the versioned `sparse_decode_fwd_mixed_v1` AOT binding and `flash_mla_with_mixed_kvcache` Python API for V4 SWA FP8 plus packed Main KV.
- Add a capability query and validate that the loaded extension supports the SM90 mixed-cache API.
- Link the SM90 head-64/head-128 mixed-cache instantiations from the pinned FlashMLA fork.
- Select the typed packed Main-KV view in attention and dispatch it to the direct consumer. Packed rows are decoded inside the kernel; no full-cache FP8 reconstruction is required.
- Keep existing sparse-prefill and SM100 attention dispatch for legacy layouts; packed Main-KV queries use the mixed consumer.
- Distinguish mixed and legacy scheduler metadata, including their cache formats. Pass the explicit SWA format to the legacy API.
- Require SM90 and the FlashMLA backend for `packed_fp4 + direct`; reject `staged`, mismatched layout/consumer choices, and unsupported hardware.
- Add reference-output, capability, runtime-gate, and CUDA Graph replay tests.

## Speed Tests and Profiling

Persistent Main-KV storage decreases from 585 to 384 physical bytes per compressed slot, a 34.36% reduction at the default page geometry.

The following latency ranges were reported in #39944 on H20 before the rebase:

| Batch size | Packed-direct latency change relative to legacy | Interpretation |
| --- | ---: | --- |
| 32 | -0.25% to +0.53% | Approximately parity under the measured conditions |
| 2 | +0.27% to +4.66% | Slower under the measured conditions |

Positive percentages mean increased latency. These figures have not been reproduced on the current commit. They do not establish current TPOT, total memory savings, or performance across the full context/batch matrix in #38902. A direct-versus-staged comparison is also outstanding. Keep `auto` on the existing path while current H20 measurements are pending.

With `packed_fp4 + direct`, this branch bypasses sparse prefill, but `_low_ratio_prefill_reads_page_indices()` still returns `False` for ordinary eager prefill with the default sparse-prefill flag enabled and no replay tail/request window.

The indexer then receives `out_page_indices=None` and only writes raw indices. The physical page indices remain initialized to `-1`, yet the mixed FlashMLA call consumes them as `main_indices`, masking out all Main KV entries.

Could we update the producer-side condition together with this dispatch change and add C1/C2 prefill integration coverage? The current kernel tests supply indices directly, so they bypass this issue.

Thanks, confirmed. The packed C1/C2 eager-prefill path bypassed sparse prefill and consumed physical page indices, while the producer gate still omitted them.

I fixed this by passing the layer into `_low_ratio_prefill_reads_page_indices()` and adding the packed-layout condition, so the producer now mirrors the mixed-path dispatch contract.

I added:
1. A packed-vs-non-packed gate regression test, verified red before the fix and green afterward.
2. C1/C2 SM90 eager-prefill integration coverage using the real low-ratio producer without seeding indices. It asserts that every entry within `topk_length` is non-negative, then checks mixed FlashMLA output against the combined reference.
