# [Perf] attention: Skip the triton MLA K rescale when k_scale is 1.0

[Upstream PR](https://github.com/sgl-project/sglang/pull/44457) · state: closed · merged: True

## Original PR description

## Motivation

For MLA, the triton backend divides K by `k_scale` before writing the KV cache, because `MLATokenToKVPool` takes no scale: a clone plus a divide on extend and an in-place divide on decode. Quark checkpoints create `k_scale` for every layer and leave it at 1.0 when there is no KV scale, so every layer divides by one.

## Modifications

When `k_scale_float == 1.0`, write K directly on both paths. A `None` `k_scale_float` keeps the divide. Non-MLA paths are unchanged. On extend, that direct write still goes through `kv_layers.layer(layer.layer_id).store` (the MLA pool's `set_kv_buffer`). It does not switch to `_set_kv_buffer`, which under DCP rewrites the location and passes a `dcp_kv_mask` that `MLATokenToKVPool.set_kv_buffer` does not take.

This touches the same extend block as #42181 (out-of-place divide) without overlapping it; the two are independent.

## Setup

Kimi-K2-Thinking-MXFP4, TP8, MI455X (gfx1250), image `rocm/sgl-dev:v0.5.22-rocm10-mi45x-20261019` (sglang ed0b8f433f; aiter 2bb549102 with Kimi-K2 GEMM configs).

Server: `--tp 8 --attention-backend aiter --prefill-attention-backend aiter --decode-attention-backend triton --page-size 64 --kv-cache-dtype fp8_e4m3 --disable-radix-cache --disable-custom-all-reduce --chunked-prefill-size 8192 --cuda-graph-max-bs-decode 128 --max-running-requests 128 --mem-fraction-static 0.8`. The checkpoint has no KV scales, so `k_scale` stays 1.0 with the fp8 KV cache. Before and after differ only by this commit on top of the image's sglang.

## Accuracy Tests

GSM8K with `few_shot_gsm8k` (8-shot, 1319 questions, `max_new_tokens` 512, the settings of sglang's AMD Kimi accuracy tests):

| | Accuracy | Invalid |
|---|---|---|
| Before | 0.941 | 0.000 |
| After | 0.939 | 0.000 |

Dividing by 1.0 does not change any value, so the difference is run-to-run variance of batched serving.

With `--prefill-attention-backend aiter` the extend change is never reached, so the extend path was checked separately with `--prefill-attention-backend triton --chunked-prefill-size 512` (512-token chunks so that later chunks of each prompt are extends with a prefix, which go through the triton MLA KV write): GSM8K 0.940, invalid 0.000. A `py-spy` sample during that run shows `forward_extend` on the new direct-write branch.

## Speed Tests and Profiling

TP8, 8k input / 1k output, concurrency 4, `bench_serving`:

| | Output tok/s | Median TTFT (ms) | Median TPOT (ms) |
|---|---|---|---|
| Before | 125.22 | 951.86 | 29.94 |
| After | 130.45 (+4.2%) | 946.31 | 28.93 (-3.4%) |

Decode profile at batch 4 (20 steps, per-step kernel time on rank 0): the elementwise bucket, which holds the divide, goes from 6.93 ms to 5.84 ms (-1.09 ms), matching the 1.0 ms TPOT drop.
