# [Perf] moe: Batch the TRT-LLM BF16 expert layout and index Qwen3.5 expert loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/47525) · state: open · merged: False

## Original PR description

## Why?

- A Qwen3.5-35B-A3B weight update (RL refit) loads about 31k per-expert tensors. On GB300's Grace CPUs, per-expert Python loops cost seconds of every update.
- The flashinfer TRT-LLM BF16 MoE stores experts in a row-permuted block layout. #33743 made refit work by undoing that layout before loading and redoing it after. Both directions loop over experts, with a few kernels and a clone per expert.
- Qwen3.5 MoE `load_weights` scans up to 768 expert mapping entries for every expert tensor, and checks `hasattr(self, "start_layer")` per tensor.
- On our internal sglang fork, these loops plus the expert-location lookup cost about 4.5 s of every update. The expert-location lookup is left to #45836.

## What?

- `_apply_trtllm_bf16_block_layout` and `_restore_trtllm_bf16_canonical_layout`: every expert of a weight shares one row permutation and one block shape, so convert 32 experts per launch with strided views instead of one expert at a time. Signatures are unchanged, and output is bitwise equal.
- Qwen3.5 MoE `load_weights` (both load paths): index the expert mapping once per call by its `experts.<id>.<proj>.` segment and look entries up by that segment. It returns the same entries in the same order as the scan. A name without that shape falls back to the scan. The layer range is read once per call.

## Verification?

```text
Qwen3.5-35B-A3B BF16, flashinfer_trtllm MoE, one weight update

Before: block layout undo/redo → a few launches per expert per weight
        expert mapping lookup   → scan of up to 768 entries × ~31k tensors
After:  block layout undo/redo → ceil(experts / 32) launches per weight
        expert mapping lookup   → one dict lookup per tensor                 (expected)
```

- A numpy simulation of the batched conversion matched main's per-expert path bitwise for 70, 33, 32 and 2 experts, including the restore: **observed** locally.
- A 200k-name fuzz matched the new lookup against the linear scan: **observed** locally.
- About 4.5 s saved per update was **observed** on our internal fork, together with an expert-location cache; not re-measured on main.
