# [Perf] speculative: batched top logprobs when every request asks the same k

## Motivation

With speculative decoding, `compute_spec_logprobs` returns the top logprobs as one GPU tensor slice per row, and there are `bs x num_draft_tokens` rows per step. Each step then pays one pinned allocation and one D2H copy per row in `GenerationBatchResult.copy_to_cpu`, and one `.tolist()` per row in the decode result path. For clients that ask for top-k logprobs on every token, this host-side work grows with batch size and draft length and slows the scheduler.

## Modifications

- `compute_spec_logprobs`: when every request in the batch asks for the same `top_logprobs_num = k`, keep the result as one `[rows, k]` value / index tensor pair from a single `topk(k)`. This is the same call `get_top_logprobs` makes (with `max_k == k`, its per-row `[:k]` slices are whole rows), so the values, ids and tie order are unchanged. Batches with mixed `k` keep the per-row path.
- `GenerationBatchResult.copy_to_cpu`: a `[rows, k]` tensor moves with one copy; a per-row list as before.
- `SchedulerBatchResultProcessor`: one helper converts either form to host lists of rows (one `.tolist()` for the tensor). The consumers keep indexing `top_logprobs_val[row]`.
- `LogitsProcessorOutput.next_token_top_logprobs_{val,idx}`: type comment updated.
- New CPU unit test `test/registered/unit/layers/test_logprob_processor_spec_top_logprobs.py`: the batched rows equal the per-row path bit for bit (greedy and temperature, ties, chain and `accept_index` layouts, k = 1, 5, 8, 32), and mixed-k batches keep row lists.

## Accuracy Tests

Identical outputs vs upstream main `8d4e1ce4c7` for a fixed batch composition, same GPU and container, `--enable-deterministic-inference`. The batched path makes the same `topk` call, so values, ids and tie order are unchanged for the same rows; across different batch compositions (concurrent requests landing in different batches) tied top-k entries (equal logprob) may come out in a different order, on main as on this PR. 1x GB300, `Qwen/Qwen3-30B-A3B` + EAGLE3 draft `Tengyunw/qwen3_30b_moe_eagle3`. Four concurrent batches of 6 prompts x 64 tokens: `top_logprobs_num` 5, 20, mixed 5/20/none, and 20 with temperature 0.7 + `sampling_seed`. Output ids, output token logprobs and top logprobs (values and ids) compared as JSON bytes.

| EAGLE3 layout | result |
|---|---|
| chain (`--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`) | identical, 24/24 requests (byte-identical dumps in our runs) |
| tree (`--speculative-num-steps 3 --speculative-eagle-topk 4 --speculative-num-draft-tokens 8`) | identical, 24/24 requests (byte-identical dumps in our runs) |

## Speed Tests and Profiling

1x GB300, same model and chain EAGLE3 config, default server flags. Arms in order main, PR, PR, main; 2 runs per launch.

```
python3 -m sglang.benchmark.serving --backend sglang --dataset-name random-ids \
  --random-input-len 512 --random-output-len 256 --random-range-ratio 1.0 \
  --num-prompts 320 --max-concurrency 64 --seed {1,2} --return-logprob --top-logprobs-num 20
```

| | output tok/s (median of 4) | median TPOT (ms) | median TTFT (ms) | accept length |
|---|---|---|---|---|
| main `8d4e1ce4c7` | 1627.4 (1584.1-1648.7) | 31.26 | 583 | 1.35 |
| this PR | 2034.2 (2024.0-2053.0) | 27.03 | 318 | 1.35 |
| change | **+25.0 %** | -13.5 % | -45 % | same |

Same command and arms on 1x H100 80GB (x86 host):

| | output tok/s (median of 4) | median TPOT (ms) | accept length |
|---|---|---|---|
| main `8d4e1ce4c7` | 1517.5 (1515.3-1537.3) | 33.0 | 1.35 |
| this PR | 1497.8 (1489.4-1520.2) | 34.2 | 1.35 |
| change | -1.3 % (run spread overlaps) | | same |

The gain is on the GB300 host (Grace CPU), where the per-row host work bounded the scheduler; on the H100 node the host was not the bottleneck and there is no measurable change.
Requests without logprobs, or batches whose requests ask different `k`, run the same code as before.

Not tested: pipeline parallelism. With PP the field now crosses stages as one tensor in the PP proxy dict instead of a list of tensors; no PP run was made.
