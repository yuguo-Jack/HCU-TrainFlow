# [Fix] disaggregation: Slice GDN conv state per head when TP exceeds key heads

[Upstream PR](https://github.com/sgl-project/sglang/pull/46357) · state: open · merged: False

## Original PR description

## Motivation

`compute_mamba_state_slice_blocks` (shared by the NIXL, Mooncake and MORI PD backends) slices each GDN conv sub-block (`cat([q | k | v])`) as `full_dim // tp`. That is only correct when the TP size divides the head count. GDN key heads (the q and k rows) are 16 on Qwen3-Next / Qwen3.5. At attention TP 32 or 64 they are replicated: rank `r` holds key head `r // (tp // 16)`, which is the layout `Mamba2StateShape.create` sizes via `extra_groups_for_head_shards`. The local q and k sub-blocks are then one head wide, not `key_dim // tp`. The `use_subdims` check (`sum(groups) == src_dim * tp`) fails, and the code falls back to one contiguous slice that straddles q/k/v and delivers the wrong channels. Nothing raises.

This affects any prefill/decode pair where either side's attention TP is larger than the number of key heads.

## Modifications

- `conv_shard_groups` entries may now be `(full_dim, num_heads)` pairs as well as bare full dims.
- `compute_mamba_state_slice_blocks` slices each sub-block on head ranges. It writes the overlap of the prefill rank's heads with the decode rank's heads, and uses the same replication rule as the state shape. In aggregation (prefill TP > decode TP), a replicated head is written only by the first writer of the decode rank.
- A bare full dim is treated as "every channel is a head", which reproduces the previous blocks exactly when the TP sizes divide the dim. The new test checks this.
- `Qwen3NextConfig.mamba2_cache_params` declares `(dim, heads)` for its q/k/v sub-blocks. Behavior is unchanged for TP ≤ 16.

## How it was found

We are writing an out-of-tree Neuron/Trainium platform plugin and serve Qwen3.5 with GDN TP up to 64. A CPU harness compared upstream's slice math with a reference implementation on synthetic GDN states. With bare dims (current behavior), **38 of 66** heterogeneous (prefill TP, decode TP) pairs across three head configurations deliver wrong data or mis-sized blocks. All 38 have TP larger than the key-head count on one side.

Note: as far as I can tell, the in-tree Qwen3-Next model (`num_k_heads // attn_tp_size`) does not run GDN with attention TP > `num_k_heads` today. So the bug is reachable from out-of-tree models and from any future in-tree support. The state-shape helper already handles the replicated case; only PD slicing did not.

## Open questions

- Encoding: I extended `conv_shard_groups` entries to optional `(dim, heads)` pairs so the backends pass them through unchanged. The alternative is a parallel `conv_shard_heads` list plumbed through `KVArgs.state_conv_shard_groups` and the three backends. Which do reviewers prefer?
- Should the Kimi linear-attention groups (`[proj_size, proj_k_size, proj_k_size]` in `mamba_utils.py`) also declare head counts?
- Temporal state still assumes TP divides the value-head count (true for all current GDN models).
