# [Refactor] Spec: Resolve the ragged-verify graph tier at a single point

[Upstream PR](https://github.com/sgl-project/sglang/pull/34038) · state: closed · merged: True

## Original PR description

The graph tier (token-source selection, floor, round-up-to-grid) was derived independently in `_ragged_verify_layout` and `_budget_aligned_to_graph_tier`, kept consistent by comment; the decode graph runner re-derived it a third time at replay and asserted it matched the layout. Extract `_resolve_verify_tier` as the single derivation point (returning a `VerifyTierResolution`), and make the runner read the tier off the layout instead of recomputing it. No behavior change. Stacks on #34031.

- claude[bot] · comment · 2026-10-29T00:51:52Z · [source](https://github.com/sgl-project/sglang/pull/34038#discussion_r4407622404)

File: `python/sglang/srt/speculative/dspark_components/dspark_planner.py` · line 536

🔴 Compact-mode DSpark verify batches that exceed the captured CUDA-graph grid now crash with a ValueError instead of falling back to eager. `_resolve_verify_tier` calls `round_up_grid` on the floor before `schedule_layout` reaches the `ragged_layout_exceeds_captured_grid` check (dspark_planner.py:438). `round_up_grid` raises when the floor is above `capture_num_tokens[-1]`. Fix: the helper should return `graph_num_tokens=None` (or flag that it exceeds) when the floor is past the grid's top tier, rather than raising. That keeps the layout path's `return None` eager fallback, and also covers the budget path at line 482.

<details>
<summary>Why this was flagged</summary>

Trigger: COMPACT ragged verify with confidence scheduling (not verify-all) and bs > the runner's max_bs = max(capture_bs). This is reached via dspark_worker_v2.py:1098 `schedule_layout`, for example when max-running-requests is above cuda-graph-max-bs. With no tier hint (DP attention on with no gathered tier, or budget None), the floor is bs*verify_num_draft_tokens, which is above grid[-1]. The new helper calls round_up_grid at dspark_planner.py:533. That raises ValueError "total ... exceeds max grid tier" (ragged_verify.py:37-41) and kills the verify step. The same happens when a large budget pushes the dynamic or DP tier past grid[-1]. On the base branch, the layout path ran ragged_layout_exceeds_captured_grid first and returned None (eager fallback). It only called round_up_grid afterwards, so it could never raise. That check now runs after the helper, too late to help. The old budget path also rounded without the check, but only when speculative_dspark_align_verify_tokens_to_graph_tier is on (off by default). So the regression hits the default config.

**Verification:** `schedule_layout` now calls `_resolve_verify_tier` at dspark_planner.py:432, before the `ragged_layout_exceeds_captured_grid` check at :438. `round_up_grid` (ragged_verify.py:37-41) raises `ValueError` when `total > grid[-1]`. On the base, the exceeds check ran first and returned None, which meant an eager fallback.

</details>
