# [Perf] [XPU] mrope: Keep M-RoPE decode deltas on device and drop per-layer GDN fills

[Upstream PR](https://github.com/sgl-project/sglang/pull/47265) · state: open · merged: False

## Motivation

While profiling Qwen3.8-27B (hybrid GDN + full attention, M-RoPE) on 4x Intel Arc Pro B70 with the decode XPU graph enabled, we found that multimodal requests decode about 0.5 ms/token slower than text-only requests with the same context length. The GPU kernel time per step is the same in both cases, so the gap comes from host-side work outside the graph replay.

There are two sources of overhead:

1. **M-RoPE decode positions are rebuilt on the host every step.** `_compute_mrope_positions_decode` collects one Python int per request and calls `torch.tensor(..., device=...)` on every decode step. On an in-order queue, this blocking H2D copy waits for the previous step to finish, so the overlap scheduler cannot prepare batch N+1 while batch N is running. Text-only requests do not take this path, which is why only multimodal decode is affected.
2. **The XPU fused GDN decode fills a mask in every layer.** `XpuGDNAttnBackend.forward_fused_gdn` allocates `torch.ones(bs, dtype=torch.bool)` in every linear-attention layer. This mask is constant, but it is recorded into the decode graph, so every replay launches one fill kernel per GDN layer (48 per step for Qwen3.8-27B).

## Modifications

- **`MultimodalInputs` / `ForwardBatch`:**
  - Add `MultimodalInputs.get_mrope_position_delta_on_device()`. It caches the per-request M-RoPE delta as a device tensor the first time it is needed.
  - The cache is invalidated together with the existing `mrope_position_delta_repeated_cache` whenever a session turn rewrites the positions.
  - `_compute_mrope_positions_decode` now builds the batch deltas from these device tensors (a slice for `bs == 1`, otherwise `torch.cat`) instead of host ints. The integer arithmetic is unchanged, so the resulting positions are bit-identical.
- **`XpuGDNAttnBackend`**
  - Allocate the all-true `has_initial_state` mask once at backend init, sized to the request pool, and slice it during decode.
  - If a batch is larger than the pool, fall back to allocating a new tensor as before.

No behavior change is intended, and no new flags or environment variables are added.

## Accuracy Tests

The M-RoPE change only moves the same int64 arithmetic (`delta - 1 + seq_len`) from host to device, and the GDN change replaces a freshly allocated all-true mask with a persistent all-true mask. Neither change alters any numerical value fed into the model.

We compared greedy outputs (`temperature=0`) between upstream `main` and this branch, running both in the same image:

| Workload | baseline vs. patched | patched vs. patched (rerun) |
|---|---|---|
| 1080p image + 32K text, 5 requests, 1K output | identical | identical |
| 1080p image + 16K text, 5 requests, 1K output | differs | **also differs** |

On the 16K workload, two runs of the *same* patched build also diverge from each other. The prompts are random tokens, which gives near-flat logits, so run-to-run floating-point nondeterminism is enough to flip the argmax. The divergence therefore does not come from this change.

## Speed Tests and Profiling

**Setup:**
- Hardware and parallelism: Qwen3.8-27B (bf16), TP4 on 4x Intel Arc Pro B70.
- Version: upstream `main` @ `019008afe0`.
- Workload: concurrency 1, one 1080p image plus 16K or 32K text, 1K output tokens.
- Method: baseline and patched builds were run in the same Docker image, swapping only the changed files; each configuration was run twice and the two runs differ by less than 0.02 ms TPOT.

Server:

    sglang serve --trust-remote-code --device xpu --model-path Qwen3.8-27B --tp 4 \
      --attention-backend intel_xpu --linear-attn-backend intel_xpu \
      --disable-radix-cache --disable-custom-all-reduce \
      --context-length 40960 --max-running-requests 1 --mem-fraction-static 0.55 \
      --chunked-prefill-size 8192 --max-prefill-tokens 16384 \
      --cuda-graph-backend-decode full --cuda-graph-bs-decode 1 \
      --cuda-graph-backend-prefill disabled

Client:

    python -m sglang.benchmark.serving --backend sglang-oai-chat \
      --dataset-name image --image-count 1 --image-resolution 1080p \
      --random-input-len {16384,32768} --random-output-len 1024 --random-range-ratio 1.0 \
      --num-prompts 5 --max-concurrency 1 --warmup-requests 1

Results:

| Workload | Metric | Baseline | + M-RoPE on device | + GDN mask reuse | Change |
|---|---|---|---|---|---|
| image + 16K | TPOT (ms) | 27.57 | 27.02 | **26.96** | **-2.2%** |
| | E2E latency (s) | 31.48 | 30.92 | **30.86** | **-2.0%** |
| | Output throughput (tok/s) | 32.53 | 33.12 | **33.18** | **+2.0%** |
| | TTFT (ms) | 3278 | 3273 | 3277 | unchanged |
| image + 32K | TPOT (ms) | 28.05 | 27.53 | **27.47** | **-2.1%** |
| | E2E latency (s) | 35.04 | 34.50 | **34.44** | **-1.7%** |
| | Output throughput (tok/s) | 29.22 | 29.68 | **29.73** | **+1.7%** |

Profiling notes:
- Eager-mode profiling with `--profile-activities CPU XPU` shows about 26.4 ms of GPU kernel time per decode step, the same for multimodal and text-only requests.
- Before this PR, multimodal decode spent about 1.2 ms per step outside kernels, versus about 0.6 ms for text-only; after this PR the two match.
- `FillFunctor<bool>` (48 launches per step) no longer appears in the decode step.
- The M-RoPE change also applies to non-XPU backends; it has not been benchmarked on CUDA.
