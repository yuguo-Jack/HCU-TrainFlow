# [AMD] DeepSeek-V4.1: route decode MXFP8 dense GEMMs above 8 rows to aiter on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/42499) · state: closed · merged: False

## Original PR description

At decode batch sizes above 8 rows, aiter's MXFP8 GEMM is faster than the native MXFP8 GEMV for several DeepSeek-V4.1-Flash dense projections (for example 6.1 us against 10.8 us for the fused q / kv down projection at 32 rows). This draft routes those shapes to aiter above 8 rows and keeps the native GEMV for small batches. The two K = 1280 projections stay on the native GEMV, because aiter's blockscale GEMM returns NaN for them at some row counts.

- Measured with a prototype before #42055 (MI355X, tensor parallel on 4 GPUs, no speculative decoding), at 32 concurrent requests: output throughput +3.5% and median inter-token latency 4.8% lower on the image of 2026-10-01, +4.8% and 5.5% lower on the image of 2026-10-02; no change at 4; GSM8K accuracy within 0.2 points.
- Re-measured on current main (with the FP8 producer inputs of #42055): aiter is still faster on all five shapes above 8 rows, for example 10.7 to 5.9 us for the fused q / kv down projection at 32 rows. The route needs a second, plain copy of these weights for aiter (about 1 GB per GPU with shared-expert fusion on), because the native Triton GEMM is slower than the GEMV at 9-32 rows. aiter also returns Inf / NaN for the fused q / kv down projection at 1, 2 and 5-8 rows, which the 8-row threshold avoids.
- Conservative expectation on current main: about 1.5% higher output throughput at 32 concurrent requests with shared-expert fusion on, no change at 4.
- Status: draft without code.
