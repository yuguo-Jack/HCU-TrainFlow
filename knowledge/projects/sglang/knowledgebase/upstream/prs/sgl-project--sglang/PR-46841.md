# [Fix] dsa: avoid KPool JIT specialization by page-table width

[Upstream PR](https://github.com/sgl-project/sglang/pull/46841) · state: open · merged: False

## Original PR description

## Motivation

Fixes #39453.

The DSA KPool decode kernel passes `block_tables.shape[1]` as `BLOCK_TABLE_COLS: tl.constexpr`. The eager decode path creates a different Triton specialization for each page-table width encountered at runtime, so ordinary requests can accumulate one compiled binary per reachable width. The bound is large for long-context models and the extra compilation occurs after the server is ready.

## Modifications

- Pass the page-table column count as a runtime argument.
- Mark `block_table_cols` with `do_not_specialize` so Triton does not include the width in the JIT cache key.
- Add a CUDA regression test that exercises widths 1, 2, 11, and 17 and checks that they share one specialization.

The clamp remains unchanged semantically; only the compile-time specialization is removed.

## Accuracy Tests

On an NVIDIA H200 NVL (PyTorch 2.14.0+cu130, Triton 3.8.0), I ran the original and patched kernel with the same deterministic random BF16/FP32 inputs. The resulting K cache bytes, tail K values, and tail scores were byte-identical:

```text
buf        equal=True  max_abs=0.0  nonzero_diff=0
tail_k     equal=True  max_abs=0.0  nonzero_diff=0
tail_score equal=True  max_abs=0.0  nonzero_diff=0
```

## Speed Tests and Profiling

I ran four widths (1, 2, 11, 17) against the same backing allocation, synchronizing after each launch. On the same H200 process:

| Version | Triton cache entries | Total first-sequence wall time |
| --- | ---: | ---: |
| Before | 4 | 2.7885 s |
| After | 1 | 0.7870 s |

The result establishes the cache-cardinality reduction. The totals include first-use JIT compilation; subsequent widths reused the compiled specialization in the patched run (0.0002--0.0005 s each). Steady-state kernel work is unchanged because the width is used as a runtime clamp value.

## Independent validation on the available H200

The available H200 NVL was also used for an independent validation with the local source snapshots. The environment for the output comparison and cache experiment was PyTorch 2.14.0+cu130 with Triton 3.8.0. With the same seeded BF16/FP32 inputs, the original and patched kernels produced byte-identical outputs:

```text
buf        equal=True  max_abs=0.0  nonzero_diff=0
tail_k     equal=True  max_abs=0.0  nonzero_diff=0
tail_score equal=True  max_abs=0.0  nonzero_diff=0
```

For widths 1, 2, 11, and 17, the original produced 4 Triton cache entries and took 2.7885 s for the first sequence; the patched version produced 1 entry and took 0.7870 s. The totals include first-use JIT compilation; subsequent patched widths took 0.0002--0.0005 s each. The registered CUDA regression test also passed in the available SGLang environment (PyTorch 2.13.0+cu130, Triton 3.7.1): `1 passed` in 9.26 s.
