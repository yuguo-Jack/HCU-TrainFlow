# [Feat] kv-indexer: Add event replay, worker liveness and indexer failover

[Upstream PR](https://github.com/sgl-project/sglang/pull/42449) · state: open · merged: False

## Original PR description

Reopened from #39822. GitHub closed that PR on 2 October when the fork it came from was deleted; its review history is still there.

## Motivation

Depends on #42447. This branch contains the three Valkey-backend commits followed by one consolidated event-plane commit.

`sgl-kv-indexer` documents what production high availability still lacks: "events published while a bridge is disconnected are not replayed", "a worker death is not detected", and "a future Snapshot plus event-replay mechanism is required before production high availability can rebuild state safely after restart or event loss". #42447 made the placement index shared and restart-safe; this PR closes the rest, so cache-aware routing survives the operational events a provider actually hits.

Three gaps, one at a time:

1. **The bridge needs an indexer to be up.** A bridge sends `ApplyExternalKvBatch` to exactly one server. Batches sent while that server is restarting are lost, and nothing replays them.
2. **A bridge outage loses events.** The worker keeps a replay buffer and a ROUTER socket to serve it (`ZmqEventPublisher._service_replay`), which nothing in the bridge used.
3. **A dead worker keeps its placements.** The router keeps sending prefix-affine traffic to a worker that is gone, and to a restarted worker whose cache is empty.

## Modifications

**Event log on Valkey Streams (`src/stream.rs`).** `KV_INDEXER_SINK=stream` makes the bridge `XADD` each decoded batch to `<prefix>events` (`MAXLEN ~`, configurable) instead of calling one indexer; `KV_INDEXER_EVENT_SOURCE=stream` makes indexers consume it through a consumer group. The keyspace is the snapshot, the stream is the replay window, so a restarted or newly added indexer needs nothing from anyone and a bridge never needs an indexer to be up.

Applies are idempotent but not commutative (a REPORT and a later REVOKE of the same block must land in that order), so consumers of the shared group run under a lease, one per group (`SET NX PX`, renewed at a third of its TTL by a compare-and-set on the holder name). One applies, the others stand by and take over inside one TTL. The holder renews as it works rather than once per batch and stops applying the moment the lease is gone, so a batch that outlasts the TTL cannot interleave with the next holder; the new holder drains the previous one's whole pending list with no idle-time floor before reading anything live, because a REPORT reclaimed after the REVOKE that followed it would leave the block present forever. A group that disappears under a running consumer (a flushed or restored Valkey) is recreated from the oldest retained entry instead of retrying NOGROUP forever. Entries are never lost while they sit in the stream, only delayed. Delivery is at-least-once and applies are idempotent; a malformed or rejected entry is acknowledged and logged, exactly as the bridge already treats an undecodable batch, while a transient failure leaves the entry pending and is retried in order.

An in-memory indexer with `EVENT_SOURCE=stream` uses a private group created at `0` and dropped on exit, so it rebuilds its index from the retained window on every start; a private group an unclean exit left behind is dropped and recreated rather than resumed where it stopped. A shared group is created at the tail because the keyspace is the snapshot, except over an empty keyspace, where it starts at the oldest retained entry: on a first deployment the tail would skip whatever the bridges published before the first indexer existed. `KV_INDEXER_CONSUMER_GROUP` and `KV_INDEXER_STREAM_START` expose the same mechanism for a deliberate rebuild into an empty keyspace.

**Worker replay and restart hygiene (`src/bridge.rs`).** With `SGLANG_KV_REPLAY_ENDPOINT` set, the bridge speaks SGLang's replay protocol: on connect and whenever the live sequence shows a gap it asks the worker's ROUTER for everything after the last sequence it forwarded and applies it before live events. A sequence that goes backwards means the publisher restarted with an empty cache, so the bridge emits `AllBlocksCleared` for that worker before the new events, mirroring what the router's own pump does with `PublisherReset`. The last forwarded sequence is checkpointed at `<prefix>seq:<worker>` when a Valkey configuration is present, so a restarted bridge replays the gap instead of the whole buffer.

**Worker liveness (`src/liveness.rs`).** The bridge writes `<prefix>alive:<worker>` with a TTL and refreshes it at a third of the TTL, gated on a TCP connect to the worker's own address while one is configured, and sets a `<prefix>hb:<worker>` marker so a bridge without heartbeats is never mistaken for a dead worker. Turning the heartbeat off deletes both keys, since a marker with nothing refreshing it behind it would read as a worker that died. A Valkey-backed indexer clears a marked worker whose key expired, through the normal apply path (`CLEAR_ALL_AT_TIER` at every tier, so hit counts, pruning and parity semantics all hold). Expiry arrives as a RESP3 keyspace notification, scoped to the database the URL selects; the indexer adds `Ex` to `notify-keyspace-events` when `CONFIG SET` is permitted and a periodic sweep over the worker set is the backstop for a managed service that refuses it, a missed notification, or a cluster node whose notification did not reach the subscriber.

A clear is deliberately conservative, because a clear of a worker that is still serving costs more than the stale placements it removes. A worker is cleared only while some other heartbeating worker is still alive: every worker looking dead at once is a Valkey event (a failover, a flush, a restore that brought back the markers but not the volatile heartbeats), and clearing the index in response would turn one incident into an outage. A worker whose heartbeat returned between the census and the clear keeps its placements. And a clear deletes that worker's `seq:` checkpoint, so the next bridge session replays its buffer from the start instead of resuming past events the index no longer holds. Size the TTL above a routine bridge restart: a bridge outage longer than the TTL reads as a worker death, which the README states.

**Router failover across endpoints (`src/config/cli.rs`, `sgl-kv-indexer/src/client.rs`).** Shared indexer state is only useful if the Router can reach another server, so `--kv-indexer-endpoint` now takes a list (space-separated or repeated) of interchangeable endpoints in preference order. The client queries the preferred one and moves to the next only while that one cannot answer: unreachable, shedding load, out of time, or a connection that broke mid-request, which arrives as a status a server could equally have sent and is told apart by the transport error attached to it. The endpoint that answered becomes preferred, so an outage costs one failover rather than a probe of a dead address on every query. A rejection is not a failover, since every server would reject the same request. The query deadline now bounds the whole query including failovers, so a longer list cannot make a slow query slower. One endpoint behaves exactly as before, and the endpoints must share state, which the README says.

Defaults keep every existing deployment on its current path: `KV_INDEXER_SINK=grpc`, `KV_INDEXER_EVENT_SOURCE=grpc`, no heartbeat without a Valkey URL. New key names are listed in the README's key table.

## Benchmarking and Profiling

Two SGLang workers (Qwen3-1.7B, one RTX 5090) behind `sgl-router --cache-prefix-provider indexer`, 8 tenants with about 7.8k-token system prompts, 6 concurrent clients. Alongside TTFT and the workers' prefix cache hit ratio, each run probes how many placements of that workload's block set the router's indexer can still answer for, which is what actually separates the backends.

**Restarting the indexer, and a rolling restart of the whole fleet.** With one endpoint configured, the in-memory index comes back empty (419 of 968 placements three seconds later) and 337 of 1,958 routing decisions had no cache candidate; the Valkey-backed index lost nothing (968 to 1,210, growing with the workload) with 12 of 2,135 blind, but still had one degraded window because a Router holding a single endpoint has nowhere to ask while that socket is down. Giving the Router both endpoints closes that: restarting both indexers one after the other moves no window at all, 0.99 hit ratio and p90 never above 73 ms throughout, 12 of 2,052 decisions blind, the same as steady state. The Router logs one failover per restart and nothing else changes.

**Rotating the fleet behind a stable address.** Killing the indexer the Router is not using and starting a new one: 10 of 1,992 decisions blind, hit ratio flat at 0.99, and the new server answers with all 968 placements five seconds after start because the state is in the keyspace. An added in-memory indexer would start empty.

**Worker restart (about 70 s down).** Right after the worker returned, the in-memory index still attributed 484 placements to it while its cache was empty; the Valkey-backed one had cleared it through heartbeat expiry and answered only for the live worker. Two honest caveats from the same runs: on a two-worker rig, clearing the dead worker concentrates every tenant on the survivor, so TTFT during the hole is worse (p50 1.0 to 3.3 s versus 0.5 to 0.9 s), and the returning worker's capacity ramps up as it re-reports rather than being assumed. Both are the desired behaviour where one worker is a small fraction of the fleet.

**Bridge outage (20 s).** No measurable difference over a steady tenant set: the index held 968 placements before and after in both modes, 9 and 10 blind decisions. Nothing new is published during the outage, so nothing is lost; flushing the worker's cache mid-outage does not change it either, since the same tenants re-store the same block hashes. The replay path is exercised in those runs (`resuming from the checkpointed sequence seq=13356`, then `replayed buffered KV event batches ... replayed=123`) and is covered deterministically by the tests; it pays off when the content changes while the bridge is away.

**Rebuild from the stream.** With the world frozen, the placement keyspace (2,230 keys, 1,251 block hashes) was deleted down to the stream alone and replayed from a 12,045-entry window by a fresh consumer group. The rebuilt index answers byte for byte identically over all 1,251 hashes, same per-worker split (630 / 621). That is the snapshot-plus-replay recovery the README asked for: the keyspace is the snapshot, the stream is the window.

## Limits

- A bridge outage longer than the heartbeat TTL reads as a worker death. Sizing guidance is in the README; the real fix is the worker publishing its own heartbeat, which needs an SGLang-side change.
- The lease bounds indexer takeover to one TTL, so a shared group's apply path pauses for up to that long when the holder dies. Entries wait in the stream; nothing is lost.
- The gRPC apply endpoint stays served while a server consumes the stream, and those applies are not serialized against the stream's lease. Point every bridge of one fleet at one sink; the server warns at startup. One group per index for the same reason: an in-memory indexer in a shared group acknowledges entries no other member will see.
- Cluster mode still keeps every key in one slot (the hash-tagged prefix), including the stream, so this is a capacity fit rather than sharding.
- `KV_INDEXER_STREAM_MAXLEN` is a retention window, not a full history: a rebuild recovers whatever the window still holds. The default 1M entries covered every event of a 12k-entry demo run, but it is a knob an operator has to size.
