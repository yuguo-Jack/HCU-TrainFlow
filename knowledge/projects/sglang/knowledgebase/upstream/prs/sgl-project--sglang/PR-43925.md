# [Rust] Refuse an unsupported multimodal model before the Rust listener binds

[Upstream PR](https://github.com/sgl-project/sglang/pull/43925) · state: closed · merged: True

## Original PR description

## Motivation

`RustServer.launch` constructed the Rust server, which binds the listen port and starts answering health checks, before `_start_multimodal` resolved the built-in multimodal pipeline. A multimodal model with no Rust pipeline was therefore refused only after the listener already reported healthy, so an orchestrator could route traffic to a process that was about to exit.

## Modifications

- `launch` resolves the pipeline first through a new `_resolve_multimodal` classmethod, before the server extension is constructed, so a refused model never accepts a connection.
- `_start_multimodal` only starts the Rust workers for the spec resolved up front. A model package whose `_start_multimodal` starts its own pipeline overrides `_resolve_multimodal` to return `None`.
- The `launch` thread-affinity comment names the threads a package's own `_start_multimodal` may create, since the built-in processor is no longer constructed there.

Tests, in `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py` (CPU, `base-a-test-cpu`):

- `test_launch_resolves_the_mm_pipeline_before_the_server_starts` asserts the server extension is never constructed when the model is refused, and that a supported model gets workers for the spec resolved before construction. It fails on main (the extension is constructed once before the refusal) and passes with this change.
- The patches `launch` reads move into a shared `launch_context` helper used by both cases.
