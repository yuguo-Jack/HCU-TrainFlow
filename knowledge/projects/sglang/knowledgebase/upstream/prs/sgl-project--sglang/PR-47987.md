# [Fix] unified-memory: Realize the reclaim certificate that relief opens on the tri-pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/47987) · state: open · merged: False

## Original PR description

## Motivation

On a Mamba + sliding-window model under `--enable-unified-memory`, a decode step could retract a request while the prefix cache held many evictable tokens.

The tri-pool chain's decode capacity check calls `ensure_capacity`, then evicts from the tree with `float_reclaim_satisfied` as the stop predicate: the tree skips eviction while the reclaim certificate (the END flushes, or a FLOAT high-side target) says the allocation can already be realized. `ensure_capacity` tries the END and FLOAT certificates once, and when neither holds it falls back to `relieve_for_alloc`. Relief flushes the ENDs and moves FLOAT pages, which can open a FLOAT certificate that was closed when it was checked, while still leaving the allocation short. `ensure_capacity` then returned False without realizing it; the eviction predicate held, so nothing was evicted, and the check failed with the cache full of evictable entries.

## Modifications

`ensure_capacity` (`mem_cache/kv/alloc/interim.py`, `_FloatChainPolicy`) now realizes the END or FLOAT certificate once more after a relief that falls short, through one helper, `_realize_token_certificate`, shared with the first attempt.

Test (CPU), `test/registered/unit/mem_cache/test_unified_tri_pool.py`: `test_a_failed_ensure_leaves_no_reclaim_certificate`: under seeded random admission, window-slide, finish and state-slot churn, with lazy and with eager compaction, every failed `ensure_capacity` leaves the reclaim certificate false and the byte accounting intact. On main it fails 10 cases (the same five states under each compaction mode); with this PR the whole file passes.
