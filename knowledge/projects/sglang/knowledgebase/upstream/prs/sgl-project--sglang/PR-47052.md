# [Perf] [AMD] qwen3: Fuse prefill QK-norm + RoPE on ROCm with the JIT qknorm_rope kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47052) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, Qwen3 prefill runs QK-norm and RoPE as five launches per layer: `apply_qk_norm` copies the strided q and k views of the packed qkv to contiguous tensors, runs two aiter RMSNorms, then `rotary_emb` launches `rotary_embedding`. The fused path in `apply_qk_norm` is CUDA-only. In a Qwen3-8B prefill profile on MI355X (batch 1/8, input 2048/8192, main `7fe5b127e4`) these kernels take 4.8% to 6.8% of GPU kernel time.

The diffusion JIT kernel `fused_inplace_qknorm_rope` already does this in one in-place launch (strided q/k, GQA, fp32 cos/sin cache table), but it does not compile on HIP: bare `__shfl_sync` with a 32-bit mask hits HIP's 64-bit-mask static_assert. So the ROCm path enabled in #35573 silently falls back to the unfused ops; the kernel's tests are registered for CUDA CI only. #40585 fixes the same shuffles for MiniMax-H3; this PR carries an equivalent fix so it does not depend on it. #47001 (open) adds the same in-place fusion for XPU through sgl-kernel-xpu, and #47785 (open) a CUDA prefill fusion; all three change `forward_prepare_native`, so whichever lands later needs a small rebase.

## Modifications

Scope: ROCm only. On HIP the kernel's NeoX variants with `round_norm_before_rope=True` now build. Two ROCm callers request them: Qwen3 attention, which also serves the models built on `Qwen3Model` (such as Qwen3-Embedding and InternVL) when the gate below accepts them, and ERNIE-Image, which keeps the fused kernel only if its first call matches its reference bit for bit. NeoX with `round_norm_before_rope=False` and KV packing stay off on HIP, so their callers, such as Cosmos3 video, keep the separate ops as on main. GPT-J variants, CUDA, XPU, NPU, and the aiter decode fusion are unchanged.

- `qknorm_rope.cuh`: on HIP, shuffle with `__shfl` / `__shfl_xor` at width 32 (the kernel's logical warp on wave64). CUDA builds are unchanged.
- `qknorm_rope_jit.py`: on HIP, `can_use_fused_inplace_qknorm_rope` returns False and a direct call raises `NotImplementedError` for the two variants without AMD numerical coverage, KV packing and NeoX with `round_norm_before_rope=False`.
- `models/utils.py`: add `can_use_jit_qk_norm_rope`, which gates on HIP, plain `RotaryEmbedding` with an fp32 cache, plain `RMSNorm` weights in the activation dtype, and no deterministic / on-policy / inductor prefill mode, and builds the kernel at init so it is never first built during graph capture; add `apply_qk_norm_rope`, which runs the kernel in place with `round_norm_before_rope=True` or falls back to `apply_qk_norm` + `rotary_emb`.
- `qwen3.py`: outside the CUDA decode branch from #46908, `forward_prepare_native` calls `apply_qk_norm_rope`. On ROCm it serves prefill / extend, and decode when the aiter decode fusion from #44267 does not apply.
- `test_qk_norm_rope_hip.py` (new, AMD CI): fused vs unfused path on strided views over head/rotary dims, GQA ratios, neox and GPT-J, 0 to 4096 tokens, fp16, int32 positions; the fused result must be no farther from an fp64 reference than the unfused one; the kernel gate rejects the two variants above on HIP; YaRN, mRoPE, eps mismatch, fp32 norm weights, deterministic and inductor fall back.
- `test_qknorm_rope_out_of_place.py`: register for AMD CI; skip the two-rows-per-warp comparison on HIP, which builds only the one-row-per-warp kernel.

## Accuracy Tests

MI355X (gfx950), torch 2.11.0+rocm10.0.0, sglang-kernel 0.4.10, aiter `285579b62`, `SGLANG_USE_AITER=1`, decode CUDA graphs on. `Qwen/Qwen3-8B` bf16, otherwise default server args. Base is main `7fe5b127e4`. GSM8K with `python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --temperature 0 --max-tokens 4096` (1314 questions after the 5 few-shot examples):

| Attention backend | Base | This PR |
|---|---|---|
| aiter | 0.9444 / 0.9422 / 0.9452 (mean 0.9439) | 0.9482 / 0.9475 / 0.9460 (mean 0.9472) |
| triton | 0.9467 | 0.9437 |

The fused kernel reads the fp32 cos/sin table, while the unfused HIP RoPE rounds it to bf16 first, so outputs differ by 1 to 2 ulp and are closer to fp64.

Unit tests, AMD CI (MI300X) on this head: [jit-kernel-unit-test-amd](https://github.com/sgl-project/sglang/actions/runs/41376859344/job/125059005167) runs `test_qk_norm_rope_hip.py` (128 passed) and `test_qknorm_rope_out_of_place.py` (1 passed, 12 skipped); [stage-a-test-1-gpu-small-amd](https://github.com/sgl-project/sglang/actions/runs/41376859344/job/125059005238) runs `test_qwen3_aiter_fused_qk_norm_rope.py` (decode path, 6 passed). With main's `qknorm_rope.cuh` the kernel fails to build for head_dim 128 neox, so `can_use_jit_qk_norm_rope` returns False and `test_qk_norm_rope_hip.py` fails at its gate assertion.

MI325X (gfx942), torch 2.11.0+rocm10.0.0, aiter `285579b62`, main `cb55d77d37` with this patch: GSM8K Qwen3-8B 0.9437 on main vs 0.9475 here.

`--enable-torch-compile` already fails on main with a memory fault during decode graph capture in the inductor output for aiter's decode op `fused_qk_norm_rope_cache_pts_quant_shuffle`, which this PR does not touch, so torch.compile is not covered.
