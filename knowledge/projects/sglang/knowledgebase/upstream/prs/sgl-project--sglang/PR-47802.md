# [Fix] attention: Triton decode reads wrong KV head for GQA groups > 16 not divisible by 16 (GLM-4-32B breaks)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47802) · state: open · merged: False

## Original PR description

## Motivation

glm-4-32b-0414 on the triton backend decodes heads 24-31 against kv head 0, so gsm8k drops from ~93% to ~51%; triton is also what sglang picks for an fp8_e5m2 kv cache on hopper. `_fwd_grouped_kernel_stage1` sets `cur_kv_head = cur_head_id // tl.cdiv(kv_group_num, BLOCK_H)` with BLOCK_H = 16, but lays tiles over query heads contiguously (`cur_head = cur_head_id * VALID_BLOCK_H + tl.arange(0, BLOCK_H)`), so when a group > 16 is not a multiple of 16 (48/2 = 24 on glm-4-32b-0414), tile 1 spans two groups and heads 24-31 read kv head 0.

## Modifications

`_grouped_head_tiles` gives every KV head a whole number of 16-head tiles (`kv_head_num * cdiv(kv_group_num, 16)`), and in `_fwd_grouped_kernel_stage1`, only when the group is not a multiple of BLOCK_H, a compile-time branch indexes the tile's heads from its group's start so the last tile of each group is partly filled and masked. Shapes whose group is a multiple of 16 compile to the same code, and `test_decode_attention_gqa_group_above_tile` tests groups 24, 20, 8, 16, and 32.

## Accuracy Tests

THUDM/GLM-4-32B-0414 on GSM8K (n = 1,319, greedy, H100, step-by-step prompt):

| Flags | Stock | Patched |
| --- | --- | --- |
| `--attention-backend triton` | 50.87% | 93.48% |
| `--attention-backend fa3` | 93.48% | - |
| `--kv-cache-dtype fp8_e5m2` | 49.51% | 92.87% |

With sgl-eval's default boxed-answer prompt all arms score lower (30.02% stock, 38.67% fixed, 38.51% FA3) because the model skips reasoning.
repro: https://gist.github.com/EvanZhuang/e205b5d8038c23ab414fccb6abdaa22a (`python3 repro.py`).
tests: `test_triton_attention_kernels.py` goes from 13 to 14 passed, 3 skipped (15 to 20 subtests); the other related test files are unchanged.

## Speed Tests and Profiling

Unaffected shapes are unchanged (0.998-1.000) and bitwise identical. The 48/2 kernel is ~1.35x slower (63.9 -> 87.5 us at 32 x 4,096, 73.5 -> 97.9 us at 128 x 1,024) because it does 4 tiles instead of 3 (the old time was for wrong results); end-to-end decode is +1.0% at batch 32 (27.00 -> 27.27 ms, FA3 26.94 ms; batch 1 25.44 -> 25.42 ms).
