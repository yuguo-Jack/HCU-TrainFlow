# [Perf] spec: Let the FlashAttention backend capture the draft-extend CUDA graph

[Upstream PR](https://github.com/sgl-project/sglang/pull/40762) · state: open · merged: False

## Original PR description

## Motivation

`EagleDraftWorker._capture_cuda_graphs` decides whether to capture the
draft-extend CUDA graph from `graph_supported_backend_types`. FlashAttention
(`fa3` / `fa4`) implements that graph path already, but it is not in the list, so
EAGLE / EAGLE3 served with `--attention-backend fa3` runs **one eager
draft-extend forward per accepted chunk** while every other phase (target
verify, draft decode) replays a captured graph.

This is the common path rather than an exotic one.
`get_default_attn_backend` (`python/sglang/srt/arg_groups/model_override_base.py`)
documents and implements "We will turn on FA3 on hopper unless user use spec
decode with topk > 1 or page_size > 1", so on Hopper:

* chain-mode EAGLE (`--speculative-eagle-topk 1`) resolves to `fa3` and silently
  loses the draft-extend graph;
* tree mode (`topk > 1`) falls back to flashinfer / triton, which are in the
  list, and keeps it.

So two rows of the same benchmark table are not directly comparable today, and
the chain rows are the penalised ones.

The behaviour also contradicts the documentation.
`docs/docs/advanced_features/attention_backend.mdx:531` states:

> CUDA Graph: the decode backend is always captured; the prefill backend is
> captured only when `--speculative-attention-mode prefill`.

`--speculative-attention-mode prefill` is the default and `fa3` is the Hopper
default, so with both defaults the docs promise a captured prefill/draft-extend
graph that the code does not capture.

Finally, the symptom is invisible in the log: the server prints
`Capture target verify ...` and `Capture draft decode ...`, and simply never
prints a draft-extend line. Nothing errors out, throughput is just lower.

## Modifications

Add `FlashAttentionBackend` to `graph_supported_backend_types` in
`python/sglang/srt/speculative/eagle_worker_v2.py`, plus the import. One file,
two lines.

`FlashAttentionBackend` already supports the phase on both sides:

* `init_forward_metadata_in_graph` branches on
  `forward_mode.is_draft_extend_v2()` and reads `self.draft_extend_metadata[bs]`;
* `init_forward_metadata_out_graph` has the matching `is_draft_extend_v2()`
  branch;
* `init_cuda_graph_state` allocates `draft_extend_metadata` whenever
  `speculative_num_draft_tokens` is set and `> 0`, so the capture buffers always
  exist when speculative decoding is on.

Nothing else changes: no new flags, no behaviour change for backends already in
the list, and the eager path remains the fallback for backends that are not.

## Accuracy Tests

Acceptance length is unchanged. Runs before and after the change agree to four
decimal places on the same fixed prompt set with greedy decoding, so the
captured graph is numerically equivalent to the eager path it replaces. This is
expected: the change only decides whether an already-supported forward is
replayed from a graph, not what it computes.

## Speed Tests and Profiling

One 8-GPU node, an MoE target with a single-layer MoE drafter, EAGLE chain mode,
greedy, batch size 1, fixed prompt set:

* **roughly 1.5x decode throughput** after the fix
* acceptance length unchanged (see above)
* graph capture costs about 1.5 s and 0.5 GB of device memory

The gain scales with how expensive the drafter is relative to the target,
because the eager forward is paid once per accepted chunk. A large target with a
light drafter will see much less -- there the eager draft-extend is a few
percent of a target forward and hides in run-to-run noise, which is the likely
reason this went unnoticed. Conversely a small target with a heavy drafter pays
the most.

After the fix the log gains the previously missing phase:

```
Capture draft extend CUDA graph begin. backend=full, ...
Capture draft extend CUDA graph end. elapsed=1.54 s, mem usage=0.45 GB
```

## Notes

**Why no unit test.** I tried to add a regression test asserting that every
member of `graph_supported_backend_types` really implements the draft-extend
graph, checked along the MRO so inherited implementations count (for example
`TokenspeedMLABackend` inherits it from `TRTLLMMLABackend` and overrides only
kernel-level methods). It does not work as a static assertion, because the
backends do not share a graph API surface: `FlashAttentionBackend` carries the
branches in `init_forward_metadata_in_graph` / `init_forward_metadata_out_graph`,
while `DeepseekV4AttnBackend` expresses the same capability through its own
`_GraphBucket.DRAFT_EXTEND`. Any such test ends up either special-casing each
backend or restating the list, so it would assert nothing. Happy to add an
end-to-end test instead if maintainers prefer -- the natural assertion is that
`cuda_graph_runner_for_draft_extend` is not `None` for a chain-mode EAGLE server
launched with `--attention-backend fa3`, which needs a GPU runner.

**Docs.** `attention_backend.mdx:531` (quoted above) becomes true for `fa3` with
this change, but it is still unconditional in a way the code is not: the prefill
backend is captured only when it is also in `graph_supported_backend_types`.
Flashinfer on an MLA model, for instance, resolves to `FlashInferMLAAttnBackend`
(`draft_utils.py`, `_create_flashinfer_prefill_backend`), which is not in the
list. Happy to add the qualifying clause in this PR or a follow-up, whichever
maintainers prefer.

### Relation to #36324

@zkyue's #36324 proposes the same enablement through a wider change, so to save a reviewer the diffing: it does three things, and on today's main they have diverged.

1. **Replace the isinstance allowlist with a capability method** — adds `AttentionBackend.supports_draft_extend_cuda_graph()` plus overrides in eight backends. This is still an open question on main: the allowlist is alive at `eagle_worker_v2.py:536-576`. It is also orthogonal to enabling fa3 — the refactor can land before or after this PR without changing its content.

2. **Publish the WAR read-done event after replay for in-graph-metadata backends** — this has already landed upstream in a more general form, so #36324's hunk no longer applies. The runner now asks the backend where its shared reads end and branches three ways (`eagle_draft_extend_cuda_graph_runner.py:661-679`):

   ```python
   self.model_runner.shared_read_done_event = None
   shared_read_ends = self.draft_extend_attn_backend.shared_read_ends(self.forward_mode)
   if shared_read_ends is SharedReadEnds.PRE_REPLAY:
       self._publish_read_done(in_graph=False)
   ...
   out = self._replay_graph(shape_key, forward_batch)
   if shared_read_ends in (SharedReadEnds.IN_REPLAY, SharedReadEnds.POST_REPLAY):
       self._publish_read_done(in_graph=False)
   ```

3. **Pin tests for the capability** — `test_draft_extend_graph_capability.py` gates FA on `use_sliding_window_kv_pool` alone. Main has since gone further: `FlashAttentionBackend.draft_extend_metadata_captured_in_graph()` (`flashattention_backend.py:521-529`) also returns `False` while `kv_index_translator.is_translating`, because a captured gather would bake virtual `req_to_token` ids into the page table.

### Why the ten lines are enough

The concern behind (2) is the one that would make a one-line allowlist entry unsafe, so to be explicit about why it does not apply here: `FlashAttentionBackend` does not override `shared_read_ends`, so DRAFT_EXTEND_V2 falls through to the conservative base default (`base_attn_backend.py:176-181`), which returns `IN_REPLAY` only for decode and target-verify and `UNKNOWN` otherwise. With `UNKNOWN` neither branch above fires, `shared_read_done_event` stays `None`, and `Scheduler._apply_war_barrier` (`scheduler.py:1944-1955`) takes its else path:

```python
if ev is not None and not envs.SGLANG_FORCE_COARSE_WAR_BARRIER.get():
    self.schedule_stream.wait_event(ev)
else:
    self.schedule_stream.wait_stream(self.forward_stream)
```

That is the coarse whole-forward fence, which strictly dominates the fine-grained event. So capturing the fa3 draft-extend graph is safe without touching the runner; what fa3 does not yet get is the scheduler overlap that a `PRE_REPLAY`/`IN_REPLAY` declaration buys. I would rather not fold that in here — declaring `shared_read_ends` for DRAFT_EXTEND_V2 is an audited claim about where FA's `req_to_token` reads end, and it wants its own benchmark. Happy to open it as a follow-up.

Import cycle, re-checked after the rebase: `flashattention_backend` does import from `sglang.srt.speculative.*` (`eagle_utils`, `ragged_verify`, `spec_info`, `spec_utils`), so the new top-level import is the risky direction, but walking all 509 modules reachable at import time from it finds no path back to `eagle_worker_v2`. I used a plain top-level import to match the neighbouring `FlashInferAttnBackend` rather than the lazy pattern used for `FlashMLABackend` and the DSA backends, since those are lazy specifically to keep CUDA-only kernel stacks out of non-CUDA builds.

If maintainers prefer the capability direction, I am glad to close this in favour of a rebased #36324. My argument for landing the ten lines first is that this is a perf regression on a default path rather than a new feature: `_get_default_attn_backend` returns `fa3` on Hopper MHA models whenever speculative decoding runs with topk == 1, so chain-mode EAGLE silently runs one eager draft-extend forward per accepted chunk today.
