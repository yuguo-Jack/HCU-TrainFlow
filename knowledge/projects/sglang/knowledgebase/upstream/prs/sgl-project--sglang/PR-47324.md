# [Perf] speculative: Fewer launches in a top-1 EAGLE decode step

[Upstream PR](https://github.com/sgl-project/sglang/pull/47324) · state: open · merged: False

## Original PR description

## Motivation

With `topk=1`, EAGLE drafts a chain, and a greedy verify only needs each row's argmax. At one or two requests, the time between a decode step's graphs is mostly small launches, and each one sits on the critical path. Many of them compute values that a neighbouring launch already holds or could write:
- the draft top-1 is a split argmax plus a finalize launch;
- the greedy verify fills the predicts and the accept index, reduces with `sampling_argmax` (`torch.argmax` on HIP), walks the chains in `verify_tree_greedy`, and on HIP broadcasts three tensors;
- after the verify, `num_correct_drafts + 1`, the relay's `index_put` of the new lengths and `prepare_draft_extend_layout` are one launch each;
- the graph replays copy inputs that are already in place: the verify's pre-planned tokens, the draft graph's positions restore, and its steps' eager input load;
- the draft graph copies its hidden states and DSA seed outside the grouped small copy;
- the overlap scheduler records a publish event that nothing waits on, and copies KV lengths to the device on steps that allocate nothing.

This PR removes those launches. Each change is on by default for the batches it applies to; every other batch keeps the current code.

## Modifications

| # | Commit | What it does | Ops a cycle (C=1) |
|---|---|---|---|
| 1 | Draft top-1 in one launch (`topk1.py`) | Each vocabulary split folds its (value, lowest index) into a per-row 64-bit key with an atomic max. The last split to arrive writes the token, the draft-token column and the position, then resets the row. Ties and NaN behave as with `torch.argmax`. | −3 |
| 2 | Greedy verify of a top-1 chain in one launch (`chain_verify.py`, `eagle_utils.py`) | `greedy_chain_verify` reduces every row the same way, and its last CTA walks every request's chain. The results are views of one buffer, so the HIP broadcast is one collective. Used for greedy top-1 trees on contiguous f32 GPU logits. | −5 |
| 3 | The verify launches write the accept lengths, the relayed lengths and the draft-extend layout | `greedy_chain_verify` and `simulated_accept` write `accept_lens`. The commit launch writes the new lengths into the overlap relay: the worker offers `FutureRelayBuffers`, as DSpark's verify does. `build_chain_tree` writes the draft extend's layout. | −3 |
| 4 | The first draft top-1 launch writes the chain's column 0 (`topk1.py`, `eagle_worker_v2.py`) | Replaces the copy of the step's input tokens before the steps. | −1 |
| 5 | EAGLE's target verify skips the re-copy of its pre-planned inputs (`decode_cuda_graph_runner.py`) | As DSpark's pre-planned verify does. The copy still runs unless the batch holds the very tensors the plan-time load copied from. | −2 |
| 6 | No positions restore after the draft graph's steps (`eagle_draft_cuda_graph_runner.py`) | Every replay loads the positions again. | −1 |
| 7 | Fewer copies in the EAGLE draft graphs' input loads (`eager_runner.py`, `small_copy.py`, draft graph runners) | `eager_inputs_in_place()`: only the draft graph's body sets it, and inside it the eager input load passes its tensors through. Every other eager forward copies as before. Fields up to 64K elements (was 8K) ride in the grouped small copy, which takes in the hidden states and the seed. | −5 |
| 8 | No publish event that nothing waits on; KV-length copies only when allocating (`scheduler.py`, `overlap_utils.py`, `eagle_utils.py`, `allocation.py`) | With GPU-only relayed lengths (HIP, no backend that needs host lengths), the publish event is recorded only for a mixed chunk or the confidence relay. The two KV-length H2D copies run only on steps that allocate. | −1, and about 5 µs of idle |
| 9 | Simulated acceptance runs its fused kernel on HIP (`spec_utils.py`) | The Triton `simulated_accept` was gated to CUDA; HIP ran about a dozen torch ops. This affects `SGLANG_SIMULATE_ACC_LEN` benchmarks only. | −10 (forced-length runs only) |

What keeps its current code: sampling, rejection sampling, `topk > 1`, non-f32 or strided logits, CPU, the post-verify-graph path, CUDA for commit 8, and every eager forward outside EAGLE's draft graph.

Tests:
- Kernel tests, on CUDA and AMD CI:
  - `test_spec_topk1.py`: ties across splits, -0.0, relaunch, 1,500 rows, column 0;
  - `test_chain_verify.py`: against the fills + `row_argmax` + `verify_tree_greedy` path, with 0–3 accepted drafts, bf16 ties, batch sizes 1–16, three vocabularies, widths 2 and 4; negative control: a target row's maximum moved;
  - `test_simulated_accept.py`: against the torch ops it replaces.
- Kernel tests registered for CUDA only:
  - `test_next_verify_prep.py`: the relay write against `publish`'s `index_put`, and the layout against `prepare_draft_extend_layout`;
  - `test_small_copy.py`: the 64K limit, and hidden rows plus a seed with index fields, bitwise.
- CPU test `test_eager_inputs_in_place.py`: the input load passes through only inside the context, and still copies inside a capture without it.

Related:
- #41172 (open) also fuses greedy chain verification with the argmax, as a finalize step after `row_argmax`. Here the reduction and the chain walk are one launch.
- #44978 (open, draft) splits the greedy-verify argmax on gfx950 and packs the HIP broadcast. Here the packed results come from the verify launch itself, on every device.
- #47200 (open, draft) fuses EAGLE index preparation, including the draft-extend layout, as a CUDA JIT kernel behind a master switch. Here `build_chain_tree` writes the layout by default for eligible batches.

## Speed Tests and Profiling

Setup:
- 8× MI355X, GLM-5.3 FP8, TP8, FP8 KV cache, 8K context.
- EAGLE 3-1-4, with the accept length forced to 2.99 (`SGLANG_SIMULATE_ACC_LEN`).
- Two servers an arm in ABBA order, 5 waves, requests paired by prompt.
- C=2 is the last-prefilled request's cycle.
- **These speed numbers were measured on the AMD monokernel path** (`--enable-amd-monokernel`). The model's forward ran in the GLM-5.3 monokernels of a test build of the sgl-amd-mono plugin that uses #47102's step-mode names. This PR changes the host and glue work between those launches, so its share of the cycle depends on how fast the forward itself is.
- Arms:
  - B0: main + #47101 + #47102 (with its gathered-logits commit);
  - B1: B0 + this PR.
