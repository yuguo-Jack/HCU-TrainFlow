# [ROCm][DSA] Add opt-in shape-aware prefill backend selection

[Upstream PR](https://github.com/sgl-project/sglang/pull/44061) · state: open · merged: False

## Original PR description

## Motivation

AITER and TileLang have different sparse-prefill crossover points. This ports our versioned GLM-5.3-MXFP4 routing policies to current upstream without changing default backend selection.

## Modifications

- Add `--dsa-prefill-policy` with explicit MI350X TP4 BF16/FP8 profiles.
- Select from host metadata once per eager sparse-prefill batch; store the decision for all layers. Keep decode, speculative, mixed and dense dispatch unchanged.
- Enforce architecture, dtype, topology and shape restrictions, with bounded TileLang fallback. Do not change KV layout/capacity, top-k or sampling.
- Add registered CPU coverage and usage documentation. No experimental force/target-verify modes or unrelated production patches.

## Accuracy Tests

22 new CPU tests pass; 25 existing namespace/runtime-context/read-ratchet tests also pass. Local tests ran in a GPU-isolated ROCm image with the HIP/device and optional AITER import boundaries switched to CPU-only behavior. These results validate routing/configuration, not GPU attention numerics or model accuracy.

AMD TP4 model replay and graph smoke on this port are still pending.

## Speed Tests and Profiling

The thresholds are carried over from earlier GLM-5.3-MXFP4 measurements, not retuned on this upstream revision. No new speedup claim. Pending validation compares prefill, cached-tail and decode/verify forward latency on the same GPU lane with unchanged KV dtype/pool budget and sampling configuration.

## Known dependency

The FP8 profile does not repair AITER softmax-numerator underflow: https://github.com/ROCm/aiter/pull/5535. It remains unqualified for promotion until the AITER variant selected by this stack passes numerical and model-level checks. No patched `.co` is bundled.

Hi @tanth47 Thanks for this. Could you please retest on current main:

Rebase onto main. [sgl-project/sglang#39083](https://github.com/sgl-project/sglang/pull/39083) (merged 10/23) changed the AITER FP8 path this policy routes batches into. It flipped fast_mode and intra_batch_mode, added q_scale/kv_scale, and made the output bf16. The FP8 thresholds were fitted before that change.
FP8 revalidation: With --dsa-prefill-backend tilelang and an FP8 KV cache, the fused rope path passes fp8 q into AITER sparse prefill. No fixed-backend config runs that combination, so it needs its own accuracy check. I’d suggest leaving FP8 out of this PR and adding it in a follow-up once [ROCm/aiter#5535](https://github.com/ROCm/aiter/issues/5535) is resolved.
Show the speedup. On MI350X TP4, compare against both plain --dsa-prefill-backend aiter and plain tilelang on the same workload. Cover both fresh prefill and cached-prefix cases, and report TTFT and prefill throughput. If the better fixed backend is within noise, the per-batch switching isn’t worth the extra code.
Accuracy. Run GSM8K or your model replay with the policy on and off.

On design: flashmla_auto / set_dsa_prefill_impl already picks the prefill kernel per batch. Could this be an aiter_auto choice with an env-var threshold (like SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD)
