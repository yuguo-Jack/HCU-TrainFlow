# perf(kernels/attention): parallelize compute_position prefix-sum for large batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/31284) · state: closed · merged: False

## Original PR description

## Motivation

`compute_position_triton` (`python/sglang/kernels/ops/attention/position.py`)
computes the per-token `positions` and per-request `extend_start_loc` for every
prefill/extend forward. It is the default position path on CUDA for all
Triton-capable attention backends (flashinfer / fa3 / triton — i.e. everything
except `torch_native` / `intel_amx`, per `support_triton`), invoked once per
forward from `forward_batch_info.py::compute_position`.

The current kernel launches **one program per request**, and each program `pid`
recomputes the exclusive prefix-sum from scratch:

```python
# NOTE: This can be slow for large bs
cumsum_start = tl.cast(0, tl.int64)
for i in range(pid):
    cumsum_start += tl.load(extend_seq_lens + i)
```

That is **O(bs²)** aggregate serial loads over a grid of `bs` blocks — the
kernel's own comment already flags it. For large batches (long prefills, high
concurrency, speculative decoding), this once-per-forward setup kernel becomes a
real cost: at bs=8192 it is **948 µs on H200** and **6.6 ms on Ascend 910B**
(which is far more core-starved on the O(bs²) grid). NPU serving hits this same
kernel: sglang-on-Ascend defaults to `attention_backend="ascend"`, for which
`support_triton` is True.

This PR adds a batch-size-adaptive striped path that bounds the aggregate
prefix-sum work to **O(min(bs, 64)²)** and shrinks the grid from `bs` blocks to
≤ 64 blocks, while leaving the small-batch path byte-identical to today.

## Modifications

Single file, `python/sglang/kernels/ops/attention/position.py` (+78 / −5). No
new files, no call-site changes; public API, signature and output dtypes
(`int64` positions, `int32` extend_start_loc) are unchanged.

- **Unchanged** — `compute_position_kernel` (the existing one-program-per-request
  kernel) is kept verbatim; it is now the small-batch path.
- **New** — `compute_position_striped_kernel`: launches ≤ 64 stripes; each stripe
  seeds its running offset once (a bounded serial prefix chain), then fills
  `ROWS_PER_STRIPE` consecutive rows. Aggregate prefix work is O(min(bs, 64)²).
- **`compute_position_triton`** dispatches on a **device-aware size tier**:
  `bs < threshold` → existing kernel; `bs ≥ threshold` → striped kernel with
  `rows_per_stripe = 16`, stripe count capped at 64
  (`rows_per_stripe = ceil(bs / 64)` past the cap). The threshold is read from
  the input tensor's device type — `1024` on GPU, `256` on NPU — matching each
  device's measured crossover (below).

The threshold is a size tier (`<` / `≥`), not shape-specific dispatch. Below it,
striping would merely under-utilize the cores (fewer blocks); the O(bs²) prefix
only dominates at large bs. The two constants are the only device-specific knob;
both kernel bodies are identical across GPU and NPU.

## Accuracy Tests

Output is integer, so the bar is **byte-equality** (`torch.equal`, atol=rtol=0)
against the current Triton kernel, plus an independent pure-PyTorch spec.
21 shapes covering the full speed envelope + edge cases: bs=1; `has_prefix`
True/False; large prefix; prime bs=97; non-divisible bs=333; bs=1025 crossing
the 64×16 stripe boundary; bs=4000 very-long; empty-batch / no-prefix.
