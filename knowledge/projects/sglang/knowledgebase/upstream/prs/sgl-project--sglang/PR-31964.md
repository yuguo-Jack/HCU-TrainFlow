# [router] service discovery: per-pod HTTP and bootstrap port overrides for hostNetwork PD co-location

[Upstream PR](https://github.com/sgl-project/sglang/pull/31964) · state: closed · merged: False

## Original PR description

## Motivation

When running PD-disaggregated sglang on Kubernetes, prefill/decode pods
often need `hostNetwork: true` so their KV-transfer backend (mooncake,
NIXL) can reach the node's RDMA fabric directly. Under `hostNetwork`,
two sglang pods on the same node share one network namespace, so they
cannot both bind port 30000 for HTTP nor port 8998 for mooncake
bootstrap — this makes it impossible to co-locate multiple sglang
replicas on a single GPU node, wasting GPU capacity on any node that
isn't already fully packed.

The router has one existing knob for this: the pod-level
`sglang.ai/bootstrap-port` annotation. But per-pod annotations are
awkward to inject from a shared pod template — controllers such as
LeaderWorkerSet inject per-pod *labels* natively (e.g.
`leaderworkerset.sigs.k8s.io/group-index`) but do not support per-pod
annotations from a shared template. Working around that today
requires either a mutating webhook or an in-cluster init container
that patches the pod's own annotations at startup, both of which add
operational complexity.

This PR completes the port-override story so that co-locating
multiple sglang PD replicas on one `hostNetwork` node works
out-of-the-box:

* HTTP serving port also gets an annotation override (same shape as
  the existing bootstrap port).
* Both ports gain a label-based fallback: the router reads a per-pod
  index label and adds it to a caller-configured base.

All new fields are opt-in and default to disabled, so existing
deployments are unaffected.

## Modifications

**`sgl-model-gateway/src/service_discovery.rs`**

* Add `resolve_pod_port_override(pod, annotation_key, label_key, label_base) -> Option<u16>`,
  a small helper that encodes the precedence rule
  (annotation → label+base → None) in one place.
* Add `PodInfo::http_port: Option<u16>`, populated from the same
  helper at pod-discovery time. `PodInfo::worker_url(port)` now
  prefers `self.http_port` and falls back to the caller-supplied
  port, so existing worker-URL formatting is a no-op change when the
  override is absent.
* `PodInfo::from_pod` uses the helper for both the bootstrap port
  (prefill pods only) and the new HTTP port.
* Extend `ServiceDiscoveryConfig` with:
  `http_port_annotation` (default `sglang.ai/http-port`),
  `http_port_label_key` (default empty),
  `http_port_label_base` (default 0),
  `bootstrap_port_label_key` (default empty),
  `bootstrap_port_label_base` (default 0).
  Empty key or zero base disables the label fallback; annotation
  defaults only fire when a pod actually carries the annotation.

**`sgl-model-gateway/src/config/types.rs`** — mirror the five new
fields on `DiscoveryConfig` (serde-deserialized YAML config) with
matching `#[serde(default)]` attributes.

**`sgl-model-gateway/src/main.rs`** — thread the five new fields
through the standalone binary. New CLI flags in the "Service
Discovery (Kubernetes)" argument group:

    --http-port-annotation           (default: sglang.ai/http-port)
    --http-port-label-key
    --http-port-label-base
    --bootstrap-port-label-key
    --bootstrap-port-label-base

At server-config construction time, YAML `discovery` values take
precedence over the CLI defaults so a config file can override the
per-flag defaults.

**`sgl-model-gateway/bindings/python/src/lib.rs`** — extend the pyo3
`Router` class with the five new fields (matching Python defaults so
existing Python constructor calls keep working).

**`sgl-model-gateway/bindings/python/src/sglang_router/router_args.py`** —
add the five fields to the `RouterArgs` dataclass and register the
matching `--*-label-key` / `--*-label-base` argparse arguments so both
the standalone binary and the Python wrapper accept the flags.

**`sgl-model-gateway/bindings/python/src/sglang_router/router.py`** —
docstring update listing the new constructor kwargs.

- whybeyoung · comment · 2026-07-24T03:10:30Z · [source](https://github.com/sgl-project/sglang/pull/31964#issuecomment-5065764235)

Good pr.

Suggestion: fail-closed on base+index port collisions

The label + base fallback is deterministic, but pushes port-range planning onto the operator. If two models on the same node share a base and label key (e.g. both use LWS group-index with base=30000), replica-N pods compute identical ports. Under hostNetwork one of them will EADDRINUSE at bind() and CrashLoop — the failure mode exists, but is opaque unless you read individual pod logs.

Router-side we can make it loud and safe instead of silent:

1. Reject the conflicting pod, don't just warn. When inserting a PodInfo, if another already-tracked pod on the same nodeName has the same http_port or bootstrap_port, skip adding it to the worker set and error! with both pod names + node + port (optionally emit a K8s Event on the pod). The first pod keeps serving; the misconfigured one is neither routed to nor silently accepted.
2. Overflow guard in resolve_pod_port_override. Use checked_add on base + index (u16); on None, treat as configuration error — skip the pod with an error! and a unit test for the boundary.
