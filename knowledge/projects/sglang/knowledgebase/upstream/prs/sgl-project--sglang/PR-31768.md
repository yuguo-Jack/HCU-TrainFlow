# [Model] Add LLaDA2.2 Block Routing MoE support

[Upstream PR](https://github.com/sgl-project/sglang/pull/31768) · state: closed · merged: True

## Original PR description

## Motivation

LLaDA2.2 uses block routing in its MoE router: each diffusion block first chooses a capacity-limited set of candidate experts, and each token then selects its top-k experts from that block-local expert set. This PR adds the SGLang serving-side implementation for that routing mode so LLaDA2 checkpoints that expose `expert_capacity` / `block_size` in their config can run through the native LLaDA2 model path.

The default LLaDA2 routing path is unchanged. Block routing is enabled only when the model config has `expert_capacity`.

## Modifications

- Add a two-phase Triton block top-k router in `python/sglang/srt/models/llada2.py`:
  - Phase 1 (`_block_aggregation_kernel`): computes block-level expert scores via max aggregation over tokens in the block, then selects `expert_capacity` allowed experts using a threshold + cumsum approach with index-based tie-breaking.
  - Phase 2 (`_token_topk_kernel`): each token selects its top-k experts from only the block-allowed set; weights are normalized via row-max rescaling with a uniform fallback for near-zero scores.
- Wire block routing through the existing `Llada2MoeBlock` by conditionally calling `block_topk_triton` when `expert_capacity` and `block_size` are present in model config, constructing `StandardTopKOutput` for downstream compatibility.
- Add a manual unit test (`test/manual/layers/moe/test_block_topk_triton.py`) comparing the Triton kernel against a pure PyTorch reference for:
  - Small and large expert counts (16 to 256 experts);
  - Various capacity constraints (tight capacity, full capacity, production-like);
  - Edge cases: `top_k=1` (no normalization path), `block_size=1` (per-token degenerate case);
  - Stress test with 256 tokens.

## Checklist

- [x] Triton kernel implementation with two-phase block routing
- [x] Unit tests (7 cases, all passing on GPU)
- [x] End-to-end serving verification with block routing active

When `num_experts_total` is not a power of two, `BLOCK_SIZE_E` will be larger than `num_experts_total`. The out-of-bound experts (indices between `num_experts_total` and `BLOCK_SIZE_E - 1`) will have their `block_expert_scores` computed as `0.0` (since their logits are loaded as `-inf` and sigmoid of `-inf` is `0.0`). 

Because of the tie-breaker subtraction `expert_offs * 3e-7`, a valid expert with a very negative logit (and thus a very small sigmoid score) at a high index can end up with a `combined_values` score that is lower than an out-of-bound expert at a lower index. This can cause invalid out-of-bound experts to be sorted before valid experts and incorrectly selected as allowed experts, taking up capacity.

To prevent this, we should explicitly mask out invalid experts by setting their `combined_values` to `-inf` before sorting, and also mask the `allowed` mask with `expert_mask`.

```python
    # Tie-break by expert index.
    combined_values = block_expert_scores - (expert_offs.to(tl.float32) * 3e-7)
    combined_values = tl.where(expert_mask, combined_values, float('-inf'))
    sorted_scores = tl.sort(combined_values, descending=True)
    mask = expert_capacity - 1 == expert_offs
    threshold_val = tl.sum(sorted_scores * mask)

    allowed = combined_values >= threshold_val
    allowed = allowed & expert_mask
    allowed_cumsum = tl.cumsum(allowed.to(tl.int32), axis=0)
    allowed = allowed & (allowed_cumsum <= expert_capacity)
```

Similar to the block aggregation kernel, we should mask out invalid experts in the token top-k kernel to prevent them from participating in sorting or being selected. Additionally, for elements where `token_expert_mask` is `False`, `token_expert_idx` is `-1`. Passing a negative offset to `tl.store` (even when masked out) can lead to undefined behavior or compiler warnings in Triton. We should use a safe index (e.g., `0`) for masked-out elements.

```suggestion
    combined_scores = masked_scores - (expert_offs.to(tl.float32) * 3e-7)
    combined_scores = tl.where(expert_mask, combined_scores, float('-inf'))
    sorted_combined = tl.sort(combined_scores, descending=True)

    threshold_token_score = tl.sum(sorted_combined * (top_k - 1 == expert_offs))
    token_expert_mask = combined_scores >= threshold_token_score
    token_expert_mask = token_expert_mask & expert_mask
    token_expert_idx_cumsum = tl.cumsum(token_expert_mask.to(tl.int32), axis=0)
    token_expert_mask = token_expert_mask & (token_expert_idx_cumsum <= top_k)
    token_expert_idx = token_expert_idx_cumsum * token_expert_mask - 1
    safe_expert_idx = tl.where(token_expert_mask, token_expert_idx, 0)
    tl.store(topk_ids_ptr + token_idx * top_k + safe_expert_idx, expert_offs, token_expert_mask)
```

The current dual-stream implementation contains unnecessary intermediate `wait_stream` synchronizations that completely serialize the execution of `_block_topk` (on `current_stream`) and `act_fn` + `down_proj` (on `alt_stream`). 

Specifically:
1. `current_stream.wait_stream(self.alt_stream)` at line 574 forces `current_stream` to wait for `gate_up_proj` to finish before starting `_block_topk`, even though `_block_topk` only depends on `router_logits` (which is already computed on `current_stream`).
2. `self.alt_stream.wait_stream(current_stream)` at line 578 forces `alt_stream` to wait for `_block_topk` to finish before starting `act_fn` and `down_proj`, even though they only depend on `shared_gate_up` (which is already computed on `alt_stream`).

By removing these intermediate synchronizations, we can achieve full overlap between the gating/routing path on `current_stream` and the shared expert path on `alt_stream`, significantly improving serving efficiency.

```python
        current_stream = torch.cuda.current_stream()
        self.alt_stream.wait_stream(current_stream)
        assert not ((self.shared_experts.tp_size == 1) and hidden_states.shape[0] == 0)
        
        # Launch shared expert gate_up_proj on alt_stream
        with torch.cuda.stream(self.alt_stream):
            shared_gate_up, _ = self.shared_experts.gate_up_proj(hidden_states)
            
        # Launch gate and block top-k on current_stream
        router_logits = self.gate(hidden_states)
        topk_weights, topk_ids = self._block_topk(router_logits)
        
        # Launch shared expert act_fn and down_proj on alt_stream
        with torch.cuda.stream(self.alt_stream):
            shared_hidden_states = self.shared_experts.act_fn(shared_gate_up)
            shared_output, _ = self.shared_experts.down_proj(shared_hidden_states)
            
        # Launch experts on current_stream
        topk_output = StandardTopKOutput(
            topk_weights=topk_weights,
            topk_ids=topk_ids,
            router_logits=router_logits,
        )
        router_output = self.experts(hidden_states, topk_output)
        
        # Wait for alt_stream to finish shared expert computation
        current_stream.wait_stream(self.alt_stream)
        return router_output, shared_output
```
