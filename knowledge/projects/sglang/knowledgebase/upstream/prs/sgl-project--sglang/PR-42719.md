# [DeepSeek-V4] Reject prompt-logprob requests at admission under decoder SWA bounded replay instead of crashing the server

[Upstream PR](https://github.com/sgl-project/sglang/pull/42719) · state: closed · merged: False

## Original PR description

## Motivation

With `--enable-decoder-swa-bounded-replay`, the non-speculative extend path restricts the layers after the last KV-source layer to each request's last SWA window, and a model guard rejects prompt-token logprobs on this path. `DeepseekV4Model._check_late_layer_tail_readers` raises `ValueError("decoder SWA bounded replay cannot return logprobs of prompt tokens ...")` in the forward pass when a request sets `return_logprob` with a `logprob_start_len` inside the prompt. Because the error is raised in the scheduler's forward pass, one such client request takes down the server.

Encoder SWA replay already rejects these requests in `TokenizerManager._validate_one_request`. Decoder bounded replay had no admission check.

Related: #41448 proposes computing the prompt rows instead. This PR rejects unsupported requests at admission.

## Modifications

- `Scheduler.handle_generate_request`: under `--enable-decoder-swa-bounded-replay`, a request with `return_logprob` and a `logprob_start_len` below the prompt length (other than `-1`) is aborted with a 400 and a message that names the flag, unless it is a streaming-session request with a nonnegative start (see below). This matches the existing MLX sampling-path check right above it. Negative values other than `-1` are rejected too, because `compute_extend_logprob_start_len` resolves them to the start of the extend. The check sits in the scheduler, so it covers every entry point, including the ones that send tokenized requests directly.
- Output-only logprobs are still accepted: `logprob_start_len=-1`, `logprob_start_len=len(prompt)`, and `token_ids_logprob` with `logprob_start_len=-1`.
- Streaming sessions: `Req.init_next_round_input` replaces a nonnegative `logprob_start_len` with -1 for streaming sessions and returns only output logprobs, so those requests do not trigger the forward-pass prompt-logprob error. The admission guard exempts exactly those requests, so `return_logprob=True, logprob_start_len=0` keeps working for streaming sessions as before. Other negative starts such as `-2` are not normalized and resolve to the start of the current extend, so they are still rejected, as are non-streaming and radix-native session requests that ask for prompt logprobs.
- New `test/registered/unit/managers/test_scheduler_bounded_replay_logprobs.py` drives `handle_generate_request` with a stubbed scheduler. Under bounded replay it checks that prompt-logprob requests (start 0, mid-prompt, `len - 1`, and `-2`) are aborted and queued, and that output-only logprob requests are not aborted. Without bounded replay, prompt logprobs are still accepted. Three more tests drive the session path: a streaming session with start 0 is admitted, a streaming session with start -2 is rejected, and a non-streaming session with start 0 is rejected.
