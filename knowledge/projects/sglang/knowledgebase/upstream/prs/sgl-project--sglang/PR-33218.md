# [PD Disagg][HiSparse] Treat the CPU KV buffer as RadixCache L1

[Upstream PR](https://github.com/sgl-project/sglang/pull/33218) · state: closed · merged: False

## Original PR description

<!-- Suggested title: [PD Disagg][HiSparse] Treat the CPU KV buffer as RadixCache L1 -->

## Motivation

Legacy HiSparse keeps full attention KV in CPU pinned memory, the historical
indexer state (`K^I`) on GPU, and a bounded full-KV hot buffer on GPU. This
reduces decode HBM usage, but the decode worker's CPU allocation is
request-local: after a request finishes, ordinary RadixCache cannot retain and
match that host-backed prefix. A later request therefore receives the same KV
from the prefill worker again even when the decode worker already computed and
stored it.

This PR makes HiSparse's CPU-backed canonical cache visible to ordinary
decode-side RadixCache. It targets PD-disaggregated workloads such as coding
agents, where many conversations share a large system/tool prefix and then grow
independently.

The initial scope is intentionally narrow so review can focus on the ownership
model, write-back fence, and supported transport/model boundary.

## Modifications

### Cache ownership

The new `RadixHiSparseTokenToKVPoolAllocator` presents one Radix-visible logical
slot namespace backed by:

- CPU full-attention KV; and
- GPU indexer history (`K^I`).

One logical token ID owns both rows for the same lifetime. RadixCache owns their
allocation, reference counts, prefix matching, and eviction. HiSparse continues
to own only the bounded GPU full-KV hot buffer and its existing LRU/swap-in
policy:

```text
Radix logical ID l ──> CPU full KV[l]   (canonical)
                   └─> GPU K^I[l]       (canonical)

CPU full KV ──top-k swap-in──> GPU HiSparse hot buffer (transient L0)
```

The `L1` term in this PR describes that composite canonical store; it is not a
new HiCache tier.

### Prefix-aware PD transfer

- Decode-side RadixCache matches and pins the reusable prefix before
  preallocation.
- The allocator reserves slots only for the missing suffix.
- Prefill sends full KV and DSA/indexer state only for that suffix.
- A complete decode-side hit is represented by empty KV and state payloads,
  instead of waiting for a transfer notification that will never arrive.
- After transfer, the ordinary Radix request-finalization path canonicalizes the
  slot IDs before HiSparse acquires its per-request hot buffer.

Prefill and decode cache hits remain independent: a prefill hit skips compute,
while a decode hit skips P-to-D KV/state transfer.

### Decode write-back ordering

- Each committed decode row is copied from the GPU hot buffer to its canonical
  CPU slot after model forward.
- KV write-back and result D2H use the ordered post-forward copy path.
- The next model forward waits on the latest KV event immediately before graph
  replay/eager execution, preventing reuse of an L0 row still being copied.
- Request completion synchronizes the write-back before ordinary Radix
  publication or resource reuse, so a prefix hit cannot observe partially
  written CPU KV.

### Compatibility and tests

- HiSparse swap kernels accept both `int32` Radix request tables and the legacy
  `int64` host-location tables without a per-step cast.
- Added allocator, prefix admission, lifetime, write-back, transfer-protocol,
  kernel-dispatch, and configuration tests.
- The existing allocator/configuration path remains selected outside the
  explicitly gated Radix HiSparse mode.

The user-facing ownership model, configuration, and limitations are documented
in `docs_new/docs/advanced_features/hisparse_guide.mdx`.

## Current Scope

Supported in this draft:

- PD decode + decode-side RadixCache + ordinary DSA HiSparse;
- overlap scheduling and full decode CUDA graph replay;
- tensor/data-parallel GLM-5.2 execution;
- Mooncake TCP end-to-end transfer and focused NIXL protocol tests.

Explicitly rejected or not claimed:

- speculative decoding;
- pipeline parallelism;
- HiCache or decode KV offload in the same process;
- hybrid SWA or Mamba/SSM models;
- DeepSeek-V4's mixed cache layout; and
- production RDMA/NIXL end-to-end validation.

These restrictions are startup guards rather than silent fallback behavior.

## Accuracy Tests

GPU verification on code commit `0a4d96500e` passed on two H100 80 GB GPUs.
The later cleanup commit only consolidates documentation into the existing
HiSparse guide:

- 209 focused pytest cases plus 24 subtests;
- the upstream HiSparse manager lifecycle suite (11 passed, 2 skipped, plus 4
  subtests);
- the dedicated SM90 swap-kernel correctness suite (11 passed, 1 skipped); and
- allocator, admission, decode write-back, transfer-protocol, dispatch, and
  argument-validation coverage.

A real Mooncake-TCP 1P1D deployment with a small GLM DSA checkpoint exercised
decode-side prefix reuse:

- prompt-only growth matched `0 -> 1024 -> 2048` decode-prefix tokens;
- carrying 64 generated tokens into each next turn matched
  `0 -> 1088 -> 2112`, exercising L0-to-CPU write-back and later reuse; P was
  flushed between steps, so these hits came from the decode tree;
- an earlier eviction/reload probe churned the L0 hot buffer, after which a
  continuation with a 2,304-token decode-side hit produced exactly the same
  output token IDs as the fully cold continuation; two measured repetitions
  also had identical output hashes; and
- full decode CUDA graphs were captured for `bs=[1,2,4]`; a sustained batch-4
  run generated 512 tokens per request while L0 reached 6,144 rows and CPU L1
  reached 3,840 published rows, with no retractions, transfer failures, cache
  exceptions, or CUDA errors.

The final pipeline-parallel startup guard is CPU-only argument validation. Its
focused suite passed 18 tests plus 4 subtests, along with Black, targeted Ruff,
`py_compile`, and `git diff --check`.

A standard GLM-5.2 W4AFP8 GSM8K evaluation also passed on two 8xH100 nodes
(one TP8/DP8 prefill node and one TP8/DP8 decode node). All arms used 500
questions, 6-shot prompts, temperature 0, 512 maximum output tokens, Mooncake
TCP, ordinary DSA HiSparse, and full decode CUDA graph capture at `bs=[1]`:

| Run | Score | Correct |
|---|---:|---:|
| Legacy HiSparse baseline | 0.958 | 479/500 |
| Radix HiSparse pass 1 | 0.946 | 473/500 |
| Radix HiSparse pass 2 | 0.956 | 478/500 |

All runs met the existing 0.94 GLM-5.2 HiSparse floor, all 1,500 answers were
parseable, and the second feature pass improved by 1.0 percentage point rather
than degrading. Legacy versus feature pass 2 had 470 jointly correct answers,
9 legacy-only correct answers, and 8 feature-only correct answers. The
bidirectional swaps and one-question net delta are consistent with the known
non-bitwise determinism of this W4AFP8 MoE/DP-attention configuration; no
feature-specific accuracy regression, transfer failure, cache exception, or
CUDA error was observed.

## Speed Tests and Profiling

The production-shaped A/B used GLM-5.2 W4AFP8 on two nodes with eight H100 SXM
GPUs each: one prefill node and one decode node. Both arms used full decode CUDA
graph replay.

The workload contained a 25,600-token shared system/tool prefix, 16 independent
conversation branches, and three monotonically growing turns per branch. Each
turn added 512 unique input tokens and generated 1,024 output tokens. The decode
node remained saturated for 48 measured requests after a separate cold-prefix
seed. The only A/B change was the decode cache policy: legacy
HiSparse/ChunkCache versus Radix HiSparse.

| Metric | Legacy HiSparse | Radix HiSparse | Delta |
|---|---:|---:|---:|
| TTFT mean | 28,790.3 ms | 26,508.1 ms | -7.93% |
| TTFT p95 | 37,007.3 ms | 33,473.8 ms | -9.55% |
| TPOT mean | 32.277 ms | 30.114 ms | -6.70% |
| Wall time / 48 requests | 201.867 s | 187.574 s | -7.08% |
| Output throughput | 243.49 tok/s | 262.04 tok/s | +7.62% |
| Decode GPU utilization | 92.38% | 97.51% | +5.13 pp |
| Logical KV/state rows transferred | 1,327,104 | 24,576 | -98.15% |

All requests in both arms generated the requested 1,024 output tokens with no
retractions, transfer failures, cache exceptions, or CUDA errors.

This is intentionally workload-dependent. In a separate single-rank eager
experiment with only 1K-4K prefixes, Radix HiSparse made the complete
conversation chain 10.44% slower because the saved transfer was too small to
amortize write-back and cache bookkeeping. The expected benefit is large reused
prefixes, repeated conversation growth, or memory-pressure regimes—not every
HiSparse request.

## Relationship to HiSparse V2

Related: [#32314](https://github.com/sgl-project/sglang/pull/32314).

HiSparse V2 uses HiCache as a GPU-first logical KV pool and writes full KV to
host under memory pressure. This PR explores a different PD-specific ownership
policy: CPU full KV is canonical from arrival, GPU memory retains the indexer
history and hot buffer, and decode-side Radix hits eliminate repeated P-to-D
prefix transfer. This PR does not use the "HiSparse V2" name.

## Review Focus

Early feedback would be especially useful on:

1. whether a composite CPU-full-KV/GPU-indexer allocator is the right boundary
   for exposing HiSparse storage to ordinary RadixCache;
2. whether the post-forward D2H event and pre-publication fence are placed at
   the right lifecycle boundaries; and
3. whether ordinary DSA + Mooncake-first PD coverage is an acceptable initial
   scope before speculative decoding, DSv4, or additional transports.
