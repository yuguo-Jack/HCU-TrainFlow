# [Fix] dsv4: Add an opt-in deterministic sparse top-k for DeepSeek-V4.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/47748) · state: open · merged: False

## Original PR description

## Motivation

Fixes #46798. On SM90 it also needs the mHC change in #46523.

Identical greedy DeepSeek-V4.1 requests decode differently from run to run. The sparse top-k returns its selection in a different order each run, and on tied scores a different set, while sparse attention sums in index order. The issue shows this on SM120. We measured the same on H20 (SM90) and B300 (SM103); the per-path breakdown is in the issue comment.

#46522 makes top-k v2 keep the lowest positions among tied scores, and #46523 switches the SM90 mHC projection to `num_stages=1`. Together they make H20 deterministic in our tests. No open PR covers the remaining sources:
- Top-k v1 emits in thread-arrival order. This is the SM120 FullTopK path.
- `topk_transform_sparse` varies its order and, on bf16 ties, its set. It runs the SM100 candidate consumers in prefill and decode.
- DeepSelect's cluster tier varies its order and, on ties, its set. The tier is chosen by buffer width (`vocab_size > 16384`). The decode logits buffer is as wide as the page table (the maximum context length, not the current one), so SM100 FullTopK decode takes the cluster tier at every length.
- Top-k v2 still varies with more than 2048 exactly-equal scores, even with #46522.

This PR adds `SGLANG_ENABLE_DETERMINISTIC_SPARSE_TOPK`, off by default. With it on, every DSV4 top-k entry point returns the same indices in the same order on every run.

## Modifications

- `srt/environ.py`: adds the flag.
- `kernels/ops/attention/dsv4/topk.py`: with the flag on, `topk_transform_paged`, `topk_transform_paged_v2`, `topk_transform_ragged_v2` and `topk_transform_sparse` call `_deterministic_paged` / `_deterministic_ragged` instead of their kernels.
  - These use DeepSelect's single-CTA kernel when it accepts the operands. `_deep_select_takes` checks dtype, alignment, the 128-byte-padded last row, `k <= 4096`, and the page table.
  - Otherwise they use `_select_positions_torch`, an exact selection. It keeps every score above the k-th, then the lowest positions among the ties, and returns them in ascending order.
  - The page transform, output offsets and `-1` padding follow each entry point's contract. ROCm and XPU are unchanged.
- `kernels/ops/attention/deep_select.py`: with the flag on, buffers wider than the cluster threshold stay on the single-CTA kernel.
- `kernels/ops/attention/dsv4/candidate_blocks.py`: `amax_topk_blocks` allocates its block keys with `aligned_new_empty`, giving 128-byte rows.
  - The default v2 path only needs `stride % 4`, so it is unaffected.
  - Without this change, keys for a 1M-token context (1048580 positions at ratio 1) do not end on a 128-byte boundary. With the flag on, DeepSelect then rejected them and the torch fallback cost about 0.2 ms per decode step on H20.
- `test/registered/kernels/ops/attention/test_dsv4_deterministic_topk.py`: 99 new cases, described below.

## Accuracy Tests

The flag is off by default, so default outputs are unchanged. With it on, the selection is still an exact top-k. Among tied scores it may keep different positions than the default kernels, which pick ties arbitrarily.

**Kernel test** (H20): 99 passed in 14 s.
- Each entry point is run on rows with plateau ties and rows with bf16 ties, eager and under CUDA-graph replay, on DeepSelect and on the torch fallback.
- Each case checks run-to-run equality, top-k membership (as a score multiset), and the output contract.
- With the flag forced off, 38 of the 50 DeepSelect-side cases fail. The 12 that pass are inputs the default kernels already handle stably: trivial `seq <= k` rows, and rows whose top-k set has no ties.

**End to end.** DeepSeek-V4.1-Flash, TP8/EP8, radix cache off, temperature 0. The same prompt is sent 10 to 30 times per length, with and without a cache flush between runs, and logprobs are compared bit for bit.

| | main | this PR, flag on |
|---|---|---|
| H20, 3 nodes, nightly 586355a8, overlap scheduling on, 10 runs per length; both columns with #46523's mHC change | 511 identical; at 8193 / 9000 / 16385 / 33000 all 10 logprob vectors differ, on every node | identical at 511 / 8193 / 9000 / 16385 / 33000 on every node |
| B300, nightly a2cafa56, overlap scheduling on, 20 runs per length | 511: 7 to 8 different outputs in 20 runs; 8193 and 32769: all 20 logprob vectors differ | identical at 511 / 8193 / 32769 |
| B300, same image, overlap scheduling off, 30 runs per length | 511: 9 different outputs in 30 runs; 8193 and 32769: all 30 logprob vectors differ | identical at 511 / 8193 / 32769 |

Eight identical requests sent at once still differ by their position in the batch. That is batch invariance and out of scope here.

**GSM8K** (all 1319 questions, 5-shot, greedy, 128 in parallel), main vs flag on, on the overlap-on servers above. One standard error at this size is 0.008.
- H20, three nodes: 0.898 / 0.904 / 0.906 vs 0.904 / 0.902 / 0.900 (means 0.903 and 0.902)
- B300: 0.905 vs 0.911

## Speed Tests and Profiling

H20, TP8/EP8, three variants: main, flag off, flag on.

- **Decode GPU time per step**, 8K context, batch size 1, torch profiler over 40 steps: 10404 µs with the flag off, 10431 µs with it on (+0.26%). DeepSelect adds 66 µs and replacing top-k v2 saves 53 µs; kernels the flag does not touch, mostly the all-reduce, make up the rest.
- **bench_serving** (random ids), main / flag off / flag on:
  - TPOT, 8K, batch size 1: 8.10 / 8.10 / 8.11 ms
  - TPOT, 32K, batch size 1: 8.15 / 8.14 / 8.19 ms
  - TPOT, 8K, concurrency 16: 13.81 / 13.86 / 14.23 ms (single run)
  - TTFT: all within ±2%
- **bench_serving rerun** on two nodes, main vs flag on, both with #46523's mHC change:
  - TPOT, 8K, batch size 1: 8.09 → 8.11 and 8.10 → 8.11 ms
  - TPOT, 32K, batch size 1: 8.15 → 8.19 and 8.16 → 8.20 ms
  - TPOT, 8K, concurrency 16: 13.43 → 13.59 and 13.83 → 13.64 ms. Main alone ranges from 13.43 to 13.83 ms across the three runs, so the +3% of the single run above is within run-to-run spread.
  - TTFT, 2K to 32K: within ±1.7%. Output throughput of the decode configs: within ±0.2%.
  - A third node is slower across the board (TPOT at concurrency 16: 24.8 ms), so its numbers are not listed. Its flag-on deltas are within ±1.2% for TPOT and ±3% for TTFT.
- **Per call under CUDA graph**, flag off vs on:
  - Top-k v2 paged fp32, 8193 positions: 5.5 → 10.1 µs
  - DeepSelect bf16, 65536 positions (single-CTA instead of the cluster tier): 6.8 → 12.3 µs

B300, TP8/EP8, default arguments, overlap scheduling on, main vs flag on, bench_serving (random ids), single run:
- TPOT, 8K, batch size 1: 4.80 → 4.84 ms
- TPOT, 32K, batch size 1: 4.86 → 4.81 ms
- TPOT, 8K, concurrency 16: 6.11 → 6.11 ms
- TTFT, prefill only, 2K / 8K / 32K: 154.5 → 153.5, 164.9 → 161.1, 551.9 → 548.7 ms
- TTFT of the same three decode runs: 169.5 → 177.2, 552.1 → 557.7, 1303 → 1335 ms (+4.5%, +1.0%, +2.5%)
