## Motivation

Joint FULL/SWA allocations can evict more cached prefixes than needed. FULL/SWA/Mamba allocations can fail despite recoverable capacity, or discard the entire cache before rejecting an impossible demand.

Seokwoo Song's original commits are preserved, rebased onto `ae28306a74fc9ba56daab9ccb06dcf45659f58af`.

## Modifications

- Stop allocation-driven eviction at a read-only sufficient-reclaim predicate; prepare and verify the physical layout at bounded phase boundaries.
- Reject demands proven impossible by byte or ID bounds before eviction, and bound token/state reclaim quotas.
- Compute exact unsharded paged-extend demand for the unified SWA allocators while preserving conservative demand elsewhere.
- Update the dLLM KV-reuse test allocator to implement the paged-demand interface with the conservative default, fixing the CPU CI failure.
- Adapt the closed-move-gate regression to the current physical-page copy interface. Preserve main's SWA-preferred reclaim planning for storage-backed HiCache and decode disaggregation.

## Motivation

In unified-memory configurations, KV + SWA allocation can evict more prefix cache than necessary. Mamba + KV + SWA allocation can also fail despite recoverable joint capacity, or discard cached entries before rejecting an impossible request. This change bounds joint reclaim for these allocators to preserve reusable cache and recover capacity for feasible allocations.

## Modifications

- Stop the victim walk when the allocator’s sufficient reclaim predicate is satisfied, then prepare and check the actual allocation.
- Keep the per-victim feasibility predicate read-only and bound preparation to reclaim phase boundaries.
- Use the exact unsharded paged-extend demand where supported, retaining the conservative fallback for other allocators and sharded layouts.
- Reject demands proven impossible by byte/ID bounds before eviction, preserving cached entries in those cases; bound remaining recovery attempts. This is not a complete feasibility solver for every FLOAT layout.

- ch-wan · comment · 2026-09-14T07:35:07Z · [source](https://github.com/sgl-project/sglang/pull/39294#discussion_r4003049663)

File: `python/sglang/srt/mem_cache/common.py` · line None

**[bug][P1] `allocation_ready` is a mutating operation passed as a loop predicate; it runs once per evicted node.** The callback here is `recovery.prepare_token_allocation(num_tokens)`, which is not a query: it calls `_flush_deferred_free_group(...)` unconditionally, and then `_relieve_for_alloc(self, num_tokens)` -- the urgent-compaction ladder that calls `flush_for_allocation()` on every chain member and relocates pages.

Follow where it is consumed. `UnifiedRadixCache._evict_device` defines `target_reached(component_type)`, whose first statement is `if allocation_ready is not None and allocation_ready(): return True`, and `target_reached(ct)` is evaluated at the bottom of the per-node `while True:` walk (`unified_radix_cache.py:907`) as well as per component at `:874`. So a deep eviction round performs a deferred-free flush per evicted node, and a full two-sided compaction per node for as long as the byte bound looks satisfiable. That is O(nodes) compactions for one allocation, on the path that runs under memory pressure.

**Suggestion:** Split the capability in two: a pure `token_allocation_ready(num_tokens)` for the loop predicate (it already exists and is side-effect free), and call the mutating `prepare_token_allocation` only at the boundaries -- once before the walk and once after it -- rather than from `target_reached`. If mid-walk reclaim is genuinely needed, gate it on progress (e.g. only after N nodes, or only when live bytes dropped since the last attempt) so it cannot run per node.

- ch-wan · comment · 2026-09-14T07:35:07Z · [source](https://github.com/sgl-project/sglang/pull/39294#discussion_r4003049666)

File: `python/sglang/srt/mem_cache/unified_radix_cache.py` · line None

**[bug] The second pass is quota'd at the entire cache, so an infeasible allocation evicts everything.** The fallback `_evict` is issued with `num_tokens=self.full_evictable_size()`, `swa_num_tokens=self.swa_evictable_size()`, `mamba_num=self.mamba_evictable_size()` -- i.e. every evictable entry -- and stops only when `allocation_ready()` turns true or the cache is exhausted. Before this change the walk was bounded by the per-component shortfall.

The stopping condition cannot be reached for a demand the pool can never serve: `_token_allocation_byte_shortfall` is `required_bytes + live_bytes + sink_bytes - total_bytes`, so once `required_bytes` alone exceeds `total_bytes - sink_bytes`, the shortfall stays positive even at zero live bytes, `prepare_token_allocation` keeps returning `False`, and the walk runs to exhaustion. The result is a fully dropped prefix cache *and* a failed allocation, where the old code would have evicted only the shortfall and failed. Since `evict_from_tree_cache` is also called speculatively from capacity probes, an over-large `num_tokens` reaching this path is not exotic.

**Suggestion:** Bound the second pass -- stop as soon as a round frees nothing (the contract the deleted tri-pool loop used), or refuse to start it when `_token_allocation_byte_shortfall(num_tokens)` exceeds what the whole cache could release. Add a case asserting that a request larger than the pool leaves the cache intact.

- ch-wan · comment · 2026-09-14T07:35:07Z · [source](https://github.com/sgl-project/sglang/pull/39294#discussion_r4003049670)

File: `python/sglang/srt/mem_cache/allocator/unified_hybrid_swa.py` · line None

**[suggestion] This fixes the same bug as #36729, which rewrites the same three files with an incompatible design.** The defect is real and well-demonstrated -- on main, `full_available_size()=4`, `swa_available_size()=4` and a 4-token request take neither branch of `if full_available_size < num_tokens or swa_available_size < num_tokens`, so nothing is evicted although joint availability is 3. But #36729 (`yonghao/ump-shared-capacity`) is fixing exactly that, and the two changes collide head-on:

- both add a capability protocol to `allocator/base.py`;
- this PR inserts a 14-line recovery block into the body of `evict_from_tree_cache`, which #36729 deletes wholesale and replaces with a one-line delegation to `allocator.evict_to_free_tokens(...)`;
- this PR **deletes** `UnifiedMambaSWATokenToKVPoolAllocator.evict_to_free_tokens`, which #36729 makes the central dispatch point (it adds two such overrides).

A textual merge will resolve to silently dropping one of the two designs. The approaches also differ in kind: #36729 computes a *minimal joint reclaim plan up front* (`reclaim_plan(n, n, ...)` over the byte model) and realizes compaction once via `ensure_capacity`, where this PR re-probes a mutating readiness predicate per evicted node. The former bounds both the eviction and the compaction work by construction.

**Suggestion:** Settle this with the #36729 author before either lands. If #36729's `reclaim_plan` already covers the joint case -- it is byte-joint by construction -- the most valuable part of this PR is the regression suite: `test_unified_joint_allocation_eviction.py` builds a real shared pool at FULL 4 / SWA 4 / joint 3, which is precisely the case #36729 has no test for. Porting those 13 cases onto #36729 would preserve the work and avoid the conflict.

File: `python/sglang/srt/mem_cache/unified_radix_cache.py` · line None

**[suggestion] A predicate named `*_ready` that mutates the allocator will be misread.** Everything at this call site reads as a query -- `if allocation_ready is not None and allocation_ready(): return True` inside a function called `target_reached` -- but the callable threaded in from `common.py` flushes deferred frees and can compact both sub-pools. The next person to add a `target_reached()` call, or to hoist it out of the loop, has no local signal that they are moving reclaim work.

**Suggestion:** Rename the parameter to something that states the side effect (`try_recover_allocation`), or -- better, and consistent with the P1 comment on `common.py` -- pass the pure `token_allocation_ready` here and keep the mutating call at the boundaries.
