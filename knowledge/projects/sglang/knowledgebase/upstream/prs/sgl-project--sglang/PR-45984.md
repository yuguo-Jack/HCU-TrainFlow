# [Feat] serving: Add --clamp-max-new-tokens-to-context to cap max_tokens when the prompt fits

[Upstream PR](https://github.com/sgl-project/sglang/pull/45984) · state: open · merged: False

## Original PR description

## Motivation

Closes #45841.

When the prompt fits the context but prompt + `max_new_tokens` does not, `TokenizerManager._validate_one_request` returns 400. Clients often cannot compute the exact prompt length (it depends on the server's tokenizer and chat template), so a client that sends a fixed `max_tokens` cap, or computes one from an estimated prompt length, gets rejected. The OpenAI API defines `max_tokens` / `max_completion_tokens` as an upper bound, and the scheduler already treats it that way: `init_req_max_new_tokens` clamps it to `max_req_len - input_len - 1` and to the KV budget. The 400 comes only from the frontend check.

The only existing switch, `--allow-auto-truncate`, also truncates prompts that are too long, so it cannot be used to get "cap the output, reject an overlong prompt".

## Modifications

- New opt-in server flag `--clamp-max-new-tokens-to-context` (`serving` namespace, default off). It is appended at the end of `POSITIONAL_FIELD_ORDER`, so existing positional slots don't move.
- `TokenizerManager._validate_one_request`: with the flag, a request whose prompt fits but whose `max_new_tokens` overshoots gets `max_new_tokens` capped to `context_len - input_tokens` (reserved tokens included), the same value the `--allow-auto-truncate` branch already sets. Prompts longer than the context still fail with the existing 400.
- `OpenAIServingChat._validate_request`: with the flag, a `max_completion_tokens` larger than the whole context is accepted as a cap, mirroring how that check already defers to `--allow-auto-truncate`.
- Docs: a row in `server_arguments.mdx`.

Without the flag, behavior is unchanged: the 400 messages match what OpenAI-compatible clients see today, and some depend on them. That is why this is opt-in. Making it the default would be a one-line change if maintainers prefer it.

Related: #33814 fixes a separate off-by-two in the scheduler's clamp at the exact context boundary. The two PRs don't overlap.

## Tests

- New `test/registered/unit/managers/test_tokenizer_manager_length_validation.py` (CPU, 3 cases):
  - With the flag, an overshooting cap becomes exactly the remaining window, reserved tokens included, and a cap that already fits is untouched.
  - Without the flag, the 400 is unchanged.
  - With the flag, an overlong prompt is still rejected and not truncated.
- `test_serving_chat.py`: `max_completion_tokens` above the whole context is a 400 without the flag and accepted with it.
- `test_request_length_validation.py` (GPU, existing file): new `TestClampMaxNewTokensToContext` class. On a server with `--context-length 1000 --clamp-max-new-tokens-to-context`, a ~500-token prompt with `max_tokens=1000` and `ignore_eos` completes with `finish_reason="length"` and prompt + completion ≤ 1000, and a 1200-token prompt still returns 400. `est_time` goes from 49 to 95 for the second server launch.

Each new unit case fails with its code path reverted (the clamp branch, the chat bypass).

Results:
- Unit: the new cases, plus server-args docs coverage and positional order, pass (11 passed). `test/registered/unit/server_args/` and `unit/api/v1/test_parity.py` pass apart from `test_default_transport_is_cpu_for_unsupported_multinode_model`, which fails identically on unmodified `main` in this environment.
- E2E: the whole `test_request_length_validation.py`, existing class and new class, passes (10 passed) on an RTX A6000. I ran it against `Qwen/Qwen3-0.6B`, because the default `meta-llama/Llama-3.2-1B-Instruct` is gated and not available on that machine. CI runs the default model.
