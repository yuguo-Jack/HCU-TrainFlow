# [AMD] Add FlyDSL GDN prefill backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/39595) · state: open · merged: False

## Original PR description

## Motivation

AITER ships fused FlyDSL implementations of the GDN prepare stages and the K5 state scan for AMD gfx95. Qwen3.5-397B has 45 Gated DeltaNet layers, and at TP4 each rank runs them with 4 key heads, 16 value heads and K=V=128. On those shapes the FlyDSL path runs a prefill batch 1.4-1.74x faster than SGLang's Triton GDN prefill.

This PR exposes that path as an opt-in prefill backend:

```bash
--linear-attn-prefill-backend flydsl
```

Decode and speculative verification stay on Triton. The backend requires gfx95 and is rejected with deterministic inference or multi-item scoring. It also serves batches that track Mamba state for the radix cache, so it stays active with radix cache on (e.g. AgentX). It falls back to Triton for unsupported input/state shapes, mixed batches, and graph-planned paths.

## Modifications

- Register `flydsl` in the linear-attention backend enum and CLI choices.
- Add `FlyDSLGDNKernel`, which runs AITER's FlyDSL prepare, FlyDSL K5 state scan and output stages.
  - Calls the stages directly instead of `chunk_gated_delta_rule_opt_vk`. That function returns `(o, final_state)`, and `snapshot_dtype` only sets the dtype of the temporary snapshot the output stage consumes, so the per-chunk states `h` never leave the wrapper. Radix-cache Mamba tracking reads `h`, which is why the adapter runs the stages itself and keeps it.
  - The L2-norm and output stages are imported from AITER's private `_triton_kernels` modules. They match AITER `4ad99832823dde2315b361cbd3b54b1c5c12acd5`, the gfx950 `AITER_COMMIT_DEFAULT` in `docker/rocm.Dockerfile` and the commit in both ROCm images used below.
  - Uses SGLang's native `[N, H, V, K]` state pool with indexed in-place state updates, and reuses the caller-provided output buffer.
  - Remaps DP-attention padding indices to the pool's padding slot, once per batch.
  - `use_exp2=True` is correct here because FlyDSL's fused prepare computes the gate cumsum itself (#39976 uses `use_exp2=False` because it starts from Triton's natural-log prepare). Recurrent state follows `--mamba-ssm-dtype`; per-chunk snapshots are bf16.
- Build AITER's prefill schedule once per eligible forward batch and reuse it across GDN layers.
- Reject FlyDSL for decode/verify, deterministic inference, and non-gfx95 with actionable errors.
- Unit tests for CLI registration, backend validation, dispatch, the AITER call contract, padding indices, per-batch index reuse, and Triton fallback.

## Accuracy Tests

Qwen3.5-397B-A17B-MXFP4, TP4, real EAGLE MTP, 200 GSM8K questions, five-shot chat template with thinking disabled:

| Configuration | Triton prefill | FlyDSL prefill |
|---|---:|---:|
| Radix cache on (state tracking active) | 0.975 | 0.970 |
| Radix cache off | 0.985 | 0.980 |

One answer apart in both modes, which is within sampling resolution at 200 questions. Both arms move together between modes. The radix-off row predates the switch to calling AITER's stages directly; kernel numerics are unchanged by it.

Kernel-level comparison of `FlyDSLGDNKernel.extend` against `TritonGDNKernel.extend` on MI355X, TP4 (Hq=4, Hv=16) and TP2 (Hq=8, Hv=32) shapes, K=V=128, BF16 Q/K/V, BF16 and FP32 state, mixed-length batches up to 16K tokens and a padding row:

- output max abs diff <= 9.77e-4
- final state <= 7.84e-3
- per-chunk states `h` <= 1.56e-2 (same shape and chunk order as Triton's; about one bf16 step)
- state slots outside the batch unchanged

Unit tests: `test_gdn_prefill_backend_policy.py` 23 passed.

## Benchmarking and Profiling

Common setup:

- Hardware: MI355X (gfx950), Qwen3.5-397B-A17B-MXFP4, AITER attention and MoE, FP8 E4M3 KV cache, page size 16, EAGLE 3 / 1 / 4.
- Images: fixed-length runs use `rocm/sgl-dev:v0.5.19-rocm720-mi35x-20260913` with radix cache off and BF16 SSM; AgentX uses `-20260915` with the recipe defaults.
- Variance is the larger of the two arms' run-to-run spreads. **Bold** changes are larger than their variance; the rest are noise.

### GDN prefill microbenchmark

One prefill batch through all 45 GDN layers, TP4 per-rank shapes, wall time including the per-batch schedule build:

| Extend tokens | Triton (ms) | FlyDSL (ms) | Change |
|---|---:|---:|---:|
| 1x1024 | 9.37 | 6.67 | −28.8% |
| 1x4096 | 10.55 | 6.72 | −36.3% |
| 4096+4096+2000+512 | 14.89 | 10.20 | −31.5% |
| 1x8192 | 19.11 | 10.98 | −42.6% |
| 1x16384 | 37.00 | 25.53 | −31.0% |

Below ~4K tokens both are launch-bound, so a batch saves ~3-4 ms. A 70K prompt is five 16384-token chunks and saves about 57 ms.

### Fixed-length serving

Setup:

- InferenceX serving client, TP4, 70000-token input / 300-token output, radix cache disabled (`--disable-radix-cache`).
- 3 runs per arm: 60 requests at concurrency 1, 240 at concurrency 4 and 8.

### AgentX benchmark

Setup:

- Recipe: local run of the InferenceX AgentX recipe (`qwen3.5_fp4_mi355x_sglang_mtp.sh`, `--random-seed 42`), TP4, 3600 s per run, no other job on the node. Not an official InferenceX result.
- Arms: the same commit, differing only in `--linear-attn-prefill-backend` (`67fc5b96` for concurrency 4, `93f3073fe9` for 16). Later commits add only the once-per-batch index remap and main merges.
- Order: Triton, FlyDSL, FlyDSL, Triton, so each arm runs first once and second once. Each value is the mean of that arm's two runs.
