# [Fix] tokenizer: Treat ASGI receive cancellation in the disconnect probe as a client disconnect

[Upstream PR](https://github.com/sgl-project/sglang/pull/39217) · state: open · merged: False

## Original PR description

## Motivation

Related to #39216.

`TokenizerManager._stream_one_response` polls `await request.is_disconnected()` every `SGLANG_REQUEST_STATE_WAIT_TIMEOUT` seconds (default 4 s) while a request is in flight. The traceback in #39216 (observed on `lmsysorg/sglang:dev-dsv41`, a ~200K-token prefill aborted by a client-side timeout) shows an `asyncio.CancelledError` escaping from uvicorn's `receive()` (`message_event.wait()`) inside that call, followed by `kill_process_tree`.

Since Python 3.8, `CancelledError` is a `BaseException`, so it bypasses the `except Exception` handlers in the request path. This PR makes the handling at this single call site explicit and unit-tested, instead of relying on whatever is above it:

- a `CancelledError` that originates from the transport/ASGI receive channel (our own task is **not** being cancelled) is treated as "the client disconnected" and flows into the existing `abort_request()` path;
- a cancellation of our own task (e.g. graceful shutdown) is **always re-raised**.

I want to be upfront about the scope: I could not make a stock server exit on a client disconnect in my own testing (details below), so this is a hardening of the exact call site in the #39216 traceback, not a change to an observed-reproducible failure. On every path I could trigger, behavior is unchanged.

## Modifications

Adds `TokenizerManager._is_request_disconnected()` and uses it at both call sites of `await request.is_disconnected()` in `tokenizer_manager.py`. When a `CancelledError` surfaces from the poll it distinguishes:

1. **Our own task is being cancelled on purpose** — detected via `Task.cancelling() > 0` on Python 3.11+, or via the engine's existing `gracefully_exit` flag as a fallback on 3.10 (`requires-python >= 3.10`, so `Task.cancelling()` cannot be relied on unconditionally). The `CancelledError` keeps propagating; swallowing it could hang shutdown.
2. **The transport tore down the connection** — treated as "client disconnected" and routed to the engine's existing per-request `abort_request()` path, unchanged.

### Why this catch is safe

`is_disconnected()` only touches the HTTP/ASGI transport layer. It never reaches the scheduler process, the KV cache or any CUDA state (all behind an IPC boundary from the tokenizer manager), so treating this particular cancellation as request-scoped cannot continue serving from corrupted GPU/scheduler state, unlike a broader catch-all would.

## Validation

Environment: 8x RTX 6000D (SM120), Python 3.12.3, one GPU per server, Qwen3.8-27B-FP8 (TP1, `--context-length 262144 --mem-fraction-static 0.88`). Two images, each run once **stock** and once **with this PR's `tokenizer_manager.py`** (applied with `git apply`; hunks apply cleanly, offsets -7 / +89..93):

- `lmsysorg/sglang:dev-dsv41` (`sha256:4a5d132a…`, sglang `da64c5cb`, the image from #39216)
- `lmsysorg/sglang:v0.5.21-cu130` (sglang `e00930c`)

**1. Unit tests (CPU only).** The 7 added tests pass in both images (13.9 s / 14.6 s).

**2. Client-disconnect tests that land on the probe** (identical script on all four servers). Every request used a never-cached random prompt; a dropped request is a socket closed by the client, alternating FIN and RST:

| Case | Requests | Client behaviour |
|---|---|---|
| A | 5 | non-streaming, ~200K-token prompt (full prefill ≈ 65 s), dropped after 20 s |
| B | 10 | 5 streaming + 5 non-streaming, 500-word prompt, `max_tokens=1500`, dropped 8 s in (decode phase) |
| C | 8 | concurrent ~200K-token prompts, dropped after 10-30 s |

Results (the same on all four servers):

| | stock dev-dsv41 | PR dev-dsv41 | stock v0.5.21 | PR v0.5.21 |
|---|---|---|---|---|
| `sglang:num_aborted_requests_total` | 23 | 23 | 23 | 23 |
| `/health` after every case (8 checks) | 200 | 200 | 200 | 200 |
| engine exit / `kill_process_tree` / `Received sigquit` in logs | 0 | 0 | 0 | 0 |
| `CancelledError` in logs | 0 | 0 | 0 | 0 |
| big (8192-token) prefill batches for 13 never-cached 200K prompts | 62 | 65 | 64 | 62 |

All 23 dropped requests were aborted by the engine. Without an abort, 13 long prompts would need about 25 prefill batches each (about 320 in total); the observed 62-65 show the prefills were cut off shortly after the disconnect.

To check whether the new branch is ever taken, the PR build was run with two temporary log lines (not part of this PR): one when `is_disconnected()` returns `True`, one when it raises `CancelledError`. On both images: `is_disconnected()` returned `True` 18 times (the disconnect probe is exercised) and **raised `CancelledError` 0 times**.

## Limitations

- I could not reproduce the engine exit from #39216 on stock `dev-dsv41` or `v0.5.21` (the DeepSeek-V4.1 TP4 configuration from the report did not load in my environment, so these runs use a single-GPU Qwen3.8-27B-FP8; the code path under test is in `TokenizerManager` and does not depend on the model).
- With a real uvicorn and real client disconnects (FIN and RST), `request.is_disconnected()` did not raise `CancelledError` in any of the 18 probe hits, so the new swallow branch is covered by the unit tests only. I do not have a trigger for the transport-originated case.
- A cancellation of the request task itself is re-raised, so this change does not alter the outcome in that case.
- Not run: the full CI suite and multi-GPU tests (no CI yet; the PR is waiting for the `run-ci` label).
