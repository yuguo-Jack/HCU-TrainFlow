# [Feat] [AMD] dsa: Enable DCP on the triton sparse-MLA backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44322) · state: open · merged: False

## Original PR description

## Motivation

[#43735](https://github.com/sgl-project/sglang/pull/43735) enabled `--dcp-size > 1` for the RoPE DSA models, but only on the `trtllm` DSA backends. ROCm runs DSA on `triton`, where DCP is still broken. This PR builds on #43735 and fixes the missing pieces:

- The triton sparse-MLA kernel returns no LSE, so the per-rank partials cannot be merged.
- The HIP FP8 latent KV write ignores DCP sharding. It writes row `slot`, while the reader looks up row `slot // dcp_size`, so DCP4 output is garbage.
- The MTP draft keeps a replicated pool that is `dcp_size` times larger and attends it with `dcp_size` 1. Under a long agentic replay this path crashed every c16 run: all 4 ranks hit a GPU memory access fault at the same trace position, about 10M cumulative prefill tokens in.

It also makes DCP prefill cheaper, since every DSA extend used to go through the decode kernel.

## Modifications

Correctness:

- **`[ROCm] DSA DCP on the triton sparse-MLA backend`**
    - `triton_sparse_mla_decode_splitk(..., return_lse=True)` returns a base-2 LSE from both the fused and the split-K reduce kernel, in the format the existing MLA DCP merge expects.
    - Under DCP, triton decode, target verify and paged extend go through #43735's `localize_dcp_page_table`, then hand `(out, lse)` to the merge.
    - The ROCm fused rope+cache write is disabled under DCP, because it writes the unsharded slot.
- **`[ROCm] Shard the DSA FP8 latent KV write under DCP`**
    - The FP8 quant write only writes `slot % dcp_size == dcp_rank`, at row `slot // dcp_size`, the same rule as the BF16 write.
- **`[ROCm] Shard the DSA MTP draft KV like the target under DCP`**
    - On ROCm the DSA EAGLE/NEXTN draft runs under DCP and shards its KV like the target: same allocator page and owner rule.
    - Draft extend goes through the DCP owned-slot path with an LSE merge.
    - The draft runner's translator is bound to its backends for gathered-prefix reads.
    - This removes the replicated draft pool and the c16 crash. The draft KV also shrinks from 5.85 GB to 2.26 GB per GPU.

Performance:

- **`[ROCm] Bound the triton DCP sparse-MLA scan by the owned top-k count`**
    - `localize_dcp_page_table` already returns the per-row owned count, but the triton path dropped it and scanned all top-k slots, masking about (W-1)/W of them.
    - The kernels now stop after the owned tiles.

- **`[ROCm] Split DSA prefill indexer rows across the DCP group`**
  - DCP now splits the rows evenly across ranks instead of computing the same top-k `W` times.
  - The results are all-gathered directly into the destination buffer when possible.

- **`[ROCm] Gather the DSA prefill prefix under DCP when beneficial`**
  - Shorter prefixes use gathered KV, avoiding the Q gather and partial-output merge.
  - Longer or unaligned prefixes and graph replays keep the owned path; a 360K-token prefill drops from 70 seconds to 18 seconds.

Without DCP nothing changes: the new arguments default to the old behavior. CUDA is untouched; the draft sharding is gated on `is_hip()`. On ROCm, pass `--dsa-prefill-backend triton --dsa-decode-backend triton`, because #43735 defaults to `trtllm` when they are unset.

## Performance

InferenceX agentic replay on this head, TP4/EP4 + DCP4 with MTP (simulated AL 3.61), 1 h per point. All four points finish with no GPU fault. The TP4 rows without DCP with HiCache are for reference only.

| Conc | Config | P90 Interactivity (tok/s/user) | TPUT per Chip (tok/s/GPU) | Chip Cache Hit Rate | CPU Cache Hit Rate | Theoretical Cache Hit Rate |
|---|---|---|---|---|---|---|
| 16 | TP4  | 53.07 | 17,396 | 71.1% | 22.7% | 97.0% |
| 16 | TP4 + DCP4 | 43.44 | 17,077 | 96.7% | — | 97.0% |
| 24 | TP4 | 14.07 | 10,872 | 18.6% | 57.5% | 96.2% |
| 24 | TP4 + DCP4 | **32.39** | **23,512** | 96.8% | — | 97.2% |
| 40 | TP4 | 7.19 | 5,144 | 31.2% | 0.9% | — |
| 40 | TP4 + DCP4 | **19.74** | **25,513** | 95.1% | — | 97.0% |
| 48 | TP4 | 6.30 | 4,781 | 27.3% | 0.9% | — |
| 48 | TP4 + DCP4 | 3.59 | **13,198** | 82.1% | — | 96.5% |

- At c24 and c40, DCP4 keeps almost the whole working set in HBM. Throughput per GPU is 2.2x and 5.0x the baseline, and P90 interactivity is 2.3x and 2.7x.
- At c16 the baseline still fits most of its working set (HBM plus host), so DCP4 matches its throughput but trails on P90 interactivity.
- At c48 the DCP4 pool fills up: chip hit rate drops to 82%, and DCP rejects HiCache, so evicted prefixes are recomputed. Throughput per GPU stays 2.8x the baseline, but P90 interactivity falls below it.

## Known issues

- DCP rejects HiCache, so once the DCP pool is full (c48 above), evicted prefixes are recomputed rather than reloaded from host. HiCache under DCP is a #43735 fast follow.
