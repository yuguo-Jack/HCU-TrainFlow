# [Perf] fp8: Hopper small-M GEMV, fused KDA output quant, CUDA grouped top-k, partial-block tails

[Upstream PR](https://github.com/sgl-project/sglang/pull/45828) · state: closed · merged: True

## Original PR description

## Motivation

Split out from the Ling-3.1-flash day-0 support effort.

Block-FP8 decode on Hopper spends small-M linear work in GEMM kernels that are built for large batches, the KDA output normalization and FP8 quantization run as separate kernels, the 512-expert sigmoid router goes through a generic Triton top-k, and weights whose K dimension is not a multiple of the 128-wide quantization block cannot use the native Triton/DeepGEMM paths at all. This PR adds opt-in fast paths for each, with explicit dispatch contracts and no change to default behavior.

Measured on H200 with Ling-3.1-flash (FP8, TP8+EP8+NEXTN, fp32 router as on current main): batch-size-1 decode output throughput **+7.3%** (218.6 → 234.6 tok/s), median TPOT **−8.5%**, both environment flags on vs current main; throughput at concurrency 16 is unchanged. Accuracy on full GSM8K is unchanged (see below).

## Modifications

- **Hopper small-M GEMV** (`SGLANG_ENABLE_FP8_BLOCK_GEMV`, default off): CUDA block-FP8 GEMV for M≤8 with optional fused side projection, and a BF16 tiny GEMV (N≤64, M≤4, SM90 only) under `--bf16-gemm-backend gemv`. Dispatch checks device, dtype, layout, scale grid, and shape; anything else keeps the existing path. Also a CUDA router gate matvec (fp32/bf16 weight) for the Bailing-class gate shape, gated the same way.
- **Fused KDA output quant** (`SGLANG_ENABLE_FUSED_KDA_OUTPUT_QUANT`, default off): the gated RMSNorm at the KDA output fuses with FP8 quantization, emitting the `(q, scale)` tuple the FP8 o_proj consumes; requires target-verify batches and BF16, falls back otherwise.
- **CUDA grouped top-k** for the 512-expert / 8-group / group-top-4 / topk≤8 sigmoid routing shape. Dispatch is shape-driven (no model check): any model with the matching shape uses it, everything else keeps the Triton path. Shared-slot weighting follows the same contract as `moe_fused_gate` (incl. `renormalize=False` and zero-score semantics).
- **Partial-block FP8 support** (opt-in per layer): serialized block-FP8 weights whose K crosses a quantization block boundary — partial-block quant/GEMM in the native Triton MoE, a `prequant_k_tail` dispatcher for pre-quantized inputs (DeepGEMM only when the TMA alignment contract holds: contiguous operands, base pointer and K divisible by 16), and fused SwiGLU+quant for two-group K-tails. All admission is opt-in and default-off; no in-tree model enables it yet (the Ling3 model PR follows separately).

Traces on H200 (bs=1 decode, flags on): the 510 dense FP8 GEMM calls move from DeepGEMM `sm90_fp8_gemm_1d2d` to the GEMV kernel, the 189 KDA norm+quant pairs collapse into the fused kernel, and the router matvec runs its CUDA path. On GB300 (SM103) every SM90-gated path is a no-op — OFF/ON kernel sequences are identical — while the shape-driven top-k runs normally.

## Accuracy Tests

- H200 8x, Ling-3.1-flash FP8, TP8+EP8+NEXTN, full GSM8K (1319 questions, temp 1.0, top_p 0.95, 2 rounds per mode): OFF 96.89% / stop 99.92% vs ON 97.04% / stop 99.89% (within ±0.5pp run noise). GB300 4x TP4+EP4: OFF 96.82% vs ON 96.97%, stop 99.92% both.
- Kernel numerics (H200 + GB300): new GEMV/side-projection, router matvec, fused KDA quant, grouped top-k (incl. `renormalize=False` shared-slot and zero-score cases), block quant tail, Triton K-tail (incl. aligned-K non-fusion and explicit zero clamp vs `None`) suites all pass; partial-K linear matches a dequant-fp32 reference on both the DeepGEMM route (K=160, descriptor built) and the Triton fallback (K=161). On GB300 the SM90-only suites skip cleanly and the K160 selector rejects with bitwise-generic output.
- Kimi-Linear-48B BF16 smoke (KDA fallback path): 100-question GSM8K 93.0%, stop 100%.

## Speed Tests and Profiling

H200, Ling-3.1-flash TP8+EP8+NEXTN, 3 rounds bs=1 (2048/512) + 2 rounds conc16 (8192/1024), `--flush-cache`, seed 11:

| workload | main | this PR (env off) | this PR (flags on) |
|---|---|---|---|
| bs=1 output tok/s | 218.6 | 221.6 (+1.4%) | 234.6 (+7.3%) |
| bs=1 median TPOT (ms) | 4.351 | 4.191 (−3.7%) | 3.981 (−8.5%) |
| conc16 output tok/s | 1087.6 | 1087.8 | 1094.9 (+0.7%, within run noise) |

The +1.4% with flags off comes from the shape-driven grouped top-k; the flags-on gain comes from the GEMV and fused KDA quant. The CUDA router matvec is neutral at fp32/M=4 (1.41 vs 1.30 ms in trace) and is not claimed as a speedup. Concurrency-16 gains are diluted by MoE/attention compute; low-batch decode is where these kernels pay.

Note: the K160 large-M specialization (H20-3e) is intentionally **not** in this PR — it needs qualifying-hardware evidence and will follow separately.
