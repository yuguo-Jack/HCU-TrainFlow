# [Perf] dsa: Reuse metadata kernels across batch sizes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43627) · state: open · merged: False

## Original PR description

## Motivation

A DSA server with speculative decoding on NVIDIA stalls requests for about 300 ms at each new capture size during ramp-up on an empty Triton cache. New containers from the shipped Docker configs start this way unless the operator provides a cache. On B200 with 2-layer DeepSeek-V3.2 and dummy weights, this PR cuts excess first-pass time on a ramp to concurrency 64 from about 12 s to about 6.5 s. At TP1, concurrency levels with a stream gap over 100 ms fall from 28 and 27 to 10 and 9.

DSA metadata kernels take batch size as a compile-time value, and capture does not run them on NVIDIA, so each new size compiles another Triton variant at its first replay.

The gain is one-time, and 40 other ramp compiles, about 4 s, remain. Non-speculative serving, a warm disk cache, steady state and peak stall show no material gain.

No open PR makes this change, but #46630 (draft) would remove this gain at k-pool 1 on CUDA, the path measured here, with new kernels that keep `bs` compile-time.

## Modifications

Decode, target verify and draft extend take batch size at runtime, in the ordinary and fused k-pool kernels. `bs` is in `do_not_specialize`, because Triton otherwise compiles a second variant for multiples of 16. Tile sizes stay compile-time, so each combination of tile sizes still compiles once. A `next_n` that is not a power of two can split a `BLOCK_BS` bucket. Existing configs keep their flags and outputs.

## Accuracy Tests

`f223b4d54e` is the last head before I squashed this branch onto main `7b88f09239`. The squash kept the same diff, and I did not repeat these runs on it. On the squashed commit, only pre-commit ran.

No model accuracy eval ran. On `f223b4d54e`, on B200 with synthetic inputs, the kernel tests match eager references. Their compile reuse checks at batch sizes 9, 12 and 16 fail on main's kernels and without the `do_not_specialize` entry. The backend replay test, at batch size 4, found fused and ordinary metadata equal. One-off sweeps at default capture sizes up to 256, the only check for writes past the live rows, found no such write and no reference mismatch.

No run of this patch checked AMD, other NVIDIA architectures, real weights, TP8, the server k-pool path, startup time, or a startup prewarm. Upstream tests have not run.

When the supported CUDA k-pool path is used (for example GLM-5.3 with `index_kpool=4` and page size 64), `SGLANG_EXPERIMENTAL_DSA_KPOOL_METADATA_FUSION` defaults to true (`environ.py:1729`) and `_init_kpool_metadata_fusion` replaces all three ordinary wrappers changed here with functions from `dsa_kpool_metadata` (`dsa_metadata_manager.py:41-70`). A repo-wide search shows those active decode/verify/draft kernels still declare `bs: tl.constexpr` (`decode.py:38`, `verify.py:42`, and `draft_extend.py:42`), so this default production path continues compiling for every batch size and does not receive the advertised stall reduction; make `bs` (and verify's `expanded_size`) runtime in the pool-aware kernels too.
