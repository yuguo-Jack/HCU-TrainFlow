# [Perf] dsa: Reuse metadata kernels across batch sizes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43627) · state: open · merged: False

## Original PR description

## Motivation

DSA metadata kernels use batch size as a compile-time value. Changing the request count can trigger another compilation and delay serving. This affects the ordinary metadata kernels and the default fused k-pool path.

## Modifications

Pass batch size at runtime for decode, target verify and draft extend, including pooled kernels. Target verify also computes the expanded size at runtime. Tile dimensions and other shape parameters remain compile-time values, so Triton can still specialize within tile buckets.

## Accuracy Tests

Both complete metadata CUDA suites pass on the updated branch on an RTX 5070 Ti (SM120), using normal package imports. They compare eager references and cover compilation reuse, request remapping, boundary cases and CUDA graph replay. The compilation-reuse regression failed before the runtime-batch change and passes afterward.

Full model accuracy, server startup and performance, and other GPU architectures remain unverified.

Run the attention kernel suites with `python -m pytest` in a compatible CUDA environment or through the registered CI runner. Scoped formatting passes.

## Speed Tests and Profiling

Earlier local measurements reused compiled kernels when tile dimensions and Triton's remaining specialization attributes matched. Launches for the measured batch-size changes took 65 to 98 ms before the change and 0.02 to 0.10 ms afterward. Triton can still create additional variants within a tile bucket, including for different integer divisibility.

Steady CUDA graph GPU medians ranged from 0.983x to 1.022x after versus before, with no material change observed. These kernel measurements predate the latest base update and do not establish end-to-end B200 or TP8 server gains.
