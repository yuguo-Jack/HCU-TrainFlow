# [Fix] mistral3: Subclass LlavaForConditionalGeneration instead of wrapping it

[Upstream PR](https://github.com/sgl-project/sglang/pull/45656) · state: closed · merged: True

## Original PR description

## Motivation

`unsloth/Mistral-Small-3.1-24B-Instruct-2503` fails to start since #44913, which breaks `test_vlms_mmmu_eval` in the `nightly-2-gpu-large` job:

```
File ".../model_executor/runner/base_runner.py", line 250, in model_context
    shared_experts=self.model_runner.model.shared_experts_config
AttributeError: 'LlavaForConditionalGeneration' object has no attribute 'shared_experts_config'
```

Failing job (nightly 10/21, `8e3e2980d`): https://github.com/sgl-project/sglang/actions/runs/39614482141/job/119271892420

**Root cause:** `Mistral3ForConditionalGeneration` was a plain Python wrapper around an inner `LlavaForConditionalGeneration`, not an `nn.Module`. Loaders keep what `model.eval()` returns. The wrapper forwarded `eval` to the inner model through `__getattr__`, so the server ended up holding the inner Llava model and the wrapper was dropped. That lost:
1. `shared_experts_config`, which `_initialize_model` sets after construction. That's the startup crash.
2. The wrapper's `load_weights`, which normalizes transformers v5 Mistral3 checkpoint names (`model.language_model.*`, `model.vision_tower.*`, `model.multi_modal_projector.*`, `lm_head.*`). Initial loading still went through the wrapper, but weight updates after startup (from disk, distributed, or tensor updates) call `load_weights` on the kept inner model, so a v5 name like `model.language_model.embed_tokens.weight` would raise `KeyError` there.

## Modifications

- Make `Mistral3ForConditionalGeneration` a subclass of `LlavaForConditionalGeneration`:
  - the base constructor already builds `MULTIMODAL_PROJECTOR_TYPE`, so the Mistral3 projector comes from that;
  - `get_image_feature` becomes a normal override instead of a method monkeypatched onto the inner model;
  - `load_weights` normalizes names, then calls `super().load_weights(...)`.
- Remove the wrapper's `inner`, the forwarding dunders (`__getattr__`, `__setattr__`, `__call__`) and the monkeypatch. Parameter names are unchanged (`language_model.*`, `vision_tower.*`, `multi_modal_projector.*`), so checkpoint loading is unaffected.
- `llava.py` imported `MistralForCausalLM` at module level only for `LlavaMistralForCausalLM`'s constructor. Move that import into the constructor to break the import cycle that motivated the wrapper.

## Tests

`test/registered/unit/models/test_mistral3_vision_feature.py`. I replaced the earlier test, which asserted that `eval()` returns the inner model, with regression tests for the full contract:
- **`eval()` keeps the Mistral3 model:** `model.eval() is model`, the same `shared_experts_config` object survives, child modules are in eval mode, and Mistral3's image-feature path still runs (the projector receives `image_sizes`).
- **Weight names:** transformers v5 checkpoint names reach the same destinations when loaded before `eval()` (initial load) and after `eval()` (weight updates).
- **Import order:** `sglang.srt.models.mistral` and `sglang.srt.models.llava` import cleanly in either order, each in a fresh interpreter.

The existing vision-feature tests are unchanged.

Before the refactor, `/rerun-test registered/accuracy/models/test_vlms_mmmu_eval.py` passed with the earlier `__setattr__` fix (MMMU 0.5598 against a 0.30 threshold). It needs a rerun on this revision.
