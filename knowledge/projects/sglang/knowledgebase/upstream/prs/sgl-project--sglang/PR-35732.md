# [Bugfix] Retry deterministic persistent kernels after shared-memory OOR

[Upstream PR](https://github.com/sgl-project/sglang/pull/35732) · state: closed · merged: False

## Original PR description

## Summary

- Retry deterministic persistent matmul and BMM with `num_stages=2` only when Triton reports a shared-memory `OutOfResources` error.
- Cache a successful fallback by operator, normalized device, dtype, and the complete original kernel config, while logging one warning per cache key.
- Add CPU tests for the exception and cache contract plus CUDA tests that exercise both real persistent kernel launch sites.

## Root cause

The fixed float16 persistent-kernel config uses `num_stages=3`. On affected SM89 deployments, Triton can compile that launch to require 106496 bytes of shared memory, exceeding the 101376-byte per-block limit. Because the footprint depends on the architecture, compiler, and specialization, a static architecture gate can either miss affected builds or unnecessarily reduce stages on builds where stage 3 fits.

This change preserves the existing stage-3 fast path. It retries only the exact shared-memory resource failure, caches only after a successful stage-2 launch, and leaves non-shared-memory failures untouched. Shapes and batch size are intentionally excluded from the cache key so one process does not switch launch configuration based on request batching.

This addresses #29149 and is a runtime alternative to the static config selection proposed in #34486.
