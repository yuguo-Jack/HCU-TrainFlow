# [Perf] [NVIDIA] deepseek_v41: enable small-batch dense split-K by default

[Upstream PR](https://github.com/sgl-project/sglang/pull/47232) · state: closed · merged: False

## Original PR description

## Motivation

On a pinned-tactic DeepSeek-V4.1-Flash baseline, small-batch WQKV-A and shared
FC1 launch only 14 and 9 CTAs per layer on B300. FlashInfer's existing
cluster-local split-K=4 improves their kernel latency. A target-only serving
A/B measured a 1.25% plain decode-throughput improvement and a 1.00% reduction
in mean full-request latency.

**Draft:** those serving measurements used SGLang
`bf9a666c7495e85f651849f154cffd0f94adb39d`, not the latest main. Current main
autotunes small-M MXFP8 calls and may already choose split-K. This PR enables
the narrowly scoped policy by default, with an explicit opt-out. A speedup
over current main has not been measured.

## Modifications

- Enable `SGLANG_OPT_DSV41_SMALL_BATCH_SPLIT_K` by default; set it to `0`
  to disable the policy.
- Apply only to the target model's `self_attn.wqkv_a` and
  `mlp.shared_experts.gate_up_proj`. NextN/DSPARK draft constructors do not
  install the override.
- Use split-K=4 only on B300/SM103, CuTe DSL, BF16 output, M=1..8 and local
  (N,K)=(1792,5120) or (1152,5120), with contiguous swizzled MXFP8 operands.
  Other calls retain their existing dispatch.
- Preserve the existing path under deterministic inference or batch-invariant
  mode. The selected tactic bypasses autotuning only for eligible calls.
- Reuse the existing linear dispatch and custom-op/fake-op boundary, plus
  FlashInfer's CuTe runner and input validation. There is no process-wide
  runner monkey patch or new CUDA kernel.
- Add GPU tests, including default-enabled and explicit opt-out behavior.

The explicit tactic currently needs FlashInfer's private runner API because
public `mm_mxfp8` has no tactic argument. This dependency is isolated in the
existing MXFP8 custom-op wrapper and needs review before promotion from draft.

## Accuracy Tests

The PR's GPU tests cover both shapes at M=1/2/4/6/8 against an independent FP32
GEMM of dequantized operands (relative L2 < 0.5%), prequantized-input parity,
unsupported shape/dtype/hardware fallbacks, both consistency controls,
model default and opt-out wiring, bias/leading dimensions, CUDA Graph replay
with changed inputs, scale length/dtype validation, and the torch.compile
custom-op boundary.

Validation completed on B300 with the PR source and FlashInfer 0.7.2:
`python test/registered/kernels/ops/gemm/test_dsv41_mxfp8_split_k.py`
passed all six tests with warmed compilation caches. The environment
used PyTorch 2.13.0+cu130; the complete current-main PyTorch 2.14.1 environment
and full-model serving were not tested. The initial five cases also passed
with FlashInfer 0.6.18 before the additional scale-buffer regression case.
All applicable pre-commit hooks passed, including registered-test validation.

The prior 60-case isolated sweep had relative L2 error < 1% against FP32 and
maximum relative L2 difference 4.71e-5 against the original BF16 outputs.
Split-K changes reduction order and is not bitwise equivalent. Checkpoint-level
accuracy/model-quality parity has not been established.

## Speed Tests and Profiling

Historical serving A/B: four B300 GPUs, TP4/EP4, FlashInfer 0.6.18,
PyTorch 2.13.0+cu130; twelve natural SPEED-Bench prompts, mean input 1074 tokens,
two repetitions/configuration, concurrency 1, 512 greedy output tokens.
All 96 requests completed. Cache was flushed before requests; profiling was
separate from timing.

| Metric | Baseline | Split-K=4 | Change |
| --- | ---: | ---: | ---: |
| Plain median TPOT | 3.58360 ms | 3.53936 ms | -1.23% |
| Plain decode throughput | 279.05 tok/s | 282.54 tok/s | +1.25% |
| Plain mean request latency | 2069.83 ms | 2049.14 ms | -1.00% |
| DSPARK mean request latency | 1144.46 ms | 1132.45 ms | -1.05%, inconclusive |
| DSPARK weighted acceptance length | 2.90634 | 2.93200 | +0.88% |

Plain trial median TPOT was 3.58422/3.58306 -> 3.53848/3.54034 ms.
DSPARK's paired prompt-bootstrap 95% interval includes zero (-2.52% to +4.58%).
Its pooled median TPOT change of -6.73% is acceptance-sensitive and is not
presented as a reproducible kernel gain. Sequential runs do not exclude drift.

Separate serving traces measured WQKV 7.390 -> 5.842 us/call and shared FC1
6.974 -> 5.110 us/call. Shared-expert work largely overlaps routed experts,
which explains why additive kernel savings exceed end-to-end savings. Every
eligible optimized target graph contained exactly 40+40 split-K calls;
baseline and draft graphs contained none. There was no separate projection
ablation or high-concurrency measurement.
