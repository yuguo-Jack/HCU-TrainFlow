# [Fix] scheduler: Skip a chunked prefill when the KV pool holds no free page

[Upstream PR](https://github.com/sgl-project/sglang/pull/45685) · state: open · merged: False

## Original PR description

## Motivation

A server started with `--schedule-policy shortest-prefill-first` dies with `RuntimeError: Out of memory. Try to lower your batch size.` once the KV pool is fully locked while a chunked prefill is in progress. We hit it on three of four one-minute windows of the Mooncake tool-and-agent trace (Kimi production traffic, FAST'25) replayed against Qwen3-8B on one A100 with `--max-total-tokens 160000`. `fcfs` and `lpm` did not pack the pool that tightly in the same runs.

A chunked prefill holds KV that is only released when the whole prefill finishes, so a continuing chunk has to run even when the pass budget is negative. The budget is negative in two different situations. Usually the running requests' decode headroom (`total_offset`) exceeds the free pool, and the chunk may borrow from it because that memory exists. Sometimes the pool is physically full: every slot locked by running requests and by the chunk's own earlier chunks, nothing free, nothing evictable. `PrefillBudget.available_chunk_tokens` returned the full chunk size in both cases. In the second one `prepare_for_extend` asked `alloc_token_slots` for tokens the pool did not hold, eviction found nothing, and the scheduler process raised:

```
Out of memory. Try to lower your batch size.
Try to allocate 1 tokens.
Available full tokens: 0 (full_available_size=0 + full_evictable_size_=0)
```

(`_get_new_batch_prefill_raw` -> `prepare_for_extend` -> `alloc_for_extend` -> `alloc_token_slots`)

## Modifications

- `PrefillBudget.available_chunk_tokens` (the single-pool budget): when the pass budget is spent, the chunk is bounded by what the pool physically holds, free plus evictable tokens minus one page, instead of getting its full size. The page keeps the chunk's page-rounded allocation inside the pool. When less than a page is left after that, it returns None and `PrefillAdder.add_chunked_req` hands the chunk back unadmitted, the path the SWA budget already takes when its window budget is spent.
- `Scheduler._get_new_batch_prefill_raw`: a chunk handed back unadmitted ends the prefill pass with no batch. The next iteration is a decode step over the running batch, which frees memory by finishing a request or retracting one, and the chunk continues the step after. Before, the pass went on to admit waiting requests. Every prefill batch counts the chunked request as a chunk in flight (`inflight_middle_chunks`), and the result processor decrements the count only for the chunk it finds inside the batch, so a batch built without the chunk would leave the count one too high for good and the request would never pass the `inflight_middle_chunks <= 0` gate that commits its output. The same hole existed for a chunk parked by `SWAPrefillBudget` while a small request still fit. The stash gate already expects a parked chunk (`extend_end` stays at `prefix_len`, #26938).

Nothing is behind a flag. Behaviour changes only in the state that raised before, plus the SWA case above. The SWA and shared-pool budgets are unchanged: `SWAPrefillBudget.available_chunk_tokens` already caps at `remaining_swa - page_size` and returns None when nothing is left, and `SharedSWAPrefillBudget.fit_chunk` searches for the largest chunk `can_reserve` accepts. The single-pool class was the only one handing out tokens the pool did not hold.

## Notes for reviewers

- Why None rather than one page: a page that does not exist fails in the allocator exactly as the full chunk did.
- A parked chunk cannot wait forever. The parked branch needs a spent budget, and `total_offset` comes from the running requests' decode headroom (plus mixed-chunk decode rows). With nothing running it is zero; the chunk's own locked prefix is at most `max_req_len - 1` tokens and `max_req_len` is below the pool size (checked in `tp_worker`), so the positive branch always hands over at least one token. With something running, the next decode step finishes or retracts a request.
- Which policies reach the state: any that admits requests next to the chunk until the pool is completely locked. `shortest-prefill-first` does, through `shortest_prefill_chunk_limit`. It needs a pool small enough for long prompts to fill (160k tokens with prompts of up to 50k tokens here). `fcfs`, `lpm` and priority scheduling did not reach it in a 75-row table at the same settings.
- TP ranks see the same allocator and tree state, so they park the same step. With the prefill delayer, `PrefillDelayerSinglePassExecutor.finalize` negotiates `local_prefillable=False` for a pass that never negotiated, so a rank that parks still takes part in the collective. Both read from the code, not measured: our runs are TP 1 without DP attention.
- Not tested: page size above 1 (the one-page slack is derived, not measured), TP above 1, DP attention, speculative decoding, PD disaggregation, Mamba and SWA models, dLLM (its chunk path does not call `available_chunk_tokens`).

## Tests

Two CPU cases in `base-a-test-cpu`:

- `test_continuing_chunk_never_exceeds_physical_tokens` in `test/registered/unit/mem_cache/test_prefill_memory_budget.py`: with the budget spent and 100 tokens free the chunk gets 99; with nothing free it is parked. Main returns the full chunk size in both.
- `test_parked_chunk_builds_no_batch` in `test/registered/unit/managers/test_scheduler_parked_chunk.py`: a parked chunk builds no batch, leaves the waiting queue intact and is not counted in flight. Main admits the waiting request and builds the batch.

Run on an A100 pod with this branch installed at upstream main `da7b97a737`: both files pass on the branch (17 and 1 tests). With the branch's test files against main's sources, the budget case fails with `AssertionError: 8192 != 99` and the parked-chunk case fails because main goes on to build the batch. CI has not run yet (draft).

## Accuracy Tests

Not affected. The change decides when a chunk runs, not what it computes; a parked chunk resumes from the same prefix one step later.

## Speed Tests and Profiling

No effect on the normal path: one extra comparison when the budget is positive. In the state that raised before, the server now survives. With the fix, the shortest-prefill-first rows on the four pinned windows (Mooncake tool-and-agent trace, 160k-token pool, arrivals slowed 15x, 1,738 requests) completed with a mean JCT of 15.46 s against 17.50 s for fcfs at the same 0.48 req/s, with two retractions. Before the fix three of those four windows died at the first fully locked pool.

Reproduction, server args of a crashed row:

```
sglang serve --model-path Qwen/Qwen3-8B --context-length 131072 \
  --json-model-override-args '{"max_position_embeddings": 131072, "rope_scaling": {"rope_type": "yarn", "factor": 4.0, "original_max_position_embeddings": 32768}}' \
  --enable-hierarchical-cache --hicache-size 80 --enable-metrics \
  --schedule-policy shortest-prefill-first --max-total-tokens 160000
```

Replay: the tool-and-agent trace at 15x slowdown, one-minute window at minute 10, each block id mapped to a fixed 512-token block so prompts keep the trace's lengths and sharing (`cache_aware_mlfq/mooncake_replay.py` in https://github.com/abdullahyousaf1798/sglang-cache-aware-mlfq, where the crash logs are kept under `cache_aware_mlfq/results/*.crashed-1/server.log`).
