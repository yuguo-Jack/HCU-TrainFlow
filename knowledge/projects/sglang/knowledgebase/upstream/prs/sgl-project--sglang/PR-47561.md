## Motivation

In a decode MoE layer two streams run after the attention boundary:

- main stream: the pre-expert projection (pooler), the all-gather, then the pre-expert RMSNorm + NVFP4 quant;
- router stream: the router GEMM and the top-8 routing.

After the two streams join, the main stream calls FlashInfer's `trtllm_fp4_block_scale_routed_moe`, which first builds the routing metadata and then runs the expert GEMMs. The metadata depends only on the top-8 ids, so it does not need to wait for the main stream.

This PR builds the routing metadata on the router stream right after the top-8, and the main stream runs only the expert GEMMs after the join.

**GB300 is not affected by this PR.**

## Modifications

- `routed_moe_split.py` (new): `RoutedMoeSplit` holds the routing metadata for one token count, shared by all layers; `populate()` builds it on the router stream and `run_body()` launches FlashInfer's expert body from it. It uses FlashInfer 0.7.2's prepared-routing objects (`DABodyRunner`), with the runner and arguments adapted from `trtllm_fp4_block_scale_moe_op`. flashinfer-ai/flashinfer#8050 makes this a public argument (`trtllm_fp4_block_scale_routed_moe(..., routing_metadata=...)`); `run_body` switches to it once SGLang requires a FlashInfer release that has it.
- `routed_moe_split.py`: `split_enabled` gates the split by `_SPLIT_MIN_TOKENS[(capability, tp)]`, the measured smallest token count where it wins (SM107 TP4 / TP8: 8); unlisted (GPU, TP) pairs keep the fused routing.
- `muse_spark.py`: `MuseSpark1xMoE` builds the split on the router stream after the top-8 when it applies (NVFP4, not Marlin, decode CUDA graph capture, enabled for this GPU and TP, M <= 1024 and FlashInfer's default tile <= 128) and passes it to the experts. `routed_moe_split` (and the FlashInfer internals it uses) is imported only once the cheap checks pass, so importing the model does not import it.
- `muse_spark_fp4_moe.py`: the experts call `moe_split.run_body` instead of `trtllm_fp4_block_scale_routed_moe` when a split is given; the arguments and outputs are the same.

The expert body's buffers are allocated per call like the ordinary routed call, so under CUDA graph capture they come from the graph pool shared by every captured batch size; only the routing metadata (a few small buffers per token count) is kept.

- Where the main stream finished last in the base (c = 4 and c >= 32), the metadata now runs in the router stream's slack: the experts start 2.5-4.5 µs earlier.
- Where the router stream already finished last (c = 1-2) or the streams tied (c = 8-16), the metadata stays on the critical path behind the router, so the saving is the join-to-metadata gap and a faster metadata kernel on the router stream: 0.6-2.5 µs.
- With this PR the router stream finishes last at every concurrency where the split runs, so shortening the router GEMM is the next lever.

**Issue**

`RoutedMoeSplit` always runs FlashInfer's untuned default tile and config (`DABody(tactic=-1, ...)`). Autotune is on by default here: the Muse Spark hook picks `flashinfer_trtllm` on SM10x, and `EagerRunner` runs autotune before graph capture. Without this PR, the captured routed call uses the tuned `[tile_N, config]` from `AutoTuner.choose_one`. With this PR, captured graphs in the split range drop it.

**Why it matters**

The speed tables used autotune off on both sides, so they do not show that the gain holds in the default config.

**Fix**

Run the tuned tactic and build the metadata for its tile, or keep the split off when autotune is on. Otherwise, post before/after numbers with autotune on.
