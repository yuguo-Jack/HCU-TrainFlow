# Optimize MiMo-V2 router GEMM with the HPC-Ops bf16xfp32 kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/41108) · state: open · merged: False

## Original PR description

## Motivation

MiMo-V2's `MoEGate` keeps an fp32 router weight, so every router GEMM upcasts the
bf16 hidden states and runs an fp32 cuBLAS GEMM on CUDA cores. For
MiMo-V2.5-Flash (hidden 4096, 256 routed experts, 47 MoE layers) that runs 47
times per forward pass.

#30247 added the HPC-Ops `gemm_bf16xfp32` path to `linear_bf16_fp32` for
LongCat-Flash. It splits the fp32 weight once into two cached bf16 halves
(`w = w_high + w_low / 256`) and runs both bf16 GEMMs fused on tensor cores with a
single fp32 accumulator. This PR routes the MiMo-V2 router through the same
dispatcher. No new kernel is added.

## Modifications

- `models/mimo_v2.py`: when `SGLANG_OPT_BF16_FP32_GEMM_ALGO=hpc` is set, the
  router weight is fp32, and the `(hidden_size, n_routed_experts)` shape has been
  benchmarked, `MoEGate.forward` dispatches to
  `linear_bf16_fp32(..., hpc_kernel_min_m=...)`.
  - The per-shape min-M table has one entry: `(4096, 256): 8`. On H100 the HPC
    kernel is at least as fast as cuBLAS for every m >= 8 on this shape.
  - Unbenchmarked shapes, bf16 routers, and the default algo keep the original
    path. Without HPC-Ops installed, or below min-M, `linear_bf16_fp32` falls back
    to the existing cuBLAS fp32 GEMM.
- Unlike LongCat, which calls `mark_hpc_bf16xfp32_gemm_enabled()` and is on
  whenever HPC-Ops is installed, the MiMo path is opt-in through the env var, for
  two reasons: the split weight makes generations differ from the cuBLAS path (see
  below), and the cached weight split makes online weight updates unsupported.
  With `algo=hpc`, `hpc_bf16xfp32_gemm_enabled()` is already True, so the
  weight-update guard from #31943 applies. MiMo users who do not set the flag,
  including RL / online-update users, are unaffected.
- Tests and benchmark:
  - `test/registered/unit/models/test_mimo_v2_router_hpc_gemm.py` (new, CPU):
    dispatch with `min_m=8`, default algo, unbenchmarked shape, bf16 router.
  - `test/registered/gemm/test_linear_bf16_fp32_hpc.py`: adds the MiMo router
    shape `(4096, 256)` to the numerical tests.
  - `test/registered/kernels/benchmark/gemm/bench_bf16xfp32_router_gemm.py`: adds
    the same shape.

## Accuracy

- `test_linear_bf16_fp32_hpc.py`: 5 passed on H100, including the MiMo shape.
- `test_mimo_v2_router_hpc_gemm.py` + `test_longcat_flash_router_hpc_gemm.py`:
  8 passed.
- Kernel-level max abs error vs an fp64 reference, using real MiMo-V2.5-Flash gate
  weights from 5 layers and 32768 random N(0,1) bf16 hidden states: cuBLAS fp32
  4.3e-5, HPC 8.5e-5. Top-8 expert selection differs from the fp64 reference for
  0.012% of tokens at worst.

Model-level accuracy is under "Model-level validation" below.

## Performance

Router GEMM microbenchmark, single idle H100, `(n, k) = (256, 4096)`:

    python test/registered/kernels/benchmark/gemm/bench_bf16xfp32_router_gemm.py

| m | cublas (us) | hpc (us) | speedup |
|---|---|---|---|
| 1 | 7.8 | 14.6 | 0.53x (below min_m; not used) |
| 8 | 21.0 | 15.0 | 1.4x |
| 64 | 16.9 | 16.8 | 1.0x |
| 512 | 45.8 | 24.0 | 1.9x |
| 1024 | 71.4 | 28.7 | 2.5x |
| 2048 | 127.7 | 28.0 | 4.6x |
| 8192 | 452.3 | 98.4 | 4.6x |

The ratio reproduced across three GPUs on the same node; the absolute times did
not (one GPU was uniformly ~2x slower in both providers, ratio still 5.1x), and
the cuBLAS fp32 baseline is unstable in the m=8..128 range (for example 21us and
40us at m=8 in different runs), so treat the absolute numbers as indicative.

## Model-level validation

MiMo-V2.5-Flash FP8, 8xH100, `--tp 8 --dp-size 2 --enable-dp-attention` (MiMo's
fused qkv weights require attention TP 4, so tp8 serving needs dp2 + DP
attention). A/B runs identical code; only `SGLANG_OPT_BF16_FP32_GEMM_ALGO`
changes. 5 independently launched servers per arm, 4 `bench_one_batch_server`
rounds each (`--dataset-name random-ids --input-len 1024 --output-len 128`), first
round dropped as warmup. Reported as the median of the 5 per-server medians.
HPC-Ops was verified mapped into the scheduler processes only in the hpc arm.

| bs | prefill tok/s | decode tok/s |
|---|---|---|
| 1 | 8665 -> 8850 (+2.1%) | 97.8 -> 105.2 (**+7.5%**) |
| 16 | 50102 -> 52331 (+4.4%) | 1400 -> 1472 (**+5.1%**) |
| 64 | 52796 -> 58633 (**+11.1%**) | 3788 -> 3900 (**+2.9%**) |

Decode is the solid result: per-server spread is under 1% and the two arms do not
overlap at any batch size. Decode improves even at bs=1 because DP attention plus
CUDA-graph padding already put the router's m at or above `min_m=8`.

For prefill only bs64 is conclusive (cuBLAS 49525-53080 vs HPC 55367-59049, no
overlap). At bs1 and bs16 the arms overlap: per-server spread reaches 26% at bs16
within the hpc arm alone, several times the effect size, so this setup cannot
resolve a prefill difference there. One bs1 cell (1 of the 5 hpc servers) was
dropped as a measurement failure: from round 2 on its ttft went 150ms -> 654ms and
decode fell to 6-24 tok/s while bs16/bs64 on the same server stayed normal, with an
unrelated process holding memory on the node's GPUs at the time. Including it would
make bs1 prefill read -0.0%.

GSM8K (1319 questions, 5-shot, parallel 128), two runs per arm:

| | accuracy | invalid |
|---|---|---|
| cublas | 0.9545 / 0.9568 | 0.000 |
| this PR | 0.9560 / 0.9591 | 0.000 |

Teacher-forced top-256 prompt logprobs over HTTP on real text (72 sequences,
71450 positions: 64 short GSM8K prompts plus 8 of ~8k tokens; requests sent one at
a time so batch composition is fixed):

| vs an fp64 router GEMM | top-1 agreement | mean KL |
|---|---|---|
| cublas fp32 (current) | 97.92% | 8.06e-3 |
| hpc (this PR) | 97.80% | 8.86e-3 |

Repeated runs of the same algo are bit-identical (greedy text 32/32, logprob KL
exactly 0), so the cross-arm difference (top-1 97.81%, mean KL 8.94e-3) is
entirely this change. MoE routing is sensitive to any router rounding: near-tied
experts reorder and the difference propagates through attention, so any change to
the router GEMM moves outputs by about this much. Measured against an fp64 router,
the HPC path is as close to exact as cuBLAS fp32 is, and it keeps the fp32-weight
routing precision that `moe_router_dtype=float32` asks for. It stays opt-in
because outputs are not bit-identical to the current default.

Environment: upstream main, torch 2.13.0+cu130, sglang-kernel 0.4.7,
flashinfer 0.6.18, HPC-Ops ab1a402 built for CUDA 13.0.
