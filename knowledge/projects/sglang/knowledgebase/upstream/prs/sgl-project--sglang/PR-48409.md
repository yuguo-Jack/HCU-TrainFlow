# [Feat] scheduler: add an opt-in bounded matching window for LPM

[Upstream PR](https://github.com/sgl-project/sglang/pull/48409) · state: open · merged: False

## Original PR description



https://github.com/sgl-project/sglang/issues/48408
## Motivation

LPM falls back to FCFS for long waiting queues to limit prefix matching and sorting costs. When reusable prefixes compete for a small KV pool, this can lose useful locality. This change offers a bounded window for cache-aware ordering while preserving the default behavior.

## Modifications

- Add `--lpm-window-size N` to the existing `lpm` policy. Default `0` preserves the current behavior, including large-queue fallback.
- With a positive window, match and stably reorder only the first N waiting requests. Leave the tail in place and bypass the large-queue fallback for this window.
- Retain admission-time matching because requests outside the window have not been matched. Retain the existing FCFS adjustment when prefix caching is disabled.
- Reject negative values and positive windows combined with another scheduling policy or priority scheduling.
- Add registered CPU tests for window boundaries, ties, tail preservation, the iterable-input/list-output contract, duplicate-prefix deferral, disabled caching, default fallback, CLI parsing and invalid configurations.
- Document empirical window selection and the tradeoff between cache locality, scheduler cost and cold-request waiting time. No experimental timers are added to production code.

The window bounds the requests considered for matching and sorting, not total scheduler work or maximum waiting time.

## Accuracy Tests

No model-forward or kernel changes. Earlier GPU validation compared the same 16 sequential requests across four policies and obtained matching outputs; this is an output regression check, not an accuracy benchmark.

The implementation is adapted to upstream `77c3bcbe2c28e1a6d1ad4121ee57231582d39bdc`, including the new iterable-input/list-output scheduling API. The GPU measurements below were collected on the earlier implementation based on `26fde018e53840238624f7810b69ca641531713c`; they have not been rerun on the rebased revision.

## Speed Tests and Profiling

45 runs: stock LPM and K=16/32/64/128, three scenarios, three repetitions. RTX 4090, Qwen3-4B, max-running-requests=32, output length 16, 512-request synthetic bursts, identical seed-11 inputs. Every trial restarts the server and follows the same initialization and cache warmup procedure. Execution order is randomized within each repeat. All 23,040 measured requests complete with zero retractions.

The constrained-cache workload has 384 hot requests across 12 shared-prefix groups and 128 cold requests, with 1040 input tokens per request. Percentages below average the changes relative to stock LPM within the same repetition.

| Window | Throughput (req/s) | Throughput change | Mean TTFT change | Cold p95 TTFT change | Cache reuse |
|---|---:|---:|---:|---:|---:|
| Stock | 15.834 | — | — | — | 25.30% |
| 16 | 19.074 | +20.48% | -25.24% | -19.62% | 44.62% |
| 32 | 24.519 | +54.86% | -43.24% | -37.58% | 56.51% |
| 64 | 29.543 | +86.58% | -55.70% | -47.88% | 63.76% |
| 128 | 32.902 | +107.81% | -65.31% | -53.12% | 68.89% |

The KV pool above holds 8192 tokens. K128 has the best throughput among the tested candidates; its three runs span 32.759–33.111 req/s versus 29.106–29.818 for K64. This does not establish a global optimum or a plateau beyond 128.

Controls matter: with a 32768-token pool, throughput changes range from -1.04% to +0.76%, while cold mean TTFT increases by 6.35%, 14.07%, and 19.31% for K32/K64/K128. K128 cold p95 changes by -1.06% but cold p99 by +1.74%; the average-delay regression must not be hidden by the p95 result. In the no-reuse control, throughput changes range from -0.18% to +0.09%.

Keep the default at 0. For similar cache-constrained prefix-sharing bursts, try 128; start with 32 if you need a smaller scheduling budget and less cold-request delay, and measure your own workload. With sufficient cache or no reuse, these measurements do not justify enabling the option. This recommendation covers one model, one GPU and one input seed with three execution repetitions, not production traffic or all batch/output settings.

The CPU microbenchmark uses Python RadixCache, not the GPU server's Rust backend. At queue length 512 and input length 1024, median thread CPU times for K16/32/64/128 are 0.431/0.904/1.585/2.953 ms. This illustrates the cost trend but is not a CPU profile of the GPU-serving process.
