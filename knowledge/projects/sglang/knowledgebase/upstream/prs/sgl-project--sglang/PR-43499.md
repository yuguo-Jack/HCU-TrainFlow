# [Fix] [AMD] deepseek-v4.1: Fix three MegaMoE crashes at attention TP > 1

[Upstream PR](https://github.com/sgl-project/sglang/pull/43499) · state: open · merged: False

## Original PR description

## Motivation

On main, DeepSeek-V4.1-Flash with MegaMoE (`--moe-a2a-backend megamoe`) at TP4 on MI355X crashes on its own warmup request, and two more crashes follow once that one is fixed. All three need an all-to-all MoE backend with attention TP > 1, so MegaMoE cannot serve this model on AMD today. This PR fixes the three crashes and changes nothing else. As the contribution guide asks for bug fixes, each fix has focused regression tests.

## Modifications

The first two fixes act only when padding rows follow the real tokens (MLP-sync padding, for example with an all-to-all MoE backend at attention TP > 1). The third acts only with MegaMoE and gives the old result at attention TP 1.

- **Padded replay-tail rows** (`layers/attention/deepseek_v4_backend_hip_radix.py`, `_build_late_layer_tail_metadata`). For a one-request extend, the contiguous slice of `out_cache_loc` kept the padding rows, and the warmup request (6 tokens, padded to 8) failed: `RuntimeError: The size of tensor a (8) must match the size of tensor b (6) at non-singleton dimension 0`. The slice is now used only when there are no padding rows; otherwise the existing index gather runs. The CUDA backend (`deepseek_v4_backend.py`) has the same slice and is not changed here (no NVIDIA run); we will send that as a separate fix.
- **Padded request indices** (`layers/attention/dsv4/dsv41_sparse.py`, `token_req_indices`, shared with the CUDA backend). The padding rows read unwritten request indices and the GPU faulted: `HSA_STATUS_ERROR_EXCEPTION: An HSAIL operation resulted in a hardware exception. code: 0x1016`. The real-row count now comes from the CPU lengths, and the padding rows use request 0, the padding row of the request pool. No device sync.
- **MegaMoE gate** (`layers/moe/mega_moe_flydsl.py`, `should_use_mega_moe`). The gate compared the global token count with MTPR, the maximum tokens per rank (default 8192). A prefill chunk above 8192 tokens went to the fallback MoE path, which cannot read MegaMoE's weight layout: `IndexError: tuple index out of range`. The gate now compares the tokens per rank (the largest DP group's tokens divided by the attention TP size, rounded up). A DP group above attention TP x MTPR tokens (32768 at TP4) still takes the fallback, and no startup check on HIP rejects that size.
- `test/registered/unit/models/test_deepseek_v4_megamoe_fixes.py`: 17 CPU cases.

The first version of this PR also fixed decode graph capture. Main fixed that in #40666, so this PR no longer changes it.

## Accuracy Tests

Setup: DeepSeek-V4.1-Flash (revision `dba1be0a40`), TP4 on 4 x MI355X, image `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261015`, SGLang main `b6d3b7e163`, `--moe-a2a-backend megamoe`, `SGLANG_AMD_USE_FLYDSL_MEGA_MOE=1`, vision layers off (`--json-model-override-args '{"vision_n_layers": 0}'`, because V4.1's vision check admits MegaMoE only on CUDA), decode CUDA graphs on. One server per row; the middle rows add this PR's fixes to main one at a time:

| SGLang | Server start | 12288-token request | 501 + 500-token batched request | 1001-token request |
|---|---|---|---|---|
| main | crash 1 on the warmup request (all 4 ranks) | - | - | - |
| main + fix 1 | crash 2 on the warmup request (all 4 ranks) | - | - | - |
| main + fixes 1 and 2 | starts | crash 3 (all 4 ranks) | - | - |
| this PR | starts | served | served | served |

GSM8K with this PR (`python -m sglang.test.run_eval`, 1,319 questions, 2,048 max tokens, 1,314 scored; one run each): MegaMoE 1279 / 1314 (0.973), default MoE 1276 / 1314 (0.971).

Unit tests (CPU): 17 of 17 pass at the PR head. With main's versions of the three source files (`d9ce511646`), the 6 cases of the fixed behavior fail and the other 11 pass. The GPU runs used `b6d3b7e163`.

## Speed Tests and Profiling

This PR makes MegaMoE run; it does not change the speed of any path. With the GSM8K settings, MegaMoE still has 34 to 52 % lower output throughput than the default MoE (random dataset, 1k and 8k input, 1 to 16 users, one run per arm). MegaMoE runs the experts with expert parallelism (EP 4); the default MoE shards each expert over the 4 GPUs.
