# [OpenAI] Return a real HTTP error for streams rejected before the first chunk

[Upstream PR](https://github.com/sgl-project/sglang/pull/43779) · state: open · merged: False

## Original PR description

## Motivation

A streaming request that the scheduler rejects before producing any output (e.g. `The request queue is full.` when `--max-queued-requests` is reached) is answered with **HTTP 200** and an in-band `data: {"error": ...}` event, while the same rejection on a non-streaming request is a **503**. Clients and proxies that retry on 429/503 never see the status. We hit this on a production batch endpoint during a load surge: a large share of streaming replies were 200s that carried no content.

This is an alternative to #28175, which targets the same problem. Reviewing #28175 found that:
- `/v1/messages` (Anthropic) iterates `_generate_chat_stream` directly, so the new exception landed in its generic handler. A queue-full rejection became `api_error "Internal server error"` (still HTTP 200), and a stack trace was logged per rejected request.
- The gRPC bridge's streaming RPC drops `status_code`, so the error became a normal final chunk.
- The `isinstance(status_code, HTTPStatus)` gate never matches under msgpack IPC, where `status_code` decodes to a plain `int`.
- It adds a second abort-to-HTTP mapping (a new exception class) next to the one `TokenizerManager._handle_abort_finish_reason` already has, and the two produce different `error.type` values.

## Modifications

- **Chat and completions generators.** When an error abort arrives before the first chunk, they now raise the same exceptions `TokenizerManager._handle_abort_finish_reason` raises for a non-stream abort: `ValueError` for 400, `HTTPException` for every other 4xx/5xx status. The streaming handlers already wait for the first chunk before sending the status line, and `handle_request` already maps these exceptions, so stream and non-stream get the same status and body. No new exception class or `except` arm is needed.
- **One shared set of statuses.** `HTTP_ERROR_ABORT_STATUSES` (in `io_struct`) contains every 400–599 status, preserving current `main` behavior, and both `TokenizerManager` and the stream path use it. Non-standard codes such as 499 and 599 are preserved too. Any abort after the first chunk keeps the in-band error event.
- **msgpack IPC.** `error_abort_status` also accepts a plain `int` `status_code`, including non-standard 4xx/5xx codes. Before, such aborts streamed with no error at all.
- **`/v1/messages`.** It pulls the first OpenAI chunk before committing HTTP 200, so a rejection is a real `503 overloaded_error` or `400 invalid_request_error`. It preserves current `main`'s error-message scrubbing: all 5xx details, including 503, remain generic in client responses. The pre-first-chunk `ValueError` branch inside `_generate_anthropic_stream` could no longer be reached, so it is removed.
- **gRPC bridge.** For a `stream: true` request, an error response is delivered as an in-band `{"error": ...}` chunk, which the streaming RPC can carry, instead of a bare error body in the final chunk. `stream: false` requests on the same RPC are unchanged.

**Behavior change.** For `stream: true`, a pre-first-chunk rejection is now `application/json` with a non-200 status, instead of `text/event-stream` with an error event under HTTP 200. That is the intent, but consumers that parsed the SSE error event for this case (routers, gateways) will now see the HTTP status instead. `/v1/messages` streams now send response headers only once the first token is ready, as the OpenAI routes already do.

**Not covered (follow-ups):**
- Native `/generate` streaming, Ollama and the Responses API still answer a pre-first-chunk rejection with 200.

- lorenzoc25 · comment · 2026-10-29T21:32:14Z · [source](https://github.com/sgl-project/sglang/pull/43779#issuecomment-6508817885)

This also fixes a case we hit: streaming requests with an invalid grammar (bad `regex`, `ebnf`, or `response_format` schema) return HTTP 200 with an in-band error, while `stream: false` returns 400. Grammar compile failures abort before any output with the default 400, so with this PR they become a real 400 on chat/completions and a 400 `invalid_request_error` on `/v1/messages`.

I explored validating grammars in the HTTP frontend before dispatch locally, and I don't think that's the right fix. Grammar validity depends on the backend and tokenizer, so a frontend check duplicates backend logic, misses tokenizer-dependent failures, and adds a second parse to valid requests (about 8-13 ms with XGrammar/llguidance and about 760 ms with Outlines on a 120 KB schema, measured on CPU). I think mapping pre-output aborts to HTTP status at the stream boundary, as this PR does, is the better fix.

One trade-off: `/v1/messages` headers now wait for the first token, which conflicts with the keepalives in #43728. Also, #23821, #28175 and #44567 target the same bug; this one covers the most, so consolidating here seems simplest.

Happy to help with an invalid-grammar regression test or the Messages changes if that would be useful.
