# [Perf] [AMD] dsv41: Compile the HIP FP4 prefill schedule kernels before serving

[Upstream PR](https://github.com/sgl-project/sglang/pull/48351) · state: open · merged: False

## Original PR description

## Motivation

On HIP, the DeepSeek-V4.1 FP4 prefill indexer builds a schedule for every prefill call with `_prefill_schedule_prep_kernel` (in `python/sglang/kernels/ops/attention/dsv4/fp4_indexer_schedule_hip.py`) and AITER's `_prefill_cta_info_kernel`. Triton specializes a plain `@triton.jit` kernel on each integer argument (whether it is 1 or a multiple of 16) and on the 16-byte alignment of each pointer, and compiles a new variant for every new combination. Each prefill call brings its own row count, table widths and strides, and `PrefillScheduleBuffers` slices its regions at a stride of exactly the row count, so the pointer alignment changes with the row count too. New variants therefore compile while serving, 0.4-2.8 s for the first call of each one on MI355X. In a short trial of a long-prompt serving benchmark with DeepSeek-V4.1-Flash at TP4, the prep kernel compiled four times, about 1.5 s each, inside one measured point. With the attention-TP row shard of #48152 the shapes differ per rank, so a compile can run on one rank while the others wait at the all-gather (suggestion 3 of our review there). This PR applies to main on its own.

## Modifications

- `_prefill_schedule_prep_kernel`: `do_not_specialize` for its per-call integers (the two page-table strides, `T`, `P`, `s_max`, the two widths and `pt_tiles_per_row`), and `do_not_specialize_on_alignment` for its row-metadata and page-table pointers. `BLOCK_T` is the only shape key left.
- `PrefillScheduleBuffers`: each row region starts on a 16-byte boundary (the stride is rounded up to 4 int32), and `[safe, total_splits]` stay adjacent at the end, because the prep kernel writes them as one pair. `_prefill_cta_info_kernel` then sees one alignment signature for every row count.
- `warm_prefill_schedule(device)`: compiles the 9 `BLOCK_T` variants (16 to 4,096 rows) and the unaligned-`local_ends` signature once per device, and is skipped during CUDA graph capture. `refresh_low_ratio_prefill_workspaces` in `python/sglang/srt/layers/attention/dsv4/low_ratio_backend_hip.py` calls it, so these compiles happen on the first prefill forward instead of while serving.
- Test: `test/registered/kernels/ops/attention/test_fp4_indexer_schedule_hip.py` (1 GPU, gfx950). After the warm-up, 10 schedule builds with every row-count residue modulo 4, varied table widths and unaligned row metadata must add no variant to either kernel.

## Accuracy Tests

The diff changes only Triton's specialization keys, the buffer offsets and one warm-up call, not what the kernels compute. `test/registered/kernels/ops/attention/test_fp4_indexer_hip.py`, which checks the indexer kernels that use this schedule against reference logits, passes (12 tests). We did not run an end-to-end accuracy test for this PR alone. We ran it on DeepSeek-V4.1-Flash, TP4, MI355X together with #48152 and the fixes we suggest there, against the same build and server config without them (baseline in parentheses):

| Mode | GSM8K | GPQA Diamond | NIAH 64k / 128k |
|---|---|---|---|
| DSpark | 97.1 (97.0) | 87.9 (90.9) | 1.0 / 1.0 (1.0 / 1.0) |
| No speculative decoding | 97.4 (97.0) | 86.9 (86.4) | 1.0 / 1.0 (1.0 / 1.0) |

GPQA Diamond has 198 questions; on this setup a change with bitwise-identical outputs moved it by -2.5 and +1.0 points, so these GPQA differences are run-to-run spread.

## Speed Tests and Profiling

Kernel check on one MI355X GPU: after each version's warm-up, 11 schedule builds over every row-count residue modulo 4, with aligned and unaligned `local_ends`. All GPU results come from our ROCm test build of SGLang (an earlier commit with extra DeepSeek-V4.1 HIP patches) with these two commits applied.

| Version | Warm-up compiles (prep / cta_info) | New variants in the 11 builds (prep / cta_info) |
|---|---|---|
| Before this PR | none | 11 / 8 (0.4-2.8 s per first call) |
| First commit only | 9 / 1 | 0 / 7 (0.28 s each) |
| This PR | 9 / 2 | 0 / 0 |

Serving, DeepSeek-V4.1-Flash, TP4, MI355X: prompts of about 92k tokens that share one long prefix, 1,000 output tokens, `--chunked-prefill-size 16384`, seven points from concurrency 1 to 64, with every Triton compile logged (`SGLANG_TRITON_SLOW_COMPILE_THRESHOLD_SECS=0`).

- Without this PR, the prep kernel compiled inside measured points. In a short trial without the row shard it compiled four times (about 1.5 s each) at concurrency 4. In a short trial with the row shard of #48152, one rank alone compiled it (1.6 s) at concurrency 1 while the others waited at the all-gather, and the P99 TTFT of that point rose from 784 to 1,564 ms against the run without the shard.
- With this PR, together with #48152 and our suggested fixes, no schedule kernel compiled inside a measured point in two full runs, with and without speculative decoding.

We did not time the warm-up on its own, and we did not run an end-to-end benchmark of this PR alone.
