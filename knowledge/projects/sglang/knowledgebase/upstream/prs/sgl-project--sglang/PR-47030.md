# [Fix] [AMD] aiter: Use the layer's KV scales in the legacy target-verify attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/47030) · state: closed · merged: True

## Original PR description

## Motivation

With the aiter attention backend, an fp8 KV cache and calibrated KV scales (for example from the checkpoint), speculative decoding produces garbage when target verify takes the legacy path, which every non-MLA target verify (NGRAM, EAGLE) takes unless unified verify applies (topk 1 with unified attention on, i.e. an SWA pool or `SGLANG_USE_AITER_UNIFIED_ATTN=1`); this is from reading the code, and only NGRAM is measured below. On that path `AiterAttnBackend.forward_extend` calls `extend_attention_fwd` with `k_scale` and `v_scale` hard-coded to 1.0, added in #19736 to fix a missing-argument TypeError. The cache holds `K / k_scale`, so the cached prefix is read back unscaled. #46528 fixed the decode and NHD prefill reads but not this call; the triton backend passes `layer.k_scale_float` at the same place.

## Modifications

- `aiter_backend.py`: pass `layer.k_scale_float` / `layer.v_scale_float` when the cache is fp8 and the layer has scales, otherwise 1.0. The Triton kernel always multiplies the cached prefix by the scale, so a bf16 cache must keep 1.0; this is the same check `forward_extend` already makes for its other paths.
- `test_aiter_fp8_kv_scales_paths.py`: add `test_extend_attention_target_verify`, three requests with 300, 77 and 512 cached fp8 prefix tokens and 4 draft tokens each, against fp32 attention over the dequantized cache. To support it, `_FakeKVPool` gets `get_key_buffer` / `get_value_buffer`, `_make_layer` sets `k_scale_float` / `v_scale_float`, and the causal reference mask is offset so the queries are the last positions of the sequence. On main the new case fails with a relative L2 error of 322.19 (threshold 0.15); with this PR it is 0.04.

## Accuracy Tests

MI355X (gfx950), torch 2.11.0+rocm10.0.0, sglang-kernel 0.4.10, aiter `285579b62`, `SGLANG_USE_AITER=1`, CUDA graphs on. Model `amd/Llama-3.1-8B-Instruct-FP8-KV` (per-layer checkpoint KV scales from 0.024 to 0.075) with `--kv-cache-dtype fp8_e4m3`; NGRAM uses its defaults. Main is `7fe5b127e4`. Only the main run used `--max-total-tokens 2000000`; the PR and no-speculation runs used the default KV pool. GSM8K with `python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --max-tokens 4096` (chat API, greedy, 1314 questions after the 5 few-shot examples):

| Config | Main | This PR |
|---|---|---|
| aiter + NGRAM | 0.0061 | 0.8037 / 0.8067 / 0.8052 |
| aiter, no speculation | | 0.8135 / 0.8067 / 0.8181 |
| triton + NGRAM (reference) | | 0.7968 |

On main the aiter + NGRAM outputs are garbage that run to the 4096-token limit (5.4M output tokens), and with the default KV pool those long outputs hit a separate int32 offset overflow in `extend_attention_fwd` (#47029), hence the smaller pool for that run.

Unit tests: `test_aiter_fp8_kv_scales_paths.py` passes on MI355X and MI325X.

MI325X (gfx942), torch 2.11.0+rocm10.0.0, aiter `285579b62`, main `cb55d77d37` with this patch: the new case fails on main and passes here. GSM8K aiter + NGRAM with `--max-total-tokens 2000000` on both arms: main 0.0050 (200 questions), this PR 0.7998 / 0.8174; aiter without speculation 0.8288.

## Speed Tests and Profiling

MI355X, same stack as above. The kernel and launch are unchanged; only the `k_scale` / `v_scale` values passed to `extend_attention_fwd` differ. End to end, aiter + NGRAM with `--max-total-tokens 2000000` on both arms, `python -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 1024 --random-output-len 512 --random-range-ratio 1.0` (fixed output length). Blocks main, PR, PR, main with one server each; each block reports the median of runs 2-4:

| Concurrency | Output throughput, main → PR (tok/s) | Median TPOT, main → PR (ms) | Accept length, main → PR |
|---|---|---|---|
| 1 | 177 → 1066 (PR blocks 991 / 1141) | 5.66 → 0.66 | 1.04 → 3.70 |
| 32 | 1770 → 7010 (PR blocks 7120 / 6900) | 17.90 → 2.97 | 1.04 → 4.14 |

The end-to-end gain comes from NGRAM accepting drafts again; on main the garbage outputs reject almost every draft. The two main blocks differ by 0.1% (c1) and 0.8% (c32) in throughput.

## Reproduce

```bash
SGLANG_USE_AITER=1 python -m sglang.launch_server --model-path amd/Llama-3.1-8B-Instruct-FP8-KV \
  --attention-backend aiter --kv-cache-dtype fp8_e4m3 --speculative-algorithm NGRAM
# Main arm: add --max-total-tokens 2000000.

python -m sglang.test.run_eval --eval-name gsm8k --num-examples 1319 --max-tokens 4096
```
