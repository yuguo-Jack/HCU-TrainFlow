# [KDA] Add zero-copy native prefill checkpoints and packed decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/34299) · state: closed · merged: False

## Original PR description

## Summary

Adds the Cake (FlashInfer) KDA kernels as selectable linear-attention backends for Kimi-Linear / Kimi-K3 serving:

- `--linear-attn-prefill-backend cake` — Cake prefill through the FlashInfer prepared export (BF16 bodies, FP32 recurrent state, native zero-copy prefill checkpoints); `--kda-cake-prefill-precision tf32` selects the TF32 export for bounded-gate models. Unsupported contracts fail closed or take a declared Triton fallback — never a silent kernel swap.
- `--linear-attn-decode-backend cake` (or `--linear-attn-backend cake` for both phases) — packed Cake decode on the BF16 state pool; the dispatcher keeps bounded-gate decode on the Triton kernel where Cake declares no support.
- Every routing decision is emitted as an `SGLANG_KDA_ROUTE_EVENT` line (mode, layer, reason, success / declared fallback / fatal) so served tests can assert the route; the backend is resolved from the active attention runner so configuration and runtime cannot diverge.
- Served parity tests `test/registered/e2e/models_large/test_kimi_linear_cake_kda_parity.py` (TP2) and `test_kimi_k3_cake_kda_parity.py` (TP8, optionally two 4-GPU nodes via the peer agent) on the shared kit `python/sglang/test/kits/kda_cake_parity_kit.py`, plus CPU unit tests for the adapter routes, telemetry schema and dispatcher.

Results below are the latest runs (2026-10-01) against FlashInfer with #5846 merged (every Cake prefill body reads the fused-projection q/k/v views in place), measured at `125d8b7ea2`; the current head `896ec5bca0` only merges `main` on top of it (two textual conflicts resolved, no functional change; the KDA / linear-attention / server-args unit tests pass on the merged tree).

## How to run: inference launch, parity tests, benchmark

**Inference.** The Cake KDA kernels are selected per phase; everything else is the usual `sglang serve` line. Flags used in all runs below: `--trust-remote-code --mamba-radix-cache-strategy extra_buffer --mem-fraction-static 0.80 --context-length 32768 --chunked-prefill-size 16384 --max-running-requests 64`.

```bash
# Cake prefill, Triton decode (recommended; FP32 state pool, BF16 prepared export) -- Kimi-Linear TP2
sglang serve --model-path moonshotai/Kimi-Linear-48B-A3B-Instruct --tp 2 --trust-remote-code \
  --linear-attn-prefill-backend cake --linear-attn-decode-backend triton

# Same on Kimi-K3, TP8 over two 4-GPU nodes (run on each node with --node-rank 0 / 1)
sglang serve --model-path moonshotai/Kimi-K3 --tp 8 --trust-remote-code \
  --nnodes 2 --node-rank 0 --dist-init-addr <rank0-host>:20000 \
  --model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 64}' \
  --linear-attn-prefill-backend cake --linear-attn-decode-backend triton

# TF32 prefill export (bounded-gate models such as Kimi-K3; Kimi-Linear declares a Triton fallback)
sglang serve ... --linear-attn-prefill-backend cake --kda-cake-prefill-precision tf32

# Cake prefill + Cake decode (correctness-validated on Kimi-K3; decode is slower than Triton today, see the throughput table)
sglang serve ... --linear-attn-backend cake --mamba-ssm-dtype bfloat16
```

`SGLANG_KDA_CAKE_PREFILL_API` (default `auto`) picks the prepared export on the FP32 pool and the FlashInfer facade route on the BF16 pool; `prepared` / `facade` force one. Every routing decision is logged as an `SGLANG_KDA_ROUTE_EVENT` line (mode, layer, reason, success / declared fallback / fatal), which is what the tests assert on.

**Correctness tests** (served parity against a Triton server with the same state-pool dtype; per-prompt tables printed before the assertions):

```bash
# CPU unit tests (adapter routes, telemetry schema, dispatcher)
pytest test/registered/unit/layers/attention/linear/kernels/test_kda_flashinfer.py \
       test/registered/unit/layers/attention/linear/test_kda_route_telemetry.py \
       test/registered/unit/layers/attention/test_kda_dispatcher_bounded_gate_decode.py

# Kimi-Linear TP2 (4 x B200): arms cake_bf16, cake_tf32 (declared fallback), cake_decode (declared fallback)
pytest test/registered/e2e/models_large/test_kimi_linear_cake_kda_parity.py -v

# Kimi-K3 TP8 on one 8-GPU node: arms cake_bf16, cake_tf32, cake_decode, cake_bf16_decode
pytest test/registered/e2e/models_large/test_kimi_k3_cake_kda_parity.py -v

# Kimi-K3 TP8 on two 4-GPU nodes: rank 0 runs pytest, rank 1 runs the peer agent
SGLANG_TEST_KDA_PARITY_NNODES=2 SGLANG_TEST_KDA_PARITY_DIST_INIT_ADDR=<rank0-host>:20000 \
SGLANG_TEST_KDA_PARITY_PEER_CONTROL_DIR=/shared/kda_parity_ctrl \
  pytest test/registered/e2e/models_large/test_kimi_k3_cake_kda_parity.py -v          # node 0
python -m sglang.test.kits.kda_cake_parity_peer --rank 1 --control-dir /shared/kda_parity_ctrl   # node 1
```

`SGLANG_TEST_KDA_PARITY_ARMS=cake_decode,cake_bf16_decode` runs a subset, `SGLANG_TEST_KDA_PARITY_CONTROL=1` adds a second Triton launch as the noise-floor row, `SGLANG_TEST_KDA_PARITY_DUMP=DIR` writes the raw observations, `SGLANG_TEST_KIMI_K3_MODEL` / `SGLANG_TEST_KIMI_LINEAR_MODEL` point at local checkpoints.

**Throughput** (per arm, against a server started as above):

```bash
for row in "4096 32 32 8" "16384 32 16 4" "1024 32 64 16" "1024 256 64 32"; do set -- $row
  python -m sglang.bench_serving --backend sglang --host 127.0.0.1 --port 30000 --model <model> \
    --dataset-name random-ids --random-range-ratio 1 --seed 1 --disable-tqdm \
    --random-input-len $1 --random-output-len $2 --num-prompts $3 --max-concurrency $4
done
```

## FlashInfer BF16 KDA prepared-export integration: results (GB300, Kimi-Linear-48B-A3B-Instruct, TP2)

**TL;DR.** The prepared BF16 export is wired in and runs for every KDA prefill (27k calls, 0 fallbacks, incl. under the breakable prefill CUDA graph); end-to-end it is numerically close (identical greedy tokens at 8K/32K/64K, gsm8k 0.90→0.92, LongBench-v2 0.39→0.45) but **slower** (serving throughput 0.87–0.95×, TTFT 0.58–0.88×; single-request prefill slower up to 8K, break-even 32K, +6 % at 64K) because each call rebuilds a host-side plan (0.5–3.5 ms/layer) although the kernel itself is 1.1–2.5× faster on GPU. The real-activation per-chunk state check **fails**: on Kimi-Linear activations with extreme per-channel gates the export's states are 5–10× (layer 0: ~100×) further from an FP32 reference than Triton's. Not ready to replace Triton; findings and reproducers below.

Code: `yyihuang/sglang` branch [`kda-integ/prepare-bf16-export`](https://github.com/yyihuang/sglang/tree/kda-integ/prepare-bf16-export) (on top of this PR's branch). It routes the FP32-state-pool Cake prefill through `flashinfer.prepare_bf16_kda_prefill` (flashinfer main after #5363 / #5370): packed q/k/v, raw gate, row-strided BF16 beta logits, host `extend_seq_lens_cpu`, int64 `cu_seqlens`, int32 state indices, BF16 per-64-token checkpoints. The `recurrent_kda(backend="cake")` facade (BF16 pool), Triton fallback and route telemetry are unchanged; `SGLANG_KDA_CAKE_PREFILL_API={auto|prepared|facade}` selects the API.

Commits: `92da0c4642` prepared route, `f1bf701cce` real-activation dump hook + replay script, `339b772dc7` checkpoint test semantics, `8fce34c0a3` allow FP32 pool for cake prefill in server_args, `c396a2a2d6` admit the unbounded softplus gate (Kimi-Linear has no `gate_lower_bound`), `11b4f65e9a` detach gate nn.Parameters (the export refuses autograd-tracked inputs), `b93921d842` per-rank dump filenames, `ff01c35bf6` replay unbounded-gate dumps + BF16-rounded checkpoint-0 test, `bc9a76b834` replay with the serving beta layout, per-file error rows, activation stats.

- **Cake export**: the *state* error (final and per-chunk checkpoints) is Cake-specific — 0.42 at layer 0, 0.05–0.14 at layers 1–4, ≤0.02 elsewhere — while Triton's chunk states stay at ≤0.007. The trigger is the dynamic range of Kimi-Linear's unbounded per-channel gate on real tokens: `g_eff = −exp(A_log)·softplus(g_raw + dt_bias)` reaches −60…−560 per token/channel (cumulative −600…−10⁴ over a chunk) on 1–19 % of the channels, i.e. channels that must be *fully* forgotten within a few tokens. The most plausible mechanism is limited range/precision in how the export applies the per-channel decay to the carried state (BF16/exp2 with clamping, or a decay applied to the wrong side of the update); that has to be located in the Cake schedule itself.
- **Production `chunk_kda` (SGLang Triton prefill)**: its *output* also deviates from the exact recurrence on the same calls (0.02–0.32; states correct), and its 64-token-chunk formulation is what the A/B "Triton arm" and the logprob baseline are. So on these sequences prefill (chunked) and decode (recurrent) in SGLang do not compute the same function today; I flag it here for the maintainers rather than treating it as part of this integration.

**Bottom line for the acceptance criterion** ("real-activation per-chunk state rel L2 of the same order as Triton"): **not met** for the Cake prepared export. It is exact on Gaussian inputs, produces identical greedy tokens and no eval regression end-to-end, but its per-chunk/final states on real Kimi-Linear activations are 5–10× worse than Triton's overall and ~100× worse at layer 0, driven by extreme per-channel gate values. This must be fixed on the kernel/export side before the prepared path can replace Triton for prefill with radix-cache checkpoints; the dumps (cluster scratch, 42 GB) and the replay / three-way / arbitration scripts in this branch reproduce it offline in minutes.

## Follow-up: root cause of the real-activation state error, and adapter default changed

**Root cause (kernel side).** The exported BF16 fused M128 schedules (`flashkda_blackwell_bf16_fused_m128.py`, `UNBOUNDED_BALANCED_EXP2_LIMIT = 126`) apply the per-channel KDA decay by splitting every pairwise factor 2^(p_i − p_j) (p = cumulative log2 gate of the channel) into a q-side term 2^(p_i − c) and a k-side term 2^(c − p_j) with a single "balanced" reference c = (chunk total)/2 per 64-token chunk, and both exponents clamped to [−126, 126] so the FP32 `ex2` never overflows. The generated CUDA shows it directly:

```c
float _max_0 = max_noftz(prefix - common_log2, -126.0f);
float _min_0 = fminf(_max_0, 126.0f);
float decay = approx_exp2(_min_0);
qd_vec[e] = decay; kd_vec[e] = decay; ki_vec[e] = k_raw_vec[e] / decay;
```

This is exact only while a channel's total log2 decay over the chunk stays within ~252 (≈ −175 nats, i.e. an average gate above ≈ −2.7 per token). Beyond that the clamp collapses factors that should be ≈ 0 into ≈ 1 (2^(−126)·2^(+126)), which corrupts the chunk state and everything downstream. On the real Kimi-Linear dumps the unbounded gate `−exp(A_log)·softplus(g + dt_bias)` reaches −60 … −560 *per token* on 1–19 % of the channels (chunk totals −600 … −10⁴ nats) — exactly the calls where the export's states were 0.05–0.42 off. FLA's `chunk_kda` avoids this by construction: it uses a reference *between* the two tokens (16-token sub-block boundaries, pairwise `exp(g_i − g_j)` inside a sub-block), so both factors are ≤ 1 and can only underflow harmlessly. Fixing the export therefore needs a schedule change (sub-block references or pairwise decays in the intra-chunk tile), not a tolerance or dtype tweak. Gaussian tests never leave the safe range (`|g_eff| ≲ 3`), which is why every unit test passes.

*(A synthetic confirmation sweep — Gaussian inputs with the gate strength scaled across the ±252 log2 chunk-total threshold, Triton and Cake vs the FP32 recurrence — is written as `stage/gate_threshold_test.py` in my workspace but did not get a GPU slot before I released the cluster allocations; the real-dump evidence above (arbitration table + gate-softening ablation) already isolates the mechanism. I can run the sweep on request.)*

**Adapter default changed (`5d48dcc595`).** `lower_bound=None` (unbounded softplus, i.e. Kimi-Linear) is no longer admitted to the prepared export by default; it stays on Triton with reason `invalid_lower_bound` unless `SGLANG_KDA_CAKE_ALLOW_UNBOUNDED_GATE=1` is set. Bounded gates (finite negative `lower_bound`) are unaffected. The unbounded unit test sets the opt-in; `test_kda_prefill_unbounded_gate_defaults_to_triton` pins the default.
