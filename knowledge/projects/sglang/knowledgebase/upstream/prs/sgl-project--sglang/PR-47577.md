# [Fix] megamoe: Allocate the symmetric buffers before KV cache sizing

[Upstream PR](https://github.com/sgl-project/sglang/pull/47577) · state: closed · merged: True

## Original PR description

MegaMoE's symmetric buffer was allocated by the first MegaMoE forward, after the KV cache had been sized. It lives for the whole run, but it came out of the runtime slack (`B * (1 - mem_fraction_static)`) meant for activations and CUDA graphs. The buffer covers the worst-case routing at `SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK` and grows with it: at the default cap of 8192 it is a few GB and fits in the slack, but at a large cap it does not. With DeepSeek-V4.1-Flash, DP attention 4, MegaMoE, DSpark and a cap of 65536, the target's buffer (22.31 GB per GPU) is allocated during the first forward and leaves no room for the draft's (11.78 GB), so startup fails with `CUDA driver error: out of memory` in `symm_mem.empty` at `--mem-fraction-static 0.9`.

- `allocate_mega_moe_buffers` allocates the buffers of the model's ready `DeepseekV2MoE` MegaMoE layers through the same `_mega_moe_buffer` the forward uses, and logs their count and size. `ModelRunner.initialize` calls it after the post-load model changes, before the KV cache is sized, so the KV budget charges the buffers like the weights; the draft worker does the same before its own KV sizing.
- `_run_mega_routed` passes that buffer into `run_mega_routed_experts` (new optional `buf`), so the DeepSeek MoE path builds the buffer key only in `_mega_moe_buffer` and the up-front buffer cannot drift from the one the forward uses. Other callers pass no `buf` and keep building their own.
- The `--speculative-enable-w4a4-mxfp4-megamoe` help text and the server-arguments doc drop the advice to lower `--mem-fraction-static` for a draft buffer allocated after the KV pool is sized.

With MegaMoE on, the KV pool is smaller by the buffer size. Other MegaMoE models (Qwen MoE, MiniMax-M3, Kimi-K3) and AMD's FlyDSL path still allocate at the first forward.

## Verification

DeepSeek-V4.1-Flash on GB300, DP attention 4, MegaMoE, DSpark, breakable prefill graphs at 4096 and 8192 tokens, `SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK=65536`, `--mem-fraction-static 0.9`:

| Code | Startup | Buffers per GPU (GB) | 8K prefill step (ms) | GSM8K (%) |
|---|---|---|---|---|
| main | fails, `CUDA driver error: out of memory` in `symm_mem.empty` | - | - | - |
| this PR | serves | 22.31 (target) + 11.78 (draft) | 87.34 | 98.00 |

GSM8K is sgl-eval, 200 questions, greedy, thinking off.
