# [Perf] [AMD] distributed: Use AITER FlyDSL INT4 QuickReduce on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/46850) · state: open · merged: False

## Original PR description

## Motivation

On MI355X (gfx950), INT4 QuickReduce (`ROCM_QUICK_REDUCE_QUANTIZATION=INT4`) runs SGLang's HIP kernels. AITER has a faster FlyDSL INT4 two-shot QuickReduce, `aiter.ops.flydsl.QuickAllReduceInt4` (ROCm/aiter#4970, merged), which SGLang does not use yet. This PR adds an opt-in switch, `SGLANG_USE_AITER_FLYDSL_QUICK_REDUCE`, that runs INT4 QuickReduce with that kernel on gfx950. At hidden 5120 and TP4 the kernel is 18 to 22% faster per call than the HIP INT4 kernel at 80 and 160 MiB (in serving, QuickReduce only gets payloads above 64 MiB) and up to 37% faster for smaller ones, with a slightly higher SQNR (19.2 vs 18.3 dB). On DeepSeek-V4.1-Flash serving, output throughput is 1.6 to 2.7% higher at 60k and 128k input and unchanged at 1k input. Nothing changes unless the switch is set. vLLM uses the same kernel since vllm-project/vllm#59478.

## Modifications

- `quick_all_reduce.py`: with the switch on, INT4 selected and a gfx95 GPU, `QuickAllReduce` creates `QuickAllReduceInt4` instead of the HIP QuickReduce, so one object owns the IPC buffers, and `quick_all_reduce` runs it. `should_quick_allreduce` keeps the existing size limits and also requires contiguous, 16-byte-aligned bf16 input, which the FlyDSL kernel needs; other payloads go to the next all-reduce method. The size limit is capped at the kernel's 4 GiB window, and `close()` releases the communicator.
- `environ.py`: `SGLANG_USE_AITER_FLYDSL_QUICK_REDUCE = EnvBool(False)`, with a row in `docs/docs/references/environment_variables.mdx`.
- `test/registered/unit/distributed/test_quick_all_reduce.py` (CPU): bf16 input goes to FlyDSL; fp16, weakly contiguous and 8-byte-offset inputs, which the existing checks accept, do not; `close()` releases the communicator. The reject cases fail without this change.
- Not changed: the all-reduce order. Custom all-reduce is still tried before QuickReduce, so QuickReduce only gets payloads above the custom all-reduce size limit; in the runs below those were prefill chunks above 64 MiB (more than about 6.5k tokens at hidden 5120). gfx942 is not enabled, because it was not tested.

## Accuracy Tests

Setup: DeepSeek-V4.1-Flash, TP4 on 4 x MI355X, image `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261026` (SGLang `316ff4dce2`, AITER `285579b62`) with this PR's `quick_all_reduce.py` and `environ.py` on both sides, `SGLANG_USE_AITER=1`, `ROCM_QUICK_REDUCE_QUANTIZATION=INT4`, chunked prefill 16384, radix cache off, `--monokernel-backend amd`. The only difference between the sides is `SGLANG_USE_AITER_FLYDSL_QUICK_REDUCE` (0 or 1). In every FlyDSL run all 4 ranks log `QuickReduce INT4 uses aiter FlyDSL QuickAllReduceInt4 (max 2048 MiB)` at start-up; no HIP run does. Two server runs per side; GSM8K (1,319 questions, 2,048 max tokens) and GPQA Diamond (198 questions, thinking on) use `python -m sglang.test.run_eval`, and NIAH uses lm-eval `niah_single_2`.

| Benchmark | HIP INT4 (run 1, run 2) | FlyDSL INT4 (run 1, run 2) | Mean change |
| --- | --- | --- | --- |
| GSM8K | 97.41, 97.03 | 97.18, 96.96 | -0.15 |
| GPQA Diamond | 89.39, 88.38 | 86.36, 87.88 | -1.77 |
| NIAH single_2, 64k and 128k | 100, 100 | 100, 100 | 0 |

Both differences are within sampling error: the standard error of the difference of the two-run means is about 0.45 points for GSM8K and 2.3 points for GPQA. On the earlier 10-03 image, FlyDSL scored higher on GPQA in both server configs (+0.5 and +2.3 points). The AITER op test (`op_tests/multigpu_tests/test_flydsl_quick_allreduce_int4.py --tp 4`) passes on every rank, and the SQNR against an fp32 all-reduce is 19.19 dB for FlyDSL and 18.31 dB for the HIP INT4 kernel.

## Speed Tests and Profiling

Kernel, same image, TP4, bf16, hidden 5120 on MI355X: CUDA-event time per call, mean over 4 ranks and 4 repeats (20 warm-up and 100 timed calls each, HIP and FlyDSL order alternated, repeats within 3%). In serving, only payloads above 64 MiB reach QuickReduce (the 80 and 160 MiB rows); custom all-reduce takes the smaller ones.

| Rows | MiB | HIP INT4 (us) | FlyDSL INT4 (us) | Change |
| --- | --- | --- | --- | --- |
| 16384 | 160 | 612.9 | 503.6 | -17.8% |
| 8192 | 80 | 333.3 | 261.1 | -21.6% |
| 4096 | 40 | 197.5 | 140.4 | -28.9% |
| 2048 | 20 | 110.2 | 73.5 | -33.3% |
| 1024 | 10 | 69.0 | 43.6 | -36.8% |

Serving, same setup as the accuracy tests: 22 points of `bench_serve` with random data (1k and 8k input with 1k output at 4 to 256 users, 60k input with 600 output and 128k input with 1k output at 4 to 32 users, range ratio 1.0, temperature 0). Each point has three paired repeats: run 1 with seeds 1 to 22 in a fresh server per side, then run 2, which runs the sweep twice in one server, first with seeds 1 to 22 and then with seeds 101 to 122, so the second pass has no warm-up or JIT effects. The two sides swapped GPUs between run 1 and run 2. For each point the table takes the median of the three FlyDSL/HIP ratios, then the geometric mean over the points.

| Input | Points | Output throughput | Median TTFT | Median TPOT | Median E2E latency |
| --- | --- | --- | --- | --- | --- |
| 1k | 7 | +0.1% | -0.9% | -0.1% | -0.1% |
| 8k | 7 | +0.6% | -1.7% | 0.0% | -0.9% |
| 60k | 4 | +1.6% | -1.1% | -1.4% | -1.4% |
| 128k | 4 | +2.7% | -3.4% | -3.4% | -1.5% |
| All | 22 | +1.0% | -1.6% | -0.9% | -0.9% |

The gain grows with input length, as expected: QuickReduce only runs for prefill chunks above about 6.5k tokens. No point has lower throughput beyond its run-to-run range, which is the change between run 1 and the first pass of run 2 at the same seed: 0.2 to 0.6% at 8 of the 14 points with 1k or 8k input, and up to 5.4% at 60k and 128k input. Single long-input points are therefore not conclusive, but 20 of their 24 throughput changes are positive. Median TPOT is 0.2% higher at the two 4-user points with 1k and 8k input, just beyond their range of 0.1 to 0.2%. On its own, the warm second pass gives +0.78% throughput over 21 points. It leaves out one HIP point (128k input, 8 users), which stalled once: p99 TTFT 32.4 s against a median of 10.9 s over the six runs of that point. The first point after a fresh server start is slow on both sides (median TTFT 2.0 to 2.8 s against 0.18 s in the second pass); the median of three repeats limits both effects. The KV pool is 3.8% larger with FlyDSL, because the HIP QuickReduce buffers are not allocated. A torch profile on the earlier 10-03 image showed 43 FlyDSL QuickReduce calls per rank for a 16384-token prefill chunk and no HIP QuickReduce kernel.
