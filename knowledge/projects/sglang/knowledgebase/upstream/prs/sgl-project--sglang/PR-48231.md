# [Fix] disaggregation: Reject a decode peer whose KV page stride differs at Mooncake registration

[Upstream PR](https://github.com/sgl-project/sglang/pull/48231) · state: open · merged: False

## Original PR description

## Motivation

Fixes #48230.

- The Mooncake sender writes decode pages at `dst_ptr + page * item_len` using the prefill's `item_len`. When the roles allocate different KV layouts, every transfer silently corrupts the decode KV, and pages near the end of the pool overrun the layer buffer (`Requested address ... not found`).
- One way to hit it is a DSA model whose prefill and decode use different DSA backends (656 B/token with `flashmla_*`, 576 B/token with `trtllm`). Another is a different `--kv-cache-dtype` on each role (#19355).
- The decode already sends its `dst_kv_item_lens` at registration, but nothing compares them outside `--enable-unified-memory`.

## Modifications

- `MooncakeKVManager._kv_layout_mismatch`: at peer registration, compares the prefill KV item lengths with the decode's. It reuses the PP-aware `_state_stride_mismatch` that already guards the state buffers. On a mismatch, the peer goes into `state_layout_rejections`, so every request to that peer fails with one clear reason (both lengths, the page size, and the likely cause) and no bytes are written. Ascend inherits the check.
- The check is skipped where the stride differs by design or is checked elsewhere: TP-sliced MHA, DCP relayout, and unified memory (`_validate_envelope_kv_layout`). There is no opt-out flag, the same as the existing state-layout check.
- `test_disaggregation_wire.py`: a regression case covering a rejected mismatch, a PP stage that judges only its own layers of a full decode, and a TP-sliced MHA peer that is not checked. It fails on main and passes with this change.

## Accuracy Tests

GLM-5.2 NVFP4 on GB300, one tray per role, Mooncake over MNNVL, the reproduction commands of #48230 (DEP4 decode, 262,144-token decode pools). Nov-03 SGLang nightly image (`lmsysorg/sglang:nightly-cu134-20261103-40a64e1`) with this branch's `python/sglang` on top. GSM8K-50 is `few_shot_gsm8k`; the load is 256 random 16k-token prompts at concurrency 64, which takes decode token usage to 0.94:

| Prefill / decode KV (B/token per layer) | Prefill | GSM8K-50 | Load: failed requests | `Requested address` | Rejected peers |
|---|---|---|---|---|---|
| 656 / 576 (flashmla prefill, default decode) | DEP4 | refused | 256 / 256, all with "PD KV layout mismatch" | 0 | 16 / 16 |
| 576 / 576 (defaults on both) | DEP4 | 0.88 | 0 / 256 | 0 | 0 |
| 576 / 576 (defaults on both) | PP4 (TP1) | 0.88 | 0 / 256 | 0 | 0 |

- Mismatched: each prefill rank rejects every decode rank at registration (`prefill=41984 decode=36864, page_size=64`), so no KV bytes are written. Each request fails at transfer time, and the client gets the reason in the 500 response. Without this change the same setup scores 0 on GSM8K and fails 83 / 256 requests with `Requested address ... not found` (#48230).
- Matched layouts are accepted with no rejection, including a PP4 prefill (each stage checks only its own layers) against a DEP4 decode.

**Issue**

The TP-sliced MHA case does not test the TP guard in `_kv_layout_mismatch`. It uses `kv_layer_ids=[]` and `dst_kv_layer_ids=[]`, so `_state_stride_mismatch` returns `None` at its MHA early return. With the `self.attn_tp_size == info.dst_attn_tp_size` guard removed, all four subtests still pass.

**Why it matters**

Hybrid pools that wrap one KV view, and the MiniMax M3 NVFP4 pool, publish KV layer ids. For those MHA peers, only this guard stops a TP 2 -> 4 peer from being rejected with `KV item length mismatch for paired entries src[0]=4096 dst[0]=2048`.

**Fix**

Give this case layer ids on both sides, for example `[0, 1, 0, 1]` (K then V), so it fails when the guard is removed.
