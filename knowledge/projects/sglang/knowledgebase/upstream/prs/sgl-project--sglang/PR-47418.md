# [Perf] [AMD] DFlash: FP8 KV and tuned launch for draft SWA verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/47418) · state: open · merged: False

## Original PR description

## Motivation

Stacked on #46648, so only the last commit is new here.

#46648's DFlash draft verify kernel only accepts BF16 and FP16 KV, so a draft with FP8 KV, like GLM-5.3-Flash's on MI355X, falls back to `extend_attention_fwd` at about 270 us per layer. Its launch config was set for Kimi-K3's draft, which has one KV head per GPU, and runs GLM-5.3-Flash's 8 KV heads slower than it could past batch 8.

## Modifications

- `can_handle` accepts `float8_e4m3fn` KV. The kernel already casts q and the softmax probabilities to the KV dtype, as `extend_attention_fwd` does.
- The split count is the power of two nearest 512 / (batch size x KV heads), between 4 and 16 and halved for blocks above 8. Tiles are 128 keys, with 2 warps when a program has at most 32 rows, else 4.
- Splits with no keys skip their partial store and the merge. When every split has keys, the merge runs without the per-split check, so its loads overlap across splits.
- The merge runs 4 warps for blocks above 8.

## Accuracy Tests

The tests also run with FP8 KV at GLM-5.3-Flash's head counts and on a batch of short windows at every split count. They pass on 1xMI355X, and the FP8 one fails on #46648. Against an FP32 reference over 110 cases, the max error matches #46648's (FP8 5.5e-2 vs 5.2e-2, BF16 4.1e-3 vs 3.8e-3).

## Speed Tests and Profiling

Per layer on 1xMI355X with the KV out of cache (us). #46648 runs `extend_attention_fwd` for FP8.

| Draft | Window | Batch | #46648 | This PR |
| --- | --- | --- | --- | --- |
| GLM-5.3-Flash, 32/8 heads, block 8, FP8 | 4095 | 1 | 272.9 | 19.6 |
| | 4095 | 8 | 274.5 | 31.4 |
| | 4095 | 32 | 1091.2 | 74.1 |
| Kimi-K3, 4/1 heads, block 8, BF16 | 4095 | 1 | 24.4 | 20.9 |
| | 4095 | 16 | 36.1 | 24.3 |
| | 512 | 16 | 10.9 | 12.2 |

With GLM's heads it's faster at every block (1 to 16), window (1 to 4095 keys), and batch (1 to 64) tested, including mixed windows. With K3's heads it's 0.3 to 1.3 us slower at batch 16 to 32 with windows of 512 keys or fewer (10 of 72 points), where #46648's 8 splits with 64-key tiles suit short windows and the split count is fixed at graph capture.
