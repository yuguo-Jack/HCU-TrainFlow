# [Feat] fp8: Write block-FP8 linear results into caller-owned outputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46466) · state: open · merged: False

## Original PR description

## Motivation

`RowParallelLinear` can write its result into caller-owned storage through the quant method's `apply_into` (fused collective buffers use it, e.g. Kimi-K3's o_proj into the all-reduce buffer), but only `UnquantizedLinearMethod` implements it. Block-FP8 projections therefore keep an extra allocation and copy per call.

## Modifications

- `fp8.py`: `Fp8LinearMethod.apply_into`. On the DeepGEMM block-FP8 path with a contiguous bf16 output it passes the tensor down and the GEMM writes it directly; every other path (Marlin, MXFP8 view, pre-packed MXFP8 inputs, Triton fallback) computes normally and copies.
- `fp8_utils.py`: `deepgemm_w8a8_block_fp8_linear_with_fallback` takes an optional `output`.
- `kernels/ops/gemm/fp8_kernel.py`: `prepare_block_fp8_matmul_inputs` / `w8a8_block_fp8_matmul_deepgemm` take an optional output tensor instead of always allocating.
- Test: `test_fp8_linear_apply_into.py` checks `apply_into` returns the passed tensor and matches `apply` bit for bit on the triton and deep_gemm backends, and rejects a wrong-shaped output.

## Accuracy Tests

GB300 (SM103): `test_fp8_linear_apply_into.py` 3 tests OK (triton and deep_gemm: `apply_into` returns the passed tensor and matches `apply` bit for bit at three shapes); `test_fp8_blockwise_linear_backends.py` 23 tests OK (7 skipped by architecture), unchanged from main. Same three tests also pass on an SM107 node.

## Speed Tests and Profiling

Kimi-K3 NVFP4 TP8, batch 1, 60k in / 1k out: 126.2 -> 132.2 output tok/s (+4.8%), 12,779 -> 12,354 kernel launches over five decode steps (fork measurement, where o_proj now writes the collective buffer directly).
