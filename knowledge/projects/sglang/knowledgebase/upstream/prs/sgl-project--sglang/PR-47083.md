# [Fix] speculative: Preserve NaN argmax semantics in verify kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/47083) · state: open · merged: False

## Original PR description

## Motivation

`row_argmax`'s two-stage path (rows <= 64) and the DSpark fused markov greedy step reduce scores with `tl.max` and an equality tie-break, so a NaN score never matches its own maximum. On current main an all-NaN row makes `row_argmax` return the vocab width (131072 on a 131072-wide row) and the markov combine return `INT_MAX` -- both out of range, and the index feeds the next embedding lookup, so a NaN batch fails device-side instead of drafting token 0 like `torch.argmax`.

Mixed rows are wrong too: a NaN anywhere in the row is invisible to the max, so the kernel returns the best finite index (or an arbitrary one) where `torch.argmax` returns the first NaN.

The medium-row path (rows > 64) already reduces with `_argmax_pair`, which implements torch's NaN priority and lowest-index ties. This PR brings the two remaining reductions to the same semantics.

Revives #46433 (same fix; the author closed it during stale-PR cleanup without review, and the bug is still live on main). This is that diff ported onto current main, plus the kernel tests the original PR didn't have.

## Modifications

One commit:

- `python/sglang/kernels/ops/speculative/row_argmax.py`: `_argmax_partial_kernel` reduces each tile with a NaN-propagating max and selects NaN lanes explicitly (equality alone cannot match them); `_argmax_final_kernel` reduces the partials with `_argmax_pair`.
- `python/sglang/kernels/ops/speculative/dspark/dspark_draft_model.py`: `_markov_greedy_partial_kernel` and `_markov_greedy_combine_kernel` reduce with `_argmax_pair`, keeping padded lanes out of the result even when every valid score is NaN or `-inf`.
- `test/registered/kernels/ops/speculative/test_spec_argmax_nan_semantics.py`: new kernel tests for both files -- all-NaN rows, first-NaN-wins, NaN-beats-finite-max, all-`-inf`, exact ties, and random parity vs `torch.argmax` on both row-count paths.

Finite-input results are unchanged: the reduction is comparison-only and the tie-break order is the same as before.

## Accuracy Tests

H100 pod, unpatched (main) vs patched files loaded side by side, `torch.argmax` as ground truth:

- Before: all 8 NaN cases wrong -- all-NaN 1x131072 -> 131072, all-NaN 4x129280 -> 2020, markov all-NaN 1x152064 -> 2147483647 (`INT_MAX`), first-NaN rows -> arbitrary indices, NaN loses to the finite max. All 7 finite cases correct.
- After: 15/15 cases match `torch.argmax` exactly (NaN priority, first-NaN / lowest-tie index, padded-lane exclusion).
- The added test file passes 10/10 on the same H100 (`Ran 10 tests in 2.473s -- OK`).

## Speed Tests and Profiling

H100, CUDA-event median of 200 iters on the changed kernels (finite random inputs -- the hot path), unpatched vs patched:

| kernel | shape | before | after |
|---|---|---|---|
| row_argmax | 1x131072 | 38.2 us | 34.5 us |
| row_argmax | 8x131072 | 37.1 us | 34.2 us |
| row_argmax | 32x152064 | 37.3 us | 34.7 us |
| row_argmax | 64x152064 | 38.9 us | 37.6 us |
| markov greedy | 1x152064 | 48.6 us | 46.0 us |
| markov greedy | 8x152064 | 85.7 us | 86.2 us |
| markov greedy | 64x129280 | 457.1 us | 459.6 us |

No regression: one `tl.reduce` replaces the old max + where + min sequence, so the changed kernels are the same speed or slightly faster. No steady-state throughput claim -- the kernels are a small slice of the decode step.
