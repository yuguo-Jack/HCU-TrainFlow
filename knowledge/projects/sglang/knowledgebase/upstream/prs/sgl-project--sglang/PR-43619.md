# [DSA] Split k-pool indexer prefill rows across attention-TP ranks

[Upstream PR](https://github.com/sgl-project/sglang/pull/43619) · state: open · merged: False

## Original PR description

## Motivation

Under attention TP, every rank runs the k-pool DSA indexer (GLM-5.3-Flash, `index_kpool > 1`) for every query row of a prefill extend, so the indexer is computed `tp_size` times. The FP8 MQA logits and pooled top-k grow with query rows x pooled keys, so at long context they dominate the extend. In a torch profile of one 8192-token extend behind a 900K-token cached prefix (4x RTX PRO 6000 Blackwell Max-Q, TP4), `fp8_mqa_logits` and `kpool_topk_transform` took 681 ms of 1680 ms of GPU time on each rank.

Each row's top-k depends only on that row's logits, pooled length and page-table row (the existing row chunking relies on this), so the rows can be divided between ranks and the results gathered.

## Modifications

- `SGLANG_DSA_INDEXER_ROW_SPLIT_MIN_ELEMS` (default 0, disabled). When an eager k-pool prefill extend scores at least this many query-row x pooled-key elements, each attention-TP rank computes the top-k for a contiguous share of the query rows (shares differ by at most one row and are padded to the largest), and the shares are all-gathered over the attention-TP group. The cost estimate sums query rows x pooled keys per request, so a batch of short requests is not counted against the batch's total key count.
- Both indexer call sites use it: the k-pool extend plan, and the per-request path (one all-gather per qualifying request).
- The split is skipped under CUDA graph capture and breakable-graph replay, under attention context parallelism, with a single-rank group, and for fewer than `4 * attn_tp_size` rows. Within attention TP, all inputs of the decision are identical on every rank.
- The existing per-chunk loop moves to `_kpool_topk_rows`, which writes rows relative to the share's first row; the memory-budget row chunks are intersected with the rank's share.

## Accuracy Tests

- New GPU test `test_dsa_kpool_indexer_row_split.py` simulates four ranks on one GPU with the real DeepGEMM logits and fused k-pool top-k kernels, and compares each rank's gathered result with the unsplit path: tail columns exactly, pooled columns by the logits they select. It covers a single chunk, budget chunks that straddle rank shares with padded output rows, and 33 rows over eight ranks.
- In a server run that also computed the unsplit result at every split indexer call (4128 calls across ranks and layers), the gathered top-k selected the same token sets as the unsplit path except at exact score ties at the k-th position. The unsplit path differs from itself at the same rate when run twice on identical logits (logits were bitwise equal), because the radix selector breaks ties arbitrarily.
- 600K-token retrieval (a 6-digit code at depths 5%, 35%, 65% and 95%): 4/4 with the split enabled.

## Speed Tests and Profiling

Author measurements on 4x RTX PRO 6000 Blackwell Max-Q (PCIe Gen4, no NVLink), GLM-5.3-Flash FP8, TP4, FP8 KV cache, `--chunked-prefill-size 8192`, EAGLE 3/1/4, on main 3831e7e0 with unrelated local patches. TTFT of single streamed requests.

| 1,040,435-token prompt, TTFT | 2 runs |
|---|---|
| Off | 171.5 s, 173.3 s (6.0K tok/s) |
| `SGLANG_DSA_INDEXER_ROW_SPLIT_MIN_ELEMS=134217728` | 134.8 s, 134.8 s (7.7K tok/s) |

TTFT of an 8192-token tail behind a cached prefix (median of 3; includes tokenizing the whole prompt). Split on is `=1` (every extend) for 16K-256K and `=134217728` for 900K:

| Cached prefix | Off | Split on |
|---|---|---|
| 16K | 1.16 s | 1.17 s |
| 32K | 1.22 s | 1.21 s |
| 64K | 1.29 s | 1.29 s |
| 128K | 1.48 s | 1.43 s |
| 256K | 1.87 s | 1.75 s |
| 900K | 4.28 s, 4.09 s | 3.72 s, 3.68 s, 3.54 s |

The split costs 10 ms at 16K and breaks even at 32K-64K; the threshold 134217728 (8192 rows x 16384 pooled keys, about 64K of context) keeps it off below that. With the threshold, cold 8K/32K/128K prompts and decode throughput were unchanged within run-to-run spread.
