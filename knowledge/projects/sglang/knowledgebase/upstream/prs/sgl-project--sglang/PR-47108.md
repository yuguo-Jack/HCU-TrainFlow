# [Fix] rust-server: Admit a multimodal model's generations only once its MM processor is installed

[Upstream PR](https://github.com/sgl-project/sglang/pull/47108) · state: closed · merged: True

## Original PR description

## Motivation

The Rust frontend's listeners start serving as soon as the runtime is constructed, and the multimodal (MM) pool, whose processor supplies the media admission hooks (`check_media` / `fetch_media`), is installed a moment later by the launcher. A generation request that arrives in that gap is admitted without those hooks: media the model cannot take is accepted instead of refused (and can reach the forward pass, where a missing encoder takes the scheduler down), and a URI the processor's fetcher would have handled gets a misleading 400 "unsupported URI".

The generation-free `/health` had the same gap: with `--skip-server-warmup` it answered 200 as soon as the listener came up, before the processor existed. The Python server never does that, because it builds its processor before its listener binds.

## Modifications

- `CoreHandle::prepare_generations` is the single admission path for native `/generate` (single and batch), the OpenAI routes, gRPC Generate and the startup warmup. For a multimodal model it now waits on a `tokio::sync::SetOnce` holding the processor, which `set_mm_processor` fills when the pool starts (`OnceLock` → `SetOnce`). Early clients see no new error; they get their answer once the processor is installed. The wait has no deadline: the pool starts during launch, and runtime shutdown cancels a waiting handler with the api runtime. Text models never wait.
- `CoreConfig` gains `multimodal`, set from `ServerArgs::model_is_multimodal()` in `runtime::start`.
- Every other route serves from the start. In particular the PD bootstrap registry is never blocked: holding the listeners instead would let another TP rank of a single-node TP>1 prefill run out of its registration retries while rank 0 builds its processor.
- `/health`, `/health_generate` and gRPC HealthCheck share one readiness check, `CoreHandle::is_serving`: startup warmup finished or skipped and, for a multimodal model, the processor installed. `/model_info` keeps answering 200 as soon as the listener is up.
- Test fixtures that build a `CoreConfig` set `multimodal: false`; the Python `RustServer` docstrings describe the new admission behaviour (no Python code change).

Tests:
- `multimodal_admission_waits_for_the_mm_pool` (`utils/runtime.rs`) starts PD-prefill runtimes so the registry is mounted. With a multimodal runtime whose pool has not started: `PUT /route` gets 200, `/health` gets 503, and a `/generate` is not admitted; the same request is admitted after `start_mm_workers_with_processor`. A text runtime admits at once. A multimodal runtime shut down with a request still waiting returns in under 3 s and closes its port.
- `generation_free_health_waits_for_the_mm_processor` (`http/native_api.rs`) calls the generation-free `/health` handler of a multimodal model with warmup skipped: 503 before the processor is installed, 200 after.

Notes on where the hunks sit: this was written against the pre-#46181 layout, where the admission path, the health probe and the handle lived together in `core/handle.rs`. On current main the same lines sit in `handlers/handle.rs` (config flag, `SetOnce` slot, `is_serving`), `handlers/generate.rs` (`prepare_generations`) and `handlers/health.rs` (`probe_health`), the new test fixtures carry the `peer_endpoints` (#46181) and `openai_chat` (#45449) fields every other fixture carries, and every `CoreConfig` construction site on main sets `multimodal: false`.

Validation run locally in `rust/`: `cargo fmt --all -- --check`, `cargo clippy --locked -p sglang-server --all-targets -- -D warnings` and `cargo test --locked -p sglang-server`.
