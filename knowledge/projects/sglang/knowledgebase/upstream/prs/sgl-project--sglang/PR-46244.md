# [Perf] diffusion: Project Wan's q/k/v with one GEMM over a shared weight

[Upstream PR](https://github.com/sgl-project/sglang/pull/46244) · state: closed · merged: False

## Original PR description

Stacked on #46228 (Wan q/k RMSNorm + RoPE fusion); review the commits after it.

## Motivation

Each Wan block projects the same normalized hidden states three times (to_q, to_k, to_v; at 720p on 4xB300 three [37800, 5120] x [5120, 5120] GEMMs per block per rank). One [37800, 5120] x [5120, 15360] GEMM reads the input once and runs with fewer tile-wave tails.

## Modifications

`models/dits/wanvideo.py`:
- `WanTransformerBlock.fuse_qkv_weights()` concatenates the three unquantized projection weights and biases into one `[3 * dim, dim]` / `[3 * dim]` buffer and rebinds each layer's parameters as views of its rows, so the parameters, the state dict and in-place weight updates keep working and no memory is added.
- The block keeps no reference to the shared buffer. `_fused_qkv(device)` reads it back from the three layers per call, as views over their storage (`_rows_of_one_buffer`), while they are still consecutive rows of one buffer on the input's device. Only the layers hold the buffer, so moving the module (component residency swapping an A14B expert, `--dit-cpu-offload`), layerwise offload or a weight swap frees it, and the block falls back to the three projections. A LoRA wrapper also turns the fused path off. The check costs ~10 us of host time per block call (4.4 us for the earlier stored-reference version) and is skipped under compile.
- `_qkv_rope` runs one `apply_unquantized_linear` over the shared weight and splits q/k/v as strided views (the fused q/k norm-rope, the Ulysses exchange and attention all take a token stride).
- `WanTransformer3DModel.post_load_weights` fuses every `WanTransformerBlock` and logs how many.

## Accuracy Tests

- `test_model_fast_paths.py::test_wan_fused_qkv_keeps_bits_and_frees_with_its_layers` (new Wan section, whose `_wan_block_env` / `_wan_block` / `_wan_block_inputs` helpers the later Wan PRs reuse): a Wan block (5120, 40 heads) gives the same bits before and after `fuse_qkv_weights`, and the layers' weights are unchanged. A weight moved out of the shared buffer turns the fused GEMM off (still the same bits). `block.to("cpu")` frees every byte the block held on the GPU, the shared buffer included; a version that keeps the buffer referenced fails this check. Re-fusing on CPU gives the concatenated weights, and moving back without re-fusing runs three GEMMs. Re-fusing on GPU runs the fused GEMM again, and every step gives the same bits.
- Wan2.2 T2V A14B 720p, 4xB300, 3-step lossless (crf 0) mp4: md5 identical to the build without the Wan stack for 3 prompts, also after the memory-lifetime fix.

## Speed Tests and Profiling

B300, `[37800, 5120] x [5120, N]` bf16 + bias, each GEMM repeated at the power cap (median): one N = 15360 GEMM 3.976 ms against three N = 5120 GEMMs 3 x 1.354 = 4.062 ms (cuBLAS picks the same `nvjet_sm103_tst_128x256_64x6_2x1_2cta` kernel; outputs bitwise equal). E2E (Wan2.2 T2V A14B 720p, 4xB300, harness single_e2e (fresh server per run, runs interleaved with the other arms)): base (fused q/k norm-RoPE stack) 90.160 / 90.214 s (mean 90.187) -> 90.034 / 90.105 / 90.143 s (mean 90.094), -0.09 s (-0.10%).
