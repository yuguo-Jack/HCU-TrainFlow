# [Fix] gpt-oss: Fix quadratic scans in the Harmony parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/42584) · state: open · merged: False

## Original PR description

## Motivation

`HarmonyParser`, used by the `gpt-oss` tool-call detector and the gpt-oss reasoning parser, has three scans that go super-linear on model output:

1. Until a parsing strategy is chosen, the whole buffer is re-searched **on every chunk** with `(?:^|\s)(?:assistant)?\s*(analysis|commentary|...)`, which backtracks O(W²) over a whitespace run of length W. `TextStrategy.parse` runs the same search.
2. `TextStrategy`'s `^\s*(?:assistant)?\s*` prefix and `(.*?)\s*assistantfinal` backtrack the same way over whitespace.
3. `iter_tokens` slices `text[marker_pos:]` and re-runs `find("|>")` to the end of the text for every unknown `<|` marker.

| Input | Before | After |
|---|---|---|
| one 16-char streaming chunk after `x` + 32,000 spaces | **23.7 s** | 3 ms |
| 32,000 leading spaces + `analysis` | 18.5 s | 10 ms |
| 80k unknown `<|a` markers | ~7x per doubling | linear |

Parsing runs synchronously on the tokenizer manager's event loop, so one such response stalls every in-flight request. Found with an Atheris fuzzing harness that records per-input parse time.

## Modifications

- The two strategy-detection searches only feed a true/false check. `(?<!\S)(?:assistant\s*)?(...)` accepts exactly the same strings (the keyword, or `assistant` followed by whitespace and then the keyword, must be preceded by whitespace or the string start) without the backtracking.
- `TextStrategy` patterns: `^\s*(?:assistant\s*)?(...)` matches the same prefixes as `^\s*(?:assistant)?\s*`. The `\s*` before `assistantfinal` is dropped: the lazy group still stops at the same (first) `assistantfinal`, and its only consumer calls `.strip()`, which removes exactly what `\s` would have.
- `iter_tokens`: the tail is sliced only when it is short enough to be a partial token (`<= len("<|constrain|>")`, the longest literal), and the last `|>` lookup is reused while it is still ahead of the current marker.
- Regression test `TestEdgeCases::test_long_whitespace_and_unknown_markers_parse_in_linear_time` (also asserts the parsed events): 105.7 s on `main`, 0.10 s here.

## Accuracy Tests

- Each rewritten regex vs the original on 500k strings: identical (31k – 237k matches per regex).
- `iter_tokens`: identical token streams on 300k strings.
- Differential test of `main` vs patched `GptOssDetector` and `HarmonyParser` under random re-chunking: **0 mismatches** over 80k inputs (49k events).
- `test/registered/unit/function_call/` + `test/registered/unit/parser/`: 1143 passed.
