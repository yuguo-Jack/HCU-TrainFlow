# [Feat] qwen4-exp: Add node-sharded Mooncake Engram storage

[Upstream PR](https://github.com/sgl-project/sglang/pull/47673) · state: open · merged: False

## Original PR description

## Motivation

Pool Qwen4-Exp PLE N-gram CPU tables across compute nodes using Mooncake EngramStore. Each node stores complete hash-head tables, while Qwen retains its computational vocabulary ownership, collectives, scaling and prefetch behavior.

This PR supports **Qwen4-Exp**, including the Qwen3.8-Flash-Next checkpoint family. It builds on the local HiCache Engram interface in #46248 and requires the remote backend in [Mooncake #5129](https://github.com/kvcache-ai/Mooncake/pull/5129). The diff against main includes the unmerged HiCache foundation.

## Modifications

- Enable `--enable-hi-engram remote` with node shard ID/count, caller configuration, Master endpoint, deployment session, lookup capacity and NIC in `--hi-engram-config`.
- Supply Qwen's head boundaries and table namespace to the shared storage adapter. Load only the node's physical head range, independently of the computational vocabulary shard.
- Preserve Qwen's global lookup IDs and computational mask. Delegate local/remote row access to EngramStore, retaining output dtype, table scaling, collectives and prefetch.
- Keep SGLang's `initialize(rows)` storage interface. Local mode calls `EngramStore.populate`; remote mode calls `EngramStore.populate_shard_and_sync` with node-owned tables and shard metadata. Mooncake encapsulates registration, discovery, RDMA setup and readiness.
- Release checkpoint CPU backing after successful publication. Mooncake shares the final CPU allocation among same-node callers.
- Keep layout selection internal to Mooncake. There are no public layout or QP options.
- Enable `NCCL_CUMEM_ENABLE=1` before distributed initialization in remote mode; reject an explicit `0` before loading weights. NCCL GIN requires cuMem.
- Append Engram fields to the ServerArgs positional field order to preserve existing positional calls.

### Head placement

For each Engram layer, node shard `s` owns whole heads in `[floor(H*s/S), floor(H*(s+1)/S))`, where `H` is the head count and `S` is the node count. This partitions contiguous head IDs by count, independently of computation ranks. With 24 heads / 2 nodes, each owns 12 heads; 10 heads / 3 nodes yields 3/3/4 heads. Different head sizes can produce unequal CPU memory usage. The adapter passes this mapping to Mooncake as `table_owners`.

Initialization must finish before CUDA Graph capture, and lookups sharing a Store workspace must be ordered.

## Speed Tests and Profiling

### Two-node full-model Engine benchmark

**Qwen3.8-Flash-Next-FP8**, two matching nodes, each running an independent **TP4/EP4** compute replica on **4 × NVIDIA L20Z (SM90, 80 GB)**. Only Engram storage is sharded across nodes. Local stores all Engram tables on each node; Shard uses two node owners, four callers per node and `mlx5_{local_rank}` RDMA devices (each selected port reports 200 Gb/s on both nodes).

Every 16K/32K/64K input × concurrency 8/16/32 case generates **1024 output tokens**, with **1 warmup wave + 3 measured waves** on both nodes in both modes. Greedy sampling, `ignore_eos`, deterministic inference, prefix cache disabled, fixed colocated batch submission and deterministic synthetic text-token inputs. No samples were trimmed from the final run. An earlier partial Shard attempt was stopped to add per-wave node synchronization; its results are archived and excluded.

Matched settings: context length 67,584; KV capacity 2,200,000 tokens (enough for 32 × (65,536 + 1,024)); max running requests 32; static memory fraction 0.85; chunked prefill 1,024; decode CUDA Graph batches `[1,2,4,8,16,32]`; prefill CUDA Graph 1,024. Both modes use cuMem=1; Shard started with the variable unset and exercised SGLang's new automatic enablement.

Each table cell averages the two nodes' per-case medians, **per independent model instance**. Throughput is generated output tokens divided by the complete wave duration, including prefill. Positive latency changes are slower; positive throughput changes are faster.

Across 18 host/configuration pairs, geometric-mean Shard/Local changes were **-0.65% output throughput**, **+0.57% TPOT**, and **+1.12% TTFT**. Per-pair throughput changes ranged from -1.26% to -0.34%.

Logical Engram tables decreased from **47.68 GiB to 23.84 GiB per node (50%)**. Median measured process-tree PSS across the node/configuration observations was **64.79 GiB Local → 41.14 GiB Shard**; PSS includes runtime and other CPU allocations and is distinct from logical table size.

Measured through the **streaming Engine API**, including IPC, scheduling and detokenization; **HTTP and input tokenization are excluded**. Concurrency is offered outstanding requests, and chunked prefill overlaps decode. These rates do not isolate stage capacities. This is one process launch per mode per node with repeated waves; it does not establish independent-launch confidence intervals or results for other models/hardware.
