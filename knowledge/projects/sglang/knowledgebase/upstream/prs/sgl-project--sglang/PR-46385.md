# [Perf] speculative: Sample the multi-layer EAGLE draft proposal inside per-step draft-extend graphs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46385) · state: open · merged: False

## Original PR description

## Motivation

With rejection sampling at topk 1 (`--speculative-use-rejection-sampling`), the multi-layer EAGLE draft's per-step draft-extend CUDA graphs computed a softmax and a top-1 that the worker then discarded: it re-sampled each step's proposal eagerly with a softmax over the full draft vocabulary. Only the single combined-graph runner drew the proposal inside its graph. Per-step graphs are what a multi-layer draft runs on wherever the combined graph is not used (for example the triton backend), so each draft step paid an extra eager softmax and sampling pass.

## Modifications

- Each step's graph now draws its proposal (`speculative/multi_layer_eagle_draft_extend_cuda_graph_runner.py`): the runner allocates the temperature and q buffers whenever its graphs may capture the proposal.
- The worker (`speculative/multi_layer_eagle_worker_v2.py`) keys the eager resample and the q snapshot on a read-only `samples_in_graph` property derived from those buffers. Rotation and the per-step top-k clones stay keyed on `rotates_in_graph`. On NPU the runner opts out and keeps the worker-side proposal.
- The proposal keeps its distribution: q = softmax(logits / T) and X ~ q, with q handed to the verify as drawn. Under `--enable-deterministic-inference` the graphs draw the seeded proposal, keyed by the same seeds, positions and draft steps as the worker's eager draw.

Tests:
- CUDA (SM90), `test/registered/kernels/ops/speculative/test_multi_layer_eagle_draft_proposal_graphs.py`: per-step graphs that draw in graph give the same proposals as the eager path over the same q, and seeded in-graph draws repeat bitwise across replays and equal the eager seeded draw.
- CPU, `test/registered/unit/spec/test_multi_layer_eagle_draft_extend_sampling.py`: which path samples (graph or worker) for each runner and flag combination, the NPU opt-out, the q handed to the verify, and the seeded equivalence.

## Accuracy Tests

Determinism, SM90, main `669292bacc` with this PR and the other open unified-memory PRs applied: `thinkingmachines/Inkling-Small`, TP 8, `--attention-backend triton`, `--speculative-algorithm EAGLE --speculative-draft-model-path thinkingmachines/Inkling-Small --enable-multi-layer-eagle --speculative-num-steps 8 --speculative-eagle-topk 1 --speculative-num-draft-tokens 9 --speculative-use-rejection-sampling`, `--enable-deterministic-inference`, temperature 1.0 with a fixed `sampling_seed`. Repeated requests decode identically on the default pool and with `--enable-unified-memory`, for single requests and for requests sharing a prefix.

GSM8K, before upstream's unified-memory rewrite (`python -m sglang.test.run_eval`, all 1314 test questions, 5-shot, greedy; median accept length from the scheduler logs), same model and draft flags on `--attention-backend fa4`, CUDA graphs on:

|---|---|---|
| default | 0.823 / 0.825 | 3.42 / 3.48 |

## Speed Tests and Profiling

Same model and draft flags, radix cache, overlap scheduler, CUDA graphs on. Throughput before and after this PR; the number in parentheses is the larger of the repeat-run and same-config spread.

| main | attention backend | pool | 100 requests of 512 input / 4096 output tokens, concurrency 128 | 192 requests sharing a 4096-token prefix + 128 tokens, 2048 output tokens, concurrency 192 |
|---|---|---|---|---|
| `259f0131c9` | fa4 | default | -1.2% (1.6) | +0.8% (1.8) |
| `259f0131c9` | fa4 | `--enable-unified-memory` | +8.7% (1.6) | +7.5% (1.8) |
| `efdcb420c7`, with #45668 | triton, `--max-running-requests 14` | default | +3.0% (0.6) | +4.6% (3.2) |
| `efdcb420c7`, with #45668 | triton, `--max-running-requests 11` | default | +6.1% (6.9) | +3.3% (2.7) |
| `efdcb420c7`, with #45668 | triton, `--max-running-requests 11` | `--enable-unified-memory` | +2.2% (4.5) | +1.8% (3.4) |

On unified fa4 mean TTFT also fell 8.3% and 7.1% and mean ITL 7.4% and 7.0%, with accept length unchanged (3.94 before, 3.95 after). The request cap is unchanged.

On triton (two runs per build and pool) the unified gain is positive in all four before/after pairs but inside the spread, so these runs cannot tell it from zero. At `--max-running-requests 11`, accept length shows no change beyond the spread: unified -2.6% (8.1) and +0.3% (2.1), default +0.4% (7.9) and +0.5% (3.5), so a small fall on the first load is not excluded. An earlier single-run comparison on `76d5b3ce02` with #45668 read +3.9% and +6.1% on the default pool and -1.3% and -1.9% on unified; these runs do not explain that difference.

To take run-to-run differences out, the first load also ran with `--enable-deterministic-inference --context-length 8192 --max-running-requests 11` and one fixed seed, two runs per build and pool. Every run did identical work: 205,228 tokens and 65,617 verify steps, with text, output ids, verify counts and accept histograms matching on all 100 requests across builds and pools. Throughput rose 3.12% on the default pool and 3.18% on unified, with repeats within 0.1%, and the decode step fell from about 67.3 ms to 65.1 ms on both. This shows the saving reaches both pools, not the gain to expect in normal serving: this mode runs a slower step (67 ms against 37 to 41 ms), uses a seeded draw instead of the graph's generator, and covers one load and one seed.

Memory: with rejection sampling at topk 1 and CUDA graphs on, per-step graphs now reserve the proposal buffer the combined graph already reserves, largest captured batch x draft steps x vocabulary size x 4 bytes per GPU. For Inkling-Small at 11 requests that is 71 MB, and free GPU memory after capture fell by 0.06 to 0.08 GB, with the same KV capacity and request cap. At a batch of 128 with this vocabulary it would be 823 MB per GPU (calculated, not measured).

Where this applies: on fa4 the default pool runs the combined draft graph, which already sampled in the graph, so it is unchanged. Unified fa4 gains here only because main falls back to per-step graphs there; #46386 moves it to the combined graph, so with that PR the fa4 row no longer adds, and this PR's lasting effect is on runs that keep per-step graphs, such as triton above. Upstream's JIT softmax for the sampler applies on SM100-class GPUs only, so it does not affect these SM90 numbers; the gain on SM100 was not measured.
