# [Scheduler] Keep a DP-converted decode batch as the running batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/43283) · state: closed · merged: True

## Original PR description

## Motivation

With DP attention, when a peer rank runs extend, `maybe_convert_decode_to_extend` converts this rank's decode batch to extend in place. `get_next_batch_to_run` then swapped the running batch for an empty placeholder, `ScheduleBatch(reqs=[], batch_is_full=...)`, so that on the next step the converted batch would come back through the last-batch extend merge instead of merging with itself. The swap has two effects:

- **Admission stays closed.** The converted batch keeps the `batch_is_full` it had before the step. When some of its rows finish, the shrink reset (`running_batch.batch_is_full = False`) goes to the placeholder, and the placeholder is then replaced by the converted batch with its stale `True`. While a peer rank keeps extending, this repeats every step, so this rank stops admitting until its running batch drains.
- **Load is under-reported.** During the converted step the running batch is the empty placeholder, so `/v1/loads` reports 0 running requests for the rank and DP load balancing sees it as idle.

## Modifications

- `Scheduler.get_next_batch_to_run`: a converted running batch stays the running batch; the placeholder swap is removed.
- In the next step's extend merge, a last batch that is the running batch itself is filtered in place (resetting `batch_is_full` on the running batch when rows finished) and not merged.
- `Scheduler.pause_generation`: when the running batch is the converted last batch, its requests are listed for retraction once, not twice.
- `test/registered/unit/managers/test_scheduler_dp_converted_batch_full.py` (CPU): over two steps, the converted batch stays the running batch, is not merged with itself, and admission sees `batch_is_full=False` after a row finishes.

Related: #35609 (open) resets `batch_is_full` at the start of every admission pass, which would also reopen admission here but not fix the load report.

Only the DP-converted path changes. `running_batch` and `last_batch` being the same object is the usual state after a decode step, and the readers of both (the invariant checker, in-flight request collection) already handle it; `pause_generation` is the one reader that needed the identity check above.

## Checks

- New unit test: fails on `main` (the running batch is the placeholder), passes with this change.
- `test_retract_after_dp_conversion_releases_each_req_once` in `test_scheduler_pause_generation.py`: a retract pause with the running batch as last batch requeues each request once.
- Stall workload, Qwen3-0.6B, `--tp 2 --dp 2 --enable-dp-attention --max-running-requests 8` (4 running requests per rank), H200. DP rank 1 extends on nearly every step (three client loops sending 6000-token prompts with `max_new_tokens=1`, `routed_dp_rank=1`); DP rank 0 serves 24 streaming requests (`routed_dp_rank=0`, `ignore_eos`, 40-600 output tokens drawn with a fixed seed). `/v1/loads` polled every ~50 ms:

| seed | DP0 makespan, main (s) | DP0 makespan, this PR (s) | DP0 mean TTFT, main (s) | DP0 mean TTFT, this PR (s) | polls reporting 0 running while DP0 had requests in flight, main (%) | same, this PR (%) |
|---|---|---|---|---|---|---|
| 0 | 50.2 | 35.0 | 20.8 | 13.0 | 44.7 | 0 |
| 1 | 53.1 | 36.2 | 19.2 | 10.9 | 33.0 | 0 |
| 2 | 40.8 | 32.6 | 15.8 | 9.4 | 52.8 | 0 |
| 3 | 56.4 | 27.8 | 25.6 | 11.9 | 38.3 | 0 |

  - DP rank 0 decode steps with a free running slot and a non-empty waiting queue: 96 of 143 on `main`, 0 of 63 with this PR.
  - With DP rank 1 idle, both builds finish the same DP rank 0 workload in 3.7-4.7 s, with no under-reported load.
- No regression, `--tp 2 --dp 2 --enable-dp-attention`: 400 few-shot GSM8K questions (parallel 128) give 42.7% on `main` and 42.5% with this PR; 600 concurrent `/generate` requests of mixed lengths all return the requested tokens on both; no traceback in any server log.
