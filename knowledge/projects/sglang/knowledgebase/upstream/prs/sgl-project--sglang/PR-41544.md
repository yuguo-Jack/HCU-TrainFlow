# Fix Baidu/Qianfan-OCR and stepfun-ai/GOT-OCR2_0

[Upstream PR](https://github.com/sgl-project/sglang/pull/41544) · state: open · merged: False

## Original PR description

## Motivation
Neither architecture existed in SGLang — these were missing-support failures.

`baidu/Qianfan-OCR` silently resolved to `TransformersForCausalLM` and died with `No module or parameter named 'model.mlp1'`. It turned out to be InternVL2.5 in disguise: the checkpoint uses InternVL weight names verbatim (vision_model.encoder.layers.N.attn.qkv, ls1/ls2, mlp1.*) with a Qwen3-4B backbone and the same <img>/<IMG_CONTEXT>/</img> tokens. So it subclasses InternVLChatModel + InternVLProcessor; only config spellings differ.

stepfun-ai/GOT-OCR2_0 had three separate bugs:

1. Its remote modeling_GOT.py imports verovio (a sheet-music renderer) lazily at line 605, but transformers' check_imports scans statically and rejects the file. Three AutoConfig sites trip on it.
2. _tokenizer_of in the shared base_processor.py did processor.tokenizer if hasattr(...) — tiktoken-backed QWenTokenizer stores its Encoding there, so the "tokenizer" was a non-callable Encoding. A genuine pre-existing bug for any tiktoken tokenizer.
3. The checkpoint kept its base model's eos_token_id: 151643 and never listed the chat terminator <|im_end|> (151645), so every request ran to max_new_tokens emitting <|im_end|>.

## Modifications

Modified files

1. configs/model_config.py — 2 lines, both additions to the multimodal_model_archs list so the two archs are recognized as multimodal:
- "QianfanOCRForConditionalGeneration"
- "GOTQwenForCausalLM"

2. multimodal/processors/base_processor.py — 8 lines. A real bug fix in shared code, not GOT-specific. _tokenizer_of did processor.tokenizer if hasattr(processor, "tokenizer"). Tiktoken-backed tokenizers (GOT's QWenTokenizer) store their Encoding object in .tokenizer, so the resolved "tokenizer" was a non-callable Encoding. Now it returns the processor as-is when it's already a PreTrainedTokenizerBase. This is behavior-identical for every model that worked before — real HF processors aren't PreTrainedTokenizerBase, and normal tokenizers have no .tokenizer attribute, so both previously landed on the same result.

3. utils/hf_transformers/config.py — 21 lines. A new _try_load_got_ocr2_config hook plus 2 lines wiring it in before AutoConfig. It matches on the raw config dict (model_type == "GOT") and returns early, so AutoConfig never resolves GOT's auto_map into the verovio-importing file. This follows the two hooks already sitting there (_try_load_longcat_config, _try_load_raw_mamba_config) and is a no-op for every other model.

New files

| File | Lines | What it does |
|---|---:|---|
| `models/qianfan_ocr.py` | 54 | `QianfanOCRForConditionalGeneration(InternVLChatModel)` plus config normalization: `text_config` → `llm_config`, tuple → integer `image_size`/`patch_size`, and defaults for dropout/`initializer_factor`. |
| `multimodal/processors/qianfan_ocr.py` | 17 | `QianfanOCRProcessor(InternVLProcessor)` normalizes the config, then reuses InternVL's dynamic tiling. |
| `configs/got_ocr2.py` | 45 | `GOTConfig(Qwen2Config)` with `model_type = "GOT"`; also adds `<\|im_end\|>` (`151645`) to `eos_token_id` for the stop-token fix. |
| `models/got_ocr2.py` | 148 | `GOTQwenForCausalLM`: reuses `deepseek_ocr.ImageEncoderViT` as the SAM tower, plus `mm_projector_vary` and `load_weights` name remapping. |
| `multimodal/processors/got_ocr2.py` | 112 | `GOTOCR2Processor`: reproduces GOT preprocessing (bicubic `1024×1024`, CLIP normalization) because the repository provides no Hugging Face image processor. |
