# [AMD][AITER attention backend] Adjust `available_bytes` in `KVCacheConfigurator` to avoid OOMs in AITER attention backend buffers allocation

[Upstream PR](https://github.com/sgl-project/sglang/pull/18263) · state: closed · merged: False

## Original PR description

Fixes https://github.com/sgl-project/sglang/issues/18262 and removes a longstanding hotfix that I think was used to bypass this issue:

https://github.com/sgl-project/sglang/blob/947a14d617f02b95fc1a04061810a73a2db962d1/python/sglang/srt/server_args.py#L4881-L4884

A fix for the same issue was attempted at https://github.com/sgl-project/sglang/pull/20890 but is IMO not correct.

## Motivation

By default, AITER attention backend needs memory depending on `max_total_num_tokens`:

https://github.com/sgl-project/sglang/blob/495ae9aaa609d39fd4e294d4f64faf52e29f50a6/python/sglang/srt/layers/attention/aiter_backend.py#L270-L277

and `max_total_num_tokens` itself does not take it into account, ending up defining too large `max_total_num_tokens` and too large KV cache, leaving not enough space for AITER attention backend buffer, resulting in OOM errors or in exceeding the `mem_fraction_static` static.

## Solution

See the comment:

```
        Solve for the KV byte budget that jointly accounts for the KV cache and
        the aiter attention workspace.

        We need to satisfy:
        - kv_budget + aiter_workspace_bytes = available_bytes
        - aiter_workspace_bytes = max_num_reqs * W
        - max_num_reqs = clamp(max_total_num_tokens * 512 / context_len, 2048, 4096),
        i.e. max_num_reqs ~= clamp(kv_budget * 512 / (context_len * cell_size), 2048, 4096)
        as max_total_num_tokens = kv_budget // cell_size.

        The `max_num_reqs` function is piecewise. We solve for each piece and pick
        the valid solution:
        - Case 1: kv_budget * 512 / (context_len * cell_size) <= 2048
        - Case 2: 2048 <= kv_budget * 512 / (context_len * cell_size) <= 4096
        - Case 3: kv_budget * 512 / (context_len * cell_size) >= 4096
```

## MLA case

Aiter attention backends also allocates buffers for MLA case, see:

https://github.com/sgl-project/sglang/blob/495ae9aaa609d39fd4e294d4f64faf52e29f50a6/python/sglang/srt/layers/attention/aiter_backend.py#L380-L401

https://github.com/sgl-project/sglang/blob/495ae9aaa609d39fd4e294d4f64faf52e29f50a6/python/sglang/srt/layers/attention/aiter_backend.py#L474-L489

These buffer sizes come from https://github.com/ROCm/aiter/blob/7c6a0ba5c9cf7b45b2fce42f3aa66a30ef627d7b/aiter/ops/attention.py#L1135 and are typically negligible <10 MB, meaning that the ~43 GB that the 0.85 factor was reserving on a 287 GB GPU was a clear over-reservation.

So removing the `mem_fraction_static *= 0.85` workaround is safe IMO.

The current logic correctly handles the dynamic calculation of `max_total_num_tokens` when `max_running_requests` is not set. However, when `max_running_requests` is specified, the code falls through to the `else` block, which does not account for the AITER workspace memory. This could still lead to Out-Of-Memory errors, which this pull request aims to fix.

To make this more robust, I suggest handling the fixed `max_running_requests` case explicitly for the `aiter` backend by calculating the workspace size and subtracting it from the available memory. This ensures memory is correctly provisioned in all scenarios for the `aiter` backend.

```python
        if (
            self.server_args.attention_backend == "aiter"
            and self.mambaish_config is None
        ):
            from sglang.srt.configs.model_config import AttentionArch
            if self.model_config.attention_arch == AttentionArch.MLA:
                # For MLA, workspace is allocated dynamically, not during init
                max_total_num_tokens = rest_memory_bytes // cell_size
            elif self.server_args.max_running_requests is None:
                # `max_total_num_tokens` is used in `ModelRunnerKVCacheMixin.init_memory_pool` to define
                # `max_num_reqs`, which is in turn used in AITER attention backend to define GPU HBM buffers for the attention.
                # The default strategy below to resolve `max_total_num_tokens` does NOT take into account the memory required for the attention backend, potentially resulting in OOM errors in AITER buffers allocation.
                max_total_num_tokens = self._solve_max_tokens_with_aiter_workspace(
                    rest_memory_bytes, cell_size, num_layers
                )
            else:
                # When max_running_requests is set, max_num_reqs is fixed.
                # We need to account for the AITER workspace memory.
                from sglang.srt.layers.attention.aiter_backend import AiterAttnBackend
                num_head = self.model_config.num_attention_heads // get_attention_tp_size()
                head_dim = self.model_config.head_dim
                max_context_len = self.model_config.context_len
                max_num_partitions = AiterAttnBackend.get_max_num_partitions(max_context_len)
                W = num_head * max_num_partitions * (head_dim * 4 + 8)
                max_num_reqs = self.server_args.max_running_requests
                aiter_workspace = max_num_reqs * W
                max_total_num_tokens = (rest_memory_bytes - aiter_workspace) // cell_size
        else:
            # No workspace overhead for other backends
            max_total_num_tokens = rest_memory_bytes // cell_size
```
