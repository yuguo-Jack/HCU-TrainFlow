# [AMD] Let the GLM DSA NextN draft declare its own shared-expert fusion architecture

[Upstream PR](https://github.com/sgl-project/sglang/pull/41258) · state: closed · merged: True

## Original PR description

## Motivation

`ModelConfig` rewrites a GLM-5 draft's architecture to `GlmMoeDsaForCausalLMNextN`. The fusion gate compares that name with `fused_shared_experts_architecture`, which the class inherited as `"DeepseekV3ForCausalLMNextN"`, so the draft was rejected even though it has the same 256 routed + 1 shared expert layout as the target model.

## Modifications

Declare `fused_shared_experts_architecture = "GlmMoeDsaForCausalLMNextN"` on the draft class.

Keep fusion disabled whenever `SGLANG_GLM_NEXTN_MOE_PTPC=1` casts the routed experts to per-channel FP8: the cast skips the shared expert, so its weight (BF16 or quantized) would land in the FP8 slot without a matching scale. On GLM-5.2-MXFP4's real layer-78 shared expert that zeroes 7-8% of the weights. GLM-5.3 checkpoints do not exclude MTP routed experts, so PTPC never applies there and the draft fuses.

Tests cover the architecture name, the loader-style gate call, the PTPC guard with the shared expert excluded or quantized, and both routed/shared checkpoint names.

## Accuracy Tests

Initial GLM-5.3 MXFP4 validation of the architecture override loaded the draft weights and measured MTP accept length 3.56 versus 3.58 on base, with GSM8K unchanged. The final PTPC guard intentionally leaves the unsupported BF16-shared configuration unfused; a real checkpoint load was not rerun after adding that guard.

Local verification:

```bash
python3 -m pytest -n 4 \
  test/registered/unit/models/test_glm_nextn_moe_ptpc.py

python3 -m pytest -n 4 \
  test/registered/unit/models/test_shared_experts_fusion_gates.py

pre-commit run --files \
  python/sglang/srt/models/glm4_moe.py \
  test/registered/unit/models/test_glm_nextn_moe_ptpc.py \
  test/registered/unit/models/test_shared_experts_fusion_gates.py
```

Result: 58 tests passed. Two broader-suite failures reproduce on current `main`: the ROCm EP gate expectation and a local Transformers/Pixtral import mismatch.

## Speed Tests and Profiling

Not isolated. Supported drafts now use the same fused shared-expert path as the target model; the PTPC + BF16-shared case remains unfused for correctness.

- BBuf · comment · 2026-09-30T16:16:11Z · [source](https://github.com/sgl-project/sglang/pull/41258#discussion_r4146792765)

File: `python/sglang/srt/models/glm4_moe.py` · line 1292

Could we handle `SGLANG_GLM_NEXTN_MOE_PTPC=1` before enabling fusion for this draft? For a Quark checkpoint whose MTP routed/shared experts are excluded (BF16), the inherited gate now permits fusion, and `_resolve_nextn_quant_config` selects PTPC-FP8 for `model.decoder.mlp.experts`. However, `_maybe_quant_glm_nextn_moe_to_ptpc` only matches `mlp.experts.<id>.*`: `mlp.shared_experts.*` passes through as BF16 without weight scales. The inherited loader subsequently renames it to expert 256 and copies it into FP8 storage, leaving that slot's scales at their initial value of 1.

I reproduced this on CPU using the actual Quark gate, GLM weight iterator, Quark FP8 weight allocation and `_load_w13` helper, with the device capability mocked to gfx95: the old architecture returns "Config does not support...", the new one returns `None`; the routed weight gets FP8 + a scale, while the shared weight stays BF16 with no scale. Shared weights of `1e-4` then become zero when loaded into the fused slot.

Please either keep fusion disabled for this PTPC path or apply the same per-channel conversion and scale emission to the shared expert, with a regression covering both the routed and shared checkpoint names.
