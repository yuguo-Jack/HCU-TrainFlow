# [Fix] multimodal: Cap local media reads at the size limit

[Upstream PR](https://github.com/sgl-project/sglang/pull/44153) · state: open · merged: False

## Original PR description

## Motivation

`download_remote_media` stops a client-supplied HTTP(S) image, audio, or video at `media_url_max_file_size_mb` (default 64 MiB). Set the flag to 0 to disable the limit. Local `file://` URLs and absolute paths did not use that cap. `load_image("file:///dev/zero")`, or a multi-gigabyte local file, is read until EOF. That blocks an IO worker and grows process memory. A file that is not an image is not returned to the caller. The default server bind is `127.0.0.1`.

Remote downloads already have this limit from #34892. #42626 also edits `get_image_bytes`, for a different bug: a bare base64 JPEG starts with `/9j/` and was opened as a path. This pull request does not decode those strings.

## Modifications

- Stat a local media path before opening it. Reject a path that is not a regular file, so a device node or a FIFO is not read.
- Reject a regular file larger than the configured byte cap. A cap of 0 still means unlimited, matching remote downloads.
- Use that check for image bytes, audio files, and video paths in `common.py`, and for the Inkling, MiMo, and Moss readers that open the same client paths.
- Leave `file://` unstripped inside `get_image_bytes`. Callers that accept a file URL strip the scheme first. The Rust loader strips it on its own.
- State in the `media_url_max_file_size_mb` help text that the limit covers local files as well as remote downloads.

## Tests

`python test/registered/unit/multimodal/test_media_url_security.py`

- A regular file one byte over a 1 MiB cap raises `ValueError` from `get_image_bytes`, `load_image`, `load_audio`, `_normalize_video_input`, and `get_video_bytes`. On the old code, `get_image_bytes` returned the bytes.
- `file:///dev/zero` raises `ValueError` before a read that would not reach EOF.
- A small local file is still read, including when the cap is 0.
