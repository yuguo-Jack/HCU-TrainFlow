## Motivation

<!-- Describe the purpose and goals of this pull request. -->


<img width="2383" height="644" alt="draft_prefetch" src="https://github.com/user-attachments/assets/7af33005-6795-42e4-bd2e-e9f39a1245be" />

In the current Eagle3 implementation, within a single `run_batch`, Decode executes in the order **Draft -> Verify -> DraftExtend**. As shown in the upper part of the figure, before the next `run_batch` can start, there is always a long **H<->D** wait that must complete. With Draft placed at the very beginning of `run_batch`, this waiting period cannot be well hidden, resulting in a Draft-and-Verify CPU dispatch bound.

By reordering the Decode execution to **Verify -> DraftExtend -> Draft(Prefetch)**, better hiding can be achieved and the CPU bound eliminated. **The prerequisite is that the draft model itself does not trigger additional H<->D transfers.** For example, in `EAGLEDraftNpuGraphRunner._replay_graph`, DSA models do not need to read `seq_lens_cpu`, achieving the effect shown in the lower part of the figure. Non-DSA models, however, still need to read the updated (post-DraftExtend) `seq_lens_cpu`; otherwise, operator OOB issues or reduced acceptance rates would occur, and adding a synchronization inside Draft to work around this would completely negate the expected gains or even degrade performance further.


## Modifications

<!-- Detail the changes made in this pull request. -->

**Core feature: DraftPrefetch -- moves Draft to right after the previous round's DraftExtend for better hiding.**

1. Draft is moved (copied) to execute after DraftExtend and renamed DraftPrefetch. Inside the method, a new batch is prepared with the updated `spec_info` and `seq_lens`, and its ForwardMode is set to `Decode`, then the entire original Draft logic runs once. The final outputs are the `topk_index` and `topk_p` derived from `draft_tokens`, which are assigned to `next_draft_input` and carried into the next `run_batch`. In the actual implementation, I reuse the existing batch by assigning attributes to it for the computation and restoring the original attributes afterwards.
2. Ahead of the Verify phase in a `run_batch`, PrepareVerifyInput now takes the place of Draft. It re-packs the inputs that were originally fed into Draft.
3. To bridge the Prefill and Decode stages (including the PD disaggregation scenario), PrepareVerifyInput must also be able to consume the `topk_index` and `topk_p` produced by Prefill. Therefore, Prefill's `topk_index` and `topk_p` are padded to satisfy the shape requirements.
4. To realize the performance gains, I added `pin_memory=True` at the H<->D trigger points during DraftPrefetch execution (`ForwardBatch.init_new`), or moved the operations onto the CPU (`EAGLEDraftNpuGraphRunner.can_run_graph`), so that the CPU operator dispatch remains fully asynchronous throughout the Verify -> DraftExtend -> DraftPrefetch process.
5. Added thorough argument validation for this feature. It is currently incompatible with speculative_adaptive, speculative_eagle_topk>1, speculative_num_steps<=1, multi_layer_eagle, and speculative_use_rejection_sampling; all of these combinations are rejected at startup.
6. Added test cases.

While adding `pin_memory=True` to `ForwardBatch.init_new`, I found that the NPU platform does not yet implement `NpuSRTPlatform`, causing `is_pin_memory_available` to return the default value False set in `DeviceMixin`. Therefore, I filed a separate PR #36472 to implement `NpuSRTPlatform`. This PR builds on top of PR #36472 and requires it to be merged first.

Thanks for the thorough profiling — a few observations:

**1. On the bubble:** The primary goal of this feature is to eliminate the CPU dispatch bottleneck between `draft_extend` and `draft`, and your trace confirms that's working. On NPU I've seen the remaining draft↔verify gap fully hidden by increasing the draft count, though on high-performance GPUs the gain may be less pronounced since the gap is narrower to begin with.

**2. On acceptance rate:** You mentioned acceptance rate is unchanged, which is a bit surprising. This feature intentionally skips (or defers) the `seq_lens_cpu` sync to avoid putting a CPU round-trip back into the critical path between `draft_extend` and `draft`. For non-DSA models that still rely on `seq_lens_cpu`, I'd expect some acceptance rate impact. Are the numbers truly identical with the flag on vs. off? This feature is a natural fit for DSA models like DeepSeek-V3.2, whose MTP doesn't depend on `seq_lens_cpu` at all.

**3. On flat TPS:** Looking at your trace, the draft GPU time is ~1.3 ms, and the restore-before-verify step introduces ~1.2 ms of CPU-bound work — consistent with your conclusion. On H20 with a pruned DeepSeek-V3.2, I measured a reduction in total time from `draft_extend` to the next `target` with the flag on. If that window is unchanged in your setup, then indeed there's no net gain.

**Summary:**
- The feature eliminates the `draft_extend`↔`draft` bubble, but the restore-before-verify step adds CPU overhead that can become the new bottleneck. 
- Increasing the draft count can mask the remaining gap, but if draft quality is low this may backfire — needs case-by-case evaluation.
- It's best suited for DSA models; other models may see acceptance rate degradation from the deferred `seq_lens_cpu` sync.
- I'll look into optimizing the restore-before-verify step on my side.

The string comparison `str(device) == "cuda"` (and similarly for `"npu"`) will fail if the device string includes an index, such as `"cuda:0"`. This is a common format for device strings in SGLang. This will cause the function to return `False` incorrectly, disabling pinned memory optimizations for indexed devices.

```suggestion
    device_type = str(device).split(":")[0]
    if device_type == "cuda":
        return _is_cuda
    if device_type == "npu":
        return _is_npu
```
