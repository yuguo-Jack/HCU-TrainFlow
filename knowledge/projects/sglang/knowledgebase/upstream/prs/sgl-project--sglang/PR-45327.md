# [Feat] constrained: Drop structural tag patterns XGrammar cannot compile (opt-in)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45327) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45224.

With strict tool calling (`SGLANG_TOOL_STRICT_LEVEL=2`, or `strict: true` on a tool), every tool schema is compiled into one XGrammar structural tag. If XGrammar can't compile one `pattern`, the whole request fails with HTTP 400, and the other tools can't be used either. In the issue, one tool out of 177 broke every request from that client.

What the pinned `xgrammar==0.2.7` does with a `pattern`, by schema style:

| `pattern` construct | `json` style (most parsers, legacy tags) | `qwen_xml` style (`qwen3_coder`), top-level parameter |
|---|---|---|
| lookahead `(?!...)` | lookahead ignored, rest enforced | **fails** |
| named group `(?P<x>...)` | compiles | **fails** |
| lookbehind, backreference, `\b`, `\p{L}` | **fails** | **fails** |

Some styles are stricter still: `minimax_m3_xml` rejects every `pattern`. XML styles (`qwen_xml`, `kimi_k3_xml`, `deepseek_xml`) compile values nested below a top-level parameter in JSON style, so a nested lookahead compiles there.

## Modifications

Opt-in and off by default. With the flag off, compile results are the same as `main`.

- **`SGLANG_ENABLE_STRUCTURAL_TAG_PATTERN_RELAXATION`** (`EnvBool(False)`), in the tool-calling section of `environ.py`, read once in `XGrammarGrammarBackend.__init__`, and documented in `environment_variables.mdx`.
- **`XGrammarGrammarBackend.dispatch_structural_tag`**: if the compile fails and the flag is on:
  1. Find each schema in the tag: `structures[i].schema` for legacy tags, and every `json_schema` / `qwen_xml_parameter` format node for native tags. The walk is generic, so schemas nested under `optional`, `repeat`, `dispatch`, `token_triggered_tags` and future containers are found too.
  2. Check each schema alone, in its own format and style, with `Grammar.from_structural_tag`. This builds no token masks, so it's cheap.
  3. In a schema that fails, remove all its `pattern`s and check it again. If it still fails, the problem isn't a pattern, so stop and return the original error without recompiling. Otherwise add the patterns back one at a time, where they sit, and drop only the ones that make the schema fail. Checking in place keeps nested patterns that compile in JSON style under an XML-style tag. `$defs`, `items`, `anyOf`, `propertyNames` and so on are covered by `iter_subschemas`. A schema with more than 64 patterns isn't checked and keeps its error (see the cost note below).
  4. Recompile once, and log one warning naming each tool's tag `begin` and a JSON pointer, e.g. `'<tool_call>\n<function=ls>\n': dropped pattern at #/properties/path`.
  5. If nothing was dropped, or the recompile still fails, return the original error as before. **Other schema errors are never relaxed**: an unresolved `$ref` or `minLength > maxLength` still returns 400.
- The compile code moves, unchanged, into `_compile_structural_tag` so it can be called twice. Matcher error messages for a relaxed grammar show the enforced schema.
- `_iter_subschemas` in `json_schema_validation.py` is renamed to `iter_subschemas`, since the XGrammar backend now uses it too.

### Points for review

- **The flag covers every structural tag.** The backend only sees the tag's JSON, so it can't tell tool-call tags from a user-supplied `response_format: structural_tag`. The env comment and the docs both say so.
- **Dropped patterns are not enforced.** A `strict` tool whose pattern was dropped may get arguments that don't match its schema (in the e2e run below, `ls.path` produced `/Notes`). The docs tell callers to validate arguments themselves. The server log names every dropped pattern.
- **Cost on user-supplied tags.** Checking one schema's patterns is quadratic in their number: 2,000 patterns took about 90 s on a laptop CPU (for scale, a valid 2,000-pattern schema takes about 74 s to compile with a 150k-token vocab). A grammar timeout can't stop a compile thread once it runs, so a cap of 64 patterns per schema bounds the check to about 0.1 s; a larger schema keeps its 400.
- **Should this be on by default?** I kept it off. `dispatch_json` already rejects keywords XGrammar silently ignores, but the structural-tag path never ran that check, so json-style tags already lose lookaheads without a warning. Happy to flip the default if maintainers prefer.
- **Why a boolean flag?** The issue suggested a policy (fail / relax / drop the tool). Only relaxing is implemented. If a drop-the-tool policy lands later, this can become an `IntEnum` policy like `ToolStrictLevel`, with this name kept as an alias.
- **Why the isolation checks don't use the tokenizer:** a compile with the tokenizer builds token masks, which is slow, and `GrammarManager` caches "timed out" for a tool set that exceeds its timeout. The real compiler runs at most twice in total, and only once when the failure isn't a pattern; the tests assert the second case.

### Out of scope

- `llguidance` / `outlines` `dispatch_structural_tag`.
- A "drop the tool entirely" policy, which would also need parser changes.
- A metric for dropped patterns. The grammar counters in `metrics_collector.py` are defined but not yet fed from `GrammarStats`, so this needs that wiring first.

## Accuracy Tests

N/A: no model math changes. With the flag off, behavior is unchanged. With it on, only patterns XGrammar can't compile are dropped (see the e2e results below).

## Speed Tests and Profiling

The relaxation runs only on the failure path, once per tool set (the result is cached under the original key). On a synthetic set of 177 tools (5 patterned string fields each, 5 tools with a lookahead) under the `qwen_3_coder` tag, `_drop_uncompilable_patterns` took a median of about **20 ms** on a laptop CPU. The issue measured about 18 s for the cold compile.

Also checked without a tokenizer, across 13 of xgrammar's built-in model tags × `tool_choice` `required`/`auto` (26 combinations), with a backreference tool, a lookahead tool and a plain tool: all 26 compile or recover. pre-commit passes.

**Review points**

1. `patternProperties` keys are not relaxed. A key with a lookahead still gives a 400 error. This is fine as scope for this PR, but a note in the docs would help.
2. Patterns under `not`, `if`, and `contains` are walked and dropped, when the schema fails to compile for another reason. In JSON Schema, removing a constraint under `not` makes the schema tighter, not looser. I think this is harmless today, because xgrammar does not enforce these keywords (a lookahead pattern under `not` compiles alone). You could skip these keywords, or add a comment about it.
