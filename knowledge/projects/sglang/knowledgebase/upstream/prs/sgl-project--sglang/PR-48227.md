# [Feat] model-loader: cap the bytes the multithreaded loader keeps in flight

[Upstream PR](https://github.com/sgl-project/sglang/pull/48227) · state: open · merged: False

## Original PR description

## Motivation

`buffered_multi_thread_safetensors_weights_iterator` bounds its sliding window by a shard **count**: `num_threads + 1` shards are in flight, so peak host RAM is about `(num_threads + 2) x shard size`. The count is the only knob, so a host with limited RAM has no direct way to bound it when shards are large or uneven, for example a checkpoint with one 50 GB shard next to 7 GB ones. With `--weight-loader-disable-mmap`, every in-flight shard is held in memory as bytes and then as tensors, so loads on RAM-limited hosts can be OOM-killed partway through.

## Modifications

- `model_loader/weight_utils.py`: `buffered_multi_thread_safetensors_weights_iterator` takes `max_inflight_bytes`. A shard is submitted only while the summed file size of the shards in the window stays within the cap. One shard is always admitted, so a shard larger than the cap still loads. `None` (the default) keeps today's count-only window.
- `model_loader/loader.py`: new `--model-loader-extra-config` key `max_inflight_bytes` (positive int), validated with the other default-loader keys and passed to the multithreaded safetensors iterator. Only `--load-format auto` and `safetensors` accept it. Formats whose loaders would ignore it (`fastsafetensors`, `pt`, ...) now reject it as an unexpected key. Under `auto` with `.bin` weights, it logs a warning that the key is ignored.
- `docs/advanced_features/model_loading.mdx`: row for the new key.
- Tests (`test/registered/unit/model_loader/test_prefetch_checkpoints.py`):
  - the window is 4 shards with no cap, 2 at a two-shard cap and 1 at a 1-byte cap, and the tensors are equal to the single-threaded loader's in every case;
  - invalid values (`0`, `-1`, `1.5`, `"1"`, `True`) are rejected;
  - the key is rejected for `fastsafetensors` and `pt`.

The tensors yielded and their order are unchanged; only when the next shard is submitted changes.

## Accuracy Tests

No model-output change: the loader yields the same tensors, and the unit test checks `torch.equal` against the single-threaded loader for every cap. In the host-RAM benchmarks below, every arm yields the same tensors (digest over names, shapes and sampled bytes identical across all arms, real and synthetic).

## Speed Tests and Profiling

Peak host RSS (`VmHWM`) of `buffered_multi_thread_safetensors_weights_iterator` with the default `num_threads=8`, in a CPU-only container on an x86_64 host (image `lmsysorg/sglang:nightly-dev-20261103-797af717`). Each arm ran 3 times in a fresh process; the table shows the median, with the range in parentheses. Every arm yields the same tensors (identical digests).

**Real checkpoint**: the ten main shards of `nvidia/Qwen3.8-Flash-Next-NVFP4` (78.9 GB of tensors, mostly 10.0 GB shards), container memory limit 60 GB:

| Tree | Mode | `max_inflight_bytes` | Peak RSS | Wall |
|---|---|---|---|---|
| main `8d4e1ce4c7` | `--weight-loader-disable-mmap` | – | **OOM-killed** at the 60 GB limit (exit 137, 1 run) | – |
| this PR | `--weight-loader-disable-mmap` | – | **OOM-killed** (exit 137, 2 runs) | – |
| this PR | `--weight-loader-disable-mmap` | 16 GiB (window: 1 shard) | **33.5 GiB** (33.3–33.6) | 93.2 s (92.4–94.4) |
| main | mmap (default) | – | 10.25 GiB (9.83–10.30) | 12.4 s (11.9–33.4) |
| this PR | mmap (default) | – | 9.87 GiB (9.77–10.08) | 19.2 s (11.3–28.4) |
| this PR | mmap (default) | 16 GiB | 3.83 GiB (3.52–3.86) | 6.2 s (6.2–6.4) |

Mmap wall times depend on how much of the checkpoint was already in the page cache (the first arm of each container read it from disk), so they are not comparable across rows.

**Synthetic**: 12 shards of 536,871,008 bytes, `--weight-loader-disable-mmap` path:

| Tree | `max_inflight_bytes` | Shards in flight | Peak RSS | Wall |
|---|---|---|---|---|
| main | – | 9 | 7.06 GiB (6.60–8.06) | 7.69 s (7.52–8.05) |
| this PR | – | 9 | 7.06 GiB (7.06–7.60) | 7.88 s (7.27–8.05) |
| this PR | 2 GiB | 3 | 4.06 GiB (4.06–4.06) | 7.75 s (7.14–7.99) |
| this PR | 1 GiB | 1 | 3.06 GiB (3.06–3.06) | 8.92 s (8.47–9.59) |

The peak is the in-flight window plus the shard being consumed, which the cap does not count (e.g. 1 GiB cap: one 0.5 GiB shard loading and one being yielded, as bytes and tensors). With the cap unset, peak and time match main within run-to-run spread. A cap trades load time for host RAM: fewer shards load in parallel, so small caps are slower (1 GiB: 8.92 s vs 7.69 s on main here). Pick the largest cap the host can afford.

**Load-time cost on a full server load**: `Qwen/Qwen3-30B-A3B` (16 shards of about 4 GB) on 1x H100, `python -m sglang.launch_server --weight-loader-disable-mmap --disable-cuda-graph --model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 8[, "max_inflight_bytes": N]}'`, page cache warm, 3 rounds; load time from the "Load weight end" log line, median with the range in parentheses:

| Tree | `max_inflight_bytes` | Peak host RSS | Load time |
|---|---|---|---|
| main | – | 61.26 GiB | 27.80 s (27.33–29.31) |
| this PR | – | 61.26 GiB (61.26–61.65) | 27.70 s (26.91–28.88) |
| this PR | 2 GiB | 9.13 GiB (9.12–9.13) | 32.50 s (32.16–33.53), **+17%** |
| this PR | 1 GiB | 9.13 GiB | 34.66 s (33.14–38.39), **+25%** |

Both caps are below one shard, so a single shard is in flight with either; host RAM drops 6.7x for 17–25% more load time here.
