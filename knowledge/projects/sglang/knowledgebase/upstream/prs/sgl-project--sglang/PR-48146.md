# [Perf] [AMD] dsv41: Run the HIP sparse prefill on the FP8 KV cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/48146) · state: open · merged: False

## Original PR description

## Motivation

On gfx950, DeepSeek-V4.1 prefill attention in the HIP backend (`DeepseekV4HipRadixBackend`, with `SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL=1`) dequantizes the selected FP8 KV cache rows to BF16 with `dequantize_k_cache_paged_dsv4` and then calls AITER's BF16 kernel `pa_sparse_prefill_opus`. AITER also has an FP8 entry, `pa_sparse_prefill_fp8_opus`, with a 16-head tile that fits TP4 (16 query heads per rank). An earlier kernel test showed 1.41x for the FP8 attention kernel, but its inputs made the BF16 kernel slow. With realistic inputs the FP8 path is only 0.98-1.05x per layer (see the update in the comments). The FP8 kernel already runs for the two-pool FP8 `unified_kv` layout (`prefill_fp8_2buff`, layout added in #37413), but that layout is not wired for decoder SWA bounded replay, and the default paged V4 layout has no FP8 prefill path.

This is a draft opened before the code, so the plan can be discussed first.

## Modifications

Planned (no code in this draft yet):

- A new switch, off by default, for gfx950: `_forward_prefill_opus` packs the selected FP8 rows into the layout the FP8 kernel reads (the FP8 NoPE bytes with their E8M0 scales, and the RoPE part in BF16) instead of dequantizing them, and calls `pa_sparse_prefill_fp8_opus`.
- The query's NoPE part is quantized to the same packed MXFP8 form, fused into an existing query kernel where possible, as the `unified_kv` path does, so no separate pass runs over the query.
- The BF16 path stays the default; decode and verify are unchanged.

## Accuracy Tests

Not run yet. Plan: the packed rows bitwise equal to the cache bytes, the attention output within tolerance of the BF16 path, then GSM8K, GPQA and long-context NIAH with the same server config, with and without the switch.

## Speed Tests and Profiling

Not run yet. Plan: per-layer time of pack + query quantization + FP8 attention against dequant + BF16 attention at the shape above, then a long-prompt serving benchmark (TTFT and output throughput) at TP4 on MI355X, with and without speculative decoding.

- amd-pedghazi · comment · 2026-11-04T06:48:46Z · [source](https://github.com/sgl-project/sglang/pull/48146#issuecomment-6624570002)

An update on the speedup in the description. The 1.41x for the FP8 attention kernel came from a test harness that picks the extend rows in blocks every 127 rows instead of the sliding window, which alone makes the BF16 kernel 19% slower. With realistic inputs on our serving build (ROCm 7.2.4, AITER 285579b6), at q [16384, 16, 512], top-k 512 + 128 and 92,160 cache rows (a ratio-1 layer), the FP8 attention kernel is 1.13x faster than BF16 (1,056 against 1,188 us). With the K repack and the query pack included, the per-layer speedup is 1.05x on ratio-1 layers, while ratio-2 and ratio-0 layers get slower (0.98x and 0.77x). A newer AITER (46729caf) leaves the V4 FP8 kernel unchanged; its new 16-head V4.1 tile reaches 1.08-1.16x per layer and needs the RoPE dims in FP8 too.

The reason is that the FP8 kernels still dequantize K inside the kernel and run PV in BF16, so only QK and the K load shrink. That is not enough to make the serving path worth building, so I'm keeping this as a held draft until a faster kernel exists, for example one that reads the V4 cache record directly.
