## DSPARK vs base (non-spec) speedup

**Setup:** Qwen3-14B target, `dspark_qwen3_14b_block7` draft, Intel Arc Pro B60, tp2, bfloat16,  `max_running_requests 2`, prefill graph disabled, decode graph default (off on XPU). Workload: input-len 1024, output-len 256, temperature 0.

### triton attention

| bs | e2e base (tok/s) | e2e dspark (tok/s) | e2e speedup | dec speedup | acc len | dec eff |
|:--:|:----------------:|:------------------:|:-----------:|:-----------:|:-------:|:-------:|
| 1  | 121.8            | 394.6              | 3.24x       | 3.94x       | 7.62    | 0.52    |
| 2  | 202.4            | 505.0              | 2.50x       | 3.04x       | 7.39    | 0.41    |

### intel_xpu attention

| bs | e2e base (tok/s) | e2e dspark (tok/s) | e2e speedup | dec speedup | acc len | dec eff |
|:--:|:----------------:|:------------------:|:-----------:|:-----------:|:-------:|:-------:|
| 1  | 109.4            | 395.8              | 3.62x       | 4.29x       | 7.62    | 0.56    |
| 2  | 197.6            | 655.2              | 3.32x       | 4.36x       | 7.23    | 0.60    |

**Best config:** intel_xpu, bs=1 → **3.62x end-to-end / 4.29x decode-only**. intel_xpu beats triton at every batch size.

> Synthetic `input-len` tokens over-accept (acc len ~7.6 of 8); real prompts (MMLU) accept ~3.65, so real-traffic e2e speedup is ~1.8–2.2x.
> `e2e` = overall throughput (prefill+decode); `dec` = output throughput (decode only); `dec eff` = dec speedup / acc len.

One suggestion on enabling DSpark Triton kernels on XPU:
inputs_on_cuda() in kernels/ops/speculative/dspark/dispatch.py returns value.is_cuda, so the DSpark Triton kernels (accept, verify window, attention metadata, schedule, draft model) quietly fall back to the PyTorch path on XPU. Since Triton already runs on XPU here (e.g. fused_kv_norm_rope_write), would it make sense to use something like value.device.type not in ("cpu", "npu"), along with the similar .is_cuda checks in the DSpark files? That should cut kernel launches and full-vocab intermediate tensors on every verify step, which likely matters on XPU since decode there is launch-bound.

- mingfeima · comment · 2026-10-08T07:51:58Z · [source](https://github.com/sgl-project/sglang/pull/33739#discussion_r4216399331)

File: `python/sglang/test/kits/basic_decode_correctness_kit.py` · line None

i suppose that the one-shot example can help other devices. stop=["\n"] does not.

`test_basic_math` lives on BasicDecodeCorrectnessMixin. CUDA DSpark, EAGLE, DFlash, DSV4, and NPU Eagle all mix this class in. Those tests already pass without stop, and the assertion only checks that "391" is in the output.

The one-shot (12×12 → 144) is a prompt change. It is device-independent, and it does help a reasoning model ramble less on CUDA too.

stop=["\n"] cuts the generation at the first newline. If CUDA already emits 391 directly, the stop does nothing. If the model emits a newline before 391, the stop drops the answer and a passing test fails. This mixin is a short decode probe for garbage output and KV corruption; truncating it means later tokens are no longer checked.

XPU cannot pass without this change? do we need to double check if this is a true bug?
