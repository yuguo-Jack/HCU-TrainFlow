## Motivation

**Evidence correction, 2026-10-25 (documentation only; no new experiments):** performance cohorts and validation revisions are separated below. Earlier allocator-overlap negative evidence is withdrawn. The observations do not establish a general speedup, a universal registration-disable penalty, or an allocation-removal mechanism.

On a two-node GB300 MNNVL deployment (4 GPUs/node, TP8/DCP8) serving Kimi-K3, DCP `a2a` can produce corrupted decode output with CUDA graphs enabled. In a 12-prompt real-prefill/decode smoke probe, the original setup produced **12/12 degenerate outputs**; restarting with `NCCL_GRAPH_REGISTER=0` reduced this to **0/12**.

SGLang already applies `_disable_nccl_graph_buffer_registration()` to the TP LM-head all-to-all path. DCP `a2a` did not apply the same startup safeguard.

The controlled correctness experiments support an interaction between NCCL graph registration and temporary DCP `a2a` exchange-buffer lifetime in this deployment; the exact low-level mechanism remains unproven. This PR keeps the minimal observed-safe startup policy: disable graph buffer registration by default for resolved DCP `a2a`.

Fixes #45367.

## Modifications

- After DCP backend resolution/validation, reuse `_disable_nccl_graph_buffer_registration()` when the resolved backend is `a2a`.
- Add four focused policy tests for the default guard, explicit env overrides, non-`a2a` backends, and invalid `a2a` configuration.

The existing helper uses `setdefault`, so explicit `NCCL_GRAPH_REGISTER=0/1` settings are preserved. This PR does not change `NCCL_GRAPH_MIXING_SUPPORT` or the DCP collective implementation.

### Earlier registration anchor and TP-path comparison — independent records

The separate same-settings `fi_a2a` anchor measured 1643.7 tok/s with the original registration environment versus 1641.3 tok/s with registration disabled (-0.15%). The observed values were close; this single pair does not quantify noise or bound the cost for other paths.

### Alternative fix and profiling scope

The additional C256 persistent-buffer-plus-guard capture had approximately the same summed kernel time (~62.2 ms per normalized iteration/GPU) and BMM medians as guarded a2a, while the local persistent/no-guard capture had lower timings (~39.8 ms). These historical captures do not establish a safe persistent-buffer alternative: the R3 failure now blocks that interpretation. They establish neither valid acceleration nor a universal guard penalty. This is not a complete 2×2 performance ablation: the comparable no-persistence/no-guard capture is missing, effective per-worker registration settings are not established by source markers alone, and device-side expert workload/runtime-state differences remain unexcluded. About 98% of the earlier difference in summed kernel duration was classified as MoE BMM, not DCP exchange; summed durations are not additive wall-clock latency, critical-path cost, or GPU utilization. The extra arm adds profiling only, not another end-to-end throughput or accuracy result.
