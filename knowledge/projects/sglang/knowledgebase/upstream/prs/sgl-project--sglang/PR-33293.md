# perf: fuse GraniteMoe scaled residual RMSNorm

[Upstream PR](https://github.com/sgl-project/sglang/pull/33293) · state: closed · merged: False

## Original PR description

## Motivation

GraniteMoe applies its residual multiplier before both residual additions in every decoder layer:

```text
hidden_states * 0.22 -> residual add -> RMSNorm
```

For `ibm-granite/granite-3.1-3b-a800m-instruct`, the decode FX graph contained 64 of these sequences per token. Nsight Systems confirmed that they produced 64 scalar-multiply launches, 64 residual-add launches, and 64 of the model's 65 RMSNorm launches per token.

This PR fuses each sequence into one JIT kernel and defers MoE residual additions into the next layer or final normalization.

## Modifications

- Extend the existing JIT fused-add RMSNorm kernel with a compile-time scaled-input specialization.
  - Preserve the existing unscaled specialization.
  - Round the scaled input and residual sum to the activation dtype at the same boundaries as the unfused path before FP32 variance accumulation.
- Register `fused_scaled_add_rmsnorm` as an opaque custom op that mutates both input and residual, keeping the fusion visible under fullgraph capture.
- Rework `GraniteMoeDecoderLayer`/`GraniteMoeModel` residual flow:
  - 32 post-attention fused norms.
  - 31 next-layer input fused norms.
  - 1 final fused norm.
  - 1 ordinary first-layer input RMSNorm.
- Guard the fast path by device, layout, dtype, RMSNorm semantics, hidden size, batch-invariant mode, and storage overlap.
  - Unsupported cases retain the original scale -> add -> platform RMSNorm order.
  - A runtime overlap check protects the CUDA kernel's `__restrict__` contract for direct or compiled custom-op calls.
- Add scaled-kernel correctness/fullgraph/alias tests, Granite residual-topology and CUDA integration tests, and a registered benchmark.

## Threats to Validity

- Measurements use one H200 GPU UUID and one Torch/CUDA environment; no cross-hardware speedup is claimed.
- The final eager and combined-mode comparisons use five warmed independent processes per condition. The older CUDA-graph-only result uses three repeats and is supporting evidence only.
- GraniteMoe uses the same untuned default Triton MoE configuration in both conditions.
- Kernel microbenchmarks isolate the target chain and do not replace end-to-end measurements.
- In combined mode, Inductor already fuses the baseline scale/add/RMSNorm chain. The opaque custom-op candidate regresses at BS1/4 and wins only from BS8 onward; the table below reports the crossover without excluding samples.
- BF16 reduction-order differences mean long greedy continuations are not guaranteed to be token-identical, so the full task-level GSM8K comparison is the accuracy criterion.
- The initial online concurrency sweep used five sequential processes per condition. C16 and C64 median-TTFT process CV exceeded 5%, so no directional TTFT claim is made for those rows.
- C32/C128 were repeated as five fixed-seed A/B pairs with alternating launch order, exact-shape unique-prompt priming, and the supported `/freeze_gc` endpoint before the measured cache flush. Throughput and median-TTFT process CVs are below 5%; tail CVs remain above 5% and are not presented as stable gains.
- `/freeze_gc` moves warmed long-lived objects to Python's permanent generation; it does not disable collection of objects created later. C128 recorded four 14-28 ms post-freeze warnings per run in both conditions.
- `--random-range-ratio 0` samples lengths from 1 through the requested maximum. A preliminary serving pass using that setting was rejected before analysis; the valid fixed 128/128 runs use `--random-range-ratio 1.0`. No valid sample was excluded.
- Raw profiler artifacts are retained outside the PR.

### FX / Nsight Systems / Nsight Compute

- FX:
  - Baseline: 64 explicit residual-scale nodes.
  - Candidate: exactly 64 `torch.ops.sglang.fused_scaled_add_rmsnorm` calls and zero explicit residual-scale nodes.
- Nsight Systems, normalized per decode token:
  - Baseline: 64 scale + 64 add + 65 RMSNorm launches.
  - Candidate: 64 scaled fused launches + 1 ordinary RMSNorm; no residual-add kernels.
  - Net: **128 fewer launches per token**.
- Nsight Compute:
  - Baseline M=1 separate chain: 2.464 us multiply + 2.528 us add + 3.392 us RMSNorm = 8.384 us.
  - Candidate fused kernel: 2.688 us at M=1, 2.880 us at M=16, 3.136 us at M=128, and 12.608 us at M=4096.
  - M=4096: 81% active warps and 43% DRAM throughput.
- In the original steady-decode trace, the remaining 270-425 us gaps are FlashInfer metadata/index-selection dispatch gaps outside this fusion.

Reviewed the correctness side closely and re-derived the residual topology independently. Summary: the arithmetic is sound and the reporting is unusually honest. One design question I'd want answered before this lands, plus two minor items.

## Verified

**The deferred residual topology is exactly equivalent.** I reimplemented both the original and the reworked form and ran them against each other — **max abs diff 0.0**. The bookkeeping holds: layer 0 takes the `residual is None` path, each layer's second residual add is deferred into the next layer's input norm, and the final norm absorbs the last one. The 32 + 31 + 1 + 1 split described in the PR is exactly what the code produces.

**The rounding boundaries genuinely match the unfused path.** The scaled branch does `scale -> round to activation dtype -> add -> round -> read back -> accumulate variance`, which is precisely what `x * 0.22`, then `x + residual`, then `norm(...)` produce as three separate ops. That is the detail most implementations of this get wrong, and the inline comment makes the intent clear.

**The guards are thorough** — device, rank, contiguity, all three dtypes, hidden size, storage overlap, and all four `RMSNorm` semantic flags (`cast_x_before_out_mul`, `fp32_residual`, `override_orig_dtype`, `variance_size_override`), plus batch-invariant mode. Those last ones are the easiest to forget.

277 lines of tests against 149 of implementation, including alias and fullgraph coverage.

## The question I'd want answered first

The combined `torch.compile` + CUDA graph numbers show a regression at small batch:

| BS | latency change |
| ---: | ---: |
| 1 | **+4.45%** |
| 4 | **+2.58%** |
| 8 and above | -1.1% to -3.7% |

The PR diagnoses this correctly — Inductor already fuses the baseline chain, and an opaque custom op prevents that. Reporting it rather than showing only the winning rows is the right call.

But BS1 is the latency-sensitive case for interactive serving, and the guard already evaluates `torch.compiler.is_compiling()` for the overlap check. The same predicate could gate the fast path itself:

```python
and not torch.compiler.is_compiling()
```

That would let Inductor win where it wins (small batch under compile) and the kernel win where it wins (eager everywhere, and compiled from BS8 up), rather than asking users to accept a small-batch regression in exchange for a large-batch gain.

Was that tried? If there's a reason it doesn't work — the compiled path needing the custom op for graph stability, for instance — that belongs in the PR body, because as written the tradeoff looks avoidable.

## Two minor items

**1. The GSM8K result is framed more strongly than the statistics support.** The body reads "improved from 738/1314 (56.16%) to 755/1314 (57.46%), a +1.29 percentage-point candidate point estimate." McNemar gives p = 0.1868 and the paired 95% CI is [-0.51, +3.10], which includes zero. Both are stated immediately after, so nothing is concealed, but a reader skimming comes away with "it improves accuracy," and the data does not show that.

Suggest leading with "no detectable accuracy change (McNemar p = 0.19)" and keeping the point estimate as supporting detail. Accuracy-neutral is the correct and entirely sufficient result for a fusion.

**2. The fused and fallback paths differ in aliasing.** The fused branch mutates `hidden_states` and `residual` in place; the fallback returns fresh tensors and leaves its inputs untouched. Nothing in the current call sites depends on the originals, so this is safe as written, but it is a latent trap. One line in the `_scaled_residual_rmsnorm` docstring noting that the fast path mutates in place would cost nothing.

Related, and worth confirming rather than assuming: the input-layernorm call now writes into the previous layer's MoE output. Mutating the prior layer's output in place is the established deferred-residual convention in this codebase (`llama.py` does exactly this), so I expect it is fine — but a pooled or reused MoE output buffer is the one place that convention could bite.

## Nit

The two specializations now accumulate variance from different values: the scaled branch from the rounded sum, the unscaled branch from the fp32 sum. This is the right decision — matching the new path to its unfused reference while leaving existing numerics undisturbed for every other model that uses this kernel — and there is a comment explaining it at the site. A note in the kernel header that the branches deliberately differ would save the next reader the puzzle.

## Recommendation

Approve once the `torch.compiler.is_compiling()` question is resolved, either by gating the fast path under compile or by documenting why the small-batch regression is unavoidable. The correctness work here is careful.
