## Motivation

Fused draft storage currently relies on a draft-specific pool facade and backend-name gates. Routed views can express shared and window-only placement while the executing backend declares the metadata and storage combinations it supports.

## Changes

- Bind draft layers to their host subpool views and retain per-step physical write locations.
- Resolve placement and eligibility from draft geometry, KV dtype and backend capabilities.
- Carry window-prefix offsets through draft metadata and extend paths, including eager-only restrictions where captured execution lacks the required mask.

## Validation

Seven isolated runner-backend checks passed, including DFLASH/DSPARK TRTLLM window drafts with graphs on/off and EAGLE controls.

Review follow-up: isolated CPU checks passed for 24 resolved graph-mode cases and eight FlashInfer capability cases, covering both override directions. GPU capture was not run.

Historical H200 validation at `a67e8f4415` (PyTorch 2.14.1, FlashInfer 0.7.2):
- gpt-oss-120b with a dummy EAGLE3 window-64 draft: static versus fused storage matched **42/42 draft records** within each execution mode.
- Eager versus graph matched only **39/42**. The later implementation in this PR rejects the unsupported captured FlashInfer window-draft route; eager serving passed.

CPU review passed per-step bindings for top-k 1/2/4. GPU serving was not rerun on the published head; dummy-draft results do not establish acceptance quality.
