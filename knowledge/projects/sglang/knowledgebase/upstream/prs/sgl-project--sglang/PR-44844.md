# [Feat] hicache: Add opt-in legacy Mooncake cache fallback

[Upstream PR](https://github.com/sgl-project/sglang/pull/44844) · state: open · merged: False

## Original PR description

## Motivation

Moving Mooncake KV objects into dtype-specific tenants in #38362 makes existing, compatible cache objects cold. Add an opt-in migration path that reads verified legacy data on a confirmed miss and promotes it into the new tenant.

**Draft; depends on #38362.** This branch is based on its head (`9e81b5ed5b54e45ff68cff36bbacca5ab25da0c8`). The diff against main currently includes that prerequisite; the new fallback is in the final feature commit. Rebase after #38362 merges.

## Modifications

- Add a separate `legacy_fallback.py` compatibility module. The option is off by default and requires matching stored dtype, host layout, page size, and an explicit `verified_compatible=true` operator attestation. Operators must verify the remaining representation/model/parallelism parameters and stop all legacy writers; unknown or mixed-format namespaces cannot be migrated safely.
- Open a separate read-only legacy client in the original configured tenant, before the dtype suffix. It mounts no storage segment, performs no warmup writes, and does not register inference buffers or reuse the primary transfer engine.
- Prefer primary objects. Fall back only on confirmed absence, validate exact byte length, copy into host buffers, and promote through the primary client. Legacy lookup/read failures remain misses; promotion errors preserve successful reads. Ordinary writes and clear operations never modify the legacy tenant.
- Disable fallback on `clear()` to avoid restoring invalidated objects in that backend instance. Remove the option before restarting if those objects must remain invalidated.
- Initially support ordinary embedded MHA/MLA pools, including multi-buffer reads. Reject standalone clients, unified/logical pools, hybrid/side pools, and group semantics rather than assuming the anchor dtype describes every payload.
- Document the migration procedure, multi-tenant master requirements, and additional CPU-copy/per-object IO cost.

## Accuracy Tests

- **11 compatibility-module CPU tests passed**, exercising actual `ctypes` buffer writes, primary-hit precedence, confirmed-miss gating, mixed batches, malformed declarations, missing/wrong-size/evicted legacy objects, multi-buffer scatter, and promotion/error handling.
- Local execution bypassed only `sglang.__init__` eager runtime imports using a namespace-package bootstrap; the compatibility implementation and CI registry were loaded normally. Mooncake clients are mocks.
- Added integration tests for tenant/client setup, unsupported modes, backend read/existence hooks, and clear behavior. The full `test_mooncake*.py` suite could not collect in the local macOS environment because `pybase64` is missing. These integration tests still require execution in the normal CPU CI environment.
- Pre-commit checks on all five changed files passed.
- No live Mooncake, RDMA, GPU inference, or model-accuracy run. Before ready-for-review, validate two simultaneous clients, master quotas, migration/promotion, and cleanup against a live multi-tenant Mooncake deployment.

## Speed Tests and Profiling

Not run. The disabled mode creates no legacy client or additional RPC. Enabled migration adds a legacy bytes read, a CPU copy, and best-effort per-object promotion; it is intended for temporary warmup.
