# [Bench] Apply the ITL convention uniformly across backends and label it

[Upstream PR](https://github.com/sgl-project/sglang/pull/43894) · state: open · merged: False

## Original PR description

### What this fixes

`bench_serving` picks its inter-token-latency definition from the backend name. At `calculate_metrics`:

```python
use_retokenized_itl = (
    accept_length is not None
    and accept_length > 0
    and backend in ("sglang-oai", "sglang-oai-chat")
)
```

When that is true, each streamed chunk's gap is divided by the tokens that chunk carried and replicated once per token. Every other backend gets the undivided gap. The selection is then applied without a trace in the output:

```python
itls = retokenized_itls if use_retokenized_itl else itls
```

The two definitions differ by the mean tokens per chunk, so one `bench_serving` run can measure two systems under two definitions. It fires exactly when speculative decoding is on, which is when chunks carry several tokens.

Nothing about the protocol forces this. `ASYNC_REQUEST_FUNCS` maps `vllm` to `async_request_openai_completions` and `vllm-chat` to `async_request_openai_chat_completions`, which are the same functions used for `sglang-oai` and `sglang-oai-chat`. Same wire format, same `text_chunks`, same samples collected. Only the correction is gated on the name. `trt`, `lmdeploy`, `truss` and `gserver` are never corrected either.

Per-token is clearly SGLang's house convention, since the server divides too and that code is written independently (`srt/observability/metrics_collector.py`). The problem is not which convention SGLang prefers. It is that the preferred one is applied to SGLang and withheld from everything it is being compared against.

Two smaller things in the same place. `mean_tpot_ms` and friends use `(latency - ttft) / (output_len - 1)` for all backends, so one run reports a divided ITL distribution next to an undivided TPOT. And the reported `*_itl_ms` fields carry no record of which convention produced them, so a number copied out of the summary table cannot be interpreted later.

### What this changes

Gate on the stream rather than the name: divide only when chunks actually carry more than one token, which is observable for any streaming backend and is a no-op when they don't. Add an `itl_convention` field, print it with the summary, and warn when the other convention would have reported a materially different median.

Reported `*_itl_ms` values are unchanged for existing SGLang runs. I deliberately have not tried to settle which convention is correct, because that is a real question and not one a bug fix should decide. vLLM's harness does not divide and documents the choice in `docs/benchmarking/cli.md`, with worked arithmetic. This PR only makes the choice uniform within a run and visible in the output.

### Not a duplicate

- #12064 (merged) introduced this convention and its own before/after shows the size of it, `Median ITL (ms): 8.72` to `3.20` on one run. It fixed SGLang's self-measurement. It did not make the convention uniform across backends.
- #33193 fixes the same class of chunk-versus-token accounting bug in this file, for peak output throughput rather than ITL.
- #36272 makes buffered decode steps observable. It does not change how a chunk's gap is attributed to tokens.
- #30918 (merged) added a steady-state window, orthogonal.

Searched open PRs and issues for `retokenized itl`, `itl accept_length benchmark`, and `retokenized_itl`. Nothing addresses the backend gate.

### Testing

The semantics are testable without a GPU or an SGLang install, by replaying a chunk stream through both conventions and through the old gate.

```
stream   backend      old gate  new gate
spec     sglang-oai   True      True
spec     vllm         False     True
spec     trt          False     True
spec     lmdeploy     False     True
plain    sglang-oai   True      False
plain    vllm         False     False
```

`spec` is twelve tokens in four chunks, `plain` is twelve tokens in twelve chunks. The old gate treats one stream two ways depending on the backend string. The new gate treats both backends alike and turns itself off when chunks carry a single token.

On the magnitude, replaying a tokens-per-chunk histogram measured on an L40S (Qwen2.5-7B with an EAGLE-3 drafter over ShareGPT, `{1: 11357, 2: 6922, 3: 5866, 4: 1677, 5: 457, 6: 208}`) with step time held constant reproduces the end-to-end ratios from a live server to within 3 percent: median 3.00x against 2.93x measured, p99 1.00x against 1.03x. That is what establishes the gap as definitional rather than behavioural.

Measured on the same setup, both conventions computed from one timestamp stream per run:

| concurrency | mean acceptance length | median ITL ratio | p99 ITL ratio |
|---|---|---|---|
| 1 | 2.073 | 2.98x | 1.01x |
| 8 | 2.002 | 2.93x | 1.03x |
| 32 | 2.007 | 2.92x | 1.18x |

The median is where the conventions part company. The real tokens-per-step distribution has its mode at one token, around 42 percent of steps, so token-weighted the p99 sample lands in that plateau under both definitions while the median token sits in a multi-token chunk and gets divided.

Static checks: syntax parses under 3.12, `BenchmarkMetrics` has one construction site and the new field sits ahead of the first defaulted field, so the dataclass still builds.

What I have not run: a live `bench_serving` against two backends. The dataclass and gate changes are covered above, but if a maintainer wants the end-to-end run before merging, that is a fair ask.
