# [Fix] QSA: Stop speculative verify from overwriting the pending index-key ring

[Upstream PR](https://github.com/sgl-project/sglang/pull/46125) · state: open · merged: False

## Original PR description

## Motivation

QSA (Qwen4-Exp / Qwen3.8-Flash-Next) keeps the raw index keys of groups that are not compressed yet in a per-request pending ring of `compress_ratio` slots, addressed as `req_pool_idx * ratio + position % ratio`.

A `TARGET_VERIFY` forward of W rows per request stores the raw key of **every** row in the ring (`qsa_index_q_norm_rope_store` in `project_qk`) before `update_key_state_and_compress` compresses the groups those rows complete, reading each group's members back from the ring. A group completed at row j reaches back `ratio - 1` positions, so its first members precede the window. If j is not the window's last row, the later rows have already overwritten those members, because `(p + ratio) % ratio == p % ratio`. The stored compressed key then averages the wrong tokens and is rotated at the RoPE position read from the overwritten first member.

Example, ratio 4, W = 4, committed length 4k+1: the verify rows are positions 4k+1..4k+4. Row 4k+3 completes the group [4k, 4k+3], but row 4k+4 has already overwritten the slot of 4k, so the group averages 4k+1..4k+4 and is rotated at 4k+4.

`_require_chain_speculation` only refuses `draft_tokens > compress_ratio`. That stops the window from colliding with itself, not with the members it reaches back for, so every target verify with 2-4 draft tokens is affected, including EAGLE/NEXTN 3/1/4 and DFLASH. The MTP draft's own QSA layer (`DRAFT_EXTEND_V2`) uses the same ring and is affected too. Prefill and plain decode are not. On the served Qwen3.8-Flash-Next with NEXTN 3/1/4, 81.5% of the compressed keys of generated text differ from the ones a prefill of the same tokens stores (tables below). Top-k selection only uses them once a context exceeds the budget (2048 tokens at ratio 4), but they stay in the radix cache and are scored by every later token and turn.

## Modifications

- `QSATokenToKVPool` sizes the ring per request with `qsa_pending_ring_size(compress_ratio, max_rows_per_request)`: the power of two `>= compress_ratio + rows - 1`, where rows is `max_speculative_num_draft_tokens()` (passed by `kv_cache_configurator`, so adaptive tiers are covered), or 1 without speculation. Without speculation the ring stays at `compress_ratio` slots and nothing changes. With 2-5 draft tokens it is 8 slots at ratio 4. The rounding gives prefill and decode servers with different draft counts the same ring, which PD transfer needs.
- `build_pending_ring_slots` / `build_group_ring_slots`, `_qsa_graph_row_metadata_kernel` and the multi-step draft metadata kernel (`RING` constexpr) address `req_pool_idx * ring + position % ring`. The extend dump stays in the never-allocated request slot 0, now `[0, ring)`.
- The PD pending-state transfer item is one request's ring (`qsa_ring_size` rows). The pool logs the ring size.
- `_require_chain_speculation` checks `compress_ratio + rows - 1 <= ring` for target verify (rows = draft tokens) and draft extend (rows = `num_tokens_per_req`). This admits verify windows wider than the ratio, e.g. NEXTN 7/1/8 (16 slots). `_capture_cuda_graph_metadata` runs it after the pool is resolved.

Interactions:

- **#40143** widens the ring to `ratio * ceil(W / ratio)` slots to allow wider windows. That is not enough, because the members before the window must survive as well. At W = 4 it keeps the 4-slot ring and this bug. At W = 7 it has 8 slots where 10 are needed: with committed length 4k+3, row 4k+3 completes [4k, 4k+3] while rows 4k+8 and 4k+9 land on the slots of 4k and 4k+1. This PR covers its use case (wider windows) with the bound the ring needs; `test_qsa_pending_ring.py` keeps the 7-row / 8-slot layout as a failing case.
- **#45865** (retraction backup) addresses ring rows as `req_pool_index * qsa_compress_ratio`; whichever lands second should use `qsa_ring_size`.
- **PD:** prefill and decode must resolve the same ring size. Every pairing the old guard admitted (2-4 draft tokens on either side, including the documented prefill 2 / decode 4 NEXTN setup) resolves to 8 slots. Mooncake and NIXL reject a QSA state layout mismatch; Mori does not check it.
- **Multi-layer EAGLE** with `SGLANG_ENABLE_MTP_BOUNDARY_KV_FIX` widens the draft extend by `num_steps - 1 +` conv warm-up front rows, past the ring. It silently overwrote the 4-slot ring before; the guard now refuses it. No QSA model enables multi-layer EAGLE today (it is auto-enabled only for Step3p5/Step3p7, and Qwen3.8-Flash-Next ships one MTP layer); sizing the draft pool for those front rows can follow if one does.

## Accuracy Tests

Environment: 8x B200 nodes; main `9c0f6d6a61` vs this PR on the same base (the rebase onto current main was conflict-free and changed no QSA code); PyTorch 2.14.1+cu130, Triton 3.8.0, FlashInfer 0.7.2, sglang-kernel 0.4.10.

**Unit tests.** `test_qsa_verify_ring.py` (GPU, 35 cases, ~2 min) drives the real `QSAIndexer`, `QSATokenToKVPool` and backend metadata (eager, and the CUDA-graph metadata kernels) through prefill + verify at widths 2-8 with full and random per-request acceptance (rejected rows carry other tokens' keys) and through MTP draft extend, and requires the compressed cache to be bit-equal to prefill + decode and to one whole-sequence prefill. `test_qsa_pending_ring.py` (CPU) replays the slot builders' stores and group reads, and checks the guard.

```bash
Q=test/registered/kernels/ops/attention/qsa
python -m pytest -q $Q/test_qsa.py $Q/test_qsa_indexer.py $Q/test_qsa_fused_kv_prepare.py \
  $Q/test_qsa_hicache.py $Q/test_qsa_strided_zero_fill.py $Q/test_qsa_determinism.py \
  $Q/test_qsa_verify_ring.py test/registered/unit/mem_cache/test_qsa_pending_ring.py \
  test/registered/unit/disaggregation/test_disaggregation_wire.py test/registered/unit/cp/test_qsa_cp_unit.py
```

main (without the two new files): 498 passed, 1 skipped. This PR: 538 passed, 1 skipped.

**Kernel level.** The same harness, compressed groups that differ from one prefill of the whole sequence (2560-token prompts, 1024 generated tokens; eager and CUDA-graph metadata give identical counts):

|---|---:|---:|

**Served model.** Released Qwen3.8-Flash-Next (BF16), one TP2 server per arm (EP2, `flashinfer_trtllm` MoE, `trtllm_mha`, FP32 SSM state, CUDA graphs, 16 running requests). For 12 agentic contexts of 17-32K tokens, a greedy generation (~1100 generated groups per arm) and then the same tokens prefilled after a flush; the compressed keys the two stored are compared per QSA layer (debug dump hook, not part of this PR):

| server | generated groups with cos < 0.98, layer 0 / all 12 layers | cos p10 / p50, layer 0 |
|---|---|---|
| no speculation | 0.19% / 0.19-3.7% | 1.000 / 1.000 |
| NEXTN 3/1/4, main | 81.5% / 81.1-82.1% | 0.799 / 0.894 |
| NEXTN 3/1/4, this PR | 0.09% / 0.09-4.1% | 1.000 / 1.000 |
| NEXTN 7/1/8, this PR | 0.27% / 0.27-3.8% | 1.000 / 1.000 |

Deeper layers drift by the same amount without speculation (BF16 decode vs prefill numerics), so with this PR speculative serving stores the same keys as plain decode.

AIME 2024 + 2025 with thinking (temperature 0.6, top-p 0.95, 32K max tokens, 16 concurrent requests per server), 1200 samples per arm (20 per problem, from three servers per arm):

| server | accuracy | vs no speculation, paired 95% CI |
|---|---:|---|
| no speculation | 91.7% | - |
| NEXTN 3/1/4, main | 91.8% | +0.2 pt [-0.8, +1.3] |
| NEXTN 3/1/4, this PR | 91.4% | -0.3 pt [-1.3, +0.8] |
| NEXTN 7/1/8, this PR | 91.2% | -0.5 pt [-1.6, +0.5] |

This PR vs main at NEXTN 3/1/4: -0.4 pt [-1.3, +0.6] (paired bootstrap over the 60 problems). Every arm truncates ~11% of answers at 32K tokens and writes ~12.5-13K tokens per answer. We do not claim a benchmark change: the fix makes speculative serving compute the compressed keys it was always meant to, and its effect on end accuracy is below what 1200 samples resolve. Within a generation, logprobs differ from the prefill's about as much with and without speculation (top-k KL 0.016-0.018 nats/token on all four servers).

## Speed Tests and Profiling

No new kernels and no extra work per forward; only the ring index arithmetic changes. Without speculation the pool layout and every launch are unchanged. KV capacity is the same on main and with this PR (1,569,216 tokens per server). From the AIME runs above (16 concurrent requests per server):

| server | output tokens/s, mean (range) of 3 servers | accept length |
|---|---:|---:|
| no speculation | 1575 (1552-1588) | - |
| NEXTN 3/1/4, main | 2173 (2134-2204) | 2.82 |
| NEXTN 3/1/4, this PR | 2171 (2148-2187) | 2.81 |
| NEXTN 7/1/8, this PR | 2085 (2055-2114) | 3.66 |

NEXTN 7/1/8 now runs (main refuses it) and accepts more per step, but does not beat 3/1/4 at this concurrency.
