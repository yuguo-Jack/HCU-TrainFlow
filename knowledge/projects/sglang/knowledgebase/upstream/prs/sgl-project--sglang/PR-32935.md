# [Perf] [AMD] kimi-k2.5: Fuse MLA projection, RoPE, and KV-cache write

[Upstream PR](https://github.com/sgl-project/sglang/pull/32935) · state: open · merged: False

## Original PR description

## Motivation

In Kimi-K2.5 MXFP4 graph decode on ROCm gfx95, the absorbed MLA key projection, RoPE and KV-cache write run as separate launches on the critical path, even though they share operands. AITER's `fused_fp4_bmm_rope_cat_and_cache_mla` does all three in one launch.

#38340 already added this fusion for FP8 `w_kc` (`fused_fp8_bmm_rope_cat_and_cache_mla`, DSA path). This PR adds MXFP4 `w_kc` as a second branch of that same structure rather than a parallel path.

## Modifications

| Piece in `forward_mla_rocm.py` | FP8 `w_kc` (#38340, unchanged) | MXFP4 `w_kc` (this PR) |
|---|---|---|
| Gate `_can_fuse_bmm_rope_cat_and_cache` | shared terms + TileLang/Triton DSA backend | shared terms + `_can_fuse_mxfp4_bmm_rope_cat_and_cache` |
| Kernel in `_fused_bmm_rope_cat_and_cache` | `fused_fp8_bmm_rope_cat_and_cache_mla` | `fused_fp4_bmm_rope_cat_and_cache_mla` |
| Call site in core | DSA branch | aiter-backend branch |

- Shared gate terms: gfx95 + AITER, kill-switch on, no DCP, has RoPE, no deep-gemm BMM, no LoRA on `kv_b_proj`. The gate then dispatches on `w_kc.dtype`.
- MXFP4 terms: graph decode only, aiter attention backend, no DSA, power-of-two `kv_lora_rank` / `qk_rope_head_dim`, `qk_nope_head_dim` a power of two in 32-256. Everything else keeps the split path.
- One `fuse_bmm_rope_cache` flag in prepare covers both dtypes; prepare skips the absorb and core runs the fused kernel.
- Q output dtype for both kernels comes from `_rope_cache_q_out_dtype`: with an FP8 cache, the aiter backend at 12 local heads keeps bf16 Q (Gluon bh16bn128); DSA always gets FP8 Q as before.
- `fused_fp4_bmm_rope_cat_and_cache_mla` is imported from `rocm_linear_utils` next to the FP8 kernel, behind the same gfx95 guard.
- Env var `SGLANG_OPT_HIP_FUSE_MLA_PROJECTION_ROPE_CACHE` (default `true`) is kept and now gates the unified fused path for both dtypes. #38340 has no switch; keeping one switch on the shared gate gives an A/B and triage kill-switch (the MXFP4 kernel is not bit-exact with an FP8 cache, see below) without a second, MXFP4-only knob. The name is dtype-neutral, so no rename is needed. Default-on means FP8 behaviour is unchanged unless it is set to `false`.

## Accuracy Tests

GSM8K, Kimi-K2.5-MXFP4, 4x MI355X, TP4, AITER attention and MoE, FP8 KV cache, 1319 questions, 8-shot, 512 new tokens:

| Fusion off | Fusion on |
|---:|---:|
| 0.925 | 0.930 |

Kernel parity test (`test/registered/kernels/ops/attention/test_rocm_mla_fp4_absorb_rope_cache.py`, MI35x suite), on K2.5 TP8 shapes with random positions and cache slots, batch 1/7/64/200, FP8 and BF16 caches:
- Every KV-cache byte matches the split path, including untouched slots.
- Q matches bit for bit with a BF16 cache. With FP8, the RoPE half matches exactly and the BMM half is within one FP8 step (about 1% of values), because the split path rounds to BF16 first.
- The test fails if the fused call gets wrong positions, wrong cache slots, or no KV scale.

CPU gate tests (`test_rocm_mla_absorb_fusion_gate.py`, FP8 and MXFP4 branches of the unified gate and kernel dispatch): 11 passed.

The accuracy and speed numbers were measured before the refactor into #38340's structure. The MXFP4 path still makes the same kernel call with the same arguments and gate terms, so they still apply.

Re-measured on this head (`2d915aae0c`, after the refactor) with sgl-eval, on/off in parallel on one node:

| `SGLANG_OPT_HIP_FUSE_MLA_PROJECTION_ROPE_CACHE` | GSM8K | Truncated | Errors |
|---|---:|---:|---:|
| 1 | 97.27% | 0 | 0 |
| 0 | 96.82% | 0 | 0 |

- Command: `sgl-eval 0.1.3 run gsm8k --num-threads 64 --temperature 1.0 --top-p 0.95 --thinking --max-tokens 32768` (full 1319; Moonshot's thinking-mode sampling, no sgl-eval preset for K2.5).
- Within sampling noise (single-run stderr ~0.46 pp at temperature 1.0).
- Server: `amd/Kimi-K2.5-MXFP4`, TP4 per arm (GPUs 0-3 on, 4-7 off), `SGLANG_USE_AITER=1`, `--attention-backend aiter --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.8 --reasoning-parser kimi_k2 --max-running-requests 64 --cuda-graph-max-bs-decode 64` (cookbook MI35x TP4 recipe plus FP8 KV). ROCm/aiter stack @ `f9b5308b2`.
