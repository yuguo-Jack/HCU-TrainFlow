# [Perf] [AMD] kimi-k2.5: Fuse MLA projection, RoPE, and KV-cache write

## Motivation

During Kimi-K2.5 MXFP4 graph decode on ROCm gfx95, the absorbed MLA key projection, rotary embedding, and KV-cache write are launched separately on the latency-critical path even though they share operands.

Fusing these operations reduces decode launch overhead and improves long-context serving performance.

## Modifications

- Fuse the absorbed MXFP4 `w_kc` projection, RoPE, and KV-cache write into one AITER grid using `fused_fp4_bmm_rope_cat_and_cache_mla`.
- Add `SGLANG_ROCM_FUSE_MLA_PROJECTION_ROPE_CACHE`, enabled by default.
- Restrict the fast path to ROCm gfx95/AITER graph decode with MXFP4 `w_kc`.
- Validate the fused kernel's shape requirements before dispatch:
  - `kv_lora_rank` must be a power of two.
  - `qk_rope_head_dim` must be a power of two and at least 2.
  - `qk_nope_head_dim` must be a power of two between 32 and 256.
- Retain the existing split path for unsupported configurations, including DSA, DCP, optimized LoRA execution, and active `kv_b_proj` LoRAs.
- Carry the fusion decision from `forward_absorb_prepare` to `forward_absorb_core` through `RocmMlaProjectionFusionPlan`.
- Add CPU unit coverage for backend, graph-decode, and kernel-shape gating.
- Document the new environment variable.

## Speed Tests and Profiling

The A/B benchmark follows the Kimi-K2.5 ROCm recipe.

Configuration:

- 4× AMD Instinct MI355X (`gfx950`)
- Kimi-K2.5 MXFP4, TP=4
- AITER prefill/decode attention and MoE
- AITER all-reduce fusion
- FP8 E4M3 KV cache, page size 16
- Breakable prefill graph and full decode graph
- Maximum concurrency: 4
- ISL: 8,192
- OSL: 1,024
- 20 measured requests after warmup
- Identical seed and generated workload for both arms
- The only A/B feature change was `SGLANG_ROCM_FUSE_MLA_PROJECTION_ROPE_CACHE=0/1`

| Metric | Fusion disabled | Fusion enabled | Change |
| --- | ---: | ---: | ---: |
| Output throughput | 428.77 tok/s | 433.33 tok/s | +1.06% |
| Total token throughput | 3,861.04 tok/s | 3,902.11 tok/s | +1.06% |
| Median TPOT | 8.81 ms | 8.68 ms | -1.48% |
| Median end-to-end latency | 8,455.36 ms | 8,328.59 ms | -1.50% |
| Median TTFT | 246.43 ms | 247.99 ms | +0.63% |

The fusion improves decode-sensitive throughput, TPOT, and end-to-end latency for the 8k/1k workload. The small TTFT variation is expected because this optimization targets graph decode rather than prefill.
