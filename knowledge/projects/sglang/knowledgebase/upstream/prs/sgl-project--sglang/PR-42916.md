# [Fix] radix-cache: Fix raw-token limits for bigram prefix matching

[Upstream PR](https://github.com/sgl-project/sglang/pull/42916) · state: open · merged: False

## Original PR description

## Motivation

Bigram prefix matching requires one successor token to prove the final reusable KV row.

The existing prefix limit is computed in reusable KV rows but passed directly as `RadixKey.limit`, whose unit is raw tokens. For a bigram cache, this drops the last otherwise reusable KV row because N reusable rows require N+1 raw tokens. Page alignment can amplify the loss: a cached 65-token prompt with page size 64 matches 0 rows instead of 64.

## Modifications

- Add a cache-level conversion from the reusable-KV-row cap to the raw-token limit used by `RadixKey`.
- Allow built-in legacy RadixCache and FULL-only UnifiedRadixCache without HiCache to read one additional successor token for single-layer, non-session/non-PD requests, without reusing it as an extra KV row.
- Keep derived/custom cache contracts conservative unless they explicitly opt in.
- Add CPU regression coverage for legacy, Python unified-tree, and native Rust unified-tree backends.

## Accuracy Tests

Added `test/registered/unit/mem_cache/test_eagle_prefix_boundary.py`, covering:

- bigram successor matching at page boundaries, including unknown successors;
- execution and logprob prefix caps;
- non-applicable request modes;
- session prefix limits and the None-limit conversion guard;
- unsupported/custom cache contracts;
- page sizes 1 and 64 across legacy, Python, and Rust tree backends.

Local validation after rebasing onto main: all six focused CPU tests pass (205 subtests), direct registered execution passes without skips, and 37 existing CPU radix tests pass (55 subtests). Changed-file pre-commit checks pass.
