# [CI] [AMD] disaggregation: Register Mooncake KV buffers with ibv_reg_mr in the PD test container

[Upstream PR](https://github.com/sgl-project/sglang/pull/45691) · state: closed · merged: False

## Original PR description

## What
Set `MOONCAKE_DISABLE_HIP_DMABUF=1` in the AMD disaggregation CI container, so Mooncake registers the KV buffers for RDMA with plain `ibv_reg_mr` as it did before #44404.

## Why
`stage-b-test-large-8-gpu-mi35x-disaggregation-amd` has failed on every lane since the `20261018` CI image ([example](https://github.com/sgl-project/sglang/actions/runs/39599109770)). In `test_disaggregation_basic.py`, the prefill and decode servers both register their KV pools with Mooncake, then crash on the scheduler's first stream access (`Scheduler.run_event_loop`, `self.schedule_stream.cuda_stream`):
- rocm10: `torch.AcceleratorError: CUDA error: out of memory`
- rocm720: segfault in `c10::hip::HIPStream::stream()`

That image is the first with #44404 (Mooncake `01d1eb2a` -> v0.3.14-rc1). In the old Mooncake, `USE_HIP_DMABUF` was set on the wrong CMake target, so the HIP dma-buf MR path was compiled out and GPU buffers went through `ibv_reg_mr`. v0.3.14 fixes the target, so this is the first image that exports dma-bufs for the KV pool. `MOONCAKE_DISABLE_HIP_DMABUF` is Mooncake's own switch back to the `ibv_reg_mr` path.

Current main passes 4/4 on the pre-bump image (`rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261017`): https://github.com/sgl-project/sglang/actions/runs/39686816061. So the regression comes from the image, not from sglang code.

## Notes for the reviewer
This only changes the CI container. A user running single-node PD on the new image with a large KV pool could hit the same crash. Whether sglang should default this variable on ROCm, or whether the dma-buf path needs a fix on the Mooncake side, is a separate decision.

## Test plan
- [x] `test_disaggregation_basic.py` passes on rocm10 with the current image, twice: https://github.com/sgl-project/sglang/actions/runs/39700935407 (attempts 1 and 2). Mooncake logs `HIP dmabuf disabled via MOONCAKE_DISABLE_HIP_DMABUF`, and there are no out-of-memory errors or segfaults.
- [ ] `test_disaggregation_pp.py` still fails on the current image. The out-of-memory crash is gone, but gsm8k slows to about 20 s per request with `KVTransferError: Failed to send aux data` and times out. On the pre-bump image the same test finishes 200/200 in 40 s with accuracy 0.955. The aux buffers are host memory and go over same-node RDMA, so this is a second regression from the Mooncake bump, not from the dma-buf path. Not fixed here.
- All four files, with `continue_on_error` (https://github.com/sgl-project/sglang/actions/runs/39725224212): basic passed, mori passed, pp failed as above, nixl failed. The nixl failure is `NIXL_ERR_BACKEND` with UCX "Destination is unreachable" during NIXL's UCX backend setup. That path doesn't involve Mooncake, and main shows the same error on the Oct 21 runs, so it's unrelated to this change.

- Lzy17 · COMMENTED · 2026-10-22T23:44:17Z · [source](https://github.com/sgl-project/sglang/pull/45691#pullrequestreview-5622263670)

Thanks for the fix. #45759 addresses the same failure the other way: it keeps dma-buf on and bounds the KV pool. Measured with a standalone HIP + ibv_reg_dmabuf_mr program, each dma-buf registration is charged against free GPU memory a second time on MI355X with ionic (100 GiB registered leaves 87 GiB free instead of 187 GiB), so the pool must be smaller than the free memory after model load. Disabling dma-buf hides this and takes the registration path real deployments use out of the tests. Please land only one of the two; I suggest #45759.
