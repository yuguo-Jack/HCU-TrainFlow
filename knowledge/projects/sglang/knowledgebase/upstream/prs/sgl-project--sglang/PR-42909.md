# [DeepSeek-V4.1] Run decoder SWA bounded replay under the breakable prefill CUDA graph

[Upstream PR](https://github.com/sgl-project/sglang/pull/42909) · state: open · merged: False

## Original PR description

## Motivation

The DeepSeek-V4.1 cookbook launch uses `--enable-decoder-swa-bounded-replay`. Today the server refuses to start when that flag is combined with a prefill CUDA graph, so V4.1 prefill always runs eagerly.

Eager prefill costs about 85 ms per batch on 4x B300, no matter how short the prompt is. A 590-token prompt pays it, and so does every follow-up turn of a long conversation.

Roadmap #42170 lists "Enable decoder bounded replay" with no owner. The draft #42078 fixes one piece of stale state and says it does not enable the combination. This PR covers that case as well.

## Modifications

With decoder bounded replay, the layers after the last KV source layer (the "late layers") only run over the last 128 tokens of each request. The number of those rows depends on how many requests are in the batch, not on how many tokens it has. A prefill CUDA graph has a fixed shape per token count, so the late layers could not be captured in it.

1. The late layers now have their own CUDA graphs, one per number of tail rows (128, 192, 256, 384, ... up to one window per request slot). The prefill graph runs the early layers and then replays the matching late-layer graph from a graph break. A batch is padded to the next size up, which is less than 1.5x its real tail.
2. All late-layer graphs are captured once at startup, during the first prefill graph warmup. No request triggers a capture.
3. The attention metadata for the late layers is captured once per tail size and refreshed in place on every replay.
4. When decoder bounded replay is on, the low-ratio compressor and indexer run eagerly at a graph break instead of inside the graph. The eager indexer handles any context length, so the graph is no longer limited to 16K tokens of context.
5. Capturing the graphs needs much less memory than before:
   - All graphs share one scratch buffer for padded query heads. Each graph used to keep its own (1 GB at 16K tokens).
   - Graph metadata is sized by the batch's own context instead of the model's maximum context, when nothing inside the graph needs the full width.
   - The candidate table from the indexer is dropped as soon as the late layers have used it.
6. Decode no longer sees late-layer metadata left behind by the previous prefill.
7. The checks that reject prompt logprobs and full hidden-state capture moved out of the captured code, because a replay skips that code.
8. Only the breakable backend is accepted. The `full` and `tc_piecewise` backends, ROCm, and prefill context parallelism are still rejected at startup.

Every batch now goes through the graph: any number of requests, any size up to the chunk size, any context length. Encoder bounded replay is not part of this PR.

## Accuracy Tests

4x B300, `deepseek-ai/DeepSeek-V4.1-Flash`, TP4 and EP4. Both columns run this branch. "Eager" is what the cookbook launch does today.

```bash
# eager
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4.1-Flash --tp 4 --ep-size 4 --mem-fraction-static 0.8 --cuda-graph-max-bs-decode 64 --max-running-requests 16 --enable-decoder-swa-bounded-replay --disable-prefill-cuda-graph
# graph
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4.1-Flash --tp 4 --ep-size 4 --mem-fraction-static 0.8 --cuda-graph-max-bs-decode 64 --max-running-requests 16 --enable-decoder-swa-bounded-replay --cuda-graph-backend-prefill breakable
# DSpark rows add: --speculative-algorithm DSPARK --speculative-dspark-block-size 5
python3 -m sglang.test.few_shot_gsm8k --num-questions 1319 --parallel 32
```

| GSM8K, 1319 questions | eager | graph |
| --- | --- | --- |
| no speculation | 0.906 | 0.905 |
| DSpark, block size 5 | 0.904 | 0.913 |

Each cell is one run. Repeated runs of one configuration moved between 0.900 and 0.915 while I worked on this, so these are within noise. The DSpark accept length is 3.39 in both columns.

- The one case that only ties is the largest one: 48 requests of about 7.4K tokens at 8 concurrent run at 105.2K input tokens/s eager and 105.6K with the graph (107.9K and 106.9K with DSpark). Those batches fill the 16K chunk and the GPU is the limit there.
- Capturing all graphs takes about 17 GB per GPU. Before the memory changes in this PR, capturing the same set ran out of memory.
- In the GSM8K runs, all but 1 of about 1,480 prefill batches used the graph.
