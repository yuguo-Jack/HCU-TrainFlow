# [Fix] diffusion: Invalidate merged LoRA cache after adapter rewrites

[Upstream PR](https://github.com/sgl-project/sglang/pull/44204) · state: closed · merged: True

## Original PR description

## Motivation

Rewriting a local LoRA adapter with different weights of the same serialized size leaves the persistent merge-cache key unchanged. A subsequent startup can silently adopt the previous adapter's merged weights.

## Modifications

Include the adapter file's nanosecond modification time in the key, using one `os.stat` call in place of the existing size lookup. Add CPU regressions for in-place rewrites and atomic replacement, including unchanged-file cache hits and round-tripping the updated merged weights.

This remains metadata-based invalidation: updates preserving both file size and modification time are outside its scope. Existing entries incur a one-time cache miss under the new key format.

## Accuracy Tests

Both regression cases fail before the fix with `updated adapter adopted stale merged weights`, and pass afterward:

```bash
PYTHONPATH=python python3 -m pytest -q test/registered/unit/multimodal_gen/test_lora_merge_cache_key.py -p no:cacheprovider
# 2 passed
```

The five existing merge-cache tests plus the two new cases also pass in an isolated CPU harness. The harness preloads the real cache module without the GPU-dependent `pipelines_core.__init__` and disables the unrelated diffusion-wide conftest. No cache behavior is mocked; the tests use tiny real safetensors. Full-model generation was not run.

Pre-commit passes for both changed files, and `git diff --check` passes.

## Speed Tests and Profiling

Not run; no inference-speed claim. Key generation still uses one filesystem metadata lookup per adapter.
