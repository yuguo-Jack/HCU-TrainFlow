# [Fix] inkling: Keep BF16 LM-head operands with FP32 output

[Upstream PR](https://github.com/sgl-project/sglang/pull/45335) · state: closed · merged: True

## Original PR description

## Motivation

BF16 projection output can round distinct token scores into a tie before the existing FP32 sampler-buffer cast. Inkling should be able to preserve FP32 projection output while retaining BF16 hidden states and head weights, without enabling the generic `--enable-fp32-lm-head` policy.

```python
# Preserve BF16 operands; produce FP32 projection output directly.
logits = torch.mm(hidden_bf16, weight_bf16.T, out_dtype=torch.float32)
```

Final sampler logits are already FP32 in either mode. Casting a rounded BF16 projection afterward cannot recover its lost score ordering.

## Modifications

- Replace Inkling's default `enable_lm_head_fp32` request with a separate `enable_lm_head_output_fp32` request.
- Use FP32 output for an unquantized CUDA head with matching FP16/BF16 operands. Keep the operands in their existing dtype.
- When this output-only path is unsupported, retain the existing projection path instead of promoting operands to FP32. LoRA and quantized-head dispatch remain unchanged.
- Preserve the existing explicit `--enable-fp32-lm-head` behavior, including its operand promotion fallback.
- Add CPU/CUDA regressions.

To opt out of the new Inkling output policy, omit `--enable-fp32-lm-head` and use:

```bash
--json-model-override-args '{"text_config":{"enable_lm_head_output_fp32":false}}'
```

The older `enable_lm_head_fp32` metadata hook remains available for existing models and explicit configurations; Inkling no longer defaults it to true.

## Scope and limitations

This changes projection-output precision; it is not a full-model FP32 conversion. The [BF16 checkpoint configuration](https://huggingface.co/thinkingmachines/Inkling-Small/blob/8cc5877b44d343f88b92086aa1fb72897950f06a/config.json) and [Transformers implementation](https://github.com/huggingface/transformers/blob/5be474e9cc2c92acaa3ef14fe9e35ea9108b06c1/src/transformers/models/inkling/modeling_inkling.py) do not establish an FP32 inference-output requirement.

Earlier same-operand FP64 controls verify a rounding-dependent greedy winner change, and first-token interventions show that FP32 can avoid entering a whitespace trajectory but does not eliminate repetition once that trajectory is seeded. The new unforced replay also reproduces loop entry with FP32 output; the earlier successful six-batch result is finite mitigation evidence, not a reliable repair. The original output issue remains unresolved. Full-model reference parity, wider task quality and matched performance are not established; upstream CI is not claimed green. The broader default-policy evaluation remains open.
