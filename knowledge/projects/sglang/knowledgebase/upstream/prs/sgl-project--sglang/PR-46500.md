# [Feat] LoRA: revamp LoRADrainer for better performance

[Upstream PR](https://github.com/sgl-project/sglang/pull/46500) · state: closed · merged: True

## Original PR description

## Motivation

When more LoRA adapters are busy than there are slots, the scheduler skips waiting requests whose adapter doesn't fit. As long as the adapters in the batch keep receiving requests, they keep their slots, and every other adapter waits until one of them happens to go idle. With 4 busy adapters on 3 slots (benchmark below), 1% of requests on `main` wait about **90 seconds** for their first token, compared to a median of **77 ms**.

#### Example

Consider 3 slots held by adapters A, B and C, which all receive steady traffic, while adapter D waits. Whenever A, B or C finishes a request, another request for it is already queued, so D never gets a slot. With this PR, once D has waited longer than `--lora-drain-wait-threshold`, the drainer drains B, the adapter that will leave the batch soonest. B stops admitting requests that would outlast the ones it is running, leaves the batch when they finish, and D takes its slot.

```
main
  slot 0 │███ A ██████████████████████████████████│
  slot 1 │███ B ██████████████████████████████████│
  slot 2 │███ C ██████████████████████████████████│
  D      │░░░ waiting ░░░░░░░░░░░░░░░░░░░░░░░░░░░░│

this PR
  slot 0 │███ A ██████████████████████████████████│
  slot 1 │███ B ██████████▒▒ B drains ▒▒███ D ████│
  slot 2 │███ C ██████████████████████████████████│
  D      │░░░ waiting ░░░░░░░░░░░░░░░░░░          │

█ running   ▒ admits only requests that finish with its running ones   ░ waiting
```

## Modifications

I rewrote `LoRADrainer` (`python/sglang/srt/lora/lora_drainer.py`), which `--lora-drain-wait-threshold` turns on. Note that this feature is off by default:

* An adapter is starving once its oldest waiting request has waited longer than the threshold. When the batch is full, the drainer drains one running adapter per starving adapter, longest wait first.
* A drain ends once the drained adapter leaves the batch, or once the starving adapter gets a slot or has nothing waiting.

## Speed Tests and Profiling

I benchmarked on a single H200 with Qwen3-30B-A3B-Instruct-2507 (MoE) and four adapters. To benchmark `main` and my branch:

1. Start the server (for `main`, drop `--lora-drain-wait-threshold 3`):

```
python3 -m sglang.launch_server \
    --model-path Qwen/Qwen3-30B-A3B-Instruct-2507 \
    --enable-lora \
    --max-loaded-loras 4 \
    --max-loras-per-batch 3 \
    --lora-drain-wait-threshold 3 \
    --lora-paths \
        adapter0=mindlab-research/Macaron-A2UI-Tall \
        adapter1=hsilvosa/hsc-wuxia-qwen-3-30b-a3b \
        adapter2=tarsur385/tau2_bench_synthetic-grpo-iter50 \
        adapter3=manjunathshiva/opendecider-medium-td
```

2. Run a benchmark where more adapters are busy than there are slots:

```
python3 -m sglang.bench_serving \
    --backend sglang \
    --dataset-name random \
    --num-prompts 800 \
    --request-rate 4 \
    --random-input-len 512 \
    --random-output-len 512 \
    --lora-request-distribution uniform \
    --lora-name \
        adapter0 \
        adapter1 \
        adapter2 \
        adapter3
```

#### Results

| Metric | `main` | PR | Change |
|---|---|---|---|
| Benchmark duration (s) | 218.9 | 218.6 | −0.1% |
| Output throughput (tok/s) | 907.2 | 908.3 | +0.1% |
| Mean E2E latency (ms) | 17,124 | 9,605 | **−43.9%** |
| Median E2E latency (ms) | 7,526 | 8,880 | +18.0% |
| P99 E2E latency (ms) | 95,087 | 25,539 | **−73.1%** |
| Mean TPOT (ms) | 26.14 | 26.15 | +0.0% |
| Median TPOT (ms) | 24.20 | 26.03 | +7.6% |
| P99 TPOT (ms) | 42.39 | 36.89 | **−13.0%** |
| Mean TTFT (ms) | 10,820 | 3,172 | **−70.7%** |
| Median TTFT (ms) | 77 | 149 | +92.6% |
| P99 TTFT (ms) | 89,612 | 14,350 | **−84.0%** |

On `main`, the adapter left without a slot waits until another one happens to go idle, so the slowest requests wait well over a minute. With the drainer, slots rotate once a request has waited 3 s, which bounds every adapter's wait at the same throughput. Median TTFT and E2E rise because the requests `main` leaves waiting are now served alongside the others.
