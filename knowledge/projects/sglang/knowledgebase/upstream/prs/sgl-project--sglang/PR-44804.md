# [Feat] tracing: Record configured request headers on root spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/44804) · state: open · merged: False

## Original PR description

## Motivation

A request's root span carries only SGLang's own `rid`. Clients, gateways and load balancers know a request by their own IDs (`x-request-id`, a correlation ID, ...), so finding its trace means correlating timestamps across systems.

## Modifications

1. **Create root spans in one function.** `start_root_span` replaces the identical root-span code in `TraceReqContext` and `TraceReqContextAsync`, so the change below applies to both sync and async tracing. Pure refactor, no behavior change.
2. **Record configured request headers on root spans.** `SGLANG_TRACE_REQUEST_HEADERS` (comma-separated, case-insensitive) names the request headers to record. Each one present on a request is set on its root span as `http.request.header.<name>`, the OpenTelemetry semantic-convention attribute for request headers.
   - Values are cut to 1024 characters, a fixed limit rather than a setting: request IDs and hashes (UUID 36, SHA-256 hex 64, SHA-512 hex 128) are far shorter, and the limit only exists so a caller can't attach unbounded data to spans.
   - Headers are recorded exactly as listed, with no filtering, as `SGLANG_LOG_REQUEST_HEADERS` already does for request logs. The operator chooses what goes on spans.
   - `extract_trace_headers` picks these headers up alongside `traceparent`/`tracestate`, so the Engine API and gRPC paths that pass `external_trace_header` record them too.

Docs: new "Finding a Request's Trace" section in `production_request_trace.mdx`, and `SGLANG_TRACE_REQUEST_HEADERS` in `environment_variables.mdx`.

### Behavior changes

None while `SGLANG_TRACE_REQUEST_HEADERS` is unset (the default).

## Accuracy Tests

Not applicable: tracing only, no change to model outputs.

## Speed Tests and Profiling

Not benchmarked. With tracing off, nothing changes; header extraction and attribute recording only run when tracing is enabled. With tracing on, it adds one dict lookup per configured header per request.

## Tests

- `test_trace.py::TestTraceFunctions::test_extract_trace_headers_adds_configured_headers`
- `test_trace.py::TestTraceReqContextEnabled::test_root_span_records_configured_headers_up_to_1024_chars`: a value longer than 1024 characters is cut, and an empty header isn't recorded.
- End to end on 2× L4 (Qwen2.5-0.5B-Instruct, spans exported to Jaeger), both with a regular server at TP=2 and with PD disaggregation: root spans recorded the listed `x-request-id` and a second custom header, and a 2000-character `x-request-id` was recorded as its first 1024 characters.
- `test/registered/unit/observability`, `managers` and `disaggregation` fail the same tests as `main` and no others.
