# [Perf] kv-shard: Batch PageInterleave allocator pops and frees per batch

[Upstream PR](https://github.com/sgl-project/sglang/pull/47578) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-kv-cache-sharding`, `PageInterleavePoolAllocator` is on the scheduler's critical path for every prefill batch and every KV release. Today its cost grows with the batch:

- `alloc_extend` loops over requests and launches several small device ops per request: an `arange`/scatter for each owner class, plus offset math and a `cat`.
- `free()` selects each owner class with a boolean mask, which costs one host sync per class.
- `free_segment()` falls back to `free()`, so it runs a `torch.unique` and gets no benefit from the base class's stride-based fast path.

## Modifications

All changes are in `mem_cache/allocator/page_interleave.py`. Allocation results are identical to the current implementation: the same pages, in the same order.

- **`alloc_extend`**
  - Reads the host lengths once as Python ints.
  - Each owner class pops its whole-batch need in a single slice.
  - A numpy host plan maps every output row to a (popped page, in-page offset) pair. The device work is one H2D copy, one gather, and one multiply-add, so the number of device ops no longer depends on batch size.
  - The plan's H2D copy goes through a reused pinned buffer. A CUDA event makes sure the buffer is only reused after its previous copy has completed.
- **Free path**
  - `free()` now goes through a shared `_free_pages()`.
  - `_free_pages()` computes per-class counts with `scatter_add_` and a single `.tolist()`, then does a stable argsort/split by owner. That is one host sync instead of one per class.
- **`free_segment()`**
  - Now has a stride-based implementation: the start must be page-aligned, so `free_index[::page_size]` gives each page exactly once and no `torch.unique` is needed.
  - Inside a free group, the page ids are buffered.
  - `free_group_end()` releases the whole group in a single call.
- **`need_sort` staging**
  - Under `need_sort`, freed pages are staged per class as a list of tensors with a host-side count. Previously each free did a `cat` onto a release tensor.
  - `merge_and_sort_free`, `class_free_page_counts`, `get_all_free_pages` and `debug_check_classes` are updated to match.
- **Tests**
  - New unit tests check that one batched alloc matches the same requests allocated one by one (`need_sort` on and off).
  - Grouped `free_segment` releases each page exactly once.
  - Unaligned segment starts are rejected.

- Result: all pass.

## Speed Tests and Profiling

Allocator microbenchmark on a single B300 GPU. Setup:
- `shard_size=8`, `page_size=64`, `need_sort=True`.
- Mixed prefix and extend lengths.
- Batched outputs were checked against the old implementation over 30 rounds and are identical.

| batch size | `alloc_extend` before → after (ms) | speedup | grouped `free_segment` before → after (ms) | speedup |
|---:|---:|---:|---:|---:|
| 1 | 0.26 → 0.24 | 1.1x | 0.47 → 0.14 | 3.3x |
| 8 | 1.42 → 0.39 | 3.6x | 0.61 → 0.23 | 2.6x |
| 32 | 5.27 → 0.89 | 5.9x | 0.81 → 0.51 | 1.6x |
| 128 | 20.59 → 2.63 | 7.8x | 1.58 → 1.52 | 1.0x |
