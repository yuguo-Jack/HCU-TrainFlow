# [Perf] model_executor: Reuse device positions for text-only MRoPE

[Upstream PR](https://github.com/sgl-project/sglang/pull/48386) · state: open · merged: False

## Original PR description

## Motivation

`ForwardBatch.init_new` already constructs token positions on the forward device. For an ordinary text-only EXTEND, `_compute_mrope_positions_extend` then rebuilds the same positions with per-request CPU `arange`/`repeat`, concatenates them, and uploads the three-axis tensor to the device.

Reuse the existing device positions when all three MRoPE axes are identical. This avoids the redundant host construction and pageable host-to-device copy while keeping the existing fallback paths. For 4096 eligible EXTEND tokens, the removed upload is 96 KiB per rank per call (192 KiB across TP2 when both ranks execute that call), in addition to avoiding the CPU position-building work. These are resource savings; an end-to-end latency benefit still needs an isolated A/B measurement.

**Validation status:** submitted for review so the upstream Draft gate does not prevent CI. This is not a claim that validation is complete. A dedicated GPU host is not currently available for an isolated upstream A/B run; CUDA correctness and performance results remain pending. This PR does not claim an end-to-end speedup and is not ready to merge without the remaining validation.

## Modifications

- Add a text-only EXTEND fast path that converts the existing positions to int64 and repeats them across the three MRoPE axes on their current device.
- Retain the original path for multimodal batches, DLLM, on-policy deterministic mode, and speculative metadata carrying explicit positions.
- Allow speculative metadata objects whose `positions` is absent/None to use the text path, instead of excluding every `spec_info` object.
- Add CPU regression coverage for prefix/chunk offsets, int32/int64 input positions, empty/4096-token chunks, metadata without explicit positions, and fallback coordinate preservation.
- No model-specific dispatch, new flag, quantization change, attention kernel change, or cache-policy change.

Related but separate: #46332 addresses multimodal decode delta uploads; #46781 addresses speculative multimodal delta uploads. This PR only changes the text-only EXTEND construction path.

## Speed Tests and Profiling

### Source-level savings

Let `N` be the total number of EXTEND tokens in this call, not the full cached context length. The old path uploads a `[3, N]` int64 position tensor after constructing it on the CPU; the new path constructs that tensor from positions already on the forward device.

| Resource | Before | With this fast path |
| --- | --- | --- |
| Position-specific host-to-device payload, per rank/call | `3 * N * 8` bytes | No host-to-device upload for this tensor |
| At `N = 4096` | 96 KiB/rank; 192 KiB across TP2 if both ranks execute the call | Removed |
| At `N = 16384` | 384 KiB/rank; 768 KiB across TP2 under the same condition | Removed |
| CPU construction | Per-request CPU `arange`/three-axis `repeat`, a Python assembly loop, and CPU `cat` | These operations are bypassed; the text-only eligibility check remains |
| Concatenated CPU tensor payload | `3 * N * 8` bytes, in addition to per-request construction temporaries | That host staging tensor is not built |
| Final device MRoPE tensor | `[3, N]` int64 | Still `[3, N]` int64; no KV-cache/weight-memory reduction |

The byte counts above follow from tensor shape and dtype; they are not measured speedups or measured process-RSS reductions. Device-side `repeat` still materializes the result. An int32 input also requires an int64 conversion (an additional `N * 8`-byte temporary), whereas an already-int64 input does not need a dtype-conversion allocation.

Removing this pageable upload also removes a host-side submission point that can wait behind preceding GPU work. How much of that wait lies on the request's critical path must be measured; it must not be counted wholesale as saved wall-clock time.

### Preliminary downstream trace observation

A prior bounded Nsight diagnostic on a customized two-rank GB10 deployment using the same reuse strategy reported:

| Rank | Captured metadata intervals | Cumulative full metadata-interval time | 98,304-byte copy events in the captured window |
| --- | --- | --- | --- |
| 0 | 11 | 18.272 ms | 0 |
| 1 | 12 | 17.895 ms | 0 |

This is a downstream sanity observation, **not** an isolated benchmark of this PR on clean upstream. The metadata times include other metadata work, are cumulative rather than per request, and have no matched before/after timing comparison here. They do not establish an end-to-end speedup or standalone MRoPE latency reduction. Other host-to-device transfers are not claimed to be eliminated.

### Validation still pending

A dedicated GPU host is not currently available for a clean-upstream A/B run. No TTFT, TPOT, throughput, or wall-clock improvement is claimed.

Before marking ready for review, validate the removed upload with a bounded trace and measure metadata/TTFT under the same inputs, cache state, batch sizes, and serving parameters. Run detailed profiling separately from the final timing comparison.
