# [Perf] [NVIDIA] kimi-k3: Fused NVFP4 routing preparation and prepared FP4 routing at M <= 8

[Upstream PR](https://github.com/sgl-project/sglang/pull/46484) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #46475. The NVFP4 checkpoint pays a separate native FP4 quantization launch before routing, and the prepared expert-tile path only covered M = 1 and M = 8. This fuses the radix routing with the NVFP4 quantization on SM107 and runs the prepared path for any `1 <= M <= 8` on both NVFP4 and MXFP4.

## Modifications

- `route_quant_metadata.cuh`: templated on a row quantizer (`Mxfp8RowQuant`, and `Nvfp4RowQuant` under `-DENABLE_FP4`); one host entry serves both formats and both write the expert-tile metadata in-kernel for M = 1..8.
- `moe_route_quant_fused.py`: `nvfp4_covered` / `route_quant_nvfp4` (SM107 only, FlashInfer's default FP4 fast math); `allocate_metadata` takes the weight dtype; the Triton `prepare_expert_tile_metadata` is padded to a power-of-two route count so M = 3, 5, 6, 7 compile.
- `route_quant_handoff.py`: `stage(x, global_scale)` selects NVFP4; `take`, `ready`, `take_metadata` serve both formats.
- `trtllm_prepared_fp4.py`: `try_prepared_k3_nvfp4`; MXFP4 and NVFP4 gates move from M in {1, 8} to `M <= 8`, with in-op finalize for M > 1.
- `flashinfer_trtllm.py`, `kimi_k3.py`: the NVFP4 runner takes the prepared input (gated on `hidden_pad == 0`, keeping main's padding and deferred-finalize checks) and tries the prepared body for deferred finalize or `1 < M <= 8`; the model stages the fused preparation at every batch size through a shared `_route_staged` helper (metadata only for M <= 8; larger M publishes none and the ordinary routed body consumes the prepared input). Main's 64-token cap on the fused route-quant coverage is kept.

## Accuracy Tests

- From the fork (B200, SM107 guard patched): NVFP4 fused output bit-exact against `route_radix` + `fp4_quantize` for M = 1..16, 31, 64, 100, 128, 129, 1000, 4096 (BF16/FP32 activations and scores, strided views, ties, graph replay); in-kernel metadata matches the Triton kernel.
- `test_prepared_nvfp4.py` (new): the prepared NVFP4 body matches `trtllm_fp4_block_scale_routed_moe` to 1e-5 on GB300 at M = 1 and M = 8, deferred and finalized, with normalized and scaled routing weights, with fresh activation/scale/routing/output buffers on every call, and under CUDA-graph replay.
- GB300 (SM103), TP8/DCP8, Kimi-K3 NVFP4, DSpark real acceptance, fp8 KV, no HiCache, this branch vs main: GSM8K 200 questions, 5-shot, temperature 0: 0.975 / 0.005 invalid vs 0.985 / 0.005; acceptance length 4.53 in both arms.
- SM107 (two trays), plain TP8, same model and settings, this branch vs main: GSM8K 0.980 / 0.005 vs 0.985 / 0.005; acceptance length 5.29 vs 5.2.

## Speed Tests and Profiling

Fork, SM107 TP8, bs=1, 60k/1k, NVFP4: routing body 12.90 -> 10.08 us, metadata prep 3.33 -> 1.57 us, fused preparation 5.61 -> 1.95 us; 144.0 -> 162.8 output tok/s (+13.1%). M8 DSpark verify (block 7, simulated acceptance 5.5): 458 -> 554 tok/s (+20.9%).
