# [Fix] Align sliding-window tiles to absolute positions in deterministic unified extend

[Upstream PR](https://github.com/sgl-project/sglang/pull/43320) · state: open · merged: False

## Original PR description

## Motivation

Addresses part of #43055: with `--enable-deterministic-inference`, gpt-oss-20b can give different outputs for the same prompt in `test_deterministic --test-mode prefix`.

**Why it happens**
- Attention adds up keys in blocks of `BLOCK_N` keys (128 on A10), called tiles. Grouping the same keys into different tiles changes float rounding a tiny bit.
- A fresh prefill starts its tiles at position 0.
- On a cache hit, sliding-window layers keep only the last 127 keys of the prefix, and the kernel started its tiles at the first kept key.
- So the same token gets different tiles depending on how much of the prompt was cached → tiny diffs → greedy output flips.
- Prefix mode is the only test mode whose cached prefixes are longer than the 127-key window, so only it fails.

**Proof (A10)**
- Fresh vs cache-hit logprobs match only when the window start is a multiple of 128 (cached ≤ 127, or 255 / 383 / 511 / 639) and differ at every other length tested.
- With `--disable-radix-cache` the test already passes.

## Modifications

- `extend_attention.py`: start the tiles at absolute positions (multiples of `BLOCK_N`) and skip the keys before the window.
  - Prefills with nothing cached compute exactly as before. Later chunks of a long chunked prefill now line up like a one-pass prefill, so their last bits can change.
  - Memory safe: the first tile can start before position 0, but those positions are masked on every load (also with `page_size > 1` and Inkling's `score_mod`).
- `triton_backend.py`: fix a wrong comment.
- New test `test_extend_attention_unified_swa_split_invariance`: extending on a cached prefix must match a fresh run bit for bit. Fails before the fix, passes after.

## Accuracy Tests

A10 (sm86), torch 2.14.1+cu130, CUDA 13.0, gpt-oss-20b with the reporter's launch command.

- Prefix test (prefixes of 1 / 511 / 2048 / 4097 chars, 30 trials), unique outputs: **1/1/2/3 → 1/1/1/1** (ran twice)
- Fresh vs cache-hit logprobs: differ at 20 of 30 cached lengths → 0 of 30
- `single` and `radix_cache` modes pass with the fix, and fresh outputs of the test prompts are the same before and after.
- Only tested on sm86, not on Hopper (`BLOCK_N` 64) or AMD.

## Speed Tests and Profiling

Kernel only, gpt-oss sliding-window layer shape, A10:

- Fresh prefill: no slowdown (4096 tokens: ~835 → ~815 us)
- Cache hit: can be slower, because it may read one extra tile (368 cached + 400 new: 103 → 113 us; 2000 cached + 1 new: 16 → 25 us)
- Only affects sliding-window layers in deterministic mode. Decode is unchanged.

## Not covered (keep #43055 open)

- This only fixes the Triton attention path. The issue's H100 failures with `fa3` attention, with `marlin` MoE, and at prefix 511 (cached part shorter than the window) have other causes.
- One likely H100 cause: the gpt-oss router uses flashinfer `tinygemm_bf16` for ≤ 128 rows even in deterministic mode (the DeepSeek gate already guards this). Can't test it on an A10.
- The `radix_cache` test uses a 100-token prefix, shorter than the window, so it can't catch this bug.
