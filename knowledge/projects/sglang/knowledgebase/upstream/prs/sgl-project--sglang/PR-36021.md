# fix: bypass Qwen3.5 fused CUDA preparation for mRoPE

[Upstream PR](https://github.com/sgl-project/sglang/pull/36021) · state: closed · merged: False

## Original PR description

## Motivation

Tighten the CUDA fused-path dispatch in `Qwen3_5AttentionDecoderLayer.self_attention` so it is selected only when the positions tensor is one-dimensional, matching the fused kernel's documented `[T]` contract. Let multidimensional mRoPE positions fall through to the existing native preparation branch, which already applies Q/K normalization and `rotary_emb` with all position axes and requires no new abstraction or kernel behavior. Add a focused CPU-CI unit test that stubs the preparation and attention operations to verify both sides of the dispatch boundary without requiring a model checkpoint or CUDA hardware.

Qwen3.5 vision-language requests pass a three-axis mRoPE position tensor into `Qwen3_5AttentionDecoderLayer.self_attention`, but the CUDA fused QK normalization/RoPE/gate kernel consumes positions as a one-dimensional token sequence. This silently applies the wrong rotary coordinates and produces severely displaced image-grounding boxes, while forcing the existing native preparation path restores parity with vLLM. The failure is independently reproduced on two Blackwell GPUs with both NVFP4 and official FP8 weights, so it is not confined to a quantized vision encoder. Text-only inputs with one-dimensional positions should retain the fused fast path.

Fixes #35949

## Modifications

- `python/sglang/srt/models/qwen3_5.py`: gate the fused CUDA path on a
  one-dimensional positions tensor; multidimensional mRoPE positions fall
  through to the existing native preparation branch.
- `test/registered/unit/models/test_qwen3_5_mrope_dispatch.py`: CPU-only unit
  test stubbing preparation and attention to assert both sides of the
  dispatch boundary, with no checkpoint or CUDA required.

## Accuracy Tests

Not run. The dispatch boundary is covered by the unit test above; the
end-to-end image-grounding parity described in #35949 was reported by the
issue author on Blackwell hardware and has not been independently reproduced
here.

## Speed Tests and Profiling

Not run. Text-only inputs keep the fused fast path unchanged, so no
throughput change is expected for them; this has not been benchmarked.
