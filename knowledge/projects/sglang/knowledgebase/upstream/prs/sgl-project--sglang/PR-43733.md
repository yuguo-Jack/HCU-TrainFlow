# [Perf] deepseek-v4.1: Replay the breakable prefill CUDA graph at any context length

[Upstream PR](https://github.com/sgl-project/sglang/pull/43733) · state: closed · merged: True

## Original PR description

## Motivation

DeepSeek-V4.1's breakable prefill CUDA graph is captured at a 16,384-token context width, and every batch with a longer context runs eager. The width is the candidate window (2,048 blocks of 8 tokens): inside it the captured full top-k equals the two-level candidate selection, and past it it does not. Eager DeepSeek-V4.1 prefill is bound by host kernel launches, so long-context requests lose the graph where it would help most.

## Modifications

The graph replays at any context length when the two-level candidate indexer runs on DeepGEMM (SM100, no prefill context parallelism, no ratio-4/128 layers):

- The full top-k layers (the ratio-2 index sources and the ratio-1 candidate source) score as eager breaks over the live batch, at the real context length, and write the sparse indices the attention break reads (`_prefill_graph_full_topk_break`). The candidate source also returns its block table (`SparseTableBackend.publish_prefill_graph`), which is copied into the addresses the consumers were captured with.
- The ratio-1 consumers always take the two-level path inside the graph (`SparseTableBackend.consume_prefill_captured`) and score only the published candidate blocks, so nothing captured depends on the context length.
- The replayed context limit moves from the DeepSeek-V4.1 server-args hook into the attention backend. `prefill_cuda_graph_default_max_seq_len` (None for every other backend) is 16,384 while the captured indexer bounds the context and None when any context replays. The runner uses it only when `cuda_graph_config[prefill].max_seq_len` is unset, so an explicit `--cuda-graph-max-seq-len-prefill` always applies.
- Replay metadata is built at the live context, decided once for the full rows and the decoder-replay late-layer tail (`_prefill_graph_context_width`). In two-level mode the ratio-1/2 indexer metadata is reference-assigned on refresh instead of copied in place.
- With decoder SWA bounded replay (the default), the candidate source is the late-layer tail's first layer, so its break takes the tail's request rows and positions.
- An idle DP-attention rank that replays the graph scores its fabricated rows instead of asserting.
- Each layer's candidate table is shared by all captured buckets.

Configurations without the candidate indexer (no candidate blocks, the torch prefill path, prefill context parallelism, or pre-SM100 GPUs) keep the 16K limit and today's behavior. The prefill graph stays opt-in for DeepSeek-V4.1 (`--cuda-graph-backend-prefill breakable`).

## Accuracy Tests

GB300 with DeepSeek-V4.1-Flash, TP4 (DSPARK, chunked prefill 8192) and DEP2 with MegaMoE, against main:

- First-token top-20 distributions, as total variation distance from main eager with decoder replay on:
  - two text needles (134K and 284K tokens): at most 0.019; main's own 16K graph is at 0.026, and a second main eager run at 0.013;
  - 155,648- and 327,680-token prefixes, cold and with 256 or 1,024 new tokens after them: at most 0.010; main's 16K graph is at 0.011, and the second eager run at 0.010.
  - Results are similar with decoder replay off and with encoder replay on, and both needles are retrieved in every run.
- GSM8K (200 questions, 8-shot prefix): 97.0% on TP4 and 97.5% on DEP2, against main eager's 97.0% and 98.0%.
- With an explicit `--cuda-graph-max-seq-len-prefill 16384`, and with `SGLANG_DSV41_TORCH_PREFILL_INDEXER=1` (no two-level candidates, so the backend default of 16,384 applies), 14 of the same 123 prefill batches replay, as on main's 16K graph; by default 121 do.
- One unit test checks the replay limit and the metadata width: a replay that is exact at any length has no default limit and its metadata spans the live context; otherwise both stay at the captured indexer width (16K).

Replacing the Python metadata objects here does not update those captured buffers, so subsequent requests can compute top-k using capture-time lengths and KV page mappings. Please retain `copy_` for that path, or move its indexer out of capture as well. A replay test that changes request lengths and KV page mappings within the same bucket would cover this regression.
