# [DeepSeek-V4.1] Replay the breakable prefill CUDA graph at any context length

[Upstream PR](https://github.com/sgl-project/sglang/pull/43733) · state: open · merged: False

## Original PR description

## Motivation

The DeepSeek-V4.1 breakable prefill CUDA graph is captured at a fixed context width (`--cuda-graph-max-seq-len-prefill`, default 16k), and `can_run_prefill_cuda_graph` sends every batch whose longest sequence exceeds it to eager. On GB300 the eager DSV4.1 prefill step is host-launch-bound (~2.5k launches per request per rank, ~10 ms of GPU work in a ~230 ms step), so for the long-context half of real traffic the graph buys nothing. Raising the capture width does not help: the captured two-level indexer asserts `width <= candidate_topk_blocks * candidate_block_size` (16,384 tokens), and the flat top-k inside the graph costs a full static-width `torch.topk` per layer (4.4 ms at 128k vs 0.34 ms per-row-length).

## Modifications

Lets every prefill chunk of any prompt length replay the graph, keeping the capture width at 16k:

- The flat index layers (ratio-2, and the ratio-1 candidate source) score as `eager_on_graph` breaks over the live batch (`_prefill_graph_flat_indexer_break`): dense scoring and per-row top-k at the real context length, writing the persistent sparse indices the attention break reads. The source also returns its candidate block table; `eager_on_graph` copies it into the addresses the captured consumers were captured with.
- The ratio-1 consumer layers always take the two-level path inside the graph (`SparseTableBackend.consume_prefill_captured`): DeepGEMM sparse logits over the published `[rows, 2048]` block table (identity inside the window, so equal to the plain top-k; correct past it). The static-width assert goes away.
- `_deep_gemm_prefill_captured` selects with `topk_transform_paged_from_metadata` (per row up to its own length) instead of `masked_fill` + full-width `torch.topk`.
- `can_run_prefill_cuda_graph` admits any context when `_prefill_graph_context_unbounded()` (breakable graph, candidate-window indexer available, no c4/c128 compress layers); replay metadata follows the live max context, and the c1/c2 indexer metadata is reference-assigned on refresh.

Two files beyond the backend: `v41_indexer/sparse_table.py` (`_SparsePrefillTable.tail_rows`, `consume_prefill_captured`) and `v41_indexer/full_topk.py` (per-row-length captured top-k).

## Accuracy Tests

Greedy outputs on 24k / 40k / 86k / 300k / 763k-token needle prompts match the eager run (key retrieved, text divergence within eager run-to-run noise); 1P1D needle smoke 4.5k / 11k / 40k correct. Measured on GB300 (A4X, 1P1D TP4+TP4, DSpark PD) with this change on top of the Oct-8 nightly (7760d526) plus a downstream decoder-bounded-replay-in-graph change equivalent to #43440; the rebase onto current `main` re-derives only the `can_run_prefill_cuda_graph` hunk and is compile- and lint-checked, so a GPU run on `main` without bounded replay is still owed.

## Speed Tests and Profiling

Real DeepSeek-V4.1-Flash production trace (ISL median 6.7k, p90 127k, max 790k; 300 s per rung), same 1P1D GB300 deployment, graph capped at 16k vs this change (any context):

| concurrency | TTFT p50 | TTFT p90 | output tok/min per chip | TPOT |
|---|---|---|---|---|
| 2 | 372 → 253 ms (−32%) | 1,668 → 1,328 ms (−20%) | +5% | −0% |
| 8 | 545 → 308 ms (−43%) | 2,149 → 1,654 ms (−23%) | +5% | +1% |
| 16 | 1,226 → 645 ms (−47%) | 6,512 → 4,229 ms (−35%) | +16% | +4% |
| 32 | 3,415 → 2,127 ms (−38%) | 17,841 → 9,523 ms (−47%) | +23% | +7% |

Over the ladder 5,670 prefill batches replayed the graph for 1 that ran eager. Against fully eager prefill the same change is TTFT p50 −36…−59% and output/chip +6…+23%.

## Same-base A/B on the Oct-8 nightly (added 2026-10-11)

Both arms on the identical stack (SGLang Oct-8 nightly 7760d526 + the same patch series and runtime), differing only in the prefill graph (this change plus the any-context replay on top; eager arm `cuda_graph_backend_prefill: disabled`). Same GB300 1P1D deployment and real-trace ladder as above, 300 s per rung, 100% success at every rung, 5,804 graph batches to 1 eager batch, 0 worker restarts.

| conc | TTFT p50 eager → graph | TTFT p90 | TPOT | output tok/min per chip |
|---|---|---|---|---|
| 1 | 263 → 142 ms (−46%) | 847 → 690 (−18%) | +1% | +3% |
| 2 | 334 → 205 (−39%) | 1,118 → 1,088 (−3%) | +1% | +1% |
| 4 | 447 → 210 (−53%) | 1,341 → 1,227 (−9%) | +1% | +5% |
| 8 | 494 → 289 (−41%) | 1,547 → 1,397 (−10%) | +2% | +2% |
| 16 | 703 → 437 (−38%) | 2,733 → 3,988 (+46%, see note) | −1% | +2% |
| 32 | 1,823 → 1,594 (−13%) | 9,423 → 8,057 (−14%) | +1% | +3% |

Note: the eager p90 of 2.7 s at 16 concurrent is far below the same arm's 6.4 s on the Sep-24 series; the graph's 4.0 s is within that spread, so the +46% is run variance rather than a regression. Idle-worker floor: 11-token request 200 → 72 ms, 11k cached-prefix request 230 → 78 ms.

Compared with the Sep-24-series numbers above, the nightly upgrade itself took most of the throughput gain (and the decode-side TPOT cost); what the prefill graph adds on current code is TTFT: p50 roughly −40% up to 16 concurrent, p90 roughly −10%, throughput +1…+5%, TPOT flat.
