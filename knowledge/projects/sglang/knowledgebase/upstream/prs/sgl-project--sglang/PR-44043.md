# [AMD][Fix][MiniMax-M3] Choose the aiter FP8 cache mode from the pool's KV scales

[Upstream PR](https://github.com/sgl-project/sglang/pull/44043) · state: open · merged: False

## Original PR description

## Motivation

`MiniMaxM3Attention._aiter_sparse_qknorm_cache` hardcodes
`kv_cache_dtype="fp8_e4m3_unit"` for any FP8 main cache. aiter has two FP8 cache
modes and they are not interchangeable — both contracts are asserted in
`csrc/kernels/fused_qknorm_idxrqknorm.cu`:

| mode | scale | scale tensors |
|---|---|---|
| `fp8_e4m3_unit` | fixed at 1.0 | **refused** — *"fp8_e4m3_unit does not accept k_scale/v_scale tensors"* |
| `fp8_e4m3_static` | from the pool | **required**, single-element contiguous fp32 |

So the mode has to be chosen from the pool's actual per-tensor scales. Today it
isn't: `k_scale_float` is never read in `minimax_m3.py`. Where the KV-cache quant
method produces a non-unit per-tensor scale, the value is written to the cache
**unscaled** and read back wrong. That is a silent numerical error rather than a
crash, and it occurs only on the fused path — so the fused and unfused paths
disagree.

## Accuracy

Measured on MI355X with aiter's own op-test harness
(`op_tests/test_fused_qknorm_idxrqknorm.py`), driving the same kernel both ways on
identical inputs and dequantizing as the reader does (`stored * scale`, the
`MHATokenToKVPool` convention), against the bf16 reference K/V the kernel itself
produces:

| mode | `k_scale = 0.25` | `v_scale = 0.5` |
|---|---|---|
| `fp8_e4m3_static` (this PR) | **2.28%** mean rel. err | **2.39%** |
| `fp8_e4m3_unit` (main today) | **75.00%** mean rel. err | **50.10%** |

The error is not noise and not data-dependent. Unit mode stores the value
unscaled; the reader multiplies by the scale, so it reads back `scale x` the
truth — a relative error of exactly `1 - scale`. The measured 74.995% and 50.102%
are that identity plus FP8 quantization noise, and the ~2.3% in the static rows is
that quantization floor on its own. A smaller scale is worse without limit.

It is silent: no assertion fires, no NaN appears, and it affects only the fused
path, so the fused and unfused stores of the same tensor disagree by this much.

(Per-element max is not quoted: it reaches 100% in *both* modes on near-zero
reference elements, so it says nothing about the defect.)

## Performance

No performance change is claimed or expected. The unit path is untouched, and the
static path adds only a dtype check and two 1-element tensors built once per
layer.
