# [Perf] rust-server: Flatten egress logprob columns only for rows that carry them

[Upstream PR](https://github.com/sgl-project/sglang/pull/47106) · state: closed · merged: True

## Original PR description

## Motivation

In Rust frontend mode, `RustServer.push_generation` runs on the scheduler thread every step, with the GIL held, and flattens the batch's logprob columns into the frame the embedded Rust server decodes. Its per-family filter tested whether a column had any entries. But the output streamer gives every request in a batch with any logprob request a cell in all twelve logprob columns, most of them empty, so the filter never skipped a family: every pair family visited every row of the batch, one bound-method call per row, and filled its value buffer with a per-element `array.extend`. A batch of a few hundred requests in which one asks for logprobs paid that cost for all of them, on the scheduler's critical path.

## Modifications

Each `*Columns` family in `utils/flatten.py` gets `fill(batch_size)` in place of the per-row `accept(i)`, and `push_generation` calls it once per family:

- `fill` finds the rows whose cell carries data (`any`, then `itertools.compress`, both in C), flattens only those rows, and scatters their lengths into place, 0 for every other row.
- A family no row carries stays empty. The Rust decoder already reads an empty column as absent (`per_req_ok` admits it, `lens_i` reads 0 for every request), and the `header_cols`/`data_cols` loops still walk every family, so column order and arity are unchanged.
- Buffers are filled with `array.fromlist` over one flattened list instead of per-element `extend`. A single carried row, such as a prefill's input logprobs over a long prompt, is appended without the flattening copy.
- The idx/val parity asserts are kept, per row and, for the ragged families, per position. The now-unused `flatten_ragged` helper is removed; nothing else referenced it.

No Rust change. The data buffer is byte-identical to before. The header differs only in that a family no row carries is sent as `[]` rather than one 0 per request, which the decoder treats identically.

## Accuracy Tests

Not applicable: no model numerics change. The logprob values that reach the client are the same floats in the same order as before; only the Python code that lays them out in the frame changes.

## Speed Tests and Profiling

No benchmark numbers in this PR. The Python work per step is now proportional to the rows that carry logprob data rather than to the batch size times the number of families: `fill` flattens only the rows with data and bulk-fills the value buffers, and a batch without any logprob request takes the existing path unchanged.

## Testing

- New unit test `test_mixed_logprob_batch_frame` in `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py` (CPU CI). It builds a four-row batch in which each family is carried by a different subset of rows (input logprobs with the leading `None`, a null top-k position, token-id logprobs, hidden states, and one family no row carries), decodes the frame in `for_each_chunk`'s column order, and checks that every row reads back its own cells and that the uncarried family's header columns are empty. Against the previous `server.py`/`flatten.py`, every value check passes and the empty-family check fails with `([0, 0, 0, 0], []) != ([], [])`.
- `pytest test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py`: 5 passed.
- `pre-commit run --files` on the three changed files: passed.
