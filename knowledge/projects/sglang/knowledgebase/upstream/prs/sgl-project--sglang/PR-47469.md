# [Perf] [NVIDIA] attention: Add opt-in LiteTopK prefill indexer top-k for DSA (FP8) and DeepSeek-V4.1 (FP4) on SM100

## Motivation

DSA-style sparse attention (GLM-5.x, DeepSeek-V4.1) picks the top-k keys of every prefill row from an indexer score over all visible keys. Today this is DeepGEMM `mqa_logits` writing the full `[rows, keys]` logits, then a separate top-k over them. At long context both the logits traffic and the top-k grow with `rows x keys`.

This PR adds an opt-in sampled-threshold path (after [LiteTopK](https://arxiv.org/abs/2607.11976), building on #46434): one SM100 kernel scores every key on the tensor cores and keeps only the keys at or above a per-row threshold taken from a strided sample of the row's scores (about 2.25 x topk candidates per row), then a small top-k selects among the candidates. The logits are never written.

## Changes

- Kernels (`kernels/jit/csrc/dsa/litetopk_prefill/`): FP8 indexer (DSA, 32/64 index heads), FP4 indexer (DeepSeek-V4.1, 32/64 index heads), fp32 / bf16 candidate top-k (topk 512 / 1024 / 2048); `attention/topk_page_table_transform.cuh` maps request-relative positions to KV slots through the page-size-64 table (PAGED output).
- Ops: `attention.fp8_indexer_topk`, `attention.fp4_indexer_topk`, `attention.topk_page_table_transform_`.
- Integration behind `SGLANG_OPT_USE_PREFILL_LITE_TOPK=1` (default off):
  - DSA prefill (RAGGED and PAGED / trtllm outputs) when the batch's longest row sees at least `8 x index_topk` keys.
  - DeepSeek-V4.1 full top-k layers when the batch's longest request has at least 24576 compressed keys.
  - Shorter batches keep the dense path.
- First commit: a refactor of the `sgl_kernel` PTX helpers into `sgl_kernel/ptx/{barrier,async,tcgen05}.cuh` (shared by the new kernels and the existing wo_a / kimi attn_res / hicache / muse kernels), plus packed fp32x2 math helpers.
- Requires nvcc >= 13.4 for the JIT kernels.

Reviewed `599923b6f48d`, focusing on test/benchmark structure and the Python integration. A few suggestions to reduce the maintenance surface:

1. **Consolidate the benchmark harness.** The three new `bench_dsa_prefill_*.py` files could share one LiteTopK benchmark entry point with separate, clearly named measurements for candidate generation, candidate top-k, and the complete indexer + top-k path. Parameterize FP4/FP8 where applicable, retaining their different quantization and shape adapters. Please make the complete-path comparison return selected indices on both sides; the FP4 comparison currently omits our final top-k (inline comment).

2. **Share the test setup and result checks instead of copying them.** FP4/FP8 both build ragged request ranges and check padding, index bounds, duplicates and selected scores. A small shared helper with explicit dtype-specific reference/tolerance handling would let the two indexer test files be combined if the measured CI runtime/partitioning permits. Keep the FP8 tail-split cases and FP4 compressed/short-row cases. Within `test_dsa_prefill_topk_candidates.py`, `run_all` and `run_bf16` duplicate output allocation, invocation, offset removal and checking: use one dtype-parameterized runner, retaining the BF16 rounding and implicit-index handling for `T = -inf`. The existing `with_offsets=False` branch is not exercised; parameterizing that would cover the no-offset contract without another test file.

3. **Keep distinct coverage, trim implementation copies.** I would keep the page-table transform test separate: it covers a separate op, runs on the H100 pool, and includes the 65536-row regression. Conversely, `test_sample_grid_cap` only exercises the test-local `sample_stride` and copied constants, so a CUDA-side stride change would not make it fail. Prefer the existing kernel-vs-reference output checks at the stride boundaries over maintaining an additional Python copy of the scheduling rule.

These are consolidation suggestions, not a request to remove dtype-specific assertions or collapse different CUDA pipelines into one large file. Please preserve CI stages/runners and remeasure registrations when combining files. Static review only; I did not rerun GPU validation.

Hi Ziyi, I tried a few changes on top of this PR (B200, nvcc 13.4.92, real GLM-5.2 dumps), with no fallback and no bigger slab. Ratios are kernel time against this PR; lower is faster.

**1. Sample single keys instead of 8-key blocks (the important one).** Top keys sit in runs, so an 8-key block either lands in one or misses it, and Threshold gets noisy. At about 1M keys some rows clip at `FP8_INDEXER_CAP`, unreported because the serving path doesn't read `overflow`, and some come back short. The change is single keys on an odd stride chosen from each block's span (65 up to 524288 keys, 129 up to 1M), loaded through a strided tensor map with one TMA call per tile, plus alpha 4.5 instead of 5.
- Correctness: 12 wrong rows (8 distinct, all on one 1M prompt) go to 0, out of 562,149 rows checked against fp64. Max candidates go from 13658 to 8620.
- Speed: 0.94 and 0.91 on layer 0 at 24K and 32K, 0.99-1.04 on later layers at 24K-32K, a tie from 64K up, including 1M.
- Trade-off: exact-copy keys whose period equals the stride resonate (64K keys, period 65: 14 to 3426 wrong rows). The 4 real files I checked have no bit-identical keys.

**2. Dynamic block claim in the FP8 indexer**, like the FP4 `BlockProducer`. Geomean 0.92 on 30 mixed chunks, a tie on single requests, 1.07 on the worst mix found.

**3. Page-table lookup inside the top-k gather**, so no transform launch. 0.97 at 24K, 0.98 at 64K, a tie at 1M.

All three together: 0.88 on layer 0 at 24K-32K, 0.94-1.00 on later layers at 24K-32K, a tie at 1M, 0.73 on a mixed 512K + 8 x 32K chunk.

In the end, thanks to your great contribution to Litetopk!

This is a tradeoff of this design: adding a fallback for this design may brings non-trivial overhead, while we almost never observe any fallback case in the latest implementation. So we keep the code simple and remove all the overflow. Even in the case of real overflow, it's expected that the overflow is small (i.e. slightly above the threshold), and the random overflow drops falls in the scores around `topk` (score in the same bin), so the impact on the precision is tiny.

Since this PR aims at a possibly lossy optimization and has no worst case performance guarantee, we choose to make it optional rather than default.
