# Fix Qwen3 Coder streaming string arguments

[Upstream PR](https://github.com/sgl-project/sglang/pull/25246) · state: open · merged: False

## Original PR description

## Motivation

Qwen3 Coder tool-call streaming currently buffers string parameter values until the parser sees `</parameter>` or another terminating tag.

For large string arguments, such as file-writing tools with a long `content` field, this causes the OpenAI streaming response to emit the whole argument as one large chunk instead of incremental `delta.tool_calls[].function.arguments` fragments.

This PR fixes Qwen3 Coder string-argument streaming so clients can receive large tool parameters progressively.

Fixes #27005.

## Modifications

- Update `Qwen3CoderDetector` to stream string-like parameters incrementally.
- Only enable incremental streaming for schema string-like types:
  - `string`
  - `str`
  - `text`
  - `varchar`
  - `char`
  - `enum`
- Keep the existing complete-value parsing path for non-string parameters such as boolean, integer, array, and object values.
- Preserve JSON validity by:
  - emitting the JSON key and opening quote once
  - JSON-escaping each streamed string fragment
  - holding potential closing-tag prefixes across chunks
  - emitting the closing quote when the parameter terminator arrives
- Add a regression test to verify a long `content` parameter emits before `</parameter>` is received.

- RedMoonnn · comment · 2026-09-26T06:13:11Z · [source](https://github.com/sgl-project/sglang/pull/25246#issuecomment-5843804952)

I tested this PR against a streaming/non-streaming equivalence suite and found a backward-compatibility regression for literal `null`.

Minimal case: a tool schema explicitly declares `content` as `type: "string"`, and the model emits:

```text
<parameter=content>null</parameter>
```

The current detector's complete-value path produces JSON `null`, but this PR produces the JSON string `"null"` when the input is split one character at a time:

```text
expected: {"content": null}
actual:   {"content": "null"}
```

The same suite covers 125 combinations of values and chunk sizes, plus delimiter splits, interruption, and bounded buffering. A safer implementation must retain enough uncommitted suffix to distinguish the existing literal-null conversion before opening a JSON string.

I also have paired physical evidence for the underlying issue: for identical final 15,375-character tool arguments, the existing detector emitted 8 SSE events with a 300.893 s maximum silence, while the corrected detector emitted 2,108 events with a 16.058 s initial delay and 0.421 s maximum gap thereafter. Final tool arguments and content SHA-256 were identical.

I opened #41313 against current `main`; it only streams schema-explicit `type: "string"` parameters and adds the equivalence/interruption/buffer-bound regressions. I am happy for maintainers to choose either implementation, but the literal-null case should be fixed before merging #25246.


- hanxiao · comment · 2026-10-21T05:24:54Z · [source](https://github.com/sgl-project/sglang/pull/25246#issuecomment-6308754839)

I ported this to v0.5.20 for a production deployment (Qwen3.8-27B, `--tool-call-parser qwen3_coder`, agent clients on `/v1/chat/completions` and `/v1/messages`) and ran into four problems. Sharing in case it helps whichever implementation lands. #41313 is the narrower alternative against current `main`; I have not tested that one.

1. **Name clash with `main`.** `main` (and v0.5.20) already has `Qwen3CoderDetector._get_param_type(self, param_schema)`, built on `infer_type_from_json_schema` and called by `_convert_param_value`. This PR adds a second `_get_param_type(self, param_name, param_config)` to the same class, and the later definition wins. So `_convert_param_value` raises `TypeError: Qwen3CoderDetector._get_param_type() missing 1 required positional argument: 'param_config'`, every `detect_and_parse` fails ("Error in detect_and_parse"), and streaming a non-string parameter crashes. The diff applies cleanly to v0.5.20, so this only shows at runtime.
2. **Typed `anyOf` parameters.** With the clash fixed by renaming the PR's helper, the existing `TestQwen3CoderDetector.test_streaming_anyof_array_parameter_conversion` fails: the PR's own schema reading treats the `anyOf` array parameter as a string and streams `'["NYC"]'` instead of a list. Deciding what to stream with the existing `self._get_param_type(param_config[param_name])` makes the streaming decision the same as the final conversion, which fixes it. A parameter missing from the schema still streams, since `_convert_param_value` returns it as a raw string too.
3. **Literal `null`**, as @RedMoonnn reported. The port holds the value back while it is still a case-insensitive prefix of `null`, before sending `"key": "`, and emits `"key": null` if it closes as null.
4. **Leading newline stripped twice.** `if not self.current_streaming_param_seen_value and text.startswith("\n")` runs again on the next chunk when the first chunk was only the newline, because nothing was emitted and `seen_value` stayed False. With 1-character chunks, `<parameter=content>\n\nbody\n</parameter>` streams as `"body"` while `detect_and_parse` returns `"\nbody"`. A one-shot flag set on the first non-empty text fixes it.

The port with all four fixes is [`docker/qwen3_coder_detector.py`](https://github.com/hanxiao/Qwen3.8-27B-abliterated-AWQ-SGLang-DFlash2-RTX-PRO-6000/blob/2a12eda0c0061ad13ae38b06db7604c0d1b5fd9d/docker/qwen3_coder_detector.py). [`docker/test_stream.py`](https://github.com/hanxiao/Qwen3.8-27B-abliterated-AWQ-SGLang-DFlash2-RTX-PRO-6000/blob/2a12eda0c0061ad13ae38b06db7604c0d1b5fd9d/docker/test_stream.py) checks that string content is emitted before `</parameter>`, and that the streamed arguments equal `detect_and_parse` for 8 calls at chunk sizes 1, 2, 3, 5, 17 and 4096. The 8 calls cover:
- long content with quotes, backslashes, CJK and a fake `</par`;
- typed int, bool and object params;
- two calls in a row;
- an empty value;
- `null` / `NULL` / `nullable`;
- `["string","null"]`, `anyOf`, untyped and unknown params;
- blank lines around the value;
- a tool missing from the list.

Stock v0.5.20 fails only the streaming check. The port passes it and the 18 `TestQwen3CoderDetector` tests (17 existing plus the one from this PR). The image build runs both, with the stock parser as the negative control.

In production (RTX PRO 6000, DFlash 2 speculative decoding), a `write` call with 16,931 characters of content went from 4 argument chunks with a 64.2 s silence to 1,744 chunks at most 0.1 s apart. Generation time stayed the same (64.2 s vs 64.0 s), and the final arguments were identical on both endpoints.

Thanks for the detailed compatibility findings. I have updated my existing PR #41313 (head `b239e3d6`) and rebased it onto the upstream main snapshot `fb6e6a09`.
