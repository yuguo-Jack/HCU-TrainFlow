# [Fix] ngram: Reject capacity <= max_trie_depth instead of aborting the scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/45109) · state: open · merged: False

## Original PR description

## Motivation

Fixes #36495.

`--speculative-algorithm NGRAM --speculative-ngram-capacity 4 --speculative-ngram-max-trie-depth 4`
is accepted at startup, but the first request that reaches the ngram corpus aborts the scheduler
with `munmap_chunk(): invalid pointer` (`Subprocess scheduler_0 crashed with exit code -6`). With
warmup on (the default), that first request is the warmup request, so the server never becomes
healthy, after the weights are already loaded.

Root cause: the trie takes its root from the same node pool, so only `capacity - 1` nodes are
usable, while inserting one suffix of length `max_trie_depth` can need `max_trie_depth` new nodes.
With `capacity == max_trie_depth`, the first long insert asks `squeeze()` to release one node. The
guard in `squeeze()` counts every in-use node as releasable, including the root (which is never in
`global_lru_`), so it passes, and the loop then calls `global_lru_.back()` on an empty list. Smaller
capacities fail the same guard with an exception that escapes the insert worker thread, which also
terminates the process. So `capacity > max_trie_depth` is an invariant of the trie, and nothing
checked it.

## Modifications

- `ngram.cpp`: `Ngram::Ngram` rejects `capacity <= max_trie_depth`, next to the existing parameter
  checks and in the same style, so every caller of `NgramCorpus` gets the invariant.
- `trie.cpp`: `Trie::squeeze` compares against `global_lru_.size()` (the nodes it can actually
  evict) instead of `node_pool_.size() - free_node_count_` (which also counts the root). An
  over-large request now throws the existing "Insufficient node size" error instead of reading
  `back()` of an empty list.
- `speculative_hook.py`: `_handle_ngram` raises a `ValueError` naming both CLI flags, so a bad config
  fails during argument handling, before the model is loaded.
- Tests (CPU, existing files):
  - `test_ngram_corpus.py::TestNgramCorpusCapacity`: `capacity == max_trie_depth` is rejected at
    construction (fails on main: `RuntimeError not raised`); `capacity == max_trie_depth + 1` still
    works and evicts the whole trie on each later full-depth insert (the boundary of the new guard).
  - `test_server_args.py::TestNgramExternalSamArgs::test_capacity_must_exceed_max_trie_depth`:
    4/4 is rejected, 5/4 is accepted (fails on main: `ValueError not raised`).

Valid configs are unchanged (defaults: capacity 10,000,000, depth 18). No test, benchmark or script
in the repo sets a capacity at or below the depth.

## Accuracy Tests

No output change for valid configs. One NVIDIA GB10, `Qwen/Qwen3-0.6B`, triton attention, NGRAM with
4 draft tokens, CUDA graphs off, three greedy requests (8 / 64 / 128 new tokens), main
(`d748bede96`) vs this PR:

| Config | main | this PR |
|---|---|---|
| capacity 4, depth 4 (warmup on) | never healthy: warmup request aborts the scheduler (`munmap_chunk(): invalid pointer`) | launcher exits in 12 s, before loading weights: `ValueError: --speculative-ngram-capacity must be greater than --speculative-ngram-max-trie-depth, got 4 and 4.` |
| capacity 5 (smallest valid), 64, and defaults | serves | identical text on 3/3 requests and identical `spec_verify_ct` for each config |

Repro:

```bash
python3 -m sglang.launch_server --model-path Qwen/Qwen3-0.6B --attention-backend triton \
  --speculative-algorithm NGRAM --speculative-num-draft-tokens 4 \
  --speculative-ngram-capacity 4 --speculative-ngram-max-trie-depth 4

python3 test/registered/unit/spec/test_ngram_corpus.py TestNgramCorpusCapacity -v
python3 test/registered/unit/server_args/test_server_args.py \
  TestNgramExternalSamArgs.test_capacity_must_exceed_max_trie_depth -v
```
