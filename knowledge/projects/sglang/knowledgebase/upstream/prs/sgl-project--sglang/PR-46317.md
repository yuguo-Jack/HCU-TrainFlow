# [Fix] disagg: Count a rebootstrap's emitted outputs once at admission

[Upstream PR](https://github.com/sgl-project/sglang/pull/46317) · state: open · merged: False

## Original PR description

## Motivation

On a PD decode server, a request that went through a true retraction (`pause_generation(mode="retract")`, or a retracted DeepSeek-V4 request) can stall the whole preallocation queue once generation resumes.

How it happens:

1. The retract pops the boundary token and sends the request back to prefill, which recomputes the prompt plus every output the request already emitted. `_rebootstrap_prefill_len(req)` is `len(origin_input_ids) + len(output_ids)`.
2. `_required_admission_tokens` sizes the request as that prefill length plus `min(max_new_tokens, CLIP_MAX_NEW_TOKEN)`. The emitted outputs are already part of `max_new_tokens`, so they are counted twice.
3. Decode intake only guarantees that the prompt plus `max_new_tokens` fits the pool. A request far enough into its output therefore needs more than the whole pool. After a retract-mode pause, the running batch is empty, so nothing is retractable either. The request is never admitted, and `pop_preallocated` stops at it, so every request queued behind it waits forever.

Example from the driver below: on a 256-token pool, a rebootstrapped request with a 143-token prompt and 59 emitted outputs has a fill length of 202 and `max_new_tokens` 111. The first term needs 202 + 53 = 255 and fits. The second term needs 202 + 111 = 313, which does not.

## Modifications

- New helper `DecodePreallocQueue._remaining_new_tokens(req)`: `max_new_tokens` minus the outputs the rebootstrap prefills, clipped by `CLIP_MAX_NEW_TOKEN` as before.
- Use it in `_required_admission_tokens` and in the SWA-tail admission estimate in `pop_preallocated`, which had the same `min(max_new_tokens, CLIP_MAX_NEW_TOKEN)` term.
- A fresh request emits nothing before preallocation (`_rebootstrap_prefill_len` is just the prompt), so its estimate does not change.
- New CPU test `test/registered/unit/disaggregation/test_decode_rebootstrap_admission.py`:
  - a rebootstrapped request 1200 tokens into a 3000-token budget, with a 1000-token prompt on a 4096-token pool, is preallocated on an empty pool (page sizes 1 and 16);
  - its admission estimate equals prompt plus `max_new_tokens`.

  Both fail on `main`.

How I tested: CPU only, no model, no server.

- On `main` (efc9849520) the new test fails (`3 failed, 1 passed`, counting subtests). With this change, `2 passed`.
- I found the stall with a CPU scheduler driver that runs the real `Scheduler` and `DecodePreallocQueue` with the fake transfer backend, and randomly pauses with `in_place` or `retract` and then continues. To keep known stalls out of the comparison, both trees also carry #46222 and #46269. Over 120 seeds (page sizes 1 and 16):
  - without this change, 34 seeds stall with the waiting and running queues empty and the requests stuck in the preallocation queue;
  - with it, all 120 finish.
- I did not cover the DeepSeek-V4 pool or SWA with paging in the driver. The SWA-tail estimate is changed the same way by reading the code.
