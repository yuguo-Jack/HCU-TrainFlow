# [Perf] [NPU] dcp: DSA extend gathers the prefix KV when that moves fewer bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/44320) · state: open · merged: False

## Original PR description

## Motivation

Under decode context parallelism (DCP), an NPU DSA extend handles its cached prefix the same way decode does. It all-gathers the absorbed and rotary query, attends over each rank's KV shard, and merges the partial outputs with an fp32 `[out, lse]` exchange (`cp_lse_ag_out_rs_mla_npu`). That exchange costs `heads × (kv_lora_rank + 1) × 4` bytes per new token and is held several times over, so it grows with the extend length:

- At `--chunked-prefill-size -1`, GSM8K at dcp16 on A3 runs out of memory in the merge. An ~11k-token batch requests 1.35 GiB with 50 GiB already allocated.
- On a long cached prefix, the query and merge traffic is paid by every new token of the tail.

Gathering the prefix KV instead costs one latent row per prefix token, whatever the head count, and nothing when there is no prefix. Which is cheaper depends on the ratio of prefix to new tokens, so the choice is made per forward.

## Modifications

The NPU logic lives under `hardware_backend/npu/`. Shared DCP code only gains defaulted parameters, and CUDA behaviour is unchanged at those defaults. `ForwardBatch` is not touched: the per-forward state lives on the DCP metadata.

**NPU**

- `hardware_backend/npu/dcp_extend_gather.py` (new; it does not import `torch_npu`, so it is tested on CPU):
  - `NPUDecodeContextParallelMetadata` subclasses `DecodeContextParallelMetadata` and adds the per-forward gather plan and the current layer's gathered KV. It is a dataclass because its base is one, and a `msgspec.Struct` cannot inherit from a dataclass.
  - **Per-forward choice** (`dcp_extend_gathers_kv`): gather the KV when `prefix × row ≤ new_tokens × heads × (row + 4 × (kv_lora_rank + 1))`. For GLM-5.2 (64 heads, 512 + 64 bf16) that is a tail of at least prefix / 178. Above 4,096 new tokens (`SGLANG_NPU_DCP_EXTEND_QUERY_GATHER_MAX_TOKENS`) the KV gather is taken regardless, because the query path's fp32 merge stops fitting beside a long context. A batch counts each request's prefix, because the gather sends each one. Decode, and extends below the threshold, keep the query gather unchanged.
  - The gather plan (`plan_dcp_extend_gather`) splits the prefix into collectives of at most `SGLANG_NPU_DCP_EXTEND_GATHER_PIECE_ROWS` rows (default 262,144). Each is followed by an `index_select` that lays every request out as one contiguous prefix+extend run. The output and scratch buffers are reused across layers and forwards, and grow only when a longer context arrives. A context-sized allocation per layer made ranks free and refill out of step, and stalled the collectives for minutes.
  - `build_dcp_extend_gather_plan` is the one place a forward decides whether it gathers: a plain extend outside DSA prefill CP gets a plan, anything else gets `None`. Each layer only checks whether the plan is set.
- `deepseek_v2_attention_mla_npu.py`: `prepare_dcp_extend_metadata_npu` builds the metadata only for a DSA extend with a bf16/fp16 KV cache that the per-forward choice sends to the KV gather; any other KV dtype keeps the query gather. It calls the shared planner and wraps the result in the NPU subclass. `_dcp_gather_extend_kv_npu` runs the plan before each layer's attention call. Only the prefix crosses the wire, because this chunk's own KV is already on every rank, and every rank runs the same collectives in the same order.
- `ascend_backend.py`: `init_forward_metadata` builds the plan, because deciding needs the forward mode and the per-request extend lengths, which the model's prepare step is not given. `_forward_sparse_dcp_gathered` runs `npu_sparse_flash_attention` over the gathered keys in the TND layout, with cumulative KV lengths and no block table.
- `memory_pool_npu.py`: `get_mla_kv_buffer` for the NPU MLA pool, which keeps the latent and rope halves in separate buffers. It keeps the base class's signature.

**Shared code** (unchanged for CUDA at the defaults)

- `models/deepseek_v2.py`: on NPU, `prepare_context_parallel_metadata_for_dcp` now hands off to `prepare_dcp_extend_metadata_npu`. It already branched on NPU here, and returned `None`.
- `layers/dcp/planner.py`: `prepare_decode_context_parallel_metadata` gains `interleave_size=1` and `allocate_kv_buffer=True`. NPU passes its page size, so this rank's prefix rows follow the page interleave its pool writes with. It also skips the context-sized `dcp_kv_buffer` it never reads (1.15 GB per extend at a 1M prefix).
- `layers/dcp/layout.py`: `dcp_local_row` is pulled out of `localize_dcp_indices`, which now calls it. `filter_dcp_local_chunk_kv_indices` gains `interleave_size=1`; at 1 it runs the existing code unchanged.

**Not reused, and why.** The shared prefix gather, `all_gather_kv_cache_for_dcp`, assumes the token round-robin layout rather than the page interleave the NPU pool writes with. It also joins the latent and rope halves that the NPU operator takes apart, and it allocates several context-sized tensors on every call, so on every layer: the allocation pattern the reused buffers above avoid.

**Settings.** The two new knobs are environment variables rather than server arguments. Both are memory-tuning sizes a deployment adjusts to its workload, which is where earlier review discussions in this repo settled similar size knobs.

- Docs: an "Ascend NPU" section in `dcp.mdx`, and the two new variables in the Ascend environment variable reference.

## Accuracy Tests

GLM-5.2 W4A8, Ascend A3, tp16, dcp16, eager, `--chunked-prefill-size -1`, `--mem-fraction-static 0.76`. GSM8K, all 1,319 questions:

| | accuracy | invalid |
|---|---|---|
| main | out of memory in `cp_lse_ag_out_rs_mla_npu` | — |
| this PR | 0.9416 | 0.000 |

For reference, the same change stacked on the DSA prefill sharding PRs (#42977, #42978) scored 0.9386. Paired against this PR, 17 questions are right only there and 21 only here (McNemar p = 0.63). tp16 without DCP scores 0.942.

**Cached-prefix read.** GSM8K never reads a cached prefix at dcp16, so this was checked separately: 8 concurrent greedy requests on a radix-cached ~5.5k-token prefix (4,096 tokens cached at dcp16), each asking for a record value stored in the prefix. All 8 answers are correct. Against the stacked version the worst |Δlogprob| on shared tokens is 0.379, and the one first-token difference is a near-tie (−0.51 vs −0.90). Two identically configured servers on this model differ by up to 0.68.

**After the review rounds** (same settings):

| round | 64-question GSM8K smoke | cached-prefix read |
|---|---|---|
| main merged, first review fixes | 0.953, same answers as the run above on all 64 | 8/8 correct, worst \|Δlogprob\| 0.50 vs the run above |
| NPU code moved out of shared files, main merged | 0.938, one question differs from the round above | 8/8 correct, worst \|Δlogprob\| 0.44 vs the round above |

64 questions cannot tell a one-question difference from run-to-run noise; the smoke only rules out a collapse. The last commit only changes where the gather decision is made. A plain extend checks the same conditions as before, so it was not re-run on the box.

## Tests

`test/registered/dcp/test_dcp_extend_gather_plan.py` (CPU, `base-a-test-cpu`):
- The gather plan rebuilds every request in position order, every rank plans the same collectives, and the pieces tile the sends, extends and output.
- Under page interleave, the prefix rows the planner reads (the chunk filter, then `dcp_local_row`) are the rows the pool's write (`localize_dcp_indices`) stored: slots from widened pages in shuffled order, several requests, prefixes that end mid-cycle.
- At interleave 1, the filter's new path selects exactly what the existing round-robin slice selects, including chunks that start mid-cycle.
- The per-forward choice: the crossover at prefix / 178, ties to the KV gather, summing over the batch, and the 4,096-token cap.
- The per-forward decision: a plain extend gets a plan; target verify, a forward that is not an extend, and DSA prefill CP get none.
- The buffer cache: distinct names get distinct storage, and a repeat request reuses one allocation.
