# [NPU DCP] DSA extend gathers the prefix KV when that moves fewer bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/44320) · state: open · merged: False

## Original PR description

## Motivation

Under decode context parallelism (DCP), an NPU DSA extend handles its cached prefix the same way decode does. It all-gathers the absorbed and rotary query, attends over each rank's KV shard, and merges the partial outputs with an fp32 `[out, lse]` exchange (`cp_lse_ag_out_rs_mla_npu`). That exchange costs `heads × (kv_lora_rank + 1) × 4` bytes per new token and is held several times over, so it grows with the extend length:

- At `--chunked-prefill-size -1`, GSM8K at dcp16 on A3 runs out of memory in the merge. An ~11k-token batch requests 1.35 GiB with 50 GiB already allocated.
- On a long cached prefix, the query and merge traffic is paid by every new token of the tail.

Gathering the prefix KV instead costs one latent row per prefix token, whatever the head count, and nothing when there is no prefix. Which is cheaper depends on the ratio of prefix to new tokens, so the choice is made per forward.

## Modifications

- **Per-forward choice** (`layout.dcp_extend_gathers_kv`): gather the KV when `prefix × row ≤ new_tokens × heads × (row + 4 × (kv_lora_rank + 1))`. For GLM-5.2 (64 heads, 512 + 64 bf16) that is a tail of at least prefix / 178. Above 4,096 new tokens the KV gather is taken regardless, because the query path's fp32 merge stops fitting beside a long context. A batch counts each request's prefix, because the gather sends each one. Decode, and extends below the threshold, keep the query gather unchanged.
- `deepseek_v2.py` (`prepare_context_parallel_metadata_for_dcp`): on NPU this returned `None`. It now builds the DCP metadata only for a DSA extend that gathers the KV, and the presence of that metadata selects the path in the attention core.
- `planner.py`: on NPU this rank's prefix rows are listed under the page interleave the NPU pool writes with (`dcp_owned_prefix_positions`, `dcp_local_row`), so a prefix that ends mid-cycle stays correct. NPU no longer allocates the context-sized `dcp_kv_buffer` it never reads (1.15 GB per extend at a 1M prefix). The CUDA branch is unchanged.
- `layout.py`: the gather plan (`plan_dcp_extend_gather`). It splits the prefix into collectives of at most `SGLANG_NPU_DCP_EXTEND_GATHER_PIECE_ROWS` rows (default 262,144), each followed by an `index_select` that lays every request out as one contiguous prefix+extend run. The output and scratch buffers are reused across layers and forwards, and grow only when a longer context arrives. A context-sized allocation per layer made ranks free and refill out of step, and stalled the collectives for minutes.
- `deepseek_v2_attention_mla_npu.py`: `_dcp_gather_extend_kv_npu` runs the plan before the attention call. Only the prefix crosses the wire, because this chunk's own KV is already on every rank. Every rank runs the same collectives in the same order.
- `ascend_backend.py`: `_forward_sparse_dcp_gathered` runs `npu_sparse_flash_attention` over the gathered keys in the TND layout with cumulative KV lengths and no block table. This path is bf16/fp16 only and raises otherwise.
- `memory_pool_npu.py`: `get_mla_kv_buffer` for the NPU MLA pool, which keeps the latent and rope halves in separate buffers.
- Docs: an "Ascend NPU" section in `dcp.mdx`, and the new variable in the Ascend environment variable reference.

## Accuracy Tests

GLM-5.2 W4A8, Ascend A3, tp16, dcp16, eager, `--chunked-prefill-size -1`, `--mem-fraction-static 0.76`. GSM8K, all 1,319 questions:

| | accuracy | invalid |
|---|---|---|
| main | out of memory in `cp_lse_ag_out_rs_mla_npu` | — |
| this PR | 0.9416 | 0.000 |

For reference, the same change stacked on the DSA prefill sharding PRs (#42977, #42978) scored 0.9386. Paired against this PR, 17 questions are right only there and 21 only here (McNemar p = 0.63). tp16 without DCP scores 0.942.

**Cached-prefix read.** GSM8K never reads a cached prefix at dcp16, so this was checked separately: 8 concurrent greedy requests on a radix-cached ~5.5k-token prefix (4,096 tokens cached at dcp16), each asking for a record value stored in the prefix. All 8 answers are correct. Against the stacked version the worst |Δlogprob| on shared tokens is 0.379, and the one first-token difference is a near-tie (−0.51 vs −0.90). Two identically configured servers on this model differ by up to 0.68.

## Speed Tests and Profiling

GLM-5.2 W4A8, Ascend A3, tp16, dcp16, `--chunked-prefill-size 4096`, `--mem-fraction-static 0.72`. A 400k-token base is cached, then fresh tails are sent on top of it (TTFT, 2 requests each):

| | main | this PR | change |
|---|---|---|---|
| cold 400k prefill (the warm-up) | 449.9 s | 354.0 s | −21% |
| 4k tail on the cached base | 9.12–9.30 s | 8.27–8.40 s | −10% |
| 16k tail on the cached base | 29.42–29.47 s | 25.61–25.66 s | −13% |

Main runs at this chunk size without running out of memory. Every hit read 399,360 cached tokens on both.

## Tests

`test/registered/dcp/test_dcp_extend_gather_plan.py` (CPU, `base-a-test-cpu`):
- The gather plan rebuilds every request in position order, every rank plans the same collectives, and the pieces tile the sends, extends and output.
- The owned-prefix positions match a walk of every position under page interleave.
- The per-forward choice: the crossover at prefix / 178, ties to the KV gather, summing over the batch, and the 4,096-token cap.
- The buffer cache: distinct names get distinct storage, and a repeat request reuses one allocation.
