# [Perf] [NVIDIA] quantization: Write SM90 UE8M0 activation scales in DeepGEMM's MN-major layout to skip its transpose

[Upstream PR](https://github.com/sgl-project/sglang/pull/46838) · state: open · merged: False

## Original PR description

## Motivation

On SM90 (H100 / H200), block-FP8 linears of checkpoints that quantize activations with power-of-two (UE8M0) scales, e.g. DeepSeek-V4.1-Flash, go through `deepgemm_w8a8_block_fp8_linear_with_fallback` with `act_scale_ue8m0=True`. The activation quant writes those scales as row-major fp32 `[M, K/128]`, while SM90 DeepGEMM consumes fp32 scales in an MN-major, TMA-aligned layout, so DeepGEMM launches `deep_gemm::transpose_fp32` before every such GEMM: three kernels per linear (quant, transpose, GEMM) where two would do. In a DeepSeek-V4.1-Flash TP4 decode step that is 210 transposes (attention and dense linears; the MoE experts run on marlin and do not take this path).

The quant kernel already supports column-major scales, but with UE8M0 its column-major output is the int32-packed format of SM100 DeepGEMM, so the SM90 path could not ask it for the fp32 MN-major layout directly.

## Modifications

- `per_token_group_quant_8bit_v2.cuh`: a `kFp32Scale` template parameter (default `false`) for column-major + UE8M0 output stored as fp32 power-of-two values, i.e. the SM90 DeepGEMM layout. The scale computation is unchanged; only the element type and the packed-format branches (remainder zeroing, `extract_required_scale_format`) are gated on the new `kPackedUE8M0 = SCALE_UE8M0 && IS_COLUMN_MAJOR && !kFp32Scale`. Existing instantiations keep `kFp32Scale = false` and compile as before.
- `per_token_group_quant_8bit_v2.py`: selects that variant when the scales are column-major, UE8M0 and the output buffer is fp32 (an int32 buffer keeps the packed path).
- `fp8_utils.py` (`deepgemm_w8a8_block_fp8_linear_with_fallback`, SM90 + `act_scale_ue8m0` branch only): for `M > 2`, allocates the scale buffer in the MN-major, TMA-aligned fp32 layout (one `torch.empty` of the padded size plus `as_strided`, so the storage covers the padding rows) and passes it as `output_s`; DeepGEMM finds the scales already in its layout and skips the transpose. `M <= 2` keeps the current row-major path; see "Why not M <= 2" below. Quantization (UE8M0 rounding, fp8 codes) is unchanged.
- Test: `test_v2_column_major_fp32_ue8m0_matches_row_major` checks, for bf16 / fp16, group sizes 32 / 128 and 1 to 4,097 tokens, that the column-major fp32 output has the same fp8 codes and the same scales (bitwise) as the row-major fp32 UE8M0 output, that the scales are powers of two, and that the buffer is MN-major and TMA-aligned.

An alternative is to teach the newer JIT `per_token_group_quant` kernel this layout instead of the v2 kernel; the v2 kernel already owns the fp32 power-of-two flavor (`_run_per_token_group_quant_8bit_kernel` routes UE8M0 + fp32 scales to it), so this PR extends it. Happy to move it if that is preferred.

Related: I found no open or closed PR / issue about this transpose. #42805 (open) also concerns `act_scale_ue8m0`: it makes the CUTLASS block-FP8 path honor the flag. It does not touch the DeepGEMM path changed here.

## Speed Tests and Profiling

**Net effect**, DeepSeek-V4.1-Flash TP4 decode: without speculative decoding, TPOT −4.5% at B = 4 and −1.8% at B = 16, B = 8 unchanged; B = 1 and 2 run the unchanged path. With DSPARK speculative decoding, time per decode step −2.3% to −2.8% at B = 4 to 16, B = 2 within noise, and +0.8% at B = 1 (see below). Per call, removing the transpose saves about 1 µs. The end-to-end change does not follow from that at small batches; I have not found why.

I tested the obvious fix: over-allocate the scale buffer by 4 KiB and start it 2 KiB into a 4 KiB page (`as_strided` with a storage offset), for every M, without the gate. Per call it works: M = 1 is 1.1 to 2.0 µs faster than before on four shapes, the same over 6 separate captures (spread ≤ 0.03 µs), and outputs are bitwise equal. End to end it does not (earlier set, three servers per side): B = 1 decode is 2.0% slower on all three servers (6.83 / 6.83 / 6.84 ms against 6.69–6.71), while B = 8 and 16 match the gated version (9.47–9.51, 12.23–12.26). - JohnZhao01 · comment · 2026-10-30T06:38:28Z · [source](https://github.com/sgl-project/sglang/pull/46838#issuecomment-6516640441)

@kabishou11 Thanks for the question. This PR is limited to dense / attention linears; it does not touch any MoE path. Line numbers below are at this PR's head (986a433, based on main 75468e4).

**What changes.** Only the SM90 + `act_scale_ue8m0` branch of `deepgemm_w8a8_block_fp8_linear_with_fallback` (`fp8_utils.py` L1559-1575). That function is the block-FP8 linear path: `Fp8LinearMethod` gets it from `dispatch_w8a8_block_fp8_linear`, with `act_scale_ue8m0` set from the checkpoint's `scale_fmt == "ue8m0"` (`fp8.py` L548-551). For M > 2 it passes an MN-major, TMA-aligned fp32 buffer as `output_s`; M <= 2 keeps the row-major path. The new `kFp32Scale` variant of the v2 quant kernel is selected only for a column-major fp32 buffer with `scale_ue8m0=True` (`per_token_group_quant_8bit_v2.py` L109), and this linear branch is the only caller outside the kernel's tests that passes one. The non-UE8M0 SM90 linear branch already wrote MN-major scales before this PR.

**What does not change.** The MoE runners. On SM90, the DeepGEMM MoE runner (`moe_runner/deep_gemm.py`) does not use UE8M0 activation scales: `DEEPGEMM_SCALE_UE8M0` is SM100 / SM120 only (`deep_gemm_wrapper/configurer.py` L58-60), so grouped-GEMM activations are quantized with plain fp32 scales, and the checkpoint's `ue8m0` format only reaches the linear path. So for sglang on SM90 the question is only about the scale layout, not about UE8M0.

**What was measured.** Only the linear path. In the runs in the PR description, the DeepSeek-V4.1-Flash experts use `--moe-runner-backend marlin` (weight-only, bf16 activations), so the expert GEMMs have no activation scales. I did not test any MoE path: no FP8-expert model, no `deep_gemm` MoE runner, no DeepEP.

**Grouped GEMMs on SM90 (from reading the code, not measured).** The masked path's default SiLU-and-mul quant already writes TMA-aligned column-major fp32 scales, so the `get_mn_major_tma_aligned_tensor` call before the down GEMM returns them unchanged (`deep_gemm.py` L1647-1660, L863). Relayout copies remain in these places:

- Contiguous path: `tma_align_input_scale` runs before both grouped GEMMs (L454, L623). The down-GEMM scales come straight from the activation quant, which is row-major on SM90 (L517-551, L582-588). Asking that quant for column-major, TMA-aligned fp32 scales and skipping the copy looks straightforward. The gate-up GEMM scales are permuted by `ep_scatter`, so the MN-major write would have to happen in the scatter. The UE8M0 branch already does that with a transposed buffer (L1146-1153).
- Masked path: the GEMM-0 scales from dispatch (L768), and the down-activation variants for SwiGLU limit, swizzle, `silu_mul_keep_fp32`, SiTU and `gemm1_alpha`, which produce row-major `(E, N, G)` fp32 scales that are re-laid out at L863.

The SM90 grouped kernels already consume MN-major, TMA-aligned fp32 scales; that is what these relayouts produce. So the change would sit on the producer side, with no kernel change. In principle that could remove these copies, but it would be a separate follow-up with its own per-call and end-to-end measurements. In this PR the per-call saving did not carry over one-to-one to decode time, and at small M the GEMM time depended on where the scale buffer starts. So I would not count on a gain on the MoE side without measuring it on an FP8-expert model, and I am keeping it out of this PR.
