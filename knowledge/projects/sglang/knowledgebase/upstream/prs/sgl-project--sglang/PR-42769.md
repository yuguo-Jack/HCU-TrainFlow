# [Tracing] Turn off FastAPI's native OpenTelemetry on SGLang servers

[Upstream PR](https://github.com/sgl-project/sglang/pull/42769) · state: closed · merged: False

## Original PR description

## What

Pass `telemetry={"tracing": False, "metrics": False, "logs": False, "auto_configure": False}` to `FastAPI()` on the main, encoder and diffusion HTTP servers. The new helper `fastapi_telemetry_disabled()` in `observability/trace.py` returns these arguments, and returns nothing on FastAPI versions without the `telemetry` parameter.

## Why

FastAPI 0.142.0 (fastapi/fastapi#16403, released 2026-09-29) turned on native OpenTelemetry by default. It now records `POST /generate`, `fastapi.dependencies`, `fastapi.endpoint` and `fastapi.serialization` spans through the global tracer provider. When tracing is enabled, SGLang installs that same provider for its own request tracing, so FastAPI's spans get exported whatever `/set_trace_level` says. `fastapi` is unpinned, so CI picked up 0.142.2 on 2026-09-30, and `observability/test_tracing.py::test_trace_level_0` has failed since then:

```
AssertionError: 6 != 0 : Spans collected but expected none: ['GET /set_trace_level', 'POST /generate', 'fastapi.dependencies', 'fastapi.endpoint']
```

Example: https://github.com/sgl-project/sglang/actions/runs/37395620023/job/112050816802

FastAPI's environment auto-configuration would also add a second OTLP exporter to SGLang's provider whenever `OTEL_EXPORTER_OTLP_*` is set. This PR turns all four settings off, which puts the servers back to their behavior before 0.142.

## Test plan

- [x] Standalone repro on FastAPI 0.142.2 with an in-memory span exporter on the global provider. Default app: `['POST /generate', 'fastapi.dependencies', 'fastapi.endpoint', 'fastapi.serialization']`. With `fastapi_telemetry_disabled()`: no spans.
- [x] FastAPI 0.141.1: the helper returns `{}`, so the app is constructed exactly as before.
- [x] `observability/test_tracing.py` on MI300 in `stage-b-test-1-gpu-small-amd` part 8: [passed](https://github.com/sgl-project/sglang/actions/runs/37478665740/job/112347556584) (`"passed": true, "elapsed": 202`), no spans collected at trace level 0.
- [x] Control: the same partition on a branch without this change still fails with `AssertionError: 6 != 0 : Spans collected but expected none: ['GET /set_trace_level', 'POST /generate', 'fastapi.dependencies', 'fastapi.endpoint']` ([run](https://github.com/sgl-project/sglang/actions/runs/37481699749/job/112346794502)).

- michaelzhang-ai · comment · 2026-10-13T05:47:25Z · [source](https://github.com/sgl-project/sglang/pull/42769#issuecomment-6139154948)

Thanks for looking. This is now superseded: #43021 (merged 10/13) landed the same change on main at five call sites, including the three here, so I'm closing this one.

On NVIDIA, though, the issue isn't backend-specific. FastAPI emits these spans into whatever global tracer provider exists, and `--enable-trace` installs one on any backend. #43021's own validation shows `test_trace_level_0` failing on FastAPI 0.143 with 5 FastAPI spans exported, and NVIDIA CI currently runs 0.143.0. FastAPI also had no native telemetry before 0.142.0, so turning it off restores the earlier constructor behavior rather than dropping spans sglang used to export.

If FastAPI's request spans are wanted when tracing is on, gating them on the trace level (FastAPI's `exclude` hook takes the ASGI scope) would be a better axis than the backend — but that'd be a change to what's on main now.
