# [NPU] Add sampling-mask support for the Ascend sampling backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/43517) · state: open · merged: False

## Original PR description

## Motivation

`return_sampling_mask` was rejected with HTTP 400 on the ascend sampling backend: that backend drew tokens from logits through a fused op and never exposed the top-k/top-p support the CUDA and torch backends build a mask from, so the scheduler refused the request outright.

The support is available after all. The fused op returns the post-filter logits, and the sampler already rebuilds probabilities from them for min-p and for the draw. This PR reuses those weights instead of replaying top-k/top-p, which could disagree with the op that actually drew the token.

## Modifications

- `top_k_top_p_min_p_sampling_from_logits_ascend` gains an opt-in `return_filtered_probs` flag that also returns the post-filter weights in vocabulary order. The export is referenced before the seeded float64 draw, and the temporary float32 copy is only kept alive when the export was requested.
- `_forward_ascend_backend` threads a `_SamplingMaskCapture` into the existing `_build_sampling_mask_output` / `materialize_sampling_mask_output` pipeline, so the Ascend path reports through the same API fields as the other backends.
- The scheduler no longer rejects `return_sampling_mask` for `--sampling-backend ascend`.
- The captured weights reach the shared packer exactly as the kernel exported them, which keeps `weights > 0` the same support predicate the other backends use.

One commit deserves its own note: an earlier revision rewrote a zero at the drawn column to `finfo.tiny` so a one-ulp mismatch would not abort the request. That substitution reports a token the op excluded as part of the support and inflates the support mass, which is precisely the distribution this mask describes to the trainer, so it is dropped. A genuine mismatch now surfaces as a failed request instead of silently drifting the reported support.

`ruff format --check` and `ruff check` pass on all changed files.

Not covered by this PR: speculative decoding, PD disaggregation, and overlap scheduling.

## Known limits

- Requests still need `top_k == 1` (greedy) or `1 < top_k <= --sampling-mask-max-tokens`, the validation the CUDA path already applies. Wide supports can still overflow the server-side cap and are reported as HTTP 400.
- With `top_p` close to 1.0 the realized support can approach the whole vocabulary, which then exceeds `--sampling-mask-max-tokens` (default 4096).
