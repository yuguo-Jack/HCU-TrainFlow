# [HiCache] Expose the Mooncake L3 object-key layout for external KV routers

## Motivation
SGLang HiCache stores one logical page as several per-pool Mooncake objects, keyed as `{key_prefix}_{page_hash}{suffix}`. An external KV-aware router that wants to score L3 hits must rebuild exactly these keys, but the suffix depends on the model's pool layout, the parallelism layout, and the resolved `--page-size`, so deriving it outside the engine is fragile and breaks silently whenever the naming changes. Mooncake already models per-pool hit policies internally (`PoolHitPolicy`: ALL_PAGES / TRAILING_PAGES); this PR surfaces the same information to external consumers.

This is the engine-side producer for the Dynamo KV router change (ai-dynamo/dynamo#14720), which consumes this layout to reconstruct the object keys.

## Modifications

- New engine endpoint `GET /get_hicache_l3_cache_layout`, following the existing `GetInternalStateReq` tokenizer→scheduler round-trip. Returns the per-pool layout: key suffixes, hit policy, trailing-page window, the key prefix, and the rank that produced it. Returns `"enabled": false` (with a debug log naming the reason) when hierarchical caching is disabled or the L3 backend is not Mooncake.
- The layout is assembled by `MooncakeStore.describe_l3_object_layout`, which reuses `_get_hybrid_page_component_keys` — the same key-building code the store writes objects with — so the reported naming cannot drift from the stored keys.
- CPU-only unit tests in `test/registered/hicache/test_hicache_l3_object_layout.py` (registered under `base-a-test-cpu`), and a section in `docs/docs/advanced_features/hicache_design.mdx`.

Two scoping decisions, happy to revisit:
- The endpoint mirrors `/model_info` (no auth); can add `AuthLevel.ADMIN_OPTIONAL` to match the adjacent `/hicache/storage-backend` if preferred.
- Suffixes are rank-independent for single-PP MLA models; with `pp_size > 1` or an MHA layout they embed the rank. The response reports `pp_rank`/`pp_size` so a consumer can check whether one response covers the whole deployment.

- stmatengss · comment · 2026-10-17T03:31:35Z · [source](https://github.com/sgl-project/sglang/pull/40467#discussion_r4301113386)

File: `python/sglang/srt/managers/scheduler.py` · line 5393

[P1] Import `msgspec_to_builtins` before invoking this handler

`msgspec_to_builtins` is neither imported nor defined in this module, so every call to `/get_hicache_l3_cache_layout` raises `NameError`, including when HiCache is disabled. `process_input_requests()` does not catch this exception; it propagates to `run_scheduler_process()`, whose exception handler sends `SIGQUIT` to the parent process. A metadata query can therefore terminate the service.

A method-level invocation reproduces the `NameError`, and [the lint run for this head](https://github.com/sgl-project/sglang/actions/runs/38153300828) reports the same F821 error. Please import the helper from `sglang.srt.utils.msgspec_utils` and add a test that actually invokes the scheduler handler.

- stmatengss · comment · 2026-10-17T03:31:35Z · [source](https://github.com/sgl-project/sglang/pull/40467#discussion_r4301113392)

File: `python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py` · line 778

[P2] Include the primary storage pools in the advertised layout

`sidecar_pool_specs` excludes the primary KV, SWA, and Mamba pools, even though those pools can be required to restore a prefix. Consequently, a plain KV model returns an empty `pools` list, and a DeepSeek V4 layout omits the required SWA objects.

In a method-level reproduction with a logical KV anchor, C4/C4-state sidecars, and SWA, all advertised sidecar objects exist but the SWA objects are missing. Checking only the advertised keys reports a hit, while the original `batch_exists_v2()` returns zero restorable pages. An external router can therefore overestimate reusable KV.

Please describe all physical pools required by storage prefetch, including the physical KV anchor and component-owned pools, with their actual hit policies and trailing windows. Logical anchors that have no stored object should remain excluded.

- stmatengss · comment · 2026-10-17T03:31:35Z · [source](https://github.com/sgl-project/sglang/pull/40467#discussion_r4301113396)

File: `python/sglang/srt/managers/scheduler.py` · line 1867

[P2] Forward the layout through the DP controller startup handshake

When `num_dp_ranks > 1`, the engine receives its startup information from `DataParallelController`. `launch_tensor_parallel_group()` only retains selected fields from the scheduler replies, and `run_data_parallel_controller_process()` constructs a new `init_info` dictionary without `hicache_object_layout`. The field added here is therefore discarded before it reaches the HTTP/gRPC frontend, so `/server_info` and `GetServerInfo.json_info` omit the advertised layout in DP deployments.

Executing the existing aggregation statements with a scheduler reply containing this field reproduces the loss. Please retain and forward the layout through the DP controller, and add a test covering that handshake; the new server-info tests inject a prebuilt `scheduler_info` and therefore bypass this path.
