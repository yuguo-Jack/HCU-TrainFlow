# [Feat] [Intel] vmoba: Add XPU varlen attention path for VMoBA

[Upstream PR](https://github.com/sgl-project/sglang/pull/46749) · state: open · merged: False

## Original PR description

## Motivation

VMoBA could not run on Intel GPUs. `vmoba.py` imports Dao's `flash_attn`, which has no XPU build, so the attention function resolved to a stub that just raises. On top of that, the VMoBA backend module imported `kernel.attn.vmoba_attn.vmoba`, a package that does not exist anywhere in the tree, so the module failed to import on **every** platform including CUDA.

This PR makes `--attention-backend vmoba_attn` work on Intel XPU. sgl-kernel already ships a SYCL varlen flash attention that returns the same `(out, softmax_lse)` pair VMoBA needs, so the XPU path is a small adapter over it rather than a new kernel.

Wan 2.1 T2V-1.3B now generates video end to end on one Intel Arc Pro B60.

## Modifications

- **`csrc/attn/vmoba_attn/vmoba/xpu_flash_attn.py`** (new, 88 lines): adapts `sgl_kernel.flash_attn.flash_attn_varlen_func` to the 4-tuple `(out, softmax_lse, S_dmask, rng_state)` that VMoBA's merge unpacks. Forward only, because sgl-kernel has no varlen backward.
- **`csrc/attn/vmoba_attn/vmoba/vmoba.py`**: if `flash_attn` is missing, try the XPU module; if both are missing, keep today's stub. CUDA takes the first branch exactly as before.
- **`runtime/layers/attention/backends/vmoba.py`**: fix the import path to the real in-tree module.
- **`runtime/platforms/xpu.py`**: let XPU select the VMoBA backend. If the dtype is wrong or the XPU attention module is missing, it raises instead of quietly falling back to dense attention, so you cannot get dense numbers while believing you measured VMoBA.
- **`runtime/pipelines_core/stages/denoising.py`**: the VMoBA branch filled in `moba_params` but never called `build()`, so `forward` received `attn_metadata=None`. One line.
- **`csrc/attn/vmoba_attn/tests/test_vmoba_selection_gpu.py`**: run on any accelerator at head_dim 64 instead of CUDA-only at head_dim 32, so its torch reference covers XPU too.
- **`test/unit/test_vmoba_xpu_integration.py`** (new): backend-selection cases plus two kernel-contract cases (see below).

CUDA and ROCm behaviour is unchanged. `platforms/cuda.py` is untouched.

## Accuracy Tests

122 cases pass on one Arc Pro B60:

| suite | result |
|---|---|
| `tests/test_vmoba_attn.py` | 96 passed, 48 skipped (pre-existing fp32 skips) |
| `tests/test_vmoba_selection_gpu.py` | 2 passed |
| `tests/test_vmoba_selection.py` | 16 passed |
| `test/unit/test_vmoba_xpu_integration.py` | 8 passed |

The shape-and-dtype cases alone are not enough. All 96 of them still pass with `softmax_lse` forced to zero, which would silently corrupt every block weight in the merge. Making `test_vmoba_selection_gpu.py` device-generic fixes that, because it compares against a plain torch reference:

| | max error | matches reference |
|---|---|---|
| as shipped | 4.63e-04 | yes |
| `softmax_lse` zeroed | **4.45e-01** | **no** |

Two kernel contracts VMoBA depends on are also pinned as tests rather than checked at runtime on every call:

- **`softmax_lse` must be populated.** With zeroed q/k/v the logsumexp over `n_kv` keys has to be `log(n_kv)`. An earlier sgl-kernel build left it unwritten.
- **Row-strided K/V must match contiguous copies.** VMoBA slices K and V out of a stacked `[tokens, 2, heads, dim]` buffer, so they arrive strided. Asserted bit-identical (`atol=0, rtol=0`); this is what makes it safe to pass them through instead of copying ~100 MB each per call.

## Speed Tests and Profiling

### End-to-end Wan generation

`Wan-AI/Wan2.1-T2V-1.3B-Diffusers`, 77 frames at 448x832, 20 steps, one Arc Pro B60 (23.9 GiB), bf16, with the shipped `wan_1.3B_77_448_832` chunking parameters. Three runs:

| run | total | denoise | peak memory | output |
|---|---|---|---|---|
| 1 | 292.63 s | 259.63 s | 22,290 MB | 693,926 B |
| 2 | 291.06 s | 259.12 s | 22,290 MB | 693,926 B |
| 3 | 288.02 s | 258.99 s | 22,290 MB | 693,926 B |

The log shows `Using Video MoBA attention backend for Intel XPU.` and no SDPA fallback, so this is really the VMoBA path.

### Per-layer, against dense attention

Same B60, bf16, 12 heads, head_dim 128, at the two shipped Wan configs. Run-to-run
spread is 1-3%, so treat smaller differences as noise.

`wan_1.3B_77_448_832`, 29,120 tokens:

| | latency | peak | vs dense |
|---|---|---|---|
| dense SDPA | 101.5 ms | 0.34 GiB | — |
| VMoBA temporal | **59.2 ms** | 1.98 GiB | **1.72x faster** |
| VMoBA spatial | **82.3 ms** | 3.67 GiB | **1.23x faster** |
| VMoBA spatio-temporal | 173.5 ms | 8.16 GiB | 0.59x |

`wan_1.3B_77_480_832`, 31,200 tokens:

| | latency | peak | vs dense |
|---|---|---|---|
| dense SDPA | 128.3 ms | 0.36 GiB | — |
| VMoBA temporal | **75.2 ms** | 2.18 GiB | **1.71x faster** |
| VMoBA spatial | 233.6 ms | 9.79 GiB | 0.55x |
| VMoBA spatio-temporal | out of memory | needed 9.48 GiB on top of 13.00 GiB | — |

### Where the time goes

Timing only the varlen attention calls each layer makes, so the rest is block
selection, gather and merge:

| layer | full | attention only | routing | now | ceiling if routing were free |
|---|---|---|---|---|---|
| temporal | 55.0 ms | 17.2 ms | 37.8 ms (69%) | 1.83x | **5.84x** |
| spatial | 82.9 ms | 22.6 ms | 60.3 ms (73%) | 1.21x | **4.46x** |
| spatio-temporal | 178.5 ms | 29.0 ms | 149.5 ms (84%) | 0.56x | **3.46x** |

The sparse attention is already 3.5-5.8x faster than dense in every layer. All of
that is spent on the machinery around it. `sgl_kernel::fwd` is 16.1% / 14.0% /
8.6% of profiled time per layer; the rest is `index_add_`, `mul`, `nonzero`,
`inclusive_scan` and friends.

### What these numbers mean

Routing cost scales with **replicated query rows**. VMoBA copies each query once
per block it selects, so from 29,120 real queries it builds:

| layer | query rows | routing | ns per row |
|---|---|---|---|
| temporal | 349,440 | 37.8 ms | 108 |
| spatial | 1,747,200 | 60.3 ms | 34 |
| spatio-temporal | 5,940,480 | 149.5 ms | 25 |

The spatio-temporal layer skips the most work of the three (12.9% of dense
attended, a 7.8x ideal) yet is the slowest, because it replicates 204x and pays
~150 ms of routing to save ~70 ms of attention.

Two of three layer types are already faster than dense at 448x832, and the
temporal layer is faster at both resolutions. Sequence length is why: dense costs
grow with the square of the token count, so at 29-31k tokens dense is ~100-130 ms
and the sparse path wins. At shorter sequences it does not.

**Memory is the real gap, and it is not solved here.** VMoBA uses 6-27x dense.
The 480x832 spatio-temporal layer fails trying to allocate 9.48 GiB on top of
13.00 GiB, which is exactly 19.9M query rows x 128 x fp32 - the merge promotes a
bf16 tensor to fp32 and doubles the largest allocation in the layer. That, the
replication, and tiling the routing are all changes above the kernel, and they
need to land before any kernel work is worth costing.

Numbers taken with sgl-kernel-xpu 0.6.0-dev. The behaviour the adapter relies on
(row-stride support from sgl-project/sgl-kernel-xpu#471) is present in the pinned
0.4.0 as well. Scripts and raw output are archived outside the repo.

### A note for anyone trying this

The config files under `configs/backend/vmoba/` are flat, but the denoising stage reads `attention_backend_config.moba_config`, so passing one of those files to `--attention-backend-config` does not work. Wrap it as `{"moba_config": {...}}`, as the README example shows. This is pre-existing and not changed here.
