# [Fix] function_call: Parse null and exponent numbers in Gemma4 tool calls

[Upstream PR](https://github.com/sgl-project/sglang/pull/48034) · state: open · merged: False

## Original PR description

## Motivation

Fixes #41316.

`--tool-call-parser gemma4` returns bare `null` and exponent-notation numbers as strings. The Gemma 4 chat template renders `None` as `null` and small or large floats in exponent form, so a call round-tripped through the template fails a schema that declares `number` or `null`:

```
input:  {exact:true,limit:null,tolerance:1e-05,values:[0,-0.5,1e+21],x:-3,y:2.5}
before: {"exact": true, "limit": "null", "tolerance": "1e-05", "values": [0, -0.5, "1e+21"], "x": -3, "y": 2.5}
after:  {"exact": true, "limit": null, "tolerance": 1e-05, "values": [0, -0.5, 1e+21], "x": -3, "y": 2.5}
```

## Modifications

`_parse_gemma4_value` is shared by the one-shot and streaming paths and by array elements, so the fix is in that one function:

- `null` now parses to `None`.
- Values containing `e` or `E` now go through `float()`.

Values that should stay strings still do:

- `1e999` overflows to `inf`, and `json.dumps` would emit the invalid token `Infinity`. It is kept as a string. This guard also applies to dotted input like `1.0e999`, which previously produced `Infinity`.
- `nan`, `inf`, `Infinity`, `e5` and `1_0e2` stay strings.

One limitation: a bare, undelimited value that looks like a number, such as `12e5`, now parses as a number even when the parameter is a string. Bare integers such as `123` already behave this way. The parser does not consult the tool schema, and the template delimits strings with `<|"|>`, so this only affects undelimited model output.
