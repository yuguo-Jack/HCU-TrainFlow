# [NPU DSA] Token shard composes with the DCP KV gather

[Upstream PR](https://github.com/sgl-project/sglang/pull/44321) · state: open · merged: False

## Original PR description

> **Depends on https://github.com/sgl-project/sglang/pull/42978** (DSA token shard, which itself depends on #42977) **and https://github.com/sgl-project/sglang/pull/44320** (DCP extend KV gather). Until those merge, this PR's diff includes them.
> Review only the last commit: "[NPU DSA] Token shard composes with the DCP KV gather".

## Motivation

The DSA token shard (#42978) turns itself off under DCP. On main, DCP's DSA extend all-gathers the query, and that path needs every head-sharded row. #44320 adds a second extend path that gathers the prefix KV instead and attends locally. That path has no such need, so the token shard can run there. On a long cached prefix the KV-gather path covers almost every extend chunk, so without this change DCP loses the token shard's prefill speed-up (−48% at 6k tokens and −54% at 16k in #42978).

## Modifications

- `dsa_token_shard.py`: the plan refuses only DCP extends that gather the query. It takes `index_topk`, and refuses a multi-request DCP extend in which any prefix is shorter than `index_topk`. `dsa_token_shard_cumulative_key_lens` gives the shortened per-rank key lengths in the cumulative form the gathered layout uses.
- `ascend_backend.py` (`_forward_sparse_dcp_gathered`): under the token shard, the gathered keys are one contiguous run per request with cumulative lengths. So a shortened key length would move the next request's start.
  - **Multi-request batch:** sharded only when every prefix reaches `index_topk`. Then the operator drops its causal crop (`sparse_mode 0`) and keeps the full per-request lengths, because the top-k alone keeps the result causal.
  - **Single request:** keeps the crop and shortens its key length to the tokens this rank attends.
- `layout.py`: `dcp_crop_free_extend`, the cached per-forward check for the multi-request case.
- `deepseek_v2_attention_mla_npu.py`: the prepare step passes `index_topk` to the plan.
- The comment in `environ.py` and the Ascend environment variable reference describe the new behaviour under DCP.
- `test_dsa_token_shard_plan.py`: `TestTokenShardUnderDcp` covers the query-gather refusal, the KV-gather admission and the multi-request `index_topk` rule.

## Accuracy Tests

GLM-5.2 W4A8, Ascend A3, tp16, dcp16, eager, `--chunked-prefill-size -1`, `--mem-fraction-static 0.76`. GSM8K, all 1,319 questions:

| | accuracy | invalid |
|---|---|---|
| #44320 alone (no token shard under DCP) | 0.9416 | 0.000 |
| this PR (with #42977, #42978, #44320) | 0.9454 | 0.000 |

Paired, 20 questions are right only with #44320 alone and 25 only with this PR (McNemar p = 0.55). The token shard ran on every rank. GSM8K's prompts are below `index_topk`, so its multi-request batches were refused as designed, and single-request extends were sharded with the causal crop kept.

**Multi-request, crop-free path.** 8 concurrent greedy requests on a radix-cached ~5.5k-token prefix (4,096 tokens cached at dcp16), each asking for a record value stored in the prefix. Every prefix reaches `index_topk`, so the batch is sharded with `sparse_mode 0`. All 8 answers are correct. Against #44320 alone the worst |Δlogprob| on shared tokens is 0.417, and the first-token differences are near-ties (the chosen token's logprob is −0.5 to −0.9). Two identically configured servers on this model differ by up to 0.68.

## Speed Tests and Profiling

GLM-5.2 W4A8, Ascend A3, tp16, dcp16, `--chunked-prefill-size 4096`, `--mem-fraction-static 0.72`. A 400k-token base is cached, then fresh tails are sent on top of it (TTFT, 2 requests each). The middle column is this branch with `SGLANG_NPU_ENABLE_DSA_TOKEN_SHARD=0`, which under DCP behaves as the parent PRs do without this commit:

| | #44320 alone | + #42977, #42978 (token shard off) | + this PR (token shard on) | this PR's change |
|---|---|---|---|---|
| cold 400k prefill (the warm-up) | 354.0 s | 173.8 s | 94.1 s | −46% |
| 4k tail on the cached base | 8.27–8.40 s | 3.94–4.07 s | 3.22–3.23 s | −19% |
| 16k tail on the cached base | 25.61–25.66 s | 10.17–10.19 s | 6.93–6.96 s | −32% |

No out-of-memory errors in any run. Every hit read 399,360 cached tokens.
