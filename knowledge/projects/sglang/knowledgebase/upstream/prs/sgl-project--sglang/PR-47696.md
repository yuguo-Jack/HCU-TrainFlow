# [Perf] diffusion: Run a single packed FA3 sequence through the batch kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47696) · state: open · merged: False

## Original PR description

## Motivation

On Hopper, `FlashAttentionImpl.forward_varlen` sends every packed call to FA3's varlen kernel. MiniMax-H3 packs one request into one sequence, padded at the tail (`cu_seqlens = (0, used, total)`). FA3 then runs the varlen template, which does extra indexing and picks a slower configuration for this shape.

The cuDNN SDPA backend already handles this case: `SDPAImpl.forward_varlen` folds equal segments that cover the query into one batch `forward()` call. This PR gives the FA3 path the same treatment.

## Modifications

`forward_varlen` (FA3 only, skip-softmax off) takes the batch kernel (`cu_seqlens=None`, the call `forward()` already makes) when the bounds hold one live sequence:

- `(0, total)`: the whole query.
- `(0, used, total)` with `packed_trailing_padding`: the live prefix, read by `trailing_padding_used_len`. Padding rows are zeroed, which is what the skip-softmax path already leaves there. No live row attends to them in either kernel.

Any other layout keeps the varlen kernel.

## Accuracy

Live rows are bit-identical to the varlen kernel: max |diff| = 0 on H200 at (0, 37742, 37760) and (0, 18000), with 56 heads and head_dim 128.

## Kernel (H200, 56 heads, head_dim 128, bf16)

| bounds | varlen | batch (this PR) |
|---|---|---|
| (0, 37742, 37760) | 61.65 ms | 60.16 ms |
| (0, 18000) | 14.51 ms | 13.58 ms |

## Tests

`test/unit/test_flash_attn_single_sequence.py` mocks the FA3 call and checks the routing:

- one sequence goes to the batch kernel;
- trailing padding runs only the live rows and zeroes the rest;
- several sequences keep the varlen kernel;
- padding without `packed_trailing_padding` keeps the varlen kernel.

- claude[bot] · comment · 2026-11-01T10:02:18Z · [source](https://github.com/sgl-project/sglang/pull/47696#discussion_r4435179936)

File: `python/sglang/multimodal_gen/runtime/layers/attention/backends/flash_attn.py` · line 645

🔴 On ROCm, or CUDA older than 12.3, single-sequence packed attention now returns uninitialized memory instead of attention output. The fast path checks only `fa_ver == 3` and depends on `out=` filling `output[:used]` from `new_empty`. It discards the call's return value. The FA2 fallback in flash_attention_v3.py ignores `out` and returns a fresh tensor. Fix: gate the fast path on `_is_fa3_supported()` (real sgl-kernel FA3), or copy the returned tensor into `output[:used]` when it is not the `out` buffer.

<details>
<summary>Why this was flagged</summary>

`fa_ver` defaults to 3 at flash_attn.py:310 and is only set to 4 on Blackwell/SM120 (cuda.py:752, sdpa.py:316). ROCm and Ampere boxes with CUDA < 12.3 run FlashAttentionBackend with fa_ver 3. On those, `_is_fa3_supported()` (flash_attention_v3.py:84-98) returns False, so `flash_attn_varlen_func` with `cu_seqlens_q=None` calls `fa2_flash_attn_func`. That call never receives `out` and returns a new tensor. The new branch at flash_attn.py:627-640 drops that return value and returns `output`. `output` was allocated with `query.new_empty` at :625, so its live rows `[:used]` are never written. Any packed varlen call with `cu_seqlens_host == (0, total)`, or trailing padding with `packed_trailing_padding`, then yields garbage attention and corrupted generations. On the base branch the varlen call's return value was returned directly, so the output was correct. The unit test mocks `flash_attn_varlen_func` to write into `out`, so it cannot catch this.

**Verification:** It fires on a CUDA setup where FlashAttentionBackend is picked with fa_ver==3 but `_is_fa3_supported()` is False. In flash_attention_v3.py:217-250, `out` is never passed, so the result is a fresh tensor that the new code drops. `output[:used]` stays as uninitialized `new_empty` memory. Base behaved correctly: the general path at flash_attn.py:641-653 uses the returned tensor.

</details>
