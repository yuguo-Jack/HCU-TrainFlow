# [Fix] rust-server: Answer health probes a busy scheduler skipped on the response ring

[Upstream PR](https://github.com/sgl-project/sglang/pull/45475) · state: closed · merged: True

## Original PR description

## Motivation

In Rust frontend mode (`SGLANG_RUST_SERVER=1`) a scheduler that is busy with a long prefill fails `/health_generate` even though it is alive, so a router in front of it marks a healthy engine unhealthy.

A busy scheduler skips health probes and acknowledges them after its next step. That acknowledgement is sent to the zmq tokenizer socket, which nothing reads in Rust mode:

- the Rust probe counts only decode-batch frames as scheduler activity, so it sees nothing until the prefill finishes and the probe times out;
- every skipped probe also queues one message on the unread socket, which is unbounded (`SNDHWM 0`).

## Modifications

- In Rust mode the scheduler pushes the acknowledgement onto the Rust response ring as a new bodiless frame, `DISPATCH_TAG_HEALTH_ACK` (`Server.push_health_ack` / `RustServer.push_health_ack`).
- The Rust dispatcher counts that frame as scheduler activity, the same way the Python `TokenizerManager` counts `HealthCheckOutput`.
- Rust probes share one heartbeat, so one acknowledgement per step answers every probe skipped so far; the scheduler clears its pending-probe queue instead of answering them one per step. A skipped probe now passes within one scheduler step. A single step longer than the client timeout still fails, by design.
- The Python frontend path is unchanged.
- Tests: `skipped_probe_passes_on_health_ack_and_cleans_up` replaces `healthy_probe_uses_shared_activity_and_cleans_up` in `handle.rs` and drives the probe through a real `Dispatcher` with an acknowledgement frame instead of bumping the counter by hand; `test/registered/unit/managers/test_scheduler_health_check_signal.py` pins the scheduler side for both modes (the Rust-mode case fails on `main`).
