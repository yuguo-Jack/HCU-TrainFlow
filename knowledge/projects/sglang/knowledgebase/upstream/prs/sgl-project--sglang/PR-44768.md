# [Fix] scheduler: Allow memory release with paused grammar compilation

[Upstream PR](https://github.com/sgl-project/sglang/pull/44768) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44744.

A retract pause leaves requests whose grammars are still compiling in the grammar queue. The paused scheduler stops polling that queue, but `release_memory_occupation` still treats it as active work even with `ignore_waiting=True`. A successful pause can therefore be followed by an assertion that kills the scheduler.

## Modifications

- Treat the grammar queue like the ordinary waiting queue when checking idleness with `ignore_waiting=True`.
- Preserve checks for requests that own KV rows and for outstanding HiCache operations.
- Keep the pending grammar future and request queued so compilation and generation can finish after memory is restored and generation continues.
- Add deterministic CPU regression coverage in the existing registered scheduler test file for the pause/release/resume lifecycle, KV ownership, and outstanding HiCache operations. The three added tests fail against the original code.

### Related work

- #32153 exempts the ordinary waiting queue after a retract pause, but leaves the grammar queue's emptiness requirement unchanged; its tests use an empty grammar queue.
- #36869 refactors idle-check diagnostics and still requires an empty grammar queue.
- #43896 changes request scanning; its current diff also retains the unconditional grammar-queue check.

This PR addresses the remaining grammar-compilation case in #44744. These PRs touch the same scheduler area, but their current changes do not fix this failure.

### A10 reproduction

Tested on one NVIDIA A10 (23 GB), Qwen/Qwen3-0.6B, Python 3.12, PyTorch 2.14.1, FlashInfer 0.7.1, and xgrammar 0.2.7. The original reproduction and GPU validation used the issue's revision, `7224fce1b`, plus this fix; the final branch is based on current main and was checked again with the CPU tests.

Server configuration:
```bash
python -m sglang.launch_server --model-path Qwen/Qwen3-0.6B \
  --enable-memory-saver --max-total-tokens 6000 --max-running-requests 32
# HiCache variant adds:
# --enable-hierarchical-cache --hicache-write-policy write_through
```

The unmodified revision reproduced the exact `release_memory_occupation should be called only when server is idle` assertion and scheduler exit on the first trial when a test-only hook held grammar compilation open for 500 ms. The hook signals when compilation starts before the client issues the pause; it is not part of the production patch.

After the fix:

| Configuration | Ordinary 5/10 ms pause timing | Compilation held open |
| --- | --- | --- |
| Without HiCache | 20/20 cycles passed | 20/20 cycles passed |
| HiCache write-through | 20/20 cycles passed | 20/20 cycles passed |

Each cycle exercised generate → retract pause → release memory → restore memory → continue generation. Every control call and resumed generation returned HTTP 200; no scheduler exception occurred.

The issue's 128-token output cap produced length-limited responses in these runs. Five additional bounded-schema cycles per configuration completed with valid JSON (10/10 total), separately checking resumed constrained generation rather than interpreting truncated JSON as a failure.
