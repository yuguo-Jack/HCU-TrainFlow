# [Fix] Benchmark: compute true peak concurrency via sweep line

[Upstream PR](https://github.com/sgl-project/sglang/pull/44323) · state: closed · merged: False

## Original PR description

## Background

Issue #44278.  `calculate_metrics` in `python/sglang/benchmark/serving.py`
computes `max_concurrent_requests` by building a per-second bucket
histogram — for each request it increments every integer-second bucket
from request start through request end (inclusive), then takes `np.max`.

## Problem

The bucket approach cannot recover actual overlap **within** a second.
Issue reproduction: five sequential non-overlapping requests with lifetimes
`[10.0000, 10.0625)`, `[10.1250, 10.1875)`, `[10.2500, 10.3125)`,
`[10.3750, 10.4375)`, `[10.5000, 10.5625)` — all touch the first
one-second bucket, so the old code reports **peak=5**.  The true maximum
simultaneous count is **1**.

The same issue also double-counts boundary handoffs — `[10, 11)` followed
by `[11, 12)` — because the range iterates `request_end_second + 1`.

## Solution

Replace the scalar peak with a **sweep line** over half-open `[start, end)`
intervals:

```python
events = [(start, +1), (end, -1) for each successful request]
events.sort()
running = peak = 0
for _, delta in events:
    running += delta
    peak = max(peak, running)
```

The per-second `concurrent_requests_per_second` array is **preserved**
for the existing `plot_throughput` output.  Only the scalar peak value
changes.

## Verification

Against the issue's reproduction example:

```
5 sequential non-overlapping requests — OLD peak=5, NEW peak=1 ✓
2 truly overlapping requests           — OLD peak=2, NEW peak=2 ✓
Boundary [0,1) + [1,2) half-open      — OLD peak=2, NEW peak=1 ✓
```
