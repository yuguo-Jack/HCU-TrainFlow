# [Feat] rust-server: Report cached_tokens and reasoning_tokens in meta_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/44531) · state: closed · merged: True

## Original PR description

## Motivation

The Python frontend reports `meta_info.cached_tokens` (prompt tokens served from the prefix cache) and `meta_info.reasoning_tokens` on every `/generate` frame, and usage accounting built on `/generate` reads cache hits from the first. The Rust frontend's `GenerateMetaInfo` carried neither, so a Rust-mode server reported no cache hits and no reasoning counts to its clients.

## Modifications

- The scheduler already counts both per request. In Rust mode the output streamer skipped them together with the fields only Python's detokenizer reads; it now records them for both frontends.
- The two counters ride the scheduler-to-Rust batch frame as two more core header columns after `tok_lens` (`BatchHeader` in `rust/sglang-server/src/message/response.rs` and `header_cols` in `python/sglang/srt/rust_server/server.py` change in lockstep). They are running totals, so each request's latest chunk value wins; `for_each_chunk` rejects a header whose new columns do not cover the batch, like the existing core columns.
- `GenerateMetaInfo` gains `cached_tokens` (uint32) and `reasoning_tokens` (uint64) in `proto/sglang/api/v1/generate.proto`. HTTP (unary, streaming, batch) and gRPC frames carry both on every frame, as the Python server does. The Rust and Python bindings are what `cargo gen-api` writes.
- Out of scope: OpenAI `usage.prompt_tokens_details.cached_tokens` (`--enable-cache-report`) and the remaining Python-only `meta_info` fields (`cached_tokens_details`, `queue_time`, speculative-decoding stats, `weight_version`). #40258 proposes a wider set of these fields over a different header encoding; this change is the smallest one that gets the two usage counters onto the wire.
