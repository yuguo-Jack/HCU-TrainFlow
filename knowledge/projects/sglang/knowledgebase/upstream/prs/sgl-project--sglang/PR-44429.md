# [Feat] wan2.2-s2v: Make the video API serve S2V

[Upstream PR](https://github.com/sgl-project/sglang/pull/44429) · state: open · merged: False

## Original PR description

`/v1/videos` rejected **every** Wan2.2-S2V request with

> `Served model with task type 'S2V' requires an 'audio_path' input`

Two independent registration gaps, both only on the served path — the CLI was unaffected because `diffusion_generator` calls the visual adjustment directly.

## Changes
- **`Wan2_2_S2V_14B_SamplingParam` declared no video request extra fields**, so `audio_path`, `pose_video_path` and `num_clip` were dropped from the request *before* validation — which then demanded the audio input that had just been discarded. Adds the `video_request_extra_fields()` override.
- **`ModelTaskType.S2V` was absent from `is_video_gen()`**, so the served path skipped `_adjust_visual_fields()`: the output file name kept no extension (ffmpeg: *"Unable to find a suitable output format"*) and the model's frame and fps defaults were never applied.

3 files, +53/−0.

## Why the second gap was reachable at all
`data_type()` returns `VIDEO` as its fallback, so S2V claimed VIDEO output while `is_video_gen()` denied it. The new test makes that class of mismatch impossible for *any* task, not just S2V:

```python
for task in Task:
    assert task.is_video_gen() is (task.data_type() is DataType.VIDEO)
```

## Testing
Three cases in `test/unit/test_multiple_task_types.py`: the invariant above, plus an S2V request driven through the real `video_api` router over both JSON and multipart.

## Base
⚠️ **Stacked on #43279** (the S2V port), included here as the first commit — S2V does not exist on `main` yet. Independent of #43288 and #44427: this touches only `configs/sample/wan.py` and `configs/task_type.py`, with **zero file overlap** with either. Merge after #43279, in any order with respect to the other two.
