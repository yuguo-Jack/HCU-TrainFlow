## Motivation
A lightweight alternative to https://github.com/sgl-project/sglang/pull/24580. This should address almost all race conditions caused by long ITL aborts.

Note: this PR cannot address the case when an ongoing prefill has already called a transfer sync that would take a very long time (maximum value -> mooncake timeout: 30s), but this case has an extremely low probability of happening (extremely hard to reproduce). We could introduce deferred release of decode-side KVCache to fix this as well, but this could harm the performance of the pre-allocation process of decode (considering this aborted req is a large ITL req that will occupy many many KVCache slots).

## Code Review

This pull request introduces a deferred KV cache release mechanism for decode-initiated aborts to prevent RDMA corruption from in-flight prefill writes. It implements an abort notification flow using ABORT and ABORT_ACK messages, along with a configurable grace period. The review feedback highlights a critical bug where an incorrect attribute name (decode_initiated_abort instead of abort_initiated) disables the deferred release mechanism. Additionally, the reviewer noted potential background thread crashes due to unvalidated message parsing and a potential memory leak from late-arriving ABORT_ACK messages.

File: `python/sglang/srt/disaggregation/decode.py` · line None

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The attribute `decode_initiated_abort` does not exist on `CommonKVReceiver`. In `CommonKVReceiver`, the attribute is named `abort_initiated` (initialized in `__init__` and set to `True` in `abort()`). Using `decode_initiated_abort` here will always return `False`, completely disabling the deferred KV cache release mechanism and leaving the system vulnerable to RDMA corruption on abort.

```suggestion
                is_decode_initiated_abort = getattr(
                    decode_req.kv_receiver, "abort_initiated", False
                )
```

File: `python/sglang/srt/disaggregation/mooncake/conn.py` · line 1408

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

Parsing the `ABORT` message directly without validation or error handling can crash the background `bootstrap_thread` if a malformed or incomplete message is received (e.g., raising `IndexError` or `ValueError`). It is safer to wrap the parsing logic in a `try-except` block and validate the length of `waiting_req_bytes` first.

```suggestion
                if room == "ABORT":
                    try:
                        if len(waiting_req_bytes) < 4:
                            logger.warning(f"Received malformed ABORT message with length {len(waiting_req_bytes)}")
                            continue
                        room_to_be_aborted = int(waiting_req_bytes[1].decode("ascii"))
                        decode_ip = waiting_req_bytes[2].decode("ascii")
                        decode_port = int(waiting_req_bytes[3].decode("ascii"))
                    except (IndexError, ValueError, UnicodeDecodeError) as e:
                        logger.error(f"Failed to parse ABORT message: {e}")
                        continue
```

Similarly, parsing the `ABORT_ACK` message directly without validation or error handling can crash the background `decode_thread` if a malformed message is received. Wrapping it in a `try-except` block makes the background thread more robust.

```suggestion
                if msg[0] == b"ABORT_ACK":
                    try:
                        ack_aborted_room = int(msg[1].decode("ascii"))
                    except (IndexError, ValueError, UnicodeDecodeError) as e:
                        logger.error(f"Failed to parse ABORT_ACK message: {e}")
                        continue
```

- gemini-code-assist[bot] · comment · 2026-06-05T09:57:36Z · [source](https://github.com/sgl-project/sglang/pull/27372#discussion_r3361876765)

File: `python/sglang/srt/disaggregation/decode.py` · line None

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

If an `ABORT_ACK` is delayed beyond the `abort_grace_period` (5 seconds by default), the deferred release entry will time out and be removed from `self.deferred_releases`. When the late `ABORT_ACK` finally arrives, it will be added to `self._abort_acked_rooms` but will never be discarded, leading to a slow memory leak over time. Consider implementing a periodic cleanup or maximum size limit for `self._abort_acked_rooms` to prevent unbounded growth.
