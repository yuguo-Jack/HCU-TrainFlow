# [Fix] epd: Accept tokens-in requests on scheduler-side transfer backends

[Upstream PR](https://github.com/sgl-project/sglang/pull/41376) · state: closed · merged: True

## Original PR description

## Motivation

With encoder disaggregation (EPD), a tokens-in multimodal request (`input_ids` plus `image_data`, no text) fails on the language server with HTTP 500 when the scheduler assembles the multimodal inputs. The `zmq_to_scheduler` and `mooncake` transfer backends and the gRPC zmq receiver all use this scheduler-side path. This affects a default EPD launch, because `--encoder-transfer-backend auto` picks `zmq_to_scheduler` for every model except Kimi-K3 with TP > 1. The scheduler stores `input_ids` as `array("q")`. A tokens-in request has no text (`None` over HTTP, `""` from the gRPC servicer), so the scheduler gives this array to the processor as the prompt. The shared base processor, which Qwen3-VL uses, reads a `list` prompt as token IDs and any other prompt as text, so the HF tokenizer gets the array as text and rejects it. #32541 added this fallback to `input_ids` without the `list()` conversion that the tokenized-input branch already has. `zmq_to_tokenizer` is not affected, because the tokenizer side already passes a list. This PR makes the scheduler side do the same.

## Modifications

- Scheduler-side EPD prompt selection converts `input_ids` to `list[int]` before it gives them to the processor.
- Text-in requests and processors that set `prefer_tokenized_input` keep the same behavior.
- A new unit test checks that a tokens-in prompt reaches the processor as a list, for `input_text=None` (HTTP) and `input_text=""` (gRPC).

## Accuracy Tests
