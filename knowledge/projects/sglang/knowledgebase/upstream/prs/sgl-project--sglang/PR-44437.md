# [Fix] mem_cache: Move FP4 MLA block scales with their KV in `move_kv_cache`

## Motivation

Speculative decoding relocates KV rows with `move_kv_cache`: accepted draft tokens are moved into place after verification (`spec_utils.py`, EAGLE with topk > 1 and NGRAM), and with page_size > 1 the prefix tail page is copied to each branch (`eagle_worker_common.py`). `MLATokenToKVPoolFP4` inherits `MLATokenToKVPool.move_kv_cache` (#26982), which copies `kv_buffer` rows only. Each moved FP4 latent is then dequantized with whatever block scales were left at its target slot, typically a rejected draft token's, and nothing reports an error.

The other quantized pools already move scales with their data (`MHATokenToKVPool`, `MHATokenToKVPoolMXFP8`, `DSATokenToKVPool`).

## Modifications

- `MLATokenToKVPoolFP4.move_kv_cache`: run the MLA move for the latent, then copy the `kv_scale_buffer` rows with the same indices.
- `test_quantized_kv_pool.py`: a CPU `MLATokenToKVPoolFP4` test that moves two slots and checks that data and scales arrive in every layer.

Out of scope: other methods inherited from `MLATokenToKVPool` also handle `kv_buffer` only (`get_cpu_copy`/`load_cpu_copy`, `get_contiguous_buf_infos`, the HiCache host pool, `get_kv_size_bytes`). As with MXFP8 (#35888, #35718), each needs its own PR.

## Accuracy Tests

Found by code inspection and verified at the unit level; not reproduced end to end, which needs an MLA model served with the FP4 KV cache and EAGLE topk > 1 or NGRAM decoding. The change only moves the scale rows of slots that the existing move already relocates.

- `python3 test/registered/unit/mem_cache/test_quantized_kv_pool.py`: OK (2 tests). On main the new test fails at the scale assertion.

## Speed Tests and Profiling

One extra gather and `index_put_` per layer per move, on `[n, kv_cache_dim / 16]` uint8 rows. Only moves on an FP4 MLA cache pay it.
