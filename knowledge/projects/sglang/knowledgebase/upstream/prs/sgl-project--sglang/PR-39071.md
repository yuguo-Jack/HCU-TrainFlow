# [Perf] [AMD] qknorm: Use the fused in-place QK norm kernel on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/39071) · state: open · merged: False

## Original PR description

## Motivation

`apply_qk_norm`'s fused in-place path is CUDA-only. On ROCm, `q`/`k` fall back to `reshape(-1, head_dim)`, and because they are slices of the fused QKV output (row stride `(num_heads + 2 * num_kv_heads) * head_dim`, e.g. 6144 for Qwen3-8B), that reshape is a full copy in every layer. The JIT `qknorm` kernel takes per-tensor strides and handles this layout without a copy, but it did not build on ROCm.

## Modifications

- `qknorm.cuh`: drop the `cuda_bf16.h` / `cuda_fp16.h` includes. `sgl_kernel/utils.cuh`, already included, provides them on CUDA and the `hip_*` equivalents on ROCm, so the CUDA build is unchanged. #40585 makes the same change to this file.
- `apply_qk_norm`: enable the fused path on HIP. `can_use_fused_inplace_qknorm` still falls back to the existing path if the kernel cannot be built.
- `apply_qk_norm`: return early on zero tokens. An idle DP-attention rank reaches the fused path with an empty batch, where `q.view(batch_size, -1, head_dim)` cannot infer the head count. CUDA takes this path on `main` as well.
- `VisionAttention`: take the JIT QK-norm branch only at TP=1. InternViT-6B (InternVL2.5-26B, InternVL3-38B/78B) normalizes across all heads, and under TP the branch saw only the local heads and skipped `_apply_qk_norm`'s all-gather. At TP=1 it is unchanged.
- `test_qknorm.py`: run on AMD CI, add a packed-QKV test for both launchers and an empty-batch test for `apply_qk_norm`. The AOT comparison stays CUDA-only because its reference, `sgl_kernel.rmsnorm`, is not in the ROCm build.

The launchers' ROCm device check (`kDLGPU`) is on `main` since #47300.

On ROCm the launcher keeps the one-row-per-warp kernel; the head_dim-128 two-rows-per-warp variant from #45214 is CUDA-only.

Unlike #21734 (reverted in #23159), the strided view only goes to the JIT kernel; the AITER RMSNorm fallback still gets the contiguous 2-D tensor.

Affected models are those that call `apply_qk_norm` on ROCm: Qwen3-MoE (its fused QK-norm + RoPE is CUDA/XPU-only), dense Qwen3, `glm4_moe`, `bailing_moe`, `sdar`, `laguna` and others. For dense Qwen3 with `SGLANG_USE_AITER=1`, decode already uses the aiter fused kernel from #44267, so only prefill and extend change. Llama 4 is unaffected: it calls `apply_qk_norm` only on CUDA.

## Accuracy Tests

Kernel on MI325X, built from this branch: for head_dim 64/128/256/512/1024 in bf16 and fp16, normalizing a strided fused-QKV slice gives bit-identical output to normalizing a contiguous copy, matches an fp32 reference (`atol=rtol=2e-2`), and leaves the V columns untouched. On `main`, the ROCm build fails (`'cuda_bf16.h' file not found`) and `can_use_fused_inplace_qknorm` returns `False`.

Kernel on MI355X, main `b960aa903a` with this PR: q/k views of a packed qkv for 10 per-rank geometries (Qwen3-8B, Qwen3-30B-A3B, Qwen3-0.6B, Qwen3-235B and GLM-4.5 at TP 8, head_dim 64 to 1024), 1 to 8192 tokens, bf16 and fp16, rows 16 B and 8 B aligned: 280 of 280 cases match a contiguous copy bit for bit and an fp32 reference (`atol=rtol=2e-2`) and leave V untouched, and the kernel replays correctly from a captured HIP graph. `apply_qk_norm` takes the fused path in place and matches the existing path within one bf16 ulp, with and without `SGLANG_USE_AITER=1`.
