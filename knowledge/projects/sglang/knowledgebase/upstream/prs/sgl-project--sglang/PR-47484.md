# [Fix] disaggregation: Back up separate draft KV pools in PD CPU retraction

[Upstream PR](https://github.com/sgl-project/sglang/pull/47484) · state: open · merged: False

## Original PR description

## Motivation

With `--disaggregation-decode-retraction-backup cpu_tensor`, a retracted PD decode request copies its KV to CPU and frees its slots. On resume it gets new slots, and the backup is written into them.

Only the target KV pool is backed up. EAGLE/EAGLE3, multi-layer EAGLE, DFLASH and DSPARK drafts that do not share the target pool keep their own KV tensors, indexed by the same token slots. Once another request reuses the freed slots, the resumed request's draft reads that request's KV. Drafts then come from the wrong context, so the acceptance rate drops. Output stays correct, because the target verifies every draft token.

The `host_pool` backend already moves draft KV through its pool transfers. `cpu_tensor` does not.

## Modifications

- `BaseSpecWorker.retraction_draft_pools()` returns the draft KV pools that a target-slot backup can carry: MHA pools with tensors of their own, indexed by the target's token slots. It skips:
  - fused drafts and drafts that write into the target pool, since the target backup already holds their KV;
  - pools shared by several draft runners, which are backed up once;
  - MLA pools, whose `get_cpu_copy` maps token ids to this DCP rank's rows;
  - the page-major MHA layout, which has no CPU copy.
- `DFlashWorkerV2` returns no pools when it uses the compact draft cache. That cache has its own request->token table, so its rows are not the target's slots.
- `Scheduler.init_memory_pools` registers these pools on the target allocator when the backend resolves to `cpu_tensor`.
- `Req.offload_kv_cache` and `load_kv_cache` copy every registered pool with the target KV. The copies are stored in `RetractionBackup.draft_cpu_tensors`.

## Accuracy Tests

The model forward is unchanged. Without this PR, a resumed request's draft reads another request's KV; that only lowers acceptance, because the target verifies every token. The unit test checks the restored draft KV directly.

## Speed Tests and Profiling

Retraction with `cpu_tensor` now also copies draft KV, roughly one extra copy per draft layer. Retraction is the slow path; other steps are unchanged.

## Tests

`test/registered/unit/mem_cache/test_retraction_draft_kv_backup.py` (new, CPU, 5 cases):

- A request with two draft pools (multi-layer EAGLE) is backed up through `backup_kv_cache`. Its slots are overwritten, and it is restored on different slots. The target KV and both draft pools hold the request's original KV.
- Without registration, the draft pools still hold the overwritten values after restore.
- Pool selection keeps a separate MHA draft pool once, and skips the target pool, fused drafts, page-major pools and MLA pools.
- DFLASH with the compact draft cache registers nothing; without the compact cache it registers its draft pool.

On `main`, 4 of the 5 cases fail. With this PR all 5 pass.

The fake allocator in `test_retraction_mamba_backup.py` gains a `retraction_draft_pools = ()` attribute.

`test_retraction_draft_kv_backup.py`, `test_retraction_mamba_backup.py`, `test_decode_retraction_backup.py` and `test/registered/unit/speculative/` on one GPU: 33 passed.
