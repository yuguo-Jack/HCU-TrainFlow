# [DSpark] Pick the static verify width per step

[Upstream PR](https://github.com/sgl-project/sglang/pull/42281) · state: closed · merged: False

## Original PR description

Split from #41994 as requested in review: the DSpark verify width part, which pays off from batch 64. The other parts are #42279 (batch < 64) and #42280 (`MinFreeSlotsDelayer`).

## Motivation

DSpark verifies `gamma + 1` tokens per request at every batch size. Past batch 8 the verify cost grows with verify tokens faster than the tail draft positions add accepted tokens, so a narrower verify commits more tokens per second.

`SGLANG_RAGGED_VERIFY_MODE=compact` selects a verify length for each request from the draft's confidence head. On main, it does not start DeepSeek-V4.1. The engram hasher (`engram.py`) and the V4.1 token-to-request mapping (`dsv41_sparse.token_req_indices`) expect the same verify length for each request. Thus compact stops at the engram assert during graph capture. #40567 changes both paths to accept different lengths. This change uses one width for all requests of a step, so the verify stays a dense `[bs, w]` block and those paths do not change. On our C1 workload on MI355X, this change is faster than compact with #40567 at batch 1-32 and 128, and equal at 64 and 256 (see below). That workload is narrow, and a re-evaluation is in preparation.

## Modifications

Off by default.

- `SGLANG_DSPARK_VERIFY_WIDTHS` (extra widths below `gamma + 1`, e.g. `3,4`) plus a diagonal SPS table (`--speculative-dspark-sps-table-path`, from `python -m sglang.benchmark.dspark_sps_profiler`) enables it. `SGLANG_DSPARK_FORCE_VERIFY_WIDTH` pins one captured width for A/B runs.
- After the full-width graphs, the worker builds a target attention backend, decode graphs and a verify epilogue for each extra width under a scoped `get_spec().override(speculative_num_draft_tokens=w)`, and swaps them onto the target model runner only around the verify forward. `model_runner.py` is unchanged.
- A step at width `w` verifies the anchor plus the first `w - 1` drafts of the unchanged proposal. Accept, commit and the folded epilogue run at width `w`, and the result carries `w` as its output row stride.
- The width maximizes predicted committed tokens per second: the expected accept length from decayed per-position acceptance, times the SPS table's steps per second at `bs * w` verify tokens, with a 2% switch margin. Acceptance counts come from a device histogram read with a fixed lag, so every TP rank picks the same width. The full width runs until every draft position is measured, and every 64th step after.
- Grammar, logprob and sampling-mask steps keep the full width. Unsupported setups fail at startup: non-static verify modes, attention DP, PP, mamba targets, `SGLANG_SIMULATE_ACC_LEN` and the DSpark debug observers. `accept_and_finalize` also takes #41981's `simulate_bonus_sampling_info`, which indexes `target_logits` by the step's width; with extra widths rejected under `SGLANG_SIMULATE_ACC_LEN`, that path behaves as on main.
- Enabling it needs an SPS table for the deployment, so the cookbook is unchanged here.

## Accuracy Tests

- Verify width off vs auto (`3,4`), 64 GSM8K questions per server: 63 and 63 off, 62 and 63 auto (63 and 63 off, 63 and 62 auto in an earlier session).
- A server with `SGLANG_DSPARK_FORCE_VERIFY_WIDTH=3` scores 62/64 on GSM8K.

### Compared with compact verify (#40567)

**Conclusion.** On our C1 workload, compact with #40567 is slower than static at batch 1-32 and at 128, and equal to this change at batch 64 and 256. The workload is narrow (see Data), so this does not show that compact is worse in general.

**Data.** We used one tree: main `57826a62ea` + #40567 (merged locally) + this change. Only the environment is different between the arms: static verify, `SGLANG_RAGGED_VERIFY_MODE=compact`, and `SGLANG_DSPARK_VERIFY_WIDTHS=3,4`. The cell, prompts and output length are the same as above. All arms use one MI355X SPS table built on that tree. Each run starts a new server, in the order static, compact, width, width, compact, static. Workload: each prompt is a 4K-token excerpt from four technical Markdown docs, followed by one of four analysis questions. Decoding is greedy, with ignore_eos and 1024 output tokens. B requests start at the same time. Compact runs without STS calibration. Decode tok/s change in the window where all requests decode, 95% interval:

| Batch | compact vs static | this change vs static | this change vs compact |
| ---: | ---: | ---: | ---: |
| 1 | -22.4% [-30.3, -15.0] | -2.0% [-5.3, -0.1] | +26.2% [+17.0, +37.3] |
| 8 | -13.7% [-14.9, -12.0] | +1.2% [-1.4, +4.4] | +17.3% [+15.2, +19.9] |
| 32 | -6.3% [-6.8, -6.0] | -0.5% [-1.3, +0.5] | +6.3% [+5.2, +7.4] |
| 64 | +6.4% [+5.1, +8.1] | +6.8% [+5.9, +7.8] | +0.4% [-0.4, +1.2] |
| 128 | -6.9% [-7.5, -6.0] | +6.2% [+5.9, +6.5] | +14.0% [+13.1, +14.7] |

At batch 256, we compare median TPOT, because without #42280 the 256 requests never decode at the same time. TPOT is 7.1% lower with compact and 7.0% lower with this change (this change vs compact +0.1% [-0.2, +0.7]). GSM8K (256 questions for each server): static 250 and 249, compact 247 and 250, this change 247 and 249.

**Analysis.** Compact makes each verify step faster from batch 32 (+29.8% cycles/s at batch 128, against +22.3% for this change). But it also removes more accepted tokens: at batch 128, the accept length is 2.32 with compact and 2.81 with this change. At batch 1, compact runs 16% fewer verify steps per second. On this workload (accept length about 3.2, almost the same for all requests), compact loses more in accepted tokens than it saves in verify time. Compact can be better on other workloads. We did not use an STS calibration table, and #40567 shows its gains on H20 PD decode with a low-acceptance input. The re-evaluation will follow the DSpark paper: SPEED-Bench and the paper's math, code and chat sets at temperature 1.0, STS calibration on a held-out split, and a concurrency sweep that reports throughput against tok/s/user.
