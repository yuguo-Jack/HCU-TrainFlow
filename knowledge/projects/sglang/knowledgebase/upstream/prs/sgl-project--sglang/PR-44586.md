# [CI] [AMD] muse-spark: Add a MI35x nightly GSM8K + MMMU accuracy gate

[Upstream PR](https://github.com/sgl-project/sglang/pull/44586) · state: open · merged: False

## Original PR description

## What

Adds a MI35x nightly accuracy gate for Muse Spark Open on the cookbook's MI355X / MXFP4 / Low Latency recipe:

- Test: `test/registered/amd/accuracy/mi35x/test_muse_spark_open_eval_mi35x.py`
- Suite: `nightly-amd-4-gpu-mi35x-muse-spark-open`
- Job: `nightly-4-gpu-mi35x-muse-spark-open` on `linux-mi35x-gpu-8` (TP4), 12600 s per-file cap

The server runs `amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4` with the recipe's flags: TP4/EP4, aiter attention at page size 16, `MUSE_MOE_BACKEND=flydsl`, DFlash2 with a Triton draft-attention backend, and the muse parsers. It runs full-split GSM8K through sgl-eval (thinking on, `reasoning_effort=xhigh`, 32768 max tokens, temperature 1.0, top_p 0.95) and 100 MMMU samples.

## Depends on

- [#44667](https://github.com/sgl-project/sglang/pull/44667), for the ROCm implementation (`sglang.srt.rocm_muse_spark`) and `3rdparty/amd/muse_spark/apply_aiter_patches.sh`. The model itself is on `main` via #44666, but without a ROCm path. This PR stays in draft until #44667 lands. (It originally depended on #44530, which was closed in favor of the split series.)
- The Muse Spark aiter patches applying to the aiter that `docker/rocm.Dockerfile` pins on `main` (now `285579b`). They were validated against `4ad9983`. Checked against `285579b` and its composable_kernel submodule (`96afae1`):
  - `01-aiter-fix-page-scatter-vm-fault.patch` does not apply. CK has since added a `page_block_size == 1` guard at the same spot in `fmha_batch_prefill_select_kv_load_mode`, but the page-size-16 case the patch fixes is still not handled there.
  - `03-plan-b-aiter-unified-attention-3d.patch` (aiter half) does not apply: `use_2d_kernel` in `unified_attention.py` was refactored. Sliding-window decode still takes the 2D kernel on the Triton path.
  - `04-aiter-muse-moe-flydsl.patch` applies.

  `apply_aiter_patches.sh` stops at the first failure, so until 01 and 03 are refreshed the job fails in its patch step, before the test runs.

## Why

On HIP, `muse_spark` dispatches to a separate ROCm implementation (`sglang.srt.rocm_muse_spark`) that no CI covers. MMMU is included because the model is multimodal and the image path through the ROCm implementation is otherwise untested.

## Notes for the reviewer

- **Aiter patches:** the job applies them to the CI image before the test, as the #44667 README describes for plain ROCm images. The Day-0 image has them baked in. So the nightly also fails when the patches stop applying to the pinned aiter.
- **Thresholds:**
  - GSM8K 0.93 and the sampling settings come from the B300 Muse Spark test (`test/registered/e2e/models/test_muse_spark_12_b300_pd.py`).
  - MMMU 0.50 is a placeholder with no AMD measurement behind it.
  - DFlash2 accept length is reported in the step summary but not gated.
- **Scope:** only the MXFP4 cell for now. The recipe's NVFP4 cell (`--quantization quark_mxfp4`) is not covered.

## Test plan

Not run on hardware yet. Once #44667 lands and the aiter patches apply, I will dispatch the job on all three images, set the MMMU threshold from the measured score, and post the runs here before marking this ready.

- The workflow parses with PyYAML, and the new job is in the `job_select` options and in `check-all-jobs.needs`.
- The test file compiles and is formatted with black/isort.
