# [AMD] Add a Muse Spark Open MI35x nightly GSM8K + MMMU accuracy gate

[Upstream PR](https://github.com/sgl-project/sglang/pull/44586) · state: open · merged: False

## Original PR description

## What

Adds a MI35x nightly accuracy gate for Muse Spark Open that covers both FP4 cells of the cookbook's MI355X / Low Latency recipe:

- Test: `test/registered/amd/accuracy/mi35x/test_muse_spark_open_eval_mi35x.py`
- Suite: `nightly-amd-4-gpu-mi35x-muse-spark-open`
- Job: `nightly-4-gpu-mi35x-muse-spark-open` on `linux-mi35x-gpu-8` (TP4), 21600 s per-file cap

The test has one class per checkpoint, each with its own server and the recipe's flags (TP4/EP4, aiter attention at page size 16, `MUSE_MOE_BACKEND=flydsl`, DFlash2 with a Triton draft-attention backend, muse parsers):

- MXFP4: `amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4`
- NVFP4: `meta-models/Muse-Spark-Open-816B-A42B-NVFP4` with `--quantization quark_mxfp4`, which requantizes to MXFP4 at load

Each server runs full-split GSM8K through sgl-eval (thinking on, `reasoning_effort=xhigh`, 32768 max tokens, temperature 1.0, top_p 0.95) and 100 MMMU samples.

## Depends on

- [#44530](https://github.com/sgl-project/sglang/pull/44530), for the model code and `3rdparty/amd/muse_spark/apply_aiter_patches.sh`. This PR stays in draft until it lands.
- The Muse Spark aiter patches applying to the aiter that `docker/rocm.Dockerfile` pins on `main` (`2bb5491`). They were validated against `4ad9983`. Against `2bb5491`, `04-aiter-muse-moe-flydsl.patch` applies, but the aiter half of `03-plan-b-aiter-unified-attention-3d.patch` does not (`aiter/ops/triton/attention/unified_attention.py:293`; that file has been refactored since). I did not check `01-aiter-fix-page-scatter-vm-fault.patch`, which targets the composable_kernel submodule. Until 03 applies, the job's patch step fails.

## Why

On HIP, `muse_spark` dispatches to a separate ROCm implementation (`sglang.srt.rocm_muse_spark`) that no CI covers. The NVFP4 cell takes a different load path from the MXFP4 one, so it gets its own server and gates. MMMU is included because the model is multimodal and the image path through the ROCm implementation is otherwise untested.

## Notes for the reviewer

- **Aiter patches:** the job applies them to the CI image before the test, as the #44530 README describes for plain ROCm images. The Day-0 image has them baked in. So the nightly also fails when the patches stop applying to the pinned aiter.
- **Thresholds:**
  - GSM8K 0.93 and the sampling settings come from the B300 Muse Spark test in #44530.
  - MMMU 0.50 is a placeholder with no AMD measurement behind it.
  - DFlash2 accept length is reported in the step summary but not gated.
- **Runner time:** it is one job because a single 8-GPU runner serves both checkpoints one after the other, at roughly 4 h.

## Test plan

Not run on hardware yet. Once #44530 lands and the aiter patches apply, I will dispatch the job on all three images, set the MMMU threshold from the measured score, and post the runs here before marking this ready.

- The workflow parses with PyYAML, and the new job is in the `job_select` options and in `check-all-jobs.needs`.
- The test file compiles and is formatted with black/isort.
