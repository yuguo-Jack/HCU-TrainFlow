# [Feat] observability: Log stats lines for idle steps on PD prefill and decode workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/45801) · state: open · merged: False

## Original PR description

## Motivation

TL;DR make post-processing of log lines be more accurate by inserting log lines even when server is idle. This is controlled by `SGLANG_LOG_IDLE_BATCH_STATS`, off by default which maintains previous behavior. Without idle logs, stats that can vary within the idle time (e.g., #transfer-req) is not visible. Furthermore, it is not possible to infer how large a time window a log line covers.

After PR:
<img width="3200" height="1440" alt="idle_logs_after_pr_t3" src="https://github.com/user-attachments/assets/ffaf6e98-c2c3-4cf7-a883-6cfb84d676bb" />

PD prefill and decode workers log a `Prefill batch` / `Decode batch` line only for forwards that do work. A worker with no forward to run, or such an attention-DP rank, prints nothing, though it can be in either of two states:

1. **Idle**: no requests exist.
2. **Blocked**: requests exist but wait on something other than compute. With the defaults (`early` decode allocation, no optimistic prefill), prefill starts a request only after decode has reserved KV cache for it. While the decode KV pool is full, new requests wait in the prefill bootstrap queue and the prefill worker has nothing to run.

Such waiting is worth observing because acting on it pays off. `--disaggregation-decode-allocation-policy prefill_complete` (#40703) reserves decode KV only after prefill, so requests compute instead of waiting for a decode slot; #45337 extends it to PP prefill and reports larger decode batches and higher throughput. Without this change, the logs show nothing in either state, and with `--enable-metrics` the Prometheus queue gauges refresh only every 30 s while idle. With it, the idle lines keep reporting `#bootstrap-req` (prefill) and `#prealloc-req` / `#transfer-req` (decode), so the logs show which state a worker is in and how long requests waited.

Line timing is the other half. Each line stands for the time since the previous line of its rank. Without lines while idle, any average over log lines over-weights busy periods, and analysis cannot tell idle time from missing data. Without a line right before the forward that ends an idle stretch, the first busy line's window also covers the idle time before it, which dilutes its throughput (see the sample below). Decode lines of attention-DP ranks also land on different forwards, because a rank does not count the idle forwards it runs in lockstep with busy peers. That makes it hard to match lines across ranks.

Example: a prefill worker busy for 1 s with 3 queued requests, then idle for 1 s. The mean `#queue-req` over its lines is 3.0 today; with this change it is about 1.5, the time average.

## Modifications

New env var `SGLANG_LOG_IDLE_BATCH_STATS` (default off, PD prefill and decode workers only). The line format is unchanged.

- **Idle-forward lines.** An attention-DP rank without work logs one prefill line per idle forward. On decode, idle forwards count toward `--decode-log-interval`, so every rank logs on the same forwards. A cache flush does not reset that count, since it reaches ranks at different forwards.
- **Timed lines.** While no forward runs, a line is logged once no line has been logged for an EMA of the recent gap between forward-paced lines (1 s before one is measured).
- **Idle boundaries.** A line is logged right before the forward that ends a stretch of timed lines (and before the first forward after startup); it reports no running requests, since none ran in its window. On decode, the first step without a forward closes the forwards since the previous line at once. An idle stretch long enough for a timed line therefore starts and ends at a line, and the first busy window after it holds only the forward, not the idle tail.
- **Line windows.** Each line covers the time since the previous line of its rank: its throughput and, with `SGLANG_ENABLE_METRICS_DEVICE_TIMER`, its occupancy.
- **Decode metrics with the flag on.**
  - Every decode line closes the window since the previous line and exports it, on ranks that log and on ranks that only export metrics. Decode gauges therefore stay current on idle attention-DP ranks and while the worker is idle.
  - Speculative acceptance gauges keep their last value through windows without speculative forwards.
  - `last_gen_throughput` (`/server_info`) keeps the last busy rate. When the worker goes idle, the `gen_throughput` gauge reads the rate of the last burst's tail, then 0.
  - `RECORD_STEP_TIME` records only windows of exactly `--decode-log-interval` forwards. The prefill and decode SoL hooks are not called for windows without work.
- **Independent of the flag.**
  - Retract-mode `pause_generation` now zeroes the exported `gen_throughput` gauge. The paused loop skips idle housekeeping, so nothing else replaced the last rate.
  - A decode export of a batch whose requests all finished reports `decode_sum_seq_lens` 0 instead of the batch's stale `seq_lens`.

With the flag off, logs and exports are unchanged apart from those two fixes.
