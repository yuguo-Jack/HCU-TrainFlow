## Motivation

Addresses the structural-tag half of #42269. With `tools`, `tool_choice="auto"` and a JSON `response_format`, `to_sampling_params` either drops the tool-call constraint ("Constrained decoding is not compatible with tool calls") or never builds one. The schema grammar then applies from the first token, so the model can never call a tool. Clients that send tools together with an output schema hit this on every request: codex `--output-schema`, and the OpenAI Agents SDK whenever an agent has both `output_type` and tools.

vLLM fixed the same bug in vllm-project/vllm#56086 with this approach.

## Modifications

- `serving_chat._tool_call_or_response_format_constraint`: under `tool_choice="auto"` with a JSON `response_format` (and no `regex`/`ebnf`), builds the **required-mode** tool-call structural tag from the parser. It is returned as a new constraint kind, `structural_tag_or_response_format`.
- `ChatCompletionRequest.to_sampling_params`: for that kind, emits one structural tag, `{"type": "or", "elements": [<tool-call format>, {"type": "json_schema", ...}]}`, in place of the bare `json_schema`. The model can make a well-formed tool call or answer in the schema, and nothing else.
- `ChatCompletionRequest.response_format_schema`: the existing response_format-to-schema logic, extracted unchanged so serving_chat and `to_sampling_params` share one predicate (including the kimi_k3 `strict=false` rule).
- `constrained.utils.structural_tag_format`: converts a legacy tag (hermes, llama3, mistral, deepseekv3, ...) to the `triggered_tags` format, the way `StructuralTag.from_legacy_structural_tag` does. Native tags (qwen3_coder, kimi_k2, ...) pass through.

Scope:
- Only the xgrammar backend compiles the `or` format; llguidance accepts only legacy tags. Other backends keep today's schema-only behavior.
- Parsers whose required mode has no structural tag (e.g. pythonic, which falls back to `json_schema`) also keep today's behavior.
- glm47 uses `full_assistant_ebnf` and is **not** changed here. The reporter's model needs a follow-up that unions the `required=True` GLM grammar with the schema grammar, with care around the thinking prefix.
- Response templates are skipped (when the reasoning parser is a `ResponseTemplateReasoningDetector` or the tool parser a `ResponseTemplateToolDetector`). They frame a JSON answer with the template's own grammar, which the `or` tag would replace.
- Both branches start at the answer (`thinking_mode=False`), because the schema branch has no reasoning prefix. With `--reasoning-parser` set, the reasoner backend still owns the think section, as before.

## Accuracy Tests

Not applicable: no kernel or model forward code changes. No GPU or end-to-end model run was done.

Unit tests, run on CPU (macOS arm64, Python 3.12, xgrammar 0.2.7, torch 2.15.0), rebased on 3a3a8611a4:
- New `test_auto_tool_choice_with_response_format_allows_tool_call_or_schema` (hermes = legacy tag, qwen3_coder = native tag) goes through `_process_messages` and then `to_sampling_params`, and compiles the result with xgrammar.
  - It accepts a tool call and schema JSON, and rejects free text and off-schema JSON.
  - **Fails on main** (both subtests: the tool call is rejected). Passes with this change.
- New `test_auto_tool_choice_with_response_format_keeps_schema_off_xgrammar`: with llguidance, the plain `json_schema` is kept.
- `test_serving_chat.py`, `test_protocol.py`, `test_responses_protocol.py`, `test_serving_completions.py`, `constrained/test_utils.py`, `constrained/test_reasoner_grammar_backend.py`, `function_call/test_function_call_parser.py` and `function_call/test_kimik3_structural_tag.py`: 613 passed, 2 failed. The same 2 fail on main in this environment (`test_inkling_scheduler_uses_native_reasoning_end` and the inkling subtest of `test_streaming_created_is_stable_across_chunks`); main has 611 passed.
- The union tag for hermes, llama3, mistral, deepseekv3, qwen3_coder and kimi_k2 also compiles through `XGrammarGrammarBackend.dispatch_structural_tag` (ad-hoc script, not committed).
