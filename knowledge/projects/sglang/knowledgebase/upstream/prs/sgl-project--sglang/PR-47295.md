# [Perf] cuda-graph: Upload each deduplicated executable on a private stream before its first launch

[Upstream PR](https://github.com/sgl-project/sglang/pull/47295) · state: closed · merged: True

## Original PR description

## Motivation

A CUDA graph executable that has never been launched is uploaded to the device implicitly by its first `cudaGraphLaunch`, through the launch stream. When that stream already has work queued, the implicit upload can block the host until the stream drains. A server that first-launches many executables while it is already serving traffic (for example when the dedup fallback keeps many graphs in separate executables) pays those stalls on the request path.

CUDA provides `cudaGraphUpload` to upload an executable ahead of its launch. Uploading every executable eagerly at capture or seal time would avoid the stalls but adds the full upload cost to startup, so this change uploads lazily instead, right before the first launch.

## Modifications

- `DedupedCudaGraphRegistry.replay` now uploads a group's executable with `cudaGraphUpload` before its first launch, on a private non-blocking stream created lazily by the registry. An event is recorded on that stream and the launch stream waits on it, so ordering is unchanged and the host does not block.
- `GraphExecGroup` gains an `uploaded` flag; the upload happens once per executable, at its first replay.
- `close()` destroys the private stream and event along with the executables.
- Capture, `register` and `seal` are untouched, so startup time is unchanged.
- `test_cuda_graph_dedup.py`: the shared-executable test now also asserts that two graphs sharing one executable upload it exactly once, at the first replay.

## Accuracy Tests

No change to kernels or outputs: the same executable is launched on the same stream, after an explicit upload that the implicit path would have done anyway. The unit test checks replay outputs are unchanged.

## Speed Tests and Profiling

Not a kernel change. The only runtime difference is where the one-time upload of each executable happens: on a private stream before the first launch instead of implicitly inside it, so the first replay of an executable no longer blocks the host behind work queued on the launch stream.
