# [Rust] Match Python's /model_info and /server_info in the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/42622) · state: closed · merged: False

## Original PR description

## Motivation

In Rust mode (`SGLANG_RUST_SERVER=1`), `/model_info` and `/server_info` diverge from the Python server:

- `/model_info` hard-codes `is_generation` and omits the capability fields, so clients see a text-only generation model whatever was loaded.
- `/server_info` omits the scheduler configuration and the startup timings that Python reports.

## Modifications

- `/model_info` reports `is_generation`, `has_image_understanding`, `has_audio_understanding`, `model_type` and `architectures` from the Python model config.
  - `tokenizer_path` stays the path the server was launched with, even when the scheduler's `rust_server_tokenizer_path()` gives the Rust tokenizer a different file.
- `/server_info` adds an allowlisted scheduler config at the top level and in `internal_states`, plus each scheduler's `startup_time` phase durations in `internal_states`.
  - The scheduler state also carries credentials and storage-backend options, so only listed fields are forwarded.
  - Its integers are signed, since launch arguments such as `hicache_size` accept nonpositive values.
  - There is no top-level `startup_time`: Python's includes the tokenizer manager's phase, which Rust mode does not have.
- `dp_size` and `attn_dp_size` stay unreported. Each DP rank has its own Rust listener, which ignores `data_parallel_rank`. A DP-aware client such as `sgl-model-gateway --dp-aware` would split one URL into virtual ranks that all reach one scheduler, so those clients keep failing at discovery, as they do today.
- VLM warmup stays on text `/generate` in Rust mode. Once `/model_info` reports image understanding, warmup would otherwise send an image chat request, which the Rust chat route rejects.
- For non-generation models: Rust mode doesn't serve them, and with this change the warmup's `/encode` request gets a 404 instead of the current scheduler crash. #42621 turns either into a clear startup error. The two PRs are independent.

## Tests

- `python -m pytest -q test/registered/unit/entrypoints/test_rust_server_dp_ports.py test/registered/unit/entrypoints/test_server_warmup.py test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py`: 22 passed.
- In `rust/`: `cargo test -p sglang-server` (334 passed), `cargo clippy -p sglang-server --all-targets -- -D warnings` and `cargo fmt --all -- --check` are clean.
- `pre-commit run --from-ref origin/main --to-ref HEAD`: all hooks pass.
- Real server on one A100 (Llama-3.2-1B-Instruct, `SGLANG_RUST_SERVER=1`), together with the related Rust-frontend PRs:
  - `/model_info` returns `is_generation: true`, `model_type: "llama"` and `architectures: ["LlamaForCausalLM"]`.
  - `/server_info` returns the scheduler config, for example `chunked_prefill_size: 8192`, `page_size: 1` and `hicache_size: 0`.
  - `internal_states[0].startup_time` has `load_weight`, `kv_cache_allocation`, `scheduler_e2e` and `cuda_graph`; there is no top-level `startup_time`.
