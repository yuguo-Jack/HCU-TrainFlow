# [Fix] Kimi-K3: Reject flashinfer_mxfp4 SiTU experts outside the SM100 family

[Upstream PR](https://github.com/sgl-project/sglang/pull/46392) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45755. On SM90 (and SM120), an explicit `--moe-runner-backend flashinfer_mxfp4` for Kimi-K3 loads and serves without any error, but the routed experts run GPT-OSS clamped SwiGLU instead of K3's SiTU. K3 passes its SiTU constants through `gemm1_alpha` / `gemm1_clamp_limit`, and `_process_weights_for_sm90_cutlass` reads them as SwiGLU scalars (`alpha=4.0`, `beta=1.0`, `limit=25.0`). `_kimi_k3_moe_runner_overrides` only picks this backend automatically on SM100/103/107, so only an explicit choice is affected.

## Modifications

- `arg_groups/model_overrides/kimi_k3.py`: when `moe_runner_backend == "flashinfer_mxfp4"` on a CUDA GPU outside the SM100 family (compute capability 10.x) and the checkpoint is MXFP4 with `hidden_act == "situ"`, raise at argument resolution, before any weights load, and point to `--moe-runner-backend marlin` (the cookbook's Hopper runner). The check mirrors `Mxfp4MoEMethod`'s kernel choice (`is_sm100` selects trtllm-gen), so SM90, SM120 and any architecture without a dedicated check are rejected, rather than listing SM90/SM120. This is fix 1 from the issue.
- `layers/quantization/mxfp4.py`: as a backstop, `Mxfp4MoEMethod.create_moe_runner` raises for a SiTU layer on the `cutlass_sm90` / `cutlass_sm120` kernels. `create_moe_runner` runs at layer construction, so this also fires before weight loading. It covers the opt-in W4A8 (`--flashinfer-mxfp4-moe-precision fp8`) path and SM120, which use the same kernels. This is fix 2 from the issue, placed one step earlier than `_process_weights_for_*`.
- SM100-family `trtllm_sm100`, which implements SiTU, and all non-SiTU models are unchanged.

Passing SiTU through to the CUTLASS kernel (fix 3 in the issue) is out of scope until flashinfer-ai/flashinfer#4209 lands.

## Accuracy Tests

The issue's "Not yet verified" item: a tensor-level check of the SM90 kernel output against SiTU.

1x H100 NVL (SM90), SGLang main `5971f47bc8`, torch 2.14.1+cu130, flashinfer 0.7.2 (+ `flashinfer-jit-cache` 0.7.2). A small MXFP4 MoE layer (8 experts, hidden 512, intermediate 256, top-2, 64 tokens, random weights) with K3's runner config (`activation="situ"`, `gemm1_alpha=4.0`, `gemm1_clamp_limit=25.0`, `gate_up_interleaved=False`) goes through `_process_weights_for_sm90_cutlass` and `_apply_sm90_cutlass`. The output is compared with two fp32 references computed from the same dequantized weights:

| input scale (gate / up std) | vs `SituAndMul(4.0, 25.0)` (what K3 needs) | vs GPT-OSS SwiGLU (alpha 4, beta 1, limit 25) |
|---|---|---|
| 0.84 / 0.85 | rel L2 1.53, cosine 0.63 | rel L2 0.0035, cosine 1.000 |
| 3.37 / 3.37 | rel L2 0.77, cosine 0.93 | rel L2 0.0036, cosine 1.000 |
| 13.5 / 13.4 | rel L2 3.31, cosine 0.90 | rel L2 0.0036, cosine 1.000 |

The SM90 path matches GPT-OSS SwiGLU to bf16 precision and does not match SiTU at any scale, which confirms the issue's formula-level analysis on the real kernel. The MoeRunner is built directly in this script, so it measures the kernel path on both main and this branch. With this PR, `create_moe_runner` refuses this configuration.

```python
"""Tensor-level check for sgl-project/sglang#45755 on one SM90 GPU.

Runs a small MXFP4 MoE layer with Kimi-K3's runner config (activation="situ",
gemm1_alpha=4.0, gemm1_clamp_limit=25.0, gate_up_interleaved=False) through
SGLang's SM90 FlashInfer CUTLASS path (_process_weights_for_sm90_cutlass +
_apply_sm90_cutlass), and compares the output with two fp32 references built
from the same dequantized weights:
  situ   - SituAndMul(beta=4, linear_beta=25), what K3 needs
  swiglu - GPT-OSS clamped SwiGLU with alpha=4, beta=1, limit=25
The MoeRunner is built directly, as SGLang's SM120 test does, so this runs on
both main and the fix branch (the fix only adds a guard in create_moe_runner).
"""

import json
import sys
from contextlib import nullcontext
from types import SimpleNamespace

import torch

import sglang.srt.layers.moe.moe_runner.flashinfer_cutlass as runner_module
from sglang.srt.layers.activation import SituAndMul
from sglang.srt.layers.moe.moe_runner.base import MoeRunnerConfig
from sglang.srt.layers.moe.moe_runner.runner import MoeRunner
from sglang.srt.layers.moe.token_dispatcher.standard import StandardDispatchOutput
from sglang.srt.layers.moe.topk import StandardTopKOutput
from sglang.srt.layers.moe.utils import MoeRunnerBackend
from sglang.srt.layers.quantization.mxfp4 import Mxfp4MoEMethod
from sglang.srt.runtime_context import get_context, get_parallel

assert torch.cuda.get_device_capability()[0] == 9, "needs SM90"
runner_module.use_symmetric_memory = lambda *a, **k: nullcontext()
runner_module.is_allocation_symmetric = lambda: False

E, K, N, TOP_K, T = 8, 512, 256, 2, 64  # experts, hidden, intermediate, top-k, tokens
dev = "cuda"
g = torch.Generator(device=dev).manual_seed(0)
E2M1 = torch.tensor([0, 0.5, 1, 1.5, 2, 3, 4, 6, -0.0, -0.5, -1, -1.5, -2, -3, -4, -6],
                    device=dev)


def dequant(packed, scale_u8):
    """[E, R, C/2] e2m1 (low nibble first) x [E, R, C/32] e8m0 -> fp32 [E, R, C]."""
    lo, hi = (packed & 0xF).long(), (packed >> 4).long()
    vals = torch.stack([E2M1[lo], E2M1[hi]], dim=-1).flatten(-2)
    scale = torch.exp2(scale_u8.float() - 127).repeat_interleave(32, dim=-1)
    return vals * scale


def rand_u8(shape, lo=0, hi=256):
    return torch.randint(lo, hi, shape, dtype=torch.uint8, device=dev, generator=g)


# K3 layout: gate_up_interleaved=False, i.e. w13 rows are [gate (N); up (N)].
w13, w2 = rand_u8((E, 2 * N, K // 2)), rand_u8((E, K, N // 2))
w13_s, w2_s = rand_u8((E, 2 * N, K // 32), 122, 126), rand_u8((E, K, N // 32), 122, 126)
W13, W2 = dequant(w13, w13_s), dequant(w2, w2_s)

layer = SimpleNamespace(
    w13_weight=torch.nn.Parameter(w13.clone(), requires_grad=False),
    w2_weight=torch.nn.Parameter(w2.clone(), requires_grad=False),
    w13_weight_scale=torch.nn.Parameter(w13_s.clone(), requires_grad=False),
    w2_weight_scale=torch.nn.Parameter(w2_s.clone(), requires_grad=False),
    w13_weight_bias=torch.nn.Parameter(
        torch.zeros(E, 2 * N, dtype=torch.bfloat16, device=dev), requires_grad=False),
    w2_weight_bias=torch.nn.Parameter(
        torch.zeros(E, K, dtype=torch.bfloat16, device=dev), requires_grad=False),
    num_local_experts=E, moe_tp_size=1, moe_tp_rank=0, moe_ep_size=1, moe_ep_rank=0,
)
method = Mxfp4MoEMethod.__new__(Mxfp4MoEMethod)
method._fi_kernel = "cutlass_sm90"
method._use_sm90_humming = False
method.num_experts = E
method.hidden_size = K
method.intermediate_size_per_partition = N
method._padded_hidden = K
method._padded_intermediate = N
config = MoeRunnerConfig(
    num_experts=E, num_local_experts=E, hidden_size=K,
    intermediate_size_per_partition=N, top_k=TOP_K, activation="situ", is_gated=True,
    gemm1_alpha=4.0, gemm1_clamp_limit=25.0, gate_up_interleaved=False,
)
config.layer = layer
layer.moe_runner_config = config
method.moe_runner_config = config
method.runner = MoeRunner(MoeRunnerBackend.FLASHINFER_MXFP4, config)
method._process_weights_for_sm90_cutlass(layer)
swiglu_params = {n: getattr(layer, n)[0].item()
                 for n in ("swiglu_alpha", "swiglu_beta", "swiglu_limit")}

results = {"gpu": torch.cuda.get_device_name(), "swiglu_params_built": swiglu_params,
           "rows": []}
for x_std in (0.25, 1.0, 4.0):
    x = (torch.randn(T, K, device=dev, generator=g) * x_std / K**0.5 * 8).bfloat16()
    logits = torch.randn(T, E, device=dev, generator=g)
    topk_w, topk_ids = torch.topk(torch.softmax(logits, -1), TOP_K, dim=-1)
    topk_w = topk_w / topk_w.sum(-1, keepdim=True)
    dispatch = StandardDispatchOutput(
        x, None, StandardTopKOutput(topk_w, topk_ids.to(torch.int32), logits))
    with get_parallel().override(tp_group=None), get_context().override_server_args():
        actual = method._apply_sm90_cutlass(layer, dispatch).hidden_states[:, :K].float()

    h = torch.einsum("tk,tsnk->tsn", x.float(), W13[topk_ids])  # [T, top_k, 2N]
    gate, up = h[..., :N], h[..., N:]
    act_situ = SituAndMul(beta=4.0, linear_beta=25.0).forward_native(h)
    gc, uc = gate.clamp(max=25.0), up.clamp(-25.0, 25.0)
    act_swiglu = gc * torch.sigmoid(4.0 * gc) * (uc + 1.0)
    row = {"x_std_scale": x_std, "gate_std": gate.std().item(), "up_std": up.std().item()}
    for name, act in (("situ", act_situ), ("swiglu", act_swiglu)):
        ref = torch.einsum("tsn,tskn,ts->tk", act.float(), W2[topk_ids], topk_w)
        rel = ((actual - ref).norm() / ref.norm()).item()
        cos = torch.nn.functional.cosine_similarity(actual.flatten(), ref.flatten(), 0)
        row[name] = {"rel_l2": round(rel, 4), "cosine": round(cos.item(), 4)}
    results["rows"].append(row)
    print(json.dumps(row))
json.dump(results, open(sys.argv[1] if len(sys.argv) > 1 else "sm90_situ.json", "w"),
          indent=1)
print("swiglu params built by SGLang for K3:", swiglu_params)
```

- xulunfan · comment · 2026-11-03T13:56:27Z · [source](https://github.com/sgl-project/sglang/pull/46392#issuecomment-6605701747)

Read this statically against `main` -- I have no K3 checkpoint on the GPUs I can reach -- and the premise holds up. Two things I would change, both small.

The arch-to-kernel split the comment claims is literally the same predicate: `Mxfp4MoEMethod.__init__` picks `trtllm_sm100` under `get_platform().is_sm100`, `cutlass_sm120` under `is_sm120`, `cutlass_sm90` under `is_sm90` (python/sglang/srt/layers/quantization/mxfp4.py:430-443), so gating the model-side reject on `not is_sm100` rejects exactly the devices that get a CUTLASS runner and no other. The field the reject reads is the field the layer is built from: `models/kimi_k3.py:515` passes `activation=config.hidden_act` into the routed-expert module. And the advice in the message is not a dead end -- the Marlin runner accepts gated `silu`/`situ` (python/sglang/srt/layers/moe/moe_runner/marlin.py:142-146) and MXFP4 Marlin is gated at SM90/SM100/SM120 (mxfp4.py:656-661), so "use --moe-runner-backend marlin" resolves on both arches the reject fires on.

I also checked whether the reject can fire on a config that would never have built the bad runner, since `create_moe_runner` early-returns for `use_mega_moe and is_flashinfer_mxfp4()` (mxfp4.py:1444-1448) and the mega call hard-codes `activation="situ"` (models/kimi_k3.py:873). It cannot: mega availability is `is_sm90_fp8_mega_moe_available`, which needs `_mega_moe_sm90_fp8_weights`, or `_device_sm // 10 == 10` (python/sglang/srt/layers/moe/mega_moe.py:169-172), so SM90/SM120 with an MXFP4 checkpoint does not reach that arm. No false positive there.

First change: `hf_config.text_config.hidden_act` is the only unconditional `.text_config` access in kimi_k3.py, and the helper called just above it is defensive about exactly this -- `_is_mxfp4_pack_quantized` does `getattr(getattr(hf_config, "text_config", hf_config), "quantization_config", None)` (python/sglang/srt/arg_groups/model_override_base.py:370-373). If a K3 export ships a flat config with no `text_config`, the reject turns into an `AttributeError` during config resolution on SM90/SM120, which is a worse failure than the one being prevented: the attribute access happens before the `!= "situ"` test, so it also breaks the non-SiTU checkpoint that this guard is written to let through. The same `getattr(hf_config, "text_config", hf_config)` idiom would match the neighbour. The new unit test only feeds configs built with `text_config=SimpleNamespace(...)`, so nothing pins either shape.

Second change: the message says the experts "would run ... with GPT-OSS SwiGLU", which is true for SM90 and SM120 but not for the arch the test uses as a stand-in. For a `device_sm` outside {90, 10x, 120} the `_fi_kernel` selection already raises "moe_runner_backend=flashinfer_mxfp4 requires SM90, SM100, or SM120" (mxfp4.py:444-448), so on SM110 the new guard preempts a message that was accurate and replaces it with one describing a kernel that would never have been chosen. Either drop SM110 from the expected-reject list, or narrow the model-side guard to `is_sm90 or is_sm120` and let the existing `NotImplementedError` cover the rest. Keeping the `NotImplementedError` keyed on `_fi_kernel != "trtllm_sm100"` rather than an allow-list is the right default-deny, and it stays correct if a kernel name is added later.

One scoping note that matters before merging a startup-time raise: on `main` the auto default resolves to `flashinfer_mxfp4` for Kimi-K3 only when `is_sm100 and device_sm in (100, 103, 107)` (python/sglang/srt/arg_groups/model_overrides/kimi_k3.py:187-197), so on SM90/SM120 this reject is reachable only by someone who typed the flag -- no default launch turns into a hard failure. And because it keys on `hidden_act == "situ"`, non-SiTU MXFP4 MoE checkpoints are untouched, which is the population that currently exercises `cutlass_sm90` and `cutlass_sm120` in production.

Happy to re-run these checks against whatever you push.
