# [Fix] scheduler: Reserve only the remaining decode when re-admitting a retracted request

[Upstream PR](https://github.com/sgl-project/sglang/pull/46352) · state: open · merged: False

## Original PR description

## Motivation

After a decode OOM retraction, a retracted request is re-admitted by re-prefilling its prompt plus the tokens it already generated. Admission then reserves its full `max_new_tokens` of decode headroom again, so those tokens are counted twice. The pass that re-admits it can end with NO_TOKEN, and fresh requests behind it wait for a later pass although the pool has room. With 8000 free tokens, a retracted request (1000 prompt, 3000 generated, `max_new_tokens=4000`) is charged 8001, and a 1500 + 500 request that fits beside it is refused.

## Modifications

The gate in `add_one_req` (python/sglang/srt/managers/schedule_policy.py:1363) already charges min(max(max_new_tokens - generated, 0), CLIP), the same formula as `_swa_new_tokens`. The commit (schedule_policy.py:1571) and the other admission paths charged min(max_new_tokens, CLIP). This renames `_swa_new_tokens` to `_remaining_new_tokens` and uses it wherever future decode is priced: whole and last-chunk commits, the ignore_eos path, dLLM staging, the HiCache load-back reshape, the running-batch offset, and the priority-preemption demand.

Requests with no output, or more than CLIP (4096) tokens from their limit, are charged as before. Two sites change for requests that were never retracted: dLLM staging rows, which return through admission every block, now reserve what they have left; and the running-batch offset is clamped at zero.

#35488 adds the same formula as `remaining_max_new` for HiSparse; whichever lands second can drop its copy.

## Accuracy Tests

Three cases in `test/registered/unit/managers/test_prefill_adder.py`: the example above; each admission path (whole, last chunk, ignore_eos, load-back, dLLM) reserving max_new_tokens minus generated output for fresh and retracted requests; and preemption sizing a retracted newcomer.

- Production change reverted: `NO_TOKEN != CONTINUE`, `8 != 2` on each retracted path, preemption returns False (the fresh cases pass). The existing helper test, renamed with the helper, fails there with `AttributeError`.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Refresh retracted input before estimating preemption demand**

For a retracted request with HiCache/LmCache prefetching disabled, `full_untruncated_fill_ids` can still contain only the last prefill: `reset_for_retract()` does not refresh it, and `scheduler.py` invokes preemption before `init_next_round_input()`. Subtracting generated output here therefore undercounts demand; a 100-token prompt with 900 outputs and a 1000-token generation limit is priced at 200 tokens although re-admission needs 1100. This lets preemption return `True` after releasing too few victims, then admission returns `NO_TOKEN`, needlessly retracting running requests without scheduling the higher-priority request. Refresh the fill IDs before sizing, or derive the current input length from the prompt plus output.
