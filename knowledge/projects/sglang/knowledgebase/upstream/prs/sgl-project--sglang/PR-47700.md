# Fix PP disaggregated decode race condition (#47613)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47700) · state: open · merged: False

## Original PR description

## Summary

Fixes a race condition in pipeline parallelism disaggregated decode that caused garbage output (runs of token 0) when `pp_async_batch_depth > pp_size / 2`.

### Root Cause

In `event_loop_pp_disagg_decode`, the downstream stage receives proxy tensors in `_pp_recv_proxy_tensors`, which allocates them with `torch.empty` on the PP comm/schedule stream. The forward stream then reads them. However, the caching allocator only tracks the allocating stream, so once the scheduler drops the Python reference (by setting `pp_proxy_tensors = None` before the next recv), the memory block goes back to the pool even if the forward that reads it has not executed yet.

With enough microbatches in flight (`pp_async_batch_depth > pp_size / 2`), the next recv can get the same block and overwrite it while the previous forward is still queued. That forward then reads another microbatch's hidden states, the logits go bad, and sampling lands on token 0.

### Fix

Call `record_stream()` on each received tensor with the forward stream in `_pp_recv_proxy_tensors`. This tells the caching allocator that these tensors are also used on the forward stream, so the memory is not recycled while queued work is still in flight after Python refs drop.

### Validation

This fix matches the approach described in #47613 which was validated by the issue author:
- PP2×TP4, depth 2: 73/192 affected requests before the fix → 0/192 after
- PP2×TP4, depth 3: 109/192 → 0/192
- PP2×TP4+DCP4, depth 2: 0/192, 0/2560, and 0/3840 affected requests at C64/C256/C384

Fixes: #47613
