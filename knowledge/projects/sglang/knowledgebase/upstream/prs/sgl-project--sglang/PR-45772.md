# [Fix] encoder: allocate embedding cache resources only on rank 0

[Upstream PR](https://github.com/sgl-project/sglang/pull/45772) · state: open · merged: False

## Original PR description

Fixes #45770.

## Motivation

With the global multimodal embedding cache enabled, every encoder TP rank
currently creates an embedding storage backend and an `EmbeddingCacheController`.
Each controller allocates and registers its own vision/audio pinned host pools
with a default combined budget of 4 GiB, and starts a cache I/O thread.

The encoder's cache-data path is already owned by rank 0: it performs lookup,
prefetch, staging, output assembly, and insertion. Other ranks participate in
cache-mask broadcasts and model computation for misses. Cached embeddings are
final encoder outputs, so those ranks do not need a copy of the cached data to
skip the corresponding forward computation. Their independently allocated
host pools therefore remain idle.

This change limits cache-data resources to rank 0 while preserving collective
participation on all encoder ranks.

## Modifications

### 1. Separate shared coordination from cache resource ownership

Move cache initialization into `MMEncoder._init_global_cache()`. It initializes
`mm_global_cache_enabled` on every rank and starts with no local controller or
cache coordination group. When caching is disabled, initialization returns at
that point.

For TP greater than one, every rank first participates in creating
`global_cache_tp_group`. Its membership comes from the existing TP CPU group,
and it uses Gloo for the CPU hit/fallback masks. Group creation happens before
the nonzero-rank return because it is a collective operation.

Only rank 0 then constructs the storage backend and `EmbeddingCacheController`.
Consequently, only rank 0 allocates/registers the host pools and starts the
controller's I/O thread. The existing embedding dimensions and model dtype
are passed through to that controller.

### 2. Keep nonzero ranks in the cache execution path

Previously, `batch_encode()` selected the cache path based on whether
`self.mm_global_cache` existed. After restricting controller ownership to
rank 0, that condition would cause other ranks to bypass cache coordination.

Select the path using the shared enabled flag instead:

```python
use_global_cache = self.mm_global_cache_enabled and not is_health_check
```

All ranks therefore enter the same cache flow even when nonzero ranks have
`mm_global_cache=None`. Health probes retain their existing cache bypass.

### 3. Give mask broadcasts their own encoder-owned group

Update `_broadcast_global_cache_mask()` to use `global_cache_tp_group` rather
than obtain a group through the local controller. Both the initial hit mask
and the later fallback mask remain available to every rank.

The controller now creates its internal `prefetch_tp_group` only when
`all_rank_get=True` and TP is greater than one. The encoder passes
`all_rank_get=False`, so constructing its controller on rank 0 no longer
invokes group creation that would also require the other ranks. Callers using
`all_rank_get=True` retain the controller group and the prefetch-completion
`all_reduce(MIN)` synchronization.

### 4. Preserve the existing request-level flow

Rank 0 determines cache hits and broadcasts the hit mask. All ranks compute
the same missing items while rank 0 prefetches the hits. Rank 0 then broadcasts
the fallback mask so that failed cache loads are recomputed consistently.
Only rank 0 assembles the complete embedding and stages it for downstream
delivery.

For example, if A is cached and B is missing, every rank computes only B;
rank 0 loads A and assembles `[A, B]`. If loading A fails, the fallback mask
makes every rank compute A before rank 0 assembles the result.

Pool paging, eviction, GET/PUT, host/device copying, and assembly algorithms
keep their existing implementations. Cache flags, default capacity, and
backend selection also retain their existing behavior.

## Memory impact

With the existing 4 GiB pool budget, aggregate embedding-pool capacity per
encoder instance is expected to change as follows:

| Encoder TP | Before | After | Expected reduction |
| --- | --- | --- | --- |
| 1 | approximately 4 GiB | approximately 4 GiB | 0 |
| 2 | approximately 8 GiB | approximately 4 GiB | approximately 4 GiB |
| 8 | approximately 32 GiB | approximately 4 GiB | approximately 28 GiB |

These are configured pool-capacity estimates, subject to page rounding.
Additional backend memory is excluded. Each independent encoder instance
retains its own rank 0 pool.
