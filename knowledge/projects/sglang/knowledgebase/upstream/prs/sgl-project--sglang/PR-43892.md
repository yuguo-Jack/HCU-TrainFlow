# [router] Disable reqwest's default 30 s TCP_USER_TIMEOUT on upstream sockets

[Upstream PR](https://github.com/sgl-project/sglang/pull/43892) · state: open · merged: False

## Original PR description

## What changes

**Before:** the router's shared upstream HTTP client inherits reqwest 0.12's default `TCP_USER_TIMEOUT` of 30 s on Linux. The kernel aborts a router-to-worker connection when the data the router sent stays unacknowledged for 30 s. This also happens when the worker is alive but reads a large request body slowly and advertises a zero receive window.

**After:** the router does not set `TCP_USER_TIMEOUT` on upstream sockets. A worker that is slow to read a request body no longer loses the connection after 30 s. `request_timeout_secs` still bounds each request.

**Who sees it:** router deployments where a worker reads large request bodies slowly. The clearest case is PD disaggregation with one decode engine under burst load. The decode HTTP process tokenizes each long prompt on its event loop. During a burst it stops reading sockets for more than 30 s.

**Why it matters in PD mode:** `execute_dual_dispatch_internal` sends the prefill and decode requests concurrently and waits for the prefill. When the kernel aborts the decode socket, the router stores the decode error and keeps waiting. The prefill engine waits in its bootstrap queue for a decode engine that never got the request. The request hangs until `SGLANG_DISAGGREGATION_BOOTSTRAP_TIMEOUT` expires. Only then does the router log `Decode request failed ... error sending request`.

**Measured evidence** (MI355X, 3 prefill engines and 1 decode engine at TP2 on two nodes, GLM-5.3-Flash MXFP4, agentic benchmark with long multi-turn prompts, concurrency 160, sglang-router 0.3.2 built with reqwest 0.12.28 and hyper-util 0.1.20):
- 279 new requests arrived in one second. Exactly 31 s later, the router logged `hyper::Error(BodyWrite, Os { code: 32, kind: BrokenPipe })` on 40 decode connections in the same second. The router was still writing their request bodies.
- On the router node, `TcpExtTCPAbortOnTimeout` rose by 53, which equals the number of stuck requests. In a second run, 38 router-to-decode sockets were in `timer:(persist)` (zero-window probing), each with about 88 KB sent and `lastsnd` near 30 000 ms. One second later the counter rose by 33.
- The decode node showed no listen overflows and no aborts of its own. A `py-spy` dump of the decode HTTP process showed the event loop in `serving_chat._render_and_encode_chat_template` (HF tokenizer `encode`).
- The stuck requests stayed in the prefill bootstrap queue until the 900 s bootstrap timeout. Then the benchmark aborted its warmup.
- A CPU-only test between two Linux 6.8 hosts sent 64 MB to a receiver that did not read for 90 s. With keepalive 30/15/3 and `TCP_USER_TIMEOUT` 30000 ms, the send failed with `ETIMEDOUT` at 30.3 s and `TcpExtTCPAbortOnTimeout` rose by 1. With the same keepalive and no `TCP_USER_TIMEOUT`, the sender completed when the receiver started to read.
- With two decode engines, each decode process reads half of the burst, and no requests got stuck in the same benchmark.

**Performance:** not measured. This change only removes a socket option, and it does not change routing.

## Implementation

`sgl-model-gateway/src/app_context.rs`: after the client builder settings, call `client_builder.tcp_user_timeout(None)` under `#[cfg(any(target_os = "android", target_os = "fuchsia", target_os = "linux"))]`. These are the targets where reqwest exposes the option and sets the default. Other platforms are unchanged.

A separate issue remains for a follow-up. When the decode send fails at the transport level before the prefill returns, the PD router could fail the request at once instead of waiting for the prefill. This PR does not change that path.
