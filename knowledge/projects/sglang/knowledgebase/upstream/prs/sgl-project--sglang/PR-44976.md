# [Fix] kimi-k3: Avoid symm-mem deadlock in shared experts

[Upstream PR](https://github.com/sgl-project/sglang/pull/44976) · state: open · merged: False

## Original PR description

## Motivation

On Kimi-K3 with an EP all-to-all MoE backend and `--enable-symm-mem`, startup intermittently deadlocks: the engine stops making progress during warmup and, when a MegaMoE kernel is in flight, is torn down one barrier timeout later by `DeepGEMM grid sync timeout`. This is the same stall reported in #36943, reached through a different path. The path is a Kimi-K3-specific allocation: the tp1 shared-expert output is taken from the symmetric-memory pool on a side stream, which lets the ranks grow the pool differently and then disagree on the window-registration collective. This PR stops allocating that tensor from the symmetric pool.

### Who is affected

All of the following must hold; all of them are the defaults for this setup:

- Kimi-K3 on CUDA (the side streams are not created on HIP).
- An EP all-to-all MoE backend (`megamoe`, `flashinfer_megamoe`, `deepep`, `mooncake`, `ascend_fuseep`, `mori`), so the shared experts are replicated per rank (`_shared_experts_tp1`: the default, i.e. `--shared-experts-tp-size` unset or 1 and shared-expert attention TP off) and run with single-batch overlap on the side stream (`_sbo_shared_overlap`).
- `--enable-symm-mem`.

It was reproduced and verified with `megamoe`. The rank-divergent registration itself does not depend on the MoE backend: with another backend the ranks would still issue mismatched registration collectives, only the second waiter would differ.

### Impact

- The engine stops with no error. Every rank is blocked, either in `ncclCommWindowRegister` or spinning in the MegaMoE kernel's cross-rank barrier. Nothing is logged until DeepGEMM's barrier timeout fires, after which every scheduler aborts and the server exits.
- If no MegaMoE kernel is in flight when the ranks diverge (for example when the extra segment is registered together with the startup prealloc), nothing ever times out and the engine stays blocked with no error - the form reported in #36943.
- It hits before the server becomes ready, so an affected deployment fails to come up, and a restart has the same chance of failing again. We also saw a hang with the same signature on a server that had already reported ready, on a later request, so it is not confined to warmup.

### How often

On one node (8x B30Z, SGLang 0.5.21, TP8/EP8, MegaMoE, cold Triton cache), 13 of 42 unfixed starts hung. The rate drifted between sessions, from 0 of 10 to 4 of 10 consecutive starts, with no code or config change, because whether it triggers depends on each rank's own CPU/GPU timing (see below).

### Mechanism

1. `RowParallelLinear.forward` always allocates its output from the symmetric-memory pool.
2. Kimi-K3's tp1 shared experts (`parallel_group="replicated"`) never feed a collective; their output is complete per rank. Under single-batch overlap they run on the MoE side stream, and the result is `record_stream`-ed onto the forward stream where it is consumed.
3. A block that was `record_stream`-ed only returns to the caching allocator's free list once the event recorded on that stream has completed. Whether the next layer's side-stream allocation can reuse the previous block therefore depends on how far that rank's GPU has progressed. A side-stream allocation also cannot use the forward-stream prealloc, so when reuse fails the pool grows a new segment, and different ranks can decide differently at the same layer.
4. A registration round issues the `ncclCommWindowRegister` collective only for segments the comm has not seen yet. When only some ranks grew, those ranks block in the registration collective while the others proceed and launch the MegaMoE kernel, whose cross-rank barrier waits for the blocked ranks. Neither side can finish.

## Modifications

- `RowParallelLinear` gains a keyword-only `symmetric_output: bool = True`. When it is `False`, the output is allocated normally instead of from the symmetric pool; reduction behavior is unchanged. The default keeps the current behavior for every existing caller, including the replicated layers that `test_replicated_model_mlps_keep_weights_and_tp_output_allocation` pins.
- `KimiK3MLP` forwards the flag, and `KimiK3MoE` builds its shared experts with `symmetric_output=not self._shared_experts_tp1`. TP-sharded shared experts, which are reduced afterwards, keep the symmetric output.

The symmetric allocation brought nothing to the tp1 shared-expert output, since that tensor never enters a collective. Other models that run a replicated `RowParallelLinear` on a side stream could hit the same race; this PR only changes Kimi-K3, where it was reproduced and verified, and leaves the opt-out available for others.

### What this buys

- The deadlock path is removed: with the fix, the side stream no longer allocates from the symmetric pool, so no rank-local pool growth can reach the registration collective.
- The symmetric pool stops growing after the prealloc. In every fixed start all ranks ended at 6 segments / 4.19 GiB, against 8 segments / 4.21 GiB without the fix.
- No behavior change elsewhere: the flag defaults to the current behavior and only Kimi-K3's tp1 shared experts turn it off.

## Verification

Every start logged each pool growth with its rank, segment count and size, so a hang can be matched to the per-rank pool state. All runs: SGLang 0.5.21, 8x B30Z, TP8/EP8, `--moe-a2a-backend megamoe`, `--enable-symm-mem`, cold Triton cache, the fix back-ported unchanged, unfixed and fixed starts alternating so that drift affects both arms equally.

1. Deterministic reproduction. A test-only patch (not part of this PR) keeps the first 16 side-stream shared-expert outputs alive on one rank (rank 3), so that rank cannot reuse those blocks while the others can - the condition in step 3 above, made certain instead of timing-dependent.

   | arm | starts | hung | per-rank pool at the end |
   | --- | --- | --- | --- |
   | unfixed + trigger | 10 | 10 | rank 3 one segment ahead of the other 7 ranks in every start |
   | fixed + trigger | 10 | 0 | all 8 ranks at 6 segments / 4.19 GiB in every start |

   The chance that all 10 hangs fall in the unfixed arm by luck is 1 / C(20,10), about 5e-6. 8 of the 10 unfixed starts hung in the first warmup request, the same place as the natural hangs, and ended in `DeepGEMM grid sync timeout`; in the other 2 the extra segment was registered together with the startup prealloc, before any MegaMoE kernel was in flight, and the engine stayed blocked with no error for 15 minutes until the harness stopped it.

2. Natural reproduction, no trigger:

   | arm | starts | hung | per-rank pool at the end |
   | --- | --- | --- | --- |
   | unfixed | 10 | 4 | hung starts: segment growth on only some ranks (e.g. 7 ranks at 7 segments, 1 rank at 8); clean starts: 8 segments / 4.21 GiB on all ranks |
   | fixed | 10 | 0 | all 8 ranks at 6 segments / 4.19 GiB in every start |

   Across all unfixed runs, every hung start had a per-rank segment-count mismatch and every clean start had matching counts.

3. Unit tests (CPU), on `main`:
   - `test/registered/unit/layers/test_linear_parallel_groups.py::test_row_symmetric_output_opt_out_skips_only_the_allocation`: with `symmetric_output=False` the layer does not enter `use_symmetric_memory`, for both a TP-sharded and a replicated layer and with either reduce group, while its output and reduction stay the same. The existing `test_replicated_model_mlps_keep_weights_and_tp_output_allocation` still pins the default symmetric allocation.
   - `test/registered/unit/layers/test_kimi_mlp_parallel_groups.py`: a directly built Kimi MLP keeps the default, and the MoE shared experts opt out exactly when they are tp1. This assertion fails if the `kimi_k3.py` change is reverted.

   ```bash
   python3 -m pytest test/registered/unit/layers/test_linear_parallel_groups.py \
       test/registered/unit/layers/test_kimi_mlp_parallel_groups.py -q
   ```

   17 tests passed (77 subtests).
