# [Perf] [Intel] gemma4: Fuse greedy verification logits finalization

[Upstream PR](https://github.com/sgl-project/sglang/pull/44884) · state: open · merged: False

## Original PR description

Stacked on #44869; the performance comparison uses that parent branch as its control.

## Motivation

Gemma4 MTP verification on Intel XPU converts BF16 vocabulary logits to FP32, softcaps them, and reduces them to greedy token IDs. Fuse this finalization into two reductions over the existing BF16 head output for eligible greedy verification batches. Model weights and the head GEMM remain unchanged.

## Modifications

- Add an XPU BF16 `sampling.softcap_argmax` kernel with Meta support. Preserve FP32 softcap ordering, saturation ties, first-index tie breaking, and nonfinite handling.
- Let Gemma4 defer FP32 conversion and softcap for local no-gather FrozenKV target verification. Preserve and slice deferred output through graph replay, then check the current sampling requirements after replay.
- Use compact token IDs only for eligible greedy requests. Restore ordinary logits through the original softcap helper for logprobs, sampling, penalties, bias, grammar, watermarking, diagnostics, and other unsupported processing.

The optimization requires no logits or hidden-state gather; serving validation below uses TP1. It eliminates FP32 logits materialization on the eligible path; existing graph buffers remain allocated. No new flag is required.

## Accuracy Tests

- 15 same-GPU control/candidate serving cases matched exactly: greedy output, returned token logprobs, and repetition-penalty/logit-bias/min-new-token fallbacks.
- Official GSM8K, 200 questions, temperature 0, seed 42: control **163/200 (81.5%)**, candidate **165/200 (82.5%)**, zero errors. Truncations: one control, two candidate. These requests exercise the fused greedy path. This small difference is not a quality-improvement claim.
- Official GSM8K candidate temperature 1 compatibility run: **165/200 (82.5%)**, zero errors, one truncation. This run exercises materialized-logits fallback and does not validate the fused greedy path.
- Four XPU kernel tests passed, including softcap saturation, NaNs/infinities, signed zero, chunk-boundary ties, strides, Meta validation, lazy-dispatch lifecycle, and graph replay with changed inputs.
- Three dedicated CPU policy/fallback tests passed; broader CPU dispatch/policy checks passed 110 tests and 15 subtests. Pre-commit passed.

Changing batch schedules can change generated texts: the c32 control repetitions differed on 44/128 texts, and candidate repetitions differed on 46/128. Exact kernel and controlled serving parity do not establish arbitrary batch-independent model equivalence.

## Speed Tests and Profiling

Same Intel XPU, pinned Gemma4 E2B BF16 checkpoint, TP1, MTP draft steps 3 / top-k 1 / draft tokens 4, full graph capture, overlap disabled, page size 64, max running requests 64, context 8192, static memory fraction 0.70. Compare this commit against its parent norm/RoPE branch. Each server switch received a 128-request c32 warmup with 256 output tokens. Measurements use control/candidate/candidate/control order; c1 has 64 requests per run, c8/c32 have 128, all with 256 output tokens and seed 42. All 12 runs completed without request errors and had identical input/output token counts.

Mean TPOT, milliseconds:

| Concurrency | Control A | Candidate A | Candidate B | Control B | Improvement vs final control | Improvement vs mean controls |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4.1377 | 4.1205 | 4.1080 | 4.1200 | 0.139% | 0.354% |
| 8 | 6.0779 | 6.0207 | 6.0189 | 6.0312 | 0.189% | 0.574% |
| 32 | 11.4920 | 11.0764 | 10.9266 | 11.2300 | **2.035%** | **3.164%** |

At c32, control A to control B improved by **2.28%**, so final-control comparison is conservative. Both candidate repetitions beat final control. C1/c8 are effectively flat at this resolution. On the 56/128 c32 requests with identical texts across all four runs, mean streaming-time improvement was 2.799%; this subset does not remove between-run drift.

A real c32 serving profile records 16 fused partial/final reduction kernels (2.429 ms total), confirming serving dispatch. Head-plus-finalization microbenchmarks show larger gains but do not represent end-to-end serving gains.
