# [Fix] radix-cache: Order linker offloads behind the forward that writes the pages

[Upstream PR](https://github.com/sgl-project/sglang/pull/45559) · state: closed · merged: True

## Original PR description

- Mooncake and mori linker offloads now record one event on the scheduler's stream (the page indices) and one on the forward stream (the forward writing the pages), and the offload thread synchronizes both, so it reads a stashed chunk's KV only after that forward. The forward stream's own order is unchanged.
- Prefill read-done is on by default since #37958. With TRTLLM MHA prefill or DeepSeek V4 (no CP, no HiSparse), the scheduler's stream then waits only on the forward's pre-replay read-done, so an offload event recorded on it alone can let the copy read KV the forward is still writing. The read-done gate turns the fast path off for HiCache, storage backends, and LMCache, but not for the external linker.
- The registry passes the model runner's forward stream to the linker, as it already does for LMCache.
- Adds unit tests for the two events, the Mooncake offload thread waiting on both, and the registry wiring.

No behavior change without the external linker. Found by code reading; not reproduced on main.

- lixiufei-leo · comment · 2026-10-21T11:55:12Z · [source](https://github.com/sgl-project/sglang/pull/45559#issuecomment-6315282747)

Same fix for the UMBP linker: #45479 records a second event on the forward stream and the offload thread waits on both, as #45559 does. #45559 also covers Mooncake, so I'm happy to close #45479 in favour of it. A few notes:

- On ROCm the coarse WAR barrier is off by default (`_war_barrier_enabled = is_cuda() or SGLANG_ENABLE_WAR_BARRIER`), so the race shows up there whenever a chunk is offloaded while its forward is in flight, independent of the read-done fast path. We reproduced it on MI355X (DeepSeek-V4-Pro 1P1D, UMBP linker, agentic c256, on 1e86143b). A diagnostic that flags offloaded rows whose last layer is still mostly unwritten at copy time counted 61.2% of 4.53M offloaded rows incomplete without the fix and 0 of 4.56M with it. On the same node pair the decode step went from 49.69 to 47.71 ms.
- The new tests check that both events are recorded and awaited, not the ordering itself. `test_umbp_direct_linker_offload_ordering.py` in #45479 runs a forward that is still writing a page on another stream and checks the offload reads the written values. Without the forward-stream event the copy reads the pre-forward contents; with it the test passes on MI355X. I can move it into #45559.
- Not for this PR, but possibly related: on ROCm the HiCache write-through D2H copy also waits only on the scheduler stream (#44800 fenced only the blocking write-back drain), and linker loads record their ready event only on the scheduler stream, while HiCache loads use `load_fence_stream`. We did not see a measurable effect from fencing linker loads, so I'm only flagging these.
