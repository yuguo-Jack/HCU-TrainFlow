# [Perf] dsv4: shard the MHC prenorm prewarm across co-located ranks

[Upstream PR](https://github.com/sgl-project/sglang/pull/39363) · state: open · merged: False

## Original PR description

## Summary

Distribute MHC prenorm bucket compilation across ranks sharing a TileLang cache using two passes: claim available buckets, then wait for deferred buckets and replay outside the lock. Every rank still materializes all kernels; kernel math, bucket selection, and prewarm timing are unchanged.

- Locks use TileLang's resolved `TILELANG_CACHE_DIR` and include GPU architecture in the bucket key.
- mkdir/open/flock/unlock/close failures fall back to independent prewarm, with one warning per process. Lock-contention waits are bounded to 300 seconds per bucket.
- Owner death releases the OS lock. Recovery or timeout may cause concurrent compilation; there is no single-waiter takeover guarantee.

## Validation

Three CPU tests pass: multiprocess claim/wait/release, bounded waiting, and parameterized lock failures that preserve full-bucket replay and propagate replay exceptions. Pre-commit checks pass.

Existing DeepSeek-V4-Flash-0731 results from the original patch (not rerun for this reliability update):

| Hardware | MHC prewarm before → after | Startup to first response before → after |
|---|---|---|
| B200 TP8 | 158.6s → 31.4s | 442.7s → 316.3s |
| GB300 TP4 | 286.0s → 81.3s | 725.5s → 518.8s |

Warm-cache prewarm was ~2.6s either way. Four deterministic DSPARK prompts produced identical text, acceptance lengths, and verification counts.

GPU cold/warm-cache reruns and real cross-node shared-filesystem validation remain outstanding. Read-only filesystem failures are covered by EROFS injection. The timeout cannot interrupt filesystem calls stuck inside the OS, and TileLang's own cache/compiler errors remain outside this helper.

- bvolpato · comment · 2026-11-03T04:01:58Z · [source](https://github.com/sgl-project/sglang/pull/39363#discussion_r4450788197)

File: `python/sglang/kernels/ops/layernorm/mhc.py` · line 853

With `--enable-symm-mem` at TP4 and no DP attention, this stalls startup. Each rank now replays buckets in its own order, and `mhc_pre` allocates `layer_input` from the symmetric pool. That pool still grows here, because the prewarm runs before `prealloc_symmetric_memory_pool`. So ranks call the collective `ncclCommWindowRegister` with different sizes and different call counts. Main avoids this because all ranks replay in the same order.

A rank that finishes waits in `tp_group.barrier()` while its peers wait in the registration. The registration has no timeout. The barrier uses the gloo `cpu_group`, which defaults to 120 minutes, so a rank in the barrier should raise after about that long. I did not run a stall that long, so I expect a very long stall and then an error.

Evidence on 4 B200s with cold caches:
- Real server, DeepSeek-V4-Flash-0731, cookbook flash-official low-latency flags at `--tp 4` plus `--enable-symm-mem`: main was ready in 670 s. This PR was not ready at my 840 s limit, and the log had no error. TP rank 1 logged "claimed 7 buckets, 15 held by peers", and the other ranks never logged that line.
- A script that runs `_prewarm_mhc_kernels` on real ranks with random weights: on main, all ranks registered the same sizes in the same order. On this PR, in the first collective step, one rank registered 2 MiB and the other three registered 20 MiB. Stack dumps then showed some ranks in `barrier` and the others in the registration under `mhc_pre`. The run was still stuck at my 900 s limit.
- The same script on a warm cache never finished within a 240 s limit.

I suggest keeping the prewarm out of the symmetric pool. The comment above `_dp_max_padding` in `dp_attention.py` already says the prewarm does not need it.

```python
# mhc_pre signature (keyword-only)
symmetric_output: bool = True,

# layer_input allocation in mhc_pre
disabled=not symmetric_output or not is_allocation_symmetric()

# mhc_pre call in replay()
symmetric_output=False,
```

With this change and `--enable-symm-mem` on cold caches, the real server had a hook time of 67 to 70 s and was ready in 465 s. Four fixed prompts at temperature 0 returned the same text as main. The script registered no windows during the prewarm.

`--enable-symm-mem` is not in the DeepSeek-V4 or GLM-5.3-Flash cookbook recipes, so those recipes do not reach this, but it is a documented server argument. One DeepSeek-V4.1 cookbook recipe sets it together with DP attention, and by trace DP attention skips the pool at load.

Not checked for this stall: TP2 and TP8, GLM-5.3-Flash with both PRs (same helper, so by trace I expect the same stall), DP attention beyond the trace, main and the suggested change on a warm cache, and whether a run where window counts happen to match could give wrong collective results. The stack dumps come from the script. For the real server I only have the log and the missed ready limit.
