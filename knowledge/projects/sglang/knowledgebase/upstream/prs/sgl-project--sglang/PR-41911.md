# [Fix] Make tokenizer request-state initialization atomic

[Upstream PR](https://github.com/sgl-project/sglang/pull/41911) · state: closed · merged: True

## Original PR description

## Motivation

`TokenizerManager._init_req_state` inserts one `ReqState` into `rid_to_state` per
(sub-)request, but the duplicate-rid guard (`raise ValueError("Duplicate request ID
detected")`) sits *inside* the insert loop, and `_init_req_state` is called *before*
the `try/except BaseException -> _release_req_states_on_failure` cleanup block in
`generate_request`. When a batch request's rid list collides with an in-flight rid at
position k, the states for items 0..k-1 have already been inserted and are never
removed: the request fails with 400, but the leaked rids stay in `rid_to_state`
forever — every later reuse fails with "Duplicate request ID", and each leaked state
holds an `asyncio.Event` plus the sub-request object.

A client fully controls the rid list, so each crafted batch (N fresh rids + 1
colliding rid) permanently leaks N-1 states; repeating this grows the tokenizer
process memory without bound and progressively poisons the rid namespace.
(Within-batch duplicates are already rejected at normalization in `io_struct.py`;
this hole is collisions with rids already in `rid_to_state`.)

Reproduced on the official `lmsysorg/sglang:v0.5.20` image, default flags, no auth:

1. Long in-flight request with `rid="victim2"`, then batch
   `{"rid": ["leak-y1", "leak-y2", "victim2"], ...}` -> 400 `Duplicate request ID
   detected: victim2`.
2. Fresh request with `rid="leak-y1"` -> 400 `Duplicate request ID detected:
   leak-y1` (the rid never ran, yet is permanently occupied).
3. A fresh rid still returns 200.

## Modifications

- `python/sglang/srt/managers/tokenizer_manager.py`: in `_init_req_state`, check all
  rids for duplicates before inserting any state. No behavior change for valid
  requests; the duplicate error message is unchanged.
- `test/registered/unit/managers/test_init_req_state_duplicate_rid.py` (CPU):
  - duplicate at tail of batch -> raises, earlier states not leaked (fails before
    this fix);
  - all-unique batch registers all states;
  - single-request duplicate raises and preserves the existing state.

`pre-commit run` passes on the changed files.

Thanks for reporting and reproducing this request-ID leak. I've closed #43751 and consolidated the broader fix into this PR so we can merge the original report here.
