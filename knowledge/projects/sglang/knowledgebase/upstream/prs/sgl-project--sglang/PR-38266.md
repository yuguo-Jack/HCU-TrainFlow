# [Intel GPU] Use the fused bf16 x bf16 -> fp32 GEMM on XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/38266) · state: open · merged: False

## Original PR description

## Motivation

`_linear_bf16_fp32_cublas` in `python/sglang/kernels/ops/attention/dsv4/gemm.py` took the fused `torch.mm(..., out_dtype=torch.float32)` call only when the activation was on CUDA:

```python
if x.is_cuda and x.dtype == torch.bfloat16 and y.dtype == torch.bfloat16:
    return torch.mm(x, y.t(), out_dtype=torch.float32)
return torch.mm(x.float(), y.float().t())
```

On Intel GPUs `x.is_cuda` is false, so every call took the fallback. The fallback copies both operands to fp32 before the multiply, and one operand is a weight.

The helper runs inside `linear_bf16_fp32`. Three files call it, and on XPU only the compressor call reaches the helper with a bf16 weight:

| Call site | Operand | On XPU |
| --- | --- | --- |
| `srt/layers/attention/dsv4/compressor.py:425` | `self.wkv_gate.weight` (replicated bf16) | fallback on base, fused with this PR |
| `srt/models/deepseek_v2.py:522,546` | MoE gate `self.weight` | not reached: both calls run only when `_is_cuda` is true |
| `srt/models/longcat_flash.py:237` | router `classifier.weight` (fp32 on this path) | fallback before and after, because the weight is not bf16 |

The compressor weight does not change, so the fallback builds the same fp32 copy on every call. A decode profile on the wider XPU campaign stack recorded input shapes and dtypes. It counted about 56 of these conversions per decode step: 4.47 ms of a 28.33 ms step.

## Modifications

The gate in `_linear_bf16_fp32_cublas` is now `(x.is_cuda or x.is_xpu)`, with both inputs in bf16.

| Runtime | Before | After |
| --- | --- | --- |
| CUDA and ROCm (device type `cuda`) | fused | fused (no change) |
| XPU | fp32 fallback | fused |
| CPU, NPU, MUSA | fp32 fallback | fp32 fallback (no change) |

`aten::mm.dtype` is a per-backend overload. On a backend without the kernel, the fused call raises `NotImplementedError` and does not use the plain `mm` instead. For this reason the gate adds XPU only. The XPU wheel that `python/pyproject_xpu.toml:62` pins (`torch==2.13.0+xpu`) registers the XPU kernel:

```
$ python -c "import torch; print(torch.__version__); print(torch._C._dispatch_dump('aten::mm.dtype'))"
2.13.0+xpu
...
XPU: registered at .../build/aten/src/ATen/RegisterXPU_0.cpp:942
```

An earlier revision (7fe937c147) probed the overload at run time and added a CPU dispatch test. This revision removes both. The pinned wheel has the kernel, so the probe is not necessary. The probe also made its own `torch.mm` call on first use. On a cold cache, the XPU test counted two calls and failed (see the XPU test table below).

## Accuracy Tests

gsm8k, 200 questions, 5-shot, temperature 0, DeepSeek-V4-Flash-0731, TP8 on eight Arc Pro B70. Both arms use the same container image and the same launch command. Only a bind-mounted `gemm.py` is different. In each container, the md5 of `gemm.py` matches the file for that arm.

| `gemm.py` | Accuracy | Invalid |
| --- | --- | --- |
| base 9fea3e9bb2 (`x.is_cuda`) | 0.965 | 0.000 |
| this PR (eb03db2) | 0.965 | 0.000 |

With 200 questions, one run has a standard error of about 1.3 points. The difference between two runs has a standard error of about 1.8 points. So this A/B can show a large regression, but not a small one.

In the campaign work that found this issue, the maximum error of the fused result against an fp32 reference was `7.6e-5`. The fused overload accumulates in fp32 and writes fp32. It does not widen the inputs first, and it runs a different kernel. So its result is close to the fallback, but not bit-identical.

`test/registered/xpu/test_dsv4_bf16_fp32_gemm.py` (`register_xpu_ci(est_time=10, suite="stage-b-test-1-gpu-xpu")`) checks on real hardware that the result matches the fp32 reference and that `torch.mm` runs once with `out_dtype=torch.float32`. On one Arc Pro B70, each run in a fresh process:

| `gemm.py` | Result |
| --- | --- |
| base 9fea3e9bb2 | fails: `KeyError: 'out_dtype'` (XPU takes the fallback) |
| 7fe937c147 (run-time probe) | fails: `AssertionError: 2 != 1` |
| eb03db2 (this PR) | passes |

## Speed Tests and Profiling

Eight Arc Pro B70 at TP8, DeepSeek-V4-Flash-0731, 1024 input and 1024 output tokens at concurrency 1, six requests plus one warmup, `ignore_eos`. Each arm had three runs from one server launch. Both arms used one image and one source tree. That tree also carried #38262 and #38272 (with `SGLANG_DSV4_DECODE_GRAPH_SEQ_LENS` not set). In the source tree, only `gemm.py` is different between the arms.

| Arm | `gemm.py` | tok/s/user | Range of 3 | ITL |
| --- | --- | --- | --- | --- |
| C | base (`x.is_cuda`) | 33.88 | 33.81 to 33.93 | 29.52 ms |
| A | earlier revision (run-time probe) | **40.71** | 40.36 to 40.92 | **24.57 ms** |

The result is +20.1% tok/s/user and -16.8% inter-token latency. The largest spread in one arm is 1.4% (arm A). The figures come from the six measured requests of each run. An earlier version of this description gave the warmup request of each run (33.80 and 40.82, +20.8%).

These numbers come from the earlier revision with the run-time probe, not from eb03db2. On XPU both revisions take the same fused call. The probe added one 1x1 `torch.mm` per process on first use.

The launch commands were not identical. The control arm set `SGLANG_OPT_FP8_WO_A_GEMM=0`. The PR arm did not set it and relied on #38262 to turn it off. So both arms ran with the flag off only if #38262 works as it claims.

In the decode profile of the wider XPU campaign, not this A/B, attention preparation falls from 3.62 ms to 0.20 ms per step.

## Limits of the evidence

- The XPU gate relies on the pin. An XPU build of torch without the XPU kernel for `aten::mm.dtype` raises `NotImplementedError` at this call, where base used the fp32 fallback. Only `torch==2.13.0+xpu` was checked.
- The speed test used one shape: 1024 input, 1024 output, concurrency 1. Long context and higher concurrency were not measured on this branch.
- Three runs from one launch per arm show measurement noise. They do not show the variance between launches from graph capture and memory layout.
- `+20.1%` applies to this configuration only. It is not the headline of the wider campaign, where most of the gain came from configuration changes.
- No CI lane runs XPU tests on pull requests to `intel_dev`. `pr-test-xpu.yml` runs on pushes and pull requests to `main` only, and no workflow names `intel_dev`. The XPU results above come from local runs.
- The three CI runs in the block below stop at gates before any test runs. PR Test (Base) and PR Test (Extra) stop at the maintenance gate: issue #21065 sets `MIN_BASE_SHA` 60878c3fba50, and `intel_dev` does not contain it. PR Test (AMD) stops at `pr-gate`, because the PR has no `run-ci` label. The `bypass-maintenance` label skips the maintenance gate.

This PR is one of several small changes from a larger DeepSeek-V4 XPU enablement branch. Its code does not depend on the others. Only the speed A/B used #38262, to turn off `SGLANG_OPT_FP8_WO_A_GEMM`.

Good question — I checked the dispatch table rather than reasoning about it.

On `torch==2.13.0+xpu`, which `pyproject_xpu.toml:62` pins, `aten::mm.dtype` registers `Meta`, `Tracer`, `XPU` and an autograd alias. So on the pinned wheel, hardcoding `True` for XPU would be correct today.

The reason it probes is what happens on a build that does not carry it. There is no fallback to the plain overload — it raises:

```
>>> torch.mm(bf16_cpu, bf16_cpu, out_dtype=torch.float32)
NotImplementedError: Could not run 'aten::mm.dtype' with arguments from the 'CPU' backend.
```

So a hardcoded `True` on a torch-xpu build without the registration is a hard failure inside the attention forward rather than a slow path, and XPU users often run source builds rather than the pinned wheel. The probe is one 1x1 allocation, `functools.cache`d, resolved during the two warmup forwards that run before graph capture.

On the other half of the question: probing `device != XPU` would enable the fused path on CPU, ROCm, NPU and MUSA wherever it happens to be registered. That is a silent numerics change on backends this PR does not test, so `return False` leaves them exactly as they are. CUDA is hardcoded `True` only to keep the previous `x.is_cuda` behaviour identical.

That said, if you would rather trust the pin and hardcode XPU, it is a two-line change and I am fine with it.
