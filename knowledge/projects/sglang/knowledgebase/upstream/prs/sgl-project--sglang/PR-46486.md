# [Perf] [AMD] dsa: Run the GLM-5 decode MLA chain as Gluon kernels on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/46486) · state: open · merged: False

## Original PR description

## Motivation

- On MI355X (gfx950) with the `triton` DSA decode backend (the ROCm default), each GLM-5 decode and MTP target-verify step runs three kernels per layer for the absorbed MLA: the aiter fused q-absorb + RoPE + fp8 KV write, SGLang's Triton split-K sparse MLA, and the aiter fp8 value-absorb BMM.
- At serving shapes (8 or 16 heads per rank, M = batch or 6 x batch) these launches are short and under-filled.
- This PR rewrites all three in Gluon for gfx950 and tunes the launch configuration per M range, lowering per-launch overhead and kernel time.
- Result: per-layer core 1.13-1.35x faster; end-to-end interactivity p50 +5.2-6.6% at TP8 and TP4/EP4; GSM8K and MTP accept length unchanged.

## Modifications

One commit per kernel:

| kernel | new file | replaces | in |
|---|---|---|---|
| sparse MLA (split-K producer + reduce) | `kernels/ops/attention/dsa/gluon_sparse_mla_decode_gfx950.py` | Triton split-K sparse MLA | `dsa_backend.py`, `"triton"` decode and target verify |
| q absorb + RoPE + KV write (one launch) | `kernels/ops/attention/gluon_mla_absorb_rope_cache_gfx950.py` | aiter `fused_fp8_bmm_rope_cat_and_cache_mla` | `forward_mla_rocm.py`, existing fused path |
| value absorb | `kernels/ops/gemm/gluon_mla_absorb_v_gfx950.py` | aiter fp8 batched GEMM | `forward_mla_rocm.py`, `rocm_absorb_v_bmm` |

- Same inputs and outputs as the calls they replace; KV-cache rows are bitwise equal to aiter's.
- Per-M launch parameters (grid, split count, tile, cache modifiers, kernarg preload) are module constants measured on MI355X.
- Sparse MLA: a generic producer for every M plus specialised producers for 7 verify shapes; at TP8 with M <= 18 the idle half of each 16-row MFMA tile computes the second half of the value dimension.
- No new environment variable, server flag or aiter dependency; the guards read existing settings only.
- Shared code touched: `dsa_backend.py`, `forward_mla_rocm.py`, one line in `deepseek_v2.py` (per-layer flag, False off gfx950). New modules are imported only behind the gfx950 check.

**Guards and coverage**

- All three require gfx950, Gluon with a CTA barrier, `--dsa-decode-backend triton` (the ROCm default), fp8_e4m3 KV, the GLM-5 MLA shape (kv_lora 512, qk_nope 192, rope 64, v_head 256), no DCP, and decode (M = batch) or target verify (M = 6 x batch). Decided at construction, shape check per call.

| kernel | TP8, 8 heads per rank: M (verify batch) | TP4, 16 heads per rank: M (verify batch) | extra conditions |
|---|---|---|---|
| sparse MLA | <= 128 (<= 21) | <= 240 (<= 40) | q already concatenated; KV rows x 576 < 2^32 |
| absorb + RoPE + KV | <= 128 (<= 21) | <= 384 (<= 64) | aiter path on (`SGLANG_USE_AITER=1`); per-tensor fp8 `w_kc`; non-neox rotary |
| value absorb | <= 128 (<= 21) | <= 72 or 97-120 (<= 12 or 17-20) | aiter path on (`SGLANG_USE_AITER=1`); per-tensor fp8 `w_kc` / `w_vc` |

- Ranges are where the Gluon kernels measured faster. Specialised sparse-MLA producers: TP8 M = 6, 12, 18, 30; TP4 M = 6, 36, 42.
- Covers the InferenceX GLM-5.2 MI355X agentic sweep (TP8 conc 1-4, TP4/EP4 conc 4-16, batch <= 2 x conc); the value absorb covers only part of the TP4 range.
- Everything else (larger batches, prefill, draft extend, any CUDA build) runs the existing kernels unchanged.

**Models**

- Matches the `glm_moe_dsa` family (GLM-5, 5.1, 5.2, 5.3); validated on GLM-5.2-MXFP4 only.
- Unaffected: GLM-5.3-Flash, DeepSeek-V3.x, Kimi, and servers using `--dsa-decode-backend tilelang` or `aiter`.

**Compiler notes**

- Value-absorb epilogue reads MFMA results in inline asm, where LLVM inserts no wait states; each variant pads it with `s_nop` to gfx950's 12. Checked in the ISA of all 96 variants on Triton 3.6.0, a 3.7-dev snapshot, ROCm 3.7.0 and 3.8.0.
- Specialised sparse-MLA producers end their softmax stage with a CTA barrier (they raced without it on the 3.7-dev snapshot). Without a Gluon CTA barrier the module is not used.
- Two wrappers set the process-global `knobs.amd.kernarg_preload_max_dwords` under a lock and restore it.

### Update-10/29: rebased onto main `b960aa903a` (conflict resolved)

- PR 44322 (DCP on the triton sparse-MLA backend) conflicted in `dsa_backend.py`. Dispatch order is now DCP → Gluon → stock Triton. The Gluon path requires `dcp_size == 1`, so the two never overlap.
- Followed two other upstream changes: sparse-attention outputs are now token-first (`.squeeze(0)`), and the KV buffer is read through `get_kv_layers()`, as the aiter path does.
- The value-absorb commit is unchanged.

```bash
# kernel and gate tests (one gfx950 GPU)
python3 -m pytest -q test/registered/kernels/ops/attention/test_gluon_sparse_mla_decode_gfx950.py \
  test/registered/kernels/ops/attention/test_gluon_mla_absorb_rope_cache_gfx950.py \
  test/registered/kernels/ops/gemm/test_gluon_mla_absorb_v_gfx950.py \
  test/registered/kernels/ops/attention/test_triton_sparse_mla_hip.py \
  test/registered/unit/layers/attention/test_dsa_gluon_sparse_mla_decode_gate.py \
  test/registered/unit/models/test_rocm_mla_absorb_fusion_gate.py
# TP4/EP4 server; max-running-requests = cuda-graph-max-bs-decode = 2 x conc (16 for GSM8K)
# TP8: --tp 8 --ep-size 1, no HiCache flags
SGLANG_OPT_USE_TOPK_V2=true python3 -m sglang.launch_server --model-path amd/GLM-5.2-MXFP4 \
  --trust-remote-code --tp 4 --ep-size 4 --kv-cache-dtype fp8_e4m3 \
  --dsa-prefill-backend triton --dsa-decode-backend triton \
  --chunked-prefill-size 32768 --mem-fraction-static 0.85 \
  --max-running-requests 8 --cuda-graph-max-bs-decode 8 \
  --speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 6 \
  --enable-hierarchical-cache --hicache-size 180 --hicache-write-policy write_through
# accuracy and accept length (no SGLANG_SIMULATE_ACC_LEN)
python3 -m sglang.test.few_shot_gsm8k --num-questions 1319 --num-shots 5 --parallel 32
# end to end: InferenceX config glm5.2-fp4-mi355x-sglang-agentic-mtp (aiperf, 1200 s)
```

### Known gaps

- gfx950 only; TP8 and TP4 head counts only; DCP keeps the existing kernels; needs a Gluon CTA barrier (Triton >= 3.6).
- Larger batches keep the existing kernels (e.g. TP8 conc 64 gets no target-verify speedup).
- GSM8K at TP4/EP4 only; GLM-5, 5.1, 5.3 not tested.
- Launch parameters and the inline-asm wait-state check need re-running after a Triton upgrade.
