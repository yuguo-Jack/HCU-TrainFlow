# [Perf] cuda-graph: Use one eager warmup per capture shape

[Upstream PR](https://github.com/sgl-project/sglang/pull/41484) · state: open · merged: False

## Original PR description

CUDA graph startup runs two eager forwards for each capture shape. Use one warmup for ordinary full and breakable capture, while retaining two where the second pass is required:

- Compiled shapes retain two warmups so TorchInductor can finish deferred autotuning before capture. The AMD TorchCompileMoe run reached coordinate-descent tuning and a forbidden device synchronization during capture with one warmup.
- Graph-pool pre-carving retains two warmups so persistent setup allocations are excluded from scratch sizing.
- Scheduled profiling retains two warmups to preserve its capture-only trace schedule.

Release each eager output before the next forward. Shared output buffers use the final warmup result. Graph buckets and replay behavior are unchanged.

### Validation

After merging main `b702f0d80e`, the focused capture and routing suites pass **14 tests and 8 subtests**, covering both full and breakable backends, compilation/pre-carving warmup requirements, output lifetime, shared output storage, profiling, and routing context. Compilation and pre-carving share one regression; the synthetic allocator test was removed. These tests mock CUDA capture. The full-model `TestTorchCompileMoe` MMLU and throughput tests passed on [AMD MI300](https://github.com/sgl-project/sglang/actions/runs/41483258610/job/125414410768) at `5eedf7fac2` and in a targeted [NVIDIA H100 run](https://github.com/sgl-project/sglang/actions/runs/41483443634/job/125407681698), validating the retained second warmup for compiled shapes.

### Earlier full-model validation

On GB300, `Qwen/Qwen3-0.6B` completes full CUDA graph capture and generation on main `5008726431` and head `3da9cd1277`. All output token IDs match for batch sizes 1, 2, 4, 8, 3, 1: 19 requests with 32 greedy output tokens each. Local runtime: PyTorch 2.11.0/CUDA 13.2, FlashInfer 0.7.2, CuTe DSL 4.8.0, and installed sgl-kernel 0.4.6.post1 with its version check bypassed (upstream expects 0.4.9). The same 19-request comparison also passes with breakable prefill capture at token sizes 8, 16, 32, and 64 plus full decode capture. The profiling-output lifetime and opt-in pre-carving fixes are covered by CPU regressions; the default-path GPU runs used `3da9cd1277`. This is correctness coverage; cold compilation and concurrent jobs make these startup times unsuitable for a speed claim.

The change removes one eager forward and synchronization/barrier for ordinary uncompiled shapes with scheduled profiling and pre-carving disabled. No controlled startup benchmark or steady-state throughput claim.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Release the prior output before the next profiling warmup**

When scheduled per-batch CUDA-graph profiling is active, this loop still executes twice, and Python evaluates `forward_fn()` before replacing the existing `warmup_output`. The first eager output (typically GPU-resident logits) therefore remains live throughout the entire second model forward; the previous implementation explicitly deleted it and retained only the final output. On large-vocabulary models or memory-constrained profiling runs, this can add a full output allocation to peak startup memory and cause capture to OOM, so the iteration-local output should be released before the next warmup while preserving only the last result needed for buffer allocation.
