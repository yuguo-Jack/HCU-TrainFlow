# [AMD][Deepseek-R1] Switch attention output projection mxfp4 gemm from triton -> asm

[Upstream PR](https://github.com/sgl-project/sglang/pull/31775) · state: closed · merged: False

## Original PR description

## Summary

Adds an opt-in path to route the DeepSeek-R1 attention output projection (o_proj) MXFP4 GEMM through aiter's ASM a4w4 kernel (gemm_a4w4) instead of the default triton kernel (gemm_afp4wfp4). Only the o_proj linear is affected; all other MXFP4 linears and MoE layers are untouched.

When enabled, the layer:
converts its serialized (triton-layout) packed weight + e8m0 block-scale into the ASM preshuffled layout once at load time, and
quantizes the activation with dynamic_mxfp4_quant(shuffle=True) and calls gemm_a4w4(..., bpreshuffle=True) at runtime.
The MLA fused-decode path is updated to skip its triton pre-quant for an ASM o_proj so the layer receives a plain bf16 activation. The feature falls back to the triton kernel if the aiter ASM build is unavailable. Also adds a CPU unit test covering the routing gate.

For smaller batch sizes the triton kernel is more efficient but for larger batch sizes >=256 the asm implementation gives significant gains. This justifies the addition of a flag to decide if the user wants to enable the asm implementation or not depending on his batch size of interest. For MLPerf, where the decode batch size operating point is around 900-1000, this gives significant gains.

The last column is an accuracy test which shows that the asm and triton kernel outputs are bit exact. So the asm kernel provides a pure speed benefit with no accuracy regression (with respect to the mxfp4 triton kernel) at higher batch sizes.

  `get_linear_scheme`, flip a `*.o_proj` `QuarkW4A4MXFP4` scheme into ASM mode
  (`enable_asm()`) when the env var is set.
- **`python/sglang/srt/layers/quantization/quark/schemes/quark_w4a4_mxfp4.py`** (+66):
  import aiter ASM entry points (`gemm_a4w4`, `shuffle_weight`,
  `dynamic_mxfp4_quant`, `e8m0_shuffle`) guarded with a triton fallback; add
  `enable_asm()`; preshuffle the weight + e8m0 block-scale into the ASM layout at
  load time (`process_weights_after_loading`, tags `mxfp4_use_asm=True`); add the
  ASM branch in `apply_weights` (activation `dynamic_mxfp4_quant(shuffle=True)` +
  `gemm_a4w4(bpreshuffle=True)`).
- **`python/sglang/srt/models/deepseek_common/attention_forward_methods/forward_mla.py`** (+5/-2):
  in the MLA absorb path, skip the triton `fused_flatten_mxfp4_quant` pre-quant
  for an ASM `o_proj` so it receives a plain bf16 activation.

## Tests 
- **`test/registered/unit/layers/quantization/test_quark_oproj_asm.py`** (+120):
  CPU-only unit test for the routing gate (no model, no kernels — aiter
  availability is mocked):
  - `enable_asm()` flips to ASM mode only on HIP with the aiter ASM kernel
    available, otherwise stays on triton.
  - `get_linear_scheme()` routes to ASM only for `*.o_proj` when
    `SGLANG_DSR_OPROJ_MXFP4_ASM=1`, and leaves other layers / env-unset / env=`0`
    on triton.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

There are two important improvements to make here:
1. Calling `.view(torch.uint8)` on `layer.weight.data` and `layer.weight_scale.data` can raise a `RuntimeError` if the tensors are not contiguous (e.g., due to slicing or sharding during tensor parallel loading). Calling `.contiguous()` first prevents this.
2. Recreating `layer.weight` and `layer.weight_scale` as plain `torch.nn.Parameter` objects discards their original custom parameter classes (`PackedvLLMParameter` and `GroupQuantScaleParameter`) and any associated custom attributes/metadata (such as `input_dim`, `output_dim`, `packed_dim`, etc.). This can break downstream components or tensor parallel communication that rely on these custom parameter types. Instead, update the parameter data in-place by assigning to `.data`.

```python
            weight = layer.weight.data.contiguous().view(torch.uint8)
            weight_scale = layer.weight_scale.data.contiguous().view(torch.uint8)
            weight = _asm_shuffle_weight(weight, layout=(16, 16))
            weight_scale = _asm_e8m0_shuffle(weight_scale)
            layer.weight.data = weight.contiguous()
            layer.weight_scale.data = weight_scale.contiguous()
```

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

If `self.use_asm` is `True` but `x` is a tuple (indicating a pre-quantized input), the code currently silently falls through to the Triton GEMM path. However, because the weights and scales have already been preshuffled for the ASM kernel during loading, running the Triton GEMM on these shuffled weights will produce completely incorrect results (silent correctness bug). We should explicitly assert or raise an error if `x` is a tuple when `self.use_asm` is enabled.

```suggestion
        if self.use_asm:
            assert not isinstance(x, tuple), "ASM path does not support pre-quantized tuple inputs."
            out_features = layer.weight.shape[0]
            if x.dim() == 3:
                out_shape = (*x.shape[:-1], out_features)
                x = x.view(-1, x.shape[-1])
            else:
                out_shape = (x.shape[0], out_features)
            x_q, x_s = _asm_dynamic_mxfp4_quant(x, shuffle=True)
            y = _asm_gemm_a4w4(
                x_q,
                layer.weight,
                x_s,
                layer.weight_scale,
                bpreshuffle=True,
            )
            if bias is not None:
                y = y + bias
            return y.view(*out_shape)
```

Instead of manually parsing the environment variable with `os.environ.get(...) == '1'`, use the codebase's idiomatic helper `get_bool_env_var` from `sglang.srt.utils`. This is more robust as it correctly handles other truthy values like `True`, `true`, `yes`, etc.

```suggestion
        from sglang.srt.utils import get_bool_env_var
        if (
            isinstance(scheme, QuarkW4A4MXFP4)
            and layer_name.endswith("o_proj")
            and get_bool_env_var("SGLANG_DSR_OPROJ_MXFP4_ASM")
        ):
            scheme.enable_asm()
```
