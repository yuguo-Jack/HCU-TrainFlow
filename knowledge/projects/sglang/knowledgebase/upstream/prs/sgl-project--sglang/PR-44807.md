# [Fix] minimax-h3: validate VAE tile settings

[Upstream PR](https://github.com/sgl-project/sglang/pull/44807) · state: open · merged: False

## Original PR description

## Motivation

The H3 video VAE splits frames into tiles of `vae_tile_size` with at least `vae_tile_overlap_min` overlap and stitches them back in pixel and latent coordinates. Nothing validated the two values, so on the real checkpoint:

- `vae_tile_overlap_min >= vae_tile_size` made `split_tiles` loop forever, and the request hung in the decoding stage after denoising had finished;
- a tile size that is not a multiple of the spatial compression ratio (16) failed only at the end of decoding with `decoded frames 736x1280 smaller than target canvas 768x1344`.

## Modifications

- `configs/models/vaes/minimax_h3_contract.py`, `minimax_h3_video.py` and `runtime/models/vaes/minimax_h3_video_vae/klvae.py`: reject non-positive or non-integer values, an overlap that is not smaller than the tile, and values that are not multiples of the compression ratio. The check runs both when the VAE config is post-processed and when the tiled-decoding settings are applied, so a bad config fails when the VAE loads.
- `test/unit/test_minimax_h3_vae_tiling.py`: invalid values at both entry points, and valid settings that reconstruct the pixel and latent canvases exactly.

## Accuracy Tests

Unit: `test_minimax_h3_vae_tiling.py` 2 passed, 60 subtests passed. Without the fix the new tests fail.

Real MiniMax-H3 FL2VA checkpoint, TP2 on 2 x B200, t2va, 4 s, 50 steps, seed 42. Server runs on this branch head, on a merge of the three H3 fixes (this PR, the VAE tile validation and the sigma preflight), and on unpatched `main` (`2948662026`).

**Tile settings** (video latent shape unchanged, 768x1344 output):

| setting | unpatched `main` | this branch |
| --- | --- | --- |
| default 256 / 64 | mp4 `d7ffac37f960` | mp4 `d7ffac37f960` (identical) |

| overlap == tile (256 / 256) | denoising finishes, then decoding hangs until the 900 s request timeout | `vae_tile_overlap_min must be less than vae_tile_size, got 256 >= 256` raised while loading the VAE |

The 128 / 32 setting does take effect, and the same output comes from `main` and from this branch (max pixel difference 0 at frames 0, 53, 106). Native-resolution crop of frame 53, default tiling vs 128 / 32; the smaller tiles give visibly blockier shading, which is a property of that setting, not of this change:

Times are seconds from server start. For `main`, healthy time and request time come from the harness; for this branch, the time is the timestamp of the startup error in the server log relative to the first log line (a few seconds after process start). The branch's process then takes about 1.5-2 more minutes to exit (existing shutdown behaviour), which is not counted. Weights were warm in the page cache, so the saving here is the rest of the load plus the failing request; for a remote repository it would also include the download. Run-to-run load time varies (main healthy in 249-312 s across these runs).
