# fix(args): capture the exact --cuda-graph-max-bs-prefill ceiling bucket

[Upstream PR](https://github.com/sgl-project/sglang/pull/41941) · state: open · merged: False

## Original PR description

Fixes #41923.

## What

`generate_prefill_cuda_graph_batch_sizes` filtered the grid with `s <= max_bs` but never appended `max_bs` itself, so an off-grid `--cuda-graph-max-bs-prefill` silently rounded down to the nearest captured bucket (3000 → 2816, 4500 → 4096, 4607 → 4096). The decode path appends the ceiling when it is off-grid, and the CPU graph path unions it in; prefill was the odd one out. Since `post_capture_kv_sizing_planned()` treats the largest captured bucket as the prefill ceiling, an off-grid value also quietly disabled post-capture KV sizing (the #33847 failure mode).

The change mirrors decode: append `max_bs` when it is not on the grid.

## Verification

New `test/registered/cpu/test_cuda_graph_batch_sizes.py` (CPU lane, no GPU needed):

- off-grid ceilings (3000, 4500, 4607, 5000, 6000, 10000) now end exactly at the ceiling and stay sorted
- on-grid ceiling (2048) is not duplicated
- ceiling below the first grid point (`2`) yields `[2]` instead of an empty list
- decode parity pinned with a real `ServerArgs`

All 5 pass locally on this branch; with the fix reverted the 3 off-grid tests fail, so they pin the changed behavior.

Not run locally: GPU capture e2e (no GPU on this machine). The change only alters which batch sizes get captured; capture itself is exercised by the existing CUDA graph CI lanes.

## Risk / rollback

One conditional append in bucket-list generation. Rollback is a revert; the pre-fix behavior is a strict subset of the post-fix bucket list, so reverting never removes a bucket anyone could have relied on.
