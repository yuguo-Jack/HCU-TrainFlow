# [Fix] diffusion/serving: Reclaim abandoned shared-memory replies

[Upstream PR](https://github.com/sgl-project/sglang/pull/46154) · state: closed · merged: True

## Original PR description

## Summary

Large local scheduler replies are spilled to `/dev/shm`, but only the receiving client removes them. If an RPC times out or is cancelled before the reply arrives, the scheduler still writes the result and no process deletes it. Repeated abandoned frame-return RPCs can exhaust shared memory.

- Scope reply files to a private directory owned by each sync/async RPC. Advertise its opaque name through the existing local ZMQ routing identity; no request payload or model changes.
- Retire the directory atomically before cleanup so a late producer cannot create new files during deletion.
- Keep inline transport for unmanaged clients, unavailable shared memory, and failed writes. Keep warning keys stable across requests.
- Extend the existing IPC/client tests and document cleanup boundaries. No new knobs or files.

## Validation

Remote Linux/H200 testing:

- 119 tests and 6 subtests passed, including timeout/cancellation before and after spill, invalid replies, write/cleanup races, concurrent ownership, and existing scheduler/health/video/disaggregation/CUDA IPC coverage. Two sync cancellation cases are skipped because synchronous calls use transport timeouts.
- 128 real ZMQ requests at concurrency 8, with 32 MiB replies: 64 completed, 64 cancelled after spill, no stale files or mixed-up replies.
- Real Wan2.1-T2V-1.3B generation (`768x512`, 33 frames, 4 steps, FA, seed 42): complete, cancel, complete. The old implementation leaves a 37 MiB file; this branch leaves none. All successful old/new frame arrays are byte-identical; health and liveness remain healthy.
- Repeated the generation/cancellation sequence with two H200 DP replicas, then drained both replicas with successful requests: no residual files, and old/new outputs are byte-identical under the same DP2 topology. DP1 and DP2 hashes differ on both versions, so cross-topology identity is not claimed.
- A 5,000-request short-RPC measurement adds approximately 29 microseconds median latency for directory ownership (147 to 176 microseconds). This is a correctness fix, not a speedup claim.

Timeout/cancellation stops waiting, not GPU work already executing. Hard process kills cannot execute cleanup; deployments should isolate their shared-memory lifetime. This does not change CUDA IPC tensor retention or the async progress API.
