# [Kernel] fp8: add FlashInfer b12x MXFP8 dense GEMM backend for SM120/…

[Upstream PR](https://github.com/sgl-project/sglang/pull/45391) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1's dense projections are `[32,32] ue8m0` block FP8. On SM120/SM121
(RTX PRO Blackwell / RTX 50 / GB10) they fall into the Triton fallback, which
takes **43.3% of GPU time** in an 8K prefill profile (no tuned configs,
`BLOCK_SIZE_K=32`, manual scale multiply):

- The block-FP8 kernels (DeepGEMM / FlashInfer groupwise / CUTLASS) only take
  128-wide K blocks — the [32,32] scale granularity does not fit.
- The official `block_fp8_as_mxfp8` route hard-fails on these parts:
  `--fp8-gemm-backend flashinfer_cutedsl` → `RuntimeError: ... requires an
  SM100/SM103 GPU` (the cute-dsl/cutlass kernels need tcgen05/TMEM, which
  SM120/121 lack).
- FlashInfer ships a warp-level **b12x** MXFP8 kernel for exactly these parts
  (`mm_mxfp8(..., backend="b12x")`, requires SM120/SM121, CUDA 13+,
  nvidia-cutlass-dsl >= 4.6.0, 1D 128x4-swizzled scales, K % 128 == 0), but
  sglang's backend registry (enum / CLI / resolve / dispatch) never wired it
  in — SM120 is currently a blank in the MXFP8 dense matrix (docs list
  h200/b200/b300/gb300/mi355x; Hopper is explicitly "no MXFP8 dense path").

This PR fills that blank by adding b12x as a peer of cute-dsl/cutlass inside
the existing `block_fp8_as_mxfp8` architecture — SM100/SM103 → cute-dsl,
SM120/SM121 → b12x.

## Modifications

- `Mxfp8DenseGemmBackend` / `Fp8GemmRunnerBackend` gain `flashinfer_b12x`
  (+ CLI choice); auto resolution picks b12x on SM120/SM121 when FlashInfer
  can run it, before falling back to cutlass.
- `resolve_block_fp8_mxfp8_backend` / `dispatch_block_fp8_mxfp8_linear` /
  `dispatch_w8a8_mxfp8_linear` accept b12x (native-MXFP8 checkpoints on
  SM120 benefit too).
- b12x weight scales are converted to the 1D 128x4-swizzled UE8M0 layout at
  load time (`mxfp8_sf_swizzle_128x4`, mirroring FlashInfer's
  `compute_sf_index_swizzled_128x4_gpu`), instead of the 2D
  `block_scale_interleave` layout the cutlass/cute-dsl backends use.
- The DeepSeek-V4.1 config-time override picks `flashinfer_b12x` on the SM120
  family when usable (registry + CUDA 13 + cutlass-dsl >= 4.6 checks), and
  stays on Triton with a warning otherwise — mirroring the SM100 →
  flashinfer_cutedsl day-0 behavior.
- `K % 128 == 0` is validated at load time (per-layer Triton fallback with
  the layer name in the warning) and in the linear wrapper.
- The FlashInfer autotune warmup whitelist covers b12x.

No default behavior changes on SM100/SM103, Hopper, or ROCm.

## Accuracy Tests

Microbench on the target host (8x RTX PRO 5000, SM120, CUDA 13): same
UE8M0 grid quantization on both sides, b12x vs the Triton fallback on the
model's real projection shapes — **median relative error 0.0 (bit-exact)**
across shapes like (N=4096, K=4096) x M in {2048, 8192, 16384}, because the
checkpoint scales are native powers of two (UE8M0) and the swizzle/E8M0
conversion is exact.

GSM8K on this exact commit: in progress (numbers to be attached before
marking ready).

## Speed Tests and Profiling

Same host, DSv4.1, ISL 8192 / C128 / 64 reqs / 3 runs, identical kernel path
(env-gated variant of this change; re-run on this exact commit before ready):

| Metric | Triton fallback | FlashInfer b12x | Δ |
|---|---:|---:|---:|
| prefill tok/s (median) | 16,924.6 | 28,237.7 | **+66.9%** |
| per-run wall | 30.98 s | 18.57 s | −40% |
| TTFT p50 | 19.4 s | 11.6 s | −40% |

Torch profiler (GPU-only, 6 steps): the dense-GEMM share drops
**43.3% → 7.9%** (the b12x kernel, 1050 launches), consistent with the
microbench speedup (5.1–5.7x on the prefill shapes).
