# [Perf] DeepSeek-V4.1: compile the vision encoder's norm, rotary and gated activation

[Upstream PR](https://github.com/sgl-project/sglang/pull/44964) · state: open · merged: False

## Original PR description

**Stacked on #44918.** Until that merges, this diff includes its commit; the change here is the last commit only.

## Motivation

The DeepSeek-V4.1 vision encoder runs its RMSNorms, 2D rotary and SiLU-gated MLP activation in fp32 eager mode, so each of
them is several elementwise kernels per layer (32 layers). With #44918 removing the host-side overhead, these launches and
the fp32 round trips through memory are a visible share of the encoder's time.

## Modifications

- `models/deepseek_v41_vit.py`: `rms_norm`, `apply_rotary` and `silu_and_mul` are wrapped in
  `torch.compile(dynamic=True, backend=get_compiler_backend())`, so each becomes one fused kernel.
  - `dynamic=True` keeps one graph across image grids; there is no recompile per image size.
  - `rms_norm` keeps `RMSNorm.forward_native`'s arithmetic (fp32 upcast, `rsqrt`, weight, downcast) and reads the module's
    weight and epsilon, so checkpoints load unchanged.
  - On by default; no new server args or env vars.
- Unit test: the compiled norm's Python function matches `RMSNorm.forward_native` bit-exactly.

## Accuracy Tests

The fused kernels reorder fp32 arithmetic, so the encoder output is not bit-exact with eager: cosine similarity 0.99974
against the eager encoder at 512x512, 768x1024 and 2048x1600 (same random weights), and identical between eager and CUDA
graph replay with this change.

MMMU, DeepSeek-V4.1-Flash TP4 on MI350X, same image with and without this commit:

| MMMU | Score |
|---|---|
| without this change (two runs) | 0.7567, 0.7400 |
| with this change | 0.7544 |

The difference is within run-to-run spread (+0.6 pts against the pooled baseline, p = 0.54; the two baseline runs differ by
1.7 pts).

`test/registered/unit/models/test_deepseek_v41_vit_graph.py`: 8 passed on MI350X.

## Speed Tests and Profiling

**Encoder alone** (MI350X, one image, CUDA graph replay from #44918, ms per image):

| Grid | Before | After | Change |
|---|---|---|---|
| 512x512 | 10.83 | 6.46 | −40% |
| 768x1024 | 18.52 | 12.83 | −31% |
| 2048x1600 | 39.84 | 30.72 | −23% |

Dynamo compiles the three functions once, on the first image, and never again across the three grids (no recompiles). In
the server that first image is the warm-up request, so the compile (3.4 s for the first image with an empty inductor
cache) finishes before the server reports ready and never lands on a client request. Server start to ready: 347/349 s
with this change, 345/345 s without.

**Serving:** DeepSeek-V4.1-Flash, TP4, MI350X, `bench_serve` with `sglang-oai-chat` and one random image per request, n = 2
runs per arm, same image with and without this commit. The rows below are the ones free of the FP4 indexer's
serving-time Triton compiles (fixed separately in #44965), which otherwise land at random in either arm:

| Image, input, concurrency | Median TTFT | Median TPOT | Output throughput |
|---|---|---|---|
| 768x1024, 1024, 16 | −3.4% | −4.6% | +4.6% |
| 768x1024, 256, 16 | −11.0% | −7.5% | +6.4% |
| 768x1024, 1024, 4 | −5.1% | −3.3% | +2.4% |
| 768x1024, 1024, 64 | −8.8% | −5.6% | +8.4% |
| 768x1024, 1024, 256 | −11.2% | −13.1% | +13.6% |
| **Geomean** | **−7.9%** | **−6.9%** | **+7.0%** |
