# [diffusion] perf: decode plain base64 MiniMax-H3 materials without a per-character loop

[Upstream PR](https://github.com/sgl-project/sglang/pull/43117) · state: closed · merged: True

## Original PR description

## Motivation

MiniMax-H3 writes base64 material URIs (Ref2VA references, keyframes, reference audio) to a local file on the HTTP path, before the request is queued. The payload was validated and decoded one character at a time in Python. A reference image at a 2048-px short edge is a ~14.5 MB PNG, about 19 M base64 characters: 3.53 s per request on the B300 host's Xeon 6787P, all of it inside the client's measured latency.

## Modifications

- A payload that is plain base64 text (the standard or URL-safe alphabet, then at most two `=`) is decoded window by window: the same 1 Mi-character windows and the same `_decode_base64_chunk` as before, one interpreter step per window instead of per character.
- Payloads with percent escapes or whitespace, which material URIs may carry, and every malformed payload, keep the per-character path. Accepted inputs, error messages, and partial-file cleanup are unchanged.
- The two paths share the length and padding checks (`_check_base64_size`).

## Accuracy Tests

The decoded file is byte-identical to the per-character path. Unit tests (`test/unit/test_minimax_h3_media.py`, 43 passed):
- Both paths agree on standard, URL-safe, and unpadded payloads at sizes that cross window boundaries (windows shrunk to 16 characters).
- Each invalid payload (empty, bad length, over-padding, data after padding, a character outside the alphabet) raises the same error and leaves no partial file.
- Escaped and whitespace payloads still decode.
- A plain payload never reaches the per-character iterator.

## Speed Tests and Profiling

- Decode of a 14.5 MB PNG reference: 3.53 s → 0.058 s.
- Ref2VA end-to-end client latency, 50 steps, 2 GPUs, Ulysses 2, all else equal: −0.75 s on 4×H200 and −0.85 s on 4×B300. The output MP4 is byte-identical.
