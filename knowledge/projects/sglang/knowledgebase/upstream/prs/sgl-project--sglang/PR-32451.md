#  [Apple Silicon] Add MLX block paged attention decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/32451) · state: closed · merged: False

## Original PR description

## Summary
This PR adds an experimental block-table paged attention decode path for the MLX backend on Apple Silicon.

Part of the Apple Device Support roadmap (https://github.com/sgl-project/sglang/issues/19137).

The existing MLX decode path keeps legacy flat/contiguous KV cache behavior and uses padded SDPA by default. This PR adds an opt-in block KV pool and Metal decode kernel that read K/V through block tables instead of padding every request to the longest sequence in the batch.
## Motivation

Skewed decode batches waste work in the padded SDPA path because each request is padded to the batch maximum sequence length. Block-table paged attention lets decode read only visible KV tokens through request block tables:

```text
block_tables[batch, logical_block] -> physical_block
k/v[physical_block, block_offset, kv_head, head_dim]
```

This keeps legacy MLX behavior available while adding a path that is closer to standard block-table paged attention.

## Modifications

- Add `SGLANG_MLX_USE_BLOCK_PAGED_ATTENTION`. set DISABLED by default.
- Add `MLXBlockPagedAttentionMetadata`.
- Add `MlxBlockAttentionKVPool`.
- Add `sgl_kernel.metal.block_paged_attention_decode(...)`.
- Implement the block decode kernel as a 256-thread multi-warp Metal kernel.
  - 8 SIMD groups per `(batch, q_head)`.
  - Per-warp online softmax state.
  - Threadgroup-memory merge of per-warp `(max, sum, accumulator)` state.
  - Supports `head_dim <= 256`.
- Add Metal AOT extension split:
  - `metal_common.{h,cpp}`
  - `bindings.cpp`
  - `paged_attention.{cpp,metal}`
- Keep legacy flat/contiguous MLX KV cache behavior as fallback/default.
- Extend `bench_one_batch` with `--skewed-input-lens` for skewed decode benchmarking.
- Update Apple Metal docs with the block paged attention opt-in flag.

## How to enable

```bash
SGLANG_USE_MLX=1 \
SGLANG_MLX_USE_BLOCK_PAGED_ATTENTION=1 \
python -m sglang.launch_server \
  --model-path mlx-community/Qwen3-0.6B-4bit \
  --host 127.0.0.1 \
  --port 30000 \
  --disable-cuda-graph
```

To force legacy MLX behavior:

```bash
SGLANG_USE_MLX=1 \
SGLANG_MLX_USE_BLOCK_PAGED_ATTENTION=0 \
python -m sglang.launch_server \
  --model-path mlx-community/Qwen3-0.6B-4bit \
  --host 127.0.0.1 \
  --port 30000 \
  --disable-cuda-graph
```

## Performance Notes

This PR should be interpreted as an opt-in block-table decode path, not as a universal replacement for the existing padded SDPA decode path yet.

The expected win is for skewed or fragmented decode batches, where padded SDPA wastes work by padding every request to the longest sequence in the batch. In those cases, block paged attention reads only the visible KV tokens through the request block table.

@jlee5814 Reviewer-reported median decode throughput `Qwen3-0.6B-4bit`, `--output-len 64`:

| Workload | Flag off | Flag on | Ratio |
|---|---:|---:|---:|
| `--batch-size 1 --input-len 128` | 301.12 | 239.22 | 0.79x |
| `--skewed-input-lens 128 512 1024 2048` | 133.98 | 209.23 | 1.56x |
| `--skewed-input-lens 32 64 512 2048` | 134.68 | 229.21 | 1.70x |

So the current result is workload-dependent:

- Uniform single-request decode regresses because there is little or no padding work to remove, while block-table metadata reads and the custom kernel dispatch still add fixed overhead.
- Skewed decode batches improve because the fallback path pads to the batch maximum sequence length, while the block path reads only each request's visible KV tokens.
- The win is expected to become more relevant for high-request-count and fragmented serving workloads, which are the workloads paged attention is primarily meant to address.

This PR is still an incremental decode-side step. Follow-up work is planned around prefill/radix integration and broader block-table plumbing, which should make the paged-attention path more representative of the intended high-fragmentation serving case.

Please do not report this decode step as synchronized to the flat radix pool merely because block-paged attention ran.

With `SGLANG_MLX_USE_BLOCK_PAGED_ATTENTION=1` and custom RoPE left disabled (the documented/default combination), `attention_wrapper.py` uses built-in RoPE and writes the new K/V only to the per-request contiguous cache and `MlxBlockAttentionKVPool`. This branch nevertheless returns `pool_synced_offsets`; `decode_batch_finalize()` then advances both `_req_synced_offset` and `_req_block_synced_offset`. `_sync_decode_kv_to_pool()` subsequently sees `current_offset <= _req_synced_offset` and skips the flat-pool copy.

I reproduced this without a model: starting with flat marker 1 and cache offset 2, block finalize moved both markers to 2; a flush left flat slot 2 at `[0, 0]`. Keeping the flat marker at 1 made the same flush write the expected `[3, 4]`. A later radix prefix hit can therefore consume stale K/V and produce incorrect logits. Please track flat and block synchronization independently, advancing the flat marker only when the fused RoPE path actually wrote valid flat-pool slots (or explicitly copy this decode K/V to the flat pool). Add a block-on/custom-RoPE-off decode -> flush/remove -> radix-reuse regression.

- yeahdongcn · comment · 2026-07-29T02:49:35Z · [source](https://github.com/sgl-project/sglang/pull/32451#discussion_r3670608448)

File: `python/sglang/srt/hardware_backend/mlx/model_runner.py` · line None

This token-derived block count does not provide the capacity exposed to scheduler admission.

Blocks are owned per request, so real consumption is `sum(ceil(request_tokens / 16))`, not `ceil(sum(request_tokens) / 16)`. With `_pool_size=256`, this creates 16 usable blocks; the 17th one-token request returns no block after only 17 of the scheduler's 256 logical token slots have been consumed. The scheduler can therefore admit a batch that this late runner-side allocator cannot represent.

The failure is also non-atomic: `prefill_finalize()` commits `_req_token_ids`, `_req_caches`, `_req_pool_idx`, and `_req_synced_offset` before `_sync_full_kv_to_block_pool()` raises. My exhaustion probe left all of those entries populated for the failed request. Please make admission block-aware (including per-request fragmentation/headroom), preflight before committing state, and roll back every allocation on failure. Add regressions with at least 17 one-token requests for a 256-token pool and with release/reallocation after exhaustion.

Please account for both KV representations in the memory budget and allocate this pool only when the block kernel is actually usable.

`_compute_pool_size()` chooses `pool_size` so one K/V representation approximately consumes `kv_budget`. With radix cache enabled, this new block pool is followed by the existing full flat `MlxAttentionKVPool`, making the feature consume roughly two KV budgets on unified memory. The allocation is guarded only by the environment flag, not by `self._aot_kernels.block_paged_attention.enabled` or model support, so missing Metal ops, `head_dim > 256`, and auxiliary-state models that fall back to padded SDPA still allocate and populate the unused block pool.

This can turn an advertised fallback into an OOM or block-exhaustion failure. Please either budget/split capacity across both representations or avoid the duplicate full-size representation, and gate block allocation/synchronization on the kernel and cache layout that will actually execute.
