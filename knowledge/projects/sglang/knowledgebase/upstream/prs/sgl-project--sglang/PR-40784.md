**Motivation**

The ROCm gfx95 linear miss planner (introduced in 4/N, `_can_use_separate_copy`) scans top-k token
tags one request at a time. For the specific swap-in shape used by GLM-5.2-style DSA HiSparse
(`swap_in_block_size=1024`, `top_k=2048`, `device_buffer_size=4096`), gfx95's wave64 execution width
lets four independent lookup passes be gathered and scanned together in one pass instead of four,
while preserving hit/eviction order and leaving the real KV copy unchanged (it still runs
immediately after planning, before any attention read of the restored KV).

**Modifications**

- `hisparse_coordinator.py`: `_can_use_batched_prefix(...)` determines whether the batched scan
  applies — HIP, `SGLANG_USE_AITER`, `is_gfx95_supported()`, the DSA MLA pool (not DSV4), and the
  qualified swap-in shape. It is unconditional on that path: any disqualifying input (wrong
  hardware, AITER off, a different swap-in shape) falls back to the existing per-request scan
  automatically, with no separate switch to enable it.
- `kernels/ops/kvcache/hisparse.py` / `hisparse.cuh`: `batched_prefix` is a compile-time kernel flag
  selecting the wave64 batched planner at JIT time; the qualification is re-checked at the kernel
  dispatch layer (shape, dtype, device) independent of the coordinator's own check.
- Gfx95 wave64 scan preserves hit/eviction order and only changes how the four lookup passes are
  gathered before scanning, not what they compute.

**Tests**

- `test/registered/unit/managers/test_rocm_hisparse_optimizations.py`:
  `test_batched_prefix_gate_requires_qualified_shape_and_hardware` directly regression-tests
  `_can_use_batched_prefix` (true for the qualified case; false for each of HIP off, AITER off,
  gfx95 off, DSV4, and each of the three shape fields individually).
  `test_batched_prefix_keeps_real_copy_after_planning` checks that, given the qualified path, the
  `batched_prefix` kwarg reaches the plan kernel call and the real copy still immediately follows
  planning with unchanged `skip_io`/ordering semantics.
- `test/registered/amd/test_hisparse_batched_prefix.py` (GPU, gfx95-only): batched vs. unbatched
  scans (`enabled in (False, True)`) are checked for bit-identical results across eager execution,
  CUDA-graph capture/replay, request-index and sequence-length dtype combinations (int32/int64), and
  five tag patterns (empty, full, mixed, newest-token, short-sequence).

## C1 steady-state decode

GLM-5.2 FP8 with BF16 KV, TP4 on MI355X, stock SGLang v0.5.20 image on ROCm 7.2.4. The workload is a 32,768-token prompt and a fixed 256-token output, measured after 64 warm tokens; each value is the median of the 192 measured intervals. The baseline is 4/N (#40783) alone on main, and the PR is 4/N plus this PR. Each arm ran 8 times, each on a fresh server, with the arms interleaved. Lower is faster.

| Prefetch | 4/N (ms/token) | 4/N + this PR (ms/token) | Change | p (Welch) |
|---|---:|---:|---:|---:|
| Off | 15.544 ± 0.018 | 15.459 ± 0.031 | −0.55% | 2.4e-5 |
| On | 16.111 ± 0.025 | 16.005 ± 0.011 | −0.66% | 8.9e-7 |

## Miss-planner microbenchmark

One MI355X. Top-k is 2048 with a 4,096-slot hot buffer, a 32K context and miss rates of 2–40%. Times are per planner call, from graph replays, with the reset cost subtracted. Outputs are identical to 4/N's for every configuration, in both eager and graph modes.
