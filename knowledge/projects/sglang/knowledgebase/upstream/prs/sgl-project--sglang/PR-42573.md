# [Fix] dots: Fix cubic regex backtracking in the tool-call parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/42573) · state: open · merged: False

## Original PR description

## Motivation

`DotsToolDetector.detect_and_parse` finds tool-call blocks with

```python
r"<dots_function_call>\s*(.*?)\s*</dots_function_call>"
```

When the model emits the opening marker but never the closing one, `\s*`, the lazy `(.*?)` and the second `\s*` backtrack over every split of a whitespace run, so the match is **cubic** in the run length:

| Input | Before | After |
|---|---|---|
| `<dots_function_call>` + 2,000 newlines (~2 KB) | 12.8 s | 0.4 ms |
| `<dots_function_call>` + 200,000 newlines | hours (extrapolated) | 0.1 ms |
| 14 KB fuzzer-found input | 54.3 s | 0.1 ms |

Tool-call parsing runs synchronously on the tokenizer manager's event loop, so a single such response, which a user can elicit through the prompt, stalls every in-flight request on the server.

Found with an Atheris coverage-guided fuzzing harness over all tool-call detectors, which records per-input parse time.

## Modifications

- Replace the regex with a linear `str.find` scan over complete `bot ... eot` blocks, the same approach `parse_streaming_increment` in this detector already uses. `_parse_block` already `.strip()`s each body, so the `\s*` around the group never affected results.
- Add a bug-regression test: a complete call followed by an unclosed marker and 20k newlines must parse in < 1 s and still return the complete call. It takes > 90 s on `main` and ~1 ms with this change.

## Accuracy Tests

No model-output change. `test_dots_detector.py`: 11/11 pass (10 existing + 1 new).

## Speed Tests and Profiling

See the table above. Re-fuzzing the fixed detector (365k executions) found no slow inputs.
