# [Fix] scheduler: Clear setwise pooling positions when a request is aborted

[Upstream PR](https://github.com/sgl-project/sglang/pull/48100) · state: open · merged: False

## Original PR description

## Motivation

An aborted setwise score request crashes the scheduler, taking down every in-flight request.

Setwise scoring (#38965, CausalLM support in #41188) reads label scores at every `score_extraction_token_id` marker in a prompt, via the request's `token_indices_to_pool`. Only those requests carry pooling positions; for all others the field is `None`.

`Req.set_finish_with_abort` shrinks the prompt to one token so the long prefill is skipped, but keeps `token_indices_to_pool`. The logits processor then reads positions past that one token and hits `vectorized gather kernel index out of bounds` (`CUDA error: device-side assert triggered`). Any abort path triggers it, the easiest being a prompt longer than the context.

## Modifications

- Clear `token_indices_to_pool` in `set_finish_with_abort`, next to the existing one-token prompt reset. Requests without pooling positions are unaffected.
- Unit test in `test_setwise_score_mixin.py` that fails on main and passes with the fix.

## Accuracy Tests

Stock `Qwen3.5-2B` with setwise scoring (`--disable-radix-cache --chunked-prefill-size -1 --max-total-tokens 4096`), on 1xH100. A 200-token request, then a 6,010-token one, then the 200-token one again:

| | main | this PR |
|---|---|---|
| over-length request | scheduler crashes, engine killed | `ValueError: Input length (6010 tokens) exceeds the maximum allowed length (4090 tokens)` |
| next request | no server | same scores as the first request |

Tested on a v0.5.22 build with main's sources.

## Speed Tests and Profiling

No performance impact: one attribute assignment on the abort path.
