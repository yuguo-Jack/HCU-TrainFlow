# [UMBP] Support MiniMax-M3 sparse KV in the direct external linker

[Upstream PR](https://github.com/sgl-project/sglang/pull/44067) · state: open · merged: False

## Original PR description

## Motivation

The direct UMBP linker (`--enable-unified-cache-external-linker`, DRAM KV offload) only builds device pool groups for DeepSeek-V4 and DSA. A MiniMax-M3 prefill with the linker fails at startup:

```
ValueError: The selected hybrid pool strategy does not support the direct external linker: _MiniMaxSparseStrategy.
```

So M3 cannot run PD prefill with UMBP KV offload, the setup AMD's agentic PD recipes use for DeepSeek-V4.

Plan:
1. This PR: linker pool group for the released M3 layout (main KV + K-only lightning-indexer cache).
2. Follow-up if needed: HiSparse, index-V sparse layers and MTP drafts (rejected for now).

## Modifications

- `linker_pool_assembler.py`: `_build_minimax_sparse_device_pool_group`.
  - `KV` = main-pool K and V of every layer.
  - `INDEXER` = K-only index cache of the sparse layers, keyed by global layer id and sharing KV's page ids (the same pairing PD transfer uses via `StateType.MINIMAX_INDEX_K`).
  - `rank_replicated=False`, since GQA KV heads are sharded across TP ranks.
  - Rows follow `kv_cache_layout`: token rows for `nhd`, page rows for `hnd` / `vectorized_5d`.
- `hybrid_pool_assembler.py`: `_MiniMaxSparseStrategy.build_direct_linker_pool_group`.
- HiSparse, index-V layers, scaled KV and MTP drafts raise instead of offloading partial state.
- Unit test in `test_linker_pool_assembler.py`; it fails on `main` with the error above.

## Accuracy Tests

Setup: MiniMax-M3-MXFP8 on one MI355X node, mori PD with TP4 prefill + TP4 decode. The prefill runs the linker against a UMBP standalone server with a 200 GB DRAM tier.

- **Load-back:** ~8K-token retrieval prompt. A = cold; C = resend (GPU radix hit); then `/flush_cache`; B = resend, with 7,936 tokens restored from UMBP. **B == C exactly**, and both give the correct `84903, 18242, 00198`.
- **Chat probe through the PD router:** GSM8K-style question answered `#### 72`, `finish_reason=stop`.

## Speed Tests and Profiling

Offload volume is 22,656 B/token/rank: 15,360 B of fp8 main KV plus 7,296 B of index-K for the 57 sparse layers. Medians; on = PD + linker, off = PD only:

| input | TTFT on / off (ms) | PD transfer tail on / off (ms) | offload write (ms) |
|---|---|---|---|
| 8K | 282 / 279 | 7.4 / 6.6 | 31 |
| 32K | 1,061 / 1,057 | 14.2 / 12.8 | 127 |
| 128K | 4,529 / 4,522 | 33.0 / 30.0 | 537 |
| 512K | 23,667 / 23,577 | 105.8 / 100.1 | 2,197 |

- The offload starts when the last chunk is queued for PD transfer and runs at ~5-6 GB/s per rank.
- Sequential TTFT cost is <= 0.4%; 8 x 32K concurrent bursts are +5% TTFT.

Known issue on the UMBP side, not introduced here: occasional first-use puts of 3-17 s, at warmup or the first burst, delay the next prefill. On the test node they correlated with host direct reclaim.

Tested on an image built from `main` at 41cbe65de0; the touched code is unchanged on current `main`. The unit test was run on this branch.
