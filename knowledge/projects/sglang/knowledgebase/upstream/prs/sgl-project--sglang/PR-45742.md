# [Feat] [Intel] xpu: Add Level Zero IPC helpers to share device memory between processes

[Upstream PR](https://github.com/sgl-project/sglang/pull/45742) · state: open · merged: False

## Original PR description

## Motivation

sglang has no way to share Intel GPU (XPU) device memory between processes. Its IPC paths, the CUDA IPC and CUDA VMM multimodal transports, custom all-reduce and the weight-update cache, are built on CUDA, and torch has no XPU counterpart to build on yet:

| What the CUDA paths use | Status for XPU in torch |
|---|---|
| `UntypedStorage._share_cuda_` / `rebuild_cuda_tensor` | No `_share_xpu_` in any build. Pickling an XPU tensor across processes fails with `_share_fd_: only available on CPU`. Storage sharing is the open PR pytorch/pytorch#191725 |
| `torch.cuda.Event(interprocess=True)` | On PyTorch main since 2026-08-18, but `torch/csrc/xpu/Event.cpp` compiles it only for `SYCL_COMPILER_VERSION >= 20260200`, and no published XPU wheel is built against SYCL 2026.2 |
| CUDA driver VMM / FABRIC handles (`cuda_vmm_transport_utils.py`) | CUDA only |

This PR adds the missing piece in the same shape as `cuda_vmm_transport_utils.py`: a small ctypes layer over the Level Zero driver, plus an fd handoff over a Unix socket. Nothing in sglang calls it yet. Its first user is sglang-omni's opt-in Level-Zero stage transport (sgl-project/sglang-omni#2802), which currently carries this code itself. With these helpers in sglang, sglang-omni keeps only its relay, and other XPU paths in sglang can use the same code.

#40763 (draft) adds Level Zero VMM export (`zePhysicalMem*`) for DWDP, exchanged collectively over a process group. This PR covers the other case: a plain device allocation exported through an IPC handle and served on demand to any local process, with no process group.

## Modifications

New `python/sglang/srt/utils/xpu_ipc_utils.py` (torch and the stdlib only):

- **`LevelZeroIpcContext`.** A private Level Zero context created through `libze_loader.so.1`. Its methods:
  - `allocate_exportable` makes device memory with a dma_buf export descriptor. Asking for export at allocation time keeps the memory uncompressed, so another card can read it, and torch's allocator settings (expandable segments included) cannot change what gets exported.
  - `export_segment` returns the 64-byte IPC handle, whose first four bytes are the dma_buf fd.
  - `open_peer_segment` / `close_peer_segment` map and unmap a peer's handle on a local device.
  - `free` and `destroy` release the memory and the context.
- **`XpuIpcHandleServer` / `fetch_xpu_ipc_handle`.** A dma_buf fd can't travel inside a pickle or a ZMQ message. The exporter therefore serves the handle and fd from an abstract-namespace `AF_UNIX` `SOCK_SEQPACKET` socket with `SCM_RIGHTS`, as `_PosixFdBroker` does for CUDA VMM.
  - Peers of another user are turned away on connect (`SO_PEERCRED`).
  - One selector thread watches every waiting peer, so a peer that never sends its request holds nobody up and is dropped at its deadline.
  - `close()` returns only once nothing can send the fd any more, so the caller can release the segment right after.
  - The importer closes any fds that arrive with a short, oversized or truncated reply.
  - Segment ids are limited to 512 bytes (`XPU_IPC_SEGMENT_ID_LIMIT_BYTES`), and the server rejects a longer one when it is constructed.
- **The fd in the handle.** The importer writes the received fd into the handle's first four bytes. If its number happens to equal the exporter's, it writes a duplicate instead. This is needed because the driver imports through `pidfd_getfd` when the handle looks unchanged, and that needs ptrace permission, which default Docker does not grant. Passing the fd over a socket needs none.
- **`tensor_from_device_pointer`.** Wraps device memory as a non-owning `uint8` tensor through `torch._C._construct_storage_from_data_pointer`, as `cuda_vmm_utils.tensor_from_pointer` does. XPU device pointers set bit 63, so the pointer is passed as a signed int64.
- **`is_xpu_ipc_available`.** Checks that the driver exposes exactly the devices torch sees (device indices travel between processes as torch indices) and that every device can export a dma_buf. The XPU runtime is initialized before the Level Zero loader is used, because a newer loader that already reported a device count before init rejects the runtime's later `zeInit`.

## Accuracy Tests

The module only shares memory; it touches no model numerics. The hardware test writes two patterns in one process and reads both through one mapping in another, comparing them byte for byte. It passes on the same card and across two cards.

## Speed Tests and Profiling

Nothing in sglang uses the module yet, so no sglang path changes speed. For scale, sglang-omni's stage relay built on this module moves payloads between two processes on 8x Arc Pro B60. It drives the production send path, and every one of 6,144 transfers was byte-exact. The table shows median delivered latency, shared memory → this module, with the speedup in brackets:

| payload | xpu:0 → xpu:0 | xpu:0 → xpu:3 |
|---|---|---|
| 1 MiB | 5.15 → 3.86 ms (1.3x) | 5.09 → 2.87 ms (1.8x) |
| 4 MiB | 9.67 → 3.24 ms (3.0x) | 9.80 → 2.90 ms (3.4x) |
| 16 MiB | 40.84 → 3.94 ms (10.4x) | 40.61 → 4.37 ms (9.3x) |
| 32 MiB | 73.47 → 5.13 ms (14.3x) | 75.15 → 6.22 ms (12.1x) |

In the same runs, sglang-omni#2802, which carries this code itself with DLPack wrapping instead of the storage constructor, measured within 5% of these numbers in every cell.

## Tests

- `test/registered/unit/utils/test_xpu_ipc_utils.py` (CPU, `base-a-test-cpu`), 14 tests:
  - the handle server: a round trip; an unknown segment and a non-UTF-8 request rejected without leaking an fd or stopping the server; an over-long segment id refused up front; close waiting for a peer being served; silent peers holding up neither an importer nor the close; another user turned away; a uid past 2^31 still read as the same user; a peer dropped while its request is pending;
  - malformed replies, which are refused without keeping an fd;
  - the fd-collision rule;
  - the probe with no XPU build, no driver, no devices, a device-count mismatch, no dma_buf export, and a missing loader.
- `test/registered/xpu/test_xpu_ipc_utils_xpu.py` (`stage-a-test-1-gpu-xpu`):
  - the two-process export/import round trip on one card and across two (the second skips on a 1-GPU runner);
  - the wrapped tensor aliasing the memory.

Run on 8x Arc Pro B60 with torch 2.13.0+xpu and torch 2.14.0.dev20260720+xpu: 17 passed. Removing the signed-pointer conversion makes the hardware tests fail, with `_construct_storage_from_data_pointer(): incompatible function arguments`.
