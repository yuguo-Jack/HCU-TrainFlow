# perf: fix overlap scheduling for NVIDIA Confidential Computing(CC) on Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/36810) · state: open · merged: False

## Original PR description

## Motivation

Under NVIDIA Confidential Computing (CC), `cudaMemcpyAsync` (D2H) is forced synchronous — it blocks at issue — so the per-step readback of `next_token_ids` / logprobs serializes onto the scheduler's critical path and kills decode overlap.

## Modifications

**`async device->host result-readback worker`** (afdde3e4a0)
- New `python/sglang/srt/managers/async_d2h_copy_worker.py` (`AsyncD2HCopyWorker`): runs the per-step D2H copy on a dedicated thread with its own private CUDA stream, off the scheduler's critical path, so overlap is preserved. `submit()` returns a `HostCopyDone` that is a drop-in for the `copy_done` CUDA event, so no result-processing code changes.
- Wired into `scheduler.py` / `managers/utils.py`; only routed through the worker when CC is detected.
- Adds `is_confidential_compute()` to `srt/utils/common.py`.

**`TRTLLM-style CC detection`** (512bd0994a)
- Prefers `nvmlSystemGetConfComputeSettings` and treats PPCIE as CC, falling back to the simple query on older GPUs.

**Review follow-ups** (0d4f4717df, 437dc1b347, cc18c816fe)
- The worker thread pins itself to the creating thread's device. Without this it defaults to device 0, and the stream context manager's enter/exit opens a CUDA context there on every non-zero rank — measured at **+622 MiB on GPU 0** from a single rank-1 process (2xB200).
- CC detection is gated on `is_cuda()` rather than `torch.cuda.is_available()`, which is also true on ROCm. AMD launches were reaching the NVML path and logging at ERROR on every scheduler process; the "cannot query" cases are now `warning`, since the fallback (`False`) is correct.
- The override moved to `envs.SGLANG_FORCE_CONFIDENTIAL_COMPUTE` (`EnvBool(None)`, `FORCE_` verb for an autodetect override) per `.claude/skills/env-var-conventions`. This also fixes a footgun: the previous `forced == "1"` check made `SGLANG_CONFIDENTIAL_COMPUTE=true` silently read as *off*.
- Test moved to `test/registered/unit/managers/` to match the current registered-test layout.
- Comments trimmed per `.claude/rules/comment-style.md` (class docstring 30 -> 9 lines; file 147 -> 106).

## Tests

`test/registered/unit/managers/test_async_d2h_copy_worker.py` — worker unit tests. `test_copy_waits_for_the_producing_stream` queues `torch.cuda._sleep` + `fill_()` on a side stream and submits with that stream current, so it fails if the readiness event is dropped or recorded on the wrong stream (verified against a patched-out `src_ready`: it reads zeros).

`test/registered/scheduler/test_async_d2h_copy_worker_server.py` — server-level coverage. CI GPUs never run CC, so the force override is what makes this path reachable. Launches a server with the worker on and runs concurrent greedy `return_logprob` requests, asserting identical completions and 1:1 logprobs. Both scheduler submit sites are covered: the inline-sample one, and `launch_batch_sample_if_needed` via `SGLANG_ENABLE_DELAY_SAMPLE`.

Both run green on 2xB200 (6 unit tests; 2 server tests in 164s, with `using async D2H copy worker` logged by each server).

[by Claude Code] **Severity: functional | Confidence: High**

**Issue**

The worker thread never sets its CUDA device, so it starts on device 0. When `with self.device_module.stream(self.d2h_copy_stream)` exits, PyTorch restores device 0's stream and calls `cudaSetDevice(0)`. On a rank whose GPU is not 0, this creates a CUDA context on GPU 0.

**Example**

On 2x A100 (PyTorch 2.5.1), a process on `cuda:1` that runs one `submit()` raises GPU 0 memory from 4 MiB to 425 MiB. With TP8, GPU 0 gets seven extra contexts after the KV pool is already sized.

**Fix**

Save `device_module.current_device()` in `__init__` and call `self.device_module.set_device(...)` first thing in `_loop`, as `memory_pool._recycle_loop` does. With that change GPU 0 stays at 4 MiB.

[by Claude Code] **Severity: functional | Confidence: Medium**

**Issue**

With the worker, the D2H copy for step N starts only after a host wait and a GIL hand-off. By then the scheduler has usually launched forward N+1 on `forward_stream`, and nothing makes that forward wait for the copy. Some copy sources are persistent buffers that forward N+1 rewrites, so the copy can read step N+1 data. The same applies at L4784.

**Example**

DSpark folded accept returns `next_token_ids` and `accept_lens` as slices of `out_tokens_buf` and `commit_lens_buf` (`dspark_verify.py`, `read_accept`). Decode CUDA graph `hidden_states` is a slice of the graph's static output.

**Fix**

Clone these tensors on `forward_stream` before `submit()`, as TRT-LLM's `_copy_to_host` does with `src.clone()`.

[By Claude Code] Not changing this one — happy to be shown wrong.

The dflash accept buffers are double-buffered (`dflash_worker_v2.py`: `for _ in range(2)`, then `slot = (slot + 1) % 2`), so forward N+1 writes the other slot, and `copy_done.synchronize()` for step N runs during iteration N+1, before forward N+2 can reuse slot N. (`dspark_verify.py` / `read_accept` do not exist on this branch, so I may be looking at the wrong thing.)

More broadly, the PR does not change this ordering. `copy_stream.wait_stream(forward_stream)` was already there, and nothing has ever made `forward_stream` wait on the copy — the existing comment states it deliberately: "it's a leaf gated by copy_done, so nothing on forward_stream waits." The worker copy has the same relationship to forward N+1 as the current `copy_stream` copy.

What does change: under CC the inline copy blocks at issue, so it finished before forward N+1 was enqueued. The worker removes that incidental serialization, which leaves CC with the same exposure as every non-CC deployment rather than a worse one. If that exposure is a real hazard it is a mainline overlap bug affecting everyone, and worth its own issue; cloning here would add a device copy to the hot path for a risk mainline already accepts.

**Issue**

`is_confidential_compute()` catches only `pynvml.NVMLError`. With an older `pynvml`, the symbol lookups here raise `AttributeError`, which escapes and fails `Scheduler.init_overlap()`. Overlap is on by default, so the server fails to start on non-CC GPUs too. `python/pyproject.toml` lists `nvidia-ml-py` with no version.

**Example**

With NVML stubbed to a non-CC result, `nvidia-ml-py` 12.535.161 and `pynvml` 11.5.3 have no `c_nvmlSystemConfComputeSettings_v1_t`, and 12.550.52 has no `NVML_CC_SYSTEM_MULTIGPU_PROTECTED_PCIE`. All three raise `AttributeError`. 12.555.43 returns `False`.

**Fix**

Catch `AttributeError` together with `pynvml.NVMLError` and return `False`, as `cuda_vmm_utils.py` does for the fabric-info struct. TRT-LLM avoids this by requiring `nvidia-ml-py>=13`.
