# [Fix] unified-memory: Refuse allocation before post-capture resize

[Upstream PR](https://github.com/sgl-project/sglang/pull/44746) · state: closed · merged: False

## Original PR description

## Motivation

`test/registered/unit/mem_cache/test_unified_post_capture_sizing.py` aborts with exit -6 (`CUDBG_EXCEPTION_WARP_MMU_FAULT` in `_zero_pages_kernel`) since #42930. It was seen on the 5090 runner and reproduces on H200 (SM90); the parent of 8d229d96e0 passes.

With post-capture KV sizing, `UnifiedKVPool.finalize_backing` backs only the final byte prefix of the reserved VA, but the unified SWA allocator keeps pricing the whole reservation until `resize()` runs. An allocation in that window gets a top-end SWA page past the backed bytes (page 131071 of a 64 MiB reservation with 16 MiB backed). Before #42930 this only touched bookkeeping for MHA pools. #42930 zeroes MHA page envelopes on hand-out, so the same allocation now writes to unmapped memory.

The production path (`kv_pool_runtime.py`) calls `finalize_backing` and then `resize` straight away, so this was hit only by the test. It is still a latent fault for any allocation before `resize`.

## Modifications

- `UnifiedSWAAllocatorBase.__init__` sets `_awaiting_resize` when post-capture backing is active; `UnifiedSWATokenToKVPoolAllocator.resize()` clears it. `ensure_capacity()` raises until then; every allocation path goes through it.
- Test: add "allocation before finalize_backing" (the construction-to-finalize window, where graph capture and prewarm run) and "allocation between finalize_backing and resize" subtests that expect the new error. The "resize with live allocations" subtest now allocates after `resize` and checks that a second `resize` is rejected as non-empty.
