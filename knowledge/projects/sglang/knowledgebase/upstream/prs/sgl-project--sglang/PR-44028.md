# [Feat][NVIDIA] DeepSeek-V4.1: Engram precompute on GPU (10/N)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44028) · state: open · merged: False

## Motivation

Issue #42170 and #39700. Currently, all the hash token ids input to engram are computed at the beginning. But engram table lookup, wkv projection, collective communication are all computed in each engram layer in an ad-hoc manner, which can be performed in advance and be overlapped with mhc/attention because none of them depends on the hidden states of previous layer.

## Modifications

1. Do the prefetch (including engram gather, collectives and wkv proj) of layer N in advance and overlap the prefetch with mhc and attention.
2. Add EngramPrefetcher to produce and consume the engram kv.
3. Add moe_fence to sync megamoe with the prefetch results. Only after prefetch megamoe can be started because megamoe has num_sm requirements and cannot be overlapped with prefetch. 
4. Currently only megamoe backend + pure dp attention is supported to run engram prefetch. Other configs such as --moe-a2a-backend none or attn-tp > 1 or attn-cp > 1 will all make this function automatically disabled at runtime. 
5. The engram prefetch is only enabled for decode and target verify.

**Our config** (8×H200, SM90): DeepSeek-V4.1-Flash, TP8/EP4, **no DP attention and no MegaMoE** (our production shape minus DSPARK and HiCache, to keep the per-step signal clean), host-table path on via env:

```

SGLANG_DSV41_ENGRAM_HOST_TABLE_LAYOUT=shared
SGLANG_DSV41_ENGRAM_HOST_TABLE_PIN=1
SGLANG_ENABLE_DSV41_ENGRAM_KV_PREFETCH=0|1     # the only difference between arms
SGLANG_DSV41_ENGRAM_PREFETCH_MODE=auto
SGLANG_DSV41_ENGRAM_PREFETCH_MAX_TOKENS=64

sglang serve --model-path DeepSeek-V4.1-Flash --trust-remote-code \
  --tp-size 8 --ep-size 4 --dp-size 1 --mem-fraction-static 0.8 \
  --attention-backend dsv4 --moe-runner-backend flashinfer_mxfp4 \
  --disable-custom-all-reduce --max-running-requests 128 \
  --cuda-graph-max-bs-decode 64 --context-length 65536 \
  --chunked-prefill-size 8192 --max-prefill-tokens 16384 \
  --watchdog-timeout 3600 --random-seed 12345 --enable-metrics
```

Benchmark: interleaved arms (off-r1 → on-r1 → off-r2 → on-r2, so same-arm drift gives the noise ruler), decode `input-len 1024 / output-len 256`, concurrency 1/8/16/32/64.

The prefetch we compared was a rows-only variant of #38856 rather than this PR's full lookup+WKV offload: gather (plus the lookup collective) on a side stream once the first Engram layer's own host access has completed, WKV left on the consumer stream, and eligibility decided by an explicit `supports_concurrent_cuda_stream()` capability instead of probing fp8 internals. That is why it also runs on a block-FP8 SM90 backend.

**On trying your launch command on this box**: as posted it is a Blackwell/MegaMoE arm, and on our H200 it would run as an A/A. Two gates, both from this PR:

- `_can_prefetch_engram()` needs `attn_tp_size == 1` with pure DP attention, MegaMoE dispatch, and max-len DP padding. Our DSv4.1-Flash serving shape here is TP8/EP4 without DP attention, so the prefetcher is never constructed.
- `Engram.supports_prefetch()` needs the WKV GEMM to be FlashInfer CuTeDSL MXFP8 (or unquantized). On SM90 our WKV resolves to the block-FP8 fallback rather than that backend, so the predicate is False — the prefetcher would be built but never take a decode step.
