# [Feat] dsa: Extend interleave-CP breakable prefill graphs to GlmMoeDs…

[Upstream PR](https://github.com/sgl-project/sglang/pull/46890) · state: open · merged: False

## Original PR description

## Motivation

Enable the stock `breakable` prefill CUDA-graph backend under interleave context-parallel prefill (`--enable-prefill-cp --cp-strategy interleave --attn-cp-size N`) for DSA models served with the production **fp8 KV + trtllm** kernels (`GlmMoeDsaForCausalLM`: GLM-5.2 / GLM-5.3 and fine-tunes, EP > 1). Today prefill CP silently disables prefill graphs, so every small uncached chunk runs eagerly; on prefix-cache-heavy traffic (~87 % hit, uncached chunks mostly ≤ 8k tokens) that eager penalty is what makes stock CP4 lose to TP4 on E2E p99.

Scope: 5 files + 1 test, no new flags or kernels, no behaviour change when prefill CP is off or for `Glm5NextForConditionalGeneration` (already supported by #43774). The same patch against `release/v0.5.22` is https://github.com/duet-labs/sglang/pull/3.

## Design

- **Positions are always global.** `forward_batch.positions` stays global in eager CP and in BCG capture/replay; the attention backend and the indexer split op shard it through the CP metadata (`cp_shard_position_ids`). Under replay BCG already rewrites `per_rank_actual_token` to the captured per-rank rows, so the shard has exactly the local K's physical rows; the backend asserts that instead of inferring layout from tensor lengths (the length heuristic in the first revision was wrong for chunks where padded local rows == global positions, e.g. 4 tokens on CP4 — see Boundary matrix).
- **Live rows are explicit.** KV-cache writes under CP use `total_seq_lens` from the metadata (`cp_live_store_rows`), asserting it fits the gathered rows and `out_cache_loc`, instead of `min(...)` over tensor sizes.
- **The graph path mirrors the eager CP path.** Where the eager CP prefill branch and the TP split op disagreed (indexer fusion, head gate, slicing to `extend_num_tokens`, `out_cache_loc`), the split op now follows the eager CP branch.
- **Memory is the trade.** CP4 (EP4 weights) costs ≈19 GB/rank static vs TP4 and the graphs add 3.6–4.5 GB/rank; the patch does not hide that.
- CP2-in-TP4 is out of scope (`main` gates CP BCG to `attn_cp_size == tp_size`).

| `srt/layers/cp/utils.py` | new `cp_local_rope_positions(forward_batch, positions, local_k)` (shard global positions via the CP metadata, assert rows == local K rows) and `cp_live_store_rows(forward_batch, gathered_rows, what)` (live rows = `total_seq_lens`, asserted) |

Dead ends, for the record: `flashmla_sparse` refuses fp8 KV in-graph; bf16 KV captures without the position fix but halves the KV pool; the CP KV all-gather was not the fault (`CUDA_LAUNCH_BLOCKING=1` localised it to the position/`RopeQuantize` path).

- Fridge003 · comment · 2026-10-29T07:48:05Z · [source](https://github.com/sgl-project/sglang/pull/46890#discussion_r4409844614)

File: `python/sglang/srt/layers/attention/dsa_backend.py` · line None

With CP4 and 4 new tokens, each rank owns one valid K row, but CP padding expands its local K tensor to 4 rows. ForwardBatch.positions still contains the 4 global positions, so the new length check incorrectly skips sharding.

For example, with global positions [100, 101, 102, 103], ranks 1–3 should use 101, 102, and 103, respectively, but all use 100. GLM-5.2/5.3’s shared-index layers reach this branch. This applies incorrect RoPE to Q/K and writes incorrect keys into the KV cache. Disabling prefill graphs does not avoid the regression because the same check also affects eager execution.

Suggested fix: Shard positions according to the existing contract that ForwardBatch.positions remains global, then trim local Q/K separately. Avoid inferring layout from tensor lengths. Add regression coverage for short suffixes and shared-index layers with prefill graphs both enabled and disabled.

You're right — gating on `rope_positions.shape[0] != k.shape[0]` was a heuristic, and it breaks exactly as you describe: the interleave CP path pads each rank's local shard to a multiple of `attn_cp_size` (4 rows), so with 4 new tokens each rank has 1 live row in a 4-row local K while `forward_batch.positions` holds the 4 global positions → equal lengths → sharding skipped → every rank applies position `p0` instead of `p0 + rank`. Measured on the pre-fix tree (`ef05f8e7`, 4×B300, `incoai/GLM-5.3-NVFP4`): for a 4-token uncached chunk the prompt logprobs of tokens 2–3 come out −10.91 / −17.13 instead of −11.76 / −13.40 (the values the same tokens get as the prefix of a 16-token chunk), the greedy continuation diverges, and — as you said — eager CP is affected the same way, not just graph replay, so a graphs-on-vs-eager comparison alone cannot see it. Our original matrix started at 100 tokens, so it never hit it.

Fixed in 29525ad7 the way you suggest: `forward_batch.positions` stays global in every mode, and the fp8-KV `_forward_trtllm` branch (plus the indexer split op) always shards it through the CP metadata — `cp_local_rope_positions` → `cp_shard_position_ids`, which pads to `per_rank_actual_token`; under BCG replay `bcg.py` already rewrites `per_rank_actual_token` to the captured per-rank rows, so the shard has exactly K's physical rows — then asserts `positions.rows == k.rows`, trims Q/K/positions to the live rows, and writes only `total_seq_lens` live rows into `out_cache_loc` (`cp_live_store_rows`, asserts instead of silently taking a `min`).
