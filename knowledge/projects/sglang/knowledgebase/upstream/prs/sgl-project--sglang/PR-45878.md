# [Feat] rust/grpc: Propagate the caller's trace context to scheduler spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/45878) · state: open · merged: False

## Original PR description


## Motivation

The Rust server currently drops a request's W3C trace context: api.v1 has no field for it, and the scheduler header always sends `time_stats=nil`. So `--enable-trace` emits no per-request spans and SGLang's scheduler will be excluded from any tracing.

The legacy `sglang.runtime.v1` path had carried this context (`GenerateRequest.trace_headers`).

## Modifications

- api.v1 `GenerateRequest` gains `map<string, string> external_trace_header = 33`, named after `GenerateReqInput`'s field. Rust HTTP `/generate` and gRPC `Generate` both honor it.
- Rust `into_requests` keeps only `traceparent` and `tracestate`, and nothing without a `traceparent`. All batch items share one `Arc`; the map still counts against the broadcast budget, since each item's header encodes its own copy.
- Scheduler header: `TokenizedGenerateReqInput` gains the tail field `external_trace_header`.
- Scheduler (`handle_generate_request`): when a request arrives with `time_stats is None` and tracing is enabled, its time stats are seeded from the header. Each rank's thread span becomes a direct child of the caller's span, with sync and async (`SGLANG_TRACE_ASYNC`) tracing alike. A `traceparent` the W3C propagator rejects seeds nothing, since each rank would otherwise start its own unrelated trace.
- `external_trace_header` stays optional. Python `/generate` now answers 400 only when a value inside the map is not a string (for example `{"traceparent": "...", "x-attempt": 2}`), because `GenerateReqInput.external_trace_header` is now typed `Dict[str, str]`.
