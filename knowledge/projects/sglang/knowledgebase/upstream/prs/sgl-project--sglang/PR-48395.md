# [Feat] kimi-k3: Support DeepEP v2 with native MXFP4 experts

[Upstream PR](https://github.com/sgl-project/sglang/pull/48395) · state: open · merged: False

## Original PR description

## Motivation

Kimi K3 cannot currently use `--moe-a2a-backend deepep_v2`: its architecture is not registered for the adapter, its automatic MoE runner selection chooses FlashInfer MXFP4, and the v2 expert-format and activation checks reject native MXFP4/SiTU. K3 also needs to treat v2 as an EP backend when choosing its token and shared-expert layout.

This draft connects K3 to the existing native DeepGEMM W4A8 path. It also fixes a scale mismatch in the contiguous SiTU quantizer used by that path: FP8 values were quantized with an unrounded scale, but the consumer rounded that scale up to UE8M0 afterwards.

Base: `27aedf7f93cc7ac3bff43e7150e42a3c0baa6957`.
Head: `15cba36b64e4dfefc139732c159bb53cfe7edd5f`.

## Modifications

- Register K3 for DeepEP v2 and select `deep_gemm` when the v2 backend is explicitly requested and the runner is `auto`.
- Recognize v2 in K3's EP token/shared-expert placement and use materialized top-k routes.
- Accept native MXFP4/SiTU on SM100/SM103 with DeepGEMM and UE8M0 scales. Validate the split gate/up layout and supported activation/weight contracts at layer initialization.
- Keep group-128 FP8 activation scales distinct from group-32 MXFP4 weight scales, and fold `routed_scaling_factor` into top-k weights once before v2 dispatch.
- Use the existing `ue8m0_scale` helper to quantize contiguous SiTU values with the same power-of-two scale that GEMM consumes.
- Extend existing CPU and kernel test files; no new configuration flags or CI jobs.

The backend remains opt-in. Existing `EP=TP`, multi-node `hybrid` mode, and overlap/speculation restrictions are unchanged. PP2 × TP8 therefore uses EP8. This does not implement EP4 × MoE-TP2, or replace PP, TP, or DCP communication. K3's custom SP multicast backend eligibility is unchanged; v2 uses the existing collective fallback.

The CPU transport fixture substitutes the ElasticBuffer and FP8 quantization; it exercises real K3/FusedMoE construction, routing, and adapter selection, not GPU transport or GEMM correctness.

Each EP8 suite uses hidden=3584, intermediate=3072, 896 experts, top-k=16 and capacity=64 source tokens/rank. Cases are eight tokens per rank, rank 0 empty with seven tokens on each other rank, and all ranks empty. Each case runs four checked forwards; 60 of the 96 checks have nonempty outputs and 36 exercise empty-input execution. Decode captures and replays graphs while changing values and concentrating routes on the first 16 experts. Prefill intentionally runs eager because its non-expanded dispatch synchronizes with the CPU.

The supplemental expert-layer harnesses use synthetic checkpoint-layout packed MXFP4 tensors and call the real post-load transform, ElasticBuffer, and GEMMs. They do not load a model checkpoint. The integrated experts have deterministic packed values and global-expert-dependent scales; references explicitly reproduce FP8/UE8M0 quantization and BF16 rounding. Relative L2 is `norm(output-reference)/max(norm(reference),1e-12)`, not model accuracy loss. Supplemental harnesses/logs are archived outside this PR; they are not registered CI tests. ## Risk

The integration changes the K3 expert execution path when v2 is explicitly selected. Single-node synthetic expert-layer tests establish only the exercised numerical, transport, layout, and CUDA Graph behavior; they do not establish complete-model accuracy, cross-node/PP correctness, or high-concurrency memory requirements. The contiguous SiTU scale fix also affects existing users of that path and still needs model-level accuracy validation before merge. Other architectures and hardware have not been validated for the new native MXFP4 branch.
