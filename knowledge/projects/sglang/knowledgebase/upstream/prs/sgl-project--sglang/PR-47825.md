# [CI] disaggregation: Fail a PD test launch fast when an H20 runner is short of GPUs

[Upstream PR](https://github.com/sgl-project/sglang/pull/47825) · state: closed · merged: True

## Original PR description

## Motivation

When a CI runner loses a GPU, PD disaggregation tests fail in a way that looks like a code bug. On 2026-11-01, `h20-bfv8sr` (an `8-gpu-h20` runner) exposed only 7 GPUs, and `test_disaggregation_different_tp.py::TestDisaggregationStagingDecodeLargerTP` failed on #47737 three times. The decode server (`--tp 4 --base-gpu-id 4`) lost its rank 3 on GPU 7 during startup:

```
torch.AcceleratorError: CUDA error: invalid device ordinal
Invalid device number 7 provided, must be in the range of 0 to 6
...
RuntimeError: Server process exited with code -9
```

The only hint that the hardware was at fault was a fixture log line (`RDMA for gpus=[4, 5, 6, 7]: total_gpus=7`) far above the traceback. The same commit passed on another `8-gpu-h20` runner.

## Modifications

Before spawning a server, `popen_launch_pd_server` now checks that every GPU the server will use is visible. That range runs up to `base_gpu_id + (tp_size * pp_size - 1) * gpu_id_step`. If `torch.cuda.device_count()` is lower, the launch raises a `RuntimeError` that says the machine is short of GPUs, and the existing `safe_setUpClass` path tears the test down.

The check only runs on the H20 runners: it returns immediately unless `RUNNER_LABELS` ends in `-gpu-h20`. Both the `extra-b` stage (`_pr-test-stage.yml`) and `/rerun-test` set that variable. Other suites, other runners and local runs are unchanged.

The check never rejects a launch that could have started:
- **Lower bound only.** It counts TP x PP on one node. DP replicas without DP attention are not counted.
- **Skipped when it can't know the device set:**
  - the server env changes `CUDA_VISIBLE_DEVICES`, `HIP_VISIBLE_DEVICES` or `ROCR_VISIBLE_DEVICES` relative to the test process (for example, tests that pin decode to `4,5,6,7` and use `--base-gpu-id 0`);
  - `--nnodes` > 1;
  - no CUDA device is visible (NPU, XPU, CPU);
  - the launch args can't be parsed.
- **No change outside H20 test runs.** It reads the same `--tp`/`--tp-size`, `--pp-size`, `--base-gpu-id` and `--gpu-id-step` forms the launch uses, and touches nothing in the server or in the launch command.

## Testing

I ran the helper on its own with a stubbed `torch.cuda.device_count()` over 21 cases. All matched the expected result: 

- The `h20-bfv8sr` case (tp4, base 4, 7 visible) raises, and the same launch with 8 visible passes. 
- `--tp-size=4`, `--tensor-parallel-size`, PP, and `--gpu-id-step` are all counted. 
- Launches are skipped with `--nnodes 2`, a remapped `CUDA_VISIBLE_DEVICES`/`HIP_VISIBLE_DEVICES`, 0 visible devices, or an unparsable value. 
- `--dp-size` and `--pp-max-micro-batch-size` are not mistaken for parallel sizes. 
- The results are the same with a global `CUDA_VISIBLE_DEVICES` in the environment.
- With `RUNNER_LABELS` set to `8-gpu-h20` or `4-gpu-h20`, all 21 cases give the results above. With `8-gpu-h200`, `8-gpu-b200`, `2-gpu-large`, `linux-mi300-8gpu-sglang`, or no label, the check never raises.
