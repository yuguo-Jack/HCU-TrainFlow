# [Rust] Reduce output chunk allocations

[Upstream PR](https://github.com/sgl-project/sglang/pull/42619) · state: open · merged: False

## Original PR description

Reduce per-chunk allocations with inline token storage and request-ID reuse. Keep cumulative buffer growth efficient and add closed-channel cleanup coverage.

Averaging three CPU-mock runs per version:

- Throughput: **810,337 → 874,485 tokens/s (+7.9%)**.
- Frontend CPU: **6.97 → 6.33 µs/token (-9.2%)**.

Main `70f0b7351e` vs. `a58ced2688`, on two exclusive Grace nodes. Incremental streaming; both use the same benchmark-only 1,048,576-item response queue.

Validation: 337 server tests, formatting, and Clippy passed. All six benchmark runs passed.

- jthomson04 · comment · 2026-10-05T18:01:59Z · [source](https://github.com/sgl-project/sglang/pull/42619#discussion_r4187149456)

File: `rust/sglang-server/src/tokenizer_manager/detokenizer.rs` · line 387

**Test gap:** The rewritten send-failure path (rid now taken from the returned frame) is only tested for `SinkError::Full` (`full_sink_drops_request_and_aborts_scheduler`). Nothing drives `handle_chunk` through `SinkError::Closed`, which must remove the table entry but must **not** send a second abort. `recover_send_keeps_the_failed_chunk_identity` only tests `try_send_recover` on its own.

If a later edit sends the abort on `Closed` or skips `table.remove`, the scheduler gets a duplicate abort (the `FrontendCall` already queued one) or the `DetokState` leaks until shutdown, and no test fails. A sibling test with a dropped receiver that asserts the entry is gone and the abort channel is empty would cover it.

- jthomson04 · comment · 2026-10-05T18:01:59Z · [source](https://github.com/sgl-project/sglang/pull/42619#discussion_r4187149465)

File: `rust/sglang-server/src/tokenizer_manager/detokenizer.rs` · line 366

**Efficiency:** The finished path still clones `ev.rid` (a heap `String`) for every completed request, so the allocation savings only apply to intermediate frames.

The `&mut` from `get_mut` isn't used after this point in the branch, so taking ownership up front avoids the clone:

```rust
if finished {
    let mut st = table.remove(&ev.rid).expect("looked up above");
    let sent = st.sink.try_send(ResponseItem::Done(ev)).is_ok();
    let _ = st.fsm.apply(if sent { Event::FinalFrameSent } else { Event::Disconnect });
}
```

The decoder-error path (`rid.clone()` around line 331) can drop its clone the same way.

- jthomson04 · comment · 2026-10-05T18:01:59Z · [source](https://github.com/sgl-project/sglang/pull/42619#discussion_r4187149481)

File: `rust/sglang-server/Cargo.toml` · line None

**Dependency hygiene:**

1. **Exact pin:** `=1.15.2` has no comment explaining it. `smallvec` is a widely shared transitive dependency (tokenizers, parking_lot, …), so an exact pin forces the whole graph to 1.15.2, and any future bump that needs ≥1.15.3 / 1.16 fails to resolve with a confusing error. The other exact pins here (regex-syntax, prost, tonic) each have a rationale comment. If there's no specific reason, `"1.15"` in `[workspace.dependencies]` (the workspace manifest says it is the single source of truth for versions) plus `{ workspace = true }` here would match the rest of the block.
2. **Ordering:** `smallvec` sorts before `socket2` in this block.
3. **`serde` feature:** it exists only for one call, `serde_json::json!(out.token_ids)` in `api_server/frame.rs:90`. `serde_json::json!(out.token_ids.as_slice())` produces the same JSON, so the feature (and the new smallvec→serde edge in Cargo.lock) can be dropped.

- jthomson04 · comment · 2026-10-05T18:01:59Z · [source](https://github.com/sgl-project/sglang/pull/42619#discussion_r4187149487)

File: `rust/sglang-server/src/message/types.rs` · line 13

**Scope of `OutputTokenIds`:** "Output chunks usually contain one token" doesn't hold with speculative decoding (EAGLE/MTP), `stream_interval > 1`, or non-streaming requests. In those cases every chunk spills, so there's no gain and every slice access pays the spilled-check branch.

This alias is also used for cumulative buffers: `FrontendOutput::append_delta` (`contract.rs:73`), `OutputAccumulator`, and the gRPC cumulative stream. Those always spill and grow 1 → 2 → 4 (a `Vec` starts at 4), which adds a realloc per request.

Consider keeping cumulative buffers as `Vec<i64>` and using `SmallVec` only for per-chunk `ChunkEvent.token_ids`, and wording the comment around the common non-spec streaming case.

- jthomson04 · comment · 2026-10-05T18:01:59Z · [source](https://github.com/sgl-project/sglang/pull/42619#discussion_r4187149493)

File: `rust/sglang-server/src/tokenizer_manager/detokenizer.rs` · line 384

**Panic path:** Because `try_send_recover` returns a generic `ResponseItem`, the caller has to destructure it again behind an `unreachable!`. It can't fire today (tokio returns the exact item sent), but a panic here would kill the pinned detok shard thread and hang every request routed to it.

Matching the variant directly removes the panic path:

```rust
if let Err((e, ResponseItem::Frame(unsent))) = st.sink.try_send_recover(ResponseItem::Frame(ev)) {
```

Alternatively, a frame-typed helper could return `(SinkError, ChunkEvent)`.
