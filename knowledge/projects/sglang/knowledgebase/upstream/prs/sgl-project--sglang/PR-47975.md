# [Feat] embedding: Accept chat-style messages on /v1/embeddings

[Upstream PR](https://github.com/sgl-project/sglang/pull/47975) · state: open · merged: False

## Original PR description

## Motivation

`/v1/embeddings` takes multimodal input as `input: [{text, image, video}]`. Each item becomes its own embedding with at most one image and one video, always rendered image, video, then text. There is no audio. A single embedding of interleaved content, such as text, an image, more text and a second image, or of audio, has to go through `/encode`.

vLLM's embeddings API accepts chat-style input for this: `messages` holds a conversation whose content parts (`text`, `image_url`, `video_url`, `audio_url`, `input_audio`) are rendered by the model's chat template in the order they are sent. Clients serving multimodal embedding models (for example retrieval over document pages) already send this shape to `vllm serve`. Today, sending it to SGLang fails silently: a conversation in `input` validates as an empty `MultimodalEmbeddingInput` (pydantic ignores the unknown `role`/`content` keys), so SGLang embeds an empty prompt (the literal `"padding"` when there is no template) and returns 200. With gme-Qwen2-VL every such request gets the same vector, whatever the conversation says (see below).

SGLang's chat path already turns these messages into a prompt with ordered placeholders plus ordered media lists, and `EmbeddingReqInput` already accepts several media items per request. This PR connects the two.

## Modifications

- **`protocol.py`**:
  - `EmbeddingRequest` gets `messages` (one conversation, or a list of conversations giving one embedding each), plus `add_generation_prompt` (default `false`) and `chat_template_kwargs`. These names and defaults match vLLM's `EmbeddingChatRequest`.
  - Conversations sent in `input` are moved to `messages`, as vLLM does.
  - Exactly one of `input` and `messages` must be set.
  - The messages use a new `EmbeddingChatMessage` with a free-form `role`, because embedding templates define their own roles (for example `query` and `document`). Content parts reuse `ChatCompletionMessageContentPart`, so `input_audio` is converted to `audio_url` as it is in chat.
- **`serving_embedding.py`**: each conversation is rendered with the same template precedence as the existing multimodal `input` path:
  - **Registered conversation template:** goes through `generate_chat_conv`, which accepts only the `system`, `user` and `assistant` roles. Other roles are rejected with a 400.
  - **Jinja template:** goes through `process_content_for_template_format` and the tokenizer's chat template, which collects the media in order and puts the placeholders where they were sent.
  - **No template:** returns a 400 telling the user to start the server with `--chat-template`.
  - **Engine prompt:** multimodal models get the text plus per-request media lists, with `None` for text-only items in a batch. Text-only models get `input_ids` encoded with `add_special_tokens=False`, as the chat path does, because the template already writes BOS.
  - **Validation:** requests are rejected with a 400 instead of having content dropped when:
    - they contain media but the model is text-only;
    - they contain media of a type the model has no encoder for, such as audio sent to a vision model (checked with the model config's `is_image_understandable_model` and `is_audio_understandable_model`; video counts as vision). Without this, the processor drops the media and the embedding covers only the placeholder text;
    - the template uses the `"string"` content format, which keeps only text parts;
    - they contain content part types other than text, image, video and audio.
  - The Jinja error handling that turns template failures into 400s is moved into one helper used by both paths, with no change in behavior.
- **`conversation.py`**: `generate_chat_conv` no longer adds a newline after the `gme-qwen2-vl` image token. This matches `generate_embedding_convs`, so `messages` and `input` give the same prompt for that template. The change only affects that embedding template.
- **Docs**: adds a "Chat-style input" section to `supported-models/embedding_models.mdx`.

Existing `input` forms (strings, token IDs, `[{text, image, video}]`) are unchanged.

## Accuracy Tests

The change touches no model or kernel code. Prompt rendering is covered by unit tests:
- the ordering of interleaved media;
- batch alignment of the media lists;
- no extra special tokens for text-only models;
- `chat_template_kwargs` precedence;
- the rejection paths, including media of a type the model can't encode;
- identical gme prompts from `messages` and `input`.

End to end, `Alibaba-NLP/gme-Qwen2-VL-2B-Instruct` was served with `--is-embedding --chat-template gme-qwen2-vl` on one NVIDIA GB10 (DGX Spark), using the `lmsysorg/sglang:dev-cu13` image (main at `38d9e4a3`) with this PR applied. Four photos were used: a volcanic crater, a dog, a man ironing on a taxi, and sandwiches.

| Check | Result |
|---|---|
| Image + caption, `input: [{text, image}]` vs `messages` (4 images) | cosine 0.999999 to 1.0, same prompt token count (318 to 474) |
| Image only and text only, `input` vs `messages` | cosine 0.999999 |
| vLLM-style conversation in `input` vs the same in `messages` | cosine 1.0 |
| Caption-to-image retrieval with `messages` (4 x 4) | each caption's top match is its own image (0.61 to 0.80, best wrong match 0.13) |
| Batch of 4 conversations vs 4 single requests | cosine 1.0 each, in order |
| Two images interleaved with text in one embedding | 633 tokens (dog alone 321, sandwiches alone 328); the two closest images are the two sent; swapping their order changes the vector (cosine 0.93) |
| `input` and `messages` together, empty `messages`, role `query` with the gme template, unknown part type, audio on gme | 400 each, and the server keeps serving |

Without this PR, on the same image and model, a vLLM-style conversation in `input` returns 200 with the embedding of an empty prompt (18 tokens): two different conversations give cosine 0.999999 to each other and 0.21 to the embedding of their actual content. `messages` returns 400 (`input` is required).

The audio check found a gap in the first version of this PR: audio sent to gme was dropped and returned 200. The second commit rejects it.

The same requests were sent to vLLM 0.32 serving the same model (`vllm serve ... --runner pooling`), and checked against a float32 Hugging Face reference built like the model's `custom_st.py` (same prompt, last-token pooling, normalized, torchvision image processor; with the PIL one, vLLM's image numbers drop to 0.9990 to 0.9999 and SGLang's stay the same):

| Requests | SGLang `messages` vs vLLM | SGLang vs HF reference | vLLM vs HF reference |
|---|---|---|---|
| Text only | cosine 0.999997 to 0.999998 | 0.999997 to 0.999999 | 0.999997 to 0.999998 |
| With an image | 0.988 to 0.998 | 0.988 to 0.998 | 0.99995 to 0.999996 |

Token counts match on every request. For image requests SGLang's existing `input` path gives the same vectors as `messages` (cosine 0.999999 to 1.0), so the lower image numbers come from how SGLang handles this model's images, which this PR doesn't change. Switching `--mm-attention-backend` from `triton_attn` to `sdpa` doesn't change them. Retrieval agrees: each caption's top match is its own image on both servers, and the two 4 x 4 similarity matrices differ by at most 0.03.

vLLM's default chat template for gme ends after the user turn, without the reference's `<|im_start|>assistant\n<|endoftext|>`, so out of the box it pools a different token (cosine 0.58 to 0.90 against SGLang). The vLLM numbers above pass it the reference prompt as `chat_template`.

## Speed Tests and Profiling

The `input` path is unchanged. `messages` adds one template render per conversation, the same work the chat path does.
