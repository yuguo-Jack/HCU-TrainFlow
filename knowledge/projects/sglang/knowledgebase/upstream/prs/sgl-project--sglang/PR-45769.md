# [Feat] checkpoint: Process checkpoint lifecycle with prepare/status/restore routes

[Upstream PR](https://github.com/sgl-project/sglang/pull/45769) · state: open · merged: False

## Original PR description

## Motivation

External checkpoint/restore orchestrators, such as ones built on CRIU and `cuda-checkpoint`, need three things from the server: a signal that it is safe to capture, one idempotent call to bring it back after the restore, and a way to prepare at startup, before state that cannot be captured (such as a P/D KV transfer transport) exists.

SGLang already has the pieces under `--enable-memory-saver`: `pause_generation`, `release_memory_occupation`, `resume_memory_occupation` and `continue_generation`. This PR sequences them behind three routes, so a prepared server behaves exactly like a server paused with `/pause_generation`. It implements the SGLang side of #44523. The vLLM counterpart is vllm-project/vllm#62570.

## Modifications

| API | Behavior |
| :-- | :-- |
| `POST /checkpoint/prepare?mode=abort\|retract` | Pause generation with `mode`, wait for the scheduler to go idle, then release the KV cache. Returns once started, or 400 with the reason and nothing changed if it cannot prepare now. |
| `GET /checkpoint/status` | 200 once prepared, 503 until then, 500 after a failure. |
| `POST /checkpoint/restore` | Bring the KV cache back and continue generation, after a restore or in place. Safe to repeat. |
| `--checkpoint-prepare-on-startup` | Prepare before the server is marked Up. |
| `Engine.checkpoint_prepare/restore/state` | The same steps in process. |

- The routes are `ADMIN_OPTIONAL`, like `/pause_generation`.
- Between prepare and restore, the server behaves like a paused one: `/ready` and the `/health` canary report 503, and new requests wait until restore.
- `continue_generation` is refused mid-cycle, since it would schedule requests while the KV cache is released.
- Each DP rank replies with the merged state of its TP ranks, so a failure on any TP rank is reported.
- Pipeline parallelism is not supported yet, and prepare returns 400 with it.

Known gap, not changed here: with `--tokenizer-worker-num > 1`, `pause_generation(mode="abort")` waits only for the requests of the worker that received it, so a late request from another worker can reach the scheduler after the KV cache is released. `pause_generation` + `release_memory_occupation` has the same race today (#45773).

## Validation

On B200 (nscale), together with the PD transport follow-up: Qwen3-0.6B (TP1) and GLM-5.3-NVFP4 (TP4/EP4) prefill and decode servers started with `--checkpoint-prepare-on-startup` reported `prepared` on `/checkpoint/status`, were captured, and were restored into new pods. After `/checkpoint/resume` (now `/checkpoint/restore`) they returned the same greedy outputs as a live baseline, refused a later prepare with 400 while still serving, and could each be deleted and restored again while the other kept serving.
