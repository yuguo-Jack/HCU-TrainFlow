# [AMD] enable aiter attention backend for non-power 2 rope/nope models

## Motivation

The fix unblocks the usage of aiter attention backend when starting the servers for models like GLM5 FP8 on MI350 accelerators. We assume that the same code change applies to MI300 accelerators as well. With the default attention backend we observe way lower performance when using  the default attention backend compare to the aiter attention backend, within the same image and the same other parameters.  For instance we have the following results for GLM5 FP8, max conc 16, ISL/OSL 8192/1024:

| attention-backend | output_throughput | total_throughput | median e2e latency (ms) |
| :---------------- | ----------------: | ---------------: | ----------------------: |
| default           |            436.04 |          3924.32 |                 37389.19 |
| aiter             |            699.58 |          6296.19 |                23465.28 |

obtained for the base image `rocm/sgl-dev:v0.5.11-rocm720-mi35x-20260505`,  using (for attention-backend "aiter") the following command
```
docker run \
  --rm \
  --name sgl-dev \
  -e SGLANG_USE_AITER="1" \
  -e AITER_ONLINE_TUNE="0" \
  -e SAFETENSORS_FAST_GPU="0" \
  -e CUDA_VISIBLE_DEVICES="0,1,2,3,4,5,6,7" \
  -e SGLANG_AITER_MLA_PERSIST="0" \
  -e SGLANG_USE_AITER_UNIFIED_ATTN="0" \
  -e SGLANG_AITER_FP8_PREFILL_ATTN="0" \
  -e USE_ROCM_AITER_ROPE_BACKEND="1" \
  --entrypoint "" \
  --network host \
  --ipc host \
  -v /data/huggingface/hub:/root/.cache/huggingface/hub \
  --device /dev/dri:/dev/dri \
  --device /dev/kfd:/dev/kfd \
  --security-opt seccomp=unconfined \
  --shm-size 128G \
  amdsiloai/sgl-dev:v0.5.11-rocm720-mi35x-20260505_nope_rope_pow2_fix \
  python -m sglang.launch_server \
    --model zai-org/GLM-5-FP8 \
    --tensor-parallel-size 8 \
    --attention-backend aiter \
    --trust-remote-code \
    --reasoning-parser glm45 \
    --tool-call-parser glm47 \
    --port 5060 \
    --watchdog-timeout 12000 \
    --kv-cache-dtype fp8_e4m3 \
    --disable-radix-cache
```
with the benchmark command:

```
python -m sglang.bench_serving \
  --backend sglang \
  --dataset-name random \
  --model zai-org/GLM-5-FP8 \
  --port 5060 \
  --ready-check-timeout-sec 7200 \
  --random-range-ratio 1 \
  --max-concurrency 16 \
  --num-prompts 96 \
  --random-input-len 8192 \
  --random-output-len 1024 \
  --seed 9 \
  --warmup-requests 16
```
To run the same benchmark for the default attention backend one needs to remove "--attention-backend aiter" from the server start command.

SGLang’s multi-head attention path for models that split keys into non-PE (“nope”) and PE (“rope”) parts uses a Triton kernel (concat_and_cast_mha_k_triton in `/sglang/python/sglang/srt/layers/attention/utils.py`) which calls `tl.arange` requiring its range length to be a power of two.  GLM5-FP8 uses a nope dimension of 192, which is not a power of two. Starting the server for this model without the proposed modification therefore fails when attention backend is set to "aiter".

## Modifications

This change pads the nope/rope ranges used inside the Triton kernel to the next power of two (while keeping the actual tensor shapes and semantics correct for the model), so non-power-of-two head widths such as 192 are supported and GLM5-FP8 can run without hitting this compiler requirement.

@rkarhila-amd that solution is not for nothing, i have got an error trying to place the calls of next power of 2 inside the kernel:

Why you see this error
@triton.jit kernels are not normal Python. Triton parses the function body (AST) to build the IR and a cache key. Only a fixed set of names/operations is allowed inside that body.

You moved triton.next_power_of_2 into the kernel. That is a normal Python function on the host. When Triton’s dependency walker hits it, it reports:

`RuntimeError: Unsupported function referenced: <function next_power_of_2 ...>
`
So the failure is not “wrong math”; it is using a forbidden construct inside a JIT kernel.

What to do instead
Compute powers of two outside the kernel, in plain Python, and pass them in as` tl.constexpr` arguments` (e.g. BLOCK_NOPE, BLOCK_ROPE, head_cnt_pad),` exactly like:

```
concat_and_cast_mha_k_kernel[grid](
    ...,
    triton.next_power_of_2(int(head_cnt)),
    ...,
    triton.next_power_of_2(int(nope_dim)),
    triton.next_power_of_2(int(rope_dim)),
)
```
Inside the kernel, only use those parameters with` tl.arange(0, BLOCK_NOPE)` etc., not` triton.next_power_of_2(...)`.

If you ever need a power-of-two purely from constexprs already in tl, you’d have to use something Triton documents as legal inside kernels (version-specific); the portable pattern is host-side triton.next_power_of_2 + pass in.

But Im continuing to investigate.
