# [Fix] rerank: Request exact yes/no logprobs for the Qwen3-VL reranker

[Upstream PR](https://github.com/sgl-project/sglang/pull/47708) · state: open · merged: False

## Original PR description

## Motivation

The Qwen3-VL reranker scores a document as `p_yes / (p_yes + p_no)` from the first output token. `_handle_vl_reranker_request` requests `top_logprobs_num=50`, and `_extract_score_from_logprobs` searches that list for the two label tokens. A label missing from the list keeps probability 0. Missing from the top 50 does not mean zero probability: for documents unrelated to the query, "yes" regularly ranks below 50, so the score is clipped to exactly 0. Several such documents then tie at 0 and can no longer be ordered among themselves.

This continues #40887 (by huhumeng2), which proposed the same fix and was closed by its author without review. This PR rebases the idea on current `main` and adds measurements from a real deployment.

## Modifications

`python/sglang/srt/entrypoints/openai/serving_rerank.py`:
- In `_handle_vl_reranker_request`, replace `top_logprobs_num=50` with `token_ids_logprob=[self._yes_token_id, self._no_token_id]`.
- In `_extract_score_from_logprobs`, read `meta_info["output_token_ids_logprobs"][0]` instead of `output_top_logprobs[0]`. The yes/no matching loop and `_qwen3_rerank_score` are unchanged.

`test/registered/prefill_only/test_serving_rerank.py`:
- Update the `test_handle_vl_reranker_request` mock to return `output_token_ids_logprobs`.
- Add `test_handle_vl_reranker_request_label_outside_top_logprobs`: "yes" ranks below 50 other tokens, and the score must still equal `p_yes / (p_yes + p_no)`. The test also checks that the request asks for exactly the two label ids and no top-k list. The mock returns label rows in requested-id order, so matching by token id is covered too.

Both tests fail on `main` and pass with this change (14 passed in the file). The `logprob_start_len` value is left as is; `token_ids_logprob` returns `output_token_ids_logprobs` with both `0` and `-1` on a live server.

## Accuracy Tests

Qwen3-VL-Reranker-2B, query "观智办公平台如何做知识库权限控制？" ("How does the platform control knowledge-base permissions?"), 12 Chinese documents. "Reference" is computed independently: the same rendered prompt is sent to `/generate` with `top_logprobs_num=5000`, and the score is computed from the yes/no entries.

| Document (translated) | Rank of "yes" | Before | After | Reference |
|---|---|---|---|---|
| KB supports department/role/user grants | 6 | 0.766294 | 0.766294 | 0.766294 |
| Today's weather in Chengdu | 61 | 0 | 0.075858 | 0.075858 |
| Python GIL limits multithreading | 73 | 0 | 0.106691 | 0.106691 |
| Braised pork recipe | 69 | 0 | 0.080357 | 0.080357 |
| Quarterly revenue grew 12% | 63 | 0 | 0.100879 | 0.100879 |
| Folder permissions inherit from parent | 14 | 0.500000 | 0.500000 | 0.500000 |

(6 of the 12 rows shown.) "Before" applies the original top-50 lookup to the same logprobs: the reference score if both labels are in the top 50, and 0 if "yes" is not. "no" ranked within the top 30 for all 12 documents. The 0 scores for the weather, GIL and braised-pork documents were also observed directly from `/v1/rerank` on an unpatched build. For every document whose "yes" is in the top 50, before and after are identical. With one document per request, all 12 "after" scores match the reference exactly. When the 12 documents are sent in one request, scores differ from the single-document scores by at most 0.015, from bf16 batch composition. This happens with and without this change.

## Speed Tests and Profiling

Requesting two token ids instead of the top-50 list does not change latency measurably (8 documents: 65.6 ms → 63.3 ms; 16 documents: 98.5 ms → 94.8 ms, same setup as #47706).

## Related

#47706 batches the per-document requests on the same code path. The two PRs are independent, but they touch adjacent lines of the `GenerateReqInput(...)` call (`top_logprobs_num` here, `logprob_start_len` there). Whichever lands second needs a trivial rebase that keeps both new values (`token_ids_logprob=[...]` and `logprob_start_len=-1`). All tests of both PRs pass with that resolution.
