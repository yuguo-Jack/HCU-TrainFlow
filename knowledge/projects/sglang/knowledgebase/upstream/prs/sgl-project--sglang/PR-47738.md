# [Perf] [AMD] fla: autotune the GDN chunk_fwd_kernel_o on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/47738) · state: open · merged: False

## Original PR description

## Motivation

`chunk_fwd_kernel_o` (`sglang/kernels/ops/attention/fla/chunk_o.py`) is the output stage of the Gated-DeltaNet chunked prefill (Qwen3-Next, Qwen3.5/3.6/3.8, ...). Its `@triton.autotune` has been commented out since the fla kernels were added, so it launches with one fixed config on every platform: `BK=128, BV=64, num_warps=4, num_stages=2`. The other fla prefill kernels autotune, as does upstream fla.

On ROCm that fixed config is well behind the best one. On RDNA3 (gfx1100), the profile below shows the kernel taking 257 ms of an 8k-token prefill of a 27B Qwen3.8 model; tuned, it takes 159-163 ms.

## Modifications

- `chunk_o.py`: on AMD, launch `chunk_fwd_kernel_o` through `triton.autotune`, using the config space from the commented-out decorator (upstream fla's) and `autotune_cache_kwargs` like the other fla kernels. Other platforms keep the fixed launch unchanged.
- The kernel only writes `o`, so the autotune benchmark reruns are safe. Like the other fla kernels, the autotune key has no sequence-length term, so the config is chosen on the first call for a given (H, K, V, BT). `chunk_delta_h`'s comment describes the in-place-state problem that rules out autotuning that kernel; it does not apply here.

I also tried restoring autotune on `recompute_w_u_fwd_kernel` and `chunk_local_cumsum_scalar_kernel`, and left them out:
- In the server, `recompute_w_u_fwd_kernel` got tuned on the short warmup batches. Its key has no sequence-length term, and the chosen config (2 warps) then made the 8k prefill slower: 422 ms became 710 ms.
- The cumsum kernel is negligible (about 1 ms).

## Accuracy Tests

- `test/registered/attention/test_chunk_gated_delta_rule.py` passes on gfx1100 with the kernel autotuned: 30 passed, 1 skipped, 6 subtests.
- In the same process, the whole chunked GDN prefill with tuned kernels (this one, plus the two I left out above, during the experiment) matches the fixed launch to within 1.2e-4 (bf16 inputs, fp32 state).

## Speed Tests and Profiling

gfx1100 (RDNA3, W7900-class), ROCm 7.2, Triton 3.7, no aiter.

**In the server**: `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16` (48 GDN layers), TP1, one 8k-token prefill (`--chunked-prefill-size 8192`), GPU kernel time from the torch profiler:

| | `chunk_fwd_kernel_o` | all GDN kernels |
|---|---:|---:|
| main | 257 ms | 852 ms |
| this PR | 163 ms | 727 ms |

**End to end**, same model and flags: 8k-token prompts, median TTFT of 8, two rounds alternating on the same GPU.

| | round 1 | round 2 |
|---|---:|---:|
| main | 9928 ms | 9551 ms |
| this PR | 9819 ms | 9332 ms |

That is -1.1% / -2.3% TTFT. The fixed config scales worse than linearly with T on this GPU (the whole GDN prefill at 8 : 24 heads: 2.8 / 8.1 / 29.2 ms at 4k / 8k / 16k), so the gain should grow with prompt length; I measured end to end at 8k only.

Loading this int4 checkpoint needs #47695, so both arms of the in-server and end-to-end runs include it. Its gfx1151-only GDN paths are off on gfx1100, so the generic `chunk_fwd_kernel_o` is the one being compared. The two PRs touch the same launch code in `chunk_o.py`, so whichever lands second needs a small rebase.

This is generic HIP code, so it targets `main`. I can send the same change to `amd_march` if that is preferred.
