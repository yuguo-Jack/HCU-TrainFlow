# [Model Loader] Add InstantTensor loader support

[Upstream PR](https://github.com/sgl-project/sglang/pull/40453) · state: closed · merged: True

## Original PR description

## Motivation

Add [InstantTensor](https://github.com/scitix/InstantTensor) as an optional high-performance loader for Safetensors checkpoints.

InstantTensor supports distributed weight loading and pipelined prefetching. This integration lets users select it with `--load-format instanttensor` while preserving SGLang's existing checkpoint discovery and model-loading flow.

It has already been integrated into several other projects, such as vLLM. https://docs.vllm.ai/en/latest/models/extensions/instanttensor/

## Modifications

- Add `instanttensor` to the supported load formats and CLI choices.
- Add an InstantTensor weight iterator based on `instanttensor.safe_open`.
- Require PyTorch's `cuda` device interface (including CUDA and ROCm). Reject unsupported devices during server-argument validation and at the iterator entry, before importing InstantTensor or accessing the current CUDA device.
- Reuse the existing Safetensors file discovery, shard index filtering, and checkpoint selection logic.
- Validate selected filenames at the InstantTensor iterator entry and reject non-`.safetensors` files before opening any checkpoint. Keep SGLang's existing discovery, download, cache, and pattern-priority behavior unchanged; unsupported selections fail explicitly rather than being automatically replaced.
- Pass SGLang's initialized device process group to InstantTensor for distributed loading.
- Support tuning through `--model-loader-extra-config`, including `buffer_size`, `chunk_size`, `io_depth`, and `backend`.
- Convert JSON backend names or ordered candidate lists to InstantTensor backend/policy enums. Skip SGLang's extra-config validation for InstantTensor and forward optional parameters without filtering. Pass filename, framework, device, process group, and `copy=True` explicitly; Python rejects duplicate arguments, and InstantTensor handles unsupported parameters and values.
- Add the optional `sglang[instanttensor]` dependency with `instanttensor>=0.1.9` to support these tuning options.
- Document core tuning options in the shared loader configuration table and link to InstantTensor for the latest options.
- Extend `SRTRunner` to select the load format and pass extra loader configuration in model-loading tests.
- Add focused CPU unit tests and a weekly single-GPU output-consistency test comparing Safetensors with explicitly configured InstantTensor loading.

### Configuration example

```bash
pip install "sglang[instanttensor]"

python -m sglang.launch_server \
  --model-path Qwen/Qwen3.5-4B \
  --load-format instanttensor \
  --model-loader-extra-config '{"backend":"URING","chunk_size":8388608,"io_depth":64}'
```

For the tuning options shown above, explicit non-null values override the corresponding `INSTANTTENSOR_*` environment variables. Omitted or `null` values retain InstantTensor's environment-variable and automatic defaults. Backend names are case-sensitive; an ordered list such as `{"backend":["URING","AIO"]}` selects the first available candidate. Additional optional parameters are forwarded unchanged, except that `filename`, `framework`, `device`, `process_group`, and `copy` cannot be overridden. Unsupported parameters, including generic loader settings such as `enable_multithread_load` and `num_threads`, are not silently dropped; they are left for InstantTensor to reject.

## Accuracy Tests

### CPU unit tests

All 8 InstantTensor-related CPU tests passed: 6 iterator tests and 2 server-argument hardware-validation tests.

These tests cover configuration forwarding (including `copy=True`), backend conversion, current-device and process-group selection, and rejection of unsupported filename suffixes at the iterator entry. Hardware tests accept the CUDA and ROCm platform classes, reject non-CUDA device types before importing InstantTensor or calling CUDA APIs, and check that other load formats remain usable with CPU devices. These are CPU-only interface tests, not ROCm hardware validation; real NCCL behavior is not covered by the mocks.

Related regression tests, CI registration checks, and applicable pre-commit checks also passed.

### GPU generation consistency

The single GPU E2E test passed. It runs weekly, defaults to `Qwen/Qwen2-0.5B`, and launches two engines: a Safetensors baseline and InstantTensor with `backend="MMAP"`, `chunk_size=8388608`, and `io_depth=2`. It clears inherited `INSTANTTENSOR_*` variables while the engines run. MMAP avoids requiring io_uring support in the CI environment.

The latest local CUDA run used `Qwen/Qwen3.5-4B` with PyTorch 2.13.0 and InstantTensor 0.1.9, using FP16 inference. An earlier run also passed with deliberately conflicting InstantTensor environment variables set before launch:

```text
Ran 1 test in 46.021s
OK
```

InstantTensor produced identical generated text to the Safetensors baseline. The maximum differences in prefill and decode log probabilities were both zero. This is an output-consistency test, not a byte-for-byte comparison of the final model parameters or a loading-speed benchmark. Registered GPU CI covers this single-GPU MMAP path, not real TP2 loading or a backend matrix.

### Previously validated serving configurations

The original end-to-end serving validation also covered:

- Qwen3-30B-A3B, TP1
- DeepSeek-R1, TP8+EP8

For every configuration, Safetensors and InstantTensor produced the same response and token IDs.

**Other Potential Collective-Loading Risks**

While looking into this, we identified other paths worth auditing for collective-loader compatibility:

| Scenario | Potential participation mismatch |
|---|---|
| Elastic EP missing-expert recovery | Only ranks with missing experts may reload from disk; filtering tensors after creating the iterator does not necessarily restrict the loader’s collectives. |
| Elastic EP expansion or worker recovery | Joining/recovering workers may load while existing workers do not. Compatibility depends on the group membership used during loading. |
| Weight-cache client fallback | If fallback decisions differ between ranks, only some may enter checkpoint loading. This matters if the fallback uses a collective loader; ordinary Safetensors fallback does not introduce this issue. |
| Selectively targeted disk weight updates | A mismatch is possible if an update reaches fewer ranks than the loader’s communication group. Updates coordinated across all required ranks are a different case. |
| Rank-local retry after a loading error | If only some ranks restart a collective iterator, collective ordering or participation may diverge. |

These are **potential risks, not confirmed failures across all backends**. They may affect collective loading through fastsafetensors, InstantTensor, or runai_model_streamer in distributed mode, **where the relevant path supports and selects that backend**. Non-collective loading and correctly coordinated groups are not implicated. Addressing these broader orchestration paths is outside this PR’s scope, but they deserve follow-up attention.

**Communicator Memory**

We added a brief lifetime-memory note to the documentation. More precisely, additional communicator memory can arise when InstantTensor uses a group that SGLang would otherwise leave unused for communication. If SGLang already uses the same group and communicator, this does not add a separate communicator allocation.

In some of our earlier tests, fastsafetensors and runai_model_streamer retained more communication-related GPU memory after loading than InstantTensor. This is an observation from those test configurations, rather than a general guarantee across backends and environments.

**InstantTensor Roadmap**

We had already planned the following InstantTensor improvements before this PR. The partial-loading scenarios above further illustrate their potential value, so we mention them here as context for future work beyond this PR.

We plan to support selective loading of requested tensors and asymmetric collective loading, where participating GPUs cooperate through communication without requiring the loader to return the same tensor list to every GPU. This differs from the current collective-loading behavior of fastsafetensors, runai_model_streamer, and InstantTensor. Beyond further accelerating target-model cold starts, we hope this will improve efficiency and compatibility for the partial-loading scenarios above. This will still require SGLang to select the correct participating group; it does not by itself eliminate collective-participation requirements.
