# [Fix] deepseek-v4.1: Leave room for encoder replay rows when sizing a prefill chunk

[Upstream PR](https://github.com/sgl-project/sglang/pull/45040) · state: closed · merged: True

## Original PR description

- With encoder SWA bounded replay, a prefix hit runs up to 128 of its cached tokens in the same step as its extend. The scheduler sized the extend from the remaining chunk and only then charged those replay rows, so the request that filled the chunk ran up to 128 rows past it. With the MegaMoE token cap set to the per-rank chunk, that step fell back to the Triton fused MoE, which asserts on DeepSeek-V4.1-Flash's block scales (`assert triton.cdiv(B.shape[-2], block_n) == B_scale.shape[-2]`).
- `PrefillAdder._select_prefill_admission` now takes the request's replay rows off the chunk limit before it sizes the extend; when no room is left for them, the request is not admitted this step (`AddReqResult.OTHER`).
- `replay_len` in `encoder_swa_replay.py` owns the replay length; the prefill budget, the MLP-sync fold-row count (`folded_replay_rows`) and the fold read it.
- Test: a hit's extend plus its replay rows fills the chunk exactly at prefix lengths 0, 64 and 4096, and a chunk smaller than the replay rows admits nothing. It fails on main.
- Checked on GB300 with DeepSeek-V4.1-Flash: DEP2 (attention DP 2, EP 2), MegaMoE with `SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK=16384` (the per-rank chunk), encoder and decoder replay, DSpark. A 24,576-token prompt, then the same prompt plus 24,576 more tokens, both on DP rank 0. On main the second request's first chunk is 16,384 new tokens plus 128 replay rows, and the server crashes in the Triton MoE. With this change that chunk is 16,128 new tokens plus 128 replay rows, and the request completes.

Behavior change only with encoder replay: the request that fills a chunk takes up to 128 fewer new tokens in that step.
