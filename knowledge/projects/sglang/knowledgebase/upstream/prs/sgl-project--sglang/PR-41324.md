# fix(openai): cache negative byte-level tokenizer verdicts in logprob bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/41324) · state: open · merged: False

## Original PR description

## Motivation

`_is_byte_level_tokenizer` (added in #38604) caches only **True** verdicts. A tokenizer that probes **False** re-runs the slow path on every call, and that path starts with `len(tokenizer.get_vocab())`, which rebuilds the full vocab dict. Such a tokenizer is one with no boolean `is_byte_level` whose sampled pieces are not byte-level.

The check is on the streaming logprobs hot path:

- once per streamed chunk, in `_build_token_logprobs_from_raw`;
- once per logprob token and per top logprob, in `token_id_to_bytes`.

So every token of a long `logprobs=true` stream pays tens of milliseconds inside `get_vocab()` on the tokenizer-manager event loop. That loop also delivers every other request's output, so one such stream stalls the first chunk of every other request on the server.

We hit this in production with DeepSeek-V4.1-Flash. Its tokenizer takes the slow path and probes False. Periodic ~90 s windows appeared where no chat response started while the scheduler kept prefilling and decoding. `/health` stayed 200, because it passes on any message from the detokenizer.

### Reproduction

DeepSeek-V4.1-Flash on 4×B200 (TP4), a build of `main` from 2026-09-22 (`4cbf290fb`). A probe sent an 8-token streaming request every 1 s throughout.

| request (same prompt) | its own duration | probe TTFT p50 / max |
|---|---|---|
| none (baseline) | — | 0.14 s / 0.2 s |
| 4000-token stream, `logprobs` off | 12.2 s | 0.15 s / 0.2 s |
| **4000-token stream, `logprobs: true`** | **86.5 s** | **38.2 s / 74.7 s** |

### Profile

`py-spy record` of the server process during the logprobs stream: 120 s at 50 Hz, 5,958 MainThread samples. The loop was ~100% busy, and 72% of its time was in this chain:

```
_generate_chat_stream (serving_chat.py)
 -> _process_streaming_logprobs
  -> _build_token_logprobs_from_raw
   -> _is_byte_level_tokenizer (openai/utils.py)
    -> tokenizer.get_vocab()          # 69.6% as the leaf frame
```

### Verified on a live deployment

We applied exactly this change as an overlay on the same DeepSeek-V4.1-Flash deployment: 4×B200 (TP4), the `main` build from 2026-09-22. We reran the reproduction above unchanged, with the same prompts and the same 1 req/s probe:

| request | before: duration / probe TTFT p50 / max | after: duration / probe TTFT p50 / max |
|---|---|---|
| 4000-token stream, `logprobs` off | 12.2 s / 0.15 s / 0.2 s | 12.1 s / 0.16 s / 0.2 s |
| **4000-token stream, `logprobs: true`** | **86.5 s / 38.2 s / 74.7 s** | **11.1 s / 0.15 s / 0.2 s** |

With the fix, a `logprobs` stream costs the same as one without, and it no longer delays other requests.

## Modifications

- Cache the verdict per tokenizer, True **or** False: `_BYTE_LEVEL_VERDICT: dict[int, bool]`, keyed by `id(tokenizer)` as before.
- Move the uncached probe into `_probe_byte_level`. The probe logic is unchanged.

## Accuracy Tests

No output change: the verdict for a given tokenizer is identical, it is just computed once.

New CPU unit test `test/registered/unit/entrypoints/openai/test_byte_level_tokenizer_cache.py` covers:

- a non-byte-level tokenizer probed once over 1000 calls;
- a byte-level tokenizer probed once;
- `token_id_to_bytes` not re-probing per token;
- the `is_byte_level` fast path;
- independent verdicts for distinct tokenizers.

On `main` without this change, the negative-verdict tests fail with `AssertionError: 1000 != 1`. With it, all pass. The existing `test_serving_chat.py` still passes:

```text
149 passed, 76 subtests passed (test_byte_level_tokenizer_cache.py + test_serving_chat.py)
```

## Speed Tests and Profiling

This removes a `get_vocab()` call per streamed chunk and per logprob token for non-byte-level tokenizers. In the reproduction above, that call was ~72% of the event loop during a logprobs stream.

- vmanvs · comment · 2026-10-13T18:17:10Z · [source](https://github.com/sgl-project/sglang/pull/41324#issuecomment-6152181860)

Thanks for tracking this down, the stall numbers are striking. One related finding: for DeepSeek the cached `False` verdict is itself wrong, so caching it makes the wrong answer fast.

DeepSeek-V3/R1/V2 tokenizers are byte-level (`tokenizer.json` has `"decoder": {"type": "ByteLevel"}`, and `get_tokenizer` keeps it). But the slow path samples ids 0–3, and id 0 is `<｜begin▁of▁sentence｜>`, whose characters aren’t in the GPT-2 byte table, so it returns False. Separately, `is_byte_level` doesn’t exist on transformers 5 fast tokenizers, so the fast path never fires for any model. Logprob `bytes` for DeepSeek then fall back to display text, which is what #38604 set out to fix:

```
DeepSeek-V3, "Café 🤖 naïve 中文 ok" (transformers 5.19.0, loaded via get_tokenizer)
'ĠðŁ¤'  true [32, 240, 159, 164]   served [32, 239, 191, 189]
'ĸ'     true [150]                 served [239, 191, 189]
```

GPT-2 and Qwen2.5 classify correctly; TinyLlama, Mistral and T5 are correctly False.

I’d like to fix the verdict by reading `backend_tokenizer.decoder` (ByteLevel, or a Sequence containing one) instead of sampling vocab pieces. That also removes the `get_vocab()` call. I’ll keep it to the verdict computation so it fits on top of your caching, and open it as a follow-up. Happy to fold it into this PR instead if you prefer.

- divyvasal · comment · 2026-10-13T19:59:32Z · [source](https://github.com/sgl-project/sglang/pull/41324#issuecomment-6154032689)

Thanks, good catch, and I can confirm the second part: on transformers 5.17, `PreTrainedTokenizerFast` has no `is_byte_level`, so every tokenizer takes the sampling probe, and sampling ids 0–3 hits special tokens like `<｜begin▁of▁sentence｜>`. Reading `backend_tokenizer.decoder` is the right fix. I'd keep it as your follow-up so this PR stays a pure caching change; the two compose cleanly, since the cache stores whatever the verdict function returns. For tokenizers without a `backend_tokenizer` (slow tokenizers), it may be worth keeping a fallback that skips `all_special_ids` when sampling. Happy to review it when it's up.
