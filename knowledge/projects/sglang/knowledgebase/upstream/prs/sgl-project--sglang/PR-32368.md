# [AMD] Enable DSV4 unified-KV HiSparse PD over MoRI

[Upstream PR](https://github.com/sgl-project/sglang/pull/32368) · state: open · merged: False

## Original PR description

## Summary

> [!IMPORTANT]
> This PR is based on and continues the work in #29168. It must not be merged until #29168 has been merged.

Enable decode-only DeepSeek-V4 HiSparse on ROCm with the unified-KV layout, and preserve the separate host/device destination index spaces across PD transfers.

- **Unified-KV HiSparse on ROCm** — add `HiSparseUnifiedC4DevicePool`, a no-allocation C4 hot pool that aliases the unified pool's compressed region, and drop the CUDA-only skips on the DSV4 paged-layout kernel tests.
- **Separate host/device KV destinations across PD** — decode allocates host C4 page ids independently of the device indexer/C128 page ids. Mooncake and MoRI now carry a second destination index array, so device buffers are written at device page offsets instead of being handed host page ids.
- **Virtual → physical KV translation at the PD boundary** — `resolve_physical_kv_indices()` translates allocator-owned virtual ids immediately before page conversion; a no-op for allocators without `translate_kv_loc`.
- **MoRI host registration** — per-buffer VRAM/DRAM memory kinds so host mirrors register as CPU memory; chunked registration aligned to `lcm(4096, item_bytes)` to stay under the Ionic MR mapping boundary; host layers padded to 2MiB hugetlb boundaries; optional rank-local HCA distribution for DP8.

Rebased onto `main` @ e1964da4. 15 source files + 10 test files, +2840 / -163.

**No compute kernel or swap-in datapath file is modified** — `kernels/jit/csrc/hisparse.cuh`, `kernels/ops/kvcache/hisparse.py`, `layers/attention/dsv4/indexer.py` and `models/deepseek_v4.py` are all untouched. The only change under `managers/hisparse_coordinator.py` is backend dispatch plus hugepage-aligned host pool sizing; per-step kernel work is unchanged.

## Performance

Enabling decode-only HiSparse is a throughput regression at high concurrency on this workload. Non-HiSparse control vs `device_buffer_size=2048`, same 1P1D topology, ISL within 1.0%:

| | non-HiSparse | HiSparse | |
|---|---|---|---|
| decode step | 55.0 ms | 76.6 ms | **+39.3%** |
| per-request decode rate | 18.19 tok/s | 13.06 tok/s | −28.2% |
| output token throughput | 2,652 tok/s | 2,041 tok/s | −23.0% |
| request throughput | 3.83 req/s | 3.14 req/s | −18.0% |

What HiSparse buys in exchange is capacity: `max_total_num_tokens` 12.90M → 17.56M (**+36%**).

The cost sits in the upstream swap-in path, not in this PR's plumbing. A `device_buffer_size` sweep — 2048 → 8192 → 16384, i.e. hot-buffer coverage 7% → 28% → 57% and roughly 8× fewer bytes moved — produced **no** improvement; decode step went 76.6 → 77.2 → **78.8 ms**, i.e. monotonically worse. So the path is latency/parallelism-bound rather than bandwidth-bound: `LaunchKernel` uses `grid = batch size`, and per-rank decode batch here is 20–23, giving ~23 blocks on 256 CUs (~9% occupancy). This lines up with #31341 ("strict 1 CTA per request") and with #30985 reporting HiSparse slower than dense at low concurrency on H200.

Reducing bytes moved is therefore not the lever; multi-CTA sharding of the copy loop (#31341) and side-stream overlap (#28523) are.


## Runtime requirements on the tested MI355X cluster

- `SGLANG_HUGEPAGE_SIZE=2MB` with roughly an 800GiB hugetlb reservation per decode node (1152GiB for DP8 with headroom)
- `SGLANG_MORI_RANK_LOCAL_IB_DEVICE=1` for DP8 rail distribution
- `SGLANG_MORI_HOST_REGISTRATION_CHUNK_BYTES=268435456`
- The default QP4 path is validated; QP1 is also functional
