# [Fix] rust-server: Let an HTTP layer start a native /generate request's timing

[Upstream PR](https://github.com/sgl-project/sglang/pull/47160) · state: closed · merged: True

## Original PR description

Follows #47112 (the native `/generate` hook's request, headers and outcome), which has merged; this PR is now based on main and its diff is the two files below.

## Motivation

An `HttpLayer` (the `http_layer` a server extension passes to `Server::start`) can do part of a request's work before the `/generate` handler runs, for example resolving the request's inputs through another service. Python's `TokenizerManager` does that kind of work after its request timer (`APIServerReqTimeStats`) has started, so it counts toward Python's `e2e_latency` and first-token latency. The native `/generate` handler started `RequestTiming` only once it had normalized the body, after any such layer had finished, so the same request's `meta_info.e2e_latency` and first-token latency read shorter than Python's by however long the layer took.

Without the new extension, nothing changes.

## Modifications

- **`RequestStart(pub Instant)`**, exported from the crate root next to `HttpLayer`, is a request extension. A layer inserts it into the request's extensions when it starts work that belongs inside the request's timing.
- **`/generate`** takes `Option<Extension<RequestStart>>` and starts `RequestTiming` from it when present (`RequestTiming::starting_at`), otherwise at the same point as before. This covers single and batch requests, unary and streaming. `e2e_latency` and the first-token latency move together; the decode latency (first output to last output) does not change.

Scope: the native `/generate` HTTP handler only. The Prometheus `time_to_first_token_seconds` and `e2e_request_latency_seconds` histograms keep their own start in the core handle and are unchanged. gRPC and the OpenAI routes do not read the extension.

Not applicable: no model numerics change.

## Speed Tests and Profiling

Not run. The handler reads one optional request extension per request.

## Testing

- `unary_http_generate_round_trips_through_frontend_handle` now sends a request whose `RequestStart` is 5 s old and checks that the response's `meta_info.e2e_latency` is at least 5 s. Without the handler change it fails.
- `generate_hook_keys_reach_every_frame` sends every case (single/batch, unary/cumulative/incremental streaming) with a 5 s old `RequestStart` and checks that `e2e_latency` appears on exactly the terminal frames and is at least 5 s on each, that a streamed request's `e2e_latency - decode_s` still covers the layer's 5 s (the decode latency starts at the first output, after the layer), and that a unary request's `decode_s` is unchanged.
- Ran locally: `cargo fmt -p sglang-server -- --check`, `cargo clippy -p sglang-server --all-targets -- -D warnings`, `cargo test -p sglang-server --lib -- api_server::http::native_api`.
