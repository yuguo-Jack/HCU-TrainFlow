# fix(gateway): give an in-flight AddWorker a head start before removing the last worker

[Upstream PR](https://github.com/sgl-project/sglang/pull/38524) · state: closed · merged: False

## Original PR description

Split out of #32322 to keep that PR to one file — this race is at the worker registry, not at the source of the jobs, and reproduces via the REST API just as well as via service discovery.

## Problem

Worker jobs run as independent concurrent tasks, so submission order does not imply completion order. A rolling update submits `AddWorker(new)` then `RemoveWorker(old)`; the removal pipeline is short and can take effect ~1 s before the replacement's multi-step activation finishes. In that window the model has zero routable workers and requests fail with 404 — the router logs `Removed policy ... (last worker removed)` one second before `Activated 1 worker(s)`.

## Fix

Before executing `RemoveWorker`, if the target is the model's last healthy worker and an `AddWorker` is pending or processing, poll at 200 ms until the model retains another healthy worker, the add finishes, or a 5 s deadline expires. Intentional scale-to-zero is not delayed (no add in flight), and a stuck add cannot block removals past the deadline.

Two approximations, both bounded and called out in the code:

- The in-flight check is **global, not per-model** — the model is not knowable here (`JobStatus` records only type, URL, status, timestamp, and discovery submits with `model_id: None`), so an unrelated model's add can defer one removal by up to the deadline.
- The wait holds a job-queue permit and delays deregistering the departing worker, which keeps sending it traffic meanwhile. Both argue for a deadline no larger than the handoff it protects; an observed activation takes about a second.

Happy to rework the signal to be per-model if you would rather not carry the approximation.

## Verification

A full rolling update under an independent prober (short non-streaming and streaming requests; error = any non-2xx, transport failure, truncated stream, or TTFT > 10 s) completed 1,409/1,409, and the zero-worker registry state both router replicas hit at every handoff before the fix did not occur once.
