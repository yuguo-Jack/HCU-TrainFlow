# [Fix] [AMD] moe: Stop dropping FP32 partials in GLM Gluon TP8 32K MoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/48397) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.2-MXFP4 on 8x MI355X with `--moe-runner-backend gluon` (TP8/EP1, the InferenceX PR 4748 config) crashes under agentic traffic. All 8 GPUs abort together with:

```
HSA_STATUS_ERROR_EXCEPTION: An HSAIL operation resulted in a hardware exception. code: 0x1016
```

This usually happens on a full 32768-token prefill chunk.

The root cause is in `fused_moe_tp8_m4193_16768`, which serves TP8/EP1 prefill for M = 4193..32768:

- `_Workspace` splits the escaped FP32 down-projection partials into `parts_low` and `parts_high`. Each is `4 * storage_m x 6144` fp32, so each is 3 GiB at M=32768. The comment says "gfx950 buffer operations have a 4-GiB addressing window".
- On gfx950 with Triton 3.7 (`3.7.0+amd.rocm7.2.0.git89002410`), `gl.amd.cdna4.buffer_store` / `buffer_load` only address **2 GiB**. Stores at byte offset >= 2^31 are silently dropped, and loads there return 0. A probe on a 3 GiB tensor works up to `2^31 - 4096` and drops everything from `2^31` on.
- `_store_w2_panel` writes the raw partials of escaped rows with `buffer_store`. For M > 21504 (`storage_m >= 22528`), escaped rows at local row >= 87381 in either half are never written. `_shared_reduce` then reads them back with `gl.load` and gets stale memory.

On real agentic traffic this is not rare. With instrumentation, the first MoE layer of the first 32K chunk had 2112 escaped dense rows, and 623 of them were past the 2-GiB window. That corrupted 563 tokens in that one layer, and every 32K chunk is affected. Whether the server crashes depends on what the stale memory holds. When it holds NaN, the logits become NaN and `torch.multinomial` hits a device-side assert. On ROCm that assert aborts the queue with exactly the 0x1016 above. With `AMD_SERIALIZE_KERNEL=3`, the faulting launch is `sampler.py` `top_k_top_p_min_p_sampling_from_probs_torch` -> `torch.multinomial`. Calling `torch.multinomial` on NaN probabilities by itself reproduces the same error.

## Modifications

- `fused_moe_tp8_m4193_16768.py`: store the raw FP32 partials with `gl.store`, which uses 64-bit addresses, instead of `buffer_store`. Element offsets stay below 2^31. `_shared_reduce` already reads them with `gl.load`. The int16 codes are 1.5 GiB per half and keep using buffer ops. Raw partials are only written for escaped rows, so the cost is negligible. The misleading 4-GiB comment is updated.
- `test_gluon_moe_gfx950.py`: add `test_tp8_m32768_raw_partials_beyond_2gib`. It uses dense random routing, fills 16 GiB of freed allocator blocks with NaN, and runs M=32768. It then checks that the output is finite and bit-exact against the same tokens run in 4224-row batches, whose workspace stays below 2 GiB.
  - The existing `tp8_m4193_16768` M=32768 case did not catch this. Its sparse 37-token fixture produces no escaped rows past the window, and fresh allocations hide stale reads.

## Accuracy Tests

Kernel level, on MI355X with image `lmsysorg/sglang-rocm:v0.5.23-rocm720-mi35x-20261102`:

| | new test | full `test_gluon_moe_gfx950.py` |
|---|---|---|
| before | FAIL (non-finite output) | n/a |
| after | PASS | 4/4 PASS (84 s) |

A standalone driver gives the same picture: M=32768 has 6 NaN rows on every call before the fix, exactly the escaped rows past the window, and none after. M=16384 and M=8192 are bit-exact both before and after.

Server level, GLM-5.2-MXFP4 TP8/EP1 with Gluon MoE and EAGLE MTP, the InferenceX AgentX workload (`semianalysis_cc_traces_weka_062126`, concurrency 2):

| run | result |
|---|---|
| before, `parts_low/high` pre-filled with NaN (worst-case stale memory) | crashes with 0x1016 on all 8 GPUs at the first 32K chunk (2/2) |
| after, `parts_low/high` pre-filled with NaN | 1 h clean, 38,400 instrumented MoE calls with M > 10922, 0 non-finite output rows |
| after, normal | 1 h clean (3831 s, 32 full 32K chunks) |
