# [Apple Silicon][MPS] Cap memory reporting to Metal's recommended working set

[Upstream PR](https://github.com/sgl-project/sglang/pull/29949) · state: open · merged: False

## Original PR description

## Motivation

Fixes #21443.

On Apple Silicon the GPU shares unified memory with the CPU, but Metal can only keep [`recommendedMaxWorkingSetSize`](https://developer.apple.com/documentation/metal/mtldevice/2369280-recommendedmaxworkingsetsize) resident on the GPU (roughly 65-75% of RAM; 17.76 GiB on the 24 GB machine used below). The MPS code paths reported plain `psutil.virtual_memory()` numbers, so memory planning could size budgets against RAM the GPU subsystem can never safely use. Overcommitting the working set causes GPU paging and driver instability, and in the worst case the IOGPUFamily kernel panic and machine reboot discussed in #21443 and diagnosed in #29439.

The MLX serving backend already caps its own pool sizing to the working set and calls `mx.set_wired_limit()` (`python/sglang/srt/hardware_backend/mlx/model_runner.py`), so this PR closes the remaining torch-MPS reporting paths named in the issue.

## Modifications

**Unified Apple Silicon memory abstraction** (suggested by @yeahdongcn): the new `python/sglang/_apple_silicon_memory.py` module is the single dispatch point for Apple Silicon GPU memory queries. `use_mlx()` routes working-set / allocated / available / total-memory queries to MLX APIs (`mx.device_info()`, `mx.get_active_memory() + mx.get_cache_memory()`, `mx.clear_cache()`); otherwise they are answered by torch-MPS (`torch.mps.recommended_max_memory()`, `driver_allocated_memory()`, `empty_cache()`). Only stdlib is imported at module level, so `_mps_stub` (installed from `sglang/__init__`) and the `multimodal_gen` platform layer can depend on it without an `sglang.srt` import-time dependency.

The two runtimes' visibility is asymmetric: torch's `driver_allocated_memory()` is MTLDevice-level and already includes MLX buffers, while MLX's counters cannot see torch-MPS allocations — and MLX serving still bridges tensors through torch-MPS (`tensor_bridge`). Under `use_mlx()` the allocated view is therefore `max(mlx_active + mlx_cache, torch_driver_allocated)`, and `empty_cache` clears both allocators.

The three callsites from #21443 now route through these helpers:

1. `get_available_gpu_memory(device="mps")` in `python/sglang/srt/utils/common.py`: reports `min(system available, working-set headroom)`, clamped at zero. The branch now also honors `empty_cache` like the other device branches. If the working-set size is unavailable (API returns 0), the legacy psutil behavior is kept so startup does not report zero memory.
2. `get_device_properties()` in `python/sglang/_mps_stub.py`: `total_memory` now reports the Metal working set instead of total system RAM, with the same fallback.
3. `MpsPlatform` in `python/sglang/multimodal_gen/runtime/platforms/mps.py`: `get_device_total_memory()` and `get_available_gpu_memory()` apply the same cap.

Notes:

- `torch.mps.recommended_max_memory()` wraps `recommendedMaxWorkingSetSize` and has been in torch since 2.5 (torch is pinned to 2.11), so this adds no dependency. The torch paths still take no MLX dependency: MLX APIs are only consulted when `use_mlx()` is active, which implies mlx is importable.
- Same direction as the plan @karanb192 posted in the issue (cap reporting to the Metal working set), with deliberate implementation differences: available memory reports the remaining headroom (working set minus allocated) rather than the raw limit, and the `min()` with system-available memory is kept because unified memory is also consumed by the CPU side.
- The `mx.set_wired_limit()` part of the issue's reference implementation is already in place for the MLX backend. torch-MPS exposes no wired-limit API, and by default its allocator permits allocations up to a 1.7x high-watermark ratio of the recommended max working set, so nothing in the runtime prevents overcommitting it — accurate reporting is the guardrail #21443 asks for.
- The MLX backend's internal pool sizing (`hardware_backend/mlx/model_runner.py`) intentionally keeps calling MLX directly: it applies `mem_fraction_static` as an internal budget and is under active review in #29439; migrating it onto these helpers is a follow-up once that PR lands.
- A repo-wide sweep found no other MPS-as-GPU `psutil` callsites. `get_device_memory_capacity()` has no MPS branch and continues to return `None` there (callers treat it as unknown); it is left unchanged to keep this PR scoped to the reporting paths from the issue.

## Test

- GPU-free unit tests in `test/registered/unit/utils/test_mps_memory.py` (23 tests, mocked `torch.mps`, `mlx.core`, and `psutil`, registered in `base-a-test-cpu`): torch-path working-set cap, driver-allocated subtraction, unified-memory min, zero clamp, unknown-limit fallback, and `empty_cache` forwarding; MLX dispatch (working-set/total queries answered by a fake `mlx.core` while `torch.mps.recommended_max_memory` carries a poison value, proving it is not consulted); mixed-residency accounting (torch-side allocations visible under MLX mode, both allocator caches cleared); and `_mps_stub` device-properties reporting, fallback, and caching. The `torch.mps` mocks do not pass `create=True`, so the suite fails loudly if torch ever drops these APIs.
- On device (Apple Silicon, 24 GB): both dispatch paths report the same 17.76 GiB Metal working set (`torch.mps.recommended_max_memory()` and `mx.device_info()["max_recommended_working_set_size"]` agree byte-for-byte), `torch.mps.get_device_properties().total_memory` reports 17.76 GiB instead of 24 GiB, and unmocked `get_available_gpu_memory("mps")` never exceeds the working set. Under `SGLANG_USE_MLX=1`, a 2 GiB torch-side allocation moves the reported allocated/available numbers by ~2 GiB; it was invisible to MLX-only counters before the mixed-residency fix.
- The MLX unit test directory (`test/registered/unit/hardware_backend/mlx/`) is unaffected by this PR: the pool/init/scheduler contract modules pass, and the two modules that fail (`test_attention_patching`, `test_metal_profiler`) fail identically on current main without this PR (pre-existing upstream issues, invisible in Linux CI where mlx is not installed).
