# [Bugfix] Load block-FP8 MoE TP shards that split checkpoint blocks

[Upstream PR](https://github.com/sgl-project/sglang/pull/42566) · state: open · merged: False

## Original PR description

## Motivation

**Depends on #43556** (SM120 UE8M0 requant for the DeepGEMM grouped GEMM). This PR is based on it and contains its commit until it merges; only the last two commits are this change. The two were split at a maintainer's request.

A block-FP8 MoE layer whose per-rank intermediate size is not a multiple of the checkpoint block is rejected at weight creation. `nvidia/Qwen3.8-Flash-Next-NVFP4`'s MTP experts (FP8, 128x128 blocks, intermediate 640) hit this at TP2:

```
ValueError: The output_size of gate's and up's weight = 320 is not divisible by weight quantization block_n = 128.
```

The cookbook works around it with the BF16 head from the RadixArk export.

## Modifications

TP splits w13 along N and
w2 along K. Every checkpoint scale covers whole blocks of a finer grid along
that dimension, so repeating the scales onto it at load time is lossless, and
each rank loads exactly its shard. Only the split dimension is refined, so w13
keeps 128-wide K blocks and TP1's activation groups:

| | w13 block | w2 block |
|---|---|---|
| Triton | `[gcd(128, shard), 128]` = `[64, 128]` | `[128, gcd(128, shard)]` = `[128, 64]` |
| DeepGEMM (UE8M0) | `[64, 128]` | `[128, 32]` (K granularity is 32 or 128 only) |

- `Fp8MoEMethod.create_weights` picks the blocks from the runner the layer
  will use (`_resolve_moe_runner_backend`, factored out of
  `create_moe_runner`) and keeps one block per weight
  (`weight_block_size`, `w2_weight_block_size`). Aligned shards, MXFP8, FP4
  experts, pre-sharded weights, online quantization and other runners are
  unchanged; an unsupported split still raises.
- The block-scale weight loaders repeat checkpoint scales onto each weight's
  grid before the usual TP narrowing.
- Triton: `w2_block_shape` reaches the down GEMM and its activation quant, and
  the down kernel's `BLOCK_SIZE_K` is capped at w2's K block, since the kernel
  applies one scale per K tile.
- DeepGEMM: each weight is requantized to UE8M0 on its own block (grouped MoE
  accepts blocks dividing 128 with K granularity 32 or 128; dense layers keep
  128x128); the down GEMM gets w2's recipe and quantizes its activation at w2's
  K. `should_deepgemm_weight_requant_ue8m0` checks a grouped layer's K against
  the block's K instead of 128.
- Cookbook: the Qwen3.8-Flash-Next NVIDIA-export note no longer says the MTP
  experts cannot be split; the measured two-node cell still uses the RadixArk
  draft.

## Accuracy Tests

`test_fp8_moe_tp_block_refine.py` builds a real `FusedMoE` with `Fp8Config`,
loads a 128x128 block-FP8 checkpoint through the layer's weight loaders at TP1
and as each of two TP ranks, and compares the summed ranks with TP1 against an
FP32 reference on the dequantized checkpoint (RTX PRO 6000, SM120):

| Runner | Tokens | TP1 rel. error | TP2 (refined) rel. error |
|---|---|---|---|
| Triton (w13 64x128, w2 128x64) | 33 | 0.04424 | 0.04368 |
| DeepGEMM (w13 64x128, w2 128x32) | 33 | 0.06400 | 0.06393 |
| DeepGEMM | 1100 (SM120 contiguous layout) | 0.06535 | 0.06535 |

Activation rounding to FP8 dominates both columns.

Without this change the Triton case fails at weight creation with the error
above. The DeepGEMM case needs #43556 on SM120: without it, it faults at TP1
already, from the unrequantized FP32 scales. The quantization and MoE unit
suites otherwise show the same failures before and after (all pre-existing on
SM120).

End to end, `nvidia/Qwen3.8-Flash-Next-NVFP4` at TP2 with its own MTP head
(NEXTN 3/1/4, draft experts on DeepGEMM), GSM8K through the chat template
(lm-eval `gsm8k`, 1,319 questions, flexible-extract): 0.976, MTP mean accept
length 3.0 of 4 (2x RTX PRO 6000).

@Fridge003 Thanks, padding works here. Before I rewrite, I'd like to agree on the tradeoff.

**Padding.** Each rank keeps 128x128 blocks and pads its shard out to whole checkpoint blocks: front pad `(rank * shard) % 128`, then round up to a multiple of 128. At I=640 TP2 that is 320 -> 384 rows on both ranks. Rank 0 pads at the end; rank 1 starts mid-block (row 320), so it pads 64 zero rows at the front. gate/up are padded separately in w13, and w2 gets the matching zero K columns. Since act(0) * 0 = 0 for the padded rows, the output is unchanged. The change stays in the weight loader and `create_weights`. The runners, the DeepGEMM requant and the down-GEMM activation quant are untouched. It also makes the bot's findings here moot (TMA group size, SiTU masked path, weight checker, CPU AMX), because every kernel still sees 128x128.

**Cost.** The padded layer does 20% more work per rank (384/320), and holds about 0.25 GB more weights per rank for this MTP layer. That is an estimate, not measured yet. Per layer it is at most ~20% slower than the refined version, probably less, because refinement has its own costs: Triton's down `BLOCK_SIZE_K` is capped at 64 and DeepGEMM's w2 runs at K granularity 32. End to end, only the MTP experts are affected. At TP2 / NEXTN 3 that is roughly +50 us on a ~16 ms verify step, ~0.3%.

**Refinement (current PR).** No extra FLOPs or memory, but it adds per-weight block shapes to the Triton and DeepGEMM paths. Those still need the fixes the bot flagged.

My preference is padding: the perf cost is small for this case, and the code is much simpler. Shards that split a block are rare outside MTP heads, as far as I know. If that matches what you want, I'll rewrite the PR that way and post measured numbers for both runners against the current tables. Or would you rather keep the refined path for the extra performance?
