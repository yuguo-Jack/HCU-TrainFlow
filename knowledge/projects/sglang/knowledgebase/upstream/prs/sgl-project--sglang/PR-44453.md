# [Fix] pp: Order output send/recv by rank parity to fix cross-node hang

[Upstream PR](https://github.com/sgl-project/sglang/pull/44453) · state: closed · merged: True

## Original PR description

## Motivation

With pipeline parallelism across nodes, both PP stages hang once two microbatches are in flight. We hit this on a cross-node PP2 PD-prefill deployment (two 8×B300 nodes). Concurrent requests arriving a few milliseconds apart are split into different microbatches; both stages then block in `d2h_event.synchronize()`, and after 10 minutes the NCCL watchdog fails a `SEND` on the PP device group. A single request, or requests that land in the same microbatch, never trigger it.

**Root cause.** On every scheduler loop iteration, `_pp_send_recv_and_preprocess_output_tensors` makes each PP rank send one microbatch's output downstream and receive another microbatch's output from upstream. The last rank returns its output to rank 0, and the other ranks relay what they received last iteration. On CUDA every rank posts its send first. The comment says that is safe because `isend` is async, but only the CPU call is async. NCCL p2p ops between a pair of ranks run in order on one stream. A send can complete before the peer posts its matching recv only while the connection's buffer has free slots: about two ops over NET/IB (any cross-node PP), and about eight over NVLink.

With two microbatches in flight on PP2, the per-pair stream order is:

```
PP0: recv out(mb2) -> send relay(mb2) -> recv out(mb0)
PP1: send out(mb2) -> send out(mb0)   -> recv relay(mb2)
```

- PP0's `send relay(mb2)` waits for PP1's `recv relay(mb2)`.
- That recv is queued behind PP1's `send out(mb0)`.
- PP1's `send out(mb0)` waits for PP0's `recv out(mb0)`, which is queued behind PP0's send.

Once the buffer cannot absorb the queued sends, the waits form a cycle and both GPUs hang.

#30775 already moved PP + speculative decoding to parity ordering for the same reason ("enqueueing that many sends before any recv can form the same ring wait on CUDA"). XPU uses parity ordering too. The non-spec CUDA path kept send-first. Single-node CI runs over NVLink, where the larger buffer hides the problem.

**NCCL-only check** (no SGLang, script below). The script replays the op order above, with each message carrying K device tensors of 2048 floats, on 2 × B300 with NCCL 2.30.7:

| Transport | send-first (main) | parity (this PR) |
|---|---|---|
| NET/IB loopback (`NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1`) | K=2 OK, **K≥3 hangs** | OK at every K tested (up to 64) |
| SHM (`NCCL_P2P_DISABLE=1`) | K=8 OK, **K=16 hangs** | not tested |
| NVLink (default) | K=8 OK, **K≥9 hangs** | OK at every K tested (up to 64) |

## Modifications

- `scheduler_pp_mixin.py`: `_pp_send_recv_and_preprocess_output_tensors` now orders send/recv by `pp_rank` parity on every backend (even: send → recv, odd: recv → send), the order XPU and PP + spec already use. Even ranks keep their current order. Odd ranks now post their recv first, so every adjacent pair has one recv-first side.
  - The function is shared by `event_loop_pp`, `event_loop_pp_disagg_prefill`, and `event_loop_pp_disagg_decode`.
  - The NPU PP2 `batch_isend_irecv` path is unchanged.
  - The unused `is_xpu` import is removed and the comment is rewritten.
- New CPU unit test `test/registered/unit/managers/test_pp_output_exchange_order.py`. It runs the real function for both PP2 ranks with two microbatches in flight and records the device p2p ops each rank posts. It then checks that the ops pair up under the worst case, where every send waits for the peer's recv at the head of its stream. On main the non-spec case fails and the spec case passes; with this PR both pass.

## Accuracy Tests

**End-to-end reproduction** on one node with 2 × B300 (PP2), Qwen3-0.6B, `--pp-size 2 --mem-fraction-static 0.5`. NCCL is forced onto NET/IB loopback so the transport matches cross-node PP:

```bash
NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1 NCCL_IB_HCA==<hca> NCCL_IB_GID_INDEX=<gid> NCCL_SOCKET_IFNAME=<ifname>
```

The client (script below) runs rounds of 4 concurrent `/generate` requests:
- 37 / 201 / 600 / 1800 random input tokens, with `return_logprob=True`, `logprob_start_len=0`, and `max_new_tokens=8`.
- Requests within a round are offset by 0, 2, 5, or 10 ms, with 6 rounds per offset.
- A round that does not finish within 30 s counts as a hang.

| Config | main | This PR |
|---|---|---|
| NET, 3 fresh server launches × 24 rounds | **hangs in all 3 launches**, within the first 3 rounds | 72 / 72 rounds pass |
| NET, `/flush_cache` before every round | - | 24 / 24 |
| NET, 12 concurrent requests up to 15000 tokens, 3 ms offset, `top_logprobs_num=5`, 8 rounds | - | 8 / 8 |
| NVLink (default) | 48 / 48 (with and without `/flush_cache`) | 24 / 24 |

On main, when the hung server is left running, PP0 and PP1 both hit `Scheduler watchdog timeout` with the batch still in flight.

**Output equivalence:** on the Qwen3-8B benchmark servers below, a greedy request with input and output logprobs (16 new tokens) returns bit-identical logprobs on main and on this PR, over both NVLink and NET (6 server launches).

**Unit tests:** `test_pp_output_exchange_order.py` (new) and `test_pp_cp_rank_offsets.py` pass.

The same change fixed the original cross-node PD-prefill hang in our fork. On upstream main it was verified with IB loopback on a single node, as above.

```python
"""NCCL-only repro of the PP2 output exchange with two microbatches in flight.

PP0: recv out(mb2) -> send relay(mb2) -> recv out(mb0)
PP1: send out(mb2) -> send out(mb0) -> recv relay(mb2)   (send_first, main)
PP1: send out(mb2) -> recv relay(mb2) -> send out(mb0)   (parity, this PR)

Each message is K small device tensors. Usage:
  python pp_output_exchange_nccl.py {send_first,parity} K
"""

import os
import random
import sys
import time

import torch
import torch.distributed as dist
import torch.multiprocessing as mp


def worker(rank, order, k, port):
    os.environ.update(MASTER_ADDR="127.0.0.1", MASTER_PORT=str(port))
    torch.cuda.set_device(rank)
    dist.init_process_group("nccl", rank=rank, world_size=2,
                            device_id=torch.device("cuda", rank))
    peer = 1 - rank
    buf = lambda: torch.ones(2048, device="cuda")
    for _ in range(2):  # warm up the connection in both directions
        if rank == 0:
            dist.send(buf(), peer); dist.recv(buf(), peer)
        else:
            dist.recv(buf(), peer); dist.send(buf(), peer)
    torch.cuda.synchronize()
    dist.barrier()

    works = []
    send = lambda: works.extend(dist.isend(buf(), peer) for _ in range(k))
    recv = lambda: works.extend(dist.irecv(buf(), peer) for _ in range(k))
    if rank == 0:
        recv(); send(); recv()
    elif order == "send_first":
        send(); send(); recv()
    else:
        send(); recv(); send()
    deadline = time.time() + 15
    while not all(w.is_completed() for w in works):
        if time.time() > deadline:
            print(f"rank{rank} HANG order={order} k={k}", flush=True)
            os._exit(1)
        time.sleep(0.01)
    print(f"rank{rank} OK order={order} k={k}", flush=True)
    dist.destroy_process_group()


if __name__ == "__main__":
    order, k = sys.argv[1], int(sys.argv[2])
    mp.spawn(worker, args=(order, k, random.randint(20000, 40000)), nprocs=2)
```

```python
"""Staggered concurrent logprob requests against a PP server; detect hangs."""

import argparse
import concurrent.futures as cf
import random
import sys
import time

import requests

p = argparse.ArgumentParser()
p.add_argument("--url", default="http://127.0.0.1:30000")
p.add_argument("--rounds", type=int, default=6)
p.add_argument("--stagger-ms", type=float, nargs="+", default=[0, 2, 5, 10])
p.add_argument("--lens", type=int, nargs="+", default=[37, 201, 600, 1800])
p.add_argument("--max-new-tokens", type=int, default=8)
p.add_argument("--top-logprobs-num", type=int, default=0)
p.add_argument("--timeout", type=float, default=30)
p.add_argument("--flush", action="store_true")
args = p.parse_args()


def one(n, seed, delay):
    time.sleep(delay)
    rng = random.Random(seed)
    payload = {
        "input_ids": [rng.randint(100, 30000) for _ in range(n)],
        "sampling_params": {"max_new_tokens": args.max_new_tokens, "temperature": 0},
        "return_logprob": True,
        "logprob_start_len": 0,
    }
    if args.top_logprobs_num:
        payload["top_logprobs_num"] = args.top_logprobs_num
    r = requests.post(args.url + "/generate", json=payload, timeout=args.timeout)
    r.raise_for_status()


for stagger in args.stagger_ms:
    for rnd in range(args.rounds):
        if args.flush:
            requests.post(args.url + "/flush_cache", timeout=30)
        with cf.ThreadPoolExecutor(len(args.lens)) as ex:
            futs = [ex.submit(one, n, rnd * 1000 + i, i * stagger / 1000)
                    for i, n in enumerate(args.lens)]
            try:
                [f.result() for f in futs]
            except Exception as e:
                sys.exit(f"HANG stagger={stagger}ms round={rnd}: {e}")
        print(f"ok stagger={stagger}ms round={rnd}", flush=True)
print("ALL PASSED")
```
