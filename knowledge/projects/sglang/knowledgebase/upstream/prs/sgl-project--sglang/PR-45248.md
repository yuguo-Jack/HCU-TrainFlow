# [Refactor] kda: Import recurrent_kda from the canonical flashinfer namespace

[Upstream PR](https://github.com/sgl-project/sglang/pull/45248) · state: closed · merged: True

## Original PR description

### Motivation

`flashinfer.kda_decode.recurrent_kda` ships in flashinfer-python 0.7.2 as a deprecated shim (added in 0.7.1 by flashinfer-ai/flashinfer#5248, marked `.. deprecated:: 0.8`): it forwards to the same decode dispatcher as `flashinfer.recurrent_kda`, calls `warnings.warn(DeprecationWarning)` with a frame walk on every call (the cost is paid even when Python's default filters hide the message), and is scheduled for removal. SGLang already pins `flashinfer_python[cu13]==0.7.2`, which ships the canonical entry point with the same decode contract, so the FlashInfer KDA wrapper can move off the shim before it disappears.

### Modifications

- `python/sglang/srt/layers/attention/linear/kernels/kda_flashinfer.py`: import `recurrent_kda` from `flashinfer` instead of `flashinfer.kda_decode`; update the module docstring.
- `benchmark/bench_linear_attention/bench_kda_flashinfer_mtp.py`: update the docstring that named the deprecated facade.

No call-site change. The shim resolved an omitted `backend` to `"cute-dsl"`; the canonical function defaults to `backend="auto"`. Both SGLang call sites (`decode` and `target_verify`) pass `cu_seqlens`, and in flashinfer 0.7.2 `backend="auto"` keeps explicit-`cu_seqlens` decode on the CuTe DSL kernel without consulting the Cake selector, so the kernel that runs is the same as before.

### Accuracy Tests

The wrapper calls the same kernel with the same arguments. `bench_kda_flashinfer_mtp.py` compares the FlashInfer output against the Triton KDA reference on every row; the max abs diff is reported in the last column of the table below and is identical before and after on every row.

### Speed Tests and Profiling

B200 (SM100), bf16, H=HV=16, K=V=128, pool 512, `benchmark/bench_linear_attention/bench_kda_flashinfer_mtp.py` per-call time from CUDA events around 100 back-to-back calls after 20 warmup calls; two independent process runs per arm, reported as run1 / run2. Decode and verify at B<=32 are host-bound, so those rows are per-call host issue time; verify at B>=64 is kernel-bound and the host path is not visible there. Before = `flashinfer.kda_decode.recurrent_kda`, After = `flashinfer.recurrent_kda`.

No regression: on every row the after arm is equal to or faster than the before arm in at least one run, and every before/after difference is inside the run-to-run spread of the same arm (up to about 10% on the host-bound rows). The kernel-bound verify rows at B>=64 agree to within 0.1 us. `out_max_diff` vs Triton is identical before and after on every row. The Cake selector (`_select_flash_kda_decode_variant_cached`, `_select_flash_kda_decode_variant`) and the Cake launcher (`_run_flash_kda_decode`) were called zero times in every run, so `backend="auto"` keeps these `cu_seqlens` call sites on the CuTe DSL kernel. An earlier set of eight runs on 2026-10-16 against the pre-rebase commit gave the same picture.

### How this was measured

One NVIDIA B200 (SM100, CC 10.0) on `cudnn-dev-keel-26-04`, container `lmsysorg/sglang:dev` with torch 2.14.1+cu130 and the flashinfer-python 0.7.2 wheel (SGLang's current pin), SGLang imported from this branch at `67b3dd32`. Each arm ran in its own process with the arm's function forced into the wrapper's lazy-import slot and asserted active (`active=flashinfer.kda_decode.recurrent_kda` vs `active=flashinfer.kda.recurrent_kda` in the log headers); default warning filters were left in place so the deprecated arm paid the shim's `warnings.warn` as SGLang does in production. Each process ended with `counts={'dispatch': 726, 'select_cached': 0, 'select_inner': 0, 'cake_launch': 0}` and `EXIT_OK`. An idle `VLLM::EngineCore` belonging to another user (55 GB, 0% utilization) was resident on the GPU throughout and was not touched. Script and logs under `/home/scratch.knam/flashinfer-work/general/.projects/recurrent-kda-unification/sglang-migration/rework_2026-10-16/`: `ab_sglang_migration.py` and `logs_{deprecated,canonical}_{decode,verify}_2026-10-19_run{1,2}.log` (eight files); the 2026-10-16 runs are the `logs_{deprecated,canonical}_{decode,verify}.log` and `_run2.log` files beside them. Correctness is against SGLang's Triton KDA kernel only, bf16, H=HV=16, K=V=128, T=1 and T=8; no other head counts, dtypes or fused-accept paths were measured, and only SM100 was exercised (the wrapper is SM100-gated).
