# [Feat] sglang-server: Serve /flush_cache from the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44766) · state: closed · merged: True

## Original PR description

## Motivation

A server running the Rust frontend answers 404 on `/flush_cache`, so a
client that clears the prefix cache between benchmark or evaluation phases
(`POST /flush_cache?timeout=30` on every engine) fails against it. The
Python frontend has served this route for a long time, and the
scheduler-side handler (`SchedulerFlushWrapper`) already runs whichever
frontend is in use; only the HTTP route and its control request were
missing on the Rust side.

A second gap sits behind the first. A flush that has to wait for running
requests (`timeout > 0` on a busy server) is answered later, from
`SchedulerFlushWrapper.check_pending`, and that deferred reply went
straight to the zmq tokenizer socket. In Rust mode nothing reads that
socket, so the HTTP call would never return.

## Modifications

- `rust/sglang-server/src/message/io_struct.rs`: add the `FlushCacheReqInput`
  control message with the same positional wire layout as the Python
  msgspec struct: `[tag, rid, http_worker_ipc, timeout_s]`.
- `rust/sglang-server/src/api_server/core/handle.rs`: `CoreHandle::flush_cache`
  sends that request through the existing control path and decodes the
  scheduler's `FlushCacheReqOutput` (`success`, `message`).
- `rust/sglang-server/src/api_server/http/info.rs`: route `GET|POST
  /flush_cache?timeout=<s>` with the Python contract: 200 and Python's
  plain-text `Cache flushed. ...` body once flushed; otherwise 400 with the
  scheduler's reason, or `Flush cache failed.` when it gave none. No content
  type, like Python's bare `Response`. A negative `timeout` is a 400 before
  anything reaches the scheduler.
- `python/sglang/srt/managers/scheduler.py`: the control-reply branch of
  `process_input_requests` becomes `Scheduler.send_control_output`, which
  takes the embedded Rust server's egress ring when there is one and the
  tokenizer socket otherwise. Behaviour at dispatch time is unchanged.
- `python/sglang/srt/managers/scheduler_components/flush_wrapper.py`: the
  wrapper takes a `send_output` callable instead of the IPC channels and
  answers a deferred flush through it, so the reply follows the same path
  as every other control reply.

Python's `TokenizerManager.flush_cache` also clears the multimodal
processor's preprocessing cache; the Rust multimodal pipeline keeps no such
cache, so there is nothing to clear there.

Tests:
- `flush_cache_relays_the_scheduler_outcome` (Rust): `GET` and `POST` send
  one `FlushCacheReqInput` carrying the query timeout, then answer 200 with
  Python's text, 400 with the scheduler's message, or 400
  `Flush cache failed.`, with no content type; a negative timeout never
  reaches the scheduler.
- `flush_cache_req_msgpack_shape` (Rust): pins the four-element wire array.
- `test_scheduler_flush_cache.py`: the existing wrapper tests now check the
  `send_output` callable, and
  `test_control_output_goes_to_the_embedded_rust_server` pins the deferred
  reply's routing (Rust egress ring when a Rust server is embedded, tokenizer
  socket otherwise).
