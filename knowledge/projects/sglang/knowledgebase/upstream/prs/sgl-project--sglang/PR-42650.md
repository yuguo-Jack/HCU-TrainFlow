# [Mamba2] Add checkpoint-preserving FlashInfer SSD prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/42650) · state: open · merged: False

## Original PR description

## Summary

Add opt-in FlashInfer SSD prefill for Mamba2 with
`--mamba-prefill-backend flashinfer` (default remains `triton`). This accelerates
recurrent prefill while preserving live states and reusable checkpoints.

## Implementation

- Prepare packed-sequence/checkpoint metadata once per forward. Capture selected
  checkpoints in the same scan, without changing checkpoint policy.
- Isolate padding in a discarded sequence so it cannot alter real final states.

Code: [SSD adapter](https://github.com/NVShreyas/sglang/blob/313fcd4ff8/python/sglang/kernels/ops/mamba/flashinfer_ssd.py),
[correctness tests](https://github.com/NVShreyas/sglang/blob/313fcd4ff8/test/registered/kernels/ops/mamba/test_flashinfer_ssd_prefill.py).
Currently requires SM100 and static contiguous pools; unified/page-major pools
are unsupported.

## Dependency / release blocker

**Waiting for a FlashInfer release containing the validated SSD changes before
updating the dependency pin and completing standalone qualification.**

SGLang main currently pins FlashInfer **0.7.1**. That version already exposes
the SSD/checkpoint APIs, but its numerical implementation differs from the one
validated here:

- 0.7.1 stores processed delta in **BF16** and uses shape-dependent scan dispatch.
- Upstream [FlashInfer #6051](https://github.com/flashinfer-ai/flashinfer/pull/6051)
  changes processed delta to **FP16** and consolidates dispatch into an
  **exact-only scan** family. It also retires the prefix route with its documented
  overflow/NaN issue.

Our validation used unmodified upstream
[`461037fbf`](https://github.com/flashinfer-ai/flashinfer/commit/461037fbf52227e6343ccbc9fc977337c1bf672b),
reporting `0.7.2+g461037fbf`: this is a **development/source build**, not a
qualified released wheel. This is a numerical-qualification dependency, not a
claim that the APIs are absent or cannot run in 0.7.1.

Once a release includes these changes, update the SGLang dependency pin and rerun
standalone SSD kernel correctness and full GSM8K **with and without SSD** on the
same environment. Those standalone accuracy runs remain pending.

**Issue**

This check accepts the flag with any installed FlashInfer, but the repo pins `flashinfer_python==0.7.1`. The PR needs FlashInfer 461037fbf, which is in no release yet. In 0.7.1, `CakeSSDCombined` takes the `prefix_varlen` route when `dt_limit[0] >= 0`, `nheads == 128`, `ngroups == 8`, and the packed batch has no more logical chunks than sequences. The `test_short_strong_decay` docstring says that route is unstable.

**Example**

Nemotron 3 Super at TP1 (128 heads, 8 groups) with a batch of short extends takes that route on 0.7.1. `test_short_strong_decay` uses the same shape and will run on 0.7.1 in CI.

**Fix**

In this PR, bump `flashinfer_python` in `python/pyproject.toml` and `FLASHINFER_VERSION` in `docker/Dockerfile` to a release with 461037fbf, and reject older versions here.

File: `python/sglang/kernels/ops/mamba/flashinfer_ssd.py` · line 183

[by Claude Code] **Severity: perf | Confidence: Medium**

**Issue**

`flashinfer_ssd_prefill` does not pass `out` to `ssd_combined_fwd`, so every call copies the whole output back here. When the token count is not a multiple of 128, it also copies x, dt, B, C, and `initial_states` to add the padding sequence (lines 150-160). At FlashInfer 461037fbf, the Cake path accepts any positive length (it handles a partial last chunk itself) and writes a contiguous token-major `out` directly.

**Example**

With 32768 tokens and 128 heads, this copy alone reads and writes 512 MiB per Mamba layer on every prefill.

**Fix**

Once the pin requires 461037fbf, pass `out=out` and drop the padding sequence and `pad_tokens`.

**Issue**

This loop copies the track-endpoint rule from `build_prefill_track_plan` in `prefill_track_metadata.py`. The comment says it must match the Triton policy exactly, but nothing links the two, and no test runs this loop; the new GPU test calls the adapter directly. **Fix**

Build the endpoints from `build_prefill_track_plan(...)`: rows in `final_rows` map to `length`, and unaligned rows map to `chunk_indices[row] * chunk_size`. Add a CPU unit test for aligned, unaligned, and shorter-than-one-chunk tracks.
