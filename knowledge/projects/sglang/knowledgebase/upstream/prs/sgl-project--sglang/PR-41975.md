# [Perf] quantization: Opt-in bf16 path for small-M block-FP8 attention projections

[Upstream PR](https://github.com/sgl-project/sglang/pull/41975) · state: open · merged: False

## Original PR description

> **Draft for code review.** This branch is based on `4358a16` (main as of 2026-09-13), the commit it was developed and tested on. It does not merge cleanly into current `main` yet; I will rebase once the approach is agreed.

## Motivation

In small-batch decode, the block-FP8 attention projections of DSA-style models (`fused_qkv_a_proj_with_mqa`, `q_b_proj`, `o_proj` and the indexer `wq_b`) run on the block-FP8 GEMM path, which is inefficient when a call has very few rows. Profiling showed these projections among the largest reducible costs of a small-batch decode step. A bf16 copy of just these weights lets small calls take the bf16 GEMM path a bf16 checkpoint would use.

## Modifications

- New env flags: `SGLANG_BF16_DECODE_PROJ=1` enables the path; `SGLANG_BF16_DECODE_PROJ_MAX_TOKENS` sets the row cutoff.
- At load, keep a bf16 copy of the four projections, made by `block_quant_dequant` of the checkpoint weight before requantization (so it is the exact dequantized weight).
- At run time, calls with at most the cutoff rows use the bf16 GEMM path; larger calls (prefill, big batches) keep the existing block-FP8 path.
- Off by default; with the flag unset nothing changes. Costs extra memory for the bf16 copies of these four projections only.

## Accuracy Tests

The bf16 weights are the exact dequantization of the FP8 checkpoint weights. GSM8K accuracy matched the default path in our tests.

## Speed Tests and Profiling

Lowers decode step time at small batch sizes; the gain shrinks as batch size grows past the cutoff. Happy to share detailed profiles with reviewers.
