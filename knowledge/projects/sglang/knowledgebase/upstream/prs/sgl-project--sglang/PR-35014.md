# Feat: [diffusion]Support MAGI-2-preview

[Upstream PR](https://github.com/sgl-project/sglang/pull/35014) · state: open · merged: False

## Original PR description


## Motivation
Relate #35011

Adds native support for [MAGI-2-preview](https://huggingface.co/sand-ai/MAGI-2-preview),
SandAI's 114B MoE model that generates a video and its synchronized stereo
soundtrack in one denoising trajectory. About 6B parameters are active per token.

Audio is not a second pass over finished video: video and audio latents share one
packed sequence and one denoise loop. Text-to-video and image+text-to-video are
both supported.

The checkpoint ships two DiTs. A preview model denoises the clip, and a refiner
then takes that result to 1920x1088; the words "preview" and "refiner" below always
mean those two.

Serving it today means standing up a second stack. The reference implementation
launches under `torchrun`, depends on SandAI's own kernels
([MagiAttention](https://github.com/SandAI-org/MagiAttention),
[MagiCompiler](https://github.com/SandAI-org/MagiCompiler), FlashAttention 3) and so
ships as a [Docker image](https://hub.docker.com/r/sandai/magi-2-preview), and its
checkpoint has no `model_index.json`. This PR builds it against SGLang's own layers
so it is served like every other family in `sglang.multimodal_gen`.

## Modifications

### New code

Four pieces the tree did not already have. Everything else goes through existing
machinery.

- **Multi-head MoE** (`runtime/layers/moe_multihead.py`). MAGI-2 routes 12
  independent heads over 256 experts each, top-6, where the tree's MoE assumes one
  routing head. Viewing tokens as `[N * 12, 256]` instead of `[N, 12, 256]` makes it
  a standard MoE with `hidden_size=256` and `num_experts=3072`, so srt's Triton
  `fused_experts` runs unmodified. A rank owns `(12 / ep_size) * 256` of those, and
  `moe_align_block_size` runs 1024 threads while indexing `prefix[num_experts]`, so
  anything past 1023 takes an illegal memory access; the experts run in balanced head
  chunks that fit, which is one call at `ep_size >= 4` and is what lets 1, 2 and 3
  work at all. MAGI-2's activation, which it calls `swiglu7`, is a sigmoid-gated GELU
  approximation clamped to ±7 and maps onto that kernel's existing `gemm1_alpha` and
  `gemm1_clamp_limit`.
- **Attention sinks** (`runtime/layers/attention/backends/flash_attn.py`). Both DiTs
  use one always-attended sink token per sequence, and the FlashAttention backend
  accepted no `sinks` argument, so those logits were dropped silently. Now plumbed
  through, along with `window_size`.
- **Block-window local attention**
  (`runtime/layers/attention/magi2_block_grid_attention.py`). Every refiner layer
  restricts video-to-video attention to a radius-(2,2,2) ball on the 3-D latent
  block grid, which no `(left, right)` flash window can express, so it is carried as
  a `flex_attention` `BlockMask` built from tile occupancy rather than through
  `create_block_mask` and its dense intermediate. The same mask is also expressed as
  token-range pairs for MagiAttention's `flex_flash_attn_func`, which is used when
  that package is importable and is 1.78x faster on the refiner's shape; without it
  the `flex_attention` path runs unchanged.
- **Multi-stream hyper-connections**, mHC (`runtime/models/dits/magi2_mhc.py`). The
  preview DiT's residual is 4 parallel streams of 3072 rather than one of 12288,
  mixed by a per-block matrix that Sinkhorn-Knopp normalization keeps doubly
  stochastic.

### Reused from the tree

Both DiTs are wired to the existing optimizations rather than reimplementing them:

- **Ulysses sequence parallelism** carries the packed sequence. Rows are sharded
  once per forward and gathered at the end, and pad rows from an uneven split get
  their own varlen segment so real tokens cannot attend to them.
- **Expert parallelism** shards the MoE head axis with one all-to-all, through the
  same `ep_group` plumbing srt's MoE uses. `ep_size` defaults to the world size and
  can be set below it through `--pipeline-config-path`, which is how 8 ranks run.
- **Layerwise and CPU offload** via `LayerwiseOffloadableModuleMixin` and
  `layer_names`, so `--dit-layerwise-offload` and `--cpu-offload-components` work
  without model-specific code.
- `AutoencoderKLWan` for the video VAE (which is what MAGI-2 ships), the UniPC
  scheduler, FSDP sharding through `_fsdp_shard_conditions`, and the
  `PipelineStage` / `Req` / `OutputBatch` contracts.

### Structure

Eleven stages under `runtime/pipelines_core/stages/model_specific_stages/magi2/`.
Two orderings matter and are easy to break in review:

Image encoding runs **before** text encoding, because each conditioning image needs
a `<Figure N>` phrase present in the prompt; pooling that phrase's embedding runs
**after**, because it needs the encoded prompt. A conditioning image is not the
clip's first frame — it is VAE-encoded, parked past the clip on the rope time axis,
and bound to the prompt through that pooled embedding.

The denoise loop is model-owned rather than delegated to `DenoisingStage`, because
video and audio carry separate guidance scales and separate multistep scheduler
state, which the shared loop's single-latent contract cannot represent. Compile,
residency and warmup still come from the base stage.

### Parallelism

`--num-gpus` must divide every Ulysses head axis, since a rank owns whole heads on
all of them: 24 preview attention heads, 32 refiner attention heads, 8 refiner GQA
key/value heads. The preview's 12 MoE heads are sharded by `ep_size` instead and are
checked against that. The refiner's 8 bind, so the two-stage tier admits 2, 4 or 8
and preview-only also admits 3, 6 and 12. All four axes are checked in
`validate_server_args`, so a bad count fails at launch instead of inside a
collective.

8 GPUs divides every Ulysses axis but not the preview's 12 MoE heads, so it needs an
explicit `ep_size` of 4: two expert-parallel groups of 4 ranks, each holding all 12
heads. The reference instead pads the head axis to 16 and gives the spare ranks
zero-weight experts; this PR needs no padding and leaves no rank idle.

`--enable-cfg-parallel` is rejected — the denoise loop already runs both branches
itself, so splitting CFG across ranks would double-apply the guidance.

Expert parallelism is also what lets the weights fit, not merely what makes them
fast: the preview partition is 228 GB in BF16 and only its expert tensors shard, while
the 6.7B refiner is replicated per rank. Below 4 ranks the expert weights need
`--dit-layerwise-offload` to fit at all.

### Deliberate divergences from the reference

Both are marked at the site in the code.

**The refiner's residual accumulates in BF16, not FP32.** The reference promotes it
at the first `down_proj` and holds FP32 through all 30 layers. Matching that roughly
doubles the residual's footprint across 30 layers at the 1080p sequence length, which
the two-stage tier does not have to spare. The refiner's QK-norm likewise stores
in BF16 while reducing in FP32, where the preview DiT can afford FP32 through the
rotary.

**Expert-parallel head padding is not implemented**, and is not needed: an `ep_size`
below the world size reaches 8 ranks without it, as described under Parallelism.

### Docs

`docs/cookbook/diffusion/MAGI/MAGI-2.mdx` covers the quality tiers, the parallelism
rules, offload recipes, and the stage timings below. Added to the compatibility
matrix.

### Known limitations

- Only 1920x1088 and 896x512 are accepted, rejected before denoising otherwise.
  1088 rather than 1080 because the VAE stride forces multiples of 16.
- 10-second clips only; the model was trained for one duration.
- `--enable-torch-compile` must be paired with `--regional-compile`. On its own it
  compiles the whole transformer, and inductor autotuning then fails on the
  multi-head MoE GEMMs, asking more shared memory than sm90 has
  (`triton_mm Required: 262144, Hardware limit: 232448`). With `--regional-compile`
  the expert GEMMs stay out of the compiled region and both DiTs compile per block.
  Compile is also rank-count dependent: it pays at 4 ranks and loses at 8, where the
  preview pass measures 335s compiled against 184s eager.
- 1 GPU passes validation but runs out of memory while loading the preview DiT, which
  casts the whole state dict to the device before layerwise offload can take over.
- 2 GPUs needs `--dit-layerwise-offload`; the expert weights are 217 GB.
- `ep_size` has no CLI flag, so the 8-rank launch needs
  `--pipeline-config-path` with `{"ep_size": 4}`.
- `--tp-size` and `--ring-degree` are rejected, per the speed tests below.
- FlashAttention only. Sinks and the packed varlen path exist nowhere else, so
  `sage_attn` is rejected rather than silently degraded.
- The two-stage tier wants `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`. Its
  decode asks for one large block while both DiTs are resident, which otherwise
  tends to fail on fragmentation well into a run. A startup warning fires when it is
  unset.

### Unit tests

59 unit tests, 51 of which need no GPU: the MoE router and expert layout, mHC
normalization, rope construction and partial rotation, the coordinate builder,
packed-sequence layout, the noise schedule the refiner restarts from, guidance
arithmetic, the block-grid mask and the block order it must be applied in,
sequence bucketing, the expert-axis sharding predicate, and which submodules the
regional-compile conditions select. The remaining 8 need CUDA and are skipped
without it: the mHC mixing kernel against an FP32 reference, and the block-window
mask against a dense `scaled_dot_product_attention` reference.

They are flat files under `test/unit/`, so `_discover_unit_tests()` picks them up
and they run in the existing suite with no CI change:

```
python3 sglang/multimodal_gen/test/run_suite.py --suite unit
```

The full 1080p path needs at least two cards and minutes per clip, so it is not in
the suite.

## Speed Tests and Profiling

All figures below are one machine's numbers — 4x H200 at `--ulysses-degree 4` with
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` — and are meant as relative
comparisons, not as sizing targets. They are eager-mode figures; the compiled
configuration and the comparison against the reference are in Benchmark below.

**One 1080p clip, 100 preview + 5 refiner steps, text-to-video — 592s total:**
text encoding 17.6s, preview denoise 452.8s, the preview-to-refiner handoff under
0.1s, refiner denoise 101.6s, decode 15.5s. Weight load is separate and paid once
per process, about 5 minutes for both DiTs. Image-to-video costs more — the
conditioning image adds 1680 patch tokens and the longer caption takes 24s to
encode — and measures 741s.

**Batch stability.** Eight clips of differing prompt length in one process gave
refiner times of 101.6, 102.4, 101.0, 101.2, 100.8, 100.4, 101.8 and 103.6s. Flat,
which is the property that matters for serving. Text encoding drops from 17.6s on
the first clip to about 9s afterwards, as the memory-mapped encoder weights stay in
the host page cache.

**Tensor parallelism**, preview tier at 896x512, 20 steps, four ranks: pure Ulysses
124.5s; `--tp-size 2 --ulysses-degree 2` 205.9s; `--tp-size 4` 608.1s, each using
more memory per rank than the last. Neither DiT has a column- or row-parallel layer,
so `--tp-size` shards no weights and only takes ranks away from Ulysses — those
ranks stop sharding the sequence and duplicate full-length work. Rejected at startup
rather than left for a user to discover.

**Sequence length.** The refiner's packed sequence is `video + audio + text +
reference`, so its length follows the prompt, and its `flex_attention` mask is
compiled per length with each graph retained. Six clips at 4 preview steps, where
the first three share a prompt length:

- rounding the sequence to a bucket: 100.8, 98.0, 99.4, 103.0, 102.3, 102.2s
- using each length verbatim: 102.6, 100.8, 102.0, 174.1, 215.5s, then out of memory

Two changes keep the graph count bounded. `Magi2RefinerDiT` rounds the sequence up
to a multiple of 1024 rows before sharding, collapsing the whole 0-7000-token prompt
range to eight lengths at under 0.4% padding. And `build_mask_mod` carries the
valid-row length as a tensor rather than an int, since dynamo guards a captured int
by value and would recompile per prompt length even at a fixed shape. `dynamic=True`
is not an alternative; it costs 26s per clip.

## Benchmark

Same box, same weights, same seed 42, same 1920x1088 two-stage tier at 100 preview +
5 refiner steps, 4 ranks on each side. This PR runs `--enable-torch-compile
--regional-compile`. Nine clips per side, discarding each process's first clip while
its graphs are still building.

One clip is 249 frames at 25 fps — just under 10 seconds of 1920x1088 video with its
synchronized stereo audio, generated together in one denoising trajectory. 10 seconds
is the only duration the model was trained for, so the figures below do not scale with
a requested length. Weight loading is separate and paid once per process, about 5
minutes for both DiTs.

| | reference | this PR |
| --- | ---: | ---: |
| preview denoise (100 steps) | 277.7s | 286.6s |
| refiner denoise (5 steps) | 46.1s | 41.9s |
| decode (video and audio) | 8.9s | 7.8s |
| **one clip, end to end** | **344.9s** | **349.3s** |

**At 4 ranks this PR is 1.3% slower** — 4.4s on a 345s clip, which is larger than the
spread between runs. The refiner and the decode are faster; preview denoise is 8.9s
slower and is where the difference sits. Stage times do not sum to the end-to-end row
on either side, because the two implementations synchronize at different points, so the
end-to-end row is the one to compare.

### Across topologies

Same clip, same seed, each column at that rank count's best configuration. Two steady
clips per arm on one 8-GPU box, so this is a narrower measurement than the nine-clip
table above; the 4-rank column reproduces its 349.3s within the noise floor, which is
what makes the columns comparable:

| | 2 ranks | 4 ranks | 8 ranks |
| --- | ---: | ---: | ---: |
| `ep_size` | 2 | 4 (default) | 4 |
| compile | regional | regional | **none** |
| offload | layerwise | none | none |
| preview denoise (100 steps) | 590.4s | 286.9s | 183.9s |
| refiner denoise (5 steps) | 79.4s | 41.3s | 31.6s |
| decode (video and audio) | 7.1s | 8.8s | 12.2s |
| **one clip, end to end** | **689.0s** | **348.2s** | **253.5s** |
| peak memory | 132208 MiB | 85274 MiB | 126572 MiB |
| GPU-seconds per clip | 1378 | 1393 | 2028 |

8 ranks is 1.37x faster per clip and spends 46% more GPU-time to get there, so it buys
latency rather than throughput, and two concurrent 4-rank deployments beat one 8-rank
deployment on total output. 2 and 4 ranks cost the same GPU-seconds, so the 2-rank arm
trades latency for hardware at no efficiency loss. Decode moves the wrong way with rank
count, so every latency gain comes from denoise.

The 8-rank arm runs eager deliberately: compiled, its preview pass measures 335.4s
against 183.9s, which is the only configuration in this PR where `--regional-compile`
is a loss. 1 rank passes validation but runs out of memory while loading the preview
DiT. The reference was not re-run at 8 ranks, so none of these are head-to-head; its
published 8-rank timings use head padding and a different step budget.
