# [Perf] deepseek-v4.1: Default PD to MegaAttention, with the KV layout in the PD handshake

[Upstream PR](https://github.com/sgl-project/sglang/pull/45075) · state: closed · merged: True

## Original PR description

- `_default_dsv4_attention_backend` no longer falls back to FlashMLA under PD, so both roles pick MegaAttention (`flashmla_mega`) on SM100/SM103, as a single server does.
- MegaAttention and FlashMLA store KV in different layouts (packed V4.1 vs V4 by default), and the PD handshake compared only `kv_cache_dtype`, so a mismatched pair would transfer KV that the decode misreads. The prefill now registers its KV layout (`DeepSeekV4TokenToKVPool.pd_kv_layout`: the main layout plus each compression ratio's), the Python and Rust bootstrap servers relay it, and the decode raises `KV layout mismatch` next to the dtype check. Other pools report no layout and skip the check.
- The trtllm PD rejection no longer says the handshake lacks a layout; trtllm under PD stays rejected as untested (#37838).
- The DeepSeek-V4.1 cookbook's PD section states the default and that both roles must match.

Verified on two GB300 nodes (DEP2 prefill + DEP2 decode, DSpark, Mooncake) with no `--dsv4-attn-backend`: both roles resolve `flashmla_mega`, and GSM8K (1,319, greedy) scores 96.66%, the same as with `flashmla` on both roles. With only the decode on `flashmla`, its first request fails with `KV layout mismatch: prefill server has kv_layout=v41,c1:v41_fp4,c2:v41_fp4, but decode server has kv_layout=v4,c1:v4,c2:v4`.

Behavior change: DeepSeek-V4.1 PD on SM100/SM103 runs MegaAttention on both roles by default. A prefill on SM100/SM103 paired with a decode on another GPU now needs `--dsv4-attn-backend flashmla` on the prefill. An older decode cannot parse the new `kv_layout` field, so upgrade both roles together.
