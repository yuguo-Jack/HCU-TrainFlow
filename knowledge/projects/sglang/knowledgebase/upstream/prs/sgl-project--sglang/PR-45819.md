# [Fix] speculative: Accept draft probabilities that round just above 1 in chain verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/45819) · state: open · merged: False

## Original PR description

## Motivation
`chain_speculative_sampling_triton` rejects any draft whose q is above 1.0, but fp32 softmax can return the top token of a peaked row as 1.0 plus a few ulp, so those drafts are always rejected and acceptance drops at temperature > 0. On an L4 (sm89, torch 2.14.1+cu130, Triton 3.8.0) the issue's synthetic chain gives num_accept 3 at q=1.0 and 0 at q=1+2**-23, 1+8e-6 and 1+4e-5 on main. Fixes #42568

#45517 reports the same overshoot from DSpark's FlashInfer softmax. #45518 clamps that output at the source; this PR fixes the guard in the verify kernel, which DSpark, EAGLE and UNO all call.

## Modifications
Accept q up to `1 + 1e-3` and clamp it to 1.0 in the token and block acceptance tests and in both residual passes; 0, negatives, NaN, +-inf and q > 1.001 are still rejected. The margin is over 100x the largest measured fp32 overshoot (8e-6) and still admits one fp16 ulp above 1 (2**-10), while 1.01, 2.0 and inf stay rejected.

## Accuracy Tests
`test/registered/kernels/ops/speculative/test_block_verification.py`, block_verification False and True: rounded q is accepted like q=1.0, the residual excludes the rounded draft token, invalid q is still rejected. On an L4 the four rounded-q cases fail on main and all 31 cases pass with the fix, under pytest and as a script. Greedy paths do not run this kernel.

## Speed Tests and Profiling
Not applicable; one extra `tl.minimum` per loaded q.

We ran this PR on four NVIDIA architectures, plus one real-serving check. Sharing in case it helps review.

The image was `lmsysorg/sglang:nightly-dev-20261103-797af717` (torch 2.14.1+cu130). For the "main" column, only `reject_sampling.py` was swapped back to main's version; the test file stayed the same.

| GPU | this PR | main kernel |
|---|---|---|
| H100 80GB (SM90) | 31 passed | 27 passed, 4 failed |
| RTX PRO 6000 Blackwell (SM120) | 31 passed | 27 passed, 4 failed |
| GB200 (SM100) | 31 passed | 27 passed, 4 failed |

On main, exactly the four new cases fail: `test_accepts_draft_probability_rounded_above_one[False/True]` and `test_residual_excludes_draft_rounded_above_one[False/True]`. That matches your L4 result.

**Real serving.** We wanted to know how often q > 1 shows up in a real deployment, so we served Qwen3.8-Flash-Next NVFP4 (public `RadixArk/Qwen3.8-Flash-Next-NVFP4`) on 2× RTX PRO 6000, TP2:

```
--tp 2 --moe-runner-backend flashinfer_cutlass --speculative-algorithm NEXTN \
--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 \
--speculative-use-rejection-sampling
```

The workload was 64 prompts × 512 tokens, 16 concurrent, with a fixed `sampling_seed` per request. A test-only hook read `draft_probs` at the proposed tokens just before `chain_speculative_sampling_triton`.

| | main | this PR |
|---|---:|---:|
| proposed draft tokens counted | 85,137 | 84,546 |
| q == 1.0 exactly | 14,620 (17%) | 15,215 (18%) |
| q > 1.0 | 0 | 0 |
| accept length, T=0.6 / 1.0 / 0.6 | 2.99 / 2.91 / 3.01 | 3.03 / 2.89 / 3.00 |

So the NEXTN draft path on this model never overshoots 1.0. About one proposal in six sits exactly at 1.0, which is right at the old boundary. As expected, the PR changes nothing there: acceptance is the same within noise. The benefit is for producers whose q does overshoot, like the DSpark FlashInfer softmax in #45517. The guard looks safe to us: values of q at or below 1 behave identically, and 1.01, 2, inf and NaN are still rejected.
