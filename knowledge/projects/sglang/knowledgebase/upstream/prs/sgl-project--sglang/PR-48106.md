# [Feat] mem_cache: Elastic hybrid-SWA KV pools (kvcached VMM), with an Intel XPU path

[Upstream PR](https://github.com/sgl-project/sglang/pull/48106) · state: open · merged: False

## Original PR description

[Feat] mem_cache: Elastic hybrid-SWA KV pools (kvcached VMM), with an Intel XPU path

## Motivation

This PR ports sgl-project/sglang#13581 onto current main and adds an Intel XPU backend.

With `SGLANG_ENABLE_ELASTIC_MEM_POOL=1`, the full-attention and sliding-window
(SWA) KV pools of a hybrid-SWA model no longer have fixed sizes. Each pool reserves
a large virtual range and backs only its current size with physical pages. The
two pools trade pages at runtime: when one pool runs hot and the other runs cold,
the cold pool's tail is drained and unmapped, and the freed memory is mapped into
the hot pool. Total device memory stays the same; only the split between the pools changes.

On gpt-oss-20b on an Intel Arc Pro B60, elastic memory raised throughput by
18-24% and cut mean TTFT by 13-22% across three workloads, using the same device
memory.

### How it works

- **`ElasticMempoolOrchestrator`** (`mem_cache/elastic/elasticmem_orchestrator.py`)
  picks the hottest and coldest pool by token usage. It resizes when all three hold:
  - the usage gap is at least `SGLANG_ELASTIC_MEM_RESIZE_TRIGGER_DIFF_RATIO` (0.2);
  - the hot pool is above `SGLANG_ELASTIC_MEM_MAP_THRESHOLD` (0.9);
  - the cold pool is below `SGLANG_ELASTIC_MEM_UNMAP_THRESHOLD` (0.8).
- **`ElasticTokenToKVPoolAllocator`** (`mem_cache/elastic/elastic_allocator.py`)
  marks the cold pool's tail as a shrink candidate and withholds its free slots.
  - The shrink happens once every in-use tail slot can be evicted from the radix
    tree. Until then it waits, or it is cancelled if the pools even out.
  - The withheld slots still count as available, so admission is unchanged.
- **`ElasticSWATokenToKVPoolAllocator`** owns the orchestrator and both
  sub-allocators. After each resize it re-syncs the `SWAKVPool` sizes and the
  full-to-SWA index mapping.
- **Pools:** `ElasticMHATokenToKVPool` on CUDA (kvcached `ETensor`), and
  `ElasticXPUMHATokenToKVPool` on XPU (kvcached `vmm_ops`, see below).
- **Scheduler:** `maybe_init_elastic_mem` attaches the allocator to the tree
  cache, and `try_resize` runs after each scheduled batch.
- **`UnifiedTreeCore.component_evictable_device_indices`** reports which slots
  can be evicted, so a tail is shrunk only when it can be drained.

### Changes from #13581

- **Device sync before unmap:** unmap is not ordered with the stream. With
  overlap scheduling, the forward still in flight can read slots that were
  just freed or evicted. The allocator therefore synchronizes the device before it
  unmaps. The cost is one wait per shrink.
- **Shrink floors:** each pool stops shrinking at a floor that keeps a
  max-length request schedulable. This keeps the scheduler's startup capacities
  and request-length limits valid:
  - the full pool keeps at least `max_req_len`;
  - the SWA pool keeps at least the sliding window plus one prefill chunk, or
    `max_req_len` when chunked prefill is off;
  - neither floor goes above the pool's startup size.
- **Leftover pages:** pages too few for the hot pool to use go back to the
  cold pool instead of staying unmapped.
- **Cheaper drain checks:** while a shrink is pending, the full-tree walk
  behind `component_evictable_device_indices` runs again only after the number of
  in-use tail slots or the evictable total changes.
- **Shutdown handling:** kvcached shuts down at exit, and before a terminating
  signal whose handler is still the default. Signals that are ignored or have a
  Python handler are left alone, so an ignored signal no longer shuts kvcached
  down while the process keeps running.
- **Tree core default:** main defaults `SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND`
  to rust, and only the Python core has `component_evictable_device_indices`.
  When the variable is unset, elastic memory picks python, as
  `--enable-kv-cache-sharding` does. An explicit non-python choice is refused.
- **Startup validation** refuses:
  - devices other than CUDA and XPU;
  - `--page-size > 1`, unified memory, the page-major layout, the memory saver and speculative decoding;
  - PD disaggregation and `--enable-hierarchical-cache` (both register KV buffers by row count once, and a resize changes the row count);
  - mxfp8/fp4 KV, `SGLANG_USE_HND_KVCACHE`, and pure-SWA models.
- **Env vars** are renamed to `SGLANG_ENABLE_ELASTIC_MEM_POOL` and
  `SGLANG_ELASTIC_MEM_*`.

### XPU pool

- **kvcached backend:** uses `kvcached.vmm_ops` with kvcached's Level Zero
  backend (ovg-project/kvcached#501):
  - `init_kvcached` runs once per process;
  - `create_kv_tensors` creates one allocator group per pool;
  - `map_to_kv_tensors` / `unmap_from_kv_tensors` work by page offset. One offset
    covers that page of K and of V in every layer.
- **No zero page:** Level Zero has no shared zero page, so every row the pool
  exposes is mapped before first use. After each resize, the K/V views and
  `_kv_buffer_descs` are re-sliced to exactly `size + page_size` rows. The data
  pointers stay the same.
- **Virtual range:** sized from total device memory. Physical memory only moves
  between the two pools.
- **Page size 1:** `intel_xpu` serves `--page-size 1` through sgl-kernel-xpu's
  gather fallback (sgl-kernel-xpu#454), which is slower than its paged kernel.
  `--attention-backend triton` works where that build is missing, or where its
  non-paged path rejects attention sinks (gpt-oss).
- **XPU startup checks:** kvcached must be installed, and kvcached's own SGLang
  autopatch (`ENABLE_KVCACHED` / `KVCACHED_AUTOPATCH`) must be off.

### Static splits vs elastic

This follows the layout of #13581: two static splits, plus elastic memory
started from the worse of the two. Each config runs on its own B60, with the gpt-oss
workload from `scripts/emem/dev.sh`: 512 prompts, 8192 in / 1024 out,
`--random-range-ratio 0.5`, concurrency 128.

| Config | Full / SWA tokens at start | Duration | Total throughput (tok/s) | Mean TTFT | Mean running requests |
|---|---|---|---|---|---|
| static, `--swa-full-tokens-ratio 0.6` | 65,632 / 39,379 | 2879 s | 1227 | 586 s | 8.4 |
| static, `--swa-full-tokens-ratio 1.0` | 52,505 / 52,505 | 3263 s | 1082 | 672 s | 6.6 |

Two B60s, `--tp 2`, same flags otherwise. Each pool starts at 379,045 tokens.

- **512 × 16384/1024, concurrency 256:** all requests succeeded at 2,567 tok/s total.
- **Two resizes:**

  | Time | Full | SWA |
  |---|---|---|
  | 20:51 | 565,247 | 196,607 |
  | 21:25 | 655,359 | 106,495 |

  Both ranks logged the same sizes within a second of each other. Each resize
  took 370-574 ms. They moved 182,438 and 90,112 tokens, against 25,318 for

- **Same speed as static TP=2 at 8192 input:** elastic ran at 2,999 tok/s and
  static at 3,059 tok/s (128 × 8192/1024). Elastic memory did not resize there.

  With torch 2.14.0+xpu, Inductor's static Triton launcher segfaults on the first
  TP=2 request, with or without elastic memory.

### Soak

One elastic server ran for 2 hours. It alternated 128 × 8192/1024 (concurrency
128) and 256 × 1024/1024 (concurrency 256) for 8 rounds, 3,072 requests in all.

- **No failures:** every request succeeded, with no leak-check failures,
  scheduler exceptions or device faults.
- **Two resizes, both early:** the pools resized twice in the first 6 minutes
  and ended at full 86,015 / SWA 20,479 tokens. 467 of 469 planned shrinks were
  cancelled.
- **Flat device memory:** `xpu-smi` showed 18.13-18.16 GiB for the server from
  the second resize to the end.
- **Same output:** the fixed prompts after the soak matched the ones from before
  any resize.

## Unit tests

`test/registered/unit/mem_cache/test_elastic_allocator.py` has 8 CPU tests (`base-a-test-cpu`):

- **Bookkeeping:** the shrink, borrow and cancel cases check that no slot is lost or handed out twice.
- **Regression cases:** the device sync before unmap, both shrink floors, the
  skipped tree walk, returning leftover pages, and the signal handling. These
  cases fail on the code before the fixes.

The kvcached-backed pools need kvcached and a GPU, so CI doesn't exercise them.

## Limitations

- **Scope:** hybrid-SWA models with both full-attention and SWA layers, at
  `--page-size 1`, MHA/GQA with the NHD layout. MLA, PD disaggregation, HiCache
  and speculative decoding are not supported. Models that are not hybrid-SWA log
  a warning and run normally.
- **Tree core:** requires the Python `UnifiedTreeCore`.
- **intel_xpu with gpt-oss:** sgl-kernel-xpu builds whose non-paged kernels
  reject attention sinks fail on gpt-oss with `intel_xpu --page-size 1`. The
  results above use `triton`.
- **Resize rate:** in the A/B run above, 113 of 114 planned SWA shrinks were
  cancelled while waiting for the tail to drain, because the usage gap fell back
  under the trigger. The trigger ratio and thresholds are tunable; they were left
  at their defaults here.
- **Short requests don't trigger it:** with #13581's 1024/1024 workload
  (1,024 prompts, concurrency 128) on one card, elastic memory never resized:
  - **Mixed lengths:** the full pool peaked at 83%, below the 90% map threshold.
  - **Equal lengths:** the full pool reached 100%, but all 27 planned SWA shrinks
    were cancelled. Requests finish together, so the SWA tail drains only when
    the full pool empties too.
- **One direction only:** every resize in these runs grew the full pool. In the
  soak, SWA usage reached 99% after its pool shrank, but it never ran 20 points
  above full usage, so no pages moved back to SWA.
