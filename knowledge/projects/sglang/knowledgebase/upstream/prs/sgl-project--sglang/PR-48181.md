# [Fix] rust-server: Parse JSON tool calls for named and required choices

[Upstream PR](https://github.com/sgl-project/sglang/pull/48181) · state: open · merged: False

## Original PR description

## Motivation

On the Rust server, non-streamed requests with a named or `required` `tool_choice` return no `tool_calls` when the parser is `pythonic`, `glm47`, `minimax-m3` or `gemma4`. The calls stay in `content` as a JSON array, with finish reason `stop`.

This affects `SGLANG_RUST_SERVER=1` (off by default) deployments running GLM-4.7-Flash with its cookbook flags or `pythonic`, which `docs/docs/advanced_features/tool_parser.mdx` documents for Llama-3.2-1B and the Llama 4 cookbook recommends for tool calling.

On main, 0 of 40 Llama-3.2-1B `pythonic` requests and 0 of 3 GLM-4.7-Flash requests returned calls per choice. With this diff, 40 of 40 and 3 of 3 did, with finish reason `tool_calls` and no `content`. Rust streaming and the Python server with `pythonic` return `tool_calls`.

With no structural tag, `tool_constraint` gives these choices a JSON schema, and the non-streaming path passes that JSON only to the parser, which does not read it.

Neither #47622 (Python server, no parser) nor draft #46521 (Rust API migration) fixes this path, but #46521 conflicts in `chat.rs` and `tools.rs` on a trial merge.

## Modifications

When that schema applies, the non-streaming path reads the bare JSON first, as Dynamo's streaming jail does. If this finds no call, the tool-call parser runs as on main. Other requests do not change.

`llama3` and `mistral` already read bare JSON. On a server, I found one change: a forced string argument with `<|python_tag|>` or `[TOOL_CALLS]` now returns calls.


| --- | --- | ---: | ---: |

| Llama-3.2-1B, `pythonic`, named and required | Streamed | 40 of 40 each | 40 of 40 each |
| Llama-3.2-1B, `glm47`, `minimax-m3`, `gemma4`, named and required (parsing path only, because the schema decides the output shape) | Non-streamed | 0 of 3 each | 3 of 3 each |
| Llama-3.2-1B, `llama3`, named, plain and strict tools | Non-streamed | 40 of 40 each | 40 of 40 each |
| Llama-3.2-1B, `llama3`, named | Streamed | 40 of 40 | 40 of 40 |
| Llama-3.2-1B, `mistral`, named and required (parsing path only) | Non-streamed | 3 of 3 each | 3 of 3 each |
| Llama-3.2-1B, `llama3`, `mistral`, named and required, schema enum forces a string with the markers, `parallel_tool_calls=false` | Non-streamed | 0 of 3 each | 3 of 3 each, exact arguments |
| Llama-3.2-1B, `llama3`, `mistral`, same string, named | Streamed | 3 of 3 each | 3 of 3 each |
| GLM-4.7-Flash, `--attention-backend triton --tool-call-parser glm47 --reasoning-parser glm45` (cookbook flags), named and required | Non-streamed | 0 of 3 each | 3 of 3 each |
| Qwen3-4B, `--tool-call-parser pythonic --reasoning-parser qwen3` (the cookbook parser is `qwen25`), named and required | Non-streamed | 0 of 3 each | 3 of 3 each |
| GLM-4.7-Flash and Qwen3-4B, same flags, named and required | Streamed | 3 of 3 each | 3 of 3 each |

No named request in these rows returned another tool.

The new test fails on the Rust class on main with `No tool_calls: '[{"name": "get_tourist_attractions", ...` and passes with this diff. `test_openai_function_calling.py` found no regression on a B200. `pre-commit` on a merge with `99fd01047d` found no issue in the changed files, with clippy on Linux.

As on main, output cut by max tokens with `[f(a=1)]` or `<tool_call>` in a string can return another tool on `pythonic` and `glm47`.

Not run: MiniMax-M3 weights, Llama 4, AMD, NPU, more than one GPU, and runtime CI. `unsloth/gemma-4-E2B-it` does not start (`no Rust MM pipeline for model_type='gemma4'`).
