# [Perf] qsa: drop the per-layer RoPE cache length check in the indexer

[Upstream PR](https://github.com/sgl-project/sglang/pull/48271) · state: open · merged: False

## Original PR description

## Motivation

`QSAIndexer` checked the RoPE cos/sin cache length before every index-Q RoPE (fused and eager Q prep) and every compressed-K RoPE: `self.rotary_emb._ensure_cos_sin_cache_length(int(positions.max().item()))`. The `.item()` is a device-to-host synchronization, once per QSA layer, whenever the indexer runs outside a captured CUDA graph.

The check never does anything useful:
- `ModelRunner` reserves every RoPE cache at load time (`reserve_rope_cache_for_long_sequences`) for the context length plus the speculative expansion plus `SGLANG_ROPE_CACHE_SAFETY_MARGIN`.
- In each Qwen4-Exp QSA layer, the attention RoPE (`_prepare_qkv_gate`) consumes the same `cos_sin_cache` with the same positions before the indexer runs, without any length check.
- The CP prefill path already skipped the check for this reason (`ensure_cos_sin_cache=False`).

Related: #37793 (open) also targets this sync, by growing the cache to the context length once, as part of a larger Qwen4 CPU-offload change. This PR is the minimal standalone version and follows the reasoning already used for the CP path.

## Modifications

- `qsa_indexer.py`: remove the cache-length check from `project_qk` (fused path) and `apply_rope`, and remove the now-unused `ensure_cos_sin_cache` parameter and its CP-path argument. Only `QSAIndexer` itself passed this keyword (its CP prefill path, with `False`), so it is removed rather than kept as a no-op.
- `test_qsa_cp_unit.py`: updated to the new contract. The CP test no longer asserts on the removed keyword. `test_qsa_apply_rope_cache_sizing_is_optional[False|True]` becomes `test_qsa_apply_rope_does_not_size_rope_cache`, which asserts that `apply_rope` never sizes the RoPE cache.
- `test_qsa_indexer.py`: `test_rope_does_not_sync_host` runs fused Q prep, eager Q prep and compressed-K RoPE under `torch.cuda.set_sync_debug_mode("error")`. It fails on main ("called a synchronizing CUDA operation" at `qsa_indexer.py:195`) and passes with this PR.

## Accuracy Tests

Outputs are unchanged: the removed code only grew the cache when positions exceeded the load-time reservation, which the attention in the same layer already relies on.

- Kernel tests (RTX PRO 6000 Blackwell, SM120): `test_qsa_indexer.py` 39 passed (incl. the new test); `test_qsa.py` 300 passed, 1 skipped.
- End-to-end exactness, `nvidia/Qwen3.8-Flash-Next-NVFP4`, 1x GB300, `--enable-deterministic-inference`, NEXTN MTP (3 steps, 4 draft tokens), greedy, main vs this PR in one container on the same GPU: 4 text prompts (incl. a ~6K-word prompt spanning several prefill chunks) and 4 image chats, each sent twice. Output tokens are **identical** to main on all 8 requests, and both arms are repeat-identical.

## Speed Tests and Profiling

The change removes one device-to-host sync per QSA layer whenever the indexer runs outside a captured graph; `test_rope_does_not_sync_host` checks this.

Same-GPU serving A/B on 1x GB300, in one container on one node: main and this PR swap the changed file over the same tree; order main, this PR, main, this PR.
- Model: `nvidia/Qwen3.8-Flash-Next-NVFP4`, TP1, `--mem-fraction-static 0.80 --mamba-ssm-dtype bfloat16 --chunked-prefill-size 8192`, NEXTN MTP (3 steps, topk 1, 4 draft tokens), default (non-deterministic) mode.
- Bench: `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random-ids --random-input-len 2048 --random-output-len 256 --random-range-ratio 1.0 --num-prompts 192 --max-concurrency 48 --seed 1 --warmup-requests 8`.
- 4 rounds per launch; round 0 is dropped as warm-up (JIT/autotune). Values are the median over the 6 remaining rounds (2 launches × 3).

| Arm | Output tok/s (median, 6 rounds) | Range | Median TPOT ms (median) | Accept length |
|---|---|---|---|---|
| main | 2521 | 2365-2615 | 16.55 | 2.47-2.51 |
| this PR | 2529 (+0.3 %) | 2396-2604 | 16.80 | 2.48-2.52 |

The difference is within the run-to-run spread (about ±4 %), so there is no measurable end-to-end change at this concurrency and input length.

At this measured point (default CUDA graphs, concurrency 48, 2K input) the removed syncs are not visible end to end.
