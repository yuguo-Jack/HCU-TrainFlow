# [AMD] [GLM-5.3-Flash] Restore two HIP fallbacks: clamped-SwiGLU Triton MoE and the fused mHC boundary

[Upstream PR](https://github.com/sgl-project/sglang/pull/41136) · state: open · merged: False

## Original PR description

## Motivation

Two HIP paths on `main` route to kernels that cannot run there. Both were found by the GLM-5.3-Flash ROCm nightly on gfx942, and both are independent of the model: any clamped-SwiGLU MoE model, and any mHC model, hits them on a HIP arch without the gfx95 kernels.

**1. Triton fused MoE with a SwiGLU clamp.** A model with `swiglu_limit` set (DeepSeek V4, GLM-5.3-Flash) served on the Triton MoE runner with every expert local (TP only, no EP) crashes on its first MoE forward:

```
AssertionError: fused silu_and_mul_clamp kernel is CUDA/XPU only; HIP must disable SWIGLU_CLAMP_FUSION
```

The fused `silu_and_mul_clamp` kernel exists only for CUDA and XPU, and `SGLANG_OPT_SWIGLU_CLAMP_FUSION`, the switch the message tells you to disable, no longer exists on `main`. So there is no way around it short of changing the parallel layout. The expert-filtered (EP) path is not affected, because `act_and_mul_triton` applies the limit itself.

Reproduced on `main` in [run 35941115240](https://github.com/sgl-project/sglang/actions/runs/35941115240) (TP8, `--moe-runner-backend triton`): all eight ranks on both MI300X (gfx942) and MI355X (gfx950) hit the assertion on the first forward, before any output.

**2. The fused mHC post/pre boundary.** On gfx942, decode CUDA graph capture dies on all eight ranks:

```
tvm.error.InternalError: Unresolved call Op(tl.get_lane_idx)
Exception: Capture cuda graph failed: Unresolved call Op(tl.get_lane_idx)
```

`mhc_fused_post_pre_fma_tilelang` uses `T.get_lane_idx()`, which TileLang's HIP codegen (`CodeGenTileLangHIP`) cannot lower. It is the small-batch kernel, chosen at 32 tokens or fewer, so every decode capture size reaches it.

`apply_mhc_post_pre_boundary` is designed to degrade here: it tries the aiter kernel, then the Triton kernel, and otherwise returns `None` so the caller runs the unfused `hc_post` + `hc_pre` sequence. But the gate in between, `_is_fused_mhc_post_pre_enabled()`, reads `SGLANG_OPT_USE_TILELANG_MHC_PRE` and `SGLANG_OPT_USE_TILELANG_MHC_POST` directly, while mhc.py's own `_use_tilelang_mhc_pre()` / `_use_tilelang_mhc_post()` add `and not is_hip()`. Those flags default on, so the gate said yes on HIP. gfx942 has neither the aiter kernel (gfx95 only) nor the Triton kernel (gfx95 and gfx1250 only), so it fell through to TileLang instead of to the unfused path.

Reproduced on `main` in [run 36079282524](https://github.com/sgl-project/sglang/actions/runs/36079282524) (job [107897366464](https://github.com/sgl-project/sglang/actions/runs/36079282524/job/107897366464), gfx942, TP8 + EP8), after a successful 3606 s weight load and prefill graph setup.

## Modifications

- `fused_moe.py`: in the `swiglu_limit` branch of `_fused_moe_kernel_sequence`, HIP now clamps the gate/up halves in place, then runs the regular HIP `silu_and_mul`. The gate is clamped from above and up is clamped to ±limit, in that order before SiLU. That is the contract of the CUDA fused kernel and of the model's own `swiglu_clamped`. The now-unreachable HIP hint is dropped from the CUDA/XPU assertion message.
- `deepseek_v4_fused_mhc.py`: `_is_fused_mhc_post_pre_enabled()` returns `False` on HIP, placed after the gfx1250 early return so gfx1250 keeps routing through its Triton kernel. gfx95 is unaffected — it keeps cross-layer fusion through `_is_aiter_gfx95_mhc_available()` in `_is_production_mhc_enabled()`. Other HIP archs now leave `hc_ffn_post_pre` unwired and run the unfused sequence, which already falls back to torch on HIP.
- Tests: a CPU unit test for the SwiGLU clamp contract and its equivalence with the reference SwiGLU, plus three cases added to the existing registered mHC gating test — the HIP guard, cross-layer fusion staying off when no HIP fused kernel exists, and gfx1250 keeping its opt-in ahead of the guard. The two HIP cases fail against `main` and pass with this change.

The first fix is the HIP branch from [#36607](https://github.com/sgl-project/sglang/pull/36607), carried on the GLM-5.3-Flash support branch. That branch was never merged into `main` as-is (the AMD work was re-landed piecemeal as the Day-0 PRs) and this piece was not among the re-landed parts. The second is not from #36607; the fused mHC boundary postdates it.

## Accuracy Tests

gfx942 now scores on `main` with these fixes: full-split GSM8K **0.9750 (1286/1319)** at TP8 + EP8 on the rocm10 image, with a 2769 s weight load and a 1391 s eval ([run 36232707853](https://github.com/sgl-project/sglang/actions/runs/36232707853)). That is bit-identical to the gfx950 score on the same eval, and it exercises the unfused torch mHC path this PR routes gfx942 to, so the mHC guard is not just a crash fix: the fallback it selects is numerically sound.

Localized first with three 64-question evals run back to back on one server image ([run 36119287477](https://github.com/sgl-project/sglang/actions/runs/36119287477)), where the AITER MoE configuration scored 63/64 at 151 generated tokens per sequence.

The same job also isolates a separate, unfixed bug that is not addressed here. With the Triton MoE runner, gfx942 generates without ever stopping: 0/64 with the default fused sgl-kernel DSA top-k, and 0/64 again with #36607's portable Torch top-k, both running every sequence to the 2048-token cap. The DSA top-k backend makes no difference, so the fault is in the Triton MoE runner on this arch. The GLM-5.3-Flash MI300X nightly in #36903 therefore uses the AITER runner.

For reference, the same clamp code on the support branch scored full-split GSM8K 0.970–0.971 at TP8 with Triton MoE on both MI300X and MI355X, on the rocm720 and rocm724 images ([33205323261](https://github.com/sgl-project/sglang/actions/runs/33205323261), [33205583516](https://github.com/sgl-project/sglang/actions/runs/33205583516), [33216905696](https://github.com/sgl-project/sglang/actions/runs/33216905696), [33216911068](https://github.com/sgl-project/sglang/actions/runs/33216911068)). gfx950 on current `main`, which takes the aiter mHC path and so never reaches either bug, scores 0.9750 (1286/1319) — [run 36011039824](https://github.com/sgl-project/sglang/actions/runs/36011039824).

Both unit tests pass locally on CPU.

## Speed Tests and Profiling

Not measured; both changes only affect configurations that previously could not run.

The clamp adds two in-place elementwise clamps on the first GEMM's output, on HIP only, in the one configuration that crashed. Dropping the fused mHC boundary on non-gfx95 HIP costs the fusion that the TileLang kernel would have provided had it compiled, which on these archs it never did.
