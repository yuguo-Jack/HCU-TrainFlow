# [Fix] HiCache: whole-page Mooncake IO for mamba pools with PLE slot side states (L3 hit rate stuck at 0)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46761) · state: open · merged: False

## Original PR description

## Fixtures

Fixes #46760

## Problem

For GDN hybrid models with PLE layers (e.g. qwen3.8-flash, config `ple_layer_ids` non-empty), the mamba host pool registers slot side states, which makes `MambaPoolHost.slot_state_device_tensors` non-empty. `MambaPoolHost.get_page_buffer_meta` raises `NotImplementedError` for such pools (zero-copy page metadata cannot describe the side states), while the Mooncake storage backend v2 path is zero-copy only.

Result in production (verified with a real cluster under traffic replay):

- Every HiCache L3 backup containing a MAMBA transfer fails: `HiCache backup failed after 0 tokens` (traceback in the issue).
- No mamba objects are ever written to the Mooncake store (6.8M exist probes, 0 fetched items).
- The hybrid hit policy requires all pools' objects to be present, so **L3 hit rate is structurally 0** even though KV objects are written and read correctly.

The same failure exists on current `main` (`get_page_buffer_meta` still raises for pools with slot side states, and `MooncakeStore._batch_io_v2` is still zero-copy only).

## Fix

Add a whole-page I/O fallback to `MooncakeStore`, used only for mamba pools with registered slot side states. All other pools (KV/MLA/MHA/draft/mamba-without-side-states) keep the byte-identical zero-copy path.

- `_get_hybrid_page_component_keys`: mamba pools with side states get a single `_{rank}_wholepage` suffix (key multiplier 1), so write, hit detection (`batch_exists_v2`) and the TRAILING_PAGES policy all derive the same key. The suffix cannot collide with any other pool's keys.
- `_batch_io_v2`: transfers are partitioned by `_needs_wholepage_io` (presence of `slot_state_device_tensors`); the zero-copy body is unchanged and skipped entirely when empty.
- New `_wholepage_io_v2`: materializes the full page payload (temporal + conv + side states) via the existing `get_data_page(flat=True)` / `set_from_flat_data_page` APIs into a persistent pinned staging buffer (default cap 256 MB, env `SGLANG_HICACHE_MOONCAKE_WHOLEPAGE_STAGING_MB`), chunked by the cap, and reuses the existing zero-copy batch put/get RPC plumbing on interior pointers into the registered staging buffer.
- Existing pages are treated as success on set (idempotent), missing pages on get are reported through the standard `_batch_postprocess` failure counts.

This mirrors the generic base-class fallback path (`hicache_storage.py`) and the hf3fs/seaweedfs backends, which already materialize whole pages.

## Results

Validated in production (10-worker Mooncake cluster, sglang serving, traffic replay):

- Before: `HiCache backup failed after 0 tokens` on every mamba backup; L3 prefetch/hits = 0.
- After: no backup failures; mamba whole-page objects written and read; L3 hits restored to ~13M-20M prefetched tokens per worker; no new master-side put/get failures.

## Testing

- New self-contained unit test `test_wholepage_mamba_v2` in `python/sglang/srt/mem_cache/storage/mooncake_store/test_mooncake_store.py`: mock mamba pool with slot side states + fake store client; verifies set/exists/get roundtrip with byte-identical side states, key layout, group ids, dedup of existing pages, multi-chunk staging growth/retirement, and that zero-copy pools still route through `get_page_buffer_meta`.
- Pools without side states are unaffected (same RPCs, same keys) - covered by the existing zero-copy assertions in the test.

## Notes

- `MooncakeDirectLinker` (PD layer-wise transfer) has the same underlying gap for these pools and is out of scope for this PR.
- The Nixl backend has the same gap; flagged for follow-up.
