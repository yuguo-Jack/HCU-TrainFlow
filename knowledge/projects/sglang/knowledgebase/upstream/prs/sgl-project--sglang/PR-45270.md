# [Perf] spec: Recover DSPARK acceptance on periodic outputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/45270) · state: closed · merged: False

## Original PR description

> Scope correction: this draft only accelerates an existing repeated output. It does not fix blank or repeating model outputs; output correctness remains under investigation.

## Motivation

Greedy DSPARK can keep proposing the wrong first token on an established periodic output, rejecting all drafts and committing only the target's bonus token. A fixed Inkling-Small-NVFP4 whitespace continuation reproduces this on main with 2,047 verifies for 2,048 output tokens.

## Changes

After at least 32 verifies with no more than 0.25 correct drafts per verify, detect a strict period of up to eight tokens in the last 32 output tokens and propose its continuation. Compute the phase from the live device prefix length, because overlap scheduling can leave host output history behind. Bind activation to the request instance so a reused request ID cannot inherit it. Keep recovery active until the verified output breaks the cycle; every candidate still goes through ordinary target verification.

Enable this only for CUDA dense drafts with static verification, TP-only execution, greedy sampling, and no grammar or logit adjustments. Confidence collection, adaptive proposal diagnostics, and simulated acceptance retain the learned proposal. `SGLANG_OPT_DSPARK_REPETITION_FALLBACK=0` disables recovery.

## Validation

- 9 CPU draft/proposal tests, 63 kernel namespace tests, the CUDA graph-replay regression, and pre-commit pass.
- 4×B300, TP4, FA4 target/draft, full graphs; Inkling-Small-NVFP4 target revision `b6a99534467840620d411e4cd4ad5819b2610d9c`, DSpark draft revision `736501c3901cfc6bbb53ba382781eb0e5d9ad66a`. Torch 2.14.1+cu130, FlashInfer 0.7.1, Triton 3.8.0, CuTe DSL 4.8.0.
- Matched 2,048-token periodic continuation: identical output IDs, verifies 2,047 → 285, response accept length 1.0005 → 7.186. A single warm measured run took 14.38 s → 2.38 s. The 256-token case also preserves output IDs, with verifies 255 → 61.
- The 48-request control batch has 42/48 exact output matches in the ordinary numerical configuration. Its changed-output timing is not a matched-work speedup or a task-accuracy result.
- Deterministic FA4/full-graph/unified-cache checks with NaN poisoning and strict memory checks: 49 sequences / 100,352 generated tokens, then 49 real decode-cache hits / 25,088 continuation tokens. Both comparisons have zero mean/max k3 KL and zero maximum absolute generation/prefill logprob difference. These checks use Mamba track interval 128; the ordinary comparison above uses 256.
- The final request-isolation follow-up has a regression that fails before the fix and passes afterward. A fresh final-commit model run with eager prefill and batch-one decode graphs preserves the exact 256/2,048-token outputs and again uses 61/285 verifies. The full-graph numerical checks above cover the preceding proposal implementation; the follow-up changes activation ownership only. This change addresses proposal rejection on periodic continuations; it does not establish why the target entered that trajectory.
