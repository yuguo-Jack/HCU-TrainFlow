# [Fix] jit: Use the ninja package's binary when ninja is not on PATH

[Upstream PR](https://github.com/sgl-project/sglang/pull/47284) · state: open · merged: False

## Original PR description

## Motivation

SGLang depends on the `ninja` package (`python/pyproject.toml`), but the JIT build runs a bare `ninja` from PATH (`kernels/jit/utils/compile/ninja.py`). The package puts its binary in the environment's scripts directory, which is only on PATH after activation. Running an environment without activating it, for example `/opt/venv/bin/python -m sglang.launch_server` from a service or a container entrypoint, fails on the first JIT build with `FileNotFoundError: [Errno 2] No such file or directory: 'ninja'`.

The Docker images are not affected because they install `ninja-build`. The Rust extension build already covers the same case by putting the interpreter's directory on PATH (`srt/rust_extensions/torch_build.py`).

## Modifications

- `toolchain.ninja_path()`: `ninja` on PATH, else the binary in `ninja.BIN_DIR`, else a `RuntimeError` naming both places, in the same shape as `hgcc_path()`.
- `ninja.build()` runs that path instead of a bare `ninja`.
- Three tests in `test/registered/unit/kernels/test_jit_cache.py`: the fallback, the error message, and `ninja.build()` with ninja missing from PATH.

## Tests

The three new tests fail without the change (`toolchain` has no `ninja_path`, and `ninja.build()` raises `FileNotFoundError`) and pass with it. The rest of `test_jit_cache.py` gives the same results before and after.

I ran this on Windows, where `sglang` itself does not import (`srt/utils/common.py` imports the Unix-only `resource`), so I loaded the modules with a local shim that skips the package `__init__` files and stubs `kernels/jit/utils/arch.py`. Tests that fail there for unrelated reasons (`tvm_ffi` and `fcntl` missing, Windows paths) fail the same way with and without the change. CI runs the file on Linux in `base-a-test-cpu`.
