# [Feat] diffusion: Support dynamic full-matrix LoKr for single-GPU Z-Image

[Upstream PR](https://github.com/sgl-project/sglang/pull/48269) · state: open · merged: False

## Original PR description

## Motivation

Add a limited first implementation of LoKr loading for users with existing Z-Image-Turbo adapters such as [F16/z-image-turbo-sda](https://huggingface.co/F16/z-image-turbo-sda).

Related to #25897 and the earlier draft #34383. This draft is for feedback on whether the feature and initial scope are useful before expanding support.

## Modifications

- Recognize full-matrix `lokr_w1`/`lokr_w2` checkpoints and map factors to existing linear layers, including fused QKV and gate/up projections.
- Apply compact Kronecker deltas through the existing adapter API, with strength control, disable/reactivate, and startup loading.
- Reject incompatible configurations before replacing cached adapter state.
- Initial scope: one adapter, one GPU, unquantized Z-Image, dynamic mode. Merge mode, decomposed/Tucker factors, quantization, and multi-GPU execution are unsupported.

## Accuracy Tests

Validated on base `57bfde9f2c62f1bc4625209912e056f5b60134e4` with one H100 80GB, PyTorch 2.14.1+cu130, eager execution, compilation and offload disabled.

- `test_lokr.py` and `test_lora_pipeline.py`: **60 passed, 0 skipped**. Ordinary LoRA switching is covered by unit tests, not full-model serving tests.
- All **240 real checkpoint projections** passed CUDA checks against dense FP32 Kronecker products and LyCORIS 3.2.0 BF16/autocast paths using seeded synthetic inputs. Maximum FP32 absolute error: `1.073e-6`; BF16 relative L2 error versus LyCORIS: `0`.
- Three prompt/seed cases at 1024×1024, 9 steps, guidance scale 0: adapter changes the output; startup and dynamic loading produce identical pixels.
- The primary case also checks baseline repeatability, zero strength, disable/reactivate, auto versus explicit dynamic mode, and rejected merge requests preserving the active output.

Pinned weights:
- Base: `Tongyi-MAI/Z-Image-Turbo@f332072aa78be7aecdf3ee76d5c247082da564a6`.
- Adapter: `F16/z-image-turbo-sda@41a61f7c06155a681a04a1c8f775243393ed64d8`, `zit_sda_v1.safetensors`.

## Speed Tests and Profiling

Three warm requests per state, same prompt/seed; timings include HTTP and image encoding.

| State | Median request latency |
| --- | ---: |
| Adapter disabled | 0.838 s |
| LoKr enabled | 1.297 s |

This dynamic implementation adds approximately **55% latency** in this configuration. No kernel profiling or comparison against merged LoKr has been performed.

Device memory sampled once per second was 24,455 MiB in both request windows. The disabled baseline was measured after loading the adapter, so this does **not** establish zero additional adapter memory.

GPU validation contributed by @AaronYu94, included as a commit co-author.
