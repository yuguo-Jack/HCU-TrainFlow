# [Fix] spec: Record spec-v2 tensors by device type, not is_cuda

[Upstream PR](https://github.com/sgl-project/sglang/pull/47936) · state: open · merged: False

## Original PR description

## Motivation

`record_stream_each` tells the caching allocator that spec-v2 tensors are also used on the forward stream, but it only records tensors with `t.is_cuda`. On devices that report `is_cuda=False`, it records nothing. In-tree, that is Intel XPU; we noticed it while porting to Cambricon MLU (#45149).

The overlap future map on the same path already filters with `device.type != "cpu"`, so the two disagree.

This is hardening, not a fix for an observed failure. On main the scheduler's two-iteration batch pin also keeps these tensors alive. We found no configuration that exposes the missing records, and saw no corruption. The pin is marked in `scheduler.py` as `FIXME(lsyin): hacky way to keep a reference`, with `NOTE: More Reliable: record all tensors into the forward stream`. This PR makes that mechanism apply on XPU too.

## Modifications

- `record_stream_each`: skip host tensors (`not t.is_cpu`) instead of recording only `t.is_cuda` ones.
- `test/registered/unit/spec/test_spec_utils_record_stream.py` (CPU, `base-a-test-cpu`): host tensors, `None` and non-tensors are skipped without raising. CPU reaches this helper with host tensors (non-overlap EAGLE-family V2 and n-gram), and `record_stream` has no CPU kernel, so an always-true filter would crash those paths. It passes on main too.
- `test/registered/xpu/test_record_stream_each_xpu.py` (XPU, `stage-b-test-1-gpu-xpu`): a recorded block must not be handed out again on its allocating stream while the recorded stream still has queued work. This is the case expected to separate main from this branch (see Testing). It allocates about 2 GiB, using the sizes from torch-xpu-ops' `test_record_stream_on_shifted_view`. That test covers the allocator; this one covers sglang's filter.
- The two cases are separate files because `test/registered/unit/` is for tests that need no accelerator. The XPU file follows the layout of `xpu/test_ptr_table.py`.

### Behavior per backend

| Backend | Before | After |
|---|---|---|
| CUDA / ROCm / SAIL / MUSA (torchada patches `is_cuda`) / Ascend NPU (`transfer_to_npu`) | recorded | recorded |
| **Intel XPU** | **skipped** | **recorded** |
| Other non-CPU backends, including HPU and out-of-tree plugins | skipped | recorded if the device has a `record_stream` kernel. Without one, EAGLE overlap decode already fails at the future map's call; only non-overlap EAGLE-family V2 would reach this call first (n-gram allows only CUDA, CPU and XPU) |
| MPS | unreachable | unreachable: `torch.mps` has no stream API, so callers fail getting the stream, before this helper |
| CPU | skipped | skipped |

Out of scope:
- UNO V2's own `is_cuda` check on `seq_lens` (UNO only supports CUDA, so it cannot skip anything) and the `.is_cuda` checks under `srt/speculative/` that select fast paths rather than tensor lifetimes.
- The same `is_cuda` guard around `record_stream` outside spec-v2: `managers/hisparse_coordinator.py`, `mem_cache/mla_host_dedup.py`, `mem_cache/unified_cache/linker_mla_dedup.py` and `managers/mm_utils.py`. We have not checked whether these paths need the records on XPU, so they are left for a follow-up. `mem_cache/l2_transfer.py` already allows XPU explicitly.

## Accuracy Tests

N/A: tensors that report `is_cuda` are recorded as before. Elsewhere this only defers reuse of recorded blocks.

## Speed Tests and Profiling

Not measured, because we have no XPU hardware. The host cost is unchanged. The expected cost on XPU is one `ext_oneapi_submit_barrier` per (recorded block, recording stream) when the block is freed, which comes to about one per verify step for `seq_lens`, plus `req_pool_indices` and extend-batch outputs on n-gram. Recording on the queue that allocated a block returns immediately, so forward-stream tensors add nothing. @arathi-hlab @polisettyvarma, please say if you would like TPOT numbers before merging.

## Testing

- pre-commit on the changed files: all applicable hooks pass, including `check-registered-tests`.
- Both test files together on this commit, torch 2.12.1 (CPU build): `1 passed, 1 skipped` (the XPU case is the skip). With the filter mutated to always-true the CPU case fails with `NotImplementedError`; with main's filter it passes.
- CPU case on torch 2.14.1 (CPU build): that environment cannot import sglang, so we checked only the behavior the case relies on, with the filter copied into a script. `torch.Stream("cpu")` constructs, the new filter skips host tensors, and an always-true filter raises `NotImplementedError`.
- XPU case: not run by us. Once a maintainer adds `run-ci`, the per-commit XPU job runs it, because the change touches `python/sglang/srt/**`. We will push a temporary commit reverting the `spec_utils.py` change, let its XPU job finish before dropping the commit (a new push cancels the running job), and link both runs here:
  - with the revert (expected to fail): pending
  - this branch (expected to pass): pending

  <details>
  <summary>Why the XPU case should not be flaky</summary>

  It needs `read_stream` to still be busy when it reallocates, and asserts `read_stream.query()` is False first. The 30 queued adds move about 90 GiB, roughly 0.2 s at the B580/B60's 456 GB/s (an estimate, not measured), while the gap between that check and the reallocation is microseconds.
  </details>
- `registered/e2e/xpu/test_spec_eagle_intel_xpu.py` is a nightly XPU test, and `/rerun-test` only dispatches cuda, multimodal_gen and cpu tests. If you want it run before merge, it needs an XPU maintainer to run it.

<details>
<summary>Which tensors actually cross streams</summary>

With overlap scheduling the batch is built under `StreamContext(schedule_stream)` and the forward runs under `forward_stream_ctx`. The tensors that cross streams here:
- `seq_lens`, resolved by the overlap future map before the forward context (except on the HIP GPU-only path);
- `req_pool_indices`. For EAGLE, the future map records `future_indices`, but that is the same tensor only until a filter/merge reallocates either side. For n-gram, `_resolve_spec_extras` returns before that record;
- n-gram extend batches, whose `prepare_for_extend` outputs come straight from the schedule stream;
- with `SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1`, the plan-stream `out_cache_loc` when `prepared_out_cache_loc` is None.

The other tensors passed in are created on the forward stream by default, so recording them has no effect.
</details>

<details>
<summary>Allocator-level illustration on Cambricon MLU590 (also is_cuda=False)</summary>

Standalone script with the two filters copied in (torch 2.12.1, torch_mlu 1.34.1), not this branch:
- The same lifetime scenario as the XPU test: main's filter reused the block in 5/5 trials, the host-skipping filter in 0/5.
- Allocate 128 MiB on stream A, queue 8 full copies on stream B, drop, reallocate and zero-fill on A. Copies 2-8 read overwritten data in every trial with main's filter, and none did with the new filter. This is PyTorch's documented `record_stream` semantics, not an sglang failure.
</details>
