# [CI] ci-monitor: Attribute pytest failures before inferring timeouts

[Upstream PR](https://github.com/sgl-project/sglang/pull/46939) · state: open · merged: False

## Original PR description

## Motivation

The CI monitor, which runs every 12 hours, can mark a file as a possible timeout when pytest listed other files as failed. A maintainer who reads its step summary or JSON artifact then looks at the wrong test. In monitor [run 41441787333](https://github.com/sgl-project/sglang/actions/runs/41441787333) on 2026-11-02, all 10 inferred timeouts show this, in `multimodal-gen-test-1-gpu-amd` partitions, on files with no failure row.

With this PR, those 10 jobs name the files that pytest listed, 14 jobs that named no file now name one, and 94 with logs still name none. In a saved-data replay on 5 AMD runs, step summary rows with a timeout mark go from 32 to 0.

In [job 124857721211](https://github.com/sgl-project/sglang/actions/runs/41309823139/job/124857721211), the monitor blames `test_component_residency.py` (`PASSED` lines, no failure row), and the real failure is `test_minimax_h3_dit_contract.py`.

With no custom `Test Summary`, the parser skips pytest's failure rows and names the file that last printed `server_args:`, even a file that passed.

I found no other open PR that changes this parser.

## Modifications

The parser now reads pytest's `FAILED`, `ERROR`, and `SUBFAILED` rows before it infers a timeout.

- The runner's `retry failed items` marker discards the attempt it replaces. A new session keeps earlier failures.
- A `-q` result after a session header is a nested run, so its rows do not count.
- Inference reads only lines after the last session header or pytest result and adds to known failures.
- `ci_auto_bisect.py` calls this parser, replacing its older copy with the same problem.

Rows that start with `Limit` show deliberate limits.
