# [Feat] [NPU] eplb: Enable dynamic expert load balancing on Ascend

[Upstream PR](https://github.com/sgl-project/sglang/pull/47574) · state: closed · merged: True

## Original PR description

## Motivation

Enable dynamic EPLB on Ascend with `--enable-eplb`, using the existing planner and single-layer weight-migration algorithm. The integration supplies valid expert-route statistics and handles NPU weight formats while preserving the storage addresses used by captured graphs.

## 1. Count valid routes in NPU DeepEP, including low-latency mode

DeepEP's communication mode and EPLB's statistics source are separate choices. This PR changes the statistics source; `low_latency` still uses low-latency dispatch, and `auto` still selects its communication mode at runtime.

In the existing gatherer factory, DeepEP `normal` uses TopK IDs, while `low_latency` uses receive-side expert counts. On NPU, graph-padding rows retain expert IDs for dispatch and have zero routing weights. Their receive counts therefore include rows that do not represent valid token routes. The NPU TopK path already provides a separate recorder view with those padded IDs masked to `-1`.

The factory now selects the existing TopK gatherer for NPU DeepEP in `normal`, `low_latency`, and `auto` modes. That gatherer counts the valid physical expert IDs and ignores `-1`; the shared accumulator reduces them and maps them to logical expert loads for the planner. No new recorder or counting kernel is introduced. Earlier `per_token` and `stat_approx` branches keep their existing selection rules, and GPU gatherer selection is unchanged.

For example, a graph bucket can contain eight rows with only four valid tokens. Zeroing the other four rows' routing weights does not remove their IDs from dispatch receive counts; masking those IDs in the recorder view excludes them from EPLB statistics. In the controlled two-rank check, real routes target rank 0 and padded routes target rank 1. Receive totals are `64/64`, while valid-route totals are `64/0`: the former reports balanced traffic even though the valid routes are entirely on rank 0.

## 2. Migrate NPU weights through ND storage

The common updater has one NPU dispatch branch. The NPU helper selects the changed layers and each rank's participation, validates TP = EP = WORLD and the selected chunk's tensor specifications, then calls the existing shared single-layer migration function.

For each participating layer:

1. Convert internal-format weights, such as NZ, to contiguous ND tensors; pack strided weights as needed. Contiguous ND weights are used directly.
2. Run the shared local-reordering and P2P algorithm on those tensors.
3. For changed local slots, restore the original format and copy into the original weight storage. This preserves addresses referenced by captured graphs.

A rank whose own slots are unchanged may still need to send an expert to another rank. It participates in that transfer but skips local writeback. With elastic EP enabled, the existing participation and missing-expert handling remain active.

Utilization-broadcast tensors also use the runtime device instead of hard-coded CUDA.

## 3. Control migration memory

These controls are included in this PR:

| Code behavior | Memory effect |
| --- | --- |
| Allocate receive buffers on the first participating layer and reuse them across the chunk | Avoid a separate receive-buffer set for every layer; idle ranks allocate none |
| Use the ND conversion result directly; reuse already-contiguous ND weights | Avoid an extra staging copy of those weights |
| Release each layer's ND references and use completion events to bound queued staging | Prevent the host from queuing temporary tensors for every layer while the device is still processing earlier transfers |
| Skip globally unchanged layers and ranks with no local changes or possible sends outside elastic EP | Avoid their conversion and receive-buffer allocations |
| Skip writeback when local slots are unchanged | Avoid unnecessary format-restoration tensors and copies on sender-only ranks |

The event queue retains two completion events; it waits before allocating further layer staging. Dropping Python references alone cannot bound the peak while earlier device work still uses that storage. The events allow completed storage to be reused by the allocator; cached memory can remain visible in device memory usage.

This controls migration's temporary allocations. Communication still uses default WORLD in this PR. TP-group reuse and draft-statistics isolation are in #47595, so their communication-memory savings are separate from these staging controls.
