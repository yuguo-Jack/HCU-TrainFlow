# [Feat] sgl-kernel: Add FlashMLA V4.1 sparse decode and MegaAttention ops for the token-interleaved KV cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/45708) · state: closed · merged: False

## Original PR description

## Motivation

The latest FlashMLA DeepSeek-V4.1 kernels read a token-interleaved KV cache: each token's data followed by its scales, no page padding. They are faster than the fork's V4.1 kernels, and they are what the serving integration in #45635 needs.

## Why a second library instead of bumping the fork's pin

The upstream FlashMLA release of 2026-09-30 that carries these kernels is V4.1-only. Compared with the fork's common base with it:

- It deletes all SM90 (Hopper) kernels and the dense decode API: 24 files.
- It deletes the SM100 DeepSeek-V3.2 and V4 sparse decode, V4 MegaAttention, and 576-dim / small-topk prefill instantiations: 17 files.
- Its KV format header defines only V41 and V41_FP4; the fork's defines V32, V32 without RoPE, V4, V41 and V41_FP4.
- The SM100 sparse decode kernel and the MegaAttention core kernel are rewritten for the interleaved layout, not edited: every line differs.

So re-pointing `flashmla.cmake` at upstream would drop Hopper, V3.2 and V4, and merging upstream into the fork means re-implementing the V3.2 and V4 formats inside the rewritten kernels and re-homing SM90 under the new tree. The two source trees also cannot share one library: the V4.1 instantiations have the same names and differ only in the layout they read. Hence a second target built from upstream, with the fork untouched. Folding the upstream kernels into the fork is the follow-up that removes it.

## Modifications

- `flashmla_v41_ops.so` in the wheel for SM100/SM103 when CUDA >= 13.0, registered as `torch.ops.sgl_flashmla_v41`.
- `sgl_kernel.flash_mla`: `is_flash_mla_v41_available()`, `flash_mla_v41_sparse_decode()`. `sgl_kernel.flash_mla_mega`: `flash_mla_mega_prefill_v41()`, `flash_mla_mega_decode_v41()`.
