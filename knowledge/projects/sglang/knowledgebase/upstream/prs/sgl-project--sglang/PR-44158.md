# [Perf] custom_op: Call register_custom_op ops directly in plain eager execution

[Upstream PR](https://github.com/sgl-project/sglang/pull/44158) · state: closed · merged: True

## Original PR description

## Motivation

Every op registered with `register_custom_op` is called through `torch.ops.sglang.<name>`, even in plain eager execution. The op is registered for a single device key and has no autograd formula. So for ordinary tensors the dispatcher does nothing except box the arguments and re-enter the same Python implementation, and that costs several microseconds per call. For diffusion models this is a noticeable share of host time per denoising step. In a py-spy profile of FLUX.2, Qwen-Image and Ideogram (H200, 2 GPUs, eager, at a size where the host bounds the step), `torch/_ops.py __call__` alone accounts for 5–8% of host time. On Grace hosts (GB200/GB300) and with several TP ranks, the step is host-bound and this time reaches end-to-end latency.

## Modifications

`CustomOpWrapper.real_impl` (`sglang/srt/utils/custom_op.py`) now returns a thin caller. It calls the op's Python function directly only for plain device tensors under `no_grad` / `inference_mode`, which is how both srt and multimodal_gen run. It calls the registered op in every other case:
- under `torch.compile` / export tracing (`torch.compiler.is_compiling()`);
- while a dispatch mode is active: fake tensors, `make_fx`, `FlopCounterMode`, or any `TorchDispatchMode`;
- while a `TorchFunctionMode` is active;
- while the profiler is enabled, so traces keep their `sglang::<op>` spans;
- with grad enabled;
- when an argument is a tensor subclass, or a host or meta tensor. These keep their previous `NotImplementedError` or fake output.
- when another function registered the name first;
- when kernel API logging is enabled.

The dispatcher sets no device guard for Python-registered kernels, so the current-device behavior is unchanged. One difference remains: the dispatcher converted arguments to the schema's types (e.g. a 0-d tensor passed for a `float`), and the direct call passes them as given. The call sites checked pass Python scalars.

No memory is involved. Compiled graphs are unchanged, because they reference `torch.ops.sglang.*` directly. Ops registered with `direct_register_custom_op` and called as `torch.ops.sglang.*` are untouched.

## Accuracy Tests

The same Python implementation runs with the same arguments, so outputs are identical. In every end-to-end configuration below, the output image md5 matched main.

`test/registered/unit/utils/test_custom_op_eager_direct.py` checks four things:
- an eager call enters the implementation directly;
- a `TorchDispatchMode` still sees `sglang.<op>`;
- grad mode, a `TorchFunctionMode` or a tensor subclass goes through the dispatcher;
- the profiler records the op;
- host tensors are still rejected;
- a name registered first by another function keeps that function;
- `torch.compile(fullgraph=True)` traces the op.

On GB300 (sm103) and H200, the existing suites that exercise these ops pass:
- diffusion kernels: `test_modulate`, `test_activation`, `test_rope`, `test_complex_rope`, `test_qknorm_rope_out_of_place`, `test_flux2_gated_resnorm`, `test_model_fast_paths`, `test_sites`, `test_residual_gate_fp32`;
- compile and communication: `test_regional_torch_compile`, `test_group_coordinator_compiled_all_reduce`, `test_torch_compile_decoration`.

The only exception is `test_rope`, whose three `test_anima_rope_bit_exact` failures also occur on main on that GPU.

## Speed Tests and Profiling

Base `8afe107`, torch 2.13, triton 3.7.1, GB300 (Grace host). Processes were pinned to the GPUs' NUMA node.

|---|---|---|
| `residual_gate_add` | 30.8 | 25.9 |
| `modulate_scale_shift` | 19.0 | 13.8 |
| `fused_silu_mul_bitexact` | 28.0 | 23.9 |
