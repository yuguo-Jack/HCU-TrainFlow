# [Feat] openai: parse DeepSeek output through deepseek-recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/45907) · state: closed · merged: True

## Original PR description

Stage B of the deepseek-recipe integration, stacked on #45315 (Python host; its commits show in this diff until it merges). Under `--chat-encoding-backend recipe`, the output of DeepSeek-V4 / V4.1 is parsed by [deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe)'s `StreamProcessor` instead of SGLang's `deepseek-v41` reasoning and `deepseekv41` tool-call detectors, so the prompt (stage A) and the output come from the one implementation of the format, the one behind the official API. The builtin backend is untouched.

## What changes

- `parser/deepseek_recipe_output.py`: `DeepSeekRecipeOutputParser` feeds the engine's token ids to recipe's `StreamProcessor` (markup is recognized by token id only) and yields `RecipeOutputDelta`s; a matched stop string is cut in the raw ids where the scheduler matched it, a matched stop token is dropped, and `no_stop_trim` keeps either, as the detokenizer does for text. `serving_deepseek_recipe.py`: the adapter implements the `ChatEncodingOutputAdapter` seam of #45300 itself, as the Inkling adapter does; it maps the deltas to SGLang's chunks, messages and Responses items. The handler keeps its role, finish and usage chunks, logprobs, `matched_stop` and `sglext`. `select_new_output_ids` moves to `chat_encoding_adapters.py`, shared with Inkling.
- All four output paths: Chat Completions streaming and non-streaming, Responses streaming and non-streaming. The two Responses protocol methods gain `request` and `require_reasoning`, which the parser needs for the thinking mode and the stop strings; both call sites had them in scope.
- SGLang's `separate_reasoning=false` (reasoning folded into `content`) and `stream_reasoning=false` (reasoning withheld until it ends) keep working.
- Startup: the recipe backend requires `--reasoning-parser deepseek-v4` / `deepseek-v41` and `--tool-call-parser deepseekv4` / `deepseekv41`, what `auto` selects, because the engine's think-end token and the tool-choice grammar still come from them.
- `server_arguments.mdx` row.

## Client-visible changes, recipe backend only

- Streamed tool-call arguments arrive incrementally, as the API streams them: the first chunk carries `id`, `function.name` and `arguments: ""`, later chunks carry pieces of the JSON. SGLang's detector emitted the whole arguments when the invoke tag closed. Clients that concatenate, as the OpenAI SDK does, are unaffected; clients that parsed each chunk's `arguments` as complete JSON must concatenate.
- Tool-call ids use the API's format (`call_00_` + 20 random characters + 4-digit checksum, an `ET_` marker on thinking turns that produced no reasoning) instead of `call_` + 24 hex characters.
- Reasoning / content boundaries follow recipe: leading newlines after `<think>` and `</think>` are dropped, a second `</think>` is dropped, text after the calls block is dropped. Matched stops are cut wherever the engine matched them, in reasoning or in content.
- `finish_reason` is recipe's (`tool_calls` once a call was named, which is what the builtin path reported too). `usage.reasoning_tokens` and `completion_tokens` stay the engine's exact counts.
- Thinking-mode requests sample at the API's temperature 1.0 and top_p even when the request asks for 0 (recipe's sampling overlay from #45315); the no-thinking path honours the request. The flag's docs row now says so.
- Requests served through sgl-router or sglang-server keep the Rust parsers until the Rust stage lands (a separate PR after #45715): whole tool-call arguments, ids in the old format.

## Tests

`test/registered/unit/parser/test_deepseek_recipe_output.py`: the outputs of `deepseek_recipe_golden.json` (sampled ids parsed by deepseek-recipe's own stream processor, whole and token by token: calls, parallel calls, cuts by `max_tokens`, `tool_choice` none, plain-token spellings of the markers, a stray `</think>`, a stop sequence, JSON output, prefix continuations), the matched-stop cut table (across tokens, inside a token, in reasoning, plain and special stop tokens, overlapping matches, `no_stop_trim`), the SGLang switches. `test/registered/unit/entrypoints/openai/test_serving_deepseek_recipe.py`: the parser pairing check, the package check, the served-tokenizer markers, the Responses handler's hooks; the chat adapter's tool-call output whole and streamed with `tool_choice` none and `separate_reasoning=False`, every token parsed once (cumulative and incremental chunks, the abort re-send, tokens appended after a chunk), matched stops in both response modes, prefix continuations. `test_serving_responses.py`: stream and non-stream Responses items from the same ids at several split points, with `tool_choice` auto and required. `deepseek_recipe_served.json` (recorded from a live V4.1-Flash server by `test/manual/parser/record_deepseek_recipe_served.py`, 14 temperature-0 requests with the prompt ids and output ids the server reported): `test_served_prompts_match` renders each request and asserts the live prompt ids; `test_served_outputs_replay` parses the live output ids whole and token by token, asserts the served message, and checks that SGLang's own DeepSeek parsers read the same reasoning, content and calls from the same ids. The e2e run on 4x B300 (both backends, chat + Responses, stream + non-stream, GSM8K) is reported in the PR comments.

## End-to-end run on the real model (B300:4, DeepSeek-V4.1-Flash @ 314113f8)

Run `e2e-1024` on Modal: the same server flags with `--chat-encoding-backend recipe` and then `builtin` (`--tp 4 --ep-size 4 --reasoning-parser deepseek-v41 --tool-call-parser deepseekv41`, nightly image 20261021 + the branch's `sgl-flash-mla` / DeepGEMM pins, `deepseek-recipe==0.2.0`). Every request was sent to `/v1/chat/completions` non-streaming (with `return_input_ids_in_sglext` / `return_output_ids_in_sglext`) and streaming, plus two `/v1/responses` cases. Raw records are in the `sglang-results` volume under `ds_api_vs_recipe/e2e/e2e-1024/`.

### What was checked

| Check | Result |
| --- | --- |
| 19 chat cases × {stream, non-stream} on the recipe backend: finish reason, reasoning / content / tool calls, JSON validity, stop string cut, no markup leaks | all pass |

| Prompt ids recipe vs builtin, identical requests | identical on all 13 cases whose rendering is specified the same way; the 6 that differ are by design: thinking on by default (recipe) vs off (builtin) without a toggle, and `json_object` instructions in the prompt (recipe) vs grammar only (builtin) |
| Output ids recipe vs builtin on identical prompts | identical on all 10 greedy no-thinking cases (plain, tools auto / required / named / parallel, JSON, stop string, continue_final_message); thinking-mode outputs differ because recipe samples thinking at the API's temperature 1.0 |
| GSM8K, 200 questions, chat API, temperature 0 | recipe 96.5% (thinking) / 95.5% (no thinking); builtin 97.0% / 97.0%; final answers agree on 197/200 (no thinking) and 196/200 (thinking) |

### Expected differences the run confirms

- `separate_reasoning: false`: builtin returns the raw text with `</think>` inside `content`; the recipe backend returns reasoning followed by content with no marker (the same as the Inkling backend on main), since recipe never decodes marker tokens.
- Streamed tool-call arguments: builtin sends them in one delta, recipe in 10–11 deltas per call (documented in the flag's row).
- Thinking mode is sampled at the API's temperature 1.0 even when the request asks for 0, so thinking-mode outputs are not reproducible across runs; the no-thinking path honours temperature 0 (identical ids across backends and across stream / non-stream).

### What this adds to the CPU tests

`test/registered/unit/parser/deepseek_recipe_served.json` holds 14 of these requests with the prompt ids and output ids the live server reported and what it served. `test_served_prompts_match` renders each request through the encoder and asserts the live prompt ids; `test_served_outputs_replay` feeds the live output ids to the parser whole and token by token and asserts the served message, then checks that SGLang's own DeepSeek parsers read the same reasoning, content and calls from the same ids. `test/manual/parser/record_deepseek_recipe_served.py` regenerates the fixture against any running server.

The first attempt of this run (`e2e-1023c`) hit two harness bugs on my side, not the code: the Responses API validates the `model` name (chat does not), and V4.1 sometimes skips thinking for a trivial tool call (first id is `</think>`, recipe's `ET_` call id), which my shape check mislabelled as missing reasoning.
