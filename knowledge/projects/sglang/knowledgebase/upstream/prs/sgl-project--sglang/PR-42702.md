# [PD] Fix retraction restores racing the in-flight decode forward

[Upstream PR](https://github.com/sgl-project/sglang/pull/42702) · state: open · merged: False

## Original PR description

## Motivation

On a PD decode server with the overlap scheduler, a retracted request's KV restored on resume can be overwritten by a forward that is still running. This holds for both retraction backups (`--disaggregation-decode-retraction-backup host_pool` or `cpu_tensor`; one of them is picked by default).

The decode event loop processes step N-1's results only after launching step N. A request that finished in step N-1 is still in batch N, so that forward writes the KV of its last token into a slot the request owned. Its slots, that one included, go back to the allocator when step N-1's result is processed (the decode radix cache is off by default). In the next iteration, `process_decode_queue` -> `DecodePreallocQueue.resume_retracted_reqs` can allocate those slots to a resumed request, and `restore_kv_cache` copies the backup into them:
- the `host_pool` backend issues a host-to-device copy on the L2 transfer stream, ordered only after an event on the scheduler stream;
- the `cpu_tensor` backend copies on the scheduler stream.

The scheduler stream does not wait for forward N's KV writes. `_apply_war_barrier` waits only for the forward's shared reads, unless it falls back to the coarse barrier. So the restore can land first, and forward N then overwrites a restored token with the finished request's KV. The resumed request continues decoding with one corrupted token in its context.

The prebuilt path in `get_new_prebuilt_batch` already drains the in-flight forward for the same reason, from #35748: `self.schedule_stream.wait_stream(self.forward_stream)` before a prebuilt request seeds a possibly reused row and before its host-received KV is restored. `resume_retracted_reqs` had no such wait.

## Modifications

- `DecodePreallocQueue.resume_retracted_reqs`: under the overlap scheduler, make the scheduler stream wait for the forward stream before each `restore_kv_cache`. Both backends issue their copy after work on the scheduler stream (the `host_pool` copy waits on an event recorded there), so both are ordered after the forward that may still write the reused slots. As with the prebuilt path, this gives up overlap for the step in which a retracted request resumes; resuming is rare (after retraction under memory pressure).
- `test_decode_queue_cleanup.py`: the hand-built scheduler of `test_paged_swa_retraction_resume_uses_physical_page_budget` sets `enable_overlap=False`.
- Test `test_resumed_restore_lands_after_the_inflight_forward` in `test/registered/unit/mem_cache/test_decode_retraction_backup.py` (CUDA). It uses real pools and a real `UnifiedRadixCache` with a host pool, and reproduces the interleaving deterministically:
  - a "forward" stream sleeps (`torch.cuda._sleep`) and then writes the slots that the resumed request is given;
  - `resume_retracted_reqs` then runs on the scheduler stream;
  - the restored KV must survive.
  On `main` the stale write lands after the restore and the test fails. A first pass with a short sleep loads every kernel first: CUDA lazy loading synchronizes the device on a kernel's first launch, which would otherwise order the race by accident.

Default behavior, not an option: the alternative is silent KV corruption, and the wait applies only in the iteration that resumes a retracted request.

This came out of auditing the retraction backup (`UnifiedRadixCache.backup_kv_cache`) for the overlap write-through race fixed in #42701. The backup is not exposed: it copies only `seqlen - 1` tokens, and the forward in flight at retraction writes only position `seqlen - 1`, so every copied position was written by a forward whose result the scheduler has already processed. The restore side, here, is exposed.

Out of scope: KV that the prefill server writes over RDMA into slots preallocated in the same iteration (`pop_preallocated`) is not ordered after the in-flight forward either. Transfer latency likely hides it, and I have not verified it.

Related: #42701 fences HiCache write-through copies for the same kind of race. The two PRs are independent and can merge in either order.
