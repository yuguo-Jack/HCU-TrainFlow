# [sglang-miles] Open a weight-update session only on an idle device

[Upstream PR](https://github.com/sgl-project/sglang/pull/44154) · state: open · merged: False

## Original PR description

## Motivation

A peer that writes the weights over RDMA (miles' p2p trainer, over Mooncake or NIXL) starts writing as soon as `begin_weight_update` returns. Its writes land in device memory outside the engine's streams, so nothing orders them after work the engine already launched.

With the overlap scheduler, an `in_place` pause can return while the last launched forward is still running on the device:

- `pause_generation(mode="in_place")` sets the paused flag and returns, leaving `last_batch` and `result_queue` untouched (`scheduler.py`, `pause_generation`), as #21705 made it to keep the KV accounting consistent;
- the overlap loop skips result processing while paused (`event_loop_overlap`, the `_engine_paused` branch), so nothing waits for that forward;
- `begin_weight_update` restores the weights and meets the TP ranks on a CPU barrier, without waiting for the device.

That forward can then read weights mid-write, and its tokens and KV are used when generation resumes. `retract` does not hit this, because it processes the last batch's result and so waits for it (`process_batch_result_*` synchronizes on `copy_done`). The engine's own update paths do not hit it either, since their writes are queued behind the forward on the engine's streams.

## Modifications

`begin_weight_update` synchronizes the device after the restores and before the TP barrier. It waits for at most the one forward still in flight, and leaves scheduler state untouched, so `in_place` resumes the frozen batch as before. The session open is where the engine hands its weights to writers, so it is where the device becomes idle, for every pause mode and every writer.

## Tests

End to end on 4×H200 with miles p2p (Mooncake): Qwen3-30B-A3B, actor CP2, one TP2 engine, `--fully-async --pause-generation-mode in_place`, 4 updates with generation in flight. The two arms differ only in sglang: `sglang-miles` `7f79d11d94` vs this PR.

The engine is instrumented on the devbox only:
- each forward starts behind a ~1 s sleep on its stream, so it reads the weights later than the ~0.4 s from pause to the trainer's first write;
- behind the forward, on the same stream, come a checksum of `embed_tokens`, layer 0 `qkv_proj` and `lm_head`, and a completion event.

Times below are ms after the in_place pause; "read" is what the forward in flight at the pause saw.

| arm | update | begin returns | in-flight forward done | first p2p write | in-flight forward read |
|---|---|---|---|---|---|
| before | 1 | 6.9 | 1018.7 | 412.7 | new weights |
| before | 2 | 6.6 | 1018.8 | 403.8 | new weights |
| before | 3 | 6.7 | 1018.4 | 397.3 | new weights |
| before | 4 | 6.7 | 1017.3 | 400.0 | mixed: new `embed_tokens`, old layer 0 and `lm_head` |
| after | 1 | 1019.0 | 1018.7 | 1425.8 | old weights |
| after | 2 | 1019.0 | 1018.7 | 1419.8 | old weights |
| after | 3 | 1018.9 | 1018.6 | 1415.5 | old weights |
| after | 4 | 1018.6 | 1018.2 | 1420.8 | old weights |

Both arms exit 0 and pass `--check-weight-update-equal`, which compares only the weights after the update. Before this change, the race is silent.

Coverage: with this change, a forward launched before the pause finishes before begin returns, whatever its length. Without the amplifier, the race needs a forward longer than the pause-to-first-write gap of the configuration; how often that happens naturally was not measured. The cost is waiting for at most that one forward.

**[P2] The quant restores in `begin_weight_update` still run before the new device drain, so they can race the forward left in flight by an `in_place` pause.**

At a6f82b9ed7, [`weight_updater.py` L410-L415](https://github.com/sgl-project/sglang/blob/a6f82b9ed78d1c35a0eb5565a579ddd9f1eabfb2/python/sglang/srt/managers/scheduler_components/weight_updater.py#L410-L415) enqueues `runner.weight_updater.begin_weight_update()` (the restores) before `torch.get_device_module().synchronize()`.

The restores run on `schedule_stream`. For decode CUDA graphs, [`_apply_war_barrier`](https://github.com/sgl-project/sglang/blob/a6f82b9ed78d1c35a0eb5565a579ddd9f1eabfb2/python/sglang/srt/managers/scheduler.py#L1900-L1911) makes `schedule_stream` wait only for the shared-read event. That event is recorded before the model layers, not at the end of the forward. Some restores rewrite weight storage in place:

- MXFP4 Marlin: `param.data.zero_()` ([mxfp4.py L666](https://github.com/sgl-project/sglang/blob/a6f82b9ed78d1c35a0eb5565a579ddd9f1eabfb2/python/sglang/srt/layers/quantization/mxfp4.py#L666)).
- MXFP4 TRT-LLM MoE: `expert.copy_(expert[rows])` ([mxfp4_flashinfer_trtllm_moe.py L248](https://github.com/sgl-project/sglang/blob/a6f82b9ed78d1c35a0eb5565a579ddd9f1eabfb2/python/sglang/srt/layers/quantization/mxfp4_flashinfer_trtllm_moe.py#L248)).

These writes can land while the paused forward is still reading the same weights. The new sync then waits for that forward to finish on weights that are already rewritten, and the `in_place` resume keeps its token and KV.

**Why P2:**

- **Impact:** wrong tokens and KV on resume, with no error.
- **Conditions:** MXFP4 Marlin or TRT-LLM MoE, overlap scheduler, CUDA-graph decode, `pause_generation(mode="in_place")`, then `begin_weight_update(sync_base=True)`. Any update path with these conditions is affected, not only p2p.
- **Not introduced here:** the race already exists on `sglang-miles`. This PR's claim that the session opens on an idle device does not hold for these restores.
- **Natural hit rate:** the in-flight forward must outlast the gap from pause to restore. That happened 0/10 times at bs=1 with gpt-oss-20b (below).

### Repro

Setup: 1x H200, gpt-oss-20b (MXFP4), `--moe-runner-backend marlin`, TP1, with the default overlap scheduler and CUDA graphs.

1. Stream a greedy generation of 48 tokens.
2. Once 16 tokens have arrived, call `pause_generation(mode="in_place")`, then `begin_weight_update(sync_base=True)`.
3. Call `update_weights_from_tensor` with the checkpoint's original expert tensors (`*_blocks`, `*_scales`, `*_bias`) and `flush_cache=False`.
4. Call `end_weight_update`, then `continue_generation`.
5. A run fails if its output ids differ from an unpaused greedy reference.

The race window is a few ms, so the repro adds a repro-only amplifier, identical in every run below, just before the layer loop in `GptOssModel.forward`:

```python
torch.cuda._sleep(600_000_000)
```

The sleep sits inside the decode graph after the WAR-barrier event, so the restore lands before the layers read the weights. A sleep placed on the stream before graph replay would delay the event as well and hide this race.

| run | amplifier | diverged | first differing index |
|---|---|---|---|
| base 7f79d11d94 | yes | 3/3 | 17 |
| this PR, a6f82b9ed7 | yes | 3/3 | 17 |
| this PR + pre-restore sync (below) | yes | 0/3 | none |
| this PR | no | 0/10 | none |

- **In this PR's runs**, `begin_weight_update` took about 610 ms, so the new sync did wait for the in-flight forward, and that forward still read the zeroed weights.
- **In the fix runs**, begin took about 615 ms and every output matched the reference.
- **The weights themselves are fine:** reference outputs are identical across all four runs and across two runs within each. A reference run after the update trials matches again, so the stored weights round-trip exactly. Only the in-flight token (index 17) is corrupted; later tokens differ because the prefix differs.

### Suggested fix

This is the code used in the "pre-restore sync" runs:

```python
if recv_req.sync_base:
    # the in_place-paused forward may still read the weights the restores rewrite
    torch.get_device_module().synchronize()
    for _, runner in self._select_runners(recv_req.selector):
        runner.weight_updater.begin_weight_update()
    # peers write over RDMA outside the engine's streams; restores must land first
    torch.get_device_module().synchronize()
```

Moving the single sync above the restores is not enough, because the restore writes would then race the peers' RDMA writes. Both syncs are inside `sync_base`, since adapter-only sessions run no restores and receive no base bytes.

Not covered: the TRT-LLM MXFP4 restore (Blackwell only), and the natural hit rate at production batch sizes.
