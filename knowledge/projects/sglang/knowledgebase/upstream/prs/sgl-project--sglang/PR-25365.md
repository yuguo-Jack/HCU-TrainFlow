# [Feat] observability: add chunked prefill trace attributes

[Upstream PR](https://github.com/sgl-project/sglang/pull/25365) · state: open · merged: False

## Original PR description

## Motivation

SGLang already emits OpenTelemetry spans for chunked prefill, but those spans do not currently expose enough attributes to distinguish intermediate chunks from the final prefill completion. This makes trace analysis harder when investigating latency distribution across chunked prefill requests.

This PR adds lightweight attributes to chunked prefill spans so users can identify chunk order and whether a span represents the final chunk.

## Changes

- Add a per-request chunked prefill counter.
- Attach `chunk_index` and `is_final_chunk=false` to intermediate `chunked_prefill` spans.
- Attach `chunked_prefill_remaining` when scheduler metadata is available.
- Mark the final prefill span with `is_final_chunk=true`.
- Reset the chunk counter when retracting request timing state.

## Validation

- `python -m py_compile python/sglang/srt/observability/req_time_stats.py python/sglang/srt/disaggregation/prefill.py python/sglang/srt/managers/scheduler_output_processor_mixin.py`
- `ruff check python/sglang/srt/observability/req_time_stats.py python/sglang/srt/disaggregation/prefill.py python/sglang/srt/managers/scheduler_output_processor_mixin.py`
- Real server validation on NVIDIA H20 with Qwen3-0.6B, `--enable-trace`, and `--chunked-prefill-size 64`. A 352-token prompt produced six `chunked_prefill` spans with chunk attributes, including the final span marked as `is_final_chunk=true`.

Conflicts resolved, and the scope is much smaller than what you approved in May. `main` had moved 5848 commits, and one of the three files this PR used to touch (`scheduler_output_processor_mixin.py`) no longer exists, so a mechanical rebase was not possible. Rather than keep asking about scope — my August comment left six open questions and stalled this for weeks — I cut the change down to the part that needs no decisions, and answered those questions myself below.

### What it does now

`set_last_chunked_prefill_finish_time` emits one trace slice per chunk, all under the same stage name, so a trace cannot tell the first chunk from the seventh:

```python
stage = RequestStage.PREFILL_CHUNKED_FORWARD
self.observe_per_stage_req_latency(stage, ts - last_time)
self.trace_slice(stage, last_time, ts)          # no attrs
```

The whole change is an ordinal, counted exactly the way `decode_ct` already counts decode-loop iterations twelve lines below in the same class:

```python
attrs = {"chunked_prefill_ct": self.chunked_prefill_ct}
self.trace_slice(stage, last_time, ts, attrs)
self.chunked_prefill_ct += 1
```

plus `chunked_prefill_ct: int = 0` declared beside `decode_ct`.

### Answering my own questions, with the precedent for each

| question | decision | why |
|---|---|---|
| 0-based or 1-based? per-attempt or per-request? | 0-based, monotonic per request | identical to `decode_ct`, which is declared `= 0`, emitted, then incremented, and is **not** reset in `set_retract_time` or the other reset path — so it counts over the request's whole life |
| `is_final_chunk` semantics? | dropped | `set_prefill_finished_time` already closes the final chunked slice separately, so finality is expressible without a new attribute and without touching retry semantics |
| `chunked_prefill_remaining` — drop or rename to `inflight_middle_chunks`? | dropped | it was the scheduler-specific attribute whose upstream field was renamed, and it is the part that required the scheduler files that have since moved |
| `chunked_prefill_end_index` absolute or attempt-relative? | dropped | same reason; belongs with the scheduler work, not here |
| PD/retry metadata in scope? | no | keeps this to the universal ordering contract |
| unqualified key or an SGLang namespace? | unqualified `chunked_prefill_ct` | matches `decode_ct`, which is already emitted unqualified in this file |

Every dropped item was scheduler-specific. What remains touches only `observability/req_time_stats.py`.
