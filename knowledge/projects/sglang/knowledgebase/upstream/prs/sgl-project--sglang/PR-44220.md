# [Fix] cuda_graph: Wait for in-flight layer-wise cache loads before prefill graph replay

[Upstream PR](https://github.com/sgl-project/sglang/pull/44220) · state: closed · merged: True

## Original PR description

## Motivation

HiCache L2 load-back, HiCache storage load-back (e.g. `buffer_only`), and the unified-cache external linker load KV/SWA/Mamba state into the device pools layer by layer, overlapped with the prefill forward. The forward waits for each layer inside the pool accessors (`get_key_buffer`, `mamba2_layer_index`, ...) through the registered `layer_transfer_counter`.

A prefill CUDA graph replay never runs those Python-level waits: the captured graph is launched as a whole. Nothing stops the graph from replaying a batch whose load is still in flight (`scheduler.py` has carried `# todo: disable cuda graph execution if hicache loading triggered` since 2025-06). The forward then reads layers that have not landed yet and produces wrong logits silently. Computed KV for the following pages is built on the corrupted state, and can be cached and backed up under the same content-addressed keys.

This is reachable on main today whenever a model replays the prefill graph for a loading batch. Inkling defaults to the Full prefill CUDA graph backend, so its HiCache path is affected. Whether it shows up depends on the race between the H2D copies and the replay: the existing Inkling HiCache bit-exact tests pass on main only because the copies usually win.

## Modifications

- `PrefillCudaGraphRunner.execute`: before a Full replay, if the KV pool's layer transfer counter has an active consumer (this batch is loading), wait until the last layer has landed. Works for both counters (HiCache `LayerDoneCounter`, a stream wait; linker `LayerWiseLoadCounter`, a CPU wait), since both complete layers in order.
- Eager and breakable prefill are unchanged and keep per-layer load/compute overlap: breakable replay runs the pool accessors at its eager breaks, so their per-layer waits still apply (except a captured state-reading linear extend, see below). A loading batch that replays a Full graph now waits for the whole load first; batches without a load are unaffected.
- Test hook `SGLANG_TEST_HICACHE_H2D_DELAY_CYCLES` (default 0, off): a GPU sleep on the host-to-device stream before each layer's load, so a replay that skips the load wait reliably reads unloaded layers.

## Accuracy Tests

Inkling (`thinkingmachines/Inkling --revision test`, deterministic inference, Full prefill graph default).

New `TestUnifiedHybridHiCacheSlowLoadBitExact` (the existing HiCache bit-exact class with `SGLANG_TEST_HICACHE_H2D_DELAY_CYCLES=50000000`):

| GPU | main | this PR |
|---|---|---|
| 1x H200 (CI arch) | avg KL 4.4e-3 (fail) | 0.0 |
| 1x GB300 | avg KL 1.7e-2 (fail) | 0.0 |

The existing `TestUnifiedHybridHiCacheBitExact` passes on both trees: without the delay the H2D copies usually win the race, which is why CI has not caught this.

Earlier probe on 1x GB300 with the same kind of injected H2D delay, also covering storage load-back; the logs confirm graph replays with an in-flight load:

| Tree | Injected H2D delay | `TestUnifiedHybridHiCacheBitExact` (L2) | `TestUnifiedHybridBufferOnlyBitExact` (L3) |
|---|---|---|---|
| main | no | avg KL 0.0 | avg KL 0.0 |
| main | yes | **avg KL 3.1e-3 (fail)** | **avg KL 6.4e-3 (fail)** |
| this PR | yes | avg KL 0.0 | avg KL 0.0 |

The same fix also restores KL 0.0 for the Mooncake direct linker on Inkling (#41343), which hits the race without any injected delay (avg KL 2.5e-3 before; 0.0 in 3/3 runs after, and 0.0 with a 0.2 s per-layer injected load delay).

Breakable check: Inkling forced to `--cuda-graph-backend-prefill breakable` with the same injected delay gives avg KL 0.0 on main and on this PR (4 replays with an in-flight load each); its state reads run at eager breaks.

**Out of scope, fixed in #44414:** a breakable graph that captures a state-reading linear extend (the Triton KDA extend captured since #41105) skips those reads' waits. GLM-5.3-Flash on 4x GB300 with the Triton KDA extend forced and the same delay: median KL 3.5-4.1e-3 on main and on this PR vs a 1.9e-4 floor; 1.4e-4 when every replay waits or when the KDA capture is disabled. Not a regression from this PR.

## Tests

- `test_prefill_cuda_graph_runner.py::TestPrefillCudaGraphRunnerLayerLoads`: the replay wait blocks until the last layer of an in-flight load completes, and is a no-op without a counter. Negative control: removing the wait fails `test_replay_waits_for_every_layer_of_an_inflight_load`.
- `test_prefill_cuda_graph_runner.py`: 18 passed, including `test_breakable_replay_keeps_per_layer_load_overlap` (fails if the wait is not limited to Full).
- `test_unified_radix_cache_kl_hybrid_bitexact.py::TestUnifiedHybridHiCacheSlowLoadBitExact`: fails on main, passes with the fix (table above); about 70 s per class.

**[suggestion]** `TestUnifiedHybridHiCacheSlowLoadBitExact` only inherits the KL branching case. That case is a valid bug regression when a Full prefill graph actually replays over a delayed H2D load, but nothing in the new class pins that those two things happened. `TestUnifiedHybridMTPBitExact` in the same file already checks `cuda_graph_config.prefill.backend == "full"` and that `sglang:cuda_graph_passes_total{mode="prefill_cuda_graph"}` increased; without the same check here, a later change that keeps this config off the Full prefill graph leaves the class green and no longer covering the race.

**Suggestion:** In this class (or an override of `test_multiturn_decode_cache_hit_branching`), assert the server is on the Full prefill backend and that `_prefill_graph_count` rises across the request, matching the MTP class a few lines below.

**[suggestion]** `test_replay_waits_for_every_layer_of_an_inflight_load` starts a non-daemon thread and, on the failure path, `join(timeout=5)` then `assertFalse(waiter.is_alive())`. If `_wait_for_layer_loads` blocks on the wrong future, the assertion fails but the waiter is still alive, so the CPU suite can hang at process exit. The breakable sibling already passes `daemon=True` for that reason.

**Suggestion:** Pass `daemon=True` on this `Thread` as well (or `addCleanup` that completes the last layer / fails the future if the waiter is still alive).
