# [diffusion] Qwen-Image 2.1 VAE decoder fast paths: bit-exact norm/bias fusions by default, channels_last decode under quality=extra-high

[Upstream PR](https://github.com/sgl-project/sglang/pull/41340) · state: open · merged: False

## Original PR description

Independent of the attention PR; both add entries to `kernels/ops/diffusion/__init__.py`, the kernel README and the fast-paths inventory (adjacent lines, trivial to rebase; the inventory section is numbered 18 assuming the attention PR's 17 lands first).

## Motivation

The Qwen-Image 2.1 VAE decode of a 1024x1024 image takes 186 ms on one SM120 GPU. Its decoder (dims 1152/1152/1152/576/288/144, five up blocks that run three residual blocks at their own resolution and then upsample) spends that time on cuDNN convs, but also on work that is pure data movement: cuDNN's NCHW/NHWC transposes around every conv (25 ms), aten's channel RMSNorm chain (fp32 copy + reduce + four pointwise passes + SiLU), a separate bias-add pass after every conv (46 launches, 10 ms) and nearest-2x upsampling that quadruples the pixels before a 3x3 conv.

This PR removes that overhead in two tiers, following the existing VAE fast-path conventions (`VaeFastPathGate` for quality-gated paths, `BitExactFusionGate` first-sight verification for default-on paths):

- **default (`quality=lossless`)**: bit-exact fusions only; the output PNG is unchanged;
- **`quality=extra-high` / `high`**: the decoder switches to channels_last and uses an NHWC norm kernel with its own reduction order plus fp32-folded upsampler weights; documented as close, not bit-exact.

## Modifications

One commit per optimization (`runtime/models/vaes/qwen_image21_vae_cuda_opt.py`, mounted from `platforms/cuda.py::optimize_vae`; parameter names are preserved so checkpoints load unchanged):

1. `a99db03979` **Lossless fast paths (default on)**: `channel_rmsnorm_finish_silu` JIT kernel keeps aten's fp32 `norm(dim=1)` reduction and fuses the pointwise finish (`max(norm, 1e-12)`, divide, scale, gamma, `+0.0`) with SiLU; `FoldedPadConv2d` folds the symmetric `F.pad` of every causal conv into the conv's own padding, verified per (dtype, shape, stride) signature because cuDNN may pick another algorithm; the fold is only attempted above 2^18 output elements, where a bit-exact first-sight match is decisive (two engines with different accumulation orders agree on all but ~1e-4 of the elements, so on a few thousand elements they can match by chance, as the H100 runner showed at a 4x4 test latent).
2. `a99052507b` **channels_last decode under the quality gate**: the decoder flips to channels_last (parameter memory only; flipping back restores the NCHW kernels exactly), `channel_rmsnorm_silu_nhwc` reduces each pixel's channels in a lane group (1-32 lanes per pixel with 16-byte loads, chosen from C by the Python wrapper so the C=144 last stage stays near bandwidth), and the nearest 2x upsample re-labels the merged-batch view with canonical NHWC strides and uses the bit-exact Triton NHWC gather.
3. `119ab3c768` **Upsampler fold (quality gate)**: each `nearest-2x + conv3x3(p1)` becomes one `ConvTranspose2d(k4, s2, p1)` whose kernel is the fp32 sum of the taps each output phase touches (2.25x fewer MACs, no 4x intermediate). The fold helper moves out of the FLUX.2 module into `vaes/conv_fold.py` so both VAEs share it.
4. `53da9a360c` **Conv bias fusions**: aten adds a conv's bias as a separate pass over the output. Each residual block's second conv now runs without its bias and the new bit-exact `bias_residual_add` JIT kernel applies bias and residual in one pass with aten's per-op bf16 rounding (default on, first-sight verified; channels_last-dense or NCHW-contiguous bf16). Under the quality gate the first conv hands its bias to the NHWC norm kernel, so that pass disappears too.
5. `8d1e569f15` **Upsampler bias into the shortcut add**: the shared Wan Triton kernel `dup_up3d_add` takes an optional per-channel bias (aten rounding), so the upsampler conv runs without its bias pass (default on, first-sight verified).
6. `16cadcebe6` kernel README rows, fast-paths inventory entry, pre-commit formatting (a marker benchmark added here was dropped again later in the series).

Fallbacks: spatial-parallel decode, ROCm, `torch.compile`, unsupported layouts and any first-sight mismatch keep the original module chain.

## Accuracy Tests

- Lossless (default) path, bit-exact: the `channel_rmsnorm_finish_silu` section of `test_norm.py` (14), the `bias_residual_add` section of `test_norm.py` (25, `torch.equal` in both layouts), the `dup_up3d_add` bias case in `test_layout.py`, and the Qwen-Image 2.1 VAE section of `test_model_fast_paths.py` (decode of an optimized tiny decoder with the real latent channel count equals the original bit for bit on a 64x64 latent, where every fold site's first-sight comparison is decisive, and again on a second latent while every gate reports verified; a mismatching kernel disables its gate and the decode stays bit-identical; `state_dict` keys unchanged). End to end the same-seed 1024x1024 PNG keeps `main`'s sha256 (`2781b27ac4b17cb1...`) in every lossless launch.
- `extra-high` path: the `channel_rmsnorm_silu_nhwc` section of `test_norm.py` (within two bf16 ulps of the eager chain, >95% of elements bit-identical, all lane-group specializations, fused bias) and the extra-high case in that section (channels_last decode close to the reference, gate off restores bit-identity). - triple-mu · comment · 2026-09-27T16:35:29Z · [source](https://github.com/sgl-project/sglang/pull/41340#issuecomment-5857721298)

Root cause of the H100 second-latent mismatch, and the fix pushed as head `daafd5dee2`.

**Mechanism.** The padding fold is accepted per input signature when the folded conv matches the padded conv bit for bit on its first sight. That comparison is only decisive when the output is large: two conv engines with different fp32 accumulation orders round to the same bf16 in all but about 1e-4 of the elements. The test decoded a 4x4 latent, so each conv produced 512 to 32k output elements; a fold whose engine differs from the padded conv's engine then matches on the first latent with high probability, is cached as verified, and differs on the next latent. The H100 log confirms cuDNN on sm90 uses a different engine for at least one folded descriptor (`Qwen-Image 2.1 VAE conv padding fold (NCHW) fast path is not bit-exact ... falling back` on the first latent, where the largest convs decided correctly), while SM86 and SM120 pick the same engine for both descriptors, which is why 300 latents locally never showed it. The eager decode was reproducible on both runs (the test checks that before asserting), so this was not a nondeterministic engine either; the self-repeat check from `d63f6f1e0e` guards a different failure and stays.

Measured on SM86 as a proxy for "cuDNN picked another engine" (padded conv run by a different engine than the folded conv, no bias, 100 random inputs per site):

| output elements per conv | mean differing bf16 elements | P(bit-identical on one input) |
|---|---|---|
| 512 to 8k (4x4 test latent, small sites) | 0.0 to 1.7 | 0.16 to 1.00 |
| 16k to 32k (4x4 test latent, largest sites) | 0.9 to 3.4 | 0.02 to 0.42 |
| >= 262k (new test latent, every site) | >= 99 | 0 in all trials |
| 4.7M (real decoder, C=1152 at a 64x64 latent) | 4036 (cuDNN NHWC vs NCHW engines) | 0 |

**Fix (`daafd5dee2`).**
- `FoldedPadConv2d` only attempts the fold when the conv output has at least 2^18 elements (`_FOLD_MIN_OUTPUT_ELEMENTS`); below that the padded conv runs, where the pad copy costs nothing. For this decoder every fold site has K >= 576, so above the floor the expected number of differing elements between two engines is >= 20 and one match decides. At 1024x1024 every site has >= 4.7M elements, so the production path is unchanged; images of 256x256 and below keep the padded conv at their early sites.
- The lossless test decodes a 64x64 latent (1024x1024 output) of a toy decoder with the real latent channel count (`z_dim=64`, decoder width 1/9 of the real one), so every fold site is above the floor and decides on first sight (1.5 s on an RTX 3080 Ti). The assertion is unchanged: `torch.equal` against the eager decode on a second latent after all gates have decided, with the eager decode checked for reproducibility first.
- The per-family isolation you asked for is in the failure message now, so it lands in the CI log without a session on the runner: eager and optimized repeatability on the second latent, the first decoder blocks whose outputs differ (module names line up between the two models), and the decode repeated on fresh optimized copies that take their first sight on the first latent with one family disabled at a time (padding fold, norm+SiLU tail, bias+residual add, upsampler bias). Validated locally against a kernel made exact on first sight and one bf16 ulp off afterwards: it names the bias+residual family and `decoder.mid_block.resnets.0` as the first divergent block. To see the isolation for the 4x4 configuration on an H100, run the test at `f04d0b4962` (the commit before the floor).
