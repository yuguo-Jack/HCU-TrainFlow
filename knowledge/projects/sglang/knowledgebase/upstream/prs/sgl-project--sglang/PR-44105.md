# [Feat] comfyui: Opt-in native worker batching (Z-Image, FLUX.1)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44105) · state: open · merged: False

## Original PR description

Refs #43411 (first model; the RFC stays open for the rest)

## Summary

ComfyUI calls the DiT with CFG cond/uncond (and `batch_size` > 1) as one batch. Since #43492 the executor sends one worker request per row. This adds opt-in batching, following the maintainer suggestion on the issue: per-row stays the default, batching is a user option, and it is only allowed for models checked against the per-row output.

- New `SGLDOptions.native_batching`: `off` (default, unchanged per-row path), `cfg_only` (one request per image holding its cond/uncond rows, so memory grows with CFG but not with `batch_size`), or `full` (one request for the whole batch).
- Each row's timestep goes in a new `Req.comfyui_row_timesteps` field; `req.timesteps` stays the one-step schedule the denoising loop walks. `DenoisingStage.expand_timestep_before_forward` uses the per-row timesteps instead of repeating one value.
- Out of memory: if the worker reports a CUDA OOM, the executor logs a warning and retries the step one mode lower (`full`, then `cfg_only`, then per-row) and stays there for the rest of the sampler run. A new run tries the chosen mode again. An OOM on the per-row path is raised as before.
- Per-row fields must have exactly B rows, and `cfg_only` needs ComfyUI's `cond_or_uncond` to find the chunks. Anything that does not match is rejected with a clear error, never split by guessing.
- `native_batching` other than `off` is refused at load time for models that are not verified and for more than one GPU. Verified so far: `lumina2` (Z-Image) and `flux` (FLUX.1, checked with FLUX.1-schnell).
- Z-Image adapter: keeps the `[B, L, D]` context and sends one text length per row (ComfyUI gives every row the same context length, same as the per-row path).
- Flux adapter: sends one CLIP and one T5 length per row (the worker checks them against the batch size). The worker takes one guidance value per request, so Flux rows with different guidance values are refused in a batch with a clear error; the per-row path still sends each row's own guidance.

## Tests

`test/unit/test_comfyui_native_batching.py` (new, 20 tests, CPU): Flux batch sends one text length per row and keeps row order; Flux rows with different guidance are refused when batched and keep their own guidance per-row; `full` is one request with per-row timesteps in order; `cfg_only` is one request per image with that image's cond and uncond rows, timesteps and options, and rows come back in ComfyUI's order; `cfg_only` with one image is one request; `cfg_only` without the cond chunks is rejected; OOM steps `full` down to `cfg_only`, or to per-row, stays there for the run and resets on the next run; OOM on the per-row path is raised; worker OOM errors are recognised and other errors are not; default still one request per row; batch of one unchanged; mismatched rows rejected; worker per-row timesteps; unverified models, multi-GPU and unknown modes refused; options node default. The rest of `test/unit/test_comfyui_*.py` passes unchanged (the 2 `test_comfyui_profile.py` failures also happen on main in my CPU environment, missing `uvicorn`). ruff, isort and codespell are clean.

## GPU check: Z-Image

Real SGLD worker in ComfyUI mode with Tongyi-MAI/Z-Image-Turbo on one L40S, driven through the real `ZImageExecutor` with ComfyUI-shaped inputs (bf16 latents and context, fp32 timesteps, random tensors; only ComfyUI itself is left out).

### Memory and speed per mode

`batch_size` 2 with CFG (4 rows). Peak GPU memory while sampling; the weights take 13.8 GiB, so the extra column is the activation memory. Modes ran smallest first.

| | worker calls / step | peak GiB | extra over weights | ms / step |
|---|---|---|---|---|
| 1024px, off | 4 | 14.46 | 0.64 | 1167 |
| 1024px, cfg_only | 2 | 15.33 | 1.51 | 1219 |
| 1024px, full | 1 | 16.83 | 3.01 | 1269 |
| 2048px, off | 4 | 16.75 | 2.93 | 6842 |
| 2048px, cfg_only | 2 | 19.53 | 5.71 | 7152 |
| 2048px, full | 1 | 25.54 | 11.72 | 7196 |

At 2048px `cfg_only` takes about 2x the per-row activation memory and `full` about 4x, as expected for CFG and for `batch_size` 2 on top of it. At 1024px the per-row figure is small enough that the ratios are rough.

Earlier runs at other sizes (ms per step, `full` vs per-row):

| | per-row | full |
|---|---|---|
| 512px, B=2 | 155 | 142 (8% faster) |
| 512px, B=4 | 312 | 284 (9% faster) |
| 1024px, B=2 | 600 | 629 (5% slower) |
| 1024px, B=4 | 1220 | 1305 (7% slower) |

Batching helps when one row does not fill the GPU and costs a little at 1024px and above on an L40S, which is another reason to keep it opt-in.

### Out-of-memory fallback

Fresh worker, 2048px, 4 rows. After a per-row step, the test process filled the GPU until 4.2 GiB was free (per-row needs 2.8 GiB on top of the weights), then ran a step with `full`:

- `full` ran out of memory, `cfg_only` ran out of memory, and the step finished per-row. Two warnings were logged: `...native_batching=full; using cfg_only...` and `...native_batching=cfg_only; using off...`.
- The result matched the per-row output exactly (relative L2 0.0). That step made 6 worker calls (the 2 failed attempts plus 4 per-row).
- The next step in the same run went straight to per-row (4 calls).
- After freeing the memory, a new run with `full` made 1 call again.

The worker kept running after both OOMs.

### Accuracy

Per-row reruns are bit identical. Relative L2 against the per-row output; the right column nudges the per-row inputs by about one bf16 rounding step (2^-8 relative) to show the noise level:

| case | batched vs per-row | nudged per-row vs per-row |
|---|---|---|
| CFG pair, B=2, 1024px (full) | 3.7% | 6.3% |
| per-row timesteps, B=3, 1024px (full) | 3.3% | 9.3% |
| batch 2 x CFG, B=4, 1024px (full) | 3.2% | 4.6% |
| 8-step Euler trajectory, B=2 (full) | 19.6% | 19.0% |
| B=4, 1024px, cfg_only / full | 3.07% / 3.06% | |
| B=4, 2048px, cfg_only / full | 3.00% / 3.00% | |

So the batched vs per-row gap is within bf16 noise for this model on these inputs. With two identical rows in one batch, the two outputs are bit identical (max abs 0.0), so rows do not leak into each other; the gap is the bf16 kernels rounding differently at another batch size. An fp32 reference was not possible: the fused RoPE kernel (`apply_rope_pos_ids_cos_sin_cache`) only dispatches half types.

Each row uses its own timestep: in a batch with timesteps 0.9 / 0.5 / 0.1, each batched row is 0.4 to 0.9 max abs from a single-row call at its own timestep and 4.7 to 6.4 from a call at a different timestep.

## GPU check: FLUX.1-schnell

Same setup with black-forest-labs/FLUX.1-schnell through the real `FluxExecutor` (T5 context 256 tokens, pooled CLIP vector, random tensors) on one L40S.

Memory and speed, `batch_size` 2 with CFG (4 rows); the weights take 24.1 GiB:

| | worker calls / step | extra over weights | ms / step |
|---|---|---|---|
| 512px, off | 4 | 0.28 GiB | 432 |
| 512px, cfg_only | 2 | 0.46 GiB | 407 (6% faster) |
| 512px, full | 1 | 0.82 GiB | 394 (9% faster) |
| 1024px, off | 4 | 0.84 GiB | 1450 |
| 1024px, cfg_only | 2 | 1.48 GiB | 1514 (4% slower) |
| 1024px, full | 1 | 2.69 GiB | 1575 (9% slower) |

Accuracy at 1024px (relative L2 against per-row; per-row reruns are bit identical; nudged = per-row inputs nudged by about one bf16 rounding step):

| case | batched vs per-row | nudged per-row vs per-row |
|---|---|---|
| CFG pair, B=2 (full) | 0.25% | 0.33% |
| batch 2 x CFG, B=4 (full / cfg_only) | 0.26% / 0.26% | 1.02% |
| per-row timesteps 0.9 / 0.5 / 0.1, B=3 (full) | 0.29% | 0.91% |
| duplicate rows, B=2 (full) | 0.26% | 0.52% |
| 4-step Euler trajectory, B=2 (full) | 0.13% | 0.40% |

- Duplicate rows in one batch give bit identical outputs (max abs 0.0).
- Each row uses its own timestep: against a single-row call, max abs 0.25 to 1.0 at its own timestep and about 4.0 at another one.
- One row looked off at first: the t=0.9 row of the 0.9 / 0.5 / 0.1 batch is 4.1% from per-row while the others are about 0.27%. That row's output is small (norm 582 vs 8,814 and 38,297), and nudging the per-row inputs moves that same row by 10% to 15% (3 seeds), so it is within noise. With both rows at t=0.9 the gap is 0.27% vs 0.5% to 0.95% for the nudge.

FLUX.1-dev uses the same DiT plus a guidance embedding, which gets one value per request; batches with mixed guidance are refused as above.

## Limitations

- Verified on one GPU for Z-Image and FLUX.1-schnell only; other models get a clear error unless `native_batching` is `off`. Each further model needs its own GPU comparison against per-row output. FLUX.1-dev was not run separately.
- Inputs were random tensors, not real prompts.
- Reference-latent and ControlNet rows do not apply to Z-Image, so they are not covered here.
- The OOM fallback depends on the worker reporting the error text "out of memory"; a hard crash of the worker process is not recovered by it.
