# feat(gateway): support /abort_request in sgl-model-gateway

[Upstream PR](https://github.com/sgl-project/sglang/pull/31685) · state: closed · merged: False

## Original PR description

Closes #6531.

## Motivation

`/abort_request` exists on the sglang HTTP server but not on `sgl-model-gateway`, so multi-worker deployments behind the router cannot abort an in-flight request from outside. Two prior attempts (#6790, #20160) were abandoned (the former targeted the old `sgl-router`; the latter got no review in 4 months).

## Modifications

- Add `abort_request` to `RouterTrait` (default 501), `RouterManager`, the regular HTTP `Router`, and a `POST /abort_request` handler in `server.rs`.
- Fan out to **all** workers and wait for every one (not first-success): the router does not track which worker owns a rid, so the abort must reach all of them; a success on any worker wins over failures. The worker-side `/abort_request` matches rid by `startswith` and is a no-op for rids it does not own, so fan-out is safe.
- Generalize `route_simple_request` with an optional JSON body and a `wait_all` flag (it previously dropped the body). `cancel_response`/`get`/`delete` keep their first-success behavior; `abort_request` uses `wait_all`.
- PD/gRPC routers fall back to 501 — PD needs the abort fanned across prefill+decode, left to a follow-up.

## Tests

- `test_abort_request_fans_out_to_all_workers_with_body` — both workers receive the abort, body intact.
- `test_abort_request_no_workers_returns_unavailable` — 503 when no workers.
- `test_abort_request_success_wins_over_partial_failure` — one worker 500, one 200; gateway returns 200 (guards wait_all success-over-failure).

File: `sgl-model-gateway/src/routers/router_manager.rs` · line 659

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Since the gateway does not track which router or worker owns a given `rid`, selecting a single router via `select_router_for_request(headers, None)` can lead to a situation where the abort request is sent to the wrong router (e.g., selecting the PD router when the request is running on the Regular router, or vice versa). Furthermore, if the selected router does not implement `abort_request` (returning `501 Not Implemented`), the abort will fail even if another router could have successfully handled it.

To ensure the abort request actually reaches the correct worker across any active router, `RouterManager::abort_request` should fan out the abort request to all registered routers concurrently, and return a success if any router succeeds (ignoring `501 Not Implemented` or other failures unless all of them fail).

```rust
    async fn abort_request(&self, headers: Option<&HeaderMap>, body: &Value) -> Response {
        let routers: Vec<_> = self.routers.iter().map(|r| r.value().clone()).collect();
        if routers.is_empty() {
            return (
                StatusCode::NOT_FOUND,
                "No router available to abort request",
            )
                .into_response();
        }

        let mut futures = Vec::new();
        for router in routers {
            let headers = headers.cloned();
            let body = body.clone();
            futures.push(async move {
                let res = router.abort_request(headers.as_ref(), &body).await;
                (router.router_type(), res)
            });
        }

        let results = futures_util::future::join_all(futures).await;
        let mut first_success: Option<Response> = None;
        let mut last_error: Option<Response> = None;

        for (_router_type, response) in results {
            if response.status().is_success() {
                if first_success.is_none() {
                    first_success = Some(response);
                }
            } else if response.status() != StatusCode::NOT_IMPLEMENTED {
                last_error = Some(response);
            }
        }

        if let Some(success) = first_success {
            success
        } else if let Some(err) = last_error {
            err
        } else {
            (
                StatusCode::NOT_IMPLEMENTED,
                "Abort request not implemented by any available router",
            )
                .into_response()
        }
    }
```

- CNSeniorious000 · comment · 2026-07-19T01:49:08Z · [source](https://github.com/sgl-project/sglang/pull/31685#discussion_r3609594340)

File: `sgl-model-gateway/src/routers/router_manager.rs` · line 659

Keeping the current single-router delegation — router-level fan-out would be redundant here.

The HTTP regular router's `abort_request` already fans out to **every** worker via `worker_registry.get_all()` (no type/mode filter), and the worker-side `/abort_request` matches `rid` by `startswith` (a no-op for rids it doesn't own), so fanning to all workers is safe and already reaches PD prefill/decode workers. Fanning out to all 5 IGW routers would be wasted work: only `HTTP_REGULAR` overrides the trait default — `GRPC_REGULAR`/`HTTP_PD`/`GRPC_PD`/`HTTP_OPENAI` all return 501.

`abort_request` also follows the established control-plane convention: `cancel_response` and `get_response` use the identical `select_router_for_request(headers, None)` pattern. Changing only `abort_request` to fan out to all routers would break that consistency.

The real gap you're pointing at — IGW mode with PD-only workers (or `x-prefer-pd: true`) selecting `HTTP_PD` → 501 — is genuine, but it's the documented follow-up, not a regression: the trait doc states "Only the regular HTTP router implements this; PD/gRPC fall back to 501 (PD needs the abort fanned across prefill+decode — follow-up)." Issue #6531 is single-router mode (`enable_igw=false`), where `select_router_for_request` returns the default router directly, so the gap doesn't manifest. When the PD/gRPC follow-up lands, the minimal fix is to delegate `RouterManager::abort_request` directly to `router_ids::HTTP_REGULAR` (always registered in IGW) — not to fan out to all routers.
