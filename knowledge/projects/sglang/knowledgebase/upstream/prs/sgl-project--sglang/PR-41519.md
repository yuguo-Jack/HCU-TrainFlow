# [AMD] Qwen3-Next: fused QK Gemma RMSNorm + partial RoPE on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/41519) · state: closed · merged: False

## Original PR description

## Motivation

Qwen3-Next full attention on ROCm still prepares Q, K, V, and the output gate as separate steps, on each of the 12 full-attention layers (every 4th of 48):

```
split packed Q/gate/K/V -> Gemma RMSNorm(Q) -> Gemma RMSNorm(K) -> partial RoPE
```

Qwen3.5 already fuses the Gemma norm (and, on CUDA, the RoPE). `qwen3_next.py` never calls that path. At TP4 the local packing is 4 query heads, 1 KV head, head dim 256, rotary dim 64, so the packed width is 2560.

This wires three shape-specialized prologues into `forward_prepare_native` and picks one from the token count. The KV-cache write stays on `RadixAttention`. The fused kernels are launched with the cache store compiled out, so they return Q, K, V, and gate and do not touch the cache.

This is a different site from #39140 (all-reduce + residual Gemma RMSNorm + FP8 quant) and #39554 (GDN decode). It runs after `qkv_proj` on the full-attention layers only.

## Modifications

New, under `python/sglang/kernels/ops/attention/qwen3_next_prologue/`:

* `attention_prologue_m64.py` — Triton. Used for M ≤ 8192.
* `attention_prologue_m128_m256.py` — Gluon. Used for 8192 < M ≤ 24576.
* `attention_prologue_prefill_1024_32768.py` — Gluon. Used for 24576 < M ≤ 32768.
* `__init__.py` — the token-count dispatch. `store_kv` is always false on this path.

Modified:

* `srt/models/qwen3_next.py` — `Qwen3HybridAttentionDecoderLayer.forward_prepare_native` tries the fused prologue before the stock split / Gemma RMSNorm / RoPE sequence. The NPU prepare is unchanged.

`m1` and `decode` specializations are not included. On the kernel sweep below they are slower at every measured M.

## Scope and fallback

ROCm gfx95 only, and only the TP4 full-attention contract: HIP, BF16, `attn_output_gate`, head dim 256, rotary dim 64, 4 local query heads, 1 local KV head, packed width 2560, eps `1e-6`.

| M | kernel | if that kernel cannot run |
|---|---|---|
| 1–8192 | m64 (Triton) | stock prepare |
| 8193–24576 | m128 (Gluon) | stock prepare |
| 24577–32768 | prefill (Gluon) | stock prepare |
| anything else | stock prepare | |

Gluon is probed at runtime and is not pinned. If `triton.experimental.gluon` cannot be imported, M above 8192 stays on the stock prepare and m64 still runs. One log line on first engage, and one if Gluon is missing.

`SGLANG_DISABLE_QWEN3_NEXT_QK_NORM_ROPE=1` forces the stock prepare.

**CUDA and every non-gfx95 platform keep the existing prepare.** The new call is reached only through the HIP + gfx95 predicate.

## Accuracy Tests

Unit test, no server. Q, K, gate, and V against a PyTorch reference of the stock sequence (deinterleave, Gemma RMSNorm `(1 + weight) * rsqrt(mean(x^2) + eps)`, partial NeoX RoPE of dim 64), at M in `{1, 8192, 8193, 24576, 24577, 32768}`:

```
PYTHONPATH=python python -m pytest -q test/registered/kernels/ops/attention/test_qwen3_next_qk_norm_rope.py
```

8 passed. Sentinel KV caches passed into the prologue are unchanged. `STORE_KV=False` matches `STORE_KV=True` on Q, K, and gate for a small M, on m64 and, when Gluon imports, on m128 and the prefill kernel.

GSM8K is not in this PR. It should be run before merge, same protocol as #39140 / #39554: 1319 questions, 3 runs per arm, Qwen3-Next-80B-A3B-Instruct-FP8, TP4, FP8 KV.

## Speed Tests and Profiling

Dispatch follows a kernel-latency sweep of the five prologue candidates (lower is better). m64 wins from M = 1 through 8192 (about 26–27). m128 wins at 12288, 16384, and 24576 (30.6, 30.9, 39.9). The prefill kernel wins only at 32768 (47.0), where m64 has climbed to 109 and m128 to 62.

With `--chunked-prefill-size 16384`, the usual large prefill chunk is 16384 tokens, which is the m128 region. Decode batch sizes up to the default graph cap of 64 are inside the m64 region. M = 32768 is outside that chunk cap, so the prefill kernel runs only if the chunk size is raised.

End-to-end output throughput and TPOT are not in this PR. A serving sweep at concurrency 1 / 8 / 32 / 64, unprofiled, plus a kernel trace of the two Gemma RMSNorms and RoPE before and after, is the remaining measurement.
