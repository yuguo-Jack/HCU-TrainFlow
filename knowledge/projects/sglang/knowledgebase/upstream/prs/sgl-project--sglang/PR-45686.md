# [Fix] scheduler: Fire priority preemption when KV runs out, and keep retracted KV behind a flag

[Upstream PR](https://github.com/sgl-project/sglang/pull/45686) · state: open · merged: False

## Original PR description

## Motivation

`--enable-priority-scheduling` documents preemption: a request whose priority exceeds a running request's by more than `--priority-scheduling-preemption-threshold` is meant to preempt it. The admission loop in `Scheduler._get_new_batch_prefill_raw` tries preemption in one situation only, when the running batch has reached its request cap. When the request does not fit because KV memory has run out, which `PrefillAdder.add_one_req` reports as `AddReqResult.NO_TOKEN`, the loop stops. On a server with the default request cap, memory is what runs out, so a higher-priority request waits behind lower-priority running requests until they finish, and the flag only orders the queue. We found this on the first run of a priority-based scheduler on Qwen3-8B: priorities changed every step and nothing was ever preempted.

The second change answers the TODO in `release_req`, "for preempted requests, we may want to insert into the tree". When a request is retracted or preempted, everything beyond its cached prompt prefix is freed, and its decoded tokens are recomputed when it comes back. `--preempt-keep-kv` inserts the request's KV, decoded tokens included, into the radix tree before its row is released, so the request resumes with a one-token prefill. Off by default.

## Modifications

- Preemption on NO_TOKEN. After `add_one_req` returns NO_TOKEN for a request that was not admitted, with preemption enabled, the scheduler calls `adder.preempt_to_schedule(req)`; if that released enough, it re-matches the request's prefix and calls `add_one_req` once more. The request-cap path is untouched; the threshold, the priority direction and the choice of victims are those of `preempt_to_schedule`, unchanged.
- Preempted requests were requeued silently. `_requeue_preempted` now counts them in the retraction metrics (`num_retracted_reqs_total` and the two token counters) before requeueing, since preemption releases KV the way a decode retraction does. The decode log line's `#retracted_reqs` is unchanged.
- `--preempt-keep-kv`: in `release_req`, `release_kv_cache` is called with `checkpoint=True` when the flag is set, the request will resume (`offload_kv`, which the PD true-retraction and the abort paths set to False), and the tree is not a Mamba tree. `checkpoint` inserts `full_untruncated_fill_ids[:owned_kv_len]` after `refresh_fill_ids` has appended the decoded tokens. The eviction that follows in `release_req` is unchanged.
- A row for the flag in `docs/docs/advanced_features/server_arguments.mdx`.

Default behaviour changes in one way: with priority scheduling on and preemption enabled, a request blocked by KV memory now preempts, as the flag says it should.

## Notes for reviewers

- NO_TOKEN also comes back after a successful admission: `add_one_req` returns `budget_state()` after admitting, and that is NO_TOKEN when the request just admitted spent the budget, a verdict about the next request. The retry is guarded by `added`, the same "last one in `can_run_list`" test the loop already uses for the Mamba slot cleanup. Without it the request is admitted twice; our first version did that and crashed once on a double release and once as a 27-token leak the memory audit caught.
- The prefix is re-matched after preemption because `release_req` evicts from the tree right away when the pool is short (`SGLANG_RETRACT_DECODE_STEPS` tokens per remaining request), which can drop the node `req.last_node` points to. The request-cap path already preempts before the prefix match; the retry keeps that order.
- The kept KV is inserted unlocked. The eviction right after retraction goes LRU-first, so the kept node is the last victim, and when nothing else is evictable it is dropped at once and the request recomputes as before: a best-effort keep. Cost per retraction: one tree insert (`checkpoint`: insert, prefix match, row rewrite), plus a host copy with HiCache write-through. The saving is the decoded tokens' prefill, about 200 tokens on average in the Mooncake trace, so in a prefix-caching engine this is a small gain; FastServe needed it because it had no prefix cache. Not measured in isolation: in the runs that used it, retraction never fired. It is here because it resolves the TODO in a few lines and is off by default.
- PD disaggregation: on a decode node `backup_kv_cache` still runs first when `offload_kv` is set; the tree insert is additional and the two were not tested together. The PD true-retraction path passes `offload_kv=False` and is unchanged.
- Mamba trees: the keep is skipped, since inserting an unfinished request forks its state and `release_kv_cache` asserts. Disabled radix cache: `checkpoint` returns at once, so the flag does nothing, as its help text says. SWA trees: untested with the flag.
- Tested: Qwen3-8B, TP 1, HiCache with write-through, overlap scheduler, page size 1, in every row of a 75-row Mooncake table and the rounds before it. Preemption fired where it was enabled: on a pinned 160k-token pool with threshold 0, 111 preemptions in one 0.4-minute window with 1.2M tokens of kept KV loaded back from host memory; with threshold 3 on a one-minute window, 38 preemptions. Those rows also show why preemption wants a high threshold: long answers' p99 JCT went from 196 s to 336 s at threshold 3, and the configuration we run elsewhere keeps `--disable-priority-preemption`. Not tested: TP above 1, DP attention, speculative decoding, PD disaggregation, Mamba, SWA models, page size above 1.

## Tests

- `test_higher_priority_request_preempts_for_kv` in `test/registered/scheduler/test_priority_scheduling.py`: on a 2,048-token pool with the request cap at 8, a priority-20 request arriving behind a running priority-0 request whose 1,500-token output is reserved must finish first. On main it finishes second.
- `test/registered/scheduler/test_retract_decode_keep_kv.py`: MMLU through `run_sgl_eval` under forced retraction (`SGLANG_TEST_RETRACT`) with the flag on and the strict memory check on, at the 0.64 threshold `test_retract_decode.py` uses for the same model; and a server-log check that every prefill after a retraction recomputes at most two tokens per resumed request, where it recomputes every decoded token without the kept KV.

Run on an A100 pod with this branch installed at upstream main `da7b97a737`, with ungated stand-ins for the gated CI models (Qwen3-1.7B for the 1B Llama, Qwen2.5-7B-Instruct for the 8B): `test_higher_priority_request_preempts_for_kv` passes on the branch and fails against main's sources, where the priority-20 request finishes second; `test_retract_decode_keep_kv.py` passes both cases, MMLU 0.742 with the flag under forced retraction (the 0.64 bar is `test_retract_decode.py`'s for this model class), and every resumed prefill after a retraction recomputed at most two tokens. CI has not run yet (draft).

## Accuracy Tests

Preemption on NO_TOKEN changes when a request runs, not what it computes. The kept KV is covered by the MMLU test above.

## Speed Tests and Profiling

No throughput claim. Preemption on NO_TOKEN runs only with priority scheduling and preemption enabled, when memory is the limiter, and its cost is the preemption itself; the numbers above are its effect on a trace where it fires often. The kept KV replaces a resume prefill of the decoded length by a one-token prefill at the cost of one tree insert per retraction, not measured in isolation.

CPU checks against the real `PrefillAdder` and `UnifiedRadixCache`; I did not run the two GPU server tests.

**1. NO_TOKEN preemption does not count held KV.** `preempt_to_schedule` sizes victims only by their remaining decode reservation (`schedule_policy.py:1684`), never by the KV that `release_req` frees. In the new test the shortfall is the victim's reserved 1,500-token `ignore_eos` output, which that loop does credit. When the pool is full of held KV, it refuses however many victims there are. Each running request holds 4,000 tokens; the new one needs ~2,064:

```
running=3: preempted=False, victims=0, freed_kv=0, needed~2064, rem_total_after=-81
running=100: preempted=False, victims=0, freed_kv=0, needed~2064, rem_total_after=-2700
```

Same on this head, main, and with #45813 merged; one release would make 4,000 available again. I can send a follow-up that credits the KV a victim's release returns or unlocks, on top of #45813, since both edit `preempt_to_schedule`.

**2. Nit.** The comment above `release_req` in `retract_decode` (`schedule_batch.py:3488`, "don't insert into the tree") now holds only with the flag off.

**3. Requeue order.** A retracted request is requeued at the tail. With the defaults (fcfs, LRU), every 32nd `calc_priority` call touches waiting prefixes head last (`schedule_policy.py:279`), so after that refresh the kept KV is the first waiting prefix LRU evicts. In a CPU probe with this branch's `release_req`, evicting 16 tokens after a refresh cut the retracted request's match from 27 to 0; two queued prompts kept theirs. Is the tail requeue intended with the flag on? Has the flag been run with HiCache write-back, where eviction moves the kept KV to host instead of dropping it (the case #26276 targeted)?
