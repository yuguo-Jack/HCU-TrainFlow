# [Fix] runtime: Run FlashInfer FP4 GEMM autotune for compressed-tensors NVFP4

[Upstream PR](https://github.com/sgl-project/sglang/pull/43464) · state: open · merged: False

## Original PR description

## Motivation

`should_run_flashinfer_autotune` only enables FP4 GEMM tactic autotune when `model_config.quantization` is `modelopt_fp4` or `modelopt_mixed`. compressed-tensors W4A4 NVFP4 checkpoints (for example llm-compressor output, `"format": "nvfp4-pack-quantized"`) go through `CompressedTensorsW4A4Fp4.apply_weights` → `fp4_gemm` → FlashInfer `mm_fp4`, exactly like modelopt NVFP4, but the gate skips them, so every FP4 GEMM in those models runs FlashInfer's default tactic. The startup log never shows `Running FlashInfer autotune` for such checkpoints.

## Modifications

- `flashinfer_autotune.py`: add `_model_uses_compressed_tensors_nvfp4(model)`, which returns true when any module of the loaded model carries a `CompressedTensorsW4A4Fp4` scheme, and treat `compressed-tensors` models that use it as FP4 models in the FP4 GEMM autotune gate. Checking the instantiated schemes (rather than the checkpoint's `format` string) also covers mixed-format checkpoints and ignored layers. The FP4 GEMM backend condition (`flashinfer_cutlass` / `flashinfer_cutedsl`) is unchanged.
- `test/registered/unit/model_executor/runner/test_flashinfer_autotune_gate.py` (new, CPU): the helper on models with no/other/NVFP4 schemes, and the gate for compressed-tensors NVFP4 (runs), compressed-tensors without NVFP4 (skips), compressed-tensors NVFP4 with a non-FlashInfer FP4 backend (skips), and modelopt FP4 (unchanged). On `main` without this change, the compressed-tensors NVFP4 gate test fails; with it, all 8 pass.

## Accuracy Tests

Autotune only changes the GEMM tactic. pplx-decider-v1.1-27b quantized to compressed-tensors NVFP4 with llm-compressor, served on `/v1/systemone`, 100 Belebele + 100 WinoGrande items compared with the checkpoint's BF16 reference implementation:

| | accuracy | top-1 agreement with BF16 | mean max\|Δp\| |
|---|---:|---:|---:|
| without this PR | 94.0% | 97.5% | 0.0283 |
| with this PR | 94.0% | 97.5% | 0.0283 |

## Speed Tests and Profiling

NVIDIA N1-Auto (sm_121, 20 SMs, FlashInfer 0.7.0.post1, CUDA 13.0, nightly `265efe5e`, whose `flashinfer_autotune.py` is identical to current `main`), same checkpoint, `--fp4-gemm-backend auto` (resolves to `flashinfer_cutlass`), `--linear-attn-prefill-backend flashinfer`, eager prefill.

Kernel level, `mm_fp4(backend="cutlass")`, down_proj shape (K=17408, N=5120):

| tokens | default tactic | autotuned tactic |
|---:|---:|---:|
| 377 | 1.240 ms | 1.005 ms (−19%) |
| 1007 | 3.343 ms | 2.895 ms (−13%) |

End to end, single `/v1/systemone` request, median latency. Prefill shapes are only covered with `SGLANG_FLASHINFER_AUTOTUNE_EXTEND=1`; the default decode-shaped pass tunes small token buckets only:

| prompt tokens | without this PR | with this PR + `SGLANG_FLASHINFER_AUTOTUNE_EXTEND=1` |
|---:|---:|---:|
| 1007 | 1181 ms | 1135 ms (−4%) |
| 4007 | 6336 ms | 5429 ms (−14%) |

Notes from the same hardware, for reviewers; neither is changed by this PR:
- A tuned `mm_fp4` call costs about 0.25 ms of host time versus 0.06 ms untuned (cache lookup), so with eager prefill on a weak host CPU, short prompts got slower (377 tokens: 483 → 679 ms). With a prefill CUDA graph (`--cuda-graph-backend-prefill breakable`) the overhead disappears and short prompts match the untuned latency (485 ms) while long prompts keep the gain (4007 tokens: 5471 ms).
- On sm_121 the tactics tuned for the 128/256/512-token buckets were slower than FlashInfer's default for requests mapping into them (147 tokens: 403 ms tuned vs 347 ms default); buckets from 768 tokens up were faster.
