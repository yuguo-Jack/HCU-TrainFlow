# Query free device memory through the active accelerator in triton_load_watch

[Upstream PR](https://github.com/sgl-project/sglang/pull/38263) · state: open · merged: False

## Original PR description

## Motivation

`triton_load_watch` warns when Triton loads a kernel specialization onto the device *after* serving started. A rare batch-size bucket or a new speculative draft length can first appear in the middle of serving. The engine's pool can leave almost no headroom outside the caching allocator. The load can then stall serving, or fail outright where the allocation cannot be satisfied.

On XPU, NPU, MUSA and HPU the low-memory warning could never fire. The base code queried memory only under `torch.cuda.is_available()`:

```python
    free_gb = None
    if torch.cuda.is_available():
        try:
            free_gb = get_available_gpu_memory(
                "cuda", torch.cuda.current_device(), empty_cache=False
            )
        except RuntimeError:
            logger.debug("Unable to query free device memory", exc_info=True)

    should_crash = envs.SGLANG_CRASH_ON_TRITON_LOAD_AFTER_READY.get()
    if not should_crash and (
        free_gb is None or free_gb >= envs.SGLANG_TRITON_LOAD_WARNING_THRESHOLD_GB.get()
    ):
        return
```

On XPU, NPU, MUSA and HPU, `free_gb` stays `None`, so the `free_gb is None` condition returns before the code builds the warning. The diagnostic is silent on these accelerators. It is also silent on CUDA and ROCm when the memory query fails, which is the case most worth surfacing. When the old warning did fire, its text named one runtime and one failure: *"Pre-load it during engine init to avoid CUDA OOM."*

Evidence that the warning is silent on XPU, NPU, MUSA and HPU: on the base commit, only the `torch.cuda.is_available()` branch assigns `free_gb`. The PR attaches no live XPU run that shows the base commit staying silent (see the limits below).

## Modifications

Resolve the device through `torch.accelerator` and make the text accelerator-neutral:

- `_free_device_memory_gb()` takes the device **type** and its **index** from `torch.accelerator`, returning `None` when there is no accelerator at all;
- the warning names the serving stall the condition actually produces instead of "to avoid CUDA OOM" (across three XPU sweep logs the check recorded 427 late device-loads, 104 of 126 in one sweep under 0.04 GiB free, none of which raised an out-of-memory error), and the module docstring no longer describes the load as `cuModuleLoadData` unconditionally;
- an unknown reading now warns **once per process** rather than returning silently, so a query that genuinely fails is visible without repeating on every kernel load;
- the code absorbs only `RuntimeError`. `get_available_gpu_memory` raises `ValueError` for an unrecognised device type (`common.py:539-543`). That is a broken contract, so the error still propagates and the code does not flatten it into "unknown".

**One subtlety worth flagging, because it was a real bug in the first draft of this change.** Taking the type from `torch.accelerator` but the index from a bare `torch.get_device_module().current_device()` mixes two different resolution paths, and they disagree. `current_accelerator()` reports the compiled-in accelerator; `torch.get_device_module()` with no argument goes through `torch._C._get_accelerator()`, which is availability-aware. With an XPU build and no visible devices:

```
torch                                         : 2.13.0+xpu
torch.xpu.device_count()                      : 0
torch.accelerator.current_accelerator()       : xpu
torch._C._get_accelerator()                   : cpu      <- what get_device_module() uses
torch.get_device_module(accelerator)          : torch.xpu
```

So the index arrives as the string `"cpu"` while the type is `"xpu"`, and `get_available_gpu_memory("xpu", "cpu", ...)` hits `assert gpu_id < num_gpus`:

```
BEFORE-FIX raised: TypeError: '<' not supported between instances of 'str' and 'int'
```

That is an unhandled `TypeError` escaping the Triton kernel-load hook. Taking the index from `torch.accelerator.current_device_index()` makes the two consistent. That call raises `RuntimeError` in the same situation, and the existing handler absorbs it:

```
WARNING:sglang.srt.utils.triton_load_watch:Triton kernel 'probe' device-loaded after
serving started (free device mem: unknown). Late loads run inside the scheduler loop
and stall serving when memory is tight; pre-load it during engine init.
AFTER-FIX: returned normally
```

On the API surface: `torch.accelerator.current_accelerator` and `current_device_index` both exist on the pinned torch (`pyproject.toml:78`, `torch==2.11.0`). The check ran on 2.11.0+cpu, where `current_accelerator()` returns `None` on a CPU-only build. The `is None` guard handles that case. `python/sglang/test/test_utils.py:2632` already calls `torch.accelerator.device_count()` unguarded, so this is not a new dependency.

**Behaviour by build.** The table compares the base commit (`9fea3e9bb2`) with this branch. It comes from reading `triton_load_watch.py` at both commits.

| torch build | base | this branch |
| --- | --- | --- |
| CUDA, memory query works | Reads free memory and warns below `SGLANG_TRITON_LOAD_WARNING_THRESHOLD_GB`. | Same reading, same threshold, same `get_available_gpu_memory("cuda", ...)` branch. Only the warning text changes. |
| CUDA, memory query raises `RuntimeError` | Logs "Unable to query free device memory" at debug level and returns. No warning. | Logs the same debug line, then warns once per process with "free device mem: unknown". Later loads with an unknown reading stay silent. |
| ROCm | `torch.cuda.is_available()` is true with a visible GPU, so the query takes the `cuda` path as on CUDA. | `current_accelerator()` should report type `cuda`, so the path and the changes match the two CUDA rows. Not run on ROCm. |
| CPU-only | `torch.cuda.is_available()` is false. Returns with no log and no warning. | `current_accelerator()` returns `None`, so the first late load warns once per process with "free device mem: unknown". |

In crash mode (`SGLANG_CRASH_ON_TRITON_LOAD_AFTER_READY=1`), both commits raise `RuntimeError` on every late load. Only the message text differs.

The hook runs only when Triton loads a kernel after serving starts. The CPU-only row therefore applies only if a CPU-only build reaches such a load.

On this branch, a CUDA build with no NVIDIA driver takes the failing-query path. On torch 2.14.0+cu130 with no NVIDIA driver, `current_accelerator()` returns `cuda` and `current_device_index()` raises `RuntimeError`. The base commit returns early in that case, with no log, because `torch.cuda.is_available()` is false.

**Cost.** On XPU, NPU, MUSA and HPU, the change adds one memory query per *late* kernel load, where previously there were none. Kernel loads after serving starts are rare by definition, and the hook already ran on every one of them.

## Limits of the evidence, and what to check hardest

- **The pre-existing CUDA test was not run.** `test/registered/unit/utils/test_triton_load_watch.py` is `register_cuda_ci(est_time=5, stage="base-b", runner_config="1-gpu-small")`. It needs a real GPU and a live Triton run, and no CUDA hardware was available here. The file patches `torch.cuda.mem_get_info` and asserts that `"free device mem"` appears in the warning. Both still hold on the new path by reading, but that is reasoning, not a run. It is the check to insist on.
- **No live XPU reproduction.** The warning fires only when a Triton specialization first device-loads after `mark_serving_started()`. That needs a workload that reaches a new bucket in the middle of serving. That was not staged. The evidence here is code reading plus the two container probes above.
- **No test covers the new accelerator path on `intel_dev`.** The existing `test_triton_load_watch.py` is CUDA-only, and no CI lane runs XPU tests on `intel_dev`.
- **The warn-once state is process-global.** That is deliberate (one warning per process for an unknown reading), but it means a long-lived process that recovers from a transient query failure will not warn again.
- CI cannot run the tests on this PR. The maintenance gate needs a `MIN_BASE_SHA` that `intel_dev` does not contain. The two failed runs in the block below stop at that gate. `intel_dev` merges do not need green CI.

One of several small, independent changes split out of a larger DeepSeek-V4 XPU enablement branch. This one is not XPU-specific. By code reading, it fixes the diagnostic on NPU, MUSA and HPU as well as XPU. It depends on none of the others.

Thanks for pushing on the OOM question! I checked the run logs and found that the results are narrower than the original PR description, so I've reworded the patch to match.

**No OOM crash.** Across all captured server logs from the XPU DSv4 sweeps there is not one out-of-memory error, and the DSv4 services running right now are clean too. If the bar is "has a Triton load ever crashed us", the answer is no.

**What we do observe is the precondition, constantly, and a latency stall.** With this patch applied, three XPU sweep logs recorded 427 late device loads. In one sweep, 104 of 126 reported under 0.04 GiB free and 21 reported exactly 0.00 GiB — the condition the existing threshold exists to flag.

It cost real time. In `r1-sweep-native/concurrency_8`, 8 of 64 requests took ~25 s to first token against ~2.2 s for every other wave (p75 2568 ms, p90 24987 ms). From the server log: an uncompiled `_paged_mqa_logits_kernel` met a new prefill shape, ~4.3 s of JIT, then ~18–20 s of device load at ~0 GiB free, scheduler blocked throughout. Decode ITL was unaffected.

**The part that bears on this PR:** in the unpatched baseline that same 25 s window is 20 seconds of complete log silence. The compile warning fires, because it never consults memory, but the device-load line is exactly the half that returns early off CUDA — so the expensive part is invisible. We could only attribute the stall because a patched arm existed to compare against. It also skewed that benchmark, moving the c=8 throughput comparison by ~2.8 points and making a "widening TTFT advantage" look real when the median gap is flat at ~12%.

So the framing was wrong and I've fixed it in dfd19bd. The docstring now gives both outcomes in the order they are actually met — a slow load that stalls serving, then outright failure where the allocation cannot be satisfied — and the warning names the stall rather than an OOM:

```
Triton kernel 'probe' device-loaded after serving started (free device mem: unknown).
Late loads run inside the scheduler loop and stall serving when memory is tight;
pre-load it during engine init.
```

On the test file — renamed to `test_triton_load_watch_dispatch.py` in 5a7f50b, with a module docstring recording why the split exists. Joining the existing file was not an option: `test_triton_load_watch.py` is `register_cuda_ci`, launches a real Triton kernel on `device="cuda"` and imports `triton`/`triton.language` at module scope, so it cannot be collected on the CPU runner. The old `_unit` suffix said none of that, which is a fair thing to have flagged. 

Still happy to drop the file altogether if you'd rather it went.
