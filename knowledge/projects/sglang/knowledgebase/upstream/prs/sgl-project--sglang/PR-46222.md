# [Fix] scheduler: Keep the paged intake limit admittable on an empty KV pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/46222) · state: open · merged: False

## Original PR description

## Motivation

With `page_size > 1`, a prompt can pass intake and then never be admitted, even on an empty KV pool. The request sits at the head of the waiting queue and nothing behind it runs.

`TpModelWorker.get_worker_info` bounds requests by `kv_capacity - 1` (then `- 5` for `max_req_input_len`). Admission is stricter: `PrefillAdder` rounds the prompt up to whole pages and reserves one more page (`per_req_token_overhead`, the `+ page_size` in `PrefillBudget.reserve`), and `init_req_max_new_tokens` clamps with the same page. So a prompt within a page of the limit is accepted, gets `max_new_tokens` clamped to 0, and is refused by every prefill pass. `BaseTokenToKVPoolAllocator.max_new_tokens_for_memory` sees the negative budget but returns 0 instead of `None`, so intake does not abort it either.

`--allow-auto-truncate` makes this easy to hit: an over-long prompt is truncated to exactly `max_req_input_len`, which with `page_size > 1` is always inside that gap. The bound only matters when the KV pool is smaller than the context length, which #42976 now warns about at startup ("long requests will be refused or truncated at serving time").

This is the symptom of #28530. That issue was closed as fixed by #25126, which aligned the `max_new_tokens` clamp; the intake limit was left at `kv_capacity - 1`. #29249 proposed tightening the limit in `validate_input_length` and was closed by the stale bot without review. This PR fixes it where the limit is computed, so every consumer of `max_req_input_len` (scheduler intake, `TokenizerManager`, DP controller, auto-truncation) gets the admittable value.

## Modifications

`TpModelWorker.get_worker_info`: the KV bound on `max_req_len` is `kv_capacity - page_size * shard_size` instead of `kv_capacity - 1`. One page per page-interleave shard matches what admission reserves (`init_req_max_new_tokens` already subtracts `page_size * (kv_shard_widening - 1)` plus the base page). With `page_size == 1` and one shard this is exactly the old `kv_capacity - 1`, so page-size-1 deployments see no change. With `page_size > 1` the limit drops by less than one page; prompts in that range could never run before.

## Tests

New CPU test `TestPrefillAdder.test_longest_accepted_prompt_fits_an_empty_paged_pool` in `test/registered/unit/managers/test_prefill_adder.py` (already in `base-a-test-cpu`). It takes `max_req_len` / `max_req_input_len` from the real `TpModelWorker.get_worker_info`, sizes the request with the real `Scheduler.init_req_max_new_tokens`, and admits a prompt of exactly `max_req_input_len` tokens (the auto-truncation target) through `PrefillAdder.add_one_req` on an empty pool, for `(page_size, kv_capacity)` in `(1, 256)`, `(16, 256)`, `(64, 512)`, `(64, 4096)`.

Scheduler-level check (CPU simulation, not an end-to-end server run): the real `Scheduler` with real pools, `UnifiedRadixCache` and `PagedTokenToKVPoolAllocator`, the model forward replaced by sampled random tokens; main is `f967418a35`. One request on an empty pool, `max_new_tokens` unset, every prompt length from 1 to the pool size:

| page_size | pool | never admitted (main) | never admitted (this PR) |
|---|---|---|---|
| 1 | 256 | 0 | 0 |
| 4 | 256 | 0 | 0 |
| 16 | 256 | 10 (prompts 240–249) | 0 |
| 64 | 512 | 58 (prompts 448–505) | 0 |

With `allow_auto_truncate=True`, over-long prompts are truncated to 250 / 506 tokens on main and never admitted for page 16 / 64; on this branch they are truncated to 235 / 443 and run. Page size 1 is admitted in both.

Random workloads through the same simulated scheduler (120 seeds; page size 4 / 16 / 64; 7 schedule policies; chunked prefill; aborts; 15% of prompts placed just under the intake limit): on main 74 seeds end with the waiting queue stuck and nothing running, all with page size 16 or 64; on this branch none do. The only other failure, one `Prefill out of memory` on this branch and two on main, is the chunked-continuation case #44823 / #45685 address.

The same gap also stalls a PD decode server. I drove the real `Scheduler` in decode mode with the fake transfer backend and the decode radix cache, on top of #46269, which fixes a separate decode-side reserve issue, with page sizes 1, 16 and 64 over 60 seeds. Without this change, 21 seeds stopped making progress, all of them with page size 16 or 64. Each time the head of the prealloc queue was a prompt that intake had accepted with `max_new_tokens` clamped to 0, whose page-rounded KV plus the pending token does not fit even an empty pool. With this change, all 60 seeds finished. The pools there are small (160–512 tokens).

Not tested: GPU, TP > 1, page-interleave sharding > 1 (derived from `init_req_max_new_tokens`, not measured), DP attention, speculative decoding, hybrid SWA / Mamba pools (their allocators override `max_new_tokens_for_memory`).
