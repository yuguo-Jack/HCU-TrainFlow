# [Feat] [AMD] minimax_m3: Extend mono decode kernels to TP2 and TP8 on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/44900) · state: open · merged: False

## Original PR description

## Motivation

PR #44319 (@zijiecode) added the MiniMax-M3 whole-layer fused decode kernel for
gfx950 at **TP4 only**. This PR extends it to **TP2 and TP8**, completing the
sub-node TP range for this model on MI355X.

It supersedes #44686, which carried the TP2 half alone. Everything there is
included here unchanged; #44686 is closed in favour of this one so the two
extensions review as a single coherent change (they share the TP-derivation
work, and splitting them meant the second PR could not state its own base).

**On placement:** @kevin-mii has pointed out that since #44353 landed, model
monokernels belong in `sgl-project/sgl-amd-mono` rather than here. That is
right, and we intend to land there, together with #44319 and @zijiecode. This
PR stays open as **draft** as the reviewable reference for the TP2/TP8 kernel
work while that port is coordinated — see "Porting to sgl-amd-mono" at the
bottom for the one framework gap that port runs into.

## What changes

`TP` is a build-time constant (`config.py`), so this is one parameterised
kernel, not three implementations. The bulk of the diff is deriving shapes from
TP that were previously TP4 literals, plus the per-TP defects that only surface
once you do.

**TP4 is byte-identical.** Every derived constant was checked against the
pre-change value at TP4 (`test_mono_m3_tp.py`), so the working TP4 build cannot
regress. This matters more than it sounds: TP4 at width 16 uses 163,664 B of a
163,840 B LDS budget — **176 bytes spare** — so any change that grows LDS at TP4
breaks it.

57 files, +10,858/−15. The TP8 half alone is 6 files, +429/−78.

### TP2: the problems that had to be solved

1. **LDS budget.** TP2 carries 32 q heads and `INTER=1536` against TP4's 16 and
   768, so a *smaller* TP buys *fewer* tokens per step. Two independent
   overflow carriers: the attention PV partials (scale with H) and the MoE
   down stage (scales with INTER). Fixed by staging attention as two 16-head
   passes; `MAX_WIDTH = 12` bounds the second.
2. **Per-head indexer selection.** At TP2 a rank holds its own *pair* of index
   heads, so index head *i* selects blocks for KV head *i*. The existing code
   refused `heads.count > 1` as context parallelism — but the counts coincide
   at 2 while the semantics do not. CP is not an alternative here: its peer
   exchange indexes up to peer 3, which does not exist in a 2-rank group.
   Added an explicit `IndexHeads.cp` flag and an own-pair selection mode.
3. **The 64-lane done-flag poll was a real defect, not just a limit.** The
   lane→task map encoded one K and one V head; at TP2 it polled the two K
   tasks and never the two V tasks, so the split stage could read stale V.
   Replaced with a multi-round poll (1 round and the original expression at
   TP4).
4. **The other-GEMV gate was the TP2 hang.** Those CTAs ran only under
   `long_step()` — a CP optimisation. Own mode reads every index head in every
   step, so head 1's rows were never written and every CTA spun forever.

### TP8: the problems that had to be solved

1. **H=8 thread map.** The split/merge stages assumed 16 heads per pass. At TP8
   a rank holds 8 query heads, so the original map wrote `sp_o` into the next
   partition — silent corruption, not a crash.
2. **Padded MoE scale stride.** aiter's `e8m0_shuffle` pads MXFP4 scale columns
   to a multiple of 8. At TP8 `INTER/32 = 12 → 16`, so the loader's view and
   the kernel's stride disagreed unless the padded stride is used.
3. **`SGLANG_AITER_K3_OPT=1` is required at TP8.** Without it the quark MXFP4
   loader pads `INTER = 3072/8 = 384` up to 512 and the kernel refuses to load.
   TP2 and TP4 are unaffected. This is a load-time refusal with a clear
   message, not a silent fallback.

## Known limitation, deliberately bounded

**TP8 does not take the narrow MoE path.** `MIN_WIDTH = 5` at TP8; steps below
that route to the module path via `srt/layers/mono/routing.py`, the existing
supported fallback.

Measured on an 8-rank decode graph capture: widths 16, 12 and 8 captured
cleanly, then width 4 took

```
Memory access fault ... on address (nil) / 0x1000 / 0x2000
```

on all eight ranks at once. Those are unpopulated pointers rather than an LDS
overflow, which is why the compile gate cannot see it — every TP8 width builds
clean at 1..16. Width 4 is the first below `layout.WIDE_FROM` (5 at TP8), i.e.
the first step on the narrow MoE path. That path has needed TP-specific repair
once before (it was sized by `HIDDEN` instead of `INTER`, which broke TP2 at
widths 3–4), so this is most likely the same class.

**The specific mechanism is not confirmed**, so `MIN_WIDTH` bounds the damage
rather than claiming a root cause. Reproducing it faults all eight ranks and
takes the node down, which is why it has not been chased further on shared
hardware. Fixing it would extend TP8 to the narrow widths where TP2 and TP4 see
their largest gains.

## Validation

**Unit:** `test_mono_m3_tp.py` parametrised over TP 2/4/8, GPU-free; TP4
constants verified byte-identical to pre-change.

**End-to-end**, MI355X 8×, `amd/MiniMax-M3-MXFP4`, a frozen 8-row
image+text sweep (ISL 256/1024/8192, concurrency 4/16/64/256):

| TP | rows | requests | memory faults |
|---|---|---|---|
| 2 | 8/8 | 1536/1536 | 0 |
| 4 | 8/8 | 1536/1536 | 0 |
| 8 | 8/8 | 1536/1536 | 0 |

The server emitted mono routing decisions at the expected widths in each case,
so the kernel demonstrably ran rather than silently falling back.

**Throughput**, mono vs the **same image** with `--layer-backend module` (so
only the backend differs; at TP8 `K3_OPT=1` is held constant on both sides
rather than being allowed to confound the result):

| TP | geomean output tok/s vs module | best row |
|---|---|---|
| 2 | +4.05% | c4 **+17.41%** |
| 4 | +10.66% | c4 **+25.39%** |
| 8 | +11.18% (all rows) / +9.42% (excl. seed 13) | — |

At TP8, `K3_OPT` alone (module→module) is +3.85%; the unconfounded
mono-vs-module figure above excludes it.

**Internal consistency check.** The `c4` row has a decode batch of 4, below
`MIN_WIDTH` at TP8, so mono provably *cannot* engage there — and at TP8 it
measures **+0.07%**. The one row where the kernel cannot run shows no change,
while rows that do reach it move by up to +24%. At TP2 and TP4, where narrow
widths do run, that same row is mono's *best* (+17.41% and +25.39%). That is
the clearest available evidence that the measured gains come from the kernel.

## Porting to sgl-amd-mono — one framework gap

Following the template in sgl-project/sgl-amd-mono#6, the M3 kernels map onto
`sgl_amd_mono/minimax_m3/{spec.py,gfx950/...}` without difficulty, with one
exception worth raising before the port rather than after.

`DeviceLimits.widths` is declared **per GPU type**, but this model's usable
width range is **per TP**:

| TP | usable widths | why the bound exists |
|---|---|---|
| 2 | 1 – 12 | LDS: width 15 reports 172,960 B against the 163,840 B limit |
| 4 | 1 – 16 | — |
| 8 | 5 – 16 | narrow MoE path faults on null pointers at width 4 |

These are different *kinds* of bound (a compile-time budget at the top, a
runtime defect at the bottom) but they share the problem: on gfx950 there is no
single `widths` tuple that is correct at all three TPs. The intersection,
5 – 12, *is* non-empty and would be safe — but it discards widths 1–4, which is
exactly where the gains are largest (the c4 row above: +17.41% at TP2, +25.39%
at TP4). So the union-by-intersection route costs roughly the entire benefit at
low concurrency.

GLM #6's approach — running the model's normal forward inside the spec for
steps outside the kernel's range — works here too and is what we would do in
the interim: the spec reads TP at `attach()` and declines steps outside that
TP's range, which is behaviourally identical to today's `routing.py` fallback.
That is a workaround inside the model, though, not routing the framework can
see or reason about. If TP-dependent `widths` is on the framework roadmap, this
model is a concrete motivating case, and we would rather consume that than
re-implement width routing per model.

## Not addressed here

The RFC #43949 conformance items (directory placement, the single
`--enable-monokernel` switch, bounded cross-GPU waits) apply to the whole mono
feature rather than to this TP extension, and are largely subsumed by the move
to sgl-amd-mono.

Moved to **sgl-project/sgl-amd-mono#9** (draft), per @kevin-mii's review here: since #44353 merged, model monokernels live in that repository rather than in `srt/`. That PR ports #44319 and this TP2/TP8 extension together, as suggested, so there is one place to review the model rather than two. This one can close in favour of it.

On the framework note about widths — you are right that `DeviceLimits.widths` is per GPU type, so the 12-row cap at TP2 cannot be stated directly. The port does what GLM (#6) does: declare the union, and run the model's normal forward from inside the spec for the steps this TP cannot take.

| TP | widths | what bounds it |
| --- | --- | --- |
| 2 | 1–12 | LDS at compile time (width 16 reports 182,304 B against a 163,840 B limit) |
| 4 | 1–16 | — |
| 8 | 5–16 | runtime: width 4 faults on null pointers on all eight ranks |

Declaring only the intersection (5–12) would be safe but costly: it discards widths 1–4, which carry the largest measured gains — at TP2 and TP4 the concurrency-4 row is the best row in the sweep. So the fall-through is load-bearing here, not a formality, and making `widths` TP-dependent would let the framework route those steps itself rather than having each spec re-implement it.

One thing found while porting that is yours, not the model's: `common/guard.py`'s `Guard.flags()` issues the peer-flag load as a single `vec_width=self.npes` buffer load, and at eight ranks that is a `vector<8xi32>` the AMDGPU backend cannot select — AMDGCN's widest is `buffer_load_dwordx4`. Nothing had hit it because the only model on the runtime today asserts `tp in (2, 4)`. Fixed in the PR by reading in four-word chunks; npes 2 and 4 issue the identical single load, so `deepseek_v41` is unaffected.
