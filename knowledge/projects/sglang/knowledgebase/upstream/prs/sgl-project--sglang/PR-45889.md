# [Fix] moe: Broadcast scalar block scales correctly with swap_ab on Triton 3.9

[Upstream PR](https://github.com/sgl-project/sglang/pull/45889) · state: closed · merged: True

## Original PR description

## Motivation

Fixes https://github.com/sgl-project/sglang/issues/45887.

On SM90, block-FP8 MoE can select `swap_ab` while the weight scale is rank 0 (`BLOCK_SIZE_N <= group_n`). Swapping the operands also swaps their scales, so the current expression slices a scalar as `a_scale[:, None]`. Triton 3.9 rejects this after [triton-lang/triton#10429](https://github.com/triton-lang/triton/pull/10429), causing DeepSeek-R1 FP8 startup to fail during prefill CUDA graph capture.

## Modifications

- Add the scalar-scale `swap_ab` case: multiply the scalar weight scale by `b_scale[None, :]`, placing the per-token scales along the transposed dot product's last axis.
- Add a numerical regression test covering swapped and unswapped operands with `BLOCK_SIZE_N=64,128,256` and `group_n=128`. Nonuniform activation/weight scales, two K groups, permuted tokens, padding and routed weights check the output against independently dequantized PyTorch matmul.

## Accuracy Tests

The current kernel's six regression configurations were checked against the PyTorch reference through Triton's CPU interpreter on 3.8.0 and the 3.9 nightly build `3.9.0+gitfc8d31a5`, using FP8 inputs and FP32 outputs (`rtol=2e-4`, `atol=2e-4`). Offline compilation for SM90 with that 3.9 nightly passes all six patched cases. The unpatched upstream kernel fails exactly the two scalar-scale cases (`swap_ab=True`, `BLOCK_SIZE_N=64,128`) with `too many indices for tensor of rank 0`; the four other cases compile. This is kernel numerical and compiler validation; no full-model accuracy evaluation was run. The registered CUDA test has not been executed on a GPU in this chat.

Existing validation of the same arithmetic change on SGLang `c1c287a42` ran DeepSeek-R1 FP8 on 2×8 H100 80GB, TP16, with DP attention off and default MoE/CUDA graph settings. The unmodified server failed on Triton `3.9.0+gitaad2a60d`; the patched server started and served. That run predates this branch and does not validate every subsequent upstream change or the new test's GPU execution.

## Speed Tests and Profiling

Existing paired serving measurements used the same public base-image digest, SGLang `c1c287a42`, checkpoint and launch flags. Benchmark: 8,000 input / 1,000 output tokens; one run per arm. Output throughput:

| Concurrency | Unpatched, Triton 3.8.0 | Patched, Triton 3.9.0+gitaad2a60d |
| --- | ---: | ---: |
| 1 | 76.24 tok/s | 75.62 tok/s |
| 64 | 734.19 tok/s | 737.21 tok/s |
| 256 | 753.10 tok/s | 755.11 tok/s |

Differences range from −0.81% to +0.41%; a single run per arm is not enough to establish a performance improvement. No profiling trace was collected. H200/H20, other models and DP attention were not run end to end.

[by Claude Code] **Severity: functional | Confidence: High**

**Issue**

This test fails on H100, its registered runner. With `swap_ab=True`, the FP8 `tl.dot` runs on WGMMA, and on SM90 Triton enables fast (reduced-precision) FP8 accumulation by default. With `randn` inputs, the error exceeds `rtol=atol=2e-4`, with or without the kernel fix.

**Example**

On H100 (torch 2.14.1, Triton 3.8.0), all three `swap_ab=True` subtests fail: 283/4864 elements mismatch, max abs diff 1.0e-2. The `swap_ab=False` subtests pass.

**Fix**

Use small integers, which FP8 holds exactly, so the dot is exact. On H100 this passes all six subtests (max diff 3.8e-6), and it still fails the scalar-scale subtests if the kernel drops the per-token scale.

```suggestion
        # Small integers keep the FP8 dot exact under Hopper's fast accumulation.
        a = torch.randint(-2, 3, (m, k), device="cuda").float()
        b = torch.randint(-2, 3, (1, n, k), device="cuda").float()
        a, b = a.to(torch.float8_e4m3fn), b.to(torch.float8_e4m3fn)
```
