# [Perf] glm5-next: Tune the fused MoE with its fused shared expert and add an RTX PRO 6000 FP8 config

[Upstream PR](https://github.com/sgl-project/sglang/pull/43647) · state: open · merged: False

## Original PR description

## Motivation

`Glm5NextForConditionalGeneration` fuses its shared expert into the routed experts by default (`determine_num_fused_shared_experts`), so serving GLM-5.3-Flash looks up fused-MoE configs for `E = n_routed_experts + 1 = 289`. The tuner in `benchmark/kernels/fused_moe_triton/common_utils.py` lists the architecture among the DeepSeek-style MoE models but not among those with a fused shared expert, so it tunes and writes `E=288` files that serving never reads. On RTX PRO 6000 Blackwell Max-Q there is no `E=289,N=512` FP8 block config, and serving falls back to the default config.

## Modifications

- Add `Glm5NextForConditionalGeneration` to the tuner's fused-shared-expert list, so `E` matches what serving looks up.
- Add the resulting Triton 3.8.0 config `E=289,N=512,device_name=NVIDIA_RTX_PRO_6000_Blackwell_Max-Q_Workstation_Edition,dtype=fp8_w8a8,block_shape=[128, 128].json` for GLM-5.3-Flash FP8 at TP4 (N=512 per rank). It is read by the Triton fused-MoE runner, which serves this FP8 checkpoint when `--moe-runner-backend` is not set.
- Add the same config as `E=288,...json` for the MTP draft layer. The NextN draft does not fuse its shared expert, so serving looks it up with E=288 (top-k 8) and previously fell back to the default config.

## Accuracy Tests

Config-only change for this shape; the kernel and its accumulation order (128-wide K blocks) are unchanged. GLM-5.3-Flash FP8 at TP4 with this config scored 1,279/1,319 on GSM8K (temperature 0, default reasoning effort, final numeric answer extracted).

## Speed Tests and Profiling

Author measurements with a standalone `fused_moe` microbenchmark (not the tuner), one RTX PRO 6000 Blackwell Max-Q 96 GB GPU at 250 W, Triton 3.8.0: E=289, top-k 9 (8 random routed experts plus the fused shared expert in every row, as in serving), hidden 4096, N=512 per rank, FP8 128x128 block weights, CUDA graph replay median of 200:

| Tokens (M) | Default config | Tuned config |
|---:|---:|---:|
| 1 | 47.6 us | 25.2 us |
| 4 | 159.8 us | 147.8 us |
| 16 | 463 us | 430 us |
| 32 | 721 us | 682 us |

At M >= 96 the tuned entries match the default's speed. The decode-relevant sizes (M = 1 to 32 at TP4 with EAGLE verification) improve.

The draft layer's shape (E=288, top-k 8 random routed experts, otherwise as above), measured the same way on two GPUs. The E=288 file was compared with the default config, and outputs were bitwise identical at every M:

| Tokens (M) | Default config, GPU 0 / GPU 1 | E=288 config, GPU 0 / GPU 1 |
|---:|---:|---:|
| 1 | 47.5 / 45.8 us | 24.3 / 23.6 us |
| 2 | 55.9 / 55.6 us | 34.6 / 33.9 us |
| 4 | 145.6 / 145.0 us | 134.6 / 134.9 us |
| 8 | 270.9 / 268.4 us | 246.3 / 246.3 us |
| 16 | 454.6 / 447.7 us | 420.2 / 419.9 us |
| 32 | 860.8 / 811.5 us | 712.6 / 705.9 us |
| 64 | 1192.5 / 1131.0 us | 1061.4 / 955.7 us |
| 8192 | 5558.3 / 5182.4 us | 5059.1 / 4739.7 us |

At M = 128 to 2048, the results were mixed within run-to-run spread; M = 128 was 20% slower on GPU 0 and 13% faster on GPU 1.

In a TP4 FP8 server with both configs (EAGLE 3/1/4, same GPUs), cold prefill at 8K-128K matched a same-session baseline within 1%. That baseline lacked the E=288 file and also differed by unrelated local changes. Decode was 75.9-76.8 target forwards/s at C1, against 74.3-76.8 in earlier runs. The draft is one layer per draft step, so its end-to-end effect is below the run-to-run spread.
