# [Perf] diffusion: Classify residual_gate_add operands once per call

[Upstream PR](https://github.com/sgl-project/sglang/pull/44478) · state: closed · merged: True

## Original PR description

## Motivation

`residual_gate_add` is the most expensive kernel wrapper on the host in several diffusion DiTs. In a py-spy profile (H200, TP2 eager, at 256² so that the host bounds the step) it takes 12.5% of the denoise host time in Qwen-Image-2.1 and 10.3% in FLUX.1-dev. The CUDA launch is only about a fifth of that. The rest goes to:
- three separate classifications of the same operand layout: `can_use_residual_gate_add_cuda`, the transposed-layout test inside the op, then `_gate_mode`;
- a `torch.cuda.device` guard entered on every call (~1.7 µs);
- `torch.empty_strided`, where `empty_like` gives the same layout.

## Modifications

All changes are in `python/sglang/kernels/kda_kernels/residual_gate_add_jit.py`:
- `_route()` classifies the operands once and returns the gate mode, `_TRANSPOSED`, or `None`. `can_use_residual_gate_add_cuda`, `residual_gate_add_cuda` and `residual_gate_add` all use it, and the chosen mode is passed into the custom op as an `int`.
- The op enters the device guard only when the residual is not on the current device.
- The CUDA path allocates with `empty_like`; its residual is contiguous.
- `_is_transposed_dense_residual` tests the stride first, so contiguous inputs leave it early.

Accepted layouts and kernel choice are unchanged, with one exception. A full-shape `[B, 1, D]` gate with gaps between rows was accepted, because it also matched the batched-row rule, and then raised in `gate.view(-1)`:

```
RuntimeError: view size is not compatible with input tensor's size and stride
```

It now runs eager. No memory is involved, and the compiled path still goes through the custom op.

## Accuracy Tests

- New test `test_residual_gate_add_strided_full_gate_runs_eager` covers the case above. It fails on main.
- On H200:
  - `test_modulate.py` 1038 passed. It includes the existing acceptance-rule, dtype, transposed, CUDA-graph and `torch.compile(fullgraph=True)` tests.
  - `test_model_fast_paths.py` 97 passed, 1 skipped.
  - `test_sites.py` 24 passed.
  - `test_residual_gate_fp32.py` 40 passed.

## Speed Tests and Profiling

Base `f7ad4345b8`, torch 2.13, H200 (Xeon 8558P), with processes pinned to the GPU's NUMA node.

**Host time per call** (µs, inference mode, bf16; the GPU is kept busy so only submission is timed):

| residual / gate | main | this PR |
|---|---|---|
| `(1, 4608, 3072)` / `(1, 1, 3072)` (FLUX, Qwen) | 20.40 | 16.08 |
| `(1, 4608, 3072)` / `(1, 4608, 3072)` | 17.30 | 14.28 |
| `(2, 1024, 3072)` / `(2, 1, 3072)` | 22.18 | 16.57 |

**End to end.** On H200, two identical main servers resident together differed by 3.5% in an A/A run at Qwen-Image-2.1 TP2 512², which is more than this change. So both paths were built into one server and chosen per request, and requests rotated through the arms in the same process. An extra base arm in each round measures in-process noise. Values are client wall-clock medians, eager:

| | vs base | faster than base in | in-process A/A |
|---|---|---|---|
| Qwen-Image-2.1 TP2 512² | −1.9% | 10/10 | +0.5% |
| Qwen-Image-2.1 TP2 1024² (GPU-bound) | 0.0% | 6/10 | +0.1% |
| FLUX.1-dev TP2 512² | −1.4% | 8/8 | −0.4% |
| FLUX.1-dev TP2 512², together with #44471 | −3.9% | 8/8 | |

Output images are unchanged: the kernels and their inputs are the same. On Grace hosts (GB200/GB300), where these Python costs are about twice as large and the step is host-bound, the gain should be larger. No GB300 was available for this run.
