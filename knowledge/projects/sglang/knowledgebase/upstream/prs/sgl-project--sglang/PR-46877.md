# [Fix] [XPU] diffusion: Copy flash-attention inputs under torch.compile

[Upstream PR](https://github.com/sgl-project/sglang/pull/46877) · state: open · merged: False

## Original PR description

## Motivation

Since #41944, compiled FLUX.2-klein serving on Intel XPU fails **every request** (0/20) with:

```
torch._dynamo.exc.BackendCompilerFailed: backend='inductor' raised:
RuntimeError: Expected !size_bytes_is_heap_allocated_ to be true, but got false.
```

The server warmup passes. The first client request with a new prompt length triggers a dynamic-shape recompile, and that recompile fails. All four klein cases (4B/9B × t2i/TI2I) fail with `--enable-torch-compile`. It still reproduces on today's `main` (`de26bb16a9`).

**Mechanism** (from `TORCH_LOGS=graph_breaks,recompiles,graph_code`, #41944 vs its parent):
1. `_as_fa_input`'s `view.data_ptr() % 16 == 0` can't be traced. Dynamo raises `TypeError: unsupported operand type(s) for %: 'int' and 'int'` internally, logs a graph break there (16×), and falls back to eager for the enclosing frames (21× vs 5× on the parent).
2. Dynamo then compiles helpers as separate frames, among them `_flux2_single_qk_rope`. That frame's q/k inputs are views of one fused-projection buffer, and `fused_inplace_qknorm_rope` mutates them in place. AOTAutograd therefore builds a synthetic base (`merge_view_inputs`).
3. The static warmup compile works. The first dynamic recompile (4624 → 4608 tokens) hits a symbolic storage size in the synthetic base's `set_()`, giving the error above.

Bisected to #41944. Skipping only the `data_ptr()` clause, with the zero-copy views kept, also fixes it, so the untraceable pointer check is the trigger, not the views.

## Modifications

- `xpu_backend.py`: under `torch.compiler.is_compiling()`, `_as_fa_input` returns the `.contiguous()` copy, as before #41944. Uncompiled behaviour, including the zero-copy path, is unchanged.
- `test_flux2_xpu_norm_fusions.py`: `test_attention_input_traces_under_torch_compile` compiles the "slice k from a fused projection, then `_as_fa_input`" path with `fullgraph=True, dynamic=True` and checks the output against eager. It **fails on `main` without this change** (`Unsupported: Observed exception`, the `data_ptr()` break) and passes with it.

Trade-off: under `torch.compile`, flash attention receives copied q/k/v again, so #41944's copy saving applies to eager only. I could not resolve a latency difference between the copy and zero-copy paths at n=20 (2.48–2.53 s across variants, within run-to-run spread). Keeping zero-copy under compile would need an alignment check Dynamo can trace. `storage_offset()` is not one either: it also graph-breaks on torch 2.14, although its break is resumable and avoids this failure.

## Accuracy Tests

Intel Arc Pro B60, torch 2.14.0+xpu. FLUX.2-klein-4B t2i, `sglang serve --enable-torch-compile --component-residency dit=resident,text_encoder=layerwise-offload` + `bench_serving --dataset vbench --num-prompts 20 --warmup-requests 2 --num-inference-steps 4`:
- The images match the pre-#41944 copy path within run-to-run noise: PSNR-Y median 36.7 dB, against a 35.6–37.8 dB cross-process reference.
- The new and existing unit tests in `test_flux2_xpu_norm_fusions.py`: 9 passed.

## Speed Tests and Profiling

All four FLUX.2-klein cases, using the same flags as the CI that reported the failure (`--max-concurrency 1 --width 1024 --height 1024` and `--warmup-resolutions 1024x1024` for 9B; TI2I conditions on 1024x1024 images):

| case | `main` `de26bb16a9` | `main` + this PR | mean latency | peak memory |
|---|---|---|---|---|
| klein-4B t2i | 0/20 | **20/20** | 2.51 s | 10434 MB |
| klein-9B t2i | 0/20 | **20/20** | 4.76 s | 20758 MB |
| klein-4B TI2I | 0/20 | **20/20** | 5.13 s | 10950 MB |
| klein-9B TI2I | 0/20 | **20/20** | 9.53 s | 22056 MB |

#41944's parent `5bef70c0a2` gives 20/20 at 2.51 s / 10432 MB on klein-4B t2i. With this PR there are 0 graph breaks in `xpu_backend.py`, and the break/recompile counts equal those of the pre-#41944 copy path.

Separate from the attention path changed here, but seen once in the code this PR lets compile again: in one of the two klein-9B runs, server warmup took 37 min. During coordinate-descent autotuning, `ocloc` spent ~18 min on a `-cl-intel-256-GRF-per-thread` config of the time-embedding GEMV (`triton_red_fused_mm_silu_t_2`). That config then failed with `OutOfResources` (per-thread scratch space) and was dropped, and serving was normal (20/20). It did not recur in the other 9B run; I have not tested whether #41944's parent hits it on 9B.

More importantly, I think we should address the root cause rather than add workarounds in the Python layer. If the 16-byte alignment requirement comes from the FlashAttention kernel, we should consider improving the kernel..

The data_ptr() check exposes low-level kernel implementation details to Python and introduces unnecessary complications for torch.compile. Ideally, this should be handled at the kernel/backend level while preserving zero-copy 
behavior.

@murthy-l-habana Additionally, we may prioritize investigating whether we can leverage XPU graph, as they may offer greater acceleration than using `torch.compile` alone. Furthermore, oneAPI is upgraded in sglang enviroment https://github.com/sgl-project/sglang/pull/43989, making XPU graph readily available; this is likely a more promising avenue to explore than relying on `torch.compile`.
