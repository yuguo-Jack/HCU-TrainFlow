# [Feat] dsv41-engram: Share Engram tables across P/D using EGM

[Upstream PR](https://github.com/sgl-project/sglang/pull/47478) · state: open · merged: False

## Original PR description

## Summary

Add opt-in external Engram placement for DeepSeek-V4.1-Flash. A persistent CUDA HOST_NUMA/FABRIC owner from [vLLM #64082](https://github.com/vllm-project/vllm/pull/64082) publishes one immutable FP8/E8M0 table generation; independent SGLang P and D workers map it read-only and use SGLang's existing `engram_gather`. Their KV transfer remains on native NIXL. Related to [RFC #64002](https://github.com/vllm-project/vllm/issues/64002).

```text
ASIS
P TP2 --> its host Engram tables (188.833 GiB)
D TP2 --> its host Engram tables (188.833 GiB)
```

```text
PR
one HOST_NUMA/FABRIC owner (188.833 GiB)
                |--> P TP2: imported GPU views --> existing gather
                +--> D TP2: imported GPU views --> existing gather
```

The measured table extent for two instances changes from 377.666 to 188.833 GiB. This is table backing, not total RSS, page cache or HBM.

## Motivation

Independent P/D instances each load an immutable table that is much larger than either worker's local HBM share. SGLang's existing CPU/peer placements address a single instance's placement and TP layout; the external option removes one P/D backing while keeping the current hash, gather, gate and KV-transfer paths. The compatible owner protocol is provided by the companion vLLM PR. The feature is opt-in and leaves the default placement unchanged.

## Modifications

- `--engram-config` gains `placement=external` with owner endpoint, private token file and expected generation. Workers validate generation, checkpoint config/index hashes, table layout and byte extent before importing read-only FABRIC mappings. A failed unmap retains the owner lease.
- External table parameters are metadata placeholders. The lazy safetensors loader skips the two large table tensors before `get_tensor`, including mixed shards, while loading the smaller weights. Online weight updates reject an attached immutable generation; start a new owner and new workers for a new checkpoint.
- [Runnable SGLang owner/P/D/router/request example](https://github.com/foraxe/sglang/tree/cf1b37ee058b96611faee9a3879e5ee7f1baebe5/examples/engram_shared), [vLLM owner/P/D example](https://github.com/foraxe/vllm/tree/e50524f1ecaea17028a7ec82e9d8e5e0ba4498ea/examples/disaggregated/shared_engram), and `docs/docs/advanced_features/engram.mdx` explain generation handoff, trust boundary and launcher-PID shutdown. [One-host cross-engine launch evidence](https://github.com/foraxe/vllm/tree/a29e4b6c0c511bb11915b8522eecda7e4b687410/evidence/shared_engram_nvl72/launch_close_loop_20261103) records both engines serving sequentially from one owner generation.

## Speed Tests and Profiling

The preceding [matched 8K local screen](https://github.com/foraxe/sglang/tree/c15cb25f5fa342b9b653ae4dd0562849e60f2185/evidence/dsv41_shared_engram_fabric) was essentially flat: ordinary/shared median TTFT 0.3346/0.3345 s and P-to-D E2E 4.6347/4.6024 s, with one arm order, three retained requests and one C4 wave. The current short-prompt arm gave median wall 4.461/4.361 s. These are diagnostic samples, not a stable speedup or tail-SLO claim. The ordinary CPU control had zero huge-page coverage in the 8K screen. The capacity claim is one avoided 188.833 GiB table backing across P and D.

Only one four-GPU GB200 host was available. Cross-host NVL72/IMEX import, remote Grace latency, 3P1D, image-bearing requests, P/D CUDA graphs, active-graph owner loss, broad model evaluation and production SLOs remain unqualified. The control channel is unencrypted and requires a trusted network.
