# [Feat] weight_cache: Support daemon-to-daemon heterogeneous weight resharding via Mooncake

## Motivation
Weight cache daemons currently load weights from disk. This PR adds daemon-to-daemon heterogeneous weight transfer. A source daemon group publishes immutable weight placement information, and a target daemon group uses Mooncake to reshard and transfer those weights into its locally allocated layout. The serving engine is not involved in manifest exchange or weight transfer. It continues to connect to the resulting daemon through the existing IPC weight-cache client path.
from roadmap: https://github.com/sgl-project/sglang/issues/33522
RFC: https://github.com/sgl-project/sglang/issues/32335

## Modifications


<!-- Detail the changes made in this pull request. -->
### Explicit model adapters

Add `weight_cache/model_adapters` with exact model-type registration and three entry points: `validate`, `build_layout`, and `finalize_target`.

- Shared helpers describe replicated, row/column-parallel, merged-column, QKV/GQA, vocabulary, and standard MoE weights using the modules' actual partition metadata.
- A common builder distinguishes transferred regions, locally initialized padding/buffers, and checkpoint-derived state. It checks coverage, overlaps, aliases, bounds, and storage bindings.
- Initial adapters support dense **Qwen3** and **DeepSeek-V2-Lite**. Additional models must register an explicit adapter and validate their layout against native loading.
- Layout construction does not record loader operations or replay checkpoint metadata through meta tensors.

### Daemon transfer and Mooncake boundary

1. The source loads its checkpoint normally, builds its declared layout, registers its owning allocations with Mooncake, and publishes a rank-local runtime manifest.
2. A lightweight **TCP** registry, owned by the source launcher, collects all expected ranks and checks their model identity, revision, topology, and device identities before publishing the complete group.
3. The target uses `DummyModelLoader` to allocate its layout, fetches the source group, and builds its own runtime manifest. Manifest fetching uses `--weight-cache-timeout`.
4. The adapter converts logical tensor declarations and physical storage fragments into Mooncake placement and runtime bindings. Tensors with matching source/target distributions share transfer groups, including GQA replica groups.
5. Mooncake plans and executes the transfers. Immutable allocation guards protect the published storage; the Mooncake API is unchanged.
6. The target restores aliases and required derived state, validates its bindings, then publishes CUDA IPC handles. DeepSeek reuses native post-load processing to rebuild MLA weights. IPC loading also rebinds tensor references retained by module attributes and dataclass configurations.

Unsupported model types, quantization, unverified packing, incomplete layouts, and overlapping source/target GPUs fail explicitly. Startup failures propagate across target ranks; there is no fallback to loading target weights from disk.

### Example: standalone TP1 → TP2

Run these as separate long-lived processes, using the same checkpoint and compatible model settings:

```bash
# Source on GPU 4.
python -m sglang.srt.weight_cache.daemon \
  --model-path "$MODEL" --dtype bfloat16 --tp-size 1 --base-gpu-id 4 \
  --weight-heterogeneous-transfer-mode source \
  --weight-heterogeneous-transfer-host 127.0.0.1 \
  --weight-heterogeneous-transfer-port 31999

# Target on GPUs 5–6; start after the source registry is ready.
python -m sglang.srt.weight_cache.daemon \
  --model-path "$MODEL" --dtype bfloat16 --tp-size 2 --base-gpu-id 5 \
  --weight-heterogeneous-transfer-mode target \
  --weight-heterogeneous-transfer-host 127.0.0.1 \
  --weight-heterogeneous-transfer-port 31999

# Optional inference engine, after the target daemons are ready.
python -m sglang.launch_server \
  --model-path "$MODEL" --dtype bfloat16 --tp-size 2 --base-gpu-id 5 \
  --weight-cache-mode client
```
