# [AMD] gfx1250: fix GDN chunked-prefill GPU fault and state corruption

[Upstream PR](https://github.com/sgl-project/sglang/pull/41868) · state: open · merged: False

## Original PR description

## Motivation

With the current ROCm Triton (3.8.0), Qwen3.5 / Qwen3-Next GDN chunked prefill on gfx1250 hits two Triton
codegen issues:

1. **GPU memory fault on the first prefill.** With async copy on (the gfx1250 default), the pipelined masked
   loads in the GDN FLA kernels are lowered to `global_load_async_to_lds_b128`, which has no bounds check.
   The server dies during autotune with `HSA_STATUS_ERROR_MEMORY_FAULT` in
   `chunk_gated_delta_rule_fwd_kkt_solve_kernel`.
2. **Silent state corruption.** At the `chunk_h` default of `BV=32 / 4 warps / 2 stages`, the pipelined
   in-place state write-back is nondeterministic for ragged batches. Answers look fluent but are wrong.

Today the only way to run is two process-wide env vars, `TRITON_HIP_USE_ASYNC_COPY=0` and
`SGLANG_GDN_CHUNK_H_NUM_STAGES=1`. The first turns async copy off for every Triton kernel in the process; the
second turns off pipelining in `chunk_h`. This PR replaces both with narrower gfx1250-only workarounds, so
gfx1250 runs with no extra env vars.

## Modifications

Both changes are gated on `is_gfx1250_supported()`; other platforms are unchanged.

- `fla/chunk.py`: run the GDN chunked forward (`l2norm_fwd` + `chunk_gated_delta_rule_fwd`) inside
  `triton.knobs.amd.scope()` with `use_async_copy = False`. The knob also sets `TRITON_HIP_USE_ASYNC_COPY`,
  which is part of Triton's compile cache key, so these kernels get their own non-async build and every other
  Triton kernel keeps async copy.
- `fla/chunk_delta_h.py`: on gfx1250, default `chunk_h` to `BV=64, num_warps=8` (still 2 stages). The
  `SGLANG_GDN_CHUNK_H_BV` / `_NUM_WARPS` / `_NUM_STAGES` env overrides still apply.

## Accuracy Tests

MI450X (gfx1250), Qwen3.5-397B-A17B-MXFP4, no workaround env vars:

- **GSM8K-1319** (`bench_sglang.py`, thinking off, parallel 8):

  | | env-var workaround | this PR |
  |---|---:|---:|
  | TP1 | 0.964 | **0.963** (invalid 0.000) |

## Speed Tests and Profiling

- GDN chunked forward: **14-19% faster** than the `num_stages=1` workaround (pipelining kept).
- End-to-end 8k in / 1k out, cc = 4..64: TP1 and TP2 sweeps completed with no GPU fault, MES error, or hang,
  with neither env var set. TP4 cc = 4..32 also ran clean.
