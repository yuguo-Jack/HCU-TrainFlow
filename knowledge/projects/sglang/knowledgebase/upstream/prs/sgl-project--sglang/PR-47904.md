# [Fix] moe: Refuse mxfp8 trtllm-gen MoE runner on consumer Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/47904) · state: open · merged: False

## Original PR description

## Motivation

`_moe_runner_backend_quant_constraints` picks the MoE runner from the quantization
alone: for `mxfp8`, the default is `triton` on gfx95 and `flashinfer_trtllm`
everywhere else (`overrides.py:1555`). Nothing asks which device that is. So
`--quantization mxfp8` with no `--moe-runner-backend` resolves to the trtllm-gen
MoE kernels on SM110/SM120/SM121 exactly as it does on SM100, and both explicit
`flashinfer_trtllm` and `flashinfer_trtllm_routed` are accepted there too.

The pinned `flashinfer_python[cu13]==0.7.2` does not have those kernels for
consumer Blackwell. Its batched-GEMM runner keeps only configs whose cubin arch
matches the device:

```cpp
// csrc/trtllm_batched_gemm_runner.cu:48-67
bool isArchCompatible(int smVersion, tg::CudaArch cubinArch) {
  switch (cubinArch) {
    case tg::CudaArch::Sm100a: return smVersion == 100;
    case tg::CudaArch::Sm100f: return smVersion == 100 || smVersion == 103;
    case tg::CudaArch::Sm103a: return smVersion == 103;
    ...  // Sm107a, under TLLM_RUBIN_FEATURES
    default: return false;      // smVersion 120 / 121 lands here
  }
}
```

and it states the same for FP8 MoE at the API layer:

```python
# flashinfer/fused_moe/api.py:508-510
# The FP8 kernels are validated on the SM100 family only -- the outer JIT module
# compiles for major 12 as well, but those cubins fail at runtime on SM120/121.
_TRTLLM_ROUTED_FP8_ARCHS = (100, 103)
```

`TrtllmFp8BlockConfig.supported()` and `TrtllmFp8PerTensorConfig.supported()` both
return against that tuple (`:873`, `:931`). The JIT module is indeed compiled for
major 12 (`jit/fused_moe.py:385-386`, `supported_major_versions=[10, 12]`), but the
manifest it is built from only carries
`BLACKWELL_CUBIN_ARCHS = ("Sm100a", "Sm100f", "Sm103a")`
(`jit/trtllm_gen_metainfo.py:48`). The launcher's own coarse check
(`csrc/trtllm_fused_moe_kernel_launcher.cu:1677`) admits `major == 10 || major == 12`,
so nothing refuses the device at entry. The refusal comes later, in the constructor
of the batched-GEMM runner the MoE call builds:

```cpp
// csrc/trtllm_batched_gemm_runner.cu:204-219, inside TrtllmGenBatchedGemmRunner's
// constructor, reached from the first MoE call
if (mPassingConfigIndices.empty()) {
  // Distinguish "this GPU has no cubins at all" from "no cubin matches these GEMM
  // options". ...
  bool anyArchCompatible = false;
  for (size_t i = 0; i < bmm.getNumBatchedGemmConfigs(); ++i) {
    if (isArchCompatible(sm_version, configs[i].mSm)) { anyArchCompatible = true; break; }
  }
  std::ostringstream arch_msg;
  arch_msg << "The trtllm-gen batched GEMM cubin manifest contains no kernels runnable on sm"
           << sm_version << "; this backend currently ships cubins for sm100, sm103 and sm107.";
  FLASHINFER_CHECK(anyArchCompatible, arch_msg.str());
}
```

That branch is the one an SM120 device takes, and the message is quoted from a run
on one (Accuracy Tests below), not from the source. It lands at the first MoE call,
so after the weights are loaded and, for a server, after warmup. The two other
failures live on either side of it in the same file: the option dump at `:221`, for
a device that does have arch-compatible kernels but none matching the GEMM options,
and `No valid config found for the given problem shape` at `:561`, inside
`getValidConfigIndices`, which a runner that constructed successfully can still
raise. Neither is what this path ends in here, and a third
(`Config index N is not in this runner's compatible config set`, `:69-77`) needs an
explicit config index.

The same limit is readable off the artifact, which is the device-free half of the
measurement reported below: flashinfer's own comment above the function says the
manifest is a downloaded artifact, so "which architectures it actually covers is
not knowable at compile time" (`trtllm_batched_gemm_runner.cu:42-47`, #4107).
`artifacts.py:144-146` of the pinned v0.7.2 sends the batched-GEMM runner to
`35cb99413a3ebce2e87a03fc04196e528e22c8d5/batched_gemm-fdba669-7e3d0a6/`, whose
`checksums.txt` (anonymous GET on
`https://edge.urm.nvidia.com/artifactory/sw-kernelinferencelibrary-public-generic-local/`)
lists 6,966 `.cubin` files tagged with three of the four arches
`isArchCompatible` knows: 3,438 `sm100f`, 3,438 `sm107a`, 90 `sm103a`, and no
`sm100a` at all. Names containing `sm89`, `sm90`, `sm110`, `sm120` or `sm121`
occur zero times, so on this device the compatible set is empty because no
kernel was ever published for the architecture -- not because a config was
mis-selected at runtime. Applying `isArchCompatible` to those tags gives the size of
the set each device is left with before any GEMM option is considered: 3,438 configs
on sm100, 3,528 on sm103, 3,438 on sm107, and 0 on sm110, sm120 and sm121. The
v0.7.1 bundle those hosts cache
(`4e73ccb74f333ecfebeac52abf3ebe1fa2dd34b3/batched_gemm-b738138-6923fec/`) has
the same 6,966 / 3,438 / 3,438 / 90 split, so the composition did not change
with the pin.

The repo states this limit twice, 30 lines and one file away. `auto` +
`modelopt_fp4` is re-routed off SM110/SM120 with the log "trtllm-gen MoE kernels
are SM100-only" (`overrides.py:1566-1575`, #41765), and `nvfp4_online` refuses
anything outside SM100/SM103 outright. In the quant method, the `flashinfer_mxfp4`
arm of the same fp8 path splits by device with the comment "SM100 uses TRT-LLM;
SM90 uses W4A16 and SM120 uses MXFP8xMXFP4"
(`layers/quantization/fp8.py:471-478`): consumer Blackwell is given a named
alternative there, while the `mxfp8` arm is the one that never got the check.

Reproduced on an 8xRTX PRO 5000 host (compute capability 12.0) by calling the
registered pass with the device's own platform answers, no mocks:

```
device: is_cuda=True is_hip=False is_npu=False device_sm=120 is_sm100=False is_sm110=False is_sm120=True
choices: MXFP8_MOE_RUNNER_BACKEND_CHOICES = ['cutlass', 'deep_gemm', 'flashinfer_megamoe', 'flashinfer_trtllm', 'flashinfer_trtllm_routed']
  auto                     -> {'moe_runner_backend': 'flashinfer_trtllm'}   # origin/main
  auto                     -> ValueError at startup                          # this patch
  flashinfer_trtllm        -> ValueError at startup                           # this patch
  flashinfer_trtllm_routed -> ValueError at startup                           # this patch
  cutlass                  -> {}                                             # unchanged, both arms
```

The gate is evaluated on the backend the pass resolved to, so a name outside that
list ends the same way -- it takes the existing device-free warning first and is
then refused, rather than being warned into a backend that cannot run. Measured
on the same device, both modes:

```
  triton                 -> WARNING "supports only ... Overriding 'triton'" -> flashinfer_trtllm   # origin/main
  marlin                 -> WARNING ...                                      -> flashinfer_trtllm   # origin/main
  flashinfer_cutlass     -> WARNING ...                                      -> flashinfer_trtllm   # origin/main
  triton                 -> WARNING ...                                      -> ValueError           # this patch
  marlin                 -> WARNING ...                                      -> ValueError           # this patch
  flashinfer_cutlass     -> WARNING ...                                      -> ValueError           # this patch
```

`flashinfer_cutlass` is worth naming: it is a valid value elsewhere in this file
(the `modelopt_fp4` resolution) but not in `MXFP8_MOE_RUNNER_BACKEND_CHOICES`, so
for `mxfp8` it is one of these off-list names rather than an accepted alternative.
The same seven names were run the same way on the SM90 host (`device_sm=90`, all
three Blackwell probes `False`) and both arms give the same answer for all seven,
so the gate fires on the device and not on the shape of the request.

## Modifications

- Refuses rather than re-routes, deliberately. A re-route needs a target
  established on the device, and this pass has one only where one exists
  (`modelopt_fp4` -> `flashinfer_cutlass`). For `mxfp8` on SM110/SM120 nothing
  else is known good: flashinfer's own CUTLASS set for MXFP8 x MXFP8 is
  `_CUTLASS_MXFP8_ARCHS = (100, 103, 107)` (`fused_moe/api.py:558`), so naming
  `cutlass` for these arches would trade a clear startup error for a different
  late one. The message says exactly that -- the remaining choices are not what
  this pass picks on CUDA and are not validated for `mxfp8` here.
- One thing that is worth naming before a reviewer finds it: flashinfer does
  claim MXFP8 MoE on these arches through a different engine. `CuTileMxfp8Config`
  accepts `_CUTILE_MXFP8_ARCHS = (120, 121)` (`fused_moe/api.py:527`, returned by
  `supported()` at `:1349` and `:1408`), which is a cuTile path, not the
  trtllm-gen one this backend dispatches. sglang exposes no name for it --
  `MXFP8_MOE_RUNNER_BACKEND_CHOICES` on today's main is `cutlass`, `deep_gemm`,
  `flashinfer_megamoe`, `flashinfer_trtllm`, `flashinfer_trtllm_routed`
  (`arg_groups/choices.py:163`), and `CuTileMxfp8` appears nowhere in the repo.
  Making it the answer here would be a new MoE runner with its own weight
  preparation and its own accuracy story (that config also states expert
  parallelism and fused shared experts are unsupported), so it is a feature PR,
  not a line inside this one. This diff only stops the launch of a kernel set
  the device does not have.
- The condition is `moe_runner_backend in ("flashinfer_trtllm",
  "flashinfer_trtllm_routed") and (is_sm110 or is_sm120)` -- the same two probes
  the `modelopt_fp4` arm next to it uses, evaluated on the backend this pass
  resolved to. It sits after the device-free `allowed` handling, so every answer
  that does not end on a trtllm runner is byte-for-byte what it was: the megamoe
  default (`moe_a2a_backend == "flashinfer_megamoe`), the gfx95 `triton` default,
  ROCm, non-`mxfp8` quantizations, and every CUDA device outside SM11x/SM12x
  (Hopper included, which this patch neither enables nor refuses -- it changes
  no answer that is not already broken by the missing cubins).
- Not widened to "everything outside the SM100 family", even though the manifest
  above shows the same hole on SM89/SM90. Three reasons: the device set here
  mirrors the `modelopt_fp4` arm the repo already wrote, so "trtllm-gen MoE is
  absent on SM110/SM120" has one definition in this file rather than two; Hopper
  is the most-deployed CUDA target in this project and a refusal there converts a
  configuration that today at least reaches a backend into a startup error; and
  the SM90 host turned out to fail for a reason this gate does not speak to. With
  the same seeded manifest it never reaches the cubin check -- the module is
  refused when flashinfer builds it: `No supported CUDA architectures found for
  major versions [10, 12]` (`jit/fused_moe.py:385`, raising at
  `compilation_context.py:162`), which is a statement about
  `supported_major_versions`, not about which cubins were published. A gate for
  that reads a different list and needs its own cases. Widening this one is a
  maintainer call, not something to slip into a consumer-Blackwell fix.
- The arch set tracks the pinned wheel, and the pin moves on its own:
  `bot-bump-flashinfer-version.yml` bumps it without touching this check, so
  widening or narrowing it stays a human edit. Hence the message attributes the
  set to flashinfer's dispatch rather than to a hardware claim.
- Two things this PR is not claiming, both from the same host. The
  `assert TopKOutputChecker.format_is_bypassed(topk_output)` that 0.5.22 raises
  before anything device-related runs is already answered on main, which
  materializes a standard topk into the routed path
  (`moe_runner/flashinfer_trtllm.py:888-896`); the bare assert survives at `:1040`,
  inside `not use_routed_topk`, where a standard topk never arrives. So this diff
  claims only the missing device check, not that wiring bug. And
  `--moe-runner-backend cutlass` with fp4 experts does fail on SM120, for a
  reason unrelated to cubins: `create_weights` initializes the stride buffers
  under `not self.is_fp4_expert and self.block_quant and is_cutlass()`
  (`fp8.py:1891-1896`) while `apply` reads them under `is_cutlass()` alone
  (`:3200`, `:3218`), and the fp4-expert arms above (`:457`, `:464`, `:471`)
  offer no cutlass option. That is an fp8 + fp4-experts defect rather than
  `mxfp8` evidence, so it belongs in a separate report and not in this diff.

## Accuracy Tests

No numerics are involved -- the patch changes which configurations are accepted,
not any computed value.

`test_mxfp8_moe_runner_backend.py` (the file #41377/#35272 left behind for the
ROCm side) gains `TestMxfp8TrtllmDeviceConstraint`: SM110/SM120/SM121 x {`auto`,
`flashinfer_trtllm`, `flashinfer_trtllm_routed`} raise, and the same three arches x
{`triton`, `marlin`, `flashinfer_cutlass`} -- names outside the choices, which the
pass warns about and then resolves to the default -- raise on that resolved value
while SM90 keeps resolving them to `flashinfer_trtllm`; SM100/SM103/SM107 accept
`auto` and keep an explicit `flashinfer_trtllm_routed`; SM90 accepts everything it
accepted before; `cutlass`/`deep_gemm` pass through untouched on SM120; the
megamoe default, ROCm (both gfx95 branches) and a non-`mxfp8` quantization are
unaffected. Every case now pins the Blackwell probes it depends on --
`override_platform` replaces only the facts it is given, so an unpinned case
would answer from the runner's own GPU. That is why two pre-existing cases in
this file (`test_cuda_still_rejects_triton`, the CUDA row of
`test_auto_default_is_unchanged`) now say `arch="sm100"`: they assert the
`flashinfer_trtllm` default, which is only true on a device that has the cubins.
In `test_model_overrides.py` the change is one assertion
(`_view(quantization="mxfp8")` -> `flashinfer_trtllm`, `:3426-3435`), and it is a real
one: run on this SM120 host against this patch, unpinned, it fails. It now names
the device that answer belongs to -- `is_sm100=True`, the idiom the
`nvfp4_online` case above it uses -- together with the two probes this gate reads,
because `is_sm100` alone would still leave `is_sm120` answering `True` from the
runner.

Both hosts run the 0.5.22 wheel, and its `overrides.py` is the same file on each
(`md5sum daec8c3ba1c599f9e0a5db7d93c77fb3`), so the pass under test is each host's
own file with the 27-line gate inserted at the same position and re-exec'd as the
module the tests import; site-packages is never written to (`md5sum` before and
after each run). The source citations above are read from the pinned v0.7.2 tag;
the two `checksums.txt` manifests are anonymous GETs against artifactory from a
host with egress, which is why the artifact-level claim is not blocked by the
offline pod. The 0.7.1 flashinfer on both test hosts carries the same
`_TRTLLM_ROUTED_FP8_ARCHS = (100, 103)`, the same comment, the same
`supported_major_versions=[10, 12]` (`jit/fused_moe.py:385-386`) and a
byte-identical runner: the `flashinfer/data/csrc/trtllm_batched_gemm_runner.cu`
bundled in each of these wheels hashes to `ce1961b9b69e8cc729b7708f455dfb1f`, the
same as that file at both the v0.7.1 and the v0.7.2 tag -- so the raise quoted
below is the raise the pinned version produces, at the same line.

The SM90 column is what the "changes no answer outside SM11x/SM12x" claim rests on,
and it is read off the device rather than mocked: `device_sm=90`,
`is_sm100/is_sm110/is_sm120` all `False`, and the resolved backends match main
exactly. It also shows the pinned assertion breaks only where this gate reads the
device -- on SM120, not on SM90 -- so the pin is required by the change, not
merely tidier. Note that SM90 answers `flashinfer_trtllm` here even though the
manifest above has no `sm90` cubin either; that is the deliberate scope line
drawn in Modifications, not an observation that Hopper works -- and the run below
shows it does not, only sooner and for another reason.

The kernel itself is now measured, on the device. The cubin bundle is a downloaded
artifact and neither test host has egress (`edge.urm.nvidia.com` connect timeout, 4
retries; `curl` to any external host fails the same way), but `get_artifact` in
`flashinfer/artifacts.py` looks in `FLASHINFER_CUBIN_DIR` first, checks the sha256,
and honours `FLASHINFER_NO_DOWNLOAD` -- so a directory seeded with the published
files closes the fetch with no network at all. Both bundles were downloaded on a
host that does have egress, and each `flashinferMetaInfo.h` matched the sha256 its
own `checksums.txt` records for it (line 6,967, the one entry after the 6,966
`.cubin` lines). Unpacked under `FLASHINFER_CUBIN_DIR` on each test host, the
artifacts load with `FLASHINFER_NO_DOWNLOAD=1`. Nothing was written into
site-packages for any of this, in either arm: `overrides.py` there is
`md5sum daec8c3ba1c599f9e0a5db7d93c77fb3` before and after every run on both hosts.

SM120, `(12, 0) NVIDIA RTX PRO 5000 72GB Blackwell`: the trtllm MoE module does
compile for this device (3m03.6s), and the header generated from the seeded
manifest carries 3,528 batched-GEMM configs (`tllmGenBatchedGemmListLen = 3528`:
Sm100f 3,438 + Sm103a 90), because `filter_metainfo` selects by variant rather than
by device and leaves the device to `isArchCompatible` -- which is where this loses.
The MXFP8 path called directly, `trtllm_fp8_block_scale_moe(...,
fp8_quantization_type = Fp8QuantizationType.MxFp8, use_shuffled_weight=True)` with
`hidden_states` in `float8_e4m3fn` and `hidden_states_scale` as `[num_tokens,
hidden // 32]` uint8, the layouts its own assertions ask for, raises:

```
RuntimeError: Error in function 'TrtllmGenBatchedGemmRunner' at
.../site-packages/flashinfer/data/csrc/trtllm_batched_gemm_runner.cu:218: The
trtllm-gen batched GEMM cubin manifest contains no kernels runnable on sm120;
this backend currently ships cubins for sm100, sm103 and sm107.
```

arriving through `fused_moe/core.py:5901` (`trtllm_fp8_block_scale_moe`) -> `:3261`
(`run_selected_tactic`) -> `:3189` -> the constructor, i.e. at the first MoE call,
after the weights are loaded. That is the failure this gate moves to the argument
stage. The two steps of the same path that run before it also run on this device
(`align_mxfp8_moe_weights_for_flashinfer_trtllm`, `flashinfer_mxfp8_quantize`), so
nothing upstream of it was substituted.

SM90, `(9, 0) NVIDIA H20`, same seeded directory: the call is refused one step
earlier, while flashinfer builds the module -- `RuntimeError: No supported CUDA
architectures found for major versions [10, 12]` at `compilation_context.py:162`,
called from `jit/fused_moe.py:385` -- in 4.0s. This is the SM90 signature referred
to in Modifications, and it is a different rule from the one this diff reads.

What is still not measured here: the accepted side, an SM100 or SM103 host running
this same call through to a launch. No machine in this fleet is one -- the CUDA
hosts available here are H20 and RTX PRO 5000. Half of that side is covered
upstream: the weekly 4-gpu-b200 job runs
`test/registered/backends/test_flashinfer_trtllm_gen_moe_backend.py` and closes
with this result line:
`{"file": "test/registered/backends/test_flashinfer_trtllm_gen_moe_backend.py", "passed": true, "elapsed": 1226}`
(run `41255710082`, job `124698375297`, head
`cda284e47b`, 2026-11-01), and each of the three `--quantization mxfp8` launches
in that log resolves to `moe_runner_backend=flashinfer_trtllm_routed` -- the
routed variant, which this gate refuses on the same devices. The one combination
with no launch anywhere on SM100/SM103 is the bare `flashinfer_trtllm` paired with
`mxfp8`; in that job it appears against `fp8`, `modelopt_fp4` and `modelopt_mixed`
only. What it rests on is therefore the artifact read above (3,438 configs survive
the arch rule on sm100, 3,528 on sm103), not a run. The remaining gap is two
environment variables wide rather than one network: point `FLASHINFER_CUBIN_DIR`
at the seeded directory, set `FLASHINFER_NO_DOWNLOAD=1` and run the call above on
the hardware. No full `mxfp8` server launch was attempted on SM120 either -- the
gate fires while the arguments are still being resolved, which is upstream of the
launch it is meant to stop.
