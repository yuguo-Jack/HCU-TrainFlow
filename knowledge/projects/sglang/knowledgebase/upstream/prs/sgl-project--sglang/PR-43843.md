# Guard get_masked_input_and_mask torch.compile against XPU, not just NPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/43843) · state: closed · merged: False

## Original PR description

## Summary

`VocabParallelEmbedding.get_masked_input_and_mask` is decorated with `@torch.compile(dynamic=True, backend=get_compiler_backend(), disable=_is_npu)` — this guards against NPU but not XPU.

torch.compile/Inductor codegen on Intel XPU under tensor parallelism is unreliable for this function, causing either:
- a scheduler watchdog timeout (stuck in Inductor's compile-worker subprocess, see `torch/_inductor/compile_worker/subproc_pool.py` in the thread dump), or
- a hard crash directly inside the compiled function: `RuntimeError: level_zero backend failed with error: 40 (UR_RESULT_ERROR_OUT_OF_RESOURCES)`

This affects any TP>1 vision model that routes position-embedding lookups through `VocabParallelEmbedding` on `intel_xpu`, observed on `meta-models/Muse-Glimmer-30B` (TP4) and `internlm/Intern-S2-Preview` (TP8) — both crash/hang inside `get_masked_input_and_mask` via `VocabParallelEmbedding.forward` → `_embed_local_shard`.

`sglang/srt/speculative/spec_utils.py` already guards the identical pattern with `disable=_is_npu or _is_xpu`; this applies the same guard here.

## Fix

Add `_is_xpu = is_xpu()` and change the decorator to `disable=_is_npu or _is_xpu`.

## Test plan

Validated on real XPU hardware (4x Intel Arc Pro B60, TP4) against the exact `lmsysorg/sglang:v0.5.21-xpu` release image running `meta-models/Muse-Glimmer-30B`:

- Before fix: crashes inside `get_masked_input_and_mask` (via `muse_glimmer.py` vision tower → `position_embedding_table`) on the very first vision-embedding lookup, every run.
- After fix: the crash no longer occurs at that call site, confirmed across multiple runs — the model proceeds past vision embedding into decode.

Note: on this specific 24GB-per-card hardware at TP4, a separate, pre-existing `mem_fraction_static` headroom issue (unrelated to this fix) can still surface a `UR_RESULT_ERROR_OUT_OF_RESOURCES` later during decode at the default 0.85 static KV-cache fraction — confirmed independent of this change and resolved by lowering `--mem-fraction-static`. That is a deployment-config tuning issue, not an sglang code bug, and is being tracked separately.
