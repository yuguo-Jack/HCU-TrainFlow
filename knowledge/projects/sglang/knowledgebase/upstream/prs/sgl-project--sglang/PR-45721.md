# [Fix] kimi_k3: Stream tool-call arguments instead of buffering the whole call

[Upstream PR](https://github.com/sgl-project/sglang/pull/45721) · state: open · merged: False

## Original PR description

### What

`--tool-call-parser kimi_k3` emits nothing while the model generates a tool call. `parse_streaming_increment()` matched only a **complete** call through `_CALL_RE`, so not even the tool name shipped until `<|close|>call<|sep|>` arrived — and the whole argument blob was then delivered as a single delta. For a `write_file` call carrying a few thousand tokens of `content`, that is tens of seconds of silence, long enough for gateways with a per-chunk idle timeout to kill the request.

Every other detector (`BaseFormatDetector`, `KimiK2Detector`, Qwen, DeepSeek, …) streams `arguments` incrementally. The K3 XTML format carries explicit open/close markers per argument, so it streams just as easily. This PR takes the approach described in the issue's *Proposed fix* section.

### How

The whole-call regex in the streaming path is replaced by a five-state scanner over the buffer:

| state | action |
| --- | --- |
| `seek_call` | find `<\|open\|>call`, holding back a partial marker suffix |
| `call_attrs` | on `<\|sep\|>`, emit `ToolCallItem(name=…, parameters="")` then `{` |
| `seek_arg` | find the next `<\|open\|>argument`, or emit `}` at `<\|close\|>call<\|sep\|>` |
| `arg_attrs` | on `<\|sep\|>`, emit `"k": "` (or `, "k": "` after the first argument) |
| `arg_value` | stream `type="string"` payloads escaped, or buffer non-strings until their close tag |

Two details worth calling out:

- **Escaping is fragment-safe.** `json.dumps` escapes per code point and never re-interprets a fragment boundary, so `_json_escape(a) + _json_escape(b) == _json_escape(a + b)`. That is what makes character-by-character streaming of string arguments correct.
- **Non-string arguments stay buffered.** `type="number"`, `"boolean"` and `"object"` values are emitted JSON-decoded at their close tag. Streaming their raw text *and* the decoded value would double-emit them; they are short, so nothing is lost.

The concatenation of all `parameters` deltas stays **byte-identical** to the non-streaming `json.dumps(arguments, ensure_ascii=False)` output, which is what `serving_chat`'s final-diff logic assumes when it slices `expected_call[len(actual_call):]`. `prev_tool_call_arr` and `streamed_args_for_tool` are kept in sync as deltas are emitted.

`detect_and_parse` (non-streaming) is untouched.

### Tests

`test/registered/function_call/test_kimik3_detector.py`:

- `test_streamed_deltas_match_non_streaming_bytes` — parametrized over chunk sizes `[1, 3, 17, 512]` × awkward payloads (embedded quotes, backslashes, control chars, unicode/emoji, empty string, and payloads containing literal `<|close|>argument<|sep|>` / `<|open|>argument key="evil" …<|sep|>` marker text). Asserts the reassembled deltas equal the one-shot output byte for byte, and that the detector's own bookkeeping agrees.
- `test_streaming_arguments_are_not_buffered_until_call_close` — >80% of a long payload ships while the call is still open.
- `test_streaming_emits_name_before_call_completes` — the name goes out with `parameters=""` as soon as the header is complete.
- `test_streaming_mixed_argument_types`, `test_streaming_call_without_arguments`.

Existing tests that assumed one delta per call were updated to fold deltas before asserting (`_reassemble` helper).


Verified end to end through `FunctionCallParser.parse_stream_chunk` at chunk sizes 1/2/7/64/4096: accumulated deltas match the one-shot result, and `serving_chat`'s final-diff logic finds nothing remaining.
