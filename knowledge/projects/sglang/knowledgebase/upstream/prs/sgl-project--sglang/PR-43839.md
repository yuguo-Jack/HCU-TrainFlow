# [Perf] [AMD] qwen3_5: Quantize the BF16 GDN projections to MXFP4 online

[Upstream PR](https://github.com/sgl-project/sglang/pull/43839) · state: closed · merged: True

## Original PR description

## Motivation

This ROCm performance change quantizes the BF16 GDN `in_proj_qkvz` and `out_proj` of Qwen3.5 / Qwen3.8 to MXFP4 once after load and runs them on AITER MXFP4 GEMMs instead of BF16 hipBLASLt, because the Quark MXFP4 checkpoints keep both projections in BF16, and cuts median TPOT by **5.1% with NEXTN MTP and 4.0% without MTP** for Qwen3.8-2.4T-A95B MXFP4 on 8x MI355X, TP8, geomean over 12 serving shapes on the SGLang main nightly with only this PR added. Output tok/s goes up by 5.9% and 4.2%. The change is on by default on gfx95x with `SGLANG_USE_AITER=1`. `SGLANG_ROCM_GDN_ONLINE_MXFP4=0` turns it off.

At TP8, `in_proj_qkvz` is a 4608x8192 weight per GPU and the largest dense weight that every decode and verify step reads. A retuned BF16 GEMM table for these shapes gave no end-to-end gain (99.8% of the current table), and no BF16 kernel we tried beat hipBLASLt on 4608x8192. An MXFP4 weight with its scales is about a quarter of the bytes. At 16 rows, the MXFP4 `in_proj_qkvz` and the BF16 `in_proj_ba` take 8.1 + 7.9 us, and the packed BF16 GEMM of both takes 23.1 us.

## Modifications

- `environ.py` adds the boolean `SGLANG_ROCM_GDN_ONLINE_MXFP4`. The default is true. `0` keeps the BF16 projections.
- `quark_w4a4_mxfp4.py` adds `AiterMxfp4OnlineLinearMethod`. A model sets it on a BF16 linear layer after `create_weights`. The loader then calls `process_weights_after_loading()`, which quantizes the loaded BF16 weight with the existing `dynamic_mxfp4_quant`, preshuffles the weight (16x16) and the E8M0 scales, and records whether AITER has a tuned preshuffled config for (N, K). A second call does nothing. `apply()` quantizes the activation with `per_1x32_f4_quant_hip`. Up to 64 rows with a tuned config, it runs the Triton `gemm_afp4wfp4_preshuffle`. All other batches run the ASM `gemm_a4w4(bpreshuffle=True)`.
- `qwen3_5.py` reads the variable at import. It has an effect only on gfx95x with `SGLANG_USE_AITER=1`, and only for the Qwen3.5 / Qwen3.8 model types (`qwen3_5_text`, `qwen3_5_moe_text`). There, each GDN layer sets `AiterMxfp4OnlineLinearMethod` on `in_proj_qkvz` and `out_proj` in `__init__`, so the model loader quantizes them in `load_model`, before SGLang sizes the KV cache and captures the CUDA graphs. It skips projections that the checkpoint already quantized, and projections with N or K not a multiple of 256. Models that reuse `Qwen3_5GatedDeltaNet`, such as `qwen4_exp` and `interns2_mobius`, keep BF16. An MXFP4 `in_proj_qkvz` is no longer an `UnquantizedLinearMethod`, so `finalize_fused_in_proj()` in `prepare_before_cuda_graph_capture` does not build the packed BF16 qkvz+ba GEMM, and `in_proj_ba` (N=32) runs alone in BF16.
- `test/registered/amd/test_qwen35_gdn_online_mxfp4.py` checks both TP8 shapes at 1, 4, 16, 31, 32, 64, 65 and 256 rows against a dequantized FP32 reference. The rows cover both sides of the 32-row scale-layout split and of the 64-row kernel cut. `register_amd_ci` puts it in the MI35x suite, because it skips on anything other than gfx95x.
- `environment_variables.mdx` adds one row for the new variable.

With `SGLANG_ROCM_GDN_ONLINE_MXFP4=0`, nothing changes. No layer is quantized, and `finalize_fused_in_proj()` builds the packed BF16 path as before. With the default, only the GDN projections of Qwen3.5 / Qwen3.8 on gfx95x with AITER change. Other platforms and other models do not change. The MI35x nightly accuracy tests of Qwen3.5-397B (BF16 and MXFP4) and Qwen3.8 MXFP4 now run the MXFP4 projections.

The Triton path for `in_proj_qkvz` needs the tuned config from [Rocm/aiter5998](https://github.com/ROCm/aiter/pull/5998) (merged). The AITER pin on main, `2bb549102b` (#44379), includes it. With an older AITER, such as `e7d2453f`, `in_proj_qkvz` takes the ASM path at every row count. The output is still correct there, but we did not measure the speed.

The MXFP4 projections do not support online weight updates, because quantization changes the weight shape and dtype at load. Set `SGLANG_ROCM_GDN_ONLINE_MXFP4=0` on servers that receive weight updates. The memory that the BF16 weights free (about 5.5 GB per GPU on Qwen3.8 TP8) goes to the KV cache, because quantization runs before SGLang sizes the pool. The pool grows by 6.4%, from 6.65M to 7.07M tokens with NEXTN and from 7.39M to 7.86M without MTP. The speed tests below ran on the first commit, which quantized after the pool was sized. There, both servers of each pair have the same KV pool, and peak usage was 63% and 56%. The speedup does not come from memory.

## Accuracy Tests

The unit test passes on MI355X, with a relative error below 1e-2 for every shape and row count. It also checks that a second `process_weights_after_loading()` call does not quantize the MXFP4 weight again. It ran in the benchmark job before the servers started.

The end-to-end evals ran on the same servers as "Speed Tests and Profiling" below. BF16 is the same image with the variable off.

| Eval | NEXTN BF16 | NEXTN MXFP4 | No MTP BF16 | No MTP MXFP4 |
| --- | ---: | ---: | ---: | ---: |
| GSM8K 5-shot, chat, thinking, flexible-extract (1319) | 0.9765 | 0.9742 | 0.9788 | 0.9818 |
| GPQA Diamond (198, thinking, temperature 1.0) | 0.9343 | 0.9091 | 0.9343 | 0.9242 |
| RULER niah_single_2, 64k | 0.996 | 0.994 | 0.996 | 0.996 |
| RULER niah_single_2, 128k | 0.994 | 0.990 | 0.998 | 0.996 |

With plain MXFP4 on these projections, the model thinks for longer. We repeated the thinking-length check of [vllm#62750](https://github.com/vllm-project/vllm/pull/62750) without MTP: thinking-on GSM8K, temperature 1.0, 8 reps of 1319 questions per arm. The MXFP4 answers are 10.7% longer than BF16 (95% CI 6.1% to 15.7%), and the accuracy goes from 0.9641 to 0.9597 (McNemar p = 0.0017). Where long reasoning matters more than the per-token speed, set `SGLANG_ROCM_GDN_ONLINE_MXFP4=0`. A Hadamard-32 rotation in the MXFP4 activation quant removes most of the increase ([Rocm/aiter6734](https://github.com/ROCm/aiter/pull/6734), open). It is a follow-up PR after the AITER pin moves.

## Speed Tests and Profiling

8x MI355X, TP8, one node, all four servers in one job. The image is `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261016` (SGLang main `34c4ba14c8`, AITER `2bb549102b`) plus the first commit of this PR, `ad94c3c8f2`, and no other change. The later commits make the variable a boolean that is on by default, limit it to the Qwen3.5 / Qwen3.8 model types and to shapes with N and K multiples of 256, change the CI suite and comments, and move the quantization into the load path. "Load path check" below compares the load path with the first commit. Page size 16, `SGLANG_USE_AITER_UNIFIED_ATTN=1`, fp8 KV cache, `--mamba-ssm-dtype bfloat16`, chunked prefill 16384, radix cache off, at most 256 running requests. NEXTN runs use 3 steps, top-k 1, 4 draft tokens, `--enable-linear-replayssm-spec` and `--speculative-draft-model-path` set to the model path. `bench_serve` random dataset, range ratio 0.8, one run per cell.

### Load path check

The same nightly image plus this PR at `0542071e02` (quantization in `prepare_before_cuda_graph_capture`) or at `2c6ceb33c0` (quantization in the load path). Both set `SGLANG_ROCM_GDN_ONLINE_MXFP4=in_proj_qkvz,out_proj`, the list form of those commits, and the flags above. The servers ran on one node in the order capture, load, load, capture, with and without NEXTN. 8k / 1k, one `bench_serve` run per cell and round. The table gives the mean of the two median TPOTs.

| Mode | Concurrency | TPOT at capture (ms) | TPOT in load path (ms) | Change |
| --- | ---: | ---: | ---: | ---: |
| No MTP | 1 | 10.480 | 10.490 | +0.1% |
| No MTP | 4 | 13.455 | 13.460 | +0.0% |
| No MTP | 16 | 22.115 | 22.150 | +0.2% |
| No MTP | 64 | 41.800 | 41.840 | +0.1% |
| NEXTN | 1 | 3.645 | 3.640 | -0.1% |
| NEXTN | 4 | 5.790 | 5.820 | +0.5% |
| NEXTN | 16 | 10.860 | 10.890 | +0.3% |

Between two rounds of the same server, the median TPOT moves by up to 2.8%. Every server logs 138 MXFP4 projections. GSM8K (first 50 questions, 5-shot, chat, thinking, greedy, flexible-extract) gives 0.98 in all four runs without MTP. With NEXTN, it gives 0.98 and 0.96 for each commit. All eight runs miss the same question, and one round of each NEXTN server misses one more, a different question each time.

We ran only Qwen3.8-2.4T-A95B MXFP4 at TP8. Qwen3.5 checkpoints and other TP sizes are untested.
