# [MoE] Improve NCCL EP LL decode with single-compute-stream TBO

[Upstream PR](https://github.com/sgl-project/sglang/pull/39546) · state: closed · merged: False

## Original PR description

## Motivation and behavior

Use **one compute stream and two independent communication streams** for eligible NCCL EP LL TBO decode. The two subbatches keep their own communication resources while their compute stages execute in order on a shared stream. Existing SBO/TBO flags remain opt-in; no compute-stream switch or kernel-tuning override is added.

The archived four-GPU experiment measured **+10.01% and +16.33% B/A throughput** for this scheduling choice. The dual-compute-stream alternative C was **3.54% and 6.89% slower than B** at those same points. These are fixed-BM16, single-run results from an experimental tree, **not measurements of this updated production head or default kernel settings**. Smaller synthetic workloads include regressions and are shown below.

This PR remains **Draft**. The update reuses existing evidence; no local tests, GPU benchmarks, GSM8K, profiler runs or documentation builds were rerun. Upstream CI is reported separately.

## Original-model decode performance and the compute-stream choice

Definitions used in both tables:

- **A:** unsplit execution, TBO disabled.
- **B:** two subbatches, one compute stream, two communication streams; the selected production scheduling policy.
- **C:** two subbatches, two compute streams, two communication streams; retained as the experimental alternative.

**4x RTX PRO6000 96G; original E64 `gaunernst/DeepSeek-V2-Lite-Chat-FP8`; TP=DP=EP=4; top-k 6; input128/output1024.** Each GPU holds 16 routed experts/layer. GPU0/1 and GPU2/3 use NODE paths, with SYS paths between pairs. Triton attention/FP8/MoE; fixed BM16, BN=BK128, GROUP_M32, four warps and three stages for both expert projections. Model revision: `2f6d5dd458e5d9673719d03d30c488866be52e1a`.

| Global batch | Mean rows/expert/child | A tokens/s | B tokens/s | C tokens/s | B/A | C/B | C/A |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1024 | 48 | 5035.2 | 5539.3 | 5343.0 | **+10.01%** | **-3.54%** | +6.11% |
| 2048 | 96 | 5100.2 | 5933.1 | 5524.2 | **+16.33%** | **-6.89%** | +8.31% |

**C regresses relative to B at both measured points, which supports selecting the single compute stream for these workloads.** C still beats A. B already permits communication/compute overlap; C/B measures the additional compute-stream choice. The measurements do not identify the cause of the regression or prove that one compute stream is optimal for all workloads. No trace was collected in this four-GPU experiment.

Throughput uses actual client SSE token arrivals inside the common interval from a verified full-batch, all-rank decode window: 32 guard steps and 256 measured steps, exact Graph buckets, no prefill, retraction or admission-retry increase. B/C use identical delivered-token counts and KV-length-bin distributions at each batch. TTFT and full-request time are separate; no TTFT improvement is claimed. The LL dispatch capacities are 256/512 per rank; the KV pool is fixed at 655360 tokens/rank (18.984375 GiB). Rows/expert/child are theoretical means.

Each configuration ran once on an independent server, without profiling or retry. The order was batch1024 A→B→C, then batch2048 C→B→A. These observations have no repeatability or statistical-significance claim. The six cases, including the C results, are all reported.

C64/C256 denote client in-flight request limits. The server running-request cap remains **128 globally, 64 per DP rank**, so C256 includes server-side queuing; it does not mean 256 simultaneously active decode tokens. TTFT includes server queuing. Per-request TPOT is `(E2E − TTFT) / 255`.

- 2× RTX PRO 6000 Blackwell Server Edition, SM120, 97,887 MiB/GPU; **SYS across NUMA nodes**, bidirectional CUDA P2P available, no NVLink.
- Driver 580.95.05; CUDA toolkit 13.0.88; Torch 2.11.0+cu130; Triton 3.6.0; nccl4py 0.4.1; nccl-extensions 0.1.0. The loaded NCCL library reports **2.30.7**, and `nccl.ep.get_lib_version()` reports 0.2.0.
- Model: `gaunernst/DeepSeek-V2-Lite-Chat-FP8`, revision `2f6d5dd458e5d9673719d03d30c488866be52e1a`.
- TP=DP=EP=2; DP attention and DP LM head enabled; attention TP=1 and dense TP=1. Triton attention, FP8 GEMM and MoE; default cuBLAS router. Shared-expert fusion and overlap scheduler disabled.
- NCCL EP low-latency mode with CUDA Graphs; LL capacity 64/rank; decode Graph buckets 2/4/8/16/32/64; prefill chunk 64 globally (32/rank); context 4096; KV capacity 131072; memory fraction 0.6; page size 1. `CUDA_DEVICE_MAX_CONNECTIONS=8`, `NCCL_CUMEM_ENABLE=1`.

**Measurement protocol**

- Each point starts a fresh server, runs **512 warmup requests** at the target concurrency, flushes cache, then measures **2048 requests**.
- Identical saved synthetic token-ID inputs and order across all six points: **128 input tokens / exactly 256 generated tokens**, temperature 0, seed 32774, EOS ignored. Special tokens are excluded from inputs, and every prompt has a unique first token. Radix cache stays enabled; measured cached tokens were zero.
- The pinned upstream serving benchmark runs streaming requests at unlimited offered request rate, bounded by the client concurrency limit. A wrapper supplies the saved token-ID workload and retains per-request records. Throughput includes request fill and drain. No Nsight/profiler; lightweight server metrics and GPU telemetry are sampled at approximately 1 Hz.
- Fixed execution order: C64/none → C256/SBO+multistream → C64/SBO → C256/SBO → C64/SBO+multistream → C256/none.
- Workload SHA256: `c88e6ce3b6930999231272e28ff1d10b3edfb37511b64c7b1734606e5bd220e8`.

**Validation and scope**

All six points completed **2048 requests and 524,288 output tokens, with zero request errors and zero cached tokens**. Independent checks verified request IDs and lengths, resolved configuration switches, throughput counts, and Mean/P50/P95/P99 TTFT, TPOT and E2E statistics recomputed from the raw request records. Reconstructed client request interval peaks were 64 and 256, respectively.

Before measuring, each configuration passed an eight-request sequential full-model check: all 256 output token IDs matched the none baseline exactly, and output logprobs were finite. This adds native/full-model evidence for these **SBO configurations at this commit**, but does not establish concurrent-output equivalence, broad model quality, or current-head TBO correctness.

There was one valid formal run per point, with no selection of the best run. Controller-only issues around cache-flush response parsing, result serialization and startup draining were corrected outside formal timing; the first completed valid result was retained, and no product code or benchmark workload was changed between valid runs.

These results cover this model, fixed-length synthetic workload and SYS topology. They are **not directly comparable to the earlier natural-EOS TBO workload** in the PR description.
