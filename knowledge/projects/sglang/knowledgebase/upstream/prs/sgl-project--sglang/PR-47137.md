# [Perf] [NVIDIA] gdn: Narrower value tile for the packed GDN decode on SM90

[Upstream PR](https://github.com/sgl-project/sglang/pull/47137) · state: open · merged: False

## Original PR description

## Motivation

`fused_recurrent_gated_delta_rule_packed_decode` is the GDN decode step of every linear-attention layer in Qwen3.5/Qwen3.8 hybrid models, and on SM90 it is the default path (Triton linear-attention backend, FP32 SSM state from the checkpoint's `mamba_ssm_dtype`). It launches `grid = (V / BV, B * HV)` with one warp per program and BV = 32, so at B = 1 with 48 value heads (Qwen3.8-27B at TP1) that is 192 single-warp programs on a 132-SM part, each walking a 128 x 32 state slice. On SM90 with an FP32 state, BV = 4 is faster at every measured shape.

This is the decode counterpart of the SM90 BV = 4 tile that `_select_recurrent_launch_config` already uses for GDN `target_verify`. Not a duplicate: #42372 also widens that branch to packed decode, but as part of a 753-line SSD weight-offload PR; this PR is only the tile change, with its own measurements. The same tile was merged in vLLM for the same kernel (vllm-project/vllm#63864).

## Modifications

`python/sglang/kernels/ops/attention/fla/fused_recurrent.py`: in `fused_recurrent_gated_delta_rule_packed_decode`, use BV = 4 when K = V = 128, the state is FP32 and `is_sm90_supported()`. Every other case keeps its current tile: BF16 states (no single tile wins everywhere on SM90), other architectures (including the existing SM100 B = 1 case), other head dims.

`test/registered/kernels/ops/attention/test_gdn_packed_decode_sm90_tile.py` (new, SM90 only): checks that an FP32 state launches with BV = 4 and gives bit-identical output and updated state to the BV = 32 launch (4 shapes, including a non-power-of-two batch), and that a BF16 state keeps BV = 32.

## Accuracy Tests

Each program reduces over the full K for its own V rows, so a narrower V tile computes the same recurrence in the same order. Output and updated state are bitwise identical to BV = 32 at all 110 FP32 points of the sweep below (and at all BF16 points, which keep BV = 32 anyway). Model outputs are therefore unchanged.

All numbers below are on main at eead03f (this PR's base) plus this change: the `lmsysorg/sglang:nightly-dev-cu13-20261028-586355a8` image (dependency pins identical to main's `pyproject.toml`; Triton 3.8.0, torch 2.14.1+cu130) with its `sglang` package replaced by the checkout. Tests on H200:

## Speed Tests and Profiling

### Kernel (cold L2)

H200 NVL (132 SMs, 60 MiB L2), K = V = 128, BF16 qkv, QK L2-norm on, FP32 state. Each CUDA graph cycles through enough disjoint state slots that the state touched between two uses of a slot is >= 4x L2 (240 MiB), so the state is never L2-resident, as in a decode step. Kernel time from CUPTI (`torch.profiler`) over graph replays; 7 rounds with the tile order shuffled each round, median reported (round-to-round spread <= 1.7%). Speedup of BV = 4 over BV = 32:

(16, 48), (8, 24), (4, 12), (2, 6) are Qwen3.8-27B at TP 1/2/4/8.

BV = 4 is the fastest of {4, 8, 16, 32} at all 110 points: 1.08-1.98x, geometric mean 1.26x. With a BF16 state the best tile varies (BV = 16 at 73 of 110 points, BV = 4 at 33, BV = 32 at 4; BV = 4 alone ranges 0.88-1.85x), so BF16 is left at 32.

Why (Nsight Compute, H200, Triton 3.8.0): with an FP32 state the BV = 32 kernel uses 212 registers per thread, so an SM holds at most 8 of these single-warp programs (12% theoretical occupancy); BV = 4 uses 56 registers and is limited only by the 32-blocks-per-SM cap (50%). At B = 1, (H, HV) = (16, 48), the 192 BV = 32 programs leave one or two warps per SM to cover DRAM latency (2.3% achieved occupancy, vs 16% with BV = 4). At B = 512 there is plenty of work, but DRAM throughput is still 81% of peak with BV = 32 vs 86% with BV = 4. DRAM traffic is the same for every tile (the repeated per-program q/k reads hit in L2), but a narrower tile executes more instructions: about 2x for BV = 4 vs BV = 32. With an FP32 state the kernel stays memory-bound and hides them. With a BF16 state the bytes halve, BV = 4 executes 2.4x the instructions of BV = 32 at B = 512 and reaches only 67% of DRAM peak, which is why BV = 4 is not used for BF16.

### End to end

Qwen/Qwen3.8-27B-FP8 (48 GDN layers, FP32 SSM state from the checkpoint), main with and without this change (same image as above), one H200 NVL, TP1, default backends (Triton linear attention, FA3), `--disable-radix-cache --max-running-requests 64`. `sglang.bench_serving --dataset-name random-ids`, 1024 in / 128 out, range ratio 1, 4 warmup requests; 32 / 64 / 256 prompts at concurrency 1 / 8 / 32. "Predicted" is the per-call kernel saving at that batch (H, HV = 16, 48) x 48 layers over the unpatched step time; the packed decode is 2.6% of a step at batch 1, 7.6% at batch 8 and 19% at batch 32. The measured gain at batch 8 and 32 is somewhat larger than this estimate. An earlier run of the same benchmark on `lmsysorg/sglang:v0.5.22` (same `fused_recurrent.py`) gave -1.2% / -2.1% / -1.8%.
