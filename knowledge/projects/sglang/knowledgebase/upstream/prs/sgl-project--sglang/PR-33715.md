# [Fix] detokenizer router: Route by rid without tokenizer worker ipcs and broadcast logging config

[Upstream PR](https://github.com/sgl-project/sglang/pull/33715) · state: closed · merged: True

## Original PR description

`MultiDetokenizerRouter` keys each request on its `http_worker_ipc`, which is only stamped with more than one tokenizer worker. Two failures follow:

- With `--tokenizer-worker-num 1 --detokenizer-worker-num > 1`, the scheduler sends `http_worker_ipcs` as a list of `None`, and the router fails its assertion on the first batch (`AssertionError: ... has invalid http_worker_ipcs`).
- `ConfigureLoggingReq` is routed like a single request, so only one detokenizer gets the new logging config. With one tokenizer worker, it hits the same assertion.

Changes:

- When a request has no `http_worker_ipc`, the router hashes its `rid` instead. Requests that have one keep the current key, so the grouped sends from #42238 and #44288 are unchanged.
- `ConfigureLoggingReq` is broadcast to every detokenizer, like `FreezeGCReq`.
- `_split_batch_by_key` takes the per-request keys and copies `http_worker_ipcs` from the output.

Verified on one H200 with Llama-3.2-1B-Instruct: on main, `--tokenizer-worker-num 1 --detokenizer-worker-num 2` crashes the router on the first request. With this PR, `/generate` and `/configure_logging` return 200 at 1/2 and 2/2 tokenizer/detokenizer workers.

Tests: `test_router_keys_on_rid_without_tokenizer_worker_ipcs` and `test_router_broadcasts_logging_config_and_routes_single_req_by_rid` in `test/registered/unit/managers/test_multi_tokenizer_mixin.py`.
