# [Perf] [AMD] attention: Use paged Gluon MLA decode in the aiter backend on gfx1250

[Upstream PR](https://github.com/sgl-project/sglang/pull/44458) · state: open · merged: False

## Original PR description

## Motivation

Using the aiter paged Gluon `mla_decode_fwd` that runs on gfx1250 with a bf16 Q over a bf16 or FP8 KV cache and reads sglang's paged KV pool through block tables. This PR extends the aiter backend's MLA decode to use it on gfx1250.

## Modifications

On gfx1250 with one CP rank, the aiter backend runs MLA decode on the paged Gluon kernel when the backend uses bf16 activations, a nonzero rope head dim and page size 64. Batches with more than one query token per sequence, including speculative verify and draft extend, run the aiter ASM decode as on gfx950. DCP keeps its existing path, and gfx950 is unchanged.

- The wrapper is `PagedGluonMlaDecode` in `aiter_mla_gluon.py`, next to the gfx950 `mla_gluon` wrapper. `SGLANG_AITER_MLA_GLUON=0` turns both off.
- The page table is rebuilt at the first layer from the graph-static batch tensors, so CUDA graph replay stays valid.
- When the paged decode is created, the persistent ASM kernel is turned off, since aiter has none for gfx1250.
- CPU unit test: `test/registered/unit/layers/attention/test_aiter_mla_gluon_paged_gate.py`.

Requires ROCm/aiter#5935, which both ROCm Docker pins in `docker/rocm.Dockerfile` already contain.

Validated on gfx1250 with Kimi-K2-Thinking-MXFP4 at TP8 (8 heads per GPU). 

## Accuracy Tests

GSM8K, 8-shot, 1319 questions:

|---|---|---|
| Before | FP8 | 0.944 |
| After | FP8 | 0.939 |

## Speed Tests and Profiling

`bench_serving`, 8k input / 1k output, concurrency 4. Before uses the triton decode backend; after uses the aiter decode backend with page size 64.

- kkHuang-amd · comment · 2026-11-04T02:00:19Z · [source](https://github.com/sgl-project/sglang/pull/44458#issuecomment-6620495174)

Reviewed the full diff. The feature itself is well-scoped and the tests are unusually thorough for a backend gate — the gate, the dispatch, the persist-kernel interaction, and "the gfx950 kernel must not be picked on gfx1250" are all covered. My comments fall into two groups: a layering concern about where the new code lives, and a few correctness gaps.

## Layering: the dependency direction is inverted

`aiter_mla_gluon.py` is currently a pure-function wrapper module. `mla_gluon_decode()` takes explicit tensors and never sees the backend:

```python
def mla_gluon_decode(
    *,
    q: torch.Tensor,
    k_buffer: torch.Tensor,
    layer: RadixAttention,
    kv_indices: torch.Tensor,
    kv_indptr: torch.Tensor,
    sm_scale: float,
    min_kv_seq_len: int,
    ...
)
```

The backend assembles metadata and calls it. One direction, no cycle.

`PagedGluonMlaDecode` reverses that. It takes the whole `AiterAttnBackend` in `create()`, reads `backend.input_dtype` / `page_size` / `dcp_world_size` / `req_to_token` / `device`, stores `self.backend` and later does `self.backend.kv_layers.read(layer.layer_id).key()`, and `aiter_mla_gluon.py` now needs a `TYPE_CHECKING` import of `AiterAttnBackend` while `aiter_backend.py` imports it at runtime. On top of that, `_create_paged_gluon_mla_decode()` mutates `aiter_backend`'s module globals (`_use_mla_ps_kernel`, `fast_mode`, `intra_batch_mode`) from inside the constructor path.

The kernel code does stay in the separate file, so the split is preserved on the surface — but the backend's state has moved into the kernel wrapper rather than the other way round. The symptom is visible in the new test: it has to build a backend with `AiterAttnBackend.__new__(AiterAttnBackend)` and hand-populate a dozen attributes plus a `KVLayerRouter`, where testing `mla_gluon_decode` needs only tensors.

There is also an existing mechanism being bypassed. `block_tables`, `seq_lens` and `cu_seqlens_q` are per-forward metadata, and the backend already has `init_forward_metadata` / `forward_metadata` for exactly that. Instead they are rebuilt inside the kernel wrapper, using `first_layer_id` to detect "this is the first layer of this forward" — a per-forward concern implemented inside a per-layer call path.

Suggested shape, matching the module's existing style:

- `paged_mla_gluon_decode(*, q, o, kv_buffer, block_tables, seq_lens, cu_seqlens_q, page_size, kv_lora_rank, qk_rope_head_dim, sm_scale, kv_descale)` as a plain function;
- `supports_paged_gluon_decode(*, input_dtype, page_size, dcp_world_size, qk_rope_head_dim) -> bool` as a pure predicate for the capability check;
- `block_tables` / `seq_lens` / `cu_seqlens_q` built in `init_forward_metadata`, and the persist-kernel decision left in the backend where the other `_use_mla_ps_kernel` logic already lives.

That removes the import cycle, drops `first_layer_id` entirely, and lets the wrapper be tested with tensors.

## Correctness

### 1. Disabling the PS kernel on gfx1250 is tied to the wrong condition

The comment states the reason as an architectural fact:

> aiter ships no persistent-scheduling MLA ASM kernel for gfx1250

but the code ties it to whether the paged kernel was successfully created:

```python
paged = PagedGluonMlaDecode.create(...)
if paged is not None:
    _use_mla_ps_kernel = False
    fast_mode = False
    intra_batch_mode = False
```

Every path where `create()` returns `None` therefore leaves PS enabled on gfx1250, i.e. running a kernel that by the comment's own premise does not exist: `SGLANG_AITER_MLA_GLUON=0`, `page_size != 64`, `dcp_world_size > 1`, `input_dtype == float16`, or an aiter too old to expose `aiter.ops.triton.attention.mla`.

The first one is the worst, because this PR's own env description promises it as the safe fallback:

> Set to 0 to force the aiter ASM `mla_decode_fwd` fallback on both (benchmarking / emergency disable).

If the premise holds, these should be two separate decisions: disable PS unconditionally under `is_gfx1250_supported()`, then decide independently whether the paged kernel can serve.

Related: the `elif` means `log_mla_gluon_capability(logger)` no longer runs on gfx1250. Harmless today since the gfx950 Gluon path is disabled there anyway, but it is an implicit consequence of the restructure rather than a stated one.

### 2. `logit_cap` is silently dropped

Every ASM decode path passes `logit_cap=layer.logit_cap` (`aiter_backend.py:1645`, `:1707`). The paged kernel has no such parameter, and `accepts()` only checks `spec_info is None and forward_mode.is_decode()`. A model with soft capping would get a silently wrong result rather than an error. MLA models are typically 0 here, but the gate should say so explicitly.

### 3. `SGLANG_AITER_MLA_DECODE_BACKEND` is not honoured

The existing Gluon path yields to ASM when asked:

```python
if prefer_mla_gluon_decode(...) and not (
    _use_mla_ps_kernel
    and self.mla_decode_backend == "asm"
    and self._asm_ps_supports_qlen(max_q_len)
):
```

The new paged branch is inserted ahead of all of this and never consults `self.mla_decode_backend`. On gfx1250, setting `SGLANG_AITER_MLA_DECODE_BACKEND=asm` has no effect; the only escape is `SGLANG_AITER_MLA_GLUON=0`, which also cancels the PS disable (point 1). The two switches' semantics are worth sorting out together.

## Worth discussing

**Is this kernel actually Gluon?** The import is `aiter.ops.triton.attention.mla.mla_decode_fwd`, which is not under `aiter.ops.triton.gluon` like the gfx950 one. Yet the class is `PagedGluonMlaDecode`, the docstring says "paged Gluon", and the kill switch reuses `SGLANG_AITER_MLA_GLUON`. If it is a regular Triton kernel, the name will mislead later readers — and putting two unrelated kernels behind one switch is precisely what makes points 1 and 3 worse.

**`page_starts` spans `max_context_len / page_size`, not the actual sequence length.** Every forward gathers a full `bs × (max_ctx / 64)` table. At 128k context and bs=256 that is ~512K int32 gathered per forward, on the decode critical path, when the kernel only reads up to `seq_len`. The forward metadata already knows `max_seq_len` and could bound the width.

**`first_layer_id` is never reset.** The comment argues it never moves because `accepts()` depends only on the batch. But the object outlives CUDA graph capture and eager replay, and the code itself notes that "a frozen-KV MTP draft swaps the backend's pool". If the same backend is ever driven over a different subset of layers (draft/target, or a hybrid backend owning only some layers), the pinned id stops being the first layer of the current forward and the page table goes stale. Moving the build into `init_forward_metadata` makes this disappear rather than needing an argument.

**Module globals mutated from an instance method.** `global _use_mla_ps_kernel, fast_mode, intra_batch_mode` matches what `__init__` already does, so this is not introduced here. But factoring it into a separate method leaves the ordering requirement carried only by the comment ("Must run before `use_any_mla_persist`").

**Test coverage gap.** The one case not covered is the one in point 1: gfx1250 where `create()` returns `None` — what should `_use_mla_ps_kernel` be then?

**Nit:** `from sglang.srt.utils import is_gfx95_supported, is_gfx1250_supported` is not in isort order (`1` sorts before `9`); pre-commit will reorder it.
