# [Fix] scheduler: Count a request's held req_to_token row once at admission

[Upstream PR](https://github.com/sgl-project/sglang/pull/44401) · state: closed · merged: True

## Original PR description

- Count a request that already holds a `req_to_token` row once at admission. Such a request (a continuing chunked prefill, a streaming-session borrow, a dLLM staging request) is in `can_run_list`, and its row is already excluded from `req_to_token_pool.available_size()`, so the gate `len(can_run_list) >= get_num_allocatable_reqs(...)` counted it twice and declared the batch full with a row still free.
- `get_num_allocatable_reqs` takes `num_held_rows` and adds those rows back to the pool term only; the `pp_max_micro_batch_size` term still counts every request. The main gate, the PD-prefill gate, and the dLLM gate pass `sum(r.kv.holds_kv for r in adder.can_run_list)`.
- Under chunked prefill this capped the running batch at `max_running_requests - 1`, and when the final chunk's pass set `batch_is_full`, nothing cleared it until a request finished, so the waiting queue starved meanwhile.
- Fix two stale comments: a chunked request keeps its row across chunks (no longer "just released"), and `update_running_batch` is no longer the only other place that clears `batch_is_full`.
- Add a CPU unit test that drives `_get_new_batch_prefill_raw` with a final chunk, two running requests, and one free row, in normal and PD-prefill mode; it fails on main.

Behavior change: a prefill pass whose batch already contains a row-holding request now admits one more request per held row; with no such request, admission is unchanged.

Fixes #38118, fixes #35537; supersedes #30295, which found the chunked-prefill case.
