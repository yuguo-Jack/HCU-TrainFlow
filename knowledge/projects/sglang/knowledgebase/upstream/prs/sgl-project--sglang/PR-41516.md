# [Perf] MiMo-VL: Shard vision encoding across the DP encoder

[Upstream PR](https://github.com/sgl-project/sglang/pull/41516) · state: open · merged: False

## Motivation

With `--mm-enable-dp-encoder`, each rank keeps a full copy of the MiMo vision tower's weights. But `MiMoV2ForCausalLM` still passed every image and video to `self.visual` on every rank, so each GPU encoded the full multimodal input and the extra ranks added no speedup. This PR spreads MiMo-VL vision encoding across the attention-TP ranks, the way Qwen2.5-VL, Qwen3-VL and GLM already do. That way, a request with many images or a long video isn't encoded in full on every GPU.

## Modifications

- `python/sglang/srt/models/mimo_v2.py`
  - `get_image_feature` and `get_video_feature` now share one `_encode_visual` path.
  - Without DP encoding, behavior is unchanged: patches are concatenated and encoded with the original `grid_thw`.
  - With DP encoding, inputs go through `run_dp_sharded_mrope_vision_model` with `rope_type="rope_3d"`:
    - Videos are split into single frames (`[t, h, w]` becomes `t × [1, h, w]`) so frames can be balanced across ranks, as `glm5_next` already does. The output is identical because MiMo's vision tower computes its rotary positions, window-attention ordering and `cu_seqlens` per frame.
    - Each rank gets its pixel data through `load_local_pixel_values`, so it only concatenates and encodes the rows it was assigned.
  - Replaced the `assert`s with a check that each item's patch count matches its grid. A mismatch now raises a clear `RuntimeError`.
- `python/sglang/srt/models/mimo_vl.py`
  - Added `MiMoVisionTransformer.out_hidden_size`. The DP helper reads it to build an empty output on a rank that gets no inputs.
- `test/registered/unit/models/test_mimo_v2_vision_dp.py` (new, CPU CI `base-a-test-cpu`), which checks that:
  - the non-DP path keeps the packed video grid;
  - the DP path splits a video into frames and the loader returns only the requested rows, for both images and videos;
  - with one rank, the real helper encodes all frames in a single call;
  - with two ranks, a rank that gets no inputs doesn't run the encoder, and receives an output of the right shape (built from `out_hidden_size`) from the owning rank;
  - a patch-count / grid mismatch raises.

## Accuracy Tests

Setup: MiMo-V2.6-Pro, TP=EP=8 on 8× H20, `--mm-enable-dp-encoder` on in both runs. Requests went through the OpenAI-compatible chat API, greedy (`temperature=0`), thinking disabled. Inputs are synthetic but generated from fixed seeds, so both runs got identical inputs with known answers:

- **Single image (10):** read a 4-digit number from a 1280×720 image.
- **Multi-image order (6):** 8 images, each showing one character; list them in image order. This checks that per-image embeddings come back in the right order after sharding.
- **Video order (3):** a 48-frame clip showing 6 digits in sequence; list them in order. This checks frame order after the per-frame split. Adjacent repeated digits count as one, because they render as a single longer segment.

| Task | main | This PR |
|---|---|---|
| Single image | 10/10 | 10/10 |
| Multi-image order | 6/6 | 6/6 |
| Video order | 3/3 | 3/3 |
| **Total** | **19/19** | **19/19** |

All 19 greedy answers are identical between the two runs.

## Speed Tests and Profiling

Same server and setup as above. Each number is the latency of one chat request with `max_tokens=1`, so it is almost entirely prefill including vision encoding: median of 5 runs after 1 warmup. Every request uses distinct images, so the multimodal embedding cache is never hit. The latency includes about 0.3 s of gateway overhead, shown by the text-only row.

| Workload | Prompt tokens | main | This PR | Speedup |
|---|---|---|---|---|
| Text only | 14 | 0.316 s | 0.336 s | – |
| 1 image, 1280×720 | 896 | 0.691 s | 0.698 s | 0.99× |
| 8 images, 1280×720 | 7,070 | 2.253 s | 1.888 s | **1.19×** |
| 16 images, 1280×720 | 14,126 | 4.073 s | 3.407 s | **1.20×** |
| 64-frame video, 1280×720 | 14,208 | 4.260 s | 3.627 s | **1.17×** |
| 8 concurrent single-image requests (total time) | 896 each | 2.389 s | 2.039 s | **1.17×** |

Multi-image, video and concurrent image requests get 17–20% faster end to end. This saves about 0.37 s at 8 images and about 0.65 s at 16 images or 64 frames. The encoder-only saving is larger than these ratios suggest, because the times also include language-model prefill over about 14k tokens. A single image is unchanged, as expected: one image goes to a single rank either way.
