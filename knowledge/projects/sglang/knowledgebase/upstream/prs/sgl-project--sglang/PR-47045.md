# [Fix] disaggregation: Agree on each prefill KV transfer's outcome across PP stages

[Upstream PR](https://github.com/sgl-project/sglang/pull/47045) · state: closed · merged: True

## Original PR description

## Motivation

With pipeline parallelism on a **PD-disaggregated prefill** server (`--disaggregation-mode prefill --pp-size N`, N > 1), the PP stages can disagree on whether a request's KV transfer succeeded. When they do, they release the request from the radix cache through different paths, and their prefix caches diverge.

Each PP stage sends the KV of **its own layers** through its own `disagg_kv_sender`. The release consensus in `event_loop_pp_disagg_prefill` (`_pp_pd_get_prefill_transferred_ids` → ring → `process_disagg_prefill_inflight_queue(rids_to_check)`) only agrees on **which** transfers have concluded: `KVPoll.Success` or `KVPoll.Failed`. Each stage then concludes the request using its own local poll:

| local poll | path | radix cache |
|---|---|---|
| `Success` | `release_kv_cache(req, tree_cache, checkpoint=True)` | release |
| `Failed` | `handle_inflight_transfer_failure(req)` | release **+** `tree_cache.finish(handle, ABORT)` (`release_aborted_request`) |

A client abort (`/abort_request` → `disagg_kv_sender.abort()` on every stage) that arrives **after the first stage has finished sending but before the later stages have** gives exactly this split. Stage 0 polls `Success`; stages 1..N-1 poll `Failed`. Both states count as "concluded", so the consensus passes, and then:

1. Stage 0 releases the request normally. Stages 1..N-1 also run `release_aborted_request`. The prefix caches are now different per stage.
2. Later requests match different prefixes on different stages, so the stages compute different extend lengths and schedule **different micro-batches**.
3. A later stage receives hidden states from the previous stage whose row count does not match its own batch. In our case this surfaced deep in the model as a shape assertion (`Size mismatch for shape#0('batch_size'): expected 32768 but got 32722` in the DSA indexer on PP stage 1). If the token counts happen to match, the stage silently computes KV from another batch's hidden states.

### How we found and reproduced it
- A PP4 prefill (2 prefill instances, 1 decode instance, Mooncake, 4×8 B300) crashed with the shape assertion above under production traffic. The traffic was long multi-turn prompts with high prefix-cache hit rates, where client cancellations and timeouts are routine.
- We enabled `SGLANG_ENABLE_RANK_CONSENSUS_CHECKER=1` and ran a stress client with 15% client-side cancellations. The client mixes long prompts across the chunked-prefill boundary, short prompts, a shared-prefix family, and bursts of 64.
- **On current main the checker fires within ~2 minutes.** For the diverging request, the later stages log `release_aborted_request(rid=...)` and stage 0 does not.
- The per-stage `ReqTimeStats` for the same request confirm the split: `transfer_total` was ~2.9 GB on stage 0 and **0 MB on stages 1–3**. In the same window, every other request was either sent by all four stages or by none.

## Modifications

- `scheduler_pp_mixin._pp_pd_get_prefill_transferred_ids` now returns `{rid: failed}` instead of a list of rids.
  - The concluded set is still the intersection over stages, as before.
  - The failure flag is OR-ed along the pipeline, so **a failure on any stage concludes the transfer as failed on every stage**.
  - The returned dict keeps the membership semantics of `rid in rids_to_check`, so the ring code that forwards it is unchanged.
- `prefill.process_disagg_prefill_inflight_queue(rids_to_check)` concludes each consensus rid with the consensus outcome rather than this stage's own poll. A stage that sent successfully but learns another stage failed takes the failure path.
  - The outcome is recorded with `rank_consensus_checker.assert_same`. This is a no-op unless `SGLANG_ENABLE_RANK_CONSENSUS_CHECKER` is set.
- Non-PP prefill (`rids_to_check is None`) and the decode side are untouched.

This change is deliberately conservative compared with a scheme where every stage follows stage 0's poll (see #45085):
- A request is released only once **every** stage has concluded its own transfer, so no stage frees pages its sender may still be writing.
- A failure on a later stage is not overridden by stage 0's success. The decode side would otherwise wait for layers it never receives.

## Accuracy Tests

N/A. There is no model-output change on the success path. On the race path above, the request is now concluded as failed on every stage (it was already failed on the later stages before this change).

## Speed Tests and Profiling

No measurable cost: one extra boolean per concluded rid in the existing per-iteration consensus message.

Stress test on the same PP4 PD setup (concurrency 96 plus bursts of 64, 15% client cancellations):

| image | first rank-consensus divergence |
|---|---|
| main | ~2 min (`release_aborted_request` on stages 1–3 only) |
| main + this PR | **none** in a full 30 min run (6,839 completed, 1,224 client-cancelled, 195M input tokens; no PP-stage divergence, no restarts) |
