# [Fix] lora: support PEFT rsLoRA and GDN adapters on Qwen3.5-family hybrid MoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/44704) · state: open · merged: False

## Original PR description

## Motivation

SGLang can't serve PEFT LoRA adapters that target the Gated DeltaNet (GDN) layers of Qwen3.5-family hybrid models (for example `Qwen/Qwen3.6-35B-A3B` and `nvidia/Qwen3.6-35B-A3B-NVFP4`). There are three separate problems:

1. **rsLoRA scaling is ignored.** Adapters trained with `use_rslora=True` are applied at `alpha/r` instead of `alpha/sqrt(r)`. At rank 64 that makes them 8× too weak, and served outputs look close to the base model's.
2. **GDN projections aren't loaded.** The target allowlist omits PEFT's GDN names (`in_proj_qkv`, `in_proj_z`, `in_proj_a`, `in_proj_b`). PEFT's combined `in_proj_qkv`/`in_proj_z` tensors aren't packed into the runtime `in_proj_qkvz`, and there is no packed target for the gating projections.
3. **Shared-expert-only adapters wrap the routed experts.** An adapter that targets only the dense shared expert still has the routed-expert bank wrapped for LoRA and gets expert LoRA buffers, because both paths use `gate/up/down_proj` names. That allocates unused memory. It also rejects MoE runner backends without routed LoRA support (for example native NVFP4 `flashinfer_cutlass`), even though the adapter never touches the routed experts.

## Modifications

Three commits, each reviewable on its own:

- **`fix(lora): honor rank-stabilized adapter scaling`.** Use `alpha/sqrt(r)` when the PEFT config sets `use_rslora`; ordinary LoRA is unchanged.
- **`fix(lora): load PEFT GDN projections for Qwen3.5 hybrids`.**
  - Normalize and pack combined QKV/Z into `in_proj_qkvz`. PEFT's shared `lora_A` is repeated per Q/K/V rank block.
  - Pack B/A into a new `in_proj_ba` target, in the base layer's order.
  - Add the target names, stacked multipliers and dimensions.
  - Add a synthetic public-model reproducer, `test/manual/lora/repro_qwen35_peft_dense_adapters.py`.
- **`fix(lora): leave untargeted routed experts on the base backend`.**
  - Infer from the initial adapters' tensors whether routed-expert LoRA is needed. When it isn't, leave the routed `FusedMoE` modules unwrapped and skip their LoRA buffers.
  - Starting with no initial adapters keeps the previous behaviour, so dynamic MoE loading still works.
  - Loading routed-expert tensors later into a dense-only pool raises a clear error instead of failing silently.

This adds no quantization kernel and no routed-expert LoRA implementation. The shared expert stays on its dense LoRA path (`--disable-shared-experts-fusion`).

## Accuracy Tests

- **Packing:** unit tests check that packed GDN products equal the original PEFT products, for both QKV/Z and B/A.
- **Synthetic public adapter**, rank 8 and 620 factors, generated from the public config only by the reproducer:
  - On `nvidia/Qwen3.6-35B-A3B-NVFP4` (revision `1355db6a`) with TP=2, all three public prompts change their next-token logprobs against the base.
  - Both TP ranks match all 380 normalized live factors exactly to their expected tensor slices.
  - Dynamic load and unload work.
- **Trained adapter:** a rank-64 rsLoRA adapter trained with PEFT on synthetic data, on attention, GDN and the shared expert. We compared fact recall on 445 held-out questions per adapter, served against local PEFT inference:
  - bf16 (`Qwen/Qwen3.6-35B-A3B`, TP=2): within ±0.007 for all three adapters tested.
  - NVFP4 with `flashinfer_cutlass` (TP=1 and TP=2, bf16 or fp8_e4m3 KV): 0.007 to 0.025 below local, consistent with quantization.
  - Without these patches, the same adapters can't be loaded, or they recall at base-model level.

## Speed Tests and Profiling

No kernel changes. For dense-only adapters, routed experts now skip the LoRA wrapper and buffers, so they run on the unmodified base MoE backend. We haven't benchmarked speed.

## Reproduction

```bash
python test/manual/lora/repro_qwen35_peft_dense_adapters.py \
  --model-path nvidia/Qwen3.6-35B-A3B-NVFP4 --base-model nvidia/Qwen3.6-35B-A3B-NVFP4 \
  --revision 1355db6a052410cfd62085d94b58866fd0f2c3c5 --output-dir /tmp/qwen-dense-lora

CUDA_VISIBLE_DEVICES=0,1 python -m sglang.launch_server \
  --model-path nvidia/Qwen3.6-35B-A3B-NVFP4 --revision 1355db6a052410cfd62085d94b58866fd0f2c3c5 \
  --served-model-name qwen --tp-size 2 --kv-cache-dtype fp8_e4m3 --moe-runner-backend flashinfer_cutlass \
  --enable-lora --lora-backend triton --lora-strict-loading --lora-paths dense-example=/tmp/qwen-dense-lora \
  --max-lora-rank 8 --max-loras-per-batch 2 --max-loaded-loras 2 --disable-shared-experts-fusion \
  --host 127.0.0.1 --port 30000

python test/manual/lora/repro_qwen35_peft_dense_adapters.py --output-dir /tmp/qwen-dense-lora \
  --check-only --already-loaded --check-url http://127.0.0.1:30000 --served-model qwen --adapter-name dense-example
```

The adapter is selected as `model=qwen:dense-example`. The random adapter shows the adapter is applied; it says nothing about task quality.

Validated on SM120 (RTX PRO 6000) with torch 2.14.1+cu130, transformers 5.19.0, FlashInfer 0.7.2 and sglang-kernel 0.4.10. GPU runs used the Python radix-tree backend, because the dev container lacked the source checkout's Rust extension.
