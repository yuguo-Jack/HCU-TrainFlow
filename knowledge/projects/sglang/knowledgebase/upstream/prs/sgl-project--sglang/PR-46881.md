# [Perf] [AMD] qwen4_exp: Fuse hyper-connection combine, norm and mix

[Upstream PR](https://github.com/sgl-project/sglang/pull/46881) · state: open · merged: False

## Original PR description

## Motivation

A qwen4_exp (Qwen3.8-Flash-Next) decode step crosses 96 gated hyper-connection boundaries. On ROCm each runs combine, per-branch RMSNorm and the low-rank mix (two GEMMs, 10240 x 320 and 320 x 10240) as 4-6 kernels: 46-56 µs per boundary on MI355X at 16-64 rows, 4.4-5.4 ms per step. With AITER's FlyDSL `hc_mix` (#41880) for the mix, the boundary takes 19-34 µs at 16-64 rows; the combine and the norm stay separate.

Related:
- #41880 (merged) runs AITER's FlyDSL `hc_mix` for the mix at 1-128 rows on gfx950, when the installed AITER has `aiter/ops/flydsl/hc_mix.py` (ROCm/aiter#5993). The AITER commit in `docker/rocm.Dockerfile` (285579b62) does not have it yet.
- #40552 reworks this boundary for SM100.

## Modifications

- `kernels/ops/gemm/hc_seam.py`: the boundary as three Triton launches (down projection with the combine fused in; reduction with norm, SiLU and the next gate; up projection with the gated mean), plus a combine-only kernel. Deterministic (no atomics or grid barriers), CUDA-graph safe; rows above 64 run in 64-row tiles.
- `GatedResidual.mix()` runs the seam for batches in the row window, decode or extend, and marks its result. The following `combine()` then runs only the combine kernel, and `seam_combine_mix()` fuses an attention write-back with the next FFN read (wired through `GatedResidualState` and `qwen4_exp.py`).
- The seam is checked before #41880's FlyDSL path. When enabled it also takes the rows FlyDSL would run. Per layer (one separate and one fused boundary) it took 9-43 % less time than FlyDSL at 1-128 rows (below).
- Opt-in, gfx950 (MI355X) only: `SGLANG_ENABLE_QWEN4_HC_SEAM=1`. Row window `SGLANG_QWEN4_HC_SEAM_MIN_ROWS` / `_MAX_ROWS` (default 1 / 193, kernel limit 256).
- Everything else keeps the existing path: other batch sizes, MTP draft layers (left for a follow-up), forwards traced by torch.compile, other GPUs.
- Numerics: the combined residual is bitwise the same as stock. The norm and mix sum in a different fp32 order, and the up-projection output is not rounded to bf16 (as in `fused_hc_mix`).
- New `benchmark/kernels/bench_hc_seam.py` and `test/registered/kernels/ops/gemm/test_hc_seam.py` (MI35x CI suite).

## Accuracy Tests

This PR's kernel and stock vs an fp64 evaluation of the same formula, on `lmsysorg/sglang-rocm:v0.5.23-rocm724-mi35x-20261030` with this PR's tree: 12 row counts from 1 to 193; separate, fused and mix-only calls; synthetic and checkpoint weights (144 cases).
- Combined residual: bitwise equal.
- Mixed output: relative L2 error at most 2.84e-3 (stock: 2.90e-3).
- Next gate: max abs error at most 2.04e-4.
  - At each row count, the worst case equals stock's; at 1 row it is lower.
  - Per case it is above stock's in 15 of 144, by at most 1.2e-7.

End to end, TP2 MI355X: `lmsysorg/sglang-rocm:v0.5.23-rocm724-mi35x-20261030` vs the same image with only this PR applied, `SGLANG_ENABLE_QWEN4_HC_SEAM=1` in both (default 1-193 rows; the baseline ignores it). Against #41880's FlyDSL `hc_mix`, the setup is the following:
- One image: the same nightly with this PR, plus AITER main's `hc_mix.py` and FlyDSL 0.4.1 as in the kernel table.
- `SGLANG_ENABLE_QWEN4_HC_SEAM` unset (FlyDSL mix) or `1` (this PR).
- 6 runs per arm and workload (server lifetimes FlyDSL, PR, PR, FlyDSL; three passes each).
- Warm caches: each arm first fills its FlyDSL and Triton caches in an unrecorded server lifetime, including FlyDSL `hc_mix` at all 128 row counts. No `hc_mix` or seam kernel compiled inside a timed pass. One unrelated Triton kernel (`chunk_fwd_kernel_o`) compiled once in each arm, in the same pass (c4, pass 2).
- GSM8K sanity (200 questions, chat 5-shot): FlyDSL 0.975, this PR 0.990.

- Values are FlyDSL mix → this PR, medians over the 6 runs. SE from each arm's run-to-run spread. Every TPOT and ITL change is beyond 2 SE; of the output tok/s changes, c4 and c64 are beyond it and c16 is within.
- Output tok/s is generated tokens over the benchmark's wall time, so it includes prefill.
- Median ITL fell by 0.17 / 0.27 / 1.12 ms at c4 / c16 / c64. The kernel table predicts 0.22 / 0.34 / 1.20 ms: 48 layers × (2 × FlyDSL mix − separate − fused).
- The gain is smaller than against the non-FlyDSL mix because FlyDSL's `hc_mix` already removes most of the boundary's time (16 rows: 51.78 → 19.05 µs). The seam also folds in the combine and the norm, which stay separate kernels on the FlyDSL path, and at 64-128 rows it takes 22-28 µs where FlyDSL takes 34-46 µs, hence the larger gain at c64.
- TPOT was the metric chosen before the run; output tok/s and ITL come from the same results.
- With fresh caches in every server lifetime, the changes are larger: TPOT -2.4 / -4.1 / -13.8 % and output tok/s +6.5 / +15.7 / +21.6 % at c4 / c16 / c64. The cause is compiles. FlyDSL's `hc_mix` compiles a kernel per row count (`M` is a `Constexpr`), and in the c64 run 59 and 72 of those compiles (the two FlyDSL server lifetimes) fell inside the timed passes. This PR compiled all of its kernels at server start.
