# [Perf] qwen4: pin the offloaded PLE table at its exact size

[Upstream PR](https://github.com/sgl-project/sglang/pull/48249) · state: open · merged: False

## Original PR description

## Motivation

With `--ple-offload-embedding` (the default for BF16 Qwen4-Exp on CUDA, and what the RTX PRO 6000 cookbook cells use), the PLE n-gram table lives in pinned host memory: `torch.empty(..., pin_memory=True)`. torch's caching host allocator rounds every block up to a power of two. For Qwen3.8-Flash-Next the FP8 table is 51,200,245,760 bytes (47.68 GiB), so the process pins **64 GiB**: 16.32 GiB of page-locked host RAM that holds nothing. The cookbook's RTX PRO 6000 notes accordingly require "≥ 64 GB of free RAM for the locked table". On hosts that run several engines per node, or that are RAM-limited, those 16 GiB per engine are the difference between fitting and not.

## Modifications

- `models/qwen4_exp_ple_table.py`: on CUDA builds the `pinned` backend allocates the table with `cudaHostAlloc`: same call and flags (`cudaHostAllocDefault`) as torch's pinned allocator, exact size. It is freed with `cudaFreeHost` when the table's storage is released. Non-CUDA builds keep `torch.empty(..., pin_memory=True)`. The `file` backend is unchanged.
- `mem_cache/pool_host/common.py`: the ownership logic of the ROCm host-pool allocator (`torch.frombuffer` over the raw allocation, free with the last view) becomes `alloc_owned_host_tensor(dims, dtype, alloc, free)`, shared by `_alloc_hip_host_tensor` and the PLE table.
- `distributed/device_communicators/cuda_wrapper.py`: `CudaRTLibrary` gains `cudaHostAlloc` / `cudaFreeHost`.
- Cookbook (`Qwen3.8-Flash-Next.mdx` and the deployment-panel config): the RTX PRO 6000 cells need ≥ 52 GB of free host RAM for the locked table, not ≥ 64 GB.
- `test/registered/kernels/ops/embeddings/test_qwen4_ple_offload.py`: a new test checks three things. The pinned table is page-locked, it does not come from torch's caching host allocator (`torch.cuda.host_memory_stats()` is unchanged), and device reads see the written rows. It repeats three times so a freed table's address range is reused. The existing gather tests now run on the new allocation.

Nothing else changes: same dtype, shape, pinned memory type and gather kernel.

The HiCache allocator (`alloc_with_host_register` on an anonymous mmap) was tried first. It pins the exact size too, but registered ranges are never unregistered when the tensor is freed. A later allocation that reuses the address then fails with `cudaErrorHostMemoryAlreadyRegistered`, which broke the existing PLE offload tests. `cudaHostAlloc`/`cudaFreeHost` tie the pinning to the storage's lifetime.

## Accuracy Tests

The table bytes and the gather are unchanged. `test_qwen4_ple_offload.py` (bitwise `assert_close(rtol=0, atol=0)` against `index_select`) passes on RTX PRO 6000: 12 passed, 3 skipped (the file-backend tests need a unified-memory device).

The full table as loaded from `nvidia/Qwen3.8-Flash-Next-NVFP4` is byte-identical: each tree's `allocate_ple_host_table((320001536, 160), float8_e4m3fn, "pinned")` (torch pinned on main, exact `cudaHostAlloc` here) is filled from the checkpoint's 128 PLE shards and hashed. Both give sha256 `b070f9644adf93794d8a1030584ab705809387e64396a9327a68fa3a3a6666b3` over 51,200,245,760 bytes, and device reads of sampled rows match.

End to end, with `nvidia/Qwen3.8-Flash-Next-NVFP4`, TP=1, on the same RTX PRO 6000 for main and this PR (launch command under Speed Tests):
- `sgl-eval run gsm8k --num-examples 200 --num-threads 32 --temperature 0 --max-tokens 2048 --chat-template-kwarg enable_thinking=false` (`sgl-eval==0.1.3`): main **96.00%** (5/200 truncated), this PR **97.00%** (3/200 truncated).
- No token-identical comparison is possible on RTX PRO 6000 (SM120): on this model and GPU, main is not repeat-deterministic. Two passes of the same prompt on one server give different prefill logprobs, and `--enable-deterministic-inference` fails at startup (QSA indexer `top_k_ragged_transform`, k=512). On a long synthetic prompt (3,000 numbered words), greedy output is token-identical across main, main again and this PR; short prompts diverge within main's own run-to-run range.
- Token-identical gates on GB200 and GB300, where deterministic inference works for this model (`--enable-deterministic-inference --attention-backend flashinfer`, `--ple-offload-embedding` with the FP8 PLE table, CUDA graphs on):
  - GB200, TP2 (`--moe-runner-backend flashinfer_cutlass --mem-fraction-static 0.85 --disable-radix-cache`): 7 greedy prompts, including a 3,000-word one, and an image chat give output ids identical to main, and every arm is repeat-identical.
  - GB300, TP1 (`--mem-fraction-static 0.80 --mamba-ssm-dtype bfloat16 --chunked-prefill-size 4096`): 16 of 16 chat responses (text prompts, one of 14,420 tokens, and image chats) are identical to main in tokens and logprobs.

## Speed Tests and Profiling

Host memory of the pinned table, allocated in a fresh process on RTX PRO 6000 (torch 2.14.1+cu130), shape (320,001,536 x 160) FP8. Both arms ran in the same container, and an earlier run of the pre-refactor code gave the same RssShmem figures:

| Allocator | Table bytes | Process RssShmem delta | cgroup delta |
|---|---|---|---|
| `torch.empty(pin_memory=True)` (main) | 51,200,245,760 | 68,719,476,736 (64.00 GiB) | 69,011,439,616 |
| this PR | 51,200,245,760 | 51,200,245,760 (47.68 GiB) | 51,543,834,624 |

Server: `python -m sglang.launch_server --model-path nvidia/Qwen3.8-Flash-Next-NVFP4 --ple-offload-embedding --json-model-override-args '{"text_config": {"ple_embedding_dtype": "float8_e4m3fn"}}' --moe-runner-backend flashinfer_cutlass --mem-fraction-static 0.85 --cuda-graph-max-bs-prefill 2048 --disable-radix-cache`, RTX PRO 6000 Blackwell Max-Q (300 W), same GPU for both arms.

| | main `8d4e1ce4c7` | this PR |
|---|---|---|
| Server processes, RssShmem | 68,763,598,848 B | 51,244,367,872 B (**−16.32 GiB**) |
| Server processes, VmRSS | 91,039,133,696 B | 73,543,540,736 B |
| GPU memory used after startup | 86,694 MiB | 86,720 MiB |
| Free device memory after the KV/mamba pools | 14.24 GB | 14.23 GB |

Each arm ran at least twice (the second time with the GSM8K run), and the RssShmem figures were byte-identical across runs of an arm. Device memory is unaffected. The KV pool differs slightly (140,928 tokens on main vs 137,728 here) because the PR run had 30 MB more free after weight loading (13.46 vs 13.43 GB), which shifts the split between the KV and mamba pools. Free device memory after both pools is within 10 MB.
