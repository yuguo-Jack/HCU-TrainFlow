## Motivation

Implement the TP1 fixed-slot recovery lifecycle proposed in #35376, building
on #39834.

This draft is logically dependent on #39834 and currently includes its
unmerged commit stack because GitHub cannot use another contributor's fork
branch as a pull-request base.

This draft now implements same-global-rank replacement using Mooncake for
recoverable process-group membership and the existing NIXL MoE endpoint APIs.
Runtime GPU/RDMA proof remains pending.

## Modifications

### Delivered in this draft

- Validates and binds runtime instance, topology generation, operation ID,
  allocation ID, and fixed global EP rank.
- Fences dispatch to the failed slot and disconnects its NIXL peers.
- Publishes replacement endpoint data in operation- and allocation-scoped
  TCPStore namespaces, preventing stale endpoint reuse.
- Reconnects replacement and survivor ranks through the existing two-sided
  `connect_ranks()` flow and waits for per-rank acknowledgements.
- Runs a correlated internal warmup before reporting `ready`.
- Retires completed local NIXL recovery state so a later replacement can be
  admitted.
- Adds CPU lifecycle/correlation tests and a manual same-rank replacement
  failure-injection test.

### Current limitations

- Recovery is limited to TP1 fixed slots.
- The supported composition is Mooncake process-group recovery with NIXL MoE
  communication. Pure NIXL/NCCL process-group recovery is not implemented.
- No GPU/RDMA two-allocation replacement end-to-end test has run.
- The local cross-VM evidence harness is prepared but intentionally not part of
  this PR. A NIXL API change will only be proposed if that run yields a minimal
  NIXL-only failing reproducer.

File: `python/sglang/srt/managers/tokenizer_control_mixin.py` · line 144

[P1] Do not wait for a reply from the failed rank

This registers recovery with the normal full-worker fan-out, but `DataParallelController.send_control_message()` dispatches only to `_active_workers`, which excludes workers whose health status is false. `TokenizerManager.update_active_ranks()` does not reduce this communicator's expected reply count. In a two-rank world with rank 1 dead, the recovery request reaches rank 0 and gets one reply, while the communicator still waits for two and times out. Recovery admission needs a correlated set of surviving recipients and a matching expected reply set; it cannot require the failed allocation to acknowledge its own recovery.

- julienmancuso · comment · 2026-10-08T15:29:47Z · [source](https://github.com/sgl-project/sglang/pull/42780#discussion_r4220936556)

File: `python/sglang/srt/elastic_ep/elastic_ep.py` · line 637

[P1] Validate the rank offset before indexing the active-rank array

The HTTP endpoint accepts any positive integer offset. Here the array is indexed before `register_recovery_operation()` calls `RecoveryOperation.validate()`. An offset beyond the array capacity raises `IndexError`, which `Scheduler.handle_recover_elastic_ep()` does not catch because it catches only `RuntimeError` and `ValueError`. That exception escapes the scheduler event loop and reaches the process-level handler that signals the parent with SIGQUIT. Please validate the topology/rank bounds before this access and return a deterministic request rejection instead of terminating the scheduler.

[P1] Support warmup when tokenizer initialization is skipped

With `--skip-tokenizer-init`, scheduler initialization sets `self.tokenizer = None`. This unconditional access therefore raises `AttributeError` as soon as an admitted recovery reaches `slot_restored`, after the phase has already advanced to `warming_up`. The error escapes idle housekeeping and can terminate the scheduler. This configuration matters for Dynamo's token-based serving path. Please obtain a valid warmup token from model configuration when no tokenizer is present, or reject unsupported configurations safely before admitting recovery.

[P1] Verify recovered membership before reporting ready

A matching request finishing without `FINISH_ABORT` does not establish that the replacement slot is still active. The elastic forward path can rebalance after a rank fault and rerun a forward on surviving ranks. If the replacement fails during warmup, that request can still finish normally, and this callback calls `complete_recovery_warmup(success=True)` and publishes `ready` without checking the recovered slot or current topology. A source-isolated reproduction reports success with the target slot inactive. Please require recovery-correlated membership/topology evidence as well as successful warmup before reporting readiness.

- julienmancuso · comment · 2026-10-08T15:29:47Z · [source](https://github.com/sgl-project/sglang/pull/42780#discussion_r4220936583)

[P1] Keep the retained scale result separate from recovery

`operation_succeeded` and `last_error` belong to the retained scale operation, whose `operation_id` is unchanged here. Recovery admission clears them, and `complete_recovery_warmup()` later sets the same `operation_succeeded` to `True`. For example, a failed `grow-1` followed by recovery of an original-world rank becomes a successful `grow-1` when warmup completes; while recovery is pending, the previously terminal scale operation becomes nonterminal. Scheduler scale retries read these fields directly. Please add separate recovery result/error fields and leave the completed scale result immutable. The tokenizer recovery-update path also currently writes the shared `elastic_last_error`.

- julienmancuso · comment · 2026-10-08T15:29:47Z · [source](https://github.com/sgl-project/sglang/pull/42780#discussion_r4220936589)

File: `python/sglang/srt/elastic_ep/elastic_ep.py` · line None

[P1] Release pending-operation exclusion after recovery finishes

Every recovery phase other than `idle` is treated as a pending recovery here, and `request_scale()` has the same exclusion. Successful warmup leaves the phase at `ready`, with no subsequent reset or terminal-phase exception. After one successful recovery, a different recovery always conflicts and every later scale request is rejected. An aborted warmup similarly leaves scheduler state at `warming_up`, even though the tokenizer receives a terminal failure. Please distinguish terminal recovery results from an in-flight recovery, retain the result for same-operation retries, and allow a new operation after completion or failure.

- julienmancuso · comment · 2026-10-08T15:29:47Z · [source](https://github.com/sgl-project/sglang/pull/42780#discussion_r4220936607)

File: `python/sglang/srt/managers/tokenizer_manager.py` · line None

[P1] Reconcile unknown recovery submissions on retry

After the communicator times out or is cancelled, this method records `submission_unknown` with no terminal result. An identical retry returns through this cached-state branch without querying or resubmitting to the scheduler, while a different operation is rejected as pending. If the original request was never accepted, or its rejection response was lost, no warmup completion update will arrive to resolve the state. The operation can therefore remain stuck indefinitely. Please reconcile scheduler acceptance using the same immutable operation identity, as the scale submission path already does, rather than returning an unknown state forever.

[P2] Let terminal recovery completion win over late acceptance

While the communicator is awaited, `forward_elastic_scale_update()` can receive the terminal recovery update and set the phase to `ready` and the result to successful. When the awaited acceptance responses subsequently return, this unconditional assignment overwrites the phase with their earlier `restoring` value. Status and retries can then permanently show `recovery_succeeded=True` but `recovery_phase=restoring`, with no later update to correct it. Please preserve a terminal result that arrived during submission and return that result instead of the stale acceptance response.
