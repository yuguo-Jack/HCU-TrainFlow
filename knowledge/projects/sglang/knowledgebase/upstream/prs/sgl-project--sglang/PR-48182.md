# [Fix] rust-server: Accept replayed assistant reasoning that Python accepts

[Upstream PR](https://github.com/sgl-project/sglang/pull/48182) · state: closed · merged: False

## Original PR description

## Motivation

The Rust server returns 400 on replayed assistant messages that Python accepts:

- `reasoning` with `reasoning_content`, even if one is null, fails with ``duplicate field `reasoning_content` ``.
- An object or number `reasoning` fails to parse as `ReasoningContent`.

Dynamo aliases `reasoning` to `reasoning_content`, even in `dynamo-protocols` 10.0.0, the latest release. This affects every model outside the five renderer models (DeepSeek-V4, V4.1, GLM-5.3, Kimi-K3, Qwen3.8), and their requests that the lowered route declines, such as `tool_choice: required`.

A client replaying a full assistant message can send these shapes, and open #47175 adds both fields to Python replies. #44109 is the Python and renderer sibling and lists this failure as a limit.

## Modifications

`ChatBody` folds `reasoning` in a copy of the body that only the typed parse reads. A string fills a missing or null `reasoning_content`, and any other `reasoning` is dropped.

Two results need review:

- A string list `reasoning` reached the template on main and is now dropped, as in Python.
- On the renderer models, string `reasoning` with null `reasoning_content` now behaves like `reasoning` alone. The prompt omits the text until #44109 merges, unless the renderer declines and the template renders the body. Kimi-K3 and Qwen3.8 handle ordinary floats but decline `1e-6` or `-0` tool arguments, GLM-5.3 declines `-0`, and DeepSeek-V4 and V4.1 never decline.

## Accuracy Tests

No accuracy evaluation ran.

Real Qwen3-0.6B servers on one B200, at main `62f9f3f785`, gave these `usage.prompt_tokens` or statuses. Histories ended with a `<tool_response>` turn.

| Assistant fields | Python on main | Rust on main | Rust with this PR |
| --- | --- | --- | --- |
| `reasoning_content` | 43 | 43 | 43 |
| string `reasoning` | 33 | 43 | 43 |
| `reasoning` and `reasoning_content` | 43 | 400 | 43 |
| `reasoning` and null `reasoning_content` | 33 | 400 | 43 |
| `reasoning` and empty `reasoning_content` | 33 | 400 | 33 |
| null `reasoning` and `reasoning_content` | 43 | 400 | 43 |
| null `reasoning` and null `reasoning_content` | 33 | 400 | 33 |
| object `reasoning` | 33 | 400 | 33 |
| object `reasoning` and `reasoning_content` | 43 | 400 | 43 |
| number `reasoning` | 33 | 400 | 33 |
| list `reasoning` | 33 | 43 | 33 |

#44109 changes Python's 33 to 43 on the rows where this PR gives 43. With both fields, a hand-edited server reply, streaming and `tool_choice: required` went from 400 to 200. No captured client request was tested.

The new test fails on main. On Linux, merged with current main, the clippy hook commands were clean. `cargo test -p sglang-server` found only an intermittent timeout in `explicit_abort_during_batch_preprocessing_preserves_other_items`, which main also shows. One-off tests outside this PR covered the renderer models.

Not validated: real weights on the renderer models, a runtime merge with #44109 or #47175, and runtime CI.
