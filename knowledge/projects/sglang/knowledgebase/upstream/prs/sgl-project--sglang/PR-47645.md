# [Fix] [AMD] aiter: Plan the DCP asm verify shard with the draft tokens under CUDA graph replay

[Upstream PR](https://github.com/sgl-project/sglang/pull/47645) · state: open · merged: False

## Original PR description

## Motivation

- At DCP, aiter's asm cp verify (#34537) reads the draft tokens from the KV cache, so each rank's KV shard must span `seq_lens + num_draft_tokens`.
- Under CUDA graph replay, the shard was planned from `seq_lens`. Every rank dropped its draft tokens and the verify never attended them.
- Result: Kimi-K3 at DCP8 lost about 2.5 points of GSM8K (0.939-0.952 vs 0.97). Eager mode and the Gluon verify were correct.

## Modifications

- `_apply_cuda_graph_metadata` plans the DCP shard with `kv_lens`, as eager does:

| Verify route | KV lengths planned |
|---|---|
| asm cp verify | `seq_lens + num_draft_tokens` (was `seq_lens` on replay) |
| Gluon verify | `seq_lens` (draft tokens come from `k_window`, unchanged) |

- `TestAiterDcpVerifyGraphReplay` replays a DCP8 verify on both routes; the asm case fails before the fix.

## Accuracy Tests

Kimi-K3, 8x MI355X, TP8/DCP8, asm cp verify, CUDA graphs. GSM8K: sgl-eval 0.1.3, 1319 questions, real acceptance, Kimi-K3 preset.

| Setup | GSM8K | Accept length |
|---|---|---|
| Before (7 runs) | 0.939-0.952 | 3.84-4.33 |
| After, DSpark block 7, 1 request | **0.9666** | 4.39 |
| After, c16 recipe (block 4, batch up to 32) | **0.9689** | 3.33 |
| Reference: DCP1 / DCP8 with the Gluon verify | 0.9704 / 0.9757 | 4.39 / 4.49 |

- A debug-only replay check (not part of this PR) found every shard one token short in 320 of 320 replays before the fix, and correct in 320 of 320 after.

## Speed Tests and Profiling

- None needed: each rank attends one more token per request.
