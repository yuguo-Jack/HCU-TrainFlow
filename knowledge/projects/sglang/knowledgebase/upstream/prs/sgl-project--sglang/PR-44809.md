# [Feat] tracing: Record detokenizer time on root spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/44809) · state: open · merged: False

## Original PR description

## Motivation

Time spent in the detokenizer is invisible in traces. It sits between the scheduler's spans and the tokenizer's, so it shows up as unexplained latency between them.

## Modifications

- With tracing on (`--enable-trace`), `DetokenizerManager.handle_batch_token_id_out` times each batch it handles, from the start of decoding (beam-search and standard) until the output is built, and sends the duration in a new `BatchStrOutput.detokenize_duration` field. The field is `None` when tracing is off.
- `TokenizerManager._handle_batch_output` adds the duration to every request in the batch, and `set_finished_time` puts two attributes on the root span:
  - `detokenize.total_ms`: summed time of the batches that carried the request (each request waits for its whole batch);
  - `detokenize.batches`: number of those batches.
- Multi-tokenizer routing copies the per-batch duration into every sub-batch: `_handle_output_by_index`, plus a `_PER_BATCH_FIELDS` exception in the generic `_handle_output_by_indices`, which would otherwise call `len()` on the float and fail.

Root-span attributes rather than a span per batch keep the span count unchanged.

## Accuracy Tests

Not applicable: tracing only, no change to model outputs.

## Speed Tests and Profiling

With tracing off, the duration isn't sent, so the cost is one `perf_counter` read and a few branches. Measured with `timeit` (Xeon 8375C, Python 3.11):

| Where | Cost, tracing off |
| --- | --- |
| Detokenizer, per batch | ~55 ns |
| Tokenizer, per batch | ~30-70 ns |
| Tokenizer, per request | ~3 ns |

## Tests

- `test_req_time_stats.py::test_sums_detokenize_time_over_the_batches_that_carried_the_request`, which also checks that a request no batch carried gets no attributes.
- `test_multi_tokenizer_mixin.py::test_split_keeps_the_batch_detokenize_duration` (single and grouped split).
- Existing tests that run `handle_batch_token_id_out` (`test_output_decode.py`, `test_trim_matched_stop.py`) pass.
- End to end on 2× L4 (Qwen2.5-0.5B-Instruct, spans exported to Jaeger): a 32-token streamed chat request recorded `detokenize.batches=10`, `detokenize.total_ms≈0.9` on a regular TP=2 server, and the same on the decode root under PD disaggregation.
- `test/registered/unit/observability`, `managers` and `disaggregation` fail the same tests as `main` and no others.
