# [Perf] LoRA: bound csgmv CUDA-graph segment grids by token count

[Upstream PR](https://github.com/sgl-project/sglang/pull/46743) · state: closed · merged: True

## Original PR description

## Motivation

CSGMV LoRA kernels launch one program per segment and column tile. Inside a CUDA graph the launch grid is fixed at capture, so the current code sizes the segment axis to the whole static metadata buffer. That buffer is sized for the largest captured batch, and every captured graph launches a program for each of its entries, which is unnecessary.

## Modifications

-  Add `csgmv_segment_grid_size` as a helper:
   - Eager launches are unchanged and use the batch's exact segment count
   - A CUDA graph launches `num_tokens // MIN_CHUNK_SIZE + max_loras_per_batch` segment programs, capped at the metadata capacity

## Accuracy Tests

- Added a new regression test
- Checked that related LoRA kernel tests pass

#### Setup

I benchmarked on 1xH200:

1. Start the server:

```
CUDA_VISIBLE_DEVICES=0 python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --enable-lora \
    --max-loras-per-batch 8 \
    --lora-paths \
        adapter0=trentmkelly/gpt-4o-distil-Llama-3.1-8B-Instruct \
        adapter1=nvidia/llama-3.1-nemoguard-8b-topic-control \
        adapter2=t83714/llama-3.1-8b-instruct-limo-lora-adapter \
        adapter3=chaeryu/llama-3.1-8b-instruct-summary-ko-100k \
        adapter4=asanchez75/Llama3.1-8b-mcq-lora \
        adapter5=algoprog/fact-generation-llama-3.1-8b-instruct-lora
```

2. Run the benchmark:

```
python3 -m sglang.bench_serving \
    --backend sglang \
    --base-url http://localhost:30000 \
    --dataset-name random \
    --num-prompts 400 \
    --max-concurrency 32 \
    --random-input-len 512 \
    --random-output-len 512 \
    --lora-request-distribution uniform \
    --lora-name \
        adapter0 \
        adapter1 \
        adapter2 \
        adapter3 \
        adapter4 \
        adapter5
```
