# [Perf] hicache: bound full-hit staging waits (superseded by #46451)

[Upstream PR](https://github.com/sgl-project/sglang/pull/40361) · state: closed · merged: False

## Original PR description

**Superseded by #46451, which is open and ready for review.** GitHub rejected reopening this closed PR; the updated implementation, regression tests and H20 results are being reviewed in #46451. The original diff is retained here for history.

## Motivation

In single-engine cache mode, short-lived host-pool pressure can prevent an otherwise reusable storage-hit span from being staged completely. Add an opt-in, bounded wait for complete staging while keeping the existing partial-prefix policy as the default.

Pending operations must also survive cancellation safely: revoking one operation must not submit its successor twice, and a late query notification from an old attempt must not revoke or change the accounting of its replacement.

## Modifications

- Track parked cache-mode hits by request handle and validate operation identity before processing hit notifications or allocating staging.
- Remove revoked hits in place and continue checking smaller hits when a larger span cannot fit.
- Add `--hicache-storage-prefetch-host-capacity-wait-ms` (default `0`). Positive values enable full-span staging with a per-hit wall-clock deadline and the existing allocation retry cap. Reaching either cap ends that prefetch operation and permits recomputation; the existing stop/admission policy still applies.
- Keep partial staging as the default. The new wait policy is disabled for buffer-only mode and TP/PP/CP groups larger than one.
- Add eight CPU regression cases using real revoke, allocation and accounting paths, covering expired heads, cancellation at different positions, terminated operations, request-ID reuse, late replaced attempts, smaller-request progress, and deadline cleanup.
- Document the new flag and its sustained-pressure tradeoff.

## Speed Tests and Profiling

Controlled experiment: one NVIDIA H20-3e, TP1, Qwen3.5-35B-A3B, Triton attention/MoE, direct IO with `page_first_direct`, and an isolated TCP Mooncake instance. A stored 16,384-token prefix is replayed with one additional input token and 16 output tokens, alongside one concurrent short request. Each case has five interleaved measured repetitions after a warm round.

Pressure is imposed by real host-pool reservations, leaving 4,096 staging tokens available. In the transient case the reservation becomes releasable after 25 ms and is freed on the next scheduler drain; this is not a fixed 25 ms actual-release guarantee. The bounded policy uses a 300 ms per-hit wait and eight allocation retries. The immediate full-miss control has zero allocation retries, while storage-miss polling is held constant.

Long-request TTFT medians:

| Host capacity | Partial staging (default) | Immediate full-span miss | Bounded full-span wait |
| --- | ---: | ---: | ---: |
| Unconstrained | 247.8 ms | 249.7 ms | 249.6 ms |
| Transient pressure | 1445.6 ms | 1413.7 ms | 304.9 ms |
| Sustained pressure | 1425.4 ms | 1343.1 ms | 1680.6 ms |

In this controlled transient case the bounded policy reduces long-request TTFT by **78.9%** versus partial staging. The concurrent short-request median changes from **232.4 ms to 143.0 ms**. Under sustained pressure, long-request TTFT increases by **17.9%** versus partial staging, supporting the opt-in default.

A full restore is credited as `storage=16384, device=0, host=0` and reads 381.4 MiB across KV and Mamba state. On this hybrid model the 4,096-token partial transfer reads 80 MiB but is not credited as a usable cached prefix. These results do **not** establish the same gain for ordinary full-attention models, remote/RDMA storage, production traffic, or throughput/SLO improvements.

Runtime boundary: the H20 experiment reuses an existing **Torch 2.13.0+cu129 / sglang-kernel 0.4.6.post1+cu129** environment with `SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1`. It exercises the candidate cache code against base `30dc2f94303e339431cbd51489b2d1719678b0c1`; it does not validate the project's standard CUDA13 dependency stack. The final main refresh does not change the tested cache/controller source bytes.
