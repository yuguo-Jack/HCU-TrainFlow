# [HiCache] Retry parked cache-mode storage hits on host capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/40361) · state: closed · merged: False

## Original PR description

## Motivation

In cache mode, a complete L3 storage hit is currently revoked as soon as the L2 host pool cannot stage the full span. A transient capacity shortfall can therefore cause a full recompute even though the store holds the complete prefix and capacity may become available shortly afterward.

This extends the full-hit staging path with a bounded cache-mode pending queue. A parked operation retries without shrinking its storage-hit length or hash list. If capacity returns, the full prefix is transferred; if it does not, the existing `host_capacity` safe-miss path remains unchanged.

## Modifications

- Add `PrefetchOperation.host_capacity_retries`.
- Add `UnifiedRadixCache.pending_storage_hits`, a FIFO queue for cache-mode full hits that cannot yet allocate their complete L2 staging span.
- Retry parked hits before servicing new hits, preserving queue order.
- Reuse `--hicache-storage-prefetch-retry-max-attempts` as the bounded retry budget.
- Enable the pending queue only for a single-engine cache topology. Distributed TP/PP/CP ranks keep the existing deterministic immediate safe miss until their capacity decisions can be synchronized explicitly.
- Remove a request's parked operation when its prefetch is revoked.
- Keep the full `storage_hit_count` and hash list unchanged; no partial L3 transfer is issued.
- Add CPU regressions for parking, capacity recovery, bounded safe-miss timeout, and the distributed immediate-safe-miss boundary.

The scheduler already skips requests whose prefetch is still in progress and continues examining later waiting requests, so a parked request does not block the queue.

- `test/registered/unit/mem_cache/test_storage_prefetch_lifecycle.py` — 12 passed.
- `test/registered/unit/mem_cache/test_hicache_staged_write_back_dispatch.py` — 17 passed, 1 existing skip.
- `test_unified_radix_cache_unittest.py -k storage` — 41 passed, 24 existing skips.
- Controlled Mooncake E2E, capacity never recovers:
  - Qwen3-4B, one H20-3e, TP=1, Triton, `write_through + wait_complete`.
  - Mooncake `batch_exists()` returned `16010 / 16010`.
  - L2 had 2,551 tokens available; full staging needed 16,010.
  - Nine full-staging attempts (initial plus eight retries) failed.
  - No partial `batch_get_v1()` was issued.
  - The replay used a normal prefill (`cached_tokens=0`) and produced the same output.
- Controlled Mooncake E2E, capacity recovers:
  - L2 capacity was 67,817 tokens.
  - The first two 16,010-token staging allocations were injected as transient failures.
  - After host eviction raised availability from 3,769 to 19,781 tokens, the next allocation succeeded.
  - The operation issued 125 × 128-page batches plus one 10-page batch, all successfully.
  - Replay returned `storage=16010`, `device=0`, `host=0`, and matched the original output.
