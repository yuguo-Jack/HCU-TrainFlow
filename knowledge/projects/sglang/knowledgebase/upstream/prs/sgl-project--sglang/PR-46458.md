## Original PR description

# [Perf] paged-experts: fewer host syncs in host-planned steps

## Motivation

This PR aims to decrease TTFT.

Currently, Paged Experts (#42557) plans a step on the host when it routes more entries than the K resident slots: prefill, and decode batches past `K // top_k`. Such a step runs in waves, and each MoE layer syncs with the GPU 6 times plus once per wave (twice on the compacted Marlin path): two reads of the device LRU state, `torch.unique().tolist()`, a blocking upload of each wave's slot map, a `nonzero()` per compacted wave, `step.item()`, and two blocking uploads of the state back. Each wave then pages its experts in with one copy per expert and paged tensor (4 for GPTQ, 6 for NVFP4).

Profiling Qwen3-30B-A3B-GPTQ-Int4 at K=92 on an RTX 5070 Ti, the GPU sat idle for 24.5 ms of a 79 ms TTFT on a 60-token prompt, inside these MoE layers. The page-in copies themselves already ran at the PCIe ceiling (51.8 GB/s); the idle time was host round trips.


## Modifications

**One host sync per host-planned MoE layer** (`residency.py`, `executor.py`, `runners.py`, `store.py`).
- The device LRU state is one packed buffer, `[slot_expert | slot_lastuse | step | counts | expert_slot]`. The step's per-expert routing counts are scattered into it on the GPU, and the whole buffer is read in one copy; all waves are planned from it.
- Every wave's slot map, and each entry's wave, go up in one pinned copy that does not wait for the GPU. A stable sort by wave gives each compacted wave its entries in order, sized from the counts, so the Marlin path needs no `nonzero()`.
- The state goes back in one such copy.
- Page-in skips zero-size tensors (GPTQ's empty `g_idx`).
- The decide kernel of the captured path reads the same state tensors as before, now views into the packed buffer.

**One gather launch per host-planned wave** (`executor.py`, `store.py`, `method.py`).
- Each wave's `(src, dst, count)` goes up in the same copy as the slot maps, and the gather kernel the captured decode step uses pages the wave in with one launch.
- A store the kernel cannot read (unpinned, or without CUDA graphs rows of an odd size or a non-contiguous GPU tensor) keeps the per-expert copies.

## Accuracy Tests

**Unit and kernel tests.**
- Multi-wave paged forward on CPU equals the unpaged reference, for both the masked (triton) and the compacted (Marlin) runner contracts.
- The packed device state round-trips through the host LRU policy.
- A wave paged in through its GPU plan in one gather launch leaves the same slots as one copy per expert and tensor, including an empty `g_idx`; a wave with nothing to page in does not read its plan.

**Paged vs unpaged, 4-layer test models** (E=32, top-4, K=8; prompt and greedy decode logprobs; RTX 5070 Ti; main 2d3de82633 and this PR in one run):

| model | runner | this PR | main |
|---|---|---|---|
| Qwen3-MoE bf16 | triton | identical | identical |
| AWQ int4 | Marlin | decode max 0.014 | decode max 0.014 |
| compressed-tensors NVFP4 | Marlin | median max 0.048, unpaged floor 0.038 | median max 0.059, unpaged floor 0.063 |

Marlin is not run-to-run reproducible, so the Marlin formats are judged against the spread of two unpaged servers (the floor); bf16 on triton is bit-identical. Each check has a negative control that must fail (a perturbed RMSNorm eps on bf16 and AWQ, unnormalized top-k weights on NVFP4), and all three do.

**GSM8K (200 questions), Qwen3-30B-A3B-GPTQ-Int4, K=92:** main 0.950 / 0.935, this PR 0.955.

## Speed Tests and Profiling

Same machine as #42557: RTX 5070 Ti 16 GB (PCIe 5.0 x16, 62 GB RAM), Qwen3-30B-A3B, 10,240 KV tokens and 4 slots, prefix caching off, 16 ShareGPT warm-up requests discarded. Decode tok/s is `1000 / median TPOT` over 8 ShareGPT prompts sent one at a time (256 output tokens each); TTFT and ITL are from the same requests. 4 requests: 16 ShareGPT prompts from 4 clients at once (output tok/s). 2k TTFT: 4 natural ~2,048-token prompts. main (upstream 2d3de82633) is measured first and last in the same run as this PR; both values are shown, and a difference inside their spread is no difference. Prefill is host-planned in every phase; decode with 4 requests stays captured (4 ≤ `K // top_k` = 11, 5 and 10 here).

| config | decode tok/s | TTFT p50 / p99 | ITL p50 / p99 | 4 requests: out tok/s | 2k TTFT p50 / p99 | peak VRAM |
|---|---|---|---|---|---|---|
| int4, K=92: main | 211.8 / 212.8 | 51 / 88, 50 / 82 ms | 4.70 / 5.35, 4.70 / 5.30 ms | 400 / 401 | 247 / 275, 239 / 274 ms | 14.7 GiB |
| int4, K=92: this PR | 212.9 | **39 / 71 ms** | 4.70 / 5.33 ms | 405 | **225 / 261 ms** | 14.6 GiB |
| FP8, K=40: main | 90.3 / 90.3 | 213 / 301, 218 / 301 ms | 10.51 / 20.74, 10.51 / 20.76 ms | 100 / 99 | 427 / 481, 424 / 487 ms | 13.4 GiB |
| FP8, K=40: this PR | 90.3 | **197 / 284 ms** | 10.50 / 20.76 ms | 100 | **411 / 468 ms** | 13.4 GiB |
| NVFP4 (Marlin), K=85: main | 189.8 / 192.9 | 72 / 119, 73 / 116 ms | 5.20 / 6.44, 5.11 / 6.32 ms | 352 / 349 | 248 / 283, 244 / 285 ms | 14.5 GiB |
| NVFP4 (Marlin), K=85: this PR | 189.0 | **59 / 88 ms** | 5.22 / 6.35 ms | 356 | **223 / 261 ms** | 14.5 GiB |

TTFT p50 drops 23% (int4), 9% (FP8) and 19% (NVFP4) for ShareGPT prompts, and 8%, 3.5% and 9% for a natural 2k prompt, against the mean of the two main runs. Decode, ITL and 4-request throughput are unchanged: captured decode does not take this path.
