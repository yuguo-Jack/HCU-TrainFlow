# [Fix] Use a safe stop-string decode window

[Upstream PR](https://github.com/sgl-project/sglang/pull/36728) · state: open · merged: False

## Original PR description

## Motivation

Fixes #36698.

Stop-string matching decodes a bounded tail of generated tokens. The bound was derived only from encoding the stop string in isolation, but generated text can use a longer non-canonical tokenization. For DeepSeek-V4-Flash-0731, `<END>` canonically encodes to 3 tokens but can be generated as 5 tokens, causing the decode window to retain only `END>` and miss the stop.

## Modifications

- Size the stop-string window using the larger of the canonical token count and UTF-8 byte length.
- Consolidate the two existing length tests into one regression test covering both sides of that bound.
- Update the existing serialization assertion for the corrected normalized value.

## Accuracy Tests

This does not change model forward computation or numerical accuracy.

- `pytest test/registered/unit/sampling/test_sampling_params.py -q`: 70 passed, 13 subtests passed.
- `pytest test/registered/unit/managers/test_stop_str_speculative.py -q`: 9 passed.
- DeepSeek-V4-Flash-0731 tokenizer check: canonical `<END>` IDs `[30, 16860, 32]`; non-canonical IDs `[30, 39, 48, 38, 32]`; corrected window decodes `香蕉<END>` and contains the stop string.

## Speed Tests and Profiling

Not run; this is a correctness fix. Normalization adds one UTF-8 encoding per configured stop string, and the existing tail decoder reads up to the corrected bound only when it is larger than the canonical token count.

Real-model A/B validation (single NVIDIA B300, 2026-08-28 UTC)

Tested exact revisions:

- baseline: `ff5578eb4e1d68d842303e3ab9ce4c86038c1c26`
- patch: `18edeb540b436f7a4d2de5fab006f7a314f4895a`
- model: `deepseek-ai/DeepSeek-V4-Flash-0731`, HF snapshot `7872f01b1d1fe23eabc4c98b48bffcef5a386062`
- image: `lmsysorg/sglang:v0.5.18` (`sha256:9e148f5ac788e856a06166bd6347a831831eb9fcfab4d1770874823a7c29a1a1`)
- runtime: Python 3.12.3, PyTorch 2.13.0+cu130, CUDA 13.0.88, driver 580.173.02

Both legs used the same server arguments and imported `sampling_params.py` from their respective exact source checkout. The model was reloaded between legs.

The model tokenizer encodes canonical `<END>` as `[30, 16860, 32]` (3 tokens), but the same text can be emitted as `[30, 39, 48, 38, 32]` (`<`, `E`, `N`, `D`, `>`, 5 tokens). I used SGLang's native `/generate` endpoint with `regex: "<END>"` and negative logit bias for every multi-character token that could encode a substring of the marker. This deterministically made the real model take the 5-token path while leaving stop handling to the server.

<details>
<summary>Identical request used for both legs</summary>

```json
{
  "text": "Output the exact marker <END> and nothing else.",
  "sampling_params": {
    "temperature": 0,
    "max_new_tokens": 8,
    "stop": "<END>",
    "regex": "<END>",
    "logit_bias": {
      "2389": -100.0,
      "4928": -100.0,
      "16860": -100.0,
      "85911": -100.0
    }
  },
  "return_logprob": true,
  "return_text_in_logprobs": true
}
```

</details>

Before (baseline):

```json
{
  "text": "<END>",
  "output_ids": [30, 39, 48, 38, 32, 1],
  "finish_reason": {"type": "stop", "matched": 1}
}
```

The baseline missed the string stop, leaked `<END>`, and continued to EOS (`1`).

After (patch):

```json
{
  "text": "",
  "output_ids": [30, 39, 48, 38, 32],
  "finish_reason": {"type": "stop", "matched": "<END>"}
}
```

The patch saw the same five generated marker tokens, matched the string stop, and trimmed it. A strict offline judge confirmed: identical requests, identical five-token marker path, baseline leak, patched trim, and patched string-stop match all passed.

Limitation: I also replayed the issue's exact English and Chinese chat prompts on both revisions. In this single-replica B300 setup, both revisions naturally used a canonical stop-token path (`banana` / `香蕉`, `matched_stop: "<END>"`), so that request did not reproduce the reported H20 PD-disaggregated symptom. The controlled A/B above validates the decode-window invariant with the actual model and exact source revisions, but is not a reproduction of the original PD topology.

Adding independent confirmation of the same decode-window bug. I opened #47059 before finding this earlier work; that duplicate is now closed in favor of this PR.

- With the public Qwen3-4B tokenizer, `encode("AAA", add_special_tokens=False)` returns `[50107]`, while `[32, 32, 32]` also decodes to `AAA`.
- In our native `/generate` validation, repeated token `32` output stopped for `AA`, but `AAA` was missed and the request reached its output-length limit. The affected integration source files matched public commit `5cbf949839b1fc73802d20670943ccbeb805d3f2`. This is not a claim of GPU testing on current main.
- Separately, normal-import CPU regressions against public main `b85d6a8893d7b81f25ad69eb1c50eee068946d90` reproduced the missing-stop behavior for sequential acceptance, a match spanning acceptance groups, and UTF-8 byte fallback. With the same byte-length-floor rule, the five affected Python test modules passed all 117 tests. These are CPU request-component tests, not full-service GPU acceptance tests.

The closed duplicate retains those request-level regressions, an equivalent Rust tokenizer-worker correction, and four passing Rust tests for reference. The Python fix direction should be credited to this earlier PR. Our source-only recheck of main `73fbf5ccd3be7c04cedccfac9bec5c2e7ae12df4` still found canonical-token-count-only normalization, so this remains relevant to main.
