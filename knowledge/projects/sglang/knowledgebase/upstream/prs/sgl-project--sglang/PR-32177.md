# feat(disaggregation): prototype live P-to-D token handoff

[Upstream PR](https://github.com/sgl-project/sglang/pull/32177) · state: closed · merged: False

## Original PR description

## Motivation

Mooncake overlaps most prompt-KV transfer with prefill, but the remaining P-to-D
commit tail is still visible in streaming TTFT for long prompts. This PR adds an
opt-in token-log handoff: Prefill keeps decoding while prompt KV is in flight,
publishes a sealed token log, and Decode verifies/replays it before taking sole
output ownership.

Related RFC: #32143

## What this changes

- adds `--enable-disaggregation-token-handoff` for the Mooncake path;
- lets P bridge-decode without monopolizing the prefill scheduler;
- publishes the sealed log length and the prefix already emitted by P separately,
  preventing duplicate or missing text at the stream boundary;
- supports exact native-Decode replay by default and an explicit experimental
  batched-EXTEND replay mode;
- sizes wire metadata from the configured bridge limit instead of a fixed
  15-token payload;
- propagates one request ID across P/D and aborts both peers on client disconnect,
  early terminal completion, or downstream failure;
- hides P's internal ownership boundary from client-visible finish events;
- adds an opt-in PD Router streaming branch behind `SGLANG_PD_TOKEN_HANDOFF`.

The guarded path currently targets page size 1, 1P1D, greedy scalar streaming,
PP=1, and matching P/D model and TP configurations. TP=1 and TP=2 have been
validated. Batch requests, returned logprobs, grammar, multimodal, and speculative
decoding fall back to ordinary P/D. The bridge limit defaults to 15 and is
configurable up to 256.

## Correctness and failure validation

Two-node H20, Qwen3-8B, Mooncake/RDMA:

- Python token-handoff and wire tests: 31 passed, plus 2 subtests;
- Rust Router token-handoff tests: 4 passed; full Router binary built from the
  current PR head on H20;
- TP=1 and TP=2 outputs matched standalone byte-for-byte;
- 8 concurrent requests all matched standalone and emitted exactly one `[DONE]`;
- a 32-token bridge log passed with the metadata limit raised to 64;
- stop/EOS on P, client cancellation, and D failure were exercised; resources
  remained healthy, cancellation reached both peers, and D failure produced one
  structured error plus one `[DONE]` without hanging;
- normal 32-token streaming emits 32 data events, only the final one carries
  `finish_reason=length`, and merged P/D text matches standalone byte-for-byte.

The batched EXTEND replay path reaches and verifies the handoff boundary, but
H20 testing found that EXTEND and sequential Decode can differ in floating-point
reduction order, allowing later greedy tokens to diverge. Native Decode replay is
therefore the correctness default; EXTEND remains an explicit experimental mode.

## H20 performance

Same two H20 nodes, Qwen3-8B, Mooncake/RDMA, 4K prompt, 32 output tokens:

| Concurrency | Mode | TTFT P50 / P95 / P99 | E2E P50 / P95 / P99 | Throughput |
|---:|---|---|---|---:|
| 1 | ordinary PD | 253.06 / 254.89 / 254.98 ms | 672.30 / 679.87 / 681.18 ms | 1.483 req/s |
| 1 | handoff | 237.53 / 240.15 / 240.45 ms | 697.31 / 751.88 / 755.70 ms | 1.404 req/s |
| 8 | ordinary PD | 1789.45 / 2034.61 / 2040.86 ms | 1801.49 / 2354.50 / 2465.33 ms | 3.887 req/s |
| 8 | handoff | 1012.12 / 1842.42 / 1976.26 ms | 1802.07 / 2495.00 / 2504.48 ms | 3.706 req/s |
| 32 | ordinary PD | 4903.89 / 7155.91 / 7161.90 ms | 5126.69 / 7605.42 / 7610.51 ms | 4.188 req/s |
| 32 | handoff | 4412.37 / 7044.36 / 7058.59 ms | 5323.93 / 7550.46 / 7556.98 ms | 4.209 req/s |

All 64 requests succeeded. TTFT P50 improved by about 6.1%, 43.4%, and 10.0% at
concurrency 1/8/32. Throughput was essentially flat at concurrency 32 and slightly
lower at 1/8, so this is presented as a streaming TTFT optimization, not an
unconditional throughput improvement.

Earlier long-prompt A/B also showed TTFT median reductions of 12.43 ms at 1K,
38.48 ms at 16K, and 33.61 ms at 32K, with end-to-end median approximately flat.
