## Motivation

`flashinfer_gdn_prefill_default` declined whenever `enable_page_major_kv_layout` was set. `--enable-unified-memory` runs page-major, so Qwen3.5 GDN prefill stayed on the Triton chunk kernels there while the default pool on the same GPU auto-selected FlashInfer. On SM90 (Qwen3.5-9B, page size 256, no speculative decoding) unified prefill cycles ran +1.24..+1.41% longer than the default pool's at matched batch size, all of it GPU time: the Triton chunk kernels cost +17.8 ms per cycle where the FlashInfer GDN kernels cost 10.7 ms. End to end that was -1.1..-1.5% throughput on every attention backend.

## Modifications

Explicit `--linear-attn-prefill-backend flashinfer` is accepted by the page-major gate, matching automatic GDN selection. The test covers this explicit configuration.

`layers/attention/linear/gdn_backend.py`: page-major no longer disqualifies the FlashInfer prefill. For prefill the layout does not matter: `forward_extend` gathers a non-contiguous pool's conv and SSM state into contiguous per-sequence copies before any prefill kernel runs and scatters them back after (`needs_state_gather`), so FlashInfer's extend sees the same contiguous, identity-indexed state as on the default pool. Decode and verify are unaffected; their backends resolve separately (verify follows decode, Triton by default).

Test (`test_gdn_prefill_backend_policy.py`): `test_selects_flashinfer_for_a_page_major_pool` (SM100 with a bf16 state, SM90 with an fp32 state) fails before (the policy returns None) and passes after; page-major leaves `test_rejects_unvalidated_runtime_modes`.
