# [HiCache] Keep protected cgroup page cache charged in host budgets

[Upstream PR](https://github.com/sgl-project/sglang/pull/42788) · state: closed · merged: True

## Original PR description

## Motivation

HiCache's cgroup headroom estimate can count file cache protected by another subtree's `memory.min` as allocatable memory. When reclaim targets a shared ancestor, its descendants' hard protection still applies, so a host pool can pass the budget check and subsequently fail allocation or trigger a cgroup OOM.

For example, a parent limited to 900 GiB contains 250 GiB of non-reclaimable engine memory and 600 GiB of clean file cache in a live sibling protected by `memory.min=600 GiB`. The current estimate reports 650 GiB of headroom, although only 50 GiB remains without reclaiming protected memory.

This follows up on #42420 and the accounting discussion in #41181. Linux calculates protection relative to the reclaim target: [page_counter_calculate_protection](https://github.com/torvalds/linux/blob/v6.12/mm/page_counter.c#L396-L419) preserves a direct child's `memory.min` even when the target's own minimum is zero.

## Modifications

- Before crediting file cache at a constrained cgroup v2 level, inspect its visible descendants for nonzero `memory.min` values. If any are configured, keep the full usage charged at that level.
- Treat unreadable descendant directories, metadata, or protection counters, and malformed protection values, conservatively. They disable cache credit while preserving the known cgroup limit, including for explicitly sized pools; they do not trigger the host-RAM fallback.
- Ignore the reclaim target's own minimum and leave v1 accounting unchanged. Unprotected subtrees retain the existing page-cache credit. `memory.low` is not treated as hard protection.
- Reuse one adjusted usage reading for both `memory.max` and `memory.high` at each level, avoiding duplicate subtree scans.
- Add one CPU regression test that checks the same sibling cache without protection (650 headroom) and with memory.min protection (50 headroom). Capture the expected warning in the existing explicit-fallback tests.

The policy is deliberately conservative: any configured descendant minimum disables all file-cache credit at that level, even if the minimum is not effectively protecting pages. It does not attempt to reconstruct the kernel's effective-protection allocation. The scan runs only during host-pool budgeting, and only for v2 levels with file cache to credit. Like the existing usage/stat reads, this is a snapshot, not an atomic reservation against concurrent allocations or protection changes.
