# [DeepSeek-V4.1] Sparse prefill group sharing

[Upstream PR](https://github.com/sgl-project/sglang/pull/42929) · state: open · merged: False

## Original PR description

## Motivation

Profiling a 1 M-token prefill of DeepSeek-V4.1-Flash on 4× B200 (TP4 + EP4, DSPARK, the cookbook low-latency recipe) shows two kinds of work that a *group* of layers shares but that the code redoes *per layer*, and both are O(context²) over a chunked prefill.

**1. Every ratio-2 index-source layer scans the whole context.** `candidate_source_layer_id` is a single layer id in the checkpoint, and `uses_candidates` is one global `layer_id` comparison, so only the ratio-1 index group gets the publish/consume treatment. On DSv4.1-Flash — `index_source_layer_ids = [2, 8, 14, 20, 24, 28, 32, 36]`, `candidate_source_layer_id = 20`, `compress_ratios = [0,0] + [2]*18 + [1]*20 + [0,0,0]` — that leaves layers 2, 8 and 14 each running a full dense `sm100_mqa_logits` scan over the entire compressed context, every prefill chunk. In the 1 M trace the dense indexer family is **7.19 s of a 26 s prefill (27.7 %)** and grows **+3.0 ms per 16 K of context per chunk**, which is exactly `Σ 1/ratio = 3×½ + 1×1 = 2.5` context-widths per chunk.

**2. The compressed-cache dequant runs once per consumer layer, not once per kv_source group.** Compressed KV for ratios 1/2 is owned by a kv_source layer (`kv_source_layer_ids = [2, 8, 14, 20]`) and read by every later layer of that ratio, but `_forward_prefill_sparse` dequantizes the whole group cache into the bf16 workspace on each of them. At 256 K that is **124.6 ms per prefill** growing **+0.77 ms per 16 K**. The HIP backend already memoizes exactly this (`_OpusPrefillState.compressed_kv`); the CUDA path did not. The dequant kernel itself was also shaped one token per program, issuing 64-element loads at ~1.1 TB/s effective.

Related issue: https://github.com/sgl-project/sglang/issues/42170

## Modifications

**1. Per-ratio candidate publishing** (`SGLANG_OPT_DSV4_PER_RATIO_CANDIDATES`, default **off**). The first index-source layer of each compress-ratio group publishes candidate blocks and the later index sources of that group consume them, exactly like the shipped ratio-1 publish/consume path; `candidate_metadata` becomes a per-ratio dict (one publisher today, two with the flag). Within a ratio group the index pools share one slot space and `consume_prefill` already scores the *consumer layer's own* keys through `get_index_k_cache(layer_id=...)`, so the published block schedule carries over unchanged — only which columns get scored changes.

<img width="2444" height="1048" alt="shot-muxtd2xa" src="https://github.com/user-attachments/assets/118bd662-de26-4672-8f14-7ef031d8478a" />

**2. Dequant dedup across a kv_source group** (`SGLANG_OPT_DSV4_SPARSE_PREFILL_DEQUANT_DEDUP`, default **on**). One dequant per `(workspace buffer, source cache, gather, rows, layout)` memoized on the per-chunk `SparsePrefillChunkCache`. Any key change — a different source group, a workspace reallocation, a different gather — falls back to a fresh dequant, and the c0 path invalidates the memo because its SWA gather starts at workspace offset 0 and overwrites the compressed region. This is invariant-preserving: it skips a byte-identical recomputation.

<img width="2368" height="1050" alt="shot-muxtdmy5" src="https://github.com/user-attachments/assets/cd4855b6-0a92-4649-a5f2-9de96ed41e91" />

**3. Vectorize the V4 paged dequant kernel** to 4 tokens per program: one `[4, 8, 64]` fp8 load (the 8-padded scale row with the pad tile masked), one `[4, 8]` scale load and one `[4, 64]` bf16 rope load per program. The dequant is elementwise, so the grid shape changes no output bit.

## Accuracy

GSM8K, 200 examples, `--temperature 0`, run against both servers in the same session:

| | score | score:std |
|---|---|---|
| baseline | 0.995 | 0.0705 |
| this PR (both flags on) | 0.995 | 0.0705 |

Changes 2 and 3 are bitwise-neutral by construction, and change 3 is covered by the shipped zero-tolerance self-test (`test/manual/kernels/attention/check_dsv4_dequant_k_cache.py`, `assert_close(atol=0, rtol=0)` against the torch reference), which passes on B200.

## Benchmarks

Warm TTFT, DeepSeek-V4.1-Flash on 4× B200, TP4 + EP4, `--speculative-algorithm DSPARK --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64`, bs = 1, random-token prompts, 3–4 seeds per cell:

| context | baseline | + changes 2&3 | + change 1 (all) |
|---|---|---|---|
| 1 M (in-len 1 048 000) | 27.58 – 27.73 s | 26.52 – 26.54 s | **23.72 – 23.79 s (−14 %)** |
| 256 K | 4.87 – 4.92 s | 4.82 – 4.90 s | — |

Per-family kernel time from the TP-0 torch traces of the same 1 M request (64 chunks of 16 K):

| family | baseline | this PR |
|---|---|---|
| indexer dense logits | 7 192 ms (27.7 %) | **4 883 ms (20.9 %)** |
| …its growth per 16 K of context | +3.0 ms | **+1.9 ms** (`Σ 1/ratio` 2.5 → 1.5) |
| …dense launches / time in the last chunk | 79 launches, 187.3 ms | **47 launches, 113.7 ms** |
| …paged-sparse launches / time in the last chunk | 4 launches, 5.5 ms | 6 launches, 8.4 ms |
| top-k kernels | 2 007 ms | **1 415 ms** |
| GPU busy, whole prefill | 25.93 s | **23.36 s** |

The two extra paged-sparse launches are layers 8 and 14 moving onto the published candidates; they cost 2.9 ms and remove 73.6 ms of dense scanning in that chunk.

Dequant, 256 K prefill (TP-0 trace) and the kernel alone (idle B200, page size 256, V4 layout):

| | baseline | this PR |
|---|---|---|
| `_dequantize_k_cache_paged` per prefill | 124.6 ms | **26.6 ms** |
| …in the last chunk | 13.58 ms | **2.15 ms** |
| …growth per 16 K of context | +0.77 ms | **+0.07 ms** |
| kernel, 262 K rows | 0.381 ms (1.1 TB/s) | **0.089 ms (4.8 TB/s)** |
| kernel, 524 K rows | 0.754 ms | **0.171 ms** |
| kernel, 16 K rows | 0.019 ms | 0.020 ms (launch-bound) |

A short-context side effect worth noting: the GSM8K run itself went from 34.3 s to 28.8 s (871 → 1017 output tok/s), because the ratio-2 layers also take the consume path at decode.

## Reproduction

```bash
# server (add SGLANG_OPT_DSV4_PER_RATIO_CANDIDATES=1 for change 1)
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code \
  --tp 4 --ep-size 4 --mem-fraction-static 0.8 --speculative-algorithm DSPARK \
  --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64 --port 31000

# kernel self-test (zero tolerance vs the torch reference)
python3 test/manual/kernels/attention/check_dsv4_dequant_k_cache.py

# accuracy
python3 -m sglang.test.run_eval --eval-name gsm8k --num-examples 200 --num-threads 32 --temperature 0 --port 31000
```

## Limitations and risks

- Change 1 is **off by default**. It changes what the ratio-2 index sources score: 2048 candidate blocks × 8 = 16 384 positions, i.e. 12.5 % of the ratio-2 window at 256 K and 3.1 % at 1 M. The ratio-1 group already ships with the same absolute budget (1.6 % of the window at 1 M), and GSM8K is unchanged, but a longer-horizon eval on a retrieval-heavy workload would strengthen the case before flipping the default.
- Change 1 is not validated under prefill context parallelism: the CP path forces `DenseBlocksBackend` for publishes, so the flag should stay off there until that fallback is lifted.
- The dequant memo assumes the group's compressed cache is not rewritten between the first consumer's read and the last one's within a forward. That holds today because only the kv_source layer writes it and it does so before its own attention; the memo key still re-validates the cache pointer, the gather and the layout on every call.
- All numbers are from one model and one shape family (DSv4.1-Flash, bs = 1, random-token prompts, 16 K chunks). The high-throughput cell (`--max-running-requests 256`, no spec decoding) was not measured in this round.
