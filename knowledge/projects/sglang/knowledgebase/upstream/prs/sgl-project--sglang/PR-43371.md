# [Fix] Configure logging in tokenizer worker processes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43371) · state: open · merged: False

## Original PR description

## Motivation

With `--tokenizer-worker-num` > 1, a tokenizer worker drops every INFO line except those from `sglang.srt.entrypoints.http_server`. Only warnings get through, so anything the tokenizer manager, a multimodal processor or an external plugin logs at INFO from a worker is lost.

Root cause:
- The workers are ASGI worker processes: uvicorn's, started by `uvicorn.run(..., workers=N)`, or Granian's with `--enable-http2`.
- They keep the server's logging config. For uvicorn that is `LOGGING_CONFIG`, to which `launch_server` adds only `sglang.srt.entrypoints.http_server` at INFO. That is why a worker still prints `Start multi-tokenizer worker process`.
- `init_multi_tokenizer` never calls `configure_logger`; the scheduler, detokenizer and DP controller each do.
- So the worker's root logger stays at Python's default WARNING.

## Modifications

- `init_multi_tokenizer` calls `configure_logger(server_args, prefix=" TokenizerWorker-<pid>")` right after it reads the server args, before it builds the tokenizer manager.
  - The prefix tells the N workers' lines apart.
  - `basicConfig(force=True)` replaces only the root logger's handlers. uvicorn's own loggers (own handlers, `propagate: False`) and the `http_server` logger keep theirs, so nothing is logged twice.
- `test/registered/tokenizer/test_multi_tokenizer.py`:
  - `TestMultiTokenizer` now captures the server's output. It is still echoed to stdout.
  - It gains `test_every_tokenizer_worker_logs_at_info`, which asserts that INFO lines arrive under 8 distinct `TokenizerWorker-<pid>` prefixes. It polls for up to 30 s, since the server answers as soon as one worker is up.
