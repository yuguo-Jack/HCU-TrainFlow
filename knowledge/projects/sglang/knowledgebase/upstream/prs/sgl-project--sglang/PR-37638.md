## Draft for maintainer review; correctness claim remains withdrawn

A maintainer reopened this PR on 2026-09-15. The current head includes a merge of `qwen4-main-squashed`; its kernel predicates and tests still do not demonstrate an observable correctness or performance benefit.

Rechecking the indexing and public consumer invalidated both the original illegal-memory-access explanation and the later cross-row-contamination explanation. Extra stores remain within their own query row, and the public wrapper masks out-of-window values before returning. The end-to-end tests also passed before this patch; raw pre-mask tests distinguish internal stores, not a public-output defect.

No fix for #37633 is claimed. Separately, merged #38346 bounds the compression gather for forwards with only 1–3 source rows; it is a different code path. Historical verification on the original H20 deployment was later reported in [the September 16 update](https://github.com/sgl-project/sglang/pull/37638#issuecomment-5695024174), but that evidence supports the independent gather fix, not the predicates proposed here. Serialization or disabling overlap suppressing a short reproduction did not establish a race as root cause.

The branch is retained as a draft for maintainer review and provenance. It is not ready to merge without an independently established correctness or performance motivation. GPU validation and any motivation for retaining these predicates need to be established independently. Previous required-base CI failures occurred before GPU testing and must not be interpreted as GPU regressions.

## Correction: this PR's root-cause analysis is wrong. The kernel fix is still valid; the crash it claimed to fix is a different bug.

Posting this proactively before review. Further debugging on our 8×H20
Qwen3.8-Flash-Next-FP8 deployment has invalidated the "Root cause"
section above. I'd rather retract it myself than have a reviewer merge
it on a false premise.

**Summary of what changed:**

| Claim in the PR body | Status |
|---|---|
| The predicated K load + predicated `Logits` store are correctness fixes | **Still true.** 9 direct pre-mask inspection tests still demonstrate thousands of stray in-bounds writes before the fix, 0 after. |
| Those stray accesses went *out of bounds* and caused the Xid 31 / illegal memory access | **False.** See below. |
| This PR "fixes a CUDA illegal-memory-access crash" / "Closes #37633" | **False.** The crash still reproduces with this patch applied. |
| Production validation: 22-concurrency clean after the fix | **Superseded.** It reproduces at only 8 concurrent requests. |

### Why the OOB story cannot be right

TileLang automatically inserts bounds predicates around accesses to
dynamically-shaped buffers. Reading the generated CUDA for the
*unfixed* kernel out of the JIT cache
(`~/.tilelang/cache/0.1.12/.../device_kernel.cu`) shows the store is
already wrapped:

```c
if (0 <= col) { if (col < keys) { if (row < rows) { Logits[...] = ...; } } }
```

So the pre-fix kernel could not write past the `Logits` allocation, and
the same auto-guarding applies to the `K` access. I also wrote a direct
canary probe for the follow-up mask kernel — allocating a padded flat
buffer, viewing the `[:rows]` slice the wrapper hands over, and counting
clobbered canary elements past the logical end. **7/7 cases clean**,
including the `rows % block_q == 0` shapes with no padding rows to absorb
an overshoot.

What the pre-fix kernel *did* do wrong is write scores into **other
packed rows' valid windows** — in-bounds, but wrong. That is a genuine
correctness bug worth fixing (a row's top-k can be computed from another
row's scores in the window between the prefill kernel and the mask
kernel, and the mask kernel cannot undo it). It is not a memory-safety
bug, so it cannot produce `cudaErrorIllegalAddress`.

### What the crash actually is

With this patch applied, `metadata.py get_prefill_mqa_inputs` →
`sequence_lengths.tolist()` still dies with `CUDA error: an illegal
memory access was encountered`, now at **8 concurrent requests** instead
of 22, reproducibly, under `sglang.bench_serving` (sharegpt, 200
prompts). Two observations localize it:

1. **`CUDA_LAUNCH_BLOCKING=1` makes it disappear entirely.** c=4 and c=8,
   200 requests each, both complete. An invalid *address* would still be
   invalid when launches are serialized, so this is a race, not an OOB.
2. **`--disable-overlap-schedule` makes it disappear.** Same workload,
   c=4/8/16 all complete (270 / 412 / 578 tok/s output throughput).

Additionally, **all 8 TP ranks fault at the same layer's `.tolist()` in
the same second.** `sequence_lengths` / `token_slot_table` /
`row_starts` / `row_ends` are replicated scheduler state, identical on
every rank, so whatever address is bad is derived from replicated
metadata rather than rank-local tensors.

The traceback runs through `scheduler.event_loop_overlap`. The overlap
scheduler runs the model forward on `forward_stream` while scheduler
bookkeeping runs on `schedule_stream`, so the working hypothesis is a
cross-stream race on state the QSA prefill indexer reads twice — note
that `get_prefill_mqa_inputs` derives the packed `compressed_keys`
layout from a **host** snapshot (`sequence_lengths.tolist()`) but
re-derives the cumulative row offsets **on device** from the live tensor
in `build_qsa_row_ranges`. If those two disagree, `row_ends` can exceed
the packed buffer and the top-k reads past the end of `logits`.

**I have not confirmed that mechanism.** Freezing the snapshot
(`self.sequence_lengths.to(torch.int32).clone()`) does empirically stop
the crash with overlap enabled — c=4/8/16/32/64 all clean, 303 / 455 /
625 / 819 / 954 tok/s — but an instrumented probe that re-reads the live
tensor and compares it against the snapshot **never once fired**. So the
clone may simply be perturbing timing enough to hide the race. I am not
proposing it as a fix on that evidence.

### What I suggest for this PR

Keep the kernel change, restate it honestly:

- Retitle to describe it as what it is — predicated K load and
  predicated `Logits` store so the QSA prefill scorer stops writing into
  other packed rows' windows.
- Drop the "Root cause", "Xid 31", and "Production validation" framing,
  and drop `Closes #37633`.
- Keep the 270-case test file and the 9 direct pre-mask inspection tests
  unchanged; they are what actually justify the change.

I'll open a separate issue for the overlap-scheduler race with the
reproducer and the two suppressing flags, and update #37633 to point at
it. Happy to split this PR or reduce its scope if maintainers prefer.

Apologies for the noise in the original write-up.

- LeslieWylie · comment · 2026-09-14T10:52:43Z · [source](https://github.com/sgl-project/sglang/pull/37638#issuecomment-5662823412)

Withdrawing this PR after rechecking the actual index and consumer path. My earlier correction still overstated the evidence for a correctness bug.

The store is `Logits[row_base + qi, col] = reduced[n, qi]`: the row index remains the query row. Computing/storing across the CTA union of K windows writes extra columns within that same row, not another query row's scores into its valid window. The public prefill wrapper masks columns outside each row's `[Starts, Ends)` before returning logits. This ordering is present in both the target branch and current main.

The retained end-to-end reference tests passed before the patch as well. The additional raw-kernel tests establish only that previously written pre-mask positions remain untouched after the patch; that is not evidence of an observable output error in the public path. An index-level CPU check confirms this distinction, but is not a new GPU validation.

The earlier out-of-bounds/crash claim was already retracted. I also retract the subsequent cross-row contamination/top-k correctness claim. No demonstrated numerical or performance benefit remains to justify the additional predicates and disabled TileLang race check.

The latest CI failure is a separate base-revision gate (`3700c4ee26a1` required while this PR targets `qwen4-main-squashed`), not a failing GPU regression. I am closing rather than retargeting/rebasing an unsubstantiated fix merely to satisfy that gate. The separately reported concurrent illegal-memory failure is not resolved by this PR.


- LeslieWylie · comment · 2026-09-16T09:13:16Z · [source](https://github.com/sgl-project/sglang/pull/37638#issuecomment-5695024174)

**Update: #38346 is now validated on the original 8×H20 workload.**

The PR description notes that the merged #38346 "has not yet been validated on our original H20 workload." It now has been, on the same Qwen3.8-Flash-Next-FP8 / 8×H20 (TP8/EP8) deployment behind the original #37633 reports.

With #38346's clamp applied (`group_locs = group_locs.clamp_max(source_keys.shape[0] - 1)` in `qsa/qsa_indexer.py`) and the overlap scheduler **re-enabled**, the exact case that used to crash — **c=16 × 1000 concurrent requests** — now completes clean. Across runs totaling **1528 requests** (c=8×240, c=16×1000, plus varied-length prompts that defeat the radix cache and force the ragged final-chunk prefill path): **0 illegal-memory-access / Xid / scheduler exceptions**, and the service never restarted. Overlap is our production default again.

This lines up with #38346's stated mechanism: a chunked-prefill chunk ending a request can carry fewer than `compress_ratio` (4) source rows, so the compress gather indexes past `token_k` and faults only when it crosses an unmapped page — matching the probabilistic, overlap-only, `CUDA_LAUNCH_BLOCKING=1`-suppressed signature described earlier in #37633.

Caveat, in the spirit of the earlier corrections in this thread: it is a probabilistic race, so 1528 clean requests is strong evidence rather than proof, and we're continuing to watch it in production. But on our workload #38346 is the change that let us turn overlap back on, and it does appear to address the #37633 root cause.

This PR's own scope (the predicated K load / `Logits` store) remains a separate matter; I'm not reasserting a correctness claim for it here.
