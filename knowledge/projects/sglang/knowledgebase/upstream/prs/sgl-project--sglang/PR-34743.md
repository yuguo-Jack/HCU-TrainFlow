# [Benchmark] Fix per-run speculative accept length for DP serving benchmarks

[Upstream PR](https://github.com/sgl-project/sglang/pull/34743) · state: closed · merged: False

## Original PR description

## Motivation

`bench_serving` historically reads speculative acceptance length from:

```python
server_info["internal_states"][0]["avg_spec_accept_length"]
```

With decode DP, `internal_states[0]` represents only one scheduler. Requests from the current benchmark may be handled by other DP ranks, and the selected scheduler may contain no speculative statistics or statistics accumulated by earlier workloads. The reported value is therefore not reliably scoped to the current benchmark run.

For example, a DP deployment can report values on only a subset of scheduler states:

```text
[null, null, 2.90, 3.67, null, 4.64, ...]
```

Reading element zero incorrectly reports no acceptance length.

## Modifications

- Request the existing `return_spec_tokens_details` extension for SGLang OpenAI backends.
- Extract each successful request's existing:
  - `sglext.spec_tokens_details.spec_accept_length`
  - `sglext.spec_tokens_details.spec_verify_ct`
- For decode `dp_size > 1`, compute a verification-count-weighted value from requests completed by the current benchmark:

```text
accept_length =
    sum(request_accept_length * request_verify_ct)
    / sum(request_verify_ct)
```

- Preserve the historical `/server_info` behavior for DP=1 and deployments without a reported DP size.
- Read the decode DP size from the PD-wrapped `server_info["decode"]` response when applicable.
- Report `accept_length_source` as either `per_request`, `server_info`, or `unavailable`.
- Include per-request acceptance lengths and verification counts with `--output-details`.
- Handle extension-only streaming Completion chunks whose `choices` list is empty.
- Add registered CPU unit tests for direct serving, PD serving, weighted aggregation, missing/failed metrics, streaming extension parsing, and multiple-choice details.

This revision uses the speculative-details protocol already present on current `main`; it does not add duplicate OpenAI response fields or modify server-side response construction.

## Accuracy Tests

Not applicable to model accuracy: this change does not alter sampling, model execution, or generated tokens.

The registered CPU tests verify the reported metric numerically. In particular:

```text
request 1: accept_length=4.0, verify_ct=100
request 2: accept_length=2.0, verify_ct=10
expected aggregate: (4.0 * 100 + 2.0 * 10) / 110 = 3.81818...
```

They also verify that DP=1 continues to use the server-reported value.

## Speed Tests and Profiling

No model or scheduler hot path is changed. Aggregation is performed once after the benchmark over the completed request outputs, with `O(num_requests)` CPU work.

For SGLang OpenAI backends, the benchmark requests the existing speculative-details extension, which is emitted in the final response metadata. No additional model forward or token-generation work is introduced.
