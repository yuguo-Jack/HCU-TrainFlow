## Motivation

Closes #37838. A startup assert in `deepseek_v4_hook.py` blocks prefill/decode disaggregation with `--dsv4-attn-backend trtllm`. The assert guarded against pairing a trtllm prefill with a FlashMLA decode. The trtllm pool stores uniform-FP8 KV rows (512 B) and FlashMLA stores packed pages (584 B), so such a decode would read garbage.

#45075 has since added that guard to the PD handshake: `DeepSeekV4TokenToKVPool.pd_kv_layout()` reports `uniform_fp8` for trtllm pools, and the decode rejects a prefill whose layout differs. With the guard in place, this PR removes the assert so a matched trtllm prefill + trtllm decode pair can run, and adds a CI test for it.

## Modifications

1. **`[DSv4] trtllm: Allow PD disaggregation`** (44fc071): removes the `--dsv4-attn-backend trtllm` + `--disaggregation-mode` assert. The transfer path needs no changes, because every transferred buffer is already described from the real pool geometry.
2. **`[DSv4] test: Run the DSv4 PD e2e test with the trtllm attention backend`** (4048518):
   - `test_disaggregation_dsv4_trtllm.py` subclasses the existing DSv4 PD e2e test, adds `--dsv4-attn-backend trtllm`, and registers it on `8-gpu-b300` (5d73f9e; PR CI's base-c stage has no `8-gpu-b200` runner).
   - The base test gains `model_repo`, `server_env`, and `extra_server_args` class attributes for this.

An earlier version of this PR also carried its own KV transfer layout id in the bootstrap handshake. That commit was dropped when #45075 landed the equivalent check on main.

## Repro

CI-equivalent run on one 8-GPU Blackwell node (CI uses B300), with prefill on GPUs 0-3 and decode on GPUs 4-7:
```bash
python -m pytest -v -s test/registered/disaggregation/test_disaggregation_dsv4_trtllm.py
```

The GB300 numbers above come from a 2-node srt-slurm (NVIDIA/srt-slurm) run, because no single 8-GPU Blackwell node was available to us at the time. Key server flags on both roles:
```bash
python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V4-Flash --trust-remote-code \
  --disaggregation-mode {prefill|decode} --disaggregation-transfer-backend mooncake \
  --dsv4-attn-backend trtllm --tp 4 --attn-dp-size 4 \
  --moe-a2a-backend deepep --deepep-config '{"normal_dispatch":{"num_sms":96},"normal_combine":{"num_sms":96}}' \
  --speculative-algorithm EAGLE --speculative-num-steps 1 --speculative-eagle-topk 1 --speculative-num-draft-tokens 2 \
  --cuda-graph-max-bs-decode 128 --max-running-requests 128 --chunked-prefill-size 4096
```
Two environment settings are specific to these GB300 nodes and are not needed in CI:
- `NVSHMEM_REMOTE_TRANSPORT=none`: otherwise DeepEP's low-latency NVSHMEM init segfaults on these nodes.
- `MOONCAKE_PROTOCOL=tcp MC_FORCE_TCP=1`: Mooncake RDMA memory registration fails on the GB300 RoCE VFs.

## Known limitations / not covered

- **Forced retraction across nodes:** with `SGLANG_TEST_RETRACT=1`, which the CI test sets, about 10% of gsm8k requests failed on the 2-node GB300 layout.
  - The failures were `KVTransferError` timeouts in `KVPoll.WaitingForInput`, and "Duplicate request ID" errors on retract-rebootstrap.
  - They happened **equally on trtllm and FlashMLA**, so this is a cross-node PD retraction issue and not specific to this PR.
  - The registered CI test runs on a single node and passed with forced retraction on (CI result above). The GB300 numbers above were taken with forced retraction off.

@YAMY1234 could you review? One open question on scope: the first commit (3ed8eee, +181/−11, a KV transfer layout id in the bootstrap handshake) is optional, and I lean toward dropping it.

**What it protects against:** prefill and decode launched with different `--dsv4-attn-backend` (trtllm writes 512 B uniform-FP8 rows, FlashMLA reads 584 B packed pages). The rest of the PR doesn't depend on it; dropping it leaves just the assert removal plus the e2e test (about +35/−15).

**Evidence (GB300, trtllm prefill + FlashMLA decode):**

| | With the layout id (job 1109512) | Without it (job 1121268) |
|---|---|---|
| Fails at | bootstrap | first KV transfer of each request |
| Error | `KV transfer layout mismatch`, naming both layouts | Mooncake's existing check: `StateType.SWA item length mismatch ... prefill=131072 decode=149760` |
| Wrong output? | no | no; client gets HTTP 500, then the router marks prefill unhealthy |

So Mooncake's existing per-request state-layout check already stops the mismatched pair before any garbage is produced. The layout id only adds an earlier error with a clearer message. That costs 52 lines of Rust bootstrap plumbing and a 71-line unit test, so I'd remove it and add a note that both roles must use the same `--dsv4-attn-backend`. If you'd rather keep the earlier error, I'll leave it in.
