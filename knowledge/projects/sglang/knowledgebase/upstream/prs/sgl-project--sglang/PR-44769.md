## Original PR description

# [Feat] [Intel] lora: Add intel_xpu LoRA backend

## Motivation

On Intel XPU, multi-LoRA serving currently has to use the generic `triton`, `csgmv`, or `torch_native` backends. This PR adds an `intel_xpu` LoRA backend that runs the native Intel XPU LoRA kernels from [sgl-kernel-xpu](https://github.com/sgl-project/sgl-kernel-xpu) on both the prefill and decode paths.

Usage:

```bash
python -m sglang.launch_server \
    --model-path <base-model> \
    --device xpu \
    --enable-lora \
    --lora-paths <name>=<adapter-path> \
    --lora-backend intel_xpu
```

## Modifications

**New backend**: `python/sglang/srt/lora/backend/intel_xpu_backend.py` (`IntelXpuLoRABackend`)
- Prefill (contiguous batch metadata, `permutation is None`): per-shape XPU kernels (`sgemm_lora_a_fwd`, `sgemm_lora_b_fwd`, `qkv_lora_b_fwd`, `gate_up_lora_b_fwd`).
- Decode: tokens are sorted by adapter (`compute_sgemm_routing`), and the chunked-SGMV shrink/expand pair are gather fused DPAS kernels. The shrink output layout `(num_tokens, num_slices * max_rank)` is exactly the expand's input, so decode stays on XPU from A to B. The expand fuses per-adapter scaling and the `base_output` residual.
- Supports decode and prefill graph capture (`supports_prefill_cuda_graph = True`, 32 fixed prefill segment slots). Batches with more requests fall back to eager prefill.
- Batch preparation (segment routing, lm_head pruning, graph metadata) follows the triton backend's `LoRABatchInfo` layout.

**Registration and CLI**
- `lora/backend/lora_registry.py`: register `intel_xpu`.
- `arg_groups/choices.py`: add `LORA_BACKEND_CHOICES` (including `intel_xpu`). `arg_groups/fields/lora.py` now reads `--lora-backend` choices from it instead of a hardcoded list, and `server_args.py` re-exports it with the other choice lists.

**Validation**
- `arg_groups/validation_hook.py`: `validate_device_lora_backend` rejects `--lora-backend intel_xpu` without `--device xpu` at argument-check time. Without it, the error only appears later as an import failure inside `LoRAManager` init. This mirrors the existing `--sampling-backend intel_xpu` check.

**Tests**
- `test/registered/unit/server_args/test_server_args.py`: `TestIntelXpuLoRABackend` (CPU CI) checks that the backend is registered and selectable from the CLI, rejected off XPU, and accepted on XPU.
- `test/manual/lora/test_lora_xpu_basics.py`: add `intel_xpu` to `DENSE_BACKENDS`, so it runs the HF+PEFT logprob comparison and the multi-LoRA batching / drainer routing tests next to `triton`, `csgmv`, and `torch_native`.

Mean E2E latency is still 15 % lower than `csgmv`'s (10140 vs 11895 ms); total throughput, TPOT, and E2E latency are the meaningful metrics for decode scenarios.

The base (no-LoRA) path is unchanged by this PR: it only adds the `intel_xpu` LoRA backend, its `--lora-backend` choice, and the `--device xpu` check.

These fused B kernels, and the decode chunked expand, read slice p at column p * max_rank and ignore `lora_ranks`, but `LoRAMemoryPool` packs a rank-r adapter's stacked A at stride r. Any adapter below `--max-lora-rank` gets wrong k, v and up deltas; triton masks by rank. Rank-aware kernels, or a max_rank-spaced pool layout?

- siju-samuel · comment · 2026-10-19T11:49:00Z · [source](https://github.com/sgl-project/sglang/pull/44769#discussion_r4313446574)

These kernels also need A rows and B columns past the adapter's rank zeroed, but slot eviction reloads only the first r, so a rank-8 adapter in a slot a rank-16 one used keeps the old tail and part of its delta leaks in.
