# [Feat] beam: Add Beam model, runtime support and checkpoints (4/7)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45256) · state: closed · merged: True

## Original PR description

## Motivation

Split #44747 into reviewable parts. This part adds the runtime support Beam relies on and the Beam model, position 4 of 7 in the merge order below. It folds in #45255, which is closed in its favor, the way Muse Spark's runtime and model landed together. It is based on #45254's branch (`beam-stack-02-kernels`), so its diff shows only this part.

## Modifications

Runtime support:
- **TRT-LLM MHA.** An extend batch whose trailing requests extend by one token runs that tail on the decode kernel. This now also covers FP8 KV and batches made only of one-token requests. It extends #43238 and runs on trtllm-gen (SM100) only; SM90 and SM120 take FMHA-v2 or the context-parallel path and never reach it.
- **FlashInfer MegaMoE.** Beam is added to the validated MegaMoE architectures. The startup autotune fix that the high-throughput recipe needs with default autotune, and the optional decode workspace, are in #46213.
- **PD decode.** A token-ID logprob row is reserved for the handoff token, so streamed rows stay aligned. That row is empty, because prefill does not send token-ID logprobs.
- **Forward-pass metrics.** DFlash is added to the spec decode pre-settlement snapshot.
- **Pool configurator.** The SWA request-cap budget now includes the DFlash draft cell.

Beam model and config:
- Hybrid sliding-window/full attention, SSMax query scaling, attention output gating, sandwich norms, depth-scaled residuals and grouped MoE routing.
- BF16, ModelOpt NVFP4 and compressed-tensors FP8 checkpoints. Compressed-tensors NVFP4 is rejected.
- **DFlash integration.** Beam uses the general CUDA attention-DP implementation from merged #46330 and draft placement from merged #46290. This PR adds the `DFlash2BeamDraftModel` alias, Beam's embedding/lm-head DP mapping, and hidden-state capture. The generic DFlash admission hook, worker, embedding helper and verify-metadata path match the parent branch.
- GB300 Triton MoE configs for `E=256,N=640`, used by the BF16 Triton MoE path.
- **Opt-in single-token MoE GEMV** (`SGLANG_OPT_BEAM_DECODE_GEMV`).
  - It uses the unquantized Triton MoE path and requires `SGLANG_OPT_FUSE_SWIGLU_INTERLEAVED=1`, BF16 experts of the Beam shape, MoE TP4/EP1 and SM103. Each invocation also needs one contiguous BF16 token.
  - Other setups, and forwards with more than one token, keep their normal MoE path. Only a failed static check logs that the switch is unused.
  - It is not bit-exact with the Triton path.

Beam's router uses the tiny FP32 GEMM up to 16 tokens for BF16 checkpoints, then the GEMV, then the cuBLAS BF16x3 GEMM. The cuTile router and `SGLANG_BEAM_ROUTER_BACKEND` are in #45361.

General fixes found while adding Beam are in their own PRs:
- #46213: MegaMoE startup autotune on FlashInfer 0.7.2, and an optional decode workspace;
- #46214: the FlashInfer ragged prefill sliding window;
- #46200: the SWA KV pool start layer under pipeline parallelism.

The only test change is DFlash in `test_forward_pass_metrics.py`'s snapshot loop. Without the metrics change, Beam with DFlash and `--enable-forward-pass-metrics` fails during startup warmup with `TypeError: 'NoneType' object is not iterable`.

The Beam E2E test is in #45257. The unchanged upstream DFlash admission, embedding and metadata tests come from #46330.

LoRA serving for Beam is not part of this split. Beam raises `NotImplementedError` for `--enable-lora` and `--lora-paths` when the model is built. LoRA serving will follow separately.

The split commits carry the `Co-authored-by` trailers of the Beam commits that touched these files.

## Validation

**Current DFlash integration cleanup (`903d45e17d`):** 58 tests passed across seven existing DFlash/draft-placement files, with one existing CUDA-only test skipped in the CPU-only run. The nine admission/embedding/metadata cases pass unchanged. No test code was added or modified. The two remaining generic DFlash overrides were removed so this branch uses #46330's implementation.

**Historical GPU/model results:** the runs below predate this cleanup and were not repeated for it.

All runs are on 4×GB300 with FlashInfer 0.7.2. The tree is this PR plus #43216, which has since merged.
- **Checkpoints:** the public `reflection/Beam-1.0-501B-A23B-NVFP4`, `reflection/Beam-1.0-501B-A23B-FP8` and `reflection/Beam-1.0-501B-A23B` checkpoints, plus the DFlash2 draft.
- **Evaluation:** GSM8K with sgl-eval 0.1.3, 1,319 questions, temperature 0.
- **Revisions:** all runs are on earlier commits of this branch.
  - Those commits also carried the FlashInfer ragged sliding-window fix (now #46214), the MegaMoE changes (now #46213) and the SWA pool start-layer change (now #46200). None of the runs uses the FlashInfer attention backend, the decode workspace or pipeline parallelism.
  - The high-throughput rows with default autotune need #46213's autotune fix.
  - Since these runs, the branch has merged newer main changes through #45254, including #46330 and #46290. The DFlash cleanup removes the earlier Beam-only admission check and the broader selector-warmup override.
- **Cold-JIT row:** this run deliberately hid the AOT top-k artifact and removed its cached build.

| Configuration | GSM8K | Notes |
|---|---|---|
| Cookbook low-latency NVFP4 (TP4, DFlash, without parser flags) | 96.36% | zero request errors; the DFlash2 selector is folded into the draft CUDA graph |
| Cookbook low-latency FP8 | 96.66% | zero errors |
| Cookbook high-throughput NVFP4 (MegaMoE TP4/DP4/EP4), cold autotune cache | 96.44% | with #46213's autotune fix; MegaMoE autotune completes |

- **Verifier.** With #45257's parser changes on top of this branch, the pinned Beam verifier `dfa85fe771b3bcf014f5af5913f2ed363d31dfdf` passes all 133 required e2e cases at temperature 0, with its source and fixture integrity check passing and no skips.
  - The run uses the cookbook low-latency recipe with parser flags and scores 96.59% on GSM8K with zero request errors.
  - Chat reasoning, streaming, a chat tool call, Responses text, a Responses function call, a Responses shell round trip and `/tokenize` all pass.
  - No optional verifier suite or third-party evaluation was run.
- **TRT-LLM mixed tail.** The mixed-tail cases from #44747 pass (16 passed, 2 skipped on SM100). They include batches of only one-token requests, split-versus-unsplit parity, long-context FP64 references and CUDA-graph replay.
- **GEMV numerics.** Both kernels were compared with an FP64 reference that rounds to BF16 where the kernels do: after the gate/up projection, after `silu(gate) * up`, and at the routing-weighted output.
  - On 8 real checkpoint experts, the GEMV's BF16 output matches the reference on nearly every element, with relative L2 below 2e-9.
  - In the tested random-input cases, the GEMV is within relative L2 3.4e-4.
  - The Triton deferred-sum path is within 4.2e-4 to 6.8e-4 of the same reference, and the GEMV versus Triton is within 6.3e-4.
  - With a fixed kernel config, the shared Triton MoE path is bitwise unchanged from the base.
- **Existing GPU tests.** Main's tests for the touched code pass unedited: TRT-LLM MHA dense, graph metadata, encoder-only and stride parity; Triton MoE padding and fused MoE; and the DFlash buffer, Domino and graph-pool tests.
- **CPU tests.** The CPU tests that import the touched modules pass, except three files that fail the same way on main in this environment. pre-commit passes.
- **Known behavior.** Under attention DP4, a request's greedy output can change with other ranks' load.
  - This was observed with MegaMoE, with the TRT-LLM MoE runner without MegaMoE, without DFlash, and on the previously published head.
  - In the probe's valid comparisons, the isolated run's top-2 logprob margin at the first differing token ranged from 0 to 0.262 nat.
  - Isolated requests were deterministic in repeat probes, and these runs showed no GSM8K accuracy regression and zero request errors.
  - This does not establish universal batch invariance or a specific kernel-level cause. BF16 with attention DP2 matched isolated outputs exactly.
- **Not validated here:**
  - NPU;
  - Hopper and SM120 (all runs are on GB300);
  - BF16 on two nodes (TP8), including the TP8 cluster path of #45254's all-reduce boundary;
  - serving with PD token-ID logprobs (that fix has CPU checks only).

## Merge order

Each part is based on the one before it, so its diff shows only its own changes. Merge bottom-up; after each part merges, the next part is retargeted to `main` and `main` is merged into it. #44747 stays open, unchanged, as the full reference. Merge in this order:

1. #45253 — Beam CUDA Docker image (merged)
2. #45291 — OpenAI SDK 2.8.0, needed by the Responses shell tools in #45257 (merged)
3. #45254 — Kernels
4. #45256 — Beam model and runtime integration (using upstream #46330 for DFlash CUDA DP) (#45255 folded in; also after #46213 for the high-throughput recipe with default autotune; #43216 is merged)
5. #45257 — Beam reasoning, tool calls, response templates and the Beam E2E test (#40478, #43941 and #40479 are merged)
6. #45290 — `nvidia-cuda-tileiras`, needed by #45361
7. #45361 — cuTile BF16x3 router GEMM (optional: without it Beam uses the cuBLAS router)

#45292 (Dynamo and `grpcio-tools` pins for the Beam image) is not in the merge order for now.
