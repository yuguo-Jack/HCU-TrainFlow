# [Fix] K-EXAONE 1.0: expose the sliding window to the attention backends [1/5]

[Upstream PR](https://github.com/sgl-project/sglang/pull/43555) · state: open · merged: False

## Original PR description

## Motivation

`ExaoneMoEForCausalLM` never set `model_runner.sliding_window_size`, so the triton backend built no window buffers and every sliding layer failed at kernel compile (`kv_indptr is None`). The window passed to `RadixAttention` was also one too large: HF counts the query token inside the window, SGLang counts only the earlier tokens (`exaone4.py` and `gemma3_causal.py` already subtract one).

Part 1 of the K-EXAONE 1.0 serving stack. (I'll continuously support EXAONE for SGLang) 

## Modifications

- Add a module-level `get_attention_sliding_window_size(config)` returning `config.sliding_window - 1` and use it for the `RadixAttention` window on sliding layers.
- Expose the same value through `ExaoneMoEForCausalLM.get_attention_sliding_window_size()` so the attention backends build their window buffers.

## Accuracy Tests

16x A100 40GB, bf16, TP16, `--attention-backend triton`: before this change the server fails at the first sliding layer; after it, generation is coherent at 400 tokens. With the follow-up MTP-head change (It will be part 2) MTP acceptance is 0.880 (gsm8k) / 0.737 (mt-bench), GSM8K 90.0 (1319, non-thinking).

## Speed Tests and Profiling

Not applicable (correctness fix; no kernel or scheduling change).
