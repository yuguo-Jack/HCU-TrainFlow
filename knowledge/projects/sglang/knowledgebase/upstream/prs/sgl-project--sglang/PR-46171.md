# [Perf] diffusion: Gather spatial-parallel decode heights on the host

[Upstream PR](https://github.com/sgl-project/sglang/pull/46171) · state: closed · merged: True

## Original PR description

Branch: mick/diffusion-vae-height-gather-host (on main 005333d029), commit 2a864e5c69

## Motivation

Spatial-parallel VAE decode shards the frame height across the decode ranks. Each output gather (`gather_and_trim_height`) and each height-dependent op (the Wan VAE's row-sharded attention, strided convs) first learns every rank's shard height through `gather_height_sizes`. That helper built a one-element CUDA tensor from a Python int, all-gathered it over the device group and read each element back with `.item()`.

Both the pageable H2D copy and the read-back block the host until every kernel queued before them has run. In the middle of a decode, that drains the GPU queue: the GPU idles while the host relaunches the rest of the decoder. The Wan VAE decodes one latent frame per call and pays this twice per frame. A Cosmos3-Nano 189-frame decode on 4xB300 (48 latent frames) issued 96 stream syncs, which held the host for 590 ms in one profiled request. About 420 ms of the 2.47 s decode window was GPU idle.

## Modifications

- `layers/parallel_conv.py`: `gather_height_sizes` all-gathers the heights as a CPU int64 tensor over the group's gloo `cpu_group` instead of the device group. It does no device work and no stream sync. The values and the call order are the same on every rank, so every decode returns the same result.
- `test_vae_spatial_parallel_decode.py`: `test_height_sizes_are_gathered_on_the_host` runs two gloo ranks with uneven shards (3 and 2 rows) and passes `meta` tensors with no device group. The gather returns `[3, 2]` on both ranks. The old device gather cannot run on meta tensors.
- `test_ltx_vae_parallel_decode.py`: the fake decode group now carries a `cpu_group`.

## Accuracy Tests

The heights are integers and only travel over a different group, so every output is bitwise unchanged. Cosmos3-Nano T2V 720p 189 frames on 4xB300: the MP4s are byte-identical to the base (md5 a494ab96ce / 80597a2763 for two requests). They are also identical at x264 crf 0 together with "Encode Cosmos3 video while it decodes".

## Speed Tests and Profiling

Cosmos3-Nano T2V 720p 189 frames, 4xB300, CFG 2 x Ulysses 2, 4-rank spatial-parallel VAE decode, synchronized stage timers, two requests per build:

| | client e2e | decode stage |
|---|---|---|
| base | 24.251 / 24.300 s | 1.818 / 1.815 s |
| this PR | 24.053 / 24.069 s | 1.619 / 1.621 s |

The decode is 0.2 s (11%) shorter. With "Encode Cosmos3 video while it decodes" on top, the decode stage absorbs the MP4 encode and still takes only 1.717 / 1.730 s. Other affected models: every spatial-parallel decode that gathers heights (Wan family, Qwen-Image, Qwen-Image 2.1, HunyuanVideo, FLUX.3, LTX-2 strided convs).
