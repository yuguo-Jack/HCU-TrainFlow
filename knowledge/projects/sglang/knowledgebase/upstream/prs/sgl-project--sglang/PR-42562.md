# [Fix] Validate weight-cache memory operations before changing state

[Upstream PR](https://github.com/sgl-project/sglang/pull/42562) · state: closed · merged: False

## Original PR description

## Motivation

With `--weight-cache-mode client` or `daemon`, releasing or resuming the shared weights is deliberately unsupported. The guard currently runs after updating `offload_tags` and, for a default release, after pausing KV memory and flushing its cache. The caller therefore receives an error after the engine has already changed state. A default resume after a valid KV/graph release can likewise remove paused tags before raising `KeyError` for the resident weights.

Reject a request containing `weights` before changing any memory region, cache, or occupancy bookkeeping, so the original state remains available for a valid follow-up operation.

## Modifications

- Move the existing weight-cache compatibility check immediately after tag resolution in both release and resume.
- Add registered CPU tests with a stateful memory-saver boundary. Cover both active cache modes, default/empty/explicit tags, preserved KV and occupancy state, and a successful follow-up resume.
- Cover valid KV-only operations with shared weights, and static-buffer restoration when weight caching is off.

Related PRs #37932 and #39472 were inspected: they address memory-release synchronization/order and disk rebuild/residency, respectively; neither moves this guard ahead of all state changes.
