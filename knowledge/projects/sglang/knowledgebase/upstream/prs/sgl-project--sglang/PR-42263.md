# [sgl-kernel] Build common_ops for sm_90a when FA3 is off (aarch64 wheels lack it)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42263) · state: closed · merged: False

## Original PR description

## Motivation

On a GH200 (aarch64, sm_90), the SM90 CUTLASS GEMMs in the released `sglang-kernel` 0.4.8 aarch64 wheel compute nothing. Each call prints

```
ERROR : Arch conditional MMA instruction used without targeting sm90a compute capability. Aborting.
```

and returns without computing the product. Some calls print the same line with "appropriate" in place of "sm90a"; that is the one the server printed. In my runs the outputs were NaN, values up to 5.8e34, or plain wrong numbers. A Qwen3.5-4B server launched with `--quantization fp8` wrote the line 188,469 times (20 MB) in under 50 seconds, starting at prefill CUDA graph capture, until my log cap cut the log off.

The aarch64 wheel's `common_ops` has no sm_90a code; the x86_64 wheel of the same release has it. #28394 made FA3 default off on aarch64. In the same change, it made the sm_90a gencode for `common_ops` conditional on FA3 ([CMakeLists.txt#L243-L247](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/kernels/aot/CMakeLists.txt#L243-L247)). Before #28394, every build with CUDA >= 12.4 added it.

## Modifications

The condition drops `AND SGL_KERNEL_ENABLE_FA3`, with a one-line comment saying why. FA3 itself stays off on aarch64.

- Builds with FA3 on, the x86_64 default with CUDA >= 12.4, get identical flags.
- Builds with FA3 off, the aarch64 default, add sm_90a to `common_ops` (both the sm90 and sm100 builds) and to `spatial_ops`. Other targets are unchanged.

I checked both with a configure-only run on aarch64, reading each target's gencodes from `build.ninja`.

`cutlass_fp8_supported()` is unchanged. It cannot tell which SASS a wheel carries without loading or disassembling the library. Wheels that are already released stay affected. On them, `USE_TRITON_W8A8_FP8_KERNEL=1` keeps FP8 linear layers off the CUTLASS path, but the INT8 linear layers and the W4A8 MoE GEMMs have no such switch.

## Accuracy Tests

I tested on one GH200 (CUDA 13.0, torch 2.13.0+cu130). To keep the builds short, I built only `common_ops_sm90_build` and only for SM90, twice: once with sm_90 + sm_90a (this PR's layout for SM90) and once with sm_90a alone. Each build went into a copy of the installed `sgl_kernel` package, in place of `sm90/common_ops.abi3.so`.

- sgl-kernel's FP8, INT8 and MoE GEMM tests (five files) pass with both rebuilt libraries, and neither prints the error. Against the wheel's library, each file fails on its first case.
- When both sm_90 and sm_90a code are present, the driver loads the sm_90a code. A probe kernel that reports `__CUDA_ARCH_FEAT_SM90_ALL` gave 1 when built for both (in either gencode order) and 0 for sm_90 alone.
- With the sm_90a-only library, the Qwen3.5-4B server with `--quantization fp8` started and did not print the line (two launches). It scores 0.830 on the first 200 GSM8K test questions. With otherwise identical flags, BF16 scores 0.870 and the wheel with `USE_TRITON_W8A8_FP8_KERNEL=1` scores 0.845. With 200 questions the 95% intervals are about 10 points wide, so this only shows that the FP8 server answers sensibly.

The full commands, per-file test counts and environment are in the details below.

### Motivation

On a GH200 (sm_90, aarch64), the SM90 CUTLASS GEMMs in the released `sglang-kernel` 0.4.8 wheel compute nothing. Each call prints

```
ERROR : Arch conditional MMA instruction used without targeting sm90a compute capability. Aborting.
```

(or the same line with "appropriate" in place of "sm90a", from CUTLASS's TMA warp-specialized pingpong and cooperative kernels; the server printed that one) from the device, then returns without computing the product. In my runs the outputs were NaN, values up to 5.8e34, or plain wrong numbers. With `python -m sglang.launch_server --model-path Qwen/Qwen3.5-4B --quantization fp8` (plus memory and batch limits for a shared GPU, listed under Accuracy Tests), the server wrote the line 188,469 times (20 MB) in under 50 seconds, starting at prefill CUDA graph capture, until my log cap cut the log off. `cutlass_fp8_supported()` is True on any SM90 GPU with CUDA >= 12.0 ([fp8_utils.py#L298](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/srt/layers/quantization/fp8_utils.py#L298)), so online FP8 quantizes weights per channel and sends the linear layers to `fp8_scaled_mm` ([L2194-L2207](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/srt/layers/quantization/fp8_utils.py#L2194-L2207); shapes with a tuned Triton config are the exception).

The aarch64 wheel's `common_ops` has no sm_90a code:

```
$ cuobjdump --list-elf sgl_kernel/sm90/common_ops.abi3.so | sed 's/.*\.\(sm_[0-9a-z]*\)\..*/\1/' | sort | uniq -c
     35 sm_100
     35 sm_110a
     35 sm_120a
     35 sm_121a
     35 sm_90
```

The x86_64 wheel of the same release has 35 sm_90a ELFs in both `sm90/` and `sm100/common_ops`, next to sm_80, sm_89, sm_90, sm_100 and sm_120a. CUTLASS's SM90 warp-specialized kernels compile to the stub that prints the message above unless they are built for sm_90a.

The cause is in `python/sglang/kernels/aot/CMakeLists.txt`. #28394 made FA3 default off on aarch64 ([L109-L115](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/kernels/aot/CMakeLists.txt#L109-L115)). In the same change, the sm_90a gencode for `common_ops` became conditional on FA3 ([L243-L247](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/kernels/aot/CMakeLists.txt#L243-L247)). Before #28394, every build with CUDA >= 12.4 added it. FlashMLA's build adds sm_90a without looking at FA3 ([cmake/flashmla.cmake#L32-L36](https://github.com/sgl-project/sglang/blob/f6fcda8827e5d8a2f0b999cd3b32f5096ee6a82c/python/sglang/kernels/aot/cmake/flashmla.cmake#L32-L36)), which is why `flashmla_ops` in the same wheel has it.

### Modifications

The condition drops `AND SGL_KERNEL_ENABLE_FA3`, and a one-line comment says why it does not depend on FA3. The flags change only where FA3 is off. I configured the build on aarch64 with CUDA 13.0 (no compile) and read each target's gencodes from `build.ninja`:

| Configuration | `common_ops` (sm90 and sm100 builds), `spatial_ops` | Other targets |
|---|---|---|
| FA3 off (aarch64 default), main | sm_90, sm_100f, sm_110a, sm_120a, sm_121a | |
| FA3 off (aarch64 default), this PR | the same plus sm_90a | unchanged |
| FA3 on (`-DSGL_KERNEL_ENABLE_FA3=ON`, the x86_64 default with CUDA >= 12.4), main and this PR | identical | identical |

All four were configured on the same aarch64 machine.

The aarch64 wheel still ships the `sm90` build that the loader picks on GH200, so GH200 is evidently meant to work. FA3 stays off on aarch64; only the `common_ops` gencode goes back to its condition before #28394. `SGL_KERNEL_ENABLE_SM90A` stays declared and unused, as it is on main.

I left `cutlass_fp8_supported()` alone. It checks the device and the CUDA version, and it cannot tell which SASS a wheel carries without loading or disassembling the library. With the build fixed, its answer is correct again. Wheels that are already released stay affected. On them, `USE_TRITON_W8A8_FP8_KERNEL=1` keeps FP8 linear layers off the CUTLASS path; the INT8 linear layers and the W4A8 MoE GEMMs have no such switch, and the FP8 MoE GEMMs use CUTLASS only with `--moe-runner-backend cutlass`.

### Accuracy Tests

On one GH200 (aarch64; driver 570.195 with the CUDA 13.0 forward-compatibility libraries, cuda-compat 580.178; CUDA 13.0 toolkit; torch 2.13.0+cu130), SGLang main at f6fcda8827. To keep the builds short, I built only `common_ops_sm90_build`, from this PR plus a local commit (not part of this PR) that drops gencodes after this PR's condition has added sm_90a. There were two builds: sm_90a alone, and sm_90 + sm_90a, which is this PR's layout for SM90. The full gencode lists above come from the configure-only check. For the tests, a copy of the installed `sgl_kernel` package with `sm90/common_ops.abi3.so` replaced by a build went first on `PYTHONPATH`; no other file changed.

With both sm_90 and sm_90a code present, the driver loads the sm_90a code on GH200. A small probe kernel that reports `__CUDA_ARCH_FEAT_SM90_ALL` gave 0 when built for sm_90 alone, 1 for sm_90a alone, and 1 when built for both, in either gencode order.

- `cuobjdump --list-elf` on the built `sm90/common_ops.abi3.so`: 35 sm_90a ELFs for the first build, 35 sm_90 and 35 sm_90a for the second (the wheel's has no sm_90a).
- Direct `fp8_scaled_mm` and `int8_scaled_mm` calls at N = 4096, K = 2560, M = 1, 16 and 256, against an FP32 reference. With the wheel's library, `fp8_scaled_mm` at M = 1 printed the error and returned NaN. With either rebuilt library, every case matched, with identical errors: max |error| at most 1.2e-4 for FP8 (outputs up to 0.023), and at most 0.25 for INT8 with BF16 output (outputs up to 125), which is BF16 rounding.
- sgl-kernel's tests, run from `python/sglang/kernels/aot/tests` against each library (the wheel's runs with `-x`, so they stop at the first failure). Both rebuilt libraries gave the counts in the last column:

  | Test file | Wheel's library | Rebuilt library |
  |---|---|---|
  | `test_fp8_gemm.py` | first case fails (max abs difference 5.8e34); error printed 512 times | 816 passed, 1 skipped |
  | `test_int8_gemm.py` | first case fails (all 16 elements mismatched); error printed 2,048 times | 1260 passed |
  | `test_fp8_blockwise_moe.py` | first case fails (the test's difference metric is 1.0, limit 0.001); error printed thousands of times | 10 passed |
  | `test_es_fp8_blockwise_moe.py` | first case fails (difference metric 1.0, limit 0.001); error printed thousands of times | 10 passed |
  | `test_cutlass_w4a8_moe_mm.py` | first case fails (945 of 1,024 elements mismatched); error printed thousands of times | 605 passed |

  The rebuilt libraries printed the error zero times.
- Qwen/Qwen3.5-4B with `--quantization fp8` (online FP8: per-channel weight scales, per-token activation scales), launched as `python -m sglang.launch_server --model-path Qwen/Qwen3.5-4B --revision 851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a --attention-backend flashinfer --mm-attention-backend triton_attn --mem-fraction-static 0.25 --max-running-requests 16 --mamba-full-memory-ratio 2 --max-total-tokens 200000 --cuda-graph-max-bs-decode 32 --random-seed 0 --quantization fp8`. With the sm_90a-only library the server started and did not print the line (two launches). It scores 0.830 on GSM8K (first 200 test questions, 5-shot, `sglang.test.few_shot_gsm8k`). With otherwise identical flags, BF16 scores 0.870 and the wheel's library with `USE_TRITON_W8A8_FP8_KERNEL=1` (Triton FP8 GEMMs instead of CUTLASS) scores 0.845 and did not print the line either. With 200 questions this only shows that the FP8 server answers sensibly: the 95% intervals (Wilson) are about 10 points wide (0.77-0.88 for 0.830, 0.79-0.89 for 0.845, 0.82-0.91 for 0.870), so it is not a measure of FP8's accuracy.

### Not tested

- Build time. Both `common_ops` builds and `spatial_ops` compile one more architecture, and the wheel build (`python/sglang/kernels/aot/Dockerfile`) runs 2 parallel jobs on ARM. For scale, my builds of `common_ops_sm90_build` took 7 minutes (sm_90a only) and 8 minutes (sm_90 + sm_90a) on 16 cores.
- Blackwell (GB200). Its loader picks the `sm100` build, which now also carries sm_90a code that never loads there, as on x86_64.
