# [Fix] speculative: add pp_proxy_tensors kwarg to UNO and Frozen KV MTP spec-v2 workers

[Upstream PR](https://github.com/sgl-project/sglang/pull/44246) · state: closed · merged: False

## Original PR description

## Background
The scheduler always passes `pp_proxy_tensors=` to all speculative workers' `forward_batch_generation()`, but UNO and Frozen KV MTP workers were missing this parameter in their method signature, causing a `TypeError` at runtime.

This is the second wave of the spec-v2 worker signature drift tracked in **#40155**: eagle / multi_layer_eagle / dflash / dspark / ngram were already patched earlier in the series; the two remaining ones are `uno_worker_v2.py` and `frozen_kv_mtp_worker_v2.py`.

## Problem
When running with `tp_size > 1` and the non-overlapped speculative decoding path, the scheduler raised:

```
TypeError: forward_batch_generation() got an unexpected keyword argument "pp_proxy_tensors"
```

## Solution
Added `pp_proxy_tensors=None` to `forward_batch_generation()` in both files:

- `python/sglang/srt/speculative/uno_worker_v2.py`
- `python/sglang/srt/speculative/frozen_kv_mtp_worker_v2.py`

UNO and Frozen KV MTP do not run pipeline-parallel stages, so they simply `del pp_proxy_tensors` to satisfy the shared signature contract — exactly the pattern the rest of the spec-v2 worker family uses for kwargs they ignore.

This brings all **7** spec-v2 workers (eagle, multi_layer_eagle, dflash, dspark, ngram, uno, frozen_kv_mtp) back to a consistent signature that accepts `pp_proxy_tensors=` unconditionally.

## Testing
- `python -c "import ast; ast.parse(open(f).read())"` on both edited files — syntax OK.
- Grep + regex verification that every `forward_batch_generation()` in `python/sglang/srt/speculative/**` now accepts `pp_proxy_tensors`.

Fixes #40155.
