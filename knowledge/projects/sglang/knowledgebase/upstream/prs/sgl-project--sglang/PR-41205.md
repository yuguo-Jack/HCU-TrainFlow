# [Sampling] Write /generate sampling masks from numpy rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/41205) · state: closed · merged: False

## Original PR description

## Motivation

After #40986, the tokenizer manager's list building bounds the sampling-mask return. It creates one Python int per support entry, plus one float per entry in support mode. At batch 256 with `top_k=8192`, a staggered RL rollout in selected mode takes 64.9 s against 11.2 s with masks off, and most of that gap is this list building.

`/generate` serializes its response with `dumps_json`, which is orjson with `OPT_SERIALIZE_NUMPY` (#19191) and writes numpy arrays as JSON lists. On `/generate`, those Python objects are built, walked by the garbage collector, serialized and freed without anything else reading them.

Builds on #40986 (merged), which introduced `SamplingMaskChunk`.

## Contract

- **`/generate`:** responses are byte-identical, streaming and non-streaming.
- **Every other caller** (`Engine`, OpenAI serving, gRPC, Ollama) still receives Python lists.
- **Request logs** (text and JSON) **and exported request metrics** write the same records. The new internal `numpy_outputs` field appears among the logged request parameters, as any request field does.
- **Masks off:** nothing changes.

## Design

1. **`/generate` marks its requests** (commit 2). The route sets `GenerateReqInput.numpy_outputs`, an internal field next to `return_bytes`, and batch sub-requests inherit it. No other entry point sets it.
2. **Rows stay numpy for those requests** (commit 2).
   - `SamplingMaskChunk.to_arrays()` mirrors `to_lists()`: it slices each token's row out of the chunk received over IPC, as a view, instead of converting it. A one-row chunk costs 0.9 µs against 1.0 µs for `to_lists`; 50 rows × 8192 cost 2.8 ms against 15.5 ms, both including `dumps_json`.
   - Support-mode logprobs are cast to float64 once per chunk. orjson writes float32 values with float32's shortest repr (`0.1`), while the lists hold Python floats (`0.10000000149011612`).
   - Selected-mode logprobs stay Python floats, one per token.
   - Stream coalescing and incremental slicing only touch the outer list, so they are unchanged.
3. **Sinks write arrays as lists** (commit 1). Request logging and the metrics exporter read the same outputs as the `/generate` serializer.
   - The JSON writers (`log_json` and the exporter) pass `default=np.ndarray.tolist`.
   - The JSON log formatter converts an array to a list before truncating it, as it already truncates lists.
   - The text formatter converts array elements before `str()`.
   - Without this commit, JSON request logging would raise `TypeError` in the request path, and the exporter would drop the record.
   - The Python-object cost is paid only while a sink is on.

### Alternatives considered

- **Numpy rows for every caller.** `Engine` users would get arrays instead of lists, and OpenAI chat's pydantic `meta_info` cannot serialize them.
- **Fall back to lists whenever a sink is enabled.** This keeps the sinks untouched, but:
  - the check has to enumerate every sink;
  - a sink enabled through `/configure_logging` after a request's rows were built would still receive arrays.

## Performance

Same-host A/B of #40986's head (now in `main`) vs this branch: one H100 machine runs both servers in turn. Qwen3-8B, TP1, `temperature=1`, `ignore_eos`, pickle IPC.

**RL rollouts with staggered finishes.** Batch 256; each request's `max_new_tokens` is spread evenly over the range. The metric is wall time for the whole batch.

| workload | mask off | #40986 | this PR |
|---|---|---|---|
| selected, `top_k=8192`, 64–1024 tokens | 11.2 s | 64.9 s | **16.9 s** |
| support, `top_k=8192`, 32–512 tokens | 5.2 s | 73.6 s | **25.7 s** |
| support, `top_k=128`, 64–1024 tokens | 11.6 s | 12.6 s | 12.5 s |
| support, `top_k=256`, 64–1024 tokens | 11.6 s | 12.7 s | 12.6 s |

**Throughput suite, 512 new tokens.** Decode throughput is within 0.7% in all 27 configurations, since the scheduler does the same work. Wall time is within 0.1 s everywhere except where the response lists were large:

| workload | #40986 | this PR |
|---|---|---|
| batch 256, `top_k=1000`, selected | 12.9 s | 9.8 s |
| batch 256, `top_k=1000`, support | 30.2 s | 14.7 s |
| batch 64, `top_k=1000`, selected | 5.3 s | 5.1 s |
| batch 64, `top_k=1000`, support | 7.5 s | 6.5 s |

**Per-token streaming** (`--incremental-streaming-output`, batch 256), wall time, one run in each order:

| workload | run 1 | run 2 (this PR first) |
|---|---|---|
| mask off, `top_k=20` | 4.3 → 4.1 s | 3.6 → 3.6 s |
| selected, `top_k=20` | 6.6 → 4.8 s | 4.6 → 4.5 s |
| support, `top_k=20` | 7.3 → 5.3 s | 5.4 → 4.5 s |
| selected, `top_k=1000` | 13.4 → 7.6 s | 10.4 → 5.3 s |
| support, `top_k=1000` | 20.9 → 11.2 s | 17.6 → 8.2 s |

In run 1, #40986's server was launched first on the machine. Its `top_k=20` rows are slower than in run 2 (6.6 and 7.3 s against 4.6 and 5.4 s), so run 2 is the cleaner comparison there. Batch 64 rows are within 0.1 s, or faster.

## Correctness

Tests in this PR:

- **`test_clients_receive_the_sampler_rows_unchanged` (extended):** across decode steps, stream emissions and both IPC codecs, `dumps_json` of the numpy rows equals `dumps_json` of the base list conversion.
- **`test_numpy_rows_write_the_same_json_as_lists`:** covers
  - float32 values whose shortest repr differs from float64's: `0.1`, `-0.0`, a subnormal, `-FLT_MAX`;
  - int32 extremes;
  - chunks without rows.
- **`test_only_numpy_output_requests_get_numpy_rows`:** a request without `numpy_outputs` gets Python lists from `_handle_batch_output`, and one with it gets the same JSON.
- **`test_finished_request_logs_numpy_rows_as_lists`:** text and JSON request logs at levels 0–3, including rows past the level's truncation length.
- **`test_write_record_writes_numpy_rows_as_lists`:** the metrics exporter.

Each part of the change has a test that fails when that part is broken:
- the float64 cast;
- the text or JSON log conversion;
- either `default` hook;
- the lists-by-default branch.

**End-to-end equivalence against `main`.** The 54-request workload from #40986 is sent to `main` twice, then to this branch, on one machine. The responses are compared floats bitwise and by each number's JSON text. All runs use `--enable-deterministic-inference`.

| configuration | main vs main | main vs this PR |
|---|---|---|
| requests sent one at a time | 54/54 | **54/54** |
| concurrent requests | 54/54 | **54/54** |
| concurrent, `--incremental-streaming-output` | 54/54 | **54/54** |
| concurrent, `--tokenizer-worker-num 2` | 54/54 | **54/54** |
| concurrent, msgpack IPC | 54/54 | **54/54** |
| concurrent, JSON request logging (level 2) | 54/54 | 51/54¹ |
| concurrent, text request logging (level 3) | 54/54 | 53/54¹ |
| concurrent, metrics export to file | 52/54¹ | **54/54** |

¹ The known row-0 difference from #40986: the logprobs of the token sampled at prefill, 1–2 float32 ulps apart, with identical support IDs, `text` and `output_ids`. It shows up between two runs of `main` too. It depends on how concurrent requests share prefill batches.

No server log in these runs has a traceback or a failed metrics write.

After rebasing onto `main` with #40986 merged, two of these configurations were rerun against `main`: requests sent one at a time, and concurrent requests with JSON request logging. Both are again 54/54 identical, including the number text, with no server errors.
