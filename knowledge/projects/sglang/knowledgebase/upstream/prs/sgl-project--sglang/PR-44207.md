# [Fix] sglang-server: Honour extra_key on the Rust frontend's /generate

[Upstream PR](https://github.com/sgl-project/sglang/pull/44207) · state: closed · merged: True

## Original PR description

## Motivation

`extra_key` is the request's prefix-cache namespace: the scheduler keys radix-cache entries by it, so two requests share cached prefixes only under the same key. The Python `/generate` route honours it (`GenerateReqInput._normalize_extra_key`), and the OpenAI-compatible processors in `rust/sglang-processor` already forward it into the native body (`"extra_key": request.extra_key`), but the Rust frontend's `/generate` schema did not carry the field. In Rust mode it was dropped as an unknown key, so every request landed in one cache namespace and requests sent under different keys could reuse each other's cached prefixes.

## Modifications

- `proto/sglang/api/v1/generate.proto`: add `extra_key` (tag 23, `StringOrList`) to `GenerateRequest`; regenerated `api_types.py`, `sglang.api.v1.rs` and `sglang.api.v1.serde.rs` with `cargo gen-api`.
- `rust/sglang-server/src/message/request.rs`: fan `extra_key` out with the Python semantics: one key broadcasts to every item, a list is per item and must match the batch size, an empty key means none, and a list on a single (non-batch) request is a 400 (`extra_key should be a string for a single request.`), as in `GenerateReqInput`.
- `rust/sglang-server/src/message/io_struct.rs`: carry it into the scheduler header's `extra_key` slot. The header is decoded positionally (`TokenizedGenerateReqInput` is an `array_like` msgspec struct), so the three slots before it (`routing_key`, `require_reasoning`, `priority`) are now emitted at their defaults; the header grows from 32 to 36 entries. Everything after `extra_key` still has a msgspec default and stays omitted.
- `test/registered/unit/api/v1/test_parity.py`: `extra_key` leaves the pinned list of Python-only request fields.
