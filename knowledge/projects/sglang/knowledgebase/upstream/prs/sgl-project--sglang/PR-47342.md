## Motivation

Bring the gfx950 TLX KDA kernels from fbtriton ([facebookexperimental/triton#4243](https://github.com/facebookexperimental/triton/pull/4243)) into SGLang as an opt-in KDA backend for Kimi-K3 on MI350/MI355X, running on ROCm Triton with the uTLX plugin.

## Modifications

- **TLX kernel backend**: `KernelBackend.TLX` (with `BaseFusedOp.forward_tlx`), and the convention that TLX kernels live in a `tlx/` subpackage of their op group (`ops/attention/tlx/`).
- **Vendored kernels**: `gfx950_prefill.py` / `gfx950_decode.py` from fbtriton `7d38f0a`, unmodified apart from a license header and formatting. The prefill uses TLX; the decode is plain Triton.
- **Backend**: `--linear-attn-{decode,prefill}-backend tlx` selects `TlxKDAKernel`. As in the other KDA backends, what the TLX kernels do not cover falls back to Triton: tracked / per-chunk states, draft extend, prefill CUDA graph tables, unsupported inputs (with a one-time warning). It also works with `--enable-linear-replayssm-spec`; verify stays on the selected verify backend.
- **No device sync in TLX prefill**: `kda_paged_prefill` takes `cu_seqlens_cpu` (filled from `extend_seq_lens_cpu`). This is a local change to the vendored file, to be upstreamed.
- The K3 HIP fused decode now logs that it takes precedence over `--linear-attn-decode-backend`, as the CUDA one does (`SGLANG_ROCM_K3_KDA_FUSED_BACKEND=none` disables it).

the modification in `.codespellrc` is to avoid lint test failure in fbtriton kernel.

Usage (Kimi-K3, TP8, MI355X, DSPARK):

```bash
SGLANG_USE_AITER=1 \
SGLANG_AITER_K3_OPT=1 \
AITER_FLYDSL_FORCE=1 \
AITER_SITUV2_A8W4=1 \
SGLANG_AITER_HONOR_EXPLICIT_MEM_FRACTION=1 \
sglang serve \
  --model-path moonshotai/Kimi-K3 \
  --trust-remote-code \
  --tp-size 8 \
  --dcp-size 8 \
  --dcp-comm-backend a2a \
  --prefill-attention-backend aiter \
  --decode-attention-backend aiter \
  --kv-cache-dtype fp8_e4m3 \
  --dtype bfloat16 \
  --mem-fraction-static 0.85 \
  --cuda-graph-max-bs-decode 256 \
  --mamba-full-memory-ratio 7.97 \
  --reasoning-parser kimi_k3 \
  --tool-call-parser kimi_k3 \
  --disable-radix-cache \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path RadixArk/Kimi-K3-DSpark \
  --speculative-dspark-block-size 7 \
  --enable-linear-replayssm-spec \
  --linear-attn-prefill-backend tlx \
  --linear-attn-decode-backend tlx
```

- `default` in the tables is the same command without the two `--linear-attn-*-backend tlx` flags; `no spec` drops the three `--speculative-*` flags and `--enable-linear-replayssm-spec`.
- The TLX prefill needs ROCm Triton with the uTLX plugin, e.g. a gfx950 rocm10 image built with `--build-arg BUILD_UTLX=1`. Leave async copy on: with the plugin, `TRITON_HIP_USE_ASYNC_COPY=0` makes the prefill fall back to Triton.
- The startup log shows which kernels run: `KDA kernel dispatcher: decode=TlxKDAKernel, verify=TritonKDAKernel, extend=TlxKDAKernel packed_decode=False`.
- Under DSPARK the target model's decode steps are verify steps, which stay on Triton, so TLX runs the prefill. Without spec, the K3 HIP fused decode still takes the decode shapes it covers; `SGLANG_ROCM_K3_KDA_FUSED_BACKEND=none` sends them to TLX.

## Accuracy Tests

Kimi-K3, TP8, MI355X, `--disable-radix-cache`, GSM8K (1319 questions):

| Config | tlx | default |
|---|---|---|
| no spec | 0.949 | 0.955 |
| DSPARK + `--enable-linear-replayssm-spec` | 0.939 | 0.944 |

Speculative accept length: 5.61 vs 5.61.

## Speed Tests and Profiling

`sglang.benchmark.serving`, random 8192 in / 256 out, concurrency 16, 64 prompts. DSPARK + replayssm-spec, 3 runs each:

| | tlx | default |
|---|---|---|
| Output throughput (tok/s) | 434–437 | 434–438 |
| Mean TTFT (ms) | 2536–2751 | 2482–2564 |
| Median TTFT (ms) | 1955–2262 | 2092–2273 |
| Mean TPOT (ms) | 25.1–26.2 | 26.0–26.5 |

End to end, tlx is on par with the default path. Without spec decoding it is also on par (TTFT 4699 vs 4721 ms, TPOT 34.5 vs 34.2 ms).

Kernel level (K3 shapes):
- The TLX prefill takes 0.71–1.00x the time of the default HIP prefill as served, which includes the HIP wrapper's q/k/v copies; the HIP kernel alone is faster on most shapes.
- `cu_seqlens_cpu` cuts the first-layer schedule overhead from 75–100 us to 6–7 us.
