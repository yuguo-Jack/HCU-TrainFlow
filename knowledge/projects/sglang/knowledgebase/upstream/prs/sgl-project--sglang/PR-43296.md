# [CustomAllReduceV2] Replace threshold heuristics with ordered dispatch tables

[Upstream PR](https://github.com/sgl-project/sglang/pull/43296) · state: open · merged: False

## Original PR description

## Motivation

Reviewing #42811 raised that the CustomAllReduceV2 dispatch has become hard to follow. Each new algorithm adds another positional threshold to `Heuristic`, another branch to the `if`-chain in `_pick_config`, and another clipping rule. An algorithm is disabled by setting two thresholds equal. This PR swaps that for a lookup table, with no change in behavior under default sizing, so #42811 can add `2shot_push` as one constant plus table rows.

The last two commits add a separate change, a prototype: eager pull reads inputs from the NCCL symmetric pool (`--enable-symm-mem`) in place instead of staging them, which brings the graph-mode zero-copy path to eager mode. Behavior only changes after a pool segment has been registered, so only with `--enable-symm-mem`. See the trade-off under Benchmark.

## Modifications

- Each `(arch, world_size)` lists plain `(max_bytes, ALGO)` rows for graph mode and eager mode. The first row with `nbytes <= max_bytes` wins. Past the last row, the call falls back to NCCL.
  ```python
  4: config(4, graph=((2.25 * MB, PUSH1), (128 * MB, PULL2)),
               eager=((3 * MB, PUSH1), (32 * MB, PULL2))),
  8: config(8, graph=((512 * KB, PUSH1), (8 * MB - 1, PULL2), (128 * MB, MC), (128 * MB, PULL2)), ...),
  ```
- `PUSH1 / PULL1 / PULL2 / MC` are `(AllReduceAlgo, use_multicast)` pairs. A multicast range that used to have a floor becomes a preceding `PULL2` row (`8 * MB - 1`; sizes are always multiples of 16 B).
- `MC` rows are dropped once at init when the group has no multicast, which resolves each table to the `(world_size, can_use_multicast)` case the review asked for.
- `_pick_config` is one loop. It checks each row against its workspace capacity (push or pull) instead of clipping the tables ahead of time.
- The forced-size env vars and `uncap_pull_thresholds()` add a row bounded only by the workspace: `(inf, PUSH1)` at the head, `(inf, PULL2)` at the tail.
- `use_graph` is derived in one place, `can_use_graph and not algo.is_push() and not use_multicast`, and the override path uses the same rule.
- Removed: `Heuristic`, `Range`, `_pack_heuristic`, every `clip()`, and the local pick-result `AllReduceConfig`. `eager` defaults to `graph` when the two are identical.
- A trailing `PULL2` row stays even where an earlier row covers it, for example SM107 world 2. It still sizes the pull plane, and the fused collectives borrow that plane's semaphores.

### Zero-copy eager pull for symmetric-pool inputs (prototype)

Eager pull stages every input through the pull plane: copy in, reduce, copy out. With `--enable-symm-mem`, `RowParallelLinear` and the MoE runners already allocate the all-reduce inputs from the NCCL symmetric pool, which every peer can map.
- **Registration.** `register_symmetric_segments()` peer-maps the pool's new segments through the existing VMM graph-input path (`VmmGraphInputManager`) into a device table of every rank's segment bases. It is a collective, and it runs at `SymmetricMemoryContext` exit, right after NCCL's own window registration, which already requires every rank to reach that point with the same new segments.
- **No offset symmetry assumed.** The pool does *not* place a block at the same offset on every rank: on B300 the same-size block sat at offset 1024 on rank 0 and 0 on rank 1. So each rank publishes where its input sits (`segment row << 40 | offset`, or -1 to stage) in its barrier semaphore before a release arrival, and peers resolve their pointers after the acquire. Ranks may differ in offsets and in whether they are in the pool at all. A rank in the pool reads in place, and `2shot_pull` runs in place there. A rank that isn't stages as before.
- **Same choice on every rank.** The algorithm choice and whether a call uses symmetric-pool mode depend only on collective state, never on local pool membership. Eager calls keep the eager table.
- **Unchanged.** Push, multicast, graph capture, tc-piecewise and multi-node groups keep their current paths.

## Accuracy Tests

An equivalence check (a script, not committed) loads `main`'s config module and this one and compares the old picker with the new one. It covers:
- all four config sets (SM90, SM100, SM107, and the unknown-arch default) and every world size in each;
- graph and eager mode, with and without multicast;
- sizes at every threshold ±32 B, plus the 1–256 MB edges;
- 20 sizing scenarios:
  - five `max_size` values, with and without `uncap_pull_thresholds()`;
  - push-only fused instances, and test-style explicit sizes;
  - forced pull and forced push sizes.

Results:
- **Default sizing: identical.** In total, 83,372 picks were checked.
- **Workspace sizes** (push slot, pull buffer, `num_mc_blocks`) are identical in all 20 scenarios.
- **All remaining differences** fall into two explained classes, both from the old clip-then-compare scheme and both needing non-default sizes:
  1. **A forced push size below the tuned 1shot crossover**, or a forced pull workspace larger than the push workspace (`SGLANG_FORCE_CUSTOM_ALL_REDUCE_V2_{PUSH,PULL}_SIZE_KB`, which nothing in the repo sets). The old code fell into a `1shot_pull` the tuning had turned off (equal thresholds). The table falls through to the next tuned row.
  2. **`SGLANG_CUSTOM_ALL_REDUCE_V2_MAX_SIZE_KB` set below a multicast floor** (SM90 world 6, SM100 world 8, graph mode). The old `Range.clip` shrank the multicast range to the single size equal to the workspace. That one size now takes non-multicast `2shot_pull` (8 picks).

**GPU tests.** `test_custom_all_reduce.py` passes 360/360 at world sizes 2, 4 and 8, three times on 8x H200 and three times on 8x B300. That is 180 existing cases plus 180 new `test_custom_all_reduce_symmetric` cases.
- The new cases cover three layouts: aligned, skewed (each rank's input at a different offset in its segment) and mixed (rank 0 staged, the others in the pool).
- Each case checks exact equality against NCCL and that `2shot_pull` ran in place exactly on the ranks in the pool.
- The skewed layout is what broke the first version of this change on B300.

A torch profiler run confirms that an in-pool eager `2shot_pull` launches only the reduce kernel, while a staged one also launches two `memcpy_kernel`s.

## Benchmark

**Throughput.** Forced `2shot_pull` (non-multicast), bf16, µs per call over 50 back-to-back calls, median of 5:

| size | B300 TP4 staged / symm / graph | B300 TP8 staged / symm / graph | H200 TP4 staged / symm / graph |
|---:|---:|---:|---:|
| 8 MB | 45.8 / 39.3 / 28.7 | 50.8 / 46.5 / 33.9 | 59.0 / 48.1 / 42.4 |
| 16 MB | 68.5 / 57.5 / 46.1 | 78.9 / 68.6 / 61.0 | 106.8 / 88.5 / 82.6 |
| 32 MB | 113.3 / 94.8 / 82.7 | 132.1 / 111.9 / 106.0 | 203.4 / 166.4 / 160.3 |
| 64 MB | 211.5 / 170.2 / 159.1 | 243.0 / 201.5 / 196.2 | 392.4 / 323.7 / 317.1 |

- At 8 MB and up, symmetric eager is 8–20% faster than staged: the two copies and two launches are gone.
- It still trails graph mode by a fixed 6–11 µs per call. That gap is the location exchange. A box-only variant with the first barrier relaxed recovers ~4 µs on B300 TP4, which puts the cost of the release/acquire at about 4 µs. The rest is the remote location loads and resolving pointers after the barrier.

**Latency.** `bench_custom_all_reduce.py` adds a `jit-eager-symm` provider. Its eager loop flushes L2 and runs a GPU barrier before every call, so it measures an isolated call. On B300 with the tuned table:
- **TP4:** symmetric eager is about 6 µs slower than staged at 4–32 MB (for example 39.9 vs 33.8 µs at 8 MB). Staged's copies overlap the wait for the slowest rank there, while the exchange sits on the critical path.
- **TP8:** the eager table uses staged multicast, so the two measure the same.

**Next step.** Remove the release/acquire and remote loads. Each sender would write its location straight into a local per-sender slot on the receiver, marker style (like `1shot_push`), so the location arrives with the barrier instead of after it. Until then, this is a throughput win and an isolated-call latency loss.
