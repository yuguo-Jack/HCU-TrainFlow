# [Feat] PD: Add opt-in first-chunk decode KV allocation

[Upstream PR](https://github.com/sgl-project/sglang/pull/44891) · state: closed · merged: False

## Original PR description

## Motivation

Decode-side `early` allocation can reserve KV capacity while prefill is still computing. `prefill_complete` avoids that reservation but delays KV transfer until prefill finishes.

Add an opt-in `first_chunk` policy: **the first accepted prefill chunk triggers one full-request destination reservation**, allowing KV transfer to overlap the remaining prefill. This reduces the time that decode KV is reserved before it can receive data.

Enable on **both P and D**:

```bash
--disaggregation-decode-allocation-policy first_chunk
```

The default remains `early`. This changes allocation timing; the configured physical KV pool is unchanged.

## Modifications

- Reuse the deferred bootstrap from #40703 and the existing destination-pointer handshake.
- Publish first-chunk readiness after result acceptance and abort/yield checks. Preserve final transfer, generation-readiness and cleanup barriers.
- Support Mamba auxiliary state through the final-chunk-only convolution/recurrent-state handoff.
- Validate matching P/D policies and retain the Mooncake, Python-bootstrap and attention TP1/CP1/PP1 restrictions. Add lifecycle coverage and documentation.

## Accuracy Tests

- **149 CPU tests passed**; 13 CUDA cases were skipped with GPUs hidden. A separate **18-test CUDA checksum suite passed**, including those cases.
- Boundary, reuse and concurrency probes matched output token sequences. Checksum-enabled cancellation/recovery checks passed, with allocator/request gauges returning to zero.
- **GSM8K: 1,319 questions per configuration**, fixed 8-shot prompts, greedy decoding, thinking disabled, normal EOS and a 1,024-token output limit:

| Configuration | Correct | Accuracy |
|---|---:|---:|
| Default early | 1275 | 96.66% |
| Matched early | 1273 | 96.51% |
| First chunk | 1278 | 96.89% |
| Prefill complete | 1275 | 96.66% |
| Monolithic | 1275 | 96.66% |

The paired first-chunk versus matched-early difference is not statistically significant (McNemar p=0.227).

Ruff, isort and `git diff --check` passed. High-pressure Mooncake TCP transport reliability remains under investigation; upstream multi-GPU CI remains pending.

## Speed Tests and Profiling

A targeted benchmark measures the intended use case: **constrained decode KV capacity with long requests arriving ahead of short requests**. These results describe this workload rather than a general speedup across workloads.

**Setup:** Qwen3.8-27B BF16, H100 80GB, TP1, same-host Mooncake TCP, prefill chunk size 2,048, context limit 16,384, prefix caching and speculation disabled. P token capacity/request limit: 131,072/16; D: 24,576/32.

Each trace contains 24 requests: four groups of one 8,192-token prompt followed by five 512-token prompts, arriving 5 ms apart, with 128 output tokens per request. Both policies use **P optimistic-prefill attempts=1** to isolate allocation timing; default `early` otherwise resolves to 0.

| Policy | Output throughput (tokens/s) | TTFT p95 (s) | TPOT p95 (ms) |
|---|---:|---:|---:|
| Matched early | 257.18 | 9.13 | 21.20 |
| First chunk | **263.61** | **8.90** | 21.16 |

**Paired throughput improvement: +2.5%**, with an exploratory 95% interval of **+1.0% to +4.0%** across three seeds. Each seed runs both forward and reverse policy orders on the same P/D pair; repeats are averaged within seed before computing paired effects. Latency values are means of per-run p95 values.

Four P/D pairs ran on eight H100 GPUs with disjoint CPU cores and ports; pairs rotated across seeds. These finite synthetic traces measure same-host TCP performance, not maximum sustainable QPS or cross-host RDMA performance.

Measured serving revision: `528b01e5f2b437ceef45b5f867de0c3cfd974096`; the PR head differs only in documentation. Runtime: Torch 2.14.1+cu130, sglang-kernel 0.4.10, Transformers 5.19.0, FlashInfer 0.7.2 and Mooncake transfer engine 0.3.12.post1.
