# [Fix] spec-v2: pass pp_proxy_tensors through FrozenKVMTP/UNO workers, declare interface on BaseSpecWorker

[Upstream PR](https://github.com/sgl-project/sglang/pull/44490) · state: open · merged: False

## Original PR description

## Motivation

Fixes #40155.

The scheduler's non-overlap speculative path always calls
`self.model_worker.forward_batch_generation(batch, pp_proxy_tensors=pp_proxy_tensors)`
(`srt/managers/scheduler.py`). Two of the seven spec-v2 workers —
`FrozenKVMTPWorkerV2` and `UnoWorkerV2` — never accepted that keyword, so any
model routed through them died on the first speculative step with
`TypeError: ... got an unexpected keyword argument 'pp_proxy_tensors'`.
(DSpark and multi-layer EAGLE were already aligned on `main`; the claimed PR
#44211 was closed unmerged, so nothing here duplicates in-flight work.)

Root cause noted in the issue: `BaseSpecWorker` never declared
`forward_batch_generation`, so each worker evolved its own signature and two
silently fell behind.

## Modifications

- `srt/speculative/frozen_kv_mtp_worker_v2.py`
  - `forward_batch_generation` now takes `pp_proxy_tensors=None`.
  - Passes it through to the target worker prefill call
    (`capture_hidden_mode=CaptureHiddenMode.FULL`) and to `self.verify(...)`
    (inherited from `EAGLEWorkerV2`, which already accepts it) so PP proxy
    tensors reach the target on both the extend and decode paths.
- `srt/speculative/uno_worker_v2.py`
  - `forward_batch_generation` now takes `pp_proxy_tensors=None` and threads
    it through `_forward_prefill` / `_forward_decode` /
    `_forward_decode_tree` / `_run_draft_block` / `_run_target_block` down to
    the two `self.target_worker.forward_batch_generation(...)` call sites
    (prefill, and the `batch=None, is_verify=True` verify path).
- `srt/speculative/base_spec_worker.py`
  - Declares `@abstractmethod forward_batch_generation(batch, on_publish=None,
    grammar_barrier=None, pp_proxy_tensors=None)` on `BaseSpecWorker`, so a
    future worker that forgets the interface fails at instantiation instead of
    at the first request. All six concrete workers (plus
    `StandaloneWorkerV2` via `EAGLEWorkerV2`) already override it, so no
    existing instantiation breaks.

## Tests

No GPU and no `torch` on this machine, so this could not be verified with a
runtime run; the fix is a pure-Python signature/pass-through change. What was
verified here:

- `ruff check --select F401,F821,F823,UP037`, `ruff format --check`,
  `python3 -m py_compile`, and `git diff --check` all pass on the three
  touched files.
- An AST audit of all seven spec-v2 workers confirms every
  `forward_batch_generation` now accepts `pp_proxy_tensors` as a keyword, so
  the scheduler's `forward_batch_generation(batch, pp_proxy_tensors=...)`
  call binds on all of them.
- The pass-through targets were checked against their real signatures:
  `TpModelWorker.forward_batch_generation` and `EAGLEWorkerV2.verify` both
  accept `pp_proxy_tensors`.
- Grep of `test/registered` shows no existing test asserting these
  signatures or instantiating the affected workers in a way the new trailing
  optional parameter would break (`test_weight_update_runners.py` builds the
  workers via `object.__new__`, which bypasses the ABC check anyway).

A maintainer-run CI pass (especially any spec-v2 / PP-adjacent coverage)
would be appreciated to confirm runtime behavior.
