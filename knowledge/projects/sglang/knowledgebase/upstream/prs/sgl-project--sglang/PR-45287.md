# [Perf] DSv4.1: cache image preprocessing across requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/45287) · state: open · merged: False

## Original PR description

[Perf] DSv4.1: Cache image preprocessing across requests

## Motivation

Multi-turn agents resend every earlier image on each turn, and the DeepSeek-V4.1 processor decodes and patchifies all of them again in the tokenizer process. The output only depends on the image bytes and the patchify backend, so it can be cached. Kimi-K3, Qwen-VL and Muse Spark already do this through `MediaArtifactCacheMixin`. This PR wires DeepSeek-V4.1 into it.

## Modifications

- `DeepseekV41ImageProcessor` now uses `MediaArtifactCacheMixin`, following the Kimi-K3 and Muse adapters.
  - `DeepseekV41ImagePreprocessArtifact` stores the CPU patchify output: `feature`, `n_vit_h`, `n_vit_w`, `token_count`.
  - `prepare_artifact_batch` patchifies cache misses. `_compose_request` places artifacts into the current prompt's token IDs.
  - The feature hash comes from the artifact key (image bytes plus processor fingerprint, which includes the patchify backend), as in Muse. A miss no longer hashes the patch tensor.
  - Patchify runs on `io_executor`, as in Muse, so it stays off the tokenizer event loop when no processor worker pool is configured.
- The cache is on by default at 256 MiB (`auto_mm_preprocess_cache_size_mb`), matching Kimi-K3 and Muse. `--mm-preprocess-cache-size-mb` resizes it and `0` turns it off.
- The GPU preprocessing backend, preprocessed inputs and cache-off requests keep the existing path. It is unchanged except for sharing the placeholder count check.
- New CPU unit tests in `test/registered/unit/multimodal/test_deepseek_v41_processor.py`:
  - Cached and uncached paths produce the same `input_ids`, offsets, `n_vit_h/w` and patches for two images of different sizes.
  - A repeated image skips patchify and gets placed per prompt, with the same hash and feature and different offsets.

## Accuracy Tests

MMMU-Pro with sgl-eval 0.1.3 and the DeepSeek-V4.1 CI settings from `dsv41_flash_common.py`: 200 examples, 64 threads, `--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash` (temperature 1.0, top_p 0.95, thinking on, reasoning effort high), `max_tokens=32768`. Pass 2 reruns the same 200 examples on the same server, so every image hits the cache. Servers and hardware match the speed tests below.

| Server | MMMU-Pro (200) | Truncated | Errors |
|---|---:|---:|---:|
| Before | 0.800 | 2.0% | 0 |
| This PR, 4096 MiB, pass 1 (cold) | 0.780 | 3.5% | 0 |
| This PR, 4096 MiB, pass 2 (all hits) | 0.795 | 2.5% | 0 |

All runs clear the CI threshold of 0.75. Standard error at temperature 1.0 and n=200 is about 2.8 points, so the gaps are sampling noise.

## Speed Tests and Profiling

Setup:

- 4x NVIDIA B300, TP4 + EP4
- `deepseek-ai/DeepSeek-V4.1-Flash`, revision `fb2764a5cf321eaa5070ca8f9e892818f477c16d`
- Cookbook B300 High-Throughput flags: `--tp 4 --ep-size 4 --max-running-requests 256 --reasoning-parser auto --tool-call-parser auto`
- Image `lmsysorg/sglang:dev-dsv41` (torch 2.13.0+cu130, FlashInfer 0.6.18). "Before" is its stock processor. "This PR" applies this diff to the same image. The image predates the `patchify_image`/`preprocess_backend` renames on main, so the diff was applied under the old names.
- PIL patchify on both sides. The image does not bundle the Rust image extension.
- Median of 3 runs per cell. Each run uses new images, so turn 0 always misses.

**Multi-turn, images resent every turn.** Same workload as Kimi-K3 in #34411: 32 conversations x 8 turns, concurrency 32, 4 seeded random JPEGs per conversation (512^2 to 2048^2) in the first user message and resent with the full history each turn, 16 output tokens with `ignore_eos`.

| Metric | Before | Cache 256 MiB (default) | Cache 4096 MiB |
|---|---:|---:|---:|
| Output tok/s | 97.90 | 117.38 (+19.9%) | 125.35 (+28.0%) |
| Requests/s | 6.12 | 7.34 (+19.9%) | 7.83 (+27.9%) |
| Median TTFT, turns 1-7 | 3111 ms | 2300 ms (-26.1%) | 2090 ms (-32.8%) |
| P90 TTFT, turns 1-7 | 4128 ms | 3212 ms (-22.2%) | 2909 ms (-29.5%) |
| Median E2E, turns 1-7 | 4285 ms | 3127 ms (-27.0%) | 2909 ms (-32.1%) |
| Median TTFT, turn 0 (miss) | 9351 ms | 8297 ms | 8390 ms |

Cached patches for a large image are about 20 MB of bf16. The 256 MiB default fits roughly a dozen images per tokenizer worker, so this workload (128 live images) only partially hits. Size the cache to your image working set if you resend many images.

**Unique images, no reuse.** Checks the cold path: 128 single-turn requests with 4 new images each, concurrency 32.
