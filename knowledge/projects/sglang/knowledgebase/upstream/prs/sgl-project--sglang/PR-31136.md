## Motivation

This PR adds a new HiCache host memory layout: `page_blob_direct`. This is a preparatory PR for the Tensorcast HiCache backend integration https://github.com/sgl-project/sglang/pull/27265. The Tensorcast backend wants a page-major host layout where each logical cache page is represented as one contiguous page blob.  As requested by @hzh0425, splitting this layout support into a separate PR keeps the Tensorcast backend PR focused on the backend itself.

The main advantages of `page_blob_direct` layout are stated in https://github.com/sgl-project/sglang/pull/27265 ("page_blob_direct layout" part). Besides, it becomes a unified HiCache host-layout option across MHA, MLA, and Mamba models, while preserving each cache type's native physical representation.

## Modifications

`page_blob_direct` essentially swaps `(page_num, 2)` positions in `page_first_direct` layout

For MHA KV cache, `page_blob_direct` stores host KV cache as:

  ```text
  kv_buffer shape:

    [page_num, 2, layer_num, page_size, head_num, head_dim]

  Conceptually, each logical page is laid out as one contiguous blob:

  page 0
  +--------------------------------------------------------------+
  | K for all layers/tokens/heads | V for all layers/tokens/heads |
  +--------------------------------------------------------------+

  page 1
  +--------------------------------------------------------------+
  | K for all layers/tokens/heads | V for all layers/tokens/heads |
  +--------------------------------------------------------------+

  page 2
  +--------------------------------------------------------------+
  | K for all layers/tokens/heads | V for all layers/tokens/heads |
  +--------------------------------------------------------------+

  In pointer form:

  page_blob(p) = base + p * (2 * page_bytes)

  K(p) = page_blob(p)
  V(p) = page_blob(p) + page_bytes
```
For MLA or Mamba cache, `page_blob_direct` is interpreted as the closest page-major direct layout for each cache type, one blob per page.

- zhou-yuhan · comment · 2026-07-22T07:13:11Z · [source](https://github.com/sgl-project/sglang/pull/31136#issuecomment-5042979619)

> I understand there's no fundamental difference between `page_blob_direct ` and `page_first_direct`. Where are the optimization points? Or could we improve `page_first_direct` instead of introducing another layout? @zhou-yuhan

Yes, there's no "fundamental" difference, but `page_blob_direct` brings three advantages (copied from https://github.com/sgl-project/sglang/pull/27265, since this layout is introduced for TensorcastStore backend but can generally benefit other backends)
- In architectural design: decouple the internal structure of each KV page from the distributed storage/transfer backend. Backends do not and should not comprehend the internal structure of a KV page corresponding to tokens (especially with more incoming attention variants) — they only manage storage and transfer. By keeping that structure inside HiCache, it becomes much easier to support more attention variants (e.g. MLA, Mamba2) without changing the storage-side protocol.
- Performance: cut the control-plane overhead of batch_[exists|set|get] calls roughly in half for MHA. The backend side gets one slot/region offset per page instead of one per K-shard plus one per V-shard, which directly halves the scatter-gather descriptors and per-page bookkeeping in the RDMA path. The benchmarked performance gain is shown in https://github.com/sgl-project/sglang/issues/26702

The check `stride % page_size_bytes == 0` is redundant because `stride` is defined as `2 * page_bytes`. If `page_bytes % page_size_bytes == 0` is true, then `stride % page_size_bytes == 0` is mathematically guaranteed to be true. We can simplify this check.

```python
        if self.layout == "page_blob_direct":

                self.kv_buffer.data_ptr() % page_size_bytes == 0
                and page_bytes % page_size_bytes == 0
            )
```
