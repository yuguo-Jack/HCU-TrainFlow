# [Refactor] kernels: Add the plugin kernel backend and split plugin contracts from their srt integration

[Upstream PR](https://github.com/sgl-project/sglang/pull/45389) · state: closed · merged: True

## Original PR description

## Motivation

Some kernels are specialized for one model, configuration and platform, and replace a model's whole step. They come from external libraries that load as SGLang plugins:

- the NVIDIA megakernel, from [sgl-nvidia-mega](https://github.com/sgl-project/sgl-nvidia-mega)
- the AMD monokernels, from [sgl-amd-mono](https://github.com/sgl-project/sgl-amd-mono)

Today these plugins serve small-batch decode and verify steps. Nothing ties them to low latency or to "mega" fusion; prefill or high-throughput specializations would plug in the same way.

SGLang's side of each integration lived in `srt/megakernels` and `srt/monokernels`. This PR splits that code at the kernel/runtime boundary:

- what a plugin implements and registers moves to `kernels/plugin_kernels/<hardware>/`, recorded by a new `KernelBackend.PLUGIN` (as with `kda_kernels/` and `cake_kernels/`)
- SGLang's serving integration stays in `srt/`, as `srt/kernel_plugins/<hardware>/`

The kernels themselves stay in their libraries.

## Modifications

```
python/sglang/kernels/plugin_kernels/   # the contract a plugin implements; imports nothing from srt
  nvidia/spec.py                        #   registration, API version, requirements, capabilities,
  amd/spec.py                           #   widths, build/forward contract
                                        #   (<hardware>/<model>/ for thin kernel wrappers later)
python/sglang/srt/kernel_plugins/       # SGLang's integration, one binding.py per hardware
  nvidia/binding.py                     #   startup checks on the resolved config, build, TP agreement,
  amd/binding.py                        #   CUDA graph coverage, forward dispatch with fallback,
                                        #   weight observation (AMD), the runtime state handed to a plugin
```

- **Move.** The code moves unchanged; only imports are combined.
  - `srt/{megakernels,monokernels}/spec.py` → `kernels/plugin_kernels/{nvidia,amd}/spec.py`.
  - Each hardware's `guards.py` + `runtime.py` (and, on NVIDIA, `binding.py`) → `srt/kernel_plugins/<hardware>/binding.py`.
  - Unit tests → `test/registered/unit/kernel_plugins/{nvidia,amd}/`. They now patch the one `binding` module.
- **No aliases.** `sglang.srt.megakernels` and `sglang.srt.monokernels` are removed.
  - The plugins import the new locations first and fall back to the old ones for earlier SGLang: sgl-project/sgl-nvidia-mega#21 and sgl-project/sgl-amd-mono#25, both merged.
  - The pins move to those merge commits:
    - `SGL_NVIDIA_MEGA_COMMIT` becomes `6fd7ac3` in both CUDA Dockerfiles. Main pins `3333e4c` (#46030), an ancestor of `6fd7ac3`.
    - The `sgl-amd-mono` pin in `pyproject_other.toml` becomes `05e0bb0`.
- **`KernelBackend.PLUGIN`.** Adds the enum value and a `forward_plugin` hook on `BaseFusedOp`, placed after KDA/CAKE in `DEFAULT_PRIORITY`. The namespace test pairs `plugin_kernels/` with this backend.
- **`--monokernel-backend amd` → `--enable-amd-monokernel`.** The flag becomes a boolean next to `--enable-nvidia-megakernel`.
  - `--monokernel-backend amd` stays as a deprecated spelling: it warns and sets the new flag. Any other value is rejected.
  - The field keeps its slot in `POSITIONAL_FIELD_ORDER`.
  - Both spellings also work in `--config` YAML files. Previously the merger accepted only `store`/`store_true` actions, which rejected the deprecated alias and, through the shared dest, the new key too.
    - The merger now passes single-value actions as `--flag value`.
    - A key stays usable when a supported flag also reads it.
    - A regression test covers `monokernel-backend: amd`, `enable-amd-monokernel: true` / `false`, and both CLI spellings. Before the fix, the three YAML cases raise `ValueError`.
  - The resolution hook is renamed `handle_amd_monokernel`.
  - Error messages, the server-args doc, the DeepSeek-V4.1 cookbook and the ROCm Dockerfile comment are updated.
- **Docs.** `kernels/README.md`, `plugin_kernels/README.md` and the kernel-organization skill describe the split.

No runtime behavior changes: the default path is untouched, and the megakernel and monokernel code is the same code at new paths.

**Not covered: the MSA plugin.** The MiniMax-M3.1 cookbook (#45924) serves the MSA plugin with `--monokernel-backend msa`. On this PR that value is rejected, and the plugin's `sglang.srt.monokernels` imports fail. That plugin is moving off the monokernel name separately.

- Oasis-Git · COMMENTED · 2026-10-22T00:17:51Z · [source](https://github.com/sgl-project/sglang/pull/45389#pullrequestreview-5607792043)

[Codex]: The plugin naming and backend classification make sense to me, but I would suggest separating the plugin contract from the serving-runtime integration before moving the whole interface into `kernels/`.

A useful boundary would be:

- `kernels/plugin_kernels/`: spec registration, API versions, capability/shape declarations, build/forward contracts, and any thin kernel wrappers. The actual implementations can remain in `sgl-nvidia-mega` and `sgl-amd-mono`.
- `srt/`: interpreting server configuration, observing checkpoint loading and retaining weight copies, coordinating TP ranks, deriving CUDA graph capture coverage, installing model-forward dispatch/fallback, and enforcing weight-update restrictions.

In particular, most of the moved `runtime.py` code manages the model's execution and resource lifecycle. Keeping that in `srt/` would avoid making whole-step plugins an exception to the kernel/runtime dependency boundary. This does not require breaking up a megakernel or changing its whole-step execution: the runtime adapter can still build the plugin once and route each supported step to it.

`guards.py` and `binding.py` also cross this boundary: capability checks and the interface presented to a plugin can belong with the contract, while reading/resolving ServerArgs and assembling bindings from the model runner, KV cache, and process groups belong in the runtime adapter. Merely moving `spec.py` would not remove existing model/config coupling; narrowing those inputs can be incremental rather than requiring a new generic abstraction in this PR.

For this refactor, could we unify the contracts and backend naming under `kernels/`, while retaining the model integration and lifecycle hooks under `srt/`? That would let future changes to model loading or CUDA graph planning stay in the serving layer without making the kernel interface responsible for those internals. Also, the current whole-step integrations still install model-forward hooks rather than dispatching through `BaseFusedOp.forward_plugin`, so this separation would make the two integration paths clearer.
