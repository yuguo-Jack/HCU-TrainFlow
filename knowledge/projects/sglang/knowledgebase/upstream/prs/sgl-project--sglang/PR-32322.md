# fix(gateway): reconcile k8s service discovery with periodic full LIST

[Upstream PR](https://github.com/sgl-project/sglang/pull/32322) · state: closed · merged: False

## Original PR description

## Motivation

Kubernetes service discovery cannot converge to the true pod set when the watch stream is unreliable, which is the normal operating condition on some managed providers: long-lived watches are dropped every few minutes and sometimes go **silently stale**, yielding neither events nor errors.

Three coupled defects in `service_discovery.rs`:

1. **Delete events are structurally lost.** The watch consumes `watcher(...).applied_objects()`, which yields only `Apply`/`InitApply` and discards `Delete`. A removal is caught only opportunistically, via an `Apply` carrying a `deletion_timestamp` during graceful termination. A pod that disappears while the watch is down, or is force-deleted, stays a registered worker forever — nothing reconciles against a fresh LIST, and the registry health checker only marks workers unhealthy, never deregisters.
2. **A silently stale watch disables the restart path.** When the stream neither yields nor errors (observed: 20+ minutes, zero watcher-error lines), `try_for_each` never returns, so the outer loop — the only place a fresh `watcher()` re-LIST could happen — never runs.
3. **The error-restart path stalls 60–360 s per reconnect**, sleeping `retry_delay` *plus* an unconditional `check_interval` every iteration.

## Change

`reconcile_from_list()`: a paged full LIST that feeds every selector-matching, non-terminating pod through the existing `handle_pod_event`, and removes every tracked pod no longer present via `handle_pod_deletion`. A pod with a `deletion_timestamp` counts as absent, mirroring the watch path watch-independently, so a draining pod stops receiving traffic even when the watch is dead. Any page failing aborts the pass before the removal phase, so a partial view can never drive removals.

Driven from a periodic timer (`--service-discovery-resync-secs`, default 30) and at the top of each watch (re)start; the redundant unconditional sleep is dropped so reconnects are prompt.

The tracked set is keyed by `pod.metadata.uid`, not by name. Under `Api::all` — the default, and what `gateway-cluster-scoped.yaml` ships — names are unique only per namespace, so a dead `ns-a/engine-0` stays tracked while `ns-b/engine-0` lives; and a pod replaced under one name is tracked alongside its predecessor instead of evicting it. The UID is stable across the status/readiness flips that make full-struct equality unusable, so it also lets `handle_pod_deletion` resolve by identity rather than exact-struct `HashSet::remove` (the fragility noted in #26842).

Two cases handled explicitly:

- A departed pod whose worker URL is claimed by a live healthy pod in the same LIST is a same-URL replacement (hostNetwork gives a pod its node's IP), so it is forgotten rather than deregistered.
- Membership in `tracked_pods` records that an AddWorker was *submitted*, not that it succeeded, and the add path short-circuits on tracked pods forever. A listed healthy pod that is tracked but absent from the registry is therefore forgotten so it is submitted again — via `find_workers_by_url`, since dp-aware workers register as `<url>@<rank>`, and gated on a per-URL in-flight check because `submit()` does not dedup.

## Relationship to #30270 and #26842

Both diagnose the same root causes and fix the **event handling**; this is complementary, adding the watch-independent periodic LIST that neither covers. When the watch is dead or silently stale — our dominant failure mode — better event handling has no events to handle.

Split out of this PR, independently reviewable: **#38523** (worker registry re-registration) and **#38524** (add/remove handoff race).

- Juhyun-Kim-Memphis · comment · 2026-08-31T11:47:09Z · [source](https://github.com/sgl-project/sglang/pull/32322#issuecomment-5477845993)

Cross-reference: I opened #37249, which removes one of the concrete causes of the state `forget_lost_registration` in this PR exists to recover.

`sgl-model-gateway` pins `wfaas = "=1.0.0"`, and in wfaas 1.0.0/1.0.1 a step that fails with `FailureAction::ContinueNextStep` is recorded in the tracker as `skipped` but signals `StepResult::Failure` to the scheduler. The scheduler enqueues a step's dependents only on `Success | Skip`, so nothing downstream ever runs and the workflow ends in the deadlock branch as `Failed`. In `create_local_worker_workflow()` that is `discover_metadata`, with `discover_dp_info` → `create_worker` → `register_workers` hanging off it — so one failing optional metadata fetch means the worker is never registered, while `handle_pod_event` has already inserted the pod into `tracked_pods` and only rolls that back when `submit()` itself fails.

That is exactly the class this PR's doc comment describes:

> Membership in `tracked_pods` records that an AddWorker job was SUBMITTED, not that it succeeded […] A job that fails after that […] only records a failed `JobStatus`, and nothing untracks the pod.

The causes named there (`detect_connection_mode` exhausting `worker_startup_timeout_secs`, a failing DP discovery, a workflow that never starts) are all comparatively rare. The wfaas one is not: a transient hiccup on a single optional HTTP call to a pod that has just started is enough to trigger it, so in practice it is a frequent producer of tracked-but-unregistered pods rather than an exotic one.

The two changes are complementary and independent, and can land in either order:

- **This PR without #37249** — the failure still happens on every occurrence; the reconcile recovers the pod, but only on a later resync tick.
- **#37249 without this PR** — that particular cause is gone, but an `AddWorker` failing for any other reason, and a pod whose event never arrives because the watch is dead or silently stale, are still unrecovered.

If it would be useful to reviewers, I am happy to extend `forget_lost_registration`'s doc comment here to name the wfaas case alongside the others once #37249's disposition is clear.

This dedup assumption holds only if membership in `tracked_pods` implies the worker actually reached the registry, and there's a path where it doesn't.

`handle_pod_event` inserts into `tracked_pods` and rolls back only when `submit()` itself fails (the `tracker.remove(pod_info)` at ~L613, i.e. channel closed/full). If the **job** fails afterwards -- `wait_for_completion` timing out (`worker_startup_timeout_secs` defaults to 1800s, `config/types.rs:514`), a failing activation step, a workflow-start error -- `record_job_completion` writes `JobStatus::failed` (`job_queue.rs:878`) and nothing else happens. `tracked_pods` is private to this file, so no other code can untrack it.

From then on this call is a permanent no-op: the pod is in `tracked_pods`, so `tracker.contains(pod_info)` short-circuits at L520 and the reconcile never retries. The pod stays absent from the registry while the reconcile believes it is registered -- the same unrecoverable state this PR closes on the delete side, still open on the add side. (Pre-existing, but this pass is the natural place to repair it, and the "authoritative resync" framing invites the assumption that it already does.)

Since the pass is already paying for a full LIST, it seems worth reconciling against the registry rather than only the shadow set: treat "tracked but absent from `worker_registry`" as missing and resubmit. Use `find_workers_by_url(registry, url, dp_aware)` rather than `get_by_url` -- in dp-aware mode workers are registered as `<url>@<rank>`, so an exact-URL lookup never matches (same reason the new handoff guard reaches for it in `job_queue.rs`).
