# [Fix] [AMD] scheduler: Keep the scheduler's GPU work on the forward stream under monokernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47491) · state: open · merged: False

## Original PR description

## Motivation

An AMD monokernel launch (`--enable-amd-monokernel`, sgl-amd-mono) keeps all of its workgroups resident and waiting on each other through device-memory flags. The overlap scheduler issues small kernels on its own `schedule_stream`, and the result readback runs on `copy_stream`. If one of those kernels takes a CU while a monokernel launch is being dispatched, some of the launch's workgroups cannot become resident. The resident ones then wait until the plugin's guard deadline (60 s) stops every rank, and the log shows a GPU memory fault at address `(nil)`.

On Muse Spark TP8 with the monokernels on 8x MI355X, this hit about once every 15-60 min at concurrency 1 and 4 on the full AgentX trace set, always in the DFlash2 draft's first launch. A standalone repro replays that launch's CUDA graph and runs one small kernel every 100 ms on a second stream: 4 of 8 GPUs hang within 7 min. The same replays without the second stream ran 200M launches clean.

## Modifications

- `python/sglang/srt/managers/scheduler.py`: with `--enable-amd-monokernel`, `schedule_stream` and `copy_stream` are the forward stream. The host side still overlaps; only the scheduler's GPU work queues behind the forward. Nothing changes without the flag.

## Accuracy

NA (no numerics change).

## Benchmark

Muse Spark Open TP8 + monokernels, 8x MI355X, InferenceX AgentX full trace set, 3600 s: concurrency 1 and 4 now run clean with no hang, at the same speed as before the change. The InferenceX sweep in [InferenceX #4606](https://github.com/SemiAnalysisAI/InferenceX/pull/4606) (`lmsysorg/sglang-rocm:muse-spark-open-1027`) carries this change.
