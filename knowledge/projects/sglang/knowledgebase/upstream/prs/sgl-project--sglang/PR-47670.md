# [Fix] mem_cache: Keep K/V in separate allocations under torch.compile

[Upstream PR](https://github.com/sgl-project/sglang/pull/47670) · state: closed · merged: True

## Original PR description

> (auto generated by Claude)

## Problem

Since #32272 (1a120754e0), `MHATokenToKVPool._create_buffers_normal` allocates each layer's K and V on CUDA as the two halves of one tensor (`k_buffer = fused[0, :rows]`, `v_buffer = fused[1, :rows]`). With `--enable-torch-compile`, decode throughput drops by 12-23x: Qwen/Qwen1.5-MoE-A2.7B bs=1 goes from 385 to 16.6 tok/s on B200, and to 22.8 tok/s on H100 in CI.

## Root cause

The KV store (`store_cache`, a custom op registered with `mutates_args=["k_cache", "v_cache"]`) is traced into the compiled graph. Its two mutated inputs are now views of the same allocation, so AOTAutograd functionalizes the mutation through a synthetic base: every layer, on every decode step, clones the layer's whole KV allocation and copies it back. A B200 profile shows two extra inductor kernels per layer, `triton_poi_fused_as_strided_clone_0` (numel 2,794,110,976, ~1.6 ms) and `triton_poi_fused_as_strided_copy__1` (~0.8 ms). Over 24 layers that is ~58 ms/step, which matches 16.6 tok/s. On H100 the pool is 1.6 GB per layer, giving ~44 ms/step and 22.8 tok/s.

## Why CI mostly did not catch it

The inductor / AOTAutograd cache key covers the traced graph and the input shapes, strides and dtypes, but not whether two inputs alias each other. #32272 does not change the traced graph, so on runners whose `~/.cache/sglang/inductor` was populated before 10-27 the old non-aliased artifact is reused and the test passes. Only cold-cache runs compile the slow graph. That is why `test/registered/moe/test_torch_compile_moe.py::test_throughput` fails intermittently with `22.8 not greater than or equal to 285`: 3 of ~130 `base-b-test-1-gpu-large` jobs between 10-25 and 10-31, with `h100-novita-host3-gpu-7` hitting it repeatedly (e.g. the scheduled run at 05fb1c98ad). Users who compile without a pre-10-27 cache always get the slow graph.

## Reproduction (1x B200, cold cache)

Server: `--model Qwen/Qwen1.5-MoE-A2.7B --enable-torch-compile --torch-compile-max-bs 4` (the server args of `test_torch_compile_moe.py`), with a fresh `SGLANG_CACHE_DIR` per launch; measure bs=1 decode of 256 tokens with the same request as `test_throughput`.

| commit | inductor cache | decode tok/s |
|---|---|---|
| 8353f86f0b (parent of #32272) | cold | 385 |
| 1a120754e0 (#32272) | cold | 16.6 |
| 05fb1c98ad (main, 10-30) | cold | 16.6 |
| 1a120754e0 / 05fb1c98ad | warm, populated by 8353f86f0b | 385 |
| 05fb1c98ad + this PR | cold | 384.7 |
| 05fb1c98ad, no torch.compile | n/a | 475 |

The flashinfer and triton attention backends show the same 16.5 tok/s, so the slowdown is not specific to one backend.

## Fix

When `enable_torch_compile` is set, keep K and V in separate allocations, as ROCm already does. The trtllm fmha_v2 prefill path from #32272 then takes its existing fallback, which copies the batch's KV pages and logs a one-time warning. So only that prefill path is slower, and only under torch.compile. A fuller fix would pass the fused base plus an offset to `store_cache`, so the op never mutates two aliased views; that changes the kernel interface, so it is left as a follow-up for #32272's owners.

## Validation

- Cold-cache B200 numbers above.
- CI: `/rerun-test` of `test_torch_compile_moe.py`, `test_mha_pool_fused_kv_layout.py` and `test_trtllm_mha.py`. A warm runner cannot reproduce the bug, so the cold-cache table is the evidence for the fix.
