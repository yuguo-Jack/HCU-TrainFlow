# [Feat] [NVIDIA] attention: add SM100 Q8KV8 sparse MLA kernel as the q8kv8_sm100 DSA backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/47905) · state: open · merged: False

## Original PR description

## Motivation

The goal of this PR is to add the SM100 version of the Q8KV8 sparse MLA kernel (`sparse_mla_q8kv8_prefill_sm90`) and to give the `trtllm` backend a readable FP8 x FP8 sparse MLA kernel. Without losing accuracy, it is faster than trtllm-gen in prefill and in most decode cases.

Speed on B200 (tables under Speed Tests):

- Against FlashInfer 0.7.2 trtllm-gen: chunked prefill is 1.38-1.51x faster for N = 4k to 256k (1400-1900 TFLOPS); decode is 1.17-1.74x faster at s_q = 16-256 and on par at s_q = 1.
- Against FlashMLA: 1.6-3.8x faster than BF16 `flash_mla_sparse_fwd` and 1.6-3.5x faster than `flashmla_kv`.

On B200, DSA models (DeepSeek-V3.2, GLM-5) served with `--kv-cache-dtype fp8_e4m3 --dsa-prefill-backend trtllm --dsa-decode-backend trtllm` run every sparse MLA call (prefill, MTP verify, decode) through `flashinfer.decode.trtllm_batch_decode_with_kv_cache_mla(..., sparse_mla_top_k=topk)`. On SM100 that is the only FP8 x FP8 sparse MLA kernel available, and it ships as a prebuilt cubin, so it cannot be read, profiled at source level, or changed in-tree.

The other SM100 options with FlashInfer 0.7.2 and the vendored FlashMLA do not cover this case:

- trtllm-gen (`backend="auto"`): `fmhaSm100fKernel_QkvE4m3OBfloat16HQk576HV512...TokenSparseP1...` cubins. The SASS runs QK^T and PV as FP8 tcgen05 MMAs (`UTCQMMA`) and quantizes P to e4m3 before PV. This is the kernel this PR matches.
- `backend="cake"`: sparse calls take the `mla_fp8_tail` program, one warp per (row, head) that decodes every e4m3 byte through a float lookup table and accumulates in FP32 on CUDA cores. Its scores live in 16 KB of shared memory, so it accepts `max_seq_len <= 4096`. Cake's FP8 tensor-core programs serve dense MLA only.
- `backend="cute-dsl"` rejects `sparse_mla_top_k`.
- FlashMLA's SM100 FP8 sparse decode (`flashmla_kv`) takes BF16 Q, dequantizes the 656 B FP8 cache to BF16 (e4m3 -> f16 -> f32 -> bf16) and runs BF16 MMAs (`UTCHMMA`).

The kernel takes the trtllm-gen inputs unchanged: merged e4m3 Q `[tokens, h_q, 576]` (RoPE included), the raw 576 B e4m3 paged KV pool, token-level slot indices (-1 is invalid), and the fused scales `bmm1_scale = q_scale * k_scale * sm_scale` and `bmm2_scale`. QK^T (NoPE and RoPE) and PV are all e4m3 x e4m3 tcgen05 MMAs.

## Modifications

- `python/sglang/kernels/jit/csrc/sparse_mla_q8kv8_sm100/{kernel.cuh,entry.cuh,helpers.h,params.h}`: the main kernel, the split-merge kernel and the TVM-FFI entry, JIT-compiled for `sm_100a`.
- `python/sglang/kernels/ops/attention/sparse_mla_q8kv8_sm100.py`:
  - `sparse_mla_q8kv8_sm100_fwd(q, kv, indices, bmm1_scale, bmm2_scale=1.0, attn_sink=None, topk_length=None, num_splits=None, *, out=None, max_logits=None, lse=None) -> (out, max_logits, lse)`.
  - `sparse_mla_q8kv8_sm100_trtllm(query, kv_cache, block_tables, bmm1_scale, bmm2_scale=1.0, seq_lens=None)`: the arguments and BF16 output of the trtllm-gen sparse call. `seq_lens` becomes `topk_length`, because trtllm-gen counts the first `min(seq_len, topk)` slots of a row as valid and does not look at -1.

- `python/sglang/srt/mem_cache/kv_cache_configurator.py` and `models/deepseek_common/attention_forward_methods/{forward_mla,forward_mha}.py`: treat `q8kv8_sm100` like `trtllm` where the raw 576-dim FP8 KV layout and the fused RoPE are decided.

Usage on B200 with `--kv-cache-dtype fp8_e4m3` (the DSA default on SM100):

- The default backends do not change and stay `trtllm`. `--dsa-prefill-backend q8kv8_sm100` and `--dsa-decode-backend q8kv8_sm100` enable this kernel, and the two can be set separately.
- Once enabled, every call of that phase can run this kernel. The SM90 counterpart, `--dsa-prefill-backend flashmla_sparse_q8`, is prefill-only (the backend rejects it for decode).
- For speed, we recommend this backend for prefill and for decode calls with at least 4 query rows per rank (running requests per rank times 1 + MTP draft tokens): in the decode table it is 1.17-1.74x faster at s_q = 16-256 and on par at s_q = 1, and the extra measurements after the table give 1.05-1.26x at 4-12 rows.

### Kernel design

- Work item = (query token, 64-head block, split). Persistent CTAs, `grid = min(items, num_SMs)`, 512 threads, one CTA per SM: 196 KiB smem, all 512 TMEM columns, 113 registers, no spills.
- Warp roles: softmax and O rescale (0-3), TMA `gather4` of K rows (4-7), MMA issuer A: Q copy to TMEM, QK^T over dims 0-255, PV (8), validity masks (9), Q TMA for the next item (10), MMA issuer B: QK^T over dims 256-511 and RoPE (11), epilogue (12-15).
- Per 64-token block: 16 TS MMAs over NoPE (Q sits in TMEM, copied into both lane halves so each lane holds a full dot product), 2 SS MMAs over RoPE, then 4 PV MMAs that read V as the K NoPE tile in MN-major order, so there is no V copy or transpose.
- O (64 x 512 fp32) stays in TMEM. P is stored as e4m3 `2^(x - m + 4)`; O is rescaled only when a block max exceeds the running max by more than 4 (log2 units). The fused scale is folded into the exp2 constant.
- Rings: 4 K stages; P and S double-buffered. The epilogue scale ring is 3 deep, because the softmax of item i+2 waits only on the PV of item i and can run two items ahead of the epilogue.
- Issuer A issues the next item's Q copy and first QK^T before the last PV of the current item, and a fourth warpgroup runs the epilogue, so item boundaries overlap.
- For `topk >= 1024` and few query tokens, the top-k is split into 2, 4 or 8 chunks (each at least 256 entries, items at most the SM count). A second kernel merges the partials by lse and adds the sink to the denominator once.
- PDL (`griddepcontrol`) is enabled only without a split; with the merge kernel in the chain it measured 5-8% slower.

### Contract and limitations

- SM100, validated on B200 (148 SMs).
- `topk` must be a multiple of 64, with int32 indices. Indices `< 0` or `>= s_kv` and positions `>= topk_length` are masked.
- Per-tensor scalar scales, as in the SM90 version and trtllm-gen. The 656 B per-128-dim-scale layout of `flashmla_kv` is not supported.
- `lse` is the natural log without the sink. A row with no valid index returns zeros, `lse = +inf`, `max_logits = -inf`.
- Host time per call is 35.9 us, against 23.4 us for trtllm-gen (s_q=16, topk=2048). The wrapper validates arguments in Python and the launcher encodes 4 TMA descriptors per call. CUDA graphs hide it; eager prefill pays it once per layer.

## Accuracy Tests

### Kernel tests

`test_sparse_mla_q8kv8_sm100.py` compares against exact fp32 attention over the dequantized e4m3 inputs, so the remaining error is the e4m3 rounding of P and the BF16 output. All 26 tests pass on B200 (79 s including the JIT build):

- 17 reference cases: topk 64 / 512 / 2048 / 2176; splits 1 / 2 / 4 / 8; `attn_sink` with +inf and -inf entries; `topk_length` including 0; 30% and 97% invalid indices; h_q 32 / 64 / 128; paged and 640 B strided KV; multi-wave persistent CTAs. Out rel_l2 2.2-2.6%; lse and max_logits about 1e-7.
- Caller-owned output buffers, including the h_q = 32 padding path, and the rejection of misaligned indices.
- Inputs built the way the DSA `trtllm` backend builds them: Q and K from `mla_quantize_and_rope_for_fp8`, a scattered 576 B pool, `transform_index_page_table_decode`, batch 1 / 16 / 64 / 200 with seq_lens from 1 to 9000. Error vs exact 0.6-2.4% (trtllm-gen: 0.7-2.8%). Passing `seq_lens` is bitwise equal to masking -1 alone, the trtllm-layout entry is bitwise equal to the flat entry, CUDA graph replay is bitwise equal to eager, and the output differs from trtllm-gen's by 1.0% rel_l2 at batch 16 (both kernels round P to e4m3).

`_forward_trtllm` itself was also run on B200 with the real index transform, trtllm-gen and this kernel (4, 16 and 64 decode rows plus DP padding rows). On the `q8kv8_sm100` path the error vs exact is 2.3% / 0.6% / 2.2% (trtllm-gen: 2.7% / 0.7% / 2.5%) and the padding rows stay zero. The CPU unit tests pin the arguments the kernel receives and the launch checks.

### End-to-end accuracy

[`zai-org/GLM-5.3`](https://huggingface.co/zai-org/GLM-5.3) (official FP8 checkpoint: 64 heads, `kv_lora_rank` 512, RoPE dim 64, `index_topk` 2048) was served on 8x B200 with DP attention=8, with this kernel on both phases, which is `--dsa-prefill-backend q8kv8_sm100 --dsa-decode-backend q8kv8_sm100` in this PR. The baseline run differs only in the DSA attention backend: FlashMLA (`flashmla_kv`: BF16 Q, 656 B FP8 KV with per-128-dim scales and BF16 RoPE). Sampling: `temperature=1.0`, `top_p=0.95`, `chat_template_kwargs={"enable_thinking": true}`.

| Benchmark | This kernel | FlashMLA (`flashmla_kv`) |
|---|---|---|
| AIME 2025 | 93.23 | 92.92 |
| HMMT 2025 | 90.83 | 91.67 |
| CMMLU | 92.08 | 91.85 |
| LiveCodeBench | 88.11 | 86.34 |
| GPQA | 82.41 | 82.26 |

The differences are within run-to-run noise. FlashMLA is the more precise baseline (BF16 RoPE, finer KV scales), so the result also covers the move to the 576 B per-tensor FP8 layout.
