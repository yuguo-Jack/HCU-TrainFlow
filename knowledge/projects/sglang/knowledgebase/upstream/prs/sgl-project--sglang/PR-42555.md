# [cake_kernels] dsa_indexer route: DeepSeek-V3.2 lightning-indexer logits (ragged + paged) through FlashInfer dense_mqa / paged_mqa

[Upstream PR](https://github.com/sgl-project/sglang/pull/42555) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V3.2 / V3.2-Exp serving spends a measurable share of every decode and prefill step in the lightning-indexer logits kernels (`deep_gemm.fp8_paged_mqa_logits` on the paged FP8 index cache, `deep_gemm.fp8_mqa_logits` on the gathered prefill KV). FlashInfer is gaining Cake-generated programs for exactly these two contracts, exposed with the same signatures as the DeepGEMM calls (`flashinfer.dense_mqa.fp8_mqa_logits`, `flashinfer.paged_mqa.get_paged_mqa_logits_metadata` / `fp8_paged_mqa_logits`). This PR wires them into `sglang.kernels.cake_kernels` behind the existing opt-in route switch so the engine can take them where they are available and keep the stock kernels everywhere else.

Stacked on the Cake forwarding series (`cake/01` .. `cake/10`); the route table (`SGLANG_CAKE_ROUTES`) and the adapter conventions are the ones introduced there.

## Modifications

* `python/sglang/kernels/cake_kernels/attention_sparse.py`: adapters `supports_fp8_mqa_logits` / `fp8_mqa_logits` (ragged prefill) and `supports_fp8_paged_mqa_logits` / `get_paged_mqa_logits_metadata` / `fp8_paged_mqa_logits` / `prepare_paged_mqa_logits` (paged decode / verify). Admission on the exact engine tensors: CUDA cc 10.0 / 10.3, FlashInfer modules present (`find_spec`), e4m3 `q` with 32 or 64 heads and D = 128, f32 weights, int32 window / length / table tensors, page 64 for the paged entry, and the shipped FlashInfer catalog serving the point (`dense_route_available` / `paged_route_available`, so new programs admit automatically when FlashInfer ships them).
* `python/sglang/kernels/ops/attention/cake.py`: `KernelSpec` registrations `attention.fp8_mqa_logits`, `attention.get_paged_mqa_logits_metadata`, `attention.fp8_paged_mqa_logits`, `attention.prepare_paged_mqa_logits` (+ `cake_*` entry points).
* `python/sglang/srt/layers/attention/dsa/cake_indexer_routes.py` (new): route helpers for the two sites. Route off touches nothing; admitted calls receive the engine's tensors positionally with `clean_logits=False` and DeepGEMM's current SM count as the CTA budget (the pipeline-parallel reservation is honoured); a FlashInfer host-side rejection is cached per reason; a shape first seen inside CUDA-graph capture falls back for that graph; the first "taken" / "fallback" per site and reason are logged once (`[cake-route] dsa_indexer/...`).
* `python/sglang/srt/layers/attention/dsa/dsa_indexer.py`: the two `deep_gemm.fp8_mqa_logits` calls of `_get_topk_ragged` go through `Indexer._fp8_mqa_logits_cuda`, the two `deep_gemm.fp8_paged_mqa_logits` calls of `_chunked_fp8_paged_mqa_logits` through `Indexer._fp8_paged_mqa_logits_cuda`; each tries the Cake route and falls back to the unchanged stock call. Chunking, `q_offset` / padding handling, `_mask_init_and_local_tokens` and `topk_transform` are untouched; the paged helper only engages for the DeepGEMM paged backend and `clean_logits=False`. The per-chunk DeepGEMM schedule metadata is now computed lazily (only when the stock call runs).
* `python/sglang/kernels/cake_kernels/_routes.py` / `README.md`: route description and the four new inventory rows.

Admission is per shape and follows the FlashInfer catalog: the 32-head ragged route (`K % 256 == 0`) and, for the 64-head indexer, only the query-count tiers whose FlashInfer programs clear the stock DeepGEMM kernel on the running device's architecture (the adapters pass the device arch, the call's batch and `max_context_len` to `dense_route_available` / `paged_route_available`). Shapes outside the admitted table take the unchanged `deep_gemm` call; the FlashInfer side publishes the admitted and withheld entries in its catalog policy, so widening admission later is a FlashInfer release, not an sglang change.

Default behaviour is unchanged: without `SGLANG_CAKE_ROUTES=dsa_indexer` every call site runs exactly the code it ran before.

## Accuracy Tests

* `test/registered/unit/kernels/test_cake_dsa_indexer_route.py` (CPU, mocked): route off touches nothing; route on + admitted forwards the engine's tensors with the DeepGEMM call contract; admission rejection, FlashInfer host rejection and in-capture first-seen shapes fall back exactly once per reason with the documented log lines.
* `test/registered/kernels/ops/attention/test_cake_dsa_indexer.py` (GPU, B200 / GB300): registry resolution of the four entries; ragged `fp8_mqa_logits` against `deep_gemm.fp8_mqa_logits` (finite logits within FP32-accumulation tolerance of exact FP8 products, atol 1e-2 of the row max / rtol 1e-2) and agreement of the top-k index sets after the engine's `+inf` init / local-token scatter (exact away from the selection boundary; indices may swap only within the logits tolerance of the k-th value); the paged entries against `deep_gemm.get_paged_mqa_logits_metadata` + `fp8_paged_mqa_logits` with the same gates (chunked oracle above the SM count); the `Indexer` helper switches on the route with the real tensors. Shapes the installed FlashInfer catalog does not serve on the test device are skipped with the reason.

* Both route helpers captured in a CUDA graph (the engine's decode / verify path) replay the eager bits after the captured output is poisoned, so kernels launched outside the capture stream fail loudly.
