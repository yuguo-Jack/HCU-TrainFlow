# [Fix] [AMD] diffusion: materialize SDPA operands for long sequences

[Upstream PR](https://github.com/sgl-project/sglang/pull/46065) · state: open · merged: False

## Original PR description

## Motivation

`SDPAImpl.forward` transposes the `[B, S, H, D]` activations into the `[B, H, S, D]` layout `scaled_dot_product_attention` expects. That transpose is always a strided view, and AOTriton's flash path only applies to **dense** operands, so on HIP a long-sequence attention silently falls back to a generic kernel.

Measured on gfx1151 (AMD Ryzen AI MAX+ 395, 32 heads x 128, bf16, one SDPA call):

| S | strided | dense | gain |
|---|---|---|---|
| 1024 | 1.39 ms | 1.18 ms | 1.18x |
| 2048 | 4.75 ms | 4.35 ms | 1.09x |
| 4096 | 20.84 ms | 15.99 ms | 1.30x |
| 8192 | 184.2 ms | 61.2 ms | 3.01x |
| 16384 | 2255 ms | 242.9 ms | **9.28x** |

The cliff is at S=8192: below it the strided layout still reaches the flash kernel (13-15 TFLOPS), above it drops to 2 TFLOPS while the dense operands hold 18 TFLOPS.

## Modifications

- Extract `sdpa_operands()` from `SDPAImpl.forward`. It still returns the heads-first view, and on HIP it materializes the operands **when `S >= 8192`**.
- The copy is layout-only: values are bit-identical, so there is no accuracy change.
- Below the threshold nothing changes. Qwen-Image 2.1 at 1024^2 (S=4096) is 5.7% *slower* when the copy is unconditional, because the per-layer allocation costs more than the 1.3x kernel gain - so the gate is a sequence threshold, not just a device check.
- The common path (CUDA, and short sequences on any device) keeps the zero-copy view and is the first branch.

## Accuracy Tests

- `python/sglang/multimodal_gen/test/unit/test_sdpa_operand_layout.py` (new, runs in the `diffusion-unit-1-gpu-h100` suite): heads-first layout and values; short sequences keep the zero-copy view; long sequences are dense only on HIP; the copy preserves every bit (`torch.equal` against the transposed view).
- End to end, the change only moves tensor layout, so no numerical change is expected by construction. Verified on Qwen-Image 2.1 at 1024^2 and 2048^2 with a fixed seed: identical image, no metric shift.

## Speed Tests and Profiling

Qwen-Image 2.1, default environment, `torch_sdpa` backend, gfx1151. Seconds per denoising step (mean over all steps), two runs per arm:

| Shape | before | after | gain |
|---|---|---|---|
| 1024^2 / 20 steps | 3.8524 | 3.8523 | 1.00x |
| 2048^2 / 12 steps | 78.04 / 77.42 | 22.04 / 22.11 | **3.54x** |

Within-arm spread <1%. The 2048^2 gain is AOTriton flash instead of the generic kernel; the 1024^2 row confirms the threshold leaves short sequences untouched.

Rebased onto `upstream/main` (`4709a3a24e`) and re-verified on gfx1151.

**Rebase / checks.** The only conflict was the import block in `sdpa.py` (upstream added `get_forward_context_or_none`); resolved by keeping both imports. `ruff format`, `ruff --select=F401,F821,F823,UP037`, `isort`, and the new `scripts/lint/check_indirect_imports.py` are clean on the two touched files. `test_sdpa_operand_layout.py` passes 4/4 on a Ryzen AI Max+ 395 (gfx1151, torch 2.9.1+rocm7.2.4, AOTriton 0.11.1).

**gfx1151 head sweep.** Your RDNA4 numbers prompted this. Same protocol as yours: same process, arms interleaved, copy cost inside the dense arm, bf16 / D=128 / B=1 / non-causal, `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`, 7 rounds, median.

| H | stride H·D·2 (B) | S=8192 | S=16384 | S=32768 |
|---|---|---|---|---|
| 12 | 3072 | 0.96× | 1.02× | 1.34× |
| 24 | 6144 | 1.02× | **2.07×** | **4.46×** |
| 32 | 8192 | **2.19×** | **6.82×** | **11.82×** |
| 40 | 10240 | 1.12× | **2.77×** | **4.75×** |
| 48 | 12288 | **2.88×** | **7.84×** | **12.58×** |
| 64 | 16384 | **2.80×** | **8.39×** | **12.31×** |

Gain = strided / dense including the copy. For scale, dense kernel-only at H=32 is 61.1 / 246.0 / 969.6 ms at S = 8192 / 16384 / 32768 versus 173.3 / 1937.2 / 12331.6 ms strided; the three copies themselves cost 0.5–12% of the strided arm.

So yes, gfx1151 falls off for other head counts as well, and the set matches neither RDNA card:

- 24, 32, 40, 48 and 64 all fall off by S=16384 (2.07–8.39×);
- 32, 48 and 64 already fall off at S=8192 (2.19–2.88×);
- only H=12 (stride 3072 B) stays on the fast path up to S=32768, where materializing is still a 1.34× win.

**On `(H * D) % 4096 == 0`.** Measured, that predicate does not describe gfx1151 and would give up real gains here. H=48 has H·D = 6144 — not a multiple — yet wins 2.88/7.84/12.58× at the three sizes; H=24 (H·D = 3072) is 2.07× at 16384; H=40 (H·D = 5120) 2.77×. The predicate would switch all three off. It does match H=32 and H=64, which fall off, so it reads as a gfx1201 property rather than a portable one.

**Suggested gate.** Keep HIP + `S >= 8192`. Across the 18 shapes above it is neutral-or-better in 17; the single loss is H=12 at S=8192 (0.96×, i.e. 4%), and H=12 recovers 1.34× by 32768. Finer gating would have to be per architecture — your gfx1100 rows fall off from H=24 at 16384, your gfx1201 rows from H=32/64, gfx1151 (this sweep) from H=32/48/64 at 8192 and H=24/40 at 16384 — and a stride predicate fitted to one card excludes gains on the other two. I'd rather keep the conservative gate than hard-code a table we cannot cross-check on gfx1100/gfx1201.

Happy to fold a per-arch predicate into this PR if maintainers prefer that; otherwise it is ready for the AMD lane (still needs the `run-ci` label).
