# [Feat] sglang-processor: Tokenizer and chat-layer APIs for rust-server, and template selection fixes

[Upstream PR](https://github.com/sgl-project/sglang/pull/46195) · state: closed · merged: False

## Original PR description

## Modifications

- **`TextTokenizer` resolves the configured BOS and encodes chats.**
  - `DynamoTokenizer::load` loads both special-token modes, plus the BOS that `tokenizer_config.json` names (Python's `bos_token_id`, looked up in the vocab, or encoded as a special for tiktoken).
  - `encode_chat` encodes as Python's chat layer does: the template without the tokenizer's specials, then the `continue_final_message` text minus one leading BOS (`_append_assistant_prefix_to_prompt_ids`).
  - The decoding handle is exposed for hosts that detokenize too.
- **`ChatModel` exposes the chat layer's model rules**, which `lower_chat` applied inline, so a host's own chat handler applies the same ones:
  - `for_formatter`: the template's reasoning facts and encoding spec.
  - `keeps_special_tokens`: Kimi K3's markers.
  - `unreported_prompt_tokens`: K3's generation stub.
  - `thinking` / `request_thinking`: `_get_reasoning_from_request`.

  `lower_chat` uses them, with unchanged behaviour.
- **`TemplateError::NeedsRenderFallback` marks the valid requests the SGLang-parity renderers decline** (`"... requires a fallback renderer"`, e.g. Qwen3.8 floats such as `0.000001`), so hosts can try another renderer instead of rejecting them.
- **`ChatFormatter::renders_requests`** names the formatters `render_request` serves, so a host picks between it and `render_prompt` without listing models.
- **`dynamo_parsers` and `minijinja` are re-exported**, since their types appear in the processor's API (minijinja's through Dynamo's request trait), so hosts keep the processor's versions.
- **Selection prefers a checkpoint's own template to the native encoder.** Python's `resolve_chat_encoding_spec` uses DeepSeek-V3.2's encoder, and the other display-name native encoders, only when the checkpoint ships no template.
- **Selection guesses a legacy template from the model path before reading the checkpoint's template files**, in Python's `load_chat_template` order. Before, a model such as llava-onevision or internvl that also ships `chat_template.json`/`.jinja` rendered with the Jinja template.

sgl-router uses the same selection and `lower_chat`, so it gets the selection fixes. It only adds context to `render_request` errors, so the new error variant changes nothing there.

## Tests

- Unit tests:
  - The tokenizer resolves the configured BOS and drops only one BOS from a continuation.
  - `ChatModel` decides reasoning as Python does, including from `reasoning_effort`.
  - A declined V4.1 developer turn is `NeedsRenderFallback`.
  - A V3.2 checkpoint's own template wins over the native encoder.
  - A legacy model path wins over a discovered `chat_template.jinja`.
- `cargo test`, clippy and fmt pass. `sglang-processor` builds with `parser`, `render`, `tokenizer`, `openai` and `render,openai` only, its parity fixtures pass, and `sgl-router` builds against it.
