# [Fix] step5: Keep FA4 SWA graph buffers fixed and accept streamed weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/44413) · state: open · merged: False

## Original PR description

Follow-up fixes for #44356 (targets its `step5-preview-support` branch).

## What each commit fixes

1. **FA4 SWA: window-align buffers stay fixed under CUDA graphs.** Captured decode graphs bake the addresses of `_swa_align_seqlens` / `_swa_align_leftpad`. An eager decode batch wider than `--cuda-graph-max-bs` replaced both tensors, so every later replay read the freed originals: SWA layers attended the wrong keys (fluent but wrong output), and could read out of bounds. The graph buffers are now allocated only by `init_cuda_graph_state` and never replaced; an oversize graph batch trips `assert_buffer_fits`; eager forwards compute the align out of place.
2. **Streamed weight updates.** `load_weights` now takes any subset in any number of calls after the checkpoint load, including per-expert names (`model.layers.L.moe.experts.E.{gate,up,down}_proj.weight[_scale_inv]`) mapped onto the packed parameter. The completeness check and duplicate-shard scan apply to the checkpoint load only. Unknown names and an expert sent twice in one call are still refused.
3. **Checkpoint-BF16 experts on Blackwell without the FlashInfer SwigluStep patch.** They use TRTLLM only when FlashInfer has the patch, otherwise the Triton runner (same post-SiLU clamp), instead of failing at startup.
4. **Disk reload of the full checkpoint.** `model.embed_tokens.weight` is stored in two shards; every later `/update_weights_from_disk` failed with "Duplicate Step5 target weight". A resent duplicate that equals the first copy is now skipped, a differing one refused.
5. **MTP draft load crash.** After (4), `Step5MTP.load_weights` passed the old argument type to the duplicate-owner scan, so every MTP/EAGLE launch raised `TypeError`.
6. **BF16 updates into FP8 experts are always requantized** (block FP8 with scales). `SGLANG_STEP5_QUANTIZE_BF16_MOE` now only controls serving the checkpoint's BF16 expert layers as FP8.
7. **FP8 into BF16 experts is refused before anything is written.** Previously the FP8 tensor was cast to BF16 without its scales and the following `weight_scale_inv` was refused after the expert was already overwritten. A tensor or update bucket is checked as a whole first.
8. **Dummy / sharded-state / remote-instance start.** Those loaders skip `load_weights`, so the first streamed update was treated as the checkpoint load (per-expert names refused, partial buckets raised after being applied). `post_load_weights` now marks the weights loaded.
9. **Per-expert duplicate key and BF16 runner log.** Resent duplicates are matched per expert, not on the packed tensor; the BF16 expert log names the runner the layer actually uses; `BF16-EXPERTS.md` updated.

## Tests

- `test/registered/unit/models/test_step5_weight_updates.py` (new): 14 tests, all pass on H200. On the base branch 8 fail: accept one expert at a time, any subset without the disk index, same expert twice in one call, disk reload resending duplicates, FP8 into BF16 experts, dummy-start loader, requantize without the opt-in, Blackwell runner selection. The MTP draft test guards (5), a regression from (4) within this PR.
- `test_flashattention_graph_metadata.py::TestSwaWindowAlignGraphBuffers`: 2 new tests, fail on the base branch and pass here. On GB300/B300 with a real FA4 kernel captured in a CUDA graph (page 64, window 127), one bs=16 eager decode with graph max-bs 4 gave max err 0.8+ or an illegal memory access on the next replays before the fix, 0.002-0.004 after.
- `test_empty_cpu_sequence_lengths_use_static_bound` in the same file fails on the base branch too (`'FlashAttentionBackend' object has no attribute 'sliding_window_size'` from its `__new__` stub); not changed here.

## Known gaps

- On Blackwell, the TRTLLM expert re-layout is not redone after a streamed expert update.
- A dummy start followed by a full disk reload still refuses the duplicated embedding (the duplicate set is only recorded by a real checkpoint load).
- The Step3p7 wrapper does not forward `post_load_weights` to the Step5 language model, so (8) does not reach it.
