# [Step5] Keep FA4 SWA buffers fixed under CUDA graphs; accept streamed weight updates (fixes for #44356)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44413) · state: open · merged: False

## Original PR description

Follow-up fix for #44356 (targets its `step5-preview-support` branch).

## Bug

`FlashAttentionBackend._swa_align_out_buffers` lazily grows `_swa_align_seqlens` / `_swa_align_leftpad`. Those two tensors are also CUDA-graph state: `init_cuda_graph_state` allocates them for `max_bs * topk`, the captured FA4 decode kernels bake their addresses, and replay prep refills them in place.

When one decode batch is wider than `--cuda-graph-max-bs` it runs eagerly. `init_forward_metadata` then reaches `_swa_align_out_buffers` with `n > capacity` and **replaces** both tensors. Every later graph replay writes the new tensors while the captured kernels read the freed originals:

- SWA layers get a stale `cache_leftpad` / `seqused_k`, so they attend the wrong keys. The model keeps producing fluent but wrong text until restart, with no error.
- Once the freed memory is reused, the stale values can also make the kernel read out of bounds (`illegal memory access`).

We hit this in RL rollouts where per-engine concurrency exceeded `--cuda-graph-max-bs`. Reaching it needs FA4 at a page size other than 128 (Step 5 at page 64, or EAGLE topk > 1 at page 1), T=1 decode on SWA layers, and one decode batch with `bs > --cuda-graph-max-bs`.

## Fix

The graph buffers have a single owner:

- They are allocated only in `init_cuda_graph_state` and never replaced.
- Only the graph paths use them: capture/replay prep (`_apply_cuda_graph_metadata`) and the in-graph draft-extend hook. An oversize graph batch now trips `assert_buffer_fits` instead of growing the buffers silently.
- The eager entry (`init_forward_metadata`) and the per-layer fallback in `_swa_window_aligned_kvcache` compute the alignment out of place, like the rest of eager metadata. Inside a capture, the fallback's allocation comes from the graph pool, so its address stays stable.
- `_fill_swa_window_align` defaults to the graph buffers. A future call site that forgets the flag therefore gets either the correct behavior or a loud assert, never a silent rebind.

## Tests

- New `TestSwaWindowAlignGraphBuffers` in `test_flashattention_graph_metadata.py`. Both cases fail on the PR head and pass with this change:

  - a graph batch larger than capacity raises instead of growing the buffers.
- Real FA4 decode kernel captured in a CUDA graph on GB300 and B300 (SM103), page 64, window 127, alignment produced by the backend's own `_fill_swa_window_align`, compared against the same kernel run unaligned:

## Other issues found on #44356 (not fixed here)

1. **FA4 on Blackwell with a non-Step-5 SWA model (e.g. gpt-oss) crashes on the first SWA decode.** `_fa4_page_constraint` forces page 128, and FA4 rejects `leftpad_k` when `page_size == tile_n`: `leftpad_k is only supported with non-TMA paged KV (page_size=128 != tile_n=128)`. The window align is enabled without checking the page size.
2. **FA4 SWA decode on Hopper crashes** with `leftpad_k is only supported on SM100/SM110 FA4`. There is no architecture check before the align is applied.
3. **Two existing unit tests fail on the PR head**, independently of this change, with `'FlashAttentionBackend' object has no attribute 'sliding_window_size'`. Their `__new__` stubs reach the new `_fill_swa_window_align` through `init_forward_metadata`:
   - `test_flashattention_graph_metadata.py::test_empty_cpu_sequence_lengths_use_static_bound`
   - `test_verify_widening_is_wired.py::test_captured_verify_build`

Until this lands, setting `--cuda-graph-max-bs` ≥ `--max-running-requests` avoids the bug, at the cost of capturing more graphs.

## Second fix: accept streamed weight updates

`Step5ForCausalLM.load_weights` was written for one checkpoint load, so RL weight sync could not use it:

- routed experts were accepted only in the packed checkpoint form, while trainers send them one expert at a time (`model.layers.L.moe.experts.E.{gate,up,down}_proj.weight[_scale_inv]`);
- every call raised unless it covered every target weight, so a bucketed update failed on its first bucket, and so would any update that leaves a frozen part out (the DSA indexer);
- every call rescanned the checkpoint's shard index on disk.

Other models' `load_weights` take any subset in any number of calls, mapping per-expert names through `make_expert_params_mapping`. Step5 now does the same after its checkpoint load: a per-expert name loads that expert's row of the packed parameter, and the completeness check and duplicate-shard resolution apply to the checkpoint load only. Unknown names and an expert sent twice in one call are still rejected; NVFP4 layers keep their per-expert path.

New CPU test `test/registered/unit/models/test_step5_weight_updates.py`: the three update cases fail on the previous head and all 7 pass with this change.
