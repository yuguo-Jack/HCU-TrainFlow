# [router] power_of_two: in-flight request load for --dp-aware decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/43483) · state: closed · merged: True

## Original PR description

## Motivation

Follow-up to #42027, which this PR is stacked on (its commit is included until it merges).

With DP attention every decode step waits for the busiest DP rank, so what matters is how many requests each rank holds. p2c on `num_total_tokens` evens out KV across decode ranks but leaves their request counts as uneven as `round_robin` (tables below).

## Modifications

`SGLANG_ROUTER_P2C_LOAD_METRIC` selects what `power_of_two` compares:

| value | compares | ties |
|---|---|---|
| `tokens` (default) | polled `num_total_tokens`, two random candidates (unchanged) | in-flight requests |
| `requests` | the router's in-flight requests, two random candidates | polled tokens |
| `least_requests` | the router's in-flight requests, every candidate | polled tokens, then random |

In-flight requests are counted from dispatch to the end of the response (#42027). For a decode rank that is its running batch, every queue (waiting, prealloc, transfer, retracted) and requests still in prefill: the set `/v1/loads` reports as `num_running_reqs + num_waiting_reqs`, but live instead of polled. `least_requests` skips workers the load monitor has no entry for unless none has one, and reads the counters without locking, so concurrent selections may pick the same worker.

The switch is an env var to keep the policy config and CLI unchanged; happy to turn it into a `--p2c-load-metric` flag instead.

## Results (MI355X)

DeepSeek-V4-Pro AgentX trace replay, 1P1D, prefill TP8/EP8 and decode TP8, both with DP attention (8 decode ranks); router `--policy consistent_hashing --dp-aware --worker-startup-check-interval 1` (the load monitor polls at that interval). Router built from this branch on `lmsysorg/sglang-rocm:v0.5.21-rocm724-mi35x-20261007`; each point is a 1 h measurement.

Absolute values; in parentheses, the change against `round_robin`. All `power_of_two` columns poll loads every 1 s.

`requests` lowers the busiest rank's batch by 6-12% and `least_requests` by 6-14%, which is where the TPOT gain comes from. Throughput moves less because output is under 1% of the tokens in this input-heavy workload. TTFT stays within run-to-run noise except c384 (p50 +12% with `requests`, +15% with `least_requests`), to be rechecked.

### Concurrency 512 over the hour

`p2c token` and `p2c in-flight requests` below are `tokens` and `requests`.

![All four arms over the hour, concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-router-p2c/c512-four-arms-over-the-hour.png)

`requests` keeps outstanding requests flat across decode ranks for the whole hour (bottom) and `least_requests` flatter still, while `tokens` is less even than `round_robin`. At 512 more than half (55-57%) of each rank's in-flight requests are still waiting on KV transfer, so equal in-flight counts no longer mean equal running batches: the busiest rank's batch (top) improves less than at lower concurrency, and evening out in-flight requests further with `least_requests` (CV 0.01 vs 0.02) leaves it unchanged (30.5 vs 30.6).

![Running requests per decode rank, p2c in-flight requests (1s), concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-router-p2c/c512-per-rank-running-p2c-inflight.png)

With `requests` every rank's hourly mean running batch is within 2% of the 8-rank mean, and no rank is the busiest more than 17% of the time (`round_robin`: DP6 at +6.3% and 21%; 12.5% if even).

## Test

Two new unit tests: `requests` prefers fewer in-flight requests over a lower token load, and `least_requests` picks the global minimum while skipping workers without a polled load. `cargo test --lib` (398 passed), `cargo clippy --all-targets --all-features -- -D warnings` and `cargo +nightly fmt -- --check` pass.
