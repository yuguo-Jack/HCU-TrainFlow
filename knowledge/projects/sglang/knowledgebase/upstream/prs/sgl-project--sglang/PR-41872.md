# [Fix] scheduler: stop latching batch_is_full when nothing can run

[Upstream PR](https://github.com/sgl-project/sglang/pull/41872) · state: closed · merged: True

## Original PR description

Fixes #41841.

## Problem

When a prefill round ends in `AddReqResult.NO_TOKEN` with an empty running batch and an empty `can_run_list`, the plain path set `running_batch.batch_is_full = True` unconditionally. `batch_is_full` is only cleared on the decode path (`update_running_batch`, the last-batch merge, retract), and an empty batch never reaches decode. So once the pool momentarily ran dry on an otherwise idle engine, the flag stuck and every later `_get_new_batch_prefill_raw` call bailed at the `batch_is_full` gate. From the outside the server stops prefilling: requests sit in the waiting queue forever even after memory frees up again.

The hicache / lmcache / unified branches right next to it already guard this latch with "only when something can actually be served". An empty batch has no such guarantee, so the guard now applies to every NO_TOKEN outcome.

## Fix

Drop the unconditional `= True` branch and use the guarded form for all NO_TOKEN results:

```python
running_batch.batch_is_full = len(adder.can_run_list) > 0 or (
    not running_batch.is_empty()
)
```

Behavior only changes in the empty + nothing-admitted case (True -> False). When work exists the flag still latches, and decode clears it as before.

NO_TOKEN is not the only site that latches an empty batch: the no-free-slot checks (`get_num_allocatable_reqs(...) <= 0`, before and inside the admission loop) set the flag the same way, for example when streaming sessions hold the request slots. So `_get_new_batch_prefill_raw` also clears the flag at the read site when the running batch is empty, which covers every set site on this path.

## Test

`test/registered/unit/managers/test_scheduler_batch_is_full_latch.py`: an empty running batch with `batch_is_full` already set still reaches admission, and the flag is cleared. It does not depend on which site set the flag, so it covers the NO_TOKEN and no-free-slot latches alike. It fails without the read-site clear and passes with it.

Full `test/registered/unit/managers/` suite: 825 passed; the 9 remaining failures are pre-existing macOS environment issues in the mm/shm/snapshot tests, identical with and without this change (verified via stash comparison). The changed logic is pure admission bookkeeping, exercised here by CPU unit tests; happy to add more if reviewers want e2e coverage.
