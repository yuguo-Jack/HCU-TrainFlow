# [Feat] rust-server: DeepSeek-V4.1 images via deepseek-recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/46562) · state: open · merged: False

## Original PR description

Stacked on #46291. Rebased onto `main` with #45449, which now renders DeepSeek-V4/V4.1 chat through deepseek-recipe in `sglang-processor` and submits recipe's ids. This PR adds image support on top of that.

Add DeepSeek-V4.1 image support to the Rust server through deepseek-recipe: recipe renders and encodes the chat prompt, and deepseek-recipe-image resizes the images.

## Modifications

- **Family-generic MM spec.**
  - Python sends the spec to Rust as Dynamo's `ProcessorSpec` JSON, and each `RUST_MM_FAMILIES` entry resolves its own fields. `MmFamily` and `MmResample` are removed.
  - The drain adapter sets M-RoPE and `model_specific_data` only when a family produces them.
  - `mm_parity` compares aux tensors by name.
- **`sglang-processor` `mm/models/`.** This holds families whose pixel path Dynamo does not ship yet; each file is deleted once Dynamo ships it. `deepseek_v41.rs` normalizes and patchifies an image that recipe has already resized: `[n_vit, 3, 14, 14]` with `n_vit_h` / `n_vit_w`, and `h*(w+1)+2` tokens. An image over the token budget is rejected.
- **Chat.**
  - Rendering DeepSeek-V4/V4.1 with recipe and submitting its prompt ids comes from #45449. This PR makes the server's `render_chat` use `ChatFormatter::encode_multimodal_request` for such formatters, so images follow recipe's placeholder order, as `serving_deepseek_recipe.py` does.
  - Recipe's render and encode run as blocking tasks (`render_chat_off_executor`), at most `--tokenizer-worker-num` at once (`ChatEncodes`), never on the HTTP executor, for both chat and `/tokenize`. A 1M-token prompt takes about a second to encode.
  - `/tokenize` with `messages` returns the ids chat submits, as Python returns `prompt_ids` (#45449 behavior, pinned here by a test).
  - `ChatFormatter::encode_multimodal_request` returns the images; `encode_request` still refuses them.
- **Pixels.**
  - The MM worker runs `OpenCvImagePreprocessor` before the pipeline. It sits behind a new `sglang-server` feature, `deepseek-image`, because it links system OpenCV. Without the feature, a DeepSeek-V4.1 image model fails at launch.
  - Recipe resizes to `ImageTokenSpec::v41()` only: 14-pixel patches, 3x3 downsample, a 544*544 minimum area, 1024 tokens, no aspect limit. The launch gate refuses a config that changes any of these (e.g. `vision_max_n_token=128` through `--json-model-override-args`), and `RecipeImages::new` checks the same.

### Known differences from Python

- Python preprocesses V4.1 images with PIL, so pixels differ by design: recipe decodes with OpenCV and re-encodes to WebP. Token counts and model kwargs match. `processor-mm-parity` records the exception, and accuracy is the gate.
- Recipe rejects BMP; Python accepts it. Recipe also scales 16-bit images instead of clipping them.
- Request `detail` is not passed through yet; recipe's default (`high`) is used.
- Chat `usage` has no `prompt_tokens_details.image_tokens`; `prompt_tokens` matches.
- With the default `--tokenizer-worker-num 1`, long DeepSeek prompts encode one at a time, as every other model's prompts do on the tokenizer pool. Raise it for more encode parallelism.

## Tests

### Unit

- `cargo test -p sglang-processor` passes: the Qwen `mm_parity` fixtures are unchanged, and the render parity fixtures pass. Two unit tests cover the DeepSeek patch layout and the token budget.
- `cargo test -p sglang-server` passes (388 tests at this head, rebased onto `main` `911693e3f8`). Clippy is clean with and without `deepseek-image`, built against OpenCV 4.6. New tests:
  - `deepseek_encode_leaves_the_executor_free`. It fails when the encode runs inline.
  - `tokenize_returns_the_ids_a_deepseek_chat_submits`.
- Python: all of `test/registered/unit/multimodal/rust/` passes (Pillow 12.3). `test_rust_mm_gate` checks that non-default V4.1 geometry is refused. `qwen/test_e2e_parity.py` now takes the feature width from the spec's fields, because `RustMmSpec` no longer has `feature_dim`.

### End to end

The DeepSeek runs below were made before the rebase onto #45449 and have not been rerun. At this head, the Qwen path is rerun: Python vs Rust server, `/generate` 9/9 and chat 4/4 bit-identical, and `test_rust_native_mm_e2e.py` 4/4.

DeepSeek-V4.1-Flash (rev `314113f`) on 2x B300, the Python server vs the Rust server (`SGLANG_RUST_SERVER=1`, built with `deepseek-image`). Flags are the cookbook's B300 High-Throughput recipe at TP2/EP2 instead of TP4/EP4, with `SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1`, because only two GPUs were free:

```
--tp 2 --ep-size 2 --max-running-requests 256 --reasoning-parser auto --tool-call-parser auto
```

**Inputs.** On both servers, prompt token counts match for images of 10x10, 800x600, 1920x1080, 4000x300 and 300x4000 (190, 323, 974, 784, 872). `/tokenize` on `Explain <think> and <｜deepseek_image｜>` returns the same 16 ids on both. The original PR commit returned 10 ids there, including an image token.

**Accuracy.** Sampling is sgl-eval's `deepseek-ai/DeepSeek-V4.1-Flash` preset: temperature 1.0, top_p 0.95, thinking, reasoning effort high.

| Benchmark | Harness | Python | Rust |
|---|---|---|---|
| MMMU val (900) | `run_eval --eval-name mmmu`, max_tokens 32768 | 0.801 | 0.813, 0.827 |
| MMMU-Pro standard (1730) | `sgl-eval run mmmu_pro` 0.1.3 | 0.757 | 0.743 |
| MMMU-Pro vision (first 500) | `sgl-eval run mmmu_pro_vision` 0.1.3 | 0.714 | 0.746 |

- The two Rust MMMU runs differ by 1.4 points. The Python-Rust gaps are about that size, with no consistent sign.
- MMMU-Pro is capped at 65,536 tokens on Rust. Python ran uncapped; every Python sample that finished used under 60k tokens. The 3 + 7 Python samples still generating after 200k tokens were stopped and count as wrong, the same as a capped (truncated) answer. Rust truncated 2 + 8.

**HTTP executor under long prompts.** 16 concurrent chats of about 1.1M tokens each are encoded and then rejected for exceeding the context, so the model does no work. Meanwhile `/v1/models` is pinged every 50 ms:

| Build | `/v1/models` p99 | max | wall for the 16 encodes |
|---|---|---|---|
| original PR commit | 4527 ms | 4527 ms | 11.5 s |
| this PR | 3.4 ms | 57.6 ms | 31.8 s (one encode at a time, `--tokenizer-worker-num 1`) |

CI does not build `deepseek-image`.
