# [Fix] rust-server: Start a transfer backend's own KV bootstrap server on prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/46074) · state: closed · merged: True

## Original PR description

Stacked on https://github.com/sgl-project/sglang/pull/46066: this PR's base is that PR's branch until it lands, so the diff shown here is only this change. It builds on `rust_server_serves_kv_bootstrap`, which that PR adds.

## Motivation

In Python mode the `TokenizerManager` calls `start_disagg_service`, which on a prefill node brings up the transfer backend's KV bootstrap server. The Rust server starts no `TokenizerManager`. Its own api listener serves the HTTP registry, which covers every backend whose `BOOTSTRAP_SERVER` is a `CommonKVBootstrapServer`, but a backend with a bootstrap server of its own was left with nothing listening. The `PrefillBootstrapQueue`'s `KVManager` registers to the bootstrap server synchronously during scheduler init, and a failed registration only retries briefly before logging, after which no PD request can be routed to that prefill.

## Modifications

- `python/sglang/srt/managers/disagg_service.py`: add `start_disagg_service_for_rust_server()`. On a prefill node whose backend's bootstrap server is not a `CommonKVBootstrapServer` it starts that server via `start_disagg_service`; otherwise it returns `None`. The note on `maybe_create_ascend_config_store` now describes both shapes the bootstrap server can take in Rust mode.
- `python/sglang/srt/entrypoints/engine.py`: in Rust-server mode, call it from the main process at the point where the `TokenizerManager` would have started the server in Python mode: after the schedulers launch and before waiting for them to become ready, so the prefill ranks find it when they register. The handle is kept on `SchedulerInitResult.kv_bootstrap_server`.
- `python/sglang/srt/managers/scheduler.py`: the comment on the rust-server prefill path now covers both the embedded registry and a backend-owned bootstrap server. The code there is unchanged: only the ascend config store is still created in the scheduler.
- `test/registered/unit/entrypoints/test_rust_server_dp_ports.py`: the two bootstrap-server test doubles now assert which of them may be constructed, and a new parametrized test covers the three cases: an HTTP-registry backend starts nothing, a backend with its own bootstrap server is started on the configured host and port on prefill, and decode starts nothing.

Built-in backends (nixl, mooncake, mori, ascend) are unchanged: the Rust server keeps serving their registry on the api port.
