# [CI] cuda: Rebuild workspace crates when the shared Cargo target dir came from another rust/ tree

[Upstream PR](https://github.com/sgl-project/sglang/pull/45557) · state: closed · merged: True

## Original PR description

## Motivation

The router tier-3 e2e job sometimes fails to compile `sglang-server` against fields that exist on neither main nor the PR. Example: https://github.com/sgl-project/sglang/actions/runs/39561816910/job/119097657305 (`Fresh sglang-api-types` → `E0063 missing field prompt_token_ids`).

Cargo decides whether a path crate needs rebuilding by mtime only. `~/.cache/sglang-cargo-target` is shared by every runner container on a host, and they all check out at the same path. So when another branch builds after this job's checkout, its artifacts look fresh here and get linked. If cargo happens not to rebuild `sglang-server` either, the tests run another PR's binary.

## Modifications

`scripts/ci/cuda/ci_install_dependency.sh`: after a successful build, record the `rust/` tree hash in the target dir. Before the next build, if the recorded hash doesn't match, touch the tracked `rust/` files so the workspace crates rebuild. Registry crates stay cached. The record is cleared before each build, so a failed build never leaves a valid one.

## Tests

Local repro: two trees at the same path share one `CARGO_TARGET_DIR`.
- Without the fix, I get the CI error.
- With the fix, jobs B, A, A, B2 (same tree as B), B produce rebuild, rebuild, reuse, rebuild, reuse. All correct.
