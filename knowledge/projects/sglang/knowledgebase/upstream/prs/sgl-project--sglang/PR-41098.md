# [DSV4.1] Add H20 block-FP8 tuned configs

[Upstream PR](https://github.com/sgl-project/sglang/pull/41098) · state: open · merged: False

## Original PR description



## Motivation

DeepSeek-V4.1-Flash TP8 has block `[32, 32]` FP8 linear shapes without
device-specific configs for `NVIDIA_H20-3e`, so these shapes use the default
Triton configuration. The Hopper kernel and its `SWAP_AB`/`SPLIT_K` dispatch
already exist from #39657; this PR adds H20-3e tuning data for that path.

## Modifications

Add six `NVIDIA_H20-3e`, `fp8_w8a8`, block `[32, 32]` config files:

- `N=1792,K=5120`
- `N=4096,K=1280`
- `N=5120,K=1024`
- `N=576,K=5120`
- `N=5120,K=288`
- `N=25600,K=6144`

Each file contains tuned M entries from 1 through 8192, covering the six
observed DeepSeek-V4.1-Flash TP8 linear shapes on H20-3e. This does not claim
coverage for other H20 product names, TP layouts, or matrix shapes.

No runtime kernel or model code is changed.

## Accuracy Tests

Validated the production JSON lookup and matmul entry with six representative
checkpoint weights and M in `{6, 12, 24}`:

- 18/18 eager cases passed against an FP32 dequantized reference
  (`relative_l2 <= 0.005`, `normalized_max_abs <= 0.01`).
- Maximum relative L2: `0.0016961`.
- Maximum normalized maximum absolute error: `0.0035183`.
- CUDA Graph replay was bitwise equal to eager in 18/18 cases.
- After changing activation values, replay was bitwise equal to the new eager
  result in 18/18 cases.

Split-K changes the FP32 accumulation tree and can change low BF16 bits, as
documented for the existing Hopper path. These tolerance and replay checks are
the numerical correctness evidence.

## Speed Tests and Profiling

The six configs improved activation-quantization plus GEMM time in all 18
M=6/12/24 microbenchmark cases, by `1.22x`–`6.91x`.

For end-to-end A/B, both phases used the same 8x H20-3e host and byte-identical
server argv: DeepSeek-V4.1-Flash, TP8/EP1, DSV4 attention, Humming MoE, DSPARK
block size 5, decoder bounded replay, decode CUDA Graph max batch size 64, and
radix cache disabled. The only intended difference was removing or restoring
the six config files. Both phases took the same FlashInfer all-reduce workspace
fallback on all eight ranks.

Workload: fixed 8192 input tokens and 500 output tokens, `random-ids`, seed 42,
temperature 0, one warmup, and ten measured requests.

| CC | Config | Mean TTFT (ms) | Mean TPOT (ms/token) | Output throughput (token/s) | Measured-request accept length |
|---:|---|---:|---:|---:|---:|
| 1 | default | 729.499 | 6.481 | 126.000 | 3.577 |
| 1 | tuned | 617.408 | 5.094 | 158.062 | 3.522 |
| 2 | default | 889.621 | 8.921 | 186.481 | 3.827 |
| 2 | tuned | 750.397 | 7.670 | 214.369 | 3.700 |

At CC1, TTFT decreased 15.37%, TPOT decreased 21.41%, and output throughput
increased 25.45%. At CC2, TTFT decreased 15.65%, TPOT decreased 14.02%, and
output throughput increased 14.95%.

All four cases completed 10/10 requests with the requested token counts and no
errors. Prompt hashes matched pairwise. The measured-request speculative accept
length decreased slightly, so the latency gain is not explained by increased
DSPARK acceptance. This is one sequential A/B run with ten requests per case;
it does not claim the same gain for every input length and concurrency.
