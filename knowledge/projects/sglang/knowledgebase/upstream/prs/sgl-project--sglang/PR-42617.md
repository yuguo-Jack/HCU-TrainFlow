# [Rust] Skip text decoding for token-only gRPC output

[Upstream PR](https://github.com/sgl-project/sglang/pull/42617) · state: open · merged: False

## Original PR description

Skip unused text decoding for token-only gRPC generation. Also avoid unused stream decoders for control requests, one-shot detokenization, and health probes.

CPU-mock results with the same enlarged response queue in both builds:

- **Throughput: +10.9%** (819k → 909k tokens/s).
- **Frontend CPU per token: −9.6%** (6.893 → 6.230 µs).

Validation: 336 server tests pass; formatting, Clippy with warnings denied, and the diff check pass.

### inline_comments

- jthomson04 · comment · 2026-10-05T17:50:15Z · [source](https://github.com/sgl-project/sglang/pull/42617#discussion_r4187038001)

File: `rust/sglang-server/src/tokenizer_manager/to_scheduler.rs` · line None

Nothing tests this passthrough. The new detokenizer test builds `DetokState` by hand and calls `new_decoder` directly, and the gRPC tests only assert `output_mode` on the intake request. If this arm regressed to `Default::default()`, every gRPC `generate` would quietly go back to minting and stepping a `DecodeStream`, and the suite would still pass. `to_scheduler_tests.rs` already matches `DetokMsg::Register { rid, .. }` in several places (e.g. L397); one of those could also assert `output_mode` for a `TokenIds` generate request.

A smaller gap of the same kind: the detokenizer test only covers a final chunk with a matched stop *token*. It doesn't exercise an intermediate (non-final) chunk or a `Matched::Str` stop in `TokenIds` mode.

- jthomson04 · comment · 2026-10-05T17:50:15Z · [source](https://github.com/sgl-project/sglang/pull/42617#discussion_r4187038016)

File: `rust/sglang-server/src/tokenizer_manager/to_scheduler.rs` · line None

Two things about this inline match:

1. It matches `req.kind` again, a few lines after the exhaustive tuple match at L347, and uses `_`. If a new `RequestKind` variant is added, L347 stops compiling but this arm silently picks `TextAndTokenIds`.
2. `Control` and `Detokenize` fall through to `TextAndTokenIds`, so the shard still mints a `DecodeStream` for every `/server_info`, internal-state, and completions-echo request. Those are answered by `handle_result` / `handle_decode`, which never touch `st.decoder`.

Folding this into the existing match fixes both:

```rust
let (decode_logprob_text, no_stop_trim, output_mode) = match &req.kind {
    RequestKind::Generate(g) => (
        g.return_text_in_logprobs.unwrap_or(false),
        g.sampling_params.no_stop_trim,
        g.output_mode,
    ),
    // Answered via `handle_result` / `handle_decode`; never read the per-request decoder.
    RequestKind::Control(_) | RequestKind::Detokenize { .. } => {
        (false, false, OutputMode::TokenIds)
    }
};
```

and then just `output_mode,` in the `Register` literal.

This comment was updated, but two others still describe `decoder == None` as meaning skip mode only:
