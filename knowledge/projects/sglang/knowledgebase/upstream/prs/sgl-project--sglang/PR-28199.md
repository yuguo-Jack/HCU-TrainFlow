# fix(lora): support Gemma 4 native LoRA adapters without v_proj weights

[Upstream PR](https://github.com/sgl-project/sglang/pull/28199) · state: open · merged: False

## Original PR description


## Motivation

Fixes #25913.

Loading a PEFT LoRA adapter trained against `google/gemma-4-E2B-it` via `--lora-paths` fails before `/model_info` readiness when the adapter's KV-sharing layers carry `q_proj`/`k_proj`/`o_proj` weights but omit `v_proj`:

```
RuntimeError: Failed to load LoRA adapter ticket-triage: 'base_model.model.model.language_model.layers.15.self_attn.v_proj.lora_A.weight'
```

The root cause is in `LoRAAdapter.normalize_qkv_proj()`. It already zero-filled a missing `k_proj`, but still unconditionally read and popped `v_proj`, so a missing V branch raises a `KeyError`. Reproducing the load on a real Gemma 4 E2B server then surfaces two adjacent native-LoRA gaps that block the same adapter (vision/audio tower wrapping, and wrong per-layer LoRA buffer dims).

## Modifications

- `python/sglang/srt/lora/lora.py`: make qkv normalization symmetric. A missing `k_proj` is zero-filled from `v_proj` when available, otherwise from `q_proj`; a missing `v_proj` is zero-filled from the resolved `k_proj`; and each branch is only popped from the tensor map when it actually existed.
- `python/sglang/srt/lora/lora_manager.py`: honor `base_model.should_apply_lora(module_name)` in `init_lora_modules()`. This fills in the gate that `init_lora_modules` already referenced in a comment ("... before the should_apply_lora gate, since VL models' should_apply_lora patterns only match language ...") but never actually called, so the method was dead on every model defining it. It is a purely additive skip-only filter: each implementation is a name filter excluding the model's own non-language towers (`qwen2_vl`/`ernie45_vl` skip the `visual`/`vision_model` prefix; `qwen3_vl`/`qwen3_vl_moe`/`qwen2_5_vl`/`mllama4`/`phi4mm`/`gpt_oss`/`qwen3_5`/`gemma3_mm`/`gemma3n_mm`/`gemma4_mm` match a language-tower regex), so a language-only adapter is unaffected (no-op).
- `python/sglang/srt/models/gemma4_mm.py`: derive Gemma 4 multimodal LoRA buffer dims from the text config per layer in `get_hidden_dim()`: `full_attention` layers use `global_head_dim` (512), sliding layers use `swa_head_dim`/`head_dim` (256), and the trailing `num_kv_shared_layers` use the double-wide MLP size. The previous code read these off the top-level multimodal config (which does not carry `intermediate_size`) and asserted a uniform list, allocating wrong shapes and tripping a request-time `o_proj` shape assertion. Also drops a duplicate `get_embed_and_head()` that was shadowed by the later PP-aware definition and dead.

## Code Review

This pull request introduces support for Gemma 4 multimodal LoRA configurations, updates QKV normalization to handle missing projection branches by zero-filling them, and adds a `should_apply_lora` check during module initialization. It also includes comprehensive unit tests for these changes. - anshulkulhari7 · COMMENTED · 2026-06-20T13:12:13Z · [source](https://github.com/sgl-project/sglang/pull/28199#pullrequestreview-4537620182)

Thanks for this — it's a careful, well-targeted fix, and the LoRA-side reasoning is genuinely subtle and correct. I read through the diff against `main` (`9bb9d17`) and traced the buffer/slice paths; my overall take is **approve-with-nits**: the core fix is right, the regression test locks in the important case, and the only thing actually keeping it red is a missing CI label, not the code. One real latent correctness gap on a Gemma-4 variant is worth a look but doesn't block the reported #25913 case.

### `python/sglang/srt/lora/lora.py` — the GQA KV zero-fill is exactly right

The both-missing KV-width derivation in `_zero_fill_kv_branch` is subtle but correct. A `q_proj` `lora_B` has out-dim `num_attention_heads * head_dim`, so `q_weight.shape[0] // num_heads` recovers `head_dim` and `* num_kv_heads` gives `num_kv_heads * head_dim` — the true K/V projection width. Deriving `head_dim` from the actual tensor shape rather than a config field is the right call for Gemma, where `head_dim * num_heads != hidden_size` (`head_dim=256`). The `"lora_B" not in weight_name -> zeros_like(q)` short-circuit is also correct, since q/k/v `lora_A` are all `(r, hidden_size)` and thus shape-identical regardless of GQA, and the `num_heads == num_kv_heads` MHA fast-path is correct (KV width == Q width there). This properly addresses the gemini-code-assist GQA concern for the q_proj-only / both-KV-missing case, and `test_missing_k_and_v_use_kv_width_for_lora_b_under_gqa` asserts the V slice is zero at the KV width — which would fail if q's wider output were used — so it actually locks the behavior in. The rewritten `normalize_qkv_proj` (popping k/v only when present, reusing v's shape for missing-k and `zeros_like(k_proj_weight)` for missing-v) is clean and the three test cases cover all three branches.

### `python/sglang/srt/lora/lora_manager.py` — load-bearing dead-gate fix

This is the quiet but important one. On `main`, `should_apply_lora` is defined on 13 model classes (the VL/audio multimodal models) but has **zero call sites** — the only non-`def` references are the comment at lines 776-778, which already says "before the should_apply_lora gate" even though no gate existed yet. So the method was dead, and every module whose leaf name matched `target_modules` (including vision/audio tower projections) was being wrapped as a LoRA layer. Wiring it via `getattr(self.base_model, "should_apply_lora", None)` is exactly right: text-only models that don't define it get a clean `None` no-op, and the gate is strictly skip-only so it can never wrongly *include* a module. I confirmed the gemma4 `lora_pattern` is anchored on `^language_model\.layers\.`, so `language_model.layers.N.self_attn.qkv_proj` matches while `vision_tower`/`audio_tower`/`embed_vision`/`embed_audio` prefixes don't — towers correctly excluded. Nice catch.

One test-gap note (non-blocking): this gate is now the behavioral core of the lora_manager change, but the new CPU test only exercises `normalize_qkv_proj` and `get_hidden_dim` — nothing touches `init_lora_modules`, and the tower-exclusion is validated only by the single gemma4 E2E run in the description. If it's feasible without a real module map, a small unit test stubbing a `base_model` whose `should_apply_lora` returns `False` for a `vision_tower.*` name and `True` for a `language_model.layers.N.self_attn.qkv_proj` name (then asserting `init_lora_modules` skips the former) would lock the regression in.

### `python/sglang/srt/models/gemma4_mm.py` — root-cause fix is right; one asymmetric-KV gap

Routing `get_hidden_dim` through `get_text_config()` is the right root-cause fix: it reads dims from the same normalized `text_config` that the config normalization mutates (swapping in `global_head_dim` for full-attention, planting `swa_head_dim`) and that the actual `Gemma4TextModel` is built from — instead of the top-level `Gemma4Config` that lacks `intermediate_size` and the per-layer attn dims. The per-layer `head_dim` split (global vs `swa_head_dim`) and the double-wide-MLP tail are handled correctly.

One real latent gap worth a look: `get_hidden_dim` now picks `head_dim` per layer, but the `qkv_proj` branch still uses the **global** `text_config.num_key_value_heads` for *every* layer. The base `qkv_proj` layer uses `swa_num_key_value_heads` on sliding layers (`gemma4_causal.py:308`), and these two diverge whenever `num_global_key_value_heads` is set (`hf_transformers/config.py:167-179`: `num_key_value_heads` becomes the global count, `swa_num_key_value_heads` keeps the raw/sliding count). The LoRA-B buffer is allocated per layer from this `output_dim`, and `slice_lora_b_weights` then slices using the base layer's per-layer KV shard size — so on a Gemma-4 variant where `num_global_key_value_heads != num_key_value_heads`, the sliding-layer qkv buffer width won't match `q + 2*kv` and you'd get a shape error at load. The fix is currently asymmetric: per-layer for `head_dim`, global for the KV-head count. Suggest mirroring the model in the non-`full_attention` branch: `num_kv_heads = getattr(text_config, "swa_num_key_value_heads", text_config.num_key_value_heads)`. This is latent on E2B (equal global/swa KV counts, which is why E2E passes), and the new test uses `num_key_value_heads=1` for both layers so it doesn't exercise it. (`o_proj` is fine since it uses `num_attention_heads`, which is constant across layers.)

Under Grouped Query Attention (GQA), the output dimension of q_proj is different from k_proj and v_proj. If both k_proj and v_proj are missing from the adapter, falling back to weights[q_name] for zero-filling will produce weights with the wrong shape (matching Q instead of KV), leading to shape mismatches and runtime errors. We should compute the correct KV output dimension using the base model's attention configuration when lora_B is being normalized.

```python
                if "k_proj" in target_module:\n                    k_proj_weight = weights[k_name]\n                elif "v_proj" in target_module:\n                    k_proj_weight = torch.zeros_like(weights[v_name])\n                else:\n                    num_heads = getattr(self.base_hf_config, "num_attention_heads", 1) if self is not None and hasattr(self, "base_hf_config") else 1\n                    num_kv_heads = getattr(self.base_hf_config, "num_key_value_heads", num_heads) if self is not None and hasattr(self, "base_hf_config") else 1\n                    if "lora_B" in weight_name and num_heads != num_kv_heads:\n                        hidden_size = getattr(self.base_hf_config, "hidden_size", 1)\n                        head_dim = getattr(self.base_hf_config, "head_dim", hidden_size // num_heads)\n                        k_proj_weight = torch.zeros(\n                            (num_kv_heads * head_dim, weights[q_name].shape[1]),\n                            dtype=weights[q_name].dtype,\n                            device=weights[q_name].device,\n                        )\n                    else:\n                        k_proj_weight = torch.zeros_like(weights[q_name])
```

The should_apply_lora gate will filter out FusedMoE layers because their module names (e.g., ending in .mlp) do not match the standard projection suffixes expected by should_apply_lora (which expects qkv_proj, o_proj, down_proj, or gate_up_proj). This will cause LoRA to be completely skipped for MoE layers on MoE models. We should handle FusedMoE specifically by checking if its constituent projections (gate_up_proj or down_proj) should have LoRA applied.

```python
            should_apply_lora = getattr(self.base_model, "should_apply_lora", None)\n            if should_apply_lora is not None:\n                if isinstance(module, FusedMoE):\n                    if not (should_apply_lora(f"{module_name}.gate_up_proj") or should_apply_lora(f"{module_name}.down_proj")):\n                        continue\n                elif not should_apply_lora(module_name):\n                    continue
```
