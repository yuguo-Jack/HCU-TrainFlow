# [Feat] sgl-router: Confirmed-first pending prefixes for cold prompts, with a follower cap

[Upstream PR](https://github.com/sgl-project/sglang/pull/46505) · state: closed · merged: True

## Original PR description

## Motivation

`--cache-pending-prefix-ttl-ms` credits a worker with a prompt's prefix until the engine's KV events confirm it, so a burst sharing a cold prefix lands together. Running it on a PD endpoint serving agent traffic (median prompt ~100k tokens, 8 prefill DP ranks) showed three problems with how the radix-tree prefix provider used it:

1. A pending stake was merged with the confirmed depths by plain max, so a stake could override a KV-event match on another worker that was just as deep.
2. The pending store was walked, and every routed request wrote its stake under the store's write lock, on every request. A turn whose history the events had already confirmed paid both for nothing: router-minus-engine TTFT at p50 rose from +200 ms with the tier off to +271 ms with it on.
3. Nothing bounded how many requests one stake could attract, so a runaway fan-out on one cold prefix could pile onto a single worker with no way to let the load policy spread it.

## Changes

Both additions are opt-in. With neither new flag set, pending prefixes behave exactly as before: the pending store is walked on every request, its depths merge with the confirmed ones by maximum, and every request stakes.

- **Confirmed-first mode**, `--cache-pending-prefix-consult-below <ratio>`. A pending stake is consulted only when it is strictly deeper than the best confirmed match anywhere, so a KV-event match that is at least as good always decides the lookup, and the pending store is walked and staked only while the confirmed match covers less than `ratio` of the prompt. A warm turn routes on its confirmed history and pays nothing for the tier; its next turn matches the same history, so it needs no stake. A first turn, or a turn racing its predecessor's events, still consults and stakes. With the switch at 0.5, router-minus-engine TTFT at p50 was +175 ms with the tier on, below the +200 ms measured with it off, and the tier kept its cache-hit gain (its follows per window were unchanged).
- **Follower cap.** `--cache-pending-prefix-max-followers` (default 0, unbounded) bounds how many requests one stake may attract within its TTL. The confirmed tree is always looked up first, in both modes; past the cap the stake is simply hidden, so the request is routed as if it did not exist, by its confirmed matches or else by the load policy. The charge and the check use the deepest block the prompt matched, not the first: the first block is the shared system prompt, and charging it capped every conversation on the worker at once (an earlier iteration did exactly that, visible as capped lookups outnumbering follows 13:1). A conversation keeps following its own stake since each turn stakes a new tail. On that endpoint a cap of 8 or 32 cost ~1.5 points of engine cache hit, because prefill serves a same-prefix burst from cache once its first member has landed, so the doc recommends it only as a safety valve.

`PrefixLookupResult` gains `pending_winners`, the workers whose reported depth came from a stake; `record_route` charges the stake when the placement followed it.

## Flags

| flag | default | meaning |
|---|---|---|
| `--cache-pending-prefix-consult-below <ratio>` | unset (original merge) | confirmed-first mode: a stake counts only where strictly deeper than the confirmed match (each stake on its own: a stake no deeper than that match is never a candidate, even beside one that is), and the store is consulted and staked only while the confirmed match covers less than this share of the prompt; above 0 and at most 1; 1 = consult on every request but keep the strictly-deeper rule; 0 is rejected since it would never consult the tier (unset the TTL flag to switch it off); 0.5 is a good starting point |
| `--cache-pending-prefix-max-followers <N>` | 0 (unbounded) | requests one stake may attract within its TTL |

Both require `--cache-pending-prefix-ttl-ms`.

## Metrics

- `sgl_router_cache_pending_prefix_followed_total`: requests routed to a worker because of its pending stake.
- `sgl_router_cache_pending_prefix_capped_total`: prefix lookups the cap left without a pending candidate.

`REFERENCE.md` (Pending prefixes) and `monitoring/README.md` are updated.

## Tests

- `state::kv_events::prefix_provider`: confirmed match wins over a shallower or equal stake; a deeper stake is consulted and reported as a pending winner; only the strictly deeper stakes join the candidates (an equal or shallower stake beside a deeper one does not), while without the switch every stake merges; the cap falls back to the confirmed tree and the worker returns once its events arrive; routing to a confirmed worker is never a follow; a warm prompt skips the tier and writes no stake; a cold prompt below the gate still uses the stake; without the switch, pending merges by maximum as before and every request stakes.
- `state::kv_events::pending`: the cap hides a stake and counts only the lookup it left with no candidate; the cap is charged on the deepest block, not the shared prefix; a follow charges the deepest *live* record, the one the lookup reported, and a stake that expired starts its follower count over when it is re-staked; no cap by default.
- `config::cli`: both flags default, parse and validate (range: 0, NaN and 1.5 are rejected; dependency on the TTL flag).
- Differential check against the merge base: a scratch harness driving the provider and the pending store through 240 random scenarios (14,370 lookups) dumps byte-identical results with both flags unset; with the flags on, 1,400 scenarios match an independent model for matches, pending winners, stake writes, hits, follows and cap visibility.

Run locally with `cargo check --locked --workspace --all-targets`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `cargo +nightly fmt --all -- --check`, and `cargo test --locked --lib -- pending prefix_provider policies config::cli kv_events`.
