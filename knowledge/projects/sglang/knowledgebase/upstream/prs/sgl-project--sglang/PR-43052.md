# [Speculative] Add draft sampling overrides and retain corrected proposal probabilities

[Upstream PR](https://github.com/sgl-project/sglang/pull/43052) · state: open · merged: False

## Original PR description

## Motivation

Stochastic draft proposals need their own sampling controls, and verification must use the exact distribution each proposal was drawn from. EAGLE and DSpark drafted at the request's temperature only, and the DFlash2 selector and LiLiCorr walks had no way to sharpen or flatten their proposals.

## Modifications

- Add `--speculative-draft-temperature`, `--speculative-draft-top-k` and `--speculative-draft-top-p`. Unset, the draft samples at the request's temperature with no cutoff, as before: the default path runs no top-k/top-p kernel, and a disabling value (`-1`, `1`) reads as unset. Draft temperature `0` makes proposals greedy; greedy requests always draft greedily.
- `srt/sampling/draft_sampling.py`: `DraftSamplingParams` carries the per-request draft policy plus the server's static apply flags; `build_draft_probs` returns q = softmax(logits / T) with top-k then top-p applied only when set. Rejection sampling stays unbiased for any q as long as verification uses the q the proposal was drawn from.
- `kernels/ops/sampling`: `top_k_renorm_probs` / `top_p_renorm_probs` now carry three registered backends, the sgl_kernel AOT op on CUDA, the Triton port on ROCm, and a graph-safe torch reference with FlashInfer's tie semantics on CPU and for NPU rows the vendor path declines, selected by the kernel registry's capability filter. MUSA and XPU keep a direct sgl_kernel call until `DeviceType` grows those members. Draft proposals and EAGLE/DFlash target verification share that one path; the per-file import chains are gone.
- EAGLE/EAGLE3/MTP rejection sampling uses it in prefill, eager decode, per-step and single CUDA graphs. The draft graph runner stages temperature/top-k/top-p and the overrides resolve inside the graph.
- DSpark keeps the fused `MarkovSampleStep` draft on the default path. A temperature override feeds that kernel, and draft temperature 0 maps to the argmax draft. A top-k/top-p override makes each step argmax in-kernel and redraw the sampling rows from the cut-off q built from the kept step logits; verification and the accept estimator rebuild that same q from `corrected_logits`, so no q buffer is retained.
- DFlash2 selector and sampled LiLiCorr apply the policy to each corrected conditional over the K candidates; top-k cannot add tokens. The walk kernel takes q only, with greedy rows one-hot.
- Plain DFlash, Domino, unsampled LiLiCorr and EAGLE tree search are unchanged.

## Accuracy Tests

- CPU (macOS ARM64, Python 3.12, PyTorch 2.14.1): **82 passed** across the draft-sampling, DSpark override, DSpark draft block and accept, DFlash selector, EAGLE graph runner, spec registry and server-args docs coverage suites. The full `test/registered/unit/spec`, `test/registered/spec/dspark` and `test/registered/unit/server_args` directories: **810 passed**; every remaining failure (CUDA-only kernels, `tvm_ffi`, grpc) fails identically on main in this environment.
- GPU tests are added or updated but **not yet run**: target/draft cutoff parity, CUDA graph replay with changing parameters, the DSpark draft graph, and the selector/LiLiCorr Triton walk.
- ruff (lint and format), isort and codespell pass on the changed files.

## Speed Tests and Profiling

Pending GPU validation; this PR is a draft. With no draft option set, no renorm kernel runs and DSpark's fused draft kernel is untouched. With a cutoff set, each draft step adds a top-k and/or top-p renormalization pass over the draft support, and DSpark additionally moves its sampling out of the fused kernel; that opt-in cost is what needs measuring against the acceptance-length gain.
