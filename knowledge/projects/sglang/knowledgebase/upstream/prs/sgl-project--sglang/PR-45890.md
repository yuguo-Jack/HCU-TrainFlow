# [Fix] [AMD] dsa: Precompile BF16 sparse MLA splits during warmup

[Upstream PR](https://github.com/sgl-project/sglang/pull/45890) · state: open · merged: False

## Original PR description

## Motivation

ROCm BF16 sparse MLA selects `inner_iter` from the current query length. The query length itself is dynamic, but `inner_iter` and the corresponding combine group count specialize two TileLang kernels. Normal startup and workload warmup can therefore miss an intermediate split and compile it while serving requests.

In a four-node GLM-5.3 TP8/PP4 run, an unseen `inner_iter=4` triggered 64 native builds (partial + combine on 32 workers). Compilation progressed through the four pipeline stages, taking 44.294 seconds from the first stage's start to the last stage's completion and producing large TTFT outliers.

## Modifications

- Add a cached helper that prepares both BF16 partial and combine kernels for every split reachable by the existing selector.
- Invoke it on the first ROCm BF16 sparse-attention forward, using the actual model dimensions, attention scale, block size, and thread count. Normal server warmup can then populate the variants before serving traffic.
- Follow the selector's halving sequence and divisibility check, including padded top-k sizes that are not powers of two.
- Add regression coverage for split coverage, cache keys/reuse, numerical results across query lengths, and graph capture/replay.

Kernel definitions, attention math, runtime split selection, FP8 paths, and NVIDIA BF16 dispatch are unchanged. This moves compilation work to the first forward; it does not remove that work. If startup warmup is disabled, the first actual forward pays the preparation cost. Persisting `TILELANG_CACHE_DIR` helps subsequent process/container starts.

## Accuracy Tests

Passed all three new regression tests in 74.403 seconds on one gfx950 GPU:

```bash
python3 test/registered/kernels/ops/attention/test_tilelang_dsa_precompile.py -v
```

The validation overlaid this PR's attention module and new test onto the previously tested ROCm image (`lmsysorg/sglang-rocm@sha256:3c01f73fe23aebf4a8853de0899a70b75c2af6c0409d2331353847aac4d3f906`). This validates the new attention code with that image's dependencies, not a full installation of current upstream SGLang.

- Selector coverage includes both ROCm block-size configurations and eight top-k sizes, including non-power-of-two tile counts.
- After a single-token warmup, query lengths 31, 32, 63, 64, 127, 128, 255, 256, 511, and 512 match a PyTorch reference while a guard rejects any new TileLang JIT lookup. Covers `(d_v, tail_dim, topk) = (512, 64, 2048)` and `(256, 0, 2112)` with masked padding.
- GPU graph capture/replay passes without new JIT lookups.
- Cache reuse and distinct model-parameter keys pass.
- All applicable pre-commit hooks pass for both changed files. Existing kernel definitions and `_pick_inner_iter` are also AST-identical to the base.

The earlier full-model investigation also passed 12 arithmetic smoke checks and completed 2,176 measured requests with zero request errors. These are smoke checks, not an accuracy-benchmark claim.

## Speed Tests and Profiling

The following end-to-end measurements are from the **earlier experimental implementation** on SGLang `0e756912eb3cd8f531f95c17299485b9312b2534`, not a full-server benchmark of this port to current main. The upstream version additionally handles non-power-of-two top-k and enables preparation directly in the BF16 path; experiment-only tracing and client timing hooks are omitted.

Configuration: `zai-org/GLM-5.3`, FP8 weights / BF16 KV, four nodes with eight gfx950 GPUs each, TP8/PP4, input/output lengths 1024/256, concurrency 32, 128 requests per full run, server/client seed 42. Each phase retained the same 32-request workload warmup. The three phases below used the same hosts and pipeline placement.

| Phase | Full runs | Mean TTFT (ms) | Aggregate output tokens/s | Native TileLang builds during measurement |
| --- | ---: | ---: | ---: | ---: |
| Develop RCCL, diagnostic baseline | 1 | 3751.32 | 429.81 | 64 |
| Develop RCCL, precompile | 3 | 851.91 | 1009.34 | 0 |
| Bundled RCCL, precompile | 3 | 857.31 | 1002.44 | 0 |

The first fixed develop run measured 886.54 ms TTFT; the three-run average includes that first run. Across ten fixed full workloads, including cached restart and alternate-seed validation, there were no requests with TTFT above five seconds and no timed TileLang lookups/builds. Cold-cache preparation took 55–58 seconds per worker; loading the prepared family after a cached restart took 6.73–8.94 seconds per worker. These are helper times, not total startup times or measured incremental startup overhead.

Matched unpatched repetitions with the two RCCL versions gave almost identical first-run TTFT (3717.07 vs. 3717.98 ms), and warmed repetitions averaged 825.94 vs. 830.03 ms. The observed large stall was first-use compilation; these measurements do not establish a steady-state RCCL regression.

Keep this PR in **draft** pending review and full-model validation of the current upstream integration. The recorded end-to-end performance improvement applies to the tested gfx950/BF16 workload.
