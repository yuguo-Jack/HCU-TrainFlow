# [CI] lora: Simplify LoRA tests and add a lora rerun group

[Upstream PR](https://github.com/sgl-project/sglang/pull/45981) · state: closed · merged: True

## Original PR description

## Motivation
The LoRA tests had grown into a matrix of model runs, second-backend arms, loud startup validators and shape snapshots that cost per-PR GPU time without guarding anything a silent failure could slip through, and there was no single command to run them. This PR applies one rule to every LoRA test — a test stays in per-PR CI only if its removal could let a silent failure through (wrong weights, routing, slot or graph buffer with no error); matrices, second-backend arms, perf and loud startup checks move to the nightly or weekly suites, duplicates go — and adds a `lora` rerun group so a LoRA change can be validated with `/run-cpu-ci` + `/rerun-group lora`. Since LoRA code changes are rare, the per-PR tier keeps only four GPU canaries plus the CPU units and the path-gated kernel lane; every other LoRA GPU test runs through the nightly suites, whose schedule fires about every other day (`0 14 */2 * *`), so a regression from an unrelated PR shows up on the next nightly run that completes, not before merge. Main's CUDA re-tier (#47619) put the LoRA e2e tests in extra and the gpt-oss-20b case in weekly; this PR takes the LoRA e2e tests one tier further (nightly), keeps `test_lora_tp` per PR as a 2-GPU canary, and leaves the gpt-oss-20b case in weekly. The numbers below are registered seconds (GPU-weighted where noted), not PR wall time or cost.

By registration (`est_time` summed over the LoRA tests, weighted by the runner's GPU count; the same files on main at their old paths):

| Tier | main (106 files, at b80178734d) | this PR (112 files) |
|---|---|---|
| per PR (including the path-gated kernel lane) | 3,103 s registered / 2,861 GPU-weighted, 76 registrations | 1,642 s / 1,948, 75 registrations |
| extra (label-gated, also main twice a day) | 2,070 s / 4,709, 14 | none |
| nightly (main every two days) | 584 s / 1,301, 6 | 2,997 s / 4,714, 30 |
| weekly | 2,712 s / 18,518, 9 | 2,562 s / 18,338, 11 |

(The 112 files are the LoRA tests this PR touches or groups: the 110 members of the `lora` rerun group plus the two weekly 8×B200 giant-model tests it leaves out; 17 of them are tests outside the LoRA directories with LoRA-named cases, unchanged by this PR, so they add the same time to both columns.)

Per-PR LoRA registered GPU-seconds drop by a third (2,861 → 1,948) on top of #47619, which had already moved four LoRA e2e tests from the per-PR tier to extra and the gpt-oss-20b case to weekly; 1,188 of the remaining 1,948 is the kernel-unit lane, which runs only on PRs that touch kernel paths and on main's scheduled runs (twice a day). What runs on every PR is the MoE LoRA engine under prefill and decode graphs (`csgmv` and `triton_v2`, compared with the same engine run eagerly), multi-adapter dense batches on the default `csgmv` backend compared with HF row by row (`torch_native` attention, graphs and radix cache off, no overlap loading), LoRA with EAGLE, LoRA at TP=2, and four small 5090 units; the kernel lane gained witnesses for the FP8 MoE runner under graph replay and the Blackwell execution of the MoE runner numerics. Graph-versus-eager comparisons are not an independent model reference: a loading or scaling error shared by both paths would pass them, and the independent MoE reference (the vLLM parity test) now runs nightly.

5. **`test: widen the decode tolerance of the RuterNorway LoRA case to 0.3`** — `test_lora_tp_overlap_loading` fails on 2×H100 at one decode position where HF fp16 generate and SGLang fp16 TP2 differ by 0.140 against the 0.1 bound. Against an fp32 HF+PEFT reference, HF fp16 deviates by about +0.080 and SGLang by about −0.060 at that token; without the adapter every pipeline is within 0.03. This adapter's LoRA deltas are as large as the base q/v projections (delta/base RMS up to 1.68), so fp16 tail logprobs move with the execution path (GPU, TP, CUDA graph vs eager, attention kernel), while overlap loading and the LoRA backends change nothing; main's own `test_lora_tp.py` overlap arm fails identically on 2×H100. 0.3 covers the observed paths (a measured TP1 path would be about 0.234) and still rejects a dropped adapter (2.1–8.4 nats at that position). Only `run_lora_test_one_by_one` reads the per-adaptor decode tolerance.
6. **`ci: add a lora /rerun-group group`** — every test whose subject is LoRA across all tiers: the LoRA directories (including main's new `unit/lora/test_lora_drainer` and `unit/lora/test_lora_pp`), the LoRA tests parked elsewhere, and the registered tests with a LoRA-named case (adapter counters, `lora_path` normalization, LoRA slots in scheduling, the LoRA name table and KV-event adapter names, `LoRARef` serialization, LoRA forward domains, the deferred all-reduce under LoRA, the LoRA gate/up wrapper in the fused dual GEMM, weight reload through `FusedMoEWithLoRA`, the Inkling LoRA layout, model LoRA hooks, the `after_down` hook, the LoRA top-k unpack): 110 members, 114 runs across 6 pools (files with an H100 and a B200 registration run on both). 7. **`ci: keep four LoRA canaries per PR and move the other LoRA GPU tests to nightly`** — per PR: `test_lora_moe_prefill_cuda_graph`, `test_multi_lora_backend`, `test_lora_spec_decoding`, `test_lora_tp` and four 5090 units (under a minute together); the other 24 per-PR and extra LoRA GPU registrations become `stage="nightly"` on their pool with `est_time` and `runner_config` kept (the five 5090 files stay on `1-gpu-small`, a row the nightly workflow has had since #47619); the gpt-oss-20b case stays in weekly, and the Nemotron-120B and LoRA-latency cases were already nightly on main after #47619; the moved files' docstrings and comments say nightly. Ordinary per-PR LoRA registrations outside the kernel-unit lane go from 1,416 to 760 GPU-weighted seconds, extra from 2,757 GPU-seconds (every labelled PR and twice a day on main) to none; per run the nightly suites gain 1,387 registered seconds on H100, 246 on the 5090, 670 on 2×H100 (1,340 GPU-weighted) and 110 on 4×H100 (440 GPU-weighted), and 4×B200 is unchanged. What a non-LoRA PR can now break without failing its own CI, found only on the next completed nightly run: adapter lifecycle and eviction, HiCache adapter isolation, the independent MoE reference (vLLM parity), overlap loading, PD transfer, the dense breakable prefill graph, the chunked-prefill HF guard, RL tensor loading and the TP matrices.
8. **`test: retry the adapter download in test_lora_load_from_tensor on hub rate limits`** — the 5090 batch of the group rerun on this branch failed in this file's `setUpClass` on a hub 429 ("3000 api requests per 5 minutes", retry after 49 s) with no cached adapter on the runner; CI retries test methods, not `setUpClass`, and waits about two seconds. The adapter download now goes through `sglang.srt.utils.retry` (three retries, about 30, 60 and 60 s).
Rerun convention (a review rule, not path-based CI enforcement): a PR that changes `python/sglang/srt/lora`, `python/sglang/kernels/ops/lora` or the LoRA tests runs `/rerun-group lora` before merge; a PR that changes the scheduler, the radix or HiCache caches, PD disaggregation or model LoRA integration reruns the affected LoRA tests with `/rerun-test`.
