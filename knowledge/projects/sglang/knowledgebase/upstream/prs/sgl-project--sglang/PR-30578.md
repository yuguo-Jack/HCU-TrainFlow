# feat: flush decode KV only for prefill reads on extend requests

## Motivation

<!-- Describe the purpose and goals of this pull request. -->
The MLX extend path calls `flush_all_decode_kv()` on every extend batch, which syncs all active decoding requests' un-synced KV from their per-request contiguous caches into the shared MlxAttentionKVPool. Only prefix-cached prefills actually read the pool, and they only read the slots in their prefix_slot_ids. So flushing every request is wasteful: with many concurrent decodes and few/small prefills, it pays an O(active-requests) GPU scatter (set_kv_all_layers across all attention layers) and drags unrelated requests' lazy decode graphs into materialization each step. This resolves the existing TODO (changminbark) in tp_worker.py.

Fixes #33547

## Modifications

<!-- Detail the changes made in this pull request. -->
- model_runner.py: Added an optional needed_slots filter to _sync_decode_kv_to_pool — if a request's un-synced slots are disjoint from needed_slots, skip the scatter and leave _req_synced_offset untouched (a later batch that reads those slots flushes them then). Replaced flush_all_decode_kv with flush_decode_kv_for_slots(needed_slots), which only syncs requests whose pending KV intersects the given slots. remove_request still does a full unfiltered flush, so KV is never lost on eviction.
- tp_worker.py: Added _gather_prefill_prefix_slots(reqs) (union of prefix_indices for prefill-routed reqs, i.e. not has_request(rid)), and both extend paths (sync_forward_batch_generation_mlx and async async_forward_batch_generation_mlx) now flush only those slots.
- Tests: Added test_sync_flush_only_uses_prefill_prefix_slots (flush receives only prefill reqs' slots, not continuations') and test_flush_decode_kv_for_slots_syncs_only_overlapping_requests (disjoint-skip: only the overlapping request syncs and advances synced_offset).

Hi @changminbark — following up here rather than on #32446, since this is where the code will land.

I believe the leak in #32446 is orthogonal to this PR and isn't covered by this branch. At `09c2381`, `remove_request` — the only thing that returns a request's per-layer `ContiguousAttentionKVCache` list to `_cache_pool` — has exactly two callers:

- `_cleanup_stale_rids`, decode branch only (unchanged on this branch; the extend branch is still `self._mlx_active_rids |= current_rids`)
- the new `prepare_for_retraction`

`sync_and_release_request` flushes the decode KV at the release point but never removes the state — it doesn't pop `_req_caches`.

So a request that finishes normally and never joins a decode batch is freed by neither path. That's real traffic: `max_new_tokens=1` scoring/classification, or TTFT-only benchmarking — the scheduler keeps building EXTEND batches and `is_decode()` is never true.

Measured on an M5 Pro / `mlx-community/Qwen3-0.6B-4bit`, unique prompts (no prefix sharing), concurrency 2, logging `len(_req_caches)` / `len(_cache_pool)` / `mx.get_active_memory()` on every extend flush:

```
req_caches=11 cache_pool=0 active_mem_gb=7.26
req_caches=12 cache_pool=0 active_mem_gb=7.70
req_caches=13 cache_pool=0 active_mem_gb=8.14
...
req_caches=22 cache_pool=0 active_mem_gb=12.07
```

~0.44 GB retained per request, linear, reuse pool pinned at 0. Worth noting this is on current main, which flushes *more* aggressively than this PR does (`flush_all_decode_kv` on every extend) — so the flush policy isn't what leaks. Sync and release are separate concerns.

The fix is ~15 lines and composes cleanly on top of yours: mark the request at the pre-release hook, release it in `_cleanup_stale_rids` on the next scheduler-built forward of either mode. It has to be deferred rather than eager — an overlap chained decode launched before the finish was known still references the request's caches and token list, and removing eagerly reproduces the #22632 KeyError family. With it applied, the same probe holds flat at `req_caches=0 cache_pool=1 active_mem_gb=2.89`.

Code and regression tests are on the closed #32446 (branch `xiaolin2004:fix-mlx-prefill-only-leak`). Happy to push it into this PR as a follow-up commit, or to have #32446 reopened rebased on top — whichever you prefer. The only genuine overlap between the two is one hunk: we both route the pre-release hook into the prefill finish path in `batch_result_processor.py`.
