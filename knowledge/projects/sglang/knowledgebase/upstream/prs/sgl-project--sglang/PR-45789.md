# [Fix] scheduler: Preserve Mamba fork and tail states across chunked prefills

[Upstream PR](https://github.com/sgl-project/sglang/pull/45789) · state: open · merged: False

## Original PR description

## Motivation

Split out from the Ling-3.1-flash day-0 support effort.

Hybrid-Mamba models cannot partially cache state mid-prefill the way KV caches can. When a chunked prefill is interrupted, the scheduler today discards the mamba fork state, so the next request that shares the prefix must recompute everything past the last completed chunk boundary.

This PR lets the scheduler split an eligible prefill at an aligned cached fork so both the fork state and the request tail state survive for the next turn, on initial admission, continuation, and after a HiCache load-back. Measured on Ling-3.1-flash (GB300): the first follow-up request recomputes **576 fewer tokens** (cached 6784 → 7360 tokens at the fork).

## Modifications

- New opt-in env `SGLANG_SPLIT_PREFILL_AT_MAMBA_FORK` (default off). Eligibility: hybrid mamba model, non-dLLM, extra-buffer radix cache strategy, env on.
- `PrefillAdder` computes the aligned fork length and caps the admitted extend at the fork on initial admission, continuation, and HiCache load-back (the load-back path recomputes the fork after over-delivery).
- The single-unfinished-chunk guard is extended from `shortest-prefill-first`-only to all scheduling policies **only when the feature engages**: `has_chunked_req and (policy == "shortest-prefill-first" or split_prefill_at_mamba_fork)`. With the env off, admission decisions are byte-identical to main for every policy (covered by a policy×env matrix test). Once an unfinished chunk is committed with the feature on, admission stops, so a following candidate can never take the chunk slot.
- Continuation splits respect the scheduler's `truncation_align_size` (deterministic inference): a misaligned fork keeps the original continuation length.

## Accuracy Tests

GB300 4x, Ling-3.1-flash FP8, TP4+EP4+NEXTN, chunked prefill 4096, extra-buffer strategy; full GSM8K (1319 questions, temp 1.0, top_p 0.95):

| env | accuracy | stop rate |
|---|---|---|
| OFF | 97.04% (1280/1319) | 99.77% |
| ON | 96.82% (1277/1319) | 99.92% |

No runaway generations; all completed answers finished with `stop`.

Multi-turn across a fork (same-session OFF/ON): the follow-up request hits 6784 cached tokens with OFF vs 7360 with ON (576 fewer recomputed tokens). HiCache load-back smoke: eviction from device, host load-back landing exactly on the fork and past the fork, correct answers, zero leaks; `/flush_cache` clean, GPU memory back to ready level after drain.

Unit: 80 passed / 94 subtests in `test_prefill_adder.py` (plus caller files), including initial/continuation/HiCache fork scenarios, a policy×env guard matrix (8 policies × OFF/ON), negative eligibility (non-mamba / no extra-buffer / dLLM), and mutation checks that each new test goes red under the corresponding code revert.

## Speed Tests and Profiling

Not a throughput PR: the value is cache completeness for hybrid-mamba multi-turn workloads (576 fewer recomputed tokens per follow-up in the measured scenario). No scheduler hot-path cost when the env is off.
