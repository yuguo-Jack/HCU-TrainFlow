# [Feat] [AMD] minimax: gfx950 sparse attention, NVFP4 KV and DSpark verify kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/46690) · state: closed · merged: True

## Original PR description

> Part of the MiniMax-M3.1-Flash AMD series that replaces #45936 (closed with its base branch `minimax-m3.1-flash`): kernel PRs #46690 (attention), #46691 (MoE / GEMM) and #46692 (quick all-reduce), each on `main`; then #46693 with the M3.1 call sites and #46694 (indexer CP). It follows the DeepSeek-V4.1 AMD layout (#41018-#41021, then #41308).

## Summary
- **NVFP4 KV (MSA-v1 layout).** `minimax_sparse/common/nvfp4.py` reads the packed rows for the Triton kernels and `nvfp4_gfx950.py` dequantizes them in Gluon. The kernel tests build their packed caches with a torch quantizer in `NVFP4KVQuantizeUtil`'s layout (`nvfp4_kv_quantize` in `sglang/test/quant_ref_utils.py`).
- **Sparse decode.** `decode/nvfp4_decode_gfx950.py` runs sparse decode over the packed NVFP4 K/V in Gluon (one program per row, top-k chunk and KV head; per-warp online softmax). `topk_sparse.py` dispatches an `Nvfp4Cache` to it, and the NVFP4 verify scorer sits beside the bf16 one in `decode/verify_topk_idx.py`.
- **Verify indexer.** `decode/verify_topk_idx.py` scores a linear draft chain against one shared prefix; `decode/verify_topk_gfx950.py` fuses the per-block max score with a streaming top-k on MFMA tiles.
- **Prefill.** `prefill/index_topk_gfx950.py` is the fused prefill indexer; `prefill/gluon_prefill_pair_gfx950.py` runs two queries per program over the union of their top-k blocks; `prefill/nvfp4_prefill.py` gathers the NVFP4 cache into the Gluon prefill's paged layout; `prefill/gluon_prefill.py` and `prefill/flash_with_topk_idx.py` take the new cache.
- **fp8 O epilogue.** `common/out_quant_gfx950.py` is shared by the Gluon decode and pair prefill: they can write O directly as the fp8 o_proj input, with the same bytes and scales as aiter's separate per-token or 1x128 quant.
- **QK-norm + RoPE.** `minimax_m3_qk_norm_rope.py` adds the gfx950 fused Gemma Q/K RMSNorm + partial RoPE + KV-cache write.
- **HiCache.** The NVFP4 page-row copy takes its CTA quota as a template argument: 32 on HIP (MI350X needs 16+ to saturate PCIe), 2 on CUDA as before.
- **Windowed verify.** `verify_mla_window.py` lets the gfx950 grouped-head split-KV verify serve the DSpark draft's sliding window (its non-causal draft block, window 4095) with a one-pass combine, as a `VerifyMLA` subclass; `num_stages=2` was 13-26% faster for that window. The shared `verify_mla.py` only gains the stage-1 window mask (a constexpr, compiled out without a window), the caller's opt-in in `can_handle`, and the two class hooks the subclass sets; Qwen3.5 and Kimi-K3 verify outputs are bitwise unchanged.
- The M3.1 call sites (NVFP4 pool, verify indexer, fp8 O for `o_proj`, windowed draft verify) are in the integration PR.

## Serving gain of each kernel
Measured in the integration PR at TP4 on MI350X (NVFP4 KV, DSpark acceptance simulated at 3 tokens per step, 32K-token contexts), each change turned off alone; the share decode TPOT or prefill latency grows without it, mean of two GPU sets:
- Windowed draft verify (`verify_mla_window`): decode TPOT +20.6% at 1 request, +8.2-9.6% at 8-64.
- Two-queries-per-program Gluon prefill (`gluon_prefill_pair_gfx950`): 32K-token prefill +10.3%, decode +4.2-5.4% at 8-64.
- Gluon prefill over an FP8 KV pool (`SGLANG_MINIMAX_M3_AMD_KV_FORMAT=fp8`): prefill +11.7% (32K tokens) and +12.4% (eight 8K requests).
- NVFP4 KV itself (kernel level, CUDA-graph replay, per layer): the verify indexer at 110K context takes 0.75-0.84x FP8's time from 8 requests and sparse decode 0.42-0.68x, with 1.78x the tokens per GB of KV.

## Changes to existing kernels
On CUDA nothing changes: `topk_sparse` only dispatches the new `Nvfp4Cache` type, the decode top-k only moves into `select_decode_topk`, and the page-row quota stays 2.

On gfx950, main's MiniMax-M3 layers switch kernels when this merges, with no new call site:
- QK-norm + RoPE + cache store (`sparse_qk_index_gemma_rmsnorm_rope_cache`) runs the tiled kernel for M3's 128-wide head with 64-dim neox RoPE; its bf16 outputs equal the per-head kernel's bit for bit.
- The Gluon sparse prefill pairs two queries per program for bf16 batches from 2048 tokens (16 query heads), and now also serves an fp8 KV pool at its per-tensor k/v scales, which `minimax_sparse_prefill` now passes on; before, an fp8 pool stayed on Triton. Both match the Triton kernel up to bf16 rounding.
- The prefill indexer uses the fused gfx950 index top-k for score-only max layers at unit scales and 128-aligned pages; on these bf16 / fp8 index caches it emits the Triton two-pass indexer's block ids exactly. It keeps Triton when Gluon's CDNA4 module is missing.

On other ROCm GPUs, the per-head QK-norm kernel, which serves them (and gfx950 heads other than M3's), no longer writes main K/V to slot 0, the reserved CUDA-graph padding slot. The unfused `store_cache` already skips it, and no real token is stored there.
