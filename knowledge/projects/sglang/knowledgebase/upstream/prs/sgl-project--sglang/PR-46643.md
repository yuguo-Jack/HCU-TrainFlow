# [Fix] scheduler: keep chunked prefill within allocatable KV under memory pressure

[Upstream PR](https://github.com/sgl-project/sglang/pull/46643) · state: open · merged: False

## Original PR description

## Motivation

Under overload on Kimi-K3 (MI355X, TP8, chunked prefill + hybrid KDA/MLA), the scheduler could stall or fail allocations:
- A continuing chunk was sized only by the token budget, so it could ask `alloc_extend` for more KV than is free.
- A second unfinished chunked request could be admitted under policies other than shortest-prefill-first, even though only one can be tracked (assert crash).
- A latched `batch_is_full` was cleared only when the running batch shrank, so the waiting queue stalled.
- On the aiter backend, an over-capacity extend inside graph context could leave the chunked-KV path.

## Modifications

- `available_chunk_tokens` caps a continuing chunk by free + evictable KV, less the page `alloc_extend` over-asks. When that leaves nothing, the chunk proceeds with the free KV or is deferred.
- The one-chunked-request guard applies under every schedule policy.
- `batch_is_full` is re-evaluated every scheduling step; `PrefillAdder` still enforces the real limits.
- Over-capacity aiter extends stay on the chunked-KV path.

## Accuracy Tests

New unit tests (`test_prefill_memory_budget.py`, `test_prefill_adder.py`, `test_scheduler_batch_is_full_latch.py`, `test_aiter_attention_backend_handler.py`): all 5 new cases fail on `main` and pass with this PR (76 passed).
End to end, the Kimi-K3 MI355X production build includes these fixes. On a 40-min overload soak (48 concurrent requests against 12 slots), 901/901 completed requests returned 200, the queue peaked at 37, and there were 0 OOM, HSA or assert errors.

## Speed Tests and Profiling

Scheduling only; no kernel change.
