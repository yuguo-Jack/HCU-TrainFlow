# [Bugfix] Fall back from batch D2H copies when host memory is not device-visible

[Upstream PR](https://github.com/sgl-project/sglang/pull/40571) · state: open · merged: False

## Original PR description

## Summary

Fixes #40232. `try_copy_page_first_pages_batch` passes the registered host pool's raw host virtual addresses to `cudaMemcpyBatchAsync`. On platforms where `cudaDevAttrCanUseHostPointerForRegisteredMem` is 0 (the reporter hit it on WSL2/GPU paravirtualization), those addresses are not valid device-space pointers, and the copy fails asynchronously with `cudaErrorIllegalAddress` — sticky, only observed at the next synchronization point, so it presents as flaky HiCache backup failures rather than a broken D2H.

The fix queries the attribute per call inside the batch helper: when the device does not report support (or the query itself errors), the helper returns false and the caller takes the existing per-page `cudaMemcpyAsync` fallback, which translates host pointers and is verified working in the issue. On mainstream platforms where the attribute is 1, the batch fast path is unchanged. No new ops, no wheel/ABI dependency, and the fallback is the code path the kernel already ships.

Design picked after discussion on the issue: the alias-translation variant (`cudaHostGetDevicePointer` per destination) is a possible follow-up refinement for performance on attribute-0 platforms, but the fallback-first version here is the smallest safe default.

## Verification

Code-level only, stated plainly: this environment has no CUDA host, so the kernel was not compiled or run here; the JIT kernel builds on GPU machines and CI exercises it. The acceptance test for the fixed behavior is the reporter's standalone repro in the issue (raw host VA vs `cudaHostGetDevicePointer` alias vs `cudaHostAlloc`), where the failing configuration is exactly the one this change now routes to the fallback.
