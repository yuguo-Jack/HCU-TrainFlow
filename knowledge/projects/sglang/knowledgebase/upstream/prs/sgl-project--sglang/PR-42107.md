# [Fix] Honor no-special-token encoding in native chat requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/42107) · state: closed · merged: False

## Original PR description

## Motivation

The native Rust chat path sets `skip_special_tokens=true` for template-rendered prompts, but the tokenizer worker implements this by stripping `encode("")` from the beginning of the encoded prompt. Tokenizers that append EOS cannot be handled this way. With the official `allenai/OLMo-7B-hf` tokenizer, `Hello` becomes `[12092, 50279]` instead of `[12092]`.

## Modifications

Load a second Dynamo tokenizer handle with `add_special_tokens=false` once at startup, following the existing `sglang-processor` design. The worker selects that handle for rendered prompts; ordinary prompts and detokenization keep the original handle. Both handles are shared across workers, and each request still performs one encode.

Use the backend's real option instead of filtering output IDs, so configured padding/truncation and special tokens explicitly present in the prompt remain correct. Preserve the existing single-handle constructor and custom tokenizer prefix fallback through an additive trait method.

## Accuracy Tests

- Six new CPU regression tests exercise actual Dynamo/Hugging Face tokenizers through `TokenizerWorker`: suffix EOS, BOS plus EOS, prefix-only/no-special controls, fixed padding, and truncation. They also check literal special tokens and both request modes. All 10 focused tests pass.
- Actual official OLMo tokenizer artifact through the worker: the original code appends EOS to `Hello`; the corrected path returns `[12092]` and preserves the explicitly written EOS in `Hello<|endoftext|>` as `[12092, 50279]`.
- Workspace Clippy with `--all-targets -- -D warnings` and full applicable repository hooks passed. The root-run server suite has 320 passing tests; 13 existing shared-memory tests fail because this sandbox rejects `shm_open` with `EPERM`.
- CPU tokenization validation only; no GPU inference or model-quality benchmark was run.

## Speed Tests and Profiling

This adds one startup tokenizer load and its resident memory, shared across all workers. In three fresh local macOS CPU processes using the unoptimized Rust dependency build and the official OLMo tokenizer, the second load took 132–140 ms and increased the cumulative process peak resident size by 15.6–17.8 MiB (`getrusage`; this is a peak delta, not live RSS). This is a local startup measurement, not a bound for other tokenizers. There are no per-request model-file loads or extra encode calls, and no inference throughput claim.
