# [DSV4] Support CPU offload of retracted KV on the PD decode node

[Upstream PR](https://github.com/sgl-project/sglang/pull/37239) · state: open · merged: False

## Original PR description

## Motivation

In PD disaggregation, when the decode node retracts a request under KV pressure, `retraction_backup()` (`srt/mem_cache/common.py`) preserves that request's KV on the host so it can resume later without recomputing its prefix. The `cpu_tensor` backend routes through `Req.offload_kv_cache` → allocator → the pool's `get_cpu_copy` / `load_cpu_copy`.

`DeepSeekV4TokenToKVPool` never implemented that pair, so it falls back to `KVCache.get_cpu_copy`, which raises `NotImplementedError`. DSV4 therefore cannot use the `cpu_tensor` retraction backup at all — a retracted request has to recompute its entire prefix through prefill.

Implementing it is not a matter of copying `indices` rows, because **DSV4 has no full-context KV pool**. `req_to_token` holds logical token ids that do not address any single buffer; one request's state is spread across eight buffers, each with its own index space and page size:

| region | buffer | how a token maps to a row |
| --- | --- | --- |
| SWA latent KV | `swa_kv_pool.kv_buffer` | `full_to_swa_index_mapping[idx]`, `> 0` filtered |
| C4 compressed KV | `c4_kv_pool.kv_buffer` | `idx // 4`, then page by 64 |
| C4 indexer KV | `c4_indexer_kv_pool.index_k_with_scale_buffer` | same as C4 |
| C128 compressed KV | `c128_kv_pool.kv_buffer` | `idx // 128`, then page by 2 |
| C4 attention state | `compress_state_pools[L]` | ring block at `swa_page * ring_size` |
| C4 indexer state | `indexer_compress_state_pools[L]` | same ring block |
| C128 state | `compress_state_pools[L]` (ratio 128) | **`req_pool_idx * ring_size + pos % ring_size`** |
| online-C128 MTP pending lens | `online_c128_mtp_pending_seq_lens` | `req_pool_idx` |

Two consequences shape the design. The compressed pools are addressed by *page*, not by token, and their fp8 pages are not contiguous per token (`[value × 64][scale × 64]`), so row-granular copying would be both wrong and layout-dependent. And the C128 state is keyed by **request slot**, which retract frees and resume reallocates — so the existing `get_cpu_copy(indices, ...)` signature cannot express it.

## Modifications

**1. New `srt/mem_cache/kv_region.py` — model-agnostic region descriptors.**

A pool declares its buffers as a list of `KVRegion`, each pairing per-layer tensors with an *addressing* object that turns `(token_indices, req_pool_idx)` into buffer row indices. `save_regions` / `load_regions` then do the copies without knowing anything about the model's compression scheme. Four addressing schemes cover DSV4:

- `PageAligned` — stride/page arithmetic on token ids (the compressed KV pools).
- `SwaMapped` — indirect through `full_to_swa_index_mapping`, dropping unmapped pages.
- `SwaPageRing` — a whole ring block per live SWA page (the compress-state pools).
- `ReqScoped` — rows owned by a request slot rather than by token location (C128 state).

Because `page_size = 256`, `c4_page = 64` and `c128_page = 2`, note that `(idx // 4) // 64 == idx // 256` and `(idx // 128) // 2 == idx // 256`: all three KV regions land on the same page row as the full page id, so one page-id computation serves them all, and copying whole `uint8` page rows sidesteps the fp8 intra-page layout entirely (dtype-agnostic byte movement).

Save and load are deliberately **not** symmetric. Whether a given token page still holds a live sliding-window slot depends on the allocator's ring state, so a request can be saved with two SWA pages mapped and resumed with one. `save_plan` records which token pages were mapped into the host blob; `load_plan` restores only the pages mapped on both sides. This mirrors what `SWAKVPool.get_cpu_copy` already does at token granularity.

**2. `DeepSeekV4TokenToKVPool.iter_kv_regions()`** declares the eight regions above; `get_cpu_copy` / `load_cpu_copy` become thin drivers over the shared engine.

**3. `req_pool_idx` threaded through `get_cpu_copy` / `load_cpu_copy`** — the allocators, the other pool implementations, and the two `schedule_batch.py` call sites. The load side passes the *current* slot, since retract released the one used at save time.

**4. Configurations that cannot be offloaded correctly now raise instead of silently moving wrong rows**, and keep using the recompute path:

- DSV4 `unified_kv` — packs the SWA ring and the compressed region into one buffer, which the region model addresses separately.
- HiSparse C4 — keeps c4 pages in its own host tier and remaps device locations.
- NPU DSV4 pools — live data sits in NPU-only `index_k_buffer` / `index_scale_buffer` and is paged by `kernel_page_size`, not the model `page_size`.

## Accuracy Tests

Unit tests (CPU, registered in `base-a-test-cpu`):

- `test/registered/unit/mem_cache/test_kv_region.py` — 19 cases: the four addressing schemes, the save/load engine, SWA save/load asymmetry, and a cross-check that `ReqScoped` reproduces the row math the PD path already uses for DSV4 C128 state (`get_dsv4_c128_state_indices`).
- `test/registered/unit/mem_cache/test_dsv4_cpu_copy.py` — 11 cases: the DSV4 region list (completeness, page-row equality across the three KV regions, round-trip into a different slot range) and that the unsupported configurations raise.

The device path is not covered by a checked-in test: it needs a GPU plus a DSV4 config, so it cannot run in CI. It was verified manually instead, as described below.

End-to-end, DSV4-Flash on 8×GPU in PD disaggregation with forced retraction (`SGLANG_TEST_RETRACT=1`), needle-in-context prompts: every retracted request resumed and still recalled a code embedded in the middle of its prompt, with save/load pairing exactly per request and no asymmetry assertions triggered.

## Speed Tests and Profiling

Offload is on the retract path only; the steady-state decode loop is untouched. Measured save → load round trip per retracted request was ~17 ms p50 / ~22 ms p90 on the internal setup. The current path instead recomputes the whole prefix through prefill; that recompute was not measured for this PR.
