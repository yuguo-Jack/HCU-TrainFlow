# [Fix] hicache: Continue eviction after a failed file unlink

[Upstream PR](https://github.com/sgl-project/sglang/pull/42488) · state: open · merged: False

## Original PR description

## Motivation

With a bounded HiCache file backend, one undeletable oldest cache page prevents eviction of every later page. `_evict_one_lru_locked` restores that entry at the LRU head and returns `stop` on OSError. Every later capacity-constrained write retries the same head and is refused, even when another page can be reclaimed.

Reproduction on official main 29bcb74a89: fill a 128-byte cap with two real 64-byte files, inject PermissionError only for the oldest file's unlink, then cache another 64-byte page. The new write returns False and the second, deletable file is never tried.

## Modifications

Retain the failed entry and its charged bytes at the end of the eviction queue, returning `skipped` so the existing bounded skip loop can try other victims. A failed unlink contributes zero reclaimed bytes and does not invalidate positive metadata. Update the helper's outcome documentation.

Two CPU regressions check:
- Selective unlink failure: a later victim is evicted, the new file contains the expected bytes, the failed file and metadata remain, and accounting stays at 128 bytes.
- All unlinks fail: the write is refused after trying both candidates, no reservation or byte refund occurs, and a later retry succeeds once unlink is allowed.

This changes eviction ordering after an unlink failure. It does not retry forever or assume the failed file was removed. It shares the existing skip budget with pending writes. Scope is one file-backend evictor, not cross-process coordination.
