# [Feat][DSV4.1][engram]: Sharing Engram via RDMA to reduce PD DRAM redundancy

[Upstream PR](https://github.com/sgl-project/sglang/pull/47460) · state: open · merged: False

## Original PR description

## Motivation

Independent serving instances can duplicate a large read-only Engram table in host memory. This draft proposes discussing how SGLang could fetch rows from a table shared across instances, including across nodes, while preserving the existing native paths by default.

**Please treat this as a design discussion, not a ready implementation.** We would like to discuss the provider boundary, configuration, completion semantics, failure handling, and lifecycle with the community before implementing the agreed design and marking this PR ready for review.

## Modifications

Add a default-off experimental adapter through the existing Engram lookup path, plus a proposal and validation checks. The SGLang branch includes the experimental reader, owner service, READ plans and launch instructions. Only the legacy DOCA 3.1 NIXL/GPUNETIO GPU-GET library is built separately; this is not a production-ready API. An opt-in path reuses the research reader’s 16-QP READ plan and early GPU-hash prefetch. Native serving remains the default. This draft is for design review; H20 serving measurements below are pinned to the revisions actually tested.

The historical prototype used an experimental GPU-initiated NIXL/GPUNETIO READ path with DOCA 3.1 and an older SGLang snapshot; its historical performance numbers do not measure this updated PR. [NIXL issue #2543](https://github.com/ai-dynamo/nixl/issues/2543) and [NIXL draft #2544](https://github.com/ai-dynamo/nixl/pull/2544) discuss the supporting device GET; #2544 is reference material, not a current-SDK implementation.

## Accuracy Tests

Run `python test/registered/unit/layers/test_remote_engram.py` with PyTorch installed. At the updated head, 16 targeted CPU tests passed in an existing SGLang environment, including adapter capture guards and owner lease handling. The packaged owner and reader also passed a single-node, two-GPU H20 test against real checkpoint rows for both layers (4096 selections each), with 16 QPs and graph replay; the owner drained and exited. This is not a new 1P1D performance measurement. The earlier tested draft commit `a4edaf95a27657069ac32f417e0857e926a1cf62` passed a native lookup and a single-rank H20 test reading four rows from each of two remote checkpoint layers with bitwise BF16 comparison and a TP-range check. At that earlier commit, a same-version 1P1D smoke completed on two H20 nodes: TP8/CP8 P used the remote reader with bounded replay disabled; DP8 D used a native per-node host table and DSpark. One 16K-token input produced 64 output tokens, with exact text match to the prior reference; P recorded one Mooncake KV transfer. The tuned reader also passed a 4096-selection-per-layer one-GPU comparison to real checkpoint rows, including duplicate-ID restoration and graph replay. This is functional evidence, not production accuracy qualification. In the separately measured prototype, 288 paired measured outputs matched across the native and shared arms. This is historical evidence, not validation of the code in this PR.

## Speed Tests and Profiling

For the earlier draft at commit `a4edaf95a27657069ac32f417e0857e926a1cf62` (before the main-branch update), a two-node 1P1D C8 test used 16K input, 64 output tokens, three rounds of 32 measured requests plus eight warmups per arm, the same D process and matching request sets. Median of the three per-round TTFT p50 values: Native 5159.83 ms; Shared 5204.95 ms (+0.87%). Output throughput: 94.33 versus 93.52 tok/s (-0.85%). All 96 paired inputs and output text hashes matched, with zero measured cache hits, retractions or client errors. Native uses SGLang’s per-node local CPU table; Shared uses remote per-rank READ with 16 QPs and prefetch. P restarted between arms, Shared ran first, and bounded replay was disabled; there was no per-window NIC audit. P99 and production conclusions are out of scope. The historical serving results used separately provisioned reader and owner files; this PR now includes their SGLang-side implementations. Reproduction still requires the separately built native research library.

On H20, three independent prefill groups and one decode group, with 16K input, 64 output tokens and client concurrency 24, the median of three round medians was 1632.793 ms native versus 1647.930 ms shared TTFT (+0.93%); output throughput was 834.304 versus 828.517 tokens/s (-0.69%). The logical P-side table payload was three copies versus one; this is not whole-process RSS. The measurement used synthetic prompts, a debug router, the older prototype and DOCA 3.1; P abort-submission counters were nonzero in both arms and their cause was not resolved. Further details and tail metrics are in the proposal. This historical result is not a measurement of the current branch.

### H20 adaptation on a separate optimized baseline

We also applied this research idea to the public [antgroup H20 branch](https://github.com/antgroup/sglang/tree/research/shared-engram-h20-20261031) at commit [`5058e1fe5`](https://github.com/antgroup/sglang/commit/5058e1fe5). It is based on antgroup/sglang `6e6d5d9e` and is separate from the code in this PR. The three integration files and reader Python files in that commit match the hashes of the measured source; that measurement used a separately provisioned native runtime and owner. See the branch [README](https://github.com/antgroup/sglang/blob/5058e1fe5/research/shared_engram_h20/README.md) for configuration and limitations.

On H20, 1P1D, P TP8/CP8, C8, 16K input and 64 output tokens, Native versus Shared TTFT p50 was **1554.647 vs 1553.763 ms**, measured as the median of three per-round p50 values. Each round used eight warmups and 32 measured requests. All 96 paired inputs and final-text hashes matched, with no measured cache hits, retractions or client errors. These results show comparable TTFT in this workload, not a measured Shared speedup. The shared case retains one external host-memory table and avoids a table replica in each consuming instance.

The same D process was used for both arms, but P and D ran different SGLang revisions. P was restarted and the arms ran in fixed order, so the three rounds were not independently restarted deployments; per-round p99 from 32 samples is exploratory. The H20 results do not replace the current-main measurements above or constitute an exact cross-version A/B. Broader accuracy, cancellation, lifecycle and current DOCA SDK support remain open.

A subsequent functional check on the H20 adaptation used a rebuilt library from the [public legacy NIXL research snapshot](https://github.com/foraxe/nixl/tree/b5322e46f6e686ff16bdb3afb8a1a940a64e1163/research/vllm_engram_repro). Real checkpoint rows matched in both layers; the 16-QP prefetch path checked 4096 selections per layer and replayed four graphs. In a separate two-node 1P1D canary, all eight P ranks mapped the rebuilt core, plugin and shim; one uncached 16K-input/8-output request matched the prior runtime's output text. P was restarted, while D and the existing table owner remained running. This is functional evidence only; the 1553.763 ms result above used the earlier runtime, and the existing owner was not rebuilt for this canary. [More details](https://github.com/antgroup/sglang/blob/24e9dcb16f/research/shared_engram_h20/README.md#public-runtime-integration-check).

### Review status and remaining work

The branch has been updated with upstream main, includes its SGLang-side reader and owner, and the experimental feature flag follows SGLang's typed environment-variable convention. The opt-in path now requires row264 storage and a prepared READ plan, and rejects lookup during unsupported CUDA graph capture. The updated head has not yet been rerun end to end on H20; serving figures above retain their original commit and runtime attribution.

A separate legacy-runtime owner lifecycle prototype was exercised with real H20 P/D: a controlled drain retired all 256 owner QPs associated with eight 16-lane readers. That prototype is not part of this PR or a supported current-SDK implementation. Crash recovery, lifetime guarantees and the GPU GET interface still need a community-reviewed design.
