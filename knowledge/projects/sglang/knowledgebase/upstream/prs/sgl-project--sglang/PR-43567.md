# [Unified Radix] Invalidate lazy Mamba checkpoints before in-place tracking

[Upstream PR](https://github.com/sgl-project/sglang/pull/43567) · state: closed · merged: True

## Original PR description

## Problem

When lazy tracking cannot allocate its optional pending slot, decode/verify overwrites the keep slot in place. Its previous checkpoint length remains valid, so overlapping prefill result processing can donate that buffer under the old prefix length and silently corrupt later cache hits. This bug exists on main independently of #43559.

## Change

Invalidate the old checkpoint before ordinary and speculative in-place fallback. Existing result processing publishes the completed checkpoint again. Allocation behavior and capacity formulas remain unchanged.

A full-vocabulary GPU KL regression reproduces the ordinary decode cache-corruption path. This is the prerequisite correctness fix for #43559 and should merge first.

## Validation

- Pre-commit passed. The GPU KL regression covers ordinary decode; speculative verify is not covered by this E2E test.
- Standalone GPU E2E: GB300, Qwen3.5-0.8B, overlap and decode CUDA graphs, 1 running request / 4 Mamba slots. Warm unrelated and matching 128-token prefixes, then repeat a 255-token prompt with 32 generated tokens. Original main returns HTTP 200 but changes output tokens on reuse (maximum logprob difference 1.043104887). This fix alone restores identical tokens and logprobs (maximum difference 0).

- Registered full-vocabulary KL regression: `test/registered/radix_cache/test_mamba_cache_kl.py` (`extra-a`, `1-gpu-large`). On GB300 / Qwen3.5-0.8B, compare the next-token distribution at the same 255-token prompt before and after cache-seeding decode under natural four-slot pressure. Reverting only this fix fails with KL=0.6494482615 (stale 192-token hit); the fix passes with KL=0 (safe 128-token hit), threshold 1e-4. Both runs use overlap and decode CUDA graphs; pre-commit passed.
