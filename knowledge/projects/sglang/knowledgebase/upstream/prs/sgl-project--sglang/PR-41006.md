# [docker] add runtime-efa target to build images with AWS EFA libs and mooncake-transfer-engine-efa

[Upstream PR](https://github.com/sgl-project/sglang/pull/41006) · state: open · merged: False

## Original PR description

## Motivation

To improve sglang out-of-box experience on AWS GPU clusters.

## Modifications
1. Added a new build target: `runtime-efa` to build image with EFA user space libraries and `mooncake-transfer-engine-efa`
2. Extended CI workflow scripts to build and publish the newly added target images.

NOTE: 
The PR adds a new target `runtime-efa` instead of updating the existing `runtime` because the `rdma-core` version from EFA installer is different from the version comes with distro. Though the latest `rdma-core` version from the EFA installer should work for non-EFA platforms as well, we didn't test that configuration. And also not to interfere with the existing build configurations, we took a new target approach.

- alexnails · comment · 2026-09-28T22:21:54Z · [source](https://github.com/sgl-project/sglang/pull/41006#issuecomment-5879806419)

Hey team, 

Can we consider an approach where we make a separate thin Dockerfile built on the published runtime image

The repo already does this: docker/sagemaker.Dockerfile is just FROM lmsysorg/sglang:latest plus a few lines. We can the same with a new docker/efa.Dockerfile (we can separate the workflows out from main workflow as well) 

```Docker
ARG BASE_IMAGE=lmsysorg/sglang:latest-runtime
FROM ${BASE_IMAGE}

ARG TARGETARCH
ARG EFA_INSTALLER_VERSION=1.50.0
ARG EFA_INSTALLER_SHA256=fa6dff8593d866866c13cb4640d9059835cd4efa427971f100ab40c97bef2841
ARG MOONCAKE_EFA_VERSION=0.3.13.post1

RUN set -eux; \
    curl -fsSL --retry 3 -o /tmp/efa.tgz \
        https://efa-installer.amazonaws.com/aws-efa-installer-${EFA_INSTALLER_VERSION}.tar.gz; \
    echo "${EFA_INSTALLER_SHA256}  /tmp/efa.tgz" | sha256sum -c -; \
    tar -xzf /tmp/efa.tgz -C /tmp; \
    apt-get update; \
    cd /tmp/aws-efa-installer && ./efa_installer.sh -y --skip-kmod --skip-limit-conf --no-verify; \
    /opt/amazon/efa/bin/fi_info -l | grep -q '^efa:'; \
    rm -rf /tmp/efa.tgz /tmp/aws-efa-installer /var/lib/apt/lists/*

RUN --mount=type=cache,target=/root/.cache/pip \
    if [ "${TARGETARCH}" = "amd64" ]; then \
        pip uninstall -y mooncake-transfer-engine-cuda13 && \
        pip install --no-deps mooncake-transfer-engine-efa-cuda13==${MOONCAKE_EFA_VERSION}; \
    fi

ENV PATH="/opt/amazon/efa/bin:${PATH}"
```

1. **NCCL doesn't pick up aws-ofi-nccl by default.** The installer puts `libnccl-ofi-ngc-v3` in `/opt/amazon/ofi-nccl/lib`, which ships only `libnccl-net-ofi.so`/`libnccl-tuner-ofi.so` and no `libnccl-net.so`.    Suggest adding `NCCL_NET_PLUGIN=ofi` to the stage's `ENV`.

2. ~~**The `runtime` base has no gdrcopy.**~~ *(edited: already fixed on main)* The published `lmsysorg/sglang:latest-runtime` (built 9/18) is missing `libgdrapi` (`ldd /usr/bin/gdrcopy_sanity` reports `libgdrapi.so.2 => not found`), so libfabric logs `gdrcopy_dl_hmem_init failed!` there. Adding some Mooncake-side context (I maintain Mooncake's EFA transport). It's actually a bit worse than "won't work over EFA": in the standard wheel, `rdma` auto-discovery also picks up the EFA NICs as verbs devices. The RC QP creation then fails (`Failed to create QP: Operation not supported`) and the transfer hangs instead of falling back. I reproduced this on p5en with the standard wheel. kvcache-ai/Mooncake#4355 makes RDMA skip EFA NICs and fall back to TCP, but it isn't released yet.

On arm64 specifically:
- aarch64 builds of `mooncake-transfer-engine-efa*` are merged (kvcache-ai/Mooncake#4305) and will first ship in Mooncake v0.3.14. After that, the amd64-only condition on the wheel swap can be dropped, and arm64 can use `MOONCAKE_PROTOCOL=efa` too.
- Until then, for arm64 in this target, I'd either skip arm64 or set `MOONCAKE_PROTOCOL=tcp` there and document it, rather than `rdma`.
- The rest of the stage (EFA installer, NIXL LIBFABRIC, aws-ofi-nccl) supports aarch64. I've only validated EFA on Graviton (CPU/DRAM), not on Grace/GB200.
