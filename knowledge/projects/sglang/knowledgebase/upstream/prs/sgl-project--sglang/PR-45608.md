# [Feat] memory: Allow prefill CUDA graph bs below chunked_prefill_size under post-capture KV sizing

[Upstream PR](https://github.com/sgl-project/sglang/pull/45608) · state: open · merged: False

## Original PR description

Implements RFC #33852.

`post_capture_kv_sizing_planned()` returned False whenever `max_prefill_buffer_tokens()` exceeded the largest captured prefill bucket. Passing `--cuda-graph-max-bs-prefill` below `chunked_prefill_size` therefore turned post-capture KV sizing off with no log line, and the mem_fraction heuristic fell back to estimating graph memory. That is what made #33847 hard to debug. Decode already handles the same gap: a captured decode `max_bs` below `max_running_requests` keeps the feature on and reserves activation headroom.

## Modifications

- `arg_groups/overrides.py`: the prefill gate keeps only the hard conditions from the RFC, a disabled prefill graph or chunked prefill off.
- `kv_pool_runtime.compute_post_capture_kv_resize()`: when the largest captured prefill bucket is below the prefill buffer ceiling, it logs both token counts and raises the headroom to `pre_capture_activation_reserve_mb()`, the reserve the decode gap already uses.
- `runtime_context.pre_capture_activation_reserve_mb()`: new optional `prefill_tokens`, passed only for that gap, so the reserve is sized for the prefill buffer ceiling. Under PP dynamic chunking the ceiling is `max(chunked_prefill_size, max_prefill_tokens, 1.25 x chunked_prefill_size)`, and the chunk-size profiler runs eager prefills of up to 1.25 x `chunked_prefill_size` right after the resize. A reserve keyed on `chunked_prefill_size` alone is too small there. Existing callers keep their values.

Nothing changes while post-capture KV sizing is off (`SGLANG_ENABLE_POST_CAPTURE_KV_SIZING` defaults to False). With it on, configs whose largest captured prefill bucket covers the prefill buffer ceiling are unchanged. Muse Spark turns the variable on by default, and its documented launch configs leave the prefill `max_bs` at `chunked_prefill_size`, so they see no gap.

The RFC's tighter variant (reserving only the delta above the largest captured bucket) is left for later, as the RFC suggests.

Related PRs:
- #41478 adds a warning to the gate and keeps the gate returning False. This PR removes that gate condition, so the shortfall is logged at resize time with both token counts while the feature stays on. Both PRs edit the same block of `post_capture_kv_sizing_planned()` and conflict; the bucket-aware remedy text from #41478 could move into the resize warning here.
- #41941 (issue #41923) makes an off-grid `--cuda-graph-max-bs-prefill` capture its own bucket. It only touches the bucket generator and applies cleanly on top of this branch. The two are complementary: with #41941, setting the flag to the ceiling removes the reserve.

Known limits, unchanged here:
- The coverage check reads the resolved config. If `capture_prefill_graph()` falls back to eager at startup (for example LoRA without prefill graph support, or non-standard GQA layers), the config still claims coverage and no prefill reserve is added. The old gate had the same blind spot.
- The gate checks `device == "cuda"`, while `is_post_capture_kv_active()` also requires `current_platform.is_cuda()`. On ROCm with the variable set, the heuristic can plan post-capture sizing that never runs. This predates the change, though more configs now pass the gate.
