# [CI] test: Relax bs=1 perf limits for CI hosts with slower CPUs

[Upstream PR](https://github.com/sgl-project/sglang/pull/47989) · state: closed · merged: True

## Original PR description

## Motivation

The 1-GPU H100 CI lane (`1-gpu-large`) now runs on hosts with slower host CPUs. Two batch-size-1 perf tests fail there on every run with no code change, which blocks PRs on that stage:

| Test | Limit | Previous hosts | Current hosts |
|---|---|---|---|
| `dllm/test_dllm_batching_fdfo.py::test_bs_1_speed` | > 250 tok/s | 257–263 | 214–252 (31 samples; medians 232 and 248 on the two host types) |
| `moe/test_torch_compile_moe.py::test_throughput` | ≥ 285 tok/s | passes | 272–276 on the slower host type |

Both tests time a single request end to end. At batch size 1 that is bound by the host CPU as much as by the GPU. dLLM decoding runs with overlap scheduling disabled (`_dllm_overlap_disable`) and syncs with the host after every denoising step (`LowConfidence.step` → `done.tolist()`). In the scheduler logs the number of denoising steps is identical across hosts (365 for the 654-token answer), and the whole per-step time distribution shifts up by 3–13% (p50 7.05 → 7.25 / 7.94 ms). That points to the host CPU, not the GPU kernels.

## Modifications

- `test_dllm_batching_fdfo`: `speed > 250` → `speed > 200`
- `test_torch_compile_moe` (CUDA): `throughput >= 285` → `throughput >= 260`

Both new limits stay well above what a real regression would produce, with ~5% margin under the slowest measured host. Accuracy assertions are unchanged.

## Follow-up

A host-independent version of these checks would assert on GPU time per step and track CPU overhead separately, so host speed stops being baked into the limits. Happy to discuss that separately.
