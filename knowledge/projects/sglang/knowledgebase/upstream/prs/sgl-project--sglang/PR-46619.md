# [Perf] Use shared metadata for GDN prefill CUDA graphs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46619) · state: open · merged: False

## Original PR description

## Motivation

Retain this PR's original GDN prefill graph implementation: shared KDA metadata, direct execution of the existing Triton kernel chain, and FP32 recurrent checkpoints. The branch remains rebased onto main 3f5b1bec8e, which also contains the alternative implementation from #45474. There is no same-base performance comparison establishing which implementation is faster.

## Modification

Use one shared metadata implementation for GDN and KDA, and restore the original gdn_extend_in_graph computation. Static sequence/chunk tables feed the convolution, QKV split, gating and delta-rule kernels directly; selected checkpoints retain FP32 precision. Adapt state access to main's layer router while preserving its configuration switch and bucket eligibility checks.

```text
prefill batch -> shared KDA tables -> captured GDN kernel chain -> FP32 checkpoint
verify batch -> existing target-verify path -> per-candidate intermediate states
```

Keep main's target-verify exclusion and the regression for stale prefill metadata during verify capture. The [reported fix](https://github.com/sgl-project/sglang/pull/46619#issuecomment-6610683706) came from blank3rs, credited as co-author. GPU replay tests retain output/state parity, checkpoint precision and return-to-eager checks.

[sglang-omni#3234](https://github.com/sgl-project/sglang-omni/pull/3234) continues to bundle the original implementation plus the verify-routing fix on SGLang 9f6678aa. [sglang-omni#3235](https://github.com/sgl-project/sglang-omni/pull/3235) adds prefix caching, with the separate policy in [#46683](https://github.com/sgl-project/sglang/pull/46683). Omni's bundle does not require this newer SGLang base or an upstream merge.

## Benchmarking Result

Historical measurement of the original graph implementation, before #45474 landed and before the current rebase. These numbers do not compare this implementation with #45474 on the same base; that comparison has not been run. Drama3 streaming on one H200, c16, prefix cache disabled. A: base 9f6678aa; B: historical measured commit 31913fac. Executed A → B → B → A with fresh servers and identical settings/seed 1234. Each visit ran 128 substantial warmup, 256 prompt-prime and 256 shape warmup requests before 256 timed requests. The conditional tail was skipped.

Both arms used the same Omni prototype, including the request-seed foundation from [sglang-omni#3134](https://github.com/sgl-project/sglang-omni/pull/3134) and the runtime bridge adaptations now carried by [sglang-omni#3234](https://github.com/sgl-project/sglang-omni/pull/3234); only the SGLang source revision changed between A and B. These measurements predate the rebased Omni PRs and bundled-patch installer, which still need fresh GPU qualification. The prefix-cache gain is measured separately in [sglang-omni#3235](https://github.com/sgl-project/sglang-omni/pull/3235).

| Visit | Arm | Requests/s | Mean TTFA (ms) |
| --- | --- | ---: | ---: |
| 1 | A | 9.157 | 265.3 |

| 3 | B | 10.301 | 222.3 |

Mean throughput rises from 9.209 to 10.311 requests/s (**+11.96%**); mean TTFA falls from 261.9 to 223.2 ms (**−14.77%**). Results cover this c16 workload without independent A/A noise calibration.

- blank3rs · comment · 2026-11-03T17:17:48Z · [source](https://github.com/sgl-project/sglang/pull/46619#issuecomment-6610683706)

We carry this PR (head 35968dbd) on v0.5.23 (297e54fd) and hit a drafting regression with it under MTP/NEXTN when the GDN extend runs on the Triton kernel (FP16 `--mamba-ssm-dtype`, or deterministic mode).

**Cause:** in `GDNAttnBackend.forward_extend` the new `if self.prefill_graph_metadata is not None:` branch comes before the target-verify path. Prefill graphs are captured before decode graphs (`model_runner_components/cuda_graph_setup.py`), and the capture path (`init_forward_metadata_out_graph`) never resets `prefill_graph_metadata` (only `init_forward_metadata` does). So every target-verify CUDA graph captured a plain prefill extend, which keeps no per-position intermediate states.

**Measured** (Qwen3.6-35B-A3B-FP8, 1x H100, TP1, NEXTN 3 steps, greedy replay of agent traffic, 1 user): 1.61 accepted tokens per verify step with FP16 state vs 3.30 with FP32 state; draft position 2 was almost never accepted.

**Fix we run:** take the prefill-graph tables only for a plain extend, as `KDAAttnBackend.forward_extend` already orders it (verify first):
```python
if (
    self.prefill_graph_metadata is not None
    and forward_batch.forward_mode.is_extend_without_speculative()
):
```
With it, on the same setup at production sampling: FP16 state 3.12 tokens per step / 579 tok/s per user vs FP32 2.93 / 571 (1 user), and FP16 stays slightly ahead at 4 and 8 users.
