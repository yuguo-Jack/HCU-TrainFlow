# [Fix] scheduler: Reserve member rows of beam leaders admitted in the same prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/46855) · state: open · merged: False

## Original PR description

## Motivation

With beam search, the scheduler can crash with this assertion when a beam request shares a prefill with other requests and req-to-token rows are scarce:

```
AssertionError: Beam member spawn needs 2 req-to-token slots but only 1 are free; the admission gate (get_num_allocatable_reqs) must reserve them.
```

How it happens:

1. A `beam_width=k` leader takes one req-to-token row at admission. It spawns its `k-1` member rows later, at its prefill relay.
2. `get_num_allocatable_reqs` subtracts `pending_member_rows(running_batch)`, which covers groups that are already running. It does not cover leaders already admitted to the prefill being built (`adder.can_run_list`).
3. A later candidate in the same pass then fits into rows the leader has promised to its members. When the leader's prefill relays, `_spawn_member_rows` finds too few free rows and the assertion takes the scheduler down.

Example: with 3 free rows, a `beam_width=3` leader is admitted (it needs 3 rows in total), then a plain request is admitted too, because the gate still sees 3 free rows for 2 requests.

The rows only bind when the running batch is near `max_running_requests`, so this shows up under load.

## Modifications

- `BeamCoordinator.pending_member_rows_of(reqs)`: the existing `pending_member_rows(batch)` over a request list. `pending_member_rows` now calls it.
- `get_num_allocatable_reqs` takes `num_admitted_member_rows` and subtracts it from the row budget. The admission loop passes the pending member rows of the requests already in `can_run_list`.
- New test `test/registered/unit/managers/test_scheduler_beam_member_row_admission.py`, using the real `_get_new_batch_prefill_raw` admission loop with a stub adder:
  - with 3 free rows, a `beam_width=3` leader followed by a plain request admits only the leader (fails on `main`, where both are admitted);
  - with 4 free rows, both are admitted, so the gate is not stricter than it needs to be.
- `test_scheduler_held_row_admission.py`: its coordinator stub gains `pending_member_rows_of`.

## Benchmarking and Profiling

How I tested: CPU only, no model, no server.

- On `main` (dba22e9b68) the new test fails (`1 failed, 1 passed`). With this change, `2 passed`. `test/registered/unit/beam_search`, `test_scheduler_held_row_admission.py` and the new test pass together (26 tests).
- I found the crash with a CPU scheduler driver. It runs the real `Scheduler` and `BeamCoordinator`, and calls `capture_pre_sample_logits` on fake logits that are a deterministic function of the tokens each KV row holds. It mixes beam requests (width 2 to 4) with plain ones. On `main`, 19 of 40 seeds hit the assertion above. With this change, none do.
- With the driver, I also found that priority preemption can preempt a beam leader and corrupt other requests' KV. That is a separate bug, so I will send a separate PR for it.
