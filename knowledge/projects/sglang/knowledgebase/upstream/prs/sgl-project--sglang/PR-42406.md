# [cake_kernels] opt-in model routes: Qwen3.5 GDN prefill/decode, FP8 grouped MoE, NVFP4 warp-decode MoE (SGLANG_CAKE_ROUTES) + Qwen3.5 e2e report

[Upstream PR](https://github.com/sgl-project/sglang/pull/42406) · state: closed · merged: False

## Original PR description

## Motivation
Part 2 of the Cake-kernel forwarding work for sgl-project/sglang#42176 (namespace per RFC #29630): wire the forwarded
FlashInfer Cake kernels into the model execution path behind an **opt-in** switch and validate them end-to-end on a
P0 model family (Qwen3.5 MoE). Nothing changes for users who do not set the switch. FlashInfer baseline:
`e4f94f94848372b5019eb1d8b4e075a7393f7e1a` for the original validation; the top commit moves the `moe_fp8_grouped` route to the FlashInfer **main `58171ea83f32185a7990cfc15c969ecf79bb406c`** contract (see "FlashInfer main re-validation" below). sglang's `flashinfer_python` dependency pin is unchanged; the route's capability probe keeps it on the stock path when the installed FlashInfer lacks the new contract.

> **Stacked on #42382 (gemm), #42383 (moe) and #42387 (linear attention).** This branch contains those PRs' commits so it is
> importable on its own; review only the top commits listed below — the diff shrinks to this PR's files once the base PRs merge.

## What this PR adds
- `SGLANG_CAKE_ROUTES` (`srt/environ.py`, `kernels/cake_kernels/_routes.py`): comma-separated route names or `all`; unknown
  names raise. Every route is still gated by the adapter's `supports_<op>()` admission and falls back to the engine's
  default kernel, logging the decision once (`[cake-route] <name>: Cake kernel selected (...)` / `fallback (<reason>)`).
- `gdn_prefill`, `gdn_decode` (`srt/layers/attention/linear/kernels/gdn_flashinfer.py`): `chunk_gated_delta_rule` /
  decode with `backend="cake_gdn"` on the FlashInfer GDN backend (`--linear-attn-backend flashinfer`).
- `moe_fp8_grouped` (`srt/layers/moe/moe_runner/deep_gemm.py`): both contiguous FP8 block-scaled expert GEMMs (gate_up, down;
  fused SwiGLU-quant when admitted) on the Cake prepared runners, with one static buffer arena per `(device, K, N)` and
  a stream drain after preparation (see Findings), DeepGEMM fallback otherwise and for shapes first seen inside CUDA-graph capture.
- `moe_nvfp4_warp_decode` (`srt/layers/moe/moe_runner/cake_warp_decode.py`, hooks in `flashinfer_trtllm.py` / `modelopt_quant.py`):
  small-token NVFP4 MoE on the Cake warp-decode runner (`1 <= num_tokens <= 32`), TRT-LLM path otherwise.
- `SGLANG_CAKE_DEBUG` (default off): one-time input summary + device sync after each Cake MoE stage for fault attribution.
- CPU unit tests: `test/registered/unit/kernels/test_cake_routes.py`, `test_cake_gdn_route.py`, `test_cake_moe_fp8_route.py`,
  `test_cake_moe_nvfp4_route.py` (route off → stock path untouched; admission → Cake; capture fallback; arena reuse/growth;
  UE8M0 unpack and `-1` padding fill).
- Full e2e report (hardware, server flags, per-arm logs, kernel-level A/B) is kept with the forwarding work's internal
  workspace; the summary below is what it supports.

## Validation (1× GB200, nvcr sglang:26.07 + FlashInfer at the pin, Qwen3.5-35B-A3B-FP8 TP1)

  baseline runs; fixed-prompt greedy logprobs drift 0.30 vs the stock FI-GDN-vs-triton-GDN spread 0.43 (within the stock
  backend-to-backend spread); MoE routes (requires `SGLANG_DEEPGEMM_STANDARD_LAYOUT=compact`, see finding 2): full GSM8K 1319 q 0.796 / 0.777 (`moe_fp8_grouped`, two runs) vs 0.813 / 0.798 stock,

- Performance (medians, GDN routes): bench_one_batch bs 1/8/32 @ 1024/128 = 203.3 / 1348.2 / 3744.7 out tok/s vs stock

## FlashInfer main re-validation (`58171ea8`, 1× GB200, sglang:26.07 + FlashInfer main, Qwen3.5-35B-A3B-FP8 TP1, compact layout both arms)
FlashInfer main replaced the prepare-bound grouped FP8 GEMM with a block-scaled UE8M0 family that rebinds `a / a_scale /
m_indices / out` per launch and skips `-1` padding rows natively. The top commit (`b89daf5637`) moves the route to that
contract: no resident arena, no fp8 hidden_states / scale / m_indices / output copies, packed UE8M0 scales read in place, no
host sync per plan; the adapter mirrors the kernel's rules (sm_100a + sm_103a, `N % 128`, 16-byte-aligned packed scales and
output, per-call storage-alignment check with a logged fallback, FlashInfer refusals at prepare → logged fallback, cached).
Fused SiLU+quant stays two-launch (its per-call form is not merged yet); the masked `auto`-layout path still has no Cake
backend for this model's (N, K) band.

## Findings (tracked in the Cake/FlashInfer tracker; numerics untouched, tolerances not loosened)
1. **Descriptor upload race**: prepared Cake grouped FP8 GEMM initializes its TMA descriptor storage with a synchronous HtoD at the first
  launch → races pending kernels on non-blocking streams (illegal instruction in graph warmup). Workaround here: stream drain after prepare.
2. **Storage binding → persistent arena**: prepared runners bind tensor storage → the route needs a persistent arena + one input and one output copy per
  layer (~1 GB at 16384 tokens). That extra resident memory flips sglang's marginal DeepGEMM *masked* JIT warm-up heuristic
  (`SGLANG_DEEPGEMM_STANDARD_LAYOUT=auto`, `_GroupedMaskedWarmupExecutor`) during prefill capture → OOM in the warm-up, not in
  Cake code. Measured with `SGLANG_DEEPGEMM_STANDARD_LAYOUT=compact` for both arms (no masked warm-up). `expandable_segments`
  is not an option: FlashInfer rejects VMM-backed descriptor storage (same finding).
3. **GDN decode manifest gap**: Cake GDN BF16 decode has no manifest row for Qwen3.5-35B TP1 serving shapes.
4. **NVFP4 warp-decode geometry gap**: Cake NVFP4 warp-decode geometry table lacks the Qwen3.5-397B expert geometry (never admits at TP1/2/4).
5. **No Cake backend for the masked layout**: masked grouped FP8 GEMM (DeepGEMM masked layout) has no Cake backend.
6. **MoE route slower end-to-end**: the Cake grouped-FP8 GEMM is at parity with DeepGEMM contiguous at decode shapes but
   42 % slower at the 16384-token prefill shape, and the storage-binding copies (finding 2) add 30–40 % per layer at large M;
   the route stays opt-in and off by default.
7. **GDN prefill manifest gap (397B TP4)**: no frozen variant for the 4 q-head / 16 v-head per-rank split; `gdn_prefill` falls back.
8. **Suspected ~2-point GSM8K drift** with the MoE route on the 35B (two paired 1319-question runs; operator-level within FP8
   tolerance); layer-wise A/B on real dispatcher inputs is the next step.
