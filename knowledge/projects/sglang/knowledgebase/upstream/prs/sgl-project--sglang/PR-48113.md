# [Perf] [NVIDIA] gemm: Enable KDA FP8 skinny GEMM for K=3072, N=5120 at M=2/4/8

[Upstream PR](https://github.com/sgl-project/sglang/pull/48113) · state: open · merged: False

## Original PR description

## Motivation

On SM120, `try_sm120_fp8_linear` routes small-M static per-tensor FP8 linears to the KDA CUTLASS skinny GEMM only when `(m, k, n)` is in `_KDA_PRODUCTION_SHAPES` (generated from `_KDA_M_BY_PROJECTION`). Every other shape returns `None` and falls back to FlashInfer `bmm_fp8` (cuBLASLt).

Qwen3.8-27B-NVFP4 at TP=2 has a per-GPU `out_proj` / `o_proj` of K=3072, N=5120. That pair is not in the table, so at decode batch sizes 2–8 all of these calls take the fallback. There are 64 such calls per decode step per GPU (48 GDN `out_proj` + 16 attention `o_proj`).

## Modifications

- `python/sglang/kernels/kda_kernels/sm120_fp8.py`: add `(3072, 5120): (2, 4, 8)` to `_KDA_M_BY_PROJECTION`.
- `test/registered/kernels/ops/gemm/test_sm120_fp8_linear.py`: add `Qwen3.8-27B-TP2/out` to `SUPPORTED_CONFIGS` at M=2/4/8, and M=3/9 at this shape to `UNSUPPORTED_CONFIGS`.
- `test/registered/kernels/benchmark/gemm/bench_kda_fp8_skinny_gemm.py`: add the shape to `PROJECTIONS`.

M=1 is unchanged (it still uses the streaming GEMV). M=9 is not added because I did not validate it. There is no new kernel and no new environment variable. The existing `capability == (12, 0)` and `_has_kda_runtime()` guards still apply, and unsupported cases still return `None`.

## Accuracy Tests

All measurements below were taken on `main` at `dbeecc9`. The branch is based on `63c6de2`; between the two, `kda_kernels/sm120_fp8.py` and `test_sm120_fp8_linear.py` are unchanged, and the only touches to `qwen3_5.py` and the FlashInfer attention backend are import-path refactors (#47990). The baseline arm is unmodified `main`; the candidate arm is the same commit plus the one-line table change. No other patches or environment variables in either arm.

**Unit tests** (2x RTX 5090): `test_sm120_fp8_linear.py` goes from 123 passed (unmodified `main`) to 133 passed with this PR. The new cases cover M=2/4/8 at three seeds and the M=3/9 fallback.

**Numerics vs. the fallback** (random synthetic FP8 weights): max abs diff 0.0078 at M=2 and 0.125 at M=4/8. Results are not bitwise identical. This is a sample, not an error bound.

**GSM8K** on Qwen3.8-27B-NVFP4, TP=2: full 1319 questions, zero-shot, temperature 0, max 512 new tokens, concurrency 8, strict numeric grading. 4 server launches in order baseline, candidate, candidate, baseline:

| | baseline (fallback) | candidate (KDA skinny) | diff |
|---|---|---|---|
| Accuracy (mean of 2 runs) | 94.77% (1251, 1249 / 1319) | 94.47% (1246, 1246 / 1319) | −0.30 pp |
| Truncated at 512 tokens | 2.81% | 3.03% | +0.23 pp |

- The pre-registered non-inferiority margin was −1.0 pp for accuracy and +1.0 pp for truncation. The paired one-sided 95% bounds were −0.87 pp (accuracy lower, both t and bootstrap) and +0.80 pp (truncation upper), so both pass.
- Run-to-run variation within the baseline arm: +0.15 pp, with 2 questions graded differently.
- Exact output text differs on 72 questions between the two baseline runs, 75 between the two candidate runs, and 1092 between a baseline and a candidate run. This is expected, since the GEMM accumulation order changes.
- GSM8K prompts are a few hundred tokens long, so this does not cover long-context behavior.

## Speed Tests and Profiling

Hardware: 2x RTX 5090 (SM120), driver 595.58.03, CUDA 13.0. Software: torch 2.14.1+cu130, flashinfer-python 0.7.2, sglang-kernel 0.4.10, triton 3.8.0.

**Kernel level** (`bench_kda_fp8_skinny_gemm` inputs at K=3072, N=5120). Each sample is 96 calls captured in one CUDA graph, rotating through 8 weight copies to approximate cold L2. 30 interleaved rounds, median per call:

| M | fallback (cuBLASLt) | candidate (KDA skinny) | change |
|---|---|---|---|
| 2 | 14.68 µs | 12.12 µs | −17.4% |
| 4 | 15.32 µs | 12.13 µs | −20.8% |
| 8 | 14.07 µs | 12.13 µs | −13.7% |

**End-to-end.** Server args:

```
--tp-size 2 --dtype bfloat16 --kv-cache-dtype bf16 --attention-backend flashinfer --context-length 4096 --chunked-prefill-size 2048 --mem-fraction-static 0.85 --max-running-requests 8 --max-mamba-cache-size 16 --disable-radix-cache --cuda-graph-max-bs-decode 8 --cuda-graph-max-bs-prefill 8 --random-seed 20261019
```

- 6 baseline/candidate pairs, 12 server launches, interleaved O,P / P,O / ...
- After warm-up, each launch ran every scenario in a seeded random order: 8 waves for the main scenarios, 3 for the edge ones.
- A wave sends `c` requests at once with `ignore_eos`; wall is first send to last token.
- The change is the geometric mean of the paired ratios, with a one-sided 95% bound from a paired t-test (df=5). I fixed the scenarios and pass/fail rules before running.

| Scenario (in / out, concurrency) | decode M | wall | 95% CI (wall) | TPOT | pairs faster |
|---|---|---|---|---|---|
| 1K / 128, c=8 | 8 | −1.00% | −1.99% to −0.01% | −1.29% | 5/6 |
| 3K / 128, c=4 | 4 | −1.40% | −2.07% to −0.72% | −1.88% | 5/6 |
| 3K / 512, c=4 | 4 | −1.79% | −2.54% to −1.02% | −1.89% | 6/6 |
| 1K / 32, c=8 | 8 | −0.74% | −1.83% to +0.37% | −1.10% | 3/6 |
| 1K / 128, c=2 | 2 | −1.82% | −2.50% to −1.13% | −2.27% | 6/6 |
| 1K / 128, c=1 | 1 | +0.48% | −0.49% to +1.47% | +0.63% | 3/6 |
| 1K / 512, c=1 | 1 | +0.47% | −0.64% to +1.59% | +0.46% | 4/6 |

The c=1 rows were expected to be neutral, since M=1 does not take the new path. Their upper bounds missed my pre-set +1.0% non-inferiority margin. The excess comes from a single launch: pair 2's candidate server was 1–2.7% slower than its arm's average in all 8 scenarios, including those where the candidate is otherwise faster. GPU temperature, clocks and power for that launch matched the others. I have not found the cause.

I then ran a supplementary check, specified before running it and outside the original plan: 2 more pairs, c=1 only, 8 waves each. The paired changes were:

| Scenario | supplementary pair 1 | supplementary pair 2 |
|---|---|---|
| 1K / 128, c=1 | −0.45% | −0.17% |
| 1K / 512, c=1 | −0.14% | −0.01% |

I read this as no visible effect at M=1. Two pairs are not enough for a formal non-inferiority test, so I report both the original and supplementary numbers.

Overall, the end-to-end gain is small: about 1–2% wall and 1.3–2.3% TPOT at M=2–8. Most of the per-call kernel saving is diluted by the rest of the decode step.
