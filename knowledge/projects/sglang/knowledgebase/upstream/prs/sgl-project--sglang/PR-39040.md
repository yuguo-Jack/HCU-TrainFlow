# Fix/encdec decode paged alloc row offset

[Upstream PR](https://github.com/sgl-project/sglang/pull/39040) · state: open · merged: False

## Original PR description

## Motivation
For encoder-decoder models the encoder KV is prepended to the request's
    req_to_token row, so decoder position L lives at row position
    encoder_len + L. `alloc_for_decode` already accounts for that when writing
    (locs = encoder_lens + seq_lens) but not when computing the paged
    allocation: last_loc was read at `row[seq_len - 1]` and the new-page
    decision used the encoder-stripped seq_len.

At page_size > 1 that makes `last_loc + 1` resolve to `row[L]` -- the slot
    already held by encoder position `L` -- so the row stops satisfying
    `row[j] == page[j // page_size] * page_size + (j % page_size)`. The paged
    free path relies on that invariant: free_segment() samples one page
    representative every page_size row entries, so an aliased row makes it
    name the same physical page twice and `available_size()` grows by one page
    per request until the idle pool-leak invariant aborts the scheduler.


## Modifications
Use the row length (encoder_lens + seq_lens) for last_loc, for the
    seq_lens handed to alloc_decode, and for the CPU mirror feeding
    `get_num_new_pages`. `page_size == 1` takes the non-paged branch before any
    of this runs, so default CUDA behaviour is unchanged, as is every
    non-encoder-decoder model.

- SKRohit · comment · 2026-09-23T10:52:58Z · [source](https://github.com/sgl-project/sglang/pull/39040#issuecomment-5793544042)

@mingfeima and @Valentine233  

The issue is the allocation of the same slot indices in `req_to_token` for both encoder and decoder tokens. And it happens due to the following logic:

- `alloc_for_extend` allocates the tokens based on seq_length=1504 (1500 encoder tokens coming from the encoder and 4 decoder prompt tokens)
- Then, for encoder decoder modesl we have this condition in scheduler:
```
if self.model_config.is_encoder_decoder:
    self.prepare_encoder_info_extend(input_ids, seq_lens)
```
this method `prepare_encoder_info_extend` trims seq_lens to 4 i.e. `seq_lens[i]      -= encoder_len`. This seq_length resetting is required for decoder self-attention. 

- But inside `alloc_for_decode`, while calculating `out_cache_loc` we use the modified `seq_lens` of 4 instead of 1504, which returns the same slot index as for `seq_lens` 4, which is already allocated for the encoder. 

Here is what is happening with slot indices of `req_to_token` during prefill and decode allocation: 

**_alloc_for_extend(batch)_** 

| Field | Value |
|---|---|
| IN (off self) | `prefix_lens=[0]`, `extend_lens=[1504]`, `seq_lens=[1504]`, `extend_num_tokens=1504`, pools |
| OUT | `out_cache_loc = 1504 slot numbers`, `req_pool_indices = [3]` |
| SIDE EFFECT | fills `req_to_token[3, 0:1504]` |

1504 tokens at page_size 128 → 12 pages (1536 slots; last page partly unused):

```text
req_to_token[3] =
  [ P0*128+0   ... P0*128+127 | P1*128+0 ... | ... | P11*128+0 ... P11*128+95 ]
    |--------- row[0..127] ---------|                         |--- row[1408..1503] ---|
```

invariant:  `row[j] == P[j//128]*128 + (j % 128)`      ✓ page-consistent

**_prepare_encoder_info_extend(input_ids, seq_lens)_** 

Derive the offset:
encoder_lens_cpu = [1500]    # from req.multimodal_inputs.num_image_tokens
encoder_cached   = [False]   # prefix_indices (0) < 1500 → encoder KV not cached yet
self.encoder_lens = tensor([1500])

Strip the dummies (the rebase):
seq_lens[0]:        1504 → 4          # -= encoder_len
input_ids[0]:    1504 ids → 4 ids     # [1500:]
extend_lens[0]:     1504 → 4
extend_num_tokens:  1504 → 4

Split the one allocation in two:
`encoder_out_cache_loc = out_cache_loc[0    : 1500]`   # 1500 slots → cross-attn writes here
`out_cache_loc         = out_cache_loc[1500 : 1504]`   #    4 slots → self-attn writes here

Fix per-req bookkeeping:
req.extend_range.start: 0 → 1500
req.logprob_start_len = max(old, 1500)
assert len(out_cache_loc) == extend_num_tokens        # 4 == 4 ✓

State after prefill

In `req_to_token[3]`:  row[0..1499] = encoder KV   │   row[1500..1503] = decoder KV
`self.seq_lens     = [4] `     ← now DECODER-ONLY
`self.encoder_lens = [1500]`   ← the offset, parked separately

The forward pass now runs on 4 tokens, not 1504 — but 1504 KV slots are reserved and recorded.

_**alloc_for_decode(batch, token_per_req)**_
| Field | Value |
|---|---|
| IN | `seq_lens=[4]` stripped, `encoder_lens=[1500]`, `req_pool_indices=[3]`, `page_size=128` |
| OUT | 1 slot |
| SIDE EFFECT | writes it to `req_to_token[3, 1500+4] = row[1504]` |

But the issue is after `seq_lens -= 1500` in `prepare_encoder_info_extend` any logic to access row positions should use `encoder_lens + seq_lens`   which is not being followed in `alloc_for_decode`. It still uses: 
```
last_loc = batch.req_to_token_pool.req_to_token[
            batch.req_pool_indices, seq_lens_gpu - 1
        ]
seq_lens_next = seq_lens_gpu + token_per_req
```
where `seq_lens_gpu` is only the decoder length, i.e., 4. 

Hence, the same slots are allocated for decode tokens. But this does not overwrite the KV tokens of the encoder because, in Whisper and other encoder-decoder models, the pool for decoder cross-attention is different:
```
encoder self-attn layers   : 0 … E-1              → caches nothing at all
decoder self-attn layers   : E … E+D-1            → writes DECODER KV
decoder cross-attn layers  : E+D … E+2D-1         ← decoder_cross_attn_layer_id
                                                    = encoder_layers + decoder_layers + layer_id
                                                  → writes ENCODER KV
```
And hence do not cause any accuracy issues. However, when we free the pages after a request finishes, the same page gets released twice; hence, in logs we will see `available tokens > total tokens`, the token difference is precisely == `page_size` and the scheduler fails.
```
pool memory leak detected! [full] total=52352, available=52480, evictable=0, protected=0, ...
# next request:
pool memory leak detected! [full] total=52352, available=52608, ...   
...
ValueError: pool memory leak detected!   (scheduler.py on_idle -> _report_leak)
SIGQUIT received. ... It usually means one child failed.
```
And this double release is happening because of `free_segment` logic: 

```
reps = free_index[::ps]    # one entry per page, ps=page_size, 
self.free_page_ids(reps // ps) # consecutive groups of page_size row entries belong to exactly one page
```

See in the example below:
```
Whisper, page_size = 128. Prefill gave 12 pages (P0..P11) covering row positions 0–1535. Decode then wrote row[1500 + L] = row[L].

At 33 output tokens the row is 1537 long, so the stride reaches one more position:

reps = row[0], row[128], row[256], … , row[1408],   row[1536]
        └────── 12 entries from the clean prefill region ──┘   └─ the aliased one ─┘

row[0]    = P0*128 + 0   → // 128 →  P0
row[128]  = P1*128 + 0   → // 128 →  P1
   …
row[1408] = P11*128 + 0  → // 128 →  P11
row[1536] = row[36]                             ← aliasing: row[1500+36] == row[36]
          = P0*128 + 36  → // 128 →  P0         ← ★ P0 AGAIN

So reps // ps = [P0, P1, …, P11, P0] — 13 entries, 12 distinct. free_page_ids trusts its contract and doesn't dedup, so _release_page_ids receives P0 twice, and the free list ends up holding it twice.
```

And this is the exact bug that is captured when using `SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_IDLE=1` which is the default now in SGLang.
