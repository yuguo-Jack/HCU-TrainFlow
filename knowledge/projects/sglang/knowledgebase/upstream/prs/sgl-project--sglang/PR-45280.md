# [Perf] detokenizer: Add SGLANG_BATCH_TOKENIZER_OUTPUTS to opt out of grouped return sends

[Upstream PR](https://github.com/sgl-project/sglang/pull/45280) · state: closed · merged: True

## Original PR description

## Motivation

#44288 made the detokenizer group its return IPC sends by tokenizer worker: a batch of N requests spread over W workers now costs W sends instead of N. That is the right default for throughput serving.

For latency-sensitive streaming workloads it is not free. Every scheduler step emits one small chunk per request, and each tokenizer worker only wants its own chunk as soon as it exists. With grouping, every reply sits behind a per-step packing hop, and the first reply of a step waits for the whole batch to be split before anything is sent. Deployments that care more about per-chunk latency than about IPC message count need a way back to per-request delivery without giving up anything else.

## Modifications

- `python/sglang/srt/environ.py`: add `SGLANG_BATCH_TOKENIZER_OUTPUTS` (`EnvBool`, default `true`).
- `python/sglang/srt/managers/multi_tokenizer_mixin.py`: `_send_output_to_tokenizer_workers` only calls `_split_batch_by_key` when the flag is on. When it is off it takes the existing per-request path, the same one already used when a batch cannot be grouped.
- `test/registered/unit/managers/test_multi_tokenizer_mixin.py`: the return-path test now runs under both settings (via `envs...override`) and asserts that grouped and per-request delivery send the same rids and strings to the same workers in the same order, and that the input batch is not mutated either way.

Nothing else changes. The GPU batch, the scheduler, and the output content are identical in both modes; only the number and shape of detokenizer -> tokenizer-worker messages differ. The default keeps today's behaviour.

## Accuracy Tests

N/A. This only changes how many IPC messages carry the same outputs between processes.

## Speed Tests and Profiling

`python -m pytest test/registered/unit/managers/test_multi_tokenizer_mixin.py`: 23 passed, 4 subtests passed. The new subtests cover both values of the flag on a batch whose owners are non-contiguous (`[worker-b, worker-a, worker-b]`), so the per-request path is checked for order as well as destination.

With the flag off, a step with N requests across W workers goes back to N sends, as before #44288; with it on (default) the W-send grouping from #44288 is unchanged.
