# [model-gateway] Fix usage accounting: clamp worker token counts and widen sums to u64

[Upstream PR](https://github.com/sgl-project/sglang/pull/43889) · state: open · merged: False

## Original PR description

Fixes #43888

## Summary

The gRPC routers aggregate worker-reported token counts (proto `int32` fields) for the client-visible `usage` fields and for token metrics using `u32` arithmetic with no clamping of the incoming values. This PR makes the accounting robust by applying, consistently across all usage paths, the convention the embedding/classify processors already use (`.max(0)`) plus wider sums:

- **Clamp at ingestion**: every worker-reported `prompt_tokens` / `completion_tokens` / `cached_tokens` is clamped with `.max(0)` before entering an accumulator, so a `-1` error sentinel can no longer surface as `4294967295` after an `as u32` cast.
- **Widen sums to `u64`**: per-choice sums (`build_usage`), per-stream chat maps, and the `/generate` streaming completion accumulators (both the plain and the input-logprobs variant) now accumulate in `u64`.
- **Saturate at the schema boundary**: the OpenAI `usage` schema stores counts as `u32`; sums that exceed that range now saturate at `u32::MAX` instead of wrapping, so a reported total can never silently drop below the true value.
- **Exact metrics**: streaming metrics (`input_tokens` / `output_tokens`, already `u64`) now receive the exact totals instead of the wrapped ones.

Paths touched: `routers/grpc/common/response_formatting.rs` (`build_usage`, used by the regular and harmony non-streaming chat paths), `routers/grpc/regular/streaming.rs` (chat streaming usage chunk + maps, `/generate` streaming accumulators, streaming metrics), `routers/grpc/regular/processor.rs` (non-streaming `/generate` meta_info), `routers/grpc/harmony/streaming.rs` (harmony chat streaming + Responses streaming usage), and two small helpers in `routers/grpc/utils.rs`.

## Verification

Unit tests added in `response_formatting.rs` cover: exact sums within range, `n`-choice sums past `u32::MAX` (saturate, don't wrap), negative prompt and completion reports (clamp to 0). Full workspace: `cargo test --lib` 400 passed / 0 failed; `cargo fmt --check` and `cargo clippy` clean.

End-to-end re-verification of the three reproductions from the issue, using a mock gRPC worker registered through `POST /workers` behind the fixed release binary:

| Case | Before (buggy) | After (fixed) |
|---|---|---|
| 5 choices x `prompt_tokens=1,859,468,194` (true sum 9,297,340,970) | `total_tokens = 707,406,378` (wrapped) | `prompt_tokens = total_tokens = 4,294,967,295` (saturates at the `u32` schema maximum; computed exactly in `u64` internally), consistent with parts |
| `/generate` stream of 2^32+66 token ids (1227 x 3.5M + 467,234 + 128) | count collapses `4,294,967,234 -> 66` mid-stream | final `meta_info.completion_tokens = 4,294,967,362` (exact, no wrap) |
| Worker reports `prompt_tokens = -1`, `completion_tokens = 67` (streaming chat, `include_usage`) | `{4294967295, 67, 66}` (total < completion) | `{0, 67, 67}` (clamped, total == parts) |

Note on the first case: the `usage` wire fields are `u32` in the `openai-protocol` schema, so a sum larger than `2^32-1` cannot be represented exactly; saturation is chosen deliberately so the failure mode is an over-bounded value rather than an undercount. If exact reporting for such aggregates is wanted, that would require widening the schema fields (out of scope here).

The hardening note for the PD router bootstrap arrays (`routers/http/pd_router.rs`) from the issue's secondary section is intentionally not addressed in this PR — a batch-item cap is a policy decision that deserves its own discussion.
