# [HiCache][PD] Allow DSA index-K elision under HiCache and disaggregation

[Upstream PR](https://github.com/sgl-project/sglang/pull/41769) · state: open · merged: False

## Original PR description

DeepSeek-DSA models mark most layers `shared` in `indexer_types`: those layers reuse the previous producer layer's top-k indices and never read an index-K of their own. GLM-5.2 has 78 layers, of which **21 are producers and 57 are shared**.

`skip_topk_layers` already lets the device pool skip allocating index-K for the shared layers — `index_key_cache` gives those layers 0 pages, and the compress tail likewise. But `_should_elide_dsa_index_k()` refused whenever HiCache or PD disaggregation was enabled:

```python
return (
    not memory_config.enable_hisparse
    and not is_draft_worker
    and not memory_config.enable_hierarchical_cache      # <-- here
    and not memory_config.enable_unified_cache_external_linker
    and get_disagg().disaggregation_mode == "null"       # <-- and here
)
```

That covers most serving deployments, so on a real deployment the device buffers for all 57 shared layers stayed allocated.

Both conditions existed for the same reason: HiCache and the PD transfer walk the per-layer buffer list, and eliding a layer leaves a zero-sized entry in it.

#38426 handles the HiCache half by building the indexer host pool from the
producer-layer set. **This PR handles the PD transfer half and removes the two conditions.**

## Modifications

Dropping the conditions is one change; the other is making the DSA transfer tolerate the zero-sized entries.

That part is subtle because the two peers do not register the same layer span. A PP prefill stage registers only its own layers while decode may register the whole model, so the elision patterns are **offset, not different**. `_send_kvcache_generic` already realigns the two via `get_mla_kv_ptrs_with_pp` (which slices `dst[prefill_start_layer : prefill_start_layer + n_src]`), but that happens after the per-entry inspection. So this aligns the spans up front with the same `_mla_kv_entry_span_with_pp` helper, and then:

- **drops** entries elided on both peers, rather than issuing zero-length DMAs;
- **skips** the entry (no bytes move) when it is elided on exactly one peer. For DSA this is expected: e.g. a dense HiSparse decode elides index-K for shared-topk layers while prefill still allocates it, so nothing needs to be transferred for that layer. Other state types are unaffected and still go through the stride check.

Re-slicing inside `_send_kvcache_generic` is then a no-op: its fast path returns unchanged once the two pointer lists have equal length.

## What breaks without the transfer-side half

Relaxing the two conditions alone is not enough. Once non-producer layers are elided, their device entries become zero-sized, and `set_transfer_blocks()` has no `item_len == 0` case:

```python
src_addr = src_ptr + int(prefill_index[0]) * item_len   # item_len == 0 -> src_ptr
dst_addr = dst_ptr + int(decode_index[0]) * item_len
length   = item_len * len(prefill_index)                # 0
transfer_blocks.append((src_addr, dst_addr, length))    # queued anyway
```

So every elided layer contributes a zero-length block, pointing at the empty allocation, for every transfer. That is silent: no error is raised, the blocks are simply handed to the transfer engine. This PR filters those entries out before the DMA instead.

The ordering matters too, and is easy to get wrong. A PP prefill stage registers only its own layers while decode may register the whole model, so the two elision patterns are **offset, not different**. Any per-entry comparison has to happen after the spans are aligned — otherwise a PP4 stage's 20 entries are compared against the decode's 78 and nothing lines up. `_send_kvcache_generic` already performs that alignment via `get_mla_kv_ptrs_with_pp`, but it does so *after* the per-entry inspection point, which is why this PR aligns up front with the same `_mla_kv_entry_span_with_pp` helper.

We hit exactly this ordering problem on an internal tree carrying an equivalent elision patch plus a stricter layout check: with PP prefill and elision forced on, **0 of 4,958 warmup requests completed in 4 hours**, every one parked in flight, because the check compared 20 prefill entries against 78 decode entries and rejected them. The same topology *without* elision ran to completion, since with no zero-length entries the check is skipped and the existing `prefill_start_layer` slicing handles PP correctly.

## Accuracy Tests

No accuracy evaluation was run.

The change should not alter what is computed: shared layers never read their own index-K, so not allocating it is expected to be a no-op for model output. That argument is structural — it rests on `dsa_layer_skips_topk()` and the existing `skip_topk_layers` path, not on an experiment run here. An accuracy comparison with elision on vs off, on a DSA model with HiCache and PD disaggregation enabled, is the right check and I have not run one.

## Benchmarking and Profiling

The win is KV cache capacity, and only that. The same index-K is computed either way; eliding the non-producer layers' device buffers hands that memory back to the KV pool, so the same GPU footprint holds more tokens. There is no throughput claim here, and the measurements below say so explicitly.
