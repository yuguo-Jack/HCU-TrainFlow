# [Doc] [NVIDIA] cookbook: Recommend the CuTe DSL all-reduce fusion backend for GLM-5.2 GB300 TP4 low latency

[Upstream PR](https://github.com/sgl-project/sglang/pull/47273) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

In every GLM-5.2 decoder layer, the attention output and the MLP output (an MoE in 75 of the 78 layers) are each summed across the tensor-parallel ranks (an all-reduce), added to the residual and normalized (RMSNorm). All-reduce fusion runs these three steps as one kernel. On one Blackwell node at TP4, SGLang turns it on by itself with `--flashinfer-allreduce-fusion-backend auto`, which resolves to FlashInfer's `mnnvl` backend (MNNVL is multi-node NVLink; these kernels exchange data over the NVLink fabric). That fusion covers batches of up to 2048 tokens; larger prefill chunks fall back to an NCCL all-reduce and a separate RMSNorm. The opt-in `cutedsl` backend uses FlashInfer kernels written in CuTe DSL (CUTLASS's Python kernel language) over the same fabric. It fuses batches up to `--max-prefill-tokens` (8192 in this deployment) and, for batches of up to 192 tokens, also folds in the MoE finalize (the weighted sum of the selected experts' outputs) and the shared-expert add.

This PR adds a Configuration Tips bullet to the GLM-5.2 cookbook that recommends `cutedsl` for one deployment: GB300 NVFP4, aggregated TP4, concurrency 1 (c1), a point of the page's Agentic Long-Context section. That section lists commands measured with AgentX, SemiAnalysis InferenceX's agentic-coding benchmark, which replays recorded multi-turn coding-agent sessions against the server. The bullet gives the measured effect, the builds the flag needs (those with #45565, which raised the default prefill CUDA-graph size for MLA models from 2048 tokens to min(8192, chunked-prefill size)), the limit of the evidence to c1, and a memory note. Defaults and runtime code do not change; the default stays `auto` because only this one deployment was measured. The PR also corrects the server-arguments row for this flag, which does not list `cutedsl` and says `auto` picks `mnnvl` on SM90 (the code picks `trtllm`).

Impact:

- **Decode (measured):** time per output token about 3.4% lower in three runs: −3.45% [95% CI −3.65, −3.18] (default vs default +0.04%), −3.41% [−3.59, −3.16] in a replicate, and −3.47% [−3.84, −2.99] in a shorter third run. GLM-5.2 NVFP4, one GB300 node, TP4, c1, AgentX replay, 148 paired requests.
- **TTFT (measured):** not worse. p90 −3.94% [95% CI −16.55, +4.43] and −4.63% [−16.22, −0.68] in the two 1,200-s runs, and +2.49% [−11.17, +67.82], within its noise, in the 900-s third run; p50 not worse in any run.
- **Throughput (measured):** +1.45% input + output tokens/s per GPU against the mean of the two default arms (replicate +1.38%).
- **Accuracy (measured):** GPQA-Diamond 0.9116 → 0.9003, −1.14 points [95% CI −2.78, +0.51], no significant change; MTP accept length 2.729 → 2.742.
- **Scope (measured):** c1 only. In a GB300 microbenchmark over 4–256 tokens per call, the CuTe DSL kernel was faster than `mnnvl` only at 4–12 tokens, and 1.05–1.13× slower at 16–20 and 1.05–1.10× slower at 96–256 tokens, so the bullet tells readers to re-measure before raising concurrency.
- **Builds without #45565 (measured):** on `nightly-dev-20261016-a93f16f0` the flag raised p50 TTFT by 9.0% (decode still −3.24%), so the bullet names a minimum build.
- **Memory (measured):** with the flag, PyTorch's caching allocator held about 8 GiB more idle cache per GPU while serving at `--mem-fraction-static 0.83`, leaving 0.45 GiB free for allocations outside PyTorch; emptying the cache brought both backends to the same level (within 0.8 GiB). No request failed.

<details>
<summary>Precision (code reading of SGLang <code>8252e3af</code> and FlashInfer 0.7.2, plus server logs)</summary>

- No dtype or quantization change. The two CuTe DSL kernels SGLang calls (all-reduce + residual + RMSNorm, and MoE finalize + all-reduce + residual + RMSNorm) read and write BF16 and accumulate in FP32; neither has an FP8 or FP4 output.
- One narrow change. In a `cutedsl` process SGLang turns off its older MNNVL all-reduce for the whole process, so two non-fused all-reduces move: the target model's last-layer all-reduce (it feeds the final norm, the logits and the draft's input hidden states) and the draft (MTP) layer's all-reduces. Up to 1,365 tokens they now use SGLang's custom all-reduce, which also accumulates in FP32. For 1,366–2,048-token prefill chunks they use NCCL, which SGLang runs with `NCCL_NVLS_ENABLE=0` (Ring/Tree, BF16 rounding at each hop) instead of MNNVL with FP32 accumulation. The default backend already sends every chunk above 2,048 tokens through that same NCCL path.
- The draft runs as shipped. The MTP layer never uses the CuTe DSL fusion (`install_cutedsl_fusion` returns `None` in speculative scope, and GLM-5.2's NextN layer skips it; the logs show 78 of 78 target layers fused on each rank), and `SGLANG_NVFP4_CKPT_FP8_NEXTN_MOE` is not set.
- Outputs are not bitwise identical to the default backend, because rounding points and summation order differ.

</details>

## Speed Tests and Profiling

**Which point, and why.** The low-latency end: GB300 NVFP4, aggregated TP4, c1 (the GLM-5.2 GB300 TP4 point of the Agentic Long-Context section). SGLang applies this fusion only to TP deployments without DP attention or a MoE all-to-all backend, so the high-throughput DP-attention points do not use it at all. At c1 a decode step usually carries one request with 5 draft tokens, so 5–15 tokens per all-reduce. Its gain most likely comes from faster small all-reduces (inferred: in the microbenchmark below, the CuTe DSL kernel takes 0.86–0.89× the time of `mnnvl` at 4–12 tokens). The same microbenchmark shows it slower at 16–20 and 96–256 tokens, which higher concurrency reaches (for example 4 or more requests with 5 draft tokens), so this PR recommends the flag only for c1.

**Why an AgentX replay rather than a static workload.** TTFT depends on prefix-cache hits and on the sizes of the prefill chunks, and this flag's effect on TTFT depends on chunk size: the regression on the older build came from chunks above 2,048 tokens. In this trace 95.5% of prompt tokens were read from the prefix cache, and 2,049–8,192-token chunks were 203 of 290 prefill forwards and 94.5% of new prefill tokens (default arm; counts include the client's warm-up phase). A fixed-length random workload would not reproduce that mix. Decode time per token was measured in the same runs.

**Setup (measured).** One GB300 node, 4 GPUs, image `lmsysorg/sglang:nightly-dev-20261026-8252e3af`, model `nvidia/GLM-5.2-NVFP4`, the AgentX command for this point launched with `sglang.launch_server` (no Dynamo frontend), AgentX client 1.0.7 at c1, simulated MTP acceptance 3.33 (InferenceX's golden value). One node per run, fresh server per arm, 1,200 s windows, order: warm-up, default, `cutedsl`, default. Run 1 used the image's own SGLang; the replicate and the GPQA runs used a newer SGLang `main` tree laid over the same image, whose files on the flag's path are identical to the image's except for an opt-in row cap that was left unset (Builds, below).

**Counter-example on an older build (measured).** On `nightly-dev-20261016-a93f16f0` (which reports SGLang `c15edf31`, the image's build commit; FlashInfer 0.7.1), prefill CUDA graphs stopped at 2,048 tokens, so larger chunks ran eagerly. The same A/B (default / `cutedsl` / default, 1,200 s each, one node) gave decode −3.24% [−3.50, −3.03] (per-request ratio), but raised TTFT p50 from 274.7 ms to 299.5 ms (+9.0%; +9.6% over the paired requests). #45565 raised the MLA prefill CUDA-graph cap to min(8192, chunked-prefill size). With it, every 2,049–8,192-token chunk in runs 1 and 2 ran in a CUDA graph, and p50 TTFT no longer rises. <details>
<summary>GPU memory headroom (measured)</summary>

- In each of the four `cutedsl` arms on this image (runs 1-3 and the excluded run), GPU memory in use while serving (nvidia-smi) settled about 8 GiB per GPU above the default arms: about 276.2 GiB against 268.2 GiB, out of 277.5 GiB. It then stayed flat for the rest of each window.
- **It is PyTorch's cache.** In run 3, after each arm's window we paused the server and called `/continue_generation` with `torch_empty_cache`. PyTorch's reserved memory went from 271.8 to 231.3 GiB with the flag and from 263.0 to 231.3 GiB without it (each rank logs it), and nvidia-smi then read 235.7 GiB with the flag against 236.5 GiB for both default arms. So the extra 8 GiB was idle cache, which PyTorch reuses and frees when an allocation fails; at startup the flag uses about 0.8 GiB less.
- What this does not show: whether the flag's peak working set during a forward is larger. Growth of the cache means only that the allocator once needed more segments, by peak or by fragmentation.
- Allocations outside PyTorch cannot use that cache. While it is held, about 0.45 GiB is free, and each `cutedsl` arm logged 64 warnings when Triton kernels were first loaded during serving (16 loads of 8 distinct kernels on each of 4 ranks, most at the first moment two requests were running): `Triton kernel '...' device-loaded after serving started (free device mem: 0.45 GiB). Pre-load it during engine init to avoid CUDA OOM.` No default arm logged it (threshold 1 GiB). Every load and request succeeded.
- The likely source of the cache (code reading, not tested): long-context prefills allocate large FP32 logits scratch blocks for the DSA indexer (GLM-5.2's sparse-attention token selector) in eager code, and which blocks the allocator keeps depends on the history of earlier allocations; the CuTe DSL workspace itself is about 267 MiB per rank.
- Only `--mem-fraction-static 0.83` at c1 was tested with this flag. A lower fraction may not restore headroom, because the indexer's scratch budget during prefill graph replay is 0.2 × (1 − mem-fraction-static) × GPU memory (code reading), so the cache can grow into the freed memory too.

</details>
