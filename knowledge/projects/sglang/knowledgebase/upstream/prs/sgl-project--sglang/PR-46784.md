## Summary

**TL;DR: After a prefill, this PR runs the MTP draft's attention, DSA indexer and MoE only for each request's last prompt token, the only one whose draft output is used; every other prompt token only writes its draft KV cache.** On GLM-5.3-Flash on H200, input throughput rises by **1.8–5.3%** for 2k- to 32k-token prompts at 8 concurrent requests and 8k-token prompts at 32 and 64, and by **3.1–3.8%** for 8k-token prompts sent one at a time, with BF16 and FP8 KV caches and MTP 5/1/6 and 1/1/2. It applies with no flag to the GLM-5 series and DeepSeek-V3.2 on CUDA; main's path is kept for other models and platforms, attention DP, context parallelism, some FP8 KV cache setups and the other settings listed in Modifications, and for prefills with no request longer than 2048 tokens or with 4096 or fewer tokens besides each request's last.

- **Performance** (GLM-5.3-Flash on H200): input throughput **1.8–5.3% higher** and mean TTFT 0.7–5.8% lower for 2k- to 32k-token prompts at 8 concurrent requests and 8k-token prompts at 32 and 64; **3.1–3.8% higher** one request at a time with 8k-token prompts in every setup, and 2.8–3.6% with 4k, 6k or 32k in some. The other rows and decode are within noise (~0%).
- **Accuracy:** effectively lossless: the draft latent KV of every prompt token but the last is byte-identical to main's with BF16 and FP8 KV caches, and GSM8K, RULER2 (16k-token prompts, where the split runs) and the acceptance length are within measurement error of main's.
- **Cost:** about 3.5 ms of CPU time per split prefill, so only prefills large enough to pay it back are split; no new flag or environment variable; the same KV cache size as main's, and free memory and time to ready within main's range.

## Motivation

**We found this in a GPU profile of main on GLM-5.3-Flash with an 8k-token prompt: the MTP draft extend after the prefill took 4.4% of the prefill step's GPU time (target + draft), and the draft's sparse attention and indexer (DSA, DeepSeek Sparse Attention) alone 2.7% of the same step, although the draft's output is used only for the last prompt token.** With MTP (multi-token prediction) speculative decoding, SGLang runs the model's one-layer NextN draft (`--speculative-algorithm EAGLE`; below, MTP s/k/n means `--speculative-num-steps s --speculative-eagle-topk k --speculative-num-draft-tokens n`). After each prefill, `EagleDraftWorker._draft_extend_for_prefill` runs the draft's ordinary forward on all prompt tokens: embedding, `eh_proj` (which joins the token embedding with the target's hidden state) and the decoder layer. It keeps the hidden state and logits only for each request's last token (`CaptureHiddenMode.LAST`); they seed the first draft step.

The other tokens matter only for the draft KV they write: the latent KV that later draft steps attend to and, for DSA, the indexer keys those steps score. Both come from the token's input to the draft layer, before attention, and the draft has no later layer, so those tokens' attention, indexer top-k and MoE change nothing. Main computes them because the ordinary forward has no KV-only mode: in a model with more layers, each layer's output feeds the next layer's KV. With DSA they are the costly part: above the dense-attention length (2048 tokens), every token scores all earlier tokens in the indexer and attends to its top-k.

This PR splits the draft extend into a KV-only pass over every token but the last, then the existing pass over the last tokens. The idea holds for any one-layer draft whose cache is attention KV; this PR implements it for the DSA NextN draft (the GLM-5 series and DeepSeek-V3.2) on CUDA and measures it on H200. Other drafts, such as DeepSeek-V4's, are separate code and keep main's path.

## Modifications

Batches that do not meet the conditions in the "When a batch is split" note, and every draft that is not a DSA NextN draft on CUDA, run main's code: the existing draft extend moves into `_run_draft_extend_for_prefill` with no change in behaviour (its context for the optional KV cache canary check, `--kv-canary`, moves into the helper `_draft_canary_ctx`, which the KV-only pass also enters).

- **`python/sglang/srt/speculative/eagle_utils.py`**: `should_split_prefill_draft_extend` decides per batch (the "When a batch is split" note); `split_prefill_draft_extend` builds two sub-batches from the prefill batch: every request's tokens but its last (positions and KV slots as in the prefill), and the last tokens (one new token per request, with its other tokens as cached prefix). For a chunked prompt, the last token is the chunk's last token.
- **`python/sglang/srt/speculative/eagle_worker_v2.py`**: `_draft_extend_for_prefill` sends a split batch to `_draft_extend_for_prefill_split`, which runs the KV-only pass and then the existing pass on the last tokens. `_can_split_prefill_draft_extend` (once at startup) checks the model and the server-wide settings in the "What keeps main's path" note; `should_split_prefill_draft_extend` checks the per-batch ones.
- **`python/sglang/srt/speculative/standalone_worker_v2.py`**: `StandaloneDraftWorker` skips `EagleDraftWorker.__init__`, so it sets `can_split_prefill_draft_extend = False` itself and keeps main's path.
- **`python/sglang/srt/models/deepseek_nextn.py`, `deepseek_v2.py`, `deepseek_common/attention_forward_methods/forward_mha.py`**: `forward_kv_only` on the draft model, decoder layer and attention: embedding, `eh_proj`, the latent KV (RoPE applied, written with the existing `_set_mla_kv_buffer`) and the indexer keys. No query up-projection, attention, MoE or LM head. The `eh_proj` step is shared with the draft's existing forward (`_project_with_target_hidden`), and the latent KV is written as in `forward_normal_prepare` (`_split_latent_cache`, factored out of it, and `_set_mla_kv_buffer`); the byte comparison shows it matches main's.
- **`python/sglang/srt/layers/attention/dsa/dsa_indexer.py`, `dsa_indexer_kpool.py`**: `forward_k_only` writes the indexer key cache through the existing write paths (`_forward_cuda_k_only`, and `_forward_cuda_skip_logits` for GLM-5.3-Flash's KPool indexer, which pools the indexer keys of groups of tokens) without the top-k.
- **`python/sglang/srt/speculative/eagle_info.py`**: `EagleDraftExtendInput.kv_only`, so the KV-only forward returns no logits.
- **`test/registered/unit/spec/test_prefill_draft_extend_split.py`** (new, `base-a-test-cpu`): the two sub-batches together give the prefill's tokens, positions and KV slots; each pass sets its own token count for the MLP sync (`global_num_tokens`); the split is skipped on a one-token extend, no request beyond the dense-attention length, too few KV-only tokens, a batch that fits a captured draft prefill CUDA graph, multimodal without the target's embeddings, the four FP8 DSA prefill backends, TRT-LLM's fused-RoPE FP8 write, decode context parallelism or `--enable-return-indexer-topk`, and deleting any one of these checks makes a case fail.
- **`test/registered/unit/layers/test_kpool_planner_cpu_mirror.py`**: an extend split into "all but the last token" and "the last token" reads the same KPool positions and leaves the same partly filled last group of pooled indexer keys as one extend.

Design notes:

- **When a batch is split.** The KV-only pass is one more draft forward: on H200 it adds about 3.5 ms of CPU time per prefill, which the attention it skips has to pay back. A batch is split only if two conditions hold. First, some request, counting its cached prefix, is longer than DSA's dense-attention length (`SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD`, 2048 for these models): up to that length, attention is dense and cheap, and the last-token pass would read the prompt's KV back from the cache. Second, the KV-only pass has more than 4096 tokens and more than a captured draft prefill CUDA graph covers, since a graph already runs the full layer cheaply (the NextN draft captures none today). With one request in the FP8, TP4 setup on H200, the split starts to gain between 4k and 6k tokens. The bound is one constant on every CUDA GPU; on hardware with a different CPU/GPU balance, the break-even point moves.
- **What keeps main's path.** Non-CUDA platforms; drafts that are not DSA NextN; attention DP (the sub-batches would differ across ranks); prefill context parallelism (its draft forward runs the model body directly and never takes the KV-only path); decode context parallelism (the split is not validated with its KV layout); `--enable-return-indexer-topk` (it records a top-k for every token); input or replaced embeddings and two-batch overlap; multimodal batches without the target's embeddings; any request with a one-token extend. With an FP8 draft KV cache, the split is off for the whole server in two cases: when TRT-LLM fuses RoPE into the FP8 write (Blackwell's default for GLM-5.3 and DeepSeek-V3.2; GLM-5.3-Flash's draft has no RoPE, so it still splits with TRT-LLM), and with the DSA prefill backends `flashmla_sparse`, `flashmla_sparse_q8`, `triton_sparse_mla` and `flashmla_auto`, which read fresh KV when no request has a prefix while the last-token pass reads the cache.

## Accuracy Tests

**Effectively lossless.** The KV-only pass writes what main writes. Only the last-token pass computes outputs, from the same layer and inputs in a smaller batch, so they differ from main's only through the batch shape (the last token's draft hidden state by at most 0.172 in relative L2; the first draft token is the same in every case in the byte-comparison table), and the target model still verifies every draft token. **Measured: GSM8K, RULER2 and the acceptance length are within measurement error of main's, and the draft latent KV of every token but the last is byte-identical to main's with BF16 and FP8 KV caches.** The byte comparison and the first-draft-step test ran at `9859a7da96` (on main `c2e5742464`), and GSM8K, RULER2 and the acceptance length on an earlier build that differs from `9859a7da96` only in checks this setup does not reach; the byte comparison was repeated on this PR's commit.

### End to end: GSM8K, RULER2, acceptance length
- **GSM8K** (sgl-eval 0.1.3, all 1,319 questions; the server and settings of the CI test `test_glm53_flash_h200_low_latency.py`, TP8, MTP 5/1/6; settings under Accuracy command): 97.04% with this PR and 97.35% on main, within the standard error of the difference (about 0.64 points). No request errors. Its prompts are short, so it checks the unchanged path.
- **RULER2** (sgl-eval 0.1.3 `ruler2` at 16,384 tokens, 50 questions in each of its 12 tasks; the same server and settings): 95.27% with this PR and 95.50% on main, within the standard error of the difference (about 1.2 points). Its prefills are split, except some short final chunks.
- **Acceptance length.** With 8k-token prompts at 8 concurrent requests and 256 output tokens, where prefills are split except some short final chunks, `bench_serving`'s accept length (accepted drafts plus the bonus token, up to 6) has a median over server restarts of 3.83 on main and 3.85 with this PR (ranges 3.77–3.85 and 3.73–3.89). The first draft step after a prefill takes its input from the last-token pass: with 300 RULER2 prompts (11k–16k tokens) sent one at a time, with temperature 0 and 2 output tokens (one verify step each), it accepted 3.56–3.57 of 5 drafts on average with this PR and 3.38–3.56 on main across server restarts.

**What the split costs, and why 4096.** A local probe (not part of this PR) ran the single pass and the split on alternate prefills in one FP8, TP4, MTP 5/1/6 server and timed both. The split adds about 3.5 ms of CPU time per prefill (3.2–5.1 ms across the batches and GPUs measured); with one 4k-token request it is the KV-only pass's kernel launches (1.3 ms), a second DSA metadata build (1.0 ms), the runner's batch setup (0.7 ms) and building the sub-batches (0.6 ms). Its GPU saving grows with the tokens: 8.3 ms with one 6k-token request, 10.8 ms with one of 8k and 11.0 ms with two of 4k. With one request of about 4k tokens or fewer, the GPU waits for the CPU in this setup, so splitting adds CPU time without a visible saving; the saving overtakes the cost between 4k and 6k tokens. Hence the bound of 4096: at 4k tokens the change is within noise, and from 6k it gains.

**Startup and memory:** the same KV cache size as main in every setup (3,828,736 tokens with BF16; 1,557,248 with FP8 and MTP 5/1/6; 1,659,648 with MTP 1/1/2), and this PR's free memory per GPU after CUDA graph capture (20.68, 35.80 and 36.29 GB) and time to ready (185 s, 130–131 s and 125 s) are within main's range.

### Draft KV, byte for byte

Same method as yours, with a local hook (not for this PR): for every batch that would be split, main's single pass ran first; then the draft's index-cache pages and KPool tail buffers were restored, the latent rows main had written were overwritten with 0x7F, and the split ran. The hook also recorded the slots each pass wrote. The bound was lowered to 0 so that every batch with a request longer than 2,048 tokens was compared. Load: 3k, 5k, 8k and 32k prompts one at a time (the 32k ones in 16,384-token chunks, so later chunks extend a prefix), 4k at 4 and 2k and 8k at 8 concurrent requests, and radix-cache hits (20,000 cached tokens, then 6,000 new). Counts are per rank and the same on all 8 ranks.

| GPU, KV cache (DSA prefill / decode) | split batches | latent rows of every token but the last that differ | same KV slots | first draft token the same |
|---|---|---|---|---|
| B300, FP8 (`trtllm` / `trtllm`) | 135 | **0 of 1,188,012** | 135 of 135 | 204 of 204 |
| H20, BF16 (`tilelang` / `tilelang`) | 197 | **0 of 1,187,971** | 197 of 197 | 243 of 245 |

The B300 row covers a write path the H200 table does not. With TRT-LLM and an FP8 cache, main's draft pass casts the latent KV to FP8 in `_forward_trtllm` (`mla_quantize_for_fp8_no_rope`) and stores the FP8 tensors, while the KV-only pass hands BF16 to the pool, which casts in `_write_mla_kv_buffer`. With TileLang both passes use the same pool write. The bytes match.

On B300 every index page that differs holds a split request's last token (113 of 4,798 touched pages), and the indexer's inputs on the KV-only rows (`x`, the key, the compress gate score) were identical in every batch.

On H20 one batch shape breaks that: extend lengths [268, 4108] after prefixes [3840, 0], i.e. 4,376 tokens in main's pass and 4,374 in the KV-only pass, seen in 4 of the 197 batches; in each of them all 19 index pages differ, on every rank. In the occurrence where the hook recorded the indexer's inputs, `x` is identical, but `k_norm(wk(x))` differs in 308 of the 4,374 rows and the compress gate score, a plain `F.linear(x, ...)`, in 1,084: the GEMMs return different bits at M = 4,376 and M = 4,374. So "pages that differ: never more than the split requests" holds only when those GEMMs give the same bits at both batch sizes. The latent KV is not affected.

On @Wangyuaneee's second question: in both setups the KV-only and last-token passes, which build their own plans instead of taking the target's `iteration_ids`, wrote exactly the slots main's pass wrote, in all 332 batches.

### Where the split pays on B300

Per draft extend on rank 0, median over batches. GPU work is measured behind a 60 ms GPU sleep, so the CPU had issued the whole pass before it started. 61 of 70 batches qualify; in the other 9 one pass waited on the GPU, each time on the first batch of a new size.

| KV-only tokens | batches | GPU work, single → split (ms) | CPU time, single → split (ms) |
|---|---|---|---|
| up to 2k | 3 | 1.34 → 0.95 | 9.6 → 14.2 |
| 2k–4k | 10 | 1.57 → 0.97 | 11.8 → 15.0 |
| 4k–6k | 13 | 2.73 → 1.19 | 11.1 → 14.9 |

What this means for the bound: on B300 the 4096 lower bound is still right (2k loses 8%, 3k breaks even). The rows that lose above it are made of prefill batches larger than the target's prefill CUDA-graph range (8,192 tokens by default, against 16,384-token chunks): in the default server every prefill batch above 8,192 tokens logged `cuda graph: False`.
