# [Feat] usage: align prompt and cache accounting across APIs

[Upstream PR](https://github.com/sgl-project/sglang/pull/46091) · state: open · merged: False

## Original PR description

## Purpose

Give Python API clients consistent prompt/cache usage across Chat, Completions, Responses and Messages. A cache miss does not prove a reusable write: this PR measures newly adopted prompt ranges and preserves the difference between **measured zero** and **unknown** through JSON and terminal streaming responses.

For K3, Responses and Messages `count_tokens` also use Chat's public prompt boundary, excluding the assistant-generation stub. This makes the APIs describe the same admitted input without changing physical cache metrics or traces.

## Design

Measure writes where the unified cache adopts reusable prompt ranges, carry cumulative measurements through the existing typed IPC, and project them at the API boundary with `--enable-cache-report`.

| Situation | Reported meaning |
| --- | --- |
| Newly reusable prompt ranges | Measured write count; earlier prefill chunks remain included. |
| Warm duplicate or normal non-disaggregated disabled cache | Measured zero. |
| Unsupported/unmeasured path, including PD decode | Unknown, even if decode's local cache is disabled. |
| Generated tokens, duplicate insertion or recomputation of an originally read prefix | Excluded from new writes. |
| Hybrid cache | Writes require a reusable state boundary. |

Responses records whether its numeric write field was measured. Messages publishes its measured input/cache partition in the terminal snapshot. Parallel choices keep writes unknown. API metadata bounds cached reads to the public input window while retaining main's `RequestOutputStats` carrier and per-output write updates.

This counts reusable cache admission. It does not promise retention, durable storage, billing policy or future residency. The separate Rust frontend does not report these writes. Includes #46549 and #46607; those smaller PRs remain open while this combined feature is reviewed. PD measurement transport is a follow-up in #48300, not an expansion of this PR.
