# [Feat] multimodal: Allow CPU image preprocessing to preserve serving GPU memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/37537) · state: open · merged: False

## Original PR description

## Motivation

Fast image/video preprocessing runs in the tokenizer process and can compete with model/KV-cache memory on the serving GPU. CPU feature transport alone does not prevent GPU preprocessing.

Add an explicit CPU placement option while keeping the torchvision implementation. This is a memory-headroom control, not a peak-VRAM budget or a performance recommendation; `auto` preserves existing platform defaults.

## Modifications

- Add `--mm-preprocessing-device {auto,cpu,cuda}`, independent of `--image-processor-backend` and `--mm-feature-transport`. CPU placement disables shared GPU JPEG decode and updates automatic worker sizing.
- Use one explicit device-then-platform decision for shared HF calls, Qwen image artifacts, Bailing and ERNIE. Gemma4 inherits the shared call. Remove unused class defaults and implicit method-override detection.
- Replace ERNIE's hardcoded `cuda` with the selected device and worker GPU ordinal. Keep existing model-specific video placement.
- Include the device choice in the preprocess-cache fingerprint, including processors that already disable GPU decode.
- Document the three independent controls and a CPU-torchvision example in the VLM guide and server arguments.

Custom paths such as Kimi-K3 preprocessing do not yet follow this option. Vision encoding stays on GPU, and CUDA IPC/VMM can still allocate GPU memory. CPU/GPU decode and resize may differ numerically. This does **not** promise a CUDA-context-free tokenizer: current main's platform detection can initialize CUDA during import, before preprocessing.

Original author commits are preserved; this follow-up simplifies and completes the existing implementation.

## Validation

Isolated B200 development validation at `f1dd829a318` (same production/test code as published `0e3b684212e`; the last commit only clarifies documentation), Python 3.12, torch 2.14.1+cu130, torchvision 0.29.1+cu130, Transformers 5.19.0:

- Device-selection suite: 34 tests and 22 subtests passed in each of GPU-visible and GPU-hidden environments.
- Related config, decode, Bailing, clone-isolation, async-call-site and preprocess-cache suites: 91 CPU tests passed, with one CUDA-only test skipped. The complete preprocess-cache suite then passed on GPU: 27 tests and 5 subtests.
- The previous PR head `d8dbce96faa` fails the added regressions: ERNIE receives `cuda` instead of `cpu` / `cuda:3`, and changing the preprocessing device leaves the artifact fingerprint unchanged.
- Real Qwen2.5-VL-3B HF processor/config, seeded JPEGs at 512/1024/1536 pixels, CPU and CUDA paths: shared preprocessing and repeated per-image artifact preparation match HF outputs exactly on the **same** device. CPU preprocessing showed zero PyTorch CUDA allocation peak; this excludes the pre-existing driver context. No CPU-vs-GPU bitwise-equivalence claim.

No model weights, full serving/EPD validation, or throughput benchmark were used for this follow-up. CPU preprocessing trades CPU work/latency for GPU headroom. CI is enabled with `run-ci`; final merge readiness still depends on CI and review.

- long10024070 · comment · 2026-10-13T19:29:32Z · [source](https://github.com/sgl-project/sglang/pull/37537#issuecomment-6153490842)

Thank you @ormandj for adding this CPU preprocessing option. We run [OneNexus/GLM-5.3-Flash-MXFP4](https://huggingface.co/OneNexus/GLM-5.3-Flash-MXFP4) on AMD MI35x and have a concrete operational use case for CPU image preprocessing.

We observed image-bearing requests returning HTTP 500 with `torch.OutOfMemoryError` in the tokenizer/Hugging Face image-preprocessing path, including `Glm5NextImageProcessor` tensor stacking and float32 conversion/normalization. The GPU had no free headroom, while the pod remained running and continued serving other requests. After moving image preprocessing to CPU, a user replayed the previously failing vision session and reported that the 500 OOM no longer reproduced.

We also validated image requests with a baseline configuration and a configuration using this PR's CPU preprocessing option on September 27, 2026:

- Model: [OneNexus/GLM-5.3-Flash-MXFP4](https://huggingface.co/OneNexus/GLM-5.3-Flash-MXFP4).
- Validated PR revision: `3fac6bfca7c3c1ee3197130297e0a4d40f983a5b`.
- Four MI355X GPUs, serving one TP4/EP4 worker behind SGLang Model Gateway.
- Both configurations used `--mem-fraction-static 0.85`; the CPU preprocessing configuration added `--mm-preprocessing-device cpu`.

In the TP4/EP4 image probes below, we observed no latency regression with CPU preprocessing: both the first image request and its cached follow-up completed faster than the baseline in the recorded runs. All requests returned HTTP 200. Durations are seconds:

| TP4/EP4 probe session | Baseline first image | CPU preprocessing first image | Baseline cached follow-up | CPU preprocessing cached follow-up |
|---|---:|---:|---:|---:|
| A | 1.894 | 1.634 | 0.393 | 0.173 |
| B | 3.047 | 1.606 | 0.516 | 0.204 |

These were functional probes on fresh servers, not repeated paired latency measurements. We are not claiming a general latency improvement.

The figures were recovered from recorded structured outputs of the historical validation; the original artifacts are currently unavailable.

The operational benefit for us is having an explicit way to keep visual preprocessing off the serving GPU when headroom is tight. We support merging this change and appreciate the work on it.
