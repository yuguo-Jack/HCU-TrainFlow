# [Fix] disaggregation: Fix Gloo collective mismatch in disagg prefill bootstrap when TP/CP > 1

[Upstream PR](https://github.com/sgl-project/sglang/pull/37909) · state: open · merged: False

## Original PR description

## Motivation

**Base version: SGLang v0.5.18**.

Under PD disaggregation with attn TP or CP world size > 1, bootstrap queues can diverge across ranks. `pop_bootstrapped` previously polled the full local queue and then ran `poll_and_all_reduce_attn_cp_tp_group`, which `all_reduce` poll tensors of unequal length and crashes with a Gloo collective mismatch:

```text
terminate called after throwing an instance of 'gloo::EnforceNotMet'
  what():  [enforce fail at .../gloo/transport/tcp/pair.cc:456] op.preamble.length <= op.nbytes. 8 vs 1. Received data size doesn't match expected size. Is there a distributed collective mismatch in your code?
Fatal Python error: Aborted
```

Relevant stack (paths redacted):

```text

File ".../sglang/srt/disaggregation/utils.py", line 199, in poll_and_all_reduce_attn_cp_tp_group
File ".../sglang/srt/disaggregation/prefill.py", in pop_bootstrapped
File ".../sglang/srt/disaggregation/prefill.py", in event_loop_normal_disagg_prefill
File ".../sglang/srt/managers/scheduler.py", in dispatch_event_loop
```

Follow-on symptom after the peer aborts:

```text
RuntimeError: [.../gloo/transport/tcp/pair.cc:...] Connection closed by peer
```

## Modifications

- In the non-PP path of `pop_bootstrapped`, when attn TP/CP world size > 1, align request rids across the group before polling:
  - `all_reduce(MAX)` a `has_req` flag so idle ranks still participate
  - `all_gather_object` local rids and take the intersection
  - poll only the common requests, then map polls back onto the local queue by rid (`poll is None` for local-only rids)
- Keep the original early-return / direct-poll path when rid alignment is not needed (TP=1 and CP=1)
- Add unit tests in `test/registered/unit/disaggregation/test_prefill_bootstrap_rid_align.py` covering empty-queue exits, rid intersection, sorted-order poll mapping, Failed handling, and sequential TP+CP intersection

- SGLang v0.5.18
- CUDA 13.0

- Joeegin · comment · 2026-10-22T04:54:20Z · [source](https://github.com/sgl-project/sglang/pull/37909#issuecomment-6333041662)

**Second independent repro (GLM-5.2, DSA/NSA model) + a different failure mode under a non-Gloo backend — this confirms the RCA and widens the blast radius.**

We hit the exact same root cause on a different model and a different collective backend, which I think strengthens the case for merging this.

**Setup**
- `sglang 0.5.23.dev286`, PD-disaggregated, prefill side.
- GLM-5.2 (DSA/NSA attention) with `--enable-nsa-prefill-context-parallel`, `tp_size=16`, `dp_size=2` across 2 nodes (8 GPUs each) → `attn_cp_size = tp_size / dp_size = 8`.
- So this is the same `attn_cp world size > 1` condition as your `--enable-dsa-prefill-context-parallel` repro, just via the NSA switch on a different model family (and at a larger cp size).

**Trigger**
Not load volume — *burst concurrency*. The system ran fine for a long time under serial / low-concurrency eval. The deadlock only appeared under a burst of ~15–30 concurrent long-context requests, i.e. the first time the per-rank `PrefillBootstrapQueue` lengths actually diverged within a single scheduler iteration (some cp ranks drained their bootstrap queue while others had not). That is precisely the unequal-length-poll-tensor condition this PR targets.

**Different symptom, same cause**
Because our collective backend is not Gloo, we did **not** get the `gloo::EnforceNotMet ... 8 vs 1` abort. Instead the mismatched collective simply never completed and the watchdog killed it after the timeout:

```
OpType=_ALLGATHER_BASE, SeqNum=156429, NumelIn=7, NumelOut=112, ran for 600004ms
```
(`NumelOut=112 = 16 ranks × 7` — the MLP-sync all_gather one group of ranks raced ahead to.)

Peer ranks then died with the same follow-on you documented:
```
RuntimeError: [.../gloo/transport/tcp/pair.cc:...] Connection closed by peer
```

**py-spy snapshot (16 ranks) — the smoking gun for "queues diverged"**
Within one DP group of 8 cp ranks, the ranks were split across *two different collectives*:
- 5 ranks parked at `dp_attn.py:184` → `all_gather` (already past bootstrap — their local queue was empty, so `pop_bootstrapped` took the `len(self.queue)==0` early return and ran ahead),
- 3 ranks parked at `utils.py` `poll_and_all_reduce_attn_cp_tp_group` → `all_reduce` inside `pop_bootstrapped` (their queue was non-empty, so they entered the cp-group collective and waited for peers that never arrive).

So even without the Gloo length assert, the **local** `len(self.queue)==0` early-return + the per-rank-length poll tensor is enough to split a cp group across two barriers and hang indefinitely. The fix in this PR (making the queue-length / early-return a collective decision instead of a per-rank one) addresses both manifestations.

Happy to share the full 16-rank py-spy dump if useful. +1 on getting this merged — we're currently carrying it as an out-of-tree patch.

Thanks @ShangmingCai - a couple of clarifications from our side:
https://github.com/sgl-project/sglang/pull/37143 does not cover this path. Its timeout scan only looks at `waiting_queue`/`running_batch` and emits `AbortReq`. Prefill requests in `disagg_prefill_bootstrap_queue` are not scanned, so that fix cannot address bootstrap-queue length/rid divergence across attn TP/CP ranks (the failure mode this PR is about).

Bootstrap timeout is also unlikely to be the source of abort/queue divergence. `_check_bootstrap_timeout()` is local, but the poll result still goes through `poll_and_all_reduce_attn_cp_tp_group` -> `all_reduce(MIN)`. `KVPoll.Failed = 0`, so if any participating rank returns failed (including bootstrap timeout), every rank in the group sees failed for that rid. In `pop_bootstrapped`, the  failed branch always removes the request. So under a shared rid set and a completed collective, one rank timing out cannot leave the request in some ranks’ bootstrap queues for the next iteration.

On our production crash dump the CP group was already split across two collectives — the same shape @Joeegin  reported. Auto py-spy after SIGQUIT shows one live scheduler MainThread still inside `pop_bootstrapped` -> `poll_and_all_reduce_attn_cp_tp_group` -> `all_reduce`, while another has already moved on to `get_new_batch_prefill` -> `check_hicache_events` -> `_sync_hicache_ready_counts` -> `all_reduce`. The first failure is `gloo::EnforceNotMet (8 vs 1)` on the bootstrap poll path; peers then die with `Connection closed by peer`. So `HiCache` is only where some ranks were when the bootstrap poll collective aborted — not evidence that `HiCache` caused the first queue divergence. That said, our serving path always had hierarchical cache on; it was production with limited capacity, so we did not A/B with `HiCache` off, and I no longer have spare machines to re-run that isolation.

Caveat: any fix that only hardens `pop_bootstrapped` has to align the queue before `poll_and_all_reduce_attn_cp_tp_group`, so some extra collective cost is inherent. Separately, I currently do not have spare machine capacity to further reproduce or dig the first divergence, so I cannot push the root-cause investigation further on my side for now.

In practice this still helps: both @Joeegin ’s independent repro and our production crashes match the unequal-length poll failure mode, and aligning rids before `poll_and_all_reduce_attn_cp_tp_group` stops that hang/crash.
