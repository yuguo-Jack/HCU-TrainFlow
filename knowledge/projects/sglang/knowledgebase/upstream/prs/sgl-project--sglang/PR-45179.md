# [Perf] diffusion/minimax-h3: Batch the video VAE decoder tiles and fuse the output chain

[Upstream PR](https://github.com/sgl-project/sglang/pull/45179) · state: closed · merged: True

## Original PR description

## Motivation

MiniMax-H3's video VAE decodes a request as overlapping spatial tiles over temporal windows and blends them back together. On `main`, base H3 runs one tile per ViT decoder forward at every quality level (only FastH3 stacked its tiles, through `stack_tiling`), and the output chain after the decoder (tile blend + crop + place, temporal window blend into the destination frames, RGB de-normalization + clamp) is a sequence of FP32 aten ops, each a full pass over the frames. On 4x RTX PRO 5000 the decode stage is 3.26 s of a 30 s five-step 768p t2va request.

This PR:

- decodes up to 64 equal-shaped tiles per decoder forward under `quality="lossless"` (the default) and `"high"` on CUDA. Batching changes the GEMM shapes and therefore the output at rounding level, so it belongs to the lossless tier like the existing fused QK RMSNorm+RoPE;
- replaces the temporal blend write and the de-normalization with JIT kernels that reproduce the eager arithmetic bit-exactly and verify that on first use, so they are not tied to a quality level and run at every level, `exact` included. The tile blend + crop + place stays eager: a kernel for it needs the tiles as one tensor, which neither the one-tile-per-forward decode nor the parallel-tiled decode (whose all-gather hands back rank-interleaved views) provides without a copy, and it is worth under 1 ms per request where it would apply.

## Modifications

Decoder batching (`minimax_h3_video_vae/klvae.py`, `batching.py`, `configs/models/vaes/minimax_h3_video.py`, `configs/pipeline_configs/minimax_h3.py`):

- `MiniMaxH3VideoVAEConfig.decoder_tile_batch` (tiles per decoder forward, default 64, 0 = all of a rank's tiles) and `window_batch` (temporal windows per forward, default 1) replace `stack_tiling`. `_run_tile_tasks` has one path through `batching.forward_many`; width 1 is the released recipe, so `exact` decodes exactly as before. The caps apply only while the VAE's `VaeFastPathGate` is enabled, through the decode stage's existing `use_vae_fast_path(vae, quality_allows(quality, "lossless"))`. No new flag or environment variable.
- `MiniMaxH3VideoVAE` creates the gate; the CUDA installer `maybe_optimize_minimax_h3_vae` registers it, hangs the fused QK RMSNorm+RoPE / cuDNN SDPA attention on it and logs the caps once. Other platforms keep one tile per forward, as on `main`.
- FastH3 sets `decoder_tile_batch = 0`, its previous all-tiles recipe, under `lossless`; its `exact` level now decodes tile by tile like base H3. `--performance-mode memory` resets both caps to 1 at every level. `window_batch` stays at 1: pooling every window into one forward measured 8% slower with a 70.2 GB peak (+10 GB) on the PCIe SM120 box (previous revision of this branch).

Output kernels (`kernels/jit/csrc/diffusion/minimax_h3_vae_output.cuh`, `kernels/ops/diffusion/layout/minimax_h3_vae_output_jit.py`, SM100+):

- `minimax_h3_vae_temporal_blend_write` (temporal ramp blend written straight into the destination frames) and `minimax_h3_vae_denorm_clamp` (RGB de-normalization + clamp, with an in-place mode `out=value` for the frames the decode stage owns, so no second copy of the video is kept). Every step spells the aten arithmetic with explicit round-to-nearest intrinsics (one rounding per op, ramp weights as `k * rcp(n)`), so `torch.equal` holds against the eager chain on both the strided and the 128-bit path.
- Each site sits behind a module-level `BitExactFusionGate`: on first use it compares against the eager result, and a mismatch drops the kernel for the process. The blend site verifies per signature (with and without a previous window, so a plain copy cannot vouch for the blend arithmetic); the de-normalization verifies one probe frame. `is_cuda_sm_at_least` in `kernels/ops/diffusion/common/platform.py` keeps ROCm's gfx-derived capability out of the SM check.

Docs: cookbook quality-level descriptions, FastH3 paragraph and deployment-details bullet; `fused_kernels.mdx`; kernels README; `existing-fast-paths.md`; performance skill.

Tests:

- `multimodal_gen/test/unit/test_minimax_h3_vae_fast_path.py` (CPU, 25 cases): batch partitioning and window iteration, the caps reach the VAE only while the gate is on, the real installer shares one gate between attention and batching, batched decode matches tile-by-tile decode with the expected batch widths, first-use verification and fallback of each output site, in-place de-normalization only on owned frames. `test_server_args.py`: memory mode keeps one tile per forward for H3 and FastH3.
- `test/registered/kernels/ops/diffusion/test_minimax_h3_vae_output.py`: `torch.equal` against the eager chain over blend extents (ramp, strided, zero-count), the in-place mode, alias and input rejections; the temporal blend site bit-exact and verified per signature; batched decode within 1e-3 of tile-by-tile with the expected batch widths on any CUDA GPU; `revert_tensor` bit-exact, in place only on owned frames. The tiny H3 VAE fixture is shared with the CPU unit tests through `sglang.test.kernels.minimax_h3_vae`.

## Accuracy Tests

4x RTX PRO 5000 72 GB (SM120), cookbook TP2 + Ulysses2 recipe, t2va 768p 16:9 5 s, 5 steps, seed 1101. The reference is `main` (62cee1b15c, the rebase base) at the same quality level, so the DiT trajectory is identical and only the VAE differs. At 1344x768 the decoder splits each frame into a 4x7 = 28-tile grid over the 4 decode ranks, so under `lossless` each rank decodes its 7 tiles in one forward per temporal window. Frame PSNR / SSIM by ffmpeg on the decoded frames; audio compared as a hash of the decoded stream.

| Request | vs `main` at the same level | Audio |
|---|---|---|
| `exact` | bit-identical frames, 3 runs (both output kernels in the loop) | identical |
| `lossless`, 7 tiles per forward per rank | worst frame 52.1 dB, mean 52.6 dB, SSIM min 0.995 | identical |

The lossless difference is the batching alone: on the previous revision of this branch (whose lossless decode is bit-identical to this head on t2va), one tile per forward with the output kernels kept gave frames and audio bit-identical to `main`'s lossless. No run on this head logged a first-use fallback. The branch was first measured against 57db5089c2 and re-measured after the rebase: `main`'s `lossless` decode and this PR's `lossless` output are bit-identical across the two bases, while `main`'s `exact` decode changed in #44690 (it dropped the Triton QK RMSNorm+RoPE the ViT attention ran at every level), and this PR's `exact` follows it bit for bit on both. On fl2va (first-frame conditioning) the previous revision measured a worst frame of 44.2 dB, mean 45.2 dB, SSIM min 0.986 and identical audio against `main` lossless; that clip differs more for the VAE on its own.

Tests on SM120: `test_minimax_h3_vae_output.py` + `test_model_fast_paths.py -k "minimax_h3 or h3_vae"`, 21 passed. The MiniMax-H3 and VAE unit files pass on CPU (379 cases; the four `test_fasth3_selects_vsa_h3_for_the_transformer` subtests fail on `main` as well on this host).

Tests on B200 (SM100, torch 2.14.1+cu130) after the rebase onto `main` 2da6c0c237: `test_minimax_h3_vae_output.py` + `test_model_fast_paths.py`, 112 passed, 21 skipped, 1 failed. The failure, `test_model_fast_paths.py::test_ernie_qknorm_rope_is_bit_exact`, fails the same way on `main` 2da6c0c237 and on the PR base 62cee1b15c in that environment (the ERNIE gate logs a mismatch against the platform's reference dispatch and falls back); `main` never runs this file on B200, and this PR no longer registers it there. CPU: `test_minimax_h3_vae_fast_path.py`, `test_minimax_h3_admission.py`, `test_minimax_h3_vdn.py` and `test_server_args.py`, 298 passed; the one failure is a `main` MOVA case that needs Hub access.

CI exposure: the H100 cases that keep goldens pin `quality="exact"` in memory mode, where the decode is unchanged; the 4-GPU H100 cases run at the default level without a golden. `minimax_h3_t2va_consumer_budget_1gpu_5090` (SM120, memory mode, pinned `exact`) is the one golden case that exercises the temporal blend and de-normalization kernels; their first-use check adds a one-window reference and a one-frame probe inside its 12 GiB cap. The kernel tests live in `test_minimax_h3_vae_output.py`, registered on the `4-gpu-b200` kernel-unit lane (the batching test also runs on the `1-gpu-large` lane, and the file is in the AMD nightly kernel suite for the ROCm fallback); `test_model_fast_paths.py` keeps its H100 registration only. This PR's CI is the kernels' first run on SM100; a first-use mismatch there would drop a kernel for the process rather than change output.

## Speed Tests and Profiling

4x RTX PRO 5000 72 GB (SM120, PCIe), torch 2.14.1+cu130, CUDA 13.0, sgl-kernel 0.4.9, flashinfer 0.7.1, driver 580.178.04; base `main` 62cee1b15c. `sglang generate` with `--tp-size 2 --ulysses-degree 2 --encoder-parallel auto --performance-mode speed`, t2va 768p 16:9 5 s, 5 steps (the VAE time does not depend on the step count), one timed request per fresh process after two warmup steps, configurations interleaved in blocks, `SGLANG_DIFFUSION_SYNC_STAGE_PROFILING=1`. Decode = `MiniMaxH3DecodingStage` duration from `perf_dump.json`; peak = runtime peak reserved.

| | decode ms, median (min–max) | vs `main` same level | peak reserved |
|---|---:|---:|---:|
| `main`, `exact` | 3404 (3402–3406), n=3 | | 58120 MB |
| this PR, `exact` | 3400 (3391–3409), n=3 | within noise | 58120 MB |
| `main`, `lossless` | 3258 (3252–3264), n=2 | | 58120 MB |
| this PR, `lossless` | 3158 (3147–3162), n=3 | −3.1% | 58120 MB |

On the previous revision of this branch (on 57db5089c2, where `main`'s `lossless` decode measured 3262 (3258–3264), n=7), the output kernels alone (one tile per forward; that revision still fused the tile assembly as well) saved 11 ms (0.3%; 3251 vs 3262 ms, n=2); the rest is the tile batching. The fl2va request showed a similar −3.4% there. End to end, the five-step request stays at 30.2 s; the decode is a tenth of it.

Kernel microbenchmarks (one SM120 GPU, 448x448 frames; measured with a local script that is not part of this PR):

| op | frames | eager µs | JIT µs |
|---|---:|---:|---:|
| temporal_blend_write | 17 | 129.8 | 81.2 |
| temporal_blend_write | 33 | 293.4 | 150.9 |
| denorm_clamp | 17 | 80.5 | 37.1 |
| denorm_clamp | 33 | 299.1 | 140.8 |

Not measured on H100/H200 (where only the batching applies) or on SM100/SM103. No benchmark script ships with this PR.
