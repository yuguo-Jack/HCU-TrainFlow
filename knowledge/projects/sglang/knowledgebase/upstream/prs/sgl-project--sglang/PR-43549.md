# [Fix] Preserve inline system messages for the dsv41 native encoder

[Upstream PR](https://github.com/sgl-project/sglang/pull/43549) · state: open · merged: False

## Original PR description

### Motivation

For DeepSeek-V4.1-Flash the native `dsv41` encoder renders a mid-conversation system
message in place, but `AnthropicServing` hoists it into the leading `system` block
anyway. Claude Code appends one inline system message per turn, so the start of the
prompt is rewritten every turn and the radix prefix cache stops matching near the
top — each turn re-reads the whole conversation.

#40077 introduced `spec_supports_inline_system()` for exactly this, and its
description says of the identical fix for `dsv4.1` (#39518, closed unmerged when the
`dsv4.1` base branch was deleted):

> Adding `dsv41` to the allowlist is a one-line follow-up once its encoder is checked.

This checks the encoder and adds it.

### Why the Jinja probe misses dsv41

`_resolve_inline_system_support()` (`serving_chat.py`) asks the allowlist first and
only then falls back to probing the tokenizer's Jinja template. dsv41 never reaches
that fallback with a usable answer:

* `DeepSeek-V4.1-Flash`'s `tokenizer_config.json` carries **no** `chat_template`, so
  the probe is handed `None`.
* `detect_inline_system_support(None)` returns `False` — a missing template is read
  as "cannot render inline", not as "unknown".

The native encoder does render it. In `encoding_dsv41.py`:

* `find_last_user_index()` — a `system` message with `index > 0` counts as a
  generation point, so a trailing inline system message still opens the assistant
  turn:

  ```python
  if role in ["user", "developer"] or (role == "system" and idx > 0):
  ```

* `render_message()` — emits the native system token for those messages:

  ```python
  if role == "system":
      if index > 0:
          prompt += SYSTEM_SP_TOKEN
  ```

* the generation branch repeats the same `system and index > 0` test.

So the encoder is generation-ready for inline system messages; the only thing
keeping them out of place is the allowlist.

### Change

```python
def spec_supports_inline_system(spec: Optional[str]) -> bool:
    """Native encoders verified to render mid-conversation system messages in place."""
    # K3's tokenizer renders in Python, so there is no Jinja source to probe.
    # dsv41 is the same shape: encoding_dsv41.render_message emits SYSTEM_SP_TOKEN
    # plus a generation header for any system message past index 0. The Jinja probe
    # cannot see either one, and DeepSeek-V4.1-Flash ships no chat_template at all.
    return spec in ("kimi_k3", "dsv41")
```

No other source change is needed: `AnthropicServing.__init__` already reads
`openai_serving_chat.supports_inline_system`, so the allowlist answer flows through to
`_merge_inline_system` unchanged.

### Blast radius

`supports_inline_system` is also read by the Responses endpoint
(`serving_responses.py`), where `True` means "return the message list uncoalesced
instead of folding every `instructions`/`developer` entry into one leading `system`
message". That is the same preserve-the-prefix semantic #40077 added for Kimi K3, and
dsv41 becomes consistent with it here.

`inkling` is deliberately **not** added: it renders prompt ids natively, but its
mid-conversation system handling has not been verified.

### Evidence

Measured on 8×H20 with DeepSeek-V4.1-Flash served through the Anthropic endpoint,
with Claude Code as the client:

| metric | before | after |
| --- | --- | --- |
| `cache_read_input_tokens` | 16,384 | 42,240 |
| prefix-cache hit rate | ~6% | ~84% |
| newly computed tokens per e2e run | 711,901 | 64,141 |
| offline render diff, turn 2 vs turn 1 | 86,265 chars (100% of prompt) | 14,273 chars (16%) |

The offline render diff is the clearest signal: 84% of the prompt is byte-identical
across turns, which is exactly the prefix the cache can reuse.

The original `dsv4.1` attempt (#39518, 8×H200) reports the same shape — prompt tokens
60,044 → 60,045 with cached 0 → 59,904.

### Test

Adds `test_dsv41_uses_the_native_inline_system_encoder` to
`test/registered/unit/entrypoints/anthropic/test_serving.py`, covering the allowlist
answers and that `AnthropicServing._merge_inline_system` follows the resolved value.
The suite is registered with `register_cpu_ci`, so it runs on the CPU CI.
