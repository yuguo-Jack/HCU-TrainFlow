# [Fix] diffusion/nunchaku: Load FLUX.1 SVDQuant checkpoints again

[Upstream PR](https://github.com/sgl-project/sglang/pull/45930) · state: open · merged: False

## Original PR description

## Motivation

Loading a Nunchaku FLUX.1 checkpoint (for example `svdq-int4_r32-flux.1-schnell.safetensors` from `nunchaku-ai/nunchaku-flux.1-schnell`) with `--transformer-weights-path` fails on current `main`. Two separate regressions are involved; the second shows up once the first is fixed.

1. **Quantized-replacement detection (#36916).** `_resolve_weight_override_quantization` sees the int8 SVDQuant weights and the checkpoint's `quantization_config` metadata (`{"method": "svdquant", ...}`, no `quant_method`). It returns "declares quantization, no config", and `_resolve_quant_config` raises:
   ```
   ValueError: Replacement checkpoint contains quantized tensors but no supported native quantization declaration
   ```
   This happens before the Nunchaku config is consulted. The existing unit test `test_resolve_transformer_quant_load_spec_keeps_nunchaku_hook` did not catch it because its fake checkpoint only has a float tensor and no metadata.

2. **FLUX.1 single-block mapping (#20137).** The FLUX.2 NVFP4 change rewrote the shared nunchaku single-block rules in `FluxArchConfig.param_names_mapping` from `qkv_proj -> attn.to_qkv` / `out_proj -> attn.to_out.0` to FLUX.2's `attn.to_qkv_mlp_proj` / `attn.to_out`. `FluxTransformer2DModel` (FLUX.1) uses the same mapping, so its single-block `attn.to_qkv` and `attn.to_out.0` are never loaded:
   ```
   ValueError: New parameter 'single_transformer_blocks.29.attn.to_qkv.proj_up' is not supported. ...
   ```

## Modifications

- `resolve_transformer_quant_load_spec`: skip the checkpoint quantization detection when Nunchaku is enabled and no explicit `--quantization` is set, since `NunchakuConfig` loads those tensors itself. With an explicit `--quantization`, the existing conflict error is still raised.
- `FluxTransformer2DModel.param_names_mapping`: restore the FLUX.1 targets for the nunchaku single-block `qkv_proj` / `out_proj` keys on the FLUX.1 model only. The shared `FluxArchConfig` mapping, which FLUX.2 uses, is unchanged.
- Tests:
  - `test_transformer_quant.py`: a fake SVDQuant checkpoint with int8 `qweight` and `quantization_config` metadata now resolves to `quant_config=None` with the Nunchaku config kept.
  - New `test_flux_nunchaku_mapping.py`: FLUX.1 single-block names map to `attn.to_qkv` / `attn.to_out.0`.
  - Both tests fail on `main` and pass with this change.

## Accuracy Tests

I don't have NVIDIA hardware. I validated end to end on an AMD Radeon PRO W7900 (gfx1100, ROCm 7.2, torch 2.10) with a ROCm build of `nunchaku` that exposes the same Python API (`nunchaku.ops.gemm.svdq_gemm_w4a4_cuda`, `nunchaku.models.linear.SVDQW4A4Linear`, ...) using Triton kernels. That run also needed two ROCm-only local changes that are **not** part of this PR: allowing ROCm in the Nunchaku platform check, and a weight-layout conversion for the Triton kernels. Both regressions above are platform-independent.

`sglang generate`, FLUX.1-schnell, 512x512, 4 steps, seed 42, `--attention-backend torch_sdpa`:

| | result |
|---|---|
| `main` + Nunchaku int4 | fails with the `ValueError` from (1) |
| this PR + Nunchaku int4 | image generated; PSNR 20.6 dB vs the BF16 output with the same seed, same composition |
| this PR, BF16 (no Nunchaku) | unchanged |

```

  --transformer-weights-path /path/to/svdq-int4_r32-flux.1-schnell.safetensors \

```
(checkpoint from `nunchaku-ai/nunchaku-flux.1-schnell`)

Unit tests: `test_transformer_quant.py` and `test_flux_nunchaku_mapping.py` pass (79 passed).

## Speed Tests and Profiling

This is a loading fix with no performance change. For reference, on the W7900 the warm Nunchaku int4 request took 1.33 s vs 1.91 s for BF16 (0.23 vs 0.30 s/step).
