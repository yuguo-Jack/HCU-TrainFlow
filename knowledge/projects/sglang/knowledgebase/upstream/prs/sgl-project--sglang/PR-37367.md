# [Perf] [AMD] moe: Resolve MoRI dispatch from the AITER activation contract

[Upstream PR](https://github.com/sgl-project/sglang/pull/37367) · state: closed · merged: True

## Original PR description

MoRI's auto dispatch picks the wire format from the expert weight dtype alone,
which does not say what the receiving kernel consumes. MXFP4 weights run a16w4,
a8w4 or a4w4 depending on the activation, gate mode, arch and token count; and
fp8 activations have two formats that share a payload but not a scale layout.

Ask AITER instead, through `resolve_activation_dtype()` (ROCm/aiter#5221), and
pass the quant type alongside the weight dtype so those two stay apart.
AITER owns the kernel dtype decision; an AITER without that API dispatches bf16
and warns.

| quant type | AITER consumes | dispatch | scales |
| --- | --- | --- | --- |
| per_1x128 | fp8 | fp8 | fp32 per 128 |
| per_1x32 | fp8 | **mxfp8** | e8m0 per 32 |
| per_1x32 | fp4x2 | fp4 | e8m0 per 32 |
| anything else, or an answer that depends on M | — | bf16 | — |

`per_Token` lands in the last row on purpose: MoRI has no per-token fp8 format.

On DeepSeek-V4-Pro the MoE is a8w4. Selecting mxfp8 dispatch matches the
activation format consumed by AITER and avoids an unnecessary
`upscale_mxfp4` plus re-quantization on the receive side.

The selection applies to the shared MoRI EPv1/EPv2 dispatcher and follows the
layer's activation and gate layout. Execution-kernel
`DISPATCHER_QUANT_CONFIG` overrides, explicit dispatch overrides, and the
existing combine selection are preserved.

## Why the answer is so often bf16

A dispatch format is fixed when the all-to-all buffers are sized — before any
token exists — while AITER's answer may depend on M. So M is not passed, and
AITER returns None wherever it would have been needed.

The two directions are not symmetric. Sending bf16 when AITER wanted fp8 costs
a quantize on the receive side. Sending a quantized format when the kernel
expects bf16 can cause a kernel-dispatch failure or incorrect output.
Unknown or batch-dependent answers therefore fall back to bf16.

`AITER_BF16_FP8_MOE_BOUND` is a common reason M matters. For the interleaved
SwiGLU path, its default of 256 allows bf16 activations for small batches,
so auto must fall back to bf16. Setting it to 0 pins fp8 for every M and allows
mxfp8 dispatch. That fallback warns and names the variable; fallbacks that
follow from the hardware stay at info.

MXFP8 dispatch also requires AITER to both emit group-32 e8m0 scales and consume
them through the receive-side passthrough. If either capability is missing,
auto falls back to bf16.

## Validation

Validated on **8× MI355X** with
`rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261028` and AITER
`285579b6211b0da30f35b91a890c29c823597cd1`:

- Full local pre-commit checks passed.
- AITER MXFP8 passthrough numerical tests: **3 passed**.
- Eight-rank MoRI EPv2 identity round trips with **automatic bf16, fp8, fp4,
  and mxfp8** selection: all passed
  (64 tokens/rank, hidden size 7168, top-k 6).
- SGLang AITER runner at **1, 8, and 112 tokens**: automatic mxfp8 output was
  **bit-identical** to bf16 input followed by internal quantization.
  The batch-dependent bf16 fallback was also exercised.
- Missing resolution API, missing MXFP8 receive capability, absent numerics,
  and separated-gate fallback checks passed.
- **DeepSeek-V4-Pro-0813, TP8 / DP8 attention / EP8 / MoRI EPv2**:
  all ranks automatically selected mxfp8; startup and decode CUDA graph
  capture succeeded. **17 completion requests**, including eight-way
  concurrency, returned the expected leading arithmetic answer and completed
  32 generated tokens each.

The model requests validate serving functionality; they are not a full
accuracy or performance benchmark.

#### 1. 🟠 Should fix: mxfp8 dispatch silently degrades to bf16 if aiter source grep breaks: this PR added source-text probe
`python/sglang/srt/layers/moe/token_dispatcher/moriep.py:141-151`

The new `can_consume` check in `_aiter_supports_mxfp8_dispatch` searches `inspect.getsource(aiter.fused_moe)` for the literal `hidden_states.dtype == dtypes.fp8 and a1_scale is not None`. If aiter rewords that line, or is installed without `.py` sources (`getsource` then raises `OSError`), the broad `except Exception` returns False and mxfp8 dispatch falls back to bf16, including under `SGLANG_MORI_DISPATCH_DTYPE=mxfp8`. A warning is logged, but the override's message only blames missing `scale_type`, so it misdiagnoses a failed source check. Prefer a feature/attribute or version probe and log which probe failed.

**Who is affected:** MoRI EP users with mxfp8 (a8w4) MoE on an aiter whose fused_moe source is reformatted or not shipped as .py.

#### 3. 🟠 Should fix: Outdated AITER silently drops MoRI dispatch from fp8/fp4 to bf16: this PR replaced the static mapping with resolve_activation_dtype
`python/sglang/srt/layers/moe/moe_runner/aiter.py:909-942`

When AITER lacks `resolve_activation_dtype` (builds older than ROCm/aiter#5221, Sep 2026), `resolve_aiter_dispatch_format` returns BF16 for every layer. MoRI then dispatches bf16 where the base sent fp8 (per_128x128 fp8) or fp4 (MXFP4), about 2x-4x the all-to-all bytes. The pinned `AITER_COMMIT_DEFAULT` (285579b6) and the shipped image already include the API, so default builds are unaffected. The fallback is logged through `warning_once` with an upgrade hint. Keeping the old `weight_dtype` mapping for the M-independent fp8-block and plain-mxfp4 cases would avoid even this.

**Who is affected:** MoRI EP users of fp8 block-quant or MXFP4 MoE models who run an AITER build older than ROCm/aiter#5221 (not the pinned one).

_Checked against the code by an independent pass._

#### 4. 🟠 Should fix: No tests cover the new MoRI dispatch-format decision logic: this PR added it without tests
`python/sglang/srt/layers/moe/moe_runner/aiter.py:439-443`

This PR adds no tests for the new dispatch-format selection: `resolve_aiter_dispatch_format`, its `wire_format` table, `_resolve_dispatch_dtype` with the mxfp8 → bf16 fallback, the `can_consume` probe, `build_dispatcher_quant_config` and `Fp8MoEMethod._aiter_moe_quant_type`. This logic picks the MoRI wire format. It also deliberately changes defaults: per-token fp8, and quant configs that report no `quant_type`, now dispatch bf16 instead of fp8. CPU unit tests with a stubbed `resolve_activation_dtype` are needed for each (quant_type, dtype) pair, the `None` and missing-API cases, the bound and None case, and the mxfp8 probe fallback; they would pin this behaviour.

**Who is affected:** Maintainers changing the MoRI/AITER dispatch selection; regressions in it would not be caught by CI.

_Checked against the code by an independent pass._
