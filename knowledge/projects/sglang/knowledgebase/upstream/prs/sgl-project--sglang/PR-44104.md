# [Perf] glm5: Prewarm mHC prenorm kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/44104) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.3-Flash can compile mHC prenorm kernels during eager prefill, delaying requests. This change uses the existing prewarm helper during model load so those kernels can be compiled before serving.

The benefit depends on startup settings. With breakable prefill graphs and the `prefill_shapes` warmup, main already compiles every mHC prenorm kernel before readiness. Without those settings, the hook trades longer startup for fewer cold first-request stalls.

## Modifications

Call the shared prewarm helper after GLM loads, using the first mHC layer and the same parameters as forward, including fused input normalization. For CPU-offloaded layers, temporarily stage the required tensors on the rank's CUDA device while leaving the original parameters offloaded.

Skip inactive CUDA/mHC configurations, encoder-only instances and disabled chunked prefill. NextN does not use this hook.

## Accuracy Tests

The registered prewarm GPU suite and scoped formatting pass on the updated branch on an RTX 5070 Ti (SM120). The suite exercises the production load wrapper and real TileLang kernels, compares forward results with Torch, and checks that a warmed forward compiles no additional kernel. It covers full and partial CPU offload while preserving the original parameter storage.

A TP4 B200 server run at revision b212f59552 confirmed that the hook ran on all ranks and the TileLang cache was complete at readiness. It predates the latest base update and the later CPU-offload staging change. The updated branch has not had a B200 server run.

Run the model prewarm tests with `python -m pytest` in a compatible CUDA environment or through the registered CI runner.

## Speed Tests and Profiling

The cold-start comparison used a GLM-5.3-Flash FP8 model on TP4 B200, with empty caches and a main nightly at commit 7224fce1b5e4. The PR arm overlaid the hook from b212f59552; it predates the latest base update and did not include the later CPU-offload staging change.

| Startup configuration | Start time, main / hook | TTFT sweep, cold / warm (main) | TTFT sweep, cold / warm (hook) |
| --- | ---: | ---: | ---: |
| Breakable prefill graphs and `prefill_shapes` warmup | 678 s / 682 s | 1.65 s / 1.40 s | 1.73 s / 1.41 s |
| No prefill graphs or warmup | 630 s / 664 s | 32.70 s / 1.44 s | 10.32 s / 1.40 s |

With warmup enabled, main already has the mHC kernels ready, so the hook adds about four seconds to startup without a measurable TTFT change. Without warmup, the hook reduces the cold sweep by about 22 seconds while adding 34 seconds to startup. DeepGEMM and Triton compilation stalls remain. Each arm ran once per configuration, except for the repeat of main in the first configuration.

TP8, other GPUs, warm-disk startup, CPU offload on B200 and a current-head B200 server run remain unvalidated.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Stage CPU-offloaded mHC weights before prewarming**

When `--cpu-offload-gb` is set, `OffloaderV1` moves the decoder layer's direct mHC parameters to CPU during `make_layers`; deriving the residual device here and passing those parameters directly bypasses the layer's functional-call onload wrapper. The load hook therefore invokes the CUDA TileLang/DeepGEMM path with CPU tensors and aborts GLM startup, so prewarming must stage device copies (or skip this path) for offloaded layers.
