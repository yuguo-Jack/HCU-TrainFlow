# [Perf] glm5: Prewarm mHC prenorm kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/44104) · state: closed · merged: False

## Original PR description

## Motivation

GLM-5.3-Flash compiles mHC prenorm kernels on first use. With `--disable-prefill-cuda-graph`, as in the language-server recipe, prewarming moves the first-use stall to startup. The cost is paid once per cold JIT cache.

On its own, this PR did not change ready time on the `test_glm53_flash_b200` low-latency recipe (590 s against 580 s, one run each), because that recipe's prefill graph capture already compiles these kernels.

Combined with #39363, which lets ranks claim buckets, ready time was 400 s, about 32% lower than main. #39363 alone gives GLM nothing, because GLM reaches that helper only through this hook. The PRs conflict on one log line, so whichever lands second needs a small rework.

## Modifications

A load hook calls the shared prewarm helper with forward's parameters and skips inactive CUDA/mHC configurations and encoder-only instances. mhc_post and fused post-pre kernels still compile on first use.

## Accuracy Tests

The hook discards kernel results, so outputs should not change. The table lists sgl-eval 0.1.3 gsm8k scores (200 examples, temperature 1.0, top_p 0.95, max tokens 32768, `--thinking`). One example is 0.5%, so scores do not separate the trees.

On a trial merge with main `ba1ed00dfe`, the test (no compile after the hook) and nearby GLM and mHC tests found no regression.

Not checked: TP8, `--attn-dp-size 4`, #39363 alone, runtime CI, and real weights with `--disable-prefill-cuda-graph`.

## Speed Tests and Profiling

One run per arm on main `582168dd7c`: the recipe (TP4, cookbook TP8) on 4 B200, real page-cached FP8 weights, empty JIT caches. Ready is polled every 10 s. The sweep is `bench_serving` after the eval: concurrency 1, 4096 input, 256 output.

| Tree | Ready (s) | Hook (s) | Prefill capture (s) | First sweep (s) | gsm8k |

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Stage CPU-offloaded mHC weights before prewarming**

When `--cpu-offload-gb` is set, `OffloaderV1` moves the decoder layer's direct mHC parameters to CPU during `make_layers`; deriving the residual device here and passing those parameters directly bypasses the layer's functional-call onload wrapper. The load hook therefore invokes the CUDA TileLang/DeepGEMM path with CPU tensors and aborts GLM startup, so prewarming must stage device copies (or skip this path) for offloaded layers.
