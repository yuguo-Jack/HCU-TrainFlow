# [Feat] scheduler: Add prefill chunk interleaving controls and support HRRN

[Upstream PR](https://github.com/sgl-project/sglang/pull/39717) · state: open · merged: False

## Original PR description

## Motivation

With chunked prefill, a long prompt occupies the whole chunk budget for many passes, and short requests queued behind it wait for every chunk (head-of-line blocking). @Oasis-Git's #40024 added `shortest-prefill-first`, which reserves part of the chunk for shorter waiters that can finish in the same pass. This PR moves that mechanism into a shared implementation, makes it controllable, and lets HRRN use it.

## Modifications

- `--[no-]prefill-interleaving`: unset keeps #40024's default (enabled for `shortest-prefill-first` only); `--prefill-interleaving` enables it for `hrrn`.
- `--prefill-interleaving-min-continuation-tokens`: the minimum kept for the continuing request. Defaults to one KV page for `shortest-prefill-first`, or half the chunk budget rounded up to a page for `hrrn` (8K of 16K). The 8K/16K HRRN default is a conservative choice for continuation progress, not a measured optimum.
- Both policies scan the first 128 waiters in queue order, skip those that don't fit, and move the selected ones ahead of the skipped ones so admission reaches them; `shortest-prefill-first` also takes only waiters shorter than the continuation. The unscanned tail stays in place.
- `PrefillAdder` refuses a second unfinished chunked request under every policy, not only `shortest-prefill-first`; it tracks one `new_chunked_req`.
- The reservation covers only waiters the pass can admit: none when the running batch is full, and at most the free request slots (PD prefill included) and `--prefill-max-requests`, minus the chunked request's slot.
- Interleaving follows the policy after adjustment, so HRRN falling back to FCFS (no tree cache) does not reorder the FCFS queue.
- Only one unfinished chunked prefill is supported, so waiters must finish their uncached prefill in the same pass. HRRN aging does not bound tail TTFT when non-fitting waiters are bypassed.

## Tests

- `test_prefill_adder.py::test_interleaving_admits_complete_waiters`: for both policies, the reservation caps the continuation and admission takes the selected waiters, HRRN past a large head it skips.
- The #40024 `shortest-prefill-first` tests carry over with the renamed `reserve_interleaved_prefills`.
- `server_arguments.mdx` rows for the two flags, checked by `test_server_args_docs_coverage.py`.

## Speed Tests and Profiling

These tested an earlier implementation of the same mechanism with smaller budgets than this PR's 8K/16K HRRN default. No 8K/16K on/off comparison has been run yet.

### Controlled GPU A/B

Kimi K3 DCP8 1P1D, a 65,536-token cold prefill followed by four 1,024-token requests, 4K continuation / 6K budget, 12 work-matched pairs:

- Mean short-request TTFT: **2.801 s → 1.502 s (−46%)**.
- Mean long-request completion: 3.041 s → 3.140 s. The interleaving arm was already 57 ms slower in long-only controls, so the whole 99 ms can't be attributed to scheduling.
- All 210 requests across primary and control phases succeeded. Batch logs confirmed interleaving with identical input-token work.

### Mirrored production-traffic canary

Kimi K3 DCP8 1P1D, HRRN prefill, FCFS decode, a 4K continuation within the 16K chunk budget (waiters up to 12K). Two gangs on mirrored production traffic on September 17, one with interleaving and one without. Admission-inclusive TTFT, from histogram rates over each window:

| Window (UTC) | Requests (off / on) | p50 off → on | p90 off → on |
| --- | --- | --- | --- |
| 09:30–10:00 | 972 / 5,496 | 263.6 s → **2.7 s** | 372.7 s → **123.6 s** |
| 18:30–19:00 | 851 / 3,137 | 10.1 s → **1.6 s** | 71.6 s → **16.7 s** |
| 18:50–19:00 | 739 / 860 | 14.29 s → **2.29 s** | 76.1 s → **34.1 s** |

Both canary gangs were prefill-saturated in these windows, so TTFT was dominated by queueing. These show the effect under saturation, not at typical load. The interleaving arm took 1.2–5.7× more traffic, which works against it. The off arm had started recently, with a colder cache, which works against the off arm. Neither is a matched-request experiment or a benchmark of this exact patch. The improvement is consistent with less head-of-line waiting: short requests finish between a long request's chunks while the continuation keeps its minimum. It doesn't mean the longest prompts got faster.
