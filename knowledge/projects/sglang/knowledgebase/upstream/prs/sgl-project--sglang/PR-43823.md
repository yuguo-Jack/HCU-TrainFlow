# [diffusion] VSA-H3: support sm80 (A100) with a raw-pointer Triton load path

[Upstream PR](https://github.com/sgl-project/sglang/pull/43823) · state: open · merged: False

## Original PR description

<h3 id="motivation" data-pm-slice="1 3 []">Motivation</h3><p>The vendored VSA-H3 Triton tile-64 block-sparse attention kernel is gated to<span data-type="hardbreak" data-is-inline="true"> </span>Hopper and Blackwell (<code>supported_capabilities = {(9, 0), (10, 0), (10, 3)}</code>).<span data-type="hardbreak" data-is-inline="true"> </span>The kernel runs correctly on sm80 (A100) as well, but Triton only lowers<span data-type="hardbreak" data-is-inline="true"> </span><code>TensorDescriptor</code> (TMA) loads on Hopper and newer. On sm80 the descriptor loads<span data-type="hardbreak" data-is-inline="true"> </span>are silently degraded to synchronous tile loads with no <code>cp.async</code> prefetch, so<span data-type="hardbreak" data-is-inline="true"> </span>every K/V tile load exposes its full latency and the kernel is several times<span data-type="hardbreak" data-is-inline="true"> </span>slower than the hardware allows.</p><h3 id="change">Change</h3><p>Add a second implementation of the same attention that loads Q/K/V/O through raw<span data-type="hardbreak" data-is-inline="true"> </span>pointers, and select between the two from the device compute capability. On sm80<span data-type="hardbreak" data-is-inline="true"> </span>the pipeliner can then issue <code>cp.async</code> for K/V; on sm90+ nothing changes.</p><ul data-spread="false"><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>runtime/layers/attention/backends/vsa_h3_kernels.py</code></p><ul data-spread="false"><li data-label="•" data-list-type="bullet" data-spread="false"><p>new <code>_attn_fwd_sparse_ptr</code>: identical arithmetic to <code>_attn_fwd_sparse</code>, raw<span data-type="hardbreak" data-is-inline="true"> </span>pointer loads instead of tensor descriptors.</p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p>new <code>_use_pointer_loads(capability)</code> (<code>capability[0] &lt; 9</code>).</p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p>new <code>_ATTN_NUM_STAGES_PTR = 2</code> — the pointer path is not TMA-prefetched, so<span data-type="hardbreak" data-is-inline="true"> </span>the deeper descriptor pipeline does not help (measured optimum on the<span data-type="hardbreak" data-is-inline="true"> </span>production DiT shape).</p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>vsa_h3_block_sparse_attn_forward</code> dispatches on the capability and gains a<span data-type="hardbreak" data-is-inline="true"> </span>q/k/v contiguity check.</p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p>the sm100 tcgen05 kernel is now imported <strong>lazily</strong> inside the branch that<span data-type="hardbreak" data-is-inline="true"> </span>calls it. Upstream had pulled <code>vsa_block_sparse_sm100</code> in at module scope,<span data-type="hardbreak" data-is-inline="true"> </span>which makes the Triton path unusable on any stack that does not ship the<span data-type="hardbreak" data-is-inline="true"> </span>Blackwell-only JIT kernel even though the branch is never taken there.</p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p>the TMA kernel and its <code>num_stages=5</code> tuning are untouched.</p></li></ul></li><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>runtime/platforms/cuda.py</code></p><ul data-spread="false"><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>_VideoSparseAttentionH3BackendResolver.supported_capabilities</code> gains<span data-type="hardbreak" data-is-inline="true"> </span><code>(8, 0)</code>; the fail-closed error message is updated.</p></li></ul></li><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>test/unit/test_vsa_h3_attention.py</code></p><ul data-spread="false"><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>test_pointer_load_path_selection</code>, <code>test_vsa_h3_backend_resolver_allows_sm80</code><span data-type="hardbreak" data-is-inline="true"> </span>and <code>test_vsa_h3_module_imports_without_sm100_symbol</code> (CPU-only).</p></li></ul></li></ul><h3 id="evidence">Evidence</h3><p>A100 80GB, <code>capability=(8,0)</code>:</p>

<p>End-to-end (FastH3 4-step, 1344×768 / 5 s, A100): the sparse path runs 59.6 s<span data-type="hardbreak" data-is-inline="true"> </span>vs 85.0 s for the dense <code>fa</code> baseline.</p><p>Re-run after rebasing onto <code>main</code> (<code>62ff466ac0</code>): the module reproduces<span data-type="hardbreak" data-is-inline="true"> </span><code>max|Δ| = 0</code> vs the TMA kernel and 37.60 vs 293.24 ms = <strong>7.80×</strong> on the<span data-type="hardbreak" data-is-inline="true"> </span>production shape, i.e. the rebase did not change sm80 behaviour.</p><p>Full e2e re-run of the PR-form module on A100 GPU 0 (the rebased<span data-type="hardbreak" data-is-inline="true"> </span><code>vsa_h3_kernels.py</code> swapped into the v0.5.20 overlay; the sm100-only symbol is<span data-type="hardbreak" data-is-inline="true"> </span>stubbed for the run only): <code>rc=0</code>, <strong>59.72 s</strong> end-to-end (denoise 42.04 s /<span data-type="hardbreak" data-is-inline="true"> </span>decode 13.33 s) vs <strong>59.59 s</strong> for the pre-PR patch-0003 build — a +0.2%<span data-type="hardbreak" data-is-inline="true"> </span>difference within run-to-run noise — and the generated mp4 is <strong>bit-identical</strong><span data-type="hardbreak" data-is-inline="true"> </span>(MD5 <code>e26c4926…</code> in both). The capability-gated dispatch therefore reproduces<span data-type="hardbreak" data-is-inline="true"> </span>the validated raw-pointer kernel exactly end-to-end, not just in isolation.</p><p>Deployed end-to-end (<code>32aa25fee0</code>, module sha256 <code>3d00b489…</code>, installed into the<span data-type="hardbreak" data-is-inline="true"> </span>overlay by <code>deploy_pr_kernel.sh</code>, <strong>no stub</strong>): <code>rc=0</code>, <strong>59.58 s</strong> (text 3.96 /<span data-type="hardbreak" data-is-inline="true"> </span>denoise <strong>41.90</strong> / decode 13.31), mp4 MD5 <code>e26c4926…</code> — bit-identical to the<span data-type="hardbreak" data-is-inline="true"> </span>patch-0003 reference, i.e. −29.9% vs the dense <code>fa</code> baseline (84.96 s) with the<span data-type="hardbreak" data-is-inline="true"> </span>same output. A per-branch launch counter inside the real e2e confirms the sm80<span data-type="hardbreak" data-is-inline="true"> </span>branch is what runs: <code>ptr=200, tma=0, sm100=0</code> (50 attention layers × 4 steps).</p><h3 id="accuracy-note">Accuracy note</h3><p>VSA-H3 is a 90 %-sparse approximation, so its output is not bit-identical to<span data-type="hardbreak" data-is-inline="true"> </span>dense attention (vs the dense baseline: PSNR 14.6 dB, audio corr 0.60). This gap<span data-type="hardbreak" data-is-inline="true"> </span>is inherent to the sparsity, not to the load path — the pointer and TMA kernels<span data-type="hardbreak" data-is-inline="true"> </span>are bit-exact with each other. The dense <code>fa</code> path remains the default; this PR<span data-type="hardbreak" data-is-inline="true"> </span>only makes the sparse path available and fast on sm80, as an opt-in tradeoff.</p><h3 id="testing">Testing</h3><ul data-spread="false"><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>pytest python/sglang/multimodal_gen/test/unit/test_vsa_h3_attention.py</code></p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p><code>ruff format --check</code>, <code>ruff check</code>, <code>isort --check-only</code></p></li><li data-label="•" data-list-type="bullet" data-spread="false"><p>CI has no A100 runner, so the sm80 GPU path is covered by the standalone probe<span data-type="hardbreak" data-is-inline="true"> </span>below rather than by CI; the two new unit tests cover the dispatch and the<span data-type="hardbreak" data-is-inline="true"> </span>resolver gate on CPU.</p></li></ul>
