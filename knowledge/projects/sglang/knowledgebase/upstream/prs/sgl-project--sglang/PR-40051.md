# fix(fc): enforce parameters schema for named tool_choice in legacy structural tag

[Upstream PR](https://github.com/sgl-project/sglang/pull/40051) · state: open · merged: False

## Original PR description

## Motivation

With `tool_choice` pinned to a specific function (`{"type":"function","function":{"name":"add"}}`) and a tool that does **not** set `strict: true`, the legacy structural tag path injects an **empty schema** into the grammar. The call format (begin/end tokens) is constrained, but the arguments payload is unconstrained — and under greedy/low-temperature decoding the model deterministically emits the minimal legal JSON, so the API returns `arguments: "{}"` with all required parameters missing.

`get_legacy_structural_tag` line:

```python
schema = function.parameters if is_strict else {}
```

### This is a regression from #21593

Before #21593, named `tool_choice` was served by the `json_schema` path (`get_json_schema_constraint` → `_get_tool_schema`), which **always** enforces the tool's real `parameters` schema regardless of `strict`. #21593 rerouted named/required choices to the legacy structural tag to preserve native call formats, but the new path's `is_strict` schema gating was designed for the `auto + strict` case — so named non-strict calls silently lost parameter enforcement.

The inconsistency is observable today from a single server process: with GLM-family parsers (`supports_structural_tag() == False`) the json_schema fallback still enforces parameters for the same request, while llama3-family parsers return `{}`.

## Evidence

Llama-3.2-1B-Instruct, `--tool-call-parser llama3`, gfx936 single card:

| scenario | result |
|---|---|
| forced tool_choice, `strict` unset, temp=0 (before fix) | `arguments: "{}"` **4/4 runs** |
| same prompt, no grammar at all | model emits correct args voluntarily |
| forced tool_choice after fix | `{"a": 213123, "b": 23131}` **6/6 runs** |

The unconstrained-generation row matters: the model wasn't "choosing" to return empty args per non-strict semantics — the grammar itself degenerated the distribution to the shortest legal string.

## Fix

In `get_legacy_structural_tag`, when the caller passes the named function:

- restrict the grammar structures to that function only (the prompt already advertises only the named tool — this also makes the grammar consistent with it);
- always inject its real `parameters` schema, mirroring `get_json_schema_constraint`.

`tool_choice: "required"` and `"auto"` behavior is unchanged (empty schema for non-strict tools is preserved for `required`; `auto` stays unconstrained).

## Test

New CPU-only unit test `test/registered/unit/function_call/test_named_tool_choice_constraint.py`:

- fails on unfixed code (2 grammar structures for a named choice + empty schema)
- passes after the fix (1 structure, real schema, name in begin token)
- asserts `required` / `auto` legacy behavior is unchanged

Ran 5 tests, OK.

- JustinTong0323 · comment · 2026-09-23T09:43:07Z · [source](https://github.com/sgl-project/sglang/pull/40051#issuecomment-5792571078)

Thanks for the careful analysis and the solid reproduction — the diagnosis is correct, and we verified it end-to-end on our side before forming an opinion.

**Our A/B verification** (sglang @ this PR head, only `function_call_parser.py` swapped pre/post fix, temp=0, named non-strict `add(a, b)` tool):

| Setup | pre-fix | post-fix |
|---|---|---|
| Llama-3.2-1B-Instruct, `llama3` parser | `arguments: "{}"` in 3/4 named calls | 4/4 correct `{"a": ..., "b": ...}` |
| Qwen3.8-27B, `qwen25` parser | all correct | all correct (identical) |

So the failure is real, but it only surfaces on weak models — stronger models fill in valid arguments voluntarily even with an unconstrained payload.

**Why we lean against changing the default, though.** Per OpenAI's documented semantics, schema adherence is exactly what `strict` opts into — [Function calling guide, "Strict mode"](https://platform.openai.com/docs/guides/function-calling):

> Setting `strict` to `true` will ensure function calls reliably adhere to the function schema, **instead of being best effort**. [...] Chat Completions requests remain non-strict by default.

So for a non-strict tool, "best effort" arguments are the documented contract, and `tool_choice` only pins *which* function is called ("Forced Function: Call exactly one specific function") — not how its arguments are validated. Enforcing the parameters schema for non-strict named `tool_choice` would make sglang's default stricter than the API semantics it implements. (vLLM does enforce unconditionally there, but that's their deviation from the documented default, not the reference behavior.) Users who want the guarantee already have two opt-ins: `strict: true` on the tool, or the server-side `SGLANG_TOOL_STRICT_LEVEL` env, which enforces parameter schemas globally.

**One part we think is worth keeping regardless**: restricting the legacy structural tag to the *named* function only. Today a named `tool_choice` puts every tool's structure into the grammar, so the constrained output can legally be a call to a *different* function — that violates the documented "call exactly one specific function" contract independent of the strict question. If you're up for narrowing this PR to just that part (dropping the non-strict schema enforcement), we'd be happy to merge it.

Heads-up: we pushed a maintainer commit (`605fce84d`) to your branch that folds your new tests into `test_json_schema_constraint.py` and trims comments — no behavior change. Feel free to keep or drop it depending on how you want to proceed.

Thanks again for digging into this — the report quality made the review easy.
