## Code Review

This pull request introduces support for ASM-based attention kernels and a SHUFFLE KV cache layout, controlled by the SGLANG_USE_ASM_ATTENTION environment variable. It includes updates to the attention backend for prefill and decode phases, metadata handling for block tables, and memory pool adjustments to support FP8 scale buffers. Feedback highlights several critical issues: the use of incorrect indptr metadata in flash_attn_varlen_func, missing scale parameters in the FP8 Triton kernel call, and a design flaw where shrinking the memory pool capacity to accommodate scales would lead to out-of-bounds accesses. Improvements were also suggested for pre-allocating temporary buffers to reduce overhead and correcting head dimension assumptions in memory calculations.

The call to `launch_reshape_and_cache_flash` in the FP8 non-SWA branch is missing the `k_scale` and `v_scale` arguments. Without these scales, the Triton kernel will perform a direct cast from BF16/FP16 to FP8 without proper scaling, leading to significant accuracy loss. Use `k_descale` and `v_descale` which are already computed in this method.

```python
                launch_reshape_and_cache_flash(
                    k.view(-1, layer.tp_k_head_num, layer.qk_head_dim),
                    v.view(-1, layer.tp_v_head_num, layer.v_head_dim),
                    k_cache.view(
                        -1, self.page_size, layer.tp_k_head_num, layer.qk_head_dim
                    ),
                    v_cache.view(
                        -1, self.page_size, layer.tp_v_head_num, layer.v_head_dim
                    ),
                    forward_batch.out_cache_loc,
                    k_scale=k_descale,
                    v_scale=v_descale,
                )
```

- gemini-code-assist[bot] · comment · 2026-04-28T15:09:12Z · [source](https://github.com/sgl-project/sglang/pull/23946#discussion_r3155176760)

File: `python/sglang/srt/mem_cache/memory_pool.py` · line 908

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Shrinking `num_pages` using `shrink_ratio` to accommodate scale buffers is problematic. The `self.size` parameter defines the total token capacity expected by the scheduler and the allocator. By reducing `num_pages` here, the physical buffers will be smaller than what the rest of the system expects, leading to out-of-bounds memory accesses when the KV cache is highly utilized. The memory for scales should be accounted for in the initial memory profiling/budgeting rather than by reducing the pool capacity silently.

File: `python/sglang/srt/layers/attention/aiter_backend.py` · line None

Allocating `tmp_2d` using `torch.zeros` inside `init_forward_metadata` will cause significant performance overhead due to frequent memory allocations and zeroing on every forward pass. Consider using a pre-allocated buffer (e.g., `self._tmp_2d_buf`) initialized in `__init__` with `max_bs` and `max_context_len` to avoid this overhead.

- gemini-code-assist[bot] · comment · 2026-04-28T15:09:12Z · [source](https://github.com/sgl-project/sglang/pull/23946#discussion_r3155176766)

File: `python/sglang/srt/mem_cache/memory_pool.py` · line 903

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

The calculation of `kv_bytes_per_page` assumes that the key and value head dimensions are identical by using a factor of `2`. This will be incorrect for models where `head_dim != v_head_dim` (e.g., some hybrid or specialized architectures). It should use `self.head_dim + self.v_head_dim` instead.

```python
                        kv_bytes_per_page = (
                            self.head_num
                            * (self.head_dim + self.v_head_dim)
                            * self.page_size
                            * elem_size
                        )
```
