# [Feat] GLM: Match reasoning and tool-call markers by output token id

[Upstream PR](https://github.com/sgl-project/sglang/pull/45587) · state: open · merged: False

## Original PR description

## Motivation

GLM-5.3 writes `<think>`, `</think>`, `<tool_call>`, `</tool_call>`, `<arg_key>`, `</arg_key>`, `<arg_value>` and `</arg_value>` as single control tokens (added tokens with `special=False`). The model also writes the same strings with ordinary BPE tokens when it explains the tool-call format, quotes code, or repeats a log. Both decode to identical text, so the `glm45` reasoning parser and the `glm47` tool-call parser cannot tell them apart:

- A spelled `</think>` ends reasoning early.
- A spelled `<tool_call>` starts a call and executes quoted text.
- A spelled `</arg_value>` cuts an argument.

vLLM resolves this by matching on token ids (vllm-project/vllm#45915), and #45458 does the same for the `</think>` boundary. #42030 found a second case in GLM traces: most `<tool_call>` tokens quoted inside reasoning are real control tokens, not spellings. Telling a quote from a call there takes position as well as id, and [the review of #42030](https://github.com/sgl-project/sglang/pull/42030#issuecomment-6073834347) asked for a cleaner solution to this tool-call leakage. This PR handles both cases by token id.

## Design

**Alignment layer** (`parser/control_token_stream.py`). `ControlTokenStream` decodes a request's output ids incrementally, next to the text its parser receives, and records where each control token starts. `view(text)` returns a same-length copy of the parser text in which every marker that does not start at a control token is defused. Parsers search the view and slice output from the real text, so the parsing logic itself does not change.

Serving keeps special tokens in the text for tool requests while the stream decodes without them. Special tokens found in the parser text are skipped over while matching, so either detokenizer setting stays aligned.

**Detectors** (opt-in; they need a `PreTrainedTokenizerFast` and output ids):

- `Glm45Detector` matches `<think>`, `</think>` and `<tool_call>` only at control tokens. A control `<tool_call>` inside reasoning is decided by position:
  - If `</think>` follows, it was a quote and stays reasoning.
  - If the output ends first, reasoning is split at the call.

  Streaming holds the text after such a `<tool_call>` until one of the two happens, so streaming and one-shot parsing agree.
- `Glm47MoeDetector` matches call and argument boundaries only at control tokens. In id mode, streaming drops calls to undeclared functions (`SGLANG_FORWARD_UNKNOWN_TOOLS` keeps them). `finish()` returns an unnamed call's text as content, as one-shot parsing does.

**Serving** (`serving_chat.py`, `serving_responses.py`) passes output ids to both parsers, streaming and non-streaming, in both `incremental_streaming_output` modes. The reasoning parser hands the ids of the normal text to the tool-call parser.

## Compatibility

- **Without output ids, matching is by text exactly as on main.** This covers detectors other than GLM, tokenizers whose markers are not single tokens, and the `/parse` endpoints.
- If the parser text ever disagrees with the decoded ids, the stream logs a warning once and falls back to text matching for the rest of that output.
- An output truncated before a control `</think>` (for example at `max_tokens`) is all reasoning with empty content, as with #45458. If it contains a control `<tool_call>`, reasoning ends at that call, as main does for any `<tool_call>`.

## Tests

`test_function_call_parser.py::TestGlmControlTokenIds` uses the real `zai-org/GLM-5.3` tokenizer. It mixes control tokens with spelled markers and checks:

- non-streaming results;
- streaming results with chunk sizes 1, 2, 3, 7 and whole, with `stream_reasoning` on and off;
- the #42030 case: a control `<tool_call>` quoted in reasoning before `</think>`. This test fails on main.
- special tokens kept in the parser text;
- undeclared calls in streaming;
- fallback without ids, and on text that disagrees with the ids.

`test_serving_chat.py::test_glm_parsers_get_the_output_ids` checks that serving feeds ids to both parsers, non-streaming and in both streaming modes.

A randomized check over 1500 generated GLM outputs (control tokens mixed with spelled markers, chunk sizes 1, 2, 3, 7 and whole, `stream_reasoning` on and off) found streaming equal to one-shot parsing in every case.

Existing suites (CPU) pass: `unit/function_call`, `unit/parser`, `test_serving_chat`, `test_serving_responses*` and `test_responses_custom_tools` (1437 passed, 1 skipped).

## Model validation

GLM-5.3-Flash FP8 on 8×H200, using the cookbook recipe with `--reasoning-parser glm45 --tool-call-parser glm47`.

**GSM8K (full 1319).** Run with sgl-eval, thinking on, `temperature=1.0 top_p=0.95 max_tokens=32768`:

| Server | Accuracy | stop rate | truncated |
|---|---|---|---|
| main | 97.04% | 100% | 0 |
| this PR | 97.27% | 100% | 0 |

**Probes.** Each probe was run three times, streaming and non-streaming, with output ids returned:

- the model explains the tool-call format without calling;
- a plain tool call;
- an explanation followed by a real call.

All 24 outputs were replayed offline through main and this PR, one-shot and streamed 1 and 3 tokens at a time.

- Plain calls and explain-then-call parse the same on main and this PR.
- In the four explain outputs that parse differently, main ended reasoning at a spelled `</think>`.
- With this PR, streaming equals one-shot parsing for 23 of 24 outputs; main matches in 14 of 24.
- The remaining output is cut at `max_tokens` inside an unclosed control `<tool_call>`. Streaming has already sent the call name, while one-shot parsing keeps the text. main behaves the same way on it.

The live server's responses equal the replay for those 23 outputs.
