# [Fix+Doc] minimax-m3: declare MiniMax2 routing and switch the GB300 MXFP8 recipe MoE runner to flashinfer_trtllm (recipe conditional on the next FlashInfer release)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47572) · state: open · merged: False

## Original PR description

## Motivation

Sibling recipe change to #47187, MoE side, in two commits that only make sense together (combined into one PR for reviewer convenience; previously split as #47572/#47573).

On GB300 (TP4, MXFP8 recipe), FlashInfer's fused MXFP8 MoE (`trtllm_fp8_block_scale_moe`) beats the recipe's DeepGEMM grouped-masked composition ~10.6x GPU-time-weighted across the serve's full measured MoE workload census (all 55 classes, decode and prefill regimes), with MoE ≈ a third of the serve's measured GPU time. End-to-end (900 s agentic-replay serving benchmark, normalized per-user interactivity, tok/s/user), switching the runner nets **+8.1% median / +9.7% p90 at 20 concurrent sessions** over `deep_gemm`, attribution controlled by a FlashInfer-pin-bump-only arm that moved nothing outside the ±3.3% noise band. Dispatch was verified per-rank (API-call census on all 4 TP ranks) with a run contract that fails on any `deep_gemm` fallback.

## Modifications

**Commit 1 — the prerequisite code fix.** MiniMax-M3's experts layer never declares a `routing_method_type`, so when the FlashInfer TRT-LLM MoE runner is selected, `Fp8MoEMethod.get_moe_routing_method_type` falls back to `RoutingMethodType.DeepSeekV3` in-kernel routing. That is wrong for M3 — its routing is sigmoid + bias → top-k → scaled-sum-normalize, i.e. `RoutingMethodType.MiniMax2` — and FlashInfer ≥ 0.7.1 rejects the fallback outright (`n_group should not be zero for DeepSeekV3 routing`), so `--moe-runner-backend flashinfer_trtllm` cannot even start an M3 serve today. One declaration at the experts constructor in `python/sglang/srt/models/minimax_m3.py` plus the import. An explicitly requested method passes through `get_moe_routing_method_type` unchanged, so no runner or quantization code changes; recipes that keep `deep_gemm` are unaffected (that runner ignores `routing_method_type`).

**Commit 2 — the recipe (docs only).** The GB300 / MXFP8 / balanced cell in `docs/src/snippets/configs/MiniMaxAI/minimax-m3.jsx` moves `--moe-runner-backend deep_gemm` → `flashinfer_trtllm`, and the M3 page gains a Note stating the gains, the FlashInfer floor, and the current-release caveat. Other platforms keep `deep_gemm`.

> **Dependency: the recipe commit is conditional on the next FlashInfer release.** The unconditional form of this recipe needs the first FlashInfer release containing [flashinfer#8042](https://github.com/flashinfer-ai/flashinfer/pull/8042) (fused shared experts beyond DeepSeekV3 routing — the extension we requested in [flashinfer#7810](https://github.com/flashinfer-ai/flashinfer/issues/7810) and validated on GB300 against the PR head). With it, shared-expert fusion adds **+13.1% median interactivity at concurrency 8 and +7.5% median / +14.3% p90 at concurrency 20** on top of the runner switch, and single-stream flips ahead of `deep_gemm` (~+8% median) — no concurrency caveat left. On today's FlashInfer releases (without #8042), SGLang auto-disables shared-expert fusion on this runner (`srt/arg_groups/overrides.py`); the switch is then positive for concurrent serving (≥ ~8 sessions) but regresses single-stream ~9% median (the unfused shared expert runs as two extra dense MXFP8 GEMMs per layer per step). The page Note states both. We kept the PR open rather than Draft to match how #47187 carries its image dependency; happy to convert to Draft, or to split the recipe commit back out, if preferred. A follow-up PR enabling shared-expert fusion on this runner (passing `num_fused_shared_experts` through the fp8 block-scale path; ~20 lines, already validated by us against the FlashInfer PR head) will come once the FlashInfer release ships.

## Numbers (GB300 sm103, TP4, MXFP8, 900 s agentic replays, zero request errors on every run)

| concurrency | deep_gemm p50 | flashinfer_trtllm p50 (current FI, shared expert unfused) | + fused shared expert (FI with #8042) |
|---|---|---|---|
| 1 | 53.7 | ~ -9% | 57.2 (**+8%** vs deep_gemm; +16.2% vs unfused) |
| 8 | 36.7 | 37.8 (+3.4%) | 41.0 (**+13.1%** vs unfused) |
| 20 | 23.6 | 25.6 (**+8.1%**, p90 +9.7%) | 28.1 (**+7.5%** more, p90 +14.3%) |
| 40 | 12.2 | 12.1 (-1.3%, queue-bound band) | 11.4 (-3.9% vs unfused, queue-bound band; most completed requests) |

Validation of the code fix: without the declaration the serve crashes at the first MoE call inside CUDA-graph capture with FlashInfer's `n_group` validation error (DeepSeekV3 fallback engaged); with it, per-rank FlashInfer API logs show `trtllm_fp8_block_scale_moe` dispatched on all 4 TP ranks (tens of thousands of calls over the 900 s replay). Kernel-level numerics gated against fp32 references throughout (max 6.9% — the same gate the recipe's DeepGEMM composition passes); no end-to-end accuracy benchmark was run — a standard accuracy check on the team's verification pipeline would be a welcome gate at merge.
