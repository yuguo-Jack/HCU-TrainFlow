# [Perf] [NVIDIA] kimi-k3: Low-latency SM107 path, prepared FP4 routing metadata and fused route preparation

[Upstream PR](https://github.com/sgl-project/sglang/pull/46473) · state: closed · merged: False

## Original PR description

## Motivation

Kimi-K3 NVFP4 decode at TP8 on SM107 is launch- and latency-bound at small batch: every MoE layer pays separate launches for the front projection, routing, activation quantization, routing-metadata preparation and the finalize all-reduce, and several of the fused K3 collectives were tuned for SM100/SM103 only. This series carries the low-latency path the fork developed for SM107 onto main, with the parts that are architecture-general (device-side routing metadata, fused route + quant, M <= 8 prepared routing) enabled on SM100/SM103 too.

## Modifications

Seven commits, in dependency order:

- **Low-latency SM107 path** (`model_overrides/kimi_k3.py`, `k3_ar_fusion.py`, `gemm_ag.cuh/.py`, `ar_fusion.cuh`, `all_reduce_residual.py`, `cutedsl_bf16_gemm.py`, `kimi_k3.py`): the K3 override admits SM107 without speculative decoding; the deferred MoE finalize + push all-reduce + RMSNorm also carries the shared-expert partials (`[latent | shared]`) so both ride one collective; the all-gather GEMM gets a tunable producer grid (`split_n=8` at BS1 on SM107) and an FP32 gather variant that shards the replicated latent down-projection across TP8; skinny BF16 projections route from TGV to the JIT tiny GEMM on SM107 when `m <= 8`, `m * n <= 8192`, `k > n`.
- **Tensor-core gemm_ag producer** (`gemm_ag.cuh`): used for `N_SPLIT == 8`, bf16 output, `4 <= M <= 8` (the verify batch); `M <= 2` keeps the CUDA-core path. New `test_gemm_all_gather_split8_with_c` covers the split-8 module at M = 1, 2, 4, 8 and runs on B200 too.
- **Shared SiTU fusion** (`k3_shared_situ.cuh/.py`, `kimi_k3.py`): BS1 TP8 SM107 only; the router rows move into the sharded FP32 latent GEMV + multicast gather, and the shared-expert gate/up is fused with SiTU on the side stream. Falls back to the existing front path otherwise.
- **Prepared expert-tile routing metadata** (`trtllm_prepared_fp4.py`, `route_quant_metadata.cuh`, `moe_route_quant_fused.py`, `route_quant_handoff.py`, `flashinfer_trtllm.py`): build the routing metadata on device and hand it to FlashInfer's native FP4 MoE body through `TrtllmMoERoutingMetadataSlot`; routes are sorted by expert with one padded CTA tile per distinct expert, so it covers token counts up to the tile size. Runs on SM100/SM103/SM107; unsupported cases fall back to normal dispatch.
- **Fused NVFP4 routing preparation, prepared routing for M <= 8** (same files): radix routing fused with native NVFP4 quantization in one kernel; `route_quant_metadata.cuh` templated on a row quantizer (MXFP8 and NVFP4) so both formats write the expert-tile metadata in-kernel for M = 1..8.
- **Fused route preparation at every batch size**: metadata stays M <= 8; larger M publishes no metadata and the ordinary routed body consumes the prepared input; `_forward_routed` stages the handoff through a shared `_route_staged` helper.
- **Pass `moe_op` to the FlashInfer MoE runner constructor** (one-line fix for the prepared path).

Port notes against main: the FP4 runner keeps main's hidden-dim padding and deferred-finalize checks (`route_quant_handoff.take` is gated on `hidden_pad == 0`); the route-quant coverage keeps main's 64-token cap; the fork-only gemm_ar test is not carried.
