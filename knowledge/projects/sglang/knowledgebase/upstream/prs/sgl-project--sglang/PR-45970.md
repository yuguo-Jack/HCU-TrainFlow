# [Feat] metrics: Export prealloc_{full,swa}_token_usage for decode requests with a pending KV transfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/45970) · state: closed · merged: True

## Original PR description

## Motivation

On a disaggregated decode engine, `sglang:full_token_usage` and `sglang:swa_token_usage` count the KV reserved for requests whose transfer from prefill is still pending together with the KV of the running batch. When a pool sits near 1.0 the exported metrics cannot say whether the running requests or the pre-allocated transfer-queue requests hold it, so sizing `--max-running-requests` and reading prealloc-queue growth is guesswork. The decode log line already prints a "pre-allocated usage" figure, but nothing exports it.

## Modifications

- `DecodePreallocQueue.pre_allocated_token_counts()` (next to `num_tokens_pre_allocated`) sums the private full and SWA KV of transfer-queue requests, host-staged ones excluded, with the pool observer's `kv_private_tokens` / `kv_private_swa_tokens`: the page-aligned fill that `_pre_alloc` charged, minus the SWA head that tail preallocation already marked evicted. This is the same charging the pool stats apply to a request's private KV.
- `PoolStats.full_capacity` is now set on the plain and hybrid-SSM paths as well (it was only set for hybrid-SWA), so every path reports the denominator `full_token_usage` divides by.
- `SchedulerStats.prealloc_full_token_usage` / `prealloc_swa_token_usage` are filled in `_update_decode_queue_stats` as ratios against `PoolStats.full_capacity` / `swa_capacity` (0 for pools without SWA), and `SchedulerMetricsCollector` exports them as `sglang:prealloc_full_token_usage` and `sglang:prealloc_swa_token_usage`.

`full_token_usage - prealloc_full_token_usage` is therefore the running batch's share of the pool, and likewise for SWA. Prefill engines never reach `_update_decode_queue_stats`, so the gauges stay 0 there.

These gauges use page-aligned counts and each pool's own capacity, so they can be subtracted directly from `full_token_usage` and `swa_token_usage`. The existing `pending_prealloc_token_usage` field is left as it is.

## Tests

New `test/registered/unit/observability/test_prealloc_token_usage.py` (`base-a-test-cpu`), 6 cases: page-charged counting for plain and tail-preallocated SWA transfer-queue requests with a host-staged request excluded, an empty queue, the hybrid-SWA and plain-pool capacity bases, zero capacity, and both gauges reaching a Prometheus registry through `log_stats`. All pass locally on this branch; `pre-commit` passes on the changed files.

To verify end to end with a public hybrid-SWA model and synthetic requests: launch a one-prefill / one-decode deployment with `--enable-metrics`, send a burst of long-input requests, and scrape the decode engine's `/metrics` while transfers are pending and again after the transfer queue drains. The two gauges should be non-zero only while `num_decode_transfer_queue_reqs` is, stay at or below the pool usage they are subtracted from, and return to zero with the queue; before this change no `sglang:prealloc_*` series exists.
