## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Dense Qwen3 prefill launches QK normalization and cached RoPE separately, then FA3 or FlashInfer materializes contiguous Q. This change combines normalization, the same cached RoPE, and contiguous Q output in one CUDA launch. K is normalized and rotated in its original packed QKV storage; Q input and V remain unchanged.

It uses the existing `--enable-fused-qk-norm-rope` opt-in and remains disabled by default on CUDA. Attention kernels and KV-cache handling are unchanged.

## Modifications

<!-- Detail the changes made in this pull request. -->

- **Kernel:** Add lazily registered `attention.qk_norm_rope` with FP16/BF16 support, tensor/device/dtype/stride/alignment checks, and explicit K/output mutation metadata. D128 processes two rows per warp; D64/D256 use one. Share the existing standalone half-warp normalization arithmetic, round normalized values before FP32-table rotation, and preserve shuffle participation for an unmatched final row.
- **Dense dispatch:** Fuse only ordinary dense-Qwen3 `EXTEND` on Hopper, head dimension 128, TP1, unquantized weights, FA3/FlashInfer, full-head unscaled NeoX RoPE, and matching activation/weight dtypes. Keep speculative, mixed, verification, inherited/non-Qwen3, deterministic, compiled, and other unvalidated configurations on the separate path. Preserve existing BF16 table decode guards.
- **Coverage/documentation:** Extend existing kernel and model fixtures for native byte parity, Q/K/V ownership, padding, empty input, fallback dispatch, and changing-input CUDA graphs. Add a cold-L2 preparation benchmark including the baseline consumer's Q conversion, and document the opt-in in the Qwen3 cookbook.

Disabling the existing flag or reverting this contribution rolls the change back; there is no checkpoint, schema, or persisted-data migration. On upstream base-versus-PR comparisons, keep the existing flag enabled in both trees so BF16 decode treatment is identical.

Common launch settings in every arm:


For Qwen3-4B use `DTYPE=bfloat16`, `BACKEND=fa3`, and append `--return-hidden-states-mode last`. For Qwen3-Embedding-0.6B use `DTYPE=float16`, `BACKEND=flashinfer`, and append `--is-embedding`. Use local model snapshots with offline Hugging Face/Transformers access and only one visible GPU.

The HTTP client uses explicit token IDs, not tokenizer-generated random text:

```python
def ids(length, seed):
    return [1000 + (i * 13 + seed * 79) % 3000 for i in range(length)]
```

- **Generation:** `POST /generate` with `input_ids=ids(4096, seed)`, `sampling_params={"temperature": 0, "max_new_tokens": 1, "ignore_eos": True}`, `return_logprob=True`, and `return_hidden_states="last"`. Hidden-state/logprob response serialization is included in the measured latency.
- **Embedding:** `POST /v1/embeddings` with one token-ID array in `input=ids(length, seed)` and `encoding_format="float"`; measure lengths 4096 and 8192 separately.
- **Order/cache:** fresh servers in A1 -> B -> A2 order for each model/configuration. Before each window issue eight concurrent warmups with seeds `700 + i` (`i=0..7`), wait for all eight, then `POST /flush_cache?timeout=60` once. Read that response as text, not JSON. Submit 200 measured requests with seeds `1000 + i` (`i=0..199`) through a semaphore of four, with no flush between requests.
- **Timing:** after acquiring the semaphore, start the request timer immediately before the HTTP POST; validate status, read the complete response body as text and JSON-decode it before stopping. Client semaphore queue time is excluded. Compute percentiles over the 200 successful request times. A separate wall timer surrounds submission/completion of all 200 requests; throughput is `200 / wall_seconds`.

`bench_serving --disable-stream` reproduces the non-streaming timing class, but ordinary `random-ids` mode does not guarantee the same IDs, diagnostic fields or JSON-read boundary. Use the explicit HTTP protocol above when matching this workload.
