# [Fix] openai: Report reasoning tokens where OpenAI clients read them

[Upstream PR](https://github.com/sgl-project/sglang/pull/45131) · state: open · merged: False

## Original PR description

## Motivation

OpenAI reports reasoning tokens at `usage.completion_tokens_details.reasoning_tokens` (`CompletionUsage`). SGLang's chat and completions usage reports them only at its own top-level `usage.reasoning_tokens` (#15562), so OpenAI clients and gateways that read standard fields see none.

## Modifications

- **Python:** `UsageProcessor.calculate_token_usage` sets `completion_tokens_details.reasoning_tokens` for chat and completions:
  - the non-streamed response;
  - the final `include_usage` chunk;
  - `continuous_usage_stats` chunks.
- The value is capped at `completion_tokens`. The reported reasoning count can exceed it: two recorded parity cases do, for example 51 of 48.
- The top-level field is unchanged.
- `UsageInfo` built without generation (embeddings, score, classify) omits the key rather than sending null.
- **Rust:** `sglang-processor` and the native `sglang-server` report the same field. `sglang-server`'s typed object also sets the spec's other detail counts to 0. The OpenAI parity fixtures gain it in every usage object.
- **Test helper:** `tool_call_test_runner.py` reads the SDK's `completion_tokens_details` as an object.
- **Not covered:**
  - `sgl-model-gateway`'s gRPC router builds its own usage; its Harmony path already reports the field.
  - `sglang-processor`'s `ChatResponseProcessor`.

**Merge notes:**
- This and #45130 both edit the generated `deepseek-v4-flash-0731.json` OpenAI parity fixture. Whichever merges second regenerates it.
- This and #45132 both add an import to `sglang-server`'s completions test module; keep both.
