# [Fix] Align prefill CUDA graph token buckets with attention TP size

[Upstream PR](https://github.com/sgl-project/sglang/pull/33200) · state: closed · merged: False

## Original PR description

<!-- Thank you for your contribution! Please follow these guidelines to enhance your pull request. If anything is unclear, submit your PR and reach out to maintainers for assistance. Join our Slack community at https://slack.sglang.io to discuss further. -->

## Motivation

When attention or MLP TP gather is enabled, prefill CUDA graph capture requires the number of tokens to be divisible by `attn_tp_size`. However, the configured prefill graph buckets may contain unaligned values such as `28`, causing collective operations such as `reduce_scatter` to fail during graph capture.
This can make server startup fail even though the normal prefill path already aligns token counts before execution.

## Modifications

- Normalize prefill CUDA graph token buckets using `get_cuda_graph_batch_size_alignment()` and `ceil_align`.
- This normalization applies not only to TP gather but also to two-batch overlap and attention CP configurations, since `get_cuda_graph_batch_size_alignment()` doubles the alignment under two-batch overlap and multiplies in attn_cp_size for attention CP.
- Deduplicate and sort the aligned token buckets.
- Drop aligned buckets that exceed the configured maximum.
- Update `prefill_config.bs` before creating `PrefillCudaGraphRunner`, so the capture runner and log use the same normalized values.

## Independent validation results

We independently validated the bucket-alignment behavior proposed by this PR at head `dc52d4ec1ed341437088a08064ca3ab78f8c3394`.

Because SGLang’s APIs have changed since the PR was authored, the original diff no longer applies cleanly to current `main`. We therefore re-expressed the same behavior against the current API and tested that version:

- Normalize the configured prefill CUDA-graph token buckets using the alignment returned by `get_cuda_graph_batch_size_alignment()`.
- Deduplicate and sort the resulting buckets.
- Assign the normalized list back to `prefill_config.bs` before constructing `PrefillCudaGraphRunner`.

### Test configuration

- Public base image: `lmsysorg/sglang:dev`
- SGLang version reported by the base image: `0.0.0.dev1+g8874c51a9`
- Model: DeepSeek-R1 671B, FP8
- Hardware: 2 nodes × 8 H100 GPUs
- Parallelism:
  - `--tp 16`
  - `--dp 2`
  - `--enable-dp-attention`
  - `--nnodes 2`
- Effective attention TP size: `attn_tp_size = tp / dp = 8`
- Workload after server startup: 8,000 input tokens / 1,000 output tokens at concurrency levels `1, 4, 16, 64, 256, 1024`

We ran paired control and treatment builds from the same public base-image digest. The only intentional code difference was the prefill CUDA-graph bucket normalization described above.

### Control result: unmodified SGLang

The unmodified build reproduced the reported failure during server initialization, before any benchmark requests could run.

Prefill CUDA-graph capture reached an unaligned bucket:

```text
num_tokens=28
attn_tp_size=8
```

It then failed in the DP gather path:

```text
dp_gather_partial
  -> _dp_gather
  -> _dp_gather_via_all_gather
  -> reduce_scatter_tensor
```

with:

```text
ValueError: input tensor must be the same size as output size times world size
```

This is consistent with `28` not being divisible by the attention TP size of `8`. The scheduler subsequently exited during initialization.

The unmodified control reproduced the same failure in two independent paired runs. In the first run, the exception appeared on 16 ranks. It did not reach a usable server state in either run.

### Treatment result: aligned prefill buckets

With the alignment change applied:

- Prefill CUDA-graph capture completed successfully.
- The server started normally.
- The `reduce_scatter_tensor` size error occurred zero times.
- The full six-point concurrency sweep completed successfully in the run with a sufficient wall-clock allowance.
- A separate earlier run also cleared graph capture and successfully completed five of the six concurrency points; it was stopped by the external job time limit while processing the last point, without reproducing the graph-capture exception.

Across both paired runs, the result was consistent:

| Configuration | Prefill graph capture | Server startup | Size mismatch |
| --- | --- | --- | --- |
| Unmodified control | Failed | Failed | Reproduced |
| Aligned buckets | Passed | Passed | Not observed |

### Root-cause confirmation

With `tp=16` and `dp=2`, the attention TP group size is `8`. The default prefill capture list contains values such as:

```text
4, 12, 20, 28, ...
```

These values are not divisible by `8`. When one reaches the gathered-buffer path during graph capture, `reduce_scatter_tensor` receives incompatible input and output sizes.

Other related paths already account for this constraint:

- Decode CUDA-graph capture uses the CUDA-graph batch-size alignment.
- The normal runtime prefill path pads token counts to the attention TP size.

The prefill CUDA-graph capture setup is the missing case. Ceil-aligning its buckets, deduplicating the results, and updating `prefill_config.bs` before runner construction removes the inconsistency. For an alignment of `8`, for example:

```text
4, 12, 20, 28  ->  8, 16, 24, 32
```

This is exactly the behavior that resolved the failure in our paired testing.

### Rebase note

The PR’s current code uses the older forms:

```python
require_attn_tp_gather(model_runner.server_args)
require_mlp_tp_gather(model_runner.server_args)
```

On current `main`, those helpers no longer take `server_args`, and the relevant composite alignment is exposed through:

```python
get_cuda_graph_batch_size_alignment()
```

The change will therefore need to be rebased and expressed using the current alignment API. The important validated behavior is that the aligned, deduplicated bucket list is written to `prefill_config.bs` before `PrefillCudaGraphRunner` is created, so logging, runner construction, and capture all consume the same normalized values.

It would also be useful to ensure that capacity filtering is applied to the final aligned values, since ceil-alignment can move a bucket above a configured capture limit.

### Suggested regression coverage

A focused unit test could verify that:

1. With a required alignment of `8`, buckets such as `4, 12, 20, 28` become `8, 16, 24, 32`.
2. Multiple input buckets that align to the same value are deduplicated.
3. The resulting list is sorted.
4. Every final bucket is divisible by the required alignment.
5. The normalized values are stored in `prefill_config.bs` before runner construction.
6. Configurations with alignment `1` preserve their existing bucket values.
7. Any bucket moved beyond `max_capture_tokens` by alignment is excluded or otherwise handled consistently.

### Conclusion

The aligned-bucket behavior fixes the reported startup failure under the tested multi-node TP16/DP2 DP-attention configuration. The unmodified build reproduced the failure consistently, while the patched build completed CUDA-graph capture, started the server, and ran the complete workload.

This validation establishes the functional fix. We did not separately characterize performance changes attributable specifically to bucket normalization.

Rounding up can push the largest bucket past the configured maximum. For example, `--cuda-graph-max-bs-prefill 20` with `attn_tp_size=8` now captures 24. With the default bucket generator this only happens for small maxima (below 32 at `attn_tp_size` 8 or 16, below 256 at 32). A custom `--cuda-graph-bs-prefill` list hits it directly. Capping at the configured max keeps the list from growing, and it matches decode, where `get_batch_sizes_to_capture` drops misaligned sizes instead of rounding them up:
