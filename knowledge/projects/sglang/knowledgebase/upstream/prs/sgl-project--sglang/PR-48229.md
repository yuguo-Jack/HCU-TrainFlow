# [Perf] dsv4: Expand the low-ratio indexer page table in one Triton kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/48229) · state: closed · merged: True

## Original PR description

## Motivation

In a DSv4.1 DEP16 decode trace with DSpark verify (bs 256 per rank), building the indexer metadata for the ratio-1 and ratio-2 layers ran a chain of torch ops for each ratio: int64 cast, multiply, broadcast add of an arange, and a cast back to int32. All of them ran at the full expanded width, `[1024, 2049 * blocks_per_page]`. Together they took about 67 µs per step.

## Modifications

- `expand_index_page_table` (`dsv4/metadata.py`) sends GPU tables with unit column stride and a power-of-two `blocks_per_page` to the existing Triton kernel in `attn_glue_hip.py`. That kernel writes the int32 table in one launch and matches the torch expression bit for bit. Other inputs keep the torch path.
- `test_dsv41_decode_glue_hip.py::test_expand_index_page_table` used `expand_index_page_table` as its reference. After this change it would compare the Triton kernel with itself, so its reference now runs the torch expression on CPU.
- `test_fp4_indexer.py::test_expand_index_page_table_matches_cpu` (CUDA) covers the CUDA dispatch, which the gfx95-gated HIP file does not. It compares the GPU result with the CPU torch path, on a contiguous and a row-strided table.

## Accuracy Tests

Output is bitwise identical. A standalone check on one GPU compared the Triton kernel with the previous torch expression using `torch.equal` on these inputs:
- `[1024, 2049]` with `blocks_per_page` 4 and 2
- `[256, 2049]`, `[3, 17]`, `[1, 300]` and an empty table
- a row-strided table
- `-1` entries and int32 edge values (`2^31 - 1`, `-2^31`, `2^30`)

All matched. `test_expand_index_page_table_matches_cpu` passes on a B300 (5/5).

## Speed Tests and Profiling

Each call was captured in a CUDA graph and replayed 200 times, in A/B/A/B order. Times include the graph-replay overhead.

| shape | blocks_per_page | before (µs) | after (µs) |
|---|---|---|---|
| `[1024, 2049]` | 4 (ratio 1) | 40.9 / 41.1 | 7.1 / 7.2 |
| `[1024, 2049]` | 2 (ratio 2) | 25.0 / 26.7 | 7.3 / 7.1 |

That is about 67 → 14 µs per decode step at bs 256. Prefill and the sparse-candidate table use the same function, so they benefit too. These numbers come from running the operation alone; end-to-end step time was not measured.
