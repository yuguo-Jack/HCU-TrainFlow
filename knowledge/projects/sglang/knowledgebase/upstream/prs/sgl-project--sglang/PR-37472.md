# [Fix] dspark: Keep verify bookkeeping in range for rows without candidates

[Upstream PR](https://github.com/sgl-project/sglang/pull/37472) · state: open · merged: False

## Original PR description

## Motivation

DSPARK verify can hand out-of-range indices to token gathers on rows with no verify candidates (padded CUDA-graph rows, `verify_lens == 0`), tripping device-side index asserts that take down the engine:

- The chain-verify buffers are allocated with `torch.empty`, and the accept kernel never writes those rows, so their uninitialized slots still feed the bonus-token gather. This is load-dependent: the buffers are reallocated with fresh memory when the batch reaches a new size tier.
- `cap_correct_len` returns `-1` for those rows.
- Rejected drafts are copied into `out_tokens`.

(This PR originally also capped draft sampling to the target vocabulary. Main now crops the draft's base logits to the target `lm_head`'s vocabulary, so that part was dropped.)

## Modifications

- Zero-initialize the chain-verify buffers (`predicts`, `accept_index`, `accept_token_num`).
- Clamp `correct_len` at 0 in `cap_correct_len` (torch and Triton).
- Zero rejected and tail slots in `build_out_tokens` (torch and Triton).

## Accuracy Tests

`test/registered/spec/dspark/test_dspark_kernel_parity.py` gains two GPU subtests (`verify_lens == 0` rows, rejected/tail slots). Both fail on main and pass here; the existing parity subtests show valid rows are unchanged.

## Speed Tests and Profiling

Not applicable: zero-init happens only on buffer (re)allocation, and the clamp and zero-fill are elementwise ops on tensors verify already touches.
