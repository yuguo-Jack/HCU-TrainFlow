# [Perf] mhc: Split hc_combine_norm_mxfp8 rows by batch size and zero padding scales in the kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/46024) · state: closed · merged: True

## Original PR description

[by Claude Code]

## Motivation

`hc_combine_norm_mxfp8` is the DeepSeek-V4.1 mHC kernel that builds the attention input on Blackwell: it combines the
four residual streams weighted by `pre` (the per-row weights of the four streams), applies RMSNorm, and writes the
result in BF16 and in MXFP8 for `wqkv_a`. It runs when the batch has at most 128 rows, and only where the previous
mHC post has not already built that input (the fused MoE all-reduce epilogue at TP2/TP4 and Mega-mHC do), so with DP
attention and Mega-mHC off, as in every published DEP recipe, it runs before 39 of the 40 attention layers of each
decode step of up to 128 tokens per rank. It had two fixed costs. It always ran 4 CTAs per row, and each of them
recomputed the whole row (the combine and the RMS statistic) to store a quarter of it; that split was chosen when the
kernel took at most 8 rows, and #42245 raised the limit to 128 rows without revisiting it. And its MXFP8 scale buffer
came from `torch.zeros`, a separate fill kernel before every call (the scales of the rows past the batch are padding
of a 128-row scale tile and must be zero). This PR picks the split by row count, as `hc_combine_norm` in the same
file already does, and zeroes the padding scales inside the kernel. The outputs are bitwise identical: every CTA still
computes the whole row in the same order, and the split only decides which CTA stores which columns.

- **Accuracy:** bitwise identical to the previous kernel on B200, B300 and VR200 (3,082-3,850 cases per GPU, 0
  mismatches). GSM8K under AgentX load on B200: 97.67% without this PR, 96.33% with it (exact McNemar p = 0.29).
- **Kernel:** 41-46% faster on average at 49-128 rows (B200 6.24 → 3.40 us, B300 5.63 → 3.20 us, VR200 4.56 →
  2.68 us) and 20-26% faster at 1-32 rows, measured alone; the fill kernel before every call is gone.
- **End to end: no measurable change.** DeepSeek-V4.1-Flash on 4x B200, the published InferenceX AgentX DEP4 c192
  cell (where this kernel runs on the most decode steps at the most rows), real speculative acceptance, 2 ABBA pairs on
  one node: per-request decode time per token −0.32% (95% interval −0.56% to +0.02%), inside the run-to-run noise of
  the same configuration (0.6-1.1%); output throughput per GPU −0.01% and −0.12%.
- **Why the kernel saving does not reach the step on B200:** in decode the combine runs at the same time as the mHC
  statistics of the same residual on a side stream (on SM100, two DeepGEMM TF32 GEMMs from 32 rows up, a Triton kernel
  below). Next to them the new kernel is not faster: with the DeepGEMM statistics beside it, a combine + GEMM
  iteration takes 19.82 us before and 21.89 us after this PR (mean over 48-120 rows, microbenchmark), and in the
  serving profile the next GEMM did not start earlier.
- **End to end (estimate, not measured):** counting the per-call saving as if the combine were on the critical path,
  a B200 DEP4 c64 profile (decode at 24-30 rows) gives 39 calls x 2.45 us = 96 us per 11.5 ms decode step, about
  0.8%. The measurement above and the side-stream overlap show that this upper bound is not reached.

## Modifications

**+41 / −25 runtime code (1 file), +74 / −1 tests (1 file).** A Triton kernel change; no new flags, no default
changes.

In `python/sglang/kernels/ops/layernorm/hc_combine_norm.py`:

- `_parts_for(m, k)` uses the same split as `hc_combine_norm`: 4 CTAs per row up to 8 rows, 2 up to 48 rows, and 1
  above that. Up to 8 rows the split is unchanged.
- The scale buffer is allocated with `torch.empty`. Extra programs after the last row zero the padding, as
  `rmsnorm_mxfp8` already does: each takes one 512-byte block of the scale buffer and zeroes the bytes of the rows
  past the batch. At hidden 5120 that is 40 extra programs; at 128 rows there is no padding and none run.
- The kernel takes the row count `M` as an argument. The per-row body is unchanged, now under `if row < M`.

**Related:** draft #41628 by @harmya contains the same row split inside a larger change (it raises the fusion batch
limits and keeps `torch.zeros`). This PR carries the split on its own, plus the in-kernel zeroing.

Tests, in `test/registered/kernels/ops/layernorm/test_mxfp8_epilogue.py`:

- The existing bitwise test against `hc_combine_norm` followed by FlashInfer `mxfp8_quantize` (cuda and cute-dsl
  backends) adds rows 48 and 49 (either side of a split threshold), 84 and 120.
- New `test_combine_norm_mxfp8_split_invariant`: with the split forced to 1, 2 and 4, the outputs equal the default
  split byte for byte, both eagerly and on a CUDA-graph replay whose outputs were first filled with `0xFF`.
- New `test_combine_norm_mxfp8_padding_disjoint_from_live_rows`: on the GPU, a padding program that also overwrote a
  live row's scales would go unnoticed, because the live row stores its scales last (on B200 even the largest grid,
  520 CTAs, runs in one wave). The test runs the kernel in Triton's interpreter (`TRITON_INTERPRET=1`, in a
  subprocess, on CPU), which runs the programs one at a time in grid order, over a scale buffer filled with `0xFF`,
  for 1, 49 and 127 rows and splits 1, 2 and 4. It checks that every byte gets written and that exactly 160 bytes per
  live row are non-zero. It takes about 20 s.

## Speed Tests and Profiling

**Microbenchmark**, one GPU, CUDA graphs. Inputs: BF16 `x` of shape [m, 4 x 5120] and FP32 `pre`. Times are per call
in us: the median of 7 repetitions, each 100 replays of a graph of 20 calls (hot L2 on purpose: the inputs are at most
5.2 MB, and in serving the kernel reads residual streams that the previous sublayer wrote just before).

| rows | B200 | B300 | VR200 (SM107) |
|---|---|---|---|
| 1 | 3.89 -> 2.87 | 3.38 -> 2.67 | 3.20 -> 2.46 |
| 32 | 4.01 -> 3.08 | 3.59 -> 2.87 | 3.45 -> 2.59 |
| 64 | 5.12 -> 3.28 | 4.51 -> 3.17 | 4.28 -> 2.65 |
| 96 | 6.18 -> 3.38 | 5.63 -> 3.18 | 4.32 -> 2.68 |
| 128 | 7.08 -> 3.48 | 6.46 -> 3.28 | 5.21 -> 2.71 |
| mean of 49, 64, 84, 96, 100, 112, 120, 128 rows | 6.24 -> 3.40 (-46%) | 5.63 -> 3.20 (-43%) | 4.56 -> 2.68 (-41%) |

- Every timed row count got faster: 17 row counts from 1 to 128 (14 on B300). At 1-32 rows each is 20-26% faster.
- Above 48 rows, the two parts of the change save, per call (means over 49-128 rows): the new split alone (the old
  kernel with only the split changed) 1.90 / 1.74 / 1.13 us on B200 / B300 / VR200, and removing the fill alone (the
  new kernel forced to 4 CTAs per row) 1.02 / 0.65 / 0.53 us. Up to 8 rows the split is unchanged; the 0.7-1.0 us
  saved there is the fill.

**Next to the side stream (B200).** In decode, `deepseek_v4_mhc` forks the mHC statistics of the same residual onto
a side stream right before the combine. On SM100 with at least 32 rows they are `hc_mix_stats_sinkhorn_deepgemm` (two
DeepGEMM `tf32_hc_prenorm_gemm` calls and a Sinkhorn kernel); below 32 rows, and where DeepGEMM's prenorm is off, the
Triton `hc_mix_stats_sinkhorn`. Per iteration: fork; side stream the statistics; main stream the combine, then a
stand-in for `wqkv_a` (BF16 GEMM [m, 5120] x [5120, 2048]); join. Mean us per iteration over 48, 60, 72, 84, 96, 108
and 120 rows (each the median of 7 repetitions), outputs checked byte for byte:

| Layout | Before | This PR | This PR, split forced to 4 | This PR, split forced to 2 |
|---|---:|---:|---:|---:|
| Combine alone | 5.48 | 3.24 | 5.03 | 3.73 |
| Combine + GEMM, no side stream | 13.90 | 11.67 | 13.48 | 12.19 |
| + DeepGEMM statistics on the side stream (the SM100 serving path) | 19.82 | 21.89 | 21.20 | 22.09 |
| + Triton statistics on the side stream | 27.04 | 22.66 | 25.84 | 23.80 |

- With the DeepGEMM statistics beside it, this PR is about equal at 48 and 60 rows (18.86 → 18.42, 19.14 → 18.79 us)
  and slower from 72 rows, by 1.3 to 4.0 us per iteration. Without the fill kernel, the combine starts as soon as the
  statistics do and competes with them for SMs; the variant that keeps 4 CTAs per row and drops only the fill is
  slower than before as well.

**In the server (B200 DEP4 c192, GPU profile of 80 steps on all ranks, one run per arm, profiler on):**

- Every target-verify decode graph holds 39 calls of this kernel in both arms. Before this PR every call (12,168 of
  12,168) directly follows the fill kernel; with it, none do.
- At 60 rows, at 37 of the 39 layers both kernels run entirely beside the side-stream DeepGEMM GEMMs. The old path
  takes 1.31 us (fill) + 0.48 us (gap) + 4.38 us (kernel), medians over all calls and ranks; the new kernel takes
  7.0 us (median; 3.2 us alone in the microbenchmark, and 4.1 us at the other two layers, where the GEMMs overlap it
  for only about 2 us). At 18-30 rows (Triton statistics) the new kernel takes 3.8 us, and the old path 6.2 us from
  the start of the fill to the end of the kernel (4.6 us of it the kernel): 2.45 us more per call, the figure the
  estimate above uses.
- The time from the end of the mHC post to the start of the `wqkv_a` GEMM was not shorter with this PR: 6.85 → 7.68
  us at 60 rows, 6.9-7.4 → 8.6-10.7 us at 18-30 rows. In both cases the GEMM waits for SMs held by the side-stream
  statistics, which start later relative to the combine once the fill is gone.

**End to end on B200.**

- Setup: DeepSeek-V4.1-Flash, 4x B200 on one node, the published InferenceX AgentX DEP4 c192 cell (command below),
  image `lmsysorg/sglang:nightly-dev-cu13-20261021-c1c287a4`, whose `hc_combine_norm.py` is byte-identical to this
  PR's base and to current main. "With this PR" is the same image with this PR's `hc_combine_norm.py` mounted over it;
  each run checks the md5 of the file Python imports before any traffic. One change from the published cell: real
  speculative acceptance (the published runs set a simulated acceptance length).

  DEP4 runs (InferenceX run 39606211010, server logs) the busiest rank decodes a median of 5 requests at c64, 10 at
  c128, 16 at c192 and 26 at c256. In our c192 windows 62% of the decode log samples ran the kernel, 41% at 49-120
  rows.
- Runs: without, with, with, without this PR, fresh server per run; AgentX (agentx-harness 1.0.12, the published
  trace set, concurrency 192, 900 s profiling window after its warm-up).
