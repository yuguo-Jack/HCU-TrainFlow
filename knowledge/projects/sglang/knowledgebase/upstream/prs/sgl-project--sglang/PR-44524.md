# [Feat] metrics: expose per-process CPU usage

[Upstream PR](https://github.com/sgl-project/sglang/pull/44524) · state: open · merged: False

## Original PR description

## Motivation

Part of #43304: CPU counters currently merge tokenizer/detokenizer workers with the same `component`, hiding per-worker load skew.

## Modifications

Add a `pid` label to the shared CPU counter and bind its child once per monitor thread. CPU delta calculation, sampling interval and launch paths remain unchanged. This applies consistently to all existing monitor callers.

This changes metric cardinality: queries expecting one series per component need `sum without (pid)`. PIDs identify process lifetimes rather than stable worker slots; exited-worker counter values remain until the multiprocess directory is cleared. These tradeoffs and example queries are documented. Processing-time and queue-latency metrics are outside this PR.

## Accuracy Tests

- **Direct regression coverage:** all 3 CPU-monitor tests pass on macOS arm64/Python 3.12.14. The two-subprocess regression fails against original production code (1 merged series instead of 2), then passes with the change. It waits for monitor initialization, uses process CPU time for its workload and waits for a positive sample.
- **Linux compatibility:** an isolated import of the production monitor on Linux arm64/Python 3.12.14 with `prometheus-client==0.20.0` (the declared minimum) produces distinct PID series and preserves the sum reported by the individual processes. This checks the monitor/collector, not a full SGLang deployment.
- **HTTP export:** two real subprocesses, the production `add_prometheus_middleware`, FastAPI/Uvicorn and an HTTP GET to `/metrics` yield two PID series distinguishing a busy process from an idle one.
- 9 neighboring metrics-utils tests also pass; these are not additional coverage of the changed behavior.
