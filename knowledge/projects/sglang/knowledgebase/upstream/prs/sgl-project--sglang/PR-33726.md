# [Fix] bcg: preserve Qwen3-VL DeepStack inputs during replay

[Upstream PR](https://github.com/sgl-project/sglang/pull/33726) · state: open · merged: False

## Original PR description

## Motivation

Prefill breakable CUDA graph (BCG) replay should preserve the same model semantics as eager execution.

Qwen3-VL passes intermediate visual features through `input_deepstack_embeds` and adds them at selected language-model layers. However, BCG did not copy this request-specific tensor into a stable graph input slot.

As a result, normal BCG execution behaved like an explicit zero-DeepStack run rather than eager execution. Requests still completed successfully, making this a silent correctness issue.

## Reproduction

Environment:

- Model: `Qwen/Qwen3-VL-8B-Instruct`
- Revision: `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`
- GPU: NVIDIA H200
- Dtype: BF16
- Decoding: greedy, `max_new_tokens=20`
- Input: deterministic RGB vertical-stripe image

The GPU test harness temporarily enabled Qwen3-VL for BCG testing.

The experiment compares four arms:

1. `eager_normal`
2. `eager_zero_deepstack`
3. `bcg_normal`
4. `bcg_zero_deepstack`

The zero-DeepStack arms replace `input_deepstack_embeds` with zeros immediately before the language-model forward call.

Each result is formatted as:

```text
(common_prefix_length, all_token_ids_equal, maximum_absolute_logprob_difference)
```

| Comparison | Before fix | After fix |
|---|---:|---:|
| `bcg_normal` vs `eager_normal` | `(7, False, 1.154)` | `(15, True, 0.071)` |
| `bcg_normal` vs `bcg_zero_deepstack` | `(20, True, 0.000)` | `(7, False, 1.148)` |
| `bcg_zero_deepstack` vs `eager_zero_deepstack` | `(20, True, 0.066)` | `(20, True, 0.066)` |
| `eager_zero_deepstack` vs `eager_normal` | `(7, False, 1.138)` | `unchanged` |

Before the fix, `bcg_normal` was identical to `bcg_zero_deepstack` and diverged from `eager_normal`.

After the fix, `bcg_normal` matches `eager_normal` at the token level and correctly diverges from `bcg_zero_deepstack`. The zero-DeepStack control remains unchanged.

Instrumentation also confirmed that `input_deepstack_embeds` was present and non-zero at the language-model entry before replay.

The RGB image is used only as a deterministic semantic-equivalence test, not as a visual-quality benchmark.

Note on text-only numerics: the slot buffer changes the captured-graph layout, so text-only completions under BCG shift slightly relative to eager (divergence around char 78 in hardware testing, with the slot verified zero throughout). This is the same class as ordinary BCG-vs-eager drift, but anyone diffing text outputs across this PR should expect it.

## Modifications

- Add an explicit `supports_bcg_deepstack_replay` capability to Qwen3-VL.
- Add an optional stable `input_deepstack_embeds` buffer and graph slot.
- Allocate the slot only for multimodal models that opt in and have a non-zero DeepStack width.
- Pass the stable slot during BCG capture so the DeepStack additions are included in the graph.
- Copy the request-specific DeepStack tensor into the slot before replay.
- Clear missing and padded regions to prevent stale data from previous requests.
- Fail closed when a non-empty DeepStack tensor does not fit the captured slot, instead of replaying with a zeroed slot.
- Add Qwen3-VL and Qwen3-VL MoE to the breakable prefill CUDA graph allowlist.
- Add unit tests for capability gating, buffer allocation, slot registration, allowlist membership, and the per-replay slot lifecycle.

Absence (`None` or an empty tensor) clears the slot silently; a non-empty tensor with a mismatched shape, dtype, or device raises rather than silently downgrading the request to zero-DeepStack semantics.

The `RuntimeError` fires inside the replayed forward, so if the guard ever trips it takes down the scheduler rather than failing a single request. That is the intended trade for an unreachable contract violation, where the alternative is serving a silently wrong answer. Eager fallback is not available at this site: `input_deepstack_embeds` is only materialized inside `model.forward` (via `general_mm_embed_routine` → `separate_deepstack_embeds`), already past `_prepare_forward_metadata_for_replay` and inside the replay context, so there is no pre-commit validation point.

`input_embeds` cannot be reused because DeepStack has a different shape and is consumed at selected intermediate language-model layers.

`supports_bcg_deepstack_replay` is inherited by every subclass of `Qwen3VLForConditionalGeneration`: Qwen3.5, Qwen3.5-MoE, InternS1-Pro, InternS2-Mobius, InternS2-Preview, and the Qwen3-Omni MoE Thinker. This is deliberate. Those archs consume DeepStack through the same code path, so any checkpoint of theirs that ships non-empty `deepstack_visual_indexes` is covered without further change. Released checkpoints for those archs currently ship empty indexes, so the replay path is a no-op for them today. `MuseGlimmerForConditionalGeneration` is on the BCG allowlist but derives from a different base and does not consume DeepStack at all, so it is unaffected.

Qwen3-VL and Qwen3-VL MoE now get prefill graphs by default. This changes replay-vs-eager numerics to the new baseline, and anyone who previously forced breakable prefill was silently running zero-DeepStack and should see grounding improve.

## Speed Tests and Profiling

This is a correctness fix, not a speed optimization.

Models that do not activate DeepStack replay do not allocate the new buffer or perform the replay copy.

For Qwen3-VL-8B with `max_num_tokens=8192`, `hidden_size=4096`, three DeepStack embeddings, and BF16, the maximum additional buffer is:

```text
8192 × 4096 × 3 × 2 bytes = 192 MiB
```

No replay-latency benchmark was performed.

- charliechenye · COMMENTED · 2026-08-14T20:18:10Z · [source](https://github.com/sgl-project/sglang/pull/33726#pullrequestreview-4940885531)

Thanks for pushing this. I reviewed the replay path closely because we are actively working on SGLang-Omni Qwen3-Omni prefill BCG performance, and correct image/video DeepStack replay is an upstream dependency for that work.

The overall abstraction here looks right to me: explicit model opt in, a separate token axis stable slot, capture time storage, replay time refresh, and tail clearing so shorter requests cannot inherit stale DeepStack rows. The four arm H200 experiment is also exactly the semantic control I would want for this kind of silent replay bug.

I found one correctness behavior I think is worth tightening before merge:

**Malformed not None DeepStack should fail closed.**

In `replay_layer_forward`, if `input_deepstack_embeds` is not None but fails the shape/dtype/device checks, the current path warns, zeros the stable slot, and still replays the graph. That knowingly changes the request to zero-DeepStack semantics, which is very close to the silent behavior this PR is fixing.

A genuinely absent DeepStack contribution can safely clear the slot. If an empty tensor is an intentional absence sentinel, that can be handled explicitly too. For a non-None tensor that is incompatible with the captured slot, I would prefer either:

1. eager fallback if validation can happen before graph commitment; or
2. otherwise a `RuntimeError` from replay rather than returning a semantically altered result.

I would also strongly recommend one focused regression around the runtime slot lifecycle itself:

1. nonzero DeepStack is copied into the stable slot;
2. a shorter same bucket request zeros the unused tail;
3. a request with no DeepStack contribution clears the slot;
4. malformed not None shape/dtype/device fails closed.

The current allocation/registry tests are useful, and the H200 four arm result is convincing. The additional lifecycle regression would directly protect the stateful same bucket behavior that can otherwise turn into cross request stale data.

For downstream context, Qwen3-Omni in SGLang-Omni produces DeepStack features for both image and video. We are working on the SGLang-Omni performance path to late-bind both final `input_embeds` and full token aligned `input_deepstack_embeds` through BCG, so this PR is directly relevant to that work. Once this contract is settled, I am happy to run Qwen3-Omni image/video validation against the exact PR head and report replay/parity evidence here if that would help.
