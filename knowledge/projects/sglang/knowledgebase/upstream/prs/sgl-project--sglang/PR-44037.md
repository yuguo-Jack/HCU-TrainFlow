# [Perf] [AMD] diffusion: enable the bit-exact Triton SiLU-mul fusion on HIP

[Upstream PR](https://github.com/sgl-project/sglang/pull/44037) · state: open · merged: False

## Original PR description

## Motivation

Qwen-Image 2.1's FFN activation fast path (`fused_silu_mul_bitexact`) is gated on `current_platform.is_cuda()`. On ROCm that predicate is `False` (`PlatformEnum.ROCM`), so the optimization is dead code on AMD hardware — even though the fused kernel is plain Triton (no CUDA JIT / PTX) and reproduces the eager `silu(a) * b` chain bit-exactly on HIP.

This is the same situation the XPU port fixed in #41940, which enabled the identical kernel via `(x.is_cuda or x.is_xpu)`. This PR does the equivalent for ROCm/HIP.

## Modifications

`python/sglang/multimodal_gen/runtime/models/dits/qwen_image21.py`:

- Add `_silu_mul_device = current_platform.is_cuda() or current_platform.is_hip()`.

- Gate `QwenImage21FeedForward.forward` on `_silu_mul_device` instead of the vendor-pure `_is_cuda`.

Every other fast path in the module (RoPE, QK-norm, packed QKV, SDPA) stays CUDA-only, because those really are CUDA JIT / PTX kernels. The existing `BitExactFusionGate` still self-verifies the first call and permanently disables the path on any mismatch, so a platform that turns out not to be bit-exact falls back to eager instead of diverging.

`python/sglang/multimodal_gen/test/unit/test_qwen_image21_silu_mul_fusion.py` (new):

- assert the guard tracks the CUDA-like device family;

- assert `fused_silu_mul_bitexact` is bit-exact vs `F.silu(a) * b` at the FFN activation shapes.

## Accuracy Tests

Environment: AMD Ryzen AI MAX 395 (Strix Halo), Radeon 8060S Graphics, `gfx1151` (RDNA 3.5), torch `2.9.1+rocm7.2.4` (hip `7.2.53211`), SGLang Diffusion, attention backend `torch_sdpa`.

1. Kernel bit-exactness on `gfx1151` — `torch.equal(fused_silu_mul_bitexact(a, b), F.silu(a) * b)`:

   | shape           | max\_abs\_diff | bit-exact |
   | --------------- | -------------- | --------- |
   | (1, 4096, 3072) | 0.000e+00      | yes       |
   | (1, 2048, 3072) | 0.000e+00      | yes       |
   | (1, 1024, 3072) | 0.000e+00      | yes       |
   | (1, 4096, 2048) | 0.000e+00      | yes       |

2. End-to-end image output — Qwen-Image 2.1 @1024², 40 steps, seed 42. Two guard-OFF runs differ by *exactly* the same amount as guard-OFF vs guard-ON (max pixel diff 8; 173502 of 1048576 pixels differ). The residual difference is therefore entirely the pipeline's own run-to-run nondeterminism — the fusion adds no systematic deviation.

3. New unit test executed on ROCm with the platform probe working (the image ships the `amdsmi` bindings): `2 passed`; the bit-exact test covers the three FFN shapes via `subTest`. On ROCm images *without* `amdsmi` bindings, `multimodal_gen`'s probe falls back to CPU while `torch.cuda` still sees the GPU, so `test_guard_tracks_the_cuda_like_device_family` fails on its "unreachable on a CUDA-like device" assertion. That is a platform-detection gap tracked in #47296 (torch-based ROCm probe), not a property of this change; the RDNA4 report on #47296 shows both tests passing with it. The kernel-level bit-exactness test is unaffected either way.

## Speed Tests and Profiling

Per-call op timing (300 iters after warmup, `gfx1151`):

| shape           | eager    | fused    | speedup   |
| --------------- | -------- | -------- | --------- |
| (1, 4096, 3072) | 547.6 µs | 328.8 µs | **1.67x** |
| (1, 2048, 3072) | 167.5 µs | 130.1 µs | 1.29x     |
| (1, 1024, 3072) | 41.1 µs  | 25.6 µs  | 1.60x     |
| (1, 4096, 2048) | 354.5 µs | 219.9 µs | 1.61x     |

End-to-end — Qwen-Image 2.1 @1024², 40 steps, seed 42, `--dit-layerwise-offload --text-encoder-cpu-offload --pin-cpu-memory`, three runs per side:

| run                    | denoising stage (s)                | avg per-step (s)            |
| ---------------------- | ---------------------------------- | --------------------------- |
| guard OFF #1 / #2 / #3 | 156.86 / 157.46 / 159.77           | 3.2955 / 3.3066 / 3.3581    |
| guard ON  #1 / #2 / #3 | 159.00 / 154.66 / 155.50           | 3.3626 / 3.2684 / 3.2869    |
| **mean**               | **OFF 158.03 → ON 156.39 (−1.0%)** | **3.3201 → 3.3060 (−0.4%)** |

ON is faster in 2 of 3 pairs. The mean denoising delta (−1.0%) is within run-to-run noise at n=3 (per-run spread ≈1.5%), so the end-to-end figure should be read as *no regression, small favorable trend*. The deterministic part of the win is the kernel-level 1.67x; under `--dit-layerwise-offload` the FFN pointwise work partially overlaps weight prefetch, which masks most of it at this configuration.

## Notes for reviewers

- Reproduced on a ROCm-only machine; on a CUDA machine the guard evaluates to `True` exactly as before, so NVIDIA behavior is unchanged.
