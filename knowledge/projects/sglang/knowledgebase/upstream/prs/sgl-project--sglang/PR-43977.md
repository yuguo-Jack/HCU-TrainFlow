# [AMD][DI][CI] glm52 2p1d-ep16: capture CUDA graph on decode (eager decode is too slow)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43977) · state: closed · merged: True

## Original PR description

## What
In the two glm52 `2p1d-ep16` recipes (plain and `-mtp`), replace `--disable-cuda-graph` on decode with `--cuda-graph-bs-decode 1..64` (`1..128` for `-mtp`). The MORI decode settings are the same as in the dsv4pro `2p1d-ep16` recipes, which already capture CUDA graph with these ranges.

## Why
With CUDA graph off, decode runs eagerly and a single request takes hundreds of seconds. The test takes anywhere from 22 minutes to 1 h 47 min, and some nights it fails with a request `TimeoutError` (2026-10-11 `-mtp`, 2026-10-12 plain) while the other variant passes.

This changes what the test measures: throughput will be much higher than the eager baseline.

## Validation
On pit2 (4 nodes), main `6a7abcf`, same image as the nightly. Decode logs show `cuda graph: True`, no capture errors, no timeouts, 7 of 7 result files each time.
- plain: 2 runs, 28 and 29 min, GSM8K 0.945 and 0.950.
- `-mtp`: 2 runs, 21 and 21 min, GSM8K 0.945 and 0.945.

- michaelzhang-ai · COMMENTED · 2026-10-13T05:41:28Z · [source](https://github.com/sgl-project/sglang/pull/43977#pullrequestreview-5499261419)

LGTM. Both nightly failures (10-12 plain, 10-11 `-mtp`) are `TimeoutError` in `tokenizer_manager._stream_one_response` during the GSM8K gate, with eager decode requests taking 10-50 s, so the diagnosis matches.

The capture ranges match the dispatch buffers:
- plain: bs 1..64 with `MORI_MAX_DISPATCH_TOKENS_DECODE: 64`, and 1024 max running requests over DP16 is 64 per rank.
- `-mtp`: bs 1..128 x 4 draft tokens = 512, matching the existing 512/2048/1024.

Suggestion: copy the note from the dsv4pro `-mtp` recipe ("MTP decode capture drives the MoE dispatch to cuda_graph_bs * draft_tokens tokens/rank...") above `decode_extra_env`, so whoever changes the capture range or the buffers next can see they are linked.

No decode `--max-total-tokens` cap like the dsv4pro recipes have for the 4 GiB RDMA memory-region limit, but that's fine: the KV pool is still sized by `mem_fraction_static`, and graph memory comes out of the remainder.
