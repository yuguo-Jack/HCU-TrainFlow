# [Feat] observability: Support tracing only the first N decode steps per request

[Upstream PR](https://github.com/sgl-project/sglang/pull/47425) · state: open · merged: False

## Original PR description

## Motivation

At trace level 3, SGLang emits a `decode_loop` span for **every** decode step of every
request. For long generations (thousands of tokens) this produces one span per token per
request, which floods the OTLP pipeline: exporter queues grow without bound, batch exports
drop spans, and the tracing backend becomes unusable in production. Users therefore have to
choose between level 3 (full detail, unusable volume) and level 2 (no per-step detail at all).

This PR adds `SGLANG_TRACE_DECODE_MAX_STEPS` so operators can trace only the first N decode
steps per request — enough to diagnose scheduling/prefill-to-decode handoff issues while
keeping span volume bounded regardless of output length.

## Modifications

* `environ.py`: new `SGLANG_TRACE_DECODE_MAX_STEPS = EnvInt(-1)`.
* `observability/req_time_stats.py`: read the env once at import (hot path — `envs.X.get()`
  does `os.getenv` + parse on every call) and skip `decode_loop` span creation once
  `decode_ct` reaches the limit. `observe_per_stage_req_latency` is untouched, so **metrics
  are not affected**; only span volume is reduced. Default `-1` keeps the current behavior
  of tracing every step. The limit is per-request and not reset by retraction; prefill and
  (in PD disaggregation) prebuilt-decode do not consume the budget. Note the unit is a decode
  *step*, not an accepted token — under speculative decoding one step can emit several tokens.
* Docs: new row in `environment_variables.mdx`, plus a note in `production_request_trace.mdx`
  under trace level 3.

## Tests

Unit tests — `test/registered/unit/observability/test_req_time_stats.py`, new
`TestDecodeLoopTraceLimit` (7 cases):
* default (`-1`) still traces every step; `DECODE_LOOP` stays at level 3
* limit honoured for both `TraceReqContext` and `TraceReqContextAsync`, span timestamps and
  `decode_ct` attrs verified
* parametrized `-1 / 0 / 1 / 3 / 20` against 12 decode steps
* per-request budget: a 15-step and a 4-step request get 10 and 4 spans respectively
* retraction keeps the budget and leaves other slices (e.g. `decode_forward`) intact
* prefill / PD prebuilt-decode do not consume the budget
* metrics collection unaffected when the limit is 0 or 3

Integration tests — `test/registered/observability/test_tracing.py`, new
`test_trace_level_3_decode_loop_limit` on `TestTraceServer`: sends a batch of 2 requests with
`ignore_eos`, waits for `decode_loop` counts to stabilise, and asserts `> 10` spans per trace
by default. `TestTraceServerAsync` reuses the same case with
`SGLANG_TRACE_DECODE_MAX_STEPS=10` and asserts exactly 10 spans per trace, so the limit is
verified end-to-end through the async ZMQ exporter. `TestTraceServerMultiTokenizer(Async)`
disable this case (`= None`) since they only cover the router-pickling regression.
