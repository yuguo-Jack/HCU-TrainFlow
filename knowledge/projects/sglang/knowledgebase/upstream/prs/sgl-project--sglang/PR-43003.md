# [Bugfix] Do not finish on grammar termination when ignore_eos is set

[Upstream PR](https://github.com/sgl-project/sglang/pull/43003) · state: open · merged: False

## Original PR description

## What changes

Constrained requests sent with `ignore_eos=true` no longer stop when their grammar terminates. Before this change they finished at the grammar's stop token (usually an EOS token) instead of running to `max_new_tokens`; after it, decoding continues unconstrained until `max_new_tokens` or a stop string, the same as for EOS and stop tokens. Requests without `ignore_eos` are unchanged.

## Problem

`Req.update_finish_state` finishes a request as soon as its grammar is terminated, without checking `ignore_eos`:

```python
if self.grammar is not None and self.grammar.is_terminated():
    self.finished_reason = FINISH_MATCHED_TOKEN(matched=self.output_ids[-1])
    return
```

The token-based check just above it (`_check_token_based_finish`) returns early under `ignore_eos`, but this grammar check does not. A grammar terminates when it accepts its stop token, which is usually an EOS token. So any constrained request with `ignore_eos=true` stops at that token instead of running to `max_new_tokens`.

The GLM47 EBNF from #38890 covers the whole assistant turn, so it terminates when the model ends its turn. With `--tool-call-parser glm47`, requests sent with `ignore_eos=true` and a fixed `max_tokens` stopped early with:

```
finish_reason {'type': 'stop', 'matched': 154827}   # 154827 = <|user|>, an eos_token_id
```

#39273 attaches that EBNF only to tool-bearing requests, which makes this less frequent. Tool-bearing requests, and any other grammar whose terminal token is an EOS, still stop early under `ignore_eos`.

## Fix

- `Req.update_finish_state`: under `ignore_eos`, grammar termination does not finish the request. This is the same rule that applies to EOS and stop tokens. After the grammar terminates, decoding is unconstrained until `max_new_tokens` or a stop string. `SamplingBatchInfo.update_regex_vocab_mask` already applies no mask to terminated grammars, and the spec-decode tree mask (`traverse_tree`) does not fill or descend below a terminated node.
- `SchedulerBatchResultProcessor._accept_grammar_tokens`: under `ignore_eos`, keep the whole accepted run and do not call `accept_token` on a terminated grammar. In the past, the run was cut after the terminating token. That was safe only because the request then finished. A request that continues must commit its full verified spec run.
- `GuidanceGrammar` (llguidance): store termination in its own flag. The scheduler writes `grammar.finished = req.finished()` after each step. llguidance used that same attribute as its termination state, so the scheduler cleared it on a request that keeps running. The matcher then masked every later step to EOS only.
- `GuidanceGrammar` also terminates on an EOS that the matcher consumes. For a grammar that can still extend (for example `a+`), the matcher is not stopped before EOS, so it consumes the EOS and stops. In the past the grammar did not terminate on this EOS, and the next mask permitted only EOS again. `rollback` now subtracts one token only for an EOS that the matcher did not consume (the matcher had already stopped).
- `OutlinesGrammar`: implement `is_terminated`. The grammar terminates when the guide accepts EOS and moves to its final state `-1`. An accepting state does not terminate the grammar, because the regex can still continue. In the past `is_terminated` was always false, so under `ignore_eos` the guide masked every step after EOS to EOS only.
- Remove the `serving_chat.py` comment that names this behavior as the reason for the tool-bearing restriction.

Without `ignore_eos`, finish behavior does not change: the new llguidance and outlines terminations happen on an EOS token, which already finishes the request.

## Tests

- `test/registered/unit/managers/test_grammar_stop_speculative.py`: under `ignore_eos` a terminated grammar does not finish the request, which finishes with `FINISH_LENGTH` at `max_new_tokens`. A control case checks that without `ignore_eos` it still finishes with `FINISH_MATCHED_TOKEN` (unchanged behavior).
- `test/registered/unit/managers/test_batch_result_processor_spec_grammar.py`: under `ignore_eos`, `_resolve_spec_v2_tokens` commits the full run after the grammar terminates and does not feed later tokens to the grammar.
- `test/registered/unit/constrained/test_llguidance_batched_mask.py`: an llguidance grammar stays terminated after the scheduler writes `finished = False`. For `ab` (matcher stops before EOS) and `ab+` (matcher consumes EOS), the first EOS terminates the grammar, the next mask is unconstrained, and `rollback` restores the mask from before the EOS. Multi-token rollbacks across the EOS (`rollback(2)` and `rollback(3)` for `ab`, `rollback(2)` for `ab+`) restore the matching earlier state, and the grammar then accepts the rest of the string again.
- `test/registered/unit/constrained/test_outlines_termination.py`: for outlines `ab` and `a+`, the accepting state is not terminated, EOS terminates the grammar, the next mask is unconstrained, and later tokens do not change this. An invalid non-EOS token that also moves the guide to state `-1` does not terminate it; the mask stays EOS-only.
- `test/registered/unit/spec/test_spec_utils_traverse_tree.py`: `traverse_tree` with a real llguidance grammar (`ab+` and `ab`). An EOS inside the tree leaves its row and its descendants unconstrained, and its rollback restores the root state for the sibling branch. In the next decode iteration, with EOS committed, the tree root is terminated: every row is unconstrained and the grammar state does not change.

The regression tests fail without the source changes; the `FINISH_MATCHED_TOKEN` control passes either way. Run with:

```
pytest test/registered/unit/managers/test_grammar_stop_speculative.py \

       test/registered/unit/managers/test_finish_length_speculative.py \
       test/registered/unit/managers/test_stop_str_speculative.py
```

Thanks for this fix. We hit the same truncation independently while benchmarking GLM-5.2-MXFP4 with fixed-length (`ignore_eos: true`) requests, and measured it on GPU before finding this PR. Sharing the results as supporting data: the tool-bearing case is still reproducible on a nightly that already contains #39273, which is exactly what the `update_finish_state` change here addresses.

### Measured on GPU (4x MI355X, TP4/EP4, GLM-5.2-MXFP4, no speculative decoding)

Request: `"messages": [{"role":"user","content":"Say hi."}]`, `max_tokens: 2048`, 4 concurrent requests per case.
Server flags: `--tp 4 --ep-size 4 --kv-cache-dtype fp8_e4m3 --reasoning-parser glm45` (+/- `--tool-call-parser glm47`).

| Case | `lmsysorg/sglang-rocm:v0.5.20-rocm720-mi35x-20260930` (0.5.20.dev20260930+gd26ec4690d) | `lmsysorg/sglang-rocm:v0.5.21-rocm720-mi35x-20261008` (0.5.21.dev20261008+g11b1fb21de, contains f17f7705a5) |
|---|---|---|
| glm47 parser, no tools, `ignore_eos: true` | 117 / 214 / 106 / 149 tokens, `stop` | 2048 x4, `length` |
| no tool-call parser, no tools, `ignore_eos: true` | 2048 x4, `length` | 2048 x4, `length` |
| glm47 parser, one non-strict tool, `ignore_eos: true` | 71 / 42 / 39 / 41 tokens, `stop` | 62 / 47 / 52 / 48 tokens, `stop` |
| no tool-call parser, one non-strict tool, `ignore_eos: true` | 2048 x4, `length` | 2048 x4, `length` |
| glm47 parser, no tools, no `ignore_eos` (baseline) | 134-303 tokens, `stop` on EOS (154827) | 126-331 tokens, `stop` on EOS (154827) |

The non-strict tool used in the tool-bearing cases:

```json
"tools": [{"type": "function", "function": {"name": "get_time", "description": "Get the current time", "parameters": {"type": "object", "properties": {}}}}]
```

In every early-finished request `matched_stop` is an ordinary token id (the last output token), not EOS, which matches the `grammar.is_terminated()` -> `FINISH_MATCHED_TOKEN(matched=self.output_ids[-1])` branch. In the tool-bearing case the visible `content` also ends with a literal `<|user|>`.

So #39273 fixes the tool-less case (the 20261008 nightly no longer truncates it), but a request that carries a non-strict tool and sets `ignore_eos: true` is still ended at the grammar's terminal state. Note that the v0.5.20 release line does not contain #39273, so tool-less requests are truncated there too.

@BBuf, could you please take a look at this PR when you have a moment? It fixes a silent output-length truncation for fixed-length benchmarks with `--tool-call-parser glm47`. Thank you!
