# [Fix] rust-server: Park the idle scheduler on its request ring only with --sleep-on-idle

[Upstream PR](https://github.com/sgl-project/sglang/pull/47963) · state: open · merged: False

## Original PR description

## Motivation

With `SGLANG_RUST_SERVER=1`, the scheduler rank that hosts the Rust listener always installs `RustServerIdleSleeper`, so between requests its idle loop parks for up to 1 s on the in-process request ring. The Python server parks only with `--sleep-on-idle`; without the flag its idle loop polls its zmq sockets without blocking. The park costs the next request: the ring wakes the parked thread the instant a request is pushed, but that thread then starts the request's first step on a core the OS had put to sleep, so at low load the time from scheduler entry to the first token is longer with the Rust server than with the Python one. Under attention DP the park also holds busy peers, since a request wakes only its own rank's ring while every step gathers all ranks (#46636 addresses that case alone, by installing no sleeper on attention-DP ranks).

## Modifications

- `RustServer.wait_request` parks on the request ring only when `--sleep-on-idle` is set. Without the flag it returns at once, so the idle loop drains the ring without blocking, as the Python loop polls its sockets without the flag.
- `RustServerIdleSleeper` stays installed with or without the flag, so a `RustServer` subclass that holds drained requests back (for example until another thread finishes preparing one) can still park the idle loop on those instead of spinning while holding the GIL. It empties the cache on `SGLANG_EMPTY_CACHE_INTERVAL` only with the flag, as the Python `IdleSleeper` is installed only with the flag.
- Cost: without `--sleep-on-idle`, the listener rank's scheduler thread uses a full core while idle, the same as the Python server. `--sleep-on-idle` restores the previous parking.
- New CPU test `test/registered/unit/managers/test_rust_server_idle_sleep.py` (`base-a-test-cpu`): without the flag the idle path still reaches a subclass's `wait_request` while it holds a request and does not park on the ring otherwise; with the flag it parks on the ring. It fails without the `wait_request` change.
  Its `get_rust_server_class` stub also answers `gather_frontend_cpu_share` and takes `launch`'s `frontend_cpu_share` keyword, which `maybe_init_rust_server` has called since #47599.

## Related

#46636 keeps idle attention-DP ranks from parking by installing no sleeper on them without the flag. This change covers that case too, for every rank, and keeps the sleeper installed; the two touch the same comment line in `maybe_init_rust_server` and `idle_sleeper.py`, so whichever lands second needs a one-line rebase there.
