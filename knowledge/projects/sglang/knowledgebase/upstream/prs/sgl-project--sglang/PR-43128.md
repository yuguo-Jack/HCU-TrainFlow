# [Perf] [AMD] kimi-k3: Add opt-in MXFP4 latent MoE projections

[Upstream PR](https://github.com/sgl-project/sglang/pull/43128) · state: open · merged: False

## Original PR description

## Motivation

- In Kimi-K3 prefill on MI355X, the replicated BF16 latent MoE projections (down `[3584, 7168]`, up `[7168, 3584]`) run on every rank. At large batches they are a large, compute-bound cost.
- gfx950 runs MXFP4 GEMMs (AITER `gemm_a4w4`) much faster than BF16. Keeping an MXFP4 copy of these two weights cuts that cost, at the price of extra memory and lossy quantization.
- So this is opt-in and only for large batches. The default serving path does not change.

## Modifications

- `sglang.kernels.ops.gemm.latent_mxfp4_aiter_hip`: a thin AITER adapter (`pack`, `run`) registered as `gemm.kimi_k3_latent_mxfp4` (HIP). It packs a BF16 weight to preshuffled MXFP4 with E8M0 scales, then runs per-1x32 activation quant plus `gemm_a4w4`.
- `kimi_k3_rocm_mxfp4.LatentMXFP4Projections` owns non-persistent packed buffers. They are built after weight loading and refilled in place on reload.
- `KimiK3MoE`: the fused and unfused paths use the MXFP4 down/up projections at or above the token threshold. Router and shared experts stay on their BF16 path; latent reduction, norm, and output combine are unchanged.
- Memory: the copies take about 2.34 GiB per GPU (92 latent MoE layers), which comes out of the KV cache budget. The docs say to recheck token capacity and `--mem-fraction-static`.
- Standalone on upstream `main` (`43728298fe`); no dependency on other PRs.

| Env var | Default | Effect |
|---|---|---|
| `SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4` | `false` | Keep MXFP4 copies of the latent down/up projections and use them for large batches (lossy) |
| `SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4_MIN_TOKENS` | `2048` | Smallest batch (tokens) that uses the MXFP4 copies; must be positive |

| Condition | Latent projections |
|---|---|
| Flag on, gfx950, `SGLANG_USE_AITER=1`, BF16 `[3584, 7168]` / `[7168, 3584]` weights, no MoE a2a, batch >= `MIN_TOKENS` | MXFP4 `gemm_a4w4` |
| Batch < `MIN_TOKENS` | BF16, as before |
| `SGLANG_USE_AITER=0`, non-gfx950, or AITER missing | BF16; one warning |
| Quantized latent projections (GGUF / ExpertPack) or an MoE a2a backend | BF16; MXFP4 copies are not built |
| Unexpected weight shape or dtype | BF16; warning |

## Accuracy Tests

- Model: `Kimi-K3-Quark-MXFP4-AttnFP8`, 8x MI355X, TP8/DCP8 (the launch setup below).
- Eval: sgl-eval 0.1.3 (separate venv), full GSM8K (1,319), single shot, 1 repeat, 64 threads, temperature 1.0, top_p 0.95, reasoning_effort max, max_tokens 32768, seed 42.

| Metric | Flag off | Flag on, MIN_TOKENS 2048 |
|---|---:|---:|
| GSM8K correct | 1285/1319 | 1286/1319 |
| Score | 97.42% | 97.50% |
| Request errors | 0 | 0 |
| Truncated responses | 0 | 0 |
| Natural stops | 100% | 100% |

- No accuracy regression in this run. The one-question gap is noise (sampling and batching differ).
- Kernel test (`test/registered/kernels/ops/gemm/test_latent_mxfp4_aiter_hip.py`, gfx950): both shapes at 1, 8, 2047, 2048, 2049 tokens vs a BF16 reference (rel L2 < 0.20, cosine > 0.98), CUDA graph replay with changed inputs, and input rejection.
- Runtime test (`test/registered/unit/models/test_kimi_k3_rocm_mxfp4.py`, CPU): fused/unfused selection, routing and shared outputs, threshold boundary, reload lifecycle, AITER opt-out.
- At the current head: 9 passed (5 GPU on MI355X, 4 CPU); `test/registered/unit/kernels/` 247 passed.

## Speed Tests and Profiling

- Setup: 8x MI355X (gfx950), `Kimi-K3-Quark-MXFP4-AttnFP8`, TP8/DCP8, no MoE a2a, no speculative decoding. Both lanes use the same source, checkpoint, flags, and workload; only `SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4` differs.
- Cookbook MI355X Balanced AITER/FP8-KV recipe, with these deviations: local Quark checkpoint, radix cache off (prefix-free traffic), 16K chunked prefill, 64K context, graph and request caps of 64 (not graph cap 256), `--mem-fraction-static 0.90` (not 0.85), `--mamba-full-memory-ratio 3.53`. Both servers resolve a memory fraction of 0.765.
- Workload: random 8192 input / 1024 output, range ratio 1, seed 42, temperature 0, ignore EOS, 4 warmup requests, cache flush. 2 reps of `2 x concurrency` requests per concurrency; all 328 requests per lane succeeded with 1024 output tokens; achieved concurrency within 1% of target.
- Values: median over the 2 reps of each run's mean latency and aggregate output throughput (all 8 GPUs, not per GPU).

| Concurrency | TTFT off/on (ms) | Change | TPOT off/on (ms) | Change | Output tok/s off/on | Change |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 820.32 / 772.75 | -5.8% | 20.01 / 19.97 | -0.2% | 96.18 / 96.56 | +0.4% |
| 16 | 4552.57 / 4241.00 | -6.8% | 29.72 / 29.51 | -0.7% | 468.57 / 475.81 | +1.5% |
| 64 | 15005.46 / 13965.27 | -6.9% | 53.96 / 52.97 | -1.8% | 933.30 / 961.47 | +3.0% |

- Memory caveat: at `--mem-fraction-static 0.85`, turning the flag on dropped `max_total_num_tokens` from 1,815,792 to 144,624. At concurrency 16 only about 15 8K requests fit, and output throughput fell from 470.93 to 365.99 tok/s. At 0.90 for both lanes, capacity is 8,882,768 (off) and 7,211,600 (on), and both sustain the target concurrency. This is not a speedup under a tight, unchanged KV budget.
- Profiler: the enabled prefill trace shows 368 `f4gemm_bf16_per1x32Fp4_BpreShuffle_256x256` launches on rank 0 attributed to `latent_mxfp4_aiter_hip.run`; the baseline shows none.
- Environment: Torch `2.11.0+rocm7.2`, Transformers `5.19.0`, FlyDSL `0.3.4`, AITER `2bb549102ba2d9e51da8ef21107361827075d8b6` with three local changes held fixed in both lanes (`pa_mqa_logits_fp4_prefill.py`, `csrc/cpp_itfs/torch_utils.py`, the gfx950 `mla_a8w8_qh64_qseqlen1_gqaratio64_nm.co` binary).

Launch (run with the flag at `0` and at `1`):

```bash
SGLANG_USE_AITER=1 SGLANG_AITER_K3_OPT=1 AITER_FLYDSL_FORCE=1 AITER_SITUV2_A8W4=1 \
SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4=0 \
python -m sglang.launch_server \
  --model-path /data/models/Kimi-K3-Quark-MXFP4-AttnFP8 --trust-remote-code \
  --tp-size 8 --dcp-size 8 --dcp-comm-backend a2a \
  --prefill-attention-backend aiter --decode-attention-backend aiter \
  --kv-cache-dtype fp8_e4m3 --dtype bfloat16 --mem-fraction-static 0.90 \
  --cuda-graph-max-bs-decode 64 --reasoning-parser kimi_k3 --tool-call-parser kimi_k3 \
  --disable-radix-cache --chunked-prefill-size 16384 --context-length 65536 \
  --max-running-requests 64 --mamba-full-memory-ratio 3.53
```

