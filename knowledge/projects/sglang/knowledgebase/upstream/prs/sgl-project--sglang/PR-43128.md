> Optional, not part of the AgentX chain. Based on #43129. Review `a2d546f85d` and `ff69d017b2` (189 lines). Compare: https://github.com/yuychang/sglang/compare/up/b5-fp8-moe-front-tail...up/b4-kda-group64-latent-mxfp4


## AITER prerequisites

None beyond AITER main. The latent down and up projections call `aiter.gemm_a4w4`. The routed-expert MXFP4 drafts ([ROCm/aiter#6264](https://github.com/ROCm/aiter/pull/6264) — non-256-aligned inter_dim, [ROCm/aiter#6263](https://github.com/ROCm/aiter/pull/6263) — fused a8w4 sort and MXFP8 quant, [ROCm/aiter#6484](https://github.com/ROCm/aiter/pull/6484) — caller-supplied BM=16 sort, [ROCm/aiter#6485](https://github.com/ROCm/aiter/pull/6485) — sort output written into the caller buffer) are not this path.

## Motivation

For large batches the Kimi-K3 latent MoE projections (7168x3584 down, 3584x7168 up) are compute-bound BF16 GEMMs. AITER's preshuffled MXFP4 GEMM is faster there on gfx950.

## Modifications

**`a2d546f85d` add a ROCm MXFP4 GEMM adapter for the Kimi-K3 latent projections**
- Add an adapter for AITER's preshuffled MXFP4 GEMM for the Kimi-K3 latent down and up projections.
- Register SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4 and its token floor, off by default.
- Register the adapter in the gemm kernel inventory and add numerical and graph-replay tests.

**`ff69d017b2` run the ROCm latent MoE projections in MXFP4 for large batches**
- Pack MXFP4 copies of the latent down and up projections after load when SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4 is set.
- Use them from SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4_MIN_TOKENS tokens per batch; smaller batches keep the BF16 GEMMs.
- Let the Quark partial front carry the MXFP4 latent path as well as the FP8 pre-route.
- Document both switches.

Switch: `SGLANG_OPT_HIP_K3_MOE_LATENT_MXFP4`. Everything is ROCm only; CUDA and other checkpoints keep the existing path.
