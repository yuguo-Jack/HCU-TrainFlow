# [Perf] mooncake: Cut the host time of direct linker layer-wise loads

[Upstream PR](https://github.com/sgl-project/sglang/pull/46168) · state: open · merged: False

## Original PR description

## Motivation

Layer-wise prefix restoration through the Mooncake direct linker spends host time opening one get session per pool and building range metadata row by row.

## Modifications

- Combine every pool's keys into one `batch_get_session_start` call per load. No thread pool or futures are needed.
- Start that batch before waiting for the GPU slot fence. Location reads and range transfers still happen after the fence.
- End the session for every submitted key in `finally`, including when only some keys started successfully. Mooncake session-end ignores absent keys.
- Build layer pointers with NumPy and share read-only size/offset lists across rows.

## Validation

- Retain the existing assembler model tests and one compact layout case covering packed/unpacked ranges, multi-buffer mappings, repeated/out-of-order rows, empty inputs, and list/NumPy inputs.
- Two session tests check a single cross-pool batch before the fence, ordered multi-request ranges after it, and cleanup after per-key partial failure.
- Changed-file pre-commit checks passed. Five focused tests passed with the actual implementation classes/methods loaded in isolation; the local environment lacks the dependencies to import the complete SGLang package. Current-head registered pool assembler/session tests and unified linker tests subsequently passed ([pool/session run](https://github.com/sgl-project/sglang/actions/runs/40069653156), [linker run](https://github.com/sgl-project/sglang/actions/runs/40069662318)).
- On current head `baf3d6bc`, a real CUDA/Mooncake check passed on 20 synthetic production `DevicePoolEntry` layouts with strided buffers, sparse layers and repeated/reordered rows. The full-buffer oracle checked 4,320 bytes (1,440 unique restored bytes plus 2,880 untouched sentinel bytes) and detected deliberate one-byte corruption. Missing-key partial starts and injected short transfer results were rejected; cleanup covered all submitted keys, with post-end access rejection checked on a sampled valid key. This is synthetic range/session correctness evidence, not full-model output parity or performance.

- The current-head DSv4.1 Direct Linker restore test passed ([run](https://github.com/sgl-project/sglang/actions/runs/40129171620)): six executed cases across encoder replay and paged SWA, each with confirmed positive external load-back tokens and mean KL below 0.03. Four inherited GSM8K/MMLU cases are explicitly skipped by this restore-focused test. This does not establish broad model accuracy or benchmark-configuration parity.

## Current-head performance validation

A matched ABBA comparison of baseline `27ac614f` and current head `baf3d6bc` measured actual external-prefix restoration with the shared `benchmark/engine_steps/bench_engine_steps.py` from #46006.

| Arm | ms/step |
|---|---:|
| Baseline A0 | 475.028 |
| Candidate B1 | 442.530 |
| Candidate B2 | 438.533 |
| Baseline A3 | 484.743 |

Order-paired throughput gains are **7.34% and 10.54%**, with **8.93%** from the ratio of mean step times. Baseline variation is 2.05%, candidate variation 0.91%. These are fixed-batch engine-step results on requests that restore external prefixes, not application-level throughput or device-prefix-hit gains.

Configuration: two GPUs, TP2/EP2/attention-DP2, replica DP1, 131072-token context, 4096-token suffix, 32768 new tokens per rank per step, 1024 replay rows (33792 actual rows), 1024 measured requests per rank, five warmup steps and eight in-flight steps. MegaMoE, DSPARK block5, simulated acceptance3.51, both bounded replay paths, Rust radix tree and `SGLANG_DP_USE_GATHERV=0`; fresh external store per arm. All 2048 measured requests per arm were retained. Original cache-tier/step guards passed and the frozen scorer exactly reproduced steps, elapsed time, token counts and every group interval from raw completions. Workload, serving configuration, dependencies and host-table placement matched across arms.

Harness provenance: the run froze the explicit-L3 integration revision `40a66d03095d0dcc1e8c59541bab2623902eaeb0`, file SHA256 `90613800ea8cb168a3acd734d59bfbc09607b335398cf3b508f11c5b139c025b`. Comparison against public #46006 head `543a2804` confirms identical prefill scoring and unchanged explicit-L3 input generation; this run is not relabeled as a `543a2804` execution. The earlier threaded-revision measurements are superseded and are not pooled with this comparison.
