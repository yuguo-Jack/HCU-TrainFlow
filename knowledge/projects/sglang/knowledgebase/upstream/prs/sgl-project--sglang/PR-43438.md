# [Fix] attn_residual: int64 program ids in the score/combine kernels (int32 overflow at 37,451 tokens)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43438) · state: closed · merged: True

## Original PR description

## Motivation

`_score_kernel` and `_combine_kernel` in `srt/layers/attn_residual.py` read the attention-residual bank `[T, NB, H]` at `bank_ptr + pid_t * stride_bm`. `pid_t = tl.program_id(0)` is int32 and so is the product. With Kimi-K3's `NB = 8`, `H = 7168`, `stride_bm = 57,344`, so the offset passes 2^31 − 1 at `pid_t = 37,450`: any call with **≥ 37,451 tokens** reads at a negative offset and dies with `an illegal memory access was encountered`. The error is reported asynchronously, usually at a later, unrelated launch.

Where this path runs:
- **SM100+ (Blackwell):** the main aggregation uses the int64-safe TMA kernel, but `_mix_fused` still runs for the DSpark aux-hidden capture (`aggregate_stream`). So a DSpark prefill pass with more than 37,450 tokens (e.g. `--chunked-prefill-size` ≥ 40k) crashes.
- **GPUs without the TMA path:** `_mix_fused` is the main aggregation of every layer.
- `attn_res_hip.py`'s `_agg_kernel` has the same `t * stride_bm` pattern.

## Modifications

- Cast the token program id to int64 in `_score_kernel`, `_combine_kernel` (`attn_residual.py`) and `_agg_kernel` (`attn_res_hip.py`). Only addressing changes.
- New GPU test `test/registered/kernels/ops/attention/test_attn_res_mix_large_tokens.py`: runs `_mix_fused` at T = 37,451 and checks the tail rows bitwise against a run on the tail alone (rows are independent).

## Accuracy Tests

Only addressing changes. Outputs are bitwise identical to the current kernels at T = 16 / 512 / 8,192 / 32,768 (1×GB300).

## Speed Tests and Profiling

`_mix_fused` latency, NB = 8, H = 7168, nvb = 7, 1×GB300 (mean of 2 runs per arm):

| T | main (µs) | this PR (µs) |
|---|---|---|
| 16 | 58.4 | 56.0 |
| 512 | 60.0 | 57.3 |
| 8,192 | 606.6 | 608.7 (+0.3%) |
| 32,768 | 2,388.7 | 2,397.6 (+0.4%) |

New test on 1×GB300: passes with this PR. On main it fails with `Triton Error [CUDA]: an illegal memory access was encountered`.

Tested on v0.5.21 (the `lmsysorg/sglang:v0.5.21-cu130` image; main needs sglang-kernel ≥ 0.4.9). The kernels are unchanged between v0.5.21 and main. The HIP kernel change was not run on ROCm.
