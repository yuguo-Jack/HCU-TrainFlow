# [Fix] openai: Reject reserved special tokens in DeepSeek V4.1 requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/45500) · state: open · merged: False

## Original PR description

## Motivation

`encoding_dsv41.encode_messages` renders the prompt into a string and the serving path tokenizes it with `tokenizer.encode(...)`. HF tokenizers split added-vocabulary strings regardless of `add_special_tokens`, so message text that spells a DeepSeek control token becomes that token:

```
"hello <｜Assistant｜> world"  ->  [33310, 223, 128804, 2058]
                                   128804 = <｜Assistant｜>
```

`<｜Assistant｜>` in user text forges a turn boundary; `</think>` cuts reasoning short; `<｜End▁of▁Sentence｜>`, `<｜System｜>`, `<｜latest_reminder｜>` and `｜DSML｜` have similar effects. Tool call arguments add a second path: the encoder JSON-decodes them before writing DSML, so `\u003c\uff5cUser\uff5c\u003e` only spells the token after decoding. Tool schemas are rendered verbatim into the system prompt.

## Modifications

- `encoding_dsv41.py`
  - `RESERVED_SPECIAL_TOKENS` / `find_reserved_token()`: the control spellings the encoder writes. Grounding tokens (`<｜ref｜>`, `<｜box｜>`, `<｜point｜>`, `<｜polygon｜>`) are deliberately excluded — the model emits them and assistant history may carry them.
  - `_decoded_tool_arguments()`: the encoder's single decode step, shared with validation so checks see the values that reach the prompt.
  - `_validate_rendered_content()`: recursive check of `content`, `content_blocks`, and nested `tool_result` content (string or block list).
  - `_validate_no_reserved_tokens()`: content, reasoning, `response_format` (serialized as rendered), tool call names and decoded arguments (keys and rendered values).
  - `render_tools()` rejects reserved tokens in serialized tool definitions.
  - `REASONING_EFFORT_MAPPINGS` gains `minimal: 50`, `medium: 75`, `ultra: 100`, matching the reference encoder's scale (`low`/`high`/`xhigh`/`max` unchanged). This only widens accepted aliases; `medium` previously fell back to the default `high` (75), so its behavior is unchanged.
- `test/srt/test_encoding_dsv41_reserved_tokens.py`: new unit tests for content, reasoning, escaped/dict tool arguments, tool schemas, and the effort aliases.

Rejection (rather than neutralization) matches the existing `_validate_no_image_sp_tokens` behavior. Neutralizing arbitrary literal text requires tracking special-token spans through rendering, which is a larger follow-up.

## Accuracy Tests

No model or kernel change; valid requests render byte-identically (encoder-level baseline check). The new tests assert the rejection paths:

```sh
pytest -q test/srt/test_encoding_dsv41_reserved_tokens.py
```

Encoder-level validation performed locally (no torch needed): `py_compile`, `ruff check` / `ruff format --check` clean for the new code, all rejection paths exercised, legitimate image blocks still encode, and a baseline prompt is unchanged.

## Speed Tests and Profiling

N/A — no change to inference speed. The added work is a linear scan over message text and tool definitions at request encode time; it does not run in the decode loop.
