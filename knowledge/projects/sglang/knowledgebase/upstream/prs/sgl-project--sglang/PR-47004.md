# [Doc] [XPU] qwen3: Add the intel_xpu attention backend and XPU graphs to the BMG recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/47004) · state: open · merged: False

## Original PR description

## Motivation

The Qwen3 cookbook's BMG (Intel Arc Pro B-Series) command is `--device xpu --tp 4` and nothing else. That runs the default attention backend with no XPU graphs, so decode is launch-bound: Qwen3-30B-A3B decodes at ~54 ms per token at c=1 on 4x Arc Pro B70.

The XPU platform docs already describe the faster configuration: the `intel_xpu` attention backend plus decode and prefill XPU graphs. The cookbook just never used it. With it, decode is 1.9x faster on Qwen3-32B and 7.7x faster on Qwen3-30B-A3B, with the same accuracy.

## Modifications

- `docs/src/snippets/autoregressive/qwen3-deployment.jsx`: the BMG command adds `--attention-backend intel_xpu --page-size 64 --cuda-graph-backend-decode full --cuda-graph-backend-prefill breakable`. Only the `arc_b` output changes. BMG's model and quantization choices stay as they are: Qwen3-32B and Qwen3-30B-A3B, bf16, TP4.
- `docs/cookbook/autoregressive/Qwen/Qwen3.mdx`: a Configuration Tips bullet for BMG. The graph flags need an image built from the current XPU Dockerfile. On the released `lmsysorg/sglang:v0.5.22-xpu` they produce corrupted output (see below), so users of that image should leave the two graph flags out.

## Accuracy Tests

GSM8K: sgl-eval, full 1319 questions, temperature 0.7, top-p 0.8, thinking off, max 2048 tokens, seed 0. Same image as the speed tests.

| model | old command | new command |
|---|---|---|
| Qwen3-32B | 95.53% | 94.92% |
| Qwen3-30B-A3B | 94.77% | 95.07% |

The differences are within sampling noise. A second run of the new command in an image with compute-runtime 26.31 gave 95.00% and 95.07%.

## Speed Tests and Profiling

**Image:** built from main's `docker/xpu.Dockerfile`, unmodified.
- oneAPI 2026.1.3, compute-runtime 26.27, torch 2.14.0+xpu.
- sglang-kernel-xpu 0.5.0, sglang `6a473b2ac7`.

**How it was run:** each server ran in its own container, with the `docker run` flags from the XPU install docs. Hardware: 4x Arc Pro B70, TP4. Workload: `bench_serving` random 512 in / 256 out; c=1 runs 8 prompts, c>=4 runs 4 x c prompts, after a warmup. Times are medians.

| model | command | c=1 TPOT | c=4 TPOT | c=16 TPOT | c=32 TPOT | c=16 tok/s | c=16 TTFT |
|---|---|---|---|---|---|---|---|
| Qwen3-32B | old | 61.70 ms | 65.02 | 71.53 | - | 207 | 1611 ms |
| Qwen3-32B | **new** | **31.73** | 32.44 | 33.89 | 38.61 | **406** | 982 |
| Qwen3-30B-A3B | old | 53.58 | 56.12 | 56.38 | - | 266 | 589 |
| Qwen3-30B-A3B | **new** | **6.99** | 11.12 | 20.60 | 26.32 | **724** | 276 |

- At c=32 the new command serves 716 tok/s on Qwen3-32B and 1158 tok/s on Qwen3-30B-A3B.
- At c=1, Qwen3-32B with the new command is at the weight-bandwidth limit: its four GEMMs per layer stream at 550-590 GB/s of the B70's ~608 GB/s.
- Startup is 83-88 s against 68-78 s with the old command. The difference is graph capture.

## The released v0.5.22-xpu image

In `lmsysorg/sglang:v0.5.22-xpu`, XPU graphs capture without error, but the model's output is garbage. Qwen3-30B-A3B answers "What is the capital of France?" with `The!!!!!!!!...` or `Question moi moi moi...`. Isolation runs in that image, all on Qwen3-30B-A3B at TP4:

| flags | output |
|---|---|
| `--device xpu --tp 4` | correct |
| + `--attention-backend intel_xpu --page-size 64` | correct |
| + `--cuda-graph-backend-decode full` (default attention) | corrupted |
| + intel_xpu + decode graph | corrupted |
| + intel_xpu + prefill graph (`breakable`) | corrupted |
| new command, main's sglang code mounted into the image | corrupted |
| same, plus sglang-kernel-xpu 0.5.0 mounted | corrupted |

So the corruption is not in sglang's code or in the kernel wheel; it comes from the image's runtime stack. The v0.5.22 image is built on the oneAPI 2026.1.2 base, against 2026.1.3 today (upgraded in #43989). The compute-runtime is the same in both (26.27).

The new command gives correct output in images built from the current Dockerfile, with compute-runtime 26.27 and with 26.31. Hence the tip in `Qwen3.mdx`. Once an XPU release image includes #43989, the tip can be dropped, and the `docker pull` tag in the XPU install docs can be bumped.
