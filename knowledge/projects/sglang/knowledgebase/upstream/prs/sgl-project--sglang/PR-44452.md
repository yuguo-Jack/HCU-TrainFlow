# fix: AudioFlamingo3 fallback via Transformers backend + generic ASR adapter default

[Upstream PR](https://github.com/sgl-project/sglang/pull/44452) · state: open · merged: False

## Original PR description

## Summary

AudioFlamingo3 has no native sglang model and no dedicated transcription adapter, so it exercises two generic fallback paths (the Transformers-backend multimodal fallback and the default transcription adapter) that both had latent bugs. Together they produced WER=100% (every sample decoded to an empty/degenerate string) on `/v1/audio/transcriptions`.

Three separate, compounding bugs, all on code paths shared by any model without a dedicated implementation:

1. **`base_processor.py`** didn't route `AudioFlamingo3Processor` through the singular `audio=` kwarg branch (other `*Processor`s with this calling convention are already listed there), so it fell into the plural `audios=` branch instead, which that processor doesn't accept the same way. Separately, `AudioFlamingo3ProcessorKwargs` defaults `audio_kwargs["padding"]` to `"max_length"` because the audio tower has a fixed-size learned positional embedding — but the top-level `padding=True` passed for text batching is un-namespaced, so `ProcessorMixin` broadcasts it into any modality kwargs that don't already set it explicitly, silently downgrading audio to dynamic pad-to-batch-longest. At `batch_size=1` that's a no-op (producing audio features shorter than the positional embedding expects → crash), and at `batch_size>1` it produces variable-length features that can't be concatenated across the batch.

2. **`transformers.py`**'s `MultiModalMixin._collect_mm_kwargs()` (the "run the whole HF model in one shot" fallback path) only device-cast multimodal tensors, never dtype-cast them — HF feature extractors return float32 regardless of the model's runtime dtype, so passing that straight into `self.model(**kwargs)` crashes against fp16/bf16 encoder weights. `_encode_modality_items()` (the separate-encoder-call path) already handles this correctly via `_cast_mm_value()`; this fixes the matching gap in the other path. `_cast_mm_value()` itself also only moved tensors to the target device inside the floating-point branch, silently leaving non-floating tensors (e.g. feature-length tensors) on the wrong device.

3. **`resolve_adapter()`** defaulted any unmatched architecture to `WhisperAdapter`, which unconditionally injects a Whisper-specific `"language"` key into `sampling_params`. Any other model's `generate()` call rejects this outright. Added `GenericAdapter` — a true no-op-language default using the same shape `GraniteSpeechAdapter`/`Qwen2AudioAdapter` already use for their own decoder-only models — and pointed `_DEFAULT_ADAPTER_KEY` at it instead.

## Test plan

Validated end-to-end on Intel XPU (TP=2) via `lmms_eval`'s `openslr_librispeech_other` task against `nvidia/audio-flamingo-3-hf` served through `/v1/audio/transcriptions`:

- Before: WER = 100 (every sample predicted an empty/degenerate string)
- After: WER = 2.86 (paper reference ≈3.13), at the model's default `batch_size=4` — no batch-size workaround needed; sample-level transcriptions match closely (e.g. `"i am from the cutter lying off the coast"` transcribed verbatim)
- Confirmed the dtype-cast and padding fixes are both required: without the padding fix, `batch_size=1` produces empty output and `batch_size=4` crashes with a tensor-size mismatch in `torch.cat`; without the dtype-cast fix, the server crashes with a dtype-mismatch error in the audio tower's first conv layer.
