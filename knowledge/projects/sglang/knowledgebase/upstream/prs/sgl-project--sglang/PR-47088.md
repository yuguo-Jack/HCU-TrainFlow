# [Perf] [NPU] allocator: Avoid device synchronization in alloc_extend

[Upstream PR](https://github.com/sgl-project/sglang/pull/47088) · state: open · merged: False

## Original PR description

## Motivation

NPU `alloc_extend` reads the device-computed page count back to the host before it can check capacity and submit the allocation kernel. When `num_new_pages` is omitted, this puts a device synchronization on the scheduler's allocation path:

1. Compute `sum(ceil(seq_len / page_size) - ceil(prefix_len / page_size))` on NPU — six small kernels per allocation.
2. Call `.item()` on that device scalar — the host waits for the scalar and any preceding work on the stream.
3. Check capacity, select the allocation kernel, and update the free-page list using the returned count.

The scheduler already passes `seq_lens_cpu` and `prefix_lens_cpu`. The page count can be computed from these host mirrors without waiting for the device queue.

## Modifications

- Reuse `get_num_new_pages(seq_lens=seq_lens_cpu, page_size=self.page_size, prefix_lens=prefix_lens_cpu)` when the count is not supplied. Its `.item()` operates on a CPU tensor; it does not read back a device scalar.
- Use the resulting `num_new_pages` for capacity checks, the `<200`-page branch, and free-page accounting. Explicit counts follow the existing path.

The allocation optimization is confined to the NPU allocator. It adds no `.cpu()` call and keeps both allocation kernel implementations unchanged.

## Accuracy Tests

Qwen3-8B BF16, one Ascend910B4, TP1, Ascend attention; page size 128, chunked prefill 4096, overlap enabled, radix cache disabled. CANN 8.5.0 / torch 2.8.0+cpu / torch-npu 2.8.0.post2 / Python 3.11.14.

- **Allocator oracle:** 120 cases × before/after = **240 NPU executions passed**. The independent token-by-token physical-page oracle checks indices, uniqueness, bounds, remaining pages, and OOM returns. Cases cover partial prefixes, page boundaries, mixed lengths, zero new pages, exact/insufficient capacity, staged-page merging, 199/200-page branches, explicit counts, and fixed-seed random inputs.
- **Model regression:** 32 fixed prompts, 192 requests across both variants. Serial generation and two-request batches each match **32/32 token sequences and texts**. Replaying the same baseline continuation in both variants also matches the next token **32/32**. Across selected-token and 16 fixed-probe logprobs, including the replayed continuation: **26,962 values, maximum absolute difference 0** (preselected tolerance: `atol=1e-4`, `rtol=1e-5`).
- **Labeled sanity tasks:** **23/24 → 23/24** in each generation mode. The same literal mismatch occurs in both: `H₂O` versus reference `H2O`.

Inputs include 127/128/129, 4095/4096/4097, 8193, and 16000-token prompts plus existing ShareGPT prompts. Generation is greedy, capped at 64 new tokens, with thinking disabled. These are sampled output-regression checks, not a standardized accuracy score or full-vocabulary KL test. Decode ran with `npu graph=False`; CI-registered regression coverage remains pending.

## Speed Tests and Profiling

### Allocator microbenchmark

Real before/after `alloc_extend` calls, 4096 allocated tokens / 32 new pages, on one Ascend910B4. Each entry is the median of 80 samples across five blocks, alternating before/after order. The queued case submits 128 preallocated BF16 2048×2048 GEMMs on the same stream and checks that the queue is still pending before the call. Queue calibration: 10.395 ms device time. No model server or profiler runs during this test.

| Input | Device state | CPU return before → after (ms) | CPU time reduction | Synchronized completion before → after (ms) | Completion time reduction |
| --- | --- | ---: | ---: | ---: | ---: |
| One request | Idle | 1.377 → 0.622 | **54.8%** | 1.879 → 1.122 | 40.3% |
| Two requests, mixed prefixes | Idle | 1.323 → 0.626 | **52.7%** | 1.812 → 1.118 | 38.3% |
| One request | Queued GEMMs | 7.189 → 0.686 | **90.5%** | 7.735 → 7.111 | 8.1% |
| Two requests, mixed prefixes | Queued GEMMs | 7.081 → 0.651 | **90.8%** | 7.594 → 7.084 | 6.7% |

Time reduction = `(before − after) / before × 100%`, calculated from the unrounded medians. These are relative reductions in elapsed time, not percentage-point changes or measured throughput gains.

- **Idle device:** CPU return drops by **52.7–54.8%**; local synchronized completion drops by **38.3–40.3%**. The page-count kernels and scalar synchronization are removed even when there is no earlier computation to wait for.
- **Queued computation:** CPU return drops by **90.5–90.8%**, releasing the host about **6.4–6.5 ms earlier**. Synchronized completion drops by only **0.51–0.62 ms** in the pooled medians: the preceding GEMMs still execute. Completion timings are noisy; the mixed queued case's per-block elapsed-time changes range from −26.76% to +40.43%.
- **Explicit page-count control:** CPU times stay within approximately ±2% between variants, consistent with both bypassing page-count computation.

CPU return times only the allocator call. Synchronized completion runs from that same call start through device synchronization, including earlier GEMMs still pending. The CPU-return gain is primarily avoided queue-drain waiting.

### Level2 profile

Separate before/after captures, **63 allocations each**:

| Observation | Before | After |
| --- | ---: | ---: |
| Synchronous ACL memcpy nested in allocation-scope device-scalar reads | 63 | **0** |
| Synchronous ACL memcpy across the capture | 408 | 345 |
| Device compute kernel launches | 28,010 | 27,632 (**378 fewer**) |
| Allocation kernel launches | 63 | 63 |
| Allocation kernel cumulative device time | ~34.17 ms | ~34.17 ms |

Each allocation removes two adds, two floor divisions, one subtraction, and one reduction. The allocation kernel itself is unchanged; the gain comes from page-count arithmetic and host synchronization.

D2H attribution follows the device `.item()` into its nested synchronous ACL memcpy. The trace does not expose separate scalar-copy DMA events or their byte counts/device durations. The baseline's failed export was recovered offline with the same torch-npu parsers; both traces' compute events were checked against `kernel_details.csv` by task ID, stream, name, and duration. Memory-record warnings prevent a complete memory-lifecycle claim.

### Full prefill serving

Qwen3-8B BF16, same compute configuration, max running requests 64, static memory fraction 0.8. Fixed 16k input / 1 output token, 256 requests per run. Independent server starts in before → after → after → before order, two repetitions per rate per start: **16 runs / 4096 completed requests**, with profiling disabled. Reported changes average two startup pairs after averaging repetitions within each start.

| Request rate | Input throughput change | Mean TTFT change | P99 TTFT change |
| --- | ---: | ---: | ---: |
| 0.6 req/s | +0.0168% | −0.0544% | −0.0317% |
| Saturated (`inf`) | +0.0499% | −0.0425% | −0.0206% |

TTFT includes queueing; one output token cannot measure TPOT. The measured benefit is local allocation overhead and earlier host progress.
