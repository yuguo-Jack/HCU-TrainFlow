# [Feat] diffusion: let replicated ranks share the merge cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/45782) · state: open · merged: False

## Original PR description

## Motivation

The LoRA merge cache bails out on any multi-rank run:

```python
if dist.is_initialized() and dist.get_world_size() > 1:
    # Sharded weights would need per-rank stores; not worth it until a
    # multi-GPU consumer deployment exists.
    return None
```

The reason holds for a tensor- or FSDP-sharded replica: each rank holds a different slice, so one entry per module name would be wrong for all but one of them. It does not hold for sequence- and data-parallel replicas, whose ranks hold the same full weights — those ranks can share one entry, and the cache is what keeps 62 GiB of merged weights out of anonymous host memory per rank.

## Modifications

Decide on the sharding that actually changes the local weights — `tp_size > 1` or `use_fsdp_inference` — instead of on the world size. Every rank then merges through the same entry: each file is written via `tmp.<pid>` + rename, so concurrent writers produce the same bytes and one manifest wins.

Nothing changes for a single-rank run, and the sharded cases still fall back to per-rank in-place merges.

## Tests

`test_merge_cache_serves_replicated_replicas_only` — the cache is offered at `tp_size=1`/no FSDP and refused at `tp_size=2` and at `use_fsdp_inference=True`. `python/sglang/multimodal_gen/test/unit/test_lora_pipeline.py` passes (21 tests).

Measured on a 2-card H3 engine with a 780 MB adapter: the engine adopted the existing cache instead of merging (`LoRA merge cache found for transformer; adopting instead of merging`), load dropped from 230 s to 170 s, the layerwise pin budget recovered from 147 GiB to 398 GiB, and the engine's two ranks held 150 GiB Pss together instead of 254 GiB.
