# [Performance] Honor explicit workload caps when sizing hybrid cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/36041) · state: closed · merged: False

## Original PR description

## Summary

When both `--max-running-requests` and `--max-total-tokens` are set, size separate Mamba and KV pools against those limits instead of always using the generic memory ratio.

The ratio remains the fallback when the requested operating point does not fit or the layout is unsupported. Explicit Mamba sizing, speculative decoding, PP, and unified-memory behavior are unchanged.

## September 14 CPU-only update

Rebased onto `7465e42b7a`, including the current CI baseline. Moved CLI help changes to `arg_groups/fields/schedule.py` to follow the current argument layout. Preserved the upstream ReplaySSM fixed/per-slot scratch calculation; workload-cap rebalancing is bypassed for active ReplaySSM.

- Nine workload-cap tests, including a new ReplaySSM fixed-scratch regression, passed in a dependency-isolated CPU harness executing the checked-out methods with runtime-context boundaries replaced.
- 27 additional default/hybrid/all-SWA byte-estimator cases passed across token caps and page sizes using the checked-out estimator definitions.
- Ruff/isort and whitespace checks passed. Full-environment CPU suites, GPU allocation, GSM8K, and serving benchmarks remain pending on this head.

## Performance (historical)

### Earlier L20 revalidation

Qwen3.8-27B-FP8, TP2 on 2x NVIDIA L20, default Mamba state dtype, `--max-running-requests 32`, and `--max-total-tokens 65000`. The workload contains 64 requests with exactly 512 input and 128 output tokens at client concurrency 32. Each measured run flushes the cache and follows 32 warmup requests. Values are means of two runs; each pair agreed within 0.06% on output throughput.

| Metric | `main` | This PR | Change |
|---|---:|---:|---:|
| Mamba state slots | 128 | 160 | +32 slots |
| Effective server concurrency | 25 | 32 | +28.0% |
| Output throughput | 411.14 tok/s | 413.62 tok/s | +0.6% |
| Mean E2E latency | 8.494 s | 8.264 s | -2.7% |
| P90 E2E latency | 14.108 s | 8.173 s | **-42.1%** |
| P90 TTFT | 8.558 s | 3.645 s | **-57.4%** |
| Median E2E latency | 7.057 s | 8.164 s | +15.7% |

The median-latency tradeoff is expected: `main` serves the workload as 25+7 requests, while this PR admits all 32 together. Compute is already saturated, so aggregate throughput is nearly flat, but queued requests no longer form a slow second wave and tail latency improves substantially.

The infeasible 64-concurrency case was also checked. The requested state + KV pools required 24.99 GiB with 19.57 GiB available, so the new logic logged the mismatch and retained the ratio-sized 128-slot pool rather than over-allocating.

### Original L40S result

The original validation used Qwen3.8-27B, TP2 on 2x L40S, 64 requests, 512 input / 128 output tokens, with cache flushes between runs:

| Configuration | Effective concurrency | Output throughput |
|---|---:|---:|
| Original baseline | 23 | 323.8 tok/s |
| Manual `--max-mamba-cache-size 160` | 32 | 417.2 tok/s |
| This change | 32 | 413.2 tok/s |

Five-run mean was +27.6% versus that historical baseline, and automatic sizing was within 1% of manual sizing.
