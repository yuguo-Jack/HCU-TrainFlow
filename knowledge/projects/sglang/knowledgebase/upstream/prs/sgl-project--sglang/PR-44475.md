# [Fix] openai: Parse required tool calls when no tool-call parser is set

[Upstream PR](https://github.com/sgl-project/sglang/pull/44475) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44474.

With effective tools and no configured tool-call parser, `tool_choice="required"` and named tool choices already get the JSON fallback constraint, which constrains the intended output to `[{"name": ..., "parameters": ...}]`. But both Chat response paths were gated by `_tool_call_parsing_active`, which requires a configured parser, so a generated fallback call ending with `stop` came back as plain `content` with `finish_reason="stop"`. The docs say `required` forces at least one tool call, and the Responses implementation already has a JSON fallback for required and named choices that does not require a configured tool-call parser.

## Modifications

`python/sglang/srt/entrypoints/openai/serving_chat.py`:

- Add `_should_parse_tool_calls`, which is true when a configured parser is active (the existing helper) or when effective tools are present and the choice is `required` or a named tool.
- Use it for the two response-path gates: the streaming tool-call branch and the non-streaming tool-call parsing. Both then reach the existing JSON fallback in `_process_tool_calls` and `_process_tool_call_stream`; no new parsing code.
- Include constrained JSON parsing in the streaming logprob flush condition, so logprobs of deltas the fallback consumes are still sent.
- The logic of `_tool_call_parsing_active` is unchanged, preserving the reasoning-parser inputs and framing decisions. Its docstring now explicitly describes the configured parser.

`auto` and `none`, requests without effective tools, and configured parsers behave as before; public validation still rejects `required` and named choices without tools.

The existing JSON streaming fallback can still emit an empty argument string when the whole call arrives in a single terminal delta; the same behavior is reproducible at `f7ad4345` with `glm45` configured.

Tests in `test/registered/unit/entrypoints/openai/test_serving_chat.py` (six methods):

- `required` without a parser (two methods: non-streaming and streaming with two cumulative chunks): one `get_weather` call with `{"location": "Tokyo"}`, no content, `finish_reason == "tool_calls"`;
- a named tool choice without a parser, non-streaming;
- streaming logprobs over two cumulative chunks without a parser, for `required` and a named choice: the call is parsed and the two supplied token logprobs are each sent exactly once;
- a configured `hermes` parser with `auto` and native-format output, in both modes;
- plain-content controls for `auto` with tools, `none` with tools, and `required` with no effective tools (response path only), in both modes.

I ran the following locally on CPU with Python 3.12.15 and PyTorch 2.14.1+cpu:

- At `a0bc728f`, `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=python ~/venvs/sg/bin/python -m pytest -p no:cacheprovider test/registered/unit/entrypoints/openai/test_serving_chat.py -q`: 162 passed, 123 subtests passed.
- With these tests and the `f7ad4345` `serving_chat.py`: 5 failed, 159 passed, 121 subtests passed. The required non-streaming, required streaming, named non-streaming, and both logprob subtests fail at the tool-call assertion (`[] != ['get_weather']`); all controls pass.
