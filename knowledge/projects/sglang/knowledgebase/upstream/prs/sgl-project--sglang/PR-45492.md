# [Perf] pd: Send prefill KV chunks without a host sync on the scheduler thread

[Upstream PR](https://github.com/sgl-project/sglang/pull/45492) · state: closed · merged: True

## Original PR description

## Motivation

On a PD prefill worker under the overlap scheduler, every KV send to the decode computed its page indices with `kv_to_page_indices`, a `.cpu()` on the schedule stream. `_apply_war_barrier` fences that stream behind the in-flight forward, so the copy returns only when that forward's reads are done: the scheduler thread waits for the previous forward on every send (twice per request: the early cached-prefix send in `run_batch` and the final send in `process_batch_result`), and the next forward launches late. With attention DP the per-batch DP sync spreads each rank's stall to its peers. This is the prefill-side counterpart of #45328.

Measured on DeepSeek-V4.1-Flash, GB300, 10 x DEP2 prefill + 1 x DEP16 decode, Mooncake transfer, AgentX traffic at 6,400 conversations: sampling the prefill schedulers' main thread once per second over a 900 s window put 30% of its samples in that `.cpu()` and 26% launching forwards.

## Modifications

- `_send_kv_chunk` computes the page indices on the device as before, copies them into pinned host memory with `non_blocking=True`, records a CUDA event on the current (schedule) stream, and passes the host tensor plus the event to the sender. The sender needs only the length on the scheduler thread. Context-parallel transfers, which filter the indices on the host, keep the synchronous path; so do backends that do not declare `supports_host_tensor_indices`.
- `TransferKVChunk.indices_event`: the Mooncake transfer worker, which already waits on the early-send event before reading KV, waits on this event too and converts the host tensor to NumPy before any use.
- `MooncakeKVSender.send` and `MooncakeKVManager.add_transfer_request` take `indices_event`.

## Benchmarking

Same shape and client, 900 s windows, sglang main `472f0d540b` + #44623:

| | Total tok/s/GPU | p90 interactivity | p90 TTFT | Requests | Errors |
|---|---:|---:|---:|---:|---:|
| before | 521,838 | 120.90 | 36.0 s | 151,612 | 1 |
| after | 543,328 | 122.36 | 29.3 s | 157,027 | 0 |

The scheduler thread's share in the send path went from 30% to 0% and its forward-launch share from 26% to 52%; the prefill queue fell from 27 to 8 requests per rank, and the decode's slot count became the bound.

## Accuracy Tests

No numerics change: the same page indices reach the transfer, later. 70,910 warmup and 157,027 window requests completed with 0 errors through the asynchronous path. The last chunk's state payloads (SWA window, DSA state) still read the device synchronously; they are once per request and left for a follow-up.

- kpham-sgl · comment · 2026-10-22T03:09:48Z · [source](https://github.com/sgl-project/sglang/pull/45492#issuecomment-6331726556)

Known risk (from Claude), to handle in a follow-up: with `--enable-kv-cache-sharding` (`kv_shard_size > 1`) the asynchronous path is still taken, and `MooncakeKVSender.send` -> `_prepare_send_indices` -> `filter_kv_indices_for_shard_rank` reads the pinned host tensor on the scheduler thread before `indices_event` has been waited on, so the shard mask can be computed from a copy that has not landed yet. `test_disaggregation_kv_cache_sharding` passed on this PR (GSM8K 0.785), so it has not been observed, but the ordering is not guaranteed.

Options: fall back to the synchronous path when `kv_shard_size > 1`, or move the shard filter into the transfer worker after the event wait. A sender-level unit test with a mock event, same pattern as `test_worker_sends_indices_after_copy_completes`, would make it deterministic.
