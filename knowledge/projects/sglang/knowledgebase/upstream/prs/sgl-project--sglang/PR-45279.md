# [Fix] qwen3_coder: match <tool_call> as a token via xgrammar token_markers

[Upstream PR](https://github.com/sgl-project/sglang/pull/45279) · state: open · merged: False

## Original PR description

## motivation

fixes #45225. the qwen3_coder structural tag currently triggers on the text `<tool_call>\n<function=`, so a literal `<tool_call>` in prose or reasoning can start a constraint, and any other whitespace after the marker never does. xgrammar main (mlc-ai/xgrammar#940) added `token_markers=True`, which matches `<tool_call>` as its dedicated token for `qwen_3_coder`.

## modifications

- `BaseFormatDetector.use_structural_tag_token_markers()` hook, default `False`.
- `Qwen3CoderDetector` opts in.
- `get_structural_tag` passes `token_markers=True` only when the detector opts in and the installed `get_model_structural_tag` accepts the argument (signature check). with the pinned xgrammar 0.2.7 / 0.2.8 nothing changes; once the pin moves to a release with #940 the token path turns on.

## tests

`test/registered/unit/function_call/test_qwen3_coder_token_markers.py` (cpu, mocks xgrammar):
- new api: qwen3_coder gets `token_markers=True`
- old api: no `token_markers` kwarg (text trigger fallback)
- detectors without the opt in keep `False`
- no xgrammar: returns `None`
