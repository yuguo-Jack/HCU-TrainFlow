# [Fix] dspark: Stop compact verify from counting padding rows as accepted drafts

[Upstream PR](https://github.com/sgl-project/sglang/pull/47694) · state: open · merged: False

## Original PR description

## Motivation

In `python/sglang/srt/speculative/dspark_components/dspark_verify.py`, compact ragged verify (`SGLANG_RAGGED_VERIFY_MODE=compact`) runs the target model on only `verify_len` rows per request. The rest of the block is filled with padding: candidate id `0` and all-zero logits.

Every accept kernel (greedy, chain sampling, block verification, blockwise rejection) still scans the whole padded block and caps the accepted count afterwards. So `cap_trim_lens`, the count of drafts the target would have accepted past the cutoff, gets inflated in three ways:
- The in-graph epilogue (`DsparkVerifyEpilogue.__call__`) compared padding id `0` against the argmax of a zero row, which is also `0`, so the whole padding tail was counted.
- That same comparison missed real accepts of the first draft past the cutoff.
- Even with real drafts as candidates, a draft whose token id is `0`, or a sampled draft against a uniform padding row, matched rows the target never scored.

This corrupts `block_accept_lens` / `spec_num_block_accept_tokens` (API `meta_info`) and the block-accept estimate recorder. Generated output is unaffected, because `cap_trim_lens` never feeds `commit_lens`, `new_seq_lens` or the bonus token.

## Modifications

- `build_accept_outs` takes a new `scored_lens` argument: the number of target rows per request that carry real logits. Row `j` verifies draft `j + 1`, so `cap_trim_lens` is bounded by `scored_lens − correct_len` (at most 1 in compact mode). The bound sits where every accept path, graph and eager, meets.
- The compact epilogue passes `scored_lens=verify_lens`. It also fills candidates past the cutoff with the real drafts from `draft_tokens_buf`, so the first draft past the cutoff is checked against its real value, as the eager path already does.
- The eager path passes `scored_lens` only when the worker ran compact verify. Cap-accept mode, where the rows past the cutoff are real, keeps its full multi-token counts.
- `test/registered/unit/spec/test_dspark_accept_tail.py` gets a new `TestCompactAcceptTail` class:
  - explicit greedy cases (padding, a token-0 draft tail, early rejection, a genuine accept past the cutoff, cap-accept kept)
  - a captured CUDA graph replayed across 8 steps with changing drafts and cutoffs
  - a deterministic compact sampled-acceptance case
  - all checked against an independent oracle, including the block-accept buffer
- The file is now also registered for AMD CI.

## Accuracy Tests

- Generated tokens are unchanged by construction; the tests also check that `correct_len`, `bonus`, `commit_lens` and `out_tokens` are identical with and without the bound.
- The new tests fail on current `main` and pass with this change. They also fail on two deliberately broken fixes: one that bounds `AcceptOuts` but writes the unbounded value to the block-accept buffer, and one that wrongly bounds cap-accept mode.
- 44 tests pass across the DSpark unit suites. Tested on an **AMD MI355 (gfx950)** machine.
