# [Perf] moe: Always pass the global token count to the Mega MoE tile heuristic

[Upstream PR](https://github.com/sgl-project/sglang/pull/46093) · state: closed · merged: True

## Original PR description

## Motivation

DeepGEMM's Mega MoE picks its tile (`block_m`) from the calling rank's own token count. With DP attention and EP, an eager prefill forward can be very uneven across ranks. For example, one 128K request is chunked on one rank while the other ranks run idle forwards. The idle ranks then size their tiles for one token, small `block_m`, but they compute experts for the busy rank's tokens. The whole fused dispatch-GEMM-combine kernel runs at the pace of the badly tiled ranks.

DeepGEMM already accepts `global_num_tokens` for this, in both `get_block_m_for_mega_moe` and `fp8_fp4_mega_moe`. SGLang doesn't pass it.

## Modifications

- Eager Mega MoE forwards pass the DP-global token count, capped at `ep_size * num_max_tokens_per_rank`, to the kernel and to both shared-expert `block_m` queries: the one in `run_mega_routed_experts` and the one in `mega_moe_input_target`, which sizes the shared-expert scale factors when Mega-mHC writes the MegaMoE input under MegaGate. Both queries then match the kernel's tile.
- CUDA-graph capture is unaffected (the hint is skipped during capture, so decode graphs are unchanged), and so is prefill context parallelism.

## Accuracy and speed

DeepSeek-V4.1-Flash, DEP4, 128K prompts, on a CC 10.7 node. Arms ran ABBA in one job:
- Single-request TTFT drops noticeably, because the idle ranks no longer pick the smallest tile.
- Multi-request prefill improves slightly.
- GSM8K is unchanged.
