# [Feat] multimodal: Add configurable hash algorithm for CPU multimodal features

[Upstream PR](https://github.com/sgl-project/sglang/pull/46815) · state: open · merged: False

## Original PR description

## Motivation

Every multimodal item gets a hash before scheduling: `MultimodalDataItem.set_pad_value` calls `hash_feature` in `managers/mm_utils.py`, and the result becomes the item's prefix-cache identity and pad value. On the CPU path, this is a single-threaded SHA-256 over the whole processed feature: `pixel_values` for images, and every patch for videos. Its cost grows with the feature size. On an Apple arm64 machine with 12 CPUs, hashing one 36.8 MiB video feature took 15.4 ms and one 5.9 MiB image feature took 2.5 ms, for every request that carries them.

This PR adds an opt-in setting to hash these features with multi-threaded `blake3` instead.

## Changes

The new setting is opt-in. When it is unset, CPU features are still hashed with SHA-256 and every hash value is byte-identical to before.

- **Configurable CPU hasher**, `SGLANG_MM_HASH_ALGORITHM`. A new `_new_mm_hasher()` returns `hashlib.sha256()` by default, or `blake3(max_threads=blake3.AUTO)` when the variable is `blake3`; any other value raises a `ValueError` that names the variable. The CPU paths of `tensor_hash` (single tensor and list) and the `np.ndarray` branch of `hash_feature` use it.
- **ndarray buffers are hashed as a flat `uint8` view.** blake3 only accepts byte-format buffers. For SHA-256, the view hashes the same bytes as before, so the default hash does not change.
- **Unchanged:** the GPU path (`gpu_tensor_hash`) and `data_hash`.

`blake3` is imported only when it is selected, so `pyproject.toml` is unchanged; deployments that opt in must install it.

## Environment variables

| variable | default | meaning |
|---|---|---|
| `SGLANG_MM_HASH_ALGORITHM` | `sha256` | algorithm for hashing CPU multimodal features: `sha256` or `blake3` (multi-threaded, requires the `blake3` package). Changing it changes multimodal prefix-cache keys, so every instance that shares a cache or a router must use the same value |

`docs/docs/references/environment_variables.mdx` is updated.

## Benchmark

CPU microbenchmark of `hash_feature` on Apple arm64 (12 CPUs), best of 5×10 runs:

| feature | size | sha256 (ms) | blake3 (ms) | speedup |
|---|---|---|---|---|
| image f32 1x(1323,1176) | 5.9 MiB | 2.51 | 1.30 | 1.93x |
| image f32 4x(1323,1176) list | 23.7 MiB | 10.10 | 6.16 | 1.64x |
| video bf16 (16384,1176) | 36.8 MiB | 15.40 | 3.93 | 3.92x |

This measures only the hash step, not end-to-end serving, and blake3's gain depends on how many CPU cores are free.

## Tests

- `test/registered/unit/managers/test_mm_hashes.py`, new `TestMmHashAlgorithm`:
  - the default `sha256` output matches a reference `hashlib.sha256` computation for a non-contiguous tensor, a strided ndarray and a nested tensor list;
  - `blake3` is deterministic, matches a reference `blake3` computation and differs from SHA-256 (skipped if `blake3` is not installed);
  - an unknown value raises a `ValueError` that names the variable.
- Differential check against the merge base: with the variable unset, `hash_feature` returns identical values before and after this change for an fp32 tensor, a transposed bf16 tensor, a strided int64 ndarray, a 0-d ndarray and a nested tensor list.
- Existing tests still pass: `test_mm_hashes.py` (13 tests), `multimodal/test_preprocess_cache.py` and `multimodal/test_media_artifact_processor.py`.

Run locally with `python3 test/registered/unit/managers/test_mm_hashes.py` and `pre-commit run --files <changed files>` (all hooks pass).
