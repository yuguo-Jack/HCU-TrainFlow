# [Fix] hicache: give a rank-sharded L3 sidecar its own key on a replicated-KV model

[Upstream PR](https://github.com/sgl-project/sglang/pull/42696) · state: closed · merged: False

## Original PR description

## Motivation

`HybridCacheController.should_backup` deliberately has **every** TP rank back up the Mamba sidecar, even on an MLA model, because the Mamba/KDA state is TP-sharded while the primary KV pool is replicated:

```python
# Kimi-K3 Mamba/KDA state is TP-sharded even when the primary MLA KV
# pool is replicated.
if transfer.name == PoolName.MAMBA:
    return True
```

But an MLA model's key deliberately carries no rank (`hicache_storage.py`: `if not is_mla_model: self.config_suffix += f"_{tp_rank}_{tp_size}"`), and `_get_component_key` only prepends the component name to that same suffix. So every rank writes its own shard to **one** key. `HiCacheFile.set` short-circuits on an existing file, so rank 0 wins and every rank loads rank 0's shard back. Silent wrong output on a Kimi-K3-class model with `--tp-size > 1` and the file or NIXL backend. Mooncake is unaffected — its key carries `local_rank`.

## Modifications

One place names the pools whose bytes differ per rank (`RANK_SHARDED_POOLS`) and derives the extra key scope (`rank_shard_key_scope`); the file and NIXL backends consume it. The scope applies only when the model's own key has no rank, so a non-MLA key is unchanged and the MLA KV key stays replicated — the dedup win is kept.

In the file backend the scope goes **before** `config_suffix`: both the LRU evictor and the metadata cache select this rank's files with `stem.endswith(config_suffix)`, so a scope appended after it would make sidecar files invisible to eviction. A test pins that.

## Accuracy Tests

New CPU test `test/registered/unit/mem_cache/test_hicache_rank_sharded_sidecar_key.py` (4 cases, 9 s): distinct keys per rank plus a real write/read-back through `HiCacheFile`; the KV key stays replicated; non-MLA keys are byte-identical to before; the scoped key still ends with `config_suffix`.

Negative control: force `rank_shard_key_scope` back to `""` → `AssertionError: 'h0.mamba_testmodel' == 'h0.mamba_testmodel' : every TP rank backs up its own Mamba shard, so the ranks must not share one key`. Restored → 4 passed.

Found while re-reviewing the unified radix cache; reproduced before the fix with the real backend — rank 1 read back rank 0's payload.

## Open question (why this is a draft)

The same audit found that **no** backend keys the page format — kv dtype, `--hicache-mem-layout`, io backend, packed MTP draft layers, fp4-vs-fp8 indexer — and that NIXL drops PP/CP while mooncake's `mha_suffix` drops `tp_size`. Those are separate silent-collision classes, and the real fix is to derive one key scope for all three backends instead of the three hand-built suffixes we have now. This PR is the minimal correctness fix for the reproduced case; I can fold it into that larger refactor instead if reviewers prefer.
