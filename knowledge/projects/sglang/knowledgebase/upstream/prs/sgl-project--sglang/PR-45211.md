# [Fix] observability: Start the TTFT histogram buckets below 0.1 s

[Upstream PR](https://github.com/sgl-project/sglang/pull/45211) · state: open · merged: False

## Original PR description

## Motivation

bdc1acf6cd (#2761, 2025-01-07) moved the first bucket of `sglang:time_to_first_token_seconds` from 0.001 s to 0.1 s and stretched the tail from 30 s to 160 s, without saying why. Since then a short prompt on a current GPU, which gets its first token in tens of milliseconds, always lands in the first bucket, and the histogram can't tell 20 ms from 90 ms. The inter-token histogram starts at 0.002 s, and the sample output in `docs/docs/references/production_metrics.mdx` still shows the `le="0.01"` to `le="0.08"` buckets.

Measured on 2026-10-17 with SGLang v0.5.21 serving Qwen3-8B (BF16) on one H100 SXM, 150-word prompts, 2 to 64 requests/s: the client measured TTFT p50 of 22 to 31 ms and p95 of 32 to 50 ms across the run, while `histogram_quantile(0.95, rate(sglang:time_to_first_token_seconds_bucket[10s]))` read 0.095 s for every second of it. The same histogram fed an Argo Rollouts canary check (canary TTFT p95 against stable), which therefore could not see a regression smaller than 100 ms.

## Modifications

- Add `0.01, 0.02, 0.04, 0.06, 0.08` in front of the default TTFT buckets. The rest of the list is unchanged, so existing dashboards keep working and `--bucket-time-to-first-token` still overrides everything. Five more buckets per label set.
- Unit test `test/registered/unit/observability/test_metrics_collector.py`: the default buckets resolve below 0.1 s, stay sorted and keep the long tail; explicit buckets are used as given.
