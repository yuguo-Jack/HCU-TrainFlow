# [Feat] rust-server: Report the model's launch-time fields in /model_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/47169) · state: closed · merged: True

## Original PR description

## Motivation

In Rust-frontend mode, `GET /model_info` (and the `/get_model_info` alias) left out five keys that the Python frontend returns: `has_image_understanding`, `has_audio_understanding`, `model_type`, `architectures` and, for a model with an embedding spec, `embedding`. Clients that read the model's modalities or architecture from the endpoint, such as routers, warmup tools and eval harnesses, got different answers depending on which frontend served the request.

## Modifications

- `sglang.srt.utils.common.build_model_info_fields(model_config, server_args)` builds the five keys. Python's `/model_info` handler calls it in place of its inline code, so Python-mode output is unchanged.
- `rust_server/config.py` calls the same helper with the scheduler's `model_config` / `server_args` and passes the result to the Rust `ServerArgs` as a new required keyword, `launch_model_info` (a JSON object string), next to the existing `launch_server_info`.
- The Rust server keeps the object in `CoreMetadata` and `ModelInfo::to_json` appends it after the typed fields, so the key order matches Python's: `... disaggregation_mode, has_image_understanding, has_audio_understanding, model_type, architectures, embedding`. The `LaunchServerInfo` JSON-object newtype is renamed `JsonObject` and backs both launch-time objects.
- Scope: HTTP only. The `api.v1` gRPC `GetModelInfoResponse` proto has no fields for these keys and is unchanged. Rust mode runs its own startup warmup and does not read these keys, so startup behaviour is unchanged.
- Tests: the Rust `/model_info` route test now sets launch fields and checks that they follow the typed fields. `test_server_info.py` gains a parity test that renders Python's `/model_info` body and the Rust launch configuration from one stubbed model config and asserts they are equal. The typed-config fixture in `test_rust_server_dp_ports.py` gains the two modality attributes the helper reads. The parity test's stub scheduler also sets `rust_server_endpoints`, which `_build_server_args` reads since #46181.
