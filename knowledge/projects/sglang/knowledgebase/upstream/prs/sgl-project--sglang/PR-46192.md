# [Fix] modelopt_fp4: skip swizzled blockscales the marlin runner never reads

[Upstream PR](https://github.com/sgl-project/sglang/pull/46192) · state: open · merged: False

## Original PR description

## What

`ModelOptNvFp4FusedMoEMethod.create_weights()` allocates an fp8 copy of *every* expert blockscale in the swizzled layout (`*_blockscale_swizzled`). Three consumers read that copy: the FlashInfer Cutlass path, the CuteDSL path, and TRTLLM.

**The marlin MoE runner never reads it.** `process_weights_after_loading()` returns right after `prepare_moe_nvfp4_layer_for_marlin(layer)` (`modelopt_quant.py:2757`), i.e. before the Cutlass branch that would compute the swizzle, and the runner reads `w13_weight_scale` / `w2_weight_scale` through `get_marlin_quant_info()`. So on the marlin path the copy is pure waste, and because the function returns early there is nothing that could ever free it.

## Change

Materialise the swizzled copy only when the selected backend consumes it — i.e. skip it for `marlin`, `flashinfer_megamoe`, `flashinfer_trtllm_moe`, and for `AUTO`. `AUTO` is resolved later in `process_weights_after_loading()`; the backends that do want the copy (Cutlass / CuteDSL) recompute and bind it there anyway via `alias_or_bind_derived_param`, so skipping the eager allocation is safe. Note `create_weights()` runs before the backend is resolved on this stack, which is why the existing condition could not catch marlin.

## Measurement

Qwen3.8-Flash-Next NVFP4, TP=2 on 2xL20 (47.45 GiB/card), `--mem-fraction-static 0.97`, CUDA graph on:

| item | before | after |
|---|---|---|
| model footprint | 44.75 GB/card | **41.27 GB/card** (-3.48 GiB, -7.8 %) |
| max_total_num_tokens | 240,192 | **547,072** |
| KV pool | 0.54 GiB | 6.26 GiB |
| decode (greedy, 5,157-token prompt) | 95.07 t/s | 95.39 t/s |

No numerical change: the marlin runner's inputs are the same tensors as before, and the freed memory goes to the KV pool. Startup and warmup still fit in the 0.97 fraction (0.94 GiB headroom left per card).

This is what makes a 262K request possible on this card pair at all: 547,072 tokens covers two 262K slots; before the fix not even one fit.

## Testing

- Ran the server end to end (TP=2, 5,157-token prompt, greedy decode, 5 consecutive starts) — 41.27 GB and identical decode throughput inside noise.
- `compileall` clean.

## What this does

The marlin path never reads the swizzled blockscale buffer -- it computes scales from the non-swizzled tensor -- but `create_weights` builds that copy eagerly anyway. Skip it when the runner is marlin and drop the allocation.

## Numbers

Modelopt NVFP4 checkpoint, 2x L20 (TP=2), 262,144 ctx, `--mem-fraction-static 0.94`:

- weight memory **44.77 -> 41.29 GiB per card (-3.48 GiB)**
- KV token capacity at identical settings **240,192 -> 547,072 slots (2.28x)**
- output ids identical on a 54-prompt probe set; no throughput change
