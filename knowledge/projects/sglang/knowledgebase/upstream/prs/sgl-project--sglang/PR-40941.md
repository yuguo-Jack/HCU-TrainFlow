# [Fix] dLLM: Size decode graphs to the default max running requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/40941) · state: closed · merged: True

## Original PR description

## Motivation

Launching DiffusionGemma with `--dllm-algorithm Gemma4Renoise` and no `--max-running-requests` fails during decode CUDA graph capture on one H200 with `torch.OutOfMemoryError` while allocating 64 GiB. The dLLM scheduler and the decode runner both limit concurrent canvases to `DllmConfig.max_running_requests`, which is 1 when the flag is unset, but the shared decode logits buffer is sized earlier from the uncapped capture list. That list is the default decode CUDA graph list up to 256, which the 2048-slot request pool leaves untrimmed, so the buffer reserves float32 logits for 256 canvases of 256 positions over the 262K vocabulary. The runner-local cap came with #34061 and never reached the buffer sizing.

## Changes

- Apply the existing dLLM request cap in `get_batch_sizes_to_capture`, so the decode runner, the shared logits buffer, and the capture log use the same batch sizes.
- Remove the decode runner's own trim, which the helper now covers.

## Validation

- `python -m sglang.launch_server` with the DiffusionGemma flags and no `--max-running-requests` starts on one H200 with decode graph batch sizes `[1]` and answers four prompts sent at once. Unchanged main runs out of memory at the same step.
- Three chat-templated prompts, including a 300-token answer that spans two canvases, were compared with main launched with `--max-running-requests 8`. A fix launch with that flag, which still captures `[1, 2, 4, 8]`, matched main. Six launches ran the fix without the flag, one through `launch_server` and five through `sglang serve` with the separate routing fix, and five of them matched main. The sixth, one of the `sglang serve` launches, returned a different 300-token answer from its 33rd token onward and repeated it exactly on four more requests. Main cannot start without the flag on one H200, so there is no baseline in that configuration, and the cause was not found.
- TP2 without the flag captures `[1]` on both ranks and answers a chat request.
- The affected CPU suites for dLLM, model runner decode rows, CUDA graph setup, and graph runners pass with the same 115 tests and 83 subtests as main. None of them runs the real `get_batch_sizes_to_capture`, so the GPU launches above are the evidence for the moved cap. Pre-commit passes.

## Limits

- The cap still applies only to dLLM algorithms with a separate context-encoding pass (currently Gemma4Renoise), as before. Other algorithms keep their capture sizes.
- The default still admits one canvas at a time, and `--max-running-requests` raises it.
