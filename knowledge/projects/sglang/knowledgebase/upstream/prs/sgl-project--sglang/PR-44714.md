# [Fix] openai: keep the tool-call parser on under tool_choice="none"

[Upstream PR](https://github.com/sgl-project/sglang/pull/44714) · state: open · merged: False

## Original PR description

## Motivation

`tool_choice="none"` currently does two things: the prompt side withholds or soft-disables tools, and the response side turns the tool-call parser off (`_tool_call_parsing_active` returns False). Nothing stops the model from writing a call anyway, for example when the user explicitly insists on a tool. When it does, the call reaches the client as **raw template syntax in `message.content`**, because no parser consumes it.

Seen in production with Kimi K3 (`--tool-call-parser kimi_k3`). The user prompt was "query the weather, you must call get_weather", sent with `tools` and `tool_choice: "none"`. On engines that run this code path, 3 of 6 responses had content like:

```
<|open|>tools<|sep|><|open|>call tool="get_weather" index="1"<|sep|>...
```

The same failure class has come up before for other formats:
- #35393, closed: post-hoc stripping of unparsed K3 syntax.
- #40237, open: DeepSeek tool markup returned as content.
- #43006, merged: withholds DSV tools from the prompt under `none`, but cannot stop the model from emitting a call.

## Modifications

`python/sglang/srt/entrypoints/openai/serving_chat.py`:
- **`_tool_call_parsing_active`** is now true whenever tools and a parser are configured, including `tool_choice="none"`. The parser consumes the call's template syntax instead of leaking it.
- **New `_drop_tool_calls(request)`:** under `"none"`, parsed calls are discarded.
  - Non-streaming returns no `tool_calls`, and a `tool_calls` finish becomes `stop`.
  - Streaming emits no tool-call deltas, never sets `has_tool_calls`, and skips the leftover-argument flush.
- **Under `"none"` with tools present, `skip_special_tokens=False`, as under `"auto"`.** This keeps the markers the parser matches decodable. The glm47 full-assistant grammar case is left as is.
- **Unchanged:**
  - What goes into the prompt under `"none"` (`tools=None` on the jinja path, `tool_choice="none"` for the K3 encoder, DSV omission).
  - The K3 `TOOLS_CLOSE` stop stays scoped to active tools (`test_kimi_k3_tool_call_stop_is_scoped_to_active_tools` still passes).

A model that obeys `"none"` behaves exactly as before. A model that calls anyway now returns its text without the call, instead of the call's raw syntax.

## Accuracy Tests

No model output or kernel change. Response post-processing only.

Unit tests (CPU), in `test/registered/unit/entrypoints/openai/test_serving_chat.py`:
- `test_tool_choice_none_keeps_tool_call_parser_active`
- `test_kimi_k3_tool_choice_none_drops_call_non_stream`: `"none"` returns content `"I'll check the weather."`, no `tool_calls`, finish `stop`. The `"auto"` control returns 1 call with finish `tool_calls`.
- `test_kimi_k3_tool_choice_none_drops_call_stream`: the stream is fed in 7-character pieces. `"none"` streams only `"I'll check."`, with no tool-call deltas. The `"auto"` control still streams the call.

**Without the fix, the new tests fail with the production symptom:** `'<|open|>' unexpectedly found in "I'll check the weather.<|open|>tools<|sep|><|open|>call tool=\"get_weather\"…"`.

**Regressions:** `test/registered/unit/entrypoints/openai/` and `test/registered/function_call/` were run on CPU with and without the patch.
- Same pre-existing environment failures on both (5 dsv4/dsv32/kimi-k3 encoding-detection tests need real model configs, and 3 modules failed to collect locally).
- With the patch: 510 passed, versus 507 without, the difference being the new tests. No new failures.

Not applicable. The extra cost only applies to `tool_choice="none"` requests with tools, which now run the same parser `"auto"` requests already run.

## Follow-up (not in this PR)

A stronger fix would be to stop the model from *starting* a call under `"none"`. For Kimi K3 that means a structural tag excluding `TOOLS_OPEN`, mirroring `get_kimik3_structural_tag(..., "required")`. It is left out here because grammar-constrained decoding under DSPARK with TP > 1 can currently deadlock (#41449), and DSPARK is a common K3 deployment recipe.
