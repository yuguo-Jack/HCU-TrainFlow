# [Fix] scheduler: Keep beam group leaders out of priority preemption

[Upstream PR](https://github.com/sgl-project/sglang/pull/46923) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-priority-scheduling` and preemption on, a beam search request can corrupt other requests' KV cache.

`PrefillAdder.preempt_to_schedule` picks victims from `running_batch.reqs`. A beam group's leader is one of them, so it can be chosen like any other request:

1. `release_req` frees the leader's KV, and the leader is requeued through `preempt_list`.
2. Nothing retires the group or frees its member rows. On the next decode, the member rows still ride the batch (`append_beam_tail`) and keep writing KV through rows that alias the leader's freed slots.
3. Those slots have already been handed to other requests, so their KV is overwritten.

`retract_decode` already handles this case: "Beam groups cannot be retracted, so they are aborted instead of being requeued". Preemption has no such branch.

Symptoms I saw: tokens in another request's KV slots that only beam selection produced, the busy-time pool check (`Full Pool Mem Leak Detected!`), and, in one run, `AssertionError: Only a mamba-capable tree cache allows freeing before alloc` on a full-attention model.

## Modifications

- `preempt_to_schedule`: do not consider beam group leaders as preemption victims. A higher-priority request then preempts other requests, or waits. Preemption is optional here, unlike retraction under memory pressure, so I kept the group running rather than aborting it.
- `test_prefill_adder.py`:
  - `create_mock_req` sets `beam_group = None`; a `spec=Req` mock would otherwise return a truthy mock attribute.
  - New tests: the only lower-priority request is a beam leader, so preemption fails and nothing is released; a plain lower-priority request next to a beam leader is preempted instead of the leader.

  Both fail on `main`.
