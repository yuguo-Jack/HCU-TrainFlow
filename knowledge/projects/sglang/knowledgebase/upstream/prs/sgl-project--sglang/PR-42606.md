# [Fix] dspark: Count attention-DP ranks in the SPS profiler

[Upstream PR](https://github.com/sgl-project/sglang/pull/42606) · state: open · merged: False

## Original PR description

Fixes #42601.

`fetch_server_context()` read `dp_size` straight off `/server_info` and used it as the number of DP rank units. Since #41818 (`--attn-dp-size`), that field counts replicas only: attention-DP groups live inside the TP group and are reported separately as `attn_dp_size`, with `num_dp_ranks = dp_size * attn_dp_size` (`num_dp_ranks_of` in `runtime_context.py`). `/server_info` reports one internal state per DP rank, so on an attention-DP server the profiler

* clamped the sweep against `effective_max_running_requests_per_dp * 1` instead of one cap per rank,
* sent `batch_size_per_rank * 1` requests, so no rank ever reached the target occupancy (each round burned `--round-timeout` in the aligned-step wait), and
* expected 1 rank row while the server reports 8, so each round died with `RuntimeError: Expected records from 1 DP ranks, got 8.`

The patch computes `num_dp_ranks` in one tested helper (`num_dp_ranks_from_internal_state`), scales the running-cap threshold / swept total batch / per-round rank-count expectation by it, and renames `ServerContext.dp_size` to `num_dp_ranks` to say what it holds (manifest key included). Same drift as `one_batch_server`, fixed there in #42331.

If you'd rather have `num_dp_ranks` exposed directly in `/server_info` so no client recomputes the product (it would also let `one_batch_server` drop its inline copy), say the word and I'll switch this over.
