# [Fix] qwen3-coder: Fix quadratic regex scan in the tool-call parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/42579) · state: open · merged: False

## Original PR description

## Motivation

`Qwen3CoderDetector` (parsers `qwen3_coder`, `step3p5`, `nanbeige`) finds tool calls in `detect_and_parse` with `re.compile(r"<tool_call>(.*?)</tool_call>", re.DOTALL).findall(text)`. When `</tool_call>` never arrives, each opening tag rescans to the end of the text, so the cost is quadratic. On the fuzzer-found inputs this `findall` accounted for all of the time: nanbeige 3.2 s at 70 KB, qwen3_coder 2.4 s at 56 KB, step3p5 0.85 s at 36 KB.

| Input (repeated `<tool_call> `) | Before | After |
|---|---|---|
| 23 KB | 0.36 s | 0.1 ms |
| 46 KB | 1.4 s | 0.1 ms |
| 93 KB | 5.8 s | 0.2 ms |

Tool-call parsing runs synchronously on the tokenizer manager's event loop, so one such response stalls every in-flight request. Found with an Atheris fuzzing harness that records per-input parse time.

## Modifications

- `_iter_tool_call_bodies`: a linear `str.find` scan yielding exactly the bodies `findall` returned. The now-unused `tool_call_regex` attribute is removed. The fallback for text with no complete block is unchanged.
- Regression test `TestQwen3CoderDetector::test_unclosed_tool_call_tags_parse_in_linear_time`: 56.2 s on `main`, fast here.

## Accuracy Tests

- Differential test of `main` vs patched detector, comparing `detect_and_parse` and every streaming result under random re-chunking: **0 mismatches** over 20k random plus 20k mutated well-formed inputs (18.7k produced parsed calls).
- `test/registered/unit/function_call/`: 630 passed.

## Speed Tests and Profiling

See the table above. A scaling probe (each token literal and each pair, repeated 2k/4k/8k times) finds no remaining super-linear input. The function and parameter regexes that run afterwards measured linear.

Related: #42573, #42574, #42575, #42576, #42577, #42578 (same issue class in other tool-call parsers).
