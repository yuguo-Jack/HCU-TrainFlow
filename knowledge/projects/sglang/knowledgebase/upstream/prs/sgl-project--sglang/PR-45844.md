# [Perf] dsa: pass tiled decode page_table_row_stride at runtime

[Upstream PR](https://github.com/sgl-project/sglang/pull/45844) · state: open · merged: False

## Original PR description

## Motivation

`transform_index_page_table_decode_tiled_kernel` declares `page_table_row_stride: tl.constexpr`, so Triton compiles a new variant for every distinct page-table row stride it sees.

The tiled kernel runs when the top-k width is not 2048, i.e. `index_topk + index_kpool - 1` with `index_kpool > 1` (2051 for GLM-5.3-Flash) and only when fused top-k is off (`SGLANG_DSA_FUSE_TOPK=0`, or paths that don't use it). On non CUDA graph paths that slice `req_to_token[req_pool_indices, :max_seqlen_k]`, the slice is a copy whose row stride equals `max_seqlen_k`, which changes as requests grow, so each new length can trigger a recompile mid-decode. CUDA-graph decode uses a fixed-width page table and isn't affected.

Follows up #38787, which reported the constexpr recompiles in the prefill and decode kernels; the tiled kernel has the same problem. Not a duplicate: #36888 changes `decode_kernel` and prefill but not the tiled kernel, and #39266 targets the older `transform_index_page_table_decode_fast`.

## Modifications

- `python/sglang/kernels/ops/attention/dsa/transform_index.py`: drop `tl.constexpr` from `page_table_row_stride` in the tiled decode kernel and add `@triton.jit(do_not_specialize=["page_table_row_stride"])`. This follows the prefill kernel in the same file, which already uses `do_not_specialize=["page_table_stride_0"]`.
- `test/registered/kernels/ops/attention/test_dsa_transform_index.py`: added `test_decode_tiled_page_table_row_stride_is_not_specialized` (param is not constexpr and is in `do_not_specialize`) and `test_decode_tiled_dynamic_page_table_row_strides`, which runs at top-k width 2051 (`KPOOL_TOPK`) so it exercises the tiled path, across page-table row lengths 4096, 4160, 4224, 4100 and 4101, and asserts the kernel cache doesn't grow. Mirrors the existing prefill pair.

`decode_kernel` (topk 2048) is unchanged here and is left to #36888.

## Accuracy Tests

Kernel logic is unchanged; only the stride is passed at runtime. Outputs match `torch.gather` exactly at top-k widths 2048, 2051, 515 and 257. The new tests' assertions were run standalone on an RTX 4090; the full test file is left to CI.

## Speed Tests and Profiling

Setup: RTX 4090, torch 2.8.0+cu128, Triton 3.4.0, base `8cd3c494a3`.
Kernel-level repro (not an end-to-end server benchmark) with 5 page-table row strides (4096, 4160, 4224, 4100, 4101):

| kernel | before | after |
|---|---|---|
| `decode_tiled_kernel` (topk 2051) | 5 compiled variants | 1 |
| `decode_kernel` (topk 2048, unchanged; see #36888) | 5 | 5 |

The non-multiple-of-16 strides (4100, 4101) don't add variants either. Recompile stall time and per-launch kernel time weren't measured; the change only removes recompiles.

Repro script: https://gist.github.com/mushyalpha/2df28fee89a410765d8945016de18287
