# [sgl-router] Read finished /generate streams to the end; expose reorg admission caps as flags

[Upstream PR](https://github.com/sgl-project/sglang/pull/43233) · state: closed · merged: True

## Original PR description

Two router changes found while E2E-testing DeepSeek-V4.1-Flash behind the router, stacked on #43000.

## 1. Read a finished /generate stream to its end

### Motivation

For an OpenAI request served through the engine's `/generate`, the router dropped the engine stream as soon as the engine's `data: [DONE]` arrived. The engine usually hadn't closed the body yet. The proxy pump then saw the drop as a client disconnect, which had two effects:
- `AbortOnDrop` sent `/abort_request` for a request that had already finished;
- `sgl_router_stream_outcome_total` counted the stream as `client_disconnect` instead of `ok`.

In the E2E run, 11 of 54 streamed chats that completed normally hit this. Responses were complete in every case.

The early drop exists because an abort or error ends the OpenAI stream before the engine is done, and dropping the upstream then aborts the remaining choices, as Python does. After `[DONE]` there is nothing left to abort. The early drop came in with #42997.

### Modifications

- `routes/chat/openai.rs`: once the responder is done, the stream is read to its end if the last frame was `[DONE]`, and dropped as before if it ended at an abort or error.
- New proxy test `a_finished_stream_sends_no_abort`: the mock engine closes its body a moment after `[DONE]`. The test fails without the fix.

### Checks

- Live, DeepSeek-V4.1-Flash behind the router, 49-case streaming chat matrix: router `/abort_request` calls went from 9 to 0, and `stream_outcome_total{outcome="ok"}` covers 49 of 49 streams (was 43 `ok` and 11 `client_disconnect`). Responses still match the engine.

## 2. Expose every reorg admission cap as a CLI flag

### Motivation

Reorg admission has five per-engine caps (`policies_reorg/admission.rs`), but the CLI set only two of them:
- `--max-kv-usage`;
- `--max-in-flight`, which also required a `--filter overloaded` that reorg never applies (the overloaded filter only runs in legacy policies).

`max_waiting_requests`, `max_pending_prefill_tokens` and `max_running_usage` were reachable only through `--bucket-config`.

This matters for `cache_aware` with `--affinity-mode prefer`. With no cap set, every prefix owner is admissible, so a hot prefix never falls back. In the E2E run, 400 requests on one 4k prefix at concurrency 128 all went to one engine, which rejected 288 of them with `503 queue full` while the other engine sat idle. The legacy `--worker-queue-limit` that guarded this is rejected under reorg.

### Modifications

- New reorg-only flags `--max-running-usage`, `--max-waiting-requests` and `--max-pending-prefill-tokens` set the default admission caps. Bucket groups still override them per group. Legacy routing rejects them, as it already rejected `--max-kv-usage`.
- Under reorg, `--max-in-flight` works without `--filter overloaded`. Legacy keeps the pairing.
- The README reorg section lists the admission flags. It also notes that engine-reported caps lag by one load report, so a burst can pass them, while the router-local `--max-in-flight` counts dispatches as they happen.

### Checks

- CLI tests cover the new flags reaching `reorg_admission`, legacy rejecting each of them, and invalid values.
- Live, with `--chat-routing reorg --policy cache_aware --max-in-flight 96 --max-waiting-requests 48` on the hot-prefix load above: 0 engine queue-full rejections (was 288), split 47/53, prefix hit rate 93.5%.

## Checks (both)

- `cargo clippy --all-targets -D warnings` and `cargo test` in `experimental/sgl-router` pass.
