# [Spec] Reduce DSpark CUDA-graph memory probe over the capture group

[Upstream PR](https://github.com/sgl-project/sglang/pull/39954) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #39886.

DSpark explicitly supports DP attention with a DeepSeek-V4/MoE draft when attention TP size is 1 and full TP size is greater than 1. In that configuration `DSparkWorkerV2` constructs `SpecTpSync` with the singleton `attn_tp_group` (correct for runtime broadcasts: peer DP ranks run different requests) while draft CUDA graph capture uses the larger `tp_group`.

The memory probe already passes that capture group to `SpecTpSync.available_memory_gb`, but the constructor had cleared every sync site because its group had one rank. The helper therefore read rank-local free memory instead of reducing the minimum over full TP. If those readings fall on opposite sides of the 1 GiB decode-graph cutoff, some ranks skip capture while others enter it and hit `tp_group` barriers in `FullCudaGraphBackend.capture_one`, which can stall startup.

The unit reproduction in the issue is the skipped reduction (`distributed=False` for a 2-rank override group). A multi-GPU hang was not reproduced here; it follows from the mismatched collective participation.

## Modifications

- Keep the configured `SGLANG_SPEC_TP_SYNC` site set on `SpecTpSync` even when the constructor broadcast group is a singleton.
- Reduce `available_memory_gb` over the caller-supplied group when that site is configured and `group.world_size > 1`.
- Leave `sync()` on the constructor group so DP-attention runtime broadcasts stay inside attn-TP.
- Add a CPU unit test for the attn-TP=1 / full-TP>1 memory probe, site-off, multi-rank constructor, and the still-disabled runtime broadcast.
