# [Fix] [AMD] dsa: Align Aiter paged rows with DP-attention metadata

[Upstream PR](https://github.com/sgl-project/sglang/pull/33059) · state: open · merged: False

## Original PR description

## Motivation

With DP-attention padding, `Indexer._get_topk_paged` can receive physical query and weight rows beyond the real query count `q_offset`. Aiter sizes its logits from the query tensor, while top-k sizes from the real-row metadata, so padded inputs fail the top-k row check. The padding restoration after top-k also excluded HIP.

Reproduced on MI355X (DeepSeek-V3.2, TP8 + `--attn-dp-size 8`, EAGLE MTP 3/1/4, eager steps above `--cuda-graph-max-bs-decode 16`): on unpatched main an eager step arrives with `q_offset=60` real rows and 64 physical rows, and the server dies in `sgl_kernel.fast_topk_transform_fused` with `RuntimeError: lengths must have one entry per score row`.

## Modifications

- Slice the Aiter query and weight inputs to `q_offset`, the same real-row contract the other paged backends use.
- Restore trailing `-1` top-k rows on HIP as well, so callers still get one row per physical query row.
- When `q_offset == 0`, return all-`-1` int32 indices without launching Aiter or top-k. This is a defensive guard: Aiter's [SplitKV scheduling](https://github.com/ROCm/aiter/blob/7559e3411beecb04d2f64ac488d6990a3b03534e/aiter/ops/triton/attention/pa_mqa_logits.py#L711) divides by the query count, and no run below reached this branch.
- Add a CPU regression test for the row contract with Aiter and top-k stubbed (`base-a-test-cpu`).
