# [mlx] Clamp decode-KV flush to the owned prefix at release

[Upstream PR](https://github.com/sgl-project/sglang/pull/42542) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #42415

On Apple Silicon with radix cache enabled, a `chat -> native -> same chat` sequence makes the second chat continue the native text instead of answering the question; disabling radix cache hides it. Root cause, traced with slot-level instrumentation (details in the issue comment):

Chained decode steps (`_launch_chained` in the MLX overlap loop) skip `prepare_for_decode`, so pool slots are only allocated for the first decode step of a request and `req_to_token` entries past that point are never written. `_sync_decode_kv_to_pool` keys its range off the contiguous cache offset, which counts every decoded token, and reads slot ids from `req_to_token[row, synced:offset]`. Past the owned prefix that slice is zeros on a fresh row, or the previous owner's content once the row is recycled, so the flush scatters the finishing request's KV into slots the radix tree still keys on. The scheduler side stays consistent because `release_kv_cache` caps the tree insert at `owned_kv_len`, which reflects the same allocation accounting.

## Modifications

- `MlxTpModelWorker.prepare_for_kv_cache_release` now flushes the request's decode KV, clamped to `req.owned_kv_len()`. This hook runs right before `release_kv_cache`, while the row is still owned.
- `MlxModelRunner.flush_decode_kv_for_request` syncs only the owned prefix and then seals the request (synced offset set to the cache offset), so the deferred flush in `remove_request` becomes a no-op. The unowned tail is never pool-addressable, so skipping it loses nothing.
- `_sync_decode_kv_to_pool` gains an optional `limit` for the clamp.
- New `test_mlx_release_flush.py` regression tests.

## Accuracy Tests

End-to-end on M-series with `mlx-community/Qwen3-0.6B-4bit`, radix on:

- The #42415 repro (`chat -> native -> identical chat`): pre-patch the second chat returned the native continuation; post-patch it repeats the first chat's answer.
- An unrelated-topic variant (chat about planets around a native prompt on quantum entanglement): pre-patch the second chat answered with the native text; post-patch both chats answer their own topic.
- Slot traces post-patch show each finish flushing exactly the one owned decode slot, vs. recycled-row reads pre-patch.

## Speed Tests and Profiling

No hot-path impact: one extra guarded flush per finished request, capped at the owned prefix; the deferred flush it replaces did strictly more work.

On an M-series box (Qwen3-0.6B-4bit, radix on, local Torch 2.11 / MLX 0.31.2 with the version gate bypassed), this fixes the sequential #42415 repro, and the root-cause trace in #42415 matches what I filed as #30093. The same corruption still happens when a request arrives while another one is mid-chain, because the next extend launch calls flush_all_decode_kv with no bound. That flush writes past the committed length into stale row entries and moves synced past the slots later decodes allocate, which then enter the tree with stale or zero KV. #43292 drops the per-extend flush and covers this case.
