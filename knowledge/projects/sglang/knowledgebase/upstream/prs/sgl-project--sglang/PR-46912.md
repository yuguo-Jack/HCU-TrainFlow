# [Fix] [AMD] attention: size the Lean decode KV tile to the device LDS budget

[Upstream PR](https://github.com/sgl-project/sglang/pull/46912) · state: open · merged: False

## Original PR description

## Motivation

`--attention-backend triton` cannot start on gfx1151. The Lean decode kernel is
captured for batch >= 16 and stages only the K tile in LDS, but on HIP head dim
128 was always given `BLOCK_N = 128`, i.e. `num_stages * BLOCK_N * head_dim * 2
= 2 * 128 * 128 * 2 = 65536` B plus the compiler's own scratch. That is 66560 B
against the 64 KiB shared memory per workgroup of gfx1151 (RDNA3.5), so graph
capture raises `OutOfResources: shared memory Required 66560, Hardware limit
65536` and no request is served. `torch_native` is the only backend left, and it
is 8-16x slower than the Triton decode kernels on this part.

## Modifications

- `_lean_decode_block_n` picks the largest tile whose staged K tile fits the
  device's `shared_memory_per_block`, instead of hard-coding `BLOCK_N = 128` on
  HIP. The candidates stay `128/64/32/16`; gfx1151 lands on 64 (32768 B).
- `num_stages` becomes `_LEAN_NUM_STAGES` so the launch and the budget
  arithmetic cannot drift apart.
- CUDA keeps `BLOCK_N = 64` and MLA head dims (288/576) keep their 16-token
  tile, so those paths are unchanged.
- New CPU test `test/registered/unit/layers/attention/test_lean_decode_block_n.py`
  feeds the budget in and pins the choice (64 KiB -> 64, 160 KiB -> 128, MLA ->
  16, CUDA -> 64, no choice overshoots). It fails on the pre-fix code.

No user-facing flag is added. On builds that expose the device budget, parts
whose LDS can hold the 128-token tile keep `BLOCK_N = 128`; this ROCm build
(torch 2.9.1+rocm7.2.4) does not expose `shared_memory_per_block`, so the
64 KiB fallback applies (see caveats).

## Accuracy Tests

The tile size changes the reduction order of the online softmax, so outputs are
not expected to be bit-exact against the grouped path. Measured on Qwen3-0.6B,
`temperature=0`, fixed `seed`, 16 concurrent, `logprobs` on:

| workload | identical outputs | max abs logprob delta | median |
|---|---|---|---|
| short KV (32 distinct prompts, 48 tokens) | 18/32 | 0.153 | 0.0005 |
| long KV (16 distinct 2036-token prompts, 32 tokens) | 15/16 | 0.120-0.173 | 0.0005 |

The same-configuration rerun noise floor (Lean on vs Lean on, identical settings)
is 1-4/32 flipped tokens with max abs delta 0.08-0.12, i.e. the same magnitude
as the differences above. Every flip observed is a near-tie that keeps the
sentence meaning. So: rounding-level differences, no systematic shift.

Unit test (re-run on the rebased head): `python -m pytest
test/registered/unit/layers/attention/test_lean_decode_block_n.py -v`
-> 5 passed in 0.05 s; 5 failed in 3.20 s against the unpatched module in the
same container. The container's installed sglang predates current `main`, so the
test was run against that file with this PR's two hunks applied; the
`_lean_decode_block_n` region is byte-identical to the head.

## Speed Tests and Profiling

Ryzen AI MAX 395 (gfx1151), torch 2.9.1+rocm7.2.4, Qwen3-0.6B, 16 concurrent,
`temperature=0`, median of 3 runs, only `SGLANG_DISABLE_LEAN_ATTENTION` differs:

| workload | Lean on | Lean off | delta |
|---|---|---|---|
| short KV (48 steps) | 33.43 ms/step | 32.30 ms/step | -3.5% |
| long KV (2035-token prompts, 32 steps) | 55.50 ms/step | 63.92 ms/step | +13.2% |

Kernel-only (bs=16, splits=16), Lean at `BLOCK_N = 64` vs the grouped kernel:

| kv | grouped | Lean | delta |
|---|---|---|---|
| 64 | 19.7 us | 22.4 us | -13.7% |
| 512 | 170.5 us | 99.2 us | +41.8% |
| 2048 | 863.2 us | 638.6 us | +26.0% |

Runtime proof that the captured graph really runs Lean: at batch 16 the trace
shows `_lean_attention_decode_kernel` 1344 times (48 steps x 28 layers); with
`--cuda-graph-max-bs-decode 8` the count is 0 and only the grouped kernels
appear.

As tested downstream on RDNA4 (gfx1201, 64 KiB LDS), reported in this thread:

| item | result |
|---|---|
| Qwen3-8B, graph capture, without this PR | `OutOfResources: shared memory Required 66560, Hardware limit 65536` |
| Qwen3-8B, with this PR | service starts in 50 s, gsm8k 98% (100 q) |
| Qwen3-8B, bench_serving random-ids, c=1 / c=8 | 25.0 / 189.6 tok/s (TPOT 39.7 / 40.7 ms) |
| same, Lean off | 25.0 / 189.5 tok/s |
| OLMoE-1B-7B, with this PR | gsm8k 60% (50 q), previously unable to serve |

That is the intended shape of the fix: it unblocks the backend and is neutral on
throughput once it runs.

Caveats for reviewers:

- Lean is only captured at batch >= 16, so single-stream workloads (the common
  ASR case, bs 1-8) neither gain nor lose from this change; they keep replaying
  the grouped kernel.
- With 16 *identical* long prompts the shared KV prefix favors the grouped path
  and Lean looks 14.6% slower; the numbers above use distinct prompts.
- Attention is only 4.9% of a batch-16 step here (GEMM is 81%); the win is real
  but bounded by where Lean is captured.
- `torch.cuda.get_device_properties()` on this ROCm build has no
  `shared_memory_per_block` attribute, so `_lean_lds_limit()` takes the 64 KiB
  fallback on gfx1151, which is the correct tile there. Whether a larger-LDS
  HIP part still selects 128 is untested on hardware; the unit test covers it
  only through an injected budget.

On the `BLOCK_N = 64` trade-off for 64 KiB cards: the staged tensor is
`num_stages * BLOCK_N * head_dim * 2 B`, so head dim 128 on a 64 KiB workgroup
cannot hold 128 without overshooting the hardware limit. 64 halves the staged
tile to 32768 B, which is what makes the graph capturable at all. It costs
nothing measurable in the shapes you measured (parity with Lean-off), and on
gfx1151 Lean at 64 is still ahead of the grouped kernel once KV is long
(kernel-only, bs=16: 22.4 us vs 19.7 us at kv=64, 99.2 us vs 170.5 us at kv=512,
638.6 us vs 863.2 us at kv=2048) — so 64 is the right point on this class of
card, not a compromise that gives back the win.

On `#47254`: agreed, the two are complementary. #47254 makes RDNA default to
Triton and leaves Lean's auto-gate off there; this change makes Lean itself fit
when it is enabled, on parts whose LDS cannot hold the 128-token tile. Neither
subsumes the other, and your throughput parity against Lean-off (25.0 vs 189.5
tok/s) is what a right-sizing fix should look like on RDNA4.

Two disclosure items from our re-run, so reviewers are not surprised:

1. On this ROCm torch build `torch.cuda.get_device_properties(...)` has **no**
   `shared_memory_per_block` attribute (checked: only `L2_cache_size`,
   `gcnArchName`, `regs_per_multiprocessor`, `max_threads_per_multi_processor`,
   ...). `_lean_lds_limit()` therefore takes its `except` branch and returns
   the 64 KiB floor on gfx1151; Triton reports the same value
   (`max_shared_mem = 65536`). So on gfx1151 the outcome is correct, but via the
   fallback rather than a real device query. Since `_lean_decode_block_n` only
   runs the budget check on HIP, this means the query is effectively a fallback
   on ROCm today. A follow-up could read `max_shared_mem` from
   `triton.runtime.driver.active.utils.get_device_properties(...)` as a second
   probe; that is not in this PR.
2. Because of (1) we cannot confirm from this box that a >64 KiB LDS AMD part
   (e.g. MI300X, 160 KiB) keeps `BLOCK_N = 128`; the unit test only proves it
   for an injected budget. If AMD CI on #47254 can print
   `_lean_decode_block_n(128)` there, that would settle it.
