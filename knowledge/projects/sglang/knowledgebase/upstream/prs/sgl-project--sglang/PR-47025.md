# [Feat] disaggregation: Add opt-in Mooncake TENT transfer engine backend for PD

[Upstream PR](https://github.com/sgl-project/sglang/pull/47025) · state: open · merged: False

## Original PR description

<!-- PR body starts below -->

## Motivation

Mooncake's next-generation transfer engine, **TENT**, can choose a transport per request, spread traffic across NICs by backlog and bandwidth, and isolate foreground and background traffic into separate QP pools. This PR adds it as an **opt-in** backend for the Mooncake PD connector so it can be evaluated. **Classic TE stays the default.**

On one node, TENT reduced KV transfer latency under NIC congestion. TTFT did not change much, because prefill compute dominates it. The numbers below are reference data points, not a general performance claim.

## Modifications

- **`kv_transfer_engine.py` (new):** a small `KVTransferEngine` interface shared by TE and TENT, plus a `TransferIntent` enum (`FOREGROUND` / `BACKGROUND`).
- **`mooncake_transfer_engine.py`:** the TE wrapper implements the interface. `SGLANG_MOONCAKE_TRANSFER_ENGINE` selects `te` (default) or `tent`. Elastic EP and expert backup rely on TE internals, so they raise an explicit error under TENT.
- **`tent_transfer_engine.py` (new):** `TentTransferEngine`, built on the native `tent` module.
  - **Transport:** RDMA only, pinned to `--disaggregation-ib-device`. `MOONCAKE_PROTOCOL=tcp` / `MC_FORCE_TCP=1` switches to TCP; other protocols are rejected.
  - **Metrics:** served on port `9100 + gpu_id`. A port clash only logs a warning.
  - **Handshake:** `session_id` is `host:rpc_port`, the same as TE, so bootstrap is unchanged.
  - **Submission:** chunks of 128 requests on 2 threads.
  - **Timeouts:** same budget as TE. On timeout or failure, every submitted task is cancelled before its batch is freed.
  - **Peer segments:** refcounted. A failure marks the segment stale, and the next transfer re-resolves the peer.
  - **`send_probe`:** forces a descriptor re-fetch from the peer over RPC.
  - **Extra config:** `SGLANG_TENT_CONFIG_OVERRIDE` (JSON) is deep-merged into the TENT config.
- **Callers:** PD KV writes in `conn.py` are tagged `FOREGROUND` (TE ignores the tag). HiCache Mooncake Store keeps its own TE instance under TENT. Both env vars are registered in `environ.py`.
- **Tests:** 18 CPU-only unit tests with a mocked `tent`. They cover engine selection, config construction, timeouts, chunking and intent, cancel/free on every error path, segment refcounting, and the probe.

**Usage**

```bash
export SGLANG_MOONCAKE_TRANSFER_ENGINE=tent     # default: te
# optional: let same-host peers use NVLink (off by default)
export SGLANG_TENT_CONFIG_OVERRIDE='{"transports": {"nvlink": {"enable": true}}}'
```

TENT needs Mooncake built with `-DUSE_TENT=ON`; the metrics HTTP endpoint also needs `-DTENT_METRICS_ENABLED=ON`. Tested with Mooncake `5d77d34`.

**Known limitations**

- **NVLink is off by default for co-located P/D:**
  - TENT's NVLink submit waits for work already queued on the caller's default stream. SGLang's overlap scheduler runs the forward pass on a separate stream, so this did not trigger in our runs.
  - Memory allocated with `expandable_segments` (CUDA VMM) cannot be registered, and there is no fallback. This applies with or without NVLink.
- Not supported under TENT:
  - Elastic EP and expert backup.
  - Sharing the engine with HiCache Mooncake Store.
  - Multimodal-gen transport (unchanged).
- No caller emits background traffic yet, so QP-pool isolation is not exercised end to end.

## Validation on real hardware

Setup: 8× H20 (NVSwitch) and 400 Gb/s RoCE NICs; each GPU uses the NIC on its own PCIe switch.

- **Engine smoke test (cross-process):**
  - A 256 MiB write is verified byte for byte.
  - The probe returns 0 for a live peer and −1 for a dead one.
  - With 4 concurrent writers, all return −1 after the peer is killed, and the segment closes only after the last writer finishes.
- **1P1D with `kill -9` on decode under load:** Qwen3-8B TP=1 and Qwen3-32B TP=2.
  - Prefill logs `Session … failed` and in-flight requests fail fast.
  - Prefill stays healthy throughout.
  - A restarted decode serves traffic again: 32B passed 48/48 before and after; 8B passed 47/48, with the same request missing the client's answer-keyword check both times.

## Accuracy Tests

KV layout and model code are unchanged; only the engine that moves the bytes changes. Transferred bytes are verified exactly in the smoke test. We can add a GSM8K PD run (TE vs. TENT) if reviewers would like one.

## Speed Tests and Profiling

Qwen3-8B, single-node 4P4D, TP=1. "Busy" means another process saturates the prefill-side NIC. All numbers are from a single machine.

**TE vs. TENT (mean, ms)**

| Case | KV transfer: TE → TENT, idle | KV transfer: TE → TENT, busy | TTFT: TE → TENT, idle |
|---|---|---|---|
| 8K, conc 1 | 7.7 → 7.3 | 14.4 → 8.5 | 1094 → 1096 |
| 32K, conc 1 | 41.5 → 20.4 | 60.2 → 33.3 | 5903 → 5234 |

- **High concurrency:** at concurrency 16 with 2 submission threads, mean TTFT is +0.9% vs. TE and P99 is −10.2%. P99 is noisy across sessions.
- **Small blocks on an idle NIC:** about 28% slower than TE (32K blocks: 22.1 vs. 30.9 GB/s). This is CPU-bound per-request submission; a batched API in the `tent` bindings would fix it.
- **One of two NICs busy:** TENT holds about 42 GB/s vs. 22 GB/s for TE (256K blocks).

**QP-pool isolation (engine level):** foreground P99 drops from 22.8 ms to 0.84 ms when tagging is combined with QP pools, and background bandwidth stays at about 48 GB/s. Tagging alone has no effect.

**Co-located P/D over NVLink (opt-in)**

- **Engine level:**
  - 256K blocks: 198.9 GB/s vs. 46.2 GB/s over RDMA, with 0 bytes on the NIC.
  - Bytes verified exactly.
  - A dead peer fails fast.
  - Per-process `CUDA_VISIBLE_DEVICES` works.
- **4P4D:** unique prompts; two interleaved rounds that agreed within 1%.

| Load | KV transfer per call, RDMA → NVLink | Mean TTFT, RDMA → NVLink |
|---|---|---|
| 2K, sequential | 8.2 → 1.6 ms | 242.3 → 235.6 ms (−2.8%) |
| 8K, sequential | 26.8 → 3.9 ms | 1034.6 → 1010.7 ms (−2.3%) |
| 8K, Poisson 3 req/s | 27.6 → 4.0 ms | 1386.0 → 1360.4 ms (−1.8%) |

KV transfer is 5–7× faster over NVLink, but TTFT drops only 1–3%, because prefill compute dominates TTFT for an 8B model on one GPU.

## Future work

- **NVLink by default:** remove the caller-stream wait in TENT's NVLink path (a Mooncake change), and measure where transfer is a larger share of TTFT.
- **CUDA VMM memory:** support registering `expandable_segments` allocations.
- **Batched submission:** add it to the `tent` bindings to remove the small-block CPU bottleneck.
- **Background traffic:** tag background traffic so QP-pool isolation applies end to end.

- staryxchen · comment · 2026-10-28T12:41:37Z · [source](https://github.com/sgl-project/sglang/pull/47025#discussion_r4400655093)

File: `python/sglang/srt/distributed/device_communicators/tent_transfer_engine.py` · line None

`send_probe` closes the cached segment, opens it again, then calls `get_segment_info`. In TENT, `get_segment_info` only reads the local segment cache (`getRemoteCached`). It does not ping the peer. The call that actually reaches the peer is `open_segment`. The Python bindings do not expose `probePeerAliveByID`, so re-opening is a reasonable stand-in for the failed-session probe, and `get_segment_info` looks redundant.

The comment that says a successful segment-info fetch proves the peer RPC server answers overclaims that. The probe loop only walks `failed_sessions`, and new transfers to those sessions are skipped, so this does not close a handle that a healthy in-flight transfer is using.

- staryxchen · comment · 2026-10-28T12:41:37Z · [source](https://github.com/sgl-project/sglang/pull/47025#discussion_r4400655094)

File: `python/sglang/srt/distributed/device_communicators/tent_transfer_engine.py` · line None

Per-layer KV writes call `batch_transfer_sync` concurrently on the same session. On any non-zero result, `_close_segment` drops that session's handle. One layer failing can close the segment while other layers still hold it for submit or poll.

The request is already failing, so this is not a happy-path bug. It would be safer if the close waited until those in-flight submits for the same session had finished.

- staryxchen · comment · 2026-10-28T12:41:37Z · [source](https://github.com/sgl-project/sglang/pull/47025#discussion_r4400655098)

File: `python/sglang/srt/distributed/device_communicators/tent_transfer_engine.py` · line None

On timeout, `_write_and_wait` returns `-1` and `_free_batches` calls `free_transfer_batch` without canceling the batch first. TENT defers `freeBatch` on a busy batch, so the WRITE may still commit on the peer. This engine does not resubmit, which is the right call. If an upper layer retries that `-1`, the KV can be written twice.

Canceling the batch before free, or documenting that a timeout is "may have landed", would match that uncertainty.
