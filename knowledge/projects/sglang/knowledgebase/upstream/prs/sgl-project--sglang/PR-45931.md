# [Fix] deepseek-v4.1: size the KV pool by the ratio-1/2 layout's own entry bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/45931) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1 keeps its ratio-1/2 compressed KV in `KVLayout.V41_FP4` (288 bytes an entry) on SM100, and on SM120 with #45851. The pool configurator still prices that entry at `kv_bytes`, which is the 584 bytes of a V4 FlashMLA slot, whatever layout the pool is built with.

For DeepSeek-V4.1-Flash, which has kv_source layers 2, 8 and 14 at ratio 2 and layer 20 at ratio 1, the configurator therefore costs a full token at 1,630 bytes, but the pools allocate 890. The KV pool ends up holding about 55% of the tokens its memory budget covers.

## Modifications

`_compressed_bytes_per_full_token` now prices a ratio-1/2 entry with `_get_paged_kv_bytes_per_token(ratio)`, the entry size of the pool's own layout. The ratio-4 and ratio-128 pools are already priced this way. The indexer term is unchanged.

Layouts that store 584 bytes an entry are unaffected. These are V4, the unified pools and trtllm, for which `_get_paged_kv_bytes_per_token` returns `kv_bytes` or the V4 page size.

## Accuracy Tests

This changes only how many tokens the budget buys; the allocation and the kernels are unchanged.

Test setup: DeepSeek-V4.1-Flash-1017 on one RTX 5070 Ti, SM120 with #45851, and the same 0.30 GB KV budget. With the larger pool the server serves normally:

- the tool-call check passes 5/5;
- the 24-piece mean NLL is 2.5965.

## Speed Tests and Profiling

| | Before | After |
|---|---|---|
| `bytes_per_full_token` | 1,630 | 890 |
| KV pool | 98,560 tokens | 180,480 tokens |
| Free memory after the pool | 2.92 GB | 2.86 GB |

Free memory after the pool is nearly unchanged, so the estimate now matches what the pools allocate.

Heads-up: I think the functional half of this already landed, one day after you opened it.

`#41275` ([Fix] deepseek-v4.1: Match KV capacity to physical layouts), merged 2026-10-27 as `20ff40cb8`, rewrites the same expression in the same place:

```
         if ratio in (1, 2):
-            return (self.kv_bytes + self.low_ratio_index_bytes) / ratio
+            return (
+                self._get_paged_kv_bytes_per_token(ratio) + self.low_ratio_index_bytes
+            ) / ratio
```

The minus-line is byte-identical to yours; `#41275` just wrote it on three lines instead of one. Current `main` therefore already reads your version apart from the comment (python/sglang/srt/model_executor/pool_configurator.py, `_compressed_bytes_per_full_token`), so the only delta left in this patch is the two-line explanation.

That explanation is worth keeping on its own merits, because both numbers in it are right. Against `kernels/ops/attention/dsv4/kv_layout.py` on `main`: `V41_FP4` is `data_bytes` 256 + `scale_bytes` 32 = 288 bytes/token, and `V4` is 576 + 8 = 584 — the same 584 that `DeepSeekV4SingleKVPool.create_buffer` asserts as `448 + 64 * 2 + 8`. The old `self.kv_bytes` is also 584 (set to `qk_nope_head_dim + qk_rope_head_dim * 2 + 8`, commented "One FlashMLA-layout latent slot"), so an FP4 ratio-1/2 layer was budgeted at 584 for 288 bytes of real entry, about 2.03x, which is capacity the configurator gave up for bytes the pool never allocates. That is exactly the sort of regression a comment like this stops from coming back.

So the remaining choice is rebase-and-keep-as-comment-only, or close as superseded. If you rebase I will run it on 8xRTX PRO 5000 (SM120) with a DeepSeek-V4.1-Flash checkpoint and report the bytes-per-token the configurator ends up using for the ratio-1 and ratio-2 layers, before and after — it is doc-only, so I expect the same numbers, but I would rather confirm that than assume the rebase is clean.
