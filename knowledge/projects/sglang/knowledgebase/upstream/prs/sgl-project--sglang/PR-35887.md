# [Bugfix] Fix Qwen3.5 MTP compressed-tensors ignore matching

[Upstream PR](https://github.com/sgl-project/sglang/pull/35887) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #35797.

Compressed-tensors Qwen3.5 checkpoints list the individual MTP projections under `quantization_config.ignore`. `Qwen3_5ForCausalLMMTP` did not expose the target model's `packed_modules_mapping`, so the loader passed an empty fused mapping into the quantization config. As a result, `qkv_proj` and `gate_up_proj` could not inherit the ignore decisions of `q_proj`/`k_proj`/`v_proj` and `gate_proj`/`up_proj`. They were built with packed parameters even though the checkpoint stores plain BF16 weights, so those MTP weights were skipped during loading.

## Modification

- Reuse `Qwen3_5ForCausalLM.packed_modules_mapping` on the MTP entry class.
- Add CPU regression coverage showing that both fused projections inherit their component ignore entries.

This preserves per-layer compressed-tensors semantics instead of disabling quantization for the entire MTP module.

- nyhhome · comment · 2026-08-27T22:45:00Z · [source](https://github.com/sgl-project/sglang/pull/35887#issuecomment-5446106644)

### Independent reproduction and fix confirmation on a separate platform

We co-diagnosed #35797, and this PR is exactly the general fix we suggested there, so we ran an independent validation of it on our own hardware. **The fix works.**

**Setup.** Single NVIDIA GB10, image `lmsysorg/sglang:nightly-dev-cu13-20260821-f825d729` (the same nightly used in the #35797 report), checkpoint `cyankiwi/Qwen3.8-27B-AWQ-BF16-INT4` (compressed-tensors, `pack-quantized` W4A16, ships its own BF16 MTP head). Flags: `--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 --mamba-radix-cache-strategy extra_buffer`, `--mem-fraction-static 0.70`, 32k context. **No workaround flags of any kind.**

The production hunk applies cleanly to that nightly (no fuzz/offset). We ran three legs that differ by one variable at a time; both speculative legs bind-mount a read-only file at the *same* path `/sgl-workspace/sglang/python/sglang/srt/models/qwen3_5_mtp.py`, so the only difference between them is the file's *content*. Their recorded launch command lines are byte-identical.

**Before the GPU legs — a CPU-only check of the mechanism**, using the checkpoint's real 456-entry `ignore` list:

| | unpatched | patched |
|---|---|---|
| `hasattr(Qwen3_5ForCausalLMMTP, 'packed_modules_mapping')` | `False` | `True` |
| `should_ignore_layer("mtp.layers.0.self_attn.qkv_proj", ignore, mapping)` | **False** | **True** |
| `should_ignore_layer("mtp.layers.0.mlp.gate_up_proj", ignore, mapping)` | **False** | **True** |
| `should_ignore_layer("mtp.layers.0.self_attn.o_proj", …)` (control, literal match) | True | True |
| `should_ignore_layer("mtp.layers.0.mlp.down_proj", …)` (control, literal match) | True | True |

The two literal-match control layers are unaffected, so the change lands precisely on the layers that need to be un-fused before matching — which is what the bug was about. We also verified inside the *running* server container (`docker exec`, not a separate `docker run`) that the module's sha256 and its `packed_modules_mapping` are what we expect, so the mount was live for the process that actually loaded the weights.

**Results.**

| | control (unpatched) | **patched** | historical workaround leg |
|---|---|---|---|
| `grep -c "not found in params_dict"` | **5** | **0** | 0 |
| accept length, code / math / prose | 1.463 / 1.403 / 1.208 | **3.793 / 3.507 / 2.246** | 3.793 / 3.507 / 2.246 |
| throughput tok/s, code / math / prose | 8.92 / 8.49 / 7.33 | **22.08 / 20.57 / 13.26** | 22.31 / 20.67 / 13.30 |

Accept length is measured as generated tokens ÷ the increment of `spec_verify_calls_total` across each benchmark category (the `spec_accept_length` gauge is instantaneous and not used). All runs are 512 tokens, temperature 0, 2 warmup + 3 runs, single stream.

The 5 skipped parameters in the control leg are `model.layers.0.{mlp.gate_proj, mlp.up_proj, k_proj, q_proj, v_proj}.weight` — i.e. exactly the projections behind the two fused layers. Corroborating log line: MTP weight loading goes from `elapsed=2.21 s` to `elapsed=4.90 s` (it now reads five more real tensors), while the *target* model's `mem usage` goes 27.87 GB → 27.46 GB, confirming the patch does not accidentally de-quantize the target.

**The main point: this makes the workaround unnecessary.**

Until now, the only workaround we found for this checkpoint's MTP head was to hand-build a 22.7 KB `--json-model-override-args` payload that re-reads the checkpoint's `quantization_config` and appends the two *fused, fully-qualified* names to `ignore` (they must be full names — a dotted suffix would match and de-quantize every attention layer in the target model). With this PR, it just works with no flags. And the two are not merely "in the same ballpark": on a 20-prompt greedy suite with logprobs, the patched leg and the workaround leg are **token-for-token identical, mean |Δlogprob| = 0.0000 over 4063 common-prefix tokens**. They are the same computation.

**It restores the correct head, not just a fast one.**

- Perplexity on our fixed corpus is **bit-identical** to the plain (non-speculative) baseline: `ppl 3.1434`, `sum_logprob -7144.3242`, `mean_nll 1.14529`, `scored_tokens 6238`. If the change had perturbed the target model's quantization or prefill scoring path, this number would move. It does not.
- Strict greedy gate, patched leg vs a plain baseline at the *same* `mem-fraction-static`: 9/20 prompts token-identical, **zero divergences with a ≥0.5 nats top-2 gap on either side**, drift 0.0042 nats — the same magnitude as plain-vs-plain (0.0038).
- The cleanest read is control vs patched (identical flags, identical memfrac, only the draft head's weights differ): 10/20 identical, drift 0.0043, **0 hard disagreements**, and the median first-divergence position moves *later*, from 49 to 114.5. Raising accept length from 1.46 to 3.79 introduces no new numerical damage.

For confidence in the comparison, our control leg is token-for-token identical to a run we recorded five days earlier on the same setup (20/20, drift 0.0000), so the reproduction is deterministic rather than approximate.

**Caveats, stated plainly.** Single GPU, single checkpoint, one quantization family (compressed-tensors W4A16); no tensor-parallel run. Only one speculative configuration (EAGLE 3/1/4). We applied the production hunk onto the 08-21 nightly rather than building the PR's actual base commit — the context matched verbatim and applied cleanly, but it is a port. We did **not** run the test file this PR adds, and we did **not** investigate the red CI; we validated the runtime behaviour of the one-line production change only.

*Disclosure: this validation was run and written up with AI assistance; the hardware, the runs and the numbers are real and reproducible, and the account owner reviewed the result before posting.*
