# [Fix] deepseek-v4: Complete the MoE output locally when the transport declares no sum group

[Upstream PR](https://github.com/sgl-project/sglang/pull/46365) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #46316.

With an a2a MoE backend (`--moe-a2a-backend flashinfer_megamoe`) DeepSeek-V4 fails while capturing the decode CUDA graph:

```
ValueError: transport finalize owes an undeclared sum group
  sglang/srt/layers/layer_boundary/row_transport.py, in finish
```

Two contracts disagree:

- `MoeTransport.__init__` requires `rows.group is None` whenever an a2a backend is set, meaning the compute already completed the sum.
- The layer still calls the MoE with `leave_output_sum=True`, so the MoE returns a `MoEOutput`. `prepare_output` wraps it in `MoeFinalize`, a `DeferredFinalize` whose `completion_group` is always `MOE_OUTPUT`.

With `rows.group is None` the declared `groups` are empty, so `TransportExit.finish` rejects the deferred finalize.

## Modifications

`MoeTransport.prepare_output` finalizes the `MoEOutput` locally (`complete(reduce=False)`) when the transport declares no sum group **and** `post_experts_output_is_complete()` says the expert outputs are already summed, as they are after the `flashinfer_megamoe` combine. This is the handling the `mlp_reduce_scatter` case already gets, and it matches the plain-tensor branch below it. `reduce=False` because the a2a combine already summed across ranks; reducing again would double-count.

`rows.group is None` alone is not enough. DeepGEMM `megamoe` can fall back to the standard dispatcher, which does not sum across ranks; finalizing that output locally would return partial expert sums without an error, and TP ranks other than 0 would also skip the replicated shared add. That case still reaches the transport's undeclared-sum check.

Why here rather than relaxing the check in `TransportExit.finish` or changing the layer's `leave_output_sum`: the check is an intentional invariant, and everything needed to decide is already in `MoeTransport`.

`test/registered/unit/models/test_deepseek_v4_boundary.py` adds a CPU test: with `flashinfer_megamoe` the output is finalized locally with no all-reduce and the shared output is added on a nonzero TP rank; with `megamoe` it stays a deferred finalize that owes `MOE_OUTPUT`.

- ch-wan · COMMENTED · 2026-10-25T10:58:40Z · [source](https://github.com/sgl-project/sglang/pull/46365#pullrequestreview-5642836509)

**[P2] Avoid silently skipping the MoE reduction for MegaMoE fallback paths**

The fix looks correct for `flashinfer_megamoe`, where the kernel already combines expert outputs. However, `self.rows.group is None` does not necessarily mean the output is fully reduced.

For example, DeepGEMM `megamoe` can fall back to the normal `FusedMoE` path when MegaMoE weights are unavailable (e.g., an unquantized NextN draft). In this case:

1. The transport declares no sum group because the configured A2A backend is `megamoe`.
2. The fallback uses `StandardDispatcher`, which does not perform the distributed expert reduction.
3. This change calls `complete(reduce=False)`, silently returning partial MoE outputs.

Previously, this configuration would fail with the undeclared-sum error. With this PR, it could silently produce incorrect draft activations.

I suggest guarding the local-finalize path with an explicit check that the expert output is already complete (e.g., `post_experts_output_is_complete()`), rather than relying solely on `rows.group is None`. The DeepGEMM fallback should separately declare and perform the required reduction.

Could we also add a regression test covering the incomplete-output fallback? The reported `flashinfer_megamoe` fix itself looks good.
