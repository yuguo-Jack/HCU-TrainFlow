# [Perf] openai: cache per-token text and bytes for logprob outputs

## Motivation

Chat completions with `top_logprobs` spend most of their per-token CPU on the same work again and again. For every output position, `TokenizerManager.detokenize_top_logprobs_tokens` runs `batch_decode` over the k ids. Then `OpenAIServingChat._build_token_logprobs_from_raw` recovers each id's bytes through the byte-level BPE table. Top-k rows repeat the same few thousand ids across positions and requests, and one id always decodes to the same text and the same bytes.

On main, with `top_logprobs=20` and the Qwen2.5 tokenizer, that path costs 70-73 us of CPU per output token: detokenize 25-27 us, building the logprob objects 38-40 us, `model_dump` 10 us. It runs in the HTTP / tokenizer-manager process. With a small model, that caps serving throughput: about 5.5k output tok/s with `top_logprobs=20` vs 16k without on an RTX PRO 6000 (table below).

Main already detokenizes only the new positions of a request (the delta memo mentioned in #10805). This PR caches per token id, so the repeated ids inside and across positions skip the tokenizer.

## Modifications

- `TokenizerManager.detokenize_logprob_tokens`: a per-id text cache (`_logprob_token_text_cache`, created in `init_tokenizer_and_processor`). Only ids not seen before go through `batch_decode`, still one id per sequence, deduplicated within the call. The result is the same `(logprob, id, text)` list.
- `OpenAIServingChat`: the two copies of the bytes logic in `_build_token_logprobs_from_raw` become `_token_bytes(...)`. For byte-level tokenizers it caches `token_id_to_bytes` per id, including `None` for ids that fall back to the text. Non-byte-level tokenizers still encode the display text. Pydantic validation of `TopLogprob` / `ChatCompletionTokenLogprob` is unchanged, so every object still gets its own `bytes` list.
- Both caches are bounded by the vocabulary size.
- Tests (CPU, `base-a-test-cpu`):
  - `test/registered/unit/managers/test_detokenize_logprob_tokens.py`: cached texts equal per-id decoding, including repeats and numpy ids; each id is decoded once across calls; top-logprob rows share the cache; `decode_to_text=False` never touches the tokenizer.
  - `test/registered/unit/entrypoints/openai/test_chat_logprob_token_bytes.py`: on byte-level and non-byte-level fake tokenizers, the output equals recovering bytes from scratch (fragment byte `0xF0`, multi-byte `é`, special id) over two calls, and each byte-level id is converted once.

## Accuracy Tests

Outputs are byte-identical to main. Same GPU (RTX PRO 6000 Blackwell 300 W), `--enable-deterministic-inference`, Qwen/Qwen2.5-0.5B-Instruct, 8 prompts including accented, CJK and emoji text:
- chat completions, non-streaming and streaming, `logprobs=true, top_logprobs=20`, 64 tokens;
- completions, `logprobs=5`, 32 tokens.

The full JSON of all responses (3.2 MB) is identical between main and this PR (`cmp`).

## Speed Tests and Profiling

**Serving.** RTX PRO 6000 Blackwell Server Edition (600 W), 1 GPU, same node, run order main / PR / PR / main.

```
python -m sglang.launch_server --model-path Qwen/Qwen2.5-0.5B-Instruct --mem-fraction-static 0.5
python3 -m sglang.benchmark.serving --backend sglang-oai-chat --dataset-name random \
  --random-input-len 256 --random-output-len 256 --random-range-ratio 1.0 \
  --num-prompts 160 --max-concurrency 32 --seed 1 \
  --extra-request-body '{"logprobs": true, "top_logprobs": 20}'
```

| top_logprobs=20, 4 runs per arm | main | this PR |
|---|---|---|
| output tok/s, median (min-max) | 5,529 (4,756-5,711) | 6,919 (6,482-8,291) (median +25%) |
| median TPOT (ms) | 5.36 | 3.98 |
| P99 E2E latency (ms) | 1,637 | 1,365 |
| P99 TPOT (ms) | 5.60 | 4.39 |

Without logprobs the changed code does not run. Same runs: 16,095 vs 15,800 tok/s median, with overlapping ranges (15,776-16,234 vs 15,525-15,897).

**CPU per output token.** The real functions run over 442 output positions with top-20 rows; warm median of 7 reps; run order main / PR / main / PR.

| us per output token | main | this PR |
|---|---|---|
| detokenize | 25.3 / 27.4 | 2.4 / 2.4 |
| build logprob objects | 38.3 / 40.4 | 20.6 / 21.0 |
| `model_dump` | 9.8 / 10.5 | 9.4 / 10.3 |
| total | 70.5 / 73.0 | 33.0 / 33.2 |

With larger models the GPU takes longer per token, so the relative serving gain shrinks. The CPU saved per output token stays the same.

Related: #24447 and #39221 (batched detokenization across positions) and #41324 (negative byte-level tokenizer verdict cache, open, different file). This PR does not batch across positions, and it does not change the generated text.
