# [Feat] rust-server: Record the tokenizer manager's request metrics in the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/46215) · state: closed · merged: True

## Original PR description

Stacked on the PR that lets an embedding package add keys to `/generate` frames (branch `oss-sync-f87ab65e2f`), which itself sits on the weight-version and media-token-count PR (branch `oss-sync-9f3a425ff9`): this PR's header column and fixture row build on those two, so review the top commit only.

## Motivation

With `--enable-metrics`, Python's `TokenizerManager` records the per-request families (`sglang:num_requests_total`, `sglang:prompt_tokens_total`, `sglang:generation_tokens_total`, `sglang:e2e_request_latency_seconds`, `sglang:time_to_first_token_seconds`, `sglang:inter_token_latency_seconds`, `sglang:time_per_output_token_seconds`, `sglang:num_aborted_requests_total`, the token histograms, ...) through `TokenizerMetricsCollector`. The Rust frontend serves `/metrics` by merging every process's prometheus_client multiprocess files, but it never recorded those families itself, so a Rust-mode server exposed the scheduler's metrics only. This PR records them in the frontend, under the same names, labels and buckets, and writes them where every other reader of the directory already looks.

## Modifications

- **`FrontendMetrics`** (`core/metrics.rs`, new): the families `TokenizerMetricsCollector` registers, with the same names, help text, labels and default buckets. `testdata/tokenizer_metrics.json`, generated from Python by `test_rust_metrics_fixtures.py`, pins them (`families_match_python`). Values are atomics; `flush` writes them as this process's multiprocess files (`counter_rust-<pid>.db`, `histogram_rust-<pid>.db`, named apart from the scheduler's in the same process) in prometheus_client's `MmapedDict` format, atomically through a `.tmp` rename, and only when the bytes changed. A PD prefill server skips TTFT, inter-token latency and TPOT, as Python does.
- **`RequestMetrics`**: one request's progress through `TokenizerManager.collect_metrics`. Started in `CoreHandle::generate` / `generate_batch` with the request's creation time, it observes every runtime item the `CoreCall` receives: TTFT once (a streaming request's first output; a non-streaming request's terminal row less the scheduler's decode latency, with the first output as the fallback), inter-token latency per new token, and on the terminal row the counters, the token histograms, e2e latency and TPOT (`stop`/`length` finishes with more than one token). A call dropped before its terminal item counts as an abort and, if it had output, as a finished request with the tokens seen so far. The health probe passes `log_metrics = false`, as Python's does, and is not counted; the warm-up request is.
- **`MetricsConfig`** (PyO3) now carries the label set, whether `priority` is a label, and the `--bucket-time-to-first-token`, `--bucket-inter-token-latency`, `--bucket-e2e-request-latency`, `--prompt-tokens-buckets` and `--generation-tokens-buckets` overrides (`None` keeps the defaults; a bad list fails startup before anything is spawned). `python/sglang/srt/rust_server/config.py` builds it through a new `tokenizer_metric_labels()` in `metrics_collector.py`, which `TokenizerManager.init_metric_collector_watchdog` now uses too. `MetricsConfig::for_dir` is the test constructor.
- **`/metrics`** flushes the frontend's files before merging the directory (best effort: a directory that cannot be written still serves what is on disk); an interval task (`FLUSH_INTERVAL`, 1 s) keeps them current for another listener, such as a DP rank's offset listener. **`/v1/loads`** observes `sglang:get_loads_duration_seconds`.
- **Batch header**: a new optional `abort_outputs` column, after the decode latencies, marks rows the scheduler ended outside the output stream (`RustServer.push_abort`), which Python's `_handle_abort_req` answers without recording request metrics; the frontend records nothing for them either (`ChunkExtras::abort_output`). An output-stream batch leaves the column empty.
- **`utils/prometheus.rs`**: `encode_entries`, `mmap_key` (Python's `json.dumps(..., sort_keys=True)`, byte for byte) and `write_file`, the write-side counterparts of the existing reader; `encodes_files_and_keys_as_python_does` re-encodes every fixture file to Python's bytes.

Tests:

- `records_request_lifecycles`: the `collect_metrics` sequence, read back through the flushed files and the existing merge/render path: streaming TTFT on the first output, inter-token latency per new token, the finished-request families at the end, a non-streaming request's first token from the terminal row less the scheduler's decode latency, the `priority` label, cached tokens, and a dropped call counted as an abort (and as finished once it had output).
- `aborts_and_prefill_skip_latencies`: an abort finish counts the request but no first-token time, a row ended outside the stream counts nothing, a PD prefill server records no first-token or inter-token latency. `configured_buckets`: overrides replace the defaults and an unsorted list fails startup. `families_match_python`: every recorded family carries Python's name, type, help, label names and default buckets; the three families Python registers that the frontend cannot record (`sglang:startup_time_seconds`, `sglang:startup_cuda_graph_time_seconds`, `sglang:spec_verify_calls_total`, whose data never reaches it) are listed as such.
- `serves_the_merged_directory` now also scrapes a frontend's own file and a frontend whose file cannot be written; `frame_metadata_matches_python` checks the abort row is the only one marked as ended outside the stream.
- Python: `test_rust_metrics_fixtures.py` (the tokenizer fixture matches Python), `test_rust_server_dp_ports.py` (the typed config carries labels and buckets), `test_rust_server_extension.py` (the abort batch carries the marker).
