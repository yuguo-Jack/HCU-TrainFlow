# [Feat] tokenizer: add an opt-in toktier backend (exact per-session repair, chunk-parallel CPU encode)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44373) · state: open · merged: False

## Original PR description

## Motivation

Agent sessions re-send the whole conversation on every turn. The radix cache handles that on the model side, but the tokenizer still encodes the full history on one CPU core, so its share of TTFT grows with the context. On SGLang v0.5.19, a Qwen3-8B chat turn with a cached 100K-token prefix spends 93 to 99 ms of its 145 ms TTFT in the Hugging Face encode. More cores do not shorten a single encode, and a faster serial encoder still re-encodes the whole history every turn.

This PR adds an opt-in backend, `--tokenizer-backend toktier`. It keeps each session's token sequence between turns and re-encodes only the appended text plus a short tail, and it encodes long stateless requests as parallel chunks on several CPU cores. Both paths return exactly the ids the loaded Hugging Face tokenizer returns from scratch, and any request for which the backend cannot establish this goes to that tokenizer unchanged. The design and the measurements are in the RFC and in two papers: [TokTier](https://arxiv.org/abs/2607.29678) (arXiv:2607.29678) and [Delta Tokenizer](https://arxiv.org/abs/2610.19801) (arXiv:2610.19801, which has the SGLang end-to-end results).

Design RFC: https://github.com/sgl-project/sglang/issues/44374 (#44374)

## Modifications

Three hunks in two files, wired like the `fastokens` branch, plus an optional extra and a unit test. Nothing changes unless the option is given.

- `arg_groups/fields/serving.py`: `toktier` as a third `tokenizer_backend` choice.
- `managers/tokenizer_manager.py`: `init_tokenizer_and_processor` wraps the loaded tokenizer with `toktier.integrations.sglang.wrap_tokenizer`, and `_tokenize_one_request` binds the request's `session_id` (else `cache_salt`) around `_tokenize_texts` through a small context manager. Only the tokenizer manager holds the wrapper; `get_tokenizer` is untouched, so the scheduler, TP worker and detokenizer keep a plain tokenizer. The wrapper is duck-typed: `__call__` and `encode` run through toktier, every other attribute is delegated, and a call shape it does not model (text pairs, truncation, `return_token_type_ids`) is delegated whole.
- `pyproject.toml`: an `sglang[toktier]` extra (`toktier>=0.3.0`). It is not added to `all` or `test`, but can be if you prefer.
- `test/registered/unit/managers/test_toktier_backend.py`: a CPU unit test, skipped unless toktier (>= 0.3.0, which ships the adapter) is installed.

How a session is found is a toktier setting, `TOKTIER_SGLANG_SESSION_KEY`, read once when the tokenizer is wrapped. The default, `auto`, uses no key. Before encoding, toktier asks its store whether a text it already encoded is a prefix of the new input, and if one is, it encodes only the appended part. The ids are still exact, SGLang has nothing to manage, and the `session_id` this patch binds is not read in that mode. With `contextvar`, the bound `session_id` (else `cache_salt`) keys the session and the request takes toktier's session route; a request without a key falls back to content lookup, or to the chunked encoder when chunking is on and the text is long enough. With `off`, every encode is stateless. A fourth value, `passthrough`, lets the wrapped tokenizer answer while the wrapper only times the calls, as a measurement aid. The binding in `_tokenize_one_request` is what `contextvar` mode reads; in the other modes it is a cheap no-op.

Chunk-parallel encoding is off by default. It applies to stateless requests (`off` mode, or a keyless request in `contextvar` mode) of at least `TOKTIER_SGLANG_CHUNKED_MIN_CHARS` characters, and `auto` mode is never chunked; toktier's docs suggest a threshold of 256K characters. The chunked encoder's worker count follows `RAYON_NUM_THREADS` in the tokenizer process, so a deployment that wants the parallel speedup should not pin that variable to 1. At 1 the chunks run one after another and the ids are still exact. When chunking is configured, the wrapper starts the chunk workers once while it wraps the tokenizer, so the first long request pays nothing extra. In a local check the first 300K-character request took 8.5 ms after a 0.65 s warm-up inside the wrap, and 621.5 ms when the wrapper was built without the warm-up.

Admission (is this tokenizer one toktier has verified?), fallback to the Hugging Face tokenizer, session state and chunking all live in toktier, so SGLang carries no checking code and supporting a new tokenizer family never touches SGLang. With the backend on, `parallel_prompt_encode` from #41259 sees a wrapped tokenizer and defers to it, so the two do not stack; with it off, nothing changes.

toktier 0.3.0 is on PyPI, so `pip install 'sglang[toktier]'` now resolves and the unit test runs instead of skipping. The PR stays a draft until the RFC has had the maintainers' read. The roadmap in the RFC continues with a worker pool, a GPU route and a Rust-side PR for sgl-router.

## Accuracy Tests

The unit test, run locally against the toktier 0.3.0 release, has 9 tests and all pass. They cover full encodes; a session append under a bound `session_id` with `TOKTIER_SGLANG_SESSION_KEY=contextvar`, where the wrapper's `stats()` shows that both encodes took the session route and the second was served as an append; the chunked path in the same mode, where `stats()` shows the chunked route and a cut text; the default `auto` mode, where the bound key is not read and the second turn is still served as an append found by content; delegated call shapes; a WordPiece tokenizer outside toktier's families passing through; the `session_id` then `cache_salt` key order, with `session_params` yielding no key; and a no-op scope for other backends. Every assertion on ids compares them with the Hugging Face tokenizer.

In the paper's serving runs (v0.5.19, Qwen3-8B and gpt-oss-120b), every prompt-token count SGLang reported equalled the reference, 2,195 and 2,268 independent re-encodes of served text across the two sets of runs found no difference, and 550 greedy completions were identical to the unpatched server's. Outside SGLang, the fast encoder matched the reference on 41.8 billion whole encodes over eleven tokenizers and on 409.6 million web documents split at the backend's cuts under four of them.

## Speed Tests and Profiling

Warm turns on SGLang v0.5.19 with Qwen3-8B (bf16) on an RTX PRO 6000, the HTTP process pinned to 16 cores of an AMD EPYC 9115, and `tokenizers` 0.22.2 as the reference. The full tables are in the RFC and the paper.

| Setting | Reference | toktier |
|---|---|---|
| Median TTFT, 400-character appends, 8K / 32K / 100K tokens | 29.1 / 55.7 / 136.8 ms | 29.2 / 37.5 / 53.7 ms |
| P99 TTFT at 100K tokens | 158.5 ms | 75.0 ms |
| Median TTFT through the chat interface, 100K tokens | 145 ms | 60 ms |
| P99 TTFT, twelve 100K-character sessions, 24 warm turns/s | 995 ms | 103 ms |

The adapter's own call is about 2 ms at 100K tokens, most of it returning the id list. When every long document is new, GPU prefill sets the tail and the two land within 5% of one another.

The gain is in session turns and in long prompts. A session turn re-encodes only what was appended. Through the adapter, a 400-character append to a 100K-character transcript took 1.1 ms in `auto` mode and 1.0 ms in `contextvar` mode. With the same engine driven through toktier's Rust API, a turn took 0.41 ms (Qwen3-8B) and 0.39 ms (Llama-3.1-8B) against 22.3 and 16.7 ms for a from-scratch Hugging Face encode, 54x and 43x. A long prompt outside a session goes through the chunked encoder when chunking is on: a 300K-character document took 6.8 to 8.5 ms with one Rayon thread and 4.9 ms with eight, against 97 to 138 ms for Hugging Face. These are local measurements outside a server, to be read as magnitudes; the Rust session-turn figures are medians over 20 turns and five processes.

The limit is on the serial route and costs speed only; the ids are exact on every route. A prompt that contains an added-token literal, which every prompt rendered from a chat template does, goes whole to the reference engine there. So a chat-templated prompt that is new to the store and below the chunk threshold runs at Hugging Face speed, and the first turn of a session is such a prompt. Through the Rust API, 100K characters of prose wrapped in the chat template took 28.1 ms against 27.5 ms for Qwen3-8B and 18.5 against 17.5 ms for Llama-3.1-8B, while the same text unwrapped took 1.46 and 1.48 ms. That text is ASCII only; on Qwen3-8B, text with non-ASCII characters runs about 4x slower on the fast engine and is still about 10x faster than Hugging Face. The Qwen3-8B session seed of 100K templated characters took 31.0 ms. Later turns of the session and the chunked path are not affected: appends repair only the tail, and the chunked path cuts at the literals and keeps the fast engine for the rest. Segmenting the serial route at added-token literals the same way is on the toktier 0.3.1 roadmap.
