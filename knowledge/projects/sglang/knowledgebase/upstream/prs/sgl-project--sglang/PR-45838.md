# [Fix] [AMD] diffusion: Fix the first-step denoise regression from compiling ENABLE_CK=0 BF16 attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/45838) · state: closed · merged: True

## Original PR description

## Motivation

**What goes wrong**
With `ENABLE_CK=0`, `AITerImpl.forward` calls `aiter.flash_attn_func` inside `torch.compile`. That dispatch opens a Triton config JSON and builds a Triton kernel Dynamo cannot reconstruct. The graph break is inside the DiT block loop, so Dynamo skips `Flux2Transformer2DModel.forward` on the first real step.

**Where it shows up**
gfx1250 already takes `AITerImpl._forward_bf16_eager`, which is `@torch.compiler.disable`, because FlyDSL's Python JIT is not traceable. gfx950 with CK enabled stays on `FlashAttnFunc` and is unchanged. The failure shows up on MI355 when the process sets `ENABLE_CK=0`, including the FLUX.2 720p run: the scored denoise's first step takes 11.8s retracing, then the rest of the steps run at 2.02 it/s. The profiled CK GEMMs and the Triton attention kernel match the previous image.

**Why #44671 did not cover it**
#44671 split the BF16 call into `_forward_bf16` (compiled) and `_forward_bf16_eager` (`@torch.compiler.disable`), and sent only `USE_AITER_GFX1250` to the eager helper. It kept gfx942/gfx950 compiled on the grounds that FlyDSL returns `None` there and the call falls through to the CK `@compile_ops` kernels, which Dynamo records as opaque graph nodes. That holds only while `ENABLE_CK=1`. With `ENABLE_CK=0`, gfx950 falls through FlyDSL into `aiter.ops.triton.attention.mha.flash_attn_func` instead, which Dynamo cannot trace, and `_forward_bf16` still calls it inside the compiled graph.

**How to fix**
Call `_forward_bf16_eager` whenever `ENABLE_CK` is off, so the untraceable Triton attention stays outside Dynamo and the rest of the compiled forward remains.

## Modifications

- `python/sglang/multimodal_gen/runtime/layers/attention/backends/aiter.py`: `AITerImpl.forward` uses the eager BF16 path when `USE_AITER_GFX1250` is true or `aiter.jit.core.ENABLE_CK` is false. `ENABLE_CK=1` on gfx950 still calls `_forward_bf16` from inside the compiled graph.
- `python/sglang/multimodal_gen/test/unit/test_aiter_attention_impl.py`: compile `AITerImpl.forward` and assert `torch.compiler.is_compiling()` is false for gfx1250 and for `ENABLE_CK=0`, and true for the CK path.

## Accuracy Tests

The eager path calls the same `aiter.flash_attn_func` with the same arguments. The unit test checks that the compiled forward returns the attention output unchanged (`torch.testing.assert_close` against the fake kernel's `q.clone()`). No weight, scale, or kernel-config change.

`PYTHONPATH=python python3 -m pytest python/sglang/multimodal_gen/test/unit/test_aiter_attention_impl.py` — 8 passed.

## Benchmarking and Profiling

Kernel time for the profiled FLUX.2 transformer forwards is not the regression. Oct 6 image total kernel time 1.512s, Oct 21 image 1.481s. The two largest CK GEMMs stay on the same tiles (`MT192x320` ~628ms, `MT256x208` ~310ms, 288 calls each).

The denoise wall gap is the first scored step. After that step the Oct 21 run holds 2.02 it/s, in line with the Oct 6 steady rate. This change removes that retrace. An after-fix end-to-end FLUX.2 number is not in this branch yet.
