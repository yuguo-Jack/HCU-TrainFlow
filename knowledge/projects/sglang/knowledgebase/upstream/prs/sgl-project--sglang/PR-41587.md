# feat: add NVFP4 DSA KV cache for TRTLLM-GEN

[Upstream PR](https://github.com/sgl-project/sglang/pull/41587) · state: open · merged: False

## Original PR description

## Motivation

Add a memory-efficient NVFP4 main-attention KV cache for DeepSeek Sparse Attention (DSA) while continuing to use TRTLLM-GEN sparse MLA for attention.

This is the SGLang counterpart of [TensorRT-LLM #17681](https://github.com/NVIDIA/TensorRT-LLM/pull/17681). It is intentionally a P0 implementation: KV is stored persistently as NVFP4, selected sparse rows are gathered/dequantized into reusable compact FP8 scratch, and the existing TRTLLM-GEN sparse MLA kernel is reused.

The independent FP8 DSA indexer cache is unchanged.

## Modifications

- Add a dedicated DSA NVFP4 token pool with separate packed-data and scale pools.
  - 288 bytes packed E2M1 data + 36 bytes E4M3 block-16 scales.
  - **324 bytes/token/layer**, with all 576 MLA dimensions quantized and no residual.
- Quantize/store the main MLA cache as NVFP4 while retaining the existing FP8 indexer.
- Add context compaction and generation gather/dequantization into compact FP8 rows.
- Add a persistent CUDA generation gather adapted from TensorRT-LLM's `nvfp4MlaKvCacheGather` kernel:
  - `cp.async` triple-buffered loads;
  - hardware E2M1 conversion where supported;
  - coalesced FP8 stores;
  - persistent output/index scratch.
- Support CUDA Graph replay for decode, target verification, draft decode, and draft extend.
- Keep prefill eager because context compaction currently uses dynamic `torch.unique`/`index_select` output sizes.
- Apply the DSA MLA scale recipe `100 / (448 * 6)`, independent of checkpoint FP8-KV scales.
- Add fail-fast validation for unsupported backends, architectures, cache/disaggregation modes, and parallel configurations.
- Add unit tests and `benchmark/kernels/attention/bench_dsa_nvfp4_cache.py`.

Current data path:

```text
FP8 DSA indexer Top-K
  -> logical-to-physical cache translation
  -> NVFP4 gather/dequantize
  -> persistent compact FP8 scratch + remapped indices
  -> existing TRTLLM-GEN sparse MLA
```

### Initial support matrix

- CUDA Blackwell SM100/SM103.
- TRTLLM attention backend for prefill and decode.
- DSA main-attention cache only; the indexer remains FP8.
- Eager prefill and CUDA-graphed generation/MTP.
- Unsupported combinations fail explicitly rather than silently falling back.

Native direct-NVFP4 consumption by TRTLLM-GEN and Rubin support are out of scope for this PR.

## Speed Tests and Profiling

Hardware/model: 4x GB300, TP4/DP4, `nvidia/GLM-5.2-NVFP4`, ISL 2,048, OSL 512. Global serving batch is four times the local batch shown below.

### TRTLLM-GEN FP8 vs NVFP4 serving

| Local batch | FP8 median ITL | NVFP4 median ITL | ITL overhead | FP8 output tok/s | NVFP4 output tok/s |
|---:|---:|---:|---:|---:|---:|
| 2 | 14.86 ms | 16.51 ms | 11.1% | 471 | 404 |
| 4 | 17.06 ms | 18.86 ms | 10.6% | 828 | 667 |
| 8 | 20.36 ms | 22.36 ms | 9.8% | 1,397 | 1,054 |
| 16 | 23.64 ms | 26.16 ms | 10.7% | 2,151 | 1,575 |
| 32 | 27.36 ms | 30.51 ms | 11.5% | 3,392 | 2,188 |
| 64 | 32.41 ms | 37.04 ms | 14.3% | 4,981 | 2,802 |
| 128 | 41.80 ms | 49.04 ms | 17.3% | 5,458 | 2,941 |

The output-throughput gap is larger than the steady decode ITL gap because these end-to-end runs include eager context compaction, prefill, and DP prefill waves.

Across 78 layers, the graphed generation gather costs approximately 0.32, 0.48, 0.64, 0.80, 1.44, 2.88, and 5.33 ms/step at local batches 2, 4, 8, 16, 32, 64, and 128 respectively.

### Persistent cache storage

| Cache | Bytes/token/layer |
|---|---:|
| This PR: packed NVFP4 + E4M3 scales | **324** |
| Direct TRTLLM-GEN FP8 | 576 |
| Existing packed FP8/BF16 MLA | 656 |

This reduces persistent main-attention cache storage by 43.8% versus direct FP8.

## Known limitations / follow-ups

- Context compaction is eager and currently dominates the end-to-end throughput loss.
- SGLang still performs separate Q preparation, temporary NVFP4 quantization outputs, and indexed cache scatters; a fused Q preparation/cache append kernel is a follow-up.
- TRTLLM-GEN still consumes compact FP8 scratch rather than NVFP4 directly.
- TBO safety needs additional validation because graph scratch is allocated per backend instance while eager scratch is CUDA-stream keyed.
- Rubin and disaggregated/hierarchical cache configurations are not enabled.
