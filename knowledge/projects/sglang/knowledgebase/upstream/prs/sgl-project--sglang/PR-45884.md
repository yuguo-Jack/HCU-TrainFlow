# [Perf] [NVIDIA] sgl-kernel: Build FlashMLA natively for sm_107a

[Upstream PR](https://github.com/sgl-project/sglang/pull/45884) · state: closed · merged: False

## Original PR description

## Motivation

On CC 10.7 devices, `flashmla_ops` runs the `sm_100f` family binary. Native `sm_107a` codegen is faster for the FlashMLA kernels DeepSeek-V4.1 uses (fused `core_attn` decode/prefill), measured with per-kernel profiles of a serving run. Numbers are available on request.

The pinned CUTLASS (147f567) lists no SM107, so an `sm_107a` build compiles but silently loses features. This happens in three headers:

- `arch/config.h`: the SM100A/F MMA and TMA enables
- `arch/reg_reconfig.h`: `CUDA_CTA_RECONFIG_ACTIVATED`, so `warpgroup_reg_alloc/dealloc` (`setmaxnreg`) become no-ops and the warp-specialized kernels spill
- `arch/grid_dependency_control.h`: `CUTLASS_GDC_ENABLED` (PDL)

## Modifications

- `cmake/flashmla.cmake`: when `nvcc --list-gpu-arch` reports `compute_107`, add `-gencode=arch=compute_107a,code=sm_107a` and patch the fetched CUTLASS headers. This is the same approach as the existing SM103 `config.h` patch.
- `cmake/patch_cutlass_sm107.py`: an idempotent patch of the three headers. Each anchor must match exactly once.

Builds with an nvcc that lacks `compute_107` are unchanged.

## Accuracy Tests

On a CC 10.7 device, with `flashmla_ops` built from this branch's cmake:
- The binary contains `sm_100`, `sm_103a` and `sm_107a` code.
- The `sm_107a` SASS has the same 254 `USETMAXREG` as the `sm_100f` build, and `core_attn` no longer spills.
- `tests/test_flashmla.py` and `tests/test_flashmla_mega.py`: 28 passed.
- DeepSeek-V4.1-Flash served end to end (TP4/EP4, DSpark) without errors.

A model-level accuracy eval is still to do (draft).

## Speed Tests and Profiling

Per-kernel A/B against the `sm_100f` binary on the same device, ABBA-ordered serving profiles: fused `core_attn` decode and prefill are faster. The other FlashMLA kernels are neutral. The end-to-end difference at bs32 128K/1K is within run-to-run noise.

- zcnrex · comment · 2026-10-22T20:14:22Z · [source](https://github.com/sgl-project/sglang/pull/45884#issuecomment-6350317696)

Status update: this PR is on hold, and its current branch does not build.

- Moving FlashMLA's CUTLASS from the 147f567 pin to v4.8.1 (the first release with native SM107 support) needs FlashMLA source changes. FlashMLA@3620b63, which sgl-kernel builds today, does not compile against it: `TMEM::MAX_CAPACITY_BITS` is gone, and the F8F6F4 UMMA op is now a template. Those fixes belong in FlashMLA, not here.
- The DSv4.1 FlashMLA kernels are moving to the `sgl-flash-mla` wheel (#45635, built by #45651's workflow). sgl-project/FlashMLA#20 bumps the fork's CUTLASS to v4.8.1 with the source fixes and adds `sm_107a` when nvcc lists compute_107. The CUDA 13.4 release build then picks that up as is.

Plan: once FlashMLA#20 lands in a released `sgl-flash-mla` and #45635 merges, I'll repurpose this PR to bump the `sgl-flash-mla` pin. I'll drop the in-tree CUTLASS change unless the remaining sgl-kernel FlashMLA paths need it.


- zcnrex · comment · 2026-10-29T20:39:26Z · [source](https://github.com/sgl-project/sglang/pull/45884#issuecomment-6507796508)

Closing: this is superseded.

- #45893 moved every CUDA FlashMLA call to the `sgl-flash-mla` wheel (via `sglang.kernels.ops.attention.flash_mla_interface`), so sgl-kernel's `flashmla_ops` is no longer used on CUDA.
- #45908 removes FlashMLA from the sgl-kernel build, including `cmake/flashmla.cmake`, the file this PR changes.
- The wheel already builds sm_107a: sgl-project/FlashMLA#20 adds `sm_107a` when nvcc reports `compute_107` and moves to CUTLASS 4.8.1, so the header patch isn't needed. The published `sgl-flash-mla==1.0.0` wheels (x86_64 and aarch64) carry native sm_107 SASS in both `cuda.abi3.so` and `_C_legacy.abi3.so`.
