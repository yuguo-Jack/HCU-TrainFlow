# [Perf] spec: Drop the draft_probs buffer from tree_speculative_sampling_target_only

[Upstream PR](https://github.com/sgl-project/sglang/pull/45616) · state: open · merged: False

## Original PR description

## Motivation

Part of #12562, which lists "Remove passing argument `draft_probs`".

The target-only tree verify kernel never reads a real draft distribution. Every caller passes `torch.zeros_like(target_probs)`, a `[bs, num_draft_tokens, vocab]` fp32 buffer allocated and zeroed on every verify step. The kernel writes the target probability of each rejected token into it and reads it back to sample `relu(q - p)`. At bs 32, 16 draft tokens and a 152064 vocab that buffer is 297 MiB per step.

#15687 also removed the argument. It added a second kernel, `tree_speculative_sampling_target_only_rejmask`, dispatched for topk <= 4 with a fixed list of four rejected ids, and kept the zero buffer inside the original op for larger topk. Its residual sum was accumulated per thread before a single block reduction, a different floating-point order from the original kernel. Its author closed it on 2026-10-07 without a maintainer review, and the kernels have since moved to JIT (#40033) and the platform dispatch to `kernels/ops` (#45504). Earlier Python-only attempts (#28581, #44125) were closed as well.

This PR changes the existing kernel in place for every topk, keeps its reduction order, and checks the outputs bit for bit against `main`.

## Modifications

- `kernels/jit/include/sgl_kernel/speculative/sampling.cuh`: the kernel drops `draft_probs`. Thread 0 appends each rejected id to a list in shared memory, and the list resets when a token is accepted, so at the end it holds exactly the children rejected at the last accepted node (at most `num_draft_tokens` entries). The residual is 0 at those ids and `max(q, 0)` everywhere else. Element by element that is the value `relu(q - p)` had with the zero buffer, NaN and negative inputs included. Both residual passes keep the original `BlockReduce` and `DeviceSamplingFromProb` calls on those values, so the sums and the sampled id come out identical. In those passes only the threads whose vocab slice holds a rejected id read the list.
- `kernels/jit/csrc/speculative/sampling.cuh`: dynamic shared memory is `sizeof(SamplingTempStorage)` (2080 B at 1024 threads) plus 4 B per draft token. The launcher opts in only above 48 KiB, which takes about 11.8k draft tokens.
- MUSA (`kernels/aot`): `setup_musa.py` builds the same device kernel from `kernels/jit/include` and launches it with a `void*` argument array. The launcher, the host function, the `sgl_kernel_ops.h` declaration, the schema in `common_extension_musa.cc` and `sgl_kernel/speculative.py` drop `draft_probs`, and the launcher sizes shared memory the same way. With only the JIT side changed, these sources built for CUDA fail the first kernel test with `CUDA error: misaligned address`.
- `kernels/ops/speculative/verify_sampling.py`: the NPU kernel (`sgl_kernel_npu`) still takes `draft_probs`, so its entry is wrapped to allocate the zero buffer itself. CUDA and MUSA resolve to their kernels directly.
- `srt/speculative/eagle_utils.py`: `eagle_sample` binds `verify_input.draft_probs` to the rejection sampler with `functools.partial`. The target-only path no longer allocates the buffer.
- `srt/speculative/dflash_utils.py`: DFlash sampling verify no longer allocates the buffer.
- `test_speculative_sampling.py`: the existing tests drop `draft_probs`, and `test_residual_masks_only_tokens_rejected_at_last_accepted_node` pins the residual contract: siblings rejected at the sampled node get no mass, and a token rejected at an ancestor keeps its mass.

## Speed Tests and Profiling

GPU: one NVIDIA GeForce RTX 4060 Ti 8 GB (sm_89, 34 SMs, 32 MiB L2, driver 610.88) that also drives a desktop. torch 2.14.1+cu130, `deterministic=True`, both thresholds 1.0.

Method. One process loads both builds: the `main` kernel straight from its JIT cache through `tvm_ffi.load_module`, and this PR's through `sglang.kernels.ops.speculative.sampling`. Inputs come from a fixed seed, and the two builds' outputs are compared before anything is timed (identical in all 36 configs). Every timed call sits between CUDA events, after a `torch.cuda._sleep` that keeps the GPU busy while the host enqueues the call, so the interval is GPU time without launch gaps. Phase 1 alternates old step and new step every iteration with the order rotated; phase 2 does the same for old kernel and new step. 50 warmup and 500 timed iterations per variant. topk 1 uses a chain (depth `ndt - 1`); topk 4 uses a breadth-first 4-ary tree, which puts the most siblings under one node and is the worst case for the mask. Draft tokens get random logit boosts so verification accepts some of them.

- old step: `torch.zeros_like(target_probs)` plus the `main` kernel, which is what `eagle_sample` and DFlash verify ran on every verify step
- old kernel: the `main` kernel alone, with one zero buffer reused across calls
- new step: this PR, the whole step

- The verify step is 1.1x to 26.4x faster at p50. The gain grows with `bs * num_draft_tokens * vocab`, because the old step's time is mostly the memset of the zero buffer.
- Against the old kernel alone, the new kernel's p50 is 2.5% to 57% lower in all 36 configs. The old kernel read the matching `draft_probs` row in both residual passes; the new one reads only the target row. The gap is largest at bs 32 with vocab 152064 (37% to 57%), the configs with the most `draft_probs` bytes to read.
- Memory: `torch.cuda.max_memory_allocated` grew by the buffer size for every old step (the caching allocator rounded 5 of the 36 sizes up, by at most 2.4%) and by 0 bytes for every new step. That is 0.5 MiB to 297 MiB per verify step in this grid. The benchmark process peaked at 598 MiB reserved.

Not measured:
- End-to-end serving (throughput, latency, acceptance length) with a real EAGLE, NGRAM or DFlash model.
- Any other GPU, including datacenter parts.
- MUSA and NPU hardware. The MUSA sources were only compiled and run for CUDA, and the NPU path keeps its zero buffer.
- `DFlashWorkerV2.prewarm_sampling` sizes its headroom by rehearsing this code path, so its measured peak should drop by the buffer size with no code change. This is an inference; I did not run it.
