# [Mamba] Store hicache checkpoints without a GPU slot

[Upstream PR](https://github.com/sgl-project/sglang/pull/44718) · state: open · merged: False

## Original PR description

## Motivation

Mamba radix checkpoints currently donate a GPU slot for every matched prefix. On a Kimi-K3 c=48 recipe that slot floor is `max_running_requests * 5` (480), so the GPU mamba pool stays large even when ReplaySSM already covers live verify and the checkpoint itself only needs to be reloaded from host.

## Modifications

Add `--enable-mamba-host-only-checkpoint` (default off). The flag requires `--enable-hierarchical-cache` and rejects `--enable-int8-mamba-checkpoint`.

When it is on:

- A finished request copies its flushed state into the hicache host pool and does not keep or donate a GPU slot.
- The mamba ratio drops to the live request plus ping-pong tracking slots. With the extra buffer and overlap that is 3 (1 active + 2 ping-pong), so a 96-wide decode pool is 288 slots. `no_buffer` with page size 1 is the path that returns 1.
- The Rust insert accepts `mamba_host_value` without a donated `mamba_value`.
- Under HiCache, a host checkpoint still counts as a device-prefix match, so the Full KV indices of that node stay reachable. Load-back still runs when the host hit length is non-zero.

The flag-off path is unchanged: the same ratio, the same donated GPU slot, and a host-only node does not advance `last_device_node`.

## Accuracy Tests

- `test/registered/unit/mem_cache/test_mamba_donated_alloc_ratio.py`: host-only ratio is 1 / 2 / 3 for no-buffer, lazy, and overlap. Flag-off cases stay at the previous ratios.
- `sglang-radix-tree` mamba component tests, including host-only insert with no GPU slot and the HiCache device-prefix match.

## Speed Tests and Profiling

Not in this PR. A c=48 AgentX run with the flag, `max-mamba-cache-size 288`, and `mem-fraction-static 0.87` is in progress separately.
