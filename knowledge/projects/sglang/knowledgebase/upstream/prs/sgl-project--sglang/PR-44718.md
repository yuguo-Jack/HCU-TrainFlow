# [Feat] [AMD] mamba: Store hicache checkpoints without a GPU slot

[Upstream PR](https://github.com/sgl-project/sglang/pull/44718) · state: closed · merged: True

## Original PR description

## Motivation

Mamba radix checkpoints donate a GPU slot for every matched prefix. On a Kimi-K3 c=48 recipe that floor is `max_running_requests * 5` (480), so the GPU mamba pool stays large even when the checkpoint only needs to be reloaded from host.

## Modifications

Set `SGLANG_OPT_MAMBA_HOST_ONLY_CHECKPOINT=1` (default off). It requires `--enable-hierarchical-cache` and rejects `--enable-int8-mamba-checkpoint`. This is an environment variable, not a server argument.

With the variable unset, the server keeps the previous path: the same mamba ratio, the same donated GPU slot, the KDA ReplaySSM ring indexed by the mamba slot, a single in-flight load-back receipt, and a device match that follows GPU mamba slots. The new `InsertParams.allow_missing_mamba` bit stays false, so an insert that omits mamba still panics.

With the variable set:

- A finished request copies its flushed state into the hicache host pool and does not keep or donate a GPU slot.
- The mamba ratio drops to the live request plus the ping-pong tracking slots the extra-buffer kernel still writes. With extra buffer and overlap that is 3 (1 active + 2 ping-pong), so a 96-wide decode pool is 288 slots. `no_buffer` with page size 1 returns 1.
- The KDA ReplaySSM ring covers live requests (`max_running_requests // attn_dp + 1`) instead of every mamba slot. Padding rows are -1.
- The Rust insert accepts `mamba_host_value` without a donated `mamba_value`. A repeat insert that already found a checkpoint may omit both values; that permission is on the insert params and applies only to that insert.
- Under HiCache, a host checkpoint still counts as a device-prefix match, so the Full KV indices in front of it stay reachable. Load-back copies into the request slot and leaves the node on the host tier.

## Memory

Per-rank GPU, MI355, Kimi-K3 c=48, 96 running requests, page size 32, extra buffer, overlap, DCP 8, ReplaySSM on. The env-on pool is the size the ratio allows; `max-mamba-cache-size` has to be lowered with it. Leaving the pool at 480 keeps the 13 GB allocation and only raises the running-request cap.

| | Env off | Env on |
| --- | ---: | ---: |
| Mamba conv + ssm | 13.00 GB (480 slots, ratio 5) | 7.81 GB (288 slots, ratio 3) |
| KDA ReplaySSM ring | 9.14 GB (one row per mamba slot) | 1.84 GB (97 rows, one per live request) |

Env off is the earlier 0.87 log: conv 0.85 GB + ssm 12.15 GB, ring 9.14 GB. Env on conv + ssm is `ci355_ix_20261015_213315_c20e` (`max-mamba-cache-size 288`): conv 0.51 GB + ssm 7.30 GB. The same class of boot with `request_ring=True` keeps that 7.81 GB pool and sizes the ring at 97 rows (d = k = rawv = rawk = 0.306 GB, g = 0.613 GB, beta = 0.005 GB). The intermediate conv window stays 0.86 GB in both measurements. The checkpoint itself sits in the existing hicache host pool.
