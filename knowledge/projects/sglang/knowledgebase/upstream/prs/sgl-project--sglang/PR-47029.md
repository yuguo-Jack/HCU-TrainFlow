# [Fix] attention: Compute extend attention KV offsets in int64

[Upstream PR](https://github.com/sgl-project/sglang/pull/47029) · state: closed · merged: True

## Original PR description

## Motivation

`_fwd_kernel` and `_fwd_kernel_unified` in `extend_attention.py` load a KV slot from `kv_indices` and multiply it by the KV buffer stride in the index dtype. With int32 `kv_indices` the product wraps once `slot >= 2^31 / stride`, which is 2,097,152 tokens for 8 KV heads x 128 head dim. The kernel then faults or, when the wrapped address is mapped, silently reads the wrong KV.

The aiter backend's CUDA-graph `cuda_graph_kv_indices` is int32 and is used as-is by the legacy target-verify path (NGRAM, EAGLE with topk > 1), so a long-running aiter server whose KV pool exceeds that size eventually crashes in `_fwd_kernel`. Spec-decode `kv_indices` built in `eagle_info.py` / `ngram_info.py` are also int32. The triton backend's own buffers are int64 and are not affected.

## Modifications

- `extend_attention.py`: cast the loaded slot to int64 before the address math in `_fwd_kernel` and `_fwd_kernel_unified`. This covers the `PAGE_SIZE == 1` and paged branches and any caller dtype.
- `test_triton_attention_kernels.py`: add `test_extend_attention_int32_kv_indices_above_2g`, which runs both kernels with int32 slots above `2^31 / stride` against the same data at low slots. The slots sit just below `2^32 / stride` so a wrapped offset reads zero rows in front of the buffer rather than faulting (~8.6 GB). On main both subtests fail (max abs diff 1.09 / 1.04); with this PR they pass.

## Accuracy Tests

Only addressing changes: for slots below 2^31 / stride the int64 cast leaves every offset unchanged, so outputs are unchanged.

MI355X (gfx950), torch 2.11.0+rocm10.0.0, triton 3.8.0, aiter `285579b62`, `SGLANG_USE_AITER=1`, CUDA graphs on, `amd/Llama-3.1-8B-Instruct-FP8-KV` with `--kv-cache-dtype fp8_e4m3 --speculative-algorithm NGRAM`; the KV pool is 3,503,271 tokens. Every fault below is a `Memory Fault` in `_fwd_kernel` with grid `[24576, 32, 1]`:

- main `7fe5b127e4`, GSM8K (1319 questions, `--max-tokens 4096`): faults between questions 430 and 485 in three runs, when cumulative allocated slots reach about 2.1M.
- With the KV-scale fix (#47030) applied, `bench_serving` random 512 in / 4096 out, 600 prompts, concurrency 48: faults after 265 s. The same run on the triton backend completes.
- This PR, the same `bench_serving` run on aiter: all 600 requests complete (2.46M output tokens, 1792 s) without a fault.

Unit tests: `test_triton_attention_kernels.py` and `test_gemma4_unified_swa_virtual_ids.py` pass (18 tests, with `SGLANG_IS_IN_CI_AMD=1`).

MI325X (gfx942), torch 2.11.0+rocm10.0.0, aiter `285579b62`, main `cb55d77d37` with this patch: the new test fails on main and passes here (the two gfx950-only tests skip). NVIDIA is not tested.
