# [Spec] Plan FlashInfer EAGLE verify and draft from host-known lengths (SGLANG_ENABLE_SYNC_FREE_SPEC_PLAN)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42195) · state: closed · merged: False

## Original PR description

## Motivation

With FlashInfer attention and CUDA graphs, every EAGLE/NEXTN target-verify replay calls `BatchPrefillWithPagedKVCacheWrapper.plan` ([flashinfer_backend.py#L2302](https://github.com/sgl-project/sglang/blob/67eab57057062e05eabd4227a943b1aa777e563f/python/sglang/srt/layers/attention/flashinfer_backend.py#L2302)). In FlashInfer 0.7.0.post1, `plan()` blocks on the GPU in the places below, and so does the multi-step draft:

- `plan()` copies `qo_indptr`, `paged_kv_indptr` and `paged_kv_last_page_len` to the host ([prefill.py#L2526-L2538](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/flashinfer/prefill.py#L2526-L2538)).
- It sizes the packed custom mask with `.item()` ([packbits.py#L132](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/flashinfer/quantization/packbits.py#L132)).
- It writes `mask_indptr[0] = 0` into a device tensor, which is a blocking pageable copy ([prefill.py#L1599](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/flashinfer/prefill.py#L1599)).
- The multi-step draft copies its `kv_indptr` rows back with `.cpu()` ([#L2420](https://github.com/sgl-project/sglang/blob/67eab57057062e05eabd4227a943b1aa777e563f/python/sglang/srt/layers/attention/flashinfer_backend.py#L2420)).

Each of these blocks the scheduler until the GPU has finished the draft work queued before it. The host planning that follows then runs while the GPU idles. Every value they return is a function of `seq_lens_cpu`, which the overlap scheduler already holds. The DFLASH verify already avoids this by swapping in `fast_prefill_plan` ([#L830-L855](https://github.com/sgl-project/sglang/blob/67eab57057062e05eabd4227a943b1aa777e563f/python/sglang/srt/layers/attention/flashinfer_backend.py#L830-L855)). The EAGLE verify cannot use it as is, because it plans with a custom mask.

## Modifications

Everything is behind `SGLANG_ENABLE_SYNC_FREE_SPEC_PLAN=1`, off by default. With the flag off, none of the new code runs.

- `fast_verify_plan`, in the new `layers/attention/flashinfer_sync_free_plan.py`, follows FlashInfer 0.7.0.post1's `plan()` for this case but takes its lengths and offsets from the host. `FlashInferAttnBackend` installs it on the target-verify CUDA-graph wrappers, as the DFLASH branch does.
- The multi-step draft takes its `kv_indptr` rows from the host on replay.
- Each sync-free plan first waits on an event from the same wrapper's previous plan. Without that wait, a plan could overwrite FlashInfer's pinned buffer before the previous copy from it has run. With the flag on, the wait also wraps the plans that were already sync-free, including plain decode on a server without speculative decoding.
- A new GPU unit test compares `fast_verify_plan` with stock `plan()` bit for bit.

<details>
<summary>Details</summary>

- New module `layers/attention/flashinfer_sync_free_plan.py`:
  - `fast_verify_plan` follows FlashInfer 0.7.0.post1's `plan()` for the fa2 backend in CUDA-graph mode with a custom mask. It takes the qo/kv layout, kv lengths and mask segment offsets from the host. The mask's bit and byte offsets, which `plan()` computes on the device, are uploaded in one pinned copy.
  - `eagle_verify_plan_host_inputs` builds those inputs from `seq_lens_cpu` the way `EagleVerifyInput.generate_attn_arg_prefill` lays them out (page size 1, as the FlashInfer backend plans).
  - `draft_kv_indptr_host` builds the rows `generate_draft_decode_kv_indices` writes, including the draft window cap and CUDA-graph padding rows.
- `FlashInferAttnBackend` installs `fast_verify_plan` after the capture-time `plan()`, for EAGLE verify on fa2 with no dispatch reason. Capture-time plans are unchanged.
- Why the wait: FlashInfer's `plan()` writes a per-wrapper pinned buffer and copies it with `cudaMemcpyAsync` without waiting. The removed reads used to keep the next plan from overwriting that buffer before the copy ran. So each sync-free plan now first waits on an event recorded after the same wrapper's previous plan, whose copy was issued a cycle earlier. The plans that were already sync-free and now also get this wait are the `fast_prefill_plan` replays (the EAGLE draft extend and the DFLASH verify) and every `fast_decode_plan` replay.
- `test/registered/unit/spec/test_fast_verify_plan.py` (GPU):
  - `fast_verify_plan` against stock `plan()` on a captured wrapper at batch 1, 3 and 16, with random lengths, padding rows and random masks. It compares `_plan_info`, the pinned plan bytes, every device buffer the graph reads and the replayed attention output, bit for bit.
  - A negative case: host lengths one token short must change the plan.
  - `draft_kv_indptr_host` against `generate_draft_decode_kv_indices` for top-k 1 and 2, with and without a draft window.

</details>

## Accuracy Tests

All on one GH200 with Qwen3.5-4B and NEXTN; the setup is in the details below.

- Unit tests on this branch: `test_fast_verify_plan.py` and the existing `test_fast_prefill_plan.py`, 5 passed.
- Greedy output equality, 64 prompts at batch sizes 1, 8 and 32 (192 requests). Main and this PR with the flag gave identical output tokens, verify-step counts and accepted-draft histograms on all 192. Two main servers against each other, as a control, also gave 192/192, and so did this PR with the flag off against main.
- Logprobs were not compared, and the timed runs below were not compared for outputs.

## Speed Tests and Profiling

With the flag, per-user output rate is 1.066-1.088 times main's at concurrency 1 to 32 (pooled means). Every main/PR pair within a session is between 1.028 and 1.104. Acceptance length is the same in every launch to within 0.004 (3.28 at concurrency 1), so the gain is not from accepting more drafts. Concurrencies above 32 were not measured.

<details>
<summary>Setup and results</summary>

Two exclusive sessions, each with one server launch per run. The first session ran main, PR, PR, main. The second ran main, PR, PR, main, then the PR with the flag off. Workload: `aiperf` in closed-loop concurrency mode with chat, code and math prompts (one third each) averaging 94 input tokens, 512 output tokens per request (`ignore_eos`), streaming. Each concurrency level ran 64 requests at c = 1-8, 128 at c = 16 and 256 at c = 32, after max(2, c) warmup requests and a prefix-cache flush. Other processes used at most 0.43 CPU cores on average during any measured point (peak 1.6).

How the numbers below are computed (fixed before the second session ran):
- Headline: for each concurrency, the lowest and highest PR/main ratio of per-user output rate over the main/PR pairs within each session (2 x 2 per session, 8 in total).
- Secondary: the ratio of the mean over all four PR launches to the mean over all four main launches.
- Launch check: a launch whose median TTFT is at least 3 ms above the median of the same setting's other launches at every concurrency is flagged as a slow launch. Ratios are also given without flagged launches.

Per-user output rate (tokens/s per request, including time to first token):

Wall time per decode pass falls by 6.5-9.1% at c = 1 and 2.2-8.4% at c = 32 over the same pairs. This is the point's span divided by the server's decode-pass count, so it includes host gaps.

The main launches vary more than the PR launches: 2.4-5.2% between the fastest and slowest at each concurrency, against 1.1-3.2%. In the first session, main's second launch, which ran last, was slower than its first at every concurrency: per-user rate 2.4-5.0% lower and median TTFT 4.0-4.5 ms higher. Other processes' CPU load was as low as in the other launches, and the SM clock read 1,980 MHz in every snapshot taken during a measured point. With all four main launches pooled, that launch's median TTFT was 1.8-2.8 ms above the median of the other three, below the 3 ms flag, and the first session's first main launch was the fastest of the four. Against that first main launch alone, the first session's PR launches were 7.1% faster at c = 1, 5.3% at c = 8 and 3.0% at c = 32.

The flag-off launch ran last in the second session. Its per-user rate was between 0.7% below and 0.8% above the slower of that session's two main launches at every concurrency, and 0.3-2.1% below the faster one.

## Not tested

- Only the configuration above was served: Qwen3.5-4B, NEXTN with top-k 1, BF16 KV cache, one GH200. The unit test covers top-k 2 draft rows and random mask layouts, but no top-k > 1 tree was served.
- DFLASH with the flag, and a server without speculative decoding with the flag. The flag adds the plan-ordering wait to their existing sync-free plans (above); neither was run.
- Other FlashInfer versions. `fast_verify_plan` mirrors 0.7.0.post1's `plan()`, the version `pyproject.toml` pins, and reads its private wrapper fields. A FlashInfer upgrade needs it rechecked; the unit test compares the full plan state and would fail on a mismatch.
- The NVFP4 KV path. `fast_verify_plan` applies `plan()`'s NVFP4 split-KV rule, but I have no hardware where that rule is active (SM120/121).
- Multi-GPU (TP, PP, DP attention).
