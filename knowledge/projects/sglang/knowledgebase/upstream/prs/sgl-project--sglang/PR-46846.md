# [Feat] [AMD] mori: Overlap shared experts with MORI EPv2 AsyncLL dispatch under SBO

[Upstream PR](https://github.com/sgl-project/sglang/pull/46846) · state: open · merged: False

## Original PR description

## Motivation

Stacked on #44492 (MORI EPv2 AsyncLL + DSV4 prefill TBO with DSpark). **Only the last commit is new here**; review it after #44492, which this PR will be rebased onto once merged.

Two-batch overlap needs a batch large enough to split, so it fits prefill. Decode batches are small and DSV4 has no decode TBO strategy. Single-batch overlap (`--enable-single-batch-overlap`) does not split the batch: on AMD it runs the shared experts in the dispatcher's dispatch hook, between `dispatch_a` and `dispatch_b`. This PR makes that overlap real for MORI EPv2 on the AsyncLL kernels.

## Modifications

| Commit | Change |
|---|---|
| `[AMD] MORI EPv2 AsyncLL: let SBO run shared experts between send and receive` | `moriep.py`: DSV4 MoE already goes through `DeepseekV2MoE.forward_deepep`, whose SBO path calls the shared experts from `MoriEPDispatcher`'s dispatch hook. With `--deepep-mode low_latency` the AsyncLL send is in `dispatch_a` and the receive in `dispatch_b`, so the shared experts overlap the transfer without changes. With `normal` + `MORI_ENABLE_SDMA=1` the receive followed the send inside `dispatch_a`, so the hook ran after the transfer. Under SBO without TBO, that path now leaves the receive to `dispatch_b` as well. |

On AMD only `SboFlags.enable_dispatch_shared_one_stream_overlap` applies (the combine / down-GEMM overlaps need DeepGEMM or CuTe DSL). Native EPv2 without AsyncLL finishes the whole transfer in `dispatch_a`, so single-stream SBO has nothing to overlap there; that path is unchanged.

## Accuracy Tests

DeepSeek-V4-Flash, gfx1250, EP4 single node (SPX), DSpark, DP attention, CUDA-graph decode, `SGLANG_MORI_RECV_BOUND=1`, `--chunked-prefill-size 32768`, no TBO. gsm8k 200 questions: 0.950 with SBO (both transports) vs 0.935–0.965 without, within run-to-run noise.

## Benchmarking and Profiling

Same setup. Decode load: 256 requests, ISL 1024 / OSL 512, concurrency 64. Prefill load: 384 requests, ISL 8192 / OSL 16, concurrency 128.

| AsyncLL transport | SBO | decode output tok/s | decode mean ITL (ms) | decode mean TTFT (ms) | prefill input tok/s |
|---|---|---|---|---|---|
| `low_latency` + SDMA | off (2 runs) | 1761 / 1799 | 29.6 / 29.5 | 1242 / 1241 | 20111 / 20095 |
| `low_latency` + SDMA | on | 1830 | 29.0 | 1205 | 20462 |
| `normal` + SDMA | off | 1766 (other node) | 29.5 | 1212 | 19770 |
| `normal` + SDMA | on (this PR) | 1847 | 28.7 | 1192 | 20711 |

Run-to-run noise on one node is about 2% (1761 vs 1799), so the +2–4% decode gain is preliminary; the `normal` + SDMA pair was measured on two nodes.

**Draft:** pending repeated same-node pairs, a profile of how much receive wait the shared experts hide, TBO + SBO together, and larger EP (EP8 / EP16 across a UALink vPOD), where transfers are longer.
