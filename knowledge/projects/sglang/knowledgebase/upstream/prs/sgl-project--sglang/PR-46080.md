# [Perf] DFLASH: Verify top-k sampled batches on the all-gathered top-k support (opt-in)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46080) · state: open · merged: False

## Original PR description

## Motivation

With TP > 1 and a softcapped lm_head, DFLASH verify finishes the logits all-gather in the worker. For a sampled batch it then:

- all-gathers the full fp32 logits of every verify row, `[bs * block, vocab]`;
- softcaps them and runs a radix top-k over the whole vocabulary;
- scatters the target p and the draft selector's q into vocab-sized tensors;
- runs the chain sampler, which scans the whole vocabulary.

When the requests sample with a top-k, as many generation configs do by default, only the top-k tokens of a row carry target mass. Almost all of that work reads and writes zeros, and the gather moves the largest tensor of the step across the TP group.

With this PR, such a batch is verified on the top-k support alone:

- each rank takes the top `next_power_of_2(max_top_k + 16)` logits of its vocab shard. The 16 spare slots hold logits tied with the k-th one;
- the ranks all-gather those (value, id) pairs instead of their shards. At TP8 and a 202K vocabulary, that is 1 KB per row from each rank instead of 101 KB;
- one Triton kernel softcaps and merges the candidates into each row's exact top-k and argmax. It uses the softcap formula of the dense gather, so the kept values equal the dense row's bit for bit;
- one Triton kernel runs the chain accept and the residual resample on that support. It makes the dense path's two uniform draws in the same order. It adapts the top-k chain sampler of #41283 to DFLASH's exactly-k top-k and sparse q.

A batch that the support cannot reproduce keeps the dense path. That covers max top_k above 64 (top_k -1 included), top-p, min-p, penalties, logit bias, a custom logit processor, grammar, logprobs, sampling-mask capture, block verification and padded vocab shards. Greedy batches already take `deferred_argmax`.

Up to fp32 rounding, only two cases can differ from the dense path, and both stay exact top-k sampling:

- a tie at rank k keeps the lowest ids, where `torch.topk` breaks it arbitrarily;
- if q >= p over the whole support, the bonus is sampled from p. The dense kernel emits the last vocabulary id there.

With the DFlash2 selector draft, the kernels compile at startup, outside any collective, for top_k 64, and the two support kernels for top_k 49-64. Any other top_k or draft compiles on its first sampled verify.

#41916 changes top-k/top-p filtering only for batches that use top-p, which keep the dense path here, so this PR stays exact with or without it. Related open PRs on the verify sampling path: #41957, #43052, #44668.

## How to enable

```bash
SGLANG_OPT_DFLASH_SPARSE_VERIFY=1   # default off
```

Requires:
- `--speculative-algorithm DFLASH` with a draft that samples its proposals, such as the DFlash2 candidate selector;
- CUDA and TP > 1;
- a target with `final_logit_softcapping`, so that verify defers the logits gather;
- requests sampled with top_k <= 64.

Other batches are unchanged.

## Tests

`test/registered/kernels/ops/speculative/test_dflash_sparse_verify.py` (new, CUDA). It runs through the worker's own support and accept methods, at a 202,048 vocab, with TP 1/2/4/8 simulated by a rank-major all-gather. It checks:
- the merged support equals `torch.topk` of the full softcapped rows, and its argmax equals `torch.argmax`;
- accept length, bonus token and the RNG stream after verify equal the dense selector verify's, at bs 1-4 and temperatures 0.6/1.0/1.3 with top_k 64;
- the same on peaked rows that accept whole blocks, so the bonus comes from the last row;
- the same on a mixed top_k `[64, 20, 1, 64]` batch with a greedy row.

`test/registered/unit/spec/test_dflash_logits.py`, 2 new CPU tests:
- every unsupported batch keeps the dense gather, including top_k 65, `[64, 128]`, top_k -1 and the flag off;
- a supported batch packs its shard with rank-major global ids and gathers `world * rows` rows.

[by Claude Code] **Severity: functional | Confidence: High**

**Issue**

`_sparse_verify` does not check that the target has a final logit softcap. With `SGLANG_OPT_DFLASH_SPARSE_VERIFY=1`, a target without softcap, a selector draft, and TP > 1, `prewarm_sampling` calls `_prewarm_sparse_verify`. It passes `final_logit_softcapping=None` to `merge_shard_topk` (line 873). Triton turns a `None` argument into a constexpr, so `x = x / softcap` in `_merge_support_kernel` fails to compile and the scheduler fails at startup. The startup log also says sparse verify is enabled, but verify never defers the gather for such a target.

**Fix**

Add `and bool(self._target_logits_processor.final_logit_softcapping)` to this condition. That matches the softcap check in `LogitsProcessor._can_gather_softcap_fused`.
