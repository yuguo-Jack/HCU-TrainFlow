# [Fix] tokenizer: Offload regular tokenization off the event loop

[Upstream PR](https://github.com/sgl-project/sglang/pull/44502) · state: open · merged: False

## Original PR description

## Motivation

Production incident follow-up to #39771 / #30770, and a rebased + de-scoped
takeover of #30771 (stalled since 2026-09-08; its `serving_base` portion was
superseded by #39771, its `tokenizer_manager` portion is still needed —see below).

### Production impact (v0.5.21, 8-node fleet)

We run 8 identical serving nodes (8x NVIDIA H20 141GB each, one `--tp-size 8`
pod per node) serving a hybrid linear-attention MoE model (GLM-5.3-Flash, fp8,
`--context-length 262144`, `--max-running-requests 8`, hierarchical cache with
mooncake storage backend, hostNetwork, Kubernetes). Traffic is long-context
agentic (prompts regularly 100k-250k tokens with very large `messages` lists),
fronted by an L7 gateway that fans each request out to all replicas
concurrently. Kubelet liveness/readiness probe `/v1/models` (30s timeout,
failureThreshold 32).

Recurring incident: **whole pods on multiple nodes stop answering all HTTP
endpoints within the same minute**; liveness probes time out continuously;
kubelet restarts the containers ~16 minutes later. Example wave (2026-10-15):
4 of 8 nodes frozen at T+0, killed at T+16min, ~13 min weight reload each.

py-spy on three frozen pods (identical stacks) showed the uvicorn event-loop
thread GIL-spinning inside the sandboxed jinja chat-template render:

```
Thread 1 (active+gil): "MainThread"
    getattr (jinja2/sandbox.py:319)
    macro (<template>:311)
    macro (<template>:337)
    render_jinja_template (transformers/utils/chat_template_utils.py:581)
    apply_chat_template (transformers/tokenization_utils_base.py:3107)
    _render_and_encode_chat_template (openai/serving_chat.py:1804)
    _process_messages (openai/serving_chat.py:1433)
    _convert_to_internal_request (openai/serving_chat.py:1211)
    handle_request (openai/serving_base.py:92)      # v0.5.21: inline call
```

A single request cannot explain a 16-minute freeze: one request with 50,000
messages renders + tokenizes in ~4s and is then correctly rejected
(381k tokens > 262k context). The freeze requires **several concurrent
conversions arriving together**, each holding the GIL for seconds, back to
back —which is exactly what a fan-out gateway produces, and why whole nodes
freeze in the same minute.

#39771 (merged 2026-10-13) moves `_convert_to_internal_request` off the loop
and fixes the render part. We validated the same change on a production
canary: under a synthetic 32-way conversion storm, `/v1/models` stayed 200
(worst latency 23s vs. the 30s probe timeout), the queue drained in ~5 min,
zero restarts —versus guaranteed liveness death on stock v0.5.21.

### What #39771 does not cover: regular tokenization is still on the loop

On current `main`, `_tokenize_one_request` still awaits `_tokenize_texts`
synchronously on the event loop for text-path requests. For models whose
chat path delivers text (our GLM-5.3-Flash does; py-spy captured the loop
thread mid-storm in `_encode_plus` via `generate_request ->
_tokenize_one_request -> _tokenize_texts`), this is the **normal path**, not
a fallback. With #39771 alone, a burst of long-context requests still blocks
the loop for the full Python-side tokenization cost of each prompt —this is
the residual that produced the 23s worst-case probe latency on our canary.

This PR ports the remaining `tokenizer_manager` half of #30771.

## Modifications

Single production file, `python/sglang/srt/managers/tokenizer_manager.py`
(same change as #30771, rebased onto current `main`):

- `TokenizerManager` gains a dedicated `ThreadPoolExecutor(max_workers=1)`
  (`init_request_preprocessor`) and an `async run_in_request_preprocessor()`
  helper that preserves contextvars (`copy_context().run`) so request-scoped
  state survives the thread hop. The only deviation from #30771: the executor
  thread is named (`thread_name_prefix="request-preprocessor"`) so py-spy /
  /proc stack dumps can distinguish it —this is what made our production
  diagnosis possible.
- The regular-tokenizer branch of `_tokenize_texts` now runs inside that
  executor via `await`, instead of calling `self.tokenizer(...)` inline on
  the event loop.

Single worker keeps tokenizer access serialized (slow pure-Python tokenizers
are not thread-safe —the same concern raised in review of #30771), at the
cost of queuing concurrent tokenizations behind each other; the rust
tokenizer releases the GIL during encoding, so the loop keeps scheduling.

Also includes the three CPU-only event-loop responsiveness tests from #30771
(unchanged; authored by @anencore94):
- `test/registered/unit/managers/test_tokenizer_manager_event_loop.py` —  fails on `main` without this change, passes with it.
- `test/registered/unit/entrypoints/openai/test_serving_base_event_loop.py`
  and `test/registered/unit/entrypoints/test_http_server_liveness.py` —  regression guards for the #39771 behavior.

Deliberately NOT included: the `serving_base.py` hunk of #30771 (superseded
by #39771's default-executor offload).

## Accuracy Tests

Not applicable to model outputs: the same tokenization runs on the same
inputs; only the executing thread changes. Serialization order of
preprocessing per process is preserved (single worker).

## Speed Tests and Profiling

Production canary (8x H20 node, tp8, v0.5.21 + conversion offload only —i.e. #39771 equivalent, without this PR's tokenizer half):

| `/v1/models` (liveness path) | stock v0.5.21 | conversion offloaded |
|---|---|---|
| under 32-way conversion storm | no answer for 16 min, pod killed | always 200, worst 23s |
| after storm | container restart + ~13 min reload | drains ~5 min, 0 restarts |

The residual 23s worst-case is the loop-side tokenization addressed by this
PR (py-spy: `MainThread` in `_encode_plus` mid-storm). With tokenization also
off the loop, the remaining loop work during storms is small Python-side
bookkeeping.

Reproducer (no GPU work needed; requests are rejected on context length
after preprocessing):

```python
import json, threading, urllib.request

def fire(i):
    msgs = [{"role": "user" if j % 2 == 0 else "assistant",
             "content": f"message number {j}"} for j in range(50_000)]
    req = urllib.request.Request(
        "http://HOST:PORT/v1/chat/completions",
        data=json.dumps({"model": "MODEL", "messages": msgs,
                         "max_tokens": 16}).encode(),
        headers={"Content-Type": "application/json"})
    urllib.request.urlopen(req, timeout=600).read()

threads = [threading.Thread(target=fire, args=(i,)) for i in range(32)]
```

While this runs, poll `/v1/models` with a 30s timeout: on `main` it starves;
with this PR it stays responsive.

Credit: the fix design and tests are @anencore94's work from #30771
(see their review fix `edde3b7` switching to the shared single-worker
executor). This PR only rebases the still-relevant half onto current `main`
after #39771, plus adds production validation data. Happy to fold this back
into #30771 instead if the maintainers prefer.
