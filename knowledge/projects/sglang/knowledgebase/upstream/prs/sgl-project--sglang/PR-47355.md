# [Refactor] multimodal: [sglang-miles] Register token-space strategies through a registry function trainers can call

[Upstream PR](https://github.com/sgl-project/sglang/pull/47355) · state: closed · merged: True

## Original PR description

## Motivation

Trainers look up token-space strategies with `strategy_for`, but only `import_processors` registered them, and it lives in `managers/multimodal_processor.py`, which imports the serving stack. A trainer therefore found no strategy for any architecture.

This syncs the fix that the main stack carries at the end of #46412 and #46414 onto sglang-miles, after the merged MM refactor stack (#46680 - #46769).

## Modifications

- `registry.register_token_space_models()`: imports every `token_space_mm_process.models` module and registers its strategies and serving specs; a module that fails to import is skipped with a warning. `registry.py` still imports no model module itself.
- The four multimodal serving entry points (tokenizer manager, scheduler, encoder receiver, Rust server) call it behind their existing multimodal checks; `import_processors` registers only legacy processors again.
- The legacy comparison test registers strategies through the same function.

## Tests

- `test_token_space_registry.py`: importing the manager still loads no strategy module; registering strategies loads no serving module; a broken model module is skipped.
- `test_mm_token_expansion.py`, `test_qwen_processor_bitwise.py` register through the new function.

🟡 (optional) Token-space strategies or serving specs in a custom `SGLANG_EXTERNAL_MM_PROCESSOR_PACKAGE` are now silently ignored. On the base branch they were registered and overrode the built-in ones. The external package is still loaded only through `import_processors(mm_process_pkg, overwrite=True)`, which no longer calls `register_token_space_classes`. `register_token_space_models()` walks only the built-in `models` package. Fix: register token-space classes from the external package too, e.g. call `register_token_space_classes` on each external module in tokenizer_manager.py:677 and rust_server/multimodal.py:238. [also at: python/sglang/srt/managers/tokenizer_manager.py:678 - Out-of-tree packages that define token-space strategies in `SGLANG_EXTERNAL_MM_PROCESSOR_PACKAGE` silently lose them after this change and fall back to the legacy processor.]

<details>
<summary>Why this was flagged</summary>

The trigger is an operator who sets SGLANG_EXTERNAL_MM_PROCESSOR_PACKAGE (environ.py:327) to a package defining TokenSpaceProcessStrategy or TokenSpaceServingSpec subclasses; external packages are outside this repo, so this population cannot be enumerated. On the base branch, import_processors called register_token_space_classes(module) on every module it imported, so tokenizer_manager.py:677-678 and rust_server/multimodal.py:238-239 registered those classes after the built-ins and let them override. This diff removes that call at multimodal_processor.py:49. The new register_token_space_models() (registry.py:52-66) only iterates the models.__path__ of sglang.srt.multimodal.token_space_mm_process.models. After the merge, strategy_for/serving_spec_for return the built-in strategy or None/the default spec for the external architecture, with no warning or error. The PR describes import_processors registering only legacy processors as intended, but it does not mention that this drops the external-package path.

**Verification:** On the base, `import_processors` in managers/multimodal_processor.py ended each module iteration with `register_token_space_classes(module)`, so the external package overrode built-in entries. This diff removes that line at multimodal_processor.py:49, and `register_token_space_models()` (registry.py:52-66) iterates only the built-in package, so the external override is dropped without any warning.

</details>
