# [sglang-miles] Support P2P replica loading and target/draft weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/42820) · state: open · merged: False

## Original PR description

Provide the engine-side support for the Miles P2P stack (radixark/miles#3939 through radixark/miles#3985). Land together with the stack: radixark/miles#3969 replaces `ParameterMapper`, and radixark/miles#3985 adds draft updates.

- **Replica construction:** add `initialize_model_without_storage`, preserving parameter subclasses, attributes and ties while returning built shapes. Buffers remain on meta.
- **Reload layout and storage:** restore TRT-LLM BF16 MoE weights to canonical shapes in place before updates; assert published parameter addresses and byte counts survive restore and postprocess.
- **Runner registration:** key weight tables and parallelism configs by `(role, tp_rank)`, defaulting to target. Publish drafts after memory-pool setup binds shared embeddings/heads, avoiding stale addresses.
- **Derived state:** pin the GLM-lite NextN post-load path to `is_nextn=True` and recompute `GemmaRMSNorm.gemma_weight` in place after loads/updates that bypass its loader.
- **Mapping removal:** remove `ParameterMapper` and its model hooks; Miles now discovers dependencies by probing `load_weights`.

`RemoteInstanceModelLoader` still queries the target role; loading a draft from a seed instance is not covered.

## Recorded validation

- H200 CPU unit runs passed model construction, MoE restore, published storage, runner roles, NextN post-load and Gemma buffer refresh checks. Relevant pre-fix revisions fail the corresponding regression checks.
- GPU equivalence: two updates of a two-layer GLM-5.2 model match sglang's own update, including parameters, buffers and attributes, with published storage unchanged. The initial five-format run used Miles #3950 and the earlier mapper; loader-probe results and MTP e2e results are tracked in radixark/miles#3985.
- Removing mapper hooks preserved all 4,816 tensor checksums across GLM-4.7-Flash and GLM-4.5-Air-FP8 with drafts, DeepSeek-V2-Lite, Qwen3-30B-A3B, GLM-4-9B-0414, Qwen3-0.6B, Qwen2.5-0.5B and TinyLlama-1.1B. DeepSeek V3 NextN and the modelopt KV-scale remap were not exercised in that comparison.
- Qwen3.5-35B-A3B and GLM-4.7-Flash P2P MTP e2e passed on the final SGLang commit, with equality checked on target and draft.

### reviews

- Zhichenzzz · COMMENTED · 2026-10-10T00:52:00Z · [source](https://github.com/sgl-project/sglang/pull/42820#pullrequestreview-5476711670)

High-level review alongside the Miles stack (radixark/miles#3939 → #3985). The design looks right, and removing `ParameterMapper` brings sglang-miles closer to main. Validated together with the Miles stack tip on 2× GB300: the p2p fast tests and the GLM-5.2 equivalence test (bf16, fp8_block ue8m0/fp32, mxfp8, nvfp4) all pass.

**Before merge**
- **Rebase needed.** The PR currently conflicts with `sglang-miles`, which has since landed the MXFP4 online-update change touching `weight_updater.py` / `loader.py` / the mxfp4 TRT-LLM MoE. CI has produced no test signal yet: the red checks are only gates (missing `run-ci` label, plus the maintenance-mode base-commit check). After the rebase, please re-validate the new published-storage address/size check against the rewritten MXFP4 TRT-LLM postprocess.
- **[P2] Loading a draft from a seed instance now gets the target's table.** `RemoteInstanceModelLoader` calls `get_remote_instance_transfer_engine_info_per_rank(seed_url, tp_rank)` without a role, so it defaults to `target`. With spec decoding + the remote-instance loader, the draft would fail at startup ("Cannot find weight info"). Please either pass the role through or reject the combination explicitly.
- **[P2] The `gemma_weight` refresh misses some update paths.** `update_weights_from_tensor(load_format="direct")` and custom loaders bypass `_weight_loader` but still set `loaded_weights=True`, so `run_post_load` is False and `gemma_weight` stays stale. The same happens in a mixed session. Refreshing unconditionally in `end_weight_update` would cover all paths.
- **[P2] The storage check is a bare `assert` in the scheduler and applies to every session type.** Once a transfer engine has registered, it also runs for disk/tensor/distributed updates. A legitimate postprocess that rebinds `.data` would raise AssertionError inside the scheduler, probably killing it rather than returning `success=False`, and the check disappears under `python -O`. Suggest a normal exception surfaced in the session result.
