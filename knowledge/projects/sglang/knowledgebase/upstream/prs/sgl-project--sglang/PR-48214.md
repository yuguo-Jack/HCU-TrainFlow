# [Doc] cookbook: Capture prefill CUDA graphs up to 16384 tokens in the GLM-5.3-Flash B300 FP8 Low Latency recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/48214) · state: open · merged: False

## Original PR description

## Motivation

On B300, `chunked_prefill_size` defaults to 16384 (GPUs with at least 160 GB, `python/sglang/srt/arg_groups/memory_hook.py`), but MLA backends cap prefill CUDA graph capture at `min(8192, chunked_prefill_size)` (#45565). GLM-5.3-Flash runs breakable prefill graphs by default, so with the B300 FP8 Low Latency command every prefill forward of 8,193–16,384 tokens runs eager. That includes each full chunk of a long prompt and any batch of shorter prompts that adds up to more than 8,192 tokens.

In the server logs of the two default-config runs below, all 314 and 256 prefill batches above 8,192 tokens ran with `cuda graph: False`. With `--cuda-graph-max-bs-prefill 16384`, all 313 and 247 such batches replayed a captured graph.

## Modifications

- Add `--cuda-graph-max-bs-prefill 16384` to the `b300 / low-latency / fp8` cell in `docs/src/snippets/configs/zai-org/glm-5.3-flash.jsx`, with a comment that explains it.
- No other cell changes. The B300 NVFP4 and High Throughput cells and the other platforms were not measured.
- `glm-5.3-flash-benchmarks.jsx` is unchanged. Its B300 Low Latency entry already has a TODO to re-measure on the current recipe, and the numbers below are an A/B from a different harness, not a replacement for that row.
- `node docs/scripts/check_cookbook_configs.mjs` passes.

## Speed Tests and Profiling

Setup:

- 8x B300 (SM103), `lmsysorg/sglang:nightly-dev-cu13-20261103-797af717` (main `797af717`), `zai-org/GLM-5.3-Flash`.
- This cell's command (TP8, FP8 KV, TRT-LLM DSA, `flashinfer_trtllm` MoE, MTP 5/1/6) plus `--watchdog-timeout 1800`, with and without `--cuda-graph-max-bs-prefill 16384`.
- Four servers in the order default, PR, PR, default. Each ran the same `bench_serving` rows after warmup: `--flush-cache`, fixed-length prompts cut from ShareGPT text with no shared prefixes, `--apply-chat-template`, and 4 output tokens for the prefill rows.
- Each number is the mean of the two servers' medians. A change is reported only when both restart pairs move in the same direction and the mean change is larger than the spread between the two servers of either version; otherwise the change is shown as ~0.

Prefill rows, median TTFT (ms):

| input tokens x concurrency | default | this PR | change |
|---|---|---|---|
| 4,096 x 1 | 114.2 | 115.0 | ~0 (control, below 8,192) |
| 8,000 x 1 | 190.5 | 188.0 | ~0 (control, below 8,192) |
| 16,384 x 1 | 425.1 | 341.5 | -19.7% |
| 32,768 x 1 | 789.1 | 675.8 | -14.4% |
| 2,048 x 8 | 376.2 | 268.0 | -28.7% |
| 4,096 x 8 | 698.3 | 455.4 | -34.8% |
| 8,000 x 8 | 1,036.6 | 624.6 | -39.7% |
| 1,024 x 16 | 398.7 | 240.1 | -39.7% |
| 512 x 32 | 397.0 | 255.4 | -35.7% |

Input throughput rose 16–42% in the rows that changed. In the last two rows each request has 1,024 or 512 tokens, but the scheduler packs them into forwards above 8,192 tokens, and they improve by about as much as the long-prompt rows. In eager mode these forwards qualify for DSA's dense MHA path (every kv_len is at most 2048), while inside the graph DSA forces `use_mha=False`; the graph still came out ahead.

Decode and mixed rows (256 output tokens):

| input tokens x concurrency | metric | default | this PR | change |
|---|---|---|---|---|
| 1,024 x 1 | TPOT (ms) | 2.8 | 2.9 | +2.7% |
| 1,024 x 16 | TPOT (ms) | 5.3 | 5.1 | ~0 |
| 16,384 x 8 | output tok/s | 563.7 | 641.9 | +13.9% |
| 4,096 x 16 | output tok/s | 1,598.4 | 1,742.3 | +9.0% |
| 4,096 x 16 | TPOT (ms) | 8.5 | 8.2 | -4.5% |

The +2.7% single-request TPOT is just above the 2.5% restart spread (pairs +1.6% and +3.9%). Decode graphs are the same in both versions, so this is probably noise, but it is listed as measured.

Startup cost, rank 0:

| | default | this PR |
|---|---|---|
| prefill graph shapes | 58 | 74 |
| prefill graph capture time | 51 s | 65–75 s |
| prefill graph memory per GPU | 2.81 GB | 4.72 GB |
| KV pool | 23,208,960 tokens | 23,208,960 tokens |

With EP8 (EP=8 in the Playground's MoE card; one server per version, so no restart spread), graph memory went from 2.99 to 5.16 GB per GPU and median TTFT changed by -17.2% at 16,384 x 1 (483.9 to 400.5 ms), -31.4% at 4,096 x 8 (772.9 to 530.2 ms) and -47.3% at 1,024 x 16 (427.3 to 225.2 ms).

Not tested:

- Playground selections on top of this cell: TP below 8, prefill CP, PD roles, HiCache, Speculative off or DFlash2.
- B200, GB200 and GB300. They also have at least 160 GB per GPU, so they default to 16,384-token chunks and hit the same 8,192 cap.
- The NVFP4 and High Throughput cells.

The default cap comes from #45565. This PR changes only the measured recipe and leaves the default alone.
