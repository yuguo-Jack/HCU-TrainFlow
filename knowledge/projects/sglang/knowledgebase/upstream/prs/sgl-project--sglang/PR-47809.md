# [Fix] attention: Honor custom masks past the causal tile in Triton extend

[Upstream PR](https://github.com/sgl-project/sglang/pull/47809) · state: open · merged: False

## Original PR description

## Motivation

With the Triton backend, Gemma 4 image tokens get bidirectional attention only inside their own query tile, not across the whole image span. Gemma 3 has the same problem.

`Gemma4ForConditionalGeneration.prepare_attn_masks` (and `Gemma3ForConditionalGeneration.prepare_attn_masks`) builds the right dense mask: causal, plus a bidirectional block for each image span. It installs that mask as `forward_metadata.custom_mask`. Gemma's decoder layers are plain `AttentionType.DECODER`, so `TritonAttnBackend.forward_extend` still calls the kernel with `is_causal=True`.

Inside `_fwd_kernel`, the custom mask replaces the per-element causal check (the `if USE_CUSTOM_MASK: ... elif IS_CAUSAL:` branch). However, the stage-2 key loop is still cut off at the causal diagonal:

```python
cur_block_m_end = cur_seq_len_extend if not IS_CAUSAL else tl.minimum(cur_seq_len_extend, (cur_block_m + 1) * BLOCK_M)
```

As a result, any key the mask allows after the query's `BLOCK_M` tile is never visited. An image token attends to later image tokens only within its own `BLOCK_M`-token query tile (on H200, 64 at head_dim 256 and 32 at head_dim 512). A Gemma 4 image is up to 1120 soft tokens long, so most of the bidirectional block is dropped without any warning. The unified kernel (`--enable-deterministic-inference`) already visits every key when a custom mask is set, so it gives the correct output. The two kernels therefore disagree on Gemma image prompts.

Related: #39703 proposed the same kernel-level change for dLLM block masks, but the stale bot closed it as a draft. #33034 and #32303 change the Gemma 4 masking itself (image spans instead of a dense mask, and scoping to sliding layers). This PR is independent of both: it makes the existing dense custom-mask path correct for every caller.

## Modifications

- `kernels/ops/attention/extend_attention.py`, `_fwd_kernel` stage 2: stop at the causal diagonal only when there is no custom mask. With a custom mask, walk the whole extend region, as `_fwd_kernel_unified` already does. Tiles where the mask allows nothing are still skipped by the existing `SKIP_TILE` check, so they only cost a mask load and no K/V load or dot product.
- Paths that use `is_causal=False`, or that have no custom mask, compile to the same kernel as before (`USE_CUSTOM_MASK` and `IS_CAUSAL` are constexpr).
- Speculative target-verify masks never allow a key after the query, so their output does not change. Their extend length is the number of draft tokens, usually a single tile, where the loop bound is the same as before.

Why fix the kernel rather than have the backend pass `causal=False` whenever a model installs a mask: in this kernel, `is_causal=False` also makes the sliding window two-sided (`kv <= q + W`). On Gemma's sliding-window layers that would cut off image tokens more than `W` positions ahead. In a kernel-level repro (head_dim 256, window 1023, 1120-token image), `causal=False` still gave a max error of 5.8 against the reference. Keeping `is_causal=True` and fixing the loop bound keeps the one-sided window, and it also fixes any other model or feature that installs a non-causal custom mask.

**End to end.**
- Model and settings: `google/gemma-4-12B-it`, `--attention-backend triton`, `--mm-process-config '{"image":{"max_soft_tokens":1120}}'`, greedy decoding, thinking off.
- Data: 100 CountBenchQA items and 100 MathVision multiple-choice items.
- Comparison: HF transformers output on the same prompts (prompt token counts match 100%).

| Setting | CountBenchQA acc | same answer as HF | MathVision MC same answer as HF |
| --- | --- | --- | --- |
| HF transformers | 96 | - | - |
| `main` (dp 8, chunked prefill 8192) | 69 | 72% | 75% |

On 0.5.23 and 0.5.17 the problem looked the same, and disabling chunked prefill or CUDA graphs, or changing dp, made no difference. The MathVision answers are mostly long-form, so the agreement on those items is noisy.

**Gemma 3** (`gemma3_mm.py`) installs the same causal-plus-image-block dense mask on `TritonAttnBackend` with `AttentionType.DECODER` layers, so it should be affected in the same way: a 256-token image is wider than one query tile. I did not run Gemma 3 end to end.

## Speed Tests and Profiling

Not benchmarked. The change only affects launches that have both a custom mask and `is_causal=True`. For each query tile it adds the key tiles after the diagonal. Tiles the mask leaves empty cost only a mask load plus `SKIP_TILE`; tiles the mask allows are real work that was previously, and wrongly, skipped. Plain causal prefill, decode and non-causal paths do not change.
