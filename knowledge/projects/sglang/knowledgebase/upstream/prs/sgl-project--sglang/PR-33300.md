# [sglang-miles] Fix LoRA usage-counter lifecycle across cleanup paths

[Upstream PR](https://github.com/sgl-project/sglang/pull/33300) · state: open · merged: False

## Original PR description

## Problem

`LoRARegistry.acquire()` increments an in-flight usage counter before request
validation/dispatch, while `/unload_lora_adapter` waits for that counter to
return to exactly zero. Request cleanup paths that miss a release leave unload
blocked forever; duplicate releases can drive the counter below zero and have
the same effect.

The original version of this PR fixed the obvious abort and failed-dispatch
leaks by coupling `rid_to_state.pop()` with `release()`. That is not sufficient
for native parallel sampling (`n > 1`), where parent states, regenerated child
states, and a prefix-cache warm-up request all observe the same acquired LoRA
references.

## Fix

This revision incorporates the lifecycle model from #31808 into the
`sglang-miles` branch and extends it for the request shapes used here:

- Add a per-`ReqState` exactly-once release guard. Normal completion, abort
  echo, scheduler error, and failed dispatch all route through the same helper.
- Keep strong references to asynchronous release tasks until they complete.
- Treat the acquired `lora_id`, rather than `lora_path`, as the ownership
  signal. This avoids `release(None)` when acquire never succeeded and remains
  compatible with #30913, where an upsert deliberately reuses the stable
  adapter ID.
- For parallel sampling, make the prefix-cache warm-up state a non-owner and
  transfer the acquired references from bookkeeping parents to exactly
  `batch_size * n` regenerated child states.
- Support an explicit parent `rid` list: one parent state temporarily owns the
  `n` references for its prompt until fan-out, so validation/tokenization
  failure before fan-out still returns every acquired reference.
- Close the abort-vs-acquire race. If an abort removes a tokenizer-held state
  while registry acquisition is awaiting, the newly acquired orphaned ID is
  returned immediately.

The resulting invariant is:

> Every successful LoRA acquire has exactly one owner and exactly one release,
> across success, abort, validation failure, and native multi-LoRA parallel
> sampling.

## Relationship to earlier LoRA PRs

- **#30913 (LoRA upsert):** already present in the `sglang-miles` base. This
  change releases the registry-provided stable `lora_id`, so an in-place upsert
  keeps the same identity and usage counter correctly.
- **#31808 (usage-counter lifecycle):** this PR is the `sglang-miles` port and
  superset of that lifecycle fix. The two PRs modify the same lifecycle lines,
  so they should not be independently stacked on `sglang-miles`; this revision
  already contains #31808's exactly-once guard, task retention, abort/error
  cleanup, and parallel warm-up ownership behavior. Shafeeq is retained as a
  co-author on the integration commit.

## Safety review: semantic rebase and lifecycle hardening required

The direction is correct, but the current head is **not safe to merge as-is**.

### 1. Semantically rebase onto the current `sglang-miles`

This PR and merged #33299 are sibling implementations from `3fe50ed`, and both change the LoRA lease lifecycle in `TokenizerManager`. Please keep exactly one guard/finalizer—not both:

- #33299: `lora_lease_released` / `_finalize_lora_lease`
- #33300: `lora_released` / `_release_lora_once`

Suggested combined model: keep the #33299 names, but add this PR's ID/bundle ownership, strong release-task retention, BAD_REQUEST cleanup, and abort-vs-acquire orphan release. Ownership must be based on the acquired `lora_id` (or explicit bundle), not `lora_path`.

Please also preserve #33299's atomic acquire, `reloadable=False`, LRU/delete behavior, and endpoint auth; #30913's stable-ID in-place upsert; and #30912's prefix-abort/`abort_before_dispatch` semantics.

### 2. Blocking gap: partial batch can release too early

With sequential batch tokenization, item 0 can already be dispatched when item 1 fails validation. The outer `_discard_pending_req_states(obj)` then removes/releases every original state, including item 0 while the scheduler may still be executing it. Counts may eventually balance, but unload/upsert can observe zero too early and mutate the slot under an active request.

Required invariant: release only when a state is known never to have been dispatched, or after observing scheduler terminal/abort ACK. Track dispatch state, or finish whole-batch validation/tokenization before dispatching any member.

### 3. Blocking gap: `n > 1` has a mid-fanout ownership hole

The current code removes/marks parents transferred before awaiting the prefix warm-up and before all children exist. A warm-up failure/cancellation or failure after child `k` leaves residual acquired IDs without an owner; generated child rids are also outside original-rid cleanup.

Keep a parent/request-group residual ledger. Transfer one ID only after its child state exists, retain dispatched children until terminal, release residual/non-dispatched ownership in `try/finally`, and track generated child rids so parent/prefix abort reaches the whole group. The warm-up owns zero leases.

At every await/exception/cancellation boundary, every successful acquire must be owned by exactly one parent ledger, child state, direct orphan-release task, or terminal-release task.

### 4. Existing branch regression

#32421 is marked merged, but its behavior is absent from the current branch: `load_lora_adapter_from_distributed` still requires `dp_size == 1`. Please restore or separately track `dp_size == 1 or enable_dp_attention` so distributed multi-LoRA upsert remains supported.

### Required regression coverage

Please retain/run:

- `test_lora_lease.py`
- `test_tokenizer_manager_rid_cleanup.py`
- `test_abort_request_prefix.py`
- `test_lora_upsert.py`

Please add cases for partial-batch failure after a sibling dispatch, warm-up cancellation/failure, failure after child `k`, parent-prefix abort during fanout, two adapters with explicit parent rids and `n > 1`, and distributed load/upsert with DP attention.

Tests must assert temporal safety, not only final acquire/release equality: unload/upsert must remain blocked while any dispatched owner exists, counters must never become negative, and all counters must reach zero after terminal cleanup.

**Bottom line:** the intended fix is compatible with the existing LoRA work, but it needs a semantic rebase plus these two ownership hardenings before it can be considered safe.
