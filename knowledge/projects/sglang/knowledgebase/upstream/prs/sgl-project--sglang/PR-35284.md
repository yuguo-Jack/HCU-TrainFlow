## Motivation

<!-- Describe the purpose and goals of this pull request. -->
DSpark currently rejects `deepep` when DP attention is enabled, even though the target and draft MoE execution paths support DeepEP.

The existing validation also applies the static-only restriction to every non-`none` MoE A2A backend. That restriction is required for MegaMoE, but it does not apply to DeepEP.

Compact verification additionally has an idle-rank issue under DP attention. An idle DP rank may observe `global_num_tokens=[0]`, an empty list, or no local token-count metadata. The previous implementation returned no ragged layout in this case. The idle rank could then select a token-keyed CUDA Graph path instead of participating in the same ragged graph family as active ranks, causing graph replay failures before the synchronized MoE collective could complete.

## Modifications

<!-- Detail the changes made in this pull request. -->
- Allow `deepep` as a DSpark MoE A2A backend when DP attention is enabled.
- Keep the static-only restriction specifically for `megamoe`.
- Allow DeepEP to use both static and compact ragged verification modes.
- Make compact idle participation construct a ragged layout with one dummy
  request when the global request count is zero or unavailable.
- Preserve zero real tokens on the idle rank; the dummy request only selects
  the correct CUDA Graph family and does not become a real verify token.
- Add unit tests covering:
  - static DeepEP admission;
  - compact DeepEP admission;
  - MegaMoE's static-only restriction;
  - unsupported backend rejection;
  - idle compact layout construction for `[0]`, `[]`, and `None` token-count
    metadata.
