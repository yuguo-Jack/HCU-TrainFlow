# [Perf] [AMD] dsa: In-tree gfx950 paged MQA logits for decode / MTP-verify rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/47897) · state: open · merged: False

## Original PR description

## Motivation

With DP attention, GLM-5.2's DSA indexer computes paged MQA FP8 logits with aiter's gluon kernel (`aiter.ops.triton.pa_mqa_logits.deepgemm_fp8_paged_mqa_logits`, preshuffled cache). On gfx950 it runs for decode / MTP-verify batches above the 48 rows that the fused gfx950 indexer takes, and for MTP draft-extend rows. At 48 to 84 rows that kernel takes 272 to 310 us per call against aiter main 6fe1bfc. This PR adds an in-tree retuned version of it that takes 93 to 97 us on the same inputs, about 3x faster.

## Modifications

- **New `kernels/ops/attention/dsa/gluon_paged_mqa_logits.py`.** It is derived from aiter's `_gluon_deepgemm_fp8_paged_mqa_logits_preshuffle` and its host wrapper (aiter e7d2453). It is reduced to the path sglang takes here (gfx950, preshuffled 64-token pages, 32 heads x 128, one query per row) and retuned:
  - **KV split.** The split is decoupled from the occupancy hint and set from the row count. Program ids are swizzled so that the pieces of one row share an XCD and its L2.
  - **Dispatch order.** MTP verify rows of one request (6 consecutive rows) are dispatched longest group first.
  - **Pair kernel.** `_gluon_paged_mqa_logits_fused2` scores two adjacent rows per program when their page tables match on their common prefix, so their K pages are read once. The match is checked on the device; rows that do not match are scored separately, so any input is exact.
  - **gfx950 instructions.** Full-rate scaled fp8 MFMA, a uniform (SGPR) row index, and `relu` as one `v_maximum3`.
- **Dispatch.** `paged_mqa_logits.aiter_paged_mqa_logits` calls it when `gluon_paged_mqa_logits.supported()` holds: gfx950, preshuffled, page 64, 32 x 128, 1 to 128 rows. Otherwise it calls aiter as before. If gluon cannot be imported, aiter is used.
- **No new flags.**
- **Tests** (`test/registered/amd/test_dsa_gluon_paged_mqa_logits.py`) compare against aiter's kernel. They check equality to fp32 rounding on every valid column, and that the top-2048 selection differs only within that rounding. Inputs:
  - 48- to 126-row MTP batches with shared tables;
  - paired rows whose tables differ;
  - plain decode with 1, 7, 48, 100 and 128 rows.

## Accuracy Tests

- **Logits.** Differences from aiter come only from summation order: max |diff| is 7.6e-6.
- **Top-k sets.** On real GLM-5.2 workset indices (48 to 84 rows, contexts up to 659k), v1 top-k gives the same top-k sets from either logits.
- **gsm8k.** GLM-5.2-MXFP4, TP8 DP8 DP-attention, MTP with acceptance not simulated, 400 questions, fresh server per run, alternating:

| | gsm8k |
|---|---|
| main (5 servers) | 0.943 / 0.945 / 0.932 / 0.930 / 0.920 (mean 0.934) |
| this PR (6 servers) | 0.920 / 0.917 / 0.925 / 0.920 / 0.945 / 0.932 (mean 0.927) |

The ranges overlap. The difference in means is within the run-to-run spread of this setup.

**A bug in the source kernel's pair path, fixed here.** In the derived kernel, each split decided between the pair pass and the two single-row passes from the page ids in its own window. The two branches partition the context differently, so when two adjacent rows had different tables and different lengths, the shorter row's tail went unwritten. This happens in plain decode with 48 rows, for example. MTP siblings never hit it. The decision now uses the whole common prefix, so all splits of a pair agree. The plain-decode test covers this case.

## Speed Tests and Profiling

**Kernel.** On MI355X:
- inputs: real GLM-5.2 verify rows (6 per request), page table 16386 pages wide (the captured graph width);
- one CUDA graph runs the call over 4 index-K pools of 294 MB each;
- medians in us per call.

| rows (real GLM-5.2 verify rows) | longest context | aiter main | this PR | speedup |
|---|---|---|---|---|
| 48 | 462k | 276.5 | 103.7 | 2.67x |
| 60 | 385k | 273.2 | 101.7 | 2.69x |
| 72 | 433k | 312.4 | 102.2 | 3.06x |
| 84 | 429k | 290.2 | 104.3 | 2.78x |

The speedup grows with context. In-server (eager, 96 rows per rank, about 16k-token contexts, torch profiler) the call takes 26.2 us against aiter's 32.5 us (1.24x).

**End to end.**
- Setup: GLM-5.2-MXFP4, TP8 DP8 with DP attention, MTP (EAGLE 5 / 1 / 6), simulated acceptance 3.61, `--max-running-requests 128 --cuda-graph-max-bs-decode 16`. That is 16 requests and 96 verify rows per rank, which is this kernel's range.
- Benchmark: `bench_serving`, random 32k input / 1k output, concurrency 128.
- Main and this PR alternate on one node, fresh server each.

| | median ITL ms |
|---|---|
| main (3 servers, 6 runs) | 13.93 - 13.95 |
| this PR (3 servers, 6 runs) | 13.79 - 13.81 |

That is 0.9% lower median ITL. At 32k contexts this kernel is a small share of the step; the per-call speedup is largest at long contexts (table above).

## How to reproduce

```bash
python3 test/registered/amd/test_dsa_gluon_paged_mqa_logits.py -v     # one gfx950 GPU
SGLANG_SIMULATE_ACC_LEN=3.61 SGLANG_SIMULATE_ACC_METHOD=match-expected SGLANG_SIMULATE_ACC_TOKEN_MODE=real-draft-token \
python3 -m sglang.launch_server --model-path amd/GLM-5.2-MXFP4 --trust-remote-code --kv-cache-dtype fp8_e4m3 \
  --dsa-prefill-backend triton --dsa-decode-backend triton --mem-fraction-static 0.85 \
  --speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6 \
  --tensor-parallel-size 8 --data-parallel-size 8 --enable-dp-attention --max-running-requests 128 --cuda-graph-max-bs-decode 16
python3 -m sglang.bench_serving --backend sglang --dataset-name random --random-input-len 32000 --random-output-len 1000 \
  --random-range-ratio 1.0 --num-prompts 256 --max-concurrency 128
```

The kernel changes were found with an automated kernel-optimization search on top of aiter's kernel. This PR ports them into sglang, fixes the pair-path bug above, and adds the dispatch gate and tests. They could equally move into aiter's own kernel later.
