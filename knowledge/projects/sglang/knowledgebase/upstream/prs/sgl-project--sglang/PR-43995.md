## Motivation
Issue: #43699. Reduce Mooncake KV transfer submission overhead under concurrent PD workloads by batching ready chunks across requests.

## Modifications

- Preserve per-request ordering, state/aux transfers, completion, and abort handling, with fallback to the existing transfer path.
- Add unit tests covering data correctness, batching limits, fallbacks, failures, and aborts.

- SuperGoodGame · comment · 2026-10-13T08:24:12Z · [source](https://github.com/sgl-project/sglang/pull/43995#issuecomment-6141443782)

@SYChen123 Thanks for the invitation to collaborate. I put runnable reproductions in https://github.com/SuperGoodGame/sglang/pull/1, based directly on your current head `fd6cf87` (no production changes).

I observed four things:

1. **Submission after a failed sub-batch.** With four requests split into two pairs and the first transport call returning -1, batching still submits the second pair to the same session. Disabled/enabled batching makes 1/2 calls respectively; `failed_sessions` is still empty at the second call. All requests ultimately become Failed; I did not observe false success or data corruption. Could we stop further submissions to that session immediately, while preserving deferred-release poisoning and failing unsubmitted members?

2. **Repeated planning on singleton fallback.** With eight requests and a byte cap that only fits one request, both modes make eight submissions, but layer planning runs 8 times with batching disabled versus 16 when enabled. The prepared singleton plan is discarded and rebuilt by the fallback. Reusing that plan, or avoiding futile preplanning, may help.

3. **Completion waits across bounded sub-batches.** At the start of request 3's transfer, requests 1–2 are already Success without batching, but neither is Success with batching. Both modes finish correctly. This is a latency tradeoff: could each completed bounded sub-batch publish its per-request completion before blocking on later sub-batches, subject to state/aux, cancellation and lifetime constraints?

4. **Adjacent ranges are concatenated rather than coalesced.** Two requests with separate K/V buffers submit 4 descriptors even when both source and destination pages are contiguous. An offline candidate uses 2 descriptors and produces identical destination buffers. Source-only or destination-only adjacency correctly leaves 4. Coalescing within compatible layer/buffer groups only when **both** ends are adjacent looks worth exploring; its speedup has not been measured.

These are CPU-copy reproductions exercising the real planner/worker, not GPU performance benchmarks. The [README](https://github.com/SuperGoodGame/sglang/blob/repro/mooncake-descriptor-coalescing/test/manual/disaggregation/README.mooncake-batching.md) has commands and expected results; both scripts and the existing 13 batching tests pass locally.

Could you try reproducing these? The [single commit](https://github.com/SuperGoodGame/sglang/commit/0c79c5403ab984d0cd74446b94cad1f148106a21) can be cherry-picked onto this branch.

- simple-sun · comment · 2026-10-13T09:30:23Z · [source](https://github.com/sgl-project/sglang/pull/43995#issuecomment-6142561827)

Hi @SYChen123, we’ve been working on incremental improvements to the fragmented equal-TP KV staging implementation in #35036, with our changes submitted to its author’s branch: https://github.com/KIOSHIROI/sglang/pull/1.

One potential integration with this PR would be:

1. Select the transfer path per chunk based on staging eligibility and fragmentation.
2. Route eligible fragmented chunks through staging.
3. Allow eligible direct-transfer chunks to participate in cross-request batching even when staging is enabled.

This integration is not implemented yet. Would you be interested in working together on it? We can contribute the staging-side changes and coordinate with you on the batching integration.

@simple-sun Hi, thanks for your information. This current PR doesn't consider staging. To adapt staging into cross-req batching, we should avoid different requests' staging buffers being reused and mixed. This will probably introduce much complexity and it's out of the scope of this PR. I think I need to first demonstrate the performance of cross-req batching. If it's truly beneficial, then we can integrate other features step by step.
