# [Perf] disaggregation: Restore host-received decode KV without blocking the scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/46689) · state: closed · merged: True

## Original PR description

## Motivation

A PD decode with `--disaggregation-decode-host-receive-threshold` below 1 receives a request's KV cache into host memory and copies it to the device when the request joins a batch. The scheduler submitted that copy as the request was admitted and then called `finish_event.synchronize()`, so it waited for the in-flight forward and then for the copy while the forward stream idled. This PR removes that host wait: the copies start early, and a request joins a batch once its copy has finished on every rank that shares it.

## Modifications

- **Copies start before admission.** At the start of decode batch assembly, `_start_host_restores` starts the host-to-device copy of every waiting host-received request (`start_restore_kv_cache`), ordered after the in-flight forward. Each request keeps its copy's finish event in `ReqKvInfo.restore_done_event`.
- **All ranks admit together.** `_host_restores_ready` checks each rank's events with a non-blocking `query()`, then combines the answers with a MIN all-reduce over the attention-TP CPU group and then the attention-CP CPU group, so all ranks of a DP shard admit the same requests. PP stages cannot all-reduce there (a stage selects a microbatch's batch before the next stage starts that microbatch), so under PP every pending restore counts as ready and admission (`finish_restore_kv_cache`) waits for the copy on the host, as the synchronous restore did.
- **Moves and frees wait for the copy.** The finish event is registered with the allocator, so device page moves and frees are ordered after the copy on the device. The host slots return once the request is admitted or its row is freed; `UnifiedRadixCache.free_kv_row` waits for an in-flight copy first, and a full cache reset finishes the pending restores before destroying the tree.
- **No host waits on the restore path.** The restore's SWA window check runs on the device (`torch._assert_async`), and `restore_kv_cache` for a retracted request makes the current stream wait for the copy instead of synchronizing the host.
- **Forward-stream restores with the kernel backend.** With `--hicache-io-backend kernel` the restore copies run on the stream the forwards run on, after the in-flight forward and before this iteration's forward, through the new `L2TransferEngine.on_current_stream()` context. The direct backend reads the device indices on the host while preparing a copy, which on the forward stream would wait for the in-flight forward, so it keeps the engine's copy stream and, with overlap scheduling, fences only that stream on the forward stream.
- **Index preparation on its own stream.** `L2TransferEngine` prepares transfer indices on a new `index_stream`, and the copy stream waits for that preparation, so a host read of the indices waits only for their producer, never for copies queued earlier on the transfer stream.
- Tests: `test_decode_retraction_backup.py` returns the restores' host slots explicitly after each restore (the restore no longer does so synchronously), and `TestTransferStreamOrdering` in `test_unified_hicache_regressions.py` expects index translation on the index stream.
