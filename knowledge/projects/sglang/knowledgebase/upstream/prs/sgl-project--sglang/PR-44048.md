# [AMD][Quark] Choose the activation precision for MXFP4 dense linears on ROCm

> Split out of #41794. Stacked follow-up: #44049 (Kimi-K3 shared experts join the fused MoE front), which needs this PR.

## Motivation

On ROCm, Quark MXFP4 dense (non-MoE) linear layers run as W4A4: the activations are quantized to MXFP4 on the fly. Activation outliers in the residual stream then land in FP4 groups, which costs accuracy. On Kimi-K3 (`Kimi-K3-Quark-MXFP4-AttnFP8`), the dense MXFP4 linears are the shared experts of the 92 MoE layers and the layer-0 dense MLP. Attention is per-channel FP8, and the routed experts and the router are excluded from the dense path.

## Modifications

- Add `SGLANG_ROCM_QUARK_MXFP4_LINEAR_ACT` (`fp4` | `bf16`, default `bf16`). `bf16` dequantizes the MXFP4 weights to BF16 once at load and runs BF16 GEMMs. `fp4` keeps the packed weights and the W4A4 path. MoE experts are not affected.
- `AITER_FORCE_A8W4=1` (GPUs without FP4 activation support, e.g. gfx1250) still forces `bf16`, with a warning when it overrides an explicit `fp4`.
- Reject unknown values at startup. Off ROCm the switch is ignored, with a warning if it is set.
- Decode MXFP4 to BF16 without the int64 LUT indices and the full-size FP32 temporary, which cuts load-time memory.
- Add `QuarkW4A4MXFP4.materialize_bf16_weight()` for callers that need a dense view of the weight.
- Document the switch in the quantization guide and the environment variable reference.

**Behavior change:** the default flips from W4A4 to BF16 for every Quark MXFP4 checkpoint on ROCm, not only Kimi-K3. Other checkpoints with the same layout (e.g. `amd/Kimi-K2.6-MXFP4`: attention excluded, MXFP4 shared experts and layer-0 MLP) change too. Those layers store about 3.8× their packed size, and only Kimi-K3 was measured. Set `SGLANG_ROCM_QUARK_MXFP4_LINEAR_ACT=fp4` to keep the old behavior.

## Accuracy Tests

**Setup.** 8× MI355X, TP8, `Kimi-K3-Quark-MXFP4-AttnFP8`; base is main at `5727f08932`. Server flags: `--tp-size 8 --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.85 --max-running-requests 256 --chunked-prefill-size 16384 --max-prefill-tokens 16384 --disable-radix-cache --attention-backend triton --prefill-attention-backend aiter --decode-attention-backend aiter --sampling-backend pytorch --cuda-graph-max-bs-decode 256`. Env: `SGLANG_USE_AITER=1 SGLANG_AITER_HONOR_EXPLICIT_MEM_FRACTION=1 SGLANG_K3_RADIX4_TOPK=1 AITER_SITUV2_A4W4=1 AITER_FLYDSL_STAGE1_SCRATCH_REUSE=1 AITER_FLYDSL_STAGE2_FP8=1`. This differs from the cookbook MI355X recipe: TP8 without DCP8, and radix cache off. AITER is at `58eced25a`. With the ROCm image's AITER (`e7d2453`), main itself gives broken output on this checkpoint (GSM8K about 0.45), with or without these PRs.

GSM8K: 5-shot, all 1319 questions, three runs per side with a fresh server each time. Speed: random 8192 in / 1024 out, concurrency 2–64, 4 waves per level, one sweep per side.

| | Run 1 | Run 2 | Run 3 | Mean |
|---|---:|---:|---:|---:|
| main (dense MXFP4 linears in `fp4`) | 0.948 | 0.936 | 0.941 | 0.942 |
| this PR (default `bf16`) | 0.942 | 0.947 | 0.939 | 0.943 |

**On current main, `bf16` does not measurably change GSM8K.** The means differ by 0.001, and main alone ranges from 0.936 to 0.948 across runs. The accuracy gain that motivated the `bf16` default does not reproduce here.

That gain came from earlier runs on the Kimi-K3 ROCm performance tree (`SGLANG_ROCM_K3_AITER_MOE_PREROUTE_FP8` and `SGLANG_ROCM_K3_PTPC_FP8` off), which compared the layer-0 MLP and the shared experts separately:

| Layer-0 MLP | Shared experts | GSM8K (1 run) |
|---|---|---:|
| fp4 | fp4 | 0.892 |
| bf16 | fp4 | 0.893 |
| fp4 | bf16 | 0.914 |
| bf16 | bf16 | 0.934 |

Main does not show the fp4 loss, so it most likely comes from how that tree runs MXFP4 shared experts, not from FP4 activations as such. The 0.947 / 0.908 figures in the env-var comment and the docs come from that tree too.
