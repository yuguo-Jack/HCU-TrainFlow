# [Fix] [AMD] custom all-reduce: skip IPC setup on ROCm when it cannot be selected

[Upstream PR](https://github.com/sgl-project/sglang/pull/43676) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, `CustomAllreduce.should_custom_ar()` only selects the custom all-reduce when the GPUs are fully connected by XGMI or the deterministic 1-stage kernel is enabled. Without either, `__init__` still allocates the meta/data buffers and exports IPC handles, although the result is never used.

That setup fails when `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`: `self.buffer` comes from the caching allocator, so it is VMM-backed (`hipMemCreate`/`hipMemMap`), and `hipIpcGetMemHandle` on it returns `invalid argument`. `CUDACHECK` then calls `exit()`, so the process dies during distributed init. The SGLang Diffusion CI cases for MiniMax-H3 set this allocator option.

Observed with SGLang Diffusion, MiniMax-H3 t2va, TP2 on two PCIe Radeon AI PRO R9700 (gfx1201):

```
Failed: Cuda error .../csrc/allreduce/custom_all_reduce.hip:152 'invalid argument'
```

Single-GPU check of the failing call (`sgl_kernel.allreduce.get_meta_buffer_ipc_handle`):

| buffer | `hipIpcGetMemHandle` |
|---|---|
| `hipMalloc` / `hipExtMallocWithFlags` (default, fine-grained, uncached, contiguous) | ok |
| `torch.empty`, `expandable_segments:False` | ok |
| `torch.empty`, `expandable_segments:True` | `invalid argument` |

## Modifications

- `CustomAllreduce.__init__`: on ROCm, when the GPUs are not fully XGMI-connected and the deterministic implementation is off, return early as disabled. `should_custom_ar()` returns `False` in this case anyway, so the selected all-reduce (RCCL) does not change; only the unused IPC setup is skipped.
- New CPU unit test `test/registered/unit/distributed/test_custom_all_reduce_rocm_topology.py`: the IPC setup is skipped without XGMI, and still runs with full XGMI and/or the deterministic implementation. The skip case fails without this change.

XGMI-connected Instinct GPUs and the deterministic path are unchanged.

## Open question for maintainers (Instinct)

I could only test on PCIe RDNA4. On XGMI-connected Instinct GPUs the custom all-reduce is actually used, so the same `hipIpcGetMemHandle` call on `torch.empty(...)` should hit the same error if `expandable_segments:True` is set, and so would `register_buffer(inp)` in the deterministic path and graph buffer registration. Could someone with MI300X/MI355X confirm? If it reproduces, possible fixes are allocating `self.buffer` outside the expandable segments, or a shareable-handle path like #27593 does for CUDA (`hipMemExportToShareableHandle`). I kept this PR to the PCIe case.

## Accuracy Tests

TP2 on 2x R9700 (PCIe), ROCm 7.15, `expandable_segments:True`. gfx1201 is not a supported `sgl-kernel` target yet, so `sgl-kernel` was built with the allowlist / wave32 changes of `docker/patches/sgl-kernel-gfx1151.sh` retargeted to gfx1201; the code path changed here is architecture-independent.

- hubertlu-tw · comment · 2026-10-13T22:30:29Z · [source](https://github.com/sgl-project/sglang/pull/43676#issuecomment-6156598428)

@Shan2L Thanks for flagging this. Short answer: **yes, it reproduces on XGMI-connected Instinct GPUs**, but only on SGLang's own `CustomAllreduce`. The default ROCm path, AITER's custom all-reduce, already handles it.

**Setup:** 8x gfx1250, fully XGMI-connected, ROCm 10 / HIP 7.15, PyTorch 2.11. This isn't an MI300X or MI355X, but the failure is in the HIP runtime (a VMM-backed pointer can't be exported through `hipIpcGetMemHandle`), so I expect the same behavior there. A quick check on MI300X/MI355X would still be welcome.

**1. Which buffers can be IPC-exported (single GPU):**

| buffer | `expandable_segments:False` | `expandable_segments:True` |
|---|---|---|
| `torch.empty` (any size, base or interior pointer) | ok | `invalid argument` |
| tensor allocated during CUDA graph capture | ok | `invalid argument` |
| `allocate_meta_buffer` (uncached `hipExtMallocWithFlags`) | ok | ok |
| raw `hipMalloc` | ok | ok |

**2. Your three suspicions, tested on 2 XGMI GPUs with `expandable_segments:True`:**

- **Init:** confirmed. `register_buffer(self.buffer)` fails at `custom_all_reduce.hip:152 'invalid argument'` and the process exits, in both deterministic and non-deterministic mode. This PR's early return only covers the non-XGMI case, so XGMI is still affected.
- **`register_buffer(inp)` in the deterministic path:** confirmed for inputs at or above `max_size`. Smaller inputs are copied into `self.buffer` first, so they only export that buffer. #34543 already removes this call: it reduces oversized inputs in `max_size` pieces through `self.buffer`. With #34543 plus an init fix, a 32 MiB deterministic all-reduce passes under `expandable_segments:True`.
- **Graph buffer registration:** confirmed on the non-deterministic SGLang path (`all_reduce_reg` during capture). Even with `self.buffer` allocated outside the caching allocator, `register_graph_buffers` fails at `custom_all_reduce_hip.cuh:535`, because the captured tensors are VMM-backed. Forcing the copy-in (unregistered) path during capture fixes it. Deterministic-mode capture only registers `self.buffer`, so it's fine once that buffer is exportable.

**3. Who is affected in practice:**

By default ROCm dispatches to AITER's `CustomAllreduce`, which already handles expandable segments (ROCm/aiter#4621): its IPC-exported buffers stay on plain `hipMalloc` memory and graph capture is forced to copy-in. On the same hardware, AITER init, eager all-reduce and graph replay all pass with `expandable_segments:True`.

SGLang's own implementation, and therefore this bug, is only used with:
- deterministic inference or `SGLANG_USE_1STAGE_ALLREDUCE=1`,
- `SGLANG_USE_AITER_AR=0`, or
- AITER not installed.

**4. Suggested follow-up (separate PR, after #34543 lands):**

1. Allocate `self.buffer` outside expandable segments, either by temporarily switching the allocator setting for that one allocation (verified to produce an exportable buffer) or with a plain-`hipMalloc` op. `allocate_meta_buffer` works, but its uncached memory would likely slow down the data buffer.
2. When expandable segments are enabled, force copy-in during graph capture on the non-deterministic path, mirroring the existing `tms_cudagraph` handling.
3. Re-run `test_amd_deterministic_custom_allreduce.py` (from #34543) and an eager-plus-graph 2-GPU test with `expandable_segments:True` as a regression test.

The shareable-handle route (`hipMemExportToShareableHandle`, as in #27593) would also work, but it's a bigger change than this needs. I think this PR is fine as-is for the PCIe case.
