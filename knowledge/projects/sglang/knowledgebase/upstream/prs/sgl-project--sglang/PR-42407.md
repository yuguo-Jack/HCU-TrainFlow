# [cake_kernels] opt-in Kimi-K3 routes: KDA recurrent decode, FP8 projections, Cake MLA (SGLANG_CAKE_ROUTES) + Kimi-K3 e2e report

[Upstream PR](https://github.com/sgl-project/sglang/pull/42407) · state: closed · merged: False

## Original PR description

## Motivation
Part 2 of the Cake-kernel forwarding work for sgl-project/sglang#42176: opt-in wiring of the forwarded Kimi-K3 Cake kernels
behind `SGLANG_CAKE_ROUTES` (introduced in the Qwen3.5 routes PR #42406). Nothing changes when the switch is unset.

> **Stacked on the Qwen3.5 routes PR #42406 (`cake/08-routes-qwen35-e2e`) and therefore on #42382, #42383, #42387.** Review only the top commits.

> **FlashInfer requirement.** The Kimi-K3 routes read the generated Cake programs from FlashInfer main, not from the
> `flashinfer_python` release SGLang pins; with the switch unset nothing is imported. Co-enabling `kimi_k3_mla` with
> `kimi_k3_fp8_projection` needs FlashInfer main at or above `50a180ed0` (flashinfer-ai/flashinfer#6126, merged 2026-10-06):
> earlier builds of the Cake FP8 MLA decode kernel emitted non-finite output rows on requests with an attention-sink key
> once decode-M Cake projection outputs fed them (see "Validation"). The latest push removes the engine-side prefill-only
> default that worked around it and re-validates the unrestricted configuration against that FlashInfer commit.

## What this PR adds
- `kda_decode` (`srt/layers/attention/linear/kernels/kda_flashinfer.py`, `kda_backend.py`): KDA recurrent / fused decode through the
  Cake adapter, stock FlashInfer when admission rejects. The Cake fused decode admits Kimi-K3's `lower_bound=-5` safe gate;
  calls it does not take fall through to the Triton safe-gate kernel (engine fix below).
- `kimi_k3_fp8_projection` (`srt/models/kimi_k3_cake_projection.py`, installed from `kimi_k3.py`): FP8 projection linears
  (`q_a/q_b/kv_a/kv_b/o_proj`, fused qkv_a) on the Cake prepared projection runner with per-M eager warm-up; original quant
  method when weights/shape are rejected or a shape is first seen inside CUDA-graph capture.
- `kimi_k3_mla` (`srt/layers/attention/trtllm_mla_backend.py`): `TRTLLMMLABackend._run_decode_kernel` calls the FlashInfer
  public MLA decode entry with `backend="cake"` when the adapter's `supports_trtllm_batch_decode_with_kv_cache_mla` admits the
  call (FP8 e4m3 query + latent cache, kv_lora_rank 512 + rope 64, page size 64, no LSE / DCP / sinks), using the reduced Cake
  contract (no PDL, no skip-softmax, no multi-CTA counter buffer, host float scale). Verdict cached per query shape, logged once.
  Explicit non-trtllm-gen kernel backends and LSE-returning calls keep their kernel.
- CPU unit tests: `test_cake_kda_route.py`, `test_cake_k3_projection_route.py`, `test_cake_k3_mla_route.py`.
- Two engine fixes the Kimi-K3 configuration needs (independent of the routes; happy to split them out if preferred):
  - `KDAKernelDispatcher.decode` / `target_verify` raised `NotImplementedError` for safe-gate models (`lower_bound` set) on any
    non-Triton kernel, so `--linear-attn-decode-backend flashinfer` took the whole Kimi-K3 server down on its first decode step.
    They now reroute such calls to the Triton kernel (as `extend` already did via `effective_extend_kernel`) unless the kernel
    declares `supports_safe_gate`, logging once per kernel and mode. `test_kda_dispatcher_safe_gate.py`.
  - `ModelOptNvFp4FusedMoEMethod` resolved `--moe-runner-backend auto` only in `create_moe_runner`, while `__init__` derived
    the weight layout from the raw value: under `auto` the weights were laid out for CUTLASS and the TRT-LLM runner then failed
    with `'FusedMoE' object has no attribute 'g1_scale_c'`. `auto` is now resolved once at construction
    (`resolve_nvfp4_moe_runner_backend`) and used by the layout, the scale-shape validation and the runner.
    `test_nvfp4_moe_runner_auto.py`.

## Validation
- Kernel-level (GB200, FlashInfer at the pin): KDA recurrent/fused/packed decode, FP8 projection (M=64/512), fused router,
  FP8 MLA pass vs FlashInfer stock + torch reference; LatentMoE/AttnRes packages skipped (plans frozen for 148-SM devices,
  GB200/GB300 have 152); var-Q-after-MLA XFAIL (tracked separately).
- Architecture e2e on 2 nodes × 4 GB300 (TP8) with `--load-format dummy` (the 1.6 TB checkpoint was not reachable from the
  GB300 cluster; dummy weights exercise the real `KimiK3ForConditionalGeneration` graph, 200 GB/GPU, modelopt NVFP4 experts +
  FP8 projections, FP8 KV page 64, `--moe-runner-backend flashinfer_trtllm`, DeepGEMM disabled in that container):
  - route admission in-server: Cake KDA fused decode at every captured CUDA-graph batch (`rows=1…119, heads=12, bf16 state,
    lower_bound=-5`), FP8 projection runner prepared on all 24 MLA layers × 4 linears per rank, `kimi_k3_mla` taken at every
    captured batch (`query=(bs,1,12,576) fp8, kv page 64`).
  - engine default (triton KDA decode, trtllm-gen MLA) vs all three routes on, warm pass then measured pass: one-batch
    1024/128 TTFT −5.7 / −6.8 / −6.2 % at bs 8 / 32 / 56, 8192-token prefill TTFT −8.4 %, steady decode +0.9 / +1.5 / +2.6 %;
    serving 200 × (1024/128) at concurrency 32: TTFT median 1734 → 1658 ms, TPOT median 18.90 → 17.91 ms, total 8311 → 8673
    tok/s; +0.66 GB per GPU. bs-1 TTFT: an ABAB repeat showed Cake +6–13 ms (+2–5 %) in 3/3 pairs; one-route-per-arm attribution runs (two samples)
    put it on the FP8 projection route alone (+5 / +30 ms at M = 1024 against a ±15 ms run-to-run spread; the MLA and KDA
    arms are within the spread), while the same route makes the 8192-token prefill −5.5 % (0.440 s vs 0.466 s, stable).
    Tracked as a kernel-side follow-up; decode rate is unchanged in every arm.
  - greedy outputs and logprobs of fixed prompts identical across the two arms (same seeded dummy weights); with dummy weights
    the logits are near-uniform, so this is an ordering check, not a quality result.
  - engine fixes, same setup: routes off + `--linear-attn-decode-backend flashinfer --mamba-ssm-dtype bfloat16` now serves
    (reroute notice logged once per rank, bs-1 TTFT 266 ms / 65 tok/s), and `--moe-runner-backend auto` serves on the TRT-LLM
    runner (266 ms / 66 tok/s) — both at the engine-default level; 42 CPU unit tests of the touched files green in the container.
- **Model quality and perf on real weights** (`nvidia/Kimi-K3-NVFP4`, TP8 over 2 nodes × 4 GB300, GSM8K 5-shot greedy on all
  1319 test questions, `--moe-runner-backend flashinfer_trtllm`, FP8 KV page 64, DeepGEMM disabled in that container):

  | configuration | GSM8K accuracy | invalid answers |
  |---|---|---|
  | stock backends | 0.954 | 0.001 |
  | `kimi_k3_fp8_projection` only | 0.948 | 0.001 |
  | `kimi_k3_mla` only | 0.948 | 0.001 |
  | `kda_decode` only | 0.951 | 0.001 |

  | all three routes, projection prefill-only workaround (previous push) | 0.940 / 0.951 (two samples) | 0.002 / 0.001 |
  | **all three routes, every M, FlashInfer `50a180ed0` (this PR)** | **0.952** | **0.001** |

  First 200 / 400 / 800 questions of the final row: 0.980 / 0.980 / 0.954 (stock backends 0.985 / 0.988 / 0.958). A
  per-call check arm of the same configuration (`SGLANG_CAKE_K3_MLA_CHECK=1`, CUDA graphs off: the stock kernel runs next
  to every Cake MLA decode call on identical inputs) over 192 000 decode calls on 24 layers × 8 ranks: **0 anomalies,
  0 non-finite elements** from either kernel, max relative difference 0.07; GSM8K-200 of that arm 0.990 / 0.005
  (0.930 / 0.020 before the fix). The projection route's own eager check flagged 557 of its calls above its 0.1
  relative-error threshold, none non-finite: the expected UE8M0 requantisation drift of that route.

  Perf of all three routes at every M vs the stock backends (same two-node TP8 GB300 setup, warm pass then measured pass,
  1024-token prompts / 128 output tokens): TTFT ×1.023 / ×0.942 / ×0.921 at bs 1 / 8 / 32, steady decode ×1.048 / ×1.035 /
  ×1.026, 8192-token prefill TTFT ×0.942; serving 200 requests at concurrency 32: median TTFT ×0.941, median TPOT ×0.969,
  total throughput ×1.028; GPU memory after load ×0.999 and at the end ×1.011. Same picture as the prefill-only
  workaround (decode gains from `kda_decode`, TTFT gains from the FP8 projection route, `kimi_k3_mla` neutral at these
  shapes); the GSM8K wall time of the unrestricted run includes a one-time 29 s first-call JIT of the now-enabled decode-M
  projection kernels. Greedy logprobs vs the stock backends (8 prompts × 32 tokens): 6/8 first tokens agree, 126/131 tokens
  before divergence, max |Δ| 1.12 on the agreeing prefix (0.196 with the projection route prefill-only), i.e. the FP8
  projection route's requantisation now also applies to decode-M calls. Not bit-identical by design; quality-neutral within
  run-to-run noise (−0.2 pt at n = 1319, 1σ ≈ 0.6 pt), invalid-answer rate at the baseline.

- **Co-enabling the projection and MLA routes (resolved upstream).** With both routes on at every M against FlashInfer
  before `50a180ed0`, GSM8K dropped to 0.846 with 5 % number-less answers; the per-call comparison above traced it to the
  Cake FP8 MLA decode kernel returning non-finite rows for some sequences (query and KV finite, stock kernel finite on the
  same tensors) when fed the Cake projection's decode-M outputs. FlashInfer #6126 fixes the kernel; this PR therefore no
  longer restricts the projection route to prefill when `kimi_k3_mla` is enabled. `SGLANG_CAKE_K3_PROJ_MIN_M=<int>` remains
  as an explicit restriction (unit tests in `test_cake_k3_projection_route.py`).
- Eager-only diagnostics behind env knobs (no effect unless set, never under CUDA-graph capture): `SGLANG_CAKE_K3_PROJ_CHECK`
  / `SGLANG_CAKE_K3_PROJ_ONLY` for the projection wrapper, `SGLANG_CAKE_K3_MLA_CHECK` / `SGLANG_CAKE_K3_MLA_DUMP_DIR` for the
  MLA decode call (stock-vs-Cake comparison and a compact per-call reproducer dump).
- Engine robustness: `SGLANG_UNBALANCED_MODEL_LOADING_TIMEOUT_S` (default unchanged, 480 s). Two-node TP8 loads of the
  1.6 TB checkpoint finish 500–800 s apart across nodes and tripped the hardcoded post-load barrier on every attempt.
