# [Feature] Forward observer and deferred outputs for out-of-tree consumers

[Upstream PR](https://github.com/sgl-project/sglang/pull/43450) · state: open · merged: False

## Original PR description

## Motivation

Out-of-tree consumers need to publish forward outputs asynchronously before returning references to clients. SpecForge uses this to write target prefill hidden states into Mooncake for draft-model training. A sampling observer cannot see all forward outputs, and synchronous auxiliary-output consumption cannot hold a response until publication finishes.

## Modifications

- `ModelRunner.forward_observer` receives the batch, forward batch and logits output immediately after target forward, before sampling can clear tensors. Its optional device output joins the existing auxiliary copy/consume path. Unsupported execution modes fail at observer installation.
- `Scheduler.defer_response(req, completion)` registers one completion for a finished, unstreamed request. A completion exposes `done()`, `result()` and `cancel()`; a `Future[None]` works directly. The scheduler owns the request, polls completion during busy/idle/paused execution, finalizes metadata on its own thread and streams once.
- Aborting a held request retires scheduler ownership and cancels its completion; unexpected completion failures return an abort response. Pending requests participate in weight-version bookkeeping. Shared publication futures must not be canceled by one sibling request.
- Held requests do not affect TP-wide idle/cache/memory decisions because only the output rank owns publication. The plugin retains captured data independently of released KV cache.
- Trim the observer/deferred-response tests from 439 to 413 lines while covering lifecycle, failure, cancellation, version tracking and unsupported paths with real Futures.

## Relationship to #43449

This PR contains only the forward-observer/deferred-response changes, based on main `b6d3b7e163`. #43449 is unchanged at `46f0562481`; it provides the target-only auxiliary hidden-state capture used by the SpecForge integration test. Combining these two branches reproduces the exact source tree tested on H200 (`4854207d5fad2ff5be24eae44ea57e839a7dc300`).

The compatible consumer and separate server/trainer environment support are on [SpecForge's companion branch](https://github.com/maocheng23/SpecForge/tree/codex/pr43450-completion-plugin), based on SpecForge main `03f3682e`.

## Validation

- Focused and adjacent SGLang scheduler/observer suites: **92 passed, 10 subtests** after separating this PR from #43449.
- SpecForge local plugin/actual SGLang CPU integration/sink tests: **42 passed, 14 subtests**; launcher/configuration checks: **126 passed**. CUDA-only cases were subsequently exercised on H200.
- Fresh separate Linux server/trainer environments installed with normal dependency resolution; both `pip check` and CUDA checks passed. Server: Torch 2.14.1+cu130, Transformers 5.19.0, this SGLang stack and packaged plugin. Trainer: Torch 2.13.0+cu130, Transformers 5.12.1 and SpecForge's pinned SGLang 0.5.18. Both used Mooncake CUDA13 0.3.13.post1.
- Two H200s: **6 CUDA regressions passed**, including actual CUDA graph replay followed by asynchronous host copy, plus CUDA arena lifetime tests.
- **TP1 and TP2: 3 live tests passed at each size**, with no skips. Real Mooncake TCP reads, independent HF hidden-state/logit parity, repeated-prompt cache isolation, EAGLE3 training, and DFlash with/without teacher metrics all passed.
- Normal single and batched generation produced identical tokens between plugins excluded and capture disabled, at both TP sizes. Prefill CUDA graphs were exercised in these normal-serving comparisons.

The CUDA arena unit tests use a stand-in TransferEngine; real multi-node NVLink/RDMA was not tested. The live fixture is a locally generated tiny Llama, not a production-size benchmark.

## Performance

The earlier GB300/Qwen3.8-27B A/B measurements recorded in this PR showed output throughput -0.21% and prefill request rate -0.04%, within run-to-run variation. Those measurements predate the completion refactor and were not rerun for the current revision. Current validation establishes functionality and inactive-plugin output equivalence, not a new throughput result.
