# [Perf] attention: Support attention sinks in the split-KV EAGLE verify kernel (gpt-oss)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47513) · state: open · merged: False

## Original PR description

## Motivation
On the Triton attention backend, EAGLE target verification runs through `extend_attention_fwd`. That is the prefill kernel: one program per (sequence, head) walks the whole prefix serially. `verify_splitkv_fwd` (#27382) replaces it at `topk == 1` with a split-KV (flash-decode) kernel. Two things keep that kernel from serving gpt-oss on NVIDIA:

1. The backend enables it only on AMD gfx95.
2. `can_handle()` rejects attention sinks, and gpt-oss has sinks in every layer.

This matters most on NVIDIA SM120 (RTX PRO 6000 Blackwell, RTX 50xx), where Triton is the default attention backend for gpt-oss.
- A torch profile of gpt-oss-120b + `nvidia/gpt-oss-120b-Eagle3-v3` at TP2, batch 1, 8K context: each of the 18 full-attention layers spends ~301 µs in `_fwd_kernel` per verify step, which is 5.4 ms of a 13.9 ms speculative step.
- The drafter accepts about half its tokens (accept length ~2.1–2.2 at 2 draft tokens), yet decoding with it was slower than without it. On a closed-loop benchmark with 7.5K-token code prompts, median TPOT at batch 1 was 6.1 ms with the drafter against 4.9 ms without.

This PR adds sink support to the split-KV verify kernel. So that it can be reviewed, tested and merged on its own, it also carries the one-line gate removal from #39316 as its first commit, with @rluisr as co-author. If #39316 merges first, I will rebase and that commit first drops out.

## Modifications

Two commits:

1. **Enable split-KV EAGLE verify on CUDA** (same change as #39316). `python/sglang/srt/layers/attention/triton_backend.py` drops `is_gfx95_supported()` from `use_verify_splitkv`, and `python/sglang/srt/environ.py` updates the `SGLANG_ENABLE_SPLITKV_VERIFY` comment. `SGLANG_ENABLE_SPLITKV_VERIFY=0` still opts out.
2. **Support attention sinks in the split-KV verify kernel**
   - `python/sglang/kernels/ops/attention/verify_splitkv.py`
     - `_verify_combine_stage2`: when `HAS_SINK`, add `exp(sink - m)` to the denominator of the final prefix/draft LSE merge. This matches `extend_attention_fwd`, where the sink contributes to the softmax denominator and not to the value.
     - Pass `sinks` through `VerifySplitKV.__call__` and `verify_splitkv_fwd`.
     - `can_handle()`: accept a 1-D sinks tensor with one logit per local query head; any other shape still falls back. Sliding-window layers still fall back; they only read the window, so the extend kernel is cheap there.
   - `test/registered/attention/test_verify_splitkv.py`
     - Sink parity against `extend_attention_fwd` at gpt-oss shapes: head_dim 64, GQA 8 with 64/8 and 32/4 local heads, 3 verify rows per sequence, prefixes up to 8K. Sinks are centred on the prefix LSE so the sink term ranges from negligible to dominant.
     - The same with an fp8 (e4m3) KV cache.
     - `can_handle()` accepts correctly shaped sinks and rejects other shapes. The old "sinks fall back" assertion is replaced.

Compatibility:
- With `sinks=None` the kernel behaves exactly as before.
- On AMD gfx95, models with sinks on the Triton backend now take this path too, and the new tests run on the MI35x lane as well.
- The call site in `TritonAttnBackend.forward_extend` already passed `sinks`, so it is unchanged.

## Accuracy Tests

- `test_verify_splitkv.py` on an NVIDIA RTX PRO 6000 Blackwell (sm_120): **12 passed** (16 subtests). Max abs diff against `extend_attention_fwd` at gpt-oss shapes is ≤ 5e-3 with an fp8 KV cache and ≤ 1e-3 with bf16.
- GSM8K, `python -m sglang.test.run_eval --eval-name gsm8k --api chat --num-examples 1319 --temperature 0 --reasoning-effort low --max-tokens 4096`. Model: gpt-oss-120b + Eagle3-v3, TP2, `--kv-cache-dtype fp8_e4m3`, CUDA graphs on.

  | | GSM8K |
  |---|---|
  | before | 0.943 |
  | after | 0.955 |

- EAGLE acceptance length is unchanged (2.1–2.2 in the runs below).

## Speed Tests and Profiling

Setup:
- gpt-oss-120b + `nvidia/gpt-oss-120b-Eagle3-v3` (2 steps, topk 1, 3 draft tokens), `--kv-cache-dtype fp8_e4m3 --moe-runner-backend marlin`.
- Triton attention (the SM120 default), CUDA graphs on, PCIe RTX PRO 6000 Blackwell.
- Measured on v0.5.22 with this change applied. The changed kernel file is identical on `main`.
- Before and after use the same build, toggled with `SGLANG_ENABLE_SPLITKV_VERIFY=0/1`.

```
python -m sglang.benchmark.serving --backend sglang --dataset-name random \
  --random-input-len 7500 --random-output-len 1155 --random-range-ratio 1.0 \
  --num-prompts max(8, 4*C) --max-concurrency C --seed 1
```

| 1 | 159.2 | 254.3 | +60% | 5.97 → 3.66 ms |
| 4 | 390.3 | 547.1 | +40% | 9.03 → 6.60 ms |
| 8 | 664.4 | 814.8 | +23% | 10.61 → 8.61 ms |
| 16 | 899.0 | 1138.3 | +27% | 16.38 → 12.66 ms |

**TP1 (1 GPU, `--context-length 32768`)**

Kernel microbenchmark: `extend_attention_fwd` against `verify_splitkv_fwd`, both with sinks, 3 query rows per sequence, head_dim 64, 32 q / 4 kv heads, fp8 KV, scattered `kv_indices`, RTX PRO 6000:

| prefix | bs 1 | bs 4 | bs 8 | bs 16 |
|---|---|---|---|---|
| 2K | 55.9 → 31.7 µs | 56.2 → 31.4 | 71.7 → 30.8 | 120.0 → 43.7 |
| 8K | 209.3 → 31.6 µs (6.6x) | 209.6 → 43.6 (4.8x) | 270.2 → 73.3 (3.7x) | 449.4 → 134.1 (3.4x) |
| 32K | 825.6 → 65.8 µs (12.5x) | 828.2 → 157.7 (5.3x) | 1113.6 → 334.4 (3.3x) | 2129.9 → 583.6 (3.6x) |

Torch profile of 30 speculative steps at batch 1, 8K context, TP2: GPU time per step fell from 13.9 ms to 8.7 ms. Attention fell from 199 ms to 34 ms per 30 steps: `_verify_prefix_stage1` takes 29 µs per full-attention layer, where `_fwd_kernel` took 301 µs.

Possible follow-ups, not in this PR:
- The drafter's own draft-extend attention and the 128-token sliding-window layers still use `extend_attention_fwd`, about 0.75 ms per step together.
- A grouped-head variant, reading each KV head once per GQA group, would help larger batches.
