# [Perf] diffusion: Keep every component resident in auto mode when memory allows

[Upstream PR](https://github.com/sgl-project/sglang/pull/45978) · state: closed · merged: True

## Original PR description

## Motivation

`--performance-mode auto` places components from a static per-model allowlist. Above `keep_resident_min_available_gb` (the model's value, else 45 GB for image and 120 GB for video models) only `keep_resident_components` stay resident: the VAE by default, plus the DiT for image models. Everything else streams layer by layer at any memory size:
- Z-Image, Ideogram-4, FLUX, Qwen-Image and LTX-2 stream their text encoder even on a 288 GB GPU. A B300 server log reads `267.1 GiB of free device memory selects layerwise offload for text_encoder` and then `resident=0/36`; Z-Image-Turbo spends 0.066 s of a 0.354 s request moving 3.4 GB over PCIe.
- Wan2.2-T2V/I2V-A14B list `auto` in `dit_layerwise_offload_modes` and set no threshold, so both 14B experts stream layer by layer on every GPU, including H200/B200/B300. That also pins ~54 GB of host memory per rank.

On H100, Z-Image-Turbo with every component resident was 12% faster than auto (0.701/0.699 vs 0.793/0.799 s). The memory-aware fix was meant to come from the warmup-calibrated planner (#37917/#37918), which is not merged. This PR adds a conservative interim rule.

## Modifications

- Memory-rich tier in auto mode (`ServerArgsAutoTuner._fits_all_components_resident`): when the least-free selected GPU has at least twice the per-GPU weight bytes free, every component without an explicit placement stays resident. That means no default layerwise list, no DiT layerwise and component offload cleared, which is the placement `speed` mode gives. Explicit placement flags still win per component.
  - Weights are sized before load from the cached checkpoint's safetensors headers (`checkpoint_component_sizes` in `loader/utils.py`): every `model_index.json` component, counted in its serving precision (`resolve_component_precision`, else as stored), with DiT folders divided by `tp_size`. Text encoders count as full copies even when TP-folded, which is conservative.
  - The tier does not apply, and the per-model policy runs as before, when the checkpoint is not fully cached yet, holds non-safetensors or quantized weights, or is overridden (`--quantization`, `--transformer-weights-path`, SVDQuant, component paths, weights or quantizations, model overlays). It also does not apply with dynamic batching (the factor of two assumes one request's activations), on shared host/device memory (GB10) or on MPS.
  - The rule is platform-agnostic. On ROCm, where auto has no layerwise defaults and offloads the text encoder whole, a GPU that fits the rule now keeps it resident too.
- Wan2.2-T2V/I2V-A14B set `keep_resident_min_available_gb=120` with the DiT and VAE resident. Both experts stay on the GPU on H200-class cards and above; 80 GB cards keep streaming (the two bf16 experts alone are 53 GiB). This holds even when the tier cannot size the checkpoint.

What changes on common GPUs (single GPU unless noted; per-GPU weights at serving precision):

| Model | Weights per GPU | Tier at 2x | H100 80 GB (~79 GiB free) | H200 (~139 GiB free) | 32 GB RTX 5090 (~31 GiB free) |
|---|---|---|---|---|---|
| Z-Image-Turbo | 19.1 GiB | 38 GiB | all resident (text encoder was layerwise) | all resident | unchanged |
| FLUX.1-dev | 31.4 GiB | 63 GiB | all resident (T5 was layerwise) | all resident | unchanged |
| Qwen-Image-2.1 | 30.2 GiB | 60 GiB | all resident | all resident | unchanged |
| Qwen-Image | 53.7 GiB (TP2: 34.7) | 107 GiB (TP2: 69) | unchanged (TP2: all resident) | all resident | unchanged |
| Cosmos3-Nano | 32.5 GiB | 65 GiB | all resident | all resident | unchanged |
| Wan2.1-T2V-1.3B | 24.3 GiB (fp32 T5) | 49 GiB | all resident | all resident | unchanged |
| LTX-2 | 65.7 GiB | 131 GiB | unchanged | all resident | unchanged |
| Wan2.2-T2V-A14B | 74.9 GiB (fp32 T5) | 150 GiB | unchanged | both experts and VAE resident (threshold), T5 layerwise | unchanged |
| Ideogram-4 FP8, ModelOpt FP8/NVFP4 | not sized (quantized or `--transformer-path`) | | unchanged | unchanged | unchanged |

B200 (178 GiB free) and B300 (288 GiB) fit every bf16 row, Wan2.2-A14B included. Rows other than Z-Image-Turbo and Wan2.2-A14B follow from the sizing rule; they were not run.

Tests:
- `test_server_args.py`: Z-Image-Turbo keeps every component resident at 139 GiB free and at 45 GiB free (the bf16 serving size fits twice there, the fp32-stored bytes would not). 31 and 23 GiB free resolve exactly as an unsized checkpoint does. Batching, shared host/device memory and an unsized checkpoint keep the text encoder layerwise. Off CUDA, the tier replaces the whole-component text-encoder offload. Wan2.2-A14B keeps both experts and the VAE resident at 139 GiB free while T5 streams, and keeps everything resident at 280 GiB free with sizes.
- `test_weight_utils.py::TestCheckpointComponentSizes`: per-component sizes from a local layout and from a cached hub snapshot without network access; a partially downloaded snapshot (only `model_index.json`, as before the worker downloads), a missing shard, `.bin` weights or FP8 weights stay unsized.
- `conftest.mock_cuda_platform` and the server-args helper stub the sizing, so tests that construct `ServerArgs` for a real repo id never read the runner's HF cache.
- Docs: the `auto` row of the performance-mode table in the deployment cookbook describes the tier.

The new tests fail on main: the sizing helper does not exist there, and the all-resident, serving-precision, off-CUDA and Wan2.2 assertions fail on their own.

## Accuracy Tests

Placement only: the same modules run on the same device, so outputs do not change. On 1xH200, Z-Image-Turbo outputs for five distinct prompts have the same md5s on main and this PR.

## Speed Tests and Profiling

Z-Image-Turbo on 1xH200, flagless `sglang serve` (auto mode), 1024x1024, 9 steps. Each run: fresh server, 2 warmup requests, then 5 measured requests, each with a distinct prompt so the conditioning cache never answers the text encoder's work. Rounds interleaved main / PR / main / PR:

| | e2e median (round 1 / round 2) | `TextEncodingStage` | Peak memory per request |
|---|---|---|---|
| main (text encoder layerwise) | 0.952 / 0.954 s | 0.130 s | 15,456 MB |
| this PR (all resident) | 0.867 / 0.863 s | 0.031 s | 22,170 MB |

That is −9% end to end. Every PR sample is below every main sample (0.860–0.872 vs 0.950–1.008 s). The server logs `Auto memory policy for ZImagePipelineConfig: 139.3 GiB free on the least-free selected GPU holds the 19.1 GiB of weights per GPU at least 2x, so every component without an explicit placement stays resident.`

The same PR with all but 30 GiB of the GPU held by another process (the inputs of a 32 GB card) keeps main's placement: text encoder and VAE layerwise, DiT component-offloaded, `TextEncodingStage` 0.130 s.

Earlier evidence for the same gap: H100 Z-Image-Turbo, all resident 0.701/0.699 s vs auto 0.793/0.799 s (−12%).

Wan2.2-T2V-A14B, flagless on 1xH200 (startup only; no timed request): main streams both experts (`transformer` and `transformer_2`: 1.74 GB on the GPU, 26.18 GB pinned on the host each) and the text encoder. This PR loads both experts on the GPU (26.62 GB each) and keeps the VAE resident and the fp32 T5 layerwise, so 52 GB less pinned host memory per rank; the tier itself does not apply (150 GiB needed, 139 free). The end-to-end gain was not measured here.

## CI and baselines

The tier changes placement on the 80 GB H100 lanes wherever the checkpoint is cached and fits twice, so these scenarios will report higher `load_peak_vram_mb` / `runtime_peak_vram_mb` and fail the up-only 1%/2% memory checks by design. Their latency baselines may become stale-high (not a failure). Re-seed them with the usual two-step flow (first run prints the blocks to add to `perf_baselines/h100.json`):
- 1 GPU: `flux_image_t2i`, `zimage_image_t2i`, `zimage_image_t2i_multi_lora`, `cosmos3_nano_t2i`, `cosmos3_nano_t2v` (transformer already pinned resident; the small components join it), `sana_video_2b_t2v`, `longlive2_t2v`, `longlive2_i2v`, `fast_hunyuan_video` (38.5 GiB, 77 of ~79 GiB: closest to the line), `wan2_2_ti2v_5b`, `fastwan2_2_ti2v_5b`, `turbo_wan2_1_t2v_1.3b`, and the Wan2.1-T2V-1.3B family (`wan2_1_t2v_1.3b`, `_teacache_enabled`, `_frame_interp_2x`, `_upscaling_4x`, `_frame_interp_2x_upscaling_4x`, `wan2_1_t2v_1_3b_lora_1gpu`).
- 2 GPUs: `flux_image_t2i_2_gpus`, `zimage_image_t2i_2_gpus`, `zimage_image_t2i_2_gpus_non_square`, `qwen_image21_t2i_tp2`, `wan2_1_t2v_1.3b_cfg_parallel`, `wan2_1_t2v_1_3b_cache_dit_sp_only_2gpu`, `fsdp-inference`.
- `wan2_1_t2v_1.3b_encoder_permanent_residents` exists to test a permanent layerwise resident set on the text encoder, so it now pins the encoder layerwise with `--component-residency text_encoder=layerwise-offload`.
- Unchanged: the 5090 lane (nothing fits twice in ~31 GiB), every quantized or `--transformer-path` case, cases with explicit placement of the components that would move, Wan2.2-A14B, Qwen-Image 1-GPU, LTX and MiniMax-H3 on H100. The B200 lane runs only ModelOpt cases with `--transformer-path`/quantized weights.

The list comes from sizing each case's checkpoint at its serving precision against ~79 GiB free; a runner whose HF cache misses a model keeps main's placement for it.

## Risks

- Steady VRAM grows by the components that used to stream (Z-Image-Turbo +6.7 GB peak, the LTX-2 text encoder on H200, ~53 GiB of Wan2.2-A14B experts on H200). The factor of two leaves at least the weights' size free for activations, assuming one request at a time.
- A checkpoint that is not cached at startup is not sized, so a first start can place components differently from later ones. That is the same placement as main, never more resident.
- `ServerArgs` now reads safetensors headers of a cached checkpoint at startup (local files only, no network).
