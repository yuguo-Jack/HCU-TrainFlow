# [Perf] diffusion: Replay Triton launches without the runner's per-launch hook metadata

[Upstream PR](https://github.com/sgl-project/sglang/pull/44471) · state: closed · merged: True

## Original PR description

## Motivation

`@replay_launches` (#43859) replays a Triton wrapper's launches through `compiled[grid](*args)`, which is Triton's per-call runner. In Triton 3.7, `knobs.runtime.launch_enter_hook` and `launch_exit_hook` are `HookChain` objects and are never `None`. So on every launch the runner:
- builds a `LazyDict` of launch metadata;
- has the C launcher call into two empty Python hook chains.

That costs about 2 µs per launch on an x86 host. It is now one of the larger pieces of a replayed call.

## Modifications

`python/sglang/kernels/ops/diffusion/common/fast_launch.py`:
- When no launch hook is registered, a replayed launch calls `compiled.run(...)` directly. It passes the current stream, exactly as the runner does, and no hook metadata.
- When a hook is registered (e.g. proton or another profiler), replay keeps going through the runner, so hooks still see every launch.
- The launcher handles (`run`, `function`, `packed_metadata`) are read when the plan is built. If Triton's compiled-kernel API moves, `_record`'s existing guard therefore leaves that signature on the normal path instead of failing at replay.

No memory is involved, and the recording path is unchanged.
