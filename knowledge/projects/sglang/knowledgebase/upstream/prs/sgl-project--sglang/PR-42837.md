# [Fix] moe_sum_reduce: gate the bf16 vectorized path on hidden % 16

[Upstream PR](https://github.com/sgl-project/sglang/pull/42837) · state: closed · merged: True

## Original PR description

## Motivation

`moe_sum_reduce` has a vectorized bf16 path for `token_num > 256` that sums 16-element chunks per lane (`VEC = 16` in `moe_sum_reduce_warp_per_token_vec_kernel`), but the launcher gates it on `hidden_dim % 8 == 0` and sizes the grid from `hidden_dim / 8`. A bf16 input whose hidden dim is 8 mod 16 (e.g. 104, 120, 1032) therefore takes the vectorized path and its last 8 columns are never written, so the output keeps whatever the buffer held. At `hidden_dim = 8` no column is written at all. No shipped model config has such a hidden dim, so this is latent, but the kernel is reachable from the Triton fused-MoE runner for any `topk != 2` and it silently returns garbage for those shapes.

## Modifications

- `python/sglang/kernels/aot/csrc/moe/moe_sum_reduce.cu`: the gate and the chunk count now derive from one shared `BF16_VEC` constant that the kernel also uses, so the three literals cannot drift again. Rows that are 8 mod 16 fall through to the scalar warp-per-token path, which writes every column. Also drops a redeclared `stream` inside the fast path that shadowed the one three lines above. 13 lines.
- `python/sglang/kernels/aot/tests/test_moe_sum_reduce.py`: regression test, three cases at 257 tokens: hidden 8 and 104 (the broken shapes) and 2048 (still on the vectorized path, guards the gate change). The output buffer is pre-filled with NaN so an unwritten column cannot pass.

## Accuracy Tests

RTX 4090, torch 2.13.0+cu130, CUDA 13.0. The patched `.cu` was built standalone with `torch.utils.cpp_extension` against the installed `sglang-kernel==0.4.7` wheel's headers and compared with the wheel's kernel.

| bf16, 257 tokens, topk 8 | wheel (main) | this PR |
|---|---|---|
| hidden 8 | 8 NaN columns | matches fp32 reference |
| hidden 104 | 8 NaN columns | matches fp32 reference |
| hidden 2048 | correct | correct |

On the shapes the wheel handles correctly the output is bit-identical to the wheel (`torch.equal`) across fp16/bf16/fp32, tokens {1, 32, 257, 1024}, topk {2, 8, 9, 17}, hidden {16, 100, 2048, 7168}: 0 mismatches over 192 combinations.

The new test fails 2 of 3 cases on the current wheel and passes with the fix.

## Speed Tests and Profiling

No performance change. Shapes with `hidden_dim % 16 == 0` take exactly the same path and launch as before; the only shapes that move are the broken ones, which now go to the scalar path instead of producing unwritten columns.
