# [Perf] hicache: add an optional minimum batch size for write_back eviction

[Upstream PR](https://github.com/sgl-project/sglang/pull/48047) · state: open · merged: False

## Original PR description

## Motivation

With HiCache `write_back`, a device eviction has to wait for the forward that is running on the device (the write fence) before it can copy its victims to the host pool. `evict_for_alloc` frees only what the allocation is short of, so a busy prefill server evicts many small batches and pays that wait each time. In a PP4 prefill (GLM-5.2, 8K-token chunks, host pool 250 GB per rank), one scheduler spent about 35% of its time in `writing_check`, 79% of it waiting for the forward to end, and the GPU idled about 46% between steps.

## Modifications

- `environ.py`: new `SGLANG_HICACHE_EVICT_HEADROOM_TOKENS` (`EnvInt`, default 0 = off).
- `unified_radix_cache.py` `evict_for_alloc`: when the policy is `write_back` and the request asks for fewer full-KV tokens than the value (and more than 0), the request is raised to the value, so one call frees a larger batch. The extra victims are demoted to the host pool and stay available as prefix cache. SWA / Mamba requests, `allocation_reclaim_satisfied` calls and non-`write_back` policies are untouched.
- Unit test: `test/registered/unit/mem_cache/test_hicache_evict_headroom.py` (off by default; small request raised; large request, zero full-KV request and non-`write_back` unchanged).

## Accuracy Tests

The victims are chosen by the existing walk and written back by the existing path; only the target size changes. Checked on a v0.5.22-based build (MI355X, GLM-5.2-MXFP4, 1 prefill TP1 x PP4 + 1 decode TP4/DP4, value 524288) with a capped-pool gate: device pool limited to 300K tokens per rank so evictions are continuous and a second 16k x 128 pass loads the host copies back.

| | knob off (control) | knob 524288 |
|---|---|---|
| GSM8K 200-prompt probe | 0.965 | 0.975 |
| garbled outputs | 4 | 4 |
| long-context needle, 16k x 128 | clean | clean |

The default-size pool never evicts in the normal correctness suites, so only this capped-pool run exercises the path.

## Speed Tests and Profiling

Same build, AgentX trace replay at concurrency 104, 1 hour:

| | knob off | knob 524288 |
|---|---|---|
| tok/s/GPU | 48,360 | 49,807 and 49,631 (+2.8% mean) |
| evictions per prefill step | 1.16 | 0.11 |
| PP0 time spent in eviction (1 h) | 1,686 s | 525 s |
| median full-chunk step | 380 ms | 328 ms |
| prefix-cache hit | same | same |

Limits and caveats:
- The extra victims are kept only if the host pool has room; when it is full, `write_back` drops them (the existing "dropped without backup" path). The dropped counter stayed 0 in these runs.
- One model, one topology (PP prefill), one GPU type. The gain depends on how often evictions happen and how long the write fence waits.
- The runs above used the same logic as an environment variable on the v0.5.22-based build, without the `is_write_back` condition added here (write_back was always on there, so the condition does not change those runs). On current `main` I could run the new unit test but not the end-to-end benchmark.
- A deeper fix would remove the fence wait itself. I tried a background pre-write-back of the oldest victims: evictions became nearly free, but end-to-end throughput did not improve in this setup, so it is not proposed here.
