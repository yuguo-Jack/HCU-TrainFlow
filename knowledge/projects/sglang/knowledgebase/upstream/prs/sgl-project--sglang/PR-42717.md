# [Fix] dspark: Keep TP ranks planning the same verify budget under overlap scheduling

[Upstream PR](https://github.com/sgl-project/sglang/pull/42717) · state: open · merged: False

## Original PR description

## Motivation

Under CUDA overlap scheduling with non-static ragged verification, DSpark's verify budget is planned from confidence relayed through `ConfidenceRelay`: each step's confidence is copied to a pinned host ring on a side stream, and planning reads the slot from two steps earlier. When dynamic graph tiers are enabled, the budget selects the verify graph tier, so all TP ranks must plan the same budget.

Two things in the relay depend on per-rank timing:

- `resolve` returned `None` when the slot's copy event had not completed (`copy_done[slot].query()`). Event completion is rank-local. One rank can then plan a budget while another plans none. With the `DSPARK_PLAN` sync site enabled (the default) and confidence-based verify-length scheduling active, only the rank with a budget enters the verify-length broadcast, so the ranks' collectives no longer match. With it disabled, the ranks can pick different verify graph tiers. No sync site broadcasts the budget itself.
- The ring copy reads `confidence_buf` on the side stream. The next step's `scatter` writes the same buffer on the current stream with no ordering between them, so a copy that runs late can capture the next step's confidence.

On the CUDA overlap path, both races can occur when `FutureMap.needs_cpu_seq_lens` is false. When it is true, `resolve_seq_lens_cpu` synchronizes the shared side stream before budget planning, which masks them. DeepSeek-V4 with DSpark is one configuration where it is false.

## Modifications

- `resolve` waits for the slot's copy (`synchronize`) instead of skipping it. The selected slot is the penultimate confidence publication.
- `scatter` makes the current stream wait for the previous ring copy before overwriting `confidence_buf`. This is a device-side wait with no host synchronization.

## Accuracy Tests

`test/registered/spec/dspark/test_dspark_confidence_relay.py`:
- `test_unfinished_copy_is_waited_for` (CPU): a slot whose copy event is still pending must be waited for and resolved. On main, `resolve` returns `None`.
- `test_next_scatter_waits_for_the_pending_copy` (CUDA): delays the ring copy on its stream with `torch.cuda._sleep`, checks that the copy is still pending once the next step's scatter is issued, and requires the ring slot to hold the first step's values. Without the fix, the overwrite can leave the second step's values in the slot.

Both tests fail with main's `overlap_utils.py` and pass with this change (RTX PRO 6000 Blackwell).

## Speed Tests and Profiling

Not benchmarked. The change adds a host wait in `resolve` and a device-side dependency in `scatter`; their performance effect was not measured.
