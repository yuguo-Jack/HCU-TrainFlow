# [CI] [AMD] docker: Build MORI into the ROCm 10.1 gfx1250 image and fix its CI setup

[Upstream PR](https://github.com/sgl-project/sglang/pull/46741) · state: closed · merged: False

## Original PR description

## Motivation

The ROCm 10.1 MI45x image (`rocm/sgl-dev:*-rocm101-mi45x-*`) is built without MORI, so the MORI tests (`test_umbp_store.py`, `test_mori_backend_basic.py`) fail on it with `No module named 'mori'`.

MORI was turned off because it used to need `rocm_smi`, which ROCm 10.1 no longer ships (only `amd_smi`). The MORI version we pin (`f39fa765`) already switches to `amd_smi` on ROCm 10.1, so it can be turned back on.

While testing, two problems in the CI install script also showed up for this image:
- It didn't recognize the image's arch tag (`gfx1250-rocm1010`), guessed `gfx942` from the runner name, and installed the wrong Python extras (not the torch 2.12 set).
- When a PR bumps `MORI_COMMIT`, it rebuilt MORI for a GPU arch guessed from the runner name (`gfx942` unless MI35x), replacing the correct gfx1250 build in MI45x images.

## Modifications

- `.github/workflows/release-docker-amd-rocm10.yml`: build the ROCm 10.1 gfx1250 image with `ENABLE_MORI=1`, same as the ROCm 10.0 one.
- `scripts/ci/amd/amd_ci_install_dependency.sh`:
  - Recognize `-rocm1010` images and install `dev_hip_rocm101` extras for them.
  - Rebuild MORI for the arch stamped in the image (`IMAGE_GFX`) instead of guessing from the runner name.

## Accuracy Tests

No change to model outputs. Tested on an MI450X (gfx1250) with ROCm 10.1, on top of `rocm/sgl-dev:v0.5.22-rocm101-mi45x-20261026`: the Dockerfile's MORI step builds unchanged in ~3 minutes, then:

|---|---|
| `test/registered/unit/mem_cache/test_umbp_store.py` | 14 passed |
| `test/registered/amd/disaggregation/test_mori_backend_basic.py` | 6 passed |
