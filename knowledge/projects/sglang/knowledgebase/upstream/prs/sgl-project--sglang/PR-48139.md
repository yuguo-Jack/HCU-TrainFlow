# [Fix] models: Set k/v_scale_float when loading KV cache scales from file

[Upstream PR](https://github.com/sgl-project/sglang/pull/48139) · state: open · merged: False

## Original PR description

## Motivation

Launching a model with `--kv-cache-dtype fp8_e4m3 --quantization-param-path <scales.json>` on the Triton attention backend crashes the scheduler at the first extend:

```
triton.compiler.errors.CompilationError: at 272:22:
                qk *= sm_scale * k_scale
AttributeError("'NoneType' object has no attribute 'type'")
```

The per-model `load_kv_cache_scales` loaders set `attn.k_scale` / `attn.v_scale` but leave `attn.k_scale_float` / `attn.v_scale_float` at their initial `None`. `TritonAttnBackend` checks `layer.k_scale is not None` and then passes `layer.k_scale_float` to the kernel. The Intel AMX backend reads `layer.k_scale_float or 1.0`, so there the loaded scales are silently ignored.

Scales loaded from a checkpoint (e.g. `neuralmagic/Meta-Llama-3-8B-Instruct-FP8-KV`) don't have this problem, because `BaseKVCacheMethod.process_weights_after_loading` sets both the tensor and the float.

## Modifications

Also set `k_scale_float` / `v_scale_float` in the per-model `load_kv_cache_scales` loaders. All 8 models that have this loader are covered: llama, qwen2, glm4, opt, solar, apertus, arcee, mimo_v2.

```python
layer_self_attn.attn.k_scale = scaling_factor
layer_self_attn.attn.v_scale = scaling_factor
layer_self_attn.attn.k_scale_float = scaling_factor
layer_self_attn.attn.v_scale_float = scaling_factor
```

## Accuracy Tests

Intel Arc Pro B60 (XPU, Triton backend), `meta-llama/Llama-3.1-8B-Instruct`, `test/manual/quant/test_fp8_kvcache.py` with `kv_cache_scales_llama3_8b.json`:

| Test | Before | After |
|---|---|---|
| `TestFp8KvcacheLlama::test_mgsm_en` | server crash (CompilationError) | 0.86 (threshold > 0.80) |
| `TestFp8KvcacheLlama::test_mmlu` | server crash (CompilationError) | 0.656 (threshold >= 0.65) |

These runs added `--mem-fraction-static 0.85`, because the default leaves only about 4k KV tokens for bf16 Llama-8B on a 24 GB card. The test file itself is unchanged.

The checkpoint-scales path is unaffected. `test/registered/e2e/quantization/test_fp8kv_triton.py::TestFP8KVCacheTritonBackend::test_gsm8k` on the same machine: 0.735 (threshold > 0.70).

## Speed Tests and Profiling

No expected speed impact. The change sets two Python floats per layer once, at model load. The forward path and the kernels are unchanged.

On the Triton backend this path crashed before, so there is no "before" number to compare. For reference, after the fix `test_mgsm_en` (250 prompts) took 156 s end to end on one B60.
