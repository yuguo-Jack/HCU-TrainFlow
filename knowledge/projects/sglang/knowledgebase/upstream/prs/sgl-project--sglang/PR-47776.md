# [Perf] [AMD] gdn: Prepare prefill steps without reading device tensors back

[Upstream PR](https://github.com/sgl-project/sglang/pull/47776) · state: closed · merged: False

## Original PR description

Stacked on #47775 (pipelined GDN chunk scan); this PR is the branch's last commit. Only its `_pipeline_plan` hunk needs #47775,
the rest applies to main as is. The first of the five host reads listed below is removed by #47432; the two PRs are
measured together.

## Motivation

With the overlap scheduler the CPU prepares step i + 1 while the GPU runs step i. A long prompt is prefilled in chunks
(16384 tokens per step here), and in a profile of a 200k-token Qwen3.8-27B request on MI355X (TP1, aiter attention,
breakable prefill CUDA graph) the GPU sits idle for 1.2-1.5 ms at the start of every chunk. Running the server with
`torch.cuda.set_sync_debug_mode` shows five host reads of device tensors per prefill step; each one blocks the CPU until
the GPU has drained, so the CPU can no longer queue the next step ahead and the GPU waits for it:

- `AiterIndicesUpdaterPrefill.update_single_wrapper`: slicing `kv_indices` at `kv_indptr[-1]` (removed by #47432);
- `prepare_chunk_indices`: `.tolist()` of the chunk counts, and the copy of the indices to the device;
- the pipelined GDN chunk scan's plan: `cu_seqlens.tolist()` for the sequence length;
- `prepare_chunk_offsets`: `cu_seqlens.new_tensor([0])` (a synchronous host-to-device copy).

The values are all known on the host: the scheduler already has the extend lengths (`extend_seq_lens_cpu`, which
`logical_num_tokens` uses today). The stall only goes away when every read of the step is gone, so this PR and #47432 are
measured together below.

## Modifications

- `ForwardMetadata.query_start_loc_cpu`: the hybrid linear-attention backend keeps `query_start_loc` on the host when the
  extend lengths are trusted (the same condition as `logical_num_tokens`: lengths for every request, no two-batch-overlap
  split); otherwise it stays `None` and nothing changes.
- The GDN backend hands it to the Triton extend kernel, which passes it to `chunk_gated_delta_rule(cu_seqlens_cpu=...)`.
- `prepare_chunk_indices(cu_seqlens, chunk_size, cu_seqlens_cpu=None)`: with host offsets the indices are built on the host
  and copied in from pinned memory without blocking; the pipelined scan takes its plan from the host offsets;
  `chunk_fwd_o` builds its indices from them too (the same cached indices when its chunk size is 64).
- `prepare_chunk_offsets` pads its leading zero on the device.

## Accuracy Tests

- Unchanged by construction: the same kernels run on the same index tables.
- Unit tests: chunk indices from host offsets equal the device-built ones (values, dtype, several length mixes); chunk
  offsets equal the previous formula; `chunk_gated_delta_rule` with host offsets gives bit-identical output, per-chunk
  states and final states (one pass with three sequences, pipelined with and without a padded tail, one pass with a padded
  tail) and runs under `torch.cuda.set_sync_debug_mode("error")`; the metadata's host offsets equal `query_start_loc`
  exactly when the lengths are trusted, `None` otherwise (decode, verify, idle, two-batch overlap). MI355X, this branch:
  `test_chunk_gated_delta_rule.py` 36 passed, 1 skipped; `test_mamba_prefill_track_metadata.py` 11 passed, 90 subtests.
- Qwen3.8-27B MXFP4 end to end on MI355X (with #47432): with sync debug mode on, three 100k-token requests log no
  synchronizing call (five call sites before); greedy output ids identical to the run without the change (4 prompts),
  needle-in-a-haystack 30/30 at 100k-200k tokens, GSM8K-200 0.940 (0.930 without it, same harness); a mixed-traffic soak
  (16 prompts of 100k-200k tokens at concurrency 2 next to 600 chat requests of 1-2k tokens at 6 requests/s) completes
  every request with the same greedy output afterwards.

## Speed Tests and Profiling

Profile of a 200k-token request (MI355X, Qwen3.8-27B MXFP4, TP1, same GPU, before then after): GPU idle 50.0 -> 35.9 ms,
gaps of 20 us or more 18.7 ms in 137 gaps -> 5.2 ms in 56; the 0.4-0.95 ms gap at the start of each prefill step is gone.

End to end: Qwen3.8-27B MXFP4 (`amd/Qwen3.8-27B-Quark-AWQ-MXFP4`), TP1 on one MI355X, `--chunked-prefill-size 16384
--page-size 1 --kv-cache-dtype fp8_e4m3 --disable-radix-cache --attention-backend aiter --cuda-graph-backend-prefill
breakable` with `SGLANG_GDN_CHUNK_PIPELINE=1`; `python3 -m sglang.bench_serving --backend sglang-oai-chat --dataset-name
random --random-range-ratio 1.0 --random-output-len 1 --max-concurrency 1 --request-rate inf --num-prompts 32
--warmup-requests 1 --flush-cache`; four GPUs, two running before / after / after / before and two after / before / before
/ after; mean of the eight runs per setting:

| prompt tokens | median TTFT before (s) | after (s) | change | mean TTFT change | input tok/s before | after |
|---|---|---|---|---|---|---|
| 100000 | 2.457 | 2.455 | -2.6 ms (-0.11%) | -0.06% | 40,516 | 40,542 |
| 120000 | 3.113 | 3.111 | -2.3 ms (-0.07%) | -0.12% | 37,744 | 37,789 |
| 140000 | 3.834 | 3.828 | -5.9 ms (-0.15%) | -0.16% | 36,740 | 36,798 |
| 160000 | 4.608 | 4.598 | -9.6 ms (-0.21%) | -0.23% | 34,754 | 34,835 |
| 180000 | 5.429 | 5.422 | -7.5 ms (-0.14%) | -0.14% | 33,186 | 33,234 |
| 200000 | 6.317 | 6.309 | -7.9 ms (-0.13%) | -0.13% | 31,926 | 31,967 |

19 of the 24 GPU x length comparisons are faster with the change. The stall is per prefill step, so it weighs more when
steps are short or the CPU has other work. Mixed traffic on one GPU (16 prompts of 100k-200k tokens at concurrency 2, plus
600 chat requests of 1-2k tokens and 100-200 output tokens at 6 requests/s; before / after / after / before): the long
prompts' input tok/s 31,065 / 31,018 -> 31,419 / 31,364 (+1.1%), their P99 TTFT 10.60 / 10.63 -> 10.11 / 10.12 s (-4.7%);
chat P99 TTFT 4.92 / 5.16 -> 4.82 / 4.82 s. Prompts that fit in one or two prefill steps see no change (2k / 8k / 32k
tokens: median TTFT -0.6 to +0.1%, within noise): with a single step there is no next step for the CPU to prepare.
