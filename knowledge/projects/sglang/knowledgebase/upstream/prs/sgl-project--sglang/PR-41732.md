# [FP8 KV] Saturate bf16->e4m3 KV/QKV casts to ±448 instead of overflowing to NaN

[Upstream PR](https://github.com/sgl-project/sglang/pull/41732) · state: closed · merged: False

## Original PR description

## Motivation

Several bf16 -> `float8_e4m3fn` producers cast with overflow-to-NaN semantics: a finite value with |x| > 448 becomes a NaN byte (0x7F/0xFF) instead of saturating to ±448. Once written into the FP8 KV cache, that NaN poisons every later attention read of that token. Affected producers on main:

- `MLATokenToKVPool.set_kv_buffer` (`.to(fp8)` on cache_k / k_nope / k_rope),
- `mla_quantize_without_rope_for_fp8` in `kernels/ops/attention/utils.py`,
- the fused JIT kernel `set_mla_kv_concat_q.cuh` (NOSAT cvt),
- `_quantize_fp8_qkv` in `trtllm_mla_backend.py` (q / k / v).

## Modifications

- Add `to_fp8_satfinite(x, dtype)` in `kernels/ops/quantization/fp8_utils.py` (clamp to ±finfo.max, then cast; NaN stays NaN; no-op if `x` is already `dtype`, matching `Tensor.to`).
- Use it in the Python producers above; switch the JIT kernel's cvt to SATFINITE.
- Tests:
  - `test/registered/unit/kernels/test_fp8_kv_satfinite_unit.py` (CPU),
  - `test/registered/unit/layers/attention/test_trtllm_mla_quantize_fp8_qkv_satfinite.py` (CPU),
  - `test/registered/kernels/ops/attention/test_set_mla_kv_concat_q_fp8.py` (18 GPU cases: bit-exact vs `clamp(±448).to(fp8)` aten chain, strided views, int32/int64 locs, CUDA-graph replay, DCP loc semantics, alignment guards).

## Accuracy Tests

- CPU: the two unit files pass (2 + 2).
- GPU: `test_set_mla_kv_concat_q_fp8.py` has **not** been run on this branch yet (CPU-only environment; its 18 cases fail with "Torch not compiled with CUDA enabled" there). It passed on our internal branch carrying the same kernel change; a Hopper run on this branch is pending.

## Speed Tests and Profiling

Saturation is one extra clamp in the Python paths and a different cvt modifier in the JIT kernel. Not separately benchmarked on main.
