# [Fix] [AMD] tilelang: Zero masked KV loads in the BF16 sparse MLA decode kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/44541) · state: open · merged: False

## Original PR description

## Motivation

On HIP, `sparse_mla_fwd_decode_partial` is used for both prefill and decode. For invalid (`-1`) top-k indices it loaded KV row 0 and relied on a `-inf` score mask. Padded CUDA-graph rows write their K/V into row 0 (`out_cache_loc` padding is 0). Once row 0 held a non-finite value, `-inf + q·k` and `0 * v` became NaN for every later request.

With BF16 KV and decode CUDA graphs, the server was correct until the first decode batch whose size had no captured graph (for example 3 requests replayed in the batch-size-4 graph). After that, every request returned the right first token followed by `!!!!...` and `None` logprobs until the server restarted. Eager decode and FP8 KV were not affected. `SGLANG_ENABLE_WAR_BARRIER=1` did not help.

This showed up on GLM-5.3-Flash BF16 RL rollout on MI355X and is independent of the model: any BF16 sparse-MLA decode that uses this kernel and CUDA graphs can poison the server.

## Modifications

In `sparse_mla_fwd_decode_partial`, masked slots now load zeros instead of row 0, in both the main and tail parts. The score mask is unchanged. The FP8 kernel (`sparse_mla_fwd_decode_partial_fp8`) has the same load pattern and is not changed here.

## Accuracy Tests

On a fresh MI355X server with BF16 KV and decode CUDA graphs, padded batches of 3 and 5 were correct, and so was every request afterward. After 128 concurrent requests with 4K outputs, single-request and 32-request probes were still correct. Teacher-forced logprobs against the previous torch sparse-MLA path differed by about 0.05 per token with no directional bias.

## Speed Tests and Profiling

MI355X, one TP8 engine, BF16, TileLang DSA, AITER MoE, decode CUDA graphs up to batch size 128: 3,575 tok/s (17.4 ms/step) at 64 requests of 512 in / 1024 out, and 4,215 tok/s (21.3 ms/step) at 128 requests of 512 in / 4096 out. The zero-fill replaces a load of row 0; it is not a throughput change.
