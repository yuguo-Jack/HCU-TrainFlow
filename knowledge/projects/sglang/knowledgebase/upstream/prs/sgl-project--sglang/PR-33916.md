# [Perf] [AMD] kimi-k3: Remove per-layer copies from the aiter MoE path

[Upstream PR](https://github.com/sgl-project/sglang/pull/33916) · state: closed · merged: True

## Original PR description

<!-- Thank you for your contribution! Please follow these guidelines to enhance your pull request. If anything is unclear, submit your PR and reach out to maintainers for assistance. Join our Slack community at https://slack.sglang.io to discuss further. -->

## Motivation

Removes 2 elementwise kernels from the Kimi-K3 MoE path: the D2D copy of the routed output and the contiguous copy of `routed_input`.

<!-- Describe the purpose and goals of this pull request. -->

## Modifications

<!-- Detail the changes made in this pull request. -->
Three independent commits.

**MoE output zero-copy.** Hooks the aiter runner into `zero_copy_context`: the caller-published buffer is passed down through a new `output` argument on `aiter.fused_moe` so the top-k sum lands there directly, dropping the trailing `latent.copy_()` in `_forward_routed`. Depends on https://github.com/ROCm/aiter/pull/4617; it is probed with `inspect.signature`, so older aiter builds fall back to the copy.

**Skip the `routed_input` contiguous copy.** The fused front splits gate_up / router_logits / routed_input out of a single GEMM's output, so `routed_input` is a non-contiguous view. The mxfp8 quant kernel aiter uses for K3 indexes rows by `input.stride(-2)`, so it can consume that view as is.

### 2. A strided `routed_input` for every aiter route

`_moe_front_needs_dense_bf16` now skips the `.to().contiguous()` for any aiter runner. As the docstring says, only one route was checked. Which route K3 takes inside `fused_moe` depends on aiter's env vars and tuned configs, not on the sglang quant method. At the pinned aiter:

- **A8W4** (`AITER_SITUV2_A8W4=1`, what the cookbook ships): the activation quant reads `input.stride(-2)` on both its fused and split paths (`fused_dynamic_mx_quant_moe_sort_hip`, `dynamic_per_group_scaled_quant`). Fine, as you say.
- **Default** (neither env var set): SiTUv2 resolves to a16w4, and the FlyDSL a16w4 gemm1 calls `a.to(torch.bfloat16).contiguous()` itself. The copy moves into aiter, so nothing is saved.
- **A4W4** (`AITER_SITUV2_A4W4=1`, listed in the cookbook as a supported alternative): stage1 receives the raw `hidden_states`. I couldn't confirm that its inline-quant kernel honors the row stride.
- **Other aiter MoE methods** (fp8, unquantized bf16, Quark W4A8): not checked.

A kernel that ignores the row stride reads the wrong rows and gives wrong output without any error. Please limit the opt-in to what was verified. One option is to key it on the A8W4 route, the same way `mxfp4.py::_aiter_situ_uses_gu_interleaved_weights` already mirrors aiter's SiTUv2 precedence. The other is to show that each remaining route gives the same result with a strided input as with a contiguous one, e.g. an op-level comparison on MI355X. The clause also relies on the front being bf16 on ROCm (`_front_fp32` is CUDA-only). Please put `not self._front_fp32` in the condition or state it in the docstring. Also, `FusedMoE` always sets `runner`, so write `self.experts.runner` instead of `getattr(self.experts, "runner", None)` (`.claude/rules/no-getattr-defensive.md`).

### 3. The correction-bias commit

- **It no longer removes a kernel.** Since #33838, `select_experts` casts the bias to the logit dtype once, through `TopKConfig.correction_bias_for_dtype`, and reuses the result. On current main, K3 on aiter launches no per-layer bias cast with or without this commit.
- **Storing the bias in bf16 rounds it, as the correction above explains.** That changes routing on one path today. With `SGLANG_OPT_USE_JIT_KERNEL_GROUPED_TOPK=1` on ROCm, K3 takes the JIT router (`num_expert_group == 1`). That router receives the exact fp32 bias on main. With this commit it gets the rounded bias, plus a `.to(float32)` cast per layer.
- **It also decides K3's routing precision on ROCm once #44797 lands:** the bias would stay bf16 instead of taking the fp32 path.

Please drop this commit from the PR, so the PR stays a pure copy removal with bit-identical outputs. If K3 should deliberately route with a bf16 bias on ROCm after #44797, that belongs in its own PR. That PR should show accuracy with a bf16 bias against an fp32 bias, and a profile showing that the logits upcast matters. If you keep it here, then:
- fix the comment (the checkpoint values are not exact in bf16);
- gate it on the consumer rather than on `SGLANG_USE_AITER` (skip it when the JIT router is enabled);
- read the flag through `envs.SGLANG_USE_AITER.get()` instead of adding a new `get_bool_env_var` call site.

**Correction:** the premise below is wrong; Kimi-K3's checkpoint bias is F32 and not exact in bf16. See https://github.com/sgl-project/sglang/pull/33916#pullrequestreview-5560853915.

Heads-up on how this composes with #44797 (open), which keeps an fp32 correction bias in fp32 on the aiter routing path (it upcasts the logits instead of downcasting the bias), because GLM-5.x stores an fp32 bias whose spread is only a few bf16 ULPs wide.

Kimi-K3 is caught by that change only because `post_load_weights` converts its bias to fp32: the checkpoint values are bf16, so they are exact in bf16 and the fp32 path gains K3 nothing while adding a logits upcast per call. With this PR, K3's bias stays in the gate-logit dtype on aiter, so K3 keeps routing in bf16 there whichever of the two lands first, while GLM-5.x gets fp32 routing from #44797. No change requested here; worth keeping in mind if either PR's condition changes.
