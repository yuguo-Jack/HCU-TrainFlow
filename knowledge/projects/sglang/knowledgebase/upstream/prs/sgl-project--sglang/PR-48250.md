# [Perf] [NVIDIA] qsa: JIT CUDA kernel for the indexer decode scoring

[Upstream PR](https://github.com/sgl-project/sglang/pull/48250) · state: open · merged: False

## Original PR description


## Motivation

The QSA indexer of Qwen3.8-Flash-Next (`qwen4_exp`) scores every compressed key of every decode and verify row once per layer (`qsa_mqa_decode`). On long contexts this decode scoring is memory-bound: each row streams its request's compressed keys, and the TileLang kernel reloads them for every row and synchronizes the CTA several times per 64-key group.

This PR adds a JIT CUDA kernel that writes **the same logits, bit for bit**, but moves the data more efficiently. Model outputs do not change.

## Modifications

- `python/sglang/kernels/jit/csrc/attention/qsa_mqa_decode.cuh` (new, JIT): every logit runs the instructions the TileLang decode kernel emits, in the same order (`mma.sync.m16n8k16` bf16→fp32 over head_dim 128 in ascending k, `max(·, 0)`, the same head-sum order, division by the scale under fast math). Only the data movement changes:
  - the query rows that share a page-table row are staged in shared memory once per CTA;
  - each CTA strides over many 64-key groups of its request with double-buffered `cp.async` page gathers;
  - verify rows of one request (`rows_per_request`) reuse one load of each key group, and a group needs two CTA barriers instead of one per row plus one.
- `python/sglang/kernels/ops/attention/qsa_mqa_decode.py` (new): the JIT loader and `qsa_mqa_decode_logits`.
- `python/sglang/srt/layers/attention/qsa/mqa.py`:
  - `cuda_qsa_mqa_decode` (same signature and logits contract as `tilelang_qsa_mqa_decode`) and `use_cuda_qsa_mqa_decode` (coverage check);
  - `qsa_mqa_decode` tries the CUDA kernel first. It covers bf16 scoring with at most 8 query heads of dim 128 and 16 compressed keys per page, on B200/GB200 (SM100), B300/GB300 (SM103) and RTX PRO 6000 / RTX 50 series (SM120). Everything else (fp8 scoring, other shapes, other devices) keeps the TileLang kernel;
  - the logits allocation and query-head padding move into two helpers shared by both paths (no behavior change).
- `python/sglang/srt/layers/attention/qsa/qsa_indexer.py`: for CUDA-graph target verify, `QSAIndexer` passes the draft-token count to `qsa_mqa_decode` as `rows_per_request` (consecutive rows that share a page-table row); `qsa_mqa_decode` forwards it to the CUDA kernel only. #46631 (open) adds the same plumbing for its grouped TileLang kernel on SM107; whichever PR merges second drops the duplicate lines.
- Tests: `test/registered/kernels/ops/attention/qsa/test_qsa_mqa_decode_cuda.py` (bitwise vs TileLang, one row per CTA and verify rows, CUDA-graph replay, dispatch). Benchmark: `test/registered/kernels/benchmark/attention/bench_qsa_mqa_decode.py`. The fake indexers in `test_qsa.py` and `test_qsa_indexer_xpu.py` and the mock in `test_qsa_determinism.py` accept the new `rows_per_request` keyword.

No new server argument or environment variable.

## Accuracy Tests

The kernel is exact, so outputs do not change.

**Kernel, bit for bit.** The CUDA kernel's logits were compared with the TileLang kernel's (`view(torch.int32)`, every written logit) on GB200 (SM100), GB300 (SM103) and RTX PRO 6000 Blackwell Server Edition (SM120): 27 cases (8-128 requests, 1/2/4 rows per request, 777-9000 compressed keys, `min_scored_len` 0 and 512, 1/7/64 CTAs per request, one row per CTA and shared verify rows). **0 mismatching logits in every case on all three GPUs.** The new unit test passes on all three (8/8).

**Full model, token-identical.** `nvidia/Qwen3.8-Flash-Next-NVFP4`, 1x GB200, same node and container for both arms:
```bash
python3 -m sglang.launch_server --model-path nvidia/Qwen3.8-Flash-Next-NVFP4 --tp-size 1 \
  --mem-fraction-static 0.80 --mamba-ssm-dtype bfloat16 --chunked-prefill-size 4096 \
  --enable-deterministic-inference --attention-backend flashinfer \
  --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4
```
- 4 text prompts (one about 6,000 words, several prefill chunks) and 4 image chats, greedy, 96 new tokens, each sent twice: **16/16 outputs identical** between main and this PR.
- 48 concurrent greedy requests with 6,000-token prompts (192 decode-verify rows), 64 new tokens: **48/48 identical** to main. A second identical pass is answered from the prefix cache, where even main differs from its own first pass (34/48), so only the first pass is compared.
- A temporary log line in the PR arm confirmed the CUDA kernel ran for both decode/draft rows (1 row per CTA) and target-verify rows (4 rows per CTA).

Existing tests, same GPU and container, main vs this PR: `test_qsa.py` (300 passed, 1 skipped), `test_qsa_indexer.py` (38 passed), `test_qsa_determinism.py` and `xpu/test_qsa_indexer_xpu.py` give identical results on GB300 (4 passed; 1 passed, 1 skipped) and RTX PRO 6000. The fakes and the mock in `test_qsa.py`, `test_qsa_indexer_xpu.py` and `test_qsa_determinism.py` take the new `rows_per_request` keyword.

The upstream e2e test `test/registered/e2e/models/test_qwen4_exp_models.py` (TP4, gsm8k 200 via `sgl-eval`, default non-deterministic serving) passes on GB200 with this PR: base 0.970 (main 0.970), MTP 0.950 (main 0.975; 5 of 200 problems, within run-to-run variance of the non-deterministic mode).

## Speed Tests and Profiling

**Kernel** (`test/registered/kernels/benchmark/attention/bench_qsa_mqa_decode.py`, `marker.do_bench` with CUDA graphs and cold L2, median µs). Qwen3.8 indexer shapes: 4 query heads x 128, 16 compressed keys per page, `min_scored_len` 512; `context` = compressed keys per request.

| 2048 | 1 | 256 | 42.94 | 42.32 | 1.01x | 100.85 | 103.41 | 0.98x |
| 2048 | 4 | 64 | 38.08 | 18.36 | 2.07x | 49.16 | 29.26 | 1.68x |
| 8192 | 1 | 64 | 50.76 | 31.85 | 1.59x | 120.62 | 97.87 | 1.23x |
| 8192 | 4 | 64 | 126.88 | 43.91 | 2.89x | 185.24 | 104.57 | 1.77x |
| 32768 | 1 | 64 | 178.35 | 97.33 | 1.83x | 485.86 | 379.75 | 1.28x |
| 32768 | 1 | 256 | 557.48 | 350.12 | 1.59x | 1560.48 | 1499.55 | 1.04x |

| 32768 | 4 | 256 | 1458.57 | 507.30 | 2.88x | 2823.94 | 1592.82 | 1.77x |

Over the full 18-shape grid: GB300 1.01-1.83x for one row per request and 1.79-3.44x for 4 verify rows; GB200 1.01-1.87x and 1.77-3.45x; RTX PRO 6000 0.98-1.28x and 1.62-2.68x. On the GDDR7 card both kernels run close to memory bandwidth for plain decode, so the gain there comes mainly from verify rows sharing each key load; the one slower shape (-2.5 %, 256 requests x 2048 keys) would prefer 16-32 CTAs per request, but 64 is within 1-2 % of the best count everywhere else and keeps one launch configuration.
