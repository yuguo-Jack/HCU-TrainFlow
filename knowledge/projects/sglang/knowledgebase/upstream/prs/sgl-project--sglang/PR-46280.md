# [Doc] cookbook: Fill the Qwen3.8-Flash-Next NVFP4 B200/B300 benchmark cells

[Upstream PR](https://github.com/sgl-project/sglang/pull/46280) · state: open · merged: False

## Original PR description

## Motivation

The B200 and B300 NVFP4 cells on the Qwen3.8-Flash-Next cookbook page have been empty placeholders. @dhruvrnaik measured both on Modal and posted the results, the raw per-run data, and the launch and benchmark commands in #41919 (B200) and #41937 (B300), naming this file as the target. This PR adds their speed rows. Thanks @dhruvrnaik for the runs and for including the raw data, which made the numbers checkable.

Closes #41919
Closes #41937

## Modifications

`docs/src/snippets/configs/Qwen/qwen3.8-flash-next-benchmarks.jsx`: the four empty B200/B300 NVFP4 entries are replaced by six speed entries (36 rows):

| Cell | PLE Offload | Concurrencies (1024/256 and 8192/1024) |
| --- | --- | --- |
| B200 low latency | Auto | 1, 16, 32 |
| B200 high throughput | Auto | 1, 16, 64 |
| B300 low latency | Auto, On | 1, 16, 32 |
| B300 high throughput | Auto, On | 1, 16, 64 |

- Entries key on `pleOffload`, an overlay dimension `findBenchmark` already supports. A PLE Offload setting nobody measured (Off on both cards, On on B200) shows the existing "pending" state instead of borrowing another setting's numbers.
- `latencyPercentile: "Mean"`, because TTFT and TPOT are per-run means. Each row records the `num_prompts` that was run, so the Reproduce modal uses the real prompt counts.

### Measured before #45245

The runs used these cells exactly as they stood on the `qwen38flashnext` image (593134d17a), which means a BF16 KV cache and a BF16 QSA indexer. #45245 has since added `--kv-cache-dtype fp8_e4m3 --qsa-indexer-dtype fp8_e4m3` and moved the image to v0.5.22, so the card now sits under a command that differs from the one measured. #45245 kept the page's existing accuracy rows on the same basis. Here, each entry also carries a card note and a `sglang_version` that say how it was measured. If you would rather wait for a v0.5.22 re-run with the FP8 flags, I can close this and ask for one on the issues.

### GSM8K left out

The issues also report GSM8K (about 91.6%), measured with `sglang.test.run_eval`, zero-shot, with the legacy numeric-answer scorer. That protocol differs from the other rows on this page (the thinking-mode evals, and the thinking-off chat protocol that scores about 97% on the DGX Spark and RTX PRO 6000 rows), and `run_eval` is deprecated in favor of sgl-eval. The scores are not comparable, so they are not added. #41937 also reports the identical score, 0.915845, for two different B300 configurations.

## Speed Tests and Profiling

The numbers come from the issues. Setup: 1x B200 or 1x B300 on Modal (8 CPU cores, 128 GiB host RAM), TP=1, `RadixArk/Qwen3.8-Flash-Next-NVFP4` at revision 7b71922. They ran `sglang.bench_serving` on the random dataset with range ratio 1, request rate `inf`, temperature 0 and `--flush-cache`: two warmup runs, then three measured runs per workload. Each metric is the median of the three per-run values, and throughput is (input + output) tok/s per GPU.

Verification:

- Recomputed every median from the raw runs posted in the issues. All 36 rows match the posted records, and every run completed all of its prompts and output tokens.
- Loaded the edited file under Node and compared each entry with the recomputed values: no mismatches.
- Replayed `findBenchmark` for B200 and B300, both strategies, and PLE Offload Auto, On and Off. Each selection resolves to the intended entry or to "pending", and the untouched cells resolve as before.
- `node docs/scripts/check_cookbook_configs.mjs` passes. It skips benchmark files, so the checks above are the ones that cover this change.
- Not rendered locally (no Mintlify CLI).

One thing to know when reading the B300 rows: short prompts are slower on B300 than on B200. At 1024/256 with concurrency 1, TTFT is about 170 ms against 80 ms, and low latency at concurrency 16 gives 5,944 against 8,436 tok/s/GPU. The 8192/1024 rows are on par. The 8-core hosts may explain it, but that is unconfirmed; the rows are kept as measured.
