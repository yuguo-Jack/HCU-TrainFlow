# [Fix] openai: Enforce --trust-request-chat-template on responses, decisions and systemone

[Upstream PR](https://github.com/sgl-project/sglang/pull/44765) · state: open · merged: False

## Original PR description

## Motivation

`--trust-request-chat-template` is off by default, so a request can't swap the server's chat template by sending `chat_template` in `chat_template_kwargs` (#28135). That check only lives in `OpenAIServingChat._validate_request`, so it only covers the routes that go through it. `/v1/responses`, `/v1/decisions` and `/v1/systemone` also take `chat_template_kwargs` and hand it straight to `apply_chat_template(**kwargs)`, so on a default server the override went through on all three.

I hit this on `/v1/responses` first and then went looking for other routes with the same field. `/v1/messages` doesn't have the field in its schema, so it isn't affected.

## Modifications

- Moved the check into `OpenAIServingBase._request_chat_template_error`. The chat route uses it with the same behavior as before.
- `create_responses`, `OpenAIServingDecisions._validate_request` and `SystemOneServing._validate_request` now call it and return a 400.
- One rejection test per route, added to the existing test files. The image-marker test in `test_serving_decisions.py` sends a request `chat_template` on purpose, so I set `trust_request_chat_template=True` there.

Checked on a live server (Qwen3-0.6B), sending `{"chat_template": ...}` with the default flags:

| route | before | after |
|---|---|---|
| `/v1/chat/completions` | 400 | 400 |
| `/v1/tokenize` | 400 | 400 |
| `/v1/responses` | 200, template applied | 400 |
| `/v1/decisions` | template applied | 400 |
| `/v1/systemone` | template applied | 400 |

With `--trust-request-chat-template` the override is still accepted everywhere, and ordinary kwargs like `enable_thinking` work the same on every route.

One behavior change to be aware of: a Harmony request that includes `chat_template` now gets the 400 too, where before the value was silently ignored. I haven't run a Harmony model.

If you'd rather keep this to `/v1/responses` and handle decisions/systemone separately, I'm happy to split it.
