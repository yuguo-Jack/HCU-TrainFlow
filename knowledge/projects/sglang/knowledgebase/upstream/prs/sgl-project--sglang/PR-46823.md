# [Fix] rust_extensions: Bound the Rust toolchain probe and run it one process at a time

[Upstream PR](https://github.com/sgl-project/sglang/pull/46823) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

In a source checkout, `load_rust_extension` fingerprints the Rust toolchain before it looks for a cached build: every process that loads an extension runs `cargo --version --verbose` and `rustc -vV` in `rust/`. `rust/rust-toolchain.toml` pins Rust 1.92. When that toolchain is missing (the SGLang images ship rustup with only `stable`), rustup's `cargo` and `rustc` proxies first download and install it, about 105 MB into `RUSTUP_HOME`.

Several processes can reach these queries at the same moment, from two places:

- Every scheduler builds its model's multimodal processor at startup for the M-RoPE fallback, and the DeepSeek-V4.1 image processor loads the `_multimodal` extension.
- Every scheduler that builds the default `UnifiedRadixCache` checks whether the Rust TreeCore is usable (`_rust_fallback_reason` in `tree_core_registry.py`), and that check runs the same two queries with a 10 s limit.

With DP attention, all ranks on a node therefore probe together and start concurrent rustup installs into one `RUSTUP_HOME`; nothing makes them wait for each other.

- In our DeepSeek-V4.1 runs on GB300 (DEP16 decode, SGLang from a source checkout), 3 of 4 ranks per node failed the probe within seconds and fell back to PIL, while the 4th installed the toolchain, usually in about 5 s.
- On one node in each of 2 launches, that 4th probe never returned: its `cargo` proxy stayed inside the install with no open sockets and its threads waiting on futexes. `subprocess.run` has no timeout, so the rank never finished init, and the other 15 ranks waited for it in the first startup all-reduce until the job was cancelled.
- #45469 reports the same probe failing intermittently in AMD CI: in `test_inkling_small_6layer_lora_ci.py`, an engine did not start because `cargo --version --verbose` returned non-zero while it loaded the Inkling Rust image processor.

This PR puts the probe in one loader helper, `probe_rust_toolchain`, and calls it from both places. The helper runs the two queries under a file lock in the extension cache, so processes probe one at a time and only the first one installs the toolchain; the others then find it installed. One deadline covers the wait for the lock and both queries: 300 s for extension loads and, as before, 10 s for the TreeCore check. A probe that passes its deadline fails the same way a missing toolchain does (the V4.1 image processor falls back to PIL, the cache to the Python TreeCore) instead of blocking startup. Fingerprint values, cache paths and build behavior are unchanged.

- **Accuracy:** no output change. Only the scheduling and duration of the version queries change.
- **Performance:** server start can no longer hang on a stuck probe. Processes that share the cache now take turns: on a machine without the pinned toolchain, the first one installs it (about 5 s in our runs) while the others wait; after that, each probe is two version queries.

## Modifications

**+87 / −25 runtime code (2 files), +177 / −16 tests (2 files).** No kernel changes.

- `loader.py`:
  - `probe_rust_toolchain(workspace, lock_path=None, timeout=300)` runs `cargo --version --verbose` and `rustc -vV` in `workspace` under `lock_path`, with one deadline for the lock wait and both queries. Past it, it raises `RuntimeError` ("the Rust toolchain probe timed out after 300 s waiting for ...").
  - `toolchain_lock_path(cache_dir=None)` returns `<cache root>/locks/toolchain.lock`. `load_rust_extension` passes it to `_build_context`, which now calls `probe_rust_toolchain`.
  - `_filesystem_lock` takes an optional deadline (a non-blocking `flock` retried every 0.1 s). The build lock still waits without one.
- `tree_core_registry.py`: `_rust_fallback_reason` calls `probe_rust_toolchain(workspace, lock_path=toolchain_lock_path(), timeout=10)` instead of running the queries itself, and falls back to the Python TreeCore when it raises.

**Issue**

This lock covers only the loader. `_rust_fallback_reason` in `python/sglang/srt/mem_cache/unified_cache/tree_core_registry.py` (lines 92-105) runs the same `cargo --version --verbose` and `rustc -vV` in `rust/` without this lock, with a 10 s timeout. Every scheduler in a source checkout runs it when it builds the default `UnifiedRadixCache` with the default Rust TreeCore.

**Example**

A text-only model with DP attention runs from a source checkout without the pinned toolchain. No scheduler loads a Rust extension before the cache build, so all ranks on a node still start rustup installs into one `RUSTUP_HOME` at once. Ranks whose probe fails or runs past 10 s fall back to the Python TreeCore.

**Fix**

Put the locked, bounded probe in one loader helper and call it from both `_build_context` and `_rust_fallback_reason`.
