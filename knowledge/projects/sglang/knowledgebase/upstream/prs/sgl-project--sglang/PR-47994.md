# [Fix] moe: Revert the JIT rewrite of `moe_finalize_fuse_shared` (#47784)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47994) · state: closed · merged: True

## Original PR description

- Revert #47784 (`ca819c11cd`), the JIT rewrite of `moe_finalize_fuse_shared`: restore `moe_finalize_fuse_shared.cu` and its Python wrapper byte for byte, and drop the new `.cuh` kernel with its unit test and benchmark.
- Keep the `fma_f32x2` / `mul_f32x2` / `add_f32x2` helpers #47784 added to `sgl_kernel/math.cuh`; `kimi_k3/attn_res/fused_tma.cuh` uses them now.
- #47784 drops GSM8K of `test_dsa_glm52_hisparse.py` (GLM-5.2-NVFP4, 1P1D, HiSparse + MTP) on 8-gpu-b200 from ~0.95 to ~0.90, below its 0.935 threshold. The test is nightly-only, so the PR's CI did not run it.
- The failure reproduces on 8-gpu-b200 only; on 8x B300 the same commits pass (0.942-0.950).

No behavior change other than going back to the pre-#47784 finalize kernel.

## Suspected cause

cc @DarkSharpness @BBuf. This is our reading of the code, not yet confirmed by a targeted run.

- With `routing_ready=True`, the default and what `finalize_flashinfer_trtllm_deferred_output` passes, the new kernel loads the routing tensors **and the `shared_output` row** before `PDLWaitPrimary` (`moe_finalize_fuse_shared.cuh`, `Token::load` and `finalize_kernel`).
- The old kernel also staged the routing tensors before `cudaGridDependencySynchronize()`, but read `shared_output` only after it. The early `shared_output` load is the one ordering change #47784 makes.
- In `DeepseekV2MoE`, `shared_output` is produced by the shared expert on `alt_stream`, and the main stream joins it with `wait_stream` right before the finalize launch. The `routing_ready` docstring requires the inputs to be complete when the kernel launches. We suspect that under CUDA graph capture with PDL, the dependency on the shared expert's last kernel is relaxed too, so finalize can read rows that are not written yet. The routing tensors come from an earlier kernel on the same stream, which is why reading them early was safe before.
- That fits the symptom: no crash, a few points of accuracy lost, and only on one GPU type, where the timing exposes the race.

## Relanding

- Keep the routing prefetch, and move the `shared_output` row load after `PDLWaitPrimary`, as the old kernel did. Or pass `routing_ready=False` whenever `shared_output` is given, at some cost in latency.
- Add a test that produces `shared_output` on a side stream inside a CUDA graph with PDL on. The current unit test builds every input before the launch, so the early read is always safe there.
- Run `test_dsa_glm52_hisparse.py` on 8-gpu-b200 before merging; it is nightly-only, so PR CI does not cover it.
