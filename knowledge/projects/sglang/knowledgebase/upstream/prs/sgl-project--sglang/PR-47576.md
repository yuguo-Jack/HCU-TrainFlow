# [Perf] cp: Upload zigzag CP metadata with one pinned non-blocking copy

[Upstream PR](https://github.com/sgl-project/sglang/pull/47576) · state: open · merged: False

## Original PR description

## Motivation

`ZigzagCPStrategy.build_metadata` runs on the scheduler/host side for every prefill-CP batch and creates twelve small int32 device tensors with `torch.tensor(..., device="cuda")`. Each of these is a pageable host-to-device copy, and a pageable H2D copy blocks the host until the work already queued on the current stream has finished. When a previous forward is still in flight (e.g. with PP, or overlap scheduling), the host stalls on every CP prefill batch until the GPU drains.

## Modifications

- `layers/cp/zigzag.py`: add `_lists_to_device`, which packs all metadata lists into one pinned host buffer (each segment 16-byte aligned), uploads it once with `non_blocking=True`, and returns per-list int32 views. `build_metadata` now uses it instead of twelve separate `torch.tensor(..., device=...)` calls. The pinned host block is not reused before the copy completes: PyTorch's caching host allocator records an event on the copy stream for non-blocking copies.
- `layers/cp/utils.py`: docstring note on `prepare_cp_forward` that the metadata tensors are uploaded asynchronously.
- `test/registered/cp/test_cp_strategy_unit.py`: `_assert_metadata_matches` now also checks values, int32 dtype and 16-byte alignment of every device tensor.

No change to the metadata values or to any attention kernel.

## Accuracy Tests

Qwen3-30B-A3B-Instruct-2507-FP8, 4x B300, `--tp-size 2 --pp-size 2 --attn-cp-size 2 --ep-size 2 --enable-prefill-cp --cp-strategy zigzag --cuda-graph-backend-prefill=disabled`, GSM8K 5-shot greedy, full test set (1319):

| | GSM8K |
|---|---|
| main | 0.9543 |
| this PR | 0.9536 |

(one-question difference, within noise; 200-example run: 0.955 vs 0.950)

Unit tests: `python -m unittest test.registered.cp.test_cp_strategy_unit` passes (25 tests) on B300.

## Speed Tests and Profiling

Host time of `ZigzagCPStrategy.build_metadata` (cp_size=8, 4 sequences, 44K extend tokens) on B300, measured with and without a long matmul chain queued on the stream:

| | main p50 | this PR p50 |
|---|---|---|
| GPU idle | 0.28 ms | 0.149 ms |
| GPU busy (forward in flight) | 31.2 ms | 0.185 ms |

With the GPU busy, main blocks the host until the queued work drains; this PR returns immediately.
