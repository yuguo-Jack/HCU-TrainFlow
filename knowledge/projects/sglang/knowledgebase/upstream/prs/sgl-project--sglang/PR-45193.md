# [Perf] [AMD] dsv41: write prefill wo_a token-major and hand wo_b its MXFP8 on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45193) · state: open · merged: False

## Original PR description

## Motivation

On gfx950, DeepSeek-V4.1 prefill / extend rows run wo_a (`o [T, G, 4096] @ wo_a [G, 1024, 4096]`; G = 4 at TP2, 2 at TP4, 8 at DP-attn) as `torch.einsum`. Only TP4 with 4096-65536 rows uses a strided `torch.bmm`. The einsum hands back its group-major result as a `[T, G, R]` view, so wo_b's `flatten(1)` copies it. wo_b (gfx950 MXFP8 route) then quantizes the bf16 copy in a separate `mxfp8_e4m3_quantize` pass, whose 64x32 tiles drop to about 2.2 TB/s once the input no longer fits in the cache. Decode / verify rows at TP2 / DP-attn already get wo_b's `Mxfp8Activation` from the wo_a GEMM epilogue (#42055).

At TP2, a 16K-row layer spends 608 us in wo_a: einsum 450 us, flatten copy about 105 us, quant about 46 us. Layers 0-20 of every 16K chunk see all rows. Layers 21-39 see 128 rows per request under decoder SWA bounded replay.

Moving the epilogue route (the Triton fork `gfx95_batched_gemm_bf16_fp8_grid`, `emit_fp8`) to prefill sizes does not pay off. I swept tile sizes, warps, `waves_per_eu`, stages, and an XCD remap with grouped tile order under the production Triton env (`TRITON_HIP_USE_ASYNC_COPY=0`). The best tile reaches about 825 TFLOP/s against hipBLASLt's about 1250. Even with the quant fused, it is 7-11% slower than today at TP2 for 4K+ rows and 18-32% slower at TP4. So this PR keeps hipBLASLt and drops the copy and the slow quant instead.

## Modifications

- `_apply_wo_a_bf16_matmul`: on V4.1 gfx950, prefill / extend rows of every local group count and row count go to `wo_a_prefill_matmul` (`deepseek_v4_gfx95_dense`):
  - `torch.bmm` writes the token-major `[T, G, R]` directly, the strided destination TP4 already uses for 4096-65536 rows. wo_b's `flatten(1)` becomes a view, and the result is bitwise the einsum's.
  - When wo_b consumes MXFP8 (`wo_b_emits_mxfp8` / `SGLANG_HIP_WO_A_MXFP8`, the decode gate), one `fp8_grid_quantize` pass (32x512 tiles) returns wo_b's `Mxfp8Activation` instead of wo_b quantizing the bf16 tensor itself. Its fp8 codes and ue8m0 scales equal wo_b's own quant for every 32-group with amax >= 1e-10; this was checked over all bf16 amax values. An all-zero group keeps its zero codes under a different exponent (85 vs 19), as in the decode epilogue.
  - Batch-invariant and deterministic inference keep the einsum.
- Decode / target-verify branches are unchanged.
- `test_deepseek_v4_amd_wo_a_bf16.py`: G = 2 / 4 / 8 at 1-16384 rows (bitwise vs the einsum; MXFP8 bytes vs `mxfp8_e4m3_quantize`, including an all-zero row), CUDA-graph replay, batch-invariant fallback, DSv4 keeps the einsum.

## Accuracy Tests

- The unit tests above pass on MI355X. Per layer, wo_b's output (aiter MXFP8 GEMM) is bitwise equal to today's at G = 2 / 4 / 8 and 128-16384 rows.
- GSM8K (1319 questions, DeepSeek-V4.1-Flash TP2, DSpark): base 0.893 / 0.891, this PR 0.903 / 0.902 (two runs per arm; the server is run-to-run nondeterministic).

## Speed Tests and Profiling

MI355X x1, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261018`, CUDA-graph replay (median), `TRITON_HIP_USE_ASYNC_COPY=0 TORCH_BLAS_PREFER_HIPBLASLT=1`. wo_a plus its quant for wo_b, us (before → after):

| rows | TP2 (G = 4) | TP4 (G = 2) | DP-attn (G = 8) |
|---:|---:|---:|---:|
| 128 | 22.8 → 17.9 | 17.1 → 12.7 | 33.9 → 27.9 |
| 1024 | 76.5 → 66.4 | 41.3 → 35.0 | 88.0 → 71.8 |
| 2048 | 84.8 → 68.3 | 77.0 → 66.2 | 155.7 → 125.6 |
| 4096 | 147.7 → 123.4 | 72.0 → 71.4 | 315.7 → 260.7 |
| 16384 | 607.8 → 488.0 | 270.3 → 257.8 | 1272.5 → 1008.6 |

Including wo_b's GEMM, a TP2 16K-row layer goes from 1048 to 933 us. Per 16K chunk of one request (layers 0-20 at 16384 rows, 21-39 at 128 rows), that is TP2 −2.6 ms, TP4 −0.3 ms, DP-attn −5.7 ms per rank.

End to end, DeepSeek-V4.1-Flash, MI355X x2 (TP2, the same two GPUs one after the other, interleaved base, PR, base, PR), DSpark, production recipe env with `SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL=true`, `--chunked-prefill-size 16384 --mem-fraction-static 0.80 --max-running-requests 64 --cuda-graph-max-bs-decode 64 --prefill-decode-interval 32 --swa-prefix-tails 2048`:

| | base (run 1 / 2) | this PR (run 1 / 2) |
|---|---:|---:|
| prefill TTFT, 16384 in / 1 out, c1, 24 prompts, median | 358.8 / 361.7 ms | 355.8 / 360.8 ms |
| prefill TTFT, p90 | 366.0 / 371.5 ms | 366.8 / 368.1 ms |
| decode 1024 / 1024 c4, median ITL | 2.07 / 2.06 ms | 2.06 / 2.08 ms |
| decode 1024 / 1024 c32, median ITL | 5.09 / 5.06 ms | 5.05 / 5.09 ms |

Averaged over the two runs, the median TTFT is 2.0 ms (0.55%) lower, in line with the −2.6 ms per-chunk estimate from the kernel timings but within the 3-5 ms run-to-run spread. Decode is untouched (median ITL unchanged). The first base run, the first server on a freshly allocated node, has decode TPOT and TTFT stalls the other runs did not have (c4 p90 TPOT 5.56 vs 3.77 ms), so TPOT and throughput are not compared.
