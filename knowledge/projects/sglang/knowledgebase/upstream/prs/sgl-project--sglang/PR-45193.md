# [Perf] [AMD] dsv41: write prefill wo_a token-major and hand wo_b its MXFP8 on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45193) · state: open · merged: False

## Original PR description

## Motivation

On gfx950, DeepSeek-V4.1 prefill / extend rows run wo_a as `torch.einsum`. Its group-major result costs wo_b a flatten copy, and wo_b then quantizes it to MXFP8 in a separate pass that slows down once the input leaves the cache. A Triton GEMM with the quant in its epilogue is slower than hipBLASLt at these sizes (about 825 vs 1250 TFLOP/s), so the GEMM stays on hipBLASLt and this PR removes the copy and the slow quant.

## Modifications

- New `wo_a_prefill_matmul` (`deepseek_v4_gfx95_dense.py`): the hipBLASLt bmm writes straight into wo_b's token-major [T, G, R] layout (a strided `out=`, so no flatten copy), then one `fp8_grid_quantize` pass produces wo_b's `Mxfp8Activation` (fp8 codes + ue8m0 scales). With a bf16 wo_b it returns the token-major bf16.
- `_apply_wo_a_bf16_matmul` uses it for V4.1 prefill / extend rows at every group count (TP2, TP4, DP-attn). Decode / verify are unchanged; deterministic and batch-invariant modes keep today's path.
- It runs only when `torch.version.hip` >= 7.15 (ROCm 10). The hipBLASLt bundled with torch's ROCm 7.2 wheel miscomputes this strided-output bmm at many shapes (for example 2 groups × 1024 rows, 4 × 640, 8 × 129), so on ROCm 7.2 `wo_a_prefill_matmul` declines and today's einsum path runs unchanged.

## Accuracy Tests

Operator check on MI355X, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025` (torch 2.11.0+rocm10.0.0, HIP 7.15), G = 2 / 4 / 8, dense and 64-head-padded `o`:

| check | result |
|---|---|
| token-major bmm vs today's einsum (bf16) | bitwise at every row count 1-1100, every 13th to 8192, and 7 counts up to 65536 (8265 shapes) |
| fp8 codes and ue8m0 scales vs wo_b's own quant of today's bf16 output | bitwise for every 32-group with amax >= 1e-10 (all bf16 amax values checked); all-zero groups get a different scale byte, codes stay 0 |
| wo_b output vs today, aiter MXFP8 GEMM (all rows) and FlyDSL MXFP8 GEMM (>= 2048 rows) | bitwise at 1-32768 rows (75 points, two GPUs with different seeds), also against an unpatched container |

On `lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261025` (HIP 7.2) the function declines at every shape, and wo_a's and wo_b's outputs are bitwise equal to main's.

GSM8K (`sglang.test.few_shot_gsm8k`, 1319 questions, parallel 64), DeepSeek-V4.1-Flash TP2 + DSpark, MI355X x2, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261018`, this design before the version gate was added:

| | run 1 | run 2 |
|---|---:|---:|
| base | 0.893 | 0.891 |
| this PR | 0.903 | 0.902 |

The GSM8K spread is the server's run-to-run nondeterminism.

## Speed Tests and Profiling

MI355X x1, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025`, CUDA-graph replay (median, mean of two GPUs), `TRITON_HIP_USE_ASYNC_COPY=0 TORCH_BLAS_PREFER_HIPBLASLT=1 SGLANG_OPT_HIP_FLYDSL_MXFP8=1`. wo_a plus its quant for wo_b, us (before → after):
