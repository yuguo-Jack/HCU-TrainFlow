## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Currently, only CUDA GPUs have a device-level mm feature transport (cuda_ipc/cuda_vmm); NPU falls back to CPU transport with extra host↔device copies. This PR adds npu_ipc, an NPU equivalent of cuda_ipc that shares multimodal features zero-copy through a bounded NPU IPC memory pool.

## Modifications

- Added `npu_ipc` as a new `--mm-feature-transport` option, providing CUDA IPC-equivalent zero-copy multimodal feature transport on Ascend NPUs, with the same bounded memory pool and CPU fallback behavior.
- Added validation for npu_ipc: requires the NPU platform and a single node.
- Generalized the transport core to be device-agnostic: stream-ordered value operations now dispatch to CANN's `acl.rt.value_write`/`value_wait` on NPU (64-bit, 8-byte-aligned control words) and to CUDA driver ops on GPU; IPC handles use `_share_npu_`/`_new_shared_npu` on NPU.
- Reused the existing IPC pool path in `BaseMultimodalProcessor` for `npu_ipc`.
- Reserved `SGLANG_MM_FEATURE_CACHE_MB` from the KV cache budget for `npu_ipc` pools.
- Replaced hard-coded `torch.cuda` calls and `device.type == "cuda"` checks with device-agnostic equivalents in the feature-consuming paths (`mm_utils`, `schedule_batch`, `kimi_k25`, `kimi_k3`, `qwen3_vl`).
- Added unit tests for server-args parsing, transport config selection, and real-device NPU IPC transport across processes and devices.

|---|---|---|---|---|

| | E2E latency | 17059 ms | 15301 ms | -10.3% |
| | TPOT | 12.55 ms | 12.33 ms | ~0 |

| | E2E latency (mean) | 37195 ms | 34420 ms | -7.5% |
| | TPOT (mean) | 27.22 ms | 26.82 ms | ~0 |

TTFT drops 25-37% because multimodal features no longer round-trip through
CPU memory between processes; the gain scales with the number of images.
TPOT is unchanged, confirming the transport only affects prefill. End-to-end
improvement is diluted by the long decode phase (1024 output tokens).
