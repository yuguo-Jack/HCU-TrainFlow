# [CI] [AMD] pr-test: Move test_quark_mxfp4 from the MI35x 1-GPU PR stage to nightly

[Upstream PR](https://github.com/sgl-project/sglang/pull/47150) · state: closed · merged: True

## Original PR description

## What

Moves `test_quark_mxfp4` (~9 min) from `stage-b-test-1-gpu-small-amd-mi35x` to the `nightly-amd-1-gpu-mi35x` suite, which the nightly `nightly-test-1-gpu-mi35x` job already runs.

## Why

`linux-mi35x-gpu-1` is the scarcest AMD runner pool. On Oct 26–28, jobs waited a median ~10 h for it, and PR runs asked it for about 1.7× the runner time it has. #47244 already merged that stage into one job per PR run. This takes another ~9 min off the job, about a fifth of its ~45 min of tests.

## Notes for the reviewer

- This PR originally also merged the stage's two shards into one job. #47244 did the same on main, so the merge from main takes main's version of the workflow, and only the test move remains.
- `test_flydsl_v4nm_decode` stays in PR CI. Moving it edits a file under `test/registered/kernels/`, which makes NVIDIA PR CI run its JIT kernel suite. That suite currently fails on main (`test_gdn_prefill_graph.py`). It can move in a follow-up.
- `test_quark_mxfp4` is gfx950-only, with no CUDA counterpart. The nightly MI35x 1-GPU job's test step currently finishes in under a minute, with a 90 min timeout and 15 min per file, so the test fits.

#### 1. 🟠 Should fix: test_quark_mxfp4 may be killed as timeout in nightly: 900s per-file budget below runtime
`test/registered/e2e/quantization/test_quark_mxfp4.py:8`

Moving to nightly cuts this file's per-file timeout from the flat 1200s default to the nightly job's `--timeout-per-file 900`. The 1200s default applied because `stage-b-test-1-gpu-small-amd-mi35x` passed no `--timeout-per-file`; there was no derived 2250s budget. On one GPU the file still launches five servers with 500-question GSM8K runs and declares `est_time=450`, so 900s leaves about 2x headroom. A slow run (cold HF cache) would be killed and reported as a timeout. The nightly job does not pass `--enable-retry` and the suite holds only this file and a 10s test, so the 90-minute step cap is not at risk. If headroom matters, use `--timeout-override test_quark_mxfp4.py=1200`.

**Who is affected:** Nightly MI35x 1-GPU runs (`nightly-test-1-gpu-mi35x`) where this file runs unusually slowly.

#### 2. 🟠 Should fix: quark_mxfp4 e2e regression can merge and surface only in nightly: this PR moves the only per-PR e2e coverage
`test/registered/e2e/quantization/test_quark_mxfp4.py:8`

Moving `test_quark_mxfp4.py` to `nightly-amd-1-gpu-mi35x` removes the only per-PR end-to-end coverage of `--quantization quark_mxfp4`. That coverage was online BF16/FP8/NVFP4->MXFP4 requant for dense and MoE models, with peak-memory and GSM8K checks. Per-PR, only the unit tests and the GDN-only `test_qwen35_gdn_online_mxfp4.py` remain. A regression in `quark_w4a4_mxfp4*.py` or the requant loaders would surface in the next nightly run, not on the PR that causes it. This is the deliberate trade-off the PR title states; consider keeping one cheap class (e.g. `TestFP8ToMXFP4DenseTP1`) per-PR if fast feedback matters.

**Who is affected:** Contributors changing the quark MXFP4 quantization paths, whose AMD MI35x PR CI no longer runs the e2e quark_mxfp4 tests.
