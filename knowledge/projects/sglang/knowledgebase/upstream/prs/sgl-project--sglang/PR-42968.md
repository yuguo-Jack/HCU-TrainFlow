# [Perf] DeepSeek-V4.1: Support indexer TP shard

[Upstream PR](https://github.com/sgl-project/sglang/pull/42968) · state: closed · merged: True

## Original PR description

## Motivation

On DeepSeek-V4.1-Flash the ratio-1/2 sparse indexer is fully replicated across the attention-TP group: `wq_b` and `weights_proj` are `ReplicatedLinear`, `n_local_heads == n_heads`, and every attention-TP rank holds the same query rows of a prefill chunk. So under TP4 each of the four ranks runs the identical dense `fp8_fp4_mqa_logits` scan over every row against the whole compressed context, then the identical top-k on it, and arrives at the identical selection. Three quarters of that work is redundant.

That redundant work is the largest O(context²) term of a long prefill. In a 1 M-token prefill on 4× B200 (TP4 + EP4, DSPARK, the cookbook low-latency recipe) the dense index logits are **6.8 s of kernel time per rank** across 2 746 launches, and the ragged top-k that reads the same score tiles is another **1.9 s**. Both grow with context per chunk, so the share keeps rising with length.

## Modifications

Behind `SGLANG_OPT_DSV4_INDEXER_TP_SHARD` (default **off**), each attention-TP rank scores a contiguous share of the chunk's rows and the selections are all-gathered, so every rank still ends up with the full selection.

<img width="2460" height="1058" alt="shot-muy3qvkh" src="https://github.com/user-attachments/assets/85a2ae63-e596-4600-8603-902385ebd9df" />

- **`RowShard`** (`v41_indexer/types.py`) partitions the rows into rank-ordered shares of `ceil(rows / world)` rounded up to the score kernel's `128 // heads` row grouping, so every MMA tile holds exactly the rows it holds unsharded. `gather` is one `all_gather_into_tensor` over the attention-TP group; the last share's padding rows fall past the row count and are dropped.
- **Full top-k path** (`scoring.py`, `full_topk.py`): `score_tiles` and `dense_prefill_topk` take an optional row range (default: all rows, so the replicated path is unchanged), and `sharded_dense_prefill_topk` scores this rank's share and all-gathers the `[rows, topk]` selection.
- **Candidate publish path** (`sparse_table.py`): the row-parallel half of `publish_prefill_table` is split out as `select_prefill_rows`. With a shard, each rank computes its share's own top-k and its top candidate blocks, all-gathers both, and then builds the sparse table over every row: DeepGEMM's schedule is built per row set and cannot be sliced, and the build is cheap next to the scan.

<img width="2512" height="820" alt="shot-muy3rfqx" src="https://github.com/user-attachments/assets/2c5d489b-1871-4260-bf55-90ff2ead3246" />

- **Gate** (`deepseek_v4_backend.py`): the shard is attached to `PrefillInputs` only on the eager extend path, when attention TP > 1 and the chunk has at least 512 rows. Prefill context parallelism keeps the replicated path, since each CP rank already holds its own interleaved subset of rows. Decode and the captured prefill graph are untouched.

**Why this is exact.** A dense score depends only on its own query row, and the aligned shares keep every MMA tile's row set the same, so each rank computes the same bits for its rows as the replicated path would, and the gathered selection is bitwise the replicated one. Every input of the gate is identical on all attention-TP ranks, so either all of them reach the all-gather or none does. The indexer runs on the `stream_sources` side stream, and the all-gather is the only collective issued during that window of `forward_prepare`; the main stream joins it before attention.

## Accuracy

GSM8K, 200 examples, `--temperature 0`, both servers built from the same tree in the same session:

| | score | score:std |
|---|---|---|
| flag off | 0.990 | 0.0995 |
| flag on | 0.995 | 0.0705 |

The one-question difference is run-to-run nondeterminism, not the change: the selection is bitwise the replicated one (see Tests), and two replicated runs of this model already differ, because the consumer layers' bf16 top-k breaks ties at the selection floor by race.

## Benchmarks

4× B200, TP4 + EP4, DSPARK block 5, `--cuda-graph-max-bs-decode 64`, `--context-length 1050624`, bs = 1, random-token prompts, 16 K prefill chunks. Same tree on both servers; only the flag differs. One warm-up, then three seeds per point:

| context | flag off TTFT | flag on TTFT | Δ |
|---|---|---|---|
| 1 M (1 048 000) | 27.73–27.80 s | 20.93–21.00 s | **−6.8 s (−24.5 %)** |
| 256 K (262 144) | 4.91–4.92 s | 4.50 s | −0.42 s (−8.5 %) |

TP-0 kernel time over the 1 M prefill. The baseline trace was taken on a tree that differs from this one only in the compressed-cache dequant path, so only the indexer kernels below are compared; the consumer-side kernels (`sm100_paged_sparse_mqa_logits`, `topk_bf16_small`) are unchanged to the launch, as expected:

| kernel | flag off | flag on |
|---|---|---|
| dense `sm100_mqa_logits` | 2 746 launches, 6.80 s | 775 launches, 1.73 s |
| `topk_ragged` | 3 827 launches, 1.90 s | 1 067 launches, 0.47 s |
| `amax8_varlen` (block keys) | 1 087 launches, 0.36 s | 298 launches, 0.09 s |
| `AllGather` (new) | — | 320 launches, 0.10 s |

Net, the indexer loses 6.66 s of kernel time per rank, which matches the −6.8 s of TTFT: at 1 M the side-stream indexer is on the critical path, so the saving passes straight through. Decode is unaffected.

**Stacked with per-ratio candidate publishing.** Same session, one tree that also carries the compressed-cache dequant dedup and per-ratio candidate publishing (#TBD) with both their flags on; only this flag differs:

| context | without this PR | with this PR | Δ |
|---|---|---|---|
| 1 M (1 048 000) | 23.78–23.83 s | 19.19–19.21 s | **−4.6 s (−19.3 %)** |
| 256 K (262 144) | 4.70–4.71 s | 4.42–4.43 s | −0.28 s (−6.0 %) |

The saving on top of per-ratio publishing is smaller than on main (−4.6 s instead of −6.8 s), because that change already removes two of the dense scans and leaves less to split. Together the three changes take a 1 M prefill from 27.73–27.80 s on main to 19.19–19.21 s (−8.6 s, −31 %). GSM8K on the stacked tree: 0.995 with this flag, 0.990 without.

## Tests

Two cases are added to `test/registered/kernels/ops/attention/test_dsv41_prefill_sparse_indexer.py` (`base-b-kernel-unit`, 4-gpu-b200), which already holds the publish/consume tests these paths share. Both run the sharded code as every rank of an attention-TP group inside one process, through a two-pass all-gather: pass one runs the production code as each rank and records the share it contributes, pass two returns every rank's recorded share in rank order, which is what the NCCL all-gather returns. The unsharded path is the oracle.

- `test_row_shards_publish_the_replicated_table`: the own top-k, `blocks`, `phys_blocks` and `valid_lens` match the replicated publish bit for bit on every rank; the schedule is compared by the sparse scores it drives on every valid position. Its buffer holds bytes the build never writes, so two replicated builds of one input already differ in about a third of its bytes and a byte comparison would be meaningless.
- `test_row_shards_select_the_replicated_full_topk`: the sharded full top-k equals the replicated one on every rank.

Cases cover a padded last share, an even split, an empty share, and shares that cut a request in two. A precondition that the shares tile the rows fails cleanly before any kernel runs; without it, a broken partition hands uninitialized block ids to the schedule build, which crashes and poisons the CUDA context for every later test in the file. Shifting each share by one row turns all seven new subtests red on that precondition and leaves the six existing tests green. On B200 the file runs 8 tests in 1.6 s warm.

## Reproduction

```bash
# server (the A/B above: flag on vs off, everything else equal)
SGLANG_OPT_DSV4_INDEXER_TP_SHARD=1 SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 \
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code \
  --tp 4 --ep-size 4 --mem-fraction-static 0.8 --speculative-algorithm DSPARK \
  --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64 \
  --context-length 1050624 --port 31000

# sharded vs replicated selection
python3 test/registered/kernels/ops/attention/test_dsv41_prefill_sparse_indexer.py

# accuracy
python3 -m sglang.test.run_eval --eval-name gsm8k --num-examples 200 --num-threads 32 --temperature 0 --port 31000
```
