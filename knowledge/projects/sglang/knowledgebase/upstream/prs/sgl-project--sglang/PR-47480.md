# [Fix] sglang-miles: Clear the multimodal embedding cache on flush_cache and weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/47480) · state: open · merged: False

## Original PR description

## Motivation

The multimodal embedding cache (`mm_schedule.embedding_cache`, `SGLANG_VLM_CACHE_SIZE_MB`) is keyed by the image's pixel hash only, and nothing ever clears it. After a weight update, an image seen again is served the embedding the old vision weights produced. In RL (the vision tower trains, and agent turns resend the previous screenshot) this silently makes rollouts off-policy. `/flush_cache` does not clear it either.

## Modifications

- `mm_schedule.clear_mm_embedding_cache()`.
- `Scheduler.flush_cache` clears it with the other pools, so `/flush_cache` and the flush inside `release_memory_occupation` drop it (and `empty_cache` returns its GPU memory before a trainer runs).
- `SchedulerWeightUpdaterManager` clears it whenever served weights may have changed, regardless of the request's `flush_cache` flag: after `update_weights_from_disk` / `update_weights_from_ipc` (failed loads included), and at every `end_weight_update`, which covers `update_weights_from_tensor`, `update_weights_from_distributed`, P2P/RDMA writes and streamed LoRA. RL trainers update with `flush_cache=False` and, in `in_place` pause mode, never call `/flush_cache`.

A related attempt, #18942, covered only the flush and was closed.

## Tests

- Unit (`test/registered/unit/managers/`): new cases in `test_scheduler_weight_version_tracking.py` (disk, disk with a failed load, IPC; tensor, distributed and P2P sessions, all with `flush_cache=False`) and `test_release_memory_flush_order.py` (`/flush_cache` and a KV release). 39 pass with the change; on the base commit all 7 new cases fail. The release-order file's harness passed `tp_cpu_group`, which is no longer a constructor field, so its existing case errored before this PR; the second commit builds it the way the other tests do. The third sorts the new imports.
- Live engines, Qwen3-VL-4B on B300, `--disable-radix-cache`, `SGLANG_VLM_CACHE_SIZE_MB=4096` vs `0`: 24 greedy requests with two 1080p screenshots each, before and after `update_weights_from_disk` / `begin -> update_weights_from_tensor -> end` (both `flush_cache=False`) to a checkpoint with the vision mergers scaled by 0.9. On the base commit the cache-on engine replays its pre-update outputs exactly (10/24 texts differ from the cache-off engine). With the change the cache-on engine is bit-identical to the cache-off engine before and after, max |dlogprob| 0.0.
- GPU memory while released, cache on, 8 requests cached: scheduler 2,450 MiB with the change vs 2,978 MiB before.
- Throughput with the cache on (now safe for RL), CUA-style closed loop, 64 clients per engine: 9.17 -> 13.15 req/s, p50 4.50 -> 2.52 s.

Scripts and raw outputs: https://github.com/softlash/LIN-2438/tree/main/docs/evidence
