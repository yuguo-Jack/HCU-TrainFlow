# [Fix] [SM120] dsv4: Keep the V4.1 indexer usable on SM12x

[Upstream PR](https://github.com/sgl-project/sglang/pull/47209) · state: open · merged: False

## Original PR description

Prerequisite for #47210 (SM120/SM121 dense FP8 native block32 DeepGEMM): without this change DeepSeek-V4.1 does not reach readiness on SM12x with either GEMM backend. The two PRs have zero file overlap and no code dependency in either direction.

## Motivation

On SM120/SM121 the DeepSeek-V4.1 candidate indexer cannot start. The selection
gate (`is_sm100_or_newer()`) compares the capability major against `>= 10`, so
SM12x enters the candidate path, while the DeepGEMM capability flag is gated on
`is_sm100`. In the pinned `sgl-deep-gemm` build the paged **sparse** MQA logits
entry points assert `get_arch_major() == 10`: the dense variant ships SM120
kernels, the sparse variant does not. `DEEPGEMM_PAGED_SPARSE_MQA_LOGITS` is
therefore false and `make_candidate_indexer` raises before the server reaches
readiness. Because the dense paged logits kernel is present on SM12x, the
already implemented dense blocks backend works there.

A SM120 sparse-table kernel exists on DeepGEMM's `nv_dev` branch (`#447`) but not
in the pinned `sgl-deep-gemm` release builds, so it cannot be enabled from SGLang
today. This change therefore fixes the failure at the capability check rather
than unifying the two gates: narrowing `is_sm100_or_newer()` to match `is_sm100`
would also fold SM100/SM103 into the dense path, where a missing sparse kernel
means a broken install and should keep raising.

Separately, `make_full_topk_indexer` derives `use_deep_gemm_decode` from
`is_sm100_or_newer()` alone. With `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH=1` the torch
path produces no DeepGEMM schedule, and the native decode then receives `None`.

## Modifications

Two production changes, 9 added and 2 deleted lines in
`python/sglang/srt/layers/attention/dsv4/v41_indexer/__init__.py`:

- When `DEEPGEMM_PAGED_SPARSE_MQA_LOGITS` is false and `get_device_sm()` is 120 or
  121, reuse the already constructed `DenseBlocksBackend` for both the prefill and
  decode slots instead of raising. SM100/SM103 keep failing loudly, because there
  the missing sparse kernel indicates a broken DeepGEMM install rather than an
  architecture gap.
- Gate `use_deep_gemm_decode` on `is_sm100_or_newer() and not
  envs.SGLANG_FP8_PAGED_MQA_LOGITS_TORCH.get()`, so the torch schedule flag is
  honored and the native decode is never handed a `None` schedule.

No new environment variable, no backend policy change, no kernel change, and no
behavior change on SM90/SM100/SM103 or ROCm.

## Accuracy Tests

`test/registered/unit/layers/test_dsv4_nonpaged_indexer.py` gains a
`TestDSV41IndexerSelection` class (CPU-registered, `est_time=11`,
`suite="base-a-test-cpu"`) that drives `make_candidate_indexer` and
`make_full_topk_indexer` through a mocked architecture/DeepGEMM fixture, 5 test
methods over 26 subtests:

- SM120/SM121 with the sparse kernel absent, at `attn_cp_size` 1 and 2, return the
  same `DenseBlocksBackend` for both slots, keep `use_deep_gemm_prefill`, and
  preserve `topk_blocks`/`block_size`.
- SM100/SM103 with the sparse kernel absent still raise on "paged sparse MQA
  logits".
- SM100/SM103 with the sparse kernel present still select `SparseTableBackend` for
  decode and keep the existing prefill choice across `attn_cp_size` and dense
  kernel availability.
- SM90, and `candidate_topk_blocks=0` on SM100, still take dense blocks without
  requiring a sparse kernel.
- `use_deep_gemm_decode` follows both the architecture check and
  `SGLANG_FP8_PAGED_MQA_LOGITS_TORCH` across SM90/100/103/120/121, and the metadata
  object reports no DeepGEMM schedule when the torch flag is set.

The complete file runs 34 test methods plus 55 subtests, all passing with no
skips, in 7.90 s in a CPU-only process. A negative control that keeps these tests
and restores only this production file to its pre-change revision fails exactly
the 8 targeted subtests — the 4 SM12x fallback cases and the 4 `torch_schedule=True`
cases on SM100/103/120/121 — on the intended assertions rather than on import or
environment errors.

## Benchmarking and Profiling

No performance claim. This change only decides which already existing backend is
constructed; it adds no kernel and does not alter the dense blocks path.

It was, however, load-bearing for measurement: a full-model DeepSeek-V4.1-Flash
run on 8x RTX PRO 5000 (TP8/EP8) does not reach readiness without it, so this
change was applied identically to both arms of a separate dense FP8 experiment on
that host.
