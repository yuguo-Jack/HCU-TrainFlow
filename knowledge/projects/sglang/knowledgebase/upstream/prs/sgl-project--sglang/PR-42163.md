# [PD] Shard Mooncake transfers by bootstrap room

[Upstream PR](https://github.com/sgl-project/sglang/pull/42163) · state: open · merged: False

## Original PR description

## Motivation

**Reproduction** (main `b37e6f79fce`): Qwen3.8-Flash-Next eager PD with Mooncake/MNNVL, prefill `--tp-size 1 --pp-size 4 --disable-overlap-schedule`, decode `--tp-size 4 --ep-size 4 --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`, random ISL/OSL `8192/2`, concurrency 32, and the default four transfer queues. There is no process exception; the raw failure signature is that independent rooms select the same worker while decode accumulates transfer requests:

```
[2026-09-30 23:48:14 PP0] D5_XFER_REQ_BEGIN room=7358507676496413592 worker=3 session=10.49.64.248:15525 last_chunk=True
[2026-09-30 23:48:14 PP1] D5_XFER_REQ_BEGIN room=7358507676496413592 worker=3 session=10.49.64.248:15525 last_chunk=True
[2026-09-30 23:50:29 TP0 EP0] Decode batch, #running-req: 1, ... #transfer-req: 31, ... gen throughput (token/s): 1.68
```

**Call path:** `MooncakeKVManager.add_transfer_request` hashes the fixed destination-session port sum → every room enters one `transfer_queue` → one `transfer_worker` drains rooms serially → each destination calls `send_kvcache` → `_await_transfer_futures` waits for that room before the worker dequeues the next one. The problem is that the queue key contains no room identity, so a fixed single decode TP replica serializes independent large hybrid KV/state transfers behind one worker.

**Trigger condition:**

- Decode attention TP>1 with one decode instance → the target-session set is fixed → every room lands on only 1/Q queues (the topology reproduced here).
- Decode TP=1 with DEP → each request contributes one random port → expected coverage is `Q·(1−(1−1/Q)^n)=2.73/4` for `n=4,Q=4`, and all four queues are distinct with probability 9.4%, so the old key is mildly imbalanced.
- Multiple decode instances → the router may spread target-session sets across queues, but provides no distribution guarantee.

## Modifications

- Add `_mix_room_id`, a 64-bit SplitMix64 finalizer, in `python/sglang/srt/disaggregation/mooncake/conn.py`.
- Change `MooncakeKVManager.add_transfer_request` to select `mix(bootstrap_room) % queue_count`; this spreads independent rooms without aliasing DEP room residues, while every chunk of one room still maps to one FIFO.
- Extend `TestMooncakeTransferQueueSharding` with congruent-room distribution, same-room multi-chunk stability, and cross-queue failed-session early-exit coverage. The last case proves that fail-fast uses the manager-wide `failed_sessions` set under `session_lock`, not queue affinity.

**Why `SGLANG_DISAGGREGATION_QUEUE_SIZE=1` is not a mitigation:** a queue owns one `transfer_worker`. That worker processes one room's destination sessions in sequence and waits for the room's submitted transfer futures before dequeuing another room. Threads parallelize per-layer work inside the current room; they do not make rooms on one queue concurrent. J1 shows the distinction directly: Q1 concentrates all 9 executor threads and improves the broken Q4 baseline by 26.1%, but its busy-worker count remains one and the room-sharded fix is another 46.8% faster. Q1 also removes useful queue parallelism from topologies whose old key happened to spread rooms, so it is not a topology-independent replacement for room sharding.

Native samples put all active executor threads below `batch_transfer_sync`, with top frames in mutex wait, `cuStreamQuery`, and `cuMemcpyBatchAsync_v2`. Increasing capacity from Q4/thread8 to Q8/thread16 reduced throughput by 7.1%, so the residual shared-engine contention is outside this patch.

The speedup scope is transfer-bound workloads such as Qwen3.8, whose transfer is about 442 MiB per request. For compute-bound models such as Qwen3.5 DEP, an external Q=1 comparison found queue distribution changes throughput by only about 1%; that result is context, not a benchmark produced by this PR.

Independent GLM-5.2/ROCm evidence supporting the room hash here (our inventory S03/S11); we will track this PR instead of opening a duplicate.

With a DCP decode replica, every room had the same destination-session set, so destination-port hashing left one transfer worker active per prefill rank. Plain `room % 4` also failed: the room residue encoded the prefill DP rank. In our historical `dcpx6 -> dcpx7b` experiment, hashing the room changed sampled active workers from 1 to 2–4 per rank and measured KV-transfer p50 from 21.3 s to 11.3 s. `dcpx7` with plain modulo did not spread work. This agrees with the congruent-room case already covered by your tests.

There is also a caution: same-node `g4tune R1 (dest) -> R2 (mix)` reduced mean transfer time from 9.98 s to 2.16 s, but TPOT worsened from about 13.3 ms to 15 ms; we did not adopt that configuration. Both comparisons are single historical runs with simulated MTP acceptance. They are transfer diagnostics, not model-accuracy validation or a claim that stack throughput belongs to this patch. The later GLM stack's PP-overlap/custom-all-reduce correctness problems also prevent using its throughput as patch evidence.

Archived evidence: `glm52.v0521-g4tune-xfer.packup_20261020` and `glm52.dcpx-pack-fix-best.packup_20261023`. Our layer-group parallelism and instrumentation are separate experiments, not additional functionality requested for this PR.
