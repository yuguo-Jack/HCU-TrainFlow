# [Fix] cuda_graph: Reset global graph pool and allocator cache on graph cleanup and recapture

[Upstream PR](https://github.com/sgl-project/sglang/pull/44296) · state: open · merged: False

## Original PR description

closes #44284

### changes
- implement `reset()` on `BreakableCUDAGraph` to iterate underlying segments and reset them (including deduped `original_graph`) and clear `_break_fns`
- in `BreakableCudaGraphBackend.cleanup()` and `FullCudaGraphBackend.cleanup()`, reset segment graphs and call `set_global_graph_memory_pool(None)` so subsequent capture passes mint fresh pool handles instead of reviving drained pools
- invoke `device_module.empty_cache()` and `_host_emptyCache()` (when available) in `BreakableCUDAGraphCapture.__enter__` matching `torch.cuda.graph` hygiene
- add `_host_emptyCache()` to `drop_elastic_cuda_graph_state()`
- added cpu unit tests covering reset, recapture fresh pool minting, and capture cache hygiene

Author of #44284 here — thanks for the quick turnaround. The approach matches what we verified independently:

- Resetting the global handle (`set_global_graph_memory_pool(None)`) so the next session mints a fresh pool id is exactly the workaround we validated: with it in place, our destroy + re-capture flow completed 5 prefill capture rounds (boot + 4 post-destroy re-captures) with zero asserts and bit-identical round-trip outputs (same image, torch 2.11.0+cu130, H20).
- Adding the `empty_cache()` / `_host_emptyCache()` hygiene to `BreakableCUDAGraphCapture.__enter__` closes the asymmetry with `torch.cuda.graph()`'s `__enter__` — consistent with the minimal-repro matrix in the issue (cases e/f).
- The new `BreakableCUDAGraph.reset()` is a good catch on its own: previously the segment graphs had no explicit reset path, so teardown relied on GC finalization to release the pool references.

Serving-level validation complete — the fix holds under our full destroy + re-capture flow.

**Method.** The PR head tree requires sglang-kernel ≥ 0.4.9, whose wheels are built against a newer torch than the v0.5.17 release image ships (2.11.0+cu130), so we applied the PR's source diff onto the v0.5.17 release tree — the version #44284 was reported against. All three behavioral changes applied with a single mechanical adjustment (`set_global_graph_memory_pool` is imported from `runner_utils/pool.py` on v0.5.17); the `drop_elastic_cuda_graph_state` hunk was skipped (the function doesn't exist on v0.5.17); test files were not backported. Environment: `lmsysorg/sglang:v0.5.17-cu130-runtime`, torch 2.11.0+cu130, H20, driver 580.126.09, `--cuda-graph-backend-prefill breakable`.

**Flow under test** (our hot-swap extension): boot Qwen3-0.6B → prewarm Qwen3-1.7B → swap → swap back. Every swap tears down all CUDA graphs (`CUDAGraph.reset()`) and re-captures in the same process. The plugin's local pool-reset workaround was disabled so only the PR's changes are in effect.

| Tree | Local workaround | Result |
|---|---|---|
| v0.5.17 pristine | off | ❌ `use_count > 0` assert (`CachingHostAllocator.h:773`) on the first post-destroy re-capture — stack via `BreakableCUDAGraphCapture.__enter__` → `_begin_new_segment` → `capture_begin`; the process did not survive the follow-up request |
| v0.5.17 + this PR | off | ✅ four consecutive post-boot prefill re-capture sessions (breakable backend) across prewarm + A→B + B→A swaps, zero asserts, correct outputs after every swap |
| v0.5.17 + this PR | on | ✅ same flow, zero asserts |

**Vanilla regression (no extension loaded, patched tree):** boot → generate → `/update_weights_from_disk` with `recapture_cuda_graph=true` (decode re-capture completed in 1.86 s) → identical outputs before/after → clean SIGTERM shutdown. No asserts, no tracebacks.

Once this lands we can delete our local workaround entirely. Could a maintainer add the `run-ci` label so checks can run? Happy to re-run the same matrix on main once a nightly image carries a compatible torch/kernel combination.
