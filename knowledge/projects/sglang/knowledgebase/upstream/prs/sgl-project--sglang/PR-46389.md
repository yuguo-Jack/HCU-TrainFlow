# [Fix] function_call: stop dropping text before a partial tool-call marker

[Upstream PR](https://github.com/sgl-project/sglang/pull/46389) · state: open · merged: False

## Original PR description

## Motivation

`BaseFormatDetector.parse_streaming_increment` loses assistant text when a streaming increment ends in a partial `bot_token`.

The buffer is held back whenever it ends with a partial start marker, so that the marker is not streamed as content. But the text *in front* of that partial marker is held back with it, and the tool-call branch further down discards everything preceding `bot_token` once the call is confirmed. That leading text is never emitted. Up to `len(bot_token) - 1` characters of the answer disappear, and how many depends on where the increment boundary happens to fall, so the same generation streams differently at different `--stream-interval` values.

Reproduction, CPU only, no model needed, on `f1065423`:

```python
from sglang.srt.entrypoints.openai.protocol import Function, Tool
from sglang.srt.function_call.qwen25_detector import Qwen25Detector

tools = [Tool(type="function", function=Function(
    name="get_weather",
    parameters={"type": "object", "properties": {"city": {"type": "string"}}}))]

detector = Qwen25Detector()
print(repr(detector.parse_streaming_increment("Let me check. <tool_", tools).normal_text))
# main: ''
# expected: 'Let me check. '
```

The same output streamed at different intervals, where `<tool_call>` is one vocab token and the `\n` that completes `bot_token` arrives in the next delta:

```
                     main                            with this PR
--stream-interval 1  OK                              OK
--stream-interval 2  OK                              OK
--stream-interval 3  'Let me check the weather for'  'Let me check the weather for you.'
--stream-interval 4  OK                              OK
```

Detectors whose streaming path reaches this hold-back are affected: `Qwen25Detector` (the `qwen25` parser, used for Qwen2.5 and Qwen3), `TrinityDetector` and `Llama32Detector`. `HermesDetector`, `MistralDetector` and `IQuestQ1Detector` compute the hold-back themselves in their own override and are unaffected, and `JsonArrayParser` has a single-character `bot_token` so it has no partial to hold back.

## Modifications

`base_format_detector.py`: hold back only the trailing partial `bot_token` and emit the text in front of it, which is what the detectors that override the streaming path already do. `_ends_with_partial_token` returns `0` when there is no partial, so the no-marker case keeps its previous behavior of flushing the whole buffer.

`test/registered/unit/function_call/test_base_format_detector.py`: a new CPU unit test covering the two failure modes, an increment ending in a partial marker, and the streamed content not depending on where the increment boundaries fall. Both cases fail on `f1065423` and pass with the fix. The file mirrors the source path per `test/registered/unit/README.md`; `BaseFormatDetector` had no test file of its own.

### Deliberately out of scope

An increment that carries the leading text *and* a complete `bot_token` still drops that text. That happens on a different path: `has_tool_call` is already true, so the hold-back branch is skipped entirely and the tool-call branch discards `current_text[:tool_call_pos]`. Emitting it there means restructuring that branch's buffer bookkeeping across its several return points, which does not belong in this change. It is the `base_format_detector` item in #31915, and #42136 is the DeepSeek V3.1 instance of the same path.
