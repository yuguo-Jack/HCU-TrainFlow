# [Spec] Add context-aware routing to adaptive speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/31716) · state: open · merged: False

## Original PR description

## Motivation

Adaptive speculative decoding currently routes by batch size. Controlled H100 measurements show that logical sequence length is an additional useful routing signal, but not because deeper drafting universally wins at long context.

At fixed BS=8, two counterbalanced server-order passes (three measured batches per pass after warmup) produced:

| Logical context | Winning K | Margin over runner-up |
|---:|---:|---:|
| 256 | 7 | 15.48% |
| 1,024 | 7 | 20.43% |
| 4,096 | 7 | 2.14% |
| 8,192 | 1 | 1.97% |
| 16,384 | 1 | 4.56% |

All output hashes matched, and end-to-end wall throughput showed the same K=7 to K=1 transition. In this workload, draft acceptance stayed high through context 4,096, then fell to roughly 1.5--1.6 at 8,192 and roughly 1.004 at 16,384, making deeper drafting overhead at long context. This is evidence for exposing context as a policy input, not for a universal context-to-K default. Full setup and limitations are recorded in [the roadmap evidence update](https://github.com/sgl-project/sglang/issues/23705#issuecomment-6023973196).

## Relationship to current adaptive-spec work

PR #37274 / commit `83bd2c473f` added injected `AdaptiveSpecPolicy` support after this PR was first opened. This rebase treats that as the current ownership boundary:

- The existing batch-only `AdaptiveSpecPolicy` interface remains unchanged, so third-party/custom policies written for #37274 continue to work.
- This PR adds a separately detected, optional `ContextAwareAdaptiveSpecPolicy` capability.
- `AdaptiveSpeculativeParams` implements that capability using independent `(batch size, context bucket)` slots; it does not replace the controller or throughput-aware policy work.
- The default 1D configuration and its behavior remain unchanged.

The non-overlapping contribution here is therefore the context signal, optional 2D slot schema, runtime-state reachability union, and end-to-end wiring.

## Changes

### Optional 2D configuration

Each per-BS entry may contain `ctx_buckets`:

```json
{
  "8": {
    "ctx_buckets": {
      "1-2047": {"candidate_steps": [0, 1, 3]},
      "2048-32768": {"candidate_steps": [1, 3]}
    }
  }
}
```

- Ranges are 1-indexed, inclusive, and must start at 1 with no gaps.
- A context above the configured final upper bound uses the final bucket.
- Entries without `ctx_buckets` retain the legacy single-slot behavior.
- Candidate steps are unioned across every context bucket when runtime states are built and CUDA-graph batch sizes are pruned. Graph capture remains BS-only; no context dimension is added to the capture set.

### CPU-only routing signal

`get_batch_context_length()` takes the upper median of `Req.seqlen` across the batch. `Req.seqlen` is already CPU-resident Python state, so routing adds no device-to-host synchronization in the decode hot path.

The signal is threaded through:

- EAGLE and frozen-KV MTP activation before drafting;
- scheduler-side acceptance feedback after accepted lengths are available on CPU;
- `BaseSpecWorker`, EAGLE, and NGRAM hook signatures; and
- the plain `BaseTpWorker` mirror used by non-last pipeline-parallel stages.

## Compatibility properties

- Legacy JSON configs route exactly as before.
- Legacy custom policies receive only the original batch-only calls even when the controller is given `ctx_repr`.
- Context-aware policies opt in structurally through two separate methods.
- The CUDA-graph capture set for a 2D config is identical to the corresponding 1D config whose per-BS candidates are the union of all context buckets.

## Code Review

This pull request introduces a 2D routing schema for adaptive speculative decoding, allowing step selection to be parameterized by both batch size and a context length representation (ctx_repr). It updates the speculative workers and managers to compute and propagate this context representation and adds extensive unit tests for validation and routing. The review feedback highlights a critical performance issue where calculating the median sequence length using PyTorch tensors on the GPU (or via .item()) causes synchronous GPU-to-CPU transfers in the hot path. The reviewer suggests computing the median directly on the CPU using the sequence lengths available in batch.reqs to avoid this overhead.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Using `batch.seq_lens.median().item()` or `batch.seq_lens_cpu.median().item()` introduces a synchronous GPU-to-CPU transfer (`.item()`) or unnecessary PyTorch tensor overhead in the hot path of decode iterations. Under CUDA graphs, `batch.seq_lens_cpu` is `None`, which forces a synchronous GPU-to-CPU transfer on every single decode step, severely degrading performance and causing CPU-GPU bubbles.

Since `batch.reqs` is already on the CPU and contains the exact same sequence length information via `req.seqlen`, we can compute the median directly on the CPU using a simple sorted list indexing. This completely avoids any host-device synchronization and PyTorch tensor overhead.

```suggestion
        if batch.reqs:
            seqlens = sorted(req.seqlen for req in batch.reqs)
            ctx_repr = seqlens[len(seqlens) // 2]
        else:
            ctx_repr = 0
```
