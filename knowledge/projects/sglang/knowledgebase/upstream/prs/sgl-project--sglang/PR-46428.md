# [Perf] GGUF/MoE: llama.cpp's MMQ (MUL_MAT_ID path) behind a new ggml_moe_mmq op

[Upstream PR](https://github.com/sgl-project/sglang/pull/46428) · state: open · merged: False

## Original PR description

## Motivation

On main, the GGUF MoE path (`fused_moe_gguf`) is slow at prefill sizes: above 64 tokens it runs the 2024 dp4a `ggml_moe_a8` for the standard and K types, and for the i-quants it stays on the per-route MMVQ kernel at every token count. This PR runs MoE layers on the same llama.cpp MMQ that #43650 brings to the dense layers, through its MUL_MAT_ID path.

**Stacked on #43650** (and through it on #43636): the first five commits here are those PRs; review the last four.

One MoE layer, 64 experts, top-8, hidden 2560, bf16, CUDA graph, RTX 5070 Ti (sm_120), ms, `fused_moe_gguf` on main -> this PR:

| layer | 256 tokens | 2560 tokens | 16384 tokens |
|---|---|---|---|
| IQ3_S gate/up + IQ4_NL down (I 640) | 8.02 -> **0.770** | 80.0 -> **3.25** | main fails above 8191 tokens |
| Q4_K (I 768) | 2.55 -> **0.848** | 24.5 -> **3.54** | 157 -> **22.8** |
| Q6_K (I 768) | 3.47 -> **1.09** | 33.1 -> **4.28** | 211 -> **26.5** |
| IQ1_M (I 768), gate/up and down | 6.91 -> **1.14** | 71.9 -> **4.13** | |

The "main" column is the AOT per-route kernel `ggml_moe_a8_vec` and the dp4a `ggml_moe_a8` as `fused_moe_gguf` dispatched them when measured; main now dispatches a JIT port of the per-route kernel (`gguf_moe_a8_vec`), which this PR leaves in place for up to 4 tokens. IQ1_M goes through MMQ with #43650's tile loader (`patches/0002`). Up to 4 tokens `fused_moe_gguf` keeps the per-route `ggml_moe_a8_vec`: it wins at 1-2 tokens and is within about 20% at 3-5 (IQ1_M at 9 tokens: 0.27 ms per-route vs 0.31 ms MMQ).

## Modifications

**`ggml_moe_mmq(X, W, topk_ids, type, row, x_per_slot)`**, a new CUDA op (fp32 `[T, top_k, row]`), for every type `ggml_mul_mat_a8` supports:
- Routes are sorted by expert on the GPU with the vendored `mm_ids_helper` (`mmid.cu` / `mmid.cuh` from the same llama.cpp commit, byte-identical, added to `SHA256SUMS`): no host sync, CUDA graph capturable.
- gate / up quantizes each token once and scatters its q8_1 blocks to the token's routes; the down projection (`x_per_slot`) gathers per route. Both are modes of #43650's quantizer.
- `topk_ids` int32 or int64. Ids < 0 (expert parallelism), ids >= the expert count, and a repeated expert within a token give zero rows.
- Token counts above `mm_ids_helper`'s shared memory or the kernels' 32-bit offsets are processed in chunks.
- `W` is `[E, rows, row_bytes]`; only the storage after the last expert needs ggml's row padding, padded at load by `GGUFMoEMethod`.

**`fused_moe_gguf`** on CUDA, for MMQ types and more than 4 tokens: `ggml_moe_mmq` (gate/up), the activation in fp32, `ggml_moe_mmq` (down), then one bmm with the top-k weights. No `moe_align_block_size`. MUSA and the other paths are unchanged, including main's handling of masked routes.

**`llama_mmq/patches/0003-mmq-fixup-ids.patch`**: llama.cpp's stream-k fixup for MUL_MAT_ID read `ids_dst` for every tile of `ncols_max` before finding an expert's tile empty, up to `(ntx - 1) * J` entries past the buffer. The values are never used, so it passes while that memory is mapped. When `ids_dst` ends an allocation next to unmapped address space it is an illegal address: we hit it within a few rounds of 24K-27K-token prefills on a 16 GB card whose expert weights are remapped through the CUDA VMM (GPU coredump: Warp MMU Fault in `mul_mat_q_stream_k_fixup<IQ1_M>`), and not once in sixteen rounds with the patch. The fixup now returns for those tiles, as the main kernel already does. Output is unchanged.

**Two fixes found on the way:**
- `ggml_moe_a8` (dp4a, still used up to 4 tokens for non-MMQ types and on MUSA) skipped every expert above 255. On models with more than 256 experts those routes gave no rows. It now takes the expert count.
- With MoE tensor parallelism (`--tp 2` without `--ep-size`), the loader split `w2` along its output dim like `w1` / `w3`, giving each rank the wrong shape. Splitting along the intermediate dim would cut GGUF blocks, so the loader now raises `NotImplementedError` pointing to expert parallelism.

**Build:** `mmid.cu` and `mmq_moe.cu` join the `sgl_llama_mmq` object library (sm_80 / 90 / 100f / 120a), about +0.4 MB of objects.

## Accuracy Tests

`tests/test_gguf.py`:
- `ggml_moe_mmq` on all 19 MMQ types, against gguf-py's dequantization: synthetic weights with rows % 128 != 0 and K % 512 != 0; 8 / 64 / 128 experts; top-k 1 / 2 / 6 / 8; 9 / 65 / 512 / 4096 tokens; unused experts, masked ids, int32 and int64 ids, gate/up and down.
- The MoE sample files (16 experts), token chunking, repeated experts, an unsupported type, CUDA graph capture and replay with new routes.
- `fused_moe_gguf` against a torch reference, on both the vector and MMQ paths.
- 300 experts with every route above 255, for `ggml_moe_a8`.

**327 passed** on this stack (278 on #43650 alone), against a standalone build of the GGUF kernels on an RTX 5070 Ti. Relative L2 is the same q8_1 activation rounding as the dense MMQ (5-7e-3).

Not run: MUSA, and execution on sm_80 / 90 / 100.
