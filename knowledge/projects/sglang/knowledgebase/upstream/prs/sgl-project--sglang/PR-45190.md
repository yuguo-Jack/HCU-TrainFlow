# [Perf] [AMD] dsv41: Emit wo_b's MXFP8 input from the TP4 wo_a GEMM for verify rows on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45190) · state: open · merged: False

## Original PR description

## Motivation

At TP4 on gfx950, DSpark verify steps run wo_a as a bf16 bmm, and wo_b then quantizes the result to MXFP8 in a separate pass. TP2 and DP attention already run wo_a through the fp8-grid GEMM, which emits wo_b's MXFP8 input from its epilogue (#42055). TP4 missed it only because its exact shape takes the bf16 fast path first. This PR routes TP4 verify rows to that same GEMM and gives it the tiles 2 groups need.

## Modifications

- `_apply_wo_a_bf16_matmul`: when wo_b consumes MXFP8, TP4 verify rows 9-128 return `wo_a_fp8_grid_matmul(..., emit_fp8=True)`, as TP2 and DP attention do. 1-row decode, 2-8 verify rows (the small-batch kernel), rows above 128 (the bmm, faster there with `TRITON_HIP_USE_ASYNC_COPY=0`), deterministic mode and a bf16 wo_b are unchanged.
- `batched_gemm_bf16_fp8_grid`: its split-K and tile choices were tuned for 4 and 8 groups, and 2 groups launch half the CTAs. For 2 groups, split-K takes 32-row tiles in 4 splits above 32 rows (at 17-32 rows the existing 16-row tiles in 8 splits are as fast or faster, see below), and the single launch takes 32-row tiles (BLOCK_K 512) at 65-128 rows. TP4 decode batches that already run this GEMM pick up the same configs. Single-launch tiles give the same bits, so deterministic mode's output is unchanged.
- `test_single_launch_tile_table_is_bitwise_the_16_row_tile` patches `_tile_config`, so it also covers the 2-group tiles.

## Accuracy Tests

Operator check on MI355X (`lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025`, Triton 3.8.0) at TP4 shapes, 5 seeded draws per row count at every row count, against today's path (bf16 wo_a, then wo_b's own MXFP8 quant), plus each path's error against an fp32 reference:

| rows | result |
|---|---|
| verify 2-8, 129-384 | today's path, bitwise unchanged |
| verify 9-32 | at most 3 of 18K-66K fp8 codes one step apart (fp32 summation order), scales equal |
| verify 33-64 | at most 7 of 68K-131K codes one step apart, scales equal |
| verify 65-128 | at most 13 of 133K-262K codes one step apart, scales equal |
| decode 2-32, 65-256 | bitwise unchanged |
| decode 33-64 (split-K order) | at most 4 of 68K-131K codes one step apart, scales equal |

Where codes differ, the relative error against fp32 changes by at most 6e-7 (about 2.7e-2 on both paths). All-zero 32-element groups get a different scale byte with zero codes, as on the TP2 route. Deterministic mode is bitwise unchanged at 2-384 rows. `test_fp8_grid_producers_gfx95.py` and `test_deepseek_v4_amd_wo_a_bf16.py` pass on the same image (15 passed, 22 subtests).

GSM8K (`sglang.test.few_shot_gsm8k`, 1319 questions, parallel 64), DeepSeek-V4.1-Flash TP4 + DSpark, MI355X x4, on an earlier revision that took the same GEMM for verify rows 9-128:

| | run 1 | run 2 |
|---|---:|---:|
| base | 0.901 | 0.904 |
| this PR | 0.902 | 0.901 |

## Speed Tests and Profiling

Kernel level, MI355X x1, `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025` (ROCm 10, Triton 3.8.0) with the AgentX recipe's `SGLANG_USE_AITER=1 TRITON_HIP_USE_ASYNC_COPY=0 SGLANG_OPT_HIP_FLYDSL_MXFP8=1 TORCH_BLAS_PREFER_HIPBLASLT=1`, TP4 shapes, CUDA graph replay median of one graph that cycles 24 weight copies (wo_a streams from HBM as across 40 layers), before and after in one process, us per call of wo_a plus the quant that produces wo_b's MXFP8 input:

| verify rows | before | after |
|---:|---:|---:|
| 6, 8 | 9.84, 9.87 | unchanged |
| 9 | 11.05 | 7.50 |
| 12 | 11.22 | 7.52 |
| 18 | 13.21 | 8.42 |
| 24 | 13.50 | 8.66 |
| 30 | 13.60 | 8.66 |
| 36 | 12.94 | 10.48 |
| 48 | 14.42 | 10.56 |
| 60 | 13.99 | 10.49 |
| 96 | 17.23 | 12.08 |
| 120 | 14.57 | 12.52 |
| 132-256 | 17.62-18.97 | unchanged |

With 6 verify rows per request and 40 layers, that is about 190-200 us less GPU time per verify step at bs 3-5, 100-155 us at bs 6-10, 206 us at bs 16 and 82 us at bs 20, and no change from bs 22 on. Under `--monokernel-backend amd`, which serves TP4 verify steps up to bs 8, the steps that still run this code are bs >= 9.

The 2-group split-K config (GEMM alone, cold weights, two GPUs): at 17-32 rows the 16-row tiles in 8 splits run 8.4-8.7 us and 32-row tiles in 4 splits 8.9-9.3 us, so the new config starts at 33 rows; at 33-64 rows it runs 10.4-10.6 us against 11.4-13.8 us.

Above 128 rows the GEMM loses to the bmm plus wo_b's quant under `TRITON_HIP_USE_ASYNC_COPY=0` (by 0.7-1.7 us per layer at 144-256 rows; with async copy on it would still win there), so this PR stops at 128 rows.
