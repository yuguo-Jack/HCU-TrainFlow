# [Perf] [AMD] dsv41: Emit wo_b's MXFP8 input from the TP4 wo_a GEMM for verify rows on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45190) · state: open · merged: False

## Original PR description

## Motivation

At TP4 each rank of DeepSeek-V4.1-Flash holds 2 of the 8 `o_groups`. On gfx950, `_apply_wo_a_bf16_matmul` computes wo_a for DSpark target-verify rows with `wo_a_bf16_small_batch` (2-8 rows) or a strided `torch.bmm` (9-384 rows) and returns bf16. wo_b's aiter MXFP8 route then quantizes that bf16 in a separate `mxfp8_e4m3_quantize` launch. At TP2 and under DP attention, the fp8-grid GEMM fork already emits wo_b's `Mxfp8Activation` from its epilogue (#42055). The caller passes `emit_fp8=True` at TP4 as well, but the TP4 branch ignores it.

On MI355X the separate quant costs about 2 us per layer at 2-8 rows. At 9-256 rows the bmm is also 1-5 us slower than the fork's kernels run at tiles sized for 2 groups.

## Modifications

- `wo_a_bf16_mxfp8_gfx95` (`kernels/ops/gemm/dsv4_wo_a.py`) computes the TP4 wo_a for 2-256 rows and returns `Mxfp8Activation`: fp8 e4m3 `[M, 2048]` plus ue8m0 `[M, 64]`, the operand wo_b's gfx950 routes take.
  - 2-8 rows: the existing `_wo_a_partial` split-K partials, then a reduce that rounds to bf16 exactly like `_wo_a_reduce` and quantizes with `fp8_grid_quant` (the rule of the TP2 epilogue). The output is bitwise equal to today's bf16 route followed by wo_b's own quant.
  - 9-256 rows: the fork's split-K and single-launch kernels with `EMIT_FP8`, at tiles measured for 2 groups. The fork's own tile table targets 4 and 8 groups and, above 64 rows, is slower than the bmm at 2 groups.
- `_apply_wo_a_bf16_matmul`: verify rows 2-256 take this route when `emit_fp8` is set, i.e. when wo_b consumes MXFP8 (`SGLANG_HIP_WO_A_MXFP8`, on by default on HIP). Other cases are unchanged:
  - 1-row decode keeps the GEMV: no MXFP8 variant was faster than GEMV plus quant.
  - More than 256 rows keep the bmm, which is as fast as the fused route there.
  - Deterministic and batch-invariant inference keep their current route: the TP4 fast path is already off.
  - The DSpark draft does not request `emit_fp8`, so it also keeps its current route.
- Kernel inventory entry and a gfx950 unit test (graph replay with mutated inputs).

Opt-in mono decode (#43497, #44033) fuses wo_a and wo_b inside its own kernel for 48 rows or fewer. This PR changes the default path.

## Accuracy Tests

- `test/registered/unit/models/test_deepseek_v4_amd_wo_a_bf16.py` (new `test_verify_rows_emit_wo_b_mxfp8`; the whole file passes on MI355X):
  - 2-8 rows: q and scale bytes are bitwise equal to the bf16 route followed by `mxfp8_operand`.
  - 9-256 rows: relative RMS of the dequantized difference is below 1e-3.
- Operator check on MI355X at 1-384 rows, with real wo_b shapes (aiter `gemm_a8w8_blockscale`, `[5120, 2048]` fp8 weight):
  - 2-8 rows: q, scale and wo_b output are bitwise identical to today's. 12-24 rows were also identical in the measured cases.
  - 36-256 rows: q and scale are bitwise equal to quantizing the new kernel's own bf16 output. Against today's hipBLASLt bf16, at most 9 of about 400K fp8 codes move by one step (fp32 summation order), and no scale byte changes.
  - All-zero 32-groups get scale byte 85 instead of 19 (the 1e-10 amax floor of `fp8_grid_quant`, as on the TP2 route). Their codes are 0, so wo_b's output is unaffected.
- GSM8K (`sglang.test.few_shot_gsm8k`, 1319 questions, parallel 64), TP4 server below, two runs per arm: 0.901 / 0.904 before, 0.902 / 0.901 after.

## Speed Tests and Profiling

With 6 verify rows per request (DSpark block 5) and 40 layers, that is about 78 us (bs 1), 178 us (bs 4) and 192 us (bs 16) less GPU time per verify step. Against the measured step times below, that is about 1.2%, 1.7% and 1.0%.

End-to-end setup:

- Hardware and model: MI355X x4, same image, DeepSeek-V4.1-Flash, TP4 + DSpark (block 5).
- Server env: the recipe env (`SGLANG_USE_AITER=1`, `AITER_BF16_FP8_MOE_BOUND=0`, `TORCH_BLAS_PREFER_HIPBLASLT=1`, ...) plus `SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL=true`.
- Server args: `--fp8-gemm-backend aiter --enforce-shared-experts-fusion --enable-decoder-swa-bounded-replay --cuda-graph-backend-prefill disabled --chunked-prefill-size 16384 --mem-fraction-static 0.80 --max-running-requests 64 --cuda-graph-max-bs-decode 64 --prefill-decode-interval 32 --swa-prefix-tails 2048`.
- Workload: random 1024 in / 1024 out, with 8 / 16 / 64 prompts at concurrency 1 / 4 / 16.
- Before and after ran on the same 4 GPUs, one after the other, interleaved (base, PR, base, PR). The first base run, the first server on a freshly allocated node, stalled in decode (c4 TTFT 206 vs 104 ms), so the table uses the second base run.

| median TPOT (ms) | 1.36 | 1.33 / 1.30 | 2.17 | 2.36 / 2.21 | 3.78 | 3.68 / 3.71 |
| accept length | 4.80 | 4.72 / 4.86 | 4.70 | 4.34 / 4.31 | 4.66 | 4.68 / 4.57 |

The verify-step time is 2.6% (c1), 6-8% (c4) and 3-6% (c16) lower, but DSpark's accept length moves by up to 0.4 between runs, so output throughput goes both ways (c4: 1520 base vs 1344 / 1383). The end-to-end runs are consistent with, but cannot resolve, the 1.0-1.7% the kernel numbers account for; the kernel numbers are the effect to attribute to this PR. Prefill (16K tokens in, c1, 24 prompts; this path is unchanged): median TTFT 237.2 ms base vs 241.2 / 236.5 ms.
