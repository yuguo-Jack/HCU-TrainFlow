# feat(kv-cache): generic OCP MXFP4 (block-32) KV cache via FlashMLA on SM100

[Upstream PR](https://github.com/sgl-project/sglang/pull/42759) · state: closed · merged: False

## Original PR description

## Summary

Adds a generic `--kv-cache-dtype mxfp4`: native OCP MXFP4 KV cache with
**block-size-32 E2M1 + one E8M0 scale per 32 values**, stored as packed `uint8`
(two E2M1 per byte) plus a separate E8M0 scale buffer and a BF16 RoPE tail.
This fills the `mxfp4` name that `configure_kv_cache_dtype` currently reserves
but does not implement.

Refs #36383.

Distinct from `fp4_mx_block16` / `nvfp4` (which use `torch.float4_e2m1fn_x2`):
mxfp4 keeps data as `uint8` with a separate E8M0 scale buffer because the
block-32 + E8M0/32 layout decouples scales from data and avoids a hard
dependency on `torch.float4_e2m1fn_x2`.

## Commits

1. `add native OCP MXFP4 KV quantization kernels` — codec (`MXFP4KVQuantizeUtil`),
   JIT dequant kernel, `mxfp4` dispatch (-> `uint8`), `--kv-cache-dtype` choices.
2. `store DSA KV cache in MXFP4 pages` — `DSATokenToKVPoolMXFP4` + configurator
   byte layout (requires `kv_lora_rank=512`, `qk_rope_head_dim=64`).
3. `route DSA MXFP4 through FlashMLA on SM100` — DSA backend + FlashMLA bridge +
   SM100 (Blackwell) gate.

## Validation (SM100)

- FlashMLA MXFP4 numerical smoke vs BF16 reference: **cosine 0.99999**.
- Codec round-trip: Triton quantize **bit-exact** vs the Torch reference;
  dequant is a fixed point.
- CUDA graph: prefill + decode capture/replay **pass** on a dense DSA config.
- End-to-end correctness on a DSA MoE model (TP8/EP8): math / factual / cache-reuse
  prompts correct.
- Memory: at equal pool budget, mxfp4 holds **~1.48x** more tokens than fp8_e4m3.

## Status / caveats (draft)

- Branch is based on an earlier `main`; **needs rebase**. The FlashMLA wrapper has
  since gained a `kv_format` parameter — the mxfp4 flag should be reconciled with
  that interface during review.
- End-to-end **CUDA-graph** on a full MegaMoE model currently hits a
  `cudaErrorLaunchFailure` during capture that reproduces with fp8 KV too and is
  masked by `CUDA_LAUNCH_BLOCKING=1` — i.e. a MegaMoE+CUDA-graph stream-ordering
  issue, independent of this KV-cache change. mxfp4 KV works in eager and on dense.
- Overlaps with the DSV4 MXFP4 effort (#32741 / #37135-#37138); happy to align.
