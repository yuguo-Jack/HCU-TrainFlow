# [Fix] Feed the relayed last token to penalizers under the overlap scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/41290) · state: open · merged: False

## Original PR description

## Relation to #41158

#41158 (@he-yufeng) targeted the same issue. After the [discussion there](https://github.com/sgl-project/sglang/pull/41158#issuecomment-5823731005), he [verified the points against current `main` and suggested opening this one](https://github.com/sgl-project/sglang/pull/41158#issuecomment-5838213994), closing #41158 as superseded. Thanks to him for the quick check, and to @Id545 for the spec-decode note (see Modifications). In short, this PR:

- applies to current `main` (#41158 edits `scheduler_output_processor_mixin.py`, which was retired in #25637);
- feeds the penalizer on the forward stream in `resolve_forward_inputs`, before `copy_for_forward()` snapshots the penalty buffers, so it doesn't depend on loop ordering or on whether sampling is delayed;
- also covers `--enable-mixed-chunk` (the version I described on #41158 left that path on the Req-side feed; this one fixes it too);
- has CPU regression tests that fail on `main`.

## Motivation

Fixes #41124. With the overlap scheduler (the default), frequency, presence and repetition penalties for output token `i` are computed over `[prompt[-1]] + output[:i-1]` instead of `output[:i]`: the first decode step penalizes the last prompt token, and every later token is penalized one step late. The issue has logprob measurements against a float32 HF recompute showing this under overlap and not with `--disable-overlap-schedule`.

Mechanism: `ScheduleBatch.prepare_for_decode` calls `cumulate_penalty_output_tokens`, which reads `req.output_ids[-1]` (or `origin_input_ids[-1]` before any output). Under overlap, the next decode batch is prepared while the previous step's token is still in flight, so `req.output_ids` trails by one step. The real token only exists on the device, in `future_map.output_tokens_buf`, and `resolve_forward_inputs` gathers it at forward entry.

## Modifications

- `schedule_batch.py`: under overlap, `prepare_for_decode` sets a `penalty_update_pending` flag instead of cumulating the Req-side token. The non-overlap path is unchanged.
- `overlap_utils.py::resolve_forward_inputs`: in the decode branch, right after gathering `input_ids` from the future map, feed those tokens to the penalizer orchestrator and clear the flag. This runs on the forward stream before `_forward_isolation` → `copy_for_forward()` → `update_penalties()` builds the accumulated penalty buffers, so the buffers used for sampling step `i` include token `i-1`. Rows past `len(reqs)` (a beam tail) are sliced off, since the penalizers are reqs-aligned.
- Mixed chunked prefill (`--enable-mixed-chunk`): `mix_with_running` appends the running decode rows after the new prefill rows, and the mixed branch of `resolve_forward_inputs` gathers their relayed tokens into `decode_gpu`. The merged batch inherits the pending flag, and that branch feeds `decode_gpu` to just those rows. For that, `BatchedPenalizerOrchestrator.cumulate_output_tokens` takes a `row_start` (default 0, so every existing caller is unchanged), and each penalizer updates only `rows = slice(row_start, row_start + len(output_ids))`. Prefill rows have no output yet and are left untouched. `min_new_tokens` gets the same row slice, so its count stays in step.
- Non-overlap is unchanged: there the previous step's result is processed before `prepare_for_decode`, so `req.output_ids[-1]` is current and is fed there as before. `resolve_forward_inputs` still gathers the relayed token on that path, but `penalty_update_pending` is only set under overlap, so nothing is fed twice (`test_non_overlap_penalizes_req_last_output_token`).
- Speculative decoding is out of scope: `prepare_for_decode` returns before this code for spec, and `eagle_prepare_for_decode` keeps its existing "relaxed" Req-side feed (`cumulate_penalty_output_tokens`, documented as relaxed in `eagle_utils.py`). The updated comment on `cumulate_penalty_output_tokens` says that the Req-side token trails by one step under overlap, so that limitation stays visible.

Stream ordering, for review: the in-place penalizer write moves from the schedule stream (in `prepare_for_decode`) to the forward stream (in `resolve_forward_inputs`, after `forward_stream.wait_stream(schedule_stream)`). On CUDA, the next iteration's schedule-stream reads and rebinds (`filter`/`merge`) come after `_apply_war_barrier()`, which waits on an event recorded after this forward's shared reads, so they see the write. Where that barrier is off (non-CUDA devices unless `SGLANG_ENABLE_WAR_BARRIER=1`), a `filter`/`merge` on the schedule stream is not fenced against this write, which is the same exposure `main` already has for the forward-stream read of these buffers in `update_penalties`. I didn't add a sync for that case; happy to if you'd prefer one.

**Related PRs.** #33643 (closed by the idle bot on 2026-09-26 while still a draft) and #40244 (closed by its author on 2026-09-25) change how *speculative* decoding feeds accepted tokens to the penalizers (a per-request cursor over `output_ids`). This PR only changes the non-spec overlap decode path, so the two don't overlap in behavior. The shared text is the comment on `cumulate_penalty_output_tokens`, and I'm happy to rebase onto either.

It also removes the per-step pinned H2D copy of the Req-side tokens in `cumulate_penalty_output_tokens` on the overlap decode path.

- he-yufeng · comment · 2026-10-04T18:25:47Z · [source](https://github.com/sgl-project/sglang/pull/41290#issuecomment-5983041153)

Coming over from #41158 as promised. Read the diff against current main and the approach is the right one: feeding on the forward stream in `resolve_forward_inputs`, ahead of the `copy_for_forward()` snapshot, removes the dependence on loop ordering that made the Req-side feed trail by one under overlap.

The one place I probed hard is the mixed-branch indexing, because it is the only spot where the alignment is implicit. It holds: `mix_with_running` sets `mix_running_indices = running_batch.req_pool_indices` (schedule_batch.py:3192), which is strictly one row per request (`batch_size() == len(reqs)`, and the beam tail lives in the GPU buffers past `bs`, never in `req_pool_indices`; the "Rows past bs are a beam tail, not requests" comment at :3262 is the same invariant your decode-branch slice relies on). So `decode_gpu.shape[0]` is exactly the running request count, `row_start = len(batch.reqs) - decode_gpu.shape[0]` lands on the first running row, and the decode-branch slice and the mixed-branch `row_start` are two spellings of the same reqs-alignment. Might be worth one line in the PR body, because the next reviewer will trip on the same spot and the beam tail reads like it could leak into the gather.

The stream-ordering argument matches what I saw when working in this file: on CUDA the next schedule-stream rebind comes after `_apply_war_barrier()`, and where the barrier is off the exposure is the same one `main` already carries for `update_penalties`, so not adding a sync here is consistent rather than careless.

Scope honesty: this is a code-reading review, I did not run the CPU tests. The `row_start` default keeps every existing caller untouched, and `len_output_tokens[rows] += 1` keeps prefill rows' min_new_tokens count at zero, which is the behavior you want on a mixed step.
