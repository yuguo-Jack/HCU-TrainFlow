# [Fix] sampling: Feed the relayed last token to penalizers under the overlap scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/41290) · state: open · merged: False

## Original PR description

## Motivation

Fixes #41124. With the overlap scheduler (the default), frequency, presence and repetition penalties are applied one token late. For output token `i` they count `[prompt[-1]] + output[:i-1]` instead of `output[:i]`. The first decode step penalizes the last prompt token, and every later token is penalized a step late. The issue shows this with logprobs against a float32 HF recompute; `--disable-overlap-schedule` is correct.

Cause: `prepare_for_decode` feeds `req.output_ids[-1]` to the penalizers. Under overlap the next batch is prepared before the previous token is processed, so that value trails by one. The real token is only on the device (`future_map`) until `resolve_forward_inputs` gathers it.

## Modifications

- Under overlap, `prepare_for_decode` marks the batch (`penalty_update_pending`) instead of feeding the stale token.
- `resolve_forward_inputs` feeds the gathered tokens to the penalizers right after the gather, before `copy_for_forward()` snapshots the penalty buffers.
- Mixed chunked prefill: the same feed goes to the running decode rows only (`cumulate_output_tokens(row_start=...)`, default 0, so existing callers are unchanged). Those rows line up with the running requests because the scheduler only mixes when no running request has a beam group; a beam tail can follow the request rows only in a plain decode forward, which the decode branch slices off with `[: len(batch.reqs)]`.
- The non-overlap path and speculative decoding are unchanged.

Stream order: under overlap the feed runs on the forward stream, while `filter()` and `merge()` copy the same buffers on the schedule stream. The orchestrator records an event right after the feed, and `filter()` / `merge()` wait on it before they copy or free the buffers, so finishing one request can't drop a surviving request's token. This doesn't rely on the scheduler's WAR barrier, which is off by default outside CUDA.

This supersedes #41158 at @he-yufeng's suggestion (it edited a file retired in #25637). Thanks to him, and to @Id545 for the spec-decode note.

- he-yufeng · comment · 2026-10-04T18:25:47Z · [source](https://github.com/sgl-project/sglang/pull/41290#issuecomment-5983041153)

Coming over from #41158 as promised. Read the diff against current main and the approach is the right one: feeding on the forward stream in `resolve_forward_inputs`, ahead of the `copy_for_forward()` snapshot, removes the dependence on loop ordering that made the Req-side feed trail by one under overlap.

The one place I probed hard is the mixed-branch indexing, because it is the only spot where the alignment is implicit. It holds: `mix_with_running` sets `mix_running_indices = running_batch.req_pool_indices` (schedule_batch.py:3192), which is strictly one row per request (`batch_size() == len(reqs)`, and the beam tail lives in the GPU buffers past `bs`, never in `req_pool_indices`; the "Rows past bs are a beam tail, not requests" comment at :3262 is the same invariant your decode-branch slice relies on). So `decode_gpu.shape[0]` is exactly the running request count, `row_start = len(batch.reqs) - decode_gpu.shape[0]` lands on the first running row, and the decode-branch slice and the mixed-branch `row_start` are two spellings of the same reqs-alignment. Might be worth one line in the PR body, because the next reviewer will trip on the same spot and the beam tail reads like it could leak into the gather.

The stream-ordering argument matches what I saw when working in this file: on CUDA the next schedule-stream rebind comes after `_apply_war_barrier()`, and where the barrier is off the exposure is the same one `main` already carries for `update_penalties`, so not adding a sync here is consistent rather than careless.

Scope honesty: this is a code-reading review, I did not run the CPU tests. The `row_start` default keeps every existing caller untouched, and `len_output_tokens[rows] += 1` keeps prefill rows' min_new_tokens count at zero, which is the behavior you want on a mixed step.
