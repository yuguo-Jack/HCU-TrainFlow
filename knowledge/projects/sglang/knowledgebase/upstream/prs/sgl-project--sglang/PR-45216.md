# [Fix] observability: Keep health probes and scrapes out of the HTTP request metrics

[Upstream PR](https://github.com/sgl-project/sglang/pull/45216) · state: open · merged: False

## Original PR description

## Motivation

`sglang:http_requests_total`, `sglang:http_responses_total` and `sglang:http_requests_active` are recorded by a middleware over every route, so they also count the orchestrator's probes (`/health`, `/health_generate`, `/ready`, `/ping`) and Prometheus's own `/metrics` scrapes. Two effects:

- A pod that is still loading answers `/ready` with 503. In an error-rate query such as `sum(rate(sglang:http_responses_total{status_code!="200"}[30s])) / sum(rate(sglang:http_responses_total[30s]))` those count as errors.
- A scrape every second adds one request per second to an idle server, so request rates and the active gauge never read zero.

Measured on 2026-10-17 with SGLang v0.5.21 serving Qwen3-8B on an H100: an Argo Rollouts canary check with the query above read 3.2% errors and rolled the new version back, while every one of its 33 chat completions had returned 200. The 503s were three readiness probes during warm-up, out of about 90 responses, most of them `/metrics` scrapes. A healthy version would have been rolled back the same way.

Companion to #45211, from the same measurement; the two are independent.

## Modifications

- `HTTP_METRICS_EXCLUDED_PATHS` in `sglang/srt/observability/http_request_metrics.py` names the probe and scrape paths the server serves; `track_http_status_code` passes those requests through without touching the three metrics. Client traffic is counted exactly as before.
- Unit tests in `test/registered/unit/observability/test_http_request_metrics.py`: the middleware on a small FastAPI app counts a chat completion and not `/ready`, `/health` or a `/metrics` scrape (metrics mocked, so the existing test's uninitialized-metrics check still holds); every excluded path other than `/metrics`, which is mounted at startup, is a route on the server's app.

Probe outcomes stay observable where they already are: the readiness and liveness state in Kubernetes, and the server log. If an opt-in flag is preferred over a changed default, the set can become a `--metrics-exclude-paths` argument with the same default.
