# [Fix] tokenizer: Fix abort race before scheduler dispatch

[Upstream PR](https://github.com/sgl-project/sglang/pull/44449) · state: open · merged: False

## Original PR description

## Motivation

This PR splits out the tokenizer-side abort race fix from @Denji-kk's [#39520](https://github.com/sgl-project/sglang/pull/39520), following the [review suggestion](https://github.com/sgl-project/sglang/pull/39520#issuecomment-5861721016) to separate it from multi-tokenizer control coordination.

In multimodal RL rollouts, an abort or an abort-mode pause can arrive while image/video loading and preprocessing are still in progress, before the request reaches the scheduler. An internal image-heavy workload exposed the practical impact: the scheduler was already idle, but pending HTTP requests continued completing slowly as preprocessing drained, and the caller's abort timeout expired. This observation motivates the change. The backlog and delay depend on input size, concurrency, and tokenizer-worker configuration.

There are three related problems at this boundary:

1. **An abort can be missed.** If `AbortReq` reaches the scheduler before the generation request, there is nothing to cancel yet. The tokenizer can subsequently dispatch the request anyway. This race also affects a single Python tokenizer worker.
2. **Checking only before dispatch still waits for useless work.** Local marking and re-checks prevent the cancelled request from being sent, but preprocessing may continue until completion before its result is discarded. The request can retain its model-update read lock during that wait, delaying request completion and abort-mode draining even when the scheduler is idle.
3. **Discarded features still need an owner to release them.** Preprocessing may already have allocated CUDA IPC leases. If the request is never dispatched, no scheduler consumer will acknowledge them. Repeated aborts can exhaust the pool and cause feature transport to fall back to CPU.

This PR therefore combines the pre-dispatch race fix from #39520 with cooperative preprocessing cancellation and undispatched-feature cleanup. For single requests and sequential batches, abort can end an interruptible preprocessing wait and let the request unwind without waiting for the discarded work to finish. Running processor threads cannot be stopped forcibly, so their late results are reclaimed instead of dispatched.

The intended latency benefit is faster cancellation and draining on these paths, not faster token generation. Resource cleanup is part of making that early exit safe, rather than a separate transport optimization. Cross-worker control coordination remains out of scope.

## Modifications

- Mark local requests before forwarding `AbortReq`, and re-check before dispatch and after asynchronous feature publication. Filter aborted batch members without dropping live requests.
- Finish intercepted requests locally with `finish_reason.type = "abort"`. Retain their state until the response waiter takes ownership, preserve one-time LoRA release, and allow subsequent rid reuse. Exclude health probes from local abort marking so they still reach the scheduler.
- Cancel preprocessing tasks for single requests and sequential batches so interruptible waits can end promptly and the request can release its read lock without waiting for unused results. Distinguish server-requested aborts from cancellation of the outer request task; client cancellation still propagates as `CancelledError`.
- Reuse VMM `cancel_for_dispatch()` and IPC `MmItemMemoryPool.cancel_proxy()` to return undispatched leases. Attach cleanup to the processor executor's underlying future so a running thread's late result is not abandoned. The same cleanup also covers exceptions during hashing or validation after multimodal preprocessing has produced IPC features.
- Propagate cancellation to parallel-sampling children and track shared IPC ownership so locally discarded children do not release features already handed to the scheduler. Keep parent states registered during expansion so `abort_all` also reaches children not yet created.

This complements the scheduler-side cleanup in [#43475](https://github.com/sgl-project/sglang/pull/43475): this PR handles work that has not reached the scheduler.

### Scope and limitations

- Worker-local only: no new cross-process messages, coordinator, broadcast/ACK barriers, timeouts, fencing, or changes to the pause/weight-update/memory-control implementations. With multiple tokenizer workers, an abort received by a non-owning worker is still forwarded as before; this PR does not solve cancellation of preprocessing in a sibling worker.
- Cancellation is cooperative. Synchronous preprocessing on the event loop, already-running thread work, and submitted GPU work cannot be forcibly interrupted. Late thread results are cleaned up rather than dispatched.
- Batched tokenization and parallel-sampling preprocessing still finish before their results are checked at dispatch; immediate preprocessing cancellation is limited to single requests and sequential batches.
- Local abort marking preserves the scheduler's prefix-matching behavior, including when the exact rid exists. This requires an O(N) scan of local request states per accepted abort; no prefix index is introduced.

## Speed Tests and Profiling

No end-to-end throughput or abort/drain-latency benchmarks were run. The internal workload observation in Motivation is not a before/after comparison, and its timing cannot be extrapolated to a single-worker deployment.

The regression tests verify that abort can finish a request while its preprocessing is blocked, and that a running processor thread's result is reclaimed after the cancelled caller has returned. These establish the early-exit behavior, not a measured speedup. The expected benefit is reduced cancellation/drain latency when interruptible preprocessing would otherwise keep requests alive.

The change adds local cancellation checks, task bookkeeping for cancellable preprocessing, and the prefix scan noted above. It adds no generation-path IPC round trip; token-generation throughput improvements are not claimed.
