# [Feat] openai: Honor the X-Session-ID request header

[Upstream PR](https://github.com/sgl-project/sglang/pull/45620) · state: open · merged: False

## Original PR description

## Motivation

vLLM's OpenAI server accepts the session identity as an `X-Session-ID` request header, so callers and proxies can leave the JSON body untouched. `sgl-router` already routes on this same header — it is its default `--session-id-header` — but the Python server ignored it, so the backend dropped the identity the router had just routed on.

## Changes

- `apply_session_id_header()` in `entrypoints/request_headers.py` fills `session_id` from `X-Session-ID` when the body leaves it unset.
- A body `session_id` always wins; this only fills a missing value.
- The header is ignored when `session_params` is present, because the scheduler treats the two session forms as mutually exclusive.
- Applied in the route handlers for `/v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/invocations` and the native `/generate` (`serve_generate_request`), which previously honored only the `x-override-*` headers.

### Why the route, not the adapted request

`session_id` already exists on `ChatCompletionRequest` / `CompletionRequest` / `ResponsesRequest`, so the header is written to the request object before dispatch instead of to the `GenerateReqInput` adapted from it. Two pieces of existing logic inspect the request first and would otherwise disagree with the backend:

- `GenerateReqInput` rejects `session_id` and `session_params` together (`io_struct.py`), and the `session_params` guard here depends on seeing the body value.
- The Unlimited-OCR v2 document splitter refuses to split a request that carries a session (`models/unlimited_ocr_v2_support/chat.py`, `_is_splittable`). With the header applied after adaptation, such a request would still be split into N windows, each registering the same session id.

The adapted request copies `session_id=request.session_id` as it already did, so no serving module changes.

## Tests

Added to `test/registered/cpu/test_request_headers.py` (`stage-a-test-cpu-intel`):

- Five unit cases on the helper: header fills an unset `session_id`, the body wins, absent/empty header is ignored, `session_params` disables it.
- Three route-level cases that post through a FastAPI app to the native `/generate` route and assert the captured `GenerateReqInput` carries the id.
- Two route-level cases that post to the real `/v1/chat/completions` route and assert the header is on the request object before dispatch.

### Known limitation

The Rust frontend (`SGLANG_RUST_SERVER`) parses only the `x-override-*` / routing-key headers, so it does not yet read `X-Session-ID`. Nothing here changes that; it is a separate parity gap.

No release-notes label needed: behavior only changes for requests that explicitly send the header.
