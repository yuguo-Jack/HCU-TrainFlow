# [AMD][Perf][mem_cache] Cut three per-step kernel launches from paged decode alloc

[Upstream PR](https://github.com/sgl-project/sglang/pull/41664) · state: open · merged: False

## Original PR description

## Motivation

Part of optimizing MiniMax-M3 for vision-language serving -- one image per request at 512x512 to 2048x1600, Measurements are on that VL sweep.

`alloc_for_decode` runs once per decode step on `[bs]`-sized tensors, where kernel launch count dominates the arithmetic entirely. Three of its launches are avoidable without changing what it computes.

## What this does

Three launches removed from the paged decode path:

1. **`last_loc` in one launch instead of two.** `req_to_token[req_pool_indices, seq_lens - 1]`
   costs an elementwise `sub` plus an advanced-index gather. `common.py` already
   has a fused Triton kernel for exactly this.
2. **One `[bs]` `copy_` dropped.** `locs = seq_lens_gpu.clone()` becomes
   `locs = seq_lens_gpu`.
3. **One `[bs]` add dropped.** The allocator already materialises
   `seq_lens + token_per_req` to size its allocation; `prepare_for_decode` then
   recomputed the identical add. The allocator now publishes it as
   `batch.seq_lens_next` and the caller adopts it.

### Isolated vs cumulative e2e performance

The sweep above is deliberately narrow -- three VL configs at TP2 -- and it isolates
this one change. It is one of a series of VL-specific optimizations (#41662, #41663, #41665, #41672),
which cumulatively give over 20% uplift over the baseline across a wider 8-row
config sweep at TP2, TP4 and TP8.

The 8-row sweep tests how the proportion of VL input tokens affects inference
performance. It is parameterized by image size, input length and concurrency:

Cumulative output throughput, geomean over the 8 rows, each against a baseline run
on the same node, tensor-parallel width and device set:

| sweep | rows | TP | cumulative output throughput |
|---|---|---|---|
| VL image sweep | 8 | TP2 | **+25.85%** |
| VL image sweep | 8 | TP4 | **+20.41%** |
| VL image sweep | 8 | TP8 | **+24.27%** |

A cumulative total cannot be divided back into per-PR shares, which is why this PR
quotes its isolated number above rather than a share of the total.

## Compatibility

This touches core decode allocation for all models and backends, so the blast
radius is wider than the other MiniMax-M3 changes — flagging that explicitly for
review. All three changes are launch-count reductions, not numeric ones: the
computed `out_cache_loc`, `last_loc` and `seq_lens` are unchanged.
`get_last_loc_triton_safe` keeps its pre-split signature, dtype and semantics.

And depends on #37732 and #38035 for accurate benchmark numbers
