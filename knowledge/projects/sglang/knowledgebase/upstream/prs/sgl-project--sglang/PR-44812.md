# [Perf] qwen3.5: fuse GemmaRMSNorm with FP8 / NVFP4 input quant

[Upstream PR](https://github.com/sgl-project/sglang/pull/44812) · state: open · merged: False

## Original PR description

## Motivation

In Qwen3.5 dense NVFP4/FP8 checkpoints (e.g. Qwen3.8-27B-NVFP4), every norm that feeds a quantized projection runs as two kernels: `gemma_fused_add_rmsnorm`, then a separate activation quant (`fp4_quantize` before `gate_up_proj`, `static_quant_fp8` before the attention `qkv_proj`). flashinfer already ships fused residual-add + RMSNorm + quant kernels for both formats. `RMSNorm` uses the FP8 one through `fuse_input_quant`; `GemmaRMSNorm` uses neither.

## Modifications

- `GemmaRMSNorm.fuse_input_quant(linear)`, mirroring `RMSNorm`. In `forward_cuda` the norm emits a pre-quantized input when the consumer qualifies:
  - static per-tensor FP8 linear: flashinfer `fused_add_rmsnorm_quant` / `rmsnorm_quant` -> `(fp8, scale, orig_dtype)`
  - NVFP4 W4A4 ModelOpt linear (non-AWQ, non-Marlin, `_accepts_prequantized_fp4`): flashinfer `add_rmsnorm_fp4quant` / `rmsnorm_fp4quant` -> `(fp4, block_scale)` in the same layout `fp4_quantize` returns (uint8 `[M, K/2]`, 128x4-swizzled uint8 `[round_up(M,128), K/16]`)
  
  Both use the stored `gemma_weight` (`1 + w`) as a plain RMSNorm weight.
- The FP8 helper is factored out of `RMSNorm.forward_with_per_tensor_quant_fusion` so both norms share it.
- `ModelOptFp8LinearMethod` is now recognized as a static per-tensor FP8 consumer (unless Marlin). Its `apply` accepts the `(fp8, scale, dtype)` tuple on every path: the SM12x small-M dispatcher (`try_sm120_fp8_linear`) and `apply_fp8_linear_bmm_flashinfer` now take an already-quantized fp8 input instead of re-quantizing; `apply_fp8_linear` already did.
- Qwen3.5 wiring: post-attention norm -> `mlp.gate_up_proj` in every dense layer; input norm -> `qkv_proj` in full-attention layers. GDN layers keep the bf16 input norm because `in_proj_ba` consumes it. `forward_prepare_cuda_fused` reads `seq_len` from `qkv` so a tuple input works.

Numerics: the fused kernels quantize the fp32 normed value directly instead of the bf16-rounded one. On random inputs about 1-2% of FP4 codes / FP8 values land one step away from the unfused chain; valid block scales differ by at most one code.

## Accuracy Tests

- `test/registered/layers/test_layernorm_fusion.py` on sm_121 (flashinfer 0.7.2): 8 passed, 38 subtests. New cases:
  - `TestGemmaRMSNormInputQuantFusion`: FP8 and NVFP4 outputs vs the unfused reference (0-dim scales, as ModelOpt layers hold them), residual update, and the unfused fallback.
  - `TestPrequantizedFp8Linear`: a pre-quantized fp8 input gives bit-identical output to the bf16 input through `apply_fp8_linear_bmm_flashinfer` and `try_sm120_fp8_linear`.
- GSM8K on Qwen3.8-27B-NVFP4 (base vs this PR): **pending** (test box offline), will be added.

## Speed Tests and Profiling

Kernel chain at bs1, hidden 5120, sm_121, CUDA-graph timed:

| chain | unfused | fused |
|---|---|---|
| add + Gemma RMSNorm + static FP8 quant | 2.33 us | 1.68 us |
| add + Gemma RMSNorm + NVFP4 quant | 3.22 us | 1.73 us |

For Qwen3.8-27B-NVFP4 bs1 decode this removes 64 FP4-quant + 16 FP8-quant kernels per step, an expected ~0.1 ms of an ~81 ms step, so it is a small win; the gain is larger relative to step time at low per-step GEMM cost. End-to-end decode A/B: **pending**, will be added.
