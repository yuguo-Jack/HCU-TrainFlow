# fix(openai): keep chat stream created timestamp stable

[Upstream PR](https://github.com/sgl-project/sglang/pull/43026) · state: closed · merged: True

## Original PR description

## Motivation

DeepSeek's Chat Completions contract states that every streaming chunk has [the same timestamp](https://api-docs.deepseek.com/api/create-chat-completion/). OpenAI likewise defines `created` as the time when the chat completion was created, and its [streaming example](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) reuses one value for the role, content, and finish chunks.

The [DeepSeek Provider Verifier](https://github.com/smg-project/deepseek-provider-verifier/blob/161fee64de1a59eb21e2c19563f0d64347a1fc78/src/deepseek_provider_verifier/protocols/chat.py#L227-L242) treats `(id, created, model)` as the streaming response identity and reports a response-envelope violation if any member changes. This exposed an SGLang behavior difference: Streaming Chat Completions currently recompute `created` while emitting chunks. A response that crosses a one-second boundary can therefore keep the same `id` and `model` while changing `created`.

SGLang calls `time.time()` while constructing the [role and finish chunks](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/serving_chat.py#L2088-L2140), as well as content, tool-call, extension, and usage chunks. This PR captures one response-level creation time and reuses it without adding a provider-specific mode.

## Minimal Reproduction

Start an SGLang server with any chat model, then request a stream long enough to cross a one-second boundary:

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 30000
```

```python
import json

import requests

payload = {
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [
        {"role": "user", "content": "Write a detailed 1,000-word explanation of radix trees."}
    ],
    "max_tokens": 1024,
    "stream": True,
    "stream_options": {"include_usage": True},
}

with requests.post(
    "http://127.0.0.1:30000/v1/chat/completions",
    json=payload,
    stream=True,
) as response:
    response.raise_for_status()
    chunks = [
        json.loads(line[6:])
        for line in response.iter_lines(decode_unicode=True)
        if line.startswith("data: {")
    ]

created = [chunk["created"] for chunk in chunks]
print(sorted(set(created)))
assert len(set(created)) == 1
```

Before this fix, a stream that crosses a second boundary prints more than one timestamp and fails the assertion. After this fix, every role, content, finish, extension, tool-call, and usage chunk carries the same response creation time.

## Modifications

- Capture `created` once when `_generate_chat_stream` starts.
- Pass that value through all content and tool-call helpers and reuse it for every response chunk.
- Add a focused CPU test whose mocked clock advances between calls and verifies that all parsed chunks keep the first timestamp.
- Extend existing tool-stream tests to verify that helper-generated chunks use the caller's response timestamp.

This does not change model execution, generated tokens, chunk ordering, usage placement, or provider-specific behavior.

## Compatibility and Merge Danger

- **Door:** Two-way; reverting restores per-chunk timestamp calculation.
- **Blast radius:** OpenAI-compatible streaming Chat Completions only.
- **Intentional behavior change:** Long streams now retain one response-level `created` value instead of changing at wall-clock second boundaries.
- **Preserved behavior:** Response IDs, model names, content, finish reasons, tool calls, extensions, usage, and chunk ordering are unchanged.
- **Canary:** Run one stream that crosses a second boundary with usage enabled and verify that every JSON chunk has exactly one distinct `created` value.
