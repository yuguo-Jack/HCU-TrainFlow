## Motivation

Part 1/5 of the DeepSeek-V4.1 CP>1 support series, split from the original combined PR [#45954](https://github.com/sgl-project/sglang/pull/45954).

`radix_tie_select` previously compared score keys only. When a tied cutoff bucket exceeds the remaining TopK slots, final atomic allocation can determine which candidates are retained. Equal indexer scores can refer to different KV positions, so different tied subsets can affect subsequent attention.

## Modifications

- Compare the existing score key first, then the inverse raw candidate index, using up to eight radix rounds. Smaller indices win only when score keys are equal.
- Update histogram/active-candidate bookkeeping and final-scatter conditions; retain early termination.
- Preserve score computation, candidate staging, and page mapping. Output order remains unspecified; the fix stabilizes membership for the same staged candidates.

For example, with `K=512`, 471 higher-scoring candidates leave 41 slots for 2048 staged equal-score candidates with indices `471..2518`. The new rule consistently retains `471..511` from that bucket. Score priority remains unchanged: `(9.0, index=1000)` still outranks `(8.0, index=1)`.

- QNan0513 · comment · 2026-11-01T11:18:49Z · [source](https://github.com/sgl-project/sglang/pull/46522#issuecomment-6557227141)

This fixes the remaining decode nondeterminism we see on Hopper in #46798.

**Why ties matter here.** DeepSeek-V4.1 index scores are bf16-rounded, so ties at the k-th score are routine. In one saved H20 decode row from layer 24, 63 positions share the 512th score and 15 of them are kept.

**Kernel level.** Replaying that row 100 times through `select_decode` (top-k v2, then sorted) gives 35 different index sets on main and 1 with this PR.

**End to end** on H20: DeepSeek-V4.1-Flash, TP8/EP8, this PR plus the SM90 mHC change from #46523. Prompts of 511, 8193, 9000, 16385 and 33000 tokens, 10 runs each, with and without `/flush_cache` between requests. Every run was bitwise identical. With only the mHC change, every length from 8000 tokens up still differs.

**Remaining case.** Rows with more than 2048 exactly-equal scores still vary, because the staged subset is taken in arrival order. On synthetic rows with thousands of zeros we saw 2 different sets in 50 runs. The top-k hunk of #41893 behaves the same, at 2–4 sets.

- QNan0513 · comment · 2026-11-01T16:17:20Z · [source](https://github.com/sgl-project/sglang/pull/46522#issuecomment-6560546528)

@DarkSharpness It is needed only for run-to-run determinism, not for accuracy: any subset of the tied scores is a valid top-k. On Hopper it is the last source of divergence we found. With only the SM90 mHC fix, identical greedy requests on H20 still decode differently from 8K tokens up, because `select_decode` keeps a different subset of the tied scores on each run.

**Cost of this PR**, measured on H20 per call under CUDA graph, main (e624174) → this PR.

DeepSeek-V4.1 decode shape (`select_decode`: k = 512, raw indices, 1M-wide buffer):
- No tie at the k-th score (random fp32 rows, a saved layer-20 decode row): −6% to +0.4%. The new early exit makes some rows faster, e.g. 6.25 → 5.87 µs at 32K.
- Ties at the k-th score (bf16-rounded rows, the saved layer-24 decode row): +1.2 to +2.0 µs (12% to 27%), e.g. 6.02 → 7.43 µs for the layer-24 row at batch 1. These rows go from 19 to 50 different index sets in 50 runs to 1.
- More than 2048 exactly-equal scores (about 300 positive scores, the rest 0): +2.0 to +3.2 µs, and the set still varies, 11 to 50 sets in 50 runs (more than the 2 we saw earlier on a different synthetic row).

DSA decode shape (`_topk_transform_v2_paged`: k = 2048, page size 64). DSA models (DeepSeek-V3.2, GLM-5) call the same kernel through `dsa_topk_backend`:
- No tie at the k-th score (random fp32 rows, also with half the scores exactly 0): −4% to +0.6%, e.g. 8.82 → 8.47 µs at batch 1 and 128K, 29.55 → 29.73 µs at batch 64 and 128K.
- Ties at the k-th score (bf16-rounded rows at 128K): +1.2 to +4.1 µs (4% to 20%), with 45 to 50 sets going to 1.
- More than 2048 exactly-equal scores (about 1000 positive scores, the rest 0): +2.0 µs (7% to 17%), still 27 to 50 sets.

So rows without an exact tie at the k-th score pay nothing. For DeepSeek-V4.1, a decode step at batch 1 and 8K context runs v2 six times, 8.8 µs per call in our profile. Even if every call hits ties, this PR adds about 12 µs to a 10.4 ms step, about 0.1%. That is an estimate; we have not measured this PR's speed end to end.

**Making it optional.** #47748 does this behind `SGLANG_ENABLE_DETERMINISTIC_SPARSE_TOPK`, off by default, and leaves the default kernels untouched. With the flag on, `topk_transform_paged_v2` and the other DSV4 top-k entry points go to DeepSelect's single-CTA kernel or an exact torch selection. That is deterministic on every row above, plateaus included, but slower per call. For the layer-24 row it takes 10.05 µs against 6.02 µs on main. The DSA paged path goes through `topk_transform_paged_v2` too, so the flag reroutes it as well, at 1.4 to 5.7 times v2's time (e.g. 8.82 → 44.75 µs at batch 1 and 128K); only the plateau rows get faster. For DeepSeek-V4.1 the flag costs 27 µs of GPU time per decode step (0.26%); TPOT at batch 1 and 8K goes from 8.10 to 8.11 ms.

So determinism does not require changing the default v2 path. If the default should stay exactly as it is, this PR's tie-break could instead be built only into the deterministic mode. There it would be much cheaper than DeepSelect, especially for DSA, though the plateau rows would still need another path.
