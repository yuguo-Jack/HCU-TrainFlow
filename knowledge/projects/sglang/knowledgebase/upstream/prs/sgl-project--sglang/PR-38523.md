# fix(gateway): replace, don't accumulate, when a worker URL is re-registered

[Upstream PR](https://github.com/sgl-project/sglang/pull/38523) · state: closed · merged: False

## Original PR description

Split out of #32322 to keep that PR to one file — this is an independent bug, reachable with no service discovery involved.

## Problem

`register()` upserts `workers` and `url_to_id`, which are keyed, but *appends* to `model_index`, `type_workers` and `connection_workers`. Registering a URL that is already known therefore leaves the previous worker in all three. `POST /workers` allows that outright, and a hostNetwork rollout produces it too, since the new pod inherits the node's IP.

Consequences, worst last:

- `model_index` holds `Arc<dyn Worker>` and is what `get_by_model` reads, so the old worker object stays **routable** while no longer being in `workers` — the health checker never visits it and its health is frozen. The URL also takes a double share of selection.
- `get_worker_distribution` takes a raw `len()`, so the duplicate inflates it and the `worker_pool_size` metric.
- The worker id is **reused** on re-registration, so an id left in the type bucket the worker was *first* filed under resolves through `workers` to the **replacement**: after a prefill pod is replaced by a decode pod at the same address, `get_by_type(Prefill)` returns the decode worker. `remove()` does not clean it up either, since it clears the buckets of whatever worker is current.

## Fix

Before indexing the new worker, remove the previous one from the secondary indexes — against *its own* model, type and connection mode, not the replacement's. `remove()` then needs no change. A replacement landing under a different model also rebuilds the ring of the model it left.

Four tests, each confirmed to fail against the append-only version. The removal case registers as Regular first on purpose: a dangling id is invisible to `get_by_type`, so the obvious spelling of that test passes vacuously.
