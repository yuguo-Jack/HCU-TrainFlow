# [sgl-kernel] Add SGLANG_KERNEL_DISABLE_FLASHINFER_NORM env var to force native norm ops

[Upstream PR](https://github.com/sgl-project/sglang/pull/30777) · state: closed · merged: False

## Original PR description

## Motivation

sgl-kernel's RMSNorm path delegates to `flashinfer.norm`, which goes through `cutlass-dsl`. cutlass-dsl 4.5.x is a CUDA 13 build; its `cuda_dialect_init_library_once` loads a CUDA 13 runtime, so it requires a CUDA 13 driver (≥ 580). On a host with an older driver (e.g. driver 535 / CUDA 12.8), FlashInfer is still **importable** but its norm kernels fail at runtime:

```
flashinfer.norm._rmsnorm_impl → rmsnorm_cute → nvidia_cutlass_dsl ... cuda_dialect_init_library_once
RuntimeError: Got Cuda Runtime Error: cudaErrorInsufficientDriver CUDA driver version is insufficient for CUDA runtime version
```

This crashes model forward at the very first RMSNorm. Switching `--attention-backend triton --sampling-backend pytorch` does **not** help, because RMSNorm is on the mandatory forward path and `sgl_kernel.rmsnorm`/`fused_add_rmsnorm` route through `flashinfer.norm` whenever FlashInfer imports successfully.

Today the only workaround is to uninstall `flashinfer-python`, but that breaks sglang's `sglang/srt/layers/sampler.py:28` which does `from flashinfer.sampling import ...` at module load — i.e. there is no way to reach the existing native fallback short of breaking the import graph.

## Modifications

Add an opt-in escape hatch `SGLANG_KERNEL_DISABLE_FLASHINFER_NORM` to `sgl-kernel/python/sgl_kernel/elementwise.py`. When set (true/1, case-insensitive), the four norm entry points (`rmsnorm`, `fused_add_rmsnorm`, `gemma_rmsnorm`, `gemma_fused_add_rmsnorm`) take their existing `_*_internal` native `torch.ops.sgl_kernel.*` path instead of `flashinfer.norm`. The native ops are C++/CUDA built against the sgl-kernel wheel's CUDA version (e.g. cu129) and have no cutlass-dsl / CUDA 13 driver dependency.

Conventions followed (per `.claude/skills/env-var-conventions/SKILL.md`):
- **Naming**: `SGLANG_KERNEL_*` prefix — `SGLANG_` matches the project convention, `KERNEL` namespaces the sgl-kernel subpackage. This matches the existing sgl-kernel precedent `SGLANG_KERNEL_API_LOGLEVEL` (`debug_utils.py`) and #30562's `SGLANG_KERNEL_ALLOW_MISSING_OPS`. `DISABLE_FOO` verb per Rule 4 (kill-switch).
- **Registration**: sgl-kernel has no `environ.py` and cannot import `sglang.srt.environ` (sglang depends on sgl-kernel, not the reverse), so the value is read with `os.environ` directly — consistent with `SGLANG_KERNEL_API_LOGLEVEL`. This is documented in a comment.
- **Parsing**: `.lower() in ("true", "1")`, matching `sglang.srt.utils.common.get_bool_env_var` semantics (so `=true` works, not just `=1`).

The default (unset) path is unchanged — FlashInfer is still used when available and working. Zero impact on the hot path.

## Accuracy Tests

No output change. The native `_*_internal` ops are the same RMSNorm math that already runs when FlashInfer is absent (the `else` branch was pre-existing). When the env var is unset, behavior is identical to before. When set, it routes to the same fallback that would trigger if FlashInfer were uninstalled, so results are identical to the no-FlashInfer build.

Verified on H20 (driver 535 / CUDA 12.8, sglang nightly 0.5.15.dev, sglang-kernel 0.4.4+cu129):
- `SGLANG_KERNEL_DISABLE_FLASHINFER_NORM=1` / `=true` / `=TRUE` → native `sgl_kernel.rmsnorm` runs successfully.
- unset / `=false` → `flashinfer.norm` path raises `cudaErrorInsufficientDriver` (confirms the env var gates the fallback correctly).
- End-to-end: `python -m sglang.launch_server --model-path Qwen3-8B --enable-flexkv --attention-backend triton --sampling-backend pytorch` with the env var set boots to "The server is fired up and ready to roll!" and serves requests (FlexKV host cache hits confirmed via `cached_tokens_details.host`).

## Speed Tests and Profiling

N/A. Opt-in escape hatch; no change to the default path. When unset, the FlashInfer path is taken exactly as before. When set, the native op is used — this is the same fallback that already exists for the no-FlashInfer build, not a new kernel.

## Notes

- This is a targeted robustness fix, not a replacement for the root cause. The deeper mismatch is that sglang's cu129 nightly depends on `flashinfer_python[cu13]==0.6.14` (needs a CUDA 13 driver) while cu129 torch runs on driver 525+; that packaging question is out of scope for this PR but the env var unblocks affected hosts.
- An alternative design (try/except around the FlashInfer call with auto-fallback on CUDA error) was considered; rejected in favor of an explicit env var for predictability and to avoid masking real errors on the hot path. Could be added later as an enhancement.
