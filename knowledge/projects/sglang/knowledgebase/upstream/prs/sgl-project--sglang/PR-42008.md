# [Feat] [AMD] diffusion: Enable residual_gate_add fast path on ROCm

## Motivation

On ROCm, the existing `residual_gate_add` Triton kernels embed NVIDIA PTX (`cvt.rn.bf16.f32` / `cvt.rn.f16.f32`, constraint `"=h"`). AMDGPU does not support the `h` register class, so LLVM aborts during compilation instead of raising a Python exception. The diffusion worker can therefore terminate during denoising before the eager fallback is reached.

<!-- Describe the purpose and goals of this pull request. -->

## Modifications

This PR adds a dedicated ROCm Triton fast path while preserving the existing CUDA implementation.

- CUDA keeps the existing JIT/custom-op path and NVIDIA PTX rounding helper, now named `_cuda_round16_f32`.
- ROCm uses a separate custom op and Triton kernels for flat and transposed layouts.
- The ROCm flat kernel also handles batched `[B, 1, D]` gates, including LTX-2's strided AdaLN views.
- ROCm BF16 rounding uses `round_bf16_to_fp32`.
- ROCm FP16 rounding uses opaque `v_cvt_f16_f32` inline assembly because a normal FP32 → FP16 → FP32 cast can be folded away by Triton.
- CUDA and ROCm use separate predicates and rounding helpers. Unsupported inputs continue to use the eager fallback.
- Existing residual-gate tests now dispatch to the appropriate backend, with a regression test ensuring HIP never enters the CUDA/PTX path.

## Accuracy Tests

On gfx1151, the ROCm path was compared against the eager reference with exact comparison for FP16 and BF16.

Coverage includes FP16/BF16/FP32, full/row-broadcast/per-token/batched gates, transposed layouts, storage offsets, graph/compile paths, and unsupported-input fallback.



## Speed Tests

gfx1151 (Radeon 8060S), ROCm 7.2.4, PyTorch 2.9.1, Triton 3.7.0.
Row-broadcast gate, wall-clock time per call:

| dtype | shape | eager | ROCm path | speedup |
|---|---|---:|---:|---:|
| bf16 | `[1, 4096, 3072]` | 560.6 µs | 333.6 µs | 1.68x |
| bf16 | `[1, 4202, 3072]` | 568.8 µs | 341.6 µs | 1.67x |
| fp16 | `[1, 4096, 3072]` | 563.5 µs | 330.5 µs | 1.71x |
| fp16 | `[1, 4202, 3072]` | 572.3 µs | 339.4 µs | 1.69x |

These measurements cover the row-broadcast path only; the transposed ROCm path has not been independently profiled on AMD, so no speedup is claimed for that layout.

- yichiche · comment · 2026-10-05T03:09:20Z · [source](https://github.com/sgl-project/sglang/pull/42008#issuecomment-5987417974)

Thanks for working on this. From the ROCm side, I think the optimization demonstrated here is still valuable even after #42391.

The current results show that the residual_gate_add operation does not fundamentally need to fall back to eager mode on HIP — the PTX-specific rounding can be replaced with a ROCm-compatible implementation while preserving bit-exact results, with a meaningful performance benefit (~1.7x at the kernel level and ~4% in Qwen-Image denoising on gfx1151).

That said, I think we should align with the dispatch structure introduced by #42391 rather than mixing CUDA/PTX and ROCm-specific logic into the same path.

My preference would be:

* Keep the existing CUDA/JIT CUDA path unchanged.
* Keep the current fallback as the safe default for unsupported backends/configurations.
* Add a dedicated ROCm Triton fast path for the supported HIP cases, with correctness tests against the eager implementation.
* Avoid making the CUDA implementation more complex solely to accommodate HIP.

This gives us a clean backend separation while still allowing ROCm to benefit from the optimization demonstrated in this PR.
