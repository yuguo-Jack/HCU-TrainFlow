# [Perf] diffusion: Serve image responses from in-memory encoded bytes

[Upstream PR](https://github.com/sgl-project/sglang/pull/45987) · state: closed · merged: True

## Original PR description

## Motivation

`/v1/images/generations` and `/v1/images/edits` spend avoidable time after the image is decoded:

1. **A disk round trip per image.** The output rank encodes the image into a file under the output directory, and the HTTP server then reads that file back to base64 it. With `--output-path ""` nothing is persisted, so the file goes to a per-request temp dir purely as a transport.
2. **A slow PNG encode.** PNG is deflated at zlib level 1 on the output rank, single-threaded. For a 1024x1024 image that is tens of milliseconds on the request's critical path, while level 0 produces the same pixels several times faster.

## Modifications

- `entrypoints/utils.py`: an image is encoded once, in memory (`_encode_image_frame`). `save_materialized_output` writes those bytes when saving and, with `return_image_bytes`, returns them even when nothing is written. `save_outputs` / `post_process_sample` collect them through `image_bytes_out`.
- PNG defaults to zlib level 0: same pixels, about 3x the bytes of level 1 on typical generations, several times faster to encode. An `output_compression` other than 75 still selects a level. JPEG and WebP go through the same imageio call into memory instead of into a file, and their bytes are unchanged.
- New sampling field `return_image_bytes` (default off, set by `/v1/images`). The output rank also encodes when `save_output` is off but the bytes are requested, and returns them in `OutputBatch.output_image_bytes`. The scheduler slices them per request when it splits a dynamic batch, and the API-side save path fills the same field.
- `image_api.py`: b64_json responses are built from `output_image_bytes`; no file is read back. A file is written only when the server persists outputs (`--output-path`, default `outputs/`) or uploads them to cloud storage, and the persisted file holds exactly the returned bytes. `file_path`, `/v1/images/{id}/content` and url responses are unchanged. GLM-Image's actual output size is read from the bytes.
- Docs: the `--async-output-save` scope now includes `return_image_bytes` requests, and the output-quality notes describe the PNG level.

Tradeoff: PNG responses and persisted PNG files are larger (1024x1024: Z-Image-Turbo RGB 1.60 → 3.15 MB, Qwen-Image-2.1 RGBA 1.83 → 4.20 MB; the b64_json body grows by 4/3 of that). Pass `output_compression` to trade encode time for size.

Tests (`test_image_response_bytes.py`):
- the returned PNG decodes to the source pixels exactly for 2-D grayscale, single-channel, RGB and RGBA frames, at the default and at explicit levels, and no file is written when `save_output` is off;
- a saved file holds exactly the returned bytes (PNG, JPEG, WebP), and JPEG/WebP bytes equal what the previous file writer produced;
- the worker returns one encoded image per output and writes the file only when saving; it encodes when either saving or returning bytes;
- a split dynamic batch keeps each request's bytes;
- both image endpoints answer b64_json from the returned bytes without a file, and request a file only when the server persists outputs.

## Accuracy Tests

Same request (seed 42, `output_format=png`, b64_json) against both arms:

- The returned PNGs decode to identical pixels for Z-Image-Turbo (RGB) and Qwen-Image-2.1 (RGBA).
- With the default `--output-path`, the persisted file is byte-identical to the response.
- With `--output-path ""`, no output file is written, `file_path` is null, and the pixels are still identical.

## Speed Tests and Profiling

Server benchmark, 2 interleaved rounds x 5 repeats, client e2e latency (median; min-max spread ≤ 6 ms in every run). Requests ask for PNG.

| case | GPUs | base (round 1 / 2) | this PR (round 1 / 2) |
|---|---|---|---|
| Z-Image-Turbo T2I 1024, TP2 | 2xH200 | 0.679 / 0.678 s | 0.640 / 0.641 s (−38 ms, −5.6%) |
| Qwen-Image-2.1 T2I 1024 | 1xH200 | 4.374 / 4.370 s | 4.331 / 4.333 s (−40 ms, −0.9%) |

The server-side stage sum is unchanged (Z-Image 0.50 s, Qwen-Image-2.1 4.22-4.23 s); the time comes out of the post-generation tail: 0.183 → 0.146 s and 0.154 → 0.115 s.
