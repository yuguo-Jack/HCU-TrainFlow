# [Perf] dp-attn: Keep MLP-sync gather on the CPU group under PP

[Upstream PR](https://github.com/sgl-project/sglang/pull/47575) · state: closed · merged: False

## Original PR description

## Motivation

With DP attention, every scheduler iteration runs an MLP-sync all-gather (`prepare_mlp_sync_batch_raw`) to exchange per-rank token counts, forward modes and CUDA-graph votes. The gather group is picked like this:

- overlap schedule on: CPU (gloo) group, unless `SGLANG_NCCL_ALL_GATHER_IN_OVERLAP_SCHEDULER_SYNC_BATCH=1`;
- overlap schedule off: device (NCCL) group, followed by a D2H read of the result.

The device group is the right choice for the plain non-overlap loop because the GPU is idle when the scheduler prepares the next batch. Pipeline parallelism always turns the overlap schedule off (`_pipeline_parallel_overlap_disable`), so PP falls into the device-group branch too. But the PP event loop schedules microbatch `i` while microbatches `i-1, i-2, ...` are still running on the GPU. The NCCL gather and its D2H copy are queued behind that in-flight work, so the scheduler blocks for roughly a whole stage forward before it can launch the next microbatch, which re-introduces the pipeline bubble PP microbatching is meant to hide.

## Modifications

- `prepare_mlp_sync_batch_raw` takes `pp_size` and only uses the device group for the non-overlap path when `pp_size == 1`. Under PP the gather stays on the CPU group, the same as with the overlap scheduler.
- `SGLANG_NCCL_ALL_GATHER_IN_OVERLAP_SCHEDULER_SYNC_BATCH=1` still forces the device group, so the old behavior stays available as an opt-in.
- `SchedulerDPAttnAdapter` and `sglang.benchmark.one_batch` pass `get_parallel().pp_size`.
- Unit test `TestMLPSyncGatherGroup` in `test/registered/unit/managers/scheduler_components/test_dp_attn.py` checks the selected group for (non-overlap, PP1) -> device, (non-overlap, PP2) -> CPU, (overlap, PP1) -> CPU, and (non-overlap, PP2, env opt-in) -> device. The PP2 case fails on main and passes with this change.

Non-PP deployments are unchanged.

## Accuracy Tests

No numerical change: the gathered values are identical, only the process group that carries them differs. The gloo path is the one already used by the overlap scheduler and is covered by `TestSyncRowExchangeGloo`.

`python -m pytest test/registered/unit/managers/scheduler_components/test_dp_attn.py`: 18 passed.

## Speed Tests and Profiling

Single node, 4 x B300, Qwen3-30B-A3B-Instruct-2507-FP8, `--tp-size 2 --pp-size 2 --dp-size 2 --enable-dp-attention --moe-runner-backend triton`, `sglang.benchmark.serving` with `random-ids`, fixed lengths. Both variants run this branch; the device-group baseline sets `SGLANG_NCCL_ALL_GATHER_IN_OVERLAP_SCHEDULER_SYNC_BATCH=1` (equivalent to main). Mean of 3 runs:

| Workload | Gather group | Output tok/s | Mean TTFT (ms) | Mean TPOT (ms) |
|---|---|---|---|---|
| in 1024 / out 256, 256 prompts, conc 64 | device (main) | 3696 | 287 | 16.22 |
| | CPU (this PR) | 3293 | 330 | 18.17 |
| in 4096 / out 64, 128 prompts, conc 32 | device (main) | 1254 | 391 | 19.54 |
| | CPU (this PR) | 1178 | 398 | 21.11 |

On this single-node, short-stage setup the CPU group is slower (-11% / -6% output throughput). Marking as draft while I profile where the time goes (gloo gather latency vs. the device-gather stall) and test a multi-node PP setup, where the stage forward is longer and the device-gather stall should dominate.
