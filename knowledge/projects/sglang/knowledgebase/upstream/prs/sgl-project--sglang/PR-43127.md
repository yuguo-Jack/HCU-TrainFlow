# [Perf] [AMD] kimi-k3: Fuse the MLA decode query and latent KV cache write

[Upstream PR](https://github.com/sgl-project/sglang/pull/43127) · state: open · merged: False

## Original PR description

## Motivation

- Kimi-K3's MLA applies no RoPE, yet on ROCm every absorbed decode and target-verify step still runs two separate launches before attention: it builds the query (`cat(q_nope, q_pe)`) and writes the latent KV cache (`kv_layers.layer(i).store(...)`).
- At AgentX decode batch sizes, those small launches add per-step latency to each of the 24 MLA layers.
- AITER's `fused_qk_rope_concat_and_cache_mla` does both in one launch. With one-row identity cos/sin tables and all-zero positions its RoPE step is a no-op, so the Q and cache bytes it writes match the split chain exactly.

## Modifications

- `sglang.kernels.ops.attention.mla_q_cache_aiter_hip` (op `attention.kimi_k3_mla_q_cache`): a fail-closed adapter for gfx950. `covered()` checks the contract and `run()` launches the op.
- `srt/models/kimi_k3_rocm_mla.KimiK3RocmMlaQCacheWriter`: installed on K3 MLA layers when the switch is set on ROCm. It uses the AITER HIP op on gfx950 and AITER's no-RoPE Triton kernel elsewhere, logging one warning on fallback.
- Memory: Q and the `k` placeholder are allocated per call and are the same size as the `cat` outputs they replace. The only persistent state is one shared int64 zero-position buffer (8 B per token).
- CUDA is unchanged.

| Env var | Default | Effect |
|---|---|---|
| `SGLANG_OPT_HIP_K3_MLA_Q_CACHE_FUSION` | `false` | Write the K3 MLA decode/verify query and latent KV cache in one launch |

| Condition | Path |
|---|---|
| AITER decode or target-verify, Triton decode; no DCP; KV scale 1 (K3 loads none) | Fused Q + cache write |
| gfx950 with the AITER HIP op, inputs inside its contract (BF16 or e4m3fn cache) | AITER HIP op |
| Otherwise, AITER Triton no-RoPE kernel available | AITER Triton kernel |
| Neither kernel available (old AITER, gfx1250) | Split chain, one warning |
| Triton target-verify (its extend kernel reads `k`) | Split chain |
| Non-unit KV scale (the split AITER write ignores it; the fused kernels divide by it) | Split chain |
| DCP, extend, other attention backends | Split chain |

## Accuracy Tests

- GSM8K: sgl-eval 0.1.3, 1,319 questions, `--load-preset-from-model-id moonshotai/Kimi-K3` (temperature 1.0, top_p 0.95, thinking on).
- With DSpark speculative decoding: block 3, AITER decode and target-verify, real acceptance, Kimi-K3 AgentX c4 shape, TP8, K3 integration build.

| | Switch off | Switch on |
|---|---:|---:|
| GSM8K | 97.35% (1 run) | 97.19%, 97.42%, 97.12% (avg 97.24%) |
| Mean accept length (max 4) | 3.14 | 3.18 |

- Without speculative decoding (earlier head): 97.12% off vs 97.50% on.
- Kernel and writer tests (`test/registered/kernels/ops/attention/test_mla_q_cache_aiter_hip.py`, MI355X): for BF16 and FP8 caches, Q and cache bytes are identical to the split chain, and a captured graph still replays correctly after a larger eager batch replaces the shared buffer.
- Gate tests (`test/registered/unit/models/test_rocm_mla_absorb_fusion_gate.py`, CPU): Triton verify, non-unit KV scale, other backends, DCP/extend, and a missing Triton fallback all keep the split chain.
- At the current head, these two files plus `test_kernels_namespace.py`: 150 passed on MI355X.

## Speed Tests and Profiling

- Setup: 8x MI355X, TP8, `Kimi-K3-Quark-MXFP4-AttnFP8`, K3 integration build. Random 8192 in / 1024 out, radix cache off, 4 x C prompts. Switch off and on alternated, 3 runs per side (spread <= 0.1 ms).

| Conc | TPOT off (ms) | TPOT on (ms) | Change |
|---:|---:|---:|---:|
| 4 | 15.66 | 15.26 | -2.6% |
| 16 | 24.02 | 23.58 | -1.8% |
| 64 | 46.30 | 45.98 | -0.7% |

- TTFT does not change (decode-only path).
- Profile: `aiter::fuse_qk_rope_concat_and_cache_mla_per_head_kernel` launches once per MLA layer (24) per decode step, replacing the `cat` and the KV-cache write.

@yuychang The NV base `base-a-test-cpu` shard fails on this PR's own test, `test/registered/unit/models/test_rocm_mla_absorb_fusion_gate.py` ([job log](https://github.com/sgl-project/sglang/actions/runs/40808276640/job/123260121488)). Rerunning won't fix it:

```
ERROR: test_fused_routes (TestKimiK3MlaQCacheWriterGate) (backend='aiter', verify=False)
  File ".../kimi_k3_rocm_mla.py", line 120, in write
  File ".../kimi_k3_rocm_mla.py", line 45, in get
  File ".../torch/cuda/graphs.py", line 92, in is_current_stream_capturing
torch.AcceleratorError: CUDA error: CUDA driver version is insufficient for CUDA runtime version
```

`_ZeroPositions.get()` calls `torch.cuda.is_current_stream_capturing()` even when the device is CPU. The test is registered with `register_cpu_ci`, and the CPU runner has no usable CUDA driver, so the call fails there. One possible fix is to check the device type first:

```diff
-            if torch.cuda.is_current_stream_capturing():
+            if device.type == "cuda" and torch.cuda.is_current_stream_capturing():
```

(ROCm tensors also report `device.type == "cuda"`, so the graph-capture guard still applies on MI35x.) I haven't run the CPU test locally with this change, so please double-check that nothing else in the CPU path touches CUDA.
