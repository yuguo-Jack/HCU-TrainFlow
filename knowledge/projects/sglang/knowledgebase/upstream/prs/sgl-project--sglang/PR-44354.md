# [Feat] lora: Add merge and unmerge endpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/44354) · state: open · merged: False

## Original PR description

## Motivation

Adding merge/unmerge feature would be helpful to dynamically switch between multi lora and base model inference depending on per-adapter batch size imbalance for example as is done in [here ](https://www.usenix.org/conference/osdi24/presentation/wu-bingyang)

## Modifications

- Add `--enable-lora-merge`, `POST /merge_lora_weights` with `{"lora_name":"adapter"}`, `POST /unmerge_lora_weights`, and synchronous/asynchronous Python engine methods. `/model_info` reports the merged adapter.
- Drain admitted requests with the existing model-update lock. Keep the same `lora_path` while merged; reject base-model and other-adapter requests until unmerge.
- Apply FP32 dense updates from the existing tensor-parallel LoRA buffers. Keep original affected weights on GPU and restore them exactly on unmerge. Roll back a failed merge across TP ranks.
- Capture a decode graph without LoRA kernels at startup. Switch graph variants without recapture; merged prefill runs eagerly. Flush prefix/recurrent state at each transition because merged low-precision arithmetic differs from unmerged LoRA arithmetic.
- Reject incompatible execution modes and weight changes while merged. Add API, arithmetic, cancellation, rollback, and restoration tests and usage documentation.

Initial scope: adapters for fused qkv/mlp projections. Currently expert layer adapters unsupported, as current implementation maintains a separate copy of each adapter tensor for unmerge (memory footprint could become high for expert adapers). 

## Accuracy Tests

On H100 80 GB GPUs, BF16, FA3 attention, with two nonzero synthetic adapters (rank 8, alpha 16, all Q/K/V/O and gate/up/down projections; server maximum rank 16):

- Qwen3-4B, TP=1 with CSGMV and TP=2 with Triton: passed. For both adapters in both configurations, online merge and an independently PEFT-merged checkpoint loaded into a fresh SGLang server produced identical input-token log probabilities on the test prompt (mean/max absolute difference 0).
- Three merge/unmerge cycles per configuration restored base-model and unmerged-adapter input log probabilities exactly, and restored base-model output token IDs exactly. The test also covers unmerge during active generation, idempotent transitions, rejection of incompatible requests/unload, and reloading an adapter after unmerge.
- Qwen3-0.6B, TP=1 with Triton and full prefill graphs: passed, including exact input-logprob agreement with both offline merged checkpoints.
- CPU regression suite: 99 tests and 47 subtests passed, including merge arithmetic at a loaded rank smaller than buffer capacity, exact repeated restoration, rollback after a partial merge or another TP rank's failure, and request draining through client cancellation.
- All applicable repository pre-commit hooks passed.
- The final Qwen3-4B runs also matched all 32 greedy output token IDs exactly against both offline checkpoints at TP=1 and TP=2.
- Upstream lint and title checks passed. Upstream GPU CI is blocked by the draft-PR gate (`PR is draft. Blocking CI.`); the results above were run independently on Modal.

Reproduce the GPU tests:

```bash
SGLANG_LORA_MERGE_MODEL=Qwen/Qwen3-4B SGLANG_LORA_MERGE_BACKEND=csgmv \
  python test/registered/lora/test_lora_merge.py
SGLANG_LORA_MERGE_MODEL=Qwen/Qwen3-4B SGLANG_LORA_MERGE_TP=2 \
  python test/registered/lora/test_lora_merge.py
SGLANG_LORA_MERGE_PREFILL=full python test/registered/lora/test_lora_merge.py
```


## Speed Tests and Profiling

Qwen3-4B, batch 8, 98 prompt tokens/request, 128 output tokens/request, `ignore_eos=True`, decode CUDA graphs, eager prefill. Two independent server runs per configuration, each with one warmup and three timed trials per mode (six measurements per mode total); prefix cache flushed before each trial. Values below are pooled median HTTP batch completion times, excluding merge/unmerge.

| Configuration | Unmerged | Merged | Batch-time reduction | Output throughput ratio |
|---|---:|---:|---:|---:|
| 1 H100, CSGMV | 905.2 ms | 580.6 ms | 35.9% | 1.56x |
| 2 H100s, Triton, TP=2 | 671.7 ms | 434.1 ms | 35.4% | 1.55x |


Transition timings include HTTP/control overhead and exclude request draining unless stated:

- TP=1: first merge 169.0–184.2 ms; later merges median 89.5 ms (range 77.6–278.2 ms); idle unmerge 9.3–10.9 ms. Unmerge during an active 128-token generation took 523.0–529.6 ms, including its drain.
- TP=2: first merge 210.7–219.0 ms; later merges median 115.5 ms (range 70.7–164.1 ms); idle unmerge 8.7–9.4 ms. Unmerge during an active 128-token generation took 373.6–377.2 ms, including its drain.

These are short, homogeneous inference measurements, not an end-to-end RL throughput result. A pool must account for request draining, lost prefix state, and the extra weight-copy memory before choosing to merge. No profiler trace was collected.
