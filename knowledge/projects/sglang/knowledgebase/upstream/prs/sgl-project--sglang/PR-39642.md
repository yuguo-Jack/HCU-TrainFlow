# [Perf][Logprob] Remove per-request CUDA syncs from token-id logprob path

[Upstream PR](https://github.com/sgl-project/sglang/pull/39642) · state: closed · merged: False

## Original PR description

## Motivation

Workloads that request `token_ids_logprob` — e.g. scoring / classification, where every request asks for the logprob of a small fixed set of token ids like Yes/No — hit two sources of avoidable device→host synchronization on every single batch. Neither is needed: in both cases the data that forces the sync is already available on the host.

At high concurrency these dominate, because the second one scales with batch size: it costs one sync *per sequence*.

## Modifications

### 1. `get_token_ids_logprobs_batch_optimized()` — 4 syncs → 0

`python/sglang/srt/layers/logprob_processor.py`

The per-request token counts come from a Python `List[List[int]]`, so they are already on the host. The function pushed them to the device and then repeatedly pulled derived values back:

| Line | Sync |
|---|---|
| `token_lengths = torch.tensor([len(t or []) for t in ...], device=device)` | H2D for data needed on the host |
| `total_tokens = int(token_lengths.sum().item())` | D2H |
| `repeat_interleave(arange(batch_size, device=device), token_lengths)` | a device-resident count tensor forces a sync to materialize the output buffer size |
| `split_with_sizes(gathered, token_lengths.tolist(), dim=0)` | D2H |

Now the lengths stay a Python list: `total_tokens` is `sum(lengths)`, `row_indices` is built on CPU and transferred once, and `split_with_sizes` receives the list directly.

`col_indices` is still constructed directly on device — the `torch.tensor(list).to(device, non_blocking=True)` form is no better here, since the host tensor is pageable and the H2D copy is synchronous either way.

### 2. `next_token_token_ids_logprobs_val` — N syncs → 1

`python/sglang/srt/managers/scheduler_components/batch_result_processor.py`, `python/sglang/srt/managers/utils.py`

Both the prefill and decode paths converted the per-sequence logprob tensors with a per-tensor `.tolist()` list comprehension:

```python
logits_output.next_token_token_ids_logprobs_val = [
    v.tolist() for v in logits_output.next_token_token_ids_logprobs_val
]
```

That is one D2H sync per sequence — N syncs at batch size N.

New `batch_convert_tensors_to_lists()` in `managers/utils.py` does `torch.cat` → a single `.tolist()` → split the flat result back into per-tensor lists. It is a passthrough when the input is empty or the first element is not a tensor, so the PP path that pre-converts these values via `_async_d2h` is unaffected.

## Correctness

The gather math, tensor shapes, and split semantics are unchanged — outputs are bit-identical. This is purely a change in *where* the index bookkeeping happens.

## Accuracy Tests

No accuracy impact is expected or possible: the same values are gathered and split into the same per-request groupings; only the host/device placement of the index arithmetic changed.

Differential test of the rewritten `get_token_ids_logprobs_batch_optimized` against the original implementation, asserting exact tensor equality on values and equality on indices, over:

- the docstring example `[[1, 3], [2], [0, 2, 4]]`
- all-empty `[[], [], []]`
- a `None` entry mixed with populated and empty entries
- a single request
- duplicate token ids within one request, plus a `None` entry

All cases identical.

`batch_convert_tensors_to_lists` checked against the per-tensor `.tolist()` baseline including a zero-length tensor in the middle, plus the empty-input and already-converted passthrough paths.

## Benchmarking and Profiling

From the original internal report of change (2), HTTP scoring, RPS=40, item_count=50, concurrency=16: 2825 requests in 60 s, 2342 items/sec, P99 442 ms.

The win scales with batch size and with how many requests carry `token_ids_logprob`; workloads that never set it are unaffected (the guarded blocks are skipped entirely).
