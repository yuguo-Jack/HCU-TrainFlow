# [Feat] [NVIDIA] dsv4.1: [1/N] Add packed FP4 Main KV storage for Hopper.

## Motivation

This PR implements part of https://github.com/sgl-project/sglang/issues/38902; rebase from https://github.com/sgl-project/sglang/pull/39810.

DeepSeek-V4.1 C1/C2 compressed latents already undergo block-16 E2M1 fake quantization, but the Hopper path requantizes those values into the legacy FlashMLA FP8 cache. Each compressed slot therefore occupies 585 physical bytes at the default page geometry.

This PR adds the versioned packed Main-KV storage foundation requested in #38902. Persisting the noPE E2M1 codes and E4M3 scales, with the RoPE tail stored as BF16, reduces Main-KV storage to 384 bytes per slot. A follow-up PR adds the SM90 attention consumer.

<!-- Describe the purpose and goals of this pull request. -->

## Modifications


- Add `DSV41_MAIN_KV_E2M1_BLOCK16_ROPE_BF16_V1`, explicit layout specifications, and typed views over contiguous `uint8` pages.
- Add dedicated ratio-1/ratio-2 Main-KV pools with a page-level structure-of-arrays layout: 224 bytes of packed E2M1 payload, 32 scale bytes, and 128 bytes of BF16 RoPE per slot. The scale row contains 28 E4M3 scales and four reserved zero bytes.
- Add CPU pack/unpack references and an NVIDIA SM90 software E2M1 writer. Preserve round-to-nearest-even conversion, nibble ordering, and the existing RoPE fake-quantization semantics.
- Route the low-ratio producer's final storage through the packed writer.
- Share storage-layout resolution between pool construction and capacity estimation, and account for physical page padding.
- Reserve `--dsv41-main-kv-layout` and `--dsv41-main-kv-consumer`. Keep `auto` on the existing layout and reject packed runtime configurations until a consumer is available.
- Reject legacy buffer access and PD transfer descriptors for packed Main KV, so callers must use the typed API.

Could we preserve the uniform-FP8 accounting for the TRT-LLM backend here?

`select_dsv4_kv_layout()` returns `KVLayout.V4` for TRT-LLM, but the actual `DeepSeekV4UniformFP8KVPool` stores 512 bytes per slot without FlashMLA scales or page padding. With a full page size of 256, the new helper charges 585 bytes per slot for both C1 and C2.

I reproduced this difference using the actual selector and allocator methods on CPU. It overestimates this component by 73 bytes per slot and reduces usable KV capacity even with the default `main_kv_layout=auto`. A TRT-LLM sizing regression test would help cover this.

Thanks. Fixed. 
TRT-LLM now keeps the uniform-FP8 accounting for C1/C2: it charges `self.kv_bytes` (512 bytes per slot) instead of applying the FlashMLA V4 page stride (585 bytes per slot). I preserved the existing TRT-LLM sizing test unchanged and added a separate regression test covering both C1 and C2 using the actual layout selector and `DeepSeekV4UniformFP8KVPool.get_bytes_per_token()`.
