# [Fix] openai: Report server context length in /tokenize max_model_len

[Upstream PR](https://github.com/sgl-project/sglang/pull/47275) · state: open · merged: False

## Original PR description

## Motivation

Fixes #41748.

`/tokenize` (and `/v1/tokenize`) reported `max_model_len` from the
tokenizer's `model_max_length`, not from the limit the server actually
enforces. For Qwen/Qwen3-0.6B the tokenizer says 131072 while a server
running with `context_len` 40960 rejects any prompt at or above 40960
with a 400, so a client budgeting prompts against `/tokenize` was told
131072 tokens fit and then failed for prompts between 40961 and 131072
tokens.

This also disagreed with `/v1/models`, which already reports
`model_config.context_len` as `max_model_len`.

## Modifications

- `python/sglang/srt/entrypoints/openai/serving_tokenize.py`:
  `OpenAIServingTokenize._handle_non_streaming_request` now reports
  `model_config.context_len` as `max_model_len`. This covers both the
  `/v1/tokenize` and `/tokenize` routes, which share this handler. The
  old fallback for absurd (out-of-int64-range) tokenizer values is gone
  with the tokenizer-derived value itself; tokenization behavior is
  unchanged, only the reported limit.
- `test/registered/unit/entrypoints/openai/test_serving_tokenize.py`:
  added `test_max_model_len_is_server_context_len`, covering a text
  prompt, a batched prompt, and chat messages with a tokenizer whose
  `model_max_length` (131072) exceeds the server's `context_len`
  (4096 in the mock). A prior PR for this issue (#41785) was closed by
  automation for inactivity, not on merit; this re-applies its approach
  on current main.

## Tests

- The new regression test lives in the existing CPU unit test file
  `test/registered/unit/entrypoints/openai/test_serving_tokenize.py`.
  It could not be executed in this environment (no torch/sglang
  install here), so it needs CI.
- Verified without a GPU here via a stub harness that executes the real
  `_handle_non_streaming_request` with a fake tokenizer
  (`model_max_length=131072`) and a fake model config
  (`context_len=4096`): text and batched prompts return
  `max_model_len=4096` with unchanged token ids/counts. The tokenizer
  behavior the test relies on (setting `model_max_length`, `<bos>`
  post-processing) was confirmed against real `transformers`/
  `tokenizers`.
- `ruff check --select F401,F821,F823,UP037`, `ruff format --check`,
  `python3 -m py_compile`, and `git diff --check` all pass on both
  touched files. No existing test contradicts the change: the only
  other `max_model_len` assertion in the tree covers `/v1/models`,
  which is untouched.
