# [Spec][Ngram] Seed the ngram corpus with each request's rendered tool calls

[Upstream PR](https://github.com/sgl-project/sglang/pull/42313) · state: open · merged: False

## Original PR description

## Motivation

Part of #21052, not on the list, I proposed it in the thread.

NGRAM drafts from what is already in the corpus: tokens that earlier requests produced, plus an external corpus if you loaded one. A tool call's syntax is not in there until some request has already produced it.

The prompt has the tool schema as JSON, while the model outputs the actual tool call syntax from its chat template, for example `<tool_call>\n{"name": ...` for Qwen and Hermes. Those are different token sequences. So the first call to each tool on a server still decodes that structure one token at a time, and on a single-user box every call is a first call.

Agentic use is a pretty large share of how these models are served now, and agent loops are dominated by tool calls. A harness might expose tens of tools and most of them only get called once per session. I've been getting deep into speculative decoding at work and this is the gap I kept running into.

The idea is pretty simple:

Render the conversation normally, then render it again with an example assistant tool call appended. The difference between those two renders is the assistant turn the model is about to generate, already in that model's own chat template and its own tokens. Put that into the corpus before the request's first draft.

Now instead of decoding the structural part of the tool call one token at a time, the model verifies a bunch of it in one step. The actual argument values are still generated by the model, this only seeds the syntax around them.

Nothing is forced. If a seed is wrong it just does not match, so the output is identical whether this is on or off, right!

This is the same idea I posted for llama.cpp (ggml-org/llama.cpp#29405) and opened for vLLM (vllm-project/vllm#59712). SGLang's shared corpus makes the port smaller than both: no new algorithm, just seeds.

## Modifications

- `sampling/sampling_params.py`: a `__sglang_ngram_corpus_seeds` key on `custom_params`, with `get_/set_request_ngram_corpus_seeds()` next to the reasoning-terminator helpers they copy. It is a flat int list with a `-1` separator, since nested lists are not a `CustomParamValue`, capped at 4096 tokens and checked in `verify()`.
- `speculative/ngram_worker.py`: a module-level `_collect_corpus_seeds()` next to `_derive_tree_links` returns the seeds of requests that have not been seeded yet. The worker `batch_put`s them before `synchronize()` in `_prepare_draft_tokens`, and forgets rids with the existing departed-rid bookkeeping. They go into the online trie, not an external SAM: the SAM path is an async bulk loader with its own budget, the trie insert is the per-step mechanism that is already there.
- `entrypoints/openai/ngram_corpus_seeding.py` + `serving_chat.py`: `render_tool_call_seeds()`, one flag computed at startup (`speculative_algorithm == NGRAM`), rendered on the plain Jinja path right after the prompt, attached next to `set_request_reasoning_end_token_ids`. Skipped for `tool_choice="none"`, `continue_final_message`, and the custom-encoder paths.
- Tests under `test/registered/unit/`: transport round trip through msgpack, validation and the `verify()` path (`sampling/test_sampling_params.py`), seed-once-per-request bookkeeping (`spec/test_ngram_worker.py`), short seeds drafted from their prefix (`spec/test_ngram_corpus.py`), the renderer and the shared cap (`entrypoints/openai/test_ngram_corpus_seeding.py`), serving transport (`entrypoints/openai/test_serving_chat.py`).
- Two lines in the Ngram section of `docs/docs/advanced_features/speculative_decoding.mdx`.

## Accuracy Tests

Output is identical with and without seeding, verification is untouched. Both servers return `get_weather({"city": "Paris"})` (20 completion tokens) and `get_time({"tz": "Asia/Tokyo"})` (23 completion tokens), parsed by the `qwen25` tool-call parser, greedy.

## Speed Tests and Profiling

`Qwen/Qwen3-0.6B`, `--speculative-algorithm NGRAM --speculative-num-draft-tokens 12`, greedy, two tools, thinking off, one request to the first tool and one to the second. `/flush_cache` before every request, so the corpus is empty each time. This is the cold case, nothing earlier on the server has produced the tool syntax. `main` vs this branch in the same venv, RTX 5080.

| request calls | seeding | verify steps | accept length | correct drafts / proposed | completion tokens |
|---|---|---:|---:|---:|---:|
| `get_weather` (1st tool) | off (main) | 18 | 1.11 | 1 / 198 | 20 |
| `get_weather` (1st tool) | on | **4** | **5.00** | 17 / 44 | 20 |
| `get_time` (2nd tool) | off (main) | 21 | 1.10 | 1 / 231 | 23 |
| `get_time` (2nd tool) | on | **7** | **3.29** | 17 / 77 | 23 |

(`spec_accept_length`, `spec_verify_ct`, `spec_num_correct_drafts`, `spec_num_proposed_drafts` from `meta_info` with `return_meta_info=true`.)

Without seeding the corpus has nothing for a first call, so NGRAM verifies 11 empty draft slots per step and accepts basically one token per step. With seeding the first tool's call decodes in 4 steps instead of 18. The second tool needs 7: its seed shares `{"name": "` with the first tool's, and the tree spends a step there before it is on the right branch.

Cost: one template render per tool, once per request, on the CPU, and only on an NGRAM server. Seeds share the corpus with everything else, so they are subject to the same capacity and eviction.
