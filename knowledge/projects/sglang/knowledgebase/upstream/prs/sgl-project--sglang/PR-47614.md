# [Fix] PP: record received proxy tensors on the forward stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/47614) · state: closed · merged: True

## Original PR description

## Motivation

Fixes #47613. With `--pp-async-batch-depth > pp_size / 2`, the PD decode loop returns runs of token 0 for many requests (Kimi-K3 PP2 × TP4 depth 2: 51–98 of 192).

A downstream stage gets its proxy tensors from `recv_tensor_dict`, which allocates them on another stream; the forward stream reads them later. `event_loop_pp_disagg_decode` drops the previous reference before posting the next recv. When enough forwards are queued, the allocator gives the next recv the same block and it overwrites data a queued forward has not read yet. Checksums taken right after the recv and right before the forward differ in 76 and 378 of ~7500 comparisons on two runs; with this change they never differ.

## Modifications

- `_pp_launch_batch`: before `run_batch`, call `record_stream(self.forward_stream)` on each non-CPU tensor in `pp_proxy_tensors`. Every PP event loop goes through `_pp_launch_batch`, so they share this fix location; runtime validation did not exercise every loop configuration; the first stage passes `None` and is unchanged.
- Existing idle-counter test: make the mocked proxy receive return `None` for the simulated rank-zero scheduler, matching the real receive path. A bare `Mock()` previously reached the new tensor iteration and caused a fixture `TypeError`.

- The earlier DCP CI fixture correction from mickqian’s [#47736](https://github.com/sgl-project/sglang/pull/47736), source commit `be43d568ca8115e173bd4b9f5d106a3060ae1f8b`, is now included in main and is no longer part of this PR's cumulative diff.

## Applicability to main

The lifetime-critical logic is the same in `release/v0.5.22` and main at `2f6e7f347526034a173424cad0e7a72a5fb61ad2`: the disaggregated decode loop clears `pp_proxy_tensors` before the next receive; `_pp_recv_proxy_tensors` wraps the received tensors without recording the forward stream; and `_pp_launch_batch` submits `run_batch` on the forward stream without recording those inputs. Main is therefore expected to be affected by the same allocator-lifetime race based on source comparison. The B300 runtime reproduction and fix validation were completed on v0.5.22; that B300 reproduction was not separately repeated on main. Upstream CPU and PP integration results are listed below. This comparison concerns the bug-relevant lifetime logic, not byte-for-byte identity of the entire scheduler file.
