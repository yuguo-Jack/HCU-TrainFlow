## Motivation

<!-- Describe the purpose and goals of this pull request. -->

SGLang's Mooncake HiCache backend currently relies on Mooncake's default
replica placement. It does not expose request-level controls for memory or
descriptor-based DFS replicas, so deployments cannot request additional memory
replicas or evaluate Mooncake's DFS replica path through the standard HiCache
configuration.

This PR exposes Mooncake replica placement through the HiCache backend while
preserving the existing default behavior.

## Modifications

<!-- Detail the changes made in this pull request. -->

- Add `replica_num` and `dfs_replica_num` to
  `--hicache-storage-backend-extra-config`, with defaults of `1` and `0`.
- Create a request-scoped `ReplicateConfig` for standard and multi-buffer
  writes, and compose it with the existing `group_ids` setting.
- Validate replica counts and reject Mooncake versions that do not expose the
  requested configuration fields.
- Fail fast when embedded DFS mode is missing SSD offload, the distributed
  storage backend descriptor, or an absolute storage path.
- Keep standalone Dummy Client mode compatible with replica configuration
  owned by the external Real Client.
- Document embedded and standalone DFS setup and the current experimental
  limitations.
- Add unit coverage for validation, compatibility, request isolation, group
  semantics, and multi-buffer writes.

The default configuration continues to use the existing three-argument
`batch_put_from` path.

Thanks for this PR — it's exactly the integration needed now that Mooncake merged DFS-only replica placement ([kvcache-ai/Mooncake#4637](https://github.com/kvcache-ai/Mooncake/pull/4637)).

I validated the DFS-only configuration (`replica_num=0, dfs_replica_num=1`, with this PR's extra-config) on top of its snapshot (`1cbab10`). Sharing the measurements plus three local patches it took to make DFS-only work, in case they're useful for review.

### Setup

Single node with 8× NVIDIA H100 80GB, SGLang v0.5.21 image, Mooncake #4637 snapshot (source-built wheel), Qwen3.5-397B-FP8 TP8, multiturn cache-reuse workload — 40 concurrent clients, 10 rounds each where every client re-sends its own ~77K-token prompt with a new 5K-token sub-question per round (so rounds 1+ exercise the L2/L3 hit path), Poisson arrivals at rate 0.8, 1K-token outputs. 3 reps with full cold restart between reps (L1+L2+L3 all cleared). L3 = Mooncake POSIX DFS adapter, 64 × 10 GB shards on a local NVMe SSD, zero memory segments mounted.

### Finding: `DEFAULT_LOCAL_BUFFER_SIZE = 16 MB` starves DFS reads

DFS/DISK replica reads stage through the client buffer allocator (`real_client.cpp` — temp buffer → scatter to destination). With the hardcoded 16 MB default, read allocation failed 845,248 times over a 3-rep benchmark (512 KB page requests), so nearly all prefetches were dropped:

| `local_buffer_size` | read alloc failures | avg cache hit | mean TTFT |
|---|---|---|---|
| (no L3 — L2-only baseline) | n/a | 50.4% | 14.2 s |
| 16 MB (current default) | 845,248 / run | 56.6% | 13.9 s |
| 2 GB | ~14K / run | 78.5% | 2.35 s |
| 16 GB | 0 | **80.6%** | **2.34 s** |

The 16 MB default looks tuned for the zero-copy write path only ("Zero copy interface does not need local buffer"). Memory-replica reads don't use this staging path, which is likely why the PR's `replica_num=1, dfs_replica_num=1` E2E didn't surface it — it only bites when DFS/DISK replicas serve reads.

### Two categories of local changes I needed

**A. To make DFS-only work at all (correctness):**

1. **Allow `(replica_num=0, dfs_replica_num=1)`** — currently rejected by `replica_num must be at least 1`. Mooncake #4637 explicitly supports this placement now (it's the object's only copy; DFS eviction/removal deletes it).
2. **The startup warmup must use the placement config** — `MooncakeStore.warmup()` (a dummy-object liveness check at store init) currently does a default 2-arg `store.put`, which requests a memory replica and fails on zero-segment setups. It needs the same `ReplicateConfig` as normal writes. (Related: passing `None` as the third arg raises a pybind11 `TypeError` — the default path must keep the 2-arg form.)

**B. To make it fast (performance):**

3. **`local_buffer_size` as an extra-config option** instead of the hardcoded 16 MB — this is the finding above. Without it DFS-only *works* but reads are starved (hit 56.6%, effectively close to the L2-only baseline).

With all three: DFS-only runs end-to-end — 677K objects / 582 GB written with zero `insufficient space`, and hit rate 80.6% vs the 50.4% L2-only baseline (+30.2 pp from the DFS tier once reads aren't starved).

One operational note: with zero memory segments, the master's `/get_all_segments` returns an empty body, so `check_server` never succeeds — `check_server: false` plus warmup-based readiness works.

Of these, (B) and the `None` TypeError fix are placement-independent. The buffer-size issue in particular applies to any DISK/DFS replica read staged through the client buffer allocator — not just this PR's placement — so it may be worth fixing even outside this PR's scope. @huangtingwei9988 would a small standalone PR for `local_buffer_size` exposure (plus the warmup `None` fix) against main make sense here, or would you prefer it folded into this PR? And if you're short on cycles, glad to take over the remaining work here.

### Results on this head (dsrh100-021, 3-rep)

| Metric | DFS-only (this head) | L2-only (no L3) |
|---|---|---|
| avg cache hit | **85.8% ± 0.5** | 50.4% |
| mean TTFT | **2.36s ± 0.16** | 14.2s |
| TTFT p90 / p99 | 6.77s / 18.6s | 42.5s / 81.8s |
| read alloc failures | 0 across all reps | n/a |
| request success | 400 / 400 per rep, all 30/30 rounds | — |
| ITL p99 | 317.7 ms | — |

L2-only is the no-L3 baseline for the same workload and cold-restart contract — the DFS tier contributes +35.4 pp of cache hit and a 6× mean-TTFT improvement, with decode unaffected (ITL p99 unchanged).

The read path is heavily exercised, not just spot-checked: master key count grows 8 → ~821K over a rep, prefetch reports pages loaded (not just matched), and per-rep I/O volume is **~1 TB written / ~1.7 TB read** (page counters × 64-token pages × ~16 KB/token).

Thanks for folding in the changes so quickly — the GB-string parsing and `setup_dummy` propagation are nice touches beyond my local patch, and nice to see this connect to your Mooncake-side [DFS replica POSIX backend](https://github.com/kvcache-ai/Mooncake/pull/2683) as well.

I also have a 3FS (hf3fs) comparison from two separate 3-rep sessions on the same node — DFS-only came out ahead on TTFT in both:

| Backend | hit | mean TTFT |
|---|---|---|
| **DFS-only (this head, 10-23)** | 85.8% ± 0.5 | **2.36s ± 0.16** |
| 3FS (10-23, same day) | 78.8% ± 1.3 | 12.17s ± 1.08 |
| 3FS (10-16, separate cluster build) | 87.1% ± 0.5 | 5.03s |

Across both sessions, TTFT favored DFS-only — even when 3FS hit a higher cache rate. That's unexpected for us since the DFS path is POSIX-based while 3FS uses USRBIO, but both sessions are internally consistent (3 reps each).
