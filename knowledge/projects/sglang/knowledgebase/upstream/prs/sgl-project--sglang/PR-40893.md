# [Fix] spec: Support a reduced draft vocabulary in rejection sampling

[Upstream PR](https://github.com/sgl-project/sglang/pull/40893) · state: open · merged: False

## Original PR description

## Motivation

`--speculative-use-rejection-sampling` with EAGLE3 and a reduced draft vocabulary (e.g. `draft_vocab_size=32000`, `target_vocab_size=128256`) currently refuses to start:

```
ValueError: --speculative-use-rejection-sampling requires the draft and target to
share one vocab, but the draft vocab (32000) != target vocab (128256).
```

The FIXME above that check says *"support reduced (hot) draft vocab by scattering draft probs into the target vocab via the d2t map before the sampling kernel"*:

https://github.com/sgl-project/sglang/blob/e33cd0c3a10474c7a0f6efeb69ce2cf4b7a55021/python/sglang/srt/speculative/eagle_worker_v2.py#L264-L278

This PR implements exactly that. Since #42297, `--speculative-use-block-verification` also turns rejection sampling on for EAGLE / EAGLE3, so an EAGLE3 draft with a reduced vocabulary hits this error under block verification without the rejection-sampling flag:

https://github.com/sgl-project/sglang/blob/e33cd0c3a10474c7a0f6efeb69ce2cf4b7a55021/python/sglang/srt/arg_groups/speculative_hook.py#L178-L198

### Why it matters for correctness

Without this, an EAGLE3 deployment with a reduced-vocab draft cannot use rejection sampling and runs the target-only tree verifier (`rejected_probs=zeros`), which never consumes the actual draft distribution `q`. How much rejection sampling gains over that verifier depends on the draft/target pair and on the entropy of the workload. We measured three internal pairs, each with a 32K hot-vocab EAGLE3 draft built on an MTP layer and run with 7 draft steps, at target T=1 / draft T=1 with top-k and top-p off, on 14 public benchmarks (gsm8k, math500, aime25, humaneval, mbpp, livecodebench, swe-bench, arena-hard, alpaca, mt-bench, translation, summarization, rag, qa), averaged over concurrency 1/4/8/16:

| draft | mean accept-length gain | per-benchmark range |
|---|---|---|
| cold-start draft, target A | +27% | +15% to +40% |
| draft warm-started from target A's MTP layer | +33% | +21% to +46% |
| draft warm-started from target B's MTP layer, on target B | +13% | +3% to +21% |

The gain tracks target entropy. On target A, per-token predictive entropy at T=1 runs from 0.23 nats (humaneval) to 1.17 nats (qa). The two lowest-entropy sets, humaneval and mbpp, gave the smallest gains in all three pairs (+3% to +24%), and open-ended chat (mt-bench, alpaca, qa) the largest. The Spearman correlation between a benchmark's entropy on target A and its gain is 0.57, 0.76 and 0.90 for the three pairs.

A test on a public pair in the comments ([Qwen3-30B-A3B with a 32K EAGLE3 draft, 3 draft steps](https://github.com/sgl-project/sglang/pull/40893#issuecomment-6608282634)) found the opposite sign: rejection sampling accepted about 4-5% fewer tokens than the target-only verifier there. A lower-entropy workload, a weaker draft (accept length about 1.7 there) and fewer draft steps each shrink the gain. So this flag is a correctness fix that lets the draft distribution count, not a guaranteed speedup.

A two-sample G-test on token-frequency histograms, with a second independent non-speculative launch as the noise floor, finds the new path indistinguishable from that floor, while the `rejected_probs=zeros` path is biased (pooled p = 3.2e-26).

**Where these numbers come from.** They were measured on an older internal fork, with a d2t scatter that is mathematically the same as this PR's but applied at each producer instead of once at the verify boundary. They show what rejection sampling with a scattered `q` does to acceptance and that it stays unbiased. The code in this PR has not been benchmarked end to end; the e2e test below is its first end-to-end check on main.

## Modifications

`spec_utils.py` - add `scatter_draft_probs_to_target_vocab()`:
- `index_copy_` the hot-vocab `q` into a target-vocab-width zero tensor. This is exact, not an approximation: the draft can only ever propose a hot token, so `q(x) = 0` off the hot set is the true proposal mass, and `relu(p - q)` keeps the full `p` there.
- Force fp32 so the eager and CUDA-graph paths hand the kernel the same dtype.
- No buffer reuse: the returned tensor outlives the call under overlap scheduling, so a cached buffer would alias across iterations.

`eagle_worker_v2.py`:
- Replace the FIXME `raise ValueError` with an info log.
- Add `_build_verify_draft_probs()`, which stacks the per-step `q` and scatters once at the kernel boundary rather than in each producer.
- Add `EagleDraftWorker.draft_probs_vocab_size`. Until the verify boundary `q` stays at the draft width, so every buffer that carries it between steps has to be that wide. The idle stub now uses it instead of the target vocab size.
- Under `SGLANG_ENABLE_ASYNC_ASSERT`, assert `q > 0` at every proposed token. A `q` scattered so that a proposed token lands off its support reads back as `q == 0`, which makes the `coin * q < p` accept test vacuously true: accept length pins to `num_steps` while the text silently degrades. Rows with no mass are skipped, because they are CUDA-graph filler: capture warms up on the zeroed `q` buffer, and replay zeroes padded rows. The gather is gated so it never runs in production.
- On a PD-disaggregation decode server, reject a reduced draft vocabulary under rejection sampling at startup. `pd_first_draft_proposal` builds a request's first `q` at the target width, which does not fit the draft-width carrier, so the alternative is a failure on the first request.
- Initialize `draft_probs_list = None` outside the rejection-sampling branch, since the new call sites would otherwise raise `NameError` when rejection sampling is off.

`eagle_draft_cuda_graph_runner.py` - size the decode graph's `draft_probs` input buffer by `draft_probs_vocab_size`, falling back to the model's vocab size for workers without it. Sized for the target vocabulary, capture fails on the first `torch.stack` and replay fails on `copy_`.

`arg_groups/speculative_hook.py` - `_should_auto_enable_hip_rejection_sampling` carried the same FIXME in its docstring ("rejection sampling still cannot consume a reduced / hot draft vocab"). Updated to reflect that the scatter now exists. The conservative behavior is kept: ROCm still does not auto-enable rejection sampling for EAGLE3 or for an EAGLE run with a token map, because this path has not been validated on ROCm. Passing the flag explicitly works.

`docs/docs/advanced_features/speculative_decoding.mdx` - `--speculative-use-rejection-sampling` had no row in the speculative parameter table. Added one: default `False`, the `--speculative-eagle-topk 1` requirement, reduced-vocabulary support and its PD-decode limitation, and the UNO incompatibility, each checked against the code. The Block verification section said the draft must produce a full target-vocabulary proposal distribution; it now says how a reduced-vocabulary EAGLE3 draft's distribution reaches the target vocabulary.

`test/registered/unit/spec/test_draft_probs_reduced_vocab.py` - CPU unit tests, registered on `base-a-test-cpu`. Seven cover the scatter: hot columns land on their target ids, non-hot mass is exactly zero, total mass preserved, output is fp32 for any input dtype, no buffer aliasing across calls, width satisfies the `eagle_utils` guard, and a 400K-sample Monte Carlo showing chain rejection sampling with a truncated `q` reproduces `p` (max deviation within 4 standard errors). Two cover the assert: CUDA-graph filler rows pass, and a proposed token without mass fires.

`test/registered/e2e/speculative/test_eagle3_reject_sampling_reduced_vocab.py` - Llama-3.1-8B with its 32000-token EAGLE3 draft under `--speculative-use-rejection-sampling` and `SGLANG_ENABLE_ASYNC_ASSERT`, with overlap scheduling and CUDA graphs on. `SpecCorrectnessKit` covers startup (both graph variants are captured), greedy requests and one sampled request; `test_sampled_batch` sends nine sampled requests so the decode batch pads to the next captured size.

## Accuracy Tests

See the G-test result above, measured on the older fork described under "Where these numbers come from".

Local checks on this branch, CPU only: the 9 unit tests above pass, and 11 other CPU unit-test files that import the changed modules (162 tests, including `test_eagle_draft_cuda_graph_runner.py` and `test_pd_eagle_draft_proposal.py`) pass the same before and after the change.

GPU check on one 80 GB Hopper GPU (SM 9.0), with torch 2.14.1+cu130 and the `pyproject.toml` dependencies but without `flashinfer-cubin`: the 9 unit tests pass, and the new e2e test passes all 5 cases (accept length 2.04 in `test_acc_length` and 1.45 in `test_batch_generation`; `test_sampled_batch` passes), with every CUDA graph captured under `SGLANG_ENABLE_ASYNC_ASSERT`. On this PR's previous head (86d49be9a), which lacked the graph-buffer change, the same test fails at draft decode CUDA graph capture: `stack expects each tensor to be equal size, but got [64, 128256] at entry 0 and [64, 32000] at entry 1`. The run used an ungated copy of Llama-3.1-8B-Instruct and a 1800 s server launch timeout, because without the cubin package the first launch JIT-compiles kernels.

## Speed Tests and Profiling

The added work is a single `index_copy_` per verify step on a `(bs, num_steps, target_vocab)` tensor. This path was previously unreachable for reduced-vocab drafts, so there is no prior behavior to regress.

- esarafian · comment · 2026-11-04T05:30:35Z · [source](https://github.com/sgl-project/sglang/pull/40893#issuecomment-6623413262)

Following up on the evidence I posted earlier: here is an optional follow-up on top of this PR, in case you'd like to fold it in.

Branch: https://github.com/esarafian/sglang/commits/reduced-vocab-mapped-draft-q (4 commits directly on your current head `7c844fe`; they cherry-pick cleanly).

**What it does:** with a reduced draft vocabulary, `q` currently gets scattered into a zero-filled `(bs, steps, target_vocab)` FP32 tensor at the verify boundary. With this change, `chain_speculative_sampling_triton` reads the compact draft-width `q` through a target→draft index map instead. The map comes from `hot_token_id` / `d2t`, the kernel uses a `MAPPED_Q` constexpr path, and the result is the same FP32 value for every target id, with 0.0 outside the draft vocabulary. Tile size and reduction order are unchanged, so outputs are bitwise identical. NPU keeps the scatter.

**Verify step** (3 draft steps, 32K draft vocab, CUDA graph, cold L2), scatter + verify → mapped verify:
| target vocab, bs | RTX PRO 6000 | GB200 | H100 |
|---|---|---|---|
| 151,936, bs 64 | 313 → 119 µs (2.6×) | 275 → 113 µs (2.4×) | 462 → 110 µs (4.2×) |
| 151,936, bs 128 | 758 → 139 µs (5.5×) | 425 → 122 µs (3.5×) | 821 → 124 µs (6.6×) |
| 248,320, bs 128 | 1675 → 206 µs (8.1×) | 608 → 194 µs (3.1×) | 1038 → 201 µs (5.2×) |

Small batches are about equal; H100 at bs 1 with a 248K vocab is 4-8 µs slower. End-to-end serving with Qwen3-30B-A3B + EAGLE3 is unchanged within noise, because the forward pass dominates there.

**Tests:**
- new `test_reject_sampling_mapped_draft_q.py`: mapped vs scattered `q`, bitwise-equal predicts, accept index and lengths; token-wise and block verification; vocabs 17 to 248K, including NaN/inf/subnormal `q`;
- the existing `test_draft_probs_reduced_vocab.py` is extended;

Deterministic end-to-end runs vs this PR are token-identical apart from one request that also varies between base launches.
