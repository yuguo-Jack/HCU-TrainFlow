# [Feat] deepseek-v4.1: Add experimental resident-weight recovery and warm standby

[Upstream PR](https://github.com/sgl-project/sglang/pull/44232) · state: closed · merged: False

## Original PR description

Superseded by [#44241](https://github.com/sgl-project/sglang/pull/44241) after renaming the source branch to `dsv41-weight-cache-recovery`. The implementation commit is unchanged.

## Motivation

This PR extends the existing Weight Cache Daemon feature introduced in
[#27139](https://github.com/sgl-project/sglang/pull/27139) and described in
[Fast Engine Recovery: Sub-Second Engine Restart for SGLang via Weight Cache Daemon](https://www.lmsys.org/blog/2026-08-21-sglang-fast-recovery)
to DeepSeek V4.1, with Engram in either GPU or host memory.

The article addresses the repeated checkpoint I/O and weight processing paid on
every engine restart, which prolong service outages during worker failures and
rolling updates. It retains processed weights in a persistent daemon and lets
replacement engines reuse them through CUDA IPC. This PR builds on that feature
and addresses the gaps that prevent the same recovery path from working for V4.1.

**Why this extension is needed:**

- **V4.1 needs more than tensor import.** Its FP8 dense / FP4 expert path has
  post-load layouts, quantization metadata and cached tensor references that a
  replacement engine must restore consistently. Related failures are documented
  in [#39794](https://github.com/sgl-project/sglang/pull/39794). This PR restores
  the processed state, rebinds mHC and TopK references, and checks backend/layout
  compatibility instead of merely relaxing the IPC admission check or repeating
  transforms on shared weights.
- **Host Engram needs its own resident recovery path.** GPU tensor IPC cannot
  share its host backing. This PR preserves daemon-owned host tables and imports
  them in replacement workers; optional HOST_NUMA VMM reuses allocation handles
  to avoid repeated `cudaHostRegister` on unchanged tables.
- **Faster checkpoint reads still pay checkpoint I/O on restart.** The
  InstantTensor and positioned-read PRs below accelerate loading from storage.
  This PR complements them by reusing already processed GPU weights and host
  Engram after a worker restart, while the daemon survives. Their cold-load
  optimizations can still benefit initial daemon startup, but are not included
  in this patch.

The result is a V4.1-specific implementation of the article's resident-weight
recovery path, plus an experimental prewarmed standby for its active-standby
scenario. Complete weight reload and service recovery results are reported below;
full long-context acceptance and other remaining gates are still pending.

## Speed Tests and Profiling

### Engram in GPU memory

Disk reload compared with resident CUDA IPC recovery:

| Metric | Before | After | Speedup |
| --- | --- | --- | --- |
| Complete main-model weight reload | **50.56 s** | **1.02 s** | **49.6×** |
| Complete service recovery: process launch → healthy service | **95.09 s** | **36.53 s** | **2.60×** |

Values are medians: two final matched disk runs and three recovery runs.
Compilation/autotuning caches were warm. The weight reload covers the entire
main model, including Engram and post-load state; service recovery also includes
communication, KV and runtime initialization.

### Engram in shared host memory

| Host layout and comparison | Metric | Before | After | Speedup |
| --- | --- | --- | --- | --- |
| Shared table: disk reload → resident IPC + memfd | Complete main-model weight reload | **85.45 s** | **14.44 s** | **5.9×** |
| Per-rank shards: existing memfd recovery → HOST_NUMA VMM | Complete main-model weight reload | **4.77 s** | **3.36 s** | **1.42×** |
| Per-rank shards: existing memfd recovery → HOST_NUMA VMM | Launch-helper return → polled service readiness | **45.54 s** | **40.53 s** | **1.12×** |

Host recovery values are medians of three runs; the shared-table disk baseline
has one sample. Shared tables and per-rank shards are separate experiments:
85.45 s is not a matched baseline for 3.36 s. Exact process-launch to healthy
service time was not measured for the host VMM comparison; its readiness timer
starts after the launch helper returns.

Both placements require an already loaded, surviving daemon for optimized
recovery; initial daemon startup is excluded.

An already prewarmed standby provided its first response token **0.205–0.422 s after active-launcher SIGKILL** in the memfd experiment. This is standby takeover, not a new worker reload. VMM plus standby has not yet had a combined full-model fault-injection run.

**Setup:** four NVIDIA L20D GPUs, TP4/EP1/attention-DP1, native FP8 dense/FP4 expert, `flashinfer_mxfp4` / `dsv4`, vision disabled, context 4096, maximum four requests, CUDA Graph and overlap disabled. The VMM experiment used private KV capacity 8192 per worker.

## Modifications

- Add explicit V4.1 recovery opt-in, a versioned post-load state contract and compatibility fingerprint. Restore processed tensor aliases, quantization metadata, mHC references and TopK correction bias without transforming shared weights again.
- Add daemon-owned host Engram FD sharing, with `memfd` and optional `cuda_vmm` backends. VMM clients map GPU views of the same physical host allocation without copying it or repeating host registration.
- Align daemon/client backend initialization and isolate draft loading from target IPC loading.
- Add an experimental two-worker standby gateway with generation warmup, promotion and replenishment. Failed requests are not replayed, and session state is rejected.
- Add registered CPU tests and [configuration/usage documentation](https://github.com/number-eleven11/sglang/blob/codex/dsv41-weight-cache-recovery/python/sglang/srt/weight_cache/README.md).

## Accuracy Tests

**71 CPU tests pass**, and upstream lint passes. GPU measurements predate formatting/documentation edits; there were no non-import AST changes when formatting the tested implementation.

For the host VMM comparison, all 30 prompt comparisons matched text and input/output token IDs; 24/30 also matched logprobs exactly. The 1401-token prompt differed even in a memfd same-service repeat, so **strict long-context numerical acceptance remains unresolved**. Short prompts and the 385-token case were exact. Host gather and shared-table CUDA Graph component checks passed; full-model CUDA Graph/shared-layout validation is pending.

## Limitations

This remains a draft. The experiment used sglang-kernel 0.4.7 with the source's expected 0.4.9 version check bypassed; aligned-dependency validation is pending. Full-capacity throughput, draft/speculative execution and other topologies remain unvalidated. The daemon must survive, and same-GPU standby workers do not isolate GPU faults. In-flight requests/KV state are not recovered. Initial daemon host allocation costs remain; this does not implement #42920's parallel checkpoint reads.
