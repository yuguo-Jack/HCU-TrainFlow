# [Perf] detokenizer: Send per-request decode inputs once and keep them in the detokenizer

[Upstream PR](https://github.com/sgl-project/sglang/pull/47260) · state: closed · merged: True

## Original PR description

The scheduler sent, on every decode step and for every emitted row, values that do not change during a request: a decode-id delta that copies `output_ids`, the read offset, three decode flags, and the tokenizer worker route. It also kept the prompt tail and all output ids just to slice that delta. These values are now sent once and kept by the detokenizer.

## Changes

- **Header once.** A request's first emitted row carries a `DetokenizeHeader`: the prompt tail, `skip_special_tokens`, `spaces_between_special_tokens`, `no_stop_trim`, and `http_worker_ipc`. The detokenizer keeps it in a per-request `DetokenizeState` (`incremental_detokenize.py`) and extends the decode ids from each row's `output_ids`. The scheduler drops `surr_offset`, `read_offset`, `send_decode_id_offset` and `init_incremental_detokenize`.
- **State lifetime.** A new header replaces any state left under the same rid. A request ended outside the output stream (`send_abort_output`) sends a `DetokenizeReleaseReq`.
- **Routing.** `MultiDetokenizerRouter` routes by rid. Finished rows carry their own `http_worker_ipc`, so they reach their tokenizer worker even without stored state.
- **Continuity alarm.** For each non-beam row the detokenizer checks the ids received so far against `completion_tokens`; a mismatch logs a warning (raises in CI) and resyncs.
- `--skip-tokenizer-init` and the Rust server are unchanged: they send no header and no release.

## Behavior changes

- A request that reuses a rid no longer decodes on top of stale state. Finished rows are delivered when one rid is in flight on two tokenizer workers, or after more than `SGLANG_DETOKENIZER_MAX_STATES` live requests, where main crashed.
- An unfinished row with no stored state gets empty text and a warning: after eviction, or a late row after `send_abort_output`.
- With several detokenizer workers, rows are assigned by rid instead of by tokenizer worker.
- The continuity alarm fires on `input_embeds` requests retracted after streaming, a path already inconsistent on main (`reset_for_retract` empties `output_ids` but keeps `send_token_offset`). Outputs there are unchanged.

## Verification

- Unit tests for the header, the release, decoding from stored state, rid reuse, missing state, routing through the streamer, the multi-detokenizer split and the multi-tokenizer fan-out, the continuity alarm, and the msgpack round trip.
- Differential test: 20,000 random request lifecycles through the real streamer, routers, detokenizer and fan-out with a Qwen3 tokenizer (multibyte characters split across tokens, special tokens, stop strings, speculative steps, stream intervals, retraction, aborts, beam search, skip-init, 1-3 workers). 0 differences from main over 542,499 rows, apart from the rid-reuse fix. Stress runs with one rid on two tokenizer workers and with 1-4 detokenizer states delivered every finished row; main crashed in both.

## Micro benchmark

CPU only, one steady decode step for 512 streaming requests with 512-token prompts, real tokenizer, pickle IPC.

| | scheduler build (us/step) | pickle (us/step) | unpickle (us/step) | detokenizer decode (us/step) | message (KB) |
|---|---|---|---|---|---|
| main | 705-732 | 398-404 | 293-298 | 1508-1530 | 51.0 |
| this PR | 500-524 | 219-223 | 163-168 | 1554-1564 | 28.4 |

The scheduler side (build + pickle) drops by about 35%; detokenizer decode is 2-3% slower (stored-state lookups, the route list and the continuity check).
