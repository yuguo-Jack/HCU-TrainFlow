# fix(nccl): disable graph buffer registration whenever a captured graph can hold a collective

[Upstream PR](https://github.com/sgl-project/sglang/pull/43216) · state: open · merged: False

## Original PR description


## Problem

`NCCL_GRAPH_REGISTER` is on by default and registers the send/recv buffers of every graph-captured collective for the lifetime of the graph. Those buffers are graph-pool temporaries, and the pool hands the same addresses to other tensors, so a replay can find its registration pointing at memory that now belongs to something else.

Both existing guards key on a feature flag rather than on that aliasing:

- `enable_tp_lm_head_all_to_all` additionally requires PD-decode, DP attention, `dp_size > 1` and `tp_size == dp_size`
- the pausable-pool check (dcf4e18) requires `enable_memory_saver` plus `SGLANG_MEMORY_SAVER_CUDA_GRAPH`, which is off by default

A plain multi-node TP deployment matches neither, so the registration stays on and the hang is reachable.

Features: more likely to appear under large batch size (> 128); not directly related to torch_memory_saver; currently does not appear in PREFILL stage but we still use any stage as gate to not regressing from the previous gate.

## Reproduction

Two TP16 engines spanning two H200 nodes each, decode batch 128, CUDA graph on, radix cache on, `max-running-requests 128`, a 501B MoE model. Load is 160 concurrent 4096-token generations per engine plus a pause/flush/continue cycle every 120s. `enable_tp_lm_head_all_to_all` and `enable_memory_saver` are both false in every run below.

Every TP rank hits the 300s scheduler watchdog within the same second:

| run | peak decode batch | NCCL | `NCCL_GRAPH_REGISTER` | result |
| --- | --- | --- | --- | --- |
| 1 | 66 | 2.29.7 | default (on) | clean for 1h |
| 2 | 128 | 2.29.7 | default (on) | hang at 19 min |
| 3 | 128 | 2.29.7 | default (on) | hang at 17 min |
| 4 | 128 | 2.29.7 | default (on), dcf4e18 applied | hang at 37 min |
| 5 | 128 | 2.29.7 | `0` | clean for 5h — 76k requests, 70M tokens, 148 cycles |
| 6 | 128 | **2.32.3** | default (on) | hang at 32 min |
| 7 | 128 | **2.32.3** | `0` | clean for 40 min |

Run 4 is why the dcf4e18 cherry-pick alone is not enough: it is in the tree, neither of its conditions matches, so the variable is never set and the hang is unchanged.

Runs 6 and 7 rule out a stale NCCL as the cause. 2.32.3 carries the fix for NVIDIA/nccl#2389, which has a similar signature, and the hang still reproduces with the registration on and still disappears with it off.

Two further conditions were tested and are *not* required: `NCCL_PXN_DISABLE=1` still hangs (7 min), and all of the above runs have the TP LM-head all-to-all and the memory saver off. Disabling GDR (`NCCL_NET_GDR_LEVEL=0`) does hold for 50 min with the registration on, which points at the network registration path, but that is not something this layer can detect at argument-resolution time.

## Cost

Same engine, same tree, same load, 10 minutes each:

| registration | requests | tokens |
| --- | --- | --- |
| on | 1,765 | 2,060,061 |
| off | 1,781 | 2,066,577 |

No measurable throughput difference. Single run per configuration, not repeated for variance. Worth noting that the non-registered path is the one every deployment used before the default flipped, so it is not a new or lightly-exercised code path.

## Change

One condition replaces both: `max(tp_size, ep_size, dp_size) > 1` with any graph phase still enabled means a capture can hold a collective, which is exactly when a registration can outlive the pool's claim on the address. It errs toward disabling — later passes can still narrow `cuda_graph_config`, and a false positive costs nothing measurable.

Keying on any phase rather than decode alone keeps the pausable-pool case that dcf4e18 added: with the decode capture off and the memory saver on, a prefill capture still lands in that pool.

The test that asserted the variable stays unset without the TP LM-head all-to-all encoded the old contract and now asserts the new one. Added alongside it: the pausable pool in isolation, a prefill-only capture, a single rank, and a fully disabled graph.

Draft while the deployment-shape coverage gets a second opinion — happy to narrow the condition if there is a configuration where the registration is known to be safe and worth keeping. The root cause is still open: these runs establish which conditions reproduce it and which do not, not the mechanism inside NCCL.
