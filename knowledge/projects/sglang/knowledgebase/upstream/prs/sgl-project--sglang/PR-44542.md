# [Fix] moe: Refresh cached correction bias after in-place weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/44542) · state: open · merged: False

## Original PR description

## Motivation

`TopKConfig.correction_bias_for_dtype` caches `e_score_correction_bias` cast to the activation dtype. The cache key includes the parameter's `_version`, which is the mechanism the existing comment relies on to drop a copy taken before weights are loaded.

That check does not fire for the writes RL actually uses. Weight loaders and the RL weight update path write through `param.data.copy_()`, and a write through `.data` does not bump `_version`. The cached BF16 bias built during warmup therefore stays in place for the rest of the process. With dummy-load startup, warmup runs on random weights, so every later routing decision uses a correction bias of about `±1e-3` instead of the real values (about 5 per expert on GLM-5.3-Flash). Weight sync replaces the parameter and the weight checker never sees the cache, because it is not a registered tensor.

This affected every RL run on the ROCm GLM-5.3-Flash branch, including MI355X, not only MI300X. It is not an AMD kernel bug. Any in-place weight update that writes `e_score_correction_bias` through `.data` leaves the cache stale, on CUDA as well as HIP.

## Modifications

When the cache key matches, copy the current bias into the existing cached tensor instead of returning it unchanged. The copy keeps the CUDA-graph address stable. A real `_version` change still allocates a new tensor, which is what `test_cache_refreshes_if_weight_is_reloaded` already checks.

`test_data_write_refreshes_cache_in_place` covers the `.data.copy_()` case: values update, and the cached storage address does not move.

## Accuracy Tests

GLM-5.3-Flash BF16 RL, 4 steps, same data, MI300X. `train_rollout_logprob_abs_diff` per step:

| Run | Gap |
|---|---|
| Before this fix | 0.153, 0.150, 0.101, 0.157 |
| After this fix | 0.087, 0.085, 0.061, 0.094 |

The fixed gap matches the previous rollout build (0.089, 0.065, 0.094). Comparing a disk-loaded server with a dummy-loaded server, the correction-bias cache was the only tensor that differed across 1,513 checked tensors: real bias summed to about 1525, the dummy cache to about 0.

The new unit test could not be executed on this machine (no local torch). It is a CPU test registered in `base-a-test-cpu`.

## Speed Tests and Profiling

The refresh is one `copy_` of the bias vector (288 elements on GLM-5.3-Flash) when the cache key hits. Rollout step time on the fixed MI300X run was 114–157 s, in the same range as the previous build (120–138 s).
