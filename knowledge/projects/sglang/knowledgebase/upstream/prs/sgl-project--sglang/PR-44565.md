# [Perf] [AMD] Qwen3-Next: reach the Gluon TP4 AR+norm+quant kernel from the boundary

[Upstream PR](https://github.com/sgl-project/sglang/pull/44565) · state: open · merged: False

## Original PR description

**Depends on #39140**, which adds the kernel this reaches. It targets `main`
independently rather than stacking: both imports of that module are guarded, so
until #39140 lands this PR is a no-op, not a build break.

Second of three:

1. #39140 — the Gluon kernel, the HIP IPC layer, the rendezvous state, the test
2. **this PR** — make it reachable from the layer boundary
3. #44565 — the Qwen3-Next opt-in that makes it the default for that model

## What this does

`layers/layernorm.py` — try the Gluon backend first inside
`_forward_with_allreduce_fusion_quant_per_group`, falling through to the
existing aiter chain when it declines (wrong arch, TP size, shape or eps). A
rendezvous failure disables the path for the process and logs, rather than
raising: the rendezvous is collective, so every rank must reach the same
verdict.

`distributed/parallel_state.py` — build the rendezvous state before CUDA graph
capture and record call sites during it. The state has to exist before capture
begins; one created mid-capture would not have its bookkeeping armed and would
silently fall back to a staging copy.

`layer_boundary/fusions/allreduce.py` — `ffn_input_fusions` gains a defaulted
`read` parameter, mirroring `attn_input_fusions`, so an FFN stage can declare a
quantized read; `fused_ffn_input` gains the matching `fuses_quant` branch.

`layer_boundary/construction.py` — thread the incoming read to the FFN side,
copying the line directly above it for attention.

## Why the FFN side needs this

`attn_input_fusions(plan, read)` already takes a read declaration and can reach
`forward_with_allreduce_fusion_quant_per_group`. `ffn_input_fusions(plan)` takes
no read and only ever calls the plain `forward_with_allreduce_fusion`, so an FFN
consumer that could take `(fp8, scale)` has no way to say so. This closes that
asymmetry in the same shape the attention side already uses.

## Behaviour

**Unchanged everywhere.** No model declares a quantized FFN read in this PR —
that is the next one. The FFN default stays `NORM_READOUT`, an unrelated type
to `NormQuantReadout`, so `fuses_quant` is `False` for every stage that has not
opted in and the existing kernel path is byte-identical. The gate also requires
`_use_aiter`, so CUDA never reaches it.

> `layer_boundary/construction.py` and `fusions/allreduce.py` are common code.
> The change is additive and behaviour-preserving, but a reviewer from the
> community on those two files would be welcome.

## Test plan

* `test_fused_ffn_input` — calls `fused_ffn_input` with `fuses_quant` and
  `keep_bf16` on a supported TP4/gfx950 shape and asserts the returned FP8
  tensor, scale and residual, letting production call
  `_try_gluon_tp_ar_norm_quant` and the Gluon kernel.
* Server start and GSM8K on Qwen3-Next, expected identical to stock since
  nothing declares the read yet.

## Hardware

gfx950 (MI355X), TP4, `SGLANG_USE_AITER=1`. Other AMD architectures and all
CUDA builds take the existing path unchanged.
