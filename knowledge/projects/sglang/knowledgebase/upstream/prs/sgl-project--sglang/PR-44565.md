# [Perf] [AMD] Qwen3-Next: reach the Gluon TP4 AR+norm+quant kernel from the boundary

[Upstream PR](https://github.com/sgl-project/sglang/pull/44565) · state: open · merged: False

## Original PR description

On gfx950, the fused all-reduce + RMSNorm + per-group FP8 quant that the layer boundary calls (`forward_with_allreduce_fusion_quant_per_group`) only ever dispatches to aiter's kernel, so the faster Gluon kernel from #39140 is never selected. At TP4 / hidden 2048 and decode batch 1–16 that kernel takes 6–14% less time per call than aiter's. This PR lets the norm module try it first, and builds the cross-rank state it needs before CUDA graph capture.

Which models it affects is decided by the model's read declaration and the kernel's shape check, not by this PR. A model reaches the kernel only if it declares a quantized attention read and runs at TP4 / hidden 2048 / eps 1e-6 on gfx950 with aiter. #44566 makes Qwen3-Next declare that read, and its end-to-end numbers are there. Qwen3.5 already declares it on `main`, so **Qwen3.5-35B-A3B-FP8 at TP4** (hidden 2048) also picks up the kernel once #39140 and this PR land, with or without #44566. Other Qwen3.5 sizes are outside the envelope.

Second of three:

1. #39140 — the Gluon kernel, the HIP IPC layer, the rendezvous state, the test
2. **this PR** — let the norm module reach it
3. #44566 — the Qwen3-Next opt-in

Each targets `main` independently rather than stacking. Both importers of the kernel module gate on `_use_aiter and is_gfx95_supported()` before importing, so until #39140 lands this is a no-op rather than a build break.

## What this does

`layers/layernorm.py` — in `_forward_with_allreduce_fusion_quant_per_group`, try the Gluon backend before the aiter chain, and fall through to the aiter chain unchanged when it declines (wrong arch, TP size, shape or eps). A rendezvous failure disables the path for the process and logs rather than raising: the rendezvous is collective, so every rank must reach the same verdict.

`distributed/parallel_state.py` — build the rendezvous state before CUDA graph capture, and record call sites during it. The state has to exist before capture begins; one created mid-capture would not have its bookkeeping armed and would silently fall back to a staging copy.

The kernel is reached through the attention boundary's existing fused-quant path, which already threads the consumer's read declaration and `keep_bf16`. **This PR does not touch `layer_boundary`.** An earlier revision also added an FFN-side quantized read there; it was dropped because on Qwen3-Next's default configuration it never engaged (details on #44566).

## Gating

Everything is gated on hardware capability, not on a flag. Both sites that import the kernel module check `_use_aiter and is_gfx95_supported()` *before* the import, so CUDA and non-gfx950 AMD parts neither load the backend nor probe the device. There is no environment variable and no constructor flag.

## Test plan

`test/registered/unit/distributed/test_gluon_tp_ar_norm_quant_gating.py` (CPU):

* `TestPreCaptureGate` — `graph_capture` gates the rendezvous build on `_use_aiter and is_gfx95_supported()`, and does not import the backend when ineligible.
* `TestEveryBackendImportIsGated` — finds every importer of the kernel module by scanning `sglang/` rather than from a hardcoded list, and asserts an eligibility check precedes each import. Verified to fail when the gate is removed from either site, and when a new ungated importer is added in an unrelated module.

On 4× MI355X, with all three PRs merged onto `main`: the 4-rank kernel test passes (bit-exact against an fp32 reference), and Qwen3-Next serves end to end. Results are on #44566.

## Results

This PR has no numbers of its own; what it changes depends on which model declares the read.

* Kernel-level numbers (−6.3% to −14.4% vs aiter at M=1…16): **#39140**
* End-to-end throughput and accuracy for the three together, on Qwen3-Next: **#44566**
* Qwen3.5-35B-A3B-FP8: not yet measured end to end with this kernel.

## Hardware

gfx950 (MI355X), TP4, `SGLANG_USE_AITER=1`, ROCm >= 7.2. Other AMD architectures and all CUDA builds take the existing path unchanged.
