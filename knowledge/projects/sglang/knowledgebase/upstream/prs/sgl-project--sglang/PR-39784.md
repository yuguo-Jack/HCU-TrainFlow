# [Feat] [NPU] HiCache: support DeepSeek V4 L3 with MemCache

[Upstream PR](https://github.com/sgl-project/sglang/pull/39784) · state: open · merged: False

## Original PR description

## Motivation

Add DeepSeek V4 NPU HiCache L3 support through the existing `npu_memcache` backend, building on the upstream DSV4 L2 and MemCache implementations.

## Changes

- Add C128 backup/prefetch descriptors and complete-group alignment. Resolve namespaced endpoint keys before allocating C128 storage-hit buffers.
- Keep the FULL anchor logical; store C4, Indexer/scale, SWA, C128 and state in their physical pools. Preserve existing MLA/DSA/DRAFT/MAMBA key layouts.
- Add the small shared transfer/alignment hooks needed to map logical pages to C128 objects and rank-consistent restore endpoints.
- Initialize MemCache and register pinned Host buffers during startup. On NPU DSV4 with `npu_memcache`, run the existing HCCL prewarm before cache construction, then reuse the existing DSV4 metadata builder with a single-token request to initialize custom AiCPU. Other storage backends keep the original HCCL prewarm position. Remove deferred initialization, pending registrations and the shared `prepare_for_backup` callback. No CPU staging.
- Add storage-contract, partial-hit, pool-transfer and restore regressions; document the required DSV4 cache layout and mode.

## Validation

Hardware E2E on 2026-09-28 at `51128f8ecd`: Ascend A3 / CANN 9.0.0, DeepSeek-V4-Flash-0731-w8a8, TP/DP/EP=8, DeepEP normal, `device_sdma`, 112 GiB Host Holder, default NPU-pinned Host pools.

This run exercises the single-token startup prewarm through the existing metadata builder, including C1/C4/C128 and Indexer metadata. The complete deployed source was verified against the commit.

Both dependencies reuse the builds from the latest master revisions retrieved on 2026-09-24:

- MemCache 1.3.0: `04f67cedb553409e99c84c267fc26b010118455b`.
- MemFabric 1.3.0: `7a2d5a3e4b4e28e757a2bcd3462f909deb01028f`, plus the one-line A3 Host/HBM classification patch.

| Input tokens | Requests / DP ranks | L3 tokens per request | Total L3 tokens | Output equality |
| --- | --- | ---: | ---: | --- |
| 131,072 | 8 / all 8 | 129,024 | 1,032,192 | 8/8 |

After flushing L1/L2 while retaining L3, every replay hit came from storage (device/host hits were zero). Each request's 32 nonempty output tokens matched its same-boundary resident reference exactly; an immediate resident repeat also matched 8/8. Post-test health passed. MemFabric native traces confirm successful SDMA reads and writes on all eight workers. This rerun used 128K only.

The no-MemCache control (HiCache L2 retained) passed startup and 128K inference on 2026-09-28 at `187b0df90f`; this refactor leaves that branch unchanged. The original lazy implementation passed with the same dependencies on 2026-09-24.

Independent probes reproduce the ordering failures without DeepEP: MemCache BM initialization before first custom AiCPU startup fails in `halMemBindSibling`; custom metadata before the first HCCL collective causes later metadata failure even without MemCache. HCCL → custom AiCPU → MemCache resolves both in the tested configuration.

Current local checks: attention unit suite **69 passed, 8 subtests passed**; cache regressions **102 passed, 1 skipped, 35 subtests passed**. Both changed Python files pass isort, Ruff F401/F821/UP037, Ruff formatting and `git diff --check`.

Shutdown again reached the existing 15-second scheduler deadline and terminated two remaining workers; this run does not establish clean graceful shutdown.

A5, RDMA, 16-rank deployment and throughput profiling were not tested. No performance claims.

## Performance test results / 性能测试结果

Completed measurements: (1) the 128K local/remote L3 matrix, and (2) the 48K L1/L2/L3 cache-tier comparison.

These are previously measured results, not a fresh rerun of the current PR HEAD. The two datasets use different configurations and should be interpreted separately.

### 1. Completed 128K L3 performance tests

Source: Excel sheet “L3指标明细”, 128K rows, cross-checked against the saved test report.

Recorded configuration: DeepSeek-V4-Flash-w8a8-mtp; 16 NPUs, TP16/DP16/EP16, DeepEP normal; `page_first_direct`, `write_through`. Local L3 used `device_sdma` with a 224 GiB Holder; remote L3 used `device_rdma` with five 112 GiB Holders (560 GiB total). Measurement concurrency was 16. Each warm case used 64 requests in four 16-request cohorts.

#### Recorded latency, throughput, and actual storage hits

| Input tokens | Target hit | Cold TTFT (ms) | Local L3 TTFT (ms) | Remote L3 TTFT (ms) | Cold input TPS | Local L3 input TPS | Remote L3 input TPS | Local / remote actual L3 hit |
|---|---|---:|---:|---:|---:|---:|---:|---|
| 128K (131,072) | 100% | 72,876.7 | 14,208.1 | 15,508.3 | 22,337.0 | 147,598.2 | 135,224.4 | 98.4375% / 98.4375% |
| 128K (131,072) | 50% | 72,876.7 | 54,518.5 | 65,966.6 | 22,337.0 | 38,466.5 | 31,790.9 | 50% / 50% |

#### Gains recorded in the workbook, relative to its cold baseline

| Input / target hit | Local TTFT reduction | Remote TTFT reduction | Local input TPS increase | Remote input TPS increase |
|---|---:|---:|---:|---:|
| 128K / 100% | 80.5% | 78.7% | 560.8% | 505.4% |
| 128K / 50% | 25.2% | 9.5% | 72.2% | 42.3% |

- TTFT reduction = `(cold - warm) / cold`; TPS increase = `(warm - cold) / cold`. These are cold/warm comparisons, **not L1-hit versus L3-hit comparisons**. The workbook cites a 24-request cold baseline; each warm case uses 64 requests.
- The “100%” cases reused all but the final 2,048-token tail: `129024/131072 = 98.4375%`.
- Both local and remote 128K cases completed at the 100% and 50% target hit settings. The recorded formal runs had no eviction or service exceptions.

### 2. L3 versus L1 cache-hit performance

Sources: `formal-48k-8dp-5rounds.json` and its benchmark log, with the matching `bench_cache_tiers.py` script.

Measured workload: **48K = 49,152 input tokens, 8 DP ranks, concurrency 8, five rounds, 40 measured requests per tier**. The script requests one generated token with temperature 0. Each measured request reused exactly **47,104 tokens**; the remaining 2,048-token tail was outside the reused prefix.

Tier selection was verified from all 40 response records per tier:

| Tier | `device` cached tokens/request | `host` cached tokens/request | `storage` cached tokens/request |
|---|---:|---:|---:|
| L1 | 47,104 | 0 | 0 |
| L2 | 0 | 47,104 | 0 |
| L3 | 0 | 0 | 47,104 |

| Cache source | Mean client request latency (ms) | P50 (ms) | P90 (ms) | Mean server E2E (ms) | Input TPS |
|---|---:|---:|---:|---:|---:|
| L1 | 2,585.39 | 2,601.72 | 2,636.80 | 2,535.71 | 148,682.98 |
| L2 | 5,966.98 | 5,975.23 | 6,053.86 | 5,917.02 | 65,247.91 |
| L3 | 6,231.52 | 6,226.48 | 6,373.89 | 6,187.59 | 62,198.24 |

**L3 versus L1 in this workload:**

- Mean client latency increased by **3,646.14 ms**, or **141.03%** (L3 latency was **2.4103×** L1).
- Input throughput decreased by **58.17%** (L3 retained **41.83%** of L1 input throughput).
- Mean server E2E latency increased by **144.02%**.

For context, L3 versus L2 increased mean client latency by **4.43%** and decreased input throughput by **4.67%**.

Interpretation: these are **end-to-end request measurements**, including cache restoration and remaining model work, not isolated memory-copy bandwidth or pure L3 get latency. Input TPS is total submitted input tokens divided by measured wave wall time, including cached input tokens; it is not output-token throughput. Do not describe the result as “128K is 58.17% slower”: this comparison was measured at 48K only.
