# [Fix] mem_cache: Size the unified-pool req_to_token row from the shared headroom helper

[Upstream PR](https://github.com/sgl-project/sglang/pull/41008) · state: open · merged: False

## Original PR description

## Summary

Three sites sized KV allocation with a copy of a formula instead of calling the helper that exists for it. Two of the copies had drifted from the computation they claim to mirror, leaving the `req_to_token` row shorter than the reserve a decode step actually takes.

## Problem

`get_req_to_token_extra_context_len()` sizes the headroom the `req_to_token` row keeps beyond `model_config.context_len`. `kv_cache_configurator.py` carried two more copies of that computation, in the unified-mamba and unified-mamba-SWA pool builders, both labelled:

```python
# Mirror the non-shared path's extra_max_context_len computation.
extra_max_context_len = 4
if get_spec().speculative_num_draft_tokens is not None:
    extra_max_context_len += get_spec().speculative_num_draft_tokens
```

The label does not hold. The helper differs in two ways:

- it reads `max_speculative_num_draft_tokens()` rather than `speculative_num_draft_tokens`, because an adaptive algorithm may raise the draft length after the scheduler has already reserved KV for the next decode batch;
- it widens to `get_alloc_reserve_per_decode() + page_size - 1` when `page_size > 1` or the algorithm is UNO.

Neither is optional. `assign_req_to_token_pool_func` writes the row out to `nxt_kv_len`, and `page_aligned_decode_alloc_lens` computes that as `committed + reserve` rounded up to the allocator's page. A row shorter than that writes past its own row into the neighbouring request's.

`pool_configurator.py` carried the third copy: `decode_alloc = 2 * get_alloc_len_per_decode()` in `compute_swa_request_cap`. That is exactly `get_alloc_reserve_per_decode()` -- the helper PR #27458 introduced specifically so that "the sites cannot drift". This one is numerically identical today, so it is a pure consolidation.

## Evidence

`needed` is the largest `nxt - committed` a decode step can ask for, computed with `page_aligned_decode_alloc_lens` -- the same function `eagle_utils` / `dflash_info_v2` / `uno_info` use to size the allocation. `before` is the deleted copy, `after` is the helper.

| algo | page_size | needed | before | after |
|---|---|---|---|---|
| DSPARK | 1 | 34 | 21 | 21 |
| DSPARK | 8 | 41 | 21 | **41** |
| DSPARK | 64 | 97 | 21 | **97** |
| DSPARK | 256 | 289 | 21 | **289** |
| EAGLE (steps=5, topk=1, tokens=8) | 1 | 16 | 12 | 12 |
| EAGLE (steps=5, topk=1, tokens=8) | 8 | 23 | 12 | **23** |
| EAGLE (steps=5, topk=1, tokens=8) | 64 | 79 | 12 | **79** |
| EAGLE (steps=3, topk=2, tokens=6) | 8 | 71 | 10 | **71** |
| EAGLE (steps=3, topk=2, tokens=6) | 256 | 2303 | 10 | **2303** |
| UNO | 1 | 18 | 12 | **18** |
| UNO | 64 | 81 | 12 | **81** |

The UNO row is worth calling out: `test/registered/unit/mem_cache/test_uno_allocation_sizing.py` already asserts `get_req_to_token_extra_context_len() >= get_alloc_reserve_per_decode()` for UNO at `page_size = 1`. The deleted copy would have failed that assertion (12 < 18), so these two builders were violating an invariant the suite already tests for the shared helper.

## Relationship to #33579 / #33581

#33579 reports the `page_size == 1` half of this shortfall (DSPARK gamma=16: headroom 21 against reserve 34) and #33581 fixes `get_req_to_token_extra_context_len` for it. That fix does not reach these two builders, because they never call the helper. After this PR they do, so the corrected sizing applies to the unified pools as well and the row no longer depends on which pool family the model uses.

This PR does not change the `page_size == 1` non-UNO branch itself -- the `before` and `after` columns are equal there and remain equal until #33581 lands.

## Testing

It asserts the headroom covers the page-rounded reserve across a grid of algorithms and page sizes, using the decode path's own sizing function as the oracle rather than a restatement of the formula; and it pins the spec-v2 term of `compute_swa_request_cap` against `get_alloc_reserve_per_decode()` by differencing against the identical config with spec disabled.
- `pytest test/registered/unit/mem_cache/test_req_to_token_row_headroom.py test/registered/unit/mem_cache/test_uno_allocation_sizing.py` -> 4 passed.
- Every hook in `.pre-commit-config.yaml` that applies to Python passes on the three files: isort 7.0.0, ruff 0.15.1 (`--select=F401,F821,UP037`), ruff-format v0.15.1, codespell 2.4.1, plus trailing-whitespace / end-of-file-fixer / check-ast.

**Not run:** an end-to-end server. The affected configuration is `--enable-unified-memory` on a hybrid-Mamba model with `--speculative-algorithm DSPARK` and `--page-size > 1`, and I have no GPU available here. The shortfall is therefore demonstrated arithmetically against the sizing functions, not by an observed row spill.
