# [Fix] [AMD] dsv41: Fix wrong TP4 wo_a output from hipBLASLt's strided bmm on ROCm 7.2

[Upstream PR](https://github.com/sgl-project/sglang/pull/46534) · state: open · merged: False

## Original PR description

## Motivation

With the ROCm 7.2 torch wheel (`lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261025`, torch 2.11.0+rocm7.2, HIP 7.2), DeepSeek-V4.1 TP4 target verify returns a wrong wo_a output at 289-294 rows on MI355X, on every layer (relative error 1.4 against an fp32 reference). DSpark verifies 6 rows per request, so a 49-request verify batch hits it. The DSpark draft takes the same route.

`_wo_a_bf16_bmm_token_major` (#46176) has hipBLASLt write the bmm straight into the token-major layout through a strided `out=`. The hipBLASLt bundled with that wheel picks a stream-K kernel at these row counts that miscomputes the strided destination; the same GEMM writing a packed result (the einsum) is exact. The ROCm 10 build of the same day (`v0.5.22-rocm10-mi35x-20261025`, torch 2.11.0+rocm10.0.0, HIP 7.15) is exact at every row count, so the change applies before HIP 7.15 only (`_STRIDED_BMM_OUT_OK`, the gate #45193 uses).

## Modifications

Before HIP 7.15, TP4 verify rows 9-384 go through `_hip.wo_a_verify_matmul`:

- MXFP8 wo_b (the gfx950 default): the packed einsum plus one fp8-grid quant launch over both groups, written straight into wo_b's token-major fp8 + ue8m0. This replaces the strided bmm plus wo_b's own quant with the same traffic and launch count. `_launch_fp8_grid_quant` also takes a `[M, G, K / G]` input read through its strides; 2-D callers keep their tiles and addresses.
- bf16 wo_b and the DSpark draft: the einsum copied token-major at the 6 broken rows only (`_WO_A_VERIFY_STRIDED_BMM_BAD_ROWS`, the measured failure set); main's strided bmm everywhere else.
- CUDA, HIP prefill and HIP >= 7.15 are unchanged. `test_deepseek_v4_amd_wo_a_bf16.py`: the bf16 verify graph test also runs 292 rows, and a new graph test covers the MXFP8 hand-off at 64 and 292 rows.

## Accuracy Tests

MI355X, `_apply_wo_a_bf16_matmul` with 2 groups (TP4) followed by a real MXFP8 wo_b. Every verify row count 1-384, 3 `o` layouts (dense, strided, 64-head padded), 2 passes per image (2 seeds, 2 GPUs):

| path | image | wrong rows, main | wrong rows, this PR |
|---|---|---:|---:|
| verify, MXFP8 wo_b | ROCm 7.2 | 289-294 (each layout) | 0 |
| verify, bf16 wo_b / DSpark draft | ROCm 7.2 | 289-294 (each layout) | 0 |
| verify, MXFP8 wo_b | ROCm 10 | 0 | 0 |
| verify, bf16 wo_b / DSpark draft | ROCm 10 | 0 | 0 |
| prefill 4096-65536 (main's code, 33 sampled row counts) | both | 0 | 0 |

Wrong means a relative error > 1e-2 against wo_b's output on the einsum (main's wrong rows are at 1.41). On ROCm 7.2 the hand-off's fp8 codes equal wo_b's own quant of the correct bf16 at every row, and wo_b's output is bitwise equal to it at every row, so it equals main's wherever main is right. The scale byte of an all-zero 32-group differs (its codes are 0 either way), as in #45193. The bf16 route differs from main only at 289-294. On ROCm 10 both routes equal main bitwise at every row. `test_deepseek_v4_amd_wo_a_bf16.py` passes on both images (8/8); on main its two 292-row cases fail on ROCm 7.2.
