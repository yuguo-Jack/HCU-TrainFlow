# [Fix] rust-server: Give each attention-DP listener its own frontend cores

[Upstream PR](https://github.com/sgl-project/sglang/pull/47599) · state: closed · merged: True

## Original PR description

Fixes #47598.

## Motivation

Under DP attention every DP rank hosts a Rust listener (`SGLANG_RUST_SERVER=1`), and each listener runs `_partition_cores()` on its own process affinity mask. DP ranks launched with one mask (no NUMA bind, or several ranks per NUMA node with it) therefore all compute the same slice and pin their frontends onto the same first cores of the mask. GLM-5.3 at TP8/DPA8 on 8xH200: all 8 listeners log `rust server cores=[2, 3, 4, 5, 6, 7, 8, 9]` out of 128 allowed cores. #47161 stopped pinning the scheduler thread, but the frontend sets still collide on `main`.

## Modifications

- `rust_server/server.py`: new collective `RustServer.gather_frontend_cpu_share(hosts_listener)`. Every rank all-gathers `(hostname, allowed cores)` for listener ranks (`None` otherwise) on the world group, and gets back its `(index, count)` among the listeners with an identical key. `launch()` takes it as `frontend_cpu_share` (default `(0, 1)`, i.e. unchanged behaviour) and hands it to `_partition_cores`.
- `rust_server/config.py`: `_frontend_cpu_key()` and the pure `_frontend_cpu_share(cpu_keys, rank)`; `_partition_cores(..., cpu_share=(0, 1))` cuts the mask into `count` contiguous blocks and partitions only block `index` (launch reserve + bounded pool, as before, inside the block). If a block would be under the existing 4-core split threshold, it keeps the whole mask and warns that the listeners overlap, i.e. the previous behaviour.
- `managers/scheduler.py` (`maybe_init_rust_server`): call the collective next to `gather_server_endpoints` (every serving rank) and pass the result to `launch`. Like `gather_server_endpoints`, an elastic-EP joiner stays out of the collective (the serving ranks never re-enter it) and keeps `(0, 1)`.
- Listeners whose masks already differ (per-rank affinity such as `SGLANG_SET_CPU_AFFINITY`, one listener per NUMA node) get `count == 1` and are partitioned exactly as before.

## Speed Tests and Profiling

The bug was measured on v0.5.21 (where the scheduler thread was still pinned too), GLM-5.3 W4AFP8, TP8/DPA8/EP8, EAGLE, HiCache, 8xH200, same engine flags behind sgl-model-gateway 0.3.2 `cache_aware`, agentic trace workload at concurrency 64 for 900 s: Python frontend 859 requests / 475.5 output tok/s / 38.8 ms per decoded token (median), Rust frontend 179 requests / 96.6 tok/s / 217 ms. The end-to-end A/B of this fix, backported onto the same v0.5.21 deployment, is in the first comment below (+13% output tok/s and -15% decode time per token over a #47161-only baseline; back to the Python frontend's speed).

Unit tests (CPU), run locally with this branch on `PYTHONPATH`:

- `test/registered/unit/multimodal/rust/shared/test_partition_cores.py`: 8 passed. The two new regression cases (8 listeners on one 128-core mask; two sockets with 4 listeners each plus a non-listener rank) fail with the block split disabled.
- `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py`: 13 passed, including the new `test_gather_frontend_cpu_share_counts_only_listeners_on_this_mask` (also covers the elastic-EP joiner skip).
- `test/registered/unit/entrypoints/test_rust_server_dp_ports.py`: 50 passed; `test_listener_rank_installs_the_sigterm_drain` now also checks that every rank joins the CPU-share gather and a listener launches with its share.
