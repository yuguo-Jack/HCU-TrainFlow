# [router] Fix power_of_two with --dp-aware

[Upstream PR](https://github.com/sgl-project/sglang/pull/42027) · state: closed · merged: True

## Original PR description

## Motivation

With `--pd-disaggregation --dp-aware --decode-policy power_of_two`:

1. 1P1D / 2P1D cannot start (`Power-of-two policy for decode requires at least 2 decode workers`). Validation counts URLs, but each URL expands into `dp_size` workers at runtime.
2. p2c is effectively random. The load monitor requests `http://host:port@rank/v1/loads`, which never reaches the engine (`host:port` is parsed as userinfo). It also reads `aggregate.total_tokens`, which current `/v1/loads` no longer returns (it returns per-rank `loads[]`). Every rank gets `-1`, which is cached, so p2c compares `-1 vs -1` and keeps the random first pick.

## Modifications

- Skip the p2c "at least 2 workers" validation when `dp_aware` is set.
- Fetch `/v1/loads` once per engine and map `loads[].num_total_tokens` by `dp_rank`. Non-DP workers use the sum, and legacy `aggregate.total_tokens` is still accepted.
- Don't publish failed loads, so p2c falls back to request counts. On token-load ties, p2c also compares request counts.
- Count PD streaming requests as in flight from dispatch, not after upstream headers arrive. Otherwise a streaming burst sees zero in-flight requests everywhere and p2c is random again.

## Test

CPU-only, in `lmsysorg/sglang-rocm:v0.5.20-rocm724-mi35x-20260930`, with fake DP engines and 64 concurrent requests:

| | stock | this PR |
|---|---|---|
| 1P1D / 2P1D, decode dp8 | fails to start | starts; 7..9 req/rank |
| 1P + 2D x dp8 (16 ranks), non-streaming | `-1 vs -1` in every decision; 0..12 req/rank | no `-1`; 2..6 req/rank; 1 `/v1/loads` per engine per poll |
| 1P + 2D x dp8 (16 ranks), streaming | 0..8 req/rank (stddev 2.0, same as random) | 2..5 req/rank (stddev 0.74) |
| one rank reports +500k tokens | still selected | never selected |

The added unit test covers `/v1/loads` parsing (per-rank and legacy formats). `cargo test --lib` and clippy pass.

- p2c now starts on 1P1D and reads each rank's load. The token load evens out KV across decode ranks (busiest / mean rank KV tokens 1.24-1.43 -> 1.08-1.23) but not the number of requests per rank, which sets the DP-attention decode step time, so throughput and TPOT stay close to `round_robin`. #43483 adds a request-count load.
- The load monitor polls at `--worker-startup-check-interval` (default 30 s), not at the policy's `load_check_interval_secs` (5 s). A 30 s snapshot is stale enough to make p2c worse than `round_robin` (last column). Not changed here.

### Concurrency 512 over the hour

![All three arms over the hour, concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-router-p2c/c512-three-arms-over-the-hour.png)

With this PR, p2c on tokens leaves the request count across decode ranks less even than `round_robin` (bottom). The in-flight request load from #43483 keeps it flat for the whole hour. At 512 more than half (55-57%) of each rank's in-flight requests are still waiting on KV transfer, so the busiest rank's running batch (top) improves less than at lower concurrency.

![Running requests per decode rank, p2c in-flight requests (1s), concurrency 512](https://raw.githubusercontent.com/AMD-yanfeiwang/sglang/pr-assets-router-p2c/c512-per-rank-running-p2c-inflight.png)

With #43483 every decode rank's hourly mean running batch is within 2% of the 8-rank mean, and no rank is the busiest more than 17% of the time (`round_robin`: DP6 at +6.3% and 21%; 12.5% if even).
