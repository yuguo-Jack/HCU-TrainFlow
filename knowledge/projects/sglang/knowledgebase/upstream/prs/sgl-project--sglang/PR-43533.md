# [PD][HiSparse] Support hybrid DSA KV pools in PD serving

## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Enable HiSparse for hybrid DSA/linear-attention models in PD serving, validated with GLM-5.3-Flash. DSA KV uses CPU backing storage and a GPU hot buffer, while KDA state remains on the GPU.

On 8 × H200 (P4/D4), this increases D-side logical KV capacity from **4.51M to 8.51M tokens (1.89×)** at the same GPU memory budget. GSM8K accuracy is **95.74% with HiSparse versus 95.89% without it**, a difference of two answers across 1,314 evaluated questions. Long-context PD requests and resource reclamation also passed validation.

This PR addresses the “HiSparse × PD: hybrid DSA pools in PD” item in the Q4 PD disaggregation roadmap (#43699).

This PR covers non-speculative decoding. A follow-up PR adding PD disaggregation + HiSparse + MTP support is coming soon.

## Modifications

<!-- Detail the changes made in this pull request. -->

- **Hybrid cache integration:** connect the HiSparse DSA backing pool to the hybrid linear KV pool, preserving KDA state access and mapping global layer IDs to DSA layers.
- **KPool and FP8 swap-in correctness:** support tail tokens alongside pooled selections, handle top-k bounds and partial scan blocks, and enable the TileLang FP8 path.
- **Consistent capacity accounting:** compute logical KV occupancy against the logical pool, while retaining separate GPU/host utilization checks.
- Add targeted regression tests for pool configuration, allocation, KPool swap-in, and occupancy accounting.

The TileLang FP8 prerequisite (#42957) is now merged upstream; this PR contains only the three HiSparse commits.

## Accuracy Tests

<!-- If this pull request affects model outputs (e.g., changes to the kernel or model forward code), provide accuracy test results. -->

Validated on GLM-5.3-Flash, 8 × H200, P4/D4, TP4/EP4, TileLang FP8 KV, Prefill BCG and Decode CUDA Graphs, without MTP. The paired configurations differ only in whether D-side HiSparse is enabled. The full GSM8K comparison used the same HiSparse code plus the optional NIC-selection change from #43482; that change is excluded from this PR. Native NIXL shared-device operation was also validated.

GSM8K: all 1,314 evaluation questions after reserving 5 few-shot examples, 8 threads, max tokens 4096, temperature 0, `reasoning_effort=low`.

| D configuration | Correct / evaluated | Accuracy |
| --- | ---: | ---: |
| HiSparse disabled | 1,260 / 1,314 | 95.89% |
| HiSparse enabled | 1,258 / 1,314 | 95.74% |

The paired run shows a **0.15 percentage-point difference**. Functional validation also covered:

- 32K-input PD requests and repeated concurrent requests, exceeding the 4,096-token GPU hot buffer.
- A separate idle-pool check: logical KV, GPU/host KV, and Mamba usage returned to zero, with request slots restored after completion.
- Targeted CPU and H200 kernel regression tests; pre-commit checks passed.

## Speed Tests and Profiling

<!-- If this pull request impacts inference speed, provide benchmarking and profiling results. -->

**Capacity result: 1.89× logical KV capacity at the same GPU memory budget.** Both configurations use D-side `--mem-fraction-static 0.75` and 80 Mamba slots; HiSparse uses `host_to_device_ratio=2`.

| D configuration | GPU KV token capacity | Logical KV token capacity | CPU KV allocation per rank |
| --- | ---: | ---: | ---: |
| HiSparse disabled | 4,512,000 | 4,512,000 | — |
| HiSparse enabled | 4,254,208 | 8,508,416 | 47.92 GB |

GPU KV allocation is **25.19 GB per rank in both cases**. CPU backing storage expands the logical pool while GPU memory holds the hot KV working set. Token capacities refer to the TP group and are not summed across ranks.

This validates capacity expansion and the PD serving path; it does not imply a proportional concurrency or throughput increase. NIC-selection performance is covered separately by #43482.
