# [DSpark] Fix draft MoE expert-location dispatch to restore speculative acceptance

[Upstream PR](https://github.com/sgl-project/sglang/pull/34846) · state: closed · merged: False

## Original PR description

## Motivation

DSpark reuses DeepSeek NextN decoder layers for its draft model. Regular NextN/MTP layers intentionally skip expert-location dispatch, but DSpark draft expert weights are loaded according to the target model's global expert-location metadata.

With a non-identity initial expert placement, the draft gate emits logical expert IDs while the corresponding weights reside in remapped physical slots. Skipping logical-to-physical dispatch therefore executes the wrong draft experts and substantially degrades speculative acceptance.

## Modifications

- Add an explicit opt-in for expert-location dispatch on NextN MoE layers.
- Keep the existing behavior unchanged for regular NextN/MTP users.
- Enable the opt-in only when constructing a `DSparkV4Stage`.
- Apply the same dispatch decision consistently to the regular, dual-stream, DeepEP, and `op_select_experts` paths.
- Add CPU unit tests covering:
  - non-NextN layers continue to use expert-location dispatch;
  - NextN layers continue to skip it by default;
  - NextN layers can explicitly opt in;
  - DSpark stages enable the opt-in.

## Accuracy Tests

GSM8K smoke test (20 questions) after the fix:

- Accuracy: `0.950`
- Invalid: `0.000`

The test confirms that the corrected draft expert routing restores valid model output. This is a small smoke test rather than a statistically strong accuracy evaluation.

## Speed Tests and Profiling

Under the same DSpark + non-identity expert-placement configuration (10 random requests):

| Metric | Before | After |
| --- | ---: | ---: |
| Mean acceptance length | 1.61 | 3.38 |
| Output throughput (tok/s) | 161.64 | 313.24 |
| Mean TPOT (ms) | 45.80 | 21.82 |

The workload is intentionally reported as a smoke/performance regression test; it is not a full throughput benchmark.

Regular NextN/MTP behavior is unaffected because the new dispatch behavior is opt-in and is enabled only by `DSparkV4Stage`.
