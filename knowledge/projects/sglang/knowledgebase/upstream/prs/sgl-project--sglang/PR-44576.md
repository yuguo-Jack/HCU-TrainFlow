# [Fix] disaggregation: Release multimodal features when PD prefill finishes a request

[Upstream PR](https://github.com/sgl-project/sglang/pull/44576) · state: open · merged: False

## Original PR description

_Posted by Kunal's robot (Claude Opus 5.5) ↓_
>
> ## Motivation
>
> A PD prefill request is marked finished after the forward pass, in the inflight-queue drain or a bootstrap failure handler, so `_maybe_clear_mm_inputs` never sees it finished. With `pp_size > 1`, consumption-time release is also off, so the request's CPU feature tensors stay alive as long as the `Req` does.
>
> On a PP8 prefill server under image traffic, the first stage's scheduler grew by about 280 MB per request until the host ran out of memory.
>
> ```
> forward --> inflight queue --> drain: Success / Failed --> (new) release
> bootstrap -----> failure handler -------------------------> (new) release
> ```
>
> ## Modifications
>
> - Factor the per-request release out of `_maybe_clear_mm_inputs` into `_release_mm_inputs`.
> - Call it from the inflight-queue drain and from the bootstrap failure handler. The failure path releases after streaming the abort, so the reported multimodal token counts stay intact.
> - Session requests keep their features, as before.
> - Add `test_prefill_mm_release.py`, and give the hand-built schedulers in `test_prefill_result_polling.py` and `test_priority_scheduling_disaggregation.py` the new method.
>
> This PR is independent of #44574 and #44575, which address the same workload.
>
> ## Accuracy Tests
>
> Not applicable: features are released only after the request finishes.
>
> ## Speed Tests and Profiling
>
> Same workload as #44574, 30 minutes, about 350 requests:
>
> | First-stage scheduler RSS | Start | End |
> |---|---|---|
> | Base | 44.6 GiB | 141.3 GiB |
> | Fixed | 38.9 GiB | 38.8 GiB |
>
> The other stages stayed flat in both runs.
