# [CI] [AMD] nightly-disagg: Keep all MI355X CI settings in the repo and clean up after failed jobs

[Upstream PR](https://github.com/sgl-project/sglang/pull/48131) · state: closed · merged: True

## Original PR description

## Motivation

The MI355X disagg nightly was down for several days this week, for two reasons:

1. Jobs that died halfway left about 1 GB of temporary files each in the runner's home folder. Once the disk quota was full, the runner could not start, and nightly jobs just sat in the queue.
2. Where to find the model files was set only on the runner machine, not in this repo. It pointed at `/tmp`, which is wiped on reboot, so after one node rebooted, every job that landed on it failed.

Several other settings were also hidden or misleading:

- Some cluster settings lived only on the runner machine.
- Each recipe named a Docker image that was never actually used.
- The GLM jobs were labelled GLM-5.2 but loaded GLM-5.1.

## Changes

- **All settings live in the repo.** The scheduler account, the partition, the model cache folder and the Docker image are set only in the workflow file. The runner machine needs no extra configuration.
- **Models are named once.** Each model is identified only by its Hugging Face name (e.g. `sgl-project/DeepSeek-V4-Flash-FP8`). The four variables that kept rewriting an old file path are gone.
- **Quick, clear failure when a model is missing.** Before starting servers, each job checks that every node it got has the model, at the same version. If not, it fails in about a minute and names the node, instead of timing out after 50 minutes.
- **Leftover files get cleaned up.** Each new job first deletes temporary files left by that runner's earlier failed jobs.
- **Unused per-recipe images removed.** The nightly always used the latest ROCm 10 image anyway, so the per-recipe images (all ROCm 7.2) are deleted.
- **No pip installs on the runner.** The packages it needs are already installed there.
- **GLM relabelled.** The GLM jobs are renamed `glm52-*` → `glm51-*` to match the model they actually load.

## Testing

- A full nightly run of this branch (all 35 jobs) is in progress: https://github.com/sgl-project/sglang/actions/runs/41616663221. The first 16 jobs all passed, with GSM8K accuracy between 0.949 and 0.957 (pass mark 0.91). That run started before the cleanup change, which has unit tests only (`test_runner_disk_preflight.py`).
- Before that, I ran three cases by hand: a missing model failed in about a minute with a clear message; Kimi-K2.6 with its draft model passed; DeepSeek-V4-Flash passed.

## After merge

Remove the old settings from the runner machine.

- michaelzhang-ai · COMMENTED · 2026-11-03T20:46:00Z · [source](https://github.com/sgl-project/sglang/pull/48131#pullrequestreview-5759227771)

The model-path changes look right to me. The draft path reaches the server, warm-up and bench scripts through `model_paths.sh`, including on the multi-node path.

One concern with the scratch reclaim: `prune_scratch()` runs inside "Reclaim old runner diagnostics and check disk headroom", which is still `timeout-minutes: 2` and not `continue-on-error`. Each leftover leg dir holds a staged copy of the checkout (~12k files plus `.git`, since checkout uses `fetch-depth: 0`) on NFS. Deleting one or more of these can take longer than 2 minutes, for example after a runner dies mid-leg or on the first run after merge, when all the old unowned dirs go at once. The step then times out and fails the leg before it launches. Could the prune be best-effort (its own step with `continue-on-error`, or a longer timeout), so only the quota probe gates the leg?
