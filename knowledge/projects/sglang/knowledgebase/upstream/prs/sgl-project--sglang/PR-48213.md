# [Fix] PD: Recover NIXL peers on the prefill across decode restarts and re-registrations

[Upstream PR](https://github.com/sgl-project/sglang/pull/48213) · state: open · merged: False

## Original PR description

## Motivation

On a 1P2D NIXL deployment (LIBFABRIC backend over EFA, SGLang `a6a8c560` with local patches) the prefill lost ~300 requests/hour to `KVPoll.WaitingForInput` timeouts on the decode side while the decode engines restarted repeatedly (a separate CUDA fault). The prefill never logged a NIXL transport error. It logged ~2000/hour `Peer <agent> was already registered, ignoring.`

Two gaps in `NixlKVManager` on the prefill:

- A decode that restarts registers a new agent name from the same ip and rank port. The prefill keeps the old agent's metadata, its transport endpoint and every room promised to it. Nothing fails those rooms until the decode's waiting timeout.
- A decode that timed out on this prefill rank drops its cached bootstrap info and registers again under the same agent name (`_check_waiting_timeout` -> `invalidate_cached_bootstrap_infos` -> `_register_kv_args`). The prefill ignores that registration, so the endpoint the decode timed out on is reused for its next room.

#41691 reloads a peer only when NIXL itself marks its metadata invalid. A transport error on a posted handle does not always do that, so the dead endpoint outlives every retry.

## Modifications

`python/sglang/srt/disaggregation/nixl/conn.py`:

- `_add_remote_peer` indexes peers by `_peer_identity` = `(endpoint, gpu_id, decode_tp_rank, dst_dcp_rank)`. The decode's rank port comes from `get_zmq_socket_on_host` (`bind_to_random_port`, so a new port per process) and its agent name is a fresh uuid, so neither identifies the process across a restart; the second commit replaces the port-based key of the first. A new agent name for a known identity means the decode process restarted: `_evict_replaced_peer` drops the old agent's NIXL metadata and dlists, flags it evicted (its registration stays in the table so a late chunk still referencing it fails through the normal not-found path), and fails its unconcluded rooms with `record_failure` + `KVPoll.Failed`, so the prefill frees their KV instead of waiting out the decode's timeout.
- A registration under an already known agent name is queued in `_peer_refresh_pending`. The transfer worker applies it before posting the next room for that peer (`_refresh_reregistered_peers`): drop and reload the remote agent, which rebuilds the transport endpoint, then rebuild the dlists. Done on the worker because it is the only thread holding the peer's dlists; throttled per peer by the existing `_PEER_RELOAD_MIN_INTERVAL_S`.
- `_reload_invalidated_peers` takes the failure: a transport error that names a peer forces that peer's rebuild even while `check_remote_metadata` is true. Peers the error does not name keep the invalidation-only behaviour, so a healthy sibling in the room is never rebuilt.
- `_rebuild_peer` is the shared drop / reload / `_prepare_payload_xfer` / `_prepare_state_xfer` step; `_peer_registry` lazily creates the bookkeeping for managers built without `__init__` (the existing test rigs).

Successful registration and transfer paths are unchanged; the new work runs on re-registration, on a replaced endpoint, and after a transfer failure.

## Accuracy Tests

No change to model forward or sampling. As a check that the KV transfer path is intact, sgl-eval against the 1P2D EFA deployment carrying this patch (Kimi K3, thinking on, temperature 0.6, top_p 0.95, 32 threads, with live shadow traffic alongside): GSM8K 1319/1319 answered, score 0.9735, 0 errors, 0 truncations; AIME26 x4 (30 problems, max_tokens 65536): pass@1 0.908 ± 0.028, majority@4 1.0, pass@4 1.0, 0 errors, 3/120 samples truncated at the 65,536-token cap.

Decode-restart run on the 1P2D EFA deployment (LIBFABRIC backend, shadow traffic) carrying this patch with the GPU-rank-keyed identity:

**Container restart, same ip** (both decode engines died within two minutes of each other, a separate scheduler crash):
- The prefill logged 32 `NIXL peer … was replaced by …; evicting it and failing its rooms` lines when the restarted decodes registered after loading (8 GPUs × 2 prefill ranks × 2 decodes).
- 0 `WaitingForInput` timeouts, 0 NIXL errors, 0 tracebacks over 4 h.
- Failed requests: 193, all within the 20 minutes around the crashes (aborted in flight, or `Bootstrapping` timeouts while the decodes reloaded); none afterwards. Before this patch the same arm produced ~300/h of 300 s timeout failures after each decode restart.

**Pod delete, new ip** (one decode pod deleted; replacement ready in ~4 min):
- Graceful drain: no aborts, no bootstrap failures, no NIXL errors.
- No eviction, as the identity includes the ip; the old registration lingers unused (documented limitation).
