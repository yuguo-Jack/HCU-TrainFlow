# [Perf] [NVIDIA] dp-attention: Route the padding rows of the TP-MoE gather to no expert

[Upstream PR](https://github.com/sgl-project/sglang/pull/48072) · state: open · merged: False

## Original PR description

## Motivation

With attention DP and TP MoE on CUDA, the MoE input of a decode step is a MAX_LEN gather: every DP rank contributes a slot of the same length, and the rows past its real requests are padding. The decode CUDA graph always uses this layout, and an idle rank still replays one fabricated row. The router sends the padding rows to experts like real tokens, so every MoE layer loads those experts' weights.

Since #46225 this costs more on hybrid models. Before it, the unpacked KDA/GDN decode left the padding rows' output unwritten. On GLM-5.3-Flash, six or seven of the seven padding rows of a one-request step then selected exactly experts 0-7 in every MoE layer, which is what the router does with NaN scores (it ranks NaN as -1e30 and breaks ties toward the lowest id). #46225 zeroes that output, which is the right fix for correctness, and the padding rows now route like real tokens. With one request on 8×H20 (attention DP8), the expert-distribution recorder counts about 41 distinct experts per MoE layer per decode step instead of about 22, and median ITL went from 11.84 ms (main before #46225) to 12.73 ms (main).

On ROCm, DeepSeek-V4 zeroes the padding rows before the gather (#43077). Zeroed rows still route, to the experts with the largest correction bias. This PR keeps them out of routing.

`SGLANG_OPT_MASK_DP_PAD_MOE` (#31888, off by default) drops the same rows from the dispatch, but only with EP: it runs in the standard dispatcher after the local expert mapping, which exists only when `moe_ep_size > 1`. With TP MoE the rows still route.

## Modifications

- `ForwardBatch.dp_real_rows_gpu` (int64, one count per DP rank) holds how many rows of each rank's slot are real, when the MoE input is a MAX_LEN decode gather. Eager decode writes it in `prepare_mlp_sync_batch`, in the same `write_host_ints` launch as `global_num_tokens_gpu`. The decode CUDA graph keeps a static copy and refreshes it on every replay with a device copy of the batch's `global_num_tokens_gpu`, which still holds the per-rank counts because the graph path skips `prepare_mlp_sync_batch`. `ForwardContext.moe_dp_real_rows` exposes it the way `moe_num_token_non_padded` is exposed.
- `select_experts` (CUDA, standard top-k output) sets the padding rows' ids to -1:
  - The Triton router `moe_fused_gate` does it inside its existing launch (`HAS_DP_ROWS`, next to `HAS_PADDING`). `select_experts` hands it the counts on the biased sigmoid / sqrtsoftplus path and on the two Triton-router branches of `biased_grouped_topk_gpu`; GLM-5.3-Flash takes the grouped one.
  - The router's two fast paths, every other router, and an EPLB remap (which would read -1 as its last entry) get one `_fill_dp_pad_rows` launch afterwards. A separate launch per MoE layer is not free: an earlier revision that always masked after the router cost 0.3-0.6% ITL at 8-128 concurrent requests on GLM-5.3-Flash DP8.
- The Triton fused MoE already skips -1 ids (the EP convention), so padding rows load no expert weights and return zeros. Real rows are unchanged bit for bit with BF16 activations and with per-token or per-group activation scales (GLM-5.3-Flash's block FP8). With per-tensor dynamic FP8 (no static `a2_scale`), the down GEMM's activation scale no longer covers the padding rows, so real rows can move by FP8 rounding.
- Scope (`_dp_tp_moe_skips_pad_rows`): CUDA; attention DP > 1 with attention TP = 1, so each rank owns one contiguous slot; no attention CP; TP MoE (EP 1, no A2A, FP4 all-gather or DWDP); no world DP gather; no two-batch overlap; non-speculative decode. `SGLANG_DP_MASK_PAD_ROWS=false` turns it off; ROCm uses the same switch for its zeroing.
- MoE runners: tested with the Triton fused MoE. The CUTLASS MoE path also treats ids outside [0, num_experts) as unused (`cutlass_prepare_moe_input`), and `flashinfer_trtllm` with in-kernel routing never sees them. Not checked: the FlashInfer CUTLASS runner and `flashinfer_trtllm` with precomputed routing.
- Not covered yet: speculative decode (verify batches carry several rows per request) and prefill steps with an idle rank (its fabricated extend rows). The same masking applies to both, with counts in rows instead of requests.
- Tests, `test/registered/moe/test_topk_padded_region.py::TestDpPadRows`:
  - `_fill_dp_pad_rows` against an eager reference over three layouts, each with an idle rank;
  - the same kernel captured in a CUDA graph and replayed with changing counts;
  - `moe_fused_gate` with `dp_real_rows`, with and without a fused shared expert;
  - `select_experts` + `fused_moe` under a forward context with DP counts, for a softmax router, a biased sigmoid router and a grouped biased sigmoid router, both with a fused shared expert: padding rows get -1 and zero output, and real rows match the unmasked run bit for bit. Dropping the mask after the router, or the counts from a Triton-router call, fails this test.

## Accuracy Tests

- `test_topk_padded_region.py` on H20: 13 passed, 3 HIP-only skipped, 56 subtests.
- GSM8K, attention DP8 (8-shot completion, all 1,319 questions, greedy, 512 tokens): main 0.931 / 0.933; this PR 0.923, and 0.936 / 0.928 for the earlier revision, which sends the same rows to -1 after the router instead of inside it.
- Greedy output ids on a fixed 1024-token prompt are identical to main.
