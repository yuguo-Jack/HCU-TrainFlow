# [Perf] dsv41: Read Engram rows in place by default for GPU tables over NVLink

[Upstream PR](https://github.com/sgl-project/sglang/pull/47033) · state: closed · merged: True

## Original PR description

Follow-up to #46955.

- With `--engram-config` `lookup` `auto` (the default) and the tables in GPU memory (the default), each rank now reads its tokens' Engram rows in place from the owning GPU, as `peer_read` does, when the TP group is one NVLink domain: one node with full NVLink, or one multi-node NVLink fabric such as GB300 NVL72. Otherwise `auto` keeps picking a collective. The choice is one more branch of `resolve_engram_config`, the single place `auto` is resolved since #46955, and the log says `Engram lookup auto -> peer_read`.
- `custom_all_reduce_utils.in_one_nvlink_domain`: the topology check, built from the existing NVLink helpers; the physical-GPU-id gather moves out of `can_use_custom_all_reduce_with_nvlink` into `gather_physical_device_ids` so both use it.
- Docs: `auto` and its measurements.

Behavior change: default DeepSeek-V4.1 deployments with TP > 1 over NVLink allocate the Engram shards through CUDA VMM and map their peers' shards at load, instead of running a collective per Engram layer per step. The shard per GPU is the same size. Host tables and explicit `lookup` values are unchanged.

## Verification

- B300, default `--engram-config` at TP 8 and TP 2: the layer builds peer shards, and the output checksums match the explicit `peer_read` run (TP 8) and the all-reduce run (TP 2).
- Unit tests: `test/registered/unit/distributed/test_custom_all_reduce_v2_capability.py`, `test_parallel_state.py`, `test/registered/unit/layers/test_engram_history.py` pass.
