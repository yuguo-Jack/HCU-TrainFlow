# [Feat] [AMD] kv-shard: Support KV cache sharding with aiter and MoRI

[Upstream PR](https://github.com/sgl-project/sglang/pull/44660) · state: open · merged: False

## Original PR description

## Motivation

ROCm support for KV cache sharding (`--enable-kv-cache-sharding`, #30501) on PD prefill, aligned with main: the aiter MLA prefill backend and the MoRI transfer backend, including kv-shard together with CPU HiCache (`--enable-hierarchical-cache`), which main supports on CUDA. The DSv4 page-striped host tier that used to be part of this PR is now a separate draft PR.

## Modifications

- aiter prefill gathers sharded prefix pages into scratch rows (layer-ahead all-gather on a side stream, after any HiCache load-back of that layer); ROCm MHA reads them via `get_mla_kv_buffer`.
- Server-arg gate accepts the aiter prefill backend and the MoRI transfer backend; refuses `--disaggregation-enable-kv-checksum` (each rank owns a subset of logical pages); decode attention TP may differ from prefill.
- Scope: aiter MLA prefill over attention TP; DSA attention backends are not covered.

## Accuracy Tests

8x MI355X, `lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261025`, DeepSeek-R1-0528 (FP8, fp8_e4m3 KV), single-node 1P1D: prefill TP4 (aiter, page 64, chunk 16384, `--max-total-tokens 524288` per rank) on GPU 0-3, decode TP4 + DP-attention on GPU 4-7, MoRI transfer, sglang router in front. Decode is identical in all arms; the arms differ only in prefill flags.

**Notation.**
- **agg TP8** (S1 only): one non-disaggregated TP8 server on all 8 GPUs, the single-node baseline. **Baseline**: 1P1D, no kv-shard, no HiCache. **HiCache only**: `--enable-hierarchical-cache --hicache-ratio 2` (write_through, kernel io, page_first). **kv-shard only**: `--enable-kv-cache-sharding` (4 ranks). **kv-shard + HiCache**: both.
- **Logical device pool**: tokens the prefill radix cache can hold across the 4 ranks (4x the per-rank pool with kv-shard).
- **|dlogprob|**: absolute difference of teacher-forced per-token logprobs on the same sequence; mean / max over 8 prompts x 24 tokens.

### A1. GSM8K, 4 prefill arms

`sgl-eval run gsm8k` through the router, 1,319 questions, T 0.6, top_p 0.95, max_tokens 32768, 128 threads.

| Arm | Logical device pool | Host pool per rank | GSM8K | Errors |
|---|---|---|---|---|
| Baseline | 524,288 | - | 95.22% | 0 |
| HiCache only | 524,288 | 1,048,640 (36.85 GB) | 94.16%, rerun 95.22% | 0 |
| kv-shard only | 2,097,152 | - | 95.22% | 0 |
| kv-shard + HiCache | 2,097,152 | 1,048,640 (36.85 GB) | 95.15% | 0 |

One sampled run per arm (binomial SE about 0.6 pp); HiCache only was rerun on a fresh server. GSM8K prompts are too short to hit the prefix cache, so this checks that the flags leave compute intact; HiCache load-back is covered by A2.

### A2. Host load-back parity

8 prompts of 24,027 tokens (key/value facts + retrieval question). Steps: cold greedy run (reference), device-hit run, evict with fillers of 1.5x the logical device pool, first touch after eviction (served from host in HiCache arms), then a second device hit. Logprob parity is teacher-forced on the reference continuation; greedy token identity is not used because aiter prefill is not bit-reproducible run to run (Baseline itself repeats 2/8 sequences exactly).

| Arm | Retrieval correct (all phases) | Host-hit tokens after eviction | After eviction vs device hit: mean / max \|dlogprob\| | Device hit vs device hit (noise): mean / max \|dlogprob\| | After eviction vs no-cache recompute: mean / max \|dlogprob\| |
|---|---|---|---|---|---|
| Baseline | 8/8 | 0 (recompute) | 0.044 / 0.854 | 0.046 / 0.918 | 0.045 / 0.928 |
| HiCache only | 8/8 | 192,000 | 0.042 / 1.100 | 0.044 / 0.762 | 0.049 / 0.914 |
| kv-shard only | 8/8 | 0 (recompute) | 0.053 / 0.706 | 0.045 / 0.617 | 0.046 / 0.720 |
| kv-shard + HiCache | 8/8 | 192,000 | 0.050 / 1.122 | 0.051 / 1.409 | 0.057 / 1.014 |

With kv-shard + HiCache all 8 prefixes (192,000 tokens) come back from the sharded host pool, and the difference from a device hit is within the same-path noise (Mann-Whitney |z| <= 0.72 in every arm).

- c64: only kv-shard + HiCache holds the reusable prefix (92.4% hit); every other arm is prefill-bound. A repeat of both c64 headline arms reproduced within 1%: agg TP8 2,767 tok/s/GPU (TTFT P50 149.79 s), kv-shard + HiCache 9,666 tok/s/GPU (TTFT P50 10.68 s).
- c32: agg TP8's 3.32M-token pool already holds most of the working set (86.6% hit). kv-shard gains 1.24x throughput from disaggregated decode (TPOT 46 vs 72 ms), but TTFT P50 is 2x agg TP8's: prefill runs on 4 GPUs and adds the KV transfer.
- HiCache without kv-shard stores a full replica per rank (2.07M-token logical host pool vs 7.84M with kv-shard) and reaches 73.0% / 48.0% total hit.

### S2. AgentX on PD prefill with a capped prefill pool: kv-shard + HiCache

Same setup as Accuracy. InferenceX AgentX FULL (3,600 s window, concurrency 32), `dsr1` capped corpus with `AIPERF_MAX_CONTEXT_LENGTH=163840` (130 of 393 traces), fresh servers per arm, one run per arm. Prefill hit rates and queue come from the prefill server metrics; tok/s/GPU counts all 8 GPUs. The prefill pool cap (`--max-total-tokens 524288` per rank, about 18 GB of KV) puts the corpus's reusable prefix well beyond one rank's pool, the regime kv-shard targets; with a pool that already holds the working set, kv-shard adds capacity that goes unused.

| Arm | Logical device pool | Host pool (logical) | Prefill hit: device / host / total | Prefill queue (avg reqs) | Total tok/s | tok/s/GPU | QPS | TTFT mean / p90 (s) | TPOT mean (ms) | E2E mean / p90 (s) |
|---|---|---|---|---|---|---|---|---|---|---|
| Baseline | 524,288 | - | 10.9% / 0 / 10.9% | 32.4 | 12,688 | 1,586 | 0.20 | 169.8 / 221.9 | 33.4 | 195.9 / 260.8 |
| HiCache only | 524,288 | 1,048,640 | 15.0% / 25.4% / 40.3% | 26.7 | 17,364 | 2,171 | 0.26 | 105.7 / 157.7 | 36.1 | 133.2 / 199.3 |
| kv-shard only | 2,097,152 | - | 74.2% / 0 / 74.2% | 17.2 | 35,822 | 4,478 | 0.62 | 33.9 / 73.9 | 40.8 | 64.0 / 119.8 |
| kv-shard + HiCache | 2,097,152 | 4,194,560 | 77.7% / 15.2% / 92.9% | 0.43 | 52,131 | 6,516 | 0.90 | 2.18 / 5.11 | 45.9 | 33.5 / 73.8 |

- kv-shard + HiCache: 3.0x the tok/s/GPU of HiCache only and 1.46x of kv-shard only; mean TTFT 2.2 s vs 105.7 s and 33.9 s. It keeps 92.9% of the trace's ~94% reusable prefix, so prefill stops queueing; the other arms are prefill-bound with 17-32 requests queued.
- With kv-shard each rank backs up and loads only its own pages: kv-shard + HiCache loads back 1.8x the tokens of HiCache only (28.5M vs 16.0M) with 0.45x the host traffic (1.00 TB vs 2.25 TB over the 4 prefill ranks).
- TPOT rises with the higher decode concurrency (decode is identical in all arms). The replay is closed-loop, so faster arms reach further into the traces (median ISL 48k vs 66k). The same 3 requests (52-60k-token outputs) hit the router's 1,800 s timeout in every arm.
