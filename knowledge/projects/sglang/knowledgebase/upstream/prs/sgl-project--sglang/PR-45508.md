# [Perf] [KDA] muse_spark: Run the one-token router GEMV on CuTe DSL

[Upstream PR](https://github.com/sgl-project/sglang/pull/45508) · state: closed · merged: True

## Original PR description

## Motivation

This PR is powered by [KDA](https://github.com/NVlabs/kda) team. `MuseSpark1xRouter` computes FP32 router logits on a side stream in every MoE layer, and the MoE waits for it. At one decode token cuBLAS runs this as a split-K GEMV plus a separate reduce kernel. In NVFP4 batch-1 decode on GB300 the main stream waits 146-152 us per step (of about 5.4 ms) for the router.

## Modifications

- `kernels/ops/gemm/muse_spark_router_gemv_cutedsl.py` (new): a CuTe DSL FP32 GEMV with one launch, no split-K workspace and a fixed reduction order, so results are deterministic and differ from cuBLAS only by FP32 summation order
- `router_gemv_cute_eligible` admits FP32 inputs on SM10x GPUs with aligned rows. Muse Spark enables TF32, under which cuBLAS already runs multi-row logits as a TF32 GEMM, so only the one-token decode call moves
- `srt/models/muse_spark.py`: `MuseSpark1xRouter.forward` calls the kernel when eligible and keeps `F.linear` otherwise
- `kernels/ops/gemm/__init__.py`, `test_kernels_namespace.py`: register `gemm.muse_spark_router_gemv` in the kernel inventory
- `test_muse_spark_router_gemv_cutedsl.py` (new): FP64 reference with an FP32 error bound, 1-16 tokens, misaligned rows, other shapes, bitwise repeatability, side-stream CUDA-graph replay and the TF32 dispatch rule. Registered on H100 (fallback path) and B200 (CuTe path)

## Accuracy Tests

- 16,600 cases over 200 configurations stay within the FP32 error bound (largest error 0.5% of it); Compute Sanitizer is clean
- GSM8K (sgl-eval, 1319 questions, 8 runs per side): NVFP4 +0.27 pt (95% CI [-0.13, +0.69]), BF16 -0.08 pt ([-0.50, +0.34])

## Speed Tests and Profiling

Kernel vs cuBLAS on GB300 at one token (hidden 8192, 256 experts), two jobs:

| Weight | cuBLAS | CuTe DSL | Speedup |
| --- | --- | --- | --- |
| cold (HBM) | 6.24 us | 4.19 us | 1.49x / 1.50x |
| warm | 4.35 us | 2.14 us | 2.03x / 2.03x |

Model, cookbook GB300 High Throughput recipe, decode-C1 mean ITL, two pairs per format:

| Format | Pair 1 | Pair 2 |
| --- | --- | --- |
| NVFP4 (1x GB300, TP4/EP4) | 1.017x | 1.007x |
| BF16 (2x GB300, TP8/EP8) | 1.030x | 1.031x |

- No repeatable regression above 2% at any serving point in either format
- The Low Latency (DFlash) recipe never calls the kernel: its verify steps route several tokens per request (0 launches in the rank-0 profiles)
- Measured before [#45112](https://github.com/sgl-project/sglang/pull/45112) moved the kernel to `ops/gemm/`; on current main the tests pass on GB300, and GSM8K with the other Muse Spark changes applied shows no loss (NVFP4 over five pairs +0.00 pt, BF16 +0.19 pt)
