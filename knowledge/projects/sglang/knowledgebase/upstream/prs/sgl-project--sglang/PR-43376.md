# [Fix] dsv41: Size prefill indexer score tiles by memory in use to avoid OOM without shrinking them

[Upstream PR](https://github.com/sgl-project/sglang/pull/43376) · state: open · merged: False

## Original PR description

## Motivation

The DeepSeek-V4.1 ratio-1/2 index layers score every prefill row against the whole compressed context with DeepGEMM `fp8_fp4_mqa_logits`, in row tiles (`score_tiles` / `flat_index_logits_tiles`). Each tile is `rows x max compressed context` fp32, allocated through the caching allocator outside every pool sized by `--mem-fraction-static`.

1. **OOM with a fixed budget.** The tile budget was a fixed 2 GiB (`_DEEP_GEMM_SCORE_BUDGET_BYTES`), and it counted only the logits: the dense-blocks publisher also allocates a bool causal mask, `select_candidate_block_ids` padded an unaligned context (`F.pad`) into a full fp32 copy of the tile, and the sparse-table publisher kept the previous tile and its block keys alive while the next was allocated. At 485K a 2 GiB tile peaked at about 4.2 GiB. On 4x RTX PRO 6000 Blackwell (SM120, about 95 GiB each), TP4, `--mem-fraction-static 0.85`, chunked prefill 8192, a conversation with about 485K cached tokens growing by small chunks OOMed in `_publish_prefill_blocks -> score_tiles -> fp8_fp4_mqa_logits` (2.00 GiB requested, 1.98 GiB free).
2. **Free memory alone is the wrong budget.** Sizing tiles from `mem_get_info` free memory (`SGLANG_DSA_MQA_LOGITS_FREE_MEM_FRACTION` of it) avoids the OOM but leaves out the caching allocator's unused blocks. A long-running server's allocator ends up holding nearly all free memory (measured on the setup above: 0.05 GiB free to the driver, 91.9 GiB reserved, 83.0 GiB allocated), so the budget falls to about 10 MiB and deep chunks run in one-row-group tiles (4 rows at 32 index heads), thousands of DeepGEMM calls per chunk. In production this showed as cold prefill decaying chunk by chunk to about 1K tok/s past 300K tokens of depth.

Related: #40967, #31704 (both closed), #39095.

## Modifications

- `scoring.prefill_score_budget_bytes`, read by `score_tiles` for its rows and width: the static budget (capped at 2 GiB) under model capture mode, stream capture or torch.compile piecewise graphs, without a device query; otherwise `mqa_logits_budget_bytes` (the free-memory fraction), capped at 2 GiB. When that first reading would leave fewer than 256 rows of the forward's widest score row per tile, it calls `torch.cuda.empty_cache()` and reads again, so the budget follows the memory in use rather than what the allocator happens to cache; an idle server's free memory already gives large tiles and skips the extra read. Forwards below `MQA_LOGITS_STATIC_SKIP_ELEMS` take the cap without a query. Breakable-graph replay runs these layers eagerly and takes the free-memory budget.
- `flat_index_logits_rows_per_tile` / `flat_index_logits_tiles` / `score_tiles` take the caller's scratch as bytes a row and bytes a tile. A tile takes all rows when their aligned allocation (rows aligned to the kernel's row group `128 // heads`, row stride aligned to 256 fp32) plus that scratch fits the budget; otherwise row-group multiples, with one row group as the floor.
- Dense-blocks publisher: tiles are `FLAT_LOGITS_WIDTH_ALIGN` (64) columns aligned, which `block_size` must divide; it passes `logits[rows, :ceil(lc / block_size) * block_size]` to `select_candidate_block_ids` and masks padding columns to `-inf` in place, so it no longer pads a copy. It declares the mask, block maxima and block top-k as row scratch and one request's int64 index vector as tile scratch. The dense-blocks consumer declares `topk_among_blocks`'s candidate gather, masks and picks as row scratch.
- Sparse-table publisher: drops each tile and its block keys before the next tile is scored, and declares the block keys as row scratch.

A fixed score-tile pool held for the server's lifetime was implemented and measured on the setup above, then dropped: held from the activation headroom it left the FlashInfer MoE workspace too little memory (warmup OOM, 942 MiB requested with 808 MiB free), and held from the KV pool it costs about 500 cached tokens per MiB at DeepSeek-V4.1's KV size. The tiles are live only while their layer scores, so they share memory with the rest of the forward.

## Accuracy Tests

CPU test `test/registered/unit/layers/test_dsv41_prefill_score_tiles.py` replaces DeepGEMM and the ragged top-k with exact references and covers allocation alignment and scratch, tiled selection parity at every tile size down to one row group, tile lifetimes, the budget (no reclaim with ample memory or enough rows per tile, one `empty_cache` and a second read when the first is low, the static budget without a query under each capture state, the query under breakable-graph replay, no query for small forwards) and that `score_tiles` sizes tiles by the budget for its own rows and width.

GPU tests in `test/registered/kernels/ops/attention/test_dense_prefill_indexer.py` (SM100 and SM120), at a 485,123-entry compressed context:
- tiles under a 256 MiB budget return bitwise the same scores as one untiled call within each row's valid window;
- publish, consume and the full top-k select positions with the same scores (exact ties may resolve to different positions) and the same blocks at a 256 MiB budget as in one tile, and the published blocks match the pad-based reference;
- with 12 query rows at one-row-group tiles, the measured requested peak bytes past each path's outputs stay within the logits allocation plus declared scratch and a 1 KiB allowance;
- memory parked in the allocator's cache leaves the tile count and the scores unchanged, and memory in use shrinks the tiles with bitwise the same scores.

On this head, rebased onto main `974831643f`: `test_dsv41_prefill_score_tiles.py` passes (12 tests), and the neighboring DSv4/V4.1 CPU suites (`test_dsa_mqa_logits_chunking.py`, `test_dsv41_candidate_blocks.py`, `test_dsv41_late_layer_tail_readers.py`, `test_dsv4_nonpaged_indexer.py`, `test_dsv4_compressed_pools.py`, the DSv4.1 draft/verify metadata glue tests, `test_encoder_swa_replay.py`) pass, 113 passed and 1 skipped in total. The GPU test file has not yet been run on this head.

The OOM scenario: on the setup above, with this change, one cold 491,520-token prompt followed by 12 turns that each resend the history plus 2,000 new tokens (prefix-cached, up to 515,520 tokens), with 8 other requests decoding and the allocator holding all but 50 MiB, ran without an OOM or restart (0.43 to 0.45 s per turn).

## Speed Tests and Profiling

DeepSeek-V4.1-Flash on 4x RTX PRO 6000 Blackwell Max-Q (250 W), TP4/EP2, FP8 KV, chunked prefill 8192, `--mem-fraction-static 0.85`, DSpark. The same image and server process configuration with only the budget changed (these two files applied to the SGLang tree of that image, which carries the first version of this PR), one cold prompt of whole 8K chunks per cell, prompt tokens per second over the whole request. "This change" was measured at the previous revision, which emptied the cache whenever the first reading was below the 2 GiB cap; that cost about 25 ms per idle 8K chunk (the idle cells), which the 256-row threshold of the current head removes:

| Cell | Free memory only | This change |
|---|---|---|
| 256K, idle | 14,938 | 14,299 |
| 512K, idle | 13,697 | 13,238 |
| 256K, allocator holding all but 50 MiB | 8,432 | 14,324 |
| 512K, allocator holding all but 50 MiB | 3,209 | 13,399 |
| 256K, 8 requests decoding | 14,572 | 14,210 |

At about 460K tokens of depth with the allocator holding all but 50 MiB, an 8K chunk took 5.4 s with a 9 MiB budget (8-row tiles, 1,024 per scorer) and 0.69 s with this change (1.48 GiB budget, about 1,660 rows per tile); idle it took 0.68 s. The idle cells are single runs; their 3 to 4% difference is within this setup's run-to-run spread. The "all but 50 MiB" cells park the rest of the free memory in the caching allocator's cache, the state of the production server where the slowdown was found (26 to 136 MiB free to the driver per GPU).
