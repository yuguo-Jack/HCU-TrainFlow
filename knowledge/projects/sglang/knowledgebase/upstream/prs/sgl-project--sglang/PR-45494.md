# [AMD][Fix] hicache: Fall back to transparent hugepages when none are reserved

[Upstream PR](https://github.com/sgl-project/sglang/pull/45494) · state: open · merged: False

## Original PR description

## What
When `SGLANG_HUGEPAGE_SIZE` is set but no huge pages are reserved (`nr_hugepages=0`), `alloc_mmap` now falls back to transparent huge pages (THP) before falling back to 4 KiB pages. THP needs no reservation and no root. It logs a warning if the kernel served some of the faults with 4 KiB pages.

## Why
The host pool is then registered with the NIC. Some NICs cap one registration at about 1M page-table entries (about 4 GiB of 4 KiB pages), so a large host pool on 4 KiB pages fails with `ibv_reg_mr` EINVAL/ENOMEM. 2 MiB pages cut the entry count by 512x. Reserving huge pages needs root, which shared CI nodes do not give.

## Limits
THP is best effort. It needs free, contiguous 2 MiB blocks. On a node whose memory is mostly page cache, the kernel compacts slowly and then serves faults with 4 KiB pages without any error (`thp_fault_fallback` in `/proc/vmstat`). We saw one HiSparse decode run on such a node: allocation took 1000 s and the registration still failed with EINVAL. Reserved huge pages remain the reliable option; this gives a working path when they are not available, and the warning makes the bad case visible.

## Validation
- Unit tests: 13 pass in the ROCm 10 image, including one that allocates real THP memory and checks alignment.
- Standalone `ibv_reg_mr` probe on an ionic NIC, one protection domain: 4 KiB-backed memory fails at about 3.75 GiB, 2 MiB-backed memory registers 100 GiB.
- MI355X, HiSparse decode over MoRI with `nr_hugepages=0`: 168 pools (8 ranks x 21 layers) allocated through THP and registered with no failures on a node with free memory; on a fragmented node the same run failed as described above.
