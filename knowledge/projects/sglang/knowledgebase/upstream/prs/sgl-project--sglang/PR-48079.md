# [Feat] scheduler: UniBoost decode time-slicing for first-token-starved waiters

[Upstream PR](https://github.com/sgl-project/sglang/pull/48079) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #48078. Under KV-memory pressure, the queue-wait tail is set by memory rather than by queue order. In 12 earlier GLM-5.3 runs of the workload below (6 scheduling configurations x 2, same seed), per-rank queues were shallow: only 9-18% of batch logs had two or more waiting requests. Requests that hit the host cache at admission (their prefix had been evicted from device) were 28-33% of all requests but accounted for 76-83% of total queue-wait seconds. They sat at the head of the queue, waiting for enough free device KV to load the prefix back. Meanwhile the device KV was held by long-running decodes that nothing can interrupt: the 10% of requests with the longest outputs held 55-58% of the decode phase's KV x time. No ordering policy can move that tail.

This PR adds decode time-slicing on top of the UniBoost order: when a first-token waiter has starved for `wait_s` and does not fit, the scheduler releases the longest-running decodes into the radix cache, admits the waiter first, and lets the released decodes resume from their cached KV. This mechanism is ours, not the paper's.

**UniBoost series** (each PR builds on the previous one; review in order):
1. #48076: the policy (`--schedule-policy uniboost`)
2. #48077: adaptive gamma from the response-time tail
3. #48078: bounded waits for requests that share a prefix
4. #48079: decode time-slicing for first-token-starved waiters

All four target `main`, so #48077 to #48079 also carry the commits of the PRs before them; each PR's own change is its last commit.

## Modifications

- `managers/decode_preemption.py` (new): the planner and its per-scheduler state.
  - **Trigger**: a waiting request that has not received its first token has queued for at least `--uniboost-preempt-wait-s`, **and** it does not fit the admission budget.
    - The budget mirrors `PrefillAdder`: free plus evictable KV tokens, minus every running request's decode reserve. The reserve uses the same `running_request_token_reserve` helper, now shared with `PrefillAdder` (`ignore_eos` requests reserve at ratio 1.0).
    - The waiter's charge is the same as `add_one_req`'s: tokens past its device prefix (host hits load into fresh device slots), the clipped decode reservation, and one page.
    - A waiter that already fits is starving for some other reason (for example the prefill delayer), and releasing decodes would only add stalls.
  - **Victims**: least attained service first, i.e. the decodes with the most generated tokens. Output lengths are heavy-tailed, so these have the longest expected remaining hold. Only as many are released as the deficit needs; if every eligible release together cannot cover it, nothing is released.
  - **Progress guarantees**:
    - a decode is eligible only after it has generated `--uniboost-preempt-quantum-tokens` (512) tokens since its latest admission, and that quantum doubles with each release;
    - at most `--uniboost-preempt-max-per-req` (2) releases per request;
    - a 1 s cooldown per scheduler;
    - only first-token waiters trigger, so a released decode never triggers releases of its own;
    - beam groups, and `input_embeds` requests that have already streamed output, are never released.
  - **Reservation**: the triggering waiter is moved to the head of the sorted queue until it is admitted, so the released memory goes to it rather than to later arrivals. The reservation lapses after 256 passes if the waiter still does not fit.
- `managers/scheduler_components/request_retirer.py`: `RequestRetirer.release_for_resume` releases a decoding request through the finished-request KV lifecycle (`release_kv_cache(..., checkpoint=True)`), so its KV is checkpointed into the radix tree and its output is kept. OOM retraction, by contrast, drops the uncached tail. It lives in the retirer because that is the one owner of KV release steps.
- `managers/schedule_batch.py`: `ScheduleBatch.preempt_decode(indices, release=...)` applies the release to the chosen rows and filters the batch. Two `Req` fields count the releases and record the output length at the latest admission.
- `managers/scheduler.py`:
  - `maybe_init_decode_preemptor` builds the preemptor (None when off);
  - `promote_target` returns the sorted order with the reserved waiter at its head, applied with `waiting_queue.replace(...)` after `calc_priority`; `on_admitted` runs after `prepare_for_extend`;
  - `_preempt_for_starving_waiters` runs in `update_running_batch` when no KV-full retraction happened in that step. It drains pending decode offloads, releases the victims, removes them from `running_reqs` and re-queues them as retracted. The overlap result processor already skips the in-flight tokens of retracted requests.
- `arg_groups/`: the three flags. `--uniboost-preempt-wait-s` defaults to 0 (off) and requires `--schedule-policy uniboost`, the radix cache and no PD disaggregation. SWA and mamba trees are rejected at scheduler init, because they keep per-request state outside the tree.
- Existing scheduler unit tests that build partial schedulers get `decode_preemptor = None`.
- `docs/.../server_arguments.mdx`: the three flags.

With the flag at 0, no preemptor is built and the scheduler path is unchanged.

Against dfs-weight, uniboost cuts TTFT p99 by 37% and Q p99 by 36%, and requests that waited more than 60 s from 36 to 15. The cost is decode speed: ITL mean +7.5%, ITL p99 +13%, Tok/s -2.9%.

**What time-slicing costs**:
- In the 3600 s run, 55 requests (2.4%) were paused mid-stream, with a pause p99 of 185.7 s.
- Counting that pause as waiting, requests that waited more than 120 s drop from 23 (dfs-weight) to 18 rather than to 14.
- Decode speed: ITL mean +7.5%, ITL p99 +13%, Tok/s -2.9% (table above, 1800 s).

It needs a pool that can keep the released decodes cached until they resume. On a single H200 serving Qwen3-30B-A3B with the same traces, 7-8 running requests filled the pool. There, at concurrency 32, time-slicing capped the worst queue wait (6975 s to 733 s) but completed 36% fewer requests (one run per arm), because released decodes of 100-240k tokens were often evicted before they resumed. The flag is off by default.

**Note:** the measured run hit 3 prefill KV allocation failures in an hour ("Prefill out of memory"), and the baseline runs never did. They come from an existing upstream issue: a chunked-prefill continuation still allocates a full chunk once running decodes have used up the pool, which #44823 fixes. Time-slicing makes it more frequent because the waiters it admits are often long, many-chunk prefills. The v0.5.21 build re-queued such a batch with a local guard, which is not part of this series.
