# :recycle: [llm][npu][quant] Delegate MXFP8 dense scheme to kernel and use torch.ops.npu

[Upstream PR](https://github.com/sgl-project/sglang/pull/28505) · state: closed · merged: True

## Original PR description

## Motivation

Follow-up to #22352 (W8A8 MXFP8 for Qwen3 Dense on Ascend NPU). It addresses two
review comments from @TamirBaydasov that were deferred to keep that already-approved
PR stable:

- https://github.com/sgl-project/sglang/pull/22352#discussion_r3395802464 — a scheme
  should own only hardware-agnostic weight creation and delegate
  `process_weights_after_loading` / `apply` to a linear-method kernel (`self.kernel`),
  like the other ModelSlim schemes.
- https://github.com/sgl-project/sglang/pull/22352#discussion_r3395718707 — NPU ops can
  be reached through `torch.ops.npu.*`, so the top-level `import torch_npu` is unnecessary.

## Modifications

- `ModelSlimMXFP8Scheme` now keeps only `create_weights` and delegates
  `process_weights_after_loading` / `apply_weights` to `NPUMXFP8LinearMethod`
  (`self.kernel`), matching `ModelSlimW8A8Int8`.
- `NPUMXFP8LinearMethod.process_weights_after_loading` branches on the weight dtype:
  pre-quantized `float8_e4m3fn` weights (offline ModelSlim) are only re-laid-out, while
  `float16`/`bfloat16` weights (online) are quantized to MXFP8 at load time. Both paths
  converge on `weight_scale_inv`, so `apply` is shared.
- MXFP8 ops now go through `torch.ops.npu.npu_dynamic_mx_quant` /
  `torch.ops.npu.npu_quant_matmul` with standard `torch.float8_*` dtypes, matching the
  int8/int4 methods in the same file. The top-level `import torch_npu` and the
  `current_platform.is_npu()` guard are dropped from both files, keeping them importable
  on non-NPU (CUDA/CPU/AMD/XPU) CI.

No functional change: the online (`--quantization mxfp8`) and offline
(`--quantization modelslim`, `W8A8_MXFP8`) paths keep the same weight/scale layout.

## Accuracy Test / Benchmark

- `pre-commit run --all-files` passes.
- Verified end-to-end on Ascend NPU: Qwen3 dense online (`--quantization mxfp8`) and
  offline (`--quantization modelslim`) both produce coherent output; the weight/scale
  layout is unchanged, so throughput is on par with the pre-refactor baseline.

This pull request refactors the NPU MXFP8 quantization implementation to support both online and offline (ModelSlim) paths under a unified `NPUMXFP8LinearMethod` kernel, removing redundant code from `ModelSlimMXFP8Scheme` and avoiding top-level `torch_npu` imports to maintain CI compatibility across different backends. ![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Evaluating `_FLOAT8_E8M0FNU_DTYPE` at the module level is risky because `linear_method_npu.py` is imported during sglang's startup to register quantization schemes, which happens **before** `torch_npu` is imported and initialized (via `init_npu_backend`). Consequently, `_FLOAT8_E8M0FNU_DTYPE` will be evaluated to `None` and will remain `None` even after `torch_npu` is loaded, causing `npu_quant_matmul` to receive `None` for scale dtypes during inference.

To prevent this import-order bug, we should resolve the dtype dynamically using a helper function.

```suggestion
# NPU ops are reached via torch.ops.npu.* (registered when torch_npu is imported
# by the runtime), so this module needs no top-level import torch_npu and stays
# importable on CUDA/CPU/AMD/XPU CI.
def _get_float8_e8m0fnu_dtype():
    return getattr(torch, "float8_e8m0fnu", None)
```

In the offline (ModelSlim) path, `layer.weight_scale` is reshaped and transposed into `layer.weight_scale_inv`. Since `layer.weight_scale` is no longer used during inference, we should unregister it from the module using `delattr(layer, "weight_scale")`. This prevents it from being included in `state_dict` or `named_parameters()`, avoiding duplicate parameter tracking and potential issues during checkpoint saving.

```suggestion
            layer.weight_scale_inv = Parameter(
                scale.transpose(0, 1), requires_grad=False
            )
            delattr(layer, "weight_scale")
```
