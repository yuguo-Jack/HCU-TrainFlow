# [Fix] Select the earliest completing literal stop in speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/42360) · state: closed · merged: False

## Original PR description

## Motivation

Literal stop-string selection depends on configured list order when speculative
decoding accepts multiple tokens. For stop `["XY", "STOP"]` and a chunk decoding
to `kSTOPXY`, the current code selects `XY` and emits `kSTOP`, while one-token
steps stop at `STOP` and emit `k`.

## Modifications

Choose the matching literal stop with the earliest token-completion boundary,
using the existing bounded locator. Keep configured list priority when multiple
stops first appear in the same token. Preserve one-token short-circuit behavior,
decoded-text fallback, regex selection, and EOS/grammar/length priority.

The existing CPU regression file compares chunked and sequential completion,
finished lengths, token IDs through the stop, and actual detokenizer trimming.
It also guards same-token ties and a single decode on the one-token path.

## Speed Tests and Profiling

No GPU or performance claim. Multi-token matching can run the bounded locator
once per matching stop candidate, causing additional prefix decodes. Single-token
matching still decodes once.
Existing decode-window/context-sensitive-tokenizer limitations are unchanged.
