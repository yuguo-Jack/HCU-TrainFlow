# [Fix] mamba: Keep chunked prefill cuts on the mamba chunk grid

## AITER prerequisites

None. The chunk alignment is in the SGLang scheduler. This change does not call an AITER kernel.

## Motivation

With the mamba extra buffer, a hybrid model can only save a state checkpoint at a depth that is both on the radix page grid and a whole number of kernel chunks from the start of the extend. Chunked prefill can cut a request at any length. After one cut that is not chunk-aligned, every later chunk of that request is off the grid, so the request saves no more checkpoints and later turns miss the prefix cache.

## Modifications

- Round a chunked-prefill cut down to the mamba chunk size when the mamba extra buffer is on.
- Leave the last chunk of a request as is, and keep a cut that would round to zero.
- Add the chunk size to the scheduler's truncation alignment, using the LCM with any existing alignment.
- Add unit tests for the rounding and for a request cut into uneven chunks.

## Speed Tests and Profiling

Result: the prefix cache hit rate rises from 68.6% to 79.6%. The ideal for this workload is about 82%: the first prompt in each group and the 1024-token question in every prompt cannot hit. Mean TTFT is 32% lower and median TTFT 58% lower. TPOT does not change.

MI355X x8, `/data/models/Kimi-K3-Quark-MXFP4-AttnFP8`, AITER [`yuychang/aiter@b9229988f`](https://github.com/yuychang/aiter/commit/b9229988f) (the bench AITER build; this scheduler change does not depend on an AITER pull request). Server flags follow the cookbook MI355X cell: TP8, `--dcp-size 8 --dcp-comm-backend a2a`, AITER prefill and decode attention, FP8 KV cache, radix cache on. Workload: `sglang.benchmark.serving --dataset-name generated-shared-prefix`, 32 groups x 8 prompts, 16384-token shared prefix, 1024-token question, 256 output tokens, concurrency 16, `--chunked-prefill-size 8192`. The cache was warmed with a different seed and flushed before the measured run. Both sides set `SGLANG_AITER_FP8_PREFILL_ATTN=0`: on `main`, the 12-head FP8 PS prefill (`_mla_fp8_prefill_attn_ps`) tries to allocate about 1.2 TiB for a cached prefix with DCP8 and runs out of memory. That bug is unrelated to this PR. The 16K prefix and the 8K chunk size make every prompt span several chunks, which is the case this PR changes.
