# [Fix] [NPU] DSA: Correct DSA Models Sparse offload index-cache budgeting

[Upstream PR](https://github.com/sgl-project/sglang/pull/45302) · state: closed · merged: True

## Original PR description

## Summary

Fix NPU sparse KV offload memory estimation for models with shared Top-K layers. Compact allocation already stores index-K only for indexer-owner layers (#44436), but the offload estimator still charges every layer. Count local owner layers using the existing compaction guard, preserving dense and draft-worker fallback.

The NPU sparse KV offload path uses NPUMLATokenToKVPool and a separate SparseKVCacheManager for the MLA KV buffers. Because its pool layout and memory accounting differ from the regular path, it has a separate cell-size calculation that returns before the existing indexer sizing logic. This change fixes the indexer layer count in that offload-specific calculation.

## How the estimate affects serving

The offload estimate becomes `self._cell_size`, the bytes charged per token. [Pool sizing](https://github.com/sgl-project/sglang/blob/f6f4a42d3d5e7212a2fed9a4d70aeec6e2c7bde9/python/sglang/srt/model_executor/pool_configurator.py#L636-L646) computes:

```python
available_bytes = max(available_bytes - self._fixed_overhead_bytes, 0)
max_total_num_tokens = (
    available_bytes // self._cell_size
    if self._cell_size
    else self._zero_kv_max_tokens
)
max_total_num_tokens = max_total_num_tokens // page_size * page_size
```

Overestimating bytes per token produces an unnecessarily small token pool. [Request-length limits](https://github.com/sgl-project/sglang/blob/f6f4a42d3d5e7212a2fed9a4d70aeec6e2c7bde9/python/sglang/srt/managers/tp_worker.py#L568-L572) also depend on that capacity:

```python
max_req_len = min(
    self.model_config.context_len - 1,
    kv_capacity - 1,
)
max_req_input_len = max_req_len - 5
```

For concurrent requests, the pool must hold their combined token histories; without shared prefixes, its approximate concurrency ceiling is `token capacity / tokens per request`, with additional headroom needed for generation.

## Validation and impact

A3 and A5 GLM-5.2 config-only NPU pool tests passed with BF16 index-K and page size 64:

- Per-token charge: **19,968 → 5,376 bytes** (78 layers → 21 owners).
- At a **512 MiB index budget**, automatic capacity: **26,880 → 99,840 tokens (3.71x)**. The larger candidate pool allocates successfully; dummy-page padding is additional to the per-token accounting budget.
- At a fixed **16,384 tokens**, both versions retain the same 21-owner layout and **88,424,448-byte tensor footprint**. Boundary read/write checks pass. Static checks also pass.

The change recovers index capacity previously left unused by the overestimate. It can allow longer requests or more concurrent long-context requests when token capacity is the bottleneck. It does not change Top-K computation or the per-request resident KV window, and it does not reduce HBM at a fixed token capacity.

These tests load no model weights and do not run a serving workload. End-to-end concurrency and throughput gains are not measured; request-slot limits, resident KV buffers, DRAM, MTP and runtime memory can impose other limits.

File: `python/sglang/srt/hardware_backend/npu/sparsity_driven_kv_offload/config.py` · line 99

The extra branch is for the existing NPU sparse KV offload pool layout: its token-based device pool is sized for index-K, while the MLA KV host and sparse device buffers are managed separately. The regular path accounts for both MLA KV and index-K, so its full cell-size calculation cannot be used unchanged.

That said, the number of indexer-owning layers is model-dependent rather than NPU-specific. The current offload path returns before the existing layer-count logic, which is why this PR duplicates it. We can extract the layer-count calculation into a shared helper, while keeping the pool-specific byte calculations separate.
