# [Fix] rust-server: Drop the fixed 64-item multimodal cap in favor of --limit-mm-data-per-request

[Upstream PR](https://github.com/sgl-project/sglang/pull/45432) · state: closed · merged: True

## Original PR description

## Motivation

The Rust frontend rejected any multimodal request carrying more than 64 media items (`MAX_ITEMS_PER_REQUEST` in `sglang-mm`), in both the prefetch layer and the driver. The Python frontend has no such fixed cap: the only per-request count limit it applies is the operator's `--limit-mm-data-per-request`, checked per modality in `TokenizerManager._validate_mm_limits`. A request with, say, 80 small images is served by the Python path and 400'd by the Rust path, with an error message no Python server produces.

The per-modality check also differed from Python in a detail that shows when several modalities are over their limit at once: Python iterates `--limit-mm-data-per-request` in its configured order and reports the first modality exceeded, while the Rust side iterated a fixed image/video/audio order.

## Modifications

- `sglang-mm` driver: remove `MAX_ITEMS_PER_REQUEST` and its check. The per-request byte budget (`MAX_REQUEST_BYTES`, 1.25 GiB) and the per-stream fetch cap stay as the memory bounds, so a request of any item count is still bounded in bytes. The README sentence describing the budgets is updated.
- `sglang-server` prefetch: drop the item-count rejection; apply `--limit-mm-data-per-request` in its configured order with Python's message (`"<Modality> count N exceeds limit M per request."`), still before a single byte is fetched. Unset means no per-modality limit.
- `ServerArgs.limit_mm_data_per_request` becomes `Vec<(String, usize)>` so the configured order survives the Python -> Rust handoff; `rust_server/config.py` passes `list(dict.items())`. `CoreConfig`/`CoreInner::mm_limits` and the test helpers follow the new type.
- Tests: the driver test now asserts that 100 images process in full while the byte budget still rejects; prefetch tests cover 200 local sources without a limit, the first-over-limit-in-configured-order message, the at-limit pass-through, and the Python unit test pins that the launcher forwards an unset limit as `[]` and a set one in its configured order.

No server behaviour changes for requests under 64 items with a single modality limit; `/server_info` output is unchanged (`ServerArgs` is not serialized).
