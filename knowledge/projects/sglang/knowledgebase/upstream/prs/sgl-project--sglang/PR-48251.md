# [Perf] qsa: 64 CTAs per row for the mid-batch indexer decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/48251) · state: open · merged: False

## Original PR description


## Motivation

`tilelang_qsa_mqa_decode` (the QSA indexer's decode scoring) launches a fixed number of CTAs per query row. A row's CTAs stride over its 64-key groups, so each CTA scores about `groups / ctas` of them back to back. `_decode_ctas_per_row` picks the count for about four waves:
- 256 CTAs per row below `4 * SMs / 16` rows;
- 16 between `4 * SMs / 16` and `4 * SMs` rows;
- 1 above.

On a 152-SM GPU the middle level covers 38-607 rows, which is the usual batch range for long-context decode and MTP verify. There, 16 CTAs per row leave each CTA a long serial walk at long contexts. With an 85K context, one CTA scores about 20 groups in sequence. The grid is large enough, but each CTA's serial work dominates.

## Modifications

- `python/sglang/srt/layers/attention/qsa/mqa.py`: `_decode_ctas_per_row` keeps the row thresholds and the 256 / 1 levels and raises the middle level from 16 to 64. The levels stay three values, so the number of TileLang specializations is unchanged.
- `test/registered/kernels/ops/attention/qsa/test_qsa_indexer.py`:
  - `test_decode_ctas_per_row_by_row_count` pins the rule on a 152-SM device;
  - `test_tilelang_mqa_decode_ctas_per_row_bitwise` (bf16 and fp8 cache) checks that the logits are bit-identical at every level. Each group is scored by exactly one CTA with the same instructions; only the CTA that owns it changes.
  - The docstring of `test_tilelang_mqa_decode_grid_covers_every_group` is updated to the new levels.

## Accuracy Tests

The logits are bit-identical for every CTAs-per-row level:
- `test_tilelang_mqa_decode_ctas_per_row_bitwise` passes for bf16 and fp8 on GB200, H100 and RTX PRO 6000;
- the benchmark below compares the logits across CTA counts at every scored shape it times, with no mismatch.

So model outputs are unchanged by construction.

End-to-end on `nvidia/Qwen3.8-Flash-Next-NVFP4`, 1x GB200, main and this PR on the same node and container:
```bash
python3 -m sglang.launch_server --model-path nvidia/Qwen3.8-Flash-Next-NVFP4 --tp-size 1 \
  --mem-fraction-static 0.80 --mamba-ssm-dtype bfloat16 --chunked-prefill-size 4096 \
  --enable-deterministic-inference --attention-backend flashinfer \
  --speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4
```
- 4 text prompts (one of about 6,000 words) and 4 image chats, greedy, 96 new tokens, each sent twice: **16/16 outputs identical** to main.
- 48 concurrent greedy requests with 6,000-token prompts (192 decode-verify rows, so the 64-CTA level is used; a temporary log line confirmed it for 40-192-row batches), 64 new tokens: **48/48 identical** to main. A second identical pass is answered from the prefix cache, and there even main differs from its own first pass (34/48), so only the first pass is compared.

The upstream e2e test `test/registered/e2e/models/test_qwen4_exp_models.py` (TP4, gsm8k 200 via `sgl-eval`) passes on GB200 with this PR: base 0.980 (main 0.970), MTP 0.975 (main 0.975).

## Speed Tests and Profiling

Kernel time of `tilelang_qsa_mqa_decode` at the Qwen3.8-Flash-Next indexer shape:
- 4 query heads padded to 8, head dim 128, bf16 compressed keys, 16 compressed keys per page;
- one row per request, context lengths uniform in [ctx/2, ctx), `min_scored_len=512`.

Timing is `sglang.kernels.jit.benchmark.marker.do_bench` with a cold L2 (200 iterations, median), median of 3 runs. Same GPU, same process; the kernel is the same and only the launch grid differs. Main picks 16 CTAs per row at these row counts; this PR picks 64. Rows below the threshold (8, 32) keep 256 and are unchanged.

The rule only sees the row count: in CUDA-graph mode the context length is not known on the host. So the trade-off is the one in the tables. From 32K up it is faster everywhere measured. At 8K and 512 rows it is 4-6 µs slower. Below 2048 tokens every row skips scoring (`min_scored_len`), and the extra CTAs cost a few µs of launch overhead (+14 µs at 512 rows on the RTX PRO 6000).

End-to-end serving (1x GB200, `nvidia/Qwen3.8-Flash-Next-NVFP4`, TP1, `--mem-fraction-static 0.85 --mamba-ssm-dtype bfloat16 --max-running-requests 64`, NEXTN MTP 3/1/4, CUDA graphs on; launches in the order main, PR, main on one node):
```bash
python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-input-len 16000 \
  --random-output-len 256 --random-range-ratio 1.0 --num-prompts 96 --max-concurrency 48 --seed 1 --warmup-requests 4
```

| Launch | Output tok/s | Median TPOT ms | Median TTFT ms |
|---|---|---|---|
| main (1st, cold JIT caches) | 467.1 | 43.82 | 9950 |
| this PR | 634.6 | 43.69 | 6561 |
| main (2nd) | 634.5 | 44.36 | 6367 |

At this 16K context the indexer decode is a small part of the step, and the difference is within launch-to-launch noise, so no end-to-end speedup is claimed. The gain is at the kernel level, and grows with context length (tables above).

#48250 adds a CUDA kernel for bf16 indexer decode scoring on SM100, SM103 and SM120. Once both land, this launch rule matters on those GPUs only for calls that kernel does not cover (fp8 indexer cache, other shapes), and for every call on other GPUs such as H100.
