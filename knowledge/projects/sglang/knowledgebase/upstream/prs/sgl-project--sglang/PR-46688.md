# [CI] [AMD] test: Register 36 portable unit tests for AMD CI

[Upstream PR](https://github.com/sgl-project/sglang/pull/46688) · state: open · merged: False

## Original PR description

## What

Adds `register_amd_ci(...)` to 36 test files that are registered for CUDA only but have nothing NVIDIA-specific in them. Each file goes to the AMD suite that matches its CUDA cadence:

| CUDA registration | AMD suite | Files |
|---|---|---:|
| `base-b`, `1-gpu-small` | `stage-b-test-1-gpu-small-amd` | 29 |
| `extra-a`, `1-gpu-small` | `extra-a-test-1-gpu-small-amd` | 5 |
| `base-b-kernel-unit`, `1-gpu-small` | `jit-kernel-unit-test-amd` | 2 |

## Why

These are unit and kernel tests for Triton kernels (dspark/eagle speculative, mamba slot and state scatter, boundary KV fix, unified MLA block table), plain torch logic (allocators, unified-pool compaction, HiCache write-back ordering, D2H copy worker, custom-op dispatch), or server-arg resolution. None of them pins FA3/FA4/FlashInfer/TRT-LLM, needs an NVIDIA compute capability, or imports a CUDA-only library. Their GPU cases only check `torch.cuda.is_available()`, which is true on ROCm. Several already run on CPU or XPU too.

No test code changes, only registrations. The est_time values are copied from the CUDA registrations.

## Runtime

Measured on MI300 in the validation run below (wall time per file, including process start):

| AMD suite | Files | Added time | Per job |
|---|---:|---:|---|
| `stage-b-test-1-gpu-small-amd` | 29 | 426 s | ~53 s per partition across 8; partitions took 11-39 min in this run |
| `extra-a-test-1-gpu-small-amd` | 5 | 82 s | ~41 s per partition across 2 |
| `jit-kernel-unit-test-amd` | 2 | 29 s | single job, 19 min in this run |

Per file it is 7-28 s, median 14 s, close to the CUDA est_time (537 s measured vs 524 s estimated for all 36). The slowest are `test_unified_cache_linker.py` (28 s), `test_dspark_draft_graph.py` and `test_decode_retraction_backup.py` (22 s each).

## Test plan

- `collect_tests()` on the changed files picks up the AMD registrations in the three suites above.
- AMD run on MI300, rocm10, with `continue_on_error` so every file reports: https://github.com/sgl-project/sglang/actions/runs/40426038546. All 36 files pass. The extra-a files ran inside stage-b small on the validation branch, so the run didn't need the 2/4-GPU extra runners; the same container and 1-GPU runner either way.
- Same suites on the other two MI300 images, also with `continue_on_error`: rocm720 https://github.com/sgl-project/sglang/actions/runs/40456886259 and rocm724 https://github.com/sgl-project/sglang/actions/runs/40456889434. All 36 files pass on both. The jobs that failed there did so on files this PR doesn't touch: `test_torch_compile_moe.py` and `test_openai_server.py` on both, and `test_fp8_moe_triton_runner_with_aiter.py` on rocm720.
- The rocm10 run had 3 more files that fail on ROCm, so they are not in this PR:
  - `unit/utils/test_weight_checker_comparator.py`: the UE8M0 case calls `transform_scale_ue8m0`, which imports `deep_gemm`.
  - `unit/model_executor/test_resolve_sliding_window_size.py`: imports `models/inkling`, which pulls in the CuTe-DSL flash_attn (`cutlass`).
  - `kernels/ops/moe/test_gemma4_fused_routing.py`: 46/47 pass, but `test_scale_applied` is off from the reference by up to 0.156 (2 of 32 weights). Worth a separate look.
- The other failure in the rocm10 run, `openai_server/basic/test_openai_server.py`, is an existing AMD registration and not touched here.
