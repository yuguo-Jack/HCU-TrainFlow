# [Feat] [AMD] mori: add XGMI data plane for single-node PD

[Upstream PR](https://github.com/sgl-project/sglang/pull/46733) · state: open · merged: False

## Original PR description

## Motivation

The MoRI PD connector always creates the MoRI-IO RDMA backend. On a single node whose NICs are not cabled (or that has
none), prefill and decode therefore cannot use MoRI at all, although MoRI-IO also ships an XGMI backend that moves KV
with GPU peer copies over XGMI. Single-node PD (for example 1P1D, or 2P1D with length-based prefill pools) is useful on
such nodes to keep long prefills from interfering with decode.

## Modifications

`SGLANG_MORI_BACKEND` (default `rdma`, so nothing changes unless it is set) selects the IOEngine data plane of
`--disaggregation-transfer-backend mori`:

- `xgmi` creates `BackendType.XGMI` with `XgmiBackendConfig()`. The XGMI engine binds no port, so it returns before the
  RDMA port check. `XgmiBackendConfig` is imported only on this path, so the RDMA path needs nothing new from MoRI.
- AUX data is CPU-resident, so with `xgmi` it always goes over TCP (`SGLANG_MORI_SEND_AUX_RDMA` applies to `rdma` only).
- An unknown value fails before the engine is created.
- Both roles must see the same `HIP_VISIBLE_DEVICES` list and pick their GPUs with `--base-gpu-id`, so a device id in a
  memory descriptor names the same GPU in both processes. Documented in `environ.py` and
  `docs/docs/references/environment_variables.mdx`.

The knob name matches `SGLANG_MORI_BACKEND` (`rdma` | `fabric`) in #44283, so whichever lands second only adds its
value to the same switch.

Example (one node, prefill on GPUs 0-1, decode on GPUs 2-3):

```bash
export SGLANG_MORI_BACKEND=xgmi HIP_VISIBLE_DEVICES=0,1,2,3
python -m sglang.launch_server --model-path <model> --tp 2 --base-gpu-id 0 --port 30000 \
  --disaggregation-mode prefill --disaggregation-transfer-backend mori --disaggregation-bootstrap-port 8998
python -m sglang.launch_server --model-path <model> --tp 2 --base-gpu-id 2 --port 30001 \
  --disaggregation-mode decode --disaggregation-transfer-backend mori
```

## Accuracy Tests

8x MI308X (gfx942), NICs down (no RDMA), MoRI 1.2.3.post1, DeepSeek-V4-Flash (FP8 per-channel checkpoint), TP2 per
server, DSpark on. 2P1D: prefill GPUs 0-1 and 2-3, decode GPUs 4-5, all with `HIP_VISIBLE_DEVICES=0,1,2,3,4,5`.
The checkpoint needs gfx942 loader fixes that are not on main yet, so the end-to-end run used this same patch on a
v0.5.19-based tree; on main the change is covered by the unit tests below.

| | result |
|---|---|
| gsm8k (8-shot, 200 questions, greedy) | 0.91 / 0.925 (two router policies) |
| needle in a haystack, 8K-60K tokens | 12/12 |
| transfer / server errors | 0 |

Earlier 1P1D runs with the same change: gsm8k 1319 0.910 vs 0.907 aggregated, TTFT +1-2 % from the transfer.

Unit tests (`test/registered/amd/disaggregation/test_mori_backend_basic.py`, 8 passed on main; the 2 new ones fail
without this change): xgmi creates the XGMI backend although the engine binds no port; unknown values are rejected.

## Speed Tests and Profiling

Not a kernel change. Standalone MoRI-IO XGMI writes reached 48 GB/s on this node.
