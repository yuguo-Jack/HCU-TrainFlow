# [Perf] [NVIDIA] mega_moe: Count EPLB load in-kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47643) · state: open · merged: False

## Original PR description

## Motivation

With EPLB recording on, each MegaMoE layer launches a separate histogram kernel over the gate's physical top-k ids to feed the expert distribution recorder. On a DeepSeek-V4.1 DEP16 decode step this is one extra launch per MoE layer, about 0.16 ms per step at 40 requests per rank.

DeepGEMM's `fp8_fp4_mega_moe` already counts, per local expert, the rows each expert receives (`cumulative_local_expert_recv_stats`, int32, one entry per local expert, accumulated). The pinned `sgl-deep-gemm==0.2.3.post2` exposes it. The histogram therefore repeats work the kernel already does.

## Modifications

The change applies when all of these hold:
- the layer runs SM100 `fp8xfp4` MegaMoE with no fused shared experts (`num_fused_shared_experts == 0`);
- the new `ExpertDistributionRecorder.get_current_pass_local_count_buffer(num_experts, ep_rank, ep_size)` returns this rank's slice of the current layer's physical count row. It returns `None` without a current layer, without the select-experts gatherer, when neither recording nor a CUDA graph capture is on (the same gate as the histogram it replaces), or when the row width differs from the layer's expert count. The no-op recorder always returns `None`.

In that case `forward_mega_moe` passes that slice as `cumulative_local_expert_recv_stats`, and runs the routing inside `disable_this_region()`. Neither the MegaGate in-buffer path nor the regular top-k fallback can then count the picks a second time. Ranks with no local tokens also pass the row: they still receive, and count, other ranks' rows.

Counts are now kept per destination rank instead of per source rank. Physical expert ids are rank-major, so the cross-rank sum gives the same physical loads.
- **`per_pass` dumps change:** each rank's row now holds the rows its experts received, not the picks it sent.
- **Padding:** padded rows (top-k id -1) are never dispatched, so they are not counted.

Where the change does not apply, the router histogram is kept and behaviour is unchanged. The only addition is one recorder lookup per layer on the host.
- **No current layer:** the recorder has no row to hand out. This happens in the DeepSeek-V4 NextN draft, and in prefill under piecewise CUDA graphs.
- **Fused shared experts:** these use the 256+EP per-rank shared-expert slot layout. Those slots are not EPLB experts, so mapping the kernel's per-slot counts would need a separate translation, which this PR does not attempt.
- **Other cases:** recording off, SM90, and other MMA types.

Routed-experts capture does not need a fallback: the kernel row is passed on every routing path, and the experts capturer is not gated by `disable_this_region()`.

The DeepSeek-V4.1 MegaMoE deployment keeps the shared expert in the kernel's own shared weights (`num_fused_shared_experts == 0`), so it takes the new path.

## Accuracy Tests

No numerical change to model outputs: only where the EPLB statistics are counted changes.

- **EP4 equality on 4 GB300 GPUs, through `forward_mega_moe` and the recorder's slice method at this PR's head.** A stand-in recorder adds a real histogram (`record_physical_counts`) into the same count row whenever it is asked to, unless a `disable_this_region()` is active, as the real recorder does. The check is: received counts summed over ranks == histogram of every rank's own top-k ids, summed over ranks.

  | per-rank routing | rows / padded | counted vs histogram | histogram calls |
  |---|---|---|---|
  | all MegaGate in-buffer | 240 / 17 | 10,704 = 10,704 | 0 |
  | one rank with zero local tokens, rest MegaGate | 384 / 5 | 13,644 = 13,644 | 0 |
  | mixed: zero tokens / top-k fallback / MegaGate / MegaGate | 960 / 40 | 33,120 = 33,120 | 0 |
  | all top-k fallback | 1152 / 0 | 55,296 = 55,296 | 0 |
  | no current layer (recorder returns the whole table) | 384 / 5 | 13,644 = 13,644 | 6 (histogram fallback) |
  | recording off | 240 / 0 | nothing counted | 0 |

  - **Routed-experts capture on:** the same six cases, with the gate returning the out-of-buffer routing it produces under capture (`mega_gate.py:206`), give the same counts as above in every case, with no histogram calls in the four counted cases.
  - **Negative control:** with `disable_this_region()` made a no-op (capture on), the four counted cases double count (for example 21,408 vs 10,704). The no-layer and recording-off cases are unchanged.
  - **Idle ranks:** an earlier variant passed the stats only on the MegaGate in-buffer path. It failed the zero-token case (5,690 vs 13,644) and the mixed case (15,346 vs 33,120). A rank without local tokens still receives other ranks' rows, so it must count them.
- **EPLB still converges:** in a DEP16 decode run with the earlier in-buffer-only form, every rebalance (every 15000 steps) reaches window balancedness 0.89-0.90. Balancedness is mean over max of the per-rank loads summed over the window, per layer.

## Benchmarking and Profiling

The workload is DeepSeek-V4.1-Flash, PD-disaggregated, with DEP16 decode. Decode runs at most 40 requests per rank (35.5 mean), with simulated acceptance length 3.51 and agentic traces. The comparison is against the same image without the change. The "this PR" row is this PR's code applied to that image.

| | decode step p50, 32-47 running | decode step p50, 16-31 running | client throughput / GPU (steady window) |
|---|---|---|---|
| base | 14.1 ms | 13.5 ms | 1.000x |
| this PR | 13.9 ms | 13.4 ms | 1.006x (within run-to-run noise) |

- The step saving matches the removed histogram launches (~0.16 ms per step in a profile at this shape).
- In this configuration, client throughput is flat within noise.
- An earlier in-buffer-only form gave the same step and throughput.
- No errors in the run.
- Both runs used the deployment above (`num_fused_shared_experts == 0`, layer index always set in the target model), where this PR's final form takes the same path as the measured form.
