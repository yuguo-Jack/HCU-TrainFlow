## Motivation

Prefix sharing creates a scheduling trade-off: cache-cold requests with the same prefix can duplicate prefill work when admitted together, while delaying related requests too long risks losing reusable KV states to eviction. Repeated full-queue prefix matching and sorting can also offset the computation saved through reuse under high concurrency.

This PR adds `prefix-weave`, a scheduling policy that balances cached-prefix reuse and in-batch overlap while limiting repeated scheduling work, targeting repeated prompts and multi-turn conversations.

## Modifications

- Add `--schedule-policy prefix-weave` and document the policy in the server arguments and tuning guides.
- Implement adaptive tier ordering based on global-cache hit ratio and prefix overlap within the candidate batch, with cached-prefix length as the within-tier ordering key.
- Bound tier assignment with a token budget derived from the prefill configuration. Use the remaining request/token admission budget after chunked-prefill handling to skip reclassification when previously classified requests already cover the next admission.
- Record completed sequence lengths by routing key and use them to estimate prefix reuse for subsequent turns. Remove admitted requests from the retained classification set.
- Add unit coverage for tier precedence, classification reuse, and cross-turn prefix estimates; update affected test fixtures for the scheduler integration.

## Speed Tests and Profiling

Environment:

- Revision: `4080e3f59a`
- Model: `Meta-Llama-3.1-8B`
- Hardware: 4 × NVIDIA H20-3e; four concurrent TP=1 servers, one policy per GPU
- Policies: `fcfs`, `lpm`, `dfs-weight`, `prefix-weave`
- Server: memory fraction 0.85; max running requests 1,024; overlap scheduling disabled
- Client settings: same host as the servers; streaming; unlimited request rate; seed 1
- 500 warmup requests; cache flushed before each measured run; workloads run serially per server
- One run per workload and policy

Benchmarks used a custom client adapted from SGLang’s `bench_serving.py` to support repeated single-turn requests and sequential multi-turn session replay. All policies used the same client, source datasets, and generation settings.

Workloads:

| Workload                 | Shape                       | Completed requests |           Input tokens | Output tokens | Client concurrency limit |
| ------------------------ | --------------------------- | -----------------: | ---------------------: | ------------: | ------------------------ |
| MMLU-Pro 5-shot `aabb` | 4,096 prompts × 8 replicas |             32,768 |             36,969,736 |       196,608 | 4,096                    |
| MMLU-Pro 5-shot `abab` | 4,096 prompts × 8 replicas |             32,768 |             36,969,736 |       196,608 | unlimited                |
| BFCL multi-turn          | 5,106 sessions              |             17,029 | 94,413,028 (estimated) |     1,100,424 | unlimited                |

`aabb` groups eight replicas of each prompt together; `abab` interleaves replicas across prompts. Both use five-shot prompts and average 6 output tokens per request. BFCL submits each turn after the previous turn completes, including the generated conversation history.

Results (request throughput):

| Workload                 | FCFS req/s | LPM req/s | DFS-weight req/s | PrefixWeave req/s | Speedup vs FCFS | Speedup vs fastest existing policy |
| ------------------------ | ---------: | --------: | ---------------: | ----------------: | --------------: | ---------------------------------- |
| MMLU-Pro 5-shot `aabb` |     37.171 |    37.229 |           31.367 |           119.455 |          3.21× | 3.21× (lpm)                       |
| MMLU-Pro 5-shot `abab` |     12.803 |    12.841 |           38.919 |           100.898 |          7.88× | 2.59× (dfs-weight)                |
| BFCL multi-turn          |      2.981 |     3.189 |            4.203 |             6.971 |          2.34× | 1.66× (dfs-weight)                |

Speedup is baseline duration / PrefixWeave duration. LPM retains its default FCFS fallback for waiting queues above 128 requests.

Latency versus FCFS (seconds; BFCL values are per turn):

| Workload                 | Policy           | Mean TTFT |  P99 TTFT |  Mean E2E |   P99 E2E |
| ------------------------ | ---------------- | --------: | --------: | --------: | --------: |
| MMLU-Pro 5-shot `aabb` | `fcfs`         |    90.647 |   110.554 |   104.803 |   116.030 |
| MMLU-Pro 5-shot `aabb` | `prefix-weave` |    28.153 |   141.528 |    32.654 |   145.003 |
| MMLU-Pro 5-shot `abab` | `fcfs`         | 1,287.281 | 2,523.791 | 1,326.719 | 2,549.735 |
| MMLU-Pro 5-shot `abab` | `prefix-weave` |   177.742 |   317.634 |   181.535 |   320.884 |
| BFCL multi-turn          | `fcfs`         |   221.030 |   461.066 |   299.162 |   649.147 |
| BFCL multi-turn          | `prefix-weave` |   141.765 | 1,296.367 |   184.112 | 1,338.706 |

PrefixWeave improves throughput by **3.21×, 2.59×, and 1.66× over the fastest existing policy**, respectively. Mean TTFT and E2E latency improve versus FCFS, but P99 E2E increases by **25.0% on `aabb` and 106.2% on BFCL**. These single-run results cover saturated, prefix-heavy workloads with overlap disabled.

Scheduler profiling (server counters):

| Workload                 | FCFS cached-input ratio | PrefixWeave cached-input ratio | Scheduler time (s) | Scheduler time / duration |
| ------------------------ | ----------------------: | -----------------------------: | ------------------: | ------------------------: |
| MMLU-Pro 5-shot `aabb` |                  79.66% |                         95.49% |              19.033 |                     6.94% |
| MMLU-Pro 5-shot `abab` |                  37.86% |                         95.29% |              47.478 |                    14.62% |
| BFCL multi-turn          |                  60.16% |                         87.00% |             140.036 |                     5.73% |

Cached-input ratio is cached tokens / input tokens. Scheduler time measures the instrumented scheduling calculation path; the final column divides it by run duration. No profiler trace is included.
