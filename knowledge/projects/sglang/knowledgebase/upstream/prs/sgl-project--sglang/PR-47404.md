# [Fix] moe: Reuse one FlashInfer MXFP4 CUTLASS MoE workspace per stream

[Upstream PR](https://github.com/sgl-project/sglang/pull/47404) · state: open · merged: False

## Original PR description

## Motivation

`flashinfer.fused_moe.cutlass_fused_moe` allocates its workspace with `torch.empty` and frees it on every call unless the caller passes `workspace_buffer`. FlashInfer documents the opt-in: query `cutlass_fused_moe_workspace_size`, allocate one buffer per CUDA stream, and pass it on every call. The MXFP4 CUTLASS runner (`_fused_experts_flashinfer_mxfp4_cutlass`) does not pass one. Each call's scratch is sized by its token count. For DeepSeek-V4.1-Flash at TP4/EP2, an 8192-token prefill chunk allocated 980 MiB per MoE call, as the size in the caching allocator's log shows. Chunks of different sizes therefore leave differently sized blocks of about 1 GiB in the caching allocator, and these compete with the rest of the forward's working set.

This PR covers the MXFP4 runner, the path measured here. The ModelOpt FP8/NVFP4/BF16 runner (`_run_flashinfer_cutlass`) calls the same kernel and could take the same helper in a follow-up.

## Modifications

- `_mxfp4_moe_workspace(...)` returns one workspace per `(device index, CUDA stream)`. Layers on a stream run one at a time, so they share it.
  - **Size.** The required size comes from `cutlass_fused_moe_workspace_size` at `max(rows, tune_max_num_tokens)`, called with the layer's own arguments: hidden size, unpacked FP4 intermediate size, global expert count, top-k, input, weight and output dtypes, activation, TP/EP layout, scaling mode, fused finalize and humming. The size is memoized per argument set (`lru_cache(maxsize=64)`).
  - **Reuse.** The buffer is reused while it is at least the current call's size. Sizing at the tuning bound means a server whose chunks never reach the bound still holds the bound's size, about 1 GiB per device and stream for the shapes above. In return, the buffer does not grow chunk by chunk.
  - **Growth.** When a call needs more, the smaller buffer is released before the larger one is allocated. `torch.cuda.empty_cache()` runs first only if `mem_get_info` shows that the driver cannot supply the new size; otherwise the cache is left alone. This is a heuristic: driver free memory leaves out the allocator's cached blocks. `empty_cache` is process-wide; SGLang runs one GPU per process.
- The function returns `None`, so FlashInfer allocates per call as on main, in these cases:
  - under CUDA graph capture, where the call's own allocation belongs to the graph's pool
  - while `torch.compiler.is_compiling()`
  - for a non-CUDA input
  - once workspaces are off
- **Workspaces turn off** for the process, with a warning, in three cases:
  - Setting the workspace up fails, for example on a FlashInfer without `cutlass_fused_moe_workspace_size`.
  - The buffer allocation raises `torch.OutOfMemoryError`. Without the off switch, every later call would retry the allocation.
  - FlashInfer raises `workspace_buffer too small`, meaning a size query disagrees with the kernel's own accounting. `_run_with_mxfp4_moe_workspace` then drops every held buffer, releases the rejected one, and reruns the call with per-call scratch. In FlashInfer 0.7.2 the binding checks the size before `runMoe` launches the MoE kernels. Any other error propagates.
- The capture check, the free-memory check and the size query run under `torch.cuda.device(x.device)`.
- Kernels, tactics and arguments are otherwise unchanged; only where the scratch lives changes.

## Accuracy Tests

New CPU test `test/registered/unit/layers/moe/test_flashinfer_cutlass_moe_workspace.py`. It mocks FlashInfer's size query and the allocator, and checks:
- **Reuse and the query.** One buffer serves every call on a stream at or below the tuning bound, and the size is queried once. The query receives the bound, hidden size, unpacked intermediate size, global expert count, top-k, the three dtypes, the activation, the TP/EP ranks, the scaling flags, fused finalize, humming and the device. The scoped checks run on the input's device.
- **Cache purge.** The cache is emptied only when the driver lacks room.
- **Growth.** A larger call replaces the buffer, and the old buffer is released before the cache purge and the new allocation; later smaller calls reuse the larger buffer. A layer that needs more on the same stream grows the shared buffer, and the smaller layer then reuses it.
- **Streams.** A second stream gets its own buffer.
- **No buffer.** None is passed under capture, while compiling, for a CPU tensor, or once workspaces are off.
- **Failures.** An out-of-memory allocation turns workspaces off, and a failed setup runs the call with per-call scratch.
- **Rejected size.** A "too small" error releases the rejected buffer, reruns with per-call scratch and turns workspaces off. Other errors propagate, as does a "too small" error when no workspace was passed.
- **Call site.** `_fused_experts_flashinfer_mxfp4_cutlass`, with a stubbed FlashInfer, sizes the workspace from the call's input, `w2_weight`, top-k and output dtype, and passes the buffer as `workspace_buffer`.

The kernels and their inputs are unchanged apart from the scratch pointer. Outputs were not compared separately. With `SGLANG_FLASHINFER_MOE_FUSED_FINALIZE` on, the fused finalize is not bitwise deterministic from run to run in either case.

No GPU test is added. A real-kernel test at 1, 512 and 8192 tokens, asserting that FlashInfer accepts the queried size, would pin the size contract; I can add one if a GPU suite fits.

## Speed Tests and Profiling

Setup: 4x RTX PRO 6000 Blackwell (SM120), DeepSeek-V4.1-Flash, TP4/EP2 over PCIe, chunked prefill of 8192 tokens. The build we serve carries the first revision of this change: one buffer per stream, sized for the first layer at the tuning bound. DeepSeek-V4.1 has one MoE shape, so that revision and this one take the same path for it. The growth and fallback paths were not exercised on GPU.

The test was a load-plus-deep-prefill run: 8 decoding requests, then nine cold prompts of 106K to 491K tokens sent at once. Across 258 chunks, 8K chunks took 0.55 s median and 0.67 s at most, and the allocator logged no OOM retries. This was not benchmarked in isolation against main.
