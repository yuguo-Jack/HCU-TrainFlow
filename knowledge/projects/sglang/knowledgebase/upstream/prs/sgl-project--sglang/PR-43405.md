# [DSv41] Engram table backends: peer-visible device shards, host tables, a gather view

Depends on #41147 (uses its `sgl_kernel/logging.h` and unified `CHECK_CUDA`); the first three commits here belong to that PR.

## Motivation

`EngramEmbedding` decided storage, sharding and lookup inline: a device shard plus an all-reduce, or a host table in one of two hand-wired layouts. Peer-visible device shards (read in place, no lookup all-reduce) and VMM-backed host memory each need their own allocation and their own way of telling the lookup where the rows are. This PR moves that into table backends with one contract.

## Modifications

- `engram_table.py`: a `Table` owns its row range, weight / scale views and device addresses, and answers `gather_view()`: every shard's addresses when this rank can read the whole table in place, else `None` (final after `finish_load`).
  - `EngramTableLayout` names visibility: `full_shared` (the whole table is readable in place) or `row_sharded` (only the rank's rows; zero-fill + all-reduce lookup).
  - Device `full_shared` keeps the rank's hash-column shard in symmetric memory, every rank laying out the widest shard, and exchanges peer addresses in `finish_load`. Device `row_sharded` is the existing private shard and stays the default.
  - Host `full_shared` is one copy every rank maps (a world of one); host `row_sharded` is a private shard. Both default to memfd / anonymous mmap; `SGLANG_OPT_DSV41_ENGRAM_HOST_TABLE_VMM=1` backs them with CUDA VMM instead.
  - `column_shard` shards on hash-column boundaries, with the equal-row split when the columns do not divide.
- `engram_gather_bf16` (JIT): reads each token's 24 hash columns from the shard that owns them and dequantizes to bf16 (exact: e8m0 scales are powers of two). `EngramEmbedding` uses it for a multi-shard view and the existing Triton gather for a world of one.
- `VMMHostMemory` (JIT tvm-ffi object): host-NUMA `cuMemCreate` mapped with device and host read-write access, exportable as a POSIX fd; `fd_exchange` passes rank 0's fd to the others over a Unix socket (`SCM_RIGHTS`).
- `SGLANG_DSV41_ENGRAM_HOST_TABLE_LAYOUT=shared|per_rank` is renamed to `SGLANG_DSV41_ENGRAM_TABLE_LAYOUT=full_shared|row_sharded`; the old name is forwarded with a deprecation warning. Cookbook updated.

## Accuracy Tests

- `engram_gather_bf16` matches a CPU dequant reference bitwise with 1, 2 and 4 shards.
- Two ranks, ragged column shards, each rank loading only its own columns and gathering its own ids: device `full_shared` (symmetric memory, two-shard view) and host `full_shared` (world-of-one view) both match the reference bitwise; device and host `row_sharded` expose no view.
- On B300, gathers over `VMMHostMemory` and memfd host tables match the reference bitwise at 2 to 96 GB tables, and two processes sharing one VMM table through `fd_exchange` read identical rows.
- End-to-end with device `full_shared` is not run yet.

- adubkov · comment · 2026-10-09T23:41:40Z · [source](https://github.com/sgl-project/sglang/pull/43405#issuecomment-6091153744)

Reading `engram_table.py` at 7bdee4b — the `Table` Protocol already names the seam, which is great, but as drawn it structurally excludes the one backend a lot of us need. Four asks, all cheap while this is still a draft.

**1. `bytes: torch.Tensor` on the Protocol forecloses a file/bounded-cache backend.**

`_HostTableVMM.__init__` materialises it as `torch.frombuffer(ctypes.cast(self.device_ptr, POINTER(c_uint8 * raw_nbytes)).contents, dtype=torch.uint8)` — i.e. the Protocol requires a fully addressable, contiguous, eagerly-mapped buffer. A disk- or cache-backed table has no such thing: rows exist only when fetched, and the whole point of the tier is that the resident working set is a small fraction of the table. Today such a class cannot satisfy the declared attribute, so adding it later means changing the Protocol rather than adding an implementation.

Could `bytes` become optional (or be joined by a gather-shaped accessor), so a fourth backend can conform without editing the interface? The rest of the split — `_DeviceTable` / `_HostTableVMM` / `_HostTablePosix` — looks like exactly the right shape for that.

**2. `create_engram_table` selects on `use_host: bool` plus capability probes.**

`if use_host: if _is_cuda and not _is_hip and is_vmm_available(): ... return _HostTablePosix(...)` leaves no way to request a specific backend without editing this function. Selecting by name (with the current auto-probe as the default value) would keep this PR's behaviour identical byte-for-byte while making the enum extensible, and would also let a user force `_HostTablePosix` to A/B the VMM path on the same box — which we could not do with the memfd code.

**3. The construction contract isn't on the Protocol.**

`_DeviceTable.__init__(layout, nbytes)` vs the host tables' `(layout, nbytes, name, group)`, plus `assert layout == EngramTableLayout.ROW_SHARDED` inside `_DeviceTable`. Attributes and two methods are declared; what a backend must *accept* in its constructor isn't, so an outside implementation has to infer it from three call sites.

**4. Could the Protocol carry a `stats()`?**

Nothing in `engram_table.py` reports row-level hits/misses/evictions today. For host/VMM tables that's harmless — but the moment a tier has a bounded cache, its own hit rate is the only measurement that distinguishes "this tier is working" from "this tier is never exercised", and it's the number reviewers will ask for. @yunwei37's field evidence on vLLM#56757 is that the low-concurrency cost was the per-step host round trip and gather orchestration rather than local NVMe bandwidth; a counter-less tier can't show which side of that line a change lands on.

**Worth flagging for the VMM path — three things we learned the hard way on an analogous table.**

We run two single-GPU sglang replicas (2× RTX PRO 6000 Blackwell, TP1 each, PCIe, no NVLink, 244 GiB host RAM) sharing one physical copy of a **47.68 GiB FP8 PLE n-gram table** (`51,200,245,760 B`) as a tmpfs `MAP_SHARED` file with `cudaHostRegister` in each process. Same model family as the `qwen4_exp` ask in vLLM#56757, so the table shape is the same even though the model isn't DeepSeek. Result: replica `anon` drops from 53.35 GiB (private table) to ~6.0 GiB, host `available` 64 → 155 GiB, both replicas log the same inode, survives a cold reboot, `cudaHostRegister` 2.1 s with an exact pin count. The certified claim is memory, not throughput — our bench could not have seen a substrate difference (0.010 ms gather against an ~11 ms step).

Three traps that map onto this PR directly:

- **Registration needs a CPU-writable VMA.** A `:ro` bind fails (`HostRegisterReadOnlySupported=0`, `cudaErrorInvalidValue` / `OSError 30`). We register writable, then `mprotect(PROT_READ)` — if any of the "no host configuration" framing relies on read-only sharing, that's the case that fails.
- **`memory.stat unevictable` reads 0 with 47.7 GiB registered.** Driver-pinned pages are invisible to that cgroup counter, so it cannot be used to confirm a pin landed. Worth stating in the docs, because it's the intuitive check and it silently passes.
- **The cross-process refcount does hold.** Hard-`docker kill`ing the sibling after both registered left the survivor's gather rate unchanged (6.93 vs 6.61 GB/s pre-kill) and it finished its run — consistent with your "no keep-alive requirement" comment on closing both fds. One caveat on the same signature: `nr_foll_pin_acquired` is a *global* counter, so with N sharers `pin_pages` reads N× the per-table expectation. That's the sharing proof, not a bug, but it looks alarming in a log.

No urgency on any of 1–4 for this PR to be mergeable — raising them now only because the file is new, so the interface is still free to change. Happy to test a `disk`/cache-shaped backend against our pair if one lands.
