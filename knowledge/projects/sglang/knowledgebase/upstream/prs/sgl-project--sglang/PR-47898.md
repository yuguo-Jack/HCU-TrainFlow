# [Perf] [NVIDIA] fused-a-gemm: Relax the CuTe DSL kernel's K alignment from 1024 to 256

[Upstream PR](https://github.com/sgl-project/sglang/pull/47898) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #47712. On SM120 the fused-A GEMM `auto` backend is the CuTe DSL kernel, which asserts `K % 1024 == 0`. Since #47712 the eligibility check honours that, so DeepSeek-style MLA models with `hidden_size` 3584 or 2560 no longer crash, but they run `fused_qkv_a_proj_with_mqa` through the regular linear layer, which is 1.6-2x slower at decode batch sizes of 2-16 on an RTX 5090.

The kernel's K indexing does not need 1024. `_global_k_col` splits K into `SPLITK=4` contiguous chunks of `K/4` and walks each chunk in `TILE_K=256` steps (64 bf16 per warp per tile), so `K % 256 == 0` keeps every tile in bounds and every `cp.async` 16-byte aligned. That is the same requirement as the JIT kernel, and the existing kernel test already says `hd_in must be a multiple of 256`. The 1024 assert appears to come from the shapes the kernel was written for (6144, 7168).

## Modifications

- `python/sglang/kernels/ops/gemm/cutedsl_dsv3_fused_a_gemm.py`: assert `K % TILE_K == 0` (256) instead of `K % 1024 == 0`, and update the two docstrings.
- `python/sglang/kernels/ops/gemm/fused_a_gemm.py`: `_K_ALIGNMENT[CUTEDSL]` 1024 -> 256, so eligibility follows the kernel.
- `test/registered/kernels/ops/gemm/test_cutedsl_dsv3_fused_a_gemm.py`: add K=2560 and K=3584 (256- but not 1024-aligned). This test runs on the H100 runner, so it also covers the kernel on Hopper.
- `test/registered/kernels/ops/gemm/test_fused_a_gemm.py` (SM120 runner): K=3584 must now be eligible and the fused path must match `F.linear`; K=3200 (not 256-aligned) must still fall back. Drops the K=7168 case, which no longer guards anything the K=3584 case does not.
- `fused_a_gemm_weight_eligible` also requires `layer.bias is None`: the kernels compute `x @ weight.T` only, so a biased layer (e.g. a Nemotron-H `fc1_latent_proj` with `mlp_bias=True`) now keeps its own linear path instead of dropping its bias. `test_fused_a_gemm.py` covers a biased K=3584 layer.

Behavior:

| GPU | backend | K % 256 == 0, K % 1024 != 0 (e.g. 3584) | K % 1024 == 0 |
|---|---|---|---|
| non-SM120 | auto (-> JIT) | fused (unchanged) | fused (unchanged) |
| SM120 | auto (-> CuTe DSL) | **fused** (was: unfused fallback) | fused (unchanged) |
| any | explicit `cutedsl` | **fused** (was: unfused fallback) | fused (unchanged) |

Models whose `fused_qkv_a_proj_with_mqa` (deepseek_v2) or `fc1_latent_proj` (nemotron_h) has such a K are affected. The `q_b_proj` path is gated to K=2048 and is unchanged.

## Accuracy Tests

Not a numerics change for shapes that were already fused. For newly fused shapes the kernel matches `F.linear`'s error.

RTX 5090 (SM120), CUDA 13.0, PyTorch 2.14.1+cu130, nvidia-cutlass-dsl 4.8.0. Kernel sweep with the assert bypassed: K = 256..4096 in steps of 256, plus 5120, 6144, 7168, 8192; N in {2112, 2624}; M = 1..16. The weight and activation sit at the start of NaN-padded buffers, so any out-of-bounds read would show up as NaN. Every shape passed, with no NaN, and the kernel's max |err| against an fp32 reference was equal to or lower than `F.linear`'s on the same inputs. Excerpt (max over M = 1..16):

```

  K= 3328 N= 2112  max|kernel-ref|=0.4994  max|F.linear-ref|=0.5006  ok
  K= 3584 N= 2112  max|kernel-ref|=0.4991  max|F.linear-ref|=0.4991  ok
  K= 3584 N= 2624  max|kernel-ref|=0.9303  max|F.linear-ref|=0.9303  ok
  K= 7168 N= 2112  max|kernel-ref|=0.9935  max|F.linear-ref|=1.1640  ok  (already allowed)
```

Unit tests on the 5090 (`test_fused_a_gemm.py` + `test_cutedsl_dsv3_fused_a_gemm.py`, full M = 1..16 locally):

End to end: a config-only `DeepseekV3ForCausalLM` (DeepSeek-V3 MLA dims, hidden_size=3584, 4 layers, 16 experts), `--load-format dummy --skip-tokenizer-init`, default server args (CUDA graph on), one `/generate` request with `input_ids`. Not run on Hopper. There `auto` resolves to the JIT kernel, whose eligibility is unchanged. The CuTe DSL kernel with the new K values is covered on H100 by `test_cutedsl_dsv3_fused_a_gemm.py`.

## Speed Tests and Profiling

RTX 5090, fused CuTe DSL kernel vs `F.linear` (which SM120 runs today for these K). Each provider is timed inside a CUDA graph, rotating over enough weight copies (>= 512 MB) that the weight is read from HBM, as in a decode step. Times are in us per call.

| K | N | M=1 | M=2 | M=8 | M=16 |
|---|---|---|---|---|---|
| 2560 | 2112 | 7.66 vs 9.39 (1.23x) | 7.72 vs 14.99 (1.94x) | 7.84 vs 15.10 (1.93x) | 8.03 vs 15.29 (1.90x) |
| 3584 | 2112 | 10.29 vs 12.41 (1.21x) | 10.36 vs 20.44 (1.97x) | 10.45 vs 20.51 (1.96x) | 10.72 vs 20.78 (1.94x) |
| 2560 | 2624 | 9.21 vs 10.79 (1.17x) | 9.32 vs 15.22 (1.63x) | 9.44 vs 15.33 (1.62x) | 9.67 vs 15.68 (1.62x) |
| 3584 | 2624 | 12.49 vs 14.32 (1.15x) | 12.50 vs 20.74 (1.66x) | 12.64 vs 20.82 (1.65x) | 12.90 vs 21.09 (1.63x) |
| 7168 (already fused) | 2112 | 19.31 vs 21.35 (1.11x) | 19.32 vs 39.19 (2.03x) | 19.50 vs 39.34 (2.02x) | 19.84 vs 39.56 (1.99x) |

The speedups for the newly allowed K match those for K=7168 and 6144, which already take this path. At K=3584, N=2112 the fused kernel reads the 15 MB weight at about 1.5 TB/s, close to the 5090's HBM bandwidth.

No change on non-SM120 GPUs with the default backend.
