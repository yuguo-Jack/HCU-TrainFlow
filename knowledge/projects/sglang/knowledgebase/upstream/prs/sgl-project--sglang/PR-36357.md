# [SM120] Enable FlashInfer GDN prefill default for consumer Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/36357) · state: open · merged: False

## Original PR description

## Motivation

`flashinfer_gdn_prefill_default()` returns `None` on SM120, so consumer/workstation
Blackwell runs GDN prefill on Triton by default — even though `gdn_flashinfer.py` already
has an SM120-specific prefill path (`use_state_pool = sm_major >= 10`,
`_prefill_needs_fp32_state = sm_major >= 12`). This PR adds SM120 to that default-selection
policy as its own validated bucket, and adds unit coverage for the bucket's boundaries.

## Modifications

**1. SM120 gets its own row in `flashinfer_gdn_prefill_default()`** — admitted to the
capability check (`sm_major not in (9, 10)` → `(9, 10, 12)`), then given SM100's runtime
envelope with its own state dtype:

| arch | CUDA floor | max `chunked_prefill_size` | expected state dtype |
|------|-----------|----------------------------|----------------------|
| SM90  | none  | 32768 | fp32 |
| SM100 | >= 13 | 8192  | bf16 |
| **SM120** (new) | **>= 13** | **8192** | **fp32** |

* **fp32 state** — the SM120 kernel entry requires it. On a bf16 pool the clean tree raises
  `RuntimeError: initial_state must have dtype torch.float32, got torch.bfloat16` from
  `delta_rule_cp_sm120.py`, which is exactly what `_prefill_needs_fp32_state` converts
  around. fp32 is also what `mamba_ssm_dtype` resolves to by default, so the widening takes
  effect on the default path.
* **CUDA >= 13, chunk <= 8192** — SM120 goes through `use_state_pool`, i.e. the same chunked
  state-pool path SM100 is gated on, so it inherits the same envelope rather than SM90's
  looser one.

SM90 and SM100 behaviour is byte-identical to `main`.

**2. Unit coverage** in `test/registered/unit/layers/attention/test_gdn_prefill_backend_policy.py`:
grant case for SM120 + fp32 + CUDA 13; rejection cases for `sm120_bf16_state`,
`sm120_cuda_12`, `sm120_large_chunk` (8193), plus `sm90_bf16_state` / `sm100_fp32_state` so
the "one validated dtype per major" rule is explicit. The two boundary rows are
load-bearing: with the looser first-commit gate they fail with
`AssertionError: 'flashinfer' is not None`.

## Accuracy Test

1x NVIDIA RTX PRO 5000 72GB Blackwell (SM120), CUDA 13.0, TP1,
`RedHatAI/Qwen3.6-35B-A3B-NVFP4` (hybrid GDN), `--chunked-prefill-size 8192
--disable-radix-cache`.

* **Default fires** — with no explicit flag the dispatcher logs
  `decode=TritonGDNKernel, extend=FlashInferGDNKernel, verify=TritonGDNKernel`
  (and since the gate passed, the pool was fp32).
* **Determinism** — greedy decoding (`temperature=0`) is byte-identical across two runs.
* **Long request** — 2359-token prompt completes coherently.
* **Multi-chunk / packed-sequence stress** — `bench_serving --dataset-name random-ids`,
  in 4000 / out 200, `--random-range-ratio 1.0 --seed 42`, C=32, N=48:
  **48/48 succeeded, zero failures**, 9600 = 48x200 output tokens.
  Server counters confirm both hunks were exercised: `#new-token == 8192` (full chunk) 22
  times, and `#new-seq` up to 6, so the multi-sequence `cu_seqlens` packing path is covered
  too, not only the single-sequence one.

## Benchmark and Profiling

Prefill A/B, same binary and request stream, measured **server-side on back-to-back full
blocks only** (`#new-token == 8192`), n=22 per arm over matched 11 s windows:

```
                min      median      max       (tok/s, #new-token == 8192)
FlashInfer     32969     34511     37186   ████████████████████
Triton         29779     31764     33635   ██████████████████
```

* median 34511 / 31764 = **+8.7%**
* pairwise rank statistic: FlashInfer > Triton in **483 of 484** (22x22) pairs; FlashInfer
  exceeds Triton's *max* in 21/22 and Triton falls below FlashInfer's *min* in 21/22 — the
  distributions are near-disjoint, far outside the 0.4-0.8% cross-restart variance on this
  box.

This is an **end-to-end prefill forward** delta, not a per-kernel profile.

Two disclosures so reviewers don't have to dig them out:

1. **The A/B ran on a bf16 pool.** Both arms were driven by explicit
   `--linear-attn-prefill-backend {flashinfer,triton}` — which bypasses the policy under
   change — with `--mamba-ssm-dtype bfloat16`. So it isolates exactly the prefill backend
   this PR defaults, but on the pool dtype this PR's gate *rejects*. On the fp32 pool the PR
   enables, the kernel receives the same fp32 initial state (the
   `_prefill_needs_fp32_state` conversion becomes a no-op) and only state marshalling
   differs — but I have not measured that arm beyond the accuracy checks above, and I am not
   translating +8.7% into a claim about it. Happy to re-run the A/B on the default fp32 path
   if you want the numbers on-configuration.
2. **One-time first-touch cost.** Client-side median TTFT reads *worse* on the FlashInfer
   arm (5578.89 vs 2018.90 ms). That is a single batch: the first time a 4224-token prefill
   shape is seen it runs at **979.79** vs Triton's **28290.28** tok/s (4.31 s vs 0.149 s),
   and that ~4.16 s accounts for essentially the whole 3.80 s duration difference.
   Steady-state decode is untouched, as expected for a prefill-only flag (`mean_tpot` 21.67
   vs 21.74 ms, +0.3%).

Scope actually validated: **bf16 pool + chunk 8192 + TP1** for the throughput A/B, fp32 pool
for the default-path accuracy checks. Not covered: TP>1 on SM120, chunk sizes other than
8192, `enable_dynamic_chunking`.

## Notes for reviewers

* **Prefill and decode stay mutually exclusive on SM120.** `server_args.py` raises when
  `linear_attn_decode_backend == "flashinfer"` and `mamba_ssm_dtype != "bfloat16"` on
  capability >= 10. Since this gate requires fp32, the two cannot both be on for SM120:
  fp32 → FlashInfer prefill + Triton decode; bf16 → FlashInfer decode possible, prefill
  stays Triton. Pre-existing, not addressed here; flagging it because fp32 also doubles SSM
  state bytes vs bf16, which matters on capacity-bound deployments.
* **MTP/target-verify untouched** — `supports_target_verify = sm_major in (9, 10)` excludes
  SM120, confirmed by `verify=TritonGDNKernel` in the log above.
* Fully opt-outable: `--linear-attn-prefill-backend triton`, and anything outside the
  envelope (CUDA 12, chunk > 8192, bf16 pool, page-major KV, dynamic chunking,
  deterministic inference) falls back to Triton automatically.

**Setup**

- Image: `lmsysorg/sglang:v0.5.21-cu130`, with `gdn_backend.py` bind-mounted. The function is identical on main.
- Models: Qwen/Qwen3.8-27B (BF16) and Qwen/Qwen3.8-27B-FP8. Both are dense hybrids, with 48 GDN and 16 full-attention layers and `mamba_ssm_dtype: float32`.
- Flags: `--context-length 131072 --mem-fraction-static 0.75`.

**The default path, no flags.**

- The server logs `Defaulting SM120 GDN prefill backend to FlashInfer.` and `Linear attention kernel backend: decode=triton, prefill=flashinfer, verify=triton`.
- BF16 prefill is 1371 and 1380 tok/s at 32K (two launches) and 1016 at 124K. That is the same as `--linear-attn-prefill-backend flashinfer` (1368–1396 and 1007–1024).

**End to end**, Triton → FlashInfer prefill. Client: `vllm bench serve`, random token prompts, greedy:

| | BF16 | FP8 (with #44792's GEMM fix) | FP8 + MTP (NEXTN, 3 steps) |
|---|---|---|---|
| prefill, 32K prompt, tok/s | 1297 → 1396 / 1368 | 1776 → 1926 | 825 → 855 |

- The FP8 + MTP arm uses the default FP8 GEMM. That GEMM dominates prefill there, hence the smaller gain.

**One test gap.** `TestFlashInferLinearGDNBackendCorrectness` in `test/registered/attention/unittests/gdn/test_flashinfer.py` exercises the path this PR turns on: FlashInfer prefill with tracked state checkpoints, against Triton. But its gate (`_sm_major == 9 or (_sm_major == 10 and _cuda_major >= 13)`) skips it on SM12x.

- With the gate widened to `_sm_major in (10, 12)`, the test passes on GB10 in 9.9 s, for both output and tracked states.
- FlashInfer warns `CP delta rule heuristic matched but CP dispatch is unavailable: CP delta rule does not support state checkpointing yet; falling back`.
- The 3-line change is https://github.com/puncsky/sglang/commit/5e8c25487e12e2ad100fe4cbbd9ce000a07ed610. It might be worth adding here, so the new SM12x default has a test that runs on SM12x.
