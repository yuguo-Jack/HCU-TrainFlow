# [Perf] openai: Cache tool schema validation

[Upstream PR](https://github.com/sgl-project/sglang/pull/42213) · state: closed · merged: False

## Original PR description

## Motivation

Each chat request validates every tool's JSON schema, a blocking Python check on the API event loop. Agents resend the same tools across turns.

## Modifications

Cache successful schema checks in a per-process LRU of at most 4,096 digests. Invalid schemas are never cached. Existing configs need no change.

Schemas that orjson cannot serialize, or with NaN or Infinity, use the existing path. With this path removed, a server accepted a null `maximum` after a NaN `maximum` over gRPC, because orjson writes NaN as null. Main rejects it.

Deliberate limits:

- Direct Python callers can pass tuples or Enums that digest like their JSON forms. HTTP and gRPC JSON cannot contain them.

These limits are deliberate. Do not add code for them without a real input that reaches the case.

## Accuracy Tests

No accuracy eval ran, because prompts and sampling are unchanged.

At `1efa97ae36` and main `e298298511` on one B200, `/v1/tokenize` token digests for `qwen3_coder.json` and `kimik3.json` matched, as did status codes and error messages (first 170 characters). HTTP chat and gRPC covered valid, invalid, null `maximum`, NaN and 2**70 schemas. HTTP chat covered aliases, reordered keys, nesting and non-objects. `/v1/tokenize` and `/v1/messages` covered valid and invalid.

With a temporary log, 4,400 distinct HTTP schemas plus gRPC traffic held the cache at 4,096 digests on the main thread, and no request failed.

The repeat-schema test fails on main with `3 != 1`. Chat, Anthropic, gRPC and normalization tests found no failures.

GLM-5.3-Flash, gRPC latency, multiple API workers and GitHub test workflows (no `run-ci` label) were not checked.
