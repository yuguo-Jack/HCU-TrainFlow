# [OpenAI] Check each tool schema once, not on every request

[Upstream PR](https://github.com/sgl-project/sglang/pull/42213) · state: open · merged: False

## Original PR description

The chat endpoint now runs `Draft202012Validator.check_schema` once for each distinct tool schema, not on every request. For an agent that sends the same 81 tools on every call, each request has 150 ms less blocking CPU on the event loop of the API server. On an idle server, the time to first token of a short chat with these tools goes from 241 ms to 77 ms.

## Motivation

The chat endpoint runs `check_schema` on the parameters of every tool of every request. `check_schema` is pure Python and runs on the event loop of the API server. An agent sends the same tools on every call, so the server checks the same schemas again and again.

For an agent with 81 tools, the check takes 150 ms for each request. During that time, this API server process admits no other request and streams no other response.

## Modifications

- `_check_tool_schema_once` remembers a schema that passed. The key is a 16-byte BLAKE2 digest of the schema as JSON with sorted keys, taken after `normalize_json_schema_types`. The memory is an LRU of at most 4,096 digests for each API server process.
- A schema that fails is not remembered. It is checked on every request and returns the same error as before.
- A schema without a safe digest is checked on every request, as before. This applies to a schema that `orjson` cannot write. It also applies to a schema with `NaN` or `Infinity`, because `orjson` writes both as `null`.
- The Anthropic Messages endpoint, chat tokenization and the gRPC bridge call the same `_validate_request`, so they get the same change.
- Four unit tests cover the change. An unchanged schema is checked once, and a changed schema is checked again. An invalid schema returns the same error on every request. A full memory forgets the least recently used schema. A schema without a safe digest is checked every time.

## Expected improvement and risk

| Change | Expected improvement | Risk | What limits or turns it off |
|---|---|---|---|
| `check_schema` runs once for each distinct tool schema | 150 ms less blocking CPU for each request with 81 tools. Idle server: time to first token of a short chat 77 ms against 241 ms. Under load, a run without this change has a median time to first token of 0.46 s against 0.24 to 0.25 s at 16 sessions in flight, and 0.37 s against 0.20 s at 4. Its engine time per output token is 3.7% higher at 16 in flight and 4.3% higher at 4 (6.37 ms against 6.14 ms, and 3.54 ms against 3.39 ms). | Low. For a schema parsed from JSON, the accept or reject result does not change. An invalid schema is still rejected on every request. A schema without a safe digest is still checked on every request. The memory is bounded. The model input and the sampling do not change. | There is no flag. Only a schema that already passed in the same API server process skips the check. The first request with a new schema pays the full check. A caller that sends new schemas on every request gets no gain. |

Measurement setup: one node with 8 B200 GPUs and two servers of 4 GPUs each, SGLang v0.5.20 with this function patched in, and an FP8 GLM-5.3-Flash checkpoint. The numbers under load are engine time per output token and time to first token in whole replayed sessions of an agent workload (temperature 1.0, top-p 0.95). Engine time per output token is the sum of the call latencies of a session divided by its output tokens. "In flight" is the number of concurrent sessions for each server. The reference server has this change and other local changes. One run removes only this change.

Why the risk is low:

- `check_schema` validates the schema against the fixed Draft 2020-12 metaschema. Its result depends only on the schema.
- The check is skipped only when a schema with the same digest already passed in this process. Key order does not change the digest. `1`, `1.0` and `true` give different digests.
- A schema that fails is never stored. A schema with `NaN` or `Infinity` is never stored.
- Limit: `orjson` writes some Python-only values as JSON values (a tuple as an array, an `Enum` member as its value). A schema that code builds in Python with such a value has the digest of its JSON form. After the JSON form passed, it skips the check, where `check_schema` rejects it. A request body parsed from JSON cannot contain these values.
- The memory holds at most 4,096 digests of 16 bytes for each API server process.
- A new schema costs one serialization and one digest more than before. A schema whose JSON contains the text `null` costs one more serialization.

## Accuracy Tests

No model code changes. The model input and the sampling are the same.

On the v0.5.20 server, a request with an invalid tool schema returned HTTP 400 on the first call and on the second call. The unit test on this branch asserts that both calls return the same message.

Local checks at the current commit, on macOS and outside upstream CI:

- The four new tests pass.
- In the whole file `test_serving_chat.py`, the only failures are the tests that need `uvloop`, which is not installed on that machine. The same tests fail at the previous commit of this branch.
- Broken variants of the helper each fail at least one of the four tests. The variants are: no `NaN` guard, no eviction, no `move_to_end`, a digest stored before the check, and no fallback for a schema without a digest.
- A direct comparison with `check_schema` gave the same accept or reject result for nested schemas with and without `null` and `NaN`, for a cyclic schema, and for values that `orjson` cannot write.
- `pre-commit run` on the two changed files passes, including `codespell`.

To verify:

```bash
python -m pytest test/registered/unit/entrypoints/openai/test_serving_chat.py -k "tool_schema and validate_request"
```

The command selects the four new tests. On a running server, send the same chat request with tools two times. The second request does not run `check_schema`.

## Speed Tests and Profiling

py-spy on the API server process showed `check_schema` under `_validate_request` as a hot path while the server ran agent sessions with tools.

All numbers below use the setup in "Expected improvement and risk". The server had other local patches, which were the same in the runs with and without this change. Compare the differences, not the absolute values.

Idle server. Median time to first token of a short streamed chat with 81 tools behind a cached prefix:

| | Median time to first token |
|---|---|
| Without this change | 241 ms |
| With this change | 77 ms |

`check_schema` alone for the 81 schemas takes 150 ms in a separate Python process.

Under load. Whole agent sessions that send the same tools on every call. Each load has one run without this change and three runs with it:

| Sessions in flight | Median time to first token, without | With | Engine time per output token, without | With |
|---|---|---|---|---|
| 16 | 0.46 s | 0.24 to 0.25 s | 6.37 ms | 6.12 to 6.16 ms |
| 4 | 0.37 s | 0.20 s | 3.54 ms | 3.38 to 3.44 ms |

Against the reference mean (6.14 ms and 3.39 ms), the engine time per output token without this change is 3.7% higher at 16 sessions in flight and 4.3% higher at 4. The reference mean is the mean of two of the three reference runs. Read a difference under about 1.5% as no measurable effect in this benchmark.

## Not verified

- This branch on `main` was not benchmarked. All speed numbers come from the same function patched into v0.5.20, before the `NaN` guard was added.
- The `NaN` guard was not timed on a server.
- Upstream CI has not run the unit tests. The pull request is a draft, and CI blocks the test jobs for a draft. The local test run was on macOS only.
- The numbers under load come from one run without the change for each load, on one machine with one GPU type and one checkpoint.
- A server with more than one API worker process was not measured. Each process has its own memory, so each process checks a schema one time.
- The gRPC bridge was not tested on a live server. The `NaN` and `Infinity` case is covered by the unit test only.
