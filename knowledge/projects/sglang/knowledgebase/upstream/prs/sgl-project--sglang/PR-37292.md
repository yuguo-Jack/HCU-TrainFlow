# [Feat] dsv4: Support deterministic inference for DeepSeek-V4

[Upstream PR](https://github.com/sgl-project/sglang/pull/37292) · state: open · merged: False

## Original PR description

## Motivation

Closes #36174.

`--enable-deterministic-inference` rejects DeepSeek-V4 at startup, and because the
model's config-time overrides pin `--attention-backend dsv4`, there is no backend to
fall back to — the flag is unusable on V4 in every configuration:

```
ValueError: Currently only ['ascend', 'fa3', 'fa4', 'flashinfer', 'intel_xpu', 'triton']
attention backends are supported for deterministic inference, but you explicitly
specified 'dsv4'.
```

Allowlisting the backend alone is not enough: with it allowlisted but nothing else
changed, DeepSeek-V4-Flash-FP8 still produces 3 distinct outputs over 20 batch sizes.
The V4 path has four separate dispatches that key off the token count.

## Modifications

Each site below picks a kernel, a tile size, or a split-K count from the number of
tokens in the batch, which is exactly what deterministic inference must not do.

1. **mHC pre-norm split-K** — `_compute_num_split_for_mhc_pre` derives `n_splits`
   from `n_sms // ceil(num_tokens / 64)`, and `n_splits` is the number of partial
   sums the K reduction is folded from, so it fixes the summation order. This is the
   first op of every layer, so a prompt prefilled alongside two others differs from
   the same prompt prefilled alone in *every* token's logprob by ~1e-2. Pinned to the
   token-independent `num_block_k // 4`. `mhc_fused_post_pre` carries the same term
   plus a `num_tokens <= 32` FMA-kernel switch, and
   `_flashinfer_mhc_pre_num_splits` is a third copy.
2. **FlashMLA sparse decode tile scheduler** — `sparse_attn_decode_interface`
   computes `payload = ceil(total_num_blocks / num_sm_parts)` over the whole batch,
   so where a request's KV range is cut depends on its co-batched requests.
   Deterministic mode issues one launch per request, which makes the schedule a
   function of that request alone.
3. **Non-paged indexer** — taken only when `batch_size == 1 and query_rows >= 8192`.
4. **Router GEMM** — `MoEGate` switches to `dsv3_router_gemm` at
   `hidden_states.shape[0] <= 16`, and `linear_bf16_fp32`'s HPC-Ops path at `M >= 8`.
   Fixing the first also fixes a startup crash: the deterministic branch of `MoEGate`
   returned bf16 router logits, and V4's fused `hash_topk` kernel requires fp32
   (`Dtype value [bfloat16] not in the allowed options: [float32]`).

Also probed and ruled out on H200, so left alone: the DeepGEMM fp8 block GEMM is
M-invariant at every V4 shape, `flash_mla_sparse_fwd` (prefill) is s_q-invariant,
and the MoE runner choice makes no difference.

Deterministic inference on `dsv4` is rejected on SM120, whose attention kernel is an
autotuned Triton kernel that picks its tile size — and with it the softmax rescaling
order — from measured timings.

Everything above is gated: with the flag off, the only changes are an extracted
`_use_sparse_prefill` predicate, two algebraically identical `max_splits` locals and
a `use_fma` local. Verified below.

## Accuracy Tests

DeepSeek-V4-Flash-FP8, 4xH200, TP=4.

**The feature.** Distinct outputs over 32 batch sizes,
`sglang.test.test_deterministic --test-mode single`:

| | distinct outputs / 32 |
| --- | --- |
| without the flag | 6 |
| with `--enable-deterministic-inference` | **1** |

All three harness modes pass with radix cache and CUDA graphs on: `single` (n=32),
`prefix` + logprobs (temperature 0.5, shared prefixes of 1 / 511 / 2048 / 4097), and
`radix_cache`. Chunked prefill was checked separately at
`--chunked-prefill-size 512` over 4097-token prompts.

**No regression with the flag off.** Same box, arms run back to back, benchmark client always from `main` so only the
server tree varies.

The strongest check pins the batch at one request, which removes batch-composition
noise entirely: 150 GSM8K completions issued serially are **150/150 byte-identical**
between `main` and this branch, as are 8/8 fixed greedy prompts.

GSM8K, 400 questions, 5-shot, greedy, `--parallel 64`:

| tree | runs |
| --- | --- |
| `main` | 0.965, 0.965, 0.968, 0.968, 0.968 |
| this branch | 0.960, 0.963, 0.970, 0.960 |

Repeats within one warm server span 0.960-0.970 on this branch, bracketing every
`main` number; at 400 questions the harness cannot resolve better than about +/-4
questions. That spread is DeepSeek-V4's own batch-composition non-determinism -- the
thing the new flag removes.

## Speed Tests and Profiling

**With the flag off** — `sglang.benchmark.serving`, random 1024/512, 200 prompts,
concurrency 32: 

| order | tree | output tok/s | total tok/s | mean TPOT |
| --- | --- | --- | --- | --- |
| 1st | `main` | 1849.80 | 5549.39 | 14.01 ms |
| 2nd | this branch | 1919.93 | 5759.80 | 13.99 ms |
| 3rd | `main` | 1919.67 | 5759.01 | 13.99 ms |

This branch lands within 0.01% of the warm `main` run. The first run is the cold
outlier (JIT and autotune caches), and that cold-start effect (+3.8%) is far larger
than anything between the trees. `MHC prenorm prewarm: 21 n_splits buckets` is logged
by both trees with the flag off, i.e. the split-K schedule is untouched there.

**With the flag on**, decode throughput (fixed batch, 128 output tokens, best of 3):

| | bs=1 | bs=16 | bs=32 |
| --- | --- | --- | --- |
| no flag | 131 | 1611 | 3045 tok/s |
| deterministic | 50 | 354 | 444 tok/s |

Deterministic inference costs ~2.1-2.5x on its own (batch-invariant matmul/rmsnorm,
pytorch sampling, NCCL tree with pinned channels, pinned MoE and mHC split-K), flat
in batch size. The per-request FlashMLA launch adds a further 2.3x at bs=16 and 3.2x
at bs=32, and is free at bs=1. It is not optional: an ablation that keeps the single
batched launch and everything else is still non-deterministic (2 distinct outputs
over 32 batch sizes).

That ablation is also the opening for a follow-up. `sparse_decode_fwd` accepts
`tile_scheduler_metadata` and `num_splits` as inputs and only computes them when
absent, so a supplied no-split schedule would recover the single launch. This PR
takes the loop instead: it is 15 lines, obviously correct, and carries no coupling to
a pinned third-party struct layout — and its bit-exact output is the oracle a
schedule builder would be validated against.

Data point from SM120 (2x RTX PRO 6000 Blackwell, TP=2, DeepSeek-V4-Flash, `--moe-runner-backend flashinfer_mxfp4`) on `0.5.19.dev410+gedff717ef` / FlashInfer 0.6.17, i.e. before this PR.

**Status quo reproduced.** `--enable-deterministic-inference` fails at startup with the ValueError in the PR description (`arg_groups/overrides.py:2278` at edff717ef; main `:1139`): the V4 override pins `attention_backend="dsv4"` (`overrides.py:1313`; main `model_overrides/deepseek_v4.py:30`) and `DETERMINISTIC_ATTENTION_BACKEND_CHOICES` (`server_args.py:241-248`; main `:233-240`) lacks `dsv4`. Same as #36174.

**Without the flag, greedy output is not run-to-run reproducible even at concurrency 1.** Same server, 32 prompts, temperature 0 / top_k 1 / concurrency 1 / `flush_cache` before every request, two passes:
- 5/32 outputs identical between passes; some diverge at the first token.
- Teacher-forced argmax over ~83k tokens: 4.8e-3 and 5.9e-3 per-token disagreement in the two passes, with 16 logit flips >1 nat that are stable across passes.
- `SGLANG_FLASHINFER_MOE_FUSED_FINALIZE=0` with a fresh autotune cache changes nothing: 6/32 identical. So the bf16 atomic MoE finalize is not the dominant source here; I have not isolated it further.

**Why this PR still leaves SM120 without a path.** It adds `dsv4` to both allowlists but raises `ValueError("... requires SM90 or SM100 ...")` for SM120 in `handle_deterministic_inference`, because the SM120 decode kernel is autotuned Triton (`flash_mla_sm120.py:245` -> `flash_mla_sm120_triton.py:40 @triton.autotune`; main `:314` / `:40`). After merge, RTX PRO 6000 / DGX Spark users get a clear error (the mdx hunk documents it, thanks) but no deterministic option.

**Why pinning the config may be sufficient for SM120 (read of the kernel, not yet tested).** `_tiled_sparse_decode_kernel` launches with `grid = (B, H)` (`flash_mla_sm120_triton.py:246`), so one program owns a whole (request, head); it accumulates with a sequential `for tile_start in range(0, topk, BLOCK_T)` loop (`:~150`) and uses no atomics and no split-K. The per-request reduction order therefore does not depend on what else is in the batch, i.e. the kernel already looks batch-invariant; the only run-to-run hazard I can see is `@triton.autotune` (`:40-46`) choosing among three configs that differ in reduction tiling and warp partitioning:
```
triton.Config({"BLOCK_T": 16}, num_warps=4, num_stages=2)
triton.Config({"BLOCK_T": 16}, num_warps=8, num_stages=2)
triton.Config({"BLOCK_T": 32}, num_warps=8, num_stages=2)   # key=["topk_rounded"]
```
Selecting one fixed config when deterministic mode is on would remove that, at a perf cost only in this kernel.

Would you consider, here or in a follow-up, pinning `flash_mla_sm120_triton` to a fixed config under deterministic mode instead of rejecting SM120? I can open a follow-up PR for that if you would rather keep this one scoped to SM90/SM100. Happy to share the scripts and logs behind the numbers above (single machine, one config).


- Wendy-Hamlet · comment · 2026-09-26T07:55:26Z · [source](https://github.com/sgl-project/sglang/pull/37292#issuecomment-5844417622)

A data point that supports routing the DSA top-k to FlashInfer's ordered path, from the batch-size-1, long-context side that the GSM8K checks here do not reach.

**Setup.** DeepSeek-V4-Flash, TP=8 on 8×H100, `c9ceab34cf` with FlashInfer 0.6.12. One InfiniteBench longbook_choice_eng prompt of 71,934 tokens, prefilled alone (B=1) in two separate server launches, without `--enable-deterministic-inference`. We captured every layer's tensors for all tokens and counted *source* tokens: tokens where a layer's inputs are bitwise identical between the two runs but its output differs.

| top-k / MoE | attention-source tokens | MoE-source tokens | final-layer hidden states that differ |
|---|---:|---:|---:|
| as shipped | 69,496, all at L2 | 0 (masked, see below) | 97.2% |
| indices sorted after top-k | 1 | 53 | 99.9% |
| sorted, plus the FlashInfer MoE fix | 4 | 1 | 84.1% |
| exact top-k (sorted, smallest-index tie-break), plus the MoE fix | **0** | **0** | **0%**: all 43 layers bitwise identical |

What each row shows:
1. **Order.** At the 69,496 L2 rows, the indexer query, the indexer scores, and the selected set of 512 are all bitwise identical; only the order differs, because output positions come from `atomicAdd`. That order changes the accumulation order in sparse attention. `main` does the same (`problem.emit(pos, idx)` with `pos` taken from `atomicAdd` in `topk_impl.cuh`).
2. **MoE.** The 53 MoE sources are a FlashInfer MXFP4 grouped-GEMM race that computes a tile with the next expert's scale. It affects 0.6.10–0.6.15.post1, is fixed on the 0.6.16+ rewrite (flashinfer-ai/flashinfer#5438), and `main` pins 0.6.18. It only became visible once L2 stopped diverging almost every token.
3. **Ties.** The 4 remaining attention sources are all rows where two candidates tie *exactly* in fp32 at the k-th position with one slot left, so the atomic race picks the winner. It is a handful of rows in a 72K prompt, yet it still changes 84% of the final hidden states.

Two suggestions for the deterministic test:
- Prompts of at most `4 × index_topk` = 2048 tokens select every candidate, so the sgl-kernel versus flashinfer choice never matters for them. A long B=1 case (tens of K tokens) would cover this path.
- Since a single exact tie flips most downstream tokens, it may be worth asserting a fixed tie-break in deterministic mode. Is the default of `_flashinfer_tie_break_value()` (env unset) deterministic under exact ties on the ordered path?

(The exact top-k we used is a slow PyTorch reference, about 22–27× the kernel time, and only served as a correctness check. We are not proposing it.)
