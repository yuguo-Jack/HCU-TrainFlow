# [NPU DSA prefill sharding 2/2] Token shard: every head for this rank's slice of the tokens

[Upstream PR](https://github.com/sgl-project/sglang/pull/42978) · state: open · merged: False

## Original PR description

> **Depends on https://github.com/sgl-project/sglang/pull/42977** (DSA indexer query sharding). Until that merges, this PR's diff includes it.
> Review only the last commit: "[NPU] DSA token shard: every head for this rank's slice of the tokens".

## Motivation

In NPU DSA prefill, attention TP splits the heads: each rank computes its 1/`attn_tp_size` of the heads
for every token. For sparse attention, each rank then reads and dequantizes the top-2048 KV rows for
every query. So the KV reads, which dominate sparse attention, are repeated on every rank.

This PR swaps the split for the attention core only. Each rank computes every head, but for its own slice
of the tokens. The weights stay head-sharded. Only the attention core changes, between the `w_kc` absorb
and `w_vc`. This is the same design as vLLM-Ascend's `enable_dsa_cp`. It needs no extra ranks, and unlike
upstream prefill CP it works with attention TP > 1.

## Modifications

- `dsa_token_shard.py` (new): the plan and the two all-to-alls. After the `w_kc` absorb, one all-to-all
  turns "my heads, every token" into "every head, my tokens". Sparse attention runs on that slice. A second
  all-to-all turns it back before `w_vc`. The KV write and the indexer stay full width.
- `deepseek_v2.py`: when the flag is on, each DSA layer gets a full-head `RadixAttention`
  (`attn_mqa_for_dsa_token_shard`). It is keyed on `use_dsa`, not on the Indexer, because a skip-top-k
  layer has no Indexer but still attends.
- `deepseek_v2_attention_mla_npu.py`, `ascend_backend.py`: the token-shard branch of the attention core,
  and per-rank query and KV lengths for the sparse operator.
- `dsa_npu_indexer.py`: when the indexer's query shard (the parent PR) picked the same rows as the token
  shard, the indexer keeps its local top-k and skips the all-gather. If the row ranges disagree, it falls
  back to the all-gather.
- The slice is cut by token position, so a request can straddle two ranks. The per-request query lengths
  are recomputed for the slice, and a request with no token on a rank keeps a zero entry, so the lengths
  stay aligned with the batch's block table. The KV lengths stay per request (paged layout), so batches
  with many requests need nothing that a single request does not.
- Extend and mixed batches only. Off at decode, and off under DCP (whose DSA path all-gathers the query).
- `SGLANG_NPU_ENABLE_DSA_TOKEN_SHARD`, **default on**, like the parent PR. Set it to `0` to get the old path.
  Documented in the Ascend environment variable reference.
- **MLAPO** (`SGLANG_NPU_USE_MLAPO`) is not refused, but it is untested together with this: on the DSA path
  MLAPO runs only at decode, and the token shard only at extend, with a full-width KV write, so they never
  meet. GLM-5.2's attention is unquantized and cannot run MLAPO, so the box could not check the pair.

## Accuracy Tests

GLM-5.2 W4A8, Ascend A3, tp16, no DCP, eager, GSM8K all 1,319 questions:

| | accuracy |
|---|---|
| this PR (flag on, with the parent PR) | 0.9477 |
| both flags off | 0.9424 |

At `--max-running-requests 64` most of these prefill batches hold many requests, and every prompt (about 950
tokens) is below `index_topk` (2048). So this covers multi-request slices and queries with unused top-k
slots. Against an earlier cut that refused multi-request batches below `index_topk` (0.9431): 20 vs 14
one-sided flips, McNemar p = 0.39.

**Not bitwise.** At tp16 the sparse operator sees 64 heads × T/16 rows instead of 4 heads × T rows, and the
changed reduction order shifts bf16 rounding. At tp16, single request, token shard on vs off, the mean
|Δlogprob| per position is 0.0008–0.009. For comparison, a cold vs warm prefix cache on the unchanged
path gives a max |Δlogprob| of 0.354 on this model.

Multi-request: 8 concurrent requests on a shared 5,504-token cached prefix, sharded vs unsharded. Worst
|Δlogprob| 0.54, and the first generated token differs on 1 of 8 requests. In an earlier run the flips were
near-ties (the chosen token's logprob was −0.7 to −1.1). A same-config control (unsharded twice, cache
flushed) gives a worst |Δlogprob| of 0.68.

## Speed Tests and Profiling

GLM-5.2 W4A8, Ascend A3, tp16, no DCP. Prefill forward time, single request, token shard on vs off
(medians; run-to-run noise is about 8.7%):

| prompt tokens | 503 | 1,003 | 2,003 | 6,007 | 16,007 |
|---|---|---|---|---|---|
| change | +4.5% (noise) | +4.7% (noise) | −28.9% | −48.1% | −54.2% |

Sharding multi-request batches was then measured on AISBench (~990k-token shared prefix, radix-cached, 16
concurrent ~10.8k-token tails): 110.2 s → 79.1 s for the 16 tails (−28%), with the single-request phase
unchanged (224.8 s → 224.1 s). That run used DCP 16 on the larger branch this PR is cut from. In this PR
the token shard turns itself off under DCP, so this number is for context, not for this PR as it stands.
