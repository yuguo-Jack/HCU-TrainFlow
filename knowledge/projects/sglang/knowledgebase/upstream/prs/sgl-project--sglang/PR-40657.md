# [Fix] diffusion: Fix the load duration missing from subclassed server tests

[Upstream PR](https://github.com/sgl-project/sglang/pull/40657) · state: closed · merged: True

## Original PR description

## Motivation

The AMD nightly `nightly-1-gpu-zimage-turbo` has failed on all three ROCm variants since the 2026-09-21 run ([job](https://github.com/sgl-project/sglang/actions/runs/35633070401/job/106443720276)), and was still failing on 2026-10-12:

```
PerformanceValidationError: [performance] zimage_image_t2i: Load duration missing or invalid: None
```

Image generation succeeds; the failure is in recording the result. #39206 added a `load_time_ms=None` parameter to `DiffusionServerBase._validate_and_record`, and a check in `_record_performance_result` that rejects a missing load duration, but only updated the base class's own call site. Three tests override `test_diffusion_generation` and call `_validate_and_record(case, perf_record)` directly, so they record `None` even though the server measured its load time:

- `test/registered/amd/test_zimage_turbo.py`
- `test/registered/xpu/test_xpu_zimage_turbo.py`
- `test/registered/xpu/test_xpu_flux2_dev.py`

## Modifications

`_validate_and_record` now takes the `ServerContext` and reads `ctx.load_time_ms` itself, as `_validate_realtime_performance` already does. The three overrides, the base-class call site and `test_performance_failure_policy.py` pass the context. Since `ctx` is required, an override still using the old call fails with a `TypeError` instead of silently recording `None`.

NVIDIA behaviour is unchanged: the base class used to pass `diffusion_server.load_time_ms` and now passes `diffusion_server`.

## Verification

- The NVIDIA diffusion suites (1/2/4-GPU, 5090, `diffusion-coverage-check`) and `multimodal-gen-unit-test` passed on this branch at e9616a3e ([run](https://github.com/sgl-project/sglang/actions/runs/38293317709)).
- The AMD zimage nightly, dispatched on this branch at c1e4114d with `continue_on_error=false` ([run](https://github.com/sgl-project/sglang/actions/runs/38473414064)), passes on rocm10, rocm724 and rocm720. Each job records the server's load time (52.3–58.6 s) instead of failing on `None`.

An earlier revision also added a guard test that drove the three overrides with a stub server. It has been removed: with `ctx` required, it no longer catches anything the signature doesn't.

## Notes for reviewers

Two XPU issues are left alone because this regression did not cause them:

- The XPU nightlies error during fixture setup with `fixture 'perf_results' not found`. `test/registered/amd/conftest.py` re-exports it (#38686), but `test/registered/xpu/` has no equivalent.
- `flux2_dev_image_t2i` has no entry in `perf_baselines/xpu_b60.json`, so once the fixture is fixed it will fail on the missing baseline (#39206 moved that check out of `if case.run_perf_check:`).

## That root cause is flaky on `main`, not caused by this PR

Worth flagging to the diffusion owners, since it makes the b200 lane a coin flip for any PR touching `multimodal_gen`.

The last scheduled `main` run's b200 job ([106570862025](https://github.com/sgl-project/sglang/actions/runs/35666291374)) failed the same nvfp4 cases and went green only on its fourth retry:

```
attempt 1: 2 failed, 3 passed
attempt 2: 2 failed, 3 deselected
attempt 3: 1 failed, 1 passed, 3 deselected
attempt 4: 1 passed, 4 deselected
```

On that `main` run, `flux1_modelopt_nvfp4_t2i` measured `e2e=1612.05ms` against `expected_e2e_ms=836.71` with a `1045.89ms` limit — `main` is ~1.9x over its own threshold on that case. My runs measured 1424–1925ms for the same test, i.e. the same range. `qwen_image_2512_modelopt_nvfp4_t2i` is similar, measuring 18.5–37.9s against a `9650.06ms` baseline.

So the outcome is decided by which retry happens to draw a fast enough sample within the 7-attempt budget. `main` drew one; these runs did not. It is also not reachable from this diff: `validate_e2e` reads `summary.e2e_ms` from `collect_metrics(perf_record)`, which this PR does not touch, and on the base-class path the change is behaviourally identical — it previously passed `diffusion_server.load_time_ms` as an argument and now reads `ctx.load_time_ms` off the same object.

Those baselines look due a re-seed, but that is a separate change in a lane this PR does not own, and I have deliberately not touched them — widening a perf gate that happens to be blocking my own PR would be the wrong fix for the wrong reason.
