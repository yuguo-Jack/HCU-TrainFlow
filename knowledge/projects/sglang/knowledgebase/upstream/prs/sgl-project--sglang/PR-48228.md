# [Fix] scheduler: use OpenAI's context-length wording when a prompt exceeds the KV pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/48228) · state: open · merged: False

## Original PR description


## Motivation

A prompt can fit `--context-length` but not the KV pool, for example `--context-length 8192 --max-total-tokens 4096` with a 6,030-token prompt. The scheduler rejects it with HTTP 400:

```
Input length (6030 tokens) exceeds the maximum allowed length (4090 tokens). Use a shorter input or enable --allow-auto-truncate.
```

OpenAI-compatible clients tell a context overflow from other bad requests by OpenAI's sentence "This model's maximum context length is N tokens". LiteLLM, for example, maps that substring to `ContextWindowExceededError`, which drives its context-window fallbacks and trimming. The tokenizer-side check for prompts over `--context-length` already uses wording these clients recognize. The scheduler-side rejection does not, so the same overflow reaches the client as something else:

| Request (Qwen/Qwen2.5-0.5B-Instruct, `--context-length 8192 --max-total-tokens 4096`) | LiteLLM 1.106.6 exception on main | with this PR |
|---|---|---|
| 10,030-token prompt (over `--context-length`, tokenizer check) | `ContextWindowExceededError` | `ContextWindowExceededError` (unchanged) |
| 6,030-token prompt (over the KV pool, scheduler check), non-streaming | `BadRequestError` | `ContextWindowExceededError` |
| same, `stream=True` | `MidStreamFallbackError` (a `ServiceUnavailableError`, which routers retry) | `ContextWindowExceededError` |

## Modifications

- `managers/utils.py` `validate_input_length`: when `--allow-auto-truncate` is off, the rejection keeps its existing sentence and adds `This model's maximum context length is {max_req_input_len - 1} tokens on this server.` The check rejects `len >= max_req_input_len`, so the quoted number is the largest prompt the server accepts, and a client that trims to it is not rejected again. `max_req_input_len` is the server's effective limit: the KV pool, or the context length when that is smaller. Text that matched the old message, such as "exceeds the maximum allowed length", still matches.
- The `--allow-auto-truncate` path and every in-range request are unchanged.
- New CPU test `test/registered/unit/managers/test_validate_input_length.py`. It checks the OpenAI sentence on rejection (it fails on main), rejection at exactly the limit, auto-truncate unchanged, and in-range unchanged.

## Accuracy Tests

No model output changes: only the text of an error message on a request that is already rejected.

End to end, on the same image (`lmsysorg/sglang:nightly-dev-20261103-797af717`, `sglang serve --model-path Qwen/Qwen2.5-0.5B-Instruct --context-length 8192 --max-total-tokens 4096`), main vs this PR, LiteLLM 1.106.6 and openai 2.54.0:
- The KV-pool rejection changes as in the table above. HTTP status and body type are unchanged: 400 `BadRequestError` non-streaming, and the existing SSE `error` event when streaming.
- Over-context (10,030 tokens) and input + `max_tokens` over context (3,030 + 6,000), each streaming and non-streaming, return byte-identical status and bodies on main and this PR. A short request succeeds (200) on both, including one sent right after the rejections.
