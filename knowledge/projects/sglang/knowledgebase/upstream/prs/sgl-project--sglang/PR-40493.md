# [diffusion] Honor --vae-slicing in the native decoding stage

[Upstream PR](https://github.com/sgl-project/sglang/pull/40493) · state: closed · merged: False

## Original PR description

## Motivation

`--vae-slicing` exists, but only the Diffusers backend honors it. The native `DecodingStage` never calls `enable_slicing()`, and `ParallelTiledVAE` (the base of the Qwen-Image 2.1, Wan and other native VAEs) has no slicing path, so the flag is a no-op there.

That matters for multi-output requests. On Qwen-Image 2.1 (`/v1/images/edits`, 1024x1024, 40 steps, RTX PRO 6000 96 GB, resident), per-stage peaks show the request peak is the batched VAE decode, growing about 3.17 GB per output:

| stage peak allocated (MB) | n=1 | n=2 | n=4 |
|---|---:|---:|---:|
| denoising | 18298 | 18712 | 19612 |
| decoding | 18829 | 22001 | 28349 |

(Per-stage numbers were taken with prefix KV sharing from #40489 applied; the decode figures equal main's request peaks below to within 3 MB.)

## Modifications

- `DecodingStage.decode`: when `pipeline_config.vae_slicing` is set, decode one sample per call and concatenate. This applies to every VAE decoded through `DecodingStage` and does not depend on each VAE's own slicing support. Pipelines with their own decode stage are not covered.
- Default stays off, so existing behavior is unchanged.

An earlier revision of this PR put the slicing in `ParallelTiledVAE` and called `enable_slicing()`. That silently did nothing on Wan's default path: `AutoencoderKLWan.decode` has no slicing check and, with the feature cache on (the default), calls its decoder directly. The current code was run on Qwen-Image 2.1 and once on Wan2.1-T2V-1.3B (n=2, 17 frames): without the flag `AutoencoderKLWan.decode` receives `z=(2, 16, 5, 60, 104)` on the feature-cache path and the decode stage peaks at 13609 MB; with it, `z=(1, ...)` twice and 7016 MB. Other models are covered by the unit test only. The measurements below were taken with that revision on Qwen-Image 2.1, where the per-sample computation is the same; one config was re-run with the current code and is pixel-identical to it, the rest were not re-run.

## Accuracy Tests

- The new unit test fails on main's stage (`[3] != [1, 1, 1]` decode batch sizes) and passes here; `test_decoding_stage_parallelism.py` passes in full (10 passed). pre-commit passes.
- Slicing is **not bit-exact** against batched decode in BF16. Versus main with the same request and seed: n=1 identical; n>1 has 5.1-7.1% of channel values differing, max abs diff 4-10 of 255, mean abs diff 0.051-0.071, PSNR 59.5-61.1 dB, 0.005-0.04% of values differing by more than 1. Sliced output is run-to-run identical. This is why it stays opt-in.

## Speed Tests and Profiling

Same protocol for every row: fresh `sglang serve` per config (`--vae-slicing true` where noted), 1 warm + 2 timed edit requests, seed 42, peaks from `perf_dump_path`. "both" adds #40489.

| config | variant | peak allocated (MB) | peak reserved (MB) | decode (ms) | latency (s) |
|---|---|---:|---:|---:|---|
| CFG off, n=1 | main | 18829 | 23404 | 434 | 9.60 / 9.62 |
| | slicing | 18829 | 23404 | 432 | 9.57 / 9.61 |
| CFG off, n=2 | main | 22002 | 31216 | 631 | 18.93 / 19.07 |
| | slicing | 20902 | 26616 | 635 | 18.91 / 19.00 |
| | both | 18839 | 24120 | 642 | 18.70 / 18.79 |
| CFG off, n=4 | main | 28352 | 46510 | 1001 | 37.97 / 38.25 |
| | slicing | 26115 | 32118 | 1221 | 37.80 / 38.04 |
| | both | 19613 | 25078 | 1223 | 37.21 / 37.51 |
| CFG 4, n=4 | main | 34346 | 55746 | - | 75.24 / 75.45 |
| | slicing | 34346 | 41354 | 1233 | 75.43 / 75.23 |
| | both | 21677 | 27384 | 1233 | 74.09 / 74.20 |

Reading: slicing alone moves the peak from decode to denoising (n=4: -2.2 GB allocated, -14 GB reserved) and does nothing for allocated peak under CFG, where denoising already dominates. With #40489 the n=4 peak is 0.8 GB above n=1. Decode costs +220 ms at n=4; end-to-end latency did not regress in these two samples per config.

Offload deployments, same protocol: RTX 5090 32 GB (default flags: `dit_cpu_offload`) and RTX 4090 24 GB (cookbook recipe: `--dit-layerwise-offload true --text-encoder-cpu-offload true`), n up to 4. There `--vae-slicing true` did not change recorded peak allocated in any config and did not resolve main's CFG n=4 OOM on its own, because decode is not the request peak: on the 4090 the conditioning stage peaks at 18650 MB for every n, against 4094 / 7267 / 13615 MB for decode at n=1/2/4. Peak reserved did drop in some configs (4090, CFG off n=4: 20490 -> 19332 MB; on top of #40489 at CFG n=4: 21990 -> 19340 MB on the 4090 and 25536 -> 23684 MB on the 5090). Latency showed no difference in these samples, and n>1 pixels differ as above (max abs diff 5-19).

Larger n on the same RTX 4090 recipe (CFG off, per-stage peak allocated from a temporary probe; the conditioning stage is 18634-18656 MB in every run):

| code | n | `--vae-slicing` | denoising (MB) | decode (MB) | result |
|---|---:|---|---:|---:|---|
| main + this PR | 6 | off | 17426 | 19967 | ok, 143.03 s |
| main + this PR | 6 | on | 17426 | 4146 | ok, 142.85 s |
| main + this PR | 8 | off / on | - | - | OOM in the first denoising step |
| + #40489 | 6 | on | 6611 | 4146 | ok, 138.83 s |
| + #40489 | 8 | off | 7503 | - | OOM in decode |
| + #40489 | 8 | on | 7509 | 4164 | ok, 187.00 s |

Slicing holds decode at about 4.1 GB regardless of n. At n=6 it moves the request peak from decode back to the conditioning stage. At n=8 the request completes only with both changes: without slicing, decode asks for a single 9.00 GiB allocation on top of 16.69 GiB, which does not fit the 23.52 GiB card (also with `expandable_segments:True`); without #40489, denoising OOMs under both allocator settings. One more config, + #40489 at n=6 without slicing, OOMed in decode under the default allocator but completed with `expandable_segments:True` (decode 19954 MB), so it is not counted as evidence here. One timed request per config.
