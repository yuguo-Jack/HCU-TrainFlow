# [Fix] scheduler: Dedupe shared prefixes in shortest-first order under SPF

[Upstream PR](https://github.com/sgl-project/sglang/pull/46022) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

With `--schedule-policy shortest-prefill-first` (SPF), a short new request can wait minutes, although SPF is meant to run it first. The cause is the in-batch prefix dedupe in `SchedulePolicy._compute_prefix_matches`. It walks the waiting queue in queue order and checks each "cold" request (at most 32 tokens already in the KV cache) against the earlier cold ones. A request that shares at least 32 tokens with one of them is held (deprioritized), so the shared prefix is computed only once, and SPF sorts held requests behind all others. When the earlier request is a long one, SPF itself runs it last, so the short request waits as long as the long one. This PR runs the dedupe in shortest-first order under SPF: in each shared-prefix group the shortest request now runs and the longer ones wait for it, so the shared prefix is still computed once. The dedupe also matches each request on its first 32 tokens only, the most that can decide a match. LPM, DFS-weight and HRRN keep queue order and hold the same requests as before. No request computes anything different; only the order of admission changes.

- **Accuracy:** GSM8K-200 on DeepSeek-V4.1-Flash, 4x B200, SPF, real DSpark speculative decoding: TP4 main 98.0 / 98.0%, this PR 97.5 / 98.0%; DEP4 with HiCache, 2 servers x 8 runs per tree: main 97.5-98.5%, this PR 97.0-98.5% (runs that answered all 200 questions).
- **Performance, live server** (4x B200, TP4, SPF): a 432-token request that shares 32 tokens with a queued 150K-token request gets its first token after 9.10-9.21 s on main and 0.22-0.27 s with this PR, the same as a request that shares nothing (0.20-0.23 s). The 150K-token request's TTFT moves from 14.96-15.00 s to 14.76-14.80 s. 4 trials per tree, ABBA on one node.
- **Performance, scheduler CPU:** `calc_priority` takes 1.78 -> 0.46 ms per call on a 14-request AgentX queue and 21.1 -> 20.2 ms on a 1,000-request worst case.
- **End to end (estimate, not measured):** in a trace replay of the scheduler on two GB300 AgentX runs, the measured 114-496 s waits drop to 0.5-0.6 s, and over 16 random session-id draws per trace p90 ITL and throughput stay within 0.2%. Whether a real run hits the bug depends on random session ids, so a GPU A/B of the whole benchmark would mostly measure that luck.

Related: SPF was added in #40024. A search found no other PR, open or closed, that targets this bug.

## Modifications

**+46 / −35 runtime code (1 file; +20 / −9 ignoring whitespace), +111 / −1 tests (1 file).** No kernel changes, no new flag.

`_compute_prefix_matches` in `python/sglang/srt/managers/schedule_policy.py`:
- First loop: match every waiting request against the KV cache and collect the cold ones. Same logic as before, now in its own loop.
- Under SPF only: stable-sort those candidates by uncached prefill work, the key SPF already sorts the queue by (`_shortest_prefill_work`; it counts a retracted request's output). Ties keep queue order, so identical prompts (parallel samples) dedupe as before.
- Second loop: the dedupe body, unchanged except that each candidate's key is its first 32 tokens (`IN_BATCH_PREFIX_CACHING_DEPRIORITIZE_THRESHOLD`). A request is held when it shares at least 32 tokens with an earlier candidate, so later tokens cannot change the result. On 1,500 seeded random queues, the held sets equal those of full-length keys under SPF, LPM and HRRN. With full keys, the split loop keeps every candidate's token list alive until the second loop, which costs +35% time and +38.8 MB per call on the 1,000-request queue below.

Why this is safe:
- In each shared-prefix group, the shortest request now runs and the longer ones wait for it. SPF serves the shortest one first anyway, so the shared prefix is still computed once.
- Other policies (LPM, DFS-weight, HRRN) keep queue order and give the same result as before: the sort runs only under SPF, and each request's dedupe decision depends only on its own cache match and on the earlier candidates, so splitting the loop does not change it. DFS-weight does not read the dedupe result.
- Trade-off: while a shorter member of its group is queued, the longer one now sorts behind all other requests, including unrelated longer ones. This lasts until the shorter one is admitted. Before, the shorter one paid this cost, for as long as SPF deferred the longer one.

Why not a smaller change:
- Skipping the dedupe under SPF also removes these waits. But requests that share a real prefix (a page or more) and are admitted together would then each compute it.
- Requiring at least one page of overlap would fix only cases where the overlap is shorter than a page. A short request that shares a real prefix with a long one would still wait for it, and LPM and HRRN would change too.

New tests in `test/registered/unit/managers/test_schedule_policy.py` (CPU), with the bug each one catches:
- `test_shared_prefix_holds_the_longer_request_not_the_shorter`: queue `[long, other, short]`, where `long` and `short` share 32 tokens. Expected order `[short, other, long]`; main returns `[long, other, short]`.
- `test_shared_prefix_group_holds_all_but_its_shortest_request`: three requests share 32 tokens; only the shortest runs (`{long, mid}` held). Main holds `{mid, short}`.
- `test_shared_prefix_group_counts_retracted_output_as_work`: a retracted request's 1,000 output tokens count as work, so it is the member that waits. Fails on main and if the sort uses prompt length only.
- `test_identical_prompts_hold_the_later_one_in_queue`: equal work keeps queue order. Fails if the sort breaks ties by rid.
- `test_other_policies_dedupe_shared_prefixes_in_queue_order`: LPM and HRRN still hold the later, shorter request. Fails if the sort is applied to every policy.
- `test_cached_request_is_not_a_dedupe_candidate` (SPF, LPM, HRRN): a request with more than 32 cached tokens takes no part in the dedupe, so a cold request that shares only those cached tokens runs. Fails if the cache-hit filter is dropped.

The first three fail on main; the last three pass on main and pin behaviour this PR must keep. Each test also fails on a mutant of the code it guards: no SPF guard, rid tie-break, no sort, no cache-hit filter, prompt-length sort, and a 31-token key.

## Speed Tests and Profiling

### Live-server probe (4x B200, TP4, SPF)

Why this workload: the bug is one request's wait, so a probe that creates the collision on purpose measures it directly. A plain AgentX A/B would depend on whether random session ids collide. Point: the TP4 point of the cookbook's B200 agentic recipe (server command above), where SPF and chunked prefill 8192 apply.

Each trial flushes the cache, then sends:
- X: 32 shared tokens + 150,000 random tokens (cold, long), together with four unrelated cold requests of 60K, 70K, 80K and 90K tokens. SPF prefills those four first, then X.
- S, 1 s later: the same 32 tokens + 400 random tokens. On main, the dedupe keeps X and holds S until X is admitted. With this PR, S runs at once and X is held.
- A control trial sends S' instead: 432 random tokens that share nothing with X.

TTFT is measured at the client (first streamed chunk; `max_new_tokens` 8, temperature 0). Each server starts with one uncounted warmup trial, because the first large prefill after a start is about 10 s slower in every arm, main and PR alike.

| Arm (in run order) | S TTFT, trial 1 / 2 (s) | S' TTFT, control (s) | X TTFT, mean (s) |
|---|---|---|---|
| main | 9.15 / 9.21 | 0.20 | 14.96 |
| this PR | 0.22 / 0.27 | 0.20 | 14.76 |
| this PR | 0.24 / 0.25 | 0.23 | 14.80 |
| main | 9.20 / 9.10 | 0.23 | 15.00 |

Run as `python3 probe_spf_dedupe.py --url http://127.0.0.1:30000 --out . --label A1 --warmup 1 --trials 2 --control 1`.

<details><summary>probe_spf_dedupe.py</summary>

```python
"""Live-server probe: under SPF, does a short request that shares 32 tokens with a queued long cold one wait for it?

Against one running SGLang server (shortest-prefill-first), per trial:
  t=0      X  = P32 + x_len random ids (cold, long) and Z1..Zk = unrelated cold requests (z_lens), each with a
           distinct first token. SPF prefills Z1..Zk first (shortest first), then X.
  t=delay  S  = P32 + s_len random ids: shares exactly 32 tokens (the dedupe threshold) with the still-queued X.
           On main the dedupe walks queue order, keeps X and holds S behind every request until X is admitted;
           with the PR it walks shortest-first, so S runs at once and X is the one held.
  control  S' = s_len + 32 random ids sharing nothing with X (admitted at once on both trees).
All requests go to /generate with input_ids, temperature 0, max_new_tokens 8, ignore_eos, streaming; TTFT is the
client-side time to the first streamed chunk. /flush_cache runs before every trial, so no trial reuses cache.
Token ids are drawn from [1000, 100000) with a per-trial seed. --warmup runs uncounted trials first.
Usage: probe_spf_dedupe.py --url URL --out DIR --label L [--trials 2] [--control 1] [--x-len 150000]
       [--z-lens 60000,70000,80000,90000] [--s-len 400] [--s-delay 1.0] [--seed 46022] [--calibrate]
"""
import argparse
import json
import random
import threading
import time

import requests


def gen_ids(rng, n, first=None):
    ids = [rng.randrange(1000, 100000) for _ in range(n)]
    if first is not None and n:
        ids[0] = first
    return ids


def flush(url):
    for _ in range(120):
        try:
            r = requests.post(url + "/flush_cache", timeout=30)
            if r.status_code == 200:
                return True
        except requests.RequestException:
            pass
        time.sleep(1)
    return False


def send(url, name, ids, rec, t_base):
    body = {"input_ids": ids, "stream": True,
            "sampling_params": {"temperature": 0, "max_new_tokens": 8, "ignore_eos": True}}
    r0 = time.time()
    rec[name] = {"len": len(ids), "send": r0 - t_base}
    try:
        with requests.post(url + "/generate", json=body, stream=True, timeout=900) as resp:
            resp.raise_for_status()
            last = None
            for line in resp.iter_lines():
                if not line or not line.startswith(b"data:"):
                    continue
                data = line[5:].strip()
                if data == b"[DONE]":
                    break
                if "first" not in rec[name]:
                    rec[name]["first"] = time.time() - t_base
                last = json.loads(data)
            rec[name]["end"] = time.time() - t_base
            meta = (last or {}).get("meta_info", {})
            rec[name]["output_ids"] = (last or {}).get("output_ids")
            rec[name]["meta"] = {k: meta.get(k) for k in ("prompt_tokens", "cached_tokens", "completion_tokens",
                                                           "e2e_latency", "spec_verify_ct", "finish_reason")}
    except Exception as e:  # recorded, judged by the analysis
        rec[name]["error"] = repr(e)
    if "first" in rec[name]:
        rec[name]["ttft"] = rec[name]["first"] - rec[name]["send"]


def trial(url, kind, k, seed, x_len, z_lens, s_len, s_delay):
    rng = random.Random(seed * 1000 + k)
    p32 = gen_ids(rng, 32, first=500)
    reqs = {"X": p32 + gen_ids(rng, x_len)}
    for i, n in enumerate(z_lens):
        reqs[f"Z{i + 1}"] = gen_ids(rng, n, first=600 + i)
    if kind == "control":
        reqs["S"] = gen_ids(rng, s_len + 32, first=700)
    else:
        reqs["S"] = p32 + gen_ids(rng, s_len)
    assert flush(url), "flush_cache did not succeed"
    rec = {}
    t_base = time.time()
    threads = [threading.Thread(target=send, args=(url, n, reqs[n], rec, t_base)) for n in reqs if n != "S"]
    for t in threads:
        t.start()
    time.sleep(max(0.0, s_delay - (time.time() - t_base)))
    ts = threading.Thread(target=send, args=(url, "S", reqs["S"], rec, t_base))
    ts.start()
    for t in threads + [ts]:
        t.join()
    return {"kind": kind, "k": k, "t_base_unix": t_base,
            "t_base_local": time.strftime("%Y-%m-%d %H:%M:%S", time.localtime(t_base)),
            "x_len": x_len, "z_lens": z_lens, "s_len": s_len, "s_delay": s_delay,
            "makespan": max(v.get("end", float("nan")) for v in rec.values()), "reqs": rec}


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--url", required=True)
    ap.add_argument("--out", required=True)
    ap.add_argument("--label", required=True)
    ap.add_argument("--trials", type=int, default=2)
    ap.add_argument("--control", type=int, default=1)
    ap.add_argument("--x-len", type=int, default=150000)
    ap.add_argument("--z-lens", default="60000,70000,80000,90000")
    ap.add_argument("--s-len", type=int, default=400)
    ap.add_argument("--s-delay", type=float, default=1.0)
    ap.add_argument("--seed", type=int, default=46022)
    ap.add_argument("--calibrate", action="store_true")
    # uncounted trials right after server start: the first large prefill after a start is ~10 s slower
    ap.add_argument("--warmup", type=int, default=0)
    a = ap.parse_args()
    z = [int(v) for v in a.z_lens.split(",")]
    results = []
    for k in range(a.warmup):
        results.append(trial(a.url, "warmup", 90 + k, a.seed, a.x_len, z, a.s_len, a.s_delay))
    if a.calibrate:
        results.append(trial(a.url, "calibration", 99, a.seed, a.x_len, z, a.s_len, a.s_delay))
        print(json.dumps({"calibration_S_ttft": results[-1]["reqs"]["S"].get("ttft")}), flush=True)
    for k in range(a.trials):
        results.append(trial(a.url, "probe", k, a.seed, a.x_len, z, a.s_len, a.s_delay))
    for k in range(a.control):
        results.append(trial(a.url, "control", 50 + k, a.seed, a.x_len, z, a.s_len, a.s_delay))
    json.dump({"label": a.label, "trials": results}, open(f"{a.out}/probe_{a.label}.json", "w"), indent=1)
    for t in results:
        r = t["reqs"]
        print(json.dumps({"label": a.label, "kind": t["kind"], "k": t["k"],
                          "S_ttft": r["S"].get("ttft"), "X_ttft": r["X"].get("ttft"),
                          "makespan": t["makespan"], "errors": [n for n in r if "error" in r[n]]}), flush=True)


if __name__ == "__main__":
    main()
```

### Where this shows up: GB300 AgentX runs

We hit this on GB300 with DeepSeek-V4.1-Flash (TP4, SPF, chunked prefill 8192, 256-token pages, 32 concurrent multi-turn agentic sessions from the InferenceX AgentX benchmark). Every prompt starts with the same 31 tokens (a fixed system prompt and a `[rid:` marker), then a random per-session id. Two sessions whose ids start with the same token share at least 32 tokens, which is enough to trigger the dedupe. With 256-token pages the KV cache never reuses such a short overlap, so here the dedupe only delays the short request. Time to first token in two GB300 runs without this fix:

| Short request | Waited | Held behind (shares ≥ 32 tokens with it) |
|---|---:|---|
| 425 tokens | 496 s | a 465K-token cold request |
| 299 tokens | 158 s | a 258K-token cold request |
| 807 tokens | 114 s | a 335K-token cold request |

The id collision only made it visible: any short request that shares 32 or more tokens with a long cold request queued ahead of it waits the same way.

Trace-replay simulation of the scheduler on these two runs (internal tool, not attached; its request-level fidelity is about 10%):
- With main's dedupe rule it reproduces the three waits: 513 s, 154 s and 120 s, against 496 s, 158 s and 114 s measured. With this change they drop to 0.5-0.6 s.
- 16 random session-id draws per trace (first / second run): short cold requests (< 4K tokens) that wait 20 s or more go from 0.50 and 0.25 per run to 0. Means over the draws: p90 TTFT -0.8% / -2.8%, p90 end-to-end time per output token -0.6% / -0.8%, p90 ITL and throughput within 0.2%.
- p99 TTFT moves both ways: mean -4.2% / +2.8%, median 0 / 0, p10 of the draws -22% / -7%, p90 +5% / +16%. That spread is the trade-off above: in a draw without the bug, the held longer request now waits behind unrelated requests while a shorter member of its group is queued.

[by Claude Code] **Severity: nit | Confidence: High**

**Issue**

The second loop binds the 32-token dedupe key to `prefix_ids`, the same name the first loop uses for the full `origin_input_ids + output_ids`. The first loop calls this value `key_ids`. A reader of the second loop alone sees `RadixKey(token_ids=prefix_ids, ...)` and `torch.empty(len(prefix_ids), ...)` and can think the whole prompt goes into `waiting_queue_radix_tree`.

**Fix**

Use one name in both loops, for example `for r, key_ids in candidates:`, and pass `key_ids` to the match, the insert, and `torch.empty`.
