# [Fix] Apply user stop strings only to the final answer, not the reasoning section

[Upstream PR](https://github.com/sgl-project/sglang/pull/47863) · state: open · merged: False

## Original PR description

## Motivation

With a reasoning parser the request starts inside the reasoning section, and models often quote the user's stop string while thinking. The scheduler matches `stop` strings and `stop_regex` over the whole output, so the request finishes in the middle of the reasoning: the client gets `content == ""` with `finish_reason == "stop"` and no error.

Reproduced on Qwen3.8-27B (`--reasoning-parser qwen3`, thinking on), prompt `What is 12*12? Answer with just the number.` with `stop=["144"]`: the model writes `12*12 = 144` in its reasoning, the request ends there and the answer is never produced. The same happens with `stop=["gamma"]` for a prompt that asks the model to write `alpha beta gamma delta`. This is easy to hit unintentionally, since eval harnesses send task stop strings on every request.

Three places treat reasoning text as stop-eligible:

1. `Req.update_finish_state` checks stop strings on every token, including while the think-end marker has not been seen.
2. Once `</think>` arrives, the stop tail window (`tail_str`, `_locate_str_stop_finished_len`) still holds the last reasoning tokens, so a string quoted in the reasoning matches one step later (or in the same step under speculative decoding).
3. `DetokenizerManager.trim_matched_stop` cuts at the first occurrence of the matched string, i.e. inside the reasoning, which empties the content even when the scheduler stopped at the right place.

Related, still open: #33152 and #33151 cover the gate and the `rfind`; they do not handle the tail window after the marker (2), which is what makes the gate alone insufficient in the live test below.

## Modifications

- `Req` records `_reasoning_end_idx`, the `output_ids` index just past the think-end marker (set in `update_reasoning_tokens`).
- `update_finish_state` skips the stop-string/regex check while `require_reasoning` is set and the reasoning section is open (`_in_reasoning()`).
- `_stop_match_tail_len` never reaches back past `_reasoning_end_idx`, so stop matching after the marker only sees the answer; `tail_str` returns `""` for an empty window. This also covers a speculative chunk that carries both the marker and answer tokens.
- `check_match_stop_str_prefix` (streaming hold-back) is inactive while reasoning is open.
- `trim_matched_stop` uses `rfind`: the hit that ended the request is the last occurrence.
- `stop_token_ids`, EOS, `max_new_tokens`, and requests without a reasoning parser (or with `enable_thinking=false`) are unchanged. For models that open the reasoning themselves (`update_self_opened_reasoning_tokens`) the stop gate stays off, but once the marker is seen stop matching starts after it.
- Tests: `TestStopStrSkipsReasoning` (6 cases) in `test_stop_str_speculative.py` and one case in `test_trim_matched_stop.py`. All 7 fail on the parent commit and pass here.

## Accuracy Tests

No forward or kernel change. Live check, Qwen3.8-27B NVFP4 + MTP-style EAGLE, `--reasoning-parser qwen3`, 1×RTX PRO 6000, release/v0.5.23 image with the patch overlaid (the same two commits cherry-picked; this branch is rebased on current `main`, covered by the unit tests only). `temperature 0.6`, `max_tokens` 1024:

| request | before | after |
|---|---|---|
| `12*12`, `stop=["144"]` (×3) | `content=''`, reasoning cut at `12*12 = ` | `content='\n\n'`, reasoning complete |
| "write alpha beta gamma delta", `stop=["gamma"]` (×6) | `content=''` | `content='\n\nalpha beta '` |
| same two prompts, `stream=true` | `content=''` | `'\n\n'` / `'\n\nalpha beta '` |
| no stop | `'\n\n144'` | `'\n\n144'` |

Few samples per row, so this is a functional check rather than a statistic.

Also run against a production deployment (1×H200, Qwen3.8-27B-FP8, `--attention-backend fa3`, EAGLE, HiCache, 1M context, `--reasoning-parser qwen3 --tool-call-parser qwen3_coder`, release/v0.5.23 with this patch mounted): same results as the table, including the streaming cases.

File: `python/sglang/srt/managers/detokenizer_manager.py` · line 183

This rfind picks the wrong hit when the token that ends the request contains the stop string more than once. On the Qwen2.5/Qwen3 vocab `\n\n\n\n` is a single token (1022), so with `stop=["\n\n"]` an output of "The answer is 42" plus that token now comes back as `"The answer is 42\n\n"` instead of `"The answer is 42"`, and `\n\n\n` (1406) leaves a stray `\n`. It doesn't need a reasoning parser to trigger, and `\n\n` is a common eval stop. Could it search forward from where the last token's text starts, or from the reasoning end, instead of taking the last occurrence?
