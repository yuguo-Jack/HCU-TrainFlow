## Motivation

<!-- Describe the purpose and goals of this pull request. -->
GLM-OCR runs on Ascend A3 out of the box, but with one defect that silently corrupts accuracy instead of raising: `MRotaryEmbedding.forward_npu` passes a literal `mrope_section=[0, 0, 0]` to `torch_npu.npu_mrope`.

Per the CANN op documentation, `mrope_section=[0, 0, 0]` means **M-RoPE is not enabled** — the op falls back to plain 1D RoPE. The section is what tells the kernel how the head's rotary lanes are split across the temporal / height / width axes.

GLM-OCR configures `mrope_section=[16, 24, 24]` (sums to `rotary_dim / 2 = 64`, exactly the constraint CANN documents) and asserts `(3, seq_len)` positions for image prefill (`python/sglang/srt/models/glm4v.py`). So on NPU the h/w axes were being dropped and multimodal prompts received degenerate 1D positions, while the CUDA path (`forward_cuda` → `forward_triton`) applied the section correctly. The failure is silent: the output looks plausible, accuracy just degrades.

## Modifications

<!-- Detail the changes made in this pull request. -->
**1. `python/sglang/srt/layers/rotary_embedding/mrope.py`** (+4/−1) — pass the real section when the input actually is M-RoPE, and keep `[0, 0, 0]` (the "not M-RoPE" sentinel) otherwise:

```diff
         rotary_mode = "half" if self.is_neox_style else "interleave"
-        mrope_section = [0, 0, 0]
+        # npu_mrope reads an all-zero section as "M-RoPE disabled"; pass the real
+        # split when the positions carry the three axes.
+        is_mrope = positions.ndim == 2 and self.mrope_section
+        mrope_section = self.mrope_section if is_mrope else [0, 0, 0]
         query_out, key_out = torch_npu.npu_mrope(
```

This keeps the CANN fused op for the common (non-interleaved) case.

**2. `docs/docs/hardware-platforms/ascend-npus/reference/support_models.mdx`** (+6) — add a GLM-OCR row to the Multimodal table. 

**3. `test/registered/rotary/test_mrope_npu.py`** (new) — regression test.

## Accuracy Tests

<!-- If this pull request affects model outputs (e.g., changes to the kernel or model forward code), provide accuracy test results. -->
Numerical, on Ascend NPU, three ways of computing the same M-RoPE:

| implementation | vs eager reference |
| --- | --- |
| `npu_mrope` with the real section (this PR) | bf16 rounding (max abs 0.0156) |
| `forward_triton` (the path CUDA uses) | bf16 rounding (max abs 0.0156) |
| `npu_mrope` with `[0,0,0]` (before) | **max abs 1.84 → 4.38**, growing with sequence length |

On NPU, `forward_npu` (this PR) and `forward_triton` are **bit-identical** (`torch.equal` true across seeds). `forward_triton` is the path CUDA takes for sectioned M-RoPE, so the NPU path now applies the same algorithm with the same section, instead of collapsing to 1D.
End-to-end accuracy through the GLM-OCR official SDK self-hosted pipeline (PP-DocLayoutV3 layout → region crop → GLM-OCR → merge), OmniDocBench v1.6 `full` (1651 pages):

| metric | this run (A3) | published GLM-OCR |
| --- | --- | --- |
| Overall | **95.26** | 95.22 |
| Text Edit | **0.0378** | 0.0440 |
| Formula CDM | 96.4113 | **97.1800** |
| Table TEDS | **93.1399** | 92.8300 |
| Table TEDS-S | **95.7556** | 95.3900 |
| Read Order Edit | 0.1394 | **0.1330** |

The published column is Zhipu's cloud `layout_parsing` service, so the layout detector differs from the local PP-DocLayoutV3 used here; a gap within ~0.4 points is expected from that alone. Overall = `((1 − Text Edit) × 100 + TEDS + CDM) / 3`
