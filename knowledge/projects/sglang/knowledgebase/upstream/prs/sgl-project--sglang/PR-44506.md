# [Fix] [NPU] glm-ocr: Fix M-RoPE section for GLM-OCR on Ascend and add A3 validation

[Upstream PR](https://github.com/sgl-project/sglang/pull/44506) · state: closed · merged: True

## Original PR description

<!-- PR title: [Perf] [NPU] glm-ocr: Run 3-axis M-RoPE on the Triton kernel on Ascend -->

## Motivation

GLM-OCR on Ascend A3 applies M-RoPE for real: `mrope_section=[16,24,24]`, and image prefill carries `(3, seq_len)` positions. After `#32745` (merged), every 2-D position tensor is answered by `forward_native`, so those rotations are correct but computed by the eager path — and on this model it is not only prefill: `ForwardBatch._compute_mrope_positions_decode` repeats `seq_lens - 1` three times, so decode keeps the 2-D shape too and pays the eager path once per layer per step.

This PR sends that one case to the Triton kernel `forward_cuda` already uses for 3-axis positions. Measured end to end on 4×910: **output throughput +18.8 %, TPOT −1.55 ms (−17.5 %)**, request latency −15.6 %.

`torch_npu.npu_mrope` is not an alternative here: passing the real section repairs only the contiguous map, the interleaved map stays wrong (max abs 6.9 vs `forward_native`, versus 1.6e-2 for bf16 rounding) whichever section it is given, and CANN rejects splits outside its whitelist (`aclnnRopeWithSinCosCache`, error 161002). At 32k tokens the Triton kernel is also 1.45x faster than the fused op (2.77 vs 4.03 ms), so nothing is given up by moving this case off it.

## Modifications

**1. `python/sglang/srt/layers/rotary_embedding/mrope.py`** — send 2-D positions to the Triton kernel and keep the rest as it was:

```python
        assert positions.ndim == 1 or positions.ndim == 2
        if query.shape[0] == 0:
            return query, key
        self._match_cos_sin_cache_dtype(query)
        if positions.ndim == 2 and self.mrope_section:
            return self.forward_triton(positions, query, key)
        # 1-D text: the fused CANN op; an all-zero section means plain RoPE.
        if query.shape[1] > 4096:
            return self.forward_native(positions, query, key, fused_set_kv_buffer_arg)
```

The condition is the one `forward_cuda` already uses. Inside sglang a 2-D position tensor only comes from the M-RoPE index (`(3, seq_len)`, always with a section), and `Ernie4_5_VLRotaryEmbedding` overrides `forward()` and dispatches to its own kernels, so it never enters `forward_npu`. The 1-D branch is unchanged, including the `query.shape[1] > 4096` fallback; the 0-token early return and the cos/sin cache dtype match are new relative to `#32745`.

**2. `test/registered/rotary/test_mrope_npu.py`** (new) — compares `forward_npu` with `forward_native` for the contiguous, interleaved and glm-interleaved maps, at fp32 and bf16, plus the 1-D and 0-token paths. Registered as `register_npu_ci(est_time=30, suite="full-1-npu-a3", nightly=True)`, next to the existing cpu and amd files in `test/registered/rotary/`; verified to fail on the pre-fix code and pass with it.

**3. `docs/docs/hardware-platforms/ascend-npus/reference/support_models.mdx`** (+6) — add the GLM-OCR row (A3) to the Multimodal table.

## Accuracy Tests

Against `forward_native` on NPU, over the three axis maps: fp32 is bit-identical, bf16 is within 1 ulp (max abs 0.031). The alternative — passing the real section to `npu_mrope` — is off by 2.0 (contiguous) / 6.9 (interleaved) on 2-D input, and an interleaved map is off by 6.9 even with the real section.

End-to-end through the GLM-OCR official SDK self-hosted pipeline (PP-DocLayoutV3 layout → region crop → GLM-OCR → merge), OmniDocBench v1.6 `full` (1651 pages, Ascend A3):

| metric          | this branch | published GLM-OCR |
| --------------- | ----------- | ----------------- |
| Overall         | **95.26**   | 95.22             |
| Text Edit       | **0.0378**  | 0.0440            |
| Formula CDM     | 96.4113     | **97.1800**       |
| Table TEDS      | **93.1399** | 92.8300           |
| Table TEDS-S    | **95.7556** | 95.3900           |
| Read Order Edit | 0.1394      | **0.1330**        |

The published column is Zhipu's cloud `layout_parsing` service, so the layout detector differs from the local PP-DocLayoutV3 used here; a gap within ~0.4 points is expected from that alone. Overall = `((1 − Text Edit) × 100 + TEDS + CDM) / 3`.

## Speed Tests and Profiling

### End to end A/B (4×910)

ABBA so drift cancels: arm A = current main (`#32745`, 2-D → `forward_native`), arm B = this PR. Same weights, same image, only `mrope.py` replaced.

4×910, `--tp 4`, `--mem-fraction-static 0.70 --chunked-prefill-size 32768 --max-prefill-tokens 65536`; first 10 pages of the OmniDocBench v1.6 demo set sent as whole pages, concurrency 1, `max_tokens=256 temperature=0 ignore_eos=true` (same output length in both arms).

| run        | output tok/s | TPOT        | request mean |
| ---------- | ------------ | ----------- | ------------ |
| A1         | 65.70        | 8.91 ms     | 3.893 s      |
| B1         | 76.01        | 7.39 ms     | 3.365 s      |
| B2         | 88.19        | 7.21 ms     | 2.899 s      |
| A2         | 72.53        | 8.79 ms     | 3.526 s      |
| **A mean** | **69.1**     | **8.85 ms** | 3.71 s       |
| **B mean** | **82.1**     | **7.30 ms** | 3.13 s       |

TTFT is inside the noise on this set (pages span 4.2k–6.1k prompt tokens) and is not part of the claim. The gain lands on decode: under graph replay the change replaces ~15 eager nodes per layer with one kernel, which is why the per-token saving is 1.55 ms and not `layers × operator time`.

### Single call of the rotation (1×910)

One 910 chip, GLM-OCR shapes (`head_size = rotary_dim = 128`, `heads/kv_heads = 16/8`, `mrope_section = [16,24,24]`), bf16, median of 30 after 10 warmups.

#### Contiguous map (GLM-OCR)

| seq   | native (ms) | triton (ms) | speedup |
| ----- | ----------- | ----------- | ------- |
| 1024  | 0.479       | 0.172       | 2.79x   |
| 4096  | 0.715       | 0.421       | 1.70x   |
| 32768 | 4.942       | 2.773       | 1.78x   |

#### Interleaved map (Qwen2-VL)

| seq   | native (ms) | triton (ms) | speedup |
| ----- | ----------- | ----------- | ------- |
| 1024  | 1.022       | 0.199       | 5.13x   |
| 4096  | 1.763       | 0.507       | 3.47x   |
| 32768 | 10.759      | 3.465       | 3.10x   |

fp32 gains are larger (2.12x at 4096, 2.89x at 32768). The interleaved map gains more than the contiguous one because native does it as a series of copies.

## Relationship to other PRs

`#32745` (merged) introduced the behaviour this PR refines: it sends every 2-D input to `forward_native`. This PR changes only the case that has an axis map; the "2-D without a section" and "1-D" branches behave as before. The dispatch test that `#32745` added (`test_npu_dispatch_preserves_multimodal_positions`) needs the same edit — 2-D to `forward_triton`, 1-D to `npu_mrope` — and lands with the rebase onto main.
