# [BugFix] Fix fake KV sender completion for chunked prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/29757) · state: closed · merged: False

## Original PR description

## Motivation

`FakeKVSender.poll()` reported `Success` after the first `send()`. During
chunked prefill, this let the scheduler remove the request from the inflight
queue before the remaining chunks were sent and released. After enough
requests, the scheduler could detect leaked KV pool memory and terminate.

A zero-page request never calls `send()`, so the fake sender must also
distinguish a request that has not been initialized from a valid `init(0)`
request that can complete immediately.

## Modifications

- Align `FakeKVSender.init()` with the `BaseKVSender` / `CommonKVSender`
  contract by recording the expected number of KV page indices.
- Accumulate the page indices received by each `send()` and report `Success`
  only after initialization and after all expected pages have been sent.
- Add focused CPU unit coverage for pre-init polling, single- and multi-chunk
  transfers, zero-page requests, and skipped empty chunks.

## Tests

- Focused CPU/import-stub test: `5 passed`.
- Pre-fix negative control: `3 failed, 2 passed`.
- Independently validated in a prefill-only deployment in
  [this review comment](https://github.com/sgl-project/sglang/pull/29757#issuecomment-5581459573).

- qidaye · COMMENTED · 2026-09-09T09:15:19Z · [source](https://github.com/sgl-project/sglang/pull/29757#pullrequestreview-5152228882)

Thanks for the rebase and for narrowing the scope — the split is exactly right. The
`fake/conn.py` completion fix stands on its own, and keeping the cache-insert default
out of this PR leaves it easy to review.

I re-read the narrowed diff and ran the new test locally:
`test/registered/unit/disaggregation/test_fake_sender_chunked.py` -> `5 passed`,
black/isort clean.

What I verified:

- `init(num_kv_indices: int, ...)` now matches `BaseKVSender.init` (base/conn.py:141)
  and `CommonKVSender.init` (common/conn.py:1265). The only caller in the tree,
  `prefill.py:392`, passes `num_pages`, and `send()` at `prefill.py:1414` receives
  page indices, so the units on both sides of the counter line up.
- `poll()` gating on `self.curr_idx < self.num_kv_indices` (fake/conn.py:56) is
  deliberately more forgiving than `CommonKVSender`'s
  `is_last_chunk = self.curr_idx == self.num_kv_indices` (common/conn.py:1312): an
  overshoot cannot wedge the request. I like that choice.
- Pre-init `poll()` still returns `WaitingForInput`, the same as the old
  `has_sent = False` path, so warmup requests see no behavior change, and no
  non-fake backend is touched.

Non-blocking comments:

1. `test_fake_sender_chunked.py:56` — `test_skipped_empty_chunk_does_not_block_conclusion`
   never actually sends an empty chunk; it is structurally the same as
   `test_chunked_request_only_concludes_on_last_chunk` above it. The property that
   really matters here is that `FakeKVSender` inherits the base
   `should_send_kv_chunk` (`num_pages > 0`, base/conn.py:163) rather than
   `CommonKVSender`'s `num_pages > 0 or last_chunk` (common/conn.py:1276), so a
   skipped chunk contributes zero to the counter and cannot strand the request.
   Suggest making that explicit:

   ```python
   def test_skipped_empty_chunk_does_not_block_conclusion(self):
       sender = _make_sender(num_pages=6)
       sender.send(np.arange(4, dtype=np.int32))
       self.assertEqual(sender.poll(), KVPoll.WaitingForInput)
       # A chunk the scheduler would skip contributes nothing.
       self.assertFalse(sender.should_send_kv_chunk(0, last_chunk=False))
       sender.send(np.empty(0, dtype=np.int32))
       self.assertEqual(sender.poll(), KVPoll.WaitingForInput)
       sender.send(np.arange(4, 6, dtype=np.int32))
       self.assertEqual(sender.poll(), KVPoll.Success)
   ```

2. `test_fake_sender_chunked.py` — four boundaries are worth pinning while you are
   in here, since they are all one-liners against the new state machine:
   `abort()` -> `Failed` (both before and after `init`), the terminal state staying
   latched across repeated `poll()` calls, a `send()` arriving after `Success`, and
   an overshoot (`send` totalling more than `num_kv_indices`) still concluding. The
   last one is what documents the `<` vs `==` choice noted above.

3. `test_fake_sender_chunked.py:37,43,58` — the tests pass Python lists where the
   signature is `npt.NDArray[np.int32]` (fake/conn.py:78). `np.arange(n, dtype=np.int32)`
   keeps the test on the real contract, and makes the empty-chunk case above natural
   to write.

4. `fake/conn.py:71` — `init()` sets `num_kv_indices` but leaves `curr_idx` as is.
   I could not find a reachable path today that re-inits a sender after a `send()`
   (`optimistic_release_and_requeue` only fires while `req.pending_bootstrap` is
   still true, i.e. before `finalize_bootstrap` has called `init`), and
   `CommonKVSender` has the same shape, so this is not a bug report. But now that
   `curr_idx` is a real counter rather than a boolean, `self.curr_idx = 0` in
   `init()` makes re-initialization safe for free.

5. `fake/conn.py:53-61` — the `# Assume handshake completed instantly` /
   `# Assume transfer completed instantly` comments went away with the old flag. One
   line stating the new invariant (the fake transfer is still instantaneous; the poll
   only withholds `Success` until the page count announced by `init()` has been
   handed to `send()`) would save the next reader a trip to `prefill.py`.

6. `test_fake_sender_chunked.py:8` — `est_time=2` is low next to its neighbours in
   the same directory (10-12) given that importing sglang alone dominates the ~6s
   wall time here. It only affects shard balancing, not the derived timeout, but ~10
   would match the file's actual cost.

One thing worth stating explicitly for the record: this change trades "concludes too
early, so the remaining chunks' KV leaks" for "never concludes, so the request sits in
the inflight queue" if the summed page count ever undershoots `num_pages`. That is the
same invariant `CommonKVSender` already relies on for `is_last_chunk`, so I think it is
the right trade — just noting it so the failure mode is documented if it ever shows up.

None of the above is blocking. We independently observed the pre-fix behavior in our
own deployment (chunked requests popped from the inflight queue after the first
`send()`, with the remaining pages never released), and the narrowed change fixes it
cleanly. LGTM once you decide what to do with the test-coverage points — happy to
approve as is if you would rather land it and follow up.

- ShangmingCai · comment · 2026-11-02T09:13:02Z · [source](https://github.com/sgl-project/sglang/pull/29757#issuecomment-6573353607)

Hi @imReese, thanks for the fix and for narrowing the scope. Thanks also to @qidaye for the independent validation.

I re-checked this against current main, and I don't think it's needed anymore, so I'm going to close it. Here's why:

- The early-Success case can't happen on main. The prefill scheduler only polls a sender before init(), before any chunk is sent, or after the last chunk is sent. Requests enter disagg_prefill_transfer_queue in one place only (process_batch_result_disagg_prefill), and send_kv_chunk(last_chunk=True) runs in that same pass. A request still waiting on bootstrap has sent nothing, because middle-chunk sends and the early prefix send are skipped until bootstrap finishes. So "Success after the first chunk" never reaches the transfer queue.
- #28652 has since changed FakeKVSender. It deliberately kept the "any chunk counts" behavior and added a waiting timeout plus should_send_kv_chunk. This branch now conflicts with that change.
- Verification: I replayed main's scheduler call order against both versions. That covered chunk sizes, page sizes, the early prefix send, staging grids, DCP segments, zero-page last chunks and aborts: 34k cases, no differences. The two versions only diverge if a poll is inserted between chunks, which the scheduler doesn't do.
- The new test is stale. It constructs FakeKVSender with dest_tp_ranks / pp_rank, which #42348 removed, so it errors on main.

If you saw the leak on a recent build, please open an issue with the version and launch flags. It may come from somewhere else, possibly the radix-cache part that was split out to #37024, and we'd be glad to look into it. Thanks again for the contribution!
