# [NPU] Init Mooncake transfer engine on the caller thread for Ascend t…

[Upstream PR](https://github.com/sgl-project/sglang/pull/44384) · state: closed · merged: False

## Original PR description

Title
[NPU] Init Mooncake transfer engine on the caller thread for Ascend transport


Body
Motivation
On Ascend (ENABLE_ASCEND_TRANSFER_WITH_MOONCAKE=1), SGLang fails at startup with:

RuntimeError: Mooncake Transfer Engine initialization failed.


The shared MooncakeTransferEngine.initialize() wraps engine.initialize(...) in run_with_deadline, which executes the callable on a freshly spawned daemon thread.

Device selection is thread-local: torch.npu.set_device() does not propagate from the calling thread to a new thread (pytorch/pytorch#56588). On NPU the device context the Ascend direct transport needs is established on the sglang side — [bootstrap.py](vscode-webview://145o48qm8kk44qos03rfouorc575u7eda3b5c5i5h4fp9l8d9tcp/python/sglang/srt/distributed/bootstrap.py:127) runs torch.get_device_module(device).set_device(get_device().gpu_id) on the main thread, and the Ascend transport relies on it. Since that context is set on the main thread while engine.initialize() runs on the worker thread, the Ascend transport initializes without a device context and returns non-zero.

On GPU this never surfaced: Mooncake's C++ layer brings up the NIC context_list_ itself, independently of the torch/ACL current-device state.

Modifications
[MooncakeTransferEngine.initialize()](vscode-webview://145o48qm8kk44qos03rfouorc575u7eda3b5c5i5h4fp9l8d9tcp/python/sglang/srt/distributed/device_communicators/mooncake_transfer_engine.py:195) now initializes the engine on the current thread for the Ascend transport, instead of routing it through run_with_deadline:

Ascend (protocol == "ascend"): call self.engine.initialize(...) directly on the calling thread — the same thread bootstrap.py selected the device on, and the same thread the later register_memory / transfer_sync calls run on. No thread hop, so the NPU device context is inherently correct and no worker-thread set_device workaround is needed. This also mirrors the memfabric-based [AscendTransferEngine.initialize()](vscode-webview://145o48qm8kk44qos03rfouorc575u7eda3b5c5i5h4fp9l8d9tcp/python/sglang/srt/disaggregation/ascend/transfer_engine.py:59), which initializes on the main thread without run_with_deadline.
All other transports (rdma / efa / tcp): unchanged — still wrapped in run_with_deadline(...) with SGLANG_DISAGGREGATION_ENGINE_INIT_TIMEOUT, so GPU keeps its init fail-fast guard.
The suffix used for the Mooncake ascend handshake keeps using the physical NPU id (ASCEND_NPU_PHY_ID override), which is distinct from the logical torch id used elsewhere — now documented with a comment.

On the init timeout (please review)
The Ascend branch of Mooncake TE init intentionally does not apply a timeout, for two reasons:

Consistency with the Ascend transfer engine. The Ascend TE path ([AscendTransferEngine.initialize()](vscode-webview://145o48qm8kk44qos03rfouorc575u7eda3b5c5i5h4fp9l8d9tcp/python/sglang/srt/disaggregation/ascend/transfer_engine.py:59), memfabric-based) already initializes on the calling thread with no run_with_deadline/timeout guard. Keeping Mooncake TE on the same NPU side timeout-free makes the two Ascend initialization paths behave identically, rather than diverging.
Correct device/thread affinity requires running on the caller thread; run_with_deadline's worker thread is what breaks the NPU context in the first place, and it cannot be cancelled on timeout (it only leaks until process exit).
If a timeout is desired on the NPU/Ascend path, please say so and I will add it — e.g. guard the direct call with the same SGLANG_DISAGGREGATION_ENGINE_INIT_TIMEOUT boundary (or restore run_with_deadline plus an in-thread set_device), depending on the preferred semantics.

Testing
Verify on NPU with PD disaggregation over Mooncake: server starts without RuntimeError: Mooncake Transfer Engine initialization failed.
Confirm the full data path on NPU — register_memory + transfer_sync — now that init and use share a thread.
Regression: CUDA PD disagg with --disaggregation-transfer-backend mooncake is unaffected (same run_with_deadline path as before).
