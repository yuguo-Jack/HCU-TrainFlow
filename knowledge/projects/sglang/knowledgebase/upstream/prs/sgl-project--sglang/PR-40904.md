# fix: harden detokenizer against custom tokenizers with stale/edge-case bugs

[Upstream PR](https://github.com/sgl-project/sglang/pull/40904) · state: closed · merged: False

## Original PR description

## Motivation

Diagnosing a real OOM-fix validation failure for `internlm/internlm3-8b-instruct` and `zai-org/chatglm2-6b` on Intel XPU surfaced two separate crashes in tokenizer handling that take down the whole detokenizer/scheduler process instead of failing gracefully for the one affected request.

## Modifications

- `DetokenizerManager`: both the batch (`_grouped_batch_decode`) and per-request decode paths called `tokenizer.decode()` with no guard against a custom `convert_tokens_to_string()` that assumes a non-empty token list. `skip_special_tokens=True` can legitimately filter every id out of a non-empty span, and some custom remote-code tokenizers (e.g. InternLM3's) raise `IndexError` on that instead of handling it. Added `_safe_decode()`, used by both paths, which returns `""` for that span instead of propagating.
- `patch_tokenizer.py`: some custom remote-code tokenizers (e.g. zai-org/chatglm2-6b's `ChatGLMTokenizer`) declare a fixed `_pad()` signature with no `padding_side` param and no `**kwargs`, predating newer `transformers` versions always forwarding `padding_side` down to `_pad()`. Every `tokenizer.encode()`/`pad()` call then raises `TypeError: ..._pad() got an unexpected keyword argument 'padding_side'`. Added a shim, following the existing Kimi tiktoken patch's pattern, that detects this structurally via `inspect` and drops the kwarg before delegating to the original `_pad()`.
