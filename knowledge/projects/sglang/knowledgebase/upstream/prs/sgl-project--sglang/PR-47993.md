# [Perf] [NVIDIA] qwen3: Reuse the table QK-norm/RoPE kernel for MRoPE decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/47993) · state: closed · merged: True

## Original PR description

## Motivation

#46908 fuses QK RMSNorm and RoPE into one Triton kernel (`table_qk_norm_rope_`) for dense text Qwen3 decode, behind `--enable-fused-qk-norm-rope`. Qwen3-VL uses the same `Qwen3Attention`, but its `MRotaryEmbedding` keeps it on the split path: JIT QK-norm, then `triton_mrope_fused`. This PR extends the table kernel to MRoPE. It supersedes #43425, which added a separate CUDA kernel for the same case.

## Modifications

- **`table_qk_norm_rope_`**
  - Takes `[3, T]` MRoPE positions (row-strided, as the decode graph runner passes them) plus `MRotaryEmbedding.axis_map`, and gathers each rotary lane's position from its own axis. Any positions are handled correctly, including precomputed spatial decode positions.
  - Accepts a BF16 rotary table. With one, it rotates in BF16 using `triton_mrope_fused`'s expression, so its output is bit-identical to the split MRoPE path.
  - Above 1024 (token, head) rows, each program handles eight heads over four warps, instead of one (token, head) per one-warp program. A `[heads, 32]` partial-sum tile keeps each head's reduction order, so the output stays bit-exact. With one head per program, the kernel's cost grew with tokens x heads and it lost to the split path at decode batches of 256-512; it now wins at every measured size (table below).
  - The rotation arithmetic is flattened into one shared multiply/add branch. The non-`match_cuda` path keeps one head per program and four warps, and its output is bit-identical to before (checked at head_dim 64/128/256).
- **`Qwen3Attention`**
  - The gate now also admits `MRotaryEmbedding` with an `mrope_section`, at head_dim 64 or 128. At head_dim 256, the table kernel's BF16 rotation isn't bit-exact with `triton_mrope_fused` (about 14% of elements differ by up to 1 ULP), so MRoPE at 256 keeps the split path. Plain RoPE still covers 64, 128 and 256.
  - With 2D positions, the layer first casts the rotary table to the activation dtype (`_match_cos_sin_cache_dtype`, the same cast the split path makes). The cast happens during graph warmup, not after capture.
  - MRoPE with 1D positions, extend, and speculative verify keep the split path.
- **Tests**
  - Kernel: BF16 table with distinct per-axis positions vs JIT QK-norm + `triton_mrope_fused`, bit for bit, at head_dim 64 and 128, for the section, interleaved, and GLM-interleaved layouts.
  - Kernel: new cases with head counts that aren't a multiple of 8, so the eight-heads-per-program path also runs partial head blocks.
  - Model: MRoPE layers in the dispatch and changing-input graph-replay tests, with distinct, row-strided axes. Graph replay includes batch 128 (1280 rows), which runs the eight-heads-per-program path inside a captured graph.
  - Model: MRoPE at head_dim 256 stays on the split path.
  - Model: 1D positions on an MRoPE layer stay on the split path.

The flag stays opt-in on CUDA.

## Accuracy

The fused path is bit-identical to the split path, so no accuracy eval was run.

- **Unit tests:** 78/78 pass on one B300 (SM 10.3): `test_table_qk_norm_rope.py` and `test_qwen3_qk_norm_rope.py`.
- **End-to-end:** `Qwen/Qwen3-VL-2B-Instruct`, TP1, default backends, decode CUDA graphs on, one B300. 6 concurrent greedy chat requests (2 with an image, 4 text-only), 256 tokens each. All 6 outputs are identical with the flag off and on. A call-recording hook on the flag-on server confirmed fused calls during capture of the bs=512 decode graph, with row-strided `[3, 512]` positions and a BF16 table.

## Benchmark

Kernel only, on one idle B300. Each value is the median per-call time in µs over 30 replays of a CUDA graph holding 100 calls. Setup: bf16, head_dim 128.
- **MRoPE:** BF16 table; split is JIT QK-norm + `triton_mrope_fused`.
- **Plain RoPE:** FP32 table; split is JIT QK-norm + `apply_rope_with_cos_sin_cache_inplace`.

Every row is bit-exact with the split path.

The fused path relies on _compute_mrope_positions_decode producing repeated positions. Its fallback path (has_precomputed_mrope) produces real spatial positions where the axes differ. If another model built on Qwen3Attention ever supplies precomputed decode positions, and the flag is on, it will produce silently wrong output, with no crash.

File: `python/sglang/srt/models/qwen3.py` · line 326

Agreed. A silently wrong fallback isn't acceptable. Fixed in b39e69bab3 and eee8d6713d by removing the assumption instead of documenting it.

The kernel now takes the full `[3, T]` MRoPE positions plus `MRotaryEmbedding.axis_map`, and gathers each rotary lane's position from its own axis. `triton_mrope_fused` does the same with its section masks, and `axis_map` encodes those masks exactly, including the interleaved and GLM-interleaved layouts. The result is correct for any decode positions, including precomputed spatial ones.

Tests now use distinct positions on each axis:
- **Kernel:** bit-exact against JIT QK-norm + `triton_mrope_fused` for the section, interleaved, and GLM-interleaved layouts.
- **Model:** the dispatch and CUDA-graph replay tests feed 2D positions with different rows.
