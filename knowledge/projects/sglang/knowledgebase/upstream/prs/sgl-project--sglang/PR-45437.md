# [Fix] srt: Pin the source address of TCP ZMQ connects for the peer allowlist

[Upstream PR](https://github.com/sgl-project/sglang/pull/45437) · state: closed · merged: True

## Original PR description

## Motivation

#45250 added `SGLANG_ZMQ_ALLOWED_PEERS`: TCP-bound IPC sockets admit only the listed peer addresses, and a multi-node data-parallel deployment lists the addresses of its own nodes. The check is on the source address of the incoming connection, and a plain `socket.connect("tcp://<peer>:<port>")` leaves the choice of source address to the kernel. On a host with several addresses, for example a container on host networking that owns one address of its own while the host has others, the kernel can pick an address that is not in the allowlist. ZAP then rejects the connection, and a PUSH socket with no admitted peer blocks forever on its first send, so the deployment hangs after start-up with no error. Connections to a peer on the same node keep working, because a connect to a local address uses that address as its source, which is why the hang shows up only across nodes.

## Modifications

- `python/sglang/srt/environ.py`: new `SGLANG_ZMQ_SOURCE_IP` (default unset), the source address for outgoing TCP IPC connects.
- `python/sglang/srt/utils/network.py`: new `zmq_connect(socket, endpoint)`. When `SGLANG_ZMQ_SOURCE_IP` is set and the endpoint is a TCP endpoint whose host is an IP literal of the same address family, it connects with libzmq's documented `tcp://<source_endpoint>;<endpoint>` form ([zmq_tcp(7)](https://libzmq.readthedocs.io/en/latest/zmq_tcp.html), "Connecting a socket"), here `tcp://<source>:0;<host>:<port>`, so the peer sees the pinned address. A hostname endpoint, an `ipc://` endpoint, an endpoint that already carries a source, a source of the other family, an invalid source, and an unset variable all connect exactly as before. `get_zmq_socket(..., bind=False)` now connects through it.
- `python/sglang/srt/managers/load_snapshot.py`: `ZmqLoadSnapshotWriter` connects through `zmq_connect` as well, since its reader is one of the allowlisting sockets.
- `test/registered/unit/utils/test_network.py` (new, `base-a-test-cpu`): the endpoint rewrite table above, and a regression test with real sockets: with an allowlist of `127.0.0.2`, a PUSH client connecting to a PULL from `get_zmq_socket` at `127.0.0.1` is not delivered, and the same client with `SGLANG_ZMQ_SOURCE_IP=127.0.0.2` is. The second case fails if `get_zmq_socket` goes back to a plain connect.

A multi-node deployment sets the variable on each node to that node's own allowlisted address, next to `SGLANG_ZMQ_ALLOWED_PEERS`. With the variable unset nothing changes. Every connect made through `get_zmq_socket(..., bind=False)` (the data-parallel controller's REQ socket, the multi-tokenizer PUSH sockets, the encoder-disaggregation sockets, the tracing PUSH socket) now goes through `zmq_connect`, so a deployment that sets the variable pins all of them, and the rewrite leaves `ipc://` endpoints alone. The KV-transfer sockets under `disaggregation/common/conn.py` call `connect` directly and are not touched.
