# [Fix] [AMD] diffusion: Keep gfx1250 FlyDSL BF16 attention out of torch.compile

[Upstream PR](https://github.com/sgl-project/sglang/pull/44671) · state: closed · merged: True

## Original PR description

## Motivation

**What goes wrong**
With `--enable-torch-compile`, the first DiT forward on gfx1250 fails inside the aiter attention backend with `RuntimeError: An MLIR function requires a Context but none was provided`. #27702 removed `@torch.compiler.disable` from `AITerImpl.forward` so the BF16 `aiter.flash_attn_func` call could be compiled. On gfx1250, aiter (ROCm/aiter#5168) routes that call to the FlyDSL `flash_attn_batch_m32x8` kernel, which JIT-compiles in Python. Dynamo traces into it (`torch_dynamo_resume_in_flash_attn_batch_m32x8_at_2181`), FlyDSL's `JitFunction.__call__` sees an MLIR context and takes the nested-trace branch, and `capture_user_location` then finds no context and raises.

**Where it shows up**
Only gfx1250 (MI450), with the aiter attention backend and torch.compile. It is not model-specific -- any diffusion model that selects the aiter backend hits it. Confirmed end to end on two, which compile very differently:

- **Wan2.2-T2V-A14B** -- `--enable-torch-compile true --regional-compile --attention-backend aiter`, `ENABLE_CK=1`. Warmup request fails in `DenoisingStage`.
- **FLUX.2-dev** -- `--enable-torch-compile true` (whole-transformer compile, no regional compile), `ENABLE_CK=0`. Request fails with the same `An MLIR function requires a Context`.

That the two differ in compile granularity (regional vs whole-transformer) and in `ENABLE_CK` and still fail identically is the point: the trigger is Dynamo reaching the FlyDSL dispatch, not any model-specific graph shape. Note `ENABLE_CK=0` does not avoid it either -- the FlyDSL attempt in `aiter/ops/mha.py` happens *before* the `if not ENABLE_CK:` branch, so turning CK off does not route around FlyDSL.

**Why the fix is gated on gfx1250 and not on ROCm**
gfx942/gfx950 are structurally immune, for two independent reasons:

1. The FlyDSL dispatch is arch-gated at the source. `aiter/ops/flydsl/fmha_kernels.py` makes `get_gfx() == "gfx1250"` the first condition of its support check, so on gfx942/gfx950 `flydsl_flash_attn_batch_func` returns `None` and FlyDSL is never entered.
2. Those arches fall through to the CK-tile / OPUS ASM kernels, which are `@compile_ops` stubs bound to precompiled pybind symbols and carry a registered fake-tensor implementation (`gen_fake=gen_mha_fwd_fake_tensors`). Dynamo records them as opaque graph nodes; no Python-level compilation runs during tracing.

FlyDSL is the opposite kind of object: a Python JIT that compiles MLIR at call time. Tracing it means Dynamo rewrites another compiler's dispatch internals, which is exactly what the `torch_dynamo_resume_in_*` frames in the traceback show.

So disabling compile across all of ROCm would add a graph break on gfx942/gfx950 that buys nothing and costs the fusion #27702 enabled there. Hence `USE_AITER_GFX1250` rather than `is_hip()`.

**How to fix**
On gfx1250, call the BF16 `flash_attn_func` through a `@torch.compiler.disable` helper, so the FlyDSL kernel runs eagerly while the rest of the DiT block stays compiled.

## Modifications

- `runtime/platforms/aiter.py`: add `USE_AITER_GFX1250`.
- `runtime/layers/attention/backends/aiter.py`: move the BF16 call into `_forward_bf16`; on gfx1250 route through `_forward_bf16_eager` (`@torch.compiler.disable`). gfx942/gfx950 and NVIDIA paths are unchanged.
- `test/unit/test_aiter_attention_impl.py`: regression test that compiles `AITerImpl.forward` with gfx1250 enabled and asserts `flash_attn_func` runs outside Dynamo. It fails on the pre-fix code (`[True] != [False]`) and passes with the fix.

## Benchmarking and Profiling

| Config | Before | After |
|---|---|---|
| Wan2.2-T2V-A14B, 1280x720x193f, 8 steps, denoise time per step | crash | 7.73 s |
| FLUX.2-dev, 720p, 50 steps, warmed request (warmup excluded) | crash | 48.88 s |

Both "before" cells are a hard failure, not a slow path: on current main these two configurations do not produce output at all, so there is no pre-fix number to compare against.

The extra cost is one graph break per attention call on gfx1250 only. Wrapping the FlyDSL path as an opaque custom op in aiter would remove it; then this workaround can be dropped.
