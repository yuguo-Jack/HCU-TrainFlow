# [Feature] Add public weight offloader factory and post-load hook

[Upstream PR](https://github.com/sgl-project/sglang/pull/43603) · state: open · merged: False

## Original PR description

## Motivation

Fixes #43139. General plugins can provide weight placement without wrapping private `ModelRunner.load_model` internals. This is independent of #43597.

## Modifications

- Add a public factory receiving frozen `OffloaderContext`. Return a runner-specific `BaseOffloader`, or `None` for native selection.
- Retain each runner's offloader. For targets, call `post_load_model` after platform processing and `post_init`, before subsequent model setup and memory sizing. Validate its returned module and release the temporary load-result reference. Drafts keep their existing `wrap_modules`-only lifecycle.
- Reject active providers combined with native offload flags or startup weight-loading overlap: overlap materializes final weights after this hook. Factory and placement failures stop initialization.
- Keep DeepGEMM's shared copy-engine choice conservative across live offloaders, so draft construction cannot erase a target's restriction. Track policies weakly without retaining them solely for this check.
- Document the entry point, lifecycle and replacement responsibilities; add registered CPU coverage.

Single-L4 live-server checks passed with Qwen3-0.6B, Torch 2.14.1+cu130, TP=1 and CUDA Graphs disabled. With no provider, an identity provider, and a CPU-offloading provider, three prompts per configuration produced identical text, token IDs and token log probabilities (72 generated token positions per configuration; maximum difference `0.0`, fixed tolerance `1e-3`). All measured requests followed HTTP readiness and completed built-in warmup, using seed 0.

The offloading provider relocated 276,861,440 bytes of CUDA parameters. `max_total_num_tokens` was 131,703 with no provider and with the identity provider, versus 134,135 with offloading (+2,432). This checks that the real KV budget reflects placement in this fixture; it is not an arbitrary-model accuracy or capacity guarantee.

A separate single-L4 comparison tested native `--cpu-offload-gb 1` against the plugin's late `OffloaderV1` placement with the same 1-GiB limit, Qwen3-0.6B and TP=1. Both captured a full decode CUDA Graph for batch size 1, with eager prefill, and completed 69 measured target-decode replays after readiness. Three prompts produced identical text, token IDs and log probabilities (24 tokens each; maximum difference `0.0`, fixed tolerance `1e-3`). Parameter layouts and placement matched: 880,932,864 CPU bytes and 311,166,976 CUDA bytes; both reported `max_total_num_tokens=139,922`. This validates the two tested placement paths, not arbitrary-provider equivalence.
