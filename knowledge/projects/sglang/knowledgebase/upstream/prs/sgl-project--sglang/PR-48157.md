# [Perf] [XPU] mamba: Fuse the Mamba-1 prefill selective scan into one Triton kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/48157) · state: open · merged: False

## Original PR description

## Motivation

Mamba-1 models (`MambaForCausalLM`, `FalconMambaForCausalLM`) run prefill through a per-token
PyTorch loop in `MambaMixer1._selective_scan`, which issues several small ops per token per layer.
On XPU, prefill throughput stays at about 210-220 prompt tokens/s for falcon-mamba-7b at TP2, at
batch 1 and 4 and at 512 and 1536 prompt tokens.

This PR adds a single-launch Triton varlen scan for Mamba-1 prefill and uses it on XPU. Other
devices are unchanged.

## Modifications

- **New kernel** `sglang.kernels.ops.mamba.triton_ops.mamba1_scan_prefill`, adapted from vLLM's
  XPU `_selective_scan_fwd_kernel` (vllm-project/vllm#43421, Apache-2.0). One launch covers the
  whole varlen prefill batch: softplus(dt), the recurrence in fp32, the D skip, the silu(gate)
  output gate, and the final state written back to `ssm_state[state_indices[i]]`. It reads
  SGLang's `(tokens, dim)` tensors through strides (no transposes) and resumes from the saved state
  when `has_initial[i]` is set (chunked prefill).
- **`MambaMixer1._forward_prefill`** calls the kernel on XPU. The per-token PyTorch loop stays as
  the path for other devices, and as a fallback on XPU.
- **New env var** `SGLANG_DISABLE_MAMBA1_TRITON_SCAN` (default `false`) in `environ.py`: a
  kill-switch that forces the PyTorch loop on XPU.
- **Decode is unchanged**: it still uses `selective_state_update` and reads the state that
  prefill writes, in the same layout and dtype as before.
- **New test** `test/registered/kernels/ops/mamba/test_mamba1_scan_prefill.py`, registered for
  `stage-b-test-1-gpu-xpu`:
  - A varlen batch against a reference recurrence, in fp32/fp16/bf16. It covers a channel count
    that isn't a multiple of the block size, mixed and absent `has_initial`, out-of-order state
    slots, strided x/gate as passed by the mixer, and checks that unused slots stay untouched.
  - A prompt scanned in two chunks equals a single pass (the chunked-prefill state handoff).
  - It can also run without a GPU via `TRITON_INTERPRET=1`.

## Accuracy Tests

Arc Pro B60, torch 2.13.0+xpu, Triton 3.7.2, bf16. "Kernel" is the default; "loop" is
`SGLANG_DISABLE_MAMBA1_TRITON_SCAN=1`. The unit, decode and e2e tests and the fp32 comparison were
rerun on this branch rebased onto `main` @ 035670b685, with identical results. That `main` pins
torch 2.14.0+xpu; these runs used 2.13.0+xpu.

**Teacher-forced vs an HF transformers fp32 CPU reference**: falcon-mamba-7b-instruct at TP2,
8 sequences, 1,899 scored tokens; logprob of the actual next token and top-1 agreement:

| | Top-1 agreement with fp32 | Mean \|Δ logprob\| | Max \|Δ logprob\| |
|---|---|---|---|
| Triton kernel | 1870/1899 (98.5%) | 0.0191 | 0.552 |
| PyTorch loop | 1865/1899 (98.2%) | 0.0199 | 0.553 |

The kernel and the loop are equally close to fp32: the top-1 gap is 5 of 1,899 tokens. An
earlier TP1 run with the same kernel gave 98.7% vs 98.5%.

**Run-to-run determinism** (falcon-mamba-7b, TP2): with the kernel, prompt logprobs from two
identical batched requests are bit-identical. With the loop they vary between runs by up to 0.90
on short prompts.

**gsm8k** (`sglang.test.few_shot_gsm8k`, 200 questions, falcon-mamba-7b, TP2): kernel 0.495
(0.5% invalid). The loop run hit `UR_RESULT_ERROR_DEVICE_LOST` inside the PyTorch loop partway
through and was not completed.

**Tests on XPU:**
- `test_mamba1_scan_prefill.py`: 13/13 pass.
- `test/registered/layers/mamba/test_mamba_ssm.py -k selective_state_update` (decode): 324 passed,
  16 skipped.
- `test/registered/e2e/xpu/test_xpu_mamba1_runtime.py`: 2/2 with the kernel and 2/2 with the loop.

## Speed Tests and Profiling

`python -m sglang.benchmark.one_batch_server --batch-size 1 4 --input-len 512 1536 --output-len 1`,
falcon-mamba-7b-instruct, TP2 on 2x Arc Pro B60, one run per point, measured before the rebase;
the two servers were measured one after the other:

| Batch x prompt tokens | Kernel | Loop | Speedup |
|---|---|---|---|
| 1 x 512 | 0.22 s | 2.45 s | 11x |
| 1 x 1536 | 0.35 s | 6.99 s | 20x |
| 4 x 512 | 0.41 s | 9.32 s | 23x |
| 4 x 1536 | 1.56 s | 27.70 s | 18x |

At batch 4, throughput is lower at 1536 than at 512 prompt tokens (3,948 vs 5,048 tok/s); I
have not profiled why.

## Notes

- **CUDA/ROCm are unchanged**: they keep the PyTorch loop. The kernel is plain Triton, but it
  has only been run on XPU and its block size was chosen there. Enabling it on other devices is a
  follow-up once it is benchmarked there.
- Accuracy numbers use falcon-mamba-7b. The smaller state-spaces checkpoints are not used for
  them because of a separate XPU rmsnorm issue that is unrelated to this PR.
- **Token-exact greedy comparisons** between the two paths are not meaningful at TP2 batched: the
  loop is not deterministic run to run (see above), so the fp32 comparison is used instead.
