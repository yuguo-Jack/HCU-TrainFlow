# [Perf] [AMD] aiter: FP8 Q for EAGLE target_verify and draft_extend attention with an FP8 KV cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/47430) · state: open · merged: False

## Original PR description


## Motivation

With `--attention-backend aiter` and an FP8 KV cache, `forward_decode` quantizes Q to FP8 (`_quantize_q_fp8`, the static q scale) before
calling aiter's `unified_attention`. The EAGLE `target_verify` call and the spec-v2 `draft_extend` call (KV catch-up after verify) pass a
bf16 Q with `q_descale=None`. aiter's gfx950 Gluon `unified_attention` kernel needs Q and KV in one dtype, so these calls fall back to the
Triton split-KV kernel, which at the backend's default page size 1 runs with a one-token KV tile.

On Qwen3.8-27B MXFP4 (GQA 6, head_dim 256, page size 1, FP8 KV), MI355X, TP1, MTP 3/1/4, 8k input / 1k output, 16 concurrent requests,
torch profiler over 30 draft/verify cycles (on the Qwen3.8 build of main described under Speed Tests):

| | before | after |
|---|---|---|
| target_verify attention (16 full-attention layers) | 24.1 ms / cycle (Triton, TILE_SIZE 1) | 2.0 ms / cycle (Gluon) |
| draft_extend attention (1 MTP layer) | 1.55 ms / cycle (Triton, TILE_SIZE 1) | Gluon |
| whole draft/verify cycle | 39.9 ms | 16.0 ms |

With the slow verify, MTP was slower than no speculative decoding on most workloads.

Related: #39998 applies the same FP8-Q idea to the prefill (`_forward_extend_unified`) path.

## Modifications

`target_verify` and `draft_extend` quantize Q with `_quantize_q_fp8` when the KV cache is FP8 and pass its `q_descale` to
`unified_attention`, exactly as `forward_decode` does. Nothing else changes: the `unified_attention_3d_mtp` verify kernel (GQA 8/16, page
size 16) and the asm ragged kernel tried first in `draft_extend` still take the bf16 Q; a bf16 KV cache keeps a bf16 Q.

## Accuracy Tests

Setup for everything below: MI355X, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`, TP1, `--attention-backend aiter --kv-cache-dtype fp8_e4m3`,
MTP 3/1/4 (`--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`),
upstream main 8080507c3e with and without this PR (ROCm 7.2.4, AITER 285579b62).

- Greedy outputs (50 ShareGPT prompts, 256 output tokens, thinking off, batch size 1): with this PR they are identical across two passes
  in one server and across a server restart (50/50 both). On main they vary across a restart (9/50 identical): with the Triton fallback
  greedy MTP output is not reproducible run to run on this setup.
- GSM8K with `sgl-eval` (gsm8k, 200 questions, temperature 0.7, top_p 0.8, thinking off, max_tokens 2048): main 0.955, this PR 0.960
  (0 errors; binomial sd about 1.5 points at n = 200).
- Earlier, on the Qwen3.8 build described below, few-shot GSM8K (5-shot, all 1319 questions, greedy): 0.925 with MTP and this change,
  0.927 with MTP without it, 0.933 without speculative decoding (binomial sd 0.7 points).
- Upstream main + this PR starts with MTP at TP1 and TP2 and serves text and image requests (accept length on the two smoke requests 2.69 at TP1, 2.78 at TP2).
