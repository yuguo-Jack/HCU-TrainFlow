# [ROCm][Spec] Route NGRAM tree reconstruction to the JIT kernel on HIP

[Upstream PR](https://github.com/sgl-project/sglang/pull/43328) · state: closed · merged: True

## Original PR description

## Motivation

NGRAM speculative decoding crashes on ROCm on the first batch, so a server launched with `--speculative-algorithm NGRAM` never becomes healthy:

```
  File "python/sglang/srt/speculative/ngram_worker.py", line 433, in forward_batch_generation
  File "python/sglang/srt/speculative/ngram_worker.py", line 345, in _prepare_for_speculative_decoding
  ...
AttributeError: '_OpNamespace' 'sgl_kernel' object has no attribute 'reconstruct_indices_from_tree_mask'
```

`ngram_worker.py` picks the tree-reconstruction kernel by platform:

```python
if is_xpu():
    from sglang.kernels.ops.speculative.reconstruct_tree import (...)
elif is_cuda():
    from sglang.kernels.ops.speculative.tree import reconstruct_indices_from_tree_mask
else:
    from sgl_kernel.speculative import reconstruct_indices_from_tree_mask
```

`is_cuda()` is `False` on ROCm, so HIP falls through to `sgl_kernel.speculative`. The Python wrapper imports fine, but the ROCm `sgl_kernel` build does not register the op, so the call fails at runtime rather than at import.

The JIT `tree` module used on CUDA already runs on HIP: EAGLE uses it there (`eagle_utils.py` imports it under `_is_cuda or _is_hip`), and #40325 made its entry points accept ROCm tensors.

## Modifications

- `ngram_worker.py`: route HIP to the JIT `tree` module, the same implementation CUDA and EAGLE-on-HIP use. XPU and the remaining platforms are unchanged.
- `test_ngram_utils.py`: import the JIT kernel unconditionally (it is what both CUDA and ROCm now run) and register the test in AMD CI (`jit-kernel-unit`).
- `test_spec_ngram_extra.py`: register the file in AMD CI. Only the triton-backend class runs on ROCm; the two flashinfer classes are skipped on HIP, following `test_spec_standalone_extra.py`.

An earlier attempt (#29346, closed) built `ngram_utils` into the ROCm `sgl-kernel` instead. Reusing the JIT kernel adds no new compiled op and no third implementation.

## Accuracy Tests

MI355X (gfx950, 256 CU), ROCm 7.2.0, torch 2.9.1, Triton 3.7.0. sglang `main` @ `c44a42e6d3`, `sgl-kernel` built from the same commit, AITER `e7d2453f` (the commit pinned in `docker/rocm.Dockerfile`).

Before this PR, the NGRAM server fails on the first batch with the error above (reproduced with Qwen3-8B, default attention backend).

After this PR:

| Test | Result |
|---|---|
| `test/registered/kernels/ops/speculative/test_ngram_utils.py` | 1 passed |
| `test/registered/spec/test_spec_ngram_extra.py` | 1 passed (triton), 3 skipped (flashinfer, CUDA-only) in 127 s |

GSM8K with the CI fixture (`Qwen/Qwen2.5-Coder-7B-Instruct`, triton backend, 200 questions, 5-shot, greedy):

| Server | GSM8K |
|---|---|
| NGRAM, `--speculative-num-draft-tokens 16` | 0.810 |
| Same server args, no speculation | 0.800 |

Average accept length on a GSM8K run with the same NGRAM server args, read from `/server_info`: **1.95** (the fixture threshold is 1.8). On a repeated prompt, once the n-gram corpus holds the first answer, the accept length reaches 15.06 of 16 draft tokens.
