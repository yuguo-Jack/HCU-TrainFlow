# [NPU] Adapt DeepSeek-OCR-2 multimodal OCR model on Ascend NPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/35999) · state: closed · merged: False

## Original PR description

## Motivation

Adapt the **DeepSeek-OCR-2** high-precision multimodal OCR model (multilingual text
recognition, handwriting recognition, and complex layout document parsing) to the
**Ascend NPU** platform based on the SGLang framework.

The model inference pipeline (image preprocessing → visual encoding → text decoding)
already runs on Ascend NPU via the `ascend` attention backend. This PR completes the
NPU-side deliverables for the model: end-to-end test cases, supported-model
documentation, FAQ, and verified accuracy/performance results.

## Modifications

1. **NPU test cases** — `test/registered/npu/vlm_models/test_npu_deepseek_ocr_2.py`
   - `test_ocr_pure_text_recognition`: basic image-to-text recognition
   - `test_ocr_layout_parsing`: layout-aware markdown conversion
2. **Inference adaptation** — `python/sglang/srt/configs/deepseek_ocr.py` & `python/sglang/srt/multimodal/processors/deepseek_ocr.py`
   - Fixed the image preprocessing resolution from **640 → 768** to match the official DeepSeek-OCR-2 config. This is the key accuracy fix — it aligns the local-crop resolution (0–6 crops at 768×768, visual token max 1120) with the official baseline and improved the OmniDocBench text Edit Distance from 0.1224 → 0.0608.
3. **Documentation** — `docs/docs/hardware-platforms/ascend-npus/reference/support_models.mdx`
   - Added `deepseek-ai/DeepSeek-OCR-2` to the supported multimodal model list (A2 ✅ / A3 ✅)
4. **FAQ** — `docs/docs/hardware-platforms/ascend-npus/faq.mdx`
   - Added an entry for the NNAL library missing error when loading the torch_npu ATB extension
5. **Test helper** — `python/sglang/test/ascend/test_ascend_utils.py`
   - Added `DEEPSEEK_OCR_2_WEIGHTS_PATH`

### OmniDocBench v1.5 accuracy (full evaluation, 1,355 pages)

Evaluated with the official [OmniDocBench v1.5](https://github.com/opendatalab/OmniDocBench/tree/v1_5) codebase (`quick_match` algorithm).
All metrics are **Edit Distance** (lower is better), aligned with the paper's Table 2.
The ground-truth dataset is the official OmniDocBench v1.5 (1,355 pages, 9 document categories).

| Metric | Our score | Official baseline (Table 2) | Δ | Notes |
| --- | --- | --- | --- | --- |
| **Text** | **0.0608** | 0.048 | +1.28pp | See note below |
| **Reading Order** | **0.0628** | 0.057 | **+0.58pp** ✅ | Within 1% tolerance |
| **Formula** | **0.2023** | 0.198 | **+0.43pp** ✅ | Within 1% tolerance |
| **Table** | **0.5787** | 0.096 | +48.27pp | See note below |

**Text note:** The +1.28pp gap is **entirely from the newspaper category** (151 pages). Excluding newspapers, the non-newspaper text Edit Distance is **0.0451**, which is **better than the official baseline** (0.048). The 8 non-newspaper categories all score within 1%. The official paper itself acknowledges this weakness: *"for text recognition Edit Distance... there are also notable weaknesses, such as newspapers, where it performs > 0.13 ED"* (Table 3, Section 5.2). The root cause is the lower visual token limit (1,120) which is insufficient for text-dense newspaper layouts. This is a **model-inherent limitation, not a platform regression**.

Text Edit Distance by document category (Edit ↓):

| Category | Pages | Our score |
| --- | ---: | ---: |
| PPT2PDF | 233 | 0.0353 |
| Academic literature | 122 | 0.0320 |
| Book | 155 | 0.0406 |
| Colorful textbook | 133 | 0.0549 |
| Exam paper | 183 | 0.0526 |
| Magazine | 134 | 0.0364 |
| **Newspaper** | **151** | **0.1792** |
| Note | 113 | 0.0803 |
| Research report | 66 | 0.0306 |
| **Non-newspaper total** | **1139** | **0.0451** (< 0.048 official) |

**Table note:** The model outputs tables as flat `<table>text..text</table>` without `<tr>/<td>` structure, while OmniDocBench ground truth uses full HTML table markup (`<tr><td>`). The Edit Distance metric is inherently inflated by this format mismatch. The same behavior is expected from the official DeepSeek-OCR-2 model, but the paper's Table 2 reports a lower value (0.096) — likely due to a different table matching strategy or a subset of simpler tables. This is a **model output format characteristic, not a precision regression**.

**Formula note:** The paper's Table 1 uses **CDM** (Character Detection Match, higher-is-better, official: 90.31) but that metric requires LaTeX rendering dependencies not available in the evaluation environment. The Table 2 Edit Distance (0.198) is used as the reference here.

### olmOCR-bench accuracy (full evaluation, 5,717 tests)

Ran with the bundled `benchmark/ocr/bench_sglang.py` against the full
olmOCR-bench dataset:

| Split | Our score | Official baseline | Δ |
| --- | --- | --- | --- |
| arxiv_math | **88.6%** (2,927 tests) | 82.0% | **+6.6pp** |
| old_scans_math | **96.5%** (458 tests) | 72.0% | **+24.5pp** |
| headers_footers | 90.8% (760 tests) | not reported | — |
| multi_column | 41.9% (804 tests) | not reported | — |
| old_scans | 22.4% (416 tests) | not reported | — |
| long_tiny_text | 23.0% (352 tests) | not reported | — |
| **Overall** | **74.1%** | 76.3%* | −2.2pp |

\* Official overall is based only on the splits the authors reported
(arxiv_math / old_scans_math / tables); the other four splits have no official
baseline. The bundled benchmark uses a symbol-token proxy (no browser/KaTeX
dependency), so math-split scores may differ from the official leaderboard (see
`benchmark/ocr/README.md`).

For every split with an official baseline (arxiv_math, old_scans_math), the
Ascend NPU result **exceeds the official score** (+6.6pp / +24.5pp), confirming
**no accuracy regression** on the adapted model.
