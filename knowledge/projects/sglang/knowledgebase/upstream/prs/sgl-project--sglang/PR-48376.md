# [Feat] qsa: host offload of the QSA K/V with a per-request GPU hot cache (1/N)

[Upstream PR](https://github.com/sgl-project/sglang/pull/48376) · state: open · merged: False

## Original PR description

## Motivation

Qwen4-Exp (Qwen3.8-Flash-Next, `qwen4_exp`) decodes with QSA sparse attention: each query row attends to at most 512 compressed blocks (2,048 tokens) per QSA layer. The full-attention K/V of every token still stays on the GPU. On `nvidia/Qwen3.8-Flash-Next-NVFP4` that is 24,576 B/token in BF16 (12 QSA layers × 2 KV heads × 256 × K+V), against 768 B/token for the GPU-resident compressed index.

On one 96 GB RTX PRO 6000, `main` at `--mem-fraction-static 0.93` has a KV pool of 306,624-307,456 tokens. At 61K-token prompts that is 4 concurrent sessions: a long-context, many-session deployment is KV-bound long before it is compute-bound.

This PR keeps the full K/V of the QSA layers in pinned host memory and keeps per request only a bounded GPU cache of the blocks the indexer selects. Upstream's HiSparse solves the same problem for DSA, DeepSeek V4 and MiniMax M3, but it requires `--disable-radix-cache`: host rows and device slots belong to one request. Here host rows are indexed by the logical KV slot (the allocator index in `req_to_token`), so a radix prefix shared by many requests shares its host rows, and the radix cache, chunked prefill and the indexer are unchanged.

**Series.** This PR stands alone: it is a complete, exact feature behind an off-by-default flag. PR 2/N, the fused CUDA-graph-safe resolve (Triton), builds on it, becomes the default on CUDA and must merge after it. Possible follow-ups, not part of this series yet: offloading the MTP draft layers' K/V, and a prefill that gathers only the context rows the top-k reads.

## Modifications

- **`mem_cache/qsa_kv_offload.py` (new).**
  - `QSAKVOffloadLayout` and `compute_offload_layout`: request regions of `(hot_blocks + 2) * compress_ratio` device rows (a 2-block tail ring for the newest tokens, then the hot blocks), plus an extend scratch.
  - `QSAKVOffloadBudget`: the cost model for KV sizing, covering the offloaded K/V bytes per token, the device rows and hot-cache tables per request slot, and the host cap.
  - `QSAKVHostOffload` holds:
    - the host K/V, `[layers, size + page, kv_heads, head_dim]` per TP rank, allocated at its exact size with `alloc_with_host_register` (mmap + `cudaHostRegister`);
    - write-through of new rows;
    - the prefill context gather;
    - the eager reference resolve: tail ring, per-request LRU of whole blocks, misses copied host→device with `transfer_hicache_one_layer`, and a block reused only while `req_to_token` still maps its positions to the slots it was filled from (radix dedup, rejected speculative tokens).
- **`mem_cache/qsa_kv_pool.py`.** With a layout, `QSATokenToKVPool` builds its full-attention `MHATokenToKVPool` with `size = device_rows` and owns the offload. Everything else keeps logical slots.
- **`layers/attention/qsa/kv_offload_attention.py` (new) and `layers/attention/qwen_sparse_attn_backend.py`.**
  - `QSAKVGatherSource` (a slot table, row→request map and row lengths) is an optional argument of `_forward_trtllm_sparse` and of the new `_forward_varlen_sparse` (the FA2/FA4/ROCm tail, split out unchanged). Only the offload path passes one; otherwise the gathers read `req_to_token` exactly as before.
  - The offload paths live in the new module, and the backend dispatches to them at three call sites:
    - `store_offloaded_kv`: stores go to the ring or scratch rows and are written through to the host;
    - `forward_offloaded_attention`: decode and target verify resolve the selected positions to device rows, then run the **same** compact gather + FlashInfer trtllm (SM100/SM120) or varlen decode;
    - `gather_offloaded_context`: a prefill with a cached prefix gathers its context from the host into the layout `pack_qsa_prefill_kv` builds.
  - The offload path never uses the fused store + attention fast path (`_supports_fused_kv_pool` is False under offload).
- **`mem_cache/kv_cache_configurator.py`.** Builds the layout for the target worker's request slots, and refuses a request pool with more slots than the `--max-running-requests + 1` the sizing budgeted.
- **`model_executor/pool_configurator.py`.**
  - `calculate_pool_sizes` budgets the hot cache of `--max-running-requests + 1` request slots.
  - `finalize_with_max_running_requests` returns the hot rows of slots the request pool does not get (e.g. the GDN-state cap) to the logical pool, up to the host cap.
  - The MTP draft pool stays on the GPU and in the cell.
- **`arg_groups`.**
  - New flags in `fields/memory.py`, with docs rows: `--enable-qsa-kv-offload`, `--qsa-kv-offload-host-size` (GB per TP rank) and `--qsa-kv-offload-hot-blocks` (default 1024, about 0.1 GB per request slot on this model).
  - `qsa_kv_offload_hook.py` validates before the weights load, with the same layout checks the pool runs plus chunked prefill on. It refuses everything that reads the full-attention K/V by logical slot outside the backend: HiCache, HiSparse, LMCache, PD, CP/DCP, DP attention, PP, mixed chunk, n-gram or tree speculation. It also refuses CUDA graphs, because this resolve is eager; PR 2/N lifts that.
- **`managers/scheduler.py`.** Unpins the host store on shutdown, like the HiCache host pools.
- **Debug: `SGLANG_DEBUG_QSA_KV_OFFLOAD_VERIFY`** (`environ.py`, documented). It keeps the full GPU pool next to the offload and checks every offloaded read against it bit for bit. It lives in production code because this is the only way to check the offload on real serving traffic: radix dedup and request-slot reuse do not occur in a kernel test.

## Accuracy Tests

The offload changes where K/V bytes live, not what attention reads.

- **Unit tests.**
  - `test/registered/unit/mem_cache/test_qsa_kv_offload_unit.py` (CPU):
    - layout and sizing (including slots the request pool does not get, and table bytes);
    - every refusal of the argument hook;
    - a simulated backend driving the resolve over 60 forwards with the hot cache far smaller than the contexts, covering decode and chain verify (2-4 rows, rejections), radix remaps and request-slot reuse. After every forward, each selected position's device row must hold exactly the logical slot's K/V.
  - `test/registered/kernels/ops/attention/qsa/test_qsa_kv_offload.py` (CUDA): the packed decode scratch and valid counts from the offload's row table are **bit-identical** to the same gather through `req_to_token` on the full pool. It covers BF16, FP8→BF16 and FP8→FP8 packing × decode and 4-row verify, with the pinned host store and JIT row copies at the model's shape.
  - `test/registered/kernels/ops/attention/qsa/test_qsa_kv_offload_backend.py` (CUDA): `QwenSparseAttnBackend` on two QSA pools, offload off and on, runs the same forwards: three prefill chunks per request (the later chunks gather their cached context from the host), then decode steps whose selections evict and reload hot-cache blocks and cross the tail ring. The attention outputs are **bit-identical**.
- **End to end: in-server verify.** `SGLANG_DEBUG_QSA_KV_OFFLOAD_VERIFY=1` packs the selected K/V both ways for every QSA layer of every decode forward and compares counts, K and V as bytes. It also compares every host-gathered prefill context with `pack_qsa_prefill_kv` on the full pool.
  - Load: 24 greedy requests with 8.7K-29K-token prompts, multi-turn radix hits of up to 29K cached tokens, a shared 20K prefix, sequential and concurrent; H = 512 blocks (2,048 tokens per request and layer).
  - Result: **≥ 20,000 checks, 0 mismatches**.
  - Setup: RTX PRO 6000 Blackwell (300 W), `nvidia/Qwen3.8-Flash-Next-NVFP4`, `--quantization modelopt_fp4`. The same gate also passed on an RTX PRO 6000 Blackwell Server Edition (600 W): 24/24 served, 20,000 checks, 0 mismatches.
- **MTP (NEXTN) with offload**, same verify gate: `--speculative-algorithm NEXTN --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`, `--qsa-kv-offload-hot-blocks 2048` (4 verify rows × 512 blocks), the same 24 requests. **24/24 served, ≥ 10,000 checks, 0 mismatches**, accept length 3.25-4.00 over 19 logged values, mean 3.75. Hardware: RTX PRO 6000 Blackwell Server Edition (600 W). The MTP draft layers' K/V stays on the GPU in this PR.
- **Token identity vs `main` on GB200**, where deterministic inference runs for this model: one GB200, TP1, `--enable-deterministic-inference --attention-backend flashinfer --disable-cuda-graph`, offload on (40 GB host, H = 512) with in-server verify. The same 24 requests give **24/24 outputs token-identical** to `main` with the same arguments (offload off) and to `main` with CUDA graphs; verify ran 20,000 checks with 0 mismatches.
- **Token identity vs `main`** cannot be gated on SM120 for this model. `main` is not run-to-run deterministic there: two identical `main` runs of the same 24 requests, sent one at a time, differ in 18/24 outputs. `--enable-deterministic-inference` fails for QSA on SM120, because batch-invariant top-k needs FilteredTopK with 128 KiB of shared memory.
- **gsm8k** (`sgl-eval run gsm8k --num-examples 200 --temperature 0 --max-tokens 4096`), eager on both arms (`--disable-cuda-graph`, `--context-length 20480`), one allocation, RTX PRO 6000 Blackwell Server Edition (600 W): offload off **95.5%**, offload on (this PR) **97.5%**. On an RTX PRO 6000 Blackwell (300 W) at the gate config, an independent run measured `main` 97.5% vs this PR 97.0%. Both differences are within run-to-run noise: two identical offload-off runs produce different text for 194 of 200 questions (PR 2/N).

## Speed Tests and Profiling

This PR's claim is **capacity**. Its resolve is the eager reference (`--disable-cuda-graph`), so decode throughput is below `main` with CUDA graphs; PR 2/N adds the CUDA-graph-safe resolve.

Setup: `main` and this PR on the same GPU and image.
- Common args: `--tp 1 --quantization modelopt_fp4 --mem-fraction-static 0.93 --max-running-requests 32 --chunked-prefill-size 4096`.
- `main` runs as deployed: decode CUDA graphs on, `--disable-prefill-cuda-graph`.
- This PR adds `--disable-cuda-graph --enable-qsa-kv-offload --qsa-kv-offload-host-size 60 --qsa-kv-offload-hot-blocks 1024`.
- Load: `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random-ids --random-range-ratio 1.0 --seed 1`.

RTX PRO 6000 Blackwell (300 W), one run per arm, at commit `9bb04dc871`. KV tokens and max running come from startup sizing. Both offload rows are host-bound and at the GDN-state cap, which the later sizing change leaves as they are: in this configuration the final sizing code gives the same 2,441,280 tokens and 11 running requests (RTX PRO 6000 Blackwell Server Edition, 600 W, measured with PR 2/N on top).

| Load | Arm | KV tokens | Max running | Output tok/s | Median TTFT | Median TPOT |
|---|---|---|---|---|---|---|
| 61,440 in / 256 out, 24 prompts, c24 | `main` (CUDA graphs) | 306,624 | **4** (KV-bound) | 42.8 | 70.1 s | 23.7 ms |
| same | this PR (eager) | 2,441,280 | **11** (GDN-state cap) | 32.6 | 93.3 s | 86.7 ms |
| 16,384 in / 256 out, 48 prompts, c32 | `main` (CUDA graphs) | 307,456 | 11 (GDN-state cap) | 127.2 | 44.2 s | 39.2 ms |
| same | this PR (eager) | 2,441,280 | 11 | 69.7 | 68.2 s | 105.0 ms |

Giving the freed GPU memory to GDN state: this PR with `--qsa-kv-offload-hot-blocks 512 --max-mamba-cache-size 100`. RTX PRO 6000 Blackwell Server Edition (600 W), final sizing, 61,440 in / 256 out, 24 prompts, c24, 3 runs per arm, median [min-max]:

| Arm | KV tokens | Max running | Output tok/s |
|---|---|---|---|
| `main` (CUDA graphs) | 308,416 | **4** (KV-bound) | 50.2 [48.3-50.4] |
| this PR (eager), H = 512, `--max-mamba-cache-size 100` | 2,071,936 | **20** (cap 20) | 37.2 [36.0-38.3] |

- **Capacity:**
  - 7.9× the logical KV tokens on the same GPU (307K → 2.44M with 60 GB of host).
  - 2.75× the concurrent 61K-token sessions at the default GDN-state budget (4 → 11), and 5× (4 → 20) with `--max-mamba-cache-size 100`.
  - With offload the GDN (Mamba) state is the limit, at 5 slots per request.
- **Costs in this PR:**
  - Throughput is below `main` with CUDA graphs. On the 300 W GPU the eager resolve adds 63 ms per decode step at 60K (TPOT 86.7 vs 23.7 ms).
  - TTFT rises because every prefill chunk after the first gathers the whole context from the host. A follow-up could gather only the rows the top-k reads.
- Capacity numbers come from startup sizing and are deterministic. Throughput numbers are reported rather than claimed.
