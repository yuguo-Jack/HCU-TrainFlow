## Original PR description

# [AMD] Fix AITER DSA prefill with an FP8 KV cache

 ## Motivation
  SGLang gathers the KV entries selected by DeepSeek Sparse Attention into a compact buffer before calling AITER. `kv_indptr` describes each query’s range within that buffer, so AITER must use this compact layout rather than
  apply another fixed top-k interpretation.
  The current integration has two independent problems.
  First, it violates AITER’s FP8 contract. It leaves `q_scale` unset, passes `1.0` instead of the layer’s actual KV-cache scale, and allocates FP8 output even though AITER’s reduction kernel writes BF16. With an FP8 KV cache,
  the stock path aborts on its first forward because the required query scale is missing.
  Second, SGLang builds AITER metadata as if the compact buffer still used a fixed sparse top-k layout. It also forces 64 work splits instead of allowing AITER to derive the split policy from `kv_indptr` and the workload. After
  correcting the FP8 dtype and scale contract, this legacy metadata path causes output-quality collapse rather than mild numerical drift. In our 60,000-token test, both 64-token generations diverged from TileLang at the first
  generated character and produced repetitive malformed text. We have reproduced this failure at 60,000 input tokens but have not established the minimum failing context length.
  This change affects only DSA calls using AITER with an FP8 KV cache. Other DSA backends and non-FP8 KV-cache paths are unchanged. It assumes that affected calls:
  - have already gathered the selected KV entries into a compact buffer;
  - describe that layout with `kv_indptr`;
  - provide a scalar `layer.k_scale`;
  - require BF16 output when the query is FP8; and
  - support AITER v1.2 fast metadata for their head count and shape.
  These assumptions are correct for the tested GLM path, but not yet demonstrated for every DSA model.


## Modifications

- Select AITER's v1.2 metadata builder with `fast_mode=True`.
- Disable the legacy v1.0 path with `intra_batch_mode=False`.
- Pass `topk=-1` because the KV entries are already compact. This makes AITER
  use the ranges in `kv_indptr`; it does not disable DSA top-k selection.
- Remove the fixed `max_split_per_batch=64` value so AITER derives the split
  count from the workload.
- Allocate BF16 output when the query input is FP8.
- Pass query scale `1.0` and the layer's KV-cache scale to AITER.
- Add AITER to the existing DSA FP8-prefill test matrix.

Cross-layer metadata reuse is intentionally excluded and will be submitted
separately.

## Accuracy Tests

Hardware: AMD MI355X, TP4, FP8 KV cache.

The existing DSA attention test suite passed the AITER BF16 and FP8 sparse
prefill cases:

```bash
python3 test/registered/attention/unittests/dsa/test_dsa.py
```

For a long-context output test, the same two fixed-seed random prompts were run
once with AITER prefill and once with TileLang prefill. Each prompt used 60,000
input tokens and 64 output tokens, with `temperature=0` and `top_p=1`. The
generated texts matched for both prompts.

## Speed Tests and Profiling

This is a correctness fix. The metadata builder changes from a fixed split
policy to AITER's workload-adaptive policy, but this PR does not claim a
standalone serving-speed improvement.

- pbkowalski · comment · 2026-10-02T08:32:53Z · [source](https://github.com/sgl-project/sglang/pull/39083#discussion_r4164089967)

File: `python/sglang/srt/layers/attention/dsa_backend.py` · line 717

Setting `intra_batch_mode=False` is necessary for metadata sizing; with intra-batch sizing, AITER reserves: `tile_count × num_kv_splits`

Using 32,768 logical batches and 64 splits produced 2,097,152 partial entries and approximately 64 GiB of FP32 partial-output. Non-intra sizing allocates against the actual capacity instead.

`fast_mode=True `already chooses V1.2 at runtime, but `intra_batch_mode` still controls the Python-side buffer dimensions, so leaving it True would retain the oversized allocation.

Regarding removing `num_kv_splits` from ` get_mla_metadata_info_v1` has no impact as that argument is effectively ignored with `intra_batch_mode=False`. But removing `max_split_per_batch` could affect V1.2 scheduling at small batch decode, so I will restore that.
