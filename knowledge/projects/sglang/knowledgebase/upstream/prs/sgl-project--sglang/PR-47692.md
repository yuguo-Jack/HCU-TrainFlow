## Motivation

<!-- Describe the purpose and goals of this pull request. -->
With `--ep` and no a2a backend, every rank gets every token, and routes to another rank's experts just have id -1. The Triton path still does work for those routes:

  - alignment keeps them in a -1 bucket, which sorts first
  - both GEMMs launch CTAs that only write zeros for them
  - quant runs over all rows
  - the combine reads all top-k slots, including the zeros

With 8 ranks, about 7 of every 8 routes are non-local on average. They contribute nothing on this rank, but at M=8192 they still take up about 27–33% of the MoE call.

 The `humming` runner already does this: it aligns with `ignore_invalid_expert=True` and combines with `moe_fused_mul_sum`, which skips negative ids (`humming.py:588`), taking the same approach on the Triton path.

Goes with the MiniMax-M2 / M2.5 `--tp 8 --ep 8` recipes on NVIDIA, which resolve to the Triton runner with `moe_a2a_backend=none`.

## Modifications

<!-- Detail the changes made in this pull request. -->
  - `_skip_nonlocal_routes` decides whether the skip applies: CUDA, `filter_expert`, top-k > 1, int32 contiguous `topk_ids`, and neither `no_combine` nor `defer_sum`.
  - When it's on, alignment uses `ignore_invalid_expert=True`, so
  -1 routes never reach the GEMMs.
  - FP8 quant before the down GEMM now covers routed rows only. It's the same sorted-row kernel, with `topk_ids.view(-1)` and `num_valid_tokens=E`, so -1 rows get filtered by the existing uint32 check.
  - `moe_sum_reduce_triton` takes an optional `topk_ids` and skips slots with a negative id. This is required, not just faster: `cache3` is allocated with `torch.empty`, so the skipped slots are never written.
  - The skipping path uses 4 warps instead of 16, based on a sweep on H200.

`no_combine` and `defer_sum` turn the skip off because both hand `cache3` to something else that doesn't know which slots are unwritten. Beam, the only `defer_sum` caller, already passes `filter_expert=False`, so this only guards future callers.

## Speed Tests and Profiling

<!-- If this pull request impacts inference speed, provide benchmarking and profiling results. -->
Tested on a H200. Synthetic tensors at `config.json` shapes, uniform routing, rank 0 (about 12.5% of routes local), CUDA graph replay, cold L2.

  | M | MiniMax before | MiniMax after | Change | DSv3 before | DSv3 after | Change |
  |---|---|---|---|---|---|---|
  | 512 | 181.0 µs | 162.0 µs | -10.5% | 438.1 µs | 401.6 µs | -8.3% |
  | 2048 | 321.7 µs | 234.4 µs | -27.1% | 720.2 µs | 577.0 µs | -19.9% |
  | 8192 | 895.6 µs | 599.9 µs | -33.0% | 1930.5 µs | 1401.2 µs | -27.4% |
  | 16384 | 1684.3 µs | 1090.5 µs | -35.3% | 3586.0 µs | 2603.4 µs | -27.4% |

At M ≤ 64 there's no meaningful change.

Per-kernel breakdown from ncu, MiniMax M=8192, measured before rebasing onto current main:

  | Kernel | Before | After |
  |---|---|---|
  | `count_and_sort_expert_tokens_kernel` | 47.8 µs | 6.5 µs |
  | up `fused_moe_kernel` | 333.5 µs | 265.2 µs |
  | down-input quant | 70.2 µs | 23.8 µs |
  | down `fused_moe_kernel` | 243.1 µs | 174.2 µs |
  | combine | 104.3 µs | 29.2 µs |

Caveats:

- All timings use uniform routing. With skewed routing, I only checked correctness.
- Real router traces and e2e serving wasn't measured.
- found no NVIDIA DeepSeek recipe that reaches this path, so the DSv3 numbers are just kernel-level. MiniMax is actually taken from cookbook.
