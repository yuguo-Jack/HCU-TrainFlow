# [Feat] simulator: support AISimulate FPM estimation modes

[Upstream PR](https://github.com/sgl-project/sglang/pull/46012) · state: open · merged: False

## Original PR description

## Motivation

Op-level modeling provides an analytical foundation for inference simulation. As model implementations and serving kernels evolve, measured forward-pass observations can help calibrate errors that are difficult to capture quickly through operator modeling alone.

This is the **second of two stacked PRs**, built on [#44253](https://github.com/sgl-project/sglang/pull/44253):

1. **#44253:** migrate the existing op-level estimator to the AISimulate SDK.
2. **This PR:** use the same pinned SDK to enable its native FPM estimation modes through the same predictor and configuration interface.

The intended merge order is #44253 first, followed by this PR. Fitting, correction, regression, and interpolation are provided by AISimulate; SGLang supplies the deployment and actual scheduled-batch inputs.

## Modifications

- Extend the existing `aisimulate` predictor with native op-level, correction, regression, interpolation, and automatic selection modes.
- Retain the existing static op-level calculation path when `estimation_mode` is omitted.
- Pass `estimator_config` and native observation data directly to the SDK.
- Capture actual prefill/decode membership and prior KV before the forward call, including mixed batches and single-token prefill after a prefix hit.
- Share deployment/quantization mapping with the existing predictor. The modern SDK namespace and dependency pin are already established by #44253.
- Add configuration examples, documentation, SDK parity tests, and CPU runner tests.

## Usage

Use the same installation extra and launch interface as #44253:

```bash
pip install -e "tools/sglang-simulator[aisimulate]"

SGLANG_USE_CPU_ENGINE=1 \
SGLANG_SIMULATOR_OUTPUT_MODE=OFFLINE \
python3 -m sglang_simulator.simulation.sglang.launch_server \
  --model-path /path/to/model \
  --sim-config-path /path/to/simulator.json
```

Choose the mode in the JSON configuration's `predictor` section:

| Mode | Configuration |
| --- | --- |
| Existing op-level path | Omit `estimation_mode` |
| Native op-level | `estimation_mode: "op_level"`, correction disabled |
| Op-level + FPM correction | `estimation_mode: "op_level"`, correction enabled, `tune_observations` |
| FPM regression | `estimation_mode: "fpm_regression"`, `tune_observations` |
| Whole-forward interpolation | `estimation_mode: "fpm_interpolation"`, matching `systems_paths` |
| SDK automatic selection | `estimation_mode: "auto"` |

For example, replace the `predictor` section with the following to enable op-level correction:

```json
{
  "predictor": {
    "name": "aisimulate",
    "estimation_mode": "op_level",
    "estimator_config": {
      "correction": {
        "enabled": true
      }
    },
    "tune_observations": "calibration/iterations.json"
  }
}
```

Observations are prepared beforehand and replayed at startup using the SDK's native format. Paths are relative to the configuration file. Hardware and topology remain in `platform` and `scheduler`; the mode is selected for each simulator run.

See `tools/sglang-simulator/docs/aisimulate_fpm.md` and `examples/sim_configs/aisimulate_native.json` for the complete configuration and observation format. `auto` selects by SDK availability, not measured accuracy.

## Reference accuracy measurements

A reference experiment using an AISimulate 0.13 development build used **H20 / Qwen3-8B / BF16 / TP1**, with 92 calibration coordinates, 48 separate evaluation coordinates, and medians of 10 timing repeats. The metric is mean absolute percentage error (MAPE) against measured GPU-forward latency.

| Mode | Prefill MAPE | Decode MAPE |
| --- | ---: | ---: |
| Op-level | 21.91% | 42.45% |
| Original phase scaling | 14.16% | 3.66% |
| Op-level + FPM correction | 9.49% | 3.66% |
| FPM regression | 4.94% | 2.70% |

These results illustrate the potential benefit of measured-data calibration. They predate this rebase and were not rerun for this adapter refactor. On a separate longer-KV stress set, regression had higher decode error than phase scaling (4.84% vs. 3.98%), so improvement is workload-dependent.

The measurements concern prediction accuracy, not hardware speedup or end-to-end serving accuracy. No interpolation accuracy result is claimed by this table.

## Validation

Re-run with the official AISimulate 0.13.0 SDK:

- 25 import, predictor, native-estimator, and CPU runner tests passed, including mixed batches and warm-prefix behavior. The interpolation interface test ran with a local matching profile.
- 20 default-path comparisons between PR1 and PR2 matched exactly, covering SOL/SILICON, prefill/decode, prefix KV, and phase scaling. Each checkout was imported in a separate process without rewriting imports.

These tests cover SDK integration and simulator behavior. The reference accuracy measurements come from the separate experiment described above.

## Current scope

- The dependency targets the official AISimulate 0.13.0 release; Linux / Python 3.12 is the integration validation environment.
- Native modes currently support PP=attention-DP=CP=1, with TP/EP modeled.
- Calibration data must match the model, hardware, quantization, topology, and timing boundary. Provenance and evaluation-split checks remain part of offline data preparation.
- Fitted state is recreated from observations at startup. Unsupported inputs and unavailable estimates fail explicitly.
