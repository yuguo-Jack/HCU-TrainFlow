# [CP] Automatically enable BCG for supported prefill CP configurations

[Upstream PR](https://github.com/sgl-project/sglang/pull/44022) · state: closed · merged: True

## Original PR description

## Motivation

Supported prefill context-parallel configurations should select breakable CUDA graphs automatically. DSV4 is temporarily excluded because its CP BCG capture path does not shard token IDs consistently with hidden states for hash routing.

## Modifications

- Centralize supported `(ContextParallelStrategyKind, CPAttentionBackendKind)` pairs in `layers/cp/bcg.py`: zigzag + TRT-LLM MHA. Keep the DSV4 backend enum, but exclude interleave + DSV4 until the capture input-ID mismatch is fixed.
- Keep automatic prefill BCG selection and compatibility checks in `cuda_graph_hook.py::apply_prefill_cp_cuda_graph_default`. The resolution pipeline invokes this hook immediately after context-parallel configuration resolves, only when `enable_prefill_cp` is enabled, retaining the existing CP=TP and PP=1 requirements and explicit user backend choices. `parallel_hook.py` is unchanged by this PR.
- DSV4 remains disabled by default while it is absent from the supported set. Preserve other compatibility restrictions, PD role rules, and DeepEP bucket alignment.
- Remove the explicit BCG flags from the GPT-OSS CP test and delete `test_dsv4_prefill_cp_bcg.py` as requested.

- Defer the CP-related BCG warning until `apply_prefill_cp_cuda_graph_default` finishes; warn only if the resulting prefill backend is not breakable. Early CP auto-disable remains silent so supported configurations do not log a misleading disable/enable sequence.

- AMD-yanfeiwang · comment · 2026-10-14T13:00:57Z · [source](https://github.com/sgl-project/sglang/pull/44022#issuecomment-6168938857)

@Fridge003 
Thanks for this PR and for pinning down the DSV4 input-ID issue so clearly. We ran into the same mismatch while porting #38603 to ROCm, and fixed it in the shared CP BCG path in #43819 (building on #40333). Sharing it here in case it helps.

**Cause:** unlike eager CP (`cp_shard_model_inputs`), the BCG capture path passed the global token-order `input_ids` to the body and never set `input_ids_global`, so DSV4's hash-routed MoE layers got ids that didn't match the CP-sharded hidden rows.

**Fix:** `PrefillCPBCGInput` now gives the captured body the same inputs as eager CP, from fixed-address buffers: CP-local `input_ids` and positions, and `input_ids_global` in eager CP's layout (rank-major for TP MoE, local for a2a). Nothing here is platform-specific.

**ROCm results (DeepSeek-V4-Flash TP4, MI355X):** without the fix, CP+BCG fails during graph capture with exactly this mismatch (`hash_topk.py: input_ids.shape=[28], hidden_states.shape=[32, 4096]`). With the fix it serves normally: GSM8K 0.9682 vs 0.9712 for eager CP (±0.005).

It would be great if CUDA and ROCm could share the same fix rather than diverge. Would you be open to this approach for CUDA as well? If so, #43819 can re-enable `(INTERLEAVE, DSV4)` for both platforms (it's currently ROCm-only), or we can split the shared fix into a small separate PR, whichever is easier for you to review. Happy to adjust either way.
