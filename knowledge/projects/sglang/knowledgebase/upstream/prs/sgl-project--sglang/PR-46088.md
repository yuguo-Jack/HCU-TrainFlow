# [Perf] dsv41: Fuse decode mHC post, combine and RMSNorm into one kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/46088) · state: closed · merged: True

## Original PR description

## Motivation

In DeepSeek-V4.1 decode and target-verify, each layer boundary runs these small kernels back to back on the critical path:
- the mHC post (`mhc_post_split_h`);
- the next sub-layer's four-stream combine and RMSNorm (`hc_combine_norm` / `hc_combine_norm_mxfp8`);
- above 128 rows, a separate MXFP8 quantize of the normed row.

Each is a few microseconds, and at decode batch sizes most of that is launch and dependency latency, not bandwidth.

## Modifications

- New JIT kernel `mhc_post_combine_norm_decode`. One CTA per row computes, in one launch:
  - the mHC post (updated residual streams);
  - the next combine weighted by `pre`;
  - RMSNorm;
  - optionally the MXFP8 output in the swizzled layout the next GEMM takes.
- `_post_fusion` in `deepseek_v4_mhc.py` uses it on Blackwell for up to 1024 rows. The threads per row are the count that needs the fewest waves, using the occupancy CUDA reports for the kernel. The DSv4.1 shape is required (mult 4, hidden 5120, bf16, fp32 coefficients). It is skipped in batch-invariant mode.
- Mega-mHC (`SGLANG_OPT_DSV41_MEGA_MHC_PREFILL`, opt-in) now serves only this rank's own extend batches (target verify excluded), read from the local forward mode. On decode/verify it computed the next sub-layer's mix statistics on the critical path instead of on the side stream beside attention/MoE, and it was slower than the unfused path at every batch size measured.
- The post output is bitwise identical to `mhc_post_split_h`. The RMS statistic is summed in a different order than the Triton kernel, so the normed row can differ in the last bf16 bit.
- Registered in the layernorm kernel inventory.
- `test_mhc_post_combine_norm_decode.py` checks every thread-count transition and the 1024-row cap against the unfused kernels, with and without MXFP8, plus the gate.

## Accuracy and speed

Validated with DeepSeek-V4.1-Flash, DEP4 decode at 128K context, ABBA arms in one job per node:
- CC 10.7: steady-state decode throughput is at or above the unfused path at every batch size from 16 to 224. GSM8K is unchanged.
- CC 10.3: at or above the unfused path at batch sizes 16 to 64.
- B200 (SM100), kernel only, CUDA graph of 32 launches over rotating inputs: up to 128 rows the fused kernel takes 3.9–4.5 µs, against 3.9–5.5 µs for the unfused kernels without MXFP8 and 5.2–9.5 µs with it. It is at or below the unfused path at every size up to 1024 rows.
- A profiler probe on each arm confirms the fused kernel replaces `mhc_post_split_h` + `hc_combine_norm(_mxfp8)` on decode, and that Mega-mHC still serves extend batches when enabled.

Reviewed head a7e7b2491a.

My main dispatch concern is whether the full _can_use_decode_post_combine predicate needs to run at every layer boundary in eager execution. The platform and HcConfig checks are fixed for the model's lifetime and could be resolved when building the boundary/dispatch plan. Please keep the row-count gate dynamic, and retain per-call dtype/contiguity fallback checks only where those properties can actually vary; otherwise, document the producer contract and rely on the kernel entry-point validation. These are host metadata checks and do not synchronize the GPU, but repeated Python dispatch still has a cost on the eager path. CUDA graph replay does not rerun this predicate, so I would measure eager CPU overhead before claiming a performance regression. Also, the current gate uses 1–1024 rows as a decode proxy; it does not explicitly check decode/target-verify mode, so small prefill batches can qualify.

Two review findings:

- [P2] Preserve batch-invariant mode. _pick_threads selects 640/320/160 threads from the batch row count, changing the RMS reduction tree, but _can_use_decode_post_combine has no batch-invariance guard. A CPU emulation of the reduction found different FP32 sums and, using a CPU reciprocal-square-root proxy, a BF16 output difference for the same row across thread choices. This is not a CUDA reproduction of rsqrt.approx.ftz, but it demonstrates that the reduction order is not invariant. Please exclude this path in batch-invariant mode until parity is established across thread-selection thresholds and the fallback above MAX_ROWS; fixing the thread count alone would not establish parity with that fallback. Restore a regression test covering these transitions—the latest head drops the kernel test.
- [P3] Register the new public operator in the kernel inventory. Add a lazy KernelSpec in python/sglang/kernels/ops/layernorm/__init__.py with the JIT backend and appropriate capability metadata. register_custom_op registers the Torch operator, but does not populate the SGLang kernel inventory.

Validation: source review and CPU reduction emulation only; no CUDA correctness or performance tests run locally.

- **Row cap.** The gain at 80 requests per rank exists only because we raised `MAX_ROWS` from 384 to 1024. With 384, the fused path is skipped above 64 running requests per rank. At our target load, the busiest decode rank holds 55-82 running requests (330-492 rows). Could the cap cover the largest decode CUDA-graph bucket?
- **Correctness above 384 rows.** The PR's tests stop at 384 rows. We checked batch invariance at 144, 240, 480 and 960 rows: each row's output is bitwise equal to the same row computed alone, which is inside the tested range.
- **Kernel time.** In nsys at 240 rows, the kernel takes about 30-65% longer than we estimated from its memory traffic, so the threads per row may be worth tuning.
- **Side stream.** With the fused kernel on the main stream, the summed time of the side-stream `_hc_mix_reduce_sinkhorn_kernel` grew about 3.9x per step, from contention. It stays mostly hidden, but it is sensitive to SM sharing.


- zcnrex · comment · 2026-10-27T04:39:33Z · [source](https://github.com/sgl-project/sglang/pull/46088#issuecomment-6433899393)

Thanks for measuring this. I pushed 5dd262e196 and aeddd7ceb8 (the kernel test was later dropped from this PR in a7e7b2491a):

- **Row cap.** `MAX_ROWS` is now 1024, which covers your 330-492 rows and a 128-request-per-rank decode graph with DSpark (768 rows). 384 had no structural reason; the kernel is one CTA per row and has no row limit of its own. I kept a cap rather than removing it because the gate is also the decode proxy, and prefill sizes go to the Mega-mHC or prefill kernels.
- **Correctness above 384 rows.** I checked 1-1024 rows (including 480, 768, 960 and 1024), with and without MXFP8 output, on sm_107: `updated` is bitwise equal to `mhc_post_split_h`, and the MXFP8 pair is bitwise equal to FlashInfer's quantizer applied to the kernel's own normed rows.
- **Threads per row.** The default was a fixed 320. It is now chosen from how many rows fit in one wave on the device: 640 threads while every row fits at one CTA per SM, then 320, then 160. Microbenchmarks on sm_107 showed that a fixed 320 or 640 falls into a second wave in your row range, and the new default matches the best fixed choice from 6 to 1024 rows. It also stays faster than the unfused post + combine + quantize across that range.
- **Side stream.** Agreed. The next layer's stats GEMM can only start once `updated` is written, so it now starts after the fused kernel instead of after the bare post. The work is still hidden at our sizes, but it does depend on how SMs are shared. I haven't changed that here.




- zcnrex · comment · 2026-10-27T21:12:13Z · [source](https://github.com/sgl-project/sglang/pull/46088#issuecomment-6453686933)

Thanks for the review. Addressed in 5bdef35 and 0b49759, then merged main (7d07f50).

**Dispatch cost.** The fixed checks (platform and `HcConfig`: `pre_from_prev`, mult, hidden, `cp_prefill`) now live in `_decode_post_combine_supported(cfg)`, which is cached per `HcConfig`. Each call runs only the row gate and the batch-invariant check. I dropped the per-call dtype and contiguity checks. The producers always pass bf16 contiguous `y`/`residual` and fp32 contiguous coefficients, which is the same contract the fused prefill branch right below already relies on. The kernel entry still verifies dtype, shape and contiguity through `TensorMatcher`, so a violation raises instead of computing garbage.

**Decode/verify mode.** This is intentional. The gate is by row count, not by forward mode. A prefill of up to 1024 rows has the same launch and dependency structure and gets the same saving, and the kernel is correct at any row count up to `MAX_ROWS`.

**[P2] Batch invariance.** The path is now skipped whenever `is_batch_invariant_mode_enabled()`, so that mode always takes the unfused post plus combine, whatever the thread choice or the `MAX_ROWS` cutover.

**[P3] Inventory.** Registered `layernorm.mhc_post_combine_norm_decode` as a JIT `KernelSpec`, CUDA `min_sm=(10, 0)`, which matches the `is_blackwell` gate.

**Test.** Restored a small test:
- At every thread-count transition on the running device (`b` and `b + 1` for each wave boundary), plus 1 and `MAX_ROWS`, with and without MXFP8, against `mhc_post_split_h` + `hc_combine_norm` (+ the FlashInfer quantizer). The post must match bitwise; the norm must match within tolerance.
- A gate check: on at `MAX_ROWS`, off above it, off at 0 rows, and off in batch-invariant mode.

Passes on sm_107.

Good catch, all three points hold: the flag is only filled in by the MLP sync, `ForwardMode.is_extend()` includes TARGET_VERIFY, and the sync max-reduces it over DP ranks. Fixed in a865b16. The gate now reads this rank's own forward mode, `mode.is_extend() and not mode.is_target_verify()`, carried on the per-forward `HcNextBoundary` (`extend`). So:

- Verify never takes it.
- Prefill graph capture still works, because the captured batch's mode is EXTEND (the same reason `should_use_mega_gate` gates on the mode).

Nothing couples across ranks: the Mega-mHC boundary is rank-local, and the mega-MoE input it may pre-fill is only produced for decode/verify.
