# [Radix Cache] Optionally keep an SWA margin beyond the window in cached prompts

[Upstream PR](https://github.com/sgl-project/sglang/pull/42703) · state: open · merged: False

## Original PR description

## Motivation

On hybrid sliding-window (SWA) models, a cached prompt can only be reused by a request whose prefix match ends exactly at the prompt's end, or one token before it. A match that ends a few tokens earlier is refused entirely, although the tree still holds the whole prefix.

Chat clients hit this on the second turn of every conversation with Gemma-4 12B, 26B-A4B and 31B. With thinking off, their chat templates end the generation prompt with `<|turn>model\n<|channel>thought\n<channel|>`, but re-render the finished assistant turn as `<|turn>model\n{reply}<turn|>`. So turn two's prompt matches turn one's cached prompt only up to 4 tokens before its end, and the second turn re-prefills its whole history. A later turn hits only while the previous turn added less than about one window of new tokens, so that the earlier window is still live behind its match point. Otherwise it misses the same way. (The current E2B and E4B templates do not add the empty thought channel and are not affected.)

Why the short match is refused:
1. Before a prefill insert, `checkpoint` frees the request's SWA out of the sliding window (`free_swa_out_of_window_slots`). At page size 1 this leaves `W + 1` live SWA tokens behind the prompt end `pe`, where `W` is `sliding_window_size` (1023 for a 1024 window), and the rest of the prompt becomes an SWA tombstone.
2. `SWAComponent.create_match_validator` accepts a match end only with at least `W` contiguous live SWA tokens behind it. Behind `pe - k` there are `W + 1 - k`, so any `k >= 2` falls back to the last valid node.

Shortening the match does not help: the live window ends at `pe`, so no match end at or before `pe - k` has a full window behind it. Accepting the incomplete window would make the extend attend to freed SWA slots.

## Modifications

`SGLANG_SWA_CACHE_WINDOW_MARGIN` (int, default 0: behavior unchanged) keeps that many extra SWA tokens live behind an insert's end, so a later match ending up to that many tokens short can still reuse the prompt.

- `SWAComponent.cached_window_size = sliding_window_size + margin`, read once at construction. The insert-time out-of-window free (`_free_out_of_window_slots`) keeps `cached_window_size`.
- The fresh-leaf split for the SWA lock (`_maybe_split_leaf_for_swa_lock`, and `maybe_split_leaf_for_swa_lock_` in the Rust tree core) caps the leaf at `cached_window_size` instead of one window. Otherwise the margin would sit in a separate parent node outside the window that the lock's LRU refresh covers, and SWA eviction would take it first. The Rust core gets the margin through a new `swa_cache_window_margin` init param (default 0).
- A prompt whose prefill insert stopped at an SWA branch point (`swa_branching_seqlen`) stays request-owned until the request finishes, and decode-time eviction, which knows only the window, would free its margin first. `UnifiedRadixCache.swa_retain_floor` now also returns `len(origin_input_ids) - cached_window_size` while that span is not yet in the tree (`cache_protected_len` below it). A prompt that is already in the tree gets no floor, so decode keeps sliding its window as before. Requests barred from the tree (`skip_radix_cache_insert`) get no floor either.
- Mamba hybrids get no margin floor: they insert at their checkpoints, so a match lands there and cannot use a margin behind the prompt end.
- A negative margin is rejected at construction; it would free in-window SWA of a running request.
- Decode-time eviction is otherwise unchanged; it still keeps one window.
- `docs/docs/references/environment_variables.mdx` documents the variable.

This is opt-in rather than a default change because it costs SWA pool capacity:
- each cached prompt keeps `margin` more live SWA tokens;
- a branch-inserted prompt holds its window + margin, and with it its reply's SWA, until the request finishes.

The margin a template needs is the number of tokens the re-rendered turn cuts from the cached prompt: 4 for the Gemma-4 templates above. An env var follows how the other SWA retention knobs are exposed (`SGLANG_SWA_EVICTION_INTERVAL`, `SGLANG_OPT_UNIFIED_CACHE_FREE_OUT_OF_WINDOW_SLOTS`). Setting it from a model's chat template automatically would need a server arg, which is left for a follow-up. The Gemma-4 cookbook page is unchanged: its recommended deployment does not change, and the margin's cost under SWA pressure has not been measured on it.

Limitations:
- The hold for a branch-inserted prompt is unbounded: it keeps the reply's SWA until the request finishes, which SWA admission does not budget for.
- HiCache load-back, storage prefetch and session coverage still size their SWA spans by one window, so the margin does not survive a round trip through the host tier.

Tests (`TestSWACacheWindowMargin` in `test/registered/unit/mem_cache/test_unified_radix_cache_unittest.py`, window 7, page size 1, 24-token prompt, next turn cut 3 tokens short). The suite also runs on the Rust tree core through `test_rust_unified_radix_cache_unittest.py`.
- Without the margin the next turn matches 0 tokens; with margin 3 it matches 21, and the inserted leaf holds window + margin. The leaf-length check fails on the Rust core without the Rust change (7 != 10).
- A prompt whose prefill insert stopped at an SWA branch point keeps window + margin through 10 decode steps and the finish insert, and the next turn matches 21.
- A prompt already in the tree is not held by the margin: after 20 decode steps the request's SWA eviction cursor is at `seq_len - 1 - W`, as without the margin. A floor that ignores whether the prompt is in the tree keeps the cursor at the prompt end and fails this case.
- A mamba hybrid before its first checkpoint gets no floor from the margin, and a negative margin raises.

Related: #42700 fixes a HiCache SWA admission crash seen under the same Gemma-4 chat load. Independent of this PR.

## Accuracy Tests

KV contents and attention are unchanged; the margin only keeps already-computed SWA KV alive longer.

Second-turn reuse with `google/gemma-4-12B-it` on one RTX 5090, launched with the Gemma-4 cookbook flags plus `--enable-cache-report` (`--reasoning-parser gemma4`; Rust tree core; page size 1). Four two-turn chats through `/v1/chat/completions`, each turn one ~1.5K-token user message, `temperature 0`; turn 2 resends turn 1's messages + the assistant reply + a new question.

| build | margin | turn 1 prompt tokens | turn 2 cached tokens | sessions where turn 2 reused turn 1 |
|---|---|---|---|---|
| `main` | - | 1519-1520 | 4 | 0/4 |
| this PR | 0 (default) | 1519-1520 | 4 | 0/4 |
| this PR | 4 | 1519-1520 | 1515-1516 | 4/4 |

The 4 cached tokens without the margin are the shared `<bos><|turn>user\n` prefix. With the margin, turn 2 reuses all of turn 1's prompt except the 4 re-rendered tokens. `google/gemma-4-E4B-it`, whose template has no empty thought channel, reuses the full turn-1 prompt in every configuration.

Reproduce: launch `python -m sglang.launch_server --model-path google/gemma-4-12B-it --reasoning-parser gemma4 --enable-cache-report` (add `SGLANG_SWA_CACHE_WINDOW_MARGIN=4` for the fixed run), then:

```python
import random, requests

words = "river stone garden window letter market winter music silver forest".split()
url = "http://127.0.0.1:30000/v1/chat/completions"

def chat(messages):
    r = requests.post(url, json={"model": "default", "messages": messages,
                                 "temperature": 0, "max_tokens": 48}).json()
    return r["choices"][0]["message"]["content"], r["usage"]

rng = random.Random(0)
messages = [{"role": "user",
             "content": " ".join(rng.choices(words, k=1500)) + "\n\nWhich word appears first?"}]
reply, usage1 = chat(messages)
messages += [{"role": "assistant", "content": reply},
             {"role": "user", "content": "Which word appears last?"}]
_, usage2 = chat(messages)
print("turn 1 prompt:", usage1["prompt_tokens"],
      "turn 2 cached:", usage2["prompt_tokens_details"]["cached_tokens"])
```
