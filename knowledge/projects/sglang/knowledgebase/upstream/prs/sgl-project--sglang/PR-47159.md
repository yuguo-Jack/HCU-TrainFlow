# [Feat] observability: Report a TTFT phase breakdown in response meta_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/47159) · state: closed · merged: True

## Original PR description

## Motivation

First-token latency is reported as a single number, but the timestamps that split it into phases are already in `ReqTimeStats`: when the tokenizer created the request, when the scheduler first ran a forward for it, when prefill finished, how long it queued, and how much of that queue was a storage prefetch wait. A consumer of `meta_info` who wants to know whether a slow TTFT came from queueing, from the prefill forward, or from the time after prefill has to subtract these by hand and re-derive the same validity conditions every time.

## Modifications

> **Update after #47166:** the tokenizer no longer receives `SchedulerReqTimeStats`, so this branch was rebased and `get_ttft_breakdown()` was adapted to read the per-request `SchedulerOutputTimeStats` that the scheduler now sends. `compute_ttft_breakdown()` and the emitted `meta_info` keys are unchanged from the first revision of this PR.

- `python/sglang/srt/observability/req_time_stats.py`
  - Add `compute_ttft_breakdown()`, a pure function that returns phase durations in seconds and omits any phase whose inputs are missing, non-finite, or out of order:
    - `storage_prefetch_wait` and `other_queue` when a finished prefetch wait is known and fits inside the queueing time;
    - `prefill_latency` from first forward entry to prefill completion (includes gaps between chunks);
    - `before_queue` and `after_prefill`, the remainders of TTFT around queue + prefill, only for requests with zero retractions, since a retraction re-queues the request and the boundaries are no longer monotonic. `after_prefill` is an elapsed-time remainder, not a transfer timer.
  - Add `APIServerReqTimeStats.get_ttft_breakdown()`, which feeds the function from the request's `SchedulerOutputTimeStats`: its wall-clock `forward_entry_time` / `prefill_finished_time` are compared against the request's creation time converted to the same clock, `queue_time` is used as is, and `storage_prefetch_wait` is already `None` while the wait is still running.
  - `convert_to_output_meta_info()` takes optional scheduler stats and `num_retractions` and merges the breakdown into `meta_info` when scheduler stats are given.
- `python/sglang/srt/managers/tokenizer_manager.py`
  - Pass the request's scheduler output time stats and retraction count into `convert_to_output_meta_info()`.

Existing fields are unchanged. Requests without scheduler time stats get no new fields; callers that do not pass `num_retractions` get `prefill_latency` and the prefetch pair but not `before_queue` / `after_prefill`.

Example, for timestamps (seconds, same clock) received=0.0, forward_entry=0.5, prefill_finished=0.9, queue_time=0.3, prefetch_wait=0.1, ttft=1.0 on a never-retracted request:

```
{"storage_prefetch_wait": 0.1, "other_queue": 0.2, "prefill_latency": 0.4,
 "before_queue": 0.2, "after_prefill": 0.1}
```

The same timestamps on a request retracted once keep `storage_prefetch_wait`, `other_queue` and `prefill_latency` but drop `before_queue` and `after_prefill`; with no prefetch wait recorded, a retracted request yields only `{"prefill_latency": 0.4}`.
