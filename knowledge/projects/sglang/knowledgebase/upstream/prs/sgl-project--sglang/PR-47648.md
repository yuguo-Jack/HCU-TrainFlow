# [Fix] [AMD] layernorm: use the Triton Gemma RMSNorm kernels on ROCm without aiter or vLLM

[Upstream PR](https://github.com/sgl-project/sglang/pull/47648) · state: closed · merged: False

## Original PR description

## Motivation

On ROCm, `GemmaRMSNorm.forward_hip` only uses SGLang's Triton Gemma RMSNorm kernels (`sglang.kernels.ops.layernorm.minimax_m3_rmsnorm`) when `_use_aiter` is set. Those kernels are plain Triton and import without aiter. `SGLANG_USE_AITER=1`, however, needs aiter installed.

So on a ROCm machine with neither aiter nor vLLM, no setting selects the kernels, and every Gemma-style norm runs `forward_native`, which is about 11 small kernels per call. That covers, for example, the Radeon GPUs aiter does not support, and `rocm/pytorch`-based images. Models using `GemmaRMSNorm` include the Gemma family, Qwen3-Next / Qwen3.5, MiniMax-M3 and Step-3.5.

## Modifications

- `layernorm.py`: use the Triton Gemma kernels whenever they import, unless aiter is off and vLLM provides the fused norm. That is, `_has_rocm_triton_gemma_rms_norm and (_use_aiter or not _has_vllm_rms_norm)`. The aiter and vLLM paths are unchanged.
- `test/registered/unit/layers/test_gemma_rmsnorm_hip_dispatch.py` (CPU): without aiter and vLLM, the Triton kernels are used, and the code falls back to `forward_native` when they do not import. The first case fails on current main.

## Accuracy Tests

The kernels are the ones already used under aiter, and `test_minimax_m3_rmsnorm.py` covers them against a reference. In addition:
- `residual_out` is bitwise equal to `forward_native`.
- The normalized output is within 0.5 ulp of a float64 reference.
- The kernel normalizes the fp32 sum while `forward_native` normalizes the bf16-rounded sum, so 69-74% of outputs are bitwise equal to native and the rest differ by at most ~2 ulp.

End to end on gfx1100 (RDNA3, W7900-class), Qwen/Qwen3.5-9B bf16, TP1, no aiter, with vLLM hidden from the environment, default flags. Both arms run on main plus #43679 (sgl-kernel build for RDNA) and #47254 (RDNA attention default): gsm8k (sgl-eval, 100 questions, thinking off, T=0.7) is 97% before and 95% after, which is within sampling noise.

## Speed Tests and Profiling

Per-call latency on gfx1100 (RDNA3), bf16, hidden 5120, eager loop:

| rows | `forward_native` (us) | Triton Gemma kernel (us) |
|---:|---:|---:|
| 1 | 46.2 | 30.6 |
| 8 | 50.6 | 30.5 |
| 1024 | 179 | 32.6 |
| 8192 | 2,670 | 467 |

On Qwen3.8-27B (bf16, TP2, gfx1100), `forward_native` norms were about 1,430 of 2,290 kernel launches per decode step.

End to end, same setup, `bench_serving` random ids (512 in / 256 out). Two rounds, alternating before / after on the same GPU:

| | c1 tok/s | c1 median TPOT | c8 tok/s | c8 median TPOT |
|---|---:|---:|---:|---:|
| main | 22.26 / 22.31 | 44.34 ms | 158.92 / 158.89 | 47.78 ms |
| this PR | 23.77 / 23.80 | 41.57 ms | 170.31 / 170.66 | 44.45 ms |

That is about 2.8 ms less per decode step (+6.8% at c1, +7.3% at c8). The rounds agree to within 0.3%.

This is generic HIP code, so it is on `main`. Radeon work otherwise lands on `amd_march`; I can send the same one-line change there if you prefer.
