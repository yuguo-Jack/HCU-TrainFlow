# [AMD][Kernel] Add a K-only store_cache and use it for the MiniMax index-K pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/41672) · state: open · merged: False

## Original PR description

## Motivation

`MHATokenToKOnlyPool.set_k_buffer` — the MiniMax sparse index-K cache — writes with
an elementwise `self.k_buffer[layer_id][loc] = cache_k`, which lowers to
`index_put_`. The JIT `store_cache` kernel already exists for exactly this shape of
write and is faster, but it has no K-only form: both `store_cache` and
`can_use_store_cache` take a K **and** a V tensor. A key-only pool could only reach
it by passing the same tensor twice, which aliases two pointers the kernel declares
`__restrict__` and issues the store twice to one address — not something to ship.

So this adds the missing form rather than abusing the existing one.

## Performance measurements

MI355X (gfx950), ROCm 7.2.4, MiniMax-M3-MXFP4, TP2.

Kernel level, from the profile config's decode plateau: the `index_put_` route
costs **287.1 us/step**; the JIT store route costs **225.6 us/step** on a strictly
larger write -- the main pool moves two heads of K and of V, this pool moves one
head of K.

### Isolated vs cumulative e2e performance

The sweep above is deliberately narrow -- three VL configs at TP2 -- and it isolates
this one change. It is one of a series of VL-specific optimizations (#41662, #41663, #41664, #41665),
which cumulatively give over 20% uplift over the baseline across a wider 8-row
config sweep at TP2, TP4 and TP8.

The 8-row sweep tests how the proportion of VL input tokens affects inference
performance. It is parameterized by image size, input length and concurrency:

A cumulative total cannot be divided back into per-PR shares, which is why this PR
quotes its isolated number above rather than a share of the total.

## Compatibility

Additive. The existing `store_cache` signature, its `v_row_bytes=0` sentinel and
every current caller are unchanged; the only behavioural change is in
`MHATokenToKOnlyPool.set_k_buffer`, which stores the same bytes at the same
indices. Numerically identical to the `index_put_` it replaces — this is a memory
movement change, not an arithmetic one.

Depends on #37732 and #38035 for accurate benchmark numbers
