# [Feat] tokenizer: await toktier's worker pool in TokenizerManager._tokenize_texts

[Upstream PR](https://github.com/sgl-project/sglang/pull/44382) · state: open · merged: False

## Original PR description

## Motivation

With the toktier backend (#44373, which this PR stacks on) the encode still runs in the tokenizer manager's process, on the event loop's thread. One long encode then holds the loop, and a short session append waits behind a whole long request. toktier ships a worker pool for this. With `TOKTIER_SGLANG_SESSION_KEY=contextvar`, keyed requests go to a home worker that holds their session state. Stateless requests (every request in `off` mode, or a long keyless one in `contextvar` mode) enter a shared shortest-first queue, cut into chunks once they reach `TOKTIER_SGLANG_SCHED_CHUNK_MIN_CHARS` characters (131072 by default). In the default `auto` mode each request is a content lookup on a worker chosen from the start of the text, never chunked, with the same ids. A request the pool cannot answer is encoded in process as before. The pool lives in toktier; SGLang needs one hook to await it. The design and the measurements are in [RFC #44374](https://github.com/sgl-project/sglang/issues/44374), roadmap item 2, and in the [Delta Tokenizer paper](https://arxiv.org/abs/2610.19801) (arXiv:2610.19801), §4.5 and §4.6.

## Modifications

One hunk in `TokenizerManager._tokenize_texts`. When the backend is `toktier` and the input is plain text (a string or a list of strings), the method awaits `toktier.integrations.sglang.tokenize_texts_with_pool`, which returns `(input_ids, None)`. With any other input (cross-encoder pairs, EmbeddingGemma, an empty string), or with no pool running, the call returns `None` and the method continues unchanged. The pool starts only when `TOKTIER_SGLANG_SCHED_WORKERS` is set above zero, so nothing changes by default even with the backend on. Worker processes are spawned (`multiprocessing` "spawn" context) and closed with the wrapper.

There is also a CPU unit test, `test/registered/unit/managers/test_toktier_pool.py`, skipped unless toktier (>= 0.3.0) is installed. toktier 0.3.0 is on PyPI (`pip install 'sglang[toktier]'` with #44373), so the test now runs instead of skipping.

Draft, stacked on #44373; the diff shows both, including the backend's test commit, until that one lands.

## Accuracy Tests

The unit test, run locally against the toktier 0.3.0 release, has 6 tests and all pass. The pool starts with two workers. A single text and a batch of texts are answered by the pool with ids equal to the Hugging Face tokenizer's. A two-turn session under a bound `session_id` with `TOKTIER_SGLANG_SESSION_KEY=contextvar` gets the same ids, and the wrapper's `stats()` shows both turns on the pool's session route, served by one worker; in the default `auto` mode the same session gets the same ids by content lookup on the pool. Cross-encoder input, an empty string, text pairs and a plain Hugging Face tokenizer fall through (`None`). The paper's serving runs with the pool reported the same prompt-token counts as the reference and no difference in 2,195 and 2,268 independent re-encodes of served text.

## Speed Tests and Profiling

Warm turns on SGLang v0.5.19 with Qwen3-8B (bf16) on an RTX PRO 6000 and the HTTP process pinned to 16 cores of an AMD EPYC 9115, from the paper. The full tables are there and in the RFC.

| Setting | Reference | toktier in process | toktier pool |
|---|---|---|---|
| P99 TTFT, twelve 100K-character sessions, 24 warm turns/s | 995 ms | 103 ms | 105 ms |
| P99 TTFT, same sessions at 8 turns/s, plus four one-million-character stateless requests every 8 s (over the model's context, declined after tokenization, so they load only the front end) | 1,441 ms | 166 ms | 63 ms |
| P99 TTFT, same sessions, plus a repeated ~100K-token document served from the prefix cache | 498 ms | 66.5 ms | 67.5 ms |

The pool's own cost is the text and the ids crossing a process boundary, about 2 ms at 100K tokens.
