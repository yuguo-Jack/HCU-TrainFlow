# [Fix] [AMD] quark: Fix the EP>1 crash in the Quark MXFP4 W4A16 MoE path and restrict it to gfx1151

[Upstream PR](https://github.com/sgl-project/sglang/pull/47408) · state: closed · merged: True

## Original PR description

## Motivation

**What goes wrong**
Serving a Quark MXFP4 MoE checkpoint with `--ep-size` > 1 on the W4A16 path added in #41389 aborts the GPU with `HSA_STATUS_ERROR_EXCEPTION: An HSAIL operation resulted in a hardware exception. code: 0x1016`. Under expert parallelism the standard dispatcher hands each rank `topk_ids` where experts owned by other ranks are `-1`, and `_apply_triton_w4a16` feeds those ids straight into `counts.scatter_add_(...)`, which writes out of bounds.

**Where it shows up**
Every GPU that takes the W4A16 path with EP > 1. It was reported on #41389 for both gfx1151 and gfx942, and reproduced here on gfx1151. The path was also enabled on every HIP GPU that is not gfx95x or gfx1250 (so gfx942/MI300X as well), although it was written and validated for gfx1151.

**How to fix**
Send `-1` ids to an extra bucket that sorts last, is left out of the ragged expert counts, and is zeroed before the top-k reduction, and enable the path only on gfx1151.

This PR also addresses the review comments on #41389 that were still open at merge time: log once when the W4A4 checkpoint runs as W4A16, register the opt-out env var in `environ.py`, and reject SwiGLU variants the path cannot compute (`gemm1_alpha`, `gemm1_beta`, `gemm1_clamp_limit`, `swiglu_limit`, e.g. gpt-oss, DeepSeek-V4, MiniMax-M3), which previously passed the `activation == "silu"` check and produced silently wrong output.

## Modifications

All runtime changes are in `python/sglang/srt/layers/quantization/quark/schemes/quark_w4a4_mxfp4_moe.py` and only take effect on gfx1151.

- Gate: `_use_triton_w4a16` is now `gfx1151 and SGLANG_ENABLE_QUARK_MXFP4_MOE_W4A16` instead of "HIP and not gfx95x and not gfx1250". gfx942 and other AMD GPUs go back to the AITER path.
- EP fix in `_apply_triton_w4a16`: `-1` ids are mapped to bucket `num_experts`, `counts` gets one extra slot that is dropped before `make_ragged_tensor_metadata`, and the scattered rows of non-local slots are zeroed with `masked_fill` before the sum over `top_k`. Everything stays on device, so CUDA graph capture still works.
- Env var: `SGLANG_QUARK_MXFP4_MOE_W4A16` becomes `SGLANG_ENABLE_QUARK_MXFP4_MOE_W4A16 = EnvBool(True)` in `python/sglang/srt/environ.py` (AMD section), read via `envs.....get()`. The name gains the `ENABLE_` verb required by the env-var conventions; it was only on the #41389 branch, never in a release.
- `_process_weights_triton_w4a16` raises `NotImplementedError` listing the unsupported SwiGLU parameters instead of running plain SwiGLU.
- `logger.info_once` reports that the W4A4 MXFP4 checkpoint runs as W4A16 and how to disable it.
- New `test/registered/unit/layers/quantization/test_quark_w4a4_mxfp4_moe_w4a16.py` (stdlib `unittest`, `register_amd_ci(est_time=40, stage="stage-b", runner_config="1-gpu-small-amd")`), entering through `create_moe_runner` / `process_weights_after_loading` / `apply_weights`:
  - `test_gfx942_keeps_the_aiter_path`, `test_gfx1151_uses_the_w4a16_path`, `test_env_switch_disables_the_w4a16_path_on_gfx1151` (gate, by reloading the module with a mocked `gcnArchName`)
  - `test_ep_rank_outputs_sum_to_single_rank_output` (ep=2 outputs summed over ranks equal the ep=1 output)
  - `test_tokens_routed_only_to_other_ranks_produce_zero_output`
  - `test_clamped_swiglu_config_is_rejected`

## Accuracy Tests

Setup for all tables: 1x gfx1151 (Radeon 8060S, 96 GB VRAM carve-out), tp=1, `amd/Qwen3.5-35B-A3B-MXFP4`, `--attention-backend triton --context-length 8192`, image `rocm/sgl-dev:v0.5.20-rocm724-gfx1151-20260923`. Before = #41389 as merged; After = this PR.

**EP crash (kernel level).** This GPU has a single device, so EP > 1 was exercised by calling `_process_weights_triton_w4a16` / `_apply_triton_w4a16` with the `topk_ids` the dispatcher produces under EP (Qwen3.5-35B-A3B MoE shapes: 256 experts, top-k 8, hidden 2048, intermediate 512; random MXFP4 weights).

|---|---|---|

| CUDA graph capture + replay with `-1` ids | n/a | bit-identical to eager |

**GSM8K at ep=1** (regression check for the default path). sgl-eval 0.1.3, 200 questions, thinking off (`enable_thinking=false`), `temperature=1.0`, `top_p=0.95`, `seed=0`, 16 concurrent requests.

| | Before | After |
|---|---|---|
| GSM8K score | 63.0% | 60.0% |

The 3-point gap is sampling noise, not a numerical change: at ep=1 the MoE output of `_apply_triton_w4a16` is bit-identical before and after (`torch.equal` on N = 1 / 16 / 27 / 512 tokens, max abs diff 0), because every id is valid and the new ops are identities. The end-to-end runs differ only through temperature-1.0 sampling with nondeterministic batching (200 questions give a standard error of about 3.4 points). With thinking off the model answers with `\boxed{N}` and little or no reasoning, so this run checks before/after equivalence, not the model's best score. For reference, before with thinking on scored 82.0%, but 31% of answers were truncated by the 8192-token context.

The 57% is in line with your thinking-off numbers on gfx1151 (60-63%). Your unit test passes here (6 passed).

RDNA3/RDNA4 are in the same position as gfx1151: no FP4 hardware and no AITER FP4 MoE kernel. So restricting the path to gfx1151 drops them. Would you consider keying the gate on "consumer RDNA" instead of gfx1151 only? For example:
- gfx11xx plus gfx1200/gfx1201, but not gfx1250, which matches `gfx12` too;
- or the `is_rdna` platform flag that #47254 adds.

gfx942 would still go back to AITER as you intend.

Separately, when the AITER path is taken without aiter installed, failing with a clear "requires aiter" error would be easier to diagnose than the `NameError`.
