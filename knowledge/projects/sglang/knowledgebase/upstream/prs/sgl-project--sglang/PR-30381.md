# Speed up FP8 per-token quant vec8 stores

[Upstream PR](https://github.com/sgl-project/sglang/pull/30381) · state: closed · merged: False

## Original PR description

## Summary

This speeds up the `kVecSize == 8` path in `sgl_per_token_quant_fp8`.

The existing `kVecSize == 16` path already used a packed `uint4` store, but the `kVecSize == 8` path fell back to element-wise FP8 stores. This PR adds a single `uint64_t` store for `kVecSize == 8`

## Code Review

This pull request optimizes memory copying for a vector size of 8 in both `per_token_quant_fp8_kernel` and `per_token_quant_fp8_small_batch_kernel` by casting the output array to `uint64_t*` instead of using element-wise copies. The reviewer noted that casting `output_arr` to `uint64_t*` or `uint4*` can cause undefined behavior or alignment faults due to the 1-byte alignment of `DST_DTYPE`. They recommended aligning `output_arr` to 16 bytes using `alignas(16)` in both kernels to ensure safe memory access.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Keep vec8 stores from assuming 8-byte output alignment**

When `output_q` is a contiguous FP8 view with a non-zero byte storage offset, `CHECK_INPUT(output_q)` still accepts it, but this casts the byte-addressed FP8 pointer to `uint64_t*` and emits a naturally aligned 8-byte store. For `hidden_dim % 8 == 0 && hidden_dim % 16 != 0`, such an output can be only byte-aligned, so the vec8 path can perform misaligned 64-bit global stores and corrupt/fault where the previous element-wise writes were safe; the identical vec8 store in the small-batch kernel needs the same guard or fallback.
