# [Perf][DSA] Pass transform_index strides at runtime instead of constexpr

[Upstream PR](https://github.com/sgl-project/sglang/pull/36888) · state: open · merged: False

## Original PR description

## Motivation

`transform_index_page_table_{decode,prefill}_kernel` declare their stride
parameters `tl.constexpr`. A `tl.constexpr` value becomes part of Triton's
compilation cache key, and one of these strides changes on almost every call:

```python
# srt/layers/attention/dsa_backend.py
max_seqlen_k = int(forward_batch.seq_lens.max().item()) + draft_token_num
page_table = self.req_to_token_pool.req_to_token[
    forward_batch.req_pool_indices, :max_seqlen_k
]
```

Advanced indexing yields a contiguous copy of shape `[bs, max_seqlen_k]`, so
`page_table.stride(0) == max_seqlen_k` — which grows as the sequence grows. In
speculative decoding, `draft_extend` is prefill-shaped and runs every MTP cycle,
so the prefill kernel is re-keyed and recompiled continuously under load.

Measured over one 300 s run at concurrency 1, by wrapping
`transform_index_page_table_prefill_fast` and logging the value:

```
calls 4,822    distinct page_table.stride(0) 4,723    range 8 .. 189,881

  call#1     stride0=8         shape=[4, 8]
  call#2     stride0=11        shape=[4, 11]
  call#3     stride0=14        shape=[4, 14]
  ...
  call#4822  stride0=112,834   shape=[4, 112,834]
```

It increments by ~3 per call — the MTP accept length — i.e. a fresh cache key on
essentially every call. Instrumenting Triton's own hooks
(`knobs.compilation.listener` plus `jit_cache_hook` / `jit_post_compile_hook`) in
every worker process over the same run:

| | before | after |
|---|---:|---:|
| Triton cache misses | 8,346 | **10** |
| compile wall, per TP rank | 158.2 s | **0.6 s** |
| `cpu/wall` during compiles | 0.979 | — |
| miss cost, median | 34.807 ms | — |
| hit cost, median | 0.429 ms | — |

`cpu/wall = 0.979` confirms CPU-bound codegen rather than I/O or lock contention;
`store_results` totals 493 ms of the 105 s, under 0.5%.

## Modifications

Signature-only. Both call sites already pass these positionally or by keyword, so
there are no caller changes.

```diff
 @triton.jit
 def transform_index_page_table_decode_kernel(
     page_table_ptr: torch.Tensor,
     topk_indices_ptr: torch.Tensor,
     result_ptr: torch.Tensor,
-    page_size: tl.constexpr,
-    page_table_row_stride: tl.constexpr,
+    page_size,
+    page_table_row_stride,
 ):
```

```diff
 @triton.jit
 def transform_index_page_table_prefill_kernel(
     page_table_ptr: torch.Tensor,
     topk_indices_ptr: torch.Tensor,
     cu_seqlens_q_ptr: torch.Tensor,
     result_ptr: torch.Tensor,
-    page_table_stride_0: tl.constexpr,
-    page_table_stride_1: tl.constexpr,
-    topk_indices_stride_0: tl.constexpr,
-    topk_indices_stride_1: tl.constexpr,
-    result_stride_0: tl.constexpr,
-    result_stride_1: tl.constexpr,
+    page_table_stride_0,
+    page_table_stride_1,
+    topk_indices_stride_0,
+    topk_indices_stride_1,
+    result_stride_0,
+    result_stride_1,
     PAGE_TABLE_IS_EXPANDED: tl.constexpr,
     TOPK: tl.constexpr,
     BLOCK_Q: tl.constexpr,
     BLOCK_TOPK: tl.constexpr,
 ):
```

### Why these are safe to make runtime, and why the others are not

Every stride appears only as a multiplier in address arithmetic:

```python
page_table_ptr + req_id * page_table_row_stride
tl.load(page_table_ptr + rows[:, None] * page_table_stride_0
                       + loaded_topk_indices * page_table_stride_1, ...)
```

No tile shape, loop bound, or branch depends on their values, so the emitted
instruction sequence is identical for stride 8 and stride 189,881 — only the
operand differs. On AMD ISA a stride of that magnitude also exceeds the
inline-immediate range and must be materialised into a scalar register either way,
so `constexpr` was not buying a folded constant here.

The remaining `constexpr` parameters are load-bearing and **kept**:

- `TOPK`, `BLOCK_Q`, `BLOCK_TOPK` — used as `tl.arange` bounds, which define tile
  shapes and must be compile-time.
- `PAGE_TABLE_IS_EXPANDED` — selects which codegen path is emitted.

All four are bounded (`TOPK` = 2048 asserted, `BLOCK_TOPK` = 256,
`BLOCK_Q` ∈ {1,2,4}, flag is a bool), so they compile once and cache. Triton also
auto-specialises integer args on divisibility-by-16 and `== 1`, so the key space
becomes a small bounded set rather than one binary — consistent with the 10
residual misses above.

`page_size` is included so this patch corresponds exactly to the configuration the
numbers were measured on. It contributes no key churn either way: it is asserted
`== 1` at both call sites, and Triton auto-specialises integer arguments on `== 1`
regardless. It is in fact never referenced in the decode kernel body, so it could
equally be deleted as separate cleanup. Happy to drop this hunk if reviewers would
rather the PR touch strides only.

## Accuracy Tests

A stride describes memory layout, not semantics: the computed address is identical
whether the multiplier arrives in the binary or in the launch arguments. Nothing
about which value is used changes.

`test/registered/kernels/ops/attention/test_dsa_transform_index.py` — the existing
test for both kernels, which includes `test_decode_fast_correctness_and_strides`
and `test_large_context_lengths` — run on MI355X (gfx950), ROCm 7.2, torch
2.9.1+rocm7.2.0, Triton 3.7.0, in both arms:

```
ARM: UNPATCHED (baseline)          7 passed, 2 subtests passed in 8.89s
ARM: PATCHED (strides at runtime)  7 passed, 2 subtests passed in 8.08s
```

End-to-end on GLM-5.2-MXFP4 in PD 2P2D at TEP2, every patched run:

- kernels per decode cycle unchanged: 238 → 238
- 120k-token needle retrieval 3/3 at 10% / 50% / 90% depth
- correctness smoke check passed

## Speed Tests and Profiling

TPOT p50, 300 s per point, same image and runner, only the patch differing:

| concurrency | before | after | ratio |
|---|---:|---:|---:|
| 1 | 21.85 ms | 8.27 ms | **2.64×** |
| 2 | 14.85 ms | 8.70 ms | 1.71× |
| 4 | 12.51 ms | 8.08 ms | 1.55× |
| 8 | 26.42 ms | 9.92 ms | **2.66×** |

Non-monotonic: the patched arm is stable at 8.08–9.92 ms while the baseline swings
12.51–26.42 ms, which is what a compile-load-dependent cost predicts. TTFT is flat
throughout (2.10–2.27 s) — this is decode-side only.

Per-launch kernel durations show no slowdown from passing the strides at runtime.
The two transform kernels move by no more than the run-to-run drift of unrelated
control kernels in the same traces (`grouped_topk_kernel` 4.76 → 4.84 µs,
`topk_kernel` 133.82 → 134.86 µs, both 1–2%). Those are separate jobs, so I claim
only "no regression" rather than a specific delta.

Environment: `sglang-0.5.17.dev20260818+g7605529bdf`, ROCm 7.2, MI355X (gfx950),
GLM-5.2-MXFP4, prefill/decode disaggregation 2P2D at TEP2.

## Scope: which configurations reach these kernels

Reachability is decided by `should_use_dsa_fused_topk()` in
`srt/layers/attention/dsa/utils.py`, not by platform capability:

```python
pd_index_share_seed = (disagg_mode != "null" and seed_dsa_topk_from_draft_extend)
return FUSE_TOPK and (
    not pd_index_share_seed or should_remap_pd_dsa_seed_to_local_slots()
)
```

The unfused Triton transform runs whenever a PD draft-extend seeds the index and
`should_remap_pd_dsa_seed_to_local_slots()` is False. On main that helper requires
`is_cuda()` **and** `disaggregation_mode == "decode"` and `not enable_hisparse`
and `not dcp_enabled`. So CUDA deployments do reach these kernels, in default
configuration, on the **PD prefill worker's draft-extend** — the function's own
docstring states "PD Prefill worker: [...] Draft extend: fused TopK disabled" —
and on the decode worker too whenever `enable_hisparse` or `dcp_enabled` is set,
or `SGLANG_DSA_FUSE_TOPK=false` / `--dsa-topk-backend torch` is selected.

Severity differs by role, though. On the decode worker `max_seqlen_k` grows by the
accept length every MTP cycle, so nearly every call mints a new key — the
4,723-distinct-values-in-4,822-calls measurement above. On the prefill worker it
takes the request's own sequence length, so churn is one new key per distinct ISL:
unbounded across a varied workload, but far fewer misses than the decode-side
figure. All performance numbers here are decode-worker, ROCm; the CUDA
prefill-worker path is reachable by inspection but I have not measured it.

## Relation to #36714

#36714 widens the PD DSA fused-TopK seed remap to ROCm. The two changes are
**complementary, not additive**: on our setup, gate alone 8.19 ms, this change
alone 8.21 ms, both together 8.32 ms at c=1. They route around the same single
cost by different means — the gate stops these Triton kernels from being invoked
at all (measured: 0 cache misses against stock's 6,494, and 238 → 235 kernels per
decode cycle), while this PR makes them cheap when they are invoked.

Their coverage does not overlap, so neither makes the other redundant:

| configuration | fused TopK on main? | addressed by |
|---|---|---|
| ROCm PD decode worker, default | no | either |
| CUDA PD decode worker, default | yes | neither needed |
| PD **prefill** worker draft-extend, any platform | no | **this PR only** |
| decode worker with `enable_hisparse` or `dcp_enabled` | no | **this PR only** |
| `--dsa-topk-backend torch` / `SGLANG_DSA_FUSE_TOPK=false` | no | **this PR only** |

The fused path is immune to this class of bug by construction — the AOT transforms
are compiled at build time and carry no runtime cache key — which is likely why it
has gone unnoticed: the configurations that reach the Triton transform are the
least exercised.

This PR stands alone and does not depend on #36714.

1. **`do_not_specialize` is still needed.** With the stride as a plain int, Triton still specialises on values divisible by 16 and on 1, so this PR gets to 2 instead of 1. Adding `@triton.jit(do_not_specialize=["page_table_row_stride"])` brings both kernels to 1 in my run.
2. **The tiled decode kernel has the same issue.** `transform_index_page_table_decode_tiled_kernel` was added after this branch was cut and still declares `page_table_row_stride: tl.constexpr` on main. Its other strides come from the top-k and result tensors, which are sized by `TOPK` and don't change between batches.
3. Related: #39266 adds column/row strides to both decode kernels but keeps them tl.constexpr, so the recompile issue above applies there too.
4. **The prefill hunk now overlaps #37093**, which already bounded prefill specialisations, so this needs a rebase.
