# [Spec] Clear stale grammar masks before DFlash and DSpark verification

[Upstream PR](https://github.com/sgl-project/sglang/pull/43518) · state: open · merged: False

## Original PR description

## Motivation

Related to #43514. A `SamplingBatchInfo` can still carry the previous extend/decode-stage `grammar_mask` when entering speculative verification. The shared DFlash/DSpark logits-adjustment helper currently applies that per-request mask to a zero-valued penalty buffer and broadcasts the result across the entire verify block. An all-masked stale row makes every verify logit `-inf`; a stale mask with a different batch size can also cause a shape mismatch.

Verify callers already apply a separate grammar mask for each current tree position. Reusing the previous per-request mask here is incorrect even if the batch sizes happen to match.

This is a draft pending normal Linux-runtime execution of the new tests and reproduction of the issue's mixed grammar/non-grammar, long-prefill overlap workload on an accelerator. The function-level regression does not establish that every possible cause of the reported production failure is fixed.

## Modifications

- Clear `sampling_info.grammar_mask` in `apply_dflash_verify_logits_adjustments` after validating the verify-logit shape, before applying any sampling adjustments.
- Remove the stale-mask-triggered dense fallback. Preserve the existing live-penalizer fallback, precomputed-penalty path, custom-logit-processor call, and logit-bias handling.
- Add a CPU-registered regression test using `CustomTestCase`, real `SamplingBatchInfo`/`GrammarMask` implementations, and CPU tensors. Only the external grammar backend and live penalizer are lightweight test doubles.
- Leave current tree-position grammar application at the existing DFlash and DSpark call sites unchanged.

### Relationship to existing work

- #40458 changes grammar synchronization for mixed decode tails; this patch concerns applying an old mask inside the verify-logits helper.
- #43207 fixes penalty accumulation/application and modifies the same helper, but still applies `sampling_info.grammar_mask`. This patch does not attempt to fix the separate accumulated-penalty field-name or scaling-penalty issues. The stale-mask clear should be preserved if those changes are integrated first.
- #28680 adds DFlash grammar support; its conditional per-request-mask reset does not cover a later verify batch with no grammar requests.

## Accuracy Tests

Added `test/registered/unit/spec/test_dflash_verify_grammar_mask.py` with five test methods covering:

1. Unconstrained verify logits and selected tokens remain unchanged despite a stale mask, including float32/bfloat16 and a changed batch size.
2. The caller's current grammar mask still constrains each verify-tree position independently.
3. Live additive penalties and logit bias still apply, with and without a stale mask.
4. Logit bias works without a live penalizer.
5. The helper's existing precomputed `acc_linear_penalties` path survives the stale mask, including float32-to-bfloat16 conversion.

Local validation on Windows used an isolated, non-shipped runner that compiles the unchanged production function/class definitions from the checkout and executes the new tests with CPU PyTorch. It bypasses package initialization and replaces only the CI test-case scaffolding with `unittest.TestCase`; it is not a normal SGLang suite run. All five test methods expose failures with the original helper and pass with this patch.

Normal test collection was attempted but stops during SGLang package initialization because Windows lacks the Unix `resource` module. No GPU model/server accuracy test has been run.

Please run in the normal Linux CI environment:

```bash
python3 test/registered/unit/spec/test_dflash_verify_grammar_mask.py
```

The issue's mixed structured-output and long-prefill speculative-decoding workload still needs accelerator validation.

## Speed Tests and Profiling

Not benchmarked. The new reset is a host-side attribute assignment, and a stale mask no longer causes allocation/application of the dense penalty buffer. No throughput or latency claim is made.
