# [Refactor] pd: Consolidate sender and receiver implementations

[Upstream PR](https://github.com/sgl-project/sglang/pull/41140) · state: open · merged: False

## Original PR description

## Motivation

Mooncake, NIXL, and Mori each implement their own KV sender / receiver lifecycle (sending, registration, metadata publication, polling, timeouts, cleanup, failure handling). The code is duplicated, and the backends are inconsistent in details such as failure-reason recording, terminal-state latching, and timeout trigger conditions.

NIXL determines transfer completion differently from the other two backends:

- Mooncake / Mori: after all chunks have been written, prefill sends a status message to decode over ZMQ, and decode determines completion by counting prefill ranks.
- NIXL: prefill attaches a notif string to every RDMA WRITE (`{room}_kv_*`, `{room}_aux`, `{room}_state_*`, `{room}_stg_*`, etc.). Decode calls `agent.get_new_notifs()` in `NixlKVReceiver.poll()` and uses `TransferStatus` to count, per PP rank, the arrival of chunks, parts, aux, and state to determine completion. Decode has to maintain a separate set of counting logic, and notifs are only read inside the receiver's `poll()`.

This PR consolidates the sender / receiver lifecycle of the three backends into a common implementation, and switches NIXL completion notification to the same ZMQ mechanism used by Mooncake / Mori, no longer using NIXL notifs.

Refs: [RFC #33861](https://github.com/sgl-project/sglang/issues/33861), [Tracking #34510](https://github.com/sgl-project/sglang/issues/34510).

## Modifications

### 1. NIXL switches to the same ZMQ completion mechanism as Mooncake and removes notifs

**Prefill side**

- For each chunk, the transfer worker waits until all of its handles reach DONE before processing the next chunk. When the last chunk completes, it calls `conclude_transfer(Success)`, which sends a `KV_STATUS` message to all non-dummy decode endpoints of the room. The failure path is the same as upstream: it sends `KV_STATUS=Failed` with the failure reason.
- Staging path: after the handle of each staged write reaches DONE, a ZMQ `CHUNK_READY` is sent, sharing `send_chunk_ready` with Mooncake. Before the next peer reuses the prefill-side packing buffer, the worker likewise waits for that handle to complete.
- NIXL transfer calls no longer pass a notif and no longer call `send_notif`.

**Decode side**

- The listener thread handles four message types: `KV_STATUS`, `CHUNK_READY`, `STAGING_REQ`, and `ABORT_ACK`. `KV_STATUS` is counted per prefill rank via `apply_prefill_status`, and the room is set to `Success` once `required_prefill_response_num` is reached; `CHUNK_READY` is passed to the staging handler via `handle_chunk_ready`, shared with Mooncake.
- The receiver's `poll()` only reads `request_status` and no longer calls `get_new_notifs()`.

**Removed**

- `TransferStatus`, `update_transfer_status()` and its notif parsing functions (`_track_kv_arrival`, `_track_kv_part_arrival`, `_handle_stg_notification`, `_handle_aux_notification`, `_maybe_submit_last_scatter`), and `check_transfer_done()`.
- `transfer_source_rank`, `TransferKVChunk.chunk_id`, the chunk counter in the sender, the `chunk_id` parameter of `add_transfer_request`, the NIXL manager's `exceptions` dict, and the receiver's `started_transfer` / `expects_state`.
- The `notif` parameter of each NIXL send function.

**Unchanged**

- The NIXL agent configuration is kept as in upstream.
- The wire format of NIXL registration and metadata messages is unchanged.

### 2. Sender / receiver lifecycle consolidated into the common implementation

- `send`, `poll`, `poll_pp_consensus`, `clear`, `failure_exception`, `abort` on the sender and `_register_kv_args`, `send_metadata`, `clear`, `failure_exception`, `abort` on the receiver are implemented in `CommonKVSender` / `CommonKVReceiver`. `poll()` and `poll_pp_consensus()` share `_poll_with_status()`, parameterized by `check_status` vs `check_status_pp_consensus`. The receiver's `poll()` uses the upstream common implementation.
- Backend subclasses:
  - `NixlKVSender`, `NixlKVReceiver`, `MooncakeKVReceiver`, and `MoriKVReceiver` are empty subclasses.
  - `MooncakeKVSender` only keeps the trace decorator `mooncake_trace_func` on `send`.
  - `MoriKVSender` only keeps `clear`, which holds the Mori-specific `_abort_ack_lock` when deferred KV release is enabled.
- Backend differences are provided through hooks on the manager:
  - `build_receiver_registration_message()` / `build_receiver_metadata_message()`: per-backend message encoding; the wire format is unchanged. Mooncake's `device_kv_indices` for DSV4 HiSparse is forwarded through `send_metadata(**backend_kwargs)`.
  - `prepare_send_state_indices()`: returns the input unchanged by default; Mori uses it to skip CP-replicated state and to normalize per component.
  - `sender_trace_module`: set to `"mooncake"` by Mooncake, used to create the sender's trace context.
  - `add_transfer_request()`: unified across the three backends to 4 positional arguments plus keyword arguments `wait_event` and `trace_ctx`, with each backend ignoring unused parameters. `wait_event` is used by Mooncake and Mori: both workers call `wait_event.synchronize()` before reading source KV, preserving Mooncake's existing path on `main`. NIXL currently ignores it; NIXL's `wait_event` support is handled by #40861. `trace_ctx` is used only by Mooncake.
- `send_chunk_ready()` / `handle_chunk_ready()` are moved to `CommonKVManager` and shared by Mooncake and NIXL.
- The decode-side `prefill_response_tracker` changes from `defaultdict(set)` to a plain `dict`, with the entry created when the receiver is constructed. The listener thread only reads the entry, so a `Success` arriving after `clear()` does not re-create it.
- `_staging_ctx` is declared on `CommonKVManager` with a default value of `None`.

## Metric Changes

**`transfer_latency_s`: Mooncake and Mori now start timing from the first chunk enqueue.**

- **Affected metrics**: `sglang:kv_transfer_latency_ms` and `sglang:kv_transfer_speed_gb_s`.
- **Mooncake / Mori**: `CommonKVSender` now records `transfer_latency_s` from the request's first chunk enqueue until `poll()` observes `Success`.
  - Previously, neither backend set this field, so the metric fell back to `completion_time - prefill_transfer_queue_entry_time`, covering only the last chunk.
  - With chunked prefill enabled, the new value includes the compute time of subsequent chunks, increasing `kv_transfer_latency_ms` and decreasing `kv_transfer_speed_gb_s`. Dashboards tracking these two metrics will see a one-time step change.
  - For Mori this fixes a bug where `transfer_latency_s` was never populated and always fell back to timing only the last chunk.
- **NIXL**: already reported this field from the first enqueue; its measurement is unchanged.
- Nothing in the repository reads these two metrics.

## Behavior Changes After Unification

### NIXL protocol

- **Source of the completion signal**: decode completion changes from counting RDMA notifications to counting `KV_STATUS=Success` messages sent by prefill ranks, matching Mooncake.
- **When `Success` is sent**: `Success` is sent when all handles of the last chunk have completed. If an earlier staging chunk has been deferred due to insufficient staging space and is still queued:
  - the prefill sender returns `Transferring` while `_staging_outstanding > 0`, so the source KV is not released;
  - the decode staging handler only marks the request complete after all allocations have been scattered.

  This matches how Mooncake handles it. Before this change, NIXL decode relied on notif counting to wait for all chunks to arrive.
- **Staging deferral retry**: when a chunk is deferred, the worker first waits for the writes already posted in the current round to complete, and then retries; previously it retried immediately without waiting for the posted handles. The retry still reprocesses all decode peers of the chunk, the same as before this change and as Mooncake.
- **Failure exception**: the sender's `failure_exception()` raises `KVTransferError`, with the reason text taken from `failure_records`. Before this change, NIXL re-raised the original exception object caught in the worker, so the exception type and text format in scheduler logs change.
- **Abort received only by prefill**: if an abort reaches only the prefill side while the last chunk's writes are in flight, prefill does not send `Success`, and decode does not complete the request. When prefill has already cleared the room, it sends no status, and decode fails the request after `SGLANG_DISAGGREGATION_WAITING_TIMEOUT`. This matches Mooncake. Before this change, NIXL decode counted all notifs once the writes landed and completed the request.

### Sender (all three backends)

- `send()` returns immediately once the sender has reached a terminal state (`Success` / `Failed`) and no longer enqueues. Before this change, Mooncake / Mori relied on the status check inside `add_transfer_request`, and NIXL relied on `_send_failed`, which was only set in `failure_exception()`.
- **Transfer latency metric**: Mooncake and Mori now report sender-measured `transfer_latency_s` starting from the first enqueue, while NIXL is unchanged. See "Metric Changes" above.
- `poll()` returns `Failed` when the room is not in `request_status`. Before this change, Mooncake raised `KeyError` in this case and NIXL returned `WaitingForInput`. `poll()` writes `conclude_state` once it observes a terminal state; before this change NIXL did not latch it.
- `clear()` saves the terminal state before removing manager state; cleanup of staging prefetch records (`prefetched_rooms` / `prefetch_requested`) is extended from NIXL to Mooncake.
- `aux_index` and `state_indices` are only passed with the last chunk. Before this change NIXL passed them with every chunk, but the worker only read them on the last chunk, so behavior is unchanged.
- When no failure reason was recorded locally, the default text of `failure_exception()` is unified as `Failed due to an unknown reason from another rank`, replacing `NIXL KVSender Exception` for NIXL and `KV transfer failed` for Mori.

### Receiver (all three backends)

- When `bootstrap_infos` is `None`, `send_metadata()` uniformly records a failure reason and sets the status to `Failed`. Before this change, NIXL only logged without recording a reason, and Mori returned directly.
- `send_metadata()` raises `NotImplementedError` when given `KVTransferDestination.HOST`. None of the three backends implements host destinations; before this change, passing this argument raised `TypeError` due to a signature mismatch.
- `clear()` writes `conclude_state` before removing manager state: a terminal state keeps its value, and a non-terminal state is recorded as `Failed`.
- `abort()` can be called repeatedly and does not overwrite an already recorded failure reason when already `Failed`. Mori's `abort()` no longer immediately calls `clear()` and removes the failure reason: cleanup is done by `failure_exception()`, which the scheduler calls after the next `poll()` returns `Failed`, so reasons such as `Aborted by AbortReq.` are preserved. Before this change, Mori's failure reason was removed early, and `failure_exception()` could only report `unknown reason from another rank`.
- When no failure reason was recorded locally, the default text of `failure_exception()` is unified, replacing `NIXL KVReceiver Exception` for NIXL and `KV transfer failed` for Mori.
- The NIXL and Mori receivers switch to the upstream common `poll()`: after metadata is published, the waiting timeout is checked in the `WaitingForInput` state. Before this change, NIXL conditioned this on `started_transfer` and read notifs inside `poll()`.
- The `bootstrap_room is None` checks in the Mori receiver are removed. The scheduler already rejects disaggregation requests without a `bootstrap_room` on intake, except for the FAKE backend, which uses `FakeKVReceiver`.

### Mooncake decode `CHUNK_READY` handling

- Switches to the common `handle_chunk_ready()`: malformed messages are dropped after logging a warning; late messages for cleared rooms are dropped; a warning is logged when the staging handler is not initialized. Before this change these cases raised an exception and triggered an `assert`, respectively.

### Wire compatibility

- The registration, metadata, and status message formats of Mooncake and Mori are unchanged, and the registration and metadata message formats of NIXL are unchanged. Unit tests assert the registration and metadata messages of all three backends frame by frame.

- Cross-node RDMA + staging end-to-end validation with NIXL:
  - **Setup**: prefill TP2 on one node and decode TP1 on a second node, with the staging buffer enabled (`SGLANG_DISAGG_STAGING_BUFFER=1`) on Qwen3-8B.
  - **2×8 H200 over InfiniBand with the UCX backend**:
    - Greedy output tokens match the baseline on 18/18 prompts.
    - Full GSM8K accuracy is 0.9386 vs 0.9356 on the baseline.
    - Under abort stress, hung requests are 0, all `/health` endpoints return 200, all queue gauges return to 0, and there are no KV leaks or tracebacks. A subsequent GSM8K-200 run scores 0.96 on both versions.
  - **2×8 B300 over EFA with the LIBFABRIC backend**:
    - Greedy output tokens on a 32k-token prompt match the baseline, and hardware RDMA write counters match the theoretical KV size of 4.832 GB.
  - **Baseline hang fixes across both clusters**:
    - **B300 (EFA / LIBFABRIC)**: the baseline hung in 7 out of 10 launches, whereas this PR completed 100% of runs. On the last chunk, the baseline prefill `transfer_worker` posts `send_kvcache_staged` as a GPU VRAM RDMA write and immediately posts `send_aux` as a CPU DRAM RDMA write before waiting on `_await_handles`. Having an in-flight VRAM write and an in-flight DRAM write concurrently on the same worker causes the NIXL `LIBFABRIC` backend to intermittently stall. This PR waits for the staged KV write to finish and sends `CHUNK_READY` before calling `send_aux`, serializing the two writes and eliminating the hang.
    - **H200 (InfiniBand / UCX)**: in 3 out of 3 runs at 16k input tokens and concurrency 32, the baseline left 1 request permanently stuck in the decode transfer queue, whereas this PR completed all 128/128 requests in every run. When the staging ring is saturated and chunks are deferred and re-enqueued, a non-last chunk can arrive at decode after the last chunk and `aux` notifications; the baseline only called `_maybe_submit_last_scatter` upon receiving the last chunk or `aux` notification, so the late arrival of an earlier chunk never triggered final completion. This PR marks transfer completion via `KV_STATUS=Success` and checks all chunk scatters in `advance_scatter`, eliminating this out-of-order deadlock.

## Speed Tests and Profiling

Setup: a single node with 8× H200, Qwen3-8B, one prefill (TP1) and one decode (TP1) instance, NIXL backend (UCX). The baseline and this PR were run alternately, restarting the servers for every run, with random-token inputs and fixed output lengths.

- TCP transport (`UCX_TLS=tcp,cuda_copy`): across loads with 2048–32768 input tokens and concurrency 1–128 (3 runs per version), no detectable difference in TTFT, ITL, or throughput.
- NVLink transport (UCX `cuda_ipc`): at concurrency 1 with 2048 input and 4 output tokens (15 runs per version), mean TTFT increases by 0.99 ms (69.59 → 70.58 ms, +1.4%) and p99 TTFT by 1.21 ms. The added time is in transfer-completion detection: decode-side `decode_transferred` increases by about 1.1 ms and prefill-side `prefill_transfer_kv_cache` by about 0.6 ms, while prefill forward time is unchanged. At concurrency 16–256, no detectable difference was observed.
  - **Decode-side ~1.1 ms increase**: in the baseline, the decode scheduler thread calls `agent.get_new_notifs()` directly inside `poll()` to read NIC-delivered notifications from memory, which takes about 1 µs. In this PR, prefill sends `KV_STATUS` over ZMQ to the background `decode_listener_thread` blocked in `recv_multipart()`, which wakes both ZMQ I/O threads and the sleeping listener thread and hands off the Python GIL to the decode scheduler thread, taking about 1.0–1.3 ms per message.
  - **Prefill-side ~0.6 ms increase**: `prefill_transfer_kv_cache` measures the time from entering `disagg_prefill_inflight_queue` until the scheduler thread observes `Success` in `sender.poll()`. The synchronous ZMQ send in the transfer worker interacts with GIL scheduling against the prefill main thread, shifting when `sender.poll()` observes `Success` by roughly one scheduler iteration at concurrency 1; at concurrency 16–256 this is hidden by batch execution.

**Cross-node RDMA + staging performance**

Setup matches the cross-node validation above: prefill TP2 on one node, decode TP1 on a second node, default 4096 MB staging ring buffer, Qwen3-8B, alternating runs with full server restarts.

1. **Summary of results**:
   - **No end-to-end regression under normal or non-saturated loads**: on H200 across low-concurrency and medium-context loads (2k–32k input at concurrency 1, and 4k input / 256 output at concurrency 32 and 128), as well as on B300 across all default-config loads, end-to-end TTFT, ITL, and throughput show no statistically significant difference from the baseline.
   - **Prefill stage `prefill_transfer_kv_cache` increases by a fixed 0.2–0.4 ms per request at low concurrency**: on H200 at concurrency 1, `prefill_transfer_kv_cache` increases by 0.24 ms at 2k input (7.31 → 7.54 ms) and by 0.38 ms at 32k input (31.20 → 31.59 ms); on B300 the last-chunk tail similarly increases by about 0.40 ms. Because this is a tiny fraction of total TTFT, end-to-end TTFT is unchanged.
   - **Queuing amplification when the staging ring buffer is fully saturated**: on H200 under a heavy load of 128 requests with 16k input tokens and 16 output tokens at concurrency 32, where the 4096 MB staging ring is continuously full and triggers ~524k chunk deferrals, `prefill_transfer_kv_cache` increases from 1460 ms to 1836 ms (+376 ms, +26%), `decode_transferred` increases from 9349 ms to 9551 ms, and mean TTFT increases from 9668 ms to 9870 ms (+2.1%). On B300, faster compute and EFA transfer keep the default staging buffer from saturating, so both versions perform identically; artificially shrinking the staging pool to fit only a single chunk reproduces the same saturation mechanism, increasing per-request ring wait time by 48% and deferral count by 72%.

2. **Root causes**:
   - **Why `prefill_transfer_kv_cache` increases by 0.2–0.4 ms per request**:
     - On the last chunk of a staged transfer, the baseline posts `send_kvcache_staged` and `send_aux` together and waits for both in a single `_await_handles` call, hiding the small `aux` write behind the KV write, at the cost of the `LIBFABRIC` concurrent-write hang noted above.
     - To match Mooncake's staging flow safely, this PR serializes the last chunk: it first awaits the staged KV write, sends a synchronous ZMQ `CHUNK_READY` (~0.09 ms), then posts `send_aux` and runs a second `_await_handles` for `aux` completion (~0.30 ms on average including posting and waiting), and finally marks `Success`. Multi-chunk requests also pay ~0.10 ms per non-last chunk for synchronous `CHUNK_READY` sends.
   - **Why saturation amplifies queuing delay**:
     - When the staging ring is full, prefill cannot send the next chunk until decode scatters the previous chunk, retires its CUDA event in `advance_scatter` at the start of the decode loop, and sends back a ZMQ `WATERMARK`.
     - In the baseline, the decode main thread reads NIC-delivered RDMA notifications directly inside `poll()` via `agent.get_new_notifs()` and submits the scatter kernel immediately, taking 0.54 ms on average from prefill write completion to scatter submission. In this PR, prefill first observes write completion and sends ZMQ `CHUNK_READY` to decode's blocking `decode_listener_thread`; waking the background thread and acquiring the GIL under load takes 1.97 ms on average. Because the background thread can submit scatters while the decode main thread is inside `run_batch`, subsequent wait time until the next `advance_scatter` check is about 0.6 ms shorter than in the baseline, leaving a net turnaround increase of ~0.8–1.0 ms per staging slot.
     - When the ring is not full, freeing a slot ~0.8 ms later does not delay any waiting chunk. When 32 concurrent 16k-token requests saturate the ring so that arrival rate exceeds slot drain rate, 128 requests (384 chunks) queue behind each other; the ~1–2 ms slower slot turnaround per chunk accumulates across the backlog in `disagg_prefill_inflight_queue`, adding 376 ms to average queue residency while increasing end-to-end mean TTFT by 2.1%.

3. **Comparison with other backends and design trade-off**:
   - Mooncake's staging path uses the exact same control-plane structure—synchronous write completion followed by ZMQ `CHUNK_READY`, background decode listener thread scatter submission, and `KV_STATUS`—and shares the same performance characteristics. Mori does not use a staging buffer and is unaffected.
   - This overhead is the inherent cost of replacing NIXL's private RDMA notification state machine with the shared ZMQ control plane used by Mooncake. Eliminating the ~1 ms background-thread wake-up latency would require re-introducing NIXL-specific notification paths or redesigning the shared staging threading model, which would add substantial complexity and work against the goal of unifying the three backends. Given that the unified implementation fixes both cross-node baseline hang bugs, has no end-to-end regression on normal workloads, and changes end-to-end TTFT by only ~2% under extreme staging saturation, we keep the simple, unified design.
