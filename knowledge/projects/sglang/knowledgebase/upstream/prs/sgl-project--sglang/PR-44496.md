## Motivation

External corpora for ngram speculative decoding (#21425, #22203) are stored as a `SuffixAutomaton` in which every state owns a `std::unordered_map` of transitions plus two sorted child vectors. After `finalize()` the SAM is read-only, but it kept this build-time layout for the lifetime of the server, costing **~525 bytes of host RAM per corpus token**.

At the default `--speculative-ngram-external-corpus-max-tokens 10000000` that is **~5.0 GB per scheduler process**, and every scheduler running `NGRAMWorker` builds its own copy (startup corpora load in `NGRAMWorker.__init__`; HTTP-added corpora are broadcast to every TP rank). TP=8 therefore needs ~40 GB of host RAM for one full-budget corpus. On my 8 GB test machine, loading a default-budget corpus through `NgramCorpus` was OOM-killed on main; with this PR it fits in 542 MB.

Related roadmap: #21052

## Modifications

Only `suffix_automaton.{h,cpp}` change. There is no change to `Ngram`, the FFI surface, or Python.

- `finalize()` now ends with `freeze_()`, which copies the automaton into flat arrays and releases the build-time `states_`:
  - per state (16 B): `link_`, `max_len_`, `occ_count_` (`uint32_t`), `edge_begin_`
  - per edge (16 B): `edge_token_` / `edge_target_`, sorted by token within each state, plus `by_recency_` / `by_freq_`, which hold edge indices in drafting order
- The child orders use the same comparators as before (frequency or recency descending, then token, then state). Separator edges stay in the token-sorted array, where `INT32_MIN` sorts first, so matching is unchanged; they are excluded from the drafting orders exactly as `children_by_*` excluded them.
- `match()` looks transitions up by binary search. The old `else if` that retried the root was unreachable: the suffix-link loop only stops at a state that has the transition, or at the root itself. I folded it into the miss case.
- The build-time `SamState` drops the two child vectors (128 → 80 bytes), which also lowers the peak while a corpus is loading.
- `buildRecency()` and `buildFrequency()` keep their algorithms; only data access changed.
- New `TestNgramCorpusExternalSamDrafts` pins what the SAM drafts. It covers recency vs frequency choice, the token tiebreak on equal frequency, a suffix-link fallback, separators never being drafted, and the full drafted tree compared as sorted paths. It passes on both main and this branch.

## Accuracy Tests

Draft output is unchanged:

- `test/registered/unit/spec/test_ngram_corpus.py`: 40 passed, 12 subtests passed, 5 skipped, identical on main and this branch. The skips are the HTTP-mock tests, which need CUDA libraries.
- I compiled a standalone driver that uses only the public `SuffixAutomaton` API once against main and once against this branch. The `buildRecency` + `buildFrequency` outputs (tokens and mask) are **byte-identical for 210,000 draft trees**:
  - corpora: Tekken-tokenized 1M / 4M / 10M tokens, regex-tokenized 1M / 4M, synthetic Zipf 2M
  - configs `(max_trie_depth, min_bfs_breadth, max_bfs_breadth, draft_token_num)`: `(18,1,8,8)`, `(18,1,8,16)`, `(6,2,4,8)`, `(32,1,10,24)`, `(12,1,1,4)`
  - contexts: exact corpus windows, windows with the last 3 tokens replaced, windows with one token replaced in the last 20, and 1–3 token contexts
- Through the FFI (`Ngram::batchMatch`, including the trie/SAM merge), ids and masks are identical on main and this branch.

## Speed Tests and Profiling

This is a CPU-only change. Setup: 2 vCPU / 8 GB, `-std=c++20 -O3` (the `load_jit` defaults). The corpus is the SGLang repository source tokenized with Mistral's Tekken tokenizer (`tekken_240911`, bundled with `mistral_common`), 26.1M tokens, fed in 4096-token chunks like `external_corpus.py`.

**Production path** (`NgramCorpus.load_external_corpus_named`, JIT build), 4M tokens:

| | main | this PR |
|---|---:|---:|
| Corpus host RSS | 2,009 MB (527 B/token) | 217 MB (57 B/token) |
| Load | 8.00 s | 8.91 s |
| `remove_external_corpus` | 0.82 s | 0.01 s |

**`SuffixAutomaton` only** (standalone driver):

| Tokens | Steady RSS | Peak while loading | Destroy |
|---|---:|---:|---:|
| 1M | 511 MB → 55 MB | 517 MB → 398 MB | 0.20 s → <0.01 s |
| 4M | 2,009 MB → 216 MB | 2,031 MB → 1,567 MB | 0.78 s → 0.01 s |
| 10M (default budget) | 4,994 MB → 541 MB | 5,050 MB → 3,901 MB | 2.05 s → 0.03 s |

The faster destroy matters beyond memory. `Ngram::removeExternalCorpus()` destroys the SAM while holding `Ngram::mutex_`, which `batchMatch()` also takes, so on main removing a full-budget corpus blocks drafting for ~2 s.

**Per-query latency**, 10M tokens, `draft_token_num=8`, `max_trie_depth=18`, µs p50 / p99:

| | main | this PR |
|---|---:|---:|
| `buildRecency` (BFS) | 10.1 / 33.6 | 5.4 / 13.6 |
| `buildFrequency` (PROB) | 5.9 / 20.1 | 5.5 / 19.8 |

PROB is unchanged within run-to-run noise on this machine. BFS was consistently about 2x faster across repeated interleaved runs.

**Build timing** at 10M tokens (append / finalize / destroy): main 13.9 / 8.9 / 2.1 s, this PR 13.2 / 10.3 / 0.03 s. `finalize()` is slower because it now frees the build-time maps, which main frees on destruction instead. End to end it is slightly faster.

Results on a regex-tokenized corpus and on a synthetic Zipf corpus were consistent: 443–515 B/token on main vs 53–55 B/token with this PR.
