# [Perf] [XPU] flux2: Fuse bit-exact LayerNorm and gated residual norm

[Upstream PR](https://github.com/sgl-project/sglang/pull/41942) · state: open · merged: False

## Original PR description

## Motivation

FLUX.2 has two eager fast paths that only exist for CUDA:

- `LN(x) * (1 + scale) + shift` → `fused_layernorm_modulate_raw`, a Triton
  kernel that reproduces **CUDA aten's** `vectorized_layer_norm_kernel` bit for
  bit, using inline PTX (`_rcp4`, `shfl.down` fold order, `div.rn` + `MUFU.RSQ`).
- gated residual + LN + modulate → `flux2_gated_resnorm_raw`, a Blackwell-only
  PTX JIT kernel, which also gates the cross-block residual deferral.

Neither can run on XPU: the PTX does not compile, and — more fundamentally —
the eager reference on XPU is torch-xpu-ops' own LayerNorm, whose reduction
order differs from CUDA aten's. FLUX.2's `BitExactFusionGate` compares against
the live eager chain with `torch.equal` and disables any kernel that does not
match, so a "close enough" kernel is not an option. On XPU both chains
therefore ran as 3-5 eager kernels per site.

## Modifications

New `kernels/ops/diffusion/norm/layernorm_modulate_xpu_triton.py` replicating
torch-xpu-ops `VectorizedLayerNormKernelFunctor` for bf16 rows with `N/4 > 1024`
(`src/ATen/native/xpu/sycl/LayerNormKernels.cpp`, `compute_stats`):

- work-group of 1024 (32 sub-groups x SIMD 32), vec_size 4;
- work-item `t` Welford-pushes vectors `t, t + 1024, ...`, each scalar as
  `mean' = fma(delta, recip(count), mean)`, `m2' = fma(delta, val - mean', m2)`;
- lane fold with `shift_group_left` offsets 16..1 (self = lower lane), then the
  sub-group fold with the same pairing;
- `var = div_rn(m2, N)`, `rstd = rsqrt(var + eps)`,
  `y = bf16(rstd * (x - mean))`, then the modulate chain rounding to bf16 after
  each op.

Two entry points share one kernel (a `GATED` constexpr selects whether the
residual add runs first), because the whole replicated reduction — Welford
accumulation, two-level fold, reciprocal table — is common to both.

**The reciprocal is the subtle part.** torch-xpu uses `sycl::native::recip` on
the running count, which differs from correctly-rounded `1/i` for 992 of the
first 8191 integers. Triton's `fast_dividef(1, x)` reproduces it in some
layouts but not others (at `num_warps=8` the statistics dropped to 96-98%
exact), so the kernel reads reciprocals from a small per-device table built once
by a kernel in the one configuration that was verified against a SYCL dump of
`native::recip`. Results are then independent of `num_warps`.

Wiring in `flux_2.py`:

- `_flux2_norm_modulate` dispatches to the XPU kernel under the existing
  `_FLUX2_LN_MOD` gate;
- `_flux2_gated_resnorm` gets an XPU path verified once per signature by a new
  `_FLUX2_XPU_GATED_RESNORM` gate;
- `_defer_gated_residual` also defers on XPU, so the block-end residual add
  fuses into the next block's norm.

Guards: bf16, contiguous 8-byte-aligned rows, `N % 4 == 0`, `1024 < N/4 < 8192`,
per-channel scale/shift/gate rows. Anything else keeps the eager path.

## Accuracy Tests

New `test/registered/kernels/ops/diffusion/test_flux2_xpu_norm_fusions.py`
(registered `register_xpu_ci(est_time=30, suite="stage-b-test-1-gpu-xpu")`),
4 cases at this point in the stack: bit-exactness of each kernel, the FLUX.2
dispatch actually taking the XPU path and the gate staying enabled, and
unsupported inputs (fp16, batch > 1, narrow rows) staying eager. All pass on
Arc Pro B70. (Later PRs in the stack add 2 more cases to the same file.)

Standalone sweep before wiring — **0 mismatching elements** vs the eager chain:

| rows | mismatches (LN+mod / gated out / residual) |
|---|---|
| 4608 | 0 / 0 / 0 |
| 4096 | 0 / 0 / 0 |
| 512 | 0 / 0 / 0 |

for 4 seeds x value scales {0.05, 1, 8, 30} x `num_warps` {4, 8, 16}
(28.3M elements per case at 4608 rows).

End to end, FLUX.2-dev 1024x1024: no
"not bit-exact ... falling back to eager" warning. Output images vs the
previous commit are 43.0 / 46.5 dB PSNR — the same level as two runs of
*identical* code (44.2 dB), because at TP>1 oneCCL's all-reduce reduction order
already makes runs non-deterministic on this stack. Image hashes are therefore
not a usable bit-exactness check here; the `torch.equal` gate and the unit tests
are.

## Speed Tests and Profiling

Kernel micro-benchmark, one card, bf16, `num_warps=4`:

| kernel | rows | eager | fused | speedup |
|---|---|---|---|---|
| LN + modulate | 4608 | 0.707 ms | 0.231 ms | 3.06x |
| LN + modulate | 4096 | 0.628 ms | 0.209 ms | 3.00x |
| LN + modulate | 512 | 0.046 ms | 0.030 ms | 1.52x |
| gated residual + LN + modulate | 4608 | 1.246 ms | 0.454 ms | 2.75x |
| gated residual + LN + modulate | 4096 | 1.129 ms | 0.408 ms | 2.77x |
| gated residual + LN + modulate | 512 | 0.087 ms | 0.037 ms | 2.37x |

At 4608 rows the memory-traffic floor is ~0.21 ms, so LN+modulate is at the
bandwidth limit.

End to end (FLUX.2-dev, 1024x1024, 8 steps, bf16, eager, warm, TP4 on 4x
Arc Pro B70), 2 runs per side:

| | denoise (8 steps) | per DiT forward |
|---|---|---|
| parent commit | 6.569 / 6.572 s | 821.3 ms |
| this commit | 6.227 / 6.234 s | **778.8 ms (-5.2%)** |

torch.profiler: `_xpu_ln_modulate_kernel` runs 91 times per forward for 34.6 ms,
replacing ~117 ms of eager LayerNorm + elementwise work (norm 29.7 → 7.1 ms,
elementwise 87.8 → 1.8 ms); device-busy time per profiled forward 919.5 → 901.7 ms.

Under `torch.compile` the kernels step aside (`torch.compiler.is_compiling()`)
and Inductor fuses the same chains, as before.
