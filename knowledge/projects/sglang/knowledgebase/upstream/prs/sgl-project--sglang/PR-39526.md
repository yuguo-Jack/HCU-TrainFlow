# [Fix] mamba: Keep extend-row checkpoint tracking through mixed chunk prefill

[Upstream PR](https://github.com/sgl-project/sglang/pull/39526) · state: open · merged: False

## Original PR description

Fixes #39342.

## Motivation

With `--enable-mixed-chunk` and the mamba radix cache (`extra_buffer`, the
default for hybrid GDN models), a prefill that lands while other requests are
decoding produces a corrupt cache entry:

1. `prepare_for_extend` (`_mamba_radix_cache_v2_req_prepare_for_extend`)
   claims the request's next ping-pong slot and stamps
   `req.kv.mamba_last_track_seqlen` for every extend row whose chunk reaches
   the checkpoint grid, before the scheduler decides whether to mix.
2. `mix_with_running` -> `merge_batch` set `mamba_track_indices / _mask /
   _seqlens` to `None`.
3. The linear-attention backends gate the extend-side checkpoint copy on
   `forward_batch.mamba_track_mask`, so the MIXED forward never wrote the
   claimed slot.
4. `cache_unfinished_req` / `cache_finished_req` (and the unified cache's
   `MambaComponent.prepare_for_caching_req`) still donated that slot at the
   stamped depth, and every later request sharing the prefix restored
   whatever the slot held before (a fresh slot is all zeros).

## Modifications

- `ScheduleBatch.mix_with_running` now carries the extend rows' track
  tensors across the merge (`_mamba_track_for_mixed`). The running decode
  tails are appended as untracked rows: `mask=False`, `seqlen=-1` (the same
  sentinel an untracked extend row already uses), and their own valid slot id
  (`prepare_for_decode`'s `mamba_track_indices`, or the slot at
  `mamba_next_track_idx` rebuilt from the reqs when spec decode left it unset)
  because index translation and the prefill-graph track buffers read every
  row.
- `set_mamba_track_indices_from_reqs` is split into a pure
  `mamba_track_indices_from_reqs` (used by the fallback above) plus the
  existing setter; the host tensor is pinned only where pinning is available,
  like the rest of `prepare_for_extend`.
- `merge_batch` is unchanged: the post-forward running-batch merge must keep
  dropping tracking, `prepare_for_decode` rebuilds it.
- Production change: `python/sglang/srt/managers/schedule_batch.py` only,
  +70 / -11 lines (first commit). Second commit (droppable):
  `test/manual/mixed_chunk_mamba/` with the log-only instrumentation patch,
  lifecycle probe, comparator (with CPU checks), shared-prefix harness and a
  launcher that runs each server in its own session and tears down only that
  process group, used for the GPU A/B below.

Why the decode tails are masked off rather than checkpointed: in a MIXED
batch every row runs through the extend kernels, and the extend-side snapshot
(conv window gathered from the kernel input, SSM state read off the chunk grid
or the final state) has no valid position for a one-token tail. Decode rows
never claimed a checkpoint on a mixed step before this change either
(`process_batch_result_prefill` does not run the decode-side boundary
update), so their behavior is unchanged.

Prior work: #24613 by @cyyc0310 (with @flyerming) concatenated the tracking
tensors inside `merge_batch` with the same mask/seqlen padding; #23075 by
@flyerming passed the extend side's tensors through `merge_batch` and sliced
the backend metadata to the prefill rows. Both were closed for inactivity
against a much older tree. This change keeps their padding idea but scopes it
to `mix_with_running`, the only merge whose result is forwarded with the
extend side's prepared tensors, and leaves the backend untouched: the
metadata helpers already mask before indexing, and the FlashInfer checkpoint
plan, the prefill CUDA-graph track slots, DP padding and the Qwen4-Exp PLE
side states treat the padded rows like an untracked extend row. #36065
(@Destination2020) stays correct: its split path falls back to the unified
extend path whenever `has_mamba_track_mask` is set.

## Tests

`test/registered/unit/managers/test_schedule_batch_mixed_mamba_track.py`
(`base-a-test-cpu`) drives the real lifecycle on CPU with a tiny real
`HybridReqToTokenPool` / `MambaRadixCache` and the GDN backend metadata: real
`prepare_for_extend`, `prepare_for_decode`, `mix_with_running`,
`_forward_metadata`, `_track_mamba_state_extend`, `cache_unfinished_req`,
`release_kv_cache` and `init_next_round_input`; only the GDN kernel is replaced
by distinguishable per-chunk / per-slot values.

- `test_mixed_forward_checkpoints_extend_rows_for_later_prefix_hits`
  (regression): chunked prefill, a prefill finishing on its first token and a
  too-short prefill mixed with a running decode; later requests over the same
  prefixes must restore the states this forward produced. Fails on the base
  SHA with the stale sentinel restored.
- `test_decode_tail_at_a_track_boundary_is_not_a_writer`: a running row on the
  track grid carries a True decode-boundary mask into the mix and must be
  masked off; its slots stay untouched.
- `test_running_batch_without_track_indices_gets_its_slots_from_reqs`: the
  spec-decode shape (indices prepared inside the forward) still yields a valid
  slot per decode row.
- `test_lazy_strategy_mixes_with_a_preallocated_boundary_slot`:
  `extra_buffer_lazy` with the boundary slot preallocated by
  `prepare_for_decode` rides the mix masked off; the extend row checkpoints
  into its single slot and donates it. (`extra_buffer_lazy` has CPU coverage
  only.)
- `test_mix_without_extra_buffer_carries_no_tracking`,
  `test_post_forward_filter_and_decode_prepare_rebuild_tracking`: negative
  and bookkeeping contracts.

Existing CPU suites touching the same code pass. `pre-commit` clean.

## Accuracy Tests

GPU A/B on 1x L40 (Triton GDN kernels + Triton attention, `--sampling-backend
pytorch`, `--mamba-ssm-dtype float32`, `--chunked-prefill-size 2048`, TP 1),
`Qwen/Qwen3.5-4B` at revision `851bf6e8`, base `242d8a70c` vs the production
commit as GPU-tested (`2b26b465`; the first commit of this PR has the same
tree `019ba85c`, only its message changed), identical prompts / seed / model /
reset protocol, default tree (`UnifiedRadixCache` + MAMBA component), eager
and `--cuda-graph-backend-prefill breakable`. Scripts and flags:
`test/manual/mixed_chunk_mamba/`. Raw logs, results, environment and the
reprocessed comparisons:
https://github.com/200lz/sglang/tree/evidence-39342 (archive sha256
`20c76a0dec461e77236096ed745a9ba84252a4383addc49e68fe4c3a81168917`).

The per-slot "fingerprint" below is five scalars of the first mamba layer's
state for one slot (SSM sum, sum of squares, abs-max; conv sum, sum of
squares), read after the forward's result sync at donation and again at
restore. Matching fingerprints are strong evidence of the same computation,
not a proof of tensor equality across all layers.

Deterministic lifecycle (8 streaming decoders, then a 4819-token
shared-prefix prefill P split into 3 mixed chunks, then R = same prefix +
other question and P2 = identical to P; reference = same requests alone with
the chunk size reduced by 8 so the checkpoint depths 1984 / 4024 / 4784
coincide; comparator status `complete` for every A and B pair):

| build (eager and graph identical) | P's chunks tracked in the mixed forwards | donated slot fingerprint at 1984 / 4024 / 4784 | R / P2 restore | answers |
|---|---|---|---|---|
| base | no (`tracked=None`, mixed `mask=None`) | `(0, 0, 0, 0, 0)` at all three depths; reference non-zero; verdict `mismatch` | zero-fingerprint slot restored at 4784 | P2 answers "662" instead of "14" |
| fix | yes (`bs=9 one_token_rows=8 tracked=[(40, 35, 2040)]`, ...) | equal to the reference fingerprints at the same depths (rel 1e-6); verdict `equal` | same depth, same fingerprint as the reference restore | all correct |

Shared-prefix harness (200 prompts, 380-fact prefix, c1 reference + c1 warm
repeat + 3x c32 cold/warm, `breakable` prefill graphs):

| arm | base: c32 mismatches vs c1 reference (6 passes) | fix |
|---|---|---|
| mixed ON, radix ON | 17, 43, 18, 44, 18, 46 (pairwise 14-47) | 0, 0, 0, 0, 0, 0 (pairwise 0) |
| mixed OFF, radix ON | 0 x6 | 0 x6 |
| mixed ON, radix OFF | 0 x6 | 0 x6 |

The c1 warm repeats and arms B/C give a 0/200 noise floor on this workload.

Not covered on GPU: FlashInfer GDN prefill (SM90+), `trtllm_mha`,
`tc_piecewise` (rejected with mixed chunk since #36288), TP > 1, spec decode,
`extra_buffer_lazy`, the reporter's private model and eval.

## Speed Tests and Profiling

No obvious p50 regression observed in this instrumented workload: c32 p50 on
arm A was 0.36-0.53 s on base and 0.36-0.55 s on the fix, c1 0.11 s on both,
with the log-only probe patch applied (it syncs the GPU per donation) and
eight output tokens per request, so this is not a throughput benchmark. Per
mixed batch the fix adds three tensor concatenations (slot ids, mask,
seqlens) and two small fills on the scheduler thread, plus one gather when
the running batch has no prepared indices; no kernel changes.

**Protocol**

The production-only change was ported to the installed `schedule_batch.py`. Diagnostic base/fix arms use matching synchronized observation hooks adapted to this image's `UnifiedRadixCache`; the older standalone MambaRadixCache instrumentation cannot be applied verbatim.

The workload follows this PR's P/R/P2 lifecycle: eight 600-token streaming decoders overlap a deterministic shared-prefix prefill P; R asks another question over the prefix; P2 repeats P. Mixed prefill uses chunk size 2048, and each arm's isolated reference uses 2040 without background decoders. Actual observed checkpoint depths are 1984, 4024 and 4784. Each base/fix arm is compared against its own isolated reference.

Relevant common settings are `--enable-mixed-chunk --chunked-prefill-size 2048 --disable-cuda-graph --cuda-graph-backend-prefill disabled --mamba-radix-cache-strategy extra_buffer`. GDN prefill is explicitly `triton` or `flashinfer`. The additional matrix configs use context 8192, max-running-requests 16, FP32 SSM, Triton decode/verify; the initial FP8/Triton/no-spec pair instead inherits context 131072 and default SSM dtype. Matched base/fix pairs preserve these settings. MTP uses NEXTN, steps 3, topk 1, draft tokens 4.

The comparator requires claim → actual scheduler mixed batch → matching backend forward → successful donation → later restoration of that donated checkpoint. This eager runner rewrites scheduler MIXED to backend EXTEND; the first corresponding forward must match ordered request-pool IDs, batch size and the exact positive decode-tail count. An arbitrary EXTEND cannot satisfy exposure.

At each checkpoint it compares up to 32 ordered elements for each recurrent/convolution state across all 48 recurrent layers (3072 sampled values), plus five first-layer moments. Missing exposure or restore provenance is incomplete, never a pass.

The poisoned-state calibration zeros a selected checkpoint before donation and verifies both R and P2 restore it. Both restores contain the zeroed sampled state, whereas the unpoisoned reference is nonzero. Instrumented latency is not used as performance evidence.

Separate performance follow-up to the checkpoint-correctness validation above. Both arms contain the tracking fix; the only configuration difference is `--enable-mixed-chunk`. This measures mixed-batching policy, not the overhead of the fix.

One benchmarking caveat: in the pinned v0.5.21 API, OpenAI `logprobs:0` still enables logprob handling, and the scheduler suppresses mixed batching when either batch requests logprobs. Our initial diagnostic therefore produced zero MIXED batches. Omitting logprobs and using `return_token_ids:true` yielded 19 actual MIXED forwards in a separate 12-request diagnostic.

Setup: one GB10, Qwen3.8-27B-FP8 revision `017b9c7af6b5689d5dd426a76e0bc077eb5ca20a`, SGLang `e00930c5489053f26d86b179cee0d087f846acbb`, with the production tracking change from PR head `a7ebbdc655671e515087bb46217cf35fe4adf1bf`. Eager execution, context 131072, chunk 2048, Triton GDN prefill, extra-buffer cache strategy, no speculation.

Uninstrumented arms replay identical timestamped synthetic request traces, with separate warmup/cache resets, concurrency capped at 8, prompt lengths 128–32768, output caps 32–256 and natural EOS.

| Workload | Mixed off/on offered p95 TTFT, seconds | Off/on actual output tok/s |
|---|---:|---:|
| Representative 0.2 req/s, median of three 60-request runs | 9.150263 / 9.660177 | 16.800472 / 16.719949 |
| Fresh reverse-order representative run | 9.030202 / 9.505290 | 16.809021 / 16.725316 |
| Held-out seed, 0.25 req/s, one run | 39.003933 / 36.858263 | 16.957020 / 17.460291 |

Offered TTFT is measured from scheduled arrival to first output token. Primary representative p95 increased 5.57%, with a 0.48% throughput reduction; the fresh reversed-order pair showed the same direction. The held-out pair improved p95 by 5.50%, illustrating load-dependent tradeoffs. All 840 measured requests completed validly with zero errors.

A separate instrumented diagnostic found that all 45 token gaps over 300 ms temporally contained a MIXED launch carrying that request as a decode tail. This is correlation, not an isolated causal contribution. Forward-stream event intervals include enqueue gaps and are not GPU-busy-time measurements.

Natural-EOS outputs differ in length for some matched requests, so throughput is not identical generated work. Single-run tail quantiles, synthetic prompts and one machine do not establish general performance or quality. The checkpoint fix remains warranted; these results support validating actual MIXED exposure and workload-specific latency tradeoffs separately.
