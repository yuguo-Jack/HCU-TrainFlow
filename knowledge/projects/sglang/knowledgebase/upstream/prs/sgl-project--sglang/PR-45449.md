# [Feat] rust-server: Render, tokenize and serve chat through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/45449) · state: closed · merged: True

## Original PR description

rust-server renders, tokenizes and serves OpenAI chat through `sglang-processor`, and keeps no tokenizer, template or model-specific chat code of its own. This folds in #46195 (the processor APIs it uses). Processor behavior fixes follow in #45659, stacked on this PR.

Rebased onto main after #46243: DeepSeek-V4/V4.1 render and encode through deepseek-recipe exactly as main does, and this PR changes no DeepSeek-V4/V4.1 rendering code.

## Modifications

**sglang-processor**
- `TextTokenizer::encode_chat` implements Python's chat encode: the template without the tokenizer's specials, then the continuation minus one leading BOS (the configured `bos_token`).
- `ChatModel::for_formatter` derives the chat layer's model rules from the served formatter. A template without a detected reasoning config falls back to the reasoning parser's `reasoning_default`, as Python does.
- `TemplateError::NeedsRenderFallback` marks a request `render_request` declines: a valid one a parity renderer cannot reproduce, or any request to a formatter without an SGLang request path.
- `ChatFormatter::render_template` and `TemplateArgs` are the template path, moved here from rust-server. It reuses the processor's `TemplateArgsRequest`.
- Re-exports `dynamo_parsers` and `minijinja`.
- Template selection follows Python's order: a legacy template is guessed from the model path before the checkpoint's own template is read (`load_chat_template`), and DeepSeek-V3.2's or a display-name native encoder is used only when the checkpoint ships no template (`resolve_chat_encoding_spec`). DeepSeek-V4/V4.1 selection is main's.

**rust-server**
- Delete `template_builtins.rs`, `template_legacy.rs`, `template_loader.rs` and the server's own tokenizer. Drop the `dynamo-*`, `minijinja` and `hf-hub` dependencies.
- **Render.** Parity formatters render the raw body. The rest render through the template, and so do the requests a parity formatter declines; on the lowered path those are served there too, not by the typed handler. The `continue_final_message` text stays apart from the prompt and is encoded on its own.
- **Tokenize.** Chat and `/tokenize` encode in the tokenizer pool through `TextTokenizer`, and the detok shards decode with the same tokenizer. DeepSeek-V4/V4.1 prompt ids come from `ChatFormatter::encode_request` (deepseek-recipe's tokenizer), as sgl-router takes them.
- **Serve chat** through the processor's OpenAI layer (`openai/lowered.rs`):
  - `lower_chat` turns the body into a `/generate` body. The native route decodes it, the core serves it, and the responder builds the reply from the frames.
  - Requests it does not reproduce keep the typed handler: `required` or named `tool_choice`, logprobs, media, and legacy conversation templates.
  - `n` choices are a batch of the prompt, bounded before it is copied. A failure before the first frame answers unary, in Python's error shape, and a failed choice answers at once, cancelling its siblings.
  - Lowered chat serves main's typed `GenerateRequest` (#46031) and tracks each call with its own `RequestState`, as the native batch does (#46205).
- `--default-chat-template-kwargs` applies beneath the request's own kwargs. A model given as an HF repo id loads its tokenizer from the local cache.

## Behavior changes

- Serving through the OpenAI layer brings `separate_reasoning`, `stream_reasoning`, `reasoning_tokens` in `usage`, and the request shapes Python accepts in line with Python.
- On the lowered path, Kimi K3 keeps its special tokens and leaves its generation stub out of `prompt_tokens`. The typed handler keeps main's behavior here; #45659 aligns it.

## Tests

- `cargo test --workspace` and `sglang-processor --all-features`, every processor feature subset, clippy with `-D warnings`, and fmt all pass. `sgl-router` passes 1463/1463 tests with model snapshots cached, the same as main. Parity fixtures check token ids against cached HF tokenizers.
- The template-path move is a no-op: before and after give identical `/tokenize` ids on 127 fixture requests and 17 template cases, through both Qwen3.8's renderer and a generic Jinja template.
- After the rebase, at the top of the stack (#45659), Qwen3-0.6B (`--reasoning-parser qwen3`) on 1x B300 each, Rust vs Python: `/tokenize` ids match on 7 request shapes (tools, thinking off, `reasoning_effort: "none"`, continuation, tool history), and sgl-eval 0.1.3 gsm8k (200 examples, `enable_thinking=false`, temp 0.7, top_p 0.8) is 60.5% on both.
- Before the rebase (DeepSeek through the processor's own port, since replaced by deepseek-recipe), on 4x B300, Rust vs Python on the same flags. sgl-eval 0.1.3, gsm8k, 200 examples:

| Model | Sampling | Rust | Python |
|---|---|---|---|
| Qwen3.8-27B | temp 1.0, top_p 0.95, `enable_thinking=true`, max_tokens 32768 | 98.0% | 97.5% |
| DeepSeek-V4.1-Flash | model preset | 96.5% | 96.5% |

- Greedy replay of the `openai_parity` fixtures against Python: Qwen3.8 11/13 and DeepSeek-V4.1 29/42 (main's rust-server: 0/42). In Qwen's `chat` case the prompt tokens are identical and the greedy output drifts mid-reasoning; `tools_required` stays on the typed handler. #45659 fixes most of the remaining differences. The rest are listed under Known gaps.

Launch commands (cookbook divergences: 4x B300, no DSpark, `--language-model-only`, `--dsv4-attn-backend flashmla`). Drop `SGLANG_RUST_SERVER=1` for Python:

```bash
SGLANG_RUST_SERVER=1 python -m sglang.launch_server \
  --model-path deepseek-ai/DeepSeek-V4.1-Flash --revision dba1be0a40aa45a94ad051997016db3960a90277 \
  --trust-remote-code --tp 4 --ep-size 4 --max-running-requests 256 \
  --language-model-only --dsv4-attn-backend flashmla \
  --reasoning-parser deepseek-v41 --tool-call-parser deepseekv41

SGLANG_RUST_SERVER=1 python -m sglang.launch_server \
  --model-path Qwen/Qwen3.8-27B --revision 1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0 \
  --trust-remote-code --kv-cache-dtype fp8_e4m3 --mem-fraction-static 0.85 --chunked-prefill-size 2048 \
  --reasoning-parser qwen3 --tool-call-parser qwen3_coder
```

## Known gaps

- `/tokenize` keeps the typed request path, so it rejects some request shapes that chat accepts, and on a generic Jinja template, tools render as Dynamo reshapes them rather than as Python's `Tool.model_dump()`. #45659 fixes both.
- The DeepSeek-V4.1 numbers above predate the move to deepseek-recipe (#46243) and have not been re-measured on this branch.
- Already on main: streamed completions with logprobs garble multi-byte text for DeepSeek-V4.1, and a too-long chat error is nested under `error`.
- GLM-5.3-Flash does not launch on the Rust server yet, because there is no Rust MM pipeline for `glm5_next`.
