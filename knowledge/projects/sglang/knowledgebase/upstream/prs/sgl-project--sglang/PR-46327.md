# [Perf] [AMD] unquant: Pad gfx115x linear and lm_head weight rows to avoid cache aliasing

[Upstream PR](https://github.com/sgl-project/sglang/pull/46327) · state: closed · merged: True

## Original PR description

## Motivation

Decode on gfx1151 (Strix Halo, LPDDR5X-8000, 256-bit bus, 256 GB/s theoretical) is memory-bound: over 98% of decode GPU time is in GEMMs. On HIP without AITER, unquantized linears run through `F.linear` (hipBLASLt). At M=1, hipBLASLt reaches only 132-193 GB/s on Llama-3.1-8B's shapes, 51-75% of the theoretical peak.

## Root cause

On gfx1151 (and on gfx1100, see Results), a weight whose row stride is a multiple of 2 KiB puts the rows a skinny GEMM reads together onto the same L2/MALL channel. Most dense-model K dims qualify (bf16 K = 2048, 3072, 4096, 14336, ...).

If each row is offset by one 128 B cache line, they spread out again. The logical shape and values stay the same; only the stride changes.

M=1 bf16, cold cache, best of 3, GB/s, plain row stride vs padded row stride, hipBLASLt default solutions, no TunableOp:

| Llama-3.1-8B shape (K -> N) | plain | padded | change |
|---|---|---|---|
| QKV 4096 -> 6144 | 151.5 | 214.4 | +42% |
| O 4096 -> 4096 | 131.6 | 213.3 | +62% |
| gate/up 4096 -> 28672 | 182.6 | 223.0 | +22% |
| down 14336 -> 4096 | 159.4 | 225.5 | +41% |
| lm_head 4096 -> 128256 | 192.5 | 226.5 | +18% |
| GEMM time per token | 89.0 ms | 67.6 ms | -24% |

All shapes reach 83-89% of peak after padding, and the output matches the unpadded output (relative error against fp32 is unchanged, 1.9-3.1e-3).

## Fix

When a qualifying unquantized weight finishes loading on gfx115x (RDNA3.5), give its rows a padded stride. This happens once per weight, at load time.

- **Rule:** `(K * element_size) % 2048 == 0`. If it holds, the row stride grows by 128 B; it's the same rule as vLLM's `cache_aliasing_pad_elems`. Only bf16 and fp16 weights are padded, since those are what was measured. fp32 linears, such as the router gates in kimi_k3, longcat_flash and hunyuan_v3/v4, are left alone; vLLM pads them too, but that was never measured here. `K` is the weight tensor's own dim 1, so a tensor-parallel row shard is judged by its own K, not the full checkpoint K.
- **Linear weights:** `UnquantizedLinearMethod.process_weights_after_loading` does the padding.
- **lm_head:** `DefaultModelLoader.postprocess_weights` calls `finalize_gfx115_weight_padding(model)`, which pads every unquantized LM head:
  - `ParallelLMHead`, untied.
  - A tied head that is the input embedding module itself (`lm_head = model.embed_tokens`). 54 model files tie this way, and the embedding's quant method cannot tell it apart from an untied input embedding, so the model's module names decide.
  - A tied head that shares a `Parameter` (`ParallelLMHead.tie_weights`). This is padded once.

  An untied input embedding is never padded: it reads one row per token, so padding gains nothing.
- **Gate:** `is_gfx115_supported()` is new in `srt/utils/common.py`: true on RDNA3.5 (`gcnArchName` starting with `gfx115`), with a `torch.cuda.is_available()` check. It's the gfx115x form of #47695's `is_gfx1151_supported()`.
- **Opt-out:** setting `SGLANG_DISABLE_GFX115_WEIGHT_PADDING=1` turns the padding off. It's on by default on gfx115x.
- **Log:** the first load logs one INFO line listing the padded and skipped shapes. Later weight updates (for example, each RL weight sync) log the same line at DEBUG. That includes a speculative-decoding draft model, which is the second model loaded in the process, so its line is at DEBUG too. Example:
  `gfx115x weight padding: padded {(6144, 4096): 32, (4096, 4096): 32, (28672, 4096): 32, (4096, 14336): 32, (128256, 4096): 1}; skipped {}`
- **Memory:** the padded weights grow by 128 B per row, about 1.5% for K = 4096. Llama-3.1-8B: +0.24 GB on 16 GB. While one weight is being padded, `F.pad` briefly holds both copies, so peak extra memory during load is at most one LM head (about 1 GB for Llama-3.1-8B). That happens before KV-cache sizing, so it doesn't reduce the cache.

## Results

## What's not affected

- **Prefill:** long-prompt GEMMs are compute-bound. TTFT and 4-way prefill throughput are within noise on every model (-3% to +4%).
- **MoE experts:** fused-MoE expert weights are 3D and go through `UnquantizedFusedMoEMethod`, so they are not padded; vLLM doesn't pad them either. On DeepSeek-V2-Lite, the attention projections, shared experts and dense layer are padded, and `kv_b_proj` (K = 512) is skipped.
- **Quantized layers:** only `UnquantizedLinearMethod` and unquantized LM heads are touched.
- **fp32 weights**, for example MoE router gates, are left alone; only bf16/fp16 was measured.
- **Outside gfx115x:** a no-op. `_is_gfx115` is computed once at import and is false on CUDA, CDNA, RDNA3 and CPU.
- **Kernels reading raw weight pointers:** the CUDA-only bf16 GEMV/CuTe paths check `weight.is_contiguous()`. `apply_into` (`torch.mm(out=)`), `F.embedding` and the lm_head `torch.matmul` all honor strides. Model code that fuses weights after loading (`torch.cat(...).contiguous()` in qwen3_5, minimax_m3) simply produces a contiguous weight.

## Related work

- vLLM #55090 (`maybe_pad_weight_avoid_cache_aliasing`, `vllm/model_executor/layers/linear.py:230`): the same rule, measured on gfx1151 (its gate covers all of gfx11). It reports only -3% TPOT because vLLM decodes through `wvSplitK`, which is less sensitive to the aliasing. sglang's hipBLASLt path is hit much harder.
- ROCm/hip-ep #1274: same cause (int4, gfx1151).
- sglang's own XPU MoE padding (`xpu_moe_ld_padding_elems`): the same idea for Xe L3 set aliasing.

## Testing

`test/registered/unit/layers/quantization/test_unquant_gfx115_weight_padding.py`:

- **CPU, registered in `base-a-test-cpu`:**
  - The pad rule counts row bytes, not elements.
  - The pad keeps shape and values and gives the same `F.linear` output, with bias.
  - The gate leaves the weight untouched off gfx115x, when opted out, when already padded, when non-contiguous, and for fp32.
  - An untied input embedding is not padded.
  - Tied heads, both forms, are padded once and still embed correctly, including across a second postprocess pass (a reload).
  - A quantized head is not padded.
  - A reload writes into the padded storage, keeping the stride and the pointer. This holds for `ColumnParallelLinear`, and at TP=4 through the checkpoint loaders models actually use: `QKVParallelLinear` and `MergedColumnParallelLinear` (which slice rows) and `RowParallelLinear` (which slices K).   - A TP=4 `RowParallelLinear` is judged by its 768-element shard, not K = 3072.

## Scope and limits

- **Hardware:** per review, the gate covers gfx115x (RDNA3.5: gfx1150 Strix Point, gfx1151 Strix Halo, gfx1152 Krackan Point), the same scope #47695 is moving to. Only gfx1151 was measured end to end (here and in vLLM #55090). gfx1150 and gfx1152 have a narrower memory system and are untested; owners, please report on #30599, and the opt-out exists for exactly that. RDNA3 (gfx110x) is outside the gate because `main` doesn't officially support it yet, even though @LZ-QWQ measured a gain on gfx1100; the gate can widen once it does.
- **Hidden size 5120:** on Qwen3-14B (all linears K = 5120 or 17408) padding is 1.5% slower end to end; see Results. Other hidden-5120 models (for example Qwen2.5-14B, Phi-4) have the same K = 5120 rows but weren't measured. The rule is kept as is, the same as vLLM's. `SGLANG_DISABLE_GFX115_WEIGHT_PADDING=1` turns it off for such models.
- **Weight reload:**
  - Reloads through `update_weights_*` keep the padding: the loaders copy into the padded storage (`narrow().copy_()`), and `postprocess_weights` re-runs. The second pass skips weights that are already padded, so storage pointers stay stable for CUDA graphs.
  - If a loader rebinds a weight to a fresh contiguous tensor, the re-run pads it again.
  - Loaders that bypass `DefaultModelLoader.postprocess_weights` (dummy, sharded-state, remote-instance) still pad linear weights but not the LM head. That affects only speed.
- **Head detection:** an LM head is found by type (`ParallelLMHead`) or by the attribute name `lm_head`. A tied head stored under another name (for example `embed_out`) isn't padded, which costs only speed.

## Known issues, unrelated or unresolved

- **One collapsed Qwen2.5-3B GSM8K run with padding on (0.0%).** From the first token of every answer, the output was the same garbage regardless of the question, with speed normal. It didn't reproduce:
  - 3 further padded runs, with the same script and server sequence, scored 84.0-86.5%.
  - Single-prompt checks after each benchmark stage were correct.
  - Concurrent 32-thread probes, with and without CUDA graphs, were correct.
  - A launch-loop test then started 50 fresh Qwen2.5-3B servers, alternating 25 padded and 25 opted out. Each server got 5 fixed prompts and then a burst of 32 concurrent requests, all checked against the expected answers. All 50 launches answered every prompt correctly.
  - Every launch was instrumented:
    - A SHA-256 over every parameter after loading, computed on the logical values. All 50 launches had the same hash, padded or not.
    - The tie (`lm_head` and `embed_tokens`): same module, same `Parameter`, same `data_ptr()` in every launch. The row stride was 2112 padded and 2048 opted out.
    - No NaN or Inf in any weight, in the first 50 eager-mode logits, or in any returned logprob.

  So I report it as a one-off that couldn't be reproduced. Before this test, padded runs had 1 collapse in 6 and opted-out runs 0 in 5. The launch loop doesn't replay the full benchmark sequence that came before the collapse, and the logits check doesn't cover decode steps replayed from CUDA graphs. @LZ-QWQ's two padded GSM8K runs on gfx1100 also showed no collapse. A similar intermittent breakdown happens with padding off on this stack: DeepSeek-V2-Lite's GSM8K answers degenerate into `!!!!` in 130 of 200 answers unpadded and 115 of 200 padded.
- **DeepSeek-V2-Lite `!!!!` breakdown:** happens without this PR. Please don't attribute it to this change.

- Both arms run in the same process on the same GPU, interleaved round by round, 15 rounds, with the first arm alternating.
- Each arm rotates over ≥1 GiB of distinct weight copies, so every call streams its weight from DRAM rather than the 96 MB last-level cache. Without this, single-copy loops overstate bandwidth on this card.
- Shapes are Qwen3-8B's. bf16, M=1, `F.linear`.
- Two independent passes; numbers are medians from pass 1, with pass 2 within 1%.

| shape (K -> N) | plain | padded | speedup |
|---|---|---|---|
| QKV 4096 -> 6144 | 148.6 µs, 339 GB/s | 119.4 µs, 422 GB/s | 1.245x |

| gate_up 4096 -> 24576 | 516.4 µs, 390 GB/s | 347.9 µs, 579 GB/s | 1.48x |
| down 12288 -> 4096 | 249.0 µs, 404 GB/s | 223.4 µs, 451 GB/s | 1.11x |
| lm_head 4096 -> 151936 | 1930.8 µs, 645 GB/s | 1814.5 µs, 686 GB/s | 1.06x |
