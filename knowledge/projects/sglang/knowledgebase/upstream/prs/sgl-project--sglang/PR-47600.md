# feat: add NCCL EP as optional moe-a2a-backend (low-latency decode)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47600) · state: open · merged: False

## Original PR description

> Supersedes #32329 and #41353, both auto-closed by `close-stale-prs.yml` (#41353 by the idle-PR quota on 2026-10-29). #41353 could not be reopened, so this is a fresh PR on the same head branch.
> Tracked by #32328 and the [Roadmap: Integrate NCCL 2.30 Features into SGLang](https://github.com/sgl-project/sglang/issues/32774).

### Summary

This PR adds **NCCL EP** as an optional `--moe-a2a-backend nccl_ep` choice, implementing the low-latency decode path with correctness parity against DeepEP.

This is the first phase of the [Roadmap: Integrate NCCL 2.30 Features into SGLang](https://github.com/sgl-project/sglang/issues/32328), leveraging NCCL EP's optimized MoE communication on Hopper/Blackwell GPUs.

### Changes

**Backend plumbing**
- **Enum**: Added `NCCL_EP` to `MoeA2ABackend` + `is_nccl_ep()` accessor
- **Server Args**: Added `--nccl-ep-mode` + capability fallback logic
- **Capability Detection**: `is_nccl_ep_available()` + `nccl_ep_capability_reason()`
- **NcclEpBuffer**: Process-wide group + static recv buffers (mirrors DeepEPBuffer)
- **NcclEpDispatcher**: LL dispatch/combine with bf16→fp8 post-quant
- **Wiring**: `create_moe_dispatcher` + `get_moe_impl_class` integration
- **Packaging**: Optional `nccl_ep = ["nccl4py[cu13]"]` dependency

**Rank-major layout (new in this revision)**
- Added `--nccl-ep-layout {expert_major,rank_major}`; `expert_major` stays the default
- `rank_major` keeps NCCL's source-rank slot order through transport and packs slots locally for the expert GEMM, instead of permuting into expert order on the wire
- New `NcclEpRankMajorDispatchOutput` / `NcclEpRankMajorCombineInput` and `DispatchOutputFormat.NCCL_EP_RANK_MAJOR`
- Triton fused gather + route-weight + fp32 reduce (`_rank_major_weighted_reduce_kernel`)
- `register_pre_permute` / `register_post_permute` hooks for `("nccl_ep_rank_major", "deep_gemm")`
- W4AFP8 expert compute via `apply_nccl_ep_rank_major`

**Unified dispatcher**
- Both layouts now resolve inside a single `NcclEpDispatcher` via `get_nccl_ep_layout()`
- The previous expert-major implementation is retained as `nccl_ep_expert_major_legacy.py` and is off the production path. The unified dispatcher always runs `_quantize_fp8` in the EM path, which the legacy module skipped — that produced `hidden_states_scale=None` for the BF16 dispatch-output dtype and crashed W4AFP8's `apply_deepep_ll`.

### Key Design

- Emits `DEEPEP_LL`-format output, reusing `run_moe_core` + `apply_deepep_ll` unchanged
- bf16 dispatch + Python-side post-quant (fp8 wire un-QA'd by NVIDIA)

### Usage

```bash
pip install "sglang[nccl_ep]"
python -m sglang.launch_server --model-path <model> --moe-a2a-backend nccl_ep
# optional: --nccl-ep-layout rank_major
```

- kwen2501 · comment · 2026-11-01T01:07:52Z · [source](https://github.com/sgl-project/sglang/pull/47600#issuecomment-6551565893)

NCCL-EP also supports FP8 quantization during low-latency dispatch, so we should be able to match SGLang's existing DeepEP LL `use_fp8=True` path instead of transferring BF16 and quantizing the received activations separately.

Specifically, `DispatchConfig(quantization_recipe=DispatchQuantizationRecipe.DS_FP8E3M4)` takes BF16 input tokens and produces E4M3 FP8 tokens plus FP32 scales (one scale per 128 elements). The caller supplies FP8 output storage and `DispatchOutputs.scales`; `inputs.scales` is omitted. This recipe requires the hidden dimension to be divisible by 512.

Could we use that path here and feed the returned FP8 activations/scales directly into the expert compute path? We'd still need to check the downstream GEMM's scale layout and rounding requirements, particularly the Blackwell UE8M0 case, and ensure the nccl4py/NCCL-EP dependency version exposes this recipe. But a separate post-transfer quantization step is not inherently required by SGLang.

- kwen2501 · comment · 2026-11-01T01:12:43Z · [source](https://github.com/sgl-project/sglang/pull/47600#discussion_r4433962980)

File: `python/sglang/srt/layers/quantization/w4afp8.py` · line 388

This adapter passes a nine-field `NcclEpRankMajorDispatchOutput` to `apply_deepep_ll()`, whose first statement unpacks the six-field DeepEP layout:

```python
hidden_states, hidden_scales, topk_ids, _, masked_m, expected_m = dispatch_output
```

Consequently, W4AFP8 with `--nccl-ep-layout rank_major` raises `ValueError: too many values to unpack (expected 6)` before reaching the expert GEMM. The rank-major tuple also places `masked_m` and `expected_m` at positions 4 and 5, whereas DeepEP has `topk_weights` at position 4, so truncating the tuple would not fix the mapping.

Could we adapt the shared compute fields explicitly, or have the common GEMM helper read them by name? A focused test passing an actual `NcclEpRankMajorDispatchOutput` through this adapter would catch the mismatch.

- kwen2501 · comment · 2026-11-01T01:22:19Z · [source](https://github.com/sgl-project/sglang/pull/47600#discussion_r4433984920)

File: `python/sglang/srt/layers/moe/token_dispatcher/nccl_ep.py` · line 855

`compact_width = t` uses this receiving rank's local send count as the bound for every source rank's received slots. That is not safe when DP ranks have unequal batches, which SGLang permits under `SUM_LEN` padding. For example, if rank A sends 1 token but receives 8 tokens from rank B routed to A's experts, this slice retains only 1 of B's 8 tokens. The remaining valid slots are excluded from expert computation, although NCCL combine still expects their contributions.

Slicing is an optimization, not a correctness requirement. Could we initially use the full receive capacity (`compact_width = recv_tokens.shape[1]`) and keep the existing `src_rank_counters` mask to exclude unused slots? If we retain the optimization, the width needs a safe bound covering all source ranks' received counts, rather than the local `t`. A test with unequal per-rank token counts would help catch this.

Both prefill and decode use this LL path, so an oversized prefill currently reaches this exception during a request rather than being caught during configuration.

For a known capacity mismatch, an early configuration error would be preferable to a warning that still allows the server to start. Please report the required token count and capacity, and suggest reducing the relevant scheduling settings (`--chunked-prefill-size` / `--max-prefill-tokens`, or decode batch/concurrency limits), accounting for model-specific sharding and speculative tokens. Also, the current message suggests increasing `--nccl-ep-num-max-dispatch-tokens-per-rank`, but the constructor rejects values above 1,024. At that cap, the diagnostic should instead direct the user to reduce the scheduling limits. The runtime guard can remain as a backstop.

This traversal skips DeepSeek: `self.model` is a `DeepseekV2ForCausalLM`, whose decoder layers are under `self.model.model.layers`, not `self.model.layers`. Consequently, its dispatchers never reach `init_handle_for_graph()` and remain on the per-forward handle create/destroy path, including during CUDA graph capture.

That would remove the dependency on model-specific layer paths and avoid per-forward handle allocation/destruction. This addresses the initialization/lifecycle issue; the remaining rank-major graph-compatibility checks can stay separate.

- kwen2501 · comment · 2026-11-01T04:40:41Z · [source](https://github.com/sgl-project/sglang/pull/47600#discussion_r4434418926)

File: `python/sglang/srt/layers/moe/token_dispatcher/nccl_ep.py` · line 749

[P1] Retain NCCL tensor descriptors until split-phase completion

With `send_only=1`, nccl-extensions 0.1.0 saves a continuation that dereferences the supplied `ncclEpTensor_t` descriptors when `complete()` runs. Here `inputs`, `outputs`, and `layout_info` go out of scope when `dispatch_a()` returns. Keeping their underlying PyTorch tensors in `_dispatch_intermediate_state` does not keep the `nccl_ep.Tensor` wrappers alive; those wrappers own the C descriptors, which are freed on GC. Completion can therefore dereference freed host memory.

Please retain the input/output/layout bundles (and their tensor wrappers) through the matching `complete()`. The same lifetime requirement applies to rank-major dispatch and both split combine paths. A CPU lifetime check of `_dispatch_a_rank_major()` showed all six descriptor wrappers were gone on return.

Release references: [saved dispatch continuation](https://github.com/NVIDIA/nccl-extensions/blob/nccl-extensions-v0.1.0/nccl_ep/nccl_ep.cc#L3475-L3594), [descriptor destruction](https://github.com/NVIDIA/nccl-extensions/blob/nccl-extensions-v0.1.0/python/nccl/_extensions/bindings/nccl_ep.pyx#L109-L138).

- kwen2501 · comment · 2026-11-01T04:40:41Z · [source](https://github.com/sgl-project/sglang/pull/47600#discussion_r4434418927)

File: `python/sglang/srt/layers/moe/token_dispatcher/nccl_ep.py` · line 792

[P1] Keep the original routing-index storage alive through rank-major combine

Separate from the split-phase descriptor lifetime: `dispatch_a()` converts routing IDs with `.to(torch.int64)`, but this rank-major state does not retain that `topk_ids` tensor. NCCL-EP 0.1.0's `UpdateHandle` copies the tensor descriptor/dimensions, not its device data; LL combine later reads the original routing pointer. When the conversion creates a new tensor, its storage can be recycled during packing/GEMM before combine uses it.

Please retain the actual dispatched `topk_ids` tensor on the dispatcher until the matching combine completes, including when reusing a persistent handle. The locally packed IDs returned in `NcclEpRankMajorDispatchOutput` are a different tensor and do not preserve the original storage.

Release references: [descriptor-only copy in UpdateHandle](https://github.com/NVIDIA/nccl-extensions/blob/nccl-extensions-v0.1.0/nccl_ep/nccl_ep.cc#L2893-L2934), [combine routing input](https://github.com/NVIDIA/nccl-extensions/blob/nccl-extensions-v0.1.0/nccl_ep/nccl_ep.cc#L4460-L4480).
