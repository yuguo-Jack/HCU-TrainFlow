# [Feat] disaggregation: Add NIXL CPU-buffer PD support for TDX/CC

[Upstream PR](https://github.com/sgl-project/sglang/pull/45779) · state: open · merged: False

## Original PR description

Qwen3.5 prefill–decode disaggregation requires transferring both attention KV cache and Gated DeltaNet (GDN) convolution and recurrent state. TDX/CC deployments that reject CUDA host registration need a host-memory transport configuration that avoids this operation and restores both kinds of data before decode starts.

On upstream snapshot `16eb87c06f`, a cross-node TP1 deployment of Qwen3.5-35B-A3B BF16 on the two H20 hosts below fails during NIXL/UCX initialization. Both workers use the same host-memory UCX settings as the successful CPU-buffer deployment: `UCX_TLS=tcp,cuda_copy,self` and `UCX_ACC_DEVICES=''`. After model loading and CUDA graph capture, the upstream path attempts to register GPU KV buffers and fails with `VRAM memory is detected as host by UCX ... VRAM registration cannot proceed`, followed by `NIXL_ERR_BACKEND`. Neither worker reaches readiness. These are existing UCX settings; the added CPU-buffer path enables KV and GDN state transfer through host memory under this configuration.

## Modifications

- Add an opt-in NIXL transport that registers pageable host buffers in place of GPU KV/state buffers. Enable it on both peers with `--nixl-use-cpu-buffer`.
- Transfer attention KV chunks and the final GDN convolution/recurrent state through host memory. Restore both to GPU before reporting success. A versioned bootstrap extension carries the host-buffer metadata, leaving the existing protocol unchanged when disabled.
- Handle allocation failures and aborts on both peers, including aborts received before prefill bootstrap. Retain buffers until pending writes have drained across TP ranks. These failure paths have unit-test coverage; cross-node fault injection remains pending.
- Continue transfer cleanup when decode admission is paused. Health-check receivers, which do not receive remote writes, bypass the write-drain check. Decode retraction defaults to `cpu_tensor`: requests temporarily removed from the running batch save their state in pageable CPU tensors, avoiding CUDA host registration.

Configuration checks, unit/integration tests, and deployment documentation accompany the transport.

The CPU-buffer path requires NVIDIA CUDA, matching attention TP sizes and KV/GDN state layouts on both peers, and PP=CP=DCP=1. It rejects QSA, speculative decoding, HiCache/HiSparse, KV offload, decode host-receive buffering, PD role switching, and GPU staging. Combining `--nixl-use-cpu-buffer` with `--enable-kv-cache-sharding` is also rejected at startup because CPU-buffer transfers require contiguous send slices. Attestation and transport encryption are outside the scope of this transport implementation.

<details>
<summary>CPU pool capacity and exhaustion behavior</summary>

`--nixl-cpu-buffer-size-gb` sets the pool capacity per worker process (per TP rank), in GiB. The default is 16 GiB. No workload-based sizing study is included for this default. The reported tests explicitly use 4 GiB per worker and do not validate the default capacity under load.

Size the pool for concurrent transfers, not model weight size. For each decode-side request, the allocation is the number of transferred KV pages multiplied by the rank-local bytes per page across all KV buffers, plus the rank-local GDN state bytes. Allocations round up to 256 bytes. Sum this over requests whose receive buffers are still held, and allow headroom for fragmentation and delayed cleanup. Prefill holds the KV chunks and GDN state buffers for outstanding writes until those writes drain. Total host memory must accommodate all worker pools on that host in addition to model/runtime memory.

Allocation is nonblocking. If no contiguous region is large enough, the affected request fails and the failure is propagated to its peer; it does not wait in a pool-capacity queue. Buffers with unsettled remote writes remain reserved until safe to reuse; timeout alone does not release a published receive buffer. Longer prompts or more concurrent transfers can therefore require a larger pool even with the same model. Increase the capacity or reduce transfer concurrency when allocation failures occur. Exhaustion and buffer-retention behavior are unit-tested; cross-node fault injection is still pending.

</details>

## Accuracy Tests

Text-generation accuracy validation uses Qwen3.5-35B-A3B, downloaded from ModelScope, in BF16 on two H20 hosts running in Confidential Computing (CC) mode, as detected by SGLang. Prefill and decode run on separate hosts over NIXL/UCX TCP. The accuracy results were collected on pre-rebase revision `66e80a8368`, with source-file hashes verified on both hosts. The branch is now based on upstream `d61f618276`; the formal results below retain their tested revision. Each TP configuration has a separately evaluated unified reference.

Transport parity uses upstream `PDLogprobParityMixin`, with 11 page/chunk-boundary prompts (15–1,025 tokens), 8 output tokens each, identical token IDs, and logprob tolerance 1e-3. Both deployments enable deterministic inference and Triton GDN prefill.

| TP per worker | Unified repeatability | Cross-node PD vs unified | Max logprob delta |
| --- | --- | --- | --- |
| 1 | 11/11 | 11/11 | 0 |
| 2 | 11/11 | 11/11 | 0 |

GSM8K evaluation uses the 5-shot completion protocol and evaluator from the [upstream Qwen3.5-35B PP test](https://github.com/sgl-project/sglang/blob/16eb87c06fca4b14f91ddc1503e2353f70094ff2/test/registered/pp/test_pp_single_node_extra.py#L254). Unified and PD evaluate the same 512 questions after excluding the five demonstration questions; temperature 0, top_p 1, max output 512 tokens. Evaluation uses concurrency 16 and chunked prefill 128 (upstream: 128 and 256, respectively), without chat-template/thinking flags or deterministic inference. The [upstream assertions](https://github.com/sgl-project/sglang/blob/16eb87c06fca4b14f91ddc1503e2353f70094ff2/test/registered/pp/test_pp_single_node_extra.py#L299) require a unified baseline score ≥ 83% and allow a 5-percentage-point PP drop. Here, the 83% floor is applied to both unified and PD, with the same 5-percentage-point allowance relative to the same-TP unified reference. This is a test acceptance threshold, not a model-card accuracy claim.

| TP per worker | Unified accuracy | Cross-node PD accuracy | PD − unified | Responses at token limit (unified / PD) |
| --- | --- | --- | --- | --- |
| 1 | 435/512 (84.96%) | 459/512 (89.65%) | +4.69 pp | 52 / 43 |
| 2 | 445/512 (86.91%) | 446/512 (87.11%) | +0.20 pp | 46 / 47 |

All four GSM8K runs meet these criteria and each completed 512 non-empty responses. The positive PD score differences are observed results from these runs, not evidence that the transport improves model accuracy. Scores cover the 512-question subset with a 512-token output limit. Responses reaching the limit remain in the denominator and are scored as returned.

The zero logprob delta above applies only to the 11 parity prompts under deterministic inference. It does not measure performance variability or establish equivalence for other prompts or serving configurations.

Both accuracy tests use Triton attention, page size 16, chunked prefill 128, and disable CUDA graphs, overlap scheduling, radix cache, and custom all-reduce. PD uses a 4 GiB CPU pool per worker with KV checksum verification. TP2 automatically skips unsupported FlashInfer all-reduce fusion. Reproduce against externally launched endpoints with `test/manual/disaggregation/eval_nixl_cpu_buffer_pd.py`; pass the matching unified result via `--reference` for PD.

## Speed Tests and Profiling

Performance sanity checks use Qwen3.5-35B-A3B BF16 on H20, pre-rebase revision `fcaf33c03a`. Five configurations ran serially, once each, using upstream `sglang.bench_serving`: 1,024 input / 128 output tokens, random dataset with tokenized ShareGPT text, range ratio 1, seed 42, ignore EOS, unlimited request rate, and 16 warmup + 80 measured requests. Both workers flushed their caches after warmup. Prefill radix caching remained enabled during measurement, allowing prefix reuse within a run. Cross-node TP1/TP2 use 2/4 GPUs in total; same-host TP1 uses 2 GPUs.

| Deployment | TP / worker | Concurrency | Output tokens/s | Median TTFT (ms) | Median TPOT (ms) |
| --- | --- | --- | --- | --- | --- |
| Cross-node | 1 | 1 | 193.25 | 201.56 | 3.58 |
| Cross-node | 1 | 16 | 947.67 | 236.22 | 12.75 |
| Cross-node | 2 | 1 | 219.21 | 160.40 | 3.14 |
| Cross-node | 2 | 16 | 1129.06 | 338.65 | 9.94 |
| Same-host | 1 | 16 | 908.47 | 414.42 | 12.68 |

All 400/400 measured requests succeeded with the requested token lengths. Across the accuracy and performance runs, the reviewed logs contained no request or transfer failures; PD accuracy runs reported no KV checksum mismatches, and performance runs showed no pool exhaustion or CUDA execution errors.

The effective configuration used FA3 attention, page size 1, chunked prefill 8,192, the `breakable` prefill CUDA graph backend (segmented capture at attention/GDN boundaries), full decode CUDA graphs, overlap enabled, and prefill radix cache enabled (decode cache disabled). Graph use was confirmed in runtime logs. Both roles use a 4 GiB CPU pool with NIXL/UCX TCP through the mini_lb router (the lightweight router that coordinates prefill and decode requests) (`UCX_TLS=tcp,cuda_copy,self`, `UCX_ACC_DEVICES=''`); checksum is off for these measurements. MTP is not enabled.

Each row is a single measurement on shared hosts, without repeat runs or an estimate of run-to-run variance. These results cover completion of the listed workloads with CUDA graphs, overlap scheduling, and prefill radix caching enabled. They do not establish a stable performance ranking or a speedup over upstream, whose matched-configuration deployment failed at startup. TP2 skips unsupported FlashInfer all-reduce fusion, and the MoE kernels use the repository's fallback tuning configuration.

At TP1/concurrency 16, same-host median TTFT is 414.42 ms versus 236.22 ms cross-node, about 75% higher. The cause has not been isolated. There are no measurements here that attribute the difference to PCIe/NVLink contention, NUMA placement, or other host activity. Repeated measurements under controlled host load and placement are needed to explain it. The optimized configuration received basic generation prechecks and these performance measurements. The full parity and GSM8K evaluations used the separate accuracy configuration above.
