# [CI] [AMD] pr-test: list tags with ls-remote, 8 small shards

[Upstream PR](https://github.com/sgl-project/sglang/pull/46453) · state: closed · merged: True

## Original PR description

## What

Two cuts to AMD PR-test GPU time, taking the parts of #45425 that still apply after #46084 and #46085. The non-AMD test skip was split out to a follow-up before merge.

| Change | Measured benefit |
|---|---|
| List release tags with `git ls-remote` instead of `git fetch --tags` | 23–30 s median per GPU job (p90 65 s); under 1 s after merge. AMD CI ran ~41,900 GPU jobs in the week of Oct 19–26, so this saves ~270–350 runner-h/week (~650–830 GPU-h, since multi-GPU jobs do the lookup too). |
| `stage-b-test-1-gpu-small-amd`: 12 → 8 shards | Measured after merge: 270 → 239 runner-min per run (−31), and 82 → 68 min from the first shard starting to the last one finishing. |
| ~~Skip AMD GPU stages when a PR only changes non-AMD tests~~ | Split to a follow-up before merge. 0 of 83 PR runs over ~1.3 days would have qualified. |

- **ls-remote.** The container scripts fetched every tag and branch head just to read one tag name. `get_version_tag.py --tag-only --remote` lists the tags on origin and keeps the same PEP 440 ordering. In job logs the lookup went from 31.9 s to 0.34 s.
- **8 shards.** The 1-gpu-small shards run at `max-parallel: 4`:
  - With 12 shards that's 3 rounds of ~20 min of tests plus setup each, about 70 min.
  - With 8 shards it's 2 rounds of ~30 min, about 65 min.

  So the same tests take no longer and need 4 fewer setups and runner waits.

## Why the 1-gpu-small timeout goes from 75 to 90 min on MI300

Each shard carries 1.5× the tests it did with 12 shards. Over the 800 passing 12-shard runs since #46084, the test step took:

| Statistic | 12 shards (measured) | ×1.5 for 8 shards |
|---|---:|---:|
| Median | 19.7 min | ~30 min |
| p99 | 35.2 min | ~53 min |
| Max | 46.1 min | ~69 min |

Shards are balanced by in-source `est_time`, which is often off for real runtimes; `test_hicache_variants`, for example, is estimated at 9 min and runs 22. The validation run's shards so far took 11–38 min. 90 min leaves room for the slowest shard without being far above it.

## Notes for the reviewer

Compared with #45425:
- **Not included: the stage-c shard counts.** They already landed in #46085.
- **Not included: always-on `--continue-on-error`.** That removes fail-fast, so a failing PR would hold the runner until the timeout.
- **Not included: merging `stage-b-test-1-gpu-large-amd` into one job.** #46086 runs its two shards at the same time instead.
- **Not included: the longer timeouts for the large and stage-c jobs.** They were sized before #46084 and #46085 roughly halved those suites.

Thanks. The ls-remote and 8-shard changes LGTM. 

On the non-AMD test skip, the script adds some new failure modes:
- AMD `run_suite.py` collects every `test/registered/**/*.py`. A broken NPU/CUDA test breaks every AMD stage, and with this skip, AMD CI won't catch it on the PR.
- `CHANGED_FILES` overflows the env var limit (`E2BIG`) on large PRs, around 2k files, and `check-changes` fails.
- Import-following is only one level deep and regex-based.

Could you split this into a follow-up PR? Or use a simpler version: exclude the other-hardware dirs in the `main_package` filter, with no script:

```yaml
- "test/!(*.md)"
- "test/!(registered|manual)/**/!(*.md)"
- "test/registered/!(*.md)"
- "test/registered/!(npu|xpu|musa|mps|mlx|cpu|gb300)/**/!(*.md)"
```

If you keep the script, please run `collect_tests` + `validate_all_suites` before returning `false`.

Or I suggest we drop non-AMD test skip part for now to land fast.
