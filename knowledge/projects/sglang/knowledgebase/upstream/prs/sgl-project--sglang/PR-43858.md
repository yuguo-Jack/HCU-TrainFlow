# [Fix] mm: Reject token-layout media spans that wrap the u32 offsets pair

[Upstream PR](https://github.com/sgl-project/sglang/pull/43858) · state: open · merged: False

## Original PR description

## Motivation

Fixes #43857.

`apply_layout` stores each media item's inclusive `(start, end)` range as a `(u32, u32)` pair while the expanded `input_ids: Vec<i64>` keeps its full 64-bit length. For prompts that expand to >= 2^32 tokens after placeholder expansion, `out.len() as u32` and `start + n as u32 - 1` wrap, and every downstream guard (e.g. `mrope_image_only`'s `start < st || end >= len`) validates the wrapped pair against the *true* length, so the wrapped offsets pass silently: image M-RoPE coordinates are then written ~2^32 tokens early — wrong position tables / misplaced media with no error and no crash. The issue has a runnable repro and lldb-verified numbers (stored pair `(66, 69)` vs true span `(4294967362, 4294967365)`).

## Modifications

- `apply_layout` now computes the media span end in `usize` and rejects the layout with a clear error when it would not fit the u32 offsets pair (`end > u32::MAX`), before materializing the expansion.
- As a side effect of restructuring the arm, the item-range and zero-token validations now also run before any tokens are appended.
- New unit test `span_past_u32_offset_limit_errs` covers the rejection cheaply (it fires before the multi-gigabyte expansion would even be built).

Why a gate instead of widening the pair to `u64`: the `Vec<(u32, u32)>` shape is the Python `get_mm_items_offset` convention and ripples through `MropeItem`, the PyO3 boundary and the sglang-server handoff. A >= 2^32-token request cannot be served anyway (its M-RoPE position table alone is ~24 bytes/token), so a loud request error is the correct outcome — silently wrong positions is the worst one.

## Verification

- `cargo test -p sglang-mm --features python,parallel`: 34 passed, 0 failed (includes the new test).
- End-to-end against the freshly built module with the issue's 4,294,967,363-token request: now rejected with `ValueError: layout: media item 0 spans to token 4294967365, past the u32::MAX offset limit; expanded prompt too long`, where current main accepts the request and silently corrupts the position table.
- A normal short image prompt (`[7, 1, 8]` + one 8x8 PNG) returns byte-identical `input_ids`, offsets `[(1, 4)]`, grid, M-RoPE table and delta before and after the change.
