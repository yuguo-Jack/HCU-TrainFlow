# [Perf] muse-spark: Enable fused RMSNorm for FP32 residuals

[Upstream PR](https://github.com/sgl-project/sglang/pull/46622) · state: open · merged: False

## Original PR description

## Changes

Keep this PR limited to Muse Spark reference RMSNorm. For CUDA FP32 residuals with BF16/FP16 gains, convert the effective gain to FP32 to enable PyTorch's fused RMSNorm path. Form zero-centered gains in the checkpoint dtype first, preserving their rounding; convert per call so live weights and autograd remain connected.

**Defaults:** DFlash capture-policy changes and their tests have been removed in response to review. All shared graph-capture defaults remain those of main. The isolated opt-in compaction and its complete c10/c24/c48 measurements are tracked separately in #46739. Other dtype/device paths are unchanged. No doc/docs files are changed.

This changes the automatic capture buckets for eligible DFlash targets across models, not only Muse Spark. The automatic list for speculative decoding is dense on purpose (`generate_decode_cuda_graph_batch_sizes` in `python/sglang/srt/arg_groups/cuda_graph_hook.py`, "less padding for smaller batch sizes"). With `max_bs=256`, enough request capacity and no extra alignment filtering, compaction keeps `[1, 2, 4, 8, 16, 32, 64, 128, 256]`, so a batch of 129 to 136 requests replays the 256 bucket instead of 136, about 1.88 times the verification rows. With `max_bs=16`, a batch of 10 replays 16 instead of 10.

The concurrency 16 experiment combines this policy with the RMSNorm change and does not characterize sustained loads between the retained buckets. Could you add comparisons on current main that isolate compaction at intermediate batch sizes such as 10, 24 and 48, with latency, throughput and graph memory? Otherwise, could compaction stay opt in until those numbers support changing the default?
