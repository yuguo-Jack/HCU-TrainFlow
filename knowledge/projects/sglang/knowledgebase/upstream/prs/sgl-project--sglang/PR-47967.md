# [Fix] [XPU] sampling: Make deterministic top-k renorm reproducible on XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/47967) · state: open · merged: False

## Original PR description

## Motivation

#38565 made top-p / top-k renorm deterministic whenever the TP group has more than one rank, because TP ranks that disagree in the last bits can sample different tokens and later hang in a collective. On XPU the policy falls through to sgl-kernel-xpu's kernels, on the assumption that they are deterministic already. That holds for top-p but not for top-k:

- `TopKRenormProbs.cpp` finds the pivot with an integer radix select, which is reproducible. It then adds each sub-group's kept mass into one shared `float` with a local-memory atomic `fetch_add`, so the order of that sum changes from call to call.
- On Arc Pro B70 (sgl-kernel-xpu 0.5.0, 256 x 151936, k = 40), 50 of 50 repeated calls differ from the first: up to 1.8e-7, in 167 of 256 rows. The kept set never changes.
- `TopPRenormProbs.cpp` keeps one histogram per sub-group and merges them in a fixed order. Its output was bit-identical over the same 50 calls.
- `test_top_k_renorm_probs_is_deterministic` fails on XPU on main. It has not run there because `test_renorm.py` is not registered for XPU CI.

This affects sampled speculative verify and the `intel_xpu` sampling backend's min-p path at TP > 1, for example the Qwen3 TP4 deployment on 4x B70.

## Modifications

- `layers/sampling_renorm.py`: when determinism is on and the tensor is on XPU, `_top_k_renorm_prob` keeps the kernel's top-k mask and renormalizes under it in torch. A single rank keeps the kernel output as is. The comment names the kernel's atomic sum as the reason, and says to drop the workaround once that sum runs in a fixed order.
- `test_renorm.py`: registered for XPU CI, and the device is picked per platform. Its determinism tests now cover the XPU path, including the `tp_size=2` default and the agreement between the fast and deterministic outputs.

## Accuracy Tests

The deterministic output differs from the kernel output by at most 1.2e-7 per element on B70, for batch 1-256 at vocab 151936. The kept set is identical.

Tests on Arc Pro B70, sgl-kernel-xpu 0.5.0:
- `test_renorm.py`: 53 passed, 3 skipped. On main, `test_top_k_renorm_probs_is_deterministic` fails on XPU.
- `test_renorm_policy.py`: 4 passed.

## Speed Tests and Profiling

The extra work runs only when the policy is deterministic. On Arc Pro B70, top-k renorm at vocab 151936, k = 40, best of 5 runs of 200 calls:

| batch | sgl-kernel-xpu (fast, not reproducible) | this PR (deterministic) | Triton renorm (deterministic) |
|---|---|---|---|
| 1 | 131 us | 145 us | 227 us |
| 4 | 133 us | 152 us | 249 us |
| 16 | 139 us | 202 us | 1243 us |
| 64 | 391 us | 705 us | 4945 us |
| 256 | 1486 us | 2801 us | 19186 us |

The Triton column shows the other deterministic option, the Triton kernels HIP uses. It is 6-7x slower than this PR from batch 16 up. The real fix is a fixed-order sum in the kernel, after which this workaround can go.
