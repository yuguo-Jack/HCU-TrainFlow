# [Feature] Gemma2/Gemma3: size sliding-window layers from the hybrid SWA pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/41143) · state: closed · merged: False

## Original PR description

## Motivation

The Gemma2/Gemma3 override disables the hybrid SWA KV pool unconditionally: for Gemma2 after the nightly failure that followed #7367 (#8693), for Gemma3 after fa3 illegal memory accesses (#8895, #9123). Every sliding-window layer is therefore allocated a full-context KV pool: half of Gemma2's layers (window 4096) and five of every six of Gemma3's (window 1024). The window is still applied in attention, so this costs capacity, not correctness.

## Modifications

- **`configs/model_config.py`**: `Gemma2ForCausalLM`, `Gemma3ForCausalLM` and `Gemma3ForConditionalGeneration` join the hybrid-SWA allowlist when they have a `sliding_window`. `get_hybrid_layer_ids` follows the models: Gemma2 windows the even layers (the rule in `models/gemma2.py`, which does not read `layer_types`), Gemma3 reads `layer_types` like Gemma4.
- **`arg_groups/model_overrides/gemma2_gemma3.py`**: keeps the pool disabled for Gemma3n (cross-layer KV sharing), under the hierarchical cache, when either attention backend resolves to aiter (see below), and for Gemma3 when one resolves to fa3 (#9123). Backends are resolved through `get_default_attn_backend`, so fa3 as the Hopper default and aiter as the ROCm default are covered.
- **`layers/attention/aiter_backend.py`**: the unified-attention decode call passed `softcap=0`; it now passes `layer.logit_cap` as the prefill calls do.
- **Tests**
  - `test_model_config.py`: layer splits for Gemma2 and Gemma3 (from real `layer_types`), the allowlist for all three architectures, no window means no hybrid pool, Gemma3n stays single-pool.
  - `test_model_overrides.py`: the golden test that expected Gemma2 to disable the pool now expects it kept on triton and fa3; Gemma3 on fa3 (explicit, decode-only, and as the default), aiter for all three architectures, the hierarchical cache and Gemma3n keep it disabled. Default backends are mocked, so the results do not depend on the host.
  - `test_aiter_fp8_q_unified_attention.py`: decode passes the layer's softcap.

## Accuracy Tests

2x MI325X, ROCm 7.2, `--attention-backend triton`, `--mem-fraction-static 0.80`, radix cache on, with the unsloth mirrors of `google/gemma-3-4b-it` and `google/gemma-2-27b-it`. The GPUs were shared with a resident service outside our control, so absolute numbers are not representative; the arms of each model ran back to back under the same conditions.

GSM8K via lm-eval (`local-chat-completions` with the chat template, 5-shot, all 1319 questions, greedy), strict match:

| model | before | after | after, `--swa-full-tokens-ratio 0.2` |
|---|---|---|---|
| gemma-3-4b-it (TP 1) | 0.821 ± 0.011 | 0.830 ± 0.010 | 0.829 ± 0.010 |
| gemma-2-27b-it (TP 2) | 0.863 ± 0.009 | 0.863 ± 0.009 | 0.865 ± 0.009 |

Greedy `/generate` outputs (48 tokens) for prompts one token under, at and over the window, a longer prompt (2x window for Gemma3; 7624 tokens for Gemma2, as much as its 8192 context allows), and a prompt followed by the same prompt extended by 512 tokens, each sent twice so the second reuses the radix cache: 12/12 token-identical to before, for both ratios and both models. GSM8K requests fit inside the Gemma2 window, which is why its scores match exactly.

## Speed Tests and Profiling

`bench_serving --dataset-name random-ids` after a warmup round.

Gemma3 4B, TP 1, `--context-length 34816`:

| | KV pool (tokens) | 384 x (4096 in, 1024 out), conc 128 | 64 x (32768 in, 1024 out), conc 64 |
|---|---|---|---|
| before | 692,275 (single pool) | 3883.3 tok/s | 1154.6 tok/s, peak running 20 |
| after | full 834,658 + SWA 667,726 | 3980.5 tok/s (+2.5%) | 1167.0 tok/s (+1.1%), peak running 24 |
| after, ratio 0.2 | full 2,179,384 + SWA 435,876 | 3915.7 tok/s (+0.8%) | 1491.2 tok/s (+29.2%), peak running 29 |

Gemma2 27B, TP 2, `--context-length 8192`, 384 x (6144 in, 1024 out), conc 128:

| | KV pool (tokens) | output tok/s | peak running |
|---|---|---|---|
| before | 395,486 (single pool) | 712.2 | 59 |
| after | full 439,429 + SWA 351,543 | 716.5 (+0.6%) | 62 |
| after, ratio 0.2 | full 659,144 + SWA 131,828 | 557.0 (-21.8%) | 29 |

The default ratio gives Gemma3 20.6% and Gemma2 11.1% more full-pool tokens. Gemma3's window is 1024, so for long prompts a lower ratio is what turns that into throughput. Gemma2's window is half of its 8192 context, so a ratio of 0.2 starves the SWA pool (131,828 tokens, about 32 windows) and halves concurrency; the default ratio is the right one there.

## aiter

On ROCm the default attention backend is aiter. Its paged decode cannot apply a window, so Gemma2 27B does not start there on the single pool, before or after this change. With the hybrid pool on, aiter decodes through unified attention instead:

- That decode call dropped the softcap Gemma2 uses (50). On a 4095-token probe, the continuation without the fix degenerates into a repeated phrase; with the fix it matches triton's continuation.
- Batched serving on that path is still not right with the fix. During GSM8K, Gemma2 27B held about 2,800 tokens per running request against 1,200 on triton (its answers ran far longer) and did not finish within an hour; Gemma3 4B scored 0.573 on GSM8K against 0.830 on triton. Throughput was 4-9x lower (Gemma2 27B 143 vs 716 tok/s, Gemma3 4B 422 vs 3980 tok/s).

So the override keeps the single pool whenever aiter is the backend, which leaves ROCm behaving as it does today; `--attention-backend triton` gets the hybrid pool there. The softcap fix stands on its own: it also applies to `SGLANG_USE_AITER_UNIFIED_ATTN=1` on the single pool. The batched behaviour, which also showed up with `SGLANG_USE_AITER_UNIFIED_ATTN=1` on the single pool, is filed as #41152. On the single pool it turned out to be a stale CUDA-graph page table at `page_size` 1, fixed in #41234. With this PR and #41234 together, `SGLANG_USE_AITER_UNIFIED_ATTN=1` on the single pool scores GSM8K 0.932 on Gemma 3 12B (triton 0.933) and 0.845 on Gemma 2 9B (triton 0.843 on the same tree). #41234 does not touch the hybrid pool's page-table path, so the hybrid-pool numbers above still stand, and the override keeps aiter on the single pool.

These runs used upstream `a1b4ec02ae` with an earlier revision of this diff (identical on triton; the aiter rule came from the results above), plus two local fp8-kernel patches that are not on these bf16 paths. The unit tests were rerun on current `main`.
