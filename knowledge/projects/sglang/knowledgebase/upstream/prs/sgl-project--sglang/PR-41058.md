# [Bugfix] Detokenizer: keep sent_offset monotonic when a character is split across steps

[Upstream PR](https://github.com/sgl-project/sglang/pull/41058) · state: open · merged: False

## Original PR description

## Motivation

Streaming CJK/multilingual output can send the same character to the client twice.

`DetokenizerManager._decode_batch_token_id_output` documents the invariant it depends on, three lines above the defect:

```python
# Streaming. Invariant: sent_offset >= decoded_text_len. The
# gap (`pending`) is "printable but uncommitted" text emitted
# in a prior "�" recovery step; we skip it from this step's
# emission so we don't double-send.
pending = s.sent_offset - s.decoded_text_len
```

The recovery arm then moves that offset backwards:

```python
printable = find_printable_text(new_text)
s.sent_offset = s.decoded_text_len + len(printable)   # can retreat
```

`find_printable_text` (`python/sglang/utils.py:345`, borrowed from the HF streamer) is a stateless heuristic, and its result is not monotonic: a step whose tail is an incomplete character can yield a *shorter* prefix than the step before it, because its branches disagree about where the last printable character is. The penultimate-CJK branch emits through a trailing CJK character; the last-space branch retreats to an earlier space; and when neither applies there is nothing to fall back to.

### Concrete case

Three consecutive detokenizer steps, each carrying several ids (speculative decoding, or a lagging detokenizer):

| step | `new_text` | `find_printable_text` | `sent_offset` |
| --- | --- | --- | --- |
| 1 | `"你�"` | `"你"` — penultimate-CJK branch | 1 |
| 2 | `"你好，�"` | `""` — `，` (U+FF0C) is not classified as CJK, and there is no space to fall back to | **0** |
| 3 | `"你好，世"` | clean, commits | re-emits from 0 |

At step 3 `pending = sent_offset - decoded_text_len = 0`, so instead of skipping the already-delivered `"你"` it re-sends the whole prefix and the client sees `"你你好，世"`.

Any generation containing a character split across tokens and no ASCII space (typical for Chinese output) reaches this. Non-streaming requests are unaffected: they materialize the text once from the committed chunks.

## Modifications

Clamp `sent_offset` so it never retreats. The emission slices already produce `""` when `pending` exceeds the available text, so only the offset needs guarding — a `sent_offset` that stays put simply means "nothing new to send this step", and the next clean step still emits exactly the not-yet-sent suffix.

### Why here, and not inside `find_printable_text`

Worth stating, since the helper is the source of the non-monotonic value:

- `find_printable_text` is a pure `str -> str` heuristic. "The result may shrink as the text grows" is a property of its contract, not a defect in it — each call re-evaluates the whole string and picks the best cut. Making it monotonic would require carrying state and changing its signature.
- The invariant that actually breaks belongs to the *stateful* caller (`sent_offset` must not go backwards within a request), so the guard belongs with the offset bookkeeping, where the rest of the incremental state already lives.

I also checked for an upstream rework of this path before writing the patch: `find_printable_text` has exactly one call site in the repository (this one), and the only open PR in this area (#34852) bounds the decode window without touching this recomputation, so the two changes are independent.

## Tests

`test/registered/unit/managers/test_detokenizer_stream_offsets.py` drives the real `_decode_batch_token_id_output` with a byte-level stub tokenizer — pure CPU, no IPC, no tokenizer download — and covers both decode paths (`_grouped_batch_decode` and the per-row path).

Before the change, 3 of 4 cases fail:

```
E  AssertionError: Lists differ: [1, 0, 4] != [0, 1, 4] : sent_offset retreated: [(0, 1), (0, 0), (4, 4)]
E  FAILED test_incomplete_character_does_not_duplicate_text
E  FAILED test_incomplete_character_does_not_duplicate_text_without_batch_decode
E  FAILED test_sent_offset_never_retreats
```

- `test_incomplete_character_does_not_duplicate_text` — the assembled client stream must equal the one-shot decode
- `test_incomplete_character_does_not_duplicate_text_without_batch_decode` — same, on the per-row path
- `test_sent_offset_never_retreats` — asserts the invariant the streaming arm relies on
- `test_plain_ascii_stream_is_unchanged` — guards against over-correcting the common case; passes before and after

After the change: 4 passed, and the wider manager test set (`test_trim_matched_stop.py`, `test_output_streamer_logprobs.py`, `test_output_streamer_customized_info.py`) passes with it — 24 passed together.

The three failures were re-checked with the fix removed, after the branch was rebased, to confirm the test is a regression guard rather than a description of current behaviour. `ruff check` and `ruff format --check` clean.

Cross-checked the reverse control on `7c205a9cb` independently. With the clamp replaced by the plain assignment in a scratch copy: **5 failed / 4 passed**, matching the numbers in the commit message. The fix itself is sound — `find_printable_text` always returns a prefix of the accumulated text, so clamping `sent_offset` to a floor can only suppress re-sends, never skip text that was never sent, and the partial-UTF-8 branch keeps `decoded_text_len` fixed while it runs, which is what makes the comparison meaningful.

One nit on the attribution, because it changes what the new tests are taken to prove: of the **three** new cases, only `test_space_retreat_does_not_duplicate_text` actually fails without the clamp.

`test_empty_streaming_step_does_not_reset_sent_offset` passes with the clamp removed, and it has to:

- when the empty delta repeats the previous step's `new_text`, the previous step is the one that already raised `sent_offset`, so `decoded_text_len + len(printable)` lands on the same value again;
- when it is a genuine empty delta (`surr_offset`/`read_offset` were advanced by a clean step), `sent_offset` is already equal to `decoded_text_len`, so both the clamp and the plain assignment agree.

So it is a fair end-to-end guard for empty deltas, but it does not pin the clamp. The coverage claim is carried by `test_clamp_is_exercised_in_both_directions` plus the space-retreat case, and those stand on their own — only the "three new cases fail" line is claiming more than the evidence supports.
