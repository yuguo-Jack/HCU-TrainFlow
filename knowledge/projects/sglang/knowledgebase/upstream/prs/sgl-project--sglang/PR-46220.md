# [Perf] pd: Apply the prefill WAR barrier after the previous result is processed

[Upstream PR](https://github.com/sgl-project/sglang/pull/46220) · state: closed · merged: True

## Original PR description

## Motivation

In the PD prefill overlap loop, `_apply_war_barrier()` runs right after `run_batch(k)`, so all schedule-stream work in the previous batch's result processing is queued behind forward k.

The barrier waits for the whole forward whenever the forward does not publish a pre-replay read-done event. On main that is any HiCache, storage-backend or LMCache deployment, plus any backend or speculative algorithm without `PRE_REPLAY`. In that case:

- The first host-blocking device-to-host copy in `process_batch_result_disagg_prefill(k-1)` waits until forward k finishes. In our traces that copy is the KV-send state page translation (`_swa_payload` -> `kv_to_page_indices`).
- The rest of the per-request bookkeeping then runs serially with the GPU idle: radix checkpoint, SWA and paged frees, KV-send translation, and the next schedule. This bookkeeping holds hundreds of small syncs per step.
- With DP attention, the other DP rank waits for this rank in the per-step metadata all-gather. So one rank's bookkeeping stalls both ranks.

On DeepSeek-V4.1-Flash prefill (DEP2), on a build where this model still fell back to the whole-forward barrier (before #45582 and #45682), Nsight showed 70-100 ms of GPU idle between consecutive prefill forwards. That is 15-20% of a ~500 ms step. On current main the same deployment publishes read-done and does not hit this; HiCache, storage-backend and LMCache prefill still do.

## Modifications

`event_loop_overlap_disagg_prefill` now applies the barrier later: after `process_batch_result(k-1)` and `process_disagg_prefill_inflight_queue()`, and before the next schedule. On the continuous-polling path, when the oldest result is not ready yet, the barrier is applied before `continue`, so later intake keeps the current ordering. The normal and decode loops are unchanged.

This is safe only in the PD prefill loop. Its result processing mutates no request that is in forward k:

- Finished, aborted and released requests are not in forward k. Their radix checkpoint, deduplicated-page frees, SWA mapping updates and KV sends only touch their own rows and slots. Freed slots are reallocated only by the next schedule, which still runs after the barrier.
- A request whose next chunk is in forward k is only read during result processing (the non-last-chunk KV send). Its chunk stash (`process_prefill_chunk` -> checkpoint) runs in the next schedule, after the barrier.
- KV transfers and cache offloads issued here read pages written by forward k-1. Forward k-1 has completed, because the schedule stream is behind the k-1 barrier and the result copy has been synchronized.

- One write can reach memory that forward k's requests hold: inserting a finished request can recover a tombstoned SWA component on a node whose Full KV is locked by a request in forward k, and rewrite that node's `full_to_swa` entries. Those positions are outside the locking request's sliding window (its in-window nodes are SWA-locked and cannot be tombstoned), so forward k never uses them.

The decode and normal loops keep the barrier right after launch. There, result processing can rewrite rows of requests still running in the next forward; that hazard is the reason the barrier was placed after launch.

The safety depends on an invariant that the code does not check: nothing between `run_batch(k)` and the barrier may allocate or evict device memory that gets reused, stash or release the continuing chunked request, or send a partial page. The inline comment states the rule.

Limits:

- With continuous input polling, when the oldest result is not ready, the barrier is still applied before `continue`, so the gain is smaller there.
- With eager unified-memory compaction, the eager free waits for the forward stream itself, which cancels the gain.
- The PP prefill loop and the non-overlap PD loop do not call the WAR barrier and are unchanged.

## Accuracy Tests

GSM8K through the full PD path (2x DEP2 prefill + DEP4 decode, DeepSeek-V4.1-Flash FP4, DSPARK). Settings: sgl-eval 0.1.3 with `--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash`, all 1319 examples, 128 threads:

| prefill cache | score | error rate | stop rate |
|---|---|---|---|
| HiCache (write_back, direct) | 0.968 | 0 | 1.0 |
| Mooncake external linker | 0.967 | 0 | 1.0 |

Unit tests: `test/registered/unit/disaggregation/` plus the prefill polling, idle-step, shared-read-done and decode shared-read fence tests pass on CPU (406 passed, 14 CUDA-only skipped).

With read-done, the barrier already releases before the forward ends, so deferring it is neutral within single-run noise. The gain applies to every deployment that still uses the whole-forward barrier. GSM8K with read-done active and this PR: 0.969.

Nsight, linker build with the whole-forward barrier, one DEP2 prefill worker (both DP ranks), 15 consecutive steps:

| | base | this PR |
|---|---|---|
| GPU idle between prefill forwards (mean per step, DP0 / DP1) | 77 / 69 ms | 0.5 / 3.2 ms |
| GPU busy / step wall time | 0.82 | 0.93 |

With this PR, the remaining long host waits in the prefill loop fall inside `run_batch`, while the GPU is busy, instead of between forwards.
