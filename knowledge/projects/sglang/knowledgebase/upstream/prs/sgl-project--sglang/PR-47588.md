# [Feat] sail: support DeepGEMM GEMM/MoE backends [4/N]

[Upstream PR](https://github.com/sgl-project/sglang/pull/47588) · state: open · merged: False

## Original PR description

## Motivation

Part 4 of the SAIL upstreaming series, following #45946 (merged). T-HEAD SAIL ships its own DeepGEMM build (`deep_gemm>=1.1.0`), DeepEP and a set of fused JIT kernels, but none of them are reachable through the shared code paths:

- The DeepGEMM wrapper only knows the community call surface. SAIL's library exposes a `nopad` grouped-GEMM interface, dispatches int8 / bf16 / fp4 / int4 kernel types, and needs the kernel configs supplied by an offline autotuner.
- `DeepGemmRunnerCore` covers blockwise FP8, MXFP4 and INT4. SAIL's expert-parallel path additionally needs per-channel FP8 and INT8 grouped GEMMs, plus a different MXFP4 / INT4 weight layout, and it fuses the SiLU-mul with the activation quantization.
- The quantization methods (`fp8`, `mxfp4`, `w8a8_int8`, `unquant`, `compressed_tensors`) never resolve to `MoeRunnerBackend.DEEP_GEMM`, so the runner is unreachable from the model side.
- The DeepEP dispatcher probes FABRIC assuming a CUDA-version-specific layout, and the masked SAIL kernels consume int64 top-k ids.

This PR makes DeepSeek / Kimi / DSpark models run on SAIL with `--moe-runner-backend deep_gemm`, for both TP (`--moe-a2a-backend none`) and EP (`--moe-a2a-backend deepep`), including the DSpark speculative path. SAIL behavior is gated behind `is_sail()` and kept in new modules; the shared runners keep their existing behavior.

## Modifications

### 1. Platform plumbing and enablement

- `kernels/jit/utils/arch.py`: `is_arch_support_pdl()` returns `False` on SAIL.
- `arg_groups/platform_hook.py`: `handle_sail_backends` turns `SGLANG_SAIL_DEEPGEMM_{DENSE,MOE}` on by default, rejects `--moe-a2a-backend megamoe`, and validates the MXFP4 W4A16 modes (VALU vs MMA are mutually exclusive and require `--moe-runner-backend deep_gemm` with `none` / `deepep`).
- `environ.py`: declares the `SGLANG_SAIL_*` knobs the later commits gate on.
- `utils/common.py`: `is_mnnvl_fabric_device()` reports `True` on SAIL, leaving the final communication mode to PCCL.
- `pyproject_other.toml`: adds `deep_gemm>=1.1.0` to `srt_sail`.

### 2. Fused SiLU-mul quantization JIT kernels

| File | Purpose |
| --- | --- |
| `jit/csrc/elementwise/silu_and_mul_post_{per_token_quant_fp8,quant_mxfp4}.cuh` | Padded (TP) layout: SiLU + mul + per-token FP8 / MXFP4 quantization in one pass. |
| `jit/csrc/elementwise/silu_and_mul_masked_post_{per_token_quant_fp8,quant_mxfp4}.cuh` | Masked (EP) layout, same fusion. |
| `ops/activation/silu_mul_quant.py` | Python entry points (`silu_and_mul_post_quant_{fp8,mxfp4}`, `silu_and_mul_masked_post_quant_*`). |
| `ops/quantization/sail_mxfp4.py` | MXFP4 weight pack/unpack and scale conversion. |
| `ops/moe/ep_moe_kernels.py` | Routes the masked quantization through the new kernels. |

Also touches `per_token_quant_fp8.cuh`, `kimi_k3/situ_and_mul.cuh`, `moe/dsv4.py`, `layernorm/mhc.py`, and adds the matching `test/registered/...` unit tests and `benchmark/kernels/bench_permute.py`.

### 3. DeepGEMM API surface and autotuner

- `kernels/ops/gemm/sail_deepgemm.py` (new): the SAIL DeepGEMM call surface, including the `nopad` grouped GEMMs and the fused activation variants.
- `deep_gemm_wrapper/{entrypoint,compile_utils,configurer}.py`: dispatch the int8 / bf16 / fp4 / int4 kernel types and the nopad interface on SAIL.
- `deep_gemm_tuner/` (new): persist and look up the tuned configs.
- `tune_deepgemm_int8.py` (new): offline tuning entry point.

### 4. TP MoE runner and quantization backends

- `moe_runner/sail_deepgemm_moe.py` (new): the tensor-parallel SAIL DeepGEMM MoE path, registered with `@register_fused_func("none", "deep_gemm")`. Supports the gather-read GEMM1 variant and the `situ_and_mul` activation.
- `moe/utils.py`: the SAIL runner-backend and int8 dispatcher-dtype entries.
- `quantization/{fp8,mxfp4,w8a8_int8,unquant}.py` and `compressed_tensors/*`: resolve `MoeRunnerBackend.DEEP_GEMM` on SAIL and build the matching `DeepGemmMoeQuantInfo`.
- `compressed_tensors_w8a8_int8_generic_moe.py`: a dynamic-token INT8 MoE scheme.

### 5. Shared DeepGEMM runner extension and the EP runner

- `moe_runner/sail_deepgemm_ep.py` (new): `SailDeepGemmEpRunnerCore(DeepGemmRunnerCore)` carries the SAIL-only expert-parallel kernels — per-channel FP8, INT8, MXFP4 and INT4, for both the contiguous and masked layouts. It dispatches on a `(masked, quant family)` table and falls back to `super().run()` for BF16 and blockwise FP8, which stay on shared code.
- `moe_runner/runner.py`: instantiates `SailDeepGemmEpRunnerCore` instead of `DeepGemmRunnerCore` when `is_sail()`.
- `moe_runner/deep_gemm.py`: SAIL branches inside the contiguous/masked runners, so the fused activation-quantization kernels and the nopad grouped GEMM are used there as well.
- `fused_moe_triton/layer.py`: feeds the dispatcher quant config into the runner.
- `ep_moe/layer.py`, `batch_overlap/single_batch_overlap.py`: follow-on plumbing.

### 6. DeepEP token dispatcher

- `token_dispatcher/deepep.py`: SAIL dispatch dtypes; probe the `Buffer` signature instead of assuming a CUDA-version-specific FABRIC path; keep the expert alignment at 1 so a rank never receives more tokens than it needs; guard the `topk_output` access that the DeepEP dispatch outputs do not provide.
- `moe/topk.py`: int64 top-k ids for the SAIL masked kernels.
- `moe/hash_topk.py` + `jit/csrc/deepseek_v4/hash_topk.cuh`: the hashed top-k variant that consumes those int64 ids.

### 7. Model enablement

- `models/{deepseek_v2,deepseek_v4,kimi_k25,kimi_k3}.py`: select the SAIL path and fix the packed-name remapping for the MXFP4 expert loader.
- `arg_groups/speculative_hook.py`: allow DeepEP all-to-all MoE under DP attention.
- `arg_groups/model_overrides/gpt_oss.py`: select the DeepGEMM MoE runner for MXFP4 weights.

### 8-9. Two standalone fixes

- `fix(sbo): skip overlap args for DeepEP normal-mode dispatch` — `compute_overlap_args` unpacks `hidden_states` as `(num_local_experts, num_tokens, hidden)`, the layout DeepEP's low-latency mode produces. Normal mode dispatches a plain `(num_tokens, hidden)` tensor, so the unpack raises. Return early for that dispatcher. This is a general fix, unrelated to SAIL, and can be split out on request.
- `fix(models): keep the outer prefix for Kimi-K25's language model` — the language model is loaded from the checkpoint, so it has to carry the prefix the parent passes in; hard-coding the bare name drops it whenever Kimi-K25 is nested under another module. Also general.

## Impact on non-SAIL platforms

Every SAIL-only kernel lives in a new module, and the shared runners only take a branch when `is_sail()` is true. The changes that do reach a non-SAIL run are:

- `DeepGemmMoeQuantInfo` gains `use_int8`, `use_mxfp4`, `use_mxfp4_w4a16`, `per_channel_quant`, `b13`, `b2`, `use_int4_w4a16`, and `use_fp8` becomes optional. The four that mirror `TritonMoeQuantInfo` are additive; the default flags keep the existing FP8 / MXFP4 / INT4 dispatch unchanged.
- The contiguous and masked DeepGEMM runners forward `gemm1_alpha`, `swiglu_limit` and `overlap_args` (both call-site level and the masked GEMM's `meta_overlap_args`), and return early when `all_tokens <= 0`.
- `fused_moe_triton/layer.py` passes the dispatcher quant config to the runner; the helper is idempotent off SAIL.
- The DeepEP alignment and int64 top-k id handling, and the two fixes above.

These need a CUDA (Hopper/Blackwell) regression run before merge; I have no CUDA device here.

## Known limitations

- `--moe-a2a-backend megamoe` is rejected on SAIL; use `none` or `deepep`.
- The MXFP4 W4A16 VALU and MMA modes are mutually exclusive, and both require `--moe-runner-backend deep_gemm`.
- `sail_deepgemm_ep.py` and `deep_gemm.py` still share the generic activation/overlap helpers; a later pass can move the remaining SAIL branches out of the shared runner entirely.
