# [diffusion] vae: fix silently ignored --vae-tiling for Sana (AutoencoderDC)

[Upstream PR](https://github.com/sgl-project/sglang/pull/34514) · state: open · merged: False

## Original PR description

### Motivation

Fixes #34482.

`--vae-tiling` was silently ignored for Sana models: the `AutoencoderDC` wrapper
does not proxy `enable_tiling` to the inner diffusers model, so the call raised
`AttributeError`, which (at the time this PR was opened) was swallowed by a bare
`except` in `DecodingStage`. On 8GB GPUs this turns a would-be-successful
generation into a fatal OOM after the full denoising loop has already run. See
the issue for the root-cause chain.

### Modifications

- `runtime/models/vaes/autoencoder_dc.py`: proxy `enable_tiling` /
  `disable_tiling` to the inner diffusers `AutoencoderDC`, which already
  implements them. `enable_tiling` is a no-op (with `warning_once`) when
  spatial-shard parallel decode is installed on this wrapper, since diffusers'
  `tiled_decode` running per-rank inside a height-sharded decoder breaks the
  halo exchange (mismatched collective rounds / wrong neighbours).
- `configs/models/vaes/sana.py`, `configs/pipeline_configs/sana.py`: update
  the two comments that claimed DC-AE tiling is unsupported.
- `test/unit/test_autoencoder_dc.py`: CPU-only unit test asserting the proxy
  forwards to the inner model and that the spatial-shard guard is a no-op.

### Scope / decisions

- **Default unchanged.** `SanaPipelineConfig.vae_tiling` stays `False`; tiling
  is opt-in via `--vae-tiling`. DC-AE is a 32x-compression autoencoder and
  tile seam quality / the benefit of diffusers' default 512 tile have not been
  validated, so a default flip does not belong in a bugfix.
- **`decoding.py` is no longer touched.** The v1 of this PR also replaced the
  bare `except` around `enable_tiling()` with a warning; main has since fixed
  that call site independently (specific `AttributeError` handling + warning),
  so that change is dropped here and the PR is now purely the wrapper-side fix.

### Test / Verification

- Before: `sglang generate --model-path Efficient-Large-Model/Sana_600M_512px_diffusers
  --prompt "..." --save-output --vae-tiling` — fatal OOM in `DecodingStage` on
  RTX 4070 Laptop 8GB (3/3 runs). Note: with DC-AE's 32x compression, tiling
  only engages at ≥1024x1024 (512x512 gives a 16x16 latent == `tile_latent_min`).
- After: same command (1024x1024) succeeds end-to-end; output image correct.
  This PR changes correctness (OOM → success), not performance; timings are
  not reported.
- `pytest python/sglang/multimodal_gen/test/unit/test_autoencoder_dc.py` passes.
- pre-commit clean.

- triple-mu · APPROVED · 2026-08-14T04:13:47Z · [source](https://github.com/sgl-project/sglang/pull/34514#pullrequestreview-4933913488)

The root cause analysis is accurate, and the change is appropriately minimal with no impact on default behaviour (the pipeline config is only overridden when `--vae-tiling` is passed explicitly). Proxying to the inner model is the right approach. A few things to address before merge:

**1. Once tiling actually takes effect, its combination with spatial-shard parallel decode becomes live** (previously inert, because `enable_tiling` raised and the exception was swallowed). See the inline comment.

**2. Two comments no longer match the code -- please update them as well** (neither file is touched by this PR):
- `configs/models/vaes/sana.py:29-30`
- `configs/pipeline_configs/sana.py:52`

These are comment-only issues with no runtime contradiction: `SanaVAEConfig.use_tiling` is never read for this VAE; the actual switch is `pipeline_config.vae_tiling`.

**3. Please settle the default value of `SanaPipelineConfig.vae_tiling` in this PR.** My suggestion is to keep it `False`: DC-AE is a 32x-compression autoencoder, and both the tile seam quality and the real benefit of the default 512 tile need to be validated separately. Changing the default rendering behaviour for every Sana user inside a bugfix is not ideal. If the decision is to keep it as is, please state that explicitly rather than leaving it open.

**4. Please note the scope of the fix in the description.** The same bare `except` still exists at `image_encoding.py:615/928`, `realtime/vae.py:152`, `mova.py:983` and `ltx_2/decoding_av.py:87`, and `encoding.py:111` has no `try` at all. Fixing only the decoding path is reasonable -- none of the others is reachable for `AutoencoderDC` -- but a sentence in the description would keep this from reading as an oversight.

For reference, and not something to handle in this PR: `enable_tiling()` is called without arguments, so diffusers' default 512 sample tile applies. With DC-AE's 32x compression a 512x512 output has a 16x16 latent, which equals `tile_latent_min`, so tiling does not actually engage until 1024x1024. The ~386MB non-fatal allocator retries you reported in the issue are likely related to the tile being large; if you want to push the 8GB case further, forwarding the tile geometry from the config would be a reasonable follow-up.

### inline_comments

- triple-mu · comment · 2026-08-14T04:13:47Z · [source](https://github.com/sgl-project/sglang/pull/34514#discussion_r3781053547)

File: `python/sglang/multimodal_gen/runtime/models/vaes/autoencoder_dc.py` · line 139

Consider making this a no-op (with a warning) when `self._spatial_parallel_decode_enabled` is true, or documenting that the two features cannot be enabled together.

With spatial-shard decode installed, `decode()` splits the latent by height via `tensor_split` and the convolutions are replaced by `SpatialParallelConv2d`, which performs halo exchanges. After this PR, diffusers' `tiled_decode` runs tile by tile *inside* each rank's shard, so the number of collective rounds becomes a function of each rank's shard height. For example, with a latent height of 128 across 3 ranks, `tensor_split` gives 43/43/42: ranks 0 and 1 run 4 tile iterations while rank 2 runs 3, which hangs. With equal shard heights there is no hang, but each rank's tiles map to different global rows, so the halo neighbours are wrong and the bottom band of each shard is corrupted.

Triggering this requires explicitly passing `--vae-config.parallel-decode-mode spatial_shard`, so the reachability is narrow and I would not treat it as blocking. `autoencoder_kl_qwenimage.py:1102` and `hunyuanvae.py:950` guard exactly this combination with `with disable_spatial_parallel_decode():` and may be a useful reference.

- triple-mu · comment · 2026-08-14T04:13:47Z · [source](https://github.com/sgl-project/sglang/pull/34514#discussion_r3781053552)

File: `python/sglang/multimodal_gen/runtime/models/vaes/autoencoder_dc.py` · line 142

A one-line comment here would help. `_ensure_inner_model()` returns early once `_inner_model` exists, so if a future caller reaches `enable_tiling()` before the weights are loaded, a randomly initialised inner model would be built via `from_config` and the real weights would then be silently discarded.

Not reachable today -- `VAELoader` calls `load_state_dict` immediately after construction, and that in turn calls `_ensure_inner_model` with the state dict, and `DecodingStage.forward` calls `load_model()` before `decode()`. Just a note for future changes.
