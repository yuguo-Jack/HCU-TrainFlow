# [Perf] [AMD] moe: Fuse MXFP8 quant into the small MoE sort

[Upstream PR](https://github.com/sgl-project/sglang/pull/42498) · state: open · merged: False

## Original PR description

## Motivation

Every decode step of DeepSeek-V4.1 sorts the tokens for each MoE layer and then quantizes them in a separate GPU launch. This PR does both in one launch, which lowers decode time per token by 1.5 to 2.6 % at 1 to 32 users. It needs no other open PR.

In detail: in decode, aiter's MoE sorts the routed tokens and, with fp8 activations, quantizes the stage-1 input to MXFP8. Main fuses that quant into the small MoE sort only when hidden % 2048 == 0, and its bitonic sort kernel (#44004) runs only without the quant, so DeepSeek-V4.1 (hidden 5120) runs two launches in every MoE layer. This PR fuses them for hidden sizes that are multiples of 1024. It follows the contribution guide's rule "Prioritize extreme efficiency" for code on the critical path, with bitwise tests against aiter.

Related PRs: none is required; this PR applies on main as it is. #43822 (open) changes the same gate for hidden 5120 and E 385; this PR covers both, and its sort + quant is as fast at 1 and 4 rows and takes 19.7 to 62.9 % less time from 5 to 36 rows (kernel table below), so only one of the two should land. Related Prs of #44004, #44601 and #45480 are merged.

## Modifications

- `moe_sorting_small.py`: the `fused_moe` gate passes the activations to the sort when `hidden % 1024 == 0` (was 2048), and the bitonic kernel also writes the quant (fp8 rows and e8m0 scales, with aiter's layout and math). For DeepSeek-V4.1 (E 385 = 384 routed + 1 fused shared expert, top 7), the sort and the quant become one launch up to 36 rows.
- Below 512 experts, the quant path takes the bitonic kernel above 32 pairs. From 512 experts on, it keeps main's kernels: at Qwen3.5's E 513 / top 11, the bitonic kernel with the quant was 4.7 to 5.2 % slower at 3 to 5 rows.
- `test_moe_sorting_small.py`: E 385 / top 7 sorting, quant bytes and scales bitwise against aiter at hidden 5120, the 36 / 37-row cutoff, and a new `test_fused_moe_a8w4_stage1_matches_aiter`: aiter `fused_moe` at DeepSeek-V4.1's TP4 shapes must take the quant from the sort and match stock aiter's stage-1 output bitwise. Hidden 7168 (DeepSeek-V3, timed below) has no correctness case.

Scope: aiter uses the stage-1 MXFP8 quant only with fp8 activations. On main, #45480 runs DeepSeek-V4.1's MXFP4 experts on MXFP8 activations at every row count, so the fused quant is used by default; all results below set `AITER_BF16_FP8_MOE_BOUND=0`, which had the same effect before #45480. Where aiter picks bf16 or fp4 activations (for example DeepSeek-V4 at the default bound, or W4A4 MXFP4 models), the sort still computes the quant and aiter does not use it; that cost is not measured here. Credit: the sort kernel is from #44004; the end-to-end test follows #43822's test.
