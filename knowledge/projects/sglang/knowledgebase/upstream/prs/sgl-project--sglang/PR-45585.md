# [Fix] [SM100] quantization: Honor `deep_gemm` for 32x32 block-FP8 linears

[Upstream PR](https://github.com/sgl-project/sglang/pull/45585) · state: closed · merged: True

## Original PR description

- `--fp8-gemm-backend=deep_gemm` now runs `[32, 32]` block-FP8 linears with UE8M0 scales (DeepSeek-V4.1) on DeepGEMM on SM100, instead of falling back to Triton. DeepGEMM serves this recipe there with `sm100_fp8_fp4_gemm_1d1d`.
- SM100 DeepGEMM casts the fp32 block scales to UE8M0 itself, which is exact only for powers of two. Weight loading checks that every block32 weight scale is a power of two (as the Hopper BF16 path already does) and the linear keeps any other layer on Triton, so a checkpoint labeled `ue8m0` with other scales keeps working. Pre-quantized `(q, scale)` input stays on Triton on SM100, since nothing checks its scales.
- Block32 weights without `scale_fmt: ue8m0` stay on Triton on SM100. An explicit `deep_gemm` that still lands on Triton for a non-128 block layout now logs a warning.
- `test_warmup_memory` now also covers the block32 kernel type on Blackwell.
- Verified on B300 through the real linear layer: UE8M0 weights run on DeepGEMM and match the Triton path within BF16 rounding over 5 shapes; scales scaled off powers of two fall back to Triton with output identical to Triton; pre-quantized input runs on Triton. Layer latency (N=4096, K=7168) drops from 135 us to 23 us at M=1, and from 1011 us to 56 us at M=2048.

Behavior changes only for `--fp8-gemm-backend=deep_gemm` on SM100; `auto`, the other backends, and SM90 are unchanged.
