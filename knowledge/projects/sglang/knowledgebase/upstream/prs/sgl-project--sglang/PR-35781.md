# [Fix] mem_cache: extend dLLM volatile-block fix (#35270) to remaining radix caches

[Upstream PR](https://github.com/sgl-project/sglang/pull/35781) · state: open · merged: False

## Original PR description

## Motivation

A dLLM request's in-flight denoise block is rewritten in full on every step (`dllm_incomplete_ids`), and `_dllm_page_size` pins `page_size` to the dLLM block size, so that block is a whole trailing page of the radix key. Inserting it into the tree makes the next step's key diverge at the block boundary. That drives the prefix match below `cache_protected_len`, inverts the `free_segment` slice (freeing nothing), and leaves the tree owning two nodes for the same physical pages. `evictable_size()` then exceeds what the pool holds, and the idle pool-invariant check trips (#35270).

#35470 (still open) fixes this for the plain `RadixCache`. This PR carries that commit, with the original authorship preserved, and extends the fix to `UnifiedRadixCache`, the tree production runs (per @rwang5203's review).

## Change

On current `main`, `cache_unfinished_req` is gone and inserts go through `checkpoint(req, up_to=...)`. `mamba_radix_cache.py`, `swa_radix_cache.py` and `radix_cache_cpp.py` no longer exist either. So the fix is applied at the call sites that exist now:

- `ReqDllmMixin.get_cacheable_fill_ids()` (from #35470): the fill ids minus the in-flight block.
- `ReqDllmMixin.cacheable_checkpoint_len(up_to)` (new): clamps a checkpoint length to where the in-flight block starts. `checkpoint` slices `full_untruncated_fill_ids[:up_to]` directly rather than calling `get_fill_ids()`, so it needs a length, not an id list.
- `RadixCache.checkpoint` and `UnifiedRadixCache.checkpoint` clamp `up_to` with it. `PureSWARadixCache` inherits `RadixCache.checkpoint`, and `FlexKVRadixCache` and `LMCacheUnifiedRadixCache` call `super().checkpoint(...)`, so they pick up the fix too.
- `UnifiedRadixCache.advance_unpublished_req` inserts `get_cacheable_fill_ids()`.
- `SWAComponent` measures the out-of-window slot-free length from the cacheable ids.

Not changed: the external-store submission in `LMCacheUnifiedRadixCache.checkpoint`. It writes to external storage rather than the radix tree this bug corrupts, but it still passes the unclamped `up_to`, so the in-flight block can reach external storage. That is outside this PR. I can clamp it here if maintainers prefer.

## Tests

`test/registered/unit/mem_cache/test_radix_cache_dllm_volatile_block.py` (CPU, `register_cpu_ci`) has four tests: the cacheable-ids helper with an in-flight block and with a resolved block, and the #35270 over-count regression on both `RadixCache` and `UnifiedRadixCache`. The regression builds real paged pools, rewrites one physical block under two different volatile keys, and asserts that `evictable_size() + protected_size()` never exceeds the tokens the tree owns.

Run locally on CPU against the current head: 4 passed. Reverting the `RadixCache` clamp makes `TestDllmVolatileBlockNotCached::test_accounting_does_not_exceed_owned_pages` fail. Reverting the `UnifiedRadixCache` clamp makes `TestDllmVolatileBlockNotCachedUnified::test_accounting_does_not_exceed_owned_pages` fail.

Five existing unit tests build hand-made request stand-ins. They now supply `cacheable_checkpoint_len` (returning `up_to`, or inheriting `ReqDllmMixin`) because `checkpoint` calls it. I ran those five files on this branch and on current `main`, and they give the same results on both. On Windows, `test_radix_cache_unit.py` fails the same tests on `main` too, so those failures are not caused by this PR.

Not covered: the `SWAComponent` slot-free length and `UnifiedRadixCache.advance_unpublished_req` have no dLLM-specific regression test. The existing disaggregation tests call `advance_unpublished_req` without an in-flight block. Both need device-backed pools that this repo has no CPU fixture for, and I have no GPU access.
