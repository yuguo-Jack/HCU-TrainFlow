# [Feat] sgl-router: Render MiniMax-M3 and M3.1 through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/47119) · state: closed · merged: True

## Original PR description

## Motivation

sgl-router renders and tokenizes chats itself for cache-aware routing and `input_ids` forwarding. MiniMax-M3 and M3.1 went through the generic Dynamo Jinja path instead. That path skips SGLang's M3-specific request handling, so these models stayed in the `Guarded` forwarding scope. This PR adds a MiniMax-M3 renderer to `rust/sglang-processor`, following the `processor-model-parity` skill and checked against fixtures, so every text chat forwards `input_ids`.

## Modifications

- `rust/sglang-processor/src/render/models/minimax_m3.rs` (new): picked by the checkpoint's `model_type == "minimax_m3_vl"` (Python's `is_minimax_m3`), with template detection as the fallback for callers without `config.json` (e.g. a `--chat-template` override, sgl-router's tokenizer files). Covers MiniMax-M3 and MiniMax-M3.1-Flash. It mirrors these steps from `serving_chat.py`:
  - `_validate_minimax_m3_request`: checks `thinking.type`, that a `root` message is first and appears at most once, and that tool calls and tool results pair up (ids as a set).
  - `_normalize_minimax_m3_request`: maps `thinking` and effort aliases onto `thinking_mode` / `reasoning_effort`, both before and after `--default-chat-template-kwargs` merge in.
  - `_canonicalize_tool_message_order(sort_text_runs=True)`: sorts tool results into tool-call order, because the template pairs them by position.
  - Tool arguments are parsed strictly. The template prints scalars with `{{ val }}`, so argument floats are printed as Python's `repr` prints them. This also covers integers beyond 64 bits, which orjson reads as floats.
  - Content is handled as the `openai` content format leaves it, with text parts concatenated as the template's `visible_text` does.
- `ChatFormatter::MiniMaxM3` variant wired through `render/mod.rs`, `loader.rs`, `template.rs`.
- `sgl-router/src/tokenizer/chat_formatter.rs`: MiniMax-M3 renders through the processor (`AllText` scope), with a unit test.
- `tests/scripts/generate_parity.py`: the stub server resolves `is_minimax_m3` from `config.json` instead of hard-coding `False`.
- Fixtures `tests/fixtures/parity/minimax-m3.1-flash.json` (rev `262ae683`) and `minimax-m3.json` (rev `d95e30cb`), 215 cases each, generated from the Python serving path.
- Docs: processor README, sgl-router README / REFERENCE (new MiniMax-M3 section).

Left to the engine (`known_gap` in the fixtures): media, floats in tool schemas (Dynamo's `tojson`), `-0` in tool arguments, `tool_reference` parts in tool results or alone in a turn, and a `chat_template` kwarg.

## Host behavior for declined and rejected requests

The renderer distinguishes two failure kinds, matching what Python does on each host:

- **Validation failures are hard errors.** Requests Python's `_validate_minimax_m3_request` / `apply_chat_template` rejects — a bad `thinking.type`, a misplaced or repeated `root` message, unpaired tool calls/results, reserved `chat_template_kwargs` — fail rendering. The engine 400s them, and sglang-server now does the same instead of falling back to the generic Jinja path (which would silently serve a late `root` or an unanswered tool call).
- **Genuinely unsupported requests decline.** Media, `-0` in tool arguments, `tool_reference` parts, floats printed unlike Python, and content-part lists with no text fall back: on sgl-router the chat leaves the `AllText` scope (engine renders), and on sglang-server the request renders through the generic template. These are the `known_gap` cases above, plus the empty-text-parts decline (a parts list joining to `""` is truthy in the template's content check, so Python renders an empty block rather than the default prompt — see the `system_empty_text_part` / `root_empty_text_part` fixture cases).

Not in this PR: porting the `minimax-m3` reasoning and tool parsers to `src/think` / `src/tool_call`. Until they're ported, the router's `lower_chat` returns `Unsupported("reasoning_parser")` and chats keep the engine's OpenAI route. This PR changes rendering only, for routing and `input_ids` forwarding.

File: `rust/sglang-processor/src/render/models/minimax_m3.rs` · line None

This turns a non-empty parts list into a string even when the joined text is empty, and that changes what the template's truthiness checks see. The M3 template does `{%- if system_message and system_message.content -%}` (and the same for `developer_message`).

For `{"role": "system", "content": [{"type": "text", "text": ""}]}`, Python hands the template a one-element list. That's truthy, so it renders an empty developer block. Here the template gets `""`, which is falsy, so it prints "You are a helpful assistant." The same happens on a `root` message, where it prints the MiniMax identity text. It also happens for `[{"text": ""}, {"type": "tool_reference", ...}]`. Under `AllText` the router then forwards these `input_ids`.

The smallest fix is probably to decline when a non-empty list joins to `""`:

```rust
fn join_text_parts(message: &mut Value) -> Result<(), RenderError> {
    if let Some(parts) = message["content"].as_array().filter(|parts| !parts.is_empty()) {
        let text: String = parts.iter().filter_map(|part| part["text"].as_str()).collect();
        if text.is_empty() {
            return Err(RenderError::Declined("content parts with no text".into()));
        }
        message["content"] = text.into();
    }
    Ok(())
}
```

Could you also add `system_empty_text_part` and `root_empty_text_part` cases to both fixtures?
