# [Feat] disaggregation: Pool-declared PD KV layout

[Upstream PR](https://github.com/sgl-project/sglang/pull/46358) · state: open · merged: False

## Original PR description

## Motivation

PD publishes a KV byte layout on the bootstrap server (`kv_args.kv_layout`, from `disaggregation.utils.get_pd_kv_layout`). It refuses to pair a prefill and a decode server that declare different layouts. Today only `DeepSeekV4TokenToKVPool` can declare one, via an `isinstance` special case. Other pools whose bytes are not the default layout have no way to say so. That includes out-of-tree platform pools, e.g. a Neuron pool that is head-major inside a page. Their peers then pair silently and exchange misinterpreted bytes. The heterogeneous-TP slice path assumes token-major rows (see the companion NIXL slice fix, which refuses declared layouts there).

## Modifications

- `KVCache.pd_kv_layout() -> Optional[str]`, default `None`, meaning the pool class's default layout. `DeepSeekV4TokenToKVPool` already defines this method, so it now simply overrides it.
- `HybridLinearKVPool.pd_kv_layout()` forwards to its `full_kv_pool`, since that is the pool whose KV bytes PD transfers.
- `get_pd_kv_layout` calls `pool.pd_kv_layout()` when the pool defines it, and returns `None` otherwise. The DeepSeek-V4 import and `isinstance` check are gone.
- The mismatch error message no longer names only the DSV4 flags.

There is no wire or behavior change for in-tree pools. DeepSeek-V4 declares the same string as before, and every other in-tree pool declares `None`, as before.

## How it was found

This came up while building an out-of-tree Neuron/Trainium platform plugin. Its KV pool lays a page out as `[head][token][dim]`, so it had to monkeypatch `get_pd_kv_layout` to declare that. Without the declaration, upstream's slice transfer wrote NHD-shaped descriptors into it.

## Open questions

- The bootstrap check only refuses when *both* sides declare a layout (`info.kv_layout is not None and self.kv_layout is not None`). A prefill that declares a non-default layout can still pair with a decode that declares `None` (the default layout). That keeps compatibility with servers that predate the field. Should a declared layout vs `None` be refused too, at least for layouts outside the DSV4 family? Or should pools be able to mark their layout as "must match exactly"?
- Should `SWAKVPool` (and other wrappers) also forward, or declare a combined layout?
