# [AMD] Register 8 MLA/quant/moe/hadamard JIT kernel tests for AMD CI

[Upstream PR](https://github.com/sgl-project/sglang/pull/30213) · state: closed · merged: False

## Original PR description

## Summary
- Second batch moving ROCm-portable JIT kernel correctness tests onto the registered `test/registered/jit/` path (the same mechanism NVIDIA uses via `register_cuda_ci`) by adding `register_amd_ci(est_time=..., suite="jit-kernel-unit-test-amd")`.
- Further closes the AMD-vs-NVIDIA "JIT kernels — separate AMD path" coverage gap on the [CI coverage dashboard](https://rocm.github.io/sglang-ci/coverage/).
- Follows batch 1 (#30212) and the established pattern (#29671, #29693, #29694, #29822).

Registered tests:
- `test_concat_mla.py`
- `test_set_mla_kv_buffer.py`
- `test_hadamard_jit.py`
- `test_timestep_embedding.py`
- `test_moe_lora_align_block_size.py`
- `test_per_token_group_quant_8bit.py`
- `test_per_tensor_quant_fp8.py`
- `test_moe_fused_gate.py`

Each keeps its `register_cuda_ci` lines unchanged; only an AMD registration (mirroring the CUDA base est_time) is added. NV-only kernels (nvfp4/marlin/cutedsl/flash-attn3-4/mxfp8/sm90), benchmarks, multi-GPU tests, `test_fused_eh_norm` (hard-skips on ROCm via `torch.version.cuda is None`), and `test_per_token_group_quant_8bit_v2` (module-level `ImportError` when the AOT op is unavailable) are intentionally excluded.

### ROCm results for this batch (per-test) — why it was closed

Source: `jit-kernel-unit-test-amd-rocm720` run [28768600693](https://github.com/sgl-project/sglang/actions/runs/28768600693) (MI325 / gfx942, `continue_on_error` so every file ran).

| Test | Result | Reason |
|---|---|---|
| `test_concat_mla.py` | ❌ fail | CUDA-only kernel: `concat_mla.cuh` includes `cuda_bf16.h` |
| `test_set_mla_kv_buffer.py` | ❌ fail | CUDA-only kernel: `set_mla_kv_buffer.cuh` includes `cuda/ptx` |
| `test_hadamard_jit.py` | ❌ fail | CUDA-only kernel: hadamard kernel includes `cuda_bf16.h` |
| `test_timestep_embedding.py` | ❌ fail | CUDA-only kernel: `timestep_embedding.cuh` includes `cuda_runtime.h` |
| `test_moe_lora_align_block_size.py` | ❌ fail | CUDA-only kernel: `moe_lora_align_kernel.cu` includes `cub/cub.cuh` |
| `test_per_token_group_quant_8bit.py` | ❌ fail | Compiles on ROCm; fp8 `float8_e4m3fn` TensorMatcher mismatch (functional gap, potentially fixable) |
| `test_per_tensor_quant_fp8.py` | ❌ fail | Same fp8 `e4m3fn` category (compiles; functional gap) |
| `test_moe_fused_gate.py` | ❌ fail | Fails to compile on ROCm (exact blocking include not cleanly captured) |

**Outcome:** 0/8 are ROCm-portable, so this PR was **closed** (superseded by #30212). The CUDA-only kernels are tracked for dashboard exclusion in ROCm/sglang-ci#297. The fp8 quant tests (`per_token_group_quant_8bit`, `per_tensor_quant_fp8`) are a genuine, potentially-fixable gap (e4m3fn vs fnuz on ROCm) and were intentionally **not** marked NV-only.
