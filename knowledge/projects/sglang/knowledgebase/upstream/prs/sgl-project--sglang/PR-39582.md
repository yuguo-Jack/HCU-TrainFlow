# [MoE] Add opt-in Hopper W4AFP8 block-scale DeepEP LL prototype

[Upstream PR](https://github.com/sgl-project/sglang/pull/39582) · state: closed · merged: False

## Original PR description

## Summary

This draft explores direct per-token-block W4AFP8 GEMM for DeepEP low-latency (LL) MoE on Hopper (SM90). Each token has one activation scale per 128-element block along K.

**Experimental and disabled by default: the current two-layer LL implementation is 2.7–4.5x slower than the existing CUTLASS path in the measured cases. This is not an EPLB bug fix or a demonstrated performance improvement.**

The prototype provides a working implementation for design discussion. Before considering a merge, we need to address the performance regression and evaluate model quality.

### Feedback requested

- Is direct per-token-block scaling a useful LL backend direction for SGLang?
- Should GEMM2 use dynamic per-token-block quantization, or retain the checkpoint's static activation policy?
- Which weight-scale layout, tile scheduling, and data-transfer changes should we prioritize to close the measured performance gap?

## How to try it

Use a Hopper SM90 GPU and a compatible W4AFP8 checkpoint. Enable the experimental backend with [`SGLANG_W4AFP8_CUTEDSL_LL=1`](sglang-main/python/sglang/srt/environ.py). Leave it unset or set it to `0` to use the existing CUTLASS LL path.

Run the following from the SGLang repository root, replacing the checkpoint placeholder:

```bash
PYTHONPATH=python SGLANG_W4AFP8_CUTEDSL_LL=1 python -m sglang.launch_server \
  --model-path <compatible-w4afp8-checkpoint> \
  --tp 8 --moe-a2a-backend deepep --deepep-mode auto \
  --max-running-requests 8 --chunked-prefill-size 512 \
  --context-length 4096 --mem-fraction-static 0.75 \
  --cuda-graph-bs-decode 8 --disable-prefill-cuda-graph
```

In this configuration, normal prefill retains the upstream implementation. LL decode uses the experimental kernel and decode CUDA Graph. Prefill CUDA Graph is outside this draft's scope.

The production LL wrapper calls the Hopper kernel directly. Unsupported hardware or an unavailable toolchain causes an error; it does not silently fall back to the Torch reference. Warm up the required kernel specializations before graph capture. See the tested software versions and local-checkpoint caveat below; the example is not a guarantee that every W4AFP8 checkpoint loads unchanged.

## Motivation and scope

The existing CUTLASS LL implementation correctly requantizes block-FP8 dispatch to a per-tensor activation scale. This is not a scale-discard bug fix: the prototype removes that bridge and changes GEMM2 from checkpoint static activation scales to dynamic block-FP8 quantization. Model-quality evaluation is still required.

Related work: #21101 (closed per-token proposal), #33669 (merged dtype/scaling fix), #35593/#35760 (merged requant support/tuning), #34694 (normal static-FP8 communication; intentionally outside this PR). Historical PR states were checked previously, not all refreshed for this submission. No claim of a globally novel kernel.

## Implementation

- Signed INT4 (two values/byte, low nibble first) is unpacked exactly into E4M3 FP8; no scales are folded into rounded FP8 operands.
- Hopper WGMMA computes FP32 partial sums for each 128-element K block. Per-token activation scales and per-output-channel weight scales are applied to those partial sums before accumulation.
- Weight scales are per channel and K-group, **not 128x128 expert weight blocks**. Existing interleaving is inverted explicitly.
- Both MoE GEMMs use the new operator; SiLU/gating and intermediate block quantization reuse existing kernels. Output is BF16, masked rows are zero, and routing weights remain in DeepEP combine.
- Vectorized activation/packed-weight transfers, small-token transposed specializations, CTA-shared scales, empty-tile skipping, and small-token packed INT4-to-FP8 lookup decoding.
- Current-stream launches, device/specialization compilation caching, explicit prewarm requirement for graph capture, layout/device/dtype checks, and failure propagation.
- Keep standard and DeepEP-normal behavior unchanged. Add explicit LL backend-selection tests and numerical/graph tests that report failures rather than swallowing exceptions.

## Correctness and runtime validation

H800, Python 3.12, torch 2.13.0+cu129, sglang-kernel 0.4.6.post1+cu129, CuTe DSL 4.4.2, DeepEP 0.1.2+cu129, DeepGEMM 0.1.7+cu129. This is the tested subset, not the full upstream pinned dependency matrix.

```bash
PYTHONPATH=python python -m pytest \
  test/registered/unit/layers/moe/test_cutedsl_w4afp8_moe.py \
  test/registered/unit/layers/moe/test_cutedsl_w4afp8_gemm_per_token_block.py \
  test/registered/unit/layers/moe/test_w4afp8_deepep_dtype.py \
  test/registered/unit/layers/moe/test_w4afp8_deepep_post_reorder.py -q
```

Result: 26 passed, 2 skipped (opt-in benchmarks), 15 subtests passed. Independent FP32 references cover block scales, INT4 values, tails, empty experts, invalid rows poisoned with NaNs, two-layer LL, streams, changed masks/scales on graph replay, and device switching. Backend-selection tests use mocks only to verify dispatch, not numerical correctness.

Previous kernel iteration additionally passed Compute Sanitizer memcheck and targeted racecheck/synccheck/initcheck; sanitizer was not rerun after this final wrapper/selection cleanup.

Real locally quantized Qwen3.5-397B model on 8xH800, TP8/EP8: forced LL eager/decode graph smoke passed. After cleanup, auto mode (normal prefill -> LL decode) passed 8 paired requests against the old CUTLASS backend with identical output text; one counting prompt hit max_tokens=64, so it is a truncation parity check, not a successful full counting task. GPU traces from all 8 ranks show new Hopper kernels and cudaGraphLaunch. The auto-mode trace contains 240 new-kernel launches and 2 cudaGraphLaunch calls per rank.

**Reproduction caveat:** this local model required a separate ignored_layers/ignore + fused in_proj_ba loader compatibility patch applied equally to both A/B servers. That patch is deliberately excluded here to avoid conflating existing community config work. The exact local checkpoint is not a public model artifact. Final rebased code was unit-tested; full model A/B was run immediately before rebase with that same LL implementation plus the loader patch.

PYTHONPATH=python SGLANG_BENCH_W4AFP8_AB=1 \
  python -m pytest test/registered/unit/layers/moe/test_cutedsl_w4afp8_moe.py \

The prototype is **2.7-4.5x slower** in these LL wrapper cases. Earlier 4-5x improvements were versus our initial correctness kernel, not mature CUTLASS.

Service auto/decode-graph smoke also regressed: serial short city-description request 3.335s new vs 0.563s old; max-64-token counting request 8.380s vs 0.981s. These are single-pass HTTP observations, not controlled TTFT/ITL/p99 benchmarks. No service speedup claimed.

## Not covered / merge blockers

- Performance regression and lack of systematic quality/logits evaluation.
- No long-duration stress, multimodal validation, full CI or hardware/toolchain matrix.
- Prefill CUDA Graph is outside this LL PR; tested auto servers disabled it. Forced-LL default prefill graph hit a dispatch capacity assertion and was not repaired here.
- Weight scales are converted on each call; dense allocation capacity limits the small-token specialization benefit.
- Profiling counter permissions unavailable; no definitive occupancy/stall/DRAM-counter diagnosis.
- No DCO sign-off added on behalf of the contributor.
