# [Rust] Let an embedding package wrap the frontend HTTP app

[Upstream PR](https://github.com/sgl-project/sglang/pull/43924) · state: closed · merged: True

## Original PR description

## Motivation

A package that embeds the Rust frontend through the `sglang-server` crate can already supply its own multimodal processor (`Server::start_mm_workers_with_processor`), but it cannot act on HTTP traffic: `runtime::start` assembles the axum app and serves it internally, with no seam for an embedding package to add a route or a middleware. A package that wants, say, its own health probe route, or a middleware that stamps a response header on the built-in routes, has no way to do it short of forking the frontend.

## Modifications

- `HttpLayer` (in `lib.rs`): `Arc<dyn Fn(axum::Router) -> axum::Router + Send + Sync>`, a function from the assembled app to the app to serve.
- `Server::start_with_http_layer`: `Server::start` plus an optional `HttpLayer`. `Server::start` (the Python constructor) now delegates to it with `None`, so the Python server is unchanged.
- `runtime::start(cfg, http_layer)` carries the layer to `http::app::serve`, which applies it right after `with_state`: inside the access log, so an added route is logged like any built-in one, and before the prefill-only PD bootstrap registry is merged, which keeps its own state and is not wrapped.
- Existing `start(cfg)` callers in tests pass `None`.

Verified locally in `rust/`: `cargo fmt --all -- --check`, `cargo clippy --locked -p sglang-server --all-targets -- -D warnings`, and `cargo test --locked -p sglang-server` pass. The new test `http_layer_wraps_the_served_app` boots the runtime with a layer that adds a route and a response-header middleware: the added route serves, and `/model_info` still answers 200 and carries the header.
