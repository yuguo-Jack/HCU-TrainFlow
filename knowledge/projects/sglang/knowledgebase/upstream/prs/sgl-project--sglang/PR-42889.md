# [Perf] Serialize OpenAI chat/completion responses in one pass

[Upstream PR](https://github.com/sgl-project/sglang/pull/42889) · state: closed · merged: True

## Original PR description

This is the `main` counterpart of #42834 on `sglang-miles`, which becomes its cherry-pick once this merges. The diff is identical; the measurements below were taken with it on `sglang-miles` (`f19dcfb12`).

## Motivation

RL rollouts that request `top_logprobs` through `/v1/chat/completions` (non-streaming, `return_meta_info=True`) spend most of the extra latency after the engine has finished. On an H200 box, a 160-token response took about 7 ms from `response_sent_to_client_ts` to the client at `top_logprobs=0`, and about 380 ms at `top_logprobs=128`. Decode throughput was unchanged.

The chat, completion and SageMaker `/invocations` endpoints return the pydantic response model to FastAPI. With no `response_model` or `response_class`, FastAPI then runs `jsonable_encoder`: `model_dump(mode="json")`, then a pure-Python walk over the whole dumped payload, then stdlib `json.dumps`. With top-k the payload holds `completion_tokens * k` candidates twice: `choices[].logprobs` and `meta_info.output_top_logprobs`. That makes the Python walk the dominant cost, and it runs on the HTTP/TokenizerManager event loop.

## Modifications

- `utils/json_response.py`: add `model_json_response`. It renders a pydantic result with `model_dump_json(by_alias=True)` in one pass and passes any other result (for example an error `ORJSONResponse` or a `StreamingResponse`) through unchanged.
- `http_server.py`: use it for `/v1/completions`, `/v1/chat/completions` and `/invocations`.
- `OpenAIServingChat` and `OpenAIServingCompletion` still return models, so the Anthropic adapter, token scoring and the gRPC bridge are unaffected.
- **Why not `response_model=`:** FastAPI ≥ 0.141 also serializes a declared `response_model` with pydantic's `dump_json`. SGLang doesn't pin FastAPI, and these routes return unions of models and `Response` objects, so the helper gives one pass on any FastAPI version.
- **Scope:** only the three routes that return chat/completion responses change; they carry the large top-k payloads. `/v1/embeddings`, `/v1/classify`, `/tokenize`, `/detokenize`, `/v1/score`, `/v1/decisions`, `/v1/rerank` and `/v1/systemone` still go through `jsonable_encoder`. Moving every route (e.g. in `ORJSONRoute`) changes serialization for their downstream consumers and needs its own testing, so it's left for a follow-up.

**Behavior:**
- **Same values.** The JSON values match FastAPI's output, aliases included. FastAPI's encoder is `model_dump(mode="json", by_alias=True)` plus a no-op walk. Float spelling can differ (for example `1e-05` vs `0.00001`), but the parsed values are equal.
- **Non-finite floats are unchanged.** `-inf`/`NaN` logprobs serialize as `null` on both paths: the chat and completion response models' wrap `model_serializer`s already map them on FastAPI's path, and `model_dump_json` does the same.

## Accuracy Tests

No model-output change. On the H200 host, I posted the real `http_server.app` `/v1/chat/completions` route with a stubbed serving object. The response was built by `_build_token_logprobs_from_raw` with the Qwen3.5-9B tokenizer and carried `meta_info` top-k. I compared the bodies from `f19dcfb12` and from this branch:

| completion tokens × top_logprobs | values equal | bytes equal |
|---|---|---|
| 160 × 0 | yes | yes |
| 160 × 32 | yes | yes |
| 160 × 128 | yes | yes |
| 1000 × 32 | yes | yes |
| 1000 × 128 | yes | no (float spelling only) |

## Speed Tests and Profiling

Same setup, real endpoint, median of 7, CPU only:

| completion tokens × top_logprobs | body | before | after |
|---|---|---|---|
| 160 × 0 | 25 KB | 3.2 ms | 0.9 ms |
| 160 × 32 | 0.68 MB | 79.8 ms | 13.2 ms |
| 160 × 128 | 2.6 MB | 310.4 ms | 52.8 ms |
| 1000 × 32 | 4.2 MB | 830.1 ms | 85.0 ms |
| 1000 × 128 | 16.4 MB | 2554.0 ms | 391.6 ms |

At 160 × 128, this accounts for most of the ~380 ms measured end to end. The remaining top-k cost is outside this PR and could be follow-ups:
- `_build_token_logprobs_from_raw`: about 77 ms locally for 160 × 128, from per-candidate `token_id_to_bytes` and pydantic construction.
- Per-position single-token `batch_decode` in `TokenizerManager.detokenize_top_logprobs_tokens`.

## End-to-end on H200

The `sglang-miles` version of this change (#42834) ran in the patched stack of the end-to-end check in #42838 (Qwen3.5-9B on H200 behind the miles session server and gateway): k=0 and k=128 requests, 32-way concurrency and three short training runs, with no serialization errors. With greedy decoding, the patched engine's nested response gives the same tokens and top-k candidates as `f19dcfb12`'s. Most of the latency gain there comes from #42838, which shrinks the payload this PR serializes.
