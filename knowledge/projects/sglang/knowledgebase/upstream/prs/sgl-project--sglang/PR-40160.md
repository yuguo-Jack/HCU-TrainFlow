# [DeepSeek V4.1] an FP8 Tensor Core path for the FP4 grouped indexer

[Upstream PR](https://github.com/sgl-project/sglang/pull/40160) · state: closed · merged: False

## Original PR description

## Motivation

DeepSeek-V4.1 verification rows from the same request score the same FP4 index-K cache. The existing Triton path decodes K independently for each query row; capacity-sized CUDA Graphs also leave substantial work on invisible positions.

This PR adds an opt-in SM90 grouped indexer that converts packed E2M1 to E5M2 in shared memory and uses FP8 WGMMA, reusing each decoded K tile across query rows. Hopper has no native MXFP4 MMA. The grouped path preserves the existing BF16 rounding points, ReLU, head weighting, and reduction order.

## Changes

- Optimize scale decoding in the existing SM90 Triton fallback.
- Add a grouped CUDA path for H64/D128 request-major verification rows, with one query per warpgroup and shared K tiles of 64 positions.
- Retain up to six decoded Q rows across 2/4/8 K tiles, with shape-dependent dispatch.
- Compute `group_max_len` on device, skip completely invisible chunks/tiles, and write `-inf`. Partial tiles avoid reading invalid `req_to_token` entries.
- Add a persistent scheduler: parallel device-side length loading, visible-chunk prefixes, a bounded resident CTA grid, and chunk sizing based on actual visible work. Q remains resident across assigned chunks from the same group.
- Add a three-stage pipeline: `cp.async` loads packed tile i+2 while CUDA cores decode tile i+1 and WGMMA consumes tile i. Unaligned cache addresses retain a scalar-load fallback.
- Extend registered tests for invisible tiles, partial groups, and CUDA Graph replay after changing lengths.

### Dispatch and compatibility

`fp4_index_logits_grouped_sm90(..., implementation=...)` accepts:

| Value | Behavior |
|---|---|
| `"auto"` (default) | Shape-dependent rectangular grid with Q residency and visibility skipping |
| `"persistent"` | Schedule visible chunks on a resident grid |
| `"pipeline"` | Persistent scheduling plus asynchronous packed-load/software-decode/WGMMA overlap |

The grouped path remains opt-in; it is not enabled globally. `auto` does not automatically select persistent/pipeline. Measurements below show that the best mode depends on shape and visibility.

Scheduler metadata is CTA-local shared memory, recomputed on every invocation and graph replay. There is no CPU length readback, global allocation/counter, or request-slot scratch. Persistent modes support up to 1024 request groups and six rows per group, falling back to the single-tile path for larger inputs. Random physical slots, partial final groups, per-row lengths, compression ratios 1/2, and padded output/cache strides are supported.

### Numerical behavior and resources

Packed FP4 block scales are factored into a common power-of-two scale, restored after FP8 accumulation, and followed by the existing BF16 dot rounding, ReLU, BF16 weighted-product rounding, FP32 head reduction tree, and final BF16 rounding.

H20 resource usage for the current four-warpgroup implementations:

| Variant | Registers/thread | Shared memory | Resident CTAs/SM | Spills |
|---|---:|---:|---:|---|
| Q-resident rectangular grid | 64 | 63,872 bytes | 2 | None |
| Persistent | 64 | 80,000 bytes | 2 | None |
| Pipeline | 64 | 105,600 bytes | 2 | 24-byte stack frame; 20 bytes each of spill loads/stores |

SASS inspection confirms QGMMA issuance, subsequent packed LDGSTS and software decode, then WARPGROUP.DEPBAR. The final build has no WGMMA serialization warning. The pipeline does not consistently outperform serial persistent scheduling.

## Validation

Executed on H20:

- 23 independent configurations: widths 1–1025, query group sizes 2/3/4/5/6/7/9, partial groups, pages 16/64, ratios 1/2, random physical slots, varying lengths including zero, padded strides and output guards. Applicable variants match the prior CUDA implementation bit for bit; an independent integer-dot oracle also matches.
- Three registered tests pass through the real Python/custom-op/JIT entry, including all three implementations against Triton with changing graph-replay visibility.
- Additional graph checks cover long → empty → short → long transitions, poisoned invisible slots and unaligned table strides; outputs match exactly.
- Metadata-capacity/fallback checks at 257, 1024 and 1025 groups, and group size nine pass.
- Full 23-case Compute Sanitizer memcheck/racecheck/synccheck: zero errors or hazards. Additional graph and metadata-boundary memcheck runs also pass.
- Pre-commit checks pass, including registered-test validation.

## Performance against the visibility-pruned Triton implementation

Comparison target: #40431 at `f9d444b20fb19ebf391712c91e5bdaccb35dc77d`, using its unmodified `fp4_index_logits_decode`.

Environment: NVIDIA H20, PyTorch 2.11.0+cu130, Triton 3.6.0. All paths in the tables ran in the same environment. All comparisons use H64/D128, group size six, page size 64 and compression ratio two. The H32 numbers in #40431's description are not reused here.

Both paths receive identical FP4-representable BF16 Q, head weights, packed K, request mapping and visible lengths. Model-side fake quantization is shared upstream and excluded. Timing uses CUDA Graphs with ten calls per replay and nine randomly interleaved rounds; figures are medians in microseconds. Capacity and visibility are compressed positions.

### Including caller preparation

Triton includes the exact slots preparation in #40431's caller: arange, visibility mask, req_to_token gather, int64 conversion, division by ratio, and masked_fill. CUDA includes its additional Q packing and directly reads req_to_token. Shared upstream query/head-weight generation and downstream top-k/attention are excluded.

| 95 | 4,096 | 4,096 | 590.38 | 156.31 | 167.51 | 169.51 |
| 383 | 4,096 | 4,096 | 2,324.02 | 534.39 | 560.33 | 562.92 |

| 384 | 16,384 | 512 | 702.04 | 225.66 | 213.05 | 208.51 |

| 96 | 524,448 | 4,352 | 3,749.59 | 383.61 | 349.65 | 348.95 |

The two large-capacity cases show **3.61–3.77× logits-only speedup** and **10.75–11.57× including preparation** for pipeline. Avoiding the capacity-sized slots intermediate contributes substantially to the latter. Persistent and pipeline are close; small/short workloads can still favor Triton, and full-length workloads often favor CUDA `auto`.

All 18 measured configurations and eight paths per configuration produce bit-identical logits and masks, with matching selected top-k sets. Every graph is replayed after poisoning its output and checked against eager execution.

These are synthetic operator measurements, not model-level TPOT or throughput claims. Equality on these inputs does not establish equivalence for arbitrary scale patterns or nonfinite inputs.
