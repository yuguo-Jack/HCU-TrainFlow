# Qwen3.5 CUDA shared-expert fusion and checkpoint loading fixes

[Upstream PR](https://github.com/sgl-project/sglang/pull/40350) · state: closed · merged: False

## Original PR description

## Motivation

Refs #33706. This continues the CUDA shared-expert opt-in for Qwen3.5 / Qwen3.6 MoE, including the FP8 checkpoint and EAGLE/MTP configuration in the issue.

**Draft — performance acceptance is not met.** The implementation and loading regressions are covered, but automatic fusion currently regresses several end-to-end cases on SM120. This should not merge as-is; the measurements below explain the remaining blocker.

## Modifications

- Enable the existing fused shared slot for CUDA Qwen3.5 MoE and load its weights/scales in the multimodal, pure-text, and MTP entry points. Handle packed routed/shared weights independently of checkpoint iteration order.
- Preserve `--disable-shared-experts-fusion`; reject incompatible MoE/A2A backends, quantization, shared/routed precision mismatches, and redundant expert layouts before constructing the model.
- Reuse the existing fused shared-gate append kernel and remove unnecessary stream waits when the shared MLP executes inside the routed MoE.
- Extend existing registered unit fixtures with eligibility and numerical weight-loading regressions. No new flag or production kernel is added.

## Accuracy Tests

RTX PRO 6000 Blackwell Server Edition (SM120), TP=1, `Qwen/Qwen3.6-35B-A3B-FP8`, PyTorch 2.13 / CUDA 13, upstream base `567d5925fe896a7b70043271f5621d6fe6e650d4`.

- 51 unit tests passed across the fusion eligibility and Qwen3.5 loading fixtures, including 24 loading combinations spanning three model entry points, separate/packed weights, FP8 scales, and both loading orders. The new loading regression fails against unmodified upstream (17 subcases).
- All 7 existing fused-append GPU tests passed on SM120.
- Real FP8 layer outputs passed numerical comparisons at M=1,4,8,16,32,64,128,512,2048.
- Ordinary serving: both variants answered all 12 fixed smoke prompts correctly. Across 95 scored input tokens, mean absolute logprob difference was 0.0472 (maximum 0.6356); top-1 agreement was 92/95. This is diagnostic coverage, not a claim of broad accuracy equivalence.

- EAGLE/MTP: both variants answered all 12 smoke questions correctly. GSM8K (5-shot, same 64 questions disjoint from the shots, temperature 0, chat API with thinking disabled, max 1024 output tokens): separate **62/64**, fused **62/64**. There were 0/0 length-truncated answers respectively. This small comparison is diagnostic coverage, not a full accuracy qualification.
- EAGLE input-logprob diagnostic: 95 tokens, mean absolute difference 0.0472, maximum 0.6356, top-1 agreement 92/95.

## Speed Tests and Profiling

Both variants use the same source and server arguments; the baseline adds `--disable-shared-experts-fusion`:

```bash
python -m sglang.launch_server --model-path Qwen/Qwen3.6-35B-A3B-FP8 \
  --tp-size 1 --attention-backend triton --sampling-backend pytorch \
  --fp8-gemm-backend cutlass --mem-fraction-static 0.8 \
  --context-length 8192 --max-running-requests 16 \
  --cuda-graph-bs-decode 1 2 4 8 16 --disable-radix-cache \
  --reasoning-parser qwen3 --tool-call-parser qwen3_coder
```

For EAGLE/MTP, append the issue's settings:

```bash
--speculative-algorithm EAGLE --speculative-num-steps 3 \
--speculative-eagle-topk 1 --speculative-num-draft-tokens 4 \
--mamba-radix-cache-strategy extra_buffer
```

Benchmarks use `sglang.benchmark.serving --dataset-name random-ids --random-range-ratio 1.0 --request-rate inf --seed 42` with the input/output lengths and concurrency below. Prefill-only rows report input tokens/s; other rows report output tokens/s. The non-speculative comparison below was rerun with both servers explicitly reporting `speculative_algorithm=None` and no draft model. Each case has four rounds with request warmup; round 0 is uniformly excluded as extra warmup, and the table averages rounds 1–3. Baseline ran first, then fusion. Request counts, input token counts, and output token counts match exactly between the variants.

EAGLE acceptance also changes between the FP8 numerical paths: after the concurrency-8 decode phase, the benchmark reports cumulative acceptance lengths of 3.3102 (separate) and 3.4504 (fused). These are cumulative server counters, not isolated per-case rates. Consequently, an EAGLE throughput gain cannot by itself establish that the fused kernels execute faster.

Full-server variants were measured sequentially on one GPU with default clocks and a small repetition count; small differences are not a statistical performance qualification.

Single-layer profiling/tuning used actual checkpoint weights and CUDA graphs. Cold-L2 CUPTI timings measure the complete kernel span, rather than summing kernels that overlap across streams or include PDL dependency waits.

- The separate shared MLP already overlaps routed-expert execution. Removing its kernels does not remove all their time from the critical path.
- Adding the shared slot changes top-k from 8 to 9. At M=4, the tiny pairwise aligner grows from a 32-element to a 64-element tile; at M=8, 72 pairs exceed its 64-pair fast-path limit.
- Giving both variants a 24-configuration GEMM search per shape left small-batch fusion slower and most larger shapes approximately tied; no broadly faster configuration emerged.
- Temporary sort/scan and gate-in-router prototypes passed numerical checks but did not establish a broad win. They are excluded from this PR.

The remaining work is a demonstrably faster implementation across both prefill and decode, followed by wider accuracy and hardware validation. TP>1 and ROCm were not exercised here.
