# [Fix] reasoning_parser: Promote a closed think block to content at stream end under force_nonempty_content

[Upstream PR](https://github.com/sgl-project/sglang/pull/44572) · state: open · merged: False

## Original PR description

## Motivation

With `force_nonempty_content` on, a reply that puts its whole answer inside a closed think block (`<think>The answer is 42.</think>` and then EOS) gets that text as `content` when `stream=false`, but `content` stays empty when `stream=true`. Avoiding the empty answer is the reason for the option, so streaming clients do not get what it promises.

The option is on when a request sets `chat_template_kwargs={"force_nonempty_content": true}`, and `granite_thinking_parser` sets it automatically for `enable_thinking=false`.

The cause is in `BaseReasoningFormatDetector`. `parse_streaming_increment` keeps the streamed reasoning so `finish()` can promote it at stream end, but it resets that copy as soon as `_in_reasoning` is false. That happens in the same call that sees `</think>`, so the copy is gone before `finish()` runs, and `finish()` only promotes while still inside reasoning (the truncated case `test_streaming_truncated_reasoning_reclassified_on_finish` covers).

## Modifications

Both changes are in `BaseReasoningFormatDetector`.

- `parse_streaming_increment` keeps the streamed reasoning until real content arrives, not until the think block closes. `MuseGlimmerDetector`'s streaming path already uses this rule.
- `finish()`, outside reasoning, returns that reasoning as content when the flag is on and the stream has sent no content.
- Streaming strips only the first `<think>`, so before promoting, `finish()` strips any repeated leading openers (`<think><think>...`), as `detect_and_parse` does. Both paths now use one helper, `_strip_repeated_think_starts`.

A reply with any content after `</think>`, a tool-start token that ends reasoning, or the flag off behaves as before. As on the truncated path, the streamed `reasoning_content` stays as sent, because streaming cannot take it back. Detectors with their own streaming path (`Apertus2509Detector`, `KimiK3Detector`, `CohereCommand4Detector`) are unchanged.

## Accuracy Tests

The same model text went through the real `OpenAIServingChat`: `_build_chat_response` for `stream=false`, and `_generate_chat_stream` with cumulative text per step and `finish_reason` stop on the last step for `stream=true`. There was no model inference.

```
model output: <think>The answer is 42.</think>

parser                    chat_template_kwargs                stream=false content   stream=true content (before)   stream=true content (after)
qwen3                     {"force_nonempty_content": true}    'The answer is 42.'    ''                             'The answer is 42.'
nemotron_3                {"force_nonempty_content": true}    'The answer is 42.'    ''                             'The answer is 42.'
granite_thinking_parser   {"enable_thinking": false}          'The answer is 42.'    ''                             'The answer is 42.'
```

New test `TestStreamingChunkSizeInvariance.test_force_nonempty_closed_block_content_matches_one_shot` streams each input at every chunk size that class uses (1 to 1000 characters), with `stream_reasoning` on and off, and compares the streamed content with `detect_and_parse`. On `main`, 32 of its 48 subtests fail (`'' != 'All reasoning, no answer'`). With this change all pass. The subtests with content after `</think>` check that no promotion happens there.

`test/registered/unit/parser` passes: 512 tests. `test/registered/unit/entrypoints/openai/test_serving_chat.py` gives the same result with and without this change (151 pass; 5 DeepSeek-V3.2/V4 and Kimi-K3 encoding tests fail on this machine for both).

Strip repeated openers from the streaming candidate before promotion.
