# [Fix] [NVIDIA] allreduce: Stage VMM graph inputs in CustomAllreduce instead of IPC-registering them

[Upstream PR](https://github.com/sgl-project/sglang/pull/44448) · state: open · merged: False

## Original PR description

## Motivation

On PCIe-only boxes, `CustomAllReduceV2` requires full NVLink, so sglang falls back to the legacy v1 `CustomAllreduce`. When `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` is set (the Qwen3.8-Flash-Next cookbook recommends it for long contexts), CUDA-graph inputs come from `cuMemCreate` memory. During capture v1 records those pointers, and `register_graph_buffers` -> `get_graph_buffer_ipc_meta` calls `cudaIpcGetMemHandle` on them, which only accepts `cudaMalloc` memory. The server dies during graph capture with `RuntimeError: invalid argument`. This is attempt 1 in #44291.

Reproduced on 2x RTX PRO 6000 Blackwell Server Edition (sm_120, PCIe, no NVLink, P2P OK), `lmsysorg/sglang:dev-cu13` at a6a8c5601, `Qwen/Qwen3-0.6B`, `--tp-size 2`:

| Run | Result |
|---|---|
| default allocator | boots, v1 registers 2850 + 2052 graph addresses |
| `expandable_segments:True` | `RuntimeError: invalid argument` in `get_graph_buffer_ipc_meta` |
| `expandable_segments:True` + `SGLANG_ENABLE_PCIE_IPC_ALLREDUCE=1` | same failure; v1 still captures alongside PCIe-IPC |
| `expandable_segments:True` + this PR | boots, same output as the default run at temperature 0 |

## Modifications

- `python/sglang/srt/distributed/device_communicators/custom_all_reduce.py`: during capture, an input that is VMM memory (checked with the existing `is_vmm_pointer`) goes through the staged path, which copies it into v1's pre-registered `cudaMalloc` IPC buffer. That is the path `SGLANG_MEMORY_SAVER_CUDA_GRAPH` already uses, so no kernel or sgl-kernel change is needed. Non-VMM inputs keep the registered path exactly as before. The check is per input, so it also covers the memory saver and symmetric-memory pools, and it only runs at capture time.
- `test/registered/kernels/ops/communication/test_custom_all_reduce_v1_vmm.py`: new 2-GPU test that runs v1 under `expandable_segments`, captures 4 all-reduces per graph (inputs from a plain tensor and from the graph's own pool), and compares against NCCL exactly.

Why not zero-copy like v2's `VmmGraphInputManager`: v1's graph slots only take `cudaIpc` handles, so zero-copy would need a new AOT op and an sgl-kernel release. Staging reuses a path that is already in production.

## Accuracy Tests

- New test on the PCIe pod: without this PR `1 failed, 1 passed` (`test_graph_all_reduce_matches_nccl[16-False]` raises `RuntimeError: invalid argument`); with it `9 passed`.
- Server: with `expandable_segments` + this PR, the smoke request returns the same text as the default allocator at temperature 0.
- Default path with this PR (registered inputs, default allocator): exact match to NCCL at every size from 2 KB to 8 MB.

## Speed Tests and Profiling

Decode with `sglang.benchmark.one_batch_server`, `Qwen/Qwen3-0.6B`, TP2, input 256, output 128, steady-state tok/s:

| Batch | main, default allocator | this PR, default allocator | this PR, `expandable_segments` |
|---|---|---|---|
| 1 | 704 | 705 | 681 |
| 8 | 3988 | 3995 | 3883 |
| 32 | 12261 | 12310 | 12030 |

Default users see no change. `expandable_segments` users go from a crash at startup to 2-3% below the default allocator.

Per all-reduce, 8 captured per graph, median of 2 runs:

| Size | v1 registered (default allocator) | v1 staged (`expandable_segments`) | pynccl |
|---|---|---|---|
| 2 KB | 4.58 us | 5.38 us | 12.39 us |
| 16 KB | 5.25 us | 6.13 us | 14.39 us |
| 1 MB | 42.0 us | 43.1 us | 47.7 us |

Staging adds about 0.8 us at decode sizes and stays 2.3-2.7x faster than falling back to pynccl.
