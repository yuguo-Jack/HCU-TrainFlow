# [Perf] scheduler: Refresh PD prefill bootstrap-queue prefixes in the waiting-prefix LRU pass

[Upstream PR](https://github.com/sgl-project/sglang/pull/46812) · state: closed · merged: True

## Original PR description

## Motivation

#41593 keeps waiting requests' device prefixes warm by touching them in the radix LRU on each refresh pass. On a PD prefill worker it walks only `waiting_queue`. Requests still in `disagg_prefill_bootstrap_queue`, which are waiting for decode to pre-allocate their slots, are never touched. When decode is full, the bootstrap queue is the deep one, and those prefixes age out while the requests wait. Each evicted prefix is then reloaded from the external (L3) tier or recomputed when the request is admitted. That slows prefill, lengthens the wait for everyone behind it, and evicts more prefixes, so the loop feeds itself.

We hit this serving DeepSeek-V4.1-Flash on GB300 with 9 DEP2 prefill workers and one DEP16 decode worker, using an agentic multi-turn trace at 7480 concurrent sessions and a Mooncake L3 tier. After the client's turn burst, the bootstrap queue held about 300 requests per prefill rank, each waiting about 100 s. Device-radix hits fell from about 65 % to 22 % of prompt tokens and L3 loads rose to 73 %. Prefill throughput collapsed and did not recover within the run. The router kept 95-98 % of turns on their session's previous worker throughout, so the prefixes were evicted while the requests waited, not routed away.

**Impact**
- The gain below is not a speedup of healthy serving. It comes from preventing this throughput collapse: with the fix, prefill recovers from the turn burst instead of staying stuck in the evict-and-reload loop.
- Only PD prefill workers whose bootstrap queue holds requests long enough for their prefixes to age out are affected. That needs decode to be the limit (slots full) and a live prefix working set at or above the device radix pool.
- Unaffected:
  - Non-PD servers and PD decode workers: the bootstrap queue is `None`, so the pass is the same as before.
  - Configurations #41593's gate already skips: cache-aware policies while they still match every waiting request (for example `lpm` with at most 128 waiting), non-LRU eviction policies, and `--disable-radix-cache`.
  - PD prefill whose bootstrap queue stays short, or whose working set fits the device pool: there is nothing left to evict, so eviction order does not change outcomes. The healthy-shape check is below.

## Modifications

- `SchedulePolicy.calc_priority` takes the PD prefill bootstrap queue. The scheduler passes `disagg_prefill_bootstrap_queue.queue`, or `None` when not running PD prefill.
- On the same refresh pass, `_touch_waiting_prefixes` touches up to `WAITING_PREFIX_REFRESH_BOOTSTRAP_MAX` bootstrap entries (512, a module constant next to the existing `WAITING_QUEUE_PREFIX_MATCH_MAX` and `WAITING_PREFIX_REFRESH_INTERVAL`) before the waiting queue, both in reverse order. The waiting-queue head therefore still carries the newest timestamp. No new environment variable: `SGLANG_ENABLE_WAITING_PREFIX_REFRESH=0` still turns the whole refresh off.
- The existing gate from #41593 is unchanged: cache-agnostic policy, LRU eviction, not decode, no fast match path, prefix sharing supported, and `SGLANG_ENABLE_WAITING_PREFIX_REFRESH` on. Non-PD and decode workers behave exactly as before.
- `test_scheduler_held_row_admission`'s `Scheduler` stub gains `disagg_prefill_bootstrap_queue = None` for the new argument.

Limits:
- Bootstrap entries are refreshed only on passes that reach `calc_priority`. The caller returns earlier when the waiting queue is empty or no request rows are free, so the bootstrap queue is not refreshed on its own.
- With more than 128 waiting entries, waiting entries past the first 128 are still not touched and can end up older than the refreshed bootstrap entries.
- The touch path is the one #41593 uses (`refresh_device_prefix` / `touch_prefix`). It never allocates or issues an external-tier lookup, including with the unified radix cache and the Mooncake external linker.

## Accuracy Tests

Not applicable: the change only reorders radix-cache eviction and does not affect model outputs.

## Speed Tests and Profiling

GB300, DeepSeek-V4.1-Flash FP4, one DEP16 decode worker, agentic multi-turn trace, 1200 s window, Mooncake L3 tier, simulated acceptance length 3.51. Dynamo frontend with its backend admission limits raised (`DYN_BACKEND_ADMISSION_*`), so waiting turns reach the prefill server as with Dynamo 1.6 and earlier.

**Collapse case, isolated on current main** (SGLang main at 5884e4fe, this PR only): 9 DEP2 prefill workers (max 64 running per rank), 7480 concurrent sessions.

| | main | with this PR |
|---|---|---|
| total throughput (tok/s/GPU) | 347,197 | **551,223** (+59 %) |
| p90 interactivity (tok/s/user) | 134.2 | 144.0 |
| p90 / p50 TTFT | 147 s / 60 s | 59.8 s / 31.5 s |
| throughput in minutes 10-20 | ~300k | ~620k |
| bootstrap queue p50 / p90 per prefill rank | 320 / 402 | 178 / 254 |
| prompt tokens from L3 / device radix | 74 % / 20.5 % | 22 % / 73 % |
| decode running per rank | 19 | 52 |
| errors | 0 | 0 |

An earlier pair on main at 656331295, with four other open PRs (#46497, #46593, #46592, #46404) on both arms, showed the same: 361,815 → 560,412 tok/s/GPU, L3 share 73 % → 21 %. Each arm is a single run at an operating point that can settle in a healthy or a collapsed state; the effect repeated on both bases and is far larger than the 3-4 % run-to-run spread we see on this setup.

**Healthy shape** (10 DEP2 prefill workers, 6400 sessions, default Dynamo admission, main at 5884e4fe): throughput −2.5 %, p90 interactivity +1.8 %, steady state identical, i.e. neutral within noise. The bootstrap queue stays at p90 4 per rank there, so the new part barely engages.

**Refresh cost** (scheduler-thread time per refresh pass, timed in the runs above):

| | per refresh p50 / p90 / p99 / max | of which bootstrap part p50 / p99 | refreshes per rank | share of wall time |
|---|---|---|---|---|
| collapse case (bootstrap 92 p50, 327 p99 entries) | 40.6 / 74 / 100 / 272 ms | 17 / 72 ms | every ~16 s | 0.24 % |
| healthy shape | 7.9 / 25 / 35 / 44 ms | 0 / 1.7 ms | every ~12 s | 0.09 % |

Most of the healthy-shape cost is the existing #41593 waiting-queue touch (about 0.2-0.25 ms per touched request at these prompt lengths). A cap of 128 bootstrap entries would bound the new part near 25 ms, but it would leave queue positions 128-320 unprotected, which is where the collapse happened, so the cap stays at 512.
