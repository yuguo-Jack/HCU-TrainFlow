# [Fix] function_call: Stop GptOssDetector replaying streamed text and dropping tool calls

[Upstream PR](https://github.com/sgl-project/sglang/pull/41045) · state: open · merged: False

## Original PR description

## Motivation

A GPT-OSS response streamed with `--reasoning-parser gpt-oss` can show the client
the raw Harmony protocol, print the answer twice, and silently lose the tool call.

Serving hands the detector one decoded token at a time, so ordinary prose always
arrives in several pieces. That alone is enough to trigger it: the text before the
first marker is streamed out as it arrives, but it also stays in `HarmonyParser`'s
buffer, and the parser replays it the moment a marker shows up. No marker has to be
split for this to happen.

`GptOssDetector` keeps its own `self._buffer`, and it also feeds `HarmonyParser`,
which keeps one too. `parse_streaming_increment` accumulated every chunk into
`self._buffer`, but handed only the newest chunk to `self.harmony_parser.parse(...)`,
so the parser accumulated the same characters on its own copy. The detector then
cleared its copy without telling the parser, and every decision that reads
`self._buffer` as "the text seen so far" was looking at the wrong text:

1. The `not events` fast path flushed `self._buffer` as normal content whenever no
   *single chunk* happened to contain a complete marker. A marker split across
   chunks was therefore never held back, and the raw protocol block was streamed to
   the client as ordinary text.
2. Once the parser did emit an event, its own buffer was flushed on top of text that
   had already been streamed, so the prose was emitted a second time.
3. The `"<|channel|>commentary to=" not in self._buffer` guard tested a buffer that
   no longer held the call, so its early return --
   `StreamingParseResult(normal_text=..., calls=[])` -- discarded the `tool_call`
   events the parser had just produced. The call was lost.

## Reproduction

### Token-shaped chunks

Special tokens such as `<|start|>` are single tokens and are never split, while
ordinary text can break anywhere. Feeding `Let me check.` followed by the call
below as marker-atomic chunks, with the text between markers cut every N
characters:

| N | before `normal_text` | after `normal_text` |
|---|---|---|
| 1 | `'Let me check.Let me check.assistant'` | `'Let me check.'` |
| 2 | `'Let me check.Let me check.assistant'` | `'Let me check.'` |
| 3 | `'Let me check.Let me check.assistant'` | `'Let me check.'` |
| 5 | `'Let me check.Let me check.assistant'` | `'Let me check.'` |
| 8 | `'Let me check.Let me check.assistant'` | `'Let me check.'` |

The sentence reaches the client twice and the next piece of the protocol
(`assistant`) reaches it as ordinary text.

### Uniform chunks

Streaming
`<|start|>assistant<|channel|>commentary to=functions.get_weather<|constrain|>json<|message|>{"city":"Paris"}<|call|>`
through `parse_streaming_increment` + `finish`, with `get_weather` in `tools`:

| chunk | before `normal_text` | before `calls` | after `normal_text` | after `calls` |
|---|---|---|---|---|
| 1 | the whole block, `<\|start\|>assistant…<\|call\|>` | `[]` | `''` | `['get_weather']` |
| 2 | the whole block, cut at `<\|call` | `[]` | `''` | `['get_weather']` |
| 3 | the whole block, cut at `<\|call` | `[]` | `''` | `['get_weather']` |
| 5 | the whole block, `<\|start\|>assistant…<\|call\|>` | `[]` | `''` | `['get_weather']` |
| 8 | the whole block, cut at `<\|ca` | `[]` | `''` | `['get_weather']` |
| 13 | `''` | `['get_weather']` | `''` | `['get_weather']` |

With the prose prefix `Let me check.` streamed one character at a time, before:
`'Let me check.<|start|Let me check.assistant<|channel|>commentary to=…<|call|'`
with `calls == []` -- the sentence is duplicated *and* the call is gone. After:
`'Let me check.'` with the call returned.

## Modifications

`python/sglang/srt/function_call/gpt_oss_detector.py`

- While `HarmonyParser` has not seen a marker yet (`harmony_parser.strategy is None`
  and no marker in the buffer), plain content is streamed straight through,
  withholding only a tail that can still complete into a marker
  (`_split_at_partial_marker`, built on the existing
  `BaseFormatDetector._ends_with_partial_token`).
- Only text the parser has not already interpreted is handed to it, and the buffer
  is cleared at the moment it is handed over, so detector and parser can no longer
  hold the same characters twice.
- `finish()` releases a withheld tail when the stream ends instead of dropping it,
  unless it did complete into a marker -- that means the protocol block was
  truncated, which is not user-visible text. `FunctionCallParser` already calls
  `detector.finish(...)` at end of stream.
- Dropped the `"<|channel|>commentary to="` guard, which read the wrong buffer and
  was the direct cause of the lost calls.

`test/registered/unit/function_call/test_function_call_parser.py`

Five regression tests: a tool call split at every chunk size, two tool calls split
across chunks, plain text emitted as it arrives, a partial marker held until end of
stream, and a truncated protocol block not shown to the client.

## Tests

- `pytest test/registered/unit/function_call/test_function_call_parser.py -q` ->
  `255 passed, 122 subtests passed`.
- `-k TestGptOssDetector` -> `7 passed, 71 subtests passed`.
- Swapping the pre-change detector back in while keeping the new tests ->
  `54 failed, 6 passed`. Every added test fails on the old code.
- Exhaustive sweep over all chunk sizes 1..39 for four inputs (call only /
  prose+call / two calls / prose+call+prose) against the one-shot parse: 0 failures,
  and `normal_text` never contains `<|`.
- Token-shaped chunking (markers atomic, the text between them split every
  1/2/3/5/8 characters) over five inputs: the pre-change detector duplicates the
  prose and leaks `assistant` on the prose-then-call input at every split size; the
  new one is clean on all of them, and on the inputs where both agree the comparison
  is exact.
- `ruff check` and `ruff format --check` clean on both files.

## Out of scope

Two neighbouring defects show up in the same sweep and are deliberately not touched
here, both in `harmony_parser.py`:

- `CanonicalStrategy` leaks a complete `<|return|>` into `normal_text` for
  `final`-channel streams. The pre-change detector behaves the same way, so this is
  not a regression.
- `HarmonyParser._parse_partial_analysis` swallows the block that follows when the
  analysis block is split across chunks.

This PR does not modify `harmony_parser.py`; #41017 covers the parser-layer holding
behaviour separately.

Related to #37650, and worth separating explicitly from #37722: that PR releases `HarmonyParser`'s buffer at end of stream. This one is the layer below it — the detector and the parser disagreeing about what text has been seen.

`GptOssDetector` keeps `self._buffer` and also feeds `HarmonyParser`, which keeps its own. `parse_streaming_increment` accumulated every chunk into `self._buffer` but handed only the newest chunk to `self.harmony_parser.parse(...)`, so the parser accumulated the same characters on its own copy; the detector then cleared its copy without telling the parser. Every decision reading `self._buffer` as "the text seen so far" was reading the wrong text: a marker split across chunks was never held back and leaked as prose, already-streamed text was emitted a second time once the parser did emit an event, and the tool-call guard tested a buffer that no longer held the call.

Flushing the parser's buffer at the end does not address any of those three, since they happen mid-stream.
