# [Feat] [AMD] multimodal: Enable feature IPC transport on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/33747) · state: open · merged: False

## Original PR description

## Motivation

`--mm-feature-transport=cuda_ipc` was rejected on ROCm even though the implementation only uses PyTorch's CUDA-compatible APIs (`torch.cuda`, `_share_cuda_`), which dispatch to HIP IPC in a ROCm build. That forced every image feature tensor through the CPU shared-memory transport. On MI325X, a paired frontend profile attributed **0.73 s** to `wrap_shm_features` / `_wrap_shm_or_inline` for 128 concurrent image requests; HIP IPC wrapping is **0.02 s** (−97.3%).

## Modifications

- Accept `cuda_ipc` on CUDA **or** ROCm/HIP in `_handle_multimodal_feature_transport`. The single-node and multimodal-splitting guards are unchanged, and the public flag name stays `cuda_ipc`.
- Unit tests: ROCm acceptance (env-isolated with `patch.dict` — acceptance writes the legacy IPC env var and must not leak into later tests) and an explicit rejection test for non-CUDA-like platforms.

## Accuracy Tests

MI325X, Torch 2.9.1 + ROCm 7.2, BF16 (`HSA_ENABLE_IPC_MODE_LEGACY=1`):

- `test/registered/unit/server_args/test_server_args.py` passes; cross-process `test_cuda_ipc_transport.py` passes.
- Standalone HIP IPC probe — allocate → pooled share → reconstruct in a spawned process — returns the exact tensor (`torch.testing.assert_close`) with exactly one cached pool handle.

## Speed Tests and Profiling

Single-image serving workload (512×512, 268 input / 32 output tokens, 512 prompts, 1 warmup + 3 measured runs, one MI325X):

| Concurrency | CPU SHM | HIP IPC | Gain |
|---:|---:|---:|---:|
| 16 | 1,374 tok/s | 1,649 tok/s | +20.0% |
| 32 | 1,686 tok/s | 2,154 tok/s | +27.8% |
