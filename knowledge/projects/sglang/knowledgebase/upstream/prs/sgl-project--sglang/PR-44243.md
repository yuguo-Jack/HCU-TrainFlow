# [Fix] sglang-processor: Follow Python's OpenAI layer through #43027, #37577, #43006, #43026, #43005

[Upstream PR](https://github.com/sgl-project/sglang/pull/44243) · state: closed · merged: True

## Original PR description

## Motivation

sgl-router and the Rust server serve OpenAI chats through `/generate`, using `rust/sglang-processor` to do what Python's OpenAI layer does. Five Python changes merged to main after the processor's parity fixtures were recorded, so the Rust path no longer matches Python's:

| Python change | What the `/generate` path did instead |
|---|---|
| sgl-project/sglang#43027 — omit absent `tool_calls` | sent `"tool_calls": null` in chat messages and in tool-parsing stream deltas |
| sgl-project/sglang#37577 — request `watermark` | **served the request through `/generate` without the field**, so a client that asked for a watermark got unwatermarked output |
| sgl-project/sglang#43006 — DeepSeek honors `tool_choice: "none"` | still rendered every tool into DeepSeek-V4/V4.1 prompts (279 tokens instead of 5 for the fixture case) |
| sgl-project/sglang#43026 — stable stream `created` | stamped each chat stream chunk with the current time |
| sgl-project/sglang#43005 — report zero cached tokens | dropped `prompt_tokens_details` when the cached count was 0 under `--enable-cache-report` |

The fixtures were recorded before these changes, so the tests kept passing. I found the first two by running Qwen3.8-27B through the router against the engine's own `/v1/chat/completions` (sgl-project/sglang#43689). The other three surfaced when I regenerated the fixtures from Python on main.

## Modifications

- `openai/chat.rs`, `openai/completions.rs`: forward `watermark` into `sampling_params` (validation stays with the engine's tokenizer manager, which serves both routes); omit null `tool_calls` from unary messages and tool-parsing stream deltas; give each chat stream a single `created`.
- `openai/wire.rs`: keep `prompt_tokens_details` with `cached_tokens: 0` when cache reporting is on.
- `render/models/deepseek_v4.rs`, `deepseek_v41.rs`: render request tools only when `serving_chat` passes them on (`tool_choice` other than `"none"`, and a named choice must match a request tool). The tools are still validated either way, as pydantic does.
- Fixtures regenerated from Python on main: `openai_parity/*` (offline, reusing the recorded engine outputs), the DeepSeek render fixtures in `tests/fixtures/parity/`, and sgl-router's `tests/fixtures/deepseek/`. Added synthetic `watermark` cases for chat (GLM-5.3) and completions (DeepSeek-V4-Flash-0731).
- `tests/openai_parity.rs`: a streamed response fails if its chunks disagree on `created`. `wire.rs` gets a unit test for zero cached tokens.
- sgl-router's `generate_deepseek_parity.py` passed `tools=None` to `_apply_jinja_template`, which the DeepSeek branch ignored until #43006. It now passes the tools `_process_messages` would. With that, regeneration only changes the two `tools_none` cases.

The fixture diffs are mostly churn: `created` timestamps, random `call_` ids (the test ignores both), the new `watermark` / `return_flat_raw_output_top_logprobs` defaults, and `chat_encoding_spec` for the DeepSeek fixtures. The semantic changes are the removed `tool_calls: null` keys and the two `tools_none` prompts.

## Accuracy Tests

- `cargo test -p sglang-processor --all-features` passes, with token ids checked against the cached pinned checkpoints. Run against the old `src/`, the regenerated fixtures fail.
- sgl-router `cargo test` passes (1077 + 208 + 138 + 8), as do `sglang-renderer` and `sglang-server`. Clippy and pre-commit are clean.
- Live, Qwen3.8-27B: one engine plus sgl-router (`--chat-routing reorg`) built from sgl-project/sglang#43689 with this branch merged in. In the 48-case router-vs-engine suite, every case served through `/generate` matches the engine's route in `input_ids` and response, apart from the expected `n: 2` stream interleaving and seeded sampling. No result masking was needed. Before this change, the `watermark: None` sampling key and `"tool_calls": null` had to be masked to get there.
- A `watermark` request through the router now takes `/generate` and gets the same 400 as the engine's own route, both for a bad key and when the server was not started with `--enable-watermark`. All 62 chunks of a streamed chat share one `created`.
