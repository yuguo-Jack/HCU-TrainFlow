Part of #37519 ([Roadmap][Feature] Support T-Head PPU). This PR implements **Phase 1 — Platform detection & build system** (PR 1.1 / 1.2 / 1.3) and the installation part of **PR 0.4 — Documentation**.

## Motivation

T-HEAD SAIL devices (ZW810 / ZW810E, ZW-M890P) expose a CUDA-compatible API through the SAIL torch backend: `torch.device("cuda")` is the only valid device type, and `torch.cuda.is_available()` returns `True`. Today SGLang therefore treats a SAIL host as plain CUDA. This works only partly, because:

- the platform layer has no SAIL identity, so later SAIL-specific work (attention hooks, compute backends, tuned configs in Phase 2 of #37519) has no clean place to branch on;
- `sgl-kernel` cannot be built: the SAIL device compiler `hgcc` does not read CUDA sources directly, rejects `-gencode` / `-Xcudafe`, and links against `libhggcrt1` / `libhggc` / `acblas*` instead of `cudart` / `cublas*`;
- JIT kernels (`sglang.kernels.jit`) fail for the same reasons, and their cache key does not tell a SAIL build apart from a CUDA build.

This PR adds the minimal, vendor-isolated basis described in #37519 §2.1:
- a SAIL SRT platform that inherits CUDA behavior;
- runtime detection;
- an AOT `sgl-kernel` build;
- a JIT toolchain path.

Every new code path is gated on SAIL detection, so CUDA / ROCm / MUSA / NPU / XPU / CPU users are unaffected by construction. Once this lands, the Triton-based end-to-end paths can run on SAIL. The Phase 2 optimizations from the roadmap build on top of it.

## Modifications

### 1. SRT platform layer (roadmap PR 1.1)

- `python/sglang/srt/platforms/device_mixin.py`: add `PlatformEnum.SAIL` and `DeviceMixin.is_sail()`. `is_cuda_alike()` now includes `SAIL`.
- `python/sglang/srt/platforms/sail.py` (new):
  - `SailDeviceMixin(CudaDeviceMixin)` reuses the CUDA device ops and overrides only the platform identity (`_enum = SAIL`, `device_name = "sail"`). `device_type` stays `"cuda"`, and `is_cuda()` returns `True`, so existing CUDA call sites keep working unchanged.
  - `SailSRTPlatform` sets:
    - `supports_fp8()` → `True` when device capability ≥ SM89 (i.e. ZW-M890P);
    - `support_cuda_graph()` and `support_piecewise_cuda_graph()` → `True`;
    - `is_zw810e()` as a device-name helper.
- `python/sglang/srt/platforms/__init__.py`: add a private `_is_sail_available()`, written the same way as the existing `_is_cuda_available()` / `_is_rocm_available()` / … helpers. The auto-discover fallback checks it **before** CUDA, because SAIL also reports `torch.cuda.is_available()`. The `_resolve_platform` docstring is updated to match.
- `python/sglang/srt/utils/common.py`: add `is_sail()`. `is_cuda_alike()` now includes SAIL.

**Detection:** a SAIL device is identified by the `"ZW"` tag in `torch.cuda.get_device_name()`. The SRT platform layer, `sglang.srt.utils.is_sail()` and the JIT layer's `is_sail_runtime()` all use this same check, so every layer agrees on what "running on SAIL" means.

### 2. AOT `sgl-kernel` build for SAIL (roadmap PR 1.2)

- `python/sglang/kernels/aot/setup_sail.py`, `pyproject_sail.toml` (new): a dedicated setuptools build that compiles `sgl_kernel.common_ops` with `hgcc`.
  - **Source conversion.** Every compiled source and its whole `#include` closure (the aot tree plus the pinned FlashInfer sources) is converted by `sailify` (T-HEAD's CUDA → SAIL source converter) into a mirror tree under `build/sailified/`. The upstream trees are never modified. A small set of post-conversion patches covers CUDA constructs that identifier-level mapping cannot express, such as constructor-style half/bf16 casts and `CUDART_INF_*`.
  - **Compiler flags.** No `-gencode` is passed: the target arch comes from SAIL torch through `PYTORCH_SAIL_ARCH` (`ppu_10`, `ppu_15`, …). `-Xcudafe` is dropped because hgcc rejects it.
  - **Libraries.** Links `hggcrt1`, `hggc`, `acblas`, `acblasLt` in place of `cudart` / `cuda` / `cublas` / `cublasLt`.
  - **Build switches.** `SGL_KERNEL_USE_SAILIFY=0` compiles a source tree that was already converted. Third-party checkout follows the existing `SGL_KERNEL_THIRD_PARTY_DIR` / `SGL_KERNEL_SKIP_THIRD_PARTY` switches.
- `python/sglang/kernels/aot/csrc/common_extension_sail.cc` (new): registers the subset of `sgl_kernel` ops built for SAIL. This includes:
  - custom all-reduce;
  - `merge_state_v2`;
  - `rmsnorm`, `fused_add_rmsnorm` and the Gemma variants;
  - `silu_and_mul`, `gelu_tanh_and_mul`;
  - the other elementwise / quant / MoE / kv-cache ops listed in `setup_sail.py`.

### 3. JIT kernel toolchain on SAIL (roadmap PR 1.2)

- `kernels/jit/utils/common.py`: add `is_sail_runtime()`, the JIT-side counterpart of `is_hip_runtime()` / `is_musa_runtime()`. All SAIL branches in the JIT layer below are gated on it.
- `kernels/jit/utils/arch.py`: add `_sail_arch_suffix()`. SAIL devices below SM89 (ZW810 / ZW810E) JIT-compile with the arch-specific `"a"` variant, and SM89+ devices stay unsuffixed.
- `kernels/jit/utils/compile/toolchain.py`:
  - `device_compiler_path()` resolves `hgcc`, looking first in `PATH`, then `$PPU_SDK`, then `$PPU_HOME`, then `/usr/local/PPU_SDK`;
  - `target_flags()` emits `--gpu-architecture=<SGLANG_SAIL_GPU_ARCH>`, after validating the value;
  - `base_link_flags()` links `-lhggcrt1 -lhggc` from `ppu_sdk_home()/lib`.
- `kernels/jit/utils/compile/sailify.py` (new): converts JIT `.cu` sources and their include closure with sailify into a content-addressed mirror under the JIT cache directory. In-tree sources are never rewritten. The mirror digest covers:
  - the sailify version;
  - the PPU SDK version;
  - the include dirs;
  - the content of every file in the closure.

  As a result, a header edit invalidates both the mirror and the build cache. The mirror is published with an atomic rename, which is safe when several processes build at the same time.
- `kernels/jit/utils/compile/loader.py`: on SAIL, prepend the toolchain include paths, convert the CUDA sources, and drop nvcc-only flags that hgcc rejects (`-Xptxas`, `-gencode`, `--generate-code`). A warning lists the dropped flags.
- `kernels/jit/utils/compile/cache.py`:
  - SAIL builds get their own target tag, `sail_<arch>`;
  - the environment fingerprint becomes `hgcc:<arch>:sailify-<version>`, so SAIL and CUDA JIT artifacts never collide.
- `srt/environ.py`: add `SGLANG_SAIL_GPU_ARCH` (default `native`). Allowed values: `native`, `all`, `all-ppu`, `all-vm`, `ppu_10`, `ppu_15`, `vm_10`, `vm_15`.

### 4. Packaging (roadmap PR 1.3)

- `python/pyproject_other.toml`: add the extras below, following the existing `hpu` / `musa` / `mps` pattern:
  - `srt_sail` (`sailify`, `torch-for-sail`, `triton-for-sail`, `sglang[runtime_common]`);
  - `all_sail`;
  - `dev_sail`.

### 5. Documentation (roadmap PR 0.4, installation part)

- `docs/docs/hardware-platforms/sail.mdx` (new) and the `docs/docs.json` navigation entry. The page covers prerequisites (driver, PPU SDK, `PPU_SDK`), installing from source, building `sgl-kernel` for SAIL, launching the server, and verification / benchmark commands.

### 6. Tests

- `test/registered/unit/platforms/test_platform_interface.py`: new `TestSailDeviceMixin`, registered in the existing CPU CI suite. It covers:
  - SAIL identity (`PlatformEnum.SAIL`, `device_name == "sail"`, `device_type == "cuda"`, `is_cuda()`, `is_sail()`, `is_cuda_alike()`);
  - CUDA-graph / piecewise-CUDA-graph capability flags;
  - `supports_fp8()` at SM89 and below;
  - `_sail_arch_suffix()` on both sides of the SM89 boundary.

### Differences from the roadmap draft in sgl-project/sglang#37519

| Roadmap draft | This PR | Reason |
| --- | --- | --- |
| `PlatformEnum.PPU` / `PPUSRTPlatform` / `ppu.py` | `PlatformEnum.SAIL` / `SailSRTPlatform` / `sail.py` | Aligns with the vendor's public product name (T-HEAD SAIL); `ppu` stays in SDK-facing names (`PPU_SDK`, `ppu_XX` arch targets). |
| Detection via the `PPU_SDK` environment variable | Detection via the `"ZW"` tag in the CUDA device name | An environment variable can be set on non-SAIL hosts and missing on SAIL ones; the device name is ground truth and is the same check in every layer. `PPU_SDK` is still used only to locate the SDK. |
| `get_jit_cuda_arch_suffix()` on `SRTPlatform` | `_sail_arch_suffix()` in `kernels/jit/utils/arch.py` | Keeps the JIT layer independent of the SRT platform layer, like the existing HIP/MUSA handling there. |
| Standalone `python/pyproject_ppu.toml` | `srt_sail` / `all_sail` / `dev_sail` extras in `pyproject_other.toml` | Reuses the existing multi-platform packaging file instead of adding one more top-level pyproject. |
| Hardware-specific dependencies (acext, deep_gemm, flash_mla, …) | Not included | Those belong to the Phase 2 PRs that use them. |

### Impact assessment

- **Other platforms.**
  - Every new branch is gated on `is_sail_runtime()` (JIT) or the SAIL platform enum / detection (SRT).
  - The only change that runs on non-SAIL hosts is `_is_sail_available()` in the platform auto-discover fallback. It runs once, the first time `current_platform` is accessed, and costs one `torch.cuda.get_device_name()` call on CUDA hosts. On hosts without CUDA it returns early through `torch.cuda.is_available()`.
  - `is_cuda_alike()` returns early through `is_cuda()` on CUDA and through `is_hip()` on ROCm, so neither result changes.
- **CUDA JIT cache.** Unchanged: the CUDA target tag and fingerprint are computed exactly as before, so existing caches stay valid.
- **Packaging.** The new extras are opt-in. No dependency of any existing extra changes.
- **Out-of-tree platform plugins.** No change. A plugin selected with `SGLANG_PLATFORM`, or one that activates automatically, still takes precedence over the in-tree SAIL fallback.
