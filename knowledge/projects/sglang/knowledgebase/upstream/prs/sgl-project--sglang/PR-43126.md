## Motivation

Kimi-K3 MoE decode runs radix-4 top-k routing, then a separate MoE sort, then MXFP8 quantization of the activations. At decode batch sizes these are three short launches.

## Modifications

- Add BM=16 HIP kernels that fuse radix-4 routing, the MoE sort and MXFP8 quantization into one launch for decode-sized batches.
- Hand the presorted result to AITER through `register_presorted_moe`.
- Add `SGLANG_ROCM_K3_RADIX4_FUSE_SORT` (default on) to turn the fused sort off.

| New env flag | Default |
|---|---|
| `SGLANG_ROCM_K3_RADIX4_FUSE_SORT` | on |

Requires `aiter.fused_moe.register_presorted_moe` from ROCm/aiter#6208.

## Speed Tests and Profiling

The fused path is used: a probe on AITER's presort lookup showed a hit for every decode batch size from 1 to 64 tokens, and larger prefill batches keep the existing sort. End to end, the change is within noise on this recipe (at most 0.6% on any metric).

MI355X x8, TP8, `/data/models/Kimi-K3-Quark-MXFP4-AttnFP8`, AITER [`yuychang/aiter@b9229988f`](https://github.com/yuychang/aiter/commit/b9229988f) (upstream AITER `main` plus the Kimi-K3 changes in the draft AITER PRs ROCm/aiter#6203 to ROCm/aiter#6217). Base and PR ran back to back on the same machine with the Kimi-K3 8K/1K recipe: random 8192 in / 1024 out, 4 waves per concurrency, `--disable-radix-cache`, 16K chunked prefill, FP8 KV cache, AITER prefill and decode attention. This recipe differs from the cookbook MI355X cell: TP8 without DCP8. Speed and GSM8K each used a fresh server.
