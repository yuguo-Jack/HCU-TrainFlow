# [Fix] flashinfer: fail fast when dtype=float32 is used with the attention backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/43628) · state: open · merged: False

## Original PR description

## Motivation

Fixes #43162.

`dtype` is a `choices`-validated server argument whose help text lists `"float32"` (and its alias `"float"`) as supported values. The argument was accepted without complaint, but starting the engine aborted the whole process group with an unhandled `KeyError: torch.float32` raised deep inside FlashInfer's decode wrapper during CUDA-graph capture. FlashInfer has no FP32 attention kernels (`torch.float32` is missing from its `filename_safe_dtype_map`), so any FP32 model on the flashinfer backend was doomed from the start, and sglang surfaced it as a mid-startup crash instead of a configuration error.

## Modifications

**`python/sglang/srt/arg_groups/attention_hook.py`**
- In `handle_attention_backend_compatibility`, right after the default attention backend is filled, raise a clear, actionable `ValueError` when `dtype` is `"float"`/`"float32"` and the resolved prefill or decode backend is `flashinfer`. The error names the unsupported combination and points at `--dtype bfloat16/float16` or an FP32-capable backend (`torch_native`, `triton`). Split prefill/decode backends are checked too, since the original crash happened in the decode path.

**`test/registered/unit/server_args/test_server_args.py`**
- Add `TestFlashInferFp32DtypeGuard` with 6 cases: explicit `flashinfer` + `float32` raises, the `"float"` alias raises, split `prefill=triton`/`decode=flashinfer` raises, and the allowed combinations (`bfloat16`+`flashinfer`, `float32`+`triton`, `float32`+`torch_native`) do not raise.

## Tests

- New unit tests follow the existing `TestFa4PageSizeAutoForce` pattern in the same file (construct `ServerArgs(model_path="dummy")`, mock `_model_config`, call `handle_attention_backend_compatibility` directly).
- Verified the guard logic against the real handler with a stub harness covering 8 scenarios (explicit backend, auto-selected backend, split backends, allowed combos): all pass.
- Could not run the full GPU e2e repro here (no CUDA on this machine); the pre-existing CPU unit suite path (`test/registered/unit/server_args`) is the appropriate gate for this change.
