## What changes

**Who sees it:** users who run a HiSparse decode server with native MTP (EAGLE) speculative decoding. They set `--enable-hisparse` and a speculative algorithm.

**Before this PR:** the server starts and serves, but only the first token of each answer matches the reference. The first token comes from prefill. Every later token differs. Also, after a request aborts, one 64-token KV page stays in use. All 72 idle samples in one run showed this (3,904 used before, 3,968 after).

**After this PR:** verification reads the right KV rows, so the output matches the reference. Aborted requests release all their pages. After the fix, every cell of one job returned to 0 used pages of 163,840.

**Conditions that change behavior:**
- Startup no longer rejects speculative decoding with `--enable-hisparse`. [#41347](https://github.com/sgl-project/sglang/pull/41347) added that rejection because the draft pool had no HiSparse mapping and verification read wrong rows. [6/N] #41780 and this PR fix both causes. The check for `--enable-mixed-chunk` stays.
- The decode attention backend must be `tilelang`, `triton` or `flashmla_sparse`. HiSparse with speculative decoding now rejects any other `--dsa-decode-backend` at startup. This excludes CUDA FP8 KV with `flashmla_kv` or `flashinfer_sparse_mla`, and ROCm `aiter`.
- HiSparse prefetch must be off. Under speculative decoding it is already off.
- Output without speculative decoding does not change.

**Needs [6/N] #41780** for the draft worker to start.

Speed is not measured for this PR.

## Problem in detail

HiSparse swaps the missed top-k rows of a decode query into the device buffer before attention. Target verification never did this. Its sparse attention translated the logical top-k rows through the logical-to-device mapping (`dsa_backend.py`). Prompt rows that exist only in the host pool mapped to slot 0.

## Implementation

- `validate_hisparse_feature_combos` (`arg_groups/hisparse_hook.py`) no longer raises for a speculative algorithm.
- `HiSparseCoordinator.gather_for_verify` (`managers/hisparse_coordinator.py`) handles each verify query in three steps:
  1. It swaps in the prompt rows that the device buffer misses. It uses the existing swap kernel.
  2. It reads generated and draft rows from their resident mappings.
  3. It copies the selected rows into per-query scratch before the next query's swap can evict them.
- `DeepseekSparseAttnBackend` sends target verification through `gather_for_verify`. The sparse kernel reads the scratch. Only the tilelang, triton and flashmla_sparse kernels can read it, and the indexer runs unfused. `validate_hisparse_spec_verify_backend` (`arg_groups/hisparse_hook.py`) enforces this at startup.
- `alloc_device_buffer` records each request's staged prompt length. It keeps an unaligned prompt tail in a mapped device page. Speculative `alloc_extend` then continues from a valid physical location.
- Request release frees the device pages that speculative `alloc_extend` owns outside the side buffer. It frees them together with the side buffer, so aliased pages are released once.
- The verify scratch comes back in the pool's KV dtype. An FP8 pool stores `uint8` bytes in `kv_buffer`. The attention path selects its kernel from the dtype that `get_key_buffer()` returns. With raw `uint8` rows, `tilelang_sparse_fwd` chose its BF16 kernel and read Q and KV at twice their width. This caused an illegal memory access in target-verify graph capture with large pools. With small pools it gave silently wrong attention.

This PR does not change the swap kernel's miss counting. `main` already counts the misses of a query from the compacting scan (`s_total_misses`, [#31446](https://github.com/sgl-project/sglang/pull/31446)). The verify gather passes -1 for rows that it does not need from the host. The kernel already reads -1 as `TOKEN_HIT`.

## Tests

- `test/registered/unit/server_args/test_server_args.py`: `validate_hisparse_feature_combos` accepts speculative decoding and still rejects `--enable-mixed-chunk`. HiSparse with speculative decoding accepts tilelang, triton and flashmla_sparse. It rejects flashmla_kv, flashinfer_sparse_mla and aiter. Without speculative decoding, the backend restriction does not apply.
- `test/registered/unit/managers/test_hisparse_verify_read.py` (CPU, mocked swap kernel): verify reads match the reference for C1 and C4, with 2, 4 and 6 queries, with and without padding. It also covers verify dispatch, partial prompt pages and the FP8 scratch dtype. The FP8 test fails without the dtype view.
- `test/registered/unit/managers/test_hisparse_unit.py` needs an accelerator. It covers eager verify gather on every accelerator, graph capture and replay on CUDA and ROCm, and the prompt-length bookkeeping.
- `test/registered/unit/mem_cache/test_hisparse_allocator.py::TestHiSparseRequestRelease`: pages outside the device buffer, mapping-only requests, aliases freed once and empty ownership.

## Measured

On a HiSparse fork build, with FP8 KV, MTP k=3, PD serving and a HiSparse decode:

- Before the dtype fix, target-verify graph capture crashed with an illegal memory access. The log showed tilelang's `Buffer dtype mismatch for parameter Q: expected bfloat16, got float8_e4m3fn`.
- After the fix, capture completes. The server answers short prompts and needle prompts of 59K to 101K tokens correctly (6 of 6). The mean accept length is 2.87.

## Known limit: HiSparse prefetch

Target verification needs HiSparse prefetch off, and `gather_for_verify` asserts this. Under speculative decoding `resolve_shared_index_layers` returns `None`, so `enable_prefetch` is `False` for any recipe. Support for prefetch with MTP needs four changes:

1. Allow the shared-index pattern under speculative decoding.
2. Size the miss plan (`_miss_src`, `_miss_dst`, `_miss_count`) and the prefetch groups for `num_draft_tokens × top_k` selections per request. Today they use `top_k`.
3. Make `gather_for_verify` use the prefetched slots. Today it swaps synchronously for each query.
4. Order the next layer's prefetch after each layer's scratch gather, with an event on the prefetch stream. Or reserve `num_draft_tokens × top_k` buffer slots per request. A prefetch must not evict rows that the current verify still reads.

All of these must keep static shapes for graph capture.

`index_kpool > 1` and pipeline parallelism stay unsupported with HiSparse verification. They are also unsupported for HiSparse decode.
