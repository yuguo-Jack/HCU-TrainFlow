# [Feat] diffusion: Plan residency as one pool on unified memory (GB10)

[Upstream PR](https://github.com/sgl-project/sglang/pull/37811) · state: open · merged: False

## Original PR description

Stacked on #37809 (calibration fixes) → #36703 (planner base). Diff here is the one-pool model only; the shared-pool streaming I/O and debug aids follow in the next PR.

## Motivation

On a DGX Spark (GB10, 121.7 GiB LPDDR5X shared by CPU and GPU) the residency planner from #36703 made choices that were right for a discrete host and wrong for one pool of memory: it counted pinned memory as spare capacity, treated the page cache as a second copy that costs nothing, and loaded its resident seed through a pinned/ATS path that took twice the component's weight. MiniMax-H3 fl2va (115 GB of weights) either exhausted the machine at load or ran at 712 s per request with every component streamed. ComfyUI runs the same request in 302.6 s.

## What this PR does

**Platform.** `device_shares_host_memory()` probes whether the CUDA device draws from the host pool (integrated GPUs, Grace Blackwell); `host_copies_are_redundant()` is the rule the budget and hosting code key on.

**Budget and hosting on a shared pool.** The host budget is the cgroup anon share (psutil available) instead of MemTotal minus device; pins count zero; every layerwise layer is hosted mapped (page cache) so weights have a single home. The loaders keep the mapped storages alive instead of copying them to anonymous memory.

**Planner accounting.** Permanent residents earn a page-cache credit (`released_cache_bytes`) in every phase: promoting a component to the device frees the cache that used to hold it. When the layers that stay mapped exceed the cache the pool can hold, their stream cost is priced as disk misses (×24 measured on this NVMe vs page-cache hits). A permanent transition costs `full − cache`, not `full`. Stage-resident candidates on a shared pool are limited to small, heavily reused components (≤ 16 GiB, ≥ 4 max layer uses), because a stage-resident load elsewhere doubles the component at the machine's tightest moment. The options log prints every candidate layout with the savings and deltas it was scored on.

**Initial residency and offload.** No resident seed on a shared pool; `auto_tune` turns pinning off and enables expandable segments; component offload takes the synchronous pageable D2H path there (the non-blocking move pinned a second copy of the 57 GiB DiT).

**CPU allocator defaults.** torch 2.13's CPU allocator is mimalloc; it reserves 1/2/4 GiB arenas (`MAP_NORESERVE` + `MADV_HUGEPAGE`) and keeps freed pages in them. The loader builds every fused QKV projection as an anonymous copy (52 × 220 MiB = 10.4 GiB for the H3 DiT) and frees them once the DiT is promoted, but the arenas kept them: 18.2 GiB anonymous after promotion on the GB10, 5.0 GiB with `MIMALLOC_PURGE_DELAY=0` and `MIMALLOC_ALLOW_LARGE_OS_PAGES=0`. The launcher sets both for the workers on a shared pool unless already chosen. (Traced with host-side bpftrace on the `mmap`/`madvise` syscalls; the stacks resolve into `libc10.so`.)

## Result (DGX Spark, MiniMax-H3 fl2va, 864×480×124f, 20 steps)

The planner chooses `transformer(resident)` + `video_vae(layerwise)` with no flags.

| | before | this stack | ComfyUI |
|---|---|---|---|
| warm request | 712 s | 270 s | 302.6 s |

Discrete hosts are unaffected: every new rule is behind `host_copies_are_redundant()`, and the existing planner tests run under a discrete-host fixture.

## Tests

`test/unit/test_shared_memory_pool.py` (15 tests: hosting, budget, pins, stream cost, cache credit, candidate filter, D2H guard, promotion of the DiT on a GB10-shaped report, allocator defaults) plus fixtures in the existing planner/offload tests.
