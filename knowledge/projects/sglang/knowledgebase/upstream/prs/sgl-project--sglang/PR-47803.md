# [Perf] [Apple] layernorm: Add a Metal RMSNorm for the Torch MPS path

[Upstream PR](https://github.com/sgl-project/sglang/pull/47803) · state: open · merged: False

## Original PR description

## Motivation

First part of the "direct Metal semantic ops for eager" item in the Apple Silicon roadmap (#32321): RMSNorm on the Torch MPS eager path. SiLU-and-mul follows in a separate PR.

Today `RMSNorm` has no MPS path, so on Apple Silicon it runs `forward_native`: an fp32 upcast, `pow`, `mean`, `rsqrt` and two multiplies, each a separate MPS kernel with its own fp32 intermediate. This PR replaces that with one Metal kernel per call.

## Modifications

- `fused_op.py`: add an `"mps"` platform key, so `BaseFusedOp` dispatches to `forward_mps` on Apple Silicon. Ops that don't define `forward_mps` still fall back to `forward_native`, so nothing else changes.
- `kernels/ops/layernorm/rmsnorm_mps.py` (new): RMSNorm and fused add + RMSNorm, compiled with `torch.mps.compile_shader`. One threadgroup per row. The sum of squares and the residual add are done in fp32, like `forward_native`; only the stores round to the input dtype. Supports fp32, fp16 and bf16. Inputs are never modified; the fused variant returns `(out, x + residual)`.
- `layernorm.py`: `RMSNorm.forward_mps` uses the kernel for the plain variant. Everything else goes to `forward_native`: `post_residual_addition`, `var_hidden_size`, `cast_x_before_out_mul`, `fp32_residual`, `override_orig_dtype`, and mismatched dtypes or shapes.
- `test_rmsnorm_mps.py` (new, registered in `stage-a-unit-test-mps`): parity against `forward_native` and a dispatch test.

## Accuracy Tests

`test_rmsnorm_mps.py` compares against `RMSNorm.forward_native` for fp32/fp16/bf16, with and without residual, on shapes `(1, 7)`, `(3, 64)`, `(5, 1000)`, `(2, 3, 2048)`, `(4, 4100)`. The odd widths leave idle threads in the last SIMD group, and 4100 makes each thread loop over several elements.
- Normalized output: `atol`/`rtol` of 1e-5 (fp32), 2e-3 (fp16), 1.6e-2 (bf16).
- Residual sum: bit-exact.
- Inputs are checked to be unchanged.

The dispatch test checks that the plain variant calls the kernel exactly once, and that `fp32_residual`, `var_hidden_size` and a dtype mismatch go to the native path.

This only touches the MPS eager path. CUDA, ROCm, NPU, XPU, MUSA and CPU dispatch is unchanged.

## Speed Tests and Profiling

Op-level microbenchmark on Apple M2 Max (64 GB), macOS 27.2, PyTorch 2.13.0. Each number is the median of 5 runs of 200 calls after warmup, with `torch.mps.synchronize()` around each run. It compares `RMSNorm.forward_native` against `forward_mps`, in µs per call, bf16:

| hidden | tokens | native | Metal | native, +res | Metal, +res |
|---:|---:|---:|---:|---:|---:|
| 4096 | 1 | 43.4 | 12.0 (3.6x) | 56.4 | 14.3 (3.9x) |
| 4096 | 16 | 58.0 | 12.2 (4.7x) | 75.1 | 13.8 (5.5x) |
| 4096 | 256 | 285.4 | 22.1 (12.9x) | 355.1 | 30.9 (11.5x) |
| 4096 | 2048 | 2418.8 | 113.8 (21.3x) | 2820.4 | 234.6 (12.0x) |
| 8192 | 1 | 43.1 | 14.2 (3.0x) | 54.4 | 15.6 (3.5x) |
| 8192 | 2048 | 4505.5 | 197.4 (22.8x) | 5664.9 | 460.0 (12.3x) |

Across hidden 2048/4096/8192, tokens 1/16/256/2048, and fp16 or bf16, the Metal path is 3.0x to 26x faster than native in every case. Decode-sized calls (1 token) go from about 40–70 µs to 11–16 µs.

These are op-level numbers. I haven't measured end-to-end serving throughput on MPS with this change.
