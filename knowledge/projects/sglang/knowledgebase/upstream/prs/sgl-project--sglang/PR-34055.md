# [CI] Fetch full history in image builds so the version stamp is real

[Upstream PR](https://github.com/sgl-project/sglang/pull/34055) · state: open · merged: False

## Original PR description

Nightly and development image builds install SGLang from the checked-out source, including its `.git` directory. The default shallow, tagless checkout prevents `scripts/release/get_version_tag.py` from finding version tags and their common ancestry, so setuptools-scm falls back to `0.0.0.dev0`. This can cause misleading vulnerability-scan matches for the installed package.

Fetch full history and tags with `fetch-depth: 0` on both architecture checkouts in `_docker-build-and-publish.yml` and the separate checkout in `release-docker-cu134-nightly.yml`. These workflows build from the local checkout with `BRANCH_TYPE=local`, allowing setuptools-scm to derive the package version from Git metadata.

Validation: applicable repository hooks and `git diff --check` pass. The current version resolver was exercised against a local Git fixture: depth 1 without tags fails; depth 1 with a divergent release tag still fails; full history and tags resolves the version. Full Docker-image build validation has not been run.

Thanks for digging into this — the PEP 440 diagnosis is right and genuinely non-obvious (scanners match on the release segment, so `0.0.0` sorts below every advisory range).

Two things I ran into while verifying, though:

### 1. The `USE_LATEST_SGLANG=1` branch is no longer reachable from the nightly build

#33738 (merged yesterday) switched the scheduled nightly to `BRANCH_TYPE=local`:

```yaml
# .github/workflows/release-docker-dev.yml:70-74
if [ "${{ github.event_name }}" = "schedule" ]; then
  echo "extra_build_args=--build-arg BRANCH_TYPE=local ..."
else
  echo "extra_build_args=--build-arg BRANCH_TYPE=local ..."
fi
```

Nothing in the repo sets `USE_LATEST_SGLANG=1` anymore, so the nightly now takes the `cp -r /tmp/local_src` branch — this change won't affect the published stamp.

### 2. The remaining cause is the workflow checkout, not the clone

`_docker-build-and-publish.yml:62-65` (and again at `:185-188`) uses `actions/checkout@v4` with defaults — `fetch-depth: 1`, no tags. `.dockerignore` symlinks to `.gitignore`, which doesn't exclude `.git`, so that shallow tagless `.git` rides into the image via `COPY . /src`. Reproduced:

```console
$ git clone --depth=1 --no-tags https://github.com/sgl-project/sglang.git probe
$ cd probe && python3 python/tools/get_version_tag.py
WARNING: No version tags (v*.*.*) found in repo
ERROR: Could not determine version from git tags.
$ echo $?
1
```

→ setuptools-scm falls back to `fallback_version` and you get `0.0.0` again.

Suggested fix: `fetch-depth: 0` on the checkout steps in `_docker-build-and-publish.yml`. Note `fetch-tags: true` alone isn't enough — with depth 1 the `merge-base` fallback in `get_version_tag.py` still fails and exits 1.

### Smaller notes

If you keep the Dockerfile change for manual `USE_LATEST_SGLANG=1` builds:

- Measured `.git` size after clone + checkout of sglang today: `--depth=1` → 30 MB, `--filter=blob:none` → 80 MB, `--filter=tree:0` → 52 MB. So it's ~**+50 MB of permanent image weight**, not 47 MB total — nothing does `rm -rf .git`. `--filter=tree:0` resolves the identical version string (`v0.5.17-211-g52afe87a`) for 28 MB less.
- Blobless clones leave `promisor = true` / `partialclonefilter` in `.git/config`, so `git log -p` / `git blame` / `git diff HEAD~1` inside the shipped container will reach out to github.com — that hangs rather than fails fast in air-gapped deployments.
- The configured fallback is `fallback_version = "0.0.0.dev0"` (`python/pyproject.toml:237`), so the stamp is plain `0.0.0.dev0`, not `0.0.0.dev1+g<sha>`. Same conclusion, just for the description.
- Heads-up for once this works: the cu12 path `sed -i`s the tracked `python/pyproject.toml` before `pip install -e` in the same `RUN`, so setuptools-scm will see a dirty tree and stamp `0.5.17.dev211+g<sha>.d20260807` rather than `0.5.17.dev<N>+g<sha>`.

Also confirmed your claim that release images are unaffected holds — `git clone --depth=1 --branch v0.5.17` → the script returns `v0.5.17` via the exact-match path.
