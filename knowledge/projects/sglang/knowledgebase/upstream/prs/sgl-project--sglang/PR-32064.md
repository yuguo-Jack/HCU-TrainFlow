# [Fix] Lazy-load SM100-only GDN BF16-state kernel so FlashInfer GDN works on Hopper

[Upstream PR](https://github.com/sgl-project/sglang/pull/32064) · state: closed · merged: False

## Original PR description

# [Fix] Lazy-load SM100-only GDN BF16-state kernel so FlashInfer GDN works on Hopper

## Motivation

Fixes #32063.

`_get_flashinfer_gdn_kernels()` unconditionally imports
`flashinfer.gdn_kernels.gdn_decode_bf16_state` inside the try/except that
decides backend availability. That module is CuTe-DSL based
(`import cutlass` at module level) and is **only consumed on SM100+**
(`use_state_pool = sm_major >= 10`; SM90 uses fp32 state per the module
docstring).

On Hopper installs without the DSL dependencies (e.g. flashinfer 0.6.12
wheel without `nvidia-cutlass-dsl`), the import raises
`ModuleNotFoundError: No module named 'cutlass'`, the availability check
swallows it, and the **entire FlashInfer GDN backend is silently disabled
on SM90** — even though every kernel SM90 actually uses imported fine.
Launching with `--linear-attn-prefill-backend flashinfer` then fails with a
misleading "Requires SM90+" error.

## Modifications

Import the BF16-state MTP kernel only on SM100+, defaulting the symbol to
`None` otherwise (the consumer side already handles `mtp_bf16_fn is None`
and is additionally gated by `use_state_pool`):

```python
            gated_delta_rule_mtp_bf16 = None
            if is_cuda() and torch.cuda.get_device_capability()[0] >= 10:
                from flashinfer.gdn_kernels.gdn_decode_bf16_state import (
                    gated_delta_rule_mtp as gated_delta_rule_mtp_bf16,
                )
```

- SM90 (Hopper): backend availability now depends only on the SM90 kernels;
  decode / prefill / MTP behavior unchanged (they never used the BF16-state
  kernel).
- SM100+ (Blackwell): unchanged — the kernel is still imported inside the
  same try/except, so a broken DSL install degrades availability exactly as
  before.

## Verification

- On 8x H800 (SM90), flashinfer 0.6.12 without `cutlass`: before the fix,
  the backend was unavailable; after the fix, "FlashInfer GDN kernels
  loaded successfully" and Qwen3.5-397B-A17B-FP8 runs end-to-end with
  `--linear-attn-prefill-backend flashinfer` (outputs match the triton
  linear-attn backend baseline).
- `FlashInferGDNKernel` init path re-checked: `mtp_bf16_fn is None` is
  already handled and the bf16 adapter is gated by `use_state_pool`.
