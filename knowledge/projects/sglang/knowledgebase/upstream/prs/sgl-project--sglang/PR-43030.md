# [Bug fix] moe_align_block_size: add the missing barrier before the expert_ids search

[Upstream PR](https://github.com/sgl-project/sglang/pull/43030) · state: open · merged: False

## Original PR description

## Motivation

**Summary.** In `moe_align_block_size_kernel`'s CUDA path, there is no barrier between the `prefix[tid]` writes and the binary search of `prefix[]` that fills `expert_ids`, so a block can get the wrong expert id. This PR adds that barrier to each CUDA copy of the kernel.

In the CUDA path, the last `__syncthreads()` publishes `scan_buf`. After it:
1. threads with `tid < num_experts` write `prefix[tid] = scan_buf[tid]`;
2. every thread then binary-searches `prefix[]` to fill `expert_ids`.

There is no barrier between the writes and the search, so a thread can read `prefix[mid]` before thread `mid` has written it. `prefix[0..num_experts-1]` holds no defined value before that write. This is a shared-memory data race, which is undefined behavior in CUDA C++.

**Effect.** A stale read sends the binary search the wrong way. The tokens of a block with the wrong id are then:
- multiplied by another expert's weights (silent wrong output),
- written as zeros (id −1 with `filter_expert`), or
- read weights at a negative offset (out of bounds).

`cumsum`, `total_tokens_post_pad` and `sorted_token_ids` are not affected.

The HIP branch of the same kernel already has this barrier, and so does `fused_align_scatter_kernel` in the LoRA file. vLLM's and TensorRT-LLM's versions use a different scan that has one.

## Modifications

A `__syncthreads()` goes right after the `prefix[tid]` write in:
- `python/sglang/kernels/aot/csrc/moe/moe_align_kernel.cu` (the default AOT `sgl_kernel` build)
- `python/sglang/kernels/jit/csrc/moe/moe_align_kernel.cu` (CUDA branch)
- `python/sglang/kernels/jit/csrc/lora/trtllm_lora_temp/moe_lora_merged_align_kernel.cu`

Each new barrier sits directly below an existing unconditional `__syncthreads()` at the same scope, so every thread of the block reaches it. The HIP branch is untouched, and no interface changes.

An alternative fix is to have the search read `scan_buf[mid]`, which the preceding barrier already published and which holds the same values for `mid < num_experts`.

## Accuracy Tests

We ran the kernel from current main in a standalone harness on an A100 (CUDA 13.2, Compute Sanitizer 13.2). It was launched as the host dispatcher launches it (2 blocks × 1024 threads), with 64–384 experts and top-8 routing.
- `racecheck` reports read-after-write hazards between the `prefix[tid]` write and the `prefix[mid]` read in the search, in every configuration.
- Under racecheck's thread schedule, the kernel returned wrong `expert_ids` (in-range ids of other experts) in 11 of 18 launches.
- With the added `__syncthreads()`, racecheck reports no hazards and the output is correct.
- At native speed, 4.1 million launches of the same harness (synthetic routings, with and without other kernels running) produced no wrong output, so we have not seen it at native timing.

## Speed Tests and Profiling

The fix adds one `__syncthreads()` per launch, directly after an existing one. We did not run a speed benchmark.
