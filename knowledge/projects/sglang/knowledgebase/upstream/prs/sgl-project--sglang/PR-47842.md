## Motivation

Enable `_can_enable_t1_fused_qk_norm_rope` for SM 120

On DGX Spark, with the DiT resident, the fused path makes Edge and Nano image requests 3.8-14.5% faster, and the output stays bit-identical. I have checked the #34347, and it has already made this kernel round the same way as the split path on SM120.

## Modifications

Add an `is_sm120` branch to the gate. Each condition comes from a measurement on Spark. The TP2 and SP2 numbers come from a test build that opened the gate for those topologies (it's a summary for the test results below):

- Edge `(relu2, 2048)` and Nano `(silu, 4096)`: Every Edge and Nano T=1 input I ran with the DiT resident is faster and bit-identical: Edge -9.0% to -14.5%, Nano -3.8% to -8.3%.
- `tp_size == 1`: On two DGX Sparks, TP2 gave no consistent gain. Nano was 0.9-2.2% slower. On Edge, identical requests return different images run to run even on main.
- `sp_size == 1`:  Under SP the fused kernel never runs at T=1, because the forward also requires sp 1. Opening the gate there only changes the RoPE cache dtype, and SP2 got 3-15% slower.
- Super and other shapes stay out: Super was not measured with the fused path. On Hopper, the dense Super shape got slower with it.

CFG parallel runs each rank at tp 1 and sp 1, so it is admitted. It measured 4-10% faster.

For test cases:
- Gate unit tests cover the admitted shapes and the excluded shapes and topologies. The test class now derives from `CustomTestCase`.
- The split-vs-fused parity test in `test_cosmos3_edge_fusions.py` now also runs on capability 12, for both the Edge (16 query heads) and Nano (32 query heads) layouts. It is also registered on `1-gpu-small` (RTX 5090), so CI will check SM120 numerics when that job runs.

**Note:** SM10x and Hopper are unchanged.

## Accuracy Tests

- Every measured configuration this PR admits gives bit-identical images on main and on this PR (SSIM 1, PSNR inf). This covers:
  - the `cosmos3-edge-t2i` and `cosmos3-nano-t2i` presets at exact, lossless and high quality;
  - `sglang serve` requests;
  - 48 more input and placement combinations, plus a repeated offload run.
- Parity test: 10 passed on DGX Spark. I broke the fused call four ways (rounding off, non-neox RoPE, K/V prefixes swapped, K norm weight used for Q); each one fails all 6 parity cases.
- `test_cosmos3.py`: 145 passed (143 on main).

## Speed Tests and Profiling

Saved-request wall time on Sparks, measured on the client from request start through response decoding. Saving the image comes after and is not included. Each arm starts a fresh `sglang serve` and sends 1 warmup and 3 measured requests. Arms run main, PR, PR, main.

| Model | main | This PR |
|-|-|-|
| Edge, 640x640, 35 steps, manual placement | 1.764 s | 1.556 s (-11.8%) |
| Nano, 1024x1024, 35 steps, auto placement (DiT resident) | 13.669 s | 12.679 s (-7.2%) |

- Other inputs with the DiT resident:
  - Edge, 20 inputs: -9.0% to -14.5%;
  - Nano, 18 inputs across 20 input and placement combinations: -3.8% to -8.3%.
- CFG parallel on two Sparks: Edge -10.1% / -8.0%, Nano -5.0% / -4.3%.
- With offload there is no consistent change:
  - Edge layerwise, 8 arms: 7.129 -> 7.136 s;
  - Nano layerwise: 64.37 -> 63.93 s;
  - Edge auto (whole-DiT CPU offload): +3.1% / +0.5%, while arm means vary by up to 12%.
- Profile, 6 profiler steps:
  - Edge: kernel launches 11282 -> 3890, GPU kernel time 283.3 -> 261.2 ms;
  - Nano: kernel launches 14258 -> 4754, GPU kernel time 2473.2 -> 2279.8 ms.
- Note: SM120 is not measured. The parity test on the RTX 5090 runner will check numerics there when it runs.
