# [Fix] GGUF: IQ3_S codebook and q8_1 block sums

[Upstream PR](https://github.com/sgl-project/sglang/pull/43636) · state: open · merged: False

## Original PR description

## Motivation

Two accuracy bugs in SGLang's GGUF CUDA kernels. Both slipped past the existing tests, whose element-wise tolerances are loose (`atol=1e-2, rtol=4e-2` for dequant, bf16 `rtol=3e1` for MMVQ and `1e4` for MMQ).

1. **IQ3_S is computed from the wrong codebook.** `dequantize_block_iq3_s` and `vec_dot_iq3_s_q8_1` look up the 3-bit codes in `iq3xs_grid` and scale each block by `d * (0.5 + s) * 0.5`. That pair belongs to a pre-release IQ3_S format. The released format, which llama.cpp writes and gguf-py reads, uses `iq3s_grid` with `d * (1 + 2s)`.
2. **The q8_1 block sums do not match the quantized activations.** `quantize_q8_1` stores the sum of the *unquantized* inputs in `ds.y`. The kernels use that sum to apply a per-block weight offset or minimum: Q4_0's -8, Q5_0's -16, IQ1_S's delta, and the Q4_K / Q5_K minimums in MMQ. Only the sum of the values that were actually multiplied cancels exactly. With the unquantized sum, the rounding error of the activations stays in the result, multiplied by the offset.

Relative L2 against an fp32 product with gguf-py's dequantized weights, measured on the `Isotr0py/test-gguf-sample` files (RTX 5070 Ti, sm_120, `randn` bf16 activations; MMVQ uses 7 tokens and MMQ uses 300):

| kernel | type | main | this PR |
|---|---|---|---|
| `ggml_dequantize` (fp32) | IQ3_S | 1.4e-2 | 0 |
| `ggml_mul_mat_vec_a8` (MMVQ) | IQ3_S | 1.6e-2 | 5.8e-3 |
| MMVQ | Q4_0 / Q5_0 / IQ1_S | 1.5e-2 / 1.5e-2 / 1.1e-2 | 5.7e-3 / 5.8e-3 / 5.9e-3 |
| `ggml_mul_mat_a8` (MMQ) | Q4_K / Q5_K / Q4_0 | 1.3e-2 / 1.3e-2 / 1.4e-2 | 5.7e-3 / 5.7e-3 / 5.7e-3 |
| all kernels | every other type | 4.2e-3 to 5.8e-3 | unchanged |

The MMQ error matters most in practice: Q4_K is one of the most common GGUF weight types (`Q4_K_M`), and MMQ is the batched path that prefill uses. The MoE kernels (`ggml_moe_a8`, `ggml_moe_a8_vec`) share the same quantizer and `vec_dot` functions, so this PR fixes them too.

We found the IQ3_S bug while serving an IQ3_S GGUF MoE: our GPU expert kernel had copied `vec_dot_iq3_s_q8_1` from here. With the fix applied there, paired NLL over 6,120 tokens moved by -0.0026 (SE 0.0014).

## Modifications

All changes are under `python/sglang/kernels/aot/`.

**Commit 1, IQ3_S:**
- `csrc/quantization/gguf/ggml-common.h`: replace `iq3xs_grid` with ggml's `iq3s_grid`. No other code used the old table.
- `dequantize.cuh` (`dequantize_block_iq3_s`) and `vecdotq.cuh` (`vec_dot_iq3_s_q8_1`): use `iq3s_grid` and the block scale `d * (1 + 2s)`, as ggml's `dequantize_iq3_s` and `vec_dot_iq3_s_q8_1` do.

**Commit 2, q8_1 sums:**
- `csrc/quantization/gguf/gguf_kernel.cu`, `quantize_q8_1`: compute the block sum over the quantized values with one more warp reduction, and store `ds.y = d * sum(q)`.

**Tests** (`tests/test_gguf.py`): three tests that compare in relative L2 against gguf-py instead of element by element:
- `test_dequantize_matches_gguf_py`: fp32, < 2e-3
- `test_mmvq_matches_gguf_py`: < 1e-2
- `test_mmq_matches_gguf_py`: < 1e-2, run over the MMQ types

The limits are the same for every type.
