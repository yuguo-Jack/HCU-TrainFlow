# [Perf] [AMD] qwen3.5: Fuse self-attn prepare on gfx950 (norm+RoPE+gate)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45529) · state: open · merged: False

## Original PR description

Route the HIP/gfx950 self-attention prepare through sglang's own fused_qk_gemma_rmsnorm_rope_gate (one Triton launch) instead of fused_qk_gemma_rmsnorm_with_gate + rotary_emb (two launches), matching the CUDA path. Defensive import under `_use_aiter and _is_gfx95` with an internal A/B toggle (_hip_fused_prep_enabled); falls back to the 2-kernel path if the kernel cannot import on ROCm Triton.

Unpack the fused-AR (bf16, fp8, scale) tuple in forward_prepare_cuda_fused before qkv_proj, like its sibling prepare methods (required now that the HIP path reaches it with --enable-aiter-allreduce-fusion).

Make the kernel importable on ROCm: guard the libdevice import and disable Hopper PDL on HIP.

## Motivation

In Qwen3.5's full-attention layers, there is a "prepare" step that builds the query, key, and gate before attention runs. On gfx950 (MI355X) this step uses **two** GPU kernels: the first does QK RMSNorm and splits out the gate, and the second applies RoPE. On NVIDIA/CUDA, the same work is already done by a **single** kernel, `fused_qk_gemma_rmsnorm_rope_gate`.

So on gfx950 we launch one extra kernel on every full-attention layer (15 of the 60 layers), on every decode step. That extra launch costs time for no real benefit.

This PR turns on the single-kernel path on gfx950, so the prepare step uses **1 kernel instead of 2**. The kernel is written in Triton (not CUDA C++), and it already handles partial RoPE, interleaved mRoPE, and the Gemma `+1` norm, so it produces the same result as before for Qwen3.5.

## Modifications

- On gfx950, send the prepare step through the single fused kernel instead of the two-kernel path. We import the kernel only when it is available (`_use_aiter and _is_gfx95`). If it cannot be imported on the installed Triton, the code falls back to the old two-kernel path, so nothing breaks. A simple on/off switch, `_hip_fused_prep_enabled` (no new environment variable), lets you compare the new path against the old one.
- When all-reduce fusion is on (`--enable-aiter-allreduce-fusion`), the input arrives as a `(bf16, fp8, scale)` tuple. We now unpack that tuple before calling `qkv_proj`, the same way the other two prepare functions already do. This does nothing on CUDA.
- Let the kernel import on ROCm. The `libdevice` import is only needed for an option that is off by default, so we wrap it in a `try/except`. We also turn off Hopper PDL on AMD, since AMD GPUs do not have it.
- No change on CUDA or on non-gfx950 GPUs.

## Accuracy Tests

gsm8k (5-shot), `amd/Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2`, TP=2, gfx950. The scores match within the margin of error:

| Build | flexible-extract | strict-match |
|---|---|---|
| before (2 kernels) | 0.9735 ± 0.0044 | 0.9735 ± 0.0044 |
| this PR (1 kernel)  | 0.9750 ± 0.0043 | 0.9757 ± 0.0042 |
