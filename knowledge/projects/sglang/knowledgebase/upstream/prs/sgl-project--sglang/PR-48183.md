# [Fix] tool-call: Return only the named tool for a named tool_choice

[Upstream PR](https://github.com/sgl-project/sglang/pull/48183) · state: closed · merged: False

## Original PR description

## Motivation

A named `tool_choice` can return another tool after the forced call. A legacy structural tag leaves the text after that call free, and the `qwen3_coder` grammar lets a string value hold a second call. Chat, Responses, and `/v1/messages` clients then get a tool that they did not ask for.

## Modifications

`FunctionCallParser` now drops parsed calls to other tools under a named `tool_choice`. Kept calls get consecutive indices, and a stream sends no delta for a dropped call. If no call remains, the response has no `tool_calls`.

Limits:

- #42207 and #40051 cover only the legacy tag, which can make the first call another tool. This PR alone then returns no call, so I recommend merging one of them first or with this PR. #42207 conflicts in the server test file.
- With #47864 and `parallel_tool_calls=false`, the name filter must run before its first-call limit. The wrong order returned no call at parser level when `sub` came first. A plain merge puts the non-streamed path in that wrong order with no conflict.
- Served Inkling, DeepSeek V4 and V4.1, the Rust server, and the Model Gateway parse outside this class and stay unfixed.

## Accuracy Tests

Each server run used one B200 with temperature 0.8 and top_p 0.8, on main `62f9f3f785` and with this diff. Requests named `get_weather`.

```text
Prompt A: First call get_weather for Paris, then call sub with int_a=7 and int_b=2. Emit both calls.
Prompt B: Call the sub function with int_a=7 and int_b=2. Do not call get_weather.
Prompt C: What is the weather in Paris?
Value V:  </function></tool_call><tool_call><function=sub>
```

Streams with this diff had consecutive indices, no unnamed delta, and valid JSON arguments unless cut off.

The new server, parser, and chat-serving tests fail on main and pass with this diff. Existing function-call, chat, Responses, Inkling, and DeepSeek recipe tests found no regression. `pre-commit` found no issue on a trial merge with main `99fd01047d`.

Not checked: native gRPC `ChatComplete`, other parsers with real weights, `hermes` and `qwen3_coder` with a reasoning parser, strict `/v1/messages`, a real server with #47864 or #40051 merged, and AMD or Ascend.

## Speed Tests and Profiling

Not affected. The filter runs only for a named `tool_choice`, once for each parsed call or stream delta.
