# [Fix] Triton SWA decode: read the full sliding window

[Upstream PR](https://github.com/sgl-project/sglang/pull/42402) · state: closed · merged: False

## Original PR description

## Motivation

Triton decode on sliding-window layers attends to one key fewer than the window: on every decode step past the window it drops the oldest in-window key. Prefill of the same tokens, and FlashInfer / fa3 / trtllm_mha decode, see the full window.

Triton is the default attention backend for Gemma 4 on every GPU except SM100 (H100 included), for gpt-oss on NVIDIA GPUs other than SM90/SM100, and for other attention-sink models there (e.g. Granite SWA), so this is their default decode path.

Same backend fix as #32087 by @v-code01, which was closed as idle without review. This PR also corrects the test reference that had pinned the short window, and the models whose runner-level window was only right because of it.

## Root cause

Models report `sliding_window_size` as the window minus one (Gemma 2/3/4 and gpt-oss return `config.sliding_window - 1`), and every consumer adds the query back:

- Triton extend keeps `q_pos <= k_pos + sliding_window_size`;
- FlashInfer decode clamps `seq_lens` to `sliding_window_size + 1`;
- fa3 / trtllm_mha take `sliding_window_size` as the left window.

Triton decode builds its window read stream with `min(seq_lens, sliding_window_size)` keys (`update_sliding_window_buffer`). Decode `seq_lens` already count the query, and the decode kernel has no window mask, so the stream is one key short.

Since #26517 the attention unit-test reference has encoded this as a Triton-only decode rule (`_SWA_DECODE_MIN_SEQ_LEN_WINDOW = {"triton"}`), and the SWA README listed `sliding_window_size + 1` as a mutation for the above-window case to catch. So the existing tests pass with the short window and fail on a fix.

Granite SWA, GraniteMoe SWA, Laguna and IQuestQ1 store `sliding_window - 1` in their layers but define no `get_attention_sliding_window_size`, so `resolve_sliding_window_size` falls back to the raw config window. That made their Triton decode right by accident, and makes their FlashInfer decode (which has no window mask either) read one key too many.

## Modifications

- `triton_backend.py`: decode (eager and CUDA-graph replay) reads `sliding_window_size + 1` keys (`_decode_window_len`, set at construction), and the CUDA-graph window index buffer is sized for it. Extend, target-verify and dLLM keep `min(prefix_lens, sliding_window_size)`; the extend kernel masks per query.
- `granite.py`, `granitemoe.py`, `laguna.py`, `iquest_q1.py`: report `sliding_window - 1`, as their layers use.
- `dense_attention.py` (test kit): one SWA reference rule for every backend. The per-backend classification existed only for Triton's short window; moving `"triton"` into the other set would leave an empty set and an error path that cannot fire, so it is removed.
- `swa/test_triton.py`: one eager decode case at the exact window edge (`seq_len == sliding_window_size + 1`). The existing cases already decode past the edge; their reference is what changed.
- `swa/README.md`: coverage and mutation notes updated; the "Next Work" item on the Triton above-window decode/reference detail is resolved here and removed.

Not changed here: MiMo-V2, Step3p5 and Jet-Nemotron pass the raw window to their layers and the runner alike, so every backend gives them window + 1 keys; with this PR Triton decode matches their prefill (their ports need the minus one, cf. #40981 for MiMo-V2). The aiter unified path passes `(sliding_window_size - 1, 0)`, which looks one key short as well.

## Accuracy Tests

On NVIDIA A100-SXM4-40GB, using upstream `5b5d7212`, Torch 2.13.0+cu130, Triton 3.7.1 and sglang-kernel 0.4.8:

- Triton SWA suite with `main`'s `triton_backend.py`: **3 failed**, all decode at or past the window edge (`swa_decode_window_edges`, `runner_cuda_graph_swa_decode_above_window`, `layout_swa_decode_page_boundary`). With the fix it passes.
- With the fix: `swa/{test_triton,test_flashinfer,test_torch_native,test_swa_out_cache_loc}.py`, `dense/{test_triton,test_flashinfer}.py` and `unit/layers/attention/test_triton_verify_metadata.py`: **49 passed** (124 subtests); `unit/dllm/test_gemma4_cuda_graph.py`, `unit/mem_cache/test_swa_eviction_interval.py`, `unit/layers/attention/test_kv_translate_ownership.py` and `dcp/test_dcp_layout_unit.py`: **28 passed** (35 subtests). Server-launching tests such as `test_gemma4_swa_triton_oob_regression.py` were not run.

Reproduce:

```bash
python3 test/registered/attention/unittests/swa/test_triton.py -v
```

End to end: `unsloth/gemma-3-1b-it` at `5b11413a10db4e486ef16a20101fd028f8f2499c` (sliding_window=512), BF16, TP1, `--attention-backend triton --disable-radix-cache`, CUDA graph on, `main` vs this PR. 24 prompts per group cut from the SGLang docs, sent one at a time so both servers see the same batches; greedy, 128 new tokens; then prompt + output re-scored in one prefill (`logprob_start_len` = prompt length).

- Prompt + output inside the window (65-376 + 128 tokens): decode log-probs **bit-identical** to `main` in 24/24 prompts.
- Prompt past the window (577-1089 tokens): decode log-probs differ from `main` in 24/24 prompts.

| | `main` | this PR |
|---|---|---|
| mean \|decode - prefill\| log-prob past the window (2294 tokens both runs generated) | 0.00715 | 0.00681 |
| few-shot GSM8K, 1319 questions (`python3 -m sglang.test.few_shot_gsm8k`) | 0.226 | 0.221 |

At a 512-token window one key is below the decode-vs-prefill numerical noise (per token, this PR is closer to prefill on 970 tokens and `main` on 986), and GSM8K is within noise. This is a consistency fix, not a model-quality claim; the unit tests check the window exactly.
