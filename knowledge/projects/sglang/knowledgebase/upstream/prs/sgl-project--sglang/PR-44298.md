# [Perf] [NVIDIA] dsa: Shard k-pool prefill rows across TP

[Upstream PR](https://github.com/sgl-project/sglang/pull/44298) · state: closed · merged: False

## Original PR description

## Motivation

Large k-pool prefills repeat indexer logits and top-k on every attention TP rank.

## Modifications

`SGLANG_OPT_USE_DSA_KPOOL_PREFILL_TP=1`, off by default, splits query rows across those ranks and gathers the indices. Existing configs do not change. The gate needs at least 4096 rows, and rows times pooled keys of at least 100 million. Context parallelism, scattered inputs, and graph capture stay replicated.

## Accuracy Tests

A registered test runs the real plan method on NCCL ranks at TP4 with synthetic inputs and compares sharded with replicated rows. It fails on a wrong offset or size, a lost row, a closed gate, a missing scattered check, or a rank over its share.

Validation on `70af701411`: this test on 4 B200s, one manual TP2 run, flag-off k-pool tests, and a RAGGED and PAGED probe at TP2 and TP4.

GSM8K and server numbers come from `f9b571c3b8`, with the same query rows and gather. GSM8K prompts do not open the gate. Long prompts do, and their greedy answers matched across instances.

```bash
# GLM-5.3-Flash FP8, 4 B200s, two instances per arm, with and without SGLANG_OPT_USE_DSA_KPOOL_PREFILL_TP=1
# test_glm53_flash_b200 low-latency recipe
python3 -m sglang.launch_server --model-path <GLM-5.3-Flash FP8 weights> --tp-size 4 \
  --dsa-prefill-backend trtllm --dsa-decode-backend trtllm --kv-cache-dtype fp8_e4m3 \
  --moe-runner-backend flashinfer_trtllm --reasoning-parser auto --tool-call-parser auto \
  --speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 6
sgl-eval run gsm8k --num-examples 200 --num-threads 64 --max-tokens 32768 \
  --temperature 1.0 --top-p 0.95 --thinking
```

Not verified on this head: full-model serving, DP2 x TP2, symmetric memory. Never verified: TP8, MSCCL++, full-model TP2, ROCm (gate opens there), other GPUs.

## Deliberate limits

- The test does not reach the 4096-row, 100 million, capture, or context parallelism checks.
- The test allows fewer than 5 differing rows, because a tie at the cutoff can swap a group. With `SGLANG_OPT_USE_TOPK_V2` off, the probe saw up to 6, unchecked for ties.

These limits are deliberate. Do not add code for them without a real input that reaches the case.

I compared replicated and sharded `_kpool_topk_by_row_chunks` at `f360044a9f` on four NVLink-connected B200s. This ran the PR’s row slicing, FP8 MQA logits, CUDA top-k transform and in-place NCCL gather, not a mocked collective. The inputs were synthetic: three requests, nonzero key offsets, 32 query heads of width 128, 2,048 pooled keys, `kpool=4`, `topk=512`, and 1,024-row budget chunks. Runtime: PyTorch 2.13.0+cu130, NCCL 2.29.7, DeepGEMM 2.8.0.

| Input | Replicated | Sharded | Output |
|---|---:|---:|---|
| 4,097 rows, shared page table with request indices, 7 padding rows | 0.325 ms | 0.267 ms | Same selected set on every row. All padding stayed `-1`. |
| 4,097 rows, per-query page table, 2 padding rows | 0.310 ms | 0.251 ms | Same selected set on every row. All padding stayed `-1`. |
| 16,384 rows, ragged offsets | 0.814 ms | 0.370 ms | One boundary tie described below. |

The sharded output was byte-identical across ranks within each gather. I would **not** require byte-identical top-k order across separate forwards: it varied even between two replicated passes. On ragged row `7462`, groups `90` and `156` also traded the last selected slot. Both logits had FP32 bits `0x428e664e`, with exactly 127 groups strictly above them and two tied for place 128. The same set difference occurred on the replicated control without sharding. A parity test should distinguish a tie at the cutoff from a missing or misordered query row.

Timings are median slowest-rank CUDA-event times over interleaved warm passes, including the gather. They measure the row method, not server prefill latency. The full planner, model accuracy and other TP sizes remain untested here.
