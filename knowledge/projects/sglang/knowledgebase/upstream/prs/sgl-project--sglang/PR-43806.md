# [UMBP] Share one direct-linker key across CP ranks for DeepSeek-V4 pools

[Upstream PR](https://github.com/sgl-project/sglang/pull/43806) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4 prefill context parallelism (`--enable-prefill-cp`, HIP CP-v2 from #34200, FP8 unified KV from #39923) leaves the **whole chunk on every CP rank** before it is cached:

| Where | What it does under CP |
|---|---|
| `models/deepseek_v4.py` (unified-KV and non-unified prefill) | `cp_materialize_global_token_order(kv)` gathers every rank's slice into global token order, then the backend writes it to the rank's own pool |
| `models/deepseek_v4.py`, V4.1 branch | "every rank writes the whole chunk's window KV" |
| `layers/attention/dsv4/compressor.py:450,512` | the compressor and indexer inputs are materialized in global order before compressing |

So every attention CP rank holds byte-identical pages, exactly like the attention TP ranks of an MLA model. The UMBP direct linker already collapses the TP term for such rank-replicated pools, but it keeps a per-rank `cp{attn_cp_rank}` term in every object key (`umbp_direct_linker.py::_storage_suffix`):

```
PCP4 prefill, one UMBP tier (1.5 TB hugepage DRAM):
  ATTN_CP0 TP0  UMBPDirectLinker ... rank_replicated=True suffix=cp0_pp0
  ATTN_CP1 TP1  UMBPDirectLinker ... rank_replicated=True suffix=cp1_pp0
  ATTN_CP2 TP2  UMBPDirectLinker ... rank_replicated=True suffix=cp2_pp0
  ATTN_CP3 TP3  UMBPDirectLinker ... rank_replicated=True suffix=cp3_pp0
```

Consequences:
- The tier stores `attn_cp_size` identical copies of every page: a 1.5 TB tier holds ~375 GB of distinct KV at PCP4 (~187 GB at PCP8), and starts evicting `attn_cp_size` times sooner.
- A CP deployment and a non-CP deployment of the same model cannot hit each other's pages, except through CP rank 0.
- Each CP rank can lose its own copy to eviction independently, so CP ranks disagree on what is restorable more often than they need to.

**Runtime evidence** (DeepSeek-V4-Pro-0813, 1P1D, prefill TP4 + PCP4 + UMBP linker, decode TP8, c48 AgentX trace replay, MI355X): instrumented each prefill rank's `batch_put_ranges_from_ptr` to log the rank-independent page key and a CRC32 of the object's leading 256 KiB.

First 200 pages each rank put per pool (keys compared with the CP term masked):

| Pool | Object bytes | CRC covers | Keys | On all 4 CP ranks | CRC equal | CRC differ |
|---|---|---|---|---|---|---|
| `deepseek_v4_c4` | 1,966,080 | first 256 KiB | 200 | 200 | 200 | 0 |
| `deepseek_v4_c4_indexer` | 122,880 | whole object | 200 | 200 | 200 | 0 |
| `deepseek_v4_c128` | 63,488 | whole object | 200 | 200 | 200 | 0 |
| `deepseek_v4_c4_indexer_scale` | 7,680 | whole object | 200 | 200 | 200 | 0 |

All 800 keys carry distinct, non-zero CRCs, so the matches are real KV rather than empty pages, and each rank stored them under its own suffix (`cp0_pp0` .. `cp3_pp0`). One ~2.06 MiB page is therefore held four times.

## Plan

1. **This PR**: let a pool group declare it is replicated across CP ranks, declare it for DeepSeek-V4, and have the UMBP direct linker drop the per-rank CP term for such groups.
2. Mooncake direct linker: same key scheme, but it writes replicated pools from one owner (`offload_owner = not rank_replicated or tp_rank == 0`). Collapsing its CP term needs that owner rule extended to CP first, or every CP rank puts the same object. Follow-up.
3. DSA (DeepSeek-V3.2 / GLM): I could not find a CP gather of KV before caching on CUDA/HIP, so its group stays per-CP-rank until that is verified. Follow-up.

## Design

`DevicePoolGroup` gains `cp_replicated: bool = False` next to `rank_replicated`. `_build_deepseek_v4_device_pool_group` sets it; nothing else does.

`_storage_suffix` (UMBP direct linker):

| Group | Before | After |
|---|---|---|
| sharded (MHA), any CP | `tp{t}_cp{c}_pp{p}` | unchanged |
| rank-replicated, not CP-replicated (DSA) | `cp{c}_pp{p}` | unchanged |
| rank- and CP-replicated (DeepSeek-V4) | `cp{c}_pp{p}` | `cp0_pp{p}` |

Why it is safe:
- The CP term is kept as the literal `cp0`, so keys of every non-CP deployment are unchanged (no persisted-key migration) and CP and non-CP deployments now share keys.
- Every rank still writes, as in the TP-replicated case: a Local-mode tier is private to its rank and a standalone server is per node, so a page written by one rank only would not be reachable from the others.
- On a shared tier (standalone server, distributed pool) the repeated writes cost no space: the page backend answers a put for a key it owns with `kSuccessAlreadyExists` without allocating, and two writers that race past allocation are settled at commit ("keep first, drop new pages"), both in mori `page_backend.cpp`. So the tier keeps one copy per page instead of `attn_cp_size`.
- Restorability is already agreed by a MIN all-reduce over `attn_cp_group` then `attn_tp_group` (`unified_radix_cache.py::_all_reduce_attn_groups`), so every CP rank loads the same prefix, now from one object.
- PP still shards layers and keeps its term.

## Tests

- `test_umbp_direct_linker_rank_keys.py`: a CP-replicated group yields one suffix (`cp0_pp1`) across 2 TP x 4 CP ranks; a group that is not CP-replicated keeps one key per CP rank.
- `test_linker_pool_assembler.py`: the DeepSeek-V4 group declares `cp_replicated`, the DSA group does not.
- 17 passed on this branch; the new and updated cases fail on `main` (6 failed, 11 passed).

## Limitations

- UMBP direct linker only; Mooncake and DSA are the follow-ups above.
- CP ranks 1..N still issue their puts; on a shared tier they resolve to "already exists" instead of a copy. Skipping them outright would also save the round trips, but only when the tier is known to be shared, so it is left out here.
- The HiCache L3 path (`storage_attachment.py`) is not touched.
