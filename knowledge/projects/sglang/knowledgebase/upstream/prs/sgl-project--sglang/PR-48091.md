# [Perf] [NVIDIA] mxfp4: Bound SM90 preprocessing memory

[Upstream PR](https://github.com/sgl-project/sglang/pull/48091) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4 SM90 MXFP4 loading creates full-layer weight/scale copies in W4A16 and large FP4 payload-rewrite intermediates in the Humming W4A8 path. These temporary allocations can exhaust VRAM even when the final model weights fit.

## Changes

Prepare eight experts at a time and copy the fresh weight and folded-scale outputs back into the input storage. The same private helper handles W4A16 and Humming, preserving the latter's per-expert residuals and existing 64x compensation. The final partial chunk is supported.

The helper comments explain both the independence argument and its allocation precondition: loader inputs are contiguous; non-contiguous inputs still work through `.contiguous()`, which can allocate full-size copies and is outside the bounded-scratch claim. SM120 and forward dispatch are unchanged.

The reasoning follows the pinned FlashInfer v0.7.2 implementation:

- The [weight binding](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/csrc/fused_moe/cutlass_backend/flashinfer_cutlass_fused_moe_binding.cu#L1659-L1702) interleaves each expert independently; the inner-dimension alignment checks are unchanged by splitting dim 0.
- [Scale folding](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/fused_moe/prepare.py#L331-L402) preserves dim 0 and element count.
- [Humming preprocessing](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/fused_moe/prepare.py#L112-L327) computes range clamps and residuals per expert, followed by elementwise payload rewriting. No reduction crosses experts.

## Loading memory and time

Measured the complete `process_weights_after_loading` method with synthetic contiguous checkpoint-format inputs (random FP4 bytes and E8M0 bytes in [110, 140)). Both arms use the same compiled FlashInfer kernels. Peak means **additional allocated CUDA memory above the already-loaded inputs**, including weight/scale preparation and residuals.

Three samples per configuration after warm-up; peak is identical across all three samples. Times are synchronized wall-time medians, including the method's existing `empty_cache()`. Hidden size is 5120 and intermediate size per rank is 640.

| Path | Local experts | Main peak (MiB) | Updated peak (MiB) | Main median (ms) | Updated median (ms) |
|---|---:|---:|---:|---:|---:|
| W4A16 | 17 | 85.54 | 27.56 | 0.829 | 1.109 |
| W4A16 | 256 | 1276.00 | 27.56 | 5.653 | 6.555 |
| Humming W4A8 | 17 | 2027.15 | 955.13 | 7.349 | 8.457 |
| Humming W4A8 | 256 | 30500.00 | 955.14 | 86.478 | 87.785 |

At 256 experts, temporary peak falls by **97.84% for W4A16** and **96.87% for Humming**. Relative to the preceding PR's weight-only optimization, W4A16 peak falls from 76.00 to 27.56 MiB. Scale chunking does not make the whole-method peak 2.4 MiB: the weight-chunk temporary still contributes.

This trades some startup time for substantially lower peak memory. Short timings are noisy; no inference-throughput or full-model quality improvement is claimed.

**2. The claim that makes this safe is stronger than the test shows, and it's provable from the binding.**

"Each expert's layout is independent" is load-bearing for correctness at arbitrary shapes, so it's worth saying where it comes from. The wrapper is `weight = weight.contiguous(); out = torch.empty_like(weight)` plus one binding call (`python/flashinfer/fused_moe/prepare.py:406-463`), and the binding is (`csrc/fused_moe/cutlass_backend/flashinfer_cutlass_fused_moe_binding.cu:1659-1702`):

```c++
int64_t const per_expert_bytes = n * (k / 2);
for (int64_t e = 0; e < num_experts; ++e) {
  uint8_t* src_e = src + e * per_expert_bytes;
  uint8_t* dst_e = dst + e * per_expert_bytes;
  ... interleave_fp4_weights_for_sm90_mixed_gemm(src_e, dst_e, n, k, stream);
}
```

`num_experts` never enters the per-expert index math and there is no cross-expert state, so a dim-0 chunk does byte-for-byte the same work as the full tensor for every shape — not just the one the test samples. Two corollaries that matter for your version: the `n % 16 == 0` / `k % 64 == 0` guards and `CHECK_CONTIGUOUS(weight)` are all on dims or properties the split leaves alone (a dim-0 chunk of a contiguous tensor is contiguous), and because `out` is always a fresh allocation, `block.copy_(...)` cannot alias its own input.

Related: `(16, 17, 768, 384, 2)` is the first partial-tail case in that file at all — 8 experts is exactly one chunk, so the three pre-existing params only ever exercised the full-chunk path. That is a real gap being closed; I'd just not read the shape coverage as the argument for general correctness when the binding gives the argument for free.

**3. After this patch the whole residual temporary peak is the scale fold, and the same trick bounds it with less risk.**

Your table decomposes exactly. At 256 experts / hidden 5120 / inter 640: w13 = 256 × 1280 × 5120 / 2 = 800 MiB and w2 = 400 MiB, so "removes 1200 MiB" is precisely the two full-size weight copies. E8M0 is one byte per 32 weights against half a byte per weight, so the scales are 1/16 of that: 50 + 25 = 75 MiB — which is your reported 76 MiB "after" peak. The scales are not the small leftover: at E=256 the 8-expert weight scratch is 1200/32 ≈ 37.5 MiB, so the scale copies are now the dominant transient, about 2× it.

They're also easier to chunk than the weights, because there is no kernel involved. `interleave_moe_scales_for_sm90_mixed_gemm` (`prepare.py:331-402`) is pure PyTorch — `reshape(e, rows//64, m_slices, folded_m, k128, groups).permute(0, 1, 4, 3, 2, 5).contiguous().reshape(...)` — dim 0 is never permuted, the element count is preserved, and both shape guards (`rows % 64`, `kgs % (128 // group_size)`) are inner-dim. And this very file already does the in-place write-back on the other branch: `mxfp4_flashinfer_cutlass_moe.py:172-173` runs `scale_u8.copy_(block_scale_interleave(scale_u8).reshape_as(scale_u8))` for SM120. Same shape of change would take 76 MiB → roughly 2.4 MiB at that configuration. Not asking you to fold it in if you'd rather keep the PR one-idea.

**4. Question about the Humming arm being left alone.**

`--flashinfer-mxfp4-moe-precision fp8` on SM90 goes through `preprocess_moe_weights_for_sm90_mixed_gemm_humming` (`prepare.py:247-327`), and read top-down its transient looks larger than the 1200 MiB you just removed: `_process_humming_mxfp4_w4a8_payload` builds `fp4_codes` and `delta` both shaped `[E, rows, K]` and casts *both* to `torch.long` before the LUT gather (`prepare.py:236-243`) — two int64 tensors at 16× the packed weight bytes — and only then interleaves the result into a third full-size weight. I'm deliberately not putting a number on it: I have not measured that arm, its operand lifetimes are not readable off the source, and it does load on our H20, so whatever the peak is, it fits there. But your independence argument carries over — the only cross-element step is the per-expert clamp at `prepare.py:141-144`, which reduces a `[E, -1]` view along dim 1. Is Humming out of scope because you wanted to keep this reviewable, or is there something in that preprocess that blocks chunking?

**5. One small thing.**

`weight.view(torch.uint8).contiguous()` means a non-contiguous input gets a full-size copy, the chunk loop writes into the copy, and the helper returns it — correct, but the bounded-scratch property quietly no longer applies, with nothing saying so. It's fine in practice (the loader hands these over contiguous) and your description does state it; a line at the helper would stop a later reader from assuming 8-expert scratch unconditionally.

Thanks for reporting the peak as "additional above the already-loaded input tensors" and for the per-row medians — that is the right way to make a startup-memory claim checkable.
