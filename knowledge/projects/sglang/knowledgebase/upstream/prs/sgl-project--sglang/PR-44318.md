# [Fix] sglang-grpc: Forward max_new_tokens=null to Python when wire field is unset

[Upstream PR](https://github.com/sgl-project/sglang/pull/44318) · state: closed · merged: False

## Original PR description

## Background

On the native gRPC server (`--grpc-port`), a `Generate` request whose `sampling_params.max_new_tokens` is omitted on the wire silently stops at 128 tokens. HTTP callers asking for no explicit cap do not see this issue. Issue reported in #44121.

## Problem

`sampling_params_to_map` in `rust/sglang-grpc/src/utils/request_utils.rs` skipped optional fields that were `None`, so an unset `max_new_tokens` produced a map with no such key. On the Python side `SamplingParams.max_new_tokens` defaults to 128, so the scheduler then treats that concrete value as a hard cap.

By contrast an HTTP caller who sends `max_new_tokens: null` ends up with `SamplingParams.max_new_tokens=None`, which `scheduler.init_req_max_new_tokens` handles correctly — it substitutes a `1 << 30` soft upper bound and further clips by memory / max_req_len.

So a gRPC caller that does not care about length (e.g. an agent streaming arbitrarily long reasoning) gets a hard 128-token ceiling no HTTP caller ever faces.

## Solution

Make the `max_new_tokens` key always present in the translated dict, mapping gRPC `None` to JSON `null`. msgspec on the Python side then keeps `max_new_tokens=None`, and the scheduler's existing no-explicit-cap branch applies.

Other optional sampling parameters (temperature, top_p, top_k, ...) are still omitted when unset — their defaults are benign. Only `max_new_tokens` exhibits a user-visible behaviour difference between the two representations, so the fix is scoped to it.

## Testing

- Added three Rust unit tests in `rust/sglang-grpc/src/utils/request_utils.rs`:
  - `sampling_params_forward_max_new_tokens_when_unset` — converter emits JSON null, not a missing key
  - `sampling_params_forward_max_new_tokens_when_set` — preserves Some(v) as an integer
  - `generate_dicts_forward_max_new_tokens_when_unset` — regression for both request builders (TextGenerateRequest, GenerateRequest)
- `cargo test --lib` in `rust/sglang-grpc`: 19 / 19 tests pass (previous suite was 16; 3 new, 0 broken).
- Pure Python sanity check with an equivalent `msgspec.Struct` confirms: dict `{}` -> default 128, dict `{'max_new_tokens': None}` -> None, dict `{'max_new_tokens': 2048}` -> 2048.

## Scope

Single file, one conditional -> unconditional insertion, three tests. No proto / Python / API changes; behaviour is strictly additive on the wire (one more key), and callers that passed an explicit value are unaffected.
