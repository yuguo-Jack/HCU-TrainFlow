# [Chore] attention: Remove the tokenspeed_mla backend and dependency

[Upstream PR](https://github.com/sgl-project/sglang/pull/44803) · state: closed · merged: True

## Original PR description

## Motivation

Remove the `tokenspeed_mla` attention backend and the `tokenspeed_mla==0.1.8` hard dependency it brings into every `pip install sglang`. On Blackwell, `cutedsl_mla` already covers the same ground as the default MLA decode backend: FP8 or BF16 KV, page size 32/64, decode context parallelism, and speculative verify of any width. Keeping a second CuTe DSL MLA backend means an extra pinned external package, an extra registry/dispatch/draft path, and extra override branches.

## Modifications

- **Backend removed:** `layers/attention/tokenspeed_mla_backend.py`. Also removed:
  - the `tokenspeed_mla` registry entry and DeepSeek MLA dispatch handler
  - the EAGLE draft decode/prefill factories and the `eagle_worker_v2` graph-support entry
  - `is_tokenspeed_mla_available`
- **Server args:**
  - `tokenspeed_mla` stays a **deprecated alias** for `cutedsl_mla`, using the same mechanism as `compressed` -> `dsv4` in `handle_deprecated_args`. It logs a warning and maps prefill to `trtllm_mla`. To keep what the old backend implied, it forces FP8 KV, and it sets `--speculative-attention-mode decode` when speculative decoding is on.
  - `tokenspeed_mla` is dropped from the chunked-prefix choices, the page-major and DCP allowlists, and the page-size and KV-dtype checks.
  - The Kimi-K3 DCP override no longer has a `tokenspeed_mla` branch. Alias users arrive as `cutedsl_mla` with FP8 KV.
- **FP8 prefill path kept:** the model-side MHA hooks `prepare_prefill_qkv` and `pack_prefix_chunk_kv` (fused RoPE + FP8 quantize, direct FP8 KV-cache write, packed FP8 prefix chunks) move to `CuteDslMLAPrefillBackend`, a `TRTLLMMLABackend` subclass in `cutedsl_mla_backend.py`.
  - `create_trtllm_mla_backend` builds it only when the decode backend is `cutedsl_mla` and KV is FP8. With `cutedsl_mla`, extend resolves to that prefill child. Standalone `trtllm_mla` is unchanged.
  - `TRTLLMMLABackend._run_prefill_kernel` skips re-quantizing inputs that are already FP8.
  - `_dspark_verify_on_decode_backend` drops its now-unused `kv_cache_dtype` argument.
- **Dependency:** `tokenspeed_mla==0.1.8` is removed from `python/pyproject.toml`.
- **Docs:**
  - The Kimi-K2.5/K2.6/K2.7 cookbook commands on B300/GB300 switch from `--attention-backend tokenspeed_mla` to `cutedsl_mla`, still with `--kv-cache-dtype fp8_e4m3`.
  - When speculative decoding is enabled, the K2.5/K2.6 commands also add `--speculative-attention-mode decode` (see Speed Tests).
  - The attention-backend table and the Kimi-K3 note drop the entry. The server-argument choices keep it as the alias.
- **Tests:**
  - The Kimi-Linear DCP4 / DCP+DSpark / PD-DCP4 tests switch to `cutedsl_mla`.
  - Removed `mla/test_tokenspeed_mla.py`, the tokenspeed stride-parity case and the tokenspeed DCP-metadata class.
  - Allowlist and LSE-base assertions are updated.
  - New `TestTokenspeedMlaAlias` (`test_server_args.py`).

Not touched: `.agents/skills/llm-torch-profiler-analysis` still recognizes TokenSpeed and vLLM kernel names when triaging traces from those frameworks. That is trace tooling for other engines, not an sglang dependency.

## Why `--speculative-attention-mode decode` with speculative decoding

`cutedsl_mla` is decode-only; prefill resolves to `trtllm_mla`. With the default `--speculative-attention-mode=prefill`, target verify runs on the prefill backend (`trtllm_mla`), while `tokenspeed_mla` used to run verify itself. That made decode up to 21% slower at long context. `decode` routes verify to `cutedsl_mla` and recovers parity (tables below).

## Accuracy Tests

GSM8K, 1,319 questions, 5-shot, greedy (`python -m sglang.test.few_shot_gsm8k`), 4x GB300, TP4:

| Config | `tokenspeed_mla` (this PR's base) | `cutedsl_mla` (this PR) |
|---|---|---|
| Kimi-K2.5 INT4 (`moonshotai/Kimi-K2.5`) | 0.942 | 0.945 |
| Kimi-K2.5 NVFP4 + EAGLE3, node A | 0.938 | 0.936 |
| Kimi-K2.5 NVFP4 + EAGLE3, node B | 0.937 | 0.939 |
| Kimi-K2.5 NVFP4 + EAGLE3, decode-mode verify | 0.934 | 0.939 |

## Speed Tests and Profiling

**Setup:**
- **Hardware:** 4x GB300 (TP4), `--kv-cache-dtype fp8_e4m3`.
- **Arms:** `tokenspeed_mla` runs on this PR's base commit; `cutedsl_mla` runs on this PR.
- **Method:** `python -m sglang.benchmark.one_batch_server` on random prompts. Arms are interleaved tokenspeed, cutedsl, cutedsl, tokenspeed, and each cell is the mean of 2 server launches per arm. Launches agree within 0.5%, except one tokenspeed INT4 8K bs1 run (160 vs 167 tok/s).
- **Metrics:** decode is steady-state output tok/s; TTFT is the last-batch time to first token.
- **NVFP4 + EAGLE3** uses the GB300 nightly-test flags: `--quantization modelopt_fp4 --moe-runner-backend flashinfer_trtllm --mem-fraction-static 0.8`, EAGLE3 with 3 steps, topk 1 and 4 draft tokens. bs64 is skipped because EAGLE caps max running requests at 48. **Known cost:** at 64K, TTFT vs `tokenspeed_mla` goes from +13–14% without the hooks to +7–8% with them. The rest is the prefill attention kernel (`trtllm_mla` ragged vs `tokenspeed_mla`'s FMHA). GSM8K with the hooks: 0.937 (`tokenspeed_mla` 0.932 on the same box).

The ported hooks were also checked on GB300 without a model:
- Fused RoPE+FP8 Q/K are bit-exact vs fp32 RoPE then `.to(fp8)`.
- The prefix pack is bit-exact vs concat then `.to(fp8)`.
- Ragged prefill with pre-quantized FP8 inputs is identical (max abs 0) to feeding the same values in bf16.
- `create_trtllm_mla_backend` builds the subclass only for `cutedsl_mla` decode + FP8 KV.

The touched unit/GPU tests pass on GB300 (383 passed). The one failure, `TestDcpCommBackendDefault::test_a5_npu_supports_dcp`, also fails without this PR on that host.

Not run: the Kimi-Linear DCP tests on `cutedsl_mla`. The GB300 Kimi-K2.5 nightly tests this PR used to update were dropped upstream (#45308).
