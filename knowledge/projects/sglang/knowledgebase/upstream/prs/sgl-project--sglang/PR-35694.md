# [mem_cache] Bound FlexKV checkpoint stores and restore DSPARK cache checks

[Upstream PR](https://github.com/sgl-project/sglang/pull/35694) · state: closed · merged: True

## Original PR description

## Summary

FlexKV recomputes the finished-request store length from raw committed KV or output IDs after the parent radix checkpoint has honored `up_to`. A stop boundary or `strip_thinking_cache` can shorten the retained prefix, leaving the external store with token IDs and KV indices beyond that boundary. Cap the FlexKV store length at `up_to` so both paths retain the same prefix.

Restore the Inkling DSPARK decode-cache hit requirement from 0.90 to 0.99. The core speculative-overshoot fix, including the visible-stop cap and Mamba checkpoint selection, already landed in main through #39273, so the relaxed threshold from #35293 is no longer needed.

## Scope

- Bound FlexKV's external store by the checkpoint boundary.
- Restore the existing DSPARK E2E decode-cache hit threshold to 0.99.

LMCache already bounds its store input with `req.full_untruncated_fill_ids[:up_to]` and further limits it to the aligned resident prefix; it needs no equivalent change.

## Validation

- Formatting, lint, and pre-commit checks passed for the retained changes.
- Local isolated validation of the FlexKV cap passed all 6 scenarios (`topk=None/1/2`, truncated/unchanged boundary). Removing the cap failed the 3 truncated-boundary scenarios while the unchanged-boundary controls passed. This isolated validation bypassed unrelated imports and dependencies; it is not a full integration test.
- No new unit test is included. Full CPU CI and the 4-GPU B200 E2E test have not been rerun locally for this revision; the local full test entry point requires Triton, unavailable in this macOS environment.

Earlier cache-hit performance measurements validated the core fix already in main and do not represent an additional performance gain from this diff.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Discard Mamba checkpoints newer than the capped key**

When unified radix caching is used for a hybrid SSM model with `extra_buffer`, the newly capped length can be earlier than `req.mamba_last_track_seqlen`. `MambaComponent.prepare_for_caching_req()` still captures the active checkpoint at that later position, while `UnifiedRadixCache.cache_finished_req()` truncates the key to this returned length and attaches the checkpoint to the resulting earlier leaf. A continuation matching that leaf can therefore restore Mamba state that has already consumed the speculative tokens excluded from its key, causing incorrect generation; the checkpoint must instead be rolled back to a valid boundary or omitted when it lies past this cap.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Propagate the cap to external cache stores**

With `--enable-lmcache` or `--enable-flexkv`, this cap is honored only by the radix-cache superclass: `LMCRadixCache.cache_finished_req()` and `FlexKVRadixCache.cache_finished_req()` subsequently rebuild their store ranges from `req.kv_committed_len` (or `len(req.output_ids) - 1`) instead of `kv_len_to_handle`. A speculative stop overshoot is consequently still written into the external key, and the async store may read its KV indices after `release_kv_cache()` frees that newly excluded tail. Those wrappers need to use the effective capped length as well.
