## Motivation

`XPUAttentionBackend.init_forward_metadata_out_graph()` built the decode page
table with separate PyTorch ops each step: strided gather from `req_to_token`,
floor-divide by `page_size`, cast to `int32`, copy into the preallocated
`page_table`, zero the trailing columns; plus separate ops for
`cache_seqlens_int32` and `cu_seqlens_k`, and a separate SWA page-table copy.

The NVIDIA FlashAttention backend already does all of this with one fused Triton
kernel, `normal_decode_set_metadata()` in
`python/sglang/kernels/ops/attention/metadata.py`. The kernel is plain Triton
with no CUDA-specific intrinsics and runs unchanged on Triton's XPU backend,
but the XPU backend did not use it.

This change calls that existing kernel from the XPU backend. No new kernel is
introduced; the Intel attention kernels, the graph runner and the KV-cache
allocator are untouched.

## Modifications

**`python/sglang/srt/layers/attention/xpu_backend.py`** (modified)

- Import `normal_decode_set_metadata` alongside the other helpers already
  imported from `flashattention_backend`.
- New private method `_set_decode_page_metadata()` issues one fused launch for
  `cache_seqlens_int32`, `cu_seqlens_k`, `page_table` and, for hybrid-SWA
  models, `swa_page_table`. It forwards `seq_len_delta` (= `kv_len_offset`) so
  target-verify and draft-decode keep their KV extension, and passes the tight
  bound `max_seq_pages = cdiv(max_seq_len_k, page_size)`.
- `init_forward_metadata_out_graph()` calls it for the ordinary
  (non-encoder-decoder) branch. The encoder-decoder branch keeps its original
  PyTorch implementation; the seq-len cast and cumsum moved into that branch.
- The separate SWA page-table gather/translate/copy block is removed. The fused
  kernel writes `swa_page_table` through `full_to_swa_index_mapping`, which is
  what `SWAKVPool.translate_loc_from_full_to_swa()` does.
- Net ~ -30 / +40 lines; one Triton launch replaces 6-8 PyTorch ops per decode step.

**`test/registered/attention/test_normal_decode_set_metadata.py`** (modified)

- Existing kernel test now runs on XPU as well as CUDA/ROCm (device from
  `get_device()`, skip only if neither is available).
- Registered for XPU CI: `register_xpu_ci(est_time=15, suite="stage-b-test-1-gpu-xpu")`.

**`benchmark/kernels/bench_xpu_decode_metadata.py`** (new)

- Standalone correctness + latency comparison of the previous PyTorch block vs
  the fused kernel on XPU. Loads the kernel from the repo file, so it needs only
  torch and triton. Exits non-zero if any live entry differs.

**Behavioral note: page-table tail columns.** The previous XPU block zeroed
columns past the batch-wide max page count every step. The fused kernel writes
only each request's live prefix (`cdiv(seq_len + delta, page_size)` pages) and
leaves the rest untouched. This is the kernel's documented contract and what the
FlashAttention backend already relies on: attention kernels bound their reads by
`cache_seqlens_int32`, and stale tail entries are always in-range page ids from
earlier steps (or zero from allocation), so whole-table gathers in the
chunked-attention path stay in bounds. Validated end to end below.

**Reproduction notes for XPU.** The decode graph is opt-in on XPU
(`--cuda-graph-backend-decode full`); without it decode runs eagerly through
`init_forward_metadata()` and this change is not exercised. The `intel_xpu`
backend accepts `--page-size` 64 or 128 only; other values are coerced to 128.

## Accuracy Tests

Environment: 1x Intel Arc Pro B70, torch 2.13.0+xpu, Triton 3.7.2,
sglang-kernel-xpu 0.3.0, image built from `docker/xpu.Dockerfile`.

| Check | Result |
|---|---|
| `python3 -m pytest test/registered/attention/test_normal_decode_set_metadata.py` on XPU | 16 passed, 8 subtests passed |
| `benchmark/kernels/bench_xpu_decode_metadata.py`: `cache_seqlens`, `cu_seqlens_k`, all live `page_table` entries vs previous PyTorch block | exact match, 36 configs (bs 1-32, ctx 1K-8K, page 1/16/64) |
| GSM8K 5-shot, 200 questions, temperature 0, Qwen2.5-1.5B-Instruct BF16, `--page-size 64 --cuda-graph-backend-decode full`, fused path | accuracy 0.625, 0 invalid |

Server log confirmed the decode graph captured (3.4 s) and every decode batch
ran through it, so the fused path was exercised on each decode step.

## Speed Tests and Profiling

**Metadata preparation, standalone** (host-inclusive latency per call,
`python3 benchmark/kernels/bench_xpu_decode_metadata.py --markdown`):

| bs | ctx | page | pytorch (us) | pytorch + .item() sync (us) | fused (us) | speedup |
|---|---|---|---|---|---|---|
| 1 | 8192 | 64 | 97.4 | 124.3 | 31.5 | 3.1x to 3.9x |
| 4 | 8192 | 64 | 103.8 | 130.6 | 31.3 | 3.3x to 4.2x |
| 16 | 8192 | 64 | 104.0 | 131.5 | 32.5 | 3.2x to 4.0x |
| 32 | 1024 | 64 | 103.5 | 130.8 | 32.3 | 3.2x to 4.0x |
| 32 | 8192 | 64 | 104.8 | 131.6 | 32.5 | 3.2x to 4.0x |

Latency is flat in batch size and context on both sides: the cost is launch
overhead, not bandwidth. Absolute microseconds vary with GPU clock state; the
ratios are stable.

**End-to-end serving** (`python3 -m sglang.bench_serving --backend sglang
--num-prompts 300 --max-concurrency {1,32}`, Qwen2.5-1.5B-Instruct BF16,
`--attention-backend intel_xpu --page-size 64 --cuda-graph-backend-decode full
--mem-fraction-static 0.8`; only `xpu_backend.py` differs between the servers;
one run per cell):

| Concurrency | Metric | Before | After | Change |
|---|---|---|---|---|
| 1 | Median ITL | 6.33 ms | 6.31 ms | -0.3% |
| 1 | Median TPOT | 6.32 ms | 6.30 ms | -0.3% |
| 1 | Output throughput | 155.1 tok/s | 155.4 tok/s | +0.2% |
| 32 | Output throughput | 2494 tok/s | 2724 tok/s | +9.2% (*) |
| 32 | Median TPOT | 10.88 ms | 9.95 ms | -8.5% (*) |
| 32 | Median ITL | 8.27 ms | 8.29 ms | 0 |

(*) The baseline run at concurrency 32 contained a ~1 s stall (max ITL 886 ms
vs 133 ms after), so these cells are single-run observations, not a claimed gain.

Interpretation: at concurrency 1 the end-to-end effect is neutral, as expected.
With the overlap scheduler the host-side metadata work runs while the device
executes the previous step, so removing ~70-100 us of host time does not
shorten a 6.3 ms step; the ~20 us that does show up matches replacing several
tiny device kernels with one. The value of this change is 3-5x faster metadata
preparation, 5-7 fewer launches per decode step, and the XPU backend sharing
the fused path with the FlashAttention backend instead of maintaining its own
PyTorch version.

## 1. PR-level comment: repeated benchmark runs

Done. I ran five alternating OLD/NEW rounds at concurrency 32 with 300 prompts, using
Qwen2.5-1.5B-Instruct in BF16 and:

```
--attention-backend intel_xpu --page-size 64 --cuda-graph-backend-decode full --mem-fraction-static 0.8
```

All runs used the same container and GPU (Arc Pro B70), with exclusive GPU access
verified before the runs. Only `xpu_backend.py` differed between OLD and NEW, and the
server was restarted from scratch for each run.

| Concurrency 32 | OLD median (range) | NEW median (range) | Δ medians |
|---|---|---|---|
| Output throughput (tok/s) | 2502 (2422–2506) | 2517 (2513–2524) | +0.6% |
| Median TPOT (ms) | 10.65 (10.56–11.21) | 10.45 (10.40–10.51) | −1.9% |
| Max ITL (ms) | 632 (578–683) | 630 (549–745) | ≈ unchanged |

The repeated runs do not reproduce the earlier single-run +9% throughput result. NEW
had higher throughput and lower median TPOT in all five paired rounds, with a narrower
observed range for both metrics. Max ITL was comparable, with overlapping ranges; these
measurements alone do not establish the cause of the stalls.

The measured end-to-end improvement is therefore small under this configuration. This
is consistent with the overlap scheduler hiding much of the metadata-preparation
overhead. The main benefits remain the measured 3–5× faster metadata preparation, 5–7
fewer launches per decode step, and reuse of the shared fused kernel instead of
maintaining an XPU-specific PyTorch implementation.

## 3. Inline comment: XPU full-graph backend regression coverage

Added and pushed `test/registered/e2e/xpu/test_xpu_fused_decode_metadata_graph.py`,
registered with `register_xpu_ci(est_time=600, suite="stage-b-test-1-gpu-xpu")`.

This implements the dense and SWA buffer-reuse coverage, including ordinary-decode
page-boundary crossings. The requested speculative page-boundary case remains
outstanding, as noted below.

The test launches a real server with:

```
--attention-backend intel_xpu --page-size 64 --cuda-graph-backend-decode full
--cuda-graph-max-bs-decode 8 --max-running-requests 8 --enable-deterministic-inference
```

This configuration exercises the new backend wiring through the full decode-graph
path, rather than testing the shared kernel in isolation.

**Buffer reuse and stale tails.** The test first records each prompt's greedy output
individually at batch size 1, then flushes the cache. It next runs eight approximately
1,200-token prompts, populating roughly 19 live pages per metadata row, before running
the prompts under test as a batch of eight.

The long batch and the subsequent test batch target the same batch-position-indexed
metadata rows. Shorter requests therefore reuse rows whose tails retain page ids from
the preceding long requests. The batched output must match the single-request
reference token for token. Deterministic inference (supported by intel_xpu) is enabled
so this cross-batch-size comparison is exact.

**Models and checks**

| Test class | Model | Metadata exercised |
|---|---|---|
| `TestXPUFusedDecodeMetadataDense` | Qwen/Qwen2.5-1.5B-Instruct | `page_table` |
| `TestXPUFusedDecodeMetadataSWA` | google/gemma-4-E2B-it (`hybrid_swa=True`, sliding_window=512) | `page_table` and `swa_page_table` through `full_to_swa_index_mapping` |

Each class runs three checks:

- `test_short_after_long_matches_single`: short requests reuse rows previously
  populated by approximately 19-page requests.
- `test_mixed_lengths_match_single`: long and short requests share one batch after
  buffer reuse.
- `test_page_boundary_lengths_match_single`: natural chat-formatted prompts of spread
  lengths exercise page-boundary crossings during decode. The test reads the
  server-reported `prompt_tokens` and asserts that at least three rows satisfy
  `(len % 64) + MAX_NEW_TOKENS >= 64`, i.e. `cdiv(seq_len, 64)` ticks over mid-decode
  on the reused rows.

The SWA model was selected because it takes the hybrid-SWA path; Gemma-2/3 are not on
the `is_hybrid_swa_model` allowlist and would not exercise this wiring.

Local result: **6 passed** on Arc Pro B70 using an image built from
`docker/xpu.Dockerfile`. The dense `short_after_long` case also passes with the
original backend, as expected.

**Remaining: speculative page-boundary crossing.** The tests above do not yet cover the
requested speculative case end to end. The kernel unit tests cover `seq_len_delta`, but
they do not validate the speculative backend wiring.

The existing `test_spec_eagle_intel_xpu.py` uses `--disable-decode-cuda-graph`, so it
does not establish coverage of this path. I am investigating the supported
EAGLE + full-decode-graph configuration on intel_xpu now and, if supported, will add a
regression case where `seq_lens + kv_len_offset` crosses a page boundary. If that
configuration is unsupported, I will report the limitation explicitly rather than
treating the kernel-only coverage as equivalent.
