# [Doc] minimax-m3: Route GB300 decode to trtllm_mha in the cookbook recipe (prefill stays fa4)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47187) · state: open · merged: False

## Original PR description

## Motivation

Follow-up to #47153, where a maintainer asked for this cookbook PR.

On GB300 (TP4, MXFP8 recipe), MiniMax-M3's full-attention **decode** is ~2x
faster on FlashInfer's trtllm-gen paged decode (the `trtllm_mha` backend's
decode entry, `trtllm_batch_decode_with_kv_cache`) than on the recipe's
fa4 path — measured 22/22 workload classes at the serve's shard geometry
(16 Q heads / 1 KV head / head_dim 128 / bf16 KV / page 128). **Prefill
points the other way** (fa4 ~1.34x faster than the best FlashInfer form,
21/24 classes), so the right recipe is a per-phase split, which SGLang
already expresses: keep `--attention-backend fa4` (serves prefill and keys
the page-128 auto-force MSA requires) and add `--decode-attention-backend
trtllm_mha`. Current `main` already allows page 128 for `trtllm_mha`
(trtllm-gen dynamic tokens-per-page kernels, FlashInfer >= 0.6.12), so no
code change is needed — but the recipe never engages it, and the pre-built
`dev-cu13-minimax-m3` image (last pushed 2026-06) predates that support
(it still clamps `trtllm_mha` to page 64, which MSA rejects). See #47153
for the full writeup.

> **Dependency: this change only reaches users once the dev image is
> rebuilt.** We cannot rebuild `dev-cu13-minimax-m3` ourselves — it comes
> out of the SGLang/model-vendor release pipeline. On the current image
> (tag last pushed **2026-06-15**) the added flag would be rejected by the
> old page-size clamp; on a build from current `main` it works with stock
> code. The rebuild ask is the first item in #47153.

As a second data point for "the rebuild, not new code, is what unlocks
measured gains": we also independently validated upstream's newer MXFP8
**dense-GEMM** default on the same GB300 recipe. Routing the MXFP8 dense
GEMMs from the frozen image's Triton block-scaled kernel — a kernel that has
since been **deleted entirely on main**, where FlashInfer `mm_mxfp8` is the
default route — measured **+11.3% p90** interactivity at concurrency 20
(same node for baseline and after; **+9.1%** against an FlashInfer-version-
only control arm, vs a stock noise band of ~1.6-3.2%), and additionally
restores the N=2464 shape family that the old Triton kernel's own
`n % block_n == 0` assert rejected (~24% of this serve's MXFP8 dense-GEMM
stream). That fix needs **zero recipe changes** — it reaches recipe users
automatically on a rebuilt image.

## Modifications

Docs/recipe only, scoped strictly to GB300:

- `docs/src/snippets/configs/MiniMaxAI/minimax-m3.jsx`: the GB300 · MXFP8 ·
  balanced cell adds `--decode-attention-backend trtllm_mha` (with a comment
  explaining the split and the current-main build requirement). B200 and
  GB200 cells are untouched — B200 is TP8 (different shard geometry) and
  GB200 was never directly benchmarked, so both intentionally stay fa4-only.
- `docs/cookbook/autoregressive/MiniMax/MiniMax-M3.mdx`: a `<Note>` under the
  existing fa4/page-128 gate paragraph documenting the split, why fa4 stays,
  the MSA-unaffected guarantee, and the image-staleness caveat (the split
  needs a build from current `main`; a rebuilt dev image would let the
  deploy panel's command work out of the box).

**Note on the cell's `verified: true` field:** I left it as it was, but the
verification sign-off is yours to adjudicate — happy to flip it to pending /
drop it until the cell goes through your validation pipeline, and happy to
re-run our A/B on a rebuilt image to confirm.

## Accuracy Tests

None run (docs-only change; no model code touched). The split was serving-
validated with zero request errors across all runs on both arms, and the
trtllm-gen decode kernel passed its numerical gate vs an fp32 reference on
all 22 measured classes at this geometry — but we did not run a task-accuracy
benchmark on the split recipe. Suggest including your standard check (e.g.
`sgl-eval run gsm8k`) in the cell's re-verification.

## Speed Tests and Profiling

Before/after on the documented GB300 recipe (TP4, MXFP8, `deep_gemm` MoE,
MSA active, page 128): 900 s agentic-replay serving benchmark per
concurrency; metric is normalized per-user interactivity (tok/s/user); one
run per cell, baseline/after pairs on distinct nodes of the same GB300
fleet. Baseline = the recipe as documented; after = identical serve +
`--decode-attention-backend trtllm_mha` (measured on the current dev image
plus a minimal in-container patch equivalent to what `main` already ships —
relaxing the image's old page-size clamp for decode-only `trtllm_mha`).

| concurrency | p50 interactivity | p90 | completed requests (fixed window) |
|---|---|---|---|
| 1 | **+12.6%** | +7.3% | +17.8% |
| 8 | **+11.1%** | +9.5% | +6.0% |
| 20 | **+14.5%** | +32.4% | +6.3% |
| 40 (saturated) | **+12.2%** | -8.0% | +5.3% |
| 60 (saturated) | **+14.4%** | -11.7% | +8.8% |

The +11-15% p50 band is uniform across five independent concurrencies vs a
<2% observed baseline run-to-run spread; at 40+ the serve runs against its
running-request cap, so the p90 there measures queueing and swings either
way while the median gain and completed-request counts persist. Zero request
errors on every run, both arms.

Dispatch verification (both phases): server log shows the hybrid backend
construction (`decode_backend=trtllm_mha, prefill_backend=fa4`) with no
page-size clamp warning; a FlashInfer API-log census shows
`trtllm_batch_decode_with_kv_cache` on every TP rank with **zero** FlashInfer
prefill plan/run calls (prefill stayed fa4), and the MSA sparse layers never
appear in the FlashInfer log (their kernel path is untouched in both phases).
