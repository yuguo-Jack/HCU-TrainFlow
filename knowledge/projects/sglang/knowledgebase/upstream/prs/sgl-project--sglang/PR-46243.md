# [Feat] rust: Render DeepSeek-V4/V4.1 prompts with deepseek-recipe in sglang-processor and sgl-router

[Upstream PR](https://github.com/sgl-project/sglang/pull/46243) · state: closed · merged: True

## Original PR description

The Python server renders DeepSeek-V4 / V4.1 prompts with deepseek-recipe (#45315). sgl-router still rendered them with Dynamo's encoder, so a request routed through it reached the worker with a different prompt than the same request sent to the worker directly. This moves `rust/sglang-processor`'s DeepSeek rendering onto deepseek-recipe's Rust crates, with the same SGLang wrapper the Python adapter applies, and sgl-router uses it.

## Changes

- `render/models/deepseek_v4.rs` (V4 and V4.1): SGLang's request semantics around recipe's Chat Completions conversion and V4 / V4.1 encodings, as `serving_deepseek_recipe.py` and `deepseek_recipe_renderer.py` apply them: thinking from `chat_template_kwargs` / `reasoning` / defaults / `SGLANG_DEFAULT_THINKING`, the request and default effort with the `SGLANG_DSV4_REASONING_EFFORT` / `SGLANG_DSV41_REASONING_EFFORT` fallback, V4.1 numeric budgets, message roles lowercased as Pydantic does, the final-assistant rule, `task`, and the handler's tool dumps.
- Prompts are segmented at their special tokens. `ChatFormatter::encode_request` encodes them with the checkpoint's `tokenizer.json`: special tokens by id, plain text without the added vocabulary, as recipe does, so text a user writes never becomes a control token. Dynamo's Hugging Face tokenizer backend cannot encode segments, so the formatter carries the tokenizer itself.
- The checkpoint effort-profile detection (`DeepSeekV4Profile`, `dsv4_reasoning_effort_profile`) and `deepseek_v41.rs` are removed. The message and tool dumps GLM-5.3, Kimi K3 and Qwen3.8 share move unchanged to `models/pydantic_dump.rs`.
- sgl-router: DeepSeek formatters load the checkpoint's `tokenizer.json` (the model's chat rendering fails to load without it) and take their prompt ids from `encode_request`. `SGLANG_DSV4_REASONING_EFFORT` / `SGLANG_DSV41_REASONING_EFFORT` must match the workers'.
- `deny.toml`: BSL-1.0 (xxhash-rust) and MIT-0 (borrow-or-share), from recipe's dependency tree.
- `generate_parity.py` builds the chat encoding adapter and records an adapter's prompt from its ids.

Output parsing in `lower_chat` still uses the processor's DeepSeek parsers; it moves to recipe in a follow-up.

## Tests

- `tests/fixtures/parity/deepseek-v4-flash-0731.json` and `deepseek-v4.1-flash.json` regenerated from the current Python path, plus a `special_token_text` case (special-token spellings in user text). Prompt text and token ids match for every case.
- Removed sgl-router's own DeepSeek fixtures, their generator and the tests over them (`tests/component/tokenizer/deepseek.rs`, the DeepSeek entry of `chat_render_parity`): the router now takes DeepSeek prompts from the processor, which the parity fixtures cover. The media check stays.
- `tests/openai_parity.rs` takes DeepSeek prompt ids from `encode_request`; the DeepSeek `/generate` prompt ids in `tests/fixtures/openai_parity/` are rerecorded from the current Python path (their recorded engine outputs and responses are unchanged; output parsing moves in the follow-up).
- Router unit tests that asserted Dynamo's DeepSeek behavior are removed or updated.

- sherlockwu · COMMENTED · 2026-10-24T05:08:59Z · [source](https://github.com/sgl-project/sglang/pull/46243#pullrequestreview-5636947329)

Checked against main's Python recipe path: ~70 probe requests per model (V4.1-Flash, V4-Flash-0731) give identical token ids except for the first item below. Two fixes before merge:

1. **Mixed-case roles fail.** Pydantic lowercases message roles; `render` passes them to recipe as sent, so `{"role": "Assistant"}`, `"SYSTEM"` or `"Developer"` fails with `unknown variant` where Python renders. Lowercasing after cloning `messages` fixes all four cases (parity still passes):
   ```rust
   // Pydantic lowercases message roles.
   for message in &mut messages {
       if let Some(role) = message["role"].as_str() {
           message["role"] = role.to_lowercase().into();
       }
   }
   ```

2. **`tests/openai_parity.rs` fails once the DeepSeek tokenizers are cached** (CI passes only because it caches none). `Checkpoint::render` tokenizes `render_request`'s text; it should take `encode_request` first:
   ```rust
   let defaults: HashMap<String, Value> = defaults.into_iter().collect();
   if let Some(ids) = self.formatter.encode_request(request.clone(), &defaults) {
       return ids.ok();
   }
   ```
