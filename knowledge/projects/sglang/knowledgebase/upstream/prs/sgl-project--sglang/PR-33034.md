# perf(gemma4): replace dense image masks with spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/33034) · state: closed · merged: False

## Original PR description

Fixes #33033.

## Motivation

Gemma4 multimodal prefill currently creates a dense
`extend_seq_len x (extend_seq_len + prefix_len)` custom attention mask so image
soft tokens can attend bidirectionally within the same image. The required
non-causal metadata is only a set of small image-token intervals, but the dense
representation has quadratic allocation, initialization, copy, and per-layer
kernel-read costs.

The generic custom mask also enables image bidirectional attention in every
decoder layer. Gemma4 expects it only in sliding-attention layers; full-attention
layers remain causal. This PR follows that layer selection, consistent with the
direction of `#32303`.

## Modifications

- Replace the dense custom mask with compact per-request metadata:
  `image_span_indptr`, `image_span_begin`, and exclusive `image_span_end`.
- Pass image spans only to sliding-attention layers.
- Evaluate `causal or same_image` directly in both the two-stage and unified
  Triton extend-attention kernels.
- Preserve the existing causal fallback and warning when chunked prefill splits
  an image span.
- Keep generic `custom_mask` behavior unchanged and make it mutually exclusive
  with image spans.
- Add coverage for batching, multiple images, image spans crossing Triton query
  blocks, compact metadata construction, and sliding-only layer selection.

## Speed Tests and Profiling

H20, BF16, Triton attention, one 336x336 image (256 image tokens), one warmup
and three measured runs, CUDA graph/overlap/radix cache disabled. Both clean
runs started with 94.78 GB available GPU memory before model loading. Each
request was one complete prefill with `chunked_prefill_size=32768`.

| Total tokens | Mode | Before | After | Change |
| ---: | --- | ---: | ---: | ---: |
| 8k | Text | 741.171 ms | 742.692 ms | +0.2% |
| 8k | Vision | 1105.432 ms | 936.549 ms | -15.3% |
| 16k | Text | 1873.754 ms | 1874.546 ms | 0.0% |
| 16k | Vision | 3030.869 ms | 2327.110 ms | -23.2% |
| 32k | Text | 5295.529 ms | 5357.104 ms | +1.2% |
| 32k | Vision | 9483.857 ms | 6721.119 ms | -29.1% |

Paired vision overhead:

| Total tokens | Before: vision - text | After: vision - text | Reduction |
| ---: | ---: | ---: | ---: |
| 8k | 364.260 ms | 193.857 ms | 170.403 ms / 46.8% |
| 16k | 1157.115 ms | 452.564 ms | 704.551 ms / 60.9% |
| 32k | 4188.328 ms | 1364.015 ms | 2824.313 ms / 67.4% |

The removed paired overhead grows by 4.13x from 8k to 16k and 4.01x from 16k
to 32k. This end-to-end scaling matches the expected `O(S^2)` cost of the old
dense mask. Whole vision TTFT speedup grows from 1.18x at 8k to 1.41x at 32k.

Decode timing is not part of the performance claim. The patch does not modify
decode attention kernels, and streaming chunk intervals showed process-level
host/runtime drift between engine launches.

An additional controlled A/B on NVIDIA DGX Spark used the same upstream
`5c6635d8f` base on both sides, with only this patch added to the after case.
The model used FP16 vision plus W4A16 compressed-tensors language weights,
Triton attention, one 336x336 image with 256 image tokens, one warmup, and three
measured requests. Each reported length is the exact combined image-plus-text
input length and executes as one complete prefill.

| Total tokens | Vision before | Vision after | Change | Speedup |
| ---: | ---: | ---: | ---: | ---: |
| 1000 | 313.058 ms | 287.546 ms | -8.15% | 1.09x |
| 1664 | 544.840 ms | 482.214 ms | -11.49% | 1.13x |
| 4000 | 1556.841 ms | 1067.809 ms | -31.41% | 1.46x |
| 8000 | 4201.442 ms | 2245.855 ms | -46.55% | 1.87x |

The dominant-color output remained `orange`/`Orange` before and after. Decode
latency remained in the same 22.8--24.6 ms/token range and is not part of the
performance claim.
