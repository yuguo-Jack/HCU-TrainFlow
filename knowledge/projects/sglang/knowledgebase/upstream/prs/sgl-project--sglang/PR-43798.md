# [HiCache] Isolate rank-sharded storage keys for MLA hybrid side pools

[Upstream PR](https://github.com/sgl-project/sglang/pull/43798) · state: open · merged: False

## Original PR description

## Motivation

For MLA models, HiCache file (L3) storage treats the primary KV pages as rank-replicated: all TP ranks resolve to the same physical files and rank 0 is the single storage owner (LRU bookkeeping/eviction is centralized there). Hybrid side pools are different — the Mamba/linear-attention state and the MHA draft pool hold *different* data on each TP rank (they are rank-sharded, not replicated).

These sidecars were keyed only by pool name (`{key}.{pool_name}`), so every rank resolved to the *same* file path. With file-storage eviction enabled this has two failure modes:
- **Correctness**: a later restore/existence check can read a *peer* rank's shard instead of its own, so a rank loads the wrong hybrid state.
- **Eviction/accounting**: because the shards share one directory and config suffix, the rank-0-centralized LRU scan/adopt/evict logic can count, adopt, or delete files that belong to other ranks' shards.

This PR gives rank-sharded side pools a per-rank key namespace so each rank only writes/reads/evicts its own shard, while replicated pools (KV, indexer) stay shared and rank-0-owned. The behavior is gated strictly on `is_mla_model` + pool type, independent of any host-dedup flag, so non-MLA and non-hybrid paths are unchanged.

## Modifications

**1. Per-rank key namespacing for rank-sharded side pools** (`mem_cache/hicache_storage.py`)
- `HiCacheFile` now records `_is_mla_model`, `_tp_rank`, `_tp_size`, and a `_rank_sharded_pools` set seeded with `PoolName.MAMBA`.
- `_log_key` appends a `.tp{rank}_{size}` suffix for MLA models when the pool is rank-sharded; the KV pool and non-sharded components keep the existing shared key. `_get_component_key` now routes the non-KV case through `_log_key`, so existence queries and reads/writes of those sidecars use the same per-rank mapping.
- `register_mem_host_pool_v2` (a) adds any non-KV `MHATokenToKVPoolHost` sidecar (e.g., the MHA draft pool) to `_rank_sharded_pools`, and (b) when a pure-MLA peer that is *not* the storage owner registers a sharded sidecar, swaps in a local (non-MLA) LRU evictor scoped to that rank's shard keys, so the peer can manage its own shards without touching rank 0's replicated files.
- Relax `HybridCacheController.should_backup()` so the file backend (not just mooncake) backs up MHA `DRAFT`/`DRAFT_SWA` on every TP rank. Now that those shards are keyed per rank, a nonzero rank that skipped backup would leave its draft file missing and collapse the cross-rank MIN of storage hits to zero (MLA target + MHA draft, e.g. Kimi-K2-Instruct + eagle3). Non-MHA (MLA/DSv4) draft hosts and backends without per-rank draft keys remain TP0-only.

**2. Ownership-aware LRU evictor** (`mem_cache/storage/file/lru_file_evictor.py`)
- New optional `owns_key` predicate (defaults to "owns everything"). `HiCacheFile._owns_file_key` parses the `.tp{rank}_{size}` suffix: a sharded file is owned only by the matching rank; an unsharded (replicated) file is owned by rank 0.
- `can_cache`, `touch`, and the on-disk scan now skip keys the rank does not own, so a rank never adopts, counts, or evicts a peer's shard files. The predicate is wired only for MLA models (`self._is_mla_model`); non-MLA backends get `owns_key=None` and behave exactly as before.

**3. Unit tests** (`test/registered/unit/mem_cache/test_hicache_file_storage_path_unit.py`)
Added `TestHybridFilePoolKeys(CustomTestCase)`:
- `test_rank_sharded_state_roundtrip_and_existence` — replicated KV/INDEXER component keys are identical across ranks while MAMBA keys differ by `.tp{rank}_{size}`; each rank's `set`/`get` and `batch_set_v2`/`batch_get_v2` round-trip its *own* shard value (`100 + rank`), and a rank cannot see a peer's shard.
- `test_bounded_shard_writes_and_eviction_preserve_peer_files` — with bounded storage, one rank's writes/eviction neither delete nor expose a peer's shard files, and rank 0's shared files survive a restart.


## Accuracy Tests

No change to model numerics on existing paths: the new key suffix and ownership checks are gated on `is_mla_model` + rank-sharded pool type, so non-MLA and non-hybrid runs are unchanged. For MLA + hybrid (Mamba / MHA-draft) models on file storage, this fixes a latent cross-rank shard mix-up (a rank could previously restore a peer's state) — it improves correctness rather than altering outputs on the healthy path. Validated by the added unit tests; an end-to-end accuracy run would need a hybrid MLA model at TP > 1 with L3 file storage, which I can add if reviewers want.

Thanks — confirmed, and fixed in the latest push (5e07c1e).

You're right: with `backup_skip = is_mla_model and tp_rank != 0`, `should_backup()` only let MHA `DRAFT`/`DRAFT_SWA` through for mooncake, so on the file backend a nonzero rank never wrote its draft shard. Since this PR keys that shard per rank, rank>0's restore missed and the cross-rank `all_reduce(ReduceOp.MIN)` on `storage_hit_count` collapsed the prefix hit to 0.

Changes:
- `should_backup()` now also allows the file backend for MHA `DRAFT`/`DRAFT_SWA` (`in ("mooncake", "file")`); non-MHA (MLA/DSv4) draft hosts and backends without per-rank draft keys (e.g. hf3fs) stay TP0-only.
- Added `test_file_backend_mha_draft_is_backed_up_per_rank`: asserts `should_backup` returns True for a file-backend MHA draft at rank>0 (False for a non-MHA host / hf3fs), and that each rank's DRAFT shard is keyed `.tp{rank}_{size}`, round-trips independently, and isn't masked by the peer's file.

For context, the pre-PR behavior was also broken, just differently: with the shared `{key}.draft`, rank>0's existence check found rank0's file and "hit" on the wrong shard. This PR + the `should_backup` relaxation makes each rank store and restore its own draft shard.
