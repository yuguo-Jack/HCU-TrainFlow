# [Fix] Responses: keep late instructions in place on the merge path

[Upstream PR](https://github.com/sgl-project/sglang/pull/46569) · state: open · merged: False

## Original PR description

## Motivation

We serve DeepSeek-V4-Flash (v0.5.22) to Claude Code over `/v1/responses` and were getting almost no prefix cache hits on long agent sessions.

Claude Code appends a system message with a `<total_tokens>` counter after every tool result. #40077 keeps such messages in place, but only when `supports_inline_system` is true, and for native encoders that's just `kimi_k3`. On `dsv4` (and `dsv32`, `--chat-template`, or system-first Jinja templates) `_construct_input_messages` still merges every system/developer message into the leading system block. So each turn the counter changes near the top of the prompt and the radix cache can't match anything after it.

Easy to reproduce with a ~3.5K token request against a single replica:

| Request | Cached tokens |
|---|---|
| First request | 0 |
| Same request again | 3,328 |
| Same request, only the `<total_tokens>` number changed | 0 |

We worked around it in our gateway by sending late system messages as user turns, which is what this PR does inside SGLang. Production traffic from the same client, before (Oct 20, 10:28-14:13 UTC) and after (14:13-14:48 UTC). The windows aren't matched, so take it as a rough comparison:

| | Before | After |
|---|---|---|
| Requests | 1,871 | 760 |
| Median prompt | ~73K | ~77K |
| Cache hit rate (token-weighted) | 6% | 97% |
| Median uncached prefill | 68,903 | 960 |
| Median request duration | 7.2 s | 1.3 s |
| p90 request duration | 24.1 s | 9.4 s |

Short replies (<300 output tokens) on 120K+ prompts went from 9.0 s to 1.0 s median.

Adding `dsv4` to the allowlist instead wouldn't work. Since #45315, dsv4 renders through deepseek-recipe, and recipe itself moves inline `system` messages up to the leading system block, so they have to reach it as something else.

## Modifications

On the merge path, system/developer messages before the first turn are still merged into the leading block, and later ones are now sent as user turns where they are. The developer label is kept, and since this runs after the stored history is added, it also covers `previous_response_id`. With dsv4, recipe puts the converted message in the same user turn as the preceding tool result, so the rendered prompt has no extra user turn.

The tradeoff is that late instructions now appear as user turns, not system. #42533 does the same for `/v1/messages`.

## Tests

Updated the merge-path cases in `test_inline_instruction_keeps_history_prefix` and added tests for a reminder after a tool result, the `previous_response_id` case, and a 4-turn agent loop rendered through deepseek-recipe's dsv4 encoding that checks each turn's prompt ids are a prefix of the next. The new tests fail on main.
