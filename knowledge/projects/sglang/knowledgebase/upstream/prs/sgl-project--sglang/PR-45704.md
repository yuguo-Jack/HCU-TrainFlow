# [Fix] [AMD] dflash: Sample-verify temperature > 0 drafts on ROCm instead of falling back to greedy

[Upstream PR](https://github.com/sgl-project/sglang/pull/45704) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, `verify_sampling` resolves no `tree_speculative_sampling_target_only` (the CUDA kernel is built on FlashInfer), so every DFLASH request with temperature > 0 is verified by greedy argmax ("DFLASH non-greedy verification is unavailable on this build/device; falling back to greedy argmax verification"). The served distribution is then not the requested one.

DFlash proposals are a linear chain (`topk == 1`), which collapses the general tree verifier into something cheap to write in Triton. This PR adds that verifier for ROCm, plus a fused fast path on the top-k support that removes the host syncs the dense path needs.

Related: #34140 adds a general Triton tree verifier for ROCm (EAGLE and DFLASH). This PR is DFLASH-only and narrower: it binds only inside `dflash_utils.py`, so EAGLE's tree verification is untouched, and the fused path covers the common top-k sampling configuration without materialising anything vocab-sized. Happy to rebase onto or fold into #34140 if reviewers prefer one path.

## Modifications

1. **`kernels/ops/speculative/dflash_chain_sampling.py`** (new): `chain_speculative_sampling_target_only`, with the CUDA operator's keyword signature. On a chain, `retrive_next_sibling` is always -1 and `prob_acc` resets on every acceptance, so the accept test at level j is local (`coin[j-1] <= tps_j / threshold_acc or tps_j >= threshold_single`) and the walk is a gather plus a leading-run count. Only the residual draw needs a kernel: a sum-reduce and scan-search over the vocabulary, including FlashInfer's two fallbacks. `draft_probs` is still written so the caller's tensor matches the CUDA path.
2. **`kernels/ops/speculative/dflash_fused_sampling.py`** (new): verify on the k-sized top-k output instead of a dense `(bs * draft_len, vocab)` pair, with no host sync. Every step that decides an acceptance uses the same operators as the dense path (temperature division, `torch.topk`, rank mask, `F.softmax`, `top_p_renorm_prob`, division by `threshold_acc`), so accept decisions are bit-identical; the Triton kernel only does the chain walk and the residual draw. `can_use_fused` declines configurations it does not cover (top-k disabled, `top_k > 64`, `draft_len > 32`), which fall through to (1).
3. **`srt/speculative/dflash_utils.py`**: on ROCm, when the general verifier is absent, bind (1) under the operator's name and try (2) first in `compute_dflash_sampling_correct_drafts_and_bonus`. `_DFLASH_SAMPLING_VERIFY_AVAILABLE` is then true on ROCm. CUDA, MUSA and NPU paths are unchanged.
4. **`test/registered/kernels/ops/speculative/test_dflash_chain_sampling.py`** (new): (1) against a scalar transcription of `TreeSpeculativeSamplingTargetOnly` restricted to a chain, exact on `accept_token_num`, `predicts` and the `draft_probs` side effect, over draft lengths 1/2/4/8 and all-accept / all-reject thresholds.

## Accuracy Tests

Qwen3.5-397B-A17B-FP8 + Qwen3.5-397B-A17B-DFlash (8 draft tokens), TP4, MI308X, ATOM plugin. Measured on the v0.5.17 and v0.5.20 release branches with the same verifier logic; this branch is the rebase onto main.

- Unit test on MI308X against this branch: 1 passed, 8 subtests.
- Distribution, fixed prompt, temperature 1.0, 400 draws of 8 tokens, against a non-speculative baseline in the same session: 365/400 vs 371/400 distinct, sum(p^2) 0.00144 vs 0.00105; permutation tests p = 0.37 (TVD) and p = 0.55 (collision probability). The same tests reject a deliberately broken variant at p = 0.0005 / 0.0002.
- GSM8K, 200 questions, 5-shot: 0.970 at temperature 0 and 0.515 at 0.7, vs 0.955 and 0.520 without DFLASH, i.e. the drop is the temperature's, not this path's.
- Temperature ladder 0.01-2.0 with top_p/top_k: all requests served, server healthy; accept length falls monotonically with temperature as the target flattens.
- End-to-end smoke, 9k in / 500 out, v0.5.20 with the same `dflash_utils` logic as this branch: all requests served, no fallback warning, no errors.

## Speed Tests and Profiling

Fused path vs the dense chain path, temperature 0.7, top_k 20, top_p 0.95, c1 (vocab 248320): the dense path spends 38.6 ms CPU per step against 5.1 ms at temperature 0, with GPU idle 24.1% vs 8.5%, because three of its ops block on the device and collapse overlap scheduling. The fused path verifies on 20 values per row instead of two 7.9 MB vocab-sized tensors and has no host sync.
