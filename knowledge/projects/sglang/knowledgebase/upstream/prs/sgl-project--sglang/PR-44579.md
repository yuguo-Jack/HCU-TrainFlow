# [Feat] multimodal: Register fetchers for custom media URL schemes

[Upstream PR](https://github.com/sgl-project/sglang/pull/44579) · state: open · merged: False

## Original PR description

_Posted by Kunal's robot (Claude Fable 5.1) ↓_
>
> ## Motivation
>
> `get_image_bytes()` understands `http(s)://`, `file` paths and `data:` URLs and base64-decodes anything else. An image URL on an object store (`s3://`, `gs://`, ...) therefore fails on `/v1/chat/completions` with `400 Non-base64 digit found`, even though the deployment can read that store. Today the only way to add a scheme is to patch the loaders.
>
> ## Modifications
>
> - `sglang/srt/utils/common.py`: a small scheme-to-callable registry. `register_media_url_resolver(scheme, resolver)` maps a URL scheme (case-insensitive) to a function returning the media bytes. `get_image_bytes()`, `_normalize_video_input()` and `load_audio()` consult it right before their fallbacks (for video, before the local-path probe, which now runs only for scheme-less inputs, so a URL whose path also exists on disk is fetched by its resolver or rejected, never opened as a file), and the Inkling processor's `_resolve_media_item()` does the same before its plain-path passthrough, inside its client-error handling. Every image entrypoint (chat `_load_single_item`, preprocess-cache hashing in `multimodal/cache/identity.py`, `load_image`) already funnels through `get_image_bytes`, so one hook covers them all. Unregistered schemes behave exactly as before.
> - `media_url_max_file_size_bytes()` exposes the configured `--media-url-max-file-size-mb` limit (0 = unlimited) so a resolver can enforce the same bound as the HTTP downloader.
> - `test/registered/unit/multimodal/test_media_url_resolvers.py`: CPU unit test covering routing through `get_image_bytes`, `load_image`, the cache identity reader, `get_video_bytes`, `load_audio` and the Inkling item resolver, case-insensitive scheme lookup, a registered video URL whose path exists locally, plus the unchanged base64 fallback for unregistered schemes.
> - `docs/docs/advanced_features/server_arguments.mdx`: one paragraph next to the existing media URL security guidance. It says what a resolver must guard (restrict buckets, enforce the size limit, raise `ValueError` for client errors) and which paths bypass the registry: processors that hand URLs to their model's own loader (Bailing, the Transformers video fallback) and the Rust frontend.
>
> Usage from a deployment, before the server starts (for example from a sitecustomize hook or a wrapper launcher):
>
> ```python
> from sglang.srt.utils.common import media_url_max_file_size_bytes, register_media_url_resolver
>
> def read_s3(url: str) -> bytes:
>     bucket, key = url.removeprefix("s3://").split("/", 1)
>     obj = s3.get_object(Bucket=bucket, Key=key)
>     if (limit := media_url_max_file_size_bytes()) and obj["ContentLength"] > limit:
>         raise ValueError(f"Remote media exceeds the {limit} byte download limit: {url}")
>     return obj["Body"].read()
>
> register_media_url_resolver("s3", read_s3)
> ```
>
> Verified end to end on a Qwen2.5-VL-3B server: with a resolver registered for an object-store scheme, `/v1/chat/completions` returns 200 and the same description as the equivalent `data:` URI; a missing object returns 400 and the server stays healthy. Without a resolver the behavior is unchanged.
>
