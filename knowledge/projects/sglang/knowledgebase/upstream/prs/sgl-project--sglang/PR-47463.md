# [Fix] stop_regex: Record the matched span, not the pattern source

[Upstream PR](https://github.com/sgl-project/sglang/pull/47463) · state: open · merged: False

## Original PR description

## Motivation

On a regex stop, the scheduler records `FINISHED_MATCHED_REGEX(matched=<the pattern source>)` — e.g. `"[0-9]+"` — but the detokenizer trims with a literal `output.find(matched)`. The pattern text almost never occurs in the output, so the find misses and the text is returned **untrimmed**. `no_stop_trim` is unreachable for regex stops (it can neither keep nor remove what was never trimmed), and regex stops behave inconsistently with stop strings, which trim correctly. Fixes #47461.

## Modifications

Two commits, `python/sglang/srt/managers/schedule_batch.py`:

- `644881a235` `[Fix] stop_regex: Record the matched span, not the pattern source` — record the matched span instead of the pattern source in `FINISHED_MATCHED_REGEX`.
- `11b64c14d4` `fix: derive the regex span from the emitted prefix` — review follow-up: take the span from `decode(output_ids[:finished_len])` in both branches. The greedy tail match can extend past `finished_len`, and text past it never reaches the detokenizer, so a tail span may not exist in the emitted output.

Net effect: the recorded `matched` string is a span found inside the emitted output, so the detokenizer's literal `output.find(matched)` trims at the first regex match and both `no_stop_trim` branches work. A zero-width span keeps the pattern source — the pre-fix behavior — instead of trimming everything. The detokenizer is unchanged.

## Accuracy Tests

Drove the real `Req.update_finish_state` with a fake tokenizer (pure CPU), same harness as the existing stop-str spec tests:

- With this branch: 20/20 pass — the existing stop-string and stop-regex tests (regression), plus the new non-literal test, which asserts the recorded span is `1` and end-to-end that `trim_matched_stop` trims the emitted `kl1` to `kl`, and a literal-parity guard.
- Against unpatched main with the same test file: the 3 span assertions fail (`matched` is the pattern source there) — the new non-literal test plus the two updated end-anchored assertions. Literal patterns are unaffected on either side (span == pattern text).

Full A/B run on one machine, `pytest test/registered/unit/managers/test_stop_str_speculative.py test_trim_matched_stop.py`.

## Speed Tests and Profiling

No inference-speed impact: the span derivation runs once per request on the finish path — one `re.search` over the emitted prefix and one decode of it. No hot-path change.
