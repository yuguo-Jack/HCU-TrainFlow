# [Perf] gemma4: Capture single-step frozen-KV drafts

[Upstream PR](https://github.com/sgl-project/sglang/pull/45771) · state: closed · merged: True

## Original PR description

## Motivation

`FrozenKVMTPDraftWorker._capture_cuda_graphs` returns early when `speculative_num_steps <= 1`, so a one-step frozen-KV draft never gets a draft graph. That guard is off by one: a one-step draft still runs the assistant seed forward every decode step, and that forward is exactly what the capture covers. With the guard as written, it always runs eagerly.

### How it was found

While profiling Gemma 4 E2B frozen-KV MTP with one draft step and two verification tokens, the assistant seed forward showed up as eager work on every decode step, even with full decode graphs enabled. `/server_info` confirmed it: `startup_time.cuda_graph.draft_decode` was `0`, while the same server with three draft steps reported a nonzero capture time. The cause turned out to be the `<= 1` early return.

## Modifications

Change the early-return guard from `<= 1` to `<= 0`, so one-step drafts are captured. The zero-step and graphs-disabled cases are still excluded. Nothing else changes; multi-step drafts take the same path as before.

## Accuracy Tests

`google/gemma-4-E2B-it` + `google/gemma-4-E2B-it-assistant`, one H200, the cookbook E2B MTP command with `--speculative-num-steps 1 --speculative-num-draft-tokens 2` (the case this PR changes).

- Six greedy chat prompts: identical output on all four runs (main ×2, this PR ×2).
- GSM8K via `sgl-eval==0.1.3`, 200 examples, greedy (`temperature=0`, `max_tokens=2048`, `enable_thinking=false`): **79.5%** on main and **79.5%** on this PR, zero errors.
