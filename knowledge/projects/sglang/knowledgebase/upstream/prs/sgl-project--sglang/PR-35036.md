# [Fix] disaggregation: route equal-TP fragmented KV transfer through staging

[Upstream PR](https://github.com/sgl-project/sglang/pull/35036) · state: open · merged: False

## Original PR description

## Problem

Equal-TP (MHA/GQA) PD-disaggregated KV transfer collapses bandwidth when the
decode-side KV cache becomes fragmented: each `(group, layer)` slice becomes a
separate transfer entry, and per-entry device-memory (D2H) copy overhead
dominates the transfer.

- engine-level: 1 entry → 4792 MB/s; 4096 entries → 15.5 MB/s
- end-to-end (200 concurrent long shared-prefix requests): 1.41 → 1.76 req/s
  (+25%), TPOT 23.03 → 13.80 ms (−40%)

This is the root cause behind the bandwidth collapse reported in #5450
(which was auto-closed without a confirmed fix; the "larger page-size"
workaround avoids, but does not fix, fragmentation).

## Root cause

1. `alloc_extend` allocates across non-contiguous free segments under pool
   pressure (decode-side radix cache reuse) → fragmented dst indices.
2. The equal-TP direct path (`send_kvcache`) emits one transfer entry per
   (group × layer), so fragmentation blows up the entry count.
3. Per-entry fixed cost × thousands of entries → bandwidth collapse.

## Fix

Route equal-TP fragmented chunks through the existing staging path
(local gather → 1 bulk RDMA → decode scatter), collapsing G×2L entries into 1.
Gated behind `SGLANG_DISAGG_STAGING_BUFFER` and
`SGLANG_DISAGG_STAGING_MIN_GROUPS` (default 8); `SGLANG_DISAGG_STAGING_ALWAYS`
opts into staging for every equal-TP chunk.

- `mooncake/conn.py`: equal-TP fragmentation branch + `_fragmented_groups` +
  `_ensure_equal_tp_staging_req` (on-demand STAGING_REQ) + bounded spin
- `decode.py`: register gate widened to non-MLA equal-TP, excluding
  fake-transfer requests (warmup/health-check) to avoid a warmup hang
- `utils.py`: poll demote gate switched to `is_staging_room`
- `environ.py`: `SGLANG_DISAGG_STAGING_MIN_GROUPS` / `SGLANG_DISAGG_STAGING_ALWAYS`

All changes are env-gated and default-off: behavior is unchanged unless
staging is explicitly enabled.

### Follow-up refinements (from KIOSHIROI/sglang#1, by @simple-sun)

The original implementation rounded non-last sends down to a full staging grid
so every staged chunk started on a grid boundary. That delayed the tail of a
cached prefix until later prefill work completed. The follow-up makes partial
grid pieces stageable and hardens the control paths:

- **Partial chunks with allocation-identity safety.** A grid-aligned piece may
  now stage with its actual page count (`_is_first_staging_piece`). Only the
  first piece of a grid slot stages; continuations that start inside an
  already-used slot stay on the direct path, so they can never reuse that
  slot's staging allocation.
- **Early-send overlap preserved.** Non-last sends are only grid-aligned when
  the sender reports `requires_staging_grid_alignment()` (PP>1, missing target
  info, or non-equal TP); equal-TP PP=1 direct sends keep their natural
  boundary.
- **No unnecessary splitting.** The scheduler asks the sender
  (`should_split_staging`) whether any grid-aligned piece can stage; contiguous
  direct sends are sent once, unsplit.
- **Convert the index range once.** `req_to_token` translation and
  `kv_to_page_indices` happen once per send range instead of per segment;
  segments slice the materialized page array.
- **Allocation-request synchronization.** On-demand STAGING_REQ
  deduplication/submission is serialized (`request_lock`), the dedup key is
  rolled back on send timeout, and STAGING_RSP updates are published under the
  watermark condition variable with `notify_all()` (closing the missed-wakeup
  window in the readiness wait).
- **Failure classification.** Allocation/control-request failures use a
  dedicated result (`_STAGING_REQUEST_FAILED`) and fail only the affected room
  instead of blacklisting the transport session; `send_kvcache_staged` returns
  the real transport code instead of raising, so RDMA failures follow the
  regular room/session failure path and unexpected exceptions still propagate.
- **Scope guard.** The optional equal-TP staging path is restricted to PP=1;
  other layouts keep the original conservative grid alignment.

Defaults are unchanged: staging off, `MIN_GROUPS=8`, `ALWAYS` off.

## Validation

- Warmup passes with `STAGING_BUFFER=1`, and with staging + decode radix cache
  on both MHA and GQA.
- Fragmented workload (200 rooms shared-prefix): 1.41 → 1.76 req/s (+25%),
  TPOT 23.03 → 13.80 ms (−40%), 90/90 staging transfers succeeded, 0 failures.
- Healthy path no regression (1.47 → 1.49 req/s, within noise).

Follow-up validation (TP1 prefill + TP1 decode on two H20-3e GPUs; 49,152
input tokens including 49,088 cached tokens, 1 output token; 60 samples per
condition after four warm-up requests; the second run reverses the
fragmentation-test order):

| KV layout | Run | Parent mean TTFT | Follow-up mean TTFT | Reduction |
|---|---|---:|---:|---:|
| Low fragmentation | 1 | 64.22 ms | 55.43 ms | 13.7% |
| Low fragmentation | 2 | 65.72 ms | 56.06 ms | 14.7% |
| High fragmentation | 1 | 84.05 ms | 58.41 ms | 30.5% |
| High fragmentation | 2 | 87.14 ms | 58.76 ms | 32.6% |

- Paired correctness checks matched output token IDs and logprobs; transfer
  observations confirmed staged 16,320-token partial pieces followed by direct
  64-token continuations.
- CPU contracts: 18 behavior tests in three `test/registered/unit/disaggregation/test_equal_tp_staging_*.py`
  files pass on the follow-up and fail on the unpatched parent (they execute
  the actual scheduler send range, partial-piece identity, direct/forced paths,
  allocation requests, waiter notification, transport return boundary, and
  worker failure handling).
- High fragmentation was constructed by permuting free slots in 16-token runs
  on an empty prefill pool: a controlled fragmentation experiment, not
  production cache aging.

## Known limitations / follow-ups

- GPU TP8 validation: TP8 was validated on 2x8xH20-3e (see the TP8 validation
  section above); TP>1 layouts other than TP8 are not measured. The TP1 A/B
  above is TP1 only.
- DCP × equal-TP interaction is not covered by the current regression tests
  (DCP transfer takes the pre-existing relayout branch; split segments carry
  per-segment `src_page_offset`/`num_kv_tokens`).
- Pre-existing ordering gaps reported separately (Success published before a
  deferred KV chunk transfer; transfer + CHUNK_READY possible after a
  cancellation during the readiness wait) reproduce on the parent revision and
  are tracked as follow-ups, not regressions from this change.
- Pre-RDMA local/destination staging-buffer capacity failures still return -1
  and follow the legacy session-failure path.

- KIOSHIROI · comment · 2026-08-17T13:12:12Z · [source](https://github.com/sgl-project/sglang/pull/35036#issuecomment-5316517104)

Hi, thanks for the review! I reproduced it on 2× A800 80GB with mooncake TCP (MC_FORCE_TCP=1). The trigger is decode-side radix cache + memory pressure, which is why it doesn't show up in the default path.

Three things are needed together:

1. **Decode radix cache** (`--disaggregation-decode-enable-radix-cache`). With shared-prefix requests the decode side reuses shared pages, so dst pages of a transfer become non-contiguous even when src is contiguous. This is the main source of fragmentation. With radix disabled (default), dst stays contiguous and we see the healthy ~56 entries/chunk.
2. **Memory pressure + concurrency.** mem_fraction 0.3 + 200 concurrent rooms makes alloc_extend span multiple non-contiguous free segments.
3. **Equal TP** (prefill TP == decode TP). The direct path emits one entry per (group × layer), so the fragmented range gets multiplied into a large number of entries.

Repro:

```bash
MEM_FRACTION=0.3 DECODE_RADIX=1 PREFILL_NO_RADIX=1 \
  scripts/start_pd_master.sh mooncake

sglang.bench_serving --backend sglang --base-url http://0.0.0.0:30000 \
  --dataset-name generated-shared-prefix \
  --gsp-num-groups 1 --gsp-prompts-per-group 200 \
  --gsp-system-prompt-len 64 --gsp-question-len 8000 --gsp-output-len 2048 \
  --request-rate inf
```

(shared 64-token system prompt, 8000-token questions, 2048-token outputs, 200 concurrent prompts, closed loop)

I re-ran this exact setup today. Entry count goes from ~56 to 952 per batch (up to 3976 in the worst batch of earlier logs), TPOT ~24 ms, throughput ~1.36 req/s. With DECODE_RADIX=0 the same workload keeps dst contiguous, entry count stays healthy, and no collapse — so the default config won't hit this.

I can attach the raw kv_transfer_*.jsonl logs (per-batch n_entries) if that helps.
