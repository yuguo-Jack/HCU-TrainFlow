# [Refactor] [NVIDIA] indexer: Move the DSA/DSV4 indexers onto DeepGEMM's fp8_fp4 MQA logits API

[Upstream PR](https://github.com/sgl-project/sglang/pull/44350) · state: open · merged: False

## Original PR description

## Motivation

sgl-project/DeepGEMM#103 merges upstream DeepGEMM's 26/09/30 release into the SGL fork. That release replaces the MQA-logits API the DSA and DSV4 indexers call:

- `fp8_mqa_logits` and `fp8_paged_mqa_logits` are removed. `fp8_fp4_mqa_logits` / `fp8_fp4_paged_mqa_logits` no longer take `clean_logits` or `logits_dtype`, and ragged logits are compressed: column `j` of row `i` is key `ks[i] + j`.
- On SM100 the kernels accept only MXFP8/MXFP4 Q and K (int32 packed UE8M0 scales, one byte per 32 channels), BF16 weights, and return BF16 logits. Paged logits need an `indices` entry per query row (`next_n == 1`), and the paged schedule uses a new format. Plain E4M3 with an FP32 per-token scale, which every sglang FP8 index-K cache stores, is SM90-only now.
- The SM120 MQA kernels are gone.

This PR moves sglang onto the new API so that it keeps working once the `sgl-deep-gemm` pin is bumped to a wheel built from that DeepGEMM PR. It is a draft until that wheel exists: this PR does not change the pin. It needs the wheel bump to land with it or before it.

## Modifications

**Shared adapter.** A new module, `srt/layers/attention/deep_gemm_mqa_logits.py`, wraps the new API in the old call shapes, so callers keep getting FP32 logits with 256-column rows:

- Q: the Q scale stays folded into the weights, and the adapter passes unit UE8M0 Q scales. Pre-quantized `(q, q_sf)` tuples pass through.
- Weights are cast to BF16, and power-of-two FP32 K scales are repacked to UE8M0.
- `indices` are passed one per row, and `[batch, next_n]` metadata is flattened to varlen rows on SM100.
- A small Triton kernel widens compressed ragged rows back to full width, because the DSA top-k backends use `ks` as a KV offset as well as a column start.

**Index-K caches on SM100.**
- Each token's scale is rounded to a power of two. When DeepGEMM reads the paged cache, the scale is stored as packed UE8M0. This is lossless and the FP8 bytes don't change.
- Writers covered:
  - the kpool Triton writers;
  - the DSA writers: `fused_store_index_k_cache`, `fused_k_indexer_norm_rope_store`, and the `act_quant` fallback;
  - the DSV4 C4 writer: `fused_norm_rope_indexer`.
- Other paged backends (cutedsl, tilelang, aiter, torch) keep FP32 scales.

**Indexers.**
- kpool and DSA ragged paths read compressed logits. On SM100, DSA paged target-verify uses one row per token instead of the native `[B, next_n]` layout.
- DSV4 C4 builds DeepGEMM's own schedule metadata on SM100; the JIT metadata kernel keeps the old format.
- V4.1 runs DeepGEMM index logits only on SM100, so SM120 takes the Triton indexer. `--enable-deepseek-v4-fp4-indexer` is limited to SM100 and gfx95.
- Logits row-chunk budgets count the BF16 buffer that is live while the logits widen to FP32 (1.5x on SM100).

**Tests.**
- New: `test_dsa_kpool_deepgemm_logits.py` covers writer packing, plus ragged and paged logits against a reference. A UE8M0 case is added to `test_fused_store_index_cache.py`.
- `test_deepgemm_paged_mqa_logits.py` now runs the SM100 path with BF16-weight tolerances.
- Mocks and direct calls are updated for the new signatures. The JIT-vs-DeepGEMM metadata equality test is skipped on SM100, where the formats differ.

## Accuracy Tests

- **SM90 (H200)**, with a wheel built from sgl-project/DeepGEMM#103.
  - The adapter matches a torch reference: max relative error 1.9e-4 for both full-width and compressed ragged logits.
  - Kernel tests that pass: `test_fused_store_index_cache`, `test_dsa_indexer`, the five kpool tests, `test_paged_mqa_metadata`, `test_dsv32_indexer_fusion`, `test_fp4_indexer`.
  - Related unit tests that pass: kpool stream scheduling, DSA chunking, DSV4 nonpaged indexer, DSV4.1 candidates, DSV4 pools, server args, and others.
  - `test_deepgemm_paged_mqa_logits` fails on SM90 with a tolerance mismatch. It fails identically on main with the current 0.2.2 wheel, and CI only runs it on B200.
- **SM100 (B300, SM103)**, with the same DeepGEMM wheel, at `fcd87ce2e7`:
  - Pass: `test_dsa_kpool_deepgemm_logits` (3), `test_fused_store_index_cache` (15), `test_dense_prefill_indexer` (5 + 17 subtests), `test_deepgemm_paged_mqa_logits` (192), `test_dsv41_prefill_sparse_indexer` (6 + 6 subtests).
  - Two of these needed test-only fixes for BF16 precision, in their own commit:
    - `test_deepgemm_paged_mqa_logits`: its per-element tolerance failed near-zero logits. The worst element is about 1% of the summed absolute head terms (about 2.5 BF16 ulps), and `calc_diff` is about 1e-5. On SM100 it now checks `calc_diff < 3e-5`, DeepGEMM's own SM100 bound.
    - `test_dsv41_prefill_sparse_indexer`: the dense reference scores are BF16 now, and at |logit| around 100 one BF16 step is 0.5 to 1. Block scores therefore tie exactly, and tie-breaking picks different members in 88 of 256 rows; every swap is an exact tie. Selections are now compared by their scores. The old test passes on `main` with the 0.2.0 wheel.
  - Still to run: a DeepSeek-V3.2 / V4 accuracy evaluation. The coarser BF16 index logits change top-k picks at ties, so the evaluation should show whether selection quality holds.
- On SM100 the indexer weights and logits pass through BF16, as upstream DeepGEMM intends, so top-k selection can differ slightly from the FP32 path at near-ties.

## Speed Tests and Profiling

Not measured yet. On SM100 the widening of logits to FP32 is one extra pass over the logits, which DeepGEMM no longer cleans. Top-k kernels that read BF16 would remove it.
