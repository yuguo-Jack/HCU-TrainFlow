# [Refactor] [NVIDIA] attention: Migrate DSA/DSV4 indexers to DeepGEMM 0.2.5.post2

[Upstream PR](https://github.com/sgl-project/sglang/pull/44350) · state: open · merged: False

## Original PR description

## Purpose and scope

Upgrade `sgl-deep-gemm` from 0.2.3.post2 to **0.2.5.post2** and migrate the DSA (including DeepSeek-V3.2), DeepSeek-V4, and DeepSeek-V4.1 indexer call sites to the replacement MQA-logits API. This is a self-contained migration; it does not depend on preparatory cleanup or performance PRs.

DeepGEMM removed `fp8_mqa_logits` / `fp8_paged_mqa_logits` and changed the `fp8_fp4_*` interfaces. On SM100 the new kernels require MX scales and BF16 weights, return BF16 logits, and use a different paged schedule. Those requirements also change the representation of FP8 index-K scales stored outside the process.

## Required migration changes

- **Compatibility adapter:** keep existing call shapes in `srt/layers/attention/deep_gemm_mqa_logits.py`. Supply unit UE8M0 scales for plain FP8 Q, pass through pre-quantized Q tuples, convert weights/scales, and widen or expand logits where existing consumers require FP32 or full-width rows.
- **Cache writers and readers:** use packed UE8M0 index-K scales where the SM100 DeepGEMM paged reader requires them. Preserve compatible FP32 representations for other readers. Update the DSA, k-pool, and V4 C4 writers together with their consumers.
- **Scheduling and memory:** match each schedule to its kernel and request grouping, retain the CuTe DSL 256-token schedule, cap SM100 DSV4 schedules at 16384 rows, and account for simultaneously live compressed and expanded logits in the affected prefill budgets. Copy chunked schedules and top-k plans in place during graph replay.
- **PD and external-cache compatibility:** reject incompatible index-K layouts, including an older decoder connecting to a UE8M0 prefill. Namespace UE8M0 pages separately in HiCache, Mooncake and MORI direct linkers, and LMCache. Python and Rust bootstrap checks participate in the same compatibility rule. These protections belong in this migration because FP32 and UE8M0 scales occupy the same number of bytes.
- **Architecture dispatch and regression tests:** keep supported fallback dispatch consistent with the new dependency; update direct calls, numerical tolerances, schedule tests, cache-format tests, and graph replay tests.

The dependency pin changes in `python/pyproject.toml` and `docker/Dockerfile.cu134`. Version 0.2.5 includes sgl-project/DeepGEMM#103 and the SM120 restoration in sgl-project/DeepGEMM#109; 0.2.5.post1 additionally fixes SM100 Mega MoE shared memory on CC 10.7 (sgl-project/DeepGEMM#125), and 0.2.5.post2 adds the CC 10.7 Mega MoE K=64 packed-FP4 MMA and SIMT dispatch pull (sgl-project/DeepGEMM#126). Neither post release touches the MQA logits kernels this PR uses.

SM120 retains the V4 FP4 indexer flag and V4.1 dense/paged DeepGEMM paths restored upstream in #109, with its required 128-token schedule splits and existing 4096-row cap. Existing SM120 backend defaults remain unchanged. Sparse-table MQA remains SM100-only; SM120 uses the dense candidate fallback.

## Deferred work

| Follow-up | V3.2 / DSA | V4 | V4.1 |
|---|---|---|---|
| Adapter relocation, API cleanup, and dispatch consolidation | Applies | Applies | Applies to shared dense/paged adapter callers; sparse logits also have a direct API path |
| BF16 top-k to remove FP32 widening | Applies to SM100 paths that widen | Applies to C4 paths that widen | Low-ratio FP4 already uses BF16 logits by default on SM100; inspect FP32 overrides and any remaining widening paths |
| Produce MX Q scales at quantization time | Applies to plain FP8 Q callers | Applies to FP8 Q callers | Low-ratio FP4 already passes packed Q scales; no unit-scale allocation to remove there |

A new pool-format abstraction, additional backend enablement, and further kernel tuning are also deferred. Preserving existing SM120 support is included in this migration. The graph replay and cache compatibility changes above remain in this PR as migration requirements.

## Known limits

- Paged DSA, k-pool, and V4 paths that widen SM100 BF16 logits retain both buffers temporarily: 1.5x the old logits storage. Their decode allocation is not covered by the prefill chunk budget.
- DSA's SM100 metadata schedule is not chunked; the upstream metadata kernel has a roughly 29k-row limit.
- PD peers must select compatible index-K formats, including backend flags and environment overrides.
- SM100 BF16 weights/logits can change top-k membership at near-ties.
- The validation below is tied to the stated commits and hardware. No DSA model, PD pair, or external L3 store has been validated end to end for this migration.

## Speed Tests and Profiling

**DeepSeek-V4-Flash serving, 4x B300**, same recipe as above, `bench_serving` random 128 in / 128 out, concurrency 256, 2048 prompts, after a warmup bench. Arms in ABBA order on one box; same-code boots differ by 0.6–1.8%.

| sglang | sgl-deep-gemm | output tok/s (run 1 / run 2) | mean TPOT ms |
|---|---|---|---|
| main `e7c55f6959` | 0.2.3.post2 | 3866 / 3887 | 60.9 / 60.6 |
| this PR, `5a4b7e7097` | 0.2.5.post1 | 3850 / 3850 | 61.1 / 61.1 |

- Within noise of main. An earlier PR head was about 7% slower because it widened the paged logits to FP32 over the whole CUDA-graph logits width (799 µs per call); the prefix-only widen takes 38 µs.
- DeepGEMM 0.2.5's SM100 paged MQA kernel costs a fixed ~1–3 µs more per call than 0.2.3 when every row is its own request, and is equal at long context. It is about 1% of a decode step at this shape.
- Grouping DSV4 C4's MTP verify rows into one DeepGEMM request makes that kernel 22–56% faster at 256–1024 rows, but measured flat end to end at both 128-token and 16k contexts (64 requests x 16k, ABBA: 6495 vs 6554 tok/s, TPOT 4.87 ms both), so it is not in this PR.

Settings: GSM8K on all 1319 questions; AIME25 with 16 samples per problem at temperature 1.0 and a 64k max-token cap. | sglang | sgl-deep-gemm | reasoning effort | AIME25 pass@1 | hit 64k cap | output tokens, mean / median | GSM8K |
|---|---|---|---|---|---|---|

| main `e7c55f6959` | 0.2.3.post2 | unset | 0.835 | 16.9% | 25.0k / 18.8k | 0.968 |
| this PR on main `e7c55f6959` | 0.2.5 | unset | 0.848 | 15.4% | 24.0k / 16.9k | 0.968 |
| main `e7c55f6959` | 0.2.3.post2 | `SGLANG_DSV4_REASONING_EFFORT=low` | 0.925 | 6.9% | 16.0k / 9.7k | 0.965 |

This PR and main score the same on the same base. The drop comes from main, and pinning the effort recovers it.

**Cause:** #45315 renders DeepSeek-V4 prompts through deepseek-recipe 0.2.0 as `ModelVersion.DeepseekV4Pro`. A request with thinking on and no `reasoning_effort` gets recipe's default tier `high`, which prepends this 79-token instruction:

```
Reasoning Effort: Absolute maximum with no shortcuts permitted.
You MUST be very thorough in your thinking and comprehensively decompose the problem ...
```

- V4-Flash's bundled `encoding/encoding_dsv4.py` and its README add that prefix only for `reasoning_effort="max"`; its default renders nothing. The removed in-tree encoder detected this "preview" profile and also rendered nothing.
- For the same AIME problem, main renders 107 prompt tokens with no effort set and 28 with `reasoning_effort="low"`. The 28-token prompt is token-identical to the checkpoint encoder's default `encode_messages(..., thinking_mode="thinking")`.

With the prefix, V4-Flash reasons about 50% longer, and about one sample in six reaches the 64k cap before answering.

#45315 lists the change under "Behavior changes", so it is intended. However, deepseek-recipe 0.2.0 has no V4-Flash model version (only `DeepseekV4Pro` and `DeepseekV41Flash`), so V4-Flash now renders as V4-Pro by default. Possible fixes:
- default V4-Flash to `low` in the adapter, which restores the checkpoint's prompt;
- or set `SGLANG_DSV4_REASONING_EFFORT=low` in the V4-Flash recipes;
- or add a V4-Flash version to deepseek-recipe.

This PR does not change prompt rendering. Accuracy comparisons for it should pin the effort, or use a base from before #45315.

## Migration scope and follow-ups

Updated for `56b3fabdee`.

This PR is the **self-contained DeepGEMM migration**: bump to 0.2.5.post1 and adapt DSA/V3.2, V4, and V4.1 indexer callers to the replacement MQA API. No preparatory refactoring PR is required.

**Keep in this PR:** the compatibility adapter and required format conversions; matching kernel/schedule grouping; row caps and affected prefill memory accounting; graph-safe metadata copies; index-cache writers/readers; PD format negotiation (including older decoders); UE8M0 namespaces for HiCache, Mooncake/MORI direct linkers, and LMCache; architecture dispatch adjustments and regression tests. The new scale representation makes PD/storage protection part of the migration, even though those files do not call DeepGEMM.

**Defer these three cleanup/performance tasks:**

| Task | V3.2 / DSA | V4 | V4.1 |
|---|---|---|---|
| Move/rename the adapter and consolidate dispatch | Yes | Yes | Yes for shared dense/paged callers; sparse logits have a separate direct API path |
| Let top-k consume BF16 logits and remove FP32 widening | SM100 paths that widen | C4 paths that widen | Low-ratio FP4 already defaults to BF16 on SM100; check FP32 overrides and other widening paths |
| Emit MX Q scales in the producer | Plain FP8 Q paths | FP8 Q paths | Low-ratio FP4 already produces packed Q scales, so this particular optimization is already unnecessary there |

Existing SM120 support stays in this migration: V4's FP4 flag and V4.1 dense/paged DeepGEMM paths are preserved, using SM120's 128-token schedule splits and 4096-row cap. SM120 backend defaults stay unchanged. Sparse-table MQA remains SM100-only, with the dense candidate fallback on SM120. Additional backend enablement, a new pool-format abstraction, and further tuning remain separate follow-ups. V4.1 is included in the migration, but its low-ratio FP4 path does not have the same conversion overhead as the older FP8 paths.

**Validation and remaining limits:** the PR description retains the accuracy/performance results with their original commit IDs; they are not claims of a fresh run on this head. Paged decode paths that widen still retain BF16 plus FP32 logits (1.5x the old logits storage), DSA metadata retains the roughly 29k-row upstream limit, and no DSA-model, PD-pair, or external-L3 E2E run has been reported. BF16 near-ties can change top-k membership. Migration correctness fixes stay here; removing conversion overhead requires a separate E2E accuracy/performance comparison.

The measured V4 C4 MTP grouping optimization remains deferred: it improved the kernel but was flat end to end in the tested workloads. See the PR's speed results for the measurements.

Suggestion: keep the FP32 index-K cache as the default and gate the new SM100 kernel behind `use_legacy`, as #45893 did for FlashMLA.

1. **Why.** 0.2.5 makes SM100 write UE8M0 scales into the bytes FP32 used, so this PR needs PD layout strings and storage tags, and those still leave gaps:
   - FP32 DSA now sends `kv_layout="index_k:fp32"` (main sent None), which breaks decoders from before #45075.
   - The `fp32` tag also covers POW2, so `mx_kv_scale` can floor non-power-of-two FP32 pages from a peer or L3.
   - The L3 tag only reaches backends that key on `model_name` (not hf3fs, aibrix, flexkv, mmap, shm).
   - DSA PD between SM100 and SM90/SM120 is refused.

   If FP32 stays the default, none of these reach default users.
2. **What DeepGEMM changed (v0.2.3.post2 to v0.2.5.post2).** The SM100 MQA kernel was rewritten, not tightened:
   - `kIsMXSF`, `kCleanLogits`, `kIsCompressedLogits` and the logits-dtype templates are gone.
   - It is MX-only, with BF16 weights and logits, a fixed 384 split, and varlen-only paged scheduling.
   - `smxx_clean_logits` and `sm100_mqa_logits_metadata` are removed.
   - SM90 and SM120 still take FP32 scales.
3. **DeepGEMM side.** Keep the 0.2.3 SM100 kernel, scheduler, layout, clean-logits and host runtime under legacy names, and add `use_legacy` to `fp8_fp4_mqa_logits`, `fp8_fp4_paged_mqa_logits` and `get_paged_mqa_logits_metadata` (the schedule formats differ). With `use_legacy=True` that is the exact kernel main runs today.
4. **sglang side.** The pool owns `index_k_scale_fmt`, FP32 by default, set once at construction. Today the format is re-derived in five places. Call sites pass `use_legacy=pool.index_k_scale_fmt == FP32`. Only UE8M0 pools report a PD layout or tag their storage keys.
5. **Open.** It is not yet checked that the 0.2.3 kernel builds against 0.2.5's shared headers (`smxx_layout.hpp` and the TMA/UTCCP utilities changed slightly). That needs an SM100 build.
