# [multimodal] Ragged feature storage, and a per-image split for Step3

[Upstream PR](https://github.com/sgl-project/sglang/pull/41016) · state: closed · merged: False

## Original PR description

**3 of 3** on multimodal feature handling (#41014, #41015, #41016). Complements #41014, which keeps the per-image list where a list is enough; this covers the case where it is not.

## Motivation

A processor that builds one tensor per image can simply keep the list — the scheduler splits a list by index, hashes it and moves it to CPU already.

A processor whose output passes through HF `BatchFeature` cannot. `process_mm_data` always asks for `return_tensors="pt"`, and `convert_to_tensors` then calls `torch.stack` on a list. Both outcomes are bad:

| input | result |
| --- | --- |
| ragged list | `ValueError` — `torch.stack` refuses |
| **uniform list** | **silently stacked**, rank 4 per image becomes one rank-5 tensor, per-item structure gone |

The uniform case is the dangerous one and it is not rare — a processor that normalises resolution produces equal per-image tile counts routinely.

## Modifications

`SegmentedFeatures` holds owning buffers plus `(buffer, start, end)` per item, and **deliberately exposes no `__len__`/`__getitem__`/`__array__`/`__iter__`**, so nothing can coerce it back. `from_parts()` is a drop-in for `torch.cat(parts, dim=0)`:

```python
-    pixel_values = torch.cat(pixel_values_lst)
+    pixel_values = SegmentedFeatures.from_parts(pixel_values_lst)
```

- **No scheduler or transport consumer sees it.** `expand_segmented_item` resolves it in `get_new_expanded_mm_items` into ordinary per-item tensors — each owning its own rows, since pickle serialises a view's whole storage — before anything hashes or transports them.
- **It degrades rather than fails.** When an item cannot be split one part per image, expansion declines and the caller takes `dense()`, which allocates exactly what the original `torch.cat` would. Adopting this cannot change what a model computes.
- **It is scoped to the processors that need it.** `step3_vl` is converted because its image inputs reach `BatchFeature`. Processors that never do should keep a plain list, and the module docstring says so.

### Step3's per-image split starts firing

Converting `step3_vl` also fixes a split that has never run. Step3 wraps every crop of an image in its own boundary tokens, so one image's placeholders arrive as `num_patches + 1` separate runs of the image token — a three-image request has eight of them, never three. The feature count and the placeholder count therefore never agree, `_try_simple_split` always declines, and the patch-aligned splitting already in `mm_utils` has never had a caller.

`num_patches` records the crop count per image, so the grouping is known. Requiring it to account for exactly every run is what makes applying it safe: a layout that merges or adds runs fails the check and falls back to the dense tensor.

## Tests

`test_step3_per_image_split.py` drives the real processor, the real splitter and the real `get_image_feature`, with only the vision tower stubbed so no weights are needed:

- one item per image comes out, over single, mixed-shape, crop-free and four-image requests;
- every per-item slice — features, `num_patches`, `patch_pixel_values`, `patch_newline_mask` — reassembles into exactly what the packed request held;
- the embedding the model builds is **bit-identical** either way, and covers exactly the placeholder tokens;
- each item leaves owning its own rows;
- identical images hash alike and different ones do not, which is the reason to split at all.

`test_segmented_features.py` covers the class: equality with `torch.cat`, no request-wide allocation, items sharing one buffer in non-item order, every validation rejection, that the class is not array-like, and the three `BatchFeature` boundary cases above — the silent stack, the ragged rejection, and this class passing through by identity.

`test/registered/unit/multimodal/` green; `isort` / `ruff check` / `ruff format` clean.
