# [LoRA] glm5_next: serve LoRA on the KDA projections

[Upstream PR](https://github.com/sgl-project/sglang/pull/44862) · state: open · merged: False

## Original PR description

## Summary
Serve LoRA adapters on GLM-5.3-Flash's KDA layers. Split out of #37753, rebased onto current sglang-miles; the rest of that PR (the glm53next port, KDA unfused layout under LoRA) is already on sglang-miles.

## Changes
- `lora/utils.py`: `b_proj`, `f_a_proj`, `f_b_proj`, `g_a_proj`, `g_b_proj` are known LoRA targets. `f_a_proj` / `g_a_proj` are replicated; `b_proj` / `f_b_proj` / `g_b_proj` shard their heads on the attention-TP group, like the KDA `qkv_proj` / `o_proj`.
- `models/glm5_next.py`: `Glm5NextForConditionalGeneration.get_hidden_dim` sizes the buffers per layer. KDA and DSA layers differ in `o_proj`, and only KDA layers carry `qkv_proj` and the gates; other modules use `get_default_hidden_dim`.

## Validation
radixark/miles#3098 (native LoRA), GLM-5.3-Flash 4-layer slice, 8×H200, colocated, TP2/EP8 trainer, two TP4 engines, R3, lr 2e-3, 5 rollouts:
- adapter served: `train/train_rollout_logprob_abs_diff` 0.0146 / 0.0175 / 0.0169 / 0.0168 / 0.0176
- same run with the adapter not served (`--lora-train-only`): 0.0144 / 1.07 / 4.90 / 26.35 / 12.18
- 76 adapter tensors per sync with `--check-lora-weight-equal`, no mismatch

Not executed: the full 45-layer model; sglang-kernel 0.4.9 (validated on 0.4.7).
