# [Fix] diffusion/api: Publish image inputs atomically

[Upstream PR](https://github.com/sgl-project/sglang/pull/46060) · state: closed · merged: True

## Original PR description

## Summary

Fix input-image persistence used by image, video, and mesh APIs.

- Stage downloads in the destination directory and publish with `os.replace`, avoiding a cross-filesystem copy and partially published files.
- Remove unpublished temporary files in `finally`, including cancellation after downloading but before publication.
- Reject destination-directory collisions instead of returning a directory path with an upload hidden inside it.
- Remove redundant exception bookkeeping so a stale retry error cannot replace the final exception.
- Reuse one atomic byte writer for multipart/raw-byte and base64 inputs. A failed write or flush must not truncate an existing destination or leave a partial new input.

Existing size limits, retry behavior, input bytes, and remote-source bypass remain unchanged. No new flags or modules. Atomic publication requires a writable parent directory; newly staged files are owner-only, matching the URL-download path.

## Validation

- Two pre-fix failures reproduced: cancellation with a congested executor leaves an orphan temporary file; a destination-directory collision silently succeeds.
- 75 related tests pass, including partial-body retries and preservation of an existing destination.
- Upload follow-up: six pre-fix disk-write regression failures reproduced; 61 focused input/API/utility tests pass after the fix. The existing URL cases already pass and remain covered.
- A separate Linux file-size-limit test triggers real write/flush failures for bytes, bytearray, memoryview, file-like objects, multipart uploads, base64, and HTTP URLs. Across all 14 combinations of source and existing/new destination, the fix preserves the old file or leaves no published file, removes staging files, and successfully handles the next input. The original version preserves only the two URL cases.
- Real HTTP checks cover redirects, 503 retries, truncated bodies, oversized responses, streaming cancellation, and byte-identical inputs through the image/video/mesh endpoints. Model preparation is replaced at that boundary; these are not GPU generation benchmarks.
- Filesystem comparison: 28,333,361-byte PNG, 10 downloads per configuration, first excluded; nine-sample median:

| Destination | Before | After |
| --- | ---: | ---: |
| Local filesystem | 61.66 ms | 62.62 ms |
| tmpfs, different from system temp | 70.19 ms | 60.12 ms |
| Shared filesystem, different from system temp | 70.12 ms | 60.20 ms |

These numbers cover HTTP download and file publication only, not generation latency. Small inputs remained around 6 ms. File hashes match and no partial files remain.

Atomic multipart/byte writes add metadata operations: in a separate 20-sample comparison, 64 KiB inputs increased by about 0.06 ms on local storage and 0.19 ms on shared storage. This is an input-integrity fix, not a claim of zero overhead or faster inference. Upload writes remain synchronous; event-loop latency and crash durability are outside this change.

Pre-commit passes. This does not change model-specific media loaders, SSRF policy, or download deadlines, and does not promise cleanup after process termination.
