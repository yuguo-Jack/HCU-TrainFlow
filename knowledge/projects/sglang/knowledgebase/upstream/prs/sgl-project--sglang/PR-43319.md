## Motivation


`TestMxfp8AiterRouteGfx95` (added in #41970) keeps failing in `stage-b-test-1-gpu-small-amd-mi35x`, e.g. https://github.com/sgl-project/sglang/actions/runs/37709475489/job/113091795880:

```
[CI Test Method] TestMxfp8AiterRouteGfx95.test_within_one_bf16_ulp_of_the_bf16_route
  File "test/registered/kernels/ops/quantization/test_mxfp8_amd_gfx95.py", line 199, in test_within_one_bf16_ulp_of_the_bf16_route
    self.assertTrue(
AssertionError: False is not true : (1792, 5120, 1, nan)
retry() failed once (0th try, maximum 1 retries). Will delay ... and retry. Error: False is not true : (1792, 5120, 1, nan)
...
Exception: retry() exceed maximum number of retries.
```

`(1792, 5120, 1, nan)` is (N, K, M, max error in bf16 ulps): the very first case already has NaN in the output. Running the test file alone always passed, so it could not be reproduced locally at first.

Running the whole CI partition on MI355X reproduced it, and so did running just the two tests that precede it on the same GPU. Narrowing it down showed the NaN comes from aiter's group32 GEMM itself: the inputs are clean and the reference side is fine, but whole 16-column output tiles come back as NaN, and only from the packed small-M kernel. Filling LDS with `0xFF` before the GEMM makes the original kernel return NaN every time, while aiter main is clean under the same condition.

The cause is that the packed kernel loads the masked K-tail E8M0 scales with `other=127`, but on gfx950 those lanes end up with whatever earlier kernels left in LDS. The matching data is 0, so the result is usually unaffected, but a leftover `0xFF` byte (E8M0 NaN) turns the tile into NaN. That is why it only fails after other tests have run on the same GPU. Upstream fixed this in ROCm/aiter#6007 by defaulting masked scales to 0. That commit sits on top of the ROCm/aiter#5862 refactor and does not apply to our pin, so this PR applies the same one-line change to `gemm_a8w8_blockscale_group32.py` in the Dockerfile.
