# [Fix] sampling: Refresh is_all_greedy / is_any_greedy when filter_batch removes rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/44923) · state: open · merged: False

## Original PR description

## Motivation

`SamplingBatchInfo.is_all_greedy` and `is_any_greedy` are computed only in `from_schedule_batch`, from each request's `top_k <= 1`. `merge_batch` combines them (`is_all_greedy &= other.is_all_greedy`, `is_any_greedy |= other.is_any_greedy`), but `filter_batch` never recomputes them. It slices `temperatures` / `top_ps` / `top_ks` / `min_ps` / `sampling_seed` and leaves both flags alone.

So when one non-greedy request is merged into a running decode batch of greedy requests, `is_all_greedy` becomes `False` and stays `False` for the rest of that batch's life. That holds even after the non-greedy request finishes and `filter_batch` removes it. Every remaining greedy request then takes the sampling path until the batch fully drains:

- `layers/sampler.py`: the `is_all_greedy` argmax fast path is skipped in favour of top-k/top-p sampling.
- Speculative verify: for example, `eagle_utils._verify_uses_greedy` and `dspark_components/dspark_verify.py`, where the fused-argmax `AcceptGreedy` path falls back to `SoftmaxTemp` + rejection sampling. The same applies to the `is_all_greedy` branches in the dflash / uno / eagle-v2 workers and the greedy CUDA-graph variant in `eagle_draft_cuda_graph_runner`.

`is_any_greedy` goes stale the same way in the other direction: it stays `True` after the last greedy row leaves.

Outputs stay correct, because a greedy row on the sampling path still ends up at its argmax. The cost is speed. With DSpark speculative decoding, after a single sampling request had passed through the batch, we measured decode steps about 37% longer for a batch-1 greedy request.

The behaviour is present on current `main` (4eb606b2) and on older commits we checked (4cbf290f, a93f16f0).

## Modifications

`python/sglang/srt/sampling/sampling_batch_info.py`:

- Add `greedy_rows: Optional[List[bool]] = None`: per-row greedy flags kept on the CPU. This follows the existing `return_sampling_masks` / `watermark_candidates_host` pattern ("CPU request flags make batch filtering cheap"), so no device sync is added.
- `from_schedule_batch`: build `greedy_rows = [r.sampling_params.top_k <= 1 for r in reqs]` and derive `is_all_greedy` / `is_any_greedy` from it. The definition is unchanged.
- `filter_batch`: when `greedy_rows` is set, slice it by `keep_indices` and recompute `is_all_greedy = all(...)` and `is_any_greedy = any(...)`. After a filter, the flags now equal what `from_schedule_batch` would compute for the remaining requests.
- `merge_batch`: concatenate `greedy_rows` when both sides have it (as a new list, since `copy_for_forward()` copies share it). Otherwise set it to `None`, which falls back to the previous behaviour: flags are AND/OR-combined on merge and left unchanged on filter. The existing `&=` / `|=` merge logic is untouched.

`SamplingBatchInfo` objects built directly rather than via `from_schedule_batch` keep `greedy_rows=None` and behave exactly as before. This covers the CUDA-graph capture info in `eagle_draft_cuda_graph_runner` and the prewarm info in `dflash_worker_v2`, which also never go through `filter_batch` / `merge_batch`.

`test/registered/unit/sampling/test_sampling_batch_info.py` (CPU only), new `TestGreedyFlags` class plus one `from_schedule_batch` end-to-end test:

1. greedy + non-greedy merged, then the non-greedy row filtered out -> `is_all_greedy` is `True` again;
2. all-greedy batch -> a non-greedy row merges in (`False`) -> filtered back out (`True`);
3. `is_any_greedy` symmetric: it goes back to `False` once the last greedy row leaves;
4. merge with a side that has no `greedy_rows` (either side, or both) falls back without error and keeps the old flag semantics;
5. per-row flags stay aligned with non-contiguous, reordered `keep_indices`, across filter -> filter -> merge -> filter, and match `top_ks`;
6. `from_schedule_batch` -> `merge_batch` -> `filter_batch` on mocked requests: the greedy flags recover after the sampling request leaves.

## Accuracy Tests

Sampled tokens do not change: a greedy row resolves to its argmax on either path. Returned logprobs for greedy rows can come from a different kernel on the sampling path (for example `log(softmax(x))` instead of `log_softmax(x)`), so while the flag was stale they could differ in the last bits from what the same request returns in an all-greedy batch. With this change they are computed the same way as in a freshly built batch with the same requests.

The refresh never routes a row to the wrong path. `is_all_greedy` can only flip back to `True` once no non-greedy row remains, so a sampling row is never routed to the greedy path. `is_any_greedy` can only flip to `False` once no greedy row remains. In both cases the flags match what `from_schedule_batch` computes for the remaining requests.

## Speed Tests and Profiling

The fix removes an avoidable slowdown and adds no work on the hot path. Each filter does an O(batch) list slice plus `all` / `any` on the CPU, next to the existing host-side flag lists, with no device sync.

Cost of the stale flag, as described above: with DSpark speculative decoding, a batch-1 greedy request's decode step was about 37% longer after a single sampling request had joined and left the batch (stale `SoftmaxTemp` verify vs. fused-argmax `AcceptGreedy`). With this change, the greedy request returns to the same path it was on before the sampling request joined.

CPU repro (only `from_schedule_batch` / `merge_batch` / `filter_batch`, two greedy requests plus one `temperature=0.7` request that joins and then leaves):

```
                     before (main)   after (this PR)
greedy batch         True            True
+1 sampling request  False           False
sampling req left    False  (stale)  True
fresh batch, same 2  True            True
```
