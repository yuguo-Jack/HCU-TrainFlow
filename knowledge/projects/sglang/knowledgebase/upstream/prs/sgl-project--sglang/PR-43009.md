# [Feat] deepseek-v4: Rebuild the evicted SWA window on a cache hit instead of prefilling again

[Upstream PR](https://github.com/sgl-project/sglang/pull/43009) · state: open · merged: False

## Original PR description

## Motivation

- DeepSeek-V4 keeps two kinds of KV for a cached prefix: the full KV (compressed entries and indexer keys) and a smaller sliding-window (SWA) KV. Under memory pressure the SWA KV of an idle prefix is evicted first.
- On main, a request that reuses such a prefix gets no cache hit. It prefills the whole prefix again even though the full KV is still on the GPU.
- This PR rebuilds the SWA KV instead. It replays only the last tokens of the prefix (5,632 for V4-Flash) and reads everything older from the cached full KV.
- On a 120K-token prompt the request after an eviction takes 0.21 s instead of 2.21 s.
- This is a smaller take on #31713 by @jellysnack. The replay length and the "at least twice the replay length" threshold come from that PR.

## Modifications

- New server flag `--enable-swa-recompute`, off by default.
- Replay length: `ceil_align(ceil_align(W, page) + (L - 1) * W, page)` for window `W` and `L` layers. Layer `l` needs window rows built from layer `l - 1`, one window further back each time, so only the last window of the replay is exact and only that window is kept.
- Cache side (`unified_cache/swa_recompute.py`):
  - A match reports how many full-KV tokens a replay would make reusable. Prefixes that would save less than twice the replay length are prefilled again as before.
  - When the request is admitted, fresh SWA rows are bound to the replayed tokens and the last window is attached to the tree. The other rows are scratch and are freed after the forward.
  - The scratch rows are freed with the page-aligned segment free, which does not call `torch.unique`.
- Worker side (`model_executor/swa_recompute.py`):
  - The replay is one extra extend forward over the replayed tokens, run before the request's normal extend.
  - It writes SWA rows and the 4x compressor state, which lives beside the SWA rows. It does not store compressed or indexer entries, so the cached full KV is not touched.
  - Window slots before the replay start are masked with the existing `swa_replay_start` floor.
  - The prefill CUDA graph is not used for the replay.
- DSpark: the draft keeps its own SWA rows. They are rebuilt from the replay's captured hidden states through the existing prefill injection path. The draft placement of each replay is computed before the target forward, like the normal prefill, because prefill read-done releases the tables it reads.
- The flag is refused at startup with DeepSeek-V4.1, DP attention, context parallelism, pipeline parallelism, PD disaggregation, the TRT-LLM attention backend, the unified KV layout, unified memory, online C128 compression, two-batch overlap, mixed chunks, HiSparse, LoRA, radix sessions, the external cache linker, speculative decoding other than DSpark, SM120 and non-CUDA hardware.
- Docs: a row in the server arguments table and a section in the DeepSeek-V4 cookbook.
- Tests: the request stubs in `test_prefill_adder.py` and `test_batch_result_processor_hidden_states.py` and the forward-batch stubs in `test_dsv41_late_layer_tail_readers.py` and `test_encoder_swa_replay.py` get the new replay fields, because the scheduler and the attention backend now read them. `test_forward_observer.py` and the hand-built cache in `test_unified_radix_cache_core.py` get them too. A new test in `test_unified_radix_cache_core.py` evicts a window, checks the reported replay hit, binds the replay rows and checks that the prefix matches again.

Differences from #31713:

1. A server flag instead of an environment variable.
2. The replay binds fresh SWA rows through the normal full-to-SWA mapping. There is no private-page routing in the planner or the attention kernels, and no change to the compress-plan JIT kernel.
3. DSpark is supported.
4. HiCache is not covered. Only full KV that is on the GPU is reused.

## Accuracy Tests

`deepseek-ai/DeepSeek-V4-Flash-0731` on 4x B300. The check is the repo's cache-hit KL helper, `test_input_output_logprobs_match_prefill_cache_hit_helper`, run on 8 LongBench-v2 prompts of 13,436 to 26,739 tokens with 512 new tokens. The helper's default prompt length is 3,000 tokens, which is too short to rebuild, so the prompts were cut at 12,000 to 36,000 tokens instead. It prefills each prompt, generates from the cache hit, and compares the output logprobs with a cold prefill of the same tokens.

The squeezed pool has 12,800 SWA rows, so each prompt's SWA KV is evicted by the next prompt. The intact pool keeps every prompt's SWA KV.

```bash
# rebuild, squeezed SWA pool
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 400000 --swa-full-tokens-ratio 0.032 --max-running-requests 1 --enable-swa-recompute

# rebuild with DSpark, squeezed SWA pool
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 400000 --swa-full-tokens-ratio 0.032 --max-running-requests 1 --enable-swa-recompute --speculative-algorithm DSPARK

# intact cache
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 400000 --swa-full-tokens-ratio 0.5 --max-running-requests 1 --enable-swa-recompute

# intact cache with DSpark
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 400000 --swa-full-tokens-ratio 0.5 --max-running-requests 1 --enable-swa-recompute --speculative-algorithm DSPARK

# flag off, squeezed SWA pool
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 400000 --swa-full-tokens-ratio 0.032 --max-running-requests 1
```

| Server | Prompts with a cache hit | Hits through the rebuild | Average KL |
|---|---|---|---|
| Rebuild, squeezed pool | 8/8 | 7 | 0.0046 |
| Rebuild with DSpark, squeezed pool | 8/8 | 7 | 0.0063 |
| Intact cache | 8/8 | 0 | 0.0048 |
| Intact cache with DSpark | 8/8 | 0 | 0.0054 |
| Flag off, squeezed pool | 0/8 | 0 | not computed |

- Each row is one run. This model is not reproducible run to run at these prompt lengths. Earlier runs of the intact row on the same prompts gave 0.0036 to 0.0059, and a cold run with DSpark and no cache hit gave 0.0071, so the rebuild rows are within noise of the intact rows.
- The last prompt is never evicted, so it is a normal hit in every row.
- No scheduler exceptions in any run.
- I merged main into this branch twenty times to clear conflicts, and ran the rebuild rows again after nineteen of them. The fifteenth merge was replaced by the next one before it ran. Every finished run gave 8/8 hits and no scheduler exceptions, with average KL between 0.0027 and 0.0071. The latest run, after merging main at `ba1ed00dfe`, gave 0.0033 with DSpark. An earlier run, at `7bc92100ad`, gave 0.0071, the same as the cold DSpark run above.
- The merge at `7bc92100ad` needed three code changes. Main removed `KVLocPlan`, so the replay uses `PrefillPlacement`. Main removed `UnifiedSWAAllocatorBase`, and unified pools are now `ChainAllocator`, which `supports_swa_recompute` already rejects. Main made `component_type` a required argument of `swa_tombstone_ranges` and `attach_swa_window`, so this PR passes it.

## Speed Tests and Profiling

Same model and hardware. A 120,000-token prompt A is prefilled, a second 120,000-token prompt evicts A's SWA KV, and A is sent again. This is repeated four more times. Numbers are time to first token.

```bash
# flag on
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --speculative-algorithm DSPARK --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 300000 --swa-full-tokens-ratio 0.032 --max-running-requests 8 --enable-swa-recompute

# flag off
python3 -m sglang.launch_server --trust-remote-code --model-path deepseek-ai/DeepSeek-V4-Flash-0731 --tp 4 --moe-runner-backend flashinfer_mxfp4 --speculative-algorithm DSPARK --mem-fraction-static 0.90 --chunked-prefill-size 8192 --max-total-tokens 300000 --swa-full-tokens-ratio 0.032 --max-running-requests 8
```

The no-DSpark row uses the flag-on command without `--speculative-algorithm DSPARK`.

| Server | Cold prefill | Hit, SWA KV intact | Hit after SWA eviction |
|---|---|---|---|
| Flag off, DSpark | 2.21 s | 0.10 to 0.14 s | 2.21 s (prefilled again) |
| Flag on, DSpark | 2.21 s | 0.10 to 0.14 s | 0.21 s |
| Flag on, no DSpark | 2.19 s | 0.10 to 0.12 s | 0.21 s |

- One server run per row. The "after eviction" number is the same within 0.01 s over the last four cycles. The first rebuild after server start takes 0.26 s.
- The rebuild costs about 0.1 s more than an intact hit. That is the replay forward over 5,632 tokens.
- After nineteen of the merges, the flag-on DSpark row was run again: 0.20 to 0.24 s after eviction and 2.18 to 2.25 s cold. The latest run, after merging main at `ba1ed00dfe`, gave 0.21 s after eviction and 2.18 to 2.19 s cold. Its first cold prefill after server start took 2.36 s.

## Follow-ups

- The new cache test covers the match and the row binding. A registered end-to-end test still needs a V4-Flash lane with a squeezed SWA pool and the KL helper on long prompts.
- HiCache, DP attention and PD disaggregation are not supported yet.
- The DSpark draft rows are rebuilt from the replay's hidden states. The KL check above does not tell an exact draft window from a stale one. The only check on the draft side is the accept length in the timing run, with 32 new tokens on a random-token prompt. In the latest run it was 2.67 to 2.91 on the five rebuilds and 2.91 to 3.20 on intact hits. Earlier runs had single rebuilds at 1.21 and 1.68, and the latest run had a cold prefill at 1.20, so a single low value is not specific to rebuilds. A real-text accept-length check is still owed.
