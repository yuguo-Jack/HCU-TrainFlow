## Motivation

TL;DR decode needs to send memory addresses reserved for a request (this is called publishing) to prefill in order for prefill to initiate kv-transfer. Publishing happens on the host, but memory allocation happens on device. Consequently decode needs a D2H, waiting on the device memory allocation, to get the memory addresses (in the form of page indices). To avoid syncing on the D2H and stalling the scheduler, we defer publishing by 1 decode iteration.

<img width="3060" height="1620" alt="pr_timeline_comparison" src="https://github.com/user-attachments/assets/9ecb04be-2c58-4235-8a37-c2dd5031b8be" />

`k` refers to which iteration it happens in. Allocation `k` is used in the far future, it is not used in forward `k` or `k+1`.

Under the overlap scheduler, PD (prefill/decode disaggregation) decode still makes the host wait on the in-flight forward about once per new request. Each wait idles the GPU, and with attention DP (data parallelism) it idles every DP rank.

After launching a forward, the scheduler fences `schedule_stream` behind it (`_apply_war_barrier`, a write-after-read barrier). A host-blocking call on `schedule_stream` while the next batch is being scheduled therefore waits for that forward. The next forward can't launch until the host returns, so the GPU idles in between. With attention DP, the per-batch DP sync spreads one rank's stall to every rank.

Two such calls remain on main's PD decode path:
1. **Destination publish.** `DecodePreallocQueue.pop_preallocated` allocates a request's KV pages on `schedule_stream`. It then immediately reads the page indices back to the host, through `kv_to_page_indices(...).cpu()` and the state-index payloads, to send them to prefill. The readback waits for the allocation, which is queued behind the forward.
2. **EAGLE draft input.** `build_eagle_disagg_draft_input` calls `torch.any(...).item()` on the remapped device tensor to check whether any DSA (DeepSeek Sparse Attention) seed row is empty. It runs after `schedule_stream` has waited on the forward stream, so it waits for the whole forward.

#38955 and #44598 made the nearby H2D (host-to-device) copies non-blocking. Within an iteration, the first blocking call pays the whole stall. The decode step stops stalling only once these two calls are gone too.

## Modifications

**1. Deferred destination publish** (`disaggregation/decode.py`). This is on when overlap and the WAR barrier are on (CUDA, or `SGLANG_ENABLE_WAR_BARRIER`), `pp_size == 1`, HiSparse is off and the staging buffer is off. Otherwise the publish runs inline as before.
- `pop_preallocated` no longer reads anything back. It does five things:
  - reserves the request's metadata buffer slot, since free slots cap admission in the same pass;
  - sets `DecodeRequest.awaiting_publish`;
  - counts the request as a published destination until the transfer queue takes it. That keeps the unified-memory move gate closed, as the inline publish did, so a later allocation in the same pass can't compact the request's pages before the publish reads them back;
  - records a CUDA event after the allocation;
  - moves the request to the transfer queue at once.

  In the transfer queue the request polls `WaitingForInput` until its KV arrives, as before.
- `publish_pending_destinations()` runs at the start of the next `process_decode_queue`. For each pending request, a side stream waits only on that request's event. It then reads the indices back and sends them to prefill through `_publish_destination`, which is the previous inline body, moved; its two defensive `getattr` calls are now `isinstance` checks. The side stream comes from PyTorch's priority -1 pool. The schedule, forward and result-copy streams all wait on the forward and come from the default pool, so the side stream can't alias them. Afterwards `schedule_stream` waits on the side stream, so later forwards see the publish's GPU writes (DSV4 request-state clears).
- Ordering:
  - The event is recorded after the allocation, which was fenced behind the previous forward's reads. So the side stream reads a finished allocation and writes only after that forward.
  - The forward in flight at publish time can't read the request's rows, because the request joins no batch until its KV arrives.
  - Prefill learns the destination only after the side stream's host readback returns, as before.
- Cost: prefill learns the destination one decode iteration later.
- Why it's off with PP, with staging, or without the WAR barrier:
  - With PP, `pop_preallocated` is called from the PP mixin rather than from `process_decode_queue`, so nothing would publish.
  - With the staging buffer, a room is registered with the staging handler only at publish, but staging polls every queued request.
  - Without the WAR barrier (the ROCm default), `schedule_stream` isn't fenced behind the in-flight forward, so the inline readback doesn't stall and deferral would only add latency. The barrier's predicate moved to `managers.utils.is_war_barrier_enabled()`, which the scheduler uses too.

**2. Failures inside the deferral window.**
- The publish all-reduces one poll per pending request over the attn-TP (attention tensor-parallel) group and skips failed requests. A request the transfer queue has already released has no receiver. `_ReleasedReceiver` stands in for it and polls as `Failed`, so every rank still passes the same list to the collective. These polls skip test failure injection (`inject_failure=False`): an injected failure leaves the receiver live, so the transfer queue would never release the skipped request.
- `pop_transferred` releases a failed request that is still `awaiting_publish` at once, instead of through deferred KV release. No prefill rank received its destination, so none can write into its pages. Deferred release would wait for drain acknowledgements that are never armed for such a request. It would hold the KV for the full `SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE_TIMEOUT` (30 s). The immediate release also clears any abort-ACK tracking that the abort, or the receiver's `clear()`, armed under the `prefill_complete` allocation policy. No drain would ever resolve it. `awaiting_publish` is the same on every attn-TP rank, so the ranks still agree on whether to hold its KV.
- `release_memory_occupation` also clears the pending publishes.

**3. DSA seed check on the host** (`speculative/eagle_disaggregation.py`). Whether any row ends up without a seed is now decided on the host copy of the seed. It uses the same per-row conditions the device remap applies:
- all entries are < 0;
- or, when remapping, any entry is < −1, ≥ `seq_len`, or ≥ the `req_to_token` width.

The remap's one device-only condition is a valid position that maps to an unallocated slot (≤ 0). It cannot hold here. Before a request reaches the prebuilt path, every slot of its `req_to_token` row below `seq_len` has been written: by prealloc, and for a cached prefix by the decode prefix cache and the HiCache restore.

**Tests** (`test/registered/unit/disaggregation/`):
- `test_deferred_destination_keeps_its_metadata_slot_until_published`:
  - nothing is sent at prealloc;
  - the publish waits on the request's event and sends with the slot reserved at prealloc;
  - the published-destination counter nets to zero.
- `test_deferred_destination_closes_the_move_gate_until_queued`: a deferred request keeps the unified-memory move gate closed until the transfer queue takes it.
- `test_released_receiver_keeps_the_publish_reduction_aligned`: a released pending request still contributes one poll and is not published.
- `test_publish_ignores_injected_poll_failures`: an injected poll failure doesn't skip a live receiver's publish.
- `test_failure_before_deferred_publish_releases_immediately`: a failure before publish is released in the same pop, not deferred, and the abort-ACK tracking its receiver's `clear()` armed is cleared.
- `test_pd_decode_fused_topk_drops_seed_past_request_length`: the host check drops the seed when a row has a position past the request length.

## Speed Tests and Profiling

The measurements below predate #38955 and #44598, so this change also made those H2D copies non-blocking. They therefore measure all the blocking sites together. If only the H2D copies are fixed, the stall moves to the two calls this PR removes. The measurements also predate this revision's review fixes (WAR-barrier gate, priority -1 side stream, move-gate count, failure-path fixes), none of which adds work to an iteration that publishes.

**Decode-only A/B (n = 1 per arm).** Setup:
- GLM-5.2 NVFP4 decode, DEP4 (attention DP + expert parallelism over 4 GPUs), with MTP (multi-token prediction) on one node.
- `--disaggregation-transfer-backend fake`, so prealloc, transfer and prebuilt run without a prefill server.
- 36 closed-loop clients, 60k to 180k-token prompts, 500 to 1,500 output tokens.
- 420 s window after a 120 s warm-up.

| | without | with |
|---|---|---|
| iterations with `process_decode_queue` or batch selection > 10 ms | 8.9% | 0.1% |
| decode step mean / p50 / p99 (ms) | 30.06 / 28.60 / 62.3 | 29.17 / 28.57 / 37.3 |
| blocking syncs per request in those two stages | 11 | 0 |
| output throughput (tok/s) | 2,946 | 3,005 (+2.0%) |

Both arms ran with CUDA sync tracing, which adds host cost to every sync. The matching p50 indicates matched load.

**Full-scale PD.** Setup: GLM-5.2 NVFP4, 4 prefill workers (PP4 each) → 1 decode worker (DEP8) with MTP, Mooncake transfer, 24 GB300 GPUs, an agentic multi-turn trace at concurrency 227. Nsight Systems captured 80 decode iterations on all 8 decode ranks:

| | without | with (3 captures) |
|---|---|---|
| iterations where a rank blocks > 10 ms in `process_decode_queue` or batch selection | 18 of 79 | 0 of 78 in each |
| GPU idle per decode step | 1.60 ms | 0.47 ms |

- Without this change, each stall was one 21 to 26 ms `cudaStreamSynchronize` on one or more ranks while the others waited at the DP sync, costing about 6 ms of GPU idle per stalled step.
- The captures with this change also switched the MoE all-to-all backend. That changes transfer time but not host stalls.

**Stability.** This change, ported to an older base and combined with unrelated prefix-cache and decode-allocation changes, ran six 1-hour runs of the full-scale deployment. Together they served about 124k measured requests plus warm-ups, with 0 errors, and every run completed.

End-to-end throughput was not measured for this change alone.

**Known limitations:**
- **Early ABORT.** Once the handshake is done, decode sends ABORT to every prefill rank, whether or not the destination was published. A prefill rank that hasn't registered the room yet drops the ABORT and waits out `SGLANG_DISAGGREGATION_BOOTSTRAP_TIMEOUT` (300 s). It holds no KV, but the client waits.
  - This already happens for aborts during the handshake; deferral widens the window by one iteration.
  - In the abort storm: 1 such timeout with this change (from a request that failed while awaiting publish), 1 without (6cac4dc).
  - The fix belongs on prefill: keep an early ABORT until the room registers.
- **GPU metadata buffers.** `SGLANG_MOONCAKE_CUSTOM_MEM_POOL=INTRA_NODE_NVLINK` puts the metadata buffers on the GPU. There the seed's `.cpu()` is a real device read, as are the existing per-request `.item()` reads in `_commit_transfer_to_req`. The default, with host buffers, is covered.
- **Stream ordering.** The unit tests mock CUDA streams, so the GPU ordering is validated only by the end-to-end runs.
- **ROCm side stream.** PyTorch gives ROCm two stream priorities, so the priority -1 pool is shared with high-priority NCCL streams (`TORCH_NCCL_HIGH_PRIORITY`). With that and `SGLANG_ENABLE_WAR_BARRIER` both set, a pool slot repeats after 32 draws. An aliased publish readback would then wait for that NCCL work. This affects latency only, not correctness.

**Issue**
