# [Perf] hicache: Optional parallel page reads in the file storage backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44776) · state: open · merged: False

## Original PR description

## Motivation

`HiCacheFile` (the `file` L3 storage backend) reads one page file at a time on each rank's single prefetch I/O thread (`open` + `readinto` per page). On a node-local NVMe tier with large prompts this serializes restores: in our tests (MiMo-V2.6-Pro, TP4 on B300, `--hicache-storage-backend file`) a rank read ~1.3 GB/s single-threaded, and when many sessions resumed at once loads queued until prefetches timed out and fell back to recompute.

The existing multi-I/O-worker work (#31440 / #31797) parallelizes whole operations, which can reorder them across ranks. This change only parallelizes the file reads *inside one* `batch_get` / `batch_get_v2` call and returns after all of them, so operation order across ranks is unchanged.

## Modifications

- New env `SGLANG_HICACHE_FILE_BACKEND_READ_WORKERS` (default `1` = current behaviour), documented in `environment_variables.mdx`.
- `HiCacheFile._map_reads`: runs the reads of one call on a lazily created `ThreadPoolExecutor`, waits for all of them, keeps input order; a read that raises becomes a miss (`None` / `False`) instead of failing the batch.
- `batch_get` uses it; `_batch_io_v2` (used by `batch_get_v2`) reads pages into private staging pages on the pool, chunked (4 × workers), while every `set_from_flat_data_page` stays on the calling thread in page order. That last point matters: a unified host pool takes a thread-local layout lease in `set_from_flat_data_page` and the caller already holds it for the whole transfer; our first version wrote pages from pool threads and deadlocked (a pool thread with lease depth 0 waited for a pending compaction, which waited for the I/O thread's lease → one rank's prefetch ack never arrived).
- Writes (`batch_set*`) stay serial.
- New CPU test `test/registered/hicache/test_hicache_file_parallel_reads.py`: parallel equals serial (bit-exact, same order), pool writes stay on the calling thread, a missing page is a miss, `batch_get` parallel equals serial, and reads really run on several threads (this one fails without the change).

## Accuracy Tests

No model code changes. With the same change on `lmsysorg/sglang:dev` (nightly 684fea8a), 8 workers, MiMo-V2.6-Pro on 4× B300: 0 hangs, 0 tracebacks, answers identical to a cold run after restores from disk (temperature 0), and ~14 h of reasoning benchmarks with the disk tier on afterwards without errors.

## Speed Tests and Profiling

Honest numbers, measured on that setup (8 workers vs serial):
- raw read throughput of real page files per rank: 1.27 GB/s (1 thread) → 3.35 GB/s (8 threads);
- end-to-end restores: ~+25 % at 32 concurrent resumes of 56k-token prompts (30.3 s vs 37.9 s, all from disk), no gain for a few large ones (4 × 741k: 78.2 s vs 71.8 s). The file read stops being the main limit; what remains is serial (existence check, per-page staging copy, page-by-page `set_from_flat_data_page`).

So this is a modest, opt-in improvement for node-local storage, not a big win; it is off by default.
