# [Feat] DSv4.1: Run deepep_v2 on DeepEP 2.5 with FP4 experts and DSpark drafts

[Upstream PR](https://github.com/sgl-project/sglang/pull/46010) · state: open · merged: False

## Original PR description

[codex/claude generated]

## Motivation

Without MNNVL, MegaMoE cannot span nodes, so `deepep_v2` is the only cross-node expert-parallel path for DeepSeek-V4.1-Flash on multi-node B300 (8 GPUs over NVLink per node, InfiniBand between nodes). On current main, that path does not work for this model:

- `deepep_v2` rejects the FP4 (1x32 UE8M0) experts.
- DSpark under DP attention does not allow `deepep_v2`.
- The backend targets DeepEP 2.1 `ElasticBuffer`. DeepEP 2.5 (main f6aa38f, deepseek-ai/DeepEP#763) replaced it with `EPBuffer` and changed the `topk_idx` handle semantics.
- With FP4 experts, the masked decode path fails in DeepGEMM. The activation scale groups are wrong, and a whole-slab clamp costs ~255 ms per step on EP16.
- Multi-node is forced into hybrid mode, although DeepEP 2.5 direct mode works over RDMA.

## Modifications

- **FP4 experts on `deepep_v2`:** accept them and run DeepGEMM's FP8 x FP4 grouped GEMM, recipe (1,128)/(1,32).
- **DSpark:**
  - Allow `deepep_v2` in DSpark's DP-attention allowlist.
  - Share one buffer across top-k values, sized for the max. Draft layers (top-3) no longer rebuild it collectively at every target/draft switch (previously 4 rebuilds, ~0.7 s).
- **DeepEP 2.5:**
  - Import `EPBuffer` from `deep_ep_v25` first. [sgl-deep-ep-v25](https://pypi.org/project/sgl-deep-ep-v25/) packages DeepEP 2.5 under that name, so it installs next to `sgl-deep-ep` (`deep_ep`).
  - Otherwise import `EPBuffer` from `deep_ep` (upstream 2.5), and fall back to `ElasticBuffer` on 2.1.
  - If `deep_ep_v25` is installed but fails its import-time host checks, log a warning and fall back to `deep_ep`.
  - Pass DeepEP a private int64 `topk_idx`, because 2.5 keeps it in the handle and asserts `do_handle_copy=False`.
  - When `SGLANG_DEEPEP_V2_NUM_SMS=0`, the buffer spans RDMA ranks, and `ibstat` is absent, use 32 SMs. DeepEP's ibstat-based estimate divides by zero in that case.
- **Masked activation group:** take it from `recipe_a` (128), not the checkpoint block size ([32, 32] for V4.1-Flash). This fixes the DeepGEMM `sf.size(-1)` assertion in the masked down GEMM. Both runners share `DeepGemmMoeQuantInfo.activation_group_size()`.
- **Masked SwiGLU limit:** the masked Triton `silu_and_mul` + per-group quant kernel now applies the DeepSeek-V4 limit itself and visits only rows below `masked_m`. Scales start zeroed, because UE8M0 packing faults on NaN in unwritten rows. This replaces the in-place clamp of the whole masked workspace.
- **Masked slab sizing:** new `SGLANG_DEEPEP_V2_NUM_MAX_MASKED_TOKENS_PER_RANK` sizes the masked decode slab separately from the dispatch capacity. Unset, it defaults to the dispatch capacity, which also caps it. A prefill-sized capacity of 8192 no longer forces a ~30 GiB decode workspace on DEP2. Oversized decode batches raise instead of overflowing, and the decode CUDA-graph budget check validates against this capacity.
- **Direct mode across nodes:** remove the `nnodes > 1` guard. DeepEP 2.5 direct mode reaches remote peers over RDMA.
- **Debugging:** optional `SGLANG_DEEPEP_V2_TRACE_MASKED` logging of the masked down-GEMM input layout.
- **Tests:**
  - `test_deepep_v2_buffer_lifecycle` is new.
  - `test_hpc_ops_runner_guard`, `test_deepep_v2_wire_dtype` and `test_server_args` cover the new guards.

## Accuracy Tests

GSM8K, native harness, DeepSeek-V4.1-Flash with DSpark (block 5), B300:

| Config | Score | Accept length |
| --- | --- | --- |
| DEP2 MegaMoE (main, baseline) | 0.9741 | 4.330 |
| DEP2 `deepep_v2` on DeepEP 2.5, CUDA graph / eager | 0.9718 / 0.9734 | 4.331 |
| DEP16 (2 nodes) `deepep_v2` hybrid | 0.9756 | 4.353 |
| DEP16 (2 nodes) `deepep_v2` direct | 0.9726 | 4.339 |

Kernel-level checks on B300:

- FP8 x FP4 grouped GEMM at the V4.1 shapes, masked and contiguous, matches a dequantized torch reference: diff ~1.4e-6, against ~1.0 for a nibble-swapped control.
- An EP2 dispatch -> FP4 MoE -> combine round trip matches a reference MoE in prefill (diff 7-10e-5) and masked decode (diff ~1e-4). Masked decode failed before this change.

## Speed Tests and Profiling

DEP16 across two B300 nodes, decode-only with simulated acceptance 3.51 and 128K contexts. The table shows decode step time:

| Arm | bs8 | bs32 | bs128 |
| --- | --- | --- | --- |
| Hybrid, before the masked-limit fix | 284 ms | 293 ms | 336 ms |
| Hybrid, this PR | 38.2 ms | 47.3 ms | 90.8 ms |
| Direct, this PR | 22.8 ms | 34.8 ms | 89.7 ms |

DeepEP 2.5 `test_ep` at EP16 (dispatch / combine, us per call):

| Tokens per rank | Direct | Hybrid, 24 SMs |
| --- | --- | --- |
| 1 | 62 / 64 | 216 / 223 |
| 48 | 78 / 72 | 220 / 223 |
| 192 | 92 / 116 | 231 / 275 |

Direct mode passes `test_ep` reference checks at 48, 768 and 4096 tokens per rank.

Limitations:

- On B300 without MNNVL, single-node DEP8 MegaMoE remains faster per GPU than this cross-node DEP16 path. For example, a DEP8 decode step is 12.7 ms at bs8. This PR makes the cross-node path correct and usable; it does not make it the faster layout.
- Decoder bounded replay remains limited to `none`/`megamoe` under DP attention, so this path runs without it.
- The perf numbers come from a decode-only simulation, not a PD production trace.
