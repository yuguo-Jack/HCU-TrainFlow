# [Fix] hicache: Consume the pending CUDA error when host registration fails

[Upstream PR](https://github.com/sgl-project/sglang/pull/41245) · state: open · merged: False

## Original PR description

## What this changes

`_cuda_host_register` now consumes the pending CUDA error before it re-raises: a small module-level helper plus one call in the existing `except` block. Nothing else changes — in particular the abort-vs-degrade policy on a failed registration is deliberately left alone.

## Why

A failed `cudaHostRegister` does not only fail that call. The error stays pending in the current thread's CUDA error slot, so the **next unrelated CUDA call** surfaces it. Measured on H20 / CUDA 13.0 / torch 2.13.0+cu130, one scenario per fresh error state:

| scenario | result |
|---|---|
| failing `cudaHostRegister` (rc=1), then an unrelated CUDA call | fails with `CUDA error: invalid argument` |
| rc=1, then `torch.cuda.synchronize()`, then an unrelated CUDA call | still fails — synchronize does not clear it |
| rc=1, then one tiny kernel launch, then an unrelated CUDA call | succeeds |
| `hasattr(cudart, "cudaGetLastError")` | `False` on this torch build, hence the kernel-launch route |

So during a HiCache startup the real `rc` is reported and then the diagnostic is destroyed: the failure resurfaces later at an unrelated call as "invalid argument", which is what made the original report hard to attribute. Consuming it inside the failure path keeps the failure where it happened.

(Correction to my earlier comment in #40926: I also claimed a rollback leak — that is **not** correct on this stack. `cudaHostUnregister` of an earlier valid range returns 0 even while the error is pending. I removed the claim from the thread; the call is kept *before* the rollback here only as a defensive ordering.)

## Verification

- `test/registered/unit/mem_cache/test_hicache_host_register.py`: one new test asserts that a failed registration consumes the pending error before the rollback and still raises. Without the change the new test cannot pass (the module has no consumer to observe); with it, it passes and the rest of the file is unaffected.
- Real startup: 8×96 GiB H20 node, hybrid SSM (27B) model with `--enable-hierarchical-cache`, host pools built and the server reached a healthy state.

## Not included

- No change to the default abort semantics of a failed registration — that is the design question raised in #40926.
- **No opt-out to disable host registration.** I prototyped it and it is not safe as-is: with registration disabled the host buffers are pageable while the `kernel` I/O path still needs device-accessible host mappings, and the instance dies on the first forward with `CUDA error: an illegal memory access` (same image/model/flags with registration enabled boots and serves — a single A/B observation, not re-run). Disabling it would require switching the transfer path too, which is a much larger change than this PR.

## Relation to the other open PRs

#38509 and #40952 both change the `cudaGetErrorString(rc)` typing in this same function (they look identical); #38832 covers the 712 double-registration path; #39744 changes the chunk loop. This PR only adds a helper and touches the `except` block, so it should merge independently — if #38832 / #39744 rewrite that block, the conflict is a two-line rebase.
