# [Fix] minimax-m2: streaming tool calls are lost and markers leak into content

[Upstream PR](https://github.com/sgl-project/sglang/pull/36691) · state: open · merged: False

## Original PR description

## Motivation

Partially addresses #35564 — the `minimax-m2` row, reported as *"the call is gone"*.

Reproducing it on CPU (no server, no model) showed the failure is broader than a lost call: with real token-by-token streaming the detector never recognises the tool call at all and emits the raw XML markers as user-visible content, one character at a time.

Investigating that surfaced four distinct divergences from `detect_and_parse`, all in `parse_streaming_increment`. They share the same buffer-handling code, so they are fixed together.

## Root causes

**1. A partial start token was flushed as normal text.** The buffer is emitted and cleared whenever it does not yet contain the complete `<minimax:tool_call>` marker. When the marker arrives in fragments — which is exactly what detokenized streaming produces — every fragment was emitted as content and the call was never detected. The trailing partial marker is now held back using the base class's `_ends_with_partial_token`, the same way `BaseFormatDetector` does.

**2. A call with no parameters streamed no arguments at all.** `_parse_and_stream_parameters` emits nothing when the parameter dict stays empty, and the closing-brace step is guarded by `if current_streamed:`, which is falsy in that case. The streamed arguments therefore stayed `""` while `detect_and_parse` returns `"{}"`. The empty object is now emitted explicitly.

**3. Text after the end token was silently dropped.** `</minimax:tool_call>` was never consumed: after the final `</invoke>` the detector stayed in tool-call mode looking for another `<invoke>`, so any trailing content remained in the buffer and was never returned. The end token is now consumed and tool-call mode exited.

**4. An unregistered tool name leaked its markup as content.** The remaining buffer was emitted verbatim, whereas `detect_and_parse` drops the entire invoke block. The block is now skipped instead. The warning also moved so it is logged once when the block is actually dropped, rather than on every character while the block is still incomplete.

## Modifications

`python/sglang/srt/function_call/minimax_m2.py` — all four fixes are inside `parse_streaming_increment`.

## Tests

New `test/registered/unit/function_call/test_minimax_m2_detector.py`, registered for CPU CI (no GPU, no model load).

11 cases, each replayed under **three** chunkings (character-by-character, whole string, split in half) for 33 assertions total. Every case asserts the streamed calls equal the `detect_and_parse` result with argument types preserved, and additionally that none of `<minimax:tool_call>`, `</minimax:tool_call>`, `<invoke`, `<parameter` ever appears in the returned content.

Coverage: calls with no arguments (both a populated and an empty schema), single/multiple/integer/unicode arguments, two calls in one block, text before and after the call, plain text with no call, and an unregistered tool name.

Verified before/after on this suite: 27/33 → 33/33.

What this PR isolates, in case any of it is missing there — four distinct defects rather than one:

Only #2 is the same class of bug as the other parsers in this issue; #1, #3 and #4 are specific to this detector's marker handling. Happy to rebase as a test-only addition on top of #35625 if that is more useful.

- adenzhou1350 · comment · 2026-10-11T19:01:25Z · [source](https://github.com/sgl-project/sglang/pull/36691#issuecomment-6112561160)

One related edge case remains in the closing-brace check at `464f1dc8` (and in #35625): braces inside JSON strings affect the raw character counts.

On current main `d62b9c24`, a declared string parameter `<parameter name="pattern">a}b</parameter>` streams `{"pattern": "a}b"` without the final object brace. The non-streaming parser returns the correct argument. This reproduces with the complete call in one increment and with separate invoke/parameter/end increments, so it does not depend on splitting the start marker. Braces in parameter names and nested string values also trigger it.

The parameter builder already uses `json.dumps` for each complete key/value and deliberately leaves the outer object open. Appending one `}` at `</invoke>` when arguments are nonempty avoids counting braces in the serialized contents. A narrow local change passed 3 tests / 52 subtests; the unchanged main had 24 failing subtests. These were real-package Linux/Python 3.12 CPU checks, not server/model tests or a full run of your PR head.

Sharing this here rather than opening another overlapping parser PR. The empty-argument branch can stay as you have it.
