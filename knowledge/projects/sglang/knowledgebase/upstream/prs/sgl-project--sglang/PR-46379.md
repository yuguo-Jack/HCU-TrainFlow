# [Feat] unified-memory: Admit fa4 for EAGLE and DFLASH

[Upstream PR](https://github.com/sgl-project/sglang/pull/46379) · state: closed · merged: False

## Original PR description

> **Superseded by #46978 and #46986; closing.** fa4 no longer needs admitting: #46978 removed the speculative backend allow-list in `arg_groups/kv_cache_hook.py`, and #46986 removed the window-draft backend list in `mem_cache/layout/fused_draft.py`. On unmodified main (`76d5b3ce02`, SM90), the configurations measured below fuse their drafts on fa4 under `--enable-unified-memory` and match the default pool on GSM8K (all 1314 questions, greedy, paired by question) and accept length: Inkling-Small multi-layer EAGLE and Qwen3.5-9B NEXTN and DFLASH with CUDA graphs on and off, and MiMo-V2-Flash NEXTN with graphs on. This PR's Inkling fa4 attention-prologue CUDA test also passes on main unchanged.
>
> The original description follows for reference.

---

Stacked on #46378 ([Feat] unified-memory: Fuse sliding-window draft layers on fa3); only the last commit is new here.

## Motivation

Under `--enable-unified-memory`, fa4 already carries the fused draft's translated ids and DSPARK is admitted on it, but EAGLE (and EAGLE3) and DFLASH were still refused at boot on fa4, and a draft with sliding-window layers declined fusion there. fa4 runs on the FlashAttention backend that fa3 uses: the same code builds the page tables, the sliding-window tables and the write locations from the unified pool's translated ids, for the target's verify (whose fa4 graph metadata is already captured from the live mapping) and for the draft's own forwards. Only the attention kernel differs.

## Modifications

- fa4 joins the speculative MHA allow-list (`arg_groups/kv_cache_hook.py`), which admits EAGLE and DFLASH targets and EAGLE drafts and is the fused draft's rail set, and the sliding-window draft backends (`mem_cache/layout/fused_draft.py`). So an Inkling MTP head or a MiMo-V2-Flash MTP head on fa4 fuses into the target's pages instead of being refused at boot.
- An MLA host stays off fa4: its EAGLE target still verifies on the MLA set.

Tests:
- CPU: the spec-gate cases (`test/registered/unit/server_args/test_unified_memory_spec_gate.py`) that admit fa4 for EAGLE and DFLASH, and the placement case that admits an fa4 window draft, fail before this change and pass after; the refused example moves to a backend outside every unified set (torch_native).
- CUDA, `test/registered/kernels/ops/attention/test_inkling_attn_prologue_strided.py`: Inkling's fused fa4 attention prologue (it reads and updates the short-conv state and stores K/V in one kernel) on the unified pool's strided views against contiguous copies, for decode, verify and extend: equal outputs, and the shared buffers change exactly where the contiguous run changed its copies.

## Speed Tests and Profiling

This PR admits a configuration; it does not change kernels. For reference, with #46376 applied, Inkling-Small's multi-layer EAGLE draft on fa4 decodes about 10% slower per step on the unified pool than on the default pool at equal batch size (100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests sharing a 4096-token prefix + 128 tokens, 2048 output tokens, concurrency 192). On the unified pool that draft runs its steps as per-step CUDA graphs that rebuild draft-extend metadata eagerly, where the default pool captures one combined graph. A follow-up PR in this series, "[Perf] unified-memory: Stage a fused draft's draft-extend metadata once per draft cycle", lets the unified pool take the combined graph too and brings the gap to about 1-2%.
