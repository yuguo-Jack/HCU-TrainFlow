# [Feat] hicache: Add unified Engram store and support Qwen4-Exp

[Upstream PR](https://github.com/sgl-project/sglang/pull/46248) · state: open · merged: False

## Original PR description

## Motivation

Add a **unified Engram store abstraction to HiCache**, and support **Qwen4-Exp as its first model integration**.

HiCache provides a common interface for storing and looking up immutable Engram tables. Models supply row IDs and interpret the returned bytes, while storage backends handle table ownership and data access. This separates model computation from the storage implementation and gives Engram integrations a shared storage contract.

This PR introduces the HiCache abstraction, implements a local backend using [Mooncake EngramStore](https://github.com/kvcache-ai/Mooncake/pull/4701), and connects Qwen4-Exp PLE N-gram tables to it. The storage interface is model-independent; Qwen4-Exp is the only model integrated and validated in this PR. This supersedes #44521.

## Modifications

- **Add the HiCache Engram store interface.** `HiCacheEngramStorage` defines `initialize(rows)`, `lookup(ids)`, and `close()` for immutable byte-row tables. It is defined at the end of `hicache_storage.py`, with row-based semantics independent of the existing KV interface. `sglang.srt.mem_cache.engram.create_storage` creates row storage within the Engram module, independently of a KV cache or host KV pool.
- **Add the Mooncake backend.** `MooncakeEngramStorage` implements the HiCache interface over Mooncake EngramStore, including owned local snapshots and CUDA stream-ordered lookup. The embedding adapter uses the HiCache storage contract.
- **Support Qwen4-Exp.** Route its PLE N-gram embedding construction through the shared adapter. The model selects the embedding class directly from `enable_hi_engram`; no `make_embedding` or `enabled` forwarding helpers are needed. `HiCacheVocabParallelEmbedding` preserves weight loading, TP shard masking and dtype/prefetch semantics, while the storage backend handles byte rows. Hashing, scales, projections, request history, collectives and prefetch scheduling stay in Qwen4-Exp.

`--enable-hi-engram local` opts into the HiCache Engram store with the Mooncake backend. Omit the option to keep the model's native implementation; there is no `native` configuration value. The options live under **Hierarchical engram**, after hierarchical sparse attention. `remote` is reserved and rejected when constructing Engram storage because Mooncake's remote table API does not yet support CUDA stream/graph lookup.

```bash
python -m sglang.launch_server \
  --model-path /models/Qwen3.8-Flash-Next-FP8 \
  --tp-size 4 --ep-size 4 --ple-offload-embedding \
  --enable-hi-engram local \
  --hi-engram-config '{"local_dir": "/dev/shm/sglang-engram"}'
```

**Dependency:** the Mooncake backend requires a CUDA-enabled build of [Mooncake #4701](https://github.com/kvcache-ai/Mooncake/pull/4701), discussed in [RFC #4692](https://github.com/kvcache-ai/Mooncake/issues/4692). This PR supports local host snapshots. Remote row storage and additional model integrations are outside its implementation scope.

The first eager lookup publishes an anonymous immutable snapshot. After publication succeeds, the HiCache embedding adapter releases the original CPU weight storage while preserving the parameter object and dtype metadata. Only the snapshot retains the table data during inference; initialization temporarily holds both copies. Warmup precedes CUDA graph capture. The existing prefetch stream and stream waits provide ordering. Live PLE weight reload is unsupported; restart the engine to change these weights.

`--hi-engram-config` accepts a JSON object. The `local_dir` key defaults to `/dev/shm/sglang-engram`; malformed JSON, unknown keys and invalid directory values are rejected by the Engram component before allocating or loading its embedding weights. Engram fields follow the HiCache group in `field_order.py`, including the positional constructor order.

## Accuracy Tests

**16 standalone Engram/CUDA checks passed** on this revision, including BF16/FP8 lookups, shard masking, prefetch, CUDA graph replay, and snapshot lifecycle. They verify that failed publication preserves the original weights, while successful publication releases their backing storage without changing lookup results. PR-scoped pre-commit passes. Experiment scripts remain outside the SGLang source tree.

The earlier native Qwen offload, PLE table, server-argument and documentation regression pass covered **352 passed tests, 4 hardware-dependent skips and 156 passed subtests**. This revision changes only HiCache embedding storage release and its README.

Real checkpoint: **Qwen3.8-Flash-Next-FP8 (Qwen4-Exp), TP4/EP4**. Fresh paired runs produce **10/10 identical output-token sequences**, **320 output tokens per backend**, with **maximum output-token logprob difference 0.0**. Coverage includes six text requests (English, Chinese, arithmetic and repeated prompts) plus seeded input-token requests of **1K, 4K, 16K and 64K**. Both use PLE prefetch and prefill/decode CUDA graphs.

Controlled accuracy settings: `context_length=66048`, `max_total_tokens=73728`, `max_running_requests=1`, `chunked_prefill_size=512`, `cuda_graph_bs_decode=[1]`, `mem_fraction_static=0.7`, `random_seed=42`, deterministic inference, overlap scheduling disabled, PyTorch sampling and FlashInfer autotuning disabled. Sampling: `temperature=0`, `max_new_tokens=32`, `ignore_eos=True`, output logprobs enabled. Only `enable_hi_engram` (`None` / `local`) differs. These are functional regression checks, not benchmark-dataset accuracy.

## Speed Tests and Profiling

**Baseline:** native Qwen4-Exp **pinned-host PLE with prefetch**. **HiCache:** local Mooncake Engram storage with **the same prefetch**. Both use commit `3e7ddaa3f8`, identical Engine settings, GPUs and seeded inputs; only `enable_hi_engram` differs.

Engram-related CLI flags (append to otherwise identical launch commands; the measurements use the Engine API):

```bash
# Baseline
--ple-offload-embedding --ple-offload-backend pinned

# HiCache local
--ple-offload-embedding --enable-hi-engram local \
  --hi-engram-config '{"local_dir": "/dev/shm/hicache-engram-memory-20261024"}'
```

These are post-warmup memory samples, not startup peak measurements: both copies still coexist temporarily during publication, and CUDA lookup pins the snapshot in full.

## Reproduction and limits

Codebase: SGLang main `55f23a8b59`; current memory-release implementation, paired performance and real-weight E2E checks: `3e7ddaa3f8`. Python 3.12.14, PyTorch 2.14.1/CUDA 13.0, Transformers 5.19.0, Triton 3.8.0, FlashInfer 0.7.2 and sglang-kernel 0.4.10. Four 80 GiB NVIDIA L20Z devices (CUDA reports SM90), TP4/EP4, on the same host for both backends. An unrelated service remained on GPU 6; all measurements use GPUs 0–3 and reported GPU memory excludes other devices. Mooncake wheel SHA256: `ce9f26965181e7b068fb4e17ca78425a401209343cc42928deb6c43f81878390` (implementation `e3d39595`; current #4701 only relocates CUDA sources/build wiring). Both backends receive the same libc memfd_create shim because the Conda Python build omits os.memfd_create.

See `python/sglang/srt/mem_cache/engram/README.md` for integration and launch instructions. These are local text-inference checks. Multimodal inputs, remote storage, other parallel layouts and live weight updates are not validated.
