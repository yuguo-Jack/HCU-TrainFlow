# [Feat] scheduler: Gate --prefill-decode-interval on running batch size

[Upstream PR](https://github.com/sgl-project/sglang/pull/44001) · state: closed · merged: True

## Original PR description

## Motivation

`--prefill-decode-interval N` forces N decode-only rounds after every prefill, regardless of how many requests are running. That protects decode ITL once the batch is large, but while the batch is still small it slows its growth: each waiting request waits up to N rounds to be admitted. Throughput-bound deployments (e.g. DeepSeek-V4.1-Flash with `--max-running-requests 48 --prefill-decode-interval 4`, where TTFT matters less than TPS) want eager admission until the batch is reasonably full, and the interval only after that.

## Modifications

- New flag `--prefill-decode-interval-min-bs` (default `0` = current behavior). The interval only applies while the running batch has at least this many requests.
- Checked in `Scheduler._should_defer_prefill(running_batch)`, not when the interval is armed. Below the threshold, any pending interval is cleared and prefill is admitted. So a batch that shrinks below the threshold mid-interval (requests finishing) resumes admission immediately.
- Under DP attention, arming still uses the globally synchronized `is_extend_in_batch`, and the threshold is compared against each rank's own running batch (no batch size is synced across ranks). A rank below the threshold admits prefill every round. Because that prefill re-arms the interval on every rank, a rank that is still above the threshold keeps deferring until the small rank crosses the threshold or drains its queue, or until its own batch shrinks below the threshold. This is bounded and adds no collective, so no desync is introduced; with the default `0` nothing changes. Gating on a group-level batch size (e.g. a slot in the DP sync tensor) can be a follow-up if a deployment needs it.
- Validation: the new value must be non-negative.
- Docs: added a row for the new flag to `server_arguments.mdx`, and while there, a row for `--prefill-decode-interval` itself (it was still on the `server_arguments_undocumented.txt` allowlist; removed from the list).

Related: #43844 (chunk-only interval protection) also changes this code path. The two policies compose; whichever lands second needs a trivial rebase.

- akhilg-nv · comment · 2026-10-20T20:03:06Z · [source](https://github.com/sgl-project/sglang/pull/44001#issuecomment-6300277486)

[by Claude Code]

Thanks for this. We hit a related case and want to suggest a small extension, since it touches the same check.

**The case.** When nothing is decoding, there is no decode ITL for the interval to protect, yet with the default
`--prefill-decode-interval-min-bs 0` the interval still applies. The interval counts scheduler loop iterations, not
decode rounds, and with no decode work those iterations are empty spins (`recv_requests` plus `on_idle`). So a long
prompt that arrives at an idle server waits about N empty iterations after each of its chunks.

We measured this end to end; numbers will come with the follow-up PR.

**Suggestion.** Treat "nothing is decoding" as below the threshold even at the default `min_bs = 0`, on the non-DP
path only:

```python
def _should_defer_prefill(self, running_batch: ScheduleBatch) -> bool:
    if self._prefill_decode_interval_remaining == 0:
        return False
    # With no decode to protect, waiting only idles the GPU between chunks.
    # DP keeps the synchronized cadence because peer ranks may still be decoding.
    nothing_decodes = running_batch.is_empty() or running_batch.is_prefill_only
    if running_batch.batch_size() < self.prefill_decode_interval_min_bs or (
        nothing_decodes and not self.require_mlp_sync
    ):
        self._prefill_decode_interval_remaining = 0
        return False
    self._prefill_decode_interval_remaining -= 1
    return True
```

Why it is safe:
- It only fires when there is no decode work, so no ITL can get worse.
- It leaves DP attention unchanged.
- It makes the bug fix default-on while your flag still controls the small-batch policy.

`min_bs = 1` already covers the non-DP part, but it is opt-in and also changes DP behavior.

We have three unit tests for exactly this, which pass with the change above:
- an empty running batch does not defer;
- a prefill-only running batch does not defer;
- DP still defers without local decode.

We are happy to push them to this branch or open a small follow-up after this lands, whichever you prefer.
