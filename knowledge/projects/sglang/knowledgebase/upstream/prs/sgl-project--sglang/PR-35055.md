# [Fix] [AMD] moe-router: Keep router GEMM output and correction bias in fp32

[Upstream PR](https://github.com/sgl-project/sglang/pull/35055) · state: open · merged: False

## Original PR description

## Motivation

Two dtype bugs on the ROCm/aiter MoE routing path (#34857), affecting DeepSeek-V2-family models (incl. GLM-5.2, GLM-5.3, GLM-5.3-Flash) run with `SGLANG_USE_AITER=1`:

1. `aiter_dsv3_router_gemm` requested `otype=hidden_states.dtype`, i.e. bf16 router logits. Every other branch of `MoEGate.forward` already produces fp32 — `dsv3_router_gemm(out_dtype=torch.float32)` and `linear_bf16_fp32`. The aiter branch was the only one that did not.
2. `e_score_correction_bias` was allocated bf16 for aiter + `fp8`/`compressed_tensors`/`quark` quant configs. Checkpoints store it fp32 (GLM-5.2: `mlp.gate.e_score_correction_bias F32 [256]`), so it was rounded on load and again every forward via `correction_bias.to(dtype=gating_output.dtype)` in `topk.py`.

#29783 fixed exactly this pair on the CUDA side and explicitly left the aiter branch untouched. This is the aiter half.

## Parity with CUDA

With this PR, the ROCm/aiter routing path keeps the same dtypes as CUDA at every step:

| Step | CUDA | ROCm/aiter before | ROCm/aiter with this PR |
|---|---|---|---|
| Correction bias storage | fp32 | bf16 under `fp8`/`compressed_tensors`/`quark` | fp32 |
| Router GEMM output | fp32 (`tiny_gemm_bf16(out_dtype=fp32)`, `linear_bf16_fp32`) | bf16 (`aiter_dsv3_router_gemm`) | fp32 |
| Bias seen by top-k | fp32 | cast to the logits' dtype, bf16 | fp32 (the cast is a no-op) |

GEMM compute stays bf16 on both platforms; only the output dtype changes.

## Relation to #37133

This PR was opened on Aug 16. #37133 (opened Aug 30, merged Sep 8) later fixed the same bias rounding for GLM-5.2 only: it skips the bf16 downcast when the architecture is `GlmMoeDsaForCausalLM` / `GlmMoeDsaForCausalLMNextN`, keeps every other aiter fp8 model on bf16, and adds a test pinning that.

An architecture allowlist misses the next model with the same bias shape. GLM-5.3 and GLM-5.3-Flash load as `Glm5NextForConditionalGeneration`, build the same `MoEGate`, and still get a bf16 bias on main.

Keeping the bias fp32 unconditionally, as CUDA and the HF reference already do, fixes this class of bug for any model instead of one architecture at a time. Rebased onto main, this PR supersedes #37133's architecture gate:

- `deepseek_v2.py`: the GLM exemption goes away together with the bf16 branch.
- `test_glmmoedsa_correction_bias_fp32.py`: removes `test_non_glm_still_downcasts_bf16`, which pinned non-GLM models to bf16. The GLM-5.2 tests pass unchanged.
- #37133's `topk.py` change stays. With fp32 router logits, its fp32 branch is always taken and its logits upcast is a no-op.

`is_glm_moe_dsa` is now unused outside its own tests; happy to drop it here or in a follow-up.

## Modifications

- `rocm_linear_utils.py`: `aiter_dsv3_router_gemm` requests `otype=torch.float32`. Compute stays bf16; only the output type changes.
- `deepseek_v2.py`: drop the aiter-specific bf16 branch for `correction_bias_dtype` (and #37133's GLM exemption inside it), so the bias is fp32 unconditionally — matching the checkpoint and every other branch.
- `topk.py` needs no change: with both of the above fp32, every cast of the bias to the logits' dtype on the aiter path becomes a no-op.
- Tests: add `test_deepseek_v2_moe_gate_correction_bias_dtype.py`; remove `test_non_glm_still_downcasts_bf16` (see above).

## Accuracy Tests

MI300X / gfx942, ROCm 7.2, aiter `0.1.14rc1.dev240+g7d604afe5`.

Routing sensitivity to each rounding, measured independently over **4096 tokens** at the production topology (256 experts, `n_group=8`, `topk_group=4`, `topk=8`), counting tokens whose selected expert set changes:

| Rounding removed | Tokens with a different expert set |
|---|---|
| Router-logit bf16 → fp32 (fix 1) | 124 / 4096 (**3.03%**) |
| Correction-bias bf16 → fp32 (fix 2) | 18 / 4096 (**0.44%**) |
| Both (this PR) | 128 / 4096 (**3.13%**) |

GEMM output accuracy against an exact fp32 reference, M=8 with a tuned kernel present: `otype=bf16` max abs error **0.0155**, `otype=fp32` max abs error **0.000001**.

**Scope caveat on fix 1.** The shipped aiter tuned-GEMM tables contain no gfx942 rows for this shape (gfx950 only). Untuned, `tgemm.mm` falls back to a path that rounds to bf16 internally regardless of the requested `otype` — both arms then return bitwise-identical values, so on stock gfx942 fix 1 is currently inert-but-correct. It becomes load-bearing as soon as a gfx942-tuned fp32 entry exists; I generated one locally with aiter's own tuner (`csrc/gemm_a16w16/gemm_a16w16_tune.py --with-hipblaslt`) to confirm the fp32 request is honored and produces the accuracy above. Fix 2 has no such dependency and is active today.

**Methodology, including two corrections I had to make.** The table above models each dtype change directly (`logits` vs `logits.bfloat16().float()`, same for the bias), which isolates the two fixes and is independent of which kernel aiter dispatches. Two earlier attempts were invalid and their numbers are not reported here:

- A first run compared `otype=bf16` against `otype=fp32` while only the fp32 rows were tuned — so the two arms used *different kernels*, and the measured delta conflated output dtype with kernel implementation.
- A second run used raw `randn` for activations and gate weights, producing logits of magnitude ~300. `biased_grouped_topk` applies `sigmoid`, which fully saturates there, so the logits carried no ranking information and the experiment measured only bias tie-breaking. The table uses RMS-normalized activations and a small-init gate (`logit |max| ≈ 8`, sigmoid range `[0.001, 0.999]`).

Small samples are also underpowered for a ~3% rate — 8- and 64-token runs returned 0 flips, consistent with the measured rate, which is why the table uses 4096.

Not run: an end-to-end GLM-5.2 accuracy eval. That needs 8 GPUs; this was validated on a single-GPU box.

**Mechanical verification on real hardware:** `MoEGate(...).e_score_correction_bias.dtype == torch.float32` for both `fp8` and no-quant configs; `aiter_dsv3_router_gemm(...)` returns fp32 through the real sglang import path; `aiter.biased_grouped_topk` accepts fp32 `gating_output`.

## Speed Tests and Profiling

Not applicable — compute dtype is unchanged (bf16 in, bf16 multiply); only the GEMM output type and a 256-element bias buffer change. No kernel is added or swapped on the shipped gfx942 path.
