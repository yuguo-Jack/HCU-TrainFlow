# [Feature] Add build_app/init_app_state factory for embedding the OpenAI server in external ASGI hosts

[Upstream PR](https://github.com/sgl-project/sglang/pull/31726) · state: closed · merged: False

## Original PR description

## What this fixes

1. Embedding SGLang's OpenAI compatible server inside another ASGI host currently means reaching into module internals: importing the global `app`, calling `set_global_state`, and hand setting several attributes on the app object.
2. Ray Serve LLM does exactly that today, so any change to those internals breaks it.

Fixes #31356.

## The fix

Two public functions, following the same shape vLLM uses:

```python
engine = sglang.Engine(**engine_kwargs)
app = build_app(engine.server_args)
init_app_state(engine, app.state, server_args=engine.server_args)
uvicorn.run(app, host="0.0.0.0", port=30000)
```

1. `build_app(server_args)` returns a fresh app with the same lifespan, middleware, exception handlers and routes as the module level app, with everything that depends on server args applied through the same helper `launch_server` uses. One code path, so the two cannot drift apart.
2. `init_app_state(engine, state, server_args)` binds an engine to that app. The lifespan prefers the app's own binding, so an embedded app keeps serving the engine it was given.
3. The self addressed HTTP warmup is off by default for built apps, and is opt in with `build_app(server_args, warmup=True)`.
4. Also fixes a bug in the existing lifespan, where the metrics middleware was attached to the module level app instead of the app being started.
5. `launch_server` behaves exactly as before, and `set_global_state`, `get_global_state` and the module level `app` all still work. An app that an external host configured by hand, the way Ray Serve does today, also still starts, because the lifespan falls back to the old warmup path when the new attribute is absent.

## Startup steps on the embedded path

An app from `build_app` now runs the same startup sequence as the standalone server. `_embedded_app_warmup` replaces exactly one step of it, the step that sends the warmup HTTP requests, and leaves the rest alone. So `checkpoint_engine_wait_weights_before_ready`, the elastic EP joiner skip, `delete_ckpt_after_loading` and `debug_tensor_dump_input_file` all take effect on an embedded app. Previously they were silently skipped.

The one step that is not shared is `launch_callback`, because it exists to report readiness back to `launch_server`, which is blocked waiting. An embedded app has no such caller, since the host starts the app and watches the ASGI lifespan itself.

Two things a host process should know:

1. `debug_tensor_dump_input_file` still ends the process once the dump is written, and that process is now the host's. Use that flag only in a debug run.
2. With `warmup=True` the requests go to `server_args.host` and port carrying `server_args.api_key`, so only enable it when the app really is served at that address. A failure is logged and leaves the engine not ready. It never kills the process.

## Limitations

1. The native endpoints such as `/generate` and `/health` still read one process wide engine binding, so only one engine per process can serve built apps. Binding a second one now fails loudly instead of quietly misrouting requests. Full isolation would mean moving the 82 module level endpoints onto app state, 29 of which read the process global engine binding directly, which is out of scope here.
2. `build_app` supports single tokenizer mode only. Multi tokenizer mode needs the shared memory bootstrap in `launch_server` and is rejected with a clear error.
3. The host must run the ASGI lifespan, because the serving handlers are created at startup.
4. If you turn the warmup on, it sends requests carrying `server_args.api_key` to `server_args.host` and port, so only enable it when the app really is served at that address. When it fails the engine stays in the starting state and the host has to notice that through its own health checks.
5. The built app installs the same CORS policy as the standalone server, which allows every origin with credentials. When the app is mounted inside a host application that policy applies to the mounted subtree. A host running its own CORS middleware still constrains preflighted requests. Making this configurable is left as a maintainer decision.
6. Registering the response metrics with two different sets of label names in one process still fails inside prometheus, because one metric name cannot carry two label sets. Repeated registration with the same label names is now safe, which covers everything `build_app` and `launch_server` do.
7. Verified with CPU only unit tests using a mocked engine. No GPU or end to end serving run.

## Testing

New tests in `test/registered/unit/entrypoints/test_http_server_app_factory.py`, registered for CPU CI with mocked tokenizer and template managers, so no server and no model weights are needed:

1. A built app serves every route of the module level app and dispatches requests.
2. Two built apps are independent, and multi tokenizer mode is rejected.
3. The api key middleware is honored, including when the app is mounted under a path prefix, where the health probe exemption must still apply.
4. `init_app_state` binds the app's own engine, the lifespan uses that binding even when a different engine is published globally, a second binding is rejected, and an app that was never bound fails with a clear error rather than silently using another engine.
5. The self addressed warmup does not run by default, and an app configured the old way by hand, with only the attributes that existed before this change, still starts and uses the old warmup path.
6. Metrics can be enabled on more than one app in one process, `/metrics` is served by the built app, and no stray mount is added to the module level app.

Fail then pass shown for every fix. Full run: 21 tests in the new file, 322 passing in the entrypoints directory. The one failure there, `test_ssl_cert_refresher.py::test_stop_cancels_tasks`, also fails on unmodified main on this machine. `pre-commit run --files` is clean.

Accessing `fast_api_app.state.global_state` directly can raise an `AttributeError` if the `global_state` attribute has not been initialized on the Starlette `State` object (for example, if the lifespan is executed on a custom or third-party `FastAPI` instance where `build_app` or `init_app_state` was not used). Using `getattr` is safer and more robust for accessing Starlette state attributes.

```suggestion
    global_state = getattr(fast_api_app.state, "global_state", None) or _global_state
```
