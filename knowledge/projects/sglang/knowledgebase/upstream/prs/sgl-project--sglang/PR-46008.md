# [Fix] mem-cache: Retain SWA behind the replay-trimmed prefix frontier

[Upstream PR](https://github.com/sgl-project/sglang/pull/46008) · state: open · merged: False

## Original PR description

## Motivation

SWA matching excludes `swa_reprefill_tail_tokens(req)` before page alignment,
but out-of-window eviction currently retains the window behind the untrimmed
frontier. At some alignments it frees a page needed behind the actual match
boundary. An otherwise reusable Full-KV prefix then falls back to an older SWA
checkpoint and unnecessarily re-prefills almost an entire 8K chunk.

With 256-token pages, a 128-token window/replay guard and a 32,576-token prefix,
the old frontier frees through position 32,256. The matched prefix needs the
preceding window too; retaining through 32,000 avoids that fallback. A
32,448-token prefix is the unaffected alignment control.

## Modifications

- Pass the existing replay-tail policy through the KV-storage `advance` API
  from both scheduler allocation and unified-cache checkpoints. Both the arena
  and static storage implementations forward it to the shared SWA helper.
- Retain the window behind the earlier, aligned replay boundary when prefix
  sharing is enabled. Keep the replay guard and attention kernels unchanged.
- Preserve checkpoint floors, previously freed cursors, and the no-replay and
  no-prefix-sharing policies.
- Add nine CPU-registered regressions executing the real helper, including an
  alignment sweep and the two caller policies. For the 256/128/128 configuration
  above, the extra retention is at most one page.

## Accuracy Tests

Ported to main `2ccbdab65fb1` through the KV-storage refactor. All nine
replay-retention tests and both existing eviction-interval tests pass using the
pinned serving image as the CPU dependency environment:

```sh
PYTHONPATH=python python test/registered/unit/mem_cache/test_swa_replay_retention.py
```

Earlier paired GPU serving tests used DeepSeek V4.1 Flash MXFP4, TP2, SM120,
8K chunks, and SGLang `ed0b8f433f88` plus the dual-EPYC integration recipe:

| Prefix | Original first replay: recomputed / elapsed | Fixed first replay |
|---|---|---|
| 32,576 tokens | 8,000 / 9.03-9.13 s | 320 / 2.87-2.88 s |
| 32,448 tokens | 192 / 2.28-2.29 s | 192 / 2.28-2.29 s |

Two cache-isolated trials per length passed. A frozen 269,913-token tool-history
fixture also returned the correct superseding facts fresh and on three cached
replays: 345 tokens recomputed instead of 5,977, with 3.38-second first-replay
TTFT. Those are bounded serving checks, not general agent-quality qualification.
The corresponding fix also passed a later serving qualification on SGLang
`20036b7add8c` plus recipe `6dcdf640065c`: two independent near-1M histories,
four concurrent sessions in a 3M pool, updated tool evidence, cancellation,
queueing and eviction recovery (32 reasoning-enabled fact checks, zero
retractions). That validates the integrated deployment; GPU inference has not
been rerun on this clean `2ccbdab65fb1` main port.

## Speed Tests and Profiling

On the matched deployed stack, single-request decode was 23.76 before / 23.86
tok/s after; four-request aggregate decode was 29.89 / 29.73 tok/s. Differences
are below 1%; no decode improvement is claimed. Cold prefill stayed unchanged.
The intended improvement is avoiding unnecessary first-replay recomputation.

- 05yuki · comment · 2026-11-03T03:21:15Z · [source](https://github.com/sgl-project/sglang/pull/46008#issuecomment-6594598988)

An independent reproduction of this bug, at SGLang `3edea93cbc`, on DeepSeek-V4.1-Flash-1017 MXFP4 with KTransformers. The setup was TP2 on 2× RTX 5070 Ti, page size 256, a 128-token window, and decoder SWA bounded replay on.

A 32,625-token prompt was sent, the request generated G tokens, and the bare prompt was sent again:

| | G = 1 | G = 2 to 512 |
|---|---|---|
| main at `3edea93cbc` | 32,256 cached (369 recomputed) | 16,384 cached (16,241 recomputed) |
| `SGLANG_OPT_UNIFIED_CACHE_FREE_OUT_OF_WINDOW_SLOTS=0` | 32,256 | 32,256 |
| checkpoint frontier minus the replay tail (below) | 32,256 | 32,256 |

HiCache on or off gave the same numbers. In a seeded multi-session check, four sessions of 786K, 131K, 65K and 33K tokens were answered and then replayed together. Their first replay recomputed 3,079-16,241 tokens a session before the change and 263-369 after.

The change we tested touches only the two pre-insert frees in `UnifiedRadixCache` (`checkpoint_into_tree` and `advance_unpublished_req`):

```python
comp.free_out_of_window_slots(
    req,
    len(radix_key) - 1 - self.swa_reprefill_tail_tokens(req),
    insert_params,
)
```

This PR also covers the scheduler-allocation path, which the change above does not. We have not run this PR's branch itself.
