# [AMD] Add ROCm 7.14 (gfx942 / gfx950) release

[Upstream PR](https://github.com/sgl-project/sglang/pull/35319) · state: closed · merged: False

## Original PR description

## Summary

This PR adds ROCm 7.14 image support for AMD Instinct MI300 (`gfx942`) and MI350 (`gfx950`). It uses AMD's versioned release wheels rather than a nightly channel, so the image remains rebuildable.

The new images use:

- Ubuntu 24.04 and Python 3.12
- ROCm SDK 7.14.0
- PyTorch 2.11.0, torchvision 0.26.0, and torchaudio 2.11.0
- Triton `3.7.1+git0263a6a6`
- AITER `c16d44b`

MI45x / `gfx1250` support is outside this PR and is being developed separately in #32754.

## What changed

- **Docker image:** added a shared ROCm 7.14 base plus `gfx942-rocm714` and `gfx950-rocm714` stages. The base installs the full ROCm development SDK and the device packages required by both architectures; AITER and SGLang kernels are still compiled for the selected GPU only.
- **ROCm SDK compatibility:** ROCm 7.14 installs under the Python environment instead of `/opt/rocm`. The image initializes that SDK and provides the paths and compatibility symlink expected by AITER, MORI, UCX, and the existing Docker build.
- **GPU detection fix:** the pip SDK can expose two copies of `libamd_smi`, causing torch to report zero GPUs even when HIP sees them. The image makes torch and `amdsmi` use the same library.
- **Dependencies:** keeps the ROCm PyTorch packages pinned during later installs, selects the existing PyTorch 2.11-compatible SGLang extras, and exposes the SDK's bundled NUMA/libdrm libraries while rebuilding MORI.
- **CI integration:** teaches `amd_ci_install_dependency.sh` to recognize the two new image flavors and rebuild AITER/MORI with the correct ROCm 7.14 paths.
- **Release workflow:** adds a manual workflow that builds `rocm714-mi30x` and `rocm714-mi35x` images; the nightly schedule remains disabled for now.

Existing ROCm 7.0, 7.2.0, and 7.2.4 image paths keep their existing behavior.

## Validation

- Both image variants built successfully: [image build run](https://github.com/sgl-project/sglang/actions/runs/32380153563).
- PR and nightly suites were run on both MI30x and MI35x. Compared with nearby ROCm 7.2.0 and 7.2.4 runs, we found **4 new failing test jobs**; all other failures were already present in at least one baseline. See the [run links and per-test comparison](https://github.com/sgl-project/sglang/pull/35319#issuecomment-5367000809).
- The AMD Extra suite passed 3/3. A targeted retry also confirmed that the V4-Pro-MTP resource failure reproduces on ROCm 7.2.4 and is not new to ROCm 7.14.

Additional checks: [Extra](https://github.com/sgl-project/sglang/actions/runs/32501007587) passed 3/3. In the [targeted retry](https://github.com/sgl-project/sglang/actions/runs/32515666906), V4-Pro passed, while V4-Pro-MTP reproduced the same out-of-resources failure seen on ROCm 7.2.4.

#### AITER provenance clarification

The validation above used AITER `d9e5ef7ce08ee7045d583aed768cff41aa9210fe`, not the current SGLang `main` pin. The linked [image build run](https://github.com/sgl-project/sglang/actions/runs/32380153563) checked out that commit for both `gfx942` and `gfx950` and published the `20260820` tags. The four PR/nightly runs above actually pulled the `20260821` tags, built by [run 32443714968](https://github.com/sgl-project/sglang/actions/runs/32443714968) at `3b9c66b`; that rebuild also checked out the same AITER commit on both architectures.

In all four test runs, `AITER_COMMIT_OVERRIDE` was empty. The dependency logs reported `Dockerfile expects AITER_COMMIT=d9e5ef7...` and image version `v0.1.20.dev12+gd9e5ef7ce`, then explicitly skipped an AITER rebuild. Therefore, these results characterize ROCm 7.14 with AITER `d9e5ef7`; they do not validate the current-main AITER pin `c16d44b93a528b2a4bfd6d8d3409116d465872a9`.
