# [Fix] scheduler: Stop the prefill delayer's queue trigger from ending its own delay

[Upstream PR](https://github.com/sgl-project/sglang/pull/42199) · state: open · merged: False

## Original PR description

## Motivation

The prefill delayer's queue trigger (`--prefill-delayer-queue-min-ratio`, #23189) should hold prefill until the queue reaches `running_req * ratio` or `--prefill-delayer-max-delay-ms` elapses, but on main it ends its own delay in three ways; this PR removes all three.

1. **The threshold collapses toward the queue.** Without `--prefill-max-requests` it is capped by the `max_prefill_bs` high-watermark, which delayed passes feed with the waiting-queue length (#34284). #35191 fixed this only when a request limit is set.
2. **A queue-only delay consumes the one-shot `skip_first_delayer` bypass** meant for the slot trigger's first `merge_batch`.
3. **`max_delay_passes` (#32880) also bounds queue delays**, so 30 passes end them long before the 5000 ms default.

## Modifications

- The threshold is `running_req * ratio`, capped only by a configured `--prefill-max-requests`.
- `skip_first_delayer` is consumed only when the slot condition holds.
- Queue-triggered delays are bounded by `max_delay_ms` alone (TP0 decides it since #42625); slot-only delays keep `max_delay_passes`.
- Help text and docs updated. Except for keeping the static cap, this is #34806 by @xdtbynd (closed unreviewed), credited as co-author.
- With the queue trigger off, `queue_condition` is always false and behavior matches main.

## Accuracy Tests

Not applicable: only admission timing changes.

`test_prefill_delayer_high_watermark.py` adds five CPU cases: one per defect, plus the `prefill_max_requests` cap and the slot-only pass bound. On main exactly the three defect cases fail; reverting one fix fails only its case. With `test_prefill_delayer_gather.py` and `test_server_args_docs_coverage.py`: 15 passed, 8 subtests passed.

## Speed Tests and Profiling

Prefill fragmentation (`Prefill batch` log lines), MI355X, TP=1, dummy weights, `main@ef867fa40d` vs. this PR; ratio 0.13, max delay 870 ms, `bench_serving` random 211/389, 613 prompts, concurrency 173; median of 3.

| model | prefill batches main → this PR |
|---|---|
| gpt-oss-120b / Llama-3.1-8B-Instruct | 53.5 → 29 / 55 → 29 (−46 % / −47 %) |
| DeepSeek-V4-Flash, GLM-5.3 (reduced layers), Qwen3.6-35B-A3B | −50 % each |
| queue trigger off (Llama) | 271 → 270 |
| `--prefill-max-requests 37` (Llama / gpt-oss) | −9 % / −12 % (defect 3) |

**Trade-off:** delays now last as long as configured, so median TTFT rises 39–66 %, TTFT p99 sits near `max_delay_ms` on four of five models, and median TPOT improves 2–7 %.

Open questions: should the 5000 ms default come down now that it binds, and should an explicit `--prefill-delayer-max-delay-passes` still bound queue delays? Affected: GLM-5.2 B200 AgentX launches, the Ascend Qwen3.6-27B recipe (300 passes), and the NPU Qwen3.6-27B GPQA test, where a queue delay can now last 30 s.

cc @paulzhang-tm: this drops the `max_prefill_bs` fallback kept in #35191.
