# [Fix]Account for DCP replication when sizing the EAGLE draft KV pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/39799) · state: open · merged: False

## Original PR description

## Motivation

Under DCP the target KV pool is sharded across ranks, but the draft pool is **replicated** — it indexes the allocator's widened virtual location space raw. `KVCacheConfigurator` says so directly:

```python
@property
def loc_space_scale(self) -> int:
    dcp_size = get_parallel().attn_dcp_size
    return dcp_size if (self.is_draft_worker and dcp_size > 1) else 1
```

```python
# Draft pools are replicated, not DCP-sharded, yet consume the shared
# allocator's virtual locs in [0, max_total * dcp_size) untranslated.
loc_scale = self.loc_space_scale
max_total_num_tokens *= loc_scale
```

Both pool configurators price the EAGLE/STANDALONE draft term at **one** replica while `dcp_size` are allocated:

- `DefaultPoolConfigurator._compute_cell_size`: `draft_num_layers = int(eagle_draft_num_layers)`
- `HybridSWAPoolConfigurator.__init__`: `draft_layers = int(kvc.spec_aux_config.eagle_draft_num_layers)`

The DFLASH term in each of those same two places already scales — `int(draft_num_layers) * get_parallel().attn_dcp_size` in the first, and `_dflash_draft_cell_size` (which multiplies by `attn_dcp_size` internally) in the second. `_dflash_draft_cell_size` even carries the matching docstring: *"Under DCP, the target pool is sharded while the draft pool spans the allocator's widened virtual location space, so the draft term is replicated across DCP ranks."* Only the EAGLE branches were left unscaled.

So `max_total_num_tokens` comes out too large and the pool overruns the memory it was sized against, by a factor of `(L + d·dcp) / (L + d)` for `L` target layers and `d` draft layers. At 32 target layers and 1 draft layer that is +9.1% at `dcp_size=4` and +21.2% at `dcp_size=8`.

## Modifications

**`DefaultPoolConfigurator`** — scale where `draft_num_layers` is derived, so both the DSA and non-DSA branches below inherit it:

```python
draft_num_layers = int(eagle_draft_num_layers) * get_parallel().attn_dcp_size
```

**`HybridSWAPoolConfigurator`** — scale the three derived per-geometry counts instead of `draft_layers` itself, because `draft_layers` indexes real draft layer ids (`for layer_id in range(draft_layers)` against `mtp_local_layer_ids`) and bounds the SWA layer clamp; multiplying it there would corrupt both:

```python
dcp_size = get_parallel().attn_dcp_size
self._draft_full_layers_num *= dcp_size
self._draft_swa_layers_num *= dcp_size
self._draft_swa_full_layers_num *= dcp_size
```

At `dcp_size == 1` both are `* 1` — existing behaviour and existing tests are untouched, and the measurements below confirm the sizing is identical there.

### Scope note on the DSA indexer

Moving the multiplier up to the shared `draft_num_layers` assignment means the DSA indexer term (`_compute_dsa_indexer_cell_size(..., num_layers=draft_num_layers, allocate_all_layers=True)`) now also scales with `dcp_size`. I believe that is correct — `_derive_pool_sizes` scales the draft worker's `max_total_num_tokens` regardless of whether the model is DSA, and the draft worker has no equivalent of the explicit c4/c128/state zeroing that would exclude an indexer pool. But I did not trace the indexer pool construction to the end, so this is the one part worth a maintainer's eye. If the DSA indexer is sized differently, the multiplier should move down into the non-DSA `else` branch instead.

## Accuracy Tests

`test/registered/unit/model_executor/test_pool_configurator.py`: **45 passed, 9 subtests passed.**

Two tests are added, one per configurator. Both assert the budget holds once the replicas are counted; the hybrid one covers a draft layer of each geometry so the full and the SWA draft terms are both exercised, and runs at `dcp_size` 1 and 4 so the unscaled path stays pinned.

Reverting both source fixes while keeping the tests shows they have power rather than merely running the code:

```
AssertionError: 10874880 not less than or equal to 10000000      <- DefaultPoolConfigurator, +8.7%
AssertionError: 19995648 not less than or equal to 10000000      <- HybridSWAPoolConfigurator, +100%
2 failed, 44 passed, 8 subtests passed
```

Exactly the two new tests fail and every pre-existing test passes, so nothing in the suite covered this before. The `dcp_size=1` subtest passes in both builds. (The hybrid figure is inflated by the tiny test model — 4 target layers against 2 draft layers — and is not a real-world severity estimate.)

## Pool sizing measurements

`Llama-3.1-8B-Instruct` (32 layers) with the EAGLE3 draft (1 layer), `sglang.bench_one_batch`, MI355X. `max_total_num_tokens` and the target KV allocation reported at startup:

| tp | dcp | before (tokens) | after (tokens) | delta | before K size | after K size |
|---|---|---|---|---|---|---|
| 4 | 1 | 6,842,949 | 6,842,949 | 0.0% | 104.42 GB | 104.42 GB |
| 4 | 4 | 1,684,034 | 1,543,698 | −8.3% | 102.79 GB | 94.22 GB |
| 8 | 8 | 1,679,771 | 1,385,811 | −17.5% | 102.53 GB | 84.58 GB |

The capacity correction matches the model exactly, to the token: at `dcp=4` the budget priced `32 + 1 = 33` layer-equivalents against `32 + 4 = 36` allocated, and `1,684,034 × 33/36 = 1,543,698`. At `dcp=8` it priced 33 against 40, and `1,679,771 × 33/40 = 1,385,811`. `dcp=1` is unchanged.

The reduction is the cost of the correction, not a regression: the previous capacity was one the allocation could not actually honour.

No end-to-end throughput or accuracy numbers. EAGLE + DCP does not run on the container I have: the aiter backend raises `RuntimeError: view size is not compatible with input tensor's size and stride` from `memory_pool.py::_set_kv_buffer_impl`, and the Triton backend raises `NotImplementedError: DCP Triton extend does not support custom masks`. Both reproduce on unpatched `main`, so neither is caused by this change, but they did stop me from measuring past pool construction.
