# [Feat] scheduler: log host-device syncs by stage and call site

[Upstream PR](https://github.com/sgl-project/sglang/pull/48270) · state: open · merged: False

## Original PR description


## Motivation

When a serving engine is host-bound, one stray host-device sync in the scheduler path (an `.item()`, a `.tolist()` of a device tensor, a pageable `torch.tensor(..., device="cuda")`) makes the host wait for the GPU queue to drain, so it can no longer launch ahead. The scheduler already exports wall time per stage (`sglang:scheduler_stage_seconds_total`, #37636, #42025), but nothing says **where** the host blocks or **how often per step**. torch's sync debug mode can report every sync, but its warnings are deduplicated per location and carry no step context, so they cannot answer "how many syncs does one decode step or one extend cost, and from which call sites?"

This PR adds an opt-in census: with `SGLANG_LOG_SCHEDULER_HOST_SYNCS_TARGET` set, the scheduler counts every sync torch reports under the scheduler stage it ran in, the forward mode of the batch being launched or processed, and its Python call site. It writes one JSON record per interval, together with the number of launched batches per forward mode. Syncs per decode step or per extend then follow by division.

## Modifications

- `python/sglang/srt/utils/scheduler_host_sync_logger.py` (new): `SchedulerHostSyncLogger`. On the first launched batch it calls `torch.cuda.set_sync_debug_mode("warn")`, adds an `"always"` filter for the sync warning, and installs a `warnings.showwarning` hook that counts each sync under `(stage, forward_mode, call_site)`. The call site is the three innermost frames outside torch and `warnings`. Every `SGLANG_LOG_SCHEDULER_HOST_SYNCS_INTERVAL` seconds it writes a `scheduler.host_syncs` record through `log_json`, using the same targets as `SGLANG_LOG_SCHEDULER_STATUS_TARGET` (`stdout` or a directory with one file per host and rank).
- `observability/scheduler_stage_metrics.py`: a read-only `current_stage` property on the existing recorder. Stages come from that recorder, so the logger needs `--enable-metrics` and raises a clear error otherwise, as the status logger does.
- `managers/scheduler_components/metrics_reporter.py`: creates the logger next to the scheduler status logger.
- `managers/scheduler.py`: two hooks, at `_on_step_launch` (inside `run_batch`) and at the top of `process_batch_result`. When the variable is unset each costs one attribute check per batch.
- `environ.py` + `docs/docs/references/environment_variables.mdx`: `SGLANG_LOG_SCHEDULER_HOST_SYNCS_TARGET` (default `""`, off) and `SGLANG_LOG_SCHEDULER_HOST_SYNCS_INTERVAL` (default `60.0`), in the Logging section.
- Tests: `test/registered/unit/observability/test_scheduler_host_sync_logger.py` (new, `1-gpu-small`). It covers enable/disable, attribution by stage, mode and call site, window reset, pass-through of other warnings, the warning when the hook is replaced, one real `.item()` on CUDA, and that the scheduler's `_on_step_launch` and `process_batch_result` call the logger's hooks once per step. Two scheduler test doubles gain the new attribute.

Limits: only syncs that torch's sync debug mode reports are counted. Explicit `torch.cuda.synchronize()` and event waits such as the result `copy_done` are not counted. The mode is process-wide, so syncs from helper threads are counted too, under the scheduler's current stage; the counter is not locked, so a sync on a helper thread that races the scheduler thread's count can be lost. The sync debug mode, the warning filter and the `showwarning` hook are process-global and stay installed for the life of the process. If another component later replaces `warnings.showwarning`, the logger logs one warning, because syncs are no longer counted from then on.

Example record (abridged):

```json
{"event": "scheduler.host_syncs", "rank": 0, "window_s": 10.09, "launched_batches": {"extend": 15},
 "total_syncs": 188, "syncs": [{"stage": "run_batch", "forward_mode": "extend",
   "call_site": "srt/layers/attention/qwen_sparse_attn_backend.py:673 _metadata_from_forward_batch <- ...", "count": 30}, ...]}
```

## Speed Tests and Profiling

Off by default. When off, the only cost is one attribute check per launched batch and one per processed batch. When on, it is a debugging mode: each reported sync walks a few Python frames.

What it shows on upstream main (`8d4e1ce4c7`), serving Qwen3.8-Flash-Next NVFP4 (RTX: `RadixArk/Qwen3.8-Flash-Next-NVFP4`; GB300: `nvidia/Qwen3.8-Flash-Next-NVFP4`) with NEXTN MTP (3 steps, top-k 1, 4 draft tokens) at TP 1:

| GPU | Decode steps | Host syncs per decode step | Syncs per extend (no prefix) | Syncs per extend (prefix-cache hit) |
|---|---|---|---|---|
| RTX PRO 6000 Blackwell Max-Q, `--quantization modelopt_fp4 --ple-offload-embedding --mem-fraction-static 0.93 --chunked-prefill-size 4096 --cuda-graph-max-bs-prefill 4096` | 11,411 | 0 | 11.35 | 26.4 |
| GB300, defaults | 1,691 | 0 | 11.7 | 32.2 |

All counted syncs sit in `run_batch` for extend batches. The top call sites are an unsized `repeat_interleave` in the QSA extend metadata (4 per extend), per-layer QSA length uploads on prefix extends, and FLA chunk-index readbacks at the first GDN layer (3 per extend). Workloads: `sglang.benchmark.serving` random-ids 256/1024 at concurrency 16 (decode), random-ids 2048/1 at concurrency 4 (extend), and generated-shared-prefix 8×8 with a 4096-token system prompt over 2 turns (prefix).
