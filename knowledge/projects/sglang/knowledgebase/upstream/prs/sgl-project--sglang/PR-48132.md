# [Perf] qsa: Pass output_size to repeat_interleave in the graph speculative layout

[Upstream PR](https://github.com/sgl-project/sglang/pull/48132) · state: open · merged: False

## Original PR description

## Motivation

`QwenSparseAttnBackend._graph_speculative_layout` builds the per-row metadata for
every speculative graph replay (target-verify and draft-extend), so it runs on the
decode critical path. It expands `req_pool_indices` into one entry per row:

```python
repeats = extend_lengths.to(device=req_pool_indices.device, dtype=torch.long)
row_req_pool_indices = torch.repeat_interleave(req_pool_indices[:bs], repeats)
```

`repeats` is a device tensor, so without `output_size` the op has to know
`sum(repeats)` on the host to allocate the result: it reads the sum back from the
device, which is a host sync. The sum is already on the host a few lines above as
`actual_rows = row_lengths.numel()`, because `row_lengths` is assembled as one run
per `extend_lengths` entry.

Same pattern as #45275, which added `output_size=` to the `repeat_interleave` in
`deepseek_v4_backend.py` for the same reason.

## Modifications

- `python/sglang/srt/layers/attention/qwen_sparse_attn_backend.py`: pass
  `output_size=actual_rows` to `torch.repeat_interleave`, with a comment stating
  why that value is the sum.
- New `test/registered/unit/layers/attention/test_qsa_graph_speculative_layout.py`
  (registered CPU unit test, no server, no weights). It pins the identity the
  argument depends on — one row per token slot, one run per extend length, in
  row-major order — over uniform extends, ragged extends, zero-length extends,
  `extend > seq_len` (the `clamp_max` path), padded rows, tail padding up to the
  captured capacity, and the capacity-overflow `ValueError`.

## Accuracy Tests

The change is behaviour-preserving; `output_size` only pre-declares the size that
the op would otherwise compute by reading the device.

- The new unit test passes unchanged against both the pre-change and post-change
  source (8/8 both ways), i.e. it asserts outputs that the patch does not alter.
- Separately, an 84-case grid (bs 1/2/4/8/16/24/32 x target-verify and
  draft-extend x uniform/ragged/zero extends x `num_padding` 0/1/bs x spare
  capacity) compared the three returned tensors with and without `output_size`:
  identical shape, dtype and values in all cases.

## Speed Tests and Profiling

Isolated measurement of just this call. Ascend 910 (`torch 2.10.0`,
`torch_npu 2.10.0`), `repeats` on device, median host wall time per call over 40
iterations:

| batch | queue state | without `output_size` | with `output_size` |
| ----: | ----------- | --------------------: | -----------------: |
| 1 | idle | 75.8 us | 19.1 us |
| 32 | idle | 79.2 us | 19.3 us |
| 1 | deep (40 x 4096^3 matmuls in flight) | 65,099 us | 37.0 us |
| 32 | deep | 65,220 us | 42.0 us |

The deep-queue numbers are the queued device work being drained by the sync, not
time saved per step; they are there to show that the call is a sync point rather
than to claim 65 ms. On an idle queue the call itself is ~4x cheaper (-60 us).

End-to-end, this change on its own is inside run-to-run noise, which is what one
removed sync per step should look like: on the same machine with a Qwen3-Next-style
hybrid model (TP2, `--speculative-algorithm NEXTN --speculative-num-steps 1
--speculative-num-draft-tokens 2`, full decode graphs), decode ITL p50 moved by
-0.44 / -0.14 / +0.03 / -0.35 / -0.13 ms at batch 1 / 4 / 8 / 16 / 32, against a
same-config noise floor of 0.37 ms median and 0.91 ms max measured over 8 server
launches. I did not measure on CUDA; the mechanism (a device-side `repeats`
forcing a host read of its sum) is not platform specific.
