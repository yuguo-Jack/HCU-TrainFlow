# [AMD] Add opt-in radix-select top-p pivot to the ROCm Triton renorm

[Upstream PR](https://github.com/sgl-project/sglang/pull/41534) · state: closed · merged: False

## Original PR description

## Motivation

On ROCm, `top_p_renorm_probs` uses the Triton renorm in `renorm_triton.py`: `torch.sort` +
`torch.cumsum` + `searchsorted` find the pivot, then Triton kernels mask, reduce and normalize with
FlashInfer's threshold semantics (ties at the pivot kept). EAGLE rejection-sampling verify calls it
every step with `bs * (k + 1)` rows. At a 154880 vocabulary on MI355X the pivot search takes most of
the ~0.7 ms per verify.

When this path runs:

- ROCm with EAGLE / MTP speculative decoding. On HIP, `--speculative-use-rejection-sampling` is turned
  on by default (otherwise verify ignores temperature and top_p), except when
  `SGLANG_SIMULATE_ACC_LEN` is set.
- The request samples: temperature > 0 and top_p < 1. GLM-5.2's `generation_config.json` defaults to
  temperature 1.0 / top_p 0.95, so chat and agentic clients that do not set sampling parameters take
  this path.
- Requests with temperature 0 do not run top-p in verify, so `bench_serving` with its default
  settings does not show any difference.

## Modifications

- `topp_radix_triton.py`: a radix select that returns the same pivot,
  `pivot = min{v in row : sum(x <= v) >= 1 - p}`. Probabilities are non-negative, so their fp32 bit
  patterns order like the values. The pivot is found 4 bits per pass from per-block partial bin masses
  (no fp32 atomics), with each pass's digit selection fused into the next: 9 launches for the pivot,
  about 13 for the whole renorm, many blocks per row, nothing vocabulary-sized materialized. When
  `1 - p <= 0` it returns 0.0, which keeps every entry, the same kept set as the sort path.
- `top_p_renorm_probs_triton` takes the pivot from it when `SGLANG_TOPP_RADIX=1`; the masking and
  normalization kernels are unchanged.
- `SGLANG_TOPP_RADIX` in `environ.py`, default off. With it unset nothing changes.
- Tests in `test_renorm.py`.

## Accuracy Tests

- The tests check the pivot against its definition in fp64 (1e-6 tolerance) on random, softmax,
  one-hot, all-equal, sparse-with-ties and tiny (1e-30) rows, top_p from 1e-6 to 1.0, and run
  `top_p_renorm_probs_triton` with `SGLANG_TOPP_RADIX=1`.
- On near-uniform rows the fp32 cdf can reach `1 - p` within rounding, so different fp32 summation
  orders may pick adjacent values; the fp64 definition check does not depend on summation order.
- Real verify-time inputs (GLM-5.2, GSM8K sampled, 300 calls, 3498 rows with top_p < 1): the kept set
  matches an fp64 reference on every row for both the sort path and radix, and the same uniform draw
  picks the same token on every row.
- GSM8K, 1319 questions, on `amd/GLM-5.2-MXFP4` (MI355X), TP4, EAGLE 3/1/4, `sgl-eval` 0.1.2 with
  thinking on and `--max-tokens 16384`, three runs per arm, sampled at temperature 1.0 / top_p 0.95:

  | `SGLANG_TOPP_RADIX` | score (3 runs) | mean | truncated_rate |
  |---|---:|---:|---:|
  | 0 | 0.9712 / 0.9674 / 0.9712 | 0.9699 | 0.0045-0.0053 |
  | 1 | 0.9644 / 0.9727 / 0.9682 | 0.9684 | 0.0076 |

  The difference between the means (0.0015) is smaller than the spread across runs within one
  setting (up to 0.0083).

TPUT delta is how much higher radix is; TPOT delta and ITL delta are how much lower radix is. ITL is the median.

- Accept length is the same in both settings (geomean ratio 0.997-1.001).
- TPUT and TPOT move with the accept length of each run, so they are noisy: between the two runs of
  the same setting TPUT differs by up to 6% and TPOT by up to 9%. At 70000 -> 300 TPOT is dominated
  by the prefill of other requests and differs by up to 8.6% between the two sort runs.
- Median ITL follows the per-round time and is stable: the two runs of the same setting are within
  1%. It is lower with radix in every cell (2.1-4.1%).
- The 8192 -> 1024 conc 4 profile with `SGLANG_TOPP_RADIX=1` shows `top_p_pivots_radix` on every
  verify step and no sort kernel.
