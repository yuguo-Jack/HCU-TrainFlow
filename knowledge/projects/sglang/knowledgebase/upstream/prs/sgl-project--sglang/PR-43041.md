# fix: use dp_size instead of attn_dp_size for msprobe rank id

[Upstream PR](https://github.com/sgl-project/sglang/pull/43041) · state: closed · merged: True

## Original PR description

The msprobe debugger derives its rank id from attn_dp_size (the attention data-parallel width), which stays 1 when data parallelism is configured via --dp-size without attention DP. As a result every DP replica falls back to rank id None and dumps into the same rank directory, so only rank0 data is collected. Use dp_size (the number of data-parallel replicas) instead so each replica gets a distinct rank id.

## Motivation

When launching SGLang with data-parallel replicas (`--dp-size=2`) without attention data parallelism, the msprobe precision dump only collected data from rank 0. This PR fixes the rank-id selection so every DP replica dumps into a distinct rank directory.

In `ModelRunner.forward()`, the msprobe rank id was derived from `attn_dp_size`:

```python
rank_id = self.gpu_id if get_parallel().attn_dp_size > 1 else None
```

`attn_dp_size` is the *attention* data-parallel width (the number of DP attention groups inside a TP group, configured via `--attn-dp-size` / the deprecated `--enable-dp-attention`). It is 1 for plain data-parallel replicas (`--dp-size=2`). As a result `rank_id` was `None`, so msprobe fell back to `torch.distributed.get_rank()`, which is 0 in every replica (each replica is a separate single-rank process). All replicas therefore wrote into the same `rank0/` directory, and only rank 0's data survived.

## Modifications

Use `dp_size` (the number of data-parallel replicas) instead of `attn_dp_size`:

```python
rank_id = self.gpu_id if get_parallel().dp_size > 1 else None
```

Each DP replica runs on a distinct `gpu_id`, so this produces a unique rank id per replica.

## Verification

```bash
python3 -m sglang.launch_server --model-path <model> --dp-size=2 --msprobe-dump-config ./config.json
```

- Before: dump output contains only `step*/rank0/`.
- After: dump output contains `step*/rank0/` and `step*/rank1/`.

- is-not · comment · 2026-10-09T06:36:09Z · [source](https://github.com/sgl-project/sglang/pull/43041#issuecomment-6075742246)

The CI failures on this PR are unrelated to the change here. The diff is a single line inside the msprobe path, and that path is never exercised by any of the failing jobs.

**Why the change can't affect these jobs**

The only edit is in `ModelRunner.forward()`:

```python
if self.msprobe_debugger is not None:
    rank_id = self.gpu_id if get_parallel().dp_size > 1 else None   # <- changed line
    self.msprobe_debugger.start(model=self.model, rank_id=rank_id)
```

`self.msprobe_debugger` is `None` unless `--msprobe-dump-config` is passed, because `create_msprobe_debugger()` returns `None` when `msprobe_dump_config is None`:

```python
def create_msprobe_debugger() -> Optional[Any]:
    if get_observability().msprobe_dump_config is None:
        return None
    ...
```

None of the failing jobs pass `--msprobe-dump-config`, so `self.msprobe_debugger is None` and the modified line is never executed.

**Breakdown of the failures**

The real test failures are all in unrelated subsystems:

- `base-b-test-16-npu-a3` — NPU prefill/decode disaggregation (`test_npu_pd_disaggregation.py`), exit code 5, no traceback (timeout/hang).
- `multimodal-gen-test-4-npu-a3` — NPU multimodal (`test_glm_image_distributed.py`): `Exception: retry() exceed maximum number of retries.`
- NPU HiCache (`test_npu_hicache_mha.py`): `RuntimeError: Boolean value of Tensor with more than one value is ambiguous` in the host-pool construction.
- NPU DeepEP MoE (`test_npu_expert_distribution_recorder_mode.py`): `RuntimeError: aclnnDispatchLayout or aclnnDispatchLayoutGetWorkspaceSize not in libopapi.so` (missing Ascend operator).
- `base-a-test-cpu` — CPU base test, exit code 255.

The remaining jobs are not test failures:

- `pr-test-finish` / `pr-test-amd-extra-finish` / `pr-test-extra-finish` — aggregators ("Check all dependent job statuses") that fail only because a dependency failed.
- `call-gate / pr-gate` — "Require run-ci-extra label (optional)", a label gate rather than a test.
- `wait-for-base-a` — waiting gate.

These look like pre-existing NPU/environment issues (missing opapi symbol, HiCache pool bug, disaggregation/multimodal flakiness). Happy to rerun the affected jobs, but I don't believe any of them are caused by this PR.
