# [Fix] gRPC: Fix Generate capping at 128 tokens when max_new_tokens is unset

[Upstream PR](https://github.com/sgl-project/sglang/pull/44257) · state: closed · merged: False

## Original PR description

## Background

On the native gRPC server (`--grpc-port`), a `Generate` request whose `sampling_params.max_new_tokens` is unset stops at 128 tokens. HTTP clients can ask for unbounded output with `"max_new_tokens": null`, but proto3 has no null value, so gRPC clients cannot express this.

## Problem

In `rust/sglang-grpc/src/utils/request_utils.rs`, `sampling_params_to_map` skipped unset fields. When `max_new_tokens` was omitted, the Python `SamplingParams` constructor received a dict without the key and fell back to its default of 128 tokens — silently capping generation.

This affected both `GenerateRequest` (tokenized) and `TextGenerateRequest` (text) paths, since both route through the same helper.

## Solution

Always emit `max_new_tokens` in the sampling_params map. When the caller omits it, send explicit `null` (`serde_json::Value::Null`) so the Python side deserializes it as `None` (unbounded) instead of applying the default 128.

All other sampling parameters keep their existing "omit when unset" behavior; only `max_new_tokens` has the semantic distinction between "explicitly unset → unbounded" vs "absent → use default".

## Testing

Added two new unit tests in `request_utils.rs`:
- `sampling_params_max_new_tokens_omitted_becomes_null` — verifies omitted field produces null
- `sampling_params_max_new_tokens_passthrough_when_set` — verifies explicit values still pass through

All 18 existing + new tests pass (`cargo test` in sglang-grpc).

Fixes #44121.
