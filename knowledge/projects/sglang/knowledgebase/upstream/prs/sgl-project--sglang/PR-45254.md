# [Feat] kernels: Beam model support

[Upstream PR](https://github.com/sgl-project/sglang/pull/45254) · state: closed · merged: True

## Original PR description

## Motivation

Split #44747 into reviewable parts. This is the kernels part, position 3 of 7 in the merge order below.

## Modifications

- **Beam fused ops**, listed by class method as in Muse Spark's kernels part:
  - `elementwise.beam_attention_gate`: the per-head gate, with Beam's activation-dtype bias and sigmoid rounding.
  - `layernorm.beam_sandwich_residual_rmsnorm`: the post-norm, depth-scaled residual and next RMSNorm in one launch.
- **`communication.beam_all_reduce_norm`**: Beam's BF16 TP all-reduce fused with that norm and residual, on CustomAllReduceV2's push plane. Each row runs on one CTA, or on a 5-CTA cluster at TP8 for up to 16 rows. It needs a new `CustomAllReduceV2.supports_push` capacity check.
- **FP32 router gates:**
  - FP32 weights in main's `tiny_gemm` (N variant) and `router_gemv` (CUDA, up to 8 rows);
  - `gemm.router_gemm_bf16x3_cublas` for larger batches, with the weight split per call by `quantization.split_fp32_to_bf16x3`.

Main's existing callers are unchanged:
- BF16 tiny GEMM builds the same kernel with the same split as on main (its JIT build key gains the weight type, so it recompiles once on first use);
- the gfx950 BF16 router GEMV path is unchanged.

`gemm.router_gemv` is registered for Triton CUDA/HIP; its existing predicate retains CUDA FP32 and gfx950 BF16 gating. `split_fp32_to_bf16x3` lives in `ops.quantization.bf16x3_split`, which #45361 now imports directly. The cuBLAS wrapper keeps its internal import.

Committed coverage adds 18 representative numerical cases, reusing the existing tiny GEMM and fused-op parity suites plus a focused CUDA router test. The collective test covers both native unicast and multicast, changing-input graph replay, interleaved regular all-reduce, and both TP8 launch shapes. These checks complement the model E2E test from #45257.

The optional SM103 single-token BF16 MoE GEMV and shared SiLU helper moved to draft #46401, with their own correctness test and performance benchmark. They are outside Day-0 kernel support; performance measurements for that follow-up remain pending.

This part changes 21 files (+1,364 / -34).

## Validation

The following focused results belong to the tested review changes preserved in `851658f9b8`. The branch subsequently merged main at `d360915f64`; verification has not been rerun after that merge.

On GB300/SM103, with torch 2.14.1+cu130 and Triton 3.8.0:

- Numerical tests: **196 tiny GEMM, 5 router and 13 fused-op parity cases passed**. The added cases check FP32 router results against FP64, exact gate rounding, BF16 norm output within one ULP, and fixed FP16 cancellation bounds. FP16 has no universal one-ULP guarantee.
- The registered collective test passed at TP2, TP4 and cross-node TP8 over MNNVL, in native unicast and multicast modes. It covers rows 1/8/16/32/64/128, top-k 1/8, optional next norm, changing payloads during graph replay, and interleaved regular all-reduce. TP8 covers one-CTA and five-CTA launches. Native pointer inspection confirmed the selected modes.
- The existing 42-tensor-per-rank probes found zero byte differences between unicast and multicast, and between multicast and the saved original baseline. Those probes cover rows through 64.
- Beam-kernel memcheck passed at TP2/TP4 through 64 rows; TP8 racecheck and synccheck passed the full registered matrix in both modes. These runs used `--report-api-errors no` after a setup-only control reproduced 41 `cuGetProcAddress_v2` API errors per rank without calling either all-reduce. Device-memory/race/sync checks remained enabled. The setup/API issue remains unresolved; this is not clean CUDA API validation. No TP8 or row-128 memcheck claim.
- Namespace tests passed 101 cases. Existing MoE suites passed. The generic custom-all-reduce TP4 suite retained **309 passes and one failure**, `test_custom_all_reduce_eager_plan_follows_config`, reproduced on the unchanged baseline.
- No physically multicast-incapable hardware, H200, ROCm or SM120 rerun was added for these review changes.

An earlier NVFP4 integration with the model/parser stack passed the original Beam verifier at `dfa85fe771`: **133/133 required chat cases and 5/5 optional raw-completion cases**. Temperature 0 applied only to recall; `no_stop_trim` applied only to raw completions. That integration included a separate parser compatibility fix and predates the final unicast restoration; it is not a fresh model run on this head or a matched reference comparison.

On 8×H200 (SM90), with the same torch and Triton and FlashInfer 0.7.2:

- **Main's tests pass:** tiny GEMM, fused MoE (SwiGLU epilogue, padding, TMA cache, `test_fused_moe`), and the kernel registry and fused-op CPU tests.
- **Numerical checks:**
  - The attention gate is bitwise equal to eager over every finite FP16 and BF16 gate value.
  - The all-reduce boundary matches an all-gather reference at TP2, TP4 and TP8 within BF16 tolerance, and its outputs are bitwise equal between the one-CTA and cluster launches.
  - compute-sanitizer racecheck and synccheck are clean on the all-reduce boundary at TP8, covering both launch shapes.
- **FP32 router:** the boundary norm followed by the FP32 tiny GEMM is 0.02–1.26 µs per layer faster than with this PR's earlier PDL ordering and split selection, at 1–16 tokens, with bitwise-identical outputs.
- **End to end:** with the same parts as above, at FP8 TP8 (`fa3`, DFlash), with the public `reflection/Beam-1.0-501B-A23B-FP8` checkpoint:
  - GSM8K 96.21% (sgl-eval, 1,319 questions, temperature 0, 0 errors);
  - the Beam Verifier required suites pass 133/133, with the recall cases at temperature 0;
  - chat reasoning, streaming, chat tool calls, Responses text and function calls, and `/tokenize` pass. The Responses shell round trip fails with the current public chat template; the fix goes in #45257.

**TP8 cluster launch.** At TP8 with up to 16 rows, each row runs as a 5-CTA cluster. Per call, compared with one CTA per row:
- on 8×H200, it is 4–10% faster with top-k 1 and 8–16% faster with top-k 8 (6.76 vs 5.68 µs at one row);
- on 8×GB300 across two nodes (MNNVL), it is 3–11% faster with top-k 8. With top-k 1 it ranges from 2.2% faster to 0.9% slower, inside run-to-run noise (median of five sweeps).

One CTA per row stays at TP2 and TP4, where it is as fast or faster on GB300 and H200. It also stays for TP8 batches above 16 rows. At 32 rows with top-k 8, a cluster would be 1.4% faster on H200 but is 3.4% slower on GB300.

Not measured here:
- end-to-end serving and compute-sanitizer at TP8 on Blackwell (TP8 there covers the all-reduce boundary only);
- ROCm (the gfx950 BF16 path is unchanged and was checked statically);
- the unicast publish path.

## Merge order

Each part is based on the one before it, so its diff shows only its own changes. Merge bottom-up; after each part merges, the next part is retargeted to `main` and `main` is merged into it. #44747 stays open, unchanged, as the full reference. Merge in this order:

1. #45253: Beam CUDA Docker image (merged)
2. #45291: OpenAI SDK 2.8.0, needed by the Responses shell tools in #45257 (merged)
3. #45254: Kernels

6. #45290: `nvidia-cuda-tileiras`, needed by #45361
7. #45361: cuTile BF16x3 router GEMM (optional: without it Beam uses the cuBLAS router)

#45292 (Dynamo and `grpcio-tools` pins for the Beam image) is not in the merge order for now.
