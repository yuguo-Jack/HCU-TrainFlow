# [Feat] rust-server: Fan control requests out to every DP rank

## Motivation

Each embedded Rust server owns exactly one scheduler, the one for its own
attention-DP leader rank. Control operations that Python's `TokenizerManager`
answers for every DP rank (`FanOutCommunicator` over `num_dp_ranks`) therefore
only reached one rank through the Rust frontend: `/flush_cache`,
`/weights_checker`, the HiCache attach/detach/clear routes, and `/server_info`
reported a single scheduler and called it the deployment.

## What this does

**Fan-out utility** (`api_server/core/fanout.rs`). `fan_out` delivers one
control request to the local scheduler and to every `ControlTarget`
concurrently, with a fresh rid per target, and collects the replies keyed by
DP rank in rank order. A target that claims a rank but returns no reply for it
is reported as a failure, so a relay that reached fewer schedulers than it
should cannot pass as success. `Replies::decode` fails the operation if any
rank failed or returned an undecodable payload, naming each rank; a
single-rank deployment's error passes through unchanged so existing status
mappings (503, legacy 499) hold. `merge_status` is Python's `merge_results`.

Replies are keyed by DP rank only. Node placement is a transport fact that
stays inside the target that reaches a rank; nothing in the control path or
the scheduler contract depends on it, matching the Python weight APIs.

**Peer transport** (`api_server/core/peer.rs`, `POST /internal/peer`). A peer
posts the control message's own wire bytes to the other listener; the reply
body is that scheduler's encoded output, decoded exactly like a local reply.
The receiving listener wraps the bytes as `ControlRequest::Forwarded` and
submits to its local scheduler only, never fanning out again. Peer HTTP
statuses map back onto the handlers' error categories; an unreachable peer is
`Unavailable` for that rank.

**Startup discovery** (`RustServer.gather_server_endpoints`). Every scheduler
rank joins one `all_gather_object` over the world CPU group at init; listener
ranks contribute `{dp_rank, endpoint}`. The sorted table rides into Rust as
`deployment_info.rust_server_endpoints`, and `peer_endpoints` turns every entry
but this rank's own into an HTTP target. A single-rank deployment gets an
empty peer list and behaves as before. A multi-node launch whose listener
address is loopback fails before the collective on every rank, with a clear
error, instead of parking the other ranks in the gather.

**Handlers split.** `core/handle.rs` and `core/hicache.rs` move to
`api_server/handlers/`, with the handle split by function: `handle.rs`
(construction, submit, the runtime-call guard), `generate.rs`, `control.rs`,
`info.rs`, `tokenize.rs`, `health.rs`, `hicache.rs`, and shared
`test_utils.rs`. `core/` keeps errors, events, fan-out, peers, and prefetch.
The move is a pure relocation: bodies were sliced from the committed file by
line range, and a line-multiset check of old versus new shows only rustfmt
rewrapping and import re-splits; the forced edits are `pub(super)` widenings
and two module paths.

## Behavior changes

- `/server_info` lists one `internal_states` entry per DP rank, in rank order.
- `/flush_cache` and HiCache clear succeed only if every rank succeeded.
  Python reports the first rank's outcome alone; this is the stricter reading.
- Merged messages drop empty per-rank messages instead of leaving blank
  separators.
- New `CoreError::DeadlineExceeded` maps to 504 / `DEADLINE_EXCEEDED`.
- `reqwest` (default features off, plain HTTP) is a new direct dependency of
  `sglang-server`; it was already in the tree via Dynamo.
