# [Feat] [AMD] DeepSeek-V4.1: Prefill CP fixes on top of #43465: zero-row groups, decode attention TP, image inputs

[Upstream PR](https://github.com/sgl-project/sglang/pull/44730) · state: open · merged: False

## Original PR description

## Motivation

#43465 (@At1a8) enables prefill context parallel (CP) for DeepSeek-V4.1 on HIP. Serving DeepSeek-V4.1-Flash with it on MI355X under long-context, mixed-length load, we hit three remaining gaps, which this PR closes:

1. **GPU memory fault at concurrency 64.** Under CP, a request group can own no rows on a rank (e.g. a one-token extend lands on another rank). The HIP low-ratio indexer still launched the fp4 prefill logits kernel for that group, and with 0 rows the kernel reads a null page table (address 0). The kernel-side issue is ROCm/aiter#6562.
2. **`--enable-cp-decode-attn-tp` does not work for DeepSeek-V4.1.** On gfx950, the V4.1 block-fp8 linears run from scale copies derived at load time (`weight_scale_mx_e8m0`, `weight_scale_inv_mx`, `weight_bf16`), which were not narrowed along with the weight.
3. **Image requests are wrong under CP.** The CP runner drives the language model directly, so image spans never reached the embeddings, and image pad hashes reached Engram / hash / vision routing unmapped.

### Relation to #43465

The first commit is #43465's change at its current head `6b04a79c` (author Wang, FangYuan), squashed onto main. It is carried only so this PR builds and tests on its own, and it drops out on rebase once #43465 merges. **Please review only the last two commits.** If the author of #43465 prefers, the two commits can also be folded into #43465.

## Modifications

1. `[AMD] DeepSeek-v4.1: Support prefill context parallel`: #43465 (head `6b04a79c`), unchanged.
2. **Zero-row groups and MXFP8 scale slicing**:
   - `low_ratio_backend_hip.py`: skip a request group that has no rows on this rank and publish no candidate mask for it (with 0 rows the fp4 logits kernel reads a null page table, and top-k cannot launch on an empty batch);
   - `cp_decode_attn_tp.py`: when narrowing the attention linears per rank, slice the gfx950 scale copies on the same dim as the weight; reject the MXFP8-native route, whose weights are pre-shuffled into scaled-MFMA lane order at load time and cannot be narrowed, with an error that names `--fp8-gemm-backend aiter` or `triton`;
   - tests: `test_dsv41_low_ratio_zero_row_hip.py`, `test_cp_decode_attn_tp.py`.
3. **Image inputs under CP**:
   - `DeepseekV4ForCausalLM.prepare_cp_inputs` reuses `prepare_language_model_inputs` to prepare the image embeddings and the remapped ids on the whole sequence before sharding; the CP runner shards them and hands the ids the hook returns to the logits step;
   - under the late-layer tail, the ids the MoE routes are gathered like its hidden states (local rows under MoE A2A); the DP attention branch is unchanged;
   - test: `test_eager_runner_cp_inputs.py`.

## Supported scope and limitations

- Validated only on ROCm gfx950 (MI355X).
- The vision tower itself is **not** context-parallel: every CP rank runs it on the whole sequence, as every TP rank does today. Vision under CP is only allowed without MoE A2A.
- `--enable-cp-decode-attn-tp` needs `--fp8-gemm-backend aiter` (or `triton`). With the default `auto`, gfx950 takes the MXFP8-native route and the server refuses to start with a `NotImplementedError` that names the fix.
- CP on HIP does not support the breakable prefill CUDA graph; all runs below use `--cuda-graph-backend-prefill disabled`.
- The zero-row skip is a framework-side guard; the kernel-side fix is tracked in ROCm/aiter#6562. The page-8 row-group fp4 indexer added on main (`SGLANG_HIP_DSV41_INDEX_K_PAGE8`, off by default) was not run with CP.
- Two cases of `test/registered/cp/test_cp_strategy_unit.py` fail on a ROCm GPU because of #43465's HIP 16-token floor (they fail with #43465 alone as well); this test runs on CPU only in CI.

## Accuracy Tests

Setup: MI355X, DeepSeek-V4.1-Flash, image `rocm/sgl-dev:v0.5.21-rocm720-mi35x-20261015` with the branch's whole `python/sglang` mounted over the image's, this PR on main `617c8b67b`, model default context (1M), paged FP8 KV. sgl-eval 0.1.3 with the settings of `test_deepseek_v41_flash_gb300.py` (`--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash --num-threads 64`, GSM8K all 1319 questions with `--max-tokens 4096`).

The InferenceY DeepSeek-V4.1-Flash TP4 recipe (`--speculative-algorithm DSPARK --speculative-dspark-block-size 5`, `--enable-decoder-swa-bounded-replay`, `--cuda-graph-backend-prefill disabled`, `--prefill-decode-interval 96`, `--swa-prefix-tails 1024`, `--max-running-requests 32`, `--mem-fraction-static 0.70`, `--fp8-gemm-backend aiter`, INT8 quick reduce, OPUS sparse prefill), without and with `--enable-prefill-cp --cp-strategy interleave --enable-cp-decode-attn-tp` (CP4), both servers on one node at the same time; acceptance length is the server's `accept len`, averaged over the GSM8K run:

| Configuration | GSM8K | Acceptance length |
|---|---|---|
| TP4 + DSpark | 96.36% | 3.52 |
| TP4 + DSpark + CP4 + decode-attn TP (this PR) | 96.21% | 3.49 |

Without DSpark, vision tower built, TP8 (`--enable-decoder-swa-bounded-replay --cuda-graph-backend-prefill disabled --fp8-gemm-backend aiter --kv-cache-dtype fp8_e4m3 --max-running-requests 64 --mem-fraction-static 0.85`), without and with `--enable-prefill-cp --cp-strategy interleave` (CP8); MMMU-Pro with 200 questions and `--max-tokens 32768` (the model preset), which exercises the image inputs of commit 3:

| Configuration | GSM8K | MMMU-Pro (image inputs) |
|---|---|---|
| TP8, no CP | 96.59% | 74.50% |
| TP8 + CP8 (this PR) | 96.21% | 78.00% |

A 200-question MMMU-Pro sample moves by a few points between runs.

No server faults or NaN in any run. Without commit 2, a ~600k-token request batched with a one-token extend under CP4 faults at address 0 every time; with it, the batch completes.

Unit tests: the three new test files pass; on the commits without the corresponding fix, the new cases fail.

## Speed Tests and Profiling

This PR fixes functionality; the prefill CP speedup itself is #43465's. `--enable-cp-decode-attn-tp`, which works for DeepSeek-V4.1 with commit 2, shards attention over the CP group in decode.

The servers of the table above; `bench_serving` with random token ids, 5 x concurrency requests (at least 16), the radix cache flushed before every run (random-ids prompts of one seed are prefixes of each other across runs, so an earlier run would otherwise warm the next one). Output tok/s and mean TTFT:

| Input / output | Concurrency | TP4 + DSpark | + CP4 + decode-attn TP |
|---|---|---|---|
| 64k / 1k | 1 | 416.8, 1.02 s | 446.1 (+7%), 0.96 s (-6%) |
| 64k / 1k | 4 | 414.9, 7.49 s | 489.4 (+18%), 6.17 s (-18%) |
| 64k / 1k | 8 | 479.6, 14.09 s | 509.6 (+6%), 13.18 s (-6%) |
| 64k / 1k | 16 | 477.6, 29.65 s | 497.2 (+4%), 28.44 s (-4%) |
| 8k / 1k | 1 | 681.4, 0.14 s | 659.1 (-3%), 0.14 s |
| 8k / 1k | 16 | 1810.7, 6.19 s | 1822.2 (+1%), 6.01 s (-3%) |

With 64k inputs, CP shortens the prefill that the queue waits on: 4–18% higher output throughput and 4–18% lower mean TTFT. With 8k inputs the two are within 3%; a single short request gains nothing from CP. Each point is a single run, and with DSpark the throughput also moves with the acceptance of the generated text.
