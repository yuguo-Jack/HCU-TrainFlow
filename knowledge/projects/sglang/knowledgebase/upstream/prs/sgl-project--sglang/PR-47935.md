# [Perf] dsv41: Keep MXFP4 Engram tables packed and decode E2M1 in the gather

[Upstream PR](https://github.com/sgl-project/sglang/pull/47935) · state: closed · merged: True

## Original PR description

## Motivation

[nvidia/DeepSeek-V4.1-Flash-1017-NVFP4](https://huggingface.co/nvidia/DeepSeek-V4.1-Flash-1017-NVFP4) stores the two Engram tables as packed MXFP4 (`uint8 [rows, 128]`, two E2M1 values per byte, even column in the low nibble, unchanged per-32 ue8m0 scales). `EngramEmbedding` allocates an e4m3 `[rows, 256]` table, so loading fails on the shape mismatch. Widening the rows to e4m3 at load would keep the FP8 checkpoint's size: about 25 GB per table per TP4 rank, about 190 GiB of host RAM per node with `placement: cpu`. Keeping the tables packed and decoding in the gather (as vllm-project/vllm#61530 does) halves that.

## Modifications

- When `quantization_config.engram_embed_quant` is `"mxfp4"`, `EngramEmbedding` allocates the table as `uint8 [rows, dim // 2]` in every layout (device table, per-rank and shared host table, peer shards), and `_load_rows` copies the packed rows as stored. Absent means `"fp8"`; any other value raises.
- `_engram_gather_kernel` and `_engram_gather_peer_kernel` take a `PACKED_FP4` constexpr that loads the byte, picks the nibble and builds the fp32 value from its bits before the unchanged e8m0 multiply. Every E2M1 value is exact in e4m3, so the output is bit-identical to the gather of the widened table, -0 included. The sign bit is set directly in the fp32 bits rather than through unary minus, which Triton before 3.8 lowers to `0 - x` (turning -0 into +0).
- The forward, staged-dequant, peer and torch-fallback lookups pass the mode. The scheduler stager moves bytes per row and needs no change.
- FP8 checkpoints allocate and gather exactly as before. A packed table in a checkpoint that does not declare `engram_embed_quant` fails at load with a message naming the key, instead of loading at twice the memory.
- New `test/registered/kernels/ops/embeddings/test_engram_gather.py`: all 256 byte values with random scales through `engram_gather` and `engram_gather_peer`, packed and widened, compared with an E2M1 spec decode as int16 bits, so signed zero is checked too.

## Accuracy Tests

GB300, TP4, one node, SGLang nightly 2026-10-30 plus this change, DSpark (block size 5), `--engram-config '{"placement": "cpu", "replication": "none", "lookup": "auto"}'`. GSM8K via sgl-eval 0.1.3: 1319 questions, concurrency 64, temperature 1.0, top_p 0.95, thinking on.

| Engram table | GSM8K | accept length |
|---|---:|---:|
| packed (this PR) | 96.82% | 3.38 |
| widened to e4m3 | 96.82% | 3.41 |

Gather checks on GB300: every packed lookup equals the same lookup on the widened table bit for bit. One GPU: all 256 byte values, random rows and scales, device, pinned-host, sharded and sorted gathers, `EngramEmbedding` with a per-rank host table, staged dequant and the torch fallback. Four GPUs: the peer kernel through real `_PeerShards` export/import. `test_engram_gather.py` passes on GB300 (Triton 3.8.0).

The GSM8K and timing runs predate setting the sign bit directly. On Triton 3.8, which lowers unary minus to `fneg`, both versions produce the same bits.

[by Claude Code] **Severity: nit | Confidence: High**

**Issue**

`-vals` loses the sign of negative zero. Triton lowers unary minus to `0.0 - x` (`sub.f32 0f00000000, x` in the sm_100 PTX), so nibble `0x8` (E2M1 -0) decodes to +0.0. The widened table decodes byte `0x80` to -0.0, and so does `_unpack_mxfp4_rows` in the torch fallback. So the packed gather is not bit-identical where no float all-reduce follows: the shared host table, TP1, staged dequant, and the gfx950 integer all-reduce. `test_engram_eager_and_graph_reconstruction` asserts that reconstruction keeps signed zero.

**Fix**

Set the sign bit before the bitcast:

```python
vals = (bits | ((nib & 0x8) << 28)).to(tl.float32, bitcast=True)
```

With this change, packed and widened outputs match under `.view(torch.int16)` in `TRITON_INTERPRET=1`.

**Issue**

This branch widens a packed table to e4m3 when the checkpoint does not declare `engram_embed_quant`. The only packed checkpoint, `nvidia/DeepSeek-V4.1-Flash-1017-NVFP4`, sets `"engram_embed_quant": "mxfp4"` in its `quantization_config`, so no known checkpoint reaches this branch. #47880 is closed, so this PR now adds the branch, `_expand_mxfp4_rows_to_fp8`, and `_MXFP4_EXPAND_CHUNK_ROWS`. A checkpoint that drops the key would load silently at twice the host RAM (about 189 GiB instead of 97 GiB per node).

**Fix**

Drop the branch and its two helpers. Fail early instead, for example `assert src.dtype != torch.uint8, "packed Engram table: set quantization_config.engram_embed_quant to 'mxfp4'"`. Also update the PR description, which still says that only the last commit belongs to this PR.

**Issue**

No registered test covers the packed decode. The nibble order, magnitude codes, and sign handling in `_row_values` and `_unpack_mxfp4_rows` are new numerics on the NVFP4 checkpoint's lookup path. The GB300 checks in the PR description are not in the repo, so CI will not catch a later break.

**Fix**

Add a small test under `test/registered/kernels/ops/embeddings/`. Build a packed table that holds all 256 byte values, widen it to e4m3, and compare `engram_gather` with `packed_fp4=True` against `packed_fp4=False` (and the same for `engram_gather_peer`). Compare with `.view(torch.int16)`, because `torch.equal` on bf16 treats -0.0 and +0.0 as equal and would miss the signed-zero issue in this function. `_unpack_mxfp4_rows` can get a CPU-only check.
