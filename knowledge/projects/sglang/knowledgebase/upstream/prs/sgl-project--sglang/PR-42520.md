# [Perf][CPU] Defer token allocator free-list copies until allocation pressure

[Upstream PR](https://github.com/sgl-project/sglang/pull/42520) · state: closed · merged: False

## Original PR description

## Motivation

The CPU `TokenToKVPoolAllocator.free()` concatenates each released slice onto an existing free list. With `need_sort=False`, every release copies the remaining free pool; with `need_sort=True`, it repeatedly copies the growing deferred-release tensor. Request turnover can therefore copy far more indices than it releases.

## Modifications

- Stage owned snapshots of released CPU indices and count them as immediately available.
- Concatenate once when an allocation exhausts the active free list; sort at that boundary only when `need_sort=True`.
- Preserve FIFO reuse for unsorted pools, sorted reuse under pressure, failed-allocation behavior, grouped release ownership, and clear/reallocation behavior.
- Use the existing `get_all_free_pages()` census in the radix checkpoint ownership test.
- Add registered CPU contract tests and a manual allocator benchmark under the memory-cache owner.

The optimization is limited to CPU allocators. An unrestricted prototype did not improve latency in an A30 allocator microbenchmark, so GPU release behavior remains as before.

Related open changes were checked: #40348 adds debug-mode double-free checks to this allocator, and #35971 optimizes the separate Mamba slot allocator. Neither addresses the repeated CPU free-list copies here.

## Accuracy Tests

## Speed Tests and Profiling

Measured on AMD EPYC 9554, Python 3.12.13, PyTorch 2.13.0+cu132, with one PyTorch CPU thread. Each sample runs 4,096 allocate/free turns of 128 slots, followed by full-pool recovery and an index census. Five baseline/candidate measurements were interleaved in the same process; the baseline class was loaded from main at `ab9d8f029c12cda8167f51d46664d643c8771a6e`.

Median milliseconds:

| Pool slots | `need_sort` | Main | This PR | Speedup |
| ---: | :---: | ---: | ---: | ---: |
| 8,192 | false | 101.77 | 103.22 | 0.99x |
| 8,192 | true | 113.43 | 114.14 | 0.99x |
| 131,072 | false | 1,686.33 | 183.93 | 9.17x |
| 131,072 | true | 802.39 | 199.17 | 4.03x |
| 524,288 | false | 6,095.88 | 203.81 | 29.91x |
| 524,288 | true | 3,305.09 | 302.89 | 10.91x |

For the 131,072-slot unsorted case, profiling reports `aten::cat` calls dropping from 4,096 to 4 and concatenation allocations from 4 GiB to 4 MiB. The staged snapshots additionally copy 4 MiB of released indices. The small-pool cases are approximately neutral. Staging adds a tensor/list entry per release until allocation pressure merges it; this trades metadata for reduced copying.

These are allocator microbenchmarks, not model-serving throughput or endpoint latency measurements. No GPU speedup is claimed.

```bash

```
