# [diffusion] attention: Wire fast path varlen attention through the attention backends

## Motivation

<!-- Describe the purpose and goals of this pull request. -->
PR https://github.com/sgl-project/sglang/pull/27066 added fast paths through varlen support to the USPAttention. This was hardcoded to either use FA (FAv3 or FAv4) or as a fallback SDPA. These calls call FA directly through the FA interface, not through the attention backends. This limits the functionality to these backends only, even when the other backend would support it (AITER on ROCm, for example).

This PR changes the call so that they go through the selected attention backend instead. The backends got a new property `has_native_varlen_kernel`, which gates the usage of these fast paths to backends that support varlen natively and thus benefit from this.



## Modifications

<!-- Detail the changes made in this pull request. -->
- Adds `AttentionImpl.has_native_varlen_kernel()`, defaulting to `False`. It declares whether the underlying kernel consumes `cu_seqlens` itself, as opposed to forward_varlen emulating segments with a per-segment Python loop. 
- `AttentionImpl.forward_varlen()` gains optional `cu_seqlens_k` / `max_seqlen_k`. Omitted, both sides use the query bounds, so every existing caller is unchanged. They exist for the K/V-gather site, where queries and keys carry different segment lengths.
-  Backends declaring native varlen override `has_native_varlen_kernel()` to `True`
- USPAttention fast paths call sites move from a direct `flash_attn_varlen_func`call to `self.attn_impl.forward_varlen()`

- avjves · comment · 2026-09-22T07:06:54Z · [source](https://github.com/sgl-project/sglang/pull/39962#issuecomment-5772515529)

@mickqian what do you think, could this be merged? My motivation here was that it was problematic for us that all these paths that are used by some common models would drop to SDPA on ROCm, as FAv3/FAv4 naturally is not available there. Weaving the varlen calls (even if it's not real "varlen") through the attention backends allows us to nicely use different backends here.

Other option would be to add a separate call function in `layer..py` where it would call either FA varlen_func AITER varlen_func, depending on the system.

WDYT? Thanks!
