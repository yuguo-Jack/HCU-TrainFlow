## Motivation

<!-- Describe the purpose and goals of this pull request. -->

The AMD monokernel backend runs the tail of each Kimi-K3 MoE layer as one persistent launch: o_proj, the attention-TP all-reduce, the MLP attention-residual seam and the MoE. For that the attention has to stop at its TP-local output and hand it over. Today both Kimi-K3 attention classes run o_proj inline, so there is no point to stop at.

That backend is sgl-project/sgl-amd-mono. It loads through the `sglang.srt.plugins` entry point and is selected with `--monokernel-backend amd`. SGLang needs nothing else for it: `install_monokernel_forward` swaps the whole model forward (`srt/monokernels/runtime.py`), so the kernels, the spec and its registration all live in the plugin. This method is the one thing the plugin cannot reach from outside, which is why it is the only change here.

## Modifications

<!-- Detail the changes made in this pull request. -->

`forward_gated_core()` on `KimiK3DeltaAttention` and `KimiK3MLAAttention`: the TP-local attention output after the output gate, before o_proj. The caller owns o_proj and the attention-TP reduction it carries, so `o_proj(forward_gated_core(x)) == forward(x)`.

- `KimiK3DeltaAttention`: a plain extract. `forward()` now calls the new method and keeps the o_proj tail; the moved body is unchanged.
- `KimiK3MLAAttention`: the MLA cores reach o_proj from several places, so the split rides on the instance-level wrapper that already applies the output gate. `forward_gated_core()` arms a one-slot sink, runs `forward()`, and takes the tensor the wrapper hands back instead of running o_proj.

Three guards on the MLA path, because it is the one that can go wrong quietly and has no in-tree caller to exercise it:

- the sink holds one tensor, so o_proj being reached twice in one forward raises instead of silently returning the first;
- a quantized o_proj input raises. On ROCm the MLA core quantizes what it hands o_proj when o_proj's weights are MXFP4 or block-scale fp8 (`forward_mla_rocm.py:325,351`), and the output gate is skipped along with it, so there is no gated bf16 tensor to hand back. Every rank quantizes alike, so this raises on all of them rather than splitting the TP group;
- the returned width is asserted against the head count the core actually ran with times `v_head_dim`, so a config that does not land on the expected width fails at the split rather than inside the kernel. The head count is recorded in the wrapper rather than read after `forward()` returns, because decode-time context parallelism lowers `num_local_heads` for the length of the core and restores it on the way out.

The standard path is unchanged: `forward()` produces what it did before.

## Accuracy Tests

<!-- If this pull request affects model outputs (e.g., changes to the kernel or model forward code), provide accuracy test results. -->

8 x MI355X, TP8 / DCP1, FP8 KV cache, DSpark block size 7. `/data-models/Kimi-K3`, GSM8K 200 questions, `--parallel 2`:

| | Accuracy |
|---|---:|
| This branch, no monokernel backend | 0.990 |
| This branch, `--monokernel-backend amd` | 0.985 |

With the backend on, the launch consumes `forward_gated_core`'s output on all 92 MoE layers, and the plugin's kernel checks put the layer output at cos 0.999994 against SGLang's ops with o_proj and the reduce run separately. That is the equivalence this PR claims, measured through the caller.

The numbers above were taken on `e5274752a8`. The branch has since been rebased onto `8e7601ae4a` and the extract re-verified there mechanically (below); the accuracy run was not repeated.
