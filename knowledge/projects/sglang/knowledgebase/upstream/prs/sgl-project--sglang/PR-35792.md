# [Fix] compressed-tensors: Honor .linear-wrapped ignore entries on fused shards

[Upstream PR](https://github.com/sgl-project/sglang/pull/35792) · state: open · merged: False

## Original PR description


Fixes #28018.

The reported llm-compressor checkpoint spells its vision-tower `ignore` entries against the `CompressedLinear` wrapper (`...q_proj.linear`). For fused `qkv_proj` / `gate_up_proj`, SGLang expands the layer into shard names without that suffix, so `should_ignore_layer` misses those wrapped entries and quantizes the corresponding fused projections. That is 135 of its 189 wrapped entries; the other 54 name `o_proj` / `down_proj`, which `ClippableRowParallelLinear` already nests at `.linear`, so those already match.

The change is therefore on the fused path only: retry the wrapper spelling once per expanded shard, after the existing comparator misses. Four lines, no new matching primitive; #32736's no-prefix invariant is untouched.

Verified on one H200 with `google/gemma-4-31B-it-qat-w4a16-ct`:

- **before** — the load reaches `compressed_tensors_wNa16` → `gptq_marlin_repack` and aborts with `size_n = 8608 is not divisible by tile_n_size = 64`, the message in #28018;
- **after** — the model loads, all 108 vision-tower projections come up `UnquantizedLinearMethod`/bf16, and `language_model.layers.0` stays `CompressedTensorsLinearMethod`;
- **minimal** — a third arm that also retried on the unfused path produced a byte-identical result.

Two behavior changes, your call:

- naming **only some** fused shards in the wrapped spelling previously loaded silently quantized, and now raises the existing inconsistent-scheme `ValueError` (whose message does not mention `.linear`);
- **mixing** plain and wrapped spellings previously raised, and now resolves to ignored.

`should_ignore_layer` is shared with `w8a8_int8.py`, where a 10-case probe moves only the three cases whose ignore list holds a `.linear` entry, and with diffusion `modelslim.py`, which passes a nested mapping and so never takes the fused path.

Tests are CPU-only and matcher-level: 10 cases, 5 red on main; the largest drives the checkpoint's 189-entry list at the tower's real runtime names. One checkpoint on one GPU, and no accuracy or throughput measurement.

#24929 identified this mechanism first; its hunk sits in `check_contains`, which the ignore path no longer reaches since #32736.
