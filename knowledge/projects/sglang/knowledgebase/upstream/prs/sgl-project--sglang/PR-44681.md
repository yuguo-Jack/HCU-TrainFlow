# [Fix] symm-mem: Name the window registration in the scheduler watchdog dump

[Upstream PR](https://github.com/sgl-project/sglang/pull/44681) · state: closed · merged: True

## Original PR description

## Motivation

With `--enable-symm-mem`, `ncclCommWindowRegister` is called from the forward
path whenever the symmetric-memory pool grows a new segment. That call blocks
in NCCL's Unix-domain-socket fd-exchange rendezvous, which has no timeout of
its own. When the rendezvous wedges, every rank in the group parks in `recvmsg`
and nothing is ever printed: the engine stays up, `/health` keeps returning
200, and no batch makes progress (#36943).

We hit exactly this on a single-node TP8/EP8 Kimi-K3 deployment with MegaMoE:
the engine hung on the first warmup prefill and the server log contained no
error line at all — the only way to tell it apart from an idle engine was to
notice that the log had stopped advancing. Roughly one cold-compile-cache start
in five hung this way.

The scheduler watchdog does eventually notice and dumps, but it cannot say
*what* was in flight, and it waits its full `--watchdog-timeout` (300 s by
default) before it does.

## Modifications

- The registration runs on a worker thread bounded by
  `SGLANG_SYMM_MEM_REGISTRATION_TIMEOUT_S` (default 120 s), so a wedge is
  reported sooner than the watchdog would report it.
- On timeout the registration is named in the log, `pyspy_dump_schedulers()` and
  `faulthandler.dump_traceback()` capture the native and Python stacks, and the
  parent is sent `SIGQUIT` — the same exit path the scheduler and the watchdog
  use, so the normal crash handling runs. The process does not continue: the
  wedged thread still holds the C++ segment mutex, so it could never register
  again.
- `describe_registration_in_progress()` publishes what is in flight, and the
  scheduler watchdog's `dump_info()` includes it, so a stall there reads as
  "symmetric-memory registration in progress: comm=… group=…" instead of a bare
  watchdog timeout.

This does **not** remove the underlying deadlock; it makes it named, fast and
diagnosable. The root cause is tracked in #36943.
