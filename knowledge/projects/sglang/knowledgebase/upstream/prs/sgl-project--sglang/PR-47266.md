# [Feat] [NPU] eplb: Enable dynamic expert load balancing on Ascend

[Upstream PR](https://github.com/sgl-project/sglang/pull/47266) · state: open · merged: False

## Original PR description

## Motivation

Enable dynamic EPLB on Ascend through the existing placement planner and single-layer migration algorithm.

NPU expert weights can use NZ storage, and DeepEP receiver counts can include graph padding. The NPU adapters collect valid sender routes and prepare expert weights for migration while preserving the addresses used by captured graphs.

## Changes

- Use the select-experts gatherer for exact Ascend DeepEP routing counts.
- Reuse the TP device group for statistics and weight transfers. Its ordered members must cover WORLD; migration requires TP = EP = WORLD. Warm collective and peer channels before serving.
- Keep draft forwards and NPU draft graph capture outside the target recorder's reset/append lifecycle.
- Select participating layers/ranks, reuse receive buffers across compatible layers, and bound queued staging work with completion events.
- Keep the existing NZ-to-ND conversion and in-place writeback path on Ascend 910C.
- Add physical-storage staging for Ascend 950PR and 950DT, selected through the existing ARCH35 check.

The shared single-layer migration algorithm is unchanged. No dedicated EPLB communication group is created.

## How to enable dynamic EPLB

Use a checkout containing this PR with an MoE model and NPU backend that provide expert routing statistics and expert-weight updates. Add the following flags to the existing `python -m sglang.launch_server` command:

```bash
--enable-eplb \
--expert-distribution-recorder-mode stat
```

`--enable-eplb` enables automatic rebalancing and weight migration. When the recorder mode is omitted, argument resolution sets it to `stat`; it is written explicitly here to make the configuration clear. Setting the recorder mode alone collects statistics but does not enable automatic rebalancing.

### Parallelism and redundant experts

This implementation requires **TP = EP = WORLD**, with TP members in WORLD rank order and EP greater than one. For a service with 16 NPU ranks, use `--tp-size 16 --ep-size 16`. In a disaggregated deployment, this requirement applies separately to the prefill service and the decode service.

Redundant experts are optional. With zero redundant experts, EPLB can move existing experts between ranks. To give the planner extra replica slots for hot experts, add:

```bash
--ep-num-redundant-experts 16
```

This allocates **16 additional expert slots per MoE layer across the whole EP group**, not 16 per rank. The routed expert count plus the redundant expert count must be divisible by EP size. For example, 256 routed experts with EP16 occupy 16 slots per rank; adding 16 redundant slots increases this to 17. Fused shared experts are separate from these redundant routed-expert slots.

Redundant slots consume additional weight memory and must be configured at startup. For an OFF/ON comparison, keep their count the same in both runs.

### Update interval and statistics window

| Flag | Meaning | Default |
| --- | --- | --- |
| `--eplb-rebalance-num-iterations I` | Number of target-model forward iterations between rebalance cycles | `1000` |
| `--expert-distribution-recorder-buffer-size W` | Capacity of the statistics window used to compute placement | Follows `I` when omitted |
| `--ep-num-redundant-experts R` | Additional routed-expert slots per layer across the EP group | `0` |

Use positive values with **`W <= I`**. These are forward iterations, not requests or seconds. With speculative decoding, a target iteration can produce multiple output tokens. A rebalance cycle does not necessarily move weights: unchanged layers and ranks with no migration work are skipped.

The following PD example uses P `50/50` and D `4000/1000` (interval/window), with 16 redundant slots per role. These are workload-specific starting values from the earlier Ascend 910C experiments, not tuned defaults for 950PR/950DT.

Append to the **prefill** launch command:

```bash
--enable-eplb \
--expert-distribution-recorder-mode stat \
--ep-num-redundant-experts 16 \
--eplb-rebalance-num-iterations 50 \
--expert-distribution-recorder-buffer-size 50
```

Append to the **decode** launch command:

```bash
--enable-eplb \
--expert-distribution-recorder-mode stat \
--ep-num-redundant-experts 16 \
--eplb-rebalance-num-iterations 4000 \
--expert-distribution-recorder-buffer-size 1000
```

Keep the placement algorithm at its default `auto` and let argument resolution choose the dispatch algorithm for the configured MoE backend. DSpark can be used alongside EPLB but is not required to enable it.

### Communication, A5 selection, and logs

EPLB reuses the TP HCCL group and its communication configuration. No separate EPLB buffer-size or communication-mode flag is required. Ascend 950PR and 950DT select the ARCH35 staging path automatically; there is no additional A5 enable flag. The real-device validation status of that path is listed below.

Startup logs include:

```text
[NPU EPLB] communication warmup finished: ...
[EPLBManager] system started, will rebalance per ... iterations.
```

Once enough target forwards have run, check the rebalance start/completion logs. For balance diagnostics, optionally add `--expert-balancedness-report-mode server_log`.

## Ascend 950PR / 950DT weight staging

MXFP4/MXFP8 loaders retain transposed NZ views. Passing these views directly to `npu_format_cast(..., 2)` is rejected by the A5 conversion interface. NZ `copy_` also restricts view destinations.

The A5 adapter snapshots complete expert storage with `copy_memory_` into a same-dtype ND allocation. A byte view exposes one row per routed expert to the existing updater. Communication moves packed FP4, FP8 and NZ padding without numerical conversion. Writeback copies the complete snapshot to the original allocation, retaining model dtype, format, shape, strides and graph addresses.

The full parameter base identifies the total expert count. Only its routed prefix participates in migration; fused shared-expert rows at the end remain unchanged. The adapter accepts dense per-expert storage with an outer expert axis, including inner transposes. Padded NZ tensors must retain the full parameter base through the routed-expert slice. Unsupported offsets/layouts and inconsistent chunk storage are rejected before migration.

Raw copies use `non_blocking=True` and the existing stream/event ordering. Staging includes padding and shared-expert suffixes; no A5 latency or memory saving is claimed.

All new A5 production code is in `hardware_backend/npu/eplb.py`. This combined branch retains its existing TP reuse, NPU draft adapters and graph-backend changes.

## Validation

The new staging implementation was checked on CPU with storage/device doubles and the production Python methods:

- 72 combinations of uint8 packed payloads, FP8/BF16 storage, transpose state, padding, shared-expert suffixes and expert placement. Local swaps, duplicate experts and A-to-B-to-A restoration preserve exact bytes and model addresses/strides.
- Three simulated ranks exercise the production P2P construction and wait sequence with byte messages, including cross-rank moves, a redundant destination and an idle rank.
- Invalid slices, offsets, capacity bounds, detached prefixes and incompatible chunk layouts are rejected before raw copies.
- Additional cases cover ND scales, canaries, inference context, sender-only layers and bounded staging lifetime.
- The Ascend 910C staging class still follows the original conversion/writeback path.
- Ruff, formatting, isort and whitespace checks pass.

These checks do not execute NPU kernels or HCCL. The 950PR/950DT path still needs real-device NZ round-trip, P2P, graph-replay and model-accuracy validation. A single-device probe is prepared outside the PR. Test scripts and reports are kept out of the production diff.

I checked this against the installed PyTorch/torch_npu code and ran a 16-rank comparison on Ascend 910C. Reusing TP is useful here: it avoids activating another communication group for EPLB.

The shared accumulator keeps `_communication_group = None`, preserving the existing default-WORLD selection for GPU. The NPU accumulator overrides the property to return `get_parallel().tp_group.device_group`. This reuses an existing group; it does not create an EPLB-specific HCCL group.

`None` does not mean “reuse whichever group already has these ranks.” The installed call paths are:

```text
reduce / broadcast(group=None)
  -> _group_or_default_group(None)
  -> _get_default_group()
  -> GroupMember.WORLD

all_reduce(group=None)
  -> _get_default_group()
  -> GroupMember.WORLD
  -> group.allreduce(...)
```

WORLD and TP are separate ProcessGroup objects even when both contain ranks 0–15. The NPU adapter checks that TP covers WORLD in rank order, so the existing global-rank indexing and root rank 0 remain valid.

For the comparison, both arms first created and used TP, then ran the same statistics and migration operations with either TP or `None`. Each arm started in fresh processes. The table measures additional device memory at the first statistics collective, relative to the already-active TP baseline:

| Configuration | Reuse TP | Use default WORLD |
| --- | ---: | ---: |
| Prefill configuration: WORLD buffer setting 2048 MiB | 0.00 MiB | 4097.94 MiB |
| Decode configuration: WORLD buffer setting 1200 MiB | 0.00 MiB | 2401.98 MiB |

The measured increase is approximately **twice the default WORLD group's configured `hccl_buffer_size`**, plus a small runtime overhead:

- Prefill: `4097.94 MiB ≈ 2 × 2048 MiB`, with the setting taken from `DEEPEP_HCCL_BUFFSIZE=2048`.
- Decode: `2401.98 MiB ≈ 2 × 1200 MiB`, with the setting taken from `HCCL_BUFFSIZE=1200` (`DEEPEP_HCCL_BUFFSIZE` was unset).

SGLang selects this value from `DEEPEP_HCCL_BUFFSIZE`, then `HCCL_BUFFSIZE`, falling back to 200. The observed relationship is therefore to the effective WORLD buffer setting, rather than always to `DEEPEP_HCCL_BUFFSIZE`.

Values are means across 16 logical devices. The statistics tensor was allocated before measurement; PyTorch allocated/reserved memory did not change across this collective. The increase appeared in total device memory usage, which includes communication resources outside the PyTorch allocator. These are communication microbenchmark measurements, not full-service ON/OFF memory deltas.

Both choices passed the statistics checks and 40 layout checks per rank, including sparse exchanges, redundant experts, NZ/ND staging, in-place writeback, and graph replay reading the updated weights. Thus the reason for keeping this parameter is resource reuse, not a claim that WORLD communication fails.

I also checked the migration path: `P2POp` resolves `None` to WORLD in its constructor. With torch 2.10.0 and torch_npu 2.10.0.post6 on the tested device, `batch_isend_irecv` uses the NPU coalescing path and sends/receives through that selected group. It does not switch back to TP.

I would keep the explicit group for all three statistics collectives. Removing it would make NPU statistics activate WORLD even though the existing TP group can handle them. If an application already activates WORLD elsewhere, its incremental memory cost must be measured from that state; the comparison above specifically verifies the already-active-TP case.
