# [Fix] sampling: Make penalizer execution order deterministic

[Upstream PR](https://github.com/sgl-project/sglang/pull/48084) · state: open · merged: False

## Original PR description

## Motivation

Fix inconsistent penalizer execution order across TP ranks, which can cause
sampled-token divergence and subsequent distributed hangs.

`SamplingBatchInfo.from_schedule_batch()` passes a `set` of penalizer classes to
the orchestrator, which preserves its iteration order and applies penalties
sequentially in the non-overlap path. Class-object set order can differ across
processes. Additive presence/frequency penalties and repetition scaling do not
commute, so different orders produce different logits and probabilities. Even
identical sampling seeds and offsets cannot prevent token divergence when the
input distributions differ.

For example, the same request enables `presence_penalty=1` and
`repetition_penalty=1.05`, with other penalties disabled. Suppose TP ranks 0
and 1 have identical model-forward logits: token A has `2.0`, B has `0.93`,
and all other candidates are lower. Their generation histories also match:
A has already been generated, B has not, so neither penalty changes B.

Because their class sets iterate differently, suppose rank 0 applies presence
before repetition, while rank 1 applies repetition before presence. Presence
subtracts 1 from A; repetition divides positive logits by 1.05. Greedy decoding
makes the resulting token divergence explicit:

| TP rank | Execution order | Final logit of A | Final logit of B | Selected token |
| --- | --- | --- | --- | --- |
| rank 0 | presence then repetition | `(2.0 - 1) / 1.05 = 0.952381...` | `0.93` | A |
| rank 1 | repetition then presence | `2.0 / 1.05 - 1 = 0.904762...` | `0.93` | B |

The request, penalty parameters, history and initial logits match across ranks;
only execution order differs. A's resulting logits differ by about `0.047619`,
so rank 0 selects A while rank 1 selects B. With stochastic sampling, the
different logits also produce different probability distributions, which can
yield different tokens even with identical seed/offset. This is not merely
floating-point rounding: subsequent generation histories or completion states
can diverge across ranks and leave distributed execution hanging.

## Modifications

- Replace the set with a tuple: frequency, minimum-new-tokens, presence, repetition.
- Change the orchestrator input annotation from `Set` to `Sequence` and update test callers.
- Add CPU regressions through the production constructor, covering different
  class hashes, combined penalties, accumulated/repeat paths, and disabled/single penalties.

The order matches the existing accumulated and speculative-repeat calculations.
No sampler kernel, collective or model-forward code changes.
