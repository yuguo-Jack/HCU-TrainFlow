# [Fix] [AMD] diffusion: Enable `--quantization fp8` on gfx1250 (torch.compile lowering + per-channel weight scales)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45304) · state: closed · merged: True

## Original PR description

## Motivation

`--quantization fp8` does not work on gfx1250. With `--enable-torch-compile` it dies in Inductor lowering on the first warmup request, before a single image:

```
LoweringException: AssertionError: target: aten._scaled_mm.default
  args[3]: ... FixedLayout('cuda:0', torch.float32, size=[], stride=[])
```

`args[3]` is the weight scale, and it is a **rank-0 scalar**. Inductor's `_scaled_mm` template loads it with two index symbols against a zero-length stride, so the `len(index) == len(stride)` assert at `ir.py:2034` fires.

The scalar comes from the missing-CUTLASS fallback: `cutlass_fp8_supported()` is `False` for every ROCm device (`fp8_utils.py:398` is `if not _is_cuda: return False`, before it looks at compute capability), so `process_weights_after_loading` falls to `input_to_float8`, whose single `aminmax()` yields a 0-dim `weight_scale` instead of a per-channel `[N]` vector. **The crash and the quality loss are therefore one bug**: a per-tensor scale that Inductor cannot lower *and* that throws away the range a BF16 checkpoint needs to survive FP8. NVIDIA takes the per-channel CUTLASS branch and sees neither symptom, which is why this is gfx1250/ROCm-only.

Avoiding the lowering is not enough on its own: hipBLASLt ships no tuned gfx1250 kernels, so at the FLUX.2-dev 720p shapes `torch._scaled_mm` FP8 reaches 471-506 TFLOPS while the BF16 torch.compile templates it replaces already reach 645-710.

**The scheme here is A8W8** -- a fully FP8 GEMM. Both operands are `e4m3`: per-token dynamic scales on the activations, per-channel scales on the weights, FP32 accumulate. It is explicitly *not* weight-only (A16W8); the activations are quantized too, so the matrix cores actually issue FP8 MFMA, which is where the speedup comes from.

**The fix** is two changes for two different reasons, either of which alone stops the crash:

* `process_weights_after_loading` takes the per-channel branch (`per_token_group_quant_fp8`), giving a real `[N]` scale. This is the *accuracy* fix; the ranks line up as a side effect.
* `apply` quantizes the activations per token and routes both operands to an A8W8 Triton tile, so `aten._scaled_mm` is never reached. This is the *performance* fix: 1150-1255 TFLOPS instead of 471-506.

This affects any gfx1250 run passing `--quantization fp8` with a BF16 checkpoint. Nothing in the fix is model-specific -- it is the shared `Fp8LinearMethod` in the diffusion stack -- though the reproduction here is FLUX.2-dev at 720p, where linears are 83% of GPU kernel time. MI300X, MI355X and NVIDIA are unaffected: `is_gfx1250_supported()` is false there, and `cutlass_fp8_supported` already routes NVIDIA to a per-channel CUTLASS GEMM.

## Modifications

* New `python/sglang/kernels/ops/gemm/fp8_gfx1250.py`: an A8W8 (per-token activation / per-channel weight) FP8 `[M, K] @ [K, N]` Triton tile plus the per-token activation quantizer that feeds it. The tile indexes its operands modulo M and N rather than masking the loads (masked loads cost ~10% on this target and the tail is at most one tile), and masks only the store. `_select_config` carries the tile sizes an offline sweep picked for the served shapes.
* `multimodal_gen/runtime/layers/quantization/fp8.py`: `Fp8LinearMethod.__init__` computes `use_gfx1250_triton_fp8` once; when set, `process_weights_after_loading` takes the **per-channel** branch for a non-FP8-serialized checkpoint -- replacing the rank-0 `input_to_float8` scale that both breaks the lowering and drops the checkpoint's range -- and `apply` tries `_apply_gfx1250_triton_fp8` first, returning `None` to the existing path for any shape the tile does not cover.
* `srt/environ.py`: `SGLANG_DISABLE_GFX1250_FP8_GEMM`, a diagnostic kill switch.
* The quantized weight is stored **row-major** `[K, N]` rather than as the transposed view of `[N, K]` that this method has always produced. A BLOCK_N slice of one k-row otherwise reads N single bytes strided by K instead of BLOCK_N contiguous ones; making it contiguous once at load is worth 1.05-1.33x per GEMM and 1.06x end to end. The tile's config table is tuned for that layout, and a unit test pins it, since a refactor that drops the transpose would be a silent regression.
* `test/registered/amd/test_fp8_gemm_gfx1250.py`: tile correctness against a dequantized reference, and the dispatch seam itself.

**BLOCK_SIZE_K is capped at 64 on purpose.** On gfx1250 with triton 3.8.0, an FP8 `tl.dot` miscompiles for `BLOCK_SIZE_K >= 128`: it silently returns NaN for every `num_warps` x `num_stages` combination tested (16 of 16), and the broken kernel *times about 40% faster than a correct one*. An autotune sweep without a correctness gate will therefore select it and report a phantom ~1730 TFLOPS. This also means 1150-1255 TFLOPS is the ceiling for correct Triton FP8 on this target today, not the hardware's ceiling. Note that `triton_scaled_mm`'s own heuristic picks `(128, 128, 128)` for M 128, so callers must not route gfx1250 FP8 there until the compiler is fixed.

## Accuracy Tests

No accuracy harness applies -- this is a diffusion image model, so there is no gsm8k-style score. The gate is instead split into the two questions that can actually be answered separately: is the kernel numerically correct, and did the image get worse.

Measured on one gfx1250 (DPX half-package), FLUX.2-dev 720p, 50 steps, seed 42, `--enable-torch-compile true`, aiter attention, all offload off. The "before" arm is BF16 at this PR's merge base. There is no "FP8 without this PR" arm, because that configuration does not run at all -- it is the lowering crash described in Motivation.

### 1. Trajectory divergence -- is the kernel correct

Comparing the per-step denoise latents of the two arms (`[1, 50, 3600, 128]`) separates the error the GEMM introduces from the amplification the sampler applies to it afterwards. One seed is sufficient here: this measures numerics, not a sample distribution.

## Benchmarking and Profiling

### End to end, on the tracked MI450 dashboard configuration

Both rows are from the same dashboard harness, same image (`rocm/sgl-dev:v0.5.22-rocm10-mi45x-20261020`), same day, same arm (**MI450-MC Hammer: DPX TP1 (A0), `--enable-torch-compile true`**). The baseline row is the arm as it ships today -- BF16, because `--quantization fp8` cannot be passed on this target without the crash above. The second row is this PR *plus* the flag it enables:

| Arm | Text encode (s) | **Denoise (s)** | VAE decode (s) | **Total (s)** |
|-----|-----------------|-----------------|----------------|---------------|
| DPX TP1 (A0) + torch-compile (BF16, today) | 0.0034 | 48.7215 | 3.0623 | 51.787 |
| + PR 45304 + `--quantization fp8` | 0.0031 | 36.0457 | 2.9947 | **39.044** |
| **Delta** | -- | **-26.0% (1.35x)** | -2.2% | **-24.6% (1.33x)** |

The entire win is in denoise, which is what the change touches; text encode and VAE decode are unchanged, and they are what keeps the e2e ratio (1.33x) below the denoise ratio (1.35x).

> Note for anyone reproducing: the `+ PR45304` row **must** carry `--quantization fp8`. Every line of this PR sits behind `Fp8LinearMethod.use_gfx1250_triton_fp8`, and that class is only constructed when the flag is passed -- so a "+PR45304" arm without it measures plain BF16 and shows no change. Also discard the first run after a cold start; cold Inductor/aiter JIT costs roughly 8 s of denoise.

### Isolated A/B on one gfx1250

FLUX.2-dev, 720p, 100 denoise steps, seed 42, one gfx1250, `--enable-torch-compile true --attention-backend aiter`, all offload off. Runs serialized on an otherwise idle box, two repetitions each, no profiler attached.

| Metric | BF16 s/step | FP8 s/step | BF16 e2e | FP8 e2e |
|--------|-------------|-----------|----------|---------|
| rep 1 | 0.7553 | 0.5553 | 87.77 s | 64.13 s |
| rep 2 | 0.7569 | 0.5592 | 87.93 s | 64.45 s |
| mean | **0.7561** | **0.5573** | **87.85 s** | **64.29 s** |

**-26.3% per denoise step (1.357x), -26.8% end to end (1.367x).** Spread across repetitions is under 0.5%.

The row-major weight layout is a further **-5.3%** on top of that, measured the same way (3 reps each, same GPU, serialized, warm compile cache):

| s/step | rep 1 | rep 2 | rep 3 | mean |
|--------|-------|-------|-------|------|
| column-major weights | 0.5522 | 0.5523 | 0.5565 | **0.5537** |
| row-major weights | 0.5234 | 0.5288 | 0.5211 | **0.5244** |

A matched pair of profiles (same step count, same GPU) attributes -174 ms of GPU time over three steps to the GEMMs, against a total of -108 ms; GPU-busy time falls 1791.5 -> 1683.6 ms, which tracks the wall-clock change. Cumulative against BF16: **0.7561 -> 0.5244 s/step, 1.44x.**

These per-step figures are the host loop average (`[DenoisingStage] average time per step`), while the dashboard's Denoise column is `[DenoisingStage] finished in`, which includes the GPU tail drain and runs ~20% higher on the same run. Compare within a table, not across the two.
