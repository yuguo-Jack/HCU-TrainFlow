# [Fix] session: Keep refused and OOM-aborted streaming turns out of the session

[Upstream PR](https://github.com/sgl-project/sglang/pull/47752) · state: open · merged: False

## Original PR description

## Motivation

Two ways a streaming session ends up with the wrong owner or the wrong history. Neither needs a test hook to trigger. Each is a small fix, and both are about the same rule: only a turn that actually holds the session may change it.

**1. A refused turn frees a session that another turn is using.**

A turn that overlaps a running one is refused in `Session.create_req`, but it keeps `req.session`. When it is scheduled, `find_active_slot` treats it as an aborted turn of this session and calls `abort_req()`, which clears the running turn's `_inflight`. The next turn is then accepted while the running turn is still decoding, and two turns share one KV record.

On `main`, one running turn and two overlapping requests are enough: the first request gets 400, the second is accepted, and the server dies. Depending on timing the error is `session_id=... already has a slot`, `KV double free` or `KV page use-after-free`. #36503 proposed this fix and was closed by the idle bot, not rejected.

**2. An OOM abort in `retract_decode` is committed as if the turn had finished.**

`retract_decode` aborts the last request when it cannot fit even alone. This is easy to reach with streaming sessions, because idle sessions keep their KV in the slot and that KV cannot be evicted. The abort sets `to_finish` and then releases the turn, so `try_cache_finished_req` sees `finished_reason=None` and takes the finished path. The client gets a 500, but the partial output stays in the session and the next turn silently builds on it.

Real KV exhaustion on a CPU server, no `SGLANG_TEST_RETRACT`: pool of 1024 tokens, turn 1 is 12 + 6 tokens, a long turn 2 is squeezed by three idle sessions until it gets the 500, those sessions are closed, then a 10-token turn 3 runs.

| | turn 2 | turn 3 `prompt_tokens` (expected 28) | turn 3 output vs. a session that only saw turns 1 and 3 |
| --- | --- | --- | --- |
| `main` | 500 | 314 | different |
| This PR | 500 | 28 | same |

## Modifications

- `Session.create_req` detaches a refused streaming turn from the session. It never took the session, so it must not release it.
- `StreamingSession.try_cache_finished_req` also treats a pending `FINISH_ABORT` in `to_finish` as an abort, which is what its docstring already promises: the turn hands back the record and the session rolls back to its last finished turn. The turn is detached there as well, because an externally aborted turn can be retracted and requeued with `to_finish` set, and it must not act on the session again once a later turn owns it.
- Tests:
  - `test_session_token_share_unit.py`: `test_refused_turn_leaves_the_running_turn_in_charge` and `test_turn_aborted_on_retract_oom_is_not_carried_over`. Both fail on `main` and pass here.
  - `streaming_session_kit.py`: an end-to-end `test_refused_turn_leaves_the_running_turn_in_charge`. It needs no pause or retract.

### Relationship to #46275

This does not replace #46275 and does not touch the same lines. That PR keeps a turn retracted by `pause_generation` or memory pressure in flight, which is a separate bug that this PR leaves as it is. The two are complementary, and I ran both together:

| Differential fuzz, tracked client context | `main` | #46275 only | This PR only | Both |
| --- | --- | --- | --- | --- |
| Overlapping turns | crash | crash | clean | clean |
| Retract + overlapping turns | crash | crash | crash on 1 of 3 seeds | clean |
| Retract + abort | wrong context | clean | wrong context on 2 of 3 seeds | clean |
| Real OOM abort, turn 3 `prompt_tokens` (expected 28) | 314 | refused once, then 28 | 28 | 28 |

`main` and #46275 alone ran 2 seeds per row, the other two columns 3. #46275 was hand-ported onto current `main` for this, because `scheduler.py` and `streaming_session.py` have moved since it was opened.

One interaction matters for whichever lands second. With #46275 alone, an OOM abort in `retract_decode` leaves `_inflight` set, because `req.finished()` is false and nothing calls `abort_req()` afterwards. The next turn is refused once, and that refusal happens to clear `_inflight` through bug 1 above. If bug 1 is fixed without fix 2, the session stays refused forever, which I measured: `Streaming session already has an active request` on every later turn. With both fixes in this PR, that path never reaches the retracted branch, so the merge order does not matter.

### Not covered

- The other `retract_decode` abort branch, and the `unresumable` branch in `pause_generation`, set the abort after the release, so this check cannot see them. Outside PD they need an `input_embeds` turn on a session, which #40728 reports as crashing and #40745 proposes to reject. Inside PD they need decode-side retraction, which I cannot run on CPU.
- An automatic retract that is not an abort still commits the partial turn. That is the #46275 fix.

## Accuracy Tests

Not applicable to model outputs. The session behavior above was checked by comparing greedy session outputs against a single fresh request with the same context.

Everything here ran on CPU only, with a tiny random Qwen2 model on `torch_native`, `SGLANG_IS_IN_CI=1`, `SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY=1` and `SGLANG_CHECK_KV_PAGE_INVARIANTS=1`. I have not run this on GPU, so the kit test still needs CI.

- Unit: `test_session_token_share_unit.py` and `test_streaming_session_unit.py` pass (18 tests).
- Kit on a CPU server: the new test passes here and fails on `main`, where the server dies. `test_nth_mid_abort_recovery`, `test_first_mid_abort_recovery`, `test_preabort_recovery` and `test_kv_cache_inheritance` pass.
- Fuzz: each finished session turn is compared against a fresh request with the same context, and the client tracks the committed context exactly. This PR plus #46275: 21 of 21 runs clean across 7 configs, plus 6 of 6 with real client disconnects. This PR alone: clean on abort, overlap, plain and tree sessions (12 of 12) and on disconnects (6 of 6). Retract combinations remain as in the table above.
