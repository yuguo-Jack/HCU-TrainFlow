# [Feat] cp: Add KV layout hooks and padded storage accounting

[Upstream PR](https://github.com/sgl-project/sglang/pull/45434) · state: closed · merged: True

## Original PR description

## Motivation

Context-parallel compute and KV storage need separate choices. Padded, rank-local KV storage also needs capacity accounting that distinguishes logical tokens from physical rows.

## Modifications

Add a KV-layout registry and optional `cp_kv_layout` configuration, with explicit conversions at allocation, scheduling, cache-release, attention-metadata, and transfer boundaries. Replicated KV storage remains the default. Replay-token compute charging stays separate from KV reservation, and continuation prefixes are not counted again in cache-hit metrics.

This PR provides infrastructure only: it registers no concrete KV layout. A follow-up must supply a compatible layout factory before a layout can be selected through `--cp-kv-layout`.

> Seems this PR only contains basic infrastructure. Do we have the accuracy/perf result of how this instructure works with kv sharding + CP + unified memory?

Yes, this PR adds the infrastructure only. We ran a small GSM8K accuracy comparison of sharded KV with CP=2 against CP off. This PR does not ship a padded layout, so the run used a downstream implementation that registers its padded layout through the layout registry added here, rather than this PR alone.

Setup, identical for both runs except the prefill CP settings:
- Model: Qwen3-8B (full attention only).
- GSM8K, 5-shot, all 1319 test questions, temperature 0, max 512 new tokens; the same questions, prompts and labels in both runs.
- Prefill/decode disaggregation with decode TP1. Prefill TP2 with CP off, versus prefill TP2 with CP2 (attention TP1) and the padded sharded-KV layout.
- One run per configuration. Radix cache, CUDA graphs and unified memory were disabled.

| Configuration | GSM8K accuracy |
|---|---|
| CP off | 1185/1319 = 89.84% |
| CP2, sharded KV | 1187/1319 = 89.99% |

That is +2 questions (+0.15 points). 18 answers differ between the runs (6 correct only with CP off, 8 correct only with CP2, 4 wrong in both); an exact McNemar test gives p = 0.79, so this comparison shows no measurable accuracy difference.

This does not cover performance: the evaluation times (1134.5 s and 1159.6 s) come from these correctness runs, not from a throughput benchmark. It also does not cover unified memory, which was not enabled.

- ZYHowell · comment · 2026-10-29T08:57:16Z · [source](https://github.com/sgl-project/sglang/pull/45434#discussion_r4410379216)

File: `python/sglang/srt/layers/cp/base.py` · line 255

Existing `page_interleave` allows different page utilization across ranks and coordinates eviction using each rank's remaining page count. With unified memory, counts alone are insufficient: eviction also depends on compaction opportunities and whether free pages at pool boundaries can be transferred between components without compaction.

This PR uses padded page interleaving so every memory operation changes the same number of pages on each rank, preserving consistent memory state across ranks. It is implemented at the scheduler/radix-tree level for future unified-memory support, since unified memory has its own allocator.

Enabling `--enable-kv-cache-sharding` together with `--cp-kv-layout` is now rejected at initialization when prefill CP is active: https://github.com/sgl-project/sglang/blob/539b85daaa7f5d0cecfd1e54a04c370125705663/python/sglang/srt/arg_groups/kv_shard_hook.py#L176-L180
