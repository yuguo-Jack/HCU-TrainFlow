# [Feat] routed-experts: routed_experts_start_len=-1 returns one row per generated token

[Upstream PR](https://github.com/sgl-project/sglang/pull/48255) · state: open · merged: False

## Original PR description


## Motivation

RL clients that replay MoE routing (R3) usually want one routed-experts row per generated token: the rows for the prompt either came with an earlier turn or are not trained on. `routed_experts_start_len` lets a client crop the response to `[start_len, seqlen - 1)`, but the client must pass the exact prompt length minus one. For multimodal prompts it cannot: the scheduler expands each image or video placeholder into many tokens, and the client never sees the expanded length.

`-1` mirrors `logprob_start_len=-1`. An explicit boolean (e.g. `routed_experts_generated_only`) was considered; the sentinel keeps one field and one contract.

This PR includes the one-line reset from "[Fix] routed-experts: reset routed_experts_start_len when a request is rejected at intake" (a separate PR for an existing crash): without it, a `-1` request rejected at intake would stop the scheduler. The hunk is identical, so the two merge in either order.

## Modifications

- `Scheduler.handle_generate_request`: `routed_experts_start_len=-1` resolves to `len(req.origin_input_ids) - 1`, the prompt length after multimodal expansion. The response then has one row per generated token. Values below -1 are rejected as before (message updated).
- `Req.set_finish_with_abort`: reset `routed_experts_start_len` to 0, next to the existing `logprob_start_len` reset. Every intake rejection goes through it, so a rejected request no longer reaches `get_topk` with a negative start. The duplicate reset in the routed-experts check is removed.
- `GenerateReqInput` comment and the `sampling_params` / OpenAI API docs describe `-1`.
- Tests:
  - `test/registered/rl/test_return_routed_experts.py::TestRoutedExpertsStartLen`: `-1` returns `completion_tokens` rows equal to the tail of the full response; `-2` is rejected; a request rejected at intake with `-1` leaves the server serving.
  - `test/registered/unit/managers/test_req_finish_state.py`: `set_finish_with_abort` resets both start lengths (CPU).

## Accuracy Tests

GB300 runs use `--moe-runner-backend triton`: the default MoE runner there (`flashinfer_trtllm`) returns placeholder routed-experts rows today, which open PRs #47524 and #42395 address. With placeholder rows every row comparison would pass trivially.

Multimodal (the case `-1` exists for): 1x GB300, `Qwen/Qwen3-VL-30B-A3B-Instruct`, `--enable-return-routed-experts --enable-deterministic-inference --moe-runner-backend triton`, `/v1/chat/completions` with one 448x336 image and a short question. The text alone is 15 prompt tokens; with the image the scheduler expands it to 157. `routed_experts_start_len=-1` returned 24 rows for 24 generated tokens, equal to rows `[156:]` of the full response (180 rows), with the same text. On main the request is rejected (HTTP 400).


`Qwen/Qwen3-30B-A3B`, TP1, `--enable-return-routed-experts --enable-deterministic-inference`, baseline `8d4e1ce4c7` and this PR on the same GPU in the same container. 1x H100 80GB (default MoE runner) and 1x GB300 (`--moe-runner-backend triton`).

| Check | upstream main | this PR |
|---|---|---|
| Default path (`start_len` unset): output ids and routed-experts rows of 6 prompts x 24 greedy tokens, single and batched (12 requests) | reference | byte-identical on H100 and GB300 |
| `start_len=-1`, 3 prompts | HTTP 400 | rows = `completion_tokens` (24), equal to rows `[prompt_tokens - 1:]` of the full response; same tokens |

`TestRoutedExpertsStartLen` on 1x GB300 node (TP2, as registered): the 3 new tests pass on this PR. On upstream main they fail and the server is gone after the intake-abort test. `test_start_len_with_cache_hit` fails on both, before and after this PR, on this setup: `--enable-deterministic-inference` turns off the radix cache there, so `cached_tokens` is 0.

No model-output change: the default path is byte-identical, and `-1` only selects rows.
