# [Perf] [AMD] batch-invariant: Tune the bf16 matmul for gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/44045) · state: open · merged: False

## Original PR description

## Motivation

This PR speeds up deterministic inference on MI350X/MI355X (gfx950): about 6% more throughput with 1k-token inputs and about 1.5% with 8k-token inputs. It gives the batch-invariant bf16 matmul a launch configuration tuned for gfx950.

With `--enable-deterministic-inference`, every linear layer goes through the persistent batch-invariant Triton matmul (`_matmul_persistent_triton`). That kernel uses one bf16 configuration on every GPU (128x128x64 tiles, 3 stages, 8 warps), with no AMD-specific options. On gfx950, a 128x64x128 tile with 16-wide MFMA instructions is up to 2x faster at decode batch sizes.

The configuration is still fixed for every M, so each output element keeps the same reduction order whatever the batch: batch invariance is unchanged.

## Modifications

- `batch_invariant_ops.py`: on gfx950 only, the bf16 entry becomes `BLOCK_SIZE_M=128, BLOCK_SIZE_N=64, BLOCK_SIZE_K=128, GROUP_SIZE_M=8, num_stages=3, num_warps=8, matrix_instr_nonkdim=16`.
  - It needs about 147 KB of LDS, so it is limited to gfx950 (160 KB).
  - Other GPUs, fp16/fp32 and the non-deterministic path are unchanged.
  - In deterministic mode every unquantized bf16 linear layer (`aten::mm`/`addmm`) runs this kernel on ROCm, so the change applies to any bf16 model. Quantized layers, MoE experts (Triton MoE runner) and attention don't use it.
- Chosen from a sweep of about 2,900 configurations on MI350X, each checked bitwise for batch invariance.
- The launch configurations are now built by a small helper, `_matmul_persistent_configs()`, and a new CPU test (`test/registered/unit/batch_invariant_ops/test_matmul_persistent_configs.py`, `base-a-test-cpu`) guards the preset: on gfx950 the bf16 entry must be exactly this configuration and fit gfx950's 160 KB of LDS, and on other GPUs it must stay the original one.

## Accuracy Tests

MI350X, `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261012` with this change applied, Qwen3-8B BF16, TP1, `--attention-backend triton --enable-deterministic-inference`, `SGLANG_USE_AITER=0`:
- `python3 -m sglang.test.test_deterministic --test-mode prefix --return-logprob` and `--test-mode radix_cache` (50 trials): pass.
- Bitwise comparison of 1,275 responses (batch sizes 1-50) against batch size 1: 1275/1275 token IDs and log-probabilities identical.
- `test/registered/unit/batch_invariant_ops/test_batch_invariant_ops.py`: 6 passed, 54 subtests, before and after (also with the helper refactor).
- `test_matmul_persistent_configs.py`: 2 passed (2 failed on the code before this PR, which has no helper).

## Speed Tests and Profiling

- aarnetalman · comment · 2026-10-19T08:00:57Z · [source](https://github.com/sgl-project/sglang/pull/44045#issuecomment-6262533887)

@HaiShaw Good question. I checked the preset on 19 layer shapes it was not tuned on (Llama 3.1 8B and 70B TP8, Phi-4, gpt-oss-20b, Qwen3-30B-A3B, Qwen3-8B TP8, three LM heads), M = 1-8192, against the default config on MI350X:

| | Decode (M <= 256) | Prefill (M >= 512) |
| --- | --- | --- |
| Tuned-on shapes (Qwen3-8B) | 1.81x | 1.03x |
| 19 untuned shapes | 1.54x | 1.03x |

The gain is structural: at decode the output has N / BLOCK_N tiles, and the default 128-wide N tile leaves most of MI350X's 256 CUs idle; the preset's 64-wide tile doubles them. So it holds for any layer up to N ~ 8k (1.58-1.89x at decode). It does not help very wide layers, which already fill the GPU: Llama 3.1 8B gate_up (N = 28,672) 0.94x, LM heads 0.97-1.02x. Every shape stayed batch-invariant, and the preset only applies to bf16 on gfx950.
