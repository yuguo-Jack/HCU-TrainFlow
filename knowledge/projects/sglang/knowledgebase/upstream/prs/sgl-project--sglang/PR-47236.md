# [Perf] [AMD] moe/topk: Use the Triton softmax top-k router for Qwen3-Next (hidden 2048)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47236) · state: closed · merged: True

## Original PR description

## Motivation

`_use_rocm_triton_softmax_topk` in `python/sglang/srt/layers/moe/topk.py` selects the Triton softmax router over AITER `aiter_fused_topk` on gfx950 for decode-sized rows. #39986 scoped it to the Qwen3.5 envelope it measured, which includes `hidden_states.shape[1] == 4096`.

Qwen3-Next-80B-A3B has the same router shape that the rest of the envelope checks: 512 experts, top-10, bf16 logits, no correction bias, no fused shared-expert slots and no packed output. Only its hidden size differs, 2048, so its decode router never reaches the Triton path. The hidden size does not enter the router computation: the Triton router reads only `gating_output`, and `hidden_states` contributes its row count.

## Modifications

- `topk.py`: accept hidden size 2048 as well as 4096. Every other condition, including the 128-row limit and the gfx950 requirement, is unchanged.
- `test/registered/amd/test_qwen35_moe_softmax_topk.py`: `test_triton_dispatch_matches_aiter` now runs at hidden 2048 and 4096; on main the 2048 cases reach AITER and fail the test's bypass assertion. `test_dispatch_envelope_is_narrow` accepts 2048 and still rejects a width outside the measured set (3072).

## Accuracy Tests

The router change does not alter which experts are chosen. `test_qwen35_moe_softmax_topk.py` on MI355X (gfx950), torch 2.11.0+rocm10.0.0:

| code under test | result |
|---|---|
| main `58214f6` | 4 failed, 1 passed, 3 subtests passed: every hidden-2048 case raises `AITER top-k should be bypassed`, and the envelope test rejects 2048 |
| this PR | 2 passed, 6 subtests passed: expert ids identical to `aiter_fused_topk` and weights within 1e-5 at 4, 12 and 128 rows for hidden 2048 and 4096 |

A Qwen3-Next-80B-A3B-Instruct-FP8 server (TP2) started from this branch takes the Triton router at every decode-sized batch it captures (1 to 128 rows, both ranks) and keeps AITER above 128 rows.

GSM8K, all 1319 questions, through sgl-eval 0.1.3 against the same TP2 server. sgl-eval has no preset for this model, so the model card's recommended sampling was passed explicitly: `--temperature 0.7 --top-p 0.8 --max-tokens 16384`, with `--seed` 0, 1 and 2 for each arm:

| seed | main | this PR |
|---:|---:|---:|
| 0 | 96.13% | 95.98% |
| 1 | 95.98% | 95.91% |
| 2 | 96.13% | 95.91% |
| mean | 96.08% | 95.93% |

The 0.15-point gap is two questions out of 1319, inside the ±0.5-point standard error of a single run at this score, and both arms sample at temperature 0.7, so this shows no regression rather than a measurable difference. The router change selects the same experts as AITER in the unit test and the microbenchmark below.

## Speed Tests and Profiling

Router microbenchmark on MI355X (gfx950), both arms through `topk.fused_topk` with only the dispatch predicate differing, per-call device time under CUDA graph replay with 50 calls captured per graph; 512 experts, top-10, bf16:

| rows | AITER (us) | Triton (us) | speedup | expert ids equal |
|---:|---:|---:|---:|---|
| 1 | 9.539 | 4.869 | 1.96x | yes |
| 2 | 9.370 | 5.074 | 1.85x | yes |
| 4 | 8.620 | 5.092 | 1.69x | yes |
| 8 | 8.961 | 5.063 | 1.77x | yes |
| 16 | 9.471 | 5.106 | 1.85x | yes |
| 32 | 9.309 | 5.089 | 1.83x | yes |
| 64 | 9.773 | 5.122 | 1.91x | yes |
| 128 | 9.900 | 5.169 | 1.92x | yes |

That is hidden 2048. The same benchmark at hidden 4096, the Qwen3.5 shape #39986 enabled, gives 1.74x to 1.97x with the same median, 1.85x, which is what you expect when the hidden size never enters the router.

End to end: `sglang.bench_serving` on Qwen3-Next-80B-A3B-Instruct-FP8, MI355X, TP2, random 1024 in / 1024 out, a fresh server per block in the order main, PR, PR, main, four runs per block with the first discarded; each block reports the median of runs 2 to 4, and each arm averages its two blocks:

| concurrency | metric | main | this PR | change | main block-to-block | PR block-to-block |
|---:|---|---:|---:|---:|---:|---:|
| 16 | output tok/s | 2292.4 | 2354.3 | +2.70% | 0.62% | 0.16% |
| 16 | median TPOT (ms) | 6.73 | 6.55 | -2.56% | 0.25% | 0.15% |
| 16 | median TTFT (ms) | 298.1 | 296.1 | -0.66% | 1.30% | 1.19% |
| 64 | output tok/s | 5507.0 | 5601.2 | +1.71% | 0.31% | 0.04% |
| 64 | median TPOT (ms) | 10.98 | 10.77 | -1.92% | 0.24% | 0.15% |
| 64 | median TTFT (ms) | 613.1 | 607.5 | -0.91% | 1.22% | 0.34% |

The throughput and TPOT changes are several times the drift between the two blocks of the same arm; TTFT moves less than that drift, as expected for a change that only touches decode-sized batches. TP2 rather than the cookbook's TP8 because the measurement used two GPUs.
