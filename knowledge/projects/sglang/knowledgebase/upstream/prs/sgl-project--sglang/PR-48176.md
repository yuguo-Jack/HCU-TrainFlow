# [CI] rerun-test: Retry diffusion reruns like the multimodal-gen CI

[Upstream PR](https://github.com/sgl-project/sglang/pull/48176) · state: closed · merged: True

## Original PR description

## Motivation

`/rerun-test` on a diffusion test can fail on noise that the multimodal-gen CI job would have retried past.

The CI jobs run pytest through `sglang.multimodal_gen.test.runner.pytest_runner.run_pytest`. It retries failed items up to 6 times when the failure is retryable: a `[performance]` check, a timeout, an OOM. It stops starting new retries once `SGLANG_DIFFUSION_RETRY_DEADLINE` is reached. The `rerun-test-multimodal-gen` job runs bare `python3 -m pytest $cmd -x` instead, with no retry. That breaks the workflow's own goal ("so a rerun validates what CI actually ran"). CUDA reruns already retry once, through `CustomTestCase` with `SGLANG_IS_IN_CI`.

The timing checks in this suite are noisy. On main's scheduled runs of `multimodal-gen-test-2-gpu` since 10-12, at least one attempt failed a timing check in 37 of 45 runs, spread across 22 cases. The retry absorbed every one: none of the 6 job-level failures in that window came from a timing check.

Example: #47962 changed only the `ltx_2_two_stage_t2v` VRAM baseline. Two `/rerun-test` runs of `test_server_2_gpu.py` failed on unrelated LTX-2.3 timing checks:
- `ltx_2.3_one_stage_ti2v` TextEncodingStage: 789 ms against a 718 ms limit ([run](https://github.com/sgl-project/sglang/actions/runs/41556835219)).
- `ltx_2.3_two_stage_t2v_2gpus` E2E: 9389 ms against an 8158 ms limit ([run](https://github.com/sgl-project/sglang/actions/runs/41572697032)).

A third rerun, narrowed to just `ltx_2_two_stage_t2v`, passed.

## Modifications

In `rerun-test-multimodal-gen`'s "Run test" step:
- Run each command through `run_pytest` (with a JUnit file, so the deadline check can estimate how long the failed items take) instead of `python3 -m pytest $cmd -x`.
- Set `SGLANG_DIFFUSION_RETRY_DEADLINE` to 50 minutes from the step's start, as `pr-test-multimodal-gen.yml` does. The step timeout is 60 minutes. A whole-file rerun of `test_server_2_gpu.py` takes about 60 minutes on its own, so it gets no retries, as today. Narrower reruns get them.
- Drop `-x`, matching CI. With retries, `-x` would also be wrong: the retry pass runs only the last-failed items, so items after the first failure would never run.

Consistency-check failures (missing or mismatched ground truth) and other non-retryable failures still fail on the first attempt, as in CI.

## Testing

I ran the new command locally on dummy tests. In the test harness only, the import pointed at a copy of `pytest_runner.py`, since importing the `sglang` package needs torch.
- A `[performance]` failure that passes on its second run: exit 0 after one retry, and the other tests in the file still ran once.
- A plain `AssertionError`: exit 1, no retry.
- An expired deadline: exit 1, "Retry budget exhausted".
- The old `pytest -x` on the same file: exit 1, and the tests after the failure never ran.

A real check needs a `/rerun-test` of a diffusion test once this is on main, since the workflow runs from the default branch.

- mickqian · comment · 2026-11-04T03:16:29Z · [source](https://github.com/sgl-project/sglang/pull/48176#issuecomment-6621571023)

My concern is that a lot of the variability comes from differences between runners, rather than noise between attempts. Diffusion reruns can land on different runners, and we have seen substantial performance differences even within the same GPU class.

Since these automatic retries stay within the same job, they will keep using the same runner. If that runner is consistently slower than the one used to establish the baseline, all retries may still fail, leaving us manually triggering `/rerun-test` repeatedly until the job lands on a faster runner. A green result would then depend on placement rather than the code change.

I understand this PR aligns `/rerun-test` with the retry behavior already used by regular CI. But could we also address runner comparability? Otherwise, I worry that many diffusion performance checks will still require multiple manual reruns, with the automatic retries adding runtime without resolving the underlying issue.

@mickqian agreed: retries can't rescue a slow runner, because every retry stays on the same host. This PR has a narrower aim. It makes `/rerun-test` match the retry regular CI already does, so a rerun doesn't fail on a single noisy attempt that regular CI would have retried.

#48256 just gave a concrete example of the runner problem. On `b200-cirrascale2`, Qwen nvfp4 per-step denoise varied from 385 to 490 ms across 7 attempts in one job, against 317–334 ms in that host's history. Retries didn't help there.

Opened #48311 for runner comparability, with that data and the 5090 data from #48196. If you'd rather not add retries to `/rerun-test` until that's resolved, I'm fine closing this.
