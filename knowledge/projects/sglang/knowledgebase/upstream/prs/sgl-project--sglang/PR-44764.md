# [Feat] rust-server: Report Python's launch-time /server_info fields from the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44764) · state: closed · merged: True

## Original PR description

## Motivation

Python's `/server_info` returns every resolved `server_args` field, `launch_command`, the scheduler's init info, `kv_events` and the startup timings. The Rust frontend returned an allowlisted handful, so a client that reads launch configuration off `/server_info` (for example `load_format` or `startup_time`) fails with a missing key as soon as the server runs in Rust mode.

## Modifications

- At launch the scheduler hands the Rust server the `/server_info` fields that are fixed by then, as one JSON snapshot built with Python's own `build_server_info` and redacted with the same `redact_watermark_secrets` the HTTP and gRPC frontends apply: the resolved `server_args`, `launch_command`, `kv_events`, and `status`, `max_total_num_tokens` and `max_req_input_len` (`rust_server/config.py`, `_launch_server_info`; carried as a new `launch_server_info` field of the typed `ServerArgs` handoff, extracted into a `LaunchServerInfo` JSON object).
- The Rust `/server_info` reports the snapshot beneath its runtime fields, which take precedence on a shared key, so the key set matches Python's apart from Rust's own `max_context_length`. The scheduler's internal state in `internal_states` keeps its existing allowlist. The native gRPC `GetServerInfo` is unchanged.
- `enable_http2` is reported false whatever the flag says: the Rust listener is HTTP/1 only and a router reads that key to pick its protocol.
- `startup_time` takes Python's engine-level shape (`load_weight`, `kv_cache_allocation`, `scheduler_e2e`, `cuda_graph`, `tokenizer_e2e`). Python's `tokenizer_e2e` runs from launch until the schedulers are ready; the Rust frontend serves from inside the scheduler process, so its phase runs from that process's spawn until initialization ends. The scheduler records it once initialization ends (`RustServer.set_startup_time`), it reaches Rust through the internal state `/server_info` already requests (`rust_server_startup_time`), and the HTTP response lifts it to the top level.
- Not covered: `tokenizer_path` stays the Rust server's own value, `kv_event_sources` (native gRPC only) is only known after the Rust server starts, and the timings are those of the scheduler hosting the listener rather than a maximum over every rank.

Tests:
- `rust/`: `cargo fmt --all -- --check` and `cargo clippy --locked -p sglang-server --all-targets -- -D warnings` are clean; `cargo test --locked -p sglang-server`: 330 passed, 1 failed. The failure is `message::response::tests::chunk_event_frame_stays_small`, a `size_of::<ChunkEvent>()` bound this branch does not touch; it fails identically on a clean checkout of `main` on the aarch64 host the tests ran on.
  - `server_info_route_serializes_only_the_typed_public_subset` (extended): the launch fields come first in order, a runtime field replaces a launch field in place, the internal state's startup timings move to the top-level `startup_time`, and the internal-state allowlist still drops `api_key`.
- `test/registered/unit/entrypoints/test_server_info.py` (`test_http_and_both_grpc_roles_share_startup_metadata` now also checks that the Rust snapshot equals the gRPC leader's startup metadata apart from the two stamped init-info keys, and that it reports `enable_http2` false for a server launched with `--enable-http2`), `test/registered/unit/multimodal/rust/shared/test_rust_server_extension.py` (new `test_startup_time_takes_the_engine_shape`) and `test/registered/unit/entrypoints/test_rust_server_dp_ports.py`: 53 passed, 14 subtests.
