# [Fix] ngram: Wire SGLANG_NGRAM_FORCE_GREEDY_VERIFY back into NGRAM verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44147) · state: open · merged: False

## Original PR description

## Motivation

Closes #43931.

`SGLANG_NGRAM_FORCE_GREEDY_VERIFY` is still registered in `environ.py` and referenced from the speculative decoding docs, but nothing consumes it anymore. NGRAM verify read the flag in `ngram_info.py` back in #13153; the read was lost when NGRAM verify moved onto the shared `eagle_sample()` helper, so setting the env var today has no effect.

## Modifications

- `eagle_sample()` gains a keyword-only `force_greedy_verify` (default `False`); when set, the greedy predicate treats the batch as all-greedy.
- The NGRAM call site passes `envs.SGLANG_NGRAM_FORCE_GREEDY_VERIFY.get()`. EAGLE and the other callers keep the default, so their acceptance behavior is unchanged.
- New unit test `test_ngram_force_greedy_verify.py` pins the plumbing at the predicate seam: flag on forces the greedy branch for a mixed batch, flag off preserves batch semantics, an already all-greedy batch is unaffected either way.

## Accuracy Tests

Default-path behavior is unchanged when the flag is unset; with the flag set, NGRAM verify selects the existing greedy branch instead of the sampling one. No GPU on this machine, so I ran the new unit test on CPU (3 passed) and left end-to-end output comparison to CI.

## Speed Tests and Profiling

N/A: one env lookup per NGRAM verify call, no kernel or hot-path changes.

- he-yufeng · comment · 2026-10-28T22:18:31Z · [source](https://github.com/sgl-project/sglang/pull/44147#issuecomment-6482103652)

Re-checked the flag semantics and its conventions against `Envs`, since this is the one thing that could make the fix wrong even when the wiring is right.

`SGLANG_NGRAM_FORCE_GREEDY_VERIFY = EnvBool(False)` is already registered in `python/sglang/srt/environ.py`, and this PR does not add or rename a key. It reads the value through `envs.SGLANG_NGRAM_FORCE_GREEDY_VERIFY.get()`, so no raw `os.getenv` or `os.environ` enters the path. Opt-in default, boolean typed, existing name kept.

The behaviour is the one the name claims: `_verify_uses_greedy` decides whether verify commits argmax rather than taking the sampling path, and this folds the flag into that predicate as `sampling_info.is_all_greedy or force_greedy_verify`. EAGLE callers never pass the kwarg, so they keep the default `False` and their predicate is byte-for-byte the old one.

Two small things I am flagging rather than hiding. The folded value goes into the `is_all_greedy` parameter, so that parameter now means "the schedule is greedy or the operator forced it"; if anyone would rather see a separate `force_greedy` argument on `_verify_uses_greedy` I am happy to widen it. And the helper's docstring still says "Whether EAGLE verify must commit argmax", which was already stale once NGRAM started reaching it through the shared `eagle_sample` helper, not something this PR introduces; I left it alone to keep the diff to the wiring.

The test pins the plumbing at the predicate seam rather than asserting a kernel outcome, which is the part that regressed, and it registers CPU CI through `register_cpu_ci` so it runs without a GPU.
