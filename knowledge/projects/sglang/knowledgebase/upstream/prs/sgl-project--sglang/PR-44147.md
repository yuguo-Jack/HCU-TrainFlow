# [Fix] Wire SGLANG_NGRAM_FORCE_GREEDY_VERIFY back into NGRAM verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44147) · state: open · merged: False

## Original PR description

## Motivation

Closes #43931.

`SGLANG_NGRAM_FORCE_GREEDY_VERIFY` is still registered in `environ.py` and referenced from the speculative decoding docs, but nothing consumes it anymore. NGRAM verify read the flag in `ngram_info.py` back in #13153; the read was lost when NGRAM verify moved onto the shared `eagle_sample()` helper, so setting the env var today has no effect.

## Modifications

- `eagle_sample()` gains a keyword-only `force_greedy_verify` (default `False`); when set, the greedy predicate treats the batch as all-greedy.
- The NGRAM call site passes `envs.SGLANG_NGRAM_FORCE_GREEDY_VERIFY.get()`. EAGLE and the other callers keep the default, so their acceptance behavior is unchanged.
- New unit test `test_ngram_force_greedy_verify.py` pins the plumbing at the predicate seam: flag on forces the greedy branch for a mixed batch, flag off preserves batch semantics, an already all-greedy batch is unaffected either way.

## Accuracy Tests

Default-path behavior is unchanged when the flag is unset; with the flag set, NGRAM verify selects the existing greedy branch instead of the sampling one. No GPU on this machine, so I ran the new unit test on CPU (3 passed) and left end-to-end output comparison to CI.

## Speed Tests and Profiling

N/A: one env lookup per NGRAM verify call, no kernel or hot-path changes.
