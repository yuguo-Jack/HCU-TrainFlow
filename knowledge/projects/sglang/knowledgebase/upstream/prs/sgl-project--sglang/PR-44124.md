# [Fix] Preserve structured values in qwen3_coder mixed unions

[Upstream PR](https://github.com/sgl-project/sglang/pull/44124) · state: open · merged: False

## Original PR description

## Motivation

Closes #44120

When a tool parameter allows a string or an object, `qwen3_coder` treats the model's object JSON as a string. After one decode of `function.arguments`, callers get `{"location": "{\"city\": \"Paris\"}"}` instead of `{"location": {"city": "Paris"}}`. String/array unions have the same problem, including streamed responses.

This can affect any model using `--tool-call-parser qwen3_coder`. The string result is schema-valid, but it loses the structured value emitted by the model.

Related work: [#30832](https://github.com/sgl-project/sglang/pull/30832) added nullable-array support, and [#36626](https://github.com/sgl-project/sglang/pull/36626) fixed top-level schema property lookup. This addresses a separate case: a known parameter whose own union allows both strings and structured values.

## Modifications

In the detector's existing string conversion branch, check `anyOf`/`oneOf` parameters for complete object or array JSON. Keep the decoded value only when it satisfies the parameter schema.

Plain strings, scalar unions, malformed JSON, values that do not match the schema, and unresolved references keep their existing behavior. Schema validation does not fetch external references.

This intentionally prefers an allowed object or array when mixed-union text could also be read as a string. String-only parameters still keep JSON-looking text as strings.

The change is limited to the Qwen3-Coder detector and its existing registered tests. The shared inference helper, other detector implementations, public APIs, and dependency lists are unchanged. `step3p5` and `nanbeige` also use this detector and receive the same behavior. Type arrays and root-level reference resolution are outside this fix.

## Accuracy Tests

Does not change kernel or affect model forward code, but does affect structured output correctness.

- Verified the regression on native v0.5.21 before the fix: 24 structured-value subtests failed at the expected assertions.
- With the fix on v0.5.21, all 20 Qwen3-Coder tests and 60 subtests pass. Coverage includes complete parsing, one- and seven-character streaming chunks, both union types and branch orders, objects/arrays, schema constraints, and string compatibility.
- Replayed six outputs captured from the live v0.5.21 Qwen3-Coder server through complete and streaming parsing. All three previously lost objects stay objects; the genuine date string and both object-only controls keep their values and types.
- A live patched v0.5.21 server using Qwen3-Coder-30B-A3B-Instruct (BF16, TP1, one B200) passed health, model listing, deterministic chat, and all 12 tool requests, including three streams. Object/array unions stay structured after one arguments decode; object-only, string-only JSON text, and numeric/string controls pass.
- Changed executable production lines have 100% coverage (11/11).

Validation used `lmsysorg/sglang:v0.5.21` (digest `sha256:b1259f3ea3275f66237c498ea388919729018bc9f01c3d638391e06e2cf3f469`). Baseline raw-output logging left conversion unchanged; the patched serving run installed only the exact candidate detector. The regression tests ran against the native runtime without adding compatibility modules.

The full original detector and relevant type-inference function are byte-identical to main (`7dc2930585782c09630d617a510bec08c1724845`), so I didn't run a separate test on main. 

These checks were only for parser correctness; no general model accuracy benchmark was run.

## Speed Tests and Profiling

No speed benchmark was run. This adds JSON parsing for string-inferred `anyOf`/`oneOf` parameters, followed by schema validation when the decoded value is an object or array. Model execution and decoding kernels are unchanged.

**Issue**

This `except` catches only `JSONDecodeError` and `Unresolvable`, so other errors from `is_valid()` now escape `_convert_param_value`. Before this PR, the string branch could not raise.

**Example**

`{"anyOf": [{"type": "string"}, {"$ref": "#"}]}` passes `check_schema` in `serving_chat.py`. When the model emits an object for it, `is_valid()` raises `RecursionError`. `detect_and_parse` then drops the tool call and returns the raw `<tool_call>` text as content, and `parse_streaming_increment` raises. The Responses API skips `check_schema`, so `"type": "map"` (`UnknownType`) or draft-07 tuple `items` (`AttributeError`) also fail this way.

**Fix**

Catch `Exception` here and return `param_value`, like the other branches in this function. Add the `$ref: "#"` case to `test_structured_union_conversion_requires_schema_match`.

[by Claude Code] **Severity: functional | Confidence: Medium**

**Issue**

The validator uses the property schema as its root, so `$ref` resolves against the property, not the tool's `parameters`. A `$ref` into the root `$defs` always raises `Unresolvable`, and the object stays a string. The PR description scopes this out, but it is how Pydantic emits model unions.

**Example**

Pydantic turns `str | Location` into `{"anyOf": [{"type": "string"}, {"$ref": "#/$defs/Location"}]}`, with `$defs` at the root. With this PR, `{"city": "Paris"}` still comes back as the string `"{\"city\": \"Paris\"}"`, the bug in #44120.

**Fix**

Pass the tool's `parameters` to `_convert_param_value` and validate with `Draft202012Validator(parameters, registry=Registry()).evolve(schema=schema)`. This also makes `#` point to the right schema. Add a root-`$defs` test case.
