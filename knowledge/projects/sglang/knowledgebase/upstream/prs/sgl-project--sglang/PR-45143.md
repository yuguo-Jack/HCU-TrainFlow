# [Perf] function_call: stop rescanning unclosed GLM tool calls per chunk

[Upstream PR](https://github.com/sgl-project/sglang/pull/45143) · state: open · merged: False

## Original PR description

## Motivation

GLM-4.5/4.6 (`Glm4MoeDetector`) and GLM-4.7/GLM-5 (`Glm47MoeDetector`) already stream args incrementally, but on every chunk they run the streaming regex over the whole buffer again, just to get the name and the args so far. So one long arg (like `write_file` content) costs O(n²). Profiling a 16k-char arg with 4-char deltas, `re.Pattern.search` is 85-87% of the time.

## Modifications

While a call is still open, the buffer only grows at the end, so the name and where the args start can't change. `_match_tool_call` remembers them after the first match, and after that only looks for `</tool_call>` (or `$`) in the new tail. It returns exactly what the call site used to read from the match, so the rest of `parse_streaming_increment` is untouched. The cache is dropped once the closer shows up.

+27/-5 and +34/-10, plus one test per detector.

## Why the output is the same

- The cache only exists while the call is open, and during that time `_buffer` is only appended to. It only gets reassigned when the closer is found, or when there's no `<tool_call>` in it, which can't happen while a call is open.
- Appending can't move the match start or the name. The name ends at the first `\n` or literal `\\n` (GLM-4.5), or the first `<arg_key` (GLM-4.7), and those are already in the buffer.
- The args end at the first `</tool_call>` or `$`. The old buffer had no closer after the args start, so a new one has to end in the new text. Scanning from `len(old) - len("</tool_call>") + 1` is enough.

## Testing

- Fuzzed against `main`: 25k random streams per detector. Half look like real calls (multiple calls, `\n` / `\\n` / no separator, empty names, unclosed calls, tag pieces inside values), half are random tag pieces, newlines and text. Chunk sizes 1-40. I compared every chunk's result, `finish()`, and all detector state. No diffs. To check the fuzzer itself, I broke the patch three ways (no tail overlap, overlap one char short, never clearing the cache), and each one fails within the first few cases on both detectors.
- New `test_streaming_long_argument_is_not_rescanned` for both: a 4000-char arg in 3-char chunks runs the streaming regex once, and the args come out right.
- `TestGlm4MoeDetector`, `TestGlm47MoeDetector`, `TestGlm47FullAssistantGrammar`, `test_glm47_schema_types.py`: no new failures.

## Benchmark

One long string arg, 4-char deltas:

| detector | chars | main | this PR |
|---|---|---|---|
| GLM-4.5 | 32,000 | 3.93s | 0.15s |
| GLM-4.5 | 128,000 | 59.30s | 0.99s |
| GLM-4.7 | 32,000 | 5.91s | 0.15s |
| GLM-4.7 | 128,000 | 88.41s | 1.15s |

What's left per chunk is plain string copying (`_buffer += new_text`, slicing the args, `_current_value += char` in the XML-to-JSON state machine). It still grows with the arg, but at memcpy speed. I kept it out of this PR to keep it small.
