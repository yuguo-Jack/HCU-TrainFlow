# [unified-memory] Stop allocation eviction on the joint FULL/SWA fit

[Upstream PR](https://github.com/sgl-project/sglang/pull/43169) · state: closed · merged: False

## Original PR description

Superseded by #39294 (`ee30dc4d40`), now on main. The rebased unified-memory stack uses main's bounded joint-reclaim implementation; this PR is no longer a dependency. Current stack: #43326 and #44973.

## Motivation

On the unified FULL/SWA pool (`--enable-unified-memory` with a hybrid sliding-window model) every cached token holds bytes on both sides, and the allocator's reclaim plan counts the same shared bytes once per side. `UnifiedRadixCache.evict_for_alloc` used to stop once each side's available view reached its own target, so the same freed bytes satisfied both targets and eviction stopped short: the allocation raised "Out of memory" with evictable cache left (on MiMo-V2-Flash geometry, an ask of 335 tokens needing 18.65 MB stopped after 288 evictions with 16.07 MB free and 2,255 tokens still evictable).

#39479 made `evict_to_free_tokens` evict the plan's per-side counts as cumulative quotas instead. That no longer stops short, but it evicts far past the fit: on a FULL/SWA pool with an 8:1 SWA:FULL entry ratio filled with one-page cached nodes, a 10-page ask now evicts 57 of the 64 pages, a 30-page ask 61, and a 3-page ask at page size 4 evicts 10 of 16, through `evict_to_free_tokens`, `reclaim_for_prealloc` and `check_decode_capacity` alike. Each such eviction throws away cached prefixes that later requests could have reused.

## Modifications

- `EvictParams` gains `alloc_demand`, the (full, swa) tokens an eviction serves. With it set, `evict_for_alloc` stops as soon as the allocator reports that demand fits, and the counts only cap each component. Callers that do not set it keep the per-side behaviour.
- `UnifiedSWATokenToKVPoolAllocator.allocation_fits` answers what `ensure_capacity` would, without compacting; both read one `_fit_state`, and `evict_to_free_tokens` passes the ask along with the plan. The plan's counts stay the caps, so no ask evicts more than it does today.

Tests (`test_unified_radix_allocation_eviction.py`, CPU): on that pool, an eviction to make room through each of the three entry points evicts exactly the pages the ask needs; before this change all nine cases over-evict (`(True, 57) != (True, 10)`, `(True, 61) != (True, 30)`, `(True, 10) != (True, 3)`). Tree tests cover the stop on the fit whatever the views read, the SWA walk, the counts as caps, and a demotion to the host cache with write-back. `allocation_fits` is pure and agrees with `ensure_capacity`. Over 400 random trees (nodes whose sliding-window KV is already freed, locked nodes, compaction allowed and blocked), every eviction the per-side stop completed still completes, and the ones it left short now complete.

## Accuracy Tests

The change is to the eviction stop rule only; no kernel or model path changes. GPU unit tests for unified memory, on this commit over main 7224fce1b5: 4108 passed, 0 failed.

On SM90 it also ran under load as part of #43326's stack: MiMo-V2-Flash at TP4 with NEXTN on triton, radix cache, overlap scheduler, CUDA graphs off and on, with the per-step pool checks and page invariants on (`SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY=1 SGLANG_CHECK_KV_PAGE_INVARIANTS=1`). Under two load tests (100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests that share a 4096-token system prompt, each with a 128-token question and 2048 output tokens, at concurrency 192) the unified pool ran full and retracted requests; every request completed, and no server reported a leak, double free, invariant violation or illegal memory access.
