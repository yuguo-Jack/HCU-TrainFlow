# [Perf] dsv4: Skip the copy when the page-index table is already aligned

[Upstream PR](https://github.com/sgl-project/sglang/pull/46835) · state: closed · merged: True

## Original PR description

[by Claude Code]

## Motivation

DeepSeek-V4 attention metadata pads its page-index tables (the per-token lists of KV slots each attention kind reads) to a multiple of 64 columns with `_pad_last_dim`, because the attention kernels read whole 64-wide tiles. `_pad_last_dim` always calls `F.pad`, and `F.pad` returns a new tensor even when the padding is zero. So every metadata build clones tables that are already aligned: the 128-wide sliding-window (SWA) table on every decode step, and the 512-wide sparse tables where they are built. This PR returns the input unchanged when it is already aligned. The table values are the same; only the copy goes away. Both DeepSeek-V4 attention backends build their metadata through this function.

- **Accuracy:** no value changes; the function returns the same data without copying it. The DeepSeek-V4 metadata and backend tests give identical results on `main` and with this PR on B300 (see Accuracy Tests). Every caller was checked for in-place writes to the returned table, since it may now share storage with its input (see Modifications).
- **Performance:** on `main`'s default FlashMLA path for DeepSeek-V4.1, a decode step makes one aligned `_pad_last_dim` call at 384 rows or fewer, and three above. Microbenchmark of those calls in a CUDA graph on B300: **-0.8 / -1.1 / -1.2 µs per decode step at 6 / 96 / 288 rows**, and -3.3 to -3.8 µs per build above 384 rows.
- **End to end (estimate, not measured):** about 1 µs against a decode step of about 5 ms at low concurrency, i.e. about 0.02%, below what an end-to-end A/B can resolve. The change is a small, value-preserving cleanup of a per-step copy.

## Modifications

**+2 / −0 runtime code (1 file), no test changes.** No kernel changes.

- `_pad_last_dim` returns its input when the last dimension is already a multiple of `multiples_of` (`python/sglang/srt/layers/attention/deepseek_v4_backend.py`).
- Aliasing check of every caller on `main` (the result may now be the input itself):
  - `_low_ratio_sparse_buffers` and `init_flashmla_related` pad a fresh `torch.full` table, and `init_compression_metadata` a fresh Triton output (`c128_page_indices`); nothing else holds them.
  - `init_compression_metadata` re-pads `swa_page_indices`. Its sources are a fresh `BuildCausalSwaPageIndices` output, the request-window layout's indices, or, on the DSpark draft path, the captured graph's own `swa_page_indices` buffer, which the draft graph rebuilds before attention (the existing comment there already notes that `copy_` onto itself is a no-op).
  - Nothing writes these tables in place afterwards: they are only read, copied out (`trtllm_c4_indices[:, :SWA_WINDOW].copy_(...)`), copied into a captured graph's metadata (`copy_fields`), reassigned (`_tile_padded`), or re-indexed out of place for context parallelism (`val[idx].contiguous()`).
- `deepseek_v4_backend_hip_radix.py` has its own copy of `_pad_last_dim` and is left unchanged.

## Speed Tests and Profiling

Microbenchmark of one metadata build's aligned `_pad_last_dim` calls inside a CUDA graph, before (`F.pad` with zero padding) and after (the input returned), B300, same process, arms rotated, median of 3 processes × 15 paired trials ([min, max] within ±0.02 µs). µs per metadata build:

| build | 6 rows | 96 rows | 288 rows |
|---|---|---|---|
| DeepSeek-V4.1 decode, ≤ 384 rows: SWA table [rows, 128], 1 call | 1.54 → 0.72 (−0.82) | 2.15 → 1.03 (−1.13) | 2.26 → 1.03 (−1.23) |
| DeepSeek-V4.1 decode, > 384 rows: SWA + two [rows, 512] sparse tables, 3 calls | 4.31 → 1.03 (−3.28) | 4.71 → 1.03 (−3.69) | 5.02 → 1.23 (−3.79) |
| DeepSeek-V4 (c4 indexer): SWA + c4 sparse [rows, 512], 2 calls | 3.28 → 1.13 (−2.15) | 3.48 → 0.93 (−2.56) | 3.59 → 1.03 (−2.56) |

The "after" column is the fixed neighbouring op both arms share. Call counts per decode step come from instrumenting `main`'s `make_core_attn_metadata` (FlashMLA, DeepSeek-V4.1, top-k 512): the target-verify build makes the calls above, the DSpark draft-extend build makes none.
