# [Perf] Cache segment token ids on the chat-template encode path

[Upstream PR](https://github.com/sgl-project/sglang/pull/47028) · state: open · merged: False

## Original PR description

## Motivation

Agentic clients resend nearly identical prompts every turn — same system prompt, same tool definitions, earlier turns — but the HF-Jinja chat-template path re-encodes the whole string every request. For a 177-tool Step-3.5 prompt (523 K chars, 142 K tokens) that is **358–395 ms per request** (measured with sglang's own `get_tokenizer`; `parallel_prompt_encode` doesn't help: the system+tools turn is a single gap, so it splits into only 2 chunks). The renderer path (`encode_prompt_segments`, used by the GLM Python renderer) already kept a per-tokenizer segment-id cache; the HF path never used it.

## Fix

`parallel_prompt_encode` now splits the rendered string at added-token boundaries and serves every piece through the shared `_SegmentEncoder` cache:

- **Warm next turn: 358 → 2.1 ms (~170×)**; 32 tools 55 → 0.70 ms. A 20-turn agent loop drops from **7.84 s to 0.70 s** of encode work (median turn 369 → 4.75 ms).
- Cold stays at parity: +1.4 ms of scan/assembly on top of the shared `encode_batch` work.
- Cache hits compose correctly because a HF fast backend matches added tokens first and encodes the text between matches independently; every flag that can change piece ids (`add_special_tokens` + `specials_added`, backend truncation/padding/`encode_special_tokens`) is pinned per call or excluded by the plan's eligibility gates, and pieces are encoded with `add_special_tokens=False`. Key: tokenizer identity (weak-keyed) + piece text.
- Bounds: per-entry cap 1/8 → 1/4 of the 1M-token budget (a 142 K-token tool block was previously encoded but **never retained**), plus a new 65,536 entry-count bound (~30 MB overhead cap).
- The `_parallel_ok` serial probe is removed: it misfires on exactly this workload (a single long gap can't spread over rayon workers, so the probe reads "serial" and permanently disables the fast path after the first request). Measured serial-mode cold is at parity (371.7 vs 367.7 ms), and the warm path doesn't depend on parallelism.

## Correctness evidence

- **236,312 cached-vs-fresh id comparisons, 0 mismatches**, across 11 real tokenizers (Step-3.5, GLM-5.3-Flash, DeepSeek-V3.2/V4-Flash with and without the repo template, Qwen3/Qwen3.8, Hy4, Ling-3, LFM3, gpt2, Mistral-7B). Corpus: rendered multi-turn conversations with shuffled tool JSON, added tokens placed at every position of mergeable pairs, partial special-token spellings, unicode/NUL/lone surrogates (same exception type both paths), cold and warm passes.
- **Ineligible pipelines never reach the cache**: Mistral's Metaspace tokenizer took the cache path 0 times (asserted).
- `test_parallel_prompt_encode.py`: 22 passed (2 new — HF path populates the cache, entry-count budget; both fail pre-fix; 5 probe tests removed with the probe). Fallback sentinel moved to `encode_layout` so it can't pass vacuously on a warm hit; the 4,030-text fuzz now encodes cold and warm.
- Sibling suites `test_serving_chat.py` + `test_glm53_chat_template.py`: 191 passed.
- `pre-commit run --files`: clean.

Not run: serve + e2e on GPU. The change is frontend tokenization verified for id identity on real tokenizers, but the standard serve+eval gate should run before merge.

- bvolpato · COMMENTED · 2026-11-02T23:48:48Z · [source](https://github.com/sgl-project/sglang/pull/47028#pullrequestreview-5745065753)

One risk to check before this lands: ids padded by another thread can get into the segment cache.

This PR removes the `_parallel_ok` probe and encodes on the shared tokenizer backend (parallel_prompt_encode.py:380) after the gate at :313. `BaseMultimodalProcessor._call_processor` calls that same tokenizer with `padding=True`, on the event loop when a fast image processor runs with one worker (base_processor.py:798, :958, :2097), while chat encode runs in the default executor (serving_base.py:102). If padding turns on between the gate and the encode call, `encode_batch` pads the shorter segments, and those ids stay in the cache.

What I ran, on this head's diff applied to main 582168dd7c on a B200 host, with `TOKENIZERS_PARALLELISM=false` as on a live multimodal server: the real LFM2.5-VL processor call in one thread, 16 chat threads, and 100 prompts of about 40K chars. This PR gave wrong ids in 6 of 6 runs (536 to 1354 wrong of about 15K calls), token counts roughly doubled (for example 11073 to 22250), and 2 to 10 prompts stayed wrong after the padding calls stopped. Main gave 0 wrong in all 6 runs.

This is an in-process race, not a production failure I can show. On a live server with dummy-weight LFM2.5-VL, about 14.2K long prompts with about 5.4K image calls gave 0 wrong ids, and Qwen3-VL-2B gave 0 wrong of 400. Instrumentation showed that chat threads do see padding on at the gate and right after encode, so the state collides, but I did not validate that live detector by injecting a wrong entry.

A private backend for `encode_batch` closes the window: `type(self.backend).from_str(self.backend.to_str())`, then `no_padding()` and `no_truncation()`. #42187 overlaps this path and does that, and it gave 0 wrong ids in the same run. It costs about 0.25 to 0.9 s of startup and 40 to 220 MB of API RSS, depending on the tokenizer.

| --- | ---: | ---: | ---: |
