# [Perf] gemm: Opt-in table of pinned bit-identical cuBLASLt algorithms for BF16 linears

[Upstream PR](https://github.com/sgl-project/sglang/pull/48294) · state: open · merged: False

## Original PR description


## Motivation

At decode batch sizes, cuBLAS's heuristic often picks a BF16 GEMM kernel whose grid leaves most SMs idle. When cuBLAS runs a GEMM without split-K, each output element is one fp32 accumulator over K, rounded once to BF16. Other split-K-free cuBLASLt algorithms of the same library build that accumulate K in **the same order** produce the same bits while using the GPU better.

This PR lets a deployment pin such algorithms per `(N, K, M)`: an opt-in JSON table, built offline by a tuner for one GPU model and one cuBLASLt version, that unquantized BF16 linears and the BF16 `lm_head` consult before calling `torch.mm`. The tuner keeps an algorithm only if it gives `torch.mm`'s bits on inputs built so that another accumulation order differs with overwhelming probability, and marks the table as checked. A plain random-input comparison is not enough for this: an algorithm that adds K in another order rounds to the same BF16 as `torch.mm` in nearly every output on normal inputs, yet differs on about one output in 10^4 on real activations, which is enough to change greedy text.

Per-GPU tables are deliberately not shipped. A `cublasLtMatmulAlgo_t` is only valid for the cuBLASLt build and GPU it was recorded on, so in-tree tables would go stale with every torch/CUDA bump. The table is generated per deployment, the same way the fused-MoE Triton configs are tuned per device (`benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py`), and complements the hand-tuned per-GPU tactic tables already in `unquant.py` (`_BF16_SPLITK_TUNED_TACTICS`, `_BF16_WARP_SPLITK_TUNED_TACTICS`).

## Modifications

- `python/sglang/kernels/jit/csrc/gemm/cublaslt_pinned_gemm.cuh` (JIT, tvm-ffi): `run` executes `out = x @ w.T` with an explicit `cublasLtMatmulAlgo_t`; `enumerate` lists every split-K-free algorithm cuBLASLt accepts for a problem (all tile/stage/swizzle/custom-option values) plus the heuristic's top choices; `version` returns `cublasLtGetVersion()`. Matmul and layout descriptors are cached per problem shape. It links the `libcublasLt` that torch already loads.
- `benchmark/kernels/pinned_bf16_gemm/tune_pinned_bf16_gemm.py`: for each `N:K` shape and M, quick-times all candidates, keeps those of the fastest `--top` (default 24) that give `torch.mm`'s bits on `order_check_operands`, times them and `torch.mm` with a cold L2 (`marker.do_bench`, CUDA graph), and writes an entry when the best one is at least `--min-speedup` (3 %) faster. The table carries `device_name`, `cublaslt_version` and `"order_checked": true`.
- `python/sglang/kernels/ops/gemm/pinned_bf16_gemm.py`: `order_check_operands`, table loading and `pinned_mm(x, w, out=None)`.
  - `order_check_operands(m, n, k)`: every output gets a +2^24 and a -2^24 product that cancel exactly, so each O(1) term added between them is rounded to 2^24's fp32 ulp. Which terms fall between the two depends on the accumulation order, so an algorithm with another order differs from `torch.mm` on some outputs with overwhelming probability, while the same order gives identical bits.
  - Loading: a table without `"order_checked": true` (for example, one written before this check existed), or recorded for another GPU or cuBLASLt version, is ignored with a warning. Loading reads the JSON only and allocates no device memory.
  - Serving re-check: the first eager call for each weight shape (N, K) runs that shape's entries on three plain random inputs with the layer's real weight and drops any entry that differs from `torch.mm`. This catches gross mismatches (a table from another build), not another accumulation order. **Exactness rests on the tuner's order check, so a hand-edited table is not protected.** All M of a shape are checked at once because CUDA graphs capture batch sizes that never ran eagerly; a shape not checked yet keeps `torch.mm` while a graph is being captured.
  - Only packed, 16-byte-aligned BF16 operands use the table; anything else returns `None` and the caller keeps `torch.mm`.
  - The cuBLASLt workspace is one buffer per (device, stream), sized to the table's largest entry, so concurrent table GEMMs on different streams (overlapped batches, auxiliary streams, graphs captured on them) never share one, and a buffer a captured graph points to is never freed.
- `python/sglang/srt/layers/quantization/unquant.py`: `UnquantizedLinearMethod.apply` / `apply_into` and `_bf16_gemm_dispatch_impl` (which also serves the fused GDN `in_proj` of Qwen3.5 / Qwen3.8) try `pinned_bf16_linear` before `F.linear` / `torch.mm` for bias-free BF16 linears. With the env var unset the added cost is one module-level bool check.
- `python/sglang/srt/layers/logits_processor.py`: the BF16 `lm_head` matmul tries the table too.
- `python/sglang/srt/environ.py`: `SGLANG_OPT_BF16_GEMM_TABLE` (path, default unset = off). Ignored with `--enable-deterministic-inference` (batch-invariant mode replaces `aten::mm`) and inside `torch.compile`.
- `test/registered/kernels/ops/gemm/test_pinned_bf16_gemm.py` (13 cases): bitwise equality and CUDA graph replay of a pinned algorithm; the order check rejects two half-K partial sums and reversed K, and every M=1 algorithm it accepts matches `torch.mm` on 64 more plain inputs; tables without the order-check marker or for another cuBLASLt version are ignored; the serving re-check drops a failing entry, runs on the real weight on the first eager call, and allocates nothing at load; no unchecked shape during capture; per-stream workspaces and concurrent use from two streams; shape/layout eligibility; routing through `UnquantizedLinearMethod.apply` / `apply_into`.
- `docs/docs/references/environment_variables.mdx`: the new env var, including the order-check marker and what each check guarantees.

Usage:

```bash
python benchmark/kernels/pinned_bf16_gemm/tune_pinned_bf16_gemm.py \
  --shapes 12352:4096 4096:4096 10240:4096 24576:4096 4096:12288 248320:4096 \
  --m 1 2 4 8 12 16 24 32 40 48 56 64 --output bf16_gemm_table.json
SGLANG_OPT_BF16_GEMM_TABLE=bf16_gemm_table.json sglang serve --model-path Qwen/Qwen3.5-9B ...
```

## Accuracy Tests

Every table in this section was written by the tuner in this PR, with its order check, on the GPU it was used on.

**Served-GEMM check (RTX PRO 6000 Blackwell Max-Q, 300 W).** A diagnostic run compared every eagerly served table GEMM with `torch.mm` on the same operands: 0 differences in 42,000 calls (Qwen2.5-0.5B-Instruct, CUDA graphs off so every call is eager). Most calls (41,856) were the 9728 x 896, M=1 entry (MLP up-projection at single-request decode); the rest were 896 x 896 and 9728 x 896 at M=8 and 12.

**7-prompt gate (Qwen2.5-0.5B-Instruct, `--disable-radix-cache`, greedy, each prompt sent alone, then repeated, then all 7 as one batch; launches table off / on / on / off):**

| GPU | Table entries active | Single, repeat and batch outputs |
|---|---|---|
| RTX PRO 6000 Blackwell Max-Q (300 W) | 20 | 7 / 7 identical in every pair of the 4 launches |
| RTX PRO 6000 Blackwell Server Edition (600 W) | 13 | single and repeat 7 / 7 in every pair; batch 7 / 7 except one table-on launch that differs from all others, including the other table-on launch, at one prompt (see below) |

**64-prompt gate (one `/generate` call with 64 greedy prompts, `max_new_tokens=160`; launches A (unset), B (table), B, A):**

| GPU | Model | Table entries active | Identical completions |
|---|---|---|---|
| H100 80GB HBM3 | Qwen/Qwen3.5-9B | 15 (lm_head 9, 24576 x 4096 6) | 64 / 64 in every pair (9,300 tokens per launch) |
| RTX PRO 6000 Max-Q (300 W) | Qwen/Qwen2.5-0.5B-Instruct | 22 | 64 / 64 between both A launches and the second B launch; the first B launch differs from all three (28 / 64) |
| RTX PRO 6000 Server (600 W) | Qwen/Qwen2.5-0.5B-Instruct | 12 | 64 / 64 between both A launches and the first B launch; the second B launch differs from all three (28 / 64) |

In each of those cases the one launch that differs also differs from the other launch with the same table, and its server log shows a different prefill grouping of the batched request (for example 3 + 61 prompts instead of 2 + 62). Greedy outputs depend on batch composition in this setup (no batch-invariant mode; main is not batch-invariant either), so these differences follow the scheduler's grouping, not the table. In all three cases the odd launch was a table-on launch; the table's first-call self-check can shift timing and with it the grouping. A different grouping does not always change outputs: on CL600 one launch grouped 1 + 63 and still matched.

## Speed Tests and Profiling

All numbers below were measured with tables from this PR's tuner. Kernel level (`tune_pinned_bf16_gemm.py`, cold L2 `marker.do_bench` under CUDA graph, median; only entries the tuner wrote, i.e. at least 3 % faster):

RTX PRO 6000 Blackwell Max-Q (300 W), dense BF16 shapes of `nvidia/Qwen3.8-Flash-Next-NVFP4` at TP1 (us):

| N x K | M | torch.mm | pinned | speedup |
|---|---|---|---|---|
| 16480 x 2560 (GDN fused in_proj) | 16 / 32 / 64 / 256 | 58.6 / 62.9 / 65.0 / 121.8 | 56.1 / 56.7 / 58.7 / 106.0 | 4.3 / 9.9 / 9.8 / 13.0 % |
| 13312 x 2560 (attention qkv) | 64 / 128 | 54.4 / 66.7 | 48.1 / 64.1 | 11.5 / 3.9 % |
| 2560 x 6144 (o_proj, out_proj) | 256 | 51.1 | 47.0 | 8.1 % |
| 2560 x 640 (shared expert down) | 8 / 16 / 32 / 64 | 6.04 / 6.12 / 6.14 / 6.25 | 5.71 / 5.80 / 5.92 / 6.04 | 5.4 / 5.4 / 3.7 / 3.3 % |
| 248320 x 2560 (lm_head) | 64 / 128 / 256 | 989.9 / 1157.9 / 1779.8 | 949.5 / 1105.9 / 1686.2 | 4.1 / 4.5 / 5.3 % |

H100 80GB HBM3, Qwen/Qwen3.5-9B at TP1 (us):

| N x K | M | torch.mm | pinned | speedup |
|---|---|---|---|---|
| 12352 x 4096 (GDN fused in_proj) | 24 / 40 / 64 | 39.0 / 40.2 / 40.0 | 37.3 / 37.8 / 38.2 | 4.6 / 6.1 / 4.7 % |
| 24576 x 4096 (gate_up) | 12 / 48 / 64 | 73.3 / 75.4 / 75.9 | 70.9 / 72.2 / 73.5 | 3.3 / 4.2 / 3.1 % |

RTX PRO 6000 Server Edition (600 W), Qwen2.5-0.5B-Instruct: 896 x 896 at M = 2-64 runs 14.6-21.8 % faster (7.4-7.6 -> 5.8-6.3 us); 9728 x 896 at M=48 4.6 %.

Where no split-K-free algorithm has `torch.mm`'s accumulation order and is faster (for example 4096 x 4096 and 4096 x 12288 on H100, 1280 x 2560 at every M and 13312 x 2560 at M 8-32 on the 300 W card), the tuner writes no entry and the shape stays on `torch.mm`.

| | | 64 | 27166 -> 27805 (+2.4 %) | 1.965 -> 1.915 (-2.5 %) | ITL disjoint; one table-on throughput round overlaps |
| RTX PRO 6000 Server (600 W) | Qwen2.5-0.5B-Instruct | 16 | 9266 -> 9402 (+1.5 %) | 1.590 -> 1.562 (-1.8 %) | ITL disjoint; throughput ranges overlap by 2.3 tok/s |
| | | 64 | 27446 -> 27754 (+1.1 %) | 1.841 -> 1.818 (-1.2 %) | disjoint |

| | | 64 | 5599 -> 5618 (+0.3 %, noise) | 9.741 -> 9.689 (-0.5 %) | throughput overlaps |

The end-to-end gain is largest where small dense GEMMs dominate decode (the 0.5B model). For Qwen3.5-9B on H100 the gain is under 1 % at concurrency 16 and within noise at 64; this PR makes no end-to-end claim for it. In those 9B launches the 12352 x 4096 shape never reached the table (no self-check logged), so its kernel gain does not show end to end. The feature costs nothing when the env var is unset.
