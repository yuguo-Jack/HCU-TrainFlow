# [Fix] Normalize grayscale JPEGs in GPU image decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/35101) · state: open · merged: False

## Original PR description

## Motivation

The torchvision CUDA JPEG decoder defaults to `ImageReadMode.UNCHANGED`, so grayscale JPEGs are decoded as `[1, H, W]` tensors while RGB JPEGs are decoded as `[3, H, W]`. The GPU-decoded tensors bypass the PIL `convert("RGB")` path in `BaseMultimodalProcessor`, causing mixed grayscale and RGB inputs to fail when an image processor stacks them.

This can return HTTP 500 for multimodal requests and can also fail later in a vision encoder that expects three input channels.

Related to #26751 and #28828. This change is based on the current `main` branch and keeps the high-fidelity `nvjpeg_fancy` path introduced by #34163 unchanged because that decoder already requests planar RGB output.

## Modifications

- Request `ImageReadMode.RGB` from the standard torchvision CUDA JPEG decoder.
- Add a deterministic CPU unit test that exercises torchvision's RGB conversion while verifying the arguments used by the CUDA path.
- Cover mixed grayscale/RGB JPEG shapes and confirm that the resulting tensors can be stacked.

## Accuracy Tests

## Speed Tests and Profiling

H20 wall-clock benchmark using random `640x384` JPEGs, with 30 warmups and 8 rounds of 300 decodes per mode. Each round was synchronized before and after measurement.

| JPEG input | `UNCHANGED` median | `RGB` median | Delta |
| --- | ---: | ---: | ---: |
| RGB | 2.3672 ms | 2.3744 ms | +0.31% |
| Grayscale | 1.8561 ms | 1.8367 ms | -1.05% |

The differences are within run-to-run variation. A `640x384` grayscale decode uses 491,520 additional output bytes when expanded from one to three `uint8` channels; RGB JPEG output size is unchanged.

Additional end-to-end confirmation on **SGLang 0.5.21**: the same-size RGB/grayscale JPEG failure is still reproducible, and applying the core change in this PR fixes it.

**Environment:** NVIDIA H20-3e (single GPU), Qwen3.5-0.8B, SGLang 0.5.21, Transformers 5.12.1, PyTorch 2.13.0, torchvision 0.28.0. Requests were sent to `/v1/chat/completions` with GPU JPEG decoding enabled by default.

We used a real cat image, resized it to 320×240, and saved RGB and single-channel `L` JPEG versions. We also created a 240×320 grayscale version. Dimensions below are **width × height**.

| Request | Before patch | After patch |
| --- | --- | --- |
| RGB only, 320×240 | HTTP 200 | HTTP 200 |
| Grayscale only, 320×240 | HTTP 200 | HTTP 200 |
| RGB + grayscale, both 320×240 | **HTTP 500** | **HTTP 200** |
| Grayscale + RGB, both 320×240 | **HTTP 500** | **HTTP 200** |
| RGB 320×240 + grayscale 240×320 | HTTP 200 | HTTP 200 |

The actual HTTP error before the patch was:

```text
Internal server error: stack expects each tensor to be equal size,
but got [3, 240, 320] at entry 0 and [1, 240, 320] at entry 1
```

Reversing the image order produced the corresponding reversed shapes. The server remained healthy after the failed requests.

For the fix, we edited the installed 0.5.21 `sglang/srt/utils/common.py`, imported `ImageReadMode`, and changed only the standard CUDA JPEG decode call to:

```python
decode_jpeg(encoded_image, mode=ImageReadMode.RGB, device="cuda")
```

After restarting the test server with otherwise identical settings, all five requests returned HTTP 200 with generated responses. A separate call to the patched **actual SGLang `_load_image`** confirmed that both RGB and grayscale JPEGs returned three-channel **CUDA tensors**, so the successful result was not due to a PIL/CPU fallback. This validates the core production change in this PR; we did not check out and test its entire branch or run its CI suite.

**Minimal request script using any local RGB photo:**

```python
import base64
import io
import sys

import requests
from PIL import Image

rgb = Image.open(sys.argv[1]).convert("RGB").resize((320, 240))
gray = rgb.convert("L")


def image_part(image):
    buf = io.BytesIO()
    image.save(buf, format="JPEG")
    encoded = base64.b64encode(buf.getvalue()).decode()
    return {
        "type": "image_url",
        "image_url": {"url": "data:image/jpeg;base64," + encoded},
    }


cases = {
    "rgb_only": [rgb],
    "gray_only": [gray],
    "mixed_same_hw": [rgb, gray],
    "mixed_same_hw_reversed": [gray, rgb],
    "mixed_different_hw": [rgb, gray.resize((240, 320))],
}
for name, images in cases.items():
    response = requests.post(
        "http://127.0.0.1:31084/v1/chat/completions",
        json={
            "model": "qwen35-gray-test",
            "messages": [{
                "role": "user",
                "content": [image_part(im) for im in images]
                + [{"type": "text", "text": "Describe the image(s) briefly."}],
            }],
            "max_tokens": 48,
            "temperature": 0,
            "chat_template_kwargs": {"enable_thinking": False},
        },
        timeout=180,
    )
    print(name, response.status_code, response.text)
```

Run against a Qwen3.5-0.8B server with `--served-model-name qwen35-gray-test --port 31084` (or adjust the script). Our test settings used TP=1, context length/max total tokens=2048, max running requests=1, max Mamba cache size=2, chunked prefill size=512, with CUDA graphs and radix cache disabled. The same settings were used before and after the patch.


This provides additional HTTP-level reproduction and before/after evidence for moving this PR forward. Thanks for the fix!
