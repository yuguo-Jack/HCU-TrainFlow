# [Docs] [AMD] Qwen3.8-27B cookbook: Add an MI355X MXFP4 recipe

[Upstream PR](https://github.com/sgl-project/sglang/pull/44728) · state: open · merged: False

## Original PR description

## Motivation

The Qwen3.8-27B cookbook page has no AMD recipe. AMD publishes an MXFP4 checkpoint for CDNA4, `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`: the language model is MXFP4 W4A4 and the vision encoder stays bf16. It runs on a single MI355X.

Rebased onto current `main` (the conflict was the Xeon CPU cell added in #40092; both cells are kept, and the DSPARK disable rule now covers Xeon and MI355X).

## Modifications

- `qwen3.8-27b.jsx`:
  - adds `mi355x` hardware and an `MXFP4` quantization option;
  - maps the model name to the AMD checkpoint;
  - sets the ROCm docker image `lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261021`, the image the AMD nightly performance config for this checkpoint uses.
- New `mi355x` / `mxfp4` cell, single GPU like the other cells. Flags follow the AMD nightly performance config for this checkpoint at TP1:
  - `SGLANG_USE_AITER=1`, `--quantization quark`, `--attention-backend aiter`;
  - `--kv-cache-dtype fp8_e4m3`, `--mem-fraction-static 0.9`, `--chunked-prefill-size 16384`;
  - `--cuda-graph-backend-prefill breakable`. On ROCm the prefill CUDA graph is off unless a backend is set (`default_prefill_backend()` returns `disabled` off CUDA). Turning it on was measured on MI355X at +9.5% image-request throughput (TTFT -16%) at TP1 and +2.5% at TP2. It passed GSM8K and MMMU checks but is not bit-exact against eager prefill, which the page says;
  - the qwen3 reasoning and tool-call parsers.

  The cell still reports **Final Verification In Progress** until the full GSM8K run for this exact cell is in.
- The DSPARK overlay is disabled on MI355X: it pins a FlashInfer draft attention backend, which ROCm does not ship.
- Page text:
  - MI355X added to the supported cards;
  - an MI355X note on the AITER/FP8-KV setup and the breakable prefill graph, and a recommendation to add `--mm-enable-dp-encoder` at `--tp-size 2`, so that each GPU encodes whole images instead of splitting every vision layer across both GPUs;
  - an optional TP2 setting, collapsed by default: INT4 QuickReduce for large prefill all-reduces (`ROCM_QUICK_REDUCE_QUANTIZATION=INT4` with `AITER_CUSTOM_AR_MAX_SIZE=8388608`, so all-reduces above 8 MiB leave the AITER custom all-reduce for QuickReduce). Measured +14% image-request throughput (TTFT -18.7%) at TP2. It is lossy, so the page marks it optional and gives its accuracy.
