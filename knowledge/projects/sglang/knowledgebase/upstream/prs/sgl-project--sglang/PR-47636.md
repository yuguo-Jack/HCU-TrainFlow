**Depends on #47561** (this PR is one commit on top of it; review the last commit).

## Motivation

With #47517 (and #47561 on SM107) the router stream finishes last at most decode sizes, so the router GEMM gates when the experts start. This PR:

1. Adds a fused split-K router GEMM (CuTe DSL, TF32): K is split across a thread-block cluster and the partial sums are reduced in distributed shared memory, in one launch instead of cuBLAS's GEMM + reduce. A per-GPU tactic table (SM103, SM107) picks the tactic per token count; ranges without a winning tactic keep cuBLAS.
2. Re-tunes #47561's split thresholds on top of it: GB300 now takes the split from M = 512 (where the main stream gates again); SM107 keeps it from M = 8.

## Modifications

- `muse_spark_router_gemm_cutedsl.py` (new): the TF32 cluster split-K GEMM (`router_tf32`), its tactic validation, and `_SERVE_TABLES`, the serving tactic per (compute capability, token range). `router_tf32_eligible` is true only where the table has a tactic (2 <= M <= 1024) and TF32 matmuls are allowed; everything else keeps cuBLAS. The fp32 inputs and the TF32 math are the same as cuBLAS's under `float32_matmul_precision("high")`, which the server sets; only the split-K reduction order differs. Under `"highest"` the kernel is never taken, so the logits stay FP32.
- `muse_spark.py`: `MuseSpark1xRouter` calls `router_tf32` when eligible (the table has a tactic for this GPU and token count), after the existing GEMV path. There is no switch: GPUs or token counts without a tactic keep cuBLAS.
- `routed_moe_split.py` (#47561): GB300 takes the routing-metadata split from M = 512 at TP4 and TP8. With this PR's router the main stream trails the router stream by 3.2-4.7 µs from M = 512, which the split recovers (2.8-4.7 µs per layer; neutral at TP8 M = 1024); below M = 512 the main stream trails by at most 1.6 µs or the router still gates, so GB300 keeps the fused routing there (see "GB300 split thresholds").

### How the tactics were picked

Same procedure on both GPUs; the tactic that is fastest alone is often not the one that ends the router stream earliest, because a large cluster waits for SMs the main stream holds.

1. Isolated sweep (CUDA graph, 60 calls with a distinct cold weight each): every valid tactic (expert tile {64, 128} x token tile x split {2, 4, 8, 16} x K tile {32, 64, 128}; GB300 also PDL on/off) at M = 8..1024, pruned to the top candidates per M (the standalone table above).
2. In context, at TP4 and TP8: the candidates on the router stream beside the main stream, CUDA graph. GB300: the decode MoE front as served (projection slice -> gather + norm + NVFP4 quant on the main stream; router GEMM -> fused top-8 routing on the router stream), distinct weights per layer, 5 rotated trials; every entry is within 0.5 µs of the best measured tactic at both TP sizes. SM107: a stand-in pooler GEMM beside the router GEMM to prune, then A/B in TP4 / TP8 serving with #47561 (DFlash decode, nsys experts start, median over layers).
3. A token range keeps cuBLAS unless a tactic beat it at both TP sizes.

### GB300 split thresholds (#47561)

With this PR, split off vs on (same tree): the split moves the routing metadata (4-8 µs) off the main stream, so it saves up to how far the main stream trails the router stream, minus its fixed cost (a separate populate launch; GEMM1 waits on a cross-stream event instead of chaining behind the routing with PDL).

| c | M | main trails router by (TP4) | TP4 saved | main trails router by (TP8) | TP8 saved |
|---|---|---|---|---|---|
| 1-32 | 8-256 | <= 1.6 µs, or the router gates | within noise or a loss | <= 0.7 µs, or the router gates | within noise |
| 64 | 512 | 3.8 µs | +3.5 µs | 4.7 µs | +4.7 µs |
| 128 | 1024 | 3.2 µs | +2.8 µs | 3.7 µs | -0.2 µs |

So the split is enabled from M = 512 at TP4 and TP8.
