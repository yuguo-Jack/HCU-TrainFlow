# SGLang Optimizations for DeepSeek-V4.1-Flash on H20: 4–10× Faster Long-Input TTFT

> Main authors: Hanlin Gao, Wengang Zheng, Yusong Gao, Yun Zhang
>
> This draft PR is a write-up, not a merge request. The code is the `dsv41-flash-h20` branch of this repository. The changes are meant to go upstream piece by piece.

## Introduction

We run an agent workload whose requests average **about 170K input tokens** each, with short outputs. On H20 the first bottleneck for this traffic is prefill. **H20 has about one seventh of the compute of H100, but its NVLink is still 900 GB/s**, so it suits splitting one long request across several GPUs.

The branch is based on SGLang upstream main (`5884e4fec6`, October 27, 2026; the same base throughout). It does three things:

- **It spreads the prefill of a long input over 8 GPUs.**
- **It removes the work that every GPU repeats during decode.**
- **It puts every optimization behind one switch.** With the switch off, the code is upstream's, except for the commits that fix upstream bugs. This makes it easy to upstream the changes one at a time.

**Results**

- **Single node (8×H20-3e):** TTFT on long inputs is **4–10× faster** than upstream main. Decode throughput is **1.9–2.3×** that of upstream main.
- **Cold start (8×H20, fresh container):** the time until the server can take requests drops from **31 minutes to 5.3 minutes**.
- **Off-peak revenue per GPU-hour:**
  - On a 34-GPU minimal reproduction demo built from sampled internal business data (2E3P1D, a fixed 3:1 ratio), the two load levels give **¥26.8 (≈$4.0)** at about 50 token/s per user and **¥14.4 (≈$2.2)** at about 100 token/s per user. At the 100 TPS level, P is only about half used.
  - At our internal system's operating point, 100 token/s per user gives about **¥24.5 (≈$3.7)**.

Revenue uses DeepSeek's official off-peak prices. USD figures use the CNY/USD ratio of DeepSeek's own price list (about 6.67).

### Cold start: 31 minutes to 5.3 minutes

Cold start does not change steady-state performance, but every new instance has to wait through it once.

**Setup:** both sides start from a fresh container: the JIT cache is empty and the checkpoint is not in the page cache.

**Result on 8×H20 (96 GB):**

| | Time to READY | TTFT of the first 128K request after READY |
|---|---:|---:|
| Upstream main | 1850 s | 364 s |
| This branch | 316 s | 1.8 s |
<img width="1440" height="735" alt="fig_coldstart_en" src="https://github.com/user-attachments/assets/e34c9fdd-8ad7-44eb-8cba-15bdce337d54" />


*Figure 2. Cold start (8×H20, TP8 + prefill CP8 + DSpark, fresh container, checkpoint not in the page cache).*

Upstream main spends its time in two places:

- **CUDA graph capture takes 1395 s.**
  - Almost all of it goes to DeepGEMM precompiling every GEMM shape for every M from 1 to 32768.
  - After READY, the first 128K request hits two shapes that only appear in long prefills, and each triggers another round of compilation. So its TTFT is six minutes.
- **Weight loading takes 340 s**, about 200 s of which is mHC warm-up compilation during loading.

This branch changes three things:

- It turns off full-M precompilation by default and warms up on sampled shapes.
- It ships a JIT manifest with the code. While weights load, 32 processes compile the kernels in the manifest in parallel.
- It keeps the page cache instead of dropping it.

The result:

- Weight loading takes 133 s and CUDA graph capture 86 s.
- After READY, no new files appear in the JIT cache directory.
- The first 128K request has about the same TTFT as steady state (1.74 s).

Note: upstream provides `python3 -m sglang.compile_deep_gemm` to compile DeepGEMM ahead of time, which makes cold start much shorter. This comparison is a plain launch with no preparation.

### How we measured

The single-node numbers were measured on 8×H20-3e (141 GB). Cold start, PD and EPD use 8×H20 (96 GB) nodes.

- **TTFT** is cold prefill: no prefix cache hit, 32 output tokens, 1 warm-up run, then the median of 3 runs.
- **Decode throughput** uses a fixed 4K input and 1K output.
- **Runs:** both sides use the same machine and the same client. Upstream main was measured once; this branch twice, averaged.

**Upstream main settings:**

- It enables the same TP8, prefill CP8 and DSpark, but not `--enable-decoder-swa-bounded-replay`. With all of these enabled together, upstream crashes on the first request (commit 2 fixes this).
- Upstream main also has 14 DSpark / CUDA graph switches that are off by default. Turning all of them on raises its decode throughput by 4–7%. This branch is then still 1.79×, 2.11× and 2.21× of it at single session, 32 concurrent and 64 concurrent.

**Cold start method:**

- Both sides start from a newly created container with an empty JIT cache.
- Before launch, `posix_fadvise(DONTNEED)` evicts the checkpoint from the page cache, and `mincore` confirms that 0% of it is resident.
- Timing runs from the launch command to `/health` returning 200.

## One switch: off means upstream

The branch adds only three environment variables:

| Variable | Effect |
|---|---|
| `SGLANG_OPT_DSV41_SM90=1` | Enables all optimizations for the deepseek_v41 model on SM90; other models and architectures are unaffected |
| `SGLANG_OPT_DSV41_SM90_DISABLE=<subsystem,...>` | Turns off individual subsystems by name |
| `SGLANG_OPT_DSV41_SM90_LOSSY=fp8_lm_head_target` | The only lossy option; must be enabled explicitly |

**Subsystems.** The switch covers 14 subsystems: `mhc`, `moe`, `fp8_gemm`, `attn_proj`, `lm_head`, `startup`, `indexer`, `cp`, `prefill_graph`, `decode`, `mix_decode`, `runtime`, `pd`, `epd`.

- The switch is parsed once at process start. Each module records the result when it is constructed and never checks again at run time.
- A misspelled subsystem name is an error at startup.

**Switch off.** With the switch off, the code that runs is upstream's. The exceptions are changes that fix upstream bugs:

- Commit 2 is not gated as a whole and can be applied to the baseline on its own.
- Ungated fixes and registrations in other commits are listed separately in their commit messages.

**Numerics.** Most changes are bit-exact with the kernels they replace. The exceptions, also listed one by one in the commit messages, are:

- Following the model's reference implementation, attention output is rounded to FP8 per 32 elements before wo_a.
- Some small-M GEMMs use split-K, which changes the FP32 summation order.
- mHC uses tf32x3.
- Under CP, the MoE reduction sums in FP32 and rounds once.
- The decode head swap changes FlashMLA's split.
- The prefill indexer scores in FP8; scores match the torch path within tolerance.
- When the FlashMLA scheduler picks a non-default split, the output differs from the original by at most 2 bf16 ulp.
- The DSpark draft uses an FP8 LM head.

All these paths are deterministic: the same input always gives the same output.

## Prefill: spreading one long request over 8 GPUs

### CP communication

Prefill CP8 interleaves a request's tokens across 8 GPUs. The upstream implementation works, but carries a lot of extra overhead:

- every per-layer row exchange goes through NCCL;
- the compressor first gathers full hidden rows, then projects all rows on every GPU;
- MoE output is all-reduced and then sliced;
- under CP each layer also has about 4 ms of host overhead that does not depend on the row count, so for short inputs the host is the bottleneck.

All of this communication now goes through NVLink symmetric memory:

- **SWA KV and the compressor gathers** are issued by the copy engine before q_b and overlap with compute.
- **The compressor** projects only its local rows and then gathers the projected results. The tail compressor goes from a 16384-row GEMM plus one full gather to a 2048-row GEMM plus one output gather.
- **MoE.** From 2048 rows per GPU, the copy engine also pulls the MoE inputs. The weighted sum of the routed experts is written straight into each rank's symmetric buffer and then summed in FP32 in rank order. This removes the NCCL all-reduce and the slicing.
- **Input embeddings and Engram lookups** are written directly from the shard owner to the target rank in the same way.

### Sparse prefill and late-layer skip

**Sparse prefill.** Under CP, upstream sends query rows into the paged decode kernel. We switch back to `flash_mla_sparse_fwd`. On 8×H20, attention time for a cold 128K request drops from 222.8 ms to 199.1 ms.

**Bounded replay.** The late-layer skip builds on upstream's bounded replay ([sgl-project/sglang#38798](https://github.com/sgl-project/sglang/pull/38798)).

- V4.1 layers 21–39 reuse layer 20's KV, but each layer still has its own 128-token sliding window.
- With bounded replay on, layer 20 and later layers compute only the last window of each prefill chunk, and the sliding window is truncated at that window's start.
- So bounded replay is an approximation. The upstream docs say it is not numerically equivalent to a full prefill, and recommend turning it off for RL, where logprobs must match the trainer ([V4.1 cookbook](https://github.com/sgl-project/sglang/blob/5884e4fec6c0f4453940605896154f5fba4badd9/docs/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.mdx)).
- Upstream made it the default without CP in [sgl-project/sglang#44403](https://github.com/sgl-project/sglang/pull/44403).
  - The PR's evaluations with it on and off are close: 97.71% for both on AIME 2026 with unlimited output, and 69.03% vs 68.14% on DeepSWE.
  - The PR also notes that single runs cannot prove accuracy equivalence.
- This branch turns it on explicitly under CP8. Commit 2 fixes the crash when these options are combined. See [Accuracy](#accuracy) for the comparison.

**Late-layer skip.** It builds on bounded replay.

- Suppose that after a chunk, every request still has at least one window left unfilled. That window will be overwritten by a later chunk, so computing it is wasted: nothing reads it.
- In that case the whole chunk stops at layer 20 (of 40). Under CP, the row layout that logits and DSpark need is still kept. The result is bit-exact with bounded replay itself.
- The scheduler helps guarantee that every late-layer value that is read comes from a full forward pass:
  - a continuation chunk that falls inside the last window must contain the whole window;
  - a request that hits the radix cache must re-prefill its last window.

### Prefill CUDA graphs

The ≈4 ms per-layer host overhead is removed with CUDA graphs.

- **Capture.** Graphs are captured lazily, at the exact local row count, with no padding. A row count is captured the second time it appears. Each segment keeps at most 32 graphs, evicted LRU.
- **What stays eager.** The CP KV gather, the indexer and the attention core still run eagerly.
- **Failure handling.** After capture, and before the custom all-reduce graph inputs are registered, all ranks vote. If any rank failed to capture, all ranks discard the capture together and fall back to eager.

### Sparse-attention indexer

In V4.1's ratio-1/2 layers, an indexer first picks the top-k KV positions for each query, and then sparse attention runs on them. Upstream's prefill indexer is in torch: it dequantizes the index keys to BF16, runs an einsum, then calls `torch.topk`.

**Prefill.**

- We unpack each request's FP4 keys once, convert them to E4M3 and score them with FP8 tensor cores.
- Once the scoring size reaches 2M, H20 switches to a keys-major Gluon kernel.
- Top-k uses top-k v2. On ties it always keeps the earlier position, so the result no longer depends on the order of atomics.
- Scores match the torch path within tolerance.

**Decode and verify.**

- FP4 keys are scored straight from the request table.
- Several verify rows of the same request share the decoded key tiles.
- When there are enough candidate windows, consumer layers score only the candidate blocks instead of scanning the whole context.

### MoE: Humming W4A8

V4.1-Flash stores its routed-expert weights in FP4 (MXFP4), but H20 is a Hopper GPU without FP4 tensor cores. This part uses Humming ([github.com/vllm-project/humming](https://github.com/vllm-project/humming)), **open-sourced by Ant Group**, a JIT-compiled quantized GEMM library.

- **How it works.** Humming converts the FP4 weights to FP8 inside the kernel, with the weights' E8M0 scales folded into the operands ahead of time. It then feeds them, together with FP8 activations, into the FP8 tensor cores (W4A8).
- **Why it helps.** The weights stay 4-bit in memory, so less data is read, and the compute still runs at FP8 speed.
- **Adoption.** SGLang already integrates it as an MoE backend ([sgl-project/sglang#23754](https://github.com/sgl-project/sglang/pull/23754)). FlashInfer's recent MXFP4×FP8 MoE path for Hopper follows Humming's weight preprocessing and dequantization method (`flashinfer-ai/flashinfer#3738`).

Humming is very efficient on H20. We once profiled a cold 128K prefill (TP4 + CP4):

- the two routed-expert GEMMs took more than a third of GPU time;
- from measured kernel times and shapes, w13 and w2 reached 84% and 83% of FP8 dense peak.

This branch changes how Humming is used:

- **Stream-K is off.** It accumulates K slices in arrival order, so the first token of a short input could vary from run to run.
- **Less padding.** Per-rank weight padding shrinks from 256/128 to 64/64. Under TP8, w13's N drops from 768 to 576.
- **Fusion.** SwiGLU and the FP8 quantization of the W2 input are fused into one kernel. The weighted sum of the routed experts is deferred until it is merged with the shared expert.
- **Tuning.** A Humming header overlay is added, and H20 tuning tables are loaded per role.

### mHC and FP8 GEMM

**mHC.** The main problem with mHC was unstable results.

- **Upstream.** On Hopper, upstream uses bf16x3 for mHC with more than 32 rows. On H20 the results change with the run and with batch size, and the error relative to fp64 is 5–10× larger.
- **This branch.** We use tf32x3 split-K plus a sinkhorn written in TileLang. Results are deterministic, and from 2 rows up they do not change with batch size.
- **Fusion.**
  - Each post is fused with the next sublayer's collapse.
  - With many rows, RMSNorm is fused in as well, and the result is bit-exact with FlashInfer's RMSNorm.

**FP8 GEMM.**

- Activations of block32 linear layers are quantized directly into the scale layout DeepGEMM expects.
- Small-M GEMMs pick a swap-AB or split-K kernel from a tuning table.
- wo_a stays in FP8, with inverse RoPE fused into the rounding kernel.
- The DSpark draft uses an FP8 copy of the LM head. The target stays BF16 by default; quantizing the target is the lossy option.

## Decode: removing the work every GPU repeats

On a single node, decode uses CP decode attention TP, and all 8 GPUs hold all decode rows. Upstream repeats the same per-row work on every GPU:

- each GPU has only 8 attention heads, yet FlashMLA pads them to 64;
- mHC and Engram compute all rows on every GPU;
- all TP all-reduces go through FlashInfer.

We split this work by row:

- **Head↔row swap (from 96 rows).** Each GPU handles 1/8 of the rows, but computes attention with all 64 heads. On 8×H20-3e at 64 concurrent requests, a single FlashMLA call drops from 257 μs to 47 μs.
- **TP-SP (from 64 rows).** Each GPU keeps only 1/8 of the residual stream. mHC, Engram and the DSpark capture compute only those rows. The result is bit-exact with the original path.

Communication and scheduling:

- **All-reduce.** TP all-reduce uses custom all-reduce v2. On 8×H20-3e at 64 concurrent requests, one call drops from 63 μs to 22 μs.
- **Graph batch size.** CUDA graphs are captured at the real batch size. Upstream kept CP alignment, so a single session replayed the bs=4 graph and computed 24 rows instead of 6.
- **FlashMLA tile schedule.** A cost model fitted on H20 picks the schedule. The scheduler is adapted from FlashMLA's `get_decoding_sched_meta` (MIT license).

DSpark:

- Draft rows are packed into a single row for FlashMLA.
- Verify's greedy argmax and the draft's candidate selection run directly on the vocabulary shards. This skips the full gather of logits, and the result is the same as with the gather.
- Draft preparation no longer copies lengths back to the host. That copy used to block the CPU for 2.8–2.9 ms per step.

**PD decode role.** The decode role in PD uses attention DP, which needs a gather before MoE and a combine after it.

- The gather moves from NCCL to an NVLink all-gather.
- The combine changes from "all-reduce, then slice" to a direct reduce-scatter.
- On an 8×H20 D at batch 256 (synthetic requests, 61440 input / 8192 output), this part of each step drops from 6.60 ms to 5.31 ms.

## Serving

Commit 9 handles serving-layer issues.

**DP dispatch for decode.**

- **Upstream.** The DP controller refreshes its load snapshot every 20 ms. Each refresh drops requests that were sent but not yet received by the rank, so bursts keep flowing to ranks that are already full.
- **This branch.** We count in-flight requests in the load and skip full ranks.
- **Example.** With 128 requests sent at once to 8 ranks (16 max each), upstream assigns [25, 25, 13 × 6]; we now assign [16 × 8].

**Admission wait.**

- DSpark has a rule that holds back prefill when fewer than 4 slots are free, so that requests can batch.
- After a burst, the last few requests then idle through a whole decode round. At 64 concurrent requests, their TTFT is about 10 s.
- Removing the rule outright makes TPOT worse and cuts throughput by 11%. So we cap this wait at 32 scheduling rounds.

**SWA prefix reuse.**

- Bounded replay writes late-layer rows only for the last window, so upstream backs off a whole window on every prefix match.
- We record on the radix tree which ranges really have late-layer rows computed, and reuse the recorded parts directly.

**HiCache.** Upstream does not allow `--hicache-size` for DeepSeek V4. Now the per-rank host cache can be set in GB.

**PD failure handling:**

- When prefill loses contact, decode no longer frees KV pages that may still be being written. It quarantines them and reclaims them after a late ACK arrives or after 300 s of lost contact.
- When a prefill rank stops reporting, or its scheduler loop is stuck for more than 180 s, the bootstrap server's `/health` returns 503. Decode's heartbeat then marks it as lost.
- When prefill gives up on a request before handoff, it tells decode the reason right away, so decode does not wait for a timeout.

**These fixes apply to upstream as well:**

- With CP + DSpark + bounded replay, the first request crashes because the tail gather has the wrong layout.
- On SM90, hc-prenorm split-K races with WGMMA when the split count does not divide the K blocks. On H20 the relative error can reach 10–18%.
- When cluster top-k's threshold bucket overflows, candidates are truncated arbitrarily.
- PD handoff has several concurrent read/write races.

## EPD: separating encode, prefill and decode

Upstream main does not support EPD deployment for V4.1 yet. Commit 10 completes this path:

- E loads only the vision part, reading 2 of 48 weight shards. P and D do not load the vision tower, and prefill still uses CP.
- Under CP, image features are merged into the full input before it is split. This fixes image Q&A, which used to fail on every request.
- D asks E only for preprocessing metadata and no longer waits for image embeddings.
- Encoders share an embedding cache through `/dev/shm`. A 503 caused by registration conflicts between multiple tokenizer workers is also fixed.
