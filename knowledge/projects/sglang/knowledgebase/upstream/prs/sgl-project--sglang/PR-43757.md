# [PD] Retract transferred decode requests on a retract pause

[Upstream PR](https://github.com/sgl-project/sglang/pull/43757) · state: closed · merged: True

## Original PR description

## Motivation

On a PD decode server, a request whose KV has arrived waits in `waiting_queue` for a running slot while it already holds its request row and KV. Since #40779, a flush issued while the engine is paused ignores `waiting_queue` (`is_fully_idle(ignore_waiting=self._engine_paused)`), on the premise that waiting requests hold no KV. That premise does not hold for these decode requests:

- `pause_generation(mode="retract")` retracts only the running and last-step requests, so the transferred waiters keep their rows.
- `flush_cache` (directly, or the one after `update_weights_*`) then succeeds and frees KV they still own.
- After `continue_generation` they decode on freed pages, and the decode scheduler stops on `pool memory leak detected` (available > total: the pages were freed twice).

## Modifications

- `Scheduler.pause_generation`, retract mode on PD decode: also retract the waiting requests that hold a request row. They take the same `hold_rebootstrap` path as the running ones and rebuild their KV under the weights in use after the pause.
- `Scheduler.is_fully_idle(ignore_waiting=True)`: still reports not idle while any waiting request holds a request row, so a paused flush cannot free KV that is in use (for example after an in-place pause).
- Tests: the decode retract case in `test_scheduler_pause_generation.py`; the refusal in `test_scheduler_flush_cache_after_retract.py`, whose waiting requests now state that they hold no row.

## Checks

- 1P1D, Qwen3-0.6B, mooncake transfer, `--max-running-requests 2`, 8 requests of 1024 tokens: pause (retract) while 6 requests wait holding KV, `flush_cache`, `continue_generation`.
  - main: the flush succeeds, the requests finish, then the decode scheduler exits with `pool memory leak detected`.
  - This PR: all requests finish and the decode server stays healthy.
- Unit tests under `test/registered/unit/managers/`, `managers/scheduler_components/`, `disaggregation/`, `batch_overlap/` and `entrypoints/`: same results as main.
