# [Perf] openai: extend parallel prompt encoding's intra-message cuts to Qwen2/Qwen3, o200k and DeepSeek-V3 pipelines

[Upstream PR](https://github.com/sgl-project/sglang/pull/44392) · state: open · merged: False

## Original PR description

## Motivation

#41259 made `parallel_prompt_encode` cut a rendered chat prompt at added-token boundaries for any fast tokenizer, and inside a message only for the exact GLM / Llama-3 `Split` regex. A single long message is most of an agentic prompt, so for Qwen3, gpt-oss and DeepSeek-V3/V4 the gap between two role markers was still encoded on one thread. This PR extends the intra-message cuts to those pipelines with the same argument the module already makes, and keeps every refusal path as it is.

## Modifications

- The single `_INTRA_SPLIT_REGEX` / `_INTRA_CUT` pair becomes a small table `_INTRA_SPLIT_REGEXES` of verified `Split` regex tuples: GLM / Llama-3, Qwen2 / Qwen3, Qwen3.5 (which keeps marks in the letter run), o200k as used by gpt-oss, and DeepSeek-V3, whose `\p{N}{1,3}` and CJK splits run ahead of its main regex. `_intra_cut_safe` still selects by the serialized backend config, which must be `Sequence[Split(Isolated, not inverted)..., ByteLevel]`, BPE without dropout, and a normalizer that is either the identity (none, or an empty `Sequence`) or NFC with every added token matched on the raw text.
- The cut points stay "letter|space letter" and "newline|letter", and a digit or a CJK ideograph (U+4E00–U+9FFF) after a newline is accepted as well. In each listed regex no match continues from a letter into a space, and no match continues from `\n` into a character other than whitespace, `\r`, `\n` or, for o200k, `/`. Truncating after a letter cannot change a match, and after `\n` the only lookahead that could flip, `\s+(?!\S)`, is shadowed by the earlier `\s*[\r\n]+` alternative. DeepSeek's leading digit and CJK splits cannot straddle such a cut, since the character before one, a letter or `\n`, is neither a digit nor in their ranges.
- With NFC, as in Qwen3, both characters beside a cut are ASCII (or, after a newline, a CJK ideograph). NFC leaves them unchanged, nothing reorders across them and neither is the second half of a canonical composition, so NFC of the text is NFC of the chunks concatenated, and the character after the cut is still not whitespace or a line break even when a following mark composes with it. Added tokens matched after normalization are invisible to the raw-text cut search, so with NFC they disable the intra cuts (Qwen3's 26 tokens are all `normalized: false`). The anchor conditions follow the cut admission argument of the Delta Tokenizer paper (https://arxiv.org/abs/2610.19801, §5 and supplement §S4); the ASCII case used here is its fast path.
- An empty normalizer `Sequence` is treated as the identity when matching `normalized: true` added tokens, as the no-normalizer case already is. DeepSeek's role markers (`<｜User｜>`, `<｜Assistant｜>`, ...) are such tokens, so they are now both protected from cuts and cut points themselves.

MiniMax-M3 and OLMo-3 stay out on purpose; their `Split` is `Removed` + `invert`, which the structural check already refuses. So do Kimi-K3, Mistral's tekken regex, Ling and Laguna. They all fall back to the added-token cuts as before.

## Accuracy Tests

An offline check outside the unit suite covers 11 real tokenizers (Qwen3-8B, Qwen3-0.6B and Qwen3.5-0.8B via `AutoTokenizer`; Qwen3.8, gpt-oss-120b, DeepSeek-V3, DeepSeek-V4-flash, DeepSeek-V4.1-flash and HY4 from their `tokenizer.json`; Llama-3.1 and GLM as regression). Each one ran 2,520 fixed-seed fuzz texts (letters, digits, CJK, kana with dakuten, Hangul jamo and syllables, combining marks and NFC-composable pairs, U+0958, emoji with variation selectors / skin tones / ZWJ, every kind of newline and whitespace, each family's special tokens), with every candidate cut point taken (143,809 per tokenizer) and the default chunking run with all three `add_special_tokens` variants, plus 7 long chat-shaped prompts per tokenizer (English, Chinese, code, logs, a mixed script, and single 141K / 178K-character messages). All ids were identical to `tokenizer.encode`. A probe over 11 candidate cut patterns confirmed that the two unsafe ones for o200k (`newline|/`, `letter|'`) are caught by the same harness (713 / 707 mismatches), and that the patterns used here show none.

The unit suite builds each verified pipeline in memory (900-token BPE, the real regexes, `NFC()` for Qwen, an empty `Sequence` plus a normalized added token for DeepSeek) and takes every cut point on 36 edge texts with four special-token placements and on fixed-seed fuzz (4,030 texts for the existing pipeline, 2,010 for each new one). A second layer runs the same on real `tokenizer.json` files when they are in the Hugging Face cache or named in `SGLANG_TEST_TOKENIZER_JSONS`, and skips otherwise. The suite also pins the new refusals: NFD, NFC with a `normalized: true` added token, a `Split` with `Removed` behaviour, and DeepSeek's splits in another order. The original tests of #41259 pass unchanged.

```bash
python3 -m pytest test/registered/unit/entrypoints/openai/test_parallel_prompt_encode.py
# 24 passed, 38 subtests passed (with real files); 23 passed, 1 skipped without
```

## Speed Tests and Profiling

The timings are for a single long message, encoded directly with `tokenizer.encode` and through `parallel_prompt_encode` with 64 chunks, one measurement per fresh process on a 2x EPYC 9115 box with the plan already built.

| tokenizer | prompt | chars / tokens | direct | parallel |
|---|---|---|---|---|
| Qwen3-8B | English | 199,850 / 59,408 | 55–57 ms | 15.5–16.2 ms |
| Qwen3-8B | Chinese | 188,050 / 100,008 | 87–115 ms | 15.5–22.4 ms |
| Qwen3-8B | code | 224,050 / 69,008 | 65–67 ms | 15.2–20.5 ms |
| gpt-oss-120b | English | 199,849 / 55,356 | 82–83 ms | 11.0–12.1 ms |
| gpt-oss-120b | Chinese | 188,049 / 128,006 | 106–108 ms | 15.8–28.5 ms |
| DeepSeek-V3 | Chinese | 188,021 / 94,002 | 120–149 ms | 14.7–17.1 ms |

Before this change these prompts had two cut points, the role markers, so the parallel path took as long as the direct encode.
