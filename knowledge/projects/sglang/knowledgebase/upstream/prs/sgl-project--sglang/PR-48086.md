# [Fix] benchmark: Support Gemma 4 in the CSGMV LoRA tuner

[Upstream PR](https://github.com/sgl-project/sglang/pull/48086) · state: open · merged: False

## Original PR description

## Motivation

The CSGMV LoRA tuner fails with `--model google/gemma-4-31B-it`:

```text
AttributeError: 'Gemma4Config' object has no attribute 'hidden_size'
```

It reads dimensions from the top-level config, while Gemma 4 stores its decoder dimensions in `text_config`. Unwrapping that config alone is not enough: sliding and full attention use different head sizes and KV head counts. Reading one global `num_key_value_heads` raises `AmbiguousGlobalPerLayerAttributeError`, and one QKV shape cannot cover both layouts.

## Modifications

- Read the decoder config with `get_text_config()`.
- Read each layer's attention dimensions from `per_layer_config`, falling back to the model config when absent. Generate QKV and output-projection shapes for each distinct layout, alongside the existing MLP shapes. The tuning loop already skips duplicate kernel cases.

For flat text-only configs with uniform attention dimensions, the generated shapes are unchanged. The manual CLI path is also unchanged.

Tuning remains limited to decoder LoRA, matching the language-model scope of `should_apply_lora` in Gemma 3/4 and Qwen-VL. It does not add tuning for vision or audio towers. Shapes without a tuned config continue to use the runtime defaults.

This changes only the offline tuner. Serving code and existing tuning JSON files are untouched.

## Accuracy Tests

Compared the old and new dimension lists on `c8704818` with Transformers 5.19.0. Gemma 4 now produces both attention layouts. Llama-like, Qwen2 without `head_dim`, and manual inputs, including an odd `--qkv-output-dim`, give identical results. This is a CPU config comparison with GPU-only imports stubbed out.

Pre-commit passes.

## Speed Tests and Profiling

On `797af71`, one L4:

```bash
python benchmark/kernels/lora_csgmv/tune_lora_csgmv.py \
  --model google/gemma-4-31B-it --rank 16 \
  --chunk-sizes 16 --total-tokens 4096
```

Without the fix, this fails while reading the config. With it, all nine distinct shrink/expand cases finish and nine tuning JSON files are written. This verifies that tuning completes; no serving speedup is claimed.
