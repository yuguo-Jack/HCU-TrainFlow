# [Test] [AMD] diffusion: Compute the VAE blend test's fp16 reference in fp32 on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/46889) · state: closed · merged: True

## Original PR description

## What

On ROCm, compute the fp16 products in `test_vae_tiled_decode_groups.py`'s per-slice reference loop as an explicit fp32 multiply rounded to fp16. CUDA and every other platform run exactly the same reference as before. No runtime code changes.

## Why

`test_blend_matches_per_slice_loop` (added with the one-pass `ParallelTiledVAE._blend` in #46240) fails on AMD for two fp16 cases, `[100--1-dtype1]` and `[100--2-dtype1]`. Both scheduled ROCm 10 runs that have reached it failed those two cases: [10-27 00:40](https://github.com/sgl-project/sglang/actions/runs/40427865857) and [10-27 12:23, job 122186651868](https://github.com/sgl-project/sglang/actions/runs/40503413710/job/122186651868).

`_blend` is not the problem. The reference loop multiplies fp16 slices by Python floats. On CUDA that multiply runs in fp32 op-math, and `_blend` reproduces it bit for bit. ROCm's fp16 tensor-times-scalar kernel rounds differently. Measured on an MI355X (torch 2.11.0+rocm10.0.0), for the dim -1, extent 66 case (100 clipped to the tile):

| fp16 x × (1 − 1/66), x = 0.0123367… | result |
|---|---|
| exact product | 0.0121498… (just below the fp16 midpoint) |
| fp64 reference, fp32 reference, CPU | 0.01214600 |
| `_blend` on ROCm | 0.01214600 |
| loop on ROCm (`fp16_tensor * float`) | 0.01215363 |

Across the case, the ROCm loop differs from the CPU loop and from the fp32 reference in 318 elements, all on odd slices. `_blend` differs from the fp32 reference in none. Strided and contiguous slices give the same result. The loop's ROCm values match multiplying by the weight rounded to fp16, so the drift only shows for extents whose weights are not exact in fp16, which is why 1 and 64 pass.

## Notes for the reviewer

- The fix is scoped to `torch.version.hip is not None and dtype == float16`. bf16 and fp32 already match on ROCm, and the CUDA reference is untouched.
- Since #46240, ROCm's seam blending is correctly rounded and matches CUDA, where the old per-slice loop did not. So this is a test-only change.

## Test plan

- MI355X, ROCm 10 image, `pytest test_vae_tiled_decode_groups.py -k blend` with `main`'s `vaes/common.py`: `main`'s test file gives `2 failed, 34 passed` (the two CI cases); this branch gives `36 passed`.
- MI300 CI, `multimodal-gen-test-1-gpu-amd` on rocm10 dispatched from this commit: [run 40587808447](https://github.com/sgl-project/sglang/actions/runs/40587808447). All four partitions passed. The blend tests ran in [partition 3](https://github.com/sgl-project/sglang/actions/runs/40587808447/job/122484054047) with no failures.
