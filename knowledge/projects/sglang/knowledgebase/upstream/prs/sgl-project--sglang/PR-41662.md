# [AMD][Perf][MiniMax-M3] Route sparse attention path to use Aiter's `fused_qknorm_idxrqknorm` 

[Upstream PR](https://github.com/sgl-project/sglang/pull/41662) · state: closed · merged: False

## Original PR description

## Motivation

Part of optimizing MiniMax-M3 for **vision-language serving** -- one image per request at 512x512 to 2048x1600, Measurements are on that VL sweep.

On a sparse layer the attention path issues separate launches for qk-norm, rope, a `div_`/cast, the main K/V store and the index-K store. Aiter ships a single fused kernel covering all of it (`fused_qknorm_idxrqknorm`), so this routes to it when — and only when — the kernel's hardcoded assumptions actually hold.


## What this does

Adds an opt-in-by-capability fused path in `MiniMaxM3Attention`. The kernel
hardcodes Gemma-style norm (`1.0f + weight[dim]`), NEOX split-half rope and
head_dim 128; each is checked as a precondition rather than assumed.

- sahirema · comment · 2026-10-13T11:25:37Z · [source](https://github.com/sgl-project/sglang/pull/41662#issuecomment-6144479066)

Closing in favour of #44043.

Since this was opened, `main` has landed `MiniMaxM3Attention._aiter_sparse_qknorm_cache`,
which routes the sparse attention path through aiter's `fused_qknorm_idxrqknorm`
with SGLang cache semantics — the same fused qk-norm + rope + KV-store this PR
was proposing. Rebasing this branch onto current `main` conflicts across ~350
lines in `models/minimax_m3.py`, and the conflict is not drift: it is two
implementations of the same feature meeting at the same call site.

One piece of this PR is **not** covered by what landed. `_aiter_sparse_qknorm_cache`
hardcodes `kv_cache_dtype="fp8_e4m3_unit"`, and `k_scale_float` is never read in
that file — so a non-unit per-tensor KV scale is written to the cache unscaled.
aiter's `fp8_e4m3_unit` and `fp8_e4m3_static` are separate kernel paths with
mutually exclusive contracts (`csrc/kernels/fused_qknorm_idxrqknorm.cu` asserts
that `_unit` refuses scale tensors and `_static` requires them), so the mode has
to be selected from the pool's actual scales. The same applies to a non-unit
index-K scale, which the kernel stores at a hardcoded unit scale.

Both of those are now in #44043 as a ~50-line change on top of the upstream
helper, rather than a second implementation beside it. The unit-scale path is
left exactly as it is.

Not carried over: the per-call reason-string gating from this branch
(`_aiter_fused_store_runtime_reason`), which names the first failing precondition
so the one-time log says *why* the fused path went dark. Upstream returns a bare
`None` from ~30 or-ed conditions. That is a diagnosability improvement rather
than a correctness fix, so it was left out to keep #44043 reviewable — happy to
raise it separately if it is wanted.

The branch is left in place; nothing here is deleted.
