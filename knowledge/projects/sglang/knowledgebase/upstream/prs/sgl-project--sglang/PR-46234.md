# [Fix] disaggregation: Key decode-offloaded KV pages by bigrams under EAGLE

[Upstream PR](https://github.com/sgl-project/sglang/pull/46234) · state: open · merged: False

## Original PR description

## Motivation

With PD disaggregation, `--disaggregation-decode-enable-offload-kvcache` and EAGLE / EAGLE3 / MTP, no page the decode instance offloads to L3 is ever hit by a later lookup. The next turn recomputes the generated tokens' KV, and the decode-side writes only cost IO and storage.

Under EAGLE the prefill tree keys pages by token bigrams, and so does the storage lookup. The decode offload manager hashed plain tokens, so its keys match no lookup. It also assumed the prefill stored `N // P * P` prompt tokens. A bigram key over N tokens has N - 1 entries, so the prefill stores `(N - 1) // P * P`, and when N is a multiple of the page size one page is written by neither side.

## Modifications

- Read `is_eagle` from the speculative algorithm at init, the same expression `kv_cache_builder.py` passes to the prefill tree. The tree's Mamba exemption does not apply, because decode offload rejects Mamba pools.
- `_compute_prefix_hash` builds a `RadixKey(..., is_bigram=is_eagle)` and hashes it with `get_storage_hash_str`, the helper the tree and the lookup use. Under EAGLE each hashed span carries one lookahead token.
- `_prefill_offloaded_len` subtracts one token under EAGLE before page-aligning.

Non-EAGLE keys are unchanged.

## Accuracy Tests

New case in `test_specv2_kvcache_offloading.py`: offload an 8-token prompt (page size 4) through `offload_kv_cache` and the write ack, then check that the prefill's stored chain plus the decode-written hashes equals the chain a next-turn lookup computes, with EAGLE on and off.

- main: `is_eagle=True` fails; `is_eagle=False` passes
- this PR: both pass

`test_scheduler_pause_generation.py` gets the new attribute on its stub manager. CPU only; no end-to-end PD run.
