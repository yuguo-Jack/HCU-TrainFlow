# [AMD][V4.1] Trim more per-cycle launches in DSpark decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/43860) · state: open · merged: False

## Original PR description

## Motivation

On MI35x, DeepSeek-V4.1-Flash DSpark decode at batch 1-2 is launch-bound: each launch costs about 2 µs of graph replay. Around the verify and draft graphs, a decode cycle still runs a chain of small glue launches whose work fits in launches that already exist:

- **Static verify epilogue:** the greedy accept, finalize, the out-token build, the int64 `correct_len` / `bonus` copies and the injected-commit gate take 10 kernels. Under TP sync they also take 3 broadcasts.
- **mHC heads:** `hc_combine` received an fp32 copy of the bf16 rows before both the target and the draft head.
- **DSpark aux captures:** the per-layer hc-means were concatenated by a `torch.cat` in the logits processor.
- **Candidate blocks:** the all-zero compact page table had its own fill launch.

## Modifications

Every change is gated to HIP, so CUDA runs exactly the code it ran before. Every result is bitwise identical to the chain it replaces.

- **One-launch static verify epilogue** (`static_verify_epilogue_triton` in `dspark_accept.py`): after the argmax, a single launch writes all six persistent accept buffers and the gated commit lengths.
  - Under TP sync it takes two launches around one broadcast of the packed `(correct_len, bonus)`, instead of three broadcasts. The cap trims are zero on every rank, so they need no broadcast.
  - `SGLANG_SIMULATE_ACC_LEN` replaces the correct length after the served accept and keeps the served bonus, as `_accept` does. Simulated-acceptance benchmarks therefore take the same path.
- **`hc_combine` reads the bf16 rows directly:** it widens unit-stride rows on load. This drops the fp32 copy in `DeepseekV4Model` and in the DSpark draft head.
- **Packed aux means:** in decode and target verify, the hc-means write their slices of one packed buffer (`torch.mean(out=)`), so the logits processor's existing tensor path skips the `torch.cat`. Extend keeps the list, because its early captures can be narrowed to the late-layer tail rows.
- **Candidate blocks:** the lengths launch also writes the zero compact page table.

Launches removed per decode cycle on main, counted with the torch profiler: 19 at TP2/TP4 (epilogue 17 kernels + 3 broadcasts → 4 + 1, 2 `hc_combine` casts, 1 `torch.cat`, 1 fill) and 18 at TP1 (epilogue 17 → 3). On top of #43821, which already trims the `_accept` chain, it is 14 and 13.

Relation to #43821: that PR trims the ROCm `_accept` chain. With this PR the static epilogue on HIP no longer calls `_accept`, which then serves only the ragged (cutoff) path. The two PRs are independent; they overlap only where both append cases to `test_dsv41_decode_glue_hip.py` and set its `est_time`.

## Accuracy Tests

`test/registered/kernels/ops/attention/dsv4/test_dsv41_decode_glue_hip.py` (gfx950): 23 passed (17 new). It takes 19.5 s with a cold cache, 16.8 s before this PR, so `est_time` goes from 15 to 20. Each new case guards one regression:

- **Static epilogue parity:** every persistent accept buffer and the gated commit lengths must equal `_accept` + the gate, bitwise.
  - Covers strides 2, 5 and 8 and batches 1, 7 and 16, with and without a gate.
  - Covers rank 0's broadcast decision overriding this rank's, and a simulated length.
- **Zero page table:** the compact page table comes from a poisoned `torch.empty`, so a row the lengths launch misses fails.
- **`hc_combine` on bf16 rows:** the result must be bitwise the fp32 copy's, which fails if the kernel computes in bf16.
- **Packed aux means:** must be bitwise mean-then-cat in capture order, and a partial capture keeps the list.

Mutation checks: removing the cap-trim store, the rank-0 broadcast, the zero page-table store, the fp32 widening in `hc_combine`, or the simulated-length override each fails its test.

Related suites, unchanged:

- `test_dspark_kernel_parity`: 1 passed (20 subtests).
- `test_ragged_verify`: 10 passed.
- `test_dspark_simulated_bonus`: 3 passed.
- `test_dspark_markov_sample`: 9 passed.
- The CPU unit tests importing the changed modules: 18 passed.

End to end, DeepSeek-V4.1-Flash TP4 with DSpark and real acceptance, on main d1357bf87b with this PR:

- Correct answers (391 / Paris / 42) and 0 NaN / error lines.
- Mean accept length 2.67 over the decode log lines, against about 2.55 on main. A wrong aux packing would show up here: it lowers acceptance but leaves the verified outputs correct.
