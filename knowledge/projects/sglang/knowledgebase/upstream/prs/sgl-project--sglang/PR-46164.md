# [Refactor] rust-server: Tokenize and apply chat model rules through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/46164) · state: closed · merged: True

## Original PR description

Stacked on #45449. #45449 integrates rust-server with `sglang-processor`; this PR moves what rust-server still duplicated into the processor, so the server renders, tokenizes and parses only through it, and fixes the processor bugs that integration surfaced.

## Modifications

**rust-server through the processor**
- **Dynamo only through the processor.** rust-server drops its own `dynamo-tokenizers`, `dynamo-parsers` and `dynamo-protocols` dependencies and uses the processor's re-exports (adding `dynamo_parsers`), so its Dynamo versions are always the processor's.
- **Tokenize through the processor's `TextTokenizer`.** The server's duplicate `TextTokenizer`/`DynamoTokenizer` are removed.
  - The processor's gains the configured BOS (Python's `bos_token_id`, looked up in the vocab) and `encode_chat`: the template without the tokenizer's specials, then the `continue_final_message` text minus one leading BOS (`_append_assistant_prefix_to_prompt_ids`).
  - The tokenizer pool encodes with `add_special_tokens` per call, as Python does, instead of stripping a probed prefix, which missed tokenizers that also append an EOS. Stop strings count their tokens without specials, as Python's `normalize` does.
  - The detok shards decode with the same tokenizer's handle. The processor loads one handle per special-token mode, so the tokenizer is loaded twice at startup.
- **Chat model rules come from the processor.** The typed chat handler hard-coded Python chat-layer rules that the processor's OpenAI layer already ports. They are now `ChatModel` methods that both use:
  - Kimi K3 keeps its special tokens (`keeps_special_tokens`) and leaves its 3-token generation stub out of `prompt_tokens` (`unreported_prompt_tokens`).
  - Whether the reply starts in reasoning (`thinking`, `request_thinking`) is decided as Python's `_get_reasoning_from_request` does, rather than from a `<think>` at the end of the prompt.

**Processor fixes**
- **Selection prefers a checkpoint's own template to the native encoder.** Python's `resolve_chat_encoding_spec` uses DeepSeek-V3.2's encoder, and the other display-name native encoders, only when the checkpoint ships no chat template. Selection picked them first.
- **Selection guesses a legacy template from the model path before reading the checkpoint's template files.** This is Python's `load_chat_template` order. Before, a model such as llava-onevision or internvl that also ships `chat_template.json`/`.jinja` rendered with the Jinja template.
- **`TemplateError::EngineOnly` marks the valid requests the SGLang-parity renderers decline** (`"... renders on the engine"`), for example Qwen3.8 floats such as `0.000001`. rust-server has no engine to hand these to, so it renders them through the formatter's own template, as before the parity path existed, instead of answering 400. DeepSeek-V4 has no other path and still declines; #45872 restores V4.1 through Dynamo's encoder.

sgl-router uses the same selection and `lower_chat`, so it gets the selection fixes. `lower_chat` now calls the new `ChatModel` methods with unchanged behaviour, and the router only adds context to `render_request` errors, so the new error variant changes nothing there.

## Tests

- Unit tests:
  - The processor tokenizer resolves the configured BOS and drops only one BOS from a continuation.
  - The tokenizer pool encodes rendered prompts without specials.
  - A V3.2 checkpoint's own template wins over the native encoder.
  - A legacy model path wins over a discovered `chat_template.jinja`.
  - Qwen3.8's `history_float_arguments` and `tool_float_values` fixtures render through the template.
- `cargo test`, clippy and fmt pass for `sglang-processor` and `sglang-server`. `sglang-processor` builds with `parser`, `render`, `tokenizer`, `openai` and `render,openai` only, its OpenAI parity fixtures pass, and `sgl-router` builds against it.
- Not live-tested on a model.

## Not covered

- A discovered `chat_template.jinja` goes through the same newline handling as a `--chat-template` file, where transformers reads it raw. This only matters for a literal `\n` in template text.
