# [Fix] mem_cache: Chunk MambaPool temporal state copy to avoid OOM spike

[Upstream PR](https://github.com/sgl-project/sglang/pull/47984) · state: open · merged: False

## Original PR description

## Motivation

Fixes #47916.

`MambaPool.copy_from` copied the temporal state with `temporal[:, dst] = temporal[:, src]`. The right-hand side gathers every source slot into one temporary of `n * slot_bytes`. When radix COW copies several checkpoints in one scheduler step, that spike can exceed free VRAM and the step fails with CUDA OOM. The issue's reporter measured 2 OOM retries on a 12-request burst (GLM-5.3-Flash, TP=2, `--mem-fraction-static` 0.965); the failed allocation (285,212,672 B) was exactly 8 slots. Credit to the reporter for the diagnosis and measurements.

## Modifications

- Add `MambaPool._copy_temporal_slots`, which copies in chunks bounded by `_MAMBA_TEMPORAL_COPY_CHUNK_BYTES` (64 MiB, at least one slot per chunk). It is used by both the fused and the fallback branch of `copy_from`.
- A copy that fits in one chunk stays a single batched assignment, so small copies are unchanged.
- Chunking is only equivalent to the batched copy when src and dst slots are disjoint, which the fused conv copy in the same function already requires. Under `SGLANG_DEBUG_MEMORY_POOL` the helper asserts this when it actually chunks.
- The fallback branch's conv copy is left as is; its per-slot state is much smaller than the temporal state.
- Tests in `test_mamba_unittest.py`: chunk-boundary correctness on the fused and fallback paths, and a CUDA-only peak-memory regression test.

## Accuracy Tests

Not applicable to model outputs; the copy is value-identical for disjoint slots. `test_mamba_pool_copy_from_chunk_boundaries` checks every destination equals its source (5 slots, 2-slot chunks) and that no other slot changes, on both the fused and the fallback path.

Tests run on 1x H100 PCIe (torch 2.14.1+cu130, Python 3.12):

- With this change: the 3 `copy_from` tests pass (2 subtests), and `test_mamba_unittest.py` plus `test_mamba_slot_fused.py` pass (20 passed).
- With only `memory_pool.py` reverted to the base commit: `test_mamba_pool_copy_from_peak_memory_is_chunked` fails, so it guards the bug.

## Speed Tests and Profiling

Same H100, using the unit-test pool (temporal slot = 36.0 MiB, bf16). "batched" is the old behaviour (chunk budget set to infinity); "chunked" is this change with the default 64 MiB budget. Peak extra memory is `max_memory_allocated` minus the baseline during one `copy_from`; time is the mean of 20 calls.

| slots | mode | extra MiB | ms/copy |
|---|---|---|---|
| 1 | batched | 36.0 | 0.242 |
| 1 | chunked | 36.0 | 0.241 |
| 2 | batched | 72.0 | 0.483 |
| 2 | chunked | 36.0 | 0.463 |
| 4 | batched | 144.0 | 0.936 |
| 4 | chunked | 36.0 | 0.906 |
| 8 | batched | 288.0 | 1.844 |
| 8 | chunked | 36.0 | 1.794 |

Peak extra memory no longer grows with the number of slots, and copy time is unchanged within noise. The 8-slot "batched" figure (288 MiB) matches the 285 MB allocation in the issue.

Not verified: an end-to-end burst test on a real hybrid model (GLM-5.3-Flash); the reporter's runtime patch used the same idea and showed 0 OOM retries.
