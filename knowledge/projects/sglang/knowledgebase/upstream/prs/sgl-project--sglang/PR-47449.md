# [Feat] scheduler: Add max-queued-tokens for request management

[Upstream PR](https://github.com/sgl-project/sglang/pull/47449) · state: open · merged: False

## Original PR description

Motivation

Limiting the number of queued requests does not bound the amount of pending work when input lengths vary. A queue containing a few long prompts can accumulate substantially more input tokens than one containing many short prompts.

Add --max-queued-tokens so users can limit queued input tokens independently of request count.

Modifications

- Add --max-queued-tokens, defaulting to None (unlimited), with support for non-negative integers and suffixes such as 100k and 1M.
- Count input tokens in the waiting queue, including cached tokens and excluding generated tokens and output budgets.
- Enforce both --max-queued-requests and --max-queued-tokens; reject requests with HTTP 503 when either limit is exceeded.
- Extend priority admission to evict multiple strictly lower-priority requests when necessary. Plan all evictions before modifying the queue so rejected requests do not cause unnecessary evictions.
- Preserve existing behavior in disaggregation mode, where these queue limits do not apply.
- Update parameter documentation and add unit tests for token boundaries, combined limits, priority eviction, atomic rejection, and CLI validation.

Ruff lint, Ruff format, isort, and git diff --check also passed.

Speed Tests and Profiling

No throughput benchmarks or profiling were run.

When the token limit is enabled, admission scans the waiting queue in O(n). Priority eviction additionally sorts queued requests in O(n log n). Queued tokens are computed from the current queue rather than maintained in a separate counter.
