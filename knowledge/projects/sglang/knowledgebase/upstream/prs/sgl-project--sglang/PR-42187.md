# [Perf] openai: Reuse encoded prompt segments

[Upstream PR](https://github.com/sgl-project/sglang/pull/42187) · state: open · merged: False

## Original PR description

## Motivation

Agent chat requests resend their conversation history on every turn. The endpoint renders and tokenizes unchanged messages again, which can block the API server's event loop. Reuse token IDs for unchanged prompt segments when the tokenizer supports safe split boundaries.

## Modifications

Add a per-handler prompt-segment LRU, enabled by default through `SGLANG_OPT_USE_CHAT_PROMPT_SEGMENT_CACHE`. Eligible cold misses are batched through the existing parallel encoder, including full validation encodes. The cache is limited to deterministic HuggingFace fast tokenizers without BPE dropout, a text normalizer, whitespace-stripping or whole-word added tokens, or sequence-rewriting post-processors. Split markers must be safe raw-text added tokens, and no added token can cross a split boundary. Unsupported tokenizers use the full-encode path.

Special-token insertion falls back to a full encode when needed. The cache compares segment IDs with a full encode at warm-up and periodically; it disables itself if they differ. Set `SGLANG_OPT_USE_CHAT_PROMPT_SEGMENT_CACHE=0` to disable it. The 64M-character budget covers cached text and does not cap process memory; a single oversized segment can exceed it. Each handler/API worker has its own cache. The environment-variable reference documents the switch.

## Accuracy Tests

The prompt-segment-cache unit suite and scoped formatting pass on the updated branch, including comparisons against full encoding. Earlier offline GLM and Llama tokenizer checks also matched. A running model server, every remote-code tokenizer and memory use near the text budget remain unverified.

Run the unit suites with `python -m pytest` and scoped formatting with `pre-commit run --files <changed-files>`.

## Speed Tests and Profiling

A local CPU benchmark on the previous PR revision with fixture fast tokenizers measured cold tokenization at 7 to 10 ms, compared with 20 to 34 ms before batching cold misses; token IDs matched a full encode. These timings cover tokenization only; they do not measure service latency.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve parallel encoding for cold cache misses**

When the cache is enabled by default, a cold long chat makes all message segments cache misses, and this direct `tokenizer.encode` loop means `_render_and_encode_chat_template` never reaches `parallel_prompt_encode`. For a >32,768-character GLM/Llama-style prompt that satisfies the existing parallel plan, the previous path encoded chunks through `encode_batch`, whereas this path encodes every miss serially and the first three cache calls then serially encode the whole prompt again for validation. One-shot or low-reuse long chats can therefore block the API event loop substantially longer than before; long misses should retain the parallel path or be batched before insertion.
