# [OpenAI] Encode chat prompts one message at a time and reuse the ids across turns

[Upstream PR](https://github.com/sgl-project/sglang/pull/42187) · state: open · merged: False

## Original PR description

## Motivation

This change makes the chat endpoint encode only the new pieces of a prompt. It reuses the token ids of the pieces that it encoded for earlier requests. For a tokenizer that passes the checks below, the ids equal the ids of a full encode.

An agent sends its whole history on every turn. The chat endpoint renders the prompt and encodes all of it again, although only a few messages are new. The encode runs on the event loop of the API server, so it also delays every other request.

This change alone is not measured. The numbers below are from a v0.5.20 backport with an earlier form of this cache and two other prompt-path changes.

## Modifications

- New `PromptSegmentCache` (`entrypoints/openai/prompt_segment_cache.py`). It splits the rendered prompt in front of the special tokens that the chat template names, keeps the ids of each piece, and encodes only the pieces it has not seen. For GLM-5.3-Flash the split tokens are the role tokens, `<sop>`, `[gMASK]`, and the image, video and audio tokens.
- `OpenAIServingChat._render_and_encode_chat_template` uses the cache on the render-then-encode path. The `apply_chat_template(tokenize=True)` path for lossy round trips is unchanged.
- Why the ids are equal: a HuggingFace fast tokenizer without a normalizer first cuts its added tokens with `normalized=False` out of the raw text, leftmost and longest match first. Then it encodes each piece between them alone. If each split point is a token boundary of that first step, the joined ids equal the ids of the whole prompt.
- The cache turns on only when all of these conditions hold. In every other case the server keeps the normal encode path, including upstream parallel encoding when eligible.
  - `SGLANG_CHAT_PROMPT_SEGMENT_CACHE` is on. This is the default.
  - The backend is a HuggingFace `tokenizers.Tokenizer`. Slow tokenizers and `--tokenizer-backend=fastokens` get no cache.
  - The tokenizer has no normalizer. The Qwen tokenizers that I checked and DeepSeek-V3.2 have one, so they get no cache.
  - No added token strips whitespace (`lstrip`, `rstrip`) or matches whole words (`single_word`).
  - The tokenizer does not split special tokens (`split_special_tokens` is off).
  - The post-processor preserves sequence IDs, using the same safety check as the parallel encoder. Sequence-duplicating `TemplateProcessing` processors and nested `Sequence` processors that rewrite IDs get no cache.
  - The chat template is a string and names at least one special token that is a safe split point, and not more than the limit (`_MAX_MARKERS = 32`).
- If a safe post-processor adds special tokens and `add_special_tokens` is omitted or true, the cache encodes the whole prompt. With `add_special_tokens=False`, it keeps segment reuse.
- A special token is a safe split point only if the backend matches it in the raw text (`normalized=False`) and no added token with `normalized=False` can start before it and reach into it.
- Self-check: the cache compares its ids with a full encode on calls 1 to 3 and on every 512th call. On a mismatch it logs a warning, turns itself off, and encodes the whole prompt from then on.
- Memory: each cache drops its least recently used pieces above its size limit (`_DEFAULT_MAX_CHARS = 64 * 1024 * 1024` characters of prompt text).
- The server logs one line for each cache that is on. The environment variable reference has a row for the switch.

## Accuracy Tests

For a tokenizer that passes the checks, the model input does not change. The evidence below separates original offline and backport validation from current-head CPU checks. Upstream runtime CI has not run the tests.

- Unit tests (`test_prompt_segment_cache.py`) build a small BPE tokenizer in memory and compare the ids with a full encode. They cover each turn of a growing conversation, and message content that holds role tokens, parts of role tokens, whitespace at both ends and non-ASCII text. For added tokens that overlap a split point, each case must give no cache or the ids of a full encode. The tests also cover the tokenizers that get no cache, the self-check, a cache that turned itself off, and the eviction order.
- Original CPU package run, before the rebase and follow-up guards: the new test file, `test_chat_prompt_round_trip.py` and `test_serving_chat.py` pass on a CPU-only macOS laptop with the real `sglang` package and the pinned `transformers` and `tokenizers` versions.
- Original real-tokenizer offline runs, before the rebase and follow-up guards: GLM-5.3-Flash, GLM-5.3, GLM-4.7-Flash and Llama-3.2-1B-Instruct. Every turn of a growing tool-calling conversation gave the same ids as a full encode. The content held role tokens, parts of role tokens, CJK text and emoji. Random strings made from the GLM-5.3-Flash split tokens and parts of them also gave the same ids.
- Original random-added-token offline runs, before the rebase and follow-up guards: random sets of added tokens over a small alphabet, half of them with an NFC normalizer. No set that got a cache gave other ids. Without the rule about tokens that reach into a split point, the same check finds sets with other ids.
- Current-head Linux CPU validation: the cache, parallel-encoding and chat round-trip test files pass with `tokenizers==0.23.2` and `transformers==5.19.0`. An isolated tokenizer-only harness loads the exact production cache, parallel encoder and environment modules, and extracts the serving methods from the source. It substitutes the test base class and CI registration; it does not validate full package startup, a running server or GPUs. The focused post-processor regressions failed before their fixes and pass after them: three one-message warm-up calls followed by a multi-message request, direct and nested sequence duplication, and safe special insertion with omitted/true/false `add_special_tokens`. Scoped `pre-commit run --files` passes.
- The absent/disabled-cache regression also verifies that eligible long prompts still reach upstream parallel encoding.
- Server, earlier form only: the v0.5.20 backport ran an earlier form of this cache, with another split rule and other limits, in whole agent sessions. Its self-check found no difference in those runs. This evidence is not for the code of this pull request.

On a server, a mismatch logs `Per-message prompt encoding differs from a full encode. The prompt segment cache is now off.`

## Speed Tests and Profiling

The numbers are in the table above. All are from SGLang v0.5.20 with local patches, not from this exact code and not from main.

Setup: one node with 8 B200 GPUs, two servers of 4 GPUs each, and an FP8 GLM-5.3-Flash checkpoint. The metric is engine time per output token in whole replayed investigations of an agent workload, at temperature 1.0 and top-p 0.95. "16 in flight" and "4 in flight" are concurrent investigations per server.

Leave-one-out: the benchmark stack has every change on, and one run removes one change. Each row is one run, and the reference ran three times. The percentages are against the mean of two reference runs. Read a difference under about 1.5% as no measurable effect.

The prompt path of the backport has three parts:

1. Token ids for text-only requests. Main has this.
2. No decode of the prompt for text-only requests. Main does not have this.
3. An earlier form of this cache.

The numbers cover all three parts, so they are an upper bound for this change. The benchmark stack also has other local patches and settings, for example speculative decoding with draft depth 4 at 16 in flight and depth 3 at 4 in flight.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve parallel encoding for cold cache misses**

When the cache is enabled by default, a cold long chat makes all message segments cache misses, and this direct `tokenizer.encode` loop means `_render_and_encode_chat_template` never reaches `parallel_prompt_encode`. For a >32,768-character GLM/Llama-style prompt that satisfies the existing parallel plan, the previous path encoded chunks through `encode_batch`, whereas this path encodes every miss serially and the first three cache calls then serially encode the whole prompt again for validation. One-shot or low-reuse long chats can therefore block the API event loop substantially longer than before; long misses should retain the parallel path or be batched before insertion.
