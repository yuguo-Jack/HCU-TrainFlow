# [Perf] openai: Reuse encoded prompt segments

[Upstream PR](https://github.com/sgl-project/sglang/pull/42187) · state: closed · merged: False

## Original PR description

## Motivation

Agent chat requests resend their history on every turn, so the server encodes unchanged messages again. On `/v1/messages`, `/v1/responses` and `/v1/tokenize`, that work also blocks the event loop.

#47028 overlaps on the same cache, but reaches it only at 32768 chars and above.

## Modifications

The Jinja chat path cuts rendered text at the template's added tokens that pass `_cuts_at`, and `encode_prompt_segments` serves repeated text from its cache. Tokenizers without such a token keep main's path.

Uncached text under `SGLANG_PARALLEL_PROMPT_ENCODE_MIN_CHARS` is joined with one cut token, encoded as one input on the calling thread, and split at that token's id.

The encoder uses a private backend copy without padding or truncation, because `BaseMultimodalProcessor._call_processor` calls the shared tokenizer with `padding=True`.

Effects:

- Tokenizers with a normalizer, such as Qwen, use this path.
- `SGLANG_PARALLEL_PROMPT_ENCODE=0` turns this path off.
- `--tokenizer-backend fastokens` no longer returns main's HTTP 500 from 32768 chars.

Open limits:

- Unique prompts lose capacity where the API process is the bottleneck, about 25% at 30K (rejected rows), with no loss in real inference at 8K or 30K. Accepting this by default is undecided.
- No self-check compares segment ids with a full encode.
- No local tokenizer uses BPE dropout, which has no gate.

## Accuracy Tests

No model accuracy eval ran. At head `47d745bdd7`, prompt ids matched a full encode on 52 real tokenizers, through real templates and raw segments. Llama-3.2-1B, Qwen3-0.6B and Qwen3-VL-2B servers matched main.

The private copy protects the batch path. With the real in-process `Lfm2VlImageProcessor` and 16 chat threads, prompts of about 40K chars gave wrong ids on a shared backend in 2 of 3 runs, and on the private copy in none of 3. The LFM2.5-VL HF processor, called directly with `padding=True` at that size, gave wrong ids on a shared backend in 6 of 6 runs, and one run kept wrong ids in the cache. It gave none on the private copy in 6 runs.

Prompts of about 3K chars use one input, and `padding=True` cannot pad one input. Through `Lfm2VlImageProcessor`, they gave no wrong ids on a shared backend in 14 runs, and none on the private copy in 24 runs. With the one-input path also removed, they gave wrong ids on a shared backend in 6 of 8 runs, and all 6 kept wrong ids in the cache. Live LFM2.5-VL HTTP traffic did not reproduce wrong ids, so the live rate is unmeasured.

Not run: GLM-5.2, GLM-4.7, Muse Spark Open and GLM-5.3-Flash serving.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve parallel encoding for cold cache misses**

When the cache is enabled by default, a cold long chat makes all message segments cache misses, and this direct `tokenizer.encode` loop means `_render_and_encode_chat_template` never reaches `parallel_prompt_encode`. For a >32,768-character GLM/Llama-style prompt that satisfies the existing parallel plan, the previous path encoded chunks through `encode_batch`, whereas this path encodes every miss serially and the first three cache calls then serially encode the whole prompt again for validation. One-shot or low-reuse long chats can therefore block the API event loop substantially longer than before; long misses should retain the parallel path or be batched before insertion.

Useful? React with 👍 / 👎.
