# [Fix] GraniteMoE: pass RoutingMethodType to FusedMoE for flashinfer_trtllm

[Upstream PR](https://github.com/sgl-project/sglang/pull/44063) · state: open · merged: False

## Original PR description

## Motivation

Serving a compressed-tensors NVFP4 W4A4 `GraniteMoeForCausalLM` checkpoint on SM100 with `--moe-runner-backend flashinfer_trtllm` fails at load with a bare `AssertionError: layer.routing_method_type is not None` (`CompressedTensorsW4A4Nvfp4MoE.apply_weights`). The default backend (`auto` / FlashInfer CUTLASS) loads and serves the same checkpoint fine.

Root cause: `GraniteMoeMoE` (in `python/sglang/srt/models/granitemoe.py`) constructs its `TopK` with `renormalize=True` but never declares a `RoutingMethodType` on its `FusedMoE` layer. The flashinfer TRT-LLM MoE path performs routing inside the fused kernel from `routing_logits` and requires the declared method to pick the right routing formula — hence the assert. Models with the same routing already pass one explicitly (e.g. `exaone_moe.py` and `qwen2_moe.py` pass `RoutingMethodType.RenormalizeNaive` alongside a renormalizing `TopK`).

Fixes #43987

## Modifications

- `python/sglang/srt/models/granitemoe.py`: pass `routing_method_type=RoutingMethodType.RenormalizeNaive` to `FusedMoE` in `GraniteMoeMoE` (plus the import). `RenormalizeNaive` is defined as "Softmax -> TopK -> Renormalize", which is exactly what this model's `TopK` does (default `scoring_func="softmax"` with `renormalize=True`), so the TRT-LLM fused kernel computes the same routing weights as the native path. No behavior change for other backends: every read of `layer.routing_method_type` lives on the flashinfer TRT-LLM branches.

## Tests

- No GPU or torch on this machine, so a runtime load test was not possible here. Verification was by source inspection against the real codebase:
  - The TRT-LLM FP4 MoE runner bypasses the separate `TopK` (`TopKOutputChecker.format_is_bypassed`) and passes `routing_logits` + `routing_method_type` into `trtllm_fp4_block_scale_moe`; declaring the method is what unblocks the NVFP4 `apply_weights` assert.
  - The pairing mirrors existing models (`qwen2_moe.py`: `TopK(renormalize=...)` + `FusedMoE(routing_method_type=RoutingMethodType.RenormalizeNaive)`; same in `exaone_moe.py`).
  - Grepped all `layer.routing_method_type` readers: they sit only on the flashinfer TRT-LLM paths (`compressed_tensors_w4a4_nvfp4_moe.py`, `compressed_tensors_w4a4_mxint4_moe.py`, `compressed_tensors_w8a8_fp8_moe.py`, `moe_runner/flashinfer_trtllm.py`), so the default CUTLASS path is unaffected.
- `ruff check --select F401,F821,F823,UP037`, `ruff format --check`, `python -m py_compile`, and `git diff --check` all pass on the touched file (two >88-col lines in the file pre-date this change).
- Requesting CI from a maintainer since I cannot run the GPU tests locally.
