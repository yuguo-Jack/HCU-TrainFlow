# [Perf] kda: Reuse one int64 cu_seqlens per batch in FlashInfer prefill to avoid per-layer host sync

[Upstream PR](https://github.com/sgl-project/sglang/pull/44846) · state: open · merged: False

## Original PR description

## Motivation

FlashInfer's CuTe DSL KDA prefill (`recurrent_kda(backend="cute-dsl")`) reads `cu_seqlens` back to the host to plan its routes. It skips that read only when it gets the same int64 tensor object as on the previous call (`kda_chunked_bt16._cu_seqlens_contents`). Our KDA backend passed `query_start_loc` as int32. FlashInfer recasts any int32 `cu_seqlens` to a new int64 tensor on every call (`kda_prefill_cute.py`), so the cached read was never reused and, on routes that read `cu_seqlens`, **every KDA layer did a blocking device-to-host copy**. The host stalled until the GPU stream drained, once per layer.

GLM-5.3-Flash has 34 KDA layers, and FlashInfer prefill is its default KDA prefill backend on SM100/SM103 (the model has a lower-bound gate).

## Modifications

- `ForwardMetadata` gains `query_start_loc_int64`. `KDAAttnBackend.init_forward_metadata` builds it once per extend forward, only when the extend kernel sets the new `uses_int64_query_start_loc` class flag. Today only `FlashInferKDAPrefillKernel` sets it.
- `forward_extend` passes it through, and `FlashInferKDAPrefillKernel` hands it to FlashInfer as `cu_seqlens`. Every KDA layer of a forward therefore gets the same tensor object, so only the first layer reads `cu_seqlens` back to the host.
- No numerics change: the kernel receives the same offsets, in the same int64 dtype FlashInfer converted them to before.

## Accuracy Tests

The kernel inputs are unchanged apart from reusing one int64 tensor, so this change has no accuracy effect. `test/registered/attention/test_kda_prefill_flashinfer.py` passes on GB300 (8 passed).

## Speed Tests and Profiling

**Setup:** GLM-5.3-Flash on 4x GB300, cookbook GB300 High Throughput command.

```
python -m sglang.launch_server --model-path zai-org/GLM-5.3-Flash --tp-size 4 \
  --dsa-prefill-backend trtllm --dsa-decode-backend trtllm --kv-cache-dtype fp8_e4m3 \
  --moe-runner-backend flashinfer_trtllm
```

**Profile: one forward pass, TP0, EXTEND stage**

16-byte `cu_seqlens` device-to-host copies:

| case | before | after |
|---|---|---|
| 1 x 4096 tokens, 34 KDA layers | 34 copies, 20.3 ms host blocked | 1 copy, 0.03 ms |
| 16 x 1024 tokens | 0 | 0 |

The 16 x 1024 batch takes a FlashInfer route that does not read `cu_seqlens` on the host, so it is unaffected either way.

Before, KDA layer 6 of the 1 x 4096 prefill: `recurrent_kda` takes 2.72 ms, 1.96 ms of it blocked in `_cu_seqlens_contents`.
