## Original PR description

# [NPU] DSA token shard: paged SFA key length is this rank's frontier

> Depends on #42978; only the commits after 0a3f03b6 are new here. The branch is cut from `TamirBaydasov/sglang@0a3f03b6` (`npu-dsa-token-shard`). Upstream has no branch of that name, so this PR targets `main` and the earlier commits are #42978. After #42978 merges, the diff shrinks to the last commit.

## Motivation
#42978 shards the DSA prefill query across attention TP and passes this rank's cumulative query lengths into paged sparse flash attention. The key side is left on the full `seq_lens`.

`npu_sparse_flash_attention` with `sparse_mode=3` right-aligns to `actual_seq_lengths_kv`. That length is one absolute value per request, the same shape as `seq_lens`. Only the rank that holds the tail of a request may see the full length. Every other rank must see the KV length of the last token of that request that landed in its slice. Leaving the full `seq_lens` makes those ranks attend the end of the sequence.

Single request, TP16, prefix 106496, 12119 new tokens (sequence 118615):

| rank | `plan.key_lens` |
|---|---|
| 0 | 107254 |
| 14 | 117866 |
| 15 | 118615 |

The indexer already passes `plan.key_lens` as `actual_seq_lengths_key`. Paged SFA has to use the same per-request frontier. Prefill-CP keeps its own paired lengths and does not take this plan.

Do not pass `cumulative(plan.key_lens)`. Unsharded SFA is given absolute `seq_lens`, not a running sum across requests. A running sum matches the frontier only when the forward has one request.

## Modifications
- `dsa_token_shard.py`: `dsa_token_shard_key_lens` copies `plan.key_lens` to an int32 device tensor once per forward. One absolute length per request. A request with no token on this rank stays 0, so the list stays aligned with the block table.
- `ascend_backend.py` `forward_sparse`: when the token-shard plan is active, this is prefill, and prefill-CP is off, `actual_seq_lengths_kv` is that tensor. Query lengths from #42978 are unchanged.
- `test_dsa_token_shard_plan.py`: pin the TP16 / 12119 frontiers above, and a two-request case whose helper output equals `plan.key_lens` (`[105, 207]`), not a prefix sum.

No new flag. Decode, DCP, and the PD guards are untouched.

## How to test
CPU:

```bash
python -m pytest test/registered/attention/unittests/dsa/test_dsa_token_shard_plan.py -q
```

Service, on top of #42977/#42978, Prefill DP2/DCP1 (global chunk 16384, 8192 per group), Decode DP8/DCP1, MTP 1/1/2. Same 1m ramp as the previous DP2 run (108k shared + 12k request, output 996, concurrency 1024). `max_running` is 1 per group, so each forward is one request and `plan.key_lens` is a single absolute length.

| | before (DP2, no token shard) | this path |
|---|---|---|
| result | TTFT gate fail | PASS, 84/84 |
| TTFT p50 / p90 / p99 | 8.72 / 8.82 / 9.10 s | 3.40 / 3.55 / 3.78 s |
| decode (TPOT p50) | 26.0 tok/s (38.41 ms) | 26.0 tok/s (38.51 ms) |
| input | ~939k TPM | 15779 tok/s, ~947k TPM |

Logs on both prefills: `DSA token-shard is ON` at `attn_tp_size=8`, and `DSA indexer query sharding is active`.

The 1m does not distinguish an absolute frontier from `cumulative(plan.key_lens)`, because there is one request per forward. The two-request CPU check is what keeps the helper from turning the lengths into a prefix sum.
