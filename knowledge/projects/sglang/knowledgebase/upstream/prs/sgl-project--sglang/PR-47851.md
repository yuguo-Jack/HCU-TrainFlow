# [Perf] [NVIDIA] mla: Serve mixed-batch decode rows with the absorbed decode kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/47851) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-mixed-chunk`, a prefill chunk carries the running requests' decode tokens at its end and the batch
runs as `EXTEND`. For DeepSeek-family MLA models on `trtllm_mla`, `handle_attention_trtllm_mla` sends every
non-speculative extend batch to `MHA_CHUNKED_KV`, so each one-token decode row is treated like a prefill request: its
whole cached context is up-projected through `kv_b_proj` and attended with the non-absorbed MHA, prefix chunk by
prefix chunk (`capacity // batch_size` tokens per request per chunk). A decode batch does the same work with one
absorbed MLA decode kernel over the latent cache. As a result, turning on mixed chunks makes decode slower: on
DeepSeek-V2-Lite (below) W3's TPOT is 7.6 ms without mixed chunks and 16.7 ms with them.

This is the MLA counterpart of #43238 (BF16 MHA decode tails on `trtllm_mha`). #30338 does the same split for the
DeepSeek-V4 backend.

Scope on current defaults: extend batches that fit the prefill CUDA graph (≤ 2048 tokens by default) already run
the absorbed MLA path inside the graph, so this changes only larger mixed batches, which is the common case with
`--chunked-prefill-size` 8k–16k.

## Modifications

- `trtllm_mla_backend.py`
  - `init_forward_metadata` finds the decode tail once per forward from `extend_seq_lens_cpu` /
    `extend_prefix_lens_cpu` (no device sync), using the same trailing-one-token rule as #43238 plus a non-empty
    cached prefix. The result goes in a new `TRTLLMMLAMixedDecodeTail` (`msgspec.Struct`) on the prefill metadata,
    with the tail's page table built once for every MLA layer.
  - `forward_mixed_decode_tail` runs the existing `_run_decode_kernel` on the tail rows. The query is built and cast
    exactly as in `forward_decode`, so fp8 and bf16 KV caches are both supported.
  - The causal and prefix passes cover only the prefill requests when the caller passes just their rows. Callers
    that pass every row (other models) get the stock behaviour unchanged.
  - The feature is enabled in `__init__` for `trtllm-gen` without DCP. Subclasses that swap the decode kernel or own
    prefill Q/K/V preparation (`cutedsl_mla`) keep the stock path.
- `forward_mha.py`: `forward_normal_chunked_kv_core` is split into the existing chunked-KV attention
  (`_chunked_kv_attn_mha`, unchanged logic) and a mixed path. The mixed path runs that attention on the prefill rows,
  then serves the tail as `q_nope · W_UK → MLA decode → · W_UV`. Gates: not DSA, bf16 `w_kc`/`w_vc`, no deep-gemm
  bmm, no `kv_b_proj` LoRA, and the query not padded past the batch's real tokens (DP attention).
- `forward_batch_deepseek_mha_mixin.py`: `prepare_chunked_prefix_cache_info(num_reqs=...)` builds the prefix-chunk
  tables for the leading requests only. `prefix_chunk_len` is still sized by the whole batch, so the prefill rows see
  exactly the chunk boundaries they saw before. This matters because the chunk merge is boundary-sensitive (#40903).
- Unit test `test/registered/unit/layers/attention/test_trtllm_mla_mixed_decode_tail.py`:
  - tail detection;
  - the request range of the causal and prefix passes;
  - the decode-tail kernel call against a PyTorch reference for fp8 and bf16 KV (SM100).

## Accuracy Tests

DeepSeek-V2-Lite-Chat (real weights) on 1× B200. It has the same per-GPU MLA geometry as DeepSeek-V3 at TP8: 16
heads, kv_lora 512, rope 64. Flags: `--attention-backend trtllm_mla --kv-cache-dtype fp8_e4m3 --enable-mixed-chunk
--chunked-prefill-size 16384`. Main = nightly `c10e0e17`; release = v0.5.22.

| config | eval | main (before) | this PR |
|---|---|---|---|
| v0.5.22, default flags | GSM8K (`sgl-eval`, 1319) | 56.1% | 56.4% |
| v0.5.22, default flags | MMLU (`sgl-eval`, 2000) | 34.7% | 35.4% |
| v0.5.22, `--disable-prefill-cuda-graph`, 2 runs | 32-shot GSM8K (~6.6k-token prompts, greedy) | 66.7 / 66.0% | 67.6 / 66.6% |
| v0.5.22, bf16 KV, `--disable-prefill-cuda-graph` | 32-shot GSM8K | 68.6% | 69.2% |
| main, `--disable-prefill-cuda-graph` | 32-shot GSM8K | 66.7% | 67.9% |

- **Why the 32-shot eval exists:** short-prompt evals barely exercise this change, because their extend batches fit
  the prefill CUDA graph. The 32-shot GSM8K uses long prompts so that mixed batches take the changed path.
  Instrumented runs confirmed the new path executes during it.
- **Not bitwise-identical:** the decode rows now go through the decode kernel instead of chunked MHA. On the 32-shot
  run, two stock runs give identical greedy text for 8.6% of prompts and the same final answer for 65.3%. Stock vs
  this PR gives 8.9% and 68.8%. So the PR adds no divergence beyond the engine's own batch-composition
  nondeterminism. The unit test bounds the kernel-level difference against an fp32 reference.

## Speed Tests and Profiling

Same model and GPU; `bench_serving --dataset-name random-ids --tokenize-prompt`. W2 = 128 × 8k → 256, all at once.
W3 = 96 × 16k → 512 arriving at 2 req/s, max concurrency 64.

| config | metric | before | this PR | Δ |
|---|---|---|---|---|
| v0.5.22, default flags | W2 TPOT | 79.2 ms | 30.5 ms | −61% |
| | W2 output tok/s | 1000 | 2295 | +129% |
| | W3 TPOT | 76.3 ms | 22.0 ms | −71% |
| | W3 output tok/s | 603 | 913 | +51% |
| v0.5.22, `--disable-prefill-cuda-graph` (2 runs) | W2 TPOT | 81.3 / 79.5 ms | 30.7 / 30.7 ms | −62% |
| | W3 TPOT | 16.8 / 16.6 ms | 7.9 / 8.0 ms | −52% |
| | W3 mean TTFT | 988 / 989 ms | 351 / 367 ms | −63% |
| v0.5.22, bf16 KV | W2 / W3 TPOT | 70.2 / 16.3 ms | 33.5 / 9.1 ms | −52% / −44% |
| main | W2 / W3 TPOT | 80.6 / 16.8 ms | 30.6 / 7.9 ms | −62% / −53% |
| v0.5.22, **without** `--enable-mixed-chunk` | W2 / W3 TPOT | 30.5 / 7.56 ms | 30.7 / 7.63 ms | no-op |

**Larger-model motivation (speed only).** These are from a truncated Kimi-K3: 48 of 93 layers, 12 of them MLA,
**dummy weights**, 8× B200, TP8. W3 TPOT −23%, W2 TPOT −25%, output throughput +24–25%. K3 has 24 MLA layers out of 93
(the rest are linear attention), so read this as a per-MLA-layer effect, not a full-model number.

**Not tested at full scale:** I don't have the hardware to run DeepSeek-V3/R1 or a full K3 with mixed chunks.
Could a reviewer run a DeepSeek-V3 `--enable-mixed-chunk` GSM8K check, or trigger the Blackwell suites?
