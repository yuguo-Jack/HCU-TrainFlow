# [HiCache] Key MLA Mamba state per TP rank in the HF3FS backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/43817) · state: open · merged: False

## Original PR description

## Summary

Fix an existing `main` bug in the HF3FS L3 backend. MLA KV is replicated across TP ranks, but Mamba state is TP-sharded and `should_backup` makes every TP rank back up its own shard. On MLA models every rank collapses to rank 0's file and metadata, and the Mamba component key is `<key>_mamba` with no rank, so every rank writes the same entry and restores another rank's state.

Following #43594 (the same fix for NIXL): on MLA models, Mamba component keys carry the TP rank (`<key>_mamba_{rank}_{size}`); KV and other pools keep their keys. Ranks still share one file and one metadata namespace, so each rank's shard gets its own pages in the shared file. `HiCacheHF3FS` now records the original TP rank before the MLA collapse and takes `tp_size` from the storage config. Existing rank-ambiguous Mamba entries read as misses.

Split out of #41907 so each storage backend is reviewed on its own.
