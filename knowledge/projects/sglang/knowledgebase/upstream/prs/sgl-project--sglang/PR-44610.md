# [Fix] mem_cache: Fix size_per_token to be per-token for DeepSeek V4 host p…

[Upstream PR](https://github.com/sgl-project/sglang/pull/44610) · state: open · merged: False

## Original PR description

## Motivation

`DeepSeekV4PagedHostPool` and `DeepSeekV4StateHostPool` returned `item_bytes` / `state_page_bytes` (per-page) instead of per-token bytes for `size_per_token`, `get_size_per_token()`, and `get_ksize_per_token()`. This caused `load_back_bytes_total` and `hicache_backup_bytes_total` Prometheus metrics to be inflated by a factor of `slot_page_size` (e.g. 128× or 256×).

This caused `load_back_bytes_total` and `hicache_backup_bytes_total` Prometheus metrics to be inflated by a factor of `slot_page_size / layer_num` (e.g. ~2× for SWA, ~8.5× for C4, ~8.5× for C128 on V4-Pro), which in turn made the derived load-back bandwidth (`load_back_bytes / load_back_duration`) unreliable for capacity planning and bottleneck analysis.

All other host pools (QSA, MLA, MHA, DSA, Mamba) correctly return per-token values. 

## Modifications

Changed 6 lines in `python/sglang/srt/mem_cache/memory_pool_host.py`:

- `DeepSeekV4PagedHostPool`: `item_bytes` → `layer_num * item_bytes // slot_page_size`
- `DeepSeekV4StateHostPool`: `state_page_bytes` → `layer_num * state_page_bytes // page_size`

This matches the pattern used by `QSAHostPool` (`pool_host/qsa.py:61`).

### Why this is safe

- **Host memory allocation**: `__init__` computes `requested_bytes` using `item_bytes` / `state_page_bytes` directly, not via `size_per_token`. No impact.
- **Eviction**: V4 host pools have `shared_allocation_domain = None`, so they bypass the shared-domain eviction path that uses `size_per_token`. No impact.
- **BufferModePipeline**: V4's anchor is `LogicalHostPool` (`size_per_token = 0`), and the pipeline has an `is None` guard that returns early. No impact.
- **Storage backends** (mooncake, hf3fs, npu_memcache): `bytes_per_page = get_ksize_per_token() * page_size` now correctly equals `layer_num * item_bytes` instead of `item_bytes * page_size`. This is a fix, not a regression.

### Known limitation

For V4 layout (`page_align=576`), C4/C128 pools where `slot_page_size=256` and `item_bytes` is not divisible by 256 have a small floor-division undercount (C4: 0.01%, C128: 11.11%). V4.1 (`page_align=512`) and V4.1_FP4 (`page_align=256`) are always exact. This is far better than the previous 256× overcount.
