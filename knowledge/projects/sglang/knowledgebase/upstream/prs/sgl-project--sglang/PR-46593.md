# [Perf] mega_moe: Raise BLOCK_M for decode-graph FP8xFP4 calls

[Upstream PR](https://github.com/sgl-project/sglang/pull/46593) · state: closed · merged: False

## Original PR description

## Motivation

DeepGEMM picks MegaMoE's BLOCK_M from the mean tokens per expert plus one sigma. Real decode routing is more skewed, so hot experts spill into a second M block that streams their weights again. Decode MegaMoE is bound by weight streaming, so that extra pass costs a full weight read. A larger BLOCK_M for decode-sized calls removes the extra pass.

## Modifications

- In decode and target-verify CUDA graphs, FP8xFP4 MegaMoE calls where DeepGEMM picks BLOCK_M 16 or 32 use 64. Larger choices are kept. `SGLANG_OPT_DEEPGEMM_MEGA_MOE_RAISE_DECODE_BLOCK_M` (default on) is the kill switch.
- The table is keyed on DeepGEMM's own choice, which depends on the expected tokens per expert (global tokens x top-k / experts) rather than the EP size, so one table covers every EP size; the DEP4 and DEP16 results below both improve. DeepGEMM only picks 16 or 32 up to 24 expected tokens per expert, so that also bounds the call size and no separate token cap is needed.
- The remap applies only to FP8xFP4 calls captured in decode or target-verify CUDA graphs (`get_is_capture_mode()` plus the forward mode). That gate also matches speculative draft decode graphs (EAGLE/MTP in `eagle_draft_cuda_graph_runner.py`, frozen-KV MTP, DSpark), so draft models whose MoE goes through this path get the remap too. Eager calls, piecewise and breakable prefill graphs, and idle prefill ranks keep DeepGEMM's choice.
- Only the DeepseekV2MoE MegaMoE path (DeepSeek-V4 and its DSpark draft stages) passes `decode_tiles`. Qwen2/Qwen3 MegaMoE call `run_mega_routed_experts` without it and are unaffected.
- The remapped BLOCK_M reaches DeepGEMM through its existing `DG_MEGA_MOE_TILES` hook, which DeepGEMM reads at each launch, so a captured graph keeps the tiles set at capture. No DeepGEMM change is needed at the pinned sgl_deep_gemm 0.2.3.post2. The variable is scoped around the `fp8_fp4_mega_moe` launch and both shared-expert BLOCK_M lookups (the MegaGate/Mega-mHC input target and `run_mega_routed_experts`), so the shared-expert SF layout matches the kernel.
- Each shared-expert lookup asserts that DeepGEMM returned the remapped BLOCK_M. The hook is not on sgl-project/DeepGEMM `main`, and #43530 (draft) moves toward upstream DeepGEMM APIs; a DeepGEMM that drops or changes the hook then fails at capture instead of silently mismatching the shared-expert SF layout. The check runs only at capture.
- If an operator sets `DG_MEGA_MOE_TILES`, that value still wins. A non-empty value forces one tile for every call, prefill included, so it is not a way to turn this change off; `DG_MEGA_MOE_TILES=""` keeps DeepGEMM's default tiles everywhere and so also disables the remap.

Interplay with #46093 (merged): it passes the global token count to the same `get_block_m_for_mega_moe` heuristic. This branch merges main and keeps that hint at both shared-expert lookups. The hint is `None` during CUDA graph capture, the only place the remap applies, so the two do not interact.

## Accuracy Tests

GSM8K, sgl-eval 0.1.3, 1319 questions, DSv4.1-Flash 1P1D: 96.89%, vs 96.82% on stock. **This run used an earlier revision of this PR without the capture gate** (the remap also applied to eager and prefill calls); its decode-graph tiles are the same as this revision's.

DeepGEMM's own `tests/test_mega_moe.py` (sgl_deep_gemm 0.2.3.post2, 4x GB300) passes with `DG_MEGA_MOE_TILES=2,96,16,128,2` and `2,64,16,128,2`, as well as with the default tiles. Its correctness check compares the fused kernel against the DeepEP dispatch + grouped GEMM + combine baseline. Cases: the test's default shape (8192 tokens per rank), 20 iterations with per-rank token counts drawn from 32-512, and DeepSeek-V4.1-Flash shapes (hidden 5120, intermediate 2304) for the target MoE (384 experts, top-6) and the DSpark draft MoE (128 experts, top-3).

## Speed Tests and Profiling

The DSpark draft stages have their own MoE (128 experts, top-3) on the same DeepseekV2MoE MegaMoE path, so these numbers include the remap in both the target-verify and the draft graphs. Decode step in ms is computed per DP rank from CUDA-graph scheduler samples, with consecutive samples in the same per-rank batch bin. The DEP4 and DEP16 tables below ran without EPLB; the EPLB section after them repeats DEP16 with dynamic EPLB.

An earlier revision also raised 64 to 96. It was neutral with dynamic EPLB (below), so this revision drops it. The no-EPLB tables were measured with both entries: their rows from about 16 requests per rank up (target verify) also include the removed entry.

### DEP16 decode with dynamic EPLB

Same model and decode topology on SGLang main at 302b78cc, with `--enable-eplb --ep-num-redundant-experts 16 --eplb-rebalance-num-iterations 15000` (400 slots, 25 per rank), 5x DEP2 prefill, 1200 s. The first rebalance lands about 5 min into the run, then every 6-8 min. "Settled" is minutes 8-20, after 2-4 rebalances. A per-step probe on the recorder's per-slot counts (40 target MoE layers) gives the load skew:

| placement | rank max/mean | hottest local expert / rank mean (p90, p99) |
|---|---|---|
| initial | 2.17 | 7.9 (12.9, 18.5) |
| settled | 1.17 | 5.8 (7.7, 9.9) |

EPLB evens out the ranks but not the hot experts inside a rank.

Concurrency 1400, ~15 requests per rank, graph batch up to ~20, so the 16/32 -> 64 entries apply. Decode step p50 in ms, settled:

|---|---|---|---|
| 4-7 | 10.5 | 10.2 | -2.9% |
| 8-11 | 11.2 | 11.0 | -1.8% |
| 12-15 | 11.5 | 11.3 | -1.7% |
| 16-19 | 11.8 | 11.7 | -0.8% |
| 20-23 | 12.2 | 12.1 | -0.8% |
| 24-27 | 12.8 | 12.6 | -1.6% |
| 28-31 | 13.2 | 13.0 | -1.5% |

Before the first rebalance the same bins gave -1.7% to -4.0%. End to end, p90 interactivity rose 4.0% at the same throughput, and TPOT p90 went from 4.04 to 3.90 ms.

Concurrency 2100, ~24 requests per rank: the busiest rank sits at 30-40, so the captured graphs were in the range of the removed 64 -> 96 entry. Settled step times match within 0.1 ms in every bin from 12 to 39, and throughput and p90 interactivity match. Before the first rebalance, bins 4-19 still gave -0.8% to -2.7%.

So with dynamic EPLB the 16/32 -> 64 entries still pay off at low decode load and 64 -> 96 was neutral, which is why it is dropped. Without EPLB, which is SGLang's default, 64 -> 96 also helped (tables above); EPLB is the better fix for that range.

A probe on every MegaMoE call (earlier revision, with the 96 entry) confirmed the scope. All prefill calls, eager and graph-captured (128-2048 tokens), kept DeepGEMM's default tiles. Only decode-side graph capture used BLOCK_M 64 and 96. At DEP4 the decode worker captures two MoE configs, which is why the token ranges overlap:

| DEP4 graph | MoE | BLOCK_M 64 | BLOCK_M 96 | DeepGEMM default kept |
|---|---|---|---|---|
| target verify (6 tokens/request) | 384 experts, top-6 | 6-384 tokens per rank | 432-768 | - |
| DSpark draft (5 tokens/request) | 128 experts, top-3 | 5-240 | 260-600 | 640 |

The draft MoE has 1.5x the expected tokens per expert at the same token count, so DeepGEMM's choice crosses 32 and 64 earlier. DEP16 shows the same split (64 at 5-96 tokens per rank, 96 at 70-192).

With a warm DeepGEMM JIT cache, CUDA graph capture time and memory are unchanged. On a cold cache, the first capture also JIT-compiles the BLOCK_M 64 kernel variant.

**Issue**

`python/sglang/srt/layers/muse_spark/muse_spark_megamoe.py` already scopes `DG_MEGA_MOE_TILES` (`_tile_override`, `_megamoe_tiles`), but it treats an empty value the opposite way. Muse treats `DG_MEGA_MOE_TILES=""` as unset, still applies its tiles, and restores `""` on exit. This helper treats `""` as an operator override that turns the remap off, and pops the key on exit. So the same setting means two things, and the 5-field DeepGEMM tile format is now written in two places.

**Fix**

Move the scoping into one shared helper, for example in `mega_moe.py`, and call it from both places with one rule for `""`.
