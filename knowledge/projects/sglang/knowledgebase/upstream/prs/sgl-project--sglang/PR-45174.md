# [Fix] Minimax-M3: Deterministic tie-breaking in the CUDA radix decode top-k

[Upstream PR](https://github.com/sgl-project/sglang/pull/45174) · state: open · merged: False

## Motivation

`minimax_decode_topk` has three selection regimes. Two of them already break exact score ties by block id (the lower id wins):

- the small path (`num_blocks <= 128`): `is_greater(...)`, "lower block id wins"
- the ROCm path: a packed `(score, ~id)` total order

The CUDA radix paths (`num_blocks > 128`, i.e. contexts above 16k tokens at block size 128) place the final-round ties in `atomicAdd` order instead. When tied blocks straddle the top-k boundary, the selected set changes from run to run. ROCm indexer CP already depends on a fixed tie order ("requires ... the ROCm radix top-k tie ordering"); the CUDA paths gave no such guarantee.

Exact ties are common for indexers whose keys carry no RoPE: the block score is the max over units, so repeated text produces equal scores. On such a model, serving the same prompts twice from a cold cache with the radix cache on gave 43/45 identical greedy outputs; with this change, 45/45.

## Modifications

- Final radix round: rank the tied candidates by block id (warp ballot + prefix sum) and keep the lowest ids, matching the small and ROCm paths. Applied to both the single-element path and the multi-element (register bucket) path.
- Fast path: when every tie is selected (`equal_count <= topk_remain`), the order does not matter (the output is sorted ascending), so the ties are written with a plain atomic as before and the ranking is skipped.
- Removes the now unused `counter_final`.
- Adds `test_decode_topk_ties_pick_lowest_ids`, which checks the selected set against `(score desc, id asc)` for 300 to 9,000 blocks with heavy ties.

ROCm is unchanged.

## Accuracy Tests

MiniMax-M3 (bf16, TP8, H200, radix cache on), main vs this PR:

- Greedy outputs on 40 MMLU-Pro prompts plus needle-in-text prompts up to 60k tokens (radix path): 45/45 identical.
- GPQA-Diamond (n=1, max_tokens 32k): 89.4 (main) vs 90.4 (this PR). (range in noise)
