# [Fix] [AMD] diffusion: Route large-M bf16 linears on gfx1250 to the FlyDSL GEMM so outputs past 2 GiB are no longer corrupted

[Upstream PR](https://github.com/sgl-project/sglang/pull/46321) · state: closed · merged: False

## Original PR description

## Motivation

**What goes wrong**
On gfx1250, `apply_unquantized_linear` sends bf16 linears to `aiter.tuned_gemm.tgemm.mm`, whose default solution is the gluon `_gemm_a16w16_gfx1250_bandwidth_bound_kernel`. That kernel indexes the output with 32-bit byte offsets, so every output row whose byte offset is at or past 2**31 comes back as garbage, with no fault and no error. The existing guard bounds element count (`numel < 2**31`), not bytes, so it lets these shapes through.

**Where it shows up**
Any gfx1250 diffusion linear whose bf16 output exceeds 2 GiB. On Wan2.2-T2V-A14B at 720p (90000 tokens per DiT forward), the FFN up-projection output is 90000 x 13824 x 2 B = 2.49 GB, so rows 77672..89999, the last latent frame, are corrupted in every block of every step. The decoded video's final frame is pure noise. Checked against an fp32 reference: rows below 77672 match to 0.016 max abs error; rows from 78000 on are off by 7.2 to 7.3. The FFN down-projection (2.5 GB input, 0.9 GB output) is unaffected, so it is the output offset. Only gfx1250 was checked; other archs reach tgemm through different kernels.

**How to fix**
On gfx1250, route large-M bf16 linears to aiter's FlyDSL `gemm_a16w16_gfx1250`, which addresses through TDM descriptors and is correct past 2 GiB, and on gfx1250 lower the remaining tgemm fallback's bound to 2**31 bytes.

## Modifications

- `python/sglang/multimodal_gen/runtime/layers/linear.py`
  - New gfx1250 path: bf16 linears with M >= 4096, N % 256 == 0, K % 64 == 0 call `aiter.ops.flydsl.gemm_a16w16_gfx1250.gemm_a16w16` with tile 256x256x64, 2x4 waves, 4 LDS buffers, `variant="compute_bound"` (the best correct config from a sweep at the Wan2.2 shapes). It is registered as an opaque custom op (`diffusion_flydsl_gfx1250_linear`) so torch.compile does not trace the FlyDSL JIT.
  - On gfx1250 only, the remaining tgemm fallback is bounded at 2**30 elements (2**31 bytes of bf16/fp16) instead of 2**31, so shapes that miss the FlyDSL path fall back to `F.linear` instead of silently corrupting. Every other arch keeps the existing 2**31-element bound, so MI300/MI355 dispatch is unchanged.
  - Small-M linears (text tokens, timestep embeddings) keep using tgemm. CUDA never enters either path (`_USE_AITER_TGEMM` is False there).
- `test/registered/unit/multimodal_gen/test_linear_tgemm_size_bound.py` (new, CPU, `base-a-test-cpu`): with meta tensors and a mocked tgemm, on gfx1250 the Wan2.2 FFN-up shape never reaches `tgemm.mm` while a 512-row linear still does, and on other archs the same large shape still reaches tgemm.
- `python/sglang/multimodal_gen/test/unit/test_gfx1250_linear_dispatch.py` (new, gfx1250 only, skipped elsewhere): the FFN-up shape through `apply_unquantized_linear` matches an fp32 reference on rows past the 2 GiB boundary.

## Accuracy Tests

sgl-eval does not cover video diffusion, so correctness is shown at the kernel and output-frame level.

| check | before (tgemm) | after (FlyDSL) |
|---|---|---|
| FFN-up 90000x13824x5120, max abs err vs fp32, rows < 77672 | 0.016 | 0.016 |
| FFN-up 90000x13824x5120, max abs err vs fp32, rows >= 78000 | **7.2 - 7.3** | 0.016 |
| Wan2.2 720p 193-frame video, last frame | pure noise | coherent scene |

Wan2.2 output is bit-exact run to run on the baseline (138 dB PSNR between two runs), so any kernel change, including this one, shifts the whole trajectory (13 dB mean PSNR vs baseline); the regression signal is the last frame, not PSNR.

## Benchmarking and Profiling

One gfx1250 DPX half-partition (96 CU), sibling partition idle, `SGLANG_USE_ROCM_AITER_TGEMM=1 HIP_FORCE_DEV_KERNARG=0`, Wan2.2-T2V-A14B, 720x1280, 8 steps, 90000 tokens per forward, BF16 attention (`--attention-backend aiter`), no torch.compile.

GEMM, M = 90000, bf16 with bias (the 5120-wide rows were timed while the sibling partition ran a Wan2.2 job, so their absolute TFLOPS are pessimistic; the ratio is same-condition):

| N x K | tgemm (gluon) | FlyDSL (this PR) | speedup |
|---|---|---|---|
| 5120 x 5120 (QKV / O) | 5.85 ms, 806 TFLOPS | 4.93 ms, 958 TFLOPS | 1.19x |
| 13824 x 5120 (FFN up) | 14.45 ms, 882 TFLOPS (wrong rows) | 13.43 ms, 946 TFLOPS | 1.08x |
| 5120 x 13824 (FFN down) | 16.67 ms, 764 TFLOPS | 14.80 ms, 861 TFLOPS | 1.13x |

End to end (`sglang generate`, `[DenoisingStage] average time per step`):

| | s / denoise step | e2e |
|---|---|---|
| before | 24.52 | 221.1 s |
| after | 24.04 | 218.9 s |

Note: these runs used 90000 tokens per forward (a local VAE `scale_factor_temporal = 8`); the upstream Wan2.2 config (factor 4, 176400 tokens) makes the outputs about 2x larger, so it crosses 2 GiB on more linears and the fix matters more there. The 176400-token config was not run.
