# [Fix] deepseek-v4.1: Match KV capacity to physical layouts

[Upstream PR](https://github.com/sgl-project/sglang/pull/41275) · state: closed · merged: True

## Original PR description

## Motivation

DeepSeek-V4.1 ratio-1/2 owners can allocate V41 FP8 or FP4 global KV, but their capacity coefficient still uses the V4 584-byte row. This underestimates V4 page padding and overestimates V41 storage, reducing the token capacity selected at startup. Finalize only updates state-pool sizes, and DeepSeek-V4 is excluded from post-capture resizing.

## Modifications

- Use the existing layout-aware paged-byte helper for ratio-1/2 growth, retaining the existing owner and backend selection rules.
- Charge reserved main/indexer pages separately, including index-page rounding at the candidate capacity, then lower capacity by full pages until the budget fits.
- Add focused CPU tests whose expected bytes come from the real main/index/state pool constructors: three layout-growth cases (V4, V41 FP8, default V41 FP4), two FP4 exact-fit/one-byte-under capacity cases including index-page rounding, stage-local owner/reuse accounting, and backend guards. Full-page 128 and stage slices are arithmetic checks; they do not extend V41 serving support.

## Accuracy Tests

Before test simplification, the larger regression matrix had 84 failing allocation/capacity subcases on the pre-fix source; 98 tests and 115 subtests passed with the fix across the five files below. Those counts describe the earlier test revision. The current revision reduces the main matrices to five representative configurations, removes repeated finalize/token-cap assertions, and retains owner/reuse and backend coverage. Ruff lint/format and diff checks pass; local execution of the revised tests was blocked by missing dependencies (NumPy/PyTorch). Targeted CI is being requested for the revised head, including DSV4 and DSV4.1 model regressions. No kernels, quantization, model forward code or allocation layout are changed. Model accuracy is not yet established.

## Speed Tests and Profiling

Allocation validation only, on one B200 without model weights or attention execution. At 1,048,576 tokens, full page 256, index page 128 and owners at layers 2/8/14/20, corrected global main+index tensor budgets equal the production constructors' measured CUDA tensor bytes:

| Layout | Old budget (B) | Corrected / measured tensor bytes (B) | Capacity under the same 1,709,178,880 B global budget |
|---|---:|---:|---:|
| V4 | 1,709,178,880 | 1,712,477,696 | 1,046,528 |
| V41 FP8 | 1,709,178,880 | 1,562,997,248 | 1,146,624 |
| V41 FP4 | 1,709,178,880 | 933,605,888 | 1,920,000 |

Each corrected capacity fits the tensor budget; one additional full page exceeds it. SWA, weights, state and CUDA allocator overhead are outside this table. The test image did not advertise V41 FlashMLA reader support; explicit V41 tensor construction was checked, not reader execution. Index page 128 was selected explicitly (the image's native setting was 64). No end-to-end throughput or latency claim.

The capacity change was exercised: with the same memory-fraction setting, the reported full-token capacity per worker increased from **60,902,656 to 111,540,736 (+83.15%)**, consistently in both runs. This is a capacity measurement, not a throughput claim.

**Interpretation:** no consistent aggregate GSM8K accuracy decrease was observed in these runs. The first comparison had 6 correct→incorrect and 4 incorrect→correct changes; the second had 7 and 10, respectively. The baseline itself changed by 3 correct answers between repeats. Greedy outputs were not bitwise invariant, including within same-revision repeats, so the first run's two-answer decrease alone does not establish a PR-induced regression.

**Scope:** this validates one model and serving configuration. Short GSM8K prompts do not fill the enlarged cache or establish long-context, high-slot, or cache restore correctness. Truncated responses remain included in the reported denominators. This is not a universal non-regression or batch-invariance guarantee.
