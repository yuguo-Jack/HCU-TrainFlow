# [Feat] mem_cache: marconi eviction policy for the mamba radix cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/46512) · state: open · merged: False

## Original PR description

## Motivation

On a hybrid recurrent model, every cached recurrent-state checkpoint costs
the same bytes: one conv and SSM state per layer, 49 MiB on Qwen3.5-4B and
72.5 MiB on Falcon-H1-1.5B. The checkpoints are worth very different amounts:

- one 512 tokens deep saves almost nothing;
- one 60k tokens deep saves a long prefill;
- one under a still-cached ancestor saves only the gap to that ancestor.

LRU over the MAMBA component ignores all of this. Marconi (Pan et al., MLSys
2025, arXiv:2411.19379) evicts the checkpoint with the lowest

```
utility = norm(recency) + alpha * norm(prefill FLOPs saved / state bytes)
```

and keeps branch points (nodes with two or more children) until no other
candidate is left. This PR adds that policy as `--radix-eviction-policy marconi`.

Credit and prior work, all closed without merge:

- #17898 (@qimcis): first Marconi port, on `MambaRadixCache`.
- #21862 "[Feature] Marconi eviction" (@qimcis): the eviction half of the
  #21860/#21862 split.
- #22172 seglen (@XinyiQiao): replay length from the nearest reusable
  ancestor. This PR uses the same idea in FLOPs, so a checkpoint whose
  ancestors were tombstoned is credited with the whole gap it saves.

Open PRs that touch `unified_cache/components/mamba.py` (conflict risk):

- #40338 (draft): shares the aux eviction driver between SWA and Mamba. If it
  lands first, the hooks here move into that driver.
- #43853, #44482.

## Modifications

- **Policy.** `MarconiStrategy(alpha)` in `evict_policy.py`, registered as
  `marconi`.
  - `--radix-eviction-policy-config '{"alpha": <float >= 0>}'`, default 1.0.
  - `alpha = 0` ranks by recency alone, but branch points still go last,
    so it is not the same order as `lru` (measured below).
  - `get_priority` is `last_access_time`, so FULL KV and SWA stay in LRU order.
- **Cost model** (`mem_cache/prefill_cost_model.py`, new).
  `F(L) = c_lin * L + c_attn * L^2 / 2` per TP rank, built once from the
  loaded model:
  - `c_lin` sums:
    - 2 FLOPs per active parameter. Routed `FusedMoE` experts are scaled by
      top_k / num_experts. Embedding / LM head and vision/audio towers are
      skipped.
    - The recurrent update per token: `k * prod(temporal state shape)` plus
      `2 * conv_numel * K / (K - 1)` for the short convolution, with
      k = 5 for Mamba2/SSD and lightning and k = 7 for GDN and KDA.
    - The linear part of sliding-window attention layers.
  - `c_attn` = `2 * heads * (qk_head_dim + v_head_dim)` per full-attention
    `RadixAttention` layer.
  - State bytes = `mamba_cache_per_req`, conv plus SSM state.
  - The recurrence kind comes from the existing `hybrid_arch` detectors (KDA,
    GDN, lightning, Mamba2), then the registry backend name.
  - If the build fails, the policy weighs checkpoints by tokens saved and logs
    a warning.
  - Logged at startup, e.g. Qwen3.5-4B:
    `gdn recurrence: 7.23e+09 FLOPs/token + 1.31e+05 FLOPs/token pair
    (attention dominates past 110317 tokens), 49.1 MiB per state checkpoint`.
  - Falcon-H1-1.5B: `mamba2 recurrence: 2.67e+09 FLOPs/token + 9.83e+04
    FLOPs/token pair (attention dominates past 54279 tokens), 72.5 MiB`.
- **Eviction walk** (`MambaComponent`, used only when the policy is
  `marconi`).
  - At `_evict_device_start`, every unlocked MAMBA checkpoint (from the LRU
    list) goes into a heap keyed by `(has >= 2 children, recency_norm + alpha
    * eff_norm)`.
    - `eff = (F(depth) - F(depth of the nearest ancestor that still holds a
      device state)) / state_bytes`.
    - Recency and eff are min-max normalized over that snapshot.
  - `_evict_device_next_node` pops lazily:
    - entries that are no longer candidates are skipped;
    - an entry whose recomputed key went up is pushed back. Its ancestor may
      have been tombstoned meanwhile, which raises its saving.
  - After a leaf is evicted, the walk re-keys the leaf's nearest stateful
    ancestor, because it may have lost its second child.
  - The per-step contract of the LRU walk is kept: each step returns a leaf to
    evict, a HiCache backup request, or one tombstone plus cascade.
- **Plumbing.**
  - `CacheInitParams.prefill_cost_model`, built in `kv_cache_builder.py` only
    when the policy is `marconi`.
  - Choices, help text and docs: `radix_eviction_policy.mdx` (table row,
    parameters section, launch example) and `server_arguments.mdx`.
- **Guards.**
  - `validate_marconi_eviction_policy` rejects:
    - a non-numeric, negative, or non-finite alpha;
    - `--enable-session-radix-cache`;
    - `--enable-hierarchical-cache`.
  - `registry.py` requires UnifiedRadixCache on a hybrid SSM model.
  - The Rust TreeCore falls back to Python with the reason "the marconi
    eviction policy requires the Python TreeCore".

### Supported combinations

| | `marconi` |
|---|---|
| Hybrid recurrent model on UnifiedRadixCache (Mamba2/SSD, GDN, KDA, lightning) | yes |
| Non-hybrid model / other caches | rejected at startup |
| `extra_buffer` | yes (benchmarked) |
| `extra_buffer_lazy`, `no_buffer` | allowed (scoring does not depend on the strategy); not tested on GPU |
| Python TreeCore | yes (selected automatically) |
| Rust TreeCore | falls back to Python |
| HiCache | rejected at startup |
| Session radix cache | rejected at startup |
| SWA + Mamba (3-component trees) | SWA keeps LRU; not benchmarked |

## Accuracy Tests

Eviction only chooses which checkpoint to drop. A surviving checkpoint is
restored exactly as under LRU.

Modal H100, this branch, 72 mamba slots (the setup of the benchmark below).
Each server runs the checks twice on a cold tree (pass 1 fills the cache,
pass 2 hits it), then once more after the GSP and trace workloads with no
flush, so the third pass runs while the tree is full and evicting:
`marconi` evicted 32,863 KV tokens in 21 eviction passes during that pass
on Qwen3.5-4B and 27,318 in 12 on Falcon-H1 (`sglang:evicted_tokens_total`).

- 28-prompt greedy check (24 prompts over 4 shared documents plus 4
  two-turn follow-ups, 48 tokens) and 15-prompt check of output ids and
  logprobs (3 random-word documents × 5 tasks, 32 tokens).
- `marconi` against `lru`: identical on both models in all three passes,
  28/28 texts and 15/15 ids with a largest |Δ logprob| of 0.000.
- Against `--disable-radix-cache` (whose two passes agree with each other
  exactly):

| model | check | `lru` | `marconi` |
|---|---|---|---|
| Qwen3.5-4B (GDN) | ids, pass 1 / 2 / under eviction | 15 / 15 / 15 of 15 | 15 / 15 / 15 of 15 |
| | largest \|Δ logprob\| | 0.082 / 0.109 / 0.082 | 0.082 / 0.109 / 0.082 |
| | greedy texts | 24 / 25 / 24 of 28 | 24 / 25 / 24 of 28 |
| Falcon-H1-1.5B (Mamba2) | ids | 13 / 12 / 13 of 15 | 13 / 12 / 13 of 15 |
| | largest \|Δ logprob\| | 0.157 | 0.157 |
| | greedy texts | 22 / 22 / 22 of 28 | 22 / 22 / 22 of 28 |

  The flips against no-cache are bf16 near-ties between a restored and a
  recomputed state; `lru` has exactly the same ones, so they are not caused
  by this PR.
- Falcon-H1 needed `--disable-prefill-cuda-graph` on this nightly. With the
  prefill CUDA graph on, the first request hits an illegal memory access in
  every config, including `--disable-radix-cache`, so the bug is independent
  of this PR.
- Startup on GPU: `marconi` with `--enable-hierarchical-cache`, with
  `--enable-session-radix-cache`, or with `alpha = -1` exits with code 1 and
  the `ValueError` from `validate_marconi_eviction_policy`.

### Unit tests (CPU)

`test/registered/unit/mem_cache/test_mamba_marconi_eviction.py`
(`register_cpu_ci`, 24 tests):

- Validation, the alpha plumbing, and the Python TreeCore fallback.
- Cost model per family:
  - state bytes including conv state, and recurrence FLOPs per token, derived
    by hand for GDN (Qwen3.5-9B shape), Mamba2 (Nemotron-H-4B shape) and KDA
    (Kimi-Linear shape);
  - `recurrence_kind` on Qwen3-Next, Kimi-Linear, Nemotron-H and Falcon-H1
    configs;
  - additivity and the quadratic term of `F`;
  - building `F` from a module set with an embedding, MoE experts, full and
    sliding-window attention, and a vision tower.
- Eviction order on a FULL + MAMBA tree:
  - alpha 0 equals recency on a tree without branch points;
  - a large saving outweighs recency;
  - the attention term favours deep checkpoints;
  - the saving is marginal to the nearest live ancestor;
  - a tombstoned parent raises the child's saving;
  - a tombstone during the walk reorders the heap;
  - a branch point goes last until it loses a child, and is re-keyed within
    the same walk;
  - locked checkpoints are skipped;
  - evicting everything balances the mamba pool.

I mutation-checked four parts of the walk: the live-ancestor check, the lazy
re-push, the ancestor refresh, and the children flag. Each mutation fails 1–2
of these tests.

Locally on CPU this file plus `test_evict_policy`, `test_tlru_eviction_policy`,
`test_mamba_unittest`, `test_unified_radix_allocation_eviction`,
`test_session_unified_radix_cache` and `test_mamba_path_state_cap` give
86 passed, 5 skipped. On GPU (Modal H100) this file and the existing mamba / unified radix test

## Speed Tests and Profiling

### Measured on GPU (Modal H100; two runs per config at 72 slots, two or three at 400)

Setup: GSP with 16×16 prompts, an 8192-token system prompt and concurrency
12; a multi-turn replay of 12 cc-traces sessions / 288 requests / 10.47M
prompt tokens; `--max-running-requests 12`; Python TreeCore in every config.
Hit rates come from the `sglang:cached_tokens_total` /
`sglang:prompt_tokens_total` deltas. Values separated by `/` are repeated
runs of the same config.

Qwen3.5-4B (GDN), 72 slots:

| eviction | GSP hit | GSP mean TTFT (ms) | trace hit | trace TTFT mean (s) | trace TTFT p90 (s) |
|---|---|---|---|---|---|
| lru | 0.601 / 0.626 | 639 / 648 | 0.756 / 0.768 | 0.449 / 0.458 | 0.84 / 0.96 |
| marconi | **0.844 / 0.858** | **406 / 453** | **0.798 / 0.801** | 0.412 / 0.446 | 0.77 / 0.84 |
| marconi, α = 0 | 0.629 / 0.636 | 552 / 542 | 0.782 / 0.783 | 0.480 / 0.515 | 0.92 / 0.83 |

Qwen3.5-4B, 400 slots:

| eviction | GSP hit | GSP mean TTFT (ms) | trace hit | trace TTFT mean (s) |
|---|---|---|---|---|
| lru | 0.881 / 0.881 | 459 / 415 | 0.874 / 0.875 | 0.396 / 0.389 |
| marconi | 0.878 / 0.886 | 556 / 398 | 0.873 / 0.873 | 0.478 / 0.417 |

Falcon-H1-1.5B (Mamba2), 72 slots, `--disable-prefill-cuda-graph`, one run:

| eviction | GSP hit | GSP mean TTFT (ms) | trace hit | trace TTFT mean / p90 (s) |
|---|---|---|---|---|
| lru | 0.714 | 536 | 0.763 | 0.238 / 0.525 |
| marconi | **0.836** | **419** | **0.814** | 0.214 / 0.485 |

What the numbers say:

- With a tight state pool, `marconi` lifts the hit rate on both models:
  GSP +0.24 on Qwen3.5-4B and +0.12 on Falcon-H1, trace +0.04 and +0.05.
  The gaps are far larger than the spread between repeats (GSP hit spread
  0.025 for `lru`, 0.014 for `marconi`; trace 0.012 and 0.003). GSP mean
  TTFT drops 30% on Qwen3.5-4B and 22% on Falcon-H1. The trace TTFT mean
  moves by less than the run-to-run spread.
- With an ample pool (400 slots) there is nothing to gain: hit rates match
  `lru` within 0.01. Mean TTFT is noisy here because a few cold 35–50k-token
  prefills queue behind each other differently from run to run. On the
  requests with the same cached tokens in both runs, the median per-request
  TTFT ratio `marconi` / `lru` is 0.96–1.05.
- One more `marconi` run at 400 slots is left out of the table: the whole
  container was slow (median prefill 19.5k tok/s and decode 576 tok/s
  against 51–53k and 910–998 in every other 400-slot run, already before
  most evictions), and its trace TTFT mean was 0.699 s. The eviction walk
  took 0.15 s of that run in total, so it cannot explain the slowdown.
- `alpha = 0` is not `lru`: branch points still go last. It keeps the hit
  rate close to `lru` (GSP +0.02, trace +0.02, just outside the `lru`
  repeat spread on the trace) and cuts GSP mean TTFT by 15%.
- Cost of the walk (`sglang:eviction_duration_seconds`): 0.3–0.5 ms per
  eviction pass at 72 slots and 1.7 ms at 400 slots, against 0.2 ms for
  `lru`; 0.12–0.17 s in total over a 100 s trace replay.

| 16 | 0.7587 | 0.8424 |

Alpha sweep, S=32: α = 0 → 0.8402, 0.5 → 0.8763, 1 → 0.9130, 2 → 0.9499,

## Benchmark recipe

The scripts are not part of this PR. They are a Modal app with three
functions:

- download the model into a volume;
- GPU unit tests;
- one self-contained function per server config: start the server, run the
  workloads, kill the server in `finally`, write JSON to a volume.

Spawn them with `modal deploy` + `Function.spawn`.

Per config:

```bash
python -m sglang.launch_server --model-path <model> --enable-metrics \
  --mamba-radix-cache-strategy extra_buffer --max-running-requests 12 \
  --max-mamba-cache-size 72 --mem-fraction-static 0.80 --context-length 72000 \
  [--radix-eviction-policy marconi]
# Python TreeCore for lru configs too, so only the policy differs:
#   SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND=python

python -m sglang.benchmark.serving --backend sglang --port 30000 \
  --dataset-name generated-shared-prefix --gsp-num-groups 16 \
  --gsp-prompts-per-group 16 --gsp-system-prompt-len 8192 \
  --gsp-question-len 256 --gsp-output-len 64 --num-prompts 256 \
  --max-concurrency 12 --request-rate inf --seed 1 --flush-cache
```

Then flush and run the trace replay. It uses 12 cc-traces sessions, one
thread per session. Each turn re-sends the previous prompt plus the real
output of that turn, with `ignore_eos` and at most 256 output tokens. Hit
rates come from `sglang:cached_tokens_total` / `sglang:prompt_tokens_total`
deltas and from `meta_info.cached_tokens`.

Cost on Modal H100 (8 CPU, 64 GB RAM), actual:

- about 5–7 minutes and $0.40 per config on Qwen3.5-4B, about half of it
  boot;
- about $7.6–7.9 in total for this verification: 15 server configs, 4
  startup-rejection boots, the GPU unit tests, two model downloads and the
  image build.

## Risks

- **Python TreeCore only.** Throughput-sensitive deployments that rely on
  the Rust TreeCore lose it under `marconi`.
- **Heap rebuilt each eviction.** The heap is rebuilt from all unlocked MAMBA
  checkpoints at every eviction start, O(N log N) for N cached states.
  Measured: 0.3–0.5 ms per eviction pass with 72 slots and 1.7 ms with 400
  slots, against 0.2 ms for `lru`. I have not profiled it at thousands of
  states.
- **Approximate cost model.** It counts packed FP4 / FP8 parameters by
  element count, assumes uniform expert routing, and ignores the extend
  overhead of short extensions. It only needs to rank checkpoints, and the
  ranking is in FLOPs per state byte.
- **No HiCache or session radix cache.** Both are rejected for now.
