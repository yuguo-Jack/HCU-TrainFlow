# [Fix] [AMD] dsv4: Let breakable prefill graphs capture without the SWA tail

[Upstream PR](https://github.com/sgl-project/sglang/pull/48148) · state: open · merged: False

## Original PR description

## Summary

`--cuda-graph-backend-prefill breakable` crashes on HIP when decoder SWA bounded replay is on.

Capture dies in `DeepseekV4Model` with `AttributeError: 'NoneType' object has no attribute 'late_layer_tail'`. The HIP backend builds `tail_forward_metadata` only on the eager path. The CUDA backend builds a fixed-capacity tail and captures the late layers over it. HIP does not.

Once that read is guarded, the first live prefill dies in `can_run_prefill_cuda_graph`. HIP borrows the CUDA method, which calls `_prefill_graph_fits_late_tail`. That helper exists only on the CUDA backend.

- Set `tail_forward_metadata = None` in the HIP capture and replay hooks.
- Treat a missing tail as "run the late layers on every row," in the model forward and in the logits path.
- Give HIP its own `can_run_prefill_cuda_graph`. It checks the context-length limit only.

Eager prefills still use the SWA tail. Graph-run prefills do not, so their late layers run on every row. Contexts past the prefill graph limit, 16384 by default, still run eager.

Seen on MI355, DeepSeek-V4.1-Flash, TP4, with decoder SWA bounded replay on. With the patch, capture finishes and prefills at or under the limit log `cuda graph: True`.

## Test plan

- [ ] Serve DeepSeek V4 on HIP with `--cuda-graph-backend-prefill breakable` and `--enable-decoder-swa-bounded-replay`. Capture should finish.
- [ ] A prefill at or under the graph context limit should replay. The prefill line shows `cuda graph: True`.
- [ ] A longer prefill should still run eager.
- [ ] CUDA is unchanged. The CUDA backend still builds the tail inside the graph.

- amd-pedghazi · comment · 2026-11-04T07:26:23Z · [source](https://github.com/sgl-project/sglang/pull/48148#issuecomment-6625192498)

Thanks! Both crash fixes are right, and DSpark stays correct. The open point is speed on longer prompts.

With decoder SWA bounded replay, eager prefill runs layers 20-39 (of 40) only on each request's last `SWA_WINDOW` rows (the tail). Graph-run prefill runs them on all 8,192 rows of an 8k request, not 128.

We tested on MI355X (DeepSeek-V4.1-Flash, TP4, DSpark). With random prompts, graphs cut median TTFT by 44% at 1k tokens and 25% at 2k. At 8k, it rises 70% (throughput -5%), and 64% with 4 requests at once (throughput -11%). On 92k-token prompts, results barely change: nearly all prefills there stay eager (over the 16K replay limit). Graph capture takes about 134 s and 22.4 GB per GPU. Startup takes about 64 s longer. GSM8K is unchanged.

CUDA avoids this with `DecoderReplayTail.run_in_prefill_graph`. Until HIP has that, please use graphs only for prefill batches up to about 2,048 tokens. Either check this in the HIP `can_run_prefill_cuda_graph`, or document `--cuda-graph-max-bs-prefill 2048`.

Smaller points:
- The new `can_run_prefill_cuda_graph` repeats the runner's `max_seq_len` check, so it is not needed.
- Attention DP (not tested): `late_layer_dp_counts` would get tail-row counts for graph steps that run all rows.
- The `None` guards also hide a missing tail on CUDA. Please keep an assert there.
- ruff-format wants a blank line before the new `def`.
