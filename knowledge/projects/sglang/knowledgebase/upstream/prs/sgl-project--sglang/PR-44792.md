# [Perf] [NVIDIA] fp8-gemm: L2-aware CTA swizzle for the SM121 (GB10) blockwise FP8 GEMM

[Upstream PR](https://github.com/sgl-project/sglang/pull/44792) · state: open · merged: False

## Original PR description

## Motivation

On GB10 (DGX Spark, SM121, 48 SMs, 24 MiB L2), Qwen3.8-27B-FP8 prefills at 850 tok/s (32K prompt) with the default `--fp8-gemm-backend auto`, which resolves to `cutlass` on SM12x. vLLM v0.31.0 on the same machine reaches 1852 tok/s. `--fp8-gemm-backend deep_gemm` gets to 1757, but it forces UE8M0 scales on SM12x (linear-layer error 3.8% vs 2.6%) and is 15% slower at decode sizes. So the default kernel needs fixing; switching backends is not the answer.

The cause is CTA rasterization. With `max_swizzle_size` left at 1, the persistent scheduler's heuristic raster walks the shorter tile dimension first. That re-reads the smaller operand once per tile row or column of the larger one. While that operand fits in L2 this is free. At prefill-sized M neither the weight nor the activation fits in 24 MiB, every re-read goes to DRAM, and the gate_up_proj GEMM drops from 175 TFLOP/s at M=2048 to 51 at M=8192.

vLLM's SM120 blockwise kernel already sets `max_swizzle_size = 8` whenever the weight exceeds L2 (`csrc/libtorch_stable/quantization/w8a8/cutlass/c3x/scaled_mm_blockwise_sm120_fp8.cu`). This PR does the same, but only when *neither* operand fits, and only on SM121 (GB10), where it was measured. The narrower condition avoids a 3% (up to 15% per GEMM) regression at M=512–1024, measured below.

Related: #33629 (SM120 FP8 blockwise GEMM optimization on Qwen3.6-27B shapes; it covered M < 64 and was closed for inactivity), #30438 (moved the SM120 kernel to JIT, added swapAB).

## Modifications

One file changes: `python/sglang/kernels/jit/csrc/gemm/fp8_blockwise/fp8_blockwise_scaled_mm_sm120.cuh`.

- A new helper `blockwise_fp8_swizzle_size(device, weight_bytes, act_bytes)` returns 8 on SM121 when `min(weight, activation) > 3/4 × L2`, and 1 otherwise, including on every SM120 part. The capability and L2 size are read once per device and cached, the same way `get_sm_count` is.
  - If you prefer, it can move to `sgl_kernel/runtime.cuh` as `get_l2_cache_size` next to `get_sm_count`.
- The non-swapAB launcher sets `args.scheduler.max_swizzle_size` from it.
  - The swapAB launcher is unchanged. Model forwards reach it only for M ≤ 128, because the FP8 linear quantizes into buffers padded to a multiple of 4 rows (`sglang_per_token_group_quant_fp8_row_padded`), so `M % 4 ≠ 0` never gets there at prefill sizes.
  - An earlier revision also set the swizzle in the swapAB launcher; thanks to @waynehacking8 for pointing out it is unreachable from forwards.
  - For M ≤ 256 the activation stays far below 3/4 of L2, so those calls keep size 1.

Effects:

- SM120 parts (RTX PRO 6000, RTX 50xx) keep the default order and stay bit-identical to main.
  - On an RTX PRO 6000 Blackwell Max-Q (128 MiB L2) the same rule was mixed just past its threshold (see the review comment), so the margin doesn't carry over by L2 size alone.
- Decode sizes are unaffected.
- Data-parallel launches produce bit-identical outputs.
- Stream-K launches (last-wave waste > 0.5) change only in the last bits, because the swizzled order changes the Stream-K split of the K loop. Relative error against an FP32 reference moves by at most 1.9e-9.

## Accuracy Tests

- **Kernel.** `out_sha256` is identical for 59/70 (shape, M) points against the unpatched kernel.
  - The 11 that differ are exactly the swizzled launches whose last wave is less than half full, predicted from the tile count and the rule (11/11).
  - In the non-swapAB launcher those are the Stream-K launches.
  - Run twice, the unpatched kernel gives 70/70 identical outputs, and so does the patched one.
  - Relative error against an FP32 matmul of the dequantized weight is 2.576e-2 on both sides, and differs by at most 1.9e-9 at any point. That figure is mostly the shared per-token FP8 activation quantization.
- **This revision on GB10** (SM121 gate, swapAB change dropped):
  - outputs are bit-identical to the first revision at all 70 points;
  - per-forward time matches it within ±1.4% at every M, in an alternating A/B in one session (per point: median 0.4%, under the 0.5% spread between two runs of the same revision).
- **End to end.** GSM8K test, 200 questions, seed 0, greedy, `enable_thinking=false`, Qwen3.8-27B-FP8:
  - default, vLLM's rule and this PR: 96.5% (193/200) each;
  - all three miss the same 7 questions.

## Speed Tests and Profiling

**Environment.**

- Hardware: DGX Spark (GB10, SM121), driver 580.178.04, CUDA 13.0, kernel 7.0.0-1019-nvidia.
- Image: `lmsysorg/sglang:v0.5.21-cu130@sha256:b1259f3e…` with the patched file bind-mounted (the file is identical on main as of 2026-10-16). sglang 0.5.21, torch 2.13.0+cu130, flashinfer 0.6.18.
- Model: Qwen/Qwen3.8-27B-FP8 (block 128×128 e4m3, revision 017b9c7a), TP=1.

**Kernel.** Shapes are the five Qwen3.8-27B FP8 linears at TP=1, the same table as #33629:

| linear | (N, K) | per forward |
|---|---|---|
| gate_up_proj | (34816, 5120) | ×64 |
| down_proj | (5120, 17408) | ×64 |
| in_proj_qkvz | (16384, 5120) | ×48 |
| qkv_proj | (14336, 5120) | ×16 |
| out_proj / o_proj | (5120, 6144) | ×64 |

Each timed call is `cutlass_w8a8_block_fp8_linear_with_fallback`: per-token-group activation quantization plus the GEMM. Timing uses `flashinfer.testing.bench_gpu_time_with_cupti(use_cuda_graph=True)`, median of the repeats. cupti-python is not in the image, so FlashInfer falls back to CUDA-graph replays timed by CUDA events. **Edit:** I first wrote "with cold L2" here, but these tables were timed with the operands captured in a closure, which FlashInfer cannot rotate, so L2 was not cold between replays. Re-timed with the activation, weight and scales passed as `input_args` (FlashInfer then rotates copies of them for a cold L2), each of the four arms in the next table moves by at most 2.7% at any M (median under 1%), about the run-to-run spread noted below, and the outputs are bit-identical (70/70 points). The gap to vLLM's rule at M = 512–1024 stays: 176.0 vs 170.3 ms at M=512 and 326.7 vs 311.2 at M=1024.

Prefill is 2.1× the default at 32K and 1.7× at 127K, within 4% of vLLM.

- A second launch of each arm gave 1768 / 1209 tok/s (vLLM rule) and 1758 / 1212 (this PR).
- Within a launch the three 32K requests agree to 0.2%. Across launches they differ by up to 6%: an earlier launch took the same kernel path at 32K and gave 1672, since every 8192-token chunk is aligned and only the 53-token tail runs the swapAB launcher, as a small-M call.
- So this PR and vLLM's rule tie end to end. The rule only matters at the M = 512–1024 kernel points above.
- The c32 TTFT gap that remains to vLLM is scheduling (prefill chunks and decode run in synchronized waves), not the GEMM.

The kernel numbers come from a standalone script that times `cutlass_w8a8_block_fp8_linear_with_fallback` at the shapes above. I can add it under `benchmark/kernels/` if that would help review.

- puncsky · comment · 2026-10-18T00:26:11Z · [source](https://github.com/sgl-project/sglang/pull/44792#issuecomment-6243706122)

Thanks for running this on a 128 MiB part. Both points hold, and I've pushed 6a23aae2:

- **swapAB.** You're right. The FP8 linear quantizes into buffers padded to a multiple of 4 rows (`sglang_per_token_group_quant_fp8_row_padded`, `row_alignment=4`), so model forwards reach the swapAB launcher only for M ≤ 128. That was already true on v0.5.21, where I measured. My "uneven prefill batches go through swapAB" came from reading the dispatch, not from a measurement, and it was wrong. The swapAB change is dropped, and the description is corrected.
- **The threshold.** I only measured the 3/4-of-L2 margin on GB10 (24 MiB L2, LPDDR5X at ~235 GB/s copy bandwidth). Your numbers put the crossover on a 128 MiB GDDR7 part well above it: −8.5% at 0.75× L2, +10% at 0.94×. So the margin doesn't carry over by L2 size alone. The swizzle now applies on SM121 only, so every SM120 part keeps size 1 and stays bit-identical to main.
- **On GB10 nothing changes.** Outputs are bit-identical to the previous revision at all 70 points, and per-forward time matches within ±1.4% at every M in an alternating A/B.

The +5% / +17% you see at M = 24576 / 32768 looks worth having on large-L2 parts. It would need its own threshold from a sweep like yours, so I'd leave it for a follow-up rather than guess one here.
