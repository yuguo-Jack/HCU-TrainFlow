# [Refactor] rust: Extract shared environment parsing helpers

[Upstream PR](https://github.com/sgl-project/sglang/pull/38906) · state: open · merged: False

## Original PR description

## Motivation

`env_bool` and `env_i64` live inside `sglang-server`, so no other Rust crate can read an environment variable without depending on the server, and every call site repeats the variable's name and default. Give the Rust side the same shape Python already has in `python/sglang/srt/environ.py`: one place that declares each variable, and call sites that only read it.

## Modifications

- Add the `sglang-environ` workspace crate (depends only on `tracing`).
- `EnvField<T>` holds a variable's name and its default; `EnvBool` / `EnvInt` / `EnvU64` / `EnvUsize` are its concrete forms and expose `.get()`. `get_with` adds a call-site rule for the one variable that needs it (the gRPC payload cap must be positive). Parsing stays crate-internal.
- `envs.rs` declares every environment variable the Rust crates read, so a call site becomes `envs::SGLANG_FOO.get()`, mirroring Python's `envs.SGLANG_FOO.get()`:

  | Variable | Type | Default |
  |---|---|---|
  | `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION` | bool | `true` |
  | `SGLANG_HEALTH_CHECK_TIMEOUT` | i64 | `20` |
  | `SGLANG_MAX_BATCH_REQS_PER_HTTP_REQ` | i64 | `4096` |
  | `SGLANG_DISAGGREGATION_BOOTSTRAP_ENTRY_CLEANUP_INTERVAL` | i64 | `120` |
  | `SGLANG_TONIC_PAYLOAD` | usize | `64 MiB` |
  | `REQUEST_TIMEOUT` | u64 | `3` |
  | `SGL_MM_RS_THREADS` | usize | `0` (= size the pool to the machine) |

- Migrate the call sites in `sglang-server`, `sglang-grpc` and `sglang-mm`, and drop what the declaration now owns: `ENTRY_CLEANUP_INTERVAL_ENV` / `ENTRY_CLEANUP_INTERVAL_DEFAULT_SECS` are gone, `DEFAULT_GRPC_MAX_MESSAGE_SIZE` points at the declared default, and `resolve_max_message_size` loses its hand-rolled `match` over `env::var`.

Accepted values, defaults, invalid-value warnings, and when each caller reads its environment are unchanged. `.get()` hits the process environment on every call, so nothing is cached inside a declaration; `MAX_BATCH_REQS_PER_HTTP_REQ` still reads once behind its `LazyLock`, and both `Duration::from_secs` call sites keep their `.max(0) as u64`.

Two deliberate side effects:

- `sglang-mm` picks up `tracing` transitively, and its two reads now warn on an invalid value instead of defaulting silently.
- The gRPC size cap logs its effective value once at startup rather than only when overridden.

This PR is independent of #38862. That HiCache change is still open; switching its Rust call site over can follow after both land.

## Accuracy Tests

Ubuntu 22.04 / x86_64, toolchain pinned by `rust-toolchain.toml` (1.92):

- `cargo test --workspace`: 311 passed, 0 failed (`sglang-environ` 2, `sglang-grpc` 13, `sglang-mm` 33 + 1, `sglang-server` 262).
- `cargo clippy --workspace --all-targets -- -D warnings`: clean.
- `cargo fmt --check`: clean.
- `cargo test -p sglang-mm --features parallel` (the wheel's feature shape, which is where `SGL_MM_RS_THREADS` is read): 33 passed.

The existing `resolve_max_message_size_honors_env_var` test is the behavior pin for the gRPC migration: unset, valid, invalid, and `0` all keep their previous results through `get_with`. `sglang-environ`'s own tests keep the Python `EnvBool.parse` parity table and add one test for typed `.get()` covering default-when-unset, parse-when-set, per-type rejection, and re-reading after the variable changes. Only that one test mutates the process environment, so nothing races under `cargo test`'s default parallelism.
