# [Fix] disaggregation: Settle the in-flight decode result before a PD decode retraction

[Upstream PR](https://github.com/sgl-project/sglang/pull/47482) · state: open · merged: False

## Original PR description

## Motivation

With overlap scheduling, a PD decode worker can retract a request while the previous decode step's result is still queued. The retraction backs up the request's device state and requeues the request. On resume, the backup is restored and the request decodes from `output_ids`.

By the time the backup is taken, the device state has already taken the in-flight step, but `output_ids` has not. Result processing skips retracted requests, so the in-flight step never reaches `output_ids`. The backup and `output_ids` end up one step apart:

- **Speculative decoding:** the in-flight verify commits its whole accepted block into KV and draft state. Those tokens never reach `output_ids`, so the resumed request skips tokens or ends early.
- **Recurrent state** (Mamba / GDN / KDA): a request has one slot that is updated in place, so the backup holds the state after the in-flight step. On resume the last token is fed again and the state advances twice.

For a pure-attention model without speculative decoding this is already correct: the offload covers `[:seqlen - 1]`, and the resumed step recomputes the last position.

`_reqs_finishing_inflight` already skips a retraction when the queued result finishes requests, but it does not settle the result.

## Modifications

- `Scheduler._settle_pd_decode_inflight` runs only when a PD decode step under overlap is about to retract, whether from memory pressure or `SGLANG_TEST_RETRACT`. It:
  - processes the queued results;
  - clears `last_batch` so the overlap loop does not process them again;
  - returns whether anything was settled.
- `update_running_batch` then drops requests that finished, and returns early if the batch is now empty. It rechecks memory, because the finished requests released their KV, and retracts only if memory is still short.
- Normal decode steps, non-PD schedulers and non-overlap schedulers keep the result in flight. Overlap is lost only on a step that retracts. `pause_generation` already drains the same way before it retracts.

## Accuracy Tests

The model forward is unchanged. The scheduler test below checks the invariant directly: a retracted request's backup has consumed exactly the tokens its `output_ids` hold.

## Speed Tests and Profiling

Only steps that retract under PD decode with overlap lose overlap. Retraction is already the slow path; other steps are unchanged.

## Tests

`test/registered/unit/managers/test_pd_decode_retract_overlap.py` (new, CPU, 8 cases) drives the real `Scheduler.update_running_batch` with a batch whose in-flight verify has advanced the device state by a 4-token accepted block:

- With an in-flight verify, the retracted request's backup matches `output_ids`, under both memory pressure and forced retraction. The result is settled before the request is requeued.
- Requests the settled result finishes leave the batch. Memory is rechecked, so nothing is retracted once their KV is freed. An emptied batch is returned without decode prep.
- Steps that do not retract, non-PD schedulers and non-overlap schedulers keep the queued result and `last_batch`.

On `main`, 5 of the 8 cases fail. With this PR all 8 pass.

CPU run of `test/registered/unit/managers/` (except `test_hisparse_unit.py`, which needs an accelerator) and `test/registered/unit/disaggregation/`: the same 2 failures as `main` (`test_mm_process_config.py::TestStreamOrderedMmFeaturePool`), plus the 8 new tests passing.
