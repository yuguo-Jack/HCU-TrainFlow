# fix: make scripted runtime request ID reuse and abort reliable

[Upstream PR](https://github.com/sgl-project/sglang/pull/38850) · state: open · merged: False

## Original PR description

## Motivation

Fixes #38788.

Scripted-runtime can reuse an ID after the scheduler finishes but before the old HTTP request finishes cleanup. Rejections become 60-second socket waits, and a late cleanup can abort the replacement request. ID-based history also lets a new handle inherit its predecessor's completion and chunk counts. Repeated aborts wait for a second scheduler message that the tokenizer never sends.

## Modifications

- Propagate HTTP errors, structured rejection bodies, and HTTP 200 SSE error events through the pending receive wait. Match generation arrivals by message type and ID.
- Check completed HTTP results before reporting completion, reusing an ID, issuing abort controls, and clearing tracking. Both scheduler and HTTP reset waits propagate late failures. Only exact HTTP 400 responses for an intentional terminal abort are accepted. An older duplicate-ID error cannot be retried as a new submission.
- Use non-streaming generation requests in the harness to avoid delayed SSE cleanup targeting a reused ID. The harness continues to observe scheduler state and actual generated tokens.
- Add `yield from t.start_req_with_retry(rid=..., max_steps=...)`. First drain the previous HTTP response, then retry only HTTP 400 with the exact duplicate-ID message, advancing real scheduler steps within one shared budget. Synchronous submission rejects reuse while the previous HTTP response remains open. Reset also drains HTTP work before discarding request tracking.
- Track each accepted submission and its actual scheduler `Req` identity. Keep old/new handles and chunk/park counts separate, and prevent old handles from aborting their replacements.
- Match abort messages by ID and type. A live first abort requires its scheduler message; repeated or completed aborts can finish after a successful HTTP acknowledgement without another message. Preserve HTTP failures and bound waits.
- Strengthen all five manual targets from the issue with actual output, finish-reason, request identity, and resource-release assertions. Add four regressions to the existing registered GPU fixture, plus deterministic CPU coverage for the lifecycle and transport boundaries.

All implementation changes are in the test harness; no serving, model-forward, or kernel code changes.

- Lipenghee · comment · 2026-09-10T09:48:43Z · [source](https://github.com/sgl-project/sglang/pull/38850#discussion_r3977758381)

This still has a late-failure hole. If the scheduler-side `Req` becomes finished before the background HTTP request fails, this branch returns `True` without ever observing `epoch.post_future.result()`. The reuse path has the same issue: it waits for `done()` but does not read the previous result before registering the next epoch, and reset only checks `done()` before clearing tracking.

I reproduced this on 508e807345 by registering an epoch, recording its `Req`, setting `req.finished_reason = FINISH_LENGTH(...)`, and then `post_future.set_exception(RuntimeError("stream failed after scheduler finish"))`; `handle.finished` returned `True`. Thus a POST error that lands after scheduler completion is still only logged by the done callback and can be discarded or overwritten, contrary to the failure-propagation contract.

Please centralize checking an epoch completed post result, including the intentional abort exceptions, and invoke it before reporting completion, before reuse replaces the epoch, and before reset clears tracking. A regression should exercise this exact ordering: scheduler finished first, post future failed second.
