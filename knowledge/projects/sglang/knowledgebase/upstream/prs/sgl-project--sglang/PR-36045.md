# fix: make FlashInfer NVFP4 speculative decoding graph-safe

[Upstream PR](https://github.com/sgl-project/sglang/pull/36045) · state: closed · merged: False

## Original PR description

## Motivation

Alternative to #36038. While #36038 routes speculative execution through TRTLLM MHA's native FP4 decode path, this PR preserves FlashInfer speculative prefill by making its dequant workspace GPU-resident and CUDA Graph safe.

With NVFP4 KV cache, FlashInfer's existing workspace path depends on CPU-side prefix metadata. Runtime speculative metadata does not always provide that mirror, so target verification—and, because the draft worker inherits the explicit NVFP4 KV dtype, draft extend—can fail or reuse stale prefill workspace metadata.

## Modifications

- Add a fixed-grid Triton kernel that dequantizes cached NVFP4 prefixes directly into the FP8 workspace at physical KV slots.
- Cover both target verification and `DRAFT_EXTEND_V2`; all request indices, sequence lengths, mappings, and output locations remain device-resident during capture/replay.
- Preserve graph-padding isolation through reserved slot 0, and support noncontiguous current K/V row strides without allocating in the graph.
- Route eager and CUDA Graph draft-extend metadata away from the CPU/page-aligned prefill workspace.
- Add explicit guards for missing speculative metadata/current K/V/write locations and for accidental entry into the CPU workspace without all host mirrors.
- Document and enforce that each workspace row equals this TP rank's `kv_heads * head_dim`.
- Account for the draft worker's independent FP4 dequant workspace when sizing the shared token budget, including integrated MTP checkpoints whose draft path is implicit.
- Extend registered CUDA and CPU regression tests for target/draft graph replay and FP4 EAGLE pool sizing.

## Accuracy Tests

Validation used the current PR source with the SGLang v0.5.18 dependency stack (`torch==2.13.0+cu130`, `flashinfer-python==0.6.17`, `sgl-kernel==0.4.6.post1`) on an RTX PRO 5000 Blackwell (SM120), TP=1.

Exact checkpoint: `RadixArk/Qwen3.8-27B-NVFP4` at `/mnt/data/modelscope-RadixArk-Qwen3.8-27B-NVFP4`. Loader output confirmed `Detected nvfp4 checkpoint`; the target loaded as ModelOpt mixed precision (20.14 GB) and the integrated `Qwen3_5ForCausalLMMTP` draft as ModelOpt mixed precision (5.53 GB).

The #36010 flags were exercised with NVFP4 KV, FlashInfer prefill, TRTLLM MHA decode, NEXTN/MTP 3/1/4, 131072 context, `mem_fraction_static=0.93`, graph BS 1/2, and radix cache disabled.

- Target prefill, target verify, draft decode, and draft extend CUDA Graph capture all completed.
- Graph replay passed at batch sizes 1 and 2; the BS=2 request specifically exercises graph padding.
- Eager speculative target/draft execution passed with CUDA Graph disabled.
- Exact 32K and 128K input-ID requests, each generating 16 tokens, returned HTTP 200 with an observed speculative acceptance length of 4.0.

| Input tokens | CUDA Graph wall time | Eager wall time |
| ---: | ---: | ---: |
| 32,000 | 8.158 s | 5.259 s |
| 128,000 | 39.283 s | 39.248 s |

The original `mem_fraction_static=0.93` startup also succeeds after pricing the independent draft FP4 workspace: the resolved token pool changes from the overcommitted 2,035,968 slots to 1,760,832 slots, leaving 10.30 GB after the target pool and 5.05 GB after the draft pool.

Local regression results:

- `test_nvfp4_kv_cache.py`: 2 passed (target verify and draft extend, bit-exact PyTorch reference plus changed-length CUDA Graph replay).
- `test_pool_configurator.py`: 36 passed, 2 subtests passed.
- `test_spec_aux_hidden_state.py`: 6 passed.
- `compileall` and `git diff --check`: passed.

## Speed Tests and Profiling

SM120 physical-workspace microbenchmark using the exact Qwen3.8 TP=1 KV row (`4 heads * 256 head_dim = 1024` elements), measured over CUDA Graph replay:

| Cached prefix | Target verify / layer | Draft extend / layer | Minimum traffic | Effective bandwidth |
| ---: | ---: | ---: | ---: | ---: |
| 32,000 | 0.229 ms | 0.228 ms | 102.4 MB | ~448 GB/s |
| 128,000 | 1.021 ms | 1.021 ms | 409.6 MB | ~401 GB/s |

For this 64-layer hybrid checkpoint (16 full-attention target layers plus one MTP draft layer), that isolates to approximately 3.89 ms per speculative cycle at 32K and 17.35 ms at 128K. The cost is linear in committed prefix length; reuse/layer batching can be explored separately if long-context profiling warrants it.

Thanks — the graph-safe workspace kernel is a clean alternative to routing verify through
trtllm_mha (#36038), and the test quality here is excellent: the bit-exact reference check
plus a real capture/replay with changed device-side prefix lengths (NaN sentinels) and
non-contiguous K/V strides is the strongest correctness evidence in either of the two
candidate fixes for #36010. Notes from static review (we have not run this branch; our
interest is a production TP=4 hybrid Qwen3.8-27B shape on SM120, page_size=1, MTP 3/1/4):

1. Things that checked out in our reading
- `prefix_lens := forward_batch.seq_lens` is correct for verify batches: seq_lens excludes
  draft tokens (eagle_utils builds out_cache_loc from `start_offset=batch.seq_lens`), so
  the prefix slots and current-token slots never overlap — no read/write race in the kernel.
- The slot-0 padding suppression matches the pool's documented design ("The padded slot 0
  is used for writing dummy outputs from padded tokens"), so graph padding is handled on
  solid ground.
- Patching the HybridLinearKVPool wrapper as well as the base pool means hybrid GDN models
  are covered — that's the exact topology in #36010 and in our deployment.

2. Questions / gaps
- Draft-side coverage: with an explicit `--kv-cache-dtype nvfp4`, the draft worker's pool
  is also NVFP4 (configure_kv_cache_dtype applies it to draft workers; only DFLASH/fa4 has
  an override). This PR handles target_verify only; draft_extend_v2 / legacy draft extend
  on the flashinfer prefill backend would still reach the old
  `get_flashinfer_dequant_workspace_kv_buffer` path. Which backend served draft decode and
  draft extend in your E2E, and is that path covered? (In #36038 the authors explicitly had
  to handle legacy draft extend being rejected by the native-FP4 guard, which suggests the
  draft side is easy to miss.)
- Consider absorbing #36038's `_reset_dequant_workspace_metadata()` / spec-forward
  rejection guards: without them, the stale-`dq_page_table` + unguarded `forward_extend`
  combination from #36010 remains reachable for any other extend-family spec forward.
- Per-step cost at long context: the kernel dequantizes the entire committed prefix on
  every verify step, per full-attention layer. Extrapolating your own microbench
  (131,072 tokens → 1.887 ms per invocation) to 16 layers at ~256K context gives on the
  order of tens of ms per verify step — fine for short contexts, but likely prohibitive
  for long-context MTP. Could you share an E2E throughput/latency number at e.g. 32K/128K
  context so users can size this? (A "dequant-once-per-prefix, reuse across steps" scheme
  or layer-batched variant might be worth exploring if the cost shows up.)
- Your E2E used Qwen3.8-27B-FP8 weights + NVFP4 KV; the reporter's environment (and ours)
  uses NVFP4 weights. The KV path is the same, but a confirmation run on an NVFP4-weight
  checkpoint would remove the last env delta vs #36010.

3. Small suggestion: an explicit `assert` or doc note that the workspace row size must
  equal `head_num * head_dim` per rank (ROW_ELEMENTS % 16 == 0 is checked; the
   per-rank-heads implication under TP>1 is worth stating for maintainers).

The physical-slot indexing also makes this route naturally page-size-agnostic — relevant
for page_size=1 deployments like ours where the XQA route's page-size affinity is a
separate unknown.

@jerry-he Thanks for the detailed review. I addressed the gaps in follow-up commit `02d55f5`.

1. **Draft-side NVFP4:** confirmed—the explicit KV dtype is inherited by the draft worker. `DRAFT_EXTEND_V2` now takes the same GPU-resident physical-slot workspace path as target verify in both eager execution and CUDA Graph replay. Draft sequence lengths are post-write, so the kernel subtracts the fixed `num_tokens_per_req` before dequantizing the committed prefix. I captured and replayed draft-extend graphs at BS 1/2. Current main only exposes `DRAFT_EXTEND_V2` as the draft-extend `ForwardMode`; the old CPU path now also fails early with a clear error if its required host mirrors are absent.

2. **Stale metadata / guards:** target verify and draft extend now branch before the ordinary prefill workspace and ignore `dq_page_table`/CPU mirrors. I added explicit checks for speculative metadata, positive fixed token width, current K/V, write locations, matching batch/length shapes, and an early guard around incomplete CPU workspace metadata.

3. **TP row invariant:** the kernel doc now states `per_rank_kv_heads * head_dim`, and the pool checks both K and V workspace row widths against the current layer's TP-local geometry.

4. **Exact checkpoint:** reran on `RadixArk/Qwen3.8-27B-NVFP4`. The loader reported `Detected nvfp4 checkpoint`; target/MTP draft loaded as ModelOpt mixed precision at 20.14/5.53 GB. 5. **32K/128K E2E (TP=1, SM120, 16 generated tokens):** both graph and eager runs returned HTTP 200 with observed acceptance length 4.0.

| Input tokens | CUDA Graph | Eager |
| ---: | ---: | ---: |
| 32,000 | 8.158 s | 5.259 s |
| 128,000 | 39.283 s | 39.248 s |

6. **Isolated dequant cost:** with the exact TP=1 row geometry (4 KV heads × 256), graph replay measured 0.229 ms/layer at 32K and 1.021 ms/layer at 128K for target verify; draft extend was 0.228/1.021 ms. It scales linearly, so dequant-once reuse remains a sensible follow-up optimization for longer contexts.
