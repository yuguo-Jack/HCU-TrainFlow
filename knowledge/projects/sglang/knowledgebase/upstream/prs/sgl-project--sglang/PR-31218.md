# [DSA] Page-aware move_kv_cache for the DSA indexer cache (fix page_size>1 corruption)

[Upstream PR](https://github.com/sgl-project/sglang/pull/31218) · state: open · merged: False

## Original PR description

## Motivation

`IndexKeyCache.move` (reached from `DSATokenToKVPool.move_kv_cache`) moves the DSA indexer cache with
a whole-row copy per token:

```python
for index_k in self.buffer:                        # PAGE-indexed: (num_pages, page_size*(...))
    index_k[tgt_loc_flat] = index_k[src_loc_flat]  # tgt/src are per-TOKEN locations
```

The buffer is **page-indexed**. Dim-0 is the page. Inside one page row, the `page_size` fp8 keys come
first as one block, then a block of `page_size` fp32 scales. But `tgt_loc/src_loc` are **token**
locations. Using them on dim-0 is only right when `page_size == 1`. At `page_size == 64` the token
locations go up to `size`, which is far past `num_pages ≈ size/64`, so the copy hits the **wrong page
row, or goes out of bounds**.

This is not a small numeric error. An out-of-bounds row index crashes or trips a device assert, and a
wrong-page write scrambles the indexer cache. Either way DSA top-k selection breaks.

## Why CUDA has not hit this

This move only runs on the **`topk>1`** path, through `move_accept_tokens_to_target_kvcache`. CUDA DSA
runs EAGLE/MTP with **`topk == 1`** (the linear chain), so the path never executes there. `page_size ==
64` is normal on CUDA DSA, but the buggy move never runs, which is why nothing has broken so far even
though the bug is not ROCm specific. That is also why the test below needs no GPU: there is no
end-to-end repro to ship until `topk>1` drafting is enabled on DSA.

## Modifications

Map each token location to its `(page, offset)` and move both of its pieces, the fp8 key and the fp32
scale, through `as_strided` views over the two blocks in a page row:

```python
sc    = hd // pool.quant_block_size * 4   # scale bytes per token, same formula as _buffer_shape
fp8   = index_k.as_strided((num_pages, ps, hd), (row_stride, hd, 1), base)
scale = index_k.as_strided((num_pages, ps, sc), (row_stride, sc, 1), base + ps*hd)
fp8[tgt_page, tgt_off]   = fp8[src_page, src_off]      # the right side gathers into a new tensor
scale[tgt_page, tgt_off] = scale[src_page, src_off]    # before the write, so overlap is safe
```

This works for any page size and covers the old `page_size == 1` case, so the per-token row copy goes
away. The base MLA `super().move_kv_cache` (token-indexed, already correct) is untouched, and so is
the 0-row placeholder skip for skip-topk layers.

> Rebased onto current `main`: the DSA index buffer now sits behind the `IndexKeyCache` facade, so the
> fix lands in `IndexKeyCache.move` instead of `memory_pool.py`. That refactor copied the bug over
> unchanged.

## Accuracy Tests

`test/registered/unit/mem_cache/test_dsa_move_kv_cache.py` — **3/3 pass**, no GPU needed. It builds
the page-packed buffer by hand, gives each token a unique value in both its key and its scale, moves a
set that crosses pages at varied offsets, and checks every moved token plus one untouched token.

`IndexError: index 66 is out of bounds for dimension 0 with size 4`.

`index_head_dim // quant_block_size * 4`, which is 4 only while those two are equal. The test uses
`quant_block_size=64` so the width is 8, and it fails if the view hard-codes 4.

## Please read before prioritising

The code is wrong and the test proves it, but **nothing can reach it today**. Both callers need
`speculative_eagle_topk > 1`, and `speculative_hook.py` rejects `topk>1` together with `page_size>1`
unless the attention backend is `flashinfer/fa3/triton` (EAGLE) or `flashinfer` (NGRAM). DSA forces
`backend="dsa"` with `page_size=64`, so it is in neither list. Confirmed by running it — NGRAM on
GLM-5.2 refuses to start:

```
ValueError: speculative_eagle_topk(10) > 1 with page_size(64) > 1 is unstable and produces
incorrect results for paged attention backends. This combination is only supported for the
'flashinfer' backend.
```

So this is groundwork for turning on `topk>1` tree drafting with DSA later, not a fix for something
users hit now.

- kalenforn · comment · 2026-08-28T08:32:49Z · [source](https://github.com/sgl-project/sglang/pull/31218#issuecomment-5450292786)

Thanks for picking this up — we hit the same bug out-of-tree and landed on the same page/offset
split, so it is good to see a main-shaped fix with a registered CPU test. Two things from our side:
one gap, and an answer to the reachability question already being discussed here.

### The gap: the ROCm aiter preshuffle layout

The views are built assuming a token's fp8 bytes are contiguous within a page:

```python
fp8 = index_k.as_strided((num_pages, ps, hd), (row_stride, hd, 1), base)
```

That matches the layout the store kernel writes in its **non**-preshuffle branch
(`python/sglang/kernels/ops/attention/dsa/index_buf_accessor.py:393-397` on `main`):

```python
out_k_offsets = (
    loc_page_index * BUF_NUMEL_PER_PAGE
    + loc_token_offset_in_page * NUM_K_ELEMS_PER_TOKEN
    + k_range
)
```

But under `PRESHUFFLE_TILE` the same kernel writes them tile-interleaved (`:379-391`):

```python
tile = PRESHUFFLE_TILE
token_tile_id = loc_token_offset_in_page // tile
token_in_tile = loc_token_offset_in_page % tile
col_tile_id   = k_range // tile
col_in_tile   = k_range % tile
out_k_offsets = (
    loc_page_index * BUF_NUMEL_PER_PAGE
    + token_tile_id * (tile * NUM_K_ELEMS_PER_TOKEN)
    + col_tile_id * (tile * tile)
    + token_in_tile * tile
    + col_in_tile
)
```

There a token's bytes sit at stride `tile`, split across `col_tile_id` blocks — not at
`(hd, 1)`. So on a preshuffle build `fp8[tgt_page, tgt_off] = fp8[src_page, src_off]` would move a
mixture of bytes belonging to several tokens in the same tile.

This does not need a ROCm build to check — the two layouts are index arithmetic, so the offset sets
can just be enumerated:

```python
hd, ps, tile = 128, 64, 16   # NUM_K_ELEMS_PER_TOKEN, page_size, PRESHUFFLE_TILE

def strided(tok):     # what as_strided((..., ps, hd), (row_stride, hd, 1)) addresses
    return {tok * hd + c for c in range(hd)}

def preshuffle(tok):  # index_buf_accessor.py:379-391
    tt, ti = tok // tile, tok % tile
    return {tt*(tile*hd) + (c//tile)*(tile*tile) + ti*tile + (c%tile) for c in range(hd)}

>>> sum(strided(t) != preshuffle(t) for t in range(ps))
64                                    # all 64 tokens in the page
>>> sorted(strided(1))[:4], sorted(preshuffle(1))[:4]
([128, 129, 130, 131], [16, 17, 18, 19])
>>> len(strided(1) & preshuffle(1))
0                                     # not one byte in common
>>> max(max(strided(t)), max(preshuffle(t)) for t in range(ps)) < ps * (hd + 4)
True                                  # every offset stays inside the page
```

The last line is why it would be **silent**: all the offsets remain inside
`BUF_NUMEL_PER_PAGE`, so the `maybe_detect_oob` page-dim probe cannot see it, and neither can an
index assert further downstream.

What makes this worth raising here rather than as a follow-up is that **preshuffle is the only ROCm
configuration in which this bug exists at all.** `DSATokenToKVPool.__init__`
(`python/sglang/srt/mem_cache/memory_pool.py:4534-4542`) pins that:

```python
if _is_hip:
    if aiter_can_use_preshuffle_paged_mqa():
        assert self.page_size % 16 == 0, "HIP preshuffle requires page_size to be a multiple of 16, ..."
    else:
        assert self.page_size == 1, "HIP legacy DSA path requires page_size == 1, ..."
else:
    assert self.page_size == 64
```

The page/offset bug only manifests at `page_size > 1`, and on HIP the only route to `page_size > 1`
is preshuffle. So the ROCm path this PR fixes and the ROCm path the strided view would get wrong are
the same path.

I think this is also why it has not come up in review: the layout walked through above was
*"each row = `ps*hd` fp8 bytes followed by `ps*4` scale bytes"*, which is exactly the non-preshuffle
formula, and against that layout the split is correct.

Two resolutions, either seems fine:

1. Branch on `aiter_can_use_preshuffle_paged_mqa()` and mirror the store kernel's tile arithmetic
   for the move.
2. Raise `NotImplementedError` naming the layout under preshuffle, so the gap is loud, and handle it
   separately.

We took (2) out-of-tree, on the grounds that copying wrong bytes into a committed KV cache is the
worst available failure mode and we had no preshuffle build to test against. A test case with
`PRESHUFFLE_TILE` set would pin whichever you choose — `test_scale_width_from_quant_block_size` is a
good precedent for that shape of test.

### On "document the real reason CUDA never triggers this"

We looked at reachability too, and found one caller that may complicate the current framing:
`python/sglang/srt/speculative/ngram_worker.py:501` calls the mover **unconditionally**, and
`--speculative-ngram-max-bfs-breadth 1` passes the `topk > 1 + page_size > 1` rejection in
`arg_groups/speculative_hook.py`. So the "nothing reaches this today" line may be narrower than it
reads.

Stated as a validation-chain reading, not a repro — we did not run it, and we are on CUDA where

**A separate matter, on the other half of the same method.** Raising it here rather than elsewhere
only because it bears on a line in this PR's description, and because it is downstream of the
reachability question above. It is **not** a request to widen this PR's scope.

The description says:

> The base MLA `super().move_kv_cache` (token-indexed, already correct) is untouched.

That holds without decode context parallelism. Under `--dcp-size > 1` it does not, and it is the
same class of bug this PR fixes — an id used in the wrong space — on the latent-KV side instead of
the indexer side.

`MLATokenToKVPool.move_kv_cache` does `kv_cache[tgt_loc_flat] = kv_cache[src_loc_flat]` with the
allocator's widened **virtual** slot ids, while under DCP that buffer holds only this rank's shard.
The write kernel's own rule is `loc % DCP_WORLD_SIZE == DCP_RANK`, stored at
`loc // DCP_WORLD_SIZE` (`kernels/ops/kvcache/mla_buffer.py`). At `dcp_size == 8`, virtual slot
300 means "rank 4, row 37" — but every rank runs `kv[70] = kv[300]` against its own buffer, reading
row 300 and writing row 70. Both rows hold other tokens, and seven of the eight ranks own neither
endpoint.

**The evidence is not a reading of mine — it is #39487.** That merged fix added

```python
indices = maybe_dcp_kernel_indices(
    indices, self._write_loc_dcp_span, get_parallel().attn_dcp_rank
)
```

to `get_cpu_copy` / `load_cpu_copy`, whose input is `req_to_token[req_pool_idx, : seqlen - 1]`.
Either that fix was a no-op, or ids drawn from `req_to_token` / `out_cache_loc` are widened — and
`move_kv_cache`, taking the same kind of id into the same buffer, needs the same treatment. One of
two sibling methods on one class has it.

Two smaller things in the same two lines:

- the bound is `maybe_detect_oob(tgt_loc, 0, self.size + self.page_size, ...)` — global ids against
  the **local** row count. `set_mla_kv_buffer`, two methods up, multiplies by
  `_write_loc_dcp_span` for exactly this reason. **This half needs no design decision**; it reads
  as a one-line omission;
- and it cannot fire in production anyway: `maybe_detect_oob` is gated by `SGLANG_INVARIANT_CHECK`,
  default `InvariantCheckLevel.OFF` — its own comment calls that the prod default. Turned **on**,
  the short bound makes it report a **spurious** OOB on a healthy run.

**One of the two call sites is free; the other is not, and the distinction is provable.** A token
move under DCP is rank-local **iff** `tgt % dcp_size == src % dcp_size`.

- `duplicate_prefix_tail_to_draft_branches` is **congruent**: the helper builds
  `src_pos = prefix_base + page_off` and
  `tgt_pos = prefix_base + b * num_new_pages * page_size + page_off` — a page-aligned base plus the
  same offset on both sides — and the paged allocator fills `req_to_token` page-aligned, so
  `src % page_size == tgt % page_size`, hence congruent modulo any `dcp_size` dividing `page_size`.
  A plain translate is correct here.
- `move_accept_tokens_to_target_kvcache` is **not**. `tgt_cache_loc` comes from
  `assign_extend_cache_locs` over `req_to_token` at sequence positions
  `[seq_lens, seq_lens + num_correct + 1)`; `accept_out_cache_loc` comes from
  `out_cache_loc[accept_index]`, the draft slots at the accepted **tree node** indices. The
  target's residue follows the sequence position and the source's follows the tree node index, so
  nothing makes them congruent. The bytes are on another rank, and a per-pool method with no
  communicator cannot move them — that needs either a collective at a higher layer or a documented
  restriction. We took the second route out-of-tree, which is containment, not a fix.

**Reachability for this half, with NGRAM's own gate applied.** That gate needs `page_size > 1` to
fire, so it says nothing at `page_size == 1`. There a tree-shaped drafter boots: NGRAM resolves
`speculative_eagle_topk` to its breadth, and the compaction is then not an identity transform,
because NGRAM drafts a **tree** — `reconstruct_indices_from_tree_mask`, parents /
`retrive_next_token` / `retrive_next_sibling`, a `draft_token_num × draft_token_num` mask. So
`accept_index` picks a path through that tree, the accepted tokens are scattered across the draft
block, and the move is real. Nothing in `arg_groups/` couples NGRAM to `dcp_size` in either
direction.

The page-major defect this PR fixes needs `page_size > 1`, since at `page_size == 1` the token id
and the page id coincide. This one does not depend on `page_size` at all — it needs the MLA buffer
to be sharded, which is `--dcp-size > 1`. Different preconditions, which is part of why they read
as separate fixes rather than one.

Stated as a validation-chain reading, not a repro. We cannot test it: our own deployment runs EAGLE
with `--speculative-eagle-topk 1` on a DSA pool, where the accepted path is already the front chain
and the compaction is an identity transform, so this code never executes for us — the same reason
this PR ships a GPU-free test.

For context, `python/sglang/srt/speculative/` contains no DCP references at all — `dcp_size`,
`dcp_rank`, `attn_dcp`, `maybe_dcp`, `KVIndexTranslator` are all zero matches across the directory
— consistent with #39330 keeping speculative decoding out of scope, and with #39117 reworking this
surface now (its new `dcp_replicated` flag makes `_write_loc_dcp_span` return 1 for replicated
pools; the sharded case above is unchanged by it).

same fix, and I did not want to attach a second defect to a PR that is already waiting.
