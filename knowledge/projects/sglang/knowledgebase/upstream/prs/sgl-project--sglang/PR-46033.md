# [Feat] unified_cache: [WIP] Support PP prefill and DSA PD decode in the Mooncake external linker

[Upstream PR](https://github.com/sgl-project/sglang/pull/46033) · state: open · merged: False

## Original PR description

> [!WARNING]
> **WIP.** Correctness is validated (below), but performance is not acceptable yet. On the GLM-5.2
> cookbook's PP4 prefill configuration at concurrency 264, the Mooncake linker reuses far fewer cached
> prefixes than HiCache does (0.27-0.78 vs 0.95 of prefill input cached), and prefill saturates. This
> PR stays a draft until that gap is understood.

## Motivation

The external linker (`--enable-unified-cache-external-linker`) fails in two independent ways on a
disaggregated GLM-5.2 deployment whose prefill uses pipeline parallelism. The GLM-5.2 cookbook offers
the linker as a KV-offload option for exactly such deployments, including its PP4-prefill
configurations. Both failures reproduce on main.

1. **DSA index-K layout (any prefill parallelism).** DSA shared-topk layers own a 0-row index-K
   placeholder (GLM-5.2: 57 of 78 layers). The linker's `DevicePoolEntry` divides by each buffer's row
   count, so `_should_elide_dsa_index_k` turned elision off whenever the linker was on. A PD decode
   without the linker keeps the compact layout, so the P->D state transfer targets decode buffers that
   were never registered. With NIXL every request fails: `createXferReq: no specified or potential
   backend had the required registrations`.
2. **No PP consensus.** Each PP stage runs its own scheduler and stores its own layers under its own
   Mooncake key suffix (`cp{c}_pp{k}`), but every linker decision was reduced over attention TP/CP only:
   - the restorable prefix (`_sync_restorable_prefix`): stages pick different hit lengths;
   - offload completions (`check_hicache_events`): a node stays locked on one stage and is evictable on
     another, so the device trees drift;
   - a failed load (`finish_loads`): requests are aborted on one stage only.

   The stages' batches then diverge. On a TP1 x PP4 prefill the stages logged 86/85/82/80 linker hits,
   then stage 1 crashed in `set_mla_kv_buffer` with `Size mismatch for shape#0('batch_size'): expected
   1803 but got 2699`: the previous stage sent 1803 tokens, while this stage had restored 14 pages less
   and scheduled 2699.

HiCache already handles PP with `_all_reduce` (PP0 reduces, `_pp_sync` hands the result down the
pipeline); this PR applies the same pattern to the linker.

## Modifications

Commit 1, `[Fix] mem_cache: Keep the compact DSA index-K layout with the external linker`:
- `_build_dsa_device_pool_group` leaves the 0-row placeholders out of the index-K entry
  (`_dsa_indexer_layers`) and maps each transfer layer to the buffers that hold keys; a packed draft
  depth N still rides on transfer layer N, alone when target layer N is shared.
- The entry is named `PoolName.COMPACT_INDEXER` (store object `<page>_<suffix>_compact_indexer`), so a
  store object written in the full layout under `indexer` is never read as the compact one, and the
  reverse. Upgrading costs one round of index-K misses for linker users whose layout did not change
  (models without shared-topk layers, NPU).
- `_should_elide_dsa_index_k` keeps the compact layout with the linker on CUDA. NPU keeps the full
  layout, since its pool drops the placeholders instead of keeping them layer-aligned.

Commit 2, `[Feat] unified_cache: Support pipeline parallelism in the Mooncake external linker`:
- Lookup: PP0 checks every stage's pages (`lookup_pipeline_stages`; for Mooncake, per-stage views of
  the store that differ only in key suffix, each restricted to that stage's pools) and intersects the
  restorable sets. The later stages skip the store and receive PP0's mask through `_all_reduce`.
  Mooncake's existence query grants a read lease on each page it finds (`BatchExistKey`), which keeps
  a later stage's pages until that stage loads them.
- Stages may hold different pools (a stage whose DSA layers all reuse another layer's top-k stores no
  index-K). The linker gathers each stage's pool set at init and fails if a stage holds a pool that
  stage 0 lacks, such as a draft pool hosted only on the last stage (FULL + MAMBA + MTP).
- Offloads: the stages adopt PP0's completion count and verdicts; a later stage blocks on its own
  copies (`pop_completed_offload(block=True)`, which only PP passes). If a later stage's own put fails
  while PP0's succeeds, PP0's lookup misses that prefix (it checks every stage's pages) and the node is
  not re-offloaded until it is evicted, so it can cost one recompute.
- A load failure under PP raises instead of aborting the requests on one stage, since only the failing
  stage knows. It relies on the Mooncake master's `--default_kv_lease_ttl` (10 s by default) outlasting
  a request's pass through the pipeline; the `--enable-unified-cache-external-linker` help text says so.
- `--enable-unified-cache-external-linker` with `--pp-size > 1` requires the Mooncake backend. A PD
  decode server only offloads, so it skips the stage-pool check.

Follow-ups, not in this PR: a consistent abort under PP (the failure would have to travel along the
pipeline's proxy/output tensors); one batched existence RPC for all stages instead of one per stage;
deriving each stage's lookup keys from its own pool map, which would lift the stage-0 pool requirement.

## Accuracy Tests

GB300, nightly image `nightly-dev-cu13-20261021-c1c287a4` with this change ported (identical hunks)
and #45559 backported, NIXL P->D, GLM-5.2-NVFP4 with EAGLE MTP, one prefill node -> one DEP4 decode node,
prefill `--max-total-tokens 65536` so prefixes are evicted from HBM and must come back from Mooncake.

| prefill | weights | client | result |
|---|---|---|---|
| TP1 x PP4, main | dummy | 48 sessions x 8 growing turns + replay | stage 1/3 crash (above); with commit 2 only, every request 500 (index-K) |
| TP1 x PP4, this PR | dummy | same | 432/432 OK; all stages logged identical `Prefill batch` sequences (224 batches); 402 lookup hits; store evicting at its watermark, 0 load failures |
| TP1 x PP4, this PR | real | needle: 32 docs of ~4.9k tokens with a hidden code, filled then queried after eviction | 32/32 correct; 156k of 159k query tokens restored from Mooncake |
| TP4 (no PP), this PR | real | needle | 32/32 correct; 156k of 159k query tokens cached, 128 linker hits (4 ranks x 32) |
| TP2 x PP2, this PR | real | needle | 32/32 correct; identical batches on both stages (31); 64 PP0 lookup hits (2 TP ranks x 32) |

Unit tests: new cases in `test_unified_cache_linker.py`, `test_linker_pool_assembler.py` and
`test_server_args.py` fail on main and pass with this PR.

## Speed Tests and Profiling

Not a performance PR, and no throughput claim is made. One scale run for stability: the GLM-5.2 cookbook's AgentX
`3p1d_pp4_dep8_c264` configuration (3 x (TP1 x PP4) prefill -> DEP8 decode) with the Mooncake linker in place of HiCache
(store capacity equal to the HiCache host pool, 185 GB per prefill rank), the cookbook's AgentX multi-turn coding
workload at concurrency 264.

- All 4 stages of each prefill worker logged identical `Prefill batch` sequences for the whole run
  (8,003, 7,339 and 5,178 batches), with no load failures while the store was up.
- The store delivered far fewer prefix hits than HiCache's host tier does on the same configuration:
  the cached fraction of prefill input was 0.27 / 0.60 / 0.78 per worker over the first 30 minutes,
  against 0.95 for the same configuration with HiCache (run on the 2026-10-16 nightly). Prefill saturated and the run was stopped before its measured phase, so
  it gives no throughput number. The linker writes through every inserted node, so the store largely
  duplicates what is still in GPU memory, while HiCache's write-back host tier holds only what GPU
  memory evicted; whether that explains the whole gap is not established here.
- On shutdown the Mooncake master stopped before the prefill workers, their in-flight loads failed,
  and the PP fail-stop raised as designed.
