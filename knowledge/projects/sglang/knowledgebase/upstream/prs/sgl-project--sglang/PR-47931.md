# [Fix] unified-cache: Skip re-offloading pages restored from the external linker

[Upstream PR](https://github.com/sgl-project/sglang/pull/47931) · state: closed · merged: False

## Original PR description

## Motivation

With the unified cache external linker, a request that restores a prefix from the store uploads that prefix again. `load_back` writes the restored tail into request-private slots. After the forward, the request inserts the tail into the tree as new nodes with `external_cache_stored=False`. Because the linker sets `write_through_threshold=1`, those nodes are backed up again right away.

Mooncake hides this: `batch_set_v2` filters out keys that already exist before writing. `UMBPDirectLinker` has no such filter, so every turn writes the whole restored prefix to the store again.

## Modifications

- `load_back` records the range it restored, `req.linker_restored_key_range = (device_hit_len, prefix_len)`, after PREPARE.
- `checkpoint_into_tree` passes the range to `skip_offload_prefix`. `_drop_offload_skip_prefix` (from #46395) drops the pages of transfers that start inside the range, and marks nodes the range fully covers as stored.
- Pages before the range are the device hit. The store may not hold them, so they are offloaded as before.
- `Req.reset_for_retract` clears the range.
- `test_full_offload_load_round_trip_and_dedup` now asserts that the consumer does not offload the restored prefix again. On main this assertion fails with both the Python and the Rust tree core.

As in #46395, there is no persistence ACK. If the store evicts the pages between the load and the insert, the node is still marked stored.

## Results

**Setup**
- Model and hardware: DeepSeek-V4.1-Flash, 1P1D on one MI355X node.
- Topology: prefill TP4/DP4 and decode TP4/DP4, both with DP attention. MoRI KV transfer.
- Store: one UMBP standalone server shared by both roles.
- Image: `lmsysorg/sglang-rocm:v0.5.23-rocm10-mi35x-20261101` with this patch and #46395 applied.
- Workload: 16 sessions, 4 turns each. The first prompt is 8K tokens; each turn generates 1K output tokens, and the next prompt adds them plus 512 new tokens. Both device caches are flushed between turns, so every prefill hit comes from the store.
- Counting: every UMBP put key was logged per process.

| Linker setup | Change | Turn 1-3 prefill hit rate | UMBP puts per distinct key |
|---|---|---|---|
| Prefill only | without this PR | 0.842 / 0.864 / 0.880 | 3.28 |
| Prefill only | this PR | 0.842 / 0.864 / 0.880 | **1.000** |
| Prefill + decode (#45556, decode radix cache) | without this PR | 0.944 / 0.949 / 0.959 | 3.33 |
| Prefill + decode (#45556, decode radix cache) | this PR | 0.946 / 0.946 / 0.958 | **1.000** |

- Prefill-only rows: prefill KV puts fall from 2624 to 800 per pool, which is 16 sessions × 50 pages, so each page is written once. The hit rate is identical: summed prefill `#cached-token` is 466,944 in both runs.
- Prefill + decode rows: prefill and decode now write disjoint key sets.

**Accuracy (gsm8k, 400 questions)**
- Prefill-only linker with this PR: 0.885.
- Prefill + decode with this PR: 0.907.
- Prefill + decode without this PR: 0.895.

### issue_comments

- AMD-yanfeiwang · comment · 2026-11-03T03:21:34Z · [source](https://github.com/sgl-project/sglang/pull/47931#issuecomment-6594603172)

Closing. The duplicate puts I measured were sglang-side `batch_put_ranges_from_ptr` calls, not store writes: UMBP already returns existing keys as success without copying (`kSuccessAlreadyExists` on the local path, `kAlreadyExists` from `BatchRoutePut` with a master), and Mooncake filters existing keys before putting. Not tracking the restored length also lets a restored key that the store later evicts be stored again, which this change would have prevented.
