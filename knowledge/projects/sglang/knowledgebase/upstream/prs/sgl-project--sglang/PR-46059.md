# [Fix] [AMD] qwen3_5: Rotate the online MXFP4 GDN projections by Hadamard-32

[Upstream PR](https://github.com/sgl-project/sglang/pull/46059) · state: open · merged: False

## Original PR description

## Motivation

This ROCm accuracy fix rotates the online MXFP4 GDN `in_proj_qkvz` and `out_proj` of #43839 by a 32-point block Hadamard matrix, because plain MXFP4 there makes Qwen3.8-2.4T-A95B MXFP4 write **11% more tokens** than BF16 on thinking-on GSM8K. With the rotation, the answers are 2% to 5% longer than BF16, and the median TPOT is the same as with plain MXFP4 (+0.0% without MTP and +0.1% with NEXTN, geomean over 12 serving shapes, 8x MI355X, TP8).

The extra length repeats in every run. Against BF16, the per-question geomean of plain MXFP4 is 1.071 and 1.070 in our two runs, and 1.073 in [vllm#62750](https://github.com/vllm-project/vllm/pull/62750). With the rotation, it is 1.017, 1.021 and 1.022. The accuracy drop of plain MXFP4 does not always repeat. It is 0.9641 to 0.9597 in our first run (McNemar p = 0.0017) and 0.9630 to 0.9586 in vllm#62750 (p = 0.0027), but 0.9628 to 0.9626 in our second run (p = 0.94). With the rotation, no run shows an accuracy change against BF16 (p = 0.62 and 0.73 here, 0.79 over 8 reps and 0.057 over 12 reps in vLLM).

The extra tokens cost decode time. At the same TPOT, the rotation gives 5.4% and 7.8% fewer tokens per thinking answer than plain MXFP4 in our two runs.

The rotation needs [ROCm/aiter#6734](https://github.com/ROCm/aiter/pull/6734) (open), which adds `hadamard_rotate` to `per_1x32_f4_quant_hip`. This PR stays a draft until the SGLang AITER pin includes it.

The 32-point Hadamard matrix H is orthonormal, so (x H)(w H)^T = x w^T and the product does not change. The rotation spreads outliers across each 32-element MXFP4 block, so the shared E8M0 scale fits the block better. SGLang rotates the weight once at load. The AITER quant kernel rotates the activation in registers, so there is no extra kernel and no extra pass over the activation. vllm#62750 (merged) adds the same rotation to vLLM in PyTorch, and [vllm#63272](https://github.com/vllm-project/vllm/pull/63272) (draft) moves it into the same AITER quant.

## Modifications

- `environ.py` adds the boolean `SGLANG_ROCM_GDN_ONLINE_MXFP4_HADAMARD`, default true. It acts only on the projections that `SGLANG_ROCM_GDN_ONLINE_MXFP4` quantizes. `0` gives the plain MXFP4 of #43839.
- `quark_w4a4_mxfp4.py`:
  - `_block_hadamard32` multiplies each 32-wide block of the last dimension by `scipy.linalg.hadamard(32) / sqrt(32)`, in fp32. The AITER kernel uses the same matrix.
  - `AiterMxfp4OnlineLinearMethod(hadamard)` keeps the flag. `quantize_` rotates the BF16 weight once, before `dynamic_mxfp4_quant`, if the flag is set.
  - `apply()` passes `hadamard_rotate=True` to `per_1x32_f4_quant_hip` on both GEMM paths: the Triton preshuffled GEMM at 64 rows or less, and the ASM `gemm_a4w4` above that. With the flag off, it does not pass the argument, so `0` runs on any AITER.
- `qwen3_5.py` passes the variable to `AiterMxfp4OnlineLinearMethod`. The load log gives the number of rotated projections. On Qwen3.8 at TP8 it is `Online MXFP4 GDN in_proj_qkvz,out_proj: 138 projections, 138 with Hadamard-32`.
- `test_qwen35_gdn_online_mxfp4.py`:
  - `TestBlockHadamard32` needs no GPU. It checks that the rotation keeps the products under the BF16 default dtype of the model loader.
  - The gfx95x test also runs every shape and row count with the rotation, against a reference built from the rotated operands.
- `environment_variables.mdx` adds one row.

The change acts only where #43839 acts: gfx95x with `SGLANG_USE_AITER=1`, the `qwen3_5_text` and `qwen3_5_moe_text` model types, and BF16 GDN projections with N and K multiples of 256. With `SGLANG_ROCM_GDN_ONLINE_MXFP4_HADAMARD=0`, nothing changes from #43839.

## Accuracy Tests

Each run used one MI355X node:

- Run 2 uses `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261023`, which has the AITER of the current pin (`285579b621`). It adds #43839 at `24b5622d2e`, the quant files of [ROCm/aiter#6734](https://github.com/ROCm/aiter/pull/6734) at `72d86b515f`, and this PR at `b193a96d88`.
- Run 1 uses `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261016`. It adds #43839 at `2c6ceb33c0`, ROCm/aiter#6734 at `72d86b515f`, and the rotation without the fallback.

The later commits of this PR change how the load log counts the rotated projections and remove the AITER check. With an AITER that has `hadamard_rotate`, they do not change the computation. The later commits of ROCm/aiter#6734 add a gfx950 check, an AR + RMSNorm epilogue that this PR does not use, and tuned a4w4 GEMM rows for N = 4608, K = 8192. The runs here do not have these rows.

Thinking length, with the method of vllm#62750. Thinking-on GSM8K, 1319 test questions, zero-shot, `\boxed{}` prompt, temperature 1.0, top-p 0.95, top-k 20, at most 32768 tokens, 8 reps per arm, 256 concurrent requests, no MTP. The token count is `usage.completion_tokens`, which includes the thinking. The arms are paired by (rep, question). The mean ratio is total tokens over total tokens, the geomean is over the per-question ratios, and the brackets are 95% bootstrap intervals over questions.

Against plain MXFP4, the rotation gives a mean ratio of 0.946 [0.906, 0.990] in run 2 and 0.922 [0.888, 0.961] in run 1. One rep alone gives a mean ratio from 1.05 to 1.25 for plain MXFP4, so the 8-rep geomean is the steadier measure. No answer in run 2 reached the 32768-token limit. With the same method over 8 reps, vllm#62750 measured a mean ratio of 1.122 and a geomean of 1.073 for plain MXFP4, and 1.059 and 1.022 for Hadamard-32.

## Speed Tests and Profiling

Run 2 images, one node per mode, with the 12 serving shapes and the server flags of #43839. Median TPOT, geomean of the per-cell ratios over the 12 cells:

| Pair | No MTP | NEXTN |
| --- | ---: | ---: |
| MXFP4 + Hadamard-32 against plain MXFP4 | +0.0% | +0.1% |
| MXFP4 + Hadamard-32 against BF16 | -3.7% | -4.8% |
| Plain MXFP4 (#43839) against BF16 | -3.7% | -5.0% |

In run 1, Hadamard-32 against plain MXFP4 gave +0.2% without MTP over the same 12 cells. A second check in run 1 started the servers in the order plain, Hadamard, Hadamard, plain, at 8k / 1k and concurrency 1 to 64. It gave -0.2%, and two rounds of one server differed by up to 0.4%. The rotation has no measurable cost.
