## Motivation

<!-- Describe the purpose and goals of this pull request. -->

Kimi-k3 with DCP + DSpark enabled will crash in eager mode due to no extend_prefix_lens is filled for eager mode
```bash
File "sglang/srt/speculative/dspark_components/dspark_verify.py", line 305, in _forward_prepared_verify
  target_out = self.target_worker.forward_batch_generation(...)
File "sglang/srt/model_executor/model_runner.py", line 1840, in _forward_raw
  ret = self.eager_runner.execute(...)
File "sglang/srt/model_executor/runner/eager_runner.py", line 303, in _execute_extend
  model_runner.model.prepare_context_parallel_metadata_for_dcp(
File "sglang/srt/models/kimi_k3.py", line 3110, in prepare_context_parallel_metadata_for_dcp
  return prepare_decode_context_parallel_metadata(
File "sglang/srt/layers/dcp/planner.py", line 64, in prepare_decode_context_parallel_metadata
  extend_cu_prefix_lens[1:] = torch.cumsum(extend_prefix_lens, dim=0)

TypeError: cumsum(): argument 'input' (position 1) must be Tensor, not NoneType
```

Root cause comes from dcp + dspark path only. The following metadata will be skipped if is_target_verify in forward batch init.

```python
if (
    forward_batch.needs_forward_metadata_init()
    or cp_active
    or forward_batch.forward_mode.is_target_verify()     # <- this one
):
    if model_runner.ps.attn_dcp_size > 1 and hasattr(
        model_runner.model, "prepare_context_parallel_metadata_for_dcp"
    ):
        forward_batch.attn_dcp_metadata = (
            model_runner.model.prepare_context_parallel_metadata_for_dcp(
                forward_batch.seq_lens,
                forward_batch.extend_prefix_lens,          # <--------------------- None on target verify path
                forward_batch.extend_prefix_lens_cpu,      # <--------------------- None on target verify path
                forward_batch.extend_seq_lens,             # <--------------------- None on target verify path
                ...
```

In `ForwardBatch.init_new` the extend tensors are filled only in the `else` branch:

```python
if ret.forward_mode.is_decode() or ret.forward_mode.is_target_verify():
    if ret.positions is None:
        ret.positions = clamp_position(batch.seq_lens)
else:
    ...
    ret.extend_prefix_lens = torch.tensor(extend_prefix_lens, ...)
    ret.extend_prefix_lens_cpu = extend_prefix_lens
```
## How to reproduce it

This issue was found on AMD MI355X  and also can be reproduced on Nvidia GB300.

The two flags that matter are `--dcp-size > 1` and `--disable-cuda-graph`, on top
of any speculative algorithm that produces `TARGET_VERIFY`.

### Single node, Kimi-K3, 8×MI355X

```bash
# Single node, Kimi-K3, 8×MI355X
SGLANG_USE_AITER=1 SGLANG_AITER_K3_OPT=1 \
AITER_FLYDSL_FORCE=1 AITER_SITUV2_A8W4=1 \
SGLANG_EXPERIMENTAL_AITER_DCP_FP8=1 \
SGLANG_ENABLE_OVERLAP_PLAN_STREAM=0 \
python3 -m sglang.launch_server \
  --model-path moonshotai/Kimi-K3 --trust-remote-code \
  --tp-size 8 --dcp-size 8 \
  --decode-attention-backend aiter \
  --dtype bfloat16 \
  --kv-cache-dtype fp8_e4m3 \
  --page-size 32 \
  --max-running-requests 64 \
  --mem-fraction-static 0.78 \
  --chunked-prefill-size 4096 \
  --max-prefill-tokens 4096 \
  --context-length 5200 \
  --mamba-full-memory-ratio 0.57 \
  --reasoning-parser kimi_k3 \
  --tool-call-parser kimi_k3 \
  --speculative-algorithm DSPARK \
  --speculative-draft-model-path RadixArk/Kimi-K3-DSpark \
  --speculative-dspark-block-size 7 \
  --enable-linear-replayssm-spec \
  --host 127.0.0.1 --port 8100 \
  --disable-cuda-graph
```

- Phoenix3334 · comment · 2026-10-15T08:23:27Z · [source](https://github.com/sgl-project/sglang/pull/38991#issuecomment-6187771516)

Thanks for the fix! We validated a backport on 8×NVIDIA B300 with Kimi-K3, DCP8 + DSpark, using SGLang `e00930c5` from our v0.5.21 image.

With maximum captured batch size 96, `max-running-requests=112`, and client concurrency 112, the original build reproduced the `cumsum(extend_prefix_lens=None)` failure in eager target verification. With this PR's change backported to the same base, all **1,120 requests completed**, benchmark exit code was **0**, `num_failed=0`, and the `cumsum(None)` error did not recur.

This confirms crash resolution for our graph-to-eager fallback configuration; it was not a full `--disable-cuda-graph` run. Our separate normal-mode GSM8K graph/eager comparison did not reach readiness because of warmup HTTP self-request timeouts, so we are not claiming new B300 output-parity or accuracy results.

The matching crash is tracked in #34920, which is still open. We also posted the validation there: https://github.com/sgl-project/sglang/issues/34920#issuecomment-6187624314. Could the maintainers link this fix and consider closing that issue?
