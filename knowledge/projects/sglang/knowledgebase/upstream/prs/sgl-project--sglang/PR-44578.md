# [true-on-policy] Keep the logits dtype in speculative-decoding logprobs

[Upstream PR](https://github.com/sgl-project/sglang/pull/44578) · state: open · merged: False

## Original PR description

## Summary

`compute_spec_logprobs` (`layers/logprob_processor.py`) scales the gathered logits with `gathered_logits / temperatures`. `temperatures` is fp32, so this out-of-place division promotes bf16 logits to fp32. The sampler instead divides in place (`logits.div_(sampling_info.temperatures)`), which keeps the logits dtype.

Under a true-on-policy contract (`qwen3_dense_true_on_policy_v1`) the next-token logits are bf16. Accepted tokens' logprobs and top-k logprobs under speculative decoding were therefore computed in fp32. They differed from non-speculative decoding and from the trainer's bf16 `log_softmax`.

The fix casts the scaled logits back to the logits dtype, which matches the sampler. fp32 serving is unchanged.

This is the same class of bug as #44517, where the CUDA-graph logits buffer forced fp32. It was found while auditing every path that produces logprobs under the contract.

## Tests

- New CPU test `test/registered/unit/spec/test_spec_logprobs_dtype.py`. It compares `compute_spec_logprobs` with the sampler's in-place division and `log_softmax` at temperatures 0.7 and 0.6:
  - bf16 logits: the dtype, accepted-token logprobs and top-k values must be bitwise equal;
  - fp32 logits: the result must be unchanged.
- On `sglang-miles` `7b6993a31` without the fix, the bf16 case fails (`torch.float32 != torch.bfloat16`). With the fix, both cases pass.
