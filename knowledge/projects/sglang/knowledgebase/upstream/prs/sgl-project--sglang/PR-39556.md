# [Fix] dsv4 encoding: open the assistant turn after inline system messages

[Upstream PR](https://github.com/sgl-project/sglang/pull/39556) · state: closed · merged: False

## Original PR description

## Motivation

`render_message` emits the assistant turn token only when the message it renders is a `user` or `developer` turn. A message list that ends with an inline `system` block therefore reaches decoding with no assistant turn open, and one with an inline `system` block directly before an assistant turn loses that turn's marker:

```
[u, a, u]      <|user|>U1<|assistant|>...A1<|end_of_sentence|><|user|>U2<|assistant|>   ok
[u, s]         <|user|>U1S1                                                            no assistant turn
[u, s, a, u]   <|user|>U1S1A1<|end_of_sentence|><|user|>U2<|assistant|>                A1 has no <|assistant|>
```

This is the shape Anthropic's mid-conversation system beta produces: Claude Code ends every `/v1/messages` request with a `role: "system"` reminder, which the Anthropic adapter passes through at its original position. On a DeepSeek-V4 deployment such a request returns empty content (`content: []`, `stop_reason: end_turn`) while the same instruction placed in the leading `system` field answers normally. `/v1/chat/completions` behaves identically, so the defect is in the shared encoder rather than in the Anthropic adapter.

Related: #39518 extends inline-system pass-through to the `dsv41` native encoder, which is only generation-ready once the encoder opens the assistant turn for these messages.

The rule this change applies is not new to the family: the V4.1 encoder (`encoding_dsv41.py`, which exists only on the `dsv4.1` branch) already treats an inline system block as a generation point (`role == "system" and index > 0`). This change brings `encoding_dsv4` in line with it.

## Modifications

- `encoding_dsv4.render_message`: a message opens the assistant turn unless it is itself assistant content or the native `latest_reminder`. A `system` block renders as bare text with no turn token of its own, so it has to open the turn like a `user` turn does.
- The file is adapted from the DeepSeek-V4 reference implementation, so the deviation is marked with a `Local change:` note in the file header and above the changed branch, to survive a future re-sync from the reference.
- `test/registered/unit/entrypoints/openai/test_serving_chat.py`: regression test for a trailing system block and for a system block before an assistant turn.

## Accuracy Tests

The change only affects prompt assembly; no kernel, model forward, or sampling code is touched.

- The new test fails on the unmodified encoder (both assertions) and passes with the change.
- Rendered prompts were compared across 11 message shapes x 2 thinking modes. Only the four `system`-bearing shapes change — `[u,s]`, `[u,s,a,u]`, `[u,s,a,u,s]`, `[u,s,r]`; `[u]`, `[s,u]`, `[u,a,u]`, `[u,a]` (prefill), `[u,r]`, `[u,r,a,u]`, `[u,s,u]` and the `task=` path render byte-identically.
- The committed test also passes on real hardware: `1 passed` on a 4x GB300 box, run from this branch's checkout.
- A Claude Code smoke (3 text turns + 1 tool round trip) against DeepSeek-V4.1-Flash served on that box passes 4/4 turns. That server ran the `dsv41` encoder, so the run exercises the rule rather than the patched `encoding_dsv4` code path.
- No model-weights run against the patched `encoding_dsv4` itself was made; forcing the `dsv4` spec for that checkpoint aborts at startup (`texts cannot be empty and tokenizer must be initialized`).

## Speed Tests and Profiling

Not applicable: string assembly only, with no change to kernels, memory, or scheduling.
