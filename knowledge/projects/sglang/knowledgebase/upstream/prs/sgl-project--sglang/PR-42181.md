# [Perf] Scale fp8 KV writes once: drop triton's K/V clones and the wrappers' unit scale

[Upstream PR](https://github.com/sgl-project/sglang/pull/42181) · state: closed · merged: False

## Original PR description

## Motivation

On an fp8 KV cache, `MHATokenToKVPool.set_kv_buffer` divides `cache_k` / `cache_v` by the KV scales **in place**. Two callers pay for that contract when they don't need to:

1. **`TritonAttnBackend.forward_extend`** reads `k` / `v` again in the attention kernel after the KV write, so on the scaled path it clones both before the write (`k.clone(),  # cloned to protect k,v from in-place mutation in set_kv_buffer`). The MLA sub-branch does the same with `k.clone().div_(layer.k_scale)`. As a result, every scaled prefill write runs a full extra copy of K and V.
2. **`HybridLinearKVPool`, `SWAKVPool` and `UnifiedSWAKVPool`** default `k_scale` / `v_scale` to `1.0` in `set_kv_buffer`, while `MHATokenToKVPool` defaults them to `None`. When a caller writes without a scale (QSA, MiniMax-M3's sparse layers through `MiniMaxSparseKVPool`, or triton on an unquantized model), the wrapper substitutes `1.0` and the MHA pool runs a full `div_(1.0)` over K and V. That is a pass over HBM that changes nothing.

This PR removes both. The bytes written to the KV cache are unchanged.

Making the pool itself out of place (`cache_k = cache_k / k_scale`) looks like the obvious fix but measures worse, so it is not what this PR does:
- Every caller that never needed protection would pay a new allocation, and that includes every triton decode step.
- `AiterAttnBackend` hands the pool a shape-`[1]` fp32 unit scale. With that scale, an out-of-place divide promotes bf16 to fp32 (a 0-dim scale would not).
- Measured on the micro below, that variant is −3.6 % (median) on the unprotected callers and −9.7 % (down to −33 %) on the aiter path.

## Modifications

- `triton_backend.py`, `forward_extend`: on the scaled MHA path, divide out of place (`k / layer.k_scale`, `v / layer.v_scale`) and pass the pool no scale. On the MLA sub-branch, `k / layer.k_scale` replaces `k.clone().div_(...)`. In both cases one divide replaces clone + divide. `layer.k_scale` is the 0-dim fp32 parameter `BaseKVCacheMethod` creates, so the result stays bf16 and is bit-identical to the pool's in-place divide.
- `HybridLinearKVPool.set_kv_buffer`, `SWAKVPool.set_kv_buffer`, `UnifiedSWAKVPool.set_kv_buffer`: change the `k_scale` / `v_scale` defaults from `1.0` to `None`.
  - Every pool these wrappers forward to treats `None` as "no divide": `MHATokenToKVPool`, `MHATokenToKVPoolFP4`, `PageInterleaveMHATokenToKVPool` and the NPU pool all guard with `if k_scale is not None`.
  - `MHATokenToKVPoolMXFP8` treats `None` as its fused quant-store signal. Its only caller passes the scales explicitly (`flashattention_backend`), so the default never reached it.
  - Callers that pass a scale explicitly are unaffected.
- New CPU unit test, `test/registered/unit/mem_cache/test_kv_write_scale_contract.py`.

`MHATokenToKVPool.set_kv_buffer`'s own semantics are untouched. #31652 (fused fp8 store, CUDA) and #40785 (fused prefix-valid commit) do not overlap this diff textually.

## Accuracy Tests

The values written to the KV cache are bit-identical:
- In the micro below, the sha1 of the fp8 bytes written into the pool matches `main` at every shape, token count and path.
- The unit test asserts the pool receives exactly `k.clone().div_(layer.k_scale)`, same dtype and same values.

No model-level accuracy run yet (see below).

## Speed Tests and Profiling

MI355X (gfx950), ROCm image with torch 2.11.0+rocm10.0.0. Measured on `main@ef867fa40d`; none of the touched files or `kv_cache.py` / `radix_attention.py` has changed between that commit and this branch's base.

The micro times the real `TritonAttnBackend.forward_extend` KV-save block and the real `MHATokenToKVPool.set_kv_buffer` on an `fp8_e4m3` pool, with K/V given as contiguous views of one fused QKV buffer. Run design:
- Shapes are kv_heads × head_dim × q_heads: 2×256×16 (Qwen3-Next / Qwen3.5), 4×128×64 (MiniMax-M3) and 8×128×48 (MiniMax-M2.7).
- Token counts are 37 / 509 / 2053 / 6151 / 30727.
- Each arm (base, this PR, and the pool-out-of-place alternative) is one consecutive block of 4 runs. Run 1 is discarded and runs 2–4 are medianed.
- Timing is device time: one call captured in a CUDA graph and replayed.

Median over the 15 shape × token points, with the range in brackets; positive means faster:

| path | who takes it | this PR | pool out-of-place (rejected) |
|---|---|---|---|
| scaled triton extend write | `--attention-backend triton` + fp8 KV + quantized attention | **+36.4 %** [+9.5, +41.4] | +35.6 % |
| same, behind `HybridLinearKVPool` | Qwen3-Next / Qwen3.5 / Qwen3.8 on triton | **+36.9 %** [+9.8, +40.9] | +36.0 % |
| unscaled write through a wrapper | QSA (Qwen3.8-Flash-Next), MiniMax-M3 sparse layers, unquantized hybrids on triton | **+53.4 %** [+42.1, +72.9] | −0.6 % |
| pool write with a 0-dim scale, no caller clone | triton decode, FA / flashinfer / hpc / xpu | −0.1 % [−0.6, +1.9] | −3.6 % [−10.7, −0.7] |
| pool write with aiter's `[1]` unit scale | aiter's non-fused branch (SWA pools) | 0.0 % | −9.7 % [−33.1, +1.7] |

**Which models reach it.** Probed with `--kv-cache-dtype fp8_e4m3`, truncated dummy-weight checkpoints, under both the ROCm default backend and `--attention-backend triton`. FP8 KV is opt-in for all of these.

| model | ROCm default backend | `--attention-backend triton` |
|---|---|---|
| Qwen3-Next-80B-FP8, Qwen3.5-397B-MXFP4, Qwen3.8-2.4T-MXFP4, MiniMax-M2.7 | aiter fused write, not reached | scaled extend write (full-attention layers) |
| MiniMax-M3-MXFP4 (text-only config) | default is triton: scaled extend write on dense layers, wrapper unscaled write on sparse layers | same |
| Qwen3.8-Flash-Next-FP8 | QSA: wrapper unscaled write | same |
| Qwen3.6-35B-A3B (bf16 weights) | aiter fused, not reached | wrapper unscaled write |
| Llama-3.1-8B, Qwen3-14B-FP8 (controls) | aiter fused | `scale=None`, not reached |
| DeepSeek-V4, GLM-5.3, Kimi-K3, Kimi-Linear, gpt-oss | 0 hits (own MLA/DSA pools, or the model fuses its KV write) | 0 hits |

**Not done yet (why this is a draft):** an end-to-end serving A/B and a GSM8K A/B with a base-repeat control. The planned runs are Qwen3.8-Flash-Next-FP8 on the default backend for the wrapper path, and Qwen3-Next-80B-FP8 with `--attention-backend triton --kv-cache-dtype fp8_e4m3` for the extend path. The micro numbers above are per KV write; the end-to-end share depends on how much of a step those writes take.
