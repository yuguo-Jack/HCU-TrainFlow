# [Fix] dLLM: Retract dLLM manager requests on pause

[Upstream PR](https://github.com/sgl-project/sglang/pull/45227) · state: open · merged: False

## Original PR description

## Motivation

Pausing a dLLM server with `/pause_generation` in `retract` mode kills the scheduler. The pause puts the last dLLM batch back in the waiting queue, but dLLM requests also stay in the dLLM manager's own queues between blocks. The next fetch then finds them twice and raises `Redundant requests detected in dLLM requests.` Requests that were waiting between blocks are not retracted at all, so they keep KV computed with the old weights, which defeats the purpose of a retracting pause during weight updates.

To reproduce, serve `inclusionAI/LLaDA2.0-mini` with `--dllm-algorithm LowConfidence`, send two long requests, call `/pause_generation` with `{"mode": "retract"}` while they decode, then `/continue_generation`. Both requests fail with a dropped connection and the server exits.

## Modifications

- `pause_generation` takes every request out of the dLLM manager once. Requests that hold KV are retracted with the rest, and requests without KV get the same state reset. All of them return to the waiting queue exactly once.
- `reset_for_retract` resets the dLLM state of a request. It drops any unresolved first-done-first-out block and algorithm state and sets the phase the request would get as a new incoming request. The KV it referred to is gone, so the request rebuilds it from its prompt and committed outputs.
- `DllmManager.pop_all_reqs` empties both manager queues.

## Accuracy Tests

With the patch, the reproduction above passes. Both requests resume after `/continue_generation` and finish all 512 tokens. The server stays healthy, and the idle KV leak check stays clean. Compared with the same two requests sent without a pause, one output is byte identical and the other diverges partway through, as expected when retraction recomputes the KV. Other lifecycle checks (over-length rejection, aborts, KV pressure, prefix cache hits) behave the same with and without the patch. There is no performance effect, because the change runs only inside a retract-mode pause with a dLLM model.

`test_retract_takes_dllm_requests_out_of_the_dllm_manager` fails before the change, because the request waiting between blocks is not retracted, and passes after it. Code is formatted with pre-commit.
