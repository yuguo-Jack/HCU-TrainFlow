# [Perf] [AMD] qwen3_5: fuse SiLU-and-mul with the down_proj MXFP4 input quantization (bit-exact)

[Upstream PR](https://github.com/sgl-project/sglang/pull/47155) · state: closed · merged: False

## Original PR description

> **Stacked on #39912.** The branch contains #39912's three commits (a5985825b5, e69dd25fcf, 65a73b0960). This PR's own change is the last commit only: 9ca029652b, 4 files, +340. To review just that, open the commit view for 9ca029652b, or run `git diff 65a73b0960 9ca029652b`. I will rebase this branch whenever #39912 changes.
>
> **Runtime dependency:** an AITER whose `act_mul_and_mxfp4_quant` supports `scaling_mode="roundup"` and `round_to_input_dtype` (ROCm/aiter#7116). The fusion is gated on that signature; with an older AITER it stays off and nothing changes.

## Motivation

On MI355X (gfx950), Quark W4A4 MXFP4 Qwen3.5/3.8 dense checkpoints can run `down_proj` on the AITER ASM FP4 GEMM (`SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM=1`). The dense MLP then does three things: SiluAndMul writes a bf16 activation, `per_1x32_f4_quant_hip(shuffle=True)` reads it back to make the FP4 input, and the GEMM consumes that input. AITER already has a fused `act_mul_and_mxfp4_quant`, but by default it quantizes the fp32 `silu(gate) * up` with even-rounded scales. That is valid MXFP4, but it is not the input the unfused path produces (about 98.2-99.5% of fp4 bytes match), and on Qwen3.8-27B at TP2 that difference was enough to move GSM8K. This PR fuses the two kernels without changing a single bit of the GEMM input.

## Modifications

- `Qwen2MoeMLP._silu_mxfp4_quant_fused` calls `act_mul_and_mxfp4_quant(gate_up, "silu", scaling_mode="roundup", shuffle=True, round_to_input_dtype=True)`:
  - `round_to_input_dtype` makes the kernel quantize `bf16(bf16(silu(gate)) * up)`, which is the tensor SiluAndMul writes;
  - `"roundup"` uses `per_1x32_f4_quant`'s E8M0 scale.
  - The result goes to `down_proj` as `_AsmShuffledMxfp4Input` (from #39912), and `down_proj` validates it before calling `gemm_a4w4`.
- `Qwen2MoeMLP.forward` takes the fused path only for 2-D, non-empty batches when `down_proj.use_aiter_asm_fp4_gemm` is set (decided after weight loading). Every other case keeps SiluAndMul followed by the normal quant.
- `_maybe_enable_silu_mxfp4_quant_fusion` (qwen3_5) turns it on for dense MLPs on ROCm only when both `gate_up_proj` and `down_proj` use `QuarkW4A4MXFP4`, and the installed AITER kernel accepts `round_to_input_dtype`. If the AITER kernel cannot reproduce the unfused bytes, the fusion stays off.
- No new env var or kill switch: the GEMM input is bit-identical.

## Setup

MI355X (gfx950), Qwen3.8-27B MXFP4 (`amd/Qwen3.8-27B-Quark-AWQ-MXFP4`), `SGLANG_ROCM_USE_AITER_FP4_ASM_GEMM=1`. SGLang TP1 with `--attention-backend aiter`, FP8 KV cache, `--enable-amd-monokernel`, chunked prefill 16384, or TP2 with INT4 quick reduce. "With vs without" = the full optimized stack vs the same build without this PR, on the same GPU, averaged over 2 GPUs. Decode = bench_serving random, 8,192 input / 1,024 output tokens; prefill = 1 request at a time, 1 output token. Repeat noise of the full stack on one GPU: TTFT 0.1-0.8%; TPOT 0.1-0.8%, except 2.4% at 16 concurrent requests on one GPU.

## Accuracy

- The fp4 codes and E8M0 scales (valid rows) equal SiluAndMul + `per_1x32_f4_quant_hip(shuffle=True)` byte for byte. Result: identical in every case of `test_silu_and_mul_mxfp4_quant.py` (32 passed, MI355X).
- Qwen3.8-27B MXFP4 on MI355X, this PR + #47154 + ROCm/aiter#7116:
  - TP1: GSM8K-200 0.930, 0.945 and 0.940; needle in a haystack (100k/131k/200k tokens x 5 depths x 2 passes) 30/30; a chat answer is correct.
  - TP2: GSM8K-200 0.935, 0.950, 0.940 and 0.950; all 1,319 questions 0.923; needle 30/30.
  - No run had an empty answer.

  With the earlier, inexact producers enabled at TP2, GSM8K-200 was 0.880-0.900 with 7-12 empty answers.

## Speed

TP1, with vs without this PR:

- time to first token at 100k / 131k / 200k tokens: 3.049 → 3.001 s (-1.8%), 4.266 → 4.185 s (-1.9%), 7.633 → 7.517 s (-1.7%);
- median time per output token (8k / 1k): 8.26 → 8.00 ms (-3.1%) at 16 concurrent requests, 19.15 → 18.75 ms (-2.1%) at 64, 57.46 → 56.83 ms (-1.1%) at 256.

## Tests

- `test/registered/kernels/ops/activation/test_silu_and_mul_mxfp4_quant.py` (gfx950, AMD CI stage-b mi35x). Byte equality of the fused path against SiluAndMul + `per_1x32_f4_quant_hip(shuffle=True)`:
  - M in {1, 7, 8, 9, 64, 255, 256, 257, 870, 2048, 4377, 6553, 16384} x intermediate size in {8704, 17408};
  - edge blocks: all-zero, below the amax floor, large;
  - a check that no scale is NaN (0xFF), and that the output passes the ASM GEMM's prequantized-input validation.
  - Result: 32 passed (MI355X).
- `test/registered/unit/models/test_qwen3_5_silu_mxfp4_quant.py` (CPU, AITER faked):
  - enable conditions: ROCm, both projections MXFP4, AITER importable, `round_to_input_dtype` supported;
  - the exact kernel arguments and output dtypes and shapes;
  - forward routing: fusion off, non-ASM `down_proj`, empty batch and 3-D input all fall back.
  - Result: 5 passed.
