## Motivation

Enable adaptive verification for DFlash on GDN models, using the existing DSpark planner. An online acceptance estimator supplies confidence for DFlash drafts without a confidence head; compact verification reduces target work as serving load rises.

This upstreams the integration tested in https://github.com/jianc99/sglang/pull/8, including its seven component changes. The implementation and original measurements are by Jian Chen and Zihan Zhang (@SubSir). This submission was prepared with AI assistance.

## Modifications

- Add online acceptance estimation and connect DFlash to DSpark budget selection, ragged packing, compact graphs, and cutoff acceptance.
- Support packed GDN verification and compact ReplaySSM state commits for DFlash/DSpark.
- Optimize convolution window stores and target-probability top-k selection.
- Add regression coverage for estimator behavior, acceptance cutoffs, ragged verification, GDN commits, convolution updates, and positions.

Enable with `SGLANG_RAGGED_VERIFY_MODE=compact`, `--enable-linear-replayssm-spec`, and `--speculative-dspark-sps-table-path <table>`. Use the existing offline `sglang.benchmark.dspark_sps_profiler` to produce the cost table. Full launch/profiling settings and per-component diffs are in the [source integration](https://github.com/jianc99/sglang/pull/8).

Related work: #38897 (ragged GDN/varlen convolution), #42688 (ReplaySSM masking), #41916 (target probabilities), #44866 (online estimator), #42711 and #42717 (planner fixes). This PR combines these areas into the DFlash compact-verification path; reviewers may prefer to land independent components first.

## Accuracy Tests

Previously reported on the source integration on GB300 (not rerun after updating to current upstream):

- 345 unit/kernel tests passed for DFlash, DSpark, speculative decoding, and the estimator; 455 passed for convolution, ReplaySSM, and Mamba. Two `test_gdn_replayssm_spec_fold` cases also fail on the source base.
- ReplaySSM circular/direct commit memcheck: 7 tests, 133 subtests, no device-side errors.
- Greedy output parity was checked against autoregressive decoding. Near-tie floating-point differences remain; outputs are not universally token-identical. Detailed parity results and limitations are in the source integration.

Current upstream integration: `git diff --check` and all applicable pre-commit hooks passed on the 38 changed files (including ruff, formatting, AST checks, and CI test registration). GPU runtime tests still need CI; this submission was prepared on a Mac without CUDA.

## Speed Tests and Profiling

Existing source-integration measurements: Qwen3.8-27B, DFlash 2 block size 8, four GB300 GPUs (TP4), SPEED-Bench first turns, temperature 1. Decode throughput below is concurrency times per-request decode rate after the first token.

| Concurrency | Autoregressive tok/s | Adaptive DFlash tok/s | Speedup |
| --- | ---: | ---: | ---: |
| 1 | 247 | 649 | 2.63x |
| 64 | 9,266 | 13,465 | 1.45x |
| 128 | 13,219 | 16,792 | 1.27x |
| 256 | 18,810 | 21,020 | 1.12x |
| 512 | 22,858 | 22,424 | 0.98x |

The high-concurrency rows use `--stream-interval 4`, a request cap of 528, and graphs/cost profiling through batch 512. Baseline/high-concurrency cells are single runs; this is not a guarantee of no regression. The source PR also separates gains from system optimizations versus adaptive verification alone.

Known limitation: compact graph selection can be slower than static full-block verification at lower concurrency. Full-block routing to batch-size-keyed graphs is left for follow-up. Benchmarks have not been rerun on this updated upstream base.
