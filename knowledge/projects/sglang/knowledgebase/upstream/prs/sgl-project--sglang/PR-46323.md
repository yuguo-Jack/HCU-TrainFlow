# [Perf] [AMD] deterministic: Faster Triton MoE config above 64 tokens on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/46323) · state: open · merged: False

## Original PR description

## Motivation

In deterministic mode every unquantized Triton MoE call runs with one fixed config (`BLOCK_SIZE_M/N/K` 64/64/32, `GROUP_SIZE_M` 8), whatever the number of tokens, because the tuned per-M configs would make a token's result depend on its batch. On MI350X that config is slow for prefill: on Qwen3-30B-A3B the MoE is the largest cost in deterministic mode. This PR uses a faster config (128/128/64, `GROUP_SIZE_M` 1, 4 warps, 2 stages) above 64 tokens and keeps the current one below. The two configs give the same bits for every token, so the switch keeps deterministic mode batch-invariant, and outputs do not change. On MI350X, deterministic Qwen3-30B-A3B throughput is 8-12% higher (1k-32k input) with every determinism check passing, and DeepSeek-V2-Lite 6-9% higher. Only unquantized MoE on gfx950 changes.

## Modifications

- `fused_moe_triton_config.py`: deterministic mode's config moves into `_deterministic_config(M, dtype, is_marlin, block_shape)`. On gfx950, for unquantized MoE (`dtype is None`, no block shape, not Marlin), it returns `_DETERMINISTIC_CONFIG_GFX950_LARGE_M` above 64 tokens; everything else keeps `_DETERMINISTIC_CONFIG` (the current config).
- New CPU test `test/registered/unit/layers/moe/test_deterministic_moe_config.py`: the switch, the cases that keep one config (quantized dtypes, block-scaled, Marlin, other GPUs), and that callers get a copy.
- New gfx950 test `test/registered/amd/test_deterministic_moe_config_gfx950.py` (`stage-b-test-1-gpu-small-amd-mi35x`): on three MoE shapes, bf16 and fp16, the two configs give bitwise identical outputs for 1,024 tokens, and rows of that batch equal the same rows computed on their own or in batches of 7-64 tokens with the small-M config.
- Unchanged: normal mode, NVIDIA, gfx942, quantized MoE.

## Accuracy Tests

MI350X, ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`, deterministic mode (`--enable-deterministic-inference`, Triton prefill and AITER decode attention, together with the other open MI350X deterministic-mode PRs).

Kernel level (Qwen3-30B-A3B shape: 128 experts, top-8, hidden 2048, intermediate 768; DeepSeek-V2-Lite shape: 64 experts, top-6, hidden 2048, intermediate 1408; bf16): all 288 fixed configs in the sweep (BLOCK_M 16-128, BLOCK_N/K 32-128, GROUP 1/8, 4/8 warps, 1/2 stages) give results bitwise identical to the current config, and every row of a 16k-token batch equals the same row computed alone or in smaller batches. Against a float32 PyTorch reference, the current and the new config have the same error (cosine similarity 0.999991, max abs diff 0.0065 / 0.0095 at 64 / 4,096 tokens).

End to end, Qwen3-30B-A3B TP1, `python3 -m sglang.test.test_deterministic` (`single`, `prefix`, `prefix --return-logprob`, `radix_cache`, 50 trials) plus a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response; the batches cross the 64-token switch): `single` 1 output, `prefix` 1/1/1/1, prefix logprobs identical, radix cache consistent, bitwise 1,275 / 1,275. GSM8K (sgl-eval 0.1.2, temperature 0, 1,319 questions): 95.00%, unchanged (with this branch). Both new tests pass on MI350X (`9 passed`, including 6 subtests).

## Speed Tests and Profiling

Kernel time per MoE call (bf16, MI350X), new config vs current, by number of tokens:

| tokens | 1 | 4 | 16 | 64 | 256 | 1,024 | 4,096 | 16,384 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Qwen3-30B-A3B shape | 0.93x | 1.03x | 1.07x | 1.01x | 1.05x | 1.24x | 1.67x | 1.83x |
| DeepSeek-V2-Lite shape | 0.94x | 1.07x | 1.04x | 1.03x | 1.11x | 1.38x | 1.69x | 1.91x |

(speed-up, higher is better; up to 64 tokens the PR keeps the current config, so those sizes are unchanged.)

End to end, deterministic mode, `python3 -m sglang.benchmark.serving --backend sglang --dataset-name random --random-range-ratio 1.0 --request-rate inf`, output throughput, main vs this PR (same server arguments, interleaved):

| model, TP | workload | main | this PR | change |
| --- | --- | --- | --- | --- |
| Qwen3-30B-A3B, 1 | 1k in / 1k out, 256 prompts | 7,452 tok/s | 8,104 tok/s | +8.7% (TTFT -27%) |
| Qwen3-30B-A3B, 1 | 8k in / 1k out, 256 prompts | 2,138 tok/s | 2,381 tok/s | +11.4% (TTFT -22%) |
| Qwen3-30B-A3B, 1 | 32k in / 256 out, 64 prompts | 172.0 tok/s | 193.3 tok/s | +12.4% (TTFT -14%) |
| Qwen3-30B-A3B, 1 | 1k in / 256 out, concurrency 1 | 163.7 tok/s | 164.3 tok/s | +0.4% |
| Qwen3-30B-A3B, 1 | 1k in / 256 out, concurrency 16 | 1,278 tok/s | 1,310 tok/s | +2.4% (TTFT -24%) |

(1k row: mean of two rounds, which agree within 0.3%; other rows one round.) The same config above 64 tokens, applied through a local switch, also gave on DeepSeek-V2-Lite TP1 +8.9% at 1k in / 1k out and +6.0% at 8k in / 1k out, and on Qwen3-30B-A3B TP1 at 64k / 120k input (YaRN) +7.7% / +5.5%. Normal mode is unchanged.
