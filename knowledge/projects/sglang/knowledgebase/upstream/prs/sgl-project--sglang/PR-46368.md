# fix(gemma4): index streamed tool calls by response order, not tool po…

[Upstream PR](https://github.com/sgl-project/sglang/pull/46368) · state: open · merged: False

## Original PR description

## What

`Gemma4Detector.parse_streaming_increment` stamped each streamed `ToolCallItem` with the tool's position in the request `tools` array. `serving_chat` emits that value as the OpenAI streaming delta `index`, which identifies a tool call by its order in the response. The base streaming parser uses its call sequence counter for this; the gemma4 detector did not.

Two observable failures:

- A single call to a tool declared second streams with `index: 1` instead of `0` (`<|tool_call>call:g{...}<tool_call|>` with tools `[f, g]`).
- Calls to `g` then `f` stream with indices `1` then `0`, so clients associate each argument delta with the wrong call.

## Fix

Use the detector's call sequence counter (`current_tool_id`, already incremented per call) for both the name chunk and the arguments chunk, matching the base streaming parser. One-shot (`detect_and_parse`) indexing is unchanged - the non-streaming path re-indexes by enumeration and only uses the value for tool-call IDs.

## Tests

Added `test/registered/unit/function_call/test_gemma4_streaming_index.py`: two calls in one increment stream indices `(g, 0), (None, 0), (f, 1), (None, 1)`, and a single call to a later-declared tool streams index `0`. Both fail on main (indices `1`/`0` swapped) and pass with the change.

Note: this touches the same detector as #46367 (different concern). Whichever lands second can be rebased.
