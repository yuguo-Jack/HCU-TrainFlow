## Original PR description

# [Spec] QSA: let the pending index-K ring hold more than one compression group

### Problem

Qwen4-Exp's QSA path refuses any speculative window wider than its compression
ratio:

```
NotImplementedError: Qwen QSA requires speculative_num_draft_tokens <= the QSA
compress ratio (4): the pending index-key ring holds one group; got 7
```

raised from `_require_chain_speculation`
(`python/sglang/srt/layers/attention/qwen_sparse_attn_backend.py:228-243`).

The reason is in the ring's addressing, not in the model. Pre-compression index-K
state is a per-request ring sized to exactly one group
(`python/sglang/srt/mem_cache/qsa_kv_pool.py:134`:

```python
ring_slots = self.qsa_num_request_slots * self.qsa_compress_ratio
```

) and addressed as `req_pool_idx * ratio + position % ratio`
(`layers/attention/qsa/metadata.py:237`, and again at `:262`). Because the offset
is `position % ratio`, a window wider than `ratio` maps two live positions onto
one slot and they overwrite each other within a single forward. The guard is
therefore correct for the layout it was written against — the layout is just
narrower than it needs to be.

### This is an implementation limit, not a property of the model

Two independent observations:

1. **vLLM serves a 7-wide verify window on this same target.** The DeepSpec
   checkpoint card for `dflash_block7_qwen38_flash_next` reports a *served*
   accepted length of **2.9837 at its native block 7** (and 2.7562 at block 4)
   against Qwen3.8-Flash-Next, i.e. Qwen4-Exp with the same QSA geometry.
2. **Nothing in the ring's arithmetic requires one group.** The slot is a pure
   function of `(request, position)`; the group count is a capacity choice, and
   the kernel that consumes the ring treats the slot tensor as an opaque index.

### What vLLM does differently

| | SGLang | vLLM |
|---|---|---|
| Window cap | `draft_tokens <= compress_ratio`, hard raise (`qwen_sparse_attn_backend.py:236`) | no equivalent cap found in the DFlash speculator path |
| Draft layout | 1+N, `hidden_states.view(bs, block_size, -1)[:, 1:, :]` (`dflash_worker_v2.py:158-160`) | 1+N, but switchable — see below |
| Official DeepSpec checkpoint | cannot be served at its native block size | served, per the card's own numbers |

The upstream serving repo carries a small patch set; the one that matters here is
`serving/patches/02-dflash-speculator-anchor-layout.diff`, whose entire content is
a four-line change that stops raising on `sample_from_anchor` and sets
`num_query_per_req = num_speculative_steps`
(`vllm/v1/worker/gpu/spec_decode/dflash/speculator.py`). Note this patch addresses
the *layout* question, not the window width — vLLM needed no change to serve a
wider window, which is the point.

> **Careful with the comparison.** The card's 2.98 is measured *with* that patch
> applied, and our 1.06 is measured without any layout fix, so the two numbers
> differ in two variables at once (window width **and** layout). I am not
> claiming this PR closes that gap. See "Scope" below.

### Measured on our side

Qwen3.8-Flash-Next, 8xA800 (SM80), main + the Qwen4-Exp capture guard, official
DeepSpec drafter, `--speculative-num-draft-tokens 4` (the current maximum):

| concurrency | requests | failures | accept length |
|---|---|---|---|
| 8 | 300 | 0 | 1.0621 |
| 24 | 300 | 0 | 1.0643 |
| 48 | 300 | 0 | 1.0629 |

Per-position, 47,411 verify steps: `P(>=1) = 0.0497`, `P(>=2) = 0.0051`,
`P(>=3) = 0.0018`. 95.0% of verify steps accept zero draft tokens.

### The change

Parameterize the ring by a group count `N`, derived once as
`ceil(max_num_draft_tokens / compress_ratio)` so it is transparent to users — no
new CLI flag. A request then owns `ratio * N` slots and position `p` lands in
group `(p // ratio) % N` at offset `p % ratio`. At `N == 1` the group term
vanishes and the arithmetic reduces to the current formula exactly.

| Site | Change |
|---|---|
| `mem_cache/qsa_kv_pool.py` | new `pending_ring_num_groups()` derivation; `qsa_num_groups` ctor arg; `ring_slots` scaled by it; **PD transfer item length scaled by it** (see below) |
| `layers/attention/qsa/metadata.py` | new `pending_ring_slot()` helper as the single formula; both ring builders take `num_groups` |
| `layers/attention/qwen_sparse_attn_backend.py` | guard window `ratio` -> `ratio * N`; `num_groups` threaded through the four builder calls |
| `layers/attention/qsa/graph_metadata.py` | the CUDA-graph metadata kernel has its **own** copy of the slot arithmetic — parameterized with a `NUM_GROUPS` constexpr |
| `layers/attention/qsa/qsa_indexer.py` | the two thin builder wrappers thread `num_groups` |
| `mem_cache/kv_cache_configurator.py` | computes `N` at pool construction (same `max_speculative_num_draft_tokens()` precedent the DSA branch already uses) |

Three things worth flagging for review — each is a place where the obvious patch
is wrong in a way that produces no error:

- **The graph-metadata kernel is the easy one to miss.** `_qsa_graph_row_metadata_kernel`
  (`graph_metadata.py:134-139`) writes the ring slots directly from Triton rather
  than calling the Python builders, so a patch that only touches `metadata.py`
  passes every `N == 1` test and silently corrupts index-K on the decode path at
  `N > 1`. It fails with wrong results, not an exception.
- **The PD transfer item length has to move with the ring.**
  `get_qsa_pending_state_buf_infos` sizes a transfer item as
  `tensor[0].nbytes * compress_ratio` — one *group* — and the peer indexes it by
  `req_pool_idx` (`disaggregation/mooncake/conn.py:770`, `src + index * item_len`).
  Once a request's ring is `ratio * N` rows, an item that covers one group reads a
  *different request's* rows for every `req_pool_idx > 0`. Both sides derive the
  length the same way, so nothing raises — the decode side just receives the wrong
  keys. The item must be one request's whole ring
  (`compress_ratio * num_groups` rows). Note `get_qsa_compressed_state_buf_infos`
  shares that helper but passes `qsa_compressed_page_size`, which is
  compression-derived and correctly unchanged.
- **The extend dump stays where it is.** `build_pending_ring_slots` sends
  pre-pending extend tokens to rows `[0, ratio)` on purpose — request slot 0 is
  never allocated, so that range is inert. It remains disjoint from every
  allocated request at any `N` (allocated requests start at `ratio * N`), so the
  branch is unchanged.

### Tests

`test/registered/unit/layers/attention/test_qsa_ring_slots.py` (CPU-only):

- **`N == 1` regression oracle** — both builders are compared against the previous
  formula, position by position, including negative and clamped positions.
- **Collision freedom** — a window of exactly `ratio * N` positions maps
  injectively for `N` in {1, 2, 4}; `ratio * N + 1` positions is asserted to
  collide, pinning the documented limit.
- **Cross-request isolation** — request `r` stays inside `[r * ratio * N, (r+1) * ratio * N)`.
- **Group-boundary neighbours** — `k * ratio +/- 1` land in adjacent groups.
- **Group members share one ring group** — holds even when `group_end` is not
  `ratio`-aligned, which the graph producer does feed (`lengths - 1`). This is why
  the group index is derived from `group_end` rather than from each member's own
  position.
- **Extend dump disjointness** at every `N`.

### End-to-end verification (SM80, 8xA800, 2026-09-18)

Real hardware, Qwen3.8-Flash-Next, TP8, decode CUDA graphs on.

**N=1 regression — the default path is unchanged in situ.** Same config, same draft, two trees:

| tree | accept length @ 4-token window |
|---|---|
| main + #38642, no QSA change | 1.1385 |
| + this patch | 1.1401 |

0.0016 apart, inside this rig's run-to-run spread (~0.002 at fixed config). So the N=1
arithmetic is a no-op on hardware, not only in the unit tests.

**N=2 — the window actually opens.**

| | result |
|---|---|
| unpatched, MTP (NEXTN3), `--speculative-num-draft-tokens 8` | `NotImplementedError: ... the pending index-key ring holds one group; got 8` |
| patched, same config | server up, 3/3 smoke, 300 requests, **accept length 3.6800** |

Up from the 4-token MTP baseline on this model — **2.81** single-node at the same window (our
own measurement; the matrix's earlier single-node entry for this cell was 3.35, PD 3.00 / 2.83)
— and the tail is fat (`P(>=7) = 0.1378`): the extra width is being used, not merely permitted.

**A real checkpoint this unblocks.** DSpark requires `num_draft_tokens = gamma + 1 = 5` at
`gamma = 4`, which the one-group ring rejects:

| | DSpark @ 5-token window |
|---|---|
| unpatched | blocked by the same `NotImplementedError` |
| patched | serves; 300 requests, accept length 1.0488 |

Be precise about what that last row shows. The window fix is what makes DSpark *runnable at
all* — that part is this patch working. The 1.0488 is a **separate** problem: that checkpoint
is trained anchor-as-first-prediction, which SGLang's 1+N assumption does not match, so it
earns little acceptance even once it runs. This PR removes the cap; it does not fix the layout.

### Scope

This removes the window cap. It does **not** make the official anchor-first
checkpoint produce useful acceptance on SGLang — that needs the layout question
resolved separately (the same `sample_from_anchor` handling vLLM's patch adds),
and the 1.06 above is a layout artifact rather than a window artifact. What this
PR unblocks is the ability to serve a draft at its trained block size at all,
which is a prerequisite for evaluating any of that.

It is also worth noting that the guard only fires on
`forward_mode.is_target_verify()` (`qwen_sparse_attn_backend.py:229`), so
draft-extend never consulted it; this change widens the verify path only.

### Open questions for maintainers

- Is a wider ring the right answer, or would you rather cap the window by
  construction and keep one group? The ring cost scales linearly with `N`
  (`ratio * num_request_slots * N` slots of index-K state per layer), which is
  small relative to the compressed-K pool but not free.
- Should `N` be user-visible after all? It is derived here so that existing
  invocations keep working unchanged; if you would rather it be explicit, the
  derivation is one call site.

Happy to adjust the shape of this to whatever fits the tree.
