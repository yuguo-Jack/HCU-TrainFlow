# [ROCm] Add DeepSeek-V4 Pro FP4 Triton Gluon decode MoE

[Upstream PR](https://github.com/sgl-project/sglang/pull/41847) · state: closed · merged: False

## Original PR description

> [!IMPORTANT]
> This is a stacked draft on #41639. Commit `140503aeb6c8a221ac02949b89f19ab414f71f03` is the exact parent of the DeepSeek-V4 Pro commit. Until #41639 merges, GitHub's upstream-main diff also displays the dependency; the DSV4-only commit is `406684a009ec479eb2cae6fac067e77b61e2745c`.

## Motivation

DeepSeek-V4 Pro FP4 decode on MI355X has the same generic runner boundary that motivated #41639: SGLang first materializes routing results and then hands them to the MoE runner. A model-specific whole-layer kernel can instead turn the learned router's top-k result directly into the expert schedule and co-schedule input quantization with router work.

This PR extends the strict Triton Gluon backend from #41639 with a DeepSeek-V4 Pro specialization. The public checkpoint already stores its routed-expert payload in packed FP4; this path does not quantize FP8 or BF16 routed weights into FP4. It is deliberately opt-in and fail-closed.

## Design

The learned-router layers execute:

```text
BF16 hidden states
  -> router projection + routed-input quantization
  -> ungrouped sqrtsoftplus top-6 selection
  -> route-specialized FP4 gate/up projection
  -> clamped SwiGLU + activation quantization
  -> FP4 down projection + weighted route reduction
  -> native FP8 shared expert add
  -> existing SGLang post-expert collective/finalization
```

The specialization implements the public DeepSeek-V4 Pro contract: hidden size 7168, 384 routed experts, local intermediate size 384 under TP8, normalized sqrtsoftplus top-6 routing, UE8M0 128x128 scales, and SwiGLU clamp 10.

The first three hash-routed layers do not have the learned router/top-k boundary consumed by this kernel. They are therefore declared as an explicit model-owned AITER subpath at construction time. This is not a shape-dependent runtime fallback: every later learned-router layer is owned by Gluon and raises on an unsupported call.

## SGLang integration and isolation

- Enable explicitly with `--moe-runner-backend gluon`; `auto` does not select it.
- The backend binds only to DeepSeek-V4 Pro native packed FP4 learned-router layers on gfx950, TP8/EP1.
- `Fp8MoEMethod` retains the AITER runner and its shuffled weight representation for the hash prefix; Gluon reuses that representation without a second packed copy. The class name reflects SGLang loader reuse, not the routed-expert dtype: AITER only pads and shuffles the checkpoint-native FP4 payload.
- `prepare_weights()` runs from the FP8 post-load hook, before CUDA graph capture, and caches the validated router/weight/scale references.
- The mixed-precision FP8 shared expert stays in SGLang's native linear path instead of being appended to the FP4 routed bank.
- The normal rank-local output ABI and SGLang post-expert collective remain unchanged.
- GLM, AITER, Triton, MegaMoE, DeepEP, and other model paths keep their existing selection behavior.

Current audited support:

| Device | TP | EP | Active M | Use |
|---|---:|---:|---:|---|
| gfx950 | 8 | 1 | 1 | target decode, concurrency 1 |
| gfx950 | 8 | 1 | 4 | DSPARK 3/4/1, concurrency 1 |
| gfx950 | 8 | 1 | 6 | DSPARK 5/6/1, concurrency 1 |

Prefill and higher-concurrency shapes are not enabled yet. They raise rather than silently switching a learned-router layer to another backend; this is one reason the PR remains Draft.

## Microbenchmark

Method:

- AMD Instinct MI355X (gfx950), production TP8 rank-local shapes.
- 09/24 daily image `lmsysorg/sglang-rocm:v0.5.20-rocm720-mi35x-20260924`.
- SGLang image SHA `4142235c2bfa3b7ffd9945ae1b6a17bb92a9fe4f`; AITER SHA `acf8fdf9307431ece8ee275971c41cb3d1a7020b`.
- BF16 router input, checkpoint-native packed FP4 experts in the AITER-shuffled device layout, and UE8M0 scales.
- Three independent GPUs/seeds; 80 repeats x 50 CUDA Graph replays per arm.
- AITER arm: router + sqrtsoftplus top-k + routed MoE. Gluon arm: complete fused routed path.
- Shared expert and TP collective are excluded from both arms, so these numbers do not claim end-to-end ITV improvement.

Median across the three runs:

| M | AITER router + top-k + routed MoE | Gluon routed path | Latency reduction | Speedup |
|---:|---:|---:|---:|---:|
| 1 | 43.62 us | 25.18 us | 42.3% | 1.73x |
| 4 | 62.56 us | 38.92 us | 36.9% | 1.58x |
| 6 | 73.33 us | 50.11 us | 31.7% | 1.46x |

The AITER router/top-k portion alone measured 17.42, 18.37, and 19.87 us at M=1/4/6. Gluon's gain is therefore not a claim that standalone top-k is faster; it comes from the fused producer/consumer boundary and route-specialized expert schedule.

## Correctness and tests

Completed on the same 09/24 ROCm image:

- `84 passed` across the Gluon backend, DSV4 shared-fusion policy, draft isolation, shared-expert scaling, and GLM NextN regression suites.
- gfx950 kernel test: `2 passed`, with all `M=1/4/6` compile/run subtests passing.
- The DSV4 sqrtsoftplus selector matches the Torch top-6 reference IDs and weights.
- FP8 post-load preparation, exact contract binding, explicit hash-prefix dispatch, unsupported-shape rejection, and invalid-model rejection have focused unit coverage.
- Ruff format and `F401,F821,F823,UP037`: pass.

The current kernel compile/safety fixture uses zero FP4 payload weights at production allocation sizes. Before marking ready for review, this still needs an actual-checkpoint nonzero output comparison, full server startup/generation accuracy, and end-to-end AgentX p90 ITV/throughput A/B.

## How to enable

Add the backend selection to a supported DeepSeek-V4 Pro TP8/EP1 decode configuration:

```bash
--moe-runner-backend gluon
```

The existing mixed-precision shared-expert policy remains authoritative; the FP8 shared expert is not repacked into the FP4 routed bank.
