# [Feat] PD: Support KV-only hybrid decode radix cache with MTP and DFlash2

[Upstream PR](https://github.com/sgl-project/sglang/pull/44889) · state: open · merged: False

## Original PR description

## Motivation

Enable decode-side prefix KV reuse for hybrid attention models in PD serving, supporting **EAGLE/MTP (top-k 1) and DFLASH (DFlash2)**. Shared-prefix requests reuse KV on the decode worker instead of allocating and transferring a separate copy for every request.

This reduces KV capacity pressure and transfer volume, allowing more requests to decode concurrently. Recurrent state remains request-local: each request uses its own full-prompt state received from prefill, including when shared prefixes have different suffixes.

## Modifications

- Decouple prefix KV matching from Mamba/KDA checkpoints while keeping recurrent-state ownership and release request-local.
- Preserve EAGLE bigram-key semantics at prefix boundaries and integrate DFLASH with its existing verification and recurrent-state update paths.
- Account for running and in-flight PD requests when budgeting persistent and speculative state.

Enabled through the existing `--disaggregation-decode-enable-radix-cache` option, using Python TreeCore. Hybrid speculative use supports EAGLE/MTP (top-k 1) and DFLASH with NIXL, without target-model sliding-window attention; unsupported cache/session combinations are rejected.

## Accuracy Tests

Validated GLM-5.3-Flash on 8 × H200 with TP4/EP4 on both P and D. Full GSM8K evaluation (1,314 examples, 5-shot, BF16 recurrent state) achieved:

| Configuration | Mean GSM8K accuracy (two runs) |
| --- | ---: |
| MTP516 + D radix cache | **95.66%** |
| DFlash2 block8 + D radix cache | **95.81%** |

Both configurations include the independent KDA tracking dtype fix in #44886.

- Shared-prefix, isolated-prefix, and concurrent requests returned the expected answers, including requests with different suffixes. D-side prefix hits were confirmed independently of P-side caching.
- **106 CPU regression tests passed**, covering KV-only matching, state isolation/release, draft-KV boundary keys, and state budgeting. Pre-commit checks passed.

## Speed Tests and Profiling

On a long shared-prefix workload, decode-side radix caching improves output throughput by **25.8% with MTP516** and **77.4% with DFlash2 block8**. TTFT P50 falls by **69.1%** and **85.0%**, respectively, as prefix KV reuse relieves decode KV capacity pressure and request admission queuing.

**Configuration:** GLM-5.3-Flash, 8 × H200 (P: GPUs 0–3; D: GPUs 4–7), TP4/EP4, FP8 target KV and BF16 recurrent state. MTP uses MTP112 on P and MTP516 on D; DFlash2 uses block8 on both workers with BF16 draft KV. D uses ReplaySSM speculative state, and P-side caching stays enabled. All configurations use the same code and common serving settings, including memory fractions and request limits. Each OFF/ON pair differs only in D-side radix caching.

**Workload:** C32, 1K output, 252K shared prefix + 4K unique suffix (~273K actual input tokens per request). Results are medians of three runs after warmup; all 512 requests per run succeeded in every configuration.

## Reproduction commands

Run P, D, and the router in separate terminals with the SGLang environment activated. The commands below reproduce the MTP configuration: P112 on GPUs 0–3 and D516 on GPUs 4–7. Use the default Triton MoE configurations (`SGLANG_MOE_CONFIG_DIR` unset).

### Prefill worker

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND=python \
SGLANG_DISAGGREGATION_ENGINE_INIT_TIMEOUT=300 \

  --model-path /path/to/GLM-5.3-Flash \
  --served-model-name llm \
  --trust-remote-code \
  --tp-size 4 \
  --ep-size 4 \
  --moe-runner-backend triton \
  --kv-cache-dtype fp8_e4m3 \
  --mamba-ssm-dtype bfloat16 \
```

- QNan0513 · comment · 2026-11-03T04:41:31Z · [source](https://github.com/sgl-project/sglang/pull/44889#issuecomment-6595629066)

Hi @Jzz1943, a sizing note from #44015 that touches the `_handle_max_mamba_cache` change here.

In KV-only decode mode this PR budgets the verify scratch for running plus in-transfer requests (`capped_reqs = min(...) + self._mamba_prealloc_requests()` in both spec-state branches). That matches what `HybridMambaDecodeReqToTokenPool` allocates on main today (`size + pre_alloc_size` rows). But in-transfer requests never run `target_verify`, and `intermediate_ssm` / `intermediate_conv_window` are indexed by batch row (`build_verify_intermediate_state_indices` over `req_to_token_pool.size`), so those rows are never used. #44015 stops allocating them in the default configuration (no ReplaySSM-spec, no `SGLANG_ENABLE_PP_SPEC`). With both PRs in, the two terms would reserve `pre_alloc_size` rows that are never allocated, and the KV pool would come out smaller than it needs to be.

The other prealloc terms look right to me: in-transfer requests do hold a persistent Mamba slot (`_mamba_running_request_capacity`), and GDN's ReplaySSM ring is keyed by `req_pool_idx` (`replay_req_slots`).

Whichever merges second can fix it: if #44015 goes first, the term can be dropped here; if this PR goes first, I'll remove it in #44015.
