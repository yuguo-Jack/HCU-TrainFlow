# fix: return 404 for unknown models on OpenAI-compatible endpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/31419) · state: closed · merged: False

## Original PR description

## Motivation

The OpenAI-compatible endpoints accepted any value for the `model` field and returned 200 even when the requested model was not the one being served. This diverges from the OpenAI spec, which returns a 404 `model_not_found` for an unknown model, and from SGLang's  `/v1/models/{model}` , which already returns 404. Fixes #31404.

## Modifications

Added a shared `validate_served_model` helper on `OpenAIServingBase` that returns a 404 `model_not_found` response for an unknown model and `None` otherwise. It accepts the served model name and any loaded LoRA adapters, including the `base-model:adapter` syntax, and skips requests that omit the model or use the default sentinel. The helper is called from `handle_request`, which every OpenAI endpoint inherits, and from `create_responses`, since `/v1/responses` does not go through `handle_request`. Rerank requests do not carry the `model` field. The 404 body matches the existing retrieve_model handler so clients get a consistent error.

Nice fix. One suggestion worth considering: an opt-out env matching vLLM's
[`VLLM_SKIP_MODEL_NAME_VALIDATION`](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/serve/engine/serving.py#L70-L75).

This is a breaking change for any deployment that today relies on the tolerant
"unknown `model` returns 200" behaviour (front-side gateways doing their own
routing, clients that pass a canonical model ID upstream of the actual served
name, older test harnesses, etc.). vLLM shipped the same change and the env
has proven useful for staged migration — operators can flip it on immediately
after upgrade, fix their clients, then turn it off.

Concretely:

In `python/sglang/srt/environ.py`, under the "HTTP server" section
```
# Opt out of OpenAI-compat `model`-field validation. When True, requests
# with an unknown `model` value pass through instead of returning 404.
# Mirrors vLLM's VLLM_SKIP_MODEL_NAME_VALIDATION for deployments that rely
# on the prior tolerant behaviour during migration.
SGLANG_SKIP_MODEL_NAME_VALIDATION = EnvBool(False)
```
And at the top of `validate_served_model`:
```
from sglang.srt.environ import envs
if envs.SGLANG_SKIP_MODEL_NAME_VALIDATION.get():
    return None
```

File: `python/sglang/srt/entrypoints/openai/serving_base.py` · line None

Subtle regression risk here: several request schemas have
`model: str = DEFAULT_MODEL_NAME` (Embedding / Classify / Rerank / Score /
Tokenize / Detokenize / Transcription) and clients routinely send bodies
without the `model` field. The current check treats those correctly
(pydantic-filled `"default"` → skip validation) — but it **also** silently
accepts a client that explicitly sends `{"model": "default"}` against a
different `served_model_name`, which is the exact class of client typo this
PR is trying to catch.

`pydantic`'s `model_fields_set` distinguishes the two cleanly:

```
def validate_served_model(self, request):
    if isinstance(request, V1RerankReqInput):
        return None

    # Only validate when the client explicitly sent `model`; pydantic
    # default-filled values (from `model: str = DEFAULT_MODEL_NAME`) are
    # respected as "use whatever's served".
    if "model" not in getattr(request, "model_fields_set", {"model"}):
        return None

    model = request.model
    if not model:
        return None
    ...
```

The `getattr(..., {"model"})` fallback keeps non-pydantic objects on the strict
path (fail-safe rather than fail-open). This also removes the need for the
explicit `== DEFAULT_MODEL_NAME` check — if a client wanted `"default"` they get
validated like any other value.
