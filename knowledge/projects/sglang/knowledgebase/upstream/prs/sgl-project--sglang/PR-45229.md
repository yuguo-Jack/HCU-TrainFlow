# [Feat] LiLiCorr: Support GGUF draft checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/45229) · state: open · merged: False

## Original PR description

## Motivation

Add support for LiLiCorr GGUF draft checkpoints, including `nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB-LiLiCorr-GGUF`.

Depends on #44563. This branch includes those changes and should be rebased onto main once it merges.

## Modifications

- Read LiLiCorr configuration and tensor mappings from GGUF metadata.
- Load packed NVFP4 weights through the existing ModelOpt implementation.
- Limit detection to GGUF checkpoints with DFlash architecture and LiLiCorr metadata.
- Add regression tests, serving tests, and a documented launch example.

NVFP4 Marlin LiLiCorr heads currently require TP1. This is an existing restriction in the LiLiCorr implementation.

## Accuracy Tests

Tested commit `653e968` with the 24GB quantized target on one H100 and the BF16 target on one B300, both at TP1. Both targets used the same published 24GB LiLiCorr drafters, in safetensors and GGUF formats, with unchanged configs. Results were nearly identical

| Target / GPU | Drafter format | GSM8K | Mean acceptance length |
| --- | --- | --- | --- |
| 24GB quant / H100 | Safetensors | 174/200 (87%) | 6.00 |
| 24GB quant / H100 | GGUF | 174/200 (87%) | 6.00 |
| BF16 / B300 | Safetensors | 173/200 (86.5%) | 6.10 |
| BF16 / B300 | GGUF | 173/200 (86.5%) | 6.10 |

All runs used DFLASH block size 8: seven proposed draft tokens plus one target/bonus token. Acceptance length includes the bonus token and is averaged over the 200 per-request values.

Both formats passed text, image-counting, and OCR smoke checks with both targets. All 54 focused regression tests passed in the H100 validation.

GSM8K used the legacy `sglang.test.run_eval` chat evaluator with 200 examples, zero shots, temperature 0, one evaluation worker, a 512-token output limit, and thinking disabled. The one-question difference is not meaningful evidence of an accuracy difference.

EDIT: After the review updates, the registered E2E test uses `sgl_eval` with thinking disabled and a prompt requesting calculations followed by a boxed final answer. On the H100 with the 24GB target and GGUF drafter, it scored 192/200 (96%).

A comparison run using `sgl_eval` with the prompt and answer extractor used with `run_eval` scored 175/200 (87.5%), consistent with the original 87% result. The new 96% score uses different prompting and grading.

The commands below reproduce the original H100 validation using the legacy `run_eval` evaluator.

```bash
target=nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB
target_revision=5165e12246e823a578bc2d483958439c38d9d6bd
draft=nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB-LiLiCorr-GGUF
draft_revision=182d2987939e12f458298b5d5f6ef98912f4ad6c

python3 -m sglang.launch_server \
  --model-path "$target" --revision "$target_revision" \
  --served-model-name validation --trust-remote-code \
  --context-length 4096 --max-running-requests 4 \
  --max-total-tokens 8192 --max-mamba-cache-size 32 \
  --mem-fraction-static 0.6 \
  --host 127.0.0.1 --port 30000 --watchdog-timeout 1200 \
  --speculative-algorithm DFLASH \
  --speculative-draft-model-path "$draft" \
  --speculative-draft-model-revision "$draft_revision" \
  --speculative-dflash-block-size 8 \
  --speculative-draft-attention-backend triton
```

BF16 validation used target revision `a6a1e5030819a130a1ea08aadb1fe42f4cc86777` of `nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-BF16` and `--mem-fraction-static 0.92`, with the same drafter revisions and remaining server settings.

For the safetensors drafter, substitute these values before launching:

```bash
draft=nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB-LiLiCorr
draft_revision=449d24140160b8e51871bfc0f0a7338abf640aa1
```

```bash
python3 -m sgl_eval.cli run gsm8k \
  --base-url http://127.0.0.1:30000/v1 \
  --model validation \

```

```bash

```

## Speed Tests and Profiling

Same H100 and server settings as above. The target-only baseline omits the five speculative options.

Synthetic requests used 256 input tokens and 128 output tokens, with 20 requests at concurrency 1 and 40 at concurrency 4. All requests completed.

| Drafter | Concurrency | Output tokens/s | Input + output tokens/s |
| --- | ---: | ---: | ---: |
| None | 1 | 89.6 | 268.7 |
| Safetensors | 1 | 107.6 | 322.8 |
| GGUF | 1 | 107.9 | 323.8 |
| None | 4 | 138.1 | 414.3 |
| Safetensors | 4 | 153.8 | 461.4 |
| GGUF | 4 | 156.7 | 470.1 |

Run against each server configuration, using a separate output directory for each:

```bash
target=nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB

for concurrency in 1 4; do
  requests=20
  if [ "$concurrency" = 4 ]; then requests=40; fi

  python3 -m sglang.benchmark.serving \
    --backend sglang --host 127.0.0.1 --port 30000 \
    --model "$target" --tokenizer "$target" \
    --served-model-name validation \
    --dataset-name random \
    --random-input-len 256 --random-output-len 128 \
    --random-range-ratio 1.0 --num-prompts "$requests" \
    --max-concurrency "$concurrency" \
    --warmup-requests 2 --flush-cache --tokenize-prompt \
    --seed 42 --temperature 0 \
    --output-file "c${concurrency}.jsonl"
done
```

File: `python/sglang/srt/utils/hf_transformers/gguf_reader.py` · line None

[by Claude Code] **Severity: perf | Confidence: Medium**

**Issue**

`lru_cache` keeps each parsed `GGUFReader` alive for the life of the process. The reader holds every metadata part as a NumPy view, so the drafter's tokenizer metadata stays in host memory after config and weight loading finish. The main process (`_resolve_speculative_algorithm_alias` -> `get_config`) and the scheduler each keep one. `build_gguf_tokenizer` now also caches the reader for GGUF-native targets such as muse-glimmer, in every process that builds the tokenizer.

**Example**

On a synthetic GGUF with the drafter's 131k tokens and 269k merges, one live reader adds about 470 MB RSS. Freeing it releases about 400 MB.

**Fix**

Cache the small derived results (architecture, LiLiCorr check, built config) instead of the reader, and let `lilicorr_gguf_weights` open a short-lived reader. Or call `get_gguf_reader.cache_clear()` once loading finishes.
