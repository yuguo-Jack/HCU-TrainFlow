# [Fix] lfm2: Fix quadratic regex scan in the tool-call parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/42582) · state: open · merged: False

## Original PR description

## Motivation

`Lfm2Detector.detect_and_parse` (`lfm2`) finds tool calls with `re.findall(rf"{bot}(.*?){eot}", text, re.DOTALL)`. When `<|tool_call_end|>` never arrives, each opening tag rescans to the end of the text, so the cost is quadratic: 320 KB of unclosed `<|tool_call_start|>` took **39.7 s**, and now takes 0.1 ms.

Tool-call parsing runs synchronously on the tokenizer manager's event loop, so one such response stalls every in-flight request. Found with an Atheris fuzzing harness that records per-input parse time.

## Modifications

- `_iter_tool_call_bodies`: a linear `str.find` scan yielding exactly the bodies `findall` returned. The now-unused `import re` is removed.
- Regression test in `TestLfm2Detector`: 16.0 s on `main`, fast here.

## Accuracy Tests

- Differential test of `main` vs patched detector, comparing `detect_and_parse` and every streaming result under random re-chunking: **0 mismatches** over 20k random plus 20k mutated well-formed inputs (15k produced parsed calls).
- `test/registered/unit/function_call/`: 630 passed.

## Speed Tests and Profiling

See above.

**Not addressed here:** `_escape_nested_quotes_in_strings` (the recovery path for a complete block that fails to parse) is also quadratic. For each broken string it tries every later quote as a closer and runs `ast.parse` on the rebuilt text: a closed block of 2,000 malformed calls (46 KB) takes about 25 s. Bounding it (for example, capping candidates or block size) may change which candidate wins on contrived inputs, so I'd like maintainers' input on the preferred limit before changing it.

Related: #42573 – #42580 (same issue class in other tool-call parsers).
