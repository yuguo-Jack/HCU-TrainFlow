# [Fix] unified-memory: Keep the host's state slot count when a draft's state fuses into it

[Upstream PR](https://github.com/sgl-project/sglang/pull/46376) · state: open · merged: False

## Original PR description

## Motivation

On a Mamba-hybrid host with `--enable-unified-memory`, a draft whose layers carry recurrent state (for example Inkling-Small's MTP head) fuses that state into every state slot of the target's buffer. The state solve then sized the slot count from the widened slot, and that count also caps `max_running_requests` (it divides by the slots each request holds). So the fused server ran fewer requests at once than the default pool, which solves the count from the target's state alone and gives the draft its own pools of the same count.

With Inkling-Small's MTP draft, the draft's state widens each slot by about 20%, so the unified server capped `max_running_requests` at 11 where the default pool allows 14.

## Modifications

- `_handle_max_mamba_cache` (`mem_cache/kv_cache_configurator.py`) solves the slot count from the host's own state, as the default pool does, and charges the widened slots in full out of the KV share. The speculative scratch, which covers only the host's layers, is priced at the host's state too.
- The fused slot is built from a pipeline rank's own layers, so its charge is no longer scaled by the rank's share of the state layers a second time. Under pipeline parallelism that scaling undercharged every slot and let the buffer outgrow its budget.

Tests (CPU), `test/registered/unit/mem_cache/test_mamba_donated_alloc_ratio.py`: with a draft state fused into every slot, the solve keeps the unfused slot count and charges the widened slots to the KV remainder, with and without speculative scratch; at PP 1, 2 and 8 over uneven stages, the charge is K + 1 slots at the rank's own fused width. This replaces the test that sized the count from the widened slot.

## Why this is a temporary fix

This PR makes unified memory match the default pool under today's calculation, but it doesn't remove the limit itself. The request cap on unified memory still comes from a calculation built for two fixed pools. The fundamental solution is a redesign of memory sizing and of how the maximum request count is calculated, which is out of scope here.

`--enable-unified-memory` keeps state and KV in one buffer that is split dynamically at runtime, so `--mamba-full-memory-ratio` should no longer limit what a server can do. At boot, it still does:

1. `_handle_max_mamba_cache` takes the ratio's share of the memory as a state budget and solves a state slot count from it, as if state had a fixed pool of its own.
2. `resolve_max_num_reqs` caps `max_running_requests` at that slot count divided by the slots each request holds.
3. `size_kv_storage` builds the buffer from the token budget plus those slots, and the token budget has already had them subtracted. So the slot count almost cancels out of the buffer's size.
4. At runtime, allocating a state slot doesn't read the slot count: state and KV share whatever room the buffer has.

So the slot count no longer describes how memory is used. What remains of it is the request cap and, through the cap, the speculative scratch reserved outside the buffer. With Inkling-Small's MTP draft and this PR, the cap is 14 requests (70 slots), while the buffer has room for well over a thousand slots. On the loads below, scheduler-reported token usage stays under 5% while requests wait in the queue.

This affects every model with recurrent state on unified memory, not only fused drafts. This PR only corrects the input for a draft with state: changing `--mamba-full-memory-ratio` still changes the cap.

A redesign would derive the maximum request count from what requests actually need: the speculative scratch, a row in the request table, and room for their state and KV in the shared buffer. Whether throughput keeps scaling past today's cap hasn't been measured, since larger batches also slow each step, so that should come first. `--max-running-requests` with `--max-mamba-cache-size` can already raise the cap for such a test. Once a redesign lands, this PR's slot count change is no longer needed, and its scratch and pipeline-parallel charges should be rechecked against the new calculation.
