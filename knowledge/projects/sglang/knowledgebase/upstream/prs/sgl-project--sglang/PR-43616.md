# [Fix] Gemma 4: skip quantization for ignored fused vision qkv/gate_up layers

[Upstream PR](https://github.com/sgl-project/sglang/pull/43616) · state: open · merged: False

## Original PR description

## Motivation

Fixes #43342. Loading `cyankiwi/gemma-4-31B-it-AWQ-4bit` (compressed-tensors W4A16) fails during weight post-processing with `gptq_marlin_repack.cuh:311: size_n = 8608 is not divisible by tile_n_size = 64`.

The Marlin shape is a symptom. The checkpoint's quantization `ignore` list excludes the vision tower, naming its clippable linears by their inner module, e.g. `model.vision_tower.encoder.layers.0.self_attn.q_proj.linear` and `...mlp.gate_proj.linear`, and stores those weights in bf16. SGLang fuses them into `qkv_proj` / `gate_up_proj`, and `should_ignore_layer` expands a fused name into shard names without the `.linear` level (`...self_attn.q_proj`), so the fused vision layers are not matched and get W4A16 schemes. Their packed weights are never loaded from the checkpoint (`Some weights are not initialized from checkpoints: [... 216 tensors: qkv_proj and gate_up_proj weight_packed / weight_scale / weight_shape / weight_zero_point for all 27 vision layers]`), and the repack then fails on gate_up's N = 2 x 4304 = 8608. The vision qkv_proj (N = 3456) passes the Marlin shape check, so it would run on uninitialized weights if only the gate_up crash were worked around. Unfused vision layers (o_proj, down_proj) already match because their prefix ends in `.linear`.

## Modifications

- `Gemma4ForConditionalGeneration.hf_to_sglang_mapper` rewrites the suffixes `.{q,k,v,gate,up}_proj.linear` to `.{q,k,v,gate,up}_proj`. The loader applies this mapper only to the quantization config (`apply_weight_name_mapper`), so the ignore entries match the fused shard names; weight loading is unchanged. `Gemma4UnifiedForConditionalGeneration` inherits it.
- `test/registered/unit/models/test_gemma4_quant_ignore.py` (CPU): with the checkpoint's vision ignore entries, the fused vision qkv_proj/gate_up_proj are ignored, and language-model qkv_proj/gate_up_proj (not listed) stay quantized.

## Accuracy Tests

On one A100-SXM4-40GB with SGLang 0.5.21 (tp=1, `mem_fraction_static=0.88`, context 4096):

| build | load | uninitialized tensors | text | image (red square left, blue circle right) |
|---|---|---|---|---|
| main | fails: `size_n = 8608 is not divisible by tile_n_size = 64` | 216 | n/a | n/a |
| this PR, `--dtype bfloat16` | ok | 0 | correct | "There is a red square on the left and a blue circle on the right." |
| padding N to 64 instead (rejected) | ok | 216 | correct | "A dark brown, textured fabric with a repeating pattern of small, light-colored, circular shapes ..." |

Note on dtype: this checkpoint's config.json sets `dtype: float16` for the model and text_config but `bfloat16` for vision_config. With `--dtype auto` the model runs in float16. Now that the vision weights are actually loaded, image requests produce NaN: `Gemma4VisionPooler` scales the pooled features by `sqrt(hidden_size)` in the working dtype, which overflows float16. (transformers scales and standardizes in float32.) With the radix cache on, requests that reuse the chat-template prefix computed by an image request also fail. So after the server's VLM warmup, which sends an image, every chat request returns `<pad>`. Serving with `--dtype bfloat16` avoids this; I verified that with the issue's command. Scaling and standardizing in float32 also fixes float16; I verified that with the stock model (see comments). Neither change is part of this PR.

Unit test: fails on main (no mapper), passes with the change. CPU check against the checkpoint's full quantization_config: before, fused vision qkv/gate_up are not ignored; after, they are ignored and all language-model layers keep their W4A16 scheme.

| float16 | empty | empty | empty |

So the float16 failure is not specific to this AWQ checkpoint or to this PR: Gemma 4's vision path produces non-finite values in float16, and because the radix cache keeps the shared chat prefix from that request, every later request is affected. The AWQ checkpoint only hits it because its config says `float16`. This PR is still needed for the load failure; the float16 behavior seems worth a separate issue (e.g. defaulting Gemma 4 to bfloat16 when the config says float16).


- JonSnow1807 · comment · 2026-10-12T01:11:32Z · [source](https://github.com/sgl-project/sglang/pull/43616#issuecomment-6115986706)

Correction to my earlier float16 note, with a narrower root cause:

- The non-finite values start in `Gemma4VisionPooler`. It multiplies the pooled features by `sqrt(hidden_size)` (≈ 33.9) in the working dtype, so anything above 65504 / 33.9 ≈ 1930 overflows in float16. I checked the test image standalone, with transformers' Gemma 4 encoder feeding SGLang's pooler code. About 420 elements overflow, and `embed_vision`'s RMSNorm then turns 53–55 of the 256 image tokens into NaN. The 27 encoder layers stay finite (max |activation| ≈ 2.8k). transformers scales and standardizes in float32 for this reason; see the docstring of its `Gemma4VisionPooler`.
- Changing only that in SGLang (scale and standardize in float32, then cast back) fixes stock `gemma-4-31B-it` with `dtype="float16"`. With the radix cache on and the image first, it gives the same image description as bfloat16, then a correct text answer, then the same description again.
- "Every later request is affected" was too broad. In my runs, text-only requests were answered correctly in float16 before and after an image request. The exception was when the radix cache was on and the image request had been the first to compute the chat-template prefix, as happens after the server's VLM warmup. With `disable_radix_cache=True`, text after an image was correct. The image request itself always returned NaN logprobs (token 0) in float16.
- My PR description blamed bidirectional image attention for the prefix corruption. That reasoning doesn't hold: `prepare_attn_masks` makes only the image rows bidirectional, and the prefix rows stay causal. I haven't traced how the NaN reaches the cached prefix, so I've removed that sentence from the description.

So instead of defaulting float16 configs to bfloat16, I'd suggest a follow-up that scales and standardizes in float32 as transformers does. I can send that as a separate PR. This PR's ignore-list fix is unchanged.
