# [Feat] kv-events: Report caller multimodal routing labels as block spans

[Upstream PR](https://github.com/sgl-project/sglang/pull/45737) · state: open · merged: False

## Original PR description

## Motivation

#43043 made SGLang derive multimodal pad values from its own item identity (four 62-bit sentinels per item), and Kimi processors now reject caller `mm_hashes`. External KV-aware routers such as NVIDIA Dynamo used `mm_hashes` to force SGLang's cache identity to match their routing keys. That no longer works. It is also unsafe: a caller hash that decides reuse can serve one image's KV for another image (#44641, gated in #44653). We reproduced this on SGLang without this change. With Dynamo's current `mm_hashes` forwarding, a blue image sent under a red image's hash reused every image block and answered "red".

This PR lets a router recover its own per-item routing identity from KV events without touching SGLang's cache identity:
- The caller attaches one opaque label to each multimodal item.
- SGLang reports where each labeled item's tokens landed in each stored block.
- SGLang keeps full control of identity and reuse, so a wrong or colliding label can only mislead the router. It can never cause wrong KV reuse.

The design is discussed in ai-dynamo/dynamo#17044 (tracking ai-dynamo/dynamo#16975). The Dynamo side is ai-dynamo/dynamo#17082. The field names are provisional. I'm happy to carry the spans in #27735 (`extra_keys` on `BlockStored`) instead if that is preferred.

## Modifications

- **Request field.** `GenerateReqInput.mm_routing_labels`, `Engine.generate(...)` and `Engine.async_generate(...)` take one optional opaque string per multimodal item, batched like `mm_hashes`.
- **TokenizerManager.** Attaches each label to the new optional `MultimodalDataItem.routing_label` when the counts match. Otherwise it logs a warning and ignores the labels for that request.
- **Label table.** `MultimodalInputs.from_dict` (scheduler) runs after pad values are set and maps pad value to label in a per-process table, `MmRoutingLabels`:
  - The first label wins.
  - The table is LRU-bounded at 2^20 pad values.
  - Only the process that records KV events fills it; other tensor-parallel ranks skip it.
  - Labels never feed `set_pad_value`, item hashes or radix keys.
- **Event field.** `BlockStored.mm_routing_spans` is optional and omitted when unset.
  - Per block, aligned with `block_hashes`, it lists the `[start, length, label]` runs of labeled multimodal tokens.
  - It is computed when events are emitted, in `KVCacheEventRecorder.record_store` and in the Rust tree core adapter. So it covers both tree cores, HiCache write-through and load-back, and event replay.
  - When `enqueue` coalesces stores, it extends the spans along with `block_hashes`.
- **Unlabeled tokens.** Bigram (EAGLE) keys carry no spans. Unlabeled requests, and items whose label has left the table, produce no spans, and consumers treat those tokens as unlabeled.

## Accuracy Tests

The forward pass and cache identity don't use labels. `test_label_does_not_change_item_identity` checks that pad values and hashes are unchanged.

## Validation

- **New CPU tests** pass on this branch: `test/registered/unit/mem_cache/test_mm_routing_labels.py`, 9 tests.
- **Existing tests:** `test_mm_hashes.py`, `test_io_struct.py`, `test_unified_pending_event_batches.py` and `test_kv_events.py` pass. The exception is `TestLocalKvEventSource::test_advertised_source_delivers_events`, which fails the same way on unpatched `main` here (ZMQ "Address already in use").
- **End to end** on one GH200, with Qwen3-VL-2B-Instruct and a reduced Kimi-K2.5 config with random weights. This ran on 3b932cd, before rebasing onto current `main`; the rebase had no conflicts.
  - **Full Dynamo stack** (frontend, KV router, two SGLang workers). The router's predicted overlap matched SGLang's `cached_tokens` whenever the label identified the cached item. That held for images (HTTP URLs, `data:` URIs, frontend-decoded content), videos, and image plus video in one request.
  - **Rust and Python tree cores, HiCache.** On write-through, device eviction and load-back, device and host stores carried spans. Replayed events were byte-identical to live ones.
  - **Kimi-K2.5.** Requests with `mm_routing_labels` succeed where `mm_hashes` is rejected, and spans cover every image token.
- **TP=2** (two ranks sharing one GPU, reduced Kimi-K2.5): only the rank that records KV events fills the label table, and spans and cache reuse match TP=1.

## Speed Tests and Profiling

When no label is registered, `mm_routing_spans` returns immediately. Otherwise it scans each stored block's tokens once in Python as the event is emitted. This is not benchmarked yet.

## Open questions

- Field names and placement: `mm_routing_labels` and `mm_routing_spans`, or #27735's `extra_keys`.
- How a server should advertise that its active cache implementation and event format emit spans.
- The table capacity (2^20 pad values per scheduler process), and whether it should be configurable.

Agreed, equal totals weren't enough. With encoder disaggregation, `get_mm_data` builds items in prompt order across types, so a video before an image swapped the two labels.

Fixed in 8fd5f0678b by matching per media type instead of by position. The labels are split by the request's image, video and audio counts, and the k-th item of a type takes that type's k-th label. If a type's item count differs from its labels (for example an unsplit bundle), that type stays unlabeled and its tokens are reported without spans; the other types keep their labels. The scheduler-side encoder assembly receives the labels already split by type.
