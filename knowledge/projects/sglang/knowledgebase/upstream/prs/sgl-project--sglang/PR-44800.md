# [Fix] hicache: Order write-back host copies after the forward that produced the KV

[Upstream PR](https://github.com/sgl-project/sglang/pull/44800) · state: closed · merged: True

## Original PR description

## Motivation

With `--hicache-write-policy write_back`, KV pages could be copied to host before the forward pass that produced them had finished. The host copy then held whatever the page contained at submit time, and a later load-back served that stale KV to another request. Two paths reached the device-to-host copy without any dependency on the forward stream:

- **Insert-time SWA window backups.** Write-back defers Full and Mamba backups to eviction, but the tree core still published an unbacked SWA window when a request's nodes were inserted. That backup was queued while the request's own forward could still be writing the window.
- **The blocking write-back drain.** Eviction submits everything queued in the tick on the device-to-host stream with no fence, and an evicted SWA page can belong to a checkpoint whose producing forward has not completed.

## Modifications

- `UnifiedTreeCore` (Python) and `unified_tree_core.rs` (Rust): under write-back, insertion never returns a `BackupKV` action, so SWA windows are no longer published at insert time. The incremental-component check no longer special-cases SWA under write-back.
- `HiCacheController.start_writing(wait_for_forward=...)`: a new keyword-only flag. When set and a `write_fence_stream` is configured, the device-to-host stream waits on it before the copies are submitted. The scheduler sets `write_fence_stream` to the model runner's forward stream next to the existing `load_fence_stream`.
- `UnifiedRadixCache.writing_check(write_back=True)` passes `wait_for_forward=True` on the blocking drain. Write-through and the asynchronous write-back flush are unchanged, and the default keeps every other caller as it was.
- Tests:
  - `test_hicache_write_back_ordering.py` (new): a checkpointed request whose forward is still writing on a separate stream; evicting an older SWA window of that request must copy the values the forward wrote, not the pre-forward contents.
  - `test_unified_hicache_regressions.py`: the blocking drain waits for the fence stream before copying both a tick's queued backup and the eviction victim.
  - `test_unified_radix_cache_unittest.py` and the Rust crate tests: write-back insertion of backed Full nodes publishes no SWA window and leaves no pending ack; the Mamba pending-ack eviction test now queues its window backup explicitly instead of relying on insert-time publication.

## Accuracy Tests

- `cargo test` for `rust/sglang-radix-tree` (`--no-default-features`, as `pr-test-rust-workspace.yml` runs it): 931 passed, 0 failed.
- On one CUDA GPU, with both `SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND=rust` and `=python`: `test_hicache_write_back_ordering.py`, `test_unified_hicache_regressions.py::TestTransferStreamOrdering`, and the two touched cases in `test_unified_radix_cache_unittest.py` pass.
- Without the runtime changes, `test_hicache_write_back_ordering.py` fails on both backends: the host copy holds the pre-forward contents instead of what the forward wrote.
- No numerics change: the fix only orders existing copies after their producer and removes an early backup that eviction performs later.

## Speed Tests and Profiling

The new wait is a single `wait_stream` on the blocking write-back drain, which already blocks on every ack; the asynchronous paths do not take it.
