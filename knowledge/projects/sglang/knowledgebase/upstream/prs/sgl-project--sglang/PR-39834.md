# [Feat] elastic-ep: Add orchestrator-safe scale-up bootstrap

[Upstream PR](https://github.com/sgl-project/sglang/pull/39834) · state: open · merged: False

## Original PR description

## Motivation

Dynamo is designing Kubernetes-managed Elastic EP in ai-dynamo/dynamo#13121. SGLang's merged scale-up path accepts an absolute EP target and reports asynchronous progress, but an external reconciler still cannot retry an ambiguous POST with transactional certainty or launch capacity allocations from one immutable Kubernetes Pod template.

This PR implements the scale-up portion of the orchestrator-facing contract proposed in #35376. It is intentionally limited to append-only growth with one joining capacity allocation per operation. An allocation may contribute multiple contiguous EP ranks; scale-down, recovery, and multi-pod allocation admission remain separate work.

## Modifications

### Restart- and retry-observable operations

- Give each running tokenizer manager a stable `instance_id`.
- Accept an optional caller-supplied `operation_id` and `expected_instance_id` on `POST /scale_elastic_ep`.
- Make retries with the same operation, target, and allocation identity return the existing operation without resubmission.
- Reconcile ambiguous scheduler submissions by safely re-fanning out the same operation; scheduler-side idempotency returns the retained pending or terminal result.
- Reject a reused operation ID with different parameters, a stale runtime instance, or a competing operation with HTTP 409.
- Retain terminal operation state and expose instance, operation, phase, target, error, effective size, and outcome through `GET /is_scaling_elastic_ep`.

### Template-invariant initial formation and append bootstrap

- Add `--elastic-ep-join-mode auto` and `--elastic-ep-allocation-index`.
- Observe one allocation's rank width from its visible accelerators and reject conflicting TP, DP, EP, node, rank-offset, or device-selection geometry.
- Form all initial allocations as one distributed world. For initial EP size `N` and allocation width `W`, indexes `[0, N / W)` derive global `tp_size = attn_dp_size = ep_size = N`, `dp_size = 1`, `nnodes = N / W`, and their node rank. Initial formation does not use synthetic grow operations.
- Resolve later indexes as append-only joiners with rank offset `allocation_index * W` and local `tp_size = attn_dp_size = ep_size = W` and `dp_size = 1`.
- Publish a runtime-scoped topology record containing the runtime instance, initial size, observed width, effective size, and monotonic `max_committed_ep_size`.
- Probe that record with bounded retries, using `--dist-init-addr` as the authoritative primary address, without changing the process-group collective timeout.
- Admit an automatic append only when its offset equals both the effective size and the maximum size ever committed. A previously occupied or mismatched slot fails immediately with a recovery-required error.
- Add `--elastic-ep-allocation-id` for an opaque capacity-allocation identity such as a Kubernetes Pod UID. The allocation index and ID can come from downward-API environment variables while every Pod uses the same template.
- Report initial size, observed allocation width, effective size, and maximum committed size through the existing status endpoint.

### Operation-bound cohort admission and status

- Publish the accepted operation to the shared TCPStore before admitting joiners.
- Scope cohort records by runtime instance and operation identity so a failed operation cannot poison a later resize from the same EP size.
- Make a joining cohort wait for its assignment and bind it to runtime instance, operation, target, rank range, and optional authorized allocation ID.
- Reject stale or mismatched cohorts explicitly.
- Report joining rank offset/count, ready rank count, and joining allocation identities in status.
- In automatic bootstrap mode, reject a target whose increase differs from the resolved allocation width. Explicit mode does not infer the joiner width from the primary; mismatched targets are rejected when the joiner registers its cohort.

### Independent operation result and runtime health

- Preserve the immutable terminal result of the latest scale operation.
- Track later runtime recovery failures separately as `runtime_health` and `runtime_error`.
- Ensure a recovery limitation cannot rewrite a successfully committed scale operation during GET or idempotent retry.

### Physical EP and logical DP units

- Integrate the shared attention-replica conversion from merged #33728, including the completed-operation retry/reconciliation path.
- Keep API targets, effective/initial/maximum sizes, and joining rank offsets/counts in physical EP units.
- Keep worker counts, control fan-out, and DP-controller activation slots in logical DP units. For example, EP6 with attention TP2 uses three DP workers.
- Retain and validate the joining cohort's attention TP/CP topology alongside its operation and allocation identity.

The existing explicit `scale`/`recover` flags remain supported.

## Known limitations

- Automatic bootstrap currently requires attention TP1 and attention CP1 (`tp_size == attn_dp_size == ep_size`).
- Explicit scale-up follows #33728's fixed-attention-topology contract: primary and joiners must use the same attention TP/CP widths. Automatic bootstrap remains restricted to attention TP1/CP1.
- Automatic mode forms the complete initial world and selects only never-occupied append slots. It never selects `recover`; refilling an inactive or previously occupied slot still requires explicit recovery mode.
- Replacing allocation index 0 creates a new primary and runtime instance. An orchestrator must recreate the complete engine group until control-authority failover is supported.
- The topology record is currently primary-owned and stored in the coordination store. Its semantics are part of the contract; the storage mechanism is not.

Good catch—there was no bound here, so a missing scheduler response could keep both the communicator call and `_elastic_scale_lock` held indefinitely. Fixed in e8abbdef: the fan-out now uses `asyncio.wait_for`, bounded by 30 seconds or the configured scale-operation timeout when that is smaller. Each fan-out attempt also gets a distinct `submission_id` echoed by schedulers, so a late response from the abandoned attempt is dropped instead of being counted toward the retry. `test_submission_timeout_releases_lock_for_retry` and `test_cancelled_call_drops_late_correlated_response` cover those cases.
