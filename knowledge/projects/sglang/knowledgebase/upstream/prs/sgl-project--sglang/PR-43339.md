# [diffusion] share the layerwise pinned weight stores across co-resident instances

[Upstream PR](https://github.com/sgl-project/sglang/pull/43339) · state: open · merged: False

## Original PR description

## Motivation

Several `sglang serve` processes on one host each materialize the **same** layerwise pinned host store. For MiniMax-H3 fl2va that store is 108.5 GiB of page-locked host memory (transformer 62.28 GB + text encoder 46.18 GB), while each server uses only ~10 GiB of a 96 GiB card — so the host, not VRAM, is what limits how many can run.

Part of that duplication is already handled: `main`'s read-only checkpoint mapping shares page-cache pages across processes (36.7 GiB per instance at N=2 in the run below). What cannot be shared that way is the **pinned** store, because `cudaHostRegister` refuses a read-only file mapping, a writable one breaks copy-on-write per process, and `_shared_storage` is an anonymous memfd that peers cannot open.

Measured on `main` with sharing off, one server per GPU started one at a time, on an otherwise idle 498 GiB host (build and its one caveat in *Speed Tests* below): the first server costs 126 GiB of host memory and **every further one costs another ~123 GiB**. Two servers already need 249 GiB and four need ~496 GiB, so four co-resident servers are not reachable today.

## Modifications

Name the segment so a peer can attach to the creator's copy:

- The first instance creates, fills and registers the segment, then publishes a per-store marker.
- A follower waits for that marker, attaches, compares the store against the weights **it** loaded from disk, and only then registers it in its own CUDA context. A store holding different bytes is refused and the caller allocates privately, so a mismatch costs memory rather than correctness.

Ownership uses two independent locks, neither ever converted (POSIX does not make `flock` conversion atomic):

- `<base>.owner` — held exclusively for life by the creator;
- `<base>.users` — held shared for life by every process serving a generation;
- `<base>.decide` — a short mutex that serialises the decision.

Reclaiming a generation requires holding **both** locks exclusively at once, which is only possible once no creator and no follower is alive, so the kernel answers "is anyone still serving?" instead of a wall clock. The participant that leaves last runs that same check on its way out, under the same `.decide` mutex, and releases the generation there — stopping the servers returns the memory instead of leaving it for a next start that may never come. That exit is a signal, not a return: a unit stops with `KillMode=control-group`, so SIGTERM reaches the worker directly and no `atexit`/finalizer runs, which is why the release hangs off a handler (and why the handler refuses to re-enter: a stop delivers that signal more than once, and an inner call re-raising it would kill the process in the middle of the release the outer one is running). A process killed with `SIGKILL` reaches no handler at all; its generation is left for the next creator, which reclaims it exactly as before. Both the create and the attach path unregister the segment from the resource tracker: `SharedMemory.__init__` registers on attach too, and the tracker unlinks what it registered when its process exits.

The decision wraps the existing `_prepare_host_buffer` call and reuses its `populated` flag, so the private path is byte-for-byte what it was. Everything is behind `SGLANG_DIFFUSION_SHARE_PINNED_STORES`, default off, so the existing layerwise tests (which monkeypatch `_shared_storage` / `_pin_in_place`) are unaffected.

## Accuracy Tests

No model-output change: the store is compared byte-for-byte against the weights each process loaded before it is used, and a mismatch falls back to a private allocation. Verified on hardware that owner and follower produce identical output for the same seed, and that all four co-resident instances still complete requests with the pool shared.

## Speed Tests and Profiling

No speed claim. This is a host-memory capacity change.

Same build, same GPUs, same payload, no other server resident; one instance per GPU, started one at a time, `Pss` read 30 s after `/health` returns. The only variable is `SGLANG_DIFFUSION_SHARE_PINNED_STORES`.

The build is this change plus the LoRA-merge-cache read-only change from #43261. That one is separate and this PR does not depend on it, but it is what makes the 62 GiB merged-weight cache shared; on a checkout of this PR alone the cache is privately mapped per process, both columns below are ~43 GiB higher per instance (measured in #43261), and the per-instance difference between the columns is the 108.5 GiB pinned store either way.

| N | sharing off | host added by this instance | sharing on | host added by this instance |
|---|---|---|---|---|
| 1 | 197.32 GiB | +126 GiB | 197.52 GiB | +127 GiB |
| 2 | 158.61 GiB | +123 GiB | 106.56 GiB | **+18 GiB** |
| 3 | — | — | 76.24 GiB | **+12 GiB** |
| 4 | — | — | **60.93 GiB** | **+18 GiB** |

(measured before the last-exit release landed; the numbers are the same store either way)

With sharing off the second instance adds a second 108.5 GiB store of its own; the run was stopped there rather than driving the host into reclaim. N=4 for that column is the measured per-instance cost extrapolated (~496 GiB), not a run — it does not fit next to a 498 GiB machine's other users.

With sharing on, four instances reach steady state at 54.53 / 60.76 / 60.74 / 60.83 GiB Pss, `/dev/shm` stays at 108 GiB with 129 segments, every process reports `deleted=0`, and the host still has 211 GiB available — 175 GiB total for four servers that previously needed ~496 GiB. All four pools log `follower, created 0, joined 2 / 50 / 27, refused 0`.

Lifecycle checks on the same build: killing the owner leaves the followers serving (`/dev/shm` unchanged, a real request still completes); restarting it logs `follower` and re-attaches the same segment with zero reclaims.

## Known limitations

- **Only layers the pin planner pinned are shared.** The join happens inside the `pin_this_layer` branch, and `main`'s host budget is derived from what is *available* when the plan is made. A follower on an already-busy host is therefore told to demote part of a component to `pageable`, and those layers get a private copy instead of joining the store. Measured with another server holding 108 GiB of pinned memory: the follower saw 77.8 GiB available and hosted 38 of 50 text-encoder layers pageable (35.99 GB private, against 1.45 GB when the host is quiet). Attaching to a store that is already registered should not be charged against the local pin budget; that is a follow-up, and until it lands the saving holds on a host that is otherwise quiet.
- The store key is structural (`component:layer_idx:dtype:total_numel`) — the manager cannot see checkpoint or LoRA identity, so correctness rests on the byte comparison and a mismatch is a silent private allocation rather than an error.
- Opt-in and default off; no default-on claim.
- A clean exit is released by the last participant to leave. A unit stop is released from a signal handler: systemd stops with `KillMode=control-group`, so SIGTERM reaches the worker directly and no exit hook would run. Only a process killed with `SIGKILL` reaches neither, and its generation stays until the next creator reclaims it — both paths are covered by the CPU test.
- Benefit is specific to **discrete** GPUs. Where `device_shares_host_memory()` is true (GB10, Jetson), `main` keeps every layer on its mapping and there is no pinned copy to share, so the gain is zero.
- No end-to-end test on a device — see below.
