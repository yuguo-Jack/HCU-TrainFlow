# [Fix] watermark: Append accepted tokens to history on fused EAGLE verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44199) · state: open · merged: False

## Original PR description

## Problem

#41175 added a fused verify-commit path to `run_eagle_verify`. On CUDA, the non-idle path now always takes the fused branch — but the watermark `append_speculative` call from #37577 was left only in the non-fused branch. As a result, on main today:

- the watermark context ring never advances past the prompt tail;
- verify rows hash stale contexts;
- **watermarked EAGLE/EAGLE3/NEXTN output is undetectable**.

## Fix

Call `append_speculative` on both branches so accepted tokens always enter the watermark history.

## Evidence

Qwen3-8B, H200, 40 essay prompts × 512 tokens, temperature 1.0, top-p 0.95, detection with the in-tree detector:

| Configuration | Requests with p < 1e-3 | Median per-request z | Accept length |
| --- | --- | --- | --- |
| No speculation | 40/40 | 8.09 | — |
| EAGLE3 3/1/4, before this fix | **0/40** | **0.66** | 2.250 |
| EAGLE3 3/1/4, with this fix | 40/40 | 7.95 | 2.261 |
| EAGLE3 tree 5/8/32, with this fix | 40/40 | 8.23 | 3.719 |

Unwatermarked control arms: 0–1 of 40 requests at p < 1e-3, median z 0.09–0.55. Accept length is unchanged by the fix (ON 2.261 vs OFF 2.238).

CUDA watermark selector/state suites: 22 passed. Endpoint e2e `test_watermark.py`: 5 passed. Detection ON/OFF control also verified with watermark enabled at the server but disabled per request.

No committed regression test: a meaningful guard needs an EAGLE-capable serve, and the endpoint e2e's Qwen2.5-0.5B has no draft model — happy to add one if reviewers want a specific harness for it.

Found while building DSPARK watermark support (follow-up PR).
