# [Feat] elastic-ep: Runtime scale-down that retires EP ranks via Mooncake deactivate_ranks

[Upstream PR](https://github.com/sgl-project/sglang/pull/33111) · state: open · merged: False

## Original PR description

## Motivation

Elastic EP today grows a serving deployment and recovers a rank that has dropped out.
This PR adds the third direction: **retiring live ranks from a deployment that keeps
serving**. Both directions are expressed on the same `active_ranks` bitmask, so a shrink
and a later grow are the same mask operation viewed from opposite ends, and a deployment
can move freely between widths under an orchestrator's control.

The driving use case is a Kubernetes reconciler reclaiming GPUs from an underloaded
deployment (Dynamo DEP #13121, RFC #35376, raised by @julienmancuso). That needs three
things from a shrink: in flight requests finish, the interruption is small enough not to
read as an outage, and the orchestrator gets a positive "this rank may now be terminated"
signal rather than having to infer it from a process exit. All three are addressed here.

On DeepSeek-V3-Lite FP8, one H100 node, 8 concurrent streams, a 4 → 3 shrink keeps
serving throughout at **8.9 ms p50 inter token latency, a 13 ms peak stall across the
reconfiguration, and a 4.1 s settle to the new width**.

## Modifications

### A scale down state machine on the active_ranks mask

`elastic_ep/scale_down_state.py` adds a per rank FSM driving
`PREPARE → DRAIN → NIXL_RETIRE → FLIP_MASK`, then `RECONFIG → COMPLETE` on a survivor and
`LOCAL_CLEANUP → EXIT` on a retiree. The tick runs at the top of the event loops, ahead of
`recv_requests`, so every rank issues its control broadcasts from the same point in the
iteration.

The side effects each transition needs sit beside the machine rather than in the runner.
`scale_down_driver.py` maps transitions onto those effects and takes the two runner owned
tails as callables, `scale_down_finalizer.py` holds the survivor rebuild sequence and
returns what it wants written, and `expert_map_repair.py` owns the map truncation and orphan
repair. `model_runner.py` constructs them, delegates, and applies the three fields the
finalizer hands back.

Both cohort barriers rendezvous over the global TCPStore and are polled across ticks, so a
rank waiting on one keeps servicing `mlp_sync` for peers that have not arrived yet. Host
agreement is all the barrier owes — the quiesce that protects the retiree is a local CUDA
synchronize before the NIXL disconnect.

Leaving `DRAIN` is a cohort decision carried on the `mlp_sync` the cohort already runs each
iteration: ranks cross only on a unanimous answer, which every rank reads in the same
iteration, and the batch step gate closes at that crossing. The shrink path
expert location broadcast is dropped with it — every survivor derives the same map by
applying the same deterministic repair to an agreed pre shrink map, so it already holds
what the broadcast would have sent.

### Requests in flight finish before their rank leaves

A retiring rank withholds its drain barrier arrival until its own queues are empty.
Survivors keep serving while they wait, and `/scale_elastic_ep` has already closed the
tokenizer admission gate for the departing slots, so their queues only drain while the
slots that are staying keep taking new work; `elastic_ep_scale_timeout` bounds it. Gating
server wide instead would let one long decode pinned to a retiring rank block admissions
everywhere for as long as it runs.
The idleness predicate is cached on the `ModelRunner` when the scheduler first supplies it,
so the forward path entry point observes the same gate as the scheduler path one. The
barrier recheck is a non blocking probe throttled by wall clock, which keeps a rank that is
still decoding at full decode speed while it waits.

One consequence of a resize completing a scatter call short. A survivor that was slow to
reply is still owed, and that reply used to land in the next call's result bucket, both
corrupting it and able to complete it early. The finished call now holds its bucket open
briefly, under the same lock the request is sent from, so no later call's bucket exists yet
and anything arriving is stale by construction. A reply slower than that window still
escapes; closing it needs the reply to name the call it answers, which none of these
payloads carry today.

### Ranks leave the group deliberately

A retiring rank proposes its own removal through `mooncake.pg.deactivate_ranks` as its
final Mooncake call, so the coordinator drops it on request instead of discovering its
absence through link timeouts. This takes a ~10 s per peer fault timeout out of every
shrink and brings reconfiguration from 11–12 s down to under 2 s. Only the retiree
proposes, and only for itself, which keeps it a full participant in the barriers it is
still inside. Because a deliberate departure raises no fault, the device is quiesced before
the NIXL disconnect and survivors wait on `get_peer_state` before any post flip collective.

The retiree then tears down its backends explicitly before exiting, so Mooncake's
destructors run against a live CUDA driver.

### The expert map and its weights follow the slots

`physical_to_logical_map` moves over the TCPStore, one inbox per reader, emptied as it is
read — freshness is the key's absence between rounds, which stays correct across a cohort
that changes width on every call. A joiner clears its inbox before announcing itself, so
only this scale's map can be read from its slot.

Relabelling a physical slot is only half the job, and both directions relabel: a shrink
repairs logical experts whose replicas lived on retiring ranks onto surviving slots
(262–531 experts per shrink at these widths), and a grow stamps real logical ids on
appended slots. Each side reloads its own weights from the backup client or disk once the
new metadata is installed, against the authoritative map it receives rather than the layout
it computed at startup. Slots the p2p could not source are left for that reload and
reported, rather than being published with a temp buffer's contents.

`EPLBManager.reshuffle_for_scale` then runs a load aware rebalance from the scale
finalizer, since a shrink concentrates the same logical experts onto fewer ranks. Its
go/no-go prechecks are decided by a TCPStore cohort vote rather than a device all-reduce,
and any post scale layout is sized from the installed metadata rather than launch time
args. Periodic EPLB is rearmed for the post shrink phase so a shrunk deployment keeps
adapting.

### Decode CUDA graphs survive a shrink

This is where the latency numbers come from — elastic EP previously ran all-eager, measured
at 7.3x decode cost.

A captured decode graph replays against the storage it recorded, so a scale must rewrite
the dispatch tensors in place rather than reallocate them. Three reads reach the expert map
from inside a captured graph and only one has a shape a scale moves:
`partial_logical_to_all_physical_map`, indexed `[topk_ids, chosen_dispatch_index]`, whose
last dim is the replica fan out. Padding that fan out to a width `--max-ep-size` fixes, and
adopting a rescaled map through `adopt_scaled_in_place` (`copy_` into the existing tensors,
the in place discipline `update()` already uses for EPLB rebalance), makes a shrink a no-op
for the graph.

The DP num token buffers a graph gathers over are held at the same pool ceiling
(`dp_capacity_for`), with the fill writing only the slots that have a live rank behind them
and zeroing the rest, so a retired slot reads as a rank contributing no tokens. Retirees are
the contiguous tail, and the MAX_LEN layout used inside graphs strides by a fixed per rank
length, so no surviving rank's offset moves.

In place adoption is what keeps a replay *valid* across the width change, but it does not
by itself make the graph current: the post shrink `reshuffle_for_scale` reinstalls the
expert layout, and `num_physical_experts` is captured as a scalar. So the shrink rebuilds
the decode graphs too, after the reshuffle, so the capture sees the layout that will
actually serve. The finalizer requests the rebuild and `tick_elastic_scale` runs it, at the
top of the event loop: with `max_ep_size == tp_size` the finalizer itself runs at the tail
of `forward()`, where dropping the graph memory pool would invalidate the output that
forward is about to return. This is gated separately from the grow side recapture, which requires
`max_ep_size > tp_size`; a shrink only cohort runs `max_ep_size == tp_size` and is exactly
the configuration that keeps its graphs, so it needs the rebuild most.

With graphs live, the drain barrier probes rather than waiting in place (`keep_serving`),
which is what its module docstring already described: every peer is still serving there,
and a zero width probe folds within the tick when they are already posted. The NIXL fold
keeps its window — past `on_depart_drain` the peers have gated their batch step, so waiting
there costs no tokens and is what makes the same tick crossing `_advance` relies on true.

### A grow reports done only once the joiner can serve

Everything that lets a joiner take part in an a2a — KV-cache allocation, NIXL buffer
creation, the prefill shape DeepGEMM JIT that only compiles once a kernel runs — happens
after its `ModelRunner.__init__`, and measures 37 s quiet, up to 68 s under load. A grow
therefore commits into a `warming_up` phase and reports done only once a forward has
returned at the new width, which proves the joiner took part because dispatch is
collective. An idle cohort has no forward coming, so the window is bounded by a deadline;
grows never close the admission gate, so traffic keeps flowing and settles it promptly.

A grow that crosses the launch width needs both a `recover_ranks` batch and a fresh join,
and `_activate` takes one `include_subgroups` flag per batch. The tokenizer manager now
derives both stages itself against the launch width, holding `pending_ep_size` at the
caller's target so a poller only ever sees the finished width reported as finished. The
second stage goes out on the first's completion, which the schedulers already withhold
until the grow leaves `warming_up`.

A grow that stays below the launch width is different, and goes direct. A recover joiner
covers `[ep_join_rank_offset, ep_join_rank_offset + tp_size)` and sizes its expert map to
that upper bound, so only a target short of that span needs an intermediate; one booted at
exactly the target does not, and that is the common case. Since nothing on the survivor
side could tell the two apart, the joiner now announces its width to the store, in its own
key space rather than the scale cohort's. It announces straight after
`init_torch_distributed`, where the store first exists, because the alternative point runs
after the weights load and publishes long after the grow it has to inform.

The timing dictates the rest. The joiner is a separate process launched alongside the
scale request and cannot announce anything until it is up, measured 11s after the request
arrived and dominated by interpreter and torch import. A scheduler cannot block that long,
so it answers from a single store read: it rejects with `retry_when_joiner_announces` while
nobody has spoken and with `required_ep_size` once it knows the joiner is wider than the
target, and `_scale_elastic_ep_locked` resends on an `asyncio.sleep` until the width is
known. Every reject lands before `request_scale`, so a resend costs a round trip rather
than risking a half committed scale, and a timeout falls back to the launch width so the
previous behaviour is the floor. Neither default is safe without an announce, which is why
the wait exists at all: going direct kills a joiner wider than the target at the cohort
barrier, while assuming the launch width asks a narrower one to fill slots it has no ranks
for.

The cohort admit vote is scoped to survivors, who all count in the same width namespace,
and runs under a deadline of its own with a retry. The shrink path derives its agreement
from the retire barrier and skips the vote entirely, which keeps it out of the forward
path.

Three rendezvous read cohort state rather than lazily built local state, so every rank
answers them the same way: barrier cycle ids are seeded from the store at admission, the
NIXL retire barrier keys off
the configured backend rather than whether this rank has built its a2a buffer, and the
survivor side disconnect names only the retirees it actually connected to.

### The active ranks bitmap is converged collectively

Mooncake surfaces a transient only on the ranks whose bitmap still lags the `active_ranks`
flip, so convergence is driven from the scale finalizer as a collective: each round every
rank attempts one WORLD all-reduce and the cohort agrees the outcome over the TCPStore, so
every rank issues the same number of collectives. The round schedule is a fixed table
rather than a wall clock deadline, so two ranks reading the clock either side of one still
agree. The probe tensor is a throwaway, so reattempting is data safe, and the hot path
takes a single all-reduce.

An unplanned rank loss has no finalizer ahead of it, so nothing converges the bitmap before
the hot path resumes: the coordinator drops the dead peer on its own heartbeat timeout, and
the `mlp_sync` gather is the first collective a tick issues. A gather landing inside that
window is refused as inactive. The refusal is a precondition check raised before the
collective is posted, so no peer can have completed a gather this rank never sent, which
makes it safe to wait out where retrying a posted collective would not be. The gather now
retries only on that refusal, bounded well under the watchdog so a view that never settles
still fails loudly rather than parking the cohort. Other backends re raise unchanged.

### The fault detector stands down while the width moves

Upstream checks for faulted ranks at the tail of every forward by comparing the current
`active_ranks` against the previous one. Both tensors live on the device, so the comparison
synchronizes the stream. While a resize is in flight that sync can land on a collective a
departing or arriving peer will never post, and the cohort sees a watchdog timeout rather
than a slow tick. The fault rebalance and the NIXL mask poll both stand down until the
resize commits, which is the rule the mask poll already applied to shrinks, and the periodic
EPLB rebalance does the same so its WORLD broadcast cannot interleave with a width change.
Detection resumes on the first forward after commit, so a real fault is deferred by one
resize rather than missed.

This narrows the window rather than closing it. A few forwards still run at the new width
while a joiner compiles its first a2a kernels, because `commit_scale` clears the pending
width before the warmup phase ends. Suppressing the comparison through warmup is not the
fix: the same comparison is what triggers the post scale expert redistribution, so standing
down that long delays the rebalance and costs accuracy. Making the comparison not
synchronize needs a host side mirror that tracks Mooncake's own writes to the mask, which is
a change to upstream's fault path and is left as a follow up.

### Orchestrator facing lifecycle

- `--elastic-ep-retiree-lifecycle {self_exit,external}` selects who ends the retiree
  process. `self_exit` is the default and unchanged; `external` parks the retiree after it
  quiesces, deactivates and tears down, for an orchestrator to terminate.
- `/is_scaling_elastic_ep` reports `safe_to_terminate_ranks`, which stays empty until the
  survivors commit — a positive signal rather than an inference from a process exit.
- `/scale_elastic_ep` accepts an optional `operation_id`, echoes it, and mirrors it in
  `/is_scaling_elastic_ep` alongside the phase and `safe_to_terminate_ranks`. It is a
  correlation tag only, so the boundary is worth stating: it is not an idempotency key.
  A retried request carrying an `operation_id` already in flight is refused like any
  other concurrent resize, rather than returning or resuming the original, and the
  refusal carries `pending_ep_size` and `scale_phase` so a caller can tell a duplicate
  from a real conflict. Reusing an id with a different target is not rejected on the id.
  Joining ranks are not bound to it either. What a later resize checks is the width: the
  cohort record a joiner registers carries `target_ep_size`, and a survivor refuses the
  join when that does not match the pending target. So a stale joiner aimed at a
  different width is caught, and one aimed at the same width is not distinguished from a
  fresh one. Idempotency and join correlation identity are tracked in RFC #35376, where
  a topology generation can carry them across endpoints.
- Scale phase transitions are timestamped at `mark_phase`, the single choke point for every
  transition, so the retiring and reconfiguring phases can be attributed separately from
  the ungated drain.

### Mooncake a2a backend

The cohort barriers rendezvous over the global TCPStore, which makes the store a
requirement of the scale path itself; its creation gate now also keys off the distributed
backend, which is what decides whether the elastic FSM can run. The NIXL lanes already
satisfied the first clause, so nothing there moves.
`SGLANG_MOONCAKE_EP_BF16_DISPATCH` gives the mooncake dispatcher the same BF16 escape the
nixl dispatcher already has, defaulted off so fp8 deployments are untouched.

The rest of the shrink path needed no change for a non NIXL dispatcher: the retire barrier
keys off the a2a backend and skips, the survivor side peer disconnect no-ops without a NIXL
buffer, and the Mooncake dispatch buffer refreshes membership in place through
`update_ep_member`, which `retire_ranks` already drives.

### Compatibility

- A shrink requires a Mooncake build providing `mooncake.pg.deactivate_ranks`. Checked when
  a shrink is requested, not at init, so a Mooncake fault tolerance deployment that never
  retires a rank is not held to it and keeps booting as before. The stock 0.3.13 wheel the
  nightly image ships carries it, so no Mooncake patch is needed.
- A shrink also requires `attn_tp_size == 1` and refuses otherwise, because it reports
  retirees as DP slots (`slot_offset`/`slot_count`, `retired_ranks`, `remove_elastic_workers`
  all index workers by EP rank), which holds only while one DP slot is one EP rank. Once DP
  moves to logical replica units (`attn_tp_size > 1`, #33728) those ranges need converting
  and a shrink has to retire whole replicas; the guard makes that a clean rejection rather
  than a wrong set of deactivated workers.
- Resizing a degraded topology is refused rather than attempted. A bare fault does not
  lower `effective_ep_size`, and every cohort rendezvous sizes itself from that width, so a
  resize issued while a rank inside the width is inactive would wait on a participant that
  cannot arrive. `/scale_elastic_ep` rejects it up front, naming the inactive ranks, before
  any barrier is posted. That holds in both directions, so an `8 -> 4` whose retiring
  suffix is already short and an append grow from a degraded cohort fail the same way.
  Replacing failed capacity is the recovery path, meaning grow into the retired slots below
  the launch width, not shrink then regrow. Recovery at a nonzero launch offset, and
  retiring a set that is not the high rank suffix, both remain out of scope here.
- Bare fault recovery at launch offset 0 readmits the subgroups now, which earlier
  revisions of this PR left out of scope. A recovered rank used to get the `active_ranks`
  mask flip in every parallel group while rejoining the Mooncake process groups for WORLD
  only, so `EPBuffer.update_ep_member` all-gathered a cohort wide list into a `moe_ep`
  group that still counted survivors and raised `Tensor list size must match active group
  size`. `try_recover_faulted_ranks` joins WORLD, its sub-PGs and every live parallel
  group, which is the same set `_recover_parallel_groups` readmits a peer to. The reason
  that was held back was partial regrow, whose joiner is already active and which
  deadlocked between the survivors' `tp_cpu_group` request broadcast and the joiner's
  WORLD all-gather: partial regrow now grows direct to the target when the joiner covers
  it, so the two no longer trade off. The end to end lanes still drive the grow over NIXL,
  since only Mooncake builds that buffer and the grow collectives are NIXL only.
- The other Mooncake wide restrictions this PR adds (rejecting `SGLANG_SYNC_TOKEN_IDS_ACROSS_TP`
  and `--enable-symm-mem`, forcing `SGLANG_USE_MESSAGE_QUEUE_BROADCASTER=False`) apply only
  when `--max-ep-size` is set, which is the opt in for a runtime scalable deployment. A
  fault tolerance only deployment logs a warning instead of failing to start, and in
  exchange it cannot shrink: `/scale_elastic_ep` refuses a scale down without
  `--max-ep-size` rather than running it on the relaxed configuration those warnings
  allowed through.
- Graph handling covers the shrink direction two ways, and composes with the decode graph
  recapture added for grow in #33723: all four of upstream's `TestElasticScaleUp*CudaGraph`
  classes pass on this tree, 3/3 each.

## Accuracy Tests

GSM8K is run before and after the scale in every correctness lane and asserted for parity.

| Shape | pre | post |
|---|---|---|
| 4 → 3, one node, NIXL a2a | 65.62% | 65.62% |
| 8 → 6, two nodes | 67.19% | 68.75% |
| 8 → 4, two nodes, Mooncake a2a | 65.62% | 70.31% |

Across every lane in the sweep the pre scale scores span 64.84–67.19% and the post scale
scores 64.06–68.75%, so the shrink sits inside the run to run spread of the evaluation
itself at this sample size.

`TestUnsourcedSlotsAreNotPublished` covers the weight reload contract directly: it asserts
that slots the p2p could not source are reported and left for the reload rather than
published.

## Speed Tests and Profiling

DeepSeek-V3-Lite FP8 on H100, decode graphs on against the all-eager mode elastic EP
previously used, median of 3 iterations per arm:

| | 4 → 3, one node, 8 streams | 8 → 4, two nodes, 16 streams |
|---|---|---|
| inter token latency p50 | 64.3 ms → **8.9 ms** | 65.6 ms → **8.5 ms** |
| peak stall over the shrink | 5075 ms → **13 ms** | 379 ms → **19 ms** |
| settle to the new width | 37.1 s → **4.1 s** | 34.0 s → **3.5 s** |

The 8 → 4 shape puts every retiree on the worker node, so the drain crosses the fabric
rather than resolving in one host's IPC. The lane that shrinks while a pinned decode drains
settles in 6.1 s with graphs against 69.3 s eager, since a drain bound shrink is bounded by
decode speed.

Graceful deactivation accounts for the reconfiguration itself falling from 11–12 s to under
2 s.

### What it does

A partial regrow now goes direct. `2 -> 3` with launch 4 is one joiner, not one per retired

wrong, so thank you for the push. The docstring blamed a `ZeroDivisionError` on an empty
replica list and `_fair_choices` is never reached. The real constraint is that a recover
joiner covers `[ep_join_rank_offset, ep_join_rank_offset + tp_size)` and sizes its expert
map to that upper bound. So only a target short of that span needs an intermediate. A joiner
booted at exactly the target never did, and that is the common case.

### Why it was not already direct

Nothing on the survivor side could tell those two joiners apart. The joiner now announces
its width to the store, in its own key space rather than the scale cohort's, since survivors
read that one to decide whether an append grow has a cohort waiting and a recover joiner
parked at the current width would answer for an unrelated grow.

The timing is what shaped the design, and it is the part worth your eye. The joiner is a
separate process the operator launches alongside the scale request, and it cannot announce
anything until it is up. Measured 11s after the request arrived, dominated by interpreter
and torch import, so no placement inside the joiner wins that race. A scheduler cannot block
that long either.

So the schedulers never wait. Each answers from a single store read: reject with
`retry_when_joiner_announces` while nobody has spoken, reject with `required_ep_size` once
the joiner is known to be wider than the target. `_scale_elastic_ep_locked` resends on an
`asyncio.sleep` until the width is known, which puts the only long wait in async code. Every
reject lands before `request_scale`, so a resend costs a round trip and never a half
committed scale.

There is no safe default without an announce, which is why there is a wait rather than a
guess. Going direct kills a joiner wider than the target at the cohort barrier. Assuming the
launch width asks a narrower one to fill slots it has no ranks for. I measured both.

Only grows landing strictly below the launch width. A recover slot is below it by definition
and a joiner spans at most up to it, so a grow that lands there serves any joiner. Shrinks,
and grows at or above the launch width, take no new path. A timeout falls back to the launch
width, so the previous behaviour is the floor.

difference, which only holds while the requested width is the larger one. A joiner regrowing

whenever the requested width is at least the base, which is every path that existed before.
