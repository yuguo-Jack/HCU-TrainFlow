# [Quant] Repack NVFP4/MXFP4 Marlin MoE experts in place (peak load memory 1.56 -> 0.39 GiB per layer)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43419) · state: open · merged: False

## Original PR description

## Motivation

`prepare_moe_nvfp4_layer_for_marlin` and `prepare_moe_mxfp4_layer_for_marlin` repack every expert into a Python list and then `torch.stack` it, while the layer's original packed weight is still alive. For one layer that is three copies of the expert weights at the peak. On a model whose weights nearly fill the GPU this transient is what fails: loading `RedHatAI/Qwen3.8-Flash-Next-NVFP4` through Marlin on a 96 GB RTX PRO 6000 ran out of memory during weight processing. With this change the same configuration loads.

The Marlin layout has exactly the same byte count as the packed FP4 checkpoint layout (`size_n * size_k / 2` bytes per expert), so the layer's own weight can hold the repacked experts.

## Modifications

- `_repack_moe_fp4_weight_for_marlin` gains `in_place: bool = False`. With `in_place=True` each expert is repacked into the input tensor's own storage, one expert at a time, and the result is returned as a Marlin-shaped view of that storage. Without it, the experts are written into one preallocated tensor instead of list + stack (two copies at the peak instead of three).
- `prepare_moe_nvfp4_layer_for_marlin` and `prepare_moe_mxfp4_layer_for_marlin` pass `in_place=True`. Both replace the layer's weight parameter with the result and never read the pre-repack tensor again. When padding is applied the input is already a fresh padded copy.
- Direct callers keep the old out-of-place behaviour. `test_mxfp4_tp8_gate_decode` relies on this: it reuses its input for the reference.
- New regression test `test_prepare_moe_nvfp4_marlin_repacks_experts_in_place`. It checks three things: the prepared weights are bit-identical to the out-of-place repack, they reuse the checkpoint storage, and the peak memory during preparation stays below one copy of the experts. It fails on `main` (new storage is allocated) and passes with this change.

## Accuracy Tests

The weights are bit-identical (`torch.equal`) to the previous implementation, so outputs are unchanged.

`test/registered/kernels/ops/moe/test_moe_wna16_marlin.py` on an RTX PRO 6000 (SM120), using the `nightly-dev-cu13-20261009-265efe5e` image with this branch mounted: 5 passed, 31 skipped. The skips are the SM80/SM90-only cases.

## Speed Tests and Profiling

The test used one Qwen3.8-Flash-Next-shaped routed-expert layer: 512 experts, hidden 2560, intermediate 640, 1.17 GiB of packed NVFP4 weights. `torch.cuda.max_memory_allocated()` above the pre-call baseline, during `prepare_moe_nvfp4_layer_for_marlin`:

| | peak during preparation | time |
|---|---|---|
| main | 1.564 GiB | 6.52 s |
| this PR | 0.391 GiB | 6.51 s |

What remains of the peak is the scale permutation.
