# [Doc] [NPU] cookbook: add NPU (A3 series) deployment scenarios for Qwen3.6

[Upstream PR](https://github.com/sgl-project/sglang/pull/38678) · state: closed · merged: True

## Original PR description

## Summary

Add BF16 deployment scenarios for Qwen3.6-27B and Qwen3.6-35B-A3B on Ascend Atlas 800I A3, with prefill and decode on the same node (task: Ascend/sglang#1219).

- Add an `A3 (NPU)` hardware option with one/two-card selection (TP2/TP4), BF16 checkpoints for both models, the Ascend attention backend, and optional NEXTN speculative decoding.
- Link environment setup to the maintained Ascend installation and quickstart guides. Explain checkpoint downloads, runtime memory overhead, and multimodal flags.
- Include 12 published BF16 scenario references, each linked to its full configuration and benchmark recipe. Their TPOT values describe those upstream recipes, not measurements of the generator's baseline command.
- Leave NPU Mamba cache selection to the installed SGLang version and link the complete Ascend prefix-cache recipes.
- Resolve the conflict with main while preserving RTX Spark and existing non-NPU command behavior.

## Validation

- All 292 valid generator combinations passed: H100 48, H200 48, B200 72, B300 72, Xeon 16, RTX Spark 4, Ascend A3 32. Existing hardware commands and retained Ascend BF16 commands are unchanged.
- Full JSX compilation with esbuild and cookbook config check passed.
- `mint broken-links`, `mint validate`, and `git diff --check` passed.

## Original hardware verification

The original PR and [verification comment](https://github.com/sgl-project/sglang/pull/38678#issuecomment-5603682883) reported tests on Atlas 800I A3 (one card / two 64 GB dies), CANN 9.0.0, SGLang v0.5.16, torch 2.10.0, torch_npu 2.10.0, and sgl-kernel-npu 2026.9.x:

- Qwen3.6-27B BF16: startup on TP1 and TP2, valid factual/math responses, and TP2 TPOT 31.2 ms with random in3500/out1500 and max-concurrency 54.
- Qwen3.6-35B-A3B BF16: startup on TP2, valid factual/math responses, and TPOT 13.7 ms with random in3500/out256 and concurrency 3.
- GSM8K greedy chat evaluation, 250 questions: both BF16 models scored 223/250 (89.2%).

These are historical hardware results. This documentation follow-up did not rerun inference, accuracy, or performance, and those results do not validate every generator combination. The older 2026.05.01.post3 kernel failed with TP2 split GDN heads; use a version-matched stack rather than assuming arbitrary wheel versions are compatible.

## Additional on-hardware verification (Qwen3.6-35B-A3B + accuracy)

Completed the remaining verification items from Ascend/sglang#1219 on the same Atlas 800I A3 (1 card / 2 dies, CANN 9.0.0, SGLang v0.5.16):

**Qwen3.6-35B-A3B, 1×A3 PD mixed (TP2, BF16):**
- Service starts cleanly, no hangs/abnormal logs; `/generate` and `/v1/chat/completions` return valid responses (factual + math spot checks correct).
- `bench_serving` (random, in3500/out256, conc 3): **TPOT 13.7 ms**, 0.75 req/s — well inside the 50 ms class of the documented best-practice scenarios.

**Accuracy (GSM8K, 5-shot-less chat eval, 250-problem sample, greedy):**
- Qwen3.6-27B BF16 TP2: **89.2%** (223/250)
- Qwen3.6-35B-A3B BF16 TP2: **89.2%** (223/250)

Both models show normal accuracy on the deployment stack — no quantization/deployment-induced degradation (BF16 checkpoints).

Note: verification used the pip-installed stack (torch 2.10.0 + torch_npu 2.10.0 + sgl-kernel-npu 2026.9.x + CANN 9.0.0). The reported TP2 tests used the newer kernel stack because the older 2026.05.01.post3 wheel failed with split GDN heads.
