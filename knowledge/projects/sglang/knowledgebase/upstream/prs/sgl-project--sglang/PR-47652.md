# [Fix] disaggregation: Ignore a late STAGING_REQ for an already-scattered staging chunk

[Upstream PR](https://github.com/sgl-project/sglang/pull/47652) · state: closed · merged: True

## Original PR description

## Motivation

`TestDisaggregationStagingRadixPrefillLargerTP` (in `test_disaggregation_different_tp.py`, 8-gpu-h20) can stall for 300s. On #47638's run, 17 of 200 requests hung, 12 of them timing out with `timed out after 300.0s in KVPoll.WaitingForInput`, and gsm8k latency was 302s instead of the usual ~3s. Decode logged `not complete 300s after all-ranks Success (a scatter never arrived)` and `releasing unscattered staging allocation`. The code under test was identical to main, which has passed this test before, so this is an intermittent race.

The race:

1. With prefill TP > decode TP, each decode rank has several prefill writers per chunk. Every writer sends a `STAGING_REQ` for each chunk. Decode dedups these through the chunk's live allocation in `chunk_staging_infos`, and broadcasts each `STAGING_RSP` to all of them.
2. Writers send `STAGING_REQ` from the scheduler thread over a prefetch socket, and `CHUNK_READY` from the transfer worker over a different socket. Across those two sockets, decode gets no ordering guarantee.
3. When every writer's `CHUNK_READY` arrives, decode scatters the chunk and resets its slot to `(-1, -1, ...)`. A writer's own `STAGING_REQ` that lands after this then looks new. Decode allocates a fresh slot that no one will ever scatter, and the room never completes.
4. Because the staging buffer is a ring, that pinned slot also blocks prefill writes for every later room until the room times out.

The window is widest right after start, when the prefetch sockets are still connecting, and for prefill radix hits, whose forward is short. All 5 rooms behind the stall came from the first ~80ms burst of the test, and all were radix hits.

## Modifications

- When a chunk scatters, mark its slot with a new `StagingAllocator.CHUNK_SCATTERED` sentinel instead of the free value.
- `handle_staging_req` drops a request for a chunk marked scattered. That writer already has its offset from the broadcast `STAGING_RSP` and has written the chunk, so no reply is needed.
- Readers that treat `info[0] >= 0` as outstanding are unaffected. The fix sits in the shared handler, so Mooncake and NIXL are both covered.

## Accuracy Tests

Not affected: data transferred to a chunk that was already scattered is unchanged.

## Testing

- New unit test `test_late_staging_req_after_scatter_does_not_reallocate` in `test_disaggregation_wire.py`: scatter a chunk, then deliver a late `STAGING_REQ` for it. It fails before the fix, with the allocator called once, and passes after.
- `test/registered/unit/disaggregation/` gives the same results with and without the fix, apart from the new test.
