# [Feat] [NVIDIA] deepseek-v4: Add deployed V4.1 SM80/A100 adaptation and opt-in optimizations

[Upstream PR](https://github.com/sgl-project/sglang/pull/44640) · state: open · merged: False

## Original PR description

## Summary

This change adds the DeepSeek-V4.1 A100/SM80 adaptation and single-request optimizations used in a real 8×A100-SXM4-80GB, TP8 deployment. The deployment has been independently rechecked on 2026-10-16: `/health` and `/v1/models` returned HTTP 200 with a 1,000,000-token model limit, and a minimal chat request returned `323` for `17 × 19` (HTTP 200, normal stop, approximately 0.212 seconds). This is not an unexecuted proof of concept.

The submitted source also includes subsequent cleanup of environment access, kernel inventory and device-specific stream/reduction policy. That cleanup has CPU regression coverage but has not yet been independently confirmed against the currently running server's source revision.

- Software FP8/FP4 KV and Engram byte decoding; paged sparse-attention runtime adapter.
- BF16/MXFP4 Marlin loading, FP8 group32 support and logical-shape-preserving K-tail padding.
- Batch-one CUDA graphs, indexer finish, sparse-attention tiling/merge/word loads, and mHC fast paths.
- Batched decode: full-graph capture for a configured `bs` list and routing of 2..N-row decode onto the tiled split-K attention component.
- Conservative architecture/shape gates and default-off tuning controls; generic Marlin changes still require cross-architecture review.

### Multi-concurrency

Two independent `bs=1`-only gates made concurrency slow, and both are addressed:

1. `flash_mla_sm80.py` routed tiled split-K attention only when `tokens == 1`. During decode `tokens` is the running batch size, so batches of 2..8 fell back to the serial sparse-attention kernel (15.5 ms/step at bs=8, 82% of the whole bs=8 step-time increase over bs=1). The gate exists to keep multi-token *prefill* on the serial kernel and that is preserved: only decode-sized counts up to `SGLANG_DSV41_SM80_TILED_MULTIROW_MAX_TOKENS` opt in, and the threshold is now parsed by `_use_tiled_decode`, which treats unset, malformed and non-positive values as "serial".
2. `deepseek_v4_hook.py` required `max_running_requests=1` and decode `bs=[1]`/`max_bs=1` for the full-graph experiment, so concurrency meant disabling CUDA graphs entirely. The graph runner already accepts a `bs` list, so the batch pin is now bypassable with `SGLANG_DSV41_SM80_FULL_GRAPH_MULTI_BS=1`; every other activation guard still runs.

`SGLANG_DSV41_SM80_ALLOW_VISION=1` additionally relaxes the SM80 multimodal fence, which was verified against a rendered test image (427 image tokens, exact text read back).

## Validation

Historical equal-condition 64K-capacity measurements: median decode 126.78 / 111.52 / 104.97 / 104.59 / 103.54 tokens/s at 64 / 4K / 16K / 32K / 65K input tokens, respectively. Each length had three cold-prefix trials with exactly 256 output tokens; 15/15 marker retrievals passed. Approximately +23% over the earlier same-capacity baseline. These are steady-state decode measurements, not end-to-end throughput. The 200 tokens/s target was not met.

The current local cleanup passes 46 CPU AST/policy tests and syntax/whitespace checks. Live health, model listing and minimal generation were independently verified on 2026-10-16 without restarting or modifying the service. Selected disk-source hashes do not match the exact submitted cleanup revision: two match the previous local deployment baseline, while two match neither compared revision. The production container does not contain Git, so its commit cannot be established from Git metadata. Accordingly, this verifies the deployed adaptation's availability, not full GPU certification of every change in the submitted revision.

Batched decode was measured on the same 8×A100 deployment (1M configuration, 256 output tokens, cold prefix, per-token gaps): 8-way aggregate went from 118 to **535 tokens/s** while the single request stayed at 125.7 tokens/s, and 16-way reached **699 tokens/s**. Batch correctness was 8/8 and 16/16 with a unique secret per request, no cross-talk and exact token counts. The routing helper and both opt-in gates now have CPU regression coverage at their boundaries.
