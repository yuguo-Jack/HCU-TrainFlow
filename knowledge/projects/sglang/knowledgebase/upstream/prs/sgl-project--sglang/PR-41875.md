# [NPU] Resolve the DSA KV cache layout from a startup capability 

[Upstream PR](https://github.com/sgl-project/sglang/pull/41875) · state: open · merged: False

## Original PR description

Part of #41866.

## Motivation

This is Phase 0 of #41866: groundwork that the INT8 C8 KV cache for DSA models on Ascend A2/A3 will build on. It adds no new KV dtype and no new flag.

Today the Ascend DSA KV path picks its layout from several separate `is_arch35` and `dtype == torch.float8_e4m3fn` checks. Each one re-derives the same decision, and at least two are wrong:

- **B1.** `--kv-cache-dtype fp8_e4m3` on a non-arch35 NPU (A2/A3) builds an unpacked FP8 pool. The packed-record gates quietly fall through. The DSA sparse attention path still branches on `kv_cache_dtype == float8_e4m3fn` (`ascend_backend.py:1441`) and expects the packed arch35 record. There is no error at startup.
- **B2.** `NPUMLATokenToKVPool.get_kv_layer_ids()` (`memory_pool_npu.py:869-873`) assumes one K and one V entry per layer, followed by the indexer entries. With the packed record, the zero-width V buffers are not transferred. The list then has more entries than `get_contiguous_buf_infos()`. With a compact indexer it is also misordered.

This PR collects the decision into one startup-resolved capability, fixes B1 and B2, and adds a per-rank PD layout check. That check stops a prefill and a decode that resolved different layouts from exchanging raw bytes.

Line numbers below refer to current `main` (86624f14eb) unless noted as "new".

## Modifications

### 1. Capability layer

New file `python/sglang/srt/hardware_backend/npu/kv_capability.py`.

- `PackedQuantKvCapability` is a frozen dataclass with these fields:
  - `kv_cache_dtype`
  - `main_kv_packed`
  - `main_kv_scale_dtype`
  - `indexer_quant`
  - `indexer_kv_dtype`
  - `indexer_scale_dtype`
  - `unsupported_reason`
- `resolve_kv_capability(kv_cache_dtype, is_arch35, soc_name, requested)` is a pure function, easy to unit test. `resolve_npu_kv_capability(dtype, requested)` wraps it with the real SoC probes.
- The resolution matches today's behavior:

  | Case | `main_kv_packed` | Scales | Indexer |
  |---|---|---|---|
  | `float8_e4m3fn` on arch35 | true | FP32 | quantized, FP8 + FP32 scale |
  | Any other dtype (BF16, FP16, `float8_e5m2`) | false | none | stored in the KV dtype, no scale |
  | `float8_e4m3fn` on a non-arch35 NPU | — | — | rejected (item 2) |

The gates that now read the capability:

| Where | Before (main) | After |
|---|---|---|
| `KVCacheConfigurator._build_ascend_mla_kv_pool` | `use_dsa_fp8_kv_cache_storage` (`kv_cache_configurator.py:1907`) | `kv_capability.main_kv_packed`; the capability is passed to the pool |
| `NPUMLATokenToKVPool.__init__` | `dtype == float8_e4m3fn and kv_cache_dim is not None` (`memory_pool_npu.py:639-643`) | `kv_capability.main_kv_packed` |
| `AscendAttnBackend` DSA sparse path | `self.kv_cache_dtype == torch.float8_e4m3fn` (`ascend_backend.py:1441`) | `self.kv_capability.main_kv_packed` |
| DSA indexer sizer | `if dtype != torch.float8_e4m3fn` (`pool_configurator.py:537`) | capability indexer dtypes (item 4) |

`is_npu_arch35()` is still read directly for `use_compact_indexer_layout` and for `allocate_all_layers` in the sizer. Neither is a KV-dtype decision, and neither is changed here. The `dsa_kv_cache_store_fp8` attribute keeps its name for its existing readers (`dsa_backend.py`, `swa_memory_pool.py`, the HiCache host pool).

### 2. B1: reject FP8 KV on non-arch35 NPUs, and make `packed` explicit

**Startup rejection.** `configure_kv_cache_dtype` (new `kv_cache_dtype.py:99-108`) resolves the NPU capability once the final dtype is known. If the result is unsupported, it raises `ValueError`. The error names the requested `--kv-cache-dtype`, the resolved torch dtype, the SoC name and the supported values. For example:

```
--kv-cache-dtype fp8_e4m3 resolves to a torch.float8_e4m3fn KV cache, which is not supported on this NPU (Ascend910B3): FP8 KV cache storage requires an Ascend arch35 NPU. Supported --kv-cache-dtype values on this device: bf16, bfloat16, or auto with a non-FP8 checkpoint.
```

Where the check lives, and what it covers:
- It is in `configure_kv_cache_dtype` rather than the server-args overrides, because the NPU overrides return early.
- It runs on the resolved dtype, so it covers `fp8_e4m3`, `mxfp8`, and `auto` with an FP8 checkpoint.
- The only NPU consumer of an FP8 KV cache is the arch35 DSA sparse path. DeepSeek-V4 is already forced to BF16 on NPU (`arg_groups/overrides.py:864-865`), so its pool never sees `float8_e4m3fn`. No configuration that works today is lost.

**Pool asserts.** The packed-record asserts in `NPUMLATokenToKVPool` are now keyed on the capability instead of the dtype:
- a one-byte element;
- `index_head_dim == 128`;
- `kv_cache_dim == kv_lora_rank + kv_lora_rank // 128 * scale_itemsize + rope * 2`.

`kv_cache_dim` must now be passed whenever the capability says packed. The only constructor (`_build_ascend_mla_kv_pool`) always passes it in that case.

**`packed` flag.** `calculate_mla_kv_cache_dim(*, model_config, kv_cache_dtype, packed)`:
- The packed record is selected only by the caller-passed `packed` (new `kv_cache_configurator.py:3024`); it is no longer inferred from `kv_cache_dtype == float8_e4m3fn` (main `:3006`).
- Inside the packed branch, `itemsize == 1` is an assertion.
- The new helper `is_packed_mla_kv_cache(dtype)` (new `:2969`) is used by the non-NPU callers:
  - `_build_dsa_kv_pool` (which also builds platform-provided DSA pool classes since #35594)
  - hybrid SWA
  - hybrid linear
  - both pool-configurator sizers
- Off NPU the helper keeps `dtype == float8_e4m3fn`, so `float8_e5m2` never selects the packed record. On NPU it returns `capability.main_kv_packed`.

### 3. B2: `get_kv_layer_ids` from the PD buffer entries

`_get_disagg_buffer_entries()` now yields `(buffer, uses_global_slots, layer_id)`:
- K and V entries carry `start_layer..start_layer+layer_num`.
- Index K and index-K-scale entries carry `indexer_layer_ids`.
- The pairs are zipped with `strict=True`.

`get_kv_layer_ids()` is derived from these entries, so it lines up with `get_contiguous_buf_infos()` by construction. `get_contiguous_buf_infos()` and `get_dcp_remote_decode_layout()` unpack the new tuple, and the DCP item-length scaling is unchanged. There is no in-tree caller of this method on the NPU MLA pool today (it was added in #38250), so no current transfer changes. It is fixed now because the INT8 layouts in #41866 would depend on it.

### 4. DSA indexer sizing follows the pool allocation

On NPU, `_compute_dsa_indexer_cell_size` (new `pool_configurator.py:519-552`) computes:

```
index_head_dim * itemsize(indexer_kv_dtype)
  + itemsize(indexer_scale_dtype)   # only if the indexer is quantized
```

This mirrors what `NPUMLATokenToKVPool` allocates. Before, the sizer relied on the GPU FP8 formula and a BF16 special case. The numbers are unchanged:
- arch35 FP8: 132 B per token per indexer layer;
- BF16: 256 B.

### 5. PD KV layout handshake

**Why a new check.** The existing check (#19407) is `CommonKVManager.try_ensure_parallel_info`, `common/conn.py:1142`, compared at `:1176-1184`, fed from `register_to_bootstrap` at `:1375`. It compares one `kv_cache_dtype` string per prefill server, on the decode side. It cannot compare per-rank buffer layouts, and those legitimately differ across ranks under PP, DCP and MHA TP slicing. That check is kept as is.

**What is exchanged.** The new check runs on the per-rank Mooncake KV args registration:
- Every Mooncake decode rank appends two frames after `kv_item_lens`, as `msg[20]` and `msg[21]`: its `kv_buf_groups` (`0` when the pool does not group its buffers) and its resolved `kv_cache_dtype_str`.
- `KVArgsRegisterInfo.from_zmq` reads them. An absent frame gives `None`.
- The staging fields are parsed from fixed indices and are unaffected.

**How the prefill uses it.**
- In the bootstrap thread, `MooncakeKVManager` calls `check_decode_kv_layout(info)` when a decode rank registers. The result is stored on the registration as `kv_layout_error` (new `mooncake/conn.py:2815`) before `_publish_peer_registration` publishes it, so a transfer never sees the registration without its verdict.
- `transfer_worker` fails every transfer to that decode rank with this reason (new `:2426`). It uses the same `conclude_failure` + `break` path as a dead decode session.
- Where the error shows up: the detailed message, with both sides' values, is logged by the prefill and becomes the prefill request's failure reason. The Mooncake/Ascend status sync carries no reason back to the decode, so the decode only sees a generic KV transfer failure for the room.
- Why the registration is recorded and then poisoned, instead of rejected: the ZMQ registration message has no reply channel.
- This is separate from the registration-time state check added in #42051 (`state_layout_rejections`). That one compares the generic state components (SWA, QSA, ...) and rejects state transfers; this one compares the main KV buffers and fails the whole transfer.
- The base implementation returns `None`, so non-Ascend Mooncake deployments are unaffected. NIXL and Mori have their own registration and are not touched.
- For older peers, a decode without the new frames makes the prefill log a warning and skip the check. An older prefill ignores the extra frames.

**Scope: Ascend only.** `AscendKVManager.check_decode_kv_layout` (new `ascend/conn.py:145`) is the only real implementation:
- It compares `kv_cache_dtype` and `kv_buf_groups`.
- For the NPU DSA layout (`kv_buf_groups == 3`), outside DCP relayout and unified memory, it also compares the per-entry `kv_item_lens`. It requires either exact equality, or that every prefill item length appears on the decode side, because a PP stage registers a subset.
- On a mismatch it logs and returns an error that lists both sides' `kv_cache_dtype`, `kv_buf_groups` and `kv_item_lens`.

It is scoped to Ascend because a generic per-rank item-length check would need backend-specific knowledge of which differences are legitimate (DCP relayout, MHA head slicing, PP subsets). The frames themselves are generic and cost nothing on other backends.

### 6. Indexer dtype axis, behavior unchanged

`NPUMLATokenToKVPool` now stores `indexer_kv_dtype`, `indexer_store_dtype` and `indexer_scale_dtype`, resolved from the capability. The code that used to assume the main KV dtype and FP32 now reads these:

| Consumer | Before (main) | After |
|---|---|---|
| `index_k_buffer` allocation | `store_dtype` | `indexer_store_dtype` |
| `index_k_scale_buffer` allocation | `torch.float32` (`memory_pool_npu.py:725`) | `indexer_scale_dtype` |
| `get_index_k_buffer` / `set_index_k_buffer` | main KV dtype | indexer dtypes |
| `dsa_npu_indexer.py` quantization target | `pool.dtype` (`:232`, `:332`) | `pool.indexer_kv_dtype` |
| `dsa_npu_indexer.py` scale cast | `torch.float32` (`:47`, `:53`) | `pool.indexer_scale_dtype` |
| Sizer | see item 4 | see item 4 |
| HiCache host pool (`page_first_kv_split`) | device `store_dtype` and a hard-coded 4-byte scale (`pool_host/mla.py:270`, `:341-344`, `:375`) | reads the device pool's indexer store and scale dtypes |

For every supported configuration the values are the same as today, so all of these changes are byte-identical.

### Behavior

Behavior is unchanged for all supported configurations. The one exception is the new startup rejection of `float8_e4m3fn` KV cache (`fp8_e4m3`, `mxfp8`, or `auto` with an FP8 checkpoint) on non-arch35 NPUs, which previously produced a pool the attention path could not consume.

The Ascend PD handshake only refuses links whose layouts already disagree. With matching builds and flags it never fires.

This PR does not touch:
- any kernel or op call, or `mla_preprocess.py`;
- `use_compact_indexer_layout`;
- environment variables and CLI flags;
- HiSparse;
- non-NPU pools.

## Unit tests

New file `test/registered/unit/npu/test_npu_kv_capability.py` (CPU, `base-a-test-cpu`, NPU extensions stubbed). It has 35 tests:

**`TestResolveKvCapability` and `TestConfigureKvCacheDtypeOnNpu`: accept/reject matrix**
- arch35 FP8 resolves to packed.
- A2 FP8 is rejected, and the message names the SoC, the requested value and the alternatives.
- `mxfp8`, and `auto` with an FP8 checkpoint, are rejected on A2.
- BF16 and `auto` are accepted on A2.
- FP8 is accepted on arch35.
- Non-NPU platforms are not checked.
- BF16, FP16 and E5M2 are unpacked on every SoC.

**`TestMlaKvCacheDim`: dim selector**
- `packed=True` gives 656 and `packed=False` gives 576.
- `packed=True` with BF16 raises an assertion.
- `is_packed_mla_kv_cache` on and off NPU; E5M2 is never packed.

**`TestNpuMlaPoolLayout`: layer ids vs. buffer entries, on real CPU-allocated pools**
- Covers packed (K, index, scale), unpacked (K, V, index), a compact indexer, and DCP item-length scaling.
- Also checks the indexer dtypes on the pool and the pool's rejection on A2.
- Against the old `get_kv_layer_ids`, the packed and compact cases fail. For example, it returns 8 ids for 6 buffers.

**`TestNpuIndexerSizing`: scale bytes are counted**
- 132 B per token for arch35 FP8 and 256 B for BF16.
- Each is cross-checked against the bytes the pool actually allocates.

**`TestPdKvLayoutHandshake`: handshake**
- `from_zmq` with the new frames, with `0` groups, and from an older peer.
- Rejects `kv_cache_dtype`, `kv_buf_groups` and `kv_item_lens` mismatches, and checks both sides' values are in the error.
- Accepts a PP subset and rejects a foreign PP item length.
- Skips the item-length check for DCP relayout and non-DSA layouts.
- An older peer is tolerated, with a warning.

**Updated tests:**
- `test/registered/unit/npu/attention/test_npu_dcp.py::test_pd_buffer_infos_expand_only_global_page_strides` sets the layer attributes its hand-built pool now needs.
- The `SimpleNamespace` decode registrations that `transfer_worker` reads in `unit/disaggregation/test_disaggregation_wire.py`, `test_mooncake_transfer_batching.py` and `test_prefill_complete_integration.py` now carry `kv_layout_error=None`, like the real `KVArgsRegisterInfo` default.
