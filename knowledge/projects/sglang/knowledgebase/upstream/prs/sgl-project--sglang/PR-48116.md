# [Fix] function_call: Type the named tool_choice item schema as an object

[Upstream PR](https://github.com/sgl-project/sglang/pull/48116) · state: open · merged: False

## Original PR description

## Motivation

With `tool_choice={"type": "function", "function": {"name": ...}}` on the `json_schema` path (`get_json_schema_constraint`, used when the tool-call detector has no structural tag support), the item schema built by `_get_tool_schema` has `properties` and `required` but no `"type"`:

```json
{"type": "array", "minItems": 1,
 "items": {"properties": {"name": {...}, "parameters": {...}}, "required": ["name", "parameters"]}}
```

In JSON Schema, `properties` and `required` only constrain values that are objects, so `[0]` or `["x"]` is a valid output. xgrammar infers an object from `properties`, which hid this. llguidance follows the spec. The model can then close the array right away (`[`, `0`, `]`, EOS). The parser finds no call and the response comes back with empty `content` and empty `tool_calls`.

`tool_choice="required"` is not affected: it already wraps the branches in `{"type": "object", "anyOf": [...]}`.

Compiling the named schema with llguidance 1.9.1:

| output | before | after |
|---|---|---|
| `[0]` | accepted | rejected |
| `["x"]` | accepted | rejected |
| `[{"name": "get_time", "parameters": {"tz": "UTC"}}]` | accepted | accepted |

## Modifications

- `_get_tool_schema` returns `"type": "object"`. The `required` path, which nests the same dict in a typed `anyOf`, behaves the same as before.
- Regression test `test_specific_tool_choice_rejects_non_object_items`: `[0]`, `["x"]`, `[None]` and `[[]]` must fail validation and a real call must pass. It fails on main and passes with the fix.

Related but separate: #40051 touches named `tool_choice` on the legacy structural-tag path, not this `json_schema` item schema.

## Accuracy Tests

Constrained decoding only: the grammar no longer allows call lists whose items are not objects; valid calls are unchanged. Found with `--grammar-backend llguidance` on a model whose tool parser has no structural tag support: the four tokens generated after the reasoning section were `[`, `0`, `]`, EOS.
