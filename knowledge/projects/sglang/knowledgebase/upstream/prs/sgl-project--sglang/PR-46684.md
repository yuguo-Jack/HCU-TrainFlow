# [Fix] dsv41: Size compressed KV pools from the allocated layout

[Upstream PR](https://github.com/sgl-project/sglang/pull/46684) · state: closed · merged: False

## Original PR description

## Motivation

DSV4.1 ratio-1/2 compressed KV pools can leave a substantial part of their memory budget unused. Their allocator selects the 288-byte FP4 layout by default, but the planner charges the legacy 584-byte FlashMLA slot size. For source ratios `[2, 2, 2, 1]` with 68-byte index-K slots, this prices a full input token at 1,630 bytes instead of 890 bytes. A multi-conversation working set can therefore spill to external storage unnecessarily.

## Modifications

- Price ratio-1/2 KV through the existing layout-aware `_get_paged_kv_bytes_per_token(ratio)`, including page padding and the existing unified/NPU/TRT exceptions.
- Add a regression case to the existing pool-configurator suite that compares the planner with actual CPU buffer allocations for FP4, explicit FP8, legacy padded layouts, and 128/256-token pages.

## Accuracy Tests

- All eight regression subcases fail before the fix and pass after it; the full pool-configurator test file passed all 66 tests in the validation checkout.
- Ruff lint/format, isort and `git diff --check` pass on this PR branch.
- Cache-hit accounting passed in the GPU experiment, and high-slot execution completed without OOM/CUDA errors.
- **Full accuracy is not established:** additional 128K random-input probes produced different greedy outputs between cached, recomputed and restored paths, including on the unmodified baseline. These probes do not establish batch invariance or prove an expansion-induced regression. Model accuracy CI is being requested separately.

The GPU measurements and 66-test run used `64fc5f0bdbee035d3341a809a81c41a9f7208eb4` plus this patch. The PR is rebased onto current main; CI results for the submitted head are separate from those local results.

## Speed Tests and Profiling

Controlled DeepSeek-V4.1-Flash test on two GB300 GPUs, attention DP2/EP2, with the Mooncake direct linker. Each rank prewrites 522 distinct 128K prompts and reuses their 126,976-token prefixes with fresh 4,096-token suffixes. Measurement: 512 requests/rank, 17 in flight/rank, one output token/request, memory fraction 0.9.

| | Before | After |
|---|---:|---:|
| Full-token slots/rank | 57,369,600 | 105,070,336 |
| Measured prefix source | 100% Mooncake | 100% GPU |
| Engine step, scheduler/log cross-checked | 188.16 ms | 102.65 ms |
| Response-arrival requests/s/GPU | 10.63 | 19.48 |

The working-set request throughput improves by 83.3%. Device-hit control steps remain approximately 101–102 ms. This is a synthetic cache-working-set experiment, not a replay of the original application burst or a general serving-throughput guarantee.

Measurements use `benchmark/engine_steps/bench_engine_steps.py` from #46006 at `543a2804d5c8f3167c8fd8bb5c3a3ef862c3774f`, with a local `resident` extension that writes distinct prefixes without flushing them afterward, records cache tiers, and separately computes response-arrival throughput. The latter is not relabeled as fixed-batch engine throughput. The benchmark extension is not part of this focused fix.

```bash
python benchmark/engine_steps/bench_engine_steps.py prefill \
  --base-url http://127.0.0.1:32170 --dp 2 --num-gpus 2 \
  --context 131072 --new-tokens 4096 --tokens-per-step 8192 \
  --requests 512 --warmup-steps 5 --in-flight-steps 8 \
  --timeout 900 --seed 733427905 --prefix-source resident \
  --server-log server.log --out result.json \
  --prefill-completions completions.json
```

The command requires the local extension described above; the stock harness at that revision does not offer `resident`.
