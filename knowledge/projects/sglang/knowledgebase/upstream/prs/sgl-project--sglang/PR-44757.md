# [Perf] glm47: Match streaming tool calls with str.find instead of a lazy regex

[Upstream PR](https://github.com/sgl-project/sglang/pull/44757) · state: open · merged: False

## Original PR description

## Motivation

`Glm47MoeDetector.parse_streaming_increment` (parsers `glm47` and `iquest_q1`) runs `re.search(r"<tool_call>(.*?)(?:(<arg_key.*?))?(?:(</tool_call>)|$)", ...)` over the whole buffered tool call on every streamed chunk. The lazy groups make the regex engine step through the buffer one character at a time, so a long call (a file write, say) costs quadratic time on the tokenizer manager's event loop. A 64 KB argument took about 7 s of CPU for one request.

## Modifications

- `_match_partial_tool_call` finds the same spans with `str.find`: the first `<tool_call>`, then whichever of `<arg_key` or `</tool_call>` comes first. It returns the same stripped name, stripped arguments, end marker and match end the regex groups gave, and replaces the regex and `_extract_match_groups`.
- Two tests: one checks the helper against the old regex on every prefix of some tricky inputs, the other streams a long value containing tag-like text in 3-char chunks.

## Accuracy Tests

Parser-only change, model output is untouched. I ran a differential test of the old and new detectors (`Glm47MoeDetector` and `IQuestQ1Detector`) on 108k random inputs mixing well-formed calls and tag soup, random chunking and 6 argument types. Every chunk's normal_text and calls, plus `finish()` and the final state, matched exactly. The helper also matched the regex on about 2.7M prefixes.

## Speed Tests and Profiling

One write_file call streamed token by token with the GLM-4.5-Air tokenizer, CPU only, median of 7 alternating fresh processes per side:

| Content | Deltas | Before | After | Speedup |
|---|---|---|---|---|
| 2 KB | 480 | 10.5 ms | 2.4 ms | 4.4x |
| 8 KB | 1885 | 136.6 ms | 12.5 ms | 10.9x |
| 25 KB | 4737 | 896.5 ms | 57.1 ms | 15.7x |
| 64 KB | 13086 | 6988 ms | 323 ms | 21.6x |

Before, 97% of the parse time was in `re.Pattern.search`; afterwards the profile is flat.
