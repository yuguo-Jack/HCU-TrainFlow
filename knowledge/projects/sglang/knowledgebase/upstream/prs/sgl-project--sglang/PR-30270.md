# fix(router): reconcile Kubernetes worker discovery events

[Upstream PR](https://github.com/sgl-project/sglang/pull/30270) · state: closed · merged: False

## Original PR description

## Motivation

Kubernetes worker discovery in the router can keep stale worker URLs after pod deletion, IP changes, or recovery from a failed worker.

The previous discovery flow consumed `applied_objects()` from the Kubernetes watcher, which only exposes applied objects and loses explicit watcher event semantics such as delete and init/resync events. Worker state was also tracked by the full `PodInfo`, so a pod whose IP or status changed could leave its old URL registered in the router. This may route requests to stale or dummy health-only workers after failure recovery.

This PR makes worker discovery reconcile by a stable pod identity so stale worker URLs are removed when pods are deleted, resynced, become unhealthy, change IPs, or no longer match the worker selector.

## Modifications

- Replace `applied_objects()`-based discovery with explicit Kubernetes watcher event handling.
- Track discovered pods by stable pod identity instead of the full worker endpoint:
  - namespaced watch: pod name
  - cluster-wide watch: `namespace/name`
- Handle watcher lifecycle events:
  - `Init`
  - `InitApply`
  - `InitDone`
  - `Apply`
  - `Delete`
- Reconcile stale entries after watcher resync by removing tracked pods that are no longer present.
- Remove old worker URLs before registering updated URLs when a pod's worker address changes.
- Remove tracked workers when pods are deleted, terminating, unhealthy, missing IP/status, or no longer match the selector.
- Add unit tests covering namespace-aware tracking, pod IP replacement, and deletion after IP changes.

We hit this same bug class in production-like conditions (managed k8s that frequently drops — and sometimes silently stalls — the long-lived watch), and can add real-world measurements confirming the diagnosis here:

- With the stock router, a plain 2-pod rolling update behind 2 router replicas produced **26 client-visible failures** (503s from an empty worker set, 500s to a draining pod, connection errors to a dead endpoint). A replacement pod that had been Ready for 12+ minutes was never registered by either replica.
- One detail worth highlighting for this PR's review: we observed the watch going **silently stale** (no events *and* no error item for 20+ minutes). In that mode `try_for_each` never returns, so the restart path never runs — event-handling improvements alone can't converge during such windows because there are no events to handle.

We've submitted a complementary, deliberately-small patch in #32322: a periodic full-LIST reconcile (plus reconcile-on-restart, reusing the existing add/delete handlers) that converges the worker set even while the watch is dead or stale. It's designed to be independent of — not competing with — the event-handling rewrite here: with both, the explicit `Delete` handling gives immediacy and the periodic LIST gives a bounded-staleness guarantee. Verified on the same failing cell: 26 failures → **0 failures / 0 server-side 5xx** across a full rolling update under steady load with no external remediation.

Happy to share raw logs/run artifacts if useful.
