# [Perf] [AMD] dsv41: All-gather the owned Engram rows instead of the int32 all-reduce

[Upstream PR](https://github.com/sgl-project/sglang/pull/42502) · state: open · merged: False

## Original PR description

## Motivation

With TP > 1 on HIP, every rank looks up all Engram hash ids of the batch. Each rank writes the rows that its table shard owns and zeros for the rest, and an int32 all-reduce of the BF16 rows rebuilds the result (`EngramEmbedding._lookup` and `_reduce_owned_rows`). Exactly one rank owns each row, so most of the reduced bytes are zeros. For DeepSeek-V4.1-Flash at TP4 and a 16,384-token prefill chunk, the all-reduce reduces 201 MB per Engram layer, while the rows each rank owns, in their stored FP8 form with their scales, are 26 MB. On MI355X this lookup takes 2.0 ms per Engram layer at that size.

This draft first planned to move this all-reduce to the custom all-reduce. Since #46994, integer all-reduces stay on RCCL, and an exact all-reduce cannot move fewer bytes anyway. So this PR all-gathers the rows each rank owns instead.

## Modifications

- `SGLANG_OPT_HIP_ENGRAM_ALL_GATHER`: a new switch, off by default (`environ.py`).
- `EngramEmbedding` (`layers/engram.py`):
  - At construction, the path is on only on HIP with TP > 1, when every rank holds whole hash columns (TP sizes that divide DeepSeek-V4.1-Flash's 24 columns, such as TP2, TP4 or TP8), with a device table and no peer or host table. Rank 0 logs one INFO line per Engram layer.
  - Per call, only extend batches without speculative decoding take it (`is_extend_without_speculative()`), outside stream capture and breakable CUDA graphs. Decode, target verify, DP attention, prefill context parallel and graph capture keep their current paths.
  - `_all_gather_lookup`: rank r takes columns `[r k, (r + 1) k)` of every token's ids. The hash puts each column's ids in its own subtable, so these are exactly the rows that the rank stores. The rank copies those FP8 rows and their E8M0 scales into one payload, with the scales padded to whole rows, and one `all_gather_into_tensor` over the TP group sends it. Each rank then lays the gathered scales out like the rows (about 3 MB at 16k tokens) and runs the existing `engram_gather` kernel once to dequantize every row into the `[tokens, 24, 256]` output.
- Exactness: the same stored bytes go through the same dequant kernel as the all-reduce path's `_owned_rows`, so the output is bitwise equal, including negative zeros and the smallest E8M0 scale.
- Bytes: for DeepSeek-V4.1-Flash at TP4 and 16,384 tokens, each rank sends 26.0 MB and receives 78 MB, where the all-reduce reduces 201 MB.
- Tests:
  - `test/registered/unit/layers/test_engram_all_gather.py` (1 GPU): with an emulated TP group, the rows are bitwise equal to the all-reduce at TP2, TP3, TP4 and TP8, also when the first and last row of every column repeat. Every rank sends one payload of the same size, so no sizes are exchanged. Only eager extend takes the all-gather, and stream capture and breakable graphs keep the all-reduce.
  - `test/registered/unit/models/test_deepseek_v4_amd_tp4.py`: `test_engram_all_gather_matches_all_reduce` on 4 GPUs, at 1 and 4,099 tokens, bitwise.
- Related work: vllm-project/vllm#59923 exchanges the packed FP8 Engram rows across DP ranks, which is where the idea to send the stored FP8 rows comes from; #46180 reads rows from peer shards on CUDA; vllm-project/vllm#63367 shards the Engram gate on ROCm.
- Open question for reviewers: should this be a `lookup` value of `--engram-config` instead of a switch, like the peer-shard lookup?

## Accuracy Tests

The lookup is bitwise equal to the all-reduce in both tests above and on every rank of the TP4 benchmark below. In one of three runs of the 4-GPU test file, two ranks aborted (SIGABRT) and the log did not keep the cause; the other two runs passed all six Engram cases.

End to end on DeepSeek-V4.1-Flash, TP4, MI355X, with the switch on, against the same build and server config without this change (baseline in parentheses):

| Mode | GSM8K | GPQA Diamond | NIAH 64k / 128k |
|---|---|---|---|
| DSpark | 97.0 (97.0) | 88.4 (90.9) | 1.0 / 1.0 (1.0 / 1.0) |
| No speculative decoding | 97.6 (97.0) | 87.4 (86.4) | 1.0 / 1.0 (1.0 / 1.0) |

The lookup output is bitwise equal, so these differences are run-to-run variation of the server. GPQA Diamond has 198 questions, so one question is 0.5 points. Over the seven measured points, the DSpark accept length is 2.801 against 2.822.

## Speed Tests and Profiling

The lookup alone, per Engram layer, with DeepSeek-V4.1-Flash's table shape (24 hash columns of 256 FP8 values), TP4, MI355X. Median of 30 runs after 5 warm-up runs, ranks aligned by a barrier, timed with HIP events. The rows are bitwise equal on every rank.

| Tokens | Zero-fill + int32 all-reduce | All-gather (this PR) | Speedup |
|---|---|---|---|
| 4,096 | 536 us | 302 us | 1.78x |
| 12,288 | 1,547 us | 736 us | 2.10x |
| 16,384 | 2,039 us | 894 us | 2.28x |

Serving on DeepSeek-V4.1-Flash, TP4, MI355X, with the switch on, against the same build and server config without this change. The workload has prompts of about 92k tokens that share one long prefix, 1,000 output tokens, `--chunked-prefill-size 16384`, and the radix cache flushed before each point. It has seven points from concurrency 1 to 64, each measured after its own warm-up pass. Throughput and mean TTFT are geometric means over the seven points.

| Mode | Output throughput | Mean TTFT | Full 16k-token prefill steps |
|---|---|---|---|
| DSpark | -0.4% | -2.5% | 1.0-3.3% faster |
| No speculative decoding | -0.1% | -0.9% | 1.6-2.3% faster |

The microbenchmark saving adds up to about 2.3 ms of a 150 ms full 16k-token prefill step (1.5%), and the measured steps are 1.0-3.3% faster at every point. In two identical runs of this benchmark, mean TTFT at single points differed by up to 4% without speculative decoding and up to 16% with DSpark, so the TTFT and throughput changes are inside the noise. All GPU results come from our ROCm test build of SGLang (an earlier commit with extra DeepSeek-V4.1 HIP patches) with this change applied. The code is the same as in this PR; only one test import differs from main.

- hnyls2002 · comment · 2026-10-28T20:52:36Z · [source](https://github.com/sgl-project/sglang/pull/42502#issuecomment-6480419099)

A heads-up for this plan: since #46994, sglang's own custom all-reduce accepts only bf16, fp16 and fp32 (`CustomAllreduce._SUPPORTED_DTYPES` in `python/sglang/srt/distributed/device_communicators/custom_all_reduce.py`, and `SUPPORTED_DTYPES` in `python/sglang/kernels/ops/communication/all_reduce.py` for v2), because its kernels have no integer path; an int64 reduce reaching v2 crashed DeepSeek-V4.1 DEP16 at startup. Integer DP gathers now always take the in-place NCCL/RCCL all-reduce (`python/sglang/srt/layers/dp_attention.py:699`).

The Engram lookup on ROCm still reduces its BF16 rows viewed as int32 through `inplace_all_reduce` (`_reduce_owned_rows`, `python/sglang/srt/layers/engram.py:1230`). An integer custom all-reduce path on gfx950 would need the chosen kernel to support it and its class to declare the dtype. Is this still planned?
