# [Feat] diffusion: Native SANA-Sprint support

[Upstream PR](https://github.com/sgl-project/sglang/pull/45960) · state: open · merged: False

## Original PR description

## Motivation

Closes #43671. Joint work with @raghulchandramouli, who independently found the SANA 1.5 qk_norm bug on #43671; his commits are listed under *Joint contributions*.

[SANA-Sprint 0.6B](https://huggingface.co/Efficient-Large-Model/Sana_Sprint_0.6B_1024px_diffusers) is a guidance-distilled SANA variant that generates 1024px images in 1–4 steps. Its checkpoint declares `SanaSprintPipeline` and `SCMScheduler`, and neither had a native implementation. This reuses the SANA transformer, Gemma2 encoder and DC-AE, and adds Sprint's pipeline, scheduler and defaults.

## Modifications

- **`SCMScheduler`** (`runtime/models/schedulers/scheduling_scm.py`): subclasses Diffusers' TrigFlow sCM scheduler. Diffusers' `SanaSprintPipeline` does three things inline in its loop: it rescales the DiT input, converts the DiT's flow prediction to TrigFlow, and divides the final sample by `sigma_data`. Here `scale_model_input` / `step` / `init_noise_sigma` do that work, so the shared `DenoisingStage` loop runs Sprint unchanged. `timesteps` holds the sCM timesteps the DiT is conditioned on. The 2-step intermediate angle (1.3) is applied only for 2 steps, so 1/3/4 steps work without passing `intermediate_timesteps=None` as Diffusers requires.
- **SANA DiT** (`runtime/models/dits/sana.py`):
  - `guidance_embeds` checkpoints get `SanaCombinedTimestepGuidanceEmbeddings`, with Diffusers' module layout and weight names.
  - `qk_norm="rms_norm_across_heads"` is now applied in both the linear self-attention and the cross-attention.
  - The arch default for `qk_norm` changes to `None`, matching Diffusers. SANA 1.0 configs omit the key and have no norm weights.
- **Pipeline** (`runtime/pipelines/sana_sprint.py`, `configs/pipeline_configs/sana_sprint.py`, `configs/sample/sana_sprint.py`):
  - Sprint's "complex human instruction" prompt prefix. It reuses SANA-Video's text stage; the instruction is now a class attribute there, and SANA-Video's behavior is unchanged.
  - Per-request embedded guidance: `guidance_scale × guidance_embeds_scale`, rounded to the DiT dtype as Diffusers does.
  - fp32 latents.
  - Defaults: 2 steps, `guidance_scale=4.5`. CFG never runs, so negative prompts are ignored.
  - **Resolution binning**, on by default as in Diffusers (`use_resolution_binning`). The DiT runs at the closest 1024px aspect-ratio bin, then a Sprint decoding stage resizes and center-crops the image back to the requested size. The bin table copies Diffusers' `ASPECT_RATIO_1024_BIN`: importing it pulls in the whole PixArt pipeline (about 8.5 s), so a unit test asserts the copy still matches.
  - **Schedule overrides** per request: `max_timesteps`, `intermediate_timesteps` and explicit `trigflow_timesteps` (`num_inference_steps + 1` decreasing angles). They are validated at admission (a bad schedule returns HTTP 400: angles must lie in [0, 1.5708], explicit schedules must end at 0, and an explicit `intermediate_timesteps` applies only to 2 steps) and declared in `image_request_extra_fields`, so the image API forwards them. Diffusers 0.37's own custom-`timesteps` path raises a `TypeError`, because `retrieve_timesteps` omits `num_inference_steps` for `SCMScheduler`, so explicit angles are checked against Diffusers' scheduler directly.
  - The SANA detector excludes Sprint ids, and `sana_sprint` registers before generic SANA.
- **Tests:**
  - `test/unit/test_sana_sprint.py` (CPU).
  - 1-GPU server cases `sana_sprint_0.6b_t2i` and `sana_sprint_1.6b_t2i` with component accuracy enabled. Perf and consistency checks are off, as for `sana_video_2b_t2v`.
  - A component-accuracy hook branch: Sprint's DiT takes the same guidance value as Diffusers, not the FLUX-style ×1000.
- **Component-accuracy harness fix** (`component_accuracy/utils.py`): `normalize_state_key` rewrites `scale` to `weight`, which turned DC-AE's `to_qkv_multiscale.*` into `to_qkv_multiweight.*`. Prefix-stripped and suffix candidates were built only from that rewritten name, so 36 of 375 VAE parameters never transferred and any DC-AE case failed at 90.4% matched. Candidates are now derived from the original name too; when the two names are equal, the candidate order is unchanged.
- **Docs:** SANA-Sprint entry in the model catalog.

### Side effect: SANA 1.5 now loads its QK-norm weights

SANA 1.5 checkpoints ship trained `attn1/attn2.norm_q/norm_k` weights in every block. sglang's SANA DiT had no such parameters, so the loader skipped those weights with a warning and served the model without QK-norm. With this PR they load. DiT output against Diffusers' `SanaTransformer2DModel` on `SANA1.5_1.6B_1024px_diffusers` (real weights, fixed random inputs, bf16):

| | `norm_q`/`norm_k` params | rel. L2 vs Diffusers | cosine |
|---|---|---|---|
| upstream main | 0 | 25.0% | 0.969 |
| this PR | 80 | 3.5% | 0.9994 |

SANA 1.0 (600M / 1600M) is unaffected: no `qk_norm` in config, so no norm modules are built.

### Joint contributions from raghulchandramouli

- **SANA-Sprint 1.6B** (`Sana_Sprint_1.6B_1024px_diffusers`) is registered by exact id next to 0.6B, in the registry, the registry test and the model catalog. Its configs differ from 0.6B only in transformer size.
- **`test/unit/test_sana_dit_param_names.py`** (CPU) builds the native and Diffusers DiTs on the meta device for six real configs (SANA 1.0 600M/1600M, SANA 1.5 1.6B/4.8B, Sprint 0.6B/1.6B) and runs the loader's own name mapping. It asserts that every checkpoint weight lands on a native parameter of the same shape, and that no native parameter is left unloaded. Against main's DiT, the four configs with qk_norm or guidance embeddings fail; SANA 1.0 passes.
- **Scheduler review and schedule validation fixes.** Out-of-range TrigFlow angles used to reach the DiT (for example, `max_timesteps=2.3562` gave a timestep of about -9e4) and are now rejected at admission. An explicit `intermediate_timesteps` with steps other than 2 used to be dropped silently and is now rejected, as in Diffusers. The review also led to the `pred_original_sample` note in `SCMScheduler.step`'s docstring.

## Test

**Scheduler:** `test_scm_scheduler_reproduces_diffusers_sprint_loop` runs a deterministic stand-in for the bf16 DiT through Diffusers' `SanaSprintPipeline` loop and through the shared-loop call order, for 1, 2 and 4 steps. The outputs match bit for bit (`atol=0`). While writing it I caught a dtype issue: a 0-dim fp32 coefficient times a bf16 DiT output stays bf16, which drifted by about 1e-2. The scheduler now upcasts explicitly, and the test fails if that upcast is removed.

| prompt 3 | 10.1% | 10.2% | 6.9% |

So sglang's output is as close to fp32 as Diffusers' bf16 path is. Switching sglang's linear attention to Diffusers' fp32 formulation, or the caption RMSNorm eps to 1e-5, does not reduce the gap.

- raghulchandramouli · COMMENTED · 2026-10-24T16:39:48Z · [source](https://github.com/sgl-project/sglang/pull/45960#pullrequestreview-5638995447)

Review of `SCMScheduler` (`runtime/models/schedulers/scheduling_scm.py`) and the schedule validation in `configs/sample/sana_sprint.py`, as offered on #43671.

**What I checked and found correct**
- `scale_model_input` + `step` reproduce Diffusers' `SanaSprintPipeline` loop: the input scaling, the flow-to-TrigFlow conversion, `pred_x0 = cos(s) x - sin(s) F`, and the `cos(t) x0 + sin(t) noise` re-noise.
- The step index can't fall back to a float-equality lookup. The shared loop calls `set_begin_index(0)` (`denoising.py:1444`), so `_init_step_index` never hits `index_for_timestep`.
- The explicit `model_output.float()` upcast is the right fix for the 0-dim-coefficient promotion issue.
- Skipping the noise draw on the final step changes the RNG stream only after its last use, so parity holds. Your `atol=0` test already shows that.

**1. Out-of-range angles pass validation and feed garbage timesteps to the DiT**

`sin(a) / (cos(a) + sin(a))` has a pole at `a = 3π/4` and goes negative past it, and also for `a < 0`. `_validate_with_pipeline_config` only checks `max_timesteps > 0`, and for `trigflow_timesteps` only checks that they're finite and decreasing. I ran this branch's `SCMScheduler` on CPU:

| request | sCM timesteps passed to the DiT |
|---|---|
| `max_timesteps=1.5708`, 4 steps | `[1.0, 0.7071, 0.5, 0.2929]` |
| `max_timesteps=2.3562`, 4 steps | `[-91255.5, 1.2483, 0.7071, 0.4005]` |
| `max_timesteps=3.0`, 4 steps | `[-0.1662, 5.1906, 0.9338, 0.4823]` |
| `trigflow_timesteps=[1.5708, -0.5, -1.0]` | `[1.0, -1.2041]` |

All four get past admission, and the last three silently produce a broken image instead of a 400. Suggestion: require every angle, including `max_timesteps` and `intermediate_timesteps`, to lie in `[0, 1.5708]`. That's the TrigFlow range Sprint was trained on. Note that 1.5708 is 3.7e-6 above π/2, so a bound of `math.pi / 2` would reject the default. Also require the last explicit angle to be `0`, since the docstring says the schedule ends at the clean sample.

**2. `intermediate_timesteps` is silently ignored unless `num_inference_steps == 2`**

Diffusers raises in this case. Here a request with `steps=4, intermediate_timesteps=1.1` runs the plain linspace schedule with no error. Because the default is `1.3` rather than `None`, the scheduler can't tell a user override from the default. Suggestion: default the field to `None`, resolve it to `1.3` when `num_inference_steps == 2`, and reject an explicit value for any other step count.

**3. (nit) `pred_original_sample` units differ on the last step**

On the final step, `prev_sample` is divided by `sigma_data`, but the returned `pred_original_sample` stays in the `sigma_data`-scaled space. Nothing on this branch reads it as far as I can see. A preview or trajectory consumer would get latents scaled 2x on that step only. A one-line note in the docstring would cover it.

I'm happy to send 1 and 2 as a PR against `feat/diffusion-sana-sprint` along with the other two items, if you'd like.
