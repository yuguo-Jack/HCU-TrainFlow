# [Fix] dumper: Advance step once per EAGLE speculation round

[Upstream PR](https://github.com/sgl-project/sglang/pull/47068) · state: open · merged: False

## Original PR description

ModelRunner.forward() advances dumper.step() on every forward. Under EAGLE-family speculative decoding one scheduler iteration runs several forwards through it -- one per draft step, one for the target verify, one for draft-extend -- and the target and draft runners share the process-wide dumper singleton. So a single round spreads over speculative_num_steps + 2 steps and the round's target tensors never carry the same step number as its draft tensors, which makes them impossible to diff element-wise.

Let a speculative worker own the counter instead:

- ModelRunner gains dumper_step_driven_externally (default False, so non-speculative paths keep the per-forward behaviour).
- EAGLEWorkerV2._take_over_dumper_step() sets the flag on the target runner and every draft runner, and marks itself as the step owner. It returns early when dumper.may_enable is False, leaving runs that do not dump completely untouched.
- _dumper_step() advances the counter at each speculation-round boundary: the decode return in forward_batch_generation, both returns in _forward_prefill_batch (including the early return taken by a rank that does not host the draft, which must stay in step with its peers), and the decode tail of _forward_dp_spec_prefill_coordination. Its prefill branch delegates to _forward_prefill_batch and is deliberately left alone so a round cannot be counted twice.
- _dumper_step() is a no-op unless this worker took the counter over, so a subclass that bypasses EAGLEWorkerV2.__init__ cannot end up counting both per forward and per round.
- StandaloneWorkerV2 replaces that __init__ but inherits forward_batch_generation, so it arms the take-over explicitly.

FrozenKVMTPWorkerV2 also bypasses EAGLEWorkerV2.__init__ and overrides forward_batch_generation, so it keeps the previous per-forward behaviour and is unaffected either way.
