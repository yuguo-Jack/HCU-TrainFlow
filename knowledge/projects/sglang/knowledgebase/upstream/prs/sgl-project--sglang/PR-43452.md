# [dLLM] Refuse unsupported features at launch and logprob requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/43452) · state: open · merged: False

## Original PR description

## Motivation

A diffusion LLM server (`--dllm-algorithm`) accepts several settings that it cannot serve, and the failure only shows up later as a crash or a wrong answer.

- With `--speculative-algorithm NGRAM`, the server dies on its warmup request, because the speculative worker hands the dLLM step loop no logits (`LowConfidence.step` reads `full_logits.shape` on `None`).
- With `--enable-deterministic-inference` on the flashinfer or triton prefill backend, deterministic mode cuts prefill at a fixed split tile, and dLLM block admission asserts that no such cut is set, so the server dies on its warmup request. The default dLLM launch resolves to flashinfer.
- With `--enable-two-batch-overlap`, the two-batch overlap split has no rule for dLLM batches and raises `NotImplementedError` while the server captures decode CUDA graphs.
- A request with `return_logprob` gets a 200 with empty logprob arrays from LowConfidence, JointThreshold, and JointThresholdInDel, because the dLLM result path computes no logprobs. `/v1/score` returns a 500 for the same reason.

This takes the refusals from #31586 as a change of its own.

## Modifications

- `handle_dllm_inference` refuses `--speculative-algorithm`, `--enable-two-batch-overlap`, and `--enable-deterministic-inference` on the flashinfer or triton prefill backend, with an error that names the flag. The check runs after the dLLM attention backend is resolved, so the launch fails during argument resolution, before weights load. Deterministic inference on other backends keeps its current behavior.
- `DllmAlgorithm.validate_request` now rejects `return_logprob` by default, so the scheduler answers such a request with a 400 before it is queued. An algorithm that computes logprobs can override it. Gemma4Renoise keeps its own override, which already rejected logprobs.
- Behavior change for dLLM servers. `/v1/score` requests, and `/v1/rerank` requests that score through logprobs (a Qwen3 reranker chat template or a Qwen3-VL model), now get a 400 that names the algorithm, instead of a 500 or empty logprobs. Requests without logprobs are unchanged, so a client that sends logprob fields without using them can drop those fields to get the same text as before.
- The first commit carries the #31586 code as written there, and the second moves the launch checks into the dLLM argument hook and limits the deterministic check to the backends that fail.

## Accuracy Tests

- One new launch case for the three flags through full argument resolution, and the existing logprob rejection case now runs for every registered dLLM algorithm. Both fail on main and pass here.

```bash
python3 -m pytest test/registered/unit/test_model_overrides.py test/registered/unit/dllm/test_gemma4_uniform_lifecycle.py
```

- The dLLM-related CPU unit files and the server argument suites (47 files) pass with the same results as main, plus the new case.
- `test/registered/dllm/test_dllm_batching_fdfo.py` and `test/registered/dllm/test_dllm_fdfo_joint_threshold.py` pass on main and on this branch.
- Served checks with LLaDA2.0-mini (LowConfidence), LLaDA2.1-mini (JointThreshold), and LLaDA2.2-mini (JointThresholdInDel). Greedy outputs of plain requests are identical to main, each refused launch exits with its error, logprob and score requests get a 400, and the server keeps serving plain requests afterward.

No performance claim.

## Limits

- On main, dLLM servers also fail with the FA3 attention backend and with attention data parallelism, with or without the flags above. This change does not address those.
