# [Fix] quantization: Load Muse-Glimmer-NVFP4's MXFP8 lm_head, and run its MXFP8 dense layers as block-FP8 off Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/48128) · state: open · merged: False

## Original PR description

Fixes #48127

## Motivation

`RadixArk/Muse-Glimmer-NVFP4` does not start with default flags. Loading fails on its MXFP8 `lm_head` (any GPU), and on Hopper the MXFP8 dense layers then fail in DeepGEMM warmup.

## Modifications

- `fp8.py`: read the attribute as `getattr(layer, "deepgemm_mxfp8_input", False)`, the same form `model_runner.py` uses.
- `modelopt_quant.py`: in `MIXED_PRECISION`, on CUDA when not on Blackwell, MXFP8 linear layers (dense and `lm_head`) get a copy of the MXFP8 config with `convert_mxfp8_to_block_fp8 = True`, so they are converted to block-FP8 [128, 128] at load and use the block-FP8 kernels, as `minimax_m3_nvfp4.py` already does. MoE layers keep the original MXFP8 config. Blackwell and ROCm are unchanged.
- `fp8.py`: the Marlin path takes the block size from the linear method (`self.weight_block_size`, [128, 128] after conversion) instead of the checkpoint config ([1, 32]). Without conversion the two are the same. This matters where Marlin is used for FP8 (auto on SM80 to SM88, or `SGLANG_FORCE_FP8_MARLIN=1`).
- The existing `SGLANG_FORCE_MXFP8_BLOCK_CONVERT` is opt-in and also converts MoE layers, so it does not give a working default.
- Tests (CPU): `test_fp8_lm_head_mxfp8.py` runs the real `process_weights_after_loading` on a real `ParallelLMHead` (block-quant weight processing mocked) and checks the Marlin block size after conversion; `test_modelopt_loader.py` checks through `from_config` and `get_quant_method` that an MXFP8 `down_proj` converts off Blackwell, not on Blackwell, and that the MoE config is untouched. On main, 3 new tests fail: two with the `AttributeError` and one on the missing conversion; with only the `getattr` change, the Marlin test fails on `[1, 32] != [128, 128]`. With this PR both files pass (36 tests).
