[Upstream PR](https://github.com/sgl-project/sglang/pull/45353) · state: closed · merged: False

## Original PR description

## [AMD] Qwen4-Exp (Qwen3.8-Flash-Next): FlyDSL monokernel for speculative verify / MTP draft on MI355X

### Motivation

This PR adds an opt-in FlyDSL "monokernel" for decode-phase speculative decoding on MI355X (gfx950). It serves
`amd/Qwen3.8-Flash-Next-Quark-MXFP4-AttnFP8-PLEFP8` at low concurrency (up to 8 running requests), using NEXTN
with topk 1.

**Why decode is launch-bound.** At these batch sizes, a target-verify step runs 48 decoder layers:
- 36 Gated-DeltaNet and 12 sparse-attention layers;
- each layer has a 512-expert MXFP4 MoE;
- each layer has a 4-way hyper-connection residual.

That step is dominated by kernel launches and small GEMVs, not by bandwidth.

**What the monokernel does:**
- **Target verify:** the whole step runs in 13 persistent launches of 256 CTAs. The step covers the embedding, PLE,
  all 48 layers and the final mixer, for R <= 8 requests x (k+1) draft tokens.
- **MTP draft:** each draft step (draft extend and draft decode) runs in one launch.

**Result:** at 8k/1k, conc 1, k = 3, output throughput is **2.50x** that of sglang main. At conc 4 it is **1.64x**.
Accuracy is unchanged.

### Modifications

**Kernel: new `sglang.kernels.ops.speculative.qwen4_exp_monokernel`.** It is registered in the `speculative` group
as `speculative.build_qwen4_exp_monokernel` (FlyDSL backend, HIP only). Group import stays lazy.

| File | Contents |
|---|---|
| `kernel.py` | `build_qwen4_exp_monokernel`, which returns the launcher for one (layer plan, R, L) shape. See below. |
| `layout.py` | Compile-time geometry, the scratch / mailbox layout, pointer-table slots, and the AITER-layout constants for the MoE / FP8 params. |
| `pack.py` | Packing of the few bf16 tensors the kernel tiles itself, pointer-table rows, MoE layout asserts, and AITER un-shuffle helpers for the load-time checks. |
| `weights.py` | Model geometry, and safetensors access for the tensors read from the checkpoint. |
| `primitives.py`, `buffer_ops.py`, `dpp_utils.py` | AMD expression helpers: buffer resources, DPP / cross-lane reductions, fast math, FP8 / MXFP4 conversions. |

`kernel.py` in more detail:
- Stages hand values over through tagged mailboxes.
- FP8 projections use `mfma_scale_f32_16x16x128_f8f6f4` with per-token FP8 activations, which match AITER's
  quantization.
- MXFP4 experts are read in the AITER layout.
- The bf16 GEMMs (mixers, router) use `mfma_f32_16x16x32_bf16`.
- GDN keeps its SSM state in f32 or bf16.
- Sparse attention uses a two-level exact top-512 and 64-bit KV addressing, up to the full 262k context.

**Runtime: new `srt/models/qwen4_exp_monokernel.py`.**

The runners are `Qwen4ExpMonoRunner` (target verify) and `Qwen4ExpMTPMonoRunner` (MTP draft extend / decode).

At load, they:
- read sglang's own weights in place, with no expert or projection copies: the MXFP4 FusedMoE `w13`/`w2` params
  (AITER-shuffled, shared expert fused) and the Quark W8A8 FP8 projections. The one exception is GDN `in_proj_ba`,
  which sglang keeps row-major (N = 96); it gets an 11 MB padded copy;
- assert shapes and dtypes, and compare a few experts / projections byte for byte against the checkpoint, so an AITER
  layout change fails loudly;
- pack about 1.4 GiB of small bf16 tensors into the kernel's tile layout (HC mixers, router, PLE).

At run time, they:
- build CUDA-graph-safe pointer tables from the KV / mamba / PLE / n-gram pools;
- cache one launcher per batch size.

Batches the runners do not support fall through to the normal path. Unsupported configs raise at startup: TP, PP, CP
or EP above 1.

**Hooks:**
- `qwen4_exp.py`: `Qwen4ExpModel.forward` returns early through the runner for target-verify batches it accepts.
  `Qwen4ExpForConditionalGeneration.precompile_kernels_after_loading` builds the runner. It runs after loading, so the
  runner sees the params after their AITER shuffle.
- `qwen4_exp_mtp.py`: the same pattern for the MTP draft.
- `environ.py`: two opt-in flags, `SGLANG_ENABLE_QWEN4_MONOKERNEL` and `SGLANG_ENABLE_QWEN4_MTP_MONOKERNEL`. Both
  default to off.

**Tests:**
- `test/registered/kernels/ops/speculative/test_qwen4_exp_monokernel_layout.py`: host-side layout-contract test.
  - The kernel's un-shuffle helpers must exactly invert AITER's FP8 `shuffle_weight` and the padded, shuffled MXFP4
    FusedMoE layout including E8M0 scales.
  - The padding constants must match `get_moe_weight_sizes`.
  - The MoE asserts must require the fused shared expert.
- `test/registered/amd/accuracy/mi35x/test_qwen4_exp_monokernel_eval_mi35x.py`: nightly e2e accuracy test on one
  MI35x GPU. It checks:
  - GSM8K (chat API) at client concurrency 1 / 2 / 4;
  - the speculative accept length;
  - that both monokernels were built and every CUDA-graph batch size ran through them with 0 fallbacks;
  - passkey retrieval at a ~126k-token context.

### How to run

```bash
export SGLANG_USE_AITER=1
export SGLANG_USE_AITER_UNIFIED_ATTN=1
export AITER_FLYDSL_FORCE=1
export SGLANG_MAMBA_SSM_DTYPE=bfloat16
export SGLANG_USE_AITER_FP8_PER_TOKEN=1
export SGLANG_AITER_HONOR_EXPLICIT_MEM_FRACTION=1   # use --mem-fraction-static as given with the aiter backend
export SGLANG_ENABLE_QWEN4_MONOKERNEL=1        # target verify through the monokernel
export SGLANG_ENABLE_QWEN4_MTP_MONOKERNEL=1    # MTP draft extend / decode through the monokernel

python -m sglang.launch_server \
  --model-path amd/Qwen3.8-Flash-Next-Quark-MXFP4-AttnFP8-PLEFP8 \
  --tp 1 --attention-backend aiter --mem-fraction-static 0.9 \
  --speculative-algorithm NEXTN \
  --speculative-num-steps 3 --speculative-num-draft-tokens 4 --speculative-eagle-topk 1 \
  --max-running-requests 1 --cuda-graph-max-bs-decode 1
```

**Parameters:**
- For concurrency C <= 8, set `--max-running-requests C --cuda-graph-max-bs-decode C`.
- For k draft steps, use `--speculative-num-steps k --speculative-num-draft-tokens k+1`. k = 1 and k = 3 are tested;
  at most 4 draft tokens are supported.

**Checking it is active.** The server log should show both of these lines:
- `Qwen4-Exp monokernel: L=4, R <= 8, ... 13 launches/verify`
- `Qwen4-Exp MTP monokernel: ...`

**Baseline.** Use the same command without the two `SGLANG_ENABLE_QWEN4_*MONOKERNEL` flags.

### Benchmark

Setup: MI355X, TP 1, NEXTN k = 3, bf16 SSM state, default 262144 context. Both paths run with the env above; the
baseline drops the two monokernel flags.

```bash
python -m sglang.bench_serving --backend sglang --dataset-name random \
  --random-input-len 8192 --random-output-len 1024 --random-range-ratio 1.0 \
  --num-prompts <max(10 x conc, 20)> --max-concurrency <conc> --warmup-requests 2 --seed 1
```

| conc | path | output tok/s | speedup | median TPOT (ms) | P90 TPOT (ms) | median TTFT (ms) | accept length |
|---|---|---|---|---|---|---|---|
| 1 | baseline | 214.7 | 1.00x | 4.18 | 5.13 | 256 | 3.43 |
| 1 | **monokernel** | **535.8** | **2.50x** | 1.54 | 1.85 | 254 | 3.52 |
| 2 | baseline | 377.9 | 1.00x | 4.71 | 5.76 | 271 | 3.40 |
| 2 | **monokernel** | **720.2** | **1.91x** | 2.41 | 3.10 | 261 | 3.28 |
| 4 | baseline | 618.7 | 1.00x | 5.29 | 7.60 | 277 | 3.33 |
| 4 | **monokernel** | **1011.8** | **1.64x** | 3.25 | 4.30 | 263 | 3.47 |

Every monokernel run had 0 fallbacks, 0 errors, and every decode step in a CUDA graph.

### Accuracy

All results are on MI355X, NEXTN k = 3, with the env above; the baseline drops the two monokernel flags.

**Full GSM8K** (all 1319 test questions, 5-shot):

| conc | monokernel accuracy | baseline accuracy | monokernel accept length | baseline accept length |
|---|---|---|---|---|
| 1 | **0.9773** | 0.9750 | 3.17 | 3.14 |
| 2 | **0.9795** | 0.9765 | 3.17 | 3.15 |
| 4 | **0.9833** | 0.9773 | 3.18 | 3.17 |

- Strict and flexible extraction give the same score in every run.
- Standard error is +/- 0.0035 to 0.0043.
- Each run used a fresh server with `--max-running-requests` / `--cuda-graph-max-bs-decode` equal to the client
  concurrency.
- Every monokernel run had 0 fallbacks.

**Other accuracy checks:**

| Test | Monokernel | Baseline |
|---|---|---|
| Needle in a haystack: passkey at 7.7k / 31k / 62k / 125k / 238k tokens x 10 / 50 / 90 % depth | **15 / 15** | 15 / 15 |
| e2e accuracy test (below) | pass | - |
| Layout-contract unit test; kernel namespace / dispatch unit tests | pass | - |

What the e2e test checks:
- GSM8K (chat API) above its threshold at client concurrency 1 / 2 / 4;
- accept length above its threshold (measured 3.10);
- every CUDA-graph batch size 1..4 ran through the monokernel, with 0 fallbacks;
- passkey retrieval at a ~126k-token context.

**Why the e2e test uses the chat API.** sglang's default `run_eval` GSM8K completion prompt does not work for this
reasoning model: after the bare `Answer:` it ends its turn immediately, so both paths score near zero on it alike. With
the chat API, both paths score the same.

**Limitations:**
- MI355X (gfx950) only.
- TP / PP / CP / EP = 1.
- NEXTN with topk 1, at most 8 running requests and at most 4 draft tokens.
