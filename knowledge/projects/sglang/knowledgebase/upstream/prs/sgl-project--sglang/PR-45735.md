## Motivation

<!-- Describe the purpose and goals of this pull request. -->

The slash command handler hard-codes the `extra` CI tier (`tag_extra`, `_run_extra_ci`, a workflow display name). This has two problems:

- **It already misses a workflow.** `run-ci-extra` gates both `pr-test-extra.yml` and `pr-test-amd-extra.yml`, but `/run-extra-ci` only re-runs the first.
- **It does not scale.** Each new tier (`run-ci-mlu`, `run-ci-ppu`, ...) would need the same set of edits again.

## Modifications

- **Registry.** Add `scripts/ci/opt_in_ci_tiers.json` to map selections to workflow files and an optional opt-in label. The shared `extra` tier contains NVIDIA and AMD extra; `nv` selects NVIDIA base/shared checks without adding a hardware label.
- **Compatible defaults.** With no arguments, `/run-ci`, `/run-base-ci` and `/tag-and-rerun-ci` use the existing broad retry path, including eligible hardware. Existing label, permission and path gates still apply. Legacy commands retain their ignored-suffix behavior.
- **Explicit selections.** `/run-ci nv` reruns only existing NVIDIA base/shared checks at the current commit, including successful runs. Missing path-filtered workflows are skipped. This selection does not restrict hardware eligibility on future pushes.
- **Structured aliases.** `/run-ci <tier>` equals `/run-<tier>-ci`. `/run-extra-ci <hardware>` equals `/run-<hardware>-extra-ci` when that tier is registered; otherwise it retains the legacy ignored-suffix behavior. New `/run-ci` aliases reject unknown or multiple arguments.
- **Shared extra.** `/run-extra-ci` and `/run-ci extra` rerun both NVIDIA and AMD extra using `run-ci-extra`. Hardware-specific extra tiers are deferred to a follow-up. Legacy `/tag-and-rerun-ci <tier>` adds labels and retries broadly.
- **Gate and validation.** Use generic `require-label` for registered tiers in `pr-gate.yml`, while retaining the legacy `require-run-ci-extra` input and its independent label check for existing callers such as Xeon. The registry linter checks labeled tiers against their workflow gates and supports selections with `label: null`.
- **Docs.** Update the contribution guide, `.github/FOLDER_README.md` and the `ci-workflow-guide` skill.

Once a hardware workflow follows the opt-in gate and event conventions, adding its command requires only a registry entry. MLU and PPU are left to follow-ups because their workflows must first drop the `labeled` trigger. They are not currently registered.
