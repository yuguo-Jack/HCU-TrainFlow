## Motivation

On the fused front's single-collective path, `KimiK3MoE` all-reduces the flat `[latent | shared]` buffer once, and then every rank runs the full latent `up_proj` (`[7168, 3584]`, bf16). Under TP8 the same GEMM runs redundantly on all ranks: at 14336 tokens it costs about 1.1 ms per layer on MI350X, across 92 MoE layers.

## Modifications

For prefill batches of at least 1024 tokens on ROCm, on the single-collective path only (not when the K3 AR fusion is active):

1. All-reduce the latent and apply the latent norm (`_reduce_latent`, as the unfused front does).
2. Add this rank's `7168 / tp_size` rows of `up_proj(latent)` into its shared partial sum, in place.
3. All-reduce the shared sum (`_reduce_shared`) and add `prefix_sum`.

The bytes on the wire are unchanged; each rank runs 1/tp_size of the GEMM, at the cost of one extra collective launch.

- New pure helpers in `kimi_k3.py`: `_sharded_up_proj_eligible`, `_tp_row_slice`, `_sharded_up_proj_tail`. Eligibility and the row slice are computed once in `__init__`.
- Eligible only for ROCm, TP > 1, and a bias-free bf16/fp16 2-D `up_proj` weight whose rows divide by TP. Quantized or packed weights, smaller batches and other platforms keep the existing path.
- The sharded GEMM uses `_k3_bf16_gemm` on a row slice of the weight (ROCm does not shuffle linear weights, so the slice is valid).
- New CPU test: `test/registered/unit/models/test_kimi_k3_sharded_up_proj.py`.

## Accuracy Tests

- Unit tests (CPU, simulated 8-rank sums): the sharded tail matches the replicated tail exactly in float64 and within bf16 rounding in bf16; the rank slices partition the rows; the eligibility rules hold. `test_stage_producers_leave_sums.py` passes.
- GPU check with real collectives at TP2 to TP8: matches the existing path within bf16 rounding (relative RMS error 4.3e-3 at TP8).
- The summation order of the routed output changes. With `ROCM_QUICK_REDUCE_QUANTIZATION=INT4` (not the default), the routed rows are now also quantized on the wire.

Kimi-K3 end to end, GSM8K (500 examples, temperature 0):

| All-reduce | main | this PR |
|---|---|---|
| default bf16 | 0.984 | 0.986 |
| QuickReduce INT4 | 0.988 | 0.986 |

MMMU (900 items, INT4): 0.674 vs. 0.670 / 0.682 on main (relative check only; long reasoning hits the 2048-token cap in all runs).

## Speed Tests and Profiling

Op level (MI350X, TP8, GEMM only, excludes the extra collective):

| tokens | replicated (us) | sharded (us) |
|---|---|---|
| 1024 | 75 | 40 |
| 4096 | 277 | 70 |
| 14336 | 1115 | 132 |

Full tail (collectives, norm, `up_proj`, adds; 8x MI355X, CUDA graph up to 2048 tokens, slowest rank), speedup of the sharded path:

| tokens | TP8 | TP4 | TP2 |
|---|---|---|---|
| 256 | 1.16x | 1.09x | 1.00x |
| 1024 | 1.16x | 1.07x | 1.00x |
| 2048 | 1.22x | 1.10x | 1.01x |
| 4096 | 1.26x | 0.88x | 0.67x |
| 8192 | 1.21x | 1.02x | 0.89x |

TP8 gains at every size. TP4 and TP2 lose at 4096 tokens and above (not investigated). The threshold stays at 1024 because smaller batches were not validated end to end.

End to end: Kimi-K3, TP8/EP8 FP4 on 8x MI350X, chunked prefill 14336, QuickReduce INT4. The baseline is the mean of two main runs; output throughput:

| Point | main (tok/s) | this PR (tok/s) |
|---|---|---|
| 512x512 ISL1024 C16 | 204.26 | 208.53 (+2.1%) |
| 768x1024 ISL1024 C16 | 167.79 | 168.42 (+0.4%) |
| 2048x1600 ISL1024 C16 | 91.67 | 96.78 (+5.6%) |
| 768x1024 ISL256 C16 | 213.70 | 212.45 (-0.6%) |
| 768x1024 ISL8192 C16 | 70.62 | 75.92 (+7.5%) |
| 768x1024 ISL1024 C4 | 83.44 | 83.41 (-0.0%) |
| 768x1024 ISL1024 C16 (4 warmup) | 170.30 | 172.15 (+1.1%) |

Prefill-heavy points (large images, long prompts, high concurrency) gain beyond the run-to-run spread of main (up to 2.8%); the others are within noise. Median TTFT improves by 3.3% and median TPOT by 3.1% (geomean).

Both arms set `SGLANG_DISABLE_KDA_PREFILL_GRAPH_EXTEND=1` and use the Kimi-K3 EP tuned MoE rows from ROCm/aiter#5804.

Not tested: NVIDIA (ROCm-only path), end to end at TP4/TP2, DP attention, other ROCm GPUs.
