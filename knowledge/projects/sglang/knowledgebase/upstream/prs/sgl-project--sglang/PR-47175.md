# [Feat] openai: Also return chat reasoning text as `reasoning`

[Upstream PR](https://github.com/sgl-project/sglang/pull/47175) · state: open · merged: False

## Original PR description

## Motivation

vLLM's chat completions return the reasoning text as `message.reasoning` and `delta.reasoning` (`ChatMessage.reasoning` in `vllm/entrypoints/openai/chat_completion/protocol.py`), and vLLM no longer sends `reasoning_content` in responses (vllm-project/vllm#50624 documents that removal as a breaking client change). SGLang returns the same text only as `reasoning_content`. A client written against vLLM therefore reads no reasoning from an SGLang server, and a deployment that serves one model from both engines gives its clients two different field names for the same text.

This came up serving DeepSeek-V4.1-Flash with its reasoning parser enabled, behind a client that had been written against vLLM: the reasoning was present in every SGLang response, under the other name.

## Modifications

The reasoning text is served under both names, with the same value and the same presence:

- `ChatMessage._serialize` (unary) and `DeltaMessage._serialize` copy `reasoning_content` to `reasoning` whenever `reasoning_content` is in the dump, so `exclude_none` drops both together.
- `sse_utils.StreamDelta`, the msgspec struct that carries every streamed reasoning and content chunk, gets a required `reasoning` field next to `reasoning_content`, set from the same argument. It is required for the reason the docstring gives for `reasoning_content`: an absent key makes `delta.reasoning` raise `AttributeError` in the OpenAI SDK.
- `docs/docs/advanced_features/separate_reasoning.mdx` names the second field.

`reasoning_content` is unchanged, so existing clients see the same payload plus one key. Streamed reasoning chunks carry the text twice, which adds bytes on the wire but no work in the serving loop beyond one more struct field.

Not in this PR: `rust/sglang-processor/src/openai/chat.rs` and the Rust server's chat handler mirror Python's response shape, and `tests/fixtures/openai_parity/*.json` record Python's responses. The Rust parity tests compare against those recorded fixtures, so they stay green here, but the fixtures and the Rust responders will need the same field once the fixtures are regenerated. I can do that in this PR or a follow-up, whichever reviewers prefer.

## Accuracy Tests

No change to model outputs. New unit test `TestModelSerialization.test_reasoning_text_is_served_under_both_names` in `test/registered/unit/entrypoints/openai/test_protocol.py` checks the unary message, the pydantic delta and a `build_sse_content` chunk, with reasoning present and absent, and that `exclude_none` does not reintroduce `reasoning`. It fails on `main` (`KeyError: 'reasoning'`), and replacing the presence check with an unconditional copy makes its `exclude_none` assertion fail.

Parsing the new payloads with `openai==2.8.0` types gives `message.reasoning` and `delta.reasoning` equal to `reasoning_content`, and `delta.reasoning is None` on content chunks.

A heads-up from testing the Rust server. A replayed assistant message with both `reasoning` and `reasoning_content`, or with `reasoning` and a null `reasoning_content`, returns 400 `duplicate field reasoning_content` on main. A non-string `reasoning` returns 400 `data did not match any variant of untagged enum ReasoningContent`. Python accepts all of these. I reproduced this on a real Rust server on one B200 with Qwen3-0.6B. The cause is a serde alias in `dynamo-protocols` (chat.rs near line 809), reached through `ChatBody` in `rust/sglang-server`.

This does not happen with today's responses, but it will once responses carry both fields and a client sends them back. Worth checking before this lands. The branch `fix-rust-reasoning-typed-400` on my fork has a tested fold if it helps. I did not test this PR's own responses end to end.
