# [Perf] dsv41: Restore the wide-prefill mHC stats overlap with the TP all-reduce

[Upstream PR](https://github.com/sgl-project/sglang/pull/42985) · state: open · merged: False

## Original PR description

## Motivation

#39704 ran each DeepSeek-V4.1 hyper-connection's mix statistics (the mix GEMM and Sinkhorn that produce `pre`, `post` and `comb`) on the model-wide stats stream beside that sublayer's TP all-reduce in wide target prefill. The stream forked after the sublayer's compute, right before the collective, and the main stream joined it before the post.

#42245 unified mHC into one state machine and listed this as "Dropped for now: wide-prefill stats multistream overlap". Since then `deepseek_v4_mhc.use_stats_stream` allows the stream only for decode and target verify, so in prefill `run_attn_post` and `run_moe_post` compute the triplet on the main stream after the all-reduce returns. That puts the mix GEMM and Sinkhorn on the critical path twice per layer, for every row of every prefill chunk. At 8192 rows each call reads the full `[8192, 4 x 5120]` BF16 residual.

This PR restores the overlap inside the state-machine design, with the gating #39704 used.

## Modifications

- `deepseek_v4_mhc.use_prefill_stats_overlap(cfg, forward_batch, x)`: the per-forward gate. True for `pre_from_prev` (V4.1) without prefill CP, CUDA rows, 4096 <= rows <= 65536, extend without speculation, Blackwell (SM100 and SM120 alike), attention DP 1, no SP, and batch-invariant mode off. These are the conditions of #39704's `_get_hc_stats_stream` prefill branch.
- `run_attn_post` / `run_moe_post` take an optional `all_reduce_stats_stream`. When it is given and the sublayer left its reduction to the post (an `AttnOutput`, or a `MoEOutput` for the MoE), the post forks that stream right before the plain all-reduce, issues the triplet on it, runs the all-reduce on the main stream (`attn_tp_all_reduce`, or `post_experts_all_reduce` of the merged pieces, plus a replicated shared expert after the reduction as in the existing path), joins, and then runs the unchanged `_post_fusion`. If the sublayer reduced its own output (the attention or MoE can decline the handover, so the type is the ground truth), the triplet runs in line as before. The fused collective kernels are not involved: they cover at most 384 rows, and this path starts at 4096.
- `DeepseekV4DecoderLayer.forward_hc_pre_from_prev`: in wide prefill it asks the attention for `defer_all_reduce=True` and the MoE for `return_moe_output=True`, and passes `hc_stats_stream` as `all_reduce_stats_stream`. It does not fork the stream before the combine in this mode. The static half of the gate is two cached properties matching #39704's layer conditions: `_can_overlap_attn_stats` (stats stream present, `tp_size == attn_tp_size == 4`, `wo_b.reduce_results`) and `_can_overlap_ffn_stats` (stats stream present, MoE `tp_size == 4`, no MoE A2A backend, `reduce_results`).
- Decode and target verify are unchanged: they still fork before each combine through `use_stats_stream`, and never take the new path. Other prefill widths, batch-invariant mode, and the excluded layouts compute the triplet in line, as on main. The DSpark draft layer is unchanged.
- On the paths prefill takes today, the kernels, their inputs and the all-reduce are the same as on main; only the stream and issue order of the mix kernels change. One latent difference: `return_moe_output=True` also forces deferred finalization for the MXFP4 TRT-LLM MoE in `forward_normal_dual_stream`. With a TP-sharded shared expert that changes the BF16 rounding from `round(round(routed) + shared)` to `round(routed + shared)`. Prefill does not reach that branch today: eager prefill takes `forward_normal`, breakable prefill graphs exclude the dual-stream branch, and the DeepSeek attention backend rejects full prefill capture. A captured wide prefill on that MoE backend would see the rounding change.

## Accuracy Tests

New CPU test `test/registered/unit/models/test_deepseek_v4_mhc_prefill_overlap.py`, in the style of the mocked-layer tests: it runs the real `forward_hc_pre_from_prev`, posts and `mix_stats` on a mocked layer with recorded streams, stopping at the kernels and collectives. It checks:
- In EXTEND, MIXED and SPLIT_PREFILL at 4096, 8192 and 65536 rows, for both hyper-connections: no fork before the combine; the attention is asked to defer and the MoE to return its pieces; the order is sublayer, (MoE merge), fork, triplet on the stats stream, all-reduce on the main stream, join, post; and the post receives the reduced rows. The residual is recorded on the stats stream and all three coefficients of each triplet on the main stream (also checked for decode and verify), so dropping either `record_stream` fails the test.
- 6, 4095 and 65537 prefill rows, batch-invariant mode, non-Blackwell, attention DP 2, prefill CP and no stats stream: everything on the main stream, triplet after the sublayer, no handover requested.
- Decode and target verify (6 and 8192 rows): fork before each combine, triplet on the stats stream, no handover requested, as on main.
- A declined attention handover computes that triplet in line while the MoE still overlaps; a replicated shared expert is added after the MoE all-reduce.
- The static attention and MoE gates.

The wide-prefill ordering tests fail with the `deepseek_v4.py` change reverted; the decode, in-line and batch-invariant cases pass on main as well.

On the active prefill paths (eager `forward_normal` MoE) the kernels, their inputs and the collective are unchanged, so prefill outputs are expected to be bitwise identical to main. The latent dual-stream deferred-finalization case above is the exception.

On the hardware below, short-prompt greedy outputs were bitwise identical between builds with and without this change. Long (8K to 32K) prefills are not bitwise reproducible run to run even within one build on this setup, so they were not compared exactly. Teacher-forced log-probability and loop checks passed with this change.

## Speed Tests and Profiling

Setup: 4x RTX PRO 6000 Blackwell (SM120), TP4 over PCIe (PCIe-IPC all-reduce), 250 W power limit, chunked prefill of 8192 tokens.

Regression after #42245, from a TP0 profiler trace of two cold 32K-token prefills (eight 8192-token chunks), comparing builds from before and after #42245:

| | before #42245 | after #42245 |
|---|---|---|
| prefill mix kernels on the stats stream | 336 calls, 302 ms | none |
| of which overlapping the PCIe-IPC all-reduce wait | 261.5 ms | none |
| prefill mix kernels on the main stream | none | 1,280 calls, 305 ms |
| main-stream busy time | 4425.8 ms | 4637.2 ms (+211 ms, about 26 ms per chunk) |

End-to-end cold prefill throughput of the same two builds changed by -3.1%, -4.0% and -4.0% at 8K, 32K and 128K tokens. These builds also differ by other upstream commits in that range; the profile attributes the per-chunk loss to the mix kernels moving onto the main stream.

With this PR:

A build with this change on top of the same base: a TP0 trace of the same two cold 32K prefills shows the prefill mix kernels back on the stats stream, overlapping the all-reduce wait, and cold prefill throughput recovers to the pre-#42245 level:

| prompt tokens | before #42245 | after #42245 | after #42245 with this PR |
|---|---|---|---|
| 8K | 10,052 | 9,736 | 10,138 |
| 32K | 12,561 | 12,057 | 12,634 |
| 128K | 12,875 | 12,354 | 12,947 |

(tok/s, median of 3, same thermal state.) Decode is unaffected: the change only applies to extend batches of 4096 to 65536 rows.
