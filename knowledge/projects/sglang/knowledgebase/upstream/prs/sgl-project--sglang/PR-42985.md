# [Perf] dsv41: Restore the wide-prefill mHC stats overlap with the TP all-reduce

[Upstream PR](https://github.com/sgl-project/sglang/pull/42985) · state: open · merged: False

## Original PR description

## Motivation

#39704 ran each DeepSeek-V4.1 hyper-connection's mix statistics (the mix GEMM and Sinkhorn that produce `pre`, `post` and `comb`) on the model-wide stats stream beside that sublayer's TP all-reduce in wide target prefill. The stream forked after the sublayer's compute, right before the collective, and the main stream joined it before the post.

#42245 unified mHC into one state machine and listed this as "Dropped for now: wide-prefill stats multistream overlap". Since then `deepseek_v4_mhc.use_stats_stream` allows the stream only for decode and target verify, so in prefill `run_attn_post` and `run_moe_post` compute the triplet on the main stream after the all-reduce returns. That puts the mix GEMM and Sinkhorn on the critical path twice per layer, for every row of every prefill chunk. At 8192 rows each call reads the full `[8192, 4 x 5120]` BF16 residual.

This PR restores the overlap inside the state-machine design, with the gating #39704 used.

## Modifications

- `deepseek_v4_mhc.use_prefill_stats_overlap(cfg, forward_batch, x)` is the per-forward gate. It is true only when all of these hold, which are the conditions of #39704's `_get_hc_stats_stream` prefill branch:
  - `pre_from_prev` (V4.1) without prefill CP
  - CUDA rows, with 4096 <= rows <= 65536
  - extend without speculation
  - Blackwell (SM100 and SM120 alike)
  - attention DP 1, no SP, and batch-invariant mode off
- `deepseek_v4_mhc.issue_prefill_stats(hc, residual, stats_stream)` forks the stats stream from the main stream and issues the triplet on it. It records the three coefficients on the main stream. It does not record the residual on the stats stream. The read state keeps the residual alive until `HcUpdate.post` has joined the stats stream, and the boundary releases it only after the post. Until a freed block returns to the driver, which synchronizes the device, the caching allocator reuses it only for allocations on the stream that allocated it (the main stream), so every reuse is ordered after the mix GEMM. Recording the residual would make the caching allocator hold each freed residual until the GPU caught up with the CPU. In a prefill forward that is most of the layers: an 8192-row chunk would hold about twenty `[8192, 4, 5120]` BF16 residuals (320 MiB each) at once.
- In `deepseek_v4_boundary`, `AttentionTransport.prepare_output` and `MoeTransport.prepare_output` call `_issue_prefill_stats` right before they hand back the output that still owes its TP sum. This is the point just before the all-reduce, which is where #39704 forked. The call is skipped when:
  - the attention did not hand back an unreduced `AttnOutput`, for example because it reduced its own output
  - the transport defers the sum to a fused post
  - decode attention TP is active
  - the MoE has no owed sum, or a reduce-scatter already sums it
  - the layer's static gate is off
  - the read state already carries stats

  `_issue_prefill_stats` stores the triplet and the stream on the `ReadState` (`stats`, new `stats_join`), and `HcUpdate.post` joins `stats_join` before running the unchanged post with the precomputed triplet.
- The static half of the gate is two cached properties on `DeepseekV4DecoderLayerBase`, matching #39704's layer conditions:
  - `_can_overlap_attn_stats`: `pre_from_prev`, a stats stream, and `tp_size == attn_tp_size == 4`
  - `_can_overlap_ffn_stats`: `pre_from_prev`, a stats stream, MoE `tp_size == 4`, and no MoE A2A backend
- Decode and target verify are unchanged: they still fork before each combine through `use_stats_stream`. Other prefill widths, batch-invariant mode and the excluded layouts compute the triplet in line, as on main.
- The kernels, their inputs and the all-reduce are the same as on main. Only the stream and the issue order of the mix kernels change.

## Accuracy Tests

New CPU test `test/registered/unit/models/test_deepseek_v4_mhc_prefill_overlap.py`. It drives the real transports' `prepare_output`, the owed sum's completion and `HcUpdate.post` with a mocked layer and recorded streams, and it checks:
- In EXTEND, MIXED and SPLIT_PREFILL at 4096, 8192 and 65536 rows, for the attention, the MoE and merged MoE output:
  - the order is fork, triplet on the stats stream, all-reduce on the main stream, join, post
  - the post receives the triplet
  - the three coefficients are recorded on the main stream
  - the residual is not recorded on the stats stream
- At 6, 4095 and 65537 prefill rows, in decode and target verify, in batch-invariant mode, on non-Blackwell, with attention DP 2, SP, prefill CP, or no stats stream: the all-reduce and the post run on the main stream with nothing issued on the stats stream.
- Stats already precomputed on the read state are kept.
- The static attention and MoE gates.

The kernels, their inputs and the collective are unchanged, so prefill outputs are expected to match main. This expectation is not a measured result.

On the hardware below, short-prompt greedy outputs were bitwise identical between builds with and without this change. Long (8K to 32K) prefills are not bitwise reproducible from run to run even within one build on this setup, so they were not compared exactly. Teacher-forced log-probability and loop checks passed with this change.

## Speed Tests and Profiling

Setup: 4x RTX PRO 6000 Blackwell (SM120), TP4 over PCIe (PCIe-IPC all-reduce), 250 W power limit, chunked prefill of 8192 tokens.

Regression after #42245, from a TP0 profiler trace of two cold 32K-token prefills (eight 8192-token chunks), comparing builds from before and after #42245:

| | before #42245 | after #42245 |
|---|---|---|
| prefill mix kernels on the stats stream | 336 calls, 302 ms | none |
| of which overlapping the PCIe-IPC all-reduce wait | 261.5 ms | none |
| prefill mix kernels on the main stream | none | 1,280 calls, 305 ms |
| main-stream busy time | 4425.8 ms | 4637.2 ms (+211 ms, about 26 ms per chunk) |

End-to-end cold prefill throughput of the same two builds changed by -3.1%, -4.0% and -4.0% at 8K, 32K and 128K tokens. These builds also differ by other upstream commits in that range; the profile attributes the per-chunk loss to the mix kernels moving onto the main stream.

With this PR:

A build with this change on top of the same base: a TP0 trace of the same two cold 32K prefills shows the prefill mix kernels back on the stats stream, overlapping the all-reduce wait, and cold prefill throughput recovers to the pre-#42245 level:

| prompt tokens | before #42245 | after #42245 | after #42245 with this PR |
|---|---|---|---|
| 8K | 10,052 | 9,736 | 10,138 |
| 32K | 12,561 | 12,057 | 12,634 |
| 128K | 12,875 | 12,354 | 12,947 |

(tok/s, median of 3, same thermal state.) Decode is unaffected: the change only applies to extend batches of 4096 to 65536 rows.
