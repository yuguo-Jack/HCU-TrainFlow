# [Fix] grpc: Preserve max_new_tokens three-state semantics

[Upstream PR](https://github.com/sgl-project/sglang/pull/44136) · state: open · merged: False

## Original PR description

## Summary

Fixes #44121 by giving native gRPC clients an explicit way to request the Python/HTTP `max_new_tokens: null` behavior without changing the Python server's default.

The original version of this PR mapped an unset proto field to JSON `null`. After checking the Python path in response to review feedback, that was not fully compatible: Python deliberately distinguishes an omitted field (default `128`) from an explicit `null` (no limit). This revision preserves all three states:

| gRPC request | Scheduler JSON | Behavior |
| --- | --- | --- |
| neither field set | key omitted | Python default: 128 |
| `max_new_tokens: N` | `"max_new_tokens": N` | explicit cap |
| `no_max_new_tokens_limit: true` | `"max_new_tokens": null` | no cap, bounded by context/memory |

`max_new_tokens` and `no_max_new_tokens_limit=true` are rejected when supplied together rather than silently choosing one.

Example:

```python
sampling_params = pb.SamplingParams(
    temperature=0,
    ignore_eos=True,
    no_max_new_tokens_limit=True,
)
```

## Implementation

- Adds the backward-compatible optional proto field `SamplingParams.no_max_new_tokens_limit`.
- Maps that flag to an explicit JSON `null` in the native gRPC request adapter.
- Leaves an unset `max_new_tokens` omitted, matching `SamplingParams.max_new_tokens = 128` in the Python server.
- Regenerates the checked-in `runtime.v1` Rust bindings with `cargo gen-api`.
- Covers `TextGenerate` and `Generate` for the default, explicit-cap, and unlimited states, plus conflicting-input validation.
