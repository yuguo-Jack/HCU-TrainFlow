# [Bug] Native gRPC: forward unset max_new_tokens as null (no limit)

[Upstream PR](https://github.com/sgl-project/sglang/pull/44136) · state: open · merged: False

## Original PR description

## Summary

Fixes #44121.

On the native gRPC server (`--grpc-port`), a `Generate` request whose `sampling_params.max_new_tokens` is unset was silently capped at 128 tokens. `sampling_params_to_map` (`rust/sglang-grpc/src/utils/request_utils.rs`) omitted unset fields from the request dict, so `SamplingParams` fell back to its 128-token default. An HTTP client can request no limit with `"max_new_tokens": null`, but proto3 has no null, so gRPC clients had no way to express it.

This change forwards an explicit JSON `null` when the proto field is unset, mirroring the HTTP `null` semantics (`None` = no limit). Explicitly set values pass through unchanged, and no other field's mapping is touched.

## Reproduction

End-to-end repro from the issue: launch with `--grpc-port`, send `Generate` with `sampling_params=pb.SamplingParams(temperature=0, ignore_eos=True)` and `max_new_tokens` unset — the reporter observed `completion_tokens` of 128, while the same prompt over HTTP with `"max_new_tokens": null` completed ~4000 tokens.

Regression test (copy-paste runnable, no GPU needed):

```bash
cd rust && cargo test -p sglang-grpc unset_max_new_tokens
```

Before the fix, `unset_max_new_tokens_maps_to_null_not_omitted` fails with:

```
unset max_new_tokens must be forwarded explicitly, got: {"temperature": Number(0.0), "ignore_eos": Bool(true)}
```

After the fix it passes, for both the `Generate` and `TextGenerate` request builders.

## Fix rationale

- Invariant: the JSON map handed to the scheduler must distinguish "client asked for no limit" from "client said nothing" exactly the way the HTTP JSON contract does (`null` = no limit, absent key = 128 default). Proto3 `optional` gives presence tracking (`Option<i32>`), so `None` now maps to an explicit JSON `null` instead of omitting the key.
- Scope is deliberately minimal: only `max_new_tokens` has `None`-means-no-limit semantics downstream (`min_new_tokens` maps `None` back to its 0 default; every other optional is a plain default), so only its mapping changes. The whole-`SamplingParams`-unset case still yields `{}`, preserving parity with an HTTP request that omits sampling params (128 default).
- Explicit values (including 0) and the negative-value validation behavior are unchanged: `Some(v)` maps exactly as before.

## Tests

- `cargo test -p sglang-grpc` — 17 passed, 0 failed (includes the new regression test `unset_max_new_tokens_maps_to_null_not_omitted` and the `Some`-path guard `explicit_max_new_tokens_still_maps_to_value`)
- `cargo clippy -p sglang-grpc --all-targets` — no warnings
