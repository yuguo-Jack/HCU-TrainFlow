# [Fix]: tracing: Generate 128-bit trace IDs from the OS entropy pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/44796) · state: open · merged: False

## Original PR description

## Motivation

`TraceCustomIdGenerator` has two problems with the IDs it generates:

- Trace IDs come from `getrandbits(64)`, so the upper half of the 128-bit W3C trace ID is always zero.
- Each process seeds its own `random.Random` with `time.time()`. Processes started at the same clock reading, such as the TP scheduler processes of one server, draw identical ID sequences, so their trace and span IDs can collide. Avoiding collisions across scheduler processes is why this custom generator exists.

## Modifications

- Draw IDs from `random.SystemRandom` (the OS entropy pool), so there is no seed to collide on.
- Trace IDs are 128-bit. Span IDs stay 64-bit, as W3C trace context requires.
- Skip the all-zero ID, which is invalid in W3C trace context.
- Preset span IDs for async tracing (`preset_next_span_id`) are unchanged.

## Accuracy Tests

Not applicable: tracing only, no change to model outputs.

## Speed Tests and Profiling

- Tracing off: no change. IDs are only generated for traced requests.
- Tracing on: `SystemRandom` costs about 1 µs more per draw (`getrandbits(64)`: ~1.2 µs vs ~0.2 µs with `random.Random`, Xeon 8375C). Each traced request draws one trace ID, plus one span ID per span.

Verified end to end on 2× L4 (Qwen2.5-0.5B-Instruct, TP=2, spans exported to Jaeger): all 8 engine-started traces had non-zero upper 64 bits. `test/registered/unit/observability`, `managers` and `disaggregation` fail the same tests as `main` and no others.
