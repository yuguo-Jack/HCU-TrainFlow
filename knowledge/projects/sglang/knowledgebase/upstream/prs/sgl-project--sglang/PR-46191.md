# [Feat] hisparse: host KV tier for the QSA (Qwen4) sparse-attention backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/46191) · state: open · merged: False

## Original PR description

## Motivation

Qwen3.8-Flash-Next has a 262K native context and ~24 KiB/token of KV (12 full-attention layers, GQA 2:1, 256 head dim, bf16). On 2xL20 (47.45 GiB/card) the weights are 44.75 GB/card, which leaves a device KV pool of **47,232 tokens** measured from the server's own log line. A single 262K request cannot be admitted at all, and the admission path rejects it in 1.5 s.

HiSparse already provides exactly the machinery needed (pinned host mirror + on-demand fetch + CUDA-graph-safe custom ops), but it is tied to the MHA backends and is explicitly rejected for `qwen4_exp` by `validate_hisparse()`.

## What this PR does

Wire the existing HiSparse two-tier cache to the QSA backend:

1. `mem_cache/hisparse_hook.py`: allow the QSA backend through `validate_hisparse()`.
2. `mem_cache/qsa_kv_pool.py`: add a HiSparse-aware QSA pool whose device side is a bounded window of the logical sequence and whose host side is a pinned mirror; register it so the scheduler's capacity accounting sees it.
3. Address translation: the four KV read points and the single write gate in the QSA kernels now map `logical -> device` slot indices and fall back to the host mirror on a miss.
4. `managers/coordinator.py` + `kv_cache_configurator.py`: call the HiSparse coordinator and multiply `logical_token_capacity()` by `host_to_device_ratio` (without this, admission still uses the device window and rejects long requests).

A later commit makes the host write capture-safe: the original code did an unpinned device->host copy inside `set_kv_buffer`, which raises `Cannot copy between CPU and CUDA tensors during CUDA graph capture unless the CPU tensor is pinned`. The host write is now a Triton kernel that scatters straight into the pinned mirror, with a fixed-shape fast path when `resident_tokens >= logical_size`.

## Result (2xL20, TP=2, bf16 KV, CUDA graph on)

`--enable-hisparse --hisparse-config '{"host_to_device_ratio": 4}' --max-total-tokens 196608`:

| item | before | after |
|---|---|---|
| admitted per request | 47,226 tok | 262,144 tok |
| 3 concurrent requests | n/a | 3 x 258,231 tok |
| decode, 3 streams | n/a | 54.06 / 53.99 / 53.99 t/s (162-165 agg) |
| decode, 1 stream @258K | n/a | 85.74 t/s (94.93 at 32K) |
| VRAM | 44.75 GB/card | 44.5 / 49.1 GB |
| host pinned | n/a | 9.0 GiB/rank |

Decode speed with the graph off is 8.3 t/s, so **CUDA graph capture must stay enabled**; the host tier is only reached on a window miss.

## Limits / notes for reviewers

- Only the QSA backend is wired; MHA/MLA keep their existing paths.
- The indexer key cache must stay device-resident (it is read on every decode step to pick the top-k blocks); only K/V are tiered.
- `--max-total-tokens` is the *device* window. Setting it to the full logical size (786,432) silently clamps to 399,360 and then allocates a 73 GiB host mirror, which the OOM killer takes. The ratio must be set via `--hisparse-config` instead.
- Host-tier read costs ~2.2 ms/token at 262K in the measured configuration.

## Testing

- Kernel-level: `test_kernels.py` (gather/scatter equivalence, host-vs-device read) and `test_fused.py` pass.
- End-to-end: three concurrent 258,231-token requests admitted and decoded on 2xL20, Xid 0 across the run. Two 8K prompts compare equal to the non-HiSparse path within the machine's own run-to-run logit spread (this box does not reproduce greedy ids between runs of the identical binary, so the check is on logits, not ids).
- `compileall` clean.

## What this does

Adds a host-side KV tier to the QSA (Qwen4 sparse-attention) backend: when the device window is full, blocks migrate to a pinned host buffer instead of being dropped, and come back on demand.

## Validation

2x L20 48 GiB (SM89), TP=2, Qwen3.8-Flash-Next NVFP4, `--context-length 262144`, radix cache off.

- **3 requests x 258,231 prompt tokens = 774,693 tokens in flight**, KV pool 786,432 slots (device window 196,608 x ratio 4, host tier 9.0 GiB/rank)
- prefill 173.6 s for the three requests (~4,460 tok/s aggregate); decode **162.2 tok/s** aggregate (54.1 / 54.0 / 54.0 per stream at 258K), 54.4 tok/s at a 128K window
- VRAM 44.6 / 44.3 GiB per card; startup ~690 s; single-stream 258K = 85.7 tok/s

One caveat worth stating up front: this stack is not bitwise reproducible request-to-request (on main either), so we validated perf plus token-id equality on a fixed probe set, not bitwise KV equality.

The test matrix is skipped on this PR because it needs the `run-ci` label -- happy to add a targeted unit test for the qsa mem-cache wiring if you can point me at the right place.

### Validation on real hardware (SM89, 2× L20)

Ran this branch (plus a local merge of `main` at `6563312`) on the box it was written for:
2× L20 48 GB (SM89), TP=2, PCIe Gen3 x16, no NVLink, Qwen3.8-Flash-Next NVFP4 (W4A16 Marlin MoE),
262,144 context, HiSparse `host_to_device_ratio=4` (9.0 GiB pinned host KV tier per rank).

Numbers from `/metrics` + a streaming probe (no synthetic kernels):

| case | result |
|---|---|
| 258K-token prompt, single stream | **TTFT 57.2 s**, 85.8 tok/s decode |
| 3 × 258K concurrent | **162.4 tok/s aggregate**, 54.1 tok/s per stream, max TTFT 175 s |
| KV pool after startup | 786,432 logical tokens (device window 196,608) |
| GPU memory resident | 44.7 / 48 GiB per card |
| dmesg Xid delta across the runs | 0 |

Same runs with the opt-in prefill CUDA graph (`--cuda-graph-bs-prefill`) OOM while capturing the
12,288 bucket on this card, so all numbers above are with the default `--disable-prefill-cuda-graph`.
