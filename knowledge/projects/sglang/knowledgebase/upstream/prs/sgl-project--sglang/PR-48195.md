# [Feat] serving: Add --max-payload-size flag to raise the HTTP request payload limit

[Upstream PR](https://github.com/sgl-project/sglang/pull/48195) · state: open · merged: False

## Original PR description

Fixes #6622

### Motivation

Sending a ~10 MB JSON body with base64-encoded images to the server fails with "payload reached size limit". With `--enable-http2`, Granian's `HTTP1Settings` defaults `max_buffer_size` to 417792 bytes (~408 KB), so any larger HTTP/1.1 request body is rejected before it reaches the app. There was no way to raise that limit: the only prior attempt (#44161) was closed unmerged when its author's account was blocked for PR flooding, not on the merits of the change, so the issue is still open and unimplemented on current main.

### Modifications

- Add a `--max-payload-size` server flag (bytes, default 10 MiB) to the `serving` namespace (`python/sglang/srt/arg_groups/fields/serving.py`), appended to `POSITIONAL_FIELD_ORDER` per the file's convention so no existing positional slot shifts.
- Wire it into all server launch paths in `python/sglang/srt/entrypoints/http_server.py`:
  - Granian (`--enable-http2`, single and multi tokenizer worker): `HTTP1Settings(max_buffer_size=max_payload_size)`, which is the cap that rejects large payloads. HTTP/2 flow-control windows are unchanged; the existing `--http2-initial-connection-window-size` flag already covers the connection window.
  - Uvicorn (default, SSL-refresh, and multi-worker paths): `h11_max_incomplete_event_size=max_payload_size` (the current uvicorn >= 0.51 kwarg name). Uvicorn imposes no body-size limit by default; this raises the incomplete-event ceiling to the same value for consistency.
- Validate in `handle_ssl_validation` (`serving_hook.py`): the value must be positive, and at least 8192 with `--enable-http2` (Granian's minimum buffer size).
- Add the `--max-payload-size` row to `docs/docs/advanced_features/server_arguments.mdx` (required by `test_server_args_docs_coverage.py`).
- Add unit tests in `test/registered/unit/server_args/test_server_args.py` (`TestSSLArgs`): non-positive values rejected, sub-8192 values rejected with `--enable-http2`, custom values and the 10 MiB default accepted.

### Tests

- New unit tests: `test_max_payload_size_must_be_positive`, `test_max_payload_size_below_granian_minimum_with_http2_raises`, `test_max_payload_size_accepted` in `test/registered/unit/server_args/test_server_args.py`. They need CI to run (no GPU-free local run of the repo test suite on this machine: `msgspec`/`torch` are not installed here).
- Verified locally with a stub harness (`harness_max_payload.py` in the contributor workspace, not part of this PR): it loads the real `handle_ssl_validation` and AST-extracts the real `_granian_http1_settings` / `_run_granian_server`, and checks 24 scenarios — validation accept/reject boundaries, `HTTP1Settings(max_buffer_size=...)` for both keep-alive branches, embedded vs multi-process Granian construction with the right workers/loop, the stop-hook wiring, the three Uvicorn call sites, the docs row, and the 10 MiB default. All 24 pass.
- `ruff check --select F401,F821,F823,UP037` and `ruff format --check` pass on every touched Python file; `python -m py_compile` passes; `git diff --check` is clean.
- Not verified here: an end-to-end server launch sending a > 408 KB body (needs a GPU box and the Granian/Uvicorn packages, neither available on this machine). The Granian `max_buffer_size` kwarg and default (417792) were confirmed against the granian 2.6.0 wheel (the minimum pinned version), and the Uvicorn kwarg against the uvicorn 0.51 wheel (the minimum pinned version).
