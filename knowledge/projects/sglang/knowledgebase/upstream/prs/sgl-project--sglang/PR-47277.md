# [Fix] mooncake: Bind the transfer engine init thread to gpu_id

[Upstream PR](https://github.com/sgl-project/sglang/pull/47277) · state: open · merged: False

## Original PR description

  ## Motivation

  Since #37874, `MooncakeTransferEngine.initialize` calls `TransferEngine.initialize` through `run_with_deadline`, which runs it on a new thread. A new thread starts on device 0, so every rank initializes Mooncake against GPU 0 instead of its own `gpu_id`, and ranks on other GPUs open an extra context on GPU 0.

  This has the same root cause as #38774 (NIXL backend init) and #45678 (Mooncake transfer worker threads). Neither of those covered the transfer engine init path.

  Related: #40056 and #44389 report that Ascend TE init fails for the same reason. This change also binds the NPU device in the init thread, which should cover their TE init failure. It does not cover the `mooncake_store` part of #40056.

  ## Modifications

  - `python/sglang/srt/distributed/device_communicators/mooncake_transfer_engine.py`: the function passed to `run_with_deadline` calls `bind_thread_to_device(self.gpu_id)` (added in #45678) before `self.engine.initialize(...)`. The init deadline is unchanged. The helper goes through `current_platform.set_device`, so it works on CUDA, NPU and XPU,
  and does nothing on platforms that do not support setting a device. It is imported inside the function, so `distributed/` does not import `disaggregation/` at module load.
  - `test/registered/unit/distributed/test_mooncake_transfer_engine_device.py`: a CPU-only regression test that uses a fake platform and the real `run_with_deadline` thread. It checks that `set_device("cuda:3")` and then `initialize` both run on the init thread, not on the caller thread. Without the fix, only `initialize` is recorded.
