# Add DDTree speculative decoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/29907) · state: closed · merged: False

## Original PR description

## Summary

This PR adds DDTree (Diffusion Draft Tree) speculative decoding support.

DDTree extends DFLASH-style draft execution with tree-based verification. Instead of verifying only a linear draft chain, DDTree can use a larger tree budget to verify multiple candidate branches and improve acceptance length. The worker uses `DFlashWorkerV2` for draft-worker initialization, memory pool setup, and CUDA graph handling, while keeping a DDTree-specific non-overlap decode loop for tree construction and verification.

## Changes

- Add `DDTreeWorker`, `DDTreeDraftInput`, and `DDTreeVerifyInput`.
- Add DDTree tree construction and EAGLE-format tree topology conversion utilities.
- Register `DDTREE` as a speculative decoding algorithm.
- Add `--speculative-ddtree-budget`.
- Add DDTree-specific environment knobs:
  - `SGLANG_DDTREE_MAX_TOPK`
  - `SGLANG_DDTREE_DEPTH_BONUS`
  - `SGLANG_DDTREE_RANK_PROBE`
- Support DDTree target-verify CUDA graph shapes where `draft_token_num = ddtree_budget + 1`.
- Support DDTree draft-worker CUDA graph replay with `input_embeds`.
- Make hybrid/Mamba target-verify metadata use per-request `spec_info.topk` and support DDTree tree topology tensors.
- Disable Mamba conv-window dedup for DDTree full-tree verify, where per-token tree ancestors are required.
- Route DDTree decode preparation through its own draft input state instead of the EAGLE prepare path.

## Validation

### Correctness

Tested on a hybrid GDN model with:

- Target model:  an SFT-tuned MoE model with NVFP4 quantization
- Draft model: a DFLASH draft checkpoint
- TP: 1
- Attention backend: Triton
- `max_new_tokens=512`
- `max_running_requests=1`
- strict memory check enabled

Single prompt generation succeeds:

- Output is correct
- `spec_accept_length = 1.8235`

The 40-prompt benchmark completes without scheduler exceptions or memory leak reports.

### Performance

Benchmark setup:

- Dataset: 40 prompts
- Warmup: 3 requests
- Max new tokens: 512
- Same target model, draft model, hardware, and runtime config across runs

| Method | Budget / Block | AL mean | AL median | AR mean | TPS mean |
|---|---:|---:|---:|---:|---:|
| DFLASH | block=16 | 2.576 | 1.607 | 0.102 | 146.2 |
| DDTree | budget=8 | 2.329 | 1.605 | 0.086 | 126.2 |
| DDTree | budget=16 | 2.621 | 1.807 | 0.105 | 128.6 |
| DDTree | budget=32 | 2.750 | 1.903 | 0.114 | 119.8 |

DDTree shows clear budget scaling:

- budget 8 -> 16: AL mean improves from `2.329` to `2.621` (+12.5%)
- budget 16 -> 32: AL mean improves from `2.621` to `2.750` (+4.9%)
- budget 8 -> 32: AL mean improves from `2.329` to `2.750` (+18.1%)

Compared with DFLASH block=16:

- DDTree budget=16 improves AL mean by +1.7% and AL median by +12.4%
- DDTree budget=32 improves AL mean by +6.8% and AL median by +18.4%

As expected, larger DDTree budgets trade additional verification work for higher acceptance length.

- Hayden727 · comment · 2026-07-10T13:35:36Z · [source](https://github.com/sgl-project/sglang/pull/29907#issuecomment-4935889345)

@wenqf11 Good question. I don't think the lower TPS should be attributed only to DDTree's algorithmic verify cost yet.

Part of it is expected: DDTree full-tree verifies `tree_budget + 1` target nodes, so `budget=32` forwards 33 verify nodes vs DFLASH block=16, while the reported AL gain is much smaller than the extra verify work.

But this PR also has several implementation overheads that can depress TPS:
- `budget < block_size - 1` still runs a full `block_size` draft forward and only truncates later, so `budget=8` does not actually save draft compute.
- Spine mode still goes through DDTree LCRS/custom-mask verify instead of the DFLASH causal verify fast path.
- Full-tree construction materializes dense vocab logits, then moves top-k data to CPU and builds the tree with Python/NumPy/heapq each decode round.
- The flat tree mask and accepted-token processing both do CPU syncs (`cpu().tolist()` / `.tolist()`) in the hot path.
- DDTree currently disables overlap scheduling, so these costs are serialized against decode.

So the benchmark currently mixes algorithmic cost with implementation overhead. It would be useful to add a breakdown for draft forward / tree build / mask build / target verify / KV materialization, and compare against DFLASH under the same overlap/non-overlap setting. I left inline comments on the concrete hot-path locations.

Follow-up after my last update (93e9850e4), addressing the review comments raised since then:
Correctness fixes from the 07-09 review (merged via a56d757cd):

- return_hidden_states — explicitly rejected for DDTree until per-request hidden-state ordering is implemented, avoiding wrong hidden rows on branching accepted paths.
- Non-Triton backend guard ([3], [7]) — DDTree now rejects non-Triton attention backends at startup (unless the matching backend/draft_token_num conditions hold), so configs where budget + 1 != block_size can no longer build mismatched QO/mask shapes on FlashAttention/TRTLLM at runtime.
- SM120 NVFP4 MoE fix (new in this update, from merging latest main). On SM120 (RTX PRO 5000), trtllm-gen MoE is SM100-only so upstream falls back to FLASHINFER_CUTLASS, but that runner assumes the dispatcher already fp4-quantized the activations (only true under DP-attention all-gather). Under tp-only serving StandardDispatcher leaves bf16 activations with scale=None, so the kernel reads garbage. The self-contained cutlass_moe_fp4 path had been removed upstream, so this PR re-adds the NVFP4 JIT kernels (jit_kernel/nvfp4.py, csrc/gemm/nvfp4/*.cuh, csrc/moe/nvfp4_blockwise_moe.cuh, with a getSMVersion rename to avoid a symbol clash) and selects cutlass_moe_fp4 unless the fp4-allgather path is active. Verified on SM120 tp1 + CUDA graph: byte-identical output vs the pre-merge baseline with matching accept length.
Note on performance: cutlass_moe_fp4 (Triton) is a correctness fallback and is slower than the FLASHINFER_CUTLASS/trtllm paths. It only kicks in on the non-DP-attention SM120 case where those paths are unavailable/incorrect, so it doesn't affect the SM100 / DP-attention high-throughput paths. A faster SM120 NVFP4 MoE path is left as a follow-up.
Performance comments from the 07-10 review (spine fast-path, dense full-vocab logit materialization, on-device tree build, flat-mask vectorization, accept_index D2H sync, overlap-schedule path): these are decode-path optimizations rather than correctness issues. The current PR is correctness-first; I'll address them as follow-ups and post benchmark numbers.
