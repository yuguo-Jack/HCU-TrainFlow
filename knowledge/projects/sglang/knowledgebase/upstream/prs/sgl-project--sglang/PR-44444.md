# [Feat] plugins: Add SGLANG_REQUIRED_PLUGINS for fail-fast loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/44444) · state: open · merged: False

## Original PR description

Closes #43133

## Motivation

SRT general plugins are best-effort: a plugin that is missing, filtered out, fails to import, raises in its callback, or has a hook that fails to apply is only logged, and the server starts without it. For a plugin that changes how a model is placed or executed, partial application is worse than none. This implements part 1 of #43133: an opt-in, plugin-agnostic fail-fast. Parts 2 and 3 (read-only hook status, `register(..., required=True)`) are left out; happy to follow up if wanted.

## Modifications

- `environ.py`: add `SGLANG_REQUIRED_PLUGINS = EnvTuple(())` next to `SGLANG_PLUGINS`.
- `plugins/__init__.py`: `load_plugins()` raises a `RuntimeError` naming the plugin and the cause when a listed plugin:
  1. has no entry point in `sglang.srt.plugins`;
  2. is excluded by `SGLANG_PLUGINS` or `SGLANG_PLATFORM`;
  3. raises in `ep.load()`;
  4. raises in its callable;
  5. registered a hook whose target was not applied.

  Load and callable errors are chained (`raise ... from e`), so the original traceback is kept.
- The required set is passed to `load_plugins_by_group()` as a new keyword parameter (default empty), so platform discovery, which shares that function, is unchanged.
- `plugin.mdx`: env-var table row, plus an SRT paragraph in the failure-semantics section.

With the env var unset, behaviour and logs are unchanged.

- piotrm-nvidia · comment · 2026-10-18T17:52:48Z · [source](https://github.com/sgl-project/sglang/pull/44444#discussion_r4308059615)

File: `python/sglang/srt/plugins/__init__.py` · line 97

Hooks registered at import time aren't covered by the final check. `_current_plugin_source` is only set around `func()` in `load_plugins()`, so a required plugin that registers at module scope registers here, during `ep.load()`, with `source=None`. That happens with `@plugin_hook`, or with `HookRegistry.register(...)` at module level as in the "Registration API" section of `plugin.mdx`. The check at the end of `load_plugins()` then skips it (`source is not None and ...`), so a renamed target in such a plugin still starts the server without the hook.

Reproduced on this PR: a required plugin whose `ep.load()` applies `@plugin_hook` to a missing target logs `Failed to apply hooks to ...`, and `load_plugins()` still returns normally.

Setting the context variable around `ep.load()` too would cover it (untested sketch):

```python
            token = _current_plugin_source.set(HookSource(ep.name, dist_name))
            try:
                func = ep.load()
            finally:
                _current_plugin_source.reset(token)
```

A test with a fake entry point whose `load()` applies `@plugin_hook` to a missing target would pin it.

- piotrm-nvidia · comment · 2026-10-18T17:52:48Z · [source](https://github.com/sgl-project/sglang/pull/44444#discussion_r4308059619)

File: `python/sglang/srt/plugins/__init__.py` · line 172

This misses a hook that was registered after its target was already patched. `apply_hooks()` skips any target already in `_patched`. If `apply_hooks()` runs before a required plugin registers, for example because an earlier plugin calls it from its own callback, the required plugin's later hook on the same target is never wrapped. The target is still in `_patched`, though, so nothing is reported. That is the "registered too late" half of case 1.5 in #43133.

Reproduced: when an earlier plugin calls `HookRegistry.apply_hooks()` from its callback and a required plugin then hooks the same target, `load_plugins()` returns normally and the required plugin's hook is never called.

A per-hook comparison would cover it, e.g. recording which `(target, hook)` entries `apply_hooks()` actually wrapped and checking the required plugins' registrations against that.
