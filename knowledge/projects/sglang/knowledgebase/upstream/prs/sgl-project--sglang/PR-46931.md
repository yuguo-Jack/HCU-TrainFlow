# [Feat] [AMD] mori: MORI EPv2 AsyncLL dispatch/combine, with shared experts overlapped under SBO

[Upstream PR](https://github.com/sgl-project/sglang/pull/46931) · state: open · merged: False

## Original PR description

## Motivation

MORI EPv2 currently runs only its native dispatch/combine, which finishes the whole transfer inside one call, so nothing can run while tokens move. MORI's AsyncLL kernels (ROCm/mori#768) split each transfer into a send and a receive half, and with `MORI_ENABLE_SDMA=1` move the tokens on the copy engine instead of CUs.

This PR drives those kernels from SGLang and uses them for single-batch overlap (`--enable-single-batch-overlap`). On AMD, SBO runs the shared experts in the dispatcher's dispatch hook, between `dispatch_a` and `dispatch_b`. With the send in `dispatch_a` and the receive in `dispatch_b`, the shared experts now overlap the transfer.

It is independent of two-batch overlap. #44492 carries the same AsyncLL dispatcher together with DSV4 prefill TBO + DSpark; whichever PR merges first, the other is rebased onto it.

## Modifications

| Commit | Change |
|---|---|
| `[AMD] MORI EPv2: run dispatch/combine on MORI's AsyncLL kernels` | `moriep.py`: EPv2 is split like EPv1 into a base plus `_MoriEPv2DispatcherImplNormal` (native kernels, unchanged) and `_MoriEPv2DispatcherImplAsyncLL(overlap)`. `--deepep-mode low_latency` or `MORI_ENABLE_SDMA=1` selects AsyncLL (`sdma` transport with SDMA, `lsa` peer stores otherwise). AsyncLL uses the hip backend, MORI's own launch geometry, no comm stream, and a cco window sized from MORI's `asyncll_regions`. It has no fp4 dispatch or quantized combine: FP4-weight MoE dispatches MXFP8 when aiter can produce it, else bf16 (gfx1250 stays bf16: its a8w4 MoE takes no pre-quantized activation); combine is bf16. `SGLANG_MORI_RECV_BOUND` covers the AsyncLL receive layout. `moe_hook.py`: low_latency no longer rewrites to normal on EPv2 and SDMA no longer forces EPv1; a MORI build without EPv2 AsyncLL falls back to EPv1. Docs, CPU unit tests, and `MODE=low_latency` / `MORI_ENABLE_SDMA=1` in the manual dispatcher test. |
| `[Fix] MORI EPv2: let every rank finish the LSA probe before tearing it down` | With `MORI_ENABLE_SDMA` the temporary device comm in `_cco_lsa_size` trades SDMA queue IPC handles; a rank closing it early left a peer blocked forever. Barrier before closing (gfx1250 EP4 sdma: 2/12 hangs before, 0/20 after). |
| `[AMD] MORI EPv2 AsyncLL: let SBO run shared experts between send and receive` | `low_latency` already receives in `dispatch_b`. `normal` + `MORI_ENABLE_SDMA=1` received right after sending; under SBO without TBO it now leaves the receive to `dispatch_b` too. Unit test pins the order. |

On AMD only `SboFlags.enable_dispatch_shared_one_stream_overlap` applies (the combine / down-GEMM overlaps need DeepGEMM or CuTe DSL). Native EPv2 finishes its transfer in one call, so single-stream SBO has nothing to overlap there; that path is unchanged.

## Accuracy Tests

DeepSeek-V4-Flash, gfx1250, EP4 single node, DSpark, DP attention, CUDA-graph decode, `SGLANG_MORI_RECV_BOUND=1`, `--chunked-prefill-size 32768`, no TBO. gsm8k, 200 questions:

| Transport | This branch, SBO off | This branch, SBO on | On #44492 (same AsyncLL code), SBO off ×2 / on ×2 |
|---|---|---|---|
| `low_latency` + SDMA | 0.960 | 0.960 | 0.960, 0.965 / 0.945, 0.945 |
| `normal` + SDMA | 0.960 | 0.955 | 0.955, 0.960 / 0.945, 0.945 |
| native EPv2 (no AsyncLL) | 0.955 | – | – |

All within the run-to-run noise of 200 questions.

## Benchmarking and Profiling

Same setup. Decode load: 256 requests, ISL 1024 / OSL 512, concurrency 64. Prefill load: 384 requests, ISL 8192 / OSL 16, concurrency 128.

This branch:

| Transport | SBO | decode output tok/s | decode mean ITL (ms) | decode mean TTFT (ms) | prefill input tok/s |
|---|---|---|---|---|---|
| `low_latency` + SDMA | off | 1755 | 29.79 | 1227 | 19696 |
| `low_latency` + SDMA | on | 1816 (+3.5%) | 28.97 | 1223 | 20583 (+4.5%) |
| `normal` + SDMA | off | 1760 | 29.73 | 1197 | 20294 |
| `normal` + SDMA | on | 1806 (+2.6%) | 28.86 | 1207 | 20475 (+0.9%) |
| native EPv2 (no AsyncLL, unchanged path) | – | 1793 | 29.18 | 1190 | 20369 |

SBO gain, repeated on the same nodes with the same AsyncLL code on top of #44492, alternating off / on / off / on:

| Transport | SBO off (2 runs) | SBO on (2 runs) | decode gain | ITL | prefill gain |
|---|---|---|---|---|---|
| `low_latency` + SDMA | 1753 / 1769 | 1816 / 1834 | +3.7% | 29.61 → 28.79 ms | +3.1% |
| `normal` + SDMA | 1744 / 1772 | 1809 / 1833 | +3.6% | 29.63 → 28.88 ms | +3.1% |

Every SBO-on run beats every SBO-off run; repeated runs of one config differ by 1–1.6%.

At this size (EP4 on one node) the native EPv2 kernels are about as fast as AsyncLL + SBO (1793 vs 1806–1816 tok/s), and AsyncLL without SBO is ~2% behind native. Larger EP (EP8 / EP16 across a UALink vPOD), where transfers are longer, is not measured yet.
