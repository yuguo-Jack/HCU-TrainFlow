# [Score API] Support caller-supplied rid on score requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/37184) · state: closed · merged: False

## Original PR description

## Motivation

`rid` is the correlation key that ties a request together across the TokenizerManager, scheduler and detokenizer logs. For generate requests a caller can already supply their own — `GenerateReqInput._normalize_rid` accepts a single `str` and expands it into per-item rids:

```python
elif isinstance(self.rid, str):
    new_rids = [f"{self.rid}_{i}" for i in range(num)]
    self.rid = new_rids
```

There is no equivalent for the Score API. `Engine.score()` / `async_score()` / `TokenizerManager.score_request()` expose no `rid` parameter, so scoring traffic always gets auto-generated ids. When a scoring request misbehaves (slow, retried, or dropped) there is no way to line the sglang-side logs up with the caller's own request id, which makes debugging in a service that fronts sglang considerably harder.

The underlying `EmbeddingReqInput` also could not accept a base rid: its batch path asserted the rid was already a list.

## Modifications

- Add an optional `rid: Optional[str] = None` to `Engine.score()`, `Engine.async_score()` and `TokenizerManager.score_request()`, threaded down to the `GenerateReqInput` / `EmbeddingReqInput` that scoring builds.
- Teach `EmbeddingReqInput.normalize_batch_and_arguments` to expand a single `str` rid into `<rid>_<i>` for a batch, mirroring `GenerateReqInput._normalize_rid`. The previous `assert isinstance(self.rid, list)` now only applies to the non-str case.

A scoring call fans out into one sub-request per item, which is why the base id is expanded rather than reused verbatim — reusing it would produce duplicate rids and trip `_validate_rid_uniqueness`.

Default behavior is unchanged: `rid=None` still auto-generates, and existing callers that pass a list still work.

## Accuracy Tests

Purely additive — no change to scoring math or to any existing code path when `rid` is not supplied. Added unit tests to `test/registered/unit/managers/test_io_struct.py` (registered CPU suite) covering rid normalization on `EmbeddingReqInput`: single (non-batch) str preserved, str expanded to `<rid>_<i>` across a batch, `None` auto-generates unique per-item ids, and an explicit list passes through untouched.

## Benchmarking and Profiling

Not applicable — no change on the hot path; this only affects how the request id is chosen.

- fortunecookiee · comment · 2026-09-11T16:00:35Z · [source](https://github.com/sgl-project/sglang/pull/37184#issuecomment-5637158054)

Rebased onto current `main` and fixed a collision hazard found in self-review.

The scheduler aborts by **prefix** match (`req.rid.startswith(recv_req.rid)`) across the waiting queue, running batch, chunked request and every disaggregation queue. Auto-generated rids are fixed-length `uuid4().hex`, so no rid can prefix another — but expanding a caller-supplied base rid as `f"{rid}_{i}"` broke that invariant. For a batch of ≥11, `base_1` prefixes `base_10`, so aborting one item (client disconnect, or one item failing validation) silently aborted its siblings. The score API is exactly the high-fan-out case where this is routine.

Changes:
- Expansion zero-pads the index to a fixed width, via a shared `expand_base_rid()` used by both `GenerateReqInput._normalize_rid` and `EmbeddingReqInput`.
- That helper rejects empty/non-str rids and rids starting with the reserved `HEALTH_CHECK` / `draft:` prefixes, which change scheduler control flow — a `HEALTH_CHECK`-prefixed request is dropped when the scheduler isn't idle and `_handle_abort_req` returns early for it, so the caller would wait forever.
- `_init_req_state` now checks all rids before inserting any. It raised mid-loop on a duplicate but is called outside the caller's `try/except`, so earlier insertions leaked with no waiter and no remover, permanently poisoning those rids.
