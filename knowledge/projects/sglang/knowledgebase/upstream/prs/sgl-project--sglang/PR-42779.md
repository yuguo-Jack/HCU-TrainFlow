# fix(sampling): reject oversized top_k, logprobs, and n before they kill the server

[Upstream PR](https://github.com/sgl-project/sglang/pull/42779) · state: closed · merged: False

## Original PR description

## Motivation

`SamplingParams.verify` range-checks almost every sampling field, but it never checks an upper bound on `top_k`, and it does not check `n` at all. `top_logprobs_num` is not a `SamplingParams` field, so it skips `verify` entirely. The values then reach torch inside the scheduler, the event loop dies, and the server stops answering `/health`.

A `/v1/completions` request with `max_tokens: 4` does this:

- `"top_k": 2147483648` overflows the int32 `top_ks` tensor (`value cannot be converted to type int32 without overflow`)
- `"logprobs": 2147483648` is passed to `torch.topk` past the vocab row (`selected index k out of range`)
- `"n": 2147483648` copies the prompt inside `normalize_batch_and_arguments`, which runs before `verify`, so the request times out and the server stops answering

The sibling fields already 400. `min_new_tokens`, a negative `top_k`, and a non-finite `frequency_penalty` all come back from `verify` without killing the process.

Tracked in [#41482](https://github.com/sgl-project/sglang/issues/41482).

Reproduced with:

```bash
python -m sglang.launch_server --model-path Qwen/Qwen3-0.6B --port 30000
python repro_sglang_sampling_upper_bound.py --base-url http://127.0.0.1:30000 --variant top_k
# one variant per fresh server: top_k, logprobs, n
```

## Modifications

Upper bounds in `sampling_params.py`, `io_struct.py`, and `tokenizer_manager.py`:

- `top_k` must be `-1` (whole vocabulary, stored as `TOP_K_ALL = 1 << 30`) or in `[1, vocab_size]`. `TOP_K_ALL` still fits in the int32 `top_ks` tensor. Both Rust `verify` copies use the same check, and a negative `top_k` is rejected before the `u64` cast.
- `n` for normal sampling must be in `[1, 128]`. The check runs in `_handle_parallel_sampling` before any list replication, and again in `verify`. An explicit JSON `null` still means one sample, same as leaving `n` out.
- Beam search does not copy the prompt, so when `beam_width > 1` the 128 cap is skipped and fan-out stays 1. `n` must still be an integer `>= 1`: `0` would return no sequences, and a negative `n` would slice from the end. `n` above `beam_width` is still rejected later by the beam coordinator.
- `top_logprobs_num` must be an integer in `[0, vocab_size]`, checked when a generate request is tokenized. `k == vocab_size` is allowed, so a reranker asking for 50 still passes. The Rust frontend checks the same bound in scheduler validation, which is the first place that knows the vocab size.

Deliberately unchanged:

- `top_k=-1` still disables the limit
- OpenAI's chat cap of 20 on `top_logprobs` (the bound is the vocab size)
- Rust parallel sampling, which already rejects `n != 1`
- The beam coordinator's existing `n <= beam_width` check

## Tests

```bash
python3 -m pytest -q \
  test/registered/unit/sampling/test_sampling_params.py \
  test/registered/unit/managers/test_io_struct.py
```

Covers `top_k` at `vocab_size` and at `TOP_K_ALL`, `top_k` past the vocab and past int32, `n` at 1 and 128, `n` of 0 and above 128, beam `n` above 128 that does not copy the prompt, beam `n` of 0 and -1, beam `n` above `beam_width` that still passes `verify`, a JSON `null` `n` that stays one prompt, and a tokenized generate request whose `top_logprobs_num` is past the vocab.

Rust: `verify` accepts `top_k == vocab` and rejects `top_k == vocab + 1` in both copies. `top_logprobs_num_is_bounded_by_vocab` calls `validate()` directly: 1001 against a vocab of 1000 returns the validation error, and `k == vocab_size` is accepted.

This environment has no Triton and no `cargo`, so the pytest files were not collected here and the Rust tests were not executed. The `SamplingParams` bounds were checked by importing that module directly.
