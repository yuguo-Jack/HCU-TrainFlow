# [Fix] Materialize contiguous int64 indices in the fused mamba conv-slot kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/42851) · state: open · merged: False

## Original PR description

## Motivation

`fused_clear_conv_slots` / `fused_copy_conv_slots` (`srt/mem_cache/mamba_slot_fused.py`) hand their index arrays to Triton kernels that read them with unit stride (`tl.load(index_arr + iid)`). The wrappers only do `indices.to(torch.int64)`, which is a no-op for a tensor that is already `int64` — so a **non-contiguous int64 view** (for example one column of a staged `[n, 2]` `(src, dst)` buffer, stride 2) is passed through unchanged and the kernel walks the wrong addresses: only the first slot is cleared/copied correctly and the rest land on neighbouring slots. `int32` inputs are not affected because `.to(torch.int64)` always materializes a fresh contiguous tensor for them, which is why the existing `test_int32_indices_accepted` could not catch this.

Today's callers happen to pass contiguous indices, so this is a latent correctness bug in the kernel wrapper rather than a reproduced end-to-end failure; the fix is three lines and keeps the wrappers safe for any caller.

## Modifications

- `python/sglang/srt/mem_cache/mamba_slot_fused.py`: add `_as_contiguous_i64()` (`.to(torch.int64).contiguous()`) and use it for the clear / copy index arrays.
- `test/registered/layers/mamba/test_mamba_slot_fused.py`: add `test_noncontiguous_int64_indices` — stride-2 `int64` views (`staged[:, 0]`, `staged[:, 1]`) for both clear and copy, checked bit-exact against the per-tensor reference loop.

## Accuracy Tests

- `test/registered/layers/mamba/test_mamba_slot_fused.py`: `7 passed` (16 subtests) with the fix on a CUDA GPU. On `main` (`660b17e8dc`) the new `test_noncontiguous_int64_indices` fails (`torch.equal(ref, got)` is false: the fused clear touches the wrong slots) and the other 6 pass.
