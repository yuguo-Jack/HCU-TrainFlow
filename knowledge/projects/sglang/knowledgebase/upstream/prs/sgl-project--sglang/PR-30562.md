# [sgl-kernel] Diagnose libtorch ABI mismatch on import instead of a cryptic undefined symbol

[Upstream PR](https://github.com/sgl-project/sglang/pull/30562) · state: closed · merged: False

## Original PR description

## Motivation

On a standalone `sglang-kernel` install next to a different PyTorch than it was built against, `import sgl_kernel` fails with `undefined symbol: c10::MessageLogger...`. That looks like a GPU-arch problem, so #29317 was filed as a "missing SM121 wheel" — but the wheel does contain `sm_121a`. The real cause is a PyTorch C++ ABI mismatch.

Docker and `pip install sglang` pin PyTorch to 2.11, so they aren't affected; this only hits the standalone-wheel + mismatched-torch case. #26598 is the long-term fix. Until then, this makes the error say the torch version is mismatched, so it stops getting misread as a missing arch.

## Modifications

- `load_utils.py`: on an `undefined symbol` failure, name the installed torch and the missing symbol instead of a generic reinstall/arch message.
- `load_utils.py` / `__init__.py`: add `load_common_ops()`; with `SGLANG_KERNEL_ALLOW_MISSING_OPS` set it warns and returns `None` instead of raising (debug only — kernels still raise if called).
- `tests/test_load_utils.py`: cover the ABI message, the non-ABI case, and the flag.
- `faq.mdx`: document the mismatch and the working install paths.

## Code Review

This pull request introduces a fallback mechanism for `sgl_kernel` when prebuilt binaries are missing for specific GPU architectures (such as NVIDIA GB10 / SM121). It allows the import to succeed with a warning when the environment variable `SGLANG_KERNEL_ALLOW_MISSING_OPS=1` is set, enabling models that rely on Triton/PyTorch fallbacks to run. The review feedback suggests improving the robustness of this fallback by supporting case-insensitive boolean parsing for the environment variable and using a dummy object instead of `None` to raise descriptive errors when missing operators are accessed.

> Why can we not add SM121 to the kernel archs

After looking into this, I made several changes to the PR. Turns out, the published cu130 aarch64 wheel already contains `sm_121a`:

```
$ cuobjdump sgl_kernel/sm100/common_ops.abi3.so | grep -oE 'sm_[0-9]+[a-z]*' | sort | uniq -c
  56 sm_90   56 sm_100a   56 sm_103a   56 sm_110a   56 sm_120a   56 sm_121a
```

(`sm90/`/`sm100/` are fast-math vs precise-math variants — both carry the full set.) `sm_121a` is at `CMakeLists.txt:222`, gated on CUDA ≥ 13.0 + aarch64. So the GB10 crash isn't a missing arch — it's a libtorch C++ ABI mismatch at import (`undefined symbol: c10::MessageLogger::stream[abi:cxx11]()`): the standalone wheel is built against torch 2.11.0 but declares `dependencies = []`, so it links against whatever torch is present. Across cu130/aarch64 torch builds only 2.11.0 imports; a source build against the installed torch works (incl. 2.13). I've reframed this PR around diagnosing that mismatch.

On your actual question, one gencode list does still lack SM121: `INFLLM_FLASH_CUDA_FLAGS` (`CMakeLists.txt:513-517`) emits only `sm_90` + `sm_120a`, and `infllm_ops` installs unconditionally (line 541), so on GB10 it has no loadable code (sm_120a is arch-exclusive to sm120, and there's no PTX for a JIT fallback). I confirmed the InfLLM kernels _do_ compile for `sm_121a` (they're generic SM80 FlashAttention kernels), so it looks like an "add the arch" fix rather than a guard-out. InfLLM-v2 (#29383) postdates the published v0.4.4 wheel (2026-06-17) so it didn't cause this issue. I can look into it separately.

Separately, a policy question for the wheel: would you want `sglang-kernel` to declare its build-target torch (e.g. inject `Requires-Dist: torch==<build version>` at build time) so pip refuses a mismatched torch up front, or keep it dependency-free by design? Happy to follow up with that change if you'd prefer the build-time declaration.

File: `sgl-kernel/python/sgl_kernel/__init__.py` · line None

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

To improve user experience and robustness, we can make two enhancements here:
1. **Case-Insensitive Boolean Parsing**: Instead of strictly checking `== "1"`, we can support other common truthy values like `"true"`, `"on"`, or `"yes"` (case-insensitive) to align with standard environment variable parsing in SGLang.
2. **Informative Dummy Object**: Setting `common_ops = None` will cause any subsequent call to raise a generic `AttributeError: 'NoneType' object has no attribute '...'`. We can define a lightweight dummy class `MissingCommonOps` that raises a clear, descriptive `RuntimeError` explaining that the compiled library could not be loaded, while preserving the original `ImportError` context.

```python
    _allow_missing_ops = os.environ.get("SGLANG_KERNEL_ALLOW_MISSING_OPS", "0").lower() in ("1", "true", "on", "yes")
    try:
        common_ops = _load_architecture_specific_ops()
    except ImportError as e:
        if not _allow_missing_ops:
            raise
        class MissingCommonOps:
            def __getattr__(self, name):
                raise RuntimeError(
                    f"[sgl_kernel] Compiled operator '{name}' is not available because the "
                    "compiled `common_ops` library could not be loaded. Please ensure "
                    "sgl_kernel is properly installed for your GPU/platform architecture."
                ) from e
        common_ops = MissingCommonOps()
```
