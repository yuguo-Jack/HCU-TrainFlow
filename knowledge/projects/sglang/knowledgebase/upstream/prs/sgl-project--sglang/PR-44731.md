# [Fix] DeepSeek-V4.1: Keep DP-attention decode collectives off per-graph registration on ROCm

[Upstream PR](https://github.com/sgl-project/sglang/pull/44731) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-dp-attention` and CUDA graph decode, DeepSeek-V4.1-Flash silently produces wrong output; nothing errors or crashes. Reproduced on MI355X with current main `d19f19d68` (TP4 + DP4 attention, paged FP8 KV, default DP communication settings):

- a short prompt sent alone decodes token 0 after its first token, or repeats one word until `max_tokens`;
- long prompts (about 16k tokens and up), alone or several at once, are correct;
- long and short prompts sent together: the long ones go wrong as well.

**Root cause.** For each batch size, DeepSeek-V4.1 captures several decode graphs (`Dsv41CandidateGraphVariants`: `candidate_all` up to 512 tokens, `candidate_c2_all` up to 1024, `candidate_unfiltered` up to 16384, filtered beyond that) and picks one from the longest request in the batch, so short contexts can skip low-ratio indexer scoring or candidate filtering. `DecodeCudaGraphRunner` picks from **this rank's** `seq_lens_cpu`; the DP ranks never agree on the pick.

Under DP attention the ranks replay their decode graphs together, and the collectives around the MoE are inside the graph. When one rank holds only short requests while another holds a long request or is idle, the ranks replay **different** graphs. The aiter custom all-gather, reduce-scatter and all-reduce register each captured graph's own buffers for IPC, so a rank reads the peer buffer that belongs to the other graph, i.e. stale data, and every rank's tokens are corrupted.

**Evidence.** Logging each rank's pick (local debug logging, not part of this PR) on main with TP4 + DP4 attention showed the ranks replaying different variants on most decode replays while the output was wrong, e.g. one rank with a 220-token request on `candidate_all` while the three idle ranks replayed `candidate_filtered`. With `--disable-custom-all-reduce`, or with all three aiter collectives kept off per-graph registered buffers (local debug patch), the output is correct although the ranks still replay different variants.

**Relation to #43077.** #43077 added `SGLANG_AITER_CAPTURE_COPY_IN` (default 0): during capture it stages the aiter all-gather and reduce-scatter inputs through the pre-registered IPC pool instead of registering per-graph buffers, which makes those two collectives independent of which graph a rank replays. It does not cover the aiter custom all-reduce, and it is off unless a recipe sets it. This PR completes it and turns it on where the ranks are known to replay different graphs.

## Modifications

- `custom_all_reduce.py`: with `SGLANG_AITER_CAPTURE_COPY_IN=1`, the aiter custom all-reduce is built with `enable_register_for_capturing=False`, as it already is under `SGLANG_MEMORY_SAVER_CUDA_GRAPH`, so all three aiter collectives in a captured graph stop reading per-graph registered peer buffers.
- `deepseek_v4_hook.py`: DeepSeek-V4.1 with DP attention on ROCm turns `SGLANG_AITER_CAPTURE_COPY_IN` on by default before the schedulers start; an explicit setting wins, and turning it off explicitly logs a warning.
- `environ.py`: `SGLANG_AITER_CAPTURE_COPY_IN` is not a new variable: main already read it in `parallel_state.py` through `os.environ`. It is now declared in `Envs` with the same default (off), and `parallel_state.py`, `custom_all_reduce.py` and the hook all read it through `Envs`. Only DeepSeek-V4.1 with DP attention on ROCm turns it on by default; an explicit setting always wins. The `parallel_state.py` comment now says it covers the all-reduce too.
- `test_dsv41_dp_attention_copy_in.py` (CPU): the hook turns the switch on for V4.1 + DP attention on ROCm and leaves an explicit value alone; with the switch on, the aiter all-reduce is built without graph registration. Both cases fail on main.

The per-rank decode graph variants stay as they are, so short contexts keep their speedup under DP attention.

## Scope

- Validated only on ROCm gfx950 (MI355X). The default only changes for DeepSeek-V4.1 with DP attention on ROCm; anyone who sets `SGLANG_AITER_CAPTURE_COPY_IN=1` elsewhere now also gets the all-reduce kept off graph registration.
- The DeepSeek-V4.1 cookbook (`docs/cookbook/autoregressive/DeepSeek/DeepSeek-V4_1.mdx`) sets `SGLANG_AITER_CAPTURE_COPY_IN=1` in its DP-attention commands. With this PR that line is no longer required on ROCm (the hook sets the same value), but it stays correct, so the cookbook is left unchanged.
- NVIDIA SM100 enables the same variants and also picks them per rank under DP attention; its collectives are different and this PR does not change or test them.
- The HIP DSA dense / sparse decode graphs (`DsaGraphVariants`, e.g. DeepSeek-V3.2) are also picked per rank and may have the same issue under DP attention; setting `SGLANG_AITER_CAPTURE_COPY_IN=1` covers their collectives too, but this PR neither turns it on for them nor tests them.

## Reproduction

DeepSeek-V4.1-Flash on 4x MI355X, image `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261025`:

```bash
SGLANG_USE_AITER=1 SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1 SGLANG_DSV41_ENGRAM_HOST_TABLE_LAYOUT=per_rank \
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code \
  --tp 4 --dp-size 4 --enable-dp-attention --kv-cache-dtype fp8_e4m3 --fp8-gemm-backend aiter \
  --enforce-shared-experts-fusion --max-running-requests 256 --cuda-graph-max-bs-decode 128 \
  --chunked-prefill-size 16384 --mem-fraction-static 0.70

curl -s localhost:30000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "deepseek-ai/DeepSeek-V4.1-Flash", "temperature": 0, "max_tokens": 1024,
  "messages": [{"role": "user", "content": "What is the capital of Australia? Answer in one sentence."}]}'
```

- main: wrong or runaway output (on this prompt the reasoning turns into a run of `<｜begin▁of▁sentence｜>`, token 0, until `max_tokens`); none of our 14 greedy prompts come back right.
- This PR, same command (no extra environment): all 14 greedy prompts and all 21 cases of a mixed long / short probe are right.

The InferenceY DP recipe (TP2 + DP2 + DSpark) already sets `SGLANG_AITER_CAPTURE_COPY_IN=1`, which covers the all-gather and reduce-scatter but not the all-reduce, so on main the recipe still goes wrong now and then: in five runs of the same mixed probe main got 20/21 and 21/21 (main `306ccf6f5`), 18/21 (`30dc2f943`) and 21/21 twice (`d19f19d68`); in the first, a 38k-token prompt sent together with short ones answered wrong and ran to `max_tokens`. This PR answered all 21 cases right in four runs with the same recipe (`306ccf6f5` twice, `d19f19d68` twice); in a fifth, with another server running on the same node, one 28k-token prompt kept reasoning in readable text past the 1024 output tokens and gave no answer, and it was right when that run was repeated.

## Speed Tests and Profiling

The InferenceY DP recipe (TP2 + DP2 + DSpark, `SGLANG_AITER_CAPTURE_COPY_IN=1` and the recipe's other DP settings), main vs this PR on one node at the same time (2 GPUs each), measured before the rebase on main `306ccf6f5` with image `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261016`; with this PR the only difference is the all-reduce kept off graph registration. `bench_serving` with random token ids, 5 x concurrency requests, the radix cache flushed before every run; four runs per point over two jobs, the two servers alternating which goes first. Mean output tok/s (min–max) and mean TPOT:

| Input / output | Concurrency | main | This PR |
|---|---|---|---|
| 8k / 1k | 64 | 3914 (3854–3993), 11.10 ms | 3960 (3903–4012), 10.94 ms |
| 1k / 1k | 64 | 6077 (5477–6574), 8.15 ms | 5978 (5207–6334), 8.31 ms |

The means are within 2% (8k / 1k: +1.2% throughput, -1.4% TPOT; 1k / 1k: -1.6% throughput, +2.0% TPOT), well inside the spread of repeated runs of the same server (up to 20% at 1k / 1k, where the first run of each job also pays its warm-up). KV capacity is unchanged (same `max_total_num_tokens` on both servers in each job). One more run on `d19f19d68` (image `rocm/sgl-dev:v0.5.22-rocm10-mi35x-20261025`) agrees: 8k / 1k 4036 vs 4043 tok/s (TPOT 10.78 vs 10.63 ms), 1k / 1k 5398 vs 5297 tok/s (TPOT 8.36 vs 7.89 ms), main vs this PR.

## Alternatives considered

- **One decode graph per batch size under DP attention** (the earlier revision of this PR): under DP attention, drop the per-rank decode graph variants so every rank captures and replays the single graph that long contexts already use. The ranks can then never replay different graphs, whatever the collectives do, but short-context decode under DP attention no longer skips low-ratio scoring and candidate filtering, so short contexts lose that speedup. It is a few lines in `decode_cuda_graph_runner.py` and can replace this PR if the variants are not worth keeping under DP attention.
- **All DP ranks pick by the global longest request.** One more integer in the per-step DP sync would keep the variants and make the ranks agree, but it touches the scheduler, the batch, `ForwardBatch` and the variant classes.
