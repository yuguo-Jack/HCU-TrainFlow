# [Fix] DeepSeek-V4.1: Keep one decode graph per batch size under DP attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/44731) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-dp-attention` and CUDA graph decode, DeepSeek-V4.1-Flash silently produces wrong output; nothing errors or crashes. Reproduced on MI355X with current main (TP4 + DP4 attention, paged FP8 KV, default DP communication settings):

- a short prompt sent alone decodes token 0 after its first token, or repeats one word until `max_tokens`;
- long prompts (about 16k tokens and up), alone or several at once, are correct;
- long and short prompts sent together: the long ones go wrong as well.

**Root cause.** For each batch size, DeepSeek-V4.1 captures several decode graphs (`Dsv41CandidateGraphVariants`: `candidate_all` up to 512 tokens, `candidate_c2_all` up to 1024, `candidate_unfiltered` up to 16384, filtered beyond that) and picks one from the longest request in the batch, so short contexts can skip low-ratio indexer scoring or candidate filtering. `DecodeCudaGraphRunner` picks from **this rank's** `seq_lens_cpu`; the DP ranks never agree on the pick.

Under DP attention the ranks replay their decode graphs together, and the collectives around the MoE are inside the graph. When one rank holds only short requests while another holds a long request or is idle, the ranks replay **different** graphs. The aiter custom all-gather, reduce-scatter and all-reduce register each captured graph's own buffers for IPC, so a rank reads the peer buffer that belongs to the other graph, i.e. stale data, and every rank's tokens are corrupted.

**Evidence.** Logging each rank's pick (local debug logging, not part of this PR) on main with TP4 + DP4 attention showed the ranks replaying different variants on most decode replays while the output was wrong, e.g. one rank with a 220-token request on `candidate_all` while the three idle ranks replayed `candidate_filtered`. With `--disable-custom-all-reduce`, or with all three aiter collectives kept off per-graph registered buffers (local debug patch), the output is correct although the ranks still replay different variants.

**Relation to #43077.** #43077 added `SGLANG_AITER_CAPTURE_COPY_IN` (default 0), which stages the aiter all-gather and reduce-scatter through the pre-registered IPC pool during capture instead of registering per-graph buffers. It does not cover the custom all-reduce, so on its own it does not fix this bug. The InferenceY DeepSeek-V4.1 DP recipe sets it together with other settings, and with the full recipe the output is correct; removing only `SGLANG_AITER_CAPTURE_COPY_IN` from the recipe brings the bug back (a short prompt sent alone loops "Weohohoh..." until `max_tokens`). With the default settings on ROCm, DeepSeek-V4.1 with DP attention is exposed. Rather than making each in-graph collective tolerate ranks on different graphs, this PR makes all DP ranks replay the same graph.

The variants come from #38798 and were enabled on gfx950 by #41308.

## Modifications

- `decode_cuda_graph_runner.py`: `_rank_consistent_attention_graph_variants()` drops the DeepSeek-V4.1 per-rank variants (`create_dsv41_candidate_graph_variants`) under DP attention, so each batch size captures the single graph that long contexts already use, which is correct for any length. This covers the decode graphs and the DSpark target-verify graphs (same runner). The server logs what it drops, e.g. `DP attention: per-rank attention graph variants ('candidate_all', 'candidate_c2_all', 'candidate_unfiltered', 'candidate_filtered') disabled`. Without DP attention nothing changes; the dLLM runner does not go through this path.
- `test_decode_cuda_graph_runner.py`: the variants are dropped with DP attention and kept without it.

## Scope

- Validated only on ROCm gfx950 (MI355X). NVIDIA SM100 enables the same variants and also picks them per rank under DP attention; not verified there.
- Only the DeepSeek-V4.1 variants change. The HIP DSA dense / sparse decode graphs (`DsaGraphVariants`, e.g. DeepSeek-V3.2) are also picked per rank and may have the same issue under DP attention; this PR neither changes nor tests them.

## Reproduction

DeepSeek-V4.1-Flash on 4x MI355X, image `rocm/sgl-dev:v0.5.21-rocm720-mi35x-20261015`:

```bash
SGLANG_USE_AITER=1 SGLANG_ENABLE_DSV41_ENGRAM_HOST_TABLE=1 SGLANG_DSV41_ENGRAM_HOST_TABLE_LAYOUT=per_rank \
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code \
  --tp 4 --dp-size 4 --enable-dp-attention --kv-cache-dtype fp8_e4m3 --fp8-gemm-backend aiter \
  --enforce-shared-experts-fusion --max-running-requests 256 --cuda-graph-max-bs-decode 128 \
  --chunked-prefill-size 16384 --mem-fraction-static 0.70

curl -s localhost:30000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "deepseek-ai/DeepSeek-V4.1-Flash", "temperature": 0, "max_tokens": 1024,
  "messages": [{"role": "user", "content": "What is the capital of Australia? Answer in one sentence."}]}'
```

- main: `We之星之星之星之星…` until `max_tokens`.
- This PR: a one-sentence answer naming Canberra.

The InferenceY DP recipe (TP2 + DP2 + DSpark, which sets `SGLANG_AITER_CAPTURE_COPY_IN=1`) answers correctly on main; with only `SGLANG_AITER_CAPTURE_COPY_IN` removed from that recipe, main returns `Weohohohoh…` until `max_tokens` for the same request, and this PR answers correctly.

## Accuracy Tests

Setup: MI355X, DeepSeek-V4.1-Flash, image `rocm/sgl-dev:v0.5.21-rocm720-mi35x-20261015` with the branch's whole `python/sglang` mounted over the image's, this PR rebased onto `06b81b120`, model default context (1M), server as in Reproduction (TP4 + DP4 attention, default DP communication, `SGLANG_AITER_CAPTURE_COPY_IN=0`).

sgl-eval 0.1.3 GSM8K, the settings of `test_deepseek_v41_flash_gb300.py` (`--load-preset-from-model-id deepseek-ai/DeepSeek-V4.1-Flash --max-tokens 4096 --num-threads 64`), all 1319 questions:

| | main | This PR |
|---|---|---|
| GSM8K | **11.14%** | **95.83%** |

The same comparison with lm-evaluation-harness (`local-chat-completions`, 5-shot, through the InferenceX eval entry; strict-match / flexible-extract): main 0.9128 / 0.8931, this PR 0.9719 / 0.9712, and main with `SGLANG_AITER_CAPTURE_COPY_IN=1` 0.9689 / 0.9629. With the InferenceY DP recipe (TP2 + DP2 + DSpark), this PR scores 0.9750 / 0.9742 on the same harness.

No server faults or NaN in any run.

An earlier revision of the same change (on top of #44031, main `d8f85223`) was also used for cross-node PD with DP attention on the decode side (TP8 + DP8 and TP4 + DP4): GSM8K 0.9719–0.9757 through the router.

## Speed Tests and Profiling

**Graph capture**: TP4 + DP4 decode graphs 61.3 s / 1.97 GB on main vs 61.6 s / 1.91 GB with this PR; the DP recipe's target-verify graphs 42.1 s / 2.57 GB vs 37.8 s / 2.53 GB.

**Cost**: under DP attention, short-context decode (16k tokens or less) no longer skips low-ratio scoring and candidate filtering.

Short-context throughput: InferenceY DP recipe (TP2 + DP2 + DSpark, where main is correct), `bench_serving` with random token ids, 1k input / 1k output, 4 x concurrency requests; main and this PR side by side on one node (2 GPUs each). Second of two rounds; the first round right after startup varied in both directions.

| Concurrency | main: output tok/s, TPOT | This PR: output tok/s, TPOT |
|---|---|---|
| 4 | 1258, 2.79 ms | 1187, 2.83 ms |
| 32 | 4458, 5.80 ms | 4166, 5.90 ms |
| 64 | 6210, 7.80 ms | 5855, 7.96 ms |

With this PR, TPOT is 1.4–2.1% higher and output throughput 5.6–6.5% lower (throughput also moves with the DSpark acceptance rate). This is the cost of the short-context variants under DP attention; the "Alternatives" section below would keep them.

## Alternatives considered

- **All DP ranks pick by the global longest request.** One more integer in the existing per-step DP sync would keep the short-context speedup, but it touches the scheduler, the batch, `ForwardBatch` and the variant classes, and an off-by-one between the synced length and the length used for the pick selects a wrong graph at the 512 / 1024 / 16384 boundaries without any error. It can be a follow-up if reviewers want to keep the short-context path.
- **Turning `SGLANG_AITER_CAPTURE_COPY_IN` on by default.** It only covers the aiter all-gather and reduce-scatter, not the custom all-reduce, and the ranks would still replay different graphs.
