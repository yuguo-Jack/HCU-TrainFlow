# [Fix] hicache: Reject incomplete NIXL cache files before reading

[Upstream PR](https://github.com/sgl-project/sglang/pull/46131) · state: open · merged: False

## Original PR description

## Motivation

Refs #45563. A failed NIXL write can leave an empty or truncated cache file. The current lookup treats any existing file as a hit, and NIXL 1.4.0 can report a short read as successful. This lets a restore publish incomplete KV or sidecar data. The issue reports incorrect DSA outputs after restoring empty indexer files.

Lookup checks alone are insufficient: hybrid restores using `assume_stored` can skip lookup. Validate the requested byte count at the shared read entrypoint before starting a transfer.

## Modifications

- Treat empty FILE objects as lookup misses.
- Reject FILE reads when any file is missing or smaller than its corresponding host buffer. Reuse the existing transfer sizes, including unequal Mamba component sizes; allow larger files for alignment padding. A rejected transfer leaves its destination unchanged and uses the existing failure propagation.
- Extend the existing POSIX tests with real truncated files for KV copy/zero-copy, indexer copy, and Mamba zero-copy paths. Cover empty, one-byte-short, complete, and padded files.

The production change adds 19 lines, with no new configuration or cached metadata. OBJ and write paths retain their existing behavior. This addresses the unsafe restore part of #45563; write alignment and batch chunking are separate work tracked by #35231, #42491, #36524, and #37690. It does not detect same-size corruption or make concurrent writes atomic.

## Speed Tests and Profiling

Each FILE read adds one batched metadata query. Measured real `batch_get_v1` on the same cache, files, and CPU tensors, switching only the original/patched transfer method. POSIX, warm Linux filesystem cache, O_DIRECT disabled, two files per logical page. Each of three process runs used 8 warmups and 120 measured reads per variant, with alternating order.

| Page size | Pages per batch | Median before / after (microseconds) | Median change across runs |
|---|---:|---:|---:|
| 8 KiB | 1 | 394.5 / 404.2 | +2.5% to +4.5% |
| 8 KiB | 32 | 647.6 / 702.1 | +7.8% to +15.8% |
| 8 KiB | 128 | 1821.8 / 2113.1 | +15.2% to +16.0% |
| 256 KiB | 1 | 419.1 / 435.5 | -5.4% to +4.8% |

Latency columns are the medians of the three per-process medians. All data restoration checks passed. The 128-page cases add roughly 0.21–0.34 ms. Single-page differences approach measurement noise. These are local CPU/POSIX microbenchmarks, not serving throughput measurements; remote filesystem metadata queries may cost more. GDS/3FS, cold-cache I/O, and end-to-end inference performance were not measured.
