# [Perf] [AMD] qwen3.5: Run each Qwen3.8 decode layer as two persistent FlyDSL launches on MI355X

[Upstream PR](https://github.com/sgl-project/sglang/pull/43516) · state: open · merged: False

## Original PR description

## Motivation

This PR speeds up Qwen3.8 (`Qwen3_5MoeForCausalLM`) decode on MI355X with ROCm. In a decode step of 8 rows or fewer, each of the 92 decoder layers runs as two persistent FlyDSL launches, ported from vllm-project/vllm#60833. Today each layer takes about a dozen kernel launches and two all-reduces, so small decode steps wait on launches and syncs. On one 8x MI355X node on `main`, TP8, no MTP, at 8k/1k, median TPOT drops **37% at concurrency 1**, with 56% more output tok/s. At concurrency 4 it drops 29%, with 40% more output tok/s. With NEXTN MTP, the second launch alone on the verify steps gives 31% more output tok/s at concurrency 1.

The change is off by default, and `SGLANG_QWEN3_5_MONO_DECODE=1` turns it on. A step it does not cover keeps the existing path. These are prefill and mixed steps, steps of more than 8 rows, PP, and any setup other than TP8 on gfx950. With the flag unset, only `qwen3_5.py` changes on the default path. Its attention and GDN forwards now call `attention_core()` or `core()`, then `o_proj` or `out_proj`. These are the same ops in the same order.

**Stacked on #43481.** That PR adds the Kimi-K3 mono framework, `k3_mono_flydsl/common` and `stages/gemv.py`. The Qwen kernels import it unchanged, so this PR does not carry a second copy. Only the commits after #43481 are new here. I will rebase once #43481 lands.

## Modifications

- `kernels/ops/moe/qwen3_5_mono_flydsl/` has the K1 and K2 kernels of #60833 at `3346929b27` and their layout module, with the imports changed to `k3_mono_flydsl`. One change is new. K1 also takes a bf16 SSM state. It widens the state to fp32 for the recurrence and rounds it on store, as the stock GDN kernel does. The dtype is part of the K1 build key.
  - K1 (`gdn_pre`, 69 GDN layers) runs the residual add and input norm, `in_proj_qkvz` and `in_proj_ba`, conv1d, the gated delta rule and the gated norm. It writes the input of `out_proj`.
  - K2 (`layer_post`, all 92 layers) runs `out_proj` or `o_proj` with an in-kernel TP all-reduce, the residual add and post norm, the top-10 router over 512 experts, the MXFP4 experts, the sigmoid-gated shared expert and the MoE all-reduce.
- `srt/layers/moe/qwen3_5_mono_decode.py` binds the kernels to SGLang's state. It reads the GDN state from the mamba pool of the hybrid backend, with `mamba_cache_indices`, conv `(slots, dim, 3)` and SSM `(slots, HV, V, K)` in fp32 or bf16. The weight-layout options of #60833 stay off. These are the fused shared expert, MXFP4 `o_proj`, `out_proj` and `in_proj_qkvz`, and the output gate in K2. SGLang loads those weights as bf16 and applies the gate in `attention_core()`. The kernels skip pad rows, marked `-1`, and the reserved slot 0. The glue checks the weights once at the first decode step. When it turns itself off, it logs the reason.
- `models/qwen3_5.py` splits `self_attention`, so `attention_core()` returns the input of `o_proj`. The 23 full-attention layers keep SGLang's fused HIP front and attention, then run K2. The GDN layer's `forward` splits the same way, and `core()` returns the input of `out_proj`. The text model's `forward` hands covered decode and target-verify steps to the mono path. The decode CUDA graph captures that path at widths 1, 2, 4 and 8.
- `environ.py` adds `SGLANG_QWEN3_5_MONO_DECODE`.
- The docs add the flag to `docs/references/environment_variables.mdx`.

The glue checks these requirements at runtime: TP8, gfx950 and `--disable-shared-experts-fusion`, because K2 runs the shared expert itself. Without speculative decoding, K1 also needs an fp32 or bf16 SSM state and no ReplaySSM ring. The glue also turns mono off on a GPU with fewer than 256 CUs, because a partitioned GPU cannot keep all 256 spinning CTAs resident. It does the same with HiCache or LMCache, because their copy kernels on another stream can hold CUs that those CTAs wait on. The launch argument checks raise `ValueError` instead of using `assert`, so `python -O` keeps them. Both changes follow the current #60833 head.

This PR has a known problem on ROCm 10 images. The peer buffer uses aiter's `UncachedIpcHeap`, and its `load_hip_runtime()` opens `libamdhip64.so` by name. With `_rocm_sdk_devel/lib` on `LD_LIBRARY_PATH`, that maps the devel HIP runtime next to the core copy that torch loads. This brings back the bug that #39513 fixed. `vattn_asm` binds to the first `libamdhip64` in `/proc/self/maps`, and #39513 assumed that this is always the copy of torch. Graph capture can then fail with this error.

```
RuntimeError: vattn_asm: hipModuleLaunchKernel failed: 709 (context is destroyed)
```

The failure needs all of these:

- A ROCm 10 image with `_rocm_sdk_devel/lib` on `LD_LIBRARY_PATH`. `rocm720` and `rocm724` images map one runtime, so they are not affected.
- Mono decode on, so the peer buffer imports `UncachedIpcHeap`.
- `vattn_asm` in use. That needs gfx950, the aiter backend, `--page-size 16`, head dim 256, and `SGLANG_ASM_VERIFY_ATTN` at its default of 1. Since #37465, `vattn_asm` runs plain q_len 1 decode (`forward_decode` calls `unified_attention_3d_mtp_decode_func`) as well as MTP target verify and draft extend. So non-MTP runs hit it too. Other page sizes do not use `vattn_asm`.

The failure is intermittent. It broke two of three non-MTP server starts here, in the decode graph capture. [ROCm/aiter#6398](https://github.com/ROCm/aiter/pull/6398) makes `load_hip_runtime()` bind to the copy that is already mapped. With that file mounted, no later start failed, with or without MTP. `smallm_moe_gfx950` looks up HIP the same way, so it is exposed too, but I have not seen it fail. #43481 imports the same `peer_memory.py`, so it also maps the second runtime on ROCm 10.

| SGLang, mono off (stock) | 0.8446 | 0.8302 |

An exact per-question McNemar test, mono on against off, finds no difference. For flexible-extract, 87 questions are right only with mono and 79 only without, p = 0.59. For strict-match the counts are 81 and 83, p = 0.94. RULER `niah_single_2` at 128k scores 0.992 with mono on.

With MTP, K2 runs only on the verify steps, as the MTP section below describes. GSM8K at concurrency 2 against the same MTP server with the flag off shows no difference. Flexible-extract is 0.8582 against 0.8461, with 85 questions right only with mono and 69 only without, p = 0.23. Strict-match is 0.8446 against 0.8370, p = 0.47.

GPQA Diamond and RULER `niah_single_2` ran at concurrency 8, so every decode step is in the mono range. Flag on and flag off use the same server config.

| | flag off | flag on |
| --- | --- | --- |
| GPQA Diamond, thinking, temperature 1.0 (2 runs each) | 0.884, 0.924 (mean 0.904) | 0.894, 0.934 (mean 0.914) |
| NIAH 64k (500 questions) | 0.994, 0.996 (2 runs) | 0.996 |
| NIAH 128k (500 questions) | 0.996, 1.000 (2 runs) | 0.992 |

GPQA samples at temperature 1.0, and the two runs of one arm differ by 4 points, so the 1-point gap is noise. NIAH is greedy. Paired per question, mono against each flag-off run gives p = 0.63 and 0.13 at 128k and p = 1.0 at 64k. The two flag-off runs also disagree with each other on 2 to 5 questions. No difference.

The unit tests in `test/registered/amd/test_qwen3_5_mono_decode.py` run on 1 GPU. They check that every fp4 byte and e8m0 scale of SGLang's gfx950 expert layout is where K2 reads it. K1 runs at widths 1, 4 and 8 against SGLang's pool layout. It writes the live rows and leaves pad rows and other slots unchanged. With a bf16 state, K1 gives the same core output and conv state as with the widened fp32 state. Its new state equals the new fp32 state rounded to bf16. The tests pass on MI355X in the v0.5.21-based image and on `main`, here the ROCm nightly of 2026-10-09 with this branch's files. The file has not run in CI yet.

The batch-invariance test in `test/registered/amd/test_qwen3_5_mono_batch_invariance.py` runs K1 on 1 GPU and K2 on 8 GPUs. It keeps one probe row fixed and changes the other rows of the step. The probe outputs must be bitwise the same at widths 1 to 8, and equal to the probe run alone. It passes on MI355X on the ROCm 10 `main` nightly.

### MTP

With speculative decoding on, K1 is off and K2 runs alone on the target-verify steps. GDN layers run SGLang's own input projection and core, then K2 runs `out_proj` and the MoE. K1 cannot run there, because it has no per-draft-token state for the SSM rollback. NEXTN runs 3 draft steps with top-k 1, so a verify step has 4 rows per request, one for each of the 4 draft tokens. Mono covers only c1 with 4 rows and c2 with 8 rows. The K1 requirements on the SSM state dtype and the ReplaySSM ring do not apply then.

The MTP A/B uses the same setup plus `--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`, so the reference is the same server without the flag.
