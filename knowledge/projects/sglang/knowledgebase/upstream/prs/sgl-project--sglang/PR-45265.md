# [Feat] deepseek-v4.1: Encoder-only prefill for PD (--dsv41-encoder-only-prefill)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45265) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

RFC #39963: on DeepSeek-V4.1-Flash, layers 21-39 own only a 128-token SWA window, so a PD prefill server needs only layers 0-19 plus the KV producers of layer 20 (the boundary `kv_source`). Dropping the rest halves prefill weights, which leaves more HBM for prefill KV and prefix cache.

This implements the RFC's split, the same semantics TRT-LLM shipped in NVIDIA/TensorRT-LLM#19727: prefill stops `128` tokens short of the prompt end, and decode runs those last tokens as an ordinary extend. It reuses the weight split and boundary layer from #40874 (credited as co-author) but differs in the handoff. #40874 transfers only global KV and has decode replay the last 128 tokens through all 40 layers without the encoder's SWA. Here prefill sends the stock SWA window, so the result equals same-server decoder bounded replay.

**Impact**
- **Accuracy:** GSM8K (1319 questions): split PD 0.905, stock PD 0.899. GPQA diamond (`sgl-eval`, ~395 answers per arm): split 90.4-90.9%, stock + prefill HiCache 91.9%, within the ~2-point standard error.
- **Performance, cache-bound point** (GB300 1P1D, AgentX c160): +5.6% requests/s over stock PD and p90 TTFT 13.7 → 1.8 s, from HBM alone; 4% behind stock with a prefill HiCache host tier.
- **Performance, max-throughput point** (GB300, 10 prefill workers + one DEP16 decode, AgentX c6400, with the fused-tail follow-up #46727): 906k vs 909k tok/s/GPU (tie), p90 TTFT −38%, p90 interactivity −4%. The split removes the prefill bottleneck at this P/D ratio and decode becomes the limit; runs with fewer prefill workers are in progress.

## Modifications

**+867 / −81 runtime code (18 files), +609 tests (5 files), +6 docs (1 file).** No kernel changes.

`--dsv41-encoder-only-prefill`, set on both servers.

**Prefill**
- Loads layers `0..boundary-1` plus the boundary layer's input norm, compressor and indexer K (`DeepseekV41EncoderBoundaryLayer`). No final norm, `lm_head`, `hc_head` or MTP. `end_layer = boundary + 1`, so the KV pool covers only layers `0..boundary` (the PP layer-range path). Only layers `0..boundary-1` send SWA: decode floors the later layers at the tail start and never reads theirs.
- Truncates each prompt at intake to `s = max(0, N - sliding_window_size)`, rounded down to even. The stock Mooncake transfer then sends global KV for `[0, s)` and the SWA window ending at `s`. An even `s` leaves no half-filled ratio-2 compressor pair, so no request-scoped state is transferred and the peers' pair rings may differ in size (decode with speculative decoding keeps 8 rows, prefill 2). Decode's tail is then 128 or 129 tokens; layer 20 writes its KV source for every tail row, so both are exact.
- `s == 0` (prompts of 128 tokens or fewer) sends an empty handoff without a forward.
- The forward returns no logits and prefill commits no token: decode samples the first token (and runs any grammar on it).
- Metadata slot 7 carries `s`; decode aborts the request if it differs from its own split point.
- Works with `--enable-encoder-swa-bounded-replay`: prefix hits rebuild the encoder SWA window as on stock prefill. The split forward returns no logits, so the replay's folded-row trim is skipped.

**Decode**
- Preallocates and receives only `[0, s)`.
- On arrival the request runs `[s, N)` as an extend, i.e. the last chunk of a chunked prefill. Main's decoder bounded replay floors layers 20-39 at `seq_len - 128 = s`; layers 0-19 read the transferred SWA.
- The extend batch merges into the running batch on the next step, and alternates with decode steps so new arrivals don't stall running requests.
- The tail replays in the breakable prefill CUDA graph by default, at any context length. The ratio-1/2 compressor and indexer run as eager breaks (as in the decoder tail graph), so no captured candidate window bounds the context; the eager breaks see only the live rows of the bucket. `--cuda-graph-backend-prefill disabled` on decode runs the tail eagerly.
- Works with decode DP attention and with DSpark on decode: the tail extend goes through the draft worker's prefill path (target hidden capture, draft KV injection), so decode drafts from its own tail and prefill sends no draft state. With DP attention, tail extends and speculative decode steps run on separate steps, as in collocated serving.
- Retraction resumes through the stock rebootstrap path: prefill re-prefills `origin + output[:-1]`, and the tail replays the last emitted token as input.
- `SGLANG_DSV41_TAIL_HOLD_MS` (default 0, off): while decode has work, waiting tails run only on the first step of each period, so one extend step serves several tails. The period is counted in forward steps (nominal 20 ms each), so every TP and DP rank makes the same choice.

**Prefill DP attention:** every rank runs layers `0..boundary` in lockstep and returns no logits; the MLP-sync post-processing now skips the missing logits.

**Speculative decoding runs only on decode.**
- The prefill server has no final layers or LM head, so it cannot run the DSpark draft model. In stock PD, prefill runs DSpark only to build the draft's starting state before the handoff.
- Here decode builds that state while it replays the tail through all 40 layers.
- DSpark's draft attention is a 128-token sliding window (`compress_ratio == 0` in `deepseek_v4_dspark.py`), so the replayed tail is exactly the context the draft needs.
- Real acceptance agrees. On AgentX c160 (one GB300 node, DSpark block 5, weighted by running requests), stock PD on this PR's earlier base averaged 3.44 accepted tokens per verify step. The split on main c1c287a4, with `SGLANG_DSV41_TAIL_HOLD_MS=500`, also averaged 3.44.

**Validation** rejects: non-V4.1, compression ratios other than 0/1/2 (an even split leaves no pending compressor state only up to ratio 2), non-Mooncake, speculative decoding on prefill, PP, CP, CUDA graphs on the prefill server, mixed chunk, LoRA, decode radix cache, decode KV offload, KV checksums, and decode without decoder replay. Prefill and decode reject the same requests with 400: multimodal input, input embeddings, prompt logprobs, hidden states, routed experts, indexer top-k, sampling masks.

## Speed Tests and Profiling

### Cache-bound point: 1P1D, c160 (measured on this PR's earlier base)

AgentX (`semianalysis_cc_traces_weka_062126`, 900 s), InferenceX GB300 1P1D recipe: prefill TP2/EP2, decode TP2/EP2, DSpark block 5, Mooncake over MNNVL, prefill CUDA graphs off in every arm.

| c160 | stock | stock + HiCache (prefill) | split, eager tail | split, graphed tail |
|---|---|---|---|---|
| prefill KV pool (tokens) | 32.8M | 32.8M + host | 94.4M | 94.4M |
| prompt cache hit / theoretical | 89.7% / 96.0% | 95.3% / 96.1% | 94.6% / 95.6% | 94.8% / 96.0% |
| TTFT p50 / p90 | 2.54 / 13.7 s | 0.73 / 2.05 s | 0.76 / 1.96 s | 0.55 / 1.77 s |
| ITL p50 | 11.0 ms | 12.6 ms | 29.4 ms | 15.8 ms |
| requests/s | 5.37 | 5.93 | 4.60 | 5.67 |

At c160 the stock prefill is cache bound (InferenceX reports 83% hit and 14 s p90 TTFT for this point). The split recovers the hit rate and TTFT from HBM alone, like HiCache does with host memory. Run eagerly, each request's 128-token tail cost decode about 100-180 ms of launches per step and the split lost 14% against stock. Replayed in the breakable graph, the tail costs 23 ms at 8k context and 40-47 ms at 131k (16 tails together: 65 ms at 8k), and the split is 5.6% faster than stock, 4% behind stock + HiCache. The remaining cost is decode's inter-token latency, which tail steps raise from 11.0 to 15.8 ms. At c96, where stock is not cache bound, the eager-tail split was 21% slower.

### Max-throughput point: 10 prefill workers + DEP16 decode, c6400

SGLang's best max-throughput PD configuration for this model on GB300 so far, served with Dynamo 1.6 and its KV router on 10 nodes (36 GPUs; the tenth node runs the frontend and client).
- **Prefill:** 10 workers, each TP2 with DP attention 2 and EP2, memory fraction 0.9. KV tiers: Mooncake store through the unified-cache external linker, plus HiCache (ratio 1.02, write-back). Encoder and decoder SWA bounded replay, `--swa-prefix-tails 2048`, DSpark.
- **Decode:** one DEP16 worker, DSpark block 5 with the configuration's simulated acceptance (3.51), EPLB with 16 redundant experts, CUDA graphs to batch 128.
- **Build:** main 39b54ae0ee, image `lmsysorg/sglang:nightly-dev-cu13-20261025-65633129`.
- **Run:** AgentX at concurrency 6400, one 1800 s run per arm, same cluster and time. Throughput is the 600-1800 s window; latency percentiles cover the whole run.

**Split arm changes:**
- `--dsv41-encoder-only-prefill` on both roles.
- Prefill: drops DSpark (rejected with the split), the external store and linker, and keeps a HiCache host tier at ratio 0.5.
- Decode: the fused-tail follow-up #46727 (`SGLANG_DSV41_FUSED_TAIL=1`, not in this PR), CUDA graphs to batch 144 and 2304 max running requests (16 tail slots per rank).

| | stock | split |
|---|---|---|
| tok/s/GPU (input incl. cached + output, 36 GPUs) | 909k | 906k |
| requests/s | 235.8 | 234.4 |
| p90 interactivity (1000 / p90 ITL) | 117.4 tok/s | 112.7 tok/s |
| ITL p50 / p90 | 7.44 / 8.52 ms | 8.38 / 8.87 ms |
| TTFT p50 / p90 / p99 | 5.9 / 17.6 / 67.2 s | 5.2 / 11.0 / 48.8 s |
| prefill requests queued per rank, mean / median | 53 / 40 | 5 / 0 |
| prompt tokens from prefill GPU cache / host or store (whole run) | 80.8% / 13.1% | 94.0% / 0.2% |
| decode running requests per rank, mean / median (cap) | 108 / 114 (128) | 125 / 143 (144) |

Here stock is prefill-bound: requests queue at every prefill rank, and 13% of prompt tokens are reloaded from the host tier and the Mooncake store. The split serves 94% of prompt tokens from its larger GPU pool, and its prefill queue stays empty. That moves the limit to decode: its slots stay full, with about 39 requests waiting per rank.
- Throughput stays the same at this P/D ratio.
- TTFT falls (p90 −38%).
- The larger decode batch plus the tail rows cost 4% of p90 interactivity.

The freed prefill capacity should let the same decode hold this rate with fewer prefill GPUs.

## Known gaps (follow-ups)

- P/D ratio: with the split, the layout above is decode-bound with spare prefill capacity. Runs with 8 and 7 prefill workers are in progress.
- The max-throughput result uses the fused-tail follow-up #46727 (tail rows run inside decode's verify steps). It is not in this PR; without it, tail extends alternate with decode steps (c160: ITL 11.0 → 15.8 ms).
- Tail work still raises decode inter-token latency (c6400 with fused tails: p50 +13%, p90 +4%).
- `test_disaggregation_dsv41_encoder_only_prefill.py` (8-gpu-b300, extra-b) has not run yet.
