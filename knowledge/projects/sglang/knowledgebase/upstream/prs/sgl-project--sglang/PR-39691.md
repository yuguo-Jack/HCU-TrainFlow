# [MoE] Add flashinfer_cutedsl_fp8 runner backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/39691) · state: closed · merged: False

## Original PR description

## Motivation

FlashInfer flashinfer-ai/flashinfer@82316cda (flashinfer-ai/flashinfer#4734) adds `flashinfer.gemm.group_gemm_fp8_nt_groupwise_contiguous`, a
persistent CuTe DSL contiguous grouped FP8 GEMM for SM100/SM103 with 1x128 activation and
128x128 weight block scales. This PR exposes it as an MoE runner backend so 128x128
block-quantized FP8 MoE checkpoints (Qwen3-*-FP8, DeepSeek-V3-style) can run on datacenter
Blackwell through FlashInfer instead of DeepGEMM or the Triton fused MoE.

## Modifications

- `--moe-runner-backend flashinfer_cutedsl_fp8` (new `MoeRunnerBackend` value + predicate,
  CLI choice, docs row).
- `moe_runner/flashinfer_cutedsl_fp8.py`: fused func for the standard dispatcher
  (`register_fused_func("none", ...)`, same shape as the `hpc_ops` backend): per-token-group
  fp8 quant -> `ep_scatter` into the 128-aligned contiguous layout -> gate/up grouped GEMM ->
  fused SiLU-and-mul + quant -> down grouped GEMM -> `post_reorder_deepgemm`.
  - The kernel forbids `-1` rows, so the padded counts are passed as the valid counts and pad
    rows carry their expert index; the gather never reads them. The row count is the
    graph-static bound of the DeepGEMM compact layout, so CUDA graphs work unchanged.
  - The kernel consumes the checkpoint's fp32 block scales, so no UE8M0 requant
    (`is_deepgemm_moe_runner_backend_enabled()` is False for this backend).
- `Fp8MoEMethod`: builds `FlashInferCuteDslFp8MoeQuantInfo` for the backend; rejects
  per-tensor / MXFP8 / FP4-expert / biased layers with a clear error.
- `MoeRunner`: startup guard (SM100/SM103 + FlashInfer with the kernel), registers the fused func.
- `moe_hook`: `quantization in {fp8, None}` and `moe_a2a_backend == none`.

A distinct backend name is used rather than reusing `flashinfer_cutedsl`: that name carries
NVFP4 semantics across the dispatcher (`skip_local_expert_mapping`), DeepEP coercion, LoRA
memory pool and SBO code paths, and its fused func for the standard dispatcher is the NVFP4
kernel. Slotting into the `deep_gemm` runner is not possible either, since DeepGEMM on SM100
requires UE8M0-packed scales that this kernel does not accept.

Performance profile: kernel-level the CuTe DSL GEMM is on par with SGLang's DeepGEMM contiguous
kernel, but the contiguous layout costs a full 128-row tile per active expert and the kernel cannot
skip the slack tiles (`-1` rows unsupported), so decode-dominated e2e latency trails the Triton fused
MoE while prefill/TTFT is substantially faster (see Benchmark). A `-1`-aware or masked variant on the
FlashInfer side would close the decode gap.

Limitations (by kernel contract): SM100/SM103 only; every GEMM dim a multiple of 128 (e.g.
Qwen3-30B-A3B at TP4 shards `768/4=192` and is rejected); standard dispatch only for now
(`deepep` normal could reuse the same contiguous path later).

## Accuracy Tests

- `test/registered/kernel/moe/test_flashinfer_cutedsl_fp8_moe.py` (4-gpu-b200, kernel-unit):
  parity vs the Triton `fused_experts` reference on Qwen3-30B-A3B-FP8 shapes at 7/64/512
  tokens, EP-style local ids with `-1` vs a torch reference, and the 128-alignment rejection.
- `test/registered/unit/layers/moe/test_hpc_ops_runner_guard.py`: startup guard off SM100 and
  fused-func registration.
- FlashInfer's own `tests/gemm/test_groupwise_scaled_gemm_fp8.py -k cute_dsl`: 69 passed on GB200.
- GSM8K few-shot (Qwen/Qwen3-30B-A3B-FP8, TP1, GB200, full 1319 questions, 5-shot, greedy):
  flashinfer_cutedsl_fp8 0.898, triton 0.908, deep_gemm 0.912 (200-question subset: 0.900 vs 0.920 triton).
