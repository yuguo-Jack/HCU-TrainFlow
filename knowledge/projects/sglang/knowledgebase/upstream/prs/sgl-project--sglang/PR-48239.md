# [Perf] eager-runner: size the input registry by the prefill limit

[Upstream PR](https://github.com/sgl-project/sglang/pull/48239) · state: open · merged: False

## Original PR description

## Motivation

The `EagerRunner` builds one fixed-size input registry at startup. Its token-axis slots (`input_ids`, `positions`, `out_cache_loc` int64 and `mrope_positions` 3 x int64: 48 bytes per token) are sized to `max(max_total_num_tokens, chunked_prefill_size)`, the whole KV pool. An eager pass carries one prefill batch, bounded by the chunk / `max_prefill_tokens`, or a decode-shaped batch, so almost all of that memory is never written. The waste scales with the KV pool: a small model on a large GPU has a multi-million-token pool and wastes hundreds of MB of device memory that activations and CUDA graphs could use.

## Modifications

- `model_executor/runner/eager_runner.py`:
  - The registry is sized by the prefill limit: `max(chunked_prefill_size (or the PP dynamic-chunking ceiling), min(max_total_num_tokens, max_prefill_tokens), max_bs * tokens_per_req)`. It is never larger than before.
  - `load_batch` regrows it when a batch is larger (e.g. chunked prefill disabled and a long prompt). The regrown registry is the next power of two, capped at the old pool-based size, and is built outside the process-wide input-buffer pool. The first regrow does not free the startup registry: it stays in that pool, whose slots the CUDA-graph runners share. Each later regrow frees the previous regrown registry.
- `model_executor/cuda_graph_buffer_registry.py`: `build_eager_registry(share_pool=...)` (default `True`, unchanged for every existing caller).
- Test: `test/registered/unit/model_executor/runner/test_eager_runner_input_registry.py` (CPU) covers four cases:
  - a large pool does not size the registry;
  - a small pool keeps the chunk ceiling;
  - a larger batch regrows the registry, and smaller batches reuse it;
  - a regrow is capped at the old size and is not kept in the shared pool.

The values copied into the slots and the kernels are unchanged.

## Accuracy Tests

`Qwen/Qwen2.5-0.5B-Instruct` with `--enable-deterministic-inference`, the same RTX PRO 6000, main vs this PR: greedy outputs of 7 prompts (single, repeated twice, and batched) are **token-identical**, and main is repeat-identical in this config. With prefill forced through the eager runner and the regrow path exercised (`--enable-deterministic-inference --chunked-prefill-size -1 --max-prefill-tokens 4096 --cuda-graph-max-bs-prefill 512`; the server logs `Eager input registry: 14408 tokens > 4096; regrowing to 16384.`), outputs are again token-identical to main.

## Speed Tests and Profiling

Device memory after startup, same GPU (RTX PRO 6000 Blackwell Max-Q, 300 W), `python -m sglang.launch_server --model-path Qwen/Qwen2.5-0.5B-Instruct --enable-deterministic-inference`. The KV pool here is 6,979,341 tokens:

| | main `8d4e1ce4c7` | this PR |
|---|---|---|
| GPU memory used after startup | 87,716 MiB | 87,396 MiB (**−320 MiB**) |
| Free after CUDA-graph capture | 9.42 GB | 9.73 GB |
| KV cache tokens | 6,979,341 | 6,979,341 |

Forced-eager config above (KV pool 7,284,335 tokens), same GPU: 91,024 MiB used on main vs 90,688 MiB with this PR (−336 MiB), and 6.19 vs 6.52 GB free after CUDA-graph capture.

The saving is freed after the KV pool is sized, so it is runtime headroom, not KV capacity, and it scales with the pool size: 48 B x (pool − prefill ceiling). With `nvidia/Qwen3.8-Flash-Next-NVFP4` on the same GPU, the pool is only 140,928 tokens, so the expected saving is 48 B x (140,928 − 16,384) = 6.0 MB, which this free-memory reading does not resolve (11.18 GB on main vs 11.20 GB with this PR after CUDA-graph capture, one run each, measured on an earlier commit of this PR with the same initial sizing; only the regrow path changed since). No saving is claimed for that model, and no speed change is claimed.
