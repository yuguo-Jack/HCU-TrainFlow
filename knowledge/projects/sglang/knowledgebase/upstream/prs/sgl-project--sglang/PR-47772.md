# [Fix] PD: Record decode handoff time for non-streaming metrics

[Upstream PR](https://github.com/sgl-project/sglang/pull/47772) · state: open · merged: False

## Original PR description

## Problem

A PD decode request never stamps `prefill_finished_time`: its prefill runs on another worker. For non-streaming output, `TokenizerManager` consequently records the arrival of the first internally flushed batch as the first-token time. A speculative step can skip the force-stream boundary, leaving the first batch until completion. We observed `first_token_latency == e2e_latency` for all 17 requests in a DeepSeek-V4-Flash/DSpark NPU run.

## Change

Record a decode-local timestamp when the sampled prefill token is committed. Export it in the existing typed timing report and use it for non-streaming first-token accounting. The scheduler-side decode latency supplied to the Rust frontend uses the same timestamp.

The timestamp is written once, survives retraction, and uses the decode worker's clock. It includes the transfer/admission before handoff; it is not the prefill worker's forward-finish time or client receipt time. Keeping it separate leaves prefill phase timing intact. Streaming arrival-based timing, output batching, token generation and metrics-disabled behavior are unchanged. The optional report field is appended so older array payloads retain their default unset value.
