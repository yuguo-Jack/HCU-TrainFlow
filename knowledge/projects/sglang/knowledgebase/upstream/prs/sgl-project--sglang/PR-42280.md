# [Fix] Stop the min-free-slots delay once every waiting request fits

[Upstream PR](https://github.com/sgl-project/sglang/pull/42280) · state: closed · merged: False

## Original PR description

Split from #41994 as requested in review: the `MinFreeSlotsDelayer` part. The other parts are #42279 (batch < 64) and #42281 (DSpark verify width).

## Motivation

`MinFreeSlotsDelayer`, auto-enabled for DSpark, holds fresh prefills until `min(4, max(2, (max_running_requests + 5) // 6))` request slots are free. When fewer requests than that wait and all of them fit, holding them cannot batch anything more. A burst of 256 requests on the High-Throughput cell (256 running requests) settles at 253 running with 3 queued, and those 3 wait for the whole decode of the running batch (75 s maximum TTFT).

## Modifications

`MinFreeSlotsDelayer.should_delay` takes the number of waiting requests and delays only while the free slots are fewer than both the threshold and the waiting requests. With at least `threshold` requests waiting, nothing changes. The new unit case covers 254 running with 2 free: 2 waiting are admitted, 3 still wait. With the old condition, the case's first assertion fails: the 2 waiting requests are delayed.

## Accuracy Tests

The change only moves when waiting requests are admitted. Full GSM8K (1319 questions, natural EOS, concurrency 128) on the High-Throughput cell with two fresh servers per arm, measured in #41994 on main `dcf4e18283`: main 97.04% and 96.82%, #41994 97.19% and 96.97%.

## Speed Tests and Profiling

256 distinct real-text 4K prompts at once, 3072 output tokens, the MI350X cookbook High-Throughput cell (decode graphs up to 256, 256 running) on 4x MI355X (gfx950), TP4/EP4, DeepSeek-V4.1-Flash, a fresh server per arm, radix cache flushed before every burst.

This change alone, on the head of #41308 (`kevin-mii/sglang` `fdf14605e5`, whose `min_free_slots_delayer.py` is identical to main's), ABCCBA against that head:

- output tok/s 7674 -> 8260, +7.68% [+7.08, +8.12]
- TTFT max 74-77 s -> 15.6 s (-79%)
- TTFT median +0.07% [-0.09, +0.34]
- every request runs at once (256 running); without the change the batch never reaches 256

On main as part of #41994, whose PR arm also has the forward-stream scheduling of #42279, ABBA on main `dcf4e18283`: output tok/s 8780 -> 9697 (+10.45% [+9.66, +11.51]), TTFT max 63.7 s -> 14.0 s, TTFT median +0.65% [+0.28, +0.94], TPOT median -1.16% [-1.42, -0.86]. On main `a702970ecb`: +8.58% [+8.17, +9.02] and 75.1 s -> 15.7 s.

Closing. With this change the delay never applies while the outstanding requests fit in `max_running_requests`, which is the closed-loop at-capacity case the delayer batches admissions for, and that case was not measured here; only a one-shot burst was. A bounded wait would remove the burst tail without that trade-off; it can come back as a separate PR with both cases measured.
