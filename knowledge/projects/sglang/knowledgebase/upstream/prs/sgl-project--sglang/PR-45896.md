# [Fix] engram: let the hasher take idle DP-attention batches

[Upstream PR](https://github.com/sgl-project/sglang/pull/45896) · state: closed · merged: True

## Original PR description

## Summary

Under attention DP, a rank with no requests can reach `EngramHasher.forward` with padded rows and an `IDLE` forward mode, and the hasher's mode assert kills that rank's scheduler. This brings Jiajun's fix (`7e74b31b26`, on `jiajun/dsv41-h200-rl`, never merged into `sglang-miles`) onto current `sglang-miles`.

## Problem

- In a decode step under attention DP, `DpPaddingMode.get_dp_padding_mode` (`layers/dp_attention.py`) picks `MAX_LEN` when `sum_len * 2 >= max_len * gather_width`. A rank with no requests is then padded to `max_len` rows but keeps `ForwardMode.IDLE`.
- `EngramHasher.forward` (`layers/engram.py`) handles extend, target-verify and decode, and otherwise asserts: `engram serves extend, target-verify and decode, not 4`.
- Seen on a 24-GPU DeepSeek-V4.1 engine (TP 24, attention DP 24, EP 24) a few minutes into an RL rollout, when one rank was momentarily empty.

## Fix

Every row of an idle batch is padding, so the hasher returns zero hash ids for all `num_tokens` rows and commits no history. The rows still join the DP lookup's gather and reduce-scatter; zero is the padding id the context-parallel path already uses.

`sglang-miles` has since added the extend fast path (`engram_hash_extend_and_commit`) at the same spot; the idle check goes before it.

## Validation

- DeepSeek-V4.1-Flash LoRA RL ran with this commit in the engine and no engram assert: the 4-layer slice on 8×H200 with `--sglang-attn-dp-size 8`, and the full model on 2×8 H200 with a 16-GPU attention-DP engine.
- Not reproduced: no run went without the commit, and none of those runs shows whether an idle `MAX_LEN` batch occurred, so they do not demonstrate the original failure.

Independent confirmation of the exact nonempty-IDLE assertion fixed here, plus a small reproducer that fails before the change and passes afterwards.

We hit this on a DeepSeek-V4.1-Flash PD decode worker with 8 NVIDIA RTX PRO 5000 Blackwell GPUs, TP=8 / attention DP=8 / EP=8, DSpark, DP LM head and overlap enabled. The decode MoE configuration was `moe-a2a-backend=none`, `moe-runner-backend=flashinfer_mxfp4`. CUDA Graph was disabled for both decode and prefill, with `CUDA_LAUNCH_BLOCKING=1`.

After approximately 2h34m of routed serving traffic, DP7 raised:

```text
_forward_decode (dspark_worker_v2.py)
  -> run_idle_participation (dspark_verify.py)
  -> _execute_idle (eager_runner.py)
  -> _forward_layers_hc_pre_from_prev (deepseek_v4.py)
  -> EngramHasher.forward (engram.py)
AssertionError: engram serves extend, target-verify and decode, not 4
```

The subsequent native dumps put the other seven ranks in `ncclAllGather -> dp_gather_replicate` during target verification. The parent then terminated the worker tree.

We backported the nine-line idle guard in this PR. Targeted before/after checks on CPU and CUDA, using the actual hasher implementation, reproduce the original assertion for nonempty IDLE batches of 1, 6, 48 and 192 token rows. With the guard, all return correctly shaped int64 zero hashes, leave request history unchanged, and tolerate consecutive idle calls. Empty batches also pass. CPU comparisons of ordinary decode, target-verify and extend produce identical hashes and history before/after; an unrelated unsupported mode still raises.

The patched eight-rank serving worker has completed warmup and resumed routed traffic. This is initial serving validation, not a completed long-duration stability test. We are not claiming that this establishes the cause of separately observed full-graph replay hangs.

Minimal checkpoint-free regression reproducer (original code raises the assertion; fixed code prints PASS). CPU tensors suffice for the Python branch; use `ENGRAM_REPRO_DEVICE=cuda:0` to check the CUDA output as well:

```python
"""Engram nonempty-IDLE regression: fails before SGLang PR #45896.

Run with a compatible SGLang environment. CPU tensors suffice to reproduce the
Python assertion; set ENGRAM_REPRO_DEVICE=cuda:0 for the same check on GPU.
No model checkpoint or serving process is needed.
"""
import os
from types import SimpleNamespace

import torch

from sglang.srt.layers.engram import EngramHasher
from sglang.srt.model_executor.forward_batch_info import ForwardMode

device = os.environ.get("ENGRAM_REPRO_DEVICE", "cpu")
hasher = EngramHasher.__new__(EngramHasher)
torch.nn.Module.__init__(hasher)
hasher.max_ngram_size = 4
hasher.register_buffer("primes", torch.ones((2, 3, 8), dtype=torch.int64, device=device))
hasher.register_buffer("offsets", torch.zeros((2, 24), dtype=torch.int64, device=device))
hasher.history = torch.arange(9, dtype=torch.int32, device=device).reshape(3, 3)
saved_history = hasher.history.clone()
input_ids = torch.zeros(6, dtype=torch.int64, device=device)
batch = SimpleNamespace(
    forward_mode=ForwardMode.IDLE,
    req_pool_indices=torch.zeros(1, dtype=torch.int64, device=device),
)
hash_ids = hasher(input_ids, batch)
assert hash_ids.shape == (6, 2, 24)
assert hash_ids.dtype == torch.int64 and hash_ids.device == input_ids.device
assert torch.count_nonzero(hash_ids).item() == 0
assert torch.equal(hasher.history, saved_history)
print("PASS: nonempty IDLE rows return zero hashes and preserve request history")
```
