# [Fix][Spec] Release draft embed/lm_head copies before KV pool sizing

[Upstream PR](https://github.com/sgl-project/sglang/pull/43074) · state: open · merged: False

## Original PR description

## Motivation

Fixes  #36452   #42510 

With EAGLE/MTP speculative decoding where the draft is taken from the **same checkpoint** as the target (the standard MTP setup, e.g. `nvidia/Qwen3.8-27B-NVFP4`), the draft worker loads full-precision copies of `embed_tokens` / `lm_head` (~2.4 GiB/rank on this model: the serialized ModelOpt checkpoint keeps the MTP module unquantized, so the draft builds BF16 embeddings and an untied `ParallelLMHead`). These copies are redundant — the draft is supposed to share the target's embed/head — and the sharing code does free them (`init_lm_head()` → `set_embed_and_head()` / `set_lm_head_from_target()`), but only inside `alloc_memory_pool()`, which the scheduler runs **after** the target pool is sized and **after** the draft pool is allocated:

```
init_target_memory_pool()      # target KV pool sized (live free-mem measurement)
draft_worker.alloc_memory_pool()
    -> TpModelWorker.alloc_memory_pool   # draft KV pool allocated  <-- OOM here
    -> init_token_map() / init_lm_head() # redundant copies freed  <-- too late
```

Because `_profile_available_bytes()` sizes the pool from the measured free GPU memory, both pools are sized while ~2.4 GiB/rank of about-to-be-freed weights is still resident: the target pool ends up under-sized and the draft pool allocation hits `torch.OutOfMemoryError` in `_create_buffers_normal` → `torch.zeros(...)` (full traceback in the issue).

## Modifications

Move the share-and-release to the **end of the draft worker constructors**, where it is guaranteed that both models are fully loaded, so the KV pool profiling that follows measures the freed memory:

- `EagleDraftWorker.__init__` (`eagle_worker_v2.py`): call `init_token_map()` + `init_lm_head()` right after the draft `TpModelWorker` is constructed (weights loaded).
- `MultiLayerEagleDraftWorker.__init__` (`multi_layer_eagle_worker_v2.py`): same for `init_lm_head()` — each per-step draft runner holds its own redundant copies.

Safety of the placement:

- The scheduler always loads the target before `maybe_init_draft_worker()`, and overlap-mode deferred weight loading is rejected under speculative decoding (`startup_weight_load.py` raises for draft workers / spec decoding), so by the end of these constructors both models' weights are final.
- `set_embed_and_head()` rebinds the **target's Parameter objects** (not data copies) and repeats a harmless `empty_cache()`, so the original late calls inside `alloc_memory_pool()` are kept unchanged as an idempotent fallback (e.g. for re-allocation paths). Standalone drafts (`init_lm_head` no-op) and non-last PP ranks are unaffected.
- No scheduler changes: the fix is contained in the spec-worker layer.

## Accuracy Tests

`nvidia/Qwen3.8-27B-NVFP4` (`Qwen3_5ForConditionalGeneration`, vocab 248320, untied lm_head, embedded MTP head, ModelOpt mixed quantization), 2x RTX 5090, `--tp 2 --mem-fraction-static 1.0 --kv-cache-dtype fp8_e4m3`, EAGLE with draft path == target path. Identical server command with vs. without the patch:

| metric | without patch | with patch |
| --- | --- | --- |
| free HBM measured at pool sizing | 17.02 GB | **19.39 GB** (+2.37 GB = exactly the freed copies) |
| target KV pool capacity | 1,043,585 tokens | **1,189,837 tokens** (+14%) |
| startup with `--max-total-tokens 1055000` | `torch.OutOfMemoryError` in draft pool `torch.zeros` (pool capped at 1,043,585, 0.89 GB left) | server starts; pool = 1,055,000 tokens; draft pool healthy (2.06 GB left) |

The unpatched failure signature matches the issue report exactly (draft `Load weight end ... mem usage=2.82 GB`, `max_total_tokens ... is larger than the profiled value` warning, OOM in `_create_buffers_normal`).

Model-output correctness:

- greedy (temperature=0) outputs on a config both servers can serve are **byte-identical** to the unpatched server — the rebind only changes *when* sharing happens, not any values
- speculative decoding stays active with unchanged quality and acceptance (accept length 2.6–3.5, accept rate 0.53–0.84 on both servers)
- non-speculative serving on the patched tree starts and generates normally (the changed path is never constructed without speculative decoding)

## Speed Tests and Profiling

N/A — this change only moves a startup-time weight-sharing step earlier; no forward-path code is touched. Inference speed is unchanged (identical accept rates above). Startup benefits: the ~2.4 GiB/rank redundant copies are freed before pool sizing instead of after pool allocation.
