# [Fix] disaggregation: Keep output ids during a PD rebootstrap instead of popping and replaying the last one

[Upstream PR](https://github.com/sgl-project/sglang/pull/47366) · state: closed · merged: True

## Original PR description

A PD decode rebootstrap (a retracted request whose prefix KV the prefill worker recomputes, e.g. DeepSeek-V4 retraction or `pause_generation(mode="retract")`) popped the last output id before the recompute and appended it back at the transfer commit, overriding the token the prefill sampled. While it was popped, `output_ids` was one shorter than what the client had already received, so an output row emitted in that window (overlap scheduling) reported a shrunken `completion_tokens`, and the replayed id and its logprob row were then streamed to the client a second time.

The last output id now stays in `output_ids`:
- The prefill payload sends `origin_input_ids + output_ids[:-1]`, the same tokens as before; the prefill's sampled token is still ignored, so the next token is sampled on the decode side with its grammar, penalties and logprob state.
- `_pre_alloc_fill_len` is one formula, `len(origin_input_ids) + max(len(output_ids) - 1, 0)`, and every decode prealloc length uses it (admission, capacity check, KV preallocation); KV sizes are unchanged.
- At commit, a rebootstrap that already emitted output appends nothing and commits no logprob, sampling mask or reasoning count; one with no output yet takes the normal path as before.
- `pd_rebootstrap_forced_output_id`, both pops and the commit-time override are gone. `pd_rebootstrap_in_progress` and `_rebootstrap_prefill_len` are gone too: the flag only told that helper to use the fill length instead of the prompt length, and the two now agree for every request in the prealloc queue (new requests have no output, rebootstrap requests had the flag set). The only other caller is the capacity check, where an offload-retracted request now sees its fill length (prompt + output - 1) instead of its prompt length; the check's `ceiling_fits` branch already used this length, and the request's KV fit the pool before the retract, so the check gives the same result.

## Verification

- CPU unit tests covering pause/retract, prealloc priority, the transfer commit, the rebootstrap payload, and the mem-cache paths that size rebootstrap requests. A new test checks that the payload length equals the decode-side fill length for 0, 1 and 2 output ids and that `output_ids` is untouched; the commit test checks the emitted ids and their mask rows survive and the prefill's token is dropped.
- GPU coverage runs in CI: `test_disaggregation_dsv4.py`, `test_disaggregation_basic.py`, `test_prefill_complete_allocation.py`, and the PD pause/retract tests.
