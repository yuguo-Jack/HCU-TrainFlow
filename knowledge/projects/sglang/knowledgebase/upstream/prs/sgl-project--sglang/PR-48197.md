## Original PR description

# [Perf] [AMD] kimi-k3: Route radix4 on bf16 with the cached bias, drop the per-call cast

Branch: `kimi_k3_rocm_radix4_avoid_extra_dtype_conversion` (one commit on `main`).

## Motivation

`SGLANG_K3_RADIX4_TOPK=1` (off by default) opts Kimi-K3 on ROCm into the radix4 router. This pull request makes bf16 the routing precision under that flag: radix4 routes on the bf16 router logits against a cached bf16 copy of the correction bias. That removes an elementwise kernel that ran before the router in every MoE layer, casting the `[num_tokens, 896]` logits to fp32, so the radix4 path launches only the router kernel.

Kimi-K3 holds `e_score_correction_bias` in fp32, and `biased_grouped_topk_gpu` currently matches the logits to it before either router runs:

```python
if correction_bias.dtype == torch.float32:
    route_logits = gating_output.to(torch.float32)
    route_bias = correction_bias
```

The radix4 kernel accepts bf16 scores with a bf16 bias and widens both to fp32 in-register, so on its path the cast costs a launch per layer per forward.

## Modifications

`python/sglang/srt/layers/moe/topk.py`:

- `select_experts`: when the bias is fp32, aiter is in use, and `SGLANG_K3_RADIX4_TOPK` is set, it fetches `TopKConfig.correction_bias_for_dtype(router_logits.dtype)` and passes it down as `radix4_bias`. That copy is built once, lazily, and keyed on the bias's `data_ptr` and `_version`, so a weight reload rebuilds it and nothing is cast per call. Only the layer's own bias is cached; a substituted bias (for example a dynamic expert bias) still takes the uncached path.
- `biased_grouped_topk_gpu`: takes the optional `radix4_bias` and hands radix4 the bf16 `gating_output` with that bias. If no cached bias is passed, it casts `correction_bias` to the gating dtype itself. The fp32 matching of logits and bias moves below the radix4 block, so only the aiter fallback runs it.

With `SGLANG_K3_RADIX4_TOPK` unset (the default), routing is bit-for-bit unchanged. Under the flag, radix4 routing is identical to aiter routing on bf16 inputs. Batches past the radix4 limit (1024 tokens) fall back to aiter, which keeps the fp32 bias and fp32 logits, so a token's experts can differ between a batch just under the limit and one just over it.

### Tests

- `test/registered/unit/layers/moe/test_topk_correction_bias_cache.py`: `test_radix4_routes_fp32_bias_in_logits_dtype` replaces `test_fp32_precision_survives_radix4_batch_cutoff`. At 1024 tokens radix4 receives bf16 logits and the cached bf16 bias (the same tensor object, so no per-call copy). At 1025 tokens aiter receives fp32 logits and the fp32 bias.
- `test/registered/kernels/ops/moe/test_moe_route_radix4.py`: `test_select_experts_preserves_offset_fp32_bias` now asserts that, within the radix4 limit, `select_experts` returns the same ids and weights as aiter routing the bf16 bias. The aiter cases still assert that the offset fp32 bias is preserved.

### Relation to #44297

#44297 adds a fused route-and-MXFP4-quant launch inside the same radix4 block, and still feeds it the fp32 `route_logits` / `route_bias`, so the cast also sits in front of the fused kernel. The two changes stack: #44297 removes the quant launch and this PR removes the cast. The fused kernel accepts bf16 scores with a matching bf16 bias. They conflict textually in `topk.py`; whichever lands second should pass `gating_output` and `radix4_bias` to `route_radix4_quant` and compare `staged.shape[0]` against `gating_output.shape[0]`.
