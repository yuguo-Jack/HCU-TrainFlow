# [Perf] [AMD] gemm: Split-K bf16 GEMV for single-row decode on gfx1151

[Upstream PR](https://github.com/sgl-project/sglang/pull/47077) · state: open · merged: False

## Original PR description

## Motivation

On gfx1151 (Strix Halo, RDNA 3.5, 20 CU) a bs=1 decode step is almost entirely single-row GEMV (`x[1,K] @ W[N,K].T`). rocBLAS serves that as a tiled GEMM with a 96-row tile, so the number of CTAs that can be resident is pinned by `N/96`: 32-64 CTAs for the dense projections of a 0.6B-9B model. On 20 compute units that is not enough to cover memory latency, and the measured read bandwidth is 45-93 GB/s, i.e. 20-40% of what the part can reach.

Splitting K gives every k-chunk its own CTA group. At M=1 the fp32 partials are `N * 4 B * split_k`, 0.2-0.4% of the weight bytes, so the extra traffic is negligible next to the 2-4x occupancy gain.

Two kernels: one CTA per (32-wide n-tile, 512-wide k-chunk) accumulating in fp32 and storing partials, then a reduce kernel with a static order that stores bf16. `tl.dot` is deliberately not used — at M=1 it requires 16 rows and spends 15/16 of the loaded weight tile on padding (76 GB/s vs 202 GB/s on `4096x1024`).

## Modifications

| File | Change |
|---|---|
| `python/sglang/kernels/ops/gemm/rdna_small_m_gemv.py` (new) | split-K kernel (`BN=32` / `BK=512` / fp32 partials) + fixed-order reduce + gate (incl. HIP `< 7.3`) + `SGLANG_ROCM_DISABLE_RDNA_SPLITK_GEMV` |
| `python/sglang/srt/layers/quantization/unquant.py` | route `UnquantizedLinearMethod.apply` to the kernel on the eager path (+ module globals injected in `initialize_bf16_gemm_config`) |
| `python/sglang/srt/utils/common.py` | `is_gfx1151_supported()`, alongside the other arch predicates |
| `python/sglang/srt/environ.py` | `SGLANG_ROCM_DISABLE_RDNA_SPLITK_GEMV` kill switch in the ROCm section |
| `python/sglang/kernels/ops/gemm/__init__.py` | `KernelSpec` entry for the new op |
| `test/registered/kernels/ops/gemm/test_rdna_small_m_gemv.py` (new) | gate accept/reject matrix (incl. the HIP bound), numeric parity vs fp32 and rocBLAS, batch invariance; registered on AMD CI |

The gate is `gfx1151` + HIP `< 7.3` + `M==1` + bf16 + contiguous + `n % 32 == 0` + `k % 512 == 0` + `2 <= k/512 <= 64` + `N/32 <= 1024`. Both bounds are measured rather than guessed: a `34816x5120` gate_up (1088 n-tiles) reaches 145.7 GB/s via rocBLAS and only 133.0 GB/s with split-K, so the crossover sits at the n-tile bound, and `split_k` up to 50 was still winning (1.27x on `5120x25600`) when the old cap was 32.

The HIP bound is there because the compared baseline moves with the stack: the constants beat the `F.linear` of ROCm 7.2.x (74-135 GB/s on the gated shapes), while on 7.13 the same call reaches 205-242 GB/s and split-K loses on every gated shape (numbers in the section below). We can only run 7.2.x here, so the wide routing stops at the last generation we measured instead of extrapolating; the bound is a single constant, so it can be raised once a newer stack has its own shape-level numbers, and `SGLANG_ROCM_DISABLE_RDNA_SPLITK_GEMV` still turns the path off outright.

Compiled graphs keep the GEMM: a raw Triton launch cannot be traced, so the branch is skipped under `torch.compiler.is_compiling()`.

## Accuracy Tests

No accuracy eval was run (the target box has no network for GSM8K). The evidence is numeric instead, against an fp32 reference on the 4B/27B decode shapes:

| n x k | split_k | split-K max abs | rocBLAS max abs | bf16 store step |
|---|---|---|---|---|
| 10240x2560 | 5 | 0.03125 | 0.03125 | 0.02098 |
| 18432x2560 | 5 | 0.03037 | 0.03037 | 0.01988 |
| 2560x9216 | 18 | 0.06160 | 0.06160 | 0.03479 |
| 5120x17408 | 34 | 0.06234 | 0.06266 | 0.05103 |

Both paths land on the same one-ulp-of-bf16 bound from the final store, so this is not an accumulation regression. Accumulation is fp32 and the reduction order is static, so the kernel is batch-invariant (covered by `test_batch_invariant`).

One caveat: a greedy 24-token decode is **not** bit-identical to rocBLAS. On the 4B, one of two prompts diverged around token 20 (`...is NOT a characteristic` vs `...is NOT a reason`) — a tie-break flip at ~1 ulp of logits, not a computation error.

## Speed Tests and Profiling

gfx1151, bs=1. Two levels of measurement, because they answer different questions.

**Kernel level** — per-shape cold-weight microbenchmarks (200 MB working set, far beyond the 2 MB L2), sglang's actual fused projection shapes:

| Shape | split_k | rocBLAS GB/s | split-K GB/s | Speedup |
|---|---|---|---|---|
| 0.6B qkv 4096x1024 | 2 | 55.0 | 201.6 | 3.67x |
| 0.6B gate_up 6144x1024 | 2 | 51.6 | 212.7 | 4.12x |
| 0.6B down 1024x3072 | 6 | 92.5 | 195.5 | 2.11x |
| 4B qkv 10240x2560 | 5 | 120.5 | 173.4 | 1.44x |
| 4B o_proj 2560x4096 | 8 | 74.2 | 196.6 | 2.65x |
| 4B down 2560x9216 | 18 | 134.8 | 220.5 | 1.64x |

**End to end, bs=1** — same overlay, only `SGLANG_ROCM_DISABLE_RDNA_SPLITK_GEMV` differs:

| Harness | rocBLAS | split-K | Delta |
|---|---|---|---|
| Original measurement in this PR, Qwen3-0.6B (8 runs, median) | 22.7 ms/token (43.99 tok/s) | 13.7 ms/token (73.03 tok/s) | 1.66x |
| Original measurement in this PR, Qwen3.5-4B (8 runs, median) | 69.2 ms/token (14.44 tok/s) | 51.5 ms/token (19.43 tok/s) | 1.34x |
| `bench_serving`, Qwen3-0.6B, random 1024 in / 256 out, 8 prompts at c=1, Triton attention, decode CUDA graphs on (independent run, thanks @twoask) | 16.99 ms TPOT (58.1 tok/s) | 15.78 ms TPOT (62.4 tok/s) | +7.5% TPOT, +7.4% throughput |

The rows use different harnesses and therefore different baselines — compare within a row, not across. The per-shape table is the harness-independent part, and it is what the gate is tuned against.

For reference, @twoask measured #46327's weight padding in the same serving harness at 16.98 -> 14.66 ms TPOT (+15.9%), so padding and split-K are complementary rather than additive.

Why the kernel is capped on this part (independent sweep by @twoask): on aliased rows (K\*2 a multiple of 2 KiB) split-K bandwidth is about 31 / 62 / 120 GB/s at `BLOCK_K` = 256 / 512 / 1024 regardless of `BLOCK_N` and warps — each CTA reads 32 rows that are 8 KiB apart, which lands on a single channel. Padded rows reach 190-218 GB/s, which is the gap #46327 addresses.

**Where the gain stops: newer ROCm stacks.** Independent runs by @twoask on ROCm 7.13 / torch 2.10.0+rocm7.13 / Triton 3.6, at head `895c4a4950`, in the same 4B `bench_serving` harness as the 0.6B row above:

| Arm | Median TPOT | Output tok/s |
|---|---|---|
| split-K off | 47.67 / 48.07 ms | 20.3 |
| split-K on | 52.38 / 52.50 ms (-9.7%) | 18.6 |
| #46327 padding off | 47.81 / 47.79 ms | 20.3 |
| #46327 padding on | 44.10 / 44.07 ms (+8.4%) | 22.0 |

Their per-shape numbers say why: on that stack `F.linear` already reads the K=2560 rows at 205-232 GB/s while split-K tops out at 195-199 (0.86-0.95x), and the aliased K=4096 rows only tie (0.96x); the 0.6B model still gains because all of its rows are K=1024. The 7.2.x baseline on the same 4B qkv shape is 120.5 GB/s — the 1.44x row in the table above — so the delta is the stack, not the shape. That is what the HIP `< 7.3` gate encodes: the 7.2.x gains are kept, and a 7.13 runner falls back to its faster stock GEMM instead of taking a 9.7% TPOT regression.

## Not covered (please weigh these before merging)

- The gate is exact to `gfx1151` because all constants were measured on the 20-CU part. Wider RDNA parts (gfx1100 etc.) have enough CTAs that the rocBLAS tile already saturates; broadening needs their own measurements.
- TP>1 mostly falls out of the gate: row-parallel K shards stop being multiples of 512 (e.g. 4B down at TP=4 is k=2304). No multi-GPU numbers.
- Qwen3.8-27B was not run end-to-end: its 54 GB of bf16 weights exceed this machine's ~47 GiB GTT limit, so the only 27B evidence is the per-shape microbenchmarks and one numeric-parity row.
- gfx1151 has no CI runner, so the numeric tests run on whatever ROCm device AMD CI has (the kernel is plain Triton, arch-agnostic); the gate tests are arch-pinned and run anywhere.
- Stacks at or above HIP 7.3 are gated off rather than re-tuned: the only end-to-end evidence there is @twoask's (0.6B +7.5%, 4B -9.7%), and the aliased `K=1024` rows that still win would need their own shape-level sweep before a narrower rule is worth adding.
