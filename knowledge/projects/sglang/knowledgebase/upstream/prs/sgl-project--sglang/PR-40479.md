# [Feat] parser: Add checkpoint-driven response-template adapters

[Upstream PR](https://github.com/sgl-project/sglang/pull/40479) · state: closed · merged: True

## Original PR description

Connect checkpoint `response_template` metadata to SGLang reasoning and tool parsing, so new response formats work without adding another parser implementation.

## Context

[Response templates](https://huggingface.co/docs/transformers/main/en/chat_response_parsing) are the output-side counterpart to chat templates. They describe how raw generated text becomes structured reasoning, content, and tool calls. The first two PRs in this stack provide the generic parser and its streaming event contract; this PR connects them to SGLang serving.

## Parser selection

- **Explicit:** `--reasoning-parser response_template` and `--tool-call-parser response_template`.
- **Auto:** with `--chat-template` unset, checkpoint metadata fills only the parser slots that existing chat-template detection left unresolved. Invalid metadata is ignored with a warning.
- **Template precedence:** an explicit `response_template` argument, then checkpoint metadata, then a detector subclass's built-in fallback. Named aliases stay thin subclasses instead of separate implementations.

## Integration flow

1. `ReasoningParser` and `FunctionCallParser` construct response-template detectors through their existing registries.
2. `ResponseTemplateStreamAdapter` feeds generated text into `chat_parsing.ResponseParser` and routes its region events into SGLang reasoning, content, and tool-call results.
3. Chat Completions and Responses keep their normal parser lifecycle and wire-format builders.

## Reasoning and content

- Derive a streaming template where supported fields are optional, allowing reasoning-only, content-only, or mixed output.
- Route `thinking` chunks to reasoning and `content` chunks to assistant content. Ordinary text is preserved when a template has only an explicit thinking field.
- Keep reasoning policy and delimiters configurable on detector subclasses.
- Keep one-shot parsing isolated from streaming state, so both paths can share a detector.

## Tool calls

- Derive a tool-focused template that parses `tool_calls` and passes all other text through unchanged.
- Stream a tool name as soon as its opener determines it, then its arguments when the region closes.
- **Drop policy:** a call is emitted only when it ends with its closer, parses, and names a requested tool. Otherwise it is dropped with a warning. If its name was already streamed, that call stays incomplete, because a streamed name cannot be retracted.
- A call cut off right after its opener is still detected and dropped, instead of returning the raw opener as content.
- Unknown tool names are dropped unless `SGLANG_FORWARD_UNKNOWN_TOOLS` is set, like other SGLang detectors.
- **Incomplete calls:** Responses marks the function-call item `incomplete`. Chat Completions keeps the engine finish reason instead of promoting it to `tool_calls`.
- Support repeated and parallel calls, stable tool indices, calls opened by the prompt prefix, and schema coercion of string arguments.

## Detokenization and prompt

- While a response-template parser is active, requests keep special tokens and their exact spacing.
- The detokenizer keeps a tool-call closer when it is the stop token, so a call that ends at its closer is not mistaken for a cut-off one.
- Parsers receive the rendered assistant prefill, either the exact prompt text or the decoded prompt ids, so they can continue regions opened in the prompt. `ReasoningParser` and `FunctionCallParser` also accept an explicit `prefix`.

## Validation and constraints

`load_response_template` validates the generic grammar. Serving adds a check for what SGLang can safely route:

- Accept `thinking`, `content`, and `tool_calls` fields. The tool detector requires a `tool_calls` field.
- Allow structured parsing and transforms for tool calls, whose values are emitted only after validation.
- Reject structured or transformed semantics for reasoning and content, rather than silently losing streamed data.
- Reuse SGLang's generic JSON-schema constraints for required or named tool choice.
- Reject strict tools and `parallel_tool_calls=False` with automatic tool choice, since the template cannot enforce them during generation.

## Compatibility coverage

The adapter is compared with the registered Gemma 4 reasoning and tool parsers across non-streaming and streaming output, repeated calls, prompt prefills, early tool-name emission, malformed or cut-off output, and arbitrary chunk boundaries. Existing explicit parsers keep precedence during `auto` detection.

Stacked on [Enrich chat_parsing streaming events](https://github.com/sgl-project/sglang/pull/40478).

## JSON-schema output and stream finalization

Required or named tool requests using the generic JSON fallback, and JSON `response_format` requests, can produce bare JSON even when every template field has an explicit opener. The adapter preserves that JSON after the reasoning boundary, or from the start when the grammar backend does not wait for reasoning. Template delimiters inside JSON strings remain data. Structural-tag, regex and EBNF output keeps the existing template parsing.

For JSON output, Chat and Responses trim a retained tool-call closer only when it is the matched stop. Chat's `no_stop_trim` option is honored.

The shared `JsonArrayParser` now flushes buffered calls at stream end. This fixes lost arguments when a complete call arrives in the final chunk. Regression coverage includes native framing, JSON literals, both API paths, multiple buffered calls and repeated finalization.

- JustinTong0323 · comment · 2026-10-21T05:43:55Z · [source](https://github.com/sgl-project/sglang/pull/40479#issuecomment-6309001228)

Findings from exercising this stack against a real checkpoint that ships `response_template` metadata (`google/gemma-4-12B-it`). Four issues, each with a repro. Fixes are ready as 4 commits on top of `2df73a5` at https://github.com/JustinTong0323/sglang/tree/tmp-pr40479-fixes-e2e — they conflict with the latest main-merge only in `serving_responses.py`'s streaming section; happy to rebase onto the new head if you want to take them as-is. File:line refs below are against `2df73a5`.

**1. JSON response-format output is reinterpreted as tool calls (P1)**

`_response_parser_grammar_start` is consumed by the reasoning detector, but automatic tool extraction still builds a native `FunctionCallParser` without that context (`serving_chat.py:3212` + `:1398`, `serving_responses.py:1094` + `:2039`). With `tool_choice="auto"` and `response_format={"type":"json_object"}`, the model output

```
<think>Plan</think>{"example": "<call:get_weather>{}</call>"}
```

yields content `{"example": ""}`, a completed `get_weather({})` call, and `finish_reason=tool_calls` — in both APIs, streaming and non-streaming. This contradicts the PR's guarantee that template delimiters inside JSON strings remain data: ordinary quoted data changes the caller's control flow. The fix needs to carry the response-format-JSON vs required/named-tool-JSON distinction through the whole pipeline and bypass native tool extraction for the former.

**2. Auto-selection accepts an implicit tool field that cannot be constructed (P2)**

`validate_response_template_for_serving()` accepts a template whose `tool_calls` field has no `open`/`open_pattern` (`response_template.py:150`, selection at `template_detection.py:979`). `_tool_extraction_template()` then unconditionally adds a second implicit region `normal`, so `FunctionCallParser` construction raises `ValueError: At most one field may omit 'open'/'open_pattern'` and tool requests 400. Minimal template:

```json
{
  "start_anchor": "<assistant>",
  "fields": {
    "tool_calls": {
      "content": "json",
      "transform": {"type": "function", "function": "{content}"}
    }
  }
}
```

Either support the shape or reject it in serving validation before auto-selection (with a warning, like other unsupported metadata).

**3. One unknown function discards valid sibling calls in a `transform_each` array (P2)**

`_to_tool_call_items()` returns `None` for the entire region when any member is rejected (`response_template.py:526`-`:531`). With only `get_weather` registered:

```
<calls>[{"name":"get_weather","arguments":{"location":"Paris"}},{"name":"unknown","arguments":{}}]</calls>
```

returns zero calls instead of keeping `get_weather({"location":"Paris"})`. The drop policy should apply per call, with indices allocated over accepted calls.

**4. Zero-width EOS closers are always classified as truncation (P2)**

`response_template.py:345`-`:351` treats `event["start"] == len(input_text)` as proof the closer was absent — but that is also where an end-of-input closer like `close_pattern: r"\Z"` legitimately matches, so an accepted template can never complete its calls. Either distinguish matched-close from forced finalization, verify the configured closer at the terminal position, or reject such closers in validation.

**Fixes on the branch above** (one commit per issue):

- (1) grammar context records what the JSON schema is for; both APIs gate tool parsing on it; required/named tool JSON keeps `JsonArrayParser`.
- (2) serving validation now builds exactly the derived templates the detectors instantiate; implicit tool fields are rejected before auto-selection with a warning.
- (3) per-member validation; indices allocated over accepted calls only.
- (4) the adapter checks the configured closer at the terminal position; `\Z` / `$` / satisfied-lookbehind closers complete the call. Related note for #40478's event contract: offsets alone can't distinguish a matched close from forced EOS finalization — an explicit `forced` flag on the close event would let the adapter drop that re-check.

**Verification:** +5 regression tests, each verified red without the fix; focused parser/serving suite 837 passed. Served `google/gemma-4-12B-it` with `--reasoning-parser response_template --tool-call-parser response_template`: full GSM8K (1319, temp 1.0 / top_p 0.95) accuracy 95.9%, 1318/1319 `finish_reason=stop` (the one outlier was a temp-1.0 sampling runaway on gsm8k-93 that does not reproduce on either this adapter or the registered `gemma4` parsers, 0/6 attempts). Tool-call streaming/non-streaming, thinking routing, and the (1) scenario through real request conversion all behave correctly.


- JustinTong0323 · comment · 2026-10-22T11:42:15Z · [source](https://github.com/sgl-project/sglang/pull/40479#issuecomment-6339879453)

Follow-up on the current head `156762435a`: the array-filtering commit introduces a value-corruption bug, fix ready.

**N1 (P2): schema coercion runs before `transform_each`, corrupting argument values**

`156762435a` replaced the extraction transform with `"{content}"` and moved member transformation after `ResponseParser._close_current()`. That ordering exposes raw function-shaped members to `ResponseParser._coerce_tool_calls()`, which casts arguments using the **pre-transform** function's schema; `_transform_members()` then transforms the already-mutated value (`response_template.py:193`-`:194`, `:410`-`:412`). When a transform maps a member to a different call, the first cast is unrecoverable. With `get_forecast.days: integer` and `echo.days: string`, and a template transforming each member into an `echo` call retaining `{function.arguments}`:

```
<calls>[{"function":{"name":"get_forecast","arguments":{"days":"003"}}}]</calls>
```

yields `echo({"days": 3})` at head (non-streaming and streaming, also through the real Chat builders); the parent `fd79edaba3` correctly preserves `echo({"days": "003"})`.

**Fix:** `017ceb66df` on https://github.com/JustinTong0323/sglang/tree/tmp-pr40479-n1-fix (single commit on top of `156762435a`, cherry-picks cleanly). Adapter-only, +6/−4 in `response_template.py`: the extraction template wraps raw members in a `{"members": ...}` envelope the generic coercer won't interpret as calls; `_transform_members()` unwraps and each member is coerced exactly once, after its own transform. `chat_parsing/` untouched; malformed-member filtering and incomplete-name bookkeeping preserved.

**Verification:** new regression test asserts the decoded value *and* its type (`"003"` str) in non-streaming, whole-chunk streaming, and per-character streaming — red at `156762435a`, green with the fix. 3,619 streaming boundary cases (chunk sizes, every two-chunk split, paired reasoning→tool) pass; malformed/unknown members still drop individually with stable indices; focused parser/serving suite 841 passed with an identical environment failure set to the head baseline. B1–B4 re-verified intact at this head.
