## Motivation

A decode node under overlap defers publishing a preallocation's destination ids: it records an event after the allocation and later reads the ids back on a side stream. A unified pool may move pages in between, so earlier PRs of this stack publish inline under unified memory. The inline publish records the receive rows as the peer's at once but sends their ids only a loop later, so a relief that had to move them would wait for a transfer the peer cannot start yet. This PR holds a request's receive rows until the publish records their transfer, restores the deferred publish, and sizes the preallocation by every window's tail.

## Modifications

- Receive holds (`disaggregation/decode.py`, `mem_cache/kv/storage.py::KVStorage.hold_receive_rows`): both publishes hold the request's receive rows (its tokens' rows in the owner and every window, and its state slots) until the publish has recorded the rows' transfer, or the request leaves. A relief keeps held rows in place whenever a layout serves its demand that way, and an opportunistic compaction leaves them; no move of a held row waits for the peer, which has not got their ids. Only when no layout serves the demand around them does a relief move them; each band counts move batches that may have moved a held row and the storage answers `move_epoch()` (always 0 for a static pool). A publish whose epoch changed reads its ids again after the move: the deferred one after the schedule stream, the inline one before it sends.
- Deferred publish restored for unified pools.
- Decode preallocation tails: the tails are computed once per preallocation and used throughout; HiSparse takes its one window's tail, and the failure report lists each window's free and evictable tokens and tail.
- Tests: `test/registered/unit/disaggregation/test_decode_queue_cleanup.py` (deferral holds rows until the publish and ends the hold for a released request; a changed epoch waits for the schedule stream; the inline publish holds its rows until the send and sends the ids a move gave them), `test/registered/unit/mem_cache/test_unified_move_destinations.py` (a relief keeps held rows when a layout allows; a forced move counts and the readback names the rows' new page).

**PD transfer completion at this head (the stack top):** no stream ever waits on a value the host writes. A row a network transfer reads or writes is reused, overwritten or moved only after the host has seen that transfer end (the prefill send's engine finished, or the decode receive succeeded, failed and drained, or timed out), agreed across the attention TP/CP ranks; each send or receive is its own transfer, so a chunked request never waits for its own later chunks. A relief first keeps such rows in place; only when no layout serves the demand around them does it move them, waiting on the host (releasing the GIL) for that transfer. This mechanism lands in #48009; with this PR's receive holds, the inline-publish window that heads #48009–#48025 carry is closed.
