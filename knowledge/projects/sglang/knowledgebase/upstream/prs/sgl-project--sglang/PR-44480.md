## Motivation

Branch update: based on `main` at `67084267289333faf784e895a88cf39d559922bd`, preserving the original fix and author. Head `8851b72606ff11a288d70ba2fcd8ff628f90b753` adds the executable pytest entrypoint required by CI. The original seven-test file passed direct `python file.py -f` execution on Torch CPU; full strict registration collection and configured pre-commit passed. The model and benchmark measurements below describe the original validation and were not rerun for this update. The three dependent PRs extend the per-layer contract separately.

`Fp8MoEMethod.create_moe_runner` runs fp8 experts on triton when `--moe-runner-backend` is `flashinfer_cutlass` or `flashinfer_cutedsl`, since `Fp8MoEMethod` has no path on either. NVFP4 checkpoints pin `flashinfer_cutlass` on sm120, and `nvidia/Qwen3.8-Flash-Next-NVFP4` keeps its MTP experts in FP8 block-scaled form, so the NEXTN draft layer ends up on triton. `StandardDispatcher` only looks at the global backend when it decides whether to translate expert ids. It sees `flashinfer_cutlass`, sets `skip_local_expert_mapping`, and the triton runner gets global ids. With `--ep-size 2` each rank holds 256 of the 512 experts, so on both ranks ids 256 to 511 index past the local weights, and on rank 1 ids 0 to 255 run the wrong experts.

This is the EP2 crash in #44291 (attempts 2 and 3), and it is what the Qwen3.8-Flash-Next cookbook means when it says these experts "fault on the triton fp8 path under EP". `MoeRunner.__init__` already guards the same hazard for `hpc_ops` (it fails at startup when a quant method falls back to another runner); the flashinfer_cutlass fallback has no guard, so it runs and faults.

Reproduced on 2x RTX PRO 6000 Blackwell Server Edition (sm_120, PCIe only, GPU0-GPU1 `SYS`), driver 595.91.07, `lmsysorg/sglang:dev-cu13` at a6a8c5601 (torch 2.14.1+cu130, flashinfer 0.7.1, triton 3.8.0), `nvidia/Qwen3.8-Flash-Next-NVFP4` @ fc694b54, `--tp-size 2 --ep-size 2 --moe-runner-backend flashinfer_cutlass --ple-offload-embedding --disable-custom-all-reduce`, NEXTN 3/1/4:

| Run | Result |
|---|---|
| no speculation, CUDA graphs | serves |
| NEXTN, CUDA graphs | `CUDA error: an illegal memory access` during draft prefill graph capture |
| NEXTN, `--disable-cuda-graph`, `CUDA_LAUNCH_BLOCKING=1` | `Triton Error [CUDA]: an illegal memory access` in `fused_moe_kernel`, called from `Fp8MoEMethod.apply` in `_draft_extend_for_prefill` |
| NEXTN + #40172 | same crash as NEXTN with graphs: #40172 changes the mapping branch, which this layer skips |
| NEXTN + this PR | serves with CUDA graphs, GSM8K 0.975, accept length 2.94 |

## Modifications

- `python/sglang/srt/layers/moe/fused_moe_triton/layer.py`: `create_moe_dispatcher` passes the backend of the runner the quant method built (`quant_method.runner.runner_backend`). The layer calls `create_moe_runner` before it builds the dispatcher, so that runner is already known. Methods with no runner of their own, including wrappers that build one on an inner scheme (compressed-tensors, Quark, AWQ/GPTQ), pass `None` and keep today's behavior.
- `python/sglang/srt/layers/moe/token_dispatcher/standard.py`: `StandardDispatcher` takes an optional `runner_backend`. Every flag still comes from `--moe-runner-backend`. The runner can only turn local-id mapping on: when the global backend keeps global ids (`_keeps_global_expert_ids`, the list that used to be inline) and the layer's runner does not. Under `auto`, AITER, or any layer whose runner keeps global ids, nothing changes. With LoRA and EP on a remapped layer it raises at startup, because the LoRA pool keys experts by the global backend's convention and would read the wrong adapters.
- `test/registered/unit/layers/moe/test_standard_dispatcher_runner_backend.py` (new, CPU): under a `flashinfer_cutlass` pin with EP2, a dispatcher built for a triton runner maps global ids to local ones and turns the other rank's experts into `-1`; `Fp8MoEMethod`'s triton fallback reaches the dispatcher through `create_moe_dispatcher`; a runner never turns mapping off (auto + `flashinfer_trtllm`); the AITER flag still follows the global backend; LoRA + EP on a remapped layer is rejected.
- `test/registered/unit/lora/test_mem_pool_ep_unit.py`: that test execs the dispatcher's `__init__` from source in a hand-built namespace, so it now also loads `_keeps_global_expert_ids` and provides `Optional` and `MoeRunnerBackendLike` for the new signature.

Not changed here: `should_use_flashinfer_cutlass_moe_fp4_allgather()` still reads the global backend (DP-attention fp4 all-gather only). Wrapper methods keep the global layout, so a wrapper whose inner scheme runs triton under a `flashinfer_cutlass` pin (Quark W8A8 FP8 per-tensor, for example) is still affected; I left that out because I could not test it.

## Accuracy Tests

- New test: without this PR `6 failed, 1 passed` (the `Fp8MoEMethod` case fails on `assert not dispatcher.skip_local_expert_mapping`), with it `7 passed`.
- With this PR, the new test, `test_hpc_ops_runner_guard.py`, `test_flashinfer_dispatcher.py`, `test_moe_runner_config_placement.py` and `test_mem_pool_ep_unit.py`: `80 passed`.
- Server, EP2 + NEXTN + CUDA graphs + this PR: `python -m sglang.test.run_eval --eval-name gsm8k --num-examples 200 --max-tokens 16384` scores 0.975, per-request accept length 2.94 (min 2.36, max 3.33).
- That server run used the first revision of this fix, which took every dispatcher flag from the runner. A review pointed out that it would change ROCm AITER BF16 MoE under EP, so I narrowed it to the version here; for this layer the two dispatch identically. The final revision was rechecked on the same pod: boots with graphs, GSM8K 50 scores 0.980, accept length 2.95.
- Without speculation, EP2 already served on main; TP2 + NEXTN with #42566 and both EP2/TP2 with the RadixArk BF16 draft also serve, so the only EP2 + NEXTN blocker on this checkpoint was this dispatcher path.
