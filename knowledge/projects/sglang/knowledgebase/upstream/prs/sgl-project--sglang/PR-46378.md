# [Feat] unified-memory: Fuse sliding-window draft layers on fa3

[Upstream PR](https://github.com/sgl-project/sglang/pull/46378) · state: closed · merged: False

## Original PR description

> **Superseded by #46986; closing.** The window-draft backend list this PR extended (`WINDOW_RAIL_BACKENDS` in `mem_cache/layout/fused_draft.py`) was removed by #46986, which binds fused drafts to routed KV views and no longer checks the attention backend when it places a draft. On unmodified main (`76d5b3ce02`, SM90), MiMo-V2-Flash's NEXTN draft, sliding-window layers included, fuses on fa3 under `--enable-unified-memory`, and GSM8K matches the default pool (all 1314 questions, greedy, paired by question, CUDA graphs on). The FlashAttention tests this PR added to pin that behavior pass on main unchanged.

## Motivation

With `--enable-unified-memory`, a speculative draft fuses its KV into the target's pool pages. A fused draft's sliding-window layers need each draft step to read its own window and write its own slots. The "swa" host kind admitted only Triton, the backend those reads and writes were first built for. So a draft with sliding-window layers (MiMo-V2-Flash's MTP head) on fa3 was declined, and on a hybrid sliding-window target an EAGLE draft that does not fuse is refused at boot: MiMo-V2-Flash with MTP on fa3 could not use the unified pool.

The FlashAttention backend already has what the fused window draft needs. Under the unified pool it reads every window layer through the iteration plan's sliding-window table, refilled from the plan on CUDA graph replay for draft decode and draft extend, and `_get_swa_write_locations` gives each multi-step draft step its own columns of the window's write ids.

## Modifications

- `WINDOW_RAIL_BACKENDS` (`mem_cache/layout/fused_draft.py`) now admits fa3.

Tests (CPU):
- `test/registered/unit/mem_cache/test_fused_draft_placement.py`: the placement case that admits an fa3 window draft fails before this change and passes after; flashinfer stays the refused example.
- `test/registered/unit/layers/attention/test_flashattention_graph_metadata.py` and `test_cuda_graph_window_rail_completeness.py` pin the FA behavior the gate relies on (green before and after): each multi-step draft step's window write ids are its own columns, a multi-layer draft extend writes the whole window, and every FA function that fills the plan's full-attention table also fills the window one.

## Accuracy Tests

SM90, `XiaomiMiMo/MiMo-V2-Flash`, TP 4, `--attention-backend fa3`, `--speculative-algorithm NEXTN --speculative-draft-model-path XiaomiMiMo/MiMo-V2-Flash --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`, radix cache, overlap scheduler. GSM8K (all 1314 test questions, 5-shot, greedy, `python -m sglang.test.run_eval`), paired by question between the pools; median accept length from the scheduler logs. The unified-memory servers ran with `SGLANG_DEBUG_POISON_POOL=1`.

| CUDA graphs | GSM8K, default pool | GSM8K, `--enable-unified-memory` | questions only one pool got right (default / unified), p | accept length (default / unified) |
|---|---|---|---|---|
| off | 0.833 | 0.830 | 93 / 89, p = 0.82 | 2.71 / 2.70 |
| on | 0.823 | 0.816 | 109 / 100, p = 0.58 | 2.69 / 2.71 |

## Speed Tests and Profiling

Same setup, CUDA graphs on, `--enable-unified-memory` against the default pool:

| load | req/s | median TTFT | median ITL |
|---|---|---|---|
| 100 requests of 512 input / 4096 output tokens, concurrency 128 | +74% | -66% | +52% |
| 192 requests sharing a 4096-token prefix + 128 tokens, 2048 output tokens, concurrency 192 | +71% | -64% | +50% |

The gain is capacity: the unified pool lends memory between the full-attention and sliding-window KV, so it kept about 24 requests running on average where the default pool kept about 10. Per-token latency rises with the larger batches; at equal batch size the decode step is within 1% of the default pool's.
