# [Fix] pd: Size decode Mamba spec-state scratch by running batch, not decode extra slots

[Upstream PR](https://github.com/sgl-project/sglang/pull/44015) · state: open · merged: False

## Original PR description

## Motivation

On the PD **decode** side, `HybridMambaDecodeReqToTokenPool` sizes the hybrid
Mamba / linear-attention **speculative** intermediate scratch (`intermediate_ssm`,
`intermediate_conv_window`) by `size + pre_alloc_size`, where
`pre_alloc_size = disaggregation_decode_extra_slots` reserves extra `req_to_token`
slots for in-transfer (being-received-from-prefill) requests.

Those in-transfer slots never need the speculative scratch: it is indexed
**positionally by running-batch slot** (`build_verify_intermediate_state_indices`
is seeded from `req_to_token_pool.size`, which is `size`, not `_alloc_size`), and
in-transfer requests are not in the running batch, so they never enter
`target_verify`. The extra rows are never touched.

They are not budgeted either. By default a decode server runs with the radix cache
disabled, and `_handle_max_mamba_cache` then reserves verify scratch for
`max_running_requests // attn_dp_size + 1` rows, while the pool allocates
`size + pre_alloc_size + 1`. The difference comes out of the memory left for CUDA
graphs and NCCL: in the run below the KV pool is 1,072,640 tokens on main and on
this branch alike, and only the free memory after startup changes.

The scratch is `[num_layers, spec_state_size + 1, draft_tokens, ...]` fp32. With
MTP on GLM-5.3-Flash (34 KDA layers, TP8) the default
`disaggregation_decode_extra_slots` (2x the per-worker running batch for small
batches) roughly triples it: `max_running_requests=64`, per-worker `size=8`,
`extra_slots=16`, so `spec_state_size=24` instead of `8`, and
`intermediate_ssm_state_cache` is **19.9 GB** instead of **7.2 GB** per GPU. On
96 GB H20 the decode server then has 2.9 GB free after weights + KV + mamba state +
decode CUDA graphs, and the PD warmup fails in the LM head's NCCL `all_to_all` with
`NCCL Error 1: unhandled cuda error`. Today the workaround is to lower
`--disaggregation-decode-extra-slots` by hand; 8 only halves the waste.

## Modifications

`python/sglang/srt/disaggregation/decode.py`,
`HybridMambaDecodeReqToTokenPool.__init__`: size the speculative scratch by `size`
instead of `size + pre_alloc_size`, matching the non-PD path
(`mamba_spec_state_size=max_num_reqs`).

```python
mamba_spec_state_size = size
if enable_linear_replayssm_spec or pp_spec_stable_rows_enabled():
    mamba_spec_state_size = size + pre_alloc_size
```

- ReplaySSM-spec keeps the padded size. GDN's spec ring and cursors (sized from `spec_state_size`) are keyed by `req_pool_idx`, which spans `size + pre_alloc_size`, and so is KDA's request ring under host-only Mamba checkpoints (#44718, `_fill_replayssm_ring_indices`). KDA's per-slot ring is indexed by mamba slot, so the padding is only conservative there; #45583 sizes that case by the running batch.
- `SGLANG_ENABLE_PP_SPEC` stable rows also index the verify scratch by `req_pool_idx`, so they keep the padded size too. PD rejects the flag only together with `pp_size > 1`, and `pp_spec_stable_rows_enabled()` reads only the env var, so the pool checks it directly.
- The main (non-spec) Mamba conv/temporal state pool is a separate allocation sized by `effective_mamba_size` and is unchanged, so in-transfer requests keep their state storage.
- The unified-memory decode pool already sizes the scratch this way: its request table covers `size + pre_alloc_size` rows, while its state view gets `spec_state_size=max_num_reqs` (`mem_cache/kv/build.py`).

Adds three CPU cases to
`test/registered/unit/disaggregation/test_decode_req_to_token_pool.py`: `size`
rows by default, and `size + pre_alloc_size` under `enable_linear_replayssm_spec`
and with `SGLANG_ENABLE_PP_SPEC`. The default case fails on main
(`assert 24 == 8`).

## Accuracy Tests

Main `6aca4198` vs this PR on the same base, image
`lmsysorg/sglang:nightly-dev-cu13-20261029-c10e0e17`, prefill and decode on two
8x H20 nodes, mooncake over RoCE. These runs predate the `SGLANG_ENABLE_PP_SPEC`
guard; the flag is unset in all of them, so they exercise the same code.

GLM-5.3-Flash FP8, TP8/EP8, attention DP8, BF16 KV, TileLang DSA, MTP (EAGLE 5/1/6),
`--max-running-requests 64`, `--mem-fraction-static 0.80`, default
`disaggregation_decode_extra_slots` (16 per DP rank):

| | main | this PR |
|---|---|---|
| decode boots | no: `NCCL Error 1: unhandled cuda error` in the LM-head all-to-all during PD warmup | yes |
| `intermediate_ssm_state_cache` per GPU | 19.92 GB | 7.17 GB |
| `intermediate_conv_window_cache` per GPU | 0.70 GB | 0.25 GB |
| KV pool (`max_total_num_tokens`) | 1,072,640 | 1,072,640 |
| `available_gpu_mem` after startup | 2.94 GB | 16.13 GB |
| consistency (4 prompts x 16 copies) | - | PASS |
| GSM8K (20-shot, 500) | - | 0.946 |
| KV transfer errors | - | 0 |

Non-speculative PD (MTP off), same layout: both trees boot with the same memory
(`available_gpu_mem` 15.24 GB, 2,078,464 KV tokens), consistency PASS on both,
GSM8K 0.932 (main) vs 0.926 (this PR), 0 transfer errors. Without speculative
decoding the pool allocates no speculative scratch, so the change does nothing there.

Second backend, GDN (Qwen3.5-9B, linear-attn + 1 MTP layer), PD + MTP (EAGLE 3/1/4),
TP8 on both nodes, `--max-running-requests 32` so `pre_alloc_size=64`
(`spec_state_size` 96 -> 32):

| | main | this PR |
|---|---|---|
| `intermediate_ssm_state_cache` | 2.27 GB | 0.77 GB (97 → 33 rows) |
| `available_gpu_mem` after startup | 5.69 GB | 7.20 GB |
| consistency | PASS | PASS |
| GSM8K (20-shot, 200) | 0.910 | 0.915 |
| accept length (server average) | 3.37 | 3.40 |

With `--disaggregation-decode-extra-slots 0` both trees allocate the same scratch
(0.77 GB) and report the same free memory (7.60 GB), so the change is a no-op when
there are no in-transfer slots.

## Speed Tests and Profiling

No inference-speed impact (allocation sizing only). Qwen3.5-9B c16 (random 2048 in /
512 out): mean TPOT 1.42 ms on both trees; output throughput 8.0k (main) vs 7.6k
tok/s in a 4 s run, where the gap is in TTFT (mean 225 vs 267 ms), not TPOT; c1 991
vs 1040 tok/s. GLM-5.3-Flash PD + MTP on this branch (main does not boot in this
configuration): c1 / c16 / c64 = 118 / 1141 / 3317 tok/s.

## Related work

- #45583 (`[Perf] kda: Size the speculative ReplaySSM ring by running requests`) is the complementary half: on PD decode it sizes the KDA + `--enable-linear-replayssm-spec` case by the running batch, the branch this PR leaves padded. Its review found the same allocation/budget gap for the KDA ring (129 rows allocated vs 65 budgeted with 64 running requests and 64 extra slots). Both PRs edit the same line, so whichever merges second takes the other's branch.
- #44889 (`[Feat] PD: Support KV-only hybrid decode radix cache with MTP and DFlash2`) budgets the verify scratch for running plus in-transfer requests in its KV-only decode radix cache mode, matching today's allocation. With this PR, that term can drop.
- #42790 (`[Feat] mamba: Allow skipping per-draft intermediate SSM state`) is orthogonal: it adds an opt-in flag to skip the `intermediate_ssm` allocation for backends that do their own rollback, which does not apply to KDA/GDN (they read the buffer). It touches the same constructor, and the two merge without conflicts.
- #42649 (merged) fixed the PD **prefill** side of the same accounting: prefill stopped reserving verify scratch it never allocates. This PR is the decode-side counterpart.
- #23643 proposed the same sizing in April and was closed by the stale bot without review. It predates the ReplaySSM-spec rings and shrinks them too, which would now break their `req_pool_idx` indexing.
