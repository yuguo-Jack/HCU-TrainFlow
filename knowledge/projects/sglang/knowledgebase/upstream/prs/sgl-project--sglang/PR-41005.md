## Motivation

The MLU backend needs trusted CI workflows in the community repository before its backend implementation PR can use them. The overall CI design and rollout are tracked in [issue #32300](https://github.com/sgl-project/sglang/issues/32300). This PR adds the workflow bootstrap only; it contains no MLU backend code or credentials.

## Modifications

- Add `.github/workflows/pr-test-mlu.yml`: opt in to MLU tests with `run-ci-mlu`, while also requiring the existing `run-ci` label. PRs without `run-ci-mlu` skip the MLU gate and test jobs. The workflow runs from the trusted base branch and submits one GitHub job per MLU suite.
- Add `.github/workflows/nightly-test-mlu.yml` for the current two-card nightly suite.
- Add `scripts/ci/utils/resolve_mlu_ci_ref.sh` to resolve a manually supplied branch, tag, or commit SHA to an exact commit SHA before submitting the CI task. Both workflows load this helper from the trusted workflow commit rather than the tested ref.
- Add `.github/workflows/mlu-ci-reliability-report.yml` and `scripts/ci/utils/mlu_ci_reliability_report.py` to publish a weekly MLU CI reliability report on [issue #32300](https://github.com/sgl-project/sglang/issues/32300).

The MLU PR workflow uses `pull_request_target`, so its new workflow definition can run for PRs only after this bootstrap is merged into the base branch. The dedicated `mlu-ci` runner group and CI service are provisioned separately.

## Accuracy Tests

No model code or outputs change in this PR. The workflows were validated in the `sglang-mlu/sglang` test repository using the bootstrap commit from this PR:

- [PR Test (MLU)](https://github.com/sglang-mlu/sglang/actions/runs/37783152550): both the one-card and two-card suites passed. Result metadata and Jenkins logs were uploaded successfully.
- [Nightly Test (MLU) with the MLU backend](https://github.com/sglang-mlu/sglang/actions/runs/37784872820): the two-card Qwen3-8B test passed.
- [Nightly Test (MLU) on bootstrap main](https://github.com/sglang-mlu/sglang/actions/runs/37785057151): the external Jenkins pipeline skipped the suite when `python/pyproject_mlu.toml` was absent, without creating an MLU test pod. The workflow completed successfully.

The four unit tests in `scripts/ci/utils/test_mlu_ci_reliability_report.py` passed, covering the reliability report generation logic.

GitHub caps a `created`-filtered run listing at 1000 results. Page 11 comes back empty instead of returning an error, so `paginate` stops and the report goes on without any warning.

`pr-test-mlu.yml` starts a run on every opened/synchronize/reopened/labeled event of every PR to main, so it will create runs at about the rate `pr-test-extra.yml` does (514 runs on 2026-10-10). That's roughly 3500 a week. Because runs come back newest-first, the report would cover only the last ~2 days while still saying it covers 7, with `collection_errors=0`. There's also no upper bound in the query, so runs created after `--end-time` count toward the 1000 too.

`get_workflow_runs` in `scripts/ci/utils/runner_utilization_report.py` already handles this by walking a cursor. Can you reuse it, or do the same walk here? Something like:

```python
runs: list[dict[str, Any]] = []
seen: set[int] = set()
upper = end
while True:
    query_values = {"created": f"{isoformat(start)}..{isoformat(upper)}"}
    if event != "all":
        query_values["event"] = event
    path = f"/repos/{repo}/actions/workflows/{encoded_workflow}/runs?{urllib.parse.urlencode(query_values)}"
    batch = paginate(api, path, "workflow_runs")  # newest first, at most 1000
    fresh = [run for run in batch if int(run["id"]) not in seen]
    seen.update(int(run["id"]) for run in fresh)
    runs.extend(fresh)
    if len(batch) < 1000 or not fresh:
        break
    upper = parse_timestamp(str(batch[-1]["created_at"]))
```

A unit test that returns exactly 1000 runs from the first query would cover this.

- Kangyan-Zhou · comment · 2026-10-12T20:33:12Z · [source](https://github.com/sgl-project/sglang/pull/41005#discussion_r4252086003)

When someone uses "Re-run failed jobs", the jobs that already passed show up again in the new attempt's job list. They get a new job id and `run_attempt=N`, but keep the original `started_at`/`completed_at`/`runner_name`. Run 38275323981 shows this: `check-changes` appears in attempt 2 as job 114946693267 with attempt 1's timestamps.

This loop records each of those jobs once per attempt. Two things go wrong:
- The job is counted twice, which inflates the attempt and runner-assigned counts.
- For the duplicate, `find_artifact` looks for `mlu-ci-result-pr-<run>-<N>-<job>`. That artifact was never uploaded; the real one is from the earlier attempt. So the job is counted as `missing_metadata` and coverage drops.

Could you skip completed jobs already seen in an earlier attempt of the same run? `carried_over_fingerprint` in `scripts/ci/utils/runner_utilization_report.py` uses the same identity:

```python
seen_executions: set[tuple] = set()
for attempt in range(1, latest_attempt + 1):
    ...
    for job in target_jobs:
        if job.get("status") == "completed":
            execution = (job.get("name"), job.get("runner_name"),
                         job.get("started_at"), job.get("completed_at"))
            if execution in seen_executions:
                continue  # carried over from an earlier attempt, not re-run
            seen_executions.add(execution)
        ...
```

Attempts are walked oldest-first, so the record you keep is from the attempt that actually uploaded the artifact. A test case with a carried-over job in attempt 2 would cover this.

- Kangyan-Zhou · comment · 2026-10-12T20:33:13Z · [source](https://github.com/sgl-project/sglang/pull/41005#discussion_r4252086012)

File: `.github/workflows/nightly-test-mlu.yml` · line None

A scheduled run has no `inputs.ref`, so it uses `refs/heads/main`. A manual dispatch on main with `ref` left empty gets the same group. With `cancel-in-progress: true`, dispatching while the nightly is running (it can take up to the 480-minute timeout) cancels the scheduled run, and the other way round.

`pr-test-amd-extra.yml` avoids this by keying scheduled runs on `run_id`:

```yaml
concurrency:
  group: nightly-test-mlu-${{ github.event_name == 'schedule' && github.run_id || inputs.ref || github.ref }}
  cancel-in-progress: true
```

Dispatches on the same ref still replace each other, and the scheduled run is never cancelled by one.
