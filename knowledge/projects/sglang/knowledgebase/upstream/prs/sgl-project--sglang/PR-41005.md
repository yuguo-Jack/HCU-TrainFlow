## Motivation

The MLU backend needs trusted CI workflows in the community repository before its backend implementation PR can use them. The overall CI design and rollout are tracked in [issue #32300](https://github.com/sgl-project/sglang/issues/32300). This PR adds the workflow bootstrap only; it contains no MLU backend code or credentials.

## Modifications

- Add `.github/workflows/pr-test-mlu.yml`: opt in to MLU tests with `run-ci-mlu`, while also requiring the existing `run-ci` label. PRs without `run-ci-mlu` skip the MLU gate and test jobs. The workflow runs from the trusted base branch and submits one GitHub job per MLU suite.
- Add `.github/workflows/nightly-test-mlu.yml` for the current two-card nightly suite.
- Add `scripts/ci/utils/resolve_mlu_ci_ref.sh` to resolve a manually supplied branch, tag, or commit SHA to an exact commit SHA before submitting the CI task. Both workflows load this helper from the trusted workflow commit rather than the tested ref.
- Add `.github/workflows/mlu-ci-reliability-report.yml` and `scripts/ci/utils/mlu_ci_reliability_report.py` to publish a weekly MLU CI reliability report on [issue #32300](https://github.com/sgl-project/sglang/issues/32300).

The MLU PR workflow uses `pull_request_target`, so its new workflow definition can run for PRs only after this bootstrap is merged into the base branch. The dedicated `mlu-ci` runner group and CI service are provisioned separately.

## Accuracy Tests

No model code or outputs change in this PR. The workflows were validated in the `sglang-mlu/sglang` test repository using the bootstrap commit from this PR:

- [PR Test (MLU)](https://github.com/sglang-mlu/sglang/actions/runs/37783152550): both the one-card and two-card suites passed. Result metadata and Jenkins logs were uploaded successfully.
- [Nightly Test (MLU) with the MLU backend](https://github.com/sglang-mlu/sglang/actions/runs/37784872820): the two-card Qwen3-8B test passed.
- [Nightly Test (MLU) on bootstrap main](https://github.com/sglang-mlu/sglang/actions/runs/37785057151): the external Jenkins pipeline skipped the suite when `python/pyproject_mlu.toml` was absent, without creating an MLU test pod. The workflow completed successfully.

The four unit tests in `scripts/ci/utils/test_mlu_ci_reliability_report.py` passed, covering the reliability report generation logic.

[agent] 

The PR description doesn't mention this `push: main` trigger, and no other PR workflow has one (`pr-test.yml` uses `schedule`). As written, every merge to main runs both MLU suites on the shared pool, and because `cancel-in-progress` is true for `refs/heads/main`, back-to-back merges cancel each other. On a busy day almost none of them would finish. The nightly already covers main, so I'd drop this trigger. If you want post-merge coverage, a `schedule` like pr-test's would work instead.
