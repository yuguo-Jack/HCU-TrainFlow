# [Feat] hicache: stripe pages over several local disks and add parallel writes (write_workers)

## Motivation

`fast_file` (#39880) writes to a single storage root (`file_storage_path`, or the shared storage-dir env var). Hosts with several local NVMe drives therefore get one drive's bandwidth and capacity, unless the operator sets up RAID or LVM first. Backups (`batch_set_v1`) are also serial: `read_workers` only parallelises reads and existence checks.

This PR adds two opt-in extras to `fast_file`. When they are unset, behaviour is unchanged.

- `write_workers`: a write thread pool, separate from the read pool.
- `file_storage_path` as a list: one root per disk. Each page file lives on exactly one root. A set `SGLANG_HICACHE_FILE_BACKEND_STORAGE_DIR` still wins and is one path, the same as the `file` backend.

## Modifications

Only `fast_file_store.py`, `lru_file_evictor.py`, two docs paragraphs and one new unit test file change. The controller, the backend factory and `HiCacheFile` are untouched.

### Commit 1: `write_workers` and one task per slice

- `write_workers` (default 1) sizes a `ThreadPoolExecutor` that is **separate from the read pool**. A large background backup should never queue ahead of a latency-sensitive prefetch or its existence checks. Both the direct `readv`/`writev` path and the staged path use it.
- Both pools now submit **one contiguous slice of pages per worker** instead of one task per page. For small pages, handing off each task costs more than the I/O it overlaps (see the benchmark below).
- A batch still **waits for every task to finish before it returns or raises**, even after the first failure. The controller may release or reuse the host pages as soon as `batch_set_v1` / `batch_get_v1` returns, so no worker may still be reading from or writing to them. A test pins this.
- `read_workers` and `write_workers` share one validator that rejects non-integers, booleans and values below 1.
- GIL: `os.readv` / `os.writev` (and open, rename and stat) release the GIL during the system call, but the per-page Python work does not: building iovecs, evictor reserve/commit and the write-lock stripe all hold it. Workers therefore overlap device time, not Python time. The default stays 1 because each extra worker competes for the GIL with the scheduler thread in the same process (see the benchmark below).

### Commit 2: striping over several storage roots

- **Config.** `file_storage_path` accepts a JSON list or a comma-separated string when the storage-dir env var is unset. Every root gets the **same namespace directory**, and the namespace name does not include the root list. Duplicate roots, including a symlink to the same directory, are rejected. Roots that share one filesystem log a warning, since striping them adds no bandwidth. `SGLANG_HICACHE_FILE_BACKEND_STORAGE_DIR` is shared with the `file` backend, so it stays a single path and takes precedence.
- **Routing (`DiskRouter`).** The page file name (blake2b, 64 bit) picks one of 2^14 buckets. At startup, each bucket is assigned once to the root with the highest **rendezvous (HRW) score** for (bucket, root path). A lookup is one hash plus a table index (about 0.5 µs here). The assignment does not depend on the list order, and adding or removing a root only moves that root's share of the buckets.
- **A change in the number of roots is only a miss.** Keys are content hashes, so a page that now routes to another root reads as a miss and is never read wrong. At startup, each root's scan deletes the pages that now route elsewhere. They can never be read again, so this reclaims their space and stops them leaking when eviction is off. The scan runs even when eviction is off.
- **One evictor per root (`StripedEvictor`).** Each root is its own filesystem, so each root gets its own `LRUFileEvictor` with an independent LRU order, cap and background drain. `StripedEvictor` wraps them behind the single-root interface. `max_size` is split across roots by their bucket share. `min_free_space` applies to **each root's filesystem**, so a full disk does not stop writes to a healthy one; a test covers this. The per-root startup scans run in parallel.
- **No path bypasses the router.** On current `main`, `HiCacheFile` no longer has `_get_component_path`. The helpers that still join `self.file_path` are `_get_file`, `_set_file`, `_file_exists`, the metadata-cache seed scan, `_collect_existing_component_keys` and `clear`. `fast_file` overrides them. A guard test lists every `HiCacheFile` method whose source mentions `self.file_path` and fails if `HiCacheFastFile` does not override it with a version that avoids `self.file_path`. That catches a future inherited method that would silently use only the first root.
- **A single root keeps the existing layout, namespace name and a plain `LRUFileEvictor`.** All 52 existing `fast_file` unit tests on current `main` pass unchanged. The pre-merge file had 53; the merged #39880 dropped `TestBatchExistsV2`.

## Speed Tests and Profiling

**Environment:** Intel Core i9-12900 (24 threads), 20 GB RAM, WSL2 (Linux 6.18), ext4 on a virtual disk, and tmpfs. Python 3.12.3, torch 2.14.0+cpu. No GPU.

**Workload:** a synthetic page-first host pool of 1024 pages × 160 KiB (64 tokens × 1280 B, K and V). It is written with `batch_set_v1` and then read with `batch_get_v1`, in batches of 128. `read_workers = write_workers = w`. "per-page" re-creates the one-task-per-page submission for comparison; "per-slice" is this PR. All roots are directories on **one** filesystem, and the page cache is hot. This measures the per-page software path (system calls, GIL, task handoff), **not disk bandwidth**, and it says nothing about a multi-disk speedup. These numbers were measured before the rebase, when the extra-config key was `storage_dir`. They were not re-measured. The key is now `file_storage_path` (the script below uses that name).

GB/s write / read, best of 3, tmpfs:

| | w=1 | w=2 | w=4 | w=8 |
|---|---|---|---|---|
| roots=1, per-page | 3.35 / 4.97 | 1.59 / 2.48 | 1.17 / 1.68 | 1.21 / 1.73 |
| roots=1, per-slice | 3.27 / 4.93 | **4.29 / 7.22** | 1.55 / 2.65 | 1.37 / 1.95 |
| roots=4, per-page | 3.10 / 4.61 | 1.54 / 2.31 | 1.19 / 1.67 | 1.21 / 1.70 |
| roots=4, per-slice | 2.93 / 4.85 | **4.06 / 6.57** | 1.48 / 2.18 | 1.33 / 1.93 |

On ext4 (virtual disk, hot page cache) the pattern is the same. With one root and per-slice submission: w1 2.95 / 6.78, w2 3.34 / 8.28, w8 1.27 / 1.96.

What I read from this:

- One task per slice was never slower than one task per page, beyond run-to-run noise. At w=2 it is 2.3 to 3.5 times faster, because per-page handoff dominates when the "device" runs at memory speed. The per-page rows also show that the existing per-page `read_workers` pool from #39880 regresses on this setup.
- **More than 2 workers regress on memory-speed storage.** Each page still needs Python work under the GIL, so extra threads mostly add contention. This is why both defaults stay 1, and I do not claim a write speedup from this data. The pool is meant for the case where the device is the bottleneck: cold reads, writes throttled by dirty-page writeback, or several physical disks. I have not measured that case (see below).
- Striping adds no measurable cost on the hot path: roots=4 is within noise of roots=1, and one `route()` call costs about 0.5 µs.
- Routing, from 200k random keys over 4 roots: key shares were 24.8 % / 25.0 % / 25.7 % / 24.5 %. After removing one root, 0 of the keys on the other roots moved. Reversing the root order changed no assignment. Building the table takes about 21 ms at startup.
- A GIL probe confirms that a thread blocked inside `os.readv` / `os.writev` does not stop the main thread from making progress: about 4M loop iterations in 0.2 s.

<details><summary>Benchmark script (run with this branch installed)</summary>

```python
"""fast_file batch_set_v1 / batch_get_v1 throughput vs. worker count and roots.

CPU only, no GPU or model: a synthetic page-first host pool of 1024 pages x
160 KiB (64 tokens x 1280 B, K and V), written and read in batches of 128.
All roots are directories on the same filesystem, so this measures the
per-page software path (syscalls, GIL, task handoff), not disk bandwidth.
"per-page" re-creates the one-task-per-page submission for comparison.
Set BENCH_DIR to choose the filesystem (e.g. /dev/shm).
"""

import os
import shutil
import tempfile
import time

import torch

from sglang.srt.mem_cache.hicache_storage import HiCacheStorageConfig
from sglang.srt.mem_cache.storage.fast_file import fast_file_store as ffs

PAGES, PAGE_TOKENS, TOKEN_BYTES, BATCH = 1024, 64, 1280, 128


class Pool:
    layout = "page_first"
    page_size = PAGE_TOKENS
    dtype = torch.uint8
    size_per_token = TOKEN_BYTES

    def __init__(self):
        self.size = PAGES * PAGE_TOKENS
        self.kv_buffer = torch.randint(0, 255, (2, self.size, TOKEN_BYTES), dtype=torch.uint8)

    def get_page_buffer_meta(self, indices):
        base = self.kv_buffer.data_ptr()
        value_offset = self.size * TOKEN_BYTES
        page_bytes = PAGE_TOKENS * TOKEN_BYTES
        ptrs, sizes = [], []
        for index in indices[::PAGE_TOKENS].tolist():
            ptrs += [base + index * TOKEN_BYTES, base + index * TOKEN_BYTES + value_offset]
            sizes += [page_bytes, page_bytes]
        return ptrs, sizes


def per_page_map_on(executor, workers, fn, *iterables):
    calls = list(zip(*iterables))
    if executor is None:
        return [fn(*args) for args in calls]
    return [f.result() for f in [executor.submit(fn, *args) for args in calls]]


def run(base, pool, roots, workers):
    dirs = [os.path.join(base, f"root{i}") for i in range(roots)]
    config = HiCacheStorageConfig(
        tp_rank=0, tp_size=1, pp_rank=0, pp_size=1, attn_cp_rank=0, attn_cp_size=1,
        is_mla_model=False, enable_storage_metrics=False, is_page_first_layout=True,
        model_name="bench",
        extra_config={"file_storage_path": dirs, "write_workers": workers, "read_workers": workers},
    )
    backend = ffs.HiCacheFastFile(config)
    backend.register_mem_pool_host(pool)
    keys = [f"k{i}" for i in range(PAGES)]
    batches = [
        (keys[s : s + BATCH], torch.arange(s * PAGE_TOKENS, (s + BATCH) * PAGE_TOKENS))
        for s in range(0, PAGES, BATCH)
    ]
    t0 = time.perf_counter()
    for batch_keys, indices in batches:
        assert all(backend.batch_set_v1(batch_keys, indices))
    write_s = time.perf_counter() - t0
    t0 = time.perf_counter()
    for batch_keys, indices in batches:
        assert all(backend.batch_get_v1(batch_keys, indices))
    read_s = time.perf_counter() - t0
    backend.clear()
    backend.close()
    gb = PAGES * 2 * PAGE_TOKENS * TOKEN_BYTES / 1e9
    return gb / write_s, gb / read_s


def main():
    base = tempfile.mkdtemp(dir=os.environ.get("BENCH_DIR"))
    pool = Pool()
    sliced = ffs.HiCacheFastFile._map_on
    print("GB/s write / read, best of 3")
    try:
        for roots in (1, 4):
            for label, map_on in (("per-page", per_page_map_on), ("per-slice", sliced)):
                ffs.HiCacheFastFile._map_on = staticmethod(map_on)
                row = []
                for workers in (1, 2, 4, 8):
                    w, r = max((run(base, pool, roots, workers) for _ in range(3)), key=sum)
                    row.append(f"w{workers} {w:5.2f} / {r:5.2f}")
                print(f"roots={roots} {label:9s} " + "   ".join(row))
    finally:
        ffs.HiCacheFastFile._map_on = sliced
        shutil.rmtree(base, ignore_errors=True)


if __name__ == "__main__":
    main()
```
