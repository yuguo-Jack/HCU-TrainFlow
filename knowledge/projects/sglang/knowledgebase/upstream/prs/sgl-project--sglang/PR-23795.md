# :sparkles: [llm][npu][quant] Add W4A4 MXFP4 quantization support for Qwen3 Dense on Ascend NPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/23795) · state: closed · merged: True

## Original PR description

# Summary

Adds **MXFP4 W4A4** quantization (4-bit weights + 4-bit activations) for Qwen3 / Qwen3.5 **dense** LLM models on Ascend NPU, continuing the NPU quantization work tracked in #21584. The **online** path uses **dual-level** MXFP4; the **offline** msmodelslim path is single-level.

> **Rebased onto latest `main`.** The two prerequisite PRs this built on — #22352 (W8A8 MXFP8) and #23650 (W4A8 MXFP4) — are now **merged**, so this PR contains only the W4A4 delta and reuses their merged infrastructure (`_NPULinearMethodBase`, the lazy `_get_float4_e2m1fn_x2_dtype()` helper, `npu_format_cast`, `ModelSlimLinearScheme`, `ModelSlimConfig.get_linear_scheme`).

Two modes are supported:

**Online quantization (`--quantization mxfp4`)**

- On the **Ascend NPU** backend, `mxfp4` dispatches to the new `Mxfp4W4A4Config` → `NPUDualLevelMXFP4LinearMethod`. On GPU/CPU the same flag still resolves to the upstream OCP `Mxfp4Config` (MoE) — the split is done purely at registration time (the NPU config is registered only inside the `is_npu()` block of `layers/quantization/__init__.py`, mirroring `GPTQAscendConfig`), so there is no collision and the upstream config is untouched.
- The online path uses **dual-level** MXFP4: at load, BF16/FP16 weights are quantised via `npu_dynamic_dual_level_mx_quant` to packed FP4 plus a fine FP8 (E4M3) **L0** block scale and a coarser **L1** scale, and the weight is cast to `FRACTAL_NZ`. At inference, activations are dynamically quantised the same way and the matmul runs via `npu_dual_level_quant_matmul`.
- **Why dual-level:** an earlier single-level online path (RTN with UE8M0 power-of-2 block scales) lost enough precision that greedy long-form decoding could degenerate into loops that never emit EOS. The dual-level FP8 L0 scale captures per-block dynamic range far more accurately, which removes that failure and lands online accuracy on par with (slightly ahead of) the calibrated offline checkpoint. Requires Ascend 950 (A5) — the `DualLevelQuantBatchMatmul` op is unavailable on A2/A3.

**Offline quantization (msmodelslim pre-quantized weights, `--quantization modelslim`)**

- `W4A4_MXFP4` checkpoints are auto-detected (via `quant_model_description.json`) and handled by `ModelSlimMXFP4Scheme`, which delegates weight post-processing + matmul to `NPUSingleLevelMXFP4OfflineLinearMethod` (`self.kernel`).
- The checkpoint stores weights as `float8_e4m3fn [out, in]` (one FP4 value per byte, fp8 as container) + `uint8` E8M0 scales `[out, in/32]`. At load they are re-packed to `float4_e2m1fn_x2` (2 FP4/byte, `[out, in//2]`) and transposed; the single-level scale is reshaped to 3D and the matmul runs via `npu_quant_matmul(x1_dtype = x2_dtype = float4_e2m1fn_x2, group_sizes=[1, 1, 32])`. Because the checkpoint ships single-level UE8M0 scales, the offline path is single-level and uses a **different matmul kernel** from the dual-level online path.

# Benchmark Results

Validated end-to-end on Ascend A5 hardware. Both W4A4 modes (online dual-level and offline msmodelslim single-level) are compared against the BF16 baseline.

# Style / consistency with #23650

This PR follows the same refactored conventions as the merged W4A8 PR:

- All NPU ops go through `torch.ops.npu.*`; **no top-level `import torch_npu`**, no `current_platform` guards (module stays importable on CUDA/CPU/AMD/XPU CI).
- The packed-FP4 dtype is resolved from the shared lazy `_get_float4_e2m1fn_x2_dtype()` helper — the `torch_npu.float4_e2m1fn_x2` int enum, **not** the `torch.float4_e2m1fn_x2` dtype object, which recent op-plugin builds reject.
- Device-agnostic config with per-device dispatch (`is_npu()` branch + `NotImplementedError` elsewhere); the offline scheme subclasses `ModelSlimLinearScheme` and delegates to a `self.kernel` kernel, registered in `get_linear_scheme`'s `linear_quant_schemes` list.

File: `python/sglang/srt/layers/quantization/modelslim/schemes/__init__.py` · line 24

I'd lean toward keeping `ModelSlimMXFP4Scheme` as is — the convention here is that `MXFP<n>` defaults to the symmetric case where weights and activations are at the same level (e.g. `ModelSlimMXFP8Scheme` is W8A8, not `MXFP8W8A8Scheme`). Only `W4A8`, where weight and activation precisions differ, carries the explicit suffix. So `MXFP4` already implies W4A4, and renaming to `MXFP4W4A4Scheme` would break symmetry with the existing `MXFP8Scheme`.
