# [Fix] modelopt: Keep NVFP4 MoE experts intact across partial weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/48299) · state: open · merged: False

## Original PR description


## Motivation

`ModelOptNvFp4FusedMoEMethod.process_weights_after_loading` rewrites the FP4 expert tensors in place for the selected backend:

- `flashinfer_trtllm` (SM100): each expert's `w13_weight` / `w2_weight` rows are shuffled, and the block scales are row-shuffled and then interleaved with `nvfp4_block_scale_interleave`;
- `flashinfer_cutlass` (SM120): the block scales are swizzled into `w13_weight_scale` / `w2_weight_scale` themselves (`alias_or_bind_derived_param`).

A weight-update session (`begin_weight_update` -> `update_weights_from_tensor` / `update_weights_from_distributed` -> `end_weight_update`) post-processes **every** MoE layer at the end, but `ModelOptNvFp4FusedMoEMethod` has no `restore_weights_before_loading`. Any update that does not rewrite every expert tensor of every MoE layer therefore permutes the untouched experts a second time. The engine keeps serving with corrupted MoE weights and reports success. Full reloads from disk are unaffected, because they rewrite everything before post-processing.

## Modifications

- `ModelOptNvFp4FusedMoEMethod.restore_weights_before_loading` undoes the repack in place (same storage, so captured CUDA graphs stay valid). Restore followed by post-processing is the identity on experts the update does not rewrite, so any subset of tensors or experts can be updated.
  - TRT-LLM: `restore_fp4_moe_weights_from_flashinfer_trtllm` inverts the row permutations (from FlashInfer's cached permute indices, checked to be bijections) and the scale interleave. FlashInfer has no inverse for `nvfp4_block_scale_interleave`; the kernel only moves bytes, so the inverse is recovered by running it on the bytes of each element's flat index (one call per byte plane, cached per shape).
  - CUTLASS: `unswizzle_blockscale` (the inverse of `swizzle_blockscale`) when the swizzled scale is aliased onto the checkpoint scale.
  - The restore is all-or-nothing: every permutation for w13 and w2 is built and checked before any byte moves, and the layer is marked restored only after the copies. A failed check raises and leaves the layer unchanged. The copies run one expert at a time, so the temporaries stay at one expert's size while the KV cache is resident.
- `process_weights_after_loading` tags a layer as restorable only when the repack is an exact byte permutation. Restore stays a no-op, which is the current behaviour, for padded TRT-LLM layouts (padded weights, or block scales whose rows are not a multiple of 128 or whose columns are not a multiple of 4, which the scale interleave pads), clamped-SwiGLU checkpoints whose w13 E4M3 scales get rescaled, interleaved-w13 checkpoints, and the CuteDSL, Marlin and MegaMoE paths; a weight update that meets such a layer logs a one-time warning.
- Tests:
  - `test/registered/unit/layers/quantization/test_modelopt_nvfp4_moe_restore.py` runs the real post-processing for both backends and checks that restore returns the checkpoint bytes in the same storage, that a partial update leaves the other experts bit-identical and equal to a fresh load, and that restore is a no-op before post-processing and when repeated. It also checks that a restore whose permutation check fails leaves the layer unchanged, and that block scales the interleave or swizzle pads (hidden size 192) are not marked restorable on TRT-LLM and keep their checkpoint copy on CUTLASS.
  - `test/registered/rl/test_update_weights_from_tensor_nvfp4_moe.py` serves `nvidia/Qwen3-30B-A3B-NVFP4` and checks with `/weights_checker` `raw_checksum` that same-bytes updates of a dense tensor, and of one expert of one layer, leave every expert parameter bit-identical.

## Accuracy Tests

Bitwise check, `nvidia/Qwen3-30B-A3B-NVFP4` on 1x GB200 (`flashinfer_trtllm`, auto), main = `8d4e1ce4c7`. `/weights_checker` `raw_checksum` (sha256 of each parameter's raw bytes) over the expert parameters before and after `begin_weight_update` -> `update_weights_from_tensor` with the checkpoint's own bytes -> `end_weight_update` (the new e2e test):

| Update | main | this PR |
|---|---|---|
| `model.norm.weight` only | 192 expert params changed | 0 changed |
| expert 0 of layer 0 (12 tensors) | 192 expert params changed | 0 changed |

192 = 48 MoE layers x {`w13_weight`, `w13_weight_scale`, `w2_weight`, `w2_weight_scale`}: on main, a weight update that does not touch any expert still corrupts every MoE layer.

The same check on 1x RTX PRO 6000 (SM120, `--moe-runner-backend flashinfer_cutlass`), where only the block scales are repacked: main 96 expert params changed (48 MoE layers x {`w13_weight_scale`, `w2_weight_scale`}) for each update, this PR 0. On 1x GB300 (`flashinfer_trtllm`) the result matches GB200: main 192 changed, this PR 0.

The new unit test fails on main (6 of 6 backend subtests) and passes on GB200, GB300 and RTX PRO 6000. Serving outputs are unchanged by construction: the hook only runs inside a weight-update session.

No runtime change: restore runs only inside a weight-update session, and serving kernels and layouts are unchanged.
