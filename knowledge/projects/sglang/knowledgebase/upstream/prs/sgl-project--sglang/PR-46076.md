# [Fix] gateway: Disable Nagle on accepted client connections

[Upstream PR](https://github.com/sgl-project/sglang/pull/46076) · state: open · merged: False

## Original PR description

## Motivation

Fixes #46067. The model gateway enables `TCP_NODELAY` on worker connections, but accepted client sockets still use the default acceptor. Small streaming responses can therefore incur Nagle/delayed-ACK stalls, including a roughly 40 ms delay observed locally over HTTPS.

## Modifications

- Use axum-server's existing `NoDelayAcceptor` for accepted HTTP connections.
- Compose `NoDelayAcceptor` inside `RustlsAcceptor` for HTTPS, setting the socket option before the TLS handshake.
- Document the behavior in the gateway README.

This keeps the existing bind, shutdown, and TLS configuration paths and adds no dependency or configuration option. #33269 addressed the separate `rust/sglang-server` implementation; it did not change this gateway. I checked open PRs referencing #46067 and `TCP_NODELAY` and found no overlapping gateway fix.

## Accuracy Tests

No model or sampling code changes. A local mock worker streamed two content chunks (`Hello`, ` world`) followed by `[DONE]` through the real compiled gateway. Both versions passed HTTP status and complete SSE-content checks for all 24 requests: 4 connections per protocol, 3 requests per connection, over HTTP and self-signed HTTPS.

## Speed Tests and Profiling

Ubuntu 24.04 under WSL2; debug gateway builds; loopback mock worker; 5 ms simulated token intervals. The client disabled `TCP_QUICKACK` to expose delayed ACKs. `strace -f -yy -e trace=accept4,setsockopt` associated each accepted client socket with its `TCP_NODELAY` call.

| Check | Main (`02b983603d34`) | This change |
| --- | --- | --- |
| HTTP client connections with `TCP_NODELAY=1` | 0 / 4 | 4 / 4 |
| HTTPS client connections with `TCP_NODELAY=1` | 0 / 4 | 4 / 4 |
| SSE responses passing content checks | 24 / 24 | 24 / 24 |
| HTTPS first-event latency on fresh connections (4 samples, range) | 41.69–45.36 ms | 1.92–2.95 ms |

These timings are a transport smoke test under tracing, not a model-inference benchmark or throughput claim. HTTP did not reproduce a 40 ms stall in this run; its socket-option check still failed before the change and passed afterward.
