# [Perf] distributed: Skip the DLPack re-wrap of custom all-reduce results

[Upstream PR](https://github.com/sgl-project/sglang/pull/44251) · state: closed · merged: True

## Original PR description

## Motivation

`custom_all_reduce` in `sglang/kernels/ops/communication/all_reduce.py` ends with `torch.from_dlpack(result)`. With apache-tvm-ffi 0.1.11 and torch's DLPack exchange API loaded (`torch_c_dlpack_ext`, present in the `lmsysorg/sglang` image), the tvm-ffi call already returns a `torch.Tensor`. So `torch.from_dlpack` does a pure torch → DLPack → torch round trip. Along the way it also builds a current-stream object from a device string and makes a `__dlpack__` call that may be retried.

On a Grace host (GB300) this round trip costs about 20 µs per call. That is about half of the ~42 µs host time of an eager TP all-reduce, and twice the cost of the tvm-ffi call itself. Diffusion DiTs run several all-reduces per block in eager mode, so on GB300 with TP the step is host-bound and this cost shows up directly in end-to-end latency.

## Modifications

Return `result` as is when it is already a `torch.Tensor`. Otherwise, e.g. with `TVM_FFI_DISABLE_TORCH_C_DLPACK=1`, keep `torch.from_dlpack`.

The returned tensor aliases the same memory as before. `torch.from_dlpack` passed the current stream, so the round trip never added a cross-stream wait, and dropping it changes no ordering. No memory is involved, and CUDA-graph capture and the compiled path (`diffusion_all_reduce`) are unchanged.

## Accuracy Tests

## Speed Tests and Profiling

Base `c54ba66cd4`, torch 2.13, apache-tvm-ffi 0.1.11, GB300 ×2 (Grace host). Processes were pinned to the GPUs' NUMA node.
