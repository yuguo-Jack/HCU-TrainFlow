# [Fix] openai: Refuse tools + output constraint consistently instead of silently dropping the tool-call grammar

[Upstream PR](https://github.com/sgl-project/sglang/pull/47191) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #47167.

OpenAI semantics keep tools callable under `tool_choice: "auto"` and constrain only the final assistant message. SGLang cannot express that combination yet: an explicit output constraint covers the whole answer, so the model can never emit a tool call and silently answers in the requested shape instead. The issue demonstrates the fallout across three models (all with `tool_choice: "auto"` + a JSON schema):

| Model / parser | `/v1/responses` (before) | `/v1/chat/completions` (before) |
|---|---|---|
| Kimi-K3 (`kimi_k3`, structural_tag) | 400 `Cannot combine tool calls...` | **no warning, fabricated schema-shaped answer, no tool call** |
| GLM-5.3 (`glm47`, full_assistant_ebnf) | **warns, drops tool grammar, fabricated answer** | same |
| DeepSeek-V4.1-Flash (`auto`, no parser grammar) | **no warning at all, fabricated answer** | same |

In every case the model invented "results" for work it never did — e.g. made-up `/tmp` file listings when driven by Codex `--output-schema`. The issue author asks to either compose the tool-call grammar with the format (the #42269 roadmap) or "at least refuse the request consistently instead of silently dropping the tools". This PR does the latter, extending the same refusal #34881 introduced for `tool_choice: "required"`.

## Modifications

`python/sglang/srt/entrypoints/openai/protocol.py`, in both `ChatCompletionRequest.to_sampling_params` and `ResponsesRequest.to_sampling_params`:

- When an explicit output constraint (`response_format` / `text.format` / regex / ebnf / structural_tag / json_schema) is present **and** `tool_choice` allows calling a tool **and** function tools are present (or the parser installed a tool-call constraint), raise a `ValueError` that maps to a 400 — regardless of whether the tool-call parser installs its own grammar.
- Removed the two warn-and-drop paths: the `full_assistant_ebnf` branch on both paths (this is the glm47 fabrication route) and the chat path's `logger.warning("Constrained decoding is not compatible with tool calls.")` fallback for `auto`.
- Deliberate non-goals, all kept working:
  - `tool_choice: "none"` + tools + format stays satisfiable: tools are not callable, so the constraint may apply to the whole answer.
  - Hosted tools (`web_search`, `code_interpreter`, ...) on `/v1/responses` are unaffected — they bypass the tool-call parser, so only `function`/`custom` tools trigger the refusal.
  - Requests where the chat-template renderer handles `response_format` natively are unaffected (no constraint is installed, so nothing conflicts).
  - gpt-oss (harmony) already rejects `text.format` earlier with a dedicated message; that path is untouched.
- Grammar composition (tools callable **and** schema-constrained final message) remains the #42269 feature; once it lands, this refusal can be relaxed for parsers that can compose.

## Regression Tests

- `test_serving_chat.py`: the locked-in "auto keeps response_format without raising" test is flipped to assert the refusal (its old premise — "dropping the tool-call constraint still leaves a satisfiable request" — is exactly what #47167 disproves: satisfiable to the grammar, but the model can never call the tool); added cases for the parser-grammars-less (DeepSeek-style) request, for `tool_choice: "none"` staying allowed with and without a tool-call constraint, and for tools without an output constraint still installing the tool-call grammar.
- `test_serving_responses.py`: new `ResponsesToolConstraintConflictTest` covering structural_tag / full_assistant_ebnf / no-grammar refusals, `required`, the `tool_choice: "none"` escape hatch, hosted-tool non-interference, and the no-format happy path.
- `test_protocol.py`: the full_assistant_ebnf warn-and-drop test is flipped to assert the conflict is refused; the no-explicit-constraint case still installs the EBNF.

## Test Results

- `test_serving_chat.py` + `test_serving_responses.py` + `test_protocol.py`: **272 passed, 5 failed — all 5 pre-existing on a clean tree** (gpt-oss harmony vocab download in this offline environment; verified by stashing the change and re-running: identical failure list).
- Full `test/registered/unit/entrypoints/openai/` sweep: 491 passed; same 5 pre-existing failures plus the one flipped test, now updated.
- `ruff check --select=F401,F821,F823,UP037` (project pre-commit rules), `ruff format`, `isort`, `codespell`: clean.

## Behavior-change note

Requests that previously "succeeded" by silently dropping the tools (auto + tools + format) now get a 400 with an actionable message. This matches the issue author's request, the #34881 precedent, and the alternative (models inventing schema-shaped results) being strictly worse for agents. If a soft-landing escape hatch is preferred (e.g. a server flag to restore the old drop behavior), I'm happy to add one — but silence was the bug.
