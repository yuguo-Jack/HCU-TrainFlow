# fix(security): bound top_logprobs_num, parallel sample n, and input_ids to prevent request-level DoS

[Upstream PR](https://github.com/sgl-project/sglang/pull/36856) · state: open · merged: False

## Original PR description

## Motivation

Three attacker-controlled request parameters can kill a default SGLang server
(no `--api-key`) with a **single unauthenticated HTTP request**. All three were
verified end-to-end against HEAD `989e51ba` with Qwen2.5-0.5B-Instruct on CUDA;
each crashed the entire server (HTTP frontend + tokenizer manager + scheduler +
workers) via the SIGQUIT kill-chain (`run_scheduler_process` -> SIGQUIT ->
`running_phase_sigquit_handler` -> `kill_process_tree`):

1. **`top_logprobs_num` unbounded** — `POST /generate {"return_logprob":true, "top_logprobs_num":10**9}` (also `/v1/chat/completions` with `top_logprobs`): the value reaches `logprobs.topk(k=n)` (`srt/layers/logprob_processor.py:94`) with `n > vocab_size` -> `RuntimeError: selected index k out of range` in the scheduler -> whole server dies.

2. **`n` (parallel sample num) unbounded** — `POST /generate {"sampling_params":{"n":5_000_000}}`: the tokenizer manager materializes one `GenerateReqInput` + `ReqState` + `asyncio.Event` **per rid** (`srt/managers/tokenizer_manager.py:3390-3433`) even though only `batch_size` are used; a ~65-byte request grew the process RSS past 22 GB and blocked the event loop for minutes (client disconnect does not stop the allocation).

3. **Out-of-vocabulary `input_ids`** — `POST /generate {"input_ids":[-1]}`: `_validate_input_ids_in_vocab` exists but was **never called**, and it only checked `id >= vocab_size` (negative ids pass). On tp=1 the ids reach an unmasked `F.embedding` gather (`srt/layers/vocab_parallel_embedding.py:566-576`) -> CUDA device-side assert `srcIndex < srcSelectDimSize` -> CUDA context poisoned, server dead. On CPU the same request raises `IndexError` in the scheduler -> same kill-chain.

## Modifications

- `python/sglang/srt/managers/tokenizer_manager.py`
  - Add `_validate_top_logprobs_num()`: reject values outside `[0, vocab_size]` (handles both int and per-request list forms).
  - Wire the existing (dead) `_validate_input_ids_in_vocab()` into `_validate_one_request()` and strengthen it to enforce `0 <= id < vocab_size` (negative ids included); guard against `None`/empty input.
- `python/sglang/srt/managers/io_struct.py`
  - Add `MAX_PARALLEL_SAMPLE_NUM = 1024` and reject `n` outside `[1, 1024]` in `_handle_parallel_sampling()` **before** any expansion (`_expand_inputs` / `_normalize_rid` / state materialization). Also reject non-integer `n`.
- `test/registered/unit/managers/test_request_param_validation.py` (new)
  - 13 tests covering the three guards (huge/zero/negative/non-int `n`, over-vocab/negative/list-form `top_logprobs_num`, negative/over-vocab/nested-batch `input_ids`, plus legitimate-value pass cases).

All rejections return an HTTP 400 error and leave the server alive; legitimate
requests are unaffected (verified live: normal generation and
`top_logprobs_num=3` both return 200 after the fix).

## Pull request overview

This PR hardens SGLang’s request validation to prevent request-level denial-of-service (DoS) conditions caused by attacker-controlled parameters reaching unsafe execution paths (e.g., `torch.topk`, per-sample request expansion, and embedding gathers).

**Changes:**
- Add validation to bound `top_logprobs_num` to `[0, vocab_size]` before it can reach `torch.topk(k=...)` and crash the scheduler.
- Bound parallel sampling fan-out (`sampling_params.n`) via `MAX_PARALLEL_SAMPLE_NUM = 1024`, rejecting invalid values before any per-sample expansion/materialization.
- Wire and strengthen `input_ids` vocabulary validation to enforce `0 <= id < vocab_size`, including negative-id rejection; add unit tests covering these guards.

### Re-checked against current `main` (`4387a94cf`)

Three of the holes are still open, and the branch is closer to mergeable than its age suggests. Some questions on how far the bounds actually reach.

### 1. Status on today's main

- `top_logprobs_num`: `get_top_logprobs_raw` still does `max_k = max(top_logprobs_nums)` then `logprobs.topk(max_k, dim=-1)` with no clamp (`python/sglang/srt/layers/logprob_processor.py:105-106`).
- `parallel_sample_num`: `io_struct.py:548` reads `sampling_params.get("n", 1)` and there is no cap on main; I checked `server_args.py` for a corresponding knob and there isn't one.
- `input_ids`: `GenerateReqInput._validate_inputs` (`io_struct.py:454-486`) checks presence and shape but never range-checks against the vocabulary, and `_validate_input_ids_in_vocab` no longer exists in `tokenizer_manager.py` at all — so the description's "wire the existing (dead) helper" no longer matches main; this PR re-adds it. Worth a line in the description about that.
- The kill-chain framing still holds structurally: `run_scheduler_process` catches any exception escaping `run_event_loop` and calls `parent_process.send_signal(signal.SIGQUIT)` (`scheduler.py:6647-6652`).

Good news on cost: `patch -p1 --dry-run` of both source hunks against `4387a94cf` applies clean (`io_struct.py`, `tokenizer_manager.py`), so the rebase is cheap despite the branch being from late August.

On CI: head `6fc4819cea` has `call-gate / pr-gate` failed and `base-a-test-cpu` plus every GPU job skipped — the fork PR has no `run-ci` label, so the 13 new tests have never run in CI. The registration itself looks right (`register_cpu_ci(est_time=5, suite="base-a-test-cpu")`, `base-a-test-cpu` is a valid suite on main, and the `if __name__ == "__main__": unittest.main()` tail is one of the two forms `test/README.md` requires).

### 2. The `n` cap bounds one factor, not the product

`_expand_inputs` computes `num = self.batch_size * self.parallel_sample_num` (`io_struct.py:618`), and `batch_size` comes straight from `len(self.text)` / `len(self.input_ids)` (`io_struct.py:497`) with no request-side ceiling that I could find. So `{"text": [<1000 prompts>], "sampling_params": {"n": 1024}}` still materializes on the order of a million sub-requests and per-rid states, which is the same failure mode vector 2 describes, just through the batch axis. Two options: bound the product rather than `n` alone, or keep the cap and note in the comment why the batch dimension is considered handled elsewhere. The manager-side coverage I read (`test/registered/unit/managers/test_io_struct.py`, `test/registered/openai_server/basic/test_openai_server.py`) only exercises `n` in the 2-3 range, so a 1024 ceiling doesn't disturb it.

Ordering is right, incidentally: `_handle_parallel_sampling()` runs at `io_struct.py:445`, before `_normalize_batch_inputs()`/`_expand_inputs()`, so rejection does happen ahead of expansion as claimed.

Should `MAX_PARALLEL_SAMPLE_NUM` be a server arg? A hardcoded 1024 gives an operator who legitimately wants more no lever short of a code change, and the repo's usual home for that is a `--max-*` flag.

### 3. Validation-only leaves the crash sites live

For vector 1, a one-line `max_k = min(max(top_logprobs_nums), logprobs.shape[-1])` in `get_top_logprobs_raw` would cost nothing on the normal path and keep a future call site from reintroducing the same whole-server kill. Request-layer validation is the right primary defense, but the topk site is cheap enough to harden as well. (For the embedding gather I agree the request layer is the only sane place — masking at `vocab_parallel_embedding` would put a check in the model forward.)

### 4. Paths that may still reach the model with unchecked ids

- `_validate_input_ids_in_vocab` returns early on empty input, and `_validate_inputs` explicitly permits an empty `input_ids` when a session is in play (`io_struct.py:500-512`, "Session history may supply the entire prompt"). Do session-reconstructed ids get range-checked anywhere, or is that a second door to the same gather?
- The `n` bound lives in `GenerateReqInput.__post_init__`, the other two live in `TokenizerManager`. Any caller that builds a tokenized object without going through `_tokenize_one_request` skips the `top_logprobs_num` and `input_ids` checks but not the `n` check. Putting all three in `io_struct` would remove that asymmetry — or it would be useful to list which entrypoints (gRPC bridge, `/encode`, `/classify`) do and do not hit the tokenizer-manager path.
- The rejection messages interpolate the whole sequence: `f"The input_ids {seq} contains values outside the vocab range..."`. With a 100k-token prompt, one bad id produces a ~1MB exception string that gets formatted, logged and echoed into the response. Suggest reporting the offending index plus a bounded preview.

### 5. Two smaller points

- The per-id check runs an `any(... for id in input_ids)` with two `isinstance` calls per element, inside the tokenizer manager's event loop, for every pre-tokenized request. `min(input_ids) < 0 or max(input_ids) >= vocab_size` gets the same coverage from builtins that run in C. A number for a long prompt (say 128k ids, before/after) would settle whether it matters.
- `_make_tokenizer_manager` uses `object.__new__(TokenizerManager)` and assigns the handful of fields the helpers touch. That will keep passing if `__init__` later makes one of those fields derived rather than stored, so the test would be validating a shape production never has. Also `test_multimodal_padding_ids_not_rejected_as_user_input` asserts that `_validate_one_request` does *not* range-check, which pins the placement: if the check later moves into `_validate_one_request`, that test flips from documenting correct behavior to blocking it.
