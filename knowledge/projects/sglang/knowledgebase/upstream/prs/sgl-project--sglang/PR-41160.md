# [Fix] hunyuan: Restore q/k shape after per-head qk_norm

[Upstream PR](https://github.com/sgl-project/sglang/pull/41160) · state: open · merged: False

## Original PR description

Split out of #39754 so this independent `models/hunyuan.py` fix is reviewed on its
own, per @ShaiShmuel's request on that PR.

## Bug

HunYuan v1 attention with `use_qk_norm: true` reshapes q/k to `(tokens*heads, head_dim)`
for the per-head RMSNorm but never restores the flat `(tokens, heads*head_dim)` layout,
so `o_proj` receives a wrongly-shaped tensor:

```
RuntimeError: mat1 and mat2 shapes cannot be multiplied (64x128 and 2048x2048)
```

Since piecewise CUDA graph became the default (#16331, v0.5.10), this crashes at
**startup/warmup on NVIDIA GPUs with default flags** for every HunYuan v1 checkpoint
that sets `use_qk_norm`. flashinfer/fa3 return `o.view(-1, heads*head_dim)`, which used
to mask the per-head shape, but the piecewise CUDA graph extend path in
`radix_attention.py` allocates `output = torch.empty_like(q)`, so the broken shape
reaches `o_proj` on every backend (flashinfer, fa3, triton). It also crashed the
non-CUDA (triton / Intel XPU) `o_proj` independent of CUDA graph.

Repro (v0.5.10.post1): `python -m sglang.launch_server --model-path tencent/Hy-MT2-1.8B`
with no extra flags. Reproduced on L4 (flashinfer, triton) and H100 (fa3, flashinfer,
triton). Prior reports #21127 / #21128 were closed as stale without a fix. Thanks to
@ShaiShmuel for the CUDA repro and root-cause detail.

## Fix

Restore the flat shape after the per-head qk_norm:

```python
q = self.query_layernorm(q.reshape(-1, self.head_dim).contiguous()).reshape(-1, self.q_size)
k = self.key_layernorm(k.reshape(-1, self.head_dim).contiguous()).reshape(-1, self.kv_size)
```

## Test

`test/registered/e2e/models/test_hunyuan_v1_qk_norm_startup.py` boots
`tencent/Hy-MT2-1.8B` with default flags (piecewise CUDA graph on) and runs a short
generation, guarding the warmup regression on every backend. Registered for CUDA CI
(`base-b`, 1-gpu).

## Accuracy

- Hunyuan-A13B, Intel XPU Arc Pro B60 tp-8: loads with 0 skipped params; gsm8k (lm-eval)
  exact_match **66.87** (H200 67.10).
- @ShaiShmuel verified on v0.5.10.post1: this patch + triton + `--disable-piecewise-cuda-graph`
  loads and serves correctly on L4.

- ShaiShmuel · COMMENTED · 2026-09-28T18:06:58Z · [source](https://github.com/sgl-project/sglang/pull/41160#pullrequestreview-5342767829)

Thanks for splitting this out. We reviewed the change, backported it onto v0.5.10.post1, and tested it live on an L4 and an H100.

**The reshape looks right.**
- `q_size` and `kv_size` are per-rank, so it holds under tensor parallelism, including KV-head replication.
- `HunYuanDenseV1ForCausalLM` subclasses the MoE class, so the dense models and A13B share the fix.
- Rotary-then-norm matches HF `modeling_hunyuan_v1_dense`.

With the fix, Hy-MT2-1.8B boots with default flags on L4 (flashinfer, triton) and H100 (fa3), and the test prompt returns ` Paris.`. On four greedy translation prompts, the served output on H100 matches a Transformers greedy decode on H100.

**On v0.5.10.post1, the reshape alone is not enough under piecewise CUDA graph.** The server boots, but on every backend we tried it dies on a later request (the 4th in our sequence) with `AssertionError: PCG capture stream is not set, please check if runtime recompilation happened`.

`TORCH_LOGS=recompiles` shows the trigger: `Recompiling function forward in hunyuan.py:522 ... GLOBAL_STATE changed: grad_mode`. Llama, Qwen2, Qwen3 and hunyuan_v3 all decorate `forward` with `@torch.no_grad()`, but `HunYuanMoEV1ForCausalLM.forward` does not. So the graph captured at init runs with grad on, requests are served with grad off, and Dynamo recompiles. A Qwen3-1.7B control with the same flags and request sequence shows no recompile.

Adding the decorator on top of this PR fixes it: 8/8 requests succeed, including 1.6k- and 2.6k-token prompts, with no recompiles and the server still up afterwards. This held on L4 flashinfer, L4 triton and H100 fa3. The change is in `HunYuanMoEV1ForCausalLM` (`hunyuan.py:600` at this head). It is outside the diff, so GitHub won't take it as a one-click suggestion:

```diff
+    @torch.no_grad()
     def forward(
         self,
         input_ids: torch.Tensor,
```

On current main this probably doesn't crash. The assert became an eager fallback, and capture now runs under `@torch.no_grad()` in `PrefillCudaGraphRunner._run_forward`. We haven't run main. The decorator would still be worth adding:
- it keeps HunYuan consistent with the other models;
- it avoids a possible silent fallback to eager;
- it makes the fix safe to backport to 0.5.10-0.5.15.

**Test suggestions**
- Send a few requests of different lengths, including a repeat of one, and check that the server is still up afterwards. On 0.5.10.post1 a single request passes even though the server dies later.
- Assert on `Paris` and add a request timeout; there is an inline suggestion for both.
- Nit: the docstring says piecewise CUDA graph is the default. On CUDA, main now defaults to the breakable prefill graph (`cuda_graph_config.py`). Both paths allocate `empty_like(q)` in `RadixAttention`, so the test still covers the bug; "prefill CUDA graph" would be more accurate.

CI hasn't run yet. The `run-ci` label is missing, so every test stage was skipped.
