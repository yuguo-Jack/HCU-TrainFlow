## Motivation

Out-of-tree (OOT) platforms cannot run EAGLE-family speculative decoding today, including NEXTN/MTP drafts:

- The built-in `EAGLEWorkerV2` keeps its bookkeeping in device tensors with data-dependent shapes. Platforms that compile a graph per shape cannot run it efficiently, so they ship their own speculative worker (for example one that keeps the bookkeeping on the host) and today have to monkeypatch `SpeculativeAlgorithm.create_worker` to install it.
- On an OOT device the built-in path is broken without saying so: `verify_tree_greedy_func` has no branch for it and returns its inputs unfilled, and `build_tree_kernel_efficient` calls a kernel that is only imported on CUDA/HIP/MUSA builds.

This PR is the first step of generic OOT speculative-decoding support. It adds the platform worker factory and makes the unsupported built-in path fail loudly. Follow-ups will add the seams the built-in worker needs on an OOT device (draft attention backend registry, draft graph runners, spec kernels on `BaseFusedOp` with native fallbacks).

## Modifications

- `SRTPlatform.get_speculative_worker_cls(algorithm)` (default `None`). On an OOT platform `create_worker` returns this class for any algorithm; `None` keeps the built-in worker. The class is constructed with the built-in worker's keyword arguments and must reject flags it cannot serve. `SpeculativeAlgorithm.get_platform_worker_cls()` is the single lookup.
- EAGLE / EAGLE3 / NEXTN / STANDALONE on an OOT platform now require `supports_speculative_algorithm(algorithm)` (NEXTN is asked as `"EAGLE"`), mirroring the existing DFLASH gate, with an actionable error.
- `adaptive_unsupported_reason()` reports a platform worker, so `--speculative-adaptive` falls back to static parameters with the existing warning instead of being silently ignored (`AdaptiveController` lives only in `EAGLEWorkerV2`).
- `build_tree_kernel_efficient` and `verify_tree_greedy_func` raise `NotImplementedError` via `reject_out_of_tree_path` on an OOT device that has no tree kernel. In-tree devices and OOT platforms on a CUDA/HIP/MUSA torch build are unchanged.
- Docs: the hook is added to the plugin guide.

**Behavior change for OOT platforms:** EAGLE-family algorithms now need `supports_speculative_algorithm(...)` to return True (default False, same as DFLASH). Built-in platforms are unaffected.

## Accuracy Tests

No change on built-in platforms: every new branch is guarded by `is_out_of_tree()` or sits on a path that previously raised or computed nothing.

## Tests

`test/registered/unit/spec/test_oot_eagle_hooks.py` (CPU, `base-a-test-cpu`):

- worker selection: the platform class wins on OOT, the built-in worker when the platform declines, in-tree platforms never consult the hook;
- algorithm gate: an unsupported OOT platform is rejected, built-in platforms are not gated;
- adaptive falls back with a platform worker and stays available with the built-in one;
- tree construction and greedy verification raise on an OOT device without a tree kernel (both fail on the pre-fix code), and the in-tree fall-through is unchanged.
