# [Perf] [NVIDIA] kimi-k3: Low-latency SM107 decode path

[Upstream PR](https://github.com/sgl-project/sglang/pull/46474) · state: open · merged: False

## Original PR description

## Motivation

Kimi-K3 NVFP4 decode at TP8 on SM107 is launch- and latency-bound at batch 1: the MoE front projection, the shared-expert path and the finalize all-reduce each pay separate launches, and the fused K3 collectives were tuned for SM100/SM103. This PR carries the SM107 low-latency path over from the fork. Every change is behind an SM107 check; nothing changes on other architectures.

## Modifications

- `model_overrides/kimi_k3.py`: admit SM107 (without speculative decoding) to the trtllm_mla default backends.
- `k3_ar_fusion.py`, `all_reduce_residual.py`, `ar_fusion.cuh`: the deferred MoE finalize + push all-reduce + RMSNorm can also carry the shared-expert partials (`[latent | shared]`) so both ride one collective. The model only takes this joint path on SM107 at BS1 (gated here; the Blackwell enablement will come with its own numbers).
- `gemm_ag.cuh/.py`: tunable producer grid (`split_n = 8` at M <= 8 on SM107) and an FP32 gather variant that shards the replicated latent down-projection across TP8; at `4 <= M <= 8` the split-8 producer runs on tensor cores (`mma.m16n8k16`), `M <= 2` stays on CUDA cores.
- `cutedsl_bf16_gemm.py`: on SM107, skinny BF16 projections (`m <= 8`, `m * n <= 8192`, `k > n`) route from TGV to the JIT tiny GEMM.
- `k3_shared_situ.cuh/.py`, `kimi_k3.py`: BS1 TP8 SM107 front path: router rows move into the sharded FP32 latent GEMV + multicast gather, and the shared-expert gate/up is fused with SiTU on the side stream.
- `test_collectives.py`: `test_gemm_all_gather_split8_with_c` covers the split-8 module at M = 1, 2, 4, 8 (runs on B200 too, calling the module directly).

## Accuracy Tests

- CI: `test_collectives.py` on 4-GPU and 8-GPU B200, `test_situ_and_mul_quant.py`, `test_cutedsl_bf16_gemm.py` (combined-branch run, same code).
- SM107 TP8: gemm_ag split-8 output matches the fp32 reference on all 8 ranks at M = 1, 2, 4, 8; GSM8K below.
- This branch vs main (39b54ae0ee) on two SM107 trays, Kimi-K3 NVFP4 TP8, DSpark block 7 with real acceptance, fp8 KV, no HiCache: GSM8K 200 questions, 5-shot, temperature 0: 0.975 / 0.005 invalid (branch) vs 0.985 / 0.005 (main); DSpark acceptance length 5.6 (branch) vs 5.2 (main) on the prompt below.

## Speed Tests and Profiling

Fork measurements on SM107 TP8 (2 x 4), Kimi-K3 NVFP4, bs=1, 60k in / 1k out, no speculative decoding: 29.2 -> 150.5 output tok/s for the low-latency path; tiny GEMM vs TGV at k = 7168: 1.44x at [1, 2432], 2.11x at [1, 1536], 2.64x at [1, 896], 3.19x at [1, 576]; tensor-core gemm_ag at M=8: 8.04 -> 6.45 us per call.

Same servers, `one_batch_server --base-url`, batch 1, 60k in / 1k out, 95% cache hit, three repeats (first branch repeat excluded: cold JIT, 5.2 s TTFT):

| Arm | Latency (s) | Output tok/s | Steady decode tok/s | Acc length |
|---|---:|---:|---:|---:|
| main | 2.33 / 2.33 | 463.7 / 464.0 | 449.5 | 5.2 |
| this PR | 2.26 / 2.26 | 479.4 / 479.5 | 496.3 | 5.6 |

Steady-state decode +10% per request, output throughput +3.4%.
