# [AMD][Kimi-K3]: skip the routed_input copy when Aiter reads the front slice as-is

[Upstream PR](https://github.com/sgl-project/sglang/pull/41848) · state: closed · merged: False

## Original PR description

# [AMD][Kimi-K3]: skip the routed_input copy when aiter reads the front slice as-is

## Motivation

On ROCm, each Kimi-K3 MoE layer copies a strided view of the front GEMM output into a dense buffer before the experts, even though aiter's A8W4 kernels already read that view in place. This pull request skips that copy when the slice is 16-byte aligned, saving about 0.3–0.4 ms of decode time per token on MI355X while leaving every other backend unchanged. More specifically, `KimiK3MoE._forward_fused` reads `hidden_states` once through the merged front weight and splits the result into `[gate_up | router_logits | routed_input]`, so `routed_input` is a **strided view** into the front GEMM's output.

Today that view is unconditionally repaired into a dense buffer before it reaches the experts:

```python
if self._moe_front_needs_dense_bf16:
    routed_input = routed_input.to(hidden_states.dtype).contiguous()
```

`_moe_front_needs_dense_bf16` only clears for the SM100 trtllm-gen mxfp4 runner, so ROCm always takes it. The front is already bf16 on HIP (`_front_fp32` is `not _is_hip and ...`), which makes the `.to()` a no-op and leaves `.contiguous()` as a pure `[num_tokens, moe_hidden_size]` device-to-device copy — once per MoE layer, per forward.

That copy is not needed under aiter's A8W4 activation mode (`AITER_SITUV2_A8W4`), which is the MoE configuration Kimi-K3 is most commonly served with on ROCm. There, `moe_runner/aiter.py` → `aiter.fused_moe` quantizes through `fused_dynamic_mxfp8_quant_moe_sort`, and both kernels behind that entry address rows via `input.stride(-2)`, with only a same-shape `view(-1, N)` in between — so aiter consumes the strided slice directly.

## Modifications

Adds `KimiK3MoE._aiter_takes_front_slice`, a cached property that is true exactly when aiter reads the routed rows as the front GEMM hands them over. It requires all of:

- ROCm, `AITER_SITUV2_A8W4`, `Mxfp4MoEMethod`, aiter runner backend, and `method.hidden_size == self.moe_hidden_size`
- `sum(self._front_sizes) % 8 == 0` **and** `sum(self._front_sizes[:-1]) % 8 == 0` — aiter's `fused_mx_quant_moe_sort_kernel` vector-loads 16 B from each row start, so both the front row pitch and the slice's own base offset into it must be 8 bf16-element aligned

The activation mode matters because only A8W4 is stride-aware end to end: a16w4 re-densifies inside the FlyDSL stage-1 port, and A4W4 hands the slice to a stage1 that takes no stride. Both keep the copy. A8W4 also wins over `AITER_SITUV2_A4W4` when both are set, matching aiter's own precedence. Gating on it is narrow in code but not in practice — it is the mode the ROCm Kimi-K3 serving configuration normally runs.

The hot-path change is one added conjunct:

```python
# False off ROCm, so this only ever widens the HIP path
if self._moe_front_needs_dense_bf16 and not self._aiter_takes_front_slice:
    routed_input = routed_input.to(hidden_states.dtype).contiguous()
```

`_aiter_takes_front_slice` is `False` off ROCm and under every other activation mode, so every other backend is bit-for-bit unchanged. The property is also added to the cache-invalidation list in `_merge_front_weights`, since it depends on `_front_sizes`.

Single file: `python/sglang/srt/models/kimi_k3.py`.

## Accuracy Tests

The strided view and the contiguous copy hold identical values, and aiter's quant kernel reads the same rows either way — this is a memory-layout change, not a numerics change.

`lm_eval` gsm8k, 5-shot, full set (1319 questions), 64 concurrent, MI355X / ROCm 7.2.4 / SGLang 0.5.20:

| Filter | Base | Strided | Δ |
|---|---|---|---|
| flexible-extract | 0.9682 ± 0.0048 | 0.9621 ± 0.0053 | -0.0061 |
| strict-match | 0.9674 ± 0.0049 | 0.9613 ± 0.0053 | -0.0061 |

Both deltas are inside run-to-run noise — about 0.85σ on the standard error of the difference, or 8 questions out of 1319. Decode results are deterministic for a fixed batch composition, but the serving runs batch differently from one another, so a delta of this size is expected. No accuracy regression.

## Speed Tests and Profiling

Removes one `[num_tokens, moe_hidden_size]` bf16 copy per MoE layer per forward.

MI355X, Kimi-K3, ROCm 7.2.4 / SGLang 0.5.20, `AITER_SITUV2_A8W4=1`, `bench_serving` random, single run per point:

| ISL/OSL | Concurrency | TPOT base (ms) | TPOT strided (ms) | Output tok/s base | Output tok/s strided | Uplift |
|---|---|---|---|---|---|---|
| 1024/1024 | 4 | 18.57 | 18.20 | 207.9 | 212.0 | +2.0% |
| 1024/1024 | 16 | 27.16 | 26.87 | 562.8 | 568.7 | +1.1% |
| 1024/1024 | 64 | 45.88 | 45.29 | 1318.0 | 1335.2 | +1.3% |
| 8192/1024 | 4 | 19.59 | 19.24 | 195.5 | 199.0 | +1.8% |
| 8192/1024 | 16 | 32.03 | 31.73 | 463.3 | 467.7 | +0.9% |
| 8192/1024 | 64 | 65.54 | 65.14 | 888.1 | 893.3 | +0.6% |

The absolute TPOT saving sits at roughly 0.3–0.4 ms/token across every point (0.59 ms at 1024/64 is the one outlier), which is what a per-step saving proportional to layer count and near-flat in batch size should look like: the copy is small and latency-bound at decode batch sizes, so the relative uplift shrinks as concurrency grows and the step gets longer. TTFT moves by ≤0.6% in either direction on the 1024-token prefills and ≤0.1% on the 8192-token ones — noise.
