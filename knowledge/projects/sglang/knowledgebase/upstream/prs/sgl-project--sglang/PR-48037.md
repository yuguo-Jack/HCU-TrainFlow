# [Perf] disaggregation: Cache host-staged decode admission accounting across a transfer pass

[Upstream PR](https://github.com/sgl-project/sglang/pull/48037) · state: open · merged: False

## Original PR description

## Motivation

`DecodeTransferQueue.pop_transferred` admits completed host-staged requests to device memory through `DecodePreallocQueue.allocate_host_staged`. #46898 made a pass stop device admission at the first refusal, because trying every later request recomputed the request-independent accounting (running-batch token sums, maximum per-request growth, transfer-queue device-destination count, retracted-token requirements) on every attempt: O(W × (R + Q + T)) per pass for W attempts, R running requests, Q transfer entries and T retracted requests.

Stopping at the first refusal trades utilization for that bound. A later, smaller request that would fit waits for the next pass even when device capacity is free, and near a full pool that is exactly when the capacity matters. This change lets every completed request in the pass try, and keeps the pass linear by computing the shared accounting once.

## Modifications

- `_HostStagedAdmissionStats` holds the pass-invariant accounting: retractable full/SWA token sums over the running batch, the maximum per-request growth (full and SWA), the number of transfer entries holding a device destination, and the retracted queue's full/SWA token requirements. Each field is filled lazily on first use and reused by later admission calls in the same pass.
- `DecodePreallocQueue._use_host_staged_admission_stats` scopes the cache with a context manager around each `allocate_host_staged` call in `pop_transferred`. Outside that scope (every other caller, the next pass, and after an exception) `_host_staged_admission_stats` is `None` and all helpers read the live queues as before.
- A successful admission increments the cached device-destination count so later checks in the same pass see it; the pass-local "first refusal" flag from #46898 is removed, so a refused request is skipped with `continue` and later ones still try, in queue order.
- `_need_space_for_single_req` returns early for an empty running batch or a `None` retractable count, then computes the maximum per-request requirement once and subtracts the retractable tokens; the result is unchanged.
- New `_retracted_token_counts` returns the retracted queue's `(full, swa)` requirements in one walk and replaces the two separate loops in the full and SWA allocatable-budget helpers.
- New `has_device_destinations` property on `DecodePreallocQueue`; `disagg_transfers_in_flight` in `disaggregation/utils.py` reads it instead of scanning the transfer queue itself, so the unified-memory pin predicate also benefits from the cached count during admission.
- `test_unified_memory_move_gate.py`: `_FakePreallocQueue` now subclasses `DecodePreallocQueue` and holds the fake transfer queue, so the move-gate test exercises the real `has_device_destinations` property.

Rebased onto main after #43908: the two new iterations over the decode transfer queue (`has_device_destinations` and `_active_req_count`) read `self.transfer_queue.queue.items()`, matching the request-list container that refactor introduced; the `pop_transferred` loop keeps its `queue = list(self.queue.items())` form.

Allocator availability, eviction credit and SWA capacity are not cached; allocation, reclamation and failed-transfer cleanup inside a pass affect the next decision. The cache holds Python integers only; the admission path adds no device readback or GPU-to-CPU synchronization.
