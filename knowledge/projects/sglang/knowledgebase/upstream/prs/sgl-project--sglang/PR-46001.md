# [CI] [AMD] diffusion: drain the VAE stream before asserting it is idle in test_overlap_and_serial_vae_inputs_match

[Upstream PR](https://github.com/sgl-project/sglang/pull/46001) · state: closed · merged: False

## Original PR description

### What

`TestCosmosDreamsRuntime::test_overlap_and_serial_vae_inputs_match` calls
`queue.stream.synchronize()` before `self.assertTrue(queue.stream.query())`.

### Why

The block under test injects a rollout failure, which cancels in-flight VAE work. The
test then asserts the stream is idle. But `Stream.query()` is a non-blocking poll -- it
reports whether the device has *already* finished, not whether it *will*. The cancelled
work is still draining when the poll happens, so `query()` returns `False` at random and
the subtest fails with no error message beyond `SUBFAILED(dtype=torch.float32)`.

`synchronize()` blocks until the device actually drains, which is what the assertion
means to check. The assertion itself is kept so the test still fails loudly if the stream
is somehow non-idle after a full drain.

This is a test-side race, not a product bug -- no mmgen runtime code is touched.

### Verification -- offline on MI300X (gfx942, ROCm 10.0)

Container from `rocm/sgl-dev:v0.5.22-rocm10-mi30x-20261017`, single GPU, **idle card**
(no competing load), 20 consecutive runs of the single test each way:

| | result |
|---|---|
| **Before** | **17 / 20 passed** -- 3 failures, ~15% flake rate |
| **After** | **20 / 20 passed** |

The failure is *not* load-dependent: it reproduces on an otherwise idle GPU, which is
consistent with a poll/teardown race rather than contention. An A/B under added GPU load
did not meaningfully change the rate.

### Note for reviewers

I did not audit the rest of the file for the same pattern. If other tests poll `query()`
right after a cancellation they will be flaky in the same way, but I only have measured
evidence for this one, so I kept the change minimal rather than speculatively editing
sites I have not reproduced.
