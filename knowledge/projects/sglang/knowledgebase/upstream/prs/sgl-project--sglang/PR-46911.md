## Original PR description

## Motivation

In PD-disaggregated serving, `MooncakeKVManager.transfer_worker` blacklists a
Mooncake session after a **single** failed KV send (threshold `>= 1`), under the
stated assumption *"Failures should never happen if the session is not dead"*
(`python/sglang/srt/disaggregation/mooncake/conn.py`).

That assumption does not hold for timeouts. `batchTransferSync` is a synchronous
call with a 30-second deadline: it returns non-zero when the deadline expires,
and the deadline can expire while the session itself is perfectly healthy — for
example when the transfer queue is stalled by sends to another peer that just
died (head-of-line blocking).

We hit exactly this in a production PD-disaggregated deployment. One decode
node hung in a half-dead state: its kernel still accepted TCP connections,
but its transfer process never answered (handshake connects succeeded and
then timed out waiting for the response, zero bytes received). This is worse
for the sender than a fully down node: a refused connection fails in
milliseconds, a hung one makes every handshake block until the socket read
timeout.

1. The transfer engine posts slices for **all** peers on a RNIC from a single
   thread, and performs the handshake for an unconnected endpoint
   synchronously on that thread. While it waited on the hung peer's
   handshake, sends to **healthy** decode peers queued behind and timed out.
2. The one-strike blacklist marked those healthy sessions as dead on their
   first (timeout-only) failure.
3. There is no automatic recovery: `SGLANG_ENABLE_FAILED_SESSION_PROBE`
   defaults to `false`, and a healthy decode side never re-registers
   `KVArgs`, so the blacklist entry is never cleared.
4. The router is unaware of the prefill's local blacklist: the healthy decode
   rank keeps being allocated rooms, so requests keep arriving whose KV
   destination is that rank; the prefill fails fast on every one of them
   (`Decode instance could be dead`) without ever attempting a send.

The result: the prefill kept erroring — with client-visible errors — long
after the faulty node had been removed. The persistent errors were no longer
caused by the dead node; they came from a **healthy** peer stuck on the
prefill's local blacklist, degrading it until process restart.

This PR makes the blacklisting threshold configurable and gives it
**consecutive-failure** semantics, so operators can absorb transient timeouts
without changing the default behavior. It complements (not replaces) the
existing failed-session probe: the probe is the recovery path, the threshold is
the false-positive guard.

## Modifications

- Add `SGLANG_MOONCAKE_SESSION_FAILURE_THRESHOLD` (`EnvInt`, default `1` —
  fully backward compatible).
- Extract the duplicated blacklisting logic into
  `MooncakeKVManager._record_session_failure()` and use it in both failure
  paths:
  - the KV chunk send failure path (previously `>= 1`),
  - the last-chunk state-component send failure path (previously blacklisted
    unconditionally, without even counting).
- Reset the per-session failure counter after a successful send
  (`_clear_session_failures()`), so the threshold counts **consecutive**
  failures instead of accumulating sporadic failures over hours.
- Document the new env var in
  `docs/docs/references/environment_variables.mdx`.

Covered cases:

- default threshold `1` blacklists on the first failure (backward compatible);
- threshold `3` tolerates two transient failures and blacklists on the third;
- a successful send resets the streak (two failures + success + two failures
  stay below a threshold of 3);
- failure streaks are independent per session;
- the env var default is `1`.
