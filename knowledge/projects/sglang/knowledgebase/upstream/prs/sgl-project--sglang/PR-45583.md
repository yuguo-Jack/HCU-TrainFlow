# [Perf] kda: Size the speculative ReplaySSM ring by running requests

[Upstream PR](https://github.com/sgl-project/sglang/pull/45583) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-linear-replayssm-spec`, KDA allocates its speculative ReplaySSM ring for every Mamba slot, but each verify only writes the running requests' rows, and the same step's commit folds them. On GLM-5.3-Flash NVFP4 at TP2 with 512 Mamba slots and 64 running requests, the ring takes 12.8 GB per GPU.

## Modifications

- Allocate the KDA spec ring with one row per running request, including on PD decode servers, and charge it to the KV pool as fixed request scratch.
- Index the ring by the verify scratch row that `intermediate_conv_window` uses: `intermediate_state_indices` during verify and `src_indices_raw` at commit (the batch row, or the request row under PP). The unfused kernel takes it as an optional `ring_indices` (note that `ring_indices` defaults to the state slot, so GDN's call doesn't change).
- Require `--speculative-algorithm` with `--enable-linear-replayssm-spec`, since the ring is now sized by `--max-running-requests`, which can't be `None`.
- Describe the ring as per request in the Kimi-K3 cookbook.

## Accuracy Tests

GLM-5.3-Flash NVFP4 on 2xB200 with a DFlash2 draft, 512 Mamba slots, 64 running requests, and ring length 16:

| | main | this PR |
|---|---|---|
| Spec ring per GPU | 12.8 GB | 1.63 GB |
| KV cache tokens | 647,680 | 1,637,120 |
| GSM8K | 0.930 | 0.930 |
| Accept length | 5.07 | 5.07 |

Both arms allocate the unused `d`/`k` rings that #45509 removes. With both PRs, the ring takes 1.08 GB per GPU.

New pool tests check that the KDA spec ring holds the accounted bytes per running request, on a regular and a PD decode server. The backend verify-commit test now sizes its rings by request. The ring, fold, fused verify, and CuTe DSL tests pass on CPU (39), 1xH200 (78), and 1xB200 (10).
