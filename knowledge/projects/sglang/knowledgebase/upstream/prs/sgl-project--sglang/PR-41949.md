# [Feat] [AMD] attention: Add UltraQuant MXFP4 KV cache backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/41949) · state: open · merged: False

## Original PR description

Long-context and agentic serving is bounded by KV-cache capacity. This PR adds UltraQuant, an MXFP4 KV cache for ROCm (FP4 E2M1 codes with a UE8M0 scale per group of 32), with keys Hadamard-rotated before quantization. On Qwen3.5-397B-A17B (MXFP4 weights) it matches FP8 KV at low concurrency and pulls ahead as the pool fills, outperforming FP8 KV with HiCache at high concurrency without needing a host-memory tier, at no cost to accuracy or time to first token.

## Modifications

- `--kv-cache-dtype ultraquant_4bit` and `--attention-backend ultraquant`.
- `UltraQuantKVCacheMethod` in the KV cache quant registry: packed code and scale buffers, cell size, and a pool cap that keeps every code buffer within the decode kernel's 32-bit buffer offset.
- `UltraQuantAttnBackend` (`srt/layers/attention/ultraquant_backend.py`), built on the Triton backend so metadata, graph capture and scheduling are unchanged. Queries are rotated into the key basis; only the kernel calls differ.
- Kernels:
  - Store: fused Hadamard rotation, quantization and scatter (`kernels/ops/kvcache/ultraquant.py`).
  - Decode: a FlyDSL kernel on gfx950 for head_dim 256 and GQA 6/8/16 (`kernels/ops/attention/flydsl/`), with a Triton FP4 decode for other shapes.
  - Extend: native FP4 Triton kernel; large chunks gather-dequantize the run once and use aiter flash attention.
- Format reference in `srt/layers/quantization/ultraquant_tensor.py`, used by the tests as the oracle.
- At head_dim 256 an MXFP4 cell is 136 bytes per token per head per side (128 code plus 8 scale) against 256 for FP8, so the pool holds 1.88x the tokens per byte.
- Supported models: bfloat16 models with MHA/GQA attention (the FlyDSL decode loads bf16 queries), on gfx950 (MI350/MI355). Rejected at startup: other devices, non-bf16 models, MLA models, sliding-window hybrid pools, and `--speculative-algorithm`, `--disaggregation-mode`, `--enable-hierarchical-cache`, `--enable-lmcache`, `--enable-unified-memory`, `--pp-size > 1`, `--dcp-size > 1`.

## Usage

```bash
python -m sglang.launch_server \
  --model-path amd/Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2 --tp 2 \
  --kv-cache-dtype ultraquant_4bit --attention-backend ultraquant \
  --page-size 16 --mem-fraction-static 0.8 \
  --reasoning-parser qwen3 --trust-remote-code
```

**GPQA-Diamond** (198 questions, output cap 131,072 tokens):

| Model | UltraQuant 4-bit | FP8 KV |
|---|---:|---:|
| Qwen3.6-27B | **85.86%** | 84.85% |
| Qwen3.8-27B | **90.40%** | 89.90% |
| Qwen3.5-397B-A17B | 86.74% | 87.75% |

The 27B rows are a single pass, and both gaps are within the standard error. The Qwen3.5-397B row averages 4 seeds (792 samples per arm) at an 81,920-token cap with that model card's thinking-mode sampling. The 1.0-point gap on Qwen3.5-397B is within noise (paired sign test over 792 pairs, p = 0.42).


## Speed Tests and Profiling

The workload is a SemiAnalysis-style agentic replay (AgentX 256K traces), run for 1 hour per concurrency point on MI355X with TP=2, no MTP, with zero failed requests.

**Qwen3.5-397B-A17B MXFP4 (GQA-16)**

**Throughput vs interactivity**

<img width="1200" height="840" alt="pr_1_pareto" src="https://github.com/user-attachments/assets/e16244c4-9bf5-4dc8-a284-4d0ccc5ff969" />


All three arms sit on one curve through C=16, after which UltraQuant takes the outer frontier: 1.05x the output throughput of FP8 KV at C=32 and 1.13x at C=40, and 1.04x to 1.11x against the stronger FP8 KV + HiCache baseline across C=16 to C=64. FP8 KV without HiCache turns back on itself at C=64, dropping to 129 output tok/s per GPU where UltraQuant sustains 643. Both arms were launched with the same `--mem-fraction-static`. UltraQuant reaches the HiCache curve without a host-memory tier.

**Inter-token latency**

<img width="1200" height="840" alt="pr_3_itl" src="https://github.com/user-attachments/assets/66a59f52-f6d9-4b4e-bb42-2732061a9d62" />


Steady-state decode cost is unchanged by the 4-bit format: 13.6 ms against 13.9 ms for FP8 KV at C=16, and 24.1 ms against 27.6 ms at C=40. Unpacking FP4 and rotating queries adds nothing measurable, and the separation at C=64 (41 ms against 218 ms) is FP8 KV thrashing on a full pool rather than a difference in kernel cost.

**Time to first token**

<img width="1200" height="840" alt="pr_4_ttft" src="https://github.com/user-attachments/assets/23f51bed-d9db-4a6a-bce0-75e939dc1348" />


Prefill is likewise unaffected: p50 and p90 track FP8 KV to within 0.03 s through C=40, so the Hadamard rotation and FP4 store cost nothing visible. Beyond C=40 the FP8 KV median rises to 71.4 s while UltraQuant stays at 1.78 s.
