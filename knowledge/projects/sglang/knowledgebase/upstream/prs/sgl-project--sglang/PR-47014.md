# [Perf] [AMD] qwen3.5: Fuse decode KV write, seg plan and cu_seqlens a…

[Upstream PR](https://github.com/sgl-project/sglang/pull/47014) · state: open · merged: False

## Original PR description

On MI355X (gfx950), each full-attention layer in decode ran three small kernels before the attention kernel (`vattn_asm`). This PR merges them into one. `reshape_and_cache_flash` now also builds the split-KV plan that `vattn_asm` needs, and `cu_seqlens_q` reuses a buffer that already exists. The extra `arange` and `_vattn_seg_plan_kernel` launches are gone.

## Motivation

In decode, each full-attention layer launched these kernels before `vattn_asm`:

| Kernel | What it does | Time per layer (before) |
|---|---|---|
| `reshape_and_cache_flash` | Writes the new K/V into the paged FP8 KV cache | 4.0 µs |
| `elementwise_kernel_with_index` | `torch.arange` that rebuilds `cu_seqlens_q`, the same values every layer | 4.2 µs |
| `_vattn_seg_plan_kernel` | Decides how to split each sequence's KV across CUs (the split-KV plan) | 5.5 µs |

Each of these kernels does very little work, so most of their time is launch overhead. Qwen3.5-397B has 15 full-attention layers, so every decode step pays for 45 of these launches.

All three kernels run one program per sequence in decode, since each sequence has exactly one new token. So the plan can be built inside the KV-cache write kernel, and `cu_seqlens_q` can come from a buffer that is already there.

## Modifications

- **`kernels/ops/kvcache/cache_ops.py`**
  - The planner logic moves into a shared Triton function, `seg_plan_program`.
  - `reshape_and_cache_flash` gets a `DO_PLAN` switch. When it is on, the program for sequence *i* also writes sequence *i*'s part of the plan. The plan is written before the slot check, so padded rows still get planned.
  - `launch_reshape_and_cache_flash` takes an optional `seg_plan` argument. Other callers don't pass it, and their behavior is unchanged.
- **`kernels/ops/attention/vattn_asm_gfx950/__init__.py`**
  - `_vattn_seg_plan_kernel` now calls the same `seg_plan_program`, so both paths build the plan with the same rules.
  - New `alloc_seg_plan()` allocates the plan buffers.
  - `mtp_verify_attn_fwd_asm` accepts a plan that was already built. In that case it skips its own plan launch.
- **`kernels/ops/attention/unified_attention_3d_mtp.py`**
  - `unified_attention_3d_mtp_decode_func` accepts `cu_seqlens_q` and `seg_plan` from the caller. It builds its own `arange` only if the caller passes nothing, or a tensor with the wrong length.
  - New `alloc_decode_seg_plan()` returns `None` when the asm kernel is not available.
- **`srt/layers/attention/aiter_backend.py`**
  - In `forward_decode`, the fused FP8 KV-write branch allocates the plan and passes it to `launch_reshape_and_cache_flash`. It only does this when the `vattn_asm` call below will use the plan, and only when the batch has one token per sequence.
  - The `vattn_asm` call gets the plan and a slice of `qo_indptr_unified_decode` as `cu_seqlens_q`.
  - When the fused write is not taken (for example SWA, the 5D shuffle cache, or non-FP8 KV), nothing changes, and the asm path plans for itself as before.

## Accuracy Tests

GSM8K (5-shot, 1319 questions) with lm-eval through the OpenAI-compatible API, on Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2, TP2, MI355X:

| | flexible-extract | strict-match |
|---|---|---|
| Baseline | 0.9735 ± 0.0044 | 0.9735 ± 0.0044 |
| This PR | 0.9727 ± 0.0045 | 0.9742 ± 0.0044 |

Accuracy is the same within the error range.

## Speed Tests and Profiling

Setup: Qwen3.5-397B-A17B-MXFP4-AttnFP8-V2, MI355X, TP2, FP8 KV cache, page size 16, input 8192 / output 1024 tokens.

| 8 | 3,573.10 | 3,622.89 | +1.39% | 9.66 | 9.53 | -1.35% | 294.06 | 292.28 |
| 16 | 4,755.50 | 4,782.05 | +0.56% | 14.49 | 14.40 | -0.62% | 294.30 | 291.09 |
| 32 | 5,887.99 | 5,922.46 | +0.59% | 23.63 | 23.48 | -0.63% | 309.98 | 309.92 |

Throughput goes up by 0.6% to 1.4% at every concurrency, and decode time per token (TPOT) goes down by about the same amount. TTFT does not change, which is expected because this PR only changes the decode path.
