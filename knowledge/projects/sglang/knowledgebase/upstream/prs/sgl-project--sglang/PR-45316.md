# [Fix] hicache: Hold PD decode restores until in-flight load-backs land

[Upstream PR](https://github.com/sgl-project/sglang/pull/45316) · state: open · merged: False

## Original PR description

## Motivation

Decode-side twin of #44070 / #44081.

A HiCache load-back attaches its device pages to the radix tree when **queued** (`commit_load_back`), before the H2D copy runs. With `--disaggregation-decode-enable-radix-cache --enable-hierarchical-cache`, the decode restore state machine (`decode_hicache_mixin.py`) marks requests READY through three shortcuts that never wait for that copy:

1. **Prealloc L1 hit**: B arrives while A loads the same prefix, matches A's pages as device prefix and is READY at once. Every reproduction hit this path.
2. **Rematch with nothing to load**: `loaded_len == 0` sets READY.
3. **State-only load** (hybrid models): `init_load_back` queues a Mamba/SWA state DMA but returns `loaded_len == 0`. The request is READY, and Phase C never runs, so the DMA is never submitted.

Decode batches don't set `hicache_consumer_index`, so the forward doesn't wait either. B reads pages still being written, which may hold another request's KV (#44070).

## Modifications

+47/-8 in two files. `decode.py`, both tree cores, `_OngoingLoadBack`, `loading_check` and the KV connectors are unchanged.

- `UnifiedRadixCache.latest_load_back_index()`: newest in-flight load-back, or -1.
- `decode_hicache_mixin.py`:
  - Phase A/B/C move unchanged into `_advance_hicache_local_restores`; shortcuts 1 and 2 no longer set READY.
  - `_try_hicache_queue_load_back` counts a DMA as queued when `load_queue` grows, so state-only loads go through Phase C.
  - New `_gate_reused_device_pages`, run after Phase C: a request reusing device pages without its own DMA binds once to the newest load-back and turns READY when it completes. Load-backs complete in order on one H2D stream. With none in flight, it is READY in the same tick, as before.

## Accuracy

2 × RTX 4090, 1P1D, `mooncake_tcp`, Qwen3-0.6B, 24,576-token shared prefix, decode HiCache (`write_through`, `direct` IO), `--disaggregation-enable-kv-checksum` on both sides. Each trial evicts prefix X to decode host memory, then sends two requests sharing X. Decode checksums the whole sequence, including the restored prefix. The existing hook `SGLANG_TEST_HICACHE_H2D_DELAY_CYCLES=50000000` stretches the H2D from ~0.12 s to ~0.76 s.

| Requests with KV checksum mismatch | main | this PR |
|---|---|---|
| Concurrent pair | **20/40** (20/20 trials) | 0/20 |
| Concurrent pair, delayed H2D | **9/20** | 0/20 |
| Second request 100 ms late, delayed H2D | **10/20** (10/10 trials) | 0/20 |
| Second request 50 ms late | — | 0/20 |
| Control: sequential pair / single request | 0/20 / 0/10 | — |

On main the failing request finishes in 0.08–0.12 s, before the H2D completes; with this PR it waits for it.

New unit test `test_decode_hicache_restore_in_flight.py` (5 cases): 4 fail on main, including the stuck state-only DMA; all pass with this PR. All 194 files under `test/registered/unit/{mem_cache,disaggregation}/` give the same results as on main. The failures that exist on main (OOM from a shared GPU, no Rust workspace in the test copy) show the same errors on both.

## Cost

The gate is conservative: a request reusing an **unrelated** device prefix also waits for the newest load-back. Extra latency for an unrelated 8K-token prefix hit arriving 20 ms into a 24K-token load-back (median; alone it takes 0.088 s):

| Timing | main | this PR |
|---|---|---|
| Host-staged KV transfer (mooncake TCP) | +0.140 s | +0.178 s |
| Delayed H2D (≈ GPUDirect RDMA timing) | +0.046 s | **+0.664 s** |

- **Host-staged**: B's KV queues behind A's H2D on the copy engine anyway, so the gate adds only ~0.04 s.
- **GPUDirect RDMA**: B's KV skips the copy engine, so the gate can hold an unrelated request for up to one full load-back. We couldn't run real RDMA. The delayed-H2D row approximates it, because the sleep kernel delays the DMA without occupying the copy engine.
- Requests with no device prefix, or arriving with no load-back in flight, are never held.

## Possible follow-up

The gate can be narrowed to requests whose prefix overlaps an in-flight load-back, by comparing tokens past the loader's pre-load device prefix. This needs no device sync and no tree-core change. An early prototype brought the unrelated-prefix delay back to main's level. I've kept it out to keep this fix small, and can send it once this lands or if you'd like it here.

## Not covered

Tested with TP=1/PP=1, the Rust tree core, the `direct` IO backend and mooncake TCP only. Not run: NIXL, real GPUDirect RDMA, PP > 1, hybrid models on GPU (the state-only path is covered by the unit test only).
