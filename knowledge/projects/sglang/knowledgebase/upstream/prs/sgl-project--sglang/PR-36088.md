# [Fix] [AMD] distributed: Fix custom AR capture for DSA DP dual graphs

[Upstream PR](https://github.com/sgl-project/sglang/pull/36088) · state: open · merged: False

## Original PR description

## Motivation

Fixes #36071.

On ROCm, DSA with DP attention allows different DP lanes to replay different
decode graphs concurrently. Custom all-reduce direct graph-input registration
assumes something stronger: every rank in the communicator replays the same
captured graph and custom-AR call ordinal in lockstep.

During capture, each custom-AR call embeds a `RankData` slot. Registration then
fills that slot with peer pointers belonging to the same captured-call ordinal.
At replay there is no runtime graph-id handshake. If TP2 lane pairs select
different graphs, each pair reads graph-local buffers that are inactive on the
other ranks. The resulting all-reduce is incomplete and can turn GLM-5.2 logits
into NaN, followed by repeated token ID 0.

This supersedes the earlier shared-memory-pool address-collision hypothesis.
Instrumentation found no pointer-registration ordering, IPC-handle, offset, or
capture-to-registration drift.

## Modifications

- Use the communicator's stable pre-registered copy-in buffer during graph
  capture when DSA DP attention is enabled.
- Apply the policy to both AITER and legacy SGLang custom all-reduce.
- Preserve direct graph-input registration for non-DP DSA and other attention
  backends.
- Add unit coverage for the graph-capture policy.

This retains custom-AR itself. Only its graph input staging changes.

## Minimal causal proof

Hardware: 8 x AMD MI350X, ROCm 7.2.4, AITER
`c16d44b93a528b2a4bfd6d8d3409116d465872a9`.

A standalone distributed reproducer captures four same-shape BF16 graphs. Each
graph contributes a distinct constant, making stale peer-buffer selection
numerically observable.

| Input registration | Replay pattern | Failed rank-results | Result |
|---|---|---:|---|
| direct | all eight ranks replay the same graph | 0/32 | exact |
| direct | DP4/TP2 skew: rank pairs replay g0/g1/g2/g3 | 8/8 | incorrect |
| copy-in | the same DP4/TP2 skew | 0/8 | exact |

The expected skewed global sum is BF16 `2080` on every rank. Direct mode
returns `206`, `414`, `624`, and `832` for the four rank pairs. These are
exactly the contributions from each active TP2 pair, proving that the other
graphs' peer buffers were not supplying the current inputs. Copy-in returns
`2080` on all eight ranks.

A stronger release/acquire system-scope barrier did not help (8/8 full-model
requests still corrupt), excluding a simple memory-visibility issue.

## Full-model accuracy tests

Model/configuration: GLM-5.2-MXFP4, BF16 KV, TP8/DP4/EP8 with DP attention,
TileLang DSA prefill/decode, full decode graphs.

| Graph collective | Result |
|---|---:|
| AITER custom AR, direct registration | 4/4 hard corrupt |
| SGLang custom AR, direct registration | 4/4 hard corrupt |
| Plain NCCL | 0/4 hard corrupt |
| AITER custom AR, copy-in | 0/4 hard corrupt |

Extended copy-in soak:

- no MTP: sequential 32/32 clean; concurrent c8 x 4 OSL64 32/32 clean;
- AITER prefill + TileLang decode + MTP + overlap: sequential 32/32 clean;
  concurrent c8 x 4 OSL64 32/32 clean;
- six policy/dispatch unit tests pass in the ROCm image.

## Performance

Three matching rounds with AITER prefill + MTP, c4, 4,096 cached + 1,024
fresh, OSL512:

| Capture input path | Mean TPOT | Mean token/s/user |
|---|---:|---:|
| direct registration | 11.753 ms | 85.14 |
| copy-in | 11.889 ms | 84.80 |

Observed throughput delta: **-0.40%**, within run-to-run variance from MTP
acceptance length.

## Design scope

The patch is the smallest safe production fix. A zero-copy replacement would
require a new runtime protocol that advertises each rank's active graph slot,
or allocator integration that makes every graph produce directly into one
stable registered address. Static same-ordinal peer registration cannot safely
support independently selected graphs.
