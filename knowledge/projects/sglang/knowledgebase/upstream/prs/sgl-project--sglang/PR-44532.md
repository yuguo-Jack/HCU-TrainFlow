# [Feat] sglang-server: serve /v1/loads from the Rust frontend

[Upstream PR](https://github.com/sgl-project/sglang/pull/44532) · state: closed · merged: True

## Original PR description

## Motivation

The Rust frontend had no `/v1/loads`, so anything that polls per-rank load from the Python server (running and waiting requests, token usage, cache hit rate, the memory/spec/lora/disagg/queues sections, as JSON or Prometheus text) got a 404 from a Rust listener.

## Modifications

- `rust/sglang-server/src/api_server/http/loads.rs`: `GET /v1/loads`. Each scheduler already publishes its load snapshot into a shared-memory file (`managers/load_snapshot.py`, `ShmLoadSnapshotWriter`). The route reads this listener's slot of that file under the same shared lock Python's reader takes, decodes the msgpack payload, and renders `LoadSnapshot.to_dict` as JSON or Prometheus text with the same `include`, `dp_rank` and `format` query parameters as the Python route. A Rust listener fronts only its own scheduler, so it reports itself as a single-rank engine: its own slot, as rank 0. When snapshots travel over ZMQ instead of shared memory (multi-node DP) there is no file to read and the route answers 503.
- `message/config.rs` / `rust_server/config.py`: the typed `ServerArgs` carries the snapshot path, DP size and this rank, plus the accelerator name and per-rank count that the endpoint reports.
- `chrono` (already in the tree via `dynamo-renderer`) for the envelope timestamp.
- `rust/sglang-server/testdata/load_snapshot.json`: two wire payloads and what Python renders from them. `test_load_snapshot_backends.py` rebuilds the fixture and asserts it is current; the Rust unit test asserts the Rust renderer produces the same output from the same bytes, key order and float formatting included, so the two renderers cannot drift apart silently.
