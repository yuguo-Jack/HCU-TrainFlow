# [Perf] dsa: Run the packed prefill top-k on CUDA

[Upstream PR](https://github.com/sgl-project/sglang/pull/45891) · state: open · merged: False

## Original PR description

[by Claude Code]

## Motivation

DSA prefill (GLM-5.x, DeepSeek-V3.2) on CUDA ranks each row's indexer logits with the legacy sgl-kernel
`fast_topk_transform_fused` (`topk_transform_prefill_kernel`). That kernel runs one CTA per row. On long contexts it
becomes a large part of prefill:
- **GB300, GLM-5.2 prefill worker** (InferenceX AgentX flags, DP attention 4; 16K-token turns on a cached prefix):
  15% of a step at 128K cached prefix and 29% at 384K. The profile and its repro are under Speed Tests.
- **VR200, GLM-5.3 TP4 AgentX run** (a profiled window): the top-k takes 2.3x the GPU time of the indexer logits
  kernel whose scores it ranks.

SGLang's top-k v2 already has a faster packed (DSA extend) entry, `topk_packed_kernel`. It fuses the top-k with the
page-table output, but it was compiled for ROCm only. Its own comment says "Nothing below is AMD-specific; the guard
can be dropped later." This PR drops the guard and routes CUDA's paged prefill to it.

**Impact**

- **Accuracy:** GB300, GLM-5.2-NVFP4 TP4, main → this PR: GSM8K 97.50% → 98.00% (300 x 2 passes), RULER2 32K 93.07%
  → 94.20% (150 x 5 passes), both within the 95% paired interval. The top-k output is exact against `torch.topk` in every check.
  The HiSparse PD and DCP2 GLM CI tests, whose prefill now takes the packed kernel, pass on B200.
- **Performance:** GB300 GLM-5.2 NVFP4 prefill workers, new-token throughput +1.5% (cold 32K) to +43% (16K-token turn
  on a 384K cached prefix) on the cookbook PP4 worker, +1.8% to +33% on the AgentX DP-attention worker. Top-k per
  call 0.51x on B200. Decode is untouched.

## Modifications

**+12 / −20 runtime code (4 files), +305 / −12 tests (3 files), +118 benchmark (1 file).** The packed kernel
itself is unchanged; this PR removes its ROCm-only guard and routes CUDA to it.

- **`kernels/jit/csrc/deepseek_v4/topk_v2.cuh`:** remove the two `USE_ROCM` guards around `TopKPackedParams` /
  `topk_packed_kernel` and the host `transform_packed`. The file's other `USE_ROCM` blocks are AMD-specific and stay.
- **`kernels/ops/attention/dsv4/topk.py`:** always register the `topk_transform_packed` wrapper, and drop the ROCm-only
  assert.
- **`layers/attention/dsa/dsa_topk_backend.py`:** the PAGED extend dispatch takes the packed kernel on CUDA too,
  except for a prefill context-parallel (CP) shard on CUDA (next bullet). On ROCm the dispatch is main's.
- **`layers/attention/dsa_backend.py`:** new `DSAMetadata.prefill_cp_sharded`, set by `init_forward_metadata` when
  interleaved prefill CP leaves this rank only its shard of the batch's tokens. On CUDA the packed dispatch declines
  such a batch, so CUDA prefill CP keeps the legacy kernel, as on main: no test has run a CP shard's rows through the
  packed kernel. ROCm ignores the flag and keeps main's packed routing.
- **`test/registered/kernels/ops/attention/test_topk_v2.py`:** the two packed-layout tests (12 cases) now run on CUDA,
  pinned exact (`max_permit_error=0`). ROCm keeps the file's default tolerance.
- **`test/registered/kernels/ops/attention/test_dsa_indexer.py`:** new `test_packed_paged_extend_dispatch`. It packs
  two requests on one key axis: page size 64, a permuted page table, the second request at unaligned column 3203,
  and row windows that reach the kernel's trivial, Register2, Register4 and Streaming paths. A whole-forward call and
  an indexer row chunk that crosses the request boundary must run the packed kernel, and every output must equal
  legacy's selection and `torch.topk`'s value multiset exactly. It fails on main, where both calls run legacy, and
  catches a wrong page size or a wrong row-to-request map. A prefill-CP shard (rank 1 of CP2) must stay on legacy
  for both calls and still match `torch.topk` exactly.
- **`test/registered/unit/mem_cache/test_page_sharded_dsa_attention.py`:** new CPU test
  `test_prefill_cp_shard_keeps_the_legacy_topk`. It builds the metadata with the real `init_forward_metadata` for two
  requests, once as rank 1 of CP2 and once unsharded: on CUDA the CP shard must call the legacy kernel and the
  unsharded batch the packed one; on ROCm both must call the packed one, as on main. It fails if the dispatch
  drops the check on CUDA or applies it on ROCm, or if the flag is never or always set.
- **`test/registered/kernels/benchmark/attention/bench_topk.py`:** a packed prefill case, `benchmark_packed`: legacy
  `fast_topk_transform_fused` vs the packed v2 kernel on GLM-shaped rows (one request, or three at unaligned bases).
  Both providers write into one poisoned output that is checked exactly against `torch.topk` before timing.

Who gets it: GLM-5.x and DeepSeek-V3.2, whenever the prefill top-k transform is PAGED. That is the case with the
trtllm prefill backend and an fp8 KV cache, the Blackwell default (`DSAAttnBackend.get_topk_transform_method`).
DeepSeek-V4 / V4.1 already run v2 in prefill and are unaffected. There is no new flag. When a shape condition does not
hold, the call falls back to the legacy kernel as before: fp32 logits, unit column stride, row stride a multiple of 4,
`0 < topk <= 2048`, `row_starts` given, and a row-to-request map available. On CUDA, prefill CP stays on legacy: a
CP-sharded batch is excluded explicitly (`DSAMetadata.prefill_cp_sharded`). ROCm's dispatch is main's, unchanged.

## Accuracy Tests

The kernel computes the same top-k as legacy. Every kernel check in the first table is exact: value multisets equal `torch.topk`
bitwise, selected positions lie in the row's window and are unique, pads are trailing `-1`, and the page-table output
inverts per row.

  spread as widely as the two arms differ.
- Almost every RULER2 miss is an output cut at the 8,192-token cap. Over 5 passes, 50 of main's 52 imperfect
  samples and 41 of this PR's 45 were cut, and no cut sample scored (50 vs 41 cut: one-sided Fisher p = 0.19). On the

- Route check: a GPU trace of one 28.6K-token prompt (4 prefill chunks x 22 indexer layers x 4 ranks = 352 calls)

## Speed Tests and Profiling

This PR changes prefill only (decode and verify keep the v2 decode top-k), and the legacy top-k's cost grows with each
row's key window, so the end-to-end runs measure GB300 disaggregated prefill workers at long cached prefixes, where
that cost sits. They are static workloads (fixed prompt and cached-prefix lengths): the top-k cost depends on row
windows and batch shape, not on the request mix, so fixed shapes isolate it.

**Per call** (top-k alone, CUDA graphs, outputs checked before timing; geomean over 31 GLM-shaped cells, K = 2048):

| GPU | packed / legacy |
|---|---|
| B200 | 0.51 |
| GB300, in a live AgentX run (same logits work in both arms) | 0.28 |

The packed case is in the tree: `python3 test/registered/kernels/benchmark/attention/bench_topk.py` (CI runs one
cell, 1,024 rows at a 32K mean window).

**End to end, GLM-5.2 NVFP4 prefill worker on GB300** (one node; InferenceX GB300 AgentX prefill worker flags: DP
attention 4, EP 4, 16,384 tokens per DP rank per step, HiCache, EAGLE; arms legacy, packed, legacy, packed, each on a
fresh server). New-token throughput, packed / legacy:

| workload | cold 32K | cold 128K | 16K-token turn on 32K cached | on 128K cached | on 384K cached |
|---|---:|---:|---:|---:|---:|
| client view, pair 1 / pair 2 | 1.018 / 1.018 | 1.061 / 1.043 | 1.034 / 1.033 | 1.140 / 1.139 | 1.333 / 1.335 |

- Same-arm drift between the two pairs is 0.1-0.2% except one cold-128K pass (1.8%).
- At 384K, compute per step drops by 628 ms. The top-k takes 523 ms less, and the page-table gathers go away: when the
  indexer splits the logits into row chunks, only the legacy path builds each chunk's page table with gathers (354
  launches and 128 ms per step, against 0.1 ms on the packed path). All other kernels together (logits, sparse MLA
  and the rest) take 22 ms more in the packed profile (table below).
- After this change the top-k is 1.6% / 4.7% / 9.7% of a step at 32K / 128K / 384K.

**Profile of this worker** (the source of the Motivation's 15% and 29%). GPU kernel time per 16,384-token step, mean
of the 4 DP ranks, first legacy/packed pair (the second pair's shares agree within 0.1 point):

| kernel | 128K legacy | 128K packed | 384K legacy | 384K packed |
|---|---:|---:|---:|---:|
| prefill top-k: `topk_transform_prefill_kernel` (legacy), `topk_packed_kernel` | 234 ms (15.3%) | 64 ms (4.7%) | 698 ms (28.9%) | 175 ms (9.7%) |
| indexer logits, `deep_gemm::sm100_mqa_logits` | 152 ms (9.9%) | 153 ms (11.1%) | 441 ms (18.3%) | 444 ms (24.7%) |
| gathers, `at::native::vectorized_gather_kernel` (at 384K: legacy's per-chunk page tables) | 0.1 ms | 0.1 ms | 128 ms (5.3%) | 0.1 ms |
| sparse MLA attention, `fmhaSm100fKernel_…TokenSparse…` | 236 ms (15.4%) | 238 ms (17.4%) | 237 ms (9.8%) | 245 ms (13.7%) |
| all other kernels (MoE, GEMMs, norms, ...) | 682 ms | 683 ms | 683 ms | 694 ms |
| collectives (NCCL transfer) | 231 ms | 231 ms | 231 ms | 239 ms |
| **step** | **1,535 ms** | **1,369 ms** | **2,418 ms** | **1,797 ms** |

- A step is one rank's non-NCCL kernel time plus the collectives' transfer, with each collective counted at its
  shortest duration over the 4 ranks. That leaves out the time a rank waits for a rank that started later, so it is
  the step of a worker whose ranks are all busy. A share is the kernel's summed time over that step.
- Both arms ran one tree: upstream main `ed8c3139f` (2026-10-15) plus this PR's change behind a temporary
  environment toggle. With the toggle off, the code path is main's. The tree also carried two default-off
  experiments for the decode top-k; both were off in both arms.

Load, for each cached-prefix length P (131,072 and 393,216):
- Each DP rank has its own prefix of seeded random token ids (uniform in [1000, 100000)). Flush the cache, then send
  each rank its P-token prefix once so that it is cached.
- A turn is that prefix plus 16,320 fresh ids. With EAGLE the radix cache matches P − 64 of the prefix tokens, so a
  turn prefills exactly 16,384 tokens: one step at `--max-prefill-tokens 16384`.
- Every request is pinned to its rank (`routed_dp_rank`) and asks for one token. Each rank keeps 2 turns in flight.
  After 36 warm-up turns per rank, profile a pass of 4 turns per rank:

`share.py` (the request count cancels in the ratio):

```python
import glob, gzip, json, statistics as st, sys
R = []
for f in sorted(glob.glob(sys.argv[1] + "/*.trace.json.gz")):  # one trace per DP rank
    k = sorted((e for e in json.load(gzip.open(f))["traceEvents"] if e.get("cat") == "kernel"), key=lambda e: e["ts"])
    nccl = [e["dur"] for e in k if "nccl" in e["name"].lower()]
    R.append(dict(nccl=nccl, compute=sum(e["dur"] for e in k) - sum(nccl),
                  topk=sum(e["dur"] for e in k if "topk_transform_prefill_kernel" in e["name"])))
transfer = sum(min(r["nccl"][i] for r in R) for i in range(min(len(r["nccl"]) for r in R)))
step = st.mean(r["compute"] for r in R) + transfer
print(f"legacy top-k: {st.mean(r['topk'] for r in R) / step:.1%} of a step")
```

It prints 15.3% at P = 131,072 and 28.9% at P = 393,216 on the legacy arm's profiles (4.5% at 32,768).

**Issue**

Dropping `_is_hip` here also moves prefill context parallel (CP) to the packed kernel on CUDA. The PR body says "The prefill context-parallel path stays on legacy", and the `else` comment at line 161 says the same. But no caller passes a Python list as `batch_idx_list`. Interleave CP calls `metadata.topk_transform(logits, ks=ks)` with `batch_idx_list=None`, so `row_to_batch` is the CP-sharded `token_to_batch_idx`.

**Why it matters**

The row-to-request map looks consistent to me, but reviewers will treat CP as untouched. The only DSA CP test, `test/registered/cp/test_dsa_prefill_cp.py`, runs in `extra-b`, not in base CI.

**Fix**

Fix the PR body and the line 161 comment, or drop the dead `else` branch. Run `test_dsa_prefill_cp.py` once (8x H200), or exclude CP explicitly.

- akhilg-nv · comment · 2026-10-27T13:59:10Z · [source](https://github.com/sgl-project/sglang/pull/45891#discussion_r4389571395)

File: `python/sglang/srt/layers/attention/dsa/dsa_topk_backend.py` · line 169

[by Claude Code] Agreed: the interleaved CP call passes `batch_idx_list=None` with the CP-sharded `token_to_batch_idx`, so this PR did send prefill CP to the packed kernel. Nothing has run that layout through the packed kernel, so 1eb13cb74 excludes CP explicitly: `init_forward_metadata` marks a CP-sharded batch (`DSAMetadata.prefill_cp_sharded`) and the packed branch declines it. CP therefore runs the same top-k as on main, and the description and the dispatch comment are now accurate. The `else` branch stays as a fallback (a Python list goes to legacy), and its comment no longer mentions CP.

Tests: `test_packed_paged_extend_dispatch` now requires a CP2 shard's whole-forward call and row chunk to run legacy and match `torch.topk` exactly. A new CPU test, `test_prefill_cp_shard_keeps_the_legacy_topk`, builds the metadata through `init_forward_metadata` and checks CP -> legacy and unsharded -> packed. Both fail if the dispatch ignores the check; the CPU test also fails if the metadata never or always sets the flag.
