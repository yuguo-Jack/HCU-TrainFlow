# [Fix] beam-search: Correct mixed-width admission and reduce decode overhead

[Upstream PR](https://github.com/sgl-project/sglang/pull/46371) · state: open · merged: False

## Original PR description

## Motivation

Mixed beam widths need admission accounting in physical request-pool rows. The current gate divides the remaining rows by the incoming candidate's width, then compares that value with the number of staged leaders. With a four-row pool, `[4, 1]` can therefore admit five rows and fail when the beam spawns. Conversely, an eight-row pool can reject the final group in `[2, 1, 4]` even though all seven rows fit.

A stop token selected on the final allowed beam step also loses its stop reason, causing it to be reported as length-finished and retained in decoded text.

## Modifications

- Charge the actual pending member rows of staged beam groups and the incoming candidate, preserving held leader rows, running-group reservations, and the pipeline microbatch limit.
- Preserve each final candidate's matched stop token, including the length-cap path.
- Supply the already-known beam-tail size to `repeat_interleave`, remove redundant copies after advanced indexing, and pass `assume_unique=True` after orphan-GC inputs have already been deduplicated.
- Add scheduler, stop/decode, snapshot-isolation, tail-layout, and fork/GC regression coverage, plus a registered real-model GPU test for a four-row pool with overlap off/on.
- Add a reproducible service benchmark client and [measurement methodology, per-round A100 results, BF16 boundary, and latency tradeoff](https://github.com/davidliuk/sglang/blob/dbd094555a01d1cc2dcc3c814a6c9aac8cd407bc/test/manual/beam_search/README.md).

## Speed Tests and Profiling

Historical single A100-SXM4-40GB, pinned Qwen2.5-0.5B-Instruct, BF16/TP1, FlashInfer, decode CUDA graphs on, prefill graphs off, Python TreeCore fallback. Each cell is the median of six measured rounds from two fresh server launches; 64 fixed output tokens per returned beam, all beams returned. These measurements predate the rebase; see the README and 48 per-round records for exact versions, flags, counting and timing boundaries.

| Scheduler | Workload | Returned tokens/s, base → PR | Change | p50 seconds, base → PR | p95 seconds, base → PR |
| --- | --- | --- | --- | --- | --- |
| Sync | 8 requests, width 4 | 1444.8 → 1550.7 | +7.3% | 1.415 → 1.318 | 1.416 → 1.319 |
| Sync | 16 requests, widths 1/2/4/8 | 1636.5 → 2085.5 | +27.4% | 1.458 → 1.836 | 2.342 → 1.837 |
| Overlap | 8 requests, width 4 | 1364.5 → 1495.0 | +9.6% | 1.499 → 1.368 | 1.500 → 1.368 |
| Overlap | 16 requests, widths 1/2/4/8 | 1557.6 → 1999.9 | +28.4% | 1.518 → 1.916 | 2.463 → 1.917 |

**Tradeoff:** mixed-width admission increases concurrency; throughput and this workload's p95 improve, but p50 worsens by about 26%. The mixed gain includes changed batching and is not a pure kernel speedup or a universal latency improvement. The sample is not a sustained-load latency study. Separately measured deterministic raw-text workloads improved +6.0% sync / +3.2% overlap; their different workload/configuration prevents estimating deterministic-mode overhead from the table above.
