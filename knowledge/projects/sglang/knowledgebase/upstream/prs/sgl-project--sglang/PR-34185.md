# Drop requests that are already too stale during a weight-update pause

[Upstream PR](https://github.com/sgl-project/sglang/pull/34185) · state: open · merged: False

## Original PR description

> **Draft.** Verified with unit tests only; the end-to-end runs are on a fork of this branch
> and not included here. Based on `sglang-miles`, the branch our training images build from.

## Motivation

In async RL the weight update pauses generation, and `mode="retract"` sends every in-flight
request back to the waiting queue to be **re-prefilled** on resume. A request that started
under weights already too old to train on therefore pays a full recompute of its context
only to be discarded afterwards.

Nothing outside the pause can prevent that: by the time generation resumes, the recompute
has already begun. So the selection has to happen while the engine is paused.

```
POST /pause_generation {"mode": "retract", "abort_below_start_weight_version": 7}
```

`mode` keeps deciding what happens to the survivors; the threshold only decides who
survives. `mode="abort"` rejects it rather than ignoring it — that mode aborts everything
already, so a filter there could only mislead.

## Why the caller declares the version

The obvious alternative — capture the server's own `ServerArgs.weight_version` when a
request is admitted — does not work, because that label is published only *after* an update
finishes:

```
trainer: weight_version += 1
         pause engines                   <- engines still report the OLD label
         transfer weights                <- engines now HOLD the new weights
         engine.update_weight_version()  <- label finally updated
         continue generation
```

For the whole duration of a transfer the engine reports `N-1` while already holding version
`N` weights. That window is not small: on our cluster a pure weight update measures ~8s for
a 30B model and ~49s for a 235B model, and requests do arrive during it. The label is also a
free-form string, so ordering it would compare `"10" < "9"`.

The rollout controller does know which weights it dispatched under, so
`GenerateReqInput.start_weight_version` is caller-declared and monotonic (`int`), and the
server only stores, echoes and filters on it — never derives or validates it. This mirrors
`priority`, likewise a caller-supplied ordinal the scheduler acts on.

It is also on `ChatCompletionRequest` / `CompletionRequest`: when an external agent driver
issues the completions itself it talks to the OpenAI-compatible endpoints, and a proxy in
front of them is what stamps the version. Dropping it there would be silent, because an
undeclared version is deliberately never selected. Not added to the Responses API, which
threads `priority` through a helper that decrements it per tool call and so needs its own
decision about whether the version stays fixed across a chain.

`meta_info["start_weight_version"]` echoes it back when declared and is omitted otherwise,
so existing responses are unchanged. `meta_info["weight_version"]` is untouched: it reports
the version a response was *emitted* under, which together with the echoed start version
gives the caller the span a long request generated across.

## Selection and termination

One predicate, `_is_stale_start_version`, shared by both pause modes. A request that
declared no version is never selected — an unknown version cannot be evaluated, and guessing
is worse than keeping the request.

Termination differs by mode, deliberately:

- **`retract`** splits where retracted requests are re-queued. `retract_all` has just
  released their KV, so finishing one there is only the echo the waiting-queue abort path
  already sends. Routing it through `abort_request` instead would mark `to_finish` and then
  wait for a forward pass a paused engine never runs, leaving the KV of already-doomed
  requests allocated for the whole weight update.
- **`in_place`** retracts nothing and so has no such split point; the stale requests are
  marked `to_finish` on the in-flight batches — the same route `abort_request` takes for a
  running request — and the first forward pass after `continue_generation` finalizes them.

`Req`'s rebootstrap payload carries the label so a PD-retracted request keeps the version it
was originally dispatched under.

## Tests

`test/registered/unit/managers/test_pause_abort_stale_start_version.py`: the predicate truth
table (strictly-below, undeclared never selected, no threshold selects nothing), the mode
validation, and the in_place sweep marking only stale unfinished requests.
