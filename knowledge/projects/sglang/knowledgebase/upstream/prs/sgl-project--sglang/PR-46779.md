# [Fix] [AMD] model-loader: register full allocations for remote weight loading

[Upstream PR](https://github.com/sgl-project/sglang/pull/46779) · state: open · merged: False

## Original PR description

## Motivation

On ROCm, remote weight loading can register a weight block that starts inside a larger allocator segment. Older Mooncake HIP IPC implementations map the allocation base but publish the registered block address, causing reads to use the wrong offset while the transfer itself may report success. This matches the class of corruption reported in [Mooncake #3546](https://github.com/kvcache-ai/Mooncake/issues/3546).

## Modifications

- Register each native ROCm allocator segment containing model weights once, using its allocation base and full size.
- Keep per-tensor transfer addresses and sizes intact.
- Preserve existing block registration for CUDA and expandable VMM segments.

## Accuracy Tests

- Added seven CPU registration-boundary regression tests: two fail before the change; all seven pass afterward, with two additional passing subtests.
- The local CPU runner exercises the real registration helper with real PyTorch parameter pointers and mocked GPU allocator snapshots/registration calls. It bypasses optional serving imports and does not exercise HIP IPC.
- Touched-file pre-commit checks pass.

Could a maintainer enable community CI, especially the AMD remote weight-loading tests? Please validate the original Llama `transfer_engine` scenarios in both Engine and Server mode on the AMD CI image, keeping the backend fixed so a random retry cannot substitute NCCL. A before/after HIP IPC suballocation reproducer would help confirm the reported corruption is resolved. AMD GPU validation is requested through community CI.

## Speed Tests and Profiling

This change affects registration ranges during model startup. No inference speed improvement is claimed. Registering full ROCm allocations can increase the registered byte range.
