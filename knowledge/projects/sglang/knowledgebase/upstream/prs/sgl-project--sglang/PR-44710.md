# [CI] 5090: Cut the install's disk footprint and guard against full disks

[Upstream PR](https://github.com/sgl-project/sglang/pull/44710) · state: closed · merged: False

## Original PR description

[by Claude Code]

## Motivation

Since 2026-10-15, `1-gpu-5090` jobs have been failing with `No space left on device (os error 28)` (#44479). The pool moved to new vast.ai hosts that start with empty caches and small disks; #44383 says the trial machines have 32 GB. On these hosts, a few jobs are enough to fill the disk:

- `UV_LINK_MODE=copy` keeps three full copies of the CUDA torch stack:
  - the uv cache;
  - the kept venv `/opt/sglang-ci-py3.12`;
  - the build environment for the editable sglang install, which needs torch because it is in `[build-system].requires`.
- Nothing evicts Hugging Face checkpoints. For example, base-b 1-gpu-small loads `meta-llama/Llama-3.1-8B-Instruct`, about 16 GB.
- The 5090 diffusion canary's `minimax_h3_t2va_consumer_budget_1gpu_5090` case downloads the 134 GiB MiniMax-H3 `FL2VA` variant on any host that doesn't have it cached.
- When the disk fills, the failure shows up deep inside uv, and nothing in the log says how much space was free.

This PR shrinks the install's footprint and makes 5090 hosts either free space or fail with a clear error. It does not remove the need to give these hosts enough disk.

## Modifications

1. **Hardlink instead of copy.** `scripts/ci/cuda/ci_install_dependency.sh` now sets `UV_LINK_MODE=hardlink` instead of `copy`. The venv and the build environment hardlink files from the uv cache, so the CUDA stack is stored once. When the cache and the venv are on different filesystems, uv falls back to copying and prints a warning; I checked both cases with uv 0.8.15. Hardlinks would let an in-place edit of an installed file change the cache too, but I found no CI step that edits installed files in place.
2. **New `scripts/ci/cuda/ensure_disk_headroom.sh`, run as the first install step.**
   - **Every CUDA runner:** print free space for the filesystems holding `/opt`, the uv cache, and the HF cache. When the lowest is below 40 GiB, run `uv cache prune`, capped at 5 minutes; it removes only entries nothing references.
   - **`SGLANG_CI_DISK_GUARD=strict`:** additionally:
     - evict least-recently-used HF repos until 40 GiB is free, skipping any repo used in the last 2 hours;
     - print the largest cache directories;
     - fail with an `::error::` if less than 10 GiB is still free.
   - **Where strict is set:** only for jobs whose `runs-on` is `1-gpu-5090`, in `_pr-test-stage.yml`, `pr-test-jit-kernel.yml`, `pr-test-multimodal-gen.yml`, `rerun-test.yml`, and `diffusion-ci-gt-gen.yml`. These hosts keep the HF cache on their own disk. On a cache volume shared by many hosts, eviction only moves the failure to the next job; `scripts/ci/amd/check_hf_cache_space.sh` documents this.
3. **New `scripts/ci/utils/evict_hf_cache.py`,** which uses only the standard library because it runs before the venv exists, plus a unit test, `test_evict_hf_cache.py`.
4. **Remove `minimax_h3_t2va_consumer_budget_1gpu_5090` from the per-PR 5090 canary** (the case and its 5090 perf baseline).
   - Per-PR CI no longer covers H3's constrained-placement path.
   - `flux_image_t2i_layerwise_cpu_offload_5090` still covers layerwise offload, with a small model.
   - The case can come back on a lane whose hosts have the checkpoint pre-cached.

Not changed: `ci_cleanup_venv.sh` still runs `uv cache prune --ci` when the disk is at least 85% full. With hardlinks, that frees less space, because entries also linked into the venv stay on disk, and later installs re-download what it removed. It is worth revisiting once the hosts have enough disk.

## Testing

- `python -m unittest discover -s scripts/ci/utils -p 'test_evict_hf_cache.py'`: both tests pass. Each one fails when I break the logic it guards (eviction order reversed, or the 2-hour window ignored).
- I ran `ensure_disk_headroom.sh` with the thresholds raised, against a temporary HF cache:
  - **Report mode:** exits 0.
  - **Strict mode:** evicts only the idle repo, keeps the recent one, and exits 1 with the error.
- uv 0.8.15 hardlinks on the same filesystem (the venv file and the cache file share an inode) and falls back to copying across filesystems.
- `pre-commit run --all-files` passes.
- Not yet run on a 5090 runner, and CI has not been triggered.
