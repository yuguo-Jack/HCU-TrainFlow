# [Perf] [NVIDIA] speculative: Move the host work between Qwen3.5 MTP decode graphs into the graphs (1/2)

[Upstream PR](https://github.com/sgl-project/sglang/pull/45474) · state: closed · merged: True

## Original PR description

## Motivation

Qwen3.5-397B-A17B (NVFP4) low-latency decode on GB300, TP8, MTP (top-k 1, 7 draft tokens). With the NVIDIA megakernel plugin, the GPU part of a decode round gets short enough that SGLang's host work becomes the bottleneck: input staging between graphs, the verify's eager sampling and commits, and the scheduler's per-pass TP syncs. This PR moves that work into CUDA graphs, into fewer launches, or off the critical path. It is the Qwen3.5 counterpart of sgl-project/sglang#45450.

This PR contains no megakernel code. It is independent of the wiring PR, sgl-project/sglang#45266: both are based on main, and either can merge first. The plugin is sgl-project/sgl-nvidia-mega#20.

Every new code path is behind an environment switch that defaults to off. With all switches off, the same GPU operations run in the same order as on main; the accuracy tests below check this. Note that main's Qwen3.5 AgentX recipes (`docs/src/snippets/agentx/Qwen/qwen3.5.jsx`) already set six of these switches to `1`.

## Modifications

One commit per change. The TPS/User figures are what removing that change alone would cost on the full stack (this PR + #45266 + plugin, TP8, one request, 128K) ¹.

1. **Post-verify CUDA graphs** (`SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH`, ≈ 78 TPS/User): the EAGLE verify's sampling, acceptance and commit outputs replay as CUDA graphs, and the mamba state commit runs on a side stream. Batches a graph cannot reproduce (grammar, penalties, per-request seeds, ...) keep the eager path.
2. **Test:** the post-verify graphs match eager sampling bitwise at batch sizes up to 64.
3. **GDN extend kernels and tables for captured prefill buckets** (no switch; used by 4).
4. **GDN extend in breakable prefill graphs** (`SGLANG_ENABLE_GDN_PREFILL_GRAPH_EXTEND`): prefill no longer leaves the graph at every GDN layer. It does not affect decode; TTFT drops from 82.9 to 40.6 ms for 256-token prompts at TP4.
5. **`small_field_copy`** (`SGLANG_Q35MF_BK_VEC_COPY`, < 1 TPS/User): a JIT kernel that copies up to 16 small fields in one launch, with a 16-byte vectorized path. Item 6 uses it.
6. **Verify-round input staging** (`SGLANG_Q35MF_MKH_N3B`, `_N3C`, ≈ 19 TPS/User):
   - reuse the previous round's mamba track indices;
   - skip input copies that a pre-planned replay already made;
   - load the post-verify graphs' inputs in one launch.
7. **Chain-tree verify build and compact top-k sampling** (`SGLANG_Q35MF_EDGE_CHAIN_TREE`, `_SPARSE_VERIFY_SAMPLING`, ≈ 70 TPS/User):
   - a top-k 1 draft builds its verify chain without the tree mask, which TRT-LLM MHA does not read;
   - a verify whose requests all use a top-k of 2–128 samples on that support instead of the full vocabulary.
8. **Packed verify broadcast** (`SGLANG_Q35MF_EDGE_PACKED_VERIFY_BCAST`, ≈ 3 TPS/User): a sampled verify result reaches the TP group in one broadcast instead of three.
9. **Scheduler TP syncs through shared memory** (`SGLANG_Q35MF_EDGE_SHM_SYNC`, `_SHM_SYNC_MULTIHOST`, `_MULTIHOST_TCP`, ≈ 121 TPS/User): the request broadcast and the HiCache ready counts go through a shared-memory table instead of gloo. Across hosts, the counts use one exchange between the host leaders.
10. **Doc:** the `environ.py` section comment names SGLang branch `nvidia/qwen35-agentx-gb300`, which reads the same switch names.

¹ Measured on an earlier head of the full stack (1,267 TPS/User at P50). Items 1, 7 and 9 are derived from host-time and Kineto measurements rather than separate runs, so the rows do not add up. Four host-side items of earlier heads were dropped: together they gave ~1.3% for 1,204 production lines.

[by Claude Code] **Severity: perf | Confidence: Medium**

**Issue**

GDN sizes its static tables by the whole request pool, while KDA caps them at `SGLANG_KDA_PREFILL_GRAPH_MAX_SEQS=128`. So `max_chunks = cdiv(bucket, 64) + min(bucket, pool_size)`. `chunk_fwd_kernel_o` runs one program per row with no early return: each padded row still loads a full `h` block (only the store is masked). `chunk_gated_delta_rule_fwd_h` also allocates `h` for every row in each GDN layer.

**Example**

With a 1024-slot pool and a 2048-token bucket, `max_chunks` is 32 + 1024 = 1056. One 2048-token request has 32 real chunks, so the o-kernel does about 33 times the needed work on every replay.

**Fix**

Cap `prefill_graph_max_seqs` with an env var as KDA does, or return early in `chunk_fwd_kernel_o` for padded rows.
