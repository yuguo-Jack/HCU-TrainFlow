# [Benchmark] Add random audio dataset support

[Upstream PR](https://github.com/sgl-project/sglang/pull/48331) · state: open · merged: False

## Original PR description

## Summary

The benchmark client has no audio dataset at all, despite the serving stack
already supporting audio end-to-end: `GenerateReqInput` already has an
`audio_data` field, and the chat-completions protocol already defines both
`input_audio` and `audio_url` content
(`python/sglang/srt/entrypoints/openai/protocol.py` — `input_audio` is
normalized server-side into the canonical `audio_url` form via
`_to_audio_url_part`).

This PR adds an `audio` dataset type:

- A new `AudioDataset` dataclass in `python/sglang/benchmark/datasets/audio.py`
  generating synthetic random-sample audio clips (via `soundfile`, base64
  data-URI), matching the existing `{"type": "audio", "audio": ...}` content
  convention already used by `qwen_audio.py`'s processor for real audio-chat
  models.
- Audio tokens are counted locally via the real HF processor, same as the
  image/video datasets.
- Wired into `serving.py`: new flags `--audio-count`, `--audio-duration`,
  `--audio-channels`, `--random-audio-count`, `--audio-format`; extended
  `--dataset-name` choices; `_EMBEDDING_UNSUPPORTED_DATASETS` extended.

## Testing

Same test image/workflow as the companion video-dataset PR. Served
`Qwen/Qwen2-Audio-7B-Instruct` on a single MI355X GPU via a `gpuq`-gated job,
and ran:

```
python3 -m sglang.benchmark.serving --backend sglang-oai-chat \
    --dataset-name audio --num-prompts 4 --audio-count 1 \
    --audio-duration 3.0 ...
```

end-to-end against the real running server. Result: 4/4 successful requests,
full benchmark summary produced (throughput, TTFT, TPOT, ITL).
