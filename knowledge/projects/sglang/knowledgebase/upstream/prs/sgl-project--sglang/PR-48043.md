# [Perf] [AMD] qwen3: Fuse the 1x128 FP8 input quant into RMSNorm and SiLU-and-mul for block-FP8 linears on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/48043) · state: open · merged: False

## Original PR description

## Motivation

On gfx950 with aiter, block-FP8 dense linears run the bpreshuffle blockscale GEMM, which takes a 1x128 group-quantized FP8 input. In a Qwen3 decoder layer each such input is quantized by a separate kernel after the op that produces it: after the input RMSNorm (`qkv_proj`), after the post-attention RMSNorm (`gate_up_proj`) and after SiLU-and-mul (`down_proj`). Each quant reads back a bf16 tensor that was just written and adds a launch. Qwen3.5 already reads its attention input through the layer boundary's `NormQuantReadout` (aiter `fused_rms_fp8_group_quant`); Qwen3 does not.

## Modifications

- `models/qwen3.py`: in decode, the attention and FFN input norms request the fp8 quant format when the following linear runs the aiter bpreshuffle block-FP8 GEMM (`aiter_takes_fp8_group_input`), on gfx95 with aiter, and not under deterministic inference or an RL on-policy target. The FFN boundary declares `read=NORM_QUANT_READOUT`. The attention norm stays unfused when `post_residual_addition` is passed (Qwen3-VL deepstack), because the fused path does not apply it. The token count and the aiter fused KV-write dtype check accept the `(fp8, scale)` tuple.
- `layers/quantization/fp8_activation.py`: on the same gfx95 bpreshuffle path, `DenseSiluAndMulQuant` (used by the Qwen2, Qwen3 and Llama dense MLPs) runs SiLU-and-mul and the 1x128 quant in one kernel.
- New Triton kernel `kernels/ops/quantization/silu_mul_fp8_group_quant.py`. It rounds like `SiluAndMul` (silu to bf16, then the product to bf16) and quantizes like aiter's per-1x128 quant, so its output is identical to the unfused path.
- `layers/layer_boundary/stage.py`: docstring only.
- Tests: new `test/registered/kernels/ops/quantization/test_fused_norm_act_fp8_group_quant_gfx95.py` (`stage-b-test-1-gpu-small-amd-mi35x`); `test_boundary_output_contracts.py` gets the new `_quant_formats` hook on its layer stub.

## Accuracy Tests

MI355X (gfx950), image `lmsysorg/sglang-rocm:v0.5.22-rocm10-mi35x-20261025` (torch 2.11.0+rocm10, aiter `285579b6`), `SGLANG_USE_AITER=1`, Qwen3-14B-FP8, TP1.

**Kernel outputs.** The fused SiLU-and-mul quant equals the unfused path exactly (fp8 values and scales) for the Qwen3-14B and Qwen3-1.7B intermediate sizes at M = 1 to 512; the test asserts equality. The fused norm is aiter's `fused_rms_fp8_group_quant`, which quantizes the fp32 normalized value directly while the unfused path rounds it to bf16 first. On 112 batch sizes (M = 1 to 64, every CUDA-graph decode size up to 512, a few odd sizes) and on 1,600 real decode inputs dumped from the server, about 2.2% of the fp8 values differ by one e4m3 step, scales differ within the bf16 rounding of the group amax, and the residual output is identical. The test bounds this (at most one step, at most 5% of values).

**GSM8K** (`python -m sglang.test.few_shot_gsm8k --num-questions 1319`, greedy):

| Base | main | This PR | Questions main-only right / PR-only right (majority over runs) | McNemar exact p |
|---|---|---|---|---|
| `68e57f4005`, 12 runs each | 0.9012 | 0.8922 | 31 / 21 | 0.21 |
| `d74749b0b6`, 3 runs each | 0.9020 | 0.8910 | 32 / 19 | 0.09 |

Accuracies are the eval's own; the per-question outcomes are parsed from its dumped outputs. Runs of the same build differ only by nondeterminism, so the per-question test is the one that matters; neither difference is significant. The change in the norm path flips about 50 borderline questions, and which way the net goes is not tied to accuracy: a torch reimplementation of the same arithmetic as the aiter kernel (at most 0.04% of fp8 values differ from it) scored 0.9018 against main's 0.9012 on the same build (12 runs each), and the bf16-rounded variant of that reimplementation scored 0.9003. The SiLU-and-mul fusion alone (norm fusion disabled) scored 0.9012 against 0.9007.

**Distance to the BF16 model.** Teacher-forced on the gold answers of 400 GSM8K questions (48,692 tokens), compared with `Qwen/Qwen3-14B` (BF16). For this measurement the fused norm was also applied in prefill (an experiment-only switch; the PR fuses decode only).

| Qwen3-14B-FP8 | mean \|Δ logprob of gold token\| | KL over BF16 top-20 | top-1 agreement |
|---|---|---|---|
| main | 0.02928 | 0.00200 | 0.99127 |
| fused norm (aiter kernel) | 0.02871 | 0.00182 | 0.99179 |

The fused norm is not further from the BF16 model than main (the gap in |Δ logprob| is significant in its favor, 95% bootstrap interval over questions [0.00025, 0.00165]).

## Speed Tests and Profiling

`python -m sglang.bench_serving --backend sglang --dataset-name random-ids --random-input-len 1024 --random-output-len 1024 --random-range-ratio 1.0`, 80 prompts at concurrency 16 and 320 at concurrency 64, servers in the order main, PR, PR, main on one GPU with the node otherwise idle, 4 runs per server with the first dropped:

| Model, base | Concurrency | Output throughput (tok/s) main → PR | Median TPOT (ms) main → PR |
|---|---|---|---|
| Qwen3-14B-FP8, `68e57f4005` | 16 | 2035 → 2145 (+5.4%) | 7.57 → 7.18 (-5.1%) |
| Qwen3-14B-FP8, `68e57f4005` | 64 | 5608 → 5805 (+3.5%) | 10.61 → 10.23 (-3.6%) |
| Qwen3-14B-FP8, `d74749b0b6` | 16 | 2040 → 2149 (+5.3%) | 7.56 → 7.15 (-5.4%) |
| Qwen3-14B-FP8, `d74749b0b6` | 64 | 5647 → 5848 (+3.6%) | 10.57 → 10.13 (-4.2%) |
| Qwen3-1.7B-FP8, `68e57f4005` | 16 | 5469 → 5702 (+4.3%) | 2.85 → 2.73 (-4.2%) |
| Qwen3-1.7B-FP8, `68e57f4005` | 64 | 13412 → 14071 (+4.9%) | 4.59 → 4.36 (-5.0%) |

The two runs of each build agree within 0.4%. The SiLU-and-mul fusion alone gives +3.1% / +2.0% (concurrency 16 / 64) on Qwen3-14B-FP8.

A torch-profiler kernel census of eager decode on Qwen3-14B-FP8 shows `_fused_rms_fp8_group_quant_kernel` and `_silu_mul_fp8_group_quant_kernel` on this PR (2240 and 1120 calls in 30 steps, batch 8) and neither on main.

Scope: block-FP8 checkpoints in compressed-tensors format (for example the published Llama-3.1-8B and Qwen2.5 FP8-block ones) load through `CompressedTensorsLinearMethod` and do not take these paths (census on `RedHatAI/Llama-3.1-8B-Instruct-FP8-block`: no fused kernels). Llama/Qwen2 checkpoints in the native `fp8` format take the SiLU-and-mul fusion only, which is bit-exact; their speed was not measured.
