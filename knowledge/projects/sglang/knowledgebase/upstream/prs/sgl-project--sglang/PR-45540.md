# [Perf] [AMD] layernorm: Use torch rms_norm in the HIP fallback without vllm

[Upstream PR](https://github.com/sgl-project/sglang/pull/45540) · state: open · merged: False

## Original PR description

## Motivation

On HIP without AITER, `RMSNorm.forward_hip` uses vllm's RMSNorm kernels when vllm is installed and `forward_native` otherwise. AITER only supports CDNA, so on consumer RDNA GPUs (gfx11xx, gfx12xx) the native path is the one that runs. It is also the only one that works there today: the vllm branch has a call-signature bug that several open-then-closed PRs tried to fix (#31403, #21697, #41355, #31553), and none was merged.

`forward_native` writes RMSNorm as separate PyTorch ops, which launch **11 GPU kernels per call** (dtype casts, add, pow, mean, add-eps, rsqrt, two muls, cast back). At decode batch sizes each kernel processes a few KB, so the cost is launch and synchronization overhead, not math. With two norms per layer, that is roughly 700 kernels per token for a 32-layer model. #39725 noted the same cost ("a dozen pointwise kernels") on the batch-invariant path.

`torch.nn.functional.rms_norm` does the normalization in a single fused kernel; the residual add is one more. `forward_musa` already uses it.

## Modifications

`python/sglang/srt/layers/layernorm.py`, `RMSNorm.forward_hip`, only in the `not _has_vllm_rms_norm` branch:

- `_can_use_torch_rms_norm` decides whether torch's `rms_norm` reproduces `forward_native`'s semantics. It falls back to `forward_native` for `post_residual_addition`, `var_hidden_size`, `cast_x_before_out_mul`, `fp32_residual`, `override_orig_dtype`, a weight dtype different from the input's, and batch-invariant mode.
- `_forward_torch_rms_norm` does the residual add and calls `nn.functional.rms_norm`. Like `forward_native`, it does not fuse `quant_linear`.

Nothing changes for CUDA, AITER (CDNA), vllm-backed HIP, or any other platform.

**Overlap with #46915:** that PR (against `amd_march`) fixes the vllm branch's call signature in the same `RMSNorm.forward_hip`; this one changes only the no-vllm branch. They're complementary and don't conflict on `main`; a backport of this PR to `amd_march` would need a small rebase onto it.

The eligibility check runs per call rather than being cached in `__init__`, because `cast_x_before_out_mul` is changed after construction in at least one model (`multimodal_gen/.../ming_image.py`). Decode replays captured CUDA graphs, so the check runs only during graph capture and prefill.

**Numerics:** the residual output is bit-identical to `forward_native`. The normalized output is not: the add is rounded to bf16 once before normalizing, while `forward_native` normalizes the unrounded fp32 sum. On gfx1151 (bf16, hidden size 3072), cosine similarity vs `forward_native` is 0.999996, max abs diff 0.016-0.031.

**Tests:** `test/registered/unit/layers/test_layernorm.py` (CPU, `base-a-test-cpu`):

- `test_plain_case_avoids_forward_native_and_matches_it`: the plain case does not route to `forward_native` (a silent perf regression otherwise), matches it within bf16 tolerance, and returns a bit-identical residual.
- `test_modes_torch_rms_norm_cannot_express_keep_native_output`: for each of the 7 fallback conditions, `forward_hip` returns exactly `forward_native`'s output and dtypes.

To check the tests guard what they claim, each of 9 mutations was applied in turn and caught by the expected test: removing the fast path, dropping the residual add, and removing each of the 7 conditions.

## Accuracy Tests

Hardware and software for my results (the gfx1201 results under Speed Tests are @vivienfanghuagood's): Radeon 8060S (gfx1151, Strix Halo), torch 2.10.0+rocm7.13.0a20260513 (TheRock nightly), `--attention-backend triton --mem-fraction-static 0.5 --context-length 8192 --disable-overlap-schedule`. On `main`, `SGLANG_DISABLE_LEAN_ATTENTION=1` was also needed: the lean decode-attention kernel requests 66560 B of shared memory and RDNA allows 65536, which is a separate issue.

**On `main` (bd5a445bf7), Phi-4-mini-instruct**, `sgl-eval` 0.1.3 GSM8K, all 1319 questions, temperature 0, max tokens 1024, 32 threads. The baseline was run twice to measure run-to-run variation:

| Comparison | Accuracy | Questions that changed outcome | McNemar p |
|---|---|---|---|
| baseline vs baseline rerun (same code) | 89.39% vs 88.93% | 36 | 0.41 |
| this PR vs baseline | 88.63% vs 89.39% | 34 | 0.12 |
| this PR vs baseline rerun | 88.63% vs 88.93% | 38 | 0.63 |

Even with greedy decoding, unpatched `main` changes 36 answers between two runs (batch composition differs at 32 concurrent requests). This PR's difference from the baseline is within that variation.

**On the #31137 branch** (with #31246 and the #31143 HIP-compat change applied), `sglang.test.few_shot_gsm8k`, 200 questions, 5-shot, greedy. These were measured before `sgl-eval` became the recommended harness:

| Model | Baseline | This PR |
|---|---|---|
| Phi-4-mini-instruct | 83.0% | 83.0% |
| DeepSeek-V2-Lite-Chat | 55.0% | 56.5% |
| Llama-3.1-8B-Instruct | 76.5% | 75.5% |

gpt-oss-20b-bf16 was not scored: it is a reasoning model, and raw few-shot completion is not a valid check for it. A spot check with the chat template gave correct answers.

## Speed Tests and Profiling

`sglang.bench_serving --backend sglang --dataset-name random --random-input-len 1024 --random-output-len 256 --random-range-ratio 1`; 1-stream = 8 prompts at `--max-concurrency 1`, 8-way = 32 prompts at `--max-concurrency 8`. Same setup as the matrix in #31137.

**On `main` (bd5a445bf7), Phi-4-mini-instruct:**

| | Baseline | Baseline rerun | This PR | Change vs baseline mean |
|---|---|---|---|---|
| 1-stream output tok/s | 18.04 | 18.18 | **19.97** | **+10.3%** |
| 1-stream mean TPOT (ms) | 54.53 | 54.17 | **49.22** | -5.1 ms |
| 8-way output tok/s | 116.54 | 117.05 | **122.99** | **+5.3%** |
| 8-way mean TPOT (ms) | 62.03 | 61.88 | **58.94** | -3.0 ms |

**On the #31137 branch** (setup as above):

| Model | Arch | 1-stream tok/s | 8-way tok/s | TPOT saved (1-stream) |
|---|---|---|---|---|
| Phi-4-mini-instruct | dense | 18.43 -> 20.02 (+8.6%) | 118.8 -> 125.2 (+5.3%) | 4.6 ms |
| gpt-oss-20b-bf16 | MoE | 21.91 -> 24.11 (+10.0%) | 63.5 -> 65.0 (+2.2%) | 4.1 ms |
| DeepSeek-V2-Lite-Chat | MoE + MLA | 13.65 -> 14.66 (+7.4%) | 44.1 -> 45.5 (+3.0%) | 4.9 ms |
| Llama-3.1-8B-Instruct | dense | 10.03 -> 10.56 (+5.3%) | 66.1 -> 69.2 (+4.8%) | 4.9 ms |

Llama-3.1-8B could not be served on `main` on this machine, with or without this PR. `main`'s HIP RoPE path keeps `cos_sin_cache` in fp32, and the locally built `sgl_kernel` (from the #31137 branch) expects bf16. That's unrelated to this change.

**gfx1201 (RDNA4), measured independently by @vivienfanghuagood** ([comment](https://github.com/sgl-project/sglang/pull/45540#issuecomment-6495357147)). Stock `rocm/pytorch` image (torch 2.10, no vllm, no AITER), so RMSNorm takes exactly the branch this PR changes. Base: `main` + #43679 (gfx1201 kernel build) + #47254 (RDNA default attention) + a local guard for the quark AITER imports; each arm is the base with or without this PR. Default server flags (Triton attention, decode CUDA graphs), two rounds alternating arms on the same GPU, `bench_serving --dataset-name random-ids` 512 in / 256 out, GSM8K with `sgl-eval` 0.1.2, `enable_thinking=false`, temperature 0.7, top_p 0.8:

| Qwen3-8B bf16 unless noted | Without this PR (round 1 / 2) | With this PR (round 1 / 2) | Change |
|---|---|---|---|
| c=1 output tok/s (median TPOT) | 25.03 / 25.02 (39.6 ms) | 28.91 / 28.92 (34.3 ms) | **+15.6%** |
| c=8 output tok/s (median TPOT) | 189.5 / 189.3 (40.6 ms) | 206.2 / 205.8 (37.5 ms) | **+8.8%** |
| GSM8K, 100 questions | 95% / 94% | 93% / 94% | within noise |
| OLMoE-1B-7B GSM8K, 50 questions | 64% / 54% | 66% / 66% | within noise |

The 5.3 ms TPOT drop matches the profile below: about 35 µs saved per call, times about 145 norms per token for Qwen3-8B (two per layer plus the Q/K norms, and the final norm).

**Profiling** (torch.profiler, one `RMSNorm` call with residual, bf16, hidden 3072, gfx1151):

| | GPU kernels | 64 calls in one CUDA graph |
|---|---|---|
| `forward_native` | 11 | 2.93 ms |
| this PR | 2 (`CUDAFunctor_add`, `vectorized_layer_norm_kernel`) | 0.67 ms |

The graph timing reuses the same inputs (hot L2). That matches serving here, since each norm's input was just written by the preceding kernel and is about 6 KB per token.
