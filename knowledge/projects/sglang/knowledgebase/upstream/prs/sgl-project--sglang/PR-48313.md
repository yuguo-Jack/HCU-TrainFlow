# [Perf] [NVIDIA] fused_moe: Add H20 down-projection (TMA) configs for GLM-5.3-Flash TP8/TP4

[Upstream PR](https://github.com/sgl-project/sglang/pull/48313) · state: open · merged: False

## Original PR description

## Motivation

#45089 added H20 configs for the GLM-5.3-Flash plain-TP fused-MoE shapes (`E=289`/`E=288` × `N=256`/`N=512`). They come from the stock `tuning_fused_moe_triton.py`, which picks one config per batch size for both GEMMs. Without a `_down` file, serving reuses that config for the down projection and turns TMA off there (`Down MoE config file not found ...; reusing the tuned up-projection config without TMA`).

`tuning_fused_moe_triton_sep.py` tunes the two GEMMs separately and writes a `_down` config next to the up config. #45591 shipped such files for H200 (`E=72,N=2048`). This PR does the same for the four H20 shapes. The up configs are re-tuned together with the down configs, so they replace the four files from #45089.

## Modifications

Eight Triton 3.8.0 configs (main pins torch 2.14.1, which ships Triton 3.8.0). Four replace the files from #45089, four are new:

| Files | Used by |
| --- | --- |
| `E=289,N=256,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP8, target layers |
| `E=288,N=256,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP8, MTP draft layer / shared-expert fusion disabled |
| `E=289,N=512,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP4, target layers |
| `E=288,N=512,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` and `..._down.json` | TP4, MTP draft layer / shared-expert fusion disabled |

How they were tuned:

- `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton_sep.py` with `--enable-tune-up-tma`. Round 1 tunes the down GEMM. Round 2 tunes the up GEMM, writing its output in the layout the chosen down config reads (sorted when the down config uses TMA).
- Routing from `--topk-ids-dir`: top-k ids captured from GLM-5.3-Flash serving on H20 (TP4, 3 ShareGPT prompts of about 8k tokens, all 42 MoE layers, 126 files of shape `[T, 9]`, of which the tuner reads 100; column 9 is the fused shared expert). The `E=288` shapes use the first 8 columns.
- Default search space (1,280 configs after the `BLOCK_SIZE_K` filter) and the default 18 batch sizes, each batch size in its own process on one GPU. The script's single-GPU path neither applies the `BLOCK_SIZE_K` filter nor writes files, so I called its `tune()` per batch size with the filtered space and wrote the files with its `save_configs_sep()`.
- To get `E=289`, I applied #43647's one-line `common_utils.py` change locally, as for #45089. Without it the tuner writes only `E=288`. This PR leaves the tuner alone.

The result uses TMA for the down GEMM in all 72 entries and for the up GEMM in 70 (not at M=4096 for `N=256`). `BLOCK_SIZE_M` is 16 for M ≤ 512 and 32 for M = 1024–3072. At M=4096 it is 64, except 32 for `E=288,N=512`. Each `_down` entry has the same `BLOCK_SIZE_M` as its up entry, which the loader requires. 71 of the 72 up entries differ from #45089's.

## Setup

- Image `lmsysorg/sglang:nightly-dev-cu13-20261031-a2cafa56` (torch 2.14.1+cu130, Triton 3.8.0), with `PYTHONPATH` set to a source tree. The "main" arm is main with #45089's files; the "this PR" arm adds the eight files. The two trees differ only in these files.
  - Kernel benchmark and numerics: main `57bfde9f2c` vs this branch.
  - Serving and GSM8K: main `ea2fda7` vs `ea2fda7` + the eight files. Between `ea2fda7` and `57bfde9f2c`, the Triton fused-MoE kernel (`fused_moe_triton_kernels.py`) and `triton_utils/` (config loader, `fused_moe.py`) are unchanged.
- The same two 8× H20 96 GB nodes as #45089. On node A, GPU 3 overheats under sustained load, so the kernel benchmark uses GPUs 0, 1, 2, 4 and TP4 serving uses GPUs 4–7. TP8 serving runs on node B. Tuning ran on these two nodes and a third 8× H20 node, without node A's GPU 3. In the kernel benchmark and in every serving case, each busy GPU's median SM clock was 1980 MHz (`nvidia-smi` sampling).

## Kernel benchmark

This benchmark calls the runtime `fused_moe` (the serving entry point, including the `_down` lookup) with random FP8 weights and scales and the captured routing. For each M, a CUDA graph holds 10 calls, one per captured routing file (MoE layers 10–13, the first M rows of each), with top-k 9 for `E=289` (the fused shared expert included, as in serving) and 8 for `E=288`. The graph is replayed 100 times and the time per call is recorded. The two arms alternate on the same GPU in ABBA order for 6 rounds, and the tables show the median of each entry. Speedup = main / this PR.

The absolute times differ from #45089's tables, which used the tuner's uniform random routing with top-k 8.

## Serving

The two arms of each pair use the same node, image and flags, and differ only in the source tree on `PYTHONPATH` (see Setup). The main arm's server log shows `Down MoE config file not found at .../E=289,N=256,...,block_shape=[128, 128]_down.json; reusing the tuned up-projection config without TMA.`; this PR's shows `Using MoE kernel config from` for both files plus `Up MoE TMA is enabled` and `Down MoE TMA is enabled`. Other settings are the same as #45089:

- Triton MoE (auto-selected), BF16 KV cache, default DSA backends, radix cache off.
- `--reasoning-parser glm45 --tool-call-parser glm47`.
- MTP: `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.
- Load: `sglang.bench_serving --dataset-name random-ids --tokenize-prompt --random-range-ratio 1.0 --request-rate inf --seed 42`, with 4× concurrency prompts (8 at concurrency 1), after one warm-up run per server start.

This PR's accept length is 0.2% (TP4) and 0.5% (TP8) lower, and the eval finishes 1.5% (TP4) and 2.9% (TP8) faster.

## Accuracy

GSM8K 20-shot, 500 questions (`sglang.test.run_eval --eval-name gsm8k --api completion --num-shots 20 --num-examples 500 --max-tokens 512`; 128 client threads without MTP, 16 in the MTP runs above):

| Layout | Mode | Main | This PR |
| --- | --- | --- | --- |
| TP8 (node B) | no MTP | 0.946 | 0.940 |
| TP4 (node A) | no MTP | 0.936 | 0.928 |
| TP8 (node B) | MTP (runs above) | 0.930 / 0.922 | 0.938 / 0.930 |
| TP4 (node A) | MTP (runs above) | 0.944 / 0.936 | 0.924 / 0.950 |

Repeated runs of the same arm differ by up to 2.6 points, against a standard error of about 1.1 points for one 500-question score at this accuracy.

Numerics (main `57bfde9f2c` vs this branch, node A GPU 0): with fixed random FP8 weights and captured routing (M from 1 to 2048), the `fused_moe` outputs of the two arms differ by at most 1.1e-3 (relative L2) on all four shapes. Against a float32 reference (dequantized weights, unquantized activations, M ≤ 64), both arms have a relative error of 4.2e-2 to 4.6e-2, and the two arms' errors differ by at most 2e-5. The reference does not quantize activations, which both arms do, so neither arm matches it exactly; their errors are the same.
