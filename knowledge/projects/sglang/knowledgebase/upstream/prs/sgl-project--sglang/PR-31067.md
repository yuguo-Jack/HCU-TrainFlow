# fix: preserve require_reasoning across parallel sampling (n>1)

[Upstream PR](https://github.com/sgl-project/sglang/pull/31067) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #30556.

With a native reasoning parser + tool-call parser and `tool_choice: "required"`, reasoning-aware required tool calling works for `n=1` but breaks for `n>1`. For every `n>1` choice the model skips its thinking phase: natural-language reasoning is not generated, the guided tool JSON is placed in `reasoning_content`, `reasoning_tokens` is `0`, and `finish_reason` is `stop` (with some parsers `tool_calls` also comes back `null`).

**Root cause.** `GenerateReqInput.__getitem__` rebuilds a per-sample sub-request when a request is split for batch / parallel sampling (`_handle_batch_request` → `objs = [obj[i] ...]`), but it forwards every field **except** `require_reasoning`, so each sub-sample silently falls back to the field default (`require_reasoning=False`).

Downstream, `require_reasoning=False` makes the scheduler initialize the reasoning-aware grammar (`ReasonerGrammarObject.maybe_init_reasoning`) in **GENERATION** mode instead of **THINKING** mode. The model is forced straight into the constrained tool JSON with no thinking phase; the server's reasoning parser then wraps that JSON as `reasoning_content`, and reasoning-token accounting (gated on `require_reasoning and think_end_id is not None`) reports `0`.

`n=1` is unaffected because `__getitem__` is only called when a request is split (`is_single=False`), which happens for `n>1`.

## Modifications

- **`python/sglang/srt/managers/io_struct.py`** — forward `require_reasoning=self.require_reasoning` in `GenerateReqInput.__getitem__`. It is a scalar shared by the whole request (never normalized into a per-item list), so each sub-sample must inherit the same value. This one change covers both the prefix-cache warmup request and the expanded samples, since both route through `obj[i]`.
- **`test/registered/unit/managers/test_io_struct.py`** — add `test_require_reasoning_preserved_in_parallel_sampling`, a CPU-only regression test asserting each `n>1` sub-sample keeps `require_reasoning=True` (and stays `False` when unset). It fails on pre-fix code and passes with the fix.

```diff
             return_indexer_topk=self.return_indexer_topk,
+            require_reasoning=self.require_reasoning,
             modalities=self.modalities[i] if self.modalities else None,
```

## Accuracy Tests

Verified the fix restores the thinking phase for `n>1` three ways.

**1. CPU repro** (`require_reasoning=True, n=2`, on `main`):

```
obj[0].require_reasoning = False   # bug (expected True)
obj[1].require_reasoning = False   # bug (expected True)
```

After the fix both return `True`.

**2. Unit tests** — `test/registered/unit/managers/test_io_struct.py`: **25 passed**. The new case fails on the pre-fix code (`AssertionError: False is not true`) and passes after the fix.

**3. End-to-end** — Qwen3-0.6B, `--reasoning-parser qwen3 --tool-call-parser qwen`, request with `tool_choice: "required"`, `chat_template_kwargs: {enable_thinking: true}`, `n=2`:

| code | `reasoning_content` for each `n>1` choice |
| --- | --- |
| before | `<tool_call>\n{"name":"get_weather", "arguments":{"location":"San Francisco"}}\n</tool_call>` — thinking skipped |
| after | `"Okay, the user wants to call the get_weather function for San Francisco. Let me check the tool"` — thinking restored |

The `n=1` control returns proper natural-language reasoning in both cases; only `n>1` was broken, and it now matches `n=1`.
