## Motivation
When prefill and decode run different attention TP sizes, `MoriKVManager.send_kvcache` always builds a per-token head-slice plan (`_build_tp_slice_transfer_plan`): one RDMA write of `heads_bytes_per_token_to_send` per token, per layer, for K and V, and the same offset lists are converted from Python lists for every layer's `batch_write`. 

With few KV heads, that "slice" is often the whole token row on both sides. Qwen3.5 has 2 KV heads, so with prefill attention TP2 and decode TP4 every prefill rank holds one head and every decode rank holds one replicated head: `compute_head_slice_params` returns zero head offsets on both sides and a slice size equal to the token row, and the source and destination pages share one layout. The slicing buys nothing yet: 
- a 108k-token request sends ~3.2M 256-byte writes to each decode rank (page-wise it is ~200k 4 KiB writes before coalescing);
- building those plans holds the GIL on the prefill scheduler process, so prefill batches slow down as more transfers are in flight;
- across nodes the KV arrives late, requests pile up on the decode side waiting for KV, and TTFT reaches 20-30 s at modest concurrency. 

This makes the "small prefill TP + larger decode TP" layout, which suits models with few KV heads.

## Modifications
`python/sglang/srt/disaggregation/mori/conn.py`: 
- `_tp_slice_is_full_row(tp_cfg)`: the TP-mismatch slice is the whole token row when the source and destination item lengths match, both head offsets are zero and the slice size equals the source token row. That holds exactly when every rank on both sides keeps whole, replicated KV heads, e.g. 2 KV heads with P2->D4, P2->D8, P4->D8, P4->D2 or P8->D2.  
- `send_kvcache`: in that case drop the slice config and send through the existing contiguous page plan, which also coalesces adjacent pages. Real head splits (for example P1->D2, where a decode rank needs part of a prefill rank's heads) keep the per-token plan unchanged. 

Only the prefill sender changes. There is no new buffer, kernel, flag, registration field or protocol change, and the decode side is untouched, so mixed old/new peers keep working. MLA, DCP relayout and state transfers (`_send_mamba_state`, SWA) are not affected.  

`test/registered/unit/disaggregation/test_mori_tp_slice_full_row.py` (CPU, MoRI stubbed like `test_mori_deferred_kv_release.py`): 
- the full-row verdict for every (prefill rank, decode rank) pair: true for replicated heads (2 KV heads with P2->D4, P2->D8, P4->D8, P4->D2, P8->D2), false for real splits (2 KV heads with P1->D2, P1->D4, P2->D1; 8 KV heads with P2->D4, P4->D2), and never dependent on the rank pair;
- for a full-row config, the per-token slice plan and the contiguous page plan cover exactly the same byte ranges, over a mix of contiguous runs and scattered pages, with one entry per page run instead of one per token;
- `send_kvcache` submits one page-plan write per layer and K/V for replicated heads, and keeps 256-byte token slices for split heads.
