# [Feat] [NVIDIA] megakernels: Qwen3.5 binding and EAGLE entry wiring for NVIDIA megakernel plugins

[Upstream PR](https://github.com/sgl-project/sglang/pull/45266) · state: closed · merged: True

## Original PR description

## Motivation

The NVIDIA megakernel for Qwen3.5-397B-A17B (NVFP4) decode on GB300 lives out of tree, in sgl-project/sgl-nvidia-mega#20. sgl-project/sglang#44945 added `--enable-nvidia-megakernel` and the plugin layer for DeepSeek-V4.1. This PR adds what the Qwen3.5 megakernel needs on the SGLang side, in the same shape:
- **a binding for Qwen3.5**: the runtime state SGLang hands the plugin, as data;
- **EAGLE draft entries**: the draft and draft-extend graph runners capture a plugin step at the batch sizes it serves;
- **KV-length attention graph variants**: a runner captures one graph per attention variant the megakernel names, and each replay picks one by KV length.

SGLang keeps every runner, worker, schedule batch and CUDA graph, and everything after a target step (sampling, acceptance, commits). The plugin gets data: the forward's attention and GDN metadata, the KV and mamba pools, and per-entry structs with SGLang-owned outputs. Before capture, every rank must offer the same entries, batch sizes and variants, or SGLang refuses to start.

This PR is based on main and does not depend on sgl-project/sglang#45474 (the runtime changes for the same decode path). Either can merge first; merged in either order, the two give the same tree. Without `--enable-nvidia-megakernel` nothing changes.

## Modifications

One commit per change:

1. **Pick each megakernel's binding by architecture, and agree on the entries it offers** (`megakernels/runtime.py`, `spec.py`). Qwen3.5's `HybridLinearAttnBackend` keeps its metadata on its two child backends, so it needs its own binding. `spec.ENTRIES` names the optional entries (`draft_sampler`, `draft_loop`, `draft_extend`, `begin_draft_round`), and every rank must offer the same ones.
2. **The binding of Qwen3.5's megakernels** (`megakernels/eagle_binding.py`, new). `EagleBinding` returns the view a covered step reads: attention metadata, GDN slots, the KV and mamba pools. Each pool is sealed at its first read, and `assert_live` fails by name if one is reallocated. The entries' structs carry tensors and numbers only. What a plugin may call or read besides data is listed in literal tuples that the plugin's contract test pins.
3. **EAGLE draft graphs run the draft megakernel's `draft_loop` and `draft_extend`** (`speculative/eagle_megakernel.py`, new, plus the worker and the two draft graph runners).
   - Before capture, each runner calls the entry's factory once with its own outputs. At the batch sizes the factory serves, the graph captures that step in place of SGLang's draft loop, or in place of the draft model step and its top-1.
   - `begin_draft_round` runs on the host before a served draft graph replays.
   - The draft worker builds the entries at the end of its `init_attention_backends`, before any capture. It refuses setups it cannot serve: a non-chain draft, rejection sampling, DP attention, a sliding-window target KV pool, or backends other than GDN with `trtllm_mha`.
4. **Capture a megakernel's KV-length attention graph variants in the verify and EAGLE draft graphs** (`spec.py`, `runtime.py`, `forward_batch_info.py`, `decode_cuda_graph_runner.py`, the draft runners).
   - A megakernel may offer `graph_variants` for `target_verify`, `draft_loop` or `draft_extend`: capture labels plus a `select` that picks one from host state. At the batch sizes that run the megakernel, the runner captures one graph per label and replays the one `select` picks.
   - `ForwardBatch.attention_kv_len_lower_bound` gives `select` a one-request batch's committed KV length without touching the device.
   - With the plugin, its split-KV kernels run from 8K (verify), 16K (draft steps) or 32K (draft extend) tokens, and SGLang's attention below.

Earlier revisions of this PR were stacked on #45474 and also offered `verify_sample` and `gdn_extend`. Both are removed: the plugin's `verify_sample` had no kernel and only turned on #45474's post-verify graphs (`SGLANG_ENABLE_EAGLE_POST_VERIFY_CUDA_GRAPH=1` does the same), and no plugin offered `gdn_extend`. They can come back in a follow-up once a plugin has a kernel for them.

Known limits: draft entries serve graph replays only; a variant's `select` gets a KV length only for one-request batches; SGLang's images pin a plugin commit without Qwen3.5 (`SGL_NVIDIA_MEGA_COMMIT`), so sgl-project/sgl-nvidia-mega#20 must be installed until that pin moves.

## Accuracy Tests

GB300, TP8, real acceptance, GSM8K on a fixed 250-question subset (sampled: temperature 0.6, top-p 0.95, top-k 20).

- **Flag off**, against main on the same trays, greedy at concurrency 1 and 16: 250 / 250 texts identical (main against a second main start: 250 / 250). The same Triton kernels and JIT modules are compiled, and no megakernel line is logged. The only visible differences are the new `ForwardBatch` field and one field in the `SGLANG_LOG_DECODE_GRAPH_KEY` debug line.
- **With the plugin** (sgl-project/sgl-nvidia-mega#20):

| configuration | greedy | sampled | acceptance length vs reference (greedy / sampled) |
|---|---|---|---|
| reference: the development build | 0.980 | 0.984 | 1 / 1 |
| main + this PR + plugin | 0.980 | 0.988 | 1.000 / 0.991 |
| main + #45474 + this PR + plugin | 0.980 | 0.976 | 1.000 / 0.998 |

  Greedy outputs match the reference on 249 / 250 questions in both rows. Every slot, entry and variant capture is active on 8 / 8 ranks.
- **CPU**: the megakernel, speculative and graph-runner unit tests pass wherever main's pass. The plugin's Qwen3.5 tests, including its contract test, pass against this head.

## Speed Tests and Profiling

GB300, TP8 across two 4-GPU trays. Static decode of one request at 128K context with forced acceptance 4.80, about 1,780 rounds per server start. TPS/User = 4.80 tokens / round time. Rows 1–3 are the mean of two pairs of trays run in opposite orders. The plugin was measured at `3509187d74`, an earlier revision of sgl-project/sgl-nvidia-mega#20; the PR head differs only by an opt-in for more than one request, off by default.

| configuration | TPS/User P50 | TPS/User P90 |
|---|---|---|
| main | 706.4 | 700.3 |
| main + this PR + plugin | 765.7 (+8.4%) | 729.6 (+4.2%) |
| main + #45474 + this PR + plugin | 1291.7 (+82.8%) | 1276.0 (+82.2%) |
| the development build (reference) ¹ | 1275.2 | 1249.5 |

¹ On a third pair of trays, row 3 reaches 101.0% of the reference at P50 at 128K, and 100.8% / 100.6% and 101.9% / 101.6% (P50 / P90) at 8K and 32K.

These results were measured on main `28448a86d4`; the branch has since been rebased onto main `b57b5e2286` without changes, and the GPU checks are being repeated on the new base.

Row 2 gains little because the round becomes host-bound: the verify takes 1.87 ms less, but the gaps between graph segments grow from 0.06 to 1.36 ms per round. Row 3 adds #45474, which removes that host work, and the gaps return to 0.06 ms.

[by Claude Code] **Severity: style | Confidence: High**

**Issue**

`megakernel_entry` reads the new optional members with `getattr(built, name, None)`, and so do `_offered_entries` (line 225) and `_offered_graph_variants` (line 232). SGLang does not allow defensive `getattr`. A plugin that misspells a member, such as `graph_variant`, silently gets SGLang's path, and type checkers cannot see these members.

**Fix**

Declare `draft_loop`, `draft_extend`, `begin_draft_round` and `graph_variants` on the `BuiltMegakernel` Protocol, as `draft_sampler` already is, and read them directly. Plugins that offer none of them then set them to `None`. If that breaks the pinned plugin, bump `MEGAKERNEL_API_VERSION`.

File: `python/sglang/srt/megakernels/runtime.py` · line None

[by Claude Code] **Severity: style | Confidence: High**

**Issue**

`_binding_class` loads the binding with `getattr(importlib.import_module(module), attr)` from a `"module:attribute"` string. SGLang does not allow this `getattr`, and the string form is not needed here. It suits plugin specs in `spec._REGISTRY`, but `EagleBinding` is in-tree, and `eagle_binding.py` does not import `runtime.py`, so a direct import has no cycle.

**Fix**

Import `EagleBinding` at the top of `runtime.py` and map architectures to the class:

```python
_BINDINGS: dict[str, type] = {arch: EagleBinding for arch in (...)}

for arch in architectures or ():
    if arch in _BINDINGS:
        return _BINDINGS[arch]
return MegakernelBinding
```

Then patch `_BINDINGS` with the `OtherBinding` class in `test_each_architecture_gets_its_registered_binding`.

File: `python/sglang/srt/speculative/eagle_megakernel.py` · line 53

[by Claude Code] **Severity: perf | Confidence: Medium**

**Issue**

`_unservable_reasons` does not refuse `--speculative-token-map`. With a token map, the draft `lm_head` keeps only the hot tokens, so the draft extend's top-1 is a hot-vocab index. SGLang's `draft_forward` maps it with `hot_token_id[topk_index]` before use. `run_draft_loop` passes `spec_info.topk_index` unmapped, and `EagleDraftLoopIO` carries no map. So `draft_tokens_out` holds hot-vocab ids, and verify rejects almost every draft.

**Fix**

Refuse it here, since the plugin cannot see `hot_token_id`:

```python
if draft.hot_token_id is not None:
    reasons.append("the entries do not run a speculative token map")
```

Add that reason to `test_every_unservable_setup_is_refused_before_any_capture`.
