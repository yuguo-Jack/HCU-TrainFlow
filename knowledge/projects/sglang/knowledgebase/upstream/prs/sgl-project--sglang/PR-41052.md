# [Test] ssl: Wait for the SSL watcher to observe a change instead of racing it

[Upstream PR](https://github.com/sgl-project/sglang/pull/41052) · state: open · merged: False

## Original PR description

## Motivation

`test_reload_cert_key_on_file_change` and `test_reload_ca_on_file_change` construct `SSLCertRefresher`, `await asyncio.sleep(0.3)` and then modify a watched file. The class watches through `watchfiles.awatch()`, whose inotify watch is only registered once the watcher task first runs. A modification written before that is **lost permanently** -- it is never replayed, so waiting longer afterwards does not help. The fixed sleep is therefore a bet on watcher readiness, and it loses often enough to make the file red on runs that no PR caused.

`test/registered/unit/entrypoints/test_ssl_cert_refresher.py` is registered in the per-commit CPU lane (`register_cpu_ci(est_time=17, suite="base-a-test-cpu")`), which is the case `unit-test-admission.md` describes:

> Suite cadence is part of admission: if a failing run cannot be attributed to a single PR's diff, the test belongs in a nightly or weekly suite rather than a per-commit lane.

So this file either needs to become deterministic or be demoted out of the per-commit lane. This PR makes it deterministic.

## Measurements (this machine, CPU, no server)

Ten runs of the whole file at `ffac53d`:

```
1 passed / 9 failed
```

Loss rate as a function of how long the test waits before writing -- the same input, only the delay changes:

| change written after | events lost |
|---|---|
| 0.0 s | 10/10 |
| 0.05 s | 9/10 |
| **0.3 s (what the test does)** | **5/10** |
| 1.0 s | 0/10 |

When the event *is* observed, the reload lands 250-400 ms after the write. A first inotify watch over the temp directory takes on the order of a second to come up on this host; on a faster CI box the effect is smaller but the same in kind, which is why it shows up as an intermittent failure rather than a hard one.

## Modifications

Both tests now rewrite the watched file until the mocked reload callback fires, with a deadline, instead of sleeping a guessed amount and asserting afterwards. That waits on the condition rather than on the timing, and on the observed schedule it converges in one or two rewrites.

Same file, ten runs after the change:

```
10 passed / 0 failed
```

`ruff` / `ruff-format` / `isort` pass on the changed file with the repository's own hooks.

## Deliberately test-only

Not adding a readiness signal to `SSLCertRefresher` (an `asyncio.Event` the test could await) is the more general fix, and I left it out on purpose: `write-sglang-test` states "No production code changes in test PRs". If you would rather have the component expose readiness so any future test can synchronize without polling, I am happy to do that instead -- say the word and I will reopen this as a product change with the test following it.

Also noting the alternative I did not take: `register_*_ci(..., disabled="flaky - see #NNNN")` would silence the lane. Fixing it seemed better than demoting a test that does guard a real behaviour (a CA or key rotation on disk must reach the live `SSLContext`), but I am fine with either call.

## Scope

Test file only, no product change. No credentials or certificates are involved; the temporary files are placeholders and the `SSLContext` is a mock at the dependency boundary, as before.
