# [diffusion] fix: select VSA-H3 for FastH3 when no transformer backend is given

[Upstream PR](https://github.com/sgl-project/sglang/pull/43690) · state: closed · merged: True

## Original PR description

## Motivation

FastH3 8-Step V2 was distilled with VSA-H3 (`fastvideo_inference.json`: `attention_backend: VIDEO_SPARSE_ATTN_H3`, `vsa_sparsity: 0.8`). Since #37662, sglang runs VSA-H3 only when it is selected with `--component-attention-backends transformer=video_sparse_attn_h3`. A FastH3 server started without it serves dense FlashAttention: the trained `to_gate_compress` branch is skipped, and on 4x H200 a request takes 12.6 s instead of 10.0 s.

That is easy to miss. Our cross-framework benchmark profile predated #37662 (#41839 selected VSA-H3 itself) and ran dense attention for three days, while vLLM-Omni served the same checkpoint with VSA. sglang went from ahead to 15% behind on H200, and the server log only says `Using fa attention backend`.

## Modifications

- `FastH3PipelineConfig.validate_server_args` selects `video_sparse_attn_h3` for the transformer when the user gave no transformer backend (neither `--attention-backend` nor a transformer entry in `--component-attention-backends`). The text encoder and VAEs keep their own backends, as the cookbook recommends.
- It does not select it, and dense attention stays, where VSA-H3 cannot run: off CUDA, on GPUs other than SM90 / SM100 / SM103 (the backend's supported set, now `VSA_H3_CAPABILITIES` in `platforms/cuda.py`), or with torch.compile, the breakable CUDA graph or ring attention, which VSA-H3 rejects.
- `ServerArgs.set_automatic_component_attention_backend` records the choice as automatic (`is_component_attention_backend_automatic`), the same way LTX-2 records its text-encoder backend.
- Cookbook: describe the default and how to select dense attention (`--component-attention-backends transformer=fa`).

## Accuracy Tests

With no transformer backend given, the default now goes through the same path as passing `--component-attention-backends transformer=video_sparse_attn_h3` explicitly. Nothing changes when a backend is given.

4x H200, base `53295c697` (main) vs this branch (`f6f923520`), the FastH3 V2 T2VA request (1344x768, 124 frames, seed 1101, 8 steps), two requests per server, MP4 md5 of each request:

| server | transformer backend | md5 (request 1 / 2) |
|---|---|---|
| main, no transformer backend | `fa` | `25b927f2` / `9de1795b` |
| **this PR, no transformer backend** | `video_sparse_attn_h3` (automatic) | **`4a7fb255` / `e62efe95`** |
| this PR, `--component-attention-backends transformer=fa` | `fa` | `25b927f2` / `9de1795b` |
| main, `--component-attention-backends transformer=video_sparse_attn_h3` | `video_sparse_attn_h3` | `4a7fb255` / `e62efe95` |

The new default matches the explicit VSA-H3 flag bit for bit, and an explicit `fa` still matches main's dense output bit for bit. Both rounds gave the same md5s.

## Benchmarking and Profiling

Same box, the four servers interleaved twice, client wall clock per request (median of two after warmup), sglang eager (`--ulysses-degree 4 --performance-mode speed --enable-torch-compile false`):

| server | round 1 (s) | round 2 (s) |
|---|---:|---:|
| main, no transformer backend (dense FA) | 12.656 | 12.639 |
| **this PR, no transformer backend** | **10.064** | **10.027** |
| this PR, `transformer=fa` | 12.646 | 12.706 |
| main, `transformer=video_sparse_attn_h3` | 10.053 | 9.994 |

On this box vLLM-Omni eager serves the same checkpoint with VSA in 10.95–11.06 s.
