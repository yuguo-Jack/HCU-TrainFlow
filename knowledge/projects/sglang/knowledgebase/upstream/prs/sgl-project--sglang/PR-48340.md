# [Feat] hicache: Add a direct_kernel IO backend on page_row for MLA/DSA pools

[Upstream PR](https://github.com/sgl-project/sglang/pull/48340) · state: open · merged: False

## Original PR description

> Written with Claude Code.

## Motivation

HiCache's `direct` IO backend moves `page_first_direct` pages with the copy engine. Before each transfer it syncs the token-slot indices to the CPU and builds one copy descriptor per (page, layer). For an MLA model with a DSA indexer (GLM-5.x, DeepSeek-V3.2) that host-side work dominates each transfer: about 0.5 us of CPU issue per page and layer, paid on every load-back and write-back.

## Modifications

The PR has two commits; reviewing them separately is easiest.

1. **`[Refactor] kvcache: Move the page_row op out of nvfp4_hicache`** moves the page-row transfer op (`_jit_page_row_module`, `warmup_page_row_transfer`, `transfer_page_rows`) unchanged from `ops/kvcache/nvfp4_hicache.py` to `ops/kvcache/page_row.py`, so host pools other than MiniMax NVFP4 can use it. No behavior change; the diff is large but contains no edits.
2. **`[Feat] hicache: Add a direct_kernel IO backend ...`** adds `--hicache-io-backend direct_kernel` for the same `page_first_direct` layout. It copies with `page_row.cuh` SM kernels that read the token-slot indices on the GPU and access the pinned host pool in place, so nothing syncs to the CPU and no descriptors are built:
   - `page_row` gains a token-slot index stride (page `p` is `indices[p * stride] / stride`), a runtime CTA quota (0 sizes the grid to the work; MiniMax NVFP4 keeps its default), and probes for a coherent host link and for GPU access to registered host memory at its CPU virtual address. Stride 1 launches its own kernel instantiation without the stride arithmetic, so MiniMax NVFP4's page-id copies keep their device code.
   - `MLATokenToKVPoolHost` and `DSAIndexerPoolHost` validate the backend and build their pointer tables in a new `prepare_io_backend`, which the controller calls at startup for every pool in the host group. `HybridCacheController.register_host_pool_entry` calls it for a sidecar that registers later (a draft pool not packed into the target pools, e.g. EAGLE3 on an MLA/DSA model). Every other host pool, DeepSeek-V4's `LogicalHostPool` included, rejects the backend at startup.
   - Startup fails with the cause when a page is not a multiple of 128 bytes, the kernels fail to load, or the GPU cannot use registered host memory at its CPU virtual address (`cudaDevAttrCanUseHostPointerForRegisteredMem`).
   - Write-back moves all layers of a pool in one launch; load moves one layer per launch, so layer-wise load overlap is unchanged.
   - The server-arg hook requires (or resolves to) `page_first_direct`, and names `--disaggregation-decode-host-receive-threshold` when that option forced `layer_first`.
   - On a pre-Blackwell GPU with a non-coherent (PCIe) host link it logs a warning, since SM stores to host memory there are expected to lose to the copy engine.
   - Docs: `hicache_design.mdx` and `server_arguments.mdx` describe the new choice and its limits.

`direct` and `kernel` are unchanged; `direct_kernel` is opt-in.

## Accuracy Tests

`nvidia/GLM-5.2-NVFP4` on one 4x GB300 node: TP4, EAGLE MTP 3-1-4, HiCache `write_back` on `page_first_direct` with a 120 GB host pool per rank. Three servers differ only in the cache flags: radix cache only, `--hicache-io-backend direct`, `--hicache-io-backend direct_kernel`. The device KV pool is capped at 131,072 tokens (`--max-total-tokens`) so that repeated prompts are evicted to the host pool and reloaded from it. Other differences from the cookbook's GB300 NVFP4 low-latency recipe: MTP 3-1-4 instead of 5-1-6, `flashinfer_cutlass` MoE and FP4 GEMM with `--disable-shared-experts-fusion`, `--mem-fraction-static 0.8`, `--max-running-requests 64`.

**Long-document key retrieval through the host pool.** 96 synthetic documents of ~18k tokens, each hiding 8 seven-digit codes at depths from 4% to 96% of high-entropy filler. Pass 1 asks for one code per document; the documents total 1.76M tokens, 13x the device pool. Pass 2 resends every document and asks for all 8 codes, so its prefix is reloaded from the host pool (HiCache arms) or recomputed (radix only). Greedy decoding, thinking off; the cache source of each request comes from `return_cached_tokens_details`.

| | radix only | `direct` | `direct_kernel` |
|---|---|---|---|
| pass 1 (96 codes) | 100% | 100% | 100% |
| pass 2 (768 codes) | 100% | 100% | 100% |
| pass 2 prompt tokens served from host | 0 | 99.3% (1,756,864 of 1,768,695) | 99.3% (1,756,864 of 1,768,695) |
| MTP accept length, whole run (of 4) | 3.54 | 3.48 | 3.49 |

The MTP draft layer's KV is packed into the same host pool and reloaded with it; an intact target with a corrupted draft would keep the answers right but drop the accept length, which stays level.

**GSM8K**, `sgl-eval` 0.1.2, all 1,319 problems, temperature 0, `enable_thinking=false`, `--max-tokens 4096`, 64 threads, run twice per server. In run 2, 68% of the prompt tokens were reloaded from the host pool on both HiCache arms.

| | radix only | `direct` | `direct_kernel` |
|---|---|---|---|
| run 1 | 84.15% | 84.99% | 83.93% |
| run 2 (reloaded from host) | 84.84% | 84.23% | 84.91% |

All six scores lie within 1.1 pp of each other (one standard error is about 1.0 pp at n = 1,319). Thinking is off and sampling greedy, rather than the recommended temperature 1.0 / top_p 0.95 with thinking, to keep the runs short and comparable, so the absolute scores sit below the model's thinking-mode GSM8K. No request errors, tracebacks or NaNs on any server.

## Speed Tests and Profiling

`test/manual/kernels/bench_hicache_direct.py` (new) on one GB300 (NVLink-C2C host link), GLM-5.2 per-rank shape under DP attention (78 MLA layers, 21 DSA indexer layers). One serialized radix-node step: evict (D2H) then load (H2D), wall time including index moves and the completion sync:

| pages/step | load `direct` -> `direct_kernel` | write-back `direct` -> `direct_kernel` |
|---|---|---|
| 1 | 2.91 -> 1.41 ms | 0.28 -> 0.14 ms |
| 64 | 7.04 -> 1.58 ms | 2.78 -> 1.13 ms |
| 1024 | 35.1 -> 15.5 ms | 34.4 -> 16.3 ms |

On a B300 host with a PCIe host link, `direct_kernel` matched `direct` on large loads and beat it on write-back (52 vs 40 GB/s at 1024 pages) and on small loads.

MiniMax NVFP4 also copies through `page_row` (`--hicache-io-backend kernel`, its default), so its transfers were measured with and without this PR on one GB300: MiniMax-M3.1-Flash host pools, 60 layers, the main KV row at TP4 / TP2 / attention-TP1 (18 / 36 / 72 KiB per page) and the indexer row (9 KiB per page), 1-512 pages, load as one launch per layer and write-back as one launch for all layers, median of 3 runs.

| pages | write-back, all rows | load, all rows |
|---|---|---|
| 1-8 | -3.3% to +0.6% | -1.9% to +4.2% (bound by host launch time, ~0.4 ms for 60 launches) |
| 64-512 | -0.2% to +0.1% | -1.5% to -0.2% |

The one cost is host launch time: the two added launch arguments add 0.1-0.25 us per launch (of ~6.3 us), which shows only in the smallest loads.

In serving, the accuracy servers above report the same effect through their own timers (`sglang:load_back_duration_seconds` and `sglang:hicache_backup_duration_seconds`, the GPU-stream span of each copy loop). Per rank, as the range over the 4 TP ranks:

| phase | volume per rank | `direct` | `direct_kernel` |
|---|---|---|---|
| long-document pass 2, load-back | 85 GB in 51-54 merged loads | 1.44-1.47 s | 0.55-0.57 s |
| long-document run, write-back | 86 GB in ~483 backups | 1.31-1.34 s | 0.50 s |
| GSM8K run 2, load-back | 3.8 GB in 583 loads | 2.54-2.78 s | 0.63-0.78 s |
| GSM8K run 2, write-back | 9.9 GB in ~1,190 backups | 0.39-0.40 s | 0.10 s |

End-to-end request latencies of these short runs are not a useful comparison: both servers started cold, and serving-time Triton compilations (3-4.5 s each, at different moments on each server) dominate the pass times.

A 30-minute agentic-coding replay of GLM-5.2-NVFP4 (3 prefill workers at PP4 with HiCache `write_back` + `direct_kernel`, 1 decode worker at DEP8, MTP; 20 GB300 GPUs) served 16,989 requests with 0 errors on this branch's transfer path before its rebase onto current main.
