# [AMD] DeepSeek-V4: compile the FP4 indexer prefill schedule kernels at startup

[Upstream PR](https://github.com/sgl-project/sglang/pull/44965) · state: open · merged: False

## Original PR description

## Motivation

On ROCm the DeepSeek-V4 FP4 indexer builds its prefill schedule per forward, outside the CUDA graph
(`build_prefill_schedule`). Its Triton kernels were compiled on the first prefill that reached each variant, and the
variants depended on the batch: Triton specializes integer arguments on divisibility by 16 and pointers on 16-byte
alignment, the prep kernel's block width was the next power of 2 of the row count, and past `MAX_FUSED_ROWS` AITER's row
plan takes its search length as a constexpr derived from `max_seq_len`. That is about 30 variants of the prep kernel
alone. Each first use was a 1.0–1.6 s compile while serving, which stalls every request on the engine.

In a DeepSeek-V4.1-Flash TP4 image benchmark on MI350X, these compiles landed in measured rows in every run (server log:
"Triton kernel … took X s to compile after serving started"), in the rows with the worst TTFT tails.

## Modifications

`kernels/ops/attention/dsv4/fp4_indexer_schedule_hip.py`:
- `do_not_specialize` on the row-count, width and stride arguments of `_prefill_schedule_prep_kernel` and
  `_pad_page_table_kernel`.
- `PrefillScheduleBuffers` starts every region on a 16-byte boundary, as AITER's `_row_plan` already does, so the pointer
  arguments don't fork a variant per `rows % 4`.
- The prep kernel's block width is one of 256 / 1024 / 4096 instead of the next power of 2.
- Past `MAX_FUSED_ROWS`, AITER's `compute_prefill_schedule` gets `max_seq_len` rounded up to a power of 2 with a floor of
  2^18 C4 tokens. The schedule does not change: the row plan picks the smallest split that fits, and that split never
  exceeds the longest row's chunk count, which any bound at or past the true one already covers.
- `warmup_prefill_schedule` compiles that fixed set; `DeepseekV4HipRadixBackend` calls it at init when the FP4 indexer is
  enabled.

No new server args or env vars.

## Accuracy Tests

The schedule is unchanged (bit-exact), so no model eval is needed:
- New: `test_prefill_schedule_matches_aiter_schedule` checks `build_prefill_schedule` against AITER's
  `compute_prefill_schedule` with the true `max_seq_len` (`torch.equal` on the padded page table and `cta_info`), on both
  sides of `MAX_FUSED_ROWS` and with grids tight enough that rows split.
- New: `test_prefill_schedule_compiles_only_at_warmup` runs row counts from 1 to 5003 and page-table widths up to 172
  pages after the warm-up and checks that no kernel of the schedule (prep, pad, AITER row plan and cta_info) compiles a
  new variant.

`test/registered/kernels/ops/attention/test_fp4_indexer_hip.py` on MI350X: 72 passed (65 passed before this change).

## Speed Tests and Profiling

DeepSeek-V4.1-Flash, TP4, MI350X, `bench_serve` with `sglang-oai-chat` and one random image per request, 8 rows (512x512 /
768x1024 / 2048x1600, input 256–8192, concurrency 4–256), n = 2 runs per arm, same image with and without this change.

**Compiles after the server is ready:** 6 and 5 per server before (3 and 2 of them inside measured rows, 1.1–1.6 s each),
0 after. Server start to ready is unchanged (388/387 s before, 390/388 s after); the warm-up takes 2.2 s with an empty
Triton cache.

Rows hit by the compiles before this change:

| Image, input, concurrency | Median TTFT | Output throughput | P99 TTFT (ms) |
|---|---|---|---|
| 512x512, 1024, 16 | −0.1% | +38.9% | 3168 → 1422 |
| 2048x1600, 1024, 16 | −4.3% | +28.2% | 2842 → 1125 |
| 768x1024, 8192, 16 | −11.8% | +19.0% | 4242 → 2450 |

The other five rows are within run-to-run noise. Geomean over all 8 rows: median TTFT −3.8%, median TPOT −0.3%, output
throughput +11.1%.

**Schedule cost per forward** (`prepare_fp4_prefill_workspace` with a reused workspace, GPU time per call, 1 GPU):

| Rows | Before (µs) | After (µs) |
|---|---|---|
| 1–1024 | 35–37 | 35–37 |
| 2000, 4096 | 36–40 | 40–45 |
| 4097–16384 (AITER row plan) | 46–93 | 58–99 |

The +4 µs at 2000/4096 rows comes from the wider fixed prep block; past `MAX_FUSED_ROWS` the fixed `max_seq_len` bound
adds 5–18 µs per call (most at short sequences, 5 µs at 64k tokens). Host time is unchanged. Kernel variants compiled over
the same 54 shapes: prep 26 → 3, row plan 3 → 1, cta_info 4 → 2, pad 1 → 1.
