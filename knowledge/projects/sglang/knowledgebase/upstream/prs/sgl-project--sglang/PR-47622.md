# [Fix] openai: Return required and named tool calls without a tool-call parser

[Upstream PR](https://github.com/sgl-project/sglang/pull/47622) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44474. Without `--tool-call-parser`, required and named tool choices return JSON in `content` instead of `tool_calls`, with `finish_reason: "stop"`. `/v1/messages` has the same issue: `any` and named tool choices return `text` instead of `tool_use`.

Both response paths already support parsing the JSON array, but their callers skip parsing when no tool-call parser is configured. The existing fallback test calls `_process_tool_calls` directly and misses this check.

## Modifications

* Add `_parses_tool_calls` and use it in both response paths. Without a configured parser, it enables JSON parsing for required or named choices, which `_validate_request` already rejects without tools. Configured-parser behavior is unchanged.
* Use the same check when flushing streaming logprobs, so tokens are preserved when `JsonArrayParser` holds back a delta.
* Keep `_tool_call_parsing_active` unchanged because the reasoning parser uses it for channel framing.
* Add tests for required and named choices, `auto`/`none` controls, and streaming logprobs.
* Update `anthropic_api.mdx`, which said tool calls always come back as text without a parser. That now applies only to `tool_choice` `auto`.

#44475 proposed the same parsing check and was closed by its author for lack of review. This PR also includes real-server verification.

## Accuracy Tests

Unit tests ran on macOS arm64 with Python 3.12 at `1f834c1964`:

* `python3 registered/unit/entrypoints/openai/test_serving_chat.py`: 176 tests passed, also on a merge with `main` at `a52ee805c8`.
* The broader entrypoint, function-call, and parser suites: 2093 passed, 16 failed. The same 16 failures occur on unmodified `main` in this environment, including failures caused by missing `torchaudio`.
* Restoring `serving_chat.py` to `main` fails all six required/named subtests and the logprobs test. The `auto`/`none` control passes on both versions.
* Removing the logprobs flush check fails its test. Enabling JSON parsing for all requests with tools fails the `auto`/`none` control.

Real-server testing used Apple Silicon, the MLX backend with `--mlx-enable-sampling`, and `mlx-community/Qwen3-0.6B-4bit`, without `--tool-call-parser`. Identical requests were sent to `main` and this branch.

| Request | `main` | This PR |
| --- | --- | --- |
| Required or named choice, streaming and non-streaming | JSON in `content`, finish `stop` | `get_weather` in `tool_calls`, finish `tool_calls` |
| `none`, non-streaming | Plain text | Plain text |
| `/v1/messages`: `any` or named tool, streaming and non-streaming | `text`, stop reason `end_turn` | `tool_use`, stop reason `tool_use` |

Additional checks covered parallel calls, `parallel_tool_calls=false`, `n=2`, and `--reasoning-parser qwen3`. Streaming logprobs included all 29 completion tokens; `main` returned 28.

Truncated output retains `finish_reason: "length"`, but its shape changes because it now takes the existing JSON path: non-streaming still returns partial JSON in `content`, while streaming now returns no text and may emit a tool call with incomplete arguments. On `main`, streaming returned the partial text as `content`.

CUDA backends were not tested. No model, kernel, or sampling code changed, so no model accuracy evaluation was run.
