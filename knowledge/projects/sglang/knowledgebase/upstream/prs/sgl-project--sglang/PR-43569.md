# [Fix] Restore previous checkpoint after failed disk weight updates

[Upstream PR](https://github.com/sgl-project/sglang/pull/43569) · state: open · merged: False

## Original PR description

## Motivation

A failed disk refit can leave parameters partially overwritten. `update_weights_from_disk()` publishes the candidate path before loading, so rollback reads the same failing checkpoint again instead of restoring the previous disk checkpoint. Preload failures also leave the recorded path changed.

The rollback loader must also support in-place loading: an engine started with a specialized loader could otherwise accept a candidate, partially overwrite its weights, and then raise again when rollback calls unsupported loader methods.

## Modifications

- Load the candidate with a separate config and publish its path only after success.
- Prepare and validate the previous checkpoint's loader before any candidate weight writes. Reject refits when that loader is not `DefaultModelLoader`-compatible.
- Restore the previous disk checkpoint using the runner's original loader settings, while retaining the current PP-stage load group.
- Rebase onto main `b9f5d7000c`, resolving the updater conflict while preserving `restore_weights_before_loading()` before threaded loader writes.
- Add registered CPU regressions for partial writes, preload failures, successful refit followed by failure, PP-stage rollback, and rejection of specialized startup loaders (`sharded_state`, `dummy`, `bitsandbytes`, `gguf`, and `remote`), with both valid and malformed candidates.

## Accuracy Tests

The regression file against the unmodified main updater at `b9f5d7000c` reports **15 failed, 2 passed**, including subtest failures. With the fix, the related suite passes **33 tests and 30 subtests**:

```bash
CUDA_VISIBLE_DEVICES=99 PYTHONPATH=python python -m pytest \
  test/registered/unit/model_executor/model_runner_components/test_weight_updater.py \
  test/registered/unit/model_executor/test_derived_weight_cache.py \
  test/registered/unit/model_executor/test_compensated_mhc_update_guard.py \
  test/registered/unit/model_executor/test_weight_update_tensor_rank.py \
  test/registered/unit/managers/test_scheduler_weight_version_tracking.py -q
```

CPU validation used Linux, Python 3.12, PyTorch `2.9.1+cu129`, Transformers `5.19.0`, and hidden CUDA devices; this does not establish compatibility with the full GPU serving dependency stack.

A separate CPU smoke uses real `.pt` and `.safetensors` files with the unmocked disk iterator. Unmodified main raises again during rollback. The fix passes four state checks: partial `.pt` failure restores the original checkpoint; a successful `.pt` refit becomes the rollback checkpoint; a later partial `.safetensors` failure restores that checkpoint; and a truncated safetensors file preserves its weights and path.

GPU HTTP validation was attempted on an NVIDIA A30 with a tiny synthetic Qwen2 checkpoint, but serving did not start: the available image has CUDA 12.9, while the required `sglang-kernel 0.4.10` wheel requires CUDA 13 (`libnvrtc.so.13` is unavailable). No GPU output/health or distributed PP result is claimed. Rollback still requires the previous checkpoint to remain available and loadable; this is not an in-memory snapshot of intervening tensor/distributed updates.

When an engine was started with a non-`DefaultModelLoader` format such as `sharded_state`, `bitsandbytes`, `gguf`, or `remote`, a failed later refit can still reach this branch because only the candidate loader is checked above. `get_model_loader` then returns a loader that lacks the default `_get_weights_iterator` and/or `load_weights_and_postprocess` interface, yet these helpers call those methods unconditionally, so rollback raises instead of returning the advertised failure and can leave the model partially overwritten. Add a loader-specific rollback path or reject these updates before any writes.
