## Motivation

<!-- Describe the purpose and goals of this pull request. -->

At low concurrency the DFLASH draft model runs its bf16 linears at small M: one block of `num_draft_tokens` tokens per request. 
Two of its paths bypass SGLang's tuned bf16 GEMM dispatch and always use cuBLAS:

- `DFlashGroupedConv.kernel_projection` is a plain `nn.Linear`;
- the candidate head in `_project_candidate_logits` calls `torch.matmul` directly.

Most of the draft's other GEMM shapes have no GB300 tuned entry and fall back to cuBLAS, which is well below the memory bandwidth
limit at these M sizes. The exception is TP4 qkv at M = 8 and 16, which already used the split-K tactics of the "GB300 TP16" block.

## Modifications

<!-- Detail the changes made in this pull request. -->
- `models/dflash.py`
  - `kernel_projection` becomes `ReplicatedLinear`, so it goes through `UnquantizedLinearMethod.apply` and the tuned dispatch.
  - The candidate head calls `bf16_gemm_dispatch` when the backend is cutedsl/gemv and the weight is bf16 on CUDA; otherwise it
    keeps `torch.matmul`.
- `layers/quantization/unquant.py`: GB300 split-K / warp split-K entries at M <= 32, TP4 and TP8.
- `kernels/ops/gemm/cutedsl_bf16_gemm.py`: TGV M ranges for three shapes at M = 17..32.

Each entry was kept only if it beats the current kernel in all three timings of the micro-benchmark below.

The tables are keyed by (M, N, K) only, so the entries are not draft-specific:

- The qkv / gate_up / down shapes (hidden 8192, intermediate 28672, 64 q / 8 kv heads) are also those of Llama-3-70B-class dense
  models at TP4 and TP8. With the default `auto` backend on SM10x those models switch kernels at M <= 32 as well. Only GB300 was
  measured; GB200 was not.
- For TP4 qkv at M = 8 and 16, the new warp split-K entries replace the existing GB300 TP16 split-K tactics (warp split-K takes
  precedence). They are faster in all three timings; see the micro-benchmark.
- `precompile_splitk_tactics()` (only Qwen4-Exp calls it) compiles every table entry, so it now builds 19 more tactics at startup.

🟡 (optional) Every Qwen4-Exp startup with split-K enabled now briefly allocates about 1.66 GB of GPU memory and JIT-builds 19 extra kernels for DFLASH shapes it never runs. precompile_splitk_tactics() (unquant.py:305) walks every key in both tactic tables and allocates a zero n x k weight per key. Fix: have the precompile build only tactics whose (n, k) matches one of the loaded model's linear layers. Qwen4-Exp still needs its own shapes compiled before CUDA graph capture.

<details>
<summary>Why this was flagged</summary>

The trigger is any Qwen4-Exp launch with SGLANG_ENABLE_BF16_SPLITK_GEMM on SM100. load_model_utils.py:59-70 calls Qwen4ExpForConditionalGeneration.precompile_kernels_after_loading (qwen4_exp.py:2676), which calls precompile_splitk_tactics() at unquant.py:305. That function loops over {**_BF16_SPLITK_TUNED_TACTICS, **_BF16_WARP_SPLITK_TUNED_TACTICS} and runs `weight = torch.zeros(n, k, ...)` at unquant.py:313 for each key. This PR adds 19 keys sized for the Muse Spark DFLASH draft and Llama-3-70B, none of them Qwen4-Exp shapes. (7, 50512, 8192) and (14, 50512, 8192) sit next to each other at unquant.py:286-287, and each needs 50512*8192*2 bytes, about 827 MB. The new zeros tensor is allocated before the old one is dropped, so peak use is about 1.66 GB. On the base branch the largest entry was (n, k) = (4608, 8192), about 75 MB. empty_cache() after the precompile frees the memory before the KV cache is sized, so the cost is startup time plus a transient spike. That spike can OOM on a GPU left with little free memory after weights load.

**Verification:** Trigger: a Qwen4-Exp launch on SM100 with the cutedsl backend and SGLANG_ENABLE_BF16_SPLITK_GEMM set (`should_enable_bf16_splitk_gemm`, unquant.py:320-322). Each of the weights for `(7, 50512, 8192)` and `(14, 50512, 8192)` at lines 286-287 is 50512*8192*2 B, about 0.83 GB. load_model_utils.py:63-70 calls `synchronize()` and `empty_cache()` both before and after `precompile()`.
