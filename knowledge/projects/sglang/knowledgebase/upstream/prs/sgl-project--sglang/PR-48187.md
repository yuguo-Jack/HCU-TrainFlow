# [Fix] spec: Apply the multi-layer boundary-KV fix to non-hybrid chain MTP drafts

[Upstream PR](https://github.com/sgl-project/sglang/pull/48187) · state: open · merged: False

## Original PR description

## Motivation

The multi-layer EAGLE boundary-KV fix (`SGLANG_ENABLE_MTP_BOUNDARY_KV_FIX`, on by default, added in #31681) widens each draft-extend window by K - 1 front rows, plus the conv warm-up rows on hybrid models, and re-runs them so the draft KV at already-landed positions is rebuilt from confirmed tokens.

`MultiLayerEagleDraftWorker._init_boundary_kv_fix_state` only turns it on when the request pool holds state slots, i.e. on hybrid (mamba / sconv) models. The conv warm-up rows are already gated on the pool on their own (`draft_extend_num_warmup_tokens`). The K - 1 rows come from the chain depth, not from the cache. So a chain draft (`chain_mtp_hidden_states`) on a plain cache never gets the fix, and its startup log never prints `SGLANG_ENABLE_MTP_BOUNDARY_KV_FIX on: draft-extend windows widened by ...`. Of the current chain drafts, `Step3p5MTP` runs on a plain cache.

Why the rows matter: in chain MTP, step k at position q embeds the token at q + k + 1. A draft-extend window only covers the K + 1 new positions, so near its end that token is still a draft guess. The next window starts past those positions and never rewrites them. Each round, step k keeps min(k + 1, accept_len) landed positions whose draft KV was built from a token that was later rejected, and the count grows with k.

## Modifications

- Gate the fix on `chain_mtp_hidden_states or req_to_token_pool.holds_state_slots`. Hybrid models are unchanged, and the conv warm-up rows stay hybrid-only.
- Non-chain drafts on a plain cache (MiMoV2) still skip the fix, as #31681 set up. The guessed-token argument looks like it applies to them as well, since they also rotate the draft guesses into `input_ids`, but I left that out of this PR.
- `test/registered/unit/spec/test_multi_layer_eagle_boundary_kv_gate.py` (CPU, `base-a-test-cpu`): front-row count and stash shapes for chain / non-chain drafts on hybrid / plain caches, and the env switch. The chain-on-plain-cache case fails on main and passes here.

The widened window needs an attention backend that reads the per-request draft-extend width. FlashAttention, which `Step3p5` selects by default on Hopper and Blackwell, takes the draft-extend-v2 width from the request's extend lengths in the eager, capture and replay paths. The DSA backend does not: its draft-extend-v2 path repeats the page table by `speculative_num_draft_tokens`. No current chain draft runs on DSA, but one that does will need that fixed too.

## Accuracy Tests

Not measured on its own. An internal fork serving a 7-step chain MTP draft on a plain (non-hybrid) MLA cache runs with this change; with it, the startup log shows the widened window. That fork also needed a second fix for chain MTP under DP attention, #48188; the acceptance numbers there were measured with both changes.

Local checks, CPU only: the new unit test, and `test_kv_cache_configurator_draft_gate.py`, `test_weight_update_runners.py`, `test_draft_per_runner_config.py`, `test_eagle_draft_extend_cuda_graph_runner.py`, `test_mlp_sync_pad_unpad.py` give the same results before and after the change. Not run end to end on Step-3.5.

## Speed Tests and Profiling

For chain drafts on a plain cache, each decode draft-extend now runs K - 1 more rows per request, the same cost hybrid models already pay. Nothing else changes.
