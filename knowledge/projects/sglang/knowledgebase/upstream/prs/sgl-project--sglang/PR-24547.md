# [diffusion] Add cancellation for async diffusion video jobs

[Upstream PR](https://github.com/sgl-project/sglang/pull/24547) · state: open · merged: False

## Original PR description

# Summary

  Add request cancellation for the SGLang-Diffusion async video gen endpoint

  `/v1/videos`  exposes an async job lifecycle where requests return a job ID immediately, generation runs in the background, and client can later inspect, delete, or cancel the job by ID

Video jobs can now be cancelled while queued or running - queued jobs are removed before execution, and running jobs observe cancellation during denoising/post-processing

In the case of dynamic batching, cancelled samples are compacted out of the active batch while surviving samples continue
  # Motivation

  Previously, `DELETE /v1/videos/{video_id}` only removed HTTP job metadata. The scheduler and GPU worker could continue processing the request after the client had deleted the video job.

# Results

2xh200, Wan-AI/Wan2.1-T2V-1.3B-Diffusers

## Case 1: single-GPU cancellation, no batching

i tested as follows:

enable single-GPU execution, `num_gpus=1`, `batching_max_size=1`
-> 1 video generation request
-> requested cancellation for request index `[0]`
-> so in this case, i expect request index `[0]` to be cancelled

i observe the following:

-> request index `[0]` was cancelled.
-> `/content` for the cancelled request returned `404`.
-> cancellation was logged cleanly without traceback.

## Case 2: distributed cancellation, no batching

enable distributed execution across 2 GPUs, `num_gpus=2`, `sp_degree=2`, `ulysses_degree=1`, `ring_degree=2`, `batching_max_size=1`
-> 1 video generation request
-> requested cancellation for request index `[0]`
-> so in this case, i expect request index `[0]` to be cancelled

observed:

-> distributed runtime initialized with `world_size=2`.
-> this exercised cancellation across the 2-GPU distributed path with `sp_degree=2`, `ulysses_degree=1`, and `ring_degree=2`.
-> request index `[0]` was cancelled.
-> `/content` for the cancelled request returned `404`.

## Case 3: dynamic batching cancellation with distributed execution

enable dynamic batching, `batching_max_size=4`, `batching_delay_ms=10`
with distributed execution across 2 GPUs, `num_gpus=2`, `sp_degree=2`, `ulysses_degree=1`, `ring_degree=2`
-> 4 concurrent video generation requests
-> requested cancellations: request indices `[1, 3]`
-> so in this case, i expect request indices `[0, 2]` to survive

observed:

-> distributed runtime initialized with `world_size=2`.
-> scheduler formed a merged batch `size=4/4`.
-> queue wait for the merged batch was `0.75ms`.
-> cancelled samples were compacted out of the active batch: `4 -> 2 active request(s)`.
-> indices: `[0, 2]` completed and downloaded valid mp4s, while `[1, 3]` were cancelled and `/content` returned `404`

Follow-up: I opened #47055. It ports this PR onto current main with a smaller scope: DELETE stops a queued job, and a running job stops after its current denoising step. Removing one request from a running dynamic batch is left for a follow-up.

One change in the design: here each rank checks the cancel marker on its own, so with sequence parallelism one rank can stop while the others wait in a collective. In #47055 the replica driver broadcasts its decision, and every rank stops at the same step. It was tested with MiniMax-H3 on 8 x H100 (Ulysses 8).

@qimcis is a co-author of the commit. @mickqian, reviews are welcome on #47055.
