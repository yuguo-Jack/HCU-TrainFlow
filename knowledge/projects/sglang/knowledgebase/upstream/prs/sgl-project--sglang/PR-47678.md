# [Perf] [NVIDIA] dflash: Fill decode-prep length buffers in bulk

[Upstream PR](https://github.com/sgl-project/sglang/pull/47678) · state: open · merged: False

## Original PR description

## Motivation

`DFlashDraftInputV2.prepare_for_decode` writes the committed, current and next KV lengths with one CPU-tensor `__setitem__` per request and field, i.e. 3 x bs element writes every decode step. On DSV4.1-Flash GB300 disagg DEP16 (40 running per rank), `prepare_for_decode` takes 1.0-1.4 ms per step, and these element writes are about 0.4 ms of it. That time sits on the pre-agreement host path of the last DP rank to arrive.

## Related PRs

One of four DSV4.1 attn-DP decode host-path changes that cut the host work between the DP agreement and the draft graph launch. They are independent in code and were measured together: #47676 (padded metadata glue), #47677 (persistent DP-MoE counts), #47678 (bulk decode-prep fill) and #47685 (KV page top-up, measured on top of the other three).

## Modifications

The per-element loop is replaced by an exact rewrite, so there is no switch:
- The committed lengths and top-k values are gathered into lists.
- Each length buffer is written once through its numpy view. The buffers, their dtypes and the point at which they are written, before the non-blocking H2D copies, are unchanged.
- The sums, max top-k and uniform top-k value are computed from the lists.

All runs: GB300, DSV4.1-Flash, on a 2026-10-30 nightly.

## Accuracy Tests

- GSM8K, 1P1D DEP16 with real DSpark acceptance, together with the two sibling host changes (#47676, #47677): 96.82% vs 96.89%; accept length 3.50 vs 3.49-3.51.
- TP4 c1 agg (mega flag on): T=1 GSM8K 97.33% vs 97.33%, long-context needle retrieval at 20K-160K tokens 48/48 vs 48/48 (greedy) and 24/24 vs 24/24 (T=1), accept length 3.591 vs 3.598.

## Speed Tests and Profiling

| | DEP16 nsys, before | DEP16 nsys, after |
|---|---|---|
| `prepare_for_decode` NVTX range, median over ranks | 1162 us | 774 us |

Combined DEP32 / DEP16 / TP4 numbers: see #47676. They come from the same runs, and those numbers are **combined** across the three changes.

The teardown note from that PR applies here as well: a MegaMoE NVLink barrier timeout after the benchmark abort also occurs without these changes; serving-phase results are unaffected.
