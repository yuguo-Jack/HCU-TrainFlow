# [Feat] rust-server: Reach every attention-DP rank with aborts and publish the listener map

[Upstream PR](https://github.com/sgl-project/sglang/pull/47532) · state: closed · merged: True

## Original PR description

Stacked on #47321 (branch `oss-sync-7ef70da4f4`): only the last commit is this change; the commit below it is that pull request.

## Motivation

Under attention DP in Rust-server mode, each DP group's leader runs its own HTTP listener on `port + local_dp_rank`, and each listener feeds only its own scheduler and tracks only its own generations. An abort sent to one listener ends that group's generations only. A gateway aborts through the deployment's base URL with no rank, so on a tp2 + attention-DP 2 run on two GPUs, `/abort_request` on `:P` for a request served on `:P+1` leaves it running to `max_new_tokens`.

## Modifications

- **An abort sent to the base URL reaches every group.** The DP rank 0 listener aborts locally and answers as before, then relays the abort to every other rank's listener through the control relay #46181 added (`peer_endpoints`, built from the `rust_server_endpoints` every rank gathers at startup, and `POST /internal/peer`), as the scheduler's own `AbortReq` for the same public rid, `abort_all` included. Only the rank 0 listener relays, the one serving the base URL. Best effort: the client's reply does not wait for the peers, each post is bounded by a 5 s timeout, at most 64 are in flight at once on a listener, and failures are logged, one line per abort naming the ranks it missed.
- **A relayed abort is served on the receiving listener, not relayed to its scheduler.** The public rid it names is known to that listener's cancellation registry; its scheduler sees uniquified internal ids. `CoreHandle::forward_control_req` tells an abort apart by the message tag (`AbortReq::decode`), ends the matching generations as `/abort_request` does, and answers whether any matched. It never relays again, so a table that points a listener back at itself serves its own abort once instead of looping. A no-op abort (no rid, not `abort_all`) is neither served nor relayed. `abort_all` rides a minted rid, as every fanned-out control request does, since the relay routes its reply by the rid.
- **The listener map is published.** The DP rank 0 listener's `/server_info` gains `dp_listeners: [{dp_rank, url}]`, by rank, from `deployment_info.rust_server_endpoints`, so a router can dial each rank's listener directly.
- **An elastic-EP joiner publishes no endpoints.** When `get_exec().moe.is_ep_joiner` is set, `gather_server_endpoints` returns an empty table without entering the collective: the serving ranks gathered at their own startup and never enter it again, so a joiner's gather cannot meet them (a scale joiner's returns at once with unset slots, a recover joiner's waits on them; #47505). The joiner's listener then fans nothing out, and the serving ranks' table and control fan-out are untouched. Serving ranks under elastic EP gather as any rank does. One unit test pins both sides.
- **`SchedulerRequestReceiver.rust_server_mode`.** The receiver takes the mode as an explicit field, passed by the scheduler, instead of reading the environment on every poll. No behaviour change.

Notes:

- No new gather, peer table, HTTP client or route: the relay reuses the `gather_server_endpoints` → `rust_server_endpoints` → `peer_endpoints` chain and the peer client of `core/peer.rs`. How a listener's address is advertised (wildcard binds, loopback across nodes) and how `/internal/peer` identifies its caller are as #46181 has them and are not changed here; those two gaps are filed separately as #47509 and #47511, and the relay here inherits them.
- No request forwarding, rank selection or health aggregation; the other control endpoints are unchanged.
