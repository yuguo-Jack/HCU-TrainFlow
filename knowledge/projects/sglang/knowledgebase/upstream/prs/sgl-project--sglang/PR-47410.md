# [Perf] deterministic: Launch a fixed number of Triton decode blocks for large split budgets

[Upstream PR](https://github.com/sgl-project/sglang/pull/47410) · state: open · merged: False

## Original PR description

## Motivation

In deterministic mode, Triton decode attention got much slower than normal mode as the batch grew. On MI350X, gpt-oss-20b in deterministic mode reached 0.33x of normal-mode throughput at 64 concurrent requests and 0.21x at 256, with inter-token latency 15.4 ms and 48.8 ms; gpt-oss-120b was 0.41x and 0.25x. A decode profile put most of the extra time in `_fwd_grouped_kernel_stage1` (453 ms vs 107 ms in normal mode with the same Triton attention) and `_fwd_kernel_stage2` (109 ms vs 14 ms).

The cause is the split budget. For batch invariance, deterministic mode fixes the decode split size (`SGLANG_TRITON_DECODE_SPLIT_TILE_SIZE`, 256 tokens), so a request's splits depend only on its own length, and sizes the budget for the longest possible request: `max_kv_splits = max_context_len / 256`, 512 for gpt-oss's 131,072-token context. The grouped stage 1 launched one block per split of that budget, `(batch, head_tiles, max_kv_splits)`, and stage 2 walked all of it. A 1k-2k-token request needs 4-8 splits, so about 99% of the blocks exited without work, and the waste grew with the batch. Normal mode uses at most 8 splits and does not have this problem.

**Which models this affects.** Every model that uses Triton decode attention in deterministic mode, more so the longer its context limit: gpt-oss (sliding window with sinks, which deterministic mode serves with Triton attention), and dense models such as Qwen3-8B (40,960 tokens, 160 splits). With this PR, deterministic gpt-oss-20b goes from 0.33x / 0.21x of normal mode to 0.63x / 0.50x at 64 / 256 concurrent requests, and gpt-oss-120b's throughput rises 63% / 2.1x. Results do not change.

## Modifications

- `decode_attention.py`, `_fwd_grouped_kernel_stage1`: a new constexpr `SPLIT_STRIDE`. With it, each block loops over the splits `split_kv_id, split_kv_id + SPLIT_STRIDE, ...` up to the request's own split count; each split is computed and stored exactly as before.
- `_decode_grouped_att_m_fwd`: when the split budget is above 32 (and the split count is not forced, as for MLA), the grid has 32 blocks per (request, head tile) instead of one per split.
- `_fwd_kernel_stage2`: with the same condition, the merge stops at the request's own split count instead of walking the empty tail. The splits are merged in the same order, so the result is the same.
- Budgets of 32 splits or less, which includes normal mode's default of 8, take the existing path unchanged. The non-grouped (MHA) decode kernel and the MLA path are unchanged.
- New test `test_grouped_decode_attention_split_programs_bitwise` in `test/registered/attention/test_triton_attention_kernels.py`: a split budget of 128 with 1, 8 and 32 blocks per (request, head tile) must give bitwise the same output as one block per split (6 requests of 1 to 20,000 tokens, GQA 64/8, attention sinks).

## Accuracy Tests

MI350X, ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`.

Kernel level (gpt-oss decode shape: 64 query heads, 8 KV heads, head dim 64, sinks; deterministic split counts `ceil(len / 256)`, budget 512): the output is bitwise identical to today's kernel for 1 x 1,500, 64 x 1k-2k, 256 x 1k-2k, 64 x 8k-9k, 4 x 64k and 1 x 120k tokens.

End to end, `--enable-deterministic-inference` (with the other open MI350X deterministic-mode changes, the same in both runs), `python3 -m sglang.test.test_deterministic` (`single`, `prefix`, `prefix --return-logprob`, `radix_cache`, 50 trials) plus a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response). With this PR every check passes:

`test_triton_attention_kernels.py` on MI350X: the new test and the existing decode tests pass. `test_extend_attention` and one case of `test_extend_attention_unified_vs_regular` fail on this image with and without this change (they test the extend kernels, which this PR does not touch).

The gain follows the context limit: the larger the split budget, the more empty blocks this removes (Phi-4's 16k limit gives 64 splits, gpt-oss's 131k gives 512). Long requests are unchanged because they already use most of their splits. Normal mode is unchanged.

With this PR, gpt-oss-20b also passes a long-context batch-invariance check (a 64k and a 120k-token prompt alone vs with 6 long batchmates, 8 / 8 identical) and a chunk-boundary check at 100k tokens (12 / 12), which exercise the looping path (up to 470 splits per request).
