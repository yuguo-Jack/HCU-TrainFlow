# [Fix] [AMD] QSA: Fit the relative prefill indexer kernel in gfx942 LDS

[Upstream PR](https://github.com/sgl-project/sglang/pull/46945) · state: open · merged: False

## Original PR description

## What

Caps the K pipeline depth of the request-relative QSA prefill scoring kernel to the device's shared-memory limit on ROCm. On MI300 (gfx942) with bf16 this means two stages instead of three; gfx950 and fp8 keep three. Behaviour on other platforms is unchanged (the new check is behind `is_hip()`).

## Why

Since #45791, the MI300 Qwen3.8-Flash-Next nightly fails on all three ROCm lanes ([example job](https://github.com/sgl-project/sglang/actions/runs/40552118021/job/122358344976)). The server dies on the first prefill:

```
RuntimeError: Initialization failed: Requested dynamic shared memory 81920 exceeds device limit 65536 for kernel_kernel
  ... qsa_indexer.py select_prefill_tokens -> mqa.py tilelang_qsa_mqa_prefill_relative
```

The kernel keeps a [128, 128] bf16 Q tile (32 KiB) plus three pipelined [64, 128] K tiles (48 KiB), 80 KiB in total. gfx942 allows 64 KiB of LDS per workgroup. With two stages it needs exactly 64 KiB. The same jobs passed on the nightly before #45791 merged; the MI355 lanes are not affected (160 KiB LDS).

## Notes for the reviewer

The stage count is computed from Triton's `max_shared_mem` for the device rather than keyed on the gfx arch, the same way `triton_sparse_mla.py` sizes its KV tile.
