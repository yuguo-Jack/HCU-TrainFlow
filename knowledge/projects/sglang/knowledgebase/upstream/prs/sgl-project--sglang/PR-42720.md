# [Scheduler] Skip the decode for a request whose last token is already in flight

[Upstream PR](https://github.com/sgl-project/sglang/pull/42720) · state: closed · merged: True

## Original PR description

## Motivation

The overlap scheduler plans step i+1 before it processes the result of step i. When that in-flight result already carries a request's last token by `max_new_tokens`, the request still looks unfinished at plan time and gets one more decode whose output is thrown away. Every request that finishes by length pays one wasted decode row, and a request finishing alone pays a whole extra forward. With `max_new_tokens=4` and 8 requests decoded together, overlap mode runs 4 decode forwards where 3 are enough.

## Modifications

- `Req.next_output_finishes_by_length()`: whether committing one more output token reaches `max_new_tokens`.
- `Scheduler._reqs_finishing_inflight(batch)`: the requests of `batch` whose queued (in-flight) result commits their last token by length. It returns nothing outside the overlap loop (`event_loop_overlap` turns it on) and skips beam requests.
- `update_running_batch` drops those requests from the decode batch after recording the batch size, so admission reopens as usual when the batch shrinks. If the remaining rows do not fit the KV pool while finishing requests are in flight, it skips decode for one step instead of retracting: the queued result frees their KV at the end of the step. It returns `None` for a skipped step.
- The mixed-chunk path drops the same requests before mixing the decode rows.
- `ScheduleBatch.filter_batch(chunked_req_to_exclude=...)` is renamed to `reqs_to_exclude`, since it now excludes more than the chunked request.

Behavior change (overlap mode, requests finishing by length only): the last output token's KV is no longer computed by a discarded decode, so a follow-up turn that reuses the prefix (radix cache, streaming sessions) prefills that one token again. With `page_size > 1` and a page-aligned total length, the cached prefix ends one page earlier. Non-overlap mode already behaved this way. Requests that finish on EOS or a stop string, and spec-decoding steps that commit more than one token past the limit, still run the trailing decode.

Tests:
- New `test/registered/scheduler/test_overlap_skip_finishing_decode.py`: 8 requests with `max_new_tokens=4` decoded as one batch take 3 decode forwards (4 before this change).
- Updated expectations that depended on the discarded decode:
  - `streaming_session_kit.py`: inherited KV may be one token short (`kv_inherit_offsets = (0, -1)` by default; the two per-class overrides are removed).
  - `kl_multiturn_utils.default_decode_cache_assert`: accepts one token less, cut to a page boundary (the page size comes from `/server_info`).
  - `test_adaptive_speculative.py`: checks that the server logged a downshift, instead of the step count left by the final verify, which the discarded verify used to set.
  - `test_scripted_runtime_core.py`: holds the `Req` while it runs, since a finished request can now leave every scheduler set in the step its last result is processed.

## Verification
