# [Spec][DSV4] Fix dense DSpark draft KV pool under CP: shard by the draft's TP width and reserve its real cost

## Motivation

A DSV4 target with a dense DSpark draft under context parallelism fails to start on main:

1. **Crash: draft KV pool has the wrong head count.** The draft model shards KV heads by `tp_size` (it is built outside the attention-TP group unless it owns attention), but its pool shards by `attn_tp_size`, which CP collapses to 1. Draft CUDA graph capture then fails in `store_cache` with `Size mismatch for shape#0('batch_size'): expected 80 but got 320`.
2. **OOM risk: the DSV4 target under-reserves the draft.** The draft sizes its pool from the target's token budget. `DSV4PoolConfigurator` reserves it as one extra DSV4 layer (`(T+1)/T`), which is far below a dense draft's per-token cost. The other configurators already charge the real cost via `dflash_draft_cell_size_per_token`.

## Modifications

- Add `dflash_draft_kv_head_tp_size()`, which mirrors `draft_tp_context` (`attn_tp_size` if the draft owns attention, else `tp_size`). The draft's MHA/SWA pools and its budget estimate both use it. Without CP it equals `attn_tp_size`, so existing deployments are unchanged.
- `DSV4PoolConfigurator` charges a dense draft its real per-token cost. A DSV4-shaped draft keeps `(T+1)/T`.

Verified on 4x H20 with DeepSeek-V4-Flash-FP8 and a 5-layer `Qwen3DSparkModel` draft (dummy weights), using TP4 + prefill CP + DSPARK:

| | main | this PR |
|---|---|---|
| draft KV heads / rank | 8 | 2 |
| draft reserved vs. allocated (B/token) | ~203 vs. 10240 | 2560 vs. 2560 |
| startup | crash in draft CUDA graph capture | ready; 128 requests at 64 concurrency all completed |
