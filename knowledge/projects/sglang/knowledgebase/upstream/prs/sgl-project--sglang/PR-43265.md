# [Fix] dsv4: Fix dense DSpark draft KV pool under CP: shard by the draft's TP width and reserve its real cost

## Motivation

A DeepSeek-V4 target with a dense DSpark draft under context parallelism has two mismatches between the draft model and its KV allocation:

- **Placement mismatch:** the dense draft partitions attention heads across full TP, while its KV pool uses the target's attention-TP width, which becomes 1 under CP. The resulting head-count mismatch causes KV writes to fail during draft CUDA graph capture.
- **Budget mismatch:** the draft inherits the target's token capacity, but the DSV4 pool configurator reserves only one additional DSV4 layer. A multi-layer dense draft has a different KV layout and can require substantially more memory per token.

The target must account for both pools before choosing their shared token capacity, using the same draft geometry that allocation and execution use.

## Modifications

- Give dense DSpark drafts the same attention-placement policy as DFLASH: full TP without CP under context parallelism, and attention TP under attention DP.
- Apply that placement consistently to draft construction, KV allocation, attention-backend initialization, CUDA graph capture, and proposal execution.
- Resolve draft KV bytes per token using the same draft TP width, and add the dense draft's cost to the DSV4 full-token memory budget.
- Preserve the existing placement and budgeting path for DSV4-shaped drafts.

Verified on 4x H20 with DeepSeek-V4-Flash-FP8 and a 5-layer `Qwen3DSparkModel` draft (dummy weights), using TP4 + prefill CP + DSPARK:

| | main | this PR |
|---|---|---|
| draft KV heads / rank | 8 | 2 |
| draft reserved vs. allocated (B/token) | ~203 vs. 10240 | 2560 vs. 2560 |
| startup | crash in draft CUDA graph capture | ready; 128 requests at 64 concurrency all completed |
