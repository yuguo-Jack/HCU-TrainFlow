# [cake_kernels] opt-in P1/P2 model routes: DeepSeek-V3 grouped routing, DeepSeek-V4 sparse MLA decode, Mamba2 SSD/SSU, SP all-gather matmul, MiniMax-H3 diffusion stages (SGLANG_CAKE_ROUTES)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42416) · state: closed · merged: False

## Original PR description

## Motivation
Part 2 of the Cake-kernel forwarding work for sgl-project/sglang#42176: opt-in wiring of the forwarded P1/P2 Cake kernels
behind `SGLANG_CAKE_ROUTES` (introduced in #42406). Nothing changes when the switch is unset; every route admits on the
real tensors at the call site and falls back to the stock kernel with identical arguments otherwise.

> **Stacked on #42407 (`cake/09-kimi-k3-e2e`) → #42406 and on the Part 1 groups #42384, #42385, #42386 (merged into this branch).** Review only this PR's own commits (the P1/P2 route commits and the FlashInfer-main re-validation commits on top).

## Routes added (`python/sglang/kernels/cake_kernels/_routes.py`)
| route | model family | engine call site | notes |
|---|---|---|---|
| `dsv3_grouped_routing` | DeepSeek-V3 / R1 / V3.2 | `srt/layers/moe/topk.py::biased_grouped_topk_gpu` | same positional contract as the stock FlashInfer branch; shared-expert append unchanged; FlashInfer host rejections cached per shape |
| `dsv4_sparse_mla_decode` | DeepSeek-V4 (trtllm backend, SM100/103), DeepSeek-V4.1 (SM120/121 default backend) | `deepseek_v4_trtllm_backend.py` decode / verify / varlen prefill; `deepseek_v4_backend.py` DSv4.1 mixed-cache decode | workspace-size admission, counter priming before CUDA-graph capture, grow-only split scratch (eager only); `dsv4/cake_routes.py` |
| `mamba_ssd_prefill`, `mamba_ssu` | Nemotron-H, granite hybrids (Mamba2) | `attention/mamba/mamba.py` SSD prefill and both `selective_state_update` sites via `mamba/cake_routes.py`; chunk-128 metadata built once per forward in `mamba2_metadata.py` | BF16/FP16 state, 128-multiple prefill; radix-cache track rows mapped onto the kernel's per-sequence checkpoints (`Mamba2Metadata.prepare_mixed`, chunk-aligned rows keep the engine's slot copy); calls in which every sequence is a single chunk-128 keep the stock kernel (see below); promoted SSU rows only |
| `sp_all_gather_matmul` | Llama-3.1-70B (`--enable-layernorm-sp`) | `srt/layers/layernorm_sp.py::column_parallel_g_matmul` | prepared / functional all-gather+matmul for unquantized BF16 participants; cached K-major weight copy; `LlamaForCausalLM` accepted as an SP architecture only while this route is selected. The FlashInfer kernel requires torch's **NVSHMEM** symmetric-memory backend: the route selects it in `distributed/bootstrap.init_parallel_runtime` (before the first symmetric allocation), the adapter admission checks it, a FlashInfer `ValueError` is a cached refusal, and torch's fused symm-mem SP ops are disabled for the process once NVSHMEM is selected (they cannot allocate under that backend). `SGLANG_CAKE_SP_CHECK=1` recomputes the stock all-gather + matmul per call and compares at BF16 tolerance (diagnostic) |
| `minimax_h3_diffusion` | MiniMax-H3 DiT (`multimodal_gen`) | `dits/minimax_h3.py` block stages via `minimax_h3_cake_routes.py` | per-stage admission (bf16 pre-attention pack, dense varlen attention, out-proj + gated residual, fc1 SwiGLU); GEMM stages only after an eager warm-up launch. Measured on MiniMax-H3 FL2VA t2va (1× GB200, 768p / 4 s / 8 steps): the attention stage is admitted on all 352 DiT calls, the GEMM stages on none (the engine's AdaLN tables have 6 or 3 rows, the FlashInfer stages require 9); e2e time unchanged (19.9 s vs 19.9 s), +0.9 GB peak; the Cake attention matches FlashAttention-4 within BF16 tolerance on the real shapes but is not faster, so the route stays opt-in |
| `dsa_indexer`, `msa_nvfp4_sparse_decode` | DeepSeek-V3.2 indexer, MiniMax-M3 | registered, **not wired** | engine contract mismatch (paged FP8 indexer logits / exact-shape dense-MQA plans; no NVFP4 KV pool for the MiniMax sparse path) — stock paths untouched |

Route logging: the first "taken" and the first fallback of every distinct reason are logged once per route
(`[cake-route] <route>: …`), so an e2e run can prove which kernel executed and why a batch did not take Cake.

## Model e2e (this round)
- **Nemotron-H-8B-Reasoning-128K BF16, TP1, 1× GB200**, `--mamba-ssm-dtype bfloat16` in every arm.
  - Default server configuration: baseline vs `mamba_ssu,mamba_ssd_prefill` vs `mamba_ssd_prefill` → GSM8K-200
    0.890 / 0.895 / 0.895, decode 335.6 / 2454 / 7540 tok/s (bs 1/8/32) in every arm, bitwise-identical logprobs.
    **The Cake kernels did not run**: plain-decode SSU (T=1, headdim 64) has no promoted Cake row, and the SSD prefill
    route is rejected because the engine requests Mamba radix-cache track states on every prefill (not mapped onto the
    Cake checkpoint contract).
  - `--disable-radix-cache` in both arms (the SSD route admits 128-multiple prefills): GSM8K-200 0.890 → 0.885 / 0.900;
    single 1024-token request prefill **24.0k → 27.7k input tok/s, TTFT 42.6 → 37.0 ms**; bs 8/32 prefill within
    1.4 %; decode identical (SSU stock); serving (200 × 1024/128, conc 32) 36.4k → 37.0k tok/s with TTFT medians
    404 → 354 ms (serving TTFT is noise-dominated at this size: identical-kernel arms spread 277–408 ms). Greedy texts
    identical; a 1024-token input-logprob probe shows the kernel difference (mean |Δ| 0.035). Route log:
    `[cake-route] mamba_ssd_prefill: Cake kernel selected (x=(1, 1024, 128, 64)/bfloat16 …)`.
  - Kernel-level A/B at the model shape (stock Triton SSD vs the Cake route helper, random inputs, BF16 state): Cake is
    1.5–2.0× faster (0.25 vs 0.50 ms at 1024 tokens) and not bitwise: max |Δ| one bf16 ulp at |out| ≈ 90, mean |Δ| 0.0077;
    against an fp32 recurrent reference 1.5 % of outputs fall outside atol/rtol 1e-2 vs 0.6 % for the stock kernel (tracked
    internally; the route stays opt-in).
  - **Radix cache ON (follow-up commits in this PR)**: the engine's Mamba track-state requests are now mapped onto the Cake
    checkpoint contract, so the SSD route admits tracked 128-multiple prefills with the default server configuration
    (route log `Cake kernel selected (x=(1, 1024, 128, 64)…)`; GSM8K 200/50/50 q baseline 0.875/0.880/0.840 vs route
    0.895/0.900/0.860; fixed-prompt logprobs identical). A prefix-hit probe (1024 cached tokens + a 128-token extend) then
    returned all-NaN logits on the route arm; isolated at the kernel level to any call in which every sequence is exactly
    one chunk-128 (random *and* zero initial states, NaN count varies per call; batches with a ≥ 2-chunk sequence are
    clean). The route keeps the stock kernel for that geometry (host extend lengths; logged once) and the probe is clean
    again (same greedy ids as the cold run, max |Δlp| 0.0009 on the outputs); the kernel defect is tracked separately.
- **DeepSeek-V4-Flash FP8, TP4, 4× GB200** (`--dsv4-attn-backend trtllm --kv-cache-dtype fp8_e4m3`, FlashInfer mHC kernels in both arms):
  baseline GSM8K 0.970 vs `dsv4_sparse_mla_decode` **0.020** — an e2e correctness regression. The route was taken on the
  SWA-only, c4 and c128 layers and on the varlen-prefill site; the eager (`--disable-cuda-graph`) arm scores the same, so
  it is not a capture/replay issue. An env-gated in-engine A/B (`SGLANG_CAKE_DEBUG_DSV4_AB`, this PR) re-runs the stock
  kernel on the identical tensors: returning the stock output restores GSM8K 0.980 with logprobs identical to the
  baseline, while the Cake output differs by up to 12–17 (abs) with 12–79 % of elements outside the FP8 tolerance. A
  standalone repro shows the upstream Cake SM100 kernel attends every column up to `sparse_topk` regardless of
  `sparse_topk_lens` (a poisoned tail beyond `lens` leaves the stock output bit-identical and destroys the Cake output)
  and does not apply the `seq_lens` sliding-window validity; FlashInfer's own hardening suite passes at the pin. Tracked
  upstream; **the route stays opt-in and must not be enabled until the FlashInfer fix lands.** Graph-batch rows also fall
  back on the compressed layers (workspace 1.1 GB > the 128 MiB engine buffer).
- **DeepSeek-V3.2-NVFP4, TP4, 4× GB200**: `dsv3_grouped_routing` is unreachable on this checkpoint — the
  `flashinfer_trtllm` MoE runner fuses the router (`BypassedTopKOutput`), so both arms ran identical kernels (GSM8K 0.970,
  bitwise-identical logprobs).
- **DeepSeek-V3-0324 FP8, TP4, 4× GB300** (real weights): under the engine default (`--moe-runner-backend auto` resolves
  to `flashinfer_trtllm` for DeepSeek-V3 fp8 on sm100) the route is likewise unreachable (0 route lines, arms bitwise
  identical, GSM8K-400 0.940 vs 0.938). With `--moe-runner-backend triton` in both arms the route is taken on every rank:
  GSM8K-400 0.935 → 0.945, every e2e metric within ±1 % (the router is microseconds per layer), memory equal. The arms are
  not bitwise identical (1024-token input logprobs: mean |Δ| 0.15 nat); a per-call stock-vs-Cake check inside the route
  (`SGLANG_CAKE_DSV3_ROUTING_CHECK=1`, eager) over 1.0 M routed rows per rank shows identical expert ids and order in
  every row and weights within one FP32 ulp of the stock FlashInfer router, while two identical stock servers are bitwise
  equal — the drift is the chaotic amplification of that rounding through 61 MoE layers, not a kernel defect. Perf-neutral,
  no production path uses it on sm100/sm103 while the default runner fuses routing; the route stays opt-in.
- MiniMax-H3: one e2e A/B on 1× GB200 (above); no video-quality eval in this round — frames differ from the stock run by
  ≈26 dB PSNR against a 36.8 dB stock run-to-run baseline, consistent with trajectory divergence from bf16 rounding-order
  differences (kernel outputs within tolerance), not certified quality-neutral.
- Llama-3.1-70B SP: GPU run on the real architecture with seeded dummy weights (1 node × 4 GB300, TP4, `--load-format dummy`,
  stock no-SP baseline vs the route): the prepared packed-QKV launcher is admitted for qkv (inp 2048×8192 bf16, weight 2560×8192,
  world 4), the per-call Cake-vs-stock check is bit-identical (1151 calls per rank, 19.7 G elements, max abs diff 0), and the
  arms' greedy tokens / logprobs are identical (256/256 tokens, 1023 input logprobs, max diff 0). e2e perf is **not** positive
  in this configuration: selecting the route forces the NVSHMEM symmetric-memory backend, under which sglang's custom
  all-reduce cannot allocate and falls back to NCCL (steady decode throughput ×0.77–0.80 at bs 1/8/32), and the prepared
  launcher is refused inside prefill CUDA-graph capture, so captured prefills run the stock SP path (TTFT ×0.99–1.02). Model
  quality on the real BF16 weights is not measured (checkpoint not reachable from the cluster). Keep the route opt-in.
- MiniMax-M2/M3: wiring + CPU tests only; MiniMax-M2 needs an NVFP4 checkpoint (none public: the warp-decode runner is
  NVFP4-only) and MiniMax-M3's MSA route needs an NVFP4 KV pool the engine does not have.

## FlashInfer main re-validation (`58171ea83f32185a7990cfc15c969ecf79bb406c`)
The Mamba2 SSD / SSU, SP all-gather+matmul and MiniMax-H3 contracts changed on FlashInfer main (any-seqlen exact-scan SSD
with token-major output and FP32 state, promoted headdim-64 SSU row, all-gather+matmul on the engine's `[N, K]` weight view
with any row count, MiniMax-H3 stages on the engine's native operands). The top commits move the three routes to those
contracts; the stock paths are untouched and the adapters keep every admission check the new kernels require. Re-measured
with FlashInfer main in the same container:

- **Nemotron-H-8B BF16 TP1, 1× GB200, radix cache ON, GSM8K-200 0.885 in all arms.** The SSD route now runs on every
  prefill of ≥ 128 tokens (log `Cake kernel selected (x=(1, 795, 128, 64) …)`); packed batches shorter than 128 tokens stay
  on the stock kernel (the FlashInfer host builds a fixed 128-row TMA token box and rejects shorter inputs — logged fallback,
  tracked upstream). `mamba_ssd_prefill`: bs1 prefill 22.5k → **28.9k input tok/s (TTFT 45.5 → 35.5 ms)**, bs32 prefill
  80.7k → 88.3k, decode unchanged, serving 36.3k → 38.1k tok/s. `mamba_ssu,mamba_ssd_prefill`: bs32 decode 7589 → **8380
  tok/s**, serving **40.1k tok/s**, TPOT 4.27 → 4.21 ms. Prefix-hit probes (1024+128, 1536+256): same greedy ids, no NaN.
  Kernel-level A/B at the model shape (random inputs, 128…1152 tokens, with/without initial states): Cake 0.12–0.15 ms vs
  stock Triton 0.42–0.55 ms (3.3–3.8×); against an fp32 recurrent reference 0.58–0.75 % of outputs fall outside atol/rtol
  1e-2 vs 0.55–0.70 % for the stock kernel (same accuracy class); the FP32-state Cake path gives bit-identical outputs to the
  BF16-state path, so the engine-default `--mamba-ssm-dtype float32` no longer silently receives BF16 states.
- **Llama-3.1-70B architecture (seeded dummy weights) TP4 `--enable-layernorm-sp`, 1× 4 GB300.** The route now covers both SP
  projections (packed QKV `N = 2560` and gate_up `N = 14336`) with the weight read in place; per-call Cake-vs-stock check
  (eager arm): 9101 calls per rank, 0 outside BF16 1e-2 over 4.2e11 elements, max |Δ| 1.2e-7; cross-arm logprobs identical.
  End to end unchanged by the re-pin: decode ×0.78–0.81, serving ×0.86, TTFT ×0.88, TPOT ×1.17 — the kernel still requires the
  NVSHMEM symmetric-memory backend, which moves the custom all-reduce onto NCCL (tracked upstream). Keep the route opt-in.
- **MiniMax-H3 FL2VA t2va, 1× GB200, 3 alternating stock/Cake pairs + stock A/A.** All four stages now run on Cake at the real
  shapes (350/350 pre-attention, 352/352 attention, 350/350 out_proj, 350/350 fc1 per run; 3- and 6-row AdaLN tables, int64
  indices, strided q/k/v); generate time 19.4–19.7 s vs 19.8–20.0 s stock; peak memory +484 MB; frame PSNR vs the paired
  stock run 26.2 / 21.6 / 27.6 dB against a 27.8 dB stock run-to-run band (two of three pairs inside it).
