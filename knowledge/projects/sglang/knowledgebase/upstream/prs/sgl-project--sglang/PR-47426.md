# [Perf] disaggregation: Keep prefill KV-send index readback off the scheduler under CP and KV sharding

[Upstream PR](https://github.com/sgl-project/sglang/pull/47426) · state: open · merged: False

## Original PR description

## Motivation

#45492 moved the prefill KV-send page-index readback off the scheduler thread for Mooncake: the indices are copied into pinned memory with `non_blocking=True`, and the transfer worker waits on an event before reading them. Two gaps remain:

1. **CP and KV sharding still block the scheduler.** The deferral is disabled whenever all CP ranks transfer (`enable_all_cp_ranks_for_transfer` without DSA layer split). That exclusion is needed today because `_prepare_send_indices` filters sharded pages by value (`kv_indices % shard_size`) on the scheduler thread, and reading the pinned buffer before its copy lands returns stale values. `--enable-kv-cache-sharding` always turns on all-CP-rank transfer, and prefill CP turns it on as well, so these configurations keep a blocking `.cpu()` on the schedule stream. `_apply_war_barrier` fences that stream behind the in-flight forward, so every send waits for that forward to finish.
2. **The transfer worker spins.** The worker waits with `Event.synchronize()` on a default event. Without the blocking-sync flag, that call busy-waits, so each waiting transfer worker holds a CPU core for the length of the forward.

The page-addressed state payloads of the final chunk (SWA window pages and full-KV pages for `QSA_COMPRESSED` / `MINIMAX_DENSE_KV` / `BLOCK_SCALE*`) also still use the blocking `kv_to_page_indices`.

## Modifications

- Deferral no longer depends on CP. `_send_kv_chunk` defers whenever the sender declares `supports_host_tensor_indices`:
  - The CP filter (`filter_kv_indices_for_cp_rank`) is positional. It slices the in-flight array and reads no values.
  - Under KV sharding, `CommonKVSender` skips the value-based shard filter when the backend sets `defers_shard_filter` (Mooncake does). The chunk is queued with `TransferKVChunk.shard_filter=True`, and `MooncakeKVManager._land_chunk_indices` applies `filter_kv_indices_for_shard_rank` on the worker after the copy lands.
  - A sender that takes host indices but does not defer the filter waits on the event before filtering, so values are never read in flight.
- Transfer metric under deferred sharding: `_record_transfer_indices` keeps the unfiltered pages together with their event. `get_transfer_metric` counts this rank's pages once they have landed.
- `kv_to_page_indices(..., non_blocking=True)` and `to_host_nonblocking` in `mem_cache/common.py` replace the inline pinned copy. The SWA-window and full-KV state payloads use them too. They are copied before the final segment's event is recorded on the same stream, so that event covers them.
- `wait_ready_event` in `disaggregation/utils.py` polls `event.query()` with a 20–200 µs backoff, replacing `synchronize()`. The event stays non-blocking-sync on purpose: recording blocking-sync events stalls the host once 56 of them are outstanding (measured below), which would put the scheduler stall back.
- Mooncake no longer needs a `torch.Tensor` → numpy conversion on the worker: host indices are numpy views of the pinned buffer.

NIXL and Mori are unchanged: they do not declare `supports_host_tensor_indices`.

## Accuracy Tests

The model forward is unchanged. The transferred page lists are the same as on `main`. The unit tests below check that the worker filters only after the copy lands, and the GPU check below compares the deferred result with the synchronous one.

## Speed Tests and Profiling

Microbenchmark on one B300. A 50 ms `torch.cuda._sleep` on the current stream stands in for the in-flight forward. The send is 32,768 token indices with `page_size=64`. Median of 5 runs.

| Scheduler-thread time of one send behind the forward | ms |
|---|---:|
| blocking `kv_to_page_indices` (used today under CP / KV sharding) | 50.06 |
| deferred (`non_blocking=True` + event record) | 0.30 |

| Transfer-worker wait for the copy behind the forward | thread CPU (ms) | wall (ms) |
|---|---:|---:|
| `Event.synchronize()` | 49.32 | 49.35 |
| `wait_ready_event` | 1.56 | 49.64 |

Recording 200 events behind a ~1 s busy stream: non-blocking-sync events take 1.32 ms in total. Blocking-sync events stall for 984 ms on the 57th record.

Correctness check on the same GPU: filtering the pinned buffer before its copy lands gives different pages than the synchronous path. Filtering after `wait_ready_event` matches it exactly. That is the race the CP exclusion was guarding against, and it is why the filter moves to the worker.

I have not run an end-to-end PD benchmark with prefill CP or KV sharding for this PR.

## Tests

`test/registered/unit/disaggregation/test_mooncake_transfer_batching.py`:
- `test_sender_leaves_shard_filter_to_the_worker`: under KV sharding, `send()` never polls the event, queues the unfiltered chunk with `shard_filter=True`, and the transfer metric counts only this rank's pages after landing.
- `test_worker_filters_shard_pages_after_copy_lands`: the worker filters the landed values and pairs them with the right destination slots. Filtering the in-flight buffer would send the wrong pages.
- `test_worker_sends_indices_after_copy_completes`: now checks that the worker polls the event and never calls `synchronize()`.

`test_dcp_pack.py::TestHostTensorIndicesEvent` now covers both all-CP-rank and non-CP senders.
