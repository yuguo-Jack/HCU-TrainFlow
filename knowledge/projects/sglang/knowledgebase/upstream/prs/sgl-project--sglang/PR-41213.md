# [Fix] [XPU] runtime: Fix XPU rotary, radix cache, and tokenizer padding

[Upstream PR](https://github.com/sgl-project/sglang/pull/41213) · state: open · merged: False

## Original PR description

## Motivation

Three independent, unrelated-but-small fixes found:

1. Partial rotary embeddings crash on XPU's fallback kernel path.
2. `UnifiedRadixCache.dec_lock_ref` missing a default argument, crashing the scheduler.
3. Custom remote-code tokenizers with a stale `_pad()` override crashing on every request once `padding_side` started being forwarded (found via `zai-org/chatglm2-6b`).

## Modifications

### 1. `RotaryEmbedding.forward_xpu()` partial rotary embeddings (`python/sglang/srt/layers/rotary_embedding/base.py`)

The fallback-kernel branch (used when `head_size` is not in `[128, 256, 512]`) calls `torch.ops.sgl_kernel.rotary_embedding(...)` without slicing to `rotary_dim` first. That compiled kernel asserts `rotary_dim == head_size` internally and raises `RuntimeError: Rotary dim doesn't match query head_size` for any model with partial rotary embeddings (`rotary_dim < head_size`) on XPU, e.g. `adept/persimmon-8b-chat`, `microsoft/phi-2`, `stabilityai/stablelm-2-1_6b`, `stabilityai/stablelm-3b-4e1t`, `stabilityai/stablelm-zephyr-3b`. Independent of `--attention-backend`, since rotary embedding dispatch is keyed on device type (`is_xpu()`).

Fix: add an `elif self.head_size != self.rotary_dim` branch that falls back to `forward_native()`, mirroring the existing pattern where `forward_cpu`/`forward_npu` already fall back to `forward_native` for their own unsupported cases.

### 2. `UnifiedRadixCache.dec_lock_ref` missing default (`python/sglang/srt/mem_cache/unified_radix_cache.py`)

`BasePrefixCache.dec_lock_ref` declares `params: Optional[DecLockRefParams] = None`, but `UnifiedRadixCache`'s override (introduced in #36848) dropped the default, requiring `params` positionally. `schedule_policy.py`'s `_lock_node` calls `self.tree_cache.dec_lock_ref(last_node)` with no `params` whenever the acquire receipt's `to_dec_params()` returns `None`, even though `is_tree_cache()` is `True` for `UnifiedRadixCache`. This crashes with `TypeError: UnifiedRadixCache.dec_lock_ref() missing 1 required positional argument: 'params'`.

Fix: restore the default, matching the abstract interface and every other concrete `dec_lock_ref` implementation. Backend-agnostic -- reproduced on Intel XPU, but the code path has no device-specific branching.

### 3. Tokenizer `_pad()` compat shim for stale custom signatures (`python/sglang/srt/utils/patch_tokenizer.py`)

transformers 5.x's `PreTrainedTokenizerBase.pad()` now always forwards `padding_side` down to `_pad()`. Custom remote-code tokenizers with a stale, fixed `_pad()` signature (no `padding_side` param, no `**kwargs` catch-all -- e.g. `zai-org/chatglm2-6b`'s `ChatGLMTokenizer`, unchanged for years) crash with:

```
TypeError: ChatGLMTokenizer._pad() got an unexpected keyword argument 'padding_side'
```

on every single generation request, regardless of memory/backend settings.

Fix: detects the mismatch structurally via `inspect.signature` (not a name/class check), so any other custom tokenizer with the same stale signature is covered too, and wraps `_pad()` to drop the `padding_side` kwarg before delegating to the original implementation (which already reads `self.padding_side` directly, so behavior is unchanged).

## Accuracy Tests

All three fixes were validated end-to-end on real Intel XPU hardware, not just reasoned about statically:

- **Rotary fix**: 20-example accuracy smoke checks (server + client, real GPU) for `adept/persimmon-8b-chat` (intel_xpu backend, gsm8k), `microsoft/phi-2` (triton backend, gsm8k), `stabilityai/stablelm-3b-4e1t` (triton backend, hellaswag), `stabilityai/stablelm-zephyr-3b` (triton backend, gsm8k) -- all previously crashed with `RuntimeError: Rotary dim doesn't match query head_size`, all now serve and produce results.
- **Radix cache fix**: reproduced the crash running `docvqa_val`/`gsm8k` evals; with the fix overlaid, prefix-cache reuse works correctly under real request traffic with no crash (confirmed via `stabilityai/stablelm-zephyr-3b` gsm8k run showing cache hits up to several thousand tokens).
- **Tokenizer `_pad()` shim**: confirmed on real Intel XPU hardware against `zai-org/chatglm2-6b`: the `TypeError` no longer occurs and generation requests proceed past tokenization/padding to a correct completion.
