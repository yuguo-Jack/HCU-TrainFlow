# [Perf] [NVIDIA] fp8-gemm: 64x256 tiles for M just above a multiple of 256 on SM90

[Upstream PR](https://github.com/sgl-project/sglang/pull/48242) · state: open · merged: False

## Original PR description

## Motivation

`fp8_scaled_mm` on SM90 (per-token activation scales x per-channel weight scales, the path FP8 dynamic / per-channel checkpoints take) dispatches every M > 128 to one config: 128x128x128 tiles in a 2x1x1 cluster (`sm90_fp8_config_default` in `fp8_gemm_sm90_dispatch.cuh`). The cluster pairs two 128-row tiles, so when M is just above a multiple of 256 most of the last 256 rows are padding:

- with an odd number of 128-row tiles (0 < M % 256 <= 128), the partner CTA of the last cluster runs the full mainloop on zero rows (it still has to load its half of the multicast B tile);
- with 128 < M % 256 <= 192, the last 128-row tile is at least half padding.

On H200 a Qwen3.8-27B gate_up GEMM therefore takes 237 us at M = 272 versus 89 us at M = 256 and 138 us at M = 512 (twice the work), and the same step repeats above every multiple of 256. Prefill chunks and mixed prefill + decode batches hit these M values all the time.

The same dispatch exists in vLLM, where the same fix is open as vllm-project/vllm#65297. There, Nsight Compute on H200 at M = 272 shows the current config executing exactly the tensor-core work of M = 512 (1,392,640 wgmma instructions for both) and reading the 178 MB weight 1.65 times from DRAM; the new config does 0.62 of that work and reads the weight about once.

## Modifications

`python/sglang/kernels/aot/csrc/cutlass_extensions/gemm/fp8_gemm_sm90_dispatch.cuh`: one new config, `sm90_fp8_config_M1024_tail` (64x256x128 tiles, cluster 1x1x1, the same Pingpong FP8FastAccum / TMA-warp-specialized schedules as the default), used for M in (128, 1024] with 0 < M % 256 <= 192. It caps the padding at 63 rows. Every other M keeps the current config, so multiples of 256, M % 256 > 192 (even tile count, no idle partner) and all M > 1024 run exactly the same kernel as today.

`python/sglang/kernels/aot/tests/test_fp8_gemm.py`: `test_accuracy` gains M = 160, 272 and 528, which take the new config (with and without bias, bf16 and fp16 output, five N and five K each). M = 189 in `test_scalar_a_channelwise_b` already takes it.

## Accuracy Tests

The new config computes the same per-element dot products with the same FP32 accumulation; only the tiling changes. Against the current dispatch, outputs are bitwise identical at every point of the sweep below (max abs diff 0 over 95 shape x M points).

How it was tested (H200, sglang `7b88f09239` + this patch, torch 2.14.1+cu130, CUDA 13.0): `csrc/gemm/fp8_gemm_kernel.cu` was compiled with sgl-kernel's own nvcc command line (taken from the configured `common_ops_sm90_build` target) once with the current header and once with this patch, each linked with a minimal binding behind a stand-in `sgl_kernel` package that exposes `fp8_scaled_mm`; the test file then runs unchanged.

## Speed Tests and Profiling

H200, GEMM only (activations pre-quantized), CUDA-graph replay with a 256 MB L2 flush before each replay, median of 20, two alternating rounds per build (run-to-run p5/p95 0.99/1.01). Shapes: Qwen3.8-27B gate_up (34816x5120) and down (5120x17408), Llama-3-8B gate_up (28672x4096) and o_proj (4096x4096), 8192x8192; M = 128, 144, 160, 192, 208, 256, 272, 320, 384, 448, 464, 512, 528, 640, 768, 784, 1024, 1040, 2048.

Alternatives measured on the vLLM copy of this dispatch and rejected: 128x128 tiles with cluster 1x1x1 for every M in (128, 1024] (no gain at multiples of 256, up to 4% slower at some M with M % 256 > 192), 64x128 tiles (up to 0.55x at multiples of 256), cluster 1x2x1 (0.8-0.9x), cooperative schedules (0.9-0.95x), 64x192 and 128x256 tiles (slower than 64x256 at the tail points).

Side note found while testing: `CMakeLists.txt` adds `-gencode=arch=compute_90a,code=sm_90a` only inside the `SGL_KERNEL_ENABLE_FA3` block, so a build with FA3 off compiles these SM90 FP8 kernels for `sm_90` only and every call aborts with "Arch conditional MMA instruction used without targeting appropriate compute capability". Default builds (FA3 on) are not affected; not changed here.
