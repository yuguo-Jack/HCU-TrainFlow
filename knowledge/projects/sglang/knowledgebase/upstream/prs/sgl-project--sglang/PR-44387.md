# [Fix] [NVIDIA] allreduce-fusion: Decline MNNVL fusion across NVLink cliques

[Upstream PR](https://github.com/sgl-project/sglang/pull/44387) · state: closed · merged: True

## Original PR description

## Motivation

On a multi-node TP group whose GPUs are in different NVLink cliques (e.g. a SLURM job placed across topology blocks), MNNVL allreduce fusion fails at workspace creation with `CUDA_ERROR_INVALID_HANDLE`. SGLang then logs one warning and silently falls back to NCCL ring allreduce. On our TP8 (2 nodes x 4 GPUs) decode workload this raised the verify step from 8.756 ms to 31.975 ms (3.65x), and AllReduce from 14.3% to 72.6% of the step, with no error.

Root cause: the fabric-handle decision uses `is_mnnvl_fabric_supported(device)`, a per-GPU query that is True on every rank, while whether rank A can import rank B's fabric handle is a property of the group. The group-aware `is_one_nvlink_clique` already exists (used by custom-AR v2) but the fusion path never called it.

Evidence: NVML probe on two nodes in different NVLink blocks gives different `clusterUuid`, same `cliqueId` (65534), and `is_mnnvl_fabric_supported` True on both. TP8 jobs placed inside one block enable fusion normally (`backend=mnnvl, world_size=8`).

## Modifications

`python/sglang/srt/layers/flashinfer_comm_fusion.py`, `FlashInferWorkspaceManager.initialize`:
- For `backend == "mnnvl"` and a group that spans nodes, run `is_one_nvlink_clique` once (all ranks reach it, result cached on the manager so re-creation does not issue a second collective). If False: set `_flashinfer_allreduce_unavailable`, warn with the topology reason, and return before any CUDA allocation. No POSIX-FD fallback (host-local handles cannot work across nodes).
- If `INVALID_HANDLE` is still hit on a cross-node group, the warning now carries a topology hint.
- The success log includes `one_nvlink_clique=...`.

`_make_flashinfer_workspace_allocation_prop` is intentionally untouched: it is only the memory-sizing preflight, not the path that throws.

## Behavior before / after

Same TP8 job (2 nodes x 4 GPUs) placed across two NVLink blocks.

**Before**
```
[TP0] [SymmDeviceMemory] Rank: 0, Group size: 8, device_idx: 0, Signal pad offset: 150994944
[TP0] Failed to initialize FlashInfer workspace (backend=mnnvl): CUDA error code=400(b'CUDA_ERROR_INVALID_HANDLE'). Disabling flashinfer allreduce fusion permanently.
```
Only a raw CUDA code, no cause, raised after allocation started. The run then completes with no error on `ncclDevKernel_AllReduce_Sum_bf16_RING_LL`.

**After**
```
[TP0] FlashInfer AllReduce fusion disabled: the 8 ranks of this group span more than one NVLink clique, which the MNNVL backend does not support. On SLURM this usually means the job was placed across topology blocks; set --segment equal to --nodes.
```
Names the cause and the fix; no `SymmDeviceMemory` allocation and no `CUDA error code=400`. The NCCL fallback still happens, but is now visible and actionable.

**Same job inside one NVLink block (unchanged behavior, one new field)**
```
FlashInfer AllReduce Fusion enabled and workspace initialized: backend=mnnvl, rank=0, world_size=8, one_nvlink_clique=True, max_token_num=..., hidden_dim=...
```

The "before" log is from a production run; the "after" text is the new warning string, covered by `test_declines_when_not_one_clique`. A real cross-block cluster run is not included.

## Accuracy / Tests

Unit tests in `test/registered/unit/layers/test_flashinfer_comm_fusion.py` (`TestMnnvlCliqueGate`): declines without creating a workspace and warns "NVLink clique"; proceeds when one clique; clique collective runs exactly once across a re-create. `pytest test/registered/unit/layers/test_flashinfer_comm_fusion.py`: 24 passed.

This PR is irrelevant to any compute/accuracy.
