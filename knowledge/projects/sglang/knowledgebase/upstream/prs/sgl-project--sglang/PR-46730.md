# [Feat] [Intel] moe: Run --moe-a2a-backend mooncake on Intel XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/46730) · state: open · merged: False

## Original PR description

## Motivation

Mooncake EP has a native Intel XPU implementation (kvcache-ai/Mooncake#4900). This PR lets SGLang use it for expert parallelism over the TP ranks of one node:

```bash
sglang serve --model-path <MODEL> --device xpu --tp 4 --ep-size 4 \
    --moe-a2a-backend mooncake --attention-backend intel_xpu
```

## Modifications

- `--deepep-mode auto` now resolves to `low_latency` for mooncake, and `normal` is rejected at startup. Mooncake only implements low latency, so both used to fail in the dispatcher.
- XPU: a masked-layout MoE runner in `DeepEPMoE` using sgl-kernel's grouped GEMM, writing its output into the received slab. The Mooncake dispatcher sends BF16, passes the top-k weights at dispatch, and keeps its all-ranks-active tensors alive for the receive hooks.
- XPU: multi-node, DP attention, TBO/SBO, elastic EP, speculative decoding and `--disable-attn-tp-gather` are rejected at startup, and MoE layers with options the runner does not apply (expert biases, gemm1/SwiGLU alpha and limits, router weights on the input) when the model is built. `chunked_prefill_size` and `max_running_requests` are capped to the dispatch's per-rank capacity.
- XPU: a Mooncake built without XPU support is rejected at startup. XPU EP needs Mooncake v0.3.14 or newer built from source with `-DUSE_XPU=ON -DWITH_EP=ON`; the published wheels are CUDA-only, so this cannot be expressed as a dependency and used to fail much later as a `torch.cuda` call.
- `SGLANG_MOONCAKE_EP_NUM_MAX_DISPATCH_TOKENS_PER_RANK` moves into `Envs`, with the same default.
- Docs on the XPU platform page and in the env var reference; unit tests for the argument handling, the XPU runners and the active-ranks ring.

Apart from the `--deepep-mode` resolution and two optional arguments of `expand_to_masked_slab` whose defaults keep its behaviour, all changes are gated on XPU.

## Accuracy Tests

GSM8K via `sgl-eval`, Qwen/Qwen3-30B-A3B (BF16), 4x Intel Arc Pro B60, all 1319
questions, `enable_thinking=false`, temperature 0.7, top-p 0.8. Both rows are from the
same session on this branch, so they are like-for-like; at temperature 0.7 a few tenths
of a point is run-to-run variation (an earlier session on the same code measured 94.92%
and 95.07%).

| Config | Score | Error rate |
|---|---|---|
| `--tp 4` (no mooncake) | 94.39% | 0.00% |
| `--tp 4 --ep-size 4 --moe-a2a-backend mooncake` | 94.84% | 0.00% |

## Speed Tests and Profiling

`python -m sglang.benchmark.serving --dataset-name random-ids --random-input-len 256
--random-output-len 256`, Qwen/Qwen3-30B-A3B (BF16), 4x Intel Arc Pro B60 on one node,
every card on its own PCIe Gen5 x8 link (no Xe Link), Mooncake at
kvcache-ai/Mooncake@e60f941b.

Mooncake forces `chunked_prefill_size` and `max_running_requests` to 512 at TP4, while
the stock baseline runs 4096 / 2048, so the middle column is the baseline re-run with
those same caps. It separates the cost of the cap from the cost of expert parallelism.

Output token throughput (tok/s):

| Concurrency | TP4, no mooncake | TP4 + mooncake's caps | TP4/EP4 mooncake | vs TP4 | vs capped TP4 |
|---|---|---|---|---|---|
| 8 | 87 | 85 | 64 | 73% | 75% |
| 32 | 344 | 332 | 249 | 72% | 75% |
| 128 | 1481 | 1256 | 1020 | 69% | 81% |
| 256 | 3020 | 2249 | 1736 | 57% | 77% |

Median TPOT / TTFT:

| Concurrency | TP4, no mooncake | TP4 + mooncake's caps | TP4/EP4 mooncake |
|---|---|---|---|
| 8 | 90 / 276 ms | 92 / 445 ms | 123 / 545 ms |
| 32 | 90 / 698 ms | 92 / 1005 ms | 125 / 1021 ms |
| 128 | 82 / 1278 ms | 91 / 2859 ms | 112 / 3538 ms |
| 256 | 73 / 1219 ms | 88 / 4835 ms | 114 / 6079 ms |

**Mooncake EP is slower than plain TP on this hardware and this PR does not claim
otherwise.** Splitting the two causes: the batch cap costs 2-4% of throughput at
concurrency 8-32 and 26% at 256, nearly all of it in TTFT; expert parallelism itself
costs a further roughly 25% of throughput and about 25 ms of TPOT, roughly flat across
concurrency.

Decode here is bound by host launch work, not by the all-to-all. TPOT is almost
unchanged from concurrency 8 to 256 (123 -> 114 ms with mooncake, 90 -> 73 ms without)
across a 32x range of batch sizes, which is what a per-step host cost looks like rather
than a per-token GPU or link cost. An XPU profile at concurrency 32 counts 1354 kernel
launches per decode step against 958 for TP: about 8 extra per MoE layer over 48 layers,
from Mooncake's dispatch and combine pair, the masked-layout copies and a `cumsum`. XPU
decode graphs are off by default, so every launch is eager.

So on a single node this backend buys the expert-parallel memory split rather than
speed. Closing the gap is follow-up work outside this PR: XPU decode graphs, and having
sgl-kernel's grouped GEMM read Mooncake's masked layout directly so the layout copies
and the `cumsum` disappear.
