# [Perf] Cache msgspec struct fields in the batch splitter

[Upstream PR](https://github.com/sgl-project/sglang/pull/43520) · state: closed · merged: True

## Original PR description

Follow-up to #44288, which landed the grouping half of #43096.

`_handle_output_by_indices` called `msgspec.structs.fields(output)` on every split. That call takes about 300 us, nearly the whole cost of a split. Since #44288, both IPC hops split each output batch once per destination, so the cost grows with the number of TokenizerWorkers (return hop) and detokenizers (router hop). This caches the field list per output type.

Split plus pickle of a 256-request `BatchStrOutput`, CPU only:

| destinations | main (ms) | this PR (ms) |
| ---: | ---: | ---: |
| 1 | 0.64 | 0.28 |
| 4 | 1.58 | 0.35 |
| 8 | 3.17 | 0.48 |
| 32 | 11.49 | 1.12 |

For reference, the per-request path before #44288 took 4.52 ms for the same batch.

Test: `test_grouped_split_caches_struct_fields_by_output_type`.

- hope1262946533 · comment · 2026-10-14T13:14:26Z · [source](https://github.com/sgl-project/sglang/pull/43520#issuecomment-6169211165)

Thanks for picking up #43096.

I filed that issue after profiling the Detokenizer → TokenizerWorker return hop on DeepSeek-V4-Pro. I have a follow-up implementation that reuses the merged Router helper from #42238 (`_handle_output_by_indices`) without modifying it, and I've opened it as #44288. The two implementations differ mainly in that mine reuses the shared splitter rather than carrying its own; I'm happy to align on whichever the maintainers prefer.

Sharing the production-scale measurements here, since they may be useful regardless of which implementation lands. Setup: SGLang 0.5.17, DeepSeek-V4-Pro, TP8/DP8, no MTP, 32/32 tokenizer/detokenizer workers, decode graph max 310, max running requests 2480, memory fraction 0.96859; aiakperf streaming generate API, concurrency 4960, 79,360 requests, input/output 60,000/1,000, 16 client processes.

1. Return-hop IPC sends: 79,376,257 → 4,790,103 / 4,325,743 / 5,063,191 (−93.6% to −94.6%), carrying the same 79,376,257 output events.
2. Return-worker CPU (single-core process-group p50): detokenizer 288.56% / 276.91% / 289.95% → 107.51% / 99.74% / 105.75%; TokenizerWorker 731.38% / 732.34% / 730.86% → 373.87% / 384.82% / 364.64%.
3. Whole-machine client output throughput, no tracing and no in-process probes, default shared-listener config: 42,297.97 / 42,564.88 / 42,306.00 → 43,740.88 / 43,106.29 / 43,025.66 token/s, i.e. +2.13% from the three-run means.

One qualification worth noting: the throughput gain is tied to the default shared-listener topology. With per-worker listeners (SO_REUSEPORT), grouping enabled vs disabled measured 42,733 vs 42,764 token/s — the gain disappears once connections are already spread across HTTP workers. Grouping helps when an output batch concentrates in few HTTP workers, which is what the default listener produces.

Separately, a documentation entry for the new environment variable is needed for the docs check.
