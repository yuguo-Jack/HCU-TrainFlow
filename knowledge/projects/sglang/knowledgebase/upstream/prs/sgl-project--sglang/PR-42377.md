# fix(function_call): stream DeepSeek V3.1 arguments that share a delta with a call boundary

[Upstream PR](https://github.com/sgl-project/sglang/pull/42377) · state: open · merged: False

## Original PR description

## Motivation

Two argument drops in `DeepSeekV31Detector.parse_streaming_increment`, both silent from the client's point of view:

1. #42137: the streaming pattern matches the function name with a greedy `(.*)`. When one delta carries the end of a call and the start of the next, the name group spans the first call, so its arguments never stream and the second call's arguments stream under the first call's index. `detect_and_parse` parses the same bytes correctly, so streaming and one-shot diverge.
2. #42373: the first pass over a matched call only sends the function name and returns. When a single delta carries a complete call (header, full arguments, end marker), which is the common case with short arguments or `--stream-interval > 1`, the arguments wait for a later increment that may never come. The serving flush then computes its remainder against the stored empty arguments and emits a literal `{}` chunk.

## Modifications

- Make the name group in the streaming pattern lazy, so it stops at the first `<｜tool▁sep｜>` instead of spanning across a completed call.
- Process the argument half in the same pass as the name instead of returning early, so a complete call in one delta streams name and arguments together.
- Add `test/registered/function_call/test_deepseekv31_detector.py` with four cases: the spanning delta, the single-delta complete call (including the flush-visible detector state), progressive argument chunks, and a one-shot sanity check. The first two fail on current main; the other two pin unchanged behavior.

`detect_and_parse` is untouched, and header-then-args splits across deltas behave exactly as before.
