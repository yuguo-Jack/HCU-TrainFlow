# [Perf] hicache: Reuse shared host indices within Mooncake offloads

[Upstream PR](https://github.com/sgl-project/sglang/pull/45788) · state: open · merged: False

## Original PR description

## Motivation

Hybrid Mooncake offloads can expand one logical index tensor into several physical pools. Each pool currently copies the same CUDA indices back to the CPU while building its buffer addresses.

## Modifications

Reuse a CPU index snapshot by tensor identity within one multi-pool write. Populate it only when a direct device pool has missing pages; preserve per-pool validation and missing-page selection. Distinct tensor views remain distinct, and snapshots never survive the write. Single-pool writes keep their existing path. Ready-event ordering and the load path are unchanged.

## Accuracy Tests

- All 14 Mooncake group-semantics unit tests pass, including a regression covering independent partial hits, all-hit laziness, freshness across writes and distinct views sharing storage. The new test fails on the base at two copies versus one.
- Actual Mooncake TCP + CUDA subsystem: 144 offloads, three physical pools with 40 distinct layer buffers each; final reload is byte-exact for all 120 buffers. Exercises CPU/CUDA indices, cold/full-hit/partial-hit requests, and 1/16/128 pages.
- Repository commit hooks pass, including formatting, lint and registered-test checks.

## Speed Tests and Profiling

GB300, PyTorch 2.14.1+cu130, base `d0a75654368`. Actual `batch_set_v2` and pool metadata code, mocked storage RPCs, ready CUDA indices. Two process runs; each case uses 20 warmups and 100 samples per version in randomized order. Address/key/size outputs are identical.

Cold writes, three pools sharing indices, 40 buffers per pool:

| Pages | Run 1 base → candidate (µs) | Run 2 base → candidate (µs) |
|---|---|---|
| 1 | 238.1 → 184.6 | 236.3 → 188.1 |
| 16 | 509.8 → 439.1 | 514.5 → 449.5 |
| 128 | 2358.7 → 2305.9 | 2375.3 → 2319.5 |

Single-pool cold differences are within 1%. CPU inputs do not benefit from fewer device copies and can incur small dictionary overhead. These are metadata microbenchmarks, not serving throughput results. The serving comparison below measures the full prefill request path with actual RDMA offloads.

Reproduction scripts and full case summaries: [HumanX evidence PR #228](https://github.com/radixark/HumanX/pull/228).


### DSv4.1 AgentX end-to-end result

No repeatable serving-throughput gain was measured. On 2×GB300 with Mooncake RDMA (`ibp0p0`), 640 conversations, 7,112 warmup requests, one-token outputs and 900 s sending windows, the A1/B1/B2/A2 comparison used base `d0a75654368a470d8484e3ea45b06e500fee57af` and head `b695b0beaf116c683787e02af3669404e8d4563b` with fresh stores per arm.

| Arm | Version | Total (tok/s/GPU) | p90 TTFT (s) | p95 TTFT (s) |
|---|---|---:|---:|---:|
| A1 | base | 2,010,666.55 | 8.7110 | 11.2779 |
| B1 | candidate | 2,025,804.50 | 8.3986 | 11.7032 |
| B2 | candidate | 2,019,949.31 | 8.0954 | 11.6157 |
| A2 | base | 2,039,167.93 | 7.7773 | 10.9936 |

Equal-weight mean throughput: base 2,024,917.24 vs candidate 2,022,876.91 tok/s/GPU (**-0.10%**); the two base runs differ by 1.42%. Mean per-run p90 TTFT is essentially unchanged (+0.03%); mean per-run p95 TTFT is higher (+4.70%). Two runs per version do not establish significance for these small throughput differences. The metadata speedup should not be presented as an end-to-end win on this workload.

All 109,442 profiling requests completed with zero HTTP errors, content-free responses or cancellations. Store occupancy increased from about 148 GB to 250 GB during each profiling window, confirming actual offload traffic. GPU 2–3 samples stayed idle; clocks and other ranks were not isolated. This is prefill-only serving, not a full decode deployment or a new model-accuracy evaluation. Client idle grace time is excluded from the unchanged request-span throughput calculation.

Exact commands, raw-data locations, storage counter caveats and cleanup verification: [HumanX end-to-end evidence PR #233](https://github.com/radixark/HumanX/pull/233).
