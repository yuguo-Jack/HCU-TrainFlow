# [Perf] [NPU] Support dynamic INT8 MLAProlog for GLM-5.2 attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/43469) · state: open · merged: False

## Original PR description

## Motivation

Enable fused MLA preprocessing for **GLM-5.2-w4a8c8 decode on Ascend NPU** when `SGLANG_NPU_USE_MLAPO=1` is set. This checkpoint uses `W8A8_DYNAMIC` for the attention projections `q_a_proj`, `q_b_proj`, and `kv_a_proj_with_mqa`.

Previously, these projections entered the legacy static ModelSlim MLAPO path, which expects `input_offset`. Dynamic INT8 layers do not have that attribute, so enabling MLAPO fails with:

```text
AttributeError: 'ReplicatedLinear' object has no attribute 'input_offset'
```

This PR routes eligible decode layers through **MLAProlog V3 dynamic INT8 mode**, fusing attention projections, normalization, Q absorption, RoPE, and KV cache writes. It also lets dynamic INT8 indexers reuse the quantized low-rank query returned by the fused operator.

The supported configuration is `weight_quant_mode=2`, `kv_cache_quant_mode=0`, and `query_quant_mode=0`: projection weights and intermediate activations use INT8, while the final query and both KV latent and RoPE key caches use BF16. The checkpoint's `w4a8c8` name describes a mixed quantization configuration; this attention path requires BF16 caches.

## Modifications

- **Fix dispatch for dynamic INT8 attention.** Detect the loaded QKV-A and Q-B quantization methods together, and use `uses_mlaprolog()` consistently for backend selection and output unpacking. Other ModelSlim projections retain their existing backend selection.
- **Add mode 2 weight and activation preparation.** Use ModelSlim's existing `[K, N]` INT8 weight layout, split the merged QKV-A weights and per-channel scales into Q-A and KV-A, and convert projection weights to FRACTAL_NZ. Dynamically quantize BF16 input activations per token and pass the activation and weight scales to `npu_mla_prolog_v3`.
- **Reuse the fused query output in the indexer.** Pass the returned INT8 `q_lora` and FP32 scale directly to dynamic INT8 indexers, eliminating repeated quantization. Recompute BF16 `q_lora` for other indexer implementations, and skip this handling when `indexer=None` on layers that reuse top-k indices.
- **Validate compatibility and preserve required weights.** Require interleaved RoPE, BF16 inputs/caches/`w_kc`, and BF16 final query output; reject unsupported weight layouts, scales, and nonzero RMSNorm bias. Keep the original projections and `w_kc` available for subsequent computation.

The runtime changes are in `mla_preprocess.py` and `deepseek_v2_attention_mla_npu.py`.

## Speed Tests and Profiling

The supplied GLM-5.2-w4a8c8 profile compares MLAPO disabled (`ori`) with dynamic INT8 MLAProlog enabled (`new`) on the same machine:

| Metric | MLAPO disabled | MLAPO enabled | Change |
| --- | ---: | ---: | ---: |
| Steady-state decode latency (ms/token) | 31.583 | 28.943 | -8.36% |
| Equivalent BS=1 generation rate (token/s) | 31.66 | 34.55 | +9.12% |
| Compute kernels per rank per decode step | 3041 | 2707 | -10.98% |

Configuration: BS=1, 3-token prefill, decode KV lengths 4-23, 78 layers per rank, 20 decode steps, and 8 ranks; CANN 9.1.0 and torch_npu 2.10.0.post6. Latency is measured between consecutive `ArgMaxV2` completion points: 19 intervals per rank, averaged across ranks. The equivalent generation rate is calculated as `1000 / latency`.

The enabled path executes 1,560 `MlaPrologV3` calls per rank across 20 steps. Standalone `DynamicQuant` calls drop from 8,220 to 6,240: 1,560 Q-B input quantizations move inside MLAProlog, and 420 redundant indexer quantizations are eliminated across 21 indexer layers.

Prefill does not use MLAProlog V3. In the 3-token sample, enabling MLAPO adds 467 compute kernels and approximately 1.23 ms of cumulative kernel time for RoPE layout compatibility; this is not a measured TTFT increase.

These results are device-profile measurements from a single A/B capture. The exact capture commit, full launch arguments, and checkpoint revision were not retained; end-to-end throughput and TTFT benchmarks remain pending.
