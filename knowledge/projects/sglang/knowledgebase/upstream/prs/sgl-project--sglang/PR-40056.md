# [PD][NPU] Fix Mooncake TE init failure caused by thread-local ACL device binding

## Motivation
PR #37874 (2026-09-03) wrapped `MooncakeTransferEngine.initialize()` with `run_with_deadline()`, which executes `engine.initialize()` in a newly created daemon thread. However, ACL device/context binding is thread-local — `aclrtSetDevice` / `aclrtGetDevice` / `aclrtGetCurrentContext` only apply to the calling thread.

On NPU, `AscendDirectTransport::allocateLocalSegmentID()` (non-agent mode) calls `CHECK_ACL(aclrtGetDevice(&device_logic_id))` at `ascend_direct_transport.cpp:244`. Since the daemon thread never called `aclrtSetDevice`, this fails with `Call acl failed, detail:` (empty error message, which is characteristic of "no device context on this thread").

The same issue affects `MooncakeStore.setup()`, where `AscendDirectTransport` is installed in the store's own TransferEngine.

Root cause chain:
1. PR #37874 introduced `run_with_deadline` for TE init timeout protection
2. `run_with_deadline` (common.py:3396) spawns a daemon thread to run `fn`
3. ACL device binding is thread-local — the calling thread's `torch.npu.set_device()` does not propagate to the daemon thread
4. `AscendDirectTransport` in the daemon thread calls `aclrtGetDevice` → fails because no device is set on that thread
5. Community never tested NPU + Mooncake path (no `set_device` in any commit history of mooncake_transfer_engine.py)

Reference: vllm-ascend's `GlobalTE.get_transfer_engine()` calls `transfer_engine.initialize()` synchronously in the same thread (no `run_with_deadline`), so `torch.npu.set_device()` in the calling thread suffices.

Fix:
- `mooncake_transfer_engine.py`: Move `torch.npu.set_device(self.gpu_id)` into the `_initialize()` closure passed to `run_with_deadline`, so the device is set inside the daemon thread. Also set it on the calling thread for subsequent ACL calls (e.g. `register_memory`).
- `mooncake_store.py`: Add `torch.npu.set_device(tp_rank)` before `store.setup()`, as `setup()` is called synchronously on the current thread but that thread may not have an NPU device context set.
