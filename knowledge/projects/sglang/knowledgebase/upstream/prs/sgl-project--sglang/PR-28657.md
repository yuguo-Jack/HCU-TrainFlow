# [Fix] openai: Handle empty messages after final assistant stripping

[Upstream PR](https://github.com/sgl-project/sglang/pull/28657) · state: open · merged: False

## Original PR description

## Problem

On the dsv32 encoding path, `continue_final_message=True` with a single trailing assistant message makes `_handle_last_assistant_message` strip that message and leave an empty list. The empty-system-prompt insertion then indexes `messages[0]` and raises `IndexError`. Guarding only the index is insufficient because no remaining message renders the assistant generation header before the continued text is appended.

Request validation only rejects an originally empty message list, so it does not cover a list emptied during rendering.

## Fix

Guard the system-prompt insertion with `not messages or messages[0]["role"] != "system"`. Record the emptied state before inserting the system message, then encode the dsv32 assistant generation header, including the appropriate thinking start or end token, before appending the continued assistant text. Remove a repeated BOS token if the tokenizer adds one to that header.

Current main routes dsv4 and dsv41 through the DeepSeek recipe adapter, so this PR now changes only the remaining dsv32 path.

## Test

Added `test_dsv32_handles_continue_final_message_only_assistant`. Against the unmodified current-main production file it fails with the original `IndexError`; with the fix it passes and checks that the rendered input contains `<｜Assistant｜></think>`.

Validation on the merged head:

- `test/registered/unit/entrypoints/openai/test_serving_chat.py`: 174 passed and 255 subtests passed.
- All pre-commit hooks on the two changed files pass, including the registered-test registry checks, Ruff, formatting, and codespell.

This is CPU unit coverage with mocked tokenizer boundaries, not a model-server or GPU acceptance run.

When `continue_final_message=True` and the request contains only a single trailing assistant message, the assistant message is stripped, leaving an empty list (or only the system message). In this case, the custom DeepSeek encoders (`dsv4` and `dsv32`) will not append the assistant start token (`<｜Assistant｜>`) because there are no user or developer messages in the remaining list. This results in a malformed prompt missing the assistant role marker.

To fix this, we should check if the remaining messages contain any user, developer, or tool messages. If they do not, we must prepend the assistant start token to `assistant_prefix` before it is encoded and appended.

```suggestion
            # If the remaining messages do not contain any user, developer, or tool messages,
            # the encoder won't append the assistant start token. We must prepend it to assistant_prefix.
            if assistant_prefix and not any(m.get("role") in ("user", "developer", "tool") for m in messages):
                assistant_start = "<｜Assistant｜>" + (
                    "<think>" if thinking_mode == ThinkingMode.THINKING else "</think>"
                )
                assistant_prefix = assistant_start + assistant_prefix

            # messages can be empty here when continue_final_message strips a lone
            # trailing assistant message, so guard before indexing messages[0].
            if not messages or messages[0]["role"] != "system":
                # insert an empty system prompt to help render tool system prompt
                messages.insert(0, {"role": "system", "content": ""})
```
