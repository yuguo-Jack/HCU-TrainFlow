# [Fix] parser: Detect the plain-JSON tool-call format for tool-call-parser=auto

[Upstream PR](https://github.com/sgl-project/sglang/pull/48342) · state: open · merged: False

## Original PR description

## Motivation

Fixes #48172.

`--tool-call-parser=auto` resolved to *no parser* for the chat templates that use the plain-JSON tool-call format, so tool calls came back as plain text with `tool_calls: null`:

```
--tool-call-parser=auto specified but could not detect tool-call parser from chat template. Disabling tool-call parser.
```

Affected templates (all of them document the format and none of them has an `enable_thinking` toggle):

- `Qwen/Qwen2.5-0.5B-Instruct` (and 7B / 32B / 72B / Coder / Math)
- `Qwen/Qwen3-4B-Instruct-2507`, `Qwen/Qwen3-30B-A3B-Instruct-2507`
- `Qwen/Qwen3-VL-8B-Instruct`, `Qwen/Qwen3-VL-30B-A3B-Instruct`
- `Qwen/Qwen3-Next-80B-A3B-Instruct`
- `inclusionAI/Ling-mini-2.0`, `inclusionAI/Ring-mini-linear-2.0`

The format is:

```
<tool_call>
{"name": "...", "arguments": {...}}
</tool_call>
```

The `qwen` detection rule keys on an `enable_thinking` toggle defaulting to `true`, which is how the Qwen3 templates that *do* have a toggle get detected. The templates above have no toggle at all, so nothing matched and the tool-call parser was disabled.

## Modifications

- `python/sglang/srt/parser/template_detection.py`: add a `_is_qwen_json_tool_call` predicate and a `qwen_json_tool_call` rule to `TOOL_CALL_PARSER_RULES`, mapping the plain-JSON format to the `qwen` parser (`Qwen25Detector`), which reads exactly this format.
  - The rule recognizes the format by its tool-call tag plus the JSON `"name"` key. The key appears either escaped (`\"name\":`) where the template documents the format inside a Jinja string literal, or plain (`"name":`) where the template renders a tool call back to the model; both forms are accepted.
  - The rule is placed after the `qwen` rule, so templates that *do* have an `enable_thinking` toggle keep resolving through `qwen` as before, and before the broad `deepseek_v3` / `deepseek_r1` fallbacks.
- `test/registered/unit/parser/test_template_manager.py`:
  - `test_plain_json_tool_call_format_detects_qwen_parser`: the escaped and the plain JSON-key shapes both resolve to `qwen`.
  - `test_tool_call_tag_without_json_name_is_not_qwen`: the XML-KV tool format (GLM style) shares the tool-call tag but has no JSON payload, so the new rule must not claim it.
  - `test_qwen25_plain_json_template_detects_qwen_tool_call_parser`: `Qwen/Qwen2.5-0.5B-Instruct` resolves to the `qwen` tool-call parser and to no reasoning parser.
  - `test_specific_rules_precede_broad_fallbacks`: asserts the new rule's position relative to `qwen` and `deepseek_v3`.

## Accuracy Tests

Not applicable: this only changes which tool-call parser `--tool-call-parser=auto` selects. It does not touch model, sampling, or serving code paths.

The selected parser was checked against the format the affected templates document:

```
<tool_call>
{"name": "get_weather", "arguments": {"city": "Paris"}}
</tool_call>
```

which `Qwen25Detector` parses into `{"name": "get_weather", "arguments": {"city": "Paris"}}` (same detector that `--tool-call-parser qwen25` selects; `qwen25` is an alias of `qwen`).

To bound the blast radius, the detection was diffed before/after this change over the chat templates *and* the real tokenizer vocabs of 41 models on the Hub:

- every template that already resolved to a parser still resolves to the **same** parser (no template changed from one parser to another);
- the templates listed above, which previously resolved to *no* parser, now resolve to `qwen`;
- the reasoning parser is unchanged for every model.

```
unchanged: 24, changed: 13, no template: 4
```
