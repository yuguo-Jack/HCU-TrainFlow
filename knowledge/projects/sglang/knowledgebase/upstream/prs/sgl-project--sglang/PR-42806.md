# [CI] wait-for-jobs: Retry transient GitHub API errors

[Upstream PR](https://github.com/sgl-project/sglang/pull/42806) · state: open · merged: False

## Original PR description

## Motivation

Thanks @leejnau for the pointer - the `retries: 2` one-liner this PR started with is superseded now that #46028 landed `retries: 3` on the same step. That alone doesn't close the gap though: the plugin's backoff adds up to about 15 s while each 502 took about 10.7 s to arrive on 10-30, so a run of 502s can still exhaust the retries, and any error that survives them is thrown out of `fetchJobs()` and ends the polling loop, failing the gate. A fresh occurrence landed in #42752 on 11-03 - a 502 from the jobs API that survived octokit's 3 retries at attempt 199 while polling stage B and killed the gate (run 41452221893).

## Modifications

I've pivoted the branch to the per-poll catch design leejnau suggested, rebuilt on current main. The polling loop now catches jobs-API errors per poll, logs a warning with the poll number and consecutive-failure count, and tries again at the next interval; the gate fails only after 3 consecutive failed polls, since this step only waits on other jobs and one missed poll costs nothing. The failure message names the tracker row (I1 in #42752) so future occurrences are easy to match. The step-level `retries: 3` from #46028 stays as the per-request retry layer, and the 304/ETag cached path and the completion detection are untouched.
