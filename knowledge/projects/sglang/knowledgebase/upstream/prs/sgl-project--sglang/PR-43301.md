# [Multimodal] Chunk and cache audio items whose offsets span several placeholder runs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43301) · state: closed · merged: True

## Original PR description

## Motivation

An audio item can be interleaved with text, so its placeholder tokens arrive in several runs (for example offsets `[(2, 3), (6, 7), (10, 11)]` for one six-token item) rather than one contiguous span. The chunked prefill embedding path treated any item with more than one offset as a "full" request: the whole request was re-encoded on every chunk and the per-item embedding cache was never consulted, so a history item replayed on the next turn was encoded again every time.

## Modifications

- `_get_chunked_prefill_embedding` keeps audio items on the per-item path even when they have several offsets. New helpers `_item_overlap` and `_slice_item_chunk` derive an item's token count and its slice for one chunk from all of its runs; single-offset items keep the previous arithmetic.
- `_get_chunked_embedding_by_item` and `_assemble_per_image_chunk` return the ordered item slices instead of concatenating them, and the caller concatenates the whole batch once. A single slice is returned as-is, so a request with one cached item gets a view of the cache entry and no copy. `PerImageRequestInfo.overlapping` now carries `(idx, item, token_count)` instead of `(idx, item, start, end)`.
- `_get_precomputed_embedding` slices each precomputed item by its own offsets instead of concatenating a request's items first and slicing with the flattened offsets, and skips the concat for a single slice.
- When `embedding_cache.set` admits an entry, the stored tensor is used as the chunk source if its token count matches, so returned chunks alias the cache entry rather than the encoder's batch output buffer.
- `test/registered/chunked_prefill/test_mm_chunked_embedding_unit.py` (CPU-only, `base-a-test-cpu`) covers multi-offset audio items on both the batched and per-request (`_is_hip`) paths: chunk boundaries inside an item, a replayed item served from the cache without re-encoding, request-order assembly with a single `torch.cat`/`torch.concat` call under cache pressure, and precomputed multi-offset slices. Existing cases are updated for the list-of-slices return type and additionally assert that returned chunks share storage with the cache entry.

## Accuracy Tests

Not applicable: the embeddings handed to the model are the same slices as before, assembled with one concat instead of several. The unit tests assert bitwise equality (`rtol=0, atol=0`) between the chunked results and the encoder output.

Local run of the three test files that import `mm_schedule`:

```
python -m pytest -q test/registered/chunked_prefill/test_mm_chunked_embedding_unit.py   # 28 passed
python -m pytest -q test/registered/unit/managers/test_mm_embedding_length.py test/registered/unit/models/test_kimi_k3_vision.py   # 34 passed
```

With the new test file run against unmodified `main`, the new cases fail (19 failed, 9 passed), so they guard the behaviour this change adds.

## Speed Tests and Profiling

No kernel change. A replayed multi-offset audio item is now a cache hit instead of a full re-encode, and a request's chunk is concatenated once instead of once per item plus once per request.
