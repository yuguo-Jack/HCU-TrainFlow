# [Fix] constrained: Do not cache grammar poll timeouts as invalid grammars

[Upstream PR](https://github.com/sgl-project/sglang/pull/45466) · state: closed · merged: True

## Original PR description

## Motivation

When a grammar request waits past `SGLANG_GRAMMAR_MAX_POLL_ITERATIONS`, `GrammarManager.get_ready_grammar_requests` caches `InvalidGrammarObject("Grammar preprocessing timed out")` for that key. `BaseGrammarBackend.get_cached_or_future_value` treats any cached object as a hit, so every later request with the same schema is aborted with `Failed to compile json grammar: Grammar preprocessing timed out` until `/flush_cache` (which needs an idle server) or a restart.

A timeout is not a property of the schema: the poll counter also runs while the compile waits in the shared executor queue, so one burst of load can permanently break a JSON schema or tool definition. This matches the symptom described in #17608, where `/flush_cache` was the workaround.

## Modifications

- Drop the cache write on the timeout path (`grammar_manager.py`). The request is still cancelled and aborted with the same message. Grammars the backend reports invalid are still cached.
- Rank consistency: the removed write ran after the TP all-gather and PP sync of ready/failed indexes, so the cache stays identical on every rank. The PD decode path calls the same `get_ready_grammar_requests`.

**Trade-off.** `Future.cancel()` cannot stop a compile that is already running.
- With xgrammar (default), the compiler cache shares an in-flight compile of the same schema and keeps its result (checked on xgrammar 0.2.7: 4 threads compiling one slow schema cost ~1 compile of CPU vs ~4x for 4 different schemas), so a retry after the compile finishes is cached normally.
- With llguidance, outlines, or framed reasoner grammars, a schema whose compile itself takes longer than the timeout (>= 50 s by default) is now recompiled on every request and can occupy the shared grammar executor under sustained traffic.
- The old negative entry did not bound this either: there is no in-flight dedup, so every request that arrived before the first timeout already submitted its own compile, and any whitespace change produces a new key.
- Per-key in-flight dedup would bound it; I'd do that as a follow-up. Caching the late result from a done-callback is not safe: it would write the cache at different times on different ranks and desync `grammar_queue` indexes.

Not changed here (follow-ups): the timeout abort still returns HTTP 400 (related to #45132); the `except Exception` branch on the ready path still caches unexpected exceptions as invalid.
