# [Perf] [AMD] GLM-5.3-Flash: Fewer DSA k-pool indexer launches in MTP verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44417) · state: open · merged: False

## Original PR description

## Summary

At concurrency 1 on MI355X, the DSA k-pool indexer in GLM-5.3-Flash's 11 sparse-attention layers costs more in small launches than in math: three GEMMs on one input with casts around them, and per-layer metadata rebuilt by index / arange / copy kernels that CUDA already fuses. This PR:

1. Stacks `wk`, the compress gate and `weights_proj` at load time; target verify projects once with an fp32-output `torch.mm`.
2. Enables CUDA's KPool metadata fusion, sibling replay copy and pooled page table on HIP.
3. Unrolls `kpool_topk_transform` row loads ×4 on ROCm.


| Kernel group, per decode step (profiler on) | Base (µs) | This PR (µs) |
| --- | --- | --- |
| Indexer GEMMs: `wk`, compress gate, `weights_proj` | 339.4 | **109.9** |
| Casts around them (`_to_copy`, bf16 ↔ fp32 copies, head-gate scale) | 225.2 | **74.0** |
| Metadata: `index`, `arange`, int elementwise, DtoD copies, `rocprim` | 642.2 | **218.0** |
| `kpool_topk_transform_kernel` | 280.4 | **256.3** |
| k_norm LayerNorm | 50.6 | 51.1 |

## Scope

HIP only; CUDA keeps today's paths. (1) is gfx950 only, for NoPE indexers whose `weights_proj` is bf16-exact, and off when LoRA wraps `wk` or `weights_proj`; `post_load_weights` refreshes the stack in place and rejects a `weights_proj` reload it cannot hold exactly. (2) reuses the metadata paths CUDA already runs; the fused replay copy covers every DSA model, the rest is k-pool only; the pooled page table is built for target verify only, since draft decode skips the indexer. (3) is `#ifdef USE_ROCM`; CUDA keeps one load per step. The KDA `cache_indices >= 0` mask deferral is left to #43861.

### inline_comments

- Raiden-Makoto · comment · 2026-10-20T00:14:26Z · [source](https://github.com/sgl-project/sglang/pull/44417#discussion_r4320179195)

File: `python/sglang/srt/layers/attention/dsa/dsa_indexer_kpool.py` · line 307

The initial fusion correctly refuses a non-BF16-exact FP32 `weights_proj`, but after `x_proj_weight` exists a reload only warns and then rounds the new FP32 weights into the BF16 stack. That silently changes model behavior for dynamic/partial weight updates.

Reproduced on MI355X at head `941642c9a040`: after creating the fused stack, adding a non-BF16-exact FP32 reload retained the same fused address and produced a 0.003272 max absolute head-weight difference from the unfused FP32 path. Please preserve the unfused path (and invalidate/recapture as needed) or reject such a reload, with coverage for this post-fusion case.

- Raiden-Makoto · comment · 2026-10-20T00:14:26Z · [source](https://github.com/sgl-project/sglang/pull/44417#discussion_r4320179205)

File: `python/sglang/srt/layers/attention/dsa/dsa_indexer_kpool.py` · line None

This selects the prepacked base-weight path solely from `x_proj_weight`, so LoRA deltas on `indexer.wk` or `indexer.weights_proj` are bypassed during target verify. Both modules are supported DSA LoRA targets, and the existing non-kpool fused path explicitly declines fusion when `set_lora` is set.

Reproduced on MI355X at head `941642c9a040`: setting `set_lora=True` with nonzero deltas still created `x_proj_weight`; fused versus LoRA-aware unfused output differed by max 2.324707 for key and 1.805089 for head weights. Please add the same admission guard here and cover target-verify output with either adapter active.
