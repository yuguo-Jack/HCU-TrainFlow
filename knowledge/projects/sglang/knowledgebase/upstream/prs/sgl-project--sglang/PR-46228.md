# [Perf] diffusion: Fuse Wan's q/k RMSNorm with its interleaved RoPE

[Upstream PR](https://github.com/sgl-project/sglang/pull/46228) · state: closed · merged: True

## Original PR description

Branch: mick/wan-fused-qk-norm-rope (on main 1e894eb92d), commit 75cc4e726b

## Motivation

Wan normalizes q and k across all heads (`qk_norm="rms_norm_across_heads"`) with FlashInfer's RMSNorm and then rotates them with FlashInfer's interleaved cos/sin-cache RoPE: three full passes over q and k in every block. On Wan2.2 A14B 720p (4xB300, 37800 x 5120 tokens per rank) they take 0.54 ms of each 55 ms block inside the denoising loop (RMSNorm 0.144 ms x 2, RoPE 0.255 ms, at the power-capped clock).

## Modifications

- `kernels/ops/diffusion/rope/rmsnorm_interleaved_rope_cutedsl.py`: `fused_rmsnorm_interleaved_rope_(x, weight, cos_sin_cache, eps, head_dim)`, in place on `x [M, H]` (row stride free). The norm part is FlashInfer's CuTe-DSL `RMSNormKernel` (single-CTA rows, same tiling, `row_reduce_sum_multirow`, fastmath rsqrt), so its bf16 output matches `flashinfer.norm.rmsnorm`; the store then rotates each (even, odd) pair of that bf16 output in fp32 with the RoPE kernel's expression (`a*c + (-b)*s`, `b*c + a*s`, row `m` at position `m % len(cache)`). Each thread's 8-column runs sit one head-multiple apart, so one 4-pair cos/sin slice (two 16-byte loads) serves all of them. `can_use_fused_rmsnorm_interleaved_rope` states the supported inputs; the kernel runs on torch's current stream.
- `models/dits/wanvideo.py`: `WanTransformerBlock._qkv_rope` projects q/k/v and, when the q/k norm runs FlashInfer's kernel (`forward_cuda`, no TP across heads) and the transformer supplies its cos/sin cache, applies the fused pass to q and k and tells `forward` to skip the RoPE. `_qkv` (used by Wan-Animate) keeps its behaviour.

## Accuracy Tests

- `test_rmsnorm_interleaved_rope.py`:
  - bitwise equal to `flashinfer.norm.rmsnorm` + `apply_flashinfer_rope_qk_inplace` (5120 / 3072 hidden, batch 1-2, rows padded apart as in a fused projection);
  - inputs produced on a side stream right before the call (it must run on torch's current stream);
  - a full Wan block (5120, 40 heads) gives the same bits with the fusion on and off;
  - unsupported inputs are rejected.
- Wan2.2 T2V A14B 720p, 4xB300, 3-step requests, lossless (crf 0) mp4: md5 identical to the base for 3 prompts.

## Speed Tests and Profiling

B300, q and k `[37800, 5120]` bf16, each call between 5120x5120 GEMMs at the power cap (median):

| | RMSNorm q | RMSNorm k | RoPE q+k | total |
|---|---|---|---|---|
| before | 0.144 ms | 0.144 ms | 0.255 ms | 0.542 ms |
| fused | 0.171 ms | 0.171 ms | - | 0.342 ms |

E2E, Wan2.2 T2V A14B 720p (81 frames, 40 steps), 4xB300, harness single_e2e (fresh server per run, runs interleaved with the base): this PR together with #46227 ("Walk several row chunks per warp in the CuTe-DSL norm kernels") took the request from 90.656 s (90.642 / 90.671) to 90.187 s (90.160 / 90.214), -0.47 s. The two changes were checked bitwise separately but timed together.
