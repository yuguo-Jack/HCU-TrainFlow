# [DSv4] Size the sparse prefill workspace per request, not num_reqs x longest

[Upstream PR](https://github.com/sgl-project/sglang/pull/43726) · state: closed · merged: False

## Original PR description

## Motivation

On DeepSeek-V4.1-Flash, a long prompt in chunked prefill that shares prefill batches with many short requests crashes the TP group with an OOM in the sparse-prefill workspace:

```
deepseek_v4_backend.py  _forward_prefill_sparse
  -> dsv4/sparse_prefill_utils.py  SparsePrefillWorkspace.get -> torch.empty(...)
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 10.29 GiB.
GPU 0 has a total capacity of 178.35 GiB of which 8.03 GiB is free.
```

Setup: B200, TP4/EP4, `--mem-fraction-static 0.80`, chunked prefill 8192. The crashing load is one ~820K-token prompt plus 40 concurrent tiny requests. The prefill batches just before the crash had 17–25 sequences, e.g. `#new-seq: 21, #new-token: 5772`. #41076 is the same allocation (27.2 GiB on TP2 B300).

Capping `--prefill-max-requests` avoids the crash but starves the long prompt under a stream of small requests. With a cap of 4, the long prompt took 272 s (820K) and 473 s (~900K) to complete under that load, against 83 s and 123 s with this change and no cap (table below).

## Root cause

`SparsePrefillChunkCache._workspace_bases`, `ensure_compressed` and `ensure_c128` give every request a compressed region of `c_max = max_seq_len // ratio`. That pads each request to the longest one in the batch. The bf16 workspace is therefore `num_reqs * (max_seq_len // ratio)` plus SWA rows, at 1 KiB per row.

- About 26 requests with the longest at ~820K gives about 10.7M rows on a ratio-2 layer (the 10.29 GiB above). The ratio-1 layers would need about twice that.
- `SparsePrefillWorkspace.get` also allocates the larger buffer while the old one is still referenced, so every growth step peaks at old + new.

## Modifications

- **Pack each request at its own length.** A query at position `pos` only reads compressed positions below `(pos + 1) // ratio <= seq_len // ratio`. `flash_mla_sparse_fwd` takes a flat `kv` with per-query indices, and `combine_topk_swa_indices` already takes a per-request `compressed_base`. So each request's compressed region is packed at `max(seq_len // ratio, 1)` rows, back to back, with the SWA gather after the last request.
  - The bases are an exclusive cumsum.
  - The total comes from the host `seq_lens_cpu` that both backends now pass into `SparsePrefillChunkCache.build`, so this adds no device sync. Without it, the code falls back to `seq_lens.tolist()`.
- **No kernel changes.** Every query's index list resolves to the same physical cache rows in the same order.
- **Free before growing.** `SparsePrefillWorkspace.get` drops the old buffer before allocating a larger one.

For the repro batch above, the workspace drops from about `num_reqs * max` rows to about `sum(seq_len) // ratio` rows, roughly the size the long request alone needs. The per-layer dequant into the workspace shrinks by the same factor.

## Accuracy Tests

New CPU test `test/registered/unit/layers/test_dsv4_sparse_prefill_workspace.py`:

- **Sizing.** 1 × 820K + 20 short requests: the workspace equals the per-request sum and stays within the long request's own size plus a small bound per short request. On `main` it fails: 17.2M rows vs 825K at ratio 1.
- **Index mapping.** Every combined index resolves to its own request's page-table token id and SWA id, for ratios 1, 2, 4 and c128, checked against a torch reference combine.
- **Host vs device.** The host-length path and the device fallback agree.
- **Growth.** Growing the workspace releases the old buffer first.

The existing `test_sparse_prefill_c4/c128_uses_live_extent` tests pass unchanged. In an old-vs-new equivalence check over 40 random batches for each of ratios 1, 2 and 4 plus c128, all 160 cases resolve to identical physical ids.

GPU validation used DeepSeek-V4.1-Flash on 8×B200 (TP4/EP4, mem 0.80, no request cap), with this change applied as a file overlay on a nightly from Sep 22 (`4cbf290f`). The same box ran first without the change, then with it:

| Check | Without this change | With this change |
|---|---|---|
| ~820K prompt + 40 concurrent tiny requests | OOM after 45 s | completed in 82.9 s; 6,242 tiny requests, 0 errors |
| ~900K prompt (context limit 906K) + same flood | — | completed in 123.4 s; 8,428 tiny requests, 0 errors |
| Needle retrieval, greedy bs=1, 8K–800K + multi-turn cached prefix | all found | all found |
| Needle retrieval, 14 prompts of 8K–400K + 20 short, sent at once | 14/14, 20/20 | 14/14, 20/20 |

GPU memory stayed flat across both flood runs.

## Speed Tests and Profiling

- **Flood load** (same box and engine, no request cap): the ~820K and ~900K prompts complete in 82.9 s and 123.4 s while 40 tiny requests keep streaming. The `--prefill-max-requests 4` workaround took 272 s and 473 s on the same load, and the unfixed engine OOMs.
- **Expected but not measured:** the per-layer dequant into the workspace shrinks with it, so mixed batches should prefill faster.
- **Should be unchanged:** single-request and uniform batches are the same size as before; the extra metadata work is one `repeat_interleave` and a gather per ratio per chunk.
- **Not done:** nsys profile and single-request 1M TTFT comparison.

## Not covered yet / follow-ups

- **Validation gaps:**
  - a bitwise comparison of `_forward_prefill_sparse` outputs between the old and new layouts on GPU;
  - GSM8K;
  - the SM90 Q8KV8 path;
  - the HIP OPUS path, whose `_opus_prefill_applies` still estimates padded rows; that is now a conservative overestimate;
  - context-parallel prefill;
  - an nsys check of metadata building.
- **Still unbounded:** a batch of many requests that are *all* long, as in #41076's queue of 170–212K prompts. Splitting the prefill batch into request groups under a row budget would close it (same idea as #40217 for the indexer). That could be a follow-up or go into this PR, whichever reviewers prefer.
- **Interaction with #42929:** that PR keys a dequant memo partly on the workspace's data pointer. Since this change frees the old buffer before growing, a new buffer can reuse the old address, so that memo should key on a buffer generation counter.

Refs #41076.
