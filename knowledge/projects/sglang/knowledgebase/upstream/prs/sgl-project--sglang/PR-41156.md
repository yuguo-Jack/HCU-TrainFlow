# [Fix] parser: Strip drifted </parameter> markers in the qwen3_coder detector

[Upstream PR](https://github.com/sgl-project/sglang/pull/41156) · state: open · merged: False

## Original PR description

## Motivation

Detector-side hardening for #27336 (auto-closed by inactivity; the earlier detector PR #27337 went stale). @JustinTong0323 on that issue: "Worth keeping both: the detector hardening as a safety net, and the grammar fix for the root cause." The grammar fix (mlc-ai/xgrammar#651) is still open.

With `--tool-call-parser qwen3_coder` and `tool_choice="required"`, arguments come back with the close marker inside the value, e.g. `{"city": "Shanghai\n</parameter1>"}`; `</parameter_function>` and a bare `</parameter` were also observed. As discussed on the issue, the origin is the structural tag: the grammar only pins the `</parameter` prefix, so the model can finish the marker any way it likes. Both detector paths look for the exact `</parameter>` token; when it never appears, the value runs on to the next `<parameter=` / `</function>` and the drifted marker stays inside the argument. Clients that validate arguments against the tool schema reject the call; clients that do not run the tool with a polluted string.

The grammar-side fix lives in xgrammar. This PR is the detector-level safety net the issue asks for, so that a call which does complete yields a clean value.

## Modifications

`python/sglang/srt/function_call/qwen3_coder_detector.py`:
- One compiled regex, `malformed_parameter_end_regex = r"\s*</parameter(?!>)[^<>]*>?\s*$"`: a trailing `</parameter` that is not the well-formed `</parameter>`, followed by non-bracket characters and an optional `>`. `[^<>]*` keeps it from eating tags that are legitimately part of the value.
- `_clean_param_value(raw_value)`: strips one such trailer, then the existing newline trim. Both the non-streaming regex path and the streaming cursor path call it, so the two paths cannot diverge again.

`test/registered/unit/function_call/test_qwen3_coder_detector.py` (new file; no unit test covered this detector):
- non-streaming: three drifted markers, each yields `{"city": "Shanghai", "days": 3}`
- streaming in 3-character chunks with a drifted marker: same result
- well-formed `</parameter>`: unchanged
- angle brackets inside a value (`a <b>tag</b> city`): preserved

The two drifted-marker cases fail on `main` with `{'city': 'Shanghai\n</parameter1>', ...}`, the reported symptom; the two guard cases pass on both, which is what shows the regex does not over-strip.

**Related open PRs.** None of them handles drifted close markers, but some touch the same file. #38624 (phantom tool calls from quoted markup) also adds `test/registered/unit/function_call/test_qwen3_coder_detector.py`, and it and #36835 edit the streaming path near the hunk changed here; whichever lands first, I'll rebase and merge the test classes. #40741 / #40778 change the text after `</tool_call>` in `detect_and_parse`, not parameter values.

Existing detector tests: `pytest test/registered/unit/function_call/` gives the same results with and without this change (the new file adds 4 passing tests; no previously passing test changes).
