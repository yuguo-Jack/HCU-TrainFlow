# fix(bf16-gemm): route gemv backend through UnquantizedLinearMethod.apply

[Upstream PR](https://github.com/sgl-project/sglang/pull/42124) · state: open · merged: False

## Original PR description

## Motivation

Fixes #42085 — credit to @SamMausberg for the analysis and the GH200 microbenchmark.

`--bf16-gemm-backend gemv` loads the Hopper BF16 GEMV in `initialize_bf16_gemm_config`, but `UnquantizedLinearMethod.apply` only consults `_bf16_gemm_dispatch_impl` when the backend is `cutedsl` (the `is_cutedsl()`-only gate), so on SM90 the server accepts the flag while every ordinary unquantized linear layer — e.g. all of Qwen3.5's — still runs on cuBLAS. The issue's CPU stub repro shows the gap directly: `apply` makes 0 GEMV calls while the dispatcher routes 1.

## Modifications

- `UnquantizedLinearMethod.apply`: extend the dispatch gate to accept `gemv` alongside `cutedsl`. The dispatcher's own predicates (`M == 1`, `bias is None`) already provide the cuBLAS fallbacks, so biased linears and larger batches keep their current path. `apply_into` is deliberately untouched — the Hopper GEMV has no `out=` variant.
- `initialize_bf16_gemm_config`: reject `gemv` under `--enable-deterministic-inference`, mirroring the existing `cutedsl` rejection — the kernel serves only `M = 1`, so a request's outputs would depend on whether it was decoded alone. (Flagged in the issue by @SamMausberg.)
- `--bf16-gemm-backend` help text: document what `gemv` actually covers and its deterministic-inference incompatibility, instead of listing it as a bare choice.

## Accuracy Tests

No output changes on any path that keeps its current behavior — the fallbacks go through the same `F.linear` call as before. On the new dispatch path, verified (CPU, stubbed kernel, mirroring the issue's repro) that the routed output is bitwise-equal to `F.linear` for the single-row case, and that `M > 1` and biased linears do not reach the kernel. New unit tests in `test/registered/unit/layers/quantization/test_unquant_apply_gemv_dispatch.py` (CUDA CI): single-row dispatch reaches the gemv path, `M = 4` and biased linears fall back to cuBLAS, and the deterministic-inference rejection is exercised — that rejection test is red on main and green with this PR.

## Speed Tests and Profiling

No new measurements in this PR. The motivation is @SamMausberg's per-GEMM GH200 (SM90) microbenchmark from the issue (e.g. 8.57 us vs 11.20 us for cuBLAS on a 2560x4096 `out_proj` at M = 1, outputs bitwise-equal on 99.6-100% of elements); serving-level impact is left for maintainers to assess on real hardware.
