# Fix HF3FS metadata reservation at capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/42059) · state: open · merged: False

## Original PR description

## Motivation

HF3FS metadata allocation raises `KeyError` when a batch consumes all free pages and there are no confirmed pages to evict. Allocations made earlier in that request are lost to the caller. For example, reserving three keys in a two-page namespace returns HTTP 500 and leaves that namespace with no usable pages. Overlapping unconfirmed write batches can also reach this state.

## Modifications

Return `(False, -1)` for keys that cannot be allocated, preserving the successful reservations in the response. Both existing HF3FS write paths already skip this sentinel and return `False` for that key, so callers can confirm successful writes or release failed writes normally. Add CPU tests for capacity exhaustion, overlapping reservations, recovery, existing-key/LRU behavior, and the HTTP response.

## Accuracy Tests

- New tests: **5 failed / 1 passed before; 6 passed after**.
- Exercised both actual backend write methods with the project's file-backed `Hf3fsMockClient`: a three-key batch in two pages returns `[True, True, False]`, successful pages read back correctly, and the refused key can be retried.
- Local CPU harnesses load unchanged metadata classes and backend methods from source while excluding unrelated GPU/native import initializers. Native 3FS and GPU inference were not run.

## Speed Tests and Profiling
