# [Perf] qknorm: run head_dim-128 rows two per warp with 16B lanes, bit-identical

[Upstream PR](https://github.com/sgl-project/sglang/pull/45214) · state: closed · merged: True

## Original PR description

## Motivation

In short: `fused_qknorm_warp` is the default QK-norm for Qwen3 dense and Qwen3-MoE on CUDA. At head_dim 128 it gives each warp one (token, head) row, so a lane moves only 8 B per row. This PR runs two rows per warp with 16 B lanes, the same scheme mickqian merged for the diffusion QK-norm + RoPE kernel. The output is bit-identical. On an H100 NVL the kernel is 1.09-1.45x faster from 32 tokens up, and 1.29x inside a Qwen3-8B prefill trace; serving throughput is flat because the kernel is under 1% of GPU time.

Details:

`fused_qknorm_warp` (`python/sglang/kernels/jit/csrc/elementwise/qknorm.cuh`) runs through `apply_qk_norm` in `python/sglang/srt/models/utils.py`. Per row it does a load, a 5-step xor reduce, an rsqrt and a store, then moves to the next row. With 8 B per lane that is at most 64 warps x 32 lanes x 8 B = 16 KB in flight per SM, and out of L2 the kernel reaches 2.8-2.9 TB/s on an H100 NVL.

## Modifications

In short: a new `fused_qknorm_half_warp` kernel for head_dim 128, picked at compile time. Each row gets 16 lanes and each lane moves 16 B. Every other head_dim, the CTA path and ROCm keep their current kernels.

How it stays bit-identical: each lane covers two lanes of the warp kernel. It keeps their two partial sums, accumulated in the same order, and replays that kernel's xor butterfly with `warp::reduce_sum<16>` (the same `Trait::reduce` as before). Offsets 16..2 become 8..1 on each partial, and the final xor-1 step becomes `part0 + part1`. The rsqrt and the per-element output are the same expressions.

Changes:

- `fused_qknorm_half_warp`: two rows per warp; a missing second row recomputes the last one and skips its store.
- The new kernel needs 16 B alignment where the warp kernel needed 8 B. If a q/k or weight pointer, or a q/k row stride, is not 16 B aligned, the launcher keeps the one-row-per-warp kernel, so every input that ran before still runs.
- `_jit_qknorm_module(half_warp=False)` builds the one-row-per-warp kernel, for the new test.
- New test `test_two_rows_per_warp_match_one_row_per_warp`: byte-compares the two kernels with q and k sliced from one qkv row as Qwen3 passes them, BF16 and FP16, 5 q heads so a q/k boundary falls inside a row pair, an odd row count, 4099 tokens so the persistent grid loops, and rows padded by 8 B so odd-token rows are only 8 B aligned and the launcher falls back.

Same scheme as [#43337](https://github.com/sgl-project/sglang/pull/43337) and [#43508](https://github.com/sgl-project/sglang/pull/43508), which changed only the diffusion `qknorm_rope.cuh`.

Not a duplicate: no PR runs `fused_qknorm_warp` two rows per warp. The open [#43425](https://github.com/sgl-project/sglang/pull/43425) refactors `fused_qknorm_warp` into a per-row helper with an epilogue hook for Qwen3-VL MRoPE fusion on Blackwell; it keeps the 8 B lane layout, but the two PRs will conflict in `qknorm.cuh`, so whichever lands second needs a rebase. [#39071](https://github.com/sgl-project/sglang/pull/39071) and [#40585](https://github.com/sgl-project/sglang/pull/40585) touch this file only for ROCm `#include` lines.

## Accuracy Tests

The output is bit-identical to main, so model accuracy can't change. I checked it at the kernel level:

- Bitwise vs main 97d3150a6a, CPU-seeded inputs, whole qkv buffer compared: 384 cases, each run with both branch kernels, **768 of 768 identical**. The two-rows kernel runs in 192 of them (head_dim 128: Qwen3-8B, Qwen3-30B-A3B, TP2 and ragged head counts, 1 to 16384 tokens, qkv-slice and contiguous layouts, BF16 and FP16, with and without PDL). The rest cover the 8 B-aligned fallback and head_dim 64 and 256, which are unchanged.
- `test_qknorm.py` and `test_rope.py`: 1827 passed. `test_rope.py` uses `fused_inplace_qknorm` as its `torch.equal` reference.
- Registers: 28 -> 40 per thread, 0 spills.

## Speed Tests and Profiling

H100 NVL (PCIe, 400 W), driver 595.91, CUDA 13.0, torch 2.14.1+cu130. Validated on main 97d3150a6a; the branch is rebased onto 5ed306bd69, and upstream only removed unused helpers from `norm.py` and `test_qknorm.py` in between. `triton.testing.do_bench_cudagraph`, median of 5 rounds that interleave the two kernels in one process. q and k are slices of one qkv row (Qwen3 layout), BF16, in place.

| tokens | Qwen3-8B (32 + 8 heads) | Qwen3-30B-A3B (32 + 4 heads) |

| 256 | 4.31 -> 3.19 us (1.35x) | 4.38 -> 3.02 us (1.45x) |
| 1024 | 6.31 -> 5.32 us (1.19x) | 6.11 -> 4.98 us (1.23x) |
| 2048 | 11.13 -> 8.39 us (1.33x) | 10.33 -> 7.84 us (1.32x) |
| 4096 | 25.96 -> 22.18 us (1.17x) | 22.13 -> 17.86 us (1.24x) |

| 65536 | 459.86 -> 414.60 us (1.11x) | 417.29 -> 374.92 us (1.11x) |

Over BF16 and FP16, both models and 1-65536 tokens: geomean 1.14x up to 256 tokens (0.95-1.45x) and 1.17x from 512 tokens (1.09-1.36x). From 8192 tokens q and k no longer fit in L2, and the kernel goes from 2.8-2.9 TB/s to 3.1-3.3 TB/s. At 1-8 tokens the difference is 0.03-0.08 us, the same spread as two runs of the same kernel.

In a model: torch profiler, Qwen3-8B TP1, 32 requests of 4096 input tokens. The QK-norm kernel goes from 43.82 to 34.09 ms over 720 launches (1.29x), from 0.94% to 0.73% of GPU time. `sglang.benchmark.serving` on the same model, 3 interleaved rounds, is flat: random 4096/1 input throughput 26597 -> 26567 tok/s (-0.11%) and random 1024/128 19.94 -> 19.93 req/s (-0.07%), while main alone moves 0.6-0.7% between rounds.
