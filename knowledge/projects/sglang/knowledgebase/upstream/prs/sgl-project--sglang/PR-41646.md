# [Feat] afd: Add attention–FFN disaggregation with pipelining and CUDA Graph support

[Upstream PR](https://github.com/sgl-project/sglang/pull/41646) · state: open · merged: False

## Original PR description

Add Qwen3 MoE and GLM MoE-DSA support with separate attention/FFN GPU groups, two-stage overlap and coordinated CUDA Graphs.

## Motivation

Attention and FFN have different memory and compute demands. Separating their execution lets deployments size the two GPU groups independently and overlap their work. This opt-in implementation keeps requests and KV on attention ranks while reusing native SGLang scheduling, sampling, HTTP, model operators and CPU overlap.

See [Issue #41648](https://github.com/sgl-project/sglang/issues/41648) for the detailed motivation, hardware resource matching, design trade-offs and roadmap. This PR focuses on the implementation and validation.

## Modifications

| Area | Implementation |
|---|---|
| Models | Qwen3 MoE and GLM MoE-DSA; router and experts run on F |
| Topology | M attention ranks and N FFN ranks, with M ≥ N and M divisible by N |
| Scheduling | Native scheduling and CPU overlap on A; a dedicated FFN service on F |
| Pipeline | Two microbatches (S2) through the native two-batch executor |
| CUDA Graphs | Per-role capture includes A/F communication; ranks finish startup capture before serving requests |
| Communication | PyNccl and StatelessProcessGroup, with peer validation and bounded shutdown |
| Reuse | Native model operators, batch helpers, graph pools and input preparation |

DeepEP, speculative decoding and A-side routing are outside this PR's scope. Model/backend combinations are checked at startup.

## Speed Tests and Profiling

Representative GPU (SM103) validation results are organized into three groups. `q_G = B / G`, where B is total concurrency and G includes all execution GPUs, both A and F. Throughput change is `(AFD / Native − 1) × 100%`.

### 1. Triton MoE

Submission: `c49726`. Triton MoE, DeepEP/MegaMoE/MTP OFF, OSL768. Attention: Qwen FA4; GLM NSA/DSA.

| Model / ISL | Layout / total GPUs | B | Batch / #GPUs | Decode tokens/s/GPU | TGS Change vs Native (higher is better) |
|---|---|---:|---:|---:|---:|
| Qwen3-235B / 39936 | 8A2F / 10 | 232 | 23.20 | 531.552 | +6.11% |
| Same | Native / 4 | 64 | 16.00 | 500.965 | — |
| GLM-5 / 39936 | 20A32F / 52 | 2120 | 40.77 | 529.025 | -7.82% |
| Same | Native / 8 | 192 | 24.00 | 573.908 | — |

Batch/#GPUs can be higher in AFD than in native execution because moving expert weights to F frees A-side memory for KV caches, enabling larger batches in capacity-bound long-context workloads.

### 3. MegaMoE

Submission: `f47bfa`. Using our plugin interface, we integrated the MegaMoE/M2N backend used in [#45562](https://github.com/sgl-project/sglang/pull/45562), with the M2N implementation from [DeepGEMM #110](https://github.com/sgl-project/DeepGEMM/pull/110), and obtained similar measured throughput.

Our AFD uses 8A8F / sixteen GPUs, S2, FP8 KV and TRTLLM for prefill and decode: MHA for Qwen3-235B and DSA for GLM-5. MegaMoE/M2N is ON; DeepEP and MTP are OFF. The Qwen Native references use eight GPUs with DeepEP or MegaMoE, as labeled.

Native throughput also differs substantially between DeepEP and MegaMoE. An AFD-only ablation experiment should therefore compare Native MegaMoE with AFD MegaMoE/M2N at matched precision, attention, cache policy and load.

### Reproduce with launch commands and the community benchmark

Use the source commit above, matching CUDA/NCCL dependencies, local model weights and a configured GPU NVLink/IMEX environment. Apply the same environment settings to native and AFD.

The commands below are a **serving smoke test** using `sglang.launch_server` and the official benchmark: context 2,048, input 1,024, output 128, 32 requests and concurrency 16. They do not reproduce the long-context performance table.

<details>
<summary>Qwen3-235B-A22B-FP8: 8A2F / native4</summary>

Set the model path on each node and replace the example IPs with reachable addresses.

```bash
MODEL=/path/to/Qwen3-235B-A22B-FP8
A_HEAD=192.0.2.10
# Replace rendezvous_host below with the F node address on every node.
AFD_CONFIG='{"stages":2,"max_hbm_bytes":8589934592,"attention_backend":"fa4","lanes":2,"attention_lanes":8,"nccl_num_channels":8,"rendezvous_host":"192.0.2.12","rendezvous_port":28219,"rendezvous_timeout_seconds":1800,"idle_timeout_seconds":86400,"close_timeout_seconds":30}'
COMMON=(
  --model-path "$MODEL"
  --tokenizer-path "$MODEL"
  --served-model-name qwen3-235b-modelopt-fp8
  --quantization modelopt_fp8
  --dtype bfloat16
  --kv-cache-dtype bfloat16
  --context-length 2048
  --moe-a2a-backend none
  --moe-runner-backend triton
  --attention-backend fa4
  --page-size 128
  --chunked-prefill-size 8192
  --max-running-requests 32
  --decode-log-interval 8
  --watchdog-timeout 1800
  --dist-timeout 1800
  --host 127.0.0.1
  --port 28200
  --nccl-port 28210
  --cuda-graph-backend-prefill disabled
  --cuda-graph-backend-decode full
  --disable-flashinfer-autotune
  --disable-shared-experts-fusion
)
```

Start F first, then A on both four-GPU nodes with `NODE_RANK=0` / `1`, using separate terminals.

```bash
# F node
CUDA_VISIBLE_DEVICES=0,1 python3 -m sglang.launch_server "${COMMON[@]}" \
  --tp-size 2 \
  --dp-size 1 \
  --ep-size 2 \
  --nnodes 1 \
  --node-rank 0 \
  --cuda-graph-bs-decode 2 4 8 \
  --cuda-graph-max-bs-decode 8 \
  --afd-execution-mode ffn \
  --afd-config "$AFD_CONFIG"

# Each A node: 0 on the head node, 1 on the second node
NODE_RANK=0
CUDA_VISIBLE_DEVICES=0,1,2,3 python3 -m sglang.launch_server "${COMMON[@]}" \
  --tp-size 8 \
  --dp-size 8 \
  --ep-size 1 \
  --nnodes 2 \
  --node-rank "$NODE_RANK" \
  --enable-dp-attention \
  --dist-init-addr "$A_HEAD:28201" \
  --cuda-graph-bs-decode 2 4 8 \
  --cuda-graph-max-bs-decode 8 \
  --afd-execution-mode attention \
  --afd-config "$AFD_CONFIG"
```

For native, stop and verify cleanup of the AFD deployment first, then use the following alternative on the head node only:

```bash
NODE_RANK=0
CUDA_VISIBLE_DEVICES=0,1,2,3 python3 -m sglang.launch_server "${COMMON[@]}" \
  --tp-size 4 \
  --dp-size 4 \
  --ep-size 4 \
  --nnodes 1 \
  --node-rank "$NODE_RANK" \
  --enable-dp-attention \
  --dist-init-addr "$A_HEAD:28201" \

  --cuda-graph-bs-decode 2 4 8 16 32
```

> I noticed that this PR now integrates the MegaMoE/M2N backend from our AFD implementation in [[#45562](https://github.com/sgl-project/sglang/pull/45562)](#45562), together with our M2N implementation in [[DeepGEMM #110](https://github.com/sgl-project/DeepGEMM/pull/110)]([sgl-project/DeepGEMM#110](https://github.com/sgl-project/DeepGEMM/pull/110)). Both are part of our team’s AFD work. Thanks for evaluating these components and reporting comparable throughput through your plugin interface.
> 
> We’d welcome you and anyone else interested in AFD to join the discussion in our [[RFC and roadmap](https://github.com/sgl-project/sglang/issues/45568)](#45568) or [[implementation PR](https://github.com/sgl-project/sglang/pull/45562)](#45562). Feedback, ideas, and code contributions are all welcome.

Thanks for sharing your team’s work. Our PR already acknowledges [#45562](https://github.com/sgl-project/sglang/pull/45562) and the underlying M2N implementation in [DeepGEMM #110](https://github.com/sgl-project/DeepGEMM/pull/110), with source attribution included in the relevant code.

This integration is experimental: our goal is to evaluate these components through our AFD plugin interface and compare performance under aligned configurations. Our earlier PR [#41646](https://github.com/sgl-project/sglang/pull/41646) explored integration with SGLang’s native scheduling, multi-lane execution, and coordinated CUDA graphs.

We’re now emphasizing pluggable FFN backends and communication interfaces to accommodate more hardware vendors and explore heterogeneous A/F deployments. We’re also using SGLang Simulator and roofline analysis to search for promising hardware and execution configurations, alongside further DeepEP and MegaMoE integration approaches.

We’d be very happy to collaborate and join the discussion, particularly on communication interfaces and execution backend design. Our testing has also identified performance bottlenecks in both AFD implementations and the MegaMoE paths; joint profiling and optimization would be a valuable opportunity to move these efforts forward together.
