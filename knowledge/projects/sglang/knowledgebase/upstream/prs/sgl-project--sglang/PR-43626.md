# [Performance] GGUF: dequantize + dense GEMM for large batches instead of MMQ

[Upstream PR](https://github.com/sgl-project/sglang/pull/43626) · state: open · merged: False

## Original PR description

## Motivation

`fused_mul_mat_gguf` sends standard and K-quant GGUF matmuls to MMQ (`ggml_mul_mat_a8`) for every batch larger than the MMVQ cutoff. MMQ's time grows linearly with the number of input rows. A prefill chunk has thousands of rows, so the GGUF linear layers become the bottleneck there.

The other option is to dequantize the weight once and run a dense bf16 GEMM, the path that I-Matrix types already take. That option has a mostly fixed cost, the dequantization, and it wins clearly once the batch is large. Measured on an RTX 5070 Ti (sm_120), as the time per call of a 4096 x 2048 matrix with weights cycled from DRAM:

| rows | Q4_K MMQ | Q4_K dequant + GEMM | Q6_K MMQ | Q6_K dequant + GEMM |
|---|---|---|---|---|
| 16 | 0.051 ms | 0.058 ms | 0.065 ms | 0.063 ms |
| 64 | 0.134 ms | 0.060 ms | 0.170 ms | 0.058 ms |
| 256 | 0.465 ms | 0.094 ms | 0.589 ms | 0.093 ms |
| 1024 | 1.80 ms | 0.24 ms | 2.28 ms | 0.24 ms |
| 4096 | 7.17 ms | 0.82 ms | 9.18 ms | 0.83 ms |
| 16384 | 28.9 ms | 2.98 ms | 36.6 ms | 2.97 ms |

At prefill sizes the dense path is about 10x faster.

## Modifications

All changes are in `python/sglang/srt/layers/quantization/gguf.py`:

- Two module-level constants, `DEQUANT_MIN_ROWS = 48` and `DEQUANT_MIN_WORK = 1 << 29`.
- In `fused_mul_mat_gguf`, after the MMVQ branch, a batch of a `DEQUANT_TYPES` type goes through the existing `dequantize_gguf_weight` + `x @ weight.T` path when both of these hold:
  - it has at least `DEQUANT_MIN_ROWS` rows, and
  - `rows * weights` (rows × out_features × in_features) is at least `DEQUANT_MIN_WORK`.
- Smaller batches keep MMQ, and decode keeps MMVQ.

The second condition is there because the dequantization has a fixed cost (about 57 µs on this GPU). For small matrices, MMQ stays ahead until more rows have arrived. Measured crossovers on this GPU, over Q2_K, Q3_K, Q4_0, Q4_K, Q5_K, Q6_K and Q8_0:

| matrix | weights | dequant + GEMM as fast or faster from |
|---|---|---|
| 1024 x 1024, 2048 x 512, 512 x 2048 | 1M | ~192-512 rows |
| 4096 x 2048, 2048 x 4096 | 8M | ~24-48 rows |
| 11008 x 4096 | 45M | ~32-48 rows |

The rule switches 1M-weight matrices at 512 rows, 8M at 64, and 45M at 48. In every case measured, it picks the dense path only where that path is as fast or faster than MMQ. The thresholds were measured on this one GPU, and other GPUs may cross over elsewhere.

The dequantized weight is a transient bf16 tensor, the same as on the existing I-Matrix path.

## Accuracy Tests

The dense path does not quantize the activations to q8_1, so it is more accurate than MMQ. The table shows relative L2 error against an fp32 reference (fp32 activations @ fp32 dequantized weights), for a 4096 x 2048 matrix at 256 rows:

| type | MMQ | dequant + bf16 GEMM |
|---|---|---|
| Q4_K | 6.0e-3 | 2.4e-3 |
| Q5_K | 5.9e-3 | 2.4e-3 |
| Q6_K | 5.6e-3 | 2.3e-3 |
| Q8_0 | 5.6e-3 | 1.7e-3 |
| Q4_0 | 1.0e-2 | 1.7e-3 |
| Q2_K | 5.6e-3 | 1.7e-3 |
| Q3_K | 5.6e-3 | 1.7e-3 |

## Speed Tests and Profiling

The kernel-level numbers are above. End to end, in our serving tree (SGLang with a KTransformers CPU/GPU hybrid MoE, so not upstream main itself), the same change took a 35K-token prefill of a GGUF model with Q4_K / Q5_K / Q6_K dense layers, TP2 on 2x RTX 5070 Ti, from 2,100 to 4,036-4,172 tok/s. That tree used a plain 64-row threshold.
