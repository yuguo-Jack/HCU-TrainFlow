# [Perf] GGUF: dequantize + dense GEMM for large batches instead of MMQ

[Upstream PR](https://github.com/sgl-project/sglang/pull/43626) · state: open · merged: False

## Original PR description

## Motivation

`fused_mul_mat_gguf` sends standard and K-quant GGUF matmuls to MMQ (`ggml_mul_mat_a8`) for every batch larger than the MMVQ cutoff. MMQ's time grows linearly with the number of input rows. A prefill chunk has thousands of rows, so the GGUF linear layers become the bottleneck there.

The other option is to dequantize the weight once and run a dense bf16 GEMM, the path that I-Matrix types already take. That option has a mostly fixed cost, the dequantization, which even a small batch amortizes. Measured on an RTX 5070 Ti (sm_120) as the time per call of a 4096 x 2048 matrix, timed in CUDA graphs with weights cycled from DRAM:

| rows | Q4_K MMQ | Q4_K dequant + GEMM | Q6_K MMQ | Q6_K dequant + GEMM |
|---|---|---|---|---|
| 16 | 0.034 ms | 0.032 ms | 0.048 ms | 0.027 ms |
| 64 | 0.118 ms | 0.035 ms | 0.154 ms | 0.030 ms |
| 256 | 0.453 ms | 0.071 ms | 0.584 ms | 0.067 ms |
| 1024 | 1.82 ms | 0.22 ms | 2.31 ms | 0.22 ms |
| 4096 | 7.29 ms | 0.81 ms | 9.21 ms | 0.81 ms |
| 16384 | 29.1 ms | 2.96 ms | 36.8 ms | 2.96 ms |

At prefill sizes the dense path is about 10x faster.

## Modifications

All changes are in `python/sglang/srt/layers/quantization/gguf.py`:

- One module-level constant, `DEQUANT_MIN_ROWS = 16`.
- In `fused_mul_mat_gguf`, after the MMVQ branch, a batch of a `DEQUANT_TYPES` type with at least `DEQUANT_MIN_ROWS` rows goes through the existing `dequantize_gguf_weight` + `x @ weight.T` path.
- Smaller batches keep MMQ, and decode keeps MMVQ.

Crossovers on this GPU, over Q2_K, Q3_K, Q4_0, Q4_K, Q5_K, Q6_K and Q8_0, 17 row counts from 16 to 16384, two passes in opposite order that pick the same winner in 357 of 357 cells:

| matrix | weights | dequant + GEMM as fast or faster from |
|---|---|---|
| 1024 x 1024 | 1M | 16-48 rows |
| 4096 x 2048 | 8M | 16-32 rows |
| 11008 x 4096 | 45M | 24-48 rows |

Summed slowdown over those cells, sum(chosen / best - 1): this rule (dense from 16 rows) 10.1, dense from 48 rows 25.3, the earlier version of this PR (48 rows and rows x weights >= 2^29) 160.3, MMQ throughout 1698.9. The earlier version's floor for small matrices came from eager per-call timing, which counted launch overhead and left small weights in L2; the review below found the same crossover on an RTX PRO 6000 Blackwell (48 rows or fewer).

The dequantized weight is a transient bf16 tensor, the same as on the existing I-Matrix path.

## Accuracy Tests

The dense path does not quantize the activations to q8_1, so it is more accurate than MMQ. The table shows relative L2 error against an fp32 reference (fp32 activations @ fp32 dequantized weights), for a 4096 x 2048 matrix at 256 rows:

| type | MMQ | dequant + bf16 GEMM |
|---|---|---|
| Q4_K | 6.0e-3 | 2.4e-3 |
| Q5_K | 5.9e-3 | 2.4e-3 |
| Q6_K | 5.6e-3 | 2.3e-3 |
| Q8_0 | 5.6e-3 | 1.7e-3 |
| Q4_0 | 1.0e-2 | 1.7e-3 |
| Q2_K | 5.6e-3 | 1.7e-3 |
| Q3_K | 5.6e-3 | 1.7e-3 |

## Speed Tests and Profiling

The kernel-level numbers are above. End to end, in our serving tree (SGLang with a KTransformers CPU/GPU hybrid MoE, so not upstream main itself), the same change took a 35K-token prefill of a GGUF model with Q4_K / Q5_K / Q6_K dense layers, TP2 on 2x RTX 5070 Ti, from 2,100 to 4,036-4,172 tok/s. That tree used a plain 64-row threshold.
