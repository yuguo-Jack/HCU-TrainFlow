# [Fix] metrics: Populate the pending_prealloc_token_usage gauge

[Upstream PR](https://github.com/sgl-project/sglang/pull/44236) · state: open · merged: False

## Original PR description

## Motivation

`sglang:pending_prealloc_token_usage` has reported `0` on every scrape since the day it was added.

`SchedulerStats` declares the field with a `0.0` default and `log_stats` reads it into the gauge, but nothing ever assigns it, so the gauge only ever publishes the dataclass default.

The metric came from #11625, an automated `scripts/copy_from_oss.py` sync that touched only `collector.py`. The producer-side change that was supposed to fill the field never came with it. `gemini-code-assist` flagged this on that PR as a critical finding and pointed at `log_prefill_stats` / `log_decode_stats` in the since-refactored `scheduler_metrics_mixin.py`, but the comment was not addressed before merge. `git log -S pending_prealloc_token_usage` returns that single commit and nothing else, so the gauge has been dead for its entire lifetime.

## Modifications

Assign the stat in `_update_decode_queue_stats()`. That is the single place the other decode queue stats are filled, and it is reached from all three reporting paths (`report_prefill_stats`, `report_decode_stats`, `_maybe_log_idle_metrics`), so it is the current equivalent of the two call sites the original review comment named.

The value itself is not new. The decode log line already formats `disagg_decode_prealloc_queue.num_tokens_pre_allocated / max_total_num_tokens` as `pre-allocated usage`. That expression moves into the stat and the log line now reads the stat back, so the `O(transfer queue)` sum behind `num_tokens_pre_allocated` is walked once per report instead of twice.

The gauge now tracks the share of the KV pool held by requests that have been preallocated on the decode side but whose KV transfer has not completed. Log output is unchanged.

## Accuracy Tests

Not applicable. Observability only, with no change to model forward or output.

## Speed Tests and Profiling

Not applicable. The change is marginally cheaper on the decode reporting path: `num_tokens_pre_allocated` is a sum over the transfer queue and was previously evaluated twice per report, now once.
