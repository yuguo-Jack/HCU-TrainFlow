# [Fix] openai: Apply --preferred-sampling-params on /v1/chat/completions

[Upstream PR](https://github.com/sgl-project/sglang/pull/45611) · state: open · merged: False

## Original PR description

## Motivation

Fixes #39096.

`--preferred-sampling-params` is inert on `/v1/chat/completions`.
`ChatCompletionRequest.to_sampling_params()` resolves every sampler key
eagerly through `get_param()` (user value → model `generation_config` →
OpenAI defaults), so `obj.sampling_params` is always fully populated.
`TokenizerManager._create_tokenized_object` then merges
`{**preferred_sampling_params, **obj.sampling_params}`, and the request
dict always wins — the server-side row can never apply. With an empty
generation config, `top_k` additionally resolves to `-1`, silently
disabling top-k sampling instead of merely picking a different value.

Concrete impact: a checkpoint like Qwen3.8 whose `generation_config.json`
carries the thinking sampler row cannot be served with its instruct row
(`temperature`, `top_p`, `presence_penalty`) via the documented flag.

## Modifications

- `python/sglang/srt/entrypoints/openai/protocol.py`
  - `ChatCompletionRequest.to_sampling_params()` accepts
    `preferred_sampling_params` and threads it through `get_param()`'s
    fallback chain. New priority:
    user value > `--preferred-sampling-params` > model generation_config >
    OpenAI defaults.
  - `presence_penalty` / `frequency_penalty` (which bypassed `get_param`
    entirely and were always lost) now resolve through it as well. They
    declare a non-`None` field default (`0.0`), so "user set" is detected
    via `model_fields_set` rather than a `None` check.
  - Added `presence_penalty` / `frequency_penalty` (OpenAI default `0.0`)
    to `ChatCompletionRequest._DEFAULT_SAMPLING_PARAMS`.
- `python/sglang/srt/entrypoints/openai/serving_chat.py`
  - The chat path passes
    `self.tokenizer_manager.preferred_sampling_params` into
    `to_sampling_params()`.
- `test/registered/unit/entrypoints/openai/test_protocol.py`
  - 4 new CPU unit tests: preferred row survives the
    `tokenizer_manager` merge (the issue repro), user values win,
    generation-config fallback is preserved for keys absent from
    preferred, preferred beats the generation config, and no-preferred
    behavior is unchanged.

Behavior is unchanged when `--preferred-sampling-params` is unset:
`get_param()` short-circuits exactly as before.

## Tests

No GPU on this machine, so the serving path could not be run end to end.
Verified instead:

- The issue's repro script against the real `to_sampling_params`
  (AST-extracted from the edited file, stub request object): with a
  preferred row set, all preferred keys survive the
  `{**preferred, **params}` merge — previously lost.
- 7-case stub harness: user-set values win; generation-config fallback
  still applies for keys absent from preferred; preferred beats the
  generation config; output is byte-identical to the pre-fix logic when
  no preferred params are given; OpenAI defaults preserved; the
  preferred dict is not mutated. 7/7 pass.
- The 4 new unit tests' assertions were executed against the real
  extracted method (all pass); they run in CI via `register_cpu_ci`.
- `ruff check --select F401,F821,F823,UP037`, `ruff format --check`,
  `python -m py_compile`, and `git diff --check` all pass on the
  touched files.
