# [Feat] ngram: let each request choose which external corpora to draft from

[Upstream PR](https://github.com/sgl-project/sglang/pull/44957) · state: open · merged: False

## Original PR description

## Motivation

A server can load several external corpora, such as code and legal text. NGRAM currently uses all of them for every request. Unrelated corpora share the draft budget and can reduce the accept length.

This PR lets each request choose its corpora. It covers the "User request take in corpus_ids to match" item in #21052.

## Modifications

Add `ngram_corpus_ids` to the request's sampling params:

```json
{"text": "...", "sampling_params": {"ngram_corpus_ids": ["code"]}}
```

| Value | Behavior |
|---|---|
| Not set | Use all loaded corpora, as before |
| `["a", "b"]` | Use only these corpora |
| `[]` | Use the online trie without external corpora |
| Unknown ID | Ignore it, since a corpus may have been removed |

The external SAM budget is split only among the selected corpora. A request that selects one of two corpora gets the same drafts as a server with only that corpus loaded.

The worker stores the selection once per request. It tracks the request itself as well as its ID, so a new request cannot inherit an old selection when it reuses that ID. Later steps of the same request keep their state.

The Python API, protobuf schema, and Rust server accept the new field. The field order matches on both sides.

## Accuracy Tests

- CPU tests: **137 passed**, plus **25 subtests**. The suite covers the corpus, request state, worker prompt, Mamba updates, and sampling params.
- The five new worker tests also pass through the registered CI entry point. They cover a reused ID with a new corpus choice, later decode steps, prefill retries, chunked prefill, and cache cleanup.
- The reuse case produced drafts from the old corpus before the fix and from the selected corpus after it.
- Pre-commit checks passed for both changed files.

The earlier H100 run passed the new corpus-selection test and the existing `test_output_as_corpus_boosts_accept_length` test. With a matching corpus, greedy text differed slightly after about 1.4K characters. Output equivalence has not been established; those tests check accept length.

## Speed Tests and Profiling

Earlier result on one H100 80GB with `Qwen/Qwen2.5-Coder-7B-Instruct`, flashinfer, 16 draft tokens, and an external SAM budget of 8:

| Selected corpus | Average accept length |
|---|---|
| Unrelated text | 1.29 |
| The model's earlier answers | 5.74 |

The test used three prompts, greedy decode, and 128 output tokens per prompt. The cache was flushed between runs. GPU tests and benchmarks were not rerun for the request-state fix.
