# [Feat] ngram: let each request choose which external corpora to draft from

[Upstream PR](https://github.com/sgl-project/sglang/pull/44957) · state: open · merged: False

## Original PR description

## Motivation

A server can load several external corpora with `/add_external_corpus`, for example one for code and one for legal text. Today every request drafts from all of them, so a coding request still searches the legal corpus. This hurts in two ways. First, all corpora share one fixed number of draft tokens per step (the external SAM budget), so the legal corpus uses up slots that the code corpus could have filled. Second, the legal corpus's matches are usually wrong, which lowers the accept length.

To fix this, this PR lets each request choose which corpora to draft from. It implements the "User request take in corpus_ids to match" item in #21052.

## What this PR adds

The choice is made with a new sampling param, `ngram_corpus_ids`:

```json
{"text": "...", "sampling_params": {"ngram_corpus_ids": ["code"]}}
```

| Value | Behavior | Why |
|---|---|---|
| not set | use all loaded corpora | same as today, so existing users are not affected |
| `["a", "b"]` | use only `a` and `b` | the main feature |
| `[]` | use no external corpus, only the online trie | lets a request opt out entirely |
| unknown id | ignored | a corpus can be removed while a request is still running, so this should not fail the request |

Choosing corpora also changes how the budget is split. The external SAM budget (`--speculative-ngram-external-sam-budget`) is divided only among the chosen corpora. So a request that chooses 1 of 2 corpora drafts exactly like it would on a server with only that corpus loaded.

## How it works

1. **C++ (`ngram.cpp`).** For each request, the C++ side already keeps a match state that tracks where the request is in the trie. The first time a request is seen, its corpus choice is saved next to that match state. On each step, `batchMatch` reads the choice, looks only at the chosen corpora, and splits the budget among them. Because the choice is saved once, nothing extra is passed from Python on later steps. It is removed together with the match state when the request finishes.
2. **Python (`ngram_worker.py`, `ngram_corpus.py`).** The worker reads `ngram_corpus_ids` from each request's sampling params and passes it to C++ the first time the request is seen. The ids are sent to C++ as one newline-joined string, so `sampling_params.py` rejects ids that are empty or contain a newline or tab.
3. **API schema (`sampling.proto`, Rust server).** The new param also has to be accepted at the API layer. Every `/generate` body is checked against the schema in `proto/sglang/api/v1`, and unknown fields get a 400. So I added `StringList ngram_corpus_ids = 28` there and regenerated the Rust and Python types with `cargo gen-api`. The Rust server also has its own `SamplingParams`. Rust sends sampling params to Python as a list where each field is identified by its position, so I added the new field in the same slot on both sides.

## Results

**Setup:** 1×H100 80GB, `Qwen/Qwen2.5-Coder-7B-Instruct`, flashinfer, 16 draft tokens, external SAM budget 8.

**Test:** Two corpora were loaded on the same server. One held the model's own earlier answers to the test prompts (`matching`). The other held unrelated text. I sent 3 prompts (greedy, 128 tokens each) and flushed the cache between runs, so the online trie did not carry over from one run to the next.

| Request uses | Avg accept length |
|---|---|
| `["unrelated"]` | 1.29 |
| `["matching"]` | **5.74** |

Beyond speed, unit tests (CPU) check that the choice is applied correctly:
- not set means all corpora;
- a listed corpus only;
- `[]` means no corpus;
- unknown ids are ignored;
- choosing 1 of 2 gives the same drafts as a server with only that corpus;
- a batch where requests choose differently;
- the choice stays fixed for the life of the request;
- the choice is cleared when the request ends.

All of the following pass:
- Unit tests: `test_ngram_corpus.py` and the API contract and parity tests, 90 passed.
- End-to-end on H100: the new test and the existing `test_output_as_corpus_boosts_accept_length`.
- Rust: `cargo check --workspace --tests`, `clippy`, and `fmt`.

One thing to note about the end-to-end test. I compared each run's output with the output for the same prompt when no corpus was used. With `["matching"]`, greedy output matched that output for about the first 1.4K characters, then drifted slightly. I believe this is because a different draft tree changes floating-point rounding during verification in bf16, but I did not check that against an unmodified build. For this reason, the new test checks accept length, not exact text, like the existing ngram tests.
