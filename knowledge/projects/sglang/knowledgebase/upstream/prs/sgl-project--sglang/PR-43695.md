# [diffusion] spectrum: bound forecaster history memory for video DiTs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43695) · state: open · merged: False

## Original PR description

ChebyshevForecaster preallocated an fp32 (history_size, numel) buffer per CFG branch and built (M + 1, numel) fp32 intermediates on every fit. For video DiTs this is tens of GiB (about 62 GiB per branch for Wan2.2-A14B at 832x480x81), so Spectrum ran out of memory at common video resolutions.

- Keep history as per-real-forward copies in the feature dtype, capped at history_size, instead of a preallocated fp32 buffer.
- Predict as a weighted sum over the history rows (weights from the same ridge solve), so no (M + 1, numel) coefficient matrix is materialized.
- For boundary MoE pipelines (Wan2.2-A14B), reset the high-noise expert's Spectrum state once the low-noise expert takes over; it does not run again in the request.

## Accuracy Tests

Wan2.2-I2V-A14B, 832x480, 81 frames, 40 steps, seed 42, bf16, TP4 on 4x Intel Arc Pro B60 (24 GB), default Spectrum parameters. Same image and prompt for every run.

- Spectrum on vs Spectrum off, same seed: PSNR 26.31 dB mean (33.77 dB on the first frame, 23.53 dB on the last). Output is visually clean; the difference is motion drift, which is expected from a skip-step method and not a change this PR introduces (main cannot run Spectrum at this shape at all, see below).
- Two Spectrum runs of this PR produce bit-identical videos.
- Forecaster numerics against an fp64 ridge reference: the bf16 prediction error is at or below main's in every tested `(m, history_size, w, taylor_order)` combination, including `history_size` smaller than the number of updates (for example `m=4, history_size=100, w=1`: 1.70e-3 vs 2.22e-3 relative L2). The Taylor-only path (`w=0`) is bit-identical.

## Speed Tests and Profiling

| | Spectrum off | Spectrum on |
|---|---|---|
| main (`11bfd868ac`) | same code path as this PR (every change is gated on `enable_spectrum`) | **OOM at denoising step 0**: `XPU out of memory. Tried to allocate 60.40 GiB. GPU 1 has a total capacity of 23.91 GiB` |
| this PR | denoise 792.7 s, end to end 815.8 s, peak 15,584 MB | denoise 365.8 s, end to end 388.5 s, peak 19,924 MB |

Spectrum on this PR: **2.17x denoise, 2.10x end to end**, for +4.3 GB peak (reserved; allocated 12,215 to 16,450 MiB).

Memory allocated per rank when VAE decode starts:

| | Allocated entering decode | After decode |
|---|---|---|
| without the post-loop reset | 6,499 MiB | 6,701 MiB |
| with it (this PR) | 312 MiB | 513 MiB |

At this shape the request peak does not move (it occurs mid-denoise, and decode with slicing is small), but decode now runs with ~6.2 GiB more headroom per rank.
