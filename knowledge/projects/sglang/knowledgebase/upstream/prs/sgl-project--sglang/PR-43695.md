# [Fix] diffusion/spectrum: Bound forecaster history memory to fix OOM on video DiTs

[Upstream PR](https://github.com/sgl-project/sglang/pull/43695) · state: open · merged: False

## Original PR description

## Motivation

`ChebyshevForecaster` preallocated an fp32 `(history_size, numel)` buffer per CFG branch and built `(M + 1, numel)` fp32 intermediates on every fit. A video DiT feature is a full-sequence hidden state, so with the default `history_size=100` that buffer alone is tens of GiB. As a result, Spectrum runs out of memory at common video resolutions: Wan2.1-T2V-1.3B at 832x480x81 already needs 18.75 GiB per branch.

## Modifications

- Store history as per-real-forward copies in the feature dtype, capped at `history_size` (`deque(maxlen=K)`). Memory now scales with the number of real forwards, not with `history_size`.
- Predict as a weighted sum over the history rows, with weights from the same ridge solve (`x* (X^T X + lam I)^-1 X^T` regrouped), so the `(M + 1, numel)` coefficient matrix is never materialized. The ridge system is now `(M + 1) x (M + 1)` with a single right-hand side.
- Free each DiT's Spectrum history once it can no longer be read:
  - after the denoising loop, so the history does not sit in memory through decode;
  - for boundary-MoE pipelines (Wan2.2-A14B), at the expert handoff for the high-noise expert, once per request.

Every change is gated on `enable_spectrum`; with Spectrum off, the output is bit-identical to main. The changes contain no device-specific code: only plain torch ops on the feature's device. Tested on CUDA and Intel XPU.

## Accuracy Tests

Wan2.1-T2V-1.3B, 832x480, 81 frames, 50 steps, seed 42, bf16, 1x A100-SXM4-40GB, default Spectrum parameters.

- Spectrum on vs off: 27.09 dB PSNR mean (26.75 dB first frame, 25.64 dB last). The output is visually clean; the difference is the usual skip-step drift.
- Two Spectrum runs of this PR produce bit-identical videos.
- At 17 frames, where main fits, this PR vs main with Spectrum on: 39.08 dB PSNR. The outputs differ slightly because history is now kept in bf16 and the reduction order changed.
- Forecaster vs an fp64 ridge reference (A100, 4M-element features, 12 updates, prediction at t=30): the bf16 error is at or below main's in every case. The Taylor-only path (`w=0`) is bit-identical to main.

## Speed Tests and Profiling

Same setup as above (832x480x81).

| | Spectrum off | Spectrum on |
|---|---|---|
| main | denoise 138.0 s, end to end 143.5 s, peak 9,838 MB | **OOM**: `CUDA out of memory. Tried to allocate 18.75 GiB` |
| this PR | denoise 138.1 s, end to end 143.7 s, peak 9,838 MB | denoise 43.3 s, end to end 48.9 s, peak 10,216 MB |

With Spectrum on, this PR is **3.19x faster in denoise and 2.94x end to end**, for +378 MB peak. At 17 frames, where main fits, peak drops from 18,890 MB to 9,622 MB at the same speed (denoise 10.5 s vs 10.4 s).

Freeing the history after the denoising loop (allocated memory on the device, Spectrum on):

| | Entering decode | After decode | Request peak |
|---|---|---|---|
| without the post-loop release | 2,935 MiB | 2,834 MiB | 12,274 MB |
| with it (this PR) | 247 MiB | 146 MiB | 10,216 MB |

With the release, decode starts with the same allocation as Spectrum off. At this shape the request peak occurs during decode, so the release also lowers it by 2 GB.
