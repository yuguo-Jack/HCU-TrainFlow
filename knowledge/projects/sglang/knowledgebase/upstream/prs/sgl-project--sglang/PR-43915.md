# [Fix] Cap transcription upload size before buffering it in host memory (#43709)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43915) · state: open · merged: False

## Original PR description

## Motivation

#43709: /v1/audio/transcriptions buffers the whole multipart upload with `await file.read()` before any validation runs — only response_format is checked first — so a single large upload lands entirely in host memory regardless of what the serving layer does with it next. Every other client-supplied media path already has a limit (the remote-media path enforces `media_url_max_file_size_mb` while streaming); the upload path had none.

## Modifications

Per-endpoint cap per the discussion on the issue: a new `--audio-transcription-max-file-size-mb` (default 25 MiB, matching the OpenAI API limit for this endpoint; 0 disables — same semantics as `media_url_max_file_size_mb`). Over-limit uploads get a 413: the declared-size precheck rejects honest clients before any buffering, and a chunked read enforces the cap when the declared size is missing or lies. I went per-endpoint rather than an app-wide body middleware since that changes every route at once — happy to switch if a middleware is preferred, and happy to close this in favor of another implementation if one is already in flight.

## Accuracy Tests

No model-output changes — the cap only gates what reaches the serving layer; under-limit uploads pass through byte-identical. New unit tests cover the precheck, streaming enforcement against a lying declared size, the pass-through, the 0-disables path, and the response_format-first ordering (`test_transcription_upload_limit.py`).

## Speed Tests and Profiling

Not perf-sensitive: one int comparison on the request path; the chunked read iterates in 1 MiB steps.
