# [Fix] conversation: Merge consecutive same-role turns in LLAMA2-style templates

[Upstream PR](https://github.com/sgl-project/sglang/pull/46283) · state: open · merged: False

## Original PR description

## Motivation

Fixes #43155. The `LLAMA2` separator style (used by the `llama-2`, `mistral` and `devstral` templates) assigns `[INST]` / `[/INST]` by message position (`self.roles[i % 2]`). OpenAI-valid requests that are not strictly alternating are therefore mislabeled. For example, two consecutive user messages render as

```
[INST] Here is my code. [/INST] Please review it. </s><s>[INST]
```

so the second user message is presented as an assistant reply, and the prompt ends with the user tag, asking the model to write the user's next turn.

## Modifications

- Before rendering, merge consecutive messages of the same role, joined with `"\n\n"`. Empty contents are skipped when joining, and the trailing generation slot (`None`) is never merged. After merging, turns alternate, so the existing positional rendering is correct and is left unchanged.
- The example above now renders as `[INST] Here is my code.\n\nPlease review it. [/INST]`. Consecutive assistant messages are merged the same way.
- Strictly alternating conversations are unaffected: I compared old and new `get_prompt()` output for `llama-2`, `mistral` and `devstral`, with and without a system message, for 1-6 alternating turns, with and without an empty first user message (72 cases), and all are byte-identical.
- Adds a regression test (user, assistant, user, user) that fails on current main and passes with this change.

## Design notes

**Why merge with `"\n\n"`?** This matches Mistral's reference implementation: mistral-common's `InstructRequestNormalizer` aggregates consecutive messages of the same role and joins them with `"\n\n"` (`_DEFAULT_JOIN_STR` in `mistral_common/protocol/instruct/normalize.py`, checked on 1.12.0). HF's Llama-2 and Mistral chat templates reject non-alternating roles outright, so merging is the behavior that both accepts the OpenAI-valid request and keeps the prompt in the shape the models were trained on.

**Why not tag each message with its stored role?** This revisits the same bug as #43266, which was closed by its author without review. That PR tags each message with its stored role. Two consecutive user messages then render as `[INST] u1 [INST] u2 [/INST]`, a shape these models never see in training. Merging produces a normal alternating prompt instead. Keeping the positional rendering after the merge also guarantees that alternating conversations render exactly as before; tagging the trailing generation slot by stored role would change the prompt of every conversation that ends with an assistant message.

**Out of scope (noticed while testing):** with a system message, the `mistral` and `devstral` templates do not emit `[INST]` before the first user message, because their `system_template` does not end with `[INST] ` as `llama-2`'s does. That is a separate issue and is not changed here.
