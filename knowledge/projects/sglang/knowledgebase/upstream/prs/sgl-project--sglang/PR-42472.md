# fix(spec): bind target embed/lm_head into the draft before KV pool profiling

[Upstream PR](https://github.com/sgl-project/sglang/pull/42472) · state: open · merged: False

## Original PR description

## Problem

MTP draft models (Qwen3.5/3.8 `*ForCausalLMMTP` and friends) allocate their **own** embedding + lm_head at construction time. For a 248K-vocab model under TP2 that is ~1.9 GB **per GPU** of duplicated tables that the checkpoint never even populates — integrated-MTP checkpoints ship only the mtp layer (~15 tensors); the tables are meant to be shared with the target via `set_embed_and_head()` (which `del`s the shell and calls `empty_cache`).

The sharing machinery exists and works — it just runs too late. `EagleDraftWorker.__init__` finishes, the scheduler runs `init_target_memory_pool()` → profiles free memory **with the shell still resident** and charges it via `account_preloaded_weights()`, sizes the KV pool against that, and only *afterwards* does `alloc_memory_pool()` call `init_token_map()` / `init_lm_head()`. The ~1.9 GB/GPU is freed back into the allocator, but the pool was already sized without it.

Measured on 2× RTX 5060 Ti 16GB (TP2), `RadixArk/Qwen3.8-27B-NVFP4`, `--kv-cache-dtype nvfp4`, `--speculative-algorithm NEXTN --speculative-num-steps 2 --speculative-eagle-topk 1 --speculative-num-draft-tokens 3`, `--mem-fraction-static 0.93 --max-total-tokens 196000`:

| | KV pool |
|---|---|
| stock (bind in `alloc_memory_pool`) | **51,456 tokens** |
| this PR (bind in constructor) | **195,968 tokens** |

Same boot, same probe set: needle-in-haystack 4/4 both ways (34K and 45K corpora), acceptance metrics unchanged (`spec_accept_length` 2.05–2.83), no decode-speed regression. The model simply gets 3.8× the usable context it was silently entitled to.

## Fix

Perform the bind at the end of `EagleDraftWorker.__init__`, right after the draft runner is constructed. The existing `init_token_map(); init_lm_head()` pair in `alloc_memory_pool()` is kept — `set_embed_and_head()` re-points at the same target tensors, so the second call is a no-op (idempotent by construction; it also keeps the hot-token path consistent when `init_token_map` loads a `--speculative-token-map`).

The one ordering constraint I checked: `init_lm_head()` reads `self.hot_token_id` (set by `init_token_map()`, called immediately before) and `self.draft_runner.model.set_embed_and_head`, and touches nothing from attention-backends/graphs/`alloc_memory_pool` state. `FrozenKVMTPDraftWorker` (the frozen-KV MTP path) already binds in its constructor for the same reason — this PR aligns the EAGLE-family worker with it.

## Test

`test_embed_bind_before_pool.py` (CPU-only): drives `EagleDraftWorker.__init__` with a fake `TpModelWorker` and asserts the embed/head bind happens **during construction**. Fails on stock code (`calls == []`), passes with the fix.

```
PYTHONPATH=python pytest test/registered/unit/spec/test_embed_bind_before_pool.py \
  test/registered/unit/spec/test_eagle_worker_v2_topk1_fastpath.py -q
# 12 passed, 7 subtests passed
```

## Notes

- Not speculative-decoding-accuracy related at all — pure memory-accounting timing. Models *without* draft embed/lm_head duplication are unaffected (bind is a no-op when there's no `set_embed_and_head`).
- Also relevant to #36010 in spirit: the nvfp4-KV × spec-decode saga had a crash (fixed by #36038) *and* this separate pool-collapse; after both, nvfp4 KV + NEXTN runs full-context on 16GB cards.

Co-authored-by: Qwen3.8-Flash-Next (served on G41:8000, SGLang + MTP) — this fix was found, patched, measured and regression-tested by that model as an autonomous agent; human supervision: minor.
