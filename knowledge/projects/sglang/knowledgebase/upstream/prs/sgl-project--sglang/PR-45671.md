# [Fix] [AMD] quark: Keep the MXFP4 dense GEMM off AITER's masked K-tail path

[Upstream PR](https://github.com/sgl-project/sglang/pull/45671) · state: open · merged: False

## Original PR description

## Motivation

- Quark W4A4 MXFP4 dense GEMMs on gfx95 intermittently return NaN when AITER's `gemm_afp4wfp4` picks a config whose `BLOCK_SIZE_K` does not divide K (masked K-tail).
- Cause: a Triton AMD backend bug leaves stale LDS data in masked scale-load lanes instead of `other=127`; a stale `0xFF` is a NaN E8M0 scale. Upstream fix: [triton-lang/triton#11256](https://github.com/triton-lang/triton/pull/11256). Triton 3.7.0 and 3.8.0+git4cff872c in current ROCm images still lack it.
- Impact: on an earlier Kimi-K3 checkpoint with MXFP4 shared experts, this produced 71 gibberish GSM8K answers (91.96% vs 97.35%).

## Modifications

- `_aiter_gemm_afp4wfp4` (Quark W4A4 MXFP4 dense linear, gfx95) now passes an explicit config to `gemm_afp4wfp4`:
  - Reads the config `gemm_afp4wfp4` itself would pick (`aiter.ops.triton.gemm_afp4wfp4._get_config`, packed K), cached per `(M, N, K)`.
  - Narrows `BLOCK_SIZE_K` to the largest power of two >= 128 that divides K, so the kernel runs with `EVEN_K`.
  - Keeps every other config field, so tuned tile sizes stay.
- Workaround comment anchored to triton-lang/triton#11256 with its retirement condition.

| Case | Config passed to `gemm_afp4wfp4` |
|---|---|
| Not gfx95, or AITER without `_get_config` | none (AITER's own selection, as before) |
| Config lookup raises `KeyError` / `AssertionError` (no config file / M bucket) | none |
| Split-K config (`NUM_KSPLIT > 1`) | none; left to AITER's `get_splitk` (the NaN did not reproduce on the M <= 8 split-K defaults) |
| `BLOCK_SIZE_K` already divides K | AITER's config |
| `BLOCK_SIZE_K` does not divide K | AITER's config with a narrowed `BLOCK_SIZE_K` |
| No power of two >= 128 divides K (e.g. K=2880) | none, and a one-time warning per K |

- Tests:
  - CPU (`test_quark_mxfp4_asm.py`): block narrowing for Kimi-K3 K=768 / 4224, even and un-narrowable K, config lookup fallbacks, split-K passthrough.
  - MI35x (`test_quark_afp4wfp4_k_tail.py`): fills LDS with `0xFF` before each GEMM and checks against a dequantized reference at N=7168, K=1536, M=16/32; asserts AITER still picks an uneven block for that shape.

## Accuracy Tests

Kernel regression: LDS filled with `0xFF` before each GEMM to reproduce the failure deterministically.

| N / K | AITER config | Failing M before | Failing M with PR |
|---|---|---|---|
| 7168 / 768 | untuned, old AITER `2bb549102` | 80, 96, 112, 128 | none |
| 7168 / 768 | tuned, pinned AITER | none | none |
| 7168 / 1536 | untuned, pinned AITER | 16, 32 | none |

GSM8K: 1,319 questions, sgl-eval 0.1.3, K3 preset, TP8, radix cache on, one run per config.

| Setup | Before | PR | Delta | Gibberish answers |
|---|---:|---:|---:|---|
| Old AITER `2bb549102`, MXFP4 shared experts | 91.96% | 97.35% | +5.39 pp | 71 -> 0 |
| Pinned AITER `285579b6`, current BF16 shared experts | 96.97% | 97.19% | +0.22 pp | not reported |

- The current checkpoint avoids the affected shapes, so its row is a regression check.
