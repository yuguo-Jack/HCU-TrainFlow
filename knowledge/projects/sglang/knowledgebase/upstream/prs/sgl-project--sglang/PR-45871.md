# [Perf] [NVIDIA] attention: Native FP8 KV cache for SM120 FA4 kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/45871) · state: open · merged: False

## Original PR description

## Motivation

On SM120 (RTX PRO 6000 Blackwell), `--attention-backend fa4 --kv-cache-dtype fp8_e4m3` fails at startup:

```
AssertionError: FP8 is only supported on SM100 (compute capability 10.x) for FA4 CuTe.
```

The SM120 FA4 kernels only accept FP16/BF16 (see also #42333). FP8 KV halves both KV-cache memory and KV bandwidth. On a bandwidth-bound decode, that means more concurrent requests and lower per-step attention time. This PR runs E4M3 Q/K/V natively through the SM120 prefill and decode kernels.

## Modifications

- `fa4_sm120/flash_fwd.py`
  - QK^T and PV both run on the E4M3 `m16n8k32` warp MMA.
  - V stays in shared memory as E4M3, so there is no BF16 copy and V smem is halved. It is loaded as the N-major B operand through `LdMatrix16x16x8bOp(transpose=True)` with an explicit TV layout and retile, ported from `quack` `GemmSm120`. The auto-generated trait reads the wrong K for this atom.
  - Before the cast, P is pre-scaled by 256. This keeps small probabilities out of the E4M3 subnormal range, which matters with attention-sink-heavy distributions. The scale is undone in the output rescale, so `row_sum`/LSE are unchanged and split-KV partials stay linear.
  - Per-(batch, kv_head) q/k/v descales: `q·k` is folded into the softmax scale, and `v / 256` into the final O rescale. When no descales are passed, they are compile-time `1.0`, so the BF16 IR is unchanged.
  - Output dtype is decoupled from the input dtype (`o_dtype = BFloat16` under FP8). `sO` aliases `sQ` with a size that covers BF16 O.
  - Shared-memory accounting uses per-buffer element sizes. New tile candidates for head dims > 256 fit the 101376 B SM120 budget, for FP8 and also BF16. BF16 HD512 previously raised `exceeds SM120 shared-memory capacity`.
- `fa4_sm120/flash_fwd_decode.py`: the transposed HD256 paged-decode kernel gets the same FP8 path. V is the M-major A operand, and P is the K-major B operand in E4M3.
- `fa4_sm120/runtime.py`: FP8 paged decode with head dim > 256 selects `num_splits` to keep about 2k CTAs in flight, capped at 16. The cached host-plan fast paths stay BF16-only.
- `flash_attn/cute/interface.py`
  - Allows E4M3 on SM120 when q/k/v share the dtype.
  - Missing descales are filled with ones, and all three are made contiguous. This is needed because `DescaleTensors` rebuilds its fields by position from the non-`None` values, and the backend passes stride-0 `expand()` views.
- `flash_attn/cute/flash_fwd.py`: adds `o_dtype` in the shared base, defaulting to `dtype`, so SM80/SM90 are unaffected.
- `flashattention_backend.py`: on SM120 FA4, q is cast to FP8 and descales are passed for prefill and for head dims > 256 as well. Other architectures keep the existing condition.

The SM90/SM100 kernels and the native `sgl-kernel` path are untouched.

## Accuracy Tests

Kernel level, against an fp32 reference on dequantized inputs. The new unit tests cover varlen and paged inputs, HD128/256/512, `pack_gqa`, sliding window, and learnable sink:

| case | cosine |
|---|---|
| paged decode HD256, window 1023 | 0.99972 |
| paged decode HD512 | 0.99974 |
| paged prefill HD256 (819 q / 8192 k), window 1023 | 0.99972 |
| paged prefill HD512 (819 q / 8192 k) | 0.99968 |
| attention-sink distribution, all four cases above | 0.999998 |

The remaining error comes from rounding P to E4M3 (3 mantissa bits). BF16 outputs are bitwise identical to `main` for HD256 prefill and decode.

End to end: `gemma-4-31B-it` (ModelOpt mixed FP8/NVFP4, 50 sliding HD256 layers + 10 full HD512 layers), 1× RTX PRO 6000, `few_shot_gsm8k` on the 1209-question GSM8K-Platinum test set:

| KV cache | accuracy | invalid |
|---|---|---|
| BF16 | 0.730 | 0.012 |
| FP8 E4M3 (this PR) | 0.742 | 0.008 |

## Speed Tests and Profiling

Kernel microbenchmark (CUDA graph, 100 replays, 9216 KV tokens, Hq=32; decode uses B=20):

| case | BF16 µs | FP8 µs | speedup |
|---|---|---|---|
| decode HD256, Hkv=16, window 1023 | 213.6 | 105.0 | 2.03× |
| decode HD512, Hkv=4 | 1018.3 | 549.6 | 1.85× |
| prefill HD256, 1024 q | 175.5 | 98.5 | 1.78× |
| prefill HD512, 1024 q | 12871.6 | 5880.1 | 2.19× |

Serving: same model and GPU, ISL 8k / OSL 1k with 90% prefix cache. The run sweeps concurrency under ITL p90 < 50 ms and TTFT avg < 8 s:

| KV cache | max concurrency | output tok/s | ITL p90 |
|---|---|---|---|
| BF16 | 20 | 383.36 | 49.12 ms |
| FP8 E4M3 (this PR) | 46 | 863.56 | 48.43 ms |

That is 2.25× output throughput at the same latency budget. With FP8, the KV pool holds 644569 full-attention and 96685 SWA tokens.

Server flags: `--attention-backend fa4 --kv-cache-dtype fp8_e4m3 --page-size 1 --swa-full-tokens-ratio 0.15 --mem-fraction-static 0.92`.

Note: Gemma 4 with FA4 and MTP speculative decoding additionally needs #43542. That fix is independent of this PR and not required for the results above.
