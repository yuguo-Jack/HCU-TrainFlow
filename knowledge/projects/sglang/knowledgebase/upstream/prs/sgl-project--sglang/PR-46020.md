# [Feat] Inkling: upgrade tml-renderers to 0.2.1

[Upstream PR](https://github.com/sgl-project/sglang/pull/46020) · state: open · merged: False

## Original PR description

## Motivation

#45340 landed the Inkling ↔ `tml-renderers` delegation at `==0.1.0`. This PR upgrades the pin to **`==0.2.1`** and adapts to it.

0.2.x is where the library is heading (multi-model renderer registry, picklable renderer, cp310 wheels), and 0.2.1 specifically fixes three issues we reported upstream with repros: renderer/parser could not be used off their creating thread, concurrent first tokenizer construction deadlocked, and truncated input discarded already-parsed messages.

The one deliberate removal in 0.2.x is `v0.Parser`'s incremental streaming surface (`parse_token` / `parse_updates` / `flush_updates` / `flush` / `is_at_message_boundary`); only batch `parse_tokens` / `parse` remain. The output side of this PR therefore reimplements the incremental semantics in sglang instead of depending on them.

## Modifications

**Output parsing** (`parser/inkling_output.py`): a per-token state machine tracks message/author/content-kind boundaries and streams text and thinking payload immediately (incremental UTF-8, special tokens spelled literally inside text blocks). At each `<|end_message|>` the complete message is parsed once through the library (`parse_tokens` with a sentinel prefix, dropped from the result), so tool-call JSON and error recovery still come from the reference implementation. Stream and non-stream share the parser; stop cutting and `max_tokens` surfacing are unchanged from #45340.

**Prompt rendering** (`parser/inkling_renderer.py`): uses the non-deprecated `O200kBaseChatTokenizer()`; renderer construction and delegation are otherwise unchanged.

**Golden fixtures**: regenerated under 0.2.1 by the checked-in generator. 0.2.1 restored the assistant tool-call header function name that 0.2.0 had dropped, so 13/14 prompts are byte-identical to 0.1.0; the remaining differences are enumerated under Behavior changes.

**Dependency**: `tml-renderers==0.2.1` (same platform markers as 0.1.0, plus cp310 wheels upstream).

## Behavior changes (vs #45340 on 0.1.0)

- History tool-call **arguments sort top-level keys only**; nested objects keep sampled key order (0.1.0 sorted recursively). Tool declarations are still deep-sorted.
- A tool call whose header name differs from its payload `name` is **rejected and surfaced as text** (was: payload name wins). Reported upstream as an open question.
- Duplicate keys directly inside `args` are last-wins again (same as 0.1.0); duplicate top-level `name`/`args` fields stay rejected (same as 0.2.0).
- Error taxonomy: `UnterminatedMessageError` split into `UnterminatedStructureError`/`UnterminatedContentError` plus `EmptyResponseError` and `NonCanonicalMessageError` subclasses. sglang catches `v0.ParseError` without dispatching on kind, so no mapping changes.

### Thread model note

0.2.0 made `v0.Renderer`/`Parser` unusable off their creating thread (panic); 0.2.1 restores cross-thread use, so the prompt path keeps one shared renderer per process. A regression test (`test_renders_and_parses_off_the_creating_thread`) renders and parses from executor threads and fails on 0.2.0 by design, so a future pin regression turns CI red.

## Known scope limits

- The incremental streaming semantics are sglang-local until/unless the library restores an official surface; the parity harness above is the guard against drift.
- `/parse_function_call` and `/separate_reasoning` remain text-level and do not use the library (as in #45340).
