# [Fix] speculative: Fix EAGLE draft token count when input_ids is None

[Upstream PR](https://github.com/sgl-project/sglang/pull/40172) · state: open · merged: False

## Original PR description

EAGLE speculative decoding + expert parallelism has been affected on main since #39574. Draft `ForwardBatch.init_new` sees `input_ids is None` and publishes a live token count of 0, so TopK masks every draft `topk_ids` row to `-1` and the eager draft forward runs the MoE without routed experts.

This PR derives the draft token width from `spec_info.num_tokens_per_req` when `input_ids` is missing.

The original second half (keeping the `-1` sentinel through `local_expert_mapping` in `StandardDispatcher`) is superseded by #40498 and was dropped in the rebase onto current main.

Unit test: a draft `ForwardBatch` with `input_ids=None` now publishes `bs * num_tokens_per_req` (fails with `0 != 4` on main, passes here). E2E data from @QNan0513 (EAGLE/MTP, TP8/EP8, full GSM8K, draft graph on and off) is in the thread below.

Fixes #40156

E2E data for the review request above: EAGLE/MTP with `moe_ep_size > 1`, full GSM8K with finish_reason and accuracy, and draft CUDA graph on and off.

**Setup.** 8x H20, GLM-5.3-Flash FP8 (288 experts, index-share MTP), TP8/EP8, `--moe-runner-backend deep_gemm`, tilelang DSA, EAGLE 5/1/6. Image: `lmsysorg/sglang:v0.5.22-cu130` (= main@684fea8a + two PD/CI cherry-picks), with files swapped in:
- **stock**: v0.5.22 unchanged.
- **#40498**: `standard.py` from the #40498 merge commit, identical to current main's.
- **#40498 + this PR**: plus this PR's `forward_batch_info.py` change, which applies to v0.5.22 with offsets only. Its `standard.py` hunk is superseded by #40498.

**GSM8K.** All 1319 questions, with the 5-shot prompt from `sglang.test.few_shot_gsm8k`, greedy, 512 new tokens, 128 parallel. Requests go through `/generate` so each one keeps its `meta_info`; accept length = sum(completion_tokens) / sum(spec_verify_ct).

**Draft graph off.** "off" = `--cuda-graph-backend-decode disabled`. v0.5.22 has no switch for the draft-decode graph alone (only `SGLANG_DISABLE_DRAFT_EXTEND_CUDA_GRAPH` for draft extend), so this also disables the target verify graph. The prefill graph stays on.

| build | draft graph | GSM8K acc | finish_reason | accept len | out tok/s | crash |
|---|---|---|---|---|---|---|
| stock | on | - | - | - | - | TP7 `illegal memory access` after 116/1319 |
| stock | off | - | - | - | - | TP7 `CUBLAS_STATUS_EXECUTION_FAILED` after 31/1319 |
| #40498 | on | 0.920 | 1319 stop | 4.131 | 1385 | none |
| #40498 + this PR | on | 0.922 | 1319 stop | 4.134 | 1453 | none |
| #40498 | off | 0.914 | 1318 stop, 1 length | 3.612 | 671 | none |
| #40498 + this PR | off | 0.914 | 1318 stop, 1 length | 4.137 | 754 | none |

- **Draft graph off.** Every draft-decode forward reaches `ForwardBatch.init_new` with `input_ids=None`. On main, every draft row is therefore masked to `-1`, and the draft MoE runs without routed experts. Accuracy and stop rate don't move, since the target still verifies every token. Accept length drops 4.14 -> 3.61 and throughput drops 11%. This PR brings accept length back to the graph-on level.
- **Draft graph on.** Both builds are the same. I put capture-safe counters next to the mapping lookup (debug only). In this workload no eager draft forward had `-1` rows; the `-1` rows all came from CUDA-graph padding (verify and prefill graphs), and #40498 already handles those. So the count only matters on the eager draft path.
- **The one `length` finish in each off row** is a different question in each build (q298 and q593). Both are long step-by-step enumerations that hit the 512-token cap, not degenerate output.
- **Crash check.** With the draft graph on, both builds also ran 21 min of 64-concurrent chat traffic (half with tools) and 2x bench_serving 2048/512 c64 without errors.
- **Box caveat.** GPU 3 on this box throttles under load (1.2-1.6 GHz average vs 1.98 GHz on the other seven). Absolute tok/s are therefore low, but each compared pair ran on the same box with similar GPU 3 clocks.
- **Rebase.** The `forward_batch_info.py` hunk applies cleanly to current main (e262b44). The `standard.py` hunk no longer applies after #40498 and can be dropped.
