# [Perf] qwen3: Fuse BF16 QK normalization and MRoPE on Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/43425) · state: open · merged: False

## Original PR description

## Motivation

Qwen3 multimodal inference currently launches Q/K normalization and MRoPE separately. This change combines them for BF16 tensors with 128-element heads, full-width NeoX rotation, and 1–128 tokens on datacenter Blackwell. Unsupported configurations retain the existing path.

## Modifications

Reuse the existing QK normalization kernel's load, reduction, and store through an epilogue hook, adding MRoPE in the existing fused RoPE source. The fused path preserves BF16 rounding between normalization and rotation, supports strided Q/K and position rows, and uses direct per-head scheduling. Ordinary QK normalization retains persistent scheduling.

The model dispatch checks the architecture, dtype, head/rotary dimensions, NeoX layout, axis map, token count, and position format, and excludes forced-native rotary, deterministic inference, and prefill Inductor configurations. Cache writes and projection fusion are outside this change.

Based on upstream main `2f1acef3d8860ffe1c4744d99368772cb940f983`.

## Validation on the Exact PR Commit

Validated commit `70b63a457583d88dee174aca53a4b2bbf481e081` on one NVIDIA GB300 GPU (SM 10.3), using PyTorch `2.14.1+cu130` and Triton `3.8.0`. Tests ran from an isolated snapshot of this commit without source modifications.

- **168/168 synthetic BF16 cases matched the split QK norm + Triton MRoPE path bit-for-bit.** Coverage: token counts 1, 2, 16, 17, 127, 128, and 129; Q/K head counts 4/1, 8/2, 16/4, and 32/8; contiguous, interleaved, and GLM MRoPE axis maps; packed QKV with and without extra row padding; and contiguous/strided position rows. V and padding were unchanged. The 129-token cases invoke the kernel directly, outside the model dispatch limit of 128.
- **27/27 changed-input CUDA-graph replays matched bit-for-bit**, including changed positions, at token counts 1, 16, and 128 across the three axis-map layouts.
- **60/60 direct base-versus-PR QK normalization comparisons matched bit-for-bit**, covering BF16/FP16, head dimensions 64/128/256, token counts 1/17/128/129/2048, and Q/K head counts 8/2 and 16/4.
- **All 560 existing QK normalization tests passed** (`test/registered/kernels/ops/layernorm/test_qknorm.py`; 57.86 seconds, 23 dependency deprecation warnings).

The split-path comparisons use the PR's normalization core; the independent base-versus-PR comparisons above check the shared-core refactor. These supplemental checks were run externally and are not added as regression tests in this diff.

Previously reported branch checks also passed pre-commit, Python AST, and static dependency/registry checks. CPU namespace/dispatch tests previously could not collect because that local environment lacked PyTorch.

## Kernel Performance and Existing Fusion Comparison

Kernel-only latency in microseconds, median of three CUDA-graph benchmark runs:

| Tokens | Q/K heads | Split QK norm + MRoPE | This PR | Existing Triton fusion | Split / PR |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 8/2 | 2.751 | 1.304 | 1.700 | 2.11x |
| 1 | 32/8 | 3.452 | 1.311 | 1.778 | 2.63x |
| 16 | 8/2 | 3.257 | 1.372 | 1.866 | 2.37x |
| 16 | 32/8 | 4.231 | 1.469 | 2.090 | 2.88x |
| 128 | 8/2 | 3.524 | 1.648 | 2.634 | 2.14x |
| 128 | 32/8 | 5.121 | 3.082 | 6.577 | 1.66x |

Methodology: `triton.testing.do_bench_cudagraph(..., rep=400)`, three runs with rotated candidate order, BF16 head dimension 128, synthetic weights/activations, contiguous MRoPE sections, packed strided QKV, and strided position rows. Triton output buffers were preallocated. Input reset and allocation were outside the measured graph; the in-place paths repeatedly transform their buffers during timing. GPU clocks were not locked. A separate reset-plus-kernel measurement with fresh input each iteration also showed the PR faster than split in all six shapes.

The existing `_fused_qk_rmsnorm_rope_gate_kernel` was tested with `WEIGHT_SHIFT=0.0` and `HAS_GATE=False`, exercising its ordinary-RMSNorm/no-gate specialization. This specialization was slower than the PR in all six kernel-only measurements. It uses FP32 rotary arithmetic and was not bitwise equivalent to the split BF16 path in any of the 168 correctness cases; the maximum absolute difference was `0.03125`. That numerical difference is not evidence of model accuracy loss, but it means this existing fusion is not an unchanged, bitwise-equivalent replacement.

## Validation Limits

These are kernel-level correctness and latency results. No end-to-end model accuracy, full model dispatch/fallback, or serving-throughput validation was performed. No serving TPS improvement is claimed. Earlier standalone measurements are superseded here by the exact-commit results above.
