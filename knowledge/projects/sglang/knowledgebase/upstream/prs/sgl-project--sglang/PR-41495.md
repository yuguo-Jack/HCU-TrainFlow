# [Feat] [NPU] weight-cache: Add NPU weight cache support

[Upstream PR](https://github.com/sgl-project/sglang/pull/41495) · state: open · merged: False

## Original PR description

## Motivation

The weight cache (`--weight-cache-mode=daemon|client`) shares preloaded weights with serving engines through zero-copy IPC, but it was gated as CUDA-alike only: the daemon rejected anything that failed `current_platform.is_cuda_alike()`, because CUDA IPC relies on torch's `_share_cuda_` handle export. Ascend has no `_share_cuda_`, but `torch_npu` registers its own multiprocessing reduction (`reduce_tensor` / `rebuild_npu_tensor`) which gives the same zero-copy handle export over the existing `ForkingPickler` framing. This PR lets the daemon/client weight-cache modes run on NPU/Ascend, with an explicit probe and graceful CPU-copy fallback when zero-copy is unavailable.

## Modifications

- `weight_cache/daemon.py` — accept NPU past the platform gate (`is_cuda_alike() or is_npu()`) in `load()`, and generalize the error message to "IPC-capable platform (CUDA, ROCm, or NPU/Ascend)". The `expandable_segments` guard is unchanged: it inspects `PYTORCH_CUDA_ALLOC_CONF` / `PYTORCH_ALLOC_CONF`, which only affect CUDA's allocator (NPU uses `PYTORCH_NPU_ALLOC_CONF`).
- `weight_cache/transport.py` — add an NPU branch to `choose_daemon_transport_backend()`:
  - import `torch_npu` before the first `ForkingPickler` dump so the native NPU reducer is registered (otherwise the tensor silently falls back to a CPU copy);
  - probe `torch.multiprocessing.reductions.reduce_tensor` on one state tensor and, if it does not resolve to `rebuild_npu_tensor`, log a warning and continue with the CPU-copy path instead of failing;
  - reuse the existing `TorchIpcTransportBackend` — no dedicated NPU backend is needed, since `torch_npu` already dispatches NPU tensors natively.
- `weight_cache/ipc_loader.py` — generalize watchdog/error wording from "CUDA IPC / GPU memory" to "zero-copy IPC / device memory"; no behavior change.
- `weight_cache/protocol.py` — formatting-only cleanup; no behavior change.

Zero-copy on Ascend requires HDK >= 25.3.RC1 and CANN >= 8.3.RC1, and is unsupported on Ascend 950DT; in those cases the daemon still works via the CPU-copy fallback (with a warning). No model forward, kernel, or checkpoint layout is changed; transferred weights are byte-identical.

## Accuracy Tests
- `test_npu_weight_cache_startup.py` — Qwen3-32B, TP=2: measures cold disk load (cache off), daemon disk load, and warm client IPC import; asserts the IPC marker appears and that the warm import is faster than the cold disk load.

## Speed Tests and Profiling

Loading and inference stay zero-copy; no extra data copies are introduced on the zero-copy path. The only added cost is a one-time `torch_npu` import plus a single `reduce_tensor` probe per process in `choose_daemon_transport_backend()`. The startup test above compares cold-load vs warm-IPC wall-clock and asserts the warm import is faster; per-token throughput is unaffected.
