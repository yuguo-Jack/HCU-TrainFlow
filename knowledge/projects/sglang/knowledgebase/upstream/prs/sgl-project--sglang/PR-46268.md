# [Fix] deterministic: Run the MoE routing functions eagerly in batch-invariant mode

[Upstream PR](https://github.com/sgl-project/sglang/pull/46268) · state: open · merged: False

## Original PR description

## Motivation

In deterministic mode, a token's routed experts must not depend on the server start or on the other tokens in the batch. The routing functions in `layers/moe/topk.py` are wrapped in `torch.compile`. Inductor tunes the generated kernels (block sizes, reduction splits) by timing them on first use, so the summation order of the routing scores can differ between server starts and batch shapes. With it, the selected experts can differ too. On MI350X this made DeepSeek-V2-Lite pass the deterministic checks on some server starts and fail on others (see below). This PR runs these routing functions eagerly in batch-invariant mode and keeps them compiled in normal mode.

**Scope.** The change applies on every platform, to models whose routing reaches these Python functions:
- DeepSeek-V2-style softmax grouped top-k (`grouped_topk_gpu`), for example DeepSeek-V2 / V2-Lite;
- Kimi K2-style biased top-k (`kimi_k2_biased_topk_impl`, `biased_topk_impl`);
- DeepSeek-V3-style sigmoid + correction-bias grouped top-k (`biased_grouped_topk_impl`, used for example by DeepSeek-V3/R1, Kimi-K3 and GLM-4.5), when no fused routing kernel takes over.

Where a fused kernel runs instead, this PR does not change anything. Examples:
- `fused_topk_deepseek` and `moe_fused_gate` on CUDA;
- AITER's routing kernel on ROCm with `SGLANG_USE_AITER=1`, which is the case for DeepSeek-V3-style routing on MI300/MI350.

DeepSeek-V4 cannot run in deterministic mode yet (its attention backend is refused), so it is not covered here.

The failure was reproduced and the fix validated end to end on DeepSeek-V2-Lite. The other models above are listed because they call these functions, not as end-to-end runs.

## Modifications

- `layers/moe/topk.py`: the five `torch.compile`'d routing functions (`grouped_topk_gpu`, `kimi_k2_biased_topk_impl`, `biased_topk_impl`, `biased_grouped_topk_impl`, `_biased_grouped_topk_postprocess`) are compiled through a small decorator, `_compile_unless_batch_invariant`, which keeps the compiled function for normal mode and calls the original one when batch-invariant mode is on. The compile options are unchanged.
- New CPU unit test `test/registered/unit/layers/moe/test_topk_batch_invariant_eager.py`: the five functions are wrapped; in batch-invariant mode the compiled function is never called and the result equals the eager function bit for bit; in normal mode the compiled function is used.
- Unchanged: normal mode (still compiled); routing paths that use fused kernels (`moe_fused_gate`, AITER) instead of these functions.

## Accuracy Tests

MI350X, ROCm 7.2.4, `rocm/sgl-dev:v0.5.22-rocm724-mi35x-20261021`, DeepSeek-V2-Lite-Chat, deterministic mode (`--enable-deterministic-inference --attention-backend triton`, AITER on and off, together with the other open MI350X deterministic-mode PRs), fresh servers, `python3 -m sglang.test.test_deterministic --test-mode single --n-trials 50` plus a bitwise batch-size check (the same prompt in batches of 1 to 50, 1,275 responses, token IDs and logprobs compared exactly with the batch-size-1 response):

| setup | servers that pass |
| --- | --- |
| before, TP1 (AITER on / off) | 4 of 6 |
| before, TP2 (AITER on / off, custom or RCCL all-reduce, with or without CUDA graphs) | 3 of 12 |
| `torch.compile` disabled entirely (`TORCHDYNAMO_DISABLE=1`), TP1 / TP2 | 12 of 12 / 3 of 3 |
| only these routing functions uncompiled, TP1 / TP2 | 8 of 8 / 3 of 3 |
| this branch, TP1 / TP2 | 8 of 8 / 8 of 8 |

Failing servers: `single` 2 outputs and bitwise 1 / 1,275 (AITER on), or identical tokens but log-probabilities 1 / 1,275 (AITER off); passing servers: 1 output and 1,275 / 1,275.

GSM8K (sgl-eval 0.1.2, `--temperature 0 --max-tokens 2048`, all 1,319 questions, DeepSeek-V2-Lite-Chat TP1, same image): 59.97% in deterministic mode with this change (before: 60.12% deterministic, 60.12% normal mode).

Unit tests (MI350X image): `python3 -m pytest -q test/registered/unit/layers/moe/test_topk_batch_invariant_eager.py`: 3 passed.

- aarnetalman · comment · 2026-10-27T11:44:30Z · [source](https://github.com/sgl-project/sglang/pull/46268#issuecomment-6441058550)

@rkarhila-amd Follow-up on the newer architectures: I checked DeepSeek-V3's router on its own. The config is 256 experts, 8 groups, top-4 groups, top-8, sigmoid + correction bias, renormalized, routed scaling 2.5. I routed the same 512 tokens in batches of 1 to 512 (bitwise per token), in 8 fresh processes each with AITER on and off, on MI350X:

| implementation | batch-size mismatches | same result in every process |
| --- | --- | --- |
| compiled `biased_grouped_topk_impl` (main) | 0 | yes (16/16) |
| eager (this PR, deterministic mode) | 0 | yes (16/16) |
| `biased_grouped_topk_gpu` with AITER on (AITER's routing kernel) | 0 | yes (8/8) |
| `biased_grouped_topk_gpu` with AITER off (falls back to the compiled function) | 0 | yes (8/8) |

So DeepSeek-V3-style routing did not show the problem here. The AITER path that ROCm uses is batch-invariant and stable across processes, and so was the compiled fallback in this test. Eager and compiled give slightly different bits (different rounding), but each is stable. The variance this PR fixes was seen on DeepSeek-V2-Lite's softmax `grouped_topk_gpu` path. For DeepSeek-V3-style models the PR is a safeguard: in deterministic mode the fallback no longer depends on Inductor's autotuning at all.
