# [Fix] hicache: Reject incomplete Mooncake KV reads

[Upstream PR](https://github.com/sgl-project/sglang/pull/46427) · state: open · merged: False

## Original PR description

## Motivation

Mooncake reports the bytes read, which can be less than the destination size. Reading a 4 KiB object into an 8 KiB buffer returns 4096 and leaves the tail unchanged, but HiCache currently treats it as a hit.

## Modifications

- Check read byte counts in `_get_batch_zero_copy_impl()` for v1, v2, and legacy reads. Scatter-gather reads must fill all destination buffers.
- Reject incomplete, oversized, and zero-byte reads, and mismatched result counts; preserve negative SDK errors.
- Extend the existing fixture to cover MHA, MLA, split-head pages, mixed buffer layouts, and a valid page following an incomplete page.

## Accuracy Tests

- Mooncake **0.3.11.post1**, private master over TCP: two 8192-byte destinations receive `[4096, 8192]`. Main accepts the page and legacy read; the patch rejects both. Complete objects and a scatter-gather read into `[4096, 4096]` still return matching data.

This is a real correctness hole, and the fix sits in the right place. A positive byte count used to count as a hit even when the read was short, so a partially filled KV buffer could be served as if it were complete. Validating at the single shared read boundary means v1, v2, and the legacy APIs all get the same check, and turning short, zero-byte, oversized, and mismatched results into misses is the safe direction.

A few things to confirm. Can you point to the SDK contract for batch_get_into_multi_buffers returning the summed total across sub-buffers? The code compares against sum(size), and your real Mooncake check supports it, but a pointer would make it explicit. Is it intended that a legitimately zero-byte object can never be a hit now? And the CI block in the description shows failing runs, are those unrelated? One note on the tests: the v1 zero-byte test documents the behavior but passes with and without this change, since old postprocessing already required a positive count. The legacy get case does discriminate, so coverage is there.

- donghyq · comment · 2026-10-26T08:26:06Z · [source](https://github.com/sgl-project/sglang/pull/46427#issuecomment-6411535526)

Thanks for the careful review.

For the summed byte count, Mooncake’s [v0.3.11.post1 test](https://github.com/kvcache-ai/Mooncake/blob/e9c61075720039bcfc5fffd19f847608402be3d0/mooncake-store/tests/pybind_client_test.cpp#L717-L745) uses ten 10-byte buffers per key and expects each result to be 100. The SDK returns the object’s total bytes, not the destination capacity, so equality with `sum(sizes)` is needed to establish a complete read.

Rejecting zero-byte hits is intentional for HiCache, including zero-sized destinations. It preserves v1/v2’s existing positive-count policy and makes the legacy APIs consistent. This is not a general restriction on empty objects in Mooncake.

You’re right about the v1 zero-byte test: it documents existing behavior rather than distinguishing the fix. The legacy `get` case does distinguish it. The description’s claim that all six new methods fail on unmodified main is inaccurate.
