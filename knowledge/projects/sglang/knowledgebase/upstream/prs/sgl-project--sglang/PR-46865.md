# [Perf] [AMD] diffusion: Keep the Wan VAE fast path and decode on one rank under multi-GPU, TP2 decode 28.5 -> 9.0 s on gfx1250

[Upstream PR](https://github.com/sgl-project/sglang/pull/46865) · state: closed · merged: False

## Original PR description

## Motivation

**What**
Stop Wan's `auto` VAE parallel-decode mode from choosing spatial-shard decode on gfx1250, and have only the main rank decode when the decode is single-rank, so multi-GPU runs keep the gfx1250 NHWC VAE fast path from #46722. Wan2.2 TP2 (`--num-gpus 2 --enable-cfg-parallel`) VAE decode goes from 28.5 s to 9.0 s and e2e from 124.7 s to 105.0 s.

Depends on #46722 (stacked on `amd/wan22-gfx1250-vae-nhwc`); this PR's own change is the last two commits.

**Why**
`WanVAEConfig.auto_parallel_decode_prefers_spatial_shard()` returns True, so with more than one rank the Wan decoder is built for spatial-shard decode, and `_maybe_optimize_wan_family_vae` then skips the fast path (`Wan VAE: spatial-parallel decode; skipping fast path.`). On gfx1250 the sharded decode on the slow NCDHW path takes 28.5 s, slower than the 8.6 s single-rank fast path. Once `auto` declines spatial-shard there, a second problem shows up: `AutoencoderKLWan.use_parallel_decode` was the raw config flag (always True), so `DecodingStage` stayed `REPLICATED` under cfg-parallel and both ranks decoded the full video, sharing one package's power budget (10.0 s). Making that flag follow the resolved decision in `auto` mode moves the stage to `MAIN_RANK_ONLY`.

## Modifications

- `configs/models/vaes/wanvae.py`: `WanVAEConfig.auto_parallel_decode_prefers_spatial_shard()` returns `not is_gfx1250_supported()`. Explicit `parallel_decode_mode=spatial_shard` still shards.
- `runtime/models/vaes/wanvae.py`: `AutoencoderKLWan.use_parallel_decode` is the config flag, except in `auto` mode where it is True only when spatial-shard decode is chosen. Explicit modes keep the config flag, so CUDA and non-gfx1250 ROCm behavior is unchanged in every mode.
- `test/unit/test_vae_spatial_parallel_decode.py`: the existing Wan assertion runs with gfx1250 patched off; new tests cover `auto` on gfx1250 (no shard, `use_parallel_decode` False), explicit `spatial_shard` / `patch` (unchanged), and non-gfx1250 `auto` (unchanged). The decode-flag test fails without the runtime change.

## Accuracy Tests

Wan2.2-T2V-A14B, same prompt and seed, compared as decoded video PSNR over all frames (720x1280):

| comparison | PSNR |
|---|---|
| TP2 after (single-rank fast-path decode) vs TP2 before (spatial-shard decode) | 38.7 dB |
| main-rank-only decode vs both ranks decoding | inf (identical) |

Spatial-shard and single-rank decode were never bit-identical; per-frame PSNR is flat (37.7-38.9 dB), with no shard seams.

## Benchmarking and Profiling

gfx1250 (MI450), Wan2.2-T2V-A14B, 720x1280, 193 frames, 8 steps, CFG, `--vae-decode-precision fp32`, `--enable-torch-compile false`, `SGLANG_USE_ROCM_FLYDSL=1`, `--attention-backend aiter`. TP2 is `--num-gpus 2 --enable-cfg-parallel` on the two halves of one package. Measured on a branch with #46722 and #46723 applied; times in seconds from the stage log lines.

| run | text encode | denoise | VAE decode | total |
|---|---|---|---|---|
| TP1 (reference) | 1.05 | 161.3 | 8.7 | 171.4 |
| TP2 before | 1.97 | 93.8 | 28.5 | 124.7 |
| TP2 after (this PR) | 1.96 | 93.6 | **9.0** | **105.0** |

TP2 e2e 1.19x faster (124.7 -> 105.0 s); TP2 vs TP1 goes from 1.37x to 1.63x. The remaining denoise gap to 2x is the package power limit (both halves pin the 1600 W socket cap, gfx clock ~1840 -> ~1360 MHz), not this code path.
