# [Perf] R3: Add --routed-experts-dtype int16 to halve the routed-expert host cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/47833) · state: open · merged: False

## Original PR description

## Why?

- `--enable-return-routed-experts` keeps every token's routed expert ids in a device buffer and a pinned host cache, and returns them in the response, all as int32.
- The ids are small. They run from `-1` (padding) to `num_experts - 1`, and models have far fewer than 32,768 routed experts, so half of every int32 is wasted.
- The bytes add up:
  - The pinned host cache is 216 GiB for Kimi-K3 with DCP16.
  - One response with 32k tokens × 60 MoE layers × top-8 carries 62.9 MB of ids (84 MB after base64).

## What?

- New server arg `--routed-experts-dtype {int32,int16}`. The default `int32` keeps today's bytes.
- With `int16`:
  - Both the device buffer and the pinned host cache are int16. The router's int32 ids are narrowed by the per-layer copy into the device buffer that capture already does, so the device-to-host copy moves half the bytes with no extra kernel, and `on_forward_end` is unchanged.
  - `get_topk` returns the stored int16, so the scheduler → detokenizer → tokenizer messages and the response also halve.
- Responses name the dtype, so clients decode with it:
  - `meta_info["routed_experts_dtype"]` next to `meta_info["routed_experts"]`.
  - `sglext.routed_experts_dtype` next to `sglext.routed_experts` in OpenAI chat and completions, streaming and non-streaming.
  - `extract_routed_experts_from_meta_info` decodes with the tag, and falls back to int32 for servers without it.
  - With the default int32, the routed-expert bytes are unchanged; responses only gain the tag.
- Startup check in `RoutedExpertsCapturer.create`. `int16` is rejected when:
  - the largest routed id (`num_experts - 1`) exceeds 32,767, or
  - the model config names no expert count.
- Why that range is safe:
  - Captured ids are logical routed ids, taken before EPLB remapping, so every id that is read back is in `[-1, num_experts)`.
  - Fused shared-expert columns in the device buffer may wrap, but they are dropped (`[:topk_size]`) before anything reads ids.
  - Nemotron-H puzzle checkpoints use their per-layer maximum, `max_n_routed_experts`.
- Indexer top-k capture stays int32.
- Docs: the server-argument row, and the routed-experts text in `openai_api_completions.mdx` and `sampling_params.mdx`, now say the dtype is named by the tag.

## Verification?

```text
Kimi-K3, DCP16, --enable-return-routed-experts

--routed-experts-dtype int32 (default) → host cache 216 GiB → response: int32 ids, routed_experts_dtype="int32"
--routed-experts-dtype int16           → host cache 108 GiB → response: int16 ids, routed_experts_dtype="int16"
(host cache sizes observed on our internal sglang fork; the response halves the same way: expected)

client: np.frombuffer(b64decode(meta_info["routed_experts"]), dtype=meta_info["routed_experts_dtype"])

--routed-experts-dtype int16, model with 32769 routed experts
→ startup ValueError: "... holds expert ids up to 32767, but the model has 32769 routed experts. Use int32."   (expected)
```
