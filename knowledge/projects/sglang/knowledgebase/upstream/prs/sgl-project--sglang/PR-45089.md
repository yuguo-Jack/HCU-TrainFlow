# [Perf] [NVIDIA] fused_moe: Add H20 configs for GLM-5.3-Flash TP8/TP4

[Upstream PR](https://github.com/sgl-project/sglang/pull/45089) · state: closed · merged: True

## Original PR description

## Motivation

With plain tensor parallelism (`--tp 8` or `--tp 4`, no `--ep`), GLM-5.3-Flash runs its routed experts through the Triton fused MoE. The serving lookups are:

- `E=289` for the target layers, because the shared expert is fused into the routed experts by default.
- `E=288` for the NextN/MTP draft layer, and for any run with `--disable-shared-experts-fusion`.

No config exists for these shapes on any GPU, so on H20 every MoE layer logs `Using default MoE kernel config` and runs with `BLOCK_SIZE_M=64`. #38913 added H20 configs for the EP4/EP8 shapes (`E=72`/`E=36`, `N=2048`). This PR adds the TP shapes.

## Modifications

Four Triton 3.8.0 configs (main pins torch 2.14.1, which ships Triton 3.8.0):

| File | Used by |
| --- | --- |
| `E=289,N=256,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` | TP8, target layers |
| `E=288,N=256,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` | TP8, MTP draft layer / shared-expert fusion disabled |
| `E=289,N=512,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` | TP4, target layers |
| `E=288,N=512,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128].json` | TP4, MTP draft layer / shared-expert fusion disabled |

The files were generated with the stock `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton.py`, using the default search space (1,280 configs after the `BLOCK_SIZE_K` filter) and the default 18 batch sizes. Each batch size was tuned in its own process on one GPU.

To get `E=289`, I applied #43647's one-line `common_utils.py` change locally. That change adds `Glm5NextForConditionalGeneration` to the fused-shared-expert list; without it, the tuner writes only `E=288`. This PR leaves the tuner alone so it does not overlap #43647.

Small batches now use `BLOCK_SIZE_M=16` (M ≤ 512), M=1024 uses 32, and M ≥ 1536 mostly uses 64. The separate down-projection (`_down`, TMA) configs from `tuning_fused_moe_triton_sep.py` are not included. Serving keeps reusing the up config for the down GEMM, as it does today.

## Setup

All numbers below are from a re-run on 2026-11-01 with this branch rebased onto main `b801787`. The four files are the ones tuned on 2026-10-19; they were not re-tuned.

- Image `lmsysorg/sglang:nightly-dev-cu13-20261031-a2cafa56` (torch 2.14.1+cu130, Triton 3.8.0, sglang-kernel 0.4.10, flashinfer 0.7.2, the versions main pins), with `PYTHONPATH` set to a source tree. The default arm uses main `b801787`. The tuned arm uses this branch rebased onto `b801787`, so it reads the four files from their in-tree location. The two trees differ only in these files.
- Tuning ran with image `nightly-dev-20261015-a6a8c560`, whose fused-MoE kernel, config loader and tuner files matched main `58ad074`. Since then main has changed the Triton fused-MoE kernel (`sglang/kernels/ops/moe/fused_moe_triton_kernels.py`) and `fused_moe.py`. The config loader and the tuner script are unchanged.
- Two 8× H20 96 GB nodes. On node A, one GPU overheats under sustained load (0.7–1.2 GHz, 87–90 °C). During tuning, the 10 batch sizes first tuned on it were re-tuned on the other GPUs, and 7 of those picks changed. The kernel benchmark (GPUs 0, 1, 2, 4) and TP4 serving (GPUs 4–7) run on node A without that GPU. TP8 serving runs on node B, where all eight GPUs stayed at 1980 MHz and at most 52 °C in every case (`nvidia-smi` sampled every 2 s).

## Kernel benchmark

Stock tuner in benchmark mode (no `--tune`; the #43647 line is applied so that `E=289` is benchmarked): 100 iterations of 10 CUDA-graph replays per M. For each shape, the default arm and the tuned arm alternate on the same GPU for 3 rounds; the table shows the median. Speedup = default / tuned.

Like the tuner, the benchmark routes each token to 8 random experts out of E. The `E=289` columns therefore treat the fused shared expert as one of 289 candidates, while serving sends every token to it (top-k 9). This is why the `E=289` and `E=288` columns are nearly identical. The serving results below use the real routing.

## Serving

The two arms of each pair use the same node, image, and flags, and differ only in the source tree on `PYTHONPATH` (see Setup). The tuned arm's server log shows `Using MoE kernel config from .../triton_3_8_0/E=289,...` (and `E=288,...` for the draft layer); the default arm's shows `Config file not found at .../triton_3_8_0/E=289,...`. Other settings:

- Triton MoE (auto-selected), BF16 KV cache, default DSA backends, radix cache off.
- `--reasoning-parser glm45 --tool-call-parser glm47`.
- MTP: `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.
- Load: `sglang.bench_serving --dataset-name random-ids --tokenize-prompt --random-range-ratio 1.0 --request-rate inf --seed 42`, with 4× concurrency prompts (8 at concurrency 1), after one warm-up run per server start.
- Accept length is the server's running average.

| Layout | Default | Tuned |
| --- | ---: | ---: |
| TP8 (node B) | 0.942 | 0.934 |
| TP4 (node A) | 0.942 | 0.948 |

On 2026-10-19 the same eval gave 0.934 → 0.942 (TP8) and 0.928 → 0.940 (TP4). The differences go both ways and are at most 1.2 points, against a standard error of about 1.1 points for a single 500-question score at this accuracy.
