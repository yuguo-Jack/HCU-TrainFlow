# [Fix] dspark: Keep the real verify accept cost under simulated acceptance

[Upstream PR](https://github.com/sgl-project/sglang/pull/46840) · state: closed · merged: True

## Original PR description

## Motivation

`SGLANG_SIMULATE_ACC_LEN` is a benchmark mode. It should change only the accepted length. Every operation real serving runs in a verify step should still run at real cost, so a simulated run's step time matches a real run at the same acceptance length.

**What this PR delivers is parity in the accept region.** After this change, the GPU work a simulated step does in its accept region is the real accept plus one row draw. Step time from the batch logs barely moves: at 128 running per rank, simulation is ~0.6 ms slower than real both before and after this PR. The remaining gap is in MegaMoE, most likely routing on the simulated text, which this PR does not touch.

DSpark had three paths that changed the per-step work only under simulation:

1. **Eager accept (#45421).** `accept_and_finalize` passed `sampling_info=None` under simulation, so a sampling batch ran `AcceptGreedy` (row argmax) instead of the sampling accept that real serving runs: the draft and target softmax plus the rejection kernel.
2. **Eager simulated bonus (#41981).** `simulated_bonus_sample` drew a Gumbel-max sample over the full vocabulary for all bs x (gamma+1) verify rows, then kept only the row at the simulated length. This is simulation-only work, about 6x what one row needs.
3. **Fused static accept tail under `SGLANG_DSPARK_SIMULATE_FOLD`** (opt-in, with `SGLANG_DSPARK_FUSED_ACCEPT_TAIL`):
   - The verify graph skipped the row argmax that the greedy accept runs.
   - With TP > 1 and the accept-site broadcast selected (the default `SGLANG_SPEC_TP_SYNC=all`), real serving turns the fused tail off and runs `_accept`: 3 broadcasts, finalize, out-tokens and the static-buffer copies. Simulation kept the fused tail with 2 broadcasts.

Items 1 and 2 roughly cancel at large batch and do not cancel at small batch, so the error changes sign with batch size (numbers below). Fixing only item 2 would make simulation cheaper than real serving at every batch size.

## Modifications

- **Eager accept.** `TargetVerifyExecutor.accept_and_finalize` runs the accept that real serving runs, for greedy and sampling batches alike. `build_accept_outs` then overrides `correct_len` with the simulated value and draws the bonus at the simulated row, as before.
- **Simulated bonus.** `simulated_bonus_sample` draws only the simulated row per request. It uses `simulated_bonus_sample_graph`, the row kernel the graph path already uses, seeded from `random.getrandbits(31)` as the graph path is. The all-rows kernels are removed. The only simulation-only work left in the accept is this one row draw (+73 us at 128 per rank).
- **Fused static accept tail.**
  - `DsparkVerifyEpilogue` takes the same fused-tail decision as real serving: the tail is off whenever the accept-site broadcast is selected. Under `simulate_fold` with the broadcast, simulation now runs `_accept` like real serving and adds the in-graph row draw.
  - `_static_accept_tail` always computes the row argmax. Under `simulate_fold` the tail still takes the simulated bonus and does not read the argmax.
- **Test.** `test_dspark_simulated_bonus.py::test_bf16_full_vocab_low_temperature` accepts any token whose logit equals the row max. bf16 logits tie at the max, and Gumbel-max may pick any tied token, while the test expected the first argmax.

`SGLANG_SIMULATE_ACC_GREEDY=1` is still the explicit way to skip the sampling work. It sets the batch's sampling info to `None` for both the draft and the accept, but only for sampling batches that have:
- no grammar;
- no penalties, logit bias or custom logit processor;
- no top-k, top-p or min-p.

Greedy requests carry top_k=1, so a mixed greedy + sampled batch also keeps the real sampling work.

What does not change:
- The accepted length comes from the same CPU draw (`sample_simulated_acc_len`), so its distribution is the same as before.
- The bonus keeps the request's sampling law: a Gumbel-max sample at the request's temperature, argmax for greedy, and unchanged top-k / top-p handling. Sampled tokens differ from before only through the RNG stream.
- Non-simulated paths are unchanged.

**AMD / HIP.** Simulated runs on HIP get slower. #41981 skipped the sampling accept under simulation on HIP on purpose, and #45421 extended that skip to CUDA. With this PR the softmax and rejection kernels run under simulation on HIP too, as they do in real serving there. Set `SGLANG_SIMULATE_ACC_GREEDY=1` to keep the old cost for temperature-only batches.

Other simulation-specific behavior I checked and left as is:
- `SGLANG_OPT_DSV41_DSPARK_SIM_DRAW_AHEAD` only moves the simulation-only length and seed draw ahead of the draft launch. It skips no real work.
- The sampling-accept region graph (`SGLANG_OPT_DSV41_SAMPLING_ACCEPT_GRAPH`) already runs the full sampling accept under simulation, then applies the simulated length and the row-c bonus. The eager path now matches it.
- `SGLANG_SIMULATE_ACC_LEN > 1` requires a verify-all schedule. A simulated run therefore cannot reproduce a deployment that trims verify windows (cap-accept, or compact with a profiled SPS table).
- The block-accept estimator refuses to run under simulation. It is observability only.
- Grammar: simulation commits `drafts[:c]` without checking them against the grammar, so a json-schema request can fail with "Grammar accept_token failed". It is not caused by this PR. On TP4 at T=1, main under simulation failed 2 of 32 requests, and this PR failed 0 of 32 in the same run and 1 of 4 in another. Every request that completed produced valid JSON.

GPU coverage:
- Covered: the eager accept under DP attention (sampled, mixed, top-p / top-k, grammar); TP4 static verify with `SIMULATE_FOLD` and the fused tail on (captured, rng sync) and off (default sync); the existing unit tests. The server does not log whether a step replayed the folded accept, so folded-step coverage rests on the capture log and the outputs.
- Not covered:
  - the sampling-accept region graph;
  - `SIM_DRAW_AHEAD`;
  - block-wise rejection;
  - compact verify;
  - PD disaggregation;
  - AMD.

## Benchmarking and Profiling

Setup:
- Hardware and model: GB300, DeepSeek-V4.1-Flash FP4, DSpark block 5.
- Serving: DEP4 (TP4, DP-attention 4, EP4, MegaMoE), static verify, default env.
- Load: chat requests at temperature 1, `ignore_eos`, 2048 output tokens, short prompts. All requests in a phase start together, giving 8, 32 or 128 running per rank.
- Arms:
  - real acceptance (no simulation);
  - main under simulation;
  - this PR under simulation.
  The simulated arms use `SGLANG_SIMULATE_ACC_LEN=2.45`, the real run's AL.

**GPU kernel time per decode step** (torch profiler, 20 steps, mean of 4 ranks). Decode is GPU-bound here: kernel time is 99% of the step.

| kernels (us per step) | 128 / rank: real | main, sim | this PR, sim | 8 / rank: real | main, sim | this PR, sim |
|---|---|---|---|---|---|---|
| target softmax (sampling accept) | 282.2 | - | 281.9 | 26.4 | - | 26.2 |
| `speculative_sampling_classic_kernel` | 118.8 | - | 115.8 | 56.5 | - | 53.1 |
| row argmax (`AcceptGreedy`) | - | 105.1 | - | - | 8.8 | - |
| all-rows simulated bonus | - | 413.8 | - | - | 31.4 | - |
| row-only simulated bonus | - | - | 74.8 | - | - | 9.2 |
| other accept-region (rand, bonus gather, seed) | 6.0 | - | 7.7 | 5.6 | - | 7.3 |
| **accept region total** | **407** | **519** | **480** | **89** | **40** | **96** |
| all kernels | 30,066 | 30,288 | 30,207 | 14,185 | 14,303 | 14,466 |
| of which MegaMoE | 16,038 | 16,246 | 16,215 | 8,152 | 8,341 | 8,431 |
| all kernels minus MegaMoE | 14,029 | 14,042 | 13,991 | 6,033 | 5,962 | 6,036 |

- **Main under simulation:** the accept region was 112 us slower than real at 128 per rank and 48 us faster at 8 per rank.
- **This PR:** the accept region is the real accept plus the one row draw (+73 us at 128, +7.7 us at 8).
- **Outside the accept region**, both simulated arms spend +0.18-0.28 ms more in MegaMoE. This is most likely routing on the simulated text, and this PR does not change it. Non-MoE time is within 0.07 ms of real.

**Decode step time from the batch logs** (running x accept len / gen throughput, p50, mean of 4 runs: two repetitions in each of two arm orders):

| running per rank | real | main, sim | this PR, sim |
|---|---|---|---|
| 8 | 14.14 ms | 14.29 ms | 14.36 ms |
| 32 | 18.92 ms | 19.12 ms | 19.19 ms |
| 128 | 30.15 ms | 30.77 ms | 30.76 ms |

The log-based gap to real is larger than the kernel-time gap, for two reasons: the MegaMoE difference, and a smaller logged batch in the real run (requests with a higher accepted length finish earlier: 126.8 vs 128 running at the 128 point). Run-to-run spread is up to 0.21 ms per cell.
