# tokenizer perf optimization

[Upstream PR](https://github.com/sgl-project/sglang/pull/39771) · state: closed · merged: True

## Original PR description

## Motivation

`OpenAIServingBase.handle_request` performs request conversion inline on the serving event loop. That conversion is not cheap: for `/v1/chat/completions` it runs the message processor and the chat template (jinja) and produces the full tokenized prompt. For a 100k+ token prompt this occupies the event loop for hundreds of milliseconds.

While the loop is blocked, everything else the server is doing stalls with it:

- new connections are not accepted,
- already-open streaming responses are not flushed, so unrelated in-flight requests see their inter-token latency spike,
- health/liveness endpoints sharing the loop stop responding.

The component that does the heavy part is the Rust tokenizer, which releases the GIL while encoding, so this work can genuinely overlap with the event loop instead of serializing behind it. The jinja render is still Python and still competes for the GIL, but the loop keeps running instead of waiting for the whole conversion to finish.

## Modifications

Single file, `python/sglang/srt/entrypoints/openai/serving_base.py`:

- In `handle_request`, `_convert_to_internal_request` is now awaited through `loop.run_in_executor(None, ...)` instead of being called inline.

The conversion logic itself is untouched, and the returned `adapted_request` /`processed_request` are the same objects as before — only the thread they are produced on changes. The surrounding flow is unchanged: validation still runs on the loop, `received_time` is still stamped before dispatch, and the streaming / non-streaming branches below are unaffected. The default executor is used, matching the existing pattern in `http_request_decompression.py`.

## Accuracy Tests

Not applicable. This PR does not touch the model forward path, kernels, sampling, or the tokenizer itself. The same conversion runs on the same inputs, so model outputs are unchanged; the only difference is which thread executes it.

## Speed Tests and Profiling

Deployment: DeepSeek-V4-Flash, PD-disaggregated `dwdp` serving config,
`--max-running-requests 480`.

Workload: long-context, average input length 265k tokens.

- QPS: **+3%** with this patch (same node, same server args).

The gain comes from the event loop no longer serializing on prompt conversion: with 265k-token inputs, jinja rendering plus full-prompt tokenization holds the loop for long enough that accepting new requests and flushing in-flight streams are both delayed, so the server is not saturated on the compute side even at max-running-requests 480.
