# [Perf] deepseek-v4.1: Run encoder SWA bounded replay in the breakable prefill graph

[Upstream PR](https://github.com/sgl-project/sglang/pull/44930) · state: closed · merged: True

## Original PR description

- `--enable-encoder-swa-bounded-replay` now accepts `--cuda-graph-backend-prefill breakable`; other prefill graph backends stay rejected, and so does any prefill graph on ROCm, which replays hits in a forward of their own
- The static batch carries the fold's `encoder_swa_replay`, `encoder_swa_row_floor` and `encoder_swa_compress_rows`, so capture and replay build the same window floors and compressor slots as an eager prefill
- Under the graph the request-window layout covers the live rows and pads to the bucket: padding rows get no window, write past the live rows and commit nowhere (`window_layout(padded_rows=...)`, `WindowLayout.leading_rows`); the window groups are fixed at one per request slot, at most one per row
- `refresh_for_breakable_cuda_graph_replay_` copies the request-window layout in place, and capture and replay activate it
- Graph metadata keeps its compressor slots in its own buffer (`_compressor_out_loc(own_buffer=True)`), so the in-place refresh before a replay leaves the static `out_cache_loc` as the runner filled it
- With DP attention, the prefill graph vote counts the folded replay rows, which an extend replay runs, so the vote agrees with the runner's own check
- The request-window workspace also covers the largest breakable prefill graph bucket, which can exceed a DP rank's share of the chunk
- Add tests for the padded layout, the slot buffer, the startup check and the workspace size; all five fail on main
- Checked on GB300, TP4/EP4, DeepSeek-V4.1-Flash, encoder and decoder replay on:
  - The replay rows' cached c1/c2 bytes, compared before and after each prefix-hit prefill: 0 rows changed over 8 graph and 8 eager hits
  - GSM8K, all 1,319 questions behind a shared 8-shot prefix (903 replay prefills, 909 of 910 prefills in the graph): 97.04%; with the same settings on the previous day's main, eager prefill with replay scored 97.50% and the graph without replay 97.27%
  - TTFT of 417 new tokens after a 13,312-token cached prefix: 81.2 ms; eager prefill with replay took 231.6 ms on the previous day's main; contexts above 16K still run eager
- Checked on GB300 with DP attention 2 / EP 2 and MegaMoE, encoder and decoder replay on: GSM8K, all 1,319 questions behind the same prefix at 64 concurrent requests, 97.27% with the graph and 97.35% eager
- Known issue on main, not changed here: with DP attention and MegaMoE, the breakable prefill graph hangs when one DP rank prefills while another is idle, because decoder replay's late-layer row-count gather runs only in the idle rank's eager forward

Supersedes #43010.

No behavior change unless encoder replay runs with the breakable prefill graph, which used to be rejected at startup; in every breakable prefill graph the captured compressor slots are now a copy refreshed before each replay instead of the static `out_cache_loc` itself.
