# [Refactor] [Apple] MLX: Fix array leak in Metal kernel bindings

[Upstream PR](https://github.com/sgl-project/sglang/pull/46262) · state: open · merged: False

## Original PR description

## Motivation

`rope_pool_fused` currently wraps every output by creating `mx.array(0)` and construct the returned C++ array over it. The original array is never destroyed, leaking its descriptor and scalar buffer on every call, even when the outputs are never evaluated.

## Modifications

- Accept MLX arrays as `const array&` arguments.
- Return `std::tuple<array, array, array, array>` through nanobind instead of manually constructing array objects.

This lets nanobind handle type conversion and object lifetime normally.

Verified on an M4 Pro, mlx 0.32.4, nanobind 3.1.0. On main each call leaks 16 bytes of active Metal memory, one scalar per output. On this head 1000 calls return to baseline. The const array& path also turns a segfault on a bad input type into a TypeError.

Two asks. The cast works only because mlx and `setup_metal.py` pin the same nanobind; a comment at the pin saying it must match mlx would save the next person a day. And the test @adityavaid asked for is on a branch for cherry pick: https://github.com/jlee5814/sglang/tree/test/rope-pool-fused-leak-46262 (1000 calls, assert `mx.get_active_memory()` returns to baseline, fails on main, passes here). Note the MPS CI job doesn't built the Metal extension, so it skips in CI until the job runs `setup_metal.py`.
