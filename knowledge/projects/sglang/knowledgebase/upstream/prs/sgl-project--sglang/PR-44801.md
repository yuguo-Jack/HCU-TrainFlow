# [Feat] tracing: Record why requests failed, and mark only server faults as errors

[Upstream PR](https://github.com/sgl-project/sglang/pull/44801) · state: open · merged: False

## Original PR description

## Motivation

Traces don't tell a failed request from a normal one, and they mark the wrong things as errors:

- A request's root span shows that it finished, but not whether it failed or why: an overloaded server, a rejected prompt and a client abort all look like a normal request.
- Every `trace_ctx.abort(abort_info=...)` sets the thread span's status to ERROR, whether the request hit a server fault, was rejected as invalid, or was aborted by its caller. A sampler or alert that keys on error spans counts every bad request and every client disconnect as a server failure.
- A request that fails in the tokenizer before reaching the scheduler (invalid input, a LoRA or encoder error) never has its trace ended. With sync tracing its root span is never exported, so rejected requests don't appear in traces at all.

## Modifications

1. **Thread spans are errors only for server faults.** Each abort that has an HTTP status passes it in `abort_info["status_code"]`, matching the status the client gets:
   - scheduler: 400 for a missing bootstrap room or a bad sampling mask, 503 when the queue is full, and the `FINISH_ABORT`'s own status when retiring an unadmitted or chunked request;
   - PD prefill: 400 over KV capacity, 500 on KV transfer or bootstrap failure, and the sampling-mask reason's status;
   - EPD encoder: 504 on timeout, otherwise `MMError.code` or the worker's error code, falling back to 500.

An aborted thread span is marked ERROR only for a 5xx, as the OpenTelemetry HTTP conventions do for server spans. Attributes whose value is None are left out instead of being exported as empty values.
2. **Root spans record how aborted requests ended.** When the tokenizer finishes an aborted request (from the scheduler's abort message, or a batch output with an abort finish reason), it sets `error.type` on the root span to the status code (e.g. `"503"`), or `"abort"` when there is none, and sets status ERROR only for a 5xx. This is implemented once, in `set_root_span_error`, for both sync and async tracing. `_handle_abort_req` now ends the trace after computing the finish reason, since attributes set after the root span ends are dropped.
3. **Traces of requests that fail before reaching the scheduler now end.** `_release_req_states_on_failure` now takes the exception. For each undelivered request it records the status the HTTP entrypoints return for that exception (an `HTTPException`'s own code, 400 for `ValueError`, 500 for any other `Exception`, none for a cancellation) and ends the trace. Dispatched requests are unchanged: their trace ends on the scheduler's abort response.

Docs: new "Failed Requests" section in `production_request_trace.mdx`.

### Behavior changes for existing tracing users

- Aborted thread spans without a 5xx status are no longer ERROR. That includes client aborts, 4xx rejections, a cancelled encode, the Mooncake sender's own abort, and spans auto-closed at garbage collection, all of which were ERROR before.
- Root spans of aborted requests gain `error.type`, plus ERROR status for a 5xx.
- Requests rejected before reaching the scheduler now end their trace with a status. Before, sync tracing didn't export them at all, and async tracing ended the root span at garbage collection with no status.

Not applicable: tracing only, no change to model outputs.

## Speed Tests and Profiling

No hot-path cost: status codes are only added on abort paths, and with tracing off the new calls go to `TraceNullContext` or return early.

## Tests

- `test_trace.py::test_aborted_thread_span_is_an_error_only_for_server_faults` (400, no status, 500)
- `test_trace.py::test_aborted_request_records_its_status_on_the_root_span` (503, 400, no status, and a non-abort finish)
- `test_tokenizer_manager_rid_cleanup.py::TestTraceRecordsAbortStatus` (the status is recorded before the root span ends, on the scheduler-abort and batch-output paths)
- `test_tokenizer_manager_rid_cleanup.py::test_undelivered_trace_ends_with_the_status_the_client_gets` (`HTTPException` 503, `ValueError`, `RuntimeError`, `CancelledError`)
- The existing `_release_req_states_on_failure` tests pass the new `error` argument.
- End to end on 2× L4 (Qwen2.5-0.5B-Instruct, spans exported to Jaeger), both with a regular server at TP=2 and with PD disaggregation (NIXL): an over-length prompt (400) ended its root spans with `error.type=400` and no ERROR status; a streamed request the client closed early ended with `error.type=abort`, not ERROR.
- `test/registered/unit/observability`, `managers` and `disaggregation` fail the same tests as `main` and no others.
