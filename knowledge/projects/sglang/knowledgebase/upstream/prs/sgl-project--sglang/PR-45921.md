# [Perf] dsv4: Optionally stage V4.1 engram rows from the shared host table on the scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/45921) · state: closed · merged: True

## Original PR description

On GPUs without ATS, the GPU maps the shared Engram host table in its own page tables. A gather of random rows from a table far larger than its translation reach then runs at a fraction of PCIe bandwidth, and it sits on the forward stream. Sorted reads soften this but do not remove it.

This adds an opt-in path, `SGLANG_OPT_DSV41_ENGRAM_HOST_STAGING=1` (default off), that moves the gather off the forward:

- The scheduler knows every token of an extend batch before its forward. `EngramRowStager` builds each token's look-back window from the requests' fill ids and hashes it on the CPU through `EngramHasher.hash_windows`, the same code the hasher's torch path runs, on host copies of the hasher's buffers.
- It gathers each Engram layer's fp8 rows and e8m0 scales from the shared table into pinned memory with a small thread pool, and copies them to the GPU on a side stream while the previous forward runs.
- The layer waits on the copy's event and only dequantizes contiguous rows (`EngramEmbedding.dequant_staged`); padded rows of a prefill graph are zero.
- Under the breakable prefill graph, the Engram lookup becomes an eager break when the path is on, and it reads the replay batch's staged rows from the forward context.

When the switch is on, the path still turns on only where it applies: every Engram table in the shared host layout (the only layout that maps every row in each process), a GPU without ATS (the same device attribute the sorted reads check), and no prefill context parallelism. Everywhere else, and always with the switch off, the stager is never built and the forward runs the table lookup exactly as before.

A batch falls back to the forward's lookup when it is not a plain extend (decode, target verify), or when a request's newest token is still on the device (a decode row in a converted or mixed batch under overlap scheduling). With encoder SWA bounded replay, the staged rows follow the folded extend, so a replayed request starts at its replay start. The unfolded replay path asserts that nothing was staged.

It is meant for large prefill batches, such as a dedicated prefill node, where the host work hides behind the previous forward. Online serving with small, variable batches may be slower with it on and is still being tuned.

Verification:

- Staged rows match the table lookup bit for bit in every layer: in eager mode and in prefill-graph replay, with encoder replay on (folded replay rows included) and off.
- DeepSeek-V4.1-Flash DEP4 offline prefill on a GPU without ATS is faster with the switch on.
- The hasher's torch path is unchanged by the extracted `hash_windows`, and the stager's CPU hash ids match it on random batches with image tokens and chunked prefixes.

The shared layout under the breakable prefill graph needs #45881 (merged), independently of this change: the hang it fixed occurs without staging.
