# [Fix] qwen4_exp: Split the PLE prefill short conv under the int32 limit

[Upstream PR](https://github.com/sgl-project/sglang/pull/46421) · state: open · merged: False

## Original PR description

## Motivation

Serving Qwen3.8-Flash-Next on ROCm, a prefill batch that holds many short requests next to one long request kills the scheduler on both TP ranks:

```text
RuntimeError: Expected canUse32BitIndexMath(input) && canUse32BitIndexMath(output)
  File ".../sglang/srt/models/qwen4_exp.py", in _short_conv
    conv_output = F.conv1d(
```

The PLE short conv pads every request in the batch to the longest one:

- conv input: `[num_requests, 10240, longest_extend + 9]` (10240 = `hidden_size × hc_count`, 9 = conv state length)
- PyTorch does not send dilated grouped convs to MIOpen, so on ROCm `F.conv1d` runs the native depthwise kernel, which requires fewer than 2**31 − 1 elements in its input and output.
- The limit is passed once `num_requests × (longest_extend + 9) ≥ 209,716`. A batch of fresh 8k prompts never gets there (the default 16,384-token chunk holds at most 3 of them). Prefix-cache hits do: 94 requests of which one extends 2,223 tokens are enough, and so are 42 requests of which one extends 4,985 tokens.
- `bench_serving --warmup-requests 128` produces such batches: it sends 128 copies of one prompt, which then hit the radix cache.

Observed: `amd/Qwen3.8-Flash-Next-Quark-MXFP4`, TP2, MI355X, random 8k-in/1k-out at concurrency 128 crashes in the bench warmup on the unmodified image with the commands below. The crashing batch logs no "Prefill batch" line, because prefill stats are logged after the forward.

Scope:

- Models: `Qwen4ExpForConditionalGeneration` (Qwen3.8-Flash-Next checkpoints). The MTP draft has no PLE layers.
- Code path: ordinary prefill/extend and target-verify batches of the PLE short conv. Decode is unchanged.
- Platforms: ROCm. On NVIDIA, PyTorch sends the over-limit depthwise conv to cuDNN when cuDNN ≥ 9.3 with the v8 API, so only older cuDNN setups reach the same check.
- Prior art: #43032 (open) replaces the padded path with a packed varlen Triton kernel. Its motivation is memory, and it is enabled only when `is_cuda()`, so ROCm keeps the padded `F.conv1d` path. No issue or PR covers this crash.

## Modifications

- `qwen4_exp.py`: new `_short_conv1d()` runs the depthwise conv in pieces whose input stays under the limit.
  - Rows are independent, so it splits by rows first.
  - If one row alone is too long (chunked prefill off, prompt ≥ 209,707 tokens), it also splits that row's output columns, each piece carrying the 9-column conv halo.
  - Batches under the limit take the same single `F.conv1d` call as before.
- The padded memory (`num_requests × longest_extend × 10240` per temporary) is unchanged; #43032 addresses it on NVIDIA.
- New CPU test `test/registered/unit/models/test_qwen4_exp_short_conv_split.py`.
  - Runs the real `_prepare_ple_batch` and `Qwen4ExpPLELayer._short_conv` on a 4-request batch with lengths `[37, 1, 3, 2]`.
  - Lowers the limit to 200 (row split) and 100 (row and column split).
  - Checks that every `F.conv1d` input is under the limit and that the output equals the single-call result.
  - On main it fails: one call, `AssertionError: 1 not greater than 1`.

## Accuracy Tests

- The split is exact: each output element is computed from the same 4 inputs and weights by the same kernel.
- CPU test: the output is `torch.equal` to the single call (integer-valued data, so no rounding differences).
- MI355X, one GPU, the conv at the limit (bf16, 10240 channels, kernel 4, dilation 3):
  - unsplit `F.conv1d`, 94 rows × width 2231 (2,147,471,360 elements): runs;
  - 94 rows × width 2232 (2,148,433,920 elements): raises `canUse32BitIndexMath`;
  - `_short_conv1d` at 94 × 2232: 16.1 ms, output `torch.equal` to two unsplit half-batch calls.
- No task-level accuracy eval was run: the change is exact, and batches under the limit take the unchanged single call.

## Speed Tests and Profiling

Setup:
- Image: `lmsysorg/sglang-rocm:v0.5.22-rocm724-mi35x-20261021`, PyTorch 2.11.0+rocm7.2; its `qwen4_exp.py` is byte-identical to SGLang `a2e4ffbcea`, and the changed code is identical on main.
- Hardware: 2× MI355X (gfx950).
- Model: `amd/Qwen3.8-Flash-Next-Quark-MXFP4`, revision `b2091c3809eb51902f46a163973362d8176f9e58`.
- Baseline: the image as shipped. Patched: this change applied to `qwen4_exp.py` (the GPU runs used a revision with two extra `max(1, …)` clamps on the piece sizes, which never take effect).
- One server launch per row below, same request stream (2,832,445 input, 353,963 output tokens).

- The patched run's 125-request batch (10,391 new and 920,576 cached tokens) sits at the point where the baseline crashed; no out-of-memory error at `--mem-fraction-static 0.9`.
