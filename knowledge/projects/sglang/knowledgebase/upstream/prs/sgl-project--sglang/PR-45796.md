# [Fix] dp-attention: Pad extend host lists out of place so pre-planned DSA metadata keeps its rows

[Upstream PR](https://github.com/sgl-project/sglang/pull/45796) · state: closed · merged: True

## Original PR description

## Motivation

TL;DR there is a bug in batch size padding when decode runs in eager mode. The attention plan holds inconsistent values: some are padded and some are not, causing assert to fire and crash the server. The padding is needed because some collectives expect the same tensor shapes on all ranks.

DP-attention decode with EAGLE MTP on a DSA model (GLM-5.2-NVFP4, DEP16, EAGLE 5-1-6, `--cuda-graph-max-bs-decode 32`) crashes every DP rank once any rank holds more requests than the draft-extend CUDA graph covers:

```
dsa_indexer.py  _get_topk_paged -> deepgemm_paged_mqa_logits_split
dsa_indexer.py  _chunked_fp8_paged_mqa_logits -> deep_gemm.fp8_paged_mqa_logits
RuntimeError: Assertion error (csrc/apis/attention.hpp:530): _batch_size == batch_size
```

In DeepGEMM v0.2.3 that assert is `block_table.size(0) == q.size(0)`: the indexer passes more query rows than page-table rows.

Mechanism:

1. When the draft-extend graph cannot run, `prepare_for_draft_extend` plans attention metadata on the local batch, before MLP-sync padding, and marks it ready. This pre-pad plan is used as-is (#27193).
2. The DSA backend stores `forward_batch.extend_seq_lens_cpu` by reference as `dsa_extend_seq_lens_list`. Its page table has `n*b` rows (`b` local requests, `n` draft tokens).
3. `ForwardBatch._pad_inputs_to_size` then grows that same list in place to the DP max `B` (`list.extend`, introduced in #33829).
4. The indexer's `q_offset = sum(dsa_extend_seq_lens_list)` becomes `n*B`, while the page table still has `n*b` rows. Every rank with `b < B` asserts. With `n*B` above the SM count, the failure is in the chunked branch, as in the trace above.

## Modifications

- `_pad_inputs_to_size` rebinds `extend_seq_lens_cpu`, `extend_prefix_lens_cpu` and `extend_logprob_start_lens_cpu` instead of extending them in place. The tensors and the mamba host lists in the same function already pad out of place.
  - Metadata planned before padding keeps the pre-pad lengths it was built from.
  - `extend_logprob_start_lens_cpu`, which `init_new` binds directly to the ScheduleBatch's list, no longer writes padding into scheduler state.
- Readers of the padded batch read the live `ForwardBatch` attribute, so they still see the padded lists.
- Regression case in `test/registered/unit/model_executor/test_mlp_sync_pad_unpad.py`.

## Validation

- Unit: `test_mlp_sync_pad_unpad.py`, 12 passed. The new case fails without the fix (`[2, 2, 2] != [2, 2]`).
- Reproducer on 1x GB300 node (152 SMs): GLM-5.2-NVFP4 with dummy weights, `--tp 4 --dp 4 --ep 4 --enable-dp-attention`, EAGLE 5-1-6, `--cuda-graph-max-bs-decode 32 --max-running-requests 192`, 160 concurrent `random-ids` requests.
  - Before: every rank crashed about 40 s after the server was ready, with the trace above (eager `_draft_extend_for_decode` -> MTP layer -> indexer, chunked branch).
  - After: 640/640 requests completed with 0 exceptions, across eager decode steps with per-rank batches of 26-45.
- Real weights, same shape, 64 concurrent greedy requests: draft extend in CUDA graphs vs forced eager (`SGLANG_DISABLE_DRAFT_EXTEND_CUDA_GRAPH=1`, which plans pre-pad on padded ranks). 3 x 512 prompts per arm, 0 errors. Mean decode-log acceptance length over windows with >= 13 running requests per rank, where padded eager draft extend runs: 4.168 (graph, n=180) vs 4.163 (eager, n=182). Bench-reported acceptance per repetition: graph 4.41 / 4.37 / 4.12, eager 4.26 / 4.32 / 4.12.
