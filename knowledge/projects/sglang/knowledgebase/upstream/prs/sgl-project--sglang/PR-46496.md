# [Fix] scheduler: Keep the new-token ratio at its floor after a KV-full retraction

[Upstream PR](https://github.com/sgl-project/sglang/pull/46496) · state: open · merged: False

## Original PR description

## Motivation

Fixes #46495.

With `max_tokens` unset (the OpenAI chat default), `max_new_tokens` is about the context length minus the prompt. After a KV-full retraction the scheduler sets the new-token ratio to `retract_decode`'s estimate, which divides by the survivors' unclipped `max_new_tokens` (`new_token_ratio_tracker.py:41-49`). So it lands far below `NewTokenRatioTracker.min`, which every other writer of the ratio (init, `decay_step`, `reset`) keeps. Admission multiplies the ratio by each running request's remainder clipped to 4096 (`schedule_policy.py:756-765`). So right after the pool ran out it reserves much less decode headroom and admits more prefill work, until the next decode step puts the ratio back at the floor.

The issue has the CPU repro and its output on main: the ratio goes 0.0980 -> 0.0117, the survivors' decode reservation drops from 15254 to 1819 tokens, and two fresh 2000-token requests are admitted with 20000 tokens free (none at the floor).

## Modifications

`update_running_batch` clamps the estimate to the tracker's floor (`scheduler.py:4471`, one line plus a comment). Above the floor the estimate is used as before: with `max_tokens=2048` it is 0.7422, and a later retraction can still lower the ratio toward the floor.

The issue lists two other forms: the estimate in clipped units, or on the clipped remainder. Both change the estimate itself, and `add_one_req_ignore_eos` (`schedule_policy.py:1217-1223`) multiplies the ratio by unclipped `max_new_tokens`: with `max_tokens` unset either would reserve about 47k tokens per running request there, against about 11k at the floor. The issue also mentions clamping to the current ratio, which would keep a ratio that an earlier retraction raised. I kept to the floor. I'll switch to another form if you prefer it.

The retraction warning now logs the applied ratio, so a clamped retraction logs `0.0980 -> 0.0980`.
