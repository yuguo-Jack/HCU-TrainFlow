# [Feat] rust-server: Give the native /generate hook the request, its headers and its outcome

[Upstream PR](https://github.com/sgl-project/sglang/pull/47112) · state: closed · merged: True

## Original PR description

Stacked on #46963 (the scheduler's per-request stats in native `/generate` `meta_info`), which sits on #46961 and #46949; this PR's own change is its last commit, and its diff against #46963 is the four files below.

## Motivation

A server extension installed with `Server::start_with_extensions` can register a `GenerateHook` that adds keys to native `/generate` response frames. The hook started from the request's typed `SamplingParams` alone and saw nothing else: not the request's id, not the HTTP headers, not what the client actually sent, not the final `meta_info`, and not a failure. That is enough to annotate frames, but not enough for an extension to produce one record per finished request the way Python mode's `RequestMetricsExporter` can (the request, how it was sampled, how it ended).

This PR gives the hook that view. Without a hook installed, nothing changes.

## Modifications

All changes are in `sglang-server`'s native `/generate` path.

- **`GenerateHook::start(&self, request, headers, client_sampling_params)`** replaces `start(&SamplingParams)`.
  - `request` is the submitted `GenerateRequest`, one per batch item, with the launch-time preferred sampling params merged in and not yet normalized. `GenerateRequest` is now re-exported from the crate root; its fields were already `pub`.
  - `headers` is the HTTP request's `HeaderMap`.
  - `client_sampling_params` is the `sampling_params` object the client sent for that item (the object itself, or the item's entry of a list), captured before the launch-time preferred params fill in beneath it. The typed `SamplingParams` cannot tell an omitted field from a default one. It is captured only when a hook is installed.
- **`GenerateFrameHook::finished(&GenerateTerminal)`**, a default no-op, runs once on the request's terminal frame, after `annotate`. `GenerateTerminal` carries the schema's `meta_info` (`GenerateMetaInfo`, now re-exported), the scheduler's request stats, the decode latency, and the number of output token logprobs the request returned over all its frames (an incremental stream's terminal frame carries only its last step's). The fields are typed; nothing is serialized for the hook.
- **`GenerateFrameHook::failed(status, message)`**, a default no-op, runs for a request that fails after submission (for example a scheduler rejection), with the status and message the client gets.
- The lowered OpenAI chat path (`openai/lowered.rs`) builds the same `RequestState` for each choice, so it passes the chat request's headers and no client `sampling_params` object (a chat body has none). That one-line call-site update is the only change outside the native handler and the hook's API.

Scope: native `/generate` and the lowered chat path that shares its request state; gRPC does not call the hook. A request dropped by its client before the terminal frame gets neither `finished` nor `failed`, matching Python's exporter, which runs only on a finished output.

## Accuracy Tests

Not applicable: no model numerics change.

## Speed Tests and Profiling

Not run. Without a hook installed the handler does the same work as before plus one counter increment per output; with one, it clones the client's `sampling_params` once per request.

## Testing

- `generate_hook_keys_reach_every_frame` now runs with a launch-time preferred `top_k`. For unary, cumulative and incremental streams, single and batch, its test hook checks what it saw at `start` (each item's client-facing rid, a request header, the merged `top_k`, and the client's own sampling params without the preferred key) and one `finished` per item, with the terminal `completion_tokens`, the item's request stats where the scheduler sent them, the decode latency, and the two output token logprobs sent over the request's two outputs.
- `per_item_error_carries_index` checks that a failed batch item reaches `failed` with the client's status and message, and that the other item reaches `finished`.
- Ran locally: `cargo fmt --all -- --check`, `cargo clippy --locked -p sglang-server --all-targets -- -D warnings`, `cargo test --locked -p sglang-server`.
