# [LoRA] Run the BF16 trtllm MoE-LoRA path on stock FlashInfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/38649) · state: closed · merged: False

## Original PR description

## Motivation

`--moe-runner-backend experimental_sgl_trtllm` serves its BF16 MoE-LoRA path through
`sgl_trtllm_bf16_routed_moe_lora`, an op that exists only in the private FlashInfer overlay vendored
under `python/sglang/kernels/ops/moe/trtllm_lora_temp/data/`. That overlay shadows the installed
`flashinfer` at JIT build time, and it is currently forked from a base six minor versions behind the
pinned wheel.

Stock FlashInfer has carried the pieces this path needs since `gemm1_lora_delta` landed: calling a
routed op with a delta and `do_finalize=True` returns
`[output, expanded_idx_to_permuted_idx, gemm1_activation_output]`, where the activation is the
post-SwiGLU FC1 output. What stock does *not* do is hand that activation back in expanded
`(token, slot)` order, which is the layout the down-projection LoRA reads.

This moves the BF16 body onto the stock op and closes the layout gap on the SGLang side.

## Modifications

- **`kernels/ops/moe/moe_gather_permuted.py`** (new): gathers the permuted activation into
  `[T, top_k, I]`. It writes **every** row and stores exact zeros where the map is negative. The
  zero fill is load-bearing rather than cosmetic — the down-LoRA expand sums over all `top_k` slots
  unconditionally, so a row left unwritten for an expert outside the local EP shard would be read as
  garbage. Semantics match the torch expression in `flashinfer/fused_moe/moe_lora_delta.py`.

- **`specialized_expand.py` promoted** from `srt/lora/trtllm_lora_temp/` to `kernels/ops/moe/`.
  It is pure triton, and a `kernels/` module was reaching back into `srt/` to import it. It gains
  `SWAP_OUT_HALVES`, implemented as a per-tile `±GATED_A_HALF` offset on the store column, default
  off so every existing caller is byte-identical.

  The swap is required: trtllm-gen adds `gemm1_lora_delta[..., :I]` to FC1's **first** half, the
  trtllm weight prep loads that half as `up`, and the expand natively emits `[gate | up]`. Left
  un-swapped the gate delta lands on the up half. Above rank 64 the generic (stock, shared) expand
  runs instead and the caller pays a `torch.cat`.

- **BF16 dispatch rewritten** onto `trtllm_bf16_routed_moe(..., gemm1_lora_delta=…, do_finalize=True)`.
  The in-op `lora_ready_event` wait has no stock equivalent, so the two-stream path now joins on the
  main stream before the call; the overlap window shrinks to routing.

- **`topk_pack.py` retired** in favour of `PackTopkIds`, which absorbs its int32/fp32/contiguity
  coercions — stock asserted where the temp copy coerced, so the coercions had to move with the
  callers. The packed encoding is bit-identical.

FP8 and NVFP4 deliberately stay on the overlay. DeepSeek-FP8 **cannot** move: its returned activation
is fp8 whose block scale the launcher never returns, so there is nothing to recover bf16 values from.
NVFP4 can, but it is a quantization-boundary rewrite rather than a call swap. The overlay therefore
stays for now; this removes the BF16 dependency on it.

## Accuracy / performance

Validated on 8×B200.

**Kernel and layer level — 213 passed, 0 failed**, four consecutive repeats with no flake:

| suite | result |
|---|---|
| `test_trtllm_moe_lora_stock_equivalence.py` | 11 passed |
| `test_specialized_expand_swap_halves.py` | 18 passed |
| `test_moe_gather_permuted.py` | 54 passed |
| `test_marlin_packed_topk_unpack.py` | 127 passed |
| `test_trtllm_bf16_moe_lora_two_stream_unit.py` | 3 passed |

A decomposition at 129 tokens shows the migrated dispatch with a zero adapter reproducing the stock
non-LoRA path exactly (rel 2.353e-3, max_rel 1.940e-2 for both), with the delta, the half swap and
the gather adding nothing measurable; the whole residual is the pre-existing bf16
`fuse_sum_all_reduce` atomic in the down expand.

**End to end.** On a 975B NVFP4 MoE with a rank-32 adapter (8×B200, TP8, 8k/1k, ≥80 requests per
cell), the shared refactor is neutral against the same build without it: GSM8K identical at 0.935
batched / 0.925 at `--parallel 1`, tok/s/user −0.4 % … +0.1 %, retention within 0.4 pt at every
concurrency from 1 to 128.

On a BF16 MoE the migrated path produces correct LoRA output and the half swap is confirmed
empirically — disabling it degrades KL-to-reference by ~80× and collapses the base-vs-LoRA
divergence, so the pairing is doing real work. A residual gap remains between the migrated path and
the overlay on that model, smaller than the swap effect by a factor of ~36 and consistent with the
overlay running a *decomposed* GEMM1 plus standalone activation kernel where stock uses the fused
SwiGLU epilogue, and with the migration re-enabling the autotuner the overlay pinned off. **That gap
is not yet isolated**, which is why this is a draft.

## Notes

- Reaching the BF16 path at all on an unquantized model requires the fix in
  `htphan/fix-experimental-trtllm-lora-unquantized` (filed separately, one concern per PR). Without
  it `FusedMoEWithLoRA` raises at init and this body has no caller.
- There is still no registered end-to-end test that pairs a non-triton MoE runner with
  `--enable-lora`. The tests added here are kernel- and layer-level.
- Not covered: EP > 1, cuda-graph replay with padding, and two-stream GPU numerics (the two-stream
  test is CPU and asserts ordering and allocation-stream ownership only). Rank > 64 takes the
  `torch.cat` fallback and carries a pre-existing gated-split defect in the shared stock expand,
  documented in the code but not fixed here.
