# [Fix] Nano-Nemotron: Keep video frame timestamps from drifting

[Upstream PR](https://github.com/sgl-project/sglang/pull/40403) · state: open · merged: False

## Original PR description

## Motivation

I reproduced incorrect frame timestamps in Nano-Nemotron's video prompts. `parse_video()` truncates `1000 / avg_fps` to an integer millisecond interval before multiplying by the original frame index, so the error accumulates throughout the video.

For a real 1,440-frame clip at 24000/1001 FPS, the last sampled frame has a decoder presentation timestamp of **60.018291667 seconds**, but the processor reports **58.999 seconds**. The resulting prompt says `59.00 seconds` instead of `60.02 seconds`.

Following the feedback on my coverage-only PR #32164, I am contributing a production correctness fix with a regression that demonstrates the bug, rather than adding coverage for its own sake. NVIDIA's [reference processor](https://huggingface.co/nvidia/NVIDIA-Nemotron-Nano-12B-v2-VL-BF16/blob/ca9543b126e8bf3176916d3d305ccc415f89fd4d/processing.py) likewise calculates timestamps in seconds without rounding each frame interval to integer milliseconds.

## Modifications

- I keep the frame interval in floating-point seconds and multiply it by the sampled source-frame indices.
- I preserve frame sampling, decoded pixels, and the existing zero-timestamp fallback for nonpositive FPS. This retains the existing average-FPS approximation; it does not add variable-frame-rate timestamp support.
- I add one regression to the existing CPU-registered processor test. It encodes a small lossless video whose pixels identify each source frame, runs the real `VideoDecoderWrapper` and processor, and checks each returned timestamp against that decoded frame's identity and the encoded frame rate. No decoder mock, server, model download, or GPU is needed.

## Accuracy Tests

I verified on Python 3.12 with PyTorch 2.13.0+cpu, TorchCodec 0.15.0+cpu, and PyAV 16.1.0:

```bash
PYTHONPATH=python SGLANG_USE_CPU_ENGINE=1 python -m pytest -q \
  test/registered/unit/multimodal/test_nano_nemotron_vl_processor.py \
  test/registered/vlm/test_video_utils.py
# 6 passed

PYTHONPATH=python SGLANG_USE_CPU_ENGINE=1 python \
  test/registered/unit/multimodal/test_nano_nemotron_vl_processor.py -v
# 2 passed through the registered test's direct entry point
```

The new regression fails before the production fix: 9 of 10 sampled timestamps are wrong, with a maximum error of 0.084291667 seconds. It passes after the fix.

I also ran separate native-decoder smoke checks on generated MP4 videos at 24000/1001 FPS (1,440 frames) and 30 FPS (1,800 frames). After the fix, every sampled timestamp matches TorchCodec's decoded presentation timestamp within 1e-9 seconds. The fractional-rate clip's maximum error before the fix was 1.019291667 seconds. The decoded pixels are unchanged.

I have not run GPU model-level accuracy evaluations; this workstation verification covers the actual video preprocessing path, not generated model answers.

## Speed Tests and Profiling

I make no inference-performance claim. Frame sampling and decoding are unchanged. Both processor test methods together took 0.007 seconds after imports in the direct-entry-point run.
