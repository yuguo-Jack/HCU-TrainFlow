[Upstream PR](https://github.com/sgl-project/sglang/pull/38401) · state: closed · merged: False

## Original PR description

# [Sampling] Find the top-p pivot on the value axis instead of ranking the row

## Motivation

On ROCm, `top_p_renorm_probs` falls back to the Triton implementation in
`python/sglang/kernels/ops/sampling/renorm_triton.py`. Today that implementation locates the
pivot by **ranking** the row: sort the probabilities ascending, take a cumulative sum, and
binary-search the CDF for the point where the retained mass reaches `p`.

That is exact and free of host synchronization, but it costs `O(V log V)` over a 100K+
vocabulary, and the cost does not grow smoothly with the verify batch. Measured on MI355X at
a 154880 vocabulary, the pivot step is flat at 0.6–0.9 ms from 2 to 48 rows and 1.39 ms at 96
rows, then steps to 4.30 ms at 144 rows and plateaus there (4.38 ms at 192, 4.75 ms at 384)
as `torch.sort` switches to a different strategy. Speculative verification calls this on
every step, so the step lands directly in the decode critical path.

The obvious repair — sort only a bounded top-k prefix — trades the sort for a host
synchronization: a row whose nucleus extends past the prefix has its pivot outside it, and
the overflow flag has to be read back to decide whether to fall back. That read drains the
queue at a flat ~3 ms whenever there is work in flight, regardless of batch size. Dispatching
between the two on row count only replaces one problem with a tuned constant.

Nothing about top-p actually requires ranking the row, so this PR stops doing it.

## Change

Search for the pivot on the **value** axis. `f(x) = sum(probs[probs > x])` is non-increasing
in `x`, so the pivot is the largest `x` whose retained mass still reaches the budget. The
kernel maintains a bracket `[low, high]` with the invariant `f(low) >= target` and
`f(high) < target`, evaluates two interior points per round, keeps the third of the bracket
that still contains the answer, and snaps the new bounds onto values that actually occur in
the row. Snapping is what makes the round count follow the data rather than the float
exponent range.

Search, threshold and renormalization fuse into a single Triton kernel, one program per row.
`row_sum`, `max_val` and the per-round reductions are all streaming passes over the row, so
nothing vocabulary-sized is materialized.

Removed on the top-p path: the sorted copy, the cumulative sum, the `searchsorted`, and the
auxiliary `out` / `partial_sums` buffers. `top_k_renorm_probs_triton` is untouched and still
uses the existing two-kernel apply path.

## Complexity

| | before (sort) | rejected alternative (top-k prefix) | this PR |
|---|---|---|---|
| device work | `O(B·V log V)` | `O(B·V log k)`, k=4096 | `O(B·V·R)`, R ≈ 20 |
| extra memory | sorted copy + CDF (`2·B·V` fp32) | prefix + mask (`~2·B·k`) | none |
| host sync | none | one read per batch | none |
| batch scaling | superlinear at the `torch.sort` strategy boundary | linear + fixed ~3 ms drain | linear |

`R` is the number of search rounds — how many times the row is streamed. Measured max 20 over
702 rows at vocabularies of 111 / 32000 / 128256 / 151936 and `p` from 0.1 to 1.0, including
softmax rows at temperature 0.3 / 1.0 / 3.0. `p >= 1.0` skips the search entirely and only
rescales.

## Semantics

Unchanged. The threshold keeps the smallest set of highest-probability entries whose mass
reaches `p`, comparing `probs >= pivot` so that entries tying with the pivot are all retained,
matching the AOT kernel. A rank-based cutoff would instead keep exactly k entries and break
ties by sort order.

The budget is taken against the row's own total rather than against 1.0, because a row of
float32 probabilities sums to slightly under one; this keeps `top_p=1` a no-op on a peaked row
instead of truncating its tail.

The loop stops once no representable float separates the two values still inside the bracket:

```
min_gt_low < max_le_high  and  next_float_up(min_gt_low) < max_le_high
```

There is no iteration cap and no auxiliary progress flag. Adjacency is the condition both of
those were approximating, and testing it directly is exact rather than heuristic.
`next_float_up` is an integer increment of the IEEE-754 bit pattern, which is a correct
`nextafter` toward `+inf` for the non-negative values a probability row contains — Triton has
no `nextafter` intrinsic. Because `low` is only ever moved to a value that still satisfies
`f(low) >= target`, every exit path leaves a valid lower bound for the pivot.

## Testing

- `test/registered/kernels/ops/moe/test_renorm.py` — `test_top_p_renorm_probs` over
  batch_size {1, 99, 989} × vocab_size {111, 32000, 128256} × p {0.1, 0.5, 0.9}.
- Numerical equivalence against that test's ground truth (`cumsum(sort(probs)) >= 1 - p`)
  over 702 rows: max absolute deviation **1.9e-5**, well inside the 1e-3 tolerance.
- Termination stress: 2500 rows at a 128256 vocabulary with `p = 0.9` — the shape where a
  round can round both interior points onto the bounds — max 20 rounds, no row failing to
  terminate.
- Degenerate rows exercised: all-equal, one-hot, all-zero, uniformly tiny (1e-30) and
  subnormal (1e-42) rows all terminate in one round and produce finite output.

## Reviewer notes

- The bracket update is written branch-free with `tl.where` rather than as an `elif` chain,
  which is the safer form under the Triton/ROCm backend.
- The kernel is one program per row with `num_warps=8`; on wave64 that is 512 threads, sized
  for the streaming reductions rather than for occupancy at small batch.
- The removed code path had no other callers. The older `top_p_renorm_triton.py` sibling is a
  separate module and is deliberately left alone in this PR.
