# [Bugfix] Restore DeepGEMM warmup state after failures

[Upstream PR](https://github.com/sgl-project/sglang/pull/43712) · state: open · merged: False

## Original PR description

## Motivation

DeepGEMM warmup temporarily sets compile mode to 1, but only restores it on the normal path. If an executor raises, subsequent work can inherit compile-only mode. The warmup group is also marked initialized before locking/compiling, so a caught failure makes a later same-group call skip warmup.

## Modifications

- Restore the saved compile mode in `finally`, including interrupted warmup.
- Remove only the failed group's initialization marker before re-raising. Keep the existing early reservation and successful-group caching.
- Retain the guard for DeepGEMM versions without both compile-mode APIs and the existing symmetric-memory restoration.

## Accuracy Tests

Added seven registered CPU tests covering success/cache reuse, execution failure and interruption, partial/absent legacy APIs, executor allocation failure, compile-mode entry failure, asynchronous synchronization failure, and lock failure without clearing other groups.

Native Linux CPython 3.12, using the actual source-package imports and `CustomTestCase`:
- Unmodified source: six failing assertions/results (reported as 2 failures + 4 errors by the CI retry wrapper); normal and legacy controls pass.
- Repaired source: all seven new tests pass; the existing warmup-memory test also passes.
- GPU/executor boundaries are mocked; the existing memory test uses meta tensors. This is not a real DeepGEMM kernel run, model test or official CI result.

The identical function/test bodies also pass component checks on native Windows Python 3.12 and 3.14. File-scoped pre-commit formatting/static checks pass. Three hooks invoke the unavailable Windows `python3` launcher; their exact scripts pass with native `python`. `git diff --check` passes.
