# [Bug] [AMD] Keep fp32 MoE correction bias in select_experts for the aiter fp32 path

[Upstream PR](https://github.com/sgl-project/sglang/pull/44797) · state: open · merged: False

## Original PR description

## Summary

Fixes #44794.

`select_experts` downcast the correction bias to the router logits' dtype whenever the aiter grouped-topk path was taken. For GLM-5.x (`GlmMoeDsa`), `MoEGate` keeps `e_score_correction_bias` in fp32 since #37133, and the aiter branch of `biased_grouped_topk_gpu` upcasts the gating logits to fp32 when it sees an fp32 bias. The downcast in `select_experts` silently disabled that branch, so GLM-5.x on ROCm routed with a bf16 bias (the offset bias collapses to a handful of distinct values in bf16 and reorders top-k) while CUDA kept fp32 routing.

The fix skips the downcast when the bias is already fp32, so #37133's fp32 aiter path engages. Behavior is unchanged for:

- non-fp32 biases (they still get the pre-existing cast to the gating dtype that `aiter_biased_grouped_topk` expects),
- the JIT-router path (`SGLANG_OPT_USE_JIT_KERNEL_GROUPED_TOPK`),
- the dynamic-expert-bias path,
- non-aiter platforms (CUDA, MUSA, ...): the whole block is gated on `_use_aiter`, so **CUDA routing is byte-identical**.

## Reproducer

Unit-level (no ROCm GPU needed; `_use_aiter` is simulated since this machine has no MI355X):

```python
from unittest.mock import patch
import torch
from sglang.srt.layers.moe import topk as topk_module
from sglang.srt.layers.moe.topk import TopKConfig, select_experts

captured = {}
def fake_biased_grouped_topk(hidden_states, gating_output, correction_bias,
                             topk, renormalize, num_expert_group, topk_group,
                             num_fused_shared_experts, routed_scaling_factor,
                             apply_routed_scaling_factor_on_output):
    captured["bias"] = correction_bias
    return (torch.zeros((gating_output.shape[0], topk)),
            torch.zeros((gating_output.shape[0], topk), dtype=torch.int32))

bias = torch.randn(256, dtype=torch.float32)  # fp32, like GlmMoeDsa's bias (#37133)
config = TopKConfig(top_k=8, use_grouped_topk=True, topk_group=8,
                    num_expert_group=32, correction_bias=bias)
router_logits = torch.randn(4, 256, dtype=torch.bfloat16)  # like aiter_dsv3_router_gemm

with (patch.object(topk_module, "_use_aiter", True),
      patch.object(topk_module, "biased_grouped_topk", fake_biased_grouped_topk)):
    select_experts(torch.randn(4, 16, dtype=torch.bfloat16), router_logits, config)

print("input bias dtype:                ", bias.dtype)
print("bias reaching aiter grouped topk: ", captured["bias"].dtype)
```

Before (on main):

```
input bias dtype:                 torch.float32
bias reaching aiter grouped topk:  torch.bfloat16
```

After (with this fix):

```
input bias dtype:                 torch.float32
bias reaching aiter grouped topk:  torch.float32
```

## Measured effect

Per the reporter's measurement on a GLM-5.3 TP8 server (MI355X, `SGLANG_USE_AITER=1`, eager, 38,325 token-layer pairs): the routed top-8 differed from the same bf16 logits routed with the fp32 bias in 67.6% of token-layer pairs (1.32 of 8 experts on average; layers 3–7 differed for nearly every token). The reporter also confirmed that skipping the downcast restores fp32 routing on the aiter path (0.0–0.1% differing pairs). CUDA behavior is unchanged.

## Tests

- New `test/registered/unit/layers/moe/test_topk_fp32_bias_aiter.py` (CPU, registered with `register_cpu_ci`):
  - fp32 bias reaches the grouped-topk kernel untouched — fails on main, passes with the fix;
  - bf16/fp16 biases keep the pre-existing cast to the logits dtype;
  - a mechanism check: the bf16 cast of an offset bias demonstrably reorders top-k routing.
- Existing `test/registered/unit/layers/moe/test_topk_correction_bias_cache.py`: 3 passed.

Thank you for the detailed report and measurements — they made this straightforward to pin down.

**Aiter branch: cast only where the result is used, and give radix4 the same dtypes as aiter.**

With this line, an fp32 bias now reaches the aiter branch of `biased_grouped_topk_gpu`. That code is outside this diff, so this can't be a suggestion block. Two things there change behaviour:

1. `bias = correction_bias.to(dtype=gating_output.dtype)` runs on every call. With an fp32 bias it is now a real cast: one allocation and one kernel per MoE layer per step. Only the radix4 path reads the result. That brings back the per-call cast that #33838 removed.
2. Radix4 (`SGLANG_K3_RADIX4_TOPK=1`) still gets that bf16 copy. For Kimi-K3, radix4 routes a batch of up to 1024 tokens with the bf16 bias, and aiter routes a larger batch in fp32. A token's routing then depends on its batch size, which `route_radix4` is written to avoid (it matches aiter row for row). Radix4 accepts fp32 scores with an fp32 bias, and `test_route_radix4_matches_aiter` already compares the two in fp32.
