# [Fix] scheduler: Keep the priority preemption order consistent across TP ranks

[Upstream PR](https://github.com/sgl-project/sglang/pull/45813) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45812.

`PrefillAdder.preempt_to_schedule` fills `preempt_list` by iterating a set of `Req` objects. `Req` hashes by `id()`, so that order follows object addresses and can differ between TP ranks. The scheduler requeues the victims in `preempt_list` order. That order stamps their `wait_queue_entry_time`, which the priority queue sort and the next victim selection both read; with `--max-queued-requests` it also decides which victim is aborted when the queue is full, and with HiCache storage it sets the order of the prefetch hit-count all-reduces. So when one preemption takes two or more victims, the ranks can go on to build different batches. Details and a CPU reproduction are in the issue. The set has been there since priority preemption was added (#8746).

## Modifications

- `preempt_to_schedule` keeps the set only for the membership test while releasing victims, and extends `preempt_list` from the ordered victim list, reversed: preferred priority first, then the earliest queued. This is the order of the default `fcfs` waiting queue, so the new `wait_queue_entry_time` stamps keep the victims' relative order. Selection order would requeue the most recently queued victim first and put the oldest one first in line for the next preemption.
- Which requests are preempted, the threshold, the token accounting and the release order (`running_batch.reqs` order) do not change. The dLLM scheduler mixin consumes `preempt_list` the same way and gets the same order.

Related: #45686 adds preemption when KV runs out, where one preemption is more likely to take several victims. The two PRs touch different files.

## Tests

- `test_preempt_list_order_independent_of_req_hashes` in `test/registered/unit/managers/test_prefill_adder.py`: five running requests are preempted under two different `__hash__` assignments, standing in for two ranks, with both values of `--schedule-low-priority-values-first`, and `preempt_list` must come out in waiting-queue order every time. On `main` all four cases fail (`['c', 'a', 'e', 'b', 'd']` and `['d', 'b', 'e', 'a', 'c']` instead of `['a', 'b', 'c', 'd', 'e']`). They also fail if the list is extended in selection order or in `running_batch.reqs` order, and the `True` cases fail if the requeue order ignores the priority direction.
- `test_prefill_adder.py`, `test_schedule_policy.py` and `test_retraction_order.py` pass locally (69 tests), and `pre-commit run` on the changed files is clean.
- The reproduction script from the issue prints `['r0', 'r1', 'r2', 'r3', 'r4']` on every run with this change.
