# [Perf] Throttle the fully-idle load snapshot publish in on_idle

[Upstream PR](https://github.com/sgl-project/sglang/pull/39315) · state: open · merged: False

## Original PR description

## Motivation

`Scheduler.on_idle` publishes a load snapshot on every pass while the engine is fully idle. With `--sleep-on-idle` off (the default) the scheduler busy-polls, so each pass walks the queues (`get_loads()`), encodes a `LoadSnapshot`, and writes it to shared memory under an exclusive `flock` — for a payload that cannot change until the next request arrives.

Measured on an idle Qwen2.5-0.5B server (1xH200, default flags): **10 470 publishes/s, 356 ms/s of scheduler CPU** (~0.36 core), each publish costing 0.020 ms (`get_loads`) + 0.011 ms (shm write) — i.e. ~2.1 k `flock` pairs/s and ~10 k shm rewrites/s per idle scheduler.

The stalled no-batch path directly above it already has a wall-clock floor (`LOAD_STALL_REFRESH_S`) for this exact reason ("this path spins without sleeping, so a wall-clock floor bounds the O(queue) get_loads"); the fully-idle path was left unfloored, so its `force=True` — meant to keep the busy->idle transition immediate — degenerated into "publish on every spin pass".

## Modifications

- `python/sglang/srt/managers/scheduler.py`
  - `on_idle` now publishes immediately on the busy->idle transition (`_was_fully_idle`) and floors the passes after it with the same 50 ms wall-clock gate used by the stall path.
  - `process_batch_result` clears that transition flag through the new `Scheduler.mark_engine_busy()` for every batch it handles, so a busy phase that never reached `on_idle` still publishes as soon as the engine drains. Filler `ForwardMode.IDLE` batches count too: a dp-attention rank emits one to join the MLP-sync collective while its own queues can hold requests, so it is a real step rather than a pass through the idle path.
  - The duplicated publish pair in both spinning paths moved into `Scheduler.publish_spinning_load()`.
  - `LOAD_STALL_REFRESH_S` -> `LOAD_SPIN_REFRESH_S` and `_last_stall_publish_ts` -> `_last_spin_publish_ts`, since both spinning paths now share the gate.
- `test/registered/unit/managers/test_scheduler_on_idle_load.py`
  - 7 new cases: idle spin publishes once per floor; the transition publishes immediately even right after a stall publish; it publishes again once the floor elapses; every return to idle publishes; a real batch makes the next idle pass publish; `process_batch_result` clears the flag for a real batch and for a filler `ForwardMode.IDLE` batch (the latter carries non-empty queues on a dp-attention rank).

Effect: **10 470 -> 20 publishes/s while idle (0.36 -> ~0.001 core in the publish path)**. The loaded path is unchanged (76 publishes/s, 7.6 ms/s measured both before and after): prefill still publishes immediately, decode still every `--load-snapshot-publish-interval` iterations.

Freshness trade-off (the only behavior change): while fully idle a reader (`/v1/loads`, `DataParallelController`) can see a snapshot up to 50 ms old instead of ~0.1 ms old — the same bound the stall path already exposes, for a payload that is constant over that window, and well inside the 1 s heartbeat the sibling router-facing publisher (`LOAD_PUBLISH_HEARTBEAT_S`) already uses for unchanged stats. The transition into idle still publishes immediately, so a router never sees a stale nonzero gauge after the engine drains. Verified by polling `/v1/loads` every 200 ms across a benchmark:

```
23:44:14 running=0   waiting=0 used_tokens=0       snap_age_ms=50.3   # idle
23:44:44 running=127 waiting=0 used_tokens=134568  snap_age_ms=21.5   # loaded
23:44:54 running=128 waiting=0 used_tokens=142442  snap_age_ms=2.4    # loaded
```

Note on what this does *not* claim: an idle scheduler already pins a core by design (busy poll; that is what `--sleep-on-idle` exists for), so `%CPU` is unchanged. What is removed is the work itself (syscalls, tmpfs traffic, cycles spent recomputing an identical payload), which matters on CPU-oversubscribed hosts (many instances per box, co-located tokenizer/detokenizer/HTTP workers, PD/RL idling between bursts).

## Accuracy Tests

Not applicable: no model forward, kernel, sampling, or tokenizer behavior changes; the change only affects the cadence of the load snapshot published from the idle spin path.

## Speed Tests and Profiling

Server: `python -m sglang.launch_server --model-path Qwen2.5-0.5B-Instruct` on 1xH200, default flags. Load: `python -m sglang.benchmark.serving --backend sglang --dataset-name random --random-input-len 1024 --random-output-len 256 --num-prompts 4000 --max-concurrency 256`.

Counted with a temporary counter around the publish call, removed before this PR:

| State | Publishes/s before | Publishes/s after | CPU in path before | CPU in path after |
| --- | --- | --- | --- | --- |
| fully idle | 10 470 | 20 | 356 ms/s | 1.2 ms/s |
| under load | 76 | 76 (unchanged) | 7.6 ms/s | 7.6 ms/s |

`py-spy` on the scheduler process over a 100 s window containing a ~45 s benchmark attributes 32.5 % of scheduler CPU to `on_idle`, of which 20.4 points are the snapshot publish (only ~0.35 point is the loaded phase; the rest is the spin after the benchmark drained) and 5.3 points are the idle leak/invariant checks (not touched here).

Serving sanity run after the change: 3000 requests at concurrency 128 (2048/256) completed with no errors, 12 725 output tok/s, 9.75 ms mean TPOT. Throughput at concurrency 256 was within run-to-run noise of the pre-change baseline (17.5K vs 18.4K output tok/s), as expected — this change does not target the loaded path.
