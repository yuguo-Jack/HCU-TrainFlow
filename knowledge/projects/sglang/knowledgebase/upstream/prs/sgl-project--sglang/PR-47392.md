# [Fix] session: Keep recurrent state aligned with kept tokens

## Motivation

A streaming session keeps a finished turn's KV row and, on hybrid models, its live Mamba/GDN state for the next turn. The kept state can cover more tokens than the session keeps, in three ways:

1. **Overshoot.** A speculative verify commits KV and recurrent state for its whole accepted run, which can pass `max_new_tokens` or a stop token. `_trim_overshoot` (#22897) cuts KV and `output_ids` back but cannot rewind the state.
2. **Bonus end.** When the run ends exactly at the limit, no forward has computed the last (bonus) token, yet the slot commits it.
3. **Rerun of a finished turn.** The overlap loop launches the next batch before it processes the result that finishes a turn, so the turn runs once more and that forward advances the kept state. #42720 drops such a request only when its next single token reaches `max_new_tokens`, so this affects speculative turns and any turn that ends on EOS or a stop token, with or without speculation.

Example: `Qwen/Qwen3.5-0.8B-Base`, `--speculative-algorithm NGRAM --speculative-num-draft-tokens 4 --enable-streaming-session --page-size 1`. Turn 1 has a 16-token prompt and `max_new_tokens: 6`. The last verify reaches 9 output tokens, so the session keeps 22 tokens while the state absorbed 24, and turn 2's first token differs from a fresh request with the same `input_ids` by 0.41 in logprob. Without speculation, a turn ending on a stop token keeps state one token ahead.

Duplicate-work check: I searched open and closed issues and PRs for streaming sessions with speculative decoding, hybrid or Mamba models, overshoot, `_trim_overshoot` and in-flight finishes. #22897 trims paged KV only, #42330 added the release path reused here, and #42720 covers the one-token in-flight length case. None covers the recurrent state.

## Modifications

- `_trim_overshoot` keeps at most the request clock (`kv_committed_len`), which counts only computed tokens. A turn ending on a bonus token keeps one token less, and the next turn prefills it.
- When the overlap loop processes a result, it marks each request that a launched or planned batch already runs again (`Req.relaunched_in_flight`). It does this only with streaming sessions on a hybrid model.
- `try_cache_finished_req`: if the record holds recurrent state that absorbed tokens past the visible output, or the turn is marked as rerun, the session returns the record through the normal release path (#42330). The turn stays in the session history, and the next turn re-prefills from the radix cache, starting at its last Mamba checkpoint (every 64 tokens in these runs).
- Processing the pending result before planning would also prevent the rerun, but it drops planning overlap for every step of such a batch. In the benchmark below that halves throughput with 64-token turns, so this PR releases the record instead.
- Tests: `test_scheduler_session_relaunch_mark.py` drives `event_loop_overlap` and checks the mark for an overlapped rerun, a synchronous step with a planned rerun, no rerun, and the feature gates. `test_streaming_session_unit.py` adds the trim, release and rerun cases.

## Speed Tests and Profiling

Only released turns cost extra: the next turn re-prefills the tokens after the last Mamba checkpoint. Batches keep planning overlap.

Throughput: 8 sequential sessions of 6 turns, overlap on, on an RTX A6000 with no other jobs. Main and this PR were launched alternately, three times each for 12-token turns and twice each for 64-token turns, with two repeats per launch.

| Workload | main (tok/s) | this PR (tok/s) | Diff | Cached tokens, main / this PR |
| --- | ---: | ---: | ---: | ---: |
| 12 output tokens per turn, NGRAM 4 | 390.4 (382.2 to 399.3) | 388.7 (377.2 to 397.3) | -0.4% | 5,280 / 3,584 to 5,120 |
| 64 output tokens per turn, NGRAM 4 | 676.5 (673.9 to 679.5) | 635.5 (634.8 to 636.0) | -6.1% | 11,520 / 8,704 to 9,728 |
| 12 output tokens per turn, no speculation | 245.0 (244.5 to 245.4) | 245.6 (244.5 to 246.6) | +0.2% | 5,240 / 5,240 |

Under overlap most speculative turns are released (21 of 24 in the length replay above), and the lower cached-token count shows the re-prefill.
