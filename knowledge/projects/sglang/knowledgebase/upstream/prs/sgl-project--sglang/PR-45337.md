# [Feat] disaggregation: Support prefill_complete with a pipeline-parallel prefill and send its Success from the transfer worker

[Upstream PR](https://github.com/sgl-project/sglang/pull/45337) · state: open · merged: False

## Original PR description

## Motivation

TL;DR This PR enables prefill_complete in #40703 for PP prefill as well. For a high throughput GLM5.2 server, prefill_complete on PP scheduler reduces ~70% of reserved requests on decode. Furthermore, we change how we send the kv-transfer completion signal under prefill_complete, improving TTFT by 1 to 2 iterations of prefill model forwards. This improves prefill_complete for overlap scheduler slightly, and is quite crucial for prefill_complete for PP scheduler to be useful.

`--disaggregation-decode-allocation-policy prefill_complete` (#40703) makes PD (prefill/decode) disaggregated decode reserve a request's KV (key-value cache) slots only after prefill finishes, instead of at bootstrap. It helps most when prefills are long, and long-context prefill is often served with PP (pipeline parallelism). This PR lets the policy run with a PP prefill, and removes the TTFT (time to first token) cost that releasing a request through the PP stages would otherwise add.

**PP prefill.** Today the policy cannot start on a PP prefill:

1. `_validate_prefill_complete` rejects `pp_size != 1` on both roles.
2. `handle_other_validations` resolves `--optimistic-prefill-attempts` to 0 whenever `pp_size > 1`, and `prefill_complete` requires optimistic prefill.
3. The decode receiver fails any room whose prefill peer has `pp_size != 1`.

Removing these checks is not enough. Each PP stage runs its own scheduler, and the stages must make identical scheduling decisions. A parked request (prefill finished, decode has not admitted it yet) is finalized when its poll turns `WaitingForInput`, and finalizing re-checkpoints it into the radix cache. If each stage acted on its own poll, stages would finalize in different iterations and schedule against different caches. The existing PP transfer-queue path also acts only on `Success` or `Failed`, so nothing would finalize a parked request.

Separately, the attention-TP (tensor parallelism) check in `_validate_prefill_complete` reads `dp_size` and `enable_dp_attention`. Since #41818, the server-args pipeline moves that width to `attn_dp_size` and resets the other two before this validator runs. The check therefore rejects every attention-DP (data parallelism) worker under either spelling, e.g. a DEP8 decode (attention DP + expert parallelism over 8 GPUs).

**When decode hears `Success`.** Under `prefill_complete`, prefill tells decode that a KV transfer succeeded only from `sender.clear()`, when the prefill scheduler releases the request. That ordering exists so decode never reuses a bootstrap room that prefill still holds: after a true retraction, decode resumes the request by asking the same prefill server to recompute it under the same bootstrap room. With a PP prefill the release waits for the stages' consensus poll, and with attention DP for the scheduler's next synchronized iteration. Decode cannot start decoding until it hears `Success`, so the release delay lands in TTFT, and decode holds the request's KV slots for that time without using them. Under `early`, the transfer worker sends `Success` as soon as the transfer ends.

On a GLM-5.2 deployment with a PP4 prefill at 0.8 req/s, PP support with `Success` sent on release trails `early` by 0.82-0.87 s of mean TTFT. With `Success` from the transfer worker it trails by 0.12-0.15 s, while decode reserves about a quarter of `early`'s KV for requests whose KV has not arrived (21.5k vs 80k tokens). The remaining gap is decode's reservation handshake, which `prefill_complete` runs after prefill; #48205 overlaps it with prefill. The `Success` change also applies without PP: with a DEP4 prefill it saves 0.22-0.34 s of mean TTFT at 0.8 req/s.

## Modifications

**Validation**
- `_validate_prefill_complete` allows PP on prefill; decode PP stays rejected. Attention TP must be 1, checked as `tp_size == attn_dp_size * attn_cp_size`. It is a product rather than a division because the validators that reject non-positive or non-dividing widths run after this hook; a division would raise `ZeroDivisionError` for `--attn-dp-size 0` and accept `--tp-size 3 --attn-dp-size 2` by flooring.
- `handle_other_validations` keeps optimistic prefill under PP only with `prefill_complete`. Other policies still resolve it to 0, because their yield paths act on per-stage polls.
- `CommonKVReceiver` accepts prefill peers with `pp_size > 1`. Attention TP and CP (context parallelism) must still be 1.

**Decode admission** (`disaggregation/common/conn.py`)
- Readiness from any prefill PP stage admits the room. Each stage sends its readiness before its own `Success` on the same socket, so a readiness never trails that stage's `Success`.
- Decode still completes the room only after every stage's `Success` (`required_prefill_response_num = pp_size`).
- In practice stage 0 finishes first. Decode then allocates and sends destinations to every stage. Each stage writes its layers' KV once its own prefill is done and its destination has arrived.

**Prefill scheduling under PP** (`disaggregation/prefill.py`, `managers/scheduler_pp_mixin.py`)
- New `pop_bootstrapped_and_resolve_parked_pp` covers three queues with one PP consensus poll per loop iteration: the bootstrap queue, waiting requests whose bootstrap is still pending, and the parked requests.
  - Stage 0 polls each room, taking the minimum status over all stages from the existing `PPConsensusStore`, and forwards the result down the pipeline, one list per queue together with each queue's bootstrap rooms (`poll_and_all_reduce_prefill_pp_sections`). A stage whose queues differ from stage 0's in membership or order fails an assertion instead of applying a poll to another request; each stage re-sorts its waiting queue on its own, so this also guards that order.
  - Every stage then pops the same bootstrapped requests, drops the same waiting requests whose bootstrap failed, and finalizes or fails the same parked requests.
  - It is one poll because a stage's send of the poll completes only when the next stage receives it in the same iteration. A second sync per iteration deadlocks the pipeline.
- `PrefillBootstrapQueue.pop_bootstrapped` accepts a poll list the caller already synced.
- `check_bootstrap` returns False under PP. Under `prefill_complete`, decode cannot admit a request before its last chunk anyway. A stage-local `Failed` poll, however, would make one stage drop a chunked request while the others schedule its next chunk. The failure is acted on once the request parks, on the consensus poll.
- Under PP, the transfer-queue release path (`process_disagg_prefill_transfer_queue`) leaves parked requests to the consensus poll. Its poll is stage-local; with `SGLANG_TEST_DISAGG_FAILURE_PROB` each stage draws its own injected failure, so acting on it there would let the stages' parked sets diverge.
- `process_bootstrapped_queue` takes the new path only with `prefill_complete`; other policies keep `pop_bootstrapped`.

**`Success` from the transfer worker** (`disaggregation/common/bootstrap.py`, `common/conn.py`, `prefill.py`)

The transfer worker now sends `Success` when the transfer ends, as under `early`, for the deferred policy too. Decode may then retract the request and resume it, reusing its bootstrap room, before prefill has released it. Prefill keeps that safe:
- `DeferredBootstrap.conclude()` commits the room's success under the room lock before `Success` goes out. It fails when a failure or cancellation already won; the worker then sends nothing, and the winner notifies decode.
- A decode registration that arrives while the room is concluded belongs to the room's next request. It is kept and applied when the sender releases the room.
- A recompute that reaches prefill before that release waits in `PrefillBootstrapQueue.room_waiters` and is enqueued once the room is free. Under PP every stage releases and admits in the same loop iteration, so the stages' queues agree. `room_waiters` is a request list (`ListKind.PD_ROOM_WAITERS`): an `AbortReq` retires matching waiters through it, a waiting recompute keeps the worker from counting as idle for a cache flush or weight update, and the load snapshot counts waiters as bootstrapping.
- A failure after `Success` concerns a request decode already holds: it neither notifies decode nor cancels the room's next request. Decode's ABORT goes through the new `DeferredBootstrap.cancel()`, which on a concluded room cancels the next request, the only one decode can still abort.
- The sender releases a concluded room only after the transfer worker's room cleanup, including after an abort that caches `Failed`, so the old worker cannot erase a recompute's transfer state.

**Docs**: the PD disaggregation page says prefill may use PP (decode may not), notes the PP limitation below, and describes the new `Success` timing.

## Accuracy Tests

No accuracy eval was run. The change touches no model or kernel code. It changes when decode allocates KV, how PP prefill stages agree on finalizing parked requests, and when decode learns that a KV transfer finished. The GPU e2e cases compare outputs: a multi-chunk request returns identical tokens and logprobs on a repeat, and a request retracted three times through `pause_generation(mode="retract")` never rewrites tokens or logprobs it already emitted. They pass with a single-GPU, a PP2 and an attention-DP2 + EP2 prefill.

**PP stage consistency under load.** A PP prefill worker logs every batch from each of its 4 stages. Across the 8 agentic runs below (29 prefill workers, about 152k batches), the 4 stages of every worker agree on every batch, on these counts: new sequences, new tokens, cached tokens, running, queued, bootstrapping, inflight (parked or transferring) and optimistic requests. A divergence would mean the stages scheduled different batches.

## Known limitations

- Decode PP remains unsupported.
- Under PP, a chunked request whose bootstrap fails keeps computing its remaining chunks, and is dropped after it parks; the waste is bounded by one request's prefill. Dropping it at the consensus poll would free its request row and KV slots while its earlier chunks may still be queued on the forward stream, and the PP loop has no barrier between the schedule and forward streams, so a same-iteration allocation could reuse them.
- A decode worker without this change fails every request from a PP prefill peer under `prefill_complete`, with an explicit reason.
- A retraction recompute that reaches prefill before prefill has finished streaming the original request's output is rejected as a duplicate rid (`TokenizerManager` still tracks the original), and decode then aborts the resumed request. `early` already has this window, since its `Success` also comes from the transfer worker; this PR gives `prefill_complete` the same window, which with a PP prefill lasts until the stages' release consensus. Under the deferred policy it takes a `pause_generation(mode="retract")` followed by `continue_generation` within that window: the deferred policies reject the DeepSeek-V4 KV pools, the other source of recomputing retractions. Giving the recompute its own rid (derived from the original, so prefix-matched aborts still reach it) closes the window; that is left to a separate PR.
- The same-build speed results are from one model and topology family at low decode load.
