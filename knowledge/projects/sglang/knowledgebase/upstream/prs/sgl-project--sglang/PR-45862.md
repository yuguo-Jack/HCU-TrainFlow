# [Perf] [NVIDIA] gemm: Add W8A16 small-M GEMM for GLM-5.2 block-FP8 decode projections

[Upstream PR](https://github.com/sgl-project/sglang/pull/45862) · state: open · merged: False

## Original PR description

## Summary

This PR adds a W8A16 GEMM for the decode attention projections of GLM-5.2-FP8 (fused qkv_a, q_b, o_proj, indexer wq_b) at M <= 16 tokens on SM10x (GB200, GB300, Rubin), with tuned configs for the TP4 and TP8 shard shapes. The FP8 E4M3 weights and their 128x128 block scales are used as stored, the activations stay BF16 and the products are accumulated in FP32. It replaces the default W8A8 path for these calls, which first quantizes the activations to FP8 with a per-token-group kernel and then runs DeepGEMM: one kernel instead of two, and no activation-quantization error.

Against the default W8A8 path:

| GPUs, layout | e2e TPOT, concurrency 1 | e2e TPOT, concurrency 2 | GSM8K, W8A8 -> W8A16 | AIME25 |
|--|--:|--:|--:|--|
| 4 x GB300 (SM103), TP4 | -6.8% | -3.4% | 97.75% -> 98.00% | 4/4 in both |
| 4 x VR200 (SM107), TP4 | -10.3% | -7.0% | 97.75% -> 98.00% | 4/4 in both |
| 8 x GB200 (SM100), TP8 | -9.2% | -6.0% | 98.50% -> 97.25% | 4/4 in both |

Per projection the kernel is 1.3-3.0x faster than W8A8 (geomean over M = 1..16) and faster at every M on GB200, GB300 and R100. In the AgentX agentic trace replay on GB300 the interactivity is 6.8% higher and the median decode step 6.3% shorter at concurrency 1.

## Accuracy

sgl-eval on the served model: GSM8K 200 x 2 (pass@1) and the first 4 AIME25 problems; thinking, temperature 1.0, top_p 0.95, 128k max tokens, seed 0; concurrency 2 with MTP 5-1-6 and real acceptance, so the verify step runs at M = 6 and 12, inside the kernel's range.

| GPUs, layout | GSM8K, W8A8 (default) | GSM8K, **W8A16 (this PR)** | AIME25, W8A8 / W8A16 |
|--|--:|--:|--|
| 4 x GB300 (SM103), TP4 | 97.75% | **98.00%** | 4/4 / 4/4 |
| 4 x VR200 (SM107), TP4 | 97.75% | **98.00%** | 4/4 / 4/4 |
| 8 x GB200 (SM100), TP8 | 98.50% | **97.25%** | 4/4 / 4/4 |

The differences are sampling noise: one standard error of the difference of two 400-sample runs at temperature 1.0 is about 1 point. 0% truncated and 0 errors everywhere.

Kernel numerics against an fp64 reference of the same effective weights (M = 1..16, heavy-tailed BF16 activations): the W8A16 relative RMS error is 1.67e-03, the floor set by rounding the exact result to BF16, and W8A8 is at 2.7e-02 (16x) because of the FP8 activation quantization. On the real checkpoint (all 79 layers, real block scales, median over layers) W8A16 is at 1.66e-03 and W8A8 at 2.7e-02.

## Modifications

- `python/sglang/kernels/jit/csrc/gemm/dsv3_fused_a_gemm_fp8.cuh` (new): the kernel, written with the same vocabulary as `dsv3_fused_a_gemm.cuh` (A / B loaders, MMA computer), with tuned configs for the GLM-5.2 TP4 and TP8 shard shapes.
- `python/sglang/kernels/ops/gemm/dsv3_fused_a_gemm.py`: JIT loader, custom op and public `dsv3_fused_a_gemm_fp8` next to the BF16 op; registry entry (SM10x: SM100, SM103, SM107) in `ops/gemm/__init__.py`, eligibility helpers in `ops/gemm/fused_a_gemm.py`.
- `python/sglang/srt/layers/quantization/fp8.py`: `Fp8LinearMethod` decides eligibility once after weight loading (block-FP8 weight, shapes in the tuned table, SM10x, `--fp8-gemm-backend auto`, `SGLANG_ENABLE_FP8_SMALL_M_W8A16` not 0) and routes decode batches of at most 16 tokens to the kernel.
- `python/sglang/srt/environ.py`: `SGLANG_ENABLE_FP8_SMALL_M_W8A16` (default on), the kill switch for the W8A16 path; an explicit `--fp8-gemm-backend` also keeps every layer on that backend.
- Tests: new cases in `test_dsv3_fused_a_gemm.py` (numerics vs an fp64 reference over shapes / M / scale formats, strided scales, torch.compile, a PDL regression test that fails when the kernel's wait on its producer is removed or moved below the loads, rejects, hook eligibility); the kernel tests skip off SM10x (the eligibility and decline tests run on any CUDA GPU) and the file is additionally registered on the `4-gpu-b200` and `4-gpu-gb300` runners. Registry rows in `test_kernels_namespace.py` check that the op is registered for SM10x only. `benchmark_fp8` in `bench_dsv3_fused_a_gemm.py` (SM10x only).

Numerics note: the tuned configs run the MMA with FP16 operands and FP32 accumulation (q_b at TP8 uses BF16 operands up to 8 tokens). E4M3 to FP16 is exact (hardware convert). The BF16 activations are converted to FP16 in registers, which is exact for 2^-17 <= |x| <= 65504; larger values saturate to 65504, smaller ones lose low bits to FP16 subnormals, and the kernel does not check the range. Eligibility is keyed on the weight shape (N, K), not on the model, so any other block-FP8 model with these shard shapes on SM10x takes this path too. An explicit `--fp8-gemm-backend` or `SGLANG_ENABLE_FP8_SMALL_M_W8A16=0` keeps the layer on the selected W8A8 backend.

The test file passes on GB300 (316 / 316); earlier revisions passed on GB200 (318 / 318) and VR200 (298 / 298 before the TP8 shapes, CUDA 13.4).

[by Claude Code]

The comment above is inaccurate: `griddepcontrol.wait` in the dependent waits for this grid to *complete* and its memory to be visible, not just for writes issued before `launch_dependents`. The trigger is scheduling-only (see the `PDLWaitPrimary` / `PDLTriggerSecondary` docs in `sgl_kernel/utils.cuh`). This PR's own `test_fp8_fused_a_gemm_waits_for_its_pdl_producer` demonstrates it: `_late_writer` triggers first and stores afterwards, and the GEMM still reads the new values.

So the trigger can move to the top of the kernel at no correctness cost, giving the next kernel an earlier launch.

Related (L434): the weight loads are issued after `PDLWaitPrimary`, but the weights don't depend on the producer. Issuing the first stage's `a_loader.load` before the wait is usually the main PDL win for a weight-streaming GEMV, and might recover part of the in-graph gap vs. the BF16 kernels described in table 6. Worth a measurement.
