# [Scheduler] Add opt-in shared schedule/forward stream for the overlap scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/44118) · state: open · merged: False

## Original PR description

## What changes

This PR adds an opt-in env flag, `SGLANG_SHARE_SCHEDULE_FORWARD_STREAM` (default off). Default behavior does not change.

- **Before:** the overlap scheduler always keeps a separate schedule stream. Every decode step has GPU waits between this stream and the forward stream: the forward stream waits for its inputs, and the WAR barrier makes the schedule stream wait for the forward stream. On ROCm, each stream maps to a different hardware queue. On gfx950, a wait that is pending on one queue slows each kernel dispatch on the busy forward queue. With `SGLANG_FORCE_COARSE_WAR_BARRIER=1`, the WAR wait is pending for almost the whole forward step. In our traces this added about 0.6 µs to each forward kernel, or about 1.1 ms per MTP decode step (about 1,860 kernels).
- **After, with the flag set:** the scheduler queues its own GPU work on the forward stream. Both waits are then in order on one stream, so no wait crosses hardware queues. With the coarse WAR barrier, the GPU order is the same as before, because the schedule work already waits for the whole forward. CPU/GPU overlap stays. The flag has no effect with pipeline parallelism.
- **Who sees it:** only servers that set the flag. We measured it on AMD MI355X (gfx950) with GLM-5.3-Flash MXFP4, MTP, and the recipe's `SGLANG_ENABLE_WAR_BARRIER=1 SGLANG_FORCE_COARSE_WAR_BARRIER=1`.

## Motivation

On gfx950, the cost appears only when a stream waits on an event that is still pending on another, busy hardware queue. ROCm/rocm-systems#12727 hides it in the HIP runtime with a CP pre-wait packet. In our measurements, that pre-wait gives the same decode gain as this flag. This PR gets the gain in SGLang with the stock runtime.

Other options we measured, on the develop runtime:

- `SGLANG_FORCE_COARSE_WAR_BARRIER=0` (fine-grained read-done event): no gain (1,235 / 1,925 tok/s at batch 8 / 16). On HIP the read-done event is recorded after the verify graph replay, so it is still pending for most of the step.
- `GPU_MAX_HW_QUEUES=1`: most of the gain (1,323 / 2,008 tok/s). But it puts every stream in the process on one hardware queue.
- `--disable-overlap-schedule` also uses one stream, but it removes CPU/GPU overlap. It was not measured.

## Modifications

- `environ.py`: add `SGLANG_SHARE_SCHEDULE_FORWARD_STREAM = EnvBool(False)`.
- `managers/utils.py`: add `select_schedule_stream()`. It returns the forward stream when sharing is on. Otherwise it keeps the existing behavior: a schedule stream distinct from the forward stream, redrawn if it aliases.
- `managers/scheduler.py`: `run_event_loop` uses the helper. Sharing applies only when the flag is set and `pp_size == 1`. The choice happens before `StreamContext(self.schedule_stream)` and `dispatch_event_loop`, so every event loop (including PD decode) and every component that reads `scheduler.schedule_stream` or the current stream sees the shared stream.
- `test/registered/unit/managers/test_select_schedule_stream.py`: CPU unit test for the default, the alias redraw, the shared case, and the flag default.

## Accuracy Tests

No accuracy run. The flag changes only the stream on which the scheduler's GPU work is queued. With the coarse WAR barrier, the GPU order is the same. All measured runs finished with 0 errors.

## Speed Tests and Profiling

See **Measured** above. Torch profiler traces of the develop runtime show two `hipStreamWaitEvent` calls per decode step: `Scheduler._apply_war_barrier` and the forward-input wait in `run_batch`. The forward stream is never idle, and its kernels run longer: the median matched kernel takes 0.6 µs more than with the pre-wait runtime.
