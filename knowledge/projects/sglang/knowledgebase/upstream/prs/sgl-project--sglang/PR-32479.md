# [Feat] [SM120] distributed: Add optional b12x PCIe all-reduce (one-shot + fused RMSNorm + FP8 DMA ring)

[Upstream PR](https://github.com/sgl-project/sglang/pull/32479) · state: open · merged: False

## Original PR description

## Motivation

On Blackwell workstation / server parts (SM120 & SM121 — RTX PRO 6000, RTX 6000D, RTX 50-series, GB10) the GPUs are connected over PCIe with no NVLink. The per-layer tensor-parallel all-reduce therefore dominates both decode latency and long-prompt prefill: on 8x RTX 6000D running GLM-5.2-NVFP4, NCCL needs 45 us for a 4 KB all-reduce and 344 us for 64 KB, which is most of the per-token budget at low batch sizes.

[`b12x`](https://pypi.org/project/b12x/) (Apache-2.0) is an SM120/SM121-only CuTe DSL kernel library that ships IPC-backed PCIe all-reduce runtimes for exactly this topology. This PR wires two of them into SGLang behind an opt-in flag.

## What this adds

A new `B12xPCIeCommunicator` and a three-tier dispatch inside `GroupCoordinator._all_reduce`:

| message size | path |
|---|---|
| `<= 8 MB` | b12x PCIe **one-shot** all-reduce (decode-sized hidden states) |
| `8 MB .. 256 MB` | b12x PCIe **DMA ring**, optional FP8 wire format (prefill chunks) |
| otherwise | existing NCCL path, unchanged |

The one-shot runtime also exposes a fused `all-reduce + residual add + RMSNorm`, plugged into the existing `fused_allreduce_rmsnorm` coordinator hook that AITER already uses (`layers/communicator.py` + `layers/layernorm.py`). That kernel is specialized for `<= 36` rows, so the dispatch helpers cap on token count and fall back when it does not apply — including an explicit all-reduce fallback in `_forward_with_allreduce_fusion`, since the caller has already skipped its own all-reduce when it takes the fusion path.

## Safety / blast radius

- Off by default: `SGLANG_B12X_PCIE_AR` and `SGLANG_B12X_PCIE_DMA` are `EnvBool(False)`.
- The communicator is only constructed for the **tensor-parallel** group (other groups would just pin IPC buffers).
- `b12x` is an optional dependency; when it is not installed the setup logs a warning and everything stays on NCCL. No changes to any default code path.
- Every tier re-checks dtype / contiguity / size and returns to NCCL when the kernel declines.

## Results

GLM-5.2-NVFP4, 8x RTX 6000D (SM120, PCIe), driver 595.71.05, KV cache FP8, greedy, prefix caching off.

**Kernel microbenchmark** (8 ranks, NCCL vs b12x one-shot): 4 KB 45.0 -> 7.3 us (6.1x), 12 KB 58.5 -> 15.3 us (3.8x), 64 KB 344.5 -> 38.5 us (8.9x).

**TP8 decode** (ISL 1 / OSL 256), median TPOT / output tok/s:

| bs | baseline (NCCL) | + b12x |
|---|---|---|
| 1 | 23.9 ms / 41 | **14.7 ms / 66** |
| 8 | 70.6 ms / 112 | **29.8 ms / 264** |
| 32 | 105.8 ms / 300 | **69.2 ms / 457** |

**TP8 e2e 8K** (ISL 8192 / OSL 64), median TTFT: `6103 ms -> 1384 ms` (DMA ring tier).

**TP4xPP2 + MTP, 64K** (ISL 65536 / OSL 1024), bs1: TTFT `11.5 s -> 9.3 s`, TPOT `10.3 ms -> 9.5 ms`, accept length 3.00.

**Accuracy**: GSM8K (20 questions) stays at 0.900 for both TP8 and TP4xPP2+MTP — identical to the NCCL baseline — with `Invalid 0.000`, and greedy output matches token-for-token on a fixed prompt.

## Test plan

- [x] TP8 and TP4xPP2(+MTP) launch with both tiers active (8/8 ranks report one-shot + DMA enabled, no init failures)
- [x] Communicator is built for the TP group only (`world=4` under TP4xPP2, PP group untouched)
- [x] GSM8K 0.900 / Invalid 0.000, greedy output matches baseline
- [x] decode (bs 1/8/32), e2e 8K, 64K sweeps as above
- [x] Gate off (default): unchanged NCCL behaviour

## Notes for reviewers

- Requires `pip install b12x` (plus `nvidia-cutlass-dsl`, pulled in as a wheel dependency; kernels are JIT-compiled on first use).
- The DMA ring allocates a scratch slab sized by `SGLANG_B12X_DMA_MAX_BYTES` (default 256 MB); on memory-tight setups this competes with the KV pool, so raise `--mem-fraction-static` accordingly when enabling it together with speculative decoding.
- `_FUSED_MAX_ROWS = 36` mirrors the current kernel limit and is duplicated in `communicator.py` as `_B12X_FUSED_MAX_ROWS`; happy to expose it from the package instead if maintainers prefer.
- This is orthogonal to #30775 (PP x speculative decoding). Stacking both is what produces the 64K number above.
