# [parser] Hold back harmony markers split across streaming chunks

[Upstream PR](https://github.com/sgl-project/sglang/pull/41017) · state: closed · merged: False

## Original PR description

## Motivation

Streaming a GPT-OSS response can lose the entire answer and every tool call.

`HarmonyParser.parse(chunk)` appends the chunk to a buffer, re-parses the whole
buffer, and resets the buffer to whatever the strategy hands back. When a
structural marker straddles a chunk boundary, `iter_tokens` folds the
incomplete tail into a `TEXT` token -- and `CanonicalStrategy` has three paths
that can meet such a fragment. Only one of them held it back. The other two let
it through, and because the fragment was emitted it also left the buffer, so the
marker could never be completed once the next chunk arrived. The analysis
channel then never closed and everything after it -- final answer, tool call --
was streamed as reasoning.

Reproduced through the real serving entry point. `--reasoning-parser gpt-oss`
resolves to `GptOssDetector`, whose streaming path is
`parse_streaming_increment` -> `HarmonyParser.parse`. A 301-character
analysis / tool-call / final stream fed in 5-character detokenizer chunks that
cut inside `<|end|>`, `<|call|>` and `<|return|>`:

| | `reasoning_text` | `normal_text` |
|---|---|---|
| before | the entire stream, markers and all | `''` |
| after | the analysis only | the tool call block plus the final answer |

So the client received no tool call and no answer at all; the whole response
was rendered as thinking. Any agent built on GPT-OSS breaks as soon as the
detokenizer happens to split a marker, which is not a rare event -- markers are
multi-token special sequences, which is exactly why the sibling detectors
already guard against it.

## The three paths

1. `_parse_partial_analysis` streamed `text[content_start:]` verbatim. This is
   the severe one: emitting the fragment also removed it from the buffer, so
   the marker was unrecoverable and the channel stayed open forever.
2. `_parse_block`'s `end_pos >= len(tokens)` branch accepts a **final** block
   that stops at end of input without a `<|return|>`. That makes it the only
   block path that can end on a partial marker, and it emitted the fragment
   into the answer.
3. `parse()` ended with `return events, ""`, dropping a partial marker left
   after a fully consumed token stream instead of handing it back.

All three now use `prefix_hold`, the helper the `TEXT` path of `parse()`
already used -- so this is consistency within the file rather than a new
mechanism. It is the same approach the sibling detectors take
(`muse_glimmer_format.partial_marker_len`,
`kimik3_format.partial_suffix_len`), and it matches the fixes already made for
other formats that hold back tags split across chunks (#31009, #33097).

## Tests

In `test/registered/unit/parser/test_harmony_parser.py`:

- `test_streaming_property_marker_split_across_chunks` -- splits every marker
  so that each chunk boundary lands inside one, then asserts the concatenated
  reasoning is `reasoning` and the normal content is `answer`, matching the
  one-shot parse.
- `test_split_call_marker_still_yields_tool_call` -- splitting `<|call|>` must
  not swallow the tool call into reasoning.
- `test_final_block_holds_partial_marker` -- for every proper prefix of every
  guard token, a final block must neither emit the fragment as content nor drop
  it from `remaining`.

- One case is deliberately *not* claimed as invariant:

  (`# Only stream analysis content - tool calls wait for completion`), not
  something this PR changes; the tool call itself is still detected and
  emitted.
