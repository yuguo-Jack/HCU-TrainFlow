# [Refactor] scheduler: Finish queue-popped aborts in place

[Upstream PR](https://github.com/sgl-project/sglang/pull/43897) · state: closed · merged: True

## Original PR description

- `abort_request` finishes a request it pops from the waiting queue with `finish_outside_step(FINISH_ABORT())` right after the pop, in every disaggregation mode; the PD decode branch's existing finish moves into this shared path. The dLLM queue branch does the same, and `_abort_on_queued_limit` finishes the request it evicts with its queue message and status 503.
- `test_scheduler_timeouts.py`: `TestQueuedAbort` sends two aborts that match one queued request still listed in the last batch; the first pops and finishes it, the second leaves it alone (no `to_finish`, released once). It fails without this change. The fake request gains `finish_outside_step`, and its `finished()` reads `finished_reason` as `Req.finished()` does.

No client-visible change. Internally:
- A later abort, in the same intake or after, skips a popped request because it is finished. Before, the running-request path (abort method 3) wrote `to_finish` into a request that was still in an in-flight batch (one requeued after its step ran) although it was already released and reported; nothing applied that field.
- Releasing a popped request that still holds KV (a PD prefill or dLLM queue request, or a waiting request on a mamba tree) now sees it finished in `claim_kv_row`: the request's PP prefetch ticket is released there (a no-op when the abort release already retired it), and a streaming-session turn that borrowed its slot's record hands the record back as an aborted turn instead of keeping it in the slot.
- In PD decode the finish is set before the host backup and HiSparse release instead of after; neither reads it.
