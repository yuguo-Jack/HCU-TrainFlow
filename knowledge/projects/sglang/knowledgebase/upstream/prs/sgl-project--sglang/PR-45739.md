# [Perf] [AMD] Qwen3-Next: fused QK Gemma RMSNorm + partial RoPE on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/45739) · state: closed · merged: True

## Original PR description

## Summary

Route the Qwen3-Next full-attention prologue — the per-head `[Q||gate]` split, Q/K Gemma RMSNorm (`x*(1+w)`), and partial NeoX RoPE (rotary_dim 64) — through the fused aiter op `fused_attention_qk_norm_rope` on gfx950, replacing three small launches with one.

## Gating 

- Gated on `SGLANG_USE_AITER` + `is_hip()` — no bespoke per-kernel flag.
- The aiter import is lazy and only reached on HIP, so the NVIDIA common path never imports or touches the AMD-only code.
- Support is probed (`fused_attention_qk_norm_rope_supported`), not asserted, so any uncovered shape (dtype/width/arch) falls back to the native split + GemmaRMSNorm + RoPE. The attention backend still writes the KV cache.

## Dependencies

- **aiter op**: `fused_attention_qk_norm_rope` in ROCm/aiter — https://github.com/ROCm/aiter/compare/main...karverma-amd:aiter:karverma/qwen3-next-fused-prologue?expand=1
- **Stacked on #45738** (the `smallm_fp8_blockscale_gfx950` import fix), which Qwen3-Next FP8 needs to serve on gfx950. The first commit in this PR is that fix; the second commit is the wiring under review here.

## Test results

E2E on Qwen3-Next-80B-A3B-Instruct-FP8, MI355X 2×TP4, latest nightly (`v0.5.22-rocm724-mi35x-20261021`) with **Triton 3.8.0**:

- Median TPOT **−2.3 to −3.0%** at concurrency 1/8/32 (throughput +2.3 to +7.9%); stable through cuda-graph capture and sustained conc-8/32/64 load.
- GSM8K 1319-question 5-shot: parity (fused 0.941 / native 0.948, 0 invalid).
- Engagement confirmed on the fused arm; fail-closed to native verified on the control arm.
- The same nightly on stock Triton 3.7 and v0.5.21 + Triton 3.8 reproduce the same −2.5 to −3.0% TPOT and GSM8K parity.
