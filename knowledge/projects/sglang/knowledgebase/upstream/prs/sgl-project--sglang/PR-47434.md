# [Fix] spec: Greedy requests keep the argmax prefill draft under rejection sampling

[Upstream PR](https://github.com/sgl-project/sglang/pull/47434) · state: open · merged: False

## Original PR description


## Motivation

With rejection sampling on (`--speculative-use-rejection-sampling`, enabled by default for EAGLE topk 1 on ROCm, where there is no
tree-sampling verify kernel), `EagleDraftWorker._draft_extend_for_prefill` draws the first draft token of every request with `fast_sample`
from `softmax(logits / T)`. `SamplingParams` turns temperature 0 into temperature 1.0 with top_k 1, so a greedy request's first draft token is
sampled at T = 1 instead of taken as the argmax. Every later draft step (`draft_forward`, `_draft_extend_for_decode`) goes through
`sample_draft_proposal`, which proposes the argmax for top_k == 1 rows.

Greedy output should not depend on the sampler state. With ReplaySSM (`--enable-linear-replayssm-spec`, Qwen3.5/3.8 GDN models) the
target's numerics depend on where accepted tokens fall in the replay ring, so a different first draft token changes later near-tie tokens:
greedy outputs of the same prompts differ between two passes in one server and across restarts.

## Modifications

`_draft_extend_for_prefill` proposes the first draft token with `sample_draft_proposal` (argmax for top_k == 1 rows), like every later
draft step. The draft distribution passed to the verify is the same `softmax(logits / T)` as before. One call per prefill batch, as before.

The multi-layer EAGLE worker's prefill path (`multi_layer_eagle_worker_v2.py`) calls `sample_draft_proposal` without `top_ks` and is not
changed here.

## Accuracy Tests

Qwen3.8-27B-Quark-AWQ-MXFP4, MI355X, TP1, `--attention-backend aiter --kv-cache-dtype fp8_e4m3`, MTP 3/1/4 (EAGLE topk 1) +
`--enable-linear-replayssm-spec`, rejection sampling auto-enabled. 50 ShareGPT prompts, greedy, 256 output tokens, thinking off,
batch size 1; identical outputs out of 50:

Upstream main 8080507c3e + #47430 (FP8 Q for the verify attention; without it the verify attention fallback on this setup makes greedy
MTP output vary from run to run by itself), with and without this PR:

| | second pass, same server | vs a separate server with rejection sampling off |
|---|---|---|
| without this PR | 41/50 | 45/50, 44/50 (both passes) |
| this PR | **50/50** | **50/50**, **50/50** |

Earlier on a Qwen3.8 build of main (e732f5d41e + 14 open AMD Qwen3.8 PRs), same check: without this PR 43/50 in one server, 38-43/50
across restarts (9 runs), 40-43/50 vs rejection sampling off; with this PR 50/50 in each.

"Rejection sampling off" is the same server with `--speculative-accept-threshold-single 0.9999999`, which keeps the auto-enable rule
from firing.

## Speed Tests and Profiling

No speed change expected: the prefill path makes the same single `sample_draft_proposal` call as `_draft_extend_for_decode`, once per
prefill batch. Not measured separately.
