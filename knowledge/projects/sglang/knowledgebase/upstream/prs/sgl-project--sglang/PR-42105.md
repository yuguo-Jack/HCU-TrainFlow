# [BugFix] Reject LoRA loads before exceeding pinned adapter capacity

[Upstream PR](https://github.com/sgl-project/sglang/pull/42105) · state: closed · merged: False

## Original PR description

## Motivation

When pinned adapters already occupy `max_loaded_loras`, both dynamic LoRA load routes issue a backend load before discovering that no adapter can be evicted. A new pinned adapter then returns an error while remaining loaded above the configured limit. A new unpinned adapter is immediately evicted again while the API reports success.

For example, with one pinned adapter and a limit of one, the current HTTP routes return 400 with both adapters registered for a pinned load, or 200 with only the old adapter remaining for an unpinned load.

## Modifications

Check pinned capacity under the existing LoRA update lock before loading a new adapter name. If pinned adapters fill the limit, return the normal failed-load response without contacting the backend or updating the registry. Both disk and tensor load routes share the check.

Existing duplicate-name diagnostics, pending-unload handling, unlimited capacity, and LRU eviction when an unpinned slot is available retain their existing behavior.

## Accuracy Tests

- Five new test methods exercise both load routes, pinned/unpinned incoming adapters, spare/unlimited capacity, mixed pinned/LRU eviction, duplicate names, and concurrent pinned loads. The original implementation fails five assertions; the changed implementation passes all ten methods in the existing LoRA update test module.
- Actual ASGI endpoint, protocol, control-method and registry reproduction: four full-capacity cases now return 400 with no backend calls or registry changes; both spare-capacity controls return 200 and retain the new adapter.
- Matching pre-commit hooks and `git diff --check` pass.

Local CPU harnesses execute the original methods and protocol definitions, complete registry/RWLock modules, and original counter/serialization helpers. They exclude GPU package initialization and replace scheduler IPC/configuration with controlled test boundaries. No GPU adapter loading or distributed inference run is claimed.

## Speed Tests and Profiling

No inference-speed claim. The check runs only on dynamic adapter loads and avoids loading adapters that cannot remain within the configured capacity.
