# [Perf] [AMD] kimi-k3: Run Quark MXFP4 shared experts in BF16 on the merged MoE front

## Motivation

The Quark Kimi-K3 checkpoint (`Kimi-K3-Quark-MXFP4-AttnFP8`) stores the shared experts in MXFP4 and leaves the router and the latent down-projection in BF16. `KimiK3MoE._merge_front_weights` concatenates only dense weights, so on ROCm these MoE layers get no merged front and run `_forward_unfused`. There the shared gate-up and down run as separate W4A4 GEMMs, with online MXFP4 activation quantization, next to separate router and latent GEMMs.

This PR adds an opt-in switch that dequantizes those shared experts to BF16 once, at load. The existing merged front and the fused single-collective path (`_forward_fused`) then cover these layers too. Decode is up to 5% faster, and GSM8K improves from 93.6% to 96.8%: with the W4A4 shared experts, 3.7% of answers turned into runaway generations, and with the switch on there are none.

## Modifications

- `QuarkW4A4MXFP4.dequantize_to_bf16` is the existing `AITER_FORCE_A8W4` dequantize step, moved into a method and made idempotent. `create_weights` always sets `layer.dequantized_bf16`, `process_weights_after_loading` skips a linear that is already densified, and `apply_weights` reads the field directly instead of through `getattr`.
- `kimi_k3_rocm_quant.densify_quark_mxfp4_shared_experts` is called from `KimiK3MoE._merge_front_weights`, behind `_is_hip` and the switch, only where the full front can be built (shared experts present, no MoE all-to-all backend).
- The switch is `SGLANG_OPT_HIP_K3_QUARK_SHARED_FULL_FRONT`, off by default, documented in `environ.py` and the AMD & ROCm table of the environment variable reference. With it off, nothing changes. CUDA and other checkpoints are not affected.
- `test_kimi_k3_rocm_quant.py` tests that densifying and the loader's post-processing commute. Two orders are covered:
  - Model first, as with `DefaultModelLoader`.
  - Loader first, as with the sharded-state and remote-instance loaders under `AITER_FORCE_A8W4=1`.

  In both, each weight must be decoded exactly once. Removing either guard makes the test fail.
- Memory: at TP8, BF16 shared experts take 24 MB more per MoE layer than MXFP4, or 2.2 GB per GPU over K3's 92 MoE layers. Measured on the server below, the KV cache and KDA state budget fell by 2.75 GB per GPU (40.4 to 37.7 GB), because some of the freed MXFP4 blocks stay in the allocator. The docs give the measured figure.
- The cookbook is unchanged. Its MI35x recipe serves `moonshotai/Kimi-K3`, whose shared experts are already BF16, and the switch stays off by default.

## Accuracy Tests

GSM8K with sgl-eval 0.1.3 on all 1319 questions, using the `moonshotai/Kimi-K3` preset (temperature 1.0, top_p 0.95, thinking on, reasoning_effort max, max_tokens 300000) and 64 threads. Each switch setting has its own server, with the configuration below and the radix cache on (the cookbook default). One run each.

```bash
sgl-eval run gsm8k --load-preset-from-model-id moonshotai/Kimi-K3 \
  --model /data/models/Kimi-K3-Quark-MXFP4-AttnFP8 --base-url http://127.0.0.1:30000/v1 --num-threads 64
```

| | Switch off | Switch on |
|---|---:|---:|
| Score | 93.56% | 96.82% |
| Answers longer than 4096 tokens | 49 (longest 104,830; 3 correct) | 0 (longest 4,056) |
| Score on answers of at most 4096 tokens | 96.93% | 96.82% |
| Mean output tokens | 1,265 | 123 |
| Truncated / errors | 0 / 0 | 0 / 0 |

The whole gap comes from the runaway answers. On the rest, the two settings score the same.

## Speed Tests and Profiling

8x MI355X, `/data/models/Kimi-K3-Quark-MXFP4-AttnFP8`. SGLang is `main` @ `2815eed49c` plus this change. The PR head carries the same code on a newer `main`; only the docs wording differs. AITER is the image's `2bb549102`.

The server is the cookbook MI355X Unified Balanced recipe, Non-Spec:

```bash
SGLANG_USE_AITER=1 SGLANG_AITER_K3_OPT=1 AITER_FLYDSL_FORCE=1 AITER_SITUV2_A8W4=1 SGLANG_MLA_DECODE_TUNE=1 \
SGLANG_AITER_HONOR_EXPLICIT_MEM_FRACTION=1 SGLANG_OPT_HIP_K3_QUARK_SHARED_FULL_FRONT={0,1} \
python -m sglang.launch_server --model-path /data/models/Kimi-K3-Quark-MXFP4-AttnFP8 --trust-remote-code \
  --tp-size 8 --dcp-size 8 --dcp-comm-backend a2a \
  --prefill-attention-backend aiter --decode-attention-backend aiter \
  --kv-cache-dtype fp8_e4m3 --dtype bfloat16 --mem-fraction-static 0.85 --cuda-graph-max-bs-decode 256 \
  --reasoning-parser kimi_k3 --tool-call-parser kimi_k3 --disable-radix-cache
```

Differences from the cookbook:
- The Quark checkpoint instead of `moonshotai/Kimi-K3`.
- Non-Spec instead of DSPARK.
- `SGLANG_AITER_HONOR_EXPLICIT_MEM_FRACTION=1`. Without it, the AITER long-context scaling turns 0.85 into 0.7225, which leaves about 6 GB for KV cache and state and limits admission to 11 requests.
- `--disable-radix-cache`, for the speed sweep only. The seed-42 random prompts repeat across levels, so with the radix cache on, later levels hit prefixes that earlier levels cached, and the two servers evict differently.

Client, 8192 input / 1024 output tokens, 4 waves per concurrency (at least 8 prompts), 32 warmup requests before the first level:

```bash
python -m sglang.benchmark.serving --backend sglang --dataset-name random \
  --random-input-len 8192 --random-output-len 1024 --random-range-ratio 1.0 \
  --max-concurrency C --num-prompts 4C --request-rate inf --seed 42
```
