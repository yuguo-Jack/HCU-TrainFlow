# [Fix] cuda-graph: Keep attention metadata and SP workspaces alive across graph variants of a batch size

[Upstream PR](https://github.com/sgl-project/sglang/pull/46720) · state: closed · merged: True

## Original PR description

## Motivation

Enabling the LoRA dual graph (a base-only `nolora` decode graph captured next to the `lora` graph for every batch size) made the graph runners capture two graphs per batch size. Attention backends that rebuilt their per-capture metadata keyed only by batch size then freed buffers the first graph still read, and replay refreshed only the table entry. The symptom depended on allocator recycling: zeroed attention rows on GB300 (full prefill backend), a wrong token at a later decode position on H200/H100 (breakable backend), nothing visible elsewhere. The LoRA CI graph tests caught it as an intermittent decode fault. The bug itself is in the attention backends and the sequence-parallel workspace and applies to any second graph per batch size (attention variants, verify tiers), not only to LoRA.

## Modifications

- `flashinfer`: share the CUDA-graph attention wrappers across the graph variants of a batch size (MHA and MLA decode with a one-time bootstrap plan, MLA verify reuse); replay refreshes buffer contents, never table entries.
- `attention` (TRTLLM MHA/MLA): keep per-batch-size capture metadata alive across graph variants, with regression tests.
- `sp_collective_gemm`: retain workspace generations that captured graphs still use when the workspace grows.
- `lora`: the dual decode graph becomes opt-in through `SGLANG_ENABLE_LORA_DUAL_GRAPH` (default off). The fixes cover the backends that exist today, but nothing guarantees that a new backend or runner keeps its per-batch-size metadata alive under a second graph, so the optimization stays off by default; the stacked PR (#46721) adds the tool and skill with which a deployment that wants it can check its own serving command before turning it on.
- test kit: the attention unit-test kit captures two real graphs per decode case, so a backend that drops the first graph's buffers fails in CI.

No tolerance, default graph backend or router precision changes.

## Accuracy Tests

- CPU regression tests (`base-a-test-cpu`): `test_attention_graph_metadata_reuse.py`, `test_trtllm_mha_paged_kv.py`, `test_layernorm_sp.py`, `test_lora_inactive_batch_skip.py`: 12 of 30 cases fail on the base commit, all pass here.
- Attention kit real captures (six backend files) pass on GB300 and H200.
- The standalone lifetime tracer of the stacked PR, run on Qwen1.5-MoE with a LoRA adapter, flashinfer attention and the dual decode graphs (TP1 and TP2): on the base commit three decode graphs read flashinfer wrappers freed while alive and the worker dies; here no dangling operand across 106 captured graphs per worker.

## Speed Tests and Profiling

No kernel or scheduling change; the fixes keep already-allocated metadata alive across captures.

🔴 Four registered DCP metadata tests on the 4-gpu-b200 CI runner will fail with KeyError after this merges. They seed `decode_cuda_graph_metadata` with the old int `bs` key. `_apply_cuda_graph_metadata` now reads `self.decode_cuda_graph_metadata[(bs, mode)]` (trtllm_mla_backend.py:626), so `{bs: metadata}` no longer matches. Fix: update every fixture that builds this dict by hand to use `(bs, ForwardMode.DECODE)` / `(bs, ForwardMode.TARGET_VERIFY)` keys, or have it go through `_init_cuda_graph_metadata`. Same pattern at 2 sites (test/registered/dcp/test_trtllm_mla_family_dcp_metadata.py:46, test/manual/attention/test_trtllm_mla_backend.py:1042).

<details>
<summary>Why this was flagged</summary>

`_make_backend` at test/registered/dcp/test_trtllm_mla_family_dcp_metadata.py:46 sets `backend.decode_cuda_graph_metadata = {bs: metadata}`. `_apply` (line 56) then calls `backend._apply_cuda_graph_metadata(..., forward_mode=ForwardMode.TARGET_VERIFY / DECODE)`. That method now builds `key = (bs, ForwardMode.DECODE if ... else forward_mode)` and indexes the dict with it (trtllm_mla_backend.py:622-626), which raises KeyError before the DCP branch runs. Affected: `test_target_verify_splits_global_and_local_lengths` and `test_decode_does_not_add_draft_tokens`, each run for `TestTRTLLMMLADCPMetadata` and `TestCuteDslMLADCPMetadata` (CuteDslMLABackend inherits the method), so four cases. They pass on the base, where the lookup was `decode_cuda_graph_metadata[bs]`. The file is registered via `register_cuda_ci(stage="base-b", runner_config="4-gpu-b200")` and is not in this PR's changed files.

**Verification:** The capture path writes with the same tuple key (line 606). The DCP test's `_make_backend` still seeds the dict by hand with an int key at line 46: `backend.decode_cuda_graph_metadata = {bs: metadata}`. That raises KeyError on line 626, before the `get_parallel().dcp_enabled` branch runs. On the base, `self.decode_cuda_graph_metadata[bs]` matched the int key and these tests passed.

</details>

File: `python/sglang/srt/layers/attention/flashinfer_mla_backend.py` · line 401

🔴 After a decode CUDA-graph recapture (update_weights with `recapture_cuda_graph=True`), FlashInfer MLA decode graphs read a stale KV-index buffer and produce wrong tokens. The base built a fresh wrapper per capture. The reuse at line 378 picks up the wrapper from the previous runner, still bound to the old `cuda_graph_kv_indices`. `init_cuda_graph_state` has already replaced that buffer, and replay writes only the new one. Fix: clear `decode_cuda_graph_metadata` and `prefill_cuda_graph_metadata` in `init_cuda_graph_state`, so a new runner never reuses wrappers bound to buffers that were swapped out.

<details>
<summary>Why this was flagged</summary>

Trigger: `WeightUpdater` (weight_updater.py:247-255) calls `recapture_decode_cuda_graph` -> `init_decode_cuda_graph`, which builds a new DecodeCudaGraphRunner on the same `model_runner.attn_backend` (decode_cuda_graph_runner.py:355) and calls `init_cuda_graph_state` again (line 454). FlashInferMLAAttnBackend.init_cuda_graph_state (flashinfer_mla_backend.py:533-556) allocates a new `self.cuda_graph_kv_indices`. `decode_cuda_graph_metadata` is only set once, in `__init__` (line 343), so the `.get(bs)` at line 378 returns the old wrapper, whose kv_indices buffer is the old tensor (line 385). On every replay, `_apply_cuda_graph_metadata` fills the NEW buffer (lines 941-945). `fast_mla_decode_plan` (lines 1389-1426) ignores `kv_indices` and copies nothing into the wrapper. The recaptured kernels therefore read the frozen old indices and attend to the wrong KV pages. On the base, each capture built a new wrapper bound to the current buffers and ran the real plan, so recapture stayed correct.

**Verification:** The decode runner reuses `model_runner.attn_backend` (decode_cuda_graph_runner.py:355). `init_cuda_graph_state` (flashinfer_mla_backend.py:533-556) allocates a new `self.cuda_graph_kv_indices`, but line 378 returns the wrapper bound to the old buffer. `fast_mla_decode_plan` (lines 1389-1426) does not copy kv_indices into `self._kv_indices_buf`.

</details>
