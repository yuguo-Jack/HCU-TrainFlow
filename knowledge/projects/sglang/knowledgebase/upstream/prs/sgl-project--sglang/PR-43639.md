# [Perf] Enable native MXFP4 routing and CuTeDSL fusion for MiMo

[Upstream PR](https://github.com/sgl-project/sglang/pull/43639) · state: open · merged: False

## Original PR description

## Motivation

MiMo MXFP4 currently computes routing separately and finalizes the MoE output before communication. Use FlashInfer native routing and deferred finalization with the existing CuTeDSL layer-boundary fusion to reduce this overhead.

## Modifications

- Add native grouped routing and deferred finalization for supported MiMo MXFP4 configurations.
- Support CuTeDSL layer-boundary fusion without shared experts.
- Automatically select CuTeDSL for supported configurations, preserving explicit backend choices.
- Keep standard routing for expert capture, distribution recording, simulated routing and expert remapping. Exclude PDMux from automatic selection.

RoPE/KV-store fusion remains in #43106.

## Accuracy Tests

The same 128 frozen GSM8K questions, normal EOS and generation settings were used for both versions. Exact numerical-answer scoring changes from 123/128 to 124/128, with two gains and one loss. Strict answer-string scoring is 119/128 and 120/128, respectively.

Fixed-prefix full-vocabulary log-probabilities were compared on 24 cases. Exact argmax matches in 22 cases; one additional mismatch falls within the baseline's tied top-1 set, while one changes the top-1 choice outside that set. Mean total variation distance is 3.15%, with a maximum of 14.10%.

FlashInfer native routing returns BF16 expert weights, while the precomputed route retains FP32 weights. Generated outputs and DFlash acceptance trajectories are not identical. These checks do not establish numerical equivalence or general quality equivalence.

## Speed Tests and Profiling

MiMo-V2.6-Pro-RL revision `73875d00b30a`, 8×B300, TP8, concurrency one, FA4, page size 128, KV capacity 32768 and prefix caching disabled.

Baseline: `6e7beace143964386ce2e4418401b7369f0dabd0`.
Candidate: `d7b192133f73ef2068debc349eda85a1d0dce218`.

Each comparison uses one fresh server per revision, three warmups and 96 frozen random-topic essay requests with 8,000 input tokens and 1,024 output tokens. EOS is ignored only for timing. Both versions use the same model, dependencies and requests; DFlash comparisons also use the same draft checkpoint.

Decode throughput uses tokens emitted after the first emission divided by the first-to-last emission interval. E2E throughput and TTFT are reported separately. Timing excludes profiling and log-probability collection.

| Mode | Decode tok/s | E2E tok/s | TTFT ms |
| --- | --- | --- | --- |
| DFlash, baseline | 302.44 | 285.44 | 204.75 |
| DFlash, candidate | 338.01 | 315.72 | 216.63 |
| Without DFlash, baseline | 176.54 | 170.75 | 202.17 |
| Without DFlash, candidate | 186.58 | 179.74 | 214.21 |

With DFlash, decode throughput improves by 11.76% and E2E throughput by 10.61%. All 96 requests have partial rejection; acceptance changes from 21.38% to 21.61%, so the measured gain includes verification-workload differences.

Without DFlash, decode throughput improves by 5.69% and E2E throughput by 5.26%. Mean TTFT increases by approximately 12 ms in both modes.

These results cover the measured single-concurrency workload and are single fresh-server pairs, not multi-run confidence estimates.
