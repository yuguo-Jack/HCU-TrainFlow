# [Fix] [NVIDIA] dist: Detect MNNVL fabric devices by NVML fabric state, not only by GB200/GB300 name

[Upstream PR](https://github.com/sgl-project/sglang/pull/46463) · state: closed · merged: True

## Original PR description

## Motivation

`is_mnnvl_fabric_device()` keys only on the GB200/GB300 device names. SM107 NVLink systems report a generic device name, so multi-node launches there never get `NCCL_MNNVL_ENABLE` / `NCCL_CUMEM_ENABLE`, custom all-reduce v2 stays intra-node, and DCP defaults to NCCL all-to-all instead of `fi_a2a`.

## Modifications

`common.py`: keep the GB200/GB300 name check as the fast path; otherwise ask NVML whether the GPU has completed NVLink fabric registration, through the existing `is_gpu_fabric_ready` probe that custom all-reduce v2 already uses per device. GPUs without a fabric manager (HGX-style nodes) report the fabric state as unsupported and stay `False`.

## Accuracy Tests

Probe on an SM107 node (device name `NVIDIA Graphics Device`, `nvidia-smi -q` fabric state `Completed`): `is_gpu_fabric_ready` True, `is_mnnvl_fabric_device()` True; before this change it returned False there. Behavior change is in communication path selection only. On a two-node SM107 TP8/DCP8 Kimi-K3 NVFP4 launch the fabric paths (custom all-reduce v2 multicast, `fi_a2a`) came up and the model served normally; see the fork measurement below.

## Speed Tests and Profiling

Two-node SM107 TP8/DCP8, Kimi-K3 NVFP4, bs=1, 61k in / 1k out, 95% prefix hit, DSpark acceptance 5.5, `one_batch_server`: 379 tok/s before, 485 tok/s median after (5 launches x 3 requests).
