# [Perf] qwen3.5: Support prefill MBO (stacked on #43655)

## Original PR description

## Motivation

This includes the prefill MBO implementation from #43655 at `cb75eee961` and adds dense Qwen3.5/Qwen3.8 support. The original Qwen follow-up is available as a focused [commit](https://github.com/1007281134yanyu-cloud/sglang/commit/6a824f0a5288a5b1b51ac9ab4d0a26047e5683a3) / [seven-file diff](https://github.com/1007281134yanyu-cloud/sglang/compare/cb75eee9610f676d52daca0fd99afb7e10ffce41...6a824f0a5288a5b1b51ac9ab4d0a26047e5683a3).

### Integration update (2026-10-27)

Merged main `618136d4d3` in [`534f79c5`](https://github.com/1007281134yanyu-cloud/sglang/commit/534f79c5a6fe3c42feedaf67325ace452afab3d2), preserving the original commits. Resolved conflicts while retaining main's DeepSeek V4 base-class dispatch, `DraftParallelLayout`, resolved prefill shared-read events and Qwen RoPE refresh policy. #43655 remains unmerged; its implementation is included here and still needs maintainer review.

Integration checks: 35 batch-overlap tests / 18 subtests, plus 25 related shared-read/Qwen tests / 36 subtests passed with GPUs hidden. This includes two new regressions for V4 subclass dispatch and eager MBO shared-read event ordering. Pre-commit and whitespace checks passed.

Fresh TP2 `/generate` smoke on 2× RTX 5090 / the public NVFP4 checkpoint completed 12 requests per arm: 1k/8k/16k/32k/64k cold inputs, a 32k cached prefix with 16k new tokens, a repeated hit, and c4×16k. All requests returned the requested 16 output IDs. Cold cache counts were zero; prefix/repeat hits reported 32,768/40,960 cached tokens. Within each arm, cached and repeated outputs matched its own cold counterpart. Across arms, first output IDs matched 12/12, while full 16-token outputs matched only 5/12; numerical equivalence is not claimed. MBO logged 82 recovered allocator warning lines across ranks (native: zero), with no serving traceback before deliberate shutdown. This smoke is not a performance or full-accuracy rerun.

**The accuracy and performance numbers below were measured on the original `6a824f0a` snapshot with FlashInfer 0.7.1. They are historical evidence for that snapshot, not a rerun of the full matrix on this integration commit.** The integration GPU checks use an isolated FlashInfer 0.7.2 environment, as required by current main.

## Modifications

- Add Qwen GDN/full-attention and FFN stages that join the previous asynchronous sum and leave their own TP sum in flight. Preserve GLM finalization while allowing Qwen to finish through its residual stream.
- Gate MoE, auxiliary hidden-state capture, MNNVL fusion, PP, mismatched attention TP, and DCP configurations. Deepstack visual embeddings fall back to unsplit execution.
- Slice/pad M-RoPE positions on the token dimension. Keep flat positions unchanged.
- Route eligible MBO batches away from unsplit prefill CUDA graph replay; otherwise graph replay bypasses eager `maybe_split`. Other batches retain their graph path.

## Accuracy Tests

Public `RadixArk/Qwen3.8-27B-NVFP4`, TP2 on 2× RTX 5090 (PCIe, no NVLink), `modelopt_fp4`, FP8 E4M3 KV. This validates the shared Qwen3.5 architecture with this checkpoint; it is not separate BF16/Qwen3.5/TP4/image-input validation.

- **24 cold long prompts:** empty cache per prompt, greedy generation of 64 tokens. First-output-token top-1 agreed 24/24; truncated top-20-union probability distance mean 0.00426, max 0.01498. Only 3/24 full 64-token outputs matched, so this is **not a losslessness claim**. The distance omits probabilities outside the two top-20 sets and is not full-vocabulary TV.
- **Cached prefixes:** four additional token-pool prompts (40k/48k total length), each tested cold, with a 32k cached prefix, and on a repeated hit. Within each configuration, all eight cache-versus-own-cold first-token distributions and full output-ID sequences were bit-identical. Across configurations, the same prompts already differed when cold (distance mean 0.07822, max 0.14932); the smaller LooGLE probe value should not be generalized.
- **LooGLE-MC:** existing 218-question subset, identical pretokenized prompts, concurrency 8, greedy, normal EOS and 4096-token output budget. This is a controlled subset comparison, not an official full-benchmark score.

| Configuration | Original parser | Require emitted `</think>` before scoring | Length finishes |
|---|---:|---:|---:|
| Native | 172/218 | 169/218 | 22 |
| MBO | 174/218 | 172/218 | 14 |

The original parser searches the whole response when `</think>` is absent, so it can count an answer inside unfinished reasoning. Both definitions are disclosed. Small single-run differences, different generation lengths, and truncation do not establish improved quality or equivalence.

- **Unit tests:** 16 tests and 14 subtests passed with GPUs hidden; covers gates, alternating layers, optional finalization, M-RoPE/flat positions, and graph split routing. `pre-commit` and `git diff --check` passed.

## Speed Tests and Profiling

All three primary arms use TP2, 8192-token chunk/max-prefill size, context 131072, page 256, max-running 16, `mem-fraction-static=0.80`, and the same 487,936-token capacity. MBO uses `SGLANG_PREFILL_MBO=1 SGLANG_PREFILL_MBO_MIN_TOKENS=8192`. Versions: torch 2.14.1+cu130, sglang-kernel 0.4.9, FlashInfer 0.7.1.
Cold prefill: output 1 token, per-length cache flush, same token-pool slices/order across arms, two rounds, 4 sequential c1 requests and 8 c4 requests per round. Below is c4 new-input tokens divided by wall time, combined over the two rounds.

| Input tokens | Native | Native prefill graph off | MBO | MBO vs native |
|---:|---:|---:|---:|---:|
| 8,192 | 13,194 | 13,262 | 18,226 | +38.1% |
| 16,384 | 12,333 | 12,388 | 15,035 | +21.9% |
| 32,768 | 10,843 | 10,870 | 12,536 | +15.6% |
| 65,536 | 8,713 | 8,730 | 9,275 | +6.5% |
| 114,688 | 6,693 | 6,739 | 6,786 | +1.4% |

The 112k case is close to flat. With a cached 32k prefix, c4 throughput improved about 7.9%/4.0% for 8k/16k new input; c1 means were effectively flat despite lower medians because slow requests remain.
Fixed-output end-to-end: 16 requests, c4, 256 output tokens; cache flushed **after** warmup in every arm.

| Nominal input | Native output token/s | MBO output token/s | Change | Native/MBO median TTFT (ms) | Native/MBO median TPOT (ms) |

Decode control (1024 input / 512 output) was effectively unchanged: c1 125.92 → 125.94 output token/s; c8 711.57 → 711.23. Speed tests use `ignore_eos=True` for fixed generation work; accuracy tests use normal EOS. Actual input totals, output totals, and cache counts were checked across all 15 serving cells.

### Memory and validation limits

- With prefill graphs enabled, a clean `MEM=0.85` MBO probe still OOMed. The 612 MiB PID was the serving launcher, not an external test process.
- `MEM=0.80` completed the full matrix including c4×112k, but reduces token capacity by 9.75% versus the historical 540,672-token `MEM=0.85` setting. MBO still emitted recovered allocation-retry warnings and had latency outliers; production tail stability is not proven.
- Exploratory `MEM=0.85` with prefill graphs disabled retained 540,672 tokens and passed the 24-prompt probe plus one small 32k/112k prefill sweep (c1=2, c4=4 per length). It still logged recovered allocation warnings and has **not** passed the full 218-question/E2E/decode matrix.
- Configurations ran sequentially, with two rounds per prefill size. No randomized run ordering, highest-stable-memory search, or new kernel profile was performed. No MoE, PP, DCP, speculative-decoding or image-input validation is claimed.
