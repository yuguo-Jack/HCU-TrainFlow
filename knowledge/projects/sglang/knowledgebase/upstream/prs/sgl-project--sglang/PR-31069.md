# [Feature] DFLASH EAGLE-style draft-tree verification

## Motivation

Adds **EAGLE-style draft *tree* verification** to DFLASH (spec-v2 worker), on top
of the existing chain verify (#16818 / #22077). The draft head proposes a top-k
tree per step; the target verifies it in one pass and accepts the best
root-to-leaf path — ~+22% accept length (budget 32) and higher low-concurrency
throughput. Opt-in via `--speculative-dflash-tree-verify` (default off = chain,
unchanged).

## Modifications

**New file**

- `kernels/ops/speculative/dflash_tree_expand_topk.py` — fused Triton kernel
  running the full per-step *expand + top-k* recurrence in one launch (power-of-2
  topk in {4, 8, 16}); the per-step loop lives inside the kernel.

**Modified files**

- `speculative/dflash_worker_v2.py` — tree draft-step, tree accept
  (`verify_tree_greedy_func` greedy / `tree_speculative_sampling_target_only`
  non-greedy), scattered-accept KV move-to-front. Top-k sampling + tree build are
  folded into the draft decode CUDA graph (mirrors #29395).
- `speculative/dflash_info.py` — tree fields + mask/positions/retrieve build in
  `prepare_for_verify`.
- `speculative/dflash_utils.py` — `build_tree_verify_tokens` (drives the fused
  kernel) + `compute_dflash_tree_sampling_accept`.
- `kernels/ops/speculative/dflash.py` — `dflash_tree_accept_compact` (tree
  analogue of the chain accept-bonus kernel).
- `model_executor/runner/decode_cuda_graph_runner.py` — mask-capable verify CUDA
  graph for tree.
- `arg_groups/speculative_hook.py` — validate `--speculative-eagle-topk` ∈ {4, 8, 16}.
- `server_args.py` — the `--speculative-dflash-tree-verify` flag.
- `test/registered/spec/dflash/test_dflash.py` — `TestDFlashServerTreeVerify`.

**Notes**

- Greedy **and** non-greedy verify (validated: temp 0.7 / top-p 0.9 / top-k 50 →
  1118 tok/s, accept 7.60 at conc=1, Qwen3-8B).
- CUDA graph for draft (sampling + tree build) and mask-capable verify; overlap
  scheduling supported.
- `--speculative-eagle-topk` limited to {4, 8, 16}; tree gains are low-concurrency.

## Accuracy Tests

Greedy tree accept is **lossless by construction** — `verify_tree_greedy_func`
commits a draft token only when it equals the target argmax.

GSM8K accuracy (chat zero-shot, temp 0, max_tokens 2048), baseline vs chain vs
tree, Qwen3-8B / 1× B200:

| conc | n | baseline | chain | tree (topk4, b32) |
|---|---|---|---|---|
| 1 | 128 | 0.773 | 0.758 | 0.711 |
| 8 | 256 | 0.785 | 0.742 | 0.754 |
| 64 | 256 | 0.766 | 0.750 | 0.793 |

The three track within sampling noise (tree is lowest at conc=1 but highest at
conc=64). `TestDFlashServerTreeVerify` (`max_running_requests=8`, batched verify)
gates gsm8k accuracy + accept length in CI — verified passing.

## Speed Tests and Profiling

`Qwen/Qwen3-8B` (+ `z-lab/Qwen3-8B-DFlash-b16`) and `Gemma-4-31B-it` (+ z-lab
DFlash draft), 1× B200, triton, overlap. Launch:

```bash
SGLANG_ENABLE_OVERLAP_PLAN_STREAM=1 python -m sglang.launch_server \
  --model-path Qwen/Qwen3-8B --trust-remote-code \
  --attention-backend triton --speculative-draft-attention-backend triton \
  --speculative-algorithm DFLASH \
  --speculative-draft-model-path z-lab/Qwen3-8B-DFlash-b16 \
  --speculative-dflash-tree-verify \
  --speculative-eagle-topk 4 \
  --speculative-dflash-block-size 16 \
  --speculative-num-draft-tokens 32 \
  --enable-torch-compile --torch-compile-max-bs 128
```

Chain baseline = drop `--speculative-dflash-tree-verify` /
`--speculative-num-draft-tokens`, set `--speculative-eagle-topk 1`. torch.compile
is used for Qwen3-8B only — on the 31B model its Triton GEMMs are slower than cuBLAS.

### Cross-dataset, conc 1 (tok/s, accept in parens)

`enable_thinking=False`, 512 samples.

**Qwen3-8B:**

| method | budget | gsm8k | math-500 | mt-bench |
|---|---|---|---|---|
| chain | 16 | 1061 (6.42) | 1168 (7.90) | 546 (4.04) |
| **ours** | 32 | **1228 (7.86)** | **1265 (9.29)** | **670 (5.06)** |
| ours | 128 | 1165 (8.72) | 1221 (10.19) | 671 (5.76) |

**Gemma-4-31B-it:**

| method | budget | gsm8k | math-500 | mt-bench |
|---|---|---|---|---|
| chain | 16 | 385 (7.09) | 410 (7.75) | 182 (3.92) |
| **ours** | 32 | **411 (8.13)** | **441 (8.82)** | **208 (4.55)** |
| ours | 64 | 409 (8.56) | 443 (9.28) | 211 (4.85) |
| ours | 128 | 364 (8.92) | 398 (9.66) | 192 (5.15) |

Budget 32 is the sweet spot: b128 raises accept but its verify cost erodes tok/s
— on the 31B model b128 gsm8k (364) even drops below chain (385).

### Concurrency sweep, gsm8k (chain vs tree b32)

Separate config (128 questions, torch.compile on), so conc=1 tok/s differs
slightly from above.

| conc | chain tok/s (acc) | tree tok/s (acc) | speedup |
|---|---|---|---|
| 1 | 1022 (6.33) | **1199 (7.78)** | **1.17×** |
| 8 | 6221 (6.47) | 5664 (7.89) | 0.91× |
| 32 | 12826 (6.44) | 8966 (7.87) | 0.70× |

### Why tree loses at high concurrency

At `b16` tree verifies the **same 16 tokens/step as chain**, isolating tree-build cost:

| conc | chain tok/s (acc) | tree b16 (acc) | speedup |
|---|---|---|---|
| 1 | 1037 (6.33) | 1139 (7.18) | **1.10×** |
| 8 | 6201 (6.47) | 6065 (7.24) | 0.98× |
| 32 | 12911 (6.45) | 11644 (7.23) | 0.90× |

Even at equal budget, tree's per-step overhead (tree build, masked attention,
scattered-accept KV move) outgrows the ~12% step savings — hidden at conc=1,
exposed once compute-bound (b32 loses more). Use tree for latency-sensitive /
low-QPS serving, chain for throughput.
