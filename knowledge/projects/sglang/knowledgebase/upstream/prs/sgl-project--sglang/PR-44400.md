# [Test] lora: Fix stale fakes in five LoRA unit tests

[Upstream PR](https://github.com/sgl-project/sglang/pull/44400) · state: open · merged: False

## Original PR description

## Motivation

Five registered CPU LoRA unit tests fail on `sglang-miles`. In each, the test's hand-built fake no longer matches the code it drives; the product code is correct. Each was reproduced on devbox: the test passes on the parent of the commit that broke it and fails on that commit (or fails from the commit that added it).

| Test | Broken by | Cause |
|---|---|---|
| `unit/lora/test_triton_dp_attention_unit.py` | 1139a6d (Kimi K3 LoRA) | `prepare_lora_batch` now calls `memory_pool.check_valid()`, which reads `invalid_uids`; the `__new__`-built fake pool lacks it |
| `unit/lora/test_lora_moe_inplace_unit.py` | 0584e0e (MoE LoRA support) | `BaseLayerWithLoRA.__init__` aliases `base_layer.named_parameters(recurse=False)`; the fake base layer is a `SimpleNamespace` |
| `unit/managers/test_lora_update_result_merge.py` | 18ce414 (streamed LoRA updates) | the streamed case calls `load_lora_adapter_from_stream`, which does not exist; streamed adapters register through `register_lora_adapter` |
| `unit/lora/test_lora_lease.py` (2 cases) | added by 18ce414 | `unload_lora_adapter` reads `get_lora()` / `get_parallel()` and `_pending_lora_publications`, not the fake's `server_args`; `_unload_lora_adapter_locked` reads `pending_lora_unloads` (since c421d16). The second case was hidden behind the first by `-f` |
| `unit/lora/test_lora_upsert.py` | added by 18ce414 | `validate_new_adapter` reads `enable_dp_attention` (since c421d16), so every load in the fake failed and the duplicate-load assertion was never reached |

On `main`, the three of these tests that exist there pass; `test_lora_lease.py` and `test_lora_upsert.py` exist only on `sglang-miles`.

## Modifications

Each fake gains the field or method the code now reads; the lease test configures LoRA through `get_context().override_server_args(...)`, as `test_lora_update_result_merge.py` already does; the streamed duplicate-load case calls `register_lora_adapter`, whose reuse-on-duplicate and cleanup-on-partial-failure behavior matches what the test asserts.

## Tests

All 21 CPU LoRA unit test files under `test/registered/unit/lora` plus `unit/managers/test_lora_update_result_merge.py` and `unit/model_executor/test_draft_runner_skips_lora.py`, run without `-f`: all pass.
