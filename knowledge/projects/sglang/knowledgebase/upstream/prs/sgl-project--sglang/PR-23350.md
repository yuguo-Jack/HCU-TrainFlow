## Code Review

This pull request introduces TP-invariant operations and infrastructure to support on-policy RL targets such as fsdp_tp. It adds a new tp_invariant_ops module that implements deterministic versions of matrix multiplication, all-reduce, and MoE reduction using fixed binary-tree orders to ensure bitwise identical results for a fixed TP degree. The changes integrate these operations into linear layers and communicators, provide mechanisms to disable incompatible fusions, and include comprehensive unit tests. Review feedback identifies a critical issue where the TP-invariant matmul path incorrectly bypasses quantization logic for quantized models and points out performance inefficiencies in the moe_sum_tree_reduce implementation due to excessive tensor allocations.

The TP-invariant matmul path uses `torch.ops.tp_inv_ops.matmul_tp_inv`, which performs a standard matrix multiplication. This bypasses the `quant_method.apply` logic required for quantized models (e.g., FP8, AWQ, GPTQ). If a quantized model is used with `fsdp_tp` enabled, this will result in incorrect computations because the quantized weights will not be properly dequantized or processed by the appropriate kernels. You should ensure this path is only taken for unquantized layers.

```suggestion
            if should_use_tp_invariant_row_linear(input_parallel.shape[-1]) and self.quant_method.__class__.__name__ == "UnquantizedLinearMethod":
                output_parallel = torch.ops.tp_inv_ops.matmul_tp_inv(
                    input_parallel, self.weight.t(), bias_
                )
```

File: `python/sglang/srt/tp_invariant_ops/tp_invariant_ops.py` · line 196

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

The implementation of `moe_sum_tree_reduce` is inefficient for large batch sizes. It iterates through all experts and top-k slots, creating a new `[tokens, hidden]` tensor via `torch.where` in each iteration. For a model with 64 experts and 8 slots, this results in 512 large tensor allocations per call. At high token counts (e.g., 32k), this could lead to OOM or severe performance bottlenecks. Consider optimizing this with a more vectorized approach while maintaining the deterministic tree reduction order.
