# [Feat] weights: let a custom weight loader reject a tensor update cleanly

[Upstream PR](https://github.com/sgl-project/sglang/pull/48276) · state: open · merged: False

## Original PR description


## Motivation

A `--custom-weight-loader` used with `update_weights_from_tensor` sometimes receives an update it cannot apply: a tensor for a parameter it keeps frozen, or the same tensor twice in one session. Today the loader has no way to refuse. Any exception it raises propagates out of `WeightUpdater.update_weights_from_tensor`, through the scheduler's request dispatcher (which does not catch handler exceptions), and stops the scheduler. The server goes down and every in-flight request is lost.

Measured on upstream main (`8d4e1ce4c7`): a custom loader that raises `ValueError` during `update_weights_from_tensor` logs `Scheduler hit an exception: ... ValueError`, the scheduler sends SIGQUIT and the whole engine process is killed (1x H100).

## Modifications

- `model_loader/utils.py`: new `WeightUpdateRejected(ValueError)`. A custom loader raises it before it writes any weight.
- `WeightUpdater.update_weights_from_tensor`: a custom loader that raises `WeightUpdateRejected` makes the call return `success=False` with `"<load_format> rejected the update: <message>"`. The scheduler does not advance the weight version, skips the cache flush if no runner on any rank applied the update, and keeps serving. The weight-update session stays open. Any other exception from a custom loader propagates as before.
- Scheduler `update_weights_from_tensor`: like `update_weights_from_ipc` and `update_weights_from_disk`, it now flushes the cache when the target runner applied the update even if a draft runner rejected it afterwards, so a partial update is never served from stale cache.
- Scheduler `update_weights_from_tensor`: the outcome is all-reduced over the tensor-parallel CPU group, so a loader that rejects on some ranks only fails the call on every rank, and every rank flushes its cache if any rank applied the update.
- `docs/docs/advanced_features/sglang_for_rl.mdx`: one note under "Update Weights from Tensor", including the limits: a rejection on any rank fails the call everywhere; the weights stay unchanged only if no rank and no earlier runner applied the update, otherwise the applied weights stay and the cache is flushed.
- New CPU unit test `test/registered/unit/model_executor/test_weight_update_custom_loader_reject.py` (`base-a-test-cpu`): a rejecting loader returns `(False, message)` and leaves the weights untouched; another exception still propagates.
- `test/registered/unit/managers/test_scheduler_weight_version_tracking.py`: a draft rejecting after the target, and a rejection on another tensor-parallel rank, both fail the call, record no version and still flush the cache.

## Accuracy Tests

No model-output change on any path. A rejected update leaves the weights as they were (TP1 runs on 1x H100 and 1x GB200; the rank-dependent case on 2x GB200):

Engine `Qwen/Qwen2.5-0.5B-Instruct`, `--enable-deterministic-inference`, 1x H100 80GB, image `lmsysorg/sglang:nightly-dev-20261103-797af717`. Greedy outputs of 3 prompts (16 tokens) before and after one `update_weights_from_tensor` whose custom loader raises:

| loader raises | upstream main 8d4e1ce4c7 | this PR |
|---|---|---|
| `ValueError` | scheduler exception, engine killed (SIGQUIT) | same (unchanged by design) |
| `WeightUpdateRejected` | n/a | `success=False`, `"reject_loader.reject_clean rejected the update: ..."`; engine keeps serving; outputs after == before (3/3 token-identical) |
| `WeightUpdateRejected` on tensor-parallel rank 1 only (TP2, 1x GB200 node) | n/a | both ranks return `success=False` ("The update was rejected on another tensor-parallel rank."); engine keeps serving; outputs after == before (3/3) |

Unit tests: `test_weight_update_custom_loader_reject.py` 2/2 and the existing `test_weight_update_tensor_rank.py` 1/1 pass.

## Speed Tests and Profiling

No speed impact: one `try` around the custom-loader call.
