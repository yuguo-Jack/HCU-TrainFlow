# [Frontend] Parallelize long chat prompt encoding

[Upstream PR](https://github.com/sgl-project/sglang/pull/41259) · state: closed · merged: True

## Original PR description

## Motivation

A rendered chat prompt goes through one `tokenizer.encode(text)` call on one thread. At agentic context lengths this is on the TTFT path: encoding a 200k-token prompt took 240 ms before the request reached the scheduler.

This is separate from #30771, which moves the work off the asyncio event loop. That fixes who waits; this reduces the work itself. The two compose.

## Modifications

`parallel_prompt_encode` cuts a rendered prompt only at boundaries where independently encoded chunk ids concatenate to the original single-call result, then uses the tokenizer backend's `encode_batch` and Rayon pool.

Verified intra-text cuts are enabled only for the exact `Split` regex + `ByteLevel` + BPE pipeline used by GLM and Llama-3-style tokenizers. Added-token boundaries remain available where their matching semantics are independent. Unsupported tokenizer pipelines, post-processors that can rewrite sequence ids (including unsafe `Sequence` children), runtime options, or a serial Rayon process fall back to the original `tokenizer.encode`; tests cover each refusal path. Rayon availability is detected from process CPU rather than caller-thread CPU and cached per PID, so cold-start result conversion cannot disable working parallelism and forked children recheck their own pool.

Two environment gates are defined in `environ.py`:

- `SGLANG_PARALLEL_PROMPT_ENCODE` (default on)
- `SGLANG_PARALLEL_PROMPT_ENCODE_MIN_CHARS` (default 32768)

## Accuracy Tests

External validation produced ids identical to `tokenizer.encode` on 117 real agentic prompts (up to 990k tokens) and 3154 edge/fuzz texts across 8 tokenizer configurations. The final probe was also checked with six real tokenizer checkpoints, explicit serial mode, a post-Rayon fork, and 1/2/4/8-CPU affinity; all ids matched, serial and one-CPU runs fell back, and multi-CPU runs stayed parallel.

The offline CPU unit suite trains a ByteLevel-BPE tokenizer in memory and covers:

- every candidate boundary on 27 edge texts with four special-token placements and 4030 fixed-seed fuzz texts;
- added-token, pre-tokenizer, normalizer, post-processor, padding, truncation, and argument fallback paths;
- threshold, environment, and serial-`encode_batch` gates.

The suite deliberately checks exact ids, not timing. Forcing unsafe cut decisions makes the relevant tests fail.

## Speed Tests and Profiling

Direct encoding of a 200k-token prompt improved from 240 ms to 28 ms.

End-to-end results compare the same GLM-5.3 MXFP4 stack without and with only this change: MI355X, TP8, MTP, EAGLE 5 steps, concurrency 4.

| metric | result |
|---|---|
| per-user interactivity P50 | +12.66%, CI [+8.71, +15.98] |
| per-user interactivity P90 | +24.12% |
| output throughput per GPU | +7.78% |
| TTFT mean | 0.788 s → 0.516 s |
| TTFT p90 | 1.525 s → 0.995 s |

GSM8K and MTP accept length were unchanged within noise.

Local verification:

  test/registered/unit/entrypoints/openai/test_parallel_prompt_encode.py

Result: 19 passed and 13 subtests passed; pre-commit passed. A 160k-character GLM prompt improved from 90.3 ms to 12.0 ms (7.5x) in the final runtime check.

Could we also validate that the post-processor preserves sequence IDs, rather than only counting added special tokens? `add_special_tokens=False` still runs the post-processor. A valid `TemplateProcessing(single="$A $A", special_tokens=[])` reports zero special tokens and passes this gate, but whole-text encoding produces `A B ... A B ...`, whereas chunk encoding produces `A A B B ...`.

I reproduced this with this PR's `_tokenizer` fixture:
```python
tok = _tokenizer(lambda b: setattr(
    b, "post_processor",
    processors.TemplateProcessing(single="$A $A", special_tokens=[]),
))
text = "hello world " + "<think>hello world</think> " * 2000
assert parallel_prompt_encode(tok, text, {"add_special_tokens": False}) == tok.encode(
    text, add_special_tokens=False
)  # fails
```
At the default threshold this is 27 chunks, with 20,006 IDs on both paths but different IDs from position 380. This is a custom post-processor case, not a claim that the tested GLM tokenizer is affected. Please fall back for processors whose ID behavior has not been verified (including `Sequence` children), and add this to the refusal tests so the default-on helper maintains its exact-ID contract.
