# [Fix] retract: Abort input_embeds requests after partial output

[Upstream PR](https://github.com/sgl-project/sglang/pull/39949) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #39645. `reset_for_retract()` discards `output_ids` for `input_embeds` because generated token IDs cannot be appended to the original embeddings. Once any output has reached the tokenizer, however, restarting generation would append generation B to generation A in `ReqState` for both streaming and non-streaming requests. Resetting the cursors alone moves the splice rather than removing it, and can also re-emit prompt placeholder IDs.

## Modifications

- Before `release_req()` resets the request, detect an `input_embeds` request with `send_token_offset > 0`. Release its KV without creating an unused host backup, then return `FINISH_ABORT` with `HTTPStatus.SERVICE_UNAVAILABLE` through `reqs_to_abort` instead of requeueing it. Non-streaming requests raise HTTP 503; streaming requests emit an error chunk with code 503. Neither path silently returns a mixed A/B response.
- Keep the silent restart only when no output has been emitted. The four output cursors restart at zero and `surr_offset`/`read_offset` return to their uninitialized sentinels. The weight-version truncation still runs before those resets so events for already-emitted output are preserved.
- Rework the regression around the real `ScheduleBatch.retract_decode()`, `release_req()`, and `Req.reset_for_retract()` path. Only the KV/cache boundaries are mocked. Both `stream=False` and `stream=True` cover the emitted-output abort and zero-output restart contracts.

## Accuracy Tests

- Against a source snapshot of current `upstream/main` (`de26bb16a972d93f354218a29dbe177bce5655a4`), the final regression reports `4 failed, 2 passed`: both stream modes requeue after emitted output, and both zero-output cases retain the old detokenizer sentinel.
- On the merged head `9837e5ad3beee463757f22aabd9584b935cffc07`, the same test reports `2 passed, 4 subtests passed`.

- sohom-cs · COMMENTED · 2026-10-24T03:10:05Z · [source](https://github.com/sgl-project/sglang/pull/39949#pullrequestreview-5636544505)

Thanks for picking this up: with the cursors reset, B's first token is no longer dropped. I traced what the client assembles, though, and I think the reset moves the splice rather than removing it.

The tokenizer appends every delta it receives (`state.output_ids.extend(...)` and `append_text`), and the detokenizer's `DecodeStatus` for the rid survives the retraction. So the client already holds generation A's first tokens, and with the cursors at 0 it then receives all of B after them.

CPU run of the real `Req.reset_for_retract`, the streamer's accumulator and `DetokenizerManager._decode_batch_token_id_output` (PR merged onto today's main; a stub tokenizer prints ids; A streamed 5 tokens; `max_new_tokens=8`):

```
main     client ids=12  text=<100><101><102><103><104><201><202><203><204><205><206><207>
this PR  client ids=13  text=<100><101><102><103><104><1><1><1><1><1><200><201><202><203><204><205><206><207>
completion_tokens=8 in both
```

On main the client loses B's first token. With the PR it gets A[:5] plus all of B, more than `max_new_tokens`, while `completion_tokens` says 8. The text also gains the last five prompt ids (input_embeds requests carry `[1] * n` placeholders): with `surr_offset`/`read_offset` back at `None`, `init_incremental_detokenize` re-sends them and the detokenizer appends them. The new test checks the scheduler-side slice, not what the client assembles.

Two consistent options:

1. Already streamed (`send_token_offset > 0`): abort through `retract_decode`'s `reqs_to_abort` with a retryable 503, as it already does for a request it cannot resume (#41103). Nothing sent yet: the silent restart is fine.
2. Keep `output_ids` and extend `input_embeds` with the generated tokens' embeddings. More correct, but it needs the embedding table at retraction time.

I can turn the client-side check into a test for this PR.

- he-yufeng · comment · 2026-11-03T02:35:38Z · [source](https://github.com/sgl-project/sglang/pull/39949#issuecomment-6593983364)

Closing this version rather than rebasing a design that is already disproved by the client-side trace. Resetting the cursors does not isolate generation B: the client retains A's streamed tokens and then appends B, including replayed prompt placeholders. That is worse than the original dropped-token behavior and also breaks the `max_new_tokens` contract.

The safe split needs two distinct paths: if output was already streamed, abort through `retract_decode` with a retryable error; only when nothing was emitted can the request restart silently. This PR currently implements neither that distinction nor a client-side assertion for it. Merging current main would preserve the wrong behavior, so I am closing this version. A future rework needs the retryable-abort path and the client-side regression before it is ready for review.
