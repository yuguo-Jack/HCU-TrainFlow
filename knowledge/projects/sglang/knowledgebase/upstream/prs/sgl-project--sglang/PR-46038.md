# [Fix] function_call: Keep JSON null in GLM tool-call string coerce

[Upstream PR](https://github.com/sgl-project/sglang/pull/46038) · state: open · merged: False

## Original PR description

## Motivation

Fixes #46037

GLM tool-call parsers corrupt a bare JSON `null` inside `<arg_value>` when the tool schema is `anyOf: [{type: string}, {type: null}]` (or anything that makes `infer_type_from_json_schema` return `\"string\"`):

- **glm4** (`Glm4MoeDetector`): `str(None)` → string `\"None\"`
- **glm47** (`Glm47MoeDetector`): falls back to raw text → string `\"null\"`

`json.loads(\"null\")` already yields Python `None`; the string coerce step then throws it away. Non-stream and stream/detect paths also disagree with each other.

## Changes

- `glm4_moe_detector.py`: keep `None` instead of `str(parsed_value)` in the string branch
- `glm47_moe_detector.py`: keep `None` instead of raw `arg_value` when `parsed_value is None`
- Regression tests for `anyOf[string, null]` on both detectors

## Test plan

- [x] Unit: `TestGlm4MoeDetector.test_anyof_string_null_preserves_json_null`
- [x] Unit: `test_glm47_schema_types` case `anyOf[{string},{null}] → None`
- [ ] Optional: hit `/v1/chat/completions` with a GLM tool-call that emits `<arg_value>null</arg_value>` and confirm arguments stay JSON null

## Related

- Opposite-direction coercion: #43017
- Same preserve-null principle as #42992
