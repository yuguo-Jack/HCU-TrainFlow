# [Fix] sampling: Reject out-of-vocab stop_token_ids in Python and Rust verify

[Upstream PR](https://github.com/sgl-project/sglang/pull/44560) · state: open · merged: False

## Original PR description

## Motivation

Fixes #44535. A `stop_token_ids` entry outside `[0, vocab_size)` crashes the server as soon as any request in the batch has `min_new_tokens > 0`: `BatchedMinNewTokensPenalizer._prepare` scatters every stop id in the batch into a `[batch, vocab_size + 1]` tensor, and an out-of-range id is a device-side assert that takes down all in-flight requests. `verify()` already bounds `logit_bias` keys the same way, but not `stop_token_ids`.

The Rust server has the same gap. It replaces `TokenizerManager` and runs its own `SamplingParams::verify` (`rust/sglang-server/src/message/sampling.rs`), which mirrors the Python checks, including the `logit_bias` bound, but not this one. Requests it accepts reach the same scheduler and penalizer, so fixing only the Python path would leave Rust-server deployments exposed.

## Modifications

- `python/sglang/srt/sampling/sampling_params.py`: `verify()` rejects `stop_token_ids` outside `[0, vocab_size)` with a `ValueError`, next to the `logit_bias` check. `TokenizerManager` turns it into a 400.
- `rust/sglang-server/src/message/sampling.rs`: the same bound and message in `SamplingParams::verify`, so both frontends behave the same.
- Regression tests on both sides: ids at `vocab_size`, far above it, and negative are rejected; ids at `0` and `vocab_size - 1` are accepted.

`vocab_size` here is `model_config.vocab_size`, the same value the penalizer sizes its tensor with (`schedule_batch.py`), and `normalize()` does not add to `stop_token_ids`, so the check only rejects ids the client sent.
