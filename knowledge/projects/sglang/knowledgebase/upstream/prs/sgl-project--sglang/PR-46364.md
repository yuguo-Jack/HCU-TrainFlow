# [Fix] constrained: Keep grammars that allow no token from crashing the server

[Upstream PR](https://github.com/sgl-project/sglang/pull/46364) · state: open · merged: False

## Original PR description

## Motivation

One constrained-decoding request can take down the whole server. The request only needs a grammar that reaches a state where no token is allowed. Two examples that reach it from the public API:

- An OpenAI `response_format` JSON schema whose `$ref` only points back to itself:
  `{"$defs": {"a": {"$ref": "#/$defs/a"}}, "$ref": "#/$defs/a"}`
- The native `ebnf` constraint `root ::= root`, or `root ::= "a" b` with `b ::= b` (the dead state comes after the first token).

XGrammar compiles these grammars without an error. In the dead state `fill_next_token_bitmask` writes an all-zero row. Applying that row sets every logit to `-inf`, `softmax` turns the row into NaN, and `torch.multinomial` in the torch top-k/top-p sampler hits a device-side assert:

```
TensorCompare.cu:109: _assert_async_cuda_kernel: Assertion `probability tensor contains either `inf`, `nan` or element < 0` failed.
  File ".../srt/layers/sampler.py", line 838, in top_k_top_p_min_p_sampling_from_probs_torch
    sampled_index = torch.multinomial(probs_sort, num_samples=1)
torch.AcceleratorError: CUDA error: device-side assert triggered
SIGQUIT received. ... kill_process_tree called
```

The scheduler exits and every in-flight and later request fails until the server is restarted. With greedy sampling the same request does not crash. `argmax` over an all `-inf` row returns token 0, the grammar rejects it, and the request is aborted with garbage output ("!!").

Related: #27618 reported that `torch.multinomial` can crash the scheduler, and its notes say no request-level trigger was known. This PR gives one and fixes it at the grammar layer.

### Reproduction

Server: `Qwen/Qwen2.5-0.5B-Instruct`, `--attention-backend triton --sampling-backend pytorch`, xgrammar grammar backend (the default).

```bash
curl -s http://127.0.0.1:30000/v1/chat/completions -H 'content-type: application/json' -d '{
  "model": "m", "messages": [{"role": "user", "content": "Hi"}], "max_tokens": 5,
  "response_format": {"type": "json_schema", "json_schema": {"name": "x",
    "schema": {"$defs": {"a": {"$ref": "#/$defs/a"}}, "$ref": "#/$defs/a"}}}}'
curl -s http://127.0.0.1:30000/health   # connection refused, the server is gone
```

The chat request picks up `top_k`/`top_p` from the model generation config, so the torch top-k/top-p path runs. On `/generate` the same happens with `"temperature": 0.7, "top_p": 0.9` and `"ebnf": "root ::= root"`.

### Root cause

- `XGrammarGrammarBackend.dispatch_json` / `dispatch_ebnf` / `dispatch_regex` / `dispatch_structural_tag` (`python/sglang/srt/constrained/xgrammar_backend.py:408`, `:416` and nearby) wrap every grammar that compiles without an error. Nothing checks that the grammar can produce any token.
- `XGrammarGrammar.fill_vocab_mask` (`xgrammar_backend.py:123`) copies XGrammar's bitmask as it is. In a dead state that row is all zeros.
- `apply_vocab_mask` (`xgrammar_backend.py:130` and `:301`) applies the row, which leaves no finite logit. The code assumes the mask always keeps at least one token. The failure surfaces later in `layers/sampler.py:838`.

## Modifications

Both changes are in `xgrammar_backend.py`.

1. Check at compile time. `_from_context_checked` builds the grammar object and asks the new `XGrammarGrammar.allows_no_token()` whether the start state allows any token (stop tokens count). If it allows none, the dispatcher returns an `InvalidGrammarObject`. The request then fails with the usual "Failed to compile ... grammar" 400 and a message pointing at self-referencing rules. This runs once per compiled grammar, and the result is cached like any other compile result.
2. Guard at runtime for dead states reached after some output. `_unmask_rows_that_allow_no_token` replaces all-zero rows with unconstrained rows right before the bitmask is applied. It is one `torch.where` over the `[batch, vocab/32]` int32 mask on the device and needs no host sync. The sampler gets finite probabilities. The grammar then rejects the sampled token in `accept_token`, and the existing handler in `batch_result_processor._accept_grammar_tokens` aborts only that request. Rows that allow at least one token are unchanged. The speculative tree traversal reads the CPU bitmask before this step, so it still sees the original rows.

Other grammar backends (llguidance, outlines) are unchanged. I did not test whether they produce all-zero masks.

Note for reviewers: #35356 also adds `test/registered/unit/constrained/test_xgrammar_backend.py` for a different change (a mask fallback for devices without a fused kernel). Whichever lands second needs a small merge of that file.

## Accuracy Tests

Model forward code is unchanged. Rows that allow at least one token are masked exactly as before (`test_constrained_rows_are_still_masked`). Only grammars that allow no token at all change behavior.

Each run below starts a clean server, sends the attack request, then sends a normal `/generate` request and checks `/health`.

Before the fix (main at 65633129), each run from a clean server start:

| run | case | result |
|---|---|---|
| before1 | chat `response_format` with self `$ref` | connection dropped, server dead, `probability tensor contains either inf, nan` assert |
| before2 | same | same |
| before3 | `/generate` `ebnf: root ::= "a" b / b ::= b`, top_p 0.9 | same |
| before4 | `/generate` `ebnf: root ::= root`, top_p 0.9 | same |

| case | result | server after |

| `ebnf: root ::= root`, greedy | 400, same message | healthy |
| chat tool_choice=required with a self `$ref` tool schema | 200, whitespace until `max_tokens` (unchanged behavior) | healthy |
| `ebnf: root ::= "a" b / b ::= b`, top_p 0.9 | 200, `finish_reason: abort` | healthy |

The one test that passes checks that rows which allow a token are still masked.

`pre-commit run --files` on the two changed files passes (isort, ruff, ruff format, codespell, CI registry checks).

- I verified this on `--sampling-backend pytorch` only. On this machine the flashinfer sampling kernel fails at launch even for a normal request ("too many resources requested for launch"), so I could not check how flashinfer sampling handles a NaN row.
- Environment: RTX 4090 (sm89), driver 560.35 (CUDA 12.6), torch 2.13.0+cu126, sglang-kernel 0.4.6.post1+cu129. main pins newer cu13 wheels, which this driver cannot run.

## Speed Tests and Profiling

The runtime guard is one elementwise compare, one `all` reduction and one `torch.where` over the packed `[batch, vocab/32]` int32 mask, on the device that already holds it, with no host sync. The compile-time check runs once per compiled grammar and fills one CPU bitmask row.
