# [Fix] hicache/hf3fs: Prevent duplicate page reservations

[Upstream PR](https://github.com/sgl-project/sglang/pull/45061) · state: open · merged: False

## Original PR description

## Motivation

Two writers can reserve different pages for the same key before either write is confirmed. The last confirmation replaces the earlier mapping and leaves an orphan page.

This patch tracks pending reservations and skips duplicate writes. It uses the existing `-1` response, so no client changes are needed.

## Modifications

- Track pending key/page pairs under the existing lock.
- Return `(False, -1)` for a key that is already pending or repeated in the same batch.
- Confirm a write only when its key and page match the pending reservation.
- Release pending pages after a failed write, and clear pending state in `clear_all()`.
- Return `-1` when all pages are pending and no page can be allocated.

The HTTP API stays the same. The existing HF3FS client already skips page index `-1`.

## Accuracy Tests

The GPU tests used SGLang `v0.5.15.post1`, Qwen3-1.7B BF16, and two ordinary TP1 engines with the same HF3FS file and metadata service. PD was disabled.

| Test | Result |
| --- | --- |
| Stock: natural, A-first and B-first concurrency | 3 pairs; each left 18 orphan pages |
| Patched: natural, A-first and B-first concurrency | 3 pairs each; all 9 had zero orphan pages |
| Real L3 reads, including serial same/different inputs | 80/80 page hashes matched earlier successful writes |
| Final registered CPU tests, imported in the fixed image | 10/10 passed |
| Production client + real metadata HTTP, with fake I/O returning zero once | Release, same-key retry and readback passed |
| Separate real USR-BIO error probe | Read-only FD caused EACCES and a zero return; restoring RW allowed write/readback |

All 24 concurrent responses returned HTTP 200, with matching output IDs within each pair. In each 256-page pool, stock left 18 orphan pages. The patch left 238 free pages and 18 mapped pages.

The failure/retry client test uses fake I/O. A single test covering real native failure through the production client, metadata release and native retry remains unverified. See the details below.

## Speed Tests and Profiling

No performance benchmark was run. The results above check page ownership and KV readback. They do not make a latency or throughput claim.

## Limits

Pending state is kept in memory. This patch does not add generation tokens. Late confirmations or releases after a page is reused are still not protected. Clear/restart with in-flight writes also remains outside this fix.

Stale-slot reads, `file_size` initialization and crash recovery are separate issues.

<summary>Reproduction steps</summary>

### CPU reproduction
In a SGLang Python environment:
~~~python
from sglang.srt.mem_cache.storage.hf3fs.mini_3fs_metadata_server import RankMetadata

for order in ((0, 1), (1, 0)):
    metadata = RankMetadata(2)
    allocations = [
        metadata.reserve_and_allocate_page_indices([("same-key", "")])[0]
        for _ in range(2)
    ]
    for writer in order:
        _, index = allocations[writer]
        if index >= 0:
            metadata.confirm_write([("same-key", index)], [])
    owned = (
        set(metadata.free_pages)
        | set(metadata.key_to_index.values())
        | set(getattr(metadata, "pending_key_to_index", {}).values())
    )
    orphan = set(range(metadata.num_pages)) - owned
    print(order, allocations, "orphan:", sorted(orphan))
    assert not orphan
~~~
The baseline leaves one orphan in either confirmation order. The patch skips the second reservation.

### GPU reproduction
Runtime: official SGLang v0.5.15.post1, commit 0b3bb0cbe31873994c9f989fddfe2f87ca839fdd; Qwen3-1.7B BF16, ordinary non-PD TP1 x2. PR base: main revision 6fe630ae149916e390a51bb61284177f356d812c, with the metadata patch backported for runtime comparison.

Prerequisites: two GPUs, the same HF3FS mount, hf3fs_fuse.io USR-BIO bindings/native libraries, shared-memory/ring facilities, and compatible model/dtype/TP/page size. Start a fresh metadata service:
~~~bash
python3 -m sglang.srt.mem_cache.storage.hf3fs.mini_3fs_metadata_server --host 0.0.0.0 --port 18000
~~~
Shared HF3FS config (create the parent directory first):
~~~json
{
  "file_path_prefix": "/mnt/hf3fs/experiment/kv",
  "file_size": 234881024,
  "numjobs": 4,
  "entries": 8,
  "metadata_server_url": "http://127.0.0.1:18000"
}
~~~
This file size corresponds to the tested 256-page Qwen3-1.7B pool, not all models.

Launch one engine per GPU, setting GPU=0 PORT=30000 for A and GPU=1 PORT=30001 for B:
~~~bash
CUDA_VISIBLE_DEVICES="$GPU" SGLANG_HICACHE_HF3FS_CONFIG_PATH=/path/to/hf3fs-config.json python3 -m sglang.launch_server \
  --model-path /path/to/Qwen3-1.7B --host 0.0.0.0 --port "$PORT" \
  --tensor-parallel-size 1 --dtype bfloat16 --page-size 16 \
  --enable-hierarchical-cache --hicache-size 8 \
  --hicache-write-policy write_through --hicache-mem-layout page_first \
  --hicache-storage-backend hf3fs \
  --hicache-storage-backend-extra-config '{"prefetch_threshold":64}' \
  --hicache-storage-prefetch-policy wait_complete \
  --max-total-tokens 16384 --random-seed 1234
~~~
The command illustrates equivalent same-host placement. The experiment used two single-GPU Pods and a shared reachable metadata endpoint.

Send the same exact input to both raw engine endpoints concurrently:
~~~python
from concurrent.futures import ThreadPoolExecutor
import requests

payload = {
    "input_ids": [16141, 448, 264, 2805, 42113, 304, 825, 3409, 13] * 15 + [21806],
    "sampling_params": {"temperature": 0, "max_new_tokens": 8},
}
urls = ["http://127.0.0.1:30000", "http://127.0.0.1:30001"]
def send(url):
    response = requests.post(url + "/generate", json=payload, timeout=60)
    response.raise_for_status()
    return response.json()
with ThreadPoolExecutor(max_workers=2) as pool:
    print(list(pool.map(send, urls)))
~~~
Each repeat needs a fresh isolated pool and empty local caches. Natural reproduction depends on timing. The CPU example is deterministic; controlled GPU rounds additionally ordered the first reservation/confirmation through a test proxy.

Record reserve/confirm operations, free/mapped/pending membership and native writes. HTTP success or equal output alone cannot identify lost capacity.

### Failure and retry

The fixture calls the actual `_batch_set()` and `_batch_get()` methods with real metadata HTTP requests. Fake I/O returns zero on the first write, then stores and reads an in-memory buffer.

~~~text
8 free
-> 7 free + 1 pending
-> failed-write release: 8 free
-> same-key retry: 7 free + 1 mapped
-> readback hash matches
~~~

This is a CPU client test with synthetic data. It does not perform native I/O.

The separate USR-BIO probe uses an extra read-only FD. Native prepare returns EACCES and `batch_write()` returns zero. Restoring the original RW FD allows a full write and matching readback.

Three attempts to combine native failure with the production client crashed during native IOR initialization (exit 139), before metadata initialization or reservation. The cause is unknown. Full native failure/release/retry remains unverified.

A release carries only a page index. A late release after page reuse can affect a new pending owner, including a different key. Generation tokens would be needed to distinguish these cases.
