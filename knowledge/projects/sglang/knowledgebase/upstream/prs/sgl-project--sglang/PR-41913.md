# GLM-5.2 NVFP4 DSA via pinned FlashMLA fork (no source patch)

[Upstream PR](https://github.com/sgl-project/sglang/pull/41913) · state: open · merged: False

## Original PR description

## Motivation

Replace the build-time FlashMLA source patch in #35237 with an immutable fork pin. This is a **separate experimental PR** based on current `main`; it does not modify #35237. The GLM-5.2 416-byte/token/layer format is distinct from SGLang's TRTLLM-GEN NVFP4 cache and FlashMLA's V4.1 FP4 cache.

Original GLM-5.2 layout and SGLang implementation: **@Njuapp**, #35237. FlashMLA kernel port: draft sgl-project/FlashMLA#16.

## Modifications

- Pin FlashMLA `f7d49d040c262f18b9973fe8cd5352669def43e8` with a verified archive SHA256 instead of patching downloaded source. The pin is an *integration merge* of the GB300-tested kernel commit `4a7e011c9cc838bacdb735cc2ae7e42565c0c23e` and the currently pinned FlashMLA `sgl` branch. This merge is preserved on a separate fork branch (`ajit283/FlashMLA:feat/glm52-sm100-nvfp4-sglang-draft`) so FlashMLA#16 remains targeted at `rebase` without unrelated `sgl` commits. **Historical GB300/SM103 validation covers integration `7c547b1094`** (details below), not all subsequent review fixes. Pin a promoted `sgl` commit after review.
- Remove the old build-time `flashmla_sm100_nvfp4.patch` and SGLang-only `flashmla_nvfp4_sm100.cu`; compile the fork's SM100 H64 split/no-split specializations instead. SGLang's libtorch registration adapter keeps its own `sgl_kernel` op while forwarding the distinct GLM52 format and persistent FP32 scale to the fork's decode API; existing FP8 calls pass no global scale.
- Port the 416-byte DSA cache writer, per-layer device scale, sizing, host-offload width, sparse BF16 prefill compatibility read, direct packed decode, graph metadata, and fail-fast shape/backend checks onto current main. Leave the FP8 DSA indexer independent. Reject DCP, prefill CP, HiSparse, incompatible Q heads/shapes/platform, and mismatched backends. Keep GenMHA NVFP4 backend resolution separate from DSA.
- Add cache/scale, offload, argument-resolution and kernel tests and document the experimental configuration.

## Reproduction

Recovered original launch/client scripts supersede the earlier approximate recipe in this section. The September 30 GB300 runs used the same local `nvidia/GLM-5.2-NVFP4` weights for both cache formats, mounted at `/model`. The recovered launcher logs do not establish the physical mount or exact checkpoint revision.

```bash
# Run each server separately; FP8 used port 37000, NVFP4 used 35000.
export MODEL_PATH=/path/to/GLM-5.2-NVFP4
export KV_DTYPE=fp8_e4m3  # repeat with nvfp4
export PORT=37000        # use 35000 for NVFP4
python3 -m sglang.launch_server \
  --model-path "$MODEL_PATH" --trust-remote-code \
  --tp-size 4 --dp-size 4 --enable-dp-attention \
  --attention-backend dsa \
  --dsa-prefill-backend flashmla_sparse \
  --dsa-decode-backend flashmla_kv \
  --kv-cache-dtype "$KV_DTYPE" --page-size 64 \
  --max-running-requests 32 --mem-fraction-static 0.80 \
  --chunked-prefill-size 4096 --disable-prefill-cuda-graph \
  --cuda-graph-max-bs-decode 32 --load-format runai_streamer \
  --host 127.0.0.1 --port "$PORT"
```

The historical resolved arguments show `chunked_prefill_size=1024` despite requesting 4096, and auto-resolved `modelopt_fp4`/`flashinfer_trtllm`. Reasoning/tool parsers were not selected. For the actual EAGLE/MTP variant, add `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.

**The reported throughput was generated by a custom `/generate` client, not `bench_serving`.** The preserved request/scoring protocols, exact historical launch details, and both client scripts are in this [public reproduction gist](https://gist.github.com/ajit283/76fa48716ec4962c5600a41305e0b424). Save `serving_probe.py` and `eval_gsm8k.py` from the gist into a local directory, then run:

```bash
python3 serving_probe.py \
  --model-path "$MODEL_PATH" --tag fp8_graph_final \
  --port 37000 --output-dir results
python3 eval_gsm8k.py \
  --port 37000 --tag fp8_graph_final --questions 500 --output-dir results

# Against the separately launched NVFP4 server:
python3 serving_probe.py \
  --model-path "$MODEL_PATH" --tag nvfp4_graph_final \
  --port 35000 --output-dir results
python3 eval_gsm8k.py \
  --port 35000 --tag nvfp4_graph_final --questions 500 --output-dir results
```

The serving client submits concurrent batches 1/4/16/32 (no arrival-rate model), with 2048-token synthetic inputs, max 128 output tokens, temperature 0, and three repetitions: first warmup, median of the remaining two. It retains the preceding historical prefix-reuse smokes and leaves radix caching enabled. The GSM8K client uses the first 20 **training** examples, first 500 test questions, max 512 output tokens, concurrency 32, and the original completion stop strings/scorer. Dataset checksums match the recovered artifacts; the generic few-shot evaluator is not an exact replacement for this protocol.

**K-scale evidence:** the available JET checkpoint at revision `aec724e8c7b8ee9db3b48c01c320f63f9cdaf8aa` has **no serialized calibrated attention K/V scales**. Its index contains 232,385 tensors / 47 shards; all 172,800 scale tensors belong to MLPs, and alternative KV/projection scale names and `amax` tensors are absent. The export summary's 156 K/V BMM quantizers all use `amax=dynamic`. Historical loader rules would give this artifact fallback K/V scales of `1.0`.

Its config matches the recovered historical config byte-for-byte, but that does **not** identify the historical weights: the physical `/model` mount/revision remains unconfirmed. The historical `Initialized DSA NVFP4 global scales for 78/78 local layers` message also counts fallback values and did not record actual runtime scales. Therefore these historical accuracy results are **not evidence of calibrated per-layer K-scale validation**. Details and config hash are in the reproduction README.

Historical measurements used H64 prefill for NVFP4 and H128 prefill for FP8, so they are not an isolated cache-format comparison and do not describe the current routing after the revert. [by Claude Code] **Severity: functional | Confidence: High**

**Issue**

An indexer page is not `page_size` rows of 132 bytes. `SetKAndS`/`GetS` store all K first (`[t*128, t*128+128)`), then all scales (`page_size*128 + t*4`). This 132-byte view copies the wrong bytes when a token moves to another in-page offset, and it does not copy the scale for partial pages.

**Example**

Moving loc 69 (page 1, offset 5) to loc 128 (page 2, offset 0) leaves mixed K bytes and a zero scale (CPU repro). `move_accept_tokens_to_target_kvcache` (NGRAM, tree EAGLE) does such moves. They used to raise an index error; now they corrupt silently. `test_nvfp4_dsa_pool_moves_main_and_index_cache_together` uses the same view, so it passes anyway.

**Fix**

Copy through `index_k[:, :ps*128].view(-1, ps, 128)` and `index_k[:, ps*128:].view(-1, ps, 4)`, indexed by `(loc // ps, loc % ps)`.
