# [MiniMax-M3][AMD] Fix EAGLE3 TARGET_VERIFY on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/35889) · state: closed · merged: False

## Original PR description

## Motivation

EAGLE speculative decoding has a verify step: the target model checks several draft tokens at once. On MiniMax-M3 sparse attention layers, SGLang expects batch metadata to include extend_seq_lens (how long each sequence chunk is).

During verify, that metadata is often None, leading verify on sparse layer to try to read extend_seq_lens.device from a non-existing object and crashing with  `AttributeError: 'NoneType' object has no attribute 'device'`
PR [#32941](https://github.com/sgl-project/sglang/pull/32941) introduced a fix that reconstructs the metadata it it is missing, but it is for NPUs only.

This fix can be extended to AMD GPUs, but with fabricated metadata, sparse layers on GPU will call minimax_sparse_prefill when they need to call decode for the verification. Wrong attention path results in garbage output.

## Modifications

Server crash is fixed by metadata reconstruction and is done similarly to PR [#33673](https://github.com/sgl-project/sglang/pull/32941) to avoid PRs conflicting with each other.

The output quality problem on MI350X/MI355X is fixed by routing TARGET_VERIFY sparse layers to minimax_sparse_decode via _forward_gfx950_triton_verify() — one decode row per draft token with correct causal KV lengths.

There are few additional lines of code for enabling HIP graphs.

## Validation on MiniMax-M3-MXFP8 on ROCm 7.2.0

`MiniMaxAI/MiniMax-M3-MXFP8` with `Inferact/MiniMax-M3-EAGLE3` on 4×MI350X (gfx950), ROCm 7.2.0.

"Unpatched" `main`: crash on TARGET_VERIFY when using EAGLE.

With this PR: 
- Server stays up
- Completions succeed
- Output throughput 296.76 tok/s on TP4 with 8000 ISL 1000 OSL 32 concurrency
  - 16 % improvement over non-speculative 254.63 tok/s  
- GSM8k score 93.5%


```
export CUDA_VISIBLE_DEVICES=4,5,6,7
export SGLANG_USE_AITER=1
export SGLANG_AITER_UNIFIED_VERIFY=1
export SGLANG_USE_AITER_UNIFIED_ATTN=1

python3 -m sglang.launch_server \
  --model-path MiniMaxAI/MiniMax-M3-MXFP8 \
  --tp 4 \
  --trust-remote-code \
  --dtype bfloat16 \
  --quantization mxfp8 \
  --page-size 128 \
  --chunked-prefill-size 32768 \
  --mem-fraction-static 0.85 \
  --kv-cache-dtype fp8_e4m3 \
  --attention-backend aiter \
  --speculative-draft-attention-backend aiter \
  --moe-runner-backend triton \
  --reasoning-parser auto \
  --tool-call-parser auto \
  --host 0.0.0.0 \
  --port 30047 \
  --watchdog-timeout 7200 \
  --cuda-graph-max-bs 8 \
  --speculative-algorithm EAGLE3 \
  --speculative-draft-model-path Inferact/MiniMax-M3-EAGLE3 \
  --speculative-draft-model-quantization unquant 
```

## Validation on MiniMax-MXFP4 on ROCm 10 with Triton 3.8.0

Tested on `lmsysorg/sglang-rocm:v0.5.19-rocm10-mi35x-20260909`. Running 
commands as with MXFP8 model above, with small changes to keep accuracy at higher concurrencies (32+):

* additional env variable `GPTOSS_SWIGLU_MXFP4_BF16_BOUND` must be higher than `max_concurrency * (num_draft_tokens+1)` to use bf16 activations in MoE for decode batches.
* AITER upgrade required for accuracy at higher concurrencies (32+). `amd-aiter==0.1.22.dev107+g9cdcea9b6` is new enough.
