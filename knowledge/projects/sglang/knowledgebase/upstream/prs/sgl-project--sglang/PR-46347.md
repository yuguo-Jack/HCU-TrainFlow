# [Fix] tokenizer_manager: Serialize disk weight updates while the engine is paused

[Upstream PR](https://github.com/sgl-project/sglang/pull/46347) · state: open · merged: False

## Original PR description

## Motivation

While the engine is paused, two `/update_weights_from_disk` calls that overlap (for example a client retrying after an HTTP timeout during the weight-sync window) share one reply slot. The second caller gets the first call's result, the first caller never returns, and the next scheduler reply raises `InvalidStateError` in the tokenizer manager's receive loop, which kills the server. Sequential updates are not affected.

Fixes #33698 (closed by the stale bot; it still reproduces on current main).

## Modifications

When paused, `update_weights_from_disk` read `is_pause` under `is_pause_cond`, released it, and then waited for the scheduler with no lock held, so a second call could replace `model_update_result` while the first was still waiting on it. The distributed, tensor, IPC and weight-update-session paths already hold `is_pause_cond` across the paused call; #22304 moved the first three to that pattern, and the disk path, which lives in `tokenizer_manager.py`, was left out. This does the same for the disk path.

The paused branch still skips the writer lock, so requests admitted before the pause, which hold the reader side, cannot block it. A `continue_generation` that arrives mid-update now waits for the update to return, as it already does for the other paths.

#39520 reworks the multi-tokenizer control path more broadly and also removes the shared slot; this is the minimal fix for #33698, and I'm happy to close it if #39520 lands first.

## Accuracy Tests

New case in `test/registered/unit/managers/test_tokenizer_manager_rid_cleanup.py`: two paused disk updates started back to back against a stub scheduler, with a request still holding the reader lock.
