# [Fix] multimodal: keep placeholder token ids at multimodal positions of input_ids

[Upstream PR](https://github.com/sgl-project/sglang/pull/48385) · state: open · merged: False

## Original PR description

## Motivation

The scheduler fills the multimodal positions of `input_ids` with per-item pad values (radix-cache keys above the vocabulary). `embed_mm_inputs` clamps that tensor **in place** to `vocab_size - 1` before the token-embedding lookup, and the tensor is `forward_batch.input_ids`.

Models can read `input_ids` again after the multimodal routine. `Qwen4ExpVLModel.forward` (Qwen3.8-Flash-Next) hands `forward_batch.input_ids` to its per-layer N-gram embedding (PLE). So every image/video token, and every N-gram that spans the end of an image, is hashed as token `vocab_size - 1`, an unrelated vocabulary entry.

The Hugging Face reference hashes the processor's token ids, which hold the placeholder token (`<|image_pad|>` / `<|video_pad|>`) at those positions. In transformers v5.19.0, `Qwen4ExpModel.forward` takes `ple_input_ids = input_ids` before `masked_scatter` replaces the image and video embeddings, and passes `ple_input_ids` to the language model ([modeling_qwen4_exp.py#L2318-L2324](https://github.com/huggingface/transformers/blob/v5.19.0/src/transformers/models/qwen4_exp/modeling_qwen4_exp.py#L2318-L2324), [#L2344](https://github.com/huggingface/transformers/blob/v5.19.0/src/transformers/models/qwen4_exp/modeling_qwen4_exp.py#L2344), [#L2372](https://github.com/huggingface/transformers/blob/v5.19.0/src/transformers/models/qwen4_exp/modeling_qwen4_exp.py#L2372)). The parity check below confirms the mismatch on upstream main and its fix.

The adaptive-dispatch split path (`_embed_mm_inputs_with_split`) embeds a `torch.cat` copy per group, so there `input_ids` kept the raw pad values (above the vocabulary) instead.

## Modifications

- `embed_mm_inputs`: before the clamp, write each modality's placeholder token id (`MultimodalInputs.im_token_id` / `video_token_id` / `audio_token_id`, set by the processor from the HF config) over that modality's mask. Modalities without a placeholder id keep the clamp, as before. `pad_mm_tokens` and the new fill share one modality-to-placeholder-id helper.
- `_embed_mm_inputs_with_split`: copy the rewritten ids of each group back into `input_ids`.
- Unchanged: the token embeddings (multimodal positions are overwritten by the encoder output either way, and the clamp still bounds every id), the host-side token ids used as radix/prefix keys, and text-only batches.
- New CPU unit test `test/registered/unit/managers/test_mm_placeholder_token_ids.py` (`base-a-test-cpu`).

**Behaviour for other models.**
- Every model that uses `embed_mm_inputs` now sees the placeholder token id, not `vocab_size - 1`, at multimodal positions of `forward_batch.input_ids` after the routine. The token embeddings at those positions are replaced by the encoder output either way.
- Gemma3n builds its per-layer inputs from `input_ids` before calling the routine, so it is unaffected.
- Input-token logprobs take their token ids from `extend_input_logprob_token_ids` (the request's own token ids), not from these `input_ids`, so they are unchanged.
- The Qwen3.8-Flash-Next MTP draft has no PLE and takes its multimodal-position inputs from `mm_input_embeds`.
- Not covered: when EVS prunes tokens, `get_embedding_and_mask` returns a new `input_ids` tensor. The fill applies to that copy, and `forward_batch.input_ids` keeps the pad values there, as today.

## Accuracy Tests

### Parity with the Hugging Face processor

`nvidia/Qwen3.8-Flash-Next-NVFP4`, `--chunked-prefill-size 4096 --disable-radix-cache`. A test-only hook around `Qwen4ExpVLModel.forward` records, for each prefill chunk, the `input_ids` the PLE receives. Each request runs alone. The same chat is then built with `AutoProcessor.from_pretrained` of the same checkpoint (transformers 5.19.0: chat template plus `Qwen3VLProcessor`, `enable_thinking=False`), and the two id lists are compared position by position. The image sides are multiples of 32, so neither processor resizes.

| Request | Prompt tokens | Image tokens | Prefill chunks | upstream main vs HF | this PR vs HF |
|---|---|---|---|---|---|
| short text | 21 | 0 | 1 | identical | identical |
| long text | 9,713 | 0 | 3 | identical | identical |
| 1 image, 448x448 | 217 | 196 | 1 | 196 ids differ | identical |
| 1 image, 640x320 | 220 | 200 | 1 | 200 ids differ | identical |
| 2 images, 512x256 + 256x512 | 278 | 256 | 1 | 256 ids differ | identical |
| 2 images, 1792x1792 (a chunk boundary falls inside the second image) | 6,295 | 6,272 | 2 | 6,272 ids differ | identical |

On upstream main, the differing positions are exactly the image positions: the PLE receives 248319 (`vocab_size - 1`) where HF has 248056 (`<|image_pad|>`). With this PR, every position matches. The result is the same on 1x GB300 (TP1, `--enable-deterministic-inference --attention-backend flashinfer`) and on 2x RTX PRO 6000 Blackwell (TP2).

### MMMU

Upstream's `benchmark/mmmu/bench_sglang.py`, `MMMU/MMMU` validation at revision `876ce5cb130f`, against the server above:

```bash
python3 benchmark/mmmu/bench_sglang.py --port <port> --concurrency 32 --max-new-tokens 512 --temperature 0 \
  --dataset-path <MMMU/MMMU validation, revision 876ce5cb130f> \
  --extra-request-body '{"extra_body": {"chat_template_kwargs": {"enable_thinking": false}}}'
```

Main and this PR ran on the same GPU(s), with the same server arguments. The comparison uses the items both runs scored.

| Hardware | Items | upstream main | this PR | Items whose answer changed | Only main correct / only PR correct |
|---|---|---|---|---|---|
| 1x GB300, TP1, deterministic | 870 | 61.1 % (532) | 60.8 % (529) | 300 | 94 / 91 |
| 2x RTX PRO 6000 Blackwell, TP2, not deterministic; 3 main runs, 2 PR runs | 780 | 61.0 / 63.6 / 64.4 % | 62.1 / 62.6 % | 252-270 (main vs main: 158-170) | — |

The fix changes about a third of the answers, but accuracy does not move beyond run-to-run noise. On GB300 (deterministic), the paired difference is 3 of 870 items (McNemar p = 0.88). On RTX PRO 6000, which has no deterministic mode, both PR runs fall inside the range of three main runs.

### Unit test (CPU)

6 tests (7 cases). On upstream main, 4 tests fail (5 cases): the placeholder positions hold `vocab_size - 1`, or raw pad values on the split path. With this PR, all 6 pass.

| Test | upstream main | this PR |
|---|---|---|
| pad values are out of vocab (fixture check) | pass | pass |
| placeholder id written in place, 1 and 2 requests | fail, fail | pass, pass |
| image and video get their own placeholder id | fail | pass |
| chunked prefill boundary inside an image | fail | pass |
| no placeholder id configured: falls back to the clamp | pass | pass |
| adaptive-dispatch split path (mixed precomputed batch) | fail | pass |

Every case also asserts that the embeddings are bitwise equal to the expected embeddings and that the host-side key ids keep their pad values. The existing `test_mm_utils_split.py` passes 16/16.

### Text outputs are unchanged

`nvidia/Qwen3.8-Flash-Next-NVFP4`, TP1 on 1x GB300, `--enable-deterministic-inference --attention-backend flashinfer`, NEXTN MTP (3 steps, 4 draft tokens), greedy, main and this PR on the same GPU:

| Requests | Main vs this PR |
|---|---|
| 4 text prompts (incl. a multi-chunk ~6K-word prompt) | identical |
| 4 image chats (3 single-image, 1 two-image) | all 4 changed: the model now sees the placeholder id at image positions |

Both arms are repeat-identical.

## Speed Tests and Profiling

No speed claim. The change adds one `masked_fill_` per modality on the multimodal prefill path, and nothing on text-only batches.
