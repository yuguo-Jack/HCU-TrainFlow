# [Fix] hisparse: Rebootstrap retracted DSA PD decode requests instead of offloading KV

[Upstream PR](https://github.com/sgl-project/sglang/pull/40732) · state: open · merged: False

## Original PR description

Fixes #40729
Complements #43936 (which fixed #33385 for DeepSeek-V4 pools)

## Motivation

A PD decode server started with `--enable-hisparse` on a DSA-style HiSparse pool
(`HiSparseDSATokenToKVPool`, e.g. DeepSeek-V3.2) crashes with an uncaught
`NotImplementedError` the first time it has to retract a decode request.

`ScheduleBatch.retract_decode` releases the victim with the default
`offload_kv=True`, so `release_req` asks `backup_kv_cache` for a host copy.
On a HiSparse decode server the backup backend always resolves to `cpu_tensor`
(`resolve_decode_retraction_backup` only picks `host_pool` for
`MHATokenToKVPool` / `SWAKVPool`, and HiSparse uses
`HiSparseDSATokenToKVPool` -> `MLATokenToKVPool`), so the path continues into
`Req.offload_kv_cache` -> `allocator.get_cpu_copy`.
`HiSparseTokenToKVPoolAllocator` does not implement it and inherits
`BaseTokenToKVPoolAllocator.get_cpu_copy`, which raises. The exception escapes
the scheduler event loop and kills the decode worker.

Implementing `get_cpu_copy` for the HiSparse pool would remove the exception
but not fix the bug. `release_req` calls `hisparse_coordinator.retract_req(req)`
*before* the backup, and `retract_req` -> `request_finished` frees the
request's HiSparse device buffer indices, frees its allocated locations and
clears its full-token -> HiSparse index mapping. A copy taken afterwards would
read slots that are already back in the allocator, so it could not be restored
from.

A HiSparse retraction is therefore always a true retraction: the prefix KV is
gone and the prefill worker has to recompute it. #43936 already does this for
every DeepSeek-V4 pool, HiSparse included: `backup_kv_cache` takes its recompute
branch when `dsv4_needs_rebootstrap` holds, and `DecodePreallocQueue.add`
rebootstraps the request. The DSA-style HiSparse pool is not a DeepSeek-V4 pool,
so it still falls through to `cpu_tensor` and crashes. This PR covers that
remaining case and leaves the DeepSeek-V4 path untouched.

## Modifications

Two small changes, reusing the machinery that is already in tree (#43936's
`dsv4_needs_rebootstrap` and the PD rebootstrap path).

**`python/sglang/srt/managers/schedule_batch.py`** - `ScheduleBatch.retract_decode`
now computes

```python
offload_kv = self.hisparse_coordinator is None or dsv4_needs_rebootstrap(
    self.token_to_kv_pool_allocator
)
```

and passes it to `self.release_req(idx, len(sorted_indices), offload_kv=offload_kv)`.
`offload_kv` already existed on both `ScheduleBatch.release_req` and the
module-level `release_req`; the two abort branches in the same loop already
pass `offload_kv=False`. Because no backup is attempted, `release_req` returns
`True`, so the request is not aborted (on `main` a failed `cpu_tensor` backup
aborts with 503 "Retracted under decode memory pressure without a KV backup.
Retry later.") and is treated as a normal retraction. DeepSeek-V4 pools,
HiSparse or not, still get `offload_kv=True` and go through `backup_kv_cache`
exactly as on `main`.

**`python/sglang/srt/disaggregation/decode.py`** - `DecodePreallocQueue.add`
extends the existing rebootstrap conversion so it also fires for HiSparse:

```python
if is_retracted and (
    self.scheduler.hisparse_coordinator is not None
    or dsv4_needs_rebootstrap(self.token_to_kv_pool_allocator)
):
```

The body is unchanged: the boundary output token is popped into
`pd_rebootstrap_forced_output_id`, `pd_rebootstrap_in_progress` is set, and the
request goes down the rebootstrap path instead of `retracted_queue` (whose
resume path would look for a host backup that does not exist). The prefill
worker recomputes the prefix KV and the normal bootstrap handshake transfers it
back.

Nothing changes for non-HiSparse PD decode: it still offloads to host and
resumes through `load_kv_cache`.

**Known gap.** Because the DSA HiSparse path skips `backup_kv_cache`, it does not
apply the rules #43936 added to that function's recompute branch: an explicit
`--disaggregation-decode-retraction-backup none` still aborts, a request with
multimodal inputs aborts, and the device is synchronized before the freed slots
can receive recomputed KV. DeepSeek-V4 + HiSparse keeps all three. Folding
HiSparse into `backup_kv_cache`'s recompute check would close the gap; it is
left for a follow-up to keep this fix small.

**Tests** - `test/registered/unit/managers/test_hisparse_retract_rebootstrap.py`
(new, registered CPU test, `suite="base-a-test-cpu"`) covers both halves and
both directions:

- `test_hisparse_decode_retract_skips_host_offload` - with a coordinator
  attached, `retract_decode` never calls `get_cpu_copy`, the request is
  retracted rather than aborted, and `reset_for_retract` ran.
- `test_non_hisparse_decode_retract_still_offloads` - without a coordinator the
  allocator is still asked for a CPU copy (guards against silently disabling
  host offload for plain PD decode).
- `test_hisparse_retracted_request_goes_to_rebootstrap` - `add(req, is_retracted=True)`
  produces a rebootstrap `DecodeRequest`, leaves `retracted_queue` empty, and
  pops the boundary token into `pd_rebootstrap_forced_output_id`.
- `test_dsv4_hisparse_decode_retract_keeps_backup_kv_cache` - with a
  `DeepSeekV4TokenToKVPool` behind the HiSparse allocator, `retract_decode` still
  calls `backup_kv_cache` exactly once (never `get_cpu_copy`). With `cpu_tensor`
  the request is retracted; with `none` it is aborted, as on `main`.
- `test_non_hisparse_retracted_request_goes_to_resume_queue` - the host-resume
  path is untouched.

The test borrows the real `Req.offload_kv_cache` body so a regression surfaces
as the production `NotImplementedError` rather than as a mock assertion. KV
release is stubbed by patching `release_kv_cache`, the same pattern other unit
tests use.

`test/registered/unit/disaggregation/test_admission_abort_not_enqueued.py`
gains `hisparse_coordinator=None` on its scheduler `SimpleNamespace` fixture,
which the new branch in `DecodePreallocQueue.add` now reads.

## Accuracy Tests

Not applicable: no change to kernels, model forward, or sampling. The retracted
request's prefix KV is recomputed by the prefill worker under the current
weights, through the same rebootstrap path the DeepSeek-V4 retraction recompute (#43936)
already uses, so the
output distribution is the one the existing rebootstrap path produces.

## Speed Tests and Profiling

Not applicable to steady-state throughput: the changed code only runs when the
decode KV pool is exhausted, which today is a crash. The retracted request now
costs a prefill recompute instead of a host->device restore; that is the only
option, since the HiSparse KV is freed before any backup could be taken.

GPU validation was done on a v0.5.17-based 2P2D HiSparse PD deployment
(prefill and decode both dp=4) carrying this same change. Because HiSparse
admission is conservative enough that natural KV pressure rarely reaches
`retract_decode`, retraction was forced on the decode workers with
`SGLANG_TEST_RETRACT=1` / `SGLANG_TEST_RETRACT_INTERVAL=50`. Over roughly 1.2k
forced retractions the decode schedulers never crashed and the retracted
requests resumed through the rebootstrap path (with the companion DP-rank pin
fix, submitted as a separate PR, also applied). A further run with the
production HiSparse config and no fault injection completed every request with
zero retractions and inter-token latency within 0.5% of the baseline, i.e. no
regression on the common path. That run used the earlier form of this change,
which skipped the backup for every HiSparse pool; for the DSA pool exercised
there it behaves identically to the narrowed predicate, while DeepSeek-V4 +
HiSparse now stays on #43936's path and was not covered by that run. The port to
current `main` is covered by the CPU unit tests below; it has not been re-run on
a GPU against `main`.
