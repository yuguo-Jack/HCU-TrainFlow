# [Fix] mooncake: Yield while decode waits for KV transfers in python=3.10

[Upstream PR](https://github.com/sgl-project/sglang/pull/45588) · state: closed · merged: False

## Original PR description

## Motivation

This draft proposes a 1 ms wait when a Mooncake decode scheduler has no runnable batch but is still waiting for work such as KV transfers. In an A10 deployment on Linux CPython 3.10.20, the existing zero-duration yield can leave background control/scatter progress stalled for tens of seconds. This reproduces in legacy PD, without role switching.

**Scope question for reviewers:** the tested source [declares Python >=3.11](https://github.com/sgl-project/sglang/blob/6cac4dc3fe9a4bf15009f300132c3c7a1853c210/python/pyproject.toml#L16). Follow-up testing on CPython 3.11.15, with 258 aligned dependency versions, did **not** reproduce the severe stall in the unmodified scheduler. On that environment, 100-request steady-state results show no material benefit from this patch. This is therefore a draft for evaluating whether the additional wait is justified, **not a claim of a reproduced regression on supported Python versions**.

The relevant existing change is [#40003](https://github.com/sgl-project/sglang/pull/40003): it skips singleton transfer-status all-reduces and adds a PD `sleep(0)` after validation exposed the loss of the collective's implicit GIL release. [#38504](https://github.com/sgl-project/sglang/pull/38504) introduced the related HiCache yield. Both commits are already in the baseline. Related [#40394](https://github.com/sgl-project/sglang/pull/40394), open when checked, expands HiCache yield coverage but still uses zero-duration sleeps.

### Mechanism and limits of the diagnosis

In the captured 3.10 baseline stacks, prefill waited in `_do_staging_transfer()` with `ready=False, c_offset=-1`, meaning that its staging allocation response was not yet available. The decode scheduler main thread was `active+gil`, while the background decode thread was in the `handle_staging_req()` response-send path. A diagnostic A/B/A run removed the long delay with a positive wait and reproduced it after reverting that wait. The serving benchmarks below use the actual source change without hooks or profiling.

Staging adds dependencies on decode background progress: `STAGING_REQ` / `STAGING_RSP` for allocation, `CHUNK_READY` handling, scatter submission, and ring-space reclamation/watermark feedback. The non-staging heterogeneous-TP slice path writes directly into the final KV pool, avoiding those per-chunk staging handshakes, while still depending on bootstrap and completion processing.

In [CPython 3.10.20](https://github.com/python/cpython/blob/v3.10.20/Modules/timemodule.c), Unix `sleep(0)` releases the GIL around zero-timeout `select()` and then reacquires it. Since [Python 3.11](https://docs.python.org/3.11/whatsnew/3.11.html#time), Unix sleep uses `clock_nanosleep` / `nanosleep` where available. Same-host microbenchmarks measured `sleep(0)` at 0.422 µs on 3.10 and 51.974 µs on 3.11, with the same 50,000 ns timer slack and 5 ms GIL switch interval. Both measured approximately 1,053 µs for `sleep(0.001)`. These results support a version-sensitive scheduling explanation; they do not establish that a waiting thread receives a guaranteed handoff or that every second of the stall was continuous GIL ownership.

## Modifications

- Add seven production lines in `Scheduler.on_idle()`: use `time.sleep(0.001)` only for the not-fully-idle Mooncake decode branch.
- Preserve prefill, NIXL, non-PD and fully-idle paths. The wait is not added after every decode step or after every empty receive.
- Do not change staging allocation/watermark state, transfer protocols, locks, teardown or role switching.
- Extend the existing `test_scheduler_on_idle_load.py`; no new repository test file.

The interval is a scheduling tradeoff, not a hard OS wakeup bound or a value proven optimal across platforms. The proposal is intentionally left as a draft given the Python 3.11 results.

## Accuracy Tests

Post-fix staging deployments were evaluated through the repository MiniLB and `/v1/chat/completions`, using the repository's `GSM8KEval`, `ChatCompletionSampler` and `run_eval_once`:

- All 1,319 GSM8K test questions; first five **training** rows as demonstrations, so no evaluated answer is in the prefix.
- Qwen/Qwen2.5-0.5B-Instruct, temperature 0, top-p 1, normal EOS, max output 512, concurrency 4.
- Incorrect and length-capped answers remain in the score. Both runs completed with no empty responses or request retry/error messages.

## Speed Tests and Profiling

### Setup

- Baseline: `6cac4dc3fe9a4bf15009f300132c3c7a1853c210`. The current upstream idle implementation was rechecked before publishing and still uses `sleep(0)`.
- NVIDIA A10; prefill TP2 on GPUs 3/4, decode TP1 on GPU 5; PP1; Mooncake RDMA with `erdma_0,erdma_1`.
- PyTorch 2.14.1 (+cu130), Triton 3.8.0, pyzmq 27.1.0, Mooncake transfer engine 0.3.11.post1, FlashInfer 0.7.0.post1, Transformers 5.19.0. These intentionally match the original deployment rather than upgrading dependencies between interpreter comparisons.
- The 3.11 environment matches 258 dependency distribution versions. Two Python <3.11 standard-library backports are omitted. SGLang and MiniLB load from the same source checkout. ABI-specific wheels necessarily differ; this is not a claim of byte-identical native libraries.
- Chunked prefill 256; page size 1; static memory fraction 0.5; context length 8192; max running requests 16; decode CUDA graph max batch 8; Triton attention; radix cache disabled on both workers.
- D staging ring 32 MiB when enabled. The model's 3,072-token KV is approximately 36 MiB, exercising ring wrap.
- Real PD requests through the repository's Python MiniLB, as used by the PD test fixture. No fake prefill, role switching, diagnostic hook or profiler. MiniLB is a debugging gateway, not a production Rust-router capacity benchmark.
- Each case uses a fresh P/D/gateway deployment. Benchmark: actual `python -m sglang.bench_serving`, concurrency 4, request rate `inf`, seed 42, random IDs, exactly 3,072 input and 128 output tokens. `--tokenize-prompt` avoids decode/re-tokenize length drift; every returned input/output length is checked. Synthetic benchmark outputs ignore EOS for equal work; they are not accuracy evidence.
- One warmup request per invocation. Startup/CUDA graph capture and warmup are excluded from the printed metrics.
- Ten-request cases reproduce the prior setup. On 3.11, a predeclared rule adds a separate 100-request run if the ten-request duration is below 30 seconds; all four cases qualified. Samples are not pooled. The 3.10 results were recorded earlier, not randomly interleaved with 3.11.
