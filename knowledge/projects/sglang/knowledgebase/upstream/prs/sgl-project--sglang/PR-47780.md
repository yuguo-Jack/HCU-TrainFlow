# [Perf] [AMD] scheduler: Prefill the partial chunk of a long prompt first

[Upstream PR](https://github.com/sgl-project/sglang/pull/47780) · state: open · merged: False

## Original PR description

## Motivation

With chunked prefill a long prompt runs as whole chunks and then the part that does not fill one. Attention over that
short last chunk has the whole prompt as context but under-fills the GPU. On MI355X, AITER's hd256 FP8 prefill kernel runs
24 x ceil(rows / 512) workgroups for Qwen3.8-27B, one per CU at a time, so its time goes in whole waves of 256 workgroups.
At 114k tokens of context: 512-5120 rows take 3.9-5.4 ms (one wave), 5632-10752 rows ~10 ms (two), 11264-16384 rows
16-17.8 ms (three). A 1748-token last chunk (a 100k-token prompt with 16384-token chunks) is one wave on 96 of 256 CUs
(3.9 ms, vs 1.9 ms at a full chunk's rate per row); a 5364-token one (120k) is a full wave plus 8 workgroups (8.0 ms, vs
5.4 ms for 5120 rows). Run first, the same short chunk attends only to itself and costs almost nothing.

## Modifications

- `SGLANG_CHUNKED_PREFILL_REMAINDER_FIRST=1` (off by default): when a request needs chunking, `PrefillAdder` takes the part
  of it that does not fill a whole chunk first, rounded up to the page size, `truncation_align_size` and the mamba cut grid,
  and the rest as whole chunks (the last one short by at most the rounding). Requests that fit whole, or whose length is a
  multiple of the chunk size, are unchanged. Both admission paths do this: `add_one_req` and the path `ignore_eos` requests
  take without a radix cache (`add_one_req_ignore_eos`).
- The budget a remainder-first chunk leaves can admit requests that fit whole. A second request that needs chunking is not
  admitted into the same batch (`AddReqResult.OTHER`): the scheduler continues one chunked request at a time, and until now
  a chunked request always used the whole chunk budget, so this case could not occur.

## Accuracy Tests

- `test/registered/unit/managers/test_prefill_adder.py`: chunk lengths for 100052 tokens at page size 1 (1748 + 6 x 16384)
  and 64 (1792 + 5 x 16384 + 16340), a whole number of chunks and a prompt that fits one chunk, with the variable on and
  off; a remainder-first chunk shares its batch with a request that fits whole and turns away a second long one; each on
  both admission paths (`ignore_eos` with and without). This branch: 56 passed, 78 subtests (with and without exact chunk
  fill); without the `add_one_req_ignore_eos` change the `ignore_eos` subtests fail. Tests that pin the default chunk
  shapes (e.g. sharded admission) expect the variable unset, as in CI.
- Qwen3.8-27B MXFP4 on MI355X with the variable on: greedy output ids identical to the run without it (4 prompts),
  needle-in-a-haystack 30/30 at 100k-200k tokens, GSM8K-200 0.920 (0.920-0.960 on builds without the change, same
  harness). The server log shows the order: a 100052-token prompt runs as 1748 + 6 x 16384 tokens.

| 140052 | 8980 | 432 | 1444.6 | 1419.3 | -25.3 |

End to end: Qwen3.8-27B MXFP4 (`amd/Qwen3.8-27B-Quark-AWQ-MXFP4`), TP1 on one MI355X, `--chunked-prefill-size 16384

--backend sglang-oai-chat --dataset-name random --random-range-ratio 1.0 --random-output-len 1 --max-concurrency 1

|---|---|---|---|---|---|---|
| 100000 | 2.612 | 2.595 | -17 ms (-0.64%) | -0.55% | 37,938 | 38,149 |

The gain follows the last chunk's size: at 180000 tokens it is 16160 rows, almost a whole chunk, so there is nothing to
recover. At the other lengths the end-to-end saving is 50-85% of the attention-kernel estimate above.
