# [Perf] [NPU] embeddings: Fuse token remapping and vocabulary mask

[Upstream PR](https://github.com/sgl-project/sglang/pull/48050) · state: open · merged: False

## Original PR description

## Motivation

Vocabulary-parallel embeddings remap global token IDs to local shard indices and construct an out-of-shard mask before the embedding lookup.

On the tested Ascend path, `get_masked_input_and_mask` executes 13 elementwise ATen calls, expanding into 16 device compute kernels, including dtype casts. This introduces launch and host submission overhead for small MTP verify inputs: the tested batch of eight requests produces only 32 token IDs per mapping call.

Fuse the remapping and mask computation into one Triton Ascend kernel, preserving the eager implementation’s output contract.

## Modifications

- Add `get_masked_input_and_mask_npu` under `sglang.kernels.ops.embeddings`, with lazy registry metadata declaring NPU capability.
- Route contiguous NPU `int32` and `int64` inputs through the fused implementation. Preserve the existing path for other devices, unsupported dtypes, and noncontiguous inputs.
- Produce local token IDs and the invalid-token mask in one kernel launch. Preserve original-vocabulary offsets, added-vocabulary offsets, padding, and exclusive range boundaries.
- Return `int64` mapped IDs and a boolean mask. This preserves the eager reference’s dtype promotion even for `int32` input.
- Handle empty inputs without launching a kernel and execute on the current NPU stream.
- Add NPU correctness tests and a standalone operator benchmark.

Embedding lookup, quantization, masked fill, AllReduce, and Mamba commit/stream dependencies remain unchanged. The fused path introduces no host scalar readback or additional synchronization.

## Accuracy Tests

Qwen3.5-35B-A3B-w8a8-mtp, two Ascend910B4 devices, TP2, Ascend attention, modelslim quantization, BF16 activations. NEXTN is normalized internally to EAGLE, with three speculative steps, top-k 1, and four draft tokens.

Recorded software: CANN 9.0.0 image, PyTorch 2.10.0+cpu, torch-npu 2.10.0, and Triton Ascend 3.2.0.

### Operator parity

Four test methods ran on each logical NPU: **eight executions passed, with no skips**. Both outputs match the original eager implementation exactly in values, dtype, shape, and device.

Coverage includes:

- Actual TP2 vocabulary shards: `[0, 124160)` and `[124160, 248320)`.
- Original and added vocabulary boundaries, padding, empty shards, and invalid tokens.
- `int32`/`int64`, integer extremes, and offsets exceeding signed int32.
- Scalar, empty, multidimensional, 32-token, and 4097-token inputs.
- Fixed-seed random inputs, noncontiguous/CPU fallback, and a non-default stream.
- Explicit expected local indices for added-vocabulary boundary cases.

## Speed Tests and Profiling

### Operator microbenchmark

Standalone measurements on Ascend910B4, with no model server running. Each configuration uses 20 warmup calls followed by seven groups of 200 calls. Entries are medians of the seven per-call group averages.

| Input dtype | Tokens | CPU submission A → B, μs | Reduction | NPU event interval A → B, μs | Reduction |
|---|---:|---:|---:|---:|---:|
| int32 | 32 | 606.87 → 342.26 | 43.60% | 607.16 → 342.81 | 43.54% |
| int32 | 4096 | 425.75 → 328.61 | 22.82% | 441.51 → 329.31 | 25.41% |
| int32 | 65536 | 543.78 → 332.18 | 38.91% | 545.11 → 332.93 | 38.92% |
| int64 | 32 | 380.29 → 335.36 | 11.82% | 381.48 → 336.16 | 11.88% |
| int64 | 4096 | 409.40 → 332.20 | 18.86% | 410.31 → 332.77 | 18.90% |
| int64 | 65536 | 472.52 → 337.30 | 28.62% | 477.27 → 338.45 | 29.09% |

Time reduction is `(A − B) / A × 100%`, calculated from unrounded values.

The service uses **32-token/int64** mapping inputs. In that case, CPU submission decreases by **44.93 μs per call**, or **11.82%**.

NPU event intervals include gaps caused by host submission and are not pure kernel execution time. CPU and event savings describe overlapping work and must not be added. Measurements were grouped by variant rather than randomly interleaved.

### Service Level2 profile

The 2026-11-02 captures use:

- Batch size **8**, with **eight active MTP decode/verify steps per TP rank**.
- Seven eligible decode warmup steps, followed by `skip_first=1`, `wait=1`, `warmup=1`, and `active=8`.
- CPU + NPU activities, Level2, PipeUtilization, shape recording, and memory profiling.
- Identical capture conditions for A/B, with `prof.step()` after `run_batch`.
- No prefill capture.

Every active step has a contiguous `[32]` int64 mapping input.

| Observation | A | B |
|---|---:|---:|
| Elementwise ATen calls per mapping | 13 | 0 |
| Device compute kernels per mapping | 16 | 1 |
| TP0 mapping kernel time, median μs | 30.744 | 6.221 |
| TP1 mapping kernel time, median μs | 30.760 | 5.920 |
| TP0 mapping CPU scope, median ms | 1.821 | 0.669 |
| TP1 mapping CPU scope, median ms | 1.893 | 0.703 |

Kernel attribution follows the mapping CPU scope through matching `async_npu` flow IDs to device endpoints on the same lane, with a 0.5 μs timestamp tolerance. Unmatched kernels are not assigned by elimination. The two output allocations are excluded from compute-kernel counts.

The CPU scope decreases by approximately **63%**, but includes profiler overhead and must not replace the independent submission benchmark.

Profiling used temporary 1 GiB swap on the 15 GiB host. Raw capture and offline export ran separately from model serving. These resource conditions further limit extrapolation from profile timing.

### Full serving: profiling disabled

The latest control uses **A1 five rounds → B ten rounds → A2 five rounds**, with five warmup rounds per phase. Each formal round submits eight identical pretokenized 19-token prompts and generates 128 tokens per request.

Service seed is fixed at `287365339`; request sampling seed is `20261102`. All formal rounds ran without profiler or swap. No formal samples were excluded or replaced.

| Variant | Formal rounds | Requests | Median output throughput |
|---|---:|---:|---:|
| A, combining A1+A2 | 10 | 80 | 53.9868 token/s |
| B | 10 | 80 | 53.9289 token/s |

B/A median throughput change is **−0.107%**, with a descriptive bootstrap 95% interval of **[−1.049%, +2.258%]** using 10,000 whole-round resamples and seed `20261102`.

All formal requests succeeded, and their texts and token IDs match across variants. Draft acceptance totals also match: **6080/12240** for each variant.

**This experiment does not demonstrate a serving throughput improvement.** It has only ten rounds per variant, uses a nonrandom block order, and does not correct for time drift or correlation between rounds. A1/A2 median throughput differs by approximately +0.82%. TTFT and TPOT were not measured.

An earlier, separate experiment with 30 steady-state rounds per variant observed **−2.43%** median throughput change, with a descriptive 95% interval of **[−3.60%, −0.45%]**. That experiment had output and acceptance-statistic differences and different request batching behavior; its samples are retained separately and are not pooled with the latest control.

The demonstrated benefit is fewer mapping kernels and lower local submission overhead. Serving-level benefit remains unproven.
