# [Fix] bench_serving: report per-run accept length (bench-only, no server change)

[Upstream PR](https://github.com/sgl-project/sglang/pull/46960) · state: open · merged: False

## Original PR description

Hi, I'm Orien from Parasail. Fixes #46959. This also covers the decode-DP case from #34743, which was auto-closed while idle; credit to its author for the per-request approach.

## Motivation

`bench_serving` reports `Accept length` from `/server_info`'s `avg_spec_accept_length`. The server accumulates that value from startup, or from the last `/flush_cache`. So the number also counts warmup requests and every earlier run on the same server. It also leaves out the last partial decode-log interval of the run. With decode DP, it reads only `internal_states[0]`. Back-to-back A/B runs on one server therefore report blended accept lengths. In our case one arm showed 4.54 vs. 4.1 for the other, and the gap came only from what had run before.

## Modifications

`python/sglang/benchmark/serving.py`:

- `RequestFuncOutput.spec_verify_ct` (new). It is read from `meta_info` next to `spec_accept_length` in the native `/generate` and chat-completions paths that already parse it.
- `calculate_run_accept_length(outputs)` (new) computes total tokens / total verify steps over this run's successful requests. That is the same definition as the server's `avg_spec_accept_length`, scoped to the run. For older servers that send `spec_accept_length` but not `spec_verify_ct`, the verify steps are recovered as `output_len / spec_accept_length`.
- `benchmark()` reports that value. It falls back to the `/server_info` value only when no response carries speculative metadata, for example on OpenAI routes without `meta_info`.
- Output compatibility:
  - The `Accept length:` line keeps its format, so log parsers that read it still work.
  - A new `Speculative stats source:` line says whether the value is per-run or the server's lifetime number.
  - The result JSON keeps `accept_length` and adds `accept_length_source` (`per_request` / `server_cumulative` / null) and `server_avg_spec_accept_length` (the old value).

## Tests

`test/registered/unit/bench/test_bench_serving_accept_length.py` (new, CPU, `base-a-test-cpu`, 38 lines) covers `calculate_run_accept_length`:

- requests are weighted by verify steps (4.0x100 and 2.0x10 give 420/110, not the 3.0 mean);
- verify steps are recovered from `output_len / spec_accept_length` for servers without `spec_verify_ct`;
- failed and non-speculative requests are skipped, and the result is `None` when no request has speculative metadata.

Local run on macOS CPU: `pytest test/registered/unit/bench/` gives 19 passed. `pre-commit run` on the changed files passes.

Not run: a GPU end-to-end run with a real speculative server. The server-side fields used here (`spec_accept_length`, `spec_verify_ct` in `meta_info`) are the ones `TokenizerManager` already sets.
