# [Fix] glm47: Strip the function name in detect_and_parse so a trailing newline does not drop the call

[Upstream PR](https://github.com/sgl-project/sglang/pull/45962) · state: open · merged: False

## Original PR description

## Motivation

Fixes #45953.

`Glm47MoeDetector.detect_and_parse` (the non-streaming path) did not strip the captured function name, while the streaming path (`_extract_match_groups`) does. When a GLM-4.7/GLM-5 model writes a newline after the function name, `func_name` kept the trailing `"\n"`, `parse_base_json` rejected the call as an undefined tool, and because the whole tool-call span had already been consumed, the response ended with **no `tool_calls` and empty `content`**.

Impact (from the issue): with `tool_choice: "required"` on GLM-5.3 with `--tool-call-parser glm47`, about 1 in 4 forced calls was silently dropped in the reporter's tests (7/30 and 10/30); streaming the same requests gave 39/40 tool calls. Streaming and non-streaming disagreed on the same output.

## Modifications

One line: strip the captured name in `detect_and_parse`, matching the streaming path's `match.group(1).strip()`:

```python
func_name = func_detail.group(1).strip() if func_detail.group(1) else ""
```

## Accuracy / Regression Tests

`test/registered/unit/function_call/test_glm47_schema_types.py`:

- `check_arguments` now takes the function name (the call text is built from `Glm47MoeDetector.bot_token`/`eot_token` instead of hardcoded tokens) and keeps running every case through both the non-streaming path and streaming at several chunk sizes.
- New `test_function_name_followed_by_newline` runs a name with a trailing newline through both paths — before the fix the non-streaming branch of that case returned no calls; after it, both paths return `{"value": "Paris"}`.

Verified locally before the fix: `detect_and_parse` on the issue's exact input returned `calls == []` and `normal_text == ""` while streaming returned `get_weather {"city": "Paris"}`; after the fix both return the call.
