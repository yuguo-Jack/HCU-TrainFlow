# [Perf] [AMD] kda: Kimi-K3 verify on gfx950: HIP chain-verify kernel, tuned Triton verify and ReplaySSM commit

[Upstream PR](https://github.com/sgl-project/sglang/pull/44982) · state: open · merged: False

## Original PR description

> Kimi-K3 on gfx950, grouped into larger drafts: prefill #44981 (with #44980) · TP8 LL collectives #44985 (with #44986) · decode routing #44987 (with #44978's argmax) · KDA verify #44982 (now includes the HIP chain-verify kernel) · then #44988. Closed as superseded on main: #44979, #44983, #44984, #44989.

## Motivation

With speculative decoding every Kimi-K3 target step is a verify. On gfx950, KDA verify runs the Triton chain (`causal_conv1d_update` + `fused_sigmoid_gating_delta_rule_update` + transposes), about 1.6 ms per step at 4 requests at TP8, and the ReplaySSM commit and the f_b projection add small launches per layer.

## Modifications

All new paths are gated on `is_gfx95_supported()`.

**HIP chain verify (new in this PR):** `kda_verify_gfx950` (`jit/csrc/attention/kda_verify_gfx950.cuh`, `ops/attention/linear/kda_verify_gfx950.py`) runs conv, gating, the delta-rule recurrence and the ReplaySSM ring writes in one kernel for 8-token verify windows (`SGLANG_ENABLE_ROCM_KDA_VERIFY_HIP`, default on).
- With ReplaySSM off, it writes per-step state snapshots into `intermediate_states_buffer` instead of the ring.
- Other window sizes, such as EAGLE's 4 tokens, keep the tuned Triton path below.
- The Triton path's narrow-tile PTX add now has a HIP guard, since the gfx950 verify tuning can select that tile.

**Triton verify and commit (from the original PR):**
- `fused_kda_conv_gating_verify`: step t + 1's inputs load before step t's stores (`PREFETCH_NEXT`). The Kimi-K3 TP8 shape picks its V tile by batch size. The output is bit-identical with and without the prefetch.
- `commit_kda_replayssm_after_verify(max_accept=)`: with at most 4 accepted tokens, the fold loads every ring row before the first update (bit-identical to the dynamic loop).
- `kimi_k3_tiny_gemm`: a K = 128 Triton GEMM for the f_b projection at verify sizes (M <= 64).
- `kda_backend`: the PP-spec validity mask is built only when PP spec reads it.
- Kimi-K3: `_may_fuse_kda_inproj` no longer requires `do_fuse_qkvbfg`; the unquantized-weight check still rejects quantized projections.

**Dropped from the original PR:** the chunk-major prefill scan (`kda_chunk_scan.py`, the chunk-major key layout and `SGLANG_ROCM_KDA_CHUNK_MAJOR_SCAN` / `SGLANG_ROCM_KDA_FUSED_OUTPUT_MAX_TOKENS`). main's HIP KDA prefill (#45710) runs first on gfx950, so it no longer ran; cold 32K prefill measured the same with it (18,000 vs 17,996 tok/s).

## Accuracy Tests

- Kernel tests on MI355X, on this branch merged with current `main`: 84 passed, 1 skipped (11 subtests) across four files.
  - `test_kda_verify_gfx950.py`: ring and snapshot modes against the Triton chain, at B = 1, 3, 8, 24 and Kimi-K3's 12 KDA heads per TP8 rank.
  - `test_fused_kda_conv_recurrent_verify.py`, `test_kda_replayssm_fold_batched.py`, `test_kimi_k3_kda_inproj_fusion.py`.
- GSM8K 200 on `main` 3a01d4cc8c (2026-10-29), Kimi-K3 TP8 + EAGLE3 (`lightseekorg/kimi-k3-eagle3.1-mla`), MI350X: 97.5 with the Triton verify changes.

## Speed Tests and Profiling

- **Triton verify changes,** same setup: C1 verify cycle -1.9%, C4 -3.8%.
- **HIP chain verify,** measured on an 8-token DSpark verify at TP8 on MI350X:
  - with ReplaySSM on, it replaces the Triton chain;
  - the snapshot mode took decode at 3 requests +2.4%, with 4 and 6 flat.

  A Kimi-K3 + public DSpark A/B is still to run.
