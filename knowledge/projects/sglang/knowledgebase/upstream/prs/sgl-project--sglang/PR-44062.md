# [diffusion][AMD] kernels: give mul_rn_f32 a ROCm path and re-enable the MiniMax-H3 VAE fused norms on ROCm

## Motivation

<!-- Describe the purpose and goals of this pull request. -->

#43350 fixed the MI3XX all-NaN decode by gating the MiniMax-H3 VAE fused norms to NVIDIA, and noted: "Re-enabling the fused path on ROCm needs a separate root-cause fix on AMD hardware." This PR fixes that.

`numerics.mul_rn_f32` is `tl.inline_asm_elementwise` with PTX. On ROCm it fails register allocation: 
```
error: couldn't allocate output register for constraint 'f'
```
and the kernel yields NaN. 

Both call sites #43350 gated (`vae_vit._fused_blocks_available`, `attention._try_fused_qk_rmsnorm_rope`) live in `h3_vae_fused_norm.py`, whose only PTX dependency is `mul_rn_f32`, everything else uses portable `tl.rsqrt`. 
So fixing that one helper restores the entire surface #43350 had to disable.

## Modifications

<!-- Detail the changes made in this pull request. -->
- numerics.py: mul_rn_f32 gets a ROCm branch. `v_mul_f32` with a VGPR (=v,v,v) constraint. `v_mul_f32` is RNE like `mul.rn.f32` and equally refuses FMA contraction. The CUDA branch is byte-identical, so NVIDIA behaviour remains unchanged.
- The two current_platform.is_cuda() gates become is_cuda() or is_rocm(). Other platforms keep the unfused fp32-norm path
