# [Bugfix] Propagate VLLM_MARLIN_INPUT_DTYPE into INC/AutoRound quant path

[Upstream PR](https://github.com/vllm-project/vllm/pull/49039) · state: open · merged: False

## Original PR description

Fixes #48904.

AutoRound (INC) checkpoints route through `inc_wna16_linear.py` and `inc_wna16_scheme.py`, which construct Marlin linear/MoE methods but never assign `input_dtype`. The attribute defaults to `None`, so the Marlin kernel never enters the int8-activation branch regardless of the `VLLM_MARLIN_INPUT_DTYPE` env var.

Fix by setting `method.input_dtype = get_marlin_input_dtype()` after construction, matching the pattern already used in `auto_gptq.py:269` and `auto_gptq.py:261` for the GPTQ/AWQ path.

- hebo1221 · comment · 2026-09-10T12:22:54Z · [source](https://github.com/vllm-project/vllm/pull/49039#issuecomment-5618607339)

I tested this on a GB10 while following up on #49546. Applying the diff from `7ad8269836ef24872de675b88fcfcfb1a9b569f8` to my PyPI vLLM 0.29.0 install exposed two reversed assertions in `AutoGPTQMoEMethod`. Both currently require 8-bit weights for 8-bit activations, which rejects this INT4 checkpoint. The changes needed in that install are:

```diff
# create_weights
- assert self.quant_config.quant_type.size_bits == 8
+ assert self.quant_config.quant_type.size_bits == 4

# process_weights_after_loading
- assert not is_a_8bit or self.quant_config.quant_type.size_bits == 8
+ assert not is_a_8bit or self.quant_config.quant_type.size_bits == 4
```

With your propagation change and those two corrections, the model loads and the corrupted output disappears on my four test prompts. I checked that the INC linear kernel configuration and both the MoE preparation and execution paths use `torch.float8_e4m3fn` in that run.

The stock FP8-option run had `AutoGPTQMoEMethod.input_dtype=None` but `MarlinExperts.input_dtype=float8_e4m3fn`. As a separate control, I left the prepared weights alone and changed only the runtime dtype on all 48 MoE backends to match the preparation dtype. That restored coherent output too, without a CUDA change.

Environment: GB10 / SM121, driver 580.126.09, PyTorch 2.13.0+cu130; `Intel/Qwen3.5-122B-A10B-int4-AutoRound` at `3045d02bb737effc4581da91bddbad3be02934e4`. TP=1, eager mode, no speculative decoding or prefix caching, context 2048, concurrency 1, KV cache 2 GiB. Generation used temperature=0, seed=0 and max_tokens=256.

This is a reproduction check, not a quality or speed benchmark. Three outputs reached the token limit; the capital question ended with Paris. The patched outputs are not all token-identical to BF16.

I also ran the six CPU checks below: **6 failed with the original guards, 6 passed with the corrections**. They cover INT4 weight creation with INT8/FP8 activations and rejection of unsupported INT8-weight/8-bit-activation combinations. The successful FP8 CUDA inference was a separate full-model run.

```python
"""Regression checks for the W4A8 vs unsupported W8A8 MoE contract.

These use the same constructor-free setup as upstream's existing
test_auto_gptq_moe_creates_zero_initialized_expert_biases.
The end-to-end GB10 model runs separately cover successful weight processing.
"""
from types import SimpleNamespace

import pytest
import torch

from vllm.model_executor.layers.quantization.auto_gptq import (
    AutoGPTQConfig,
    AutoGPTQMoEMethod,
)


def method_for(bits, activation):
    method = object.__new__(AutoGPTQMoEMethod)
    method.quant_config = AutoGPTQConfig(bits, 128, False, True, False, {}, {})
    method.input_dtype = activation
    method.experts_cls = None
    method.moe = SimpleNamespace(w13_num_shards=2)
    return method


def create(method):
    layer = torch.nn.Module()
    method.create_weights(
        layer, 2, 256, 128, torch.bfloat16,
        intermediate_size_full=128, weight_loader=lambda *args, **kwargs: None,
    )
    return layer


@pytest.mark.parametrize('activation', [torch.int8, torch.float8_e4m3fn])
def test_int4_moe_accepts_eight_bit_activation(activation):
    layer = create(method_for(4, activation))
    assert layer.w13_qweight.shape == (2, 32, 256)
    assert layer.w2_qweight.shape == (2, 16, 256)


@pytest.mark.parametrize('activation', [torch.int8, torch.float8_e4m3fn])
@pytest.mark.parametrize('operation', ['create', 'process'])
def test_int8_moe_rejects_unsupported_eight_bit_activation(activation, operation):
    method = method_for(8, activation)
    with pytest.raises(AssertionError, match='W8A8-INT8 is not supported'):
        if operation == 'create':
            create(method)
        else:
            method.process_weights_after_loading(torch.nn.Module())
```
