# [Benchmark][Spec Decode] Add reference-replay oracle benchmark

[Upstream PR](https://github.com/vllm-project/vllm/pull/62258) · state: open · merged: False

## Original PR description

## Overview

This adds an oracle benchmark for #61024. It uses saved target-model output as draft tokens, so users can compare real draft methods with reference replay on the same prompts.

## Claims

- A baseline run saves the reference output. Separate runs compare baseline, oracle, ngram, and EAGLE3 throughput.
- Each run saves throughput, draft acceptance, and exact output matches to JSON. The oracle uses the existing `custom_class` interface, with no engine changes.
- The oracle also includes the fix from @dilberx's review. If tokens repeat in the reference, it uses the nearest match instead of the last one. This fixes the reported jump past useful draft tokens.

## Validation

**Scope:** the GPU tests below ran on engine base `5fa7b7b`. The benchmark and test files are unchanged. Local pre-commit checks passed at `6c370bbb5`; GPU tests have not been rerun on the current branch.

Five regression tests ran on one H100 SXM 80GB. Four check repeated matches and ties. One uses OPT-125m to check the output tokens and confirm that draft tokens are accepted.

| Benchmark source | Result |
| --- | --- |
| Before the match fix | 4 failed, 1 passed |
| After the match fix | 5 passed |

The performance comparison used Qwen3-8B on the same H100: BF16, TP=1, greedy output, and at most 384 output tokens. Thinking mode and async scheduling were off. Each setup ran three times, for **27 successful runs** in total.

Values below are median output tokens/s. `k` is the draft length; the cap is `max_num_seqs`, not a fixed batch size.

| Concurrency cap | k | Baseline | Old oracle | Fixed oracle |
| --- | --- | --- | --- | --- |
| 1, serial | 12 | 123.70 | 456.91 | 478.97 |
| 8 | 12 | 894.87 | 4325.28 | 4560.13 |
| 32 | 16 | 2795.72 | 9295.55 | 9334.39 |

Median throughput rose by 4.8% at cap 1 and 5.4% at cap 8. At cap 32, the 0.4% difference is within run variation, so there is no clear gain.

Outputs and their lengths differed in some runs. The throughput numbers therefore do not compare identical outputs in every case. Exact output matches do not measure task accuracy, and the benchmark does not explain the differences. Draft lengths were fixed; this was not a search for the best configuration.

The last GitHub CI run stopped at the contributor eligibility check before tests could run. It is separate from the H100 and local results above.

## Details

If output differs from the saved reference, the oracle uses its last three tokens to find a place to resume. When there is more than one match, it selects the match whose end is nearest to the current output length. Ties favor the earlier match. Use `--strict` to disable this rule.

This remains a heuristic. Replay takes CPU time, and draft tokens can be rejected, so the oracle is a measured performance reference rather than a theoretical upper bound.

- dilberx · comment · 2026-10-30T13:50:59Z · [source](https://github.com/vllm-project/vllm/pull/62258#discussion_r4424334292)

If the 3-gram appears more than once in `ref`, this jumps to the last copy, which can be far past where the generation is. Code outputs repeat 3-grams a lot (indentation, `return`). With `ref = [1, 2, A, B, C, 3, 4, 5, A, B, C, 6, 7, 8, A, B, C, 9, 20, 21]` and `gen = [1, 99, A, B, C]`, it resyncs to 17 and drafts `[9, 20, 21]` where the next tokens should be `[3, 4, 5]`. Every later step for that request goes through `_resync` too, so the oracle numbers come out low. Taking the match closest to `len(gen)` fixes it:

```suggestion
        end = int(idx[np.argmin(np.abs(idx + m - len(gen)))]) + m
```
