# [ROCm][MLA][DCP] Advertise Triton MLA non-causal multi-token DCP

[Upstream PR](https://github.com/vllm-project/vllm/pull/54546) · state: closed · merged: False

## Original PR description

## Summary

Declare that Triton MLA can serve a non-causal multi-token decode block while the MLA KV cache is DCP-sharded, scoped to ROCm.

`forward_mqa` already flattens a non-causal block into one decode row per query token. Every row attends the same committed prefix, so a rank-local `seq_len` fully describes the row under DCP. Without this capability, backend selection rejects Triton MLA for this combination and pushes the multi-token block away from its decode path.

## Why this is separate

This is split out of #51705 on reviewer request. #51705 implements causal multi-token target verification in the ROCm AITER backend; this two-line capability is the only part that touches a backend shared with CUDA and XPU.

## Scope and behavior

`AttentionBackend.supports_non_causal_dcp()` is a backend-eligibility gate, and Triton MLA is selectable on CUDA, XPU, and ROCm. The flatten itself is platform independent, but this DCP configuration has only been validated on ROCm, so the capability remains `current_platform.is_rocm()`.

A single module-level constant feeds both read sites: the class capability and the `supports_dcp_with_varlen` builder argument. With DCP disabled, behavior is unchanged. With DCP enabled on ROCm, a non-causal multi-token group retains its decode reorder threshold instead of being forced back to single-token support. Only the affected KV-cache group is promoted to `UNIFORM_BATCH` graph support.

Hi @YukioZzz, thanks for this. We need this PR merged to have  Kimi-K3 + DSpark + DCP working on gfx942 (MI325X): ROCM_AITER_MLA has no non-causal decode kernels there, so TRITON_MLA is the only backend that can serve the DSpark draft, and today that only works at DCP 1.

Would you have time to work on this? It needs a rebase, but the rebase isn't just a plain conflict fix. 

#51065 (merged Sep 18) removed the `_init_reorder_batch_threshold(...)` block in `TritonMLAMetadataBuilder.__init__` that your second hunk edits. On main, the threshold is set once in `MLACommonMetadataBuilder.__init__`, and `_init_reorder_batch_threshold` clamps it to 1 under DCP unless `supports_dcp_with_varlen` is passed. So keeping only the capability flag isn't enough. The draft passes backend selection and `_validate_dspark_dcp_support`, but its builder stays at threshold 1. FULL cudagraph capture of the 7-token draft block would then trip `assert m.max_query_len <= self.reorder_batch_threshold` in `build_for_cudagraph_capture` (from reading the code; we did not run the flag-only variant).

The obvious fix, passing `supports_dcp_with_varlen=True` from TRITON_MLA, is unsafe. It also raises the threshold for causal TRITON_MLA groups under DCP, such as an MTP/Eagle target. Their multi-token verify would then go to `forward_mqa` and hit `assert self.dcp_world_size == 1, "causal multi-token decode is not supported with DCP"`. Today those batches safely run as prefill.
