# [Kernel][LoRA][MoE] Keep the MoE-LoRA shrink/expand intermediate in fp32 and round the output once

[Upstream PR](https://github.com/vllm-project/vllm/pull/64747) · state: open · merged: False

## Original PR description

Stacked on #64746; review only the last commit ("Keep the MoE-LoRA shrink/expand intermediate in fp32 and round the output once"). Diff of that commit: 2 files, +95 / -3.

## Purpose

On the shrink/expand path the rank-sized intermediate (`x @ A^T`) is stored in bf16/fp16, and expand adds its result to the output in the 16-bit dtype. The LoRA delta is therefore rounded twice before it reaches the output, and its error is 1.2-2.2x the error of rounding the exact result once (kernel numbers below).

## Changes

- For batches of up to `FUSED_MOE_LORA_TWO_KERNEL_MAX_TOKENS` (256) tokens, and whenever `SPLIT_K > 1` (already the case since #64746), the shrink output is kept in fp32.
- Expand splits the fp32 value into a hi/lo pair of 16-bit values and runs two dots against the 16-bit B weights, so the intermediate is used at fp32 accuracy with 16-bit tensor-core MMA.
- Expand adds the LoRA delta to the output in fp32 (`FP32_ADD_INPUTS`, previously XPU only), so the output is rounded once.

Batches above 256 tokens on the one-shot kernel are unchanged.

## Accuracy with a real LoRA

Setup:
- `allenai/OLMoE-1B-7B-0125-Instruct` + `jeeejeee/olmoe-instruct-text2sql-spider` (rank 8, alpha 32; attention, router and per-expert MLP), bf16, 1 GPU.
- 24 prompts: the text2sql template from `tests/lora/test_olmoe_tp.py` with its 4 questions plus 20 more on the same schema. Continuations: 64 greedy tokens, generated once with main. Every build then scores the same 24 sequences with `prompt_logprobs` (6147 scored tokens).
- Reference: HF transformers 5.20 in fp32 with the adapter merged into the weights (`W += alpha/r * B @ A`, computed in fp64, for every adapter module including the router). PEFT is not used because the adapter stores per-expert keys while transformers 5 stores OLMoE experts as fused 3D tensors. A reference without the router LoRA is further from every vLLM build (0.079 vs 0.058 mean), so vLLM does apply it. A vLLM `dtype=float32` run fails at engine init and is not used.
- `max_num_batched_tokens` 64 / 256 / 8192 with chunked prefill, so every forward has ≤ 64 tokens, ≤ 256 tokens, or about 6.2k tokens (one-shot kernel in every build).
- "main" is e49ea84e9, "#64653", "#64746" are the parents in this stack. main and this PR were each run twice.

What this shows:
- The bf16 model's error against fp32 (about 0.06 nats mean, about 1 nat max) comes mostly from the rest of the model. Without batch invariance, two runs of the same build already differ by 0.01-0.04 nats mean, and every kernel change moves the end-to-end error by a few percent in either direction. In default mode this PR is 7% / 4% lower than main at ≤ 64 tokens and 3% higher at ≤ 256 tokens (GB200 / H200); at about 6.2k tokens it matches main, as expected since the one-shot kernel is unchanged.
- With batch invariance the runs are deterministic. #64653 and #64746 give logprobs bit-identical to main, and this PR lowers the mean error by 3% (GB200) and 13% (H200) for batches of up to 256 tokens, and is bit-identical to main above 256 tokens.
