# [Rust Frontend] Support --exclude-tools-when-tool-choice-none

[Upstream PR](https://github.com/vllm-project/vllm/pull/62741) · state: closed · merged: True

## Original PR description



## Overview

The Rust frontend now supports `--exclude-tools-when-tool-choice-none`. Before this change, it rejected the flag at startup. Its default handling of tools for `tool_choice="none"` now also matches the Python frontend.

## Claims

- `--exclude-tools-when-tool-choice-none` works with `vllm serve` (including the Python→Rust `--args-json` handoff) and with `vllm-rs render`. When the flag is set and a chat completion request has `tool_choice="none"`, its request-level `tools` are left out of the prompt.
- **Default behavior change (now matches Python):** by default, request tools are rendered into the prompt even when `tool_choice="none"`. Before this change, the HF, DeepSeek (V3/V3.2/V4/V4.1), Harmony and Inkling renderers always dropped them, as if the flag were always on. Kimi K3 already matched Python. `tool_choice="none"` still disables tool-call parsing, and tool calls that a unified parser (Gemma 4, HunYuan, Inkling, Kimi K3, …) still recognizes are now dropped from the response instead of being returned as `tool_calls`, matching Python's parser engine.

All tests pass except three that also fail on `main` or for environment reasons in my setup. None of them involve this change:
- `grammar_replay`: HF cache permission error while downloading DeepSeek-V4.1-Flash.
- `roundtrip_gemma4_hf`: the locally cached tokenizer has no `response_template`. It fails on `main` too.
- `timing::tests::does_not_enable_debug_at_info`: order-dependent in a full workspace run and passes on its own. It is in the untouched `vllm-tracing` crate.

New and updated tests:
- `exclude_tools_only_drops_tools_for_tool_choice_none`: only an explicit `"none"` drops tools. `"auto"` and an unset `tool_choice` keep them.
- `chat_template_exposes_tools_to_templates_for_any_tool_choice`: the HF renderer passes tools to the template for both `auto` and `none`.
- `frontend_config_excludes_tools_when_tool_choice_none_from_args_json`: the flag survives the `--args-json` handoff from Python.
- `processor_excludes_request_tools_for_tool_choice_none_when_configured`: with the flag on, `none` drops only request-level tools and keeps developer-message tools; `auto` keeps both; without the flag, `none` renders both.
- `tool_choice_none_drops_tool_calls_parsed_by_unified_parsers`: a Gemma 4 tool call is returned for `auto` and dropped for `none`.

## Details

- **Where the flag is applied.** Python configures the flag on `OnlineRenderer` at construction and sets `tool_dicts = None` for `tool_choice == "none"`. Here it is likewise configured on `ChatRequestProcessor` at construction (like `tool_strict_level`) and applied right before rendering, so the chat-completions, `/render` and tokenize paths all get the same behavior. Request tools are still converted and validated; only request-level tools are dropped, and message-scoped tools are kept, as in Python. The server stores the setting in `Config`, and `vllm-rs render` in `RenderConfig`.
- **Dropping tool calls under `none`.** Unified parsers are built from the request tools regardless of `tool_choice`. Now that tools are rendered for `none`, a model may emit a call there, so structured assembly limits surfaced tool calls to zero for `none`, reusing the existing `parallel_tool_calls=false` limit (now `max_tool_calls: Option<usize>`).
- **Renderer change.** The renderers decided whether to render tools based on `tool_parsing_enabled()`, which is false for `tool_choice="none"`. Python's native renderers never look at `tool_choice` when deciding whether to render tools, so those gates are removed. Without that removal, the flag would have no effect for every renderer except Kimi K3.
- **Not duplicating existing work.** No open PR covers this flag. The other unsupported flags mentioned alongside it in the tracking note are out of scope here.
- **Follow-up.** The GPT-OSS cases in `test_serving_chat.py` start the server with this flag. Running them under the Rust frontend in CI would need a larger GPU than the current Rust e2e step uses, so this PR doesn't add them.
