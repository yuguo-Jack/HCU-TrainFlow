![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The documentation states that AsyncScheduler resets num_output_placeholders to 0 and sets discard_latest_async_tokens = True whenever a request is preempted. However, the current implementation in vllm/v1/core/sched/async_scheduler.py does not override _preempt_request, and the base Scheduler._preempt_request (lines 949-970 in scheduler.py) does not perform these actions. These fields are currently only updated during a prefix cache reset (lines 1876-1880 in scheduler.py). This discrepancy could lead to the 'spurious duplicate output token' issue the documentation claims to prevent if a request is preempted due to cache pressure. Please either update the implementation to include these actions in the general preemption path or clarify the documentation to reflect the current behavior.

- copilot-pull-request-reviewer[bot] · comment · 2026-04-01T17:03:15Z · [source](https://github.com/vllm-project/vllm/pull/38741#discussion_r3023415456)

`num_computed_tokens` is reset to 0 on preemption, but when the request is re-admitted the scheduler may immediately restore a non-zero computed-token count via prefix caching (and/or externally matched KV tokens via the KVConnector). Describing this as “recompute from scratch” is inaccurate; consider rephrasing to “recompute missing tokens (no CPU swap), potentially skipping cached prefixes.”
```suggestion
2.  `num_computed_tokens` is reset to `0`. When the request is re-admitted, it
    recomputes only the missing tokens (no KV swap to CPU), and the scheduler
    may immediately restore progress via prefix caching or externally matched
    KV tokens.
3.  The request is prepended to the front of the waiting queue with
    `PREEMPTED` status, so it is re-admitted before any new requests.

!!! note
    vLLM V1 does not swap KV cache to CPU memory. Preempted requests
    recompute missing tokens but may skip cached prefixes. Prefix caching
    makes this inexpensive for requests that share a common prompt prefix.
```

The statement that a preempted request is “prepended to the front of the waiting queue … so it is re-admitted before any new requests” only holds for FCFS. Under the Priority policy, `prepend_request` re-inserts into a heap ordered by (priority, arrival_time), so a preempted request can be scheduled after newly arrived higher-priority requests.
```suggestion
3.  The request is re-queued with `PREEMPTED` status:
    - Under **FCFS**, it is prepended to the front of the waiting queue, so it
      is re-admitted before any later-arriving requests.
    - Under **Priority**, it is reinserted into the priority queue ordered by
      `(priority, arrival_time)`, so newly arrived higher-priority requests
      may still be scheduled first.
```
