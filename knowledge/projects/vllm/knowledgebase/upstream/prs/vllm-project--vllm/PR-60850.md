# [Kernel] Parallelize CUTLASS FP4 expert offset scan

[Upstream PR](https://github.com/vllm-project/vllm/pull/60850) · state: open · merged: False

## Original PR description

## Overview

Replace the single-thread expert/block-scale offset calculation in CUTLASS FP4 MoE setup with a block-wide prefix scan for up to 512 experts. This is independent of the BF16 output-reduction fusion in #60846.

## Claims

- Compute token and padded block-scale prefixes together with one 256-thread CUB scan, processing two consecutive experts per thread.
- Preserve the existing integer prefix values, 128-row padding, and final valid-route offset used to append invalid routes. Keep the serial fallback above 512 experts and the non-block-scaled FP8 path.
- In the submitter's isolated SM120 JIT benchmark, reduce complete routing-setup latency from 20.387 to 4.480 us at M=1 (4.55x) and 20.693 to 4.800 us at M=4 (4.31x). Installed-extension and end-to-end model validation remain pending.

## Validation

**Draft: isolated JIT compilation, routing checks, and GPU microbenchmarks passed in the submitter's container on 2026-10-12. The production extension, repository GPU regression suite, end-to-end model behavior/latency, and steady-state CPU overhead have not yet been validated.**

Hardware/software: NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition, SM120, PyTorch `2.13.0+cu130`, CUDA 13.0. Performance cases use 512 experts, topk=10, N=640, K=2560, gated setup, M=1/4.

The standalone JIT harness compiles the MoE setup source into a separate operator namespace and exposes serial/parallel scan selection in the same process. Each timed operation includes scratch zeroing, expert counting/problem sizes, the offset scan, and permutation generation. Measurements are hot-cache CUDA-graph batch averages: 32 operations per graph, 20 replays per trial, seven trials per implementation, randomized implementation order after warmup. CUDA events measure the graph execution outside the profiler. These are operation averages, not request-tail percentiles or model latency.

| M | Serial median (us) | Parallel median (us) | Saved (us/call) | Speedup | Latency reduction |
|---|---:|---:|---:|---:|---:|
| 1 | 20.387 | 4.480 | 15.907 | 4.55x | 78.0% |
| 4 | 20.693 | 4.800 | 15.892 | 4.31x | 76.8% |

Seven-trial min/max ranges (us): M=1 serial 20.3808–20.3920, parallel 4.4784–4.4816; M=4 serial 20.6913–20.6993, parallel 4.7989–4.8032.

**Checks completed in the isolated harness:**

- Both serial and parallel dispatch choices compile/load and run on SM120.
- Exact integer expert prefixes, padded block-scale prefixes, and both GEMM problem-size arrays.
- Routing/permutation semantics: valid destinations are unique and in range, destinations belong to the selected expert, input rows are recovered correctly, and invalid routes use the expected sentinels. Arbitrary atomic order within an expert is not compared.
- 1/511/512/513 experts, empty expert segments, counts of 1/4/127/128/129 routed rows, mixed invalid IDs, and the >512-expert serial fallback.
- M=1/4 topk=10 routing and CUDA-graph replay after changing input routes and restoring them; checks complete before timing results are printed.

This does not establish a pass for the committed pytest suite or full expert GEMM/model outputs. The committed tests additionally cover all-invalid routing; that suite still needs execution against the rebuilt production extension.

<summary>Diagnostic GPU/CPU observations and interpretation</summary>

Separate one-call profiler captures attribute most of the GPU saving to the scan:

| M | Serial scan (us) | Parallel scan (us) |
|---|---:|---:|
| 1 | 17.439 | 1.344 |
| 4 | 17.408 | 1.344 |

Both captures retain four GPU activities and four `cudaLaunchKernel` calls. The count, permutation and scratch-zeroing kernels remain approximately unchanged. These diagnostic durations are not the seven-trial benchmark samples.

The M=4 profiler reports increased Self CPU time, with this breakdown:

| CPU event | Serial (us) | Parallel (us) | Difference (us) |
|---|---:|---:|---:|
| Activity Buffer Request | 42.913 | 188.673 | +145.760 |
| cudaLaunchKernel, four calls total | 25.888 | 92.545 | +66.657 |
| cudaDeviceSynchronize, two calls total | 10.848 | 7.808 | -3.040 |
| Total Self CPU | 79.649 | 289.026 | +209.377 |

About 70% of that increase is attributed to profiler activity-buffer requests. At M=1, the direction reverses: total Self CPU is 297.698 us serial versus 230.850 us parallel. The harness creates a separate profiler session for each single-call diagnostic and explicitly synchronizes; these totals do not measure steady-state application CPU overhead. NVIDIA documents that activity-buffer callbacks run on the application thread and can delay submission ([CUPTI tracing overhead](https://docs.nvidia.com/cupti/main/main.html#execution-overhead)). The remaining launch-time variation cannot be resolved from one capture per path. No CPU performance improvement or regression is claimed from these samples.

A follow-up CPU check should warm up both paths, time repeated submissions with the profiler disabled, and report host enqueue time separately from synchronized elapsed time. Test eager execution and graph replay separately. GPU event time and profiler Self CPU totals should not be added together as a request-latency estimate.

## Details

The existing setup launches `compute_expert_blockscale_offsets<<<1, 1>>>`, serially reading each expert's token count and updating two running totals. The replacement forms `(count, ceil(count / 128) * 128)` pairs and performs an exclusive scan with CUB `BlockScan<int2, 256>`. Masked experts contribute zeros. Each thread stores its two prefixes; thread zero stores the final totals. Expert counting, permutation generation, and GEMM arithmetic are unchanged.

This adds no host synchronization, new dependency, or model/runner interface. CUB is already used by the CUDA kernels. The parallel scan is dispatched for 1–512 experts; its effect on small expert counts and other supported GPUs still needs measurement. More than 512 experts retains the old kernel.

Duplicate-work searches for `blockscale_offsets` and MoE prefix scans found no open PR implementing this change. #60846 handles weighted expert-output reduction; #43190 handles the shared-expert sigmoid gate. Neither changes this setup scan.
