# [Model] Support Decision 3.0 prefix_bidir attention (vllm-sr/d3-turbo)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62584) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Serve [`vllm-sr/d3-turbo`](https://huggingface.co/vllm-sr/d3-turbo) (27B) with `vllm serve vllm-sr/d3-turbo` and no other flags, and ask it typed questions on `/v1/systemone`. Today it stops at start-up with `ValueError: unsupported decision_config.json attention_mode 'prefix_bidir'`: its checkpoint declares an attention mode that `D3ForSequenceClassification` does not take yet. Follow-up to #61565 and #61778, which added Decision 3.0 and its other sizes.

## Claims

- **`prefix_bidir` gets the checkpoint's own mask.** A prompt is a state block (the system turn, the media, `State:` and the state) followed by a question block. Each request's two blocks become the PrefixLM ranges of the full attention layers, the mask vLLM already applies to multimodal prefix-LM models (causal, or both ways within a range): the state reads itself both ways, the question reads the state and itself both ways, and the state never sees a question. The linear-attention layers stay causal.
- **`/v1/systemone` gives the checkpoint runtime's answers** on one AMD Instinct MI325X: 1 of 260 decisions changed (a near-tie: the reference's two best answers are 0.0056 apart), median |dp| 0.0007, max 0.026, over text, JSON, one image, several images, a video and a 24K-token state. At long context (64K to 117K-token states, `--max-model-len 131072`) 0 of 6 changed, max |dp| 0.014.
- **No flags needed.** The checkpoint declares the length it was validated at (`validated_length`, 32,768 tokens per question), and it becomes the default `max-model-len` when none is given; `--max-model-len 131072` serves long contexts. The other Decision 3.0 checkpoints declare none and are unaffected.
- **`D3Strategy` sends each prompt's state block size**, counted with the runtime's own rule: the lead tokens that end by the end of the state text, so a token joining the state's last character to the question block belongs to the question.
- The other Decision 3.0 models are unchanged (their GPU tests pass). The docs list d3-turbo and its long-context limit, the test registry lists it, and a new GPU test runs `prefix_bidir` in CI on a small checkpoint against d3-turbo's own runtime.

## Details

- **The mask**: the Triton, FlexAttention and FlashAttention 4 backends already OR per-request bidirectional ranges into the causal mask for multimodal prefix-LM models. Two ranges per request, `[0, s)` for the state block and `[s, n)` for the question block, give exactly the runtime's `prefix_bidir` mask, so no kernel changes are needed.
- **Where the ranges come from**: `D3Strategy` counts each prompt's state block (images and videos included, since they come first) and sends it as `PoolingParams.extra_kwargs["d3_state_tokens"]`. `D3PrefixBidirModelState`, the model's Model Runner V2 state, turns it into the request's two ranges. The only change outside the model is a `DefaultModelState.get_mm_prefix_ranges` hook that `prepare_attn` calls; its default is the previous inline code.
- **Detection and config**: the arch config convertor already detects Decision 3.0 checkpoints by their `decision_config.json`; for `prefix_bidir` it also sets `is_mm_prefix_lm`, so attention backends that take the ranges are selected. The config hook keeps the text layers causal (decoder attention that reads the ranges) and marks the model non-causal, so chunked prefill and prefix caching stay off as for the other Decision 3.0 models. A declared `validated_length` sets `max_model_len` only when the user gives none.
- **Tradeoffs and limits**
  - State per question: the runtime reads a request's state once and answers every question from it. vLLM reads it again for each question, one engine request per question as for the other Decision 3.0 models, so many questions about a large state (several images, long text) cost more than in the runtime (latency table). The media themselves are processed once per request and the vision encoder output is cached.
  - Long prompts: at 64K tokens one question takes about 28 s in vLLM and the runtime's state pass about 10 s; most of the gap is the attention kernel with ranges, which is slower than the runtime's SDPA at that length on this GPU.
  - Model Runner V2 on CUDA or ROCm GPUs only: Model Runner V1 does not give the ranges to the attention, so loading a `prefix_bidir` checkpoint there raises a clear error. FlexAttention does not take this model's hybrid KV cache layout (784-token blocks), so on ROCm the Triton backend serves it.
  - `/classify` and `/pooling` cannot carry the state block size, so a `prefix_bidir` prompt sent there reads as a single block; `LLM.classify` takes it through `PoolingParams`, as the new test does.
  - Not in this PR: Box and Track questions and images inside questions or options, which `/v1/systemone` does not offer; NVIDIA measurements beyond CI (no NVIDIA GPU was available to me); tensor parallelism; LoRA.
- **CI**: the new test runs in the optional "Multimodal Models (Extended Pooling)" step on d3-edge's weights (already downloaded there) plus six small runtime files from d3-turbo at a pinned revision. d3-turbo's own 52 GB checkpoint is covered by the measurements above, not CI.
- **Not a duplicate**: no open or closed PR or issue covers d3-turbo or `prefix_bidir` (searched for d3-turbo, `prefix_bidir`, Decision 3.0, `D3ForSequenceClassification`). #61251 changes how `/v1/systemone` tokenizes a shared state and also edits `D3Strategy.read()`; whichever lands second rebases, and the state block size here is computed on the same prompt either way.
- **AI assistance** was used for the code, tests, measurements and this description. The PR stays a draft until the submitter has reviewed every line.

## Follow-ups

- **State once**: answer all of a request's questions from one pass over its state, either as one engine request per state or with prefix caching restricted to KV blocks that lie entirely inside the state block (the question block reads itself both ways, so blocks that cross into it cannot be shared).
- **A faster attention path for long `prefix_bidir` prompts on ROCm.**
- **Box and Track questions** and images inside questions and options on `/v1/systemone`.

Hi @Xunzhuo, thanks for `prefix_bidir`. We built prefix caching of the D3 state block on top of it (RFC:
https://github.com/vllm-project/vllm/issues/64267). Two things from this PR's code:

1. **A bool is not a state block size.** The state length was checked with `isinstance(state, int)`, which accepts
   a bool, so `extra_kwargs={"d3_state_tokens": True}` made a one-token state block. Accept only an int, as
   PrefixLMScheduler does for `prefix_lm_len`: https://github.com/zamog/vllm/commit/99fd132590e2baf143c3dcacb478118dcaedffa3
2. **Keep the hybrid model state.** `D3PrefixBidirModelState` derives from `DefaultModelState`, so a `prefix_bidir`
   checkpoint bypasses the `MambaHybridModelState` the runner picks for Qwen3.5 otherwise.
   - Without prefix caching that is harmless.
   - With `--enable-prefix-caching` the model runs in Mamba `align` mode, whose state seeding and pre-copy live only
     in `MambaHybridModelState`.
   - Deriving from it fixes that. Its `prepare_attn` passes the PrefixLM ranges (from #63114): https://github.com/zamog/vllm/commit/8e8f6ce375526fd531813848590e9b5bd3da8276
