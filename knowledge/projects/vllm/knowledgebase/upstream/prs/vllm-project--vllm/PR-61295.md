# [Bugfix] Stop draft-only spec decode queries under PP and clamp the EAGLE sample index

[Upstream PR](https://github.com/vllm-project/vllm/pull/61295) · state: open · merged: False

## Original PR description



## Overview

With pipeline parallelism (PP > 1) and speculative decoding, the scheduler can schedule a request with only its draft tokens, with no bonus-token row in front of them. The code after the scheduler expects `num_draft_tokens + 1` rows per request. When all drafts are rejected, `eagle_prepare_inputs_padded_kernel` then returns `token_indices_to_sample[i] = query_start_loc[i] - 1`. That is -1 for request 0, and a row of the previous request for every later request. The target model's verification (`_calc_spec_decode_metadata`) reads the wrong rows too.

This PR fixes the scheduler so it no longer builds that query. If a request's drafts follow a token that is still in flight, the request waits one step. It is then scheduled with that token and its drafts together. The PR also clamps the kernel's index to the request's first row, as the issue asks.

Fixes vllm-project/vllm issue 60897

Compared with #60898, this fix:

- Removes the draft-only query in the scheduler, where it starts. [60898](https://github.com/vllm-project/vllm/pull/60898) only clamps the kernel. On its tree, a PP=2 scheduler simulation still builds `{'0': 2, '1': 2}` with no bonus row, and target verification still reads `logits_indices [-1, 0, 1, 1, 2, 3]`. The new scheduler test in this PR fails on [60898](https://github.com/vllm-project/vllm/pull/60898)'s tree.
- Gives the drafter the right row, not only an in-range row. With [60898](https://github.com/vllm-project/vllm/pull/60898)'s clamp alone, the index lands on a draft row of the same request, not on the row of the token the drafter must follow. With this fix, the query always has its bonus row, so the kernel's formula picks the right row.

## Claims

- Under PP with spec decode, the scheduler no longer schedules a query of only draft tokens. The drafts wait one step and are then used, so spec decode stays on.
- `eagle_prepare_inputs_padded_kernel` keeps `token_indices_to_sample[i] >= query_start_loc[i]` for any input. When the bonus row is present, the result does not change.
- Outside PP order (plain sync and async scheduling), the scheduler builds the same batches as before.
- Two new tests. Both fail on the base commit and pass with this PR.

## Details

Root cause. With PP > 1, the engine uses a batch queue. `EngineCore._process_engine_step` calls `post_step` after every `step_with_batch_queue` call, even when that call returned right after scheduling a batch. `post_step` calls `take_draft_token_ids`, and `Scheduler.update_draft_token_ids` sets the new drafts on the request before `update_from_output` has run for that batch. So the token those drafts follow (t0) is not in the request yet. Take a request whose last prefill chunk is in flight. It has `num_computed_tokens == num_tokens`. Without drafts it gets `num_new_tokens == 0` and waits. With drafts it gets `num_new_tokens = len(spec_token_ids)`, which is a query of only `[d1, ..., dk]`. The same happens for an in-flight decode whose new drafts are longer than the ones it was scheduled with.

The fix:

1. `Scheduler.schedule` (11 lines): skip a running request that has drafts while `num_computed_tokens >= num_tokens + num_output_placeholders`. This only applies when `num_sampled_tokens_per_step > 0`. It is the same wait that PP already applies to an in-flight request with no drafts. It does nothing for `AsyncScheduler`, where `num_output_placeholders` counts the pending token. It also does nothing for diffusion models, where a query of only canvas tokens is correct.
2. `eagle_prepare_inputs_padded_kernel` (3 lines): `index_to_sample = max(q_last - num_rejected, query_start_loc[i])`. With the scheduler fix, vLLM no longer sends this kernel a query without a bonus row. The clamp keeps the contract the issue states: the index must stay inside the request's own rows.

MRV2: with sync scheduling and PP, MRV2 uses the same scheduler path, so the guard covers it. From reading `vllm/v1/worker/gpu/model_runner.py` (not run), the draft-only query would trip `assert (num_scheduled_tokens_np >= num_logits).all()` there. The kernel clamp is MRV1-only.

Limitations:

- No end-to-end PP=2 run. The engine order comes from reading `vllm/v1/engine/core.py`. The scheduler part is shown with the real `Scheduler` driven in that order, and with the new scheduler test.
- The CPU copy of the kernel in `csrc/cpu/spec_decode_utils.cpp` is not changed. It is compiled code, and we could not build or test it here. It uses the same scheduler, so with the guard it no longer gets the draft-only query from vLLM. To keep the two kernels the same, the matching change there would be `std::max<int32_t>(q_last_tok_idx - num_rejected, query_loc_ptr[req_idx])`.
