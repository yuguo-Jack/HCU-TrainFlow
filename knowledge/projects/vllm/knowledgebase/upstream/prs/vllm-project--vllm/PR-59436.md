# [Bugfix][Attention] Sync vllm-flash-attn pin to include the SM90 SplitKV fix

[Upstream PR](https://github.com/vllm-project/vllm/pull/59436) · state: closed · merged: False

## Original PR description

## Purpose

Fix #59362.

On SM90, the FA4 CuTe-DSL forward kernel ignores `num_splits`: `flash_fwd_sm90.py` builds
`BlockInfo` without passing `num_splits`, so `BlockInfo.get_n_block_min_max()` falls back to
the constructor default `Int32(1)` and every split processes the **full** KV range. The
SplitKV work partitioning is effectively a no-op — decode gets slower, not faster, as
`num_splits` grows past 1.

The fix already landed upstream as vllm-project/flash-attention#198
("Fix SM90 SplitKV block range partitioning", `6d11b3c1`). This PR only moves the CMake
`GIT_TAG` pin forward by one commit to pick it up:

```diff
 cmake/external_projects/vllm_flash_attn.cmake
-          GIT_TAG 9cd61de38763d712bb6ce56e2a02cc2bf718c89f
+          GIT_TAG 6d11b3c1b6ca7dac0b111bb0db63ca16eeb19a46
```

`compare 9cd61de...6d11b3c1` on `vllm-project/flash-attention`: `ahead_by: 1`, `behind_by: 0`,
one file changed (`flash_attn/cute/flash_fwd_sm90.py`), `+1/-0`:

```python
             qhead_per_kvhead_packgqa=self.qhead_per_kvhead if const_expr(self.pack_gqa) else 1,
+            num_splits=num_splits,
         )
```

This affects both default decode (`num_splits=0` → library heuristics) and full-CUDA-graph
decode (`num_splits=32` via `flash_attn_max_num_splits_for_cuda_graph`), so it is not
limited to one execution mode (vllm/v1/attention/backends/flash_attn.py, the
`max_num_splits` computation).

## Test Plan

Environment: 8x H20 (SM90), driver 535.247.01 / CUDA 13.0, `vllm==0.30.0` wheel
(`torch 2.13.0+cu130`, `nvidia-cutlass-dsl 4.7.1`), single GPU
(`CUDA_VISIBLE_DEVICES=4`).

The wheel ships a vendored copy of `flash_fwd_sm90.py` whose imports are rewritten to
`vllm.vllm_flash_attn.cute.*`; it is otherwise **byte-identical in logic** to the file at
pin `9cd61de` (verified by diff: only 2 import hunks, same 2182 lines). Therefore
"wheel file + the one upstream line" is an exact stand-in for rebuilding with the new pin.
Both arms were measured from a cold JIT (the CuTe DSL disk cache is disabled by default —
`FLASH_ATTENTION_CUTE_DSL_CACHE_ENABLED` defaults to `"0"`), so no stale-kernel
contamination is possible.

Three levels of evidence, all scripts attached below:

1. **Kernel repro** (issue geometry: `SEQK=7040, PAGE=32, HD=512, NQ=16, NKV=2, BS=1`,
   CUDA-graph replay timing, sweeping `num_splits` in (0, 1, 4, 16, 64)).
2. **End-to-end decode** — Qwen/Qwen3-1.7B, `attention_backend="FLASH_ATTN"` +
   `attention_config={"flash_attn_version": 4}` (FA4 is not the SM90 default; this overrides
   it explicitly), TP=1, greedy, `ignore_eos`, 64 decode steps at ctx≈5900 and ctx≈600.
3. **Numerical cross-check vs a dense fp32 torch reference** to confirm the fix changes only
   performance, not accuracy.

A/B order was run both ways (shipped→fixed and fixed→shipped) to rule out machine-load drift.

## Test Result

### 1. Kernel level — issue geometry (hd512, SEQK=7040)

| `num_splits` | before (µs) | after (µs) | speedup |
|---:|---:|---:|---:|
| 0 (auto) | 883.1 | **36.2** | **24.4x** |
| 1 | 876.6 | 876.5 | 1.00x |
| 4 | 874.4 | 230.0 | 3.80x |
| 16 | 878.8 | 64.7 | 13.6x |
| 64 | 882.9 | **48.4** | **18.2x** |

Before the fix the timing is flat (±1%) across all `num_splits` and
`max|o(ns=1) - o(ns=64)| == 0.0` — the kernel never reads `num_splits`. `num_splits=1` is
unchanged as expected (one split already covers the whole KV, and the fix is a no-op there).

### 2. Kernel level — Qwen3-1.7B geometry (hd128, SEQK=5900)

| `num_splits` | before (µs) | after (µs) | speedup |
|---:|---:|---:|---:|
| 0 (auto) | 223.0 | **36.4** | **6.13x** |
| 1 | 220.4 | 220.4 | 1.00x |
| 4 | 222.7 | 63.0 | 3.53x |
| 16 | 222.9 | **41.3** | **5.40x** |
| 64 | 223.2 | 65.5 | 3.41x |

### 3. End-to-end (Qwen3-1.7B, FA4, H20)

64-token greedy decode, median of 3, raw wall time:

| ctx | before (s) | after (s) | speedup |
|---:|---|---:|---:|
| 5900 | 0.525 / 0.525 / 0.525 | 0.192 / 0.192 / 0.193 | **2.73x** |
| 600 | 0.183 / 0.184 / 0.184 | 0.148 / 0.149 / 0.149 | 1.23x |

Reverse-order re-run reproduces the same numbers (0.524 / 0.192 at ctx=5900), so this is not
load drift. Within-arm spread is ±0.5%.

### 4. Numerical correctness

Against a dense fp32 reference (`softmax_scale = 1/sqrt(head_dim)`), hd128/SEQK=5900:

- All `num_splits` values match the fp32 reference with the same relative error as before the
  fix (2.951e-3, i.e. ~1 bf16 ulp) — for both arms.
- After the fix, outputs across `num_splits` differ by at most 2.44e-4 (`3.2e-3` relative),
  i.e. the expected bf16 reassociation across different reduction orders — not an accuracy
  change.

This change does not touch model code, weights, or numerics; it only restores the intended
SplitKV partitioning. No eval regression is expected or observed.

> Note for anyone re-running the issue's kernel script: it uses `softmax_scale=1.0` with
> `head_dim=512`, where logits have stddev ≈ 22.6 and softmax is nearly one-hot, so output
> diffs there are not a correctness metric. Use `1/sqrt(head_dim)` when cross-checking
> numerics.
