# [Bugfix][Parser] Preserve trailing text in non-streaming tool responses

[Upstream PR](https://github.com/vllm-project/vllm/pull/55199) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Non-streaming responses from engine-based tool parsers can drop assistant text after a tool call, leaving clients with incomplete `message.content`. #59218 reported this and was closed by its author, and the bug still reproduces on main. Drain the deferred text while preserving tool-call order and arguments.

## Claims

- Retain assistant prose before, between, and after tool calls.
- Preserve tool order, decoded arguments, and existing whitespace behavior.
- Leave streaming parsing unchanged.

## Validation

A real OpenAI server preserves text around tool calls with this change, and the regressions fail without it. GPU results used NVIDIA B200 GPUs with driver 580.95.05 and a precompiled build of main `b8c04dd3b4`, which this branch includes. The comparison tree is this branch with only the production files restored to main.

```sh
.venv/bin/python -m pytest \
  tests/entrypoints/openai/chat_completion/test_completion_with_function_calling.py -q
.venv/bin/python -m pytest tests/tool_parsers tests/parser tests/reasoning -q
```

```text
Without the fix: test_non_streaming_preserves_text_after_tool_call
                 assert None == 'I will check the weather.'
                 test_extract_tool_calls_keeps_text_around_tool_calls
                 assert 'Before.' == 'Before.  Between.  After.'
With the fix:    the commands above pass
```

This real-server run with `qwen3_coder` shows the client-visible result. It ran on the same hardware against main `3a90cc6fd0`, before the latest commits on this branch. Tool names and arguments matched in every case.

| Model output | `message.content` without the fix | `message.content` with the fix |
| --- | --- | --- |
| Text after one tool call | `None` | `'I will check the weather.'` |
| Text before, between, and after two tool calls | `'Before.'` | `'Before.Between.After.'` |
| Text before one tool call | `'Before.'` | `'Before.'` |
| No text | `None` | `None` |

Parser-level comparison of a complete parse and a stream of the same output on this branch:

| Parser | Output | Stream | Complete parse without the fix | Complete parse with the fix |
| --- | --- | --- | --- | --- |
| `minimax_m2` | Text after a tool call | `'After.'` | `None` | `'After.'` |
| `minimax_m2` | Text before and after a tool call | `'Before. After.'` | `'Before.'` | `'Before. After.'` |
| `gemma4` | Text after a tool call | `'Done.'`, in chunks of 1 and 7 characters | `None` | `'Done.'` |

A wider selection also passes on this branch: the parser files in `tests/tool_use`, `tests/entrypoints/tool_parsers`, and the chat, responses, and message-assembly unit tests in `tests/entrypoints/openai`. The only errors are the `[llama]` cases of `test_hermes_tool_parser.py`, which need a gated checkpoint that this host cannot access, and they error the same way on main.

Two existing tests recorded the dropped text, so this PR changes their expectations. `test_step3p5_tool_parser.py` expected `'hello'` in its non-streaming case, while the same file's streaming case expects both `hello` and `hi`. `test_gemma4_response_template_preserves_content_after_tool_call` expected `None` from the registered parser and `'Done.'` from the response template parser, and both now return `'Done.'`.

The real-server file and the three test directories also pass with this branch merged onto main `410ab341a8`, with the same build, because no native code changed between the two commits.

Model quality was not evaluated, because the change only returns text that the model already generated.

**CI coverage:** `(CPU) Tool Parsers` selects the moved adapter regression and the Step3p5 test. `(H200 MIG 35GB) Entrypoints Integration (OpenAI API chat_completion)` and its `(MI355 DPX)` mirror select the real-server regression, but ROCm was not run. No enabled step selects `tests/parser`, because its step in `misc.yaml` is commented out, so the Gemma4 test and `test_inkling.py` ran only in the validation above.

`(H200 MIG 35GB) Rust Frontend Tool Use` and its mirror exclude the new regression. A real Rust frontend build returned `assert None == 'I will check the weather.'` for it. Under an answer constraint the Rust grammar keeps tool calls optional (`tool_grammar_applies`), so the regex does not force text after a call. The rest of the file passes on that Rust frontend build. The regressions of this PR also pass with this branch merged onto main `b2a9480dc7`, with its own precompiled build and `VLLM_WORKER_MULTIPROC_METHOD=spawn` as in CI. Upstream checks are stopped at contributor authorization, so Buildkite has not run this branch.

## Details

Streaming conversion defers text after tool events until the next delta. The complete-parse path returns without that next conversion, so queued prose is lost. Drain that shared buffer through the existing converter before normalizing the response. `InklingParser` had its own override that drained the same buffer, so this change removes that override. Qwen3 adapter and real-server regressions cover the client-visible behavior, and the tool-calling guide describes it.

The tool-calling guide names the limit of this change: parsers such as `deepseek_v4` stop at the tool call by design, and their text after a tool call is still dropped in both modes.

**Rust frontend:** This change touches only the Python frontend. Rust `qwen_coder` already keeps text after a tool call in a complete parse, checked with a temporary `cargo test` on `parse_complete`, so this change makes the Python result match it. Rust `minimax_m2` ignores that text in both modes (`minimax_m2_parse_complete_preserves_prefix_and_ignores_trailing_text`). The Python `minimax_m2` stream already returned it, so the frontends already differed for streaming. With this PR, Python complete parses also return it, so the frontends now also differ for complete parses of `minimax_m2`. This PR keeps Python consistent with its own stream and does not change Rust.

This does not duplicate an open PR. #59234 proposed an overlapping fix, and its author closed it without a merge. #56270 fixed the same class of bug in the DeepSeek-V3 parser and also kept the text. Open #63093 changes only the `dots` parser, which does not use this engine.
