# [Bugfix] Fix startup illegal memory access from unaligned extensible KV cache segments

[Upstream PR](https://github.com/vllm-project/vllm/pull/65554) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The extensible KV cache (#56492) can leave too little physical memory mapped at the start of a layer's KV view during startup. The view spans the full reserved capacity, but allocation initially commits only the null block. If the layer's segment starts near the end of a memory granule, a kernel reading farther into the view can cross into unmapped memory and trigger an illegal memory access.

Call `pad_kv_cache_segments()` for every extensible KV cache in `Worker.initialize_from_config()`, aligning segments in block-compact, layer-outermost layouts. Each layer then starts at a granule boundary, so committing its null block maps the full first granule. This extends the segment padding introduced for RDMA connectors in #65225 to caches without a connector.

<img width="1037" height="633" alt="image" src="https://github.com/user-attachments/assets/45e757d3-f156-48ec-9022-7a618adf07b3" />

## Claims

- Fixes the startup illegal memory access reproduced with DeepSeek-V3.2 (EP + TP2 + DP2 + PP2) on B300.
- Maps the full first granule of every layer when the null block is committed, without changing logical block counts or block strides.
- Leaves host-resident tensors and layouts that are not block-compact unchanged.

- Eager execution; prefix caching disabled.
- `max_model_len=8192`, `max_num_batched_tokens=8192`, `max_num_seqs=64`, `gpu_memory_utilization=0.85`.
- Empty `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` for each startup test to exercise the autotune dummy run.

| Check | main | This PR | Extensible KV cache disabled |
|---|---|---|---|
| Startup | Illegal memory access in 3/3 runs | Pass | Pass |
| GSM8K accuracy, 250 questions | — | 0.884 | 0.880 |
| 32 requests with 4096-token prompts | — | 32/32 succeed | 32/32 succeed |

On main, every stage-0 worker faults at `model.layers.17`, with all sparse indices inside block 0. That layer has only 80,128 bytes mapped from its cache start, the only MLA cache on the stage below 128 KiB. All MLA caches on PP2 stage 1 and in the PP1 run have at least that much mapped memory.

### Kernel reproduction

On one GPU, place a bf16 KV view near a granule boundary and commit only block 0 (73,728 bytes). The minimum mapped size depends on the indices:

| Inputs | Faults when mapped bytes from the view's start are below |
|---|---|
| Indices inside block 0, as in the failing startup | 128 KiB |
| All indices `-1`, `topk_length=0` | Approximately 100 KiB |

Views fully contained in committed memory do not fault in these tests. The following reproduces the all-invalid-indices case:

```python
import torch
from vllm.third_party.flashmla.flash_mla_interface import flash_mla_sparse_fwd
from vllm.utils.extensible_tensor import ExtensibleTensor

BLOCK, D, HQ, TOPK, SQ, G = 64, 576, 64, 2048, 128, 2 << 20
room = 81408  # Mapped bytes from the KV view's start to the granule boundary.
dev = torch.device("cuda")
q = torch.randn(SQ, HQ, D, dtype=torch.bfloat16, device=dev)
indices = torch.full((SQ, 1, TOPK), -1, dtype=torch.int32, device=dev)
topk_length = torch.zeros(SQ, dtype=torch.int32, device=dev)

offset, view_bytes = 4 * G - room, 1024 * BLOCK * D * 2
buf = ExtensibleTensor(
    offset + view_bytes,
    device=dev,
    segment_capacities=[offset, view_bytes],
)
buf.resize_segments_([0, BLOCK * D * 2], zero_new=True)
kv = buf.full_view()[offset:].view(torch.bfloat16).view(-1, 1, D)
flash_mla_sparse_fwd(q, kv, indices, D**-0.5, topk_length=topk_length)
torch.cuda.synchronize()  # Illegal memory access: only 81,408 bytes are mapped.
```

## Details

**Root cause.** `ExtensibleKVCache.allocate()` commits only each segment's null block, and physical memory is mapped in 2 MiB granules. With unaligned segments, the mapped memory from a layer's cache start to the next granule boundary can be much smaller than a granule. The attention kernel still receives a view of the full reserved capacity, including the unmapped region beyond that boundary.

FlashMLA's SM100 sparse prefill kernel reads KV rows beyond those selected by the sparse indices, up to 128 KiB from the start of the view, even when every index is invalid. These reads stay inside the view, so they are harmless with an ordinary allocation; here they can cross into the unmapped granule. The FlashInfer autotune dummy run invokes this kernel before warmup commits more blocks, so the crash appears at startup.

**When it triggers.** The null block occupies 72 KiB here. A segment starting between 72 KiB and 128 KiB before a granule boundary leaves the null block mapped but the kernel's extra reads unmapped. Closer to the boundary, the null block itself crosses into the next granule and maps it. This window covers about 2.7% of the possible start offsets. Segment offsets depend on per-layer capacity, parallelism and available memory, and a GPU holds 30–60 MLA layers, so about one layer per GPU is expected to fall in the window for an arbitrary configuration. An empty autotune cache exposes the crash; subsequent startups load the cached result and skip the failing dummy run.

**Why padding.** Aligning each segment makes the full first granule available to these reads as soon as the null block is committed, without extra physical memory, since commits already map whole granules per segment. It reuses the existing padding path instead of committing a kernel-specific minimum size. The existing view construction and cache extension paths already handle the padded offsets and layer strides.
