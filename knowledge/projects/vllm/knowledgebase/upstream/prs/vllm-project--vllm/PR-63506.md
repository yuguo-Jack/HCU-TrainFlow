# [Fast Start] Key the weight cache on MoE and linear kernel backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/63506) · state: closed · merged: True

## Original PR description

## Purpose

Part of the cache-key audit in the Fast Start roadmap (#56049).

`process_weights_after_loading` converts weights into the selected kernel backend's layout, for example shuffled or repacked. Weights processed for one backend are therefore wrong for another. `WeightCacheKey` did not include the kernel backends, so an `ipc_cache` engine whose `--moe-backend` or `--linear-backend` differed from the daemon's still mapped the daemon's weights.

The NVFP4 MoE pre-processed path has a guard, but it only checks the **engine's** backend. That leaves one case silently wrong:

- the daemon runs with `--moe-backend flashinfer_cutlass`, so the weights are in CUTLASS layout;
- the engine runs with `auto`, which resolves to `FLASHINFER_TRTLLM` on B300;
- the engine maps the CUTLASS-layout weights, `/health` returns 200, and every completion is garbage.

This PR adds `moe_backend`, `linear_backend` and `linear_backend_per_quant` to `WeightCacheKey`. The daemon and the IPC loader both build the key from `vllm_config.kernel_config`. A backend mismatch is now reported as a key mismatch on the backend field before any tensor is mapped. With `fallback=true` (the default) the engine then loads from disk.

The key uses the **configured** backends rather than the resolved ones. This is conservative:
- A daemon on `auto` and an engine on the backend `auto` resolves to counts as a miss and falls back to disk.
- Two `auto` configs that resolve differently, e.g. because of different environment variables, are not caught.

Keying on the resolved backend would close both gaps. It needs the resolution to run before the key is built, so I left it for a follow-up.
