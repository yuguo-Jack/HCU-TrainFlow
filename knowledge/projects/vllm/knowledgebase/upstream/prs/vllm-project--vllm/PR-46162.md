# [Bugfix][Frontend] Use api_error for Anthropic streaming error events

[Upstream PR](https://github.com/vllm-project/vllm/pull/46162) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Since #61947, `message_stream_converter` forwards the original error message and closes the open content block when the chat stream fails, which fixes the masking reported in #46028. The error event it sends still has `"type": "internal_error"`, which is not an Anthropic error type. This PR changes it to `api_error`.

## Claims

- A streaming `/v1/messages` request that fails mid-stream now ends with `{"type": "error", "error": {"type": "api_error", "message": ...}}`. Anthropic's [errors page](https://platform.claude.com/docs/en/api/errors) defines `api_error` as "An unexpected error has occurred internal to Anthropic's systems", and its streaming docs send mid-stream errors in the same shape ([Error events](https://platform.claude.com/docs/en/build-with-claude/streaming#error-events)). `internal_error` is not on that list, nor among the nine values of the `anthropic` Python SDK's `ErrorType` (1.15.0).
- Nothing else changes: the message, the `content_block_stop` before the error event and the missing `message_stop` stay as #61947 left them.

This PR and #40986 are coupled, and neither thread currently references the other. Flagging the relationship plus one review point before I go through the diff properly.

### How they interact

The converter consumes the chat surface's SSE frames (`message_stream_converter`, `anthropic/serving.py:993-1007`), so what reaches the `ValidationError` path here is decided entirely by what `chat_completion_stream_generator` emits.

- **Mid-stream failures** already produce an `{"error": {...}}` frame on current `main`, so this PR is needed today — that is exactly the GLM-5.2 report in #46028.
- **Failures before the first generated token** are swallowed upstream on current `main`: the empty-chunk guard `continue`s past `_raise_if_error`, so the chat generator emits no error frame at all and the converter never sees one. #40986 fixes that.

So #40986 widens the set of inputs this PR has to handle. The pre-first-token shape is the one that matters for disaggregated prefill, where a KV-load failure fails the request while it is still in `WAITING_FOR_REMOTE_KVS` and its first and only output carries `finish_reason="error"` with `new_token_ids=[]`.

### Measured effect on `/v1/messages`

Driving `message_stream_converter` with recorded chat frames for the tokenless-error shape, then replaying the resulting Anthropic SSE through the official `anthropic` SDK (1.6.0):

| chat-side state | Anthropic events | `anthropic` SDK |
| --- | --- | --- |
| before #40986 | `message_start` → `message_stop` | **completes, no exception**, text `''` |
| after #40986 | `message_start` → `error` | raises `APIStatusError` |

Worth stating explicitly since #46028 doesn't cover it: `/v1/messages` had the same silent-success failure mode as `/v1/chat/completions`, and a failed request came back as a well-formed empty message. With #40986 in place the error becomes reachable here, which is what makes this PR's forwarding logic matter for that case.

**Review suggestion:** the tests here cover the error-chunk shape directly, which is right, but it would be worth adding a case driven from a tokenless `finish_reason="error"` output end-to-end through the chat generator, so this stays correct as the upstream emission changes.

### One separate point: `internal_error` is not a valid Anthropic error type

Both the current code and this PR emit `AnthropicError(type="internal_error", ...)`. Anthropic's error `type` is a closed discriminated union of nine values — `invalid_request_error`, `authentication_error`, `billing_error`, `permission_error`, `not_found_error`, `rate_limit_error`, `timeout_error`, `api_error`, `overloaded_error`. A server-side failure is `api_error`.

This is pre-existing, not introduced here, but this PR is already touching the construction site so it may be the natural place to correct it. `AnthropicError.type` is a bare `str` (`anthropic/protocol.py:16`), so nothing currently constrains it; typing it as a `Literal` union would prevent recurrence.

Impact is moderate rather than breaking: the SDK's streaming path raises off the HTTP status via `_make_status_error`, not off the body discriminator, so clients still get an exception. It affects clients that branch on `error.type`. Happy for this to be split out if you'd rather keep the PR scoped.

### Conformance against the documented error event

Anthropic documents the mid-stream error event as:

```
event: error
data: {"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}
```

| axis | Anthropic | this branch | |
| --- | --- | --- | --- |
| event name | `error` | `error` | match |
| envelope | `{"type":"error","error":{...}}` | identical | match |
| `error.message` | human-readable string | `"Internal server error"` | match |
| `error.type` | closed union of nine values; a server-side failure is `api_error` | `internal_error` | mismatch |
| HTTP status | 200 | 200 | match |
| after the error event | stream ends | stream ends (`return`, no `message_stop`) | match |

So this lands spec-conformant on every axis except the `error.type` value, which is the point from my earlier comment.

### One open question: unclosed content blocks

In the mid-stream case the converter emits `content_block_start` and `content_block_delta`, then goes straight to `error` — block index 0 is never closed, and there is no `content_block_stop` or `message_delta`.

I could not determine whether real Anthropic closes in-flight blocks before an error event. The streaming docs say errors "may occasionally" appear in the stream and do not specify the interaction with open blocks, and I have no way to provoke a genuine mid-stream failure against the live API to observe it. So I am raising this as a question, not a defect, and explicitly not as something to block on.

If it does turn out to matter, the converter already has a `stop_active_block()` / `stop_and_flush()` helper used on the `[DONE]` path, so closing the block before yielding the error event would be a small change. Worth a decision either way, since a client accumulating content blocks by index will be left with an open block — though in practice it is raising on the error anyway, so this may be moot.
