# [Rust Frontend] Support echo with truncate_prompt_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/65624) · state: open · merged: False

## Original PR description

## Overview

Python accepts `echo=true` together with `truncate_prompt_tokens` on `/v1/chat/completions` and `/v1/completions`. The Rust frontend rejected the combination with a 400 ("`echo=true` is not supported with `truncate_prompt_tokens`") in the shared `validate_generation_prompt_truncation`. This PR lifts the rejection and makes the completions echo match the tokens actually sent to the engine, as Python's renderer does since vllm-project/vllm#61876.

## Claims

- The 400 is gone on both routes; `validate_generation_prompt_truncation` keeps only its `>= -1` check.
- **Chat** echoes the last assistant message's content, which truncation does not change (Python `chat_completion/serving.py`); Rust's chat echo already comes from the request messages.
- **Completions, token-ID prompt**: truncation is applied up front and the echo is the decode of the tokens that remain, matching Python's renderer (`renderers/base.py`, `test_detokenization_matches_truncated_tokens`).
- **Completions, text prompt**: echoes its text as sent, truncated or not, as Python `main` does today. Token-ID prompts with `return_token_ids` still echo an empty string. Both unchanged.

## Validation

New tests in `vllm-server` (all three fail on `main`; with the rejection removed but the echo still decoding the untruncated IDs, the two completions tests fail):

- `routes::tests::non_stream_completions_echo_reports_the_truncated_prompt`: token IDs of `hello world`, `truncate_prompt_tokens=5` (left): the engine gets `world`, the response text is `worldhi`, `prompt_tokens=5`.
- `routes::tests::completions_echo_stream_reports_the_truncated_prompt`: streaming, right side, limit 5: token IDs of `hello world` echo `hello`; the text prompt `hello world` echoes `hello world`.
- `routes::tests::chat_completions_echo_stream_with_prompt_truncation`: the engine gets 4 prompt tokens and the stream content is `Sure, hi`.

## Details

**Ownership.** Truncation stays in `vllm-text` (`PromptTruncation::apply`, reached through `TextRequestProcessor`), the only code that knows which prompt tokens remain. The completions converter in `vllm-server`, which builds the echo, asks it for the final tokens instead of decoding the request's: a token-ID prompt with `echo` goes through `TextRequestProcessor::tokenize_in_place`, the existing entry point chat uses to get final prompt tokens before submission. The request then carries the final token IDs, so generation does not truncate again. Without truncation the call only validates and keeps the IDs, and the echo is the decode of the whole prompt, as before.

**Signature change.** `prepare_completion_request` (and `lower_completion_request`, used by `/v1/completions/render`) now takes the `TextRequestProcessor` instead of the bare tokenizer it used only for echo; the convert tests build one from a two-method test backend (mechanical change at 20 call sites). `/v1/completions/render` shares this lowering, so it also computes the echo it discards; the extra work is one decode of a token-ID prompt that render tokenizes anyway, as it already did for untruncated token-ID echo.

**Known follow-up: text prompts.** Python echoes a truncated text prompt as sent, because the tokenizer truncates while encoding and the renderer only detokenizes prompts without text. Open vllm-project/vllm#62691 changes that for an explicit `truncation_side`, excluding the special tokens the tokenizer added (BOS, appended EOS) through an encoding-time special-tokens mask. This PR follows Python `main`. Porting that behavior to Rust needs the same mask: locating the text's own tokens by re-encoding cannot tell an added BOS or EOS from the same token written by the client (for example a literal `"<s>"` in the prompt), and `vllm-tokenizer` does not expose the mask yet. That is a follow-up once vllm-project/vllm#62691 lands.

**Contract.** OpenAI has no `truncate_prompt_tokens`. For token-ID prompts, echo plus logprobs now reports the kept tokens' logprobs against the kept tokens' text.

**Not a duplicate.** vllm-project/vllm#62691 changes the Python renderers for text prompts and does not touch the Rust frontend. vllm-project/vllm#62684 edits the same Rust completions files but changes echo with `return_token_ids` for string prompts, not truncation. No other open PR lifts the Rust echo/truncation rejection.
