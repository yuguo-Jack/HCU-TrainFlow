# [Perf][DSv4.1] Replay one row for prefill chunks far from the prompt end

[Upstream PR](https://github.com/vllm-project/vllm/pull/62817) · state: open · merged: False

## Original PR description

## Overview

With decoder SWA bounded replay, every DeepSeek-V4.1 prefill chunk runs the replay layers (20-39) on its last 128 rows, but after the prefill only the prompt's last window is read. This PR replays one row for chunks that end far from the prompt's end. A 124K prompt in 16K chunks now skips 7 of its 8 replay tails. The same idea is DeepSeek DeepInfer's `clip_prefix` rule.

The rule isn't gated on CUDA, so it covers ROCm too. @frida-andersson tested it on 4x MI325X ([numbers](https://github.com/vllm-project/vllm/pull/62817#issuecomment-6370899321)) and is co-author. Her #61682 does the ROCm side of this and she'll close it once this lands.

## Claims

- A prefill chunk that ends at least `decoder_replay_trim_threshold + window` (768 + 128) tokens before its prompt's end replays only its last row, which reads only itself. Chunks within that reach keep the 128-row replay.
- The prompt's last window is computed as before. Greedy outputs on 3 prompts of ~98.6K tokens are identical with and without this change.
- No step reads replay-layer KV that a one-row chunk skipped. Every later chunk whose window still reaches back past a one-row chunk starts its replay window after it and takes the replay batch. A new `ModelState.needs_eager_forward` hook runs such a step eager when it would otherwise keep the whole batch.
- Default decoder replay graph sizes add 1, 2, ..., 64, so a one-row replay batch doesn't pad to 128 rows.
- Single-request TTFT on 2xB200 TP2: 124K -2.4%, 64K -1.6%.

## Details

- Why `trim_threshold + window`: steps that keep the whole batch (FULL graphs, PIECEWISE graphs below `decoder_replay_trim_threshold`) let every row read `window - 1` rows back through the batch's SWA metadata. With this reach, the finishing chunk only follows a one-row chunk when it is at least `trim_threshold + window` tokens long, so its own step trims and its window starts inside it. Without replay graphs the reach falls back to `max_num_batched_tokens + window`.
- Any other chunk after a one-row chunk (a short chunk cut by the token budget, the encoder budget or `long_prefill_token_threshold`) gets the window floor and the replay batch, and so does each later chunk until its window no longer reaches the skipped rows. `needs_eager_forward` sends its step to eager when it would keep the whole batch. With default scheduling those chunks sit in full-budget steps above the max capture size, which are eager already.
- The model state records per request where its last one-row chunk ended, until no later chunk's window reaches it. A prefix-cache hit, or a chunk that ran in a whole-batch step, doesn't trigger the floor or the hook.
- `_gather_replay_batch_kernel` takes a per-request KV floor from the host instead of deriving `seq_len - window` itself. Under PCP that floor is the global window start.
- In replay batch steps the layer before the replay layers finalizes its MoE. A one-row or follow-up chunk can put the replay batch on a step of 16 tokens or fewer, where the fused all-reduce + mHC boundary would otherwise leave it unfinalized.
- Prompt-logprob and routed-expert requests keep every row, as before. Under PCP (#62384) every trimmed request keeps its whole window, so the one-row rule is off there.
