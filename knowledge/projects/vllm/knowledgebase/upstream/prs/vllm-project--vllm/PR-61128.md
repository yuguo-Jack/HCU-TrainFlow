# [Bugfix][Rust Frontend] Read the text config under `thinker_config`

[Upstream PR](https://github.com/vllm-project/vllm/pull/61128) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The Rust frontend now finds the text config under `thinker_config`, so Qwen2.5-Omni, Qwen3-Omni and Qwen3-ASR checkpoints no longer fail at startup with "the model config does not define `vocab_size`". Fixes part 2 of #61057.

## Claims

- `VLLM_USE_RUST_FRONTEND=1 vllm serve Qwen/Qwen2.5-Omni-3B` starts and serves requests without `--hf-overrides`; before this change it exits during startup.
- Same for Qwen3-ASR once a `tokenizer.json` is present (the missing `tokenizer.json` is part 1 of #61057 and is not addressed here).
- `vocab_size`, `eos_token_ids`, `model_type` and the expert count (`is_moe`) now come from the same config Python's `get_text_config()` returns for these models. Top-level values still take precedence, so `--hf-overrides` behaves as before.

## Validation

Unit tests (Linux, Rust 1.95.0):

```
cargo test -p vllm-text --lib backend::hf::config
test result: ok. 14 passed; 0 failed
```

End to end on one A40 (driver 580.159.04), with the Rust frontend built from the base commit and from this change against the same Python install:

```
VLLM_USE_RUST_FRONTEND=1 VLLM_RUST_FRONTEND_PATH=<vllm-rs> \
  vllm serve <model> --max-model-len 4096 --gpu-memory-utilization 0.85
```

## Details

**Root cause.** These configs nest the language model config two levels deep:

```
{ "model_type": "qwen3_asr",
  "thinker_config": { "audio_config": {...}, "text_config": { "vocab_size": 151936, ... } } }
```

`ModelConfig` in `rust/src/text/src/backend/hf/config.rs` only looks at the top level and `text_config` (alias `llm_config`). On the Python side, `Qwen3ASRConfig.get_text_config()` (and the transformers configs for Qwen2.5-Omni / Qwen3-Omni) return `thinker_config.text_config`, which is why the Python frontend works.

**Change.** Add `thinker_config` to `ModelConfig`, and a `nested_config()` that returns `text_config`, else `thinker_config`. `effective_text_config()` now descends through it recursively, and `vocab_size()`, `eos_token_ids()` and `model_type()` use it where they previously used `text_config` directly. Each accessor keeps its existing precedence, and `text_config` still wins over `thinker_config` when both exist, so every config that worked before resolves the same way. `talker_config` is not followed.

**Side effect worth reviewing.** For Qwen3-Omni, `num_experts` (128) also lives under the thinker, so `is_moe()` changes from false to true. In `vllm-rs serve`, that value decides whether the in-process DP coordinator is started (`rust/src/server/src/config.rs`). The new value matches what the Python engine computes, but I have only reasoned about this from the code and have not run Qwen3-Omni with DP > 1.

**Not in this PR.** Part 1 of #61057 (no `tokenizer.json` in the official Qwen3-ASR / Qwen3-Omni repos). I asked in the issue whether a clearer error or building the tokenizer from `vocab.json`/`merges.txt` is preferred.

**Duplicate check.** No open PR references #61057. #60979 touches the same model family but only the Python side (`qwen3_asr.py`, ragged audio batches).
