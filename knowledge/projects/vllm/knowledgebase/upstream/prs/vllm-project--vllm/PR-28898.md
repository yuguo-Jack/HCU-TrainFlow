# [Bugfix] fix core engine monitor error condition

[Upstream PR](https://github.com/vllm-project/vllm/pull/28898) · state: open · merged: False

## Original PR description

The current engine monitor may output "unexpected error" even if the engine works correctly.

This is because the garbage collection happens lazily, and process exits before full gc. To fix this, this PR adds an explicit gc here, to prevent the confusing error message.

## Purpose
Prevent the confusing error message "unexpected error" when the engine exits normally.

- ErenAta16 · COMMENTED · 2026-07-13T13:37:29Z · [source](https://github.com/vllm-project/vllm/pull/28898#pullrequestreview-4685200965)

Traced this against the current file rather than just the diff, and found two things worth fixing before merge.

`engine_processes` at the start of `monitor_engine_cores()` is not defined anywhere in this file. `start_engine_core_monitor()` only binds `engine_manager` (from `self.resources.engine_manager`), never `engine_processes`. That means `sentinels = [proc.sentinel for proc in engine_processes]` raises a `NameError` the moment this thread runs. Since it's a daemon thread, the exception won't crash the process, it'll just silently kill the monitor thread on every engine start and print a traceback to stderr, so neither the new gc-timing fix nor the original engine-death detection ever actually runs.

Checked what the intended value probably is: `CoreEngineProcManager.__init__` sets `self.processes: list[BaseProcess] = []`, so `engine_manager.processes` looks like what this meant to reference. But `engine_manager` can also be a `CoreEngineActorManager` (the Ray-actor-based path for multi-node deployments), which has no `.processes` attribute at all, it tracks `actor_run_ref_dict`/`run_refs` instead of OS processes with a `.sentinel`. So even the corrected reference would need to branch on the manager type, or skip the sentinel-wait for the actor case.

Separately, the `gc.get_referrers(self_ref())` loop that logs every referencing object at `logger.error` looks left in from debugging the gc-timing issue rather than intended for the shipped fix. `gc.get_referrers` does a full heap scan, and this would fire (and spam error logs with raw object reprs) on every detected engine death. Worth confirming whether that's meant to stay.

Smaller thing: `died = multiprocessing.connection.wait(sentinels)` is never used afterward. If the intent is to only proceed once a process is confirmed dead, this should probably check `died` rather than fall through unconditionally.

This block of code appears to be for debugging purposes to identify referrers to the client object. While useful for development, it should not be part of the production code for several reasons:

- It introduces a local import (`import inspect`), which is against Python's best practices. Imports should be at the top of the file.
- It uses `logger.error` to log debugging information. This will pollute error logs with non-error messages, making it harder to identify real issues.
- The logging can be very verbose and is not suitable for a production environment.

The `gc.collect()` call is the intended fix, and this debugging code is not necessary for it to work. Please remove this block.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Fix logging format in frame reporting**

The new debug logging in `monitor_engine_cores` calls `logger.error("Frame at:", r.f_code.co_name, "locals:", r.f_locals.keys())`, but the logging module expects a %-style format string when additional arguments are supplied. Because the string literal contains no `%` placeholders, this call raises `TypeError: not all arguments converted during string formatting` as soon as a frame is encountered. The exception terminates the monitor thread before `_self.resources.engine_dead` is set or the client is shut down, so dead engine processes will no longer be detected. Please add format specifiers (e.g., `%s`) or build the string before calling `logger.error` so the monitor can complete.
