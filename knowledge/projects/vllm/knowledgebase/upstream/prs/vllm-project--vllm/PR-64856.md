# [Bugfix][MiniMax-M3.1] Reserve MSA Q8KV4 prefill workspace

[Upstream PR](https://github.com/vllm-project/vllm/pull/64856) · state: open · merged: False

## Original PR description

## Overview

Fixes #60791 item 7 by reserving MiniMax-M3 MSA Q8KV4 (NVFP4 KV) sparse prefill split partials during model load, so profiling counts them before sizing the KV cache.

## Claims

- Reserve split partials for the maximum batch and share them across layer impls, so they count once per `(device, topk_blocks, max_num_batched_tokens, num_q_heads)` key per process against `--gpu-memory-utilization`.
- Remove the late SM107-only builder allocation and `MiniMaxM3SparseMSAPrefillMetadata` plumbing; `PrefillWorkspace` preserves SM107 locality striping. Most of the diff is deletion (+72/-142, net -70 lines); the core reservation/sharing logic is about 20 lines.

## Details

Memory profiling skips attention, leaving per-call split partials uncounted. Allocating them after KV-pool sizing causes OOM at startup in the FlashInfer-autotune dummy run (the issue's repro), or on the first large prefill.

**Why not just remove the SM107 capability check?** The old workspace was allocated by metadata builders inside `initialize_kv_cache` → `init_attn_backend`, after `determine_available_memory`/profiling had fixed the KV pool size. Ungating would reserve it on top of an already-sized pool on every device, spreading the same OOM. Even on SM107, that allocation is unaccounted today: it was added for Rubin locality-domain striping, not memory accounting.

`MiniMaxM3SparseMSANvfp4Impl.__init__` now reserves the workspace during model load, inside the profiling snapshot. Impls are per layer (60 on MiniMax-M3.1), so independent reservations would cost 60 × 8.6 GiB. A process-local `WeakValueDictionary` keyed by `(device_index, topk_blocks, max_tokens, num_q_heads)` shares one workspace across matching impls; live impls retain it, and teardown releases it.

With `enable_cumem_allocator`, single-locality-domain devices (such as B300) allocate partials in the `runtime` pool, which offloads and restores their contents across sleep/wake. Level-2 sleep discards the default/weights pool and wake restores only named model tensors, so the runtime tag preserves this workspace.

On multi-domain devices (Rubin/SM107), the pinned `vllm-project/MSA@25c144700f` library instead uses `alloc_locality_striped`: a driver allocation outside CuMemAllocator tracking. These partials stay resident during sleep (~8.6 GiB at `max_num_batched_tokens=32768`), as they did in the old builder path. Sleep integration for this path needs an MSA-library follow-up. Profiling accounts for both allocation paths through free-memory differences.

Scope is NVFP4 prefill. BF16-KV prefill still allocates partials per call and needs kernel workspace support in a follow-up. The PP2 failure above remains unresolved.

Not a duplicate: #60186 fixes workspace accounting at KV initialization, a different, complementary allocation site; no open PR covers #60791 item 7.
