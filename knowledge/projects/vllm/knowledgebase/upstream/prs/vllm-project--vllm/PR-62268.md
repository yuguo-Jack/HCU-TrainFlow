# [Bugfix] Guard Conch W4A16 preconditions and pad non-tile-multiple outputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62268) · state: open · merged: False

## Original PR description

## Overview

`--linear-backend conch` dies at the first forward pass on `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16`:

```
Memory access fault by GPU node-6 (Agent handle: 0x30a2bea0) on address 0x7e69a4600000. Reason: Unknown.
```

48 of the model's layers are fused `in_proj_ba` projections with `N=96`. Conch's W4A16 kernel loads the weight block and the per-group scales in 64-column tiles with no bounds mask, so the second tile covers columns 96-127: **128 B of packed weight and 64 B of scales per row past the end of the buffer**.

This PR handles those shapes in vLLM's Conch wrapper: a `K` the kernel cannot address is refused, and `N` is padded up to the kernel's tile width. All 48 layers then load and run - decode TPOT **-31.7% / -29.4% / -22.5%** vs the default Triton kernel at c=1/8/32 (8k-in / 1k-out). Selection is untouched: Triton stays the default, Conch stays opt-in, and conch
itself is not patched.

The change is shape arithmetic in the wrapper rather than anything platform-specific, so it should hold for any conch-enabled target; validated on `gfx950` (MI355X).

## Claims

* **Refuse the K side.** Every kernel implements `can_implement`, the hook vLLM calls to ask "can you run this layer?". `ConchLinearKernel.can_implement` now says no when the input dimension `K` is not a multiple of the kernel's 64-wide tile, or not a multiple of the quantization group size; channelwise layers (`group_size == -1`, one scale per output column) are checked as if the group size were `K`. None of this model's `K` values (5120, 6144, 17408) trip these, so the checks do not fire here - they stop another model from reaching the kernel with a `K` it mis-addresses.
* **Pad the N side.** Refusing works for `K` but not for `N`: with `uint8b128` weights and bf16 activations Conch is the only kernel available on ROCm (Triton supports only 4-bit weight types, Exllama needs fp16 activations), so refusing a non-multiple `N` would make those layers unloadable. Instead the packed weights, their scales and their zero points are zero-extended along `N` to the kernel's tile width, and the extra output columns are dropped before the bias is added - `N=96` becomes 128 that way. The pad is taken from the unpacked launch-layout weight, so `N` must be a whole number of packing groups (8 for 4-bit); a partial group is refused at selection. This checkpoint has no `uint8b128` layers.
* **Refuse to serve stale weights after a reload.** The pad cache is derived state, and the layerwise reload path re-registers the pre-reload buffers while its captured metadata (recorded at model construction, before any pads exist) has no pads at all - so a reloaded padded layer would keep the old weights in its pads while the parameters get the new ones. Reprocessing a padded layer now raises with an actionable message. The check keys on a plain attribute rather than on the buffers, precisely because the reload deletes every registered tensor before it re-runs this method. Not covered: a reload that supplies weights already in kernel format (`is_checkpoint_format=False`), which skips weight processing entirely and so cannot be detected from inside the kernel; that combination is documented as unsupported.
* All 48 `N=96` layers load (`Using ConchLinearKernel for mixed-precision linear`), 0 memory faults.
* Decode TPOT **-31.7% / -29.4% / -22.5%** at 8k-in / 1k-out, c=1/8/32; our own A/B/B/A harness on short prompts gives **-38.1% / -37.7% / -36.6%** (method in the collapsible below). Prefill is slower - see the note under the bench table.
* Greedy 4/4 byte-identical between backends; gsm8k equal to the last reported digit.

New coverage, all behavioural (real kernel, or the real reload entry points):

## Details

The two loads that feed the tile in `conch/kernels/quantization/gemm.py` - the weight block and the per-group scales - are plain `tl.load`s with no bounds mask, unlike the masked loads and the masked output store next to them. With `N=96` the second 64-column tile reads columns 96-127, past the end of each row of packed weights and scales. If the following page is unmapped that faults (what we first saw); if it is mapped the read is silently out of bounds, and because the tail columns are masked at store time the results stayed correct in that case. A `K` that is not a multiple of the group size walks the scale buffer the same way, which is why the K side is refused rather than padded.

The fix is on our side because conch is pinned (`conch-triton-kernels==1.2.1`), its repository has been quiet since 2025-10-02, and the same unguarded code is in the 1.3 wheel. 

Notes:

* The pads live in three non-persistent buffers (each a tensor or `None`): out of `state_dict()`, moved by `Module.to()` / `Module.cpu()`, and kept at a stable address so CUDA graph replay reads them. That stable address is also why a reload cannot refresh them - see the guard above. Registered parameters keep their original shapes.
* The tile width is read from the kernel at first use rather than hard-coded. If that private helper disappears we fall back to conch 1.2.1's 64 x 64, which would silently under-pad if a future conch used wider tiles.
* A `uint8b128` layer whose `K` Conch cannot address is now unselectable (fails at selection with the reason) instead of being accepted and faulting at runtime.
* The reload gap is general, not conch-specific: registering a buffer does not make a layerwise reload refresh it (the reload restores the pre-reload captured allocation). It is tracked in the stable-runtime-tensor RFC (#57895) and being migrated kernel by kernel (#59000); until that lands, a padded layer refuses.
