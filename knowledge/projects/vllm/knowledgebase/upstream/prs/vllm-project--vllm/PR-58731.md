# [ROCm][AITER] Wire relu2 (non-gated) activation into AITER fused MoE backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/58731) · state: open · merged: False

## Original PR description

## Purpose

Wires `relu2` (non-gated, `MoEActivation.RELU2_NO_MUL`) support into vLLM's ROCm AITER fused-MoE backend, so NemotronH-style models (which use a non-gated MLP activation via `activation_without_mul()`) can dispatch through `AiterExperts` instead of falling back to a slower/incompatible path.

This is Tier 3 of a larger effort: Tier 1 added the relu2 activation kernel, Tier 2 added CK-Tile fused MoE GEMM support for relu2 in [ROCm/aiter#5708](https://github.com/ROCm/aiter/pull/5708). This PR is the vLLM-side integration that lets `AiterExperts` actually route relu2 MoE layers into that aiter kernel.

**Dependency:** requires CK-Tile relu2 MoE GEMM support, which already  available in the [AITER v0.1.26](https://github.com/ROCm/aiter/releases/tag/v0.1.26) version.

**Note:** On 8x AMD Instinct MI350 (gfx950), TP=8, mxfp4 without this PR falls back to vLLM's `OCP_MXQuantizationEmulationTritonExperts` backend, which dequantizes weights on the fly for every MoE forward pass (vLLM itself logs this as a known-slower path — see `ocp_mx_emulation_moe.py:97`). This PR enables AITER's native CK-Tile Relu2 kernel to operate directly on mxfp4 without dequantization. The speedup is largest at low concurrency (where per-request decode cost isn't amortized across a batch) and narrows  but does not disappear,  as concurrency increases and GPU-side batching absorbs more of the per-token emulation overhead.
