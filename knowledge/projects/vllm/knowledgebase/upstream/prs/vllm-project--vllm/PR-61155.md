# [ROCm][Model][BugFix] Fix DiffusionGemma hang with TP4 with AITER on or with AITER off while another process uses GPU memory or intermittently with TP8

[Upstream PR](https://github.com/vllm-project/vllm/pull/61155) · state: open · merged: False

## Original PR description

>  This PR addresses four scenarios for `RedHatAI/diffusiongemma-26B-A4B-it-FP8-dynamic`
  1)  AITER ON for TP4
  2) AITER ON for TP8
  3) AITER OFF for TP4 while another process holds GPU memory
  4) AITER OFF for TP8
> Performance and `lm_eval` numbers are included for comparison and to obtain a complete comparison for running this model at TP4 and TP8 for AITER ON and AITER OFF.

## Overview

The sampler splits the batch into tiles sized from the GPU's free memory, and each tile does a tensor-parallel all-reduce. Free memory differs slightly between ranks. As a result, the ranks run a different number of tiles and issue a different number of all-reduces and wait on each other forever. In the failing run, rank 3 had more free memory than ranks 0-2, so it ran 1 tile while they ran 2

```
DG_TILE rank=0 free=12769558528 num_decode=8 run=[0,8) W=256 budget=7 ntiles=2
DG_TILE rank=1 free=12719226880 num_decode=8 run=[0,8) W=256 budget=7 ntiles=2
DG_TILE rank=2 free=12798918656 num_decode=8 run=[0,8) W=256 budget=7 ntiles=2
DG_TILE rank=3 free=12949913600 num_decode=8 run=[0,8) W=256 budget=8 ntiles=1
```

This bug is not specific to `AITER`. With `AITER` off, holding 6.6 GiB on one GPU hangs the server in the same
way. At TP8, the server also hangs intermittently with `AITER` off, while serving rather than at startup. Without this PR, 5 of 30 TP8 runs on MI300X hung, with the same log message. The script and the results are in the TP8 hang section below.

This PR takes the minimum free memory across all ranks, so every rank computes the same tile size and runs the same all-reduces. vLLM already does the same when sizing the KV cache:

https://github.com/vllm-project/vllm/blob/d4e92ccc37e67048a957aa8e08dc5a2bc665f422/vllm/v1/core/kv_cache_utils.py#L2647-L2652

The all-reduce makes every rank wait for the slowest one. Running it on every decode step lowers TP8 throughput by 8.4% at concurrency 32, so it runs once every 32 decode steps, and every rank reuses the result in between. All ranks see the same decode requests, so they refresh on the same step, and they all skip it when there are no decode requests. With this, the cost at TP8 is within run-to-run noise. The numbers are in the all-reduce cost section below.

## Claims

- `DiffusionGemma` at TP4 starts and serves with `AITER `on, on MI300X and on MI355X.
- `GSM8K `scores at TP4 with `AITER` on are in line with `AITER` off.
- `DiffusionGemma` at TP8 no longer hangs with `AITER` off. With this PR, none of 30 TP8 runs hung, against 5 of 30 without it.
- The all-reduce adds no measurable latency at TP8 on MI300X.

#### TP8 hang

This script starts a TP8 server for each run, 30 by default, and sends 32 requests at concurrency 32 to each one. It stops at the first run that does not complete all 32 requests, and reports whether that run hung or failed for another reason. Run it from an empty directory, since it writes each server's log there.

```bash
#!/bin/bash
# Usage: repro_tp8_hang.sh [runs]   (default 30)

MODEL=RedHatAI/diffusiongemma-26B-A4B-it-FP8-dynamic
TP=8
PORT=8002
RUNS=${1:-30}

export VLLM_ROCM_USE_AITER=0

for i in $(seq 1 $RUNS)
do
  # setsid starts the server in its own process group, so killing the group stops its workers too.
  setsid vllm serve $MODEL --dtype auto -tp $TP --port $PORT \
                    --disable-uvicorn-access-log --trust-remote-code \
                    --max-model-len 4096 \
                    --kv-cache-dtype auto > server_$i.log 2>&1 &
  server=$!
  # The benchmark waits for the server to come up, then sends 32 requests at once.
  vllm bench serve --model $MODEL --host 127.0.0.1 --port $PORT \
                   --trust-remote-code --percentile-metrics tpot,ttft,itl,e2el \
                   --dataset-name random --ignore-eos --temperature 1.0 \
                   --random-input-len 1024 --random-output-len 1024 \
                   --max-concurrency 32 --num-prompts 32 \
                   --ready-check-timeout-sec 600 > bench_$i.log
  # A hung server ignores SIGTERM, so stop it with SIGKILL.
  kill -9 -- -$server
  wait $server
  # A run that does not complete all 32 requests either hung or failed for another reason.
  if ! grep -q "Successful requests: *32" bench_$i.log
  then
    if grep -q "No available shared memory broadcast block" server_$i.log
    then
      echo "run $i: hang, see server_$i.log"
      exit 1
    fi
    echo "run $i: failed, see server_$i.log"
    exit 2
  fi
  # Give the GPUs time to free the memory before the next server starts.
  sleep 30
done
echo "no hang in $RUNS runs"
```

| # | GPU | TP | vLLM | AITER | # Runs | Hung |
|---|---|---|---|---|---|---|
| 1 | MI300X | 8 | without this PR | off | 30 | 5 |
| 2 | MI300X | 8 | this PR | off | 30 | 0 |

Each row started in a fresh container from the `vllm/vllm-openai-rocm:v0.32.0` image, with one warm-up run that is not counted. When a run hangs, it counts, and the script is rerun for the remaining runs. A run that fails for another reason is not counted, and the script is rerun for the remaining runs. Without this PR, runs 1, 2, 5, 10 and 29 hung. These runs also include https://github.com/vllm-project/vllm/pull/61093 and https://github.com/vllm-project/vllm/pull/61444.

In a hung server, every worker waits for the next step, and rank 0's output thread waits for its GPU stream, which never finishes. This is what ranks that issue different numbers of all-reduces look like.

####  TP4 with another process using GPU memory

Without this PR, another process using memory on one of the server's GPUs is enough to cause the hang. This script runs itself in the `vllm/vllm-openai-rocm:v0.32.0` image, holds 6 GiB on GPU 0 in a separate process, and starts the server at TP4 with `AITER` off.

```bash
#!/bin/bash

# Run this script again inside the vLLM image.
if [ -z "$IN_DOCKER" ]; then
  docker run --rm --ipc=host --device=/dev/kfd --device=/dev/dri \
             --security-opt seccomp=unconfined -e IN_DOCKER=1 \
             -v "$(realpath "$0")":/repro.sh -v "$PWD":/work -w /work \
             --entrypoint bash vllm/vllm-openai-rocm:v0.32.0 /repro.sh
  exit
fi

MODEL=RedHatAI/diffusiongemma-26B-A4B-it-FP8-dynamic
PORT=8002

export VLLM_ROCM_USE_AITER=0

# Another process holds 6 GiB on GPU 0.
python3 -c "import torch, time; x = torch.empty(6 << 30, dtype=torch.uint8, device='cuda:0'); time.sleep(1e6)" &
holder=$!
sleep 30

setsid vllm serve $MODEL --dtype auto -tp 4 --port $PORT --trust-remote-code \
                  --max-model-len 4096 --kv-cache-dtype auto > server.log 2>&1 &
server=$!
vllm bench serve --model $MODEL --host 127.0.0.1 --port $PORT --trust-remote-code \
                 --dataset-name random --ignore-eos --temperature 1.0 --random-input-len 1024 --random-output-len 1024 \
                 --max-concurrency 32 --num-prompts 32 --ready-check-timeout-sec 1200 > bench.log
kill -- -$server
kill $holder

grep -q "Successful requests: *32" bench.log && echo "no hang" || echo "hang, see server.log"
```

On MI300X, the server hangs during startup with v0.32.0. With this PR's change applied to the image, it starts and completes all 32 requests.

#### Cost of the all-reduce

DiffusionGemma at TP8 with `AITER` off on MI300X, with the all-reduce removed, run every 32 decode steps as in this PR, and run on every decode step. Each version ran 3 times, in turn, and the table shows the means. The change is relative to the version without the all-reduce, which can hang, although none of those three servers did.

| # | max-concurrency | All-reduce | Median TPOT (ms) | Median ITL (ms) | tok/s |
|---|---|---|---|---|---|
| 1 | 1 | none | 2.01 | 686.70 | 369.40 |
| 2 | 1 | every 32 decode steps (this PR) | 1.99 (-0.8%) | 679.93 (-1.0%) | 371.06 (+0.4%) |
| 3 | 1 | every decode step | 2.01 (+0.3%) | 686.76 (+0.0%) | 368.76 (-0.2%) |
| 4 | 32 | none | 7.15 | 2434.23 | 825.63 |
| 5 | 32 | every 32 decode steps (this PR) | 7.26 (+1.6%) | 2473.04 (+1.6%) | 814.83 (-1.3%) |
| 6 | 32 | every decode step | 7.79 (+8.9%) | 2631.73 (+8.1%) | 756.54 (-8.4%) |

The ITL is the time between output chunks, since the model returns a canvas of tokens at a time. At concurrency 32, the three runs without the all-reduce are within 2.1% of their mean. So the cost of running it every 32 decode steps is within noise, while running it on every decode step costs about 8%.
