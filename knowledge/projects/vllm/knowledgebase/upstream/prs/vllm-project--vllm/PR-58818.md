# [Perf][DSv4.1] Share the FlashMLA decode plan across KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/58818) · state: open · merged: False

## Original PR description

## Purpose

`DeepseekSparseSWAMetadataBuilder.build()` creates one empty `FlashMLASchedMeta` per DeepSeek-V4 layer type. The first `flash_mla_with_kvcache` call of each type runs FlashMLA's tile-scheduler planner, and the later layers of that type reuse the plan (the comment calls it "shared across all ~60 layers of that type within a decode step").

However, the builder runs once per KV cache group. With the packed KV cache layout, DeepSeek-V4.1-Flash's sliding-window caches are spread over 8 groups, and each group builds its own holders. So the planner runs once per (group, layer type). A torch-profiler trace of one TP8 decode step shows 18 planner launches in the target model (before layers 0-9 and 20-27) and 3 in the DSpark drafter (one per draft layer), where 4 are enough.

`get_mla_metadata_kernel` is a single 32-thread block with a serial loop over the SM partitions, and every launch sits in front of its layer's attention. On H20 it takes 16.6 µs per launch at 1 request and about 41 µs at 64 requests.

A plan depends on the batch shape and on the values of the decode `topk_length` / `extra_topk_length`. FlashMLA's interface allows reuse only while those values stay the same, but it asserts only shapes and config. Across the KV cache groups of one metadata build pass the values do match:
- The SWA lengths come from the same query and sequence lengths, window, valid-token mask and `replay_start`. Each group builds the mask from its own slot mapping, but every sliding-window group writes each scheduled token, so the masks agree; `replay_start` is one tensor passed to every builder.
- The top-k lengths count the valid entries each index layer writes. Every decode top-k path fills the entries past a row end derived from `seq_lens` and `next_n` alone with -1 (for example `rowEnd` in `csrc/libtorch_stable/sampler.cu`), under the same valid-token mask. So each index layer of a compress ratio yields `min(rowEnd, topk)`.

That second point is also why a group's same-type layers can already share one plan today, though they take their top-k from different index layers.

This PR lets the groups share the holders:
- MRV2's `build_attn_metadata` passes one dict to every group's `CommonAttentionMetadata`, next to the existing `_token_to_req_indices_cache`.
- The sliding-window builder takes its plan holders from that dict, keyed by its block size, causality and index width.

What stays as before:
- Callers that do not pass the dict (the V1 runner, the draft metadata refresh of the autoregressive speculator) keep one plan per group.
- DBO micro-batches and the DSpark drafter build in separate passes, so they never share a plan.
- SM100 does not take this path: it defaults to FlashMLA mega attention, which does not use these plan holders.

Planner launches per decode step drop from 21 to 4.

**Duplicate check.** `gh pr list --repo vllm-project/vllm --state all --search` for `tile_sched`, `FlashMLASchedMeta`, `get_mla_metadata`, `tile scheduler` and `planner flashmla` shows no PR that shares the plan across KV cache groups.

Related: #58762 (RFC #58638) reuses Mamba/GDN metadata across KV cache groups in the same `build_attn_metadata` loop. This PR does the same for DeepSeek-V4's FlashMLA plans, which are built per group however many groups there are.

## Test Plan

**Setup**
- Hardware: 8× H20 (SM90, 96 GB, NVLink).
- Model: DeepSeek-V4.1-Flash, HF revision `dba1be0a40aa45a94ad051997016db3960a90277`.
- vLLM: "main" is the nightly wheel `0.30.1rc1.dev85+g8b84e1506` as installed; "this PR" is the same wheel with this diff applied as a Python overlay. The three changed files are identical between that nightly and current `main`.

**Server.** TP8 + EP8. DSpark uses synthetic acceptance with a configured mean acceptance length of 3.51, the same distribution in both arms, so acceptance does not depend on the model's outputs:

```bash
vllm serve deepseek-ai/DeepSeek-V4.1-Flash --revision dba1be0a40aa45a94ad051997016db3960a90277 \
  --tensor-parallel-size 8 --enable-expert-parallel \
  --language-model-only --tokenizer-mode deepseek_v41 --max-model-len 262144 \
  --max-num-batched-tokens 8192 --max-num-seqs 128 --gpu-memory-utilization 0.90 \
  --no-enable-prefix-caching --engram-config '{"cpu_offload":false}' \
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","rejection_sample_method":"synthetic","synthetic_acceptance_length":3.51,"enable_adaptive_verification":false}' \
  --profiler-config '{"profiler":"torch","torch_profiler_dir":"<dir>","torch_profiler_activities":["CUDA"],"torch_profiler_with_stack":false,"ignore_frontend":true,"max_iterations":20}'
```

**Load.** One `vllm bench serve` call per point, with these values:

| Point | ISL | OSL | C | N |
|---|---:|---:|---:|---:|
| 8K prompt TTFT | 8192 | 1 | 1 | 5 |
| 1K in / 1K out, C1 | 1024 | 1024 | 1 | 6 |
| 1K in / 1K out, C64 | 1024 | 1024 | 64 | 192 |


```bash
vllm bench serve --backend openai --endpoint /v1/completions --dataset-name random \
  --random-input-len <ISL> --random-output-len <OSL> --random-range-ratio 0 --ignore-eos \
  --max-concurrency <C> --num-prompts <N> --num-warmups <C> --seed 1
```

**Arms.** Five fresh servers, run in the order B1, A1, A2, B2, B3:
- main (A1, A2);
- a prototype that shared the plans at forward time (B1, B2);
- this PR's metadata-level sharing (B3).

B3, the profile and this PR's GSM8K runs used the diff before `non_causal` joined the cache key. In every measured path the target groups are causal and the drafter builds in its own pass, so that key element changes nothing there. Every arm passes the same `--profiler-config`, which stays idle while the benchmarks run.

**Profile.** 20 decode steps under the torch profiler (`/start_profile`), 1K in / 1K out, at C1 and C64.

**Accuracy.** Full GSM8K (1,319 questions) through `/v1/chat/completions`: 5-shot multi-turn chat, thinking off (`chat_template_kwargs: {"thinking": false}`), temperature 0, seed 123, `max_tokens` 1024, 32 concurrent requests; 

## Test Result

**Serving.** The last column compares B3 with the mean of the main arms. Higher output throughput and lower ITL and TTFT are better.

| Point | Metric | main A1 | main A2 | this PR B3 | Change |
|---|---|---:|---:|---:|---:|
| 1K in / 1K out, C1 | output tok/s | 317.3 | 318.9 | 326.0 | **+2.5%** |
| 1K in / 1K out, C1 | median ITL (ms) | 10.42 | 10.36 | 10.12 | **−2.6%** |
| 1K in / 1K out, C64 | output tok/s | 1937.6 | 1942.7 | 1949.2 | +0.5% |
| 1K in / 1K out, C64 | median ITL (ms) | 84.15 | 83.84 | 83.51 | −0.6% |
| 8K prompt, C1 | TTFT (ms) | 1216.5 | 1220.0 | 1216.6 | −0.1% |

B3 is a single run. The main arms differ by 0.5% at C1 and 0.3% at C64, so the C64 change is small. The gain is largest at low concurrency, where the planner is a larger share of a short step. Prefill does not plan decode tiles, so TTFT is unchanged. The forward-time prototype, which also launches the planner 4 times per step, measured 325.2 and 329.2 tok/s at C1 and 1957.9 and 1952.6 tok/s at C64.

**Profile** (rank 0, 20 decode steps, B3's code):

| | main | this PR |
|---|---:|---:|
| Planner launches per step (target + drafter) | 21 | 4 |
| Planner time per step, C1 | 348 µs | 66 µs |
| Planner time per step, C64 | 868 µs | 161 µs |

**Accuracy.** Two full GSM8K runs per side, each on a fresh server:

| GSM8K, 5-shot chat, greedy (1,319 questions) | main | this PR |
|---|---:|---:|
| Run 1 | 96.97% (1279) | 96.44% (1272) |
| Run 2 | 96.51% (1273) | 96.74% (1276) |
| Mean | 96.74% | 96.59% |
| DSpark acceptance length (runs 1 / 2) | 3.863 / 3.851 | 3.865 / 3.851 |

main's own two runs differ by 6 questions, more than the 2-question gap between the means. Greedy decoding at concurrency 32 varies with how requests are batched, so this rules out a large accuracy change but cannot show identical outputs.

**What covers the new path.** The unit tests below construct `CommonAttentionMetadata` directly, so `_cross_group_cache` stays `None` and they never take the sharing branch. They only show nothing else changed. The new path is covered on H20 by:
- the profile: 4 planner launches per step, so the groups do share;
- the serving runs;
- GSM8K with real DSpark verification.

The serving numbers use synthetic acceptance to measure speed and say nothing about accuracy.

**Tests.** `tests/v1/attention/test_deepseek_v4_swa_visible.py` and `tests/v1/attention/test_dspark_noncausal_sparse_mla.py` give 38 passed and 31 skipped on one H20, with and without this diff. The pinned `ruff` (0.14.0) and `typos` checks pass on the changed files.
