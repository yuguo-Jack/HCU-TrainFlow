# [Bugfix] Warn when VLLM_PLUGINS names match no installed plugin

[Upstream PR](https://github.com/vllm-project/vllm/pull/60974) · state: open · merged: False

## Original PR description

## Overview

`VLLM_PLUGINS` matches plugin names against the entry point registry by exact string, so a name that matches nothing is dropped silently — no error, no warning, exit code 0. `docs/design/lora_resolver_plugins.md:13` names the built-in HF Hub resolver `hf_hub_resolver`, but `pyproject.toml:47` registers it as `lora_hf_hub_resolver`. Following the doc loads nothing: the resolver is never registered, and requests fail later with "adapter not found".

Fixing the doc alone is not enough. The wrong name has shipped in released docs (e.g. v0.25.0) and in configs the project does not control; and the existing guard in `hf_hub_resolver.py` cannot cover this case, because it is the entry point target and only runs once the plugin is loaded — which already requires the name to match.

This warns once per process when a `VLLM_PLUGINS` name matches no installed plugin, and lists the available names.

## Claims

- An unknown `VLLM_PLUGINS` name now emits a warning listing the available plugin names, instead of being ignored with no diagnostics.
- `docs/design/lora_resolver_plugins.md:13` now uses `lora_hf_hub_resolver`.
- No model output, accuracy, or serving behaviour changes, so no model evaluation is included.

## Validation

`load_general_plugins()` returns `None`, so the reproducer observes the log rather than a return value.

    # before (main) / after (this branch): the typo is silent on main, warned here
    VLLM_PLUGINS=hf_hub_resolver python -c "from vllm.plugins import load_general_plugins; load_general_plugins()"
    main:  (no output — a typo is indistinguishable from a correct name)
    here:  VLLM_PLUGINS contains ['hf_hub_resolver'], which match no installed plugin. These entries will be ignored. Available plugins: ['lora_filesystem_resolver', 'lora_hf_hub_resolver']

    # a valid name must not warn (guards the cross-group union against false positives)
    VLLM_PLUGINS=lora_hf_hub_resolver python -c "from vllm.plugins import load_general_plugins; load_general_plugins()"
    (no output)

    # with the documented name the resolver is never registered
    VLLM_LORA_RESOLVER_HF_REPO_LIST=foo/bar VLLM_PLUGINS=hf_hub_resolver python - <<'EOF'
    from vllm.plugins import load_general_plugins
    from vllm.lora.resolver import LoRAResolverRegistry
    load_general_plugins()
    print(sorted(LoRAResolverRegistry.get_supported_resolvers()))
    EOF
    []

    # real server, single GPU (vLLM 0.31.1rc1.dev245+gbe0823357): warning once per process at startup, before the model loads
    VLLM_PLUGINS=hf_hub_resolver vllm serve Qwen/Qwen2.5-0.5B-Instruct --enable-lora --gpu-memory-utilization 0.8
    (EngineCore pid=6295) WARNING ... [__init__.py:104] VLLM_PLUGINS contains ['hf_hub_resolver'], which match no installed plugin. These entries will be ignored. Available plugins: ['lora_filesystem_resolver', 'lora_hf_hub_resolver']

Lint: `pre-commit run --files vllm/plugins/__init__.py docs/design/lora_resolver_plugins.md` — all hooks passed.

## Details

Root cause: `vllm/envs.py` parses `VLLM_PLUGINS` with `.split(",")`, and `load_plugins_by_group` tests `plugin.name in allowed_plugins` — exact membership; an unmatched name is dropped with no signal.

`VLLM_PLUGINS` is one global allowlist shared by all five plugin groups, so "unknown" is judged against the union of every group's entry points; a per-group check would false-positive on another group's names. The check lives in `load_general_plugins` rather than `load_plugins_by_group` because it does not use the `group` argument and can reuse the existing once-per-process `plugins_loaded` guard.

`PLUGIN_GROUPS` is a module-level tuple of every group whose entry points are filtered by `VLLM_PLUGINS`, kept next to the group constants so that a new group is added in one place rather than in a list inside `load_general_plugins`. It still has to be extended by hand when a group is added; `load_plugins_by_group` is the only consumer of `VLLM_PLUGINS` (`load_endpoint_plugins` goes through it), so this tuple is the definition of the filtered set and the module level is the right home for it.

It is informational, not a failure: it names both the unmatched entries and the available names, so an intentional absence (e.g. one `VLLM_PLUGINS` shared across heterogeneous containers) is recognisable rather than alarming. It only fires when `VLLM_PLUGINS` is set and lists a name not installed anywhere in this environment; unset, or `VLLM_PLUGINS=""` (which parses to `[""]` and is excluded), stays silent.

The available names are already logged, but only at `DEBUG` for this group, and that log never says a `VLLM_PLUGINS` entry matched nothing — searching it for the typo'd name even hits the module path, which reads as "it's there".
