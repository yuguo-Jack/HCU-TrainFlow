# [Bugfix][Multimodal] Pad MiniMax-M3 encoder graph cu_seqlens with zero-length sequences

[Upstream PR](https://github.com/vllm-project/vllm/pull/65226) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The MiniMax-M3 encoder CUDA graph declares the unused rows of a captured buffer as one extra attention sequence, so every replay smaller than its budget runs full self-attention over its padding rows. This PR pads `cu_seqlens` with zero-length sequences instead, as the Qwen2.5-VL, Kimi-K2.5, LFM2 and DeepSeek-V4.1 encoder graphs already do.

The main reason is correctness with shared capture buffers (#65084). The speedup is large only when replays carry many padding rows, e.g. the default power-of-two budgets.

## Why the padding sequence existed, and why it is no longer needed

- #58673 added the padding sequence to avoid NaN. FlashAttention does not write rows that belong to no sequence. With an uninitialized output those rows hold garbage, and a real sequence's last K/V tile in the next layer reads them: the mask sets P = 0, but 0 · NaN = NaN.
- #56711, merged the same day after #58673, makes FA's output `torch.zeros` while capturing ([`vit_attn_wrappers.py`](https://github.com/vllm-project/vllm/blob/254a2a33908a9bd974e9656f05592f83de604298/vllm/v1/attention/ops/vit_attn_wrappers.py#L61-L69)). The memset is recorded in the graph, so rows outside every sequence replay as 0.
- Outside attention, the MiniMax tower is row-wise: LayerNorm, MLP, residual, and the 2x2 merge on aligned row groups. The input tail is zeroed by the encoder graph manager and the rope tail by `pad_rope_planes`. So padding rows stay finite and cannot reach real rows.
- Poisoning FA's captured output with NaN does reproduce NaN in real rows with zero-length padding, so the zeroed output is what makes this safe.
- **ROCm.** The change applies to every platform. ROCm AITER does not take `out=`, so its output is not zeroed. This PR does not add a ROCm-specific path: Qwen2.5-VL and Kimi-K2.5 already use zero-length padding there. MiniMax encoder graphs on ROCm were not tested with this change.

## Claims

- **Correct with shared capture buffers (#65084).** The old padding looks up its total by `cu_seqlens.data_ptr()`. With buffers shared across budgets, all budgets share one pointer and replays use the wrong total. On #65084 alone, MiniMax encoder outputs are wrong and every replay takes ~140 ms. With this PR on top, outputs are correct.
- **Same outputs.** Every replay is bitwise equal to before the change and to an eager forward of the same batch.
- **Less work on padding.** Padding rows no longer attend to each other. That attention costs O(padding rows²), about 1.25e-7 ms per row² (GB200, TP1).

## How much padding there is

Encoder CUDA graphs are opt-in (`cudagraph_mm_encoder`), and no MiniMax-M3 recipe enables them. A batch replays the smallest budget that fits it, so its padding is the gap to that budget:

| Budgets | Largest padding per replay | Cost of the padding sequence |
| --- | --- | --- |
| Default when enabled (powers of two, 64…16384, 64 items) | up to ~32k rows | up to ~130 ms |
| #58673 benchmark config (`[512, 1024, 2048]`, 2 items, 336² images) | ~1.5k rows | ≤ 0.3 ms |
| A finer grid (e.g. quarter-octave steps up to ~2560 tokens) | ~2k rows | ≤ 0.5 ms |

The end-to-end gains reported in #58673 still hold: in that config the padding sequence costs well under 1 ms per replay. The large gains below come from the default budgets, where a batch just above a power of two pads almost 2x.

## Validation

Encoder-only benchmark with the real MiniMax-M3.1-Flash vision weights: GB200, BF16, FA4, TP1. Default encoder graph budgets (64…16384, 64 items). Synthetic images were processed by the model's own image processor. Each value is the median of 15 interleaved runs of the full encoder call, including input staging and output copies. Correctness is checked against an eager forward of the same batch.

The table shows the batches with the most padding, plus a few full batches. Batches that fill their budget are unchanged.

| Batch | Images | Tokens | Padding rows | Before (ms) | This PR (ms) |
| --- | --- | --- | --- | --- | --- |
| 224² x 1 | 1 | 64 | 0 | 2.2 | 2.3 |
| 224² x 16 | 16 | 1024 | 0 | 8.5 | 8.4 |
| 672² x 1 | 1 | 576 | 1,792 | 9.2 | 8.7 |
| 672² x 4 | 4 | 2304 | 7,168 | 35.7 | 29.5 |
| 672² x 8 | 8 | 4608 | 14,336 | 84.2 | 58.6 |
| 1344² x 1 | 1 | 2304 | 7,168 | 45.8 | 38.8 |
| 1344² x 2 | 2 | 4608 | 14,336 | 102.6 | 77.1 |
| 1344² x 4 | 4 | 9216 | 28,672 | 251.8 | 151.8 |
| 336² x 17 | 17 | 2448 | 6,592 | 33.4 | 27.5 |
| 13 mixed sizes | 13 | 5298 | 11,576 | 86.7 | 67.5 |
| 25 mixed sizes | 25 | 9214 | 28,936 | 227.6 | 122.5 |

The full matrix has 35 batches: small, medium, large, wide, unaligned and random mixes. It was run once after a large batch had dirtied the buffers, to check that stale tail rows do not leak.

- Every single-replay batch is bitwise equal to eager, before and after.
- Batches that the default dispatch splits into two replays differ from eager by the same relative L2 (0.0013) before and after. That comes from bf16 accumulation order across replays, not from padding.
- A 336x336 single image differs from eager by relative L2 0.016 with every graph variant, the padding sequence included. At layer 0 both paths are equally close to an fp32 reference (0.00171 vs 0.00172), so it is bf16 accumulation order, unrelated to this change.

## Details

One file, +7/−19, mostly deletions. No change outside the MiniMax-M3 encoder graph mixin.

- `pad_cu_seqlens` now repeats the last real offset into the tail slots. The `data_ptr` registry and the spare `cu_seqlens` slot are removed.
- `max_seqlen` stays at the captured row count, since one image can still fill the buffer.

**Not a duplicate.** No open PR changes MiniMax-M3 encoder graph padding. #65084 (shared capture buffers) depends on this fix to stay correct on MiniMax; it does not touch the padding.

**Tests.**
- `tests/models/multimodal/generation/test_vit_cudagraph.py -k minimax_m3`: image test passed, video skipped (image-only model). It uses dummy weights and budget 512, so it covers replay with padding but only checks that generation runs. Run locally against a MiniMax-M3.1-Flash config with `block_size=128`, because the cached `MiniMaxAI/MiniMax-M3` snapshot has no tokenizer.
- Output correctness: the real-weight encoder benchmark above (35 batches, checked against eager).
- `pre-commit` passes.
- **Not tested on ROCm.** All validation above is on NVIDIA GB200 (FA4). No ROCm hardware was available, and AMD CI does not run `test_vit_cudagraph.py`.
