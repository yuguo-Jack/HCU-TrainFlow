# [Refactor] [AMD] flydsl: Move UltraQuant/TurboQuant decode to public APIs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61649) · state: closed · merged: True

## Original PR description

## Purpose

Follow-up to #47896 (TurboQuant FlyDSL decode) and #57057 (UltraQuant FlyDSL
decode), addressing review feedback that both kernels lean on low-level FlyDSL
APIs that are unstable or slated for deprecation. The kernels are rewritten
against FlyDSL's public `fx.*` API, following aiter's
`flydsl-kernel-code-cleanup` guide.

It also fixes a load failure on the pinned stack (`AITER_BRANCH=v0.1.24.post1`,
flydsl 0.3.4.1): neither FlyDSL decode kernel currently loads on main, and both
silently fall back to Triton. `tq_decode.py` / `tq_decode_gqa6.py` import
`buffer_ops` and `vector` from `flydsl.expr`, and `ultraquant_decode_hd256.py`
imports them from aiter internals (`aiter.ops.flydsl.kernels`); none of these
exist in the pinned versions. After this PR the kernels use only public FlyDSL
APIs and no aiter internals.

No behaviour change: outputs are bit-identical to the merged kernels on every
tested shape.

## Changes

| Legacy API | Replacement | UQ | TQ |
|---|---|---|---|
| `ArithValue` / `arith.*` / `_mlir.ir` types | typed `fx.Int32` / `fx.Float32` / `fx.Vector`, Python operators | done | done |
| raw `scf.ForOp` / `scf.IfOp` | `range(..., init=[...])`, Python `if` / `const_expr` | done | done |
| `buffer_ops.*` | `fx.rocdl.make_buffer_tensor` views + `fx.copy` with `BufferCopy` atoms (`buffer_utils.py`) | done | done |
| raw `rocdl.mfma_*` / `mfma_scale_*` | `fx.make_mma_atom` + `fx.gemm` (`mma_utils.py`) | done | done |
| `s_waitcnt(0xC07F)` | `rocdl.s_waitcnt(lgkmcnt=0)` | done | done |
| `SmemAllocator` / `SmemPtr` | `fx.SharedAllocator` | done | DONE |
| stale / verbose comments, dead code | trimmed (AST-checked) | done | done |

- okorzh-amd · comment · 2026-10-15T03:17:36Z · [source](https://github.com/vllm-project/vllm/pull/61649#discussion_r4278652343)

File: `vllm/v1/attention/ops/flydsl_kernels/tq_decode.py` · line None

block_base = phys_block * _stride_cache_block is i32, and every K/V/meta load goes through the single kv_buf4/kv_buf_i16 view on the cache base (L203-204). Once a layer's TQ cache view reaches 4 GiB, the voffset wraps. Because num_records is 0xFFFFFFFF, it silently reads another block instead of faulting. The merged kernel has the same issue, but main never runs it on the pinned stack (it falls back to int64 Triton), and this PR turns it back on. UQ already folds a 64-bit block base into the descriptor (ultraquant_decode_hd256.py:449-455). Small eligible models on one MI355X get past 4 GiB: about 5.3 GB/layer for Qwen2.5-3B and about 6.5 GB/layer for Qwen2.5-1.5B (GQA-6). Could you mirror UQ (fx.Int64(fx.Uint32(phys_block)) * stride passed as base_byte_offset), or at least gate FlyDSL on the cache view being under 4 GiB, and add a >4 GiB TQ case?

- okorzh-amd · comment · 2026-10-15T03:19:13Z · [source](https://github.com/vllm-project/vllm/pull/61649#discussion_r4278660149)

File: `vllm/v1/attention/ops/flydsl_kernels/tq_decode.py` · line 254

Q is always bitcast to bf16 here, but the launcher pools q_rot with dtype=q_dtype (flydsl_turboquant_decode.py:272). The TQ backend allows fp16, and the eligibility check doesn't look at dtype. An fp16 model (e.g. Qwen3-32B-AWQ) with turboquant_4bit_nc therefore gets silently wrong attention: the fp16 and bf16 builds produce byte-identical ISA. The bug predates this PR, but this PR makes it reachable. Fix: allocate the pooled q_rot as torch.bfloat16, or gate eligibility on bf16.

The TQ backend advertises kernel block sizes 16/32/64/128, but flydsl_eligible never checks kv_cache.shape[1], and this assert only accepts 16/32. On main FlyDSL fails to import on the pinned image, so these configs decode via SoA Triton. With this PR FlyDSL loads, so a turboquant_4bit_nc model with head 128 and GQA 6/8/16 run with --block-size 64/128/256, or a hybrid model whose kernel block resolves to 128, hits AssertionError at the first decode. Add kv_cache.shape[1] in (16, 32) to flydsl_eligible so those layers fall back to Triton.
