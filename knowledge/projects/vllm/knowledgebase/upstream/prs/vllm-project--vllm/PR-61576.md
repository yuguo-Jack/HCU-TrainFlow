### 📁 vllm/benchmarks/serve.py — ⚠️ 两个潜在回归

#### 🔴 回归 1: probe_loop 共享 session（并发竞争风险）

**Before:** probe_loop 使用独立的 `probe_session(limit=1)`，与主 session 隔离

**After:** probe_loop 共享主 `session`，连接池被 `max_concurrency` 限制

**问题：**
- 主 session 的连接池被限制在 `max_concurrency`
- 当 `max_concurrency` 较小时，probe 可能因为主流量占满连接池而被严重延迟甚至阻塞
- 原来单独的 probe_session(limit=1) 保证了 probe 有独立连接，不受主流量影响

**建议：** 要么恢复独立 session，要么加注释说明为什么共享是安全的。

#### 🟡 回归 2: probe 停止顺序导致 benchmark_duration 被拉长

**Before（正确）:**
```
outputs = await asyncio.gather(*tasks)   # 主 workload 完成
benchmark_duration = ...                  # ← 先测 duration
probe_stop.set(); await probe_task        # ← 后停 probe
```

**After（有问题）:**
```
outputs = await asyncio.gather(*tasks)   # 主 workload 完成
probe_stop.set(); await probe_task        # ← 先停 probe（等待 sleep 结束！）
benchmark_duration = ...                  # ← 后测 duration
```

**问题：** probe_loop 是 request → sleep → check stop 循环。当主 workload 完成调用 probe_stop.set() 时，如果 probe 正在 asyncio.sleep(interval)，它必须等 sleep 结束才会退出。这段等待时间被计入了 benchmark_duration！

例如：probe_request_rate = 10 → interval = 0.1s。最坏情况下 duration 会被额外拉长 ~0.1s。如果 benchmark 只有 10s，这就是 1% 的误差。

**正确做法：** 恢复原来的顺序（先测 duration 后停 probe），或者在 probe_loop 里实现可取消的 sleep。
