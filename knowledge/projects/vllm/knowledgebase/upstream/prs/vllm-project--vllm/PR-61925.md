# [Attention][SM86] Occupancy-adaptive Triton split-K segments for single-query decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/61925) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Extend the occupancy-adaptive Triton split-K segment count from #58482 (SM120 only) to SM86 **for single-query batches**. On SM86, when `padded num_seqs × KV heads × 16 < SM count` and the batch is single-query, Triton unified attention's 3D path uses 64 softmax segments instead of 16. Multi-query batches (speculative-decode verification) keep 16 on SM86, because 64 segments slow short-context verification there (below). The gate, scratch sizing, and fallback are #58482's; the change adds `(8, 6)` to the capability check plus one clause to the existing 64→16 fallback. Tests make the builder tests independent of the host GPU and cover 64-segment kernel execution.

## Claims

- **Single-query decode on SM86 (RTX 3090, 82 SMs), end to end on main `e2ad0ce5f`:** `vllm bench latency --attention-backend TRITON_ATTN`, Qwen2.5-1.5B-Instruct (2 KV heads), batch 1: **6.1–6.8% lower latency at 8k and 16k prompts** in 3/3 repetitions; no change at 512; gate-off control unchanged (H07).
- **Kernel level:** on the submission-base H04 sample (1 or 2 KV heads), single-query decode speedups are 1.00–3.03×. The broader H01 sample on vLLM 0.31.0 includes a 0.94–0.95× result at 1k context with 4 KV heads; the single-query restriction does not exclude that configuration.
- **Known tradeoff:** with 4 KV heads at batch 1, very short contexts are slower at the kernel level with 64 segments: about 23% at 128 tokens and 7% at 512, break-even near 1k, faster from 4k (see Design note). Not measured end to end for a 4-KV-head model.
- **Speculative-decode verification keeps 16 segments on SM86:** 64 segments would increase attention-kernel latency by up to approximately 34% at 1k context (H04: 0.747× speedup). H06 detected no end-to-end slowdown with a draft model; those runs used random prompts with low acceptance and a noisier host than H07.

## Design note

The #58482 gate counts requests and ignores context length. On SM86 it benefits the measured long-context single-query workloads, but 64 segments slow short-context verification (H04: 0.747–0.956× at 1k in five configurations). This change therefore keeps SM86 verification at 16. Alternatives considered: a context-length condition (needs its own crossover measurement and CUDA-graph dispatch analysis), or reporting measurements instead of patching.

**Short-context tradeoff (H08 review probe).** On the v3 checkout at `e2ad0ce5f`, with the existing environment, BF16, Hq:Hkv:D = 28:4:128, batch 1 and single-query decode, two seeds gave 16/64 time ratios of 0.813 at 128 tokens, 0.927–0.931 at 512, 1.016–1.027 at 1k and 1.418–1.439 at 4k. At 128 tokens, attention takes 6.25 µs with 16 segments versus 7.68 µs with 64 (about 23% higher kernel latency). This configuration still selects 64 under the proposed rule. This is a kernel-level tradeoff; H07's end-to-end result covers a two-KV-head model and does not measure its end-to-end impact.

## Details

- **Why:** with 16 segments the 3D grid is `num_seqs × num_kv_heads × 16` programs. Small-KV-head models at small batch launch fewer programs than SMs (1 × 2 × 16 = 32 on 82 SMs). #58482 addressed this for SM120 and left other capabilities unchanged because they were unmeasured.
- **Scope / limitations:** measured on one SM86 part (RTX 3090). Other 8.6 parts (including A10, A40 and RTX A-series GPUs) were not measured. SM80, SM89, SM90, and SM120 behavior is unchanged. Speculative-decoding measurements use random prompts (low acceptance). H03–H07 used `VLLM_USE_PRECOMPILED` binaries from `fe4df3df0`; H08's builder and kernel validation uses a fresh source build on `47fd76e4`.
- **Relevance:** FA2 is the default backend on SM86, so this affects only deployments that select TRITON_ATTN. FP8 (e4m3) KV is not a motivating case on SM86 here: Triton cannot compile `fp8e4nv` for SM86.
- **Not a duplicate:** no open PR or issue extends #58482 beyond SM120 (searched 2026-10-15). #56276 and #57409 change the same field on ROCm only. Open draft #61760 edits `tests/kernels/attention/test_triton_unified_attention.py` and the kernel, but not the builder gate; the test edits here may need a rebase if it lands first.
- **Builder construction without a visible CUDA device:** if NVML reports an SM86 GPU but CUDA exposes none, builder init reaches `num_compute_units()` and raises, as the SM120 path already does. The tests now mock the platform, so they no longer depend on this.
