# [Core][Perf] Evict superseded Mamba align states first

[Upstream PR](https://github.com/vllm-project/vllm/pull/64975) · state: open · merged: False

## Original PR description

Draft for early review. No blocking issues.

## Overview

With Mamba `align` prefix caching, each turn of a multi-turn conversation resumes from the previous turn's Mamba state and caches a deeper one. The old state is then dead for the conversation, but `BlockPool.free_blocks` queues it at the most-recently-used end, so under pool pressure it outlives live conversations' prefixes. This adds an opt-in `--evict-superseded-mamba-states` that frees such states to the front of the free queue, hashes kept.

## Claims

- With the flag, a finished request's Mamba states that it resumed from, and that a deeper cached state on its own tokens supersedes, move to the front of the free queue, or go there when their last reference is freed. They stay hashed until handed out, so a branch can still hit them.
- Nothing changes for preempted requests, turns that cache no deeper state, states up to a shared-prefix junction, or with the flag off.
- Off by default: a branch, retry or shared system prompt that resumes from a superseded state misses once the block is handed out, which is the next allocation, since the front of the queue is ahead of never-used blocks.
- Kimi-K3 1P1D on MI355X, 88 concurrent agentic sessions with the prefill pool near capacity: +2.1% tok/s/GPU, mean TTFT 8.90 to 7.64 s. Neutral at 72 sessions.

## Validation

- `tests/v1/core/test_mamba_superseded_states.py`: 8 passed; all 8 fail on main. `tests/v1/core`: 1234 passed. pre-commit clean.
- End-to-end numbers come from the runtime prototype this ports, not from this branch.

<details><summary>Unit tests</summary>

CPU only, `pytest tests/v1/core/test_mamba_superseded_states.py`, with the real `KVCacheManager` and `BlockPool` in a TP8-like hybrid layout: three Mamba `align` groups with 896-token blocks, 4 speculative and 1 prefill-checkpoint block each, one 7,168-token attention group, 128-token hashes, retention interval 0.

- After a warm turn, the three states it resumed from are the only cached blocks queued ahead of an uncached one. Off: none.
- A branch from the cold prompt hits them while they are free and misses once the pool hands them out. Off: it still hits.
- A turn ending inside the block it resumed in, a preempted request, and states up to a shared-prefix junction: nothing moves.
- A state held elsewhere at finish moves when its last reference is freed; a prefix-cache hit cancels that.

On main all 8 fail: 7 with `TypeError` on the new `KVCacheManager` argument, 1 with `AttributeError` for `BlockPool.prioritize_eviction`. Seven single-line reverts of the change (no finish hook, demote on preemption, drop hits on preemption, no deeper-state check, no junction exclusion, `free_blocks` ignoring the mark, `touch` keeping it) each fail at least one test.

</details>

<details><summary>End-to-end benchmark</summary>

Kimi-K3, 1 prefill + 1 decode instance on 2 nodes of 8x MI355X, TP8 + DCP8 per role, FP8 KV cache, DSpark speculative decoding, Mooncake RDMA from P to D, and `MooncakeStoreConnector` as a host-memory KV tier on the prefill instance. vLLM ROCm nightly `3966924d` with the change applied as a runtime patch. Multi-turn agentic trace, same config with and without the change. The two 88-session runs used different node pairs.

88 concurrent sessions, prefill near pool capacity. Per-request values are means:

| Metric | Without | With |
| --- | ---: | ---: |
| tok/s/GPU | 17,141.6 | 17,496.3 (+2.1%) |
| Mean TTFT | 8.90 s | 7.64 s |
| Local prefix hit per request | 95.9K | 99.4K tokens |
| Mooncake Store loads per request | 9,977 | 7,372 tokens (-26%) |
| Freshly computed per request | 5,804 | 5,762 tokens |

By the end of the run 9,705 states had been superseded and 21 of them were hit again before reuse.

72 concurrent sessions, prefill not the bottleneck: 16,523.8 to 16,510.4 tok/s/GPU (neutral). GSM8K 0.9545 with the change.

Prefill-only replay of 88 sessions on one TP8 prefill instance: at 16 in flight, local hit 90.8% to 98.2%, recompute per request 27.9K to 3.7K tokens, goodput 1,457 to 4,883 tok/s until the working set outgrows the pool (about +220 blocks, 4.6% effective capacity). At 32 in flight, hit 81.6% to 88.6%. Outputs matched. A branch from a superseded state after its block was reused hit 0 and gave outputs identical to a cold recompute; with a Store tier the Store keeps its copy.

The prototype also moved states the request itself cached below its latest one, and ran with shared-prefix checkpoints off. This PR moves only states a request resumed from and keeps states up to a junction. How many of the prototype's 9,705 were resumed-from states was not counted, and this branch was not re-measured.

</details>

<details><summary>Notes</summary>

- The deeper state is looked up at finish with the Mamba manager's own `find_longest_cache_hit`, so a state another request cached on the same tokens also counts, and a deeper state evicted before finish does not.
- Speculative blocks are never hashed, so they are not affected. Checkpoints placed under `drop_eagle_checkpoint_block` were not tested.
- Non-`align` Mamba modes have no prefix caching, so no hits are recorded and the flag is a no-op.
- Blocks a KV connector releases with `unpin_blocks` keep going to the end of the queue. With delayed frees for P/D, states move when the blocks are actually freed.
- `tests/v1/core` ran on CPU without `prefix_cache/test_hybrid_prefix_cache_hit_rate.py`, which needs `orjson`, and the two `_e2e` files. `tests/engine/test_arg_utils.py`: 117 passed.
- Not run: GPU, end to end on this branch.

AI assistance (Claude in Cursor) was used to write the change, the tests and this description.

</details>

Hi @whx-sjtu, #63808 (opened 2026-10-26) adds the same rule to the GPU prefix cache: when a request finishes, the Mamba `align` states it superseded move to the front of the free queue with their hashes kept, and preemptions and the shared-prefix junction are excluded. It is opt-in as `--prefix-cache-eviction-policy mamba_aware_lru`, the same policy name that #63578 adds for the CPU offload tier.

Differences:
- **Held states:** #64975 marks a state that is still referenced at finish and demotes it once its last reference is freed, unless a hit comes first. #63808 leaves such states in LRU order, so yours is better here.
- **Scope:** #64975 demotes the state a request resumed from. #63808 keeps a set of tips (each finished request's deepest cached state) and demotes every earlier tip between a request's hit and its end.
- **Evidence:** #63808 has a 1-hour AgentX A/B on its own branch (Nemotron 3.5 Super, GB200, GPU-only, two servers per policy): +5.4% requests/hour and −15% recomputed prompt tokens per request. Your Kimi-K3 results on MI355X are a useful second data point.

Rather than two PRs for one rule, I'd suggest folding your deferred demotion into #63808, with you as co-author. Would that work for you, or would you rather consolidate differently?
