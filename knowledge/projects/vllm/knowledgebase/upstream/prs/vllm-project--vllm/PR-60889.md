# [ROCm] MonoKernel for GLM 5.2

[Upstream PR](https://github.com/vllm-project/vllm/pull/60889) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

An opt-in decode path for GLM-5.2 (`glm_moe_dsa`, MXFP4 experts) at TP8 on MI355X (gfx950). It runs each MoE decoder layer (3..77) as one persistent FlyDSL kernel, in "layer mode", inside the stock layer loop.

It uses the `SpecializedDecode` interface of #61867 (Kimi-K3, merged):
- the switch is `additional_config={"decode_backend": "latency_specialized"}`;
- the model refuses unsupported deployments at startup;
- a `ModelState` builds and binds the executor;
- `plan()` runs once per step.

RFC: #60904.

**Related work, and why this isn't a duplicate.** Checked with `gh pr list --state open --search "GLM-5.2 monokernel"` / `"GLM 5.2 decode ROCm"` and against the RFC thread.

| PR | What it is | How it relates |
| --- | --- | --- |
| #61867 (merged) | Kimi-K3 SpecializedDecode, NVIDIA | Same interface and the same batch-size approach; this is the first AMD user of it, for a different model |
| #60397 (merged) | DeepSeek-V4.1-Flash mono decode, MI355X | Different model and kernels |
| #61482, #60731, #60683, #61662 (open) | DSv4-Pro, DSv4.1 on gfx942, Kimi-K3, GLM-5.3-Flash on ROCm | Different models; nothing shared with GLM-5.2's DSA + MXFP4 MoE layer |
| #61311 (open) | Shared specialized-decode abstractions | This PR keeps its runtime per model, as #61867 does, and can move onto shared helpers if those land |

No other PR targets GLM-5.2 decode kernels.

## Claims

- **Speed:** decode TPOT falls by 2.30× at batch 1 and 1.51× at batch 8 on 8× MI355X, GLM-5.2-MXFP4, 3000-token prompts, FULL decode graphs.
- **Accuracy:** at parity with stock on GSM8K (5-shot, greedy, n=1319).
- **Weights:** served at the checkpoint's precision, read in place from vLLM's loaded modules. Nothing is re-quantized at load time.
  - BF16-attention checkpoints (`amd/GLM-5.2-MXFP4`) run BF16 attention, and vLLM's indexer refreshes the indexer layers. Validated on GPU.
  - Checkpoints that ship Quark per-channel FP8 attention (`amd/GLM-5.2-Quark-MXFP4-AttnFP8`) run FP8 attention units with the checkpoint's per-row scales. With `max_model_len` ≤ 4096 they also run the indexer fused into the kernel. Validated on GPU (results below).
- **Supported configurations:** listed in `specialized_decode/README.md`, which grows as support is added.
- **Stock path unchanged:** without the switch, `specialized_decode_config()` returns `None`, and the model, model state and layer loop behave exactly as before.
- **Refusal at startup:** if you set the switch on a deployment it can't serve, startup fails with one `ValueError` that names every unsupported setting.

## Details

**Shape.** Layer mode of the #61867 interface:
- `specialized_decode_config()` runs in `__init__`, before any weights are allocated.
- `DeepseekV32ModelState` builds the executor after the weights load, and calls `prepare_kv()` from `ModelState.initialize_kv_cache` at every KV bind.
- `forward()` calls `plan()` once per step. It returns a `Step` only for plain decode steps the kernels serve, and the layer loop then asks `step.layer(i)` for a kernel. Prefill and mixed batches run the stock layers unchanged.
- The kernel reads vLLM's loaded weights and its KV and index caches in place. There is no second weight copy or checkpoint re-read.

**Batch sizes.** This follows #61867's approach.
- Two constants in `specialized_decode/runtime/__init__.py` set the limit:
  - `BATCH_SIZES = (1, 2, 4, 5, 6, 8, 10, 12)` is what the kernel can be built for;
  - `MAX_BATCH_SIZE = 8`, set from the sweep above.
- The kernels are built for the batch sizes up to 8: 1, 2, 4, 5, 6 and 8. A smaller batch pads up to the next of these (3 runs as 4).
- A step with at most 8 requests runs the kernels; a larger one runs vLLM's decode.
- Larger batches run vLLM's decode.
- Capture sizes and `max_num_seqs` aren't restricted. FULL graphs above 8 capture vLLM's decode. The startup log says `layers 3..77, batch sizes (1, 2, 4, 5, 6, 8); larger batches run vLLM's decode`.

**Unsupported, refused at startup**
- model_type other than `glm_moe_dsa`; TP≠8; PP, DP, EP, DCP, PCP or DBO;
- speculative decoding, sleep mode, LoRA, KV-transfer connectors, routed-expert capture;
- AITER fused shared experts;
- dtype other than bf16; `kv_cache_dtype` other than auto/bf16;
- MRV1; `STOCK_TORCH_COMPILE`;
- not gfx950;
- malformed `specialized_decode` options; `step_sync` under FULL graphs.

**FP8-attention checkpoints**
- The path is chosen from the loaded weights, with no option to set:
  - all four attention matrices FP8 per-channel gives FP8 attention;
  - FP8 `wq_b` and `max_model_len` ≤ 4096 add the fused indexer.
- Partial or mixed FP8, and block, per-tensor or non-Quark FP8, are refused.
- vLLM's FP8 GEMM layouts, including AITER's (16,16) preshuffle, are undone by byte permutation only.
- The BF16 kernels compile to byte-identical code with this change. The FP8 + fused-indexer kernels build at every batch size with no VGPR spills.

**Checked later**
- When the executor is built: the MoE layout and backend, BF16 attention weights (a checkpoint with quantized attention is refused here), and the RoPE table.
- At each KV bind: the caches are bound and contiguous, use the MLA row layout, and are under 4 GiB.

**Core components and complexity**
- No core files are touched. Outside the new directories, the only changes are `amd/model.py` +60/−1, `amd/model_state.py` +21 (new) and one Buildkite step.
- New code: about 1.5k lines of runtime (`specialized_decode/runtime/`), 3.7k lines of vendored FlyDSL kernel (`specialized_decode/flydsl/`, JIT-compiled, no binaries, ruff-clean without excludes) and 1.5k lines of tests.

**MRV2 only.** The path is built on MRV2's `ModelState` hooks. With MRV1, startup is refused with the reason, since this architecture still defaults to MRV1 on ROCm.

**Tradeoffs and limitations**
- Only plain decode at batch sizes up to 8 is accelerated, which is the latency-serving case.
- **Host syncs:** `VLLM_GPU_SYNC_CHECK=error` stops at `rocm_aiter_mla_sparse.py:726`, in vLLM's ROCm sparse-MLA metadata builder, and stock vLLM stops at the same line. With `VLLM_GPU_SYNC_CHECK=warn` on the same workload (batch 1 and 8), stock logs 384 `synchronize` calls and the specialized decode 352, so the specialized decode adds none of its own.
- **Follow-ups:**
  - FP8-attention checkpoints (e.g. `amd/GLM-5.2-Quark-MXFP4-AttnFP8`), including the fused indexer;
  - MTP, which is refused for now;
  - TP other than 8, and other GPUs.

**Interactions with open PRs**
- **#61941** turns AITER fused shared experts on by default for GLM-5.x MXFP4. This path refuses that setting, so once #61941 lands, users of this switch must turn the fusion off. Alternatively the kernel could learn that layout.
- **#61985** adds an MXFP4 indexer K cache, which needs a refusal or kernel support before it becomes the default.
