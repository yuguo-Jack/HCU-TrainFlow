# [Bugfix][Worker] Keep prefill-bearing batches out of FULL (decode-only) cudagraphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62535) · state: closed · merged: False

## Original PR description

## Purpose

Fixes the DSpark speculative-decoding output corruption reported in #62417 (and any other model where a prefill-bearing batch can land in a FULL cudagraph).

## Root cause

Under `cudagraph_mode=FULL`, MRV2's varlen decode graphs are captured on a decode-shaped batch (num_reqs x 1 token per request, bucketed by padded token count). At dispatch time, a batch that contains prefill tokens sets `max_query_len=None` (documented as "varlen decode graphs replay decodes only"), but `_is_compatible` treats `desc.max_query_len is None` as "no constraint" — so an unconstrained FULL descriptor matches, and the prefill batch is padded into a decode-shaped graph. The query block layout no longer matches the graph's capture shape, and the target's logits for the prefill's last position come out flattened (observed top-1 logit ~16.9 with the top-5 packed within 0.6, vs the usual 26-31 spike); every subsequently generated token is garbage.

We confirmed this on 8x RTX PRO 6000 (SM120) with DeepSeek-V4.1-Flash-1017 + DSpark k=3: `1 req / 6 tokens` was dispatched into a `num_tokens=8, num_reqs=8, cg=FULL` decode graph. Only 4-token prompts (= bucket size, no padding) looked unaffected, which made the bug look content-dependent.

## Fix

Pass `allow_full=False` through `dispatch_cg_and_sync_dp` -> `CudaGraphManager.dispatch` whenever the batch has prefill tokens, and skip FULL candidates in that case. Decode-only batches are unaffected.

## Validation (8x RTX PRO 6000, SM120, DeepSeek-V4.1-Flash-1017, DSpark k=3, fp8 KV)

Applied on both v0.32.0 and the current nightly:

- 7-probe corruption set (short prefill + thinking scaffold, CJK, cat-repeat, chat, tools): byte-identical to the `--enforce-eager` and cudagraph-NONE baselines after the patch; before the patch, 4/7 emitted degenerate loops from the first token.
- chat + tools end-to-end: `17*19=? answer with the number only` -> reasoning + `content=323`; tools request -> structured `tool_calls` (`get_gpu_alert({"node":"gpu-03"})`).
- token-length sweep 1-12 and 6/7/11/12/13/20/110/455: all clean after the patch.
- `--no-swa-bounded-replay` and `engram cpu_offload=false` variants: logits unchanged (rules out replay/engram interactions).

Co-worker evidence, dispatch debug lines, and the probe corpus are archived in xzwgit/llm-test `dsv41-flash-1017-sm120`; the issue thread has the full isolation matrix.

## Notes

A separate, subtler effect remains after this fix and is tracked in #62417: with DSpark on, greedy generation is not token-identical to no-speculation (first token always matches; occasional later-token divergences, e.g. `.` vs `.\n`). Per-row attention bounds (SWA lens, indexer top-k bounds, verify positions) were verified correct by instrumentation; the divergence is k-independent and graph-mode-independent, pointing at multi-row verify numerics rather than dispatch. That is out of scope for this PR.

Rebased onto current main (semantic re-apply after 856b9841 and the new `allow_skip_drafts`/`need_eager` parameters in dp_utils) — mergeable again.

Verified while rebasing that main still has no prefill-vs-FULL-graph guard: `dispatch()` selects candidates purely via `_is_compatible` (token counts / reqs / loras / ubatches), and the pre-existing `max_query_len = None` on prefill batches actually makes them *more* likely to match FULL graphs, since FULL descriptors carry `max_query_len=None` ("does not constrain query length"). The new `decode_graph_eligible`/`prefill_runs_as_decode` state added by the recent spec-decode work feeds input preparation and masks only; it is not consulted during cudagraph candidate selection. So the `allow_full` guard in this PR remains the only thing keeping prefill-bearing batches out of decode-shaped FULL graphs.
