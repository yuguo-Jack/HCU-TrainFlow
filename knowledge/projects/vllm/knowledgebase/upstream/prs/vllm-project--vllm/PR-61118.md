# [Bugfix] Enable inductor batch-invariant mode under VLLM_BATCH_INVARIANT

[Upstream PR](https://github.com/vllm-project/vllm/pull/61118) · state: closed · merged: True

## Original PR description

## Purpose

With torch.compile (used under batch invariance for quantized models, among others), RMSNorm and the other vLLM custom ops are lowered by inductor instead of using vLLM's batch-invariant kernels. Inductor picks the tile config of its reduction kernels in each worker process by on-device autotuning among candidates whose reduction block differs (`dynamic_scale_rblock`), and the reduction block sets the fp32 accumulation order: logging the decisions (`TORCH_LOGS=+torch._inductor.runtime.triton_heuristics`, block 3c) shows the same fused residual-add + RMSNorm kernel autotuned to `R0_BLOCK: 1024` in some workers and compiled pieces and to `R0_BLOCK: 512` in others, so two workers can norm the same row to different bits. Inductor has a batch-invariant mode for exactly this (`torch._inductor.config.batch_invariant`, "stable per-sample compiled kernel across batch sizes"; it implies inductor's deterministic mode, which skips that autotuning), but `VLLM_BATCH_INVARIANT=1` did not enable it: every generated kernel carried `'deterministic': False, 'batch_invariant': False` in its `inductor_meta`.

This showed up as MoE models served with DP > 1, TP > 1 and expert parallelism not being batch invariant. The split itself is not specific to that layout: the DP=4 x TP=1 + EP layout's fused norm kernel shows it too (block 3c), and that layout passed the check in every run here. What the sequence-parallel MoE path adds is that a token's MoE input is the post-attention norm output of whichever TP rank's chunk holds the token, and that depends on the token's position in the batch, so within one replica the disagreement becomes a batch dependence. The failure is intermittent (1 to 14 of 32 prompts per run, usually a sampled token flipping at a late decode step from a small logprob change), and it disappears with `--enforce-eager`, with the custom ops kept (`custom_ops=all` or `none,+rms_norm`), with dynamo alone (`DYNAMO_TRACE_ONCE`), or with `TORCHINDUCTOR_BATCH_INVARIANT=1` / `TORCHINDUCTOR_DETERMINISTIC=1`; it stays with CUDA graphs off, with every fusion pass off, with the EP combine replaced by an all-to-all + fixed-order sum, with the router padding mask chunk-aligned, and with `moe_forward`'s stale `mutates_args` removed.

This PR sets inductor's `batch_invariant` config in `enable_batch_invariant_mode()`, which every worker runs before compiling. Nothing changes when `VLLM_BATCH_INVARIANT` is unset. With it, the DP x TP + EP deployment passes with sequence-parallel MoE enabled.

The first revision of this PR disabled sequence-parallel MoE under batch invariance as a stopgap; following review, it now fixes the cause instead, and the evidence below replaces the earlier description.

@yewentao256 Done: I replaced the override with a root-cause fix, and the sequence-parallel path now stays enabled under batch invariance.

**Cause.** With torch.compile, RMSNorm is lowered by inductor instead of using vLLM's batch-invariant kernel. Inductor autotunes its reduction kernels per worker process, and the same fused residual-add + RMSNorm kernel ends up with `R0_BLOCK: 1024` in some workers and `R0_BLOCK: 512` in others. The reduction block sets the fp32 accumulation order of the variance, so two workers can norm the same row to different bits. The same split shows up in the DP=4 + EP layout, so it is not specific to sequence parallelism. That path is where it turns into a batch dependence: a token's MoE input comes from whichever TP rank's chunk holds it, and that depends on the token's position in the batch. Inductor has its own batch-invariant mode for this (`torch._inductor.config.batch_invariant`, which implies its deterministic mode and skips that autotuning); `VLLM_BATCH_INVARIANT=1` did not turn it on.

**Fix.** `enable_batch_invariant_mode()` now sets `torch._inductor.config.batch_invariant = True`. It is a few lines and applies to every compiled model under batch invariance, not just this deployment.

**Evidence** (4x GB300, current `main`, same online bitwise check, each line one server start; raw logs in the updated description):
