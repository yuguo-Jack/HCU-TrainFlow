# [Build] Move extras to pyproject.toml and gate precompiled wheels on [build-system]

[Upstream PR](https://github.com/vllm-project/vllm/pull/61548) · state: open · merged: False

## Original PR description



## Overview

Move vLLM's optional dependencies (`extras_require` in `setup.py`) to `[project.optional-dependencies]` in `pyproject.toml`. They were a fixed dict, so nothing requires them to be computed at build time.

Because `pyproject.toml` now changes more often, the precompiled-wheel fallback from #58871 only refuses an older wheel when `pyproject.toml`'s `[build-system]` table changed, not on any edit.

## Claims

- The extras are now static PEP 621 metadata, so tools that read `pyproject.toml` (dependency scanners, Dependabot, editors) see them without running `setup.py`.
- The built metadata is unchanged apart from the expected `Dynamic: provides-extra` line, which is removed.
- An extras pin bump (or a lint-config edit) no longer makes `VLLM_USE_PRECOMPILED=1` installs fail until the commit's own wheel is published; `[build-system]` changes still block.

## Validation

`VLLM_TARGET_DEVICE=empty python setup.py egg_info` before and after:

- `requires.txt` is identical (all 15 extras and their requirements).
- `PKG-INFO` differs only by the removed `Dynamic: provides-extra` line.

`pytest tests/test_zentorch_version_pin.py` and `python3 standalone_tests/test_precompiled_wheel.py` (as CI runs it) pass (the new pyproject test fails on `main`'s check), and `pre-commit` passes on the changed files.

## Details

- `pyproject.toml`: add `[project.optional-dependencies]` with the same extras, pins and comments; remove `optional-dependencies` from `dynamic`.
- `setup.py`: drop `extras_require` from `setup()`. Install requirements stay dynamic because they depend on the target device.
- `tests/test_zentorch_version_pin.py` and the comment in `.buildkite/hardware_tests/cpu.yaml` now point at `pyproject.toml` for the `zen` pin, and the CPU test image (`docker/Dockerfile.cpu`) copies `pyproject.toml` instead of `setup.py` for that test.
- Precompiled installs: when no wheel is published yet for a commit, `find_published_wheel_commit` falls back to an older one unless compiled inputs changed. Any `pyproject.toml` edit counted, so moving the extras there would make every extras pin bump block `VLLM_USE_PRECOMPILED=1` until the commit's own wheel is published. Now only a change to the `[build-system]` table blocks, reported as `pyproject.toml [build-system]` (as does a `pyproject.toml` that is missing or can't be read at either commit); other edits, such as extras or ruff/typos config, don't affect the compiled extensions and pass silently. The comparison is deliberately the whole table rather than just the torch pin, so it never blocks less than before for build changes. Covered by a new test in `tests/standalone_tests/test_precompiled_wheel.py`, and the precompiled section of the CUDA install docs now says the same.
- `tools/use_existing_torch.py`: its default mode drops every `pyproject.toml` line containing "torch", which would now include the `zen` extra. It now leaves `[project.optional-dependencies]` alone, so it removes exactly the same lines as on `main` in both modes (checked by running both versions).
- CI routing: `setup.py` is a run-all trigger in `.buildkite/ci_config.yaml` and gets the `ci/build` label from `.github/mergify.yml`; `pyproject.toml` is neither. A PR that only bumps an extra will no longer run full CI or be labeled `ci/build`, and the zentorch pin test won't run for a pin-only change. Adding `pyproject.toml` to either list would also fire on lint-config edits, so I've left that to maintainers.
- Open PRs that add an extra in `setup.py` (#60988, #47863) will need to move that line to `pyproject.toml` after this lands.

**Duplicate check.** No open PR moves the extras out of `setup.py`.
