# [Bugfix][Parser] DeepSeek V4.1: don't leak a `<｜DSML｜ tool_calls>` opener into content

[Upstream PR](https://github.com/vllm-project/vllm/pull/62517) · state: open · merged: False

## Original PR description



## Overview

The `deepseek_v41` parser now accepts `<｜DSML｜ tool_calls>` (V4's wrapper name, V4.1's spacing) as a tool-call opener, so it no longer leaks into `content`. Part of #62051 (the "V4 spelling" row); the other rows are not changed here.

## Claims

- For V4.1 output whose tool block opens with `<｜DSML｜ tool_calls>`, the opener no longer appears in `content`, in both streaming and non-streaming. The tool calls are parsed as before.
- Like the canonical `<｜DSML｜ calls>`, this opener also ends an open reasoning block.
- No change for the canonical spelling, the unspaced V4 spelling, or truncated calls.

## Details

**Root cause:** `deepseek_v41_config` replaces V4's `TOOL_START` (canonical spelling plus `DSML_TOOL_START_VARIANTS`) with the single string `<｜DSML｜ calls>`. When the block opens with `<｜DSML｜ tool_calls>`, the V4.1 invoke that follows still matches through the existing `(CONTENT, INVOKE_PREFIX)` transition, so the call is parsed. The opener before it, however, stays in `CONTENT` and is emitted as text.

**Fix:** add it as a `TOOL_START` variant in `deepseek_v41.py`, the same way #56141 added misspelled wrappers to the V4 config. `token_id_terminals` is unchanged: in the V4.1 tokenizer only `｜DSML｜` is an added token (non-special), so the tags reach the parser as text.

**Notes for reviewers:**

- A prose mention of `<｜DSML｜ tool_calls>` now behaves like a prose mention of `<｜DSML｜ calls>`: it opens a tool block. This matches what #56141 accepted for the V4 variants.
- **Open question (the "unspaced V4 spelling" row of #62051):** a fully V4-spelled block (`<｜DSML｜tool_calls>`, `<｜DSML｜invoke …>`) is still returned as text. That matches the Rust frontend, which keeps V4 tags as text in the V4.1 dialect on purpose (`v4_tags_remain_text_in_v41_dialect`, #56208). If V4.1 should accept V4 spellings, I can do that in both frontends in a follow-up.
- **Rust frontend:** it parses invokes only inside a recognised block, so it returns this whole block as text, and this PR doesn't change that. I can align it in a follow-up if you'd like.
- Related: #62259 (truncation rows of #62051) touches other parts of the same file. #61142 (another V4.1 opener drift) edits the same config; whichever lands second needs a small rebase.
