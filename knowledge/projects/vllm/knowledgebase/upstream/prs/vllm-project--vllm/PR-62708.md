# [ROCm][Quantization] Add load-time int4 lm_head quantization for RDNA…

[Upstream PR](https://github.com/vllm-project/vllm/pull/62708) · state: open · merged: False

## Original PR description

## Overview

This PR adds an opt-in `KernelConfig.lm_head_quantization` option for RDNA (ROCm gfx11/gfx12). With `"int4_per_group_32"`, an unquantized fp16/bf16 lm_head is quantized while the model loads:

- asymmetric uint4 weights;
- one scale and zero point per 32 input channels.

The quantized lm_head runs on the existing RDNA hybrid W4A16 op (`rdna_hybrid_w4a16_apply`): `wvSplitK_int4_g` for decode (up to 5 tokens) and the Triton W4A16 kernel for prefill.

```bash
vllm serve <model> --kernel-config '{"lm_head_quantization": "int4_per_group_32"}'
```

**Why.** Decode reads the whole lm_head every step. Many int4 checkpoints keep it in full precision, so on bandwidth-bound RDNA GPUs it becomes one of the largest per-token costs. Qwen3.6-35B-A3B (Quark UINT4 group 128) is one example:

- Its 248320 × 2048 fp16 lm_head is about 970 MB, read every token: 4.5 ms at 211 GB/s on Strix Halo (gfx1151), the largest single item in decode.
- llama.cpp's Q4_K_M GGUF of the same model stores it as Q6_K.

Quantizing at load time needs no new checkpoint and no new kernel.

**Design.**

- **New method:** `Int4LMHeadMethod` (`quantization/online/int4_lm_head.py`) creates the weight like `UnquantizedEmbeddingMethod`, so checkpoint loading does not change. In `process_weights_after_loading` it:
  - quantizes the weight in row chunks, which bounds the fp32 working set;
  - widens each group's range to include 0;
  - writes the codes in the layout `wvSplitK_int4_g` expects (ExLlama-shuffled int4, padded off the vector-cache cliff on gfx1151);
  - writes packed zero points `[N/8, K/32]`.
- **Shared layout code:** `pack_skinny_int4` is split, so `skinny_int4_layout` (the gfx1151 padding step) can be reused on already-shuffled weights.
- **Hook:** `ParallelLMHead` calls `_maybe_quantize_lm_head` only when no quant method was preselected, so the drafter lm_head copies made by `quantized_lm_head_copy` are not affected. The method class is imported lazily.
- **Tied embeddings:** `replace_parameter` rebinds only the lm_head's `weight`, so tied input embeddings keep their full-precision weight. An untied head frees its fp16 weight; a tied head adds the int4 copy (about 0.29 GB at this size) on top of the shared embedding.
- **Errors:** the option raises `ValueError` when it can't apply:
  - a GPU other than gfx11/gfx12;
  - an lm_head that is already quantized;
  - a `head_dtype` different from the model dtype;
  - LoRA;
  - a vocab shard not divisible by 8, or a hidden size not divisible by 32.

  It never falls back silently. The default (`None`) changes nothing.

## Claims

Strix Halo (Radeon 8060S, gfx1151, 40 CUs, LPDDR5X about 211 GB/s), Qwen3.6-35B-A3B Quark UINT4-G128 (fp16 lm_head, 248320 × 2048). Decode benchmark: 512 input / 512 output tokens, batch size 1, greedy, `ignore_eos`, median of 5 runs after 3 warmups, CUDA graphs on (`FULL_AND_PIECEWISE`).

| MoE backend | lm_head | TPOT (ms) | Output tok/s | Change |
|---|---|---|---|---|
| Triton (default) | fp16 | 29.76 | 33.6 | |
| Triton (default) | **int4 g32 (this PR)** | **26.66** | **37.5** | −3.10 ms, 1.12x |
| `rdna3_w4a8` ([#62480](https://github.com/vllm-project/vllm/pull/62480)) | fp16 | 20.69 | 48.3 | |
| `rdna3_w4a8` ([#62480](https://github.com/vllm-project/vllm/pull/62480)) | **int4 g32 (this PR)** | **17.50** | **57.1** | −3.19 ms, 1.18x |

- **Saving vs bandwidth math:** the measured 3.1 to 3.2 ms/token saving matches the expected value. The lm_head read drops from about 970 MB to about 300 MB per token, about 3.2 ms at 211 GB/s.
- **Weight memory:** 18.51 GiB → 17.87 GiB.
- **Run variance:** in the combined run, 4 of 5 runs were 17.47 to 17.53 ms; one outlier at 19.53 ms doesn't change the median.
- **llama.cpp reference:** llama.cpp (Q4_K_M, `llama-bench` tg512) measures 17.82 ms on the same machine. The combined configuration is the first vLLM setup to match it on this model.

**Accuracy:** GSM8K is unchanged within noise. There is a small token-level cost, measured below.

## Validation

**Unit tests:** `pytest tests/kernels/quantization/test_rdna_int4_lm_head.py`

- CPU:
  - quantization error is at most one step, with a bounded RMS error (fp16 and bf16);
  - zero-point packing round-trips;
  - the packed layout unshuffles back to the codes;
  - selection: the lm_head keeps its method by default, the int4 method is selected on a mocked gfx1x device, and the option raises on other GPUs and on an already quantized head.
- gfx11/gfx12 GPU:
  - output matches a dequantized reference for 1, 4, 5, 6 and 32 tokens, which covers both the HIP and the Triton paths;
  - output stays close to the fp16/bf16 lm_head;
  - a tied lm_head leaves the input embedding in full precision.

**GSM8K, real int4 kernel** (lm-eval 0.4.13 `gsm8k_nothink`, 5-shot, first 100 questions, standard error about ±3.4 points):

| MoE backend | lm_head | flexible-extract | strict-match |
|---|---|---|---|
| Triton | fp16 | 88% | 88% |
| Triton | int4 g32 | 87% | 87% |
| `rdna3_w4a8` | fp16 | 89% | 88% |
| `rdna3_w4a8` | int4 g32 | 86% | 87% |

- **Changed answers:** 3 with Triton and 7 with `rdna3_w4a8`, all within noise. One of the `rdna3_w4a8` changes is formatting only ("16.00" for 16).
- **Full test set** (1,319 questions, lm_head fake-quantized to the same int4 g32 scheme): bf16 90.37% / 89.76%, int4 g32 90.30% / 90.07% (flexible / strict). This matches the published 90.2% for the uint4 g128 checkpoint.

**Token-level fidelity** (WikiText-2, 296,670 tokens, fake-quantized lm_head):

| lm_head | Perplexity | Change | Top-1 agreement with bf16 |
|---|---|---|---|
| bf16, second run (noise floor) | 7.3725 | −0.02% | 98.14% |
| int4 g32 | 7.4282 | +0.74% | 94.58% |

int4 has a small, measurable token-level cost: perplexity rises 0.74%, and about 3.6% more top-1 tokens flip than the bf16 rerun does. It doesn't show up in GSM8K. That is why the option is opt-in rather than a default. A quality-neutral int8 per-channel format (perplexity +0.01%, top-1 99.34%) is proposed as a follow-up in [#63402](https://github.com/vllm-project/vllm/pull/63402), on top of this PR.

## Details

- **Scope:**
  - RDNA gfx11/gfx12 only, and only lm_heads that load unquantized.
  - There are no C++ changes: everything runs on ops already in `main`.
- **Not covered:**
  - LoRA and a separate `head_dtype` are rejected rather than supported.
  - Drafter lm_head copies keep their existing `draft_lm_head_quantization` handling.
- **Follow-ups:**
  - int8 per-channel lm_head ([#63402](https://github.com/vllm-project/vllm/pull/63402));
  - possibly int6 group 32, which matched llama.cpp's Q6_K accuracy (perplexity +0.07%, top-1 98.67%).
