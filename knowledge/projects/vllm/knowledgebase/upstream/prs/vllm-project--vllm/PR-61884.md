# [Bugfix] Reject LoRA at config time for models without SupportsLoRA

[Upstream PR](https://github.com/vllm-project/vllm/pull/61884) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Reject `enable_lora=True` during config validation for models that don't implement `SupportsLoRA`, instead of failing later inside EngineCore. Fixes #61850.

## Claims

- `LLM(model="Zyphra/Zamba2-7B-instruct", enable_lora=True)` now fails during config validation (a `ValidationError` from `VllmConfig`) with `LoRA is not supported for Zamba2ForCausalLM (Zyphra/Zamba2-7B-instruct). ...` instead of a bare `AssertionError` in EngineCore surfacing as `RuntimeError: Engine core initialization failed`.
- The check applies to every registered model without `SupportsLoRA` (125 architectures today), not only Zamba2 and Mamba2.
- No behavior change for models that support LoRA, or for any model run without `enable_lora`.

## Validation

Reproducer: the snippet from #61850, run on the CPU backend with `load_format="dummy"` (the failure happens in the model constructor, before weights load).

| Model | `enable_lora` | Before (main @ a97d19d792) | After |
|---|---|---|---|
| Zyphra/Zamba2-7B-instruct | True | `AssertionError` at `zamba2.py:719` → `Engine core initialization failed` | `ValidationError` at config validation, no EngineCore started |
| Zyphra/Zamba2-1.2B-instruct | False | starts and generates | starts and generates |

- New tests: `test_registry_supports_lora` and `test_lora_rejected_at_config_time_for_unsupported_model`. They pass with this change; with the source changes reverted, the four cases that check the new behavior fail.

Validated on the CPU backend only. The change touches config validation and the model registry, not device code; both test files run in CI (`models_basic.yaml`, `engine.yaml`).

## Details

**Root cause:** whether a model supports LoRA is already known from the `SupportsLoRA` interface, but it was only checked in `LoRAModelRunnerMixin.load_lora_model` (`lora_model_runner_mixin.py:47`), after the model is constructed inside the worker. `Zamba2Model` and `Mamba2Model` guard against LoRA with a bare `assert` in their constructors, which runs first, so the existing descriptive error was never reached, and the failure was only visible in EngineCore's stderr.

**Fix:** follows the existing pattern used for pipeline parallelism (`supports_pp` → `ModelConfig.is_pp_supported` → checked in `ModelConfig.verify_with_parallel_config`):

- `registry.py`: record `supports_lora` in `_ModelInfo`, computed with the existing `supports_lora()` helper.
- `config/model.py`: expose it as `ModelConfig.is_lora_supported`.
- `config/lora.py`: raise in `LoRAConfig.verify_with_model_config`, which already runs during `VllmConfig` validation.
- `zamba2.py`, `mamba2.py`: drop the now-unreachable asserts.

**Notes for reviewers:**

- No configuration that worked before is newly rejected: the runtime check calls the same `supports_lora()` on an instance of the same class, and no model sets `supports_lora` dynamically. Across all 390 loadable architectures, the class-level check also logs none of `supports_lora()`'s attribute-mismatch warnings.
- Cached model info from older versions lacks the new field; `_ModelInfo(**cached)` then raises, which `_load_modelinfo_from_cache` already catches, so the model is re-inspected.
- The runtime check in `LoRAModelRunnerMixin` is left in place.
- #61870 replaces the two asserts with `ValueError` in the constructors. That gives a clearer message, but it still runs inside EngineCore, so the user-facing error remains `Engine core initialization failed` (checked with the same reproducer). This PR moves the check to config validation, as the issue requests.
