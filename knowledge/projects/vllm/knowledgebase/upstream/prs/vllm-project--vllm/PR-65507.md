# [KVConnector] Enable LMCache MP connector for the extensible kv cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/65507) · state: open · merged: False

## Original PR description

## Overview

This enables the LMCache MP connector when using the extensible KV cache (introduced in #56492).

## Claims

LMCache MP is now runnable with the extensible KV cache with LMCache/LMCache#6266 (see the details below).

With `"lmcache.mp.use_vmm_api": true` in the `LMCacheMPConnector`'s own `kv_connector_extra_config` (directly or as a MultiConnector child), the extensible KV cache, on by default with the V2 model runner, is now enabled for it, and vLLM allocates it as POSIX-fd-exportable memory. All other configurations are unchanged, including every other extensible KV cache. The user-facing change is documented in the `--enable-extensible-kv-cache` help and in `examples/disaggregated/lmcache/README.md`.

Not a duplicate: no other open PR enables `LMCacheMPConnector` for the extensible KV cache. AI assistance (Claude Code) was used.

## Validation

### How to reproduce

Tested on 1× H200 (driver 580.105.08, torch 2.14.0+cu132) with Qwen/Qwen3-0.6B. LMCache must include the POSIX-fd channel for VMM memory (LMCache/LMCache#6266). The LMCache server and vLLM run on the same host and GPU, as the same user, and share `/dev/shm` (use `--ipc host` for containers).

**1. Start the LMCache MP server**

```bash
CUDA_VISIBLE_DEVICES=0 lmcache server \
  --host 127.0.0.1 --port 16555 \
  --http-port 18081 --prometheus-port 18092 \
  --l1-size-gb 8 --eviction-policy LRU --chunk-size 256
```

Expected log line: `LMCache fd channel listening on /dev/shm/lmcache_fd_16555.sock`

**2. Start vLLM with LMCache MP over VMM handles**

```bash
CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen3-0.6B \
  --port 18000 --max-model-len 8192 \
  --no-enable-prefix-caching \
  --max-num-batched-tokens 4096 \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_module_path":"lmcache.integration.vllm.lmcache_mp_connector","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":16555,"lmcache.mp.use_vmm_api":true}}'
```

- The extensible KV cache is on by default here. `--enable-extensible-kv-cache` makes the request explicit.
- `--no-enable-prefix-caching` makes repeated requests read their prefix from LMCache, not from vLLM's own prefix cache.
- `--max-num-batched-tokens 4096` splits the first request's prefill at the same 4096-token boundary as the LMCache hit, so greedy outputs can be compared exactly.

MultiConnector variant (the flag sits in the child's own config):

```bash
  --kv-transfer-config '{"kv_connector":"MultiConnector","kv_role":"kv_both","kv_connector_extra_config":{"connectors":[{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_module_path":"lmcache.integration.vllm.lmcache_mp_connector","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":16555,"lmcache.mp.use_vmm_api":true}}]}}'
```

**3. Send the same request three times**

```bash
PROMPT=$(python3 -c 'print(" ".join(f"Fact {i}: the number {i} squared is {i*i}." for i in range(220)) + " Summarize the pattern:")')
BODY=$(python3 -c 'import json,sys; print(json.dumps({"model": "Qwen/Qwen3-0.6B", "prompt": sys.argv[1], "max_tokens": 48, "temperature": 0}))' "$PROMPT")
for i in 1 2 3; do
  curl -s localhost:18000/v1/completions -H 'Content-Type: application/json' -d "$BODY" \
    | python3 -c 'import json,sys; print(repr(json.load(sys.stdin)["choices"][0]["text"]))'
done
curl -s localhost:18000/metrics | grep -E '^vllm:external_prefix_cache_(queries|hits)_total'
```

- njhill · comment · 2026-11-04T00:23:04Z · [source](https://github.com/vllm-project/vllm/pull/65507#discussion_r4462090712)

File: `vllm/utils/vmm_driver.py` · line None

This applies to every extensible KV cache allocation on CUDA, not just LMCache: `CudaVmmDriver` is a process-wide singleton and the extensible cache is on by default with MRV2. Only LMCache MP with `use_vmm_api` needs the FD handle; nothing else in vLLM exports this memory.

I don't expect this to break typical bare-metal setups, but the risk is untested and everyone else gets no benefit from it:
- If a device rejects the handle type, `vmm_unavailable_reason()` fails and `core.py` disables the extensible cache with a warning, even when it was explicitly requested. The server still starts, but the error is a bare driver message that doesn't point at this flag.
- That probe doesn't cover RDMA registration, so a problem with this flag plus `gpuDirectRDMACapable` on NIXL, Mooncake etc. wouldn't show up until registration. PyTorch's `expandable_segments` uses the same combination, so this may well be fine, but it isn't validated here.
- The existing code is more cautious: `cumem_allocator.cpp` and PyTorch both request fabric first on fabric-capable devices, and the cuMem allocator only uses POSIX as a fallback. This would be a default-on path requesting POSIX directly on those devices (e.g. GB200). PyTorch also [disabled these handle types in fbcode](https://github.com/pytorch/pytorch/pull/132890) after job failures, though no root cause is public.

Could this be requested only when `lmcache.mp.use_vmm_api` is set, e.g. an `exportable` option passed through `ExtensibleTensor` and `create()`? `vmm_unavailable_reason()` would need the same option so the probe tests the same properties. That would also match the LMCache PR's hint text, which says vLLM requests exportable memory when the flag is set.

Two compatibility issues with existing LMCache versions:

1. **The dependency isn't released.** This relies on LMCache/LMCache#6266, which is still open, while `requirements/kv_connectors.txt` allows `lmcache >= 0.5.6` and the CUDA 12 file pins `== 0.5.6`. v0.5.6 has no `fd_channel.py`, and its design doc says FD-kind wrappers fail at `to_tensor`. So this message points users at a setting that fails on those versions. I'd hold this PR until there's an LMCache release with the change and bump the minimum version.

2. **Upgrading can break a working setup.** `use_vmm_api: true` with the cuMem allocator on a fabric-capable device works with v0.5.6 through fabric handles. After this PR, `requested=None` resolves to on for that config, the allocation is POSIX-only, and registration fails on v0.5.6. LMCache's `isolated_ipc` is also affected, since its docs say POSIX-only pools are rejected at registration. Could the extensible cache require an explicit opt-in here, and/or request fabric first as the cuMem allocator does?

- njhill · comment · 2026-11-04T00:23:04Z · [source](https://github.com/vllm-project/vllm/pull/65507#discussion_r4462090746)

File: `vllm/config/kv_transfer.py` · line 59

Listing LMCache MP here makes sense for the padding and defragmenting, but the connector doesn't yet follow the remaps those other connectors handle. `LMCacheMPConnector` has no `unregister_kv_caches` / `restore_kv_caches`, so the calls before `release_physical()` in `gpu_worker.py` (sleep) and `extensible_kv_cache.py` (weight update) do nothing. `supports_sleep_mode` also defaults to `True`, so the config is accepted.

The LMCache PR documents the result: the server keeps the old chunks, so an H200 freed 2 GiB of a 136 GiB pool and then hit `CUDA_ERROR_OUT_OF_MEMORY` on `wake_up`. If the wake succeeds, I'd also expect a silent problem, though this is my inference: the server keeps reading and writing the old chunks while vLLM uses the new ones, so loads could produce wrong output with no error. The weight-update path matters because it can release the cache without sleep mode being enabled, and an extensible cache leaves little free memory by design. With MultiConnector, NIXL would re-register correctly while LMCache goes stale.

Could the connector implement those hooks? Otherwise, I think this config needs to reject sleep mode (`supports_sleep_mode` returning `False` when `use_vmm_api` is set) and guard the weight-update release.
