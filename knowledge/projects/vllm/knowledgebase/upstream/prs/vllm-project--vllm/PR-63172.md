# [Perf] Pad one-row BF16 lm_head GEMMs to two rows on GB10

[Upstream PR](https://github.com/vllm-project/vllm/pull/63172) · state: closed · merged: False

## Original PR description



## Overview

On GB10 (DGX Spark, sm_121), cuBLAS runs a **one-row** BF16 lm_head (`x[1, K] @ W[V, K]^T`) as a GEMV that reads the weight at ~175 GB/s. With two rows it uses a GEMM at ~235 GB/s, the memory-bandwidth limit. Single-request decode computes logits for exactly one row, so this PR pads that row to two in `UnquantizedEmbeddingMethod.apply`, on sm_121 only. Part of #63152.

## Claims

- lm_head GEMM at M=1 on GB10 is **1.32-1.38x faster** for every vocab x hidden shape tested (128k-262k vocab, hidden 2048-5120). For example, a 152k x 2048 head goes from 3.49 to 2.64 ms.
- Single-request decode of Qwen3-1.7B (BF16) on GB10: **47.7 → 50.1 tok/s (+5%)**. Two concurrent requests are unchanged (120 tok/s).
- No change on other GPUs: the gate is `is_device_capability(121)`. On H200 padding gives no gain (0.96-0.99x), so it stays off there.
- The output equals a two-row GEMM bit for bit. Against the unpadded GEMV, only the summation order differs (max abs diff 1.6e-2 on BF16 logits of magnitude ~1). Greedy outputs in the e2e check were identical.

## Validation

**Microbench** (`F.linear`, BF16, weights rotated across two copies, CUDA graph of 20 calls, median of 5; µs per call; `pad2` includes the `torch.cat` and slice):

| vocab x hidden | GB10 M=1 | GB10 M=1 pad2 | speedup | GB10 M=2 | H200 M=1 | H200 M=1 pad8 |
|---|---|---|---|---|---|---|
| 131072 x 2560 | 3,879 | 2,831 | 1.37x | 2,829 | 170 | 175 |
| 262144 x 2560 (Gemma 3) | 7,679 | 5,670 | 1.35x | 5,655 | 327 | 332 |
| 151936 x 2048 (Qwen3-1.7B) | 3,492 | 2,639 | 1.32x | 2,635 | 155 | 161 |
| 152064 x 3584 (Qwen2.5-7B) | 6,255 | 4,620 | 1.35x | 4,615 | 267 | 274 |
| 151936 x 5120 (Qwen3-14B) | 9,123 | 6,663 | 1.37x | 6,608 | 383 | 390 |
| 128256 x 4096 (Llama 3 8B) | 5,949 | 4,457 | 1.33x | 4,451 | 256 | 261 |

- On GB10, only M=1 is slow. M=2..8 already run at ~235 GB/s, and padding them to 8 is neutral to -2%. Padding M=1 to 2 rows beats padding to 4 or 8 by 0.5-1%.
- On H200, every M from 1 to 8 runs at ~4 TB/s already, and padding costs 1-4%.

**End to end** (Qwen3-1.7B BF16, offline `LLM.generate`, 128-token prompt, 512 output tokens, `ignore_eos`, best of 3; same node, alternating runs):

| GPU | c=1 before | c=1 after | c=2 before | c=2 after |
|---|---|---|---|---|
| GB10 | 47.6 / 47.8 / 47.8 | 50.0 / 49.9 / 50.2 | 120.2 / 120.3 / 120.7 | 120.1 / 120.5 / 120.8 |
| H200 NVL | (gate off) | 445.3 | | 891.0 |

Before and after produced the same greedy token ids. Padding every one-row BF16 GEMM in the model, not only the lm_head, gave the same 50.0 tok/s, so the change stays limited to the lm_head.

**Test**: `tests/model_executor/test_lm_head_single_row_pad.py`. With the gate forced on, M=1 must equal a two-row GEMM bit for bit and match the unpadded GEMV within BF16 tolerance; M=2 and M=5 must be unchanged bit for bit; shape and dtype are preserved. It passes on GB10 and H200. `pre-commit` passes.

## Details

- **Where.** `UnquantizedEmbeddingMethod.apply` is the unquantized lm_head path. The batch-invariant branch and the fp32 `head_dtype` path come before it and are not affected. Quantized lm_heads are not touched.
- **Gate.** sm_121 (GB10) is the only measured device that shows the problem. sm_120 (RTX 50xx / RTX PRO 6000) was not measured; it can be added if it shows the same GEMV choice. The check is `functools.cache`d.
- **Cost.** One `torch.cat` of a [1, hidden] row per decode step. This runs outside CUDA graphs (`compute_logits`) and does not sync.
- **Out of scope:** model-specific heads that bypass `UnquantizedEmbeddingMethod`.

Closing this. The root cause is a cuBLAS heuristic choice on sm_121 (a one-row BF16 GEMV at ~175 GB/s where the two-row GEMM reaches ~235 GB/s), so the right fix is in cuBLAS rather than a device-specific special case in the shared lm_head path that also changes the summation order of the default logits.
