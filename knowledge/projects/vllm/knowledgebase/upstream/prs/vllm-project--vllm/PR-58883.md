# [Bugfix][Quantization] Name the layer when a MoE expert weight is unquantized

[Upstream PR](https://github.com/vllm-project/vllm/pull/58883) · state: open · merged: False

## Original PR description

## Purpose

A ModelOpt checkpoint can store a MoE submodule unquantized while leaving it out of the
quantization exclude list. The layer is then built for packed low-precision weights and the
weight loader is handed a floating point tensor of the logical width, so the load dies inside
`Tensor.copy_` with a message that names neither the layer nor the cause:

```
RuntimeError: The size of tensor a (256) must match the size of tensor b (512) at non-singleton dimension 1
```

The two numbers differ by exactly 2, which is the FP4 packing factor, but it reads like a
tensor-parallel sharding bug. The ratio is identical at every TP size, so the obvious
experiment (change `--tensor-parallel-size`) costs a full model load and proves nothing. The
traceback ends in a generic loader and names no module, so there is nothing to grep for.

This PR raises a targeted error instead. The check only fires where `copy_` would already
fail, so no configuration that loads today changes behaviour.

### The checkpoint that prompted it

`nvidia/GLM-5.3-Flash-NVFP4` has `num_hidden_layers: 45` and `num_nextn_predict_layers: 1`, so
layer 45 is the MTP layer. Reading the safetensors headers, layer 45 is unquantized and layer
44 is not:

| tensor | layer 44 | layer 45 |
| --- | --- | --- |
| `mlp.experts.0.gate_proj.weight` | `U8 (2048, 2048)` | `BF16 (2048, 4096)` |
| `mlp.experts.0.gate_proj.weight_scale` | `F8_E4M3 (2048, 256)` | absent |
| whole-layer dtypes | 864 `U8` + 864 `F8_E4M3` | 888 `BF16` + 1 `F32` |

`quantization_config.ignore` has 132 entries covering layers 0 to 44 and nothing matching
layer 45, so `is_layer_excluded()` returns False and the experts are built NVFP4. The
checkpoint's own `.quant_summary.txt` lists layer indices 0 to 44 only, so ModelOpt never
processed the MTP layer. Adding a pattern for that layer to the exclude list makes the config
describe the weights, and the model then serves with MTP at 75% draft acceptance.

For comparison, `nvidia/DeepSeek-R1-0528-FP4` avoids all of this because its `exclude_modules`
excludes `model.layers.61*` wholesale, which covers its MTP layer.

### Why the message mentions module paths

The exclude pattern is matched against the vLLM module path. `Glm5NextMTP` builds the MTP layer
as its own text-only model rooted at `model`, so its experts are `model.layers.45.mlp.experts`,
while the checkpoint spells the target model `model.language_model.layers.*`.
`Glm5NextForConditionalGeneration` defines no `hf_to_vllm_mapper`, so `apply_vllm_mapper()`
never bridges the two and a pattern written in checkpoint spelling cannot match. The error says
so, because that difference is not obvious from the checkpoint.

### Scope

Same class as #49539, which keeps unquantized routed experts unquantized under AutoGPTQ. That
PR changes behaviour for one quantization backend; this one only improves the diagnostic, and
deliberately does not add a silent fallback, since building a layer differently from what the
config declares would change numerics and memory without the user asking for it. #52501 added
an equivalent NaN sentinel with an actionable message for the linear case; this follows that
precedent for the MoE case.

## Test Plan

```bash
pytest -q tests/kernels/moe/test_moe_unquantized_expert_weight_error.py
```

End to end on 4x B300, `v0.30.0` plus this patch, against the checkpoint above:

```bash
vllm serve nvidia/GLM-5.3-Flash-NVFP4 \
  --tensor-parallel-size 4 --kv-cache-dtype fp8 --max-model-len 262144 \
  --trust-remote-code \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

## Test Result

`7 passed`. The suite covers the raising case plus five that must stay silent: both sides
floating point, shapes already matching, an already-packed checkpoint tensor, and
float8/float16/float32 destinations.

Before, on every rank at ~140 s:

```
  File ".../vllm/v1/worker/gpu/spec_decode/eagle/utils.py", line 111, in load_eagle_model
  File ".../vllm/models/glm5next/nvidia/mtp.py", line 385, in load_weights
  File ".../vllm/model_executor/layers/fused_moe/routed_experts.py", line 755, in weight_loader
  File ".../vllm/model_executor/layers/fused_moe/routed_experts.py", line 350, in _load_model_weight_or_group_weight_scale
  File ".../vllm/model_executor/layers/fused_moe/routed_experts.py", line 541, in _load_w2
    expert_data.copy_(loaded_weight)
RuntimeError: The size of tensor a (256) must match the size of tensor b (512) at non-singleton dimension 1
```

After, same image and same run:

```
ValueError: Expert weight for layer 'model.layers.45.mlp.experts' is torch.bfloat16
(4096, 512) in the checkpoint, but the layer was built for packed torch.uint8 (4096, 256)
weights. The checkpoint stores this module unquantized without listing it in the
quantization exclude list, so add a pattern that matches it. The pattern is matched
against the vLLM module path, which can differ from the checkpoint path (a
multi-token-prediction layer is built as its own model and so loses any parent prefix).
```

Serving the same checkpoint without `--speculative-config` is unaffected, before and after.
