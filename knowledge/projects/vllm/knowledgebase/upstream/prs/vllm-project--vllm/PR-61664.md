# fix(mamba): prune broken sm90 triton autotune configs in ssd_chunk_scan (#61603)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61664) · state: closed · merged: False

## Original PR description

fixes #61603

### description

on sm90 (hopper), triton 3.2-3.6 software pipelining codegen bug emits invalid pipelined instructions in `_chunk_scan_fwd_kernel` for configs satisfying:
`BLOCK_M >= 64 and BLOCK_N >= 64 and num_warps == 4 and num_stages >= 2` (8 configs)

because vllm autotunes at startup and caches the picked cubin, fresh server instances randomly pick one of these 8 configs, causing intermittent and persistent stretches of nan rows and endless `<unk>` token generation.

this pr prunes those 8 configs when running on sm90 platforms (and registers `early_config_prune` to guard dynamic autotune passes), while keeping the other 15 clean configs across all warp and tile shapes.

also updates `TritonPlaceholder.Config` so dummy configs preserve their kwargs on non-gpu/cpu platforms, and adds unit test coverage in `tests/kernels/mamba/test_ssd_chunk_scan_configs.py`.

Confirming from the original issue's environment (H20-3e, sm90; vLLM 0.19.1, Triton 3.6.0): we swept all 23 autotune configs of _chunk_scan_fwd_kernel individually — each config run in a fresh process, 100 replay reps against a captured input bundle that had produced NaN. The configs that produced NaN were exactly the 8 matching BLOCK_M >= 64 && BLOCK_N >= 64 && num_warps == 4 && num_stages >= 2 — identical to this PR's predicate — and every other config was 0/100, including the two BLOCK_N == 32 configs that the broader filter in #61718 also drops.

Caveat: 100 reps can't rule out rarer failures, so the N==32 configs being clean here doesn't contradict the register-conflict theory in #61718 — it just bounds what we observed. Full sweep details in the comment I left on #61718.
