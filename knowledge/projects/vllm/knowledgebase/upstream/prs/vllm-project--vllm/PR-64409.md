# [Perf][Core] Bound block-hash slices to newly cached blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64409) · state: open · merged: False

## Original PR description

Limit cache_full_blocks() to materializing hashes in [num_cached_blocks, num_full_blocks), rather than the entire remaining request. Chunked prefill otherwise repeatedly copies unused hashes and, when group blocks are coarser than hash blocks, resolves unused view entries. Cache registration and event contents remain unchanged.

Extend test_cache_blocks from 2 to 8 parameter combinations:
- SHA-256 and SHA-256/CBOR.
- Hash block sizes 2 and 4 with a cache block size of 4, exercising both direct hash lists and coarser block-size views.
- KV events enabled and disabled.
- Exact hashes across successive chunks, lookup misses before the next chunk is cached, and event token ranges and parent hashes. Allocate the test blocks through the real BlockPool.

Validation:
- Directly invoked all 8 combinations and 4 existing multi-group/event cases on both baseline and optimized source: 12 assertion cases passed on each. This does not execute pytest's fixture setup/teardown.
- Attempted normal pytest collection/execution with: uv run --offline --no-project .venv/bin/python -m pytest \ tests/v1/core/test_prefix_caching.py -k test_cache_blocks -v It selected 9 cases; the first case's assertions passed, then the global cleanup fixture crashed in torch.accelerator.empty_host_cache() with exit 139. A PyTorch-only reproducer also crashes with torch 2.14.0 on this macOS host, both inside and outside the sandbox. The pytest suite is not reported as passing. No cleanup bypass or skip was added.

Quantification (isolated CPU harness, macOS ARM64, Python 3.12.16):
- Extracted the actual baseline and optimized cache_full_blocks() and _insert_block_hash() methods; KV events disabled, hash block size 16, 1024-token chunks, one cache group. Timed cumulative registration for one full prompt, excluding request/block construction and hash creation.
- Medians of 15 samples per version, after warmup, with alternating order:
```
  Prompt tokens | Group block size | Before ms | After ms | Time saved
          65536 |               16 |    2.2830 |   2.0126 |      11.8%
          65536 |               64 |    2.9512 |   0.6226 |      78.9%
         131072 |               16 |    5.2856 |   4.0857 |      22.7%
         131072 |               64 |   10.5651 |   1.2592 |      88.1%
```
For 65536 tokens and 16-token blocks, cumulative sliced hash references fall from 133120 to 4096 (32.5x fewer). A single-chunk 1024-token prompt showed no meaningful timing change (0.0320 vs 0.0322 ms). These are local CPU registration measurements, not end-to-end serving or GPU speedups. No model evaluation, build, or formatting checks were run.
