# [MooncakeStore] Report KV load tier in cache events

[Upstream PR](https://github.com/vllm-project/vllm/pull/52731) · state: open · merged: False

## Original PR description

## Purpose

Report the actual MooncakeStore replica tier in KV cache events.

Mooncake already exposes whether a loaded replica is memory-backed or disk-backed, but this information was not propagated to `BlockStored` events. This change maps:

* memory-backed replica → `CPU`
* disk-backed replica → `STORAGE`
* unknown tier → `None`

Successful events are emitted only for blocks that actually load successfully. Scheduler lookup and connector protocol behavior are unchanged.

Validated:

* memory-backed replicas map to `CPU`
* disk-backed replicas map to `STORAGE`
* unknown tier leaves `medium` unset

* replica-tier lookup is skipped when both KV events and tier logging are disabled
* block hashes remain correctly aligned through rotation and disk-budget splitting

### Integration smoke test

Ran vLLM with MooncakeStore on an A100 using a 256 MB embedded Mooncake segment.

A real Mooncake-backed reload reported:

```text
batch_keys=35
memory_keys=35
disk_keys=0
unknown_keys=0
success_keys=35
failed_keys=0
bytes_by_tier={'memory': 82575360, 'disk': 0, 'unknown': 0}
```

This confirms that the runtime replica metadata path correctly identifies real memory-backed loads.

Disk persistence was also exercised successfully, but a disk-only reload could not be observed with the embedded-store setup because the in-memory replica remains available. A true disk-backed reload would require a standalone-store configuration.

The focused unit tests directly validate the disk-replica → `STORAGE` event mapping.

- vMaroon · CHANGES_REQUESTED · 2026-10-17T08:52:38Z · [source](https://github.com/vllm-project/vllm/pull/52731#pullrequestreview-5557100790)

I think a load is the wrong trigger for `BlockStored`. Loading from Mooncake reads an existing object, it does not add a copy, and the GPU prefix cache already announces the `GPU` copy of the loaded blocks when the scheduler commits them. Under the per-copy refcounting consumers use (hash, `medium`, `group_idx`, ...), each load adds a reference that no `BlockRemoved` ever withdraws, so the index tracks load frequency rather than residency.

The tier signal itself is useful. Wonder if we could keep it out of the event stream at load time and instead carry it where the copy is created: the send path, where Mooncake residency is announced today. That is being reworked in #58293 and #60887 (which also removes `update_kv_event`, so this PR would need to move anyway), so might be worth coordinating there. For load-time visibility, `VLLM_MOONCAKE_STORE_TIER_LOG` plus the connector stats already cover it.

If we do keep load events, a few things need to be true first:
- `token_ids` must be a list. Every load job has `token_ids=None` because `ReqMeta.from_request_tracker` forces `skip_save` when `can_load`, and llm-d's decoder rejects the whole batch on a nil `token_ids`, so GPU events in the same batch are dropped too.
- `medium` must match the send path. The send path publishes `"cpu"` and this publishes `"CPU"`/`"STORAGE"`, so Dynamo (uppercase only) and llm-d (lowercases) end up with different views of the same connector.
- Unknown tier should not map to nil `medium`: both llm-d and Dynamo read nil as the GPU tier, so a failed `batch_get_replica_desc` announces a GPU copy that does not exist.
- The receive path on main now builds one key per store shard (`store_layout.local_shard_ids`), so events need dedup by logical block the way the send path does it.

The parent-chain, replica-selection and TP-aggregation issues yokinoshitayoki raised also still apply.
