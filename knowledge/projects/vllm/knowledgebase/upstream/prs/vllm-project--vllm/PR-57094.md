# [Bugfix][Attention] Avoid NaN from empty seq_len in Triton MLA decode (CUDA graph pad)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57094) · state: open · merged: False

## Original PR description

## Purpose

Fixes #57017

DeepSeek-V2-Lite with `--quantization fp8` on sm89 (`TRITON_MLA`) returns NaN logits for every request once three or more sequences share one CUDA-graph decode batch. Eager / `cudagraph_mode: NONE` are fine; `--max-num-seqs 2` sidesteps it.

### Root cause

1. Default CUDA-graph capture sizes are `[1, 2, 4, 8, ...]`, so a 3-sequence decode batch is padded to 4. Inactive pad slots get `seq_lens=0` (and `NULL_BLOCK_ID` in the block table).
2. `triton_decode_attention` stage2 always did `acc / e_sum`. For `seq_len=0`, stage1 writes nothing and `e_sum` stays 0, so the pad row becomes `0/0 = NaN`.
3. Online FP8 MoE (`Fp8PerTensorOnlineMoEMethod`) quantizes expert activations with a **per-tensor** dynamic scale (`kFp8DynamicTensorSym`), i.e. `amax` over the whole batch. One pad NaN makes the scale NaN and poisons every co-batched request.

Dense Cutlass FP8 linears use per-token scales, so they would not amplify a pad NaN the same way; the MoE path is what turns a pad-slot NaN into batch-wide NaN logits.

## Softcap PR

#56579 (Triton softcap overflow) is unrelated; DeepSeek MLA does not use `logits_soft_cap` on this backend.

## Test Plan

```bash
pytest tests/kernels/attention/test_triton_decode_attention.py -k zero_seq_len_pad_no_nan -v
```

New test: batch of 3 active rows + 1 `seq_len=0` pad (MLA / GQA / MHA). Asserts no NaN/Inf, pad outputs are zero, and active rows match an unpadded run.

## Test Result

Verified on NVIDIA RTX 2000 Ada (CUDA 12.8, torch 2.8.0+cu128):

```

# 3 passed, 115 deselected in 2.90s
```

All three `test_decode_attention_zero_seq_len_pad_no_nan[...]` parametrizations passed.
