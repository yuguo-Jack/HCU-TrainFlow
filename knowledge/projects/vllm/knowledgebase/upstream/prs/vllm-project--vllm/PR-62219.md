# [Kernel][Perf] Add H100 tuned configs for Llama-3.1-8B and Qwen3-8B to the batch-invariant matmul table

[Upstream PR](https://github.com/vllm-project/vllm/pull/62219) · state: open · merged: False

## Original PR description

## Overview

In short: in batch-invariant (BI) mode (`VLLM_BATCH_INVARIANT=1`), every bf16 linear layer and the lm_head run the Triton kernel `matmul_kernel_persistent` instead of cuBLAS. Its tile comes from a per-GPU table, and the Hopper table only has the five Qwen3-1.7B shapes (measured on an H20), so Llama-3.1-8B and Qwen3-8B run the default 128x128x64 tile on H100. This PR adds H100-measured entries for their 8 TP=1 shapes to the `"hopper"` family.

With BI on, on an H100 SXM:
- `vllm bench latency` is 1.85-2.79x faster than main.
- The BI tax (latency with BI on / latency with BI off) drops from 2.13-2.99x on main to 1.03-1.20x with this PR.
- GSM8K stays within 0.5 standard error (SE) of main.

Related: tracker [#27433](https://github.com/vllm-project/vllm/issues/27433), same kind of table as [#53247](https://github.com/vllm-project/vllm/pull/53247), [#57456](https://github.com/vllm-project/vllm/pull/57456), [#58495](https://github.com/vllm-project/vllm/pull/58495).

## Key results

- 8 new `(N, K)` entries in `_BATCH_INVARIANT_MATMUL_TUNED_CONFIGS["hopper"]`: gate_up/down/lm_head of Llama-3.1-8B and Qwen3-8B plus their shared qkv/o. Existing entries and other families are not touched.
- One `BLOCK_K` per shape, so a row's K-reduction order does not depend on M. Checked bit for bit through the real `matmul_persistent` dispatch: 2028/2028 cases identical.
- Kernel (H100 SXM, cold L2): geomean 2.03x vs main over 80 (shape, M) cases, 2.89x at M <= 64; the slowest case is 1.00x (Qwen3 gate_up at M=2048, 827 vs 828 us). At M <= 64 the kernel is now 0.90-1.12x of cuBLAS time (main: 1.48-4.09x).
- E2E latency with the flag on (fresh process per run, 2 interleaved rounds):

| model, workload | BI=0 (s) | BI=1 main (s) | BI=1 this PR (s) | PR vs main | BI tax main -> PR |
|---|---|---|---|---|---|
| Llama-3.1-8B, 32 in / 128 out, bs 8 | 0.854 | 2.452 | 0.881 | 2.78x | 2.87x -> 1.03x |
| Llama-3.1-8B, 1024 in / 32 out, bs 8 | 0.403 | 0.859 | 0.444 | 1.94x | 2.13x -> 1.10x |
| Qwen3-8B, 32 in / 128 out, bs 8 | 0.893 | 2.668 | 0.956 | 2.79x | 2.99x -> 1.07x |
| Qwen3-8B, 1024 in / 32 out, bs 8 | 0.414 | 0.917 | 0.495 | 1.85x | 2.22x -> 1.20x |

- `vllm bench serve` (1024 in / 128 out, 1000 prompts, rate inf, 3 interleaved rounds, req/s; rounds 1 / 2 / 3, then the mean). Llama-3.1-8B gains 13.6%. Qwen3-8B does not change; Details explains why (the execution mode these shapes switch on, not the tiles).

## Validation

**Setup.**
- GPU: 1x H100 80GB HBM3 SXM, 132 SMs, power limit 700 W of 700 W.
- Software: driver 595.91.07, CUDA 13.0, torch 2.14.0+cu130, triton 3.8.0.
- main = 307c5844ad. PR = main + this commit, applied on the box with `git am` (same diff).
- main and PR are the same checkout, switched with `git checkout`. Every run is a fresh process.
- Llama-3.1-8B-Instruct checkpoint: `unsloth/Llama-3.1-8B-Instruct`, an ungated copy. It has the same architecture and layer shapes as `meta-llama/Llama-3.1-8B-Instruct`; its config.json adds `pad_token_id`. I did not compare the weights against the gated repo.
- [#61118](https://github.com/vllm-project/vllm/pull/61118) merged after this base. It enables Inductor's `batch_invariant` flag. It can only change the torch.compile arms (main, and PR + torch.compile under Details). It does not change this PR's default breakable-graph mode, because that mode does not run Inductor.

**Bitwise.**
- Path: `matmul_persistent` on the PR tree, all 13 hopper shapes.
- Check: a probe row at rows 0, M/2 and M-1 must equal the same row computed at M=1.
- M values (39): 1-17, every bucket edge ±1, 100, 1000, 3000 and 4096.
- 2 seeds. Weight as `w.t()` (the linear layout) and as a contiguous `(K, N)` tensor.
- Result: 2028/2028 identical, 0 mismatched.

## Details

**These shapes also change the execution mode.**
- Since [#57586](https://github.com/vllm-project/vllm/pull/57586), BI mode checks the model's qkv/o/gate_up/down shapes against the device's table.
- If one shape is in the table (bf16, unquantized, CUDA, not `enforce_eager`, `VLLM_USE_BREAKABLE_CUDAGRAPH` unset), the model runs with breakable CUDA graphs and without torch.compile.
- In that mode the tile is looked up from the runtime M. Under torch.compile the lookup is frozen to one tile at trace time ([#54243](https://github.com/vllm-project/vllm/issues/54243)).
- So this PR moves Llama-3.1-8B and Qwen3-8B to breakable graphs, in addition to the new tiles.

To separate the two effects, I ran two extra arms, 1 round each (raw output in the "mode diagnostic" dropdown under Validation):
- main + breakable graphs (`VLLM_USE_BREAKABLE_CUDAGRAPH=1`): the mode change only.
- PR + torch.compile (`VLLM_USE_BREAKABLE_CUDAGRAPH=0`): the new tiles. qkv/o/gate_up/down are frozen to one tile; lm_head runs outside the compiled forward and keeps the per-M lookup.

| model | arm | latency 32/128 (s) | latency 1024/32 (s) | serve (req/s) |
|---|---|---|---|---|
| Llama-3.1-8B | main | 2.452 | 0.859 | 21.64 |
| Llama-3.1-8B | main + breakable graphs | 2.423 | 0.856 | 21.34 |
| Llama-3.1-8B | PR + torch.compile | 1.824 | 0.667 | 24.81 |
| Llama-3.1-8B | PR (default: breakable graphs) | 0.881 | 0.444 | 24.59 |
| Qwen3-8B | main | 2.668 | 0.917 | 21.48 |
| Qwen3-8B | main + breakable graphs | 2.639 | 0.926 | 20.30 |
| Qwen3-8B | PR + torch.compile | 2.120 | 0.763 | 22.66 |
| Qwen3-8B | PR (default: breakable graphs) | 0.956 | 0.495 | 21.48 |

What the table shows:
- The gain comes from the tiles. Breakable graphs alone change latency by about 1%.
- Per-M tile selection makes decode fast: 0.881 s, against 1.824 s with one frozen tile.
- In all four latency workloads, breakable graphs win by 1.5-2.2x.
- In the prefill-heavy serve workload, torch.compile wins:
  - Dropping Inductor costs 5.5% on Qwen3-8B and 1.4% on Llama-3.1-8B.
  - With breakable graphs, the new tiles only win back that 5.5% on Qwen3-8B.
  - PR + torch.compile is ahead by 5.5% (Qwen3-8B) and 0.9% (Llama-3.1-8B), 1 round each.
- This trade-off comes from the [#57586](https://github.com/vllm-project/vllm/pull/57586) gate, not from these entries. I did not change the gate.
- With this table, `VLLM_USE_BREAKABLE_CUDAGRAPH=0` gives Qwen3-8B serving +5.5% over main.

**How the entries were picked.**
- Search space and BLOCK_K rule are the same as [#57456](https://github.com/vllm-project/vllm/pull/57456):
  - BLOCK_K {32, 64, 128} x BLOCK_M {16, 32, 64, 128} x BLOCK_N {32, 64, 128, 256} x warps {4, 8} x stages {2, 3, 4, 5}.
  - Timed at M in {1, 4, 8, 16, 32, 64, 256, 512, 1024, 2048}.
  - One BLOCK_K per shape, by the decode-weighted score. Then the fastest tile per bucket with that BLOCK_K.
- Two differences from [#57456](https://github.com/vllm-project/vllm/pull/57456):
  - Cold-L2 timing. Each point is a CUDA graph that cycles over enough copies of `(x, w)` to read >= 4x L2 per pass. o (32 MB) and qkv (48 MB) fit in the 50 MB L2, so warm timing would make them look faster than in the model.
  - The bitwise gate runs on all 10 buckets, not 4. A probe row at rows 0, M/2 and M-1 must equal the M=1 output.
- Before the gate, the top 3 configs per (bucket, BLOCK_K) were re-timed over 5 interleaved passes.
- Margins:
  - 43 of 80 picks beat the runner-up by more than the pass-to-pass spread.
  - The other 37 are within the spread. 20 of them are within 1%. The rest are at M >= 256, where the spread is larger.
  - Every pick is faster than main's default tile. In 77 of 80 buckets the margin is larger than the spread; the other 3 are 1.04-1.07x.
- Result: BLOCK_K = 64 for Llama gate_up, 128 for the other 7 shapes.

**Not a duplicate.**
- [#60034](https://github.com/vllm-project/vllm/pull/60034) (draft) tunes five other Hopper shapes (17408x5120, 5120x8704, 8192x5120, 5120x3072, 124160x5120) for M <= 16. No overlap.
- [#54503](https://github.com/vllm-project/vllm/pull/54503) and [#55752](https://github.com/vllm-project/vllm/pull/55752) change how the M bucket is selected at runtime. They work with any table entries.
- [#59952](https://github.com/vllm-project/vllm/pull/59952) (split-K for N <= 64) replaces the table lookup in `matmul_persistent` with a fixed heuristic. If it lands as written today, these entries and the existing Ada/Hopper/Blackwell/SM120 entries no longer set the tile. The [#57586](https://github.com/vllm-project/vllm/pull/57586) gate still reads the table, so they would still switch the execution mode.
- [#53446](https://github.com/vllm-project/vllm/pull/53446) (closed) proposed H100 NVL configs for the Qwen3-1.7B shapes already in the table. This PR adds new shapes only. It does not change existing entries.

**Limitations.**
- Measured on H100 SXM only. The `"hopper"` key also covers H100 PCIe/NVL, H200, H800 and H20. For these shapes they run the default tile today. I have not measured them.
- With these entries, the jit monitor logged at most one `matmul_kernel_persistent` compile per process. In latency and serve runs it came during warmup, never in a measured iteration (none in the Llama decode latency runs). In lm_eval, which has no warmup, it came on the first request; that changes timing only, not scores. main logged none.
- TP > 1 per-rank shapes are not included.
- The table and the [#57586](https://github.com/vllm-project/vllm/pull/57586) gate use only `(N, K)`. Other bf16 models with the same shapes also get these tiles and the mode change. Example: Mistral-7B-v0.3 has exactly the layer shapes of Llama-3.1-8B. I have not measured those models.
- CI: the H100 Batch Invariance job runs `test_batch_invariance.py` (Qwen3-1.7B, plus needle tests on DeepSeek-V2-Lite and Qwen3-30B-A3B-FP8) and the RMSNorm and LoRA-shrink tests. It does not run `test_matmul_batch_invariant.py`, and none of its models use these shapes. So only the validation above covers these entries.
