# [Bugfix][MoRIIO] Preserve WRITE receive mappings after consumer abort

[Upstream PR](https://github.com/vllm-project/vllm/pull/59058) · state: open · merged: False

## Original PR description

## Overview

Fix a KV block leak on the MoRIIO WRITE consumer (D) when a request is aborted while waiting for remote KV. Related: #56089 fixes scheduler-side transfer accounting. This PR keeps the MoRIIO consumer mapping that the late completion needs.

## Claims

- An aborted WRITE receive keeps its `transfer_id` mapping until `finished_recving`, so a late `write_done` still frees its blocks.
- A non-streaming client abort also sends a rejection notice under a new request id with the same `transfer_id`. If another in-flight receive still owns that transfer, the notice is ignored: it neither unmaps the transfer nor releases the prefill blocks. A rejection with no live owner still releases them.

## Details

When D is aborted in `WAITING_FOR_REMOTE_KVS`, the scheduler holds its blocks until the receive finishes. The connector removed the transfer mapping at abort time, so the late `write_done` matched nothing and the blocks leaked. Tracking is now limited to WRITE receives with `do_remote_prefill` and external tokens.

Limitation: if P is also cancelled and never sends `write_done`, D still holds the request and its blocks. This PR adds no consumer timeout, because a timeout alone would not make the blocks safe to reuse.

- tjtanaa · comment · 2026-11-02T03:36:07Z · [source](https://github.com/vllm-project/vllm/pull/59058#discussion_r4438703112)

File: `vllm/distributed/kv_transfer/kv_connector/v1/moriio/moriio_connector.py` · line 1618

This misses one path, which I reproduced on MI355X over xGMI: a non-streaming client abort still leaks the blocks. A streaming abort frees them correctly.

When a non-streaming request raises or returns an error, `_with_kv_transfer_rejection_cleanup` (`vllm/entrypoints/generate/base/serving.py`) calls `notify_kv_transfer_request_rejected`, which submits a pre-aborted request with a new id and the same `transfer_id`. Its request_finished lands in this else branch, and unmap_request_id's transfer-id fallback removes the mapping you are retaining. The late write_done then has nothing to match. The log shows MoRI-IO unmap via transfer_id: '9cb85e907a15f4ec' -> 'cmpl-…'.

Could you ignore a notice for a transfer that a finished request still owns? This fixed it in my GPU runs (non-streaming abort, and a request failed by #58962's watchdog):

```
if not self.is_producer:
    owner = self.transfer_id_to_request_id.get(
        params.get("transfer_id") if params else None
    )
    if owner != request_id and owner in self._write_recvs_in_flight:
        # Rejection notice for a transfer a finished request still owns.
        return False, None
```

Returning here also keeps it from reaching `_release_write_prefill_blocks`, which could otherwise release a prefill that is still writing when the address is in the params. Please add a regression case: after the abort, call `request_finished` with a second request carrying the same `transfer_id`, then deliver the late `write_done` and assert the blocks are back.
