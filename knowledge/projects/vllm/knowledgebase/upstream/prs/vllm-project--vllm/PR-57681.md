# [Bugfix] fused_qk_norm_rope: partial rotary neox path shuffled from a divergent branch

[Upstream PR](https://github.com/vllm-project/vllm/pull/57681) · state: open · merged: False

## Original PR description

## Purpose

`fused_qk_norm_rope` with `rotary_dim < head_dim` (partial rotary, e.g. GLM-4 / GLM-4.5 with `partial_rotary_factor=0.5`) only lets `rotary_lanes = rotary_dim / elems_per_lane` lanes into the RoPE branch. The neox path then calls `__shfl_xor_sync` / `__syncwarp` inside that branch with a full-warp mask, i.e. from a divergent branch where the mask names lanes that never arrive. That is undefined behaviour. With the single-head kernel it happens to produce the right values; with the N-token-heads kernel (`token_heads_per_warp > 1`, auto-selected on SM90 once `num_tokens * (num_heads + num_kv_heads) >= 10240`) it returns garbage or NaN on H200 for such layers.

## Changes

Do the warp exchange once before the lane guard with the whole warp participating; only the rotary lanes use the exchanged values. Same for both kernels. The `__syncwarp()` calls around the shuffle are no longer needed (the shuffle itself synchronises the participating lanes).

## Test plan

Standalone build of this file on H200 against a vLLM 0.28.0 install, compared with that install's `fused_qk_norm_rope`:

- full rotary (`rotary_dim == head_dim`) and all gptj/interleaved cases: bitwise identical to the shipped kernel before and after (bf16/fp16, head_dim 64/128/256, 1–8192 tokens, `token_heads_per_warp` 1/2/4/8).
- partial rotary, neox, e.g. hq32/hkv8/d128 with `rotary_dim=64`: shipped kernel at 300 tokens differs from the fp32 reference by up to 2.9, and is NaN at 2048/8192 tokens; the fixed kernel is finite and matches the fp32 reference at every size (and is still bitwise identical to the shipped kernel wherever `token_heads_per_warp == 1`).

## Rebase note (2026-10-19)

Rebased onto main after #60721 moved the kernel from `csrc/libtorch_stable/` to `csrc/fused_qknorm_rope_kernel.cu`; the change is identical, only the path moved. The `__shfl_xor_sync` inside the `laneId < rotary_lanes` guard is still present on main (both kernels), so the fix still applies.
