# [Perf][Frontend] Serialize multimodal render responses directly

[Upstream PR](https://github.com/vllm-project/vllm/pull/58660) · state: open · merged: False

## Original PR description

## Purpose

`/render` returns preprocessed multimodal features as large JSON strings. For a four-image Qwen3-VL request, the response is 57.7 MB. The current `JSONResponse(content=result.model_dump())` materializes a Python dictionary and then encodes it using the standard JSON encoder; 75.1% of inclusive samples in the baseline profile fell under `json/encoder.py`.

Serialize successful `GenerateRequest` responses directly with Pydantic's `model_dump_json()`. Use a `TypeAdapter` for the list returned by completions render. Keep error responses, status codes, content type, schemas, and every render endpoint's `response_model` unchanged. This only changes serialization; it does not remove or defer image preprocessing or alter the wire payload.

## Validation

On one AutoDL A800 host with a 14-core CPU cgroup quota, vLLM 0.29.0 wheel, Qwen3-VL-2B-Instruct, a GPU-less render server, four 720p JPEGs per request, and 3 requests/s for 20 seconds (60/60 HTTP 200 responses each run):

| | Baseline | Patched run 1 | Patched run 2 |
| --- | ---: | ---: | ---: |
| Client p95 | 388.8 ms | 193.0 ms | 196.1 ms |
| Render process CPU time | 20.20 s | 9.01 s | 9.20 s |

The p95 improvement was 49.6–50.4% and process CPU time fell 54.5–55.4%. The original and patched responses parsed to identical JSON after removing only random `request_id` values for both multimodal chat render and two-prompt completions render. A real GPU-backed Qwen3-VL request returned HTTP 200 from the patched render endpoint and successfully generated a description through `/v1/chat/completions`.

Three focused serialization tests passed against the patched router after failing against the original. All applicable pre-commit hooks passed for the changed files, including Ruff, mypy 3.10 and test tethering; the manual mypy 3.12 hook and `git diff --check` also passed. The full current-main render test suite was not run because the remote executable was a 0.29.0 wheel, not an editable build of main. The live HTTP A/B uses that wheel with only the candidate router substituted, so the benchmark is evidence for this hot path rather than a whole-main performance claim.

The load driver sent deterministic four-image JPEG requests over loopback at a fixed 3 RPS. Reported percentiles are client-observed body-read latencies; CPU time is the render process's `/proc` user+system tick delta divided by `CLK_TCK=100`. The two patched runs and one baseline run are single-host measurements, not a cluster throughput claim.

## Relation to existing work

This work was motivated by [llm-d-router #2685](https://github.com/llm-d/llm-d-router/issues/2685). It is not a duplicate of #46722: that RFC moves multimodal tensor preprocessing and addresses transfer size. This PR keeps the current payload and reduces JSON encoding CPU. It is also distinct from #58314, which optimizes ordinary completion responses in `vllm/entrypoints/openai/completion/api_router.py`; this PR changes `vllm/entrypoints/scale_out/render/api_router.py`. Open-PR searches for the issue and render JSON serialization found no equivalent open PR.
