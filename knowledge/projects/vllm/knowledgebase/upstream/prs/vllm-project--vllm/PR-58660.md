# [Perf][Frontend] Share orjson responses across render and pooling

[Upstream PR](https://github.com/vllm-project/vllm/pull/58660) · state: closed · merged: True

## Original PR description

## Overview

Use shared `create_json_response()` in `api_utils.py` for render, embedding, token-embedding and generic pooling responses. Encode with orjson, including native NumPy input, and simplify hf3fs now that orjson is a required dependency.

Fix #44997. Latest head: `7f06159438` (token-embedding changes in `913437ee00`), including the [integration request](https://github.com/vllm-project/vllm/pull/58660#issuecomment-6333029142) for token embeddings introduced by #61772.

## Claims

- Accept Pydantic models, sequences of models and ready dictionaries. Preserve error statuses, explicit success statuses, integer keys and JSONResponse fallback for unsupported values such as opaque integers outside 64 bits.
- Reuse the helper across the affected render/pooling routes. Keep schemas, vector shapes, late-chunking field omission, usage accounting and binary streaming behavior unchanged. Plain Response objects retain load accounting until response completion.
- Avoid Python-list expansion for native NumPy embedding matrices. Earlier local measurements also show substantially faster serialization of large multimodal render responses; these are microbenchmarks, with no final-orjson end-to-end latency claim.

## Details

The helper materializes model dictionaries, encodes with `OPT_NON_STR_KEYS | OPT_SERIALIZE_NUMPY`, and returns application/json bytes directly. ErrorResponse retains its JSONResponse/status path. An orjson TypeError falls back to JSONResponse using the materialized content and requested status, preserving arbitrary-size opaque integers without an extra hot-path scan.

The integration with #61772 removes ServingTokenEmbedding's reference to the deleted response-class selector, which otherwise breaks frontend imports and mypy. It now passes its existing dictionary payload to the shared helper and calls the existing ndarray-capable encoder directly, retaining that encoder's dtype fallback. Token/chunk algorithms and response metadata remain those introduced by #61772.

The latest main sync also resolved the import conflict in pooling utilities: preserve main's `dataclasses.replace`/`reserve_tokens` additions while keeping the obsolete response selector removed.

The hf3fs server/client use the required orjson dependency; five server response sites construct ORJSONResponse directly. `orjson>=3.11.6` matches the existing test dependency floor.

Motivated by [llm-d-router #2685](https://github.com/llm-d/llm-d-router/issues/2685). This updates the existing render serialization PR: #46722 addresses multimodal preprocessing/transfer size, while #58314 targets ordinary completion responses in a different router.
