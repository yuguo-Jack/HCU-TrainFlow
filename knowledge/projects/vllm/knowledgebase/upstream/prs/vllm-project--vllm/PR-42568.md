# [Bugfix][V1] Let completed async KV loads promote and run under saturation

[Upstream PR](https://github.com/vllm-project/vllm/pull/42568) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #42371, where `SimpleCPUOffloadConnector` under sustained load settles into `Running: 0, Waiting: N` with zero throughput while HTTP keeps returning 200.

Two things in `main` cause it, and the change below fixes both.

**`main` puts the capacity gate above promotion.**

```python
# Paused streaming sessions (WAITING_FOR_STREAMING_REQ) are not
# in `running` but still hold a model-runner request slot.
num_running = len(self.running) + self.num_waiting_for_streaming_input
if num_running >= self.max_num_active_reqs:
    break
```

`main` reaches `_try_promote_blocked_waiting_request()` only after that `break`. So once running requests fill the gate, `main` never polls `skipped_waiting`, and a load whose transfer has finished is never promoted. A parked `WAITING_FOR_REMOTE_KVS` request is in neither term of that sum, so it is not what closes the gate; running requests are.

**`main` lets a blocked queue head strand requests behind it.** A promoted request holds its prompt blocks while it waits to be scheduled. When the head of `skipped_waiting` cannot allocate, `main` breaks out of the loop, so that request never runs and never frees its blocks, and with nothing running nothing else frees any either.

## Change

`vllm/v1/core/sched/scheduler.py`, 49 lines.

1. The gate moves below the promotion attempt, and a request whose status was `WAITING_FOR_REMOTE_KVS` on entry is exempt from it, so a completed load can be promoted and scheduled on the step its transfer lands.
2. While any queued request still holds allocated blocks, a head that cannot allocate is skipped rather than ending the loop.
3. `num_remote_kv_loading_reqs` is added to the gate's sum, so in-flight loads count toward admission the same way paused streaming sessions already do.

Point 1 means the promotion attempt is reached on more steps, which @kenhaesler raised on #53130 as the remote-KV branch doing block accounting more often. It does not. `_update_waiting_for_remote_kv` sits behind `if request.request_id not in self.finished_recving_kv_req_ids: return False`, so the accounting still runs once per completed transfer and what the extra steps add is that set lookup. Upstream reached it on fewer steps only by skipping transfers that had already completed, which is the bug.

Point 2's condition is a scan over `itertools.chain(self.skipped_waiting, self.waiting)`. Both call sites break when it is false, so a full traversal ends the loop and happens at most once per `schedule()`; when true it short-circuits on a holder, which `prepend_request` keeps near the head. Under `--scheduling-policy priority`, where iterating the queue copies and re-pops the heap, the `or` ahead of it skips the scan whenever a load is in flight. A counter will not work, because a request keeps its blocks after its status stops being a blocked one, and hoisting the value out of the loop breaks capacity accounting.

Point 3 follows the rule the gate's own comment states above: a request not in `running` that still holds a model-runner slot counts. An in-flight load is the same category and holds the slot its promotion will ask for, so counting streaming sessions and not loads lets admission over-commit and then fail at promotion. `num_remote_kv_loading_reqs` is maintained at the same three kinds of site as the streaming counter: incremented on entering the state, decremented on leaving it and on finish.

The two are deliberately asymmetric in `get_num_unfinished_requests`, which subtracts streaming sessions and should not subtract loads: a paused session waits on the client and should not make the engine look busy, while a load is engine work in progress.

## Relationship to #53130 and #53772

@kenhaesler described that first, in #53130 on 21 August as sketch 5, and #53772 implements a post-loop sweep from the same analysis.

Both can apply. Once promoted, a request's status is no longer a blocked status, so #53772's sweep skips it and there is no double promotion. They do not overlap on the second mechanism: that sweep advances state and leaves scheduling order to the queue, so the loop still breaks on the head's allocation failure and the promoted request behind it still never runs. I ran `test_async_load_deadlock_head_of_line_blocking` against #53772 locally and it fails.

#53772 also adds `iter_unordered()`, which would drop `PriorityRequestQueue` traversal to O(N); I have not used it here because it would couple the two PRs, and will switch if it lands first.

#53130's front-runner mechanism is token-budget starvation, which #42371 is not. This PR references it for the shared analysis, not as its fix.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

This `break` condition introduces a potential deadlock in `PRIORITY` scheduling mode. If a high-priority new request is at the head of the queue but cannot be scheduled because the `max_num_running_reqs` limit is reached (due to other requests currently in `WAITING_FOR_REMOTE_KVS` status), the loop terminates. This prevents the scheduler from ever seeing and promoting those loading requests, even if their KV transfers have completed. Since the loading requests hold GPU slots that the high-priority request needs, the system stalls.

To fix this, the scheduler should use `continue` instead of `break` when the limit is reached for a new request, allowing it to skip the new request and still process/promote already-active loading requests further down the queue. Additionally, requests that were already loading should bypass the limit check since they already count towards the occupancy.

```suggestion
                if (
                    not was_waiting_for_remote_kvs and
                    len(self.running) + num_remote_kv_loading_reqs
                    >= self.max_num_running_reqs
                ):
                    request_queue.pop_request()
                    step_skipped_waiting.prepend_request(request)
                    continue
```

Calculating `num_remote_kv_loading_reqs` by iterating over `self.skipped_waiting` is an $O(N)$ operation performed at the start of every scheduling step. Thanks. I agree an incremental counter would be the right optimization if this shows up as a scheduler hot path, but I kept this PR scoped to a derived count for correctness.

`WAITING_FOR_REMOTE_KVS` requests can leave that state through promotion, abort/finish handling, and transfer failure/recovery paths.
