You are right that `_supports_flattened_device_query_lens()` is the one to open, and you are right that the missing evidence is SM120 hardware. We have it — so let us run the experiment you can't.

## Where this stands on our side

We filed #63343 on exactly this gate. On RTX PRO 6000 (SM120, 12.0), `DeepseekV41IndexerBackend.supports_device_cpu_query_lens_mismatch()` returns `False`, so `enable_adaptive_verification` cannot start at all, and the failure is a `ValueError` at profile/CUDA-graph setup rather than a kernel fault. The cause is that **both** gates exclude SM120:

- `_supports_varlen_paged_mqa_logits()` — allow-lists the SM100 family only
- `_supports_flattened_device_query_lens()` — allow-lists the SM90 family only

SM120 is in neither, so the capability question never reaches the kernel. That is consistent with your read that this is a builder/gate problem rather than a numerics problem.

## What we can run

Our box: 8× RTX PRO 6000 Blackwell **Max-Q** (96 GB), SM120, PCIe-only, no NVLink but all-P2P across the rail, 4 NUMA domains. vLLM `0.31.1rc1.dev253+g7d0b4e57a`, FlashInfer `0.7.1rc5`, DeepSeek-V4.1-Flash-1017, `--kv-cache-dtype fp8 --block-size 64`, 1M context.

Proposed two-step, cheapest first:

**Step 1 — does the DeepGEMM kernel actually work on SM120?** Patch the capability gate locally to admit `12.0` in `_supports_flattened_device_query_lens()` **only**, leaving the SM100 gate untouched so `_supports_varlen_paged_mqa_logits()` still excludes us. Boot DSv4.1 with `enable_adaptive_verification` and run a correctness probe before reading any throughput:

- arithmetic at `temperature=0`, ×20 for determinism
- 512-token degeneration length
- concurrency 8 / 16 / 32

If that is clean, your guess is confirmed and the fix is a one-line allow-list. If it is not clean, we learn the kernel genuinely does not run on SM120 and the fix is a port, not a gate — either outcome settles it.

**Step 2 — if step 1 passes**, A/B the tier matrix with adaptive verification on vs off at our production shapes, with the usual caution: on this stack we have already seen silent data-path corruption that looks healthy at the engine level (the IPC × DSpark interaction in #60762), so every arm gets the probe at temp=0 before any tok/s number is reported.

## One question before we burn a window

Is the allow-list the patch you would want, or do you know a reason `_supports_flattened_device_query_lens()` is SM90-specific — i.e. does the flattened-query-lens path depend on something SM90-only (a TMA/warp-specialisation assumption), rather than just having never been tried elsewhere?

If it is a real hardware dependency, a gate patch would only move the failure later, and step 1 is not worth the GPU window. If it is just "never validated on SM120", we can have you the answer this week.

We are happy to post step 1's result here either way, including a clean negative — a documented "SM120 does not support this path" is worth having in the thread.

- Lei-010 · comment · 2026-11-04T04:25:07Z · [source](https://github.com/vllm-project/vllm/pull/62515#issuecomment-6622518274)

Opened #65527 following your suggestion — it admits SM120 to `_supports_flattened_device_query_lens()` and nothing else (one line in `vllm/v1/attention/backends/mla/indexer.py`, plus a test that pins the allow-list without needing SM120 hardware in CI). `_supports_varlen_paged_mqa_logits()` is deliberately left untouched, so SM100 keeps the varlen kernel.

Two things from the run that bear on your "I have no HW to validate" caveat:

**1. The gate is the only blocker on our box.** Step 0 probe (no model load, ~30 s): `get_device_capability()` = (12, 0), `has_deep_gemm()` = True, `_supports_flattened_device_query_lens()` False → True with the patch, and `supports_device_cpu_query_lens_mismatch()` flips False → True with it. Config validation for `enable_adaptive_verification` then passes.

**2. The allow-list is already inconsistent on SM120.** `_use_flattening()` returns True on SM120 whenever `next_n > 2`, because `_supports_native_decode()` falls through to `next_n in (1, 2)` off SM90/SM100 — so with `num_speculative_tokens >= 2` the flattened path is *already* the default on SM120. The SM90 allow-list therefore only blocks the adaptive branch (where `next_n` varies per batch and hits the `next_n ∈ {1, 2}` case) and, through `supports_device_cpu_query_lens_mismatch()`, engine startup. That asymmetry is the bug, not a capability gap.

Correctness on 8× RTX PRO 6000 Max-Q (SM120, PCIe, no NVLink): adaptive ON vs OFF on the same patched image, arithmetic 10/10 both arms, no long-form degeneration in either, identical degenerate-flag counts. Throughput numbers in the PR are **directional only** — the c8 −19.7 % row comes from a 16-request / 9.75 s window and I do not consider it established; I will post a steady-state re-run (≥8 samples/arm, min–max, accept rate) in #63343 before this is merged.
