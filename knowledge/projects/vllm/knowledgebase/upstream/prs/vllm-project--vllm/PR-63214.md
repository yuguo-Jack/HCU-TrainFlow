# [Profiler] Record the graph warm-up next to its capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/63214) · state: open · merged: False

## Original PR description

## Purpose

**Depends on #54061.** This branch is #54061 plus one commit, `[Profiler] Record the graph warm-up next to its capture`; only that commit is new here. I will rebase it when #54061 changes. @devalshahamd, happy to fold this into #54061 instead if you prefer.

With `capture_torch_profiler` on, #54061 writes one trace per captured shape, holding the capture under `capture_<tokens>_<mode>`. This also records the eager warm-up that runs just before the capture, in the same trace, under `warmup_<tokens>_<mode>`.

Why: a graph capture records its launches without running them, so the capture trace carries no kernel names, and a replayed graph can run on several streams. The warm-up runs the same forward eagerly for the same batch descriptor, so its kernels name, in order, the launches the capture records. That is what lets a replayed decode step be attributed to the code that issued each kernel.

How:
- `graph_capture_shape()` holds one profiler session open across a shape's warm-up and capture; `graph_capture_warmup()` and `graph_capture_step()` record into it.
- Outside `graph_capture_shape()`, `graph_capture_step()` opens its own session as before, so the encoder and speculator capture loops are unchanged.
- Applied to the V2 `CudaGraphManager.capture` and the V1 runner's `_warmup_and_capture`.

The warm-up only adds to the trace when `capture_torch_profiler` is on; nothing changes otherwise. The diff of `cudagraph_utils.py` and `gpu_model_runner.py` is mostly re-indentation (view with whitespace hidden).

## Before / after

The capture trace of the 16-token FULL decode graph of GLM-5.3-Flash on B200, opened in Perfetto. The "before" trace comes from a TP4 run with capture recording only, the "after" from a TP8 run with this change; the graph shape is the same.

**Before (capture only).** During capture the GPU does not run the captured kernels, it only records them. So the CPU side of the trace has every launch call, with its Python stack, but no launch reaches a kernel: of the ~1,400 kernel launch calls made while the forward is captured (746 `cuLaunchKernelEx`, 356 `cudaLaunchKernelExC`, 309 `cudaLaunchKernel`), none has a GPU kernel at the other end, so none has a kernel name or stream. Below, one of them selected: `Glm5NextDecoderLayer_3` → `Glm5NextMLAAttention_0` → `Indexer_0` → `aten::linear` → `aten::mm` → `cuLaunchKernelEx`. The stack says exactly which module launched it, but the launch has only a correlation id and no flow to a kernel (the after shot below shows that flow), so nothing says which kernel it was.

![before: a captured launch with no kernel](https://raw.githubusercontent.com/amd-sriram/vllm/e1b73bb3cfac0b5a201d57f414a04d930d44414b/pr2_before_captured_launch.png)

The only GPU events in the `capture_16_FULL` span are input and metadata preparation that runs eagerly around the forward. Area-selecting the span lists all of them: 12 device-to-device copies and 44 small kernels (fills, `arange`, `indexSelectSmallIndex`, `searchsorted`, `_indexer_decode_metadata_kernel`, `sm100_paged_mqa_logits_metadata`, ...), about 0.1 ms in total. None of them is a GEMM, attention or MoE kernel.

![before: every GPU event in the capture span](https://raw.githubusercontent.com/amd-sriram/vllm/df76765c413d048dcdd2138307658b3ea8f0f5bc/pr2_before_capture_kernels.png)

**After (warm-up + capture in the same trace).** The same launch, in the warm-up recorded just before the capture: same module stack (`Glm5NextDecoderLayer_3` → `Glm5NextMLAAttention_0` → `Indexer_0` → `aten::linear` → `aten::mm` → `cuLaunchKernelEx`), but now it has a following flow to the kernel it ran, `nvjet_sm100_tst_32x64_64x16_4x1_v_bz_splitK_TNN` on stream 95. Across the whole `warmup_16_FULL` span that holds for 1,391 kernels on 13 streams, in launch order, right before `capture_16_FULL`.

![after: the same launch, now with its kernel](https://raw.githubusercontent.com/amd-sriram/vllm/45a09ed509108d0171c4ebdbfac0e5e1e8da12b0/pr2_after_warmup_launch.png)

One warm-up kernel selected: its name, its stream and the flow back to the CPU launch that issued it.

![after, one kernel](https://raw.githubusercontent.com/amd-sriram/vllm/59fc23655c34b382a784f65c0af00d2d0765439c/pr2_after_warmup_kernel.png)

## Test Plan

```bash
pytest tests/v1/worker/test_gpu_profiler.py
```

New tests: warm-up and capture share one session per shape, in that order; the warm-up label follows the binding's prefix; the shape session closes when the capture raises; `CudaGraphManager.capture` and the V1 `_warmup_and_capture` record the warm-up before the capture in one session.

## Test Result

The new tests pass. The same recording, carried in our serving images, names every kernel in the captured decode graphs of GLM-5.3-Flash TP8 on MI355X and B200, which we match against the replayed steps.
