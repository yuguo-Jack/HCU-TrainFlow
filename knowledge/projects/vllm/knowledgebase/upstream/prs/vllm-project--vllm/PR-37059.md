# fix(moe): detect and handle unquantized MoE weights in NVFP4 checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/37059) · state: closed · merged: False

## Original PR description

## Summary

ModelOpt NVFP4 exports can leave MoE expert weights unquantized while the checkpoint metadata still says NVFP4. In that case, vLLM allocates packed `uint8` tensors for the MoE weights, but the checkpoint can contain `bf16`/`fp16`/`fp32` tensors instead, which causes loading to fail.

I originally built this for myself while experimenting with local models on my DGX Spark, but a couple of comments on the fork PR suggested this may be useful upstream too.

Original fork PR and discussion:
https://github.com/Th0rgal/vllm/pull/2

Thanks for the nudge here, @catswe and @voipmonitor.

## Changes

- Detect unquantized MoE expert weights in ModelOpt NVFP4 checkpoints during load.
- Log a warning once when mixed quantization is detected.
- Resize the target parameter tensor back to the unpacked shape and switch dtype to match the checkpoint tensor.
- Fall back to the standard unquantized loading path for the affected experts.

## Limitations

- This fixes loading for affected layers only.
- Full inference support may still require kernel selection changes for unquantized MoE experts.
- The ideal long-term fix is likely on the ModelOpt export side so these checkpoints are emitted consistently.

## Testing

Tested with GLM-4.7-Flash quantized using ModelOpt 0.35.0 on a DGX Spark GB10 GPU.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve existing experts when switching to unpacked weights**

Reassigning `param.data` to a fresh zero tensor here discards any experts that were already loaded into this parameter before the first unquantized tensor is encountered. In `load_weights`, experts are loaded sequentially, so a mixed checkpoint (some experts still packed `uint8`, others fp16/bf16/fp32) can hit this branch after earlier experts were populated, and those earlier values are silently replaced with zeros and never restored. This leads to corrupted MoE weights at runtime.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Switch quant path when accepting unpacked NVFP4 weights**

This branch loads bf16/fp16/fp32 expert weights and returns success, but it leaves the layer on the NVFP4 quantization path, so `process_weights_after_loading()` still runs NVFP4 kernel-format conversion on these tensors. **<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Rebuild runner when switching to unquantized MoE method**

This fallback mutates `self.quant_method`/`self.base_quant_method` directly, but `FusedMoE.forward_native()` executes through `self.runner`, and `DefaultMoERunner` stores its own `quant_method` at construction time. If this path is hit, post-load processing will run on the new unquantized method while runtime execution can still use the stale NVFP4 method from the runner, leading to kernel mismatch or incorrect inference for affected checkpoints. The method swap here needs to keep the runner in sync (e.g., via the existing replacement hook).

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep NVFP4 unpacked handling active for later weight loads**

This condition depends on `quant_method_name`, which is derived from `self.quant_method` at the start of each `weight_loader` call. After the first unpacked tensor flips `self.quant_method` to `UnquantizedFusedMoEMethod`, subsequent MoE weight tensors no longer enter this NVFP4-specific block, so parameters that are still in packed `uint8` layout skip the resize/unpacked path and are loaded via generic sharded copy logic. In checkpoints where multiple MoE weight tensors are unpacked, later tensors can be truncated/cast into packed buffers and silently corrupted.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Reject cross-parameter format mixing before method swap**

This branch switches the whole layer to `UnquantizedFusedMoEMethod` as soon as one NVFP4 MoE weight arrives unpacked, but the consistency check is only per-parameter (`_modelopt_nvfp4_moe_weight_format` on `param`). A checkpoint where `w13_weight` stays packed `uint8` while `w2_weight` is unpacked `bf16/fp16/fp32` will pass loading, then `process_weights_after_loading()` runs the unquantized path over both tensors even though one is still packed/half-width, which can break finalization or produce incorrect runtime behavior. The fallback should validate format consistency across both MoE weight tensors before switching the layer method.
