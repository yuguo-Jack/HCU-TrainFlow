# [ROCm][Perf][DSv4.1] Mono: tuned K1/K2 for the TP2 compress-ratio-2 layers on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/63027) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Faster K1/K2 for the DeepSeek-V4.1-Flash mono decode layer on gfx950 (MI355X), applied only to the compress-ratio-2 target layers at TP2. A static build flag, `MonoBuild.tuned`, selects the new paths; their outputs are bit-identical to main's, and every other build (ratio 0/1, TP4, DSpark draft, gfx942, FFN launch) compiles to the same MLIR as on main.

1. **Tuned builds of the ratio-2 layers**: the `MonoBuild.tuned` gate with its own scratch; unsigned index math in the MoE stages; polled ready flags replicated on separate lines; independent loads issued ahead of waits.
2. **Down stage**: two-task down CTAs pipeline their rounds through LDS; their shared-expert down rows are offloaded to the next one-task CTAs.
3. **FFN seam and attention hand-offs**: a shorter seam -> norm -> router chain, whole-sector attention partials, per-tile `wo_a` ready flags.

Each commit builds and is bit-exact on its own. Related: #61482 (moves these kernels to `vllm/models/common/amd/mono/`).

**Rebased** onto main 8977b13a1c, which includes #63576 (K2's combine awaits `krdy` before reading `klen` in index-source launches) and #63689 (vLLM's scale code for zero and subnormal MXFP8 groups). Both fixes apply to the tuned builds as well: the tuned paths share `stage_combine` and its `krdy` wait, and quantize with the same `vllm_mx_code` / `mx_code`. No conflicts; the diff is unchanged.

**Result vs main:** ratio-2 layer K1+K2 8.6-18.1% faster (M = 1..48), index-source launches included; E2E TPOT p50 −3.3% (c32) and −3.7% (c4).

## Validation

## Details

**Where it applies**: gfx950, TP 2, compress ratio 2, the target's routing (384 experts, top-6) and SWA window. The gate is static per build; no new flag or env var.

**Tradeoff**: tuned builds lay out their scratch differently, so the runner keys scratch by (width, tuned): up to ~20 MB per tuned width per rank. Peer memory is unchanged.

**Not covered**: gfx942 and DSpark draft builds were not run on GPU (MLIR identical to main's); TP4 is not tuned.

@frida-andersson re: per-commit gains. We measured end to end on 4x MI355X (DeepSeek-V4.1-Flash, --monokernel, DSpark k=5, synthetic acceptance length 3.51, concurrency 1, 100k-token cached prefix, OSL 1000, median of 3 runs). The commits were applied one after another on top of a nightly (335dd77b0 + #63892).

TP2 c1 (TP2, Engram on host, max-num-batched-tokens 32768; one round, noise about ±1%):
| commit | tok/s/user @100k | @800k | Δ decode step @100k |
|---|---|---|---|
| base | 559.2 | 551.1 | |
| + 3dd9b21 (index math, 8-copy poll flags, loads ahead of waits) | 573.3 | 563.8 | −155 µs |
| + f77d25c (two-task down pipeline + shared-row offload) | 568.5 | 562.1 | ≈ 0 (+52 µs, within noise) |
| + 412fe07 (FFN seam → router chain, attention hand-offs) | 576.6 | 570.5 | −87 µs |

At c1 the down pipeline and the shared offload contribute nothing. As far as we can tell that is by design: the pipeline only engages past 72 picks (12 rows), and the shared offload past one token tile, while a c1 DSpark step has 6 rows. Their benefit should show up at higher concurrency; we have not measured that yet.

TP4 c1: this PR alone is ≈ 0, as expected, since no TP4 build is tuned. Its K1 paths are what #63893 turns on at TP4: + #63893 gives −300 µs per step (669 → 710 tok/s/user @100k). With a local knob inside #63893's K1:
- the tuned front (copied flags plus early norm / wq_b loads) gives ≈ −180 µs;
- the gate placement gives ≈ −95 µs;
- the tuned seam gives ≈ 0.

Turning seam or gate on without the tuned front hangs at graph capture, so those parts are not independent.
