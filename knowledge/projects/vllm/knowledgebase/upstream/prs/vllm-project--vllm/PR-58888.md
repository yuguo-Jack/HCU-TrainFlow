# [Security] Reject short Voxtral Realtime audio before the encoder

[Upstream PR](https://github.com/vllm-project/vllm/pull/58888) · state: open · merged: False

## Original PR description

## Summary

A Voxtral Realtime chat or transcription request can carry an `input_audio` clip of only a few mel frames (about 10–80 ms at 16 kHz). The realtime feature extractor does not pad streaming audio, and `embed_multimodal` then trims the mel spectrogram and the conv output to a multiple of the block pool. When that trim empties the tensor, a reachable assertion in the worker kills EngineCore and the API server.

This rejects those clips while the multimodal processor is still building the request, so the client gets a 400 and the engine stays up. If a short waveform still reaches the worker, `embed_multimodal` returns empty embeddings instead of asserting, which is the same non-fatal path already used when realtime audio is missing.

## Changes

- `vllm/model_executor/models/voxtral_realtime.py`: reject waveforms that cannot produce a pooled encoder row (centered STFT pad, even mel trim, conv stride, block pool). Apply that check in `VoxtralRealtimeMultiModalProcessor` and, as a backstop, return empty embeddings from `embed_multimodal` instead of running the encoder.
- `tests/models/multimodal/processing/test_voxtral_realtime_audio.py`: cover the reported 800-sample clip, the 1280-sample minimum, processor rejection before tokenization, and the worker backstop.

## Codepath coverage

- `POST /v1/chat/completions` (`input_audio`) → renderer → `VoxtralRealtimeMultiModalProcessor`: rejected.
- `POST /v1/audio/transcriptions` → `render_cmpl_async` → the same processor: rejected.
- `WS /v1/realtime` → `render_cmpl_async` → the same processor: a short frame is rejected; frames that already meet the pool size are unchanged.
- Offline `LLM.generate` runs the same processor before the engine step.
- Worker `embed_multimodal` if a short waveform is still scheduled: returns empty embeddings and does not assert.

## Duplicate-work check

Searched open and merged PRs for `voxtral_realtime`, `_truncate_left`, and short-audio handling, and read the diffs that touch this file:

- #39229 fixes mixed-batch `embed_input_ids` shape, not encoder truncation.
- #54516 caps transcription length after the prompt. Its "audio is too short" error is a max-token check, not this encoder trim.
- #58251 is a typing change around `forward_conv`.
- #40072 is a scheduler `max_model_len` guard.

None of those diffs reject a short waveform before `_truncate_left`.
