# [Bugfix][Tool Parser] Preserve format-only structured outputs under auto tool choice with parser default strict level

[Upstream PR](https://github.com/vllm-project/vllm/pull/62499) · state: open · merged: False

## Original PR description

## Purpose

Fixes #62483.

In `DelegatingParser._apply_structural_tag` (`vllm/parser/abstract_parser.py`), when `--tool-strict-level` is not explicitly configured (`self.tool_strict_level is None`), `strict_level` unconditionally fell back to `tool_parser.default_tool_strict_level`.

For tool parsers whose `default_tool_strict_level` is `ToolStrictLevel.FUNCTION` (such as `Glm47MoeModelToolParser`, introduced in #56403), a request combining:
- `tools` without `strict: true`,
- `tool_choice="auto"`, and
- an explicit `response_format` (e.g., `json_schema` / `json_object`) or `structured_outputs`

had `strict_level` elevated to `ToolStrictLevel.FUNCTION`. As a result, `resolve_tool_strictness` treated the non-strict tools as active and `_apply_structural_tag` replaced `request.response_format` with `OrFormat(elements=[tools_structural_tag.format, output_format])`, allowing the model to emit `<tool_call>...` instead of adhering strictly to the caller's `response_format` schema (contrary to the `single_call` guard right below it: *"Auto with structured outputs keeps its format-only grammar, so the flag never makes calls possible that are impossible without it"*, and #56403's contract that requests with explicit structured outputs / JSON response format remain unchanged).

This PR guards the `tool_parser.default_tool_strict_level` fallback when `is_auto and structured_outputs is not None`, keeping `strict_level = ToolStrictLevel.AUTO` unless `--tool-strict-level` is explicitly configured by the operator or a tool has `strict: true`.
