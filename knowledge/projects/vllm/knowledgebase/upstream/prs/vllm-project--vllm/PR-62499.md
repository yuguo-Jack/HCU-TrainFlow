# [Bugfix][Tool Parser] Preserve format-only structured outputs under auto tool choice with parser default strict level

[Upstream PR](https://github.com/vllm-project/vllm/pull/62499) · state: open · merged: False

## Original PR description

## Purpose

Fixes #62483.

In `DelegatingParser._apply_structural_tag` (`vllm/parser/abstract_parser.py`), when `--tool-strict-level` is not explicitly configured (`self.tool_strict_level is None`), `strict_level` falls back to `tool_parser.default_tool_strict_level`.

For tool parsers whose `default_tool_strict_level` is `ToolStrictLevel.FUNCTION` (such as `Glm47MoeModelToolParser`, introduced in #56403), a request combining:
- `tools` without `strict: true`,
- `tool_choice="auto"`, and
- an explicit `response_format` (e.g., `json_schema` / `json_object`) or `structured_outputs`

had the `resolve_tool_strictness` gate evaluated at `ToolStrictLevel.FUNCTION`. As a result, `resolve_tool_strictness` treated the non-strict tools as active and `_apply_structural_tag` replaced `request.response_format` with `OrFormat(elements=[tools_structural_tag.format, output_format])`, allowing the model to emit `<tool_call>...` instead of adhering strictly to the caller's `response_format` schema (contrary to the `single_call` guard right above it: *"Auto with structured outputs keeps its format-only grammar, so the flag never makes calls possible that are impossible without it"*, and #56403's contract that requests with explicit structured outputs / JSON response format remain unchanged).

This PR passes `ToolStrictLevel.AUTO` to the `resolve_tool_strictness` gate when `self.tool_strict_level is None and is_auto and structured_outputs is not None`, while keeping `strict_level = tool_parser.default_tool_strict_level` for `tool_parser.get_structural_tag(...)` once a `strict: true` tool opens the gate.

- vadiklyutiy · comment · 2026-10-24T14:09:38Z · [source](https://github.com/vllm-project/vllm/pull/62499#issuecomment-6385205349)

The override changes `strict_level` for both of its uses, not only for the gate:

1. `resolve_tool_strictness(..., strict_level)`. `AUTO` is what we want here, so a parser default no longer makes tool calls possible next to a structured output.
2. `tool_parser.get_structural_tag(..., strict_level=strict_level)`. Here it also changes how strictly the tag constrains the calls once a `strict: true` tool has opened the gate.

Because of (2), when a parser's default is `PARAMETER` and a request has a `strict: true` tool next to a non-strict one, the non-strict tool's arguments are no longer constrained. For example, with `minimum: 5` the grammar now accepts `n=2`, which the current code rejects. No in-tree parser defaults to `PARAMETER` today, but a plugin parser (`--tool-parser-plugin`) can.

Passing `AUTO` only to the gate and keeping the parser default for the tag avoids this:

```python
strict_level = self.tool_strict_level
if strict_level is None:
    strict_level = tool_parser.default_tool_strict_level
...
resolved_tools = resolve_tool_strictness(
    get_structural_tag_tools(
        tool_parser.structural_tag_model,
        request.tools,
        request.tool_choice,
    ),
    request.tool_choice,
    # Next to a structured output, a parser default only constrains
    # the calls a strict tool makes possible.
    ToolStrictLevel.AUTO
    if self.tool_strict_level is None
    and is_auto
    and structured_outputs is not None
    else strict_level,
)
```

A test that covers it: a parser with `default_tool_strict_level = PARAMETER`, `tool_choice="auto"`, a `response_format`, one `strict: true` tool, and a non-strict tool whose parameter has `minimum: 5`. The resulting grammar should reject a call with `n=2`. That passes on `main` and with the change above, and fails with the current PR.
