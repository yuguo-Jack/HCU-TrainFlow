# [FlashInfer][Flint] Support attention sinks with fp8/NVFP4 KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/63826) · state: open · merged: False

## Original PR description

## Overview

Enable attention sinks with a quantized KV cache on the FlashInfer backend: NVFP4 KV is served by the plain fa2 paged prefill wrapper at `return_lse=True` with the sink applied exactly as an epilogue rescale `out * sigmoid(ln2 * lse - sinks)` (new, SM12x-only), and fp8 KV is unblocked by the same non-bf16 routing in flint's model code. This unblocks quantized weight+KV GGUF models with learned sinks (e.g. RecursiveSI/flint) on RTX 50-series, requested in #63605.

## Claims

- `has_sinks + kv_cache_dtype="nvfp4"` now serves on the fa2 NVFP4 path **on SM12x only**, gated on the *resolved* decode kernel: XQA decode applies sinks natively, but where the builder would revert to the plain fa2 decode wrapper (unsupported head_dim, DCP, non-divisible GQA) setup raises — a direct probe on flashinfer 0.7.2.post1 shows that wrapper's `sinks=` is silently ignored (bit-identical output with or without sinks). SM8x/90 rejections, the head_size-64 rejection, and the nvfp4_trtllm/SM100 path are untouched.
- RecursiveSI/flint NVFP4 GGUF serves end-to-end on RTX 5090 with GSM8K parity vs bf16 (strict 0.4989 vs 0.5087, < 1 stderr). **KV capacity ×3.55 at TP=4** (3.13M → 11.12M tokens; concurrency for 209,632-token requests 14.91× → 53.02×); at TP=1 it enables max-model-len 262144 that bf16 cannot even initialize.
- **fp8 KV also works with no extra code** (routing keyed on any non-bf16 dtype): GSM8K parity (0.5186), 424,435-token pool at TP=1 / 6.25M at TP=4, and on the 9-point TP4 grid below fp8 matches or beats bf16 at 5/9 points — including 131k×32, where nvfp4 pays −21%. Its two regressions (−25% at 16384×8, −43% at 32768×32, each reproduced in a second run) are prefill-side via the pre-existing fmha_v2 fp8 sink-prefill wrapper, not this PR (the new epilogue is nvfp4-only).
- Cost, opt-in only: nvfp4 is −8% to −21% out tok/s on the 5090 grid (fa2 JIT dequantizes fp4 in-kernel; SM120 has no tuned fp4 attention kernel — trtllm-gen fp4 is SM100+). Default `kv_cache_dtype="auto"` paths are untouched. On bandwidth-limited SM120 cards the tradeoff flips positive — see the independent 5060 Ti reproduction in Validation.

## Details

**Root cause.** `BatchAttentionWithAttentionSinkWrapper` cannot read packed NVFP4 pages (pre-existing rejection). The plain fa2 paged wrapper *does* read them on SM12x via JIT but silently ignores `sinks=` (verified empirically) — while supporting `return_lse=True`. The sink contributes denominator mass `exp(sink)`; fa2's LSE is log2-domain, so `out * sigmoid(ln2 * lse − sinks)` is exact (one multiply in fp32, `out=` in place).

**Gating.** On SM12x, decode runs XQA, which applies sinks natively; off SM12x decode would land on the plain fa2 decode wrapper, probed to silently ignore `sinks=`. Hence the rejection for device major != 12 in both `supports_combination` and the builder, and the SM12x gate additionally keyed on the resolved decode kernel (XQA revert → raise). Holds until a sink-capable decode wrapper ships (#6021, merged but unreleased) and is validated off-12x.

**Flint side.** Flint's fused `qk_norm_rope` kernel writes the KV cache through bf16 views, which don't apply to quantized packed layouts, so for any non-bf16 `kv_cache_dtype` the model routes through `unified_kv_cache_update` — one shared `impl_owns_kv_cache` flag drives the assert, the custom-decode gate, the forward path, and `_cache_views` (also fixes a pre-existing `== "nvfp4"` vs `startswith` inconsistency). This is what unblocks fp8 as a side effect. bf16 serving is unchanged (same kernels, same paths; the bf16 GSM8K row was measured on this branch).

**Adjacent work (not duplicates).** #63169 opens fa2 NVFP4 at head_size 64 but keeps the sink rejection — this PR does the reverse, disjoint. #59878 opens sink wrappers for SM8x and, in its latest revision, also routes NVFP4+sinks through FlashInfer's sink prefill/decode wrappers — but those wrappers come from flashinfer-ai/flashinfer#6021, which is merged yet unreleased: vLLM pins flashinfer 0.7.2.post1, where `BatchDecodeWithAttentionSinkWrapper` does not exist (top-level `from flashinfer import` fails outright) and the sink prefill wrapper has no functional `kv_cache_sf` support, so that NVFP4 path cannot run until a flashinfer release ships #6021 and vLLM bumps the pin. This PR's epilogue approach works on the pinned release today, SM12x-only. #53979 built the fa2 NVFP4 prefill path this rides on. #60452 added XQA NVFP4 decode (enablement precedent).

**Scope notes.** NVFP4 KV cache itself remains undocumented in `docs/features/quantization/quantized_kvcache.md` (pre-existing gap — happy to add a section if reviewers want one). flashinfer quirk noted for reviewers: on the pinned 0.7.2.post1 the sink-wrapper JIT URI lacks head dims, so head_dim-128 and 256 wrappers in one process share a compiled module and one returns wrong output — already fixed upstream in flashinfer-ai/flashinfer#6021 (unreleased); the CI selector above avoids co-selecting them. Bench/eval numbers: bf16/nvfp4 at a22868a, fp8 at e7002bd4f2 (the pre-rebase tip; the later rebase onto main b71c1d5f14 changed only the CI selector line, no code, so the numbers carry over). The two review-round commits (d813a759: fp32 epilogue rounding + arch gate; e7002bd: gate on resolved decode kernel + reject test + LSE layout pinned in the epilogue comment) likewise change no math.

AI assistance was used (Claude Code) for implementation, testing and benchmarking; every changed line was reviewed and all validations above were run by the human submitter on the pod configuration described.

### Review notes

1. **SM8x/SM90 decode with sinks + NVFP4.** I'm not sure this is safe. On SM120 decode goes through XQA (`can_use_xqa_or_trtllm_gen_decode` is True for `nvfp4_fa2` on family 120), and XQA applies the sinks, which matches my results. But the PR also opens `has_sink + nvfp4` for SM8x/SM9x, both in `supports_combination` and in the `__init__` check. There, decode falls back to `BatchDecodeWithPagedKVCacheWrapper(use_tensor_cores=True)` on fa2. In FlashInfer 0.7.2.post1 that path calls the same fa2 `paged_run` that you found silently ignores `sinks=` in prefill. If so, SM8x/SM90 would decode without the sink and give wrong output with no error. I can't test SM8x/SM90 here. Options: restrict the gate to SM12x (the only arch validated), or apply the same LSE epilogue in the fa2 decode path and add a decode test there.
2. **fp8 KV for Flint.** The model-side change (`k_cache=None` in `qk_norm_rope_cache`, then `unified_kv_cache_update`) is exactly what I had done locally for fp8. It works on SM120 with the stock sink wrappers: 351,744-token pool, same speed as bf16, coherent output. Could the Flint check be generalized from `nvfp4` to "any non-bf16 KV dtype"? That would be `self.attn.kv_cache_dtype not in ("auto", "bfloat16")`, both for the assert/`flint_decode` gate and in `_cache_views`. Then fp8 works too, with no extra code. `_cache_views` checks `== "nvfp4"` while `forward` checks `self.impl.is_kvcache_nvfp4` (`startswith("nvfp4")`), so a single shared flag would also keep the two in sync.
3. **Nit.** `sink_corr.to(out_pre.dtype)` rounds the correction to bf16 before the multiply. Doing the multiply in fp32 and casting once avoids that extra rounding. Running the wrapper with `out=out_prefill` and an in-place `mul_` would also save the temporary and the `copy_`.

Thanks again! Happy to re-run any of this on the 5060 Ti setup if you change the gating.
