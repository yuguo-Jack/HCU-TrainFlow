# [Bugfix][FA4] Cover paged dense prefill specializations in the warmup

[Upstream PR](https://github.com/vllm-project/vllm/pull/63279) · state: open · merged: False

## Original PR description

## Overview

This PR closes two FA4 warmup gaps that leave real prefill shapes to compile during serving. The dense FA4 warmup now covers the paged prefill specializations of every model family, and it sizes its synthetic page table so that a cache page larger than the warmup length warms the same specialization that serving uses. It started in #62800, which keeps the KV cache page fixes. The two PRs share no files and don't depend on each other, so either can land first. It is also independent of #62961, #62962, #62963 and #62964.

## Claims

- FA4 warmup covers the dense paged prefill specializations (packed-query staging, persistent and non-persistent, SplitKV, and the varlen batch lookup when `max_num_seqs` exceeds FA4's `BIN_BATCH_SEARCH_THRESH`) for every model family, and each warmup key compiles a distinct kernel. The existing specialized hd256 and SM90 hd512 paths stay as they are.
- The warmup sizes its synthetic page table with ceiling division. A cache page larger than the warmup length otherwise warms a broadcast (zero-stride) specialization that serving never uses.

## Validation

AI assistance (Claude) was used to prepare this change; I reviewed every changed line and ran the tests listed below.

The new test is a native compilation-cache test. It fails when a served shape misses the warmup or when two warmup keys compile the same kernel. I broke the page-table fix on purpose to check that the test catches it, and reverting it fails the 4 large-page cases of the 8 native tests on B300. Letting SplitKV keys claim static persistence fails all 8 on the duplicate-kernel check.

On CPU (`VLLM_TARGET_DEVICE=cpu`, one pytest process per file), the 8 native tests in `test_flash_attn_warmup.py` skip without CUDA. Across 21 attention, KV-cache, spec-decode and worker test files, this PR passes 735 tests, the same as `main` (`537a79f0fc`). The 77 failures are the same pre-existing cases on both builds: 62 tests that need Hugging Face model configs the offline runner lacks, 8 CPU-builder cases in `test_group_head_counts.py` and 7 in `test_gpu_model_runner.py`. One more `test_kv_cache_planning.py` test timed out in its subprocess during the parallel run on this PR, and it passes on both builds when run alone. `pre-commit` passes on the range.

On B300, `test_flash_attn_warmup.py` passes natively (8 passed). A CUDA probe ran real paged attention after the warmup over 102 served shapes (batches of 1, 16 and 300, query lengths from 1 to 1611, full and sliding-window layers, automatic SplitKV). It had 0 forward compilation misses against 14 on `main`, and its outputs matched `main` bit for bit. The warmup compiles 5 forward kernels from 5 keys with `max_num_seqs=256` and 8 from 8 with `max_num_seqs=1024`, and the hd256 warmup compiles the same native kernels as on `main`. A TP4 hybrid Mamba2 model with a 9728-token page served 8 requests with 0 runtime forward misses and 0 inference-time JIT warnings. I measured the Mamba2 run on the previous base (`56e67b46a3`) before the warmup key change, where the first two commits sat together with the KV cache fixes that are now #62800.

```bash
pre-commit run --from-ref origin/main --to-ref HEAD
VLLM_TARGET_DEVICE=cpu python -m pytest -q tests/v1/attention/test_flash_attn_warmup.py
python -m pytest -q tests/v1/attention/test_flash_attn_warmup.py   # on B300
```

## Not a duplicate

I ran the duplicate-work searches from `AGENTS.md` §1 (open PRs, with keywords on FA4 warmup, `FA4DenseAttentionKernel` and warmup page tables). They found related work, and none of it makes the same fix. This PR uses no code from them.

- #48156 (dense FA4 warmup) predates the in-tree `FA4DenseAttentionKernel` warmup framework from #55768. This PR extends that framework.
- #61221 adds the persistent variant to Kimi-K3's vision FA4 warmup, which is a separate warmup provider. This PR covers the dense paged attention provider.

## Includes and credits

This PR contains no code from other open PRs.

## Details

- The changes touch only the warmup provider. Runtime attention dispatch and arithmetic are unchanged, and so are the existing specialized hd256 and SM90 hd512 warmup paths. Warming every model family trades startup time for no forward-kernel compilation during serving. SplitKV's combine and scheduling kernels still compile on first use (3 compilations across the 102 probe shapes). On B300 the dense warmup compiles in 8 to 13 s per attention spec. Qwen3.8-27B selects FlashInfer by default on B300, so its server start does not include this cost, and the startup cost on a full FA4 model is still to be measured.
- All GPU measurements are on B300.
