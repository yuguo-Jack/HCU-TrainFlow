# [Model Runner V2] Optional post-capture warmup of every decode batch size, logits row count and graph size

[Upstream PR](https://github.com/vllm-project/vllm/pull/59976) · state: open · merged: False

## Original PR description




## Overview

Adds an opt-in startup pass to Model Runner V2, `--kernel-config '{"enable_batch_size_warmup": true}'` (default off). It runs right after CUDA graph capture. The pass runs one scheduler step for every decode batch size, every logits row count and every CUDA graph capture size. Each shape's first use then happens at startup, not on a live request.

## Claims

- After capture, each captured graph (target and drafter) gets replayed once. The pass reaches every uniform-decode batch size from 1 to `max_num_seqs` and one prefill at every capture size.
- The eager logits GEMM, the TP logits gather and the sampler/rejection sampler run at every row count a step can have: `q*a + c` rows with `a + c <= max_num_seqs`, where `q = num_speculative_tokens + 1`. That covers first-use cuBLAS heuristic selection, lazy CUDA module loading, Triton specializations and graph upload. Without this pass, each of these can stall the first request that reaches a new batch size.
- The plan depends only on the config, so every TP rank runs the same steps and collectives.
- With the flag unset, nothing changes.

## Validation

### Test plan

- CPU unit tests (new file `tests/v1/worker/test_batch_size_warmup.py`). They check the plan's coverage: every decode batch size, every reachable logits row count, and every capture size within the token/context limits. A stub worker replays the steps and checks the KV block reservations: lookahead included, block 0 never used, no block held by two live requests. The tests also check that every warmup request finishes, and that the pass skips when the KV cache is too small or under DP.
  ```
  pytest tests/v1/worker/test_batch_size_warmup.py
  ```
- `ruff check`, `ruff format` and `mypy` on the touched files.
- GPU check (not yet run on this branch). Start any V2 model with the flag and compare it with a run without the flag. Check the `Batch-size warmup ran N steps ... in X s` log line on every rank. Then check that `--jit-monitor-verbose` reports no compiles during a mixed-concurrency replay. For example:
  ```
  VLLM_USE_V2_MODEL_RUNNER=1 vllm serve <model> -tp 2 \
    --speculative-config '{"method": "eagle3", "model": "<draft>", "num_speculative_tokens": 3}' \
    --kernel-config '{"enable_batch_size_warmup": true}'
  ```

### Test result

- Unit tests: 8 passed on CPU (macOS, torch 2.14.1). ruff and mypy are clean.
- GPU evidence comes from an earlier, larger, model-gated version of this mechanism, not from this branch. Setup: 8×B300, MiniMax-M3 NVFP4, TP2 engines with EAGLE3 (3 draft tokens) and CPU KV offload, an older nightly (`af7f9488c`) and our own benchmark harness. That version ran the same steps, but used dispatch introspection to skip graph sizes that were already hit. It also had an extra model-specific cuBLAS sweep, which is not part of this PR. We have not yet measured this PR on main.
  - **Without the warmup:** first use of a new batch size during serving JIT-compiled sampler kernels (`_topp_sb_*`, `_topk_topp_kernel`) mid-replay, and caused multi-second stalls. Separately, 5 of 94 TP2 engine runs hung. Each hang came on the first step of a new size (a new graph or eager lm-head row count), all within ~15 min of serving start. In one dump, one rank sat inside the first eager lm-head GEMM at a new M while its peer waited in the logits all-gather. We have not established the root cause of the hang. Pre-warming removes its precursor, but that does not prove it is fixed.
  - **With the warmup:** all 113 captured graphs replayed and 141 logits row counts ran (146 steps, about +5–12 s of startup at TP2, `max_num_seqs` 36, `num_speculative_tokens` 3). Serving logged no first-use JIT compile and no stall, and KV cache capacity was unchanged.
    - We then made the warmup the default for all our TP2 runs. Since then we have seen no further first-use hang. We did see one TP2 hang with a different signature: GPU-side, on a step that was not a first use. So this is not a fix for every TP hang.
    - Later runs without the warmup hung again on the first decode step at a new batch-size peak, inside the first-use cuBLAS lm-head GEMM.
    - GSM8K with the warmup in the stack matched the baseline.
    - We have no clean throughput A/B that isolates the warmup. It only changes startup, so we expect no steady-state effect.
- Startup cost of this branch's plan, as step counts from a CPU dry run (the time per step depends on the model):

  | max_num_seqs | num_speculative_tokens | Steps (with 26 capture sizes) |
  |---|---|---|
  | 36 | 3 | 167 |
  | 256 | 0 | 282 |
  | 256 | 7 | 2053 |

## Details

**Motivation.** The existing `warmup_kernels` runs before capture, at a handful of shapes, and targets the JIT registry and sampler features. It does not reach every batch size. Shape-dependent first-use work stays lazy until serving, as do the first replay of each captured graph and cuBLAS kernel selection for the eager lm-head GEMM at each M. Under TP, a first-use stall on one rank also holds its peers in the next collective. #48572 (open, V1 runner) fixes one instance of this: the spec-sized logits all-gather. This PR covers all row counts in V2.

**Design.**
- `plan_batch_size_warmup` (pure, unit-tested) builds the step list:
  1. Prefill a pool of `min(max_num_seqs, budget // (q+1))` requests.
  2. For `r = pool..1`, decode `r` requests. With spec decoding, also decode `r-1` of them next to `b = 1..q-1` new prefills.
  3. Run one prefill of each capture size.
- `warmup_batch_sizes` turns the steps into `SchedulerOutput`s and drives them through the worker's `execute_model`/`sample_tokens`, the same path as `warmup_kernels`.
  - KV blocks are reserved with the existing `_warmup_block_counter`, so lookahead is included. They start at 1 and are recycled after their request finishes.
  - The KV connector is disabled during the pass, and block 0 is re-zeroed afterwards, as in `warmup_kernels`.
  - Sampling uses the model's default generation-config parameters, the ones serving requests get by default. It does not use `for_sampler_warmup()`, whose `prompt_logprobs` would make capture-size prefills allocate full-vocab logits for every prompt token.
- A CPU dry run checks the block and context needs first. If they don't fit, the pass logs a warning and skips.
- The hook sits in `Worker.compile_or_warm_up_model`, after `capture_model` and before the seed reset.

**Why opt-in.** Startup time grows with `max_num_seqs × num_speculative_tokens`, and most deployments don't need it. It pays off for latency-sensitive or large TP deployments where a first-use stall is visible.

**Limitations.**
- Skipped for PP, DP, PCP, adaptive verification, pooling and encoder models. DP engines may size different KV caches and so plan different steps, which would desynchronize their DP collectives.
- The pass covers one decode query length, so dynamic speculative decoding is only partly covered. It does not cover eager steps above the largest capture size, where cuBLAS can pick new kernels at each M; `CUDA_MODULE_LOADING=EAGER` is the M-independent backstop for module loading there. Prompt-logprobs shapes are also not covered.
- Some capture sizes may be warmed twice, because the plan does not ask the dispatcher which graph each step hits. That keeps the code small, at the cost of a few extra cheap steps.
