# [Model] Qwen4Exp: stage CPU-offloaded PLE rows on the host when UVA is unavailable

[Upstream PR](https://github.com/vllm-project/vllm/pull/62847) · state: open · merged: False

## Original PR description



## Overview

Qwen4Exp PLE `cpu_offload` currently requires UVA. When UVA is unavailable, the NVIDIA path now keeps the table in host memory and stages each step's rows through the staging path that #59958 added for disk offload, instead of failing at init. This lets Qwen3.8-Flash-Next run on one H100 under NVIDIA Confidential Computing, where #59981 turns UVA off.

Closes #62815. Related: #57224 (root cause: under CC, pinned host memory reports `is_pinned() == False` and UVA views of it go stale), #59981 (CC detection that disables UVA), #59958 (PLE disk offload, whose staging this PR shares), #54371 (UVA PLE offload).

**Not a duplicate.** #59958, #58815 and #58439 read PLE rows from the checkpoint files (disk / page cache). This PR keeps the table in anonymous host memory and needs neither UVA nor file-backed reads; in a confidential VM, storage I/O patterns are visible to the host, so disk-backed tables are not an option there. Since #59958 has landed, this PR reuses its per-step staging and only adds the host-memory row source.

## Claims

- With `cpu_offload` on and `is_uva_available()` false, Qwen4Exp (NVIDIA) selects a new `Qwen4ExpPLEHostMemoryEmbedding` instead of raising `Engram CPU offload requires UVA support`. BF16, FP8 and NVFP4 tables are supported.
- The per-step staging of disk offload moves into a shared `Qwen4ExpPLEHostStagedEmbedding` base, unchanged in behaviour. Disk offload and the new host-memory table differ only in where `_read_rows` reads the rows from.
- The forward only reads persistent device buffers, so the default `FULL_AND_PIECEWISE` CUDA graphs are kept.
- No change when UVA is available: the pinned UVA path and its prefetch are untouched.

## Validation

All on one H100 NVL 94 GB in CC mode (Azure `Standard_NCC40ads_H100_v5`, driver 580.95.05, CUDA 13.0).

**Unit tests (current head)**: nightly `5689c279` + this PR, `python -m pytest tests/models/qwen4_exp/test_ple.py tests/models/qwen4_exp/test_config.py` on that GPU: 140 passed, 8 failed, 2 skipped. The new and renamed cases pass: the graph-replay comparison against the resident table for both row sources (disk and host memory) in BF16, FP8 and NVFP4, the ETP owner masking, and the fallback selection. The 8 failures are the same set without this PR: 7 pinned/UVA tests fail because UVA views of pinned memory go stale under CC (this run has no #59981), and 1 config test needs PP=2 on a one-GPU node.

## Details

**Design.** PLE lookups depend only on token IDs, so the rows a step needs are known before its forward. #59958 stages them in `Qwen4ExpModelState.prepare_inputs`: n-gram IDs to the host, one stream sync, distinct rows read per storage plane, one H2D per plane into fixed device buffers, NVFP4 decoded on the GPU. This PR moves that into `Qwen4ExpPLEHostStagedEmbedding` with one abstract `_read_rows(name, ids, rows)`. `Qwen4ExpPLEDiskOffloadEmbedding` keeps its `preadv` reads there. `Qwen4ExpPLEHostMemoryEmbedding` gathers from the ETP-sharded host table with `index_select` on raw bytes, zeroes rows owned by other ETP ranks, and reduces after the lookup like the pinned-host table. `stage_checkpoint_rows` becomes `stage_host_rows`.

**Tradeoff: one host sync per step on this path.** The IDs hash the tokens sampled by the previous step on the GPU, so the read-back waits for that step to finish, which removes some async-scheduling overlap. This is the same sync disk offload already makes. Only the fallback pays it; the UVA path is unchanged. I could not measure the overlap loss on CC, since there is no UVA path to compare against there. `VLLM_GPU_SYNC_CHECK=error` could not be exercised on CC either: it first stops in #59981's staged input copy, because pinned host memory reports `is_pinned() == False` under CC.

**Limitations.**
- NVIDIA path only. The AMD Qwen4Exp path still requires UVA.
- ETP spanning DP ranks (`embedding_across_dp`) is rejected with `NotImplementedError`. TP/ETP within one DP rank is supported (rows owned by other ranks are zeroed, then reduced). Unlike disk offload, each rank keeps only its own rows in host memory.
- DeepSeek V4.1 Engram is not covered.
- The NVIDIA Qwen4Exp model never selects this path on stock main unless UVA is unavailable (for example with #59981 under CC, or where pinned memory is unavailable).

**CI.** The new tests live in `tests/models/qwen4_exp/test_ple.py` and `test_config.py`, which the existing Qwen4 Exp lanes run. The ETP owner-masking test also runs on CPU. CC hardware is not available in CI; the end-to-end results above were collected outside CI.
