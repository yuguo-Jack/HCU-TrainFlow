# [Bugfix][Tokenizer] Honor generation controls in DeepSeek V3.2

[Upstream PR](https://github.com/vllm-project/vllm/pull/64493) · state: open · merged: False

## Original PR description

## Overview

Honor the existing `add_generation_prompt` and `continue_final_message` controls in the DeepSeek V3.2 Python tokenizer. This fills the V3.2 gap corresponding to #64431 and #46256.

## Claims

- `add_generation_prompt=False` no longer adds an assistant header after the final user/developer message.
- `add_generation_prompt=True` opens a fresh assistant turn after a completed assistant message.
- `continue_final_message=True` leaves the final assistant message open: content prefills in chat mode and reasoning prefills in thinking mode.
- Thinking-mode content-only assistant messages remain invalid unless they include reasoning or tool calls, matching DeepSeek V3.2's reference encoder.
- Regression tests exercise the `ChatCompletionRequest` parameter path and are collected by the existing CPU renderer test job.

## Behavior before and after

| Case | Before | After |
|---|---|---|
| User message ends the prompt; `add_generation_prompt=False` | Still appends `<｜Assistant｜></think>` after the user text. | Ends at the user text; no assistant header is added. |
| Completed assistant message; `add_generation_prompt=True` | Ends at the assistant EOS, with no new assistant header. | Appends `<｜Assistant｜></think>` in chat mode, or `<｜Assistant｜><think>` in thinking mode. |
| Assistant content prefill in chat mode; `continue_final_message=True` | Appends EOS, so the model sees the prefill as a closed message. | Omits EOS so the model continues the prefilled content. |
| Thinking-mode reasoning prefill; `continue_final_message=True` | Closes `<think>` and appends EOS before generation resumes. | Leaves `<think>` open and omits EOS, so generation resumes inside reasoning. |
| Thinking-mode content-only assistant message; `continue_final_message=True` | Rejected because it has neither reasoning nor tool calls. | Still rejected, preserving DeepSeek V3.2's native thinking-format validation. |
| `continue_final_message=True` with a non-assistant final message | Accepted without continuation behavior. | Raises `ValueError`. |

`continue_final_message` and `add_generation_prompt` are mutually exclusive; the continuation cases use `add_generation_prompt=False`. Hugging Face documents these controls as opening a new assistant message versus removing the final message's ending marker to continue it. The thinking-mode validation follows the [DeepSeek V3.2 reference encoder](https://huggingface.co/deepseek-ai/DeepSeek-V3.2/blob/main/encoding/encoding_dsv32.py), which requires reasoning or tool calls for assistant messages in thinking mode.

## Cross-model behavior

These controls have shared meanings, but model renderers do not all implement the same policy:

- **DeepSeek V3.2 Python:** this PR adds the handling above.
- **DeepSeek V4 Python:** the current main implementation still has the gap. #46257 proposes the parallel fix and is open; its latest review asks that closed-history fixtures explicitly set `add_generation_prompt=False` and that tests pin the intended thinking mode.
- **DeepSeek V4.1 Python:** the current main implementation still has the gap. #62729 proposes the parallel fix and is open with approval; it covers content and reasoning prefills.
- **DeepSeek V4/V4.1 Rust:** #62189 proposes opening a new assistant turn after a final assistant message. The V4.1 issue report #64431 also records that Rust already handles `add_generation_prompt=False` and `continue_final_message` cases.
- **Generic Hugging Face renderer:** forwards these controls to `apply_chat_template`; the exact prompt depends on the model's chat template.
- **Mistral:** validates the flags, rejects using both together, and rejects `add_generation_prompt=True` after an assistant-final message.
- **Inkling:** supports `add_generation_prompt` but explicitly rejects `continue_final_message`.

This PR follows the DeepSeek fresh-turn behavior: `add_generation_prompt=True` after a completed assistant message opens another assistant turn. It does not claim all vLLM model renderers have identical behavior.

## Details

The V3.2 tokenizer wrapper previously discarded both request controls. Its encoder always emitted an assistant prefix after user/developer messages and always closed assistant messages with EOS. The change passes the controls into the encoder, conditionally renders the final assistant prefix, and omits EOS for a continued final assistant message. In thinking mode, a reasoning prefill remains inside the open `<think>` block; a content-only assistant message remains rejected in line with V3.2's reference format.

This does not duplicate #64453: that WIP PR enables custom chat templates for V3.2 variants; this PR handles generation controls for the built-in V3.2 format. They touch the same tokenizer module and test path, so the changes may need coordination when both are merged. No docs change is needed because this makes existing request controls work for V3.2 rather than adding a new user-facing option.
