# [Bugfix][KV Offload] Deduplicate replicated GQA heads in canonical storage

[Upstream PR](https://github.com/vllm-project/vllm/pull/62160) · state: open · merged: False

## Overview

Fix canonical tiering storage sizing when TP exceeds the number of KV heads, so replicated GQA caches can be persisted and reused across TP sizes. Discovered during the chunked-local work in #61886 and reproduced independently with full attention.

Follow-up: #62162 enables chunked-local canonical offload on top of this fix.

## Claims

- Canonical storage counts unique KV-head copies rather than physical TP ranks.
- Worker mmap population stays within the deduplicated row.
- Default CPU offloading, noncanonical layouts and existing MLA replication semantics are preserved.

## Details

Canonical mappings already deduplicate replicated GQA heads, but tiering allocated rows using physical world size. With one KV head, TP1 and TP2 therefore shared a storage namespace while expecting different file sizes (4096 versus 8192 bytes in the minimal Linux reproducer), causing the TP2 reader to reject TP1 files.

Carry the certified canonical replication factor into tiering's copy-count calculation and map population ranks to unique head slots. The canonical mapping's rank and writer-selection logic remains unchanged. Regression mutations removing either the sizing correction or the rank correction fail the targeted tests.

Canonical format **v2** isolates compact files from v1 readers for every TP size, preventing old readers from treating new files as truncated and deleting them. Compatible v2 TP1/TP2 instances still share caches; NHD/HND remain separate. All v1 canonical caches become cold after upgrading, even where row size did not change. No automatic migration or deletion is performed; noncanonical namespaces are unchanged.

Duplicate-work check: #56953 concerns per-group slot sizing, whereas this fixes replicated TP copies; #60782 refactors shared-region classes without changing their sizing semantics. Neither implements this fix. Related tracking issue: #61886 (not closed by this PR).
