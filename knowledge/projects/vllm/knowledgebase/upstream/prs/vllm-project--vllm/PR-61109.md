# [ROCm][Perf] Two-level all-reduce for TP=8 across two XGMI islands (8x MI210)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61109) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On 8x MI210 the GPUs form two fully connected 4-GPU XGMI islands joined only by PCIe. The flat custom all-reduce needs every GPU linked to every other, so at TP=8 it turns itself off and every all-reduce goes through RCCL's ring, which crosses PCIe on every step. This PR adds an `ISLAND` backend that reduces inside each island first, then across GPU pairs:

- below 2.25 MiB: the existing custom all-reduce inside each island, then across the GPU pair at the same island position;
- from 2.25 MiB: RCCL reduce-scatter inside the island, all-reduce of the quarter-size shard across the four pairs, all-gather inside the island.

It adds no kernels (it reuses `CustomAllreduce` and `PyNcclCommunicator`), and both paths also run inside CUDA graphs. Fully connected gfx90a groups (MI210 TP=2/4, MI250X TP=8) are handled by #63226; the two PRs don't overlap.

## Claims

- TP=8, Qwen2.5-72B on 8x MI210: decode TPOT −12.5% / −23% / −18% at 1 / 8 / 16 users, TTFT −18% on a 3k-token prompt.
- Only active for that topology on ROCm; everything else keeps its current backend. `VLLM_ROCM_ISLAND_ALLREDUCE=0` turns it off.

## Validation

8x MI210 (GPUs 0-3 and 4-7 are the islands), ROCm 7.2, upstream's nightly ROCm image with this PR's files mounted over it.

`vllm serve Qwen/Qwen2.5-72B-Instruct -tp 8 --max-num-seqs 16`, `vllm bench serve --dataset-name random --ignore-eos --temperature 0` (128 in / 256 out; prefill 3,000 in / 32 out), four boots per comparison in on-off-off-on order:

| | 1 user | 8 users | 16 users |
|---|---|---|---|
| Decode TPOT p50, off → on | 26.7 → 23.3 ms | 53.2 → 41.0 ms | 53.9 → 44.1 ms |

Prefill 3k TTFT p50: 1,099 → 905 ms. With `--max-num-seqs 256`, 192-480-token prompts run the large path inside CUDA graphs and their TTFT drops 7-16%. Greedy outputs of an on boot and an off boot match on 9-12 of 16 prompts, the same rate as two boots of the same arm. No accuracy benchmark was run.

Tests: `pytest tests/distributed/test_island_all_reduce.py` gives 13 passed (topology detection without GPUs, sums vs fp32 on both paths in bf16/fp16, islands interleaved in rank order, declined sizes, custom path off, graph replay through `graph_capture()`). `test_custom_all_reduce.py` and `test_pynccl.py` give the same result with and without this PR. With #63226 applied too, TP=8 still selects `ISLAND`. A server with `VLLM_GPU_SYNC_CHECK=error` and speculative decoding (Qwen3-8B + DFlash, both model runners) run cleanly. AMD CI has no MI200, so only the topology test runs there.

## Details

- Islands come from the link topology (`is_fully_connected`), so the TP rank order doesn't have to follow them. Anything else falls through to the existing dispatch.
- Both thresholds are 2.25 MiB (`VLLM_ROCM_ISLAND_AR_CUSTOM_MAX_BYTES`, `VLLM_ROCM_ISLAND_AR_HIER_MIN_BYTES`): the microbenchmark crossover is near 1 MiB, but 1 MiB made 96-160-token prompts 3-9% slower in a server.
- The custom kernels always copy into the pre-registered buffer: registered graph buffers give wrong sums on MI210 (`test_custom_allreduce[test_target1-2-2]` fails on main; #63226 forces copy-in for the flat path for the same reason).
- With a draft model on the V1 model runner the custom path is off: V1 replays drafter graphs before `graph_capture()` fills in the buffer addresses, which crashed with `hipErrorIllegalAddress`. V2 is unaffected.
- Off under `VLLM_BATCH_INVARIANT`, since the algorithm depends on size.
- Limitations: tested on 8x MI210 with one hidden size (6144). Running the large path alongside GPU-direct RDMA from the same GPUs hard-reset our node, which looks like a platform issue. `--disable-custom-all-reduce` doesn't turn the backend off yet, because vLLM sets it itself on MI200 today; I'll follow up once #63226 lands.

No existing PR or issue covers this; related: #63226, #19744 (QuickReduce), #46065 (AITER all-reduce).

Questions: should it be on by default for this topology or opt-in? Is the GPU-free test plus our MI210 logs enough without MI200 CI?
