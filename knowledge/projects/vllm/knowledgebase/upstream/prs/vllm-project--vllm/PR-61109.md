# [ROCm][Perf] Island all-reduce for TP8 on 2x4 XGMI-island nodes (MI210)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61109) · state: open · merged: False

## Original PR description



## Overview

Adds an `ISLAND` all-reduce backend for a TP group of 8 on ROCm nodes whose GPUs form two fully connected 4-GPU XGMI islands joined only by PCIe (8x MI210). Today such a group uses RCCL's flat ring for every all-reduce, because the custom all-reduce needs full connectivity and is enabled on MI300+ only.

## Claims

- On 8x MI210, TP=8, `Qwen/Qwen2.5-72B-Instruct`: decode TPOT p50 −12.5% at 1 user, −23% at 8 users, −18% at 16 users; TTFT for a 3,000-token prompt −18%; output throughput +14% to +29%.
- With vLLM's default capture sizes (graphs up to 512 tokens), TTFT for 192–480-token prompts −7% to −16%, because the large-tensor path also runs inside CUDA graphs.
- Per all-reduce it is 1.1–2.4x faster than `PyNcclCommunicator` up to 1.5 MB and 1.4–1.9x from 2.25 MB to 48 MB.
- No new kernels: it composes `CustomAllreduce` and `PyNcclCommunicator`.
- Active only on ROCm, TP=8, two-island topology, when neither the flat custom all-reduce nor AITER is in use; everything else keeps its current backend. `VLLM_ROCM_ISLAND_ALLREDUCE=0` turns it off.

## Validation

Hardware: one node with 8x MI210 (gfx90a), ROCm 7.2.3, RCCL 2.27.7. Software: the nightly ROCm image at `2eb491e` with the four changed Python files of this PR mounted over the installed package.

**End to end**, backend on vs off (off = PyNccl only). `vllm serve Qwen/Qwen2.5-72B-Instruct --tensor-parallel-size 8
--max-num-seqs 16 --max-model-len 8192`, with `VLLM_ROCM_ISLAND_ALLREDUCE=1` or `0`; load from
`vllm bench serve --dataset-name random --ignore-eos --temperature 0 --request-rate inf` (decode: 128 tokens in / 256 out; prefill: 3,000 in / 32 out). Four server boots in A-B-B-A order; each cell is the mean of the two boots of that
arm, which agree within 0.5% on TPOT. No request failed.

**CI gap.** AMD CI has no MI200 runners, so the GPU tests skip there (they need 8 ROCm GPUs in two islands); only the topology-detection test runs. The numbers above are the validation for the hardware path.

## Details

- **Small tensors (< 2.25 MiB):** `CustomAllreduce` inside each 4-GPU island, then across the GPU
  pair at the same island position (a 2-GPU group, which `CustomAllreduce` already allows without full connectivity).
- **Large tensors (>= 2.25 MiB):** `PyNcclCommunicator` reduce-scatter inside the island, all-reduce of the
  quarter-size shard across the four pairs, all-gather inside the island. A quarter of the data crosses PCIe, on four
  links in parallel.
- **Island detection.** The islands are found from the link topology: the GPUs with a direct XGMI link to the first
  GPU form one island and the rest the other, and both must be fully connected groups of four. The TP rank order does
  not have to follow the islands; the k-th GPU of one island is paired with the k-th GPU of the other.
- Both paths run eagerly and inside CUDA graphs.
- Other inputs (size not a multiple of 16 bytes below the large threshold, non-contiguous) return to the existing
  dispatch chain.
- **Thresholds.** In a tight loop the hierarchical path overtakes the custom path at about 1 MiB. In a running server
  the break-even is about 2.25 MiB: with both thresholds at 1 MiB, TTFT for 96–160-token prompts was 3–9% worse than with 3 MiB (measured on our v0.25.1-based fork, A-B-B-A). Both default to 2.25 MiB and are tunable
  (`VLLM_ROCM_ISLAND_AR_CUSTOM_MAX_BYTES`, `VLLM_ROCM_ISLAND_AR_HIER_MIN_BYTES`).
- **Copy-in path only.** The custom kernels are called with `registered=False`, also inside graphs. On MI210 with
  ROCm 7 the registered-graph-buffer mode returns wrong sums; that is the pre-existing failure of
  `test_custom_allreduce[test_target1-2-2]` on this node.
- **Batch invariance.** The algorithm depends on tensor size, so the backend is off under `VLLM_BATCH_INVARIANT` (documented in `docs/features/batch_invariance.md`).
- **Limitations.** TP=8 on this topology only. Tested on MI210 only. A standard 4-module MI250 node is fully
  XGMI-connected (every GPU pair is one hop), so the backend does not activate there. Thresholds come from one node type. On our nodes, running the large path at the same time as GPU-direct RDMA writes out of the same GPUs (a KV-transfer connector that registers GPU memory with the NICs) hard-reset the machine; this looks like a platform issue outside vLLM and is the reason the large path has its own switch.
- **Not a duplicate.** I searched open and closed PRs and issues for MI200/MI210/MI250, "island" and two-level
  all-reduce and found none. Related: #19744 (QuickReduce), #46065 (AITER custom all-reduce), both MI300-class.

**Questions for maintainers**

1. Default on for the detected topology, or opt-in?
2. AMD CI has no MI200 runners. Is the GPU-free topology test plus the logs from our MI210 node enough, or do you want something else?
3. Any preference on where the backend sits in the dispatch order? It runs after AITER and before `CUSTOM`, and only when neither of those is active.
