# [Perf][ToolParser] Scan required-tool streaming deltas incrementally

[Upstream PR](https://github.com/vllm-project/vllm/pull/60882) · state: open · merged: False

## Original PR description

## Overview

The required-tool scanner introduced in [#60354](https://github.com/vllm-project/vllm/pull/60354) scans the entire accumulated JSON array on every streaming delta. This repeats CPU work as tool arguments grow, including ordinary document and code-writing calls.

The scanner now owns accumulated text and lexical state and accepts only `delta_text`, so each update scans only new text. This also lets the generic required-tool path work with engine-based parsers that do not retain text history.

This PR also Fixes #49216. With strict tool calling disabled, engine-based parsers can route
`tool_choice="required"` to the generic JSON parser without accumulated history.
The scanner now retains that history, including across reasoning-to-tool
transitions, while the engine path keeps its text and token history empty.

## Claims

Reduce CPU time for generic `tool_choice="required"` streaming while preserving tool names, arguments, indices and announcement timing. The helper uses one scanner per stream; the stateless mode is removed.

## Validation

Required-tool helper CPU timings against the original scanner:

| Workload | Before | After | Speedup |
| --- | ---: | ---: | ---: |
| 256-character string | 0.87 ms | 0.41 ms | 2.1x |
| 1 KiB string | 5.91 ms | 1.45 ms | 4.1x |
| 4 KiB string | 65.90 ms | 5.66 ms | 11.6x |
| GPU-generated document replay, 1,610 argument characters | 11.09 ms | 2.05 ms | 5.4x |

The first three rows are five-run medians with four-character increments. The last row replays 400 argument increments captured from Qwen3.5-0.8B, with ten-run medians. Each version gets one warmup and execution order alternates. Every run checks reconstructed arguments; per-delta outputs also match the original scanner. Before/after ranges are 0.870-0.916/0.412-0.421 ms, 5.906-5.924/1.444-1.452 ms, 65.550-65.969/5.643-5.682 ms and 11.031-11.124/2.037-2.052 ms.

These measurements cover CPU parsing. Small lookup calls save little time, and they do not establish serving throughput gains.

The updated parser and required-tool suites pass **6,640 tests and 384 subtests**. The new streaming regression covers both legacy and engine adapters; the engine-adapter case fails with the original extraction method. A differential experiment compares **12,009 inputs and 2,419,657 deltas** against the original scanner with no differences, covering multiple calls, reordered fields, nesting, escapes, Unicode, empty deltas and truncated output.

The updated parser is validated by replaying GPU captures from Qwen3.5-0.8B on NVIDIA GB10 using `pythonic` tool parsing, with and without `qwen3` reasoning. Both complete parsers produce identical outputs for **42 streams and 9,806 deltas**, covering `n=1/2`, parallel calls, nested parameters, length truncation and reasoning-to-tool transitions. Random UUID values are normalized; ID presence and all other fields are compared.

Tokenizer fixtures use equivalent ModelScope snapshots with unchanged assertions. Full touched-file pre-commit and whitespace checks pass.

## Details

Each `StreamState` owns a scanner. Lexical state is updated directly instead of copied into and out of local variables. The text length before each append determines which calls and argument characters have already been sent, preserving announcement timing. Model grammars and native tool-parser routes are unchanged. Legacy parsers still retain their own history, so this does not eliminate all text-copying costs.
