# [Perf][MRv2] Add static split selection for token logprobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61991) · state: open · merged: False

## Original PR description

## Overview

Addresses [[#60095](https://github.com/vllm-project/vllm/issues/60095)](https://github.com/vllm-project/vllm/issues/60095) with an alternative token-logprob implementation to [[#60097](https://github.com/vllm-project/vllm/pull/60097)](https://github.com/vllm-project/vllm/pull/60097). This implementation uses vector-tiled reduction, a two-stage merge, and static vocabulary-split selection.

## Claims

- On an NVIDIA H200, the candidate was **3.54× faster in CUDA Graph device time** and **1.36× faster in synchronized wall time** than #60097, using geometric means across 57 shapes.
- Compared with the pre-PR baseline used in the experiment, the candidate was **12.20× faster in device time** and **2.19× faster in synchronized wall time**. This is not a comparison against current `main`.
- All 57 benchmark shapes passed the correctness checks in three runs per implementation.

## Validation

- H200 kernel microbenchmark: 57 combinations of vocabulary size, batch size, and K; three runs per implementation; correctness checks passed.
- The measurements compare complete source snapshots. The candidate is based on a newer `main` snapshot than #60097, so the comparison does not isolate the split-selection change.
- These are synthetic-logits kernel measurements. No end-to-end model-serving, TTFT, or throughput evaluation has been run.
- The benchmark scripts, raw results, environment snapshot, and analysis are archived [[here](https://github.com/RichterWang/vllm-lab/tree/e569cbdb316493b3b3f56c05467302ec1831c71a/benchmarks/kernels/issue60095/h200_reference)](https://github.com/RichterWang/vllm-lab/tree/e569cbdb316493b3b3f56c05467302ec1831c71a/benchmarks/kernels/issue60095/h200_reference). To regenerate the three-way analysis, run `python analyze_three_way.py --input-dir results` from that directory.

## End-to-end serving validation

- An exploratory H100 serving benchmark was run with Qwen3-0.6B (logprobs=5) at concurrency 1, 16, and 64. Each configuration used three alternating runs of 200 requests.
- Compared with the PR's direct parent, median output throughput was +4.7% at concurrency 1, -5.3% at concurrency 16, and +10.5% at concurrency 64. The concurrency-64 throughput improvement was positive in all three paired rounds; concurrency 16 was mixed. These results indicate a workload-dependent effect, not a uniform serving speedup.
- The tested implementation revision was b2625fd. The benchmark used the PR's logprob.py in the parent environment; it was not a separately installed PR wheel. All 27 runs completed with zero benchmark errors. This serving experiment is separate from the H200 kernel microbenchmark above.
Raw outputs, logs, telemetry, analysis, and environment details: [H100 end-to-end report](https://github.com/RichterWang/vllm-lab/blob/my_60095_pr/benchmarks/kernels/issue60095/h100_e2e_61991/results/h100_20261016T152655Z/REPORT.md).

The result is exploratory: three rounds do not establish statistical significance, and the benchmark covers one model and workload. It does not establish broad end-to-end gains.

## Details

#60097 uses online reduction and its own split heuristic. This implementation instead computes per-tile max/sum partials with vector loads, merges those partials in a second kernel, then gathers the requested token logits. A static rule selects the split count from vocabulary size, batch size, and the GPU's SM count; no startup calibration or autotune cache is used.

The candidate comparison is against #60097's implementation at `0ddd6017793c943a2091a5800f0cbac1daaa3e02`. The pre-PR baseline is `d09ff7763747bbe7cd153edd8017479804f47be7`, the direct parent of #60097. Because the candidate is based on a newer `main` snapshot, the baseline-to-candidate result compares full implementations rather than attributing the entire gain to one change.
