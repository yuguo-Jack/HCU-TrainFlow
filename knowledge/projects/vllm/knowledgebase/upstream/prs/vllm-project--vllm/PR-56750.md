# [Perf][Distributed] Make MNNVL Lamport RS/AG message-size caps configurable

[Upstream PR](https://github.com/vllm-project/vllm/pull/56750) · state: closed · merged: False

## Original PR description

## Purpose

DeepSeek-V4.1 enables sequence parallelism when a MegaMoE backend is selected (EP, TP>1, PP1). Every decoder layer then gathers the mHC hidden states before attention and reduce-scatters the attention output through `CustomAllreduce`'s MNNVL multicast Lamport kernels; messages larger than 16 MiB (reduce-scatter) or 2-8 MiB (all-gather) fall back to the NCCL collective. At `max_num_batched_tokens 65536`, full-chunk messages are about 640 MiB (RS) / 80 MiB (AG) per layer, so most prefill SP collectives take the fallback.

On 8xB200 TP8 the existing Lamport kernels are faster than the production NCCL fallback across the whole relevant range (below), so this PR exposes both caps as `VLLM_MNNVL_REDUCE_SCATTER_MAX_SIZE_BYTES_MB` and `VLLM_MNNVL_ALL_GATHER_MAX_SIZE_BYTES_MB`. Defaults are preserved; raising a cap only grows the multi-stage symmetric staging buffer (6x the cap, plus AG x world_size). Recommended recipe for this deployment: RS=96, AG=40 MiB (staging 96 MiB -> 1.88 GiB per rank). Giant-chunk RS (>320 MiB) is intentionally left to NCCL: the kernel advantage there is <= 2% end-to-end unmeasurable, and a 640 MiB cap would cost a 4 GiB stage per rank.

Why this is not duplicating existing work: #55072 adds a *new* low-SM multimem reduce-scatter backend with a dispatcher policy for the <=16/64 MiB bands; this PR does not introduce any new kernel or backend policy, it only sizes the existing Lamport path (the two are complementary and can be recombined later). #49194 changes NCCL symmetric-memory RS staging, not the custom Lamport path. No other open PR makes these caps configurable.

## Test Plan

Deployment (DeepSeek-V4.1-Flash, 8xB200, TP8/EP, FlashInfer sparse MLA, FP8 KV, SP via MegaMoE backend):

```bash
vllm serve /gpfs/mszn/models/deepseek-ai/DeepSeek-V4.1-Flash \
  --trust-remote-code --served-model-name dsv4 --tensor-parallel-size 8 \
  --distributed-executor-backend mp --enable-expert-parallel \
  --tokenizer-mode deepseek_v41 --attention-backend FLASHINFER_MLA_SPARSE_DSV41 \
  --kv-cache-dtype fp8 --max-model-len 1048576 --max-num-batched-tokens 65536 \
  --max-num-seqs 96 --gpu-memory-utilization 0.90 \
  --kernel-config '{"moe_backend":"deep_gemm_mega_moe"}' --no-enable-flashinfer-autotune
# PR arm adds: VLLM_MNNVL_REDUCE_SCATTER_MAX_SIZE_BYTES_MB=96 VLLM_MNNVL_ALL_GATHER_MAX_SIZE_BYTES_MB=40
```

Benchmarks on the same server/session, seed 42, `--ignore-eos`:

```bash
vllm bench serve --backend vllm --endpoint /v1/completions --model dsv4 \

  --prefix-repetition-output-len 1024 --num-prompts 960 --max-concurrency 96 \

```

Kernel-level sweep: 8-GPU offline harness timing `CustomAllreduce.custom_{reduce_scatter,all_gather}` vs the NCCL fallback at hidden 5120 BF16 (max-rank median CUDA-event time), included in the PR records.
