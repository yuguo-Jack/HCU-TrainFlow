# Align speculator hidden norm in GLM-4.5/4.6 MoE and GLM-OCR MTP with GLM5Next to recycle post-final-hidden.

[Upstream PR](https://github.com/vllm-project/vllm/pull/62234) · state: open · merged: False

## Original PR description

### Overview

Three GLM-family MTP (Multi-Token Prediction) models — `glm4_moe_mtp.py` (GLM-4.5 / GLM-4.5-Air / GLM-4.6), `glm4_moe_lite_mtp.py`, and `glm_ocr_mtp.py` — return the **pre-final-norm** hidden from the MTP layer, so the speculator recycles a hidden that is one RMSNorm short into the next draft step's `hnorm`. The established GLM/DeepSeek-NextN contract (already merged in vLLM by #47448 and also SGLang's `glm4_moe_nextn`/`deepseek_nextn` `vllm/models/glm5next/common/mtp.py`) recycles the **post-final-norm** hidden. This PR extends that contract to the three models it missed. Draft-only change; verified output is unaffected.

### Claims

- **Correctness/contract alignment:** each MTP layer now applies the final norm once (fused `shared_head.norm(hidden, residual)`) and returns the post-final-norm hidden for both tuple positions, with `compute_logits` consuming it directly — identical to #47448 and `glm5next`.
- **Lossless:** speculative decoding verifies every drafted token, so the target-visible output is unchanged; only the drafter's recycled state changes (affects draft steps ≥1, i.e. `num_speculative_tokens ≥ 2`).
- **No performance regression, and no performance claim.** On a real checkpoint (GLM-4.5-Air) a controlled, paired acceptance measurement shows **no statistically significant change** in draft acceptance (details below). This is a pure correctness fix — it is not expected or claimed to change speed.

### Validation

**Unit test** — `tests/v1/spec_decode/test_mtp.py::test_glm_mtp_layer_recycles_post_final_norm_hidden`, parametrized over all three layer classes. Uses a **real `RMSNorm` with non-uniform weights** and asserts the layer returns `(post, post)` equal to the independently-computed fused final norm of `block_hidden + residual` (and not the pre-norm value). It also asserts **logits-equivalence**: the fused `shared_head.norm(hidden, residual)` is numerically equal to the prior eager `shared_head(residual + hidden)`, so the draft-logits input is preserved. Passes on the fix; fails on all three originals.

**Acceptance measurement (end-to-end, fixed-prefix)** — GLM-4.5-Air (bf16), `method=mtp`, k=3, 600 gsm8k prompts, each generating one spec-decode round from a **fixed starting prefix**, paired per prompt. Position 0 does not consume the recycled hidden, so it is a near-control (not bit-exact — see below):

| position | before (pre-norm) | after (post-norm) | diff | p |
|---|---|---|---|---|
| p0 (near-control) | 0.7330 | 0.7298 | −0.0032 | 0.88 |
| p1 | 0.5438 | 0.5479 | +0.0042 | 0.86 |
| p2 | 0.2232 | 0.2277 | +0.0045 | 0.82 |

Paired per-prompt accepted tokens: +0.018 ± 0.016 (Wilcoxon p=0.25). The position-0 result is **statistically consistent with no change** (p=0.88); its tiny numeric drift is floating-point from the eager→fused add+norm (the two are mathematically identical), not a real acceptance change. No affected position shows a significant change either. This is an **end-to-end acceptance comparison from fixed prefixes** — it does not isolate each later position's *conditional* acceptance, since draft histories can still diverge within a round. Net: **acceptance (and thus speed) is effectively unaffected**, consistent with a pure correctness fix.

**Reference** — SGLang `glm4_moe_nextn.py` / `deepseek_nextn.py` apply the final norm and recycle the post-norm hidden; GLM-4-MoE NextN is a faithful DeepSeek-V3 NextN clone.

### Details

Root cause: the MTP layer forward ended with `hidden_states = residual + hidden_states; return hidden_states` (pre-final-norm), and `compute_logits` applied `shared_head` to it. The AR / multi-module speculators store the model's returned hidden as the next step's `previous_hidden_states` (fed into `hnorm`). With a single pre-norm tensor the recycled state is missing the final `shared_head` RMSNorm that DeepSeek/`glm5next` apply; the logits path was always correctly single-normed. Fix (per file):

```python
# Apply the final norm once (fused add+norm) and recycle the post-final-norm
# hidden; compute_logits consumes it directly. Matches #47448 and glm5next.
hidden_states, _ = self.shared_head.norm(hidden_states, residual=residual)
return hidden_states, hidden_states
```

plus `compute_logits`: `shared_head.head, hidden_states` (drop the second norm). Affects the single-module AR path (`num_nextn_predict_layers=1`, k≥2 — the common GLM-4.5/4.6 case) and the multi-module path; k=1 is unaffected.

No speculator change is needed, and the two tuple elements are intentionally the same post-norm tensor — identical to #47448 and `glm5next`, which flow through the same recycle sites. The AR step-0 setup takes the `last_hidden_states is hidden_states` branch and stores `last_hidden_states[idx]`, which is now the post-norm hidden; AR steps ≥1 (`_generate_draft`) and the multi-module path recycle the second tuple element unconditionally. So the post-norm hidden is what gets recycled on every path. The fused `shared_head.norm` is mathematically identical to the prior eager `shared_head(residual + hidden)`, so draft logits are preserved up to floating point (asserted in the unit test).

Could we double-check whether the v1 proposer also needs an update for this new tuple-return contract?

`SpecDecodeBaseProposer.model_returns_tuple()` recognizes `DeepSeekMTPModel`, `DeepseekV32MTPModel`, `Glm5NextMTPModel`, and `KimiK3MTPModel`, but not `Glm4MoeMTPModel`, `Glm4MoeLiteMTPModel`, or `GlmOcrMTPModel`.

Since the speculative config rewrites these GLM models to the corresponding `*MTPModel` architecture names, it seems possible that the proposer may still treat `(hidden_states, hidden_states)` as a single Tensor. If so, the later indexing or sampling of `last_hidden_states` could receive a tuple instead of a Tensor.

I may be missing another dispatch path here, but would it make sense to update the tuple-return handling for all three architectures, including the corresponding paths in `glm4_moe_lite_mtp.py` and `glm_ocr_mtp.py`, or otherwise verify this contract in the proposer?
