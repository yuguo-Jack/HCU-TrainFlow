# [Simulator] Timing, recording, disaggregated prefill and configuration search for simulated execution

[Upstream PR](https://github.com/vllm-project/vllm/pull/61506) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Simulated execution for vLLM. The real engine runs (scheduler, KV cache manager, prefix caching, async scheduling, frontend), but each step takes the time a timing model predicts instead of running the model, so a deployment's TTFT, TPOT and throughput can be predicted, and its configuration searched, without its hardware. Design and discussion: RFC #61305.

This includes and builds on @sagearc's KV cache simulator (#47922, which this PR contains with its commits and authorship), at the maintainers' choice of landing order: #47922 first and this on top, or both together.

## Claims

- **Timing:**
  - `SimulationConfig` selects a per-step timing provider: `zero`, `linear`, `table` (k-NN over recorded steps), `replay` (exact batch-composition match), or a plugin class.
  - A step's predicted host time holds the engine thread; its device time runs on a modeled device queue, as under async scheduling.
- **Recording:** `record_step_timing` logs a real deployment's per-step device and host times, KV transfers and NIXL read postings in the providers' format, without waiting on the device.
- **Clocks:** offline runs on `fast_forward` or deterministic `virtual` clocks, much faster than real time; `vllm serve --simulate-forward` runs on the real clock behind any client.
- **Simulated features:**
  - speculative decoding (sampled acceptance);
  - TP / PP / DP, including MoE DP, and prefill and decode context parallelism;
  - quantized checkpoints, built with their weight quantization as deployed, including online FP8 quantization;
  - GPU-free runs on the CPU platform, modeling the GPU deployment's settings;
  - CPU KV offloading;
  - multi-turn sessions;
  - a host-time model fitted from a recording.
- **Disaggregated prefill (NIXL):**
  - in-process driver for any P:D ratio;
  - served instances behind any proxy;
  - heterogeneous TP;
  - push mode with prefill PP;
  - the decode instance's read-posting cost (see #55434).
- **Configuration search:** `vllm bench sweep simulate` runs a `vllm bench sweep serve` experiment's combinations in simulation, optionally searching each for the highest request rate meeting latency SLOs. It covers aggregated and P/D combinations, and its output works with the existing sweep plots.
- **Off by default:** with simulation off nothing changes. There are no new CPU/GPU syncs, the config hash is unchanged, and the core changes (about 370 lines outside the simulator) are seams it reuses (the CPU platform's hybrid block-size fix it needed landed separately as #61805):
  - MRV2: `ActiveKVConnector.register_kv_caches`, and runner and worker methods split out for overriding (KV cache allocation, request-state updates, connector creation, device binding);
  - NIXL: a `worker_cls` attribute on the pull and push connectors, and shared lease and side-channel-port helpers;
  - `vllm bench serve`: `get_request_delays` and the metric-result builders factored out, so simulated runs report the same metrics;
  - fake implementations of the three FP8 quantization ops, so online quantization runs on meta weights;
  - the worker-class selection in `SimulationConfig`, CPU-platform settings that keep a modeled GPU deployment's configuration, and optional `trace_decode_token_ids` on the completion and chat requests;

## Validation

**Sensitivity to step-time error.** Simulated execution keeps the scheduler in the loop, so an error in step time also changes queueing and batch sizes. To see how far that carries, Qwen3-8B (AISimulate timing, H200) was run with every step's device time scaled by 0.97 and 1.03, on the same 400 requests (random 1024/256, Poisson arrivals) at each load. The table gives each metric's relative change divided by 3%, as the mean (min–max) over 5 seeds:

| Load ρ (fraction of saturated throughput) | 0.3 | 0.6 | 0.8 | 0.9 | 0.96 | 1.0 |
| --- | --- | --- | --- | --- | --- | --- |
| Mean TPOT | 1.3× | 1.6× | 2.1× | 2.4× (2.1–2.6) | 2.3× | 2.1× (1.5–2.6) |
| P99 TTFT | 1.4× | 2.0× | 2.0× | 4.7× (2.2–14) | 5.2× (1.9–14) | 14× (2.2–27) |
| Max rate meeting P99 TTFT ≤ 500 ms | 1.06× (1.00–1.09), independent of load |

The max rate under an SLO moves about as much as step time does. Mean TPOT moves up to about 2.4× as much, and the factor stops growing near saturation. P99 TTFT close to saturation moves by a large, seed-dependent amount. A step-time model that is accurate to a few percent therefore gives max rate and TPOT to a similar accuracy, but cannot pin down tail TTFT near saturation.

## Details

- **Not a duplicate:**
  - #47922 is the base of this PR and is included.
  - RFC #61406 and #61407 propose a related simulator, with a meta-mode forward for CPU CI and the simulation outside the tree behind import-time hooks. This PR keeps simulation in the tree behind `SimulationConfig` and skips the forward instead of running it. The two meet at the step-timing contract: an analytical predictor plugs in as a `TimingProvider` plugin, and one wrapping AISimulate (the successor of AIConfigurator) already runs out of tree. We would like to converge with it rather than maintain two simulators; on #61406 we proposed landing #47922, then this PR, then #61407's meta forward as an option of the simulated runner, and its author agreed with that option.
- **Size:** about 6.9k lines, roughly 2.1k of them tests, docs and CI. The feature commits are kept separate and can be split as maintainers prefer.
- **Reading guide:** the parts build on each other, and each part after the first can be reviewed on its own.
  1. *Overview:* `docs/features/simulated_execution.md`.
  2. *Core changes* (about 370 lines, listed under "Off by default" above). The largest are in `vllm/benchmarks/serve.py`, `vllm/v1/worker/gpu_worker.py`, `vllm/platforms/cpu.py` and `vllm/v1/worker/gpu/model_runner.py`.
  3. *Simulator core* (about 1.5k lines): `vllm/config/simulation.py` (options and worker-class selection); `simulated/timing.py` (`StepDescriptor` → `TimingProvider` → `StepCost`, the built-in providers, and the clocks); `simulated/model_runner.py` (MRV2 bookkeeping with the forward replaced by the predicted time); `simulated/worker.py` (no weights or KV tensors). Tests: `tests/v1/worker/simulated/test_timing.py`, `tests/v1/e2e/test_simulated_forward.py`.
  4. *Offline driver and recording:* `simulated/offline.py` (`make_engine`, `run`, `simulate` on the virtual and fast-forward clocks) and `simulated/recording.py` (`record_step_timing`).
  5. *KV transfers* (about 1.5k lines): `simulated/kv_transfer.py` (connector worker side, CPU offloading), `simulated/kv_nixl.py` (pull- and push-mode NIXL), `simulated/disaggregated.py` (in-process P/D driver). Tests: `test_kv_transfer.py`, `test_kv_nixl.py`.
  6. *Configuration search:* `vllm/benchmarks/sweep/simulate.py`, `docs/benchmarking/sweeps.md`, `tests/benchmarks/sweep/test_simulate.py`.
- **Known limitations:**
  - Real prefill steps run about 4% slower under sustained load, which a replay cannot capture.
  - The read-posting model is linear in runs of consecutive blocks.
  - Recording MoE-DP gathers step descriptors on the engine thread every step.
  - The simulation clocks are process-wide objects. An explicit runtime handle would be cleaner, at the cost of threading it through engine construction.
  - On the CPU platform, layers still pick the CPU's attention backends and kernels, so a model needing a GPU-only one (sparse MLA, DCP, NVFP4 or MXFP4 weights, online FP8 quantization) does not build there.
- **AI assistance:** this PR was developed with Claude Code, and the author reviewed every change. The submitting human has reviewed every changed line and run the tests above.
