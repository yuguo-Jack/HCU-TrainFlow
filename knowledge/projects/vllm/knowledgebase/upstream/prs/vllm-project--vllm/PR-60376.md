# [Perf] Faster BF16x3 router GEMM at large batch sizes on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/60376) · state: open · merged: False

## Original PR description

## Overview

Add a large-M path to the SM100 BF16x3 router GEMM. Past a shape-dependent crossover (448-1024 tokens), a Triton kernel splits the FP32 router weights into three BF16 planes once per call, and a new direct-orientation CuTeDSL tcgen05 GEMM (tokens on the MMA M side, cta_group=1/2, split-K with the existing reduce, 256-bit epilogue stores) consumes them. Below the crossover, the existing in-kernel-decomp kernel runs with tuned tile/split-K bands. Dispatch and warmup share one `_pick_config`; tuning tables come from GB300 sweeps of both tiers.

The dispatched op is faster at every measured token count on the MiniMax-M3.1 router shape (K=6144, N=128): 1.1-1.5x at 129-2048 tokens and ~1.8x at 8K+ tokens, sustaining 79% of the measured B300 BF16 tensor-core ceiling at M=16384 while performing 3x the MACs of a plain GEMM.

**19/19 SM100 numerical cases passed on B300** (FP32 outputs vs FP64 reference, mean absolute error below `5e-6`; both dispatch tiers, one- and two-CTA large-M execution, multi-chunk accumulation, partial token-pair tail, odd-expert fallback). In an nsys trace of an M3-MXFP8 serving run, traced router GEMM time at large M drops from 14.5 ms to 6.9 ms (2.1x) with total GPU time equal between arms. dspark acceptance length is unchanged (~2.0 both arms).

Caveats: no task-level quality eval yet; all perf numbers are B300 (GB200 untested).

## Details

The existing swap-AB kernel repeatedly decomposes weights per token tile and places tokens on the MMA N side. The large-M path first decomposes contiguous FP32 `W [N,K]` into `[3,N,K]` BF16 terms, then uses tokens on the MMA M side with vectorized epilogue stores. One-CTA and two-CTA configurations provide different work granularities. Main-term accumulation is drained every eight K tiles, with a separate residual accumulator and a final split-K reduction.

`_pick_config` shares dispatch decisions with warmup. Ordered tables tune MiniMax-M3/M2 and Hunyuan-V3/V4 shapes; other shapes use a default table. Large-M execution requires `K % 64 == 0` and `N % 8 == 0`, with the small-M kernel handling other shapes. The large-M path requires contiguous weights. The custom-op interface and FP32 output shape remain unchanged. Weight decomposition runs on every call, avoiding persistent derived-weight state across reloads.

**Why this is not duplicate work:** this extends the existing BF16x3 kernels from [#47973](https://github.com/vllm-project/vllm/pull/47973) / [#55899](https://github.com/vllm-project/vllm/pull/55899). Open-PR searches for BF16x3, router GEMM, and references to #60376 found no competing large-M SM100 implementation. [#50177](https://github.com/vllm-project/vllm/pull/50177) migrates router warmup and overlaps these files; it does not implement this optimization. [#49312](https://github.com/vllm-project/vllm/pull/49312) adds an opt-in external HPC backend on SM90 with cached weight decomposition. This PR improves the existing SM100 CuTeDSL path without that dependency. The open ROCm BF16x3 work targets a different backend.
