# [Perf] Faster BF16x3 router GEMM at large batch sizes on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/60376) · state: open · merged: False

## Original PR description

## Overview

Adds a large-batch path to the SM100 BF16x3 router GEMM (`torch.ops.vllm.bf16x3_router_gemm`, used by `GateLinear` for FP32 router weights) and retunes the dispatch between it and the existing kernel (#47973 / #55899). The new path splits the FP32 router weights into three BF16 planes once per call and runs a direct-orientation CuTeDSL tcgen05 GEMM over them.

## Claims

- **1.27-1.48x faster at 320-2048 tokens, ~2x at 8K+ tokens, up to 1.30x at 33-256 tokens** on MiniMax-M3, MiniMax-M2, Hunyuan-V3 and Hunyuan-V4 router shapes (GB300). Never slower outside noise.
- Untuned shapes get a new default table: 1.01-1.52x up to 256 tokens and 1.23-2.05x above (K=7168 / 256 experts, K=2048 / 128 experts, K=5120 / 160 experts).
- At 32K tokens the new path sustains 1232-1599 TFLOPS on the four tuned shapes (counting the three BF16 MMAs), against 1924 TFLOPS for cuBLAS BF16 on 8192^3.
- Same accuracy contract as the existing kernel: bitwise identical when both pick the same split-K, otherwise a few FP32 ulp apart.

<summary>Microbenchmark reproduction</summary>

Run in a vLLM CUDA development venv with FlashInfer and `cupti-python` installed (without `cupti-python`, FlashInfer silently falls back to CUDA-event timing). Run it on `main` and on this branch, 5 fresh processes each with seeds 1-5, and compare per-case medians.

```python
"""BF16x3 router GEMM: time the dispatched op of the checkout vLLM imports.

CUPTI kernel time (first kernel start to last kernel end per call, so the
large-M path includes decomp + GEMM + split-K reduce), cold L2, CUDA graphs.
TFLOPS counts the three BF16 MMAs: 3 * 2 * tokens * experts * K.
Run once per checkout (main, this PR) in fresh processes; prints JSON
{"name/tokens": us}.
"""

import json
import random
import statistics
import sys

import importlib.util

import torch
from flashinfer.testing import bench_gpu_time_with_cupti

MOD = "vllm.model_executor.layers.fused_moe.router.bf16x3_router_gemm_cutedsl"
if len(sys.argv) > 2:  # local A/B only: load another copy of the router file
    spec = importlib.util.spec_from_file_location(MOD, sys.argv[2])
    sys.modules[MOD] = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(sys.modules[MOD])
_bf16x3_router_gemm = importlib.import_module(MOD)._bf16x3_router_gemm

SHAPES = {
    "MiniMax-M3": (6144, 128),
    "MiniMax-M2": (3072, 256),
    "Hunyuan-V3": (4096, 192),
    "Hunyuan-V4": (2816, 256),
    "K7168-E256": (7168, 256),
    "K2048-E128": (2048, 128),
    "K5120-E160": (5120, 160),
}
TOKENS = [33, 64, 96, 128, 192, 256, 320, 512, 1024, 2048, 8192, 32768]

seed = int(sys.argv[1]) if len(sys.argv) > 1 else 0
cases = [(s, t) for s in SHAPES for t in TOKENS]
random.Random(seed).shuffle(cases)
g = torch.Generator(device="cuda").manual_seed(seed)
weights = {
    s: torch.randn(E, K, device="cuda", generator=g) * 0.053
    for s, (K, E) in SHAPES.items()
}
out = {}
for s, T in cases:
    K, _ = SHAPES[s]
    x = torch.randn(T, K, dtype=torch.bfloat16, device="cuda", generator=g)
    fn = lambda: _bf16x3_router_gemm(x, weights[s])  # noqa: E731
    fn()
    torch.cuda.synchronize()
    out[f"{s}/{T}"] = statistics.median(
        bench_gpu_time_with_cupti(fn, use_cuda_graph=True)
    ) * 1e3
print(json.dumps(out))
```

## Details

**Why.** The existing kernel (swap-AB, weights decomposed into TMEM per tile) suits small token counts, but at prefill sizes tokens sit on the MMA N side, forcing a scalar epilogue, and every K-tile pays the decomposition. The new path decomposes once per call and keeps tokens on the MMA M side.

**Design.**

- **Weight split** (`_bf16x3_decomp_kernel`, Triton): FP32 `W [experts, K]` -> `[3, experts, K]` BF16, bit-exact with the torch FP32 -> BF16 chain, at the memcpy floor. It indexes `W` flat, so the new path raises on a non-contiguous `W`.
- **GEMM** (`Sm100BF16x3RouterGemmLargeM`, CuTeDSL tcgen05): one (token tile, expert tile, K-slice) work item per CTA or CTA pair; `cta_group=1` (m128n128) or `cta_group=2` (m256n128 per pair). Split-K partials go through the existing Triton reduce.

**Dispatch.** `_pick_config` serves the op and warmup. Configs are `SmallMConfig(BM, split_k)` (existing kernel) and `LargeMConfig(cta_group, split_k)` (new path), with `split_k=None` filling one wave of SMs. Tuned shapes have ordered `(max tokens, config)` tables from a joint GB300 cold-L2 sweep of both kernels; untuned shapes use a 4-entry default table. Fixed split-K entries stay within one wave on B200's 148 SMs. The new path needs `K % 64 == 0` and `experts % 8 == 0`.

**Naming.** `M` = tokens, `N` = experts throughout; the existing kernel is renamed `Sm100BF16x3RouterGemmSmallM`.

**Related.** #50177 (router GEMM warmup migration) touches the same file; whichever lands second needs a rebase. No other open PR adds a large-batch path or retunes this dispatch.
