# Fix shutdown order: drain engines before stopping API servers with --api-server-count > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/61598) · state: open · merged: False

## Original PR description

## Background

With `--api-server-count > 1`, `--shutdown-timeout` had no effect on in-flight requests. All requests failed immediately with `EngineDeadError` because API servers were shut down before the engines.

## Root cause

In `run_multi_api_server`, the shutdown order was wrong:

```python
api_server_manager.shutdown(timeout=timeout)          # 1. SIGTERM the API servers
local_engine_manager.shutdown(timeout=to_timeout(shutdown_by))   # 2. SIGTERM the engines
```

Each API server worker handles SIGTERM by calling `engine_client.shutdown(timeout=N)`. In multi-server mode the worker has no `engine_manager` (engines are owned by the launcher), so `MPClient.shutdown` immediately marks the engine dead, closes ZMQ sockets and cancels the output queue task. That enqueues `EngineDeadError`, which propagates to every waiting `generate()` call, and all in-flight requests return 500. Only then does the launcher send SIGTERM to the engines — which log draining and keep computing outputs on PUSH sockets with no peer.

Single-server shutdown works correctly by construction: `MPClient.shutdown` first waits for `engine_manager.shutdown(timeout=N)`, then closes its sockets.

## Solution

Reorder shutdown to mirror the single-server semantics: engines drain first (while API servers still relay outputs and engines reject new requests via `_reject_add_in_shutdown`), then API servers exit cleanly with the remaining timeout budget.

```python
# BEFORE (broken):
api_server_manager.shutdown(timeout=timeout)
local_engine_manager.shutdown(timeout=to_timeout(shutdown_by))

# AFTER (fixed):
local_engine_manager.shutdown(timeout=timeout)        # engines drain in-flight requests
api_server_manager.shutdown(timeout=to_timeout(shutdown_by))  # API servers exit
coordinator.shutdown(timeout=to_timeout(shutdown_by))
```

## Testing

- Added regression assertions in `test_multi_api_server_shutdown` that in-flight requests should NOT all fail with 500 errors after SIGTERM
- The test now waits for the engine to admit a running request (via the Prometheus gauge) before sending SIGTERM, using the same pattern as `test_wait_timeout_completes_requests`

Fixes #61561.
