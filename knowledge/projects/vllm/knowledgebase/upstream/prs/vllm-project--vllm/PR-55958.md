# [Bugfix][Determinism] Refuse batch-invariant mode on unsupported platforms

[Upstream PR](https://github.com/vllm-project/vllm/pull/55958) · state: open · merged: False

## Original PR description

## Purpose

`enable_batch_invariant_mode()` branches on `current_platform.is_cuda()`, which matches `PlatformEnum.CUDA` only. ROCm is a separate enum member, so on ROCm the function takes neither the CUDA branch nor the XPU branch:

- the matmul overrides are never installed (`aten::mm`, `aten::addmm`, `aten::matmul`, `aten::linear`)
- the cuBLAS workspace config that disables split-k is never pinned
- `_fp16_block_size_n`, `_fp32_block_size_n` and `_fp32_num_stages` are never derived from the device's shared memory size, so they keep their module defaults (256/128/3)
- `resolve_tuned_matmul_configs()` gates on `is_cuda()` as well (`batch_invariant_configs.py:286`), so `capability` is `None` and no tuned configs are selected

The softmax, log_softmax, mean and bmm overrides are still registered, because that block is gated on `if not current_platform.is_xpu()`, which is true on ROCm. The function then returns normally and sets `_batch_invariant_MODE = True`.

The result is a mode that reports success while matmul, the dominant source of batch variance, stays batch-variant. Nothing else compensates: `VLLM_BATCH_INVARIANT` is not platform-gated anywhere (it is honored in `config/vllm.py`, `config/parallel.py`, `all_reduce_utils.py` and `cuda_communicator.py`), and `vllm/platforms/rocm.py` contains no determinism handling. ROCm reaches this code through the same worker path as CUDA (`init_batch_invariance()` at `gpu_worker.py:1486`).

This PR refuses unsupported platforms instead of half-enabling them. A caller that asked for bitwise-reproducible outputs is better served by a clear error than by a silent downgrade. The check runs before any global state is touched, so a caller that handles the error is not left with a partially installed mode.

## Behavior change

A ROCm deployment currently running with `VLLM_BATCH_INVARIANT=1` will now fail at startup with an actionable message instead of starting with partial invariance. That is the intent, but it is a breaking change for anyone relying on the current silent behavior. If you would rather log a warning and continue, swapping the raise for `logger.warning_once` is a one-line change and I am happy to do that.

I deliberately did not touch the `is_cuda()` gate in `resolve_tuned_matmul_configs()`. With this guard in place it is unreachable for unsupported platforms, and changing it only matters if ROCm support is actually implemented.

## Test Plan

New tests in `tests/v1/determinism/test_unsupported_platform.py`. They use a stub platform, so they need no GPU and run in the CPU test selection:

```bash
pytest -v tests/v1/determinism/test_unsupported_platform.py
```

Regression check, running the same tests against the unfixed module:

```bash
git stash push vllm/model_executor/determinism/batch_invariant.py
pytest -q tests/v1/determinism/test_unsupported_platform.py
git stash pop
```

Existing suite, for regressions:

```bash
pytest -q tests/v1/determinism
```

The CUDA-gated coverage that exercises the supported path is `tests/v1/determinism/test_batch_invariance.py` and `tests/v1/determinism/test_matmul_batch_invariant.py`. I have no GPU available, so I am relying on CI for those two.


Without the fix, the two behavioral tests fail:

```text

2 failed, 1 passed
```

`test_already_enabled_returns_before_the_platform_check` passes either way, which confirms the existing idempotence guard still short-circuits ahead of the new check.

Existing determinism suite, identical before and after the change on this machine:

```text
3 passed, 576 skipped
```

The 576 skips are the CUDA-gated tests, since this run had no GPU.

Behavior before the fix, on a platform that takes the same branch ROCm takes:

```text
platform: CpuPlatform | is_cuda: False | is_xpu: False | dispatch_key: CPU
enable_batch_invariant_mode() returned WITHOUT error
mode flag        : True
torch.bmm patched: True
block sizes      : fp16_n=256 fp32_n=128 stages=3 (module defaults, never tuned)
```

PyTorch also warns that the Triton `_log_softmax` override replaced the registered CPU kernel, which shows the overrides land on whatever dispatch key the platform reports.

Linting: `ruff check` and `ruff format` pass on both changed files.

## Verification scope

I have no ROCm or NVIDIA device. The ROCm control flow is established from the platform predicates (`is_cuda()` matches `PlatformEnum.CUDA` only, while `is_cuda_alike()` covers CUDA and ROCm) and reproduced on another platform that takes the same branch, as shown above. I did not measure batch invariance on ROCm hardware. Confirmation from someone with a ROCm device would be welcome, and I am relying on CI for the CUDA-gated tests.
