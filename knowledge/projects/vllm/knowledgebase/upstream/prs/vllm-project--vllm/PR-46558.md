# [Bugfix][Attention] Enable FlashInfer mm-prefix attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/46558) · state: open · merged: False

## Original PR description

## Purpose

This keeps multimodal PrefixLM batches on the native FlashInfer backend. It is the vLLM adapter for FlashInfer's mm-prefix batch-prefill wrapper: it builds per-query `[start, end]` rows from request metadata, decides when the path is eligible, and calls the wrapper, whose attention variant evaluates `(causal AND sliding_window) OR mm_prefix` on every KV tile. No `O(qo_len * kv_len)` mask is materialized; the ranges are one `int32 (N, 2)` buffer sized by scheduled tokens, 128 KiB at 16384 tokens. The prefill still traverses the full rectangle, so the gain is memory, not FLOPs.

The wrapper comes from FlashInfer PR 5189 and first ships in 0.7.1 (0.7.1rc1 is tagged). Main pins 0.7.0.post1, which does not have it, so until the 0.7.1 pin bump `supports_mm_prefix()` returns `False` and this backend is demoted before selection. FlashInfer builds the variant's JIT module when the wrapper is constructed.

The mm-prefix wrapper is planned beside the regular prefill path rather than replacing it, so text-only batches, decodes and layers whose ranges are cleared at forward time (Gemma 4 full-attention groups) keep trtllm-gen or FA3 with main's query dtype and scales. On the SM100 family `TRITON_FLASHINFER` stays the automatic choice; an explicitly selected `FLASHINFER` serves the ranges natively and does not advertise large pages. An SM100 NVFP4 cache keeps its V scale factors in the trtllm-gen swizzle, so native mm-prefix accepts it only when FlashInfer's wrapper takes `v_sf_swizzled`, which no FlashInfer release has yet, and rejects it otherwise. One predicate, `_native_mm_prefix`, decides eligibility for selection and the builder's range state, so the composite's FlashInfer child keeps main's routing and allocates no range buffers. On SM90 the automatic priority still prefers the `TRITON_FLASH_ATTN` composite; this PR leaves that priority unchanged, while native FlashInfer can be selected explicitly. For native mm-prefix, FlashInfer rejects `fp8_e5m2`, `nvfp4_4over6`, sinks and DCP at selection, and `logits_soft_cap` at engine start. The ubatch split now carries `mm_req_doc_ranges`, re-keyed to local request indices, and `is_prefilling`, so a short chunked-prefill tail inside a range stays a prefill.

An `fp8` or `fp8_e4m3` cache takes the native path too. fa2 has no FP8 query or output, so only the mm-prefix call adapts: a query the layer already quantized to FP8 goes back to the model dtype losslessly with its q_scale, and a fused FP8 output is quantized after the call. Native mm-prefix models are offered FP8 output fusion only, as the composite is.

#47118 also enables FlashInfer for Gemma 4 multimodal models, but only for text-only requests; this PR serves the mm-prefix batches.

## Test Result

With FlashInfer 0.7.1rc5 on sm_80 this revision gives 106 passed and 22 skipped; the skips are the FA4 mask_mod tests and the Hopper and Blackwell composite tests. On sm_103, with FlashInfer 0.7.1 plus the `v_sf_swizzled` option, code equivalent to `37c1fa3980` (before the cleanup) gave 122 passed and 7 skipped: FA4 at head size 512 and the Hopper composite. The CPU tests cover the KV dtype, sink and wrapper-availability rejections, DCP, the FP8 query dtype and q_scale with SM100 left on its FP8 query and q_scale, the SM100 and SM90 automatic priorities with and without the wrapper, and ubatch re-keying and slicing. The GPU tests compare builder, impl and wrapper against a dense float32 reference on paged KV, with a sliding window narrower than the widest range so both window formulas are checked, and they cover the causal fallback, text-only and decode-only gating, short-extend reclassification and fail-fast on soft-cap. The FP8 case writes the cache with distinct non-unit K/V scales, rebuilds the reference from what was stored, and sets a non-unit q_scale on the model-dtype query. The GPU tests select `FLASHINFER` explicitly and use FlashInfer's KV layout for the platform, so on SM100 they run the native path next to trtllm-gen. SM90 is checked with mocked capabilities only. pre-commit passes.

On sm_103 with `RedHatAI/gemma-4-12B-it-NVFP4` and an FP8 KV cache, explicit `FLASHINFER` was measured against `TRITON_FLASHINFER` with one run per configuration, with code equivalent to `37c1fa3980`, before the cleanup. Text throughput was 0.2% lower at concurrency 32; image throughput was 0.8% lower at concurrency 1 and 0.5% and 1.6% higher at 32 and 128; ChartQA (500 examples, relaxed accuracy) was 68.2 against 66.8. These numbers describe this run only. The compiler-fused FP8 output path has not been verified on a full model. Gemma 3 4B with an NVFP4 KV cache, which `TRITON_FLASHINFER` rejects on SM100, scored 43.8 on the same ChartQA set against 43.6 with FP8 KV.

**Real-world impact report + offer to test on SM120 (production Gemma-4 multimodal)**

We run vLLM in production serving `gemma-4-26B-A4B-it-FP8` (multimodal, `is_mm_prefix_lm=True`) on 2× RTX 5090 (SM120), TP=2, fp8 KV cache, `ngram_gpu` speculative decoding (k=8), mostly long-context RAG traffic.

Because the FlashInfer backend does not declare `supports_mm_prefix`, backend selection disqualifies it for this model and falls back to `TRITON_ATTN` — for every request, including the 100%-text traffic that dominates our workload. Verified on v0.25.1 and again on v0.28.0 (boot log: `Using AttentionBackendEnum.TRITON_ATTN backend.`). `--limit-mm-per-prompt '{"image": 0, "video": 0}'` does not lift the gate, since `is_mm_prefix_lm` is a model-architecture property rather than an input question (and attempting that flag with a warm compile cache also runs into the cache-key collision from #50891). So there is currently no configuration that lets an mm-prefix model reach the SM12x XQA decode path added in #49718.

The cost on consumer Blackwell is large: flashinfer-ai/flashinfer#4137 measured XQA against vLLM's Triton unified-attention kernel on RTX PRO 6000 (SM120) at 2.4–3.6× for m=1 decode, and up to 14–18× for spec-decode verification (m=4/8) on full-attention layers at 32k context — exactly our decode profile. Today, mm-prefix models are excluded from all of it.

This PR would unblock a real production speedup for Gemma-4-class multimodal models. If it helps, we are happy to run correctness and throughput A/B on our 2× RTX 5090 setup once the PR is in a reviewable state — we have 0.25.1 baselines and a test harness ready.

*Disclosure: drafted with AI assistance; the deployment details and observations above are from our own production system.*
