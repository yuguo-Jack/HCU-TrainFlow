# [ROCm][Perf][Attention] AITER gluon attention backend for Qwen3.8-27B

[Upstream PR](https://github.com/vllm-project/vllm/pull/65248) · state: open · merged: False

## Original PR description

## Overview

Add `ROCM_AITER_FA_GLUON`, a subclass of `ROCM_AITER_FA` that runs single-token decodes on AITER's gluon paged attention (`pa_decode_gluon`) under the shuffle KV-cache layout, for head-size-256 attention with GQA group 6 (the full-attention layers of Qwen3.5 / 3.6 / 3.8-27B). Everything else (prefill, multi-token decodes, other head configs) runs the parent backend unchanged.

#54805 reverted the earlier in-place gluon decode in `ROCM_AITER_FA` (#52849) because ragged speculative-decode batches broke it. This PR keeps `ROCM_AITER_FA` as it is and takes the gluon path only when every decode in the batch is one token. Needs no AITER change.

## Claims

- Decode attention per call, Qwen3.8-27B TP1, against main's default backend (`ROCM_ATTN`, plain KV layout): **123.0 → 17.1 µs at c4, 153.8 → 61.8 µs at c64** (`kernel_paged_attention_2d` → gluon `paged_attention_decode_sliding_window` + its split reduce).
- Serving, against main's default: **+8.9 to +21.5% total tok/s and −9.2 to −17.9% mean TPOT at c4–c64**; GSM8K unchanged. This is what a user gets by turning on `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1`. Main has no shuffle-layout baseline for this model (`ROCM_AITER_FA` refuses the hybrid page layout).
- No change for other models, platforms, KV-cache dtypes or layouts, or for runs on more than one GPU (TP, PP, PCP) or with expert parallelism. A user-selected `--attention-backend` always wins over the config hook.

### Tests

- `tests/kernels/attention/test_rocm_aiter_fa_gluon.py` (ROCm only): 14 cases; 10/10 passed on 8b4526704f, the 4 newer cases TBD.
  - `test_pa_gluon_supports`: which head configs and KV caches take the gluon decode. Pure Python, no AITER needed.
  - `test_qwen3_5_config_selects_gluon_backend` (gfx950): the hook selects the backend only for the supported shape with the shuffle layout on a single GPU without expert parallelism, and never overrides a user-selected backend.
  - `test_gluon_decode_matches_reference` (gfx950, skipped without AITER's gluon module): a 24 q / 4 kv head, head-256 layer on the shuffle cache with 16-token blocks, ragged decode lengths (17, 100, 333, 1,100 and 1, 2,048 tokens), block-table padding pointing at block 0, and block 0 filled with NaN. It checks that `build()` zeroes block 0, that the gluon kernel runs, and that the output matches a float32 torch reference (atol/rtol 2e-2). Removing the zeroing or transposing the 5-D K/V views fails it.

## Details

- `rocm_aiter_fa.py`: the shuffle-layout decode branch moves unchanged into `AiterFlashAttentionImpl._decode_shuffle_layout`, the one step the subclass overrides.
- `rocm_aiter_fa_gluon.py` (new): `_decode_shuffle_layout` calls `pa_decode_gluon` (`ps=True`, `get_recommended_splits`, 128-token context partitions), imported inside the method like the parent backend's AITER imports, so the module and `pa_gluon_supports` import without AITER. It falls back to the parent decode for multi-token decodes, other block sizes and layers that `pa_gluon_supports` rejects.
- The backend pins kernel blocks to 16 tokens, which the hybrid KV manager's pages split into. 128-token partitions give the kernel occupancy 2 (256 gives occupancy 1).
- The gluon kernel reads V rows of the null block (block 0) for masked positions, so the metadata builder zeroes block 0 of the gluon layers on every step with decodes (one `torch._foreach_zero_`).
- `Qwen3_5ForConditionalGenerationConfig.verify_and_update_config` selects the backend when no backend was chosen, the run uses one GPU (`world_size == 1`, so TP 1 and therefore DCP 1) without expert parallelism, AITER MHA and the shuffle layout are enabled, the GPU is gfx950, and `pa_gluon_supports` holds for the head counts. It logs the choice once and names the opt-out (`--attention-backend ROCM_AITER_FA`); without that line, the backend-selection log reports it as "selected via --attention-backend".
