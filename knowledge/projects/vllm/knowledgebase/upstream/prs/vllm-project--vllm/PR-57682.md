# [Kernel][torch.compile] CUDA fused QK-norm + RoPE + KV-cache write (fuse_qk_norm_rope_kvcache on FlashAttention)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57682) · state: open · merged: False

## Original PR description

## Purpose

Depends on #57681 (stacked; its commit is included here until it lands).

CUDA counterpart of the ROCm `fuse_qk_norm_rope_kvcache` pass (#42749 / #42755): fuse Q/K RMSNorm + RoPE + the paged KV-cache write into one launch on the FlashAttention backend. Today the CUDA path runs `fused_qk_norm_rope` (which writes the rotated Q/K back into `qkv`) and then `reshape_and_cache_flash`, which reads K and V back out of `qkv` only to scatter them into the cache. The new kernel keeps K/V in registers and stores them to `q_out`/`k_out` and to the cache directly, so K/V are never re-read. This fills the "QK Norm + RoPE + Cache" CUDA gap in #36066.

## Changes

- `csrc/fused_qknorm_rope_kernel.cu`: `WRITE_CACHE` template variant of both kernels (1-head and N-token-heads). In that mode `qkv` is read-only, Q/K land in contiguous `q_out`/`k_out`, K/V are scattered into the (possibly strided) flash-layout cache via `slot_mapping`; V heads get their own warps. Tokens beyond `slot_mapping.size(0)` or with slot `-1` are normalised/rotated but not cached, matching `reshape_and_cache_flash`. All stores happen before the PDL trigger. The existing `fused_qk_norm_rope` entry is unchanged in behaviour (same kernel, `WRITE_CACHE=false`).
- New op `_C.fused_qk_norm_rope_kvcache` (+ `vllm._custom_ops` wrapper).
- `FlashAttentionImpl.fused_qk_norm_rope_kvcache_supported()` / `do_qk_norm_rope_kvcache_update()`: enabled for `kv_cache_dtype="auto"`, decoder layers, `head_size ∈ {64,128,256}`, no KV sharing, no DCP.
- `QkNormRopeKvCacheFusionPass`: works with opaque `LayerName` graph inputs (`VLLM_USE_LAYERNAME`, torch ≥ 2.11), registers the fp8-query variants only on ROCm (they trace `rocm_aiter_per_tensor_quant`). No change to the ROCm behaviour otherwise.
- `PassConfig.fuse_qk_norm_rope_kvcache`: allowed on CUDA (opt-in, still auto-enabled only on ROCm at O1+).
- Tests: `tests/kernels/core/test_fused_qk_norm_rope_kvcache.py` (bitwise vs `fused_qk_norm_rope` + `reshape_and_cache_flash`, all `token_heads_per_warp`, padded/short slot mappings) and `tests/compile/passes/test_qk_norm_rope_kvcache_fusion.py` (pattern matches and results agree on FlashAttention, both cache layouts).

## Test plan / results (H200, Qwen3-8B, bf16, dummy weights)

**Kernel** (standalone build of this file, bitwise vs the shipped `fused_qk_norm_rope` + `reshape_and_cache_flash` pair, 74 cases: bf16/fp16, neox/gptj, head_dim 64/128/256, partial rotary, `token_heads_per_warp` 1/2/4/8, padded and short slot mappings): q_out/k_out/key_cache/value_cache identical in every case, qkv untouched. GPU time of the fused launch vs the two kernels (hq32/hkv8/d128, neox): 64 tokens −31%, 256 −20%, 2048 −6%, 8192 −16%.

**End to end** (`fuse_qk_norm_rope_kvcache=True` on top of `enable_qk_norm_rope_fusion=True` + `use_inductor_graph_partition=True`, in both arms; ABBA, two runs per arm):

| workload | base | fused | Δ |
|---|---|---|---|
| `bench latency` bs=1, 128 in / 128 out | 0.6725 / 0.6731 s | 0.6711 / 0.6687 s | −0.6% |
| `bench latency` bs=8 | 0.7242 / 0.7244 s | 0.7198 / 0.7198 s | −0.6% |
| `bench latency` bs=32 | 0.8251 / 0.8261 s | 0.8171 / 0.8181 s | −1.0% |
| `bench throughput` prefill 2048 in / 1 out | 29448 / 29483 tok/s | 29390 / 29546 tok/s | ±0 |
| `bench throughput` decode 128 in / 256 out | 30028 / 30083 tok/s | 30097 / 30086 tok/s | +0.1% |

Greedy outputs (12 sequences, 32–64 new tokens) are token-for-token identical between the two arms. Profiling a decode step at bs=8 shows the saving is exactly the kernel pair (per 64 steps × 36 layers: 5.27 ms + 5.05 ms → 7.29 ms), with no extra copies.

Raising `rope_kvcache_fusion_max_token_num` so the pass also covers the prefill ranges did not move the needle (same latency sweep: −0.9% / −0.4% / −0.9%), so the default gate is left unchanged.

Stacked on #57681 (the first commit here): the new compile test covers partial rotary at 2048 tokens, which hits the warp-shuffle UB that PR fixes.

Note on validation: the kernel was compiled standalone with nvcc against the torch of a vLLM 0.28.0 environment and checked bitwise against that build's shipped `fused_qk_norm_rope` + `reshape_and_cache_flash`; the end-to-end numbers were taken with this branch's pass and FlashAttention hooks overlaid onto vLLM 0.28.0 (same integration path). I could not build main from source in that environment, so the new unit/compile tests have not been run locally and rely on CI.

## Relation to the Step-5 fused kernel (#62132)

#62132 (merged 2026-10-17) added `fused_qknorm_rope_cache` (`csrc/fused_qknorm_rope_cache_kernel.cu`): a QK-norm + partial-NeoX-RoPE + KV-cache-insert op written for Step-5 Preview / Muse Spark Open, which their model code calls explicitly (#61727, #61879). It is a standalone `_custom_ops` entry, not wired into `QkNormRopeKvCacheFusionPass` or any attention backend, and it follows that model's eager numerics (norm output rounded to the activation dtype before RoPE, sub-warp XOR reduction), with FP32 norm weights, `norm_weight_bias`, head_dim 192 and FP8 caches.

This PR serves a different contract: the compile-time pass on the FlashAttention backend, for any model whose graph contains the `qk_norm -> rope -> reshape_and_cache_flash` chain. Its `WRITE_CACHE` variant extends the existing `fused_qk_norm_rope` kernel so the fused result stays bitwise identical to the `enable_qk_norm_rope_fusion` + `reshape_and_cache_flash` path it replaces. Pointing the pass at `fused_qknorm_rope_cache` instead would change the numerics of every fused layer and require the pass to allocate separate q/k/v outputs, so the two kernels are kept separate here; sharing an epilogue between them is possible as a follow-up and is orthogonal to enabling the pass on CUDA.
