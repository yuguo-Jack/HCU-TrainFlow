# [Refactor][MoE] Migrate Quark static INT8 to the MoE oracle

[Upstream PR](https://github.com/vllm-project/vllm/pull/58672) · state: open · merged: False

## Original PR description

## Summary

Migrate the static-activation INT8 path in `QuarkW8A8Int8MoEMethod` to the MoE oracle and modular kernel for single-rank and naive AllGather/ReduceScatter execution.

This addresses the Quark static INT8 portion of #54959. Other all-to-all configurations retain the legacy path.

## Dependency and review scope

This PR depends on the independent activation/weight scale-indexing fix tracked in #58532. Related prerequisite PR: #58570.

The branch includes my prerequisite implementation at `eef597461aa5496a10165baa7280f9fad619a7e5`, with the migration changes in a separate commit. The diff against upstream main therefore includes both the prerequisite and the migration.

The migration can be reviewed independently of the prerequisite implementation. Once the prerequisite lands, I will rebase onto the accepted implementation and remove the prerequisite commit from this PR.

## Changes

- Route supported static INT8 configurations through oracle selection, weight conversion, quant-config construction, and modular kernel execution.
- Preserve loaded A1/A2 scales, FP16/BF16 compute dtype, bias handling, and the legacy input-side router-weight order.
- For naive AllGather/ReduceScatter, dispatch floating-point activations and quantize on the destination rank using its local static scale.
- Handle empty static INT8 inputs in the local quantization helper so empty ranks still participate in communication.
- Explicitly reject static INT8 with LoRA until router weighting is supported consistently across the base and adapter branches.
- Preserve independent weight-scale indexing in the remaining legacy fallback.

<details>
<summary>Model-level migration comparison</summary>

Used real Quark INT8 weights from
[`amd/Qwen1.5-MoE-A2.7B-Chat-w-int8-a-int8-sym`](https://huggingface.co/amd/Qwen1.5-MoE-A2.7B-Chat-w-int8-a-int8-sym).

The source checkpoint uses dynamic per-token activations. A local static per-tensor variant was derived by collecting actual activation scales through the normal `vllm.LLM` eager entry point on 40 calibration prompts. Initialization/profile samples were excluded. Per-layer maxima with a 1.05 margin were written as static input scales; the original quantized weights were unchanged.

Compared the prerequisite commit `eef5974` running the legacy static path against the tested migration commit running the modular static path:

| Metric | PR A + legacy eager | Modular eager |
| --- | ---: | ---: |
| Deterministic generation prompts | 4 | 4 |
| WikiText-2 segments | 32 | 32 |
| Evaluated tokens | 3,080 | 3,080 |
| NLL | 9,726.221237358173 | 9,726.221237358173 |
| Perplexity | 23.520303764476 | 23.520303764476 |

Token IDs, generated text, and cumulative logprobs were identical across both paths for all four generation prompts.

A tiny random-weight Qwen3-MoE static fixture also produced identical tokens, text, and cumulative logprobs for all four prompts.

The legacy baseline required a validation-only runner compatibility shim: treat `experts_cls=None` as non-monolithic so execution reaches the legacy `apply()` path. The shim was applied in the baseline overlay, not committed to either worktree or included in this PR.

The static checkpoint was locally calibrated from real Quark INT8 weights. This evaluation checks migration parity on the tested inputs, rather than establishing the checkpoint's overall model quality.

The derived static checkpoint's eager PPL is 4.989% higher than the source dynamic checkpoint's. This is a separate checkpoint/quantization comparison; the legacy and modular paths produce identical eager metrics on the same derived static checkpoint.
