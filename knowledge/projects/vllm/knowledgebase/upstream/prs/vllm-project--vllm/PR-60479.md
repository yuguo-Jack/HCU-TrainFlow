# [Bugfix] Keep GPTQ linear layers batch invariant

[Upstream PR](https://github.com/vllm-project/vllm/pull/60479) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `VLLM_BATCH_INVARIANT=1`, `AutoGPTQLinearMethod` still runs the Marlin GEMM. Marlin picks its tiling and K-split from the number of tokens, so the reduction order changes with the batch size and the logprobs depend on the batch.

This PR makes the GPTQ path use `matmul_batch_invariant` directly: in batch-invariant mode it skips the Marlin kernel selection and repacking, keeps the checkpoint layout in memory, and unpacks the weight in `apply()`.

(The matching AWQ change was part of this PR until 2026-10-19 and was dropped: on current `main` the AWQ fallback is already batch invariant through #52231, which overrides `aten::mm.out`/`aten::addmm.out`; #60013, which this PR deferred to, was closed for the same reason.)

## Claims

- On `main`, `tests/v1/determinism/test_batch_invariance.py` fails for `Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4` (14 of 22 ids). With this PR all 22 ids pass.
- Accuracy is unchanged: `lm_eval` gsm8k on the batch-invariant path matches the Marlin path within noise, and the top-1 tokens of the two GPTQ paths agree on a fixed prompt set.
- Without `VLLM_BATCH_INVARIANT` nothing changes: the same Marlin kernel is selected.
- Throughput in batch-invariant mode is lower than on `main` (numbers below): the GPTQ weight is dequantized on every forward and the model uses the batch-invariant Triton matmul instead of Marlin.
- New unit test checks the GPTQ unpack against vLLM's reference packer bit for bit.

## Details

**Root cause.** `vllm/model_executor/determinism/batch_invariant.py` overrides `aten::mm`/`aten::matmul` through `torch.library` and exposes `matmul_batch_invariant` for callers; linear methods that run their own kernels have to opt in. `AutoGPTQLinearMethod` never did: it always builds a Marlin `MPLinearKernel`. The same pattern is why `UnquantizedLinearMethod` calls `linear_batch_invariant` explicitly.

**Change.**
- `auto_gptq.py`: with `VLLM_BATCH_INVARIANT=1`, `AutoGPTQLinearMethod` skips `verify_marlin_supported` / `choose_mp_linear_kernel`, leaves `qweight`/`scales`/`qzeros` in the checkpoint layout, and `apply()` unpacks the weight (`(q - bias) * scale` in the scales dtype, the same arithmetic as the Marlin dequantization) and calls `matmul_batch_invariant`. Without the flag the code path is unchanged.
- `tests/kernels/quantization/test_gptq.py`: `_dequantize_gptq_weight` is compared bit for bit against `gptq_quantize_weights` + `gptq_pack` for 4/8 bit, group sizes -1/32/128, fp16/bf16.

**Trade-offs and limitations.**
- The GPTQ weight is unpacked on every forward in batch-invariant mode, and the model runs the batch-invariant Triton matmul instead of Marlin. On the A10 this costs throughput in batch-invariant mode (blocks in section 6): the decode-heavy benchmark takes about 2.5x longer than `main`'s non-invariant Marlin path, the prefill-heavy one about 1.4x. Keeping a dequantized copy would be faster but would need the memory of the unquantized model, which is usually why a GPTQ checkpoint is used. A fused batch-invariant W4A16 Triton kernel would remove the cost; I kept that out of this PR.
- Only symmetric GPTQ without act-order is covered, which is what `AutoGPTQLinearMethod` supports today (`desc_act=True` is rejected at config time).
- `AutoGPTQMoEMethod` (GPTQ MoE experts) still uses Marlin MoE and is not batch invariant; #46639 covers that kernel. (The compressed-tensors wNa16 dense scheme was fixed separately in #60524.) This PR covers the dense GPTQ path that was tested.
