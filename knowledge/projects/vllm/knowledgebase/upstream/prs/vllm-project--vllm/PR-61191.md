# [Bugfix][Mamba] Keep mamba_config backend unless --mamba-backend is set

[Upstream PR](https://github.com/vllm-project/vllm/pull/61191) · state: open · merged: False

## Original PR description



## Overview

Fixes #61188.

A Mamba backend passed through `mamba_config` (e.g. `LLM(..., mamba_config={"backend": "flashinfer"})`) was silently replaced with Triton, because `--mamba-backend` defaulted to `TRITON` and was always copied into `mamba_config.backend`. This PR defaults `--mamba-backend` to `None` and overrides `mamba_config.backend` only when the flag is set.

## Claims

- `mamba_config.backend` now reaches the engine unchanged when `--mamba-backend` is not set.
- `mamba_config={"backend": "flashinfer", "ssu_algorithm": "vertical"}` no longer fails with "Mamba SSU algorithm selection is only supported with the FlashInfer backend".
- `--mamba-backend` behaves as before: unset resolves to Triton, and an explicit value still wins over `mamba_config.backend`.

## Validation

End to end on the macOS CPU backend (Apple M3 Pro) with the native Mamba2 model from the test registry, `yujiepan/mamba2-codestral-v0.1-tiny-random` (`LLM(..., runner="generate")`, 8 greedy tokens):

| Configuration | `vllm_config.mamba_config.backend` on main | with this PR | Generation |
|---|---|---|---|
| no backend set | `TRITON` | `TRITON` | same output |
| `mamba_backend="triton"` | `TRITON` | `TRITON` | same output |
| `mamba_config={"backend": "cpu"}` | `TRITON` (runtime then logs "overriding Mamba SSU backend from 'triton' to 'cpu'") | `CPU` | same output |

Tests:

pytest tests/v1/attention/test_replayssm_metadata_builder.py   # 15 passed, 1 skipped

`test_mamba_config_backend_not_overridden_by_default` fails on main with the `ValueError` from the issue and passes with this change. `test_mamba_backend_cli` guards the CLI default and the explicit flag. The 14 `tests/test_config.py` failures are identical on main in this environment (gated Hugging Face models and CPU-platform defaults), so they are unrelated.

Not covered locally: the FlashInfer SSU kernel itself needs an NVIDIA GPU. The change only decides which backend value reaches `VllmConfig`, and the unit tests assert that value directly.

## Details

Root cause: `EngineArgs.mamba_backend` defaulted to `MambaBackendEnum.TRITON`, and the `--mamba-backend` CLI default comes from `MambaConfig.backend` (also `TRITON`). `create_engine_config` then assigned it to `mamba_config.backend` unconditionally. The other `mamba_config` overrides (`--mamba-ssu-algorithm`, `--enable-mamba-cache-stochastic-rounding`, `--mamba-cache-philox-rounds`) are only applied when set. The override was introduced with the FlashInfer backend in #36162.

Changes, all in `vllm/engine/arg_utils.py`:

- `EngineArgs.mamba_backend` defaults to `None`, and the `--mamba-backend` CLI default is set to `None`.
- `mamba_config.backend` is overridden only when `mamba_backend` is not `None`. String-to-enum conversion reuses `MambaConfig.validate_backend_before` instead of duplicating it.

Precedence: an explicit `--mamba-backend` still overrides `mamba_config.backend`, matching the other Mamba flags. The issue also suggested raising an error when both are set, as `attention_backend` does, but `MambaConfig.backend` defaults to `TRITON` rather than `None`, so an explicit `triton` cannot be told apart from the default. I kept the smaller change; happy to add a conflict error for non-default values if preferred.

Compatibility: `EngineArgs.mamba_backend` is now `None` by default instead of `TRITON`. No code in the repo reads it outside `create_engine_config`, and the resolved `VllmConfig.mamba_config.backend` default is still `TRITON`. `vllm serve --help` shows `None` as the `--mamba-backend` default.

Duplicate check: no open PR covers this (searched "61188", "mamba_backend default", "mamba_config backend"; #48980 only reads the backend).
