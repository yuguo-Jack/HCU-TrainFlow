# [Core] Let TP-replicated Mamba state share a sharded state KV cache group

[Upstream PR](https://github.com/vllm-project/vllm/pull/61048) · state: closed · merged: False

## Original PR description



## Overview

In the packed (block-outermost) hybrid KV layout, a TP-replicated Mamba state layer (Qwen4Exp's PLE short-conv state) always gets its own KV cache group. That group then takes whole pool blocks for a few hundred KB of real state: in align mode, 2 + `num_speculative_tokens` blocks per running request. This PR lets replicated and sharded Mamba state share a group when their page sizes match. It keeps the old grouping when the NIXL connector is configured, because NIXL expects the PLE state alone in its group.

**Draft:** the unit test passes locally (CPU). A GPU serving check is TODO, and I will add it before I mark the PR ready.

## Claims

- For Qwen3.8-Flash-Next at TP8 with MTP 3 in align mode: 6 KV cache groups and 21 state blocks per running request become 5 groups and 16 blocks. The pool block size does not change.
- **Expected gain (computed from the measured pool sizes, not yet measured in serving):**

| Running requests | Pool freed, block 800 (fp32 SSM) | Pool freed, block 480 (bf16 SSM) |
|---|---|---|
| 16 | 2.8 % | 1.7 % |
| 20 | 3.5 % | 2.1 % |
| 32 | 5.6 % | 3.4 % |

- No change for models without TP-replicated Mamba state, for non-packed layouts, or when the padded pages differ (the bucket stays split).

## Validation

- New `TestReplicatedStateSharesShardedStateGroup` in `tests/v1/core/test_contiguous_kv_packing.py`, with the real per-GPU byte sizes at TP8, for block 800 (fp32 SSM) and block 480 (bf16 SSM). It checks:
  - the groups and state blocks per request, before and after;
  - that the pool block is unchanged;
  - that every group fits in one block;
  - that with NIXL the PLE state stays alone.

  It fails without the change and passes with it.
- `tests/v1/core` (macOS, CPU): 943 pass. The same 58 failures and 4 errors occur on the base commit; they come from the environment (EC connector, model-registry inspection).
- `tests/v1/kv_connector/unit` (NIXL descriptor geometry, offloading, Mooncake store worker): 986 pass. 2 offloading tests try to download a gated HF repo; this is a network failure, unrelated to the change.
- `ruff check`, `ruff format --check`: clean.
- **TODO (GPU):** start-up log `kv cache group sizes` shows 5 entries instead of 6, and "GPU KV cache size" rises. Then a serving run with prefix hits and MTP, to check the align-mode copies and prefix caching on the merged group.

## Details

- **Root cause:** `MambaSpec.is_uniform_with_collection` requires equal `tp_replicated`. Every Mamba layer already gets the same padded page (`cache_config.mamba_page_size_padded`), so this flag is the only thing that splits the PLE state from the GDN state. Core scheduling never reads `tp_replicated`. The worker already handles mixed Mamba types inside one group, per layer (`v1/worker/mamba_utils.py`).
- **Guard:** the NIXL worker requires a PLE group with exactly one layer (`nixl/base_worker.py`). With a merged group, it would build wrong descriptors without an error. So the packed bucketing does not mix replicated and sharded state when `kv_transfer_config.has_connector("NixlConnector")`.
- **Not done:** moving the QSA raw-key ring (`CircularBufferSpec`, 1 block per request) out of the shared pool. That needs a per-request-slot buffer in the model runner.
- **Size:** core +32 / −3 (`kv_cache_interface.py`, `kv_cache_utils.py`); test +134.
- **Risks to check on GPU:**
  - prefix caching in align mode: PLE and GDN now share block ids;
  - MTP align copies: per layer, so the code paths exist;
  - Mooncake hetero-TP: it handles PLE per layer.
