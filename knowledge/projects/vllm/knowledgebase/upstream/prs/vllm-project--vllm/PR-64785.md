# [ROCm][KV Connector] Add MoRIIO transfer stats and Prometheus metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/64785) · state: open · merged: False

## Original PR description

## Overview

Adds KV connector stats and Prometheus metrics to the MoRIIO connector, which today reports none. Addresses gap 11 (observability) of the MoRIIO RAS RFC, [ROCm/mori#759](https://github.com/ROCm/mori/issues/759). The design follows the Mooncake connector's stats (`mooncake/stats.py`).

This is not a duplicate. The only earlier attempt, #43218 ("[ROCm] MoRI connector telemetry", by @simondanielsson), was closed by its author after it went stale and needed a rebase. This PR starts again from current `main` and addresses that PR's review comments: a missing-key `KeyError`, the notify port in logs, and thread safety. No other open PR adds MoRIIO stats.

## Claims

- MoRIIO now reports stats in the periodic `KV Transfer metrics` log line and exports six Prometheus series, each with the standard `model_name` and `engine` labels:
  - `vllm:moriio_xfer_time_seconds`, `vllm:moriio_bytes_transferred`, `vllm:moriio_num_descriptors` (histograms, one sample per request transfer);
  - `vllm:moriio_num_failed_transfers`, `vllm:moriio_num_failed_notifications`, `vllm:moriio_num_kv_expired_reqs` (counters).
- Successful transfers are recorded where the data moves: on D in READ mode, and on P in WRITE mode.
- Each failure path is counted once, at the place that detects it:
  - **Failed transfer:** on D, a READ that fails or hits `recv_abort_timeout`, and any WRITE failure P reports to D. On P, a WRITE task that raises.
  - **Failed notification:** the release message after a failed READ, or the `write_failed` message after a WRITE timeout, could not be sent.
  - **KV expired:** P freed blocks without a transfer. That is either the scheduler's READ-mode `defer_timeout` reap or the writer's WRITE-mode defer timeout.
- The READ-mode reap no longer counts a request as expired when its ACK arrived in the same step. The blocks were already freed through the ACK path, so counting it would overstate expiry.
- The READ failure and timeout logs, and the WRITE failure and timeout logs, now name the transfer ID and the peer address. The READ logs also say how many reads failed or were still pending.
- The MoRIIO usage docs gain a "Prometheus metrics" section.

The metric surfaced a pre-existing stall: on the xgmi backend, every multi-block transfer takes exactly `transfer_timeout` (30 s by default). Rerunning with `transfer_timeout=3` gives P90 3070 ms, so the delay tracks that setting.

The cause is in mori's `TransferStatus::WaitFor` (`include/mori/io/common.hpp`):
- XGMI/Fabric completions are polled from a HIP event, and nothing notifies the condition variable.
- A bounded wait therefore polls once, then sleeps until the deadline before polling again.
- vLLM calls `wait_all(timeout_ms=transfer_timeout)`, so it always hits this path.

That fix belongs in mori and is out of scope for this PR.

## Details

**Why the connector measures timing itself.** MoRI-IO's `TransferStatus` exposes only a code, a message and a terminal state; it has no timing or size data. So duration runs from the connector posting the first RDMA op of a request to the connector observing completion:
- **READ (D):** bytes and descriptors are summed in `_post_read_with_backoff`, the single place every READ is posted. A SQ-full retry is counted once. The duration ends when `_pop_done_transfers` sees the batch DONE, so it is rounded up to the step that polls it.
- **WRITE (P):** KV is pushed layer by layer, so `RemoteAllocInfo` accumulates bytes, descriptor counts and the first post time across layer tasks. The duration ends after `write_done` is sent in `_finalize_if_complete`, so it includes the forward pass of later layers. The docstring and the docs state this.

**Thread safety.** WRITE stats are recorded on the `MoRIIOWriter` thread while the main thread snapshots them in `get_kv_connector_stats()`. The stats class therefore takes a lock around every record and `clone_and_reset()`, and drops the lock when serialized, exactly as Mooncake does. READ bookkeeping is main-thread only.

**Scheduler-side stats.** The READ-mode reap happens in `MoRIIOConnectorScheduler.update_connector_output`, where no worker stats exist. The scheduler keeps its own stats object, and `MoRIIOConnector.get_kv_connector_stats()` returns whichever side the connector instance owns. The engine core already merges scheduler-side stats into the worker stats (`scheduler.py`, after `update_connector_output`).

**Tradeoffs and limitations.**
- A WRITE failure is counted on P and again on the D that is told about it. They are separate engines, and each counts what it saw.
- Unlike NIXL, notification failures are a separate counter and are not folded into failed transfers, so the two counters can be summed.
- Counters for failure modes other RFC gaps are still fixing are left to those PRs, rather than adding keys that are always zero here:
  - handshake failures (gap 4);
  - lease expiry and notifications after expiry (gap 2);
  - unmatched `write_done` (gap 10).
- A WRITE that `seal_pending_transfers` finalizes on the main thread still lets a failure escape the writer's error handler. That predates this PR, so such a failure is not counted.
