# [CI][ROCm] Check skinny-GEMM guard dispatch without torch.profiler

[Upstream PR](https://github.com/vllm-project/vllm/pull/64655) · state: closed · merged: True

## Original PR description

- Detect whether `rocm_unquantized_gemm_impl` took the skinny path by wrapping `ops.wvSplitK`, instead of reading kernel names from `torch.profiler`
- Drop the profiler capture retry loop and the kernel-name matchers that worked around empty captures
- Check numerics on the same call whose dispatch was asserted, under both caps

The four dispatch tests added in #63179 fail with `kernels=[]` on the daily Full CI run on MI300 ([build 98403](https://buildkite.com/vllm/ci/builds/98403#01a188d7-e91a-4a6f-82cf-7640a13143d4), both attempts) but pass on per-commit builds. Only the daily run arms the kernel recorder from vllm-project/ci-infra#685, which registers its own ROCProfiler SDK tool through `ROCP_TOOL_LIBRARIES`. With that set, the SDK configures only the listed tool. Kineto's `rocprofiler_configure` in `libtorch_cpu.so` never registers, and `torch.profiler` records nothing, not even a plain `a @ a`. The guard's contract is which branch runs, so the test now checks that directly, regardless of what else is profiling the process.

Validation on MI355X, with the ci-infra recorder built from source and armed the way the daily run arms it:

- Before: `pytest tests/model_executor/layers/test_lmhead_skinny_gemm_guard.py` passes 9/9 without the recorder and fails the same 4 tests as CI with it.
- After: 9/9 passed in 10/10 runs without the recorder, 10/10 with it, and with `VLLM_ROCM_USE_AITER=1`.
- Mutation check: removing the guard from the dispatch fails `test_n5_big_weight_dispatch[None-False]`; removing the n=1 carve-out fails `test_n1_big_weight_dispatch_unchanged`.
- Full `pytest -v -s model_executor -m '(not slow_test) and (not distributed)'` under the recorder: 1403 passed, 90 skipped, 0 failed (same count as per-commit CI).

No open PR touches this test (searched `test_lmhead_skinny_gemm_guard`, `skinny gemm guard`, `kernrec`). MI300 was not available locally; the CI group runs there.
