# [XPU] Route Inkling to the portable AMD Triton kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/59581) · state: closed · merged: False

## Original PR description

## Purpose

Enable Inkling models on Intel XPU by routing them to the existing portable
AMD Triton kernels (`vllm/models/inkling/amd/`) instead of adding a parallel
XPU tree. XPU lacks CuTe/FA4 and the Lamport all-reduce used by the NVIDIA
path. All changes are platform-gated; ROCm and CUDA behaviour is unchanged.

- `inkling/__init__.py`: dispatch `amd/` ops on ROCm or XPU.
- `amd/ops/fa4_rel_attention.py`: import `on_gfx950` only on ROCm (the ROCm
  platform module queries `torch.cuda` at import). Add a `Q_TILE_PLAIN_PTR`
  constexpr, enabled on XPU, that loads the Q tile with plain pointers;
  triton-xpu 3.8 miscompiles the 3-D block_ptr + reshape + dot pattern when
  BLOCK_Q > 1 (wrong Q rows). The original block_ptr path is kept for ROCm.
- `amd/ops/norm.py`, `amd/ops/silu_and_mul.py`: query compute units through
  `current_platform` instead of CUDA device properties.
- `amd/ops/qkvr_prep.py`: run K/V prep inline when no aux stream exists.

## Test Plan

The full checkpoint (~495 GiB BF16) does not fit on a single XPU node, so
real-weight runs used reduced copies of the model on Intel Arc Pro B70. In
each reduced copy all 42 layers, attention, dense MLPs and both shared experts
are kept at full size; only the routed experts are cut (taking the first E of
256), with the router sliced to match (shared-expert router rows kept); MTP
dropped. The reduced models are numerical fixtures, so these runs check parity
with a reference, not output quality.

- Kernel-level validation of the AMD-route ops against a PyTorch reference,
  covering TP 1/2/4/8, KV page sizes 16/32/64/128, decode, prefill and chunked
  prefill, with a K-fault negative control and a control that forces the
  block-ptr branch on XPU.
- Inkling unit tests on XPU.
- Real-weight greedy and logprob parity on two partial-expert checkpoints:
  16 experts (~41 GiB) at TP=2, and 64 experts (~131 GiB) at TP=8 on
  `vllm/vllm-openai-xpu:nightly` (`0.30.1rc1.dev493+gac9126e58`) with this
  commit applied. Compared against a CPU transformers reference built from the
  same checkpoint (fp32 and bf16), with and without chunked prefill, plus a
  decode-vs-prefill consistency check repeated three times to establish
  run-to-run noise. The CPU bf16-vs-fp32 comparison serves as the noise floor.
- `vllm serve` smoke test on the 64-expert checkpoint at TP=8: startup,
  `/health`, `/v1/models`, `/v1/completions`, `/v1/chat/completions`.

## Test Result

- Kernel matrix: 777/777 pass at TP 1/2/4, 193/193 at TP=8. K-fault control
  fails as intended. Forcing the block-ptr path on XPU reproduces 216
  failures, confirming the gate is what fixes correctness.
- Unit tests: 109 passed, 4 skipped (CUDA-only).
- Serve (E=64, TP=8): startup clean, all four endpoints return 200.
- Parity (top-1 agreement / median prompt logprob delta / p95):

| Checkpoint | Comparison | Top-1 | Median Δlp | p95 Δlp |
|---|---|---|---|---|
| E=16, TP=2 | XPU vs CPU fp32 | 0.985 | 0.0013 | – |
| E=16, TP=2 | XPU chunked prefill vs CPU fp32 | 0.985 | – | – |
| E=64, TP=8 | XPU vs CPU fp32 | 0.951 | 0.0013 | 0.62 |
| E=64, TP=8 | XPU chunked prefill (256) vs CPU fp32 | 0.954 | 0.0012 | 0.68 |
| E=64, TP=8 | CPU bf16 vs CPU fp32 (noise floor) | 0.960 | 0.0014 | 0.59 |

  The E=64 XPU results sit within the CPU bf16-vs-fp32 floor. The lower
  agreement there is a property of the reduced model (64-expert top-6 routing
  has many near-tie decisions), as CPU bf16 and fp32 diverge to the same
  degree.
- Decode-vs-prefill consistency median delta: 0.034-0.054 (E=16) and
  0.031-0.043 (E=64) across three runs, within run-to-run noise.
