# [KVConnector][NIXL] Add stream-ordered same-host CUDA IPC pulls

[Upstream PR](https://github.com/vllm-project/vllm/pull/65639) · state: open · merged: False

## Original PR description



## Overview

Add an opt-in same-host CUDA IPC pull path to `NixlConnector`. Decode admits the request in the compute batch, copies the producer's cache with `swap_blocks_batch`, and waits on a CUDA event before consuming it, avoiding the normal receive-completion scheduler round trip.

Related design discussion: #50913. This targets direct device-memory pulls on one host; the NIXL handshake, descriptor mapping and completion notifications are retained.

## Claims

- `kv_connector_extra_config.enable_local_fastpath=true` enables direct CUDA IPC imports and batched device-to-device copies for matching P/D TP and cache geometry. The default is off; cross-host peers use ordinary NIXL pulls.
- Adjacent and aliased ranges are merged only when their source-to-destination byte mappings agree. Conflicting overlapping destinations and descriptors crossing an exported allocation are rejected.
- The copy stream waits for destination initialization. A completion event gates the compute stream before KV/SSM state preprocessing, while CPU input preparation can overlap the copy. Producer completion notifications remain gated on the copy event.

The human submitter provided and confirmed a serving-profile report collected on **2026-11-04**. These measurements are from an internal downstream adaptation, rather than a GPU run of this upstream branch. The upstream patch includes the same allocation-bound checks, alias coalescing and copy-stream initialization fence.

Configuration: **8×H20, P/D TP4/4, Qwen3.8-Flash-Next, attention KV in FP8, SSM state in BF16, block size 864, DFlash with 5 draft tokens**, `max_num_seqs=48`, `max_num_batched_tokens=32768`. P graph mode was `FULL_AND_PIECEWISE` with a 16,384 capture limit; D used `FULL_DECODE_ONLY` with a 288 capture limit. Each arm used the same 10,244-token input and a 32-token output budget, with prefill split into 8,640 + 1,603 computed tokens.

**One profiled request per arm after warmup.** The node differed, baseline P scheduling was async while the IPC producer was synchronous, and the sampling seed was not fixed. Consequently these are observations of the transfer path, not a controlled end-to-end speedup or throughput claim.

|---|---:|---:|
| Copied bytes per D rank | 184,653,312 (176.099 MiB) | 106,094,592 (101.180 MiB) |
| GPU P2P copy events per D rank | 832 | 1 batch event |
| GPU copy active time per D rank | 2.652–2.694 ms | 0.362848–0.363807 ms |
| Copy window across all four D ranks | 13.050650 ms | 0.713240 ms |
| P last GPU work → earliest D graph kernel | 47.264269 ms | 25.936590 ms |

The four-rank window means earliest copy start to latest copy completion, not a sum of rank durations. The handoff difference is **21.327679 ms**. Its non-overlapping components were:

| Handoff segment | NIXL | IPC |
|---|---:|---:|
| P last GPU work → first copy | 18.195734 ms | 21.451926 ms |
| Four-rank copy window | 13.050650 ms | 0.713240 ms |
| All copies complete → first D graph kernel | 16.017885 ms | 3.771424 ms |

The IPC trace shows 24 visible CPU input operators overlapping D0's GPU copy, with a 113.401 µs overlap union. No GPU kernel overlapped cache copying on any D rank. Baseline was already GPU P2P; this is not evidence of switching TCP to NVLink. A batch event does not imply one contiguous range or one hardware DMA operation. The byte reduction is consistent with alias deduplication, but per-alias address attribution was not captured.

Both requests generated 32 reasoning tokens with DFlash enabled. Their draft acceptance paths diverged; **output equivalence, acceptance-rate correctness and model accuracy have not been established**. Client latency was 894.672107 → 841.450084 ms in these two profiled requests, but node, scheduling, sampling and collective-wait differences prevent attributing that entire delta to this connector.

## Details

The changed request flow is:

1. P completes prefill under synchronous scheduling and publishes its usual block lease and remote block metadata, plus a local-host marker. The handshake carries CUDA IPC allocations and GPU identity.
2. D recognizes the matching boot identity, allocates destination blocks and admits the request in the same scheduler step instead of parking it in `WAITING_FOR_REMOTE_KVS`.
3. After destination initialization and block-table updates, the MRV2 connector hook resolves the existing NIXL descriptor IDs, imports P allocations, validates ranges and merges compatible spans.
4. A dedicated stream waits for initialization, calls `swap_blocks_batch` and records completion. The compute stream waits before state preprocessing; the CPU can continue input preparation.
5. Event polling triggers the usual notification and metadata cleanup only after copying completes. No NIXL receive-handle completion is reported for this already-admitted request; source leases and deferred destination block release protect cache lifetime.

The substantial connector-side code is isolated from the scheduler/model runner. The common interface only declares stream-ordered load support and its early-load hook; the scheduler retains unready prefix blocks and defers their reuse. MRV2 receives the new runner integration; no model kernels are changed. `swap_blocks_batch` already provides `cuMemcpyBatchAsync` when built with CUDA 12.8+ and supported by the driver, with its existing per-range fallback on older builds.

**Compatibility:** Linux CUDA device buffers, identical P/D TP, block size, layout and physical cache geometry; PP=PCP=DCP=1. Both ends must opt in and use `--disable-extensible-kv-cache`; P must use `--no-async-scheduling`. Sleep mode is rejected. Consumers must exit before producers during ordered shutdown. Once a request selects IPC, setup/copy errors are surfaced rather than silently switching its execution contract. The metadata compatibility version is bumped, so P and D should run the same revision. MultiConnector composition and heterogeneous TP/layouts are outside this initial scope.

Enable on both ends, changing `kv_role` to `kv_consumer` on D:

```json
{
  "kv_connector": "NixlConnector",
  "kv_role": "kv_producer",
  "kv_buffer_device": "cuda",
  "kv_connector_extra_config": {"enable_local_fastpath": true}
}
```

Usage and compatibility are documented in `docs/features/nixl_connector_usage.md`.

**Duplicate-work checks:** searched open PRs for `NIXL CUDA IPC`, `NIXL fast path`, and references to #50913/#56874. #65137 repairs UCX transport selection for extensible allocations; #61056 batches host-buffer staging copies; #51919 adds dispatch/notification side channels and first-token seeding; #63936 reports ordinary NIXL pull completion earlier; #65319 starts async loads while a batch is full; #56874 overlaps layer-wise NIXL WRITEs. This patch instead imports same-host allocations directly, deduplicates the device-copy plan and admits decode under a compute-stream event dependency. It does not implement layer-wise or chunk-wise P-side early sending.
