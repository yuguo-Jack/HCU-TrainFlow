# Hardware-agnostic model definition for DeepSeek V4

[Upstream PR](https://github.com/vllm-project/vllm/pull/45470) · state: open · merged: False

## Original PR description



## Purpose

> Scope of this PR: A work in-progress sketch of how a hardware-agnostic
> model definition could look in-tree, using DeepSeek V4 as the case study.
> Feedback and discussion are highly appreciated.

vLLM has recently moved toward hardware-specific model definitions:
[#42770](https://github.com/vllm-project/vllm/issues/42770) split DeepSeek V4 into per-platform branches (`nvidia/`, `amd/`, `xpu/`), each owning the kernels that are fastest on that hardware. The follow-up [#44219](https://github.com/vllm-project/vllm/issues/44219) proposed extending this with a dedicated *hardware-agnostic* sibling so out-of-tree accelerators have a working path to deployment.

Three principles guided the structure:

1. **Strict isolation from vendor branches.** 
 `hw_agnostic/` never  imports from `nvidia/`, `amd/`, or `xpu/`.
  It only relies on shared infrastructure in `hw_agnostic/ops/`, `common/ops/`, `compressor.py`, `sparse_mla.py`'s V4 backend and the `model_executor` with core layers / activations / quantization.
2. **Full-graph `torch.compile` support.** 
  It allows the use of `@support_torch_compile`
3. **Pluggability for OOT vendors.**
  It leverages the infrastructure of `CustomOps` and `PluggableLayers` to enable OOT vendors to replace specific components. For the attention, the MLA wrapper `DeepseekV4MultiHeadLatentAttentionWrapper` is a `PluggableLayer`, which can also be overridden.

In particular this PR introduces a new `hw_agnostic` folder, next to the hardware-specific folders, containing a hardware-agnostic implementation of the DeepSeek V4 model. The implementation is isolated from the hardware-specific implementations such as `nvidia`, `amd` or `xpu` and does not interfere with them.
It subclasses `DeepseekV4FlashMLABackend` and the four perf-critical attention kernels live in hw_agnostic/ops/ (adapted from XPU); Furthermore, it employs the existing `FusedMoE` rather than NVIDIA's SM100-only MegaMoE. 

Points that potentially require further discussion:

- What should be a proper selection mechanism for this code path? Currently it is handled via an environment variable `VLLM_USE_HW_AGNOSTIC`. 
- What is the right level of pluggability? For example, in the current approach, the entire attention wrapper `DeepseekV4MultiHeadLatentAttentionWrapper` is a `PluggableLayer` an would need to be overridden by an OOT plugin.
- How should the testing look like and where should it take place?

cc @tdoublep @zou3519

This PR has been significantly updated. At this point, the DSv4 model is fully functional in eager-mode as well as with torch.compile. In short, the PR now

As mentioned, this PR is a sketch of how the hw-agnostic modelling code could be structured and any feedback, discussion or comments on how to improve the concept is highly welcome.

1. Leave the custom passes intact as they are now. Only very few, generic passes, such as NoOp elimination or DCE, are really relevant and even triggered for the hw-agnostic path. This will still use the `VllmBackend` for compilation, using piecewise CUDA graphs and the entire custom pass machinery from vLLM gets invoked.
2. Still use the `VllmBackend`, but disable the custom passes from vLLM. For example, we can turn the `pass_config` flags off, which still keeps the pass-manager loaded but with an empty pass list. Again, this approach uses the piecewise CUDA graph infrastructure.

4. Make the breakable CUDA graphs to work with `STOCK_TORCH_COMPILE`. Potentially fast, plus only PyTorch native custom passes.

Options 2-4 would avoid using the vLLM custom passes, which to me should be okay for the hw-agnostic modeling definitions. Questions might arise though for the vLLM IR, as this relies on custom passes...

@zou3519 This is a very good point. The current code in this PR is utilizing a tiny [plugin](https://github.com/bohnstingl/vllm/tree/migratedsv4/tests/plugins/vllm_dsv4_oot_platform) to invoke the `hw-agnostic` path of the DSv4 model. In principle this plugin can be installed on a machine with any underlying hardware, such as GPUs, that supports all the used operation, but it is set to currently piggybacking on the `PlatformEnum.CUDA`.

However, there are still some constraints as to where this code can run in reality. For example, the current code is only supported on infrastructure that has native fp8 compute support, such as Blackwell or Hopper GPUs. To run the model on older generations of GPUs, such as A100s, one would need to have a workaround for the fp8 compute that I developed in a branch on top of this one, see https://github.com/bohnstingl/vllm/pull/2.

So I guess the bigger questions to ask here are:

1. Which tests to run in the first place? E2E tests with the DSv4 model? Layer / op / backend specific tests?
2. On which hardware do we want to run those tests? CPU, GPU, or OOT devices?
3. If we'd like to run on GPU, on which exact generation to run? H100 with fp8 support and leave the validation of other, potentially older GPUs for OOT work?
