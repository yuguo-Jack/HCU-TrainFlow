# [Spec Decode] Replace torch.compile'd AV draft-budget selection with a Triton kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/63421) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Replace adaptive verification's `torch.compile(dynamic=True)` draft-budget selection with a single-launch Triton kernel, JIT'd once in `warmup_kernels`. This removes the mid-serving compile stalls and cuts the host cost of every budget-binding step about 6x.

Related: #62539 fixes the same stall by pre-compiling the Dynamo specializations at startup. This PR instead removes the compile, which also removes the launch overhead it never paid for (details below). Credit to #62539 for the root cause and for spotting the `max_num_reqs` duck-sizing specialization.

## Claims

- No budget-kernel compiles during serving: one Triton JIT at warmup (0.45 s warm cache, 1.0 s cold) instead of 4–5 Dynamo graphs compiled on the first trimmed steps (1.8–4.7 s per process).
- Host time per budget-binding step drops from 76–90 µs (compiled) to ~15 µs. GPU time drops from 85–100 µs to 22–30 µs at typical batch sizes.
- Qwen3-4B + DSpark, GSM8K, concurrency 16 (H200): adaptive verification goes from 4,783 to 6,803 output tok/s (median), on par with #62539 (6,756; within run-to-run noise). Accuracy unchanged.

## Details

- **Root cause.** `warmup_kernels` runs with adaptive verification off, and cost profiling never trims, so the compiled budget function first ran on a live trimmed step. It then recompiled for each 0/1 specialization (and for `num_reqs == max_num_reqs`, per #62539).
- **Why not keep the compile.** The op is about six tiny kernels and is bound by host launch overhead. Compiled it saves only ~0–20 µs over eager, and it still costs ~80 µs of host time on every binding step. It runs eagerly in `prepare_inputs`, outside any CUDA graph, so that cost lands on the step's host critical path whenever the host is the bottleneck.
- **Kernel.** A single program does three passes:
  1. Survival prefix products, stored as float bits. Values are non-negative, so int order matches float order; ineligible slots store −1.
  2. A binary search on the bits for the `draft_budget`-th largest value.
  3. Per-request counts above the threshold, with ties handed out in request order.

  Survival is non-increasing along a request, so per-request counts fully describe the winners, as before. With distinct values the result is identical to the old top-k. On exact ties, top-k's choice was already unspecified.
- **Specialization.** `num_reqs` and `draft_budget` are `do_not_specialize`, so the one JIT in `warmup_budget_kernel()` covers every shape. The kernel needs a `max_num_reqs × K` int32 scratch buffer.
- **Tradeoffs.** The binary search takes 31 sequential passes over `num_reqs × K` slots, so GPU time grows with very large batches (67 µs at 1,024 requests and K=8). That's still below the old path, and negligible next to a step at that batch size. I couldn't test ROCm or XPU here, where adaptive verification is also used. The kernel uses only standard Triton ops (`bitcast`, `cumsum`, `debug_barrier`, a scalar `while`).
