# [Bugfix][Multimodal] Guard GLM-5.3-Flash video sampling against zero source fps

[Upstream PR](https://github.com/vllm-project/vllm/pull/62261) · state: closed · merged: False

## Original PR description

## Overview

Fixes #62260. `Glm5NextVideoBackend` divides by `source.original_fps` when building frame timestamps, and every vLLM decoder reports an unknown/VFR frame rate as `0`, so those videos crashed with an unhandled `ZeroDivisionError` (HTTP 500) before any frame was read. Raise a descriptive `ValueError` instead, which maps to HTTP 400.

## Claims

- A video whose container reports no frame rate now fails with `ValueError("GLM-5.3-Flash video sampling needs a known source fps, ...")` instead of `ZeroDivisionError: float division by zero`, for both the reported-duration and the derived-duration paths.
- Known-fps sampling is unchanged; no other code path is touched.
- Adds two tests: `test_glm5next_backend_rejects_unknown_source_fps` (the sampler itself) and `test_glm5next_load_bytes_rejects_unknown_source_fps` (the same via `load_bytes`, with the decoder reporting 0 fps).

## Validation

Reproducer (no weights, no GPU, no video file; pure frame-index selection):

```python
from vllm.multimodal.video import Glm5NextVideoBackend
from vllm.multimodal.video_decoders.base import (
    VideoSourceMetadata,
    VideoTargetMetadata,
)

target = VideoTargetMetadata(num_frames=-1, fps=2, max_duration=300)
for duration in (5.0, 0.0):
    source = VideoSourceMetadata(
        total_frames_num=150, original_fps=0.0, duration=duration
    )
    Glm5NextVideoBackend.compute_frames_index_to_sample(source, target)
```

## Details

Root cause: `_sample_frame_indices` builds `timestamps = [i / fps for i in range(total_frames)]` and the duration fallback immediately above it already guards the zero case (`... if fps else 0`), but `duration_per_frame = 1 / fps` on the next line does not. `source.original_fps` reaches it unchanged because `Glm5NextVideoBackend` has no `_prepare_source` override.

Every decoder reports an unknown frame rate as `0.0`, not `None`: OpenCV returns `cap.get(cv2.CAP_PROP_FPS)` directly, TorchCodec falls back to `0.0` when `average_fps` is falsy. HF's `Glm5NextVideoProcessor.sample_frames` raises `ValueError` in this situation, so raising matches the reference behavior and maps to HTTP 400 through `create_error_response`.

Why not mirror the Qwen3-VL fix (#60501): that one substitutes 24 fps because HF's Qwen3VL processor does. HF's GLM5Next processor raises instead, so substituting a rate here would silently invent timestamps the processor would never produce.

This follows the guards already present in `Qwen2VLVideoBackend`, `GLMGAVideoBackend` (#54396) and `ClefOmniVideoBackend`.

### Not a duplicate

- #55727 caps request-controlled `fps`/`max_frames` for this backend — a different defect (request amplification), and it does not touch zero source fps.
- #54396 guards `GLMGAVideoBackend` only. A reviewer asked whether Glm5Next belongs in that PR; the author who raised it said they were not planning a separate PR for it. If #54396 is updated to cover Glm5Next (it currently has merge conflicts and does not), this PR should be closed in favour of it — the change is identical in shape.
- #54390 / #53844 / #60501 cover Qwen3-VL (`#60501` merged).
