# [CPU][GDN] Route FP16 attention through Triton/FLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/60405) · state: open · merged: False

## Original PR description

Keep BF16 on the optimized C++ kernels while allowing FP16 models to use the supported Triton/FLA fallback path.



## Overview

CPU GDN attention rejects FP16 before any kernel runs (`CPU GDN attention requires BF16`). Route FP16 through the existing Triton/FLA path in `layer._forward_core`, and leave BF16 on the C++ kernels.

## Claims

- FP16 CPU GDN (Qwen3.5 gated-delta) completes instead of dying on the BF16 assert.
- BF16 still uses `cpu_gdn_attention_core` and the packed C++ conv / chunk kernels.
- FP16 accuracy was measured on the full GSM8K test set: **0.9083** exact match for both strict-match and flexible-extract.

## Validation

Qwen/Qwen3.5-4B, `dtype=float16`, GSM8K, 5-shot, greedy (`max_gen_toks=2048`), `max_model_len=4096`, `language_model_only`, `enable_thinking=False`, `mamba_ssm_cache_dtype=auto`. Triton wheel `3.8.0+cpu`. vLLM `v0.30.1rc1.dev727+g331382598`. All 1319 problems finished.

| Filter | Metric | Score |
| --- | --- | --- |
| flexible-extract | exact_match | 0.9083 ± 0.008 |
| strict-match | exact_match | 0.9083 ± 0.008 |

The two filters agree, and the first sample is a normal solution ending in `#### 18`. Without this branch the same launch asserts in `cpu_gdn_attention_core` and never scores.

```bash
VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=400 TRITON_PRINT_AUTOTUNING=1 lm_eval \
  --model vllm \
  --model_args pretrained=Qwen/Qwen3.5-4B,dtype=float16,max_model_len=4096,language_model_only=True,enable_thinking=False,trust_remote_code=True,mamba_ssm_cache_dtype=auto \
  --tasks gsm8k \
  --num_fewshot 5 \
  --batch_size auto \
  --gen_kwargs max_gen_toks=2048 \
  --apply_chat_template \
  --output_path accuracy-dir \
  --log_samples
```

CPU GDN FP16 with this checkpoint is not in CI. The run above is the validation.

## Details

`QwenGatedDeltaNetAttention.forward_cpu` always calls `cpu_gdn_attention_core`. That op asserts `mixed_qkv.dtype == torch.bfloat16`, so `dtype=float16` (which casts the BF16 checkpoint to FP16) never reaches a kernel. The C++ conv and chunk kernels are BF16 implementations; opening them to FP16 is a separate change.

The FP16 branch calls `layer._forward_core` and returns. On CPU that path already uses PyTorch conv and the FLA chunk and decode kernels, which accept FP16. BF16 falls through to the existing assert and the C++ nonspec / spec paths. The branch sits in front of the spec-cache split, so FP16 spec-decode also takes `_forward_core`. The GSM8K run was non-speculative (`speculative_config=None`).

A cold Triton autotune on the first prefill can exceed the default 300s `execute_model` timeout. The scored run got past that and then ran normally.
