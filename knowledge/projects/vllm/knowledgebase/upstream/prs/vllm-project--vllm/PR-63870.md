# [Rust Frontend][gRPC] Separate liveness from inference readiness

[Upstream PR](https://github.com/vllm-project/vllm/pull/63870) · state: closed · merged: True

## Original PR description

## Update: stacked on #64265, readiness reported by the engines

**Stacked on #64265** (`[Rust Frontend] Run utility calls to completion when the caller is cancelled`). The base branch `bz/rust-uncancellable-utility` mirrors #64265's head; this PR will be retargeted to `main` once #64265 merges. Its three commits:

- f2ed5490bc (Julien): this PR's net change, squashed from the previous history (last head 21feaf4a8e, which also merged main).
- c7c67d866c: holds the readiness guard until the engines reply.
- 5ac1ff2fe7: withdraws readiness before the gRPC listener stops, including when the server is aborted.

This revision keeps the gRPC service mapping and changes how the frontend learns the engine state. The original revision inferred it in the client from the results of the control calls it sent (`client/availability.rs`: per-call facts, `resolve`, epochs, and a confirm loop asking `is_sleeping` plus a worker RPC). EngineCore already owns that state, so it now reports it:

- `EngineCore.is_inference_ready()` (Python, 8 lines): not paused (including for a checkpoint) or asleep, and no worker reports `has_incomplete_weight_update()`.
- The client (`client/readiness.rs`) withdraws readiness before a call that stops serving is sent (pause, sleep, checkpoint prepare, start weight update), and rechecks after every control call ends by asking the engines `is_inference_ready`. An epoch discards answers that predate a call, so readiness becomes `SERVING` only from an engine answer. The public `collective_rpc` also rechecks, which covers weight updates and the dev-mode `/collective_rpc` route.
- A control call passes its readiness guard to `call_utility`, whose task (from #64265) holds it until the engines reply. A caller cancelled after sending a pause, for example by a client disconnecting from `/pause`, therefore cannot recheck before the engines have handled the pause.
- The client asks only while someone subscribes (the gRPC server), so HTTP-only deployments add no worker RPC after control calls.
- With sleep mode, the client asks once at connect: only such engines can start prepared for a checkpoint (`--checkpoint-prepare-on-startup`), and an engine without the utility fails startup with an error naming it.
- gRPC wiring: `EngineHealth` groups the client's liveness and readiness watches, and `HealthMonitor` registers the services before the listener accepts connections and then follows the watches.
- Shutdown order: `HealthMonitor::serve` runs the gRPC server, and both the signal that stops its listener and the forced abort (immediate with the default `--shutdown-timeout 0`) wait until every service except `liveness` reports `NOT_SERVING`. A `Health/Watch` subscriber therefore receives the withdrawal before its connection closes. A `Check` on a new connection after shutdown starts gets `NOT_SERVING`, an unknown service, or a refused connection; probes treat all three as not ready. `lib.rs` and the gRPC test server share this wiring.
- `finish_weight_update` clears the worker's incomplete-update flag only after the draft model's quantized LM heads are restored, so a failed restore keeps readiness withdrawn.

The service mapping is the same as in the original revision:

| Service | Reports `NOT_SERVING` when |
| --- | --- |
| `liveness` | The engine has failed. |
| `readiness` and `vllm.Inference` | The engines report not ready, a call that stops serving is in flight, the engine has failed, or shutdown has started. |
| `vllm.Control` and `""` | The engine has failed or shutdown has started. |

`readiness` always equals `vllm.Inference`; both are kept. Kubernetes probes and the Dynamo sidecar use `liveness` and `readiness` (ai-dynamo/dynamo#14897), while `vllm.Inference` and `vllm.Control` remain the per-service statuses.

## Original description (previous revision)

## Overview

The Rust frontend's gRPC health service reports the same status for every service name, so Kubernetes and sidecars cannot tell an engine paused for an RL weight update from one that needs a restart. This adds two health services: `liveness`, which fails only when the engine fails, and `readiness`, which also fails while the engine is paused (including for a process checkpoint) or asleep, or while a weight update has not finished successfully. `vllm.Inference` now reports the same status as `readiness`; `vllm.Control`, `""`, and the protobufs are unchanged. Motivation: [ai-dynamo/dynamo#14897](https://github.com/ai-dynamo/dynamo/issues/14897).

**Size: about 325 lines of non-test Rust and 8 lines of Python** (+336/−34, not counting tests, comments, blank lines, reindentation, or the 39 lines moved unchanged onto `ClientInner`). The logic is four pieces:

- the engine-state tracker in `client/availability.rs`, about 170 lines:
  - two facts (every engine is scheduling; every worker's weights are complete) and the rule that readiness is SERVING when both allow serving, keeping its last value while one is being confirmed;
  - a guard each control call holds, which withdraws readiness before a pause or update start is sent and records the fact the call's result settles;
  - a background loop that runs while either fact is unknown (after a resume, a weight-update finish, a failed or cancelled call, or overlapping calls). It asks the engines `is_sleeping` and the workers `has_incomplete_weight_update`, asks again if another control call made the answer stale, and retries a failed attempt every second.
- the wiring in `client.rs` and `client/imp.rs`, about 90 lines:
  - each pause, sleep, resume, wake-up, weight-update and checkpoint method takes the guard;
  - `ClientInner` keeps the engine IDs and client index, so the loop can call the engines;
  - `subscribe_availability`, the loop's task, and one `is_sleeping` call at connect for sleep-mode engines, which may start prepared for a checkpoint.
- the gRPC mapping in `grpc/health.rs` and `lib.rs`, about 70 lines:
  - register `liveness`, and register `readiness` and `vllm.Inference` with the current availability;
  - drive `readiness` and `vllm.Inference` from the tracker;
  - on shutdown, publish NOT_SERVING before the listener stops accepting connections.
- the worker method `has_incomplete_weight_update()` in `gpu_worker.py` and `worker_base.py`, 8 lines: tracked per target (base or draft model), set once an update starts, and cleared by that target's successful finish. Because of the second target, a successful finish asks the workers rather than assuming the weights are complete.

Moving the existing `call_utility` and `collective_rpc` fan-out onto `ClientInner` changes no behavior. The rest of the +1119/−162 diff is:
- tests (+575/−63): 7 new tests (5 Rust, 2 Python), the two existing health tests and the existing full-wake-up test extended, gRPC test setup that passes the tracker, and the new worker attribute in hand-built test workers;
- docs (+43 in `docs/deployment/k8s.md` and `rust/README.md`);
- doc comments.

## Claims

- `liveness` reports `NOT_SERVING` only after an engine failure. Pause, sleep, checkpoint prepare, weight updates, and orderly shutdown do not affect it until the listener closes.
- `readiness` and `vllm.Inference` report `NOT_SERVING` in these cases:
  - while a pause, sleep (including a partial wake-up), or process-checkpoint prepare sent through this frontend's HTTP or gRPC control APIs is in effect;
  - while an engine started with `--checkpoint-prepare-on-startup` is not yet restored;
  - from the start of a weight update until one finishes successfully, including after a failed load;
  - on engine failure or shutdown. On shutdown they are withdrawn before the listener stops accepting connections. With the default `--shutdown-timeout 0`, the gRPC server is aborted without a grace period, so a Watch can see its connection close before it receives `NOT_SERVING`; probes treat both as not ready.
- Kubernetes probes: startup and liveness use `liveness`, readiness uses `readiness`, as documented in `docs/deployment/k8s.md`. A liveness probe that names `vllm.Inference` now fails while the engine stays paused, so it should move to `liveness`. Likewise, a client that waits for `vllm.Inference` to be SERVING before it connects now waits while the engine is paused. Dynamo's vLLM sidecar does this at startup (`lib/sidecar/vllm/src/engine.rs`). To connect to a paused engine, wait on `vllm.Control`, which reports SERVING while paused in every version; earlier versions do not have `liveness`.

## Details

The worker reports `has_incomplete_weight_update` rather than whether an update session is active because a failed `update_weights` ends the session without restoring the weights, so generation fails until a later update finishes.

Known limitations:
- Pauses that bypass these client methods, such as the dev-mode `/collective_rpc` route, are not observed.
- A full wake-up after a level-2 sleep reports SERVING before the weights are reloaded. The documented order (wake `weights`, reload, then wake `kv_cache`) keeps readiness down until the weights are back.
- A failed process checkpoint leaves the engine paused, with no way to restore. `readiness` stays `NOT_SERVING` and `liveness` stays `SERVING`, so whatever drives the checkpoint must restart the pod when `/checkpoint/status` reports the failure.

The frontend infers engine state from the results of the calls it sends and asks the engines when a result is not conclusive. An engine-reported readiness state, as proposed in [#60505](https://github.com/vllm-project/vllm/pull/60505), could replace these confirmations.

No open or merged PR splits Rust gRPC liveness from readiness (checked 2026-10-26). [#60505](https://github.com/vllm-project/vllm/pull/60505) and [#59179](https://github.com/vllm-project/vllm/pull/59179) add Python HTTP readiness endpoints; [#56886](https://github.com/vllm-project/vllm/pull/56886) (draft) adds a gRPC shutdown grace period.
