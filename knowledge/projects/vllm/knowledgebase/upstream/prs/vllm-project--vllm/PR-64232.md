# [Rust Frontend] Log one structured access log event per HTTP response

[Upstream PR](https://github.com/vllm-project/vllm/pull/64232) · state: closed · merged: True

## Original PR description

## Overview

Log one structured INFO event per HTTP response on the Rust frontend, and make `--disable-uvicorn-access-log` and `--disable-access-log-for-endpoints` real options instead of no-ops. Python's API server logs one uvicorn access line per response by default; the Rust frontend logged none, so a deployment moved to it lost its request log.

## Claims

- Every response gets one INFO event once its head is ready, including 401s from API-key auth and 404s for unknown routes; a streaming response is logged once, when its stream starts:

  ```text
  HTTP response client=127.0.0.1:52344 method=GET uri="/v1/models?limit=1" version=HTTP/1.1 status=200 latency=1.2ms
  ```

  `client` is absent on a Unix-domain socket, and `latency` covers the time until the response head is ready, not a streamed body.
- `--disable-access-log` (with `--disable-uvicorn-access-log` as a visible alias) turns it off, on `vllm-rs serve` and on the Python launcher path.
- `--disable-access-log-for-endpoints /health,/metrics` drops responses whose path, without the query string, matches exactly; the list is split on commas and trimmed like Python's.

## Details

Python logs through uvicorn's access logger at INFO, on by default. `--disable-uvicorn-access-log` turns it off, and `--disable-access-log-for-endpoints` drops responses by exact path match (`UvicornAccessLogFilter` in `vllm/logging_utils/uvicorn_logging.py`, built by `get_uvicorn_log_config` in `vllm/entrypoints/launchers/utils/server_utils.py`). uvicorn logs when the response head is sent, so every response gets a line. The Rust frontend declared both flags as no-ops, and its `TraceLayer` logs requests only at DEBUG.

- New `middleware::log_access` emits the event, layered outside auth next to `TraceLayer`, so rejected and unrouted requests are logged as uvicorn logs them.
- Both flags are real options on `SharedRuntimeArgs`. They reach Rust through `--args-json` under the Python launcher (a serde alias accepts Python's `disable_uvicorn_access_log` key) and are parsed into a new `AccessLogConfig` on `Config` and `AppState`, which follows the `CorsConfig` path.
- The hand-rolled serve loop now inserts the TCP peer into each request as axum's `ConnectInfo<SocketAddr>`, as `axum::serve` does, so the event carries the client address.

**Layering.** The access log describes HTTP exchanges, so it lives in the server's middleware stack, the only layer that sees every response including those auth or routing reject. The peer address is known only in the serve loop, which exposes it through the standard axum extension rather than a new type.

**Why not raise `TraceLayer` to INFO.** Its default span and `on_response` event already carry method, URI, version, status and latency. But the vLLM log formatter prints every enabled span in scope as a prefix, so an INFO span would prefix every request-scoped log line (output logs, warnings, the chat `request_id` span) with the HTTP fields, and the access log flag would change the shape of unrelated log lines. `TraceLayer` stays at DEBUG.

**Flag names.** There is no uvicorn in the Rust frontend, so the canonical flag is `--disable-access-log`. The Python name stays as a visible alias: `vllm-rs serve` routes only long names and visible aliases to the frontend (`collect_option_names` in `vllm-managed-engine`) and passes anything else through to Python, so a hidden alias would silently do nothing. Python's `--no-disable-uvicorn-access-log` form is not accepted, like the `no-` forms of the other real bool flags; the launcher never forwards it, since it sends only non-default values.

**Differences from Python.**

- The access log is a structured `tracing` event, not uvicorn's request line; the same facts (client, method, target, version, status) are fields, plus `latency`, and the status has no reason phrase.
- IPv6 clients print as `[::1]:52344` (Rust's `SocketAddr`), where uvicorn prints `::1:52344`.
- The path is printed raw as received, where uvicorn re-quotes the decoded path; the two are the same for ordinary ASCII paths.
- `--uvicorn-log-level` stays unsupported. In Python it also sets the access logger's level; in Rust, `RUST_LOG=vllm_server::middleware::access_log=warn` silences the access log on its own.
- Not covered: routes merged through `serve_with_router_extension` sit outside every layer `build_router` installs (auth, HTTP metrics, CORS, `TraceLayer`), and the engine-free `vllm-rs render` server has its own narrow flag set and serve loop. Both are separate follow-ups.

Behavior change: existing Rust-frontend deployments now get one INFO event per response by default, as Python deployments get one line.

Like that draft, it adds a middleware and makes both flags real; unlike it, the event carries the client address and latency as structured fields.
