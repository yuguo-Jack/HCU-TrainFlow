# [Perf][Qwen4Exp] Tune the Qwen3.8-Flash-Next skinny GEMMs for sm_120

[Upstream PR](https://github.com/vllm-project/vllm/pull/59869) · state: closed · merged: False

## Original PR description



## Overview

Enables the CuTe skinny GEMM on sm_120 for `qwen4_exp` models, adds the measured plan table it needs, and adds the tuner that produced it.

Complementary to #59753 (sm_121 LM head, merged) and #59632 (sm_121 plans): both target sm_121, and `_gemm_plans()` still returns `{}` on sm_120. Opened as a draft so the overlap with #59632 can be settled before review — see *Coordination* below.

## Claims

- `_gemm_plans()` has no sm_120 branch, so the skinny GEMM never runs on RTX 5090 / RTX PRO 6000 Blackwell.
- The plan tables are keyed by the TP-local `(N, K)`; the shipped ones were measured at TP=4, so the TP=1 and TP=2 shapes miss every key.
- Adds 58 measured configs over 13 shapes, TP=1 and TP=2, for the sm_120 table.
- Adds `benchmarks/kernels/qwen38fn_skinny_gemm/`, which produced the table and can reproduce or extend it on other parts.

Reproduce:

```bash
python benchmarks/kernels/qwen38fn_skinny_gemm/benchmark_skinny_gemm.py \
  --mode sweep --tp 1 2 --m 1 2 4 8 16 \
  --num-config-shards "$SLURM_ARRAY_TASK_COUNT" --config-shard "$SLURM_ARRAY_TASK_ID"
python benchmarks/kernels/qwen38fn_skinny_gemm/benchmark_skinny_gemm.py \
  --merge 'skinny_sweep.shard*.jsonl'
```

A candidate is kept only if it beats `F.linear` both hot and with the weights rotated past L2, and only if it is at least as accurate against an FP32 reference. The merge reproduces the committed table exactly.

Tests: `tests/kernels/test_bf16_skinny_gemm.py` gains the sm_120 capability-routing case, a table-validity test, and a per-shape dispatch test asserting the selected config is the one used. The CPU-only tests run anywhere; the dispatch test needs an sm_120 card, which CI does not have, and was run on the hardware instead.

## Details

The change to `low_latency_gemm.py` is 113 lines of measured data plus a four-line `_is_sm120()` branch alongside the existing sm_103 / sm_100 / sm_90 / sm_121 ones. No existing path changes behaviour; the diff is purely additive.

**Where the gain comes from.** It peaks at M=2 and M=4 and is modest at M=1, and that shape comes from the baseline, not from this kernel. At M=1 cuBLAS dispatches a dedicated GEMV; from M=2 it must use a tiled GEMM and pads a minimum tile height the work never fills. The shared-expert projection shows it plainly: `F.linear` goes 0.0068 → 0.0145 ms between M=1 and M=2 and stays flat to M=16, while the skinny kernel climbs smoothly 0.0042 → 0.0076. With MTP the verification GEMM runs at `M = (k + 1) * batch_size`, so batch size 1 lands in that window at both k=1 and k=3.

The LM head is the exception at 1.06x, flat across M: it is bandwidth-bound, so cuBLAS wastes nothing there. That inverts what the same sweep found on GB10, where the LM head was the dominant term — this part has far more bandwidth, which stops bandwidth binding anywhere but the largest shape.

**Coordination.** #59632 is titled "Add SM12x plans" but the predicate it adds is `is_device_capability((12, 1))`, so it covers sm_121 only. Six of its shapes coincide with the TP=2 shapes here. If that PR is meant to cover sm_120 as well, this table can be folded into it instead; happy to do that rather than land two tables.

**Limitations.**

- These are per-kernel ratios, not weighted end-to-end gains. Which shapes a deployment actually reaches depends on its quantization config: the same sweep on GB10 found only five of thirteen shapes in an nsys profile, because the per-layer projections were covered by the quantization config and never reached `UnquantizedLinearMethod`. Weighting all thirteen by layer count is how an earlier estimate came out a factor of two high.
- No end-to-end serving numbers on sm_120: Qwen3.8-Flash-Next does not fit in the 32 GB of the RTX 5090 used for the sweep, which needs an RTX PRO 6000. The sweep itself is unaffected, since it measures kernels on synthetic tensors and never instantiates the model.
- The kernel refuses M > 16, so the verification GEMM leaves the tuned range above batch size 8 at k=1 and above 4 at k=3. The gain is a low-batch latency effect by construction, not a throughput one.
