# [MoE] Add locality-domain allocation for FlashInfer CuTeDSL NVFP4

[Upstream PR](https://github.com/vllm-project/vllm/pull/61685) · state: closed · merged: True

## Original PR description



## Overview

Add opt-in locality-domain weight allocation and MoE execution on Rubin, using upstream PyTorch locality APIs and FlashInfer CuTeDSL. Requires the stream-execution compatibility fix in [FlashInfer #6488](https://github.com/flashinfer-ai/flashinfer/pull/6488).

## Claims

- Support locality-domain allocation and localized MoE execution.
- Support optional backfill, overlapping output memset, and releasing full-width weights.
- Use CUDA graph autotuning consistently for localized and baseline execution.

## Validation

### MoE op performance

Measured on Rubin with NVFP4 inputs/weights, BF16 output, SiTU activation, and balanced routing. Both paths independently autotune with CUDA graph profiling—no manually fixed tactics. Timing covers **FC1 + memset + FC2**, excluding routing and input preparation.

Per-rank shapes (hidden / intermediate / experts / top-k):

- **TP8-shaped:** 3584 / 384 / 896 / 16; no backfill.
- **TEP16-shaped:** 3584 / 3072 / 56 / 16; backfill enabled.

## Details

Enable with `VLLM_USE_LOCALITY_DOMAINS=1` and `--moe-backend flashinfer_cutedsl`. Requires compatible PyTorch, CUDA, and FlashInfer builds. Optional controls:

- `VLLM_MOE_LOCALIZE_BACKFILL=1`: enable backfill.
- `VLLM_MOE_LOCALIZE_FREE_FULL_WEIGHTS=1`: release original weights and restrict tuning to localized execution.
- `VLLM_MOE_LOCALIZE_MEMSET_OVERLAP`: enabled by default.

Localization is disabled by default; localized per-token activation quantization is unsupported.

Also includes K3 KDA compatibility adjustments for Triton nightly: remove `B` from `do_not_specialize` because it is not a kernel argument in the NVIDIA/AMD implementations, and align gated normalization with [upstream FLA #1062](https://github.com/fla-org/flash-linear-attention/pull/1062), preserving K3's head-aware, row-strided gate addressing. The block-pointer migration is already in vLLM main; the remaining gated-norm diff only aligns the gate-load expression/mask and records upstream provenance. AMD runtime validation remains pending.
