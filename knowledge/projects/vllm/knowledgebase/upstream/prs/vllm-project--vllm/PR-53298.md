# [Bugfix][KV Connector] Restore state after KV load rejection

[Upstream PR](https://github.com/vllm-project/vllm/pull/53298) · state: open · merged: False

## Original PR description

## Purpose

Fixes #49250.

When a synchronous external KV load is rejected under
`kv_load_failure_policy="recompute"`, scheduler state is rewound but Model
Runner V2 can retain state written by discarded in-flight frames. With
overlapping batches, the stale state can affect later decoding. The result does
not match full recomputation.

This change:

- marks the exact in-flight token positions stale and clears speculative and
  placeholder state when a failed load is recomputed;
- derives the safe shared-prefix offset from all active optimistic frames while
  excluding output that was already marked stale;
- serializes repair of physically shared KV blocks: dependent requests wait for
  worker-confirmed owner progress (or a safely ordered Model Runner V2
  same-frame repair), invalid blocks are quarantined from new prefix-cache
  users, and unfinished repair ownership transfers on cancellation/preemption;
- propagates an explicit `rewound_req_ids` marker with cached-request data;
- applies the scheduler's absolute computed-token offset to Model Runner V2
  only for those explicit rollbacks;
- restores device-side token history, sequence length, last sampled token, and
  output penalty counts to the scheduler's accepted output prefix;
- clears speculative draft/lookahead state and resets sampled-history caches;
- restores Mamba hybrid acceptance and align-copy state from the same absolute
  scheduler position; and
- adds focused scheduler and worker regression tests, including a multi-token
  speculative async frame and emulated rank-local/PP ordering.

There is no connector-specific special case.

This is materially different from #49252. That PR's scheduler fix derives a
frame count from `num_output_placeholders - 1` and explicitly scopes out
speculative decoding and diffusion. This change uses the existing exact
`num_in_flight_tokens` accounting and an explicit CPU-to-GPU rewind signal; it
was validated with EAGLE3. The difference was documented on #49250 before this
PR was opened.

GPU negative-control protocol:

1. Run greedy decoding without a KV connector and record token IDs.
2. Use a connector that promises a block-aligned synchronous load and rejects
   it before copying KV.
3. Compare clean-base and patched output against the no-connector baseline for
   sync, async, and async EAGLE3 scheduling.
4. Repeat with real `LMCacheConnectorV1`, injecting a one-shot failure in a
   16-token retrieval before KV is copied.

The Codex-review follow-ups add direct device-state controls. One simulates two
discarded sampled tokens and compares exact old head `b688039af0` with the
patched worker. The other restores Mamba align state at absolute offsets 0, 8,
and 9 while preserving unrelated request slots.

The Qwen follow-up compares rejected requests against connector-free full
recomputation and unaffected requests against successful reuse, while checking
state and ordering invariants separately. Different execution shapes can

unaffected requests matched successful reuse. This also corrected the earlier
interpretation of an `819f20e19f` whole-file mismatch; that mismatch compared
different valid execution paths rather than showing recovery corruption.

Full all-request byte equality can still vary at BF16
ties/near-ties when the execution shape changes. Exact logit traces and an
unrelated-request control separate that numerical sensitivity from the
owner/dependent scheduling invariant fixed here.

First, `819f20e` had a real shared-prefix recovery bug. One affected peer had

prefix-cache reuse for all four requests in both cold repetitions, while the
rejected path matched full recomputation. So the existing `run.sh` can still
fail even when recovery is correct: its final `cmp` uses successful external
reuse as the recovery oracle. The appropriate oracle here is connector-free
recomputation at the same decode configuration. I have documented that
distinction in the PR description; the example/connector cleanup is separate
follow-up work.

Your precompiled-wheel caveat does not invalidate this comparison: this PR's
delta is Python-only, and you verified the loaded source in each arm.

When a rejected KV-load frame reaches the end of prefill and samples a token, `_post_update_kernel` has already incremented `total_len`, written `all_token_ids` and `last_sampled_tokens`, and updated `output_bin_counts`; overlapping async frames can add more such state. This branch restores only `num_computed_tokens`, even though the scheduler now discards those sampled tokens. The recovery token is consequently appended after the stale tokens, so subsequent decoding and sampling penalties use the wrong history. Rebuild or roll back all sampled-token state for rewound requests, not just the computed-token offset.
