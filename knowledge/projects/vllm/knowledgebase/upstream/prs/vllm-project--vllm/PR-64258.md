# [ROCm][Perf][GLM-5.3-Flash] MonoKernel: fetch the shared expert's up/gate weights before the top-8 (on #64245)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64258) · state: open · merged: False

## Original PR description

## Overview

In the MonoKernel's expert up/gate stage, half of the 256 CTAs also compute one 8-column chunk of the shared expert. Those CTAs ran up/gate about 2 µs longer than the rest, and the slowest of them set when the down stage could start. The shared expert needs no routing, yet its weights were fetched only after the top-8 selection. This PR issues those weight loads before the routing wait, so the bytes stream while the CTA would otherwise sit idle in the top-8. The units, the MFMA order and the reduction are unchanged, so outputs are bit-identical.

**Stacked on #64245** (and through it on #64225 and #61662), which has not landed, so the diff against main includes them. This PR's own change is the last commit, `dc17d297ba` (`mono/ffn/kernel.py` only): [compare against #64245](https://github.com/amd-dlimpus/vllm/compare/aff9dc4a91...dc17d297ba). `dc17d297ba` has the same tree as `acc8087d86`, which the numbers below were measured on; only a missing Signed-off-by was added.

**Independent of the KV cache dtype**: the change is in the MoE stage, after attention.

## The change

`ug8_units` moves out of the round loop and takes its 8-column chunk explicitly. Each CTA's shared-expert units, always in its first round, are issued right at the start of the stage, before `dn_route`. A unit only loads weights when it is built; it reads the activations from LDS later, in `mma_units`. So the early loads need nothing from the routing or the activation staging. Round 0 then uses the already-loaded registers.

## Why it helps

From a traced width-4 launch (TP2, FP8 KV), up/gate busy time per CTA:

| CTAs | p50 | max |
| --- | --- | --- |
| also running a shared-expert chunk (128) | 24.3 µs | 26.8 µs |
| routed slots only (128) | 22.2 µs | 23.7 µs |

## Accuracy

Bit-identical. The kernel dump (seeded weights and inputs, an FFN launch and a KDA launch, TP2, widths 2 and 4, both ranks) matches #64225's head bit for bit, and #64245 is bit-identical to #64225 by the same check. It also matches #64245's head directly, at TP2 (widths 2 and 4, both ranks) and at TP4 (widths 2, 4 and 8, all four ranks).

## Tests

- Kernel bit-identity as above.
- Compile-checked at TP2 (widths 2 and 4) and TP4 (widths 4 and 8).
- MonoKernel GPU tests at TP4 on dc17d297ba (`pytest tests/kernels/models/amd/glm5next_mono`): 67 passed, 5 skipped. The 5 skips are TP8 cases.
- Registers (gfx950 ISA, untraced sparse-attention launch): the early shared-expert loads stay live across the routing wait, so the PR raises VGPRs. All 256 CTAs must be co-resident, and they still are.

| Launch | #64245 | This PR |
| --- | --- | --- |
| TP2, width 4: VGPRs / VGPR spills / scratch | 225 / 0 / 0 B | 229 / 0 / 0 B |
| TP4, width 8: VGPRs / VGPR spills / scratch | 256 / 12 / 52 B | 256 / 12 / 52 B |

  The TP4 width-8 spills are already there on #64245, and this PR doesn't add any. TP2 width 8 isn't built, because the runtime caps TP2 steps at 4 rows.
