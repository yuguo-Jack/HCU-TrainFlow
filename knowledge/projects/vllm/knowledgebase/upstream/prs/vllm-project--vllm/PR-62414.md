# [Bugfix][KV Offload] Count reused key residencies

[Upstream PR](https://github.com/vllm-project/vllm/pull/62414) · state: open · merged: False

## Overview

Fix KV offload event metadata loss when one `OffloadKey` is evicted and
stored again before the asynchronous primary-tier store event is translated.
This PR is based on `main` and is independent of #59855.

## Claims

- Preserve the complete payload for every queued or in-flight event mentioning
  a reused key.
- Prevent a valid delayed `BlockStored` from degrading to a `block_size=0`
  placeholder.
- Keep primary CPU, secondary storage, and owned secondary residencies
  independent without changing the event wire schema.

## Details

### Failing case before this change

The same content-addressed key can be reused after the cache policy evicts it.
The old tracker modeled primary residency as a set, so the old and new
lifecycles shared one `(CPU, None)` entry:

```text
step t:     K is resident; its complete metadata is tracked
step t:     eviction queues BlockRemoved(K)
step t:     a later allocation records a new store for K
step t+k:   async transfer completes and queues BlockStored(K)
```

When `BlockRemoved(K)` was translated, it removed the only CPU residency and
the tracker discarded the payload. The later store then produced:

```text
BlockStored(
    block_hashes=[tail_hash],
    token_ids=[],
    block_size=0,
)
```

The cache contained the newly stored block, but the external KV event stream
reported a placeholder and lost the block's token and hash composition.

### Root cause

The policy and manager queue preserve two lifecycle transitions, while the
tracker kept one metadata object and one residency token per key. A removal
could therefore consume the token belonging to a store that was still in
flight. This is a tracker accounting bug; it does not require changing
`OffloadingEvent` or the public KV event schema.

### Fix

The tracker keeps one payload snapshot per key and counts outstanding
residencies by `(medium, ownership)`:

```text
record_store(K)       CPU count += 1
BlockRemoved(K)       CPU count -= 1
final BlockRemoved(K) CPU count reaches 0, metadata is released
```

Secondary stores with `removal_expected=True` increment their own residency
count. Their removals decrement only that count, so a secondary event cannot
consume the primary store's lifetime. Metadata is released when all residency
counts are exhausted.

The regression covers both same-batch and delayed-drain ordering. In both
cases the old removal and delayed store now carry the complete payload, and a
later final removal releases the metadata. Partial-tail lookup/store handling,
secondary residency, unmatched removals, reset cleanup, and the CPU manager
suite remain covered.

This is separate from [#52103](https://github.com/vllm-project/vllm/pull/52103),
which changes event provenance and chunk-key semantics. This PR keeps those
interfaces unchanged and fixes the existing tracker lifecycle accounting.
