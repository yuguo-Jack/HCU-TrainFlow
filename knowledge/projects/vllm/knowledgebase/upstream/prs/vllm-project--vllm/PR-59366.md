# [Spec Decode][Qwen4Exp] Run GDN RecoverSSM verify in the fused CUDA MTP kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/59366) · state: open · merged: False

## Original PR description

> **Stacked on vllm-project/vllm#58863 (head `7f7b3295fe`, which includes our fixes from jschmied/vllm#2, its FULL-graph builders and the forward commit). Only the last two commits, "Run GDN RecoverSSM verify in the fused CUDA MTP kernel" and "Record exp(g) in the fused GDN RecoverSSM replay", are new.** I'll rebase this PR onto main once #58863 lands. Draft until then.

## Purpose

`--use-replayssm` on Qwen4Exp (#58863) forces `gdn_decode_kernel = "triton"`. Pure spec-decode batches then lose vLLM's fused CUDA MTP kernel, `fused_gdn_decode_post_conv_mtp`, which does the recurrence, the gated RMSNorm and the output gate in one launch. They run the Triton RecoverSSM verify followed by a separate norm instead.

This PR adds a replay mode to that CUDA kernel, exposed as `fused_gdn_decode_post_conv_mtp_replay`. RecoverSSM spec-decode batches keep the fused kernel:
- Each window starts from its checkpoint in `state_indices[:, 0]`. The kernel only reads it.
- Instead of a recurrent state per window position, the kernel writes that position's replay record `[correction (V), normalized key (K), decay exp(g) (1)]`. It uses the same fp32 `[slot, HV, spec_query_len, V + K + 1]` layout the Triton verify writes, so the existing commit replays it unchanged.
- The math, the output, the norm and the gate are the same code path as the snapshot mode, and the outputs are bit-identical to it.
- CUDA graph padding rows (null slot or zero-length window) write nothing.
- `state_indices` rows may be strided, because the RecoverSSM builder passes the checkpoint column of the `[N, 1 + num_spec]` spec indices. The snapshot mode now also accepts strided rows.

`QwenGatedDeltaNetAttention` keeps the CUDA decode kernel under RecoverSSM. Pure spec-decode batches run the conv update from the checkpoint column and then the replay kernel. Batches with prefills keep the Triton verify. If the op is not built, the layer falls back to Triton as before.

With the FULL-graph builders #58863 now carries, it runs inside FULL decode graphs; under PIECEWISE it runs as an eager break.

## Test Plan

`tests/kernels/mamba/test_recoverssm_gdn_fused.py` (new) checks the replay mode against three references:
- Outputs are bit-identical to the native snapshot mode, including with strided `state_indices` and BF16 or FP32 state, at HV/H of 1 and 3.
- Replay records match the Triton RecoverSSM verify.
- The commit after a replay reproduces the native fused kernel's states bit for bit (`torch.equal`): the kernel's update (`h *= decay`, then `h += k * delta` as one FMA) is the commit's `fma(c, k, h * decay)` on the recorded floats.
- Checkpoints are untouched, and the state after commit matches the native per-token states for 1 to 4 accepted tokens.

It also checks that graph-padding rows and null slots are skipped and that malformed shapes are rejected.

## Test Result

On RTX PRO 6000 (SM120) and H200 (SM90), this branch passes `test_recoverssm_gdn_fused.py`, `test_recoverssm_gdn.py`, `test_recoverssm_ple.py`, `tests/config/test_recoverssm_config.py` and `test_gdn_fused_mtp.py`: 128 passed on each.

End to end, on Qwen3.8-Flash-Next NVFP4 with MTP3 (probabilistic drafts) and align-mode prefix caching, on the V2 runner. The results are also in #58863 ([comment](https://github.com/vllm-project/vllm/pull/58863#issuecomment-5903790894)).
