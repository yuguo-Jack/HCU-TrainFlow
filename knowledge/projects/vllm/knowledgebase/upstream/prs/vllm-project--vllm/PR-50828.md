## Original PR description

## Summary

Completes the remaining source-level documentation items (1-3) of #41230: explain what the NIXL \`KV Transfer metrics\` log line and the NIXL Prometheus metrics mean, with a focus on the multi-rank (TP > 1) aggregation semantics that previously caused user confusion.

Covers:

- \`NixlKVConnectorStats\` - per-interval telemetry container: what each \`data\` key holds, its units, and the pooling (never per-rank averaging) semantics of \`aggregate\`.
- \`record_transfer\` - per-transfer telemetry from NIXL: \`xferDuration\` (end-to-end, posting + data movement) and \`postDuration\` (time to submit the transfer to the RDMA backend), both converted from microseconds to seconds; bytes and descriptor counts stored as-is.
- \`clone_and_reset\` / \`is_empty\` / \`num_successful_transfers\` - the snapshot-and-reset contract, and why failure-only intervals are intentionally kept so they still reach the logger and Prometheus.
- \`reduce\` - definitions of every field in the log line: mean/P90 durations in ms, MiB conversion (bytes / 2**20), aggregate throughput (total MiB / sum of transfer durations, not wall-clock), descriptor mean, and the all-zeros path when no transfer succeeded.
- \`NixlPromMetrics.observe\` - histogram vs counter recording per engine.
- \`KVConnectorLogging.observe\` / \`log\` - the scheduler-sync vs logging-interval distinction and the accumulator lifecycle.

## Why this is not duplicating an existing PR

- #44055 (merged) covered item 4 only - the user-facing docs page (\`docs/features/nixl_connector_usage.md\`); its changed files were limited to that page. Maintainer markmc confirmed items 1-3 (source-level documentation in \`stats.py\` / \`metrics.py\`) remain open (2026-06-12).
- No open PR touches these two files for documentation purposes. Commenters on #41230 (ammmanism, kritikagarg, dhariskhan1275) expressed interest, but no PR had been opened for items 1-3.

- n-dlms · comment · 2026-10-09T12:59:10Z · [source](https://github.com/vllm-project/vllm/pull/50828#discussion_r4230339556)

File: `vllm/distributed/kv_transfer/kv_connector/v1/nixl/stats.py` · line None

Verified against the code and by running it, and the answer is now documented in the reduce docstring: successes and failures are recorded independently, so partial failures leave the timing and throughput stats defined over the successful transfers only, while the grouped failure counts ride the same log line. Concretely, an interval with 2 successes, 1 failed transfer, 1 failed handshake and 1 KV-expiry logs Num successful transfers=2 with its timing stats plus Num failed transfers=2 (transfers plus handshakes plus notification failures grouped as sporadic transport events) and Num KV expired reqs=1. An interval with only failures is not empty (is_empty returns False) and logs zero timing stats alongside its non-zero failure counts, so nothing is silently dropped. record_transfer also ignores None telemetry, so a completion without telemetry counts as neither a success nor a failure. One correction to my original docstrings, which predate this: they claimed failures were surfaced through Prometheus only, while reduce has since evolved to include the counts directly in the log line. The updated docstrings in this PR now describe the current behavior.
