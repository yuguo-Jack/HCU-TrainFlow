# [Bugfix][Audio] Honor VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=0 as documented

[Upstream PR](https://github.com/vllm-project/vllm/pull/61173) · state: open · merged: False

## Original PR description



## Overview

Fixes #61170. `docs/usage/security.md` states that setting any listed media limit to `0` disables it, but `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=0` enforced a 0-byte cap instead, rejecting every non-empty audio input. This PR makes `0` disable the compressed-audio filesize check on all four enforcement paths of that limit.

## Claims

- Setting `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=0` now disables the compressed-audio filesize check, as documented in `docs/usage/security.md`. Inputs reach the decoder instead of being rejected with "Maximum file size exceeded".
- Positive limits behave exactly as before; unset keeps the 25 MB default.
- With the audio-specific limit disabled, remote fetches still fall back to the global `VLLM_MAX_MEDIA_DOWNLOAD_SIZE_MB` cap in `vllm.connections`, and the decode-stage limits (`VLLM_MAX_AUDIO_DECODE_DURATION_S`, `VLLM_MAX_AUDIO_DECODE_BYTES`) are untouched.

## Details

**Root cause.** The four enforcement sites computed `int(env * MiB_bytes)`, so `0` produced a 0-byte cap and every comparison `size > 0` rejected non-empty input.

**Implementation.** When the configured value is `<= 0`, the limit getters return `None` (matching the `MediaIO.get_max_bytes() -> int | None` contract; the base implementation already returns `None`) and each check site skips enforcement:
- `vllm/multimodal/media/audio.py`: `AudioMediaIO.get_max_bytes()` returns `None`; `_validate_encoded_size` and `load_base64` skip when `None`. This covers chat multimodal URLs, data: URLs, and local file paths (all flow through `load_bytes`/`load_base64`/`load_file`).
- `vllm/entrypoints/launchers/run_batch.py`: `_get_audio_download_limit_bytes()` returns `None`; the data-URL check is skipped and `None` is passed through to `async_get_bytes`, which accepts `int | None`.
- `vllm/entrypoints/speech_to_text/base/utils.py`: `read_upload_with_limit` skips both the Content-Length pre-check and the chunked-read check when disabled.
- `vllm/entrypoints/speech_to_text/realtime/connection.py`: the per-append check is skipped when disabled.

This follows the existing repo precedent (`vllm/utils/sparse_utils.py`: `if max_bytes > 0:` — only positive values enforce). The change is opt-in only via the documented `0` setting; there is no behavior change for unset or positive values.

**Tradeoffs.** Disabling the check is explicitly documented as not recommended for untrusted deployments. Defense in depth is retained: HTTP(S) fetches still enforce the global media download cap, and the duration/decoded-bytes guards still bound decode memory.

**Not duplicating an existing PR.** Checked before opening: the issue timeline has no cross-referenced PRs, `gh pr list --search "61170 in:body"` returns nothing, and the only open PRs mentioning this env var (#48130, #47664) are unrelated features.

**Model evaluation.** Not applicable: this change touches no model code, no output/accuracy logic, and no serving-path behavior at default configuration. The only behavior change occurs when an operator explicitly sets the documented disable value.
