- MinhaoLi0318 · COMMENTED · 2026-10-24T13:42:18Z · [source](https://github.com/vllm-project/vllm/pull/57905#pullrequestreview-5638450061)

I read this at `551d268` and ran the two changed worker files on a Mac (PyTorch MPS backend, single rank). Making the `_all_ranks_result_ready` collective unconditional (`eplb_state.py:659`) matches direction 3 in #57883. The two 60 s timeouts follow direction 1, but as written they end the worker thread instead of failing loudly, and they break async EPLB during normal operation.

**1. `rearrange_event.wait(timeout=60.0)` kills the worker whenever no rearrangement starts within 60 s** ([async_worker.py#L82](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/async_worker.py#L82))

- `rearrange_event` is recorded only in `rearrange()` ([eplb_state.py#L948-L950](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L948-L950)). `step()` calls `rearrange()` once every `step_interval` steps ([#L666-L677](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L666-L677)), 3000 by default ([config/parallel.py#L67](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/config/parallel.py#L67)). When the engine has no requests, `step()` is not called at all ([core.py#L2273-L2276](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/v1/engine/core.py#L2273-L2276)).
- On timeout, `CpuGpuEvent.wait` raises `TimeoutError` ([eplb_utils.py#L58-L59](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_utils.py#L58-L59)). `thread_target` catches it, logs once and returns ([async_worker.py#L34-L41](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/async_worker.py#L34-L41)). Nothing restarts the thread: `start_async_loop()` only creates a worker when `self.async_worker is None` ([eplb_state.py#L960-L964](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L960-L964)), and the dead `Thread` object stays assigned. So its callers (`load_model()` in both model runners, and the Elastic EP reshuffle at [elastic_execute.py#L568](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/elastic_ep/elastic_execute.py#L568)) never start a new one.
- The next `rearrange()` sets `rebalanced = True` ([eplb_state.py#L947](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L947)), but no worker publishes a result. `_all_ranks_result_ready` then stays `False` ([#L1029](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L1029)), and `step()` takes the bail-out at [#L666-L675](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L666-L675) from then on. "steps until the next rearrangement" goes negative, which is the symptom reported in #57883.
- `drain_async()` then spins forever as well ([eplb_state.py#L989-L999](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L989-L999)), so an Elastic EP scale-up or scale-down after that point would hang ([elastic_execute.py#L365](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/elastic_ep/elastic_execute.py#L365), [#L608](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/elastic_ep/elastic_execute.py#L608)); I only read this path.
- This can also happen under steady traffic. Between cycles the worker waits about `step_interval - num_moe_layers` steps, so with the default interval it times out whenever the mean step time is above roughly 60 s / 3000 = 20 ms. The first wait starts in `load_model()`, and the first `rearrange()` comes 750 counted steps later (the counter starts at 3/4 of the interval, [#L459-L463](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L459-L463)).

Repro: I loaded `async_worker.py` and `eplb_utils.py` from `551d268` unmodified, with single-rank stubs for the process groups and a no-op `transfer_layer`, plus a `torch.Stream` subclass whose `synchronize()` does a device-wide sync, since MPS has no per-stream sync. I started the worker and recorded nothing for 62 s. The thread exited with `async loop error (Rank 0): CpuGpuEvent.wait() timed out`, and a `rearrange_event.record()` after that was never consumed. With the same two files from main (`5f63ea461`; its `async_worker.py` also has migration batching, which was off in this run), the thread was still alive after 62 s and consumed the event. I did not run this on CUDA GPUs or with more than one rank.

**2. `consumed_event.wait(timeout=60.0)` fails the same way mid-cycle, and it does not make the #57883 stall visible to the engine** ([async_worker.py#L160](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/async_worker.py#L160))

- If traffic stops after a layer result is published, the main thread does not step and the worker exits after 60 s. In the same harness, layer 0 was published and not consumed for 62 s, and the worker exited. After the main thread then consumed layer 0, layer 1 was never published. With main's files, layer 1 was published.
- In the #57883 stall itself, the timeout turns a blocked worker into a dead one plus one log line on that rank. `rebalanced` stays `True`, so EPLB stays stuck as before and `/health` does not change.
- Suggestion: keep both waits unbounded on the worker side. For `consumed_event`, wait in a loop and log on each timeout instead of raising, e.g. `while not self._recorded.wait(timeout): logger.warning(...)` with rank, `layer_idx` and elapsed time. `rearrange_event` needs no timeout, since a long wait there is normal. To fail loudly, check on the main thread: in `step()`, raise if `rebalanced` is set and `self.async_worker` is not alive, and warn when the bail-out at L666-L675 has been taken for more than N consecutive steps. A step count does not fire while the engine is idle.

**3. The unconditional collective now runs on every forward step** ([eplb_state.py#L656-L664](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L656-L664))

- On main it runs only while `rebalanced` is set, at least `num_moe_layers` steps (one layer is consumed per step) out of every `step_interval`. With this change every step, real or dummy, does a blocking all_reduce on the EP CPU group ([#L1031-L1035](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L1031-L1035)), cross-node in the EP16 setup from the issue. TPOT at low concurrency before and after this change would show whether that cost matters.
- One way to keep call counts equal without the per-step cost: gate on a main-thread-only "cycle in flight" flag, set in `rearrange()` (same step on every rank) and cleared only from the collective's own result, instead of on `rebalanced`, which the worker thread also writes ([async_worker.py#L126](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/async_worker.py#L126)).
- The gate before `rearrange()` at [#L666-L670](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L666-L670) still reads the local `rebalanced`, and `rearrange()` runs `_allreduce_list` ([#L801](https://github.com/vllm-project/vllm/blob/551d2680741d8a07746d11ce0cecfd8a6069638f/vllm/distributed/eplb/eplb_state.py#L801)). If `rebalanced` can still differ across ranks at that point, that call can mismatch in the same way. A test that clears `rebalanced` on one rank only would show whether that path hangs.

**4. No tests.** Three that would pin this down:

- With no `rearrange()` for longer than the wait timeout, the worker is still alive and consumes a later `rearrange_event.record()`. If the timeout becomes a module constant, the test can set it to 0.1 s.
- Same, with a published layer result that is not consumed for longer than the timeout.
- The stall warning or error from point 2 fires after N bail-out steps.

- ilmarkov · comment · 2026-11-02T11:22:13Z · [source](https://github.com/vllm-project/vllm/pull/57905#issuecomment-6575885567)

Thanks for revising this. I’m not yet convinced `cycle_in_flight` addresses #57883. The report shows that workers on several ranks published results and waited for consumption, but it does not show every rank’s rebalanced and `pending_result` state, or establish that ranks disagreed about entering `_all_ranks_result_ready()`. Could you provide a per-rank trace or a multi-rank reproduction of that specific failure?

The new flag mostly follows rebalanced, so it adds a second lifecycle that must stay synchronized. In the proposed recovery case, a rank with `rebalanced=False` can clear `cycle_in_flight` locally while a peer consumes a non-final result and remains in flight. 

What ensures both ranks participate in the next readiness collective? I’d like a multi-rank regression test covering that transition. The added event-wait test does not exercise the changed EPLB state logic.
Until we establish the cause of the reported stall and test the corresponding transition, I’m hesitant to consider this a fix for #57883.
