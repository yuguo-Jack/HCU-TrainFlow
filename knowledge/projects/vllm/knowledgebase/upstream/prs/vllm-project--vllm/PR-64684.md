# [Security] Bound Ovis2.5 processed media allocations

[Upstream PR](https://github.com/vllm-project/vllm/pull/64684) · state: open · merged: False

## Original PR description

## Overview

Bound Ovis2.5's aggregate processed image/video tensor bytes before resizing. Tiny source images can otherwise expand into gigabytes of retained float32 tensors before prompt-length validation.

## Claims

- Share one processed-media budget across images and videos in each processor call, using `VLLM_MAX_MEDIA_REQUEST_DECODE_BYTES`.
- Account for resized RGB float32 pixels and temporal padding before image preprocessing; direct preprocessing calls also enforce the limit.
- Keep the existing tensor values, shapes, placeholders, and grids for accepted inputs.

## Details

The media loader's source-pixel accounting does not measure the larger tensors produced by Ovis2.5's minimum-size upscaling. This change uses the existing `MediaDecodedBudget` for a separate processor-output bound and charges the padded output geometry before resizing. The counter is local to a processor call, rather than stored on the shared processor instance. The existing zero-disables-limit behavior is preserved. Operators processing unusually large legitimate inputs, including profiling/offline calls, may need to raise this limit.

Codepath coverage: the control is in the processor shared by Python online rendering (chat, batch chat, Responses, Messages, tokenization/render and SageMaker delegation), offline processing, and direct processor calls. Both image and video branches share the same counter. Rust and precomputed-feature paths do not call this processor. Existing request-error handling maps `ValueError` to a client error.

Duplicate-work check: searched open/draft and merged PRs by processor filename, `preprocess_multidata`, Ovis memory, and processor budgets, and read the relevant diffs. #61226 bounds source-media decoding and #58830 gates request kwargs; neither bounds default processor expansion. #62777 and #33826 concern encoder compilation/graphs; #47876 concerns token estimates; #52623 concerns special tokens; #53610 changes processor plumbing; #57076 checks expanded prompt length afterward. #63291, #63822, and #64495 concern scheduling/caches, while #64682 affects Rust decoded-image copies.
