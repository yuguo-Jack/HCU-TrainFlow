# [Perf][MoE] Add H100 FP8 fused MoE config for GLM-4.5/4.6/4.7 TP8

[Upstream PR](https://github.com/vllm-project/vllm/pull/63883) · state: open · merged: False

## Original PR description

## Overview

GLM-4.5, GLM-4.6 and GLM-4.7 FP8 (160 routed experts, `moe_intermediate_size=1536`) at TP8 look up the fused MoE config `E=160,N=192,device_name=NVIDIA_H100_80GB_HBM3,dtype=fp8_w8a8.json`. vLLM ships this key for H200, B300 and MI350 but not for H100, so on H100 the Triton fused MoE uses the default config for every layer. This PR adds a tuned H100 file for that key. It contains only the config file.

## Claims

- **Fused MoE kernel, 1xH100, per-token activation / per-channel weight FP8:** this is the quantization scheme of the public `zai-org/GLM-4.x-FP8` compressed-tensors checkpoints, and the file applies when the Triton MoE backend is selected. The tuned file is 6-11% faster at 16-128 tokens, 14-18% at 256-512 and 25-36% at 1024-4096, and within ±1% at 1-4 tokens.
- **GLM-4.7-FP8, TP8 on 8xH100, `--moe-backend triton`, mean of 3 server launches per arm:**
  - Concurrency 256: output throughput +12.9%, mean TPOT -11.4%, p99 TTFT -14%.
  - Concurrency 16-64: output throughput +2.4-2.9%, mean TPOT -2.3-2.5%.
  - Concurrency 1: unchanged.
- **Correctness:** at all 18 batch sizes in the file, the kernel output was bit-identical to the default config's. gsm8k accuracy stays within the run-to-run spread.
- **Tradeoffs:**
  - **First-pass TTFT tail:** on the first benchmark pass of each server, p99 TTFT at concurrency 16 and 64 is worse with this file. On a second pass on the same server (one launch per arm) it is 28% and 17% better (see Validation).
  - **Per-tensor FP8:** per-tensor checkpoints read the same file name, and their kernels get 2-3.5% slower at 1536, 2048 and 4096 tokens.

## Validation

**Setup:** 8x H100 80GB HBM3 (SXM), driver 580.159.04, running the post-merge image of `af6665b5` (vLLM 0.32.1rc1.dev565, torch 2.14.0+cu130, Triton 3.8.0). All commands below ran inside that image.

**Tuning:** I used the stock `benchmarks/kernels/benchmark_moe.py` from that commit without changes, with the default search space and batch sizes (1-4096, the same keys as the existing H200 file). Since #62763, the script prints `Benchmarking per-token activation and per-channel weight FP8.` for this checkpoint and tunes that kernel variant. Tuning took 51 min on 8 GPUs.

```bash
VLLM_MOE_TUNE_CACHE_CLEAR_INTERVAL=0 python3 benchmarks/kernels/benchmark_moe.py \
  --model zai-org/GLM-4.7-FP8 --tp-size 8 --dtype fp8_w8a8 --tune
```

The tuner and this A/B route with random gating logits through plain top-k, not GLM's grouped sigmoid routing with correction bias. Real routing is more skewed. The end-to-end numbers below use the real weights and router.

### Kernel correctness

- **Setup:** GLM-4.x TP8 shape (`E=160, N=192, K=5120`, top-8, per-token FP8), all 18 keys in the file. Each config is applied with `override_config`.
- **Reference:** the native per-column implementation from `tests/kernels/moe/test_triton_moe_ptpc_fp8.py`.
- **Result:**
  - Mean relative error was 1.2-1.8% with both configs; the test's threshold is 5%.
  - The tuned and default outputs were bit-identical (`torch.equal`) at every M. Both configs use `BLOCK_SIZE_K=128` at every key.
  - The check asserts both error bounds and equality, and it printed `PASS`. The script is in the collapsed block below; run it from the repo root as `python3 check_ptpc.py 'vllm/model_executor/layers/fused_moe/configs/E=160,N=192,device_name=NVIDIA_H100_80GB_HBM3,dtype=fp8_w8a8.json'`.

```python
# Compare fused MoE output (per-token act / per-channel weight FP8) with the default
# config and the tuned config against a native torch reference at the GLM-4.x TP8 shape.
import json
import sys

import torch

from vllm import _custom_ops as ops
from vllm.config import VllmConfig, set_current_vllm_config
from vllm.model_executor.layers.activation import SiluAndMul
from vllm.model_executor.layers.fused_moe import fused_experts, fused_topk, override_config
from vllm.model_executor.layers.fused_moe.config import fp8_w8a8_moe_quant_config
from vllm.model_executor.layers.fused_moe.fused_moe import get_default_config

E, N, K, TOPK = 160, 192, 5120, 8
tuned = {int(k): v for k, v in json.load(open(sys.argv[1])).items() if k != "triton_version"}


def mm(A, B, As, Bs, dt):
    C = torch.matmul(A.float(), B.float().t())
    return (As * C * Bs.view(1, -1)).to(dt)


def mask8(a, m):
    return a.view(torch.int8)[m].view(a.dtype)


def ref(a, w1, w2, w1_s, w2_s, tw, ti):
    B, D = a.shape
    a_q, a_s = ops.scaled_fp8_quant(a, use_per_token_if_dynamic=True)
    a_q = a_q.view(B, -1, D).repeat(1, TOPK, 1).reshape(-1, D)
    a_s = a_s.view(B, -1, 1).repeat(1, TOPK, 1).reshape(-1, 1)
    out = torch.zeros(B * TOPK, K, dtype=a.dtype)
    ti = ti.view(-1)
    for i in range(E):
        m = ti == i
        if m.sum():
            h = SiluAndMul().forward_native(mm(mask8(a_q, m), w1[i], mask8(a_s, m), w1_s[i], a.dtype))
            hq, hs = ops.scaled_fp8_quant(h, use_per_token_if_dynamic=True)
            out[m] = mm(hq, w2[i], hs, w2_s[i], a.dtype)
    return (out.view(B, -1, K) * tw.view(B, -1, 1).to(out.dtype)).sum(dim=1)


@torch.inference_mode()
def main():
    torch.set_default_device("cuda")
    torch.manual_seed(0)
    f8 = torch.finfo(torch.float8_e4m3fn)
    w1 = (((torch.rand(E, 2 * N, K) - 0.5) * 2) * f8.max).clamp(f8.min, f8.max).to(torch.float8_e4m3fn)
    w2 = (((torch.rand(E, K, N) - 0.5) * 2) * f8.max).clamp(f8.min, f8.max).to(torch.float8_e4m3fn)
    w1_s = torch.rand(E, 2 * N, 1) * 1e-2
    w2_s = torch.rand(E, K, 1) * 1e-2
    qc = fp8_w8a8_moe_quant_config(per_act_token_quant=True, w1_scale=w1_s, w2_scale=w2_s, block_shape=None)
    rows = []
    with set_current_vllm_config(VllmConfig()):
        for M in sorted(tuned):
            a = torch.randn(M, K, dtype=torch.bfloat16) / 10
            score = torch.randn(M, E, dtype=torch.float32)
            tw, ti, _ = fused_topk(a, score, TOPK, True)
            r = ref(a, w1, w2, w1_s.squeeze(-1), w2_s.squeeze(-1), tw, ti)
            cfg_t = tuned[min(tuned, key=lambda x: abs(x - M))]
            cfg_d = get_default_config(M, E, N, K, TOPK, "fp8_w8a8", None)
            outs = {}
            for name, cfg in (("default", cfg_d), ("tuned", cfg_t)):
                with override_config(cfg):
                    outs[name] = fused_experts(a, w1, w2, tw, ti, quant_config=qc)
            rel = {k: (torch.mean(torch.abs(v.float() - r.float())) / torch.mean(torch.abs(r.float()))).item() for k, v in outs.items()}
            rows.append({"M": M, "rel_default": rel["default"], "rel_tuned": rel["tuned"],
                         "bitwise_equal": torch.equal(outs["default"], outs["tuned"]),
                         "max_abs_diff": (outs["default"].float() - outs["tuned"].float()).abs().max().item(),
                         "BK_default": cfg_d["BLOCK_SIZE_K"], "BK_tuned": cfg_t["BLOCK_SIZE_K"]})
            print(json.dumps(rows[-1]), flush=True)
    assert all(r["rel_tuned"] < 0.05 and r["rel_default"] < 0.05 for r in rows)
    assert all(r["bitwise_equal"] for r in rows)
    print("PASS")


main()
```

## Details

- **When this file is loaded:**
  - In the tested deployment (H100, TP8, compressed-tensors per-channel/per-token FP8, no LoRA), the FP8 MoE oracle picks `VLLM_CUTLASS` by default. The CUTLASS wrapper falls back to Triton only on SM100.
  - So this file is used with `--moe-backend triton`, as #62763 is for Beam on H200, and whenever auto selection falls through to Triton.
  - An MTP drafter on these checkpoints inherits the target's `--moe-backend` and has the same MoE shape, so it would load this file too. I did not validate MTP.
- **Default backend comparison:** one launch with the default backend in the same setup gave 74.6 / 590.4 / 1572.6 / 2787.8 output tok/s at concurrency 1 / 16 / 64 / 256.
  - That is 13-25% below Triton with this file, and 2-25% below Triton with the default config.
  - gsm8k was 0.9333 with a 76.8 s wall time.
  - This is a single launch and out of scope for a config-only PR. Backend priority on Hopper for this quant scheme may still be worth a separate look, and I can open an issue with the data if that helps.
- **Per-tensor FP8:** the per-tensor path shares this file name. I kept the configs tuned for the per-token path because the GLM-4.5/4.6/4.7 FP8 checkpoints use per-token activations.
- **What changes at large M:** the configs that win at 1024-4096 use `BLOCK_SIZE_M=64-128`, `BLOCK_SIZE_N=128` and `num_warps=4` (`GROUP_SIZE_M` 1-32). The default uses a 128×128 tile with `num_warps=8`. On the per-token path, the default config is much slower than on the per-tensor path at large M (1145.5 vs 726.8 µs at M=4096), and this file closes most of that gap. I did not run an ablation of the individual parameters.
- **E=160:** the shared expert runs separately, so the key counts only the routed experts.
- **Not covered:**
  - TP4 (`N=384`), EP (different E/N keys) and MTP speculative decoding.
  - H100 PCIe/NVL, which have different device names.
  - Serving traffic other than random 1024/256 prompts.
- **Not a duplicate:** no open PR adds `E=160,N=192` for H100. The only open H100 MoE-config PR, #63484, is for `E=128,N=192` block FP8.
