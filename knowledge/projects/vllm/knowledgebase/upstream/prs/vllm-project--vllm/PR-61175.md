# [KV Connector][Mooncake] Add DFS support to MooncakeStoreConnector

[Upstream PR](https://github.com/vllm-project/vllm/pull/61175) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Add an opt-in Mooncake DFS tier (e.g. 3FS) to `MooncakeStoreConnector`, so stored KV can live in a shared file system instead of, or in addition to, host memory. Builds on #42689.

## Claims

- `"enable_dfs": true` in the Mooncake config writes one DFS replica per object plus `replica_num` memory replicas (`kv_connector_extra_config`, default 1).
- `replica_num: 0` stores KV only in DFS (requires kvcache-ai/Mooncake#4637).
- Invalid setups (DFS with a non-default tenant or the cross-encoder cache, `replica_num` without DFS) fail at startup.

## Validation

- Mooncake store unit tests and pre-commit pass.
- 3FS on Mooncake main `d855a6ae`, Qwen2.5-0.5B-Instruct, single GPU: generate, reset the local prefix cache, generate again.

| `replica_num` | Keys with a memory replica | Store hits on 2nd request | Output tokens match |
| --- | --- | --- | --- |
| 0 | 0 / 33 | 528 / 537 | Yes |
| 1 | 33 / 33 | 528 / 537 | Yes |

## Details

- `enable_dfs` lives in the Mooncake JSON with other `setup()`-time options (`enable_offload`, `tenant_id`); `replica_num` lives in `kv_connector_extra_config` with other per-put options (`preferred_segment`). Setup steps are in the usage guide's "DFS Tier" section.
- Limitations: default tenant only; `replica_num: 0` needs an unreleased Mooncake Master; one load receive thread, since concurrent GETs share the client buffer (a warning is logged otherwise); validated on a single node in `embedded` mode and in `standalone-store` mode with `enable_offload`. CI cannot run the DFS path because it needs 3FS.

- liulanze · comment · 2026-10-20T23:07:20Z · [source](https://github.com/vllm-project/vllm/pull/61175#discussion_r4331282889)

File: `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/worker.py` · line None

With `enable_offload` and `enable_dfs` both on, this limit becomes `local_buffer_size`. But Mooncake reads the LOCAL_DISK (SSD) replica before the DFS replica, and the SSD owner buffer is only 1280 MB. So a load over 1280 MB now fails with BUFFER_OVERFLOW. Before, it was split to fit.

- daegyu94 · comment · 2026-10-21T00:45:27Z · [source](https://github.com/vllm-project/vllm/pull/61175#discussion_r4331866012)

File: `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/worker.py` · line None

Good catch, thanks. I reproduced it on 3FS with standalone-store, enable_offload + enable_dfs and local_buffer_size=2GB: with the memory replicas evicted, a 30k-token prompt (~1.7 GB of KV) went out as one GET of 1874 keys, the owner returned BUFFER_OVERFLOW and the request failed. With both flags on, the budget is now min(local_buffer_size, 1280 MB), so the same load is split into two GETs, all keys load, and the output matches. Added a unit test and a line in the docs.
