# [Metrics][KV Cache] Add per-type KV cache usage for hybrid models

[Upstream PR](https://github.com/vllm-project/vllm/pull/64491) · state: open · merged: False

## Original PR description



## Overview

Add `vllm:kv_cache_usage_perc_by_type{kv_cache_type=...}`, which splits
`vllm:kv_cache_usage_perc` by KV cache type for hybrid models (full attention +
Mamba/GDN, full attention + sliding window, ...). The per-type values sum
exactly to the existing aggregate usage.

Related: #57336 (token-level usage, aggregate only for hybrid models), #54840
(startup log of per-group blocks per request), #33434/#33435 (evictable-block
gauges, declined), #63808/#63578 (Mamba-aware eviction policies).

## Claims

- New gauge `vllm:kv_cache_usage_perc_by_type`, labeled by KV cache spec kind
  (`full_attention`, `mamba`, `sliding_window`, ...). Groups of the same kind
  are summed, so label cardinality is bounded by the number of spec kinds.
- Values are fractions of the **shared** block pool and sum exactly to
  `vllm:kv_cache_usage_perc`, so the gauge breaks down existing dashboards
  without changing them.
- Emitted only for hybrid models (>1 KV cache group) with stats logging on.
  Non-hybrid models and `--disable-log-stats` see no new series and no extra
  bookkeeping.
- Bookkeeping is O(1) per block ref-count 0 <-> >0 transition. No GPU work, no
  CPU/GPU sync.

## Validation

**Unit tests**

```bash
pytest tests/v1/core/test_prefix_caching.py tests/v1/core/test_single_type_kv_cache_manager.py
# 275 passed
pytest tests/v1/core/test_prefix_caching.py -k usage_by_type
pytest tests/v1/engine/test_output_processor.py -k kv_cache_usage_by_type
```

- `test_hybrid_usage_by_type[sliding_window|mamba]`: per-type usage sums to
  `manager.usage` across allocation, free, and blocks revived from the free
  queue by a prefix-cache hit. Each such block is charged to the group that
  wrote it.
- `test_usage_by_type_disabled`: tracking stays off for single-group models
  and without `log_stats`.
- `test_kv_cache_usage_by_type_gauge`: the Prometheus gauge is emitted only
  when per-type usage is present.
- Invariant check (local only, not committed): I temporarily asserted
  `sum(by_type) == usage` on every allocate/free and forced tracking on for
  all hybrid managers. `tests/v1/core` passed in full.

**End-to-end, H20 96 GB, `Qwen/Qwen3.5-4B`** (GDN hybrid: 1 full-attention
group + 3 Mamba groups). Fixed KV pool via `--kv-cache-memory-bytes`, load
from `vllm bench serve --dataset-name random --random-range-ratio 0
--ignore-eos`. Steady-state `/metrics` samples:

| Workload | Prefix caching | running / waiting | `kv_cache_usage_perc` | `full_attention` | `mamba` |
|---|---|---|---|---|---|
| A: 32000 in / 256 out, concurrency 128 | off | 15 / 113 | 0.9687 | 0.9233 | 0.0454 |
| B: 128 in / 384 out, concurrency 256 | off | 227 / 29 | 0.9989 | 0.2497 | 0.7492 |
| A': same as A | on | 15 / 49 | 0.9648 | 0.9087 | 0.0561 |

- **Same aggregate, opposite bottleneck.** A and B both sit at ~97-100% usage
  with a queue. In A, full attention holds 95% of the pool. In B, Mamba state
  holds 75%: each request needs 3 Mamba blocks but only 1 attention block, and
  admission stops at 227 ≈ pool / 4. The aggregate gauge looks the same in
  both cases.
- **Additivity.** In every sample, `full_attention + mamba ==
  kv_cache_usage_perc`.
- **Preemption.** When a request is preempted (running 15 → 14 in A), `mamba`
  drops by exactly 3 blocks, so Mamba blocks are released together with
  attention blocks.
- **Not derivable with prefix caching on.** In A' (`mamba_cache_mode=align`),
  `mamba` is ~52-56 blocks, more than the 15 × 3 = 45 that
  `num_requests_running` would predict. It also does not drop when running
  goes 15 → 14.

## Details

**Motivation.** Hybrid models put every KV cache group in one shared
`BlockPool`, but `vllm:kv_cache_usage_perc` only reports the total. The types
in that pool scale along different load dimensions:

- Full attention grows with context length.
- Sliding window grows with min(context, window).
- Mamba/GDN state is a fixed number of blocks per request, so it grows with
  concurrency (plus `align`-mode checkpoints and speculative blocks).

When the pool saturates and requests queue or get preempted, operators cannot
tell from the aggregate whether to lower `max_model_len` / cap long requests
(attention-bound, workload A) or lower `max_num_seqs` (state-bound,
workload B). The split can only be back-computed in the simplest
configuration (prefix caching off, uniform request lengths, known internal
group layout). It breaks with prefix caching, sliding-window layers, mixed
request lengths, or spec decode. Other cases:

- #53130: a gpt-oss deployment stalled at ~99.5% usage, and a GDN-hybrid user
  suspected state pages filling the pool. Neither could check.
- The recent Mamba-aware eviction work (#63808/#63578) changes how much of the
  pool Mamba state holds, and nothing currently exposes that number.

**Design.**

- `BlockPool.enable_group_usage_tracking(num_groups)` records which group last
  allocated each block (`_block_group`) and keeps per-group counts of blocks
  with `ref_cnt > 0`.
- Counts change only on 0 <-> >0 transitions: `get_new_blocks` (now takes
  `kv_cache_group_id`), `touch`, `free_blocks`, and `unpin_blocks`.
- Prefix-cache keys include the group id, so a block cached in the free queue
  can only be hit by the group that wrote it. Keeping its group label while it
  is free is therefore correct.
- Direct `ref_cnt += 1` on CoW paths only touches blocks that are already held
  (`ref_cnt > 0`), so it does not need accounting.
- `KVCacheManager.get_usage_by_type()` sums groups by spec kind and divides by
  the shared pool size (minus the null block). This keeps the split additive.
- When tracking is on, `get_new_blocks` asserts that a group id is passed, so
  a new call site cannot silently drop blocks from the split.


**Non-goals.** No evictable/cached-block gauges. That was proposed in
#33434/#33435 and declined, since at steady state it is ≈ 1 - usage. Blocks
with `ref_cnt == 0` (including cached ones) are counted as free, matching
`kv_cache_usage_perc`.

**Limitations.**

- If the hybrid KV cache manager is disabled (non-GPU platform, a connector
  without HMA support, `--disable-hybrid-kv-cache-manager`, chunked-local
  attention without `VLLM_ALLOW_CHUNKED_LOCAL_ATTN_WITH_HYBRID_KV_CACHE=1`),
  all layers form one group and the gauge is not emitted.
- With data parallelism the gauge is per engine, like
  `kv_cache_usage_perc`.
