# [Quantization][Perf] FP8-input consumer for block-FP8 linear on sm90

[Upstream PR](https://github.com/vllm-project/vllm/pull/63202) · state: open · merged: False

## Original PR description



## Overview

Stacked on #61073 (`maybe_fused_norm_quant` producer + `QuantizedActivation` contract): until it
merges, this diff includes its commits; only d418185ac9 and 454f231d39 are mine.

Lets the default sm90 block-FP8 kernel, `FlashInferFp8DeepGEMMDynamicBlockScaledKernel`, consume
activations already quantized by the fused RMSNorm + 1x128 FP8 producer, instead of re-quantizing
BF16 input itself. Opt-in via `VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER_FP8_INPUT=1`; default behavior is
unchanged.

## Claims

- With the switch on, sm90 advertises `kFp8Dynamic128Sym` through `input_quant_key()`, so #61073 fuses
  norm + quant for qkv_proj / gate_up_proj; the GEMM keeps its batch split (FlashInfer swapAB for
  M < 32, DeepGEMM for M >= 32) and drops its internal quant.
- Output is bit-exact against the BF16-input path when fed the same quantized activations.
- At M ≥ 32 the FP8-input path is slightly closer to an fp32 reference (2.57e-2 vs 2.67e-2 mean
  rel. error), since it keeps exact fp32 activation scales.
- No accuracy change (GSM8K within 1σ). End-to-end gain depends on the producer kernel, which is
  why this stays opt-in (see Details).

## Details

**Design.** `input_quant_key()` returns `kFp8Dynamic128Sym` only on sm90 with FlashInfer blockscale
available and the switch on (computed once in `__init__`). `apply_weights` unwraps the
`QuantizedActivation` with `as_quantized_activation`; plain tensors go through the unchanged BF16
path. A new custom op, `vllm::flashinfer_deepgemm_blockscale_gemm_fp8_input`, keeps the `torch.cond`
M < 32 split: `fp8_blockscale_gemm_sm90(x_fp8, w, x_scale, w_scale)` below 32,
`fp8_gemm_nt((x_fp8, x_scale), ...)` from 32. The default `VLLM_USE_DEEP_GEMM_E8M0=1` doesn't block
it: on sm90 fp32 and UE8M0-rounded scales go to the same 1D2D kernel.
The FP8-input op is kept separate so the BF16 path stays untouched; happy to factor out a shared
helper if preferred. Happy to switch the env var to a config flag if preferred.

**Stride guard.** Both GEMMs read the scale through a raw pointer / TMA descriptor and never check
strides (FlashInfer only checks dtype/device; DeepGEMM silently re-lays-out a mismatch). The op
therefore checks, from tensor metadata only (no host sync): `x_fp8` contiguous e4m3; `x_scale` fp32,
shape `(M, K/128)`, strides `(1, round_up(M, 4))` (stride(0) exempt at M=1), and raises otherwise.
The op is tagged `needs_exact_strides` so Inductor keeps the padded layout.

**Why opt-in.** Per call in the model at bs=1, #61073's current 3-pass `rms_norm_per_block_quant`
takes 5.95 µs and #62514's single-pass kernel 3.1 µs, vs 2.08 + 1.57 = 3.65 µs for the unfused
norm + quant pair it replaces. With the current producer the switch is a net loss (+4.1% / +3.2% /
+1.8% wall clock at bs 1/32/256; earlier run, precompiled build, not part of the table above); with
#62514 it turns into the gain shown above. Proposed path: land this opt-in, revisit the default
after #62514 or the FlashInfer producer (and with a broader model sweep).

**CI.** 454f231d39 adds `scaled_mm/flashinfer.py` and `scaled_mm/deep_gemm.py` to the
`source_file_dependencies` of the `kernels-deepgemm-test-h100` step, which runs `test_block_fp8.py`
on H100; before, a change to those kernels alone did not trigger it.

**Not duplicating:** no other open PR implements this consumer; agreed as the #61073 follow-up.

**Limitations.** sm90 only. End-to-end gains need #62514 or the FlashInfer producer. Qwen3 isn't
wired in #61073 (Llama only); the e2e numbers used local Qwen3 wiring, which I'll upstream as a
follow-up. `VLLM_GPU_SYNC_CHECK=error` not run yet (the guard reads only shapes/strides).
