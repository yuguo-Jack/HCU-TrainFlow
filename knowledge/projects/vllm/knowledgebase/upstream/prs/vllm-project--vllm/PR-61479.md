# [Frontend] Advertise `--enable-x`/`--disable-x` for boolean CLI flags

[Upstream PR](https://github.com/vllm-project/vllm/pull/61479) · state: closed · merged: True

## Original PR description

## Overview

Boolean CLI flags named `enable_*` / `disable_*` now advertise `--enable-x` and `--disable-x` as each other's inverse, instead of argparse's `--no-enable-x` / `--no-disable-x`. The `--no-` spellings keep working but are hidden.

## Claims

- `--enable-x` and `--disable-x` are inverses for every `BooleanOptionalAction` flag whose name starts with `enable_` or `disable_` (50 on `vllm serve`):
  - `enable_prefix_caching`: `--enable-prefix-caching` sets it to `True`; `--disable-prefix-caching` sets it to `False`.
  - `disable_hybrid_kv_cache_manager`: `--disable-hybrid-kv-cache-manager` sets it to `True`; `--enable-hybrid-kv-cache-manager` sets it to `False`.
- **Backwards compatible:** `--no-enable-x` and `--no-disable-x` still parse, including from YAML configs (`enable_x: false`). They no longer appear in `--help`, the generated CLI docs or usage strings.
- **Other bool flags unchanged:** flags without the prefix (e.g. `--data-parallel-hybrid-lb`) keep `--x` / `--no-x`, and short aliases like `-ep` stay positive.
- **Docs and messages:** user-facing docs, examples and error messages now use the advertised spelling. Tests, CI and benchmark scripts keep `--no-enable-x`, which still works and exercises the compatibility path.

  --disable-hybrid-kv-cache-manager, --enable-hybrid-kv-cache-manager

## Details

Follows the maintainer discussion on Slack. `--disable-x` reads more naturally than `--no-enable-x`, and flags that start with `disable_` should get `--enable-x` symmetrically. The original `BooleanOptionalAction` standardisation is kept; only the advertised names change.

**Implementation.** `FlexibleArgumentParser` registers `EnableDisableAction` in place of `BooleanOptionalAction` in its action registry. Argument groups and subparsers share that registry, so no call sites change. The action:

- registers the inverse prefix alongside argparse's `--no-` variants;
- decides the value from whether the option used was a negative one;
- has its `option_strings` trimmed back to the advertised ones after registration, so the `--no-` forms stay registered with the parser but leave help, usage and docs.

To trim after registration, the `add_argument` / argument-group overrides that previously existed only for Python < 3.13 (for the `deprecated` kwarg) are now unconditional; the `deprecated` handling inside them is still version-gated.

**Limitations.**

- If a parser defines both `--enable-x` (bool) and a separate `--disable-x` option, argparse raises a conflicting-option error at parser construction. No such pair exists today.
- `store_true` flags such as `--disable-log-stats` are untouched, since they have no inverse form today.

**Sequencing with #61489.** That PR points docs at `--no-enable-flashinfer-autotune`. Whichever of the two lands second should switch those references to `--disable-flashinfer-autotune`.

Not a duplicate: searched open PRs for `disable alias enable flag argparse`, `no-enable disable cli alias` and `FlexibleArgumentParser disable`; nothing related.
