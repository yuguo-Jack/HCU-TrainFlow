# [Bugfix][KV Transfer] Allow DMA-only connectors with expandable_segments:True

[Upstream PR](https://github.com/vllm-project/vllm/pull/42405) · state: open · merged: False

## Original PR description

## Summary

PR #41237 added a blanket rejection of **all** KV connectors when `expandable_segments:True` is set in `PYTORCH_CUDA_ALLOC_CONF`. This is correct for RDMA-based connectors (`NixlConnector`, `MooncakeConnectorV1`) whose registered memory regions become stale after CUDA VMM remaps virtual addresses. However, it's a false positive for DMA-only connectors like `SimpleCPUOffloadConnector`, which transfer data via `torch.cat`/tensor slicing — operations that are transparent to VMM remapping.

This PR introduces a `SupportsVmmSafeTransfers` marker class that connectors opt into by inheriting. The config validation checks this marker before rejecting, allowing DMA-only connectors to work with `expandable_segments` without requiring sleep mode.

### End-to-end validation on hardware

**Setup:** 3× NVIDIA RTX 3060 12GB, AMD EPYC 7551P 32-Core, 260 GB RAM

**Model:** `groxaxo/Qwen3.6-27B-GPTQ-Pro-4bit` (GPTQ-Pro 4-bit, Marlin kernels, ~21 GB weights, 64-layer hybrid: 16 full attention + 48 linear attention)

**Config:**
```
--pipeline-parallel-size 3
--gpu-memory-utilization 0.93
--max-model-len 252000
--kv-offloading-backend native
--kv-offloading-size 16
--kv-cache-dtype fp8
--enforce-eager
--max-num-seqs 4
--max-num-batched-tokens 1568
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

 Without the PR, you cannot use both  **PYTORCH_CUDA_ALLOC_CONF** and **--kv-offloading-***. Which means having to drop expandable_segments — which means higher memory fragmentation, more OOM risk during sustained serving, and less efficient VRAM utilization on consumer GPUs.

**Results on unmodified nightly** (`v0.20.2rc1.dev209`):
```
ValueError: KV connector SimpleCPUOffloadConnector is incompatible with
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True unless enable_sleep_mode
is also enabled.
```

**Results on nightly + this PR:**
- Server starts, all 3 PP ranks initialize `SimpleCPUOffloadConnector` successfully
- 168 ± 5 tok/s at 887-token prompt prefill
- Sleep mode overhead (~868 MiB/GPU for CuMemAllocator pools) is avoided, critical for 12 GB GPUs where every MiB counts

Note: Longer prompts (10K+) on the nightly image hit a separate FLA linear attention kernel memory regression unrelated to this PR. The v0.20.2 release with the same PR overlay works fine up to 252K context.

### Why this is not duplicating an existing PR
No open PR addresses this specific gap. PR #41237 introduced the blanket rejection. This PR relaxes it for DMA-only connectors via an opt-in marker.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The current implementation of `_connector_supports_vmm_safe_transfers` is fragile because it doesn't handle `ImportError` (which can be raised by `importlib.import_module` inside `get_connector_class`) or `TypeError` (which can be raised by `issubclass` if `connector_cls` is not a class). Additionally, the call to `supports_vmm_safe_transfers` is outside the `try-except` block, meaning any failure there will crash the configuration initialization. 

To maintain the conservative approach described in the PR (rejecting if safety cannot be determined), the `try-except` block should encompass the entire resolution and check process, and include `ImportError` and `TypeError` to handle environment or configuration issues gracefully.

```suggestion
        try:
            connector_cls = KVConnectorFactory.get_connector_class(
                self.kv_transfer_config
            )
            return supports_vmm_safe_transfers(connector_cls)
        except (ValueError, AttributeError, ImportError, TypeError):
            return False
```
