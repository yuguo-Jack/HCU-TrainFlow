# [Bugfix] Fix MLA accuracy drop under DCP with RoPE + KV-cache fusion (GSM8K 77% to 1.5%)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64520) · state: open · merged: False

## Original PR description



## Overview

With decode context parallelism (DCP) and the MLA RoPE + KV-cache fusion on, MLA models give wrong outputs. On DeepSeek-Coder-V2-Lite-Instruct with TP=2 and DCP=2, GSM8K accuracy drops from 77.1% to **1.5%**. This PR fixes the fused kernel so it still applies RoPE to tokens that have no local KV slot.

## Claims

- `concat_and_cache_mla_rope_fused` now rotates `q_pe` and `k_pe` for every token. It skips only the KV-cache store when the slot is -1.
- With DCP and the fusion on, GSM8K accuracy goes back from 1.5% to 78.1%. It is 77.1% without the fusion.
- The fusion also matches on DeepSeek-R1 and Kimi-K2, built from their real configs with a few layers. So these models take the same path.

## Validation

I built `_C_stable_libtorch` from main and from this branch and ran the new kernel test on an L40S.

```
pytest tests/kernels/core/test_rotary_embedding_mla_cache_fused.py -k slot_minus_one
```

On main both cases fail with `Mismatched elements: 4096 / 8192 (50.0%)` on `q_pe`. That is exactly the odd tokens, which have slot -1. With the fix both pass, and the whole file passes (146 passed).

I ran the new `test_context_parallel.py` case on 2x H200 with both builds.

```
pytest tests/distributed/test_context_parallel.py -k DeepSeek-V2-Lite-Chat
```

On main the new case fails with `TP+DCP accuracy too low: 0.000 < 0.640`. With the fix it passes with 0.657.

I also ran GSM8K (5-shot, all 1319 questions, greedy) on 2x H100 with TP=2 and DCP=2. Inductor graph partition was on in all three runs, so only the fusion and the build differ.

| Model | Fusion | Build | GSM8K |
|---|---|---|---|
| DeepSeek-Coder-V2-Lite-Instruct | off | main | 77.1% |
| DeepSeek-Coder-V2-Lite-Instruct | on | main | **1.5%** |
| DeepSeek-Coder-V2-Lite-Instruct | on | this PR | 78.1% |

The fusion matched on 27 of 27 layers on both DCP ranks in the two fused runs. I also compiled DeepSeek-R1 (4 layers) and Kimi-K2-Instruct (2 layers) from their real configs with dummy weights, like `tests/compile/fusions_e2e` does. The fusion matched on every layer in both.

## Details

Under DCP, each rank's slot mapping is -1 for tokens whose KV is stored on another rank. The rank still computes attention for those tokens' queries. The fused kernel returned early on slot -1 before the Q RoPE loop, so those queries reached attention without RoPE. The early return was written for padded tokens, whose outputs are dropped. The check used to sit after the Q RoPE loop. #40392 moved it to the top of the kernel. #54908 fixed the same early return in the DeepSeek-V3.2 norm + RoPE kernel.

The unfused path applies RoPE to every token and checks the slot only for the cache write. The sibling fused kernels for MiniMax-M3, Kimi-K3 and DeepSeek-V4 do the same. This PR moves the slot check to the store. Padded tokens now get RoPE too, as in the unfused path.

The fusion is off by default today. It turns on with inductor graph partition, and #49142, #60326 and #57349 would make it apply more often. The new `test_context_parallel.py` case covers DCP with the fusion on, following #30309.
