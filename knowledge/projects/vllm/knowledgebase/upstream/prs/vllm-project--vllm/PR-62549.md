# [Bugfix][Responses API] Return 400 when streaming retrieval has no stored events

[Upstream PR](https://github.com/vllm-project/vllm/pull/62549) · state: open · merged: False

## Original PR description

## Purpose

`GET /v1/responses/{response_id}?stream=true` on a stored response that was **not** created with `background=true` **and** `stream=true` currently returns `HTTP 200` with `content-type: text/event-stream`, then drops the connection.

Why it happens: `retrieve_responses` returns `responses_background_stream_generator(...)` without checking that the response has stored events. That generator is lazy, so its existing `Unknown response_id` `VLLMValidationError` is raised only on the first `__anext__`, after Starlette has already sent the 200 headers. The server logs `Exception in ASGI application`. The client gets an empty, truncated body (curl exit 18), and SDK clients see a broken stream instead of an API error.

Only `_run_background_request_stream` fills `event_store`. This covers:
- `store=true` foreground requests (sync or streaming)
- `background=true, stream=false` requests

This PR checks `event_store` in `retrieve_responses` and returns a regular 400 `invalid_request_error` (`param="stream"`) before any streaming starts. All other errors on this endpoint (404 etc.) are already returned this way.

The background `stream=true` replay path is unchanged. A client can only learn a background-stream response id from the stream's first event, and the producer task has populated `event_store` by then, so the eager check cannot reject a valid replay.

## Not a duplicate

I searched open and closed issues and PRs for `retrieve stream`, `Unknown response_id`, `responses_background_stream_generator`, `event_store`, and `responses background stream`. The closest open PRs touch the same generator but not this path:
- #49721 terminates consumers when the producer exits early.
- #62324 rejects a negative `starting_after`.

Neither adds a pre-stream check for responses with no stored events.

2. `POST` with `store=true, background=true` (no stream), then `GET ...?stream=true`.
3. Control: `POST` with `background=true, stream=true`, then `GET ...?stream=true` replays the events.
