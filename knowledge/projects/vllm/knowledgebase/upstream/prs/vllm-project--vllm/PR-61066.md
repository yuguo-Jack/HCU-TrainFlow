# [Bugfix][Quantization] Keep per-shard weight global scales in compressed-tensors NVFP4 linears

[Upstream PR](https://github.com/vllm-project/vllm/pull/61066) · state: open · merged: False

## Original PR description

## Purpose

`CompressedTensorsW4A4Fp4.process_weights_after_loading` runs a fused NVFP4 linear (`qkv_proj`, `gate_up_proj`,
Qwen3.5's `in_proj_qkvz` / `in_proj_ba`, ...) with the largest `weight_global_scale` divisor of its shards and only
logs a warning when they differ. Every shard with a smaller divisor is then dequantized `gs_shard / gs_max` times too
small.

llm-compressor gives each checkpoint tensor its own global scale unless it fuses them. For example,
`sakamakismile/Huihui-Qwen3.8-27B-abliterated-NVFP4` (Qwen3.5 architecture) has different scales for `in_proj_qkv` /
`in_proj_z` and `in_proj_b` / `in_proj_a` in all 48 Gated DeltaNet layers. In every layer, one side of each pair is dequantized
x0.36 to x0.99 too small. That changes z (output gate), b (beta) and a (decay) relative to the rest; these are used
without normalization. Generation stays coherent, which is why this is easy to miss.

## Changes

- Keep the GEMM exactly as today (the largest divisor). Record the column ranges of the shards whose divisor differs,
  with the factor `gs_max / gs_shard`, and multiply those output columns in place in `apply_weights`, before adding
  the bias. Adjacent shards with the same factor are merged into one range (e.g. q/k/v of `in_proj_qkvz`).
- It works for any number of partitions and with every NVFP4 linear kernel, because it wraps
  `kernel.apply_weights`. The factors are applied as fp32 scalars.
- Layers with a shared global scale take the unchanged path.
- The warning for mismatched *weight* global scales is removed, because they are now handled. The warning for
  mismatched *input* global scales stays: those cannot be corrected after the GEMM.

Related:
- #47515 uses the same idea for two-partition layers only (3+ partitions keep `.max()`), with a full-output multiply
  by a vector cast to the output dtype. It would fix `in_proj_ba` but not `in_proj_qkvz`.
- #59845 fixes the ModelOpt path at load time by rescaling the e4m3 block scales. For comparison I also measured that
  approach on the compressed-tensors path (results below). If reviewers prefer one policy for both paths, this can
  be switched.
- #55073 is the NVFP4 MoE w13 counterpart.

## Test Plan

    pytest tests/quantization/test_compressed_tensors.py -k fused_shards_keep_global_scales -v
    pre-commit run --files <changed files>

The new test quantizes two and four shards with their own global scales, runs the scheme with the emulation kernel
and compares the result with a per-shard dequantized reference.

End to end on an RTX 5090: `sakamakismile/Huihui-Qwen3.8-27B-abliterated-NVFP4`, FlashInfer CUTLASS NVFP4 kernel,
Model Runner V2, torch.compile + CUDA graphs. The change was applied to a v0.30.0 install; this file is identical on
main.

## Test Result

- New test: 2 passed (CPU and CUDA). Fails on main (max abs diff 32.9 / 18.6).
- Layer level with the real FlashInfer CUTLASS kernel, 2- and 4-partition layers, M = 1..300: cos 0.999995+ against
  an fp32 per-shard reference; eager and `torch.compile` outputs are identical.
- Model (94 layers rescaled, factors 1.01 to 2.81):

| | wikitext-2 NLL (compiled) | wikitext-2 NLL (eager) | GSM8K 5-shot, chat (1319) |
|---|---|---|---|
| main | 2.0020 | 2.0011 | 94.69 % |
| this PR | 1.9786 | 1.9719 | 95.38 % |
| load-time e4m3 block-scale rescale (alternative) | 1.9809 | 1.9767 | 95.75 % |

  wikitext-2-raw test: 64 x 2048-token windows. GSM8K: `tests/evals/gsm8k/gsm8k_eval.py`, chat mode,
  `enable_thinking=False`, max_tokens 512. The GSM8K differences are within about 1 standard error.
- Cost of the rescale (eager, CUDA graph, N=16384 K=5120): +1-3 us per call at M <= 128, +7 % at M = 1024. The
  wikitext prefill run took 8.90 s on main and 9.26 s with the change. Nothing changes for checkpoints with shared
  scales.
