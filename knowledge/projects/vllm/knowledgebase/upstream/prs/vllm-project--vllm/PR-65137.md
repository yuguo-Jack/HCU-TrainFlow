# [Bugfix][KV Connector] Keep same-host NIXL on NVLink with the extensible KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/65137) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Since the extensible KV cache (#56492) became the default, same-host NIXL P/D silently moves KV over TCP instead of NVLink. This keeps NVLink: with an IMEX channel the cache gets a FABRIC handle, and without one it stays off for NIXL by default.

## Claims

- Per KV transfer, same-host: **9.9 s → about 24 ms**.
- With an IMEX channel, NVLink and the extensible KV cache work together.
- Nothing changes without NIXL on device memory.

## Validation

GLM-5.3-Flash 1P1D on one node, DEP4 + DEP4, 8x B200, driver 590.48.01, NIXL 1.5.2, real MTP 5, 1,319 GSM8K prompts:

| Build | KV read protocol | Avg transfer | GSM8K | GSM8K time |
|---|---|---:|---:|---:|
| main | `software emulation`, `tcp/cilium_host` | 9.9 s | – | ~5 min |
| main, without `UCX_CUDA_COPY_DMABUF=no` | same | 205 s | – | >50 min |
| main, `--disable-extensible-kv-cache` | `zero-copy`, `cuda_ipc` | 23.4 ms | 0.9742 | 49 s |
| **This PR, no channel** | `zero-copy`, `cuda_ipc` | 23.6 ms | 0.9757 | 52 s |
| This PR, with a channel | `zero-copy`, `cuda_ipc` | 24.2 ms | 0.9750 | 49 s |

Both PR rows ran on `4904c38f42`. Under load, on the previous commit `ff4c74f38c` with no channel, a one-hour AgentX run at concurrency 256 made 24,041 transfers averaging 894 MB in 22.1 ms, with 0 failures.

The new tests fail with the rule and driver change reverted. To see the transport, run P and D on one node with `UCX_PROTO_INFO=y` and look for `remote memory read by ucp_get*(multi)` in D's log.

## Details

**Root cause.** No code chooses TCP. #56492 maps the KV cache with `cuMemCreate` + `cuMemMap`. UCX's `cuda_ipc` exports plain memory with `cuIpcGetMemHandle`, which cannot export driver-mapped memory, and uses a FABRIC handle only on memory created with one. So that memory has no `cuda_ipc` path and UCX picks the next transport without an error. Accuracy does not change, so #56492's NIXL accuracy check would not show it. This is inferred from UCX's protocol tables and library strings, and the comment on the `LMCacheMPConnector` gate; I did not read UCX's source.

**Fix.**
- `CudaVmmDriver` requests `CU_MEM_HANDLE_TYPE_FABRIC` when the device supports it and an IMEX channel opens. The attribute alone is not enough: it reads 1 with no channel.
- `_resolve_extensible_kv_cache` keeps the feature off by default with NIXL on device memory and no channel. An explicit `--enable-extensible-kv-cache` is honored with a warning.

- weimin023 · comment · 2026-11-04T06:16:58Z · [source](https://github.com/vllm-project/vllm/pull/65137#issuecomment-6624076747)

@gcanlin On a PCIe-only box (no NVLink, no IMEX channel), turning the extensible KV cache off, which this PR does by default for NIXL without a channel, is not enough. Same-host pull still goes over TCP unless `UCX_CUDA_IPC_ENABLE_GET_ZCOPY=on` is also set.

Setup: 2x RTX PRO 6000 Blackwell Server Edition (SM120, driver 595.99.02) behind one PCIe switch (PIX), no RDMA. Qwen3.8-27B-FP8, TP=1, 1P1D, `NixlConnector` (pull), NIXL 1.5.2, 199 MB KV per request, `--enforce-eager`.
"Extensible off" is `--no-enable-extensible-kv-cache`; I did not run the PR itself.

| Extensible KV | `UCX_CUDA_IPC_ENABLE_GET_ZCOPY` | KV read | Mean TTFT, c1 cold / warm |
|---|---|---|---|
| on (main) | unset | about 380 ms | 561 / 548 ms |
| on | on | 376 to 444 ms | 569 / 616 ms |
| off (this PR) | unset | about 377 ms | 579 / 546 ms |
| off | on | 22 to 25 ms | 226 / 192 ms |

Cause: without NVLink, UCX disables cuda_ipc GET zero-copy (`cuda-ipc get zcopy disabled as no nvlinks detected`) and the read uses `software emulation | tcp/eth0`. nixl#2208 enables it by default, but it is on main only, not in v1.5.2.

Would you take a small follow-up that does `os.environ.setdefault("UCX_CUDA_IPC_ENABLE_GET_ZCOPY", "on")` next to the existing `UCX_RCACHE_MAX_UNRELEASED` default in `nixl_utils.py`, or would you rather only document it?
