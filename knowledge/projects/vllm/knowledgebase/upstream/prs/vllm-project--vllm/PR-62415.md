# [ROCm][Bugfix] Zero out-of-window V in ROCM_ATTN's sliding-window kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/62415) · state: open · merged: False

## Original PR description



## Overview

`ROCM_ATTN`'s Triton kernels (`context_attention_fwd` in `prefix_prefill.py` and `kernel_paged_attention_2d` in `chunked_prefill_paged_decode.py`) mask QK for keys outside the sliding window but still load V for those keys unmasked. If an out-of-window slot sits in a freed block that now holds NaN/Inf, the output row becomes NaN even though its softmax weight is 0. This PR zeroes V for out-of-window tokens in both kernels.

Found while answering a review question on #61433: why does a DFlash2 drafter accept far more tokens on `TRITON_ATTN` than on `ROCM_ATTN`?

## Claims

- `ROCM_ATTN` gives finite, correct sliding-window output when the out-of-window part of the KV cache holds NaN/Inf, for both causal and non-causal attention.
- Qwen3.8-27B + `z-lab/Qwen3.8-27B-DFlash2` (non-causal drafter, window 2048), with `ROCM_ATTN` for both target and drafter on MI355X:
  - 8k input, concurrency 16: acceptance length goes from 1.21 to 3.22, and output throughput from 132.5 to 225.3 tok/s.
  - 64k input, concurrency 1: the run no longer fails (9.6 tok/s, acceptance length 2.84).
- No change for models without a sliding window: the new code sits under `if SLIDING_WINDOW > 0` (a constexpr).

## Validation

**Unit test.** `tests/kernels/attention/test_prefix_prefill.py::test_sliding_window_ignores_non_finite_out_of_window_kv` is new:
- It writes K/V into the paged cache, fills every slot outside all queries' windows with NaN or Inf, and calls `chunked_prefill_paged_decode` with `sliding_window=64`.
- The batch mixes prefill chunks (`query_len=8`, `context_attention_fwd`) and decodes (`query_len=1`, `kernel_paged_attention_2d`).
- It compares against an fp32 reference for causal and non-causal attention.

## Details

**Root cause.** For a query at position `q`, keys at `k <= q - W` get score `-inf` (or `-10000`), so `p = 0` for them. The kernels still load `V` for those keys and run `tl.dot(p, v)`. The KV manager frees blocks that are entirely outside the window, and another request (or, in a hybrid model, mamba state) can reuse them. Such a block can hold any bytes, including NaN/Inf, and `0 * NaN = NaN`. A non-causal drafter like DFlash2 is hit hardest: one NaN row rejects all drafts in the step.

**Fix.** Zero `V` where the key is outside the window:
- `kernel_paged_attention_2d` already has an `in_window` condition per key, so it reuses that condition for `V`.
- `context_attention_fwd` processes a tile of `BLOCK_M` queries. It zeroes keys that are outside the window of the tile's first query (`ctx_len + start_m * BLOCK_M`). The later queries in the tile have larger positions, so these keys are outside their windows too and `p` is already 0 for them. The KV manager frees blocks relative to the first scheduled query of the request, so every key that can be in a freed block gets zeroed.

The cost is one `tl.where` on a tile that is already in registers, and only when the model has a sliding window.
