# [Spec Decode] Add draft_context_window to bound DFlash/DSpark draft attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/61261) · state: open · merged: False

## Original PR description

## What this does

Adds an opt-in `draft_context_window` to `--speculative-config` for DFlash and DSpark (MRV2). When set, the drafter only attends to the last N context tokens. Positions stay absolute. Target verification doesn't change. Default is `None`, so nothing changes unless you turn it on.

Context: #47930. We run Kimi K3 with `Inferact/Kimi-K3-DSpark` on long agent sessions, and acceptance falls off a cliff past ~128K. This fixes it for us.

## Why

Accept length (k=3, out of 4) on main, DCP 1:

| context | main | main + `draft_context_window: 32768` |
|---|---|---|
| 0-16K | 2.48 | 2.49 |
| 16-64K | 2.39 | 2.40 |
| 64-128K | 2.29 | 2.27 |
| 128-256K | **1.45** | **2.29** |
| 256K+ | **1.26** | **2.22** |
| mixed 16-300K, c16 | 1.90 | 2.28 |

Below 128K: no change. Above it: back to short-context levels. Output tok/s goes up +31% at 128-256K and +23% at 256K+, +9% on the mixed run.

Same thing with DCP 4 (with #59392 applied, since main still crashes there, see below):

| context | main | window 32K |
|---|---|---|
| 64-128K | 2.26 | 2.29 |
| 128-256K | 1.46 | 2.28 |
| 256K+ | 1.26 | 2.20 |
| mixed c16 | 1.92 | 2.27 |

## Is it the kernel? No

Same build, no window, only the drafter's attention backend swapped:

| context | FLASHINFER_MLA | TRITON_MLA |
|---|---|---|
| 128-256K | 1.448 | 1.437 |
| 256K+ | 1.257 | 1.253 |

Same collapse on both. And on v0.30 it's the same with prefix caching and KV offload fully off (numbers in #47930), so it's not restored KV either. Looks like the drafter just doesn't generalise past what it was trained on (the model card only goes to ~95K). 64K behaves like 32K. I can't prove which shared bit is to blame (drafter weights vs. its RoPE/YaRN handling), but the window fixes it either way.

## Quality

GSM8K, first 200, `reasoning_effort: low`, temp 1.0:

| | main | window 32K |
|---|---|---|
| plain prompts (window never kicks in) | 0.985 | 0.990 |
| same problems behind a ~98K prefix (window drops ~65K) | 0.985 | 0.980 |

1 problem out of 200 either way. Noise.

## Soak

c24, prompts 16-400K, 30 min, same seed. Prefill-bound on purpose (pool oversubscribed).

| | main | window run A | window run B |
|---|---|---|---|
| requests | 331 | 341 | 345 |
| errors / restarts | 0 / 0 | 0 / 0 | 0 / 0 |
| accept length | 1.61 | 2.27 | 2.27 |
| output tok/s | 130 | 153 | 146 |
| TTFT p50 | 58 s | 48 s | 47 s |

No shm_broadcast hangs after load, no Xid. One heads-up: our repeated-tail detector flagged one output in run A (129K prompt, ran to `max_tokens`). Didn't capture the text that time, so I couldn't look at it. Run B captured text and flagged nothing. 1 in 686 vs 0 in 331, so no conclusion either way. The shift can't reach target inputs or target KV (more below), and with probabilistic drafting the output distribution doesn't depend on the drafter anyway.

## How it works

In `DFlashSpeculator.propose`, right after `prepare_dflash_inputs` has computed slot mappings from the full table, a small Triton kernel does, per request:

- excess = `max(seq_len - num_query - N, 0)`, rounded down to whole block-table entries
- shift that request's `input_block_tables[gid]` row left by that many entries
- subtract the dropped positions from `seq_lens`

Keys already carry absolute RoPE, query positions aren't touched, so relative positions inside the window are unchanged. Draft sees at least N tokens, less than N plus one entry.

Why editing those buffers in place is fine:
- `input_block_tables` get re-gathered from the persistent tables at the start of every step, before the target runs. Nothing after `propose` reads them in the same step.
- `seq_lens` is the draft's own buffer.
- Slot mappings are computed before the shift, so KV writes land where they should.
- Dummy runs (capture, profiling) skip it.

DCP: one entry covers `block_size * dcp_size` positions, and `block_size % cp_kv_cache_interleave_size == 0` is already enforced, so whole entries keep every position on its rank. Draft KV groups share `seq_lens`, so all groups drop the same count (a multiple of `dcp_size * lcm(block sizes)`), and only the last one writes it back.

CUDA graphs: runs eagerly before replay and only writes buffers the graph already reads. No new host syncs.

Scope: all DFlash-family speculators go through this `propose`, so it covers `dflash` and `dspark`. Rejected for other methods and on V1, so it never gets silently ignored. Only measured on DSpark / Kimi K3 (MLA drafter). Non-MLA drafters take the same path with `dcp_size=1`, which the unit tests cover.

Tradeoffs: you lose long-range context the drafter could in theory use. For this drafter that's a net loss past ~128K anyway. The right N depends on the drafter, hence off by default. No memory saved, only attention is bounded.
