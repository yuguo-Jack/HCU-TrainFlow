# [ROCm][Qwen4Exp] Enable fp8 KV and indexer caches on the AMD QSA path

[Upstream PR](https://github.com/vllm-project/vllm/pull/61529) · state: closed · merged: True

## Original PR description

## Summary

On AMD GPUs, two vLLM flags that enable 8-bit (fp8) KV caching did not work for Qwen4Exp models. This PR makes both flags work. Users get ~33% more KV cache capacity at 16K context with no quality change outside the eval noise. Peak batch throughput at concurrency 16 is ~6% lower; single-request speed is unchanged. Both flags are opt-in.

```bash
vllm serve Qwen/Qwen3.8-Flash-Next-FP8 ... \
  --kv-cache-dtype fp8 \
  --attention-config.indexer_kv_dtype fp8
```

`--kv-cache-dtype fp8` shrinks the main KV cache; `--attention-config.indexer_kv_dtype fp8` shrinks the compressed-key cache of the model's sparse indexer (QSA). The indexer's raw state cache stays bf16. AMD has two fp8 encodings — FNUZ on gfx942 (MI300) and OCP on gfx950 (MI355) — and the caches use the platform's native one.

## Claims

- **Capacity:** +33% at tensor-parallel size 1 (TP1) and 16K context with both flags (2,505,113 → 3,336,874 tokens); the main KV cache halves. Measured on the pre-merge head (`87b62b06e8`). Capacity comparisons are same-max-model-len only.
- **Quality:** neutral on GSM8K 5-shot (strict 0.899 vs 0.902; flexible 0.881 vs 0.895, with overlapping run ranges), within the binomial error on GPQA-Diamond (0.4747 vs 0.4596), and identical long-context retrieval (90/90 NIAH cells).
- **Deterministic gates:** greedy outputs are byte-identical to the bf16 baseline (a 391-token arithmetic prompt ×3 and a France→Paris continuation at temperature 0).
- **Tradeoff:** single-request decode is unchanged; concurrency-16 aggregate throughput is ~6% lower with both flags. The flags are opt-in, a capacity-vs-concurrency choice.

## Validation

### Unit tests

`pytest -v tests/models/qwen4_exp/test_qsa_prepare_amd.py tests/models/qwen4_exp/test_qsa_amd.py` → **55 passed** on MI355X (gfx950, ROCm 7.2.3, torch 2.13.0+rocm7.2). The same suite runs on the new MI300 CI step (gfx942/FNUZ); that leg is the regression guard for the gfx942-only scale fix and is pending a full CI run on this head.

Both paths write the platform's native flavor, so the C++ op is a valid unfused reference on both arches. The sparse-attention test is parametrized over bf16 and platform fp8; its reference consumes the quantized cache upcast to float, directly exercising the new fp8 read path.

## Limitations / known gaps

- **Unit KV scales only.** The fp8 main KV cache requires unit per-tensor scales (the default). The layer rejects a checkpoint `kv_cache_scheme`, and `forward_qsa` raises `NotImplementedError` if the runtime `_k_scale_float`/`_v_scale_float` are not 1.0. The Triton kernel casts fp8 K to the query dtype and V to fp16 without multiplying by the scale. The NVIDIA port's host-side dequant fold is the follow-up if calibrated scales matter.
- **No serve-level gfx942 run.** Unit and kernel tests cover gfx942/FNUZ; the serving, capacity, and quality numbers are MI355X/OCP. A full gfx942 serve run has not been performed.
- **Concurrency tradeoff.** Concurrency-16 aggregate is ~6% lower with both flags; decode is unchanged. Both flags are opt-in.

## Details

<details><summary>What changed (three logical changes, plus review fixups)</summary>

1. **Fix the fp8 scale divide for FNUZ destinations.** On gfx942 the fp8 cache is FNUZ (`tl.float8e4b8`); on gfx950 it is OCP (`tl.float8e4nv`). `_to_dst_dtype` divided by the KV scale only for OCP, so FNUZ destinations skipped the divide. With the unit scales this path requires today, dividing by 1.0 is a no-op; the fix matters if calibrated KV scales are supported. The test uses 0.5/2.0 scales to exercise the divide.
2. **Support `indexer_kv_dtype=fp8`.** Wires `--attention-config.indexer_kv_dtype` through `amd/indexer_qsa.py`, mirroring the NVIDIA reference. The compressed-key cache and the query-side cast use `current_platform.fp8_dtype()`; the raw state cache stays bf16. The fused kernel already handled fp8-typed stores and loads; the wiring and test coverage were missing.
3. **Support fp8 main KV cache.** Lifts the dtype gates and interprets the uint8 main cache in the platform's native flavor at the typed boundaries. The sparse-attention kernel gains an `IS_FP8` constexpr (K upcast to the query dtype for the QK dot; V to fp16 for the PV dot). The QSA implementation passes `"auto"` to the FlashAttention base class for its fp8-support probe and restores the real dtype afterwards, mirroring NVIDIA; the backend's combination check delegates with no fp8 dtype, so only that probe is bypassed while the other checks remain. `--kv-cache-dtype-skip-layers` is honored per layer. The QSA cache dtype list now covers fp8 alongside the Octave formats (#59774).

</details>

<details><summary>Flavor design and the C++ reference</summary>

AMD has two fp8 encodings: FNUZ on gfx942 (MI300) and OCP on gfx950 (MI355). The main cache is allocated as uint8 and reinterpreted with `current_platform.fp8_dtype()` in the fused prepare, the attention read, and the C++ cache-update path. The C++ `reshape_and_cache_flash` follows the platform flavor (verified on gfx950: 1.0 → 0x38 and -1.0 → 0xb8, i.e. OCP; FNUZ would encode 1.0 as 0x40). The test therefore uses the C++ op as the unfused reference, with separate contiguous uint8 buffers and the same scales.

</details>

<details><summary>Cross-arch and TP4 notes</summary>

Validated end-to-end on gfx950/MI355X. The gfx942/FNUZ leg is unit/kernel-test validated; a serve-level gfx942 run has not been performed. At TP4, the indexer side cache is replicated while the main KV shards, so the indexer-fp8 capacity gain grows from +1.5% at TP1 to +3.05% (11,541,981 → 11,893,691 tokens); the absolute gain scales ~9×. The TP4 FP8 checkpoint needs `VLLM_ROCM_USE_AITER_MOE=0` and `--disable-custom-all-reduce` on this tree; the open #60839 adds automatic fallbacks for both.

</details>

**Why 2.0 and 0.5?**

They're different numbers on purpose. The kernel divides K by one scale and V by the other before storing them as fp8 codes. If we used the same number for both (like 1.0), a bug that drops one divide would be invisible. Using 0.5 for K and 2.0 for V means a missing divide on either side shows up as exactly the wrong size, which the code comparison catches immediately. Different values also mean a bug in K can't accidentally cancel out a bug in V.

**Won't this trip the "scales must be 1.0" check?**

No — those are two different things. The 1.0 requirement is on the scales the model checkpoint provides (the config-level `kv_scale`). The 0.5/2.0 in the test are values we pass directly to the kernel to prove the divide logic works. The 1.0 guard never sees them.

**But production forces 1.0 anyway — isn't the divide dead code?**

It's a no-op in production today, yes, but the divide is infrastructure for when calibrated scales are supported (the known follow-up — the NVIDIA port folds them host-side). Testing it now means the kernel is already correct when that lands. It's also what verified the FNUZ fix in the first commit: the bug was specifically that the scale divide was being skipped for FNUZ destinations, and this test with non-trivial scales is what caught it.
