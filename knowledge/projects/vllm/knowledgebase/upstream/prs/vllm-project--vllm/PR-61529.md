# [ROCm][Qwen4Exp] Enable fp8 KV and indexer caches on the AMD QSA path

[Upstream PR](https://github.com/vllm-project/vllm/pull/61529) · state: open · merged: False

## Original PR description

## Overview

This PR enables the recipe's two fp8 cache flags on the Qwen4Exp AMD (ROCm) QSA path, mirroring the NVIDIA-side support:

```bash
vllm serve Qwen/Qwen3.8-Flash-Next-FP8 ... \
  --kv-cache-dtype fp8 \
  --attention-config.indexer_kv_dtype fp8
```

Three commits:

1. **`[ROCm][Bugfix] Apply FP8 cache scales to FNUZ destinations in the AMD fused QSA prepare`** — `_to_dst_dtype` divided by the main-attention KV cache scale only for `tl.float8e4nv` (OCP) destinations. On ROCm, FP8 KV caches type as `float8_e4m3fnuz` (Triton `tl.float8e4b8`), so the scale was never applied: FP8-typed destinations received `k_scale`/`v_scale` times the intended magnitude. Latent before this PR (the AMD path restricted KV dtypes to auto/bfloat16), required before FP8 KV can be enabled.
2. **`Support indexer_kv_dtype=fp8`** — wires `--attention-config.indexer_kv_dtype` through `amd/indexer_qsa.py`, mirroring the NVIDIA reference (`fp8` → `torch.float8_e4m3fn` for the compressed key cache and the query side; the raw state cache stays bf16). The fused kernel already handled fp8-typed indexer caches; only the wiring and test coverage were missing (the indexer cells were skipped as "bf16-only").
3. **`Support fp8 main KV cache`** — lifts the remaining dtype gates and reinterprets the uint8 main cache at the boundaries in the platform's native fp8 flavor — **OCP (`float8_e4m3fn`) on gfx950/CDNA4, FNUZ (`float8_e4m3fnuz`) on gfx942/CDNA3** — matching the C++ cache-update op, which follows the platform flavor the same way (`HIP_FP8_TYPE_OCP`), so no C++ changes are needed. The sparse attention kernel gains an `IS_FP8` constexpr with the NVIDIA port's casts (fp8 K upcast to the query dtype for the QK dot; fp8 V to fp16 for the PV dot). A `kv_reads_bypass_flash_attn` class attribute lets the QSA impl skip the FlashAttention library's kv-dtype support check, since QSA reads its cache through its own Triton kernel. The test's `main_fp8` parametrization covers both flavors.

## Claims

- **KV capacity: +33%** at TP1 (2,505,113 → 3,336,874 tokens) with both flags; the main KV cache is the dominant consumer and halves.
- **Quality-neutral** on GSM8K 5-shot (6-run pairs): strict-match 0.899 vs 0.902 baseline; flexible-extract 0.881 vs 0.895 with fully overlapping run ranges.
- **Quality-neutral** on GPQA-Diamond (198 questions, greedy): 0.4596 vs 0.4747 flexible-extract (within the ±3.5 pt binomial SE); NIAH retrieval identical (90/90 at every length and depth, 8K-32K).
- **Greedy outputs byte-identical** on the arithmetic/coherence gates in-session (391 ×3 + a France continuation, temperature 0).
- **Throughput**: decode is unchanged; concurrency-16 aggregate is ~6% lower with both flags (documented tradeoff below — the flags are opt-in, a capacity-vs-concurrency choice).

## The concurrency-16 tradeoff (and where the fix work is)

Decode throughput is unchanged (110.5-110.6 vs 111.0-111.5 tok/s baseline, 7k context / 512 tokens). At concurrency 16, aggregate throughput is ~6% lower with both flags, stable across host load levels:

| config | conc16 aggregate tok/s (×3) |
| --- | --- |
| bf16 baseline (same session) | 509.0 / 510.1 / 508.4 |
| indexer fp8 | 509.1 / 512.1 / 510.6 |
| main KV fp8 only | 491.7 / 510.3 / 497.9 |
| both fp8 | 464-485 across 6 runs and two load levels |

Both flags are opt-in, so this is a capacity-vs-concurrency choice for the operator: +33% KV capacity (more concurrent long-context requests) against ~6% at conc16 on this workload. Where we believe the fix work is:

- The `IS_FP8` cast sites in the sparse attention kernel (`amd/ops/qsa.py`): fp8 K is upcast to the query dtype (bf16) before the QK dot and fp8 V to fp16 before the PV dot, per the NVIDIA port's measurements on its own hardware. On gfx950 the fp8 tensor cores are native, so **revisiting native fp8 QK dots on CDNA4** is the first thing to try — the NVIDIA-side comment's "fp8 QK measured slower and less accurate" does not necessarily transfer to this arch.
- A concurrency-16 profile of the attention kernel to pin the mechanism (decode is unaffected, so the cost only appears under batch).

## Details

- **Flavor design**: the C++ cache-update op selects its fp8 flavor from the platform (`HIP_FP8_TYPE_OCP`: FNUZ on CDNA3, OCP on CDNA4), and the cache is allocated as uint8. This PR reinterprets the cache at the typed boundaries in the same per-arch flavor, so the fused Triton writes, the triton reads, and the C++ unfused-path writes all agree on both arches with zero C++ changes. The `_to_dst_dtype` scale divide covers both flavors (commit 1).
- **Cross-arch scope**: validated end-to-end on gfx950 (MI355X). The gfx942/FNUZ leg is design-consistent and kernel-side-unit-validated (the fnuz flavor cells pass), but a serve-level gfx942 run has not been performed; happy to add one on request.
- **Known gap**: per-tensor dequant scales are not yet folded into the kernels. Default scales are 1.0 and this checkpoint declares no `kv_cache_scheme`, so it is a no-op today; the NVIDIA port's host-side folding (K scale into the softmax scale, V scale as the output scale) is the follow-up if calibrated scales ever matter.
- TP4 notes: the FP8 checkpoint at TP4 on this tree requires `VLLM_ROCM_USE_AITER_MOE=0` and `--disable-custom-all-reduce` (#60839 automates both fallbacks); with those flags both TP4 arms serve and gate correctly.

You're right — the fold is missing. The NVIDIA port solves this by absorbing the scales into the attention math rather than doing an explicit multiply-back: `k_scale` is pre-multiplied into the softmax scale (`softmax_scale = head_dim^-0.5 * k_scale`) and `v_scale` becomes the kernel's output scale, folded into the reciprocal normalizer (with the split-K LSE kept unscaled so the merge stays correct — see `nvidia/ops/qsa.py`).

It's inert on this path today because all three mechanisms that could set non-unit scales are blocked: `set_default_quant_scales` hard-codes 1.0, the layer raises on `quant_config.kv_cache_scheme`, and `--calculate-kv-scales` doesn't participate in QSA. But the write-divide/read-no-multiply pairing is only sound under an invariant nothing enforces.

I've added a fail-fast in `forward_qsa` (87b62b06e8): `NotImplementedError` if fp8 KV and either scale != 1.0, with the message pointing at the NVIDIA fold as the fix. Happy to port the fold in a follow-up if you'd prefer that over the guard.

Checked — deliberate. Unlike the main cache (flavor dictated by the C++ cache-update op, which follows the platform), the compressed indexer cache is a standalone typed tensor that never passes through C++, and its contents are scale-free e4m3 (Q and compressed K are RMSNormed before quantization). The NVIDIA reference also hardcodes `e4m3fn`. The only arch question is Triton `float8e4nv` store/load on gfx942, which the new MI300 CI step exercises — if that fails, switching only the indexer cache to `fp8_dtype()` would be numeric-safe (it's only compared against similarly quantized Q), but parity with NVIDIA wins if CI is green.
