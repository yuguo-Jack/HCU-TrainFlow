# [Bugfix][Frontend] Leave GLM-4.7 array and object tool arguments unpinned

[Upstream PR](https://github.com/vllm-project/vllm/pull/64615) · state: closed · merged: True

## Original PR description



## Overview

The non-strict GLM-4.7 structural tag from #56403 pins array and object tool arguments to JSON. When GLM writes one of those values as text that is not valid JSON, the grammar forces tokens the model rates near zero, and the call can loop until `max_tokens`. This leaves array and object values as raw text, the way string values already are.

## Claims

- Only requests that get the non-strict GLM-4.7 tag change, and only in array and object arguments, plus type lists that contain them. These are `glm47` requests with tools (`tool_choice` auto, required or a named tool), and `ling3` requests with `required`, a named tool, or `--tool-strict-level function`. The value becomes text that ends at `</arg_value>`. Integer, number, boolean, null and enum values keep their JSON pins, and so do argument keys and the call envelope.
- A valid JSON value parses exactly as before. A value that is not JSON reaches the client as the raw string, through the parser's existing fallback (`coerce_to_schema_type`). On main the grammar rules such values out by forcing other tokens instead.
- Strict tools (`strict: true` or `--tool-strict-level parameter`) are unchanged. No other parser uses this tag.
- The change is in `_glm_4_7_value_format` only: 13 lines added and 10 removed, plus tests.

## Details

**Root cause.** `_glm_4_7_value_format` returns `JSONSchemaFormat(json_schema={"type": t})` for every non-string type, arrays and objects included. Two things go wrong inside that element when the model's text is not JSON.

1. After a backslash inside a JSON string, the grammar admits only `" \ / b f n r t u`. GLM-5.3 writes Windows paths with single backslashes. On a captured request ending in `"path": "D:\`, the unconstrained next token is `SV` at p = 0.999998, and the grammar blocks all of the top 20 candidates. Sampling then picks a token the model rates below 1e-9 (`b`). The path fills with invented `\b...` and `\f...` names, and a 20-token cycle forms that top_p 0.95 cannot leave. With `max_tokens` unset, it runs to the context limit.
2. The JSON element has no excludes. When the model over-escapes a key's closing quote (`[{"newText\": ...`), the key string stays open, so `</arg_value>` and `</tool_call>` are read as string text and no stop token is allowed. In one captured turn the model wanted to stop (`<|observation|>` at p = 0.999993 unconstrained) and was forced on to 322 calls. If a later quote closes the key instead, the grammar allows only whitespace or `:`, and the output is whitespace until `max_tokens`.

We saw both in production with GLM-5.3 coding agents. In one afternoon we caught seven looping requests, and six of them were tool calls under this tag. Before #56403 these requests had no grammar. `--tool-strict-level auto` avoids the problem today by dropping the tag for non-strict auto requests, but that also drops the call-envelope constraint.

**Change.** A value keeps a JSON pin only when every type it allows is a scalar (`integer`, `number`, `boolean`, `null`). Anything else gets `AnyTextFormat(excludes=_GLM_4_7_VALUE_EXCLUDES)`, the format string values already use. That covers `array`, `object`, `string`, a missing type, and a type list that includes any of these. A type list with `string` was already free text in practice, because `OrFormat` with free text admits everything the JSON branch admits.

**Tradeoff.** In non-strict mode, array and object arguments lose their shape constraint. A model that writes malformed JSON there now gets it through as a string, which the client sees as an argument of the wrong type. Clients that need the shape enforced can mark the tool `strict: true`. This is the same contract string arguments have.

**Related.** #61205 (open) caps whitespace in these tags at 64 characters. That shortens the whitespace tail in case 2, but the grammar then forces `:` and the broken call continues. This PR removes the JSON element those runs happen in. The two PRs touch the same last line of `_glm_4_7_value_format`, so whichever merges second needs a one-line rebase. #62499 (open) changes when the tag applies alongside `response_format`, a different path. No open PR changes the GLM value formats.
