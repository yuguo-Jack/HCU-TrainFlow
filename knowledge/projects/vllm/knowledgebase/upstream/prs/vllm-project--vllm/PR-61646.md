# [Perf][Attention] Split only the sliding window into Triton split-K decode segments

[Upstream PR](https://github.com/vllm-project/vllm/pull/61646) · state: open · merged: False

## Original PR description

## Overview

In the Triton split-K (3D) decode path of `kernel_unified_attention`, the 16 segments split the
whole sequence, so with a sliding window only 1-2 segments overlap the window once
`seq_len >> window`, and they walk it serially. This PR splits only the window's tiles into the
segments. Sliding-window decode then costs the same at any context length instead of growing
linearly. Complementary to #60418, which routes RDNA sliding-window layers to TRITON_ATTN;
interacts with #56148 (multi-query split-K), see Details.

## Claims

- **Per sliding-window layer, decode on TRITON_ATTN:** the cost no longer grows with context.
  1.57× faster at 4K, 2.73× at 8K, 3.90× at 12K and ~10× at ≥ 32K tokens (window 2048, batch 1,
  cold L2; AMD Radeon AI PRO R9700).
- **End to end, Muse Glimmer 30B, TP=4 on 4× R9700, `--attention-backend TRITON_ATTN`:**
  - TPOT −1.2% at 4K and **−4.9% at 12K** context (c=1);
  - unchanged below the window;
  - GSM8K unchanged.
- **gpt-oss-20b** (window 128, attention sinks; TP=1 on one R9700): correct with sinks;
  sliding-window attention per call 10.3 → 5.0 µs in serving (rocprofv3); TPOT −0.1…−0.3% at
  c=1. The gain is smaller because the window spans only 8-9 tiles.
- **No change where the window does not bound the keys or the path differs:**
  - full attention, context ≤ window (~1% overhead there, see Details);
  - the 2D path, spec-decode verify (`max_seqlen_q > 1`);
  - chunked-local, multimodal-prefix, R-SWA and per-sequence-causal masks.
- **Tests:** two new tests guard that the window layout is actually used and is correct; the
  existing numerical test would not notice it silently turning off.

## Details

**Root cause.** `tiles_per_segment = cdiv(seq_len, NUM_SEGMENTS * TILE_SIZE)` lays the segments
over `[0, seq_len)`. `compute_tile_loop_bounds` then intersects each segment with the window. For
`seq_len >> window` the window falls into one or two segments, each walking up to
`min(window, seq_len / 16)` tokens serially, while the other segments exit. The cost therefore
grows with context until `seq_len = 16 × window`.

**Change.**

- `split_k_segment_layout()` (new, `triton_attention_helpers.py`) returns
  `(base_tile, tiles_per_segment, num_active)`. With `WINDOW_SEGMENTS` the segments cover the
  decode query's window tiles `[⌊max(L−W,0)/T⌋, ⌈L/T⌉)`; otherwise the whole sequence, with the
  same values as before. Both `kernel_unified_attention` and `reduce_segments` call it, so they
  always agree on which segments are active.
- `compute_tile_loop_bounds()` gets an optional `segm_base_tile_or_0` (default 0); other callers
  are unchanged. The kernel's early exit becomes `segm_idx >= num_active`, which is equivalent to
  the previous condition.
- The launcher enables `WINDOW_SEGMENTS` only for the 3D path with `max_seqlen_q == 1`, causal,
  and a plain sliding window: not chunked-local, mm-prefix, R-SWA or per-sequence causal. In
  those cases the window does not bound the keys of a single decode query, or (spec-decode
  verify, enabled in 3D by #56148) there are several queries per sequence. Both kernels receive
  the same flag. `reduce_segments` gets `SLIDING_WINDOW` only when the flag is on, to avoid
  compiling a reduce variant per window size.
- `window_aware_segments: bool = True` on `unified_attention()` forces the old split. The new
  tests and the A/B benchmark use it.

**Tradeoffs and limitations.**

- About 1% slower on SWA layers when the context is shorter than the window: the window-range
  arithmetic runs even when the window covers everything (≈ 0.05 µs of ~5 µs).
- No benefit:
  - for multimodal-prefix models with an image in the batch (`mm_prefix_range` is batch-wide);
  - for the int4 per-token-head KV cache (separate kernel);
  - above the 3D threshold (`128 / KV heads per GPU`);
  - on backends other than TRITON_ATTN.
- On ROCm, plain-SWA models default to ROCM_ATTN unless TRITON_ATTN is selected (or #60418
  applies). Models with sinks (gpt-oss) and mm-prefix models already land on TRITON_ATTN.
- No CPU/GPU synchronization is added: the gate uses only host-side launcher arguments.
- Complexity: +82 / −9 lines outside tests.

**Our case: a speculative-decoding drafter, not single-token decode.** The DFlash2 drafter we run for a Qwen3.8-27B target (R9700 / gfx1201, TP=1) has 5 sliding-window layers (window 2048, 32 Q / 8 KV heads, head 128) that run `kernel_unified_attention` on the 3D path with 8 **non-causal** query tokens per request. Your launcher gate (`max_seqlen_q == 1`, causal) keeps those calls on the whole-sequence split, so past ~32k their window still lands in 1–2 segments.

**What we changed on top of the same idea:** the layout's base tile takes the query span into account, so a block of up to `SHORT_Q_3D_MAX` (8) trailing queries is covered:

```
base_tile = max(seq_len - SLIDING_WINDOW - Q_SPAN + 1, 0) // TILE_SIZE
```

with `Q_SPAN = 1` for single-token decode (your case, same tiles) and `SHORT_Q_3D_MAX` otherwise; non-causal windows are already clamped at `seq_len` by `compute_tile_loop_bounds`. The kernel and `reduce_segments` share one helper so they cannot disagree. Gate: 3D, plain window, `max_seqlen_q <= SHORT_Q_3D_MAX`, no chunked lookback / per-seq causal / mm prefix / R-SWA (same exclusions as yours).

- lobo235 · comment · 2026-11-03T18:45:56Z · [source](https://github.com/vllm-project/vllm/pull/61646#issuecomment-6612553130)

Thanks for the review and for pushing it through CI.

On the CDNA exposure question — here's what I can say precisely, since it's my gate:

**Nothing in the change is arch-conditional**, so a CDNA run that lands on `TRITON_ATTN` does take the new segment layout. But the gate is narrow. `WINDOW_SEGMENTS` is a `tl.constexpr` that is only true for **plain causal sliding-window decode** on the 3D split-K path — so `max_seqlen_q == 1`, a real window bounding the keys, and not spec-decode verify, chunked-local, multimodal-prefix, R-SWA or per-sequence-causal. `test_window_aware_segments_gate` pins each of those off. A full-attention layer is bit-identical: same kernel, same layout, the flag is false.

And on gfx9 you have to get to `TRITON_ATTN` first. In `vllm/platforms/rocm.py` the priority list appends it *after* `ROCM_ATTN`, `ROCM_AITER_FA` and `ROCM_AITER_UNIFIED_ATTN`; the only promotion is the gfx1201/gfx1100 swap, which doesn't apply to you. So CDNA reaches this code only if those are unavailable or someone asks for `TRITON_ATTN` explicitly.

Where I'd expect a CDNA regression if there is one is **not** correctness but the below-window overhead — the window-range arithmetic runs whether or not the window bounds anything, and on R9700 that cost me 0.978–0.998× on SWA layers with context under the window. It's cheap to check: `window_aware_segments=False` gives you an exact A/B inside one process against the same kernel, no rebuild, which is how all the numbers in the description were taken. Worth doing at bs 16 too — that's the one place my own cold-L2 numbers flatten out (0.98–1.02× up to 12K before the gain shows at 32K).

If the overhead does turn out to matter on CDNA, making the flag conditional is a one-line change at the launch site rather than anything structural — happy to add it. Muse Glimmer is the right model to point it at; window 2048 means you need context past ~4K before there's anything to see.
