# [Kernel] Fuse align and sort for small-batch many-expert routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/44167) · state: closed · merged: False

## Original PR description

## Purpose

This PR adds a CUDA fast path for `moe_align_block_size` when routing small batches across many experts.

The existing generic path launches two kernels:

- `moe_align_block_size_kernel`
- `count_and_sort_expert_tokens_kernel`

For decode-like many-expert shapes, the work is small enough to fit in one CTA.

This does not simply widen the existing `moe_align_block_size_small_batch_expert_kernel` from #19572. That kernel uses per-thread per-expert counters, so at `num_experts=256` it needs about 264 KB dynamic shared memory and fails to launch on H800.

- copilot-pull-request-reviewer[bot] · comment · 2026-06-01T07:40:10Z · [source](https://github.com/vllm-project/vllm/pull/44167#discussion_r3332407475)

File: `csrc/moe/moe_align_sum_kernels.cu` · line None

The kernel’s prefix-sum/termination logic implicitly assumes `num_experts < 1024` and also requires the existence of a thread with `threadIdx.x == num_experts` to write `cumsum[num_experts]` and `total_tokens_post_pad[0]`. This breaks for `num_experts == 1024` (no thread 1024 exists) and for any `num_experts > 1024` (only the first 1024 experts participate in the scan). A concrete fix is to either (a) tighten the fast-path guard to `num_experts <= 1023` and fall back otherwise, or (b) rewrite the kernel to compute `cumsum[num_experts]`/`total_tokens_post_pad` without relying on a sentinel thread (e.g., use an inclusive scan and have the last participating thread store the total), and handle `num_experts > blockDim.x` via tiled scans or a different scan strategy.

- copilot-pull-request-reviewer[bot] · comment · 2026-06-01T07:40:11Z · [source](https://github.com/vllm-project/vllm/pull/44167#discussion_r3332407523)

File: `csrc/moe/moe_align_sum_kernels.cu` · line 616

The new mode allocates dynamic shared memory proportional to `num_experts` (`(3*num_experts+1)*4` bytes) *plus* CUB BlockScan temp storage. For large `num_experts`, this can exceed per-block shared-memory limits and cause kernel launch failures. Consider adding an explicit upper bound in the mode guard based on (1) supported `num_experts` for the algorithm (see scan assumptions) and (2) the device shared-memory limit (or at least a conservative cap like `num_experts <= 512/768/1023` depending on expected GPUs), with a safe fallback to the existing kernel when exceeded.
