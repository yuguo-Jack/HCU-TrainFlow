# [Bugfix][Frontend] Stop double-encoding tool call arguments

[Upstream PR](https://github.com/vllm-project/vllm/pull/54964) · state: open · merged: False

## Original PR description

## Purpose

Granite 4 models emit tool call `arguments` already serialized as a JSON string rather than as an object:

```text
<tool_call>{"name": "get_db_config", "arguments": "{\n  \"param\": \"max_connections\"\n}"}</tool_call>
```

The hermes tool parser serializes that value again, so the client receives a JSON string that decodes to another JSON string instead of an object. `_postprocess_messages` in `vllm/renderers/chat_utils/chat_message.py` then decodes it once, finds a `str` rather than a `dict`, and coerces it to `{}` (the guard added in #48922, commit `161ffd37`). The arguments are silently dropped from the replayed conversation history, so multi-turn tool calling loses the previous turn's arguments. The rendered turn 2 prompt, before and after that guard landed:

```text
before: {"name": "get_db_config", "arguments": {"param": "buffer_pool_size"}}
after:  {"name": "get_db_config", "arguments": {}}
```

Server log fingerprint: `Tool call 'X' arguments decoded to str, not a JSON object; coercing to an empty object.`

The fix is in the tool parsers. `granite4_tool_parser.dump_args()` already had exactly this guard, so the quirk was already known upstream; the guard just never made it into hermes. Rather than add a second near-duplicate, this hoists one shared `dump_tool_arguments()` into `vllm/tool_parsers/utils.py` and calls it from both parsers. Both hermes paths are fixed. The streaming path double-encoded by a different mechanism: `_extract_tool_args` regex slices the raw text after `"arguments":`, which for a string-valued argument is the escaped string literal.

Only a string that holds a JSON object or array is unwrapped, so an `arguments` string that is not itself JSON is still serialized and reaches the client as valid JSON. Both paths route that decision through the one `dump_tool_arguments`, so they agree byte for byte. Since JSON validity cannot be judged from a prefix and an unwrap already streamed cannot be retracted, the streaming path returns nothing for a string-valued `arguments` until the literal closes, then applies the same rule; such arguments therefore arrive in a single chunk, while object-valued `arguments`, the normal case, still stream incrementally. Unwrapping only real JSON is a small behavior change for `granite4`, which previously forwarded any string untouched; its own test suite passes unchanged.

`_postprocess_messages` is not changed, so the coercion from #48922 behaves exactly as before. An earlier revision also unwrapped one more level there, to repair histories that already carry double-encoded arguments. That is not needed for this bug and would change a message-processing path shared by every chat request, so the last commit reverts it.

Several other parsers also call `json.dumps` on the model's `arguments` without a string check. Whether any of their models emit string-valued arguments is unverified, so routing them through `dump_tool_arguments` is left as a follow-up.

Related but distinct: #46924 (tool parsers returning nested object arguments as JSON strings).

### Why the existing tests missed this

`tests/entrypoints/tool_parsers/test_hermes_tool_parser.py` serves `ibm-granite/granite-4.0-h-tiny` only with `--tool-call-parser granite4`, and `docs/features/tool_calling.md` recommends that pairing, so hermes with a Granite 4 model is off-doc and untested. `tests/tool_parsers/test_granite4_tool_parser.py` does deliberately exercise string-valued arguments via `create_complex_input(create_string_args=True)`, so the model quirk was covered, but only for the one parser that already handled it. Separately, no test replays a parser's own output back as assistant history, which is the path that actually breaks; the server-level tests assert on the first response only.

Adding an "arguments arrive already serialized" case to `tests/tool_parsers/common_tests.py` would codify this for every parser, but it is left as a follow-up: `test_hermes_tool_parser.py` does not use that mixin, so it would not have caught this bug, and the shared config would need a new required field in all 7 files that do. The new non-streaming tests here do run against both the hermes and granite4 parsers, through the parametrized fixture that file already has.

## Test Plan

Unit tests, model-free:

```bash
pytest tests/tool_parsers/test_hermes_tool_parser.py
pytest tests/tool_parsers/test_granite4_tool_parser.py   # guards the shared helper
```

New cases: a string-valued `arguments` returns single-encoded JSON, non-streaming and streaming at stream intervals 1, 2, 3 and 5; a bare non-JSON string argument still arrives as valid JSON; streaming output equals non-streaming output for string-valued arguments, including strings that only look structured (`{hello world}`, `[oops`, `{"a": 1} tail text`).

End to end: `granite-4.0-h-small` in bf16 on one Intel Gaudi 3 card, served with `--enable-auto-tool-choice --tool-call-parser hermes`, running a 3-turn scenario in which turns 2 and 3 are elliptical follow-ups on the same tool, so the model has to read the previous call's arguments out of the conversation history.

`arguments` on the wire for turn 1:


Streaming and non-streaming output were then compared directly on 5 string-valued `arguments` payloads at 2 stream intervals, including three that only look structured. All 10 agree and are valid JSON; on the first version of this PR, 6 of the 10 disagreed and delivered invalid JSON, which is what the third commit fixes.

The double-encoding fix is real and regression-proven. I checked out head 9e2ce7f4f9 and ran the PR's own new tests on the base worktree (origin/main 80389cf): all 7 new tests FAIL on base (6 hermes parser tests + 1 chat_utils double-encoded test) and PASS on head; the granite4 suite and neighboring chat_utils tests pass unchanged. `_postprocess_messages` unwrap logic is careful (#48922 guard preserved: `"hello"` still coerces to {}, and the new `'"42"'`/`'"true"'`/`'"[]"'` parametrizations confirm double-encoded non-objects still fall through to coercion).

One inconsistency I found between the two fixes, both verified by execution on head:

**Streaming `_extract_tool_args` unwraps ANY decoded string whose first char is `{`/`[`, even when the content is not valid JSON — while non-streaming `dump_tool_arguments` requires a successful `json.loads`. Same input, different output paths.**

hermes_tool_parser.py:206 uses `decoded.lstrip()[0] in "{["` as the unwrap test, but utils.py:163 (`dump_tool_arguments`) uses `json.loads` + isinstance(dict,list). A string argument that merely *starts* with a brace but is not JSON (e.g. a model emitting `"{hello world}"`, `"[oops"`, or `"{\"a\": 1} tail text"`) is:
- non-streaming: kept as a quoted string `'"{hello world}"'` (valid JSON string) — correct;
- streaming: unwrapped to bare `'{hello world}'` / `'[oops'` / `'{"a": 1} tail text'` — **invalid JSON delivered to the client**, and a change from base behavior (base delivered the quoted string in both paths).

The PR body's own claim ("Only a string that holds a JSON object or array is passed through, so an arguments string that is not itself JSON is still serialized and reaches the client as valid JSON") holds for the non-streaming path but not the streaming one. Since a tool call's `arguments` must be parseable JSON for the client, this matters for exactly the class of quirky models this PR is defending against.

Suggested direction: in the streaming path, gate unwrapping on a real parse when the data is available — e.g. when `is_complete` and the decoded value round-trips through `json.loads` as dict/list, unwrap; otherwise keep the quoted literal. For partial streams the string may not yet be decidable, but a string whose decoded content never becomes valid JSON should end up quoted, matching the non-streaming behavior. Worth a parametrized test comparing streaming vs non-streaming output on non-JSON brace-leading strings.

Thanks, this is a real bug and I reproduced it independently before touching anything. Probing head against base with `arguments` values `{hello world}`, `[oops` and `{"a": 1} tail text`, at stream intervals 1, 2, 3, 5 and one shot: 15 of 15 streaming results differed from non-streaming and were invalid JSON, against 0 of 15 on base. My own monotonicity probe missed the class because every payload I had checked held either valid JSON or text with no leading brace.

Fixed in 0eb73d6, taking the stronger version of your suggestion. Rather than add a second JSON test to the streaming path, the streaming path now defers to `dump_tool_arguments`, the same function the non-streaming path uses:

```python
if raw.startswith('"'):
    if not is_complete:
        return None
    try:
        decoded = json.loads(raw)
    except json.JSONDecodeError:
        return None
    return dump_tool_arguments(decoded)
```

The two paths now agree by construction rather than by two rules that happen to coincide. `decode_json_string_prefix`, which the previous version needed in order to decode partial literals, is gone.

On the "for partial streams the string may not yet be decidable" half: I do not think an incremental unwrap can be made safe here. `_compute_args_diff` diffs by length prefix, so an unwrap already sent cannot be retracted, and JSON validity is not knowable from a prefix. Gating on a partial parse would not fix `{"a": 1} tail text` either, because at the point where the decoded prefix is `{"a": 1}` the partial parse succeeds and the unwrap is already on the wire. It would also make the outcome depend on token boundaries, so the same input would behave differently at different stream intervals. Hence waiting for the closing quote: string-valued `arguments` now arrive as a single chunk, while object-valued `arguments`, the normal case, keep streaming incrementally.

Your suggested test is in as `test_hermes_streaming_string_arguments_match_non_streaming`: it asserts that streaming output equals non-streaming output and is valid JSON, parametrized over your three payloads plus a valid serialized object and a bare string, at intervals 1 and 3. On the previous head it fails 6 of 10, exactly the three brace-leading payloads at both intervals, and passes the two controls; on the new head all 10 pass. The file is 50 passed, 1 skipped; `test_chat_utils.py -k tool` 16 passed; the granite4 suite 4 passed. End to end on the same Gaudi 3 server the 3-turn scenario is still 3/3, and `stream=True` still returns single-encoded arguments, now in one chunk instead of eleven.

I have also corrected the PR description, which stated the valid-JSON guarantee as though it already applied to both paths.
