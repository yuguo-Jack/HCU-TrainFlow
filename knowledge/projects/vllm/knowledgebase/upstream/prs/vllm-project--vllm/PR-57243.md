# [Bugfix][Frontend] Support scalar priority and wire priority into LLM.chat()

[Upstream PR](https://github.com/vllm-project/vllm/pull/57243) · state: closed · merged: True

## Original PR description

## Purpose

`OfflineInferenceMixin._add_chat_requests` accepts a priority and applies it:

```python
seq_priority = self._priority_to_seq(priority, len(seq_convs))
```

Its only caller, `_run_chat`, has no `priority` parameter and never passes one, and
neither does `LLM.chat()`. `LLM.generate()`, `LLM.enqueue()` and `LLM.enqueue_chat()`
all expose it, so the value is plumbed the whole way down and is reachable from every
offline entrypoint except this one:

```
>>> llm.chat(messages, priority=1)
TypeError: LLM.chat() got an unexpected keyword argument 'priority'
```

A second defect sits in the same class. `_priority_to_seq` calls `len(priority)`
whenever priority is not `None`, so a single value fails even for a single prompt:

```
>>> llm.generate("Hello", priority=1)
TypeError: object of type 'int' has no len()
```

Its two siblings, `_params_to_seq` and `_lora_request_to_seq`, both test
`isinstance(x, Sequence)` first and broadcast a scalar with `[x] * num_requests`.
`_priority_to_seq` is the only one of the three without that branch.

Normalising `None` to `0` first leaves the rest of its body identical to those two.
Existing callers are unaffected: a list is still length-checked and paired one by one
with the prompts, and `None` still yields `[0] * num_requests`.

The scalar half is the looser of the two, since the annotation did say `list[int]`.
Happy to drop it and keep this to the `LLM.chat()` gap.
