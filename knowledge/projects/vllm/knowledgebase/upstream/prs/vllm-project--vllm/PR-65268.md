# [Feature] Segment attention layout for one-pass multi-candidate scoring

[Upstream PR](https://github.com/vllm-project/vllm/pull/65268) · state: open · merged: False

## Original PR description

## Overview

Some scoring workloads read one shared prefix against many candidates: a cross-encoder or listwise reranker scoring one
query against N documents, or a decision model answering N questions about one state. Today each candidate is a separate
request, so the prefix is encoded N times. For encoder-only (non-causal) models prefix caching cannot help, because
bidirectional keys depend on the whole prompt.

This PR adds an opt-in **segment attention layout** for encoder-only models. The prompt is the prefix followed by the
candidates, read in one forward:

- the prefix attends to itself;
- each candidate attends to the prefix and to itself, never to another candidate;
- each candidate's positions restart right after the prefix, so it sees the positions it would see in a
  `prefix + candidate` prompt;
- the output has one row per candidate (the mean of its contextual token states).

Request it with a pooling parameter on the `token_embed` task:

```python
from vllm import LLM, PoolingParams
from vllm.pooling_params import SegmentLayoutParams

llm = LLM(
    model,
    runner="pooling",
    pooler_config={"task": "token_embed"},
    attention_backend="FLEX_ATTENTION",
)
ids = prefix_ids + [t for c in candidate_ids for t in c]
out = llm.encode(
    [{"prompt_token_ids": ids}],
    pooling_params=PoolingParams(
        segment_layout_params=SegmentLayoutParams(
            [len(prefix_ids)] + [len(c) for c in candidate_ids]
        ),
    ),
    pooling_task="token_embed",
)
# out[0].outputs.data: [num_candidates, hidden_size]
```

The online `token_embed` request takes the same field (`"segment_layout_params": {"segment_lengths": [...]}`) for
token-id prompts.

Changes:

| area | change |
|---|---|
| `vllm/pooling_params.py` | `SegmentLayoutParams(segment_lengths)`; `PoolingParams.segment_layout_params`, `token_embed` only, not with late chunking / late interaction, encoder-only models, skips prefix-cache reads |
| `vllm/v1/engine/input_processor.py` | lengths must sum to the prompt length; requires the V2 model runner and `FLEX_ATTENTION` |
| `vllm/v1/worker/gpu/model_states/encoder_only.py` | per-request segment ids and restarted positions; positions passed as a model-input override, segment ids into the encoder attention metadata |
| `vllm/v1/attention/backend.py` | `CommonAttentionMetadata.encoder_segment_ids` (optional, `None` unless a request in the batch has a layout) |
| `vllm/v1/attention/backends/flex_attention.py` | encoder-only mask: same request AND (key in segment 0 OR key in the query's segment); unchanged when no layout is present |
| `vllm/model_executor/layers/pooler/tokwise/heads.py`, `special.py` | per-candidate mean pooling in the token embedding head (same path as late chunking) |
| `vllm/entrypoints/pooling/token_embed/protocol.py` | `segment_layout_params` request field |

Requests without the parameter, other attention backends, and decoder models are unaffected.

## Claims

- The layout is exact with respect to its definition: each candidate's output equals a forward of the full prompt with
  the isolating mask and restarted positions (tested against a Transformers reference with an explicit mask).
- The outputs equal N separate `prefix + candidate` forwards **only for models trained with this layout** (or whose
  prefix does not attend to later tokens). For an ordinary bidirectional encoder, a separate read lets the prefix attend
  to the candidate, which this layout does not.
- No change for requests that do not set the parameter.

## Benchmark

`benchmarks/benchmark_segment_layout.py`, `BAAI/bge-base-en-v1.5`, BF16, `token_embed`, random token ids. Packed = one
request per group with `segment_layout_params` (FLEX_ATTENTION); separate = N `prefix + candidate` requests with the
default backend (FLASH_ATTN). Latency: median of 20 single-group reads. Throughput: 32 groups at once.

NVIDIA L40S:

| prefix x candidate tokens | N | packed latency | separate latency | packed cand/s | separate cand/s |
|---|---|---|---|---|---|
| 256 x 32 | 4 | 7.0 ms | 9.0 ms | 1,735 | 974 |
| 256 x 32 | 16 | 8.9 ms | 16.2 ms | 8,897 | 1,629 |
| 256 x 32 | 64 | 9.8 ms | 48.2 ms | 10,355 | 1,737 |
| 32 x 128 | 4 | 8.7 ms | 6.5 ms | 2,838 | 2,267 |
| 32 x 128 | 16 | 8.9 ms | 11.1 ms | 3,739 | 2,589 |
| 32 x 128 | 64 | 15.7 ms | 34.6 ms | 3,887 | 2,961 |

The gain grows with the prefix share of the tokens: with a long prefix and short candidates, N = 64 is 4.9x faster per
group and 6.0x higher in candidates per second; with a short prefix it is 2.2x and 1.3x, and N = 4 is slower than
separate reads (FlexAttention vs FlashAttention for short sequences).

NVIDIA GB200 (one GPU):

| prefix x candidate tokens | N | packed latency | separate latency | packed cand/s | separate cand/s |
|---|---|---|---|---|---|
| 256 x 32 | 4 | 8.0 ms | 11.8 ms | 2,534 | 2,582 |
| 256 x 32 | 16 | 10.9 ms | 15.4 ms | 10,457 | 3,506 |
| 256 x 32 | 64 | 11.9 ms | 29.0 ms | 17,223 | 4,268 |
| 32 x 128 | 4 | 10.6 ms | 9.1 ms | 3,288 | 3,291 |
| 32 x 128 | 16 | 10.9 ms | 14.4 ms | 6,763 | 4,884 |
| 32 x 128 | 64 | 12.3 ms | 22.8 ms | 8,482 | 5,360 |

On GB200, N = 64 is 2.4x faster per group and 4.0x higher in candidates per second with a long prefix, and 1.9x and
1.6x with a short prefix.
