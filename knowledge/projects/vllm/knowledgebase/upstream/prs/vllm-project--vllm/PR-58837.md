# [Perf][Scheduler] Add risk-aware prefix-cache admission

[Upstream PR](https://github.com/vllm-project/vllm/pull/58837) · state: open · merged: False

## Original PR description

## Purpose

Related to #48485. This is an opt-in admission-side approach to prefix-cache
reuse loss under constrained KV capacity. It does not implement the issue's
proposed waiting-queue-informed eviction policy; block eviction remains unchanged.

Before allocating blocks for a fresh waiting request, the risk policy inspects
the free-block queue against estimated full-prompt block demand, excluding the
candidate's own cache-hit blocks. Potential cached-block exposure triggers
ranking of a bounded waiting window by cached-prefix length.

- Skip policy lookups when no admission slot is available, including slots held
  by paused streaming sessions.
- Recompute a promoted head's cache hit and allocation demand before allocation.
- Allow at most one risk-ranking attempt per admission position.
- Bound free-queue inspection; an inconclusive scan does not reject admission.

The window defaults to zero, leaving the policy disabled. The risk path currently
uses the custom scheduler entry point; selecting a nonzero window alone on the
base scheduler enables the threshold-based path instead. For the risk path, set:

```python
scheduler_cls="vllm.v1.core.sched.qwenfuse_risk.RiskPerfScheduler"
cache_aware_admission_window=16
enable_prefix_caching=True
async_scheduling=False
```

The supported risk-policy scope is synchronous FCFS with local prefix caching
and a single full-attention KV group. KV connectors, LoRA, encoder-decoder
models, speculative/lookahead decoding, and prefix replay are excluded by the
current guard. The risk subclass uses exposure, rather than the configured
legacy usage threshold, as its ranking trigger.

## Test Plan and Current Results

Validated after integrating upstream main at
`e5f3d08d722870a5301560fad0cfa65b7e333900`. The update adapts risk admission
to the upstream KV-holding waiting queue and deferred-request handling.
It retains upstream queue priority, avoids popping an admitted request twice,
and resets the bounded ranking retry when the admission position advances.
The change relative to that main snapshot remains confined to nine scheduler,
configuration, KV-manager, and test files.

```bash
.venv/bin/python -m pytest tests/v1/core/test_scheduler.py -q --tb=short
.venv/bin/python -m pytest tests/v1/core/test_scheduler.py   -k 'cache_aware_admission or risk_admission' -q --tb=short
```

- Targeted admission regression: **25 passed**. Three added tests cover
  KV-holding request priority, risk rechecking after a successful admission,
  and risk rechecking after a promoted request is skipped.
- Full scheduler regression: **220 passed, 2 failed**. Both failures reproduce
  on unmodified target main in the same single-GPU environment:
  `test_async_scheduling_pp_allows_rescheduling_with_output_placeholders`
  and `test_diffusion_read_deferral_keeps_a_longer_pp_wait` fail GPU-count
  validation for PP=2 and PP=3 respectively. They were not skipped or
  reported as passing.
- Local style and type checks: **passed** on all nine changed Python files, using the applicable upstream hooks, including Ruff, typos, mypy for Python 3.10-3.13, SPDX headers, and Buildkite test tethering.
- Qwen3-8B BF16 / FlashAttention 2 eager smoke passed with the risk policy,
  APC, chunked prefill, window 4, and a 4 GiB KV budget. One warmup request
  and two subsequent requests completed with 8 output tokens each;
  the repeated prompt reused **224 cached tokens**.

This validation used the updated Python source with the existing Python
3.12.14 / PyTorch 2.13.0+cu130 environment and September 20 native extensions
on an A100-PCIE-40GB. It is not a fresh native build or new performance result.
The eager smoke does not establish CUDA Graph execution, model-quality
equivalence, or multi-GPU compatibility.

## Historical Performance Results

Measurements on commit `27757dde`, A100-PCIE-40GB, Qwen3-8B BF16,
FlashAttention 2, with APC and chunked prefill enabled. Baseline and risk-policy
runs used the same operator configuration; only the admission policy differed.

For the constrained 8 GiB random mixed fixed-burst workload:

- Median throughput improvement: **5.02%**.
- Median batch completion time reduction: **4.78%**.
- Five of six paired comparisons improved; throughput changes ranged from
  **-2.37% to +6.12%**.
- Sufficient-capacity and all-cold controls showed near-zero median changes.
- Cold-request TTFT increased substantially for one seed.

These are historical fixed-burst measurements, not sustained-serving results
or performance measurements on the current submitted head.

## Known Limits and Review Questions

- Cached-prefix ranking can delay cold requests; the current implementation
  does not provide an aging mechanism or a bound on waiting time.
- A bounded waiting window cannot discover reusable prefixes beyond that window.
- Exposure is a snapshot-based estimate, not proof that a particular waiting
  request's reusable prefix will be evicted. Decode growth and future frees
  are not predicted.
- Scheduler CPU overhead, sustained-load fairness, and updated-head performance
  still need measurement. No overhead-neutrality or starvation-free guarantee
  is claimed.
- The current integration uses a custom scheduler subclass and retains the
  threshold-based base path. Feedback on the preferred upstream configuration
  and integration surface is welcome.
