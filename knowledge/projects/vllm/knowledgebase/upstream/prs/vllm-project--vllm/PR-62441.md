# [Feature][MoE] Support explicit row layouts for routed-expert capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/62441) · state: open · merged: False

## Original PR description

## Overview

Allow MoE backends to describe physical routing rows through an optional capture layout instead of replacing the shared capturer. Relates to #61539 and preserves the default restoration introduced by #61388.

## Claims

- Optional process-group shard sizes and ordered source spans restore uneven TP shards and skip interior padding.
- Layout metadata passes through the router before EPLB mapping, so capture retains logical expert IDs.
- Calls without a layout retain the default restoration and previous callback/selection signatures. Empty capture ranges still participate in the supplied collective.

## Details

For physical shards `(7,7)`, `source_ranges=((0,3),(7,2))` records five rows in token order and skips padding between shards. Backends construct this metadata where physical ownership is known; upstream performs gather/select/write. No model, scheduler or model-runner changes are included.

The existing default restoration helper is unchanged. This does not duplicate #61388: it adds an explicit contract for backend row layouts that cannot be inferred from shape alone. No open implementation PR for #61539 or capture-layout support was found during duplicate checks.

The prototype takes a raw `torch.distributed.ProcessGroup`; a vLLM communication abstraction is an alternative for review. The group's backend must support the supplied shard shapes. All ranks must supply compatible collective plans, and sizes/ranges must stay stable across graph replay. No Python communication hook or new host read of accelerator tensor values is introduced.
