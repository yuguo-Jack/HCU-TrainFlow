# [Feature][MoE] Use explicit forward-context layouts for routed-expert capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/62441) · state: open · merged: False

## Original PR description

## Overview

Use explicit forward-context layouts for all routed-expert capture paths, replacing shape-based restoration. This follows the review on #62441 and addresses the backend layout differences discussed in #61539.

## Claims

- Providers return per-layer layouts directly, after the runner activates the forward context and prepares backend metadata. Built-in DP/SP construction is an optional helper, not a required backend policy.
- Keep `capture()` and router selection signatures unchanged. Capture reads its layer's layout from `ForwardContext` and uses `GroupCoordinator.all_gatherv()` when needed.
- Ordinary MoE uses `MoERunner` as its layout provider; native MegaMoE uses `DeepGemmMegaMoEExperts` through the same interface. Kimi and DeepSeek declare their existing input SP partition count at construction; no per-forward arguments are added.

## Validation

On the current forward-context revision (macOS arm64, CPU environment):

```bash
.venv/bin/python -m pytest \
  tests/model_executor/test_routed_experts_capture.py \
  tests/v1/worker/test_gpu_ubatch_slicing.py \
  -q --disable-warnings --maxfail=1
```

- **99 passed, 10 skipped**. Coverage includes DP/SP restoration, uneven/empty shards, ordered spans, full-buffer writes, repeated forwards, missing/duplicate layouts and DBO offsets. Custom providers use active-context metadata to restore uneven or internally padded shards on both ranks without the built-in helper; the DBO test checks that providers see the microbatch context.
- The MegaMoE provider test uses its real constructor and checks the default unsharded input and both SP=2 ranks against the full capture buffer. Hardware checks and collectives are mocked; it does not execute the MegaMoE kernel. The test failed before the provider was added.
- Earlier checks of this forward-context implementation rejected six in-memory mutations: skipping the collective for empty ranges, using the wrong DP rank, writing to the wrong layer, dropping the DBO offset, replacing provider layouts with the default policy, and failing to activate the microbatch context.
- Applicable pre-commit hooks and `git diff --check` pass. Collectives are mocked at the communication boundary.
- **GPU model execution, real collectives and graph replay have not been validated for this refactor.** The GPU-only DBO tests remain in the suite; the DeepSeek V4.1 replay-context test also requires GPU execution. Earlier device results below apply to prior revisions only.

## Details

The capturer now has one layout-based gather/select/write path; `_restore_local_topk_ids` and router layout forwarding are removed. This extends the restoration work in #61388 rather than introducing a parallel capture implementation.

Capture binding registers provider modules on the target model. The collector calls each provider's `get_routed_experts_capture_layouts(num_tokens_across_dp, dp_rank)` explicitly. Before a forward, the runner activates its context, calls the providers and stores their layouts by layer ID. Missing or duplicate layer declarations fail before model execution. DBO and DeepSeek V4.1 internal replay activate their own contexts; graph recording uses the recorded execution sizes. Replacing registered modules requires rebinding.

The intermediate `Spec` is removed. Built-in providers reuse `make_routed_experts_capture_layout()` for DP-major / even-SP placement; other backends return `RoutedExpertsCaptureLayout` directly through the same interface, without replacing the capturer. Providers may share a layout across their layers; automatic cross-provider deduplication is not required. The integration contract and a padded-shard example are documented in `docs/training/routed_experts.md`.

All participating ranks must agree on the collective plan, including empty shards, and the communicator must support the supplied sizes. Metadata must stay stable across graph replay.

Moving per-layer gathers to snapshot time remains out of scope. No end-to-end performance improvement is claimed.

- aoshen02 · comment · 2026-10-28T08:15:53Z · [source](https://github.com/vllm-project/vllm/pull/62441#issuecomment-6464075260)

Thanks for tackling this. A few suggestions to make the explicit layout the only path rather than a second one:

1. Replace `_restore_local_topk_ids` instead of keeping it as the fallback. If the default path also describes its layout explicitly (DP slice, even SP shards), there is one mechanism, and row-count guessing goes away for every backend.
2. Keep `capture()` and the router / `select_experts` signatures unchanged; no `capture_layout` argument through the router.
3. Let whoever creates the layout set it once per step in the forward context (physical `shard_sizes` plus a logical-to-physical row map), validated once per step instead of on every layer. vllm-ascend can fill it from its own runner, so main needs no backend-specific code.

Moving the per-layer gather out of the CUDA graph (one gather per step at snapshot time) is a pre-existing issue on main and out of scope here; with the layout carried in the forward context, that can be a follow-up confined to the capturer.
