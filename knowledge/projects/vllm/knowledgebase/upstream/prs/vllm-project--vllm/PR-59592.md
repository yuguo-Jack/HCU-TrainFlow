# [Bugfix][KV Connector] Mooncake: reject mismatched block sizes in the handshake

[Upstream PR](https://github.com/vllm-project/vllm/pull/59592) · state: open · merged: False

## Original PR description



## Overview

`MooncakeConnector` now exchanges the KV cache block size in the transfer handshake, and the producer rejects a consumer whose block size differs with an error that names both sizes.

## Claims

- A prefill/decode pair with different block sizes fails with `Mooncake requires the same KV cache block size on prefill and decode, but prefill uses 1568 tokens and decode uses 784. Set --block-size to the same value on both.` instead of an unrelated region-length error.
- Peers that do not send the new field are still accepted, so mixed versions keep working.

## Validation

- New tests: `test_block_size_mismatch_error` and `test_send_kv_to_decode_rejects_block_size_mismatch`. `test_receive_kv` now also checks that the consumer sends its block size. The rejection test fails without the check.
- `pytest tests/v1/kv_connector/unit/test_mooncake*.py`: 475 passed.
- pre-commit hooks pass on the changed files.
- End to end: Qwen3.8-Flash-Next (hybrid GDN + attention, 2 KV heads), P TP2 → D TP4 over Mooncake/RDMA. Without a common block size every pull failed with `Mooncake KV region length mismatch for homogeneous TP at region 12: local=1605632, remote=802816`. With `--block-size 1568` on both instances, GSM8K (200 questions, 32 in flight) scored 0.985, the same as the TP2 → TP2 pair. This run used the connector with #53078 applied.

## Details

Block IDs only name the same tokens when both sides use one block size, and the transfer plan assumes they do: the producer maps the consumer's logical block IDs with its own block size. Mooncake never compared the two.

For hybrid models the block size is not a user choice by default. The platform raises the attention block size until an attention page holds the largest Mamba state, and that state shrinks with TP. In the run above, TP2 picked 1568 tokens and TP4 picked 784. Both instances were started with the same flags, and the only error was a region-length mismatch that does not mention block size.

The check runs on the producer, next to the existing PP-compatibility check, and returns the usual `ERROR` response, so the consumer logs it on the failed pull. It compares `cache_config.block_size`, the logical size that the scheduler's block IDs are expressed in.

Pairing different block sizes is out of scope. NIXL supports some of those cases through `block_size_ratio`; Mooncake would need the same per-region remapping.

Related: #53078 (Mooncake heterogeneous TP for hybrid GDN models), where this mismatch showed up. #58525 changes which local block size the connector uses for transfers; this PR only compares the scheduler block size across the pair, and does not depend on it.
