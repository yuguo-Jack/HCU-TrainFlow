# [Bugfix][Benchmark] Keep oversampled request IDs unique after filtering

[Upstream PR](https://github.com/vllm-project/vllm/pull/64537) · state: open · merged: False

## Original PR description



## Overview

Fix benchmark oversampling aborting with `Duplicate request_id` after dataset filtering. For example, retained Blazedit row IDs `bench-0`, `bench-3`, and `bench-4` collide with new IDs previously allocated from the retained request count.

## Claims

- Skip existing request IDs when assigning IDs to additional samples.
- Preserve original requests, prefixes, payloads, and seeded sample selection; continue rejecting duplicate input IDs.
- Add dataset regressions, a real-server benchmark regression, and a Blazedit documentation note.

## Details

Filtering retains original row indices as request IDs. The shared helper now advances its monotonically increasing ID counter past IDs already in the input. It continues drawing from the same original requests with the same random seed and number of random choices. The final duplicate-input check remains intact.

The new CPU suite checks consecutive collisions, contiguous IDs, empty/custom prefixes, `--no-oversample`, payload preservation, seeded selection, and genuinely duplicated inputs. The server regression verifies that filtering and oversampling still complete the requested benchmark workload. Both suites are selected by the existing benchmark CI step.

Duplicate-work checks were refreshed before submission using `oversample request_id`, `"Duplicate request_id"`, `"maybe_oversample_requests"`, `"request IDs" oversample`, `oversampling`, and `Blazedit`. No competing fix was found. Related #48369 concerns a prefix-cache analyzer; #50810 adds dataset wrappers/tests and does not change this ID allocation.
