# [ROCm][Perf] Keep 32-bit buffer addressing for per-token-head KV and AITER cross-attention fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/64317) · state: closed · merged: True

## Overview

<!-- Summarize the change in 1-2 lines. Link relevant issues and PRs. -->

Follow-up to #60084. On ROCm, two more paths now give their KV-cache views a Triton `ptr_range()`, so Triton's AMD backend keeps 32-bit buffer addressing for them:
- the per-token-head quantized KV cache (`int8_per_token_head`, `fp8_per_token_head`) in `TRITON_ATTN`;
- the non-causal fallback of `ROCM_AITER_UNIFIED_ATTN`, which runs vLLM's `kernel_unified_attention` for encoder-decoder cross-attention.

Updated to current `main`, which now includes the extensible KV cache (#56492). How the two interact is described under Details.

## Claims

<!-- State the accomplishments in a few concrete bullets: speedups, feature support, bug fixes, etc. -->

- Throughput on Radeon Pro W7900 (gfx1100), current `main`, default settings:
  - **+56%** for Qwen2.5-7B-Instruct, `TRITON_ATTN` with an `int8_per_token_head` KV cache: 1.93 → 3.02 req/s.
  - **+60%** for Qwen2.5-7B-Instruct with an `fp8_per_token_head` KV cache: 2.01 → 3.22 req/s.
- When the extensible KV cache is off (V1 model runner, explicit `kv_cache_memory_bytes`, or no VMM support):
  - **+49%** for gpt-oss-20b with an `int8_per_token_head` KV cache: 2.46 → 3.66 req/s.
  - **+1%** for Whisper-large-v3 on `ROCM_AITER_UNIFIED_ATTN`: 6.88 → 6.95 req/s.
- No regressions: AITER's own causal kernel is not touched, and the other workloads measured are unchanged.
- No accuracy change: Whisper transcripts are token-identical, and GSM8K with per-token-head KV caches (Qwen2.5-7B, gpt-oss-20b) is within run-to-run noise.
- 6 lines in two files; no new configuration.

- **Code generation** (Triton cache of each run, current `main`):
  - Per-token-head (Qwen2.5-7B): `key_cache_ptr`, `value_cache_ptr`, `k_scale_cache_ptr` and `v_scale_cache_ptr` carry `tt.pointer_range = 32` in `kernel_unified_attention` and `_reshape_cache_per_token_head`.   - gpt-oss-20b with the extensible KV cache off: split-KV decode variants 255/256 → 156/167 VGPRs (INT8).

- **No new tests:** the change only affects code generation, and CI has no RDNA runners.

## Details

<!-- Explain motivation, design decisions, root cause, tradeoffs, and limitations concisely. Link or collapse lengthy supporting material. -->

**Root cause.**
- #60084 fixed the 32-bit addressing loss caused by #51718's single KV-cache allocation, but only for the K/V views built in `TritonAttentionImpl.forward` and `do_kv_cache_update`.
- The per-token-head path builds its views in `_pth_key_value_caches()`. Its per-(token, head) scale caches are strided float32 views of the same storage.
- The AITER backend calls `kernel_unified_attention` directly for non-causal attention.
- In all these cases Triton's `is_within_2gb` saw the whole allocation and chose 64-bit addressing.

**Change.**
- `TritonAttentionImpl`, on ROCm (existing `_set_kv_ptr_range` flag):
  - `_ensure_scale_caches()` sets the bound once on the two scale caches when it creates them;
  - `_pth_key_value_caches()` sets it on the K/V views on every call.
- `RocmAiterUnifiedAttentionImpl.forward` sets it on the K/V views right before the non-causal fallback call.
- All reuse `set_triton_ptr_range` from #60084; the bound is the distance from each view's `data_ptr()` to the end of the layer's region.

**Interaction with the extensible KV cache (#56492).**
- Until warmup ends, each layer's view spans the layer's whole *reservation*; CUDA graphs are captured in this phase. After `extend_kv_cache`, `committed_views()` rebinds each layer to storage of exactly its committed blocks.
- Eager launches after the extend therefore get 32-bit addressing without any hint (Whisper above: base = PR). The fallback hint still matters when the extensible cache is off.
- Kernels captured in CUDA graphs keep the binary compiled during warmup. When a layer's reservation is ≤ 2 GiB (Qwen2.5-7B), this PR gives them 32-bit addressing. When it exceeds 2 GiB, nothing can: gpt-oss-20b INT8 here reserves 126,664 blocks × 17,408 B = 2.05 GiB per layer, while the committed size is 1.64 GiB. Traced inside the engine, the hint reports 2.054 GiB during capture and 1.641 GiB afterwards, and Triton correctly refuses the first.
- This also affects #60084, is independent of this PR, and is better handled separately.

**Safety.**
- The scale and K/V offsets the kernels compute are non-negative and stay within the layer: block-table index × block stride + slot/head/channel offsets.
- Triton still checks the bound against 2 GiB at every launch. `set_triton_ptr_range` reads only shapes, strides and `data_ptr()`; it never touches uncommitted memory.
- The INT4 per-token-head kernel and AITER's causal kernel are unchanged.

**Limitations.**
- Measured on RDNA3 only.
- Not covered:
  - `TRITON_MLA` / AITER MLA `decode_attention_fwd`, which reviewers of #60084 measured a CDNA gain on; left for a separate PR;
  - `TritonAttentionDiffKVImpl` and the gfx1250 shuffled-KV Triton cache write.

**Duplicates.** I searched open and closed PRs and issues for `ptr_range`, `set_triton_ptr_range`, per-token-head + `ptr_range`, and AITER cross-attention; only #60084 overlaps.
