# [Feat] Add HALOps as an opt-in MXFP8 GEMM backend for Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/65099) · state: open · merged: False

## Original PR description



## Overview


Add [HALOps](https://github.com/PaddlePaddle/HALOps) as an opt-in MXFP8 W8A8 dense-GEMM backend for Blackwell (SM100), selected with `--linear-backend halops`. An MXFP8 MegaMoE online-quantization path lets a BF16 checkpoint run with MXFP8 experts (canonical per-32 UE8M0 scales) without pre-quantized expert weights or scales.

## Claims


- New opt-in `halops` linear backend: W8A8 MXFP8 `dense_gemm` plus the fused `group_wise_quant` activation quantizer, wrapped in one CUDA-graph-safe custom op. Defaults are unchanged: `auto` keeps HALOps last in the CUDA MXFP8 priority list and the package is imported lazily.
- Accuracy parity with the DeepGEMM dense MXFP8 baseline on the full GSM8K test set (1319 questions, 5-shot, greedy): 0.884 / 0.889 / 0.8787 vs. 0.873 / 0.8757 / 0.8802.
- End-to-end throughput within 0.96–1.02× of the DeepGEMM baseline at concurrency 1–64 for both 1k-in/256-out and 4k-in/1k-out workloads.
- Ships as an optional extra (`vllm[halops]`) with a documentation page and CPU unit tests (21 passed).

Reproduce the serving configuration (DeepSeek-V4-Flash BF16, online MXFP8, HALOps dense GEMM and MXFP8 MegaMoE):

```bash
vllm serve "$MODEL_PATH" \
  --served-model-name deepseek-v4 \
  --trust-remote-code \
  --tensor-parallel-size 4 \
  --enable-expert-parallel \
  --quantization mxfp8 \
  --quantization-config '{"ignore": ["*.wo_a"]}' \
  --linear-backend halops \
  --moe-backend deep_gemm_mega_moe \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85 \
  --port 30082
```

## Details


**Motivation.** [HALOps](https://github.com/PaddlePaddle/HALOps) is the PaddlePaddle team's high-performance kernel library for NVIDIA Blackwell (SM100). vLLM already serves MXFP8 dense linears through FlashInfer, Marlin, Torch and b12x; this PR adds HALOps as another explicitly selected backend while leaving every default untouched (`auto` keeps it last in the CUDA MXFP8 priority order).

**Packaging.** The `halops` wheel is published on PaddlePaddle's CUDA 13.2 index rather than PyPI, so it cannot be a hard wheel dependency (`pip install vllm` would fail without that index). It is an optional extra:

```bash
uv pip install "vllm[halops]" \
  -f https://www.paddlepaddle.org.cn/packages/stable/cu132/halops/
```

**Changes.**

- `vllm/model_executor/kernels/linear/mxfp8/halops.py` (new): `HALOpsMxfp8LinearKernel` with a lazy `halops` loader and install hint, SfAtom weight-scale swizzle at load time, and `group_wise_quant` + `dense_gemm` wrapped in one custom op with a fake impl (CUDA-graph safe).
- `vllm/model_executor/kernels/linear/__init__.py`: register the kernel in `_POSSIBLE_MXFP8_KERNELS[CUDA]` (last) and `_LINEAR_BACKEND_KERNEL_MAP["halops"]`.
- `vllm/config/kernel.py`: add `"halops"` to the `LinearBackend` literal and its docstring.
- `setup.py`, `requirements/halops.txt`, `docs/features/quantization/halops.md`: optional extra, pinned standalone requirement, and a backend page with supported configurations.
- `tests/model_executor/kernels/test_halops_linear.py` (CPU): registration, `--linear-backend halops` selection and fallback, `can_implement()` limits, weight preparation, custom-op registration, and the `apply_weights` call shape, with a stand-in for the `halops` package.
- `docs/features/quantization/README.md`: link the new backend page from the supported-formats list.
