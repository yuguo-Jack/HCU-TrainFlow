# [Kernel][GDN] Tune packed decode launch on SM120

[Upstream PR](https://github.com/vllm-project/vllm/pull/54181) · state: closed · merged: False

## Original PR description

## Overview

Review summary: tune the SM120 packed GDN decode launch using rotating-cache measurements, with a conservative fallback for larger grids. Kernel math and APIs are unchanged.

## Claims

- Choose `BV` from `B * HV` and state dtype; no fixed `H == HV == 16` restriction.
- With BF16 QKV on RTX PRO 5000 72GB, selected configurations beat BV32 at all 211 changed BF16/FP32-state points. Geometric-mean kernel speedups are 1.109x (BF16 state) and 1.296x (FP32).
- A separate seven-round boundary sweep confirms the rule without regressions in the measured cases. These are kernel results, not serving-throughput gains.

## Validation

Selection hardware/software: RTX PRO 5000 72GB, SM120, 96 MiB L2; Torch 2.13.0+cu130, Triton 3.7.1, FlashInfer 0.7.0.post1, CUPTI 13.4.0. The table below refers to that stack, not the later dependency update on main.

Cold/rotating method: independently allocated buffers, with more than 2x L2 of accessed recurrent state between reuses. CUDA Graph replays are timed with CUPTI; the metric is graph span divided by the number of kernel invocations. Warm-cache results are excluded from selection and this description.

| State dtype | Selection sweep: changed points / total | GM speedup / minimum | Held-out boundary: changed points / total | GM speedup / minimum |
|---|---:|---:|---:|---:|
| BF16 | 127 / 204 | 1.109x / 1.023x | 27 / 32 | 1.131x / 1.016x |
| FP32 | 84 / 204 | 1.296x / 1.056x | 18 / 32 | 1.353x / 1.061x |

Selection: 25 head layouts, three shuffled rounds, 20 graph replays per arm per round, seed 54181. Boundary confirmation: 32 layouts/batches at and around work=32/64/96/160, including small grids and grouped heads; seven shuffled rounds, 20 replays per arm, seed 84217. Ratios are per-case median BV32 time divided by selected-BV time; geometric means are equally weighted across changed cases. Across the seven paired rounds, boundary geometric means ranged from 1.1302–1.1310x (BF16 state) and 1.3526–1.3530x (FP32). The smallest grid was also checked in a separate seven-round pilot. Fallback cases retain BV32. The full sweeps also checked FP16-state compatibility (612 selection / 96 boundary points across three state dtypes), without adding FP16 public test cases.

After rebasing onto main's Torch 2.14.0+cu130 / Triton 3.8.0 update, the same 96-point, seven-round boundary sweep was rerun with CUPTI 13.0.85. It found no selected-case median regressions: changed-case GM/minimum speedups were **1.200x/1.0036x** for BF16 state and **1.403x/1.0385x** for FP32. Seven paired-round geometric means ranged from 1.1998–1.2006x and 1.4028–1.4043x respectively. FP16 compatibility checks also passed (minimum 1.0091x). A separate 24-point pilot passed beforehand. The narrowest BF16 margin is small, not a universal performance guarantee; the 612-point selection sweep above remains labeled as Torch 2.13 data.

Correctness on the exact final kernel source:

- Contributed test file: **34 passed**, including strided projections and padding, rerun on main's new Torch 2.14.0+cu130 / Triton 3.8.0 stack. Added cases use BF16 QKV with BF16/FP32 state; the existing upstream FP16 case is unchanged.
- **1,221** BF16-input wrapper cases, plus **432** FP16/FP32-input cases covering state dtypes, striding, padding and both normalization settings: output and full state bit-exact versus upstream BV32 after 10 eager and 10 CUDA-Graph updates. Both matrices also passed on Torch 2.14 / Triton 3.8.
- Rotating-buffer parity and post-timing finiteness checks passed. The initial sweep checked every buffer; boundary confirmation checked three evenly spaced buffers plus all-buffer finiteness, with the independent wrapper matrix above covering the dispatch.
- Changed-file pre-commit: passed.

The source-isolated GPU harness executes real wrappers, Triton compilation and kernels; it does not validate a full upstream serving installation. Hosted CI currently stops before testing at the contributor-eligibility gate. SM120 execution is validated locally; generic GPU CI may only cover the unchanged fallback.

Serving model evaluation (`vllm bench serve`): a short Qwen3.5-0.8B pilot on an internal vLLM 0.24 stack used a selector-only backport: 600 requests per arm at offered 15 QPS, approximately 5.6K input / 300 output tokens, FP8 weights/KV and FP16 recurrent state, identical prefix-cache warmup. Both arms completed all requests without errors and with identical input/output token totals. Mean TTFT was 253.841 -> 257.055 ms and TPOT was 3.426 -> 3.435 ms; this does **not establish an E2E benefit**. It is not full upstream serving validation, and no task-level model accuracy benchmark was run. The earlier 1.90% E2E reduction used a different rule and is not attributed to this revision. No serving-throughput, accuracy or capacity improvement is claimed.

## Details

For exact SM120 and `K == V == 128`, let `work = B * HV`:

| Condition, in order | BV |
|---|---:|
| work <= 32 | 4 |
| work <= 64 | 8 |
| FP32 state and work <= 96 | 8 |
| FP16/BF16 state and work <= 160 | 16 |
| Otherwise | upstream default 32 |

SM100 tuning, non-SM120 devices and other dimensions retain their existing behavior. No steady-state GPU synchronization or allocation is added. The measurements cover BF16 QKV/output tensors and fully valid IDs on one GPU SKU; padded-heavy performance and other SM120 GPUs are not established. Correctness coverage is broader than performance coverage.

For Qwen3.5-0.8B (`HV=16`), this tunes batches up to 10 for FP16/BF16 state and up to 6 for FP32. Captured batch 16/24 retains BV32, so the expected serving benefit depends on the actual captured-batch distribution. Kernel speedups do not imply a capacity increase at a fixed offered QPS.

Duplicate-work check: this updates the existing SM120 packed-decode PR in response to review. The neighboring SM100 launch tuning remains unchanged; this is not another implementation of that change. AI assistance was used for code, experiments and write-up.
