# [Core][Feature] Observation Plugin for Intercepting & Routing on Activations

[Upstream PR](https://github.com/vllm-project/vllm/pull/37002) · state: open · merged: False

## Original PR description

This PR introduces the **Native Observation Plugin API (Phase 1)**. 

To ensure stability and a clean, risk-free review process, the integration is broken into multiple phases. This PR strictly covers Phase 1 (Core API abstractions, configuration plumbing, and dummy interfaces).

#### Phased Rollout Plan:
1. **Phase 1 (This PR)**: Basic concepts, `ObservationPlugin` interface, `PluginManager`, `VllmConfig` parsing, dummy tests, and design documentation.
2. **Phase 2 (Upcoming)**: Hooking into `gpu_model_runner.py` to capture and route intermediate hidden states safely directly to loaded plugins.
3. **Phase 3 (Upcoming)**: Finalizing the `ABORT` action mechanisms inside the engine (`engine/core.py`) to halt aborted sequences dynamically based on plugin verdicts.

Please check [RFC: Observation Plugin for Intercepting & Routing on Activations](https://github.com/vllm-project/vllm/issues/36998)

Co-authored-by: Gemini <gemini@google.com>
Signed-off-by: Bei Wang <wangbei@google.com>

<!-- markdownlint-disable -->

## Purpose
Create an Observation Plugin into vLLM (Phase 1). It allows developers to register custom plugins that can securely intercept, inspect, and react to model activations (hidden states) during the forward pass of generation, without requiring core vLLM code modifications.

## Code Review

This pull request introduces a new Observation Plugin feature, which is a significant and valuable addition for monitoring and intercepting model activations. The implementation is comprehensive, including documentation, examples, and tests. However, I've identified several critical issues that need to be addressed. There's a bug in the plugin loading mechanism that will cause a `TypeError`, and another in the example plugin that could lead to an `IndexError`. Most importantly, the observation results from the plugins are currently being dropped in the `gpu_model_runner`, which makes the feature non-functional. I've also noted a potential data corruption issue in the observation hook and some incorrect type hints in the configuration classes. Addressing these points will ensure the feature is robust and works as intended.

@mgoin - Thanks for the direct feedback — really helpful to understand the hesitation.
On invasiveness: we've refactored since the initial submission. The current PR:

- Moves all hook management into a helper package
- Core file has a **two-line init call** only
- Hooks apply **only during prefill, only when a plugin is active**
- **Zero overhead** when no plugin is registered — no conditional checks, no function calls, nothing in the hot path

On justification: the use cases are production failure detection that current tooling can't catch:

- **NaN/Inf in late layers** — A single overflow propagates through the residual stream. The token sampler emits garbage. No metric trips until users complain. With observation hooks, we abort the request before output.
- **Bad checkpoint load** — Wrong model shard loaded after a deploy. Throughput looks normal. Outputs are subtly wrong. Activation statistics detect the distribution shift immediately.
- **Quantization degradation** — FP8/INT4 produces NaN-adjacent activations on rare prompts. Most requests fine, a few catastrophic. Current evals miss the tail.

These are real failure modes in production LLM serving. The observation hook makes them detectable at runtime.

```python
                plugin_instance = plugin_cls()
```
