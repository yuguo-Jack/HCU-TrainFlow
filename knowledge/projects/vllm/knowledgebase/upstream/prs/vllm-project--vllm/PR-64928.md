# [ROCm][Multimodal] FP8 ViT attention on AITER asm kernel: pad head_dim to 128, (1,) descales, atomic scale file

[Upstream PR](https://github.com/vllm-project/vllm/pull/64928) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Moves ROCm FP8 ViT attention onto AITER's assembly FP8 kernel for vision towers with head_dim 80 (e.g. MiniMax-M3), and makes static FP8 scale calibration reliable with a data-parallel encoder. Three small code commits (the padding is opt-in) and two test commits.

| # | Commit | Why |
|---|---|---|
| 1 | Pad FP8 ViT attention head_dim to 128 (`VLLM_ROCM_VIT_FP8_PAD_HEAD_DIM=128`; default 16, unchanged) | Padding head_dim 80 only to a multiple of 16 keeps the encoder off AITER's hd128 FP8 kernel |
| 2 | Write the FP8 ViT scale file atomically; optional rewrite at every amax wrap (`VLLM_MM_ENCODER_FP8_SCALE_SAVE_EVERY_WRAP`, default off) | With `--mm-encoder-tp-mode data`, every rank writes `mm_encoder_fp8_scale_save_path` at the same time, so a reader can see a torn file. The rewrite option lets a calibration run end with the scales of its last window. |
| 3 | Pass 1-element FP8 descales to AITER as shape `(1,)` | Shape `(1,1,1,1)` makes AITER pick its CK-tile kernel instead of the asm FP8 kernel (same math) |
| 4 | Run the FP8 ViT scale tests on ROCm; test the atomic scale-file write | `test_vit_fp8_scaling.py` skipped the whole module without FlashInfer/cuDNN, so commit 2 had no test on ROCm |
| 5 | Test padded FP8 ViT attention in the encoder CUDA graph layout | Graph replays with pad 128 run the hd128 kernel on zero-length `cu_seqlens` slots, rows past the last image and a buffer-sized `max_seqlen`; the existing varlen test covers packed sequences only |

Commits 1 and 3 work together: the asm kernel needs head_dim 128 (commit 1) and receives the descales only in the shape commit 3 passes. Sequence-parallel MiniMax ViT, previously part of this PR, is split back out to #65311: it showed no measured gain on top of 1+3.

## Claims

- ViT FP8 attention for one 2048x1600 image on MI355X: **2.41 -> 1.32 ms** per layer, including the quantize and slice (the attention kernel alone: 2.30 -> 1.24 ms). That is about 35 ms less encoder time per image over the tower's 32 layers.
- MiniMax-M3 VL serving, MI355X, TP2, 8 image rows, four A/B pairs against this PR's parent:
  - **2048x1600 images: +5.7% throughput (162.8 -> 172.0 tok/s), mean TTFT −7.4% (3.84 -> 3.55 s), median end-to-end latency −5.9% (5.64 -> 5.31 s)**, better in each of the 4 pairs;
  - **+1.1% throughput over the 8 rows** (geomean). No row is worse than the base beyond its pass-to-pass spread in throughput, median TTFT, P99 TTFT or median TPOT.
- Accuracy unchanged: MMMU val 0.6567 vs 0.6600 (± 0.0148 each).
- No TTFT change on 512x512 and 768x1024 images. One metric moves the other way on 2048x1600: median TPOT is higher while mean, P90 and P99 TPOT and end-to-end latency improve. This is explained below.

**Per commit** (same node, leave-one-out: the 4 B passes against one pass without the commit; 2048x1600 row):

- commit 3 (descales of shape `(1,)`; without it, AITER runs CK-tile at head_dim 128): +3.4% throughput, +3.7% E2E. It also gives +1.1% to +2.1% throughput on five of the six 768x1024 rows, because padding without the asm kernel costs a little.

## Details

- **Why the descale shape matters:** AITER selects the asm FP8 kernel only when the descales arrive as 1-element tensors of shape `(1,)` and head_dim is 128. Otherwise it falls back to CK-tile, which is about 1.7x slower at 16k patches.
- **Why the gain follows image size:** attention cost grows with the square of the patches per image. A 2048x1600 image is 16,416 patches, a 768x1024 image 4,144 and a 512x512 image 1,444. Inside the encoder CUDA graphs:
  - the asm kernel is 0.44 ms faster per 768x1024 replay (one image) and 2.6 ms faster per two-image replay;
  - it is about 0.3 ms slower per 512x512 replay;
  - both effects are too small to show end to end.
- **Padding cost:** padding 80 to 128 spends compute on zero columns. A native head_dim-80 asm kernel would avoid it.
- **Interaction with encoder CUDA graph work:** the padded kernel runs inside encoder graph replays (commit 5 tests that layout). It is independent of #65084/#65227, which change budgets and capture.
- **Overlap:** #60809 also edits `mm_encoder_attention.py`; the two are independent. No other open PR changes these code paths.
- **AI assistance:** AI assistance was used to write the code and tests, run the experiments and draft this description. The submitter reviewed every changed line and the results.
