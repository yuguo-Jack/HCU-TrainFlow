# [MRV2][Spec Decode] Confidence stop for autoregressive drafting

[Upstream PR](https://github.com/vllm-project/vllm/pull/60068) · state: open · merged: False

## Original PR description

## Overview

**+2.7% to +4.7% decode at c=1 on SPEED-Bench over the best fixed draft depth** (11 categories, four same-node runs, mean about +3.7%), within noise at c=4, GSM8K within run-to-run noise, on Qwen3.8-Flash-Next-NVFP4 + MTP, one DGX Spark (SM121), with the NVFP4 draft head from #59973.

Opt-in. While one request is decoding, `draft_confidence_threshold` turns `num_speculative_tokens` into a maximum depth: drafting stops once the drafter's top-1 probability falls below the threshold (the first draft is always kept), and only the drafted prefix is verified, using FULL CUDA graphs captured per verify length for a single request, as Dynamic SD (#32374) does per K. With more than one request the stop is off and the speculator drafts and verifies `draft_confidence_fallback_depth` tokens, with no readback. The stop reads only the drafter's distributions, never the drawn tokens, so rejection sampling stays exact.

```bash
vllm serve <model> --speculative-config '{"method": "mtp", "num_speculative_tokens": 6,
  "draft_confidence_threshold": 0.6, "draft_confidence_fallback_depth": 3}'
```

Model Runner V2, MTP/EAGLE/EAGLE3, SM121 only; any other configuration is rejected at startup.

## Results

SPEED-Bench qualitative (32 prompts per category, greedy, 256 tokens), Flash-Next NVFP4, #59973 NVFP4 draft head, BF16 KV, both arms on one GB10 node (median SM clock 2522 MHz), one run per arm, measured on the final commit 7c4775ff31. Fixed 3 is the best fixed depth: in two other same-node sweeps fixed 4 was 0.1% and 0.6% slower, and on another node fixed 6 was 6.6% slower than fixed 3.

## Design questions raised on earlier attempts (#35301, #43522, #44885)

- **Host sync.** The stop reads its chain flag after each draft step, but only when one request is decoding; with more requests there is no readback. On GB200 the readback made decode 24.7% slower (fixed 6: 378.4, stop: 284.8 tok/s), which is why it is SM121 only. A sync-free version is not cheap: about 65% of the gain is the shorter verify, so the host needs the drafted count, and reading it once per round was just as slow on GB200 (286.8). CUDA graph IF nodes can skip draft steps on the device (about 15 us each), but a device-side verify would need a switch over per-length verify graphs and device-side input preparation.
- **Variable verify length.** Each verify length 1..K has its own FULL graph at batch size 1 (larger batches keep only the fallback and full lengths), so a shorter verify never replays a graph captured for another shape. Cost here: 13 FULL graphs instead of 5, 0.65 vs 0.45 GiB graph memory, capture time unchanged. Attention backends that only take an optimized path at a fixed spec-token count may run slower at the shorter lengths; this was measured with Qwen4Exp QSA/GDN only.
- **Baselines and data.** Compared against the best fixed depth from a same-node sweep, on SPEED-Bench, not synthetic or ShareGPT prompts.
- **Gains at higher batch.** The mean chain length flattens with batch size, so the stop only runs at one request.
- **Hardware specific.** Yes: it helps where a draft step is long, which is why it is gated. SM120 (RTX PRO 6000, RTX 5090) is untested.

## Not a duplicate

- #35301 (same knob) and #28693 were closed as stale; #43522 and #44885 (confidence-based verify truncation for DFlash/PARD) were closed.
- #52228 trims verify width from an online estimator and needs varlen attention backends, which Qwen4Exp QSA/GDN lack; it does not stop drafting. #52559 picks a per-step K for DFlash from past averages and reports no gain at c=1.
- #32374 (Dynamic SD) picks K per batch-size range; at c=1 that is the fixed-depth baseline. Once its MTP drafter capture fix lands (#58821), a Dynamic SD schedule could drive the fallback depth instead of a separate key.

- TheEpicDolphin · COMMENTED · 2026-10-08T21:07:59Z · [source](https://github.com/vllm-project/vllm/pull/60068#pullrequestreview-5462863825)

Thanks for the thorough writeup and measurements. My main concern is the maintenance cost relative to the scope. The PR touches several shared paths (model runner input prep, cudagraph capture candidates, base and autoregressive speculators) for a gain limited to c=1 on SM121. `TargetDependentARSpeculator` and the surrounding MRV2 paths are already complex, and every future optimization/feature that lands there will have to keep this one working. As it stands, I don't think the tradeoff is worth it. I'd be more comfortable if the approach generalized to more concurrencies and hardware, and the changes were more localized.

Perhaps we can take a different direction where we instead add varlen support to the QSA/GDN backends, and leverage AV to handle the trimming for us? AV currently uses stale confidence scores to decide on the batch size. For low-concurrency cases where a sync pays off (e.g. SM121 at c=1), we could extend AV with an opt-in mode that reads the fresh confidences. That would still be hardware-specific, but contained to AV rather than spread through the runner. Just an idea.

Stopping drafting early is trickier, since we're pushing `TargetDependentARSpeculator` toward fusing the last N-1 decode steps, and this PR currently disables fused decode whenever the feature is enabled. CUDA graph conditional nodes inside the fused graph might be a sync-free way to do it (you mentioned measuring ~15 µs per step), but I'd explore that separately, after the target-side trimming.
