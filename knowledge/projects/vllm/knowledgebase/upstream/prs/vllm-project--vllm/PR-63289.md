# [Bugfix][HiSparse] Pin the shared host pool once instead of once per TP rank

[Upstream PR](https://github.com/vllm-project/vllm/pull/63289) · state: open · merged: False

## Original PR description

> [!WARNING]
> **Blocker: this breaks HiSparse P/D over RDMA.** With a NIXL decoder (TP2, `UCX_TLS=rc,cuda_copy,self`, B200 with mlx5), registering the shared pool fails: `ucp_mem_map ... (cuda) ... ibv_reg_mr ... Bad address`. NIXL 1.5.0's `memReg` doesn't pass a memory type to `ucp_mem_map`, and UCX classifies this CUDA-managed host allocation as CUDA memory. Main passes the same P/D oracle (5/5 prompts in both GPU-landing and host-fallback modes). `UCX_CUDA_COPY_DMABUF=no` doesn't help. This PR stays a draft until this is resolved.

## Overview

Fixes the HiSparse shutdown stall in #61859 at its root. TP rank 0 allocates the shared host KV pool once with `cuMemCreate` and hands POSIX fds to the other local TP ranks. Previously every rank ran `cudaHostRegister` on the whole `/dev/shm` mmap, so each rank pinned and unpinned the same pages.

This is an alternative to #62166, which raises the timeouts instead.

## Claims

- Shutdown no longer scales with TP × pool size. GLM-5.3-NVFP4 TP4: workers exit in 3.3–3.8s vs 8.5–9.5s at 64 GiB. TP8 at 256 GiB: 30s vs 86–90s.
- Startup is faster: 130–135s vs 145s, measured end to end on TP4.
- Steady-state serving and accuracy are unchanged, including runs that read heavily from the host tier.
- Net −105 lines outside tests. The per-rank registration and registration-chunking code is gone; the new code is self-contained in `vllm/v1/hisparse/shared_host_pool.py`.

## Details

**Root cause:** `cudaHostRegister` pins per process. With N local TP ranks sharing one mmap, every page is pinned and unpinned N times, and the ranks contend on the same pages. Teardown routinely outlives the 5s worker grace period, and SIGKILL doesn't help, because the kernel still unpins at exit.

**Design:**
- Rank 0 creates one `CU_MEM_LOCATION_TYPE_HOST_NUMA` allocation per NUMA node of the TP GPUs, so host memory is spread across sockets like before.
- It exports POSIX fds and sends them over an abstract Unix socket. It only hands fds to peers whose `SO_PEERCRED` pid belongs to a TP rank.
- Every rank maps the chunks contiguously and grants access to its GPU and the CPU.
- `HiSparseSharedHostPool` keeps the `base_tensor`/`cleanup()` surface that `SharedOffloadRegion` provided here.

**Requirements and limitations:**
- **CUDA only:** `use_shared_hisparse_host_pool` now requires `is_cuda()`, since HiSparse kernels are CUDA-only today. If #57602 lands first, ROCm would fall back to private pools until it has an equivalent.
- **Device support:** each rank checks `HOST_NUMA_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED` and `HANDLE_TYPE_POSIX_FILE_DESCRIPTOR_SUPPORTED` and fails with a clear error. There is deliberately no fallback to the per-rank path.
- **GPU visibility:** rank 0 must see a GPU on each NUMA node it allocates on. The `mp` executor, which the shared pool already requires, provides this.
- **Pool memory:** the pool is now pinned driver memory charged to the process's memory cgroup, not to `/dev/shm`.
- **Release time:** each rank still takes about 9s to release a 256 GiB mapping (unmapping that GPU's view of it), which exceeds the 5s grace period at very large pools. Ranks are no longer serialized on page pins, though.

**Not validated:**
- NIXL P/D end to end. Only RDMA registration of the memory was tested.
- TP8 with real weights.
- Pools above 256 GiB.

**Supersedes:**
- #62166: it raises shutdown timeouts instead of removing the per-rank unpin.
- #61680: it parallelizes filling the shared pool's `/dev/shm` file, which this PR removes.
- #58852, for pinning only: its hugetlbfs backing makes per-rank `cudaHostRegister` cheap, and this PR removes per-rank pinning entirely without requiring reserved huge pages. Its other benefit remains. The driver allocation is mapped with 4 KiB pages, so NIXL's RDMA registration on TP rank 0 still pays per page, about 10s per NIC for a 448 GiB pool:

  | B200, mlx5, `ibv_reg_mr` per NIC | per GiB |
  |---|---|
  | main: `/dev/shm` + `cudaHostRegister`, 64 GiB | 18.6 ms |
  | this PR: driver pool, 64 GiB | 25–28 ms |
  | this PR: driver pool, 448 GiB | 21–23 ms (9.4–10.3s) |

  That cost is once per NIC that UCX uses, at startup. Hugetlbfs pages would cut it to near zero, but they can't back a driver allocation, so they'd stay a separate opt-in backing for P/D deployments with very large pools.
