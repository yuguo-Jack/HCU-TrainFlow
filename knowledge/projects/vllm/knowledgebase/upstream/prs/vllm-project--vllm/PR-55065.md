# [Attention] Add FlashInfer SM120 FP8 PRIMS prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/55065) · state: open · merged: False

## Original PR description

## Overview

Add an opt-in vLLM integration for FlashInfer's SM120 FP8 paged prefill backend from [flashinfer-ai/flashinfer#4714](https://github.com/flashinfer-ai/flashinfer/pull/4714).

## Claims

- Select it with `VLLM_FLASHINFER_PREFILL_BACKEND=cute-dsl-prims`; `auto` remains the default.
- Use FP8 E4M3 queries for SM120 prefill and model-dtype queries for XQA decode.
- Publish compact, separate HND K/V cache planes and forward vLLM's block tables to the PRIMS planner.

### Prior end-to-end evidence

Earlier validation used an RTX PRO 6000 (SM120), vLLM v0.28.0 with the equivalent adapter, FlashInfer #4714 at `73c0663`, FP8 E4M3 KV cache, TP=1, and `nvidia/Qwen3.6-35B-A3B-NVFP4`. Both variants completed 32 concurrent requests with 65,536 input tokens and one output token per request.

| Prefill backend | Reported throughput (tokens/s) | Relative |
| --- | ---: | ---: |
| `auto` | 20,140 | 1.00x |
| `cute-dsl-prims` | 31,851 | 1.58x (+58.1%) |

This was a serving A/B with `--num-warmups 0`, not a repeated statistical benchmark. No separate accuracy evaluation was recorded. These historical numbers do not validate the rebased revision; warmed long-prompt runs and accuracy comparison against `auto` are still needed.

## Details

- Current upstream already pins `flashinfer-python==0.7.2` and `nvidia-cutlass-dsl[cu13]==4.8.0`. FlashInfer 0.7.2 contains the paged PRIMS backend, so no dependency change or FlashInfer source build is required.
- Initialization rejects unsupported devices, KV dtypes, model dtypes, head sizes, DCP, sinks, sliding-window attention, logits soft cap and batch-invariant mode.
- The rebase preserves upstream's NVFP4 KV-cache views and fa2 store path. It removes this PR's obsolete cascade-specific code, following upstream [#61126](https://github.com/vllm-project/vllm/pull/61126). Prefix caching remains available.
- The existing backend correctness helper retains upstream's K/V scale parameters. The PRIMS cases cover prefill and mixed prefill/decode with CUDA graphs.
- Duplicate check: an updated search of open vLLM PRs for `cute-dsl-prims` found only this PR.
- AI assistance: OpenAI Codex assisted with the original implementation, conflict resolution and static review. The human submitter remains responsible for the contribution.

@wqyg18 Results on an RTX PRO 6000 (SM120) with your head on main `153a17166e` (FlashInfer 0.7.2), FP8 KV, the FlashInfer backend and prefix caching off; TTFT is the median of five requests after a warmup:

| | `auto` | `cute-dsl-prims` |
| --- | --- | --- |
| Qwen3.6-35B-A3B-NVFP4, TTFT at 16K / 32K / 64K | 619 / 1499 / 4073 ms | 538 / 1161 / 2719 ms |
| Qwen3.6-35B-A3B-NVFP4, 32 x 64K, one output token | 16,700 tok/s | 25,921 tok/s |
| Qwen3-4B, TTFT at 8K / 16K / 32K | 371 / 918 / 2561 ms | 321 / 720 / 1766 ms |
| Qwen3-4B, 16 x 16K, one output token | 18,392 tok/s | 23,873 tok/s |

Decode TPOT is unchanged and GSM8K doesn't move (0.851 against 0.850 on Qwen3-4B, 0.955 against 0.953 on the 35B model). Against a BF16 KV run, though, PRIMS shifts mean NLL by -0.022 to -0.025 on Qwen3-4B where `auto` shifts it by -0.006 to -0.012 (WikiText-2 windows of 16K to 64K tokens), and with a 32K cached prefix, turns of 8 to 16 new tokens take 17 to 19% longer on Qwen3-4B; flashinfer-ai/flashinfer#6393 on top of 0.7.2 removes most of both at the same long-prompt speed.

Two test fixes are needed on current main:

1. `test_flashinfer_prims_prefill_correctness` names the gated `meta-llama/Meta-Llama-3-8B` (#61732 moved this file to `Qwen/Qwen3-0.6B`) and needs the `default_vllm_config` fixture, since `get_q_data_type` calls `force_use_trtllm_attention()`, which asserts without a config; with both it passes.
2. `test_flashinfer_xqa_single_token_decode_preserves_cudagraph_padding` fails with `AttributeError: 'FlashInferImpl' object has no attribute 'uses_separate_kv_planes'` because it builds the impl with `object.__new__`; setting `impl.uses_separate_kv_planes = False` fixes it. It runs on CPU, so CI will hit it.
