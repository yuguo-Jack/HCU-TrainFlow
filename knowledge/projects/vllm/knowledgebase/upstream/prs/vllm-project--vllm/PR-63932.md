# [Bugfix][Mooncake] Cancel queued lookups when requests finish

[Upstream PR](https://github.com/vllm-project/vllm/pull/63932) · state: open · merged: False

## Original PR description

## Overview
Cancel a finished or aborted Mooncake Store request's queued lookup in its finish callback, before the next scheduler metadata batch.

## Claims
- Both finish APIs reuse the existing idempotent `discard()` operation.
- Already-running RPCs are not interrupted. No TTFT or throughput gain is claimed.

## Validation
Head `fdd78debf`, base `d0d681e40`. Existing connector/scheduler CPU suites: **113 passed**; whole-diff pre-commit, including mypy, passed. A separate cancellation probe passed for both finish APIs; replacing cleanup with the old no-op makes both probes fail because two RPCs are issued instead of one. Events control the external reply; the lookup executor is real. The probe is external validation, not a committed CI regression.

```bash
HF_HUB_OFFLINE=1 VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' \
uv run --no-project .venv/bin/python -m pytest -q \
  tests/v1/kv_connector/unit/test_mooncake_store_connector.py \
  tests/v1/kv_connector/unit/test_mooncake_store_scheduler.py
```

Earlier native Mooncake + OPT-125M checks returned identical tokens and top-5 logprobs for base/patch/reference, including misses, remote hits and reset; not rerun this round. Local validation does not mean upstream CI passed.

## Details
`request_finished()` delegates to `request_finished_all_groups()`, so one cleanup site covers both APIs. The standalone PR is limited to two production lines; the added test and its dedicated CI step have been removed. This independent finish cleanup complements #61292's input-thread prefetch; #50464 concerns teardown. AI assistance was used for implementation and validation.
