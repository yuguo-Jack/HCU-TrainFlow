# [Bugfix] Add interlaced video deinterlacing via PyAV + yadif

[Upstream PR](https://github.com/vllm-project/vllm/pull/47853) · state: open · merged: False

## Original PR description

## Motivation

vLLM's OpenCV video path silently produces all-zero (black) frames for
interlaced videos. `cap.retrieve()` internally calls libswscale for the
`yuv420p → bgr24` conversion; when a frame is flagged `interlaced_frame=True`,
swscale refuses the conversion ("Cannot convert interlaced to progressive
frames or vice versa") but `retrieve()` still returns `True`, leaving the
output buffer all-zero. The model then receives black frames and produces
wrong inference with no hard error.

This reproduces on cv2 4.13 + FFmpeg 4.4.2, so it is an inherent OpenCV-path
defect, not a stale-FFmpeg issue.

Measured on a 720p interlaced H.264 clip (`interlaced_frame=True`), same env:
- OpenCV `cap.retrieve()` → sampled frames all-zero (`mean=0.0`)
- TorchCodec `VideoDecoder` → valid frames (`mean≈132-145`)

## What this PR does

Adds an automatic fallback from OpenCV to TorchCodec when OpenCV returns
all-zero frames:

- The OpenCV path is unchanged for the common (progressive) case — zero
  overhead, zero behavior change.
- After OpenCV decoding, if `frames.max() == 0` (the signature of swscale
  refusing an interlaced conversion; genuine dark scenes still carry encoder
  noise so `max > 0`), retry with TorchCodec, whose decode path does not go
  through the failing swscale refusal.
- TorchCodec is a soft, optional dependency. If unavailable, the original
  OpenCV frames are returned unchanged — no regression.
- No PyAV, no yadif: the interlaced clip's decoded frames have no comb
  artifacts, so TorchCodec's direct decode is sufficient.

## Compatibility

- Progressive videos: unchanged OpenCV path, no fallback triggered.
- Interlaced videos: automatically fall back to TorchCodec; model receives
  valid frames instead of black frames.
- Output format identical `(N, H, W, 3)` RGB uint8.
- No new hard dependency (TorchCodec is optional, soft-imported).
- No API changes (`data` is threaded through `read_frames` to enable fallback).

## Testing

- Interlaced H.264 clip (`interlaced_frame=True`): OpenCV produces all-zero →
  fallback to TorchCodec → model returns a correct description (previously
  described the video as entirely black).
- Progressive clips: unchanged OpenCV path, no fallback, no behavior change.
