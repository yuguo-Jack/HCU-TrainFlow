# [DSv4][Performance][MoE] Optimize pack_bitmatrix Triton kernel for CDNA GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/43159) · state: open · merged: False

## Original PR description

## Purpose
This PR improves the performance of DSv4 Pro by replacing the naive pack_bitmatrix Triton kernel with an optimized implementation that:
- Uses tighter K_PAD heuristic (next_power_of_2 of n_expts_act) to cut memory traffic vs fixed BLOCK_SIZE_K=32
- Reduces warp count to 2 (launch-bound kernel benefits from higher occupancy)
- Adds a Python-level wrapper with torch.compile compatibility
- Provides a vectorized uint32 packing path for CDNA architectures
- Includes a hand-written HIP kernel fast-path that eliminates Triton per-launch dispatch overhead on ROCm
 
co-authored with @heachary. 
This fix was suggested by Claude.

There is a potential integer overflow vulnerability. The `n_rows` parameter, which is an `int64_t`, is cast to an `int` here before being passed to `pack_bitmatrix_hip_launch`. Given that `n_rows` can be very large in vLLM (potentially exceeding 2^31 - 1), this cast can lead to truncation and incorrect behavior, such as processing only a fraction of the rows or memory corruption. 

To fix this, `n_rows` should be handled as a 64-bit integer throughout the C++ and HIP call chain. This involves updating:
1. The forward declaration of `pack_bitmatrix_hip_launch` (line 415) to accept `int64_t n_rows`.
2. This call to `pack_bitmatrix_hip_launch` to pass `n_rows` without casting.
3. The `pack_bitmatrix_hip_launch` function definition in `_HIP_KERNEL_SRC` (line 370) to accept `int64_t n_rows`.
4. The `pack_bitmatrix_hip_kernel` in `_HIP_KERNEL_SRC` (line 337) to accept `int64_t n_rows`.

🟡 **Severity: MEDIUM**

The JIT-compiled HIP shared library is cached in a **predictable world-writable directory** (`/tmp/vllm_pack_bm_hip_v2`). On shared GPU servers a local attacker can pre-populate this path with a malicious `.so`; PyTorch's `load_inline` may then load it, achieving arbitrary code execution in the victim process. PyTorch itself moved to a user-specific cache dir (`torch._appdirs.user_cache_dir`) to mitigate exactly this class of attack.
