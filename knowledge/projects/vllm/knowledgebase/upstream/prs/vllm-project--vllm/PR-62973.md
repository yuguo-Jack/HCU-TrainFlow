# [Feature][Elastic EP] Bootstrap external ranks from a shared launch template

[Upstream PR](https://github.com/vllm-project/vllm/pull/62973) · state: open · merged: False

## Original PR description

## Overview

Add shared-template automatic bootstrap for externally managed Elastic EP.
Initial clients and append joiners declare stable rank ranges, discover the
complete active target, and retain their local engine ownership.

Related: #42515, #43202, [DEP #13121](https://github.com/ai-dynamo/dynamo/issues/13121).
Operation correlation is separate (#62082); native multi-rank resize is a
[stacked follow-up](https://github.com/julienmancuso/vllm/pull/1).

## Claims

- Separate initial/max DP inputs from the discovered live target. Use either
  explicit first rank or `allocation_index × local_count` from one Pod template.
- Bind one launch/handshake identity atomically to every owned rank; reject
  overlaps, conflicting geometry, and incomplete allocation boundaries.
- Reuse native local-range request routing and abort correlation. The default
  local width is one and stays fixed through later `nnodes` config inference.
- Preserve local routing/load state when an old or incomplete global coordinator
  snapshot omits owned ranks, while still observing activity and wave progress.

## Details

Automatic mode owns startup discovery, not membership recovery or process
supervision. Rank zero creates the world; other initial clients rendezvous and
append clients discover an active native resize. One multi-engine client uses
the existing local-range load balancer. This PR explicitly rejects multi-rank
resize until the separate coordinator extension is present.

The resolved local width is carried into EngineArgs before later inference can
change it. Incomplete coordinator statistics cannot replace the local counters
used for routing. Both fixes remain in this owning layer rather than a child PR.

FT serving/recovery, multi-node TP, model-quality parity, and performance are not
claimed. Duplicate checks found no equivalent native shared-template startup
implementation. AI assistance was used; the human submitter remains responsible
for complete review and native qualification.

- julienmancuso · comment · 2026-10-22T15:21:04Z · [source](https://github.com/vllm-project/vllm/pull/62973#issuecomment-6344381217)

@lqh-hh Yes—the shared launch template is the motivation, but I agree that giving
`--data-parallel-size` an initial-size meaning is counterintuitive.

The revision in [01332f37a](https://github.com/vllm-project/vllm/commit/01332f37a9681ef28cf509287767498033f55e75) separates those concepts:

```bash
--elastic-ep-auto-bootstrap \
--elastic-ep-initial-dp-size 2 \
--elastic-ep-max-dp-size 4 \
--data-parallel-rank "$DP_RANK"
```

Initial ranks and joiners use that same template, without
`--data-parallel-size`. The initial-size argument remains 2; joiners discover
the actual target through rank zero's existing handshake before engine config
creation. Runtime `data_parallel_size` therefore always describes the resolved
topology, not bootstrap intent.

The two CLI size inputs are mutually exclusive, including aliases and config
files. Manual launches keep their existing behavior. Discovery still does not
commit membership or authorize serving; native reconfiguration and endpoint
readiness remain authoritative.

Validation: 175 CPU tests and applicable pre-commit hooks pass. The real-GPU
rerun also passed both manual and automatic DP2 → DP3 growth, including
completion serving from all three ranks. FT-enabled serving remains unvalidated
because of the previously reproduced native NIXL initialization failure.
