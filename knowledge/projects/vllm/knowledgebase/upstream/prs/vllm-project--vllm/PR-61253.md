# [Bugfix][Parser] Stop re-parsing the whole GLM tool argument per chunk

[Upstream PR](https://github.com/vllm-project/vllm/pull/61253) · state: closed · merged: True

## Original PR description

## Overview

Streaming a GLM tool call re-parses the whole argument on every chunk, so a long argument (for example a 100 KB file `Write`) costs quadratic CPU on the API server. This PR streams the open argument value with work proportional to each chunk.

Related: #51141 fixes the same pattern for the Inkling parser only (compared under Details).

## Claims

- Parser cost per streamed GLM argument chunk no longer grows with argument length: 6.4 ms at 100 KB and 12.7 ms at 200 KB become 7 us at every size (M4 Pro, table below).
- Streamed deltas are unchanged, including schema type coercion and the held-back trailing value for non-string keys.
- Opt-in per parser through a new `ParserEngineConfig.arg_value_extender`. Only `glm47_moe` (GLM-4.7 and later, including GLM-5.x) sets it. Every other parser keeps its current path.
- Model evaluation does not apply, since model output and streamed tool-call text are unchanged.

## Details

**Trigger.** Any streamed GLM tool call with a long argument, for example a coding agent writing a file.

**Mechanism.** `_compute_arg_delta` runs once per `ARG_VALUE_CHUNK`. Each run works on the whole argument received so far:
- joins `slot.args`;
- runs `_glm47_arg_converter`: three regex passes and `json.dumps`;
- runs `_fix_arg_types`: `json.loads`;
- runs `_safe_arg_prefix`: a Python character loop over the whole JSON, 89% of the time under cProfile.

GLM sets `stream_arg_deltas=True` and no `arg_structural_chars`, so every chunk takes this path.

**Effect.** Cost per chunk grows linearly with the argument, so one tool call costs quadratic time. It runs inside `parse_delta` on the API server's event loop, so it also delays other requests on that server.

**Why the fix is in `engine/`.** The full conversion per chunk lives in `ParserEngine._compute_arg_delta`. Every parser that sets `arg_converter` and streams deltas without `arg_structural_chars` runs it on every chunk: GLM-4.7, Granite, Inkling, MiniMax-M2, Nemotron-v3, Qwen3 and Step-3.5. The engine part is a generic opt-in hook, and the format knowledge stays in each parser's file. This PR wires GLM only.

**Fix.**
- After a full conversion, once the safe prefix is sent, the engine calls `arg_value_extender(slot.args)`. It returns an extender for the open trailing value, or `None`.
- For each later chunk, the extender returns the JSON text the chunk appends to that value, or `None` when the chunk may change anything else. On `None`, the engine runs the full conversion as today, which may create a new extender.
- `_safe_arg_prefix` also reports whether the open value streams. If it does, the engine sends the extender's text. If the value is held back (non-string key), it sends nothing, as today.
- `ToolCallSlot.streamed_json` keeps its parts in a list and joins them on read, like `args`, so the fast path does no work proportional to the argument.

Full conversions now happen only around argument boundaries.

**Why the GLM extender gives the same output.**
- The open value runs to the end of the raw arguments, and the converter emits it as a JSON string with `json.dumps`. JSON string escaping maps each character on its own, so a chunk appends `json.dumps(chunk)[1:-1]`.
- A chunk can only change the parse by completing `</arg_value>`. The extender keeps the last 11 raw characters, so it also sees a closing tag split across chunks.
- The extender is only created when the open key is the last key of the parsed arguments. A repeated earlier key updates an earlier position, so that case falls back to the full conversion.
- Schema coercion leaves string keys alone and coerces earlier values the same way every time, so the JSON before the open value stays the same.

**Overlapping PRs** (checked 2026-10-12).
- #51141 (Inkling) caches the wrapper offset, scans the safe prefix incrementally, and sets `arg_structural_chars`. Its scan resumes from the previous end of the JSON. That fits Inkling, whose converter returns a growing slice of the raw text. The GLM converter closes the JSON (`"}`) again on every chunk, so it needs a different approach. I think Inkling could implement `arg_value_extender` too, so both parsers share one mechanism; we can align with #51141 on the order.
- #54971 changes only the GLM key regexes. The extender reuses `_ARG_RE` and `_PARTIAL_ARG_RE`, and its close check depends only on `</arg_value>`, so it works with either version (differential above).
- #53739 and #58780 also edit `_compute_arg_delta` or `_safe_arg_prefix`, so whichever lands second needs a rebase.

**Limitations.** All measurements drive the parser code directly. There is no end-to-end run on a GPU serving deployment.
