# [XPU][UT] Turn on batch invariance for prompt-embeds comparison tests of pythia-70m on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/63905) · state: closed · merged: False

## Original PR description

## Overview
Enable batch invariance (`VLLM_BATCH_INVARIANT=1`) for `EleutherAI/pythia-70m` model unit test on XPU when `use_prompt_embeds=True` to avoid batch variance. Otherwise, this case fails because of mismatches between outputs generated from token IDs and prompt embeddings.

## Claims

- In the model ut of pythia-70m on XPU, batch variance causes mismatched logprobs between prompts-based and embeddings-based generation, making this ut fail.
- The root cause is that batch variance leads to different batch shapes. Then numerical differences occur on layer1 attn and accumulate across layers to the final output diff.
- Turning on batch invariance can fix the issue and make this case pass on XPU.

## Details
### Root cause: batch variance introduces numerical differences amplified across layers
Local tracing showed different batching for the same prompts:
```
Token-ID inputs:   (step 0) prefill [20, 21]
Embedding inputs:  (step 0) prefill [21] → (step 1) [decode 1, prefill 20]
```
Different batch shapes introduce numerical differences in attn that propagate through the model and change the generated outputs. For the first prompt, the differences in attention tensors between token-id-based and embedding-based generation are shown below (diff = `max|a − b|`):

Layer | Q diff | K diff | V diff | Attn output diff
-- | -- | -- | -- | --
0 | 0 | 0 | 0 | 0
1 | 9.77e-4 | 1.95e-3 | 9.77e-4 | 4.88e-4
2 | 3.91e-3 | 3.13e-2 | 1.95e-3 | 1.95e-3
3 | 0.125 | 3.13e-2 | 1.95e-3 | 2.93e-3
4 | 0.375 | 3.13e-2 | 1.95e-3 | 0.136
5 | 2.5 | 0.133 | 3.49e-2 | 0.878

### Another solution 
**Following ROCm to change `max_num_seqs` from 2 to 1 can also remove the effects of batch variance and make this ut pass on XPU.** This is clean but probably a workaround. As stated in the comments below, this was configured because batch invariance was not supported at that time. https://github.com/vllm-project/vllm/blob/ed1a7307950ab5e6593d25123579ed7ca998b350/tests/models/language/generation/test_common.py#L202-L205
Now batch invariance has been basically supported (pls see https://github.com/vllm-project/vllm/issues/27433) and my local test shows it works on this ut. So this PR enables batch invariance for this case on XPU to fix its failure.
