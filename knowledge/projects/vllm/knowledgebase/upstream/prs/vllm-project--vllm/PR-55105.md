# Fix moe scratch buffer sizing for the TP>1 and DP>1 case

[Upstream PR](https://github.com/vllm-project/vllm/pull/55105) · state: closed · merged: False

## Original PR description

## Purpose

Fix the Humming MoE scratch-buffer assertion with DeepEP v2, expert parallelism, and tensor sequence parallelism.

`FusedMoEConfig.max_num_tokens` is the scheduler capacity for one DP rank. DeepEP v2 previously treated that unsharded value as the capacity of every physical EP input rank. With TP sequence parallelism, each input rank instead owns at most `ceil(max_num_tokens / sp_size)` rows. The oversized DeepEP CUDA-graph receive tensor then exceeded Humming's DP-sized scratch buffer.

This change establishes one CUDA-graph-stable capacity for both sides:

```text
per_ep_rank_capacity = next_power_of_2(ceil(max_num_tokens / sp_size))
post_dispatch_capacity = per_ep_rank_capacity * ep_size
```

DeepEP v2 uses the per-rank value for handle initialization and runtime decode buckets. Humming uses the corresponding post-dispatch value. For DP=4, TP/SP=8, EP=32, and `max_num_tokens=128`, both now agree on 512 rows instead of allocating 4096 rows in DeepEP and 512 in Humming.

This is separate from #56079: that PR invalidates sequence-parallel padding during routing, but does not change DeepEP's receive allocation or Humming's scratch-capacity validation.
