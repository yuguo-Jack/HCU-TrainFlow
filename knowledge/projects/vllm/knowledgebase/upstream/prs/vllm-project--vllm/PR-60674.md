## Overview

This pull request introduces optimized fused Triton kernels (`vllm/model_executor/layers/fused_gemma4_ops.py`), integrates them directly into Gemma 4 core text models (`vllm/model_executor/models/gemma4.py`), and adds comprehensive unit and numerical parity tests (`tests/layers/test_fused_gemma4_ops.py`).
Duplicate-work check: verified via `gh pr list --repo vllm-project/vllm --search "fused gemma4 ops"` and `gh issue list` that no open pull request implements fused norm/RoPE/PLE/MoE kernels for Gemma 4.

## Claims

- **Realistic End-to-End Serving Impact (NVIDIA A100-SXM4-80GB Measured)**:
  - **gemma-4-E2B-it**: Up to **1.90x** prefill throughput speedup (67,488.9 tok/s vs 35,480.8 tok/s at BS=4, 1k prefill) and **1.06x** decode throughput speedup with 100.0% token match.
  - **gemma-4-E4B-it**: Up to **1.50x** prefill throughput speedup (34,290.8 tok/s vs 22,787.7 tok/s at BS=4, 1k prefill) and **1.05x** decode throughput speedup with 100.0% token match.
  - **gemma-4-12B-it**: Up to **1.05x** prefill throughput speedup and **1.04x** decode throughput speedup with 100.0% token match.
  - **gemma-4-26B-A4B-it**: Up to **1.05x** prefill throughput speedup and **1.04x** decode throughput speedup with 100.0% token match.
  - **gemma-4-31B-it**: Up to **1.04x** prefill throughput speedup and **1.04x** decode throughput speedup with 100.0% token match.
- **Component Microbenchmark Timings (NVIDIA A100-SXM4-80GB Measured, 113 Test Cases, 0 Regressions)**:
  - **100% of 113 benchmark cases demonstrate speedup > 1.00x** (range: **1.06x to 4.98x**).
  - SWA QKV Norm+RoPE across all 5 models: 1.087-1.273 ms -> 0.315-0.598 ms (**1.88x to 3.85x speedup**, eliminates separate PyTorch RMSNorm and RoPE kernel launches per attention block).
  - Global QKV Norm+RoPE (Standard, KV-shared, k_eq_v) across all 5 models: 1.060-1.779 ms -> 0.311-1.013 ms (**1.55x to 4.98x speedup**).
  - Dense Decoder Layer across models: 2.020-2.619 ms -> 1.049-1.838 ms (**1.42x to 1.93x speedup**).
  - MoE Decoder Layer (26B-A4B): 4.199-4.685 ms -> 2.516-2.825 ms (**1.66x to 1.72x speedup**).
  - Fused PLE Projections (`project_per_layer_inputs`): 0.334-0.350 ms -> 0.263-0.322 ms (**1.06x to 1.30x speedup**).
  - Multi-Layer Stack (10 layers): 22.956-24.517 ms -> 13.450-15.515 ms (**1.54x to 1.71x speedup**).
- **Lossless Numerical & Parity**: Cosine similarity >= 0.99999 across all configurations, 65.0% to 100.0% within 1-ULP.
- **Encapsulation & Zero Regression Guard**: Unconditionally enabled across all Gemma 4 decoder layers without impacting non-Gemma models.

    def compute_ulp_diff_bf16(a: torch.Tensor, b: torch.Tensor) -> torch.Tensor:
        a_f, b_f = a.to(torch.bfloat16), b.to(torch.bfloat16)
        a_i, b_i = a_f.view(torch.int16), b_f.view(torch.int16)
        exact = (a_i == b_i) | ((a_f == 0) & (b_f == 0)) | ((a_f.float() - b_f.float()).abs() <= 1e-6)
        ulp = torch.where((a_i >= 0) == (b_i >= 0), (a_i.to(torch.int32) - b_i.to(torch.int32)).abs(), 999999)
        return torch.where(exact, 0, ulp)

    def compute_ulp_diff_fp32(a: torch.Tensor, b: torch.Tensor) -> torch.Tensor:
        a_f, b_f = a.to(torch.float32), b.to(torch.float32)
        a_i, b_i = a_f.view(torch.int32), b_f.view(torch.int32)
        exact = (a_i == b_i) | ((a_f == 0) & (b_f == 0)) | ((a_f - b_f).abs() <= 1e-7)
        ulp = torch.where((a_i >= 0) == (b_i >= 0), (a_i.to(torch.int64) - b_i.to(torch.int64)).abs().to(torch.int32), 999999)
        return torch.where(exact, 0, ulp)

    def compute_parity_metrics(base, feat):
        if isinstance(base, (tuple, list, dict)):
            items = base.values() if isinstance(base, dict) else base
            f_items = [feat[k] for k in base] if isinstance(base, dict) else feat
            ml = [compute_parity_metrics(b, f) for b, f in zip(items, f_items)]
            return {k: float(sum(m[k] for m in ml) / len(ml)) if "pct" in k else (max(m[k] for m in ml) if "max" in k else min(m[k] for m in ml)) for k in ml[0]}
        b_c, f_c = base.detach().cpu(), feat.detach().cpu()
        if b_c.numel() == 0:
            return {"bit_exact_pct": 100.0, "within_1ulp_pct": 100.0, "max_abs_diff": 0.0, "cosine_sim": 1.0}
        exact = (b_c.contiguous().view(torch.uint8) == f_c.contiguous().view(torch.uint8)).all(dim=-1)
        b_f, f_f = b_c.float(), f_c.float()
        diff = (b_f - f_f).abs()
        max_diff = float(diff.max().item()) if diff.numel() > 0 else 0.0
        u1 = (compute_ulp_diff_bf16(b_c, f_c) <= 1) if b_c.dtype == torch.bfloat16 else ((compute_ulp_diff_fp32(b_c, f_c) <= 1) if b_c.dtype == torch.float32 else (diff <= 1e-4))

        else:

        return {"bit_exact_pct": float(exact.float().mean().item() * 100.0), "within_1ulp_pct": float(u1.float().mean().item() * 100.0), "max_abs_diff": max_diff, "cosine_sim": cos}

## Details

### Root Cause
Gemma 4 introduces structural elements that exacerbate memory bandwidth bottlenecks in vLLM:
1. **Per-Layer Embeddings (PLE)**: Injects unique token representations at each decoder layer, requiring extra linear projections, RMSNorms, and residual additions.
2. **Dual Residual Streams & Post-Norms**: Employs independent input, post-attention, pre-feedforward, and post-feedforward normalizations per layer.
3. **Cross-Layer KV-Sharing (YOCO style)**: Early layers write KV states that later layers consume, requiring Q-only projections on later layers.
4. **Independent Q/K/V RMSNorms**: Normalizes Q, K, and V vectors individually prior to rotary position embeddings.

In upstream vLLM, each operation launched as an independent eager PyTorch kernel. A single decoder layer executed up to 56 separate kernel launches, round-tripping intermediate activation tensors to High Bandwidth Memory (HBM).

### Design & Implementation
Introduced `vllm/model_executor/layers/fused_gemma4_ops.py` providing Triton kernels with FP32 internal accumulation:
1. **`fused_qkv_norm_rope`**: Loads fused QKV output once into SRAM. Fuses Q-norm, K-norm, FP32 RoPE angle calculation, rotation, and optional weightless V-norm in a single memory pass, writing directly to attention input buffers.
2. **`fused_post_attn_add_pre_ff_norm`**: Fuses post-attention residual addition and pre-feedforward RMSNorm into a single kernel, eliminating intermediate HBM roundtrips.
3. **`fused_mlp_ple_epilogue`**: Combines post-feedforward residual add, PLE projection, PLE RMSNorm, residual combination, and pre-next-layer RMSNorm into a single fused epilogue kernel.
4. **Two-Stage MoE Epilogue Pipeline**: Fuses post-attention addition with MoE router pre-norm (`fused_post_attn_add_moe_prenorms`), allowing FusedMoE to execute without bypassing router semantics, followed by `fused_moe_combine_norm_ple_epilogue` to combine expert outputs with PLE and pre-next-layer norms.
5. **Fast KV-Sharing Prefill**: Avoids unneeded K and V projections on shared layers, dispatching Q-only fused kernels.

### Tradeoffs & Encapsulation
- **Numerical Parity Invariant**: FP32 intermediate accumulation prevents numerical drift. All outputs maintain >= 0.99999 cosine similarity against eager baseline.
- **Strict Architecture Scoping**: All fusions reside in `fused_gemma4_ops.py` and are enabled strictly when loading Gemma 4 models. Other architectures remain untouched.

Hi @lucianommartins, I happened to have Gemma 4 E2B/E4B set up on an RTX 5090 for some unrelated tests, so I gave this PR a try on the default serving path while I was at it. I haven't gone through the whole PR, so please take these as a few observations from one card rather than a full review. Sharing them in case they are useful.

In short:
- Two things broke for me: `import triton` at module level (CPU builds without Triton), and the `M <= 16` PLE path with online FP8 (eager mode, or `max_num_batched_tokens <= 16`).
- Under `torch.compile` the `M <= 16` branch seems to be fixed at trace time, so on the default config those kernels never ran.
- On the default path I see decode +1.7…2.7 %, prefill bs4 within noise, prefill bs1 (E2B) −7…−12 %. With your script and your two commits, prefill bs4 came out at +0.7 % instead of +90 %.
- NLL is 0.26 % worse on 254 of 300 samples; GSM8K unchanged.

## 1. `import triton` at module level

`fused_gemma4_ops.py` imports `triton` directly, and `gemma4.py` imports it unconditionally. On a CPU build without Triton (macOS arm64), `import vllm.model_executor.models.gemma4` fails with `ModuleNotFoundError: No module named 'triton'`; on current main the same import works. Going through `vllm.triton_utils` (as `gemma4.py` already does for the routing kernel) might be enough to fix it.

## 2. The small-M PLE path with online FP8

`fused_mlp_ple_epilogue` takes the `0 < M <= 16` branch whenever `per_layer_input_gate` has a `.weight`, and passes that weight to `_fused_post_ff_norm_add_ple_gate_gelu_kernel`, which calls `tl.dot` on it (line 911). With `--quantization fp8_per_tensor` the PLE `ReplicatedLinear` layers are quantized online, so `.weight` is FP8 with no scale applied, and Triton 3.8 rejects bf16 × fp8 in `tl.dot`. What I saw on E2B (main serves the same requests in every case):

| Setting | This PR |
|---|---|
| default (`max_num_batched_tokens=8192`, compiled) | runs (the branch is not taken, see 3) |
| `--enforce-eager` | engine starts, then the **first request** fails: `AssertionError: Unsupported rhs dtype fp8e4nv` (raised at the kernel launch, `fused_gemma4_ops.py:2014`) |
| `max_num_batched_tokens=16` | fails at startup in `profile_run` with the same error |

One more thing I noticed while looking at it: the wrapper passes `w_gate.stride(1)` / `w_gate.stride(0)` as the K / P strides, which assumes an `[out, in]` layout, while the online FP8 weight is `qweight.t()` (`[in, out]`). So even a dtype-tolerant kernel would read it transposed. A dtype/quantization check before taking this branch, like the `_is_unquantized` check the attention path already has, might cover both.

## 3. The `M <= 16` branch under `torch.compile`

`if 0 < M <= 16` is Python control flow inside the compiled region. With the default dynamic-shape config (`BACKED`, `evaluate_guards=False`) the branch gets fixed by the size seen at trace time, which is `profile_run` with `max_num_batched_tokens` tokens. In a default E2B run, `_fused_post_ff_norm_add_ple_gate_gelu_kernel` never showed up in decode traces (0 launches, decode M = 8); with `max_num_batched_tokens=16` it ran on every step (3710 launches). So as far as I can tell the small-M kernels only run in eager mode or with a very small token budget. If they are meant for decode, moving the M check inside the custom op (evaluated at runtime) might be one option.

What the profiles show on this card:
- **Prefill bs4:** GEMM time is identical (65.33 vs 65.30 ms; 212 GEMMs in both). The fused kernels take 2.01 ms and replace 1.94 ms of Inductor-generated kernels, so the forward totals are 80.03 vs 80.05 ms. The GEMMs already run at about the calibrated peak of this card (≈226 TFLOP/s), so there is not much left to win in prefill here.
- **Prefill bs1 (E2B):** GPU kernel time is about the same (23.30 vs 23.53 ms), but GPU idle time between kernels grows from 7.09 to 9.60 ms. My guess is that the per-layer Python work of the custom-op wrappers shows up when the step runs outside CUDA graphs and the GPU part is short. E4B, with more GPU work per step, shows no slowdown.

## 5. Accuracy

E2B, default path:
- NLL over 300 GSM8K question+answer texts (BOS added): +0.257 % for the PR, against +0.017 % between the two main runs. The PR is worse on 254 of 300 samples (between the two main runs: 163 of 300). Small, but systematic.
- GSM8K, 5-shot, 1319 questions: 57.09 % on both (the second main run gives 57.32 %).

## 6. Compared with the numbers in the PR description

On this card I couldn't reproduce the 1.9× prefill gain, even with your script and commits. Your E2B bs4 numbers (115.56 ms base, 60.75 ms feature, about 15.4 TFLOP) work out to roughly 43 % and 81 % of the 312 TFLOP/s peak, and the second figure includes attention and the non-GEMM kernels, so one of the two is hard to explain from the compute side. If you still have a profiler trace of a baseline and a feature prefill step, or know which attention backend was selected on the A100, that would probably explain the gap quickly. I may well be missing something about that setup.
