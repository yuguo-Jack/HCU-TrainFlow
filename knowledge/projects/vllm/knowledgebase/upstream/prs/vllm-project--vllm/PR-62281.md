# [Bugfix] Preserve existing files when downloads fail before writing

[Upstream PR](https://github.com/vllm-project/vllm/pull/62281) · state: open · merged: False

## Original PR description



## Overview

Preserve an existing destination when an HTTP download fails before opening it for writing. A failed asset fetch can otherwise delete a file that another concurrent fetch has just cached.

## Claims

- Synchronous and asynchronous downloads leave existing files intact on an HTTP error before writing starts.
- Failures after opening the destination still clean up the incomplete file.

## Validation

- `uv run --offline --no-project --python .venv/bin/python -m pytest tests/test_connections.py -q`: **12 passed** on Linux. The added regression tests fail twice on the base commit, for synchronous and asynchronous HTTP 404 responses with an existing destination.
- A local HTTP reproducer using two concurrent `get_vllm_public_assets` calls confirmed that a failed request deletes the successful request's cache file before this patch and preserves it afterward.
- `pre-commit run --files vllm/connections.py tests/test_connections.py`: passed, including mypy and test tethering.

## Details

Cleanup currently checks only whether the destination exists. Track whether this invocation opened it for writing before allowing cleanup. This keeps the existing failed-write behavior; it does not make concurrent writes atomic.

I checked the open PR inventory and related changes to `connections.py`; none of the inspected changes handles this destination cleanup. #62204 concerns download-budget accounting in the in-memory read path.
