# [Bugfix][Model] Inkling: skip EP-alignment padding experts when loading expert weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/65111) · state: open · merged: False

## Original PR description


## Purpose

Inkling cannot start with an expert-parallel size that does not divide its 256
routed experts (e.g. `--data-parallel-size 3 --tensor-parallel-size 2
--enable-expert-parallel`, EP=6). Weight loading fails on the last EP rank
(vLLM 0.32.0):

```
vllm/models/inkling/nvidia/moe.py:608, in load_expert_weight
    slab = weight[gid].narrow(0, tp_rank * 2 * half, 2 * half)
IndexError: index 256 is out of bounds for dimension 0 with size 256
```

`InklingMoE` pads the routed expert count to a multiple of the EP size so the
TRTLLM MoE kernels get equal per-rank slabs (`moe.py:440`, 256 → 258 on EP6),
and `finalize_load` already zeroes those padding slots. `load_expert_weight`,
however, iterates over every local slot from `_local_expert_slots()`, including
the padding ids (256, 257), and indexes the checkpoint tensor with them.

This PR filters the padding slots (`gid >= n_routed_experts`) out of the slot
map in `load_expert_weight`, for both the NVIDIA and AMD implementations. The
padding behaviour itself is unchanged; the router only selects among the
`n_routed_experts` real experts, so padding slots are never routed to.

Power-of-two EP sizes (no padding) are unaffected: the filter is a no-op there.

## Test Plan

Unit test (added to `tests/models/inkling/test_moe_weight_layout.py`, which the
`inkling-unit-tests-b200` Buildkite step already runs): a rank owning
`{2: 0, 3: 1}` with a 3-expert checkpoint must load expert 2 and leave the
padding slot untouched, for a per-expert weight (`w2_weight`) and a
per-expert scalar scale (`w13_weight_scale_2`). The two existing
`load_expert_weight` tests now also set `n_routed_experts` on their fake layer.

```bash
pytest tests/models/inkling/test_moe_weight_layout.py -v
```

The unit tests were run against a vLLM 0.32.0 install, whose
`load_expert_weight` is identical to `main`, with the patched module swapped in.

End-to-end on 6× B200 (vLLM 0.32.0, whose `load_expert_weight` is identical to
`main`), `thinkingmachines/Inkling-NVFP4`:

```bash
vllm serve thinkingmachines/Inkling-NVFP4 \
  --data-parallel-size 3 --tensor-parallel-size 2 --enable-expert-parallel \
  --max-model-len 16384 --gpu-memory-utilization 0.90 \
  --reasoning-parser inkling --tool-call-parser inkling --enable-auto-tool-choice \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

## Test Result

Unit test, before the fix:

```
FAILED test_moe_weight_layout.py::test_moe_skips_ep_padding_experts_during_load[w13_weight_scale_2-...]
FAILED test_moe_weight_layout.py::test_moe_skips_ep_padding_experts_during_load[w2_weight-...]
E   IndexError: index 3 is out of bounds for dimension 0 with size 3
2 failed, 33 passed
```

After the fix:

```
35 passed
```

End-to-end, EP6:

| | before | after |
|---|---|---|
| startup | `IndexError` during weight loading | starts (`Local/global number of experts: 43/258`, 106.81 GiB weights per GPU) |
| 18 concurrent short factual prompts, greedy | – | 18/18 correct (one answered `H₂O` vs expected `H2O`) |
| image / audio / tool-call requests | – | correct |
| MTP acceptance (3 draft tokens) | – | 56.6 % (all 3 DP engines served traffic) |

Misplaced or garbage experts on the padded ranks would have shown up as
broken output and a collapsed MTP acceptance rate.

The AMD change is the same filter; it was not run on AMD hardware.
