# [Perf][ROCm][GLM-5.3-Flash] Default to breakable CUDA graphs on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/63070) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

GLM-5.3-Flash cannot be compiled with torch.compile. On ROCm, the default FULL_AND_PIECEWISE mode therefore falls back to FULL_DECODE_ONLY, and every prefill or mixed prefill+decode step runs eagerly.

Breakable CUDA graphs give this model piecewise graphs without torch.compile. On CUDA, `Glm5Next*` already defaults to them. This PR adds the two `Glm5Next` architectures to the ROCm list in `default_breakable_cudagraph_architectures`, next to `DeepseekV41ForCausalLM`.

Related: #61761 (DFlash2 performance on ROCm).

## Claims

On MI355X, TP2, `amd/GLM-5.3-Flash-Quark-MXFP4`, output tok/s goes up in every configuration below:
- With a DFlash2 drafter at default capture sizes: +14% at c=1 and c=16.
- With `max_cudagraph_capture_size` 2048: +21% at c=1, +34% at c=16 and +37% at c=64.
- Without spec decode, at default capture sizes: +14% to +17%.

Users no longer need to set `VLLM_USE_BREAKABLE_CUDAGRAPH=1`. Setting it to 0 still turns the feature off.

## Validation

**End to end.** Output tok/s, with the c=64 TPOT in parentheses. The DFlash2 rows also have #63071 and #63069 applied.

| config | FULL_DECODE_ONLY (main) | breakable (this PR) |
|---|---|---|
| DFlash2, default capture sizes | 330.2 / 1649.9 / 3346.8 (17.42 ms) | 375.2 / 1881.0 / 3064.1 and 3465.9 (19.38 / 16.31 ms) |
| DFlash2, capture size 2048 | 330.2 / 1649.9 / 3346.8 (17.42 ms) | 398.4 / 2215.3 / 4598.4 (12.73 ms) |
| no spec decode, default capture sizes | 124.2 / 979.9 / 2253.8 | 141.9 / 1145.0 / 2575.3 |

- Columns within a cell are c=1 / c=16 / c=64.
- The DFlash2 c=64 result at default capture sizes is noisy. Two runs gave 3064.1 and 3465.9 tok/s. At c=64, a mixed step has 64 × 8 decode tokens plus a prefill chunk, which is more than the default limit of 512 tokens, so many of those steps still run eagerly.
- Capture size 2048 removes that noise. The cost is about 30 GiB of graph pool per GPU, compared with 1.25 GiB for FULL_DECODE_ONLY. This PR does not change the default capture size.
- The server log shows `Auto-enabling VLLM_USE_BREAKABLE_CUDAGRAPH=1`.
- GSM8K with breakable graphs, capture size 2048, #63071 and #63069 is 0.9704. I did not run GSM8K with FULL_DECODE_ONLY.

**Test.** `test_breakable_cudagraph_platform_default` in `tests/test_config.py` gets 4 new cases: both `Glm5Next` architectures on CUDA and on ROCm.
- On main, the 2 ROCm cases fail (`Glm5NextForCausalLM-True-True`, `Glm5NextForConditionalGeneration-True-True`).
- With this PR all 16 cases pass (at `9417b22e95`, rebased on main on 2026-10-29).

<summary>Setup and commands</summary>

One MI355X node (gfx950). TP2. Image `vllm/vllm-openai-rocm:nightly-rocm100-e68efc685a`, with the patches named in each row applied on top. `VLLM_ROCM_USE_AITER=1 VLLM_USE_V2_MODEL_RUNNER=1`.

```bash
vllm serve amd/GLM-5.3-Flash-Quark-MXFP4 -tp 2 --max-model-len 16384 --max-num-seqs 256 \
  --gpu-memory-utilization 0.85 --limit-mm-per-prompt '{"image": 0, "video": 0}' \
  --no-enable-prefix-caching \
  [--compilation-config '{"max_cudagraph_capture_size": 2048}'] \
  --speculative-config '{"method": "dflash", "model": "incoai/GLM-5.3-Flash-DFlash2", "num_speculative_tokens": 7}'
vllm bench serve --dataset-name sharegpt --sharegpt-output-len 512 --temperature 0 --seed 0 \
  --num-prompts max(64, 8*C) --max-concurrency C
```

- Acceptance length comes from the `vllm:spec_decode_*` counters, read before and after each concurrency.
- GSM8K uses all 1319 test questions: zero-shot chat, greedy, thinking on, up to 6144 output tokens, concurrency 64. The score is the last number after `</think>`.
- Each row is one run. Acceptance length varies by about ±0.15 between runs, so the step time is given as TPOT × acceptance length, which is one spec step.

</details>

## Details

- The change is limited to the ROCm branch of `default_breakable_cudagraph_architectures`, and only these two architectures get the new default.
- The default is applied only when `VLLM_USE_BREAKABLE_CUDAGRAPH` is not set, so `VLLM_USE_BREAKABLE_CUDAGRAPH=0` still opts out.
