# [Bugfix] Index mamba spec-decode block tables by request slot, not batch row

[Upstream PR](https://github.com/vllm-project/vllm/pull/55506) · state: open · merged: False

## Original PR description

## What this fixes

With **pipeline parallelism + MTP + prefix caching** on a hybrid model (reproduced on Qwen3.8-Flash-Next, PP≥2, `max_num_seqs`≥3), **14–33 % of requests degenerate into a constant-token loop** (`ductductduct…`, prompt-independent) and speculative acceptance collapses (~50 % → ~26 %). Threshold is exactly 2→3 concurrent slots; MTP alone and PP alone are both clean.

The loop token is `1023`, which is what the sampler deterministically emits for an **all-NaN logits row** — the request's recurrent state has been poisoned and never recovers. This is the same fault as the illegal-memory-access reports in #54173: loud on sm_121, silent on sm_80 where the misdirected read stays mapped.

## Root cause

`MambaSpecDecodeGPUContext` captures the block tables' raw data pointers **exactly once** (`initialize_from_forward_context` is idempotent by design), and the two align copy kernels resolved the table row as

```python
bt_row_idx = batch_idx if HAS_IDX_MAPPING else req_idx
```

while the V2 runner bound that capture to the **per-step gathered** `input_block_tables` — batch-ordered and re-gathered every step.

Under async scheduling with PP, a non-last rank runs its postprocess `pp_size` steps *after* its batch was gathered, so the batch mapping it holds is **stale**. Indexing the current tables by batch row then walks another request's block ids (freed, or already reallocated). On hybrid models with a unified cache layout, main KV, GDN conv/SSM and PLE conv state all alias the same physical page and are distinguished *only* by block-id ownership — so those copies land inside a live request's state.

## Change

Bind the context to the **source per-request-slot** tables (`BlockTables.block_tables[i].gpu`: persistent `[max_num_reqs, max_blocks]`, stable `data_ptr`, row = request-state slot, mutated only by stream-ordered staged writes) and index rows by `req_idx` in both kernels.

That is the contract the V1 path already relies on — it launches with `HAS_IDX_MAPPING=False` and indexes by `req_idx` against exactly those tables — so V2 was the outlier.

The context no longer touches the gathered tables at all, so nothing needs to rotate them. A pool of rotating gathered-table sets is **not** a valid substitute: with full CUDA graphs a captured graph bakes whichever slot's pointer was current at capture, and the remaining replays run against stale tables — same corruption by another road.

## Test

`tests/kernels/mamba/test_precopy_mamba_align.py` only ever launched with `idx_mapping = arange(num_reqs)`, where batch row == request slot, so it cannot distinguish the two indexings — which is how this shipped. The added tests permute `idx_mapping` **and** make the per-slot decisions differ (copy / same-block skip / fresh skip / biased copy) over disjoint per-row block ids:

| build | result |
|---|---|
| old indexing | fails — ~10.6 % of destination-pool elements mismatch (real state corruption) |
| this PR | passes (both conv layouts, all existing cases unaffected) |

## Production measurement (4× CMP 170HX, sm_80, PP4 `13,13,13,9`, MTP4)

| | before | after |
|---|---|---|
| 8-way soak, same harness | **16/48 loops (33 %)** | **0/56 loops** |
| mean acceptance length | 2.80 (observed on this box pre-fix) | 4.90–5.00 |
| 294 K / 509 K long-context needle | — | both exact |

No perf cost: the kernels, launch counts and copied bytes are unchanged, only the row index. Soak rounds got ~14 % faster (the corrupt requests used to burn to `max_tokens` at degraded acceptance).

## Credit

The root cause and this fix direction were identified **first** by @zebgop-ops, with the forensics published at <https://github.com/zebgop-ops/qwen38-flashnext-pp> (`FINDINGS.md` addenda 11–19, patch `0010`; their ablation established that req-indexed source tables are necessary and sufficient, and that the table pool is not). This PR is our port of that finding to current `main` plus the regression test; the production A/B above is ours.

Good catch -- you are right, and thanks for the pointer to the K3 path. I checked both call chains and pushed a fix: `c3cad71`.

**Why it was wrong.** The runner hands `preprocess_state()` the SOURCE per-request-slot tables (`gpu/model_runner.py`, the call right above `model_state.prepare_attn`), and the ctx captures those pointers once -- that is what makes the deferred-postprocess case work, since the fused copy kernels resolve rows through `idx_mapping`. But `compute_aligned_state_indices()` in the same ctx used the kernel's `rows` directly as the table row (`... + rows[None, :, None] * block_table_stride_req`), while `seq_lens` in and `state_indices` out are batch-row ordered. Correct only while batch order == request-slot order; wrong as soon as the batch is compacted or, exactly in the PP case this PR is about, a deferred step runs with another step's mapping. Before this PR the ctx held the gathered (batch-ordered) views, which is why batch-row indexing was consistent then -- the binding change is what made it inconsistent, so it belongs in this PR rather than a follow-up.

**The fix.** `HAS_IDX_MAPPING` on `get_aligned_state_indices_multi_group_kernel` (same idiom as the other mamba kernels in the file): the table row comes from `idx_mapping[row]`, rows whose mapping is the `-1` sentinel are skipped, and `seq_lens`/output stay in batch order -- `builder.mamba_aligned_state_indices` consumers index by batch row, so that part must not change. `compute_aligned_state_indices()` takes the mapping as an optional third argument (default `None` keeps the previous behaviour for V1-style callers) and `mamba_hybrid.py` passes `input_batch.idx_mapping`.

**Verification, honestly scoped.** Static: signature/caller reconciliation, `py_compile`, and the index math itself under a permuted batch plus a sentinel row (the old expression picks slot `r` where slot `idx_mapping[r]` is required; the new one matches, and `-1` rows can never form a negative row index because the load is masked with `other=0`). Not run end-to-end: this box is 4x CMP 170HX (sm_80) and we have no KDA/Kimi model here, so I could not exercise the K3 path or the CUDA-graph init case. If you want a kernel test for it, point me at the harness you would like it in (`tests/kernels/mamba/test_precopy_mamba_align.py` already uses `HAS_IDX_MAPPING` for the neighbouring kernels, so the plumbing is there) and I will add one -- I would rather not land an unrunnable test blind.

**One thing I noticed while doing this, for whoever owns the ctx lifecycle:** `_ensure_align_ctx()` initializes from whichever tables arrive first -- `preprocess_state()` passes the source tables, while `prepare_attn()` calls it with the gathered views. Per the runner comment `preprocess_state` runs first on real batches, so the binding is the intended one today, but the correctness of the copy kernels now depends on that ordering. Making it explicit (only the source tables may initialize the ctx, or two contexts) would be a good hardening; happy to do it here or separately, your call.

- Karl0007 · comment · 2026-09-23T23:18:55Z · [source](https://github.com/vllm-project/vllm/pull/55506#issuecomment-5804551652)

Both findings are fixed in **`5f71d6f`**, with your test branch as the acceptance run.

**Padded rows.** The mapping load is now clamped by the mapping length (a runtime `num_mapping_rows`, added to `do_not_specialize` so it does not recompile per batch), and padded rows resolve to slot 0 -- the in-range equivalent of the zeroed padding row the gathered path used to read. Your `test_padded_rows_do_not_read_past_idx_mapping` was the single failure at `a28e902`; it passes now.

**Capture-time binding.** Confirmed in the code, not just in the fixture: `prepare_inputs_to_capture` builds capture metadata from `get_dummy_block_tables()` and calls `model_state.prepare_attn` (`cudagraph_utils.py:824`), which is the only path that reaches `_ensure_align_ctx` on a dummy batch -- `preprocess_state`, the source-table caller, is skipped on dummy runs and cannot correct the binding afterwards. Fixed by making the binding source-only: `_ensure_align_ctx` returns `(ctx, temporary)`, `preprocess_state` asserts `not temporary`, and `prepare_attn` releases a temporary binding in a `finally` after its launch. A capture/dummy batch can no longer decide what later launches read, so no post-capture reset hook is needed.

Pre-PR a padded row read the gathered padding row -- all zeros -- so it resolved to block id 0's state slots; now it resolves to request slot 0's block ids. Both are in-range blocks owned by someone, chosen deterministically, and neither is read by a copy: the align copy kernels index by request state slot, not by batch row, so padding rows carry no request anywhere in this metadata.
