# [ROCm][Perf][DSv4.1] Skip the redundant output copy in MoRI finalize

[Upstream PR](https://github.com/vllm-project/vllm/pull/65243) · state: open · merged: False

## Original PR description

## Overview

`MoriPrepareAndFinalize.finalize` copies the first `num_tokens` rows of MoRI's combine output into the modular kernel's `output` tensor (`output.copy_(result[:num_token])`). This PR returns that slice instead, so each MoE layer launches one fewer copy kernel on the MoRI EP path. Within a forward pass, outputs are bit-identical.

Related:
- #44452 (closed, never merged) proposed this for every backend.
- #61361 (MoRI EP v2, merged) keeps the same copy in its own class.
- #65128 adds dual batch overlap to EP v2.
- #53108 and #63412 trim the MoRI dispatch.

See Details.

## Claims

- Removes one device copy (`__amd_rocclr_copyBuffer`) per MoE layer per forward on the MoRI all2all backend. That is about 2.0–2.2 µs standalone at 48–224 tokens per rank on MI350X, and 4.4 µs per layer in a profiled DeepSeek-V4.1-Flash decode step. Over the model's ~43 MoE layers, that's roughly 0.1–0.2 ms per decode step.
- Bit-identical outputs within a forward pass: the experts' results and every reader of the MoE output inside the model see the same values.
- No new env var or config field. One contract changes: for the MoRI backend, the tensor `FusedMoE` returns is now a view of MoRI's combine buffer, valid until the next MoE layer's combine; see Details. Every other prepare/finalize implementation, and the async-finalize path, is unchanged.

## Validation

- **Unit test:** extends `tests/kernels/moe/test_mori_prepare_finalize.py`. It runs on CPU with a fake `mori` module, so the existing `kernels/moe` CI steps run it.
  - At 1, 48, 128 and 224 tokens, the tensor `finalize` returns exactly equals what `output.copy_(buffer[:n])` wrote (dtype, shape and values). It is a view of MoRI's buffer (same `data_ptr`), and `output` is left unwritten.
  - A second test checks that `FusedMoEKernelModularImpl` returns that tensor, or returns `output` when `finalize` returns `None`.
  - On the parent commit, all five new cases fail.

  - **Profile:** in that deployment's decode profile, the copy accounted for 4.4 µs of each MoE layer.

## Details

**Why the copy is unnecessary inside the model:**
- **The buffer's lifetime:** MoRI's `combine` returns a view of one fixed buffer (`comb_out`). MoE layers with the same config share it, so a layer's output stays valid until the next MoE layer's combine.
- **The readers:** every reader inside the model runs on the same stream before that. The shared-expert add (`shared_output + fused_output`) allocates a new tensor, and the residual path consumes the layer output before the next MoE layer.
- **Excluded cases:**
  - Dual batch overlap can't run on this class: `supports_dbo()` is False, and `_finalize` asserts it.
  - The pipeline-parallel send completes before the next step starts.

**Changes:**
- **`modular_kernel.py`:**
  - `FusedMoEPrepareAndFinalizeModular.finalize` may now return an `(M, K)` tensor of its own instead of writing into `output`, and the docstring says so.
  - `FusedMoEKernelModularImpl` uses the returned tensor when it isn't `None`. Every other implementation still returns `None`, so their behaviour is unchanged.
- **`prepare_finalize/mori.py`:** `finalize` returns `result[:num_token]` instead of copying it.

**Limitations and tradeoffs:**
- **Lifetime:** a caller that keeps the result across MoE calls sees it overwritten. `test_mori_moe.py`'s CUDA-graph case does exactly that: it saves `actual = run()`, replays the graph with new inputs, and compares. `TODO:` say how this is handled. Either clone in that test because it holds output across calls (not a weakening of what it checks), or keep the copy for graph-captured paths. State the choice explicitly.
- **Scope:**
  - The async-finalize path (`finalize_async`) is untouched and still copies.
  - #61361 (MoRI EP v2) has merged and keeps the copy in its own class. Dropping it there needs more care, because #65128 adds dual batch overlap to that class, and there the other micro-batch's combine would overwrite a returned view.

**Not duplicated** (searched `2026-11-02`):
- **Commands:** `gh pr list --repo vllm-project/vllm --state {open,merged,closed} --search` with "mori finalize", "MoriPrepareAndFinalize", "mori copy", "prepare_finalize mori" and "mori combine". No open PR removes this copy.
- **#44452** (closed, stale on merge conflicts): the broader version, making every `finalize` return its own output. This PR applies it to MoRI only.
- **#65128, #63412, #53108, #61962 and #64235:** touch MoRI's `prepare`, dual batch overlap or the combine's data type. None removes this copy. #63412 also edits `test_mori_prepare_finalize.py`, in different hunks.
