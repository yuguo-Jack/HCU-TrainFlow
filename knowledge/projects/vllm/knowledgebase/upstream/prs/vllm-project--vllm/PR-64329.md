# [Bugfix] Apply the layer q_scale only to FP8 queries in FlashInfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/64329) · state: open · merged: False

## Original PR description

## Overview

Fixes #63043.

When the query that reaches FlashInfer is BF16/FP16, `FlashInferImpl.forward` still passed the layer's FP8 query scale (`layer._q_scale_float`) to the kernel. FlashInfer multiplies the softmax scale by it, so with a checkpoint that has a non-unit `q_scale` the attention output is wrong. This PR adds `FlashInferImpl.get_q_scale(layer, q_data_type)`. It returns the layer's q scale only for an FP8 query and 1.0 for any other dtype. Every place where the backend hands a q scale to FlashInfer now uses it.

Compared with #53754, this fix:

- No activity in #53754 for 2 months
- Also applies the rule to the cached `self.bmm1_scale`, which trtllm-gen decode and TRTLLM prefill read on SM100. With #53754's change on B200 and `disable_flashinfer_q_quantization`, the end-to-end checkpoint test below still gives garbage text, and the two TRTLLM rows of `test_flashinfer_bf16_query_ignores_q_scale` still fail.
- Has tests that go through the real `FlashInferImpl.forward`. The test in #53754 only calls the new helper. It still passes 4/4 when the helper is added but `forward` keeps the bug.

## Claims

- With a non-unit checkpoint `q_scale` and a query that is not FP8, FlashInfer no longer descales the query. This fixes native prefill, sink prefill, native decode, DCP native decode and trtllm-gen decode.
- An FP8 query still gets the layer's q scale on every path. `get_xqa_bmm1_scale` returns the same values as before.
- Two related defects are not fixed here (see Details).

## Validation

Reproducer (from the issue): a CPU check, with no server and no model. It builds random BF16 Q and FP8 K/V and calls the real `FlashInferImpl.forward`. Only the FlashInfer GPU wrapper is replaced by a CPU stand-in. The stand-in records the `q_scale` it receives and computes attention with it. `error` is the max abs difference from an FP32 reference. The `stored_q_scale=1.0` case is the control.

```python
"""CPU-only argument-boundary repro; the GPU wrapper is a numerical stand-in."""

import os

os.environ["CUDA_VISIBLE_DEVICES"] = ""

from types import SimpleNamespace
from unittest.mock import patch

import torch
import torch.nn.functional as F
import vllm.v1.attention.backends.flashinfer as backend


def main():
    torch.set_num_threads(1)
    generator = torch.Generator(device="cpu").manual_seed(7)
    n, heads, dim = 16, 2, 64
    sm_scale, kv_scale = dim**-0.5, 0.125
    q, k, v = [
        torch.randn(n, heads, dim, generator=generator).to(torch.bfloat16)
        for _ in range(3)
    ]
    k8, v8 = [(x.float() / kv_scale).to(torch.float8_e4m3fn) for x in (k, v)]
    cache = torch.cat((k8, v8), dim=-1).transpose(0, 1).unsqueeze(0)
    kh, vh = [x.float().transpose(0, 1) * kv_scale for x in (k8, v8)]
    scores = (q.float().transpose(0, 1) @ kh.transpose(-1, -2)) * sm_scale
    scores.masked_fill_(torch.ones(n, n, dtype=torch.bool).triu(1), -torch.inf)
    expected = (scores.softmax(-1) @ vh).transpose(0, 1)
    selected = []

    class CPUPrefill:
        _window_left, _logits_soft_cap = -1, 0.0
        _sm_scale, _causal = sm_scale, True

        def run(self, query, kv, *, q_scale, k_scale, v_scale, out, **kwargs):
            selected.append(q_scale)
            result = F.scaled_dot_product_attention(
                query.float().transpose(0, 1),
                kv[0][0].float() * k_scale,
                kv[1][0].float() * v_scale,
                is_causal=True,
                scale=sm_scale * q_scale,
            )
            return out.copy_(result.transpose(0, 1))

    for stored_q_scale in (1.0, 0.25):
        impl = object.__new__(backend.FlashInferImpl)
        impl.__dict__.update(
            bmm1_scale=None,
            bmm2_scale=None,
            scale=sm_scale,
            kv_cache_dtype="fp8",
            is_kvcache_nvfp4=False,
            nvfp4_fa2=False,
            nvfp4_trtllm=False,
            dcp_world_size=1,
            head_size=dim,
            num_kv_heads=heads,
            window_left=-1,
            logits_soft_cap=0.0,
        )
        layer = SimpleNamespace(
            _q_scale=torch.tensor(stored_q_scale),
            _q_scale_float=stored_q_scale,
            _k_scale_float=kv_scale,
            _v_scale_float=kv_scale,
        )
        metadata = SimpleNamespace(
            prefill=backend.FIPrefill(CPUPrefill()),
            decode=None,
            kv_cache_layout=backend.KVCacheLayout.LBHNC,
            num_actual_tokens=n,
            num_decode_tokens=0,
            num_prefill_tokens=n,
            q_data_type_prefill=q.dtype,
            causal=True,
        )
        out = torch.empty_like(q)
        with patch.object(backend, "BatchPrefillWithPagedKVCacheWrapper", CPUPrefill):
            impl.forward(layer, q, k, v, cache, metadata, out)
        error = (out.float() - expected).abs().max().item()
        print(
            f"stored_q_scale={stored_q_scale}: passed={selected[-1]}, error={error:.6f}"
        )
        assert not torch.cuda.is_initialized()
        assert selected[-1] == 1.0, "BF16 Q must not receive FP8 query descaling"
        assert error < 0.01


if __name__ == "__main__":
    main()
```

## Details

Root cause: FlashInfer's `q_scale` is the dequantization scale of an FP8 query ("The calibration scale of query for fp8 input"). FlashInfer multiplies the softmax scale by it and does not check the query dtype. The sink prefill wrapper and the TRTLLM kernels take the same factor folded into `sm_scale` / `bmm1_scale`. vLLM quantizes the query with `layer._q_scale` only when the query that reaches the kernel is FP8 (in `maybe_quant_query`, or earlier in the layer's `query_quant`). But `forward` applied `layer._q_scale_float` at every native call (except NVFP4 fa2) and in the cached `self.bmm1_scale`. `layer._q_scale_float` comes from the checkpoint and is set even when the KV cache is not quantized. The query stays BF16/FP16 in these cases:

- an FP8 KV cache on fa2-only GPUs (SM8x, SM12x);
- an FP8 KV cache with `disable_flashinfer_q_quantization`, on any GPU;
- SM90 native decode;
- an unquantized KV cache.

With a real checkpoint (q scale about 0.03), the output is garbage. With `q_scale == 1.0`, the bug is hidden.

Fix:

- The XQA decode path already had the right rule, in `get_xqa_bmm1_scale`. The rule moves into `get_q_scale`, and `get_xqa_bmm1_scale` now calls it.
- Each of the four native calls passes the dtype of the query tensor it hands to the kernel.
- The cached `self.bmm1_scale` uses `attn_metadata.q_data_type_prefill`. Only SM100 reads it (TRTLLM prefill, trtllm-gen decode), and there prefill and decode use the same query dtype.
- The `1.0 if self.nvfp4_fa2` special case is dropped. The fa2 NVFP4 query stays in the model dtype, so the dtype rule already gives 1.0.
- Not chosen: setting `layer._q_scale_float` to 1.0 when the query is not quantized. On SM90/SM12x one layer runs an FP8 prefill query and a BF16 decode query, so one value per layer cannot be right for both.

Tests:

- `test_flashinfer_bf16_query_ignores_q_scale`: real kernels, q scale 0.25, `disable_flashinfer_q_quantization=True`. Its 6 rows cover FP8 or unquantized KV, native or TRTLLM, and prefill or decode.
- `test_flashinfer_sink_prefill_and_dcp_decode_q_scale`: runs the real `forward` with a `Mock(spec=...)` wrapper that records the scale, because the real kernels need SM90/SM12x (sinks) or several GPUs (DCP). BF16 rows expect 1.0, and FP8 rows expect 0.25.
- `test_flashinfer_bf16_query_with_checkpoint_q_scale`: uses `nm-testing/TinyLlama-1.1B-Chat-v1.0-kvcache-fp8-tensor` (per-layer q scale about 0.03) with FP8 KV. It compares FlashInfer greedy logprobs (with `disable_flashinfer_q_quantization`) against Triton.
- The test helpers get `q_scale` / `layer_q_scale` / `attention_config` arguments. The defaults keep the old behaviour. When the backend takes an FP8 query, the helper now quantizes `query / layer_q_scale`. With the default 1.0, this gives the same values as before.
- The backend tests are in `tests/v1/attention`, which the `V1 Attention` Buildkite step already runs.

Not fixed here (each needs a separate change):

- TRTLLM prefill with a BF16 query over an FP8 KV cache (SM100, `disable_flashinfer_q_quantization=True`) still applies the k/v scales twice. This PR removes the wrong q-scale factor there, but that path is still wrong when `k_scale != 1`.
- DCP prefill (`BatchDCPPrefillWrapper.run`) passes no q scale at all, so an FP8 query there is never descaled.
