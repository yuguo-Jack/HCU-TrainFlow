# [Bugfix][V1] Gate async-scheduling output-token-id repair on a declared logitsproc capability

[Upstream PR](https://github.com/vllm-project/vllm/pull/52698) · state: open · merged: False

## Original PR description

## Purpose

Fixes #52461.

Under async scheduling (default-on since 0.27) the worker pads each request's
output token id list with `-1` placeholders every step; the real ids are only
patched back in when `logitsprocs_need_output_token_ids` is set. Today that flag
is `bool(custom_logitsprocs)` — i.e. it keys off whether a *CLI* custom
processor is present — which is both an under- and an over-approximation of the
real question ("does any loaded processor read output token *values*?"):

- **Stateful processors registered via `BUILTIN_LOGITS_PROCESSORS` are missed.**
  They silently read `-1` placeholders under async scheduling: full per-step
  overhead is paid, results are wrong, and there is no warning. (The three
  in-tree builtins happen to read only the list *length*, so nothing in-tree
  trips over it today — see the reporter's SynthID-Text watermarking case in the
  issue for a real "reads values" consumer: 8/8 detections with
  `--no-async-scheduling` → 0/8 with async scheduling.)
- **Value-agnostic CLI processors are over-counted**, forcing an unnecessary
  device sync in async mode.

## Change

Add a declarative capability to the interface, mirroring `is_argmax_invariant()`:

```python
@classmethod
def needs_output_token_ids(cls) -> bool:
    return True  # conservative default; out-of-tree processors are correct by default
```

- The three in-tree builtins (`MinP`, `LogitBias`, `MinTokens`) override to
  `False` — they read at most `len(output_tok_ids)`, which is unaffected by
  placeholder *values*.
- `LogitsProcessors` ORs the declaration across every loaded processor (builtin
  + entry-point plugin + CLI) and exposes a single `needs_output_token_ids`.
- `GPUModelRunner` feeds that into `InputBatch` instead of
  `bool(custom_logitsprocs)`. Thinking-budget tracking stays dynamic (unchanged).

Net effect: the async-scheduling repair now runs iff some loaded processor
actually reads token values — fixing the silent-wrong-output case and dropping
the needless sync for value-agnostic processors.

## Not a duplicate of #38199

#38199 targets only the entry-point-plugin gap, via a coarser
`LogitsProcessors.has_custom` flag (true for any non-builtin processor). That
leaves the `BUILTIN_LOGITS_PROCESSORS`-registered stateful case in this issue
still broken, and does not help the value-agnostic over-count. The per-processor
declaration here is a superset covering all three cases; happy to coordinate
landing order with that PR.


- Full file: **42 passed** (includes the CUDA `test_logitsprocs[...]` correctness

### End-to-end validation under async scheduling

Ran a discriminating A/B on GPU (RTX A6000, `facebook/opt-125m`, `enforce_eager`,
async scheduling on). A probe `LogitsProcessor` registered via
`BUILTIN_LOGITS_PROCESSORS` snapshots each request's `output_tok_ids` from
`apply()` (single-process, `VLLM_ENABLE_V1_MULTIPROCESSING=0`). Only the probe's
`needs_output_token_ids()` declaration differs between runs:

| `needs_output_token_ids()` | observed `output_tok_ids` in `apply()` | outcome |
| --- | --- | --- |
| `True` (this PR's default for out-of-tree procs) | `[5] → [5, 812] → [5, 812, 9] → …` (real ids) | correct |
| `False` (today's behavior for builtin-registered procs) | `[-1] → [-1, -1] → [-1, -1, -1] → …` | silently reads placeholders |

Both runs produce identical output text (the probe only observes), so this
isolates the output-token-id view. The `False` case reproduces the exact silent
failure from the issue; with the declaration wired through the gate, the async
`-1` repair runs and the processor sees real ids.

### Why this is a V1-runner fix (and V2 does not need the same change)

The V2 model runner (`vllm/v1/worker/gpu/model_runner.py`) does not run
custom/plugin logits processors at all: `_get_v2_model_runner_unsupported_features`
lists `"custom logits processors"` as unsupported whenever
`model_config.logits_processors` or a `vllm.logits_processors` entry point is
present (`vllm/config/vllm.py:2447-2450`), so those configs fall back to the V1
runner. The gate this PR fixes lives on the V1 path, which is exactly where such
processors execute. (The e2e forces `VLLM_USE_V2_MODEL_RUNNER=0` only because
`opt-125m` happens to default to V2; a real custom/plugin processor forces V1 on
its own.)
