# [XPU][Attention] Widen prefill BLOCK_M to 32 for power-of-2 GQA (~2x prefill on BMG)

[Upstream PR](https://github.com/vllm-project/vllm/pull/47246) · state: open · merged: False

## Original PR description

## Purpose

Prefill in the Triton unified attention kernel is matmul-bound, but the default `BLOCK_M=16` (for the common `num_queries_per_kv <= 16` case) leaves the `Q@K` / `P@V` dots too small to saturate the Intel XPU matrix engine — measured a flat **~5.7 TFLOPS on Arc Pro B60 (BMG)** regardless of sequence length.

For prefill (`max_seqlen_q > 1`) on the tensor-descriptor path with **power-of-2** `num_queries_per_kv`, widen the Q tile to `BLOCK_M=32`.

## Why gated to power-of-2 GQA

`BLOCK_M` must stay a power of 2 — the kernel uses `tl.arange(0, BLOCK_M)` and the TD Q-load's `block_shape` must be pow2. Widening a non-pow2 ratio (e.g. Qwen2-7B, 28/4=7) would make `BLOCK_M=28`, which is invalid, so those shapes keep the default. Decode (`max_seqlen_q == 1`) is latency/occupancy bound and a wider tile can regress it, so it is also left at the default. Both are no-ops.

## Test plan / results (Arc Pro B60, bf16, vs a torch SDPA paged reference)

Verified on this branch of `main`. Correct in all cases (outputs identical to baseline):

| Config | before | after | speedup |
|---|---|---|---|
| GQA=4 prefill 4k | 23.9 ms | 12.0 ms | 1.99x |
| GQA=8 prefill 4k | 47.0 ms | 23.6 ms | 1.99x |
| GQA=4 chunked 3x2k | 20.0 ms | 10.4 ms | 1.93x |
| GQA=7 (non-pow2) prefill | 46.1 ms | 46.1 ms | 1.00x (no-op) |
| GQA=4 decode | 0.387 ms | 0.388 ms | 1.00x (no-op) |

### End-to-end (Qwen2.5-3B, 14k-token prefill, `attention_backend=TRITON_ATTN`, median of 5)

| Build | median latency | tok/s |
|---|---|---|
| baseline | 2.936 s | 4361 |
| this PR | 1.947 s | 6574 |

**~1.5x E2E prefill speedup**, reproduced across runs. Note the gain requires the Triton unified backend to be selected — XPU defaults to the FlashAttention backend, which does not use this kernel.

Scope note: this narrows but does not fully close the gap to the vendor CUTLASS/SYCL kernel on prefill; the remainder is a deeper kernel-structure item. This is an XPU-focused tuning change (gated on the TD path); it is a no-op on non-XPU paths that don't set `use_td`.
