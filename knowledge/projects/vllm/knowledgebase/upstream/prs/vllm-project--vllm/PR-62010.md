# [Bugfix][Frontend] Fix auto truncation without an output token limit

[Upstream PR](https://github.com/vllm-project/vllm/pull/62010) · state: closed · merged: True

## Original PR description




## Overview

Fix automatic prompt truncation in Chat Completions and Responses when no output token limit is specified. Previously, truncation could fill the entire context window, leaving no room for generation and causing requests to fail.

## Claims

- Reserve one token for generation when automatic truncation is enabled without an explicit output limit.
- Preserve existing behavior for explicit output limits and zero-output budgets.
- Keep pooling requests able to use the full input context.

## Validation

Added regression tests covering text and token-ID prompts, Chat serving, and unspecified, zero, and positive output budgets.

Validated with `DeepSeek-R1-Distill-Qwen-1.5B` (`max_model_len=512`):

| Request | Before | After |
| --- | --- | --- |
| Chat, output limit omitted | HTTP 400: `max_tokens` is 0 | HTTP 200 |
| Responses, output limit omitted | HTTP 400: prompt fills context | HTTP 200 |

Both requests produced 511 input tokens and 1 output token after the fix. Requests with explicit output limits remained unchanged.

- **54 tests passed**.
- All applicable pre-commit checks passed, including mypy.

```bash
pytest -q \

  tests/entrypoints/openai/responses/test_sampling_params.py \

  tests/entrypoints/openai/chat_completion/test_serving_chat.py::test_serving_chat_mistral_token_ids_prompt_too_long_is_rejected
```

## Details

Both request protocols converted an unspecified output limit from `None` to `0` when constructing `TokenizeParams`. Automatic truncation interpreted this as a zero-output budget, allowing the prompt to fill the entire context window.

Preserve `None` for unspecified output limits so automatic truncation reserves one token for generation. Keep the `TokenizeParams` default at `0` to preserve behavior for callers that do not generate output.

Yes, I reproduced this with online inference using `DeepSeek-R1-Distill-Qwen-1.5B` and `--max-model-len 512`.

**Server:**

```bash
CUDA_VISIBLE_DEVICES=0 python -m vllm.entrypoints.openai.api_server \
  --model /models/DeepSeek-R1-Distill-Qwen-1.5B \
  --served-model-name truncation-test \
  --host 127.0.0.1 --port 18961 \
  --max-model-len 512 \
  --gpu-memory-utilization 0.10 \
  --max-num-seqs 1 --enforce-eager
```

**Reproduction:**

```python
import requests

url = "http://127.0.0.1:18961"
text = "hello " * 1500

cases = [
    (
        "/v1/chat/completions",
        {
            "model": "truncation-test",
            "messages": [{"role": "user", "content": text}],
            "truncate_prompt_tokens": -1,
            "temperature": 0,
        },
    ),
    (
        "/v1/responses",
        {
            "model": "truncation-test",
            "input": text,
            "truncation": "auto",
            "temperature": 0,
        },
    ),
]

for endpoint, payload in cases:
    response = requests.post(url + endpoint, json=payload, timeout=120)
    print(endpoint, response.status_code, response.text)
```

**Results:**

| Endpoint | Before | After |
| --- | --- | --- |
| Chat Completions | HTTP 400: `max_tokens must be at least 1, got 0` | HTTP 200 |
| Responses | HTTP 400: prompt length 512 exceeds `max_model_len` | HTTP 200 |

Both requests used 511 input tokens and generated 1 output token after the fix.

The issue is triggered by an overlong prompt with automatic truncation enabled and no explicit output token limit.
