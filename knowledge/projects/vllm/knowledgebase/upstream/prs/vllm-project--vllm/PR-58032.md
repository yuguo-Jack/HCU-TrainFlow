# [Bugfix][Quantization] Clamp FP8 scales before UE8M0 rounding

[Upstream PR](https://github.com/vllm-project/vllm/pull/58032) · state: closed · merged: True

## Original PR description



## Purpose

Without this PR, [this reproducer][reproducer] crashes during DeepGEMM warmup for `Qwen/Qwen3-30B-A3B-Base` with the DeepGEMM FP8 linear backend.

`QuantFP8._quantize_group_native` previously rounded activation scales to UE8M0-compatible powers of two before applying `_FP8_MIN_SCALING_FACTOR`. For zero or sufficiently small activation groups, the subsequent clamp replaced the rounded value with `_FP8_MIN_SCALING_FACTOR`, which is not a power of two. DeepGEMM requires FP32 scale factors used for UE8M0 packing to have zero sign and mantissa bits, so these clamped scales triggered a device assertion while DeepGEMM packed them.

This PR applies the minimum-scale clamp before UE8M0 rounding. The resulting scale therefore remains at least `_FP8_MIN_SCALING_FACTOR` while satisfying the exponent-only representation expected by DeepGEMM. The non-UE8M0 path retains its existing behavior.

The existing group-quantization edge-case test is extended to cover an all-zero input with UE8M0 enabled. It verifies both the minimum-scale bound and the zero-sign-and-mantissa invariant enforced by DeepGEMM.

[reproducer]: https://gist.github.com/rao-ashish/8a648b7aadbf4380bc3a6e643b1cb471

## Test Result

- The targeted pytest test passes.
- Before this change, the reproducer triggers the assertion in `smxx_layout.cuh` that FP32 scale factors must have zero sign and mantissa bits, followed by `CUDA_ERROR_LAUNCH_FAILED`.
- After this change, the reproducer completes model initialization and DeepGEMM warmup without that assertion or CUDA launch failure.
- No documentation update is needed because this only corrects existing quantization behavior.
