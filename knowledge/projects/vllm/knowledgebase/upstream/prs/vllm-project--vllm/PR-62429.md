# [Rust Frontend] Emit transfer params at the top level of render output

[Upstream PR](https://github.com/vllm-project/vllm/pull/62429) · state: closed · merged: True

## Original PR description



## Overview

Since vllm-project/vllm#61241, Python's render routes (`/v1/chat/completions/render`, `/v1/completions/render`) emit `kv_transfer_params` and `ec_transfer_params` only as top-level `GenerateRequest` fields, and `/inference/v1/generate` copies them back into `extra_args`. Rust render still leaves both top-level fields unset and keeps the values inside `sampling_params.vllm_xargs`, so a Rust render followed by a Python generate drops the P/D and E/PD transfer params. This PR makes Rust render hoist them the same way.

## Claims

- Rust render output carries `kv_transfer_params` / `ec_transfer_params` at the top level and no longer inside `sampling_params.vllm_xargs`, matching Python's `_hoist_transfer_params` (`vllm/entrypoints/scale_out/render/serving.py`).
- `vllm_xargs` is dropped from the render output when nothing else is left in it, like Python setting `extra_args` to `None`.
- Rust render → Rust generate is unchanged: Rust generate already merges the top-level fields back into `vllm_xargs` (`routes/inference/generate/convert.rs`), and the round-trip test now checks that both params reach the engine request's `extra_args`.

`render_chat_response_can_be_submitted_to_generate_unchanged` now sends both transfer params through the render → generate round trip and asserts that they appear at the top level of the render output, that `vllm_xargs` keeps only the unrelated `custom` key, and that both reach the engine request's `extra_args` after generate. With the `render.rs` change reverted, the test fails on the `vllm_xargs` assertion: `{"custom": 1, "ec_transfer_params": {...}, "kv_transfer_params": {...}}` vs `{"custom": 1}`.

## Details

- **Layering.** The render route owns its output wire shape, so the hoist lives in `routes/render.rs` next to `lower_render_request`, mirroring Python's helper. Chat/completions lowering and the shared `merge_*_transfer_params` helpers stay unchanged; generate and the OpenAI routes use them to feed the engine.
- **Non-object values.** A value under `vllm_xargs.kv_transfer_params` that is not a JSON object cannot fit the typed top-level field. It stays where the request put it, which is the current behavior. Python's `vllm_xargs` does not accept object values, so Python never sees this case.
- **Out of scope.** Rust render still emits other xargs under `sampling_params.vllm_xargs`, while Python generate reads `extra_args`; switching that key depends on Rust generate accepting `extra_args` and is left to a follow-up.
- **Duplicate check.** No open PR covers this. Searched open PRs for render/transfer-param and Rust render keywords: vllm-project/vllm#60002 (render token offsets) touches `render.rs` but not the transfer params, and vllm-project/vllm#56814 (reject reserved transfer keys inside `vllm_xargs` at the request merge) is adjacent but does not change the render output shape.
