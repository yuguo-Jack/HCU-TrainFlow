# [ROCm][Quantization] Add FP8 block GEMM configs for gfx1100 (AMD_Radeon_Graphics)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65393) · state: open · merged: False

## Original PR description

Adds six tuned config files for `device_name=AMD_Radeon_Graphics`.

Related: #52663. I found that issue after I'd already spent a day on this, and the configs
posted in the thread are close to what I ended up with, so this is partly an attempt to actually
get something merged there.

### The problem, briefly

On gfx1100 the FP8 block-scaled GEMM is JIT-compiled when the engine starts. With the built-in
fallback (`BLOCK_SIZE_M=64`) a single kernel variant takes ~13 minutes to compile, and a 1.5B
model needs ~39 minutes from process start to the first token. That's a 600s engine-ready
timeout blown by a factor of four, which is what #52663 is about.

With these files on the same box, same model, same run, cold `TRITON_CACHE_DIR`:

| | fallback (BM=64) | this config (BM=32) |
|---|---|---|
| engine init | 778.1 s | 148.4 s |
| first generation | 1542.9 s | 270.5 s |
| start → first token | 2321.0 s (38.7 min) | 418.9 s (7.0 min) |
| second generation (warm) | 7.82 s | 5.28 s |

I also checked I wasn't trading steady state for startup. Three batch sizes, median of 5 rounds,
run-to-run spread under 0.1%:

| batch | fallback tok/s | this config | speedup |
|---|---|---|---|
| 1 | 4.09 | 6.07 | 1.48x |
| 4 | 16.00 | 24.10 | 1.51x |
| 8 | 31.83 | 47.84 | 1.50x |

Both get better.

### Why one config for every M

This is the part I'd like people to push back on if I've got it wrong.

Compile cost here is set by the tile size of the constant tuple, not by `BLOCK_SIZE_M` alone,
and it's flat with respect to the matrix shape (compile a tuple once, and a different `(N, K)` is
a ~0.1s cache hit). All of these are measured with `benchmarks/kernels/benchmark_w8a8_block_fp8.py`
from this repo, cold `TRITON_CACHE_DIR`:

| BM x BN | elements | num_warps=4 | num_warps=8 |
|---|---|---|---|
| 16 x 64 | 1024 | 6.2 s | — |
| 16 x 128 | 2048 | 20 s | — |
| 32 x 128 | 4096 | 135 s | 18.7 s |
| 64 x 64 | 4096 | 145 s | — |
| 64 x 128 (the fallback) | 8192 | 779 s | 142 s |
| 128 x 128 | 16384 | didn't finish in 52 min | — |

Roughly 6-7x per doubling of the tile, and `num_warps=8` buys back about one doubling.

So the fallback sits at the worst point we measured, which is where the 39 minutes comes from.
And the per-M tables in #52663 come out to 12 distinct tuples across their five shape files. Each
of those is a separate compile of the same kernel. Adding up the measured points that's around
22 minutes for those files, against 135s for the single tuple here. If one of those entries is
unlucky (the 128x128 one, for instance) it's much worse than 22.

The existing per-M tables make sense when compilation is cheap, which is true on the datacenter
parts. It isn't here, so tuning per M spends minutes of startup to buy a few percent of runtime.
Hence one tuple for the whole model.

### Why 32 and not 16

16 is cheaper to compile (20s) and faster in decode, but prefill falls off a cliff. Relative to
the BM=64 fallback, same harness:

| | decode (M=1) | prefill (M=2048) |
|---|---|---|
| BM=16 | 0.51-0.53x | 1.39-1.57x (39-57% slower) |
| BM=32 | 0.67-0.69x | 0.97-1.07x |

32 is the knee. Wider check across 4 fused shapes x 5 M values: BM=32 wins 17 of 20 against
BM=64, ties 1, loses 2. The two losses are both N=17920 in prefill, 4.6-5.6%.

### Files

Six shapes, taken from what a Qwen2.5-1.5B actually asks for on this GPU. Note N=2048 and not
3x1536, vLLM fuses q/k/v:

```
N=1536,K=1536
N=1536,K=8960
N=2048,K=1536
N=256,K=1536
N=8960,K=1536
N=17920,K=1536
```

Each has the same 18 M keys (`1`...`16384`), all pointing at `BLOCK_SIZE_M=32,
BLOCK_SIZE_N=128, BLOCK_SIZE_K=128, GROUP_SIZE_M=32, num_warps=4, num_stages=2`.

Filenames follow `get_device_name_as_file_name()`, which gives `AMD_Radeon_Graphics` on this card
because `0x744b` isn't in `_ROCM_DEVICE_ID_NAME_MAP` yet (#65392 is the one-line PR for that). If
that lands first these six need renaming.

### Verifying

`vllm bench serve --model <fp8 block-quantized model>`, then look for
`Using configuration from .../N=...,K=...json` in the log. Without the files you get
`Using default W8A8 Block FP8 kernel config`.

### What this doesn't claim

I'm not going to argue that FP8 is the right quantization format for RDNA3 — there's a fair point
in the #52663 thread that the FP8 path is emulated and the gains are modest. My take is narrower:
if vLLM supports FP8 block quantization on this card, which it does, then it shouldn't be missing
its tuned configs and make people eat a 30-minute first start.

Also, only tested on gfx1100 / 48 GB / ROCm 7.2.4 / torch 2.13.0+rocm7.2 / triton 3.7.1, single
GPU, TP=1. Other RDNA3 cards that also report `"AMD Radeon Graphics"` will pick these files up —
that's the market-name fallback being what it is, these files can't fix it.
