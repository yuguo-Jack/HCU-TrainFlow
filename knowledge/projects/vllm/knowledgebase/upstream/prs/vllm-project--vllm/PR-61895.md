# [ROCm][Perf] Any-shape low-latency MoE router GEMM on MI355

[Upstream PR](https://github.com/vllm-project/vllm/pull/61895) · state: closed · merged: True

## Original PR description



## Overview

On MI355 (gfx950), the MoE router GEMM now has a low-latency kernel for **any** router shape (fp32 or bf16 weights, fp32 output, M ≤ 32), matching the CuTeDSL `ll_fp32w` / `ll_bf16` router kernels from #44343 and #50174. Previously only five hard-coded `(hidden_size, num_experts)` shapes had a fast path; every other model paid 9–13 µs per MoE layer per decode step in `F.linear` / hipBLASLt.

## Claims

- **Decode 1–14% faster** on all 8 tested MoE models whose router path changes, largest at low concurrency.
- **No accuracy change**: GSM8K matches `main` on every model (paired McNemar p = 1.0 and 0.34 where runs varied most).
- **No regressions**: prefill, an unchanged-path control (Qwen3-30B-A3B) and the 5 previously tuned shapes stay flat; shapes where the kernel would lose keep today's path.
- **New MI355 CI job** mirroring `(B200) Gate Linear CuTeDSL Kernels`.

Changes:

- Generalize `rocm_fp32_router_gemm` to any shape: masked K tail, MI355-swept launch rule, bf16 weights, size guards
- `GateLinear`: enable the fp32 router tier on gfx950 for any shape and route bf16-weight fp32-logit gates (tier 6) through the same dispatch op
- Extend `test_rocm_fp32_router_gemm.py` and fix the now-outdated rejection test in `test_gate_linear_rocm_dispatch.py`
- Add `:amd: (MI355) Gate Linear Router Kernels` (B200 mirror + optional `test-amd.yaml` entry) and move the 3 ROCm router test files there from MI355 Misc

<details>
<summary>Methodology and accuracy details</summary>

- `vllm bench serve`, random dataset, prefix caching off, 1–8 input / 256–512 output tokens. `main` and the PR were served at the same time on separate GPUs, alternating every run, with GPU load logged each rep.
- GSM8K: lm_eval 5-shot chat, median of 3+ runs.
- Nemotron and DeepSeek-V4 were re-run with `--log_samples` for a paired per-question test. Nemotron PR vs `main`: 9 / 9 discordant, McNemar p = 1.0; `main` vs `main` A/A: 9 / 6, p = 0.61. DeepSeek-V4: 3 / 7 in the PR's favor, p = 0.34. An earlier DeepSeek-V4 round read 96.06 → 95.53; the repeat did not reproduce it.
- ERNIE's −0.7% prefill is within the 0.3–0.5% spread between GPUs, which a GPU-swap A/B confirmed. Trinity's prefill TTFT ranges overlap.
- **Why decode improves:** one router GEMM per MoE layer per step drops from 9–13 µs (`F.linear`) or 5–11 µs (hipBLASLt) to 1.9–4.9 µs at ≤ 8 tokens, saving 0.2–0.6 ms per step. Prefill and large batches never reach the kernel.

</details>

<details>
<summary>Design details, scope and related PRs</summary>

- **Launch rule:** one program computes `BLOCK_M` tokens for one expert. Narrow routers (< 64 experts) keep `BLOCK_M = 1`; wide routers grow it with the token count. Fitted on 12 shapes, checked on 10 held-out shapes: within 1.11× of the per-shape best and faster than the fallback everywhere.
- **Size guards:** at M·N·K ≥ 2^27 (fp32) or tokens × experts > 8192 (bf16) the fallback is faster, so the kernel declines and today's path runs.
- **Compile safety:** runtime branching stays inside the existing `fp32_router_gemm_dispatch` custom op.
- **Scope:** gfx950 only; gfx942, CUDA, biased/quantized gates and batch-invariant mode are unchanged.
- **Not covered end to end:** MiniMax-M2.5-MXFP4 decodes at ~196 ms/token on both `main` and the PR, so the difference is unmeasurable. Kimi-Linear-48B and LongCat-Flash-Lite-FP8 crash on unmodified `main`, unrelated to this change. Their router shapes are covered by the kernel tests.
- **Related PRs:** #59023 does the bf16 extension for Kimi-K3's 7168×896 gate only (this PR gives the same M ≤ 9 limit there, for any shape). #57626 forces fp32 weights for the 5 listed shapes instead; this PR runs bf16 weights directly with no fp32 copy. #61687 targets a separate AITER tier and is orthogonal.

</details>
