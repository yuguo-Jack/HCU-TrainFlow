# [XPU] Implement stateless_init_device_torch_dist_pg for XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/57196) · state: open · merged: False

## Original PR description

## Purpose

`stateless_init_torch_distributed_process_group` (`vllm/distributed/utils.py:576`) has two
arms: `gloo` goes to `init_gloo_process_group`, and every other backend is dispatched to
`current_platform.stateless_init_device_torch_dist_pg`. `Platform` leaves that classmethod
as `raise NotImplementedError` (`vllm/platforms/interface.py:1191`); `CudaPlatform`
(in `cuda.py`) and `RocmPlatform` (in `rocm.py`) override it, and `XPUPlatform` does not.

So on XPU, any caller asking for a device-backend stateless group gets
`NotImplementedError` — even though `XPUPlatform.dist_backend` already returns `"xccl"` and
`torch.distributed.is_xccl_available()` is true on a normal XPU torch build. The in-tree
caller affected today is `vllm/distributed/stateless_coordinator.py:126`, which builds its
device group with `backend=backend` (the CPU group next to it, line 135, is hardcoded
`gloo` and is unaffected).

This PR implements the missing method for XPU with `ProcessGroupXCCL` and
`ProcessGroup.BackendType.XCCL`, following `CudaPlatform`'s implementation step for step.

Scope notes:

- **No behaviour changes on any existing path.** `ParallelConfig.stateless_init_dp_group`
  (`vllm/config/parallel.py:685`) hardcodes `backend="gloo"`, as do both fault-tolerance
  sentinels (`vllm/v1/worker/sentinel/gpu_worker_sentinel.py:62`,
  `vllm/v1/fault_tolerance/engine_core_sentinel.py:161`). None of them reach the platform
  hook, so DP group formation is untouched. This only turns a raise into a working group
  for callers that explicitly request the device backend.
- Related history: #18763 introduced this hook, #22243 made DP group init
  platform-dispatchable, and #31107 reported that a non-gloo implementation hung on a
  CPU-based communication check. That check is no longer present in
  `stateless_init_torch_distributed_process_group` on current `main`, and the DP path is
  back to unconditional `gloo`, so neither hazard applies here.

## Why this is not duplicating an existing PR

```

gh api "search/issues?q=repo:vllm-project/vllm+is:pr+xccl+stateless"                               # 0, any state
```

No open PR implements this method for any platform. #46210 (`add torchcomms backend for
xpu support`) is the only other open PR editing `vllm/platforms/xpu.py`, but it changes
`get_device_communicator_cls`; there is no textual or semantic overlap with this change.
#53076 touches `xpu_worker.py`/`envs.py` only.

## Test Plan

```bash
pre-commit run --files vllm/platforms/xpu.py
```

Functional verification is end-to-end rather than by unit test: a unit test for this method
needs two real XPU devices to complete the XCCL rendezvous, which no CI lane in this repo
currently provides. Rather than add a test that would be skipped everywhere, the method was
exercised through a stateless-process-group consumer on hardware — a TRL GRPO server-mode
weight-transfer run, where a vLLM server process and a separate trainer process form an
ad-hoc 2-rank group over this code path.

## Test Result

- `pre-commit run --files vllm/platforms/xpu.py`: all hooks pass, including
  `Run mypy for Python 3.10`, `Check SPDX headers`, and `Prevent new 'torch.cuda' APIs call`.
- On 2x Intel Arc Pro B70 (`xccl`, TP=1, one card per process): the group forms, both ranks
  log joining it, collectives complete against real tensors, and both processes exit
  cleanly. Before this change the same path raised `NotImplementedError` at group
  construction.

No model evaluation is included: this change adds a process-group constructor and does not
touch sampling, kernels, scheduling, or any code on a forward pass, so it cannot affect
model output or accuracy. It is unreachable unless a caller explicitly requests a non-gloo
stateless group.

## Notes

This change is a requirement for a PR enabling XCCL weight transfer needed for reinforcement learning scenarios.
