# [Security] Keep prefill truncation state internal to each request

[Upstream PR](https://github.com/vllm-project/vllm/pull/64964) · state: open · merged: False

## Original PR description

## Overview

Keep producer-side prompt-truncation state on the internal `Request`, rather than in client-supplied KV-transfer metadata. Apply the same control to NIXL pull/push, Mooncake, and MoRIIO READ/WRITE.

## Claims

- A client-supplied `_p_side_truncated` value cannot suppress the producer's required N-1 cut.
- Re-admitting the same request remains idempotent; separate requests sharing sampling metadata each receive their own cut.
- Transfer schemas and normal backoff rules are unchanged.

## Details

1. The frontend forwards KV-transfer metadata into a new engine `Request`.
2. Producer admission checks whether prompt truncation has already happened. Reading that guard from client metadata lets the producer skip its cut while the decoder still expects N-1 tokens.
3. A fresh internal flag now starts false and becomes true only after the producer truncates. Re-admission reads that same request-owned state.

All entry points constructing engine requests, including library, HTTP, batch, gRPC and MultiConnector paths, reach the same protected scheduler hooks. No broader peer validation or block-pairing changes are included.

Duplicate-work review: read the relevant diffs for #59330, #58556, #53523, #53663, #37310, #51052, #50063, #47843, #54807, #64891, #63610, #64096, #50897, #63425, #55374, #55589, #56874, #62453, #64371, #54411, #53298 and #59793. None moves or protects this marker. In particular, #59330 retains the client-dictionary guard; this patch adds the missing state ownership control.
