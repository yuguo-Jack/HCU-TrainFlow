# [Bugfix][CPU] Use the PyTorch GDN conv path on macOS

[Upstream PR](https://github.com/vllm-project/vllm/pull/65320) · state: open · merged: False

## Original PR description



## Overview

On macOS arm64 CPU, Gated DeltaNet models such as Qwen3.5 fail to load in bf16 since #54093. The C++ causal conv1d kernels are not built on Apple, but the Python checks still select them. This makes the checks look at the compiled ops, so Apple uses the PyTorch conv path again, as it did before #54093.

## Claims

- Fixes `AttributeError: '_OpNamespace' '_C' object has no attribute 'causal_conv1d_weight_pack'` when loading GDN models on Apple Silicon CPU.
- Prefill and decode on Apple take the PyTorch conv path; outputs match Transformers (fp32).
- No change on Linux aarch64 or x86, where the kernels are built.

## Validation

MacBook Air M2 (8 GB), macOS, CPU build of `a801d9ea3`, `Qwen/Qwen3.5-0.8B`, bf16, `language_model_only=True`, `enforce_eager=True`.

bf16 is the default here: `CpuPlatform.supported_dtypes` enables it on M2 and later (`FEAT_BF16`), so `vllm serve Qwen/Qwen3.5-0.8B` with no `--dtype` hits this.

**Before:** model loading fails in `dispatch_cpu_unquantized_gemm`:

## Details

**Root cause.** #54093 builds `csrc/cpu/sgl-kernels/conv.cpp` only on aarch64 Linux (`ASIMD_FOUND AND NOT APPLE_SILICON_FOUND` in `cmake/cpu_extension.cmake`, `!defined(__APPLE__)` in `torch_bindings.cpp`). The Python side selects the kernels with `is_arm_bf16()`, which is also true on M-series CPUs:

- `dispatch_cpu_unquantized_gemm` checks `hasattr(ops, "causal_conv1d_weight_pack")`. `ops` is `vllm._custom_ops`, whose wrapper always exists, so the check always passes and it calls the missing op.
- `gdn_attention.py` calls `ops.causal_conv1d_fwd_cpu` / `causal_conv1d_update_cpu` whenever `is_arm_bf16()` is true.

**Fix.** Both checks now use `hasattr(torch.ops._C, "causal_conv1d_weight_pack")`, the same pattern used for other optional CPU ops (e.g. `init_shm_manager`). The weights are then left unpacked and `gdn_attention.py` uses the existing PyTorch conv path. The kernel tests that skip on `is_arm_bf16()` now skip on Apple.

**Tests.** The existing prepack test now mocks the op on `torch.ops._C` instead of the Python wrapper. Two small tests check that neither path selects the kernels when the op is missing.

**Limitations.**
- The macOS smoke test runs on M1 (no BF16) with a non-GDN model, so CI cannot catch this. The new tests run on Linux by simulating the missing op.
- Building `conv.cpp` on Apple would also work, but needs Apple Clang support for `conv_arm.h` and is a separate change. This PR only stops selecting a kernel that is not built.
- Not checked on macOS: speculative decoding with GDN.

Not a duplicate: searched open PRs and issues for `causal_conv1d_weight_pack`, `is_arm_bf16`, `54093 in:body`, "macOS CPU GDN" and "Apple Silicon CPU Qwen3.5". #55876 references #54093 but does not touch these checks. #64863 (draft) moves the same `utils.py` line to `cpu_ops` without changing behaviour; whichever lands second needs a small rebase.
