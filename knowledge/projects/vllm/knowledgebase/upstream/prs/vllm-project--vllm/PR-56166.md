# [Bugfix][KVConnector] Report Mooncake P2P pull failures to the scheduler

[Upstream PR](https://github.com/vllm-project/vllm/pull/56166) · state: closed · merged: False

## Original PR description

# [Bugfix][KVConnector] Report Mooncake P2P pull failures to the scheduler

Fixes #55870.

## Problem

Mooncake P2P pull failures on the decode side are currently only logged. The scheduler is never notified, so affected requests can remain stuck in `WAITING_FOR_REMOTE_KVS` until the client times out.

Three failure paths drop the error:

- `_connect_to_prefiller_bootstrap()` does not propagate bootstrap failure to callers.
- `handle_new_engine_id()` bare-returns when the remote engine is unavailable, abandoning the pending `PullReqMeta`s.
- `process_pulling_result()` handles `ok_reqs` but only logs `err_reqs`.

The scheduler already supports recovery through `KVConnectorOutput.invalid_block_ids`: affected blocks are invalidated and recomputed. `NixlConnector` already reports both handshake and transfer failures through this mechanism; Mooncake P2P was missing the equivalent wiring.

## Change

In `mooncake_connector.py`:

- Add `fail_pull_reqs()` to:
  - enqueue failed requests' `local_block_ids` for invalidation,
  - report them through `finished_recving_reqs`,
  - record failed-transfer stats.
- Make `handle_new_engine_id()` fail pending pulls when bootstrap discovery does not produce a remote engine.
- Map `err_reqs` back to `PullReqMeta` in `process_pulling_result()` and report them as failed.
- Implement and forward `get_block_ids_with_load_errors()`, matching the NIXL connector.

`queue.Queue` is used because the receiver event loop produces invalid block IDs while the worker thread drains them.

## Not a duplicate

Related Mooncake PRs address different issues:

- #55137 / #55763: producer-side bootstrap registration/retry behavior.
- #55297: `MooncakeStoreConnector` load retry behavior.
- #55523 / #54421 / #51978: mixed-TP, piecewise, and layerwise transfer changes.

Those changes may reduce bootstrap failures; this PR handles requests correctly when a failure still occurs.

## Tests

Added two fault-injection tests:

- `test_bootstrap_discovery_failure_reports_terminal_failure`
- `test_transfer_error_reports_terminal_failure`

Both verify that failed requests are reported through `finished_recving_reqs` and their blocks are returned exactly once by `get_block_ids_with_load_errors()`.

Results on RTX PRO 4000 Blackwell, CUDA 13.0:

```text
new tests                                      2 passed
new tests with fix reverted                    2 failed
test_mooncake_connector + test_mooncake_stats 91 passed
KV load failure/recovery tests                16 passed
pre-commit                                    passed
```

With the fix reverted, the new tests fail because the request never reaches `finished_recving_reqs`, reproducing the failure mode from the issue.

Validation is unit-level; I did not run a full disaggregated P/D deployment. Scheduler-side rescheduling/recomputation is covered by the existing invalid-block recovery tests and uses the same mechanism already exercised by `NixlConnector`.
