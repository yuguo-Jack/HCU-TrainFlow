# [KV Connector] Mooncake store: skip padding in stored KV blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63513) · state: closed · merged: True

## Original PR description

## Purpose

In a hybrid model, the KV cache groups share one allocation. Layer `j` of every group is a view of the same layer slot, there are as many slots as layers in the largest group, and each slot's page is sized for the largest per-layer state. Groups are kept apart by block ids: a block belongs to one group at a time.

The Mooncake store connector registered every layer for every group, and copied whole pages. So each value of a Mamba / linear-attention group also held:

- the layer slots of the group's padding layers, which only other groups use, and
- the padding of each state up to the page size.

Kimi K3 (DCP8) has 3 KDA groups of 23 layers and 1 attention group of 29 layers (24 MLA + 5 drafter), sharing 29 slots of 516,096 B per block. Every key therefore stored 29 × 516,096 B = **14.97 MB**. A KDA group uses only 23 slots, and each KDA state is 457,728 B. The real data is 23 × 457,728 B = **10.53 MB**, so **30% of every KDA value was bytes the group does not use**: 20.7% is the 6 slots of other groups and 9.0% is state padding. A saved KDA state (3 KDA groups × 8 DCP ranks = 24 keys) drops from about 359 MB to 253 MB.

This PR:

- **Registers each group's own layers only.** Each group's values are built from the regions of that group's own layers, with each Mamba state view as its own region.
- **Copies only the used bytes of each block.** `RankLocalStoreLayout` now keeps `block_len` next to `block_stride`. `block_stride` is still the stride used to find a block in the GPU cache, and `block_len` is the number of bytes copied from it: up to the last byte the group uses. Mooncake stores the concatenation of the copied pieces, so the padding never reaches the store.

Keys are unchanged. A model with a single KV cache group, or an attention group without padding, stores the same bytes as before. If a group has no layers on a PP rank, its keys are still written from all layers' regions, as before. HiSparse and TP-shared layouts are unchanged.

A Mamba value now has one region per state view instead of one per layer slot. The measured put and get times still go down (below).

## Test Plan

- Unit tests (`tests/v1/kv_connector/unit/`, all 376 Mooncake store tests pass). The new or changed tests below fail on main:
  - `test_rank_local_layout_skips_block_padding`: on a layer-outermost buffer, checks the regions, `block_stride` and `block_len`, `prepare_values` sizes (single and multi-block chunks), and `prepare_value_for_block`.
  - `test_hybrid_mamba_values_hold_only_group_states`: an attention group and a padded Mamba group are overlaid by `allocate_kv_cache`, and each Mamba layer has two state views of different dtypes with a gap between them. The test checks that the saved value is exactly the states of the block. It then clobbers the block and restores it: only the state bytes come back; the gap, the padding and the attention-only layer slot are untouched.
  - The SWA HMA test now also checks that each group registers only its own region.
- Accuracy, Kimi K3 agg (TP8 + DCP8, dspark4 MTP with real rejection): GSM8K 50-shot, two passes. Prompts are ~8.1k tokens, which is more than one 7,168-token store block. Between the passes the GPU prefix cache is reset with `/reset_prefix_cache`, so pass 2 loads from Mooncake.
- Perf A/B, Kimi K3 agg (2 GB300 nodes, 1.28 TB Mooncake store, agentic coding traces, 60 min, concurrency 64/80/96). The base build is the same build without this commit.
