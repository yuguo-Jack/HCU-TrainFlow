# [Bugfix][NIXL] Fail closed on HMA receive errors

[Upstream PR](https://github.com/vllm-project/vllm/pull/52232) · state: open · merged: False

## Original PR description

## Summary

NIXL receive failures are currently propagated through flat block IDs. That
works for uniform KV caches, but HMA block IDs are scoped to independent pools,
so the worker intentionally omits them. The failed request is then reported as
finished receiving without any failure signal, allowing decode to continue with
invalid KV.

This change:

- propagates unrecoverable HMA receive failures by request ID;
- aggregates that signal across workers until the receive is complete;
- applies the same aggregation to uniprocess execution so failure and completion
  notifications cannot be split across scheduler steps; and
- fails the request before consuming any sampled tokens, regardless of the
  block-recovery policy.

Uniform-cache failures keep the existing block-level fail/recompute behavior.

## Duplicate-work check

This is not duplicated by an open PR:

- #40364 fixed handshake-failure recovery through `invalid_block_ids`, but
  explicitly left HMA failure handling as a TODO because its block IDs are not
  group-qualified.
- #50754 reports push-side write-posting failures to the decode worker; it still
  relies on the downstream receive-failure path fixed here.
- #50494 and #48263 extend supported HMA layouts rather than propagating failed
  receives to the scheduler.

The serving regression was reproduced with Gemma-4-26B FP8, NIXL HMA,
prefill block size 128, and decode block size 64. Both runs used the same
Manifesto-rendered PD topology and EPP always-disaggregated routing:

- current main `71b0da7c4e`: the compatibility hash passed, the NIXL handshake
  then raised the heterogeneous-block-size assertion, and the API returned
  HTTP 200 with 64 tokens of gibberish despite zero successful KV transfers;
- this change `9e80dac9eb`: the identical handshake failure logged
  `Failing 1 request(s) due to unrecoverable KV receive failure` and the API
  returned HTTP 500 with only an error object—no choices, content, usage, or
  generated tokens.

No model-quality evaluation is applicable: successful KV transfer and model
output paths are unchanged. The serving validation targets the changed failure
path and asserts that no generated tokens escape.

Thanks for this fix. Additional serving validation with **DeepSeek-V4-Flash-0731, TP1 P/D, fp8 HMA KV, NIXL 1.3.2** confirms the need for request-level HMA failure propagation. It also exposed a streaming API edge case.

I adapted this PR's HMA changes to main `8369affa5`. An existing TP1 packed-layout fix and a separate local peer-recovery candidate were present in the comparison. The test deliberately removed only Decode's local remote metadata, with no active reads, while Prefill stayed alive with the same engine ID. A subsequent real NIXL read failed with `NIXL_ERR_NOT_FOUND`. This is controlled native invalidation, not a reproduction of a natural UCX disconnect.

| Configuration | Failure response | Generated tokens |
|---|---|---:|
| Before HMA fix, Chat non-streaming | HTTP 200, invalid output | 32 |
| With HMA fix, Chat non-streaming | HTTP 500, `InternalServerError` | 0 |
| With HMA fix, existing Chat streaming handler | HTTP 200, role/usage/`[DONE]`, **no error event** | 0 |
| With HMA fix + API follow-up, Chat and Completion non-streaming | HTTP 500, `InternalServerError` | 0 |
| With HMA fix + API follow-up, Chat and Completion streaming | HTTP 200, SSE error code 500, then `[DONE]` | 0 |

**API follow-up:** both streaming handlers skip empty text/token output before `_raise_if_error`. A terminal failure before the first token can therefore disappear. Moving the existing terminal error check before that filter/parser handling fixes this without changing the SSE error schema. The final Completion failure response was:

```text
data: {"error": {"message": "Internal server error", "type": "InternalServerError", "param": null, "code": 500}}

data: [DONE]
```

- Focused API regressions (before/after first token, with/without usage): existing handlers **4 expected failures / 4 passes**; follow-up **8 passes**.
- Combined selected connector/HMA/aggregation/executor/API regressions: **425 passed**.
- Final serving scenario: **10 requests passed** (2 normal, 4 native failures, 4 fresh Chat recoveries). Failed requests emitted no generated content; fresh requests re-handshook and returned the expected answers without restarting either engine during the scenario. This is failure-path validation, not general model-accuracy or performance evidence; multi-rank native races and RDMA/NVLink were not tested.

[Full evidence bundle](https://gist.github.com/xijiaat/a975858a507d6c45fd394b3675cc0ab9): complete selected logs, responses/SSE, exact test command transcript, and separate patches for the tested integration and API follow-up. Internal addresses/paths are anonymized and terminal carriage returns normalized; no lines of the selected logs were removed. The integration, tests and this report used OpenAI Codex assistance. The HMA propagation implementation is credited to this PR, not claimed as a separate fix of mine.
