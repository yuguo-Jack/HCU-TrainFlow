# [Feature][LoRA][MoE] Expert LoRA for FlashInfer TRTLLM MXFP4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/61979) · state: closed · merged: True

## Original PR description

## Overview

Add expert LoRA to the fused FlashInfer TRTLLM MoE kernel for MXFP4 expert weights with BF16 activations (`TrtLlmMxfp4LoRAExperts`, next to `TrtLlmBf16LoRAExperts`). TP > 1 relies on #61235 (merged).

## Claims

- MXFP4 MoE models can serve expert LoRA adapters on `moe_backend="flashinfer_trtllm"` instead of falling back to Marlin / unfused Triton.
- Opt-in: `moe_backend="auto"` selects the same backend as before. `flashinfer_trtllm_afp8` (MXFP8 activations) with expert LoRA is rejected with an explicit reason.
- Requires FlashInfer >= 0.6.18 (`gemm1_lora_delta` on `trtllm_fp4_block_scale_routed_moe`, flashinfer-ai/flashinfer#3987); vLLM pins 0.7.2.

## Validation

Environment: `vllm/vllm-openai` nightly arm64 image built from `af7f9488c` (flashinfer-python 0.7.0, torch 2.13.0+cu130), NVIDIA GB300, with the changed files of this PR and #61235 backported onto that commit and mounted over the image. Not run on the PR base itself; the changed files apply to it without conflicts.

**Kernel-level** — `pytest tests/lora/test_trtllm_mxfp4_lora_moe.py -v`: 9 passed. Random MXFP4 weights through vLLM's TRTLLM weight conversion, float64 reference from the dequantized weights, with and without an FC1/FC2 bias:

- delta in `[up | gate]` order: output and FC1 activation within 2% relative error of the reference; the swapped order is off by more than 30%;

## Details

Design. `TrtLlmMxfp4LoRAExperts` subclasses `_TrtLlmLoRAExpertsBase` and reuses its flow unchanged: the gate/up delta is computed by punica and passed as `gemm1_lora_delta`, so the kernel adds it before the activation; the down delta is computed from the post-activation FC1 output the kernel returns, and the base finalize and the delta reduction happen in one FP32 pass. Kernel arguments (`gemm1_alpha/beta/clamp_limit`, unpadded hidden size) come from the existing `TrtLlmMxfp4ExpertsBase`.

Three things differ from the BF16 class, each behind the new `prepare_gemm1_lora_delta` hook or a small base change:

- FC1 bias. The kernel has one FC1 bias slot, used either by the static `gemm1_bias` or by the per-token delta. On the LoRA path the static bias (GPT-OSS has one) is un-shuffled to logical order and added to the delta; `gemm1_bias` is then not passed. The sum is rounded to BF16, the dtype the kernel takes for the delta.
- Delta layout. The kernel takes `[up | gate]` halves. Per-expert adapters already arrive that way (or as interleaved pairs for `SWIGLUOAI`); fused 3D adapters arrive in checkpoint row order. All four cases are converted.
- Hidden padding. MXFP4 TRTLLM pads the hidden size (2880 -> 3072 for GPT-OSS) and returns an unpadded output, so the shared finalize now writes `output.size(1)` columns instead of the padded width. No change for the BF16 class, where the two are equal. The modular kernel also sized its output from the padded input and asserted on the narrower result in the no-op finalize; it now asks the experts for the output hidden size (`FusedMoEExpertsModular.output_hidden_dim`, default: the input size; the TRTLLM MXFP4 experts return the unpadded size) and allocates `output` at that width up front, so the result is used without a copy on a single rank. This also applies to the non-LoRA `TrtLlmMxfp4ExpertsModular`. This was found by the end-to-end run, not by the kernel tests.

MXFP8 activations are not supported because the kernel then returns the FC1 activation as uint8 without block scales (observed with FlashInfer 0.6.18), so the down delta cannot be computed.

Limitations.

- DP is rejected (explicit `flashinfer_trtllm` + LoRA + DP raises, as before this PR): the inherited no-LoRA fast path reads the local batch's adapter flag, while under DP the experts see the gathered batch. `TrtLlmBf16LoRAExperts` has the same gap; left for a separate fix.
- Top-1 routing with the weight applied on the input double-weights through the shared LoRA base (also `TrtLlmBf16LoRAExperts`); fixed separately in #62019.
- The kernel tests need SM100, so the H200/L4 LoRA CI shards skip them; they were run on GB300 only.
- Not chunked, like `TrtLlmBf16LoRAExperts`: the LoRA token mapping covers the whole batch. The TRTLLM-Gen grid limits one call to about `(65535 - num_experts) * 8 / top_k` tokens (~130k for GPT-OSS).
- `SITU` activation is not enabled for the LoRA class (untested).
- With a static FC1 bias, a delta far below the BF16 step of the bias is rounded away.

Related work, not duplicated: #47226 adds FlashInfer MoE LoRA for FP8 / MXFP8 / MxInt4 (not MXFP4, not updated since July) and uses the same opt-in rule; #34421 routes NVFP4 LoRA to Marlin; #61164 and #61165 fix other parts of the MoE LoRA path and do not overlap.
