# [Bugfix][Frontend] Don't crash beam search on an extreme length_penalty

[Upstream PR](https://github.com/vllm-project/vllm/pull/59506) · state: open · merged: False

## Original PR description

## Purpose

A beam search request with a large `length_penalty` returns a 500 error. `get_beam_search_score` divides by `max(seq_len, 1) ** length_penalty`:

- A large negative penalty underflows that to `0.0`, which raises `ZeroDivisionError: float division by zero`.
- A large positive one raises `OverflowError`.

Both happen while sorting beams, after generation has already run. The schemathesis test on main (`test_openapi_stateless[POST /v1/chat/completions]`, build 91958) found it:

```
vllm/entrypoints/generate/beam_search/online.py:196 beam_search
  -> utils.py:159 sort_beams_key -> utils.py:154 get_beam_search_score
ZeroDivisionError: float division by zero
```

The `max(seq_len, 1)` guard from #56249 covers a zero length but not an extreme exponent.

## Change

- `get_beam_search_score` saturates instead of raising. An overflowed denominator gives a score of about 0. An underflowed one gives `-inf`, or `0.0` when the log-prob is 0. Beam order still follows the score everywhere it's finite.
- `BeamSearchParams` rejects a non-finite `length_penalty` (`inf`/`nan`) with a `VLLMValidationError`, next to the existing `beam_width` check, so the API returns 400.

This isn't a duplicate: I searched open PRs for `length_penalty`, `get_beam_search_score` and beam-search ZeroDivisionError, and found nothing related.
