# [Bugfix][Tool Parser] Preserve non-canonical numeric strings when schema allows string

[Upstream PR](https://github.com/vllm-project/vllm/pull/62254) · state: open · merged: False

## Original PR description

## Overview

Fixes #62252

When a tool parameter schema allows both `string` and a numeric type (e.g. `"type": ["string", "integer"]`), `coerce_to_schema_type` silently converts non-canonical numeric strings such as `"0017"`, `"+17"` or `"1_000"` into integers, corrupting IDs, ZIP codes and similar values that the model emitted as strings.

## Claims

- When `string` is an allowed type, a numeric coercion is accepted only if it round-trips (`str(coerced) == value`); otherwise the original string is kept.
- Canonical values (`"17"`, `"-5"`, `"3.5"`) still coerce to numbers exactly as before.
- When `string` is not allowed (e.g. `"integer"` only), behavior is unchanged: `"0017"` still becomes `17`.

## Validation

```
pytest tests/tool_parsers/test_utils.py -k coerce
```

- New parametrized regression tests: `"0017"`, `"+17"`, `"1_000"`, `"-0"`, `"3.50"`, `"1e5"`, `"1.0e2"`, `"5.0"` stay strings; `"17"`, `"-5"`, `"0"`, `"-42"`, `"3.5"` still coerce; non-canonical values still coerce when `string` is not allowed.
- The new tests fail on `main` and pass with this change; all 83 `coerce_to_schema_type` tests pass.
- `ruff check` / `ruff format` pass.

## Details

The check lives in the `integer` and `number` branches of `coerce_to_schema_type` (`vllm/tool_parsers/utils.py`), guarded by a single `string_allowed` flag computed from the normalized types, so the extra cost is one string comparison and only applies to union types that include `string`. Trade-off: scientific notation and trailing-zero floats (`"1e5"`, `"3.50"`) are kept as strings when `string` is allowed, since they cannot be reproduced exactly from the parsed number.
