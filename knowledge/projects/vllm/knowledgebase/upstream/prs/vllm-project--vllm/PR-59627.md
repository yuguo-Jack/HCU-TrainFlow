# [Bugfix][Structured Output] Feed the token that implicitly ends reasoning to the grammar

[Upstream PR](https://github.com/vllm-project/vllm/pull/59627) · state: closed · merged: True

## Original PR description

## Overview

Structured output skipped a reasoning-end token that is also content, such as GLM's `<tool_call>` with no `</think>` before it. The grammar then forced a second `<tool_call>`, and `required`/named tool calls were lost. This PR feeds that token to the grammar, which matches what `extract_content_ids` already does. Fixes #59608.

## Claims

- For `ParserEngine`-based parsers, the grammar now consumes a reasoning-end token that `extract_content_ids` keeps as content, if the grammar accepts it. Close tags such as `</think>` are still skipped. `ReasoningParser` and legacy parsers do not change.
- On GLM-5.3-Flash, the doubled-`<tool_call>` signature went from 7/40 (`required`) and 8/40 (named) to 0/40. With MTP speculative decoding it went from 9/40 and 11/40 to 0/40.
- Under speculative decoding, a drafted `<tool_call>` cannot force the end of reasoning, and when it is the last draft the bonus row is masked from the grammar state after it.
- The same failure reproduces on Qwen3 (`qwen3` + `hermes`), and the fix removes it there too. Correct-call rates on the GLM tool-result prompt did not go up, because of a separate argument bug (see Limitations).

## Details

**Root cause.** `_get_constraint_start` returned the index after the reasoning-end token. That is right for `</think>`, which is not content. A tool-call start that ends reasoning is content, so the grammar started one token after the content did. This came in with #55223, and #48200 kept it.

**Change.**

- `ParserEngine.find_reasoning_end_offset` becomes `find_reasoning_end`, which returns `ReasoningEnd(offset, implicit)`. `implicit` is True when the end token is not the close tag, the same rule `extract_content_ids` uses.
- `StructuredOutputManager._get_constraint_start` becomes `_get_constraint_bounds`, which returns `ConstraintBounds(grammar_start, constraint_start)`. For an implicit end that the grammar accepts, the grammar starts at the end token and masking starts one token later. Otherwise both equal the old value.
- `validate_tokens`, the spec-decode loop of `grammar_bitmask` and `accept_tokens` feed the grammar from `grammar_start`. Masked rows and early returns still use `constraint_start`, so a drafted `<tool_call>` cannot force the target to end reasoning.
- The "grammar accepts it" check keeps the old skip when the grammar cannot start with that token, such as a `json_schema` response format with tools present.

**Affected parsers.** Every in-tree `ParserEngine` config whose tool-call start ends reasoning now feeds that token to the grammar: glm47_moe (and ling3), qwen3 (and mimo), nemotron_v3, granite_thinking, seed_oss, gemma4, kimi_k2, minimax_m2, deepseek_v4, deepseek_v41, plamo3, and mistral with `reasoning_encoding="special_token"`. A token counts only if the tokenizer has a single id for it. On the real DeepSeek-V4 tokenizer the DSML opener is several tokens, so deepseek_v4 does not change in practice. For plamo3 the token is the end-of-turn tag, which is normally a stop token; I expect that to be harmless but did not test it.

**Tradeoffs.**

- No measurable cost. After reasoning ends, `_get_constraint_bounds` returns before any reasoner call. Only a step with an implicit end token runs one extra single-token `validate_tokens` on the CPU. There is no CPU/GPU sync.

**Limitations.**

- A separate bug, similar to #58315, remains. The GLM tool grammar allows the special `<tool_call>` token inside `<arg_value>`. When the model quotes tool-result text that contains it, arguments break (`Write({})`, missing arguments). Many responses this PR recovers now hit that bug. It will be reported separately.
- Legacy (non-`ParserEngine`) parsers such as `k2_horizon` keep the old behavior until they move to `ParserEngine`.
- Under spec decode, the target can still reject a draft and then sample an implicit end token that the grammar rejects. This predates the PR. @yzong-rh plans to file an issue for it.
- Also unchanged: a prompt that already ends with an implicit end token (`continue_final_message`) still starts the grammar after it, and multi-token text markers cannot be expressed as a token-id set.

**Related.** No open PR changes where the grammar starts after reasoning; #36138, #56403, #57718 and #57754 touch nearby paths.

- yzong-rh · APPROVED · 2026-10-07T23:44:15Z · [source](https://github.com/vllm-project/vllm/pull/59627#pullrequestreview-5449731069)

Great catch! Thanks for the PR.

I attempted a fix that makes `_get_constraint_start` return `reasoning_end_offset` instead `reasoning_end_offset + 1` for `inclusive_reasoning_end_token_ids`. However, it changed the output distribution under spec decode and was incorrect.

The correct fix, as implemented here, is to distinguish between `grammar_start` and `constraint_start`.
- `validate_tokens` validate from `grammar_start`
- `grammar_bitmask` will consume tokens from `grammar_start` but only create bitmasks for tokens from `constraint_start`
- `accept_tokens` advance grammar from `grammar_start`

Note that failures due to implicit reasoning end can still occur during rejection sampling when the target rejects a draft and samples an grammar-invalid reasoning end marker (e.g. `<tool_call>` is sampled when grammar disallows tool calls). However, this is a pre-existing issue and not introduced by this PR.  I'll create a bug report for more discussion on this.

NIT:
Current implementation adds more coupling between `StructuredOuptutManager` and `ReasoningParser`. The former now reaches into `reasoner.inclusive_reasoning_end_token_ids`.

A cleaner impl could be to
- rename and rewrite `ParserEngine.find_reasoning_end_offset` to also indicate if a reasoning end is implicit or explicit. 
- rename and rewrite `StructuredOutputManager._get_constraint_start` to return both grammar start and constraint start (or constraint start and a grammar start offset)
- trim abstract `ReasoningParser` changes and limit the fix to engine-based parsers
