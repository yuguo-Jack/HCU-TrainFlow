# [Attention] Remove cascade attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/61126) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Remove cascade attention from vLLM: its kernels, heuristics, metadata, scheduler/KV-cache plumbing, model-runner logic, config/flag handling, tests, and docs.

Cascade attention has been opt-in (`disable_cascade_attn=True` by default), already hard-disabled for FlashInfer (see #25679), force-disabled for async spec decode / DBO / batch invariance / CPU, and unsupported by most backends — yet it still costs a per-step scheduler scan, branches in the model runner and backends, and recurring bugs (#55674, #47183, #39208, #55227, #53690 are open fixes/workarounds that this PR makes moot).

**This PR is non-breaking for hardware plugins.** Plugin-facing APIs (`build(common_prefix_len, ...)`, `SchedulerOutput.num_common_prefix_blocks`, etc.) are kept as deprecated no-ops; a follow-up PR removes them once plugin maintainers have been notified.

## Claims

- No behavior change for default configurations (cascade was off by default); net **-901 lines in `vllm/`** (+504 / -1,405; most `+` lines are de-indentation in the FA/AITER forward paths after removing the cascade branch).
- The scheduler no longer scans the running request's blocks every step.
- Out-of-tree plugins keep working unchanged (checked against vllm-ascend, tpu-inference, vllm-gaudi, vllm-spyre, vllm-metal).
- `--disable-cascade-attn` / `disable_cascade_attn=` still parse; they warn and have no effect (to be removed in v0.33.0, same schedule as `--log-config-file`).

## Details

- **Config / CLI:** removed every place that read or force-set `disable_cascade_attn` (`VllmConfig` for async spec decode, batch invariance, DBO; `CpuPlatform`) and the "no piecewise cudagraph for cascade" warning.
- **Scheduler / KV cache:** the scheduler no longer computes common prefix blocks; `get_num_common_prefix_blocks` is removed from the coordinators and all single-type managers.
- **Model runner (V1):** removed `_compute_cascade_attn_prefix_len(s)`, cascade-driven FULL-cudagraph exclusion, and the cascade-only `num_sms` / `_init_device_properties`, `num_query_heads`, `use_alibi`. MRV2 never used cascade.
- **Backends:** removed `cascade_attention()` / `use_cascade_attention()` from FlashAttention (and diffkv), `MultiLevelCascadeAttentionWrapper` from FlashInfer, and `use_cascade` / prefix–suffix metadata fields and branches from Triton, ROCm, ROCm AITER FA/unified, segmented, flex, CPU, and `CacheOnlyAttention`. `merge_attn_states` is unaffected (still covered by `test_merge_attn_states.py`).
- **Tests / docs:** deleted `test_cascade_flash_attn.py` and `test_cascade_attention.py` (and the system-message fixture/data only the latter used); updated `docs/design/cuda_graphs.md`.

**Kept as deprecated no-ops for out-of-tree plugins** (removed in a follow-up):

| API | Used by |
|---|---|
| `AttentionMetadataBuilder.build(common_prefix_len, ...)` (always 0) | ~20 vllm-ascend builders, tpu-inference, Cambricon, MetaX, Enflame |
| `SchedulerOutput.num_common_prefix_blocks` (now last field, defaults to `[]`) | vllm-ascend, tpu-inference, vllm-gaudi, vllm-spyre |
| `KVCacheManager.get_num_common_prefix_blocks()` (returns zeros) | vllm-ascend custom schedulers |
| `GPUModelRunner.cascade_attn_enabled = False`, `_determine_batch_execution_and_padding(use_cascade_attn=...)` (ignored) | vllm-ascend `NPUModelRunner` |
| `ModelConfig.disable_cascade_attn` (no effect) | vllm-ascend, vllm-metal |

**Known plugin impact:** the cascade fields of vLLM's attention metadata dataclasses (`use_cascade`, `common_prefix_len`, `cu_prefix_query_lens`, `prefix_kv_lens`, `suffix_kv_lens`, `prefix_scheduler_metadata`) are removed. Cambricon vllm-mlu's `MLUFlashAttentionMetadata(FlashAttentionMetadata)` passes them and will need to drop them when it moves to a release containing this PR (it currently tracks vLLM releases, not main). Enflame vllm-gcu pins `vllm==0.11.0` and is unaffected.

**Tradeoffs:** users who explicitly opted in with `--no-disable-cascade-attn` lose the heuristic-gated, FA-only cascade speedup for large shared-prefix batches. No new CPU/GPU syncs (the Triton/ROCm cascade paths' `seq_lens.cpu()` and FlashInfer's cascade-forced `seq_lens_cpu` requirement are gone). vllm-ascend's service-profiling config references `GPUModelRunner._compute_cascade_attn_prefix_lens`; that entry only matters when that profiler is enabled.

@noooop how is cascade attn relevant to Jev?

Dropping cascade attn doesn't mean dropping prefix caching. When two prompts share the same prefix, vLLM will deduplicate that part (if the model is decoder-only). Cascade attention is mostly useful for decode scenarios, where a batch of requests need to load the same KV cache of the shared prefix. For prefills, I believe it doesn't matter.

Also, MRV2 doesn't support cascade attn anyways.
