## Code Review 摘要

The conversion from f-strings to lazy `%s` formatting across these call sites and the new `*args` support in `info_once`/`warning_once` is the right direction and most of the rewritten messages match their arguments correctly. One conversion is not safe, though: `vllm/multimodal/profiling.py` passes the `dict` returned by `_get_mm_num_tokens()` as a format argument, and because the log-once helpers are wrapped in `@lru_cache`, the call now raises `TypeError: unhashable type: 'dict'` instead of printing the warning — precisely on the branch whose purpose is to warn about an undersized profiling sequence length (both the encoder and the decoder variant at line 249). Beyond that call site, please double-check the other converted call sites for hashable arguments (e.g. `self.hf_text_config.model_type` in `vllm/config.py`), since the same failure occurs whenever a non-hashable value reaches these helpers.

- BranchSun · comment · 2026-10-12T17:09:39Z · [source](https://github.com/vllm-project/vllm/pull/17425#discussion_r4250555411)

File: `vllm/multimodal/profiling.py` · line 224

🟠 **bug** (high)

This call will now raise instead of logging. `_get_mm_num_tokens()` is typed `-> Mapping[str, int]` and returns a plain `dict`, and `logger.warning_once` is backed by `_print_warning_once`, which is decorated with `@lru_cache` in `vllm/logger.py`. `lru_cache` computes its cache key by hashing the full argument tuple, and a `dict` is not hashable, so the lookup fails before anything is logged: `TypeError: unhashable type: 'dict'`. The exception propagates out of `get_encoder_dummy_data`, so multi-modal profiling aborts on V0 models where `total_len > seq_len` — i.e. the branch exists precisely to warn about a real misconfiguration, and instead of a warning it now gives a crash. The old f-string version worked because the dict was stringified inside the f-string. The identical pattern is used in `get_decoder_dummy_data` (the same `self._get_mm_num_tokens(mm_inputs)` argument, line 249), so both call sites need the same fix.

**建议**: Pass a hashable value. The simplest fix, which also keeps the original output identical, is: `str(self._get_mm_num_tokens(mm_inputs))`:

```python
logger.warning_once(
    "The encoder sequence length used for profiling "
    "(max_num_batched_tokens / max_num_seqs = %d) is too short ... "
    "(%%d tokens in total, out of which %%s are reserved for multi-modal "
    "embeddings). ...",
    seq_len,
    total_len,
    str(self._get_mm_num_tokens(mm_inputs)),
)
```

Alternatively, split the mapping into per-modality integers passed as separate `%s` args, or make the log-once helpers in `vllm/logger.py` tolerate unhashable arguments. Please apply the same change to the decoder call at line 249.

**证据**: `                self._get_mm_num_tokens(mm_inputs),`

- BranchSun · comment · 2026-10-12T17:09:39Z · [source](https://github.com/vllm-project/vllm/pull/17425#discussion_r4250555428)

File: `vllm/logger.py` · line 83

🟡 **maintainability** (medium)

Threading `*args` through these helpers is the right idea, but it interacts badly with the existing `@lru_cache` decorator on `_print_warning_once` / `_print_info_once`: the dedupe key is now the whole `(msg, *args)` tuple, so "print once per message" silently becomes "print once per message + argument values", and, more importantly, every format argument must now be hashable or the call raises `TypeError` before emitting anything (this is already hit by the new call in `vllm/multimodal/profiling.py`). Non-hashable log values are easy to pass by accident — a `dict` of token counts, a `list`, a `set`. The `Hashable` annotation hints at the constraint but nothing in the docstrings explains it, and the docstrings still promise "subsequent calls with the same message are silently dropped", which is no longer accurate once arguments participate in the key. Since this is a shared utility used across the codebase, the contract should be explicit (or relaxed) so callers do not have to know about the caching implementation detail.

**建议**: Either (a) document the constraint in both docstrings, e.g. "subsequent calls with the same message **and arguments** are silently dropped; arguments must be hashable", or (b) make the helper robust, for example by keying the cache on a hashable representation while keeping lazy formatting:

```python
@lru_cache
def _print_warning_once(logger: Logger, msg: str, *args: Hashable) -> None:
    logger.warning(msg, *args, stacklevel=2)

class _VllmLogger(Logger):
    def warning_once(self, msg: str, *args: object) -> None:
        _print_warning_once(self, msg, *map(repr, args))
```

Note that `(b)` changes how values are rendered in the key selection (not in the output), so (a) plus `str(...)`/`repr(...)` at the few call sites that pass containers is the lower-risk option. This is a first review in this repository, so also consider adding a short test or comment recording the "args participate in the dedupe key" behaviour.

**证据**: `    def warning_once(self, msg: str, *args: Hashable) -> None:`
