# [Bugfix][LoRA] Avoid double rounding in fused MoE expand

[Upstream PR](https://github.com/vllm-project/vllm/pull/63894) · state: closed · merged: True

## Original PR description

## Overview

Fix FP16 residual accumulation in the fused MoE LoRA fallback on XPU, without changing tests or tolerances. CUDA and ROCm keep their previous accumulation behavior.

## Claims

- Keep the XPU expand accumulator and residual sum in FP32, converting only when storing the result.
- Preserve the existing dtype conversion and addition order for non-XPU backends.
- Addresses the precision path introduced by #59931 without changing shared behavior on CUDA/ROCm.

## Validation

- Atomic-add cast cleanup: `ZE_AFFINITY_MASK=6,7 /work/vllm/.venv/bin/python -m pytest -q tests/lora/test_fused_moe_lora_kernel.py -k large_rank_fallback` — 16 passed; file-level pre-commit passed. A direct `SPLIT_K=2` shrink check also matched the FP32 reference exactly for binary-scaled FP16/BF16 inputs on XPU.
- After removing the redundant cast before `tl.store`: `ZE_AFFINITY_MASK=6,7 /work/vllm/.venv/bin/python -m pytest -v -s tests/lora/test_fused_moe_lora_kernel.py` — 433 passed in 309.11s on two Intel Arc Pro B60 GPUs; original tests/tolerances unchanged. CUDA was unavailable.
- `ZE_AFFINITY_MASK=6,7 /work/vllm/.venv/bin/python -m pytest -v -s tests/lora/test_fused_moe_lora_kernel.py -k test_fused_moe_lora_kernel_large_rank_fallback` — 16 passed on Intel Arc Pro B60.
- `pre-commit run --files vllm/lora/ops/triton_ops/fused_moe_lora_op.py` — passed.
- The CI BMG-specific numerical discrepancy was not reproduced on local B60; Intel CI is still needed to validate that hardware-specific case.

## Details

The XPU specialization keeps the FP32 dot accumulator through residual addition so the LoRA result is not rounded to FP16 before adding the residual. It is selected only for XPU expand calls; shrink and all non-XPU calls retain the existing conversion order. No test code or tolerance was modified.
