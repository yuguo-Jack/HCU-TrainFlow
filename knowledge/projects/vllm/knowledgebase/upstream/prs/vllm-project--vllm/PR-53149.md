# [Model] Enable LoRA support for tower and connector in GLM-ASR

[Upstream PR](https://github.com/vllm-project/vllm/pull/53149) · state: open · merged: False

## Original PR description

## Purpose

Part of #31479 (LoRA for the tower and connector of more multimodal models).

Enable tower/connector LoRA for GLM-ASR (`GlmAsrForConditionalGeneration`). The audio tower (`GlmAsrEncoder`) and projector (`GlmAsrMultiModalProjector`) are already vLLM-native linear layers and `get_mm_mapping` already maps them, so this PR sets `supports_tower_connector_lora = True` and overrides `get_mm_lora_token_counts`, which tells the LoRA machinery how many rows each audio item occupies in those layers:

- Every 30 s chunk is padded to 3000 mel frames, which the conv stack downsamples to `audio_config.max_position_embeddings` (1500) tower rows; the projector runs on the 4x frame-merged output before the padded frames are trimmed, so it sees 375 rows per chunk (also the number of LM tokens a full chunk yields).
- With `mm_kwargs`, the counts come from the item's `input_features` (chunks x padded length). `num_mm_embeds` alone is not invertible when the tail chunk is nearly empty (a 30.02 s audio yields 375 LM tokens but 2 chunks / 3000 tower rows).
- Without `mm_kwargs` (sizing the punica wrappers at engine init), whole chunks are budgeted for the given LM-token budget.

On current `main` without this PR, `--enable-tower-connector-lora` is accepted but GLM-ASR is logged as not supporting it: no tower or projector layer is wrapped and tower/projector adapter weights have no effect (outputs bit-identical to no adapter).

Not a duplicate: GLM-ASR is not on the done/WIP list of #31479 and no comment claims it (I claimed it on the issue before opening this PR); `gh pr list --state open --search "31479 in:body"` (LFM2-VL #51498, Intern-S1 #48129, Cosmos3-Edge #51949, Voxtral #45697, Qwen2-Audio #45944, Mistral3 #42228, Llama Nemotron VL #52749), `--search "LoRA tower connector"`, `--search "get_num_mm_encoder_tokens"` and `--search "GLM-ASR"` return nothing for this model. Related: #53092 (merged) replaced the `hasattr`-based support detection with the explicit `supports_tower_connector_lora` flag, which this PR sets; #55071 (merged) unified the multimodal LoRA token-count hooks into `get_mm_lora_token_counts`, which this PR overrides.

## Test Plan

Re-validated the current head merged into `main` (c23ca06b6d) on 1x NVIDIA H200 with `zai-org/GLM-ASR-Nano-2512` @ 61ba4e0b, torch 2.13.0+cu130, transformers 5.19.0, peft 0.21.1, on both model runners (MRV2 default and MRV1), using synthetic random-weight adapters in PEFT format plus one adapter saved by PEFT itself:

- Row accounting: forward hooks on the tower and projector linears compared with the active punica mapping length and `get_mm_lora_token_counts` for 1 s, 16 s, 30.0 s, 30.02 s, 55 s, 95 s, 655 s and 660 s audio.
- Routing: in one mixed engine step (full, tower-only, projector-only, zero-B and no adapter; different audio lengths), the delta each row receives at tower and projector LoRA layers compared with `scale * x A^T B^T` computed from that request's own adapter file.
- Zero-B adapter vs no adapter vs a LoRA-disabled engine.
- WER on `hf-internal-testing/librispeech_asr_dummy` (73 utterances).
- Regression: `tests/lora/test_qwenvl.py`, `tests/lora/test_lora_manager.py`, `tests/v1/worker/test_gpu_model_runner.py -k mm_lora`, `tests/models/multimodal/processing/test_common.py -k GLM-ASR`, `tests/models/test_initialization.py -k GlmAsr`, `tests/models/multimodal/generation/test_transformers_audio.py -k GLM-ASR`; pre-commit on `glmasr.py`.

## Test Result

- 128 tower and 2 projector linears are LoRA-wrapped. Input rows == active punica mapping length == `get_mm_lora_token_counts` at every length above (chunks x 1500 tower rows, x 375 projector rows), single requests and mixed batches, MRV2 and MRV1.
- Routing: rows of requests without weights for a layer get exactly zero delta; each adapted row's delta matches its own adapter (relative error at most 0.27, against 1.0 or more for any other adapter), MRV2 and MRV1.
- A zero-B adapter gives output identical to no adapter and to a LoRA-disabled engine (`VLLM_BATCH_INVARIANT=1`).
- WER: 5.13% LoRA disabled, 5.13% zero-B adapter (identical transcripts), 5.04% tower LoRA enabled without an adapter (one word differs).

  redundant model tests" skips), test_lora_manager 20 passed, test_set_active_mm_loras 1 passed, GLM-ASR processing 3,
  initialization 1, transformers audio generation 1. pre-commit passes on glmasr.py.

Two issues with the feature as it stands (I'd like your preference before changing anything):
1. The tower/projector LoRA index buffers can be too small for one engine step. They are sized at engine init from the encoder
   budget in LM tokens: with the LLM-class defaults on H200 (max_num_batched_tokens=16384) that is 66000 tower rows
   (`ceil(16384 / 375)` chunks x 1500). Every chunk is padded to 1500 tower rows however short the audio, so one step with 48
   one-second requests needs 72000 rows and the engine stops with
   `RuntimeError: The size of tensor a (66000) must match the size of tensor b (72000) at non-singleton dimension 0`,
   even when no request uses an adapter. 40 such requests (60000 rows) and 64 with LoRA disabled run fine. I hit it with all
   requests queued before the first step (in-process engine); a default multiprocess `LLM.generate` over 650 one-second clips
   did not hit it. With the API server default on H200 (8192 batched tokens) the limit would be 22 chunks (from the code, not
   run).
   This is not specific to GLM-ASR: on main without this PR, LLaVA-NeXT (llava-v1.6-mistral-7b-hf) with
   `--enable-tower-connector-lora` stops with the same error (16384 vs 17310) on one request with ten 336x336 images, because
   its tower buffer is sized at the token budget while each such image costs 3 x 577 = 1731 tower rows for 1176 tokens.
   The hook only sees `num_mm_embeds`, and a GLM-ASR chunk that costs 1500 tower rows can yield a single LM token, so
   `num_mm_embeds` alone only gives a bound of 1500 rows per token. Since GLM-ASR takes one audio per prompt, the model could
   instead budget `ceil(budget / 375) + max_num_seqs` chunks (about 96 MB of index buffers here), but that only moves the
   limit: with LoRA disabled, main already runs out of memory in the audio encoder when about 600 one-second requests share
   one step (910500 tower rows), because the encoder budget counts LM tokens rather than padded encoder rows. So I think the
   fix belongs in the scheduler or runner: count padded encoder rows in the encoder budget for chunk-padded models, or split
   encoder batches to the LoRA capacity. Which would you prefer?
2. Adapters saved by PEFT from the transformers v5 model are silently ignored. PEFT 0.21 + transformers 5.19 save keys as
   `base_model.model.model.audio_tower.*`, `...model.multi_modal_projector.*` and `...model.language_model.*`; GLM-ASR's
   `hf_to_vllm_mapper` does not map these, so the adapter loads without a warning and applies nothing (also true today for
   LM-only LoRA on main). Mapping the transformers v5 prefixes (the three module prefixes plus `lm_head.` -> `language_model.lm_head.`), as LLaVA-NeXT and Gemma3n do, fixes it: the PEFT-saved adapter then
   applies the same per-layer deltas as the same weights under checkpoint names, outputs are bit-identical with
   VLLM_BATCH_INVARIANT=1 (without it, LoRA outputs are not bit-reproducible across requests), and base weights and outputs
   are unchanged. I have that change with a small CPU mapping test ready, and can add it here or as a separate PR.

Unrelated to this PR, found while testing (will open separate issues if useful): MRV1 with VLLM_BATCH_INVARIANT=1 and CUDA
graphs produces degenerate text for GLM-ASR prompts short enough to be graph-captured, also with LoRA disabled; the encoder's
conv2 output depends on how many chunks share an encoder batch, so mixed batches are not bit-identical to single requests even
under VLLM_BATCH_INVARIANT=1 (the first difference appears before any LoRA layer); and the encoder out-of-memory above.
