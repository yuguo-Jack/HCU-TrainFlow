# fix(quantization): filter gpt_oss mxfp4 priority backends by platform (#61854)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61923) · state: open · merged: False

## Original PR description

### Purpose
Fixes #61854.

In `vllm/model_executor/layers/fused_moe/oracle/mxfp4.py`, `_get_priority_backends_for_gpt_oss()` contained an unfiltered monolithic list of backends including ROCm-only (`AITER_*`, `EMULATION`), XPU, and CPU backends alongside CUDA backends. When running on CUDA with unsupported activation schemes such as `kMxfp4Dynamic`, candidate evaluation produced ROCm-specific diagnostic advice (`VLLM_ROCM_USE_AITER`, `amd-quark`) on CUDA environments.

### Changes
1. Filter `_get_priority_backends_for_gpt_oss()` by `current_platform` (`is_rocm()`, `is_xpu()`, `is_cpu()`, CUDA default), matching the platform separation pattern in `_get_priority_backends()`.
2. Enhance `select_mxfp4_moe_backend()` error messages to include the active platform name and clearly report when no candidates exist for the requested activation scheme.
3. Add regression unit tests in `tests/kernels/moe/test_ocp_mx_moe.py` verifying that ROCm/AITER backends do not leak into priority candidates on CUDA, and that expected backends are properly returned on ROCm.

### Test Verification
- Executed unit tests in `tests/kernels/moe/test_ocp_mx_moe.py`:
  - `test_get_priority_backends_for_gpt_oss_does_not_leak_rocm_backends_on_cuda`: PASSED
  - `test_get_priority_backends_for_gpt_oss_returns_rocm_backends_on_rocm`: PASSED
