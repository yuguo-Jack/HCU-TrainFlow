# [Kernel] Coalesce reshape_and_cache stores by taking a KV block at a time

[Upstream PR](https://github.com/vllm-project/vllm/pull/61417) · state: open · merged: False

## Original PR description

## Overview

`reshape_and_cache` writes the paged KV cache one token per block, which makes every
store a column write and leaves the kernel at roughly 8% of achievable bandwidth. This
takes a whole KV block of tokens per block instead, so both destinations are contiguous.
**3.3x on the kernel; see the honest end-to-end read below before judging the value.**

This op has one caller in tree — `PagedAttention.write_to_paged_cache`, used only by
`vllm/v1/attention/backends/rocm_attn.py` — so the change is ROCm-only in practice.

## Claims

- **3.32x on the kernel in situ**, measured by profiler inside a real decode run
  (31264us -> 9405us over 128 calls), matching the microbenchmark.
- 1.56x to 3.80x in microbenchmark at 1024-8192 tokens, across aligned *and* misaligned
  slot mappings; no regression where the new path is not taken (1.00x).
- **Mean TTFT improves up to 1.17x under load** (1024-token prompts, concurrency 64;
  median 1.20x, p99 1.10x), which is where a faster KV write should show.
- **End-to-end throughput is unchanged** — the kernel is ~3% of prefill device time, so
  the ceiling is ~2.2% and measurement is flat. TPOT is likewise ~1.000x: this patch
  touches the prefill KV write, not the decode inner loop.
- Output is bit-identical to the unpatched kernel on every tested shape and slot layout;
  NIAH accuracy unchanged.
- No API change, no new kernel entry point, one file touched.

## Validation

**In-tree test:** `pytest tests/kernels/attention/test_cache.py -k "test_reshape_and_cache and not flash"` — 72 passed.

**Bitwise.** 380 cases — 5 `(heads, head_size, block_size)` combinations, bf16 and fp16,
1 to 8192 tokens, contiguous / mid-block / random / partly-masked slot mappings — hash
identically to the unpatched build (SHA-256 of raw cache bytes, not a tolerance).

**Kernel**, MI355X, bf16, head_size 128, block_size 16, HIP-graph replay, minimum of 15
replays of a 50-call graph. Slot mappings are built the way vLLM builds them: every
request draws its own shuffled blocks and requests are concatenated along the token
dimension, so a request whose length is not a multiple of `block_size` misaligns every
group after it.

| 8 heads, 8192 tokens | before | after | |
|---|---|---|---|
| one request, aligned | 105.56us | 31.14us | 3.39x |
| two requests [100, 8092] | 105.03us | 28.90us | 3.63x |
| eight requests, random lengths | 104.54us | 29.28us | 3.57x |
| one request, starts mid-block | 105.91us | 29.59us | 3.58x |
| one request, 10% slots masked | 103.32us | 27.22us | 3.80x |

At 1 head / 2048 tokens the launch is below the threshold, the per-token kernel runs
unchanged, and all five scenarios measure 1.00x.

**In situ**, Llama-3.1-8B, prefill of 8192 tokens x 8 sequences, prefix caching disabled:

| | device time | calls | share of step |
|---|---|---|---|
| `reshape_and_cache` (base) | 31264us | 128 | 3.15% |
| `reshape_and_cache_grouped` (patched) | 9405us | 128 | 0.98% |

The grouped path took all 128 calls with no fallback, and the 3.32x matches the
microbenchmark.

**End-to-end**, `VLLM_PLUGINS=` (upstream vLLM), default compiled path, ROCM_ATTN
backend, output throughput, mean of 4 reps with arms rotated across GPUs and benchmark
positions (measured GPU-to-GPU bias on identical builds: 0.21%):

- Llama-3.1-8B, 8 workloads from in=128/conc=1 to in=32768/conc=4: 0.995x to 1.008x
- Qwen3-30B-A3B, 6 workloads: 0.997x to 1.008x

Flat, as the 3.15% share predicts. The `in=200, conc=64` point deliberately exercises
misaligned, fallback-heavy slot runs: 1.008x, no regression.

**TTFT and TPOT.** Throughput is the wrong lens for a prefill-side KV write, so taking the
latency metrics directly — Llama-3.1-8B, in=1024:

| | base | patched | |
|---|---|---|---|
| mean TTFT, conc=32 | — | — | **1.064x** |
| mean TTFT, conc=64 | — | — | **1.170x** |
| median TTFT, conc=64 | — | — | **1.204x** |
| p99 TTFT, conc=64 | — | — | 1.101x |
| TPOT, all points | — | — | ~1.000x |

TTFT improves with load, which is the expected shape: more concurrent prefills mean more
KV-write work per step. Total benchmark duration is unchanged, so this is latency
redistribution rather than extra throughput — useful if TTFT under load is the SLO, not
if the goal is tokens per second.

**Models exercised, including those that showed nothing.** Reach was verified by loading
each model and reading vLLM's `Op '<x>' not present in model` log plus worker profiler
kernel counts:

| model | reaches `reshape_and_cache` | result |
|---|---|---|
| Llama-3.1-8B | yes (10080 calls) | throughput flat, TTFT as above |
| Qwen3-30B-A3B | yes (15120 calls) | throughput flat |
| DeepSeek-V4-Flash | no — fuses into `fused_qnorm_rope_kv_insert` | not benchmarked |
| MiniMax-M3 | no — aiter's KV writer | not benchmarked |
| Kimi-K3 | no — MLA uses `concat_and_cache_mla` | not benchmarked |
| Qwen3.8-27B | no — hybrid KV takes a Triton writer | not benchmarked |

**Accuracy.** lm_eval RULER NIAH (`niah_single_2`, `niah_multikey_1`) at 8192 and 32768
tokens, 100 docs per cell, both models: 1.0 in all cells, patched identical to base.

## Details

**Root cause.** The key cache is `[num_blocks, num_heads, head_size/x, block_size, x]` and
the value cache `[num_blocks, num_heads, head_size, block_size]`. With one token per
block, a thread writing the value cache touches elements `block_size` apart, so a cache
line is spent to move 2 bytes. At 4096 tokens the kernel moved 34 MB in 47us.

**Change.** Both layouts are contiguous in the other direction — key over
`(block_offset, i)`, value over `block_offset` — so a block now takes one KV block's worth
of tokens and stages `[block_size, head_size]` tiles through LDS, writing each destination
in its own order. Loads and stores are both contiguous, 16 bytes per thread. Two details
that mattered more than expected, each measured: the key and value halves load before a
*single* barrier (one barrier each serialises two independent streams and costs ~20%), and
the tile rows are padded so reading a tile down a column does not put every thread on one
LDS bank.

**Fallback.** A group only takes the fast path when its slots are one full, block-aligned
run. Ragged request boundaries, prefix-cache hits starting mid-block and masked tokens
(`slot < 0`) take the per-token path, which spreads `block_size * head_size/x` copies over
the whole block so it keeps the occupancy of the original kernel.

**Reach.** Over 64 checkpoints, at most 11 can route here: MLA (36) and hybrid-attention
(11) architectures cannot reach `reshape_and_cache` at all, and some GQA models bypass it
via an aiter fused KV writer.

**What this is worth.** A 3.3x kernel improvement that does not survive to end-to-end
throughput, because the kernel is ~3% of prefill device time. If the goal is throughput,
this is a null result at the step level. The case for it is that the kernel win is real
and verified in situ, the change is contained to one file with no API change, accuracy is
unchanged, and TTFT under load improves — plus it leaves less on the table as KV writes
grow with longer prefills. I would rather state that plainly than present the 3.3x alone.

**Limitation.** The fast path fires only when `block_size` consecutive tokens land on one
aligned KV block, which is not guaranteed in a multi-request batch. The misaligned path is
faster than base rather than slower, so the patch wins either way, but grouping by each
request's own aligned interval (via `query_start_loc`) would make the fast path fire far
more often. Not done here — happy to fold it in if preferred.
