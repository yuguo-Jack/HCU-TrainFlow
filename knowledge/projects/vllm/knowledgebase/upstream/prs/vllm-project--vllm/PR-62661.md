# [Rust Frontend] Cap structured-output JSON nesting at 64 levels

[Upstream PR](https://github.com/vllm-project/vllm/pull/62661) · state: closed · merged: True

## Original PR description

## Overview

Python rejects a structured-output JSON schema nested more than 64 levels deep, and a structural tag nested more than 64 + 16 levels, with a 400 (`check_json_nesting` in `vllm/sampling_params.py`, vllm-project/vllm#60036). The Rust frontend has no cap and forwards any schema to EngineCore, where grammar conversion cost grows roughly with size × depth²: vllm-project/vllm#60036 measured 98 s for a depth-512 structural tag. This PR applies the same caps and message in the Rust frontend.

## Claims

- A JSON schema (object or JSON string) nested more than 64 levels, or a structural tag nested more than 80, returns 400 "The JSON schema is nested too deeply: objects and arrays may nest at most 64 levels" before the request reaches EngineCore.
- This covers chat `response_format`, `structured_outputs` on chat, completions, and generate, and the tool-call structural tags that output parsers build.
- A structural tag that is not valid JSON now returns 400 "Invalid structural tag specification." instead of being forwarded to EngineCore, as Python's backend validation does.

- `validate_caps_json_schema_nesting` (`vllm-engine-core-client`): 64 levels pass and 65 fail with Python's message, both as a schema object and as a JSON string.
- `validate_caps_structural_tag_nesting_with_wrapper_allowance`: a structural tag passes at 80 levels and fails at 81.
- `validate_rejects_malformed_structural_tag`: a non-JSON structural tag returns "Invalid structural tag specification."
- `prepare_chat_request_rejects_deeply_nested_json_schema` (`vllm-server`): a chat `response_format` with a 65-level schema returns 400 with the message.

The behavioral tests fail with the check removed from `validate`.

## Details

The check lives in `StructuredOutputsParams::validate` (`vllm-engine-core-client`), the existing owner of Python's `_validate_structured_outputs` rules. It already runs at every entry point, including `lower_sampling_params` on the final constraint, so parser-built tool-call structural tags are covered as in Python. A new `nesting` submodule sits next to the existing `xgrammar` one. Every constraint is checked on its parsed value: the schema check runs at the start of `validate_json_schema`, which both JSON branches already call, and a structural tag is parsed and then checked. `serde_json` stops parsing at 128 levels, so a document deeper than that is rejected as invalid JSON (still a 400, with a different message than Python's). For the same reason a structural tag that fails to parse is rejected, so a tag past the parse limit cannot skip the check.

One difference: Rust's parser-built structural tags nest tool argument schemas up to 20 wrapper levels deep (Python's stay within 15), so for that parser a strict tool's parameter schema is effectively capped near 62 levels instead of 64. Real tool schemas are far below either limit, so this PR keeps Python's single 16-level allowance.

Not a duplicate: no open upstream PR adds a nesting cap to the Rust frontend; vllm-project/vllm#62506 validates JSON Schema keyword values in the Python frontend.
