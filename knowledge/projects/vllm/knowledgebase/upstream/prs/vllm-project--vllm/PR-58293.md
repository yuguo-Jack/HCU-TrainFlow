# [Bugfix][KV Connector][Mooncake] Announce residency for every Store write

[Upstream PR](https://github.com/vllm-project/vllm/pull/58293) · state: open · merged: False

## Original PR description

## Purpose

`MooncakeStoreConnector` writes to the Store from two places, and only the positional save published the `BlockStored` event for what it committed. The hand-off path that persists mamba `align` boundary states stored its keys with no event at all, and `store_mask` keeps mamba groups out of the positional save, so that path is their only writer. A consumer intersecting the cache groups of a block therefore saw the mamba groups as missing everywhere, including on the rank that had just stored them.

Both paths now go through a single `_write`, which owns dedup, transfer, failure handling, statistics and the residency event, so a block this rank persists is announced by construction. The producers only describe what to write (`StoreBlock` / `StoreObject`), and `StoreResidencyEvents` is the only place a `BlockStored` is built. A block is announced once all of its Store objects are committed.

The events also carry `group_idx` plus the group's `kv_cache_spec_kind` and sliding window — the same metadata the core annotates its own prefix-cache events with — so a consumer can classify the group an event names (#49537 asks for this on hybrid models). The announced `block_size` is the token span the Store objects cover, matching how the core describes a partially filled block.

The other half of the same gap is that a hand-off the connector never persists is silent. Hand-offs it discards in the worker — no usable source block, a boundary past the request's hashed prefix, sub-block tails with partial hash hits disabled — now report it once, and the scheduler counts why it declined each hand-off and logs the totals, so a mamba group staying out of the Store can be attributed instead of only showing up as a lower hit rate.

Nothing about what is written or read changes: keys, dedup and retry accounting are untouched, and the put still carries only the objects that are missing from the Store. The write path costs a few microseconds more per block (measured on a microbenchmark of the producers and the two filter passes, 4 cache groups, 528-token blocks, 264-token hash unit): the descriptors are built instead of flat parallel lists, and addresses are resolved once per group before the dedup check rather than only for the missing chunks. A save batch in the same configuration costs tens of milliseconds, and the payload of an event is now built only for the blocks that are actually announced.

`test_handoff_offload_announces_mamba_boundary_state` and `test_block_aligned_snapshot_offload_announces_mamba_group` are the regression tests for the reported behavior; both fail on the base commit, where the hand-off published nothing. `test_boundary_store_stats_*` cover each hand-off decline reason, the consumer-role discard, the finish-time tail path and the snapshot semantics of the counters.

End-to-end, Qwen3.5-4B (GDN linear attention plus full attention, 4 cache groups) against a real Mooncake master, TP=2, `--mamba-cache-mode align --enable-prefix-caching --kv-events-config` on a zmq publisher, three ~4.4k-token prompts plus one repeat:

| | base | this change |
| --- | --- | --- |
| Store objects per group (0/1/2/3) | 6/6/6/48 | 6/6/6/48 |
| Store-side events per group | 0/0/0/24 | 3/3/3/24 |

Every stored block is announced exactly once and the counts match what the master lists. `ruff check` and `ruff format --check` are clean; `mypy` reports the same pre-existing errors as the base commit.

No model evaluation: this changes control-plane event metadata and diagnostics only, not stored bytes, transfers, scheduling or outputs.

- vMaroon · COMMENTED · 2026-10-17T08:52:46Z · [source](https://github.com/vllm-project/vllm/pull/58293#pullrequestreview-5557101707)

I think `group_idx` needs to change before this lands. The wire stays additive (`kv_cache_spec_kind` and `kv_cache_spec_sliding_window` already exist on `BlockStored`, and positional-save events keep their shape), but `group_idx` is still the Store's index into `prefix_cacheable_groups`, not the core group id, and this PR now attaches that group's kind to it. When the Store skips a group the core keeps (the QSA ring the scheduler comment mentions), a Store `mamba` event names the id of a different core group, so consumers that learn group metadata from events (llm-d's `groupCatalog` keys it by `(pod, group_idx)`) would mislabel that core group. On main the index was already the Store's, but without a kind it could not mislabel anything.

#60887 fixes this in e384204 and also replaces the count-based `MooncakeStoreKVEvents` quorum the new hand-off events go through. Since #60887 already carries this PR as its first commit, wonder if we could fold this into #60887 and review them as one unit, so main never publishes kind keyed by the Store index. If we prefer to land this first, I think e384204 should move into this PR.

Two cross-PR notes:
- Removing `KVTransferThread.update_kv_event` / `get_kv_events` leaves #52731's receive-thread events without a sink, so whichever lands second needs a load-side equivalent of `StoreResidencyEvents`.
- #52731 publishes `MEDIUM_CPU` for loads while Store writes stay `"cpu"`, so one connector would publish two spellings of the same tier. Dynamo's `from_kv_medium` only matches uppercase, so it drops every Store event today, the new hand-off ones included.

The `BoundaryStoreStats` counters and the decline log look useful but are independent of event emission. Might be cleaner as a separate PR, or as fields on `MooncakeStoreConnectorStats` so they reach Prometheus. `MooncakeStoreConnector.get_boundary_store_stats` has no caller yet.

- CAICAIIs · comment · 2026-10-18T05:35:11Z · [source](https://github.com/vllm-project/vllm/pull/58293#issuecomment-6246151935)

@vMaroon thanks your review! `a177cc09f` has all four.

**`group_idx`** names the core cache group now. `StoreResidencyEvents` takes each Store group paired with the id its events must publish, and `record()` emits that id; Store keys and every other Store-side address keep the Store index, and `_store_group_ids` on the scheduler side is untouched. Knock-on that came with it: `MooncakeStoreKVEvents` indexed a Store-ordered tuple with `event.group_idx`, so the worker's `group_tp_replication_factors` is keyed by core group id.

**`medium`** is `MEDIUM_CPU`. With the lowercase value a consumer matching the uppercase spelling dropped every Store event.

**Tests** pin the payload now: the block-aligned hand-off carries the preceding block's hash, the sub-block tail starting at token 0 gets `parent_block_hash=None`, both `token_ids == []` with a nonzero `block_size`.

**Counters** report per-report deltas through `MooncakeStoreConnectorStats` and land on `vllm:mooncake_store_boundary_handoffs_total{outcome=...}`; `get_boundary_store_stats` is gone from the connector and the scheduler.

On folding into #60887: e384204's mapping is applied here instead, so main never publishes a kind keyed by the Store index.

E2E on an H20, kimi-linear-tiny (KDA + MLA, 4 cache groups), TP=1, `--mamba-cache-mode align`, three 1646-token prompts plus a repeat, same tree base with only the store package swapped between runs:
