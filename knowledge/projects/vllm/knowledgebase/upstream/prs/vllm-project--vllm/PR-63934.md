# [Perf][Core] Skip no-op KV allocation passes for running requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/63934) · state: open · merged: False

## Original PR description

## Overview
Skip the full KV allocation passes when every group of a running request needs no freeing, allocation or cache registration.

## Claims
Check all three operations separately, including lookahead, in-flight-token retention and available hashes. Managers explicitly opt in; subclasses and unsupported layouts retain the full path. No end-to-end throughput gain is claimed.

## Validation
Head `c05170252`, base `4b1c04e76`; code is unchanged this round. Current allocator/prefix suites: **281 passed**, including real-manager differential allocation and subclass opt-in coverage. Whole-diff pre-commit including mypy passed.

```bash
HF_HUB_OFFLINE=1 VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' \
uv run --no-project .venv/bin/python -m pytest -q \
  tests/v1/core/test_single_type_kv_cache_manager.py \
  tests/v1/core/test_prefix_caching.py
```

Earlier CPU measurement of this fast path: **3.08–3.14 → 1.63–1.69 ms/step**, using 88 running requests and 10 hybrid KV groups over 300 steps, with speculative lookahead. This measures allocation CPU time. Earlier synthetic-model serving checks passed before the conservative subclass guard; they were not rerun on this head. Upstream CI is separate from these local checks.

## Details
`KVCacheManager` guards request-level eligibility; the coordinator checks each group's manager. Full-sequence admission, external/encoder work, reservations and delayed caching use the original path. The check itself adds work to eligible running steps. Closed #29206/#34568 addressed related allocation work; #63441 concerns eviction events. AI assistance was used for implementation and validation.
