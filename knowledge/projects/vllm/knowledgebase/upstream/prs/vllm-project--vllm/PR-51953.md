# [Bugfix][MRV2] Fix DiffusionGemma runtime OOM via tiled logits projection

[Upstream PR](https://github.com/vllm-project/vllm/pull/51953) · state: closed · merged: True

## Original PR description

## Purpose

- Fixes #50699: full-batch logits grow with concurrency and OOM the first decode batch
- Project logits per tile in the sampler; reserve the transient during profiling via a `profile_run` hook
- Not a duplicate: #46155 is an opt-in env-var sampler; this fixes the default path

## Test Plan

- `pytest tests/v1/worker/test_gpu_diffusion_sampler.py -v` (RTX 5090)
- `gpu-memory-utilization` A/B sweep, RTX 5090 32GB, NVFP4 26B, 8 concurrent requests x 512 tokens
- GSM8K 200 questions 5-shot, before vs after

## Test Result

- 4 passed, 0 failed

| util | before | after |
|---|---|---|
| 0.70-0.80 | serves | serves |
| 0.85 | engine dies on first batch (`Tried to allocate 2.00 GiB`, the #50699 failure) | serves |
| 0.90 | startup OOM | serves |
| 0.92 | startup OOM | startup OOM (prompt-logprobs path, follow-up) |

- Max stable KV cache: 508k -> 689k tokens (+36%); reserve costs ~55k tokens at low utils
- GSM8K: 92.0% -> 92.5% (noise), 5.67 -> 5.58 q/s; tiling no longer bit-identical, hence the eval

- TanishGudise · comment · 2026-10-28T18:40:29Z · [source](https://github.com/vllm-project/vllm/pull/51953#issuecomment-6477500725)

Tested this PR (head aae8574) on vLLM v0.32.0 on one H100 80GB HBM3 (driver 595.91.07) with `RedHatAI/diffusiongemma-26B-A4B-it-FP8-dynamic` (revision 3b3dae4), `--max-model-len 4096 --diffusion-config '{"canvas_length": 256}'`.

The PR does not apply to v0.32.0 as is. The rebase needed two manual edits: v0.32.0's `get_top_k_top_p` returns two values (and takes no vocab-size argument) and its `apply_top_k_top_p` has no `has_topp_only_rows`, so the old full-batch top-k/top-p block was removed by hand and the new per-tile call was changed to that API. `tests/v1/worker/test_gpu_diffusion_sampler.py` passes against v0.32.0 with the rebased files installed (4 passed).

At `--gpu-memory-utilization 0.90`:

| | v0.32.0 | v0.32.0 + this PR |
|---|---|---|
| `--max-num-seqs 16 --max-num-batched-tokens 4096`, 256 requests | starts, then the engine core dies on the first load (OOM in `_softcap_logits`, 4.00 GiB); 0/256 served | 256/256 served |
| `--max-num-seqs 64 --max-num-batched-tokens 16384` | does not start (15.75 GiB OOM in `_softcap_logits` during the decode-step kernel warmup, `warmup_kernels`) | starts; 256/256 served at 64 concurrent |
| GSM8K, 1319 questions, 64 concurrent | - | 0.957 (v0.32.0 at 32 seqs / util 0.65: 0.956) |

In row 1 the v0.32.0 load was sent at 64 concurrent and the PR's at 16; both servers run at most 16 requests at once.

Same config for both builds (32 seqs / 8192 tokens / util 0.65; 3 fresh servers each, alternated), v0.32.0 vs this PR, mean of 3 servers:
- interval between consecutive decode-sampler calls (about one decode step; median of steady 25-call windows): 74.7 vs 76.2 ms at 16 concurrent (ranges 74.0-75.9 vs 75.9-76.5) and 147.2 vs 145.8 ms at 32 concurrent (144.9-148.5 vs 144.6-146.5);
- `torch.cuda.max_memory_allocated` at 32 concurrent: 62.3 vs 56.3 GiB.

Both builds carried a small logger for these two metrics (every 25 sampler calls) and an experimental softcap change of ours, switched off. The allocation that fails (`_softcap_logits`, called from `compute_logits` with the softcap on, as in v0.32.0) is unmodified; the hook adds one wrapper frame. The 64-seq startup failure also reproduces on an unmodified v0.32.0 install.

Happy to share the rebased diff if it helps. AI assistance (Claude) was used for the rebase, the measurements and drafting this comment; I reviewed the setup and the numbers.
