# [Frontend] Add derender output mode to generate

[Upstream PR](https://github.com/vllm-project/vllm/pull/60082) · state: open · merged: False

## Original PR description

## Overview

Adds `output_mode="derender"` to `/inference/v1/generate`, so the generate server returns the parsed assistant message itself. This is Phase 2 of #56851 and builds on #60073.

## Claims

- `output_mode="derender"` returns `message` (content, reasoning, tool calls) on every choice without a separate `/derender` call
- `message`, `finish_reason` and `logprobs` match coupled `/v1/chat/completions` even for parsers whose `adjust_request` changes decoding. `/derender` can't match those
- `/v1/chat/completions/render` and `/v1/messages/render` now return `parse_context`. Other output modes ignore it, so prefill legs don't change
- A bad `parse_context` gets a 400 before generation. When a parser hides the reasoning, `token_ids` are dropped along with logprobs, like coupled chat
- Batch `/derender` now supports `parallel_tool_calls=false`, like coupled chat

## Validation

```bash
pytest tests/entrypoints/scale_out/token_in_token_out/test_protocol.py -v
pytest tests/entrypoints/scale_out/token_in_token_out/test_serving_tokens.py -v
pytest tests/entrypoints/scale_out/derender/test_derender_stream.py -v 
pytest tests/entrypoints/scale_out/derender/test_derender_parity.py -v 
```

The parity tests run R1-Distill with hermes and deepseek_r1 against coupled chat. They cover plain output, reasoning shown and hidden, `tool_choice` auto, required and named, `parallel_tool_calls=false`, a stop string, `n=2` and logprobs with `top_logprobs=3` and `logprob_token_ids`. Every case checks `finish_reason` and the tool call ID shape.

## Details

The derender level parses the engine's own `output.text`. That text already has the stop string cut and was decoded with the flags `adjust_request` set which is where `/derender` drifts from coupled chat (#42729).

- **Chat context.** `/render` puts a `ParseContext` on the `GenerateRequest` with the tools, `tool_choice`, `parallel_tool_calls`, `include_reasoning`, resolved `chat_template_kwargs` and the history tool call count. It's only read when `output_mode="derender"`. I went with always sending it, rather than only on request, so a rendered request works as is (decision 2 on #56851). `parse_context` is validated in `serve_tokens` before the request reaches the engine and unknown fields are rejected. The trade-off is that every rendered request carries the tools list, prefill legs included.
- **Parsing.** The generate server builds a slim `ChatCompletionRequest` from `parse_context` and reuses `_parse_and_assemble` from #60073. ` /render` resolves the template kwargs once and uses them for both `reasoning_parser_kwargs` and `parse_context`. Tool call IDs keep the parser's `tc.id` (#61852).
- **`finish_reason`** goes through `resolve_finish_reason` (#59324), the same as coupled chat and batch `/derender`.
- **Logprobs** are chat shaped and cut with `chat_top_logprobs_limit` (#59518). They're on whenever `num_logprobs` is set, so `logprob_token_ids` works. When a parser hides the reasoning, `logprobs` and `token_ids` are both dropped. The tokens and text levels don't  change.

Limitations:
- Streaming returns a 400 for now. That's Phase 3.
- The `text` level still ignores `logprob_token_ids`. That gap was already there.
- #57442 and #60915 add logprob flags this level can't support. Neither is on `main` yet, so there's a TODO and whichever PR lands second adds the 400.
