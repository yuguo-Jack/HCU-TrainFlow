# [Kernel] Add opt-in LiteTopK FP32 decode with producer histograms

[Upstream PR](https://github.com/vllm-project/vllm/pull/59921) · state: open · merged: False

## Original PR description

Thanks to @TKONIY for the collaboration on this work.

## Overview

Add opt-in producer-assisted LiteTopK for paged FP8/FP32 decode and verify,
ported from the SGLang decode work. Requires
[DeepGEMM #24](https://github.com/vllm-project/DeepGEMM/pull/24).
This description includes the optimized companion producer measurements;
the vLLM FP32 integration needs no additional code change.

## Claims

- Supports the H32/D128, page64, top2048 SM100-family decode contract for n=1..4.
- Selects exact logical indices with lower-index tie breaking and persistent
  workspace; preserves prefill, explicit backend and unsupported-path fallbacks.
- The updated companion removes repeated varlen histogram flushes for n>1.

## Validation

B200 (148 SMs), Torch 2.13.0+cu130, Python 3.12.3, PDL enabled.
Three isolated process blocks per version; nine shuffled CUDA-graph samples per
block. Captured GLM-5.2/DSpark operands use distinct KV replicas totaling at least
256 MiB. Timings include metadata generation/copy once per eight layers and are
reported per layer. They exclude the rest of the model and are not serving
latency. Across all 40 shapes, live logits, exact histograms and logical-index
selection agree between submitted and optimized versions in all 240 cases.
The full grid with ranges, the method and the validation record are below.


| dtype | B | n | context | submitted µs | optimized µs | old/new | default/new |
|---|---:|---:|---:|---:|---:|---:|---:|
| fp32 | 1 | 4 | 1048320 | 65.637 | 39.280 | 1.671x | 1.565x |
| fp32 | 4 | 4 | 1048320 | 222.181 | 116.323 | 1.910x | 1.511x |

The updated producer suite passed 8 FP32 native/varlen cases, including live
length and request-ID changes during graph replay. The combined route suite
passed 18 cases; the unchanged native selector passed its 30-case suite during
the original migration. Commands:

```bash
.venv/bin/python -m pytest tests/v1/attention/test_litetopk_decode.py -v -s
.venv/bin/python benchmarks/kernels/benchmark_litetopk_decode.py --widths 8192 65536 262144 1048576 --requests 1 4 --repeats 5
```

The repository benchmark is a hot per-layer check and excludes shared metadata.
The table above comes from the metadata-inclusive captured benchmark below. Some 8K shapes remain slower than default.

DeepGEMM was rebuilt from the companion changes. vLLM validation
used current Python source, the separately compiled selector, and unchanged
binaries from `f944491db`; this was not a full exact-base wheel build.
The complete draft-test module is unavailable because the generated FlashMLA
Python interface is missing; the two modified cases and actual metadata builder
were executed through narrow imports. Applicable lint/type checks and clean
patch-application/tree checks passed.

**Model evaluation:** not completed. The available model weights total
510,296,708,312 bytes, more than the single ~179 GiB B200 I had for this.
No output-quality, speculative-acceptance or end-to-end serving gain is claimed.
Full model evaluation remains required before merge.

**Method.** One NVIDIA B200 (148 SMs), Torch 2.13.0+cu130, Python 3.12.3, PDL enabled; clocks not locked, and the GPU was checked to be idle before each process. Operands are real captures (GLM-5.2 layer 0 FP8, DSpark layer 20 MXFP4); prefix lengths and batches are built from the captured query/weight bank, and KV bytes are copied into separate page sets per request and layer. This repeats one captured layer's operands, not an actual eight-layer model run. Each graph cycles over at least 256 MiB of actively read KV across at least eight layer replicas. The generic split256 metadata plus its copy is timed once per eight layers in every arm; the submitted BF16 version additionally builds split384 metadata and casts weights in every layer, while the optimized version builds and copies split384 metadata once per eight layers (n=1–5 pass FP32 weights, n=6 keeps the BF16 cast). Three fresh process blocks per version with alternating order; within a process, baseline/LiteTopK order is randomized for each of nine samples, each replaying its CUDA graph four times. Values are medians of the three block medians, with [min, max] block medians. Submitted and optimized DeepGEMM run as separate installed packages. Warmup, JIT, host work, operand setup, Q quantization, KV writes, candidate publication, attention and the rest of the model are outside the timed interval. Across the 40 cells, the default chain drifted between package runs by -0.55% to 0.92%.

`old/new` compares the submitted LiteTopK code with the optimized code; `default/new` compares the unchanged FP32-score + auto-selector chain with the optimized LiteTopK chain in the same process. Higher is faster. µs are per layer.

## Details

Enable with `--kernel-config '{"enable_litetopk_decode": true}'`; default is off.
vLLM passes producer histograms to the native selector and shares reusable
workspace across layers. The producer now keeps independent bins for all active
tokens of a varlen Q block, instead of flushing one slot on every token/KV split.
It retains exact per-score counts and handles partial blocks.

**Duplicate-work check:** this updates the existing decode PR and its companion;
[vLLM #48726](https://github.com/vllm-project/vllm/pull/48726) covers prefill.
This adds paged decode/verify integration rather than another prefill PR.
