# [Bugfix][SM120] Admit SM120 to the flattened device-query-lens path

[Upstream PR](https://github.com/vllm-project/vllm/pull/65527) · state: open · merged: False

## Original PR description

## Purpose

On RTX PRO 6000 (SM120, capability 12.0), `DeepseekV41IndexerBackend.supports_device_cpu_query_lens_mismatch()` returns `False`, so `enable_adaptive_verification` cannot start at all. The failure is a `ValueError` during config validation / CUDA-graph setup — it never reaches a kernel. Both gates exclude SM120: `_supports_varlen_paged_mqa_logits()` allow-lists the SM100 family, and `_supports_flattened_device_query_lens()` allow-lists the SM90 family.

Per @cjackal in #62515, the one to open is `_supports_flattened_device_query_lens()`. This PR does that and nothing else.

Fixes #63343.

## Why this is a gate, not a hardware dependency

Reading the DeepGEMM helper layer this path calls, SM120 is already handled there explicitly:

- `vllm/utils/deep_gemm.py::native_next_n_supported` — *"SM90 implements only {1, 2, 4}; **SM100 and SM120** schedule any `next_n` via multi-atom tiles."*
- `get_paged_mqa_page_sizes()` — returns `(64,)` on SM120 and `(32, 64)` elsewhere, and documents that larger storage blocks are split into one of those pages.
- `fp8_fp4_mqa_logits()` — *"SM100 takes MXFP8 or MXFP4 with packed UE8M0 block scales; **SM90/SM120** also take FP8 Q with `q_scale=None`."*
- `mqa_logits_use_mx_scales()` — `True` only on SM100. This is why SM120 belongs on **this** path and not the SM100 one: it shares Hopper's fp32-scale format.
- `_paged_mqa_logits_schedule_slots()` — the only architecture special case is SM90 `next_n=4` 2-CTA multicast; SM120 falls through to `num_sms`.

So the flattened path's kernel is not SM90-specific; the allow-list is a "never validated here" list, not a capability list.

## The gate is also internally inconsistent today

`_use_flattening()` already returns `True` on SM120 whenever `next_n > 2`: `_supports_native_decode()` falls through to `next_n in (1, 2)` off SM90/SM100, so with `num_speculative_tokens >= 2` the flattened path is **already the default on SM120**. The SM90 allow-list therefore only blocks the *adaptive-verification* branch — and, through `supports_device_cpu_query_lens_mismatch()`, engine startup.

That asymmetry is exactly what breaks adaptive verification: `next_n` varies per batch, so at `next_n ∈ {1, 2}` the second branch of `_use_flattening()` is the one that has to hold, and on SM120 it evaluates `False`.

## Validation

**Hardware**: 8× RTX PRO 6000 Blackwell Max-Q 97.9 GB (SM120, 12.0), PCIe, no NVLink (`nvidia-smi topo -p2p r` reports all 28 pairs `OK`), 4 NUMA domains. vLLM `0.31.1rc1.dev253+g7d0b4e57a`, FlashInfer `0.7.1rc5`, torch `2.13.0+cu130`, CUDA 13.0. DeepSeek-V4.1-Flash-1017, `--tensor-parallel-size 8 --block-size 64 --kv-cache-dtype fp8`, `indexer_kv_dtype: fp8`, DSpark k=3 with the 3-tier batch schedule, 1M ctx.

### Step 0 — gate logic, temp container, no model load (single GPU, ~30 s)

| probe | stock | patched |
|---|---|---|
| `get_device_capability()` | (12, 0) | (12, 0) |
| `has_deep_gemm()` | True | True |
| `_supports_varlen_paged_mqa_logits()` | False | False (untouched) |
| `_supports_flattened_device_query_lens()` | False | **True** |
| `DeepseekV4IndexerBackend.supports_device_cpu_query_lens_mismatch()` | False | **True** |

`has_deep_gemm()` is True on this stack, so the capability allow-list is the only blocker — and config validation for `enable_adaptive_verification` then passes (no LoRA, full cudagraphs, PP=1 all satisfied).

### Step 1 — full-model correctness (both arms on the same patched image, only the flag differs)

| probe | adaptive ON | adaptive OFF |
|---|---|---|
| arithmetic (numeric compare, 10 q) | 10/10 | 10/10 |
| 512-token long-form degeneration | none (distinct-4gram 0.992) | none (0.982) |
| degenerate-flag counts c16 / c32 | 2/32, 1/64 | 2/32, 1/64 |

The degenerate-flag counts are identical across arms, so they are prompt-structure artifacts of the repetition heuristic rather than a regression from this change.

### Step 1 — throughput: directional only, not steady-state

| c | ON | OFF | Δ |
|---|---|---|---|
| 8 | 398.8 | 496.4 | −19.7% |
| 16 | 828.2 | 717.1 | +15.5% |
| 32 | 1211.2 | 1181.0 | +2.6% |

**Read this as directional, not as a property of the feature.** The bench used 16 / 32 / 64 requests in ~10 s windows (9.75 / 9.15 / 12.63 s wall), with aggregate output tok/s that includes prefill and per-request startup — a different measurement from the 30 s / 60 s, 512-tok-per-stream, engine-counter harness the other numbers in #63343 come from. That is why the c8 row reads 398.8 tok/s where the same box measures ~760 tok/s at c8 under the longer harness, and the non-monotonic shape (−20 % / +15 % / +3 %) is what a 16-request, 9.75 s window produces. **The c8 −19.7 % is not established**; I will post a steady-state re-run (≥8 samples per arm, min–max, accept rate attached) in #63343 before this is merged, and will update this table then.

One operational cost that *is* solid: the ON arm captured more graphs and took **25.5 min vs 16.8 min** to cold-boot.

## Test plan

New `tests/v1/attention/test_deepseek_v41_sm120_flattened_qlen.py` pins the allow-list without needing SM120 hardware in CI — it monkeypatches `current_platform` to capability family 12.0 and asserts:

- `_supports_flattened_device_query_lens()` is `True` on family 90 and 120, `False` on 100 (SM100 must stay on the varlen kernel);
- it is `False` on 90/120 when `has_deep_gemm()` is `False`;
- `_supports_varlen_paged_mqa_logits()` is still `False` on SM120 (the SM100 gate is deliberately untouched);
- `supports_device_cpu_query_lens_mismatch()` is `True` for both `DeepseekV4IndexerBackend` and `DeepseekV41IndexerBackend` on SM120, and `False` without DeepGEMM;
- `_use_flattening()` selects the flattened path for the adaptive arm and not for the fixed arm.

The assertions were executed against the real gate functions extracted from the patched file with a stubbed platform (all pass), so the test encodes observed behaviour rather than an assumption.

## Notes / risks

- One-line allow-list widening; the SM100 gate is left untouched, so SM120 does not silently acquire the MX-scale path.
- `DeepseekV41IndexerBackend.get_supported_kernel_block_sizes()` returns `128` on SM120 while the paged MQA logits kernel takes 64-entry pages there; `get_paged_mqa_page_sizes()` documents that larger storage blocks are split, so this is expected rather than a conflict — but it is the first thing to check if a numerics failure ever shows up on this path.
- Related: #60762 declares 64-token kernel blocks for the SM120 sparse backends; this PR does not touch block-size declaration.
