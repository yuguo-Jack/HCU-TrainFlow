# [Bugfix] Keep content after stray <tool_call> in hermes streaming 

[Upstream PR](https://github.com/vllm-project/vllm/pull/63327) · state: open · merged: False

## Original PR description

## Overview

FIX #63309

Streaming with `--tool-call-parser hermes` drops the rest of an assistant message when a literal `<tool_call>` shows up in normal prose. The non-streaming response already keeps the full text. This makes streaming return that same text, and real tool calls still parse.

## Claims

- Text after a stray `<tool_call>` is included in the streamed content.
- Streaming and non-streaming return the same content when the tag is not a real tool call.
- A normal streamed tool call still returns the function name and arguments.

## Validation

Test plan:

- `pytest tests/tool_parsers/test_hermes_tool_parser.py`
- `pre-commit run --files` on `vllm/tool_parsers/hermes_tool_parser.py`, `vllm/parser/abstract_parser.py`, `tests/tool_parsers/test_hermes_tool_parser.py`, and `tests/tool_parsers/utils.py`

Test results:

- Before the change, the new stray-tag cases failed. Streaming stopped at the text before `<tool_call>`, and a `"name"` mention in prose was parsed as a tool call. A normal streamed tool call passed.
- After the change, `tests/tool_parsers/test_hermes_tool_parser.py`: 39 passed, 1 skipped.
- pre-commit on the changed files passed (ruff check, ruff format, mypy).

## Details

`_extract_content` stopped at the first `<tool_call>` and kept everything after it as a possible call. With no `"name"` in that region, streaming produced no tool-call delta and never sent the held text. A tag with an empty or whitespace body stayed held until the request finished, and Hermes had no flush for that.

The parser now sends a region as content when it cannot be a JSON tool call. `finish_streaming` sends any remainder when the stream ends without a tool name. The serving parser calls that for legacy tool parsers such as Hermes. No open PR already covers #63309.

I filed #63309, so I gave this a closer look than usual. **Two checks, both pass**

**1. Truncation sweep**

I took three fixed sample outputs:
- (a) a short intro followed by one complete get_weather call;
- (b) two complete calls in one output;
- (c) The literal <tool_call> tag opens a call. Done. — the #63309 case, where the tag only appears in prose.

For each sample I cut the text at every length from 0 to full (the tag stays where it is; the cut point moves — this is what max_tokens or a stop string does to a stream mid-generation), ran each truncation through both extract_tool_calls and extract_tool_calls_streaming + finish_streaming (streaming fed one token at a time), and compared what the two paths return:

| | before | after this patch |
|---|---|---|
| cut points where both paths agree | 85 | **177** |
| cut points where they diverge | 223 | 131 |
| crashes | 0 | 0 |

The 92 cut points that flipped to agreement are exactly those where a <tool_call> marker has appeared but no tool name has parsed yet. Where a name was already emitted the two paths still diverge — that's the truncation semantics discussed in #47903, correctly out of scope. No previously-agreeing cut point changed, so the blast radius is precisely the stray-marker recovery.

**2. Tests**

tests/tool_parsers/test_hermes_tool_parser.py: 39 passed, 1 skipped locally, matching the PR description. The DelegatingParser EOS test covering the serving wiring is a nice touch.

Two non-blocking observations:

1. Text after a completed call followed by a later stray marker (e.g. First. <tool_call>{…}</tool_call> Second. <tool_call>) is still dropped by streaming while non-streaming falls back to raw text. Pre-existing and out of scope, but it might deserve a follow-up issue so it's tracked.
2. _flush_legacy_tool_parser and the run_tool_extraction_streaming change extend EOS flushing to every legacy parser defining finish_streaming (in-tree that's only Hermes; out-of-tree plugins that defined it as dead code will start seeing it called). The engine route avoids flipping the tool_choice="none" routing gates that setting engine_based_streaming = True on Hermes would, which looks like the tighter blast radius — just flagging the shared-surface changes for maintainer judgment, and since tests/tool_parsers/utils.py is shared, a CI run over the other parser suites would be good confirmation (I could only run the hermes suite offline).

Happy to share the scan script if it's useful.
