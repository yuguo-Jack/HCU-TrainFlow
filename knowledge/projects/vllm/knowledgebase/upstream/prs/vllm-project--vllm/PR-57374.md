# [XPU] Move weight transfer to torch.distributed where NCCL is absent

[Upstream PR](https://github.com/vllm-project/vllm/pull/57374) · state: open · merged: False

## Original PR description

## Purpose

The `nccl` weight-transfer backend reaches NCCL through `PyNcclCommunicator`, which loads
`libnccl` itself. On any accelerator that has no NCCL the communicator sets
`available = False, disabled = True` and every collective early-returns, so a full RL
weight-update round reports success while moving nothing and the workers keep serving the
weights they started with. #57022 turns that silence into an error; this PR gives those
platforms a transport that actually works.

The backend does not need NCCL itself — the engines only ever ask their communicator to
`broadcast`, and every accelerator torch supports already has a collective library behind
`torch.distributed` (`xccl` on XPU). So keep the backend named `nccl` and choose the
transport by platform. That distinction matters because the RL control plane lives in the
*trainer*: TRL and similar frameworks select `backend="nccl"`, name NCCL in their config
schemas, and call `packed_nccl_broadcast_producer` directly. A new backend *name* would have
to be taught to each of them; a transport chosen by the platform works with the trainers
that exist today.

`TorchDistTransport` wears the same shape as `PyNcclCommunicator` (`broadcast`,
`rank`/`world_size`, `available`/`disabled`, `group`) over a stateless `torch.distributed`
group on the platform's own `dist_backend`. The group is stateless for the same reason the
NCCL engine's is: the trainer is a separate process and not a member of the workers'
tensor- or pipeline-parallel groups, so broadcasts address the sender by its rank *within
the transfer group* (`group_src`).

Two things oneCCL needs that NCCL does not:

- **A barrier after every broadcast.** With `async_op=False` the host returns before the
  data has landed, so nothing throttles the sender; it enqueues its whole stream of tensors
  while the receiver is still loading the first. Past a drift of a handful of collectives,
  oneCCL deadlocks — none of them ever completes and both ranks spin in the next device
  synchronization. One barrier per broadcast bounds the drift at a single collective.
- **A teardown that runs off the caller's thread.** Whichever side finishes first faces a
  peer still in the group, and `~ProcessGroupXCCL` then blocks in the KVS handshake for as
  long as that peer holds its end — which in weight transfer means the rest of the inference
  server's life. Neither `abort()` nor `shutdown()` shortens it; both leave finalization to
  the destructor. So `destroy()` hands the group to a daemon thread that aborts, unregisters
  and drops it while the process gets on with exiting.

Alongside: the one-by-one broadcasts get a platform-aware `current_stream()`, the post-send
sync goes through `torch.accelerator` rather than `torch.cuda`, and the engines' `shutdown()`
leaves the group instead of only dropping the reference. The unique-id rendezvous stays
CUDA-only and now says so — an `ncclUniqueId` is NCCL's own handle, with nothing to fall
back to.

## Points a reviewer should weigh

Called out rather than left to be discovered:

- **`_require_usable_communicator` from #57022 becomes unreachable once this lands.** That
  guard fires only when `not current_platform.is_cuda_alike()`, and both of its call sites
  now return or raise on exactly that condition *before* reaching it. The two PRs are
  deliberately separable — #57022 is the small, backportable "stop lying about success" fix
  and can land or be backported alone — but if both go in, the guard is dead code and I am
  happy to delete it here or in a follow-up, whichever reviewers prefer.
- **Why this lives in `weight_transfer/` and not `device_communicators/`.** It is the
  counterpart of `PyNcclCommunicator`, so the other directory is the obvious guess.
  `PyNcclCommunicator` earns its place there by being shared across three subsystems
  (`cuda_communicator.py`, `eplb_communicator.py`, and weight transfer); this class has one
  consumer, and `weight_transfer/` already houses its own transports (`RdtRouter`,
  `PackedBufferImporter`, the sync clients). It is also not a `DeviceCommunicatorBase`, even
  though `XpuCommunicator.broadcast` issues nearly the same call: that family wraps groups
  vLLM's own world owns, while a transfer group is an ad-hoc rendezvous with an external
  trainer process, and the base's `broadcast` has neither a `stream` parameter nor
  `available`/`disabled`. It is named `TorchDistTransport` rather than `...Communicator` so
  it does not read as a peer of that family.
- **`_TransferGroupHandle` exists to satisfy trainer code, not vLLM.** Trainers reach into
  `communicator.group` to drop the rendezvous store and its socket when done (TRL's
  `close_communicator` does), so the attribute must exist and accept assignment. A torch
  process group holds no such objects, so both fields are inert. This is a compatibility
  shim shaped around an external caller; if that is unacceptable upstream, the alternative
  is asking trainers to guard those attribute writes.
- **The barrier is unconditional.** A full update round issues a few hundred of them and
  their cost has not been isolated from the transfer itself. If it proves material the bound
  can be loosened to every Nth broadcast rather than dropped; dropping it reintroduces the
  deadlock.
- **`destroy()` aborts rather than shuts down.** A transfer group ends every round
  synchronized, so there is nothing in flight to lose, and `shutdown()` would wait on a peer
  that may never arrive — on oneCCL, failing hard enough to take the process down if that
  peer has already died.

  transport against mocks, covering transport selection off CUDA, the unique-id refusal,
  the backend and device the group joins over (and that it never reports itself disabled),
  `group_src` addressing with its barrier and stream entry, abort-and-unregister-once off
  the caller's thread, and that teardown does not wait for the destructor. It is a new file
  rather than an addition to `test_weight_transfer_nccl_uid.py` because that suite requires
  ray and real GPUs, so hardware-free cases cannot run there; I kept it to the behaviours
  that would silently regress and left out anything that only restated a constructor.
- On 2x Intel Arc Pro B70 (`xccl`, TP=1, one card per process): TRL GRPO server mode
  completes 5 steps, exit code 0, weights verifiably updated on the server, both processes
  exit cleanly. Before this change the same run transferred nothing and the policy never
  moved. Per-step weight sync measured 0.636 s steady state (3.25 s on the first step, which
  includes group formation); end to end the run is 1.40x colocate mode's wall clock on twice
  the cards.

`tests/distributed/test_weight_transfer_nccl_uid.py` is unchanged by this PR and was not run
here — it requires `ray` and real GPUs, which this host does not have.

## Model evaluation

No accuracy eval is included, and here is the reasoning rather than an omission:

- On CUDA and ROCm this PR is a no-op for model output. Transport selection is gated on
  `not current_platform.is_cuda_alike()`, so those platforms keep `PyNcclCommunicator`
  unchanged. The teardown change is deliberately scoped to the new transport only —
  `PyNcclCommunicator.destroy()` (which calls `ncclCommAbort`) is *not* called, so CUDA
  engine shutdown behaves exactly as before.
- Off CUDA there is no baseline to compare against: weight transfer previously moved zero
  bytes, so any eval would be measuring "the base model forever" against "the model the
  trainer actually produced".
- What the hardware run does check is the property that matters — that the served weights
  change to the trainer's weights, and that GRPO reward moves across steps rather than
  flatlining, which is precisely the symptom the silent no-op produced.

A comparative eval would need a supported RL trainer plus a multi-card XPU or other
non-CUDA CI lane; I am glad to add one if a maintainer can point me at a lane that has it.
