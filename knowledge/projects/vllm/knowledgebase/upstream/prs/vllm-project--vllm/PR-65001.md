# [Rust Frontend] Support --log-error-stack

[Upstream PR](https://github.com/vllm-project/vllm/pull/65001) · state: closed · merged: True

## Original PR description



## Overview

Support `--log-error-stack` in the Rust frontend, so `VLLM_USE_RUST_FRONTEND=1 vllm serve ... --log-error-stack` starts instead of failing on an unsupported argument. Part of the logging argument parity item in #44280.

## Claims

- `--log-error-stack` is accepted and logs one ERROR event per error response built from `ApiError`.
- Like Python, it defaults to `VLLM_SERVER_DEV_MODE`, on both the `vllm-rs serve` path and the Python-supervised `--args-json` path.

## Validation

- New CLI test `log_error_stack_defaults_to_server_dev_mode`: flag, env default, and explicit `false` overriding dev mode, for both the clap and `--args-json` paths.
- New route tests `log_error_stack_logs_error_responses` and `log_error_stack_disabled_logs_nothing` against the mock engine. With the layer disabled, the first one fails.
- `cargo test -p vllm-cmd -p vllm-server`, `cargo fmt --check`, and `cargo clippy --all-targets` pass.

Live check against `vllm-mock-engine`, following `rust/src/mock-engine/README.md`:

```bash
vllm-rs serve Qwen/Qwen3-0.6B --data-parallel-size 1 --data-parallel-size-local 0 \
  --handshake-port 29550 --port 8765 --log-error-stack
vllm-mock-engine --handshake-address tcp://127.0.0.1:29550
```

One valid chat request (200), then a wrong model, broken JSON, and `max_tokens: -5`. Each failure logs one ERROR event and the valid request logs none:

```
INFO  [access_log.rs:47] HTTP response ... status=200 ...
ERROR [error_log.rs:22] Error response method=POST path="/v1/chat/completions" status=404 error_type="NotFoundError" error="The model `nope` does not exist."
ERROR [error_log.rs:22] Error response method=POST path="/v1/chat/completions" status=400 error_type="Bad Request" error="Failed to parse the request body as JSON: key must be a string at line 1 column 2"
ERROR [error_log.rs:22] Error response method=POST path="/v1/chat/completions" status=400 error_type="Bad Request" error="Failed to deserialize the JSON body into the target type: max_tokens: invalid value: integer `-5`, expected u32 at line 1 column 86"
```

Error replies to clients are unchanged.

## Details

`ApiError::into_response` attaches its `ErrorResponse` to the response extensions, and a `log_error_response` middleware, installed only when the flag is set, logs it.

Python only forwards non-default args in `--args-json`, and the default of `log_error_stack` is `VLLM_SERVER_DEV_MODE`. So the Rust side reads `VLLM_SERVER_DEV_MODE` itself, through a hidden env-bound arg and `apply_env_fallbacks`, the same way `VLLM_SKIP_MODEL_NAME_VALIDATION` works.

Deviations from Python:

- Rust errors have no stack trace, so the event logs the error message instead. For internal errors the message already includes the source chain.
- Python logs its internal request ID. That ID is not available where `ApiError` becomes a response, so the event logs method and path instead.
- Only `ApiError` responses are logged. Python also logs `HTTPException`s such as unrouted 404s. Rust's unrouted 404s and auth 401s do not go through `ApiError`, so they are not logged.
- `--no-log-error-stack` is not accepted on the `vllm-rs` CLI; use `--log-error-stack false`. This matches earlier boolean flag ports. Python passes the value through `--args-json`, so `vllm serve --no-log-error-stack` still works.
