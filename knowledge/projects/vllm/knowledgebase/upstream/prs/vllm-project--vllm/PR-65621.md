# [Rust Frontend] Accept refusal content parts in assistant messages

[Upstream PR](https://github.com/vllm-project/vllm/pull/65621) · state: open · merged: False

## Original PR description

## Overview

OpenAI's chat API allows a `refusal` content part in assistant messages (`ChatCompletionContentPartRefusalParam`; the assistant `content` array is `text | refusal`), so a client that replays a model's refusal as structured history sends it. The Python frontend accepts it and replays the refusal string as text. The Rust frontend rejects the whole request at deserialization (`unknown variant 'refusal'`), because `ContentPart` only knows `text`, the three media URLs and `input_audio`.

This PR adds `ContentPart::Refusal` and lowers it where the role is known.

## Claims

- **Assistant messages:** a refusal part becomes an `AssistantContentBlock::Text`, like a text part, so every renderer sees it as the turn's text (the same choice the Rust Responses conversion already makes for `refusal` input parts). `echo` includes it, as Python's echo of the parsed last message does.
- **Other roles:** 400 with OpenAI's message, "Only assistant messages can have a 'refusal' content type."

## Validation

Python `vllm launch render` vs Rust `vllm-rs render` with this commit, both on `Qwen/Qwen3-0.6B` (HF renderer), `POST /v1/chat/completions/render` (measured on the same commit over main `39dbf51839`):

- assistant `[{"type":"refusal","refusal":"I can't."}]`: identical token IDs on both, and identical to the same turn sent as `"content": "I can't."`.
- user `[{"type":"refusal",...}]`: Python renders it as text; Rust returns the 400 above (intended, per OpenAI; see Details).

New tests in `vllm-server` `routes::openai::chat_completions::convert`, both failing on `main` (the request does not deserialize):

- `prepare_chat_request_replays_assistant_refusal_parts_as_text`: a JSON request whose assistant message is one refusal part (OpenAI's documented shape), with `echo`; asserts one assistant text block and the echo text.
- `prepare_chat_request_rejects_refusal_parts_outside_assistant_messages`: a user refusal part returns OpenAI's message.

## Details

**Layering.** The role-dependent rule lives in the server's DTO lowering (`convert_assistant_text_blocks` / `convert_content` in `chat_completions/convert.rs`), the only place that knows the role; `vllm-chat` already has the text block it maps onto.

**Scope and intentional deviations from Python.** Python also accepts `input_text`, `output_text`, `input_image`, `thinking` and bare-string parts on chat completions, but only because its chat parser is shared with the Responses path (`MM_PARSER_MAP` in `vllm/renderers/chat_utils/chat_message.py`). A live probe of the OpenAI API (2026-11-03, one request per case) settles which are contract:

| Part on `/v1/chat/completions` | OpenAI | Python | Rust before | Rust after |
|---|---|---|---|---|
| `refusal` in an assistant message | 200 | text | 400 | text |
| `refusal` in a user message | 400 "Only assistant messages can have a 'refusal' content type." | text | 400 (serde) | 400 (OpenAI's message) |
| `input_text`, `output_text` (any role) | 400 "Invalid value" | text | 400 | 400 (unchanged) |
| `input_image` | 400 "Invalid value" | image | 400 | 400 (unchanged) |
| bare string in the parts list | 400 "expected an object" | text | 400 | 400 (unchanged) |

So only the assistant `refusal` part is implemented, and a `refusal` part outside assistant messages follows OpenAI rather than Python. Clients with Responses-shaped content can use the Rust `/v1/responses` route (vllm-project/vllm#63902), which accepts all of these. Python's Mistral `thinking` part (vllm-project/vllm#21333) is out of scope here.

**Harmony.** Python's Harmony path (gpt-oss) drops an assistant refusal part (`harmony_utils.py`, `TODO: Support refusal`); Rust's Harmony renderer keeps it as text like every other renderer.

**Known difference not changed here.** An assistant message with several text-like parts is joined with `"\n"` by Python and concatenated by Rust's HF renderer (`[text "Sorry.", refusal "I can't."]` renders `Sorry.\nI can't.` vs `Sorry.I can't.`). The same already holds for multiple text parts and is a separate fix.

**Not a duplicate.** No open PR adds `refusal` content parts to the Rust frontend. Open PRs mentioning refusal parts target Python paths: Harmony (vllm-project/vllm#55479) and Responses input reconstruction (vllm-project/vllm#49130, vllm-project/vllm#48237). vllm-project/vllm#56648 also extends Rust chat content types but adds `image_embeds` in `vllm-chat`, not refusal parts.
