# [Perf][Frontend] Compute prompt block hashes in the Rust frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63842) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Let the Rust frontend compute a request's prompt block hashes, so the engine's input thread no longer hashes long prompts while holding the GIL the engine loop needs. Revives the idea of #15652 for the Rust frontend; complementary to #63454 (cheaper engine-side hashing) and related to #43483 (frontend hashes for DP routing). Part of the long-context P/D CPU-overhead work in #63439.

## Claims

- The engine accepts frontend-computed prompt block hashes; prefix-cache hashes are unchanged (byte-identical), so cache hits, KV connectors and KV events are unaffected.
- The Rust frontend covers `sha256` and `sha256_cbor` for plain, LoRA, cache-salt and lookahead (EAGLE) requests; other requests are hashed by the engine as before.
- Removes the GIL-held prompt hashing from the engine's input thread (~50 ms per 227K-token prompt with `sha256`, ~150 ms with `sha256_cbor`), which otherwise stalls the engine loop: +9.6% decode throughput with `sha256` and +39% with `sha256_cbor` on a workload that admits long cached prompts during decode (below).

## Validation

- `pytest tests/v1/core/test_kv_cache_utils.py`: 114 passed. `cargo test -p vllm-engine-core-client -p vllm-llm`: all passed, including known-answer vectors generated from the engine's own `Request` / `get_request_block_hasher`.
- E2E on GB300 with `VLLM_USE_RUST_FRONTEND=1`, using a test-only engine patch that recomputes the hashes of every request that arrives with frontend hashes and compares them:

| Config | Requests | Hash check | Cached tokens on repeat |
|---|---|---|---|
| Qwen3-0.6B, `sha256`, LoRA | 12 (plain, salts incl. non-ASCII / 300-byte, short, LoRA, LoRA + salt) | 12/12 match | 5424/5427; a new salt or LoRA starts at 0 |
| Qwen3-0.6B, `sha256_cbor`, LoRA | 12 | 12/12 match | same |
| Qwen3-1.7B + EAGLE3 (lookahead 1) | 8 | 8/8 match | same |

Benchmark (GB300, `Qwen3-0.6B`, Rust frontend, CUDA graphs): 64 streaming decode requests while fully prefix-cached 30K-token prompts (token ids, `max_tokens=1`) arrive at 20/s for 40 s. This resembles a P/D decode instance admitting long prompts. Same binaries in both arms; the "engine" arm stops the engine from advertising `prefix_hash_config`. Mean of 2 interleaved rounds (each within 2%):

| Hash | Prompt hashing in | Decode tok/s | ITL mean / p90 / p99 (ms) | Long-request TTFT p50 / p99 (ms) |
|---|---|---|---|---|
| `sha256` | engine (main) | 16,870 | 3.77 / 8.36 / 10.10 | 27.6 / 46.1 |
| `sha256` | frontend (this PR) | 18,494 (+9.6%) | 3.44 / 6.51 / 9.83 | 25.6 / 37.8 |
| `sha256_cbor` | engine (main) | 13,244 | 4.80 / 10.41 / 15.64 | 34.9 / 61.1 |
| `sha256_cbor` | frontend (this PR) | 18,366 (+39%) | 3.46 / 6.45 / 10.04 | 25.6 / 35.5 |

The gain depends on how much of the engine loop the hashing displaces: a small model and a high arrival rate of long prompts make it large; larger models see a smaller relative gain.

## Details

- `EngineCoreReadyResponse.prefix_hash_config` (algorithm, `hash_block_size`, `NONE_HASH`, lookahead) is set when the engine hashes blocks. Sending `NONE_HASH` means frontends needn't reproduce the seed logic.
- `EngineCoreRequest.block_hashes` seeds `Request.block_hashes`; the existing hasher continues from there. The engine only checks the count (`(prompt_len - lookahead) // hash_block_size`) and otherwise hashes the prompt itself.
- The Rust encoder writes pickle protocol 5 / canonical CBOR exactly. It leaves to the engine: multimodal and prompt-embeds requests, `xxhash*`, keys over one 64 KiB pickle frame, and the rare requests whose strings pickle could memoize by identity.
- The Python frontend doesn't send hashes yet.
