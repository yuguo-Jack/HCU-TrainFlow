# [ROCm][Quantization] Add AITER hipBLASLt MXFP8 linear kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62088) · state: open · merged: False

## Original PR description

## Overview

**This draft PR is for demonstration purposes only.** It demonstrates MXFP8 linear operations on gfx950 using AITER activation quantization and `hipb_mm` with swizzled operand scales.

Requires [ROCm/aiter#6582](https://github.com/ROCm/aiter/pull/6582) and hipBLASLt >= 1.3.

## Claims

- Enable the demonstration by setting `VLLM_ROCM_USE_AITER_LINEAR_HIPBMM=1` before starting vLLM. It is disabled by default.
- Swizzle weight scales once during loading and produce swizzled activation scales during quantization; FP8 weight values keep their ordinary layout.
- Support `torch.compile` through registered custom operations and their fake implementations.

## Validation

### Model prefill

We requantized the original BF16 Muse Glimmer 30B and Qwen3.8-27B checkpoints to MXFP8 for this demonstration. Qwen3-32B uses the existing INCModel MXFP8 checkpoint.

Measured on one MI355X (gfx950) using the official [ROCm 10.1 vLLM image](https://hub.docker.com/r/rocm/vllm/tags?name=rocm10.1.0_ubuntu24.04_py3.14-pytorch_2.13.0_vllm-0.29.0), which contains vLLM `0.29.1.dev0+g98dff2a81.d20261002.rocm101` and PyTorch 2.13.0. Both implementations used the same image and MXFP8 checkpoints; native vLLM used unswizzled scales, and AITER + hipBLASLt used swizzled scales.

Each latency is the arithmetic mean of model prefill execution times from two independent performance processes, measured from profiler timestamps. Each process ran one unprofiled warm-up with the same shape for each prompt before measurement. The maximum spread between repeats was 3.274%, measured as `(max/min - 1) × 100`. Speedup is native latency divided by AITER latency.

### Kernel validation

The same kernel implementation passed **65 test cases** on MI355X (gfx950) with vLLM 0.31.0, ROCm 7.2.3, and hipBLASLt 1.5:

```sh
HIP_ONLINE_TUNING=0 PYTHONFAULTHANDLER=1 PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 pytest -q -x --noconftest \
  tests/kernels/quantization/test_rocm_mxfp8_linear.py::test_rocm_mxfp8_linear_matches_dequant_reference \
  tests/kernels/quantization/test_rocm_mxfp8_linear.py::test_gfx950_scale_layout_linear_compiles
```

The tests compare native and AITER outputs against dequantized references and check compiled execution with padded scales.

## Details

```sh
export VLLM_ROCM_USE_AITER_LINEAR_HIPBMM=1
```

The selection log reports `Using RocmHipbmmMxfp8LinearKernel for MXFP8 GEMM`. The implementation requires `K` divisible by 128 and uses `BLK32_UE8M0_32_8_EXT` for both operands with automatic hipBLASLt algorithm selection. It also respects an explicitly set `HIP_ONLINE_TUNING`; validation used `0`.

Separate standalone validation found correctness failures for two prefill shapes with `K=29568` in the existing AITER quantizer. The model checks above do not cover those shapes.

This is a hipBLASLt backend for gfx950 dense MXFP8 linears. Related [#60169](https://github.com/vllm-project/vllm/pull/60169) uses FlyDSL for DeepSeek's 32x32 block scales, and [#60384](https://github.com/vllm-project/vllm/pull/60384) targets gfx942 decode with an A16W8 assembly kernel. Neither adds this `hipb_mm` path.
