# [Perf] Shard the GLM kpool decode indexer across the attention TP group

[Upstream PR](https://github.com/vllm-project/vllm/pull/60804) · state: open · merged: False

## Original PR description

## Description

`wq_b` is `ReplicatedLinear` and `wk` runs with TP disabled, so the GLM kpool decode scorer's inputs are bit-identical on every attention-TP rank: the paged MQA logits GEMM, the top-k, and the pool expand all run `tp_size` times per sparse layer per step, about 12 times per engine step with k=7 drafting.

This adds an opt-in row sharding behind `VLLM_GLM_KPOOL_DECODE_INDEXER_ROW_SHARD`. Rank `r` scores only requests `r::tp_size` via an `index_select` gather, builds the per-rank DeepGEMM schedule in-op, and the expanded pool ids (int32, about 2051 per row) are all-gathered and reordered locally. K-cache and tail-cache writes stay replicated, so outputs are unchanged. Every gate is host-side metadata identical on every rank, so CUDA-graph capture/replay and rank consistency hold. Verify batches at 32 or fewer requests keep the replicated path: the all-gather costs more than the GEMM it saves at that size.

Measured on GLM-5.3-Flash (NVFP4), 8x B300 (SM103), TP8, FP8 KV cache, MTP k=7, 1M context, `vllm bench serve`, random dataset, seed 42, medians of 3 warm runs, patch applied alone:

| workload (1024-in / 1024-out) | TPOT mean | TPOT p99 | TTFT median |
|---|---|---|---|
| 8 concurrent | 5.40 -> 4.74 ms (-12.2%) | 8.26 -> 7.10 ms (-14.0%) | 288 -> 286 ms |
| 32 concurrent | 7.85 -> 7.44 ms (-5.2%) | 12.24 -> 13.30 ms (+8.7%) | 1113 -> 1150 ms |
| 8x 128K prompts, 64 out | 159.8 -> 170.0 ms | 162.2 -> 170.0 ms | 6.14 -> 5.27 s (-14.3%) |

Draft until the comparison at `num_requests >= tp_size` with 512K-1M context is run: that is the shape the sharding is built for, and the c32 TPOT delta above sits within run-to-run variance for that workload. The p99 cost at 32 concurrent is real.
