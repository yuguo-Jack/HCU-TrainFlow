# [ROCm][Kernel] Pick the split of `top_k_per_row_decode` per row on the device

[Upstream PR](https://github.com/vllm-project/vllm/pull/65427) · state: open · merged: False

## Original PR description

### Purpose

`torch.ops._C.top_k_per_row_decode` takes about 100 µs for short decode rows of
wide logits, even rows no longer than k, which only need their own indices. On
MI300X/MI325X, with logits at least 200,000 wide (the sparse-attention indexer
case), main splits every row into 10 blocks and merges their 10·k candidates,
whatever the row's length:

| rows × seq_len (k = 2048, width 262,144, FP32, MI325X) | main | this PR |
|---|---|---|
| 8 × ≤ k | 104 µs | 5 µs |
| 8 × 2–4K | 42 µs | 20 µs |

**Root cause.** A block whose chunk holds fewer than k live logits pads its k
candidates with `-FLT_MAX`. For a row with `seq_len <= k`, almost all of the
merge's 10·k candidates are then the same value. The merge is a radix select:
on every pass those ~19k identical candidates fall into one histogram bin, and
their shared-memory atomics serialize (about 100 µs on MI300X). Rows slightly
longer than k pay a smaller version of the same cost, plus the merge of 10·k
candidates for a row that one block would finish faster.

The split cannot be decided on the host: `seq_lens` lives on the device and the
call is captured in CUDA/HIP graphs, so one captured graph has to be correct and
fast for any lengths.

The new split is ROCm-only, because it was only measured on MI300X/MI325X. CUDA
keeps the fixed split. The PR also fixes wrong indices for wide strided logits,
on every platform (see below).

### Change

On ROCm, the split-work path (`csrc/sampler.cu`, `numColumns >= 200000`) now
launches
`topKPerRowDecodeSplitWork` on a `(rows, maxBlocks)` grid that depends only on
the number of rows and the logits width. Each row decides on the device how
many of its `maxBlocks` blocks to use, from its own length only:

- Rows shorter than 16K logits run in one block, which writes the output
  directly. Rows no longer than k take the existing shortcut in
  `topKPerRowJob`, so the ≤ k case no longer goes through a merge at all.
- Longer rows use `floor(1.25 · (512/k)^(1/4) · sqrt(L/k))` blocks. The
  `sqrt(L/k)` term balances the per-block scan of L/n logits against the merge
  of n·k candidates. The extra factor was measured, because the merge costs more
  per candidate as k grows.
- When the rows' preferred splits would not fit on the GPU, each row gets an
  equal share of one block per SM, `numSMs / rows`. A row also gets enough blocks
  for chunks of at most 32K logits, so the longest rows of a mixed-length batch
  do not hold up the others.
- A block count of at least twice `4096 / k` is rounded down to a multiple of
  that number, so that the merge's float4 loads are whole.
- The unused blocks exit at once. The row's block count goes to a small
  `auxNumBlocks` workspace, and `topKPerRowDecodeSplitWorkMerge` merges only the
  `numBlocks · k` real candidates. Rows that ran in one block return from the
  merge immediately.

The output contract is unchanged: each row holds its `min(row_end, k)` indices
followed by `-1` padding. The consumers were checked, and they read only the
valid prefix or treat `-1` as masked: FlashMLA sparse, FlashInfer sparse MLA,
ROCm AITER sparse MLA, and `triton_convert_req_index_to_global_index`.

`next_n > 1` is handled as before: row `i` of entry `e` has
`seq_lens[e] - next_n + (i % next_n) + 1` live logits, or the 2-D `seq_lens`
value.

**Strided logits.** On main, logits at least 200,000 wide with
`stride(1) != 1` were split like contiguous ones, and every split block after
the first returned wrong indices: the strided loop already counts from the
block's start, and the block then adds that start again. In the new test, rows
of 100,003 and 262,144 logits at k = 512 got only 249 and 244 of their 512
indices inside the row. Strided logits now use the unsplit radix kernel on every
platform.

On gfx950, the dedicated k = 512 and k = 1024 paths are unchanged, except that
strided logits no longer reach the k = 1024 split kernels. Other gfx950 shapes,
such as k = 2048, take the new policy, which has not been measured on gfx950.
With AITER enabled, `rocm_aiter_mla_sparse` sends the uncompressed indexer's
k = 2048 decode on gfx950 to AITER (`is_indexer_top_k_supported`), so there the
new policy runs only with AITER off.

On CUDA, the only change is the strided-logits fix. Everything else compiled for
CUDA is the same as main, apart from two standard includes and one template
parameter that changed from `bool` to `int`.

Two launches are kept because the merge has to wait for all of a row's split
blocks. Merging in the last block to finish would need a device-wide counter
that has to be reset between graph replays, or a cooperative launch.

### Test Plan

- `pytest tests/kernels/test_top_k_per_row.py` (ROCm, MI325X). The CUDA-only
  per_row tests were also run on ROCm by widening their skips locally.
- New regression tests:
  - `test_top_k_per_row_decode_split_work_short_rows`: rows of length 0, 1,
    k − 1, k, k + 1 and 3k, up to the full width, at k ∈ {512, 1024, 2048},
    next_n ∈ {1, 2}, with 1-D and 2-D `seq_lens`. The values are BF16-rounded so
    there are many ties, and the logits past each row's end are huge garbage
    values that must never be selected. The test checks that the indices are
    exact and that each row is a valid prefix followed by `-1`.
  - `..._graph_replay`: one captured graph, replayed while the device-side
    lengths move rows between the single-block and split paths.
  - `..._strided_logits`: wide logits with `stride(1) == 2`.
  - `..._many_rows`: batches of 128 and 320 rows, so more rows than SMs, with
    mixed lengths.
- The new tests were also run against main's kernel, which is what CUDA still
  runs apart from the strided-logits fix. They all pass except
  `..._strided_logits`, which fails on main for both k values.
- Benchmarks on MI325X, FP32 logits, graph replay time:
  - rows ∈ {1, 8, 16, 32, 64, 128, 256};
  - widths ∈ {163,840, 262,144, 1,048,576};
  - k ∈ {512, 1024, 2048}, next_n ∈ {1, 2};
  - seq_len buckets ≤ k, 2–4K, 16–32K, 64K, 128K and ≈ width, plus two
    mixed-length buckets (16–64K, and 2K to the full width);
  - two logit distributions: Gaussian, and tightly clustered (`0.01·N(0,1) + 3`),
    the worst case for a radix select because every pass sees a single bin.

### Comparison with AITER

The ROCm sparse MLA indexer calls AITER's decode top-k only on gfx950
(`rocm_aiter_ops.is_indexer_top_k_enabled`). On gfx942 this kernel is the only
one used, and this PR does not change that routing.

For reference, AITER 0.1.26's `top_k_per_row_decode` in the same benchmark, at
k = 2048, width 262,144, 8 rows and Gaussian logits (µs):

| | ≤ k | 2–4K | 16–32K | 64K | 128K | ≈ width | mixed 16–64K | mixed 2K–width |
|---|---|---|---|---|---|---|---|---|
| main | 104 | 42 | 47 | 47 | 52 | 59 | 46 | 69 |
| this PR | 5 | 20 | 39 | 44 | 51 | 60 | 42 | 59 |
| AITER | 3 | 12 | 22 | 32 | 63 | 110 | 33 | 111 |

At this width AITER runs each row in a single block. It is faster on rows up to
about 64K and slower from about 128K, where one block scans the whole row. With
clustered logits or 32 rows the crossover is also near 128K. On short rows the
remaining gap is in the single-block radix select (`topKPerRowJob`), which main
already runs for logits narrower than 200,000 and which this PR does not change.

No NVIDIA GPU was available, which is why CUDA keeps the fixed split. CUDA's
split has the same padded merge, but it matters less there. On ROCm, the
indexer's `auto` top-k backend always resolves to `per_row`, i.e. this kernel.
On CUDA, for k ∈ {512, 1024, 2048}, it resolves to `cooperative_topk` or
`persistent_topk` (see `_resolve_auto` in
`vllm/model_executor/layers/indexer_topk.py`), so this path runs there only for
other k or when `per_row` is requested explicitly. Using the new split on CUDA
would need NVIDIA measurements first.
