# [Perf][Spec Decode] Drop the per-request .item() from the ngram_gpu draft-trim loop

[Upstream PR](https://github.com/vllm-project/vllm/pull/58356) · state: closed · merged: False

## Original PR description

## Purpose

With `ngram_gpu` speculative decoding, `update_scheduler_for_invalid_drafts()` runs on
the host once per engine step. It waits for the draft-count D2H copy and then trims each
request's spec slots to its valid draft count. It read each count with

```python
valid_k = int(num_valid_draft_tokens_cpu[req_index].item())
```

`Tensor.__getitem__` allocates a fresh 0-d tensor per request before `.item()` unwraps
it, and that allocation dominates the loop's cost.

This PR:

- takes one `.numpy()` view of the CPU buffer outside the loop and indexes that. It is
  zero-copy, because the buffer is already a CPU tensor;
- returns early when `scheduled_spec_decode_tokens` is empty. The scheduler omits
  requests without draft tokens from that dict, so an empty mapping means every loop
  iteration would be skipped, and the event does not need to be awaited;
- looks up `scheduled_spec_decode_tokens` before `req_id_to_index`, so requests that did
  not speculate skip one dict lookup;
- adds unit tests for the function, which had none.

Behaviour is unchanged: `total_num_scheduled_tokens`, `num_scheduled_tokens` and
`scheduled_spec_decode_tokens` come out identical to main's.

Scope: this is host-side bookkeeping in the V1 runner. `ngram_gpu` currently forces the
V1 runner (it is in `_get_v2_model_runner_unsupported_features`), so every model that
runs `ngram_gpu` calls this once per step. The function sits in `_update_states`, which
runs outside CUDA graphs, so it executes under `FULL_AND_PIECEWISE` as well. It does not
touch any kernel, the n-gram matcher, or acceptance.

Related PRs:
- #44056 and #52097 both make this function return a `dict` of trimmed counts. They
  compose with this change; whichever lands second needs `return {}` on the early-return
  path.
- #40704 ports `ngram_gpu` to the V2 runner. After it lands, this path remains the
  default only for `ROCM_DEFAULT_MRV1_ARCHITECTURES` (DeepSeek-V3.2/V4, GLM-MoE-DSA) or
  with `VLLM_USE_V2_MODEL_RUNNER=0`.
- The `assert num_speculative_tokens == self.k` in `propose()` (dynamic SD with
  `ngram_gpu`) is deliberately left alone; #46399 addresses it.

## Test Plan

- `pytest tests/v1/spec_decode/test_ngram.py`
- Micro benchmark of the real function imported from the tree, with real
  `SchedulerOutput`/`CachedRequestData`, rebuilding the input for every call and
  subtracting the rebuild cost. Each arm ran as a consecutive block of 4 runs; the first
  run is discarded and the median of runs 2–4 is reported. A second unpatched arm
  (`base2`) gives the noise floor. Each point was pinned to one core, with host load
  logged.
- In-engine check: an in-process engine with
  `speculative_config={"method": "ngram_gpu", "num_speculative_tokens": 3}` and a counter
  on the function, run on the models listed below.

Hardware and software: 1x MI355X (gfx950), torch 2.12.0, ROCm 7.2.3. The measured tree is
upstream main's Python on the host's compiled extensions. `ngram_proposer_gpu.py` is
byte-identical between the measured main and this PR's base.

## Test Result

**Unit tests:** 5 passed. The added tests were also run against four deliberately wrong
versions: indexing by loop position, dropping the `min(valid_k, scheduled_k)` clamp,
keying the early return off `req_ids`, and not updating `total_num_scheduled_tokens`.
Each fails at least one test, and main fails only the no-speculation test, because main
always waits on the event.

**Micro benchmark**, µs per call, k=3, every request speculated unless noted:

| requests | main | main (repeat) | this PR | change |
|---:|---:|---:|---:|---:|
| 7 | 7.06 | 6.98 | 2.35 | −66.7 % |
| 37 | 36.68 | 36.74 | 9.89 | −73.0 % |
| 133 (53 % speculated) | 72.48 | 72.27 | 18.67 | −74.2 % |
| 133 | 136.89 | 135.53 | 33.58 | −75.5 % |
| 261 | 263.64 | 263.50 | 66.34 | −74.8 % |
| 509 | 522.00 | 516.02 | 127.12 | −75.6 % |
| 133, nothing speculated | 3.75 | 3.82 | 0.03 | early return |

Outputs are identical across arms at every point. With the runner's actual pinned buffer
(133 requests), main costs 150.6 µs and this PR 33.7 µs; `.item()` on pinned memory is
slower, while the numpy read is unaffected. Nearly all of the gain comes from the numpy
view; the early return only matters on steps where nothing was speculated.

**In engine**, Llama-3.1-8B-Instruct, `ngram_gpu` k=3, 509 prompts, `max_num_seqs=509`
(one run per arm): the loop takes 478.0 µs per step on main and 142.6 µs with this PR, at
a median of 461 requests per step, with identical step counts and batch distributions.

**Reach:** the function is called exactly once per engine step, on the V1 runner, for
DeepSeek-V4-Flash, DeepSeek-V4-Pro, GLM-5.3, GLM-5.3-Flash, GLM-5.3-MXFP4, Kimi-Linear-48B,
MiniMax-M2.7, Qwen3.5-397B, Qwen3.6-35B, Qwen3.8-2.4T, Qwen3-Next-80B, gpt-oss-120b and
Llama-3.1-8B (dummy weights, truncated depth for the large ones).

**End-to-end:** the saving is roughly 0.1 ms per step at 128 requests and 0.34 ms at 461,
about 0.5–1 % of a decode step. That is below what a single throughput run resolves. An
earlier serving A/B (Qwen3-8B, `ngram_gpu`, 150 concurrent requests) measured throughput
as unchanged. An end-to-end `vllm bench serve` run against current main is still to come
before this leaves draft.

- ZhengGong-amd · comment · 2026-10-26T05:19:29Z · [source](https://github.com/vllm-project/vllm/pull/58356#issuecomment-6408832088)

Closing. Since #40704 made V2 the default runner for `ngram_gpu`, V2's `NgramGPUSpeculator` handles both `ngram` and `ngram_gpu` and has no host loop, so `update_scheduler_for_invalid_drafts` runs 0 times per step on the default path. It runs once per step only with `VLLM_USE_V2_MODEL_RUNNER=0`. That matches the `mrv1-only` label. Also, a correction to the description: the `.item()` reads a pinned host buffer, so it was never a device sync; the cost was a per-request host allocation.

The branch `ZhengGong-amd:spec-ngram-gpu-trim-host-loop` rebases cleanly onto `main@7128f568ac` if V1 still needs it.
