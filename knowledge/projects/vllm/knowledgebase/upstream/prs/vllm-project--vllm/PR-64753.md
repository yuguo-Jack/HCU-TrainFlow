# [Quantization][MoE] Keep CSF-compressed NVFP4 expert scales resident on B12X

[Upstream PR](https://github.com/vllm-project/vllm/pull/64753) · state: open · merged: False

## Original PR description

## Overview

Keeps the CSF-compressed routed-expert block scales of `nvidia/Qwen3.8-Flash-Next-FP4-Local` compressed on the GPU when the NVFP4 MoE backend is B12X: -2.57 GiB of weights, which is +18.7% KV cache on one RTX PRO 6000 Max-Q and +2.4 GiB of free memory on DGX Spark. GSM8K is unchanged.

Builds on #64312, which decodes CSF scales at load. Loading the checkpoint from the Hub also needs #64739 (shards under `tensors/`).

## Claims

- Lossless: the resident scales expand to exactly the scales #64312 decodes. A real-shape layer (512 experts, TP1/TP2/TP4 shards) expands every expert's scales byte-equal, and the encoder reproduces the checkpoint's own `csf` streams.
- Memory: weights 72.08 to 69.51 GiB on both GPUs.
- Cost: median ITL -4.0% at c=1, +6.9% at c=4, +8.8% at c=8 on DGX Spark (MTP-3); +1.4% / +3.0% / +6.8% on RTX PRO 6000. This is a capacity trade, taken only for checkpoints that declare `weight_scale_encoding: csf`.
- Only B12X W4A4 keeps scales resident. Other backends, W4A16, `csf_32x2_v1` and a `b12x` without the CSF API keep #64312's decode at load.

## Details

**Design.** `ModelOptNvFp4FusedMoE` takes the layer's `weight_scale_encoding` (per layer for `modelopt_mixed`) and asks the NVFP4 MoE oracle whether the selected backend keeps `csf` scales (`nvfp4_backend_supports_csf_scales`). Today only B12X with NVFP4 activations does, when the installed b12x exposes `Nvfp4CsfWeights` (FlashInfer 0.7.2.post1 does). `B12xExperts.process_weights_after_loading` re-encodes the rank's decoded scales, hands them to b12x as `CsfScalePlanes`, and drops the decoded scale params. b12x expands only the routed experts' scales per call into one zero-initialized scratch per layer shape that all layers share; layers run one at a time on one stream, which makes sharing safe. The scratch is allocated at load, so CUDA graphs capture fixed pointers.

**Why re-encode instead of keeping the checkpoint streams.** #64312 decodes the streams in the weight iterator, before TP slicing, and the gate and up projections are separate matrices. Re-encoding the rank's decoded slice needs no loader change and works for any TP size. The encoder picks each row's base the way `csf` checkpoints do, so it costs nothing in size; FlashInfer 0.7.2.post1 ships no encoder to reuse.

This PR does not:
- keep `csf_32x2_v1` (GLM-5.3-Flash-FP4-Local) or W4A16 expert scales resident, or load streams straight to the GPU; released b12x has no API for that yet.
- change any backend other than B12X.
- support expert parallelism (B12X is TP-only) or weight reloading for resident layers (`NotImplementedError`, because captured graphs read the first load's storage).

A question before I start anything: are you planning an MXFP4 follow-up? I sampled gpt-oss-120b's expert scales and only about 1.2–3.5% fall outside a base/base+1 window, so it would save roughly 75–80% of them (around 2.8 GB on gpt-oss-120b). We already keep MXFP4 scales compressed in our own serving setup, so I'd be happy to send it as a follow-up on top of this one if you're not planning it.

Since MXFP4 checkpoints have no `weight_scale_encoding` to opt in with, would you rather gate it on a flag or a config option?

- kirillbilchenko · comment · 2026-10-30T22:05:53Z · [source](https://github.com/vllm-project/vllm/pull/64753#issuecomment-6534497781)

@stecasta  I found a FlashInfer dispatch issue while investigating resident-scale overhead: https://github.com/flashinfer-ai/flashinfer/pull/8053.

The tensor API used here builds `MoeDecodeQuery` without forwarding `weight_plan.nvfp4_inline_scales`. It therefore leaves the capability false and expands the scales before dynamic GEMM, even when the existing kernel can read the compressed planes inline. The canonical preparation API already forwards this field. The fix adds the missing argument; existing batch/geometry eligibility checks still decide which kernel to use. The scale encoding, stored payload and compression ratio are unchanged.

On one DGX Spark (GB10, SM121), I checked a synthetic NVFP4 W4A4 layer at this PR's Qwen TP1 geometry: E512, H2560, I640, top-10, BF16 I/O, SiLU. Before/after use identical compressed weights, with 0.5% outlier scale bytes. Cold-L2 CUDA-graph CUPTI timings, median of three alternating rounds of 40 samples:

| Tokens | Spread routes: expansion → inline | Routes repeated over 16 experts: expansion → inline |
| ---: | ---: | ---: |
| 8 | 1325.27 → 1093.64 µs | 334.99 → 305.73 µs |
| 16 | 2551.57 → 2123.81 µs | 352.27 → 325.42 µs |
| 32 | 5019.16 → 4166.72 µs | 379.87 → 328.30 µs |

The probe checks exact output against a predecoded control and confirms that inline execution leaves poisoned expansion scratch untouched. The touched FlashInfer test file passes all 16 cases; three new compressed-plan cases fail without the fix. The existing vLLM resident-scale TP1/TP2/TP4 integration/graph tests also pass. The linked PR includes the reproducer and environment.

These are isolated synthetic MoE results, without the full model, TP collectives or MTP. They suggest an avoidable source of CSF overhead, but do not establish a full-model speedup or explain the entire reported ITL regression. I do not have this NVFP4 checkpoint cached for a matching serving run.
