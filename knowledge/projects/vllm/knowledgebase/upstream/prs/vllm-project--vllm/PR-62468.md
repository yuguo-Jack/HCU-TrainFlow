# [Loading] Fix misleading logs when multiple models are loaded

[Upstream PR](https://github.com/vllm-project/vllm/pull/62468) · state: open · merged: False

## Original PR description

Note: https://github.com/vllm-project/vllm/pull/62421 duplicated this fix and this PR only fixes the duplicate misleading `Loading weights took` now.

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

DeepSeek-V4.1-Flash on ROCm appeared to hang after the shard progress bar reached 100%:

```
Loading safetensors checkpoint shards:  94% Completed | 45/48 [00:35<00:01,  2.15it/s]
Loading safetensors checkpoint shards:  96% Completed | 46/48 [00:35<00:00,  2.44it/s]
Loading safetensors checkpoint shards: 100% Completed | 48/48 [00:35<00:00,  1.34it/s]

(Worker_TP0 pid=9428) INFO 10-19 08:24:53 [default_loader.py:501] Loading weights took 240.81 seconds
```

This was fixed in #58857 for Nvidia but not AMD.

Cause is the AMD multimodal wrapper sorted the entire weight stream, which drained the lazy iterator before any weight had been copied, so all real loading happened afterwards with no progress output. That list also made the load itself slower: every shard was read once to build it and touched a second time during the copy phase.

This PR streams the language-model weight group instead, matching `deepseek_v41/nvidia/vl_model.py` and `deepseek_v4/common/vl_model.py`.

This PR also fixes misleading `Loading weights took` logs in case several models (base + draft) are loaded.

## Claims

The AMD V4.1 wrapper was the last place that sorted the entire weight stream before handing it to the child loader (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/models/deepseek_v41/amd/vl_model.py#L337-L347); it now streams the language-model group with `stream_language_model_first` (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/models/deepseek_v4/common/vl_model.py#L82-L97), as the NVIDIA V4.1 wrapper already does (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/models/deepseek_v41/nvidia/vl_model.py#L323). Weights are copied while the shard bar advances instead of after it completes, which removes the multi-minute silent phase between `Loading safetensors checkpoint shards: 100%` and the next log line.

Target `Loading weights took` on MI350, DeepSeek-V4.1-Flash, TP=4, one run per row, checkpoint evicted from page cache:

| condition | `main` | this branch |
|---|---|---|
| warm page cache | 23.0 s | 23–25 s |
| cold page cache | 233.7 s | **213.6 s** |

The ~20 s reduction (~8.6%) comes from the checkpoint no longer being traversed twice — once while the bar advances, then again in sorted order during the copy phase. With a warm cache both branches load in ~23 s and the difference disappears. The message is also attributed to a model (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/model_executor/model_loader/default_loader.py#L500-L505), so the target and draft timings of a speculative-decoding worker can be told apart in the log.

Unattributed timings on `main`, cold page cache. The bar completes, then ~3.5 min pass with no output, then both loads report the same message:

```
Loading safetensors checkpoint shards: 100% Completed | 48/48 [00:35<00:00,  1.34it/s]
(Worker_TP0 pid=9428) INFO 10-19 08:24:53 [default_loader.py:501] Loading weights took 240.81 seconds
Loading safetensors checkpoint shards: 100% Completed | 48/48 [00:26<00:00,  1.80it/s]
(Worker_TP0 pid=9428) INFO 10-19 08:25:21 [default_loader.py:501] Loading weights took 26.72 seconds
```

With this change, same command and same conditions. The copies now happen inside the bar:

```
Loading safetensors checkpoint shards:  98% Completed | 47/48 [03:12<00:08,  8.74s/it]
Loading safetensors checkpoint shards: 100% Completed | 48/48 [03:39<00:00, 14.36s/it]
(Worker_TP0 pid=14044) INFO 10-19 12:00:31 [default_loader.py:506] Loading weights took 220.06 seconds (model=DeepseekV41ForCausalLM)
Loading safetensors checkpoint shards: 100% Completed | 48/48 [00:05<00:00,  9.24it/s]
(Worker_TP0 pid=14044) INFO 10-19 12:00:38 [default_loader.py:506] Loading weights took 5.20 seconds (model=DSparkDeepseekV4ForCausalLM)
```

## Validation

Command (ROCm, MI350, TP=4; identical for both branches). The checkpoint is evicted from page cache first, because with a warm cache both branches finish in ~23 s and the difference is not observable:

```bash
# 1. Evict the checkpoint from page cache (advisory, no root needed)
python3 - <<'EOF'
import glob, os
snap = glob.glob(os.path.expanduser(
    "~/.cache/huggingface/hub/models--deepseek-ai--DeepSeek-V4.1-Flash-1017/snapshots/*"))[0]
for path in glob.glob(os.path.join(snap, "model-*-of-00048.safetensors")):
    fd = os.open(os.path.realpath(path), os.O_RDONLY)
    os.posix_fadvise(fd, 0, 0, os.POSIX_FADV_DONTNEED)

export OMP_NUM_THREADS=1

vllm serve deepseek-ai/DeepSeek-V4.1-Flash-1017 \
  --tokenizer-mode deepseek_v41 \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.9 \
  --moe-backend aiter \
  --tool-call-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --reasoning-parser deepseek_v41 \

  --block-size 64 &> ds_serve.log &
```

Method: the server log was sampled every 30 s during the load.

| | `main` | this branch |
|---|---|---|

| silent phase after bar | ~210 s | none |

## Details

**Root cause.** `AutoWeightsLoader._groupby_prefix` groups with `itertools.groupby` on the first path component (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/model_executor/models/utils.py#L263-L281), so a child module is delegated once per *contiguous* run of its names, and the V4.1 language model finalizes fused expert weights inside `load_weights` and must be called exactly once. `sorted()` therefore drained the mmap-view generator (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/model_executor/model_loader/weight_utils.py#L1083) while the tqdm bar is driven by the shard loop (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/model_executor/model_loader/weight_utils.py#L1169), leaving every `copy_` for after the bar.

**Alternative considered.** `finalizes_weights_during_load = False` (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/models/deepseek_v4/amd/model.py#L1466) would drop the contiguity requirement, but nothing on this path reads the flag and it would move the backbone's finalization (https://github.com/vllm-project/vllm/blob/255f14599ec0544c35539414810abdfa7e4e1c86/vllm/models/deepseek_v41/amd/model.py#L1404-L1412) after per-layer quantization finalize; left as a follow-up.

**Behavior changes.**

- No API, configuration or numerical change: same tensors, same order, finalization at the same point.
- The shard bar is slower per shard because it now includes the copies; total load time is lower and the post-bar stall is gone.
- `Loading weights took` now always carries a ` (model=<Class>)` suffix, so per-model timings are attributable.
