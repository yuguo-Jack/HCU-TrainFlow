# [Bugfix] Parenthesize penalties Triton chained `or` for Ascend backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/64013) · state: closed · merged: True

## Original PR description

## Overview

Fixes #64046

**One-line:** Ascend Triton cannot lower chained boolean `or` in V1 `_penalties_kernel` (`A or B or C` → `UnsupportedLanguageConstruct`). The first request with non-default sampling penalties can kill the TP worker group / EngineCore. This PR parenthesizes into binary `or`s. CUDA Triton semantics unchanged.

---

## What broke (feature)

This is the OpenAI-compatible **sampling penalty** path (`repetition_penalty` / `frequency_penalty` / `presence_penalty`), **not** MTP / EPLB / MDRv2 / KV pool. Those may be enabled in the same deployment but are unrelated to the compiler failure.

---

## Environment where we hit it

| Item | Value |
|------|--------|
| Hardware | Ascend A3 NPU |
| Deploy | PD disagg **4P8–1D8**, 505B W4A8, Ascend Triton |
| Path | `vllm/v1/worker/gpu/sample/penalties.py` → `_penalties_kernel` |
| Trigger | **First** request with non-default penalties (lazy JIT) |
| Incidents | 2026-10-24 14:35 (p0), 2026-10-26 22:34 (p1, `Worker_TP13`) |

Traffic without penalties can look healthy for a long time; sibling nodes on the same build are latent until they see a penalty request.

---

## Claims

- Removes Ascend Triton’s **chained-`or` AST** failure for `_penalties_kernel`.
- No intended behavior change on CUDA.
- Does **not** claim to fix every Ascend follow-on (BiShengIR / UB tile, missing `aclnnRightShift` in alternate torch paths). Those stay in NPU plugins / stack work.
- Not duplicating an open upstream PR for this AST issue (searched `UnsupportedLanguageConstruct` / chained boolean).

## Root cause / fix

| Layer | Status in this PR |
|-------|-------------------|
| L1 chained `or` | **Fixed** via parentheses |
| L2 BiShengIR / tile after parens | Out of scope (downstream) |
| L3 torch `>>` / RightShift gaps | Out of scope (downstream) |

```python
# before
use_penalty = use_rep_penalty or use_freq_penalty or use_pres_penalty

# after
use_penalty = (use_rep_penalty or use_freq_penalty) or use_pres_penalty
```

Ascend’s own error text recommends splitting the chain with parentheses.

---

## Validation

**Outside CI (Ascend NPU, production-like PD):**
- Repro: chat/completions with e.g. `repetition_penalty=1.1` (+ optional freq/pres).
- Before: `UnsupportedLanguageConstruct` on chained `or`, then worker/Engine death.
- After parentheses: this specific AST error is gone on stacks that only needed L1.

**CI / tests:**
- No new unit test: failure requires Ascend Triton; default CUDA CI cannot exercise it (documented resource constraint).
- Expect existing CUDA sampling / penalties paths to keep passing.

**Limitation:** some Ascend builds may still fail later (L2). NPU plugins may additionally shrink `BLOCK_SIZE` or ship a torch fallback (see omniinfer [#3147](https://gitee.com/omniai/omniinfer/pulls/3147) merged Triton adapt / [#3148](https://gitee.com/omniai/omniinfer/pulls/3148) torch exploration); that does not replace making upstream source AST-safe.

## Details / tradeoffs

- Tiny readability change; no CUDA perf impact expected.
- Keeps one shared kernel instead of forking Ascend-only source in core.
- **Merged NPU-plugin fix (same L1):** https://gitee.com/omniai/omniinfer/pulls/3147 — Ascend-compatible MRv2 penalty kernel writing + UT (merged). This upstream PR mirrors the L1 parentheses part into vLLM `main`.
- Alternate NPU torch rewrite (L2/L3 context, closed): https://gitee.com/omniai/omniinfer/pulls/3148
