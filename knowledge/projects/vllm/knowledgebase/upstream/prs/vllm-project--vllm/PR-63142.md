# [KVConnector][Mooncake] Coalesce descending block ids to reduce descriptor number for Mooncake TE

[Upstream PR](https://github.com/vllm-project/vllm/pull/63142) · state: closed · merged: True

## Original PR description



## Overview

Implements phase 1 of [RFC #63006: Reduce descriptor and WR overhead to improve Mooncake KV transfer bandwidth](https://github.com/vllm-project/vllm/issues/63006). Reallocated blocks can arrive in descending order, which Mooncake's ascending-only grouping leaves as individual descriptors. Coalescing these blocks reduces descriptor construction and downstream Transfer Engine (TE) request/WR overhead.

## Claims

- For Qwen3-235B-A22B + 16k prompt, the descending layout drops from **96,256 × 8 KiB descriptors to 94 × 8 MiB descriptors**, with the same 752 MiB payload per rank/request. With 64 KiB Mooncake TE slices, data WRs drop from 96,256 to 12,032.  Reduces **KV xfer time by 56.38%** (79.832 -> 34.820 ms) and increases **KV bandwidth by 125.32%** (9,590.51 -> 21,609.67 MiB/s).

- Reaches comparable performance with NIXL connector for 1-16k prompt length, as benchmarked in [RFC #63006](https://github.com/vllm-project/vllm/issues/63006), instead of a significant gap.

- This PR can **only cover jointly descending runs** (e.g. P `[3, 2, 1]` blocks and D `[10, 9, 8]` blocks). Anti-diagonal src-dst pairs (e.g. P `[3, 2, 1]` blocks and D `[8, 9, 10]` blocks) cannot be coalesced and remain per-block descriptors.

## Details

Add a `_normalize_paired_block_order()` helper in `_build_transfer_params()`, before logical-to-kernel expansion and `group_concurrent_contiguous()` (which produces `group_remote_block_ids`). For each request/KV group, reverse segments where both source and destination IDs decrease consecutively by one, applying the same permutation to both lists. This preserves every `(src, dst)` pair and lets `group_concurrent_contiguous()` produce fewer descriptors.

- Why normalize before kernel expansion, instead of inside the grouping helper: With two kernel blocks per logical block, source `[3, 2]` and destination `[13, 12]` expand into `[6, 7, 4, 5]` and `[26, 27, 24, 25]`. These kernel lists have no consecutive descending edges, so reversing descending runs inside grouping would miss the merge. Normalize logical IDs first to `[2, 3]` / `[12, 13]`, then expand to `[4, 5, 6, 7]` / `[24, 25, 26, 27]`

- Why not full sort: sort takes O(NlogN), we reverse segments in O(N) to minimize the overhead of the helper. We identify jointly descending consecutive segments, and each segment is reversed independently. With vectorized numpy implementation, the helper overhead is **0.2 ms avg**, **0.64 ms max** with 16k prompt runs.

### Execution Time Breakdown

We show the 16k prompt run execution time breakdown with the same approach in [RFC #63006](https://github.com/vllm-project/vllm/issues/63006). Each call transfers 752 MiB, mean values:

| Configuration / input layout | Calls | Descriptors/call | Submit (ms) | Wait (ms) | First post offset (ms) |
| --- | ---: | ---: | ---: | ---: | ---: |
| Before normalization, ascending| 600 | 94 | 2.275 | 40.825 | 2.881 |
| Before normalization, descending| 600 | 96,256 | 30.483 | 52.060 | 33.254 |
| After normalization| 1,200 | 94 | 2.464 | 31.382 | 3.247 |

- **submit** constructs and enqueues WRs
- **wait** polls completion while background workers continue posting and progressing RDMA.
- **first post offset** is the wall time from the C++ API entry to the return of the first worker WR post. Normalization reduces descriptors so that TE workers don't need to wait for a long WRs contruction period.

Thanks for the review. The "descending prefix + ascending tail" case is expected to emit one `+1` run, and I have added this test case in the new commit.

The root cause of the performance gap in the 32K run is interesting: with APC disabled, blocks are returned to the allocator in reversed order, but a request's block lifecycle management diverges between P and D: for request R1, D can release its blocks after a forward, and these blocks are allocated again for request R2 in reversed order.  But P needs to reserve R1's blocks during KV transfer,  while the newly arrived request R2 needs to apply for new blocks. As a result, I observe this 4-cycle loop in the 32K run (after warmup requests):

Request # | P source IDs | D destination IDs | Descriptors
-- | -- | -- | --
1 | 2048 → 1 | 2048 → 1 | 94
2 | 2049 → 4096 | 1 → 2048 | 94
3 | 1 → 2048 | 2048 → 1 | 192,512
4 | 4096 → 2049 | 1 → 2048 | 192,512

Therefore, half of the requests' blocks cannot be coalesced as P/D block ids go in different directions. The average API call time alternates between 67.36 ms and 259.56 ms, resulting in 160 ms total average. This phenomenon is expected, as coalescing cannot decide the block allocation logic on both sides.

1-16K runs do not show this pattern because at 0.5 rps, P/D block allocations are basically "synchronized": P can release a request's block before the next request comes. In the 32K run, P is saturated (> 100s TTFT, queueing), but D rps is throttled by P's request-handling throughput, thereby this pattern appears.

With 32k run + APC on, P/D reserves all allocated blocks for each request, and this 4-cycle loop disappears. The average API call is 69.672 ms, KV BW is 21612.980 MiB/s, aligned with NIXL performance.
