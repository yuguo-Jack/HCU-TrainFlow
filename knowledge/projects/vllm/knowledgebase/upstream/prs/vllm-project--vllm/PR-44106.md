# fix: prompt logprobs in Model Runner V2

[Upstream PR](https://github.com/vllm-project/vllm/pull/44106) · state: open · merged: False

## Original PR description



## Purpose
Fix V2 model runner prompt logprobs returning logprobs for the wrong token IDs.

In async V2, prompt logprob target IDs were derived from mutable GPU request state. By the time prompt logprobs were computed, that state could already reflect later runner input, causing responses like `/v1/completions` with `echo=true&logprobs=...` to fail for the actual prompt token ID. This PR stores immutable prompt token IDs in `PromptLogprobsWorker` and derives prompt-logprob targets from that source.

The Triton target-ID kernel was removed because it read mutable runner/GPU state and was the source of the race. Ideally we should reintroduce a GPU path if prompt token IDs are carried through an immutable per-request/batch buffer. I havent tested for any perf impact with this PR yet, but the triton kernel should be investigated.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Copy cached prompt ids before storing**

For streaming sessions that request prompt logprobs, this stores the same `prompt_token_ids` list object that comes from the scheduler (`NewRequestData.from_request` passes `request.prompt_token_ids` through directly), but streaming updates mutate that list in place when the session continues. If such a request remains resident across a stop/wait-for-streaming transition or has chunked prompt-logprob state, the worker can later read the mutated prompt rather than the snapshot that matches the runner's cached `prompt_len`/`computed_prefill`, producing shifted or incorrect prompt-logprob token ids. Store `list(prompt_token_ids)` here so the runner state is immutable for the lifetime of this cached request.
