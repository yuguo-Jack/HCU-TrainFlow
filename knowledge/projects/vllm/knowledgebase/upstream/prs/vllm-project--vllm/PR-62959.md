# [Bugfix][Multimodal] Fix Qwen3-VL EVS M-RoPE positions for the outer vision marker and chunked prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/62959) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #62937 and #62969. #62975 is folded into this PR, as requested in review.

With video pruning (EVS / VidCom2) on Qwen3-VL-family models, `recompute_mrope_positions` placed video M-RoPE positions wrong in two ways:

1. **Outer marker (#62937).** The prompt keeps the outer `<|vision_start|>` (transformers >= 5.10), and the recompute treated it as frame 0's marker, so the video started `num_timestamp_tokens + 1` tokens too early. After a short prefix this crashed EngineCore on the first prefill step. After a longer one it silently overwrote the positions of the preceding text.
2. **Mid-video chunks (#62969).** A chunked-prefill boundary inside a video placeholder gave wrong positions to every following token, and a wrong `mrope_position_delta` for decode.

Both model runners now pass each media slice's placeholder offset, and 5-channel slices are placed from it. The `vision_start` search is kept as the fallback for callers that pass no offsets, and it now recognizes the outer marker.

## Claims

- No more `RuntimeError: The expanded size of the tensor (0) must match ...` for Qwen3-VL video requests with `--video-pruning-rate` after a short text prefix.
- M-RoPE positions for Qwen3-VL-family models (Qwen3-VL, Qwen3-VL-MoE, Qwen3.5, Cosmos3, Cosmos3-Edge, InternS1-Pro) and Cohere Compass no longer depend on where chunked prefill splits a placeholder, on both Model Runner V1 and V2. This also covers several media items in one chunk and the `vision_start | media` split (#48833).
- The 4-channel path (Qwen2.5-VL) and the prompt layout without outer markers (Cosmos3-Edge) are unchanged.

## Details

**Root cause.** Qwen3-VL's pruned video placeholder is registered with `PromptUpdateDetails.from_seq`, so the runner passes positional slices of the placeholder whose t/h/w values are relative to its first token. Placing a slice needs the placeholder offset (for the anchor) and the slice start (`max(num_computed_tokens, offset)`). `recompute_mrope_positions` received neither, and inferred them from `vision_start` indices and media-token counts:
- With the outer marker kept, the first `vision_start` found is the outer one, so subtracting `num_timestamp_tokens` lands 7 tokens early.
- Inside a placeholder, the anchor, the write offset, and the "all media tokens seen" early exit are all wrong, because the prompt lumps every retained video token on frame 0 while the model spreads them across frames (traces in #62969).

**Change.**
- `recompute_mrope_positions` takes an optional `multimodal_offsets`. With offsets and 5-channel entries, a small separate loop anchors each slice at `positions[-1, offset - 1] + 1`, writes it at `max(num_computed_tokens, offset)`, and extends the trailing text positions.
- `GPUModelRunner._gather_mm_embeddings` (V1) and `MultiModalPruner` (V2) pass the offsets they already compute while windowing; in V2, `_num_window_embeds` became `_window_offsets`. The protocol and the in-tree implementations (Qwen3-VL, Qwen2.5-VL, Cohere Compass) forward the new keyword.
- In the fallback search, the outer `vision_start` is recognized by frame 0's own `vision_start`, which follows it after `num_timestamp_tokens`. The placeholder then starts right after the outer marker.

**Compatibility.** The new keyword defaults to `None`. Both runners pass it, so an out-of-tree `SupportsMultiModalPruning` model would need to accept it.

**GPU sync.** The new path uses fewer `nonzero` / `count_nonzero` ops than the old one and keeps the single `.item()` for the delta. The fallback check adds one scalar read, inside the existing `gpu_sync_allowed()` region.

**Not changed.** The V1 drafter pass (`shift_computed_tokens=1`) still calls the recompute with the unshifted `num_computed_tokens` (#43820). V2 doesn't recompute in the draft pass.

**Not a duplicate.** No other open PR addresses #62937 or #62969. #48835 (for #48833) rewrites the same `vision_start` search; it is still relevant for the 4-channel path.
