# [Bugfix][KV Offload][P2P] Prefill locally while a peer handshake is pending

[Upstream PR](https://github.com/vllm-project/vllm/pull/64501) · state: closed · merged: True

## Original PR description



## Overview

A symmetric-P2P consumer now prefills locally instead of waiting while a session's handshake is pending, so a request that names a stopped or deleted source returns at once rather than after up to `VLLM_P2P_HANDSHAKE_TIMEOUT_S` (30 s). Closes the gap reported in https://github.com/vllm-project/vllm/issues/63602#issuecomment-6491634566.

## Claims

- `remote_kv_source` requests to a stopped (SIGSTOP), force-deleted or gracefully deleted source: p50 15.7–17.0 s / max 30.1 s → p50 22 ms / max 4.7 s. The worst case is now the 8 s lookup timeout, for a lookup already in flight when the source stops.
- No regression in the reproducer's other checks: A never freezes, A→C pulls stay at 100%, and pulls from B or its replacement B2 recover fully.
- The PD path (`remote_prefiller`) is unchanged and keeps its eager HIT.

## Details

**Root cause.** For a `remote_kv_source` request, `on_new_request` opens a session to the source, and `lookup()` registers a probe and returns RETRY until the LookupResp arrives. `ClientRole.flush_pending_lookups` holds probes until the peer acks ConnectMsg, and the 8 s lookup deadline only starts when the LookupMsg goes out. While the handshake is pending, the only bound on the request is the 30 s handshake deadline.

When the source stops or goes away:
1. The first lookup timeout ends the session.
2. No reconnect backoff applies, since backoff is scheduled only after a data-plane fault.
3. The next request opens a new session at once and waits on its handshake.

Each request therefore waits for whatever remains of the current 30 s handshake, which gives the ~17 s p50 and 30 s max.

**Fix.** `lookup()` treats a session that is not `ready` like a missing session and returns MISS. It returns before `register_lookup`, so the peer never gets lookup state for the request, and `finish` owes it no terminal FetchMsg. Inbound and outbound sessions both send ConnectMsg and become `ready` on the ack, so reused inbound sessions behave the same way.

**Tradeoff.** A request that arrives before its session's handshake completes now recomputes instead of pulling. That includes the first request to a new or replacement peer. Sessions persist across requests (idle ones are reaped only near `VLLM_P2P_MAX_PEERS`), so this costs one window per peer of about the handshake time, 14–40 ms of registration on these pods. The c8 rolling-replace run pulled 400/400 from B2. Recomputing a prefix is cheaper than waiting up to 30 s on a peer that may be gone.

**Not changed.**
- The reconnect backoff for timeout-ended sessions (the issue's other proposal) is not added. With this change, a dead peer costs at most one cheap connect attempt per handshake window, and no request waits on it.
- A lookup already in flight when its source stops still waits up to the 8 s lookup timeout (#63781).
