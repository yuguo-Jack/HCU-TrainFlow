# [Bugfix][KV Offload] Anchor the partial-tail lookup on the full-attention prefix

[Upstream PR](https://github.com/vllm-project/vllm/pull/58618) · state: closed · merged: True

## Original PR description

## Purpose

Split out of #57216 per @orozery's review (part 1 of 2): the lookup half. The DCP store half is #58619.

`_lookup` anchors the partial-tail search on `_lookup_complete_chunks`, which requires *every* KV cache group to have a complete chunk at the anchor boundary, including the recurrent groups. A recurrent `align` group holds state only where a scheduler step ended on one of its block boundaries: in practice at the producer prompt's last full recurrent block and at its tail.

With **uniform block sizes** (dcp=1, the only shape `supports_partial_tail` admits today) the last-full-block boundary is also a full-attention chunk multiple, so that aligned row lands on the chunk grid, `complete_hit` reaches it, and the existing one-window probe finds the tail. The anchor only fails when that row is missing, e.g. evicted separately from the tail. So on `main` today this is a robustness fix.

With **mixed block sizes** -- under DCP the full-attention offload block is `dcp x` the attention block while recurrent blocks stay unsharded (12288 vs 1536 at DCP 8) -- the aligned row sits at a recurrent multiple that is essentially never a full-attention multiple. `complete_hit` is then 0 for any prompt past the first chunk, the search is capped at one window from zero, and a correctly stored tail further out is never probed although it is resident. That is the state #58619 (the DCP store side) would land in without this PR: tails get stored, but only those within one window of the complete-chunk hit are ever found -- the "#58619 only" column of the hardware table below. **This PR is the prerequisite for #58619's lookups to work.**

Instrumented `_lookup` on a replay (chunk 12288, hash 128), before the change:

```
n=12620  complete_hit=12288  complete_boundary=12288  max_boundary=12544
           boundary=12544 ALL GROUPS HIT                  <- restores
n=15136  complete_hit=0      complete_boundary=0      max_boundary=12160
           boundary=12160 group=0 MISS ... 11776 MISS     <- tail stored at 15104,
                                                            never probed
```

Fix: anchor the partial-tail search on the boundary the full-attention groups proved, which `_lookup_complete_chunks` already returns (since #63566), and check recurrent groups only at the candidate boundary. Per review, the search runs from one window past the anchor down to the complete-chunk hit and skips block-aligned boundaries (complete chunks, which the complete-chunk lookup already missed), so a longer full-attention prefix stored by another request cannot hide this request's own tail. If a full-attention chunk between the complete hit and the anchor is still being loaded, the search falls back to the complete hit. No second lookup and no new parameters.

The reported hit is never shorter than the complete-chunk hit, so the change can only widen what a lookup reports. Pending full-attention chunks are handled exactly as in the complete-chunk lookup on `main`.

- zamog · comment · 2026-10-28T19:22:15Z · [source](https://github.com/vllm-project/vllm/pull/58618#issuecomment-6478427034)

Hi @nvyutwu, we build on the same idea for Decision 3.0 state caching (RFC #64267): CPU-tier loads of Mamba states
saved inside a block. Once such loads happen, we found a scheduler deadlock that this PR could expose on main.

An async KV load that ends inside a block is promoted by caching the loaded tokens. That registers a partial hit in
every align-mode Mamba group (`_cache_partial_tail_block`), and the next `allocate_slots` copies the state into a
new block per group. The admission gate (`reserved_blocks`) and the in-flight reservation
(`_request_remaining_blocks`) estimate the request before promotion, so they don't count that block. Concurrent
loads can then fill the pool: every load completes, none can be promoted, nothing is running to free blocks, and
the scheduler stalls.

- Reproduced on our branch: 4 concurrent questions whose 600-token states load from the CPU tier, 24-block pool
  (block 64, prefix match unit 16). Without the fix they never finish.
- Current main can't reach it. It stores the mid-block state, but the lookup never loads it (0 load jobs; the
  question recomputes all its tokens). So it shows up only with mid-block lookups like this PR's.
- We haven't run this PR's branch. If its lookup loads such a state asynchronously, the same promotion path applies.

Our fix (+37/−3, as #57104 does for spec-decode lookahead blocks): a per-manager `get_num_load_cow_blocks` hook
(one block per align-mode Mamba group when the load ends inside its block, 0 otherwise), added in both places.
https://github.com/zamog/vllm/commit/9099abf22ba0b74fa79c69eacfe35341dfbb4f35 (test:
`test_concurrent_loads_reserve_the_promotion_cow_block`).

Would you like it as a commit for your branch, or as a follow-up PR stacked on yours?

AI assistance (Claude Code) was used to find this and write the fix and test, and AI agents reviewed them.

— Gilad Zamoscinski
