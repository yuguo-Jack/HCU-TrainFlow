# [Perf][Hybrid] Reserve Mamba speculative-decoding scratch per running request instead of per KV-concurrency slot

[Upstream PR](https://github.com/vllm-project/vllm/pull/57261) · state: closed · merged: False

## Original PR description

## Purpose

For a hybrid (Mamba / linear-attention) model with speculative decoding, `MambaSpec.max_memory_usage_bytes` charges each request `num_speculative_blocks` extra state pages per Mamba group. In `align` mode:

```python
return self.page_size_bytes * (
    2 + self.num_speculative_blocks + self.num_prefill_checkpoint_blocks
)
```

`get_max_concurrency_for_kv_cache_config` then divides the whole block pool by that per-request footprint — so the drafting scratch is reserved **once per KV-concurrency slot**.

But scratch is not a per-request resident working set. `MambaManager` allocates it once, when a request first gets blocks, relocates it in place every step (`_relocate_speculative_block` moves the block within the request's block list rather than allocating a new one), and frees it with the request. Only a *running* request drafts, so at most `max_num_seqs` copies of the scratch exist at any instant — no matter how many requests the pool could hold.

On GLM-5.3-Flash at TP4 with MTP `num_speculative_tokens=3` (34 KDA linear-attention layers in 3 Mamba groups + 12 MLA groups), the per-request charge is 45 blocks, of which **9 are Mamba speculative scratch**, and that 9 was being multiplied by 19.4 concurrency slots although only 8 requests can ever speculate at once.

### The change

* New `KVCacheSpec.speculative_scratch_bytes(vllm_config)`, returning `0` by default. `MambaSpec` returns `page_size_bytes * num_speculative_blocks`; `UniformTypeKVCacheSpecs` aggregates it the same way it aggregates `max_memory_usage_bytes`.
* New helper `_pool_concurrency_limit(num_blocks, blocks_per_request, scratch_per_request, max_num_seqs)`: reserve `max_num_seqs * scratch_per_request` blocks **once**, then divide the remainder by the scratch-free per-request cost.
* Below the crossover — when the pool holds fewer than `max_num_seqs` requests — every resident request may also be running, so the old formula is kept. The two branches agree exactly at `all_running == max_num_seqs`, so the curve is continuous.
* With no speculative scratch (`num_speculative_blocks == 0`, spec decode off, or any non-Mamba spec) the result is bit-identical to before, including for the separate host-resident pool, which goes through the same helper.
* A spec can never claim more scratch than footprint (`scratch = min(scratch, required)`).

**Allocation itself is unchanged.** The block pool keeps its full size, and the scheduler still allocates scratch on demand against the real free-block count, so the reserve cannot be over-committed. Only the *reported* capacity changes — i.e. how much of `max_model_len` worth of KV cache vLLM tells you it has, and the `GPU KV cache size` / `Maximum concurrency` log line.

**The one design point worth a reviewer's opinion:** reported max concurrency now depends on `max_num_seqs` for models that have speculative Mamba scratch. That is intentional — the quantity being reserved genuinely scales with the running-batch bound, not with the pool — but it does mean the same pool reports a different concurrency under a different `--max-num-seqs`. Happy to change the shape of the fix if maintainers would rather keep concurrency a pure function of the pool.

This applies to any Mamba / linear-attention hybrid with `num_speculative_blocks > 0` (Nemotron-H, Kimi Linear, GLM-5.x, …), and is pure Python capacity arithmetic — no kernels, no device-specific code.

## Test Plan

* 4 new unit tests in `tests/v1/core/test_kv_cache_utils.py`, covering the accounting:
    * `test_mamba_speculative_scratch_excluded_from_concurrency` — 873 blocks, 3 Mamba groups, `n_spec=3`, `max_num_seqs=8`: the reserved pool is exactly `max_num_seqs * scratch_per_request`, and `get_kv_cache_capacity` agrees with `get_max_concurrency_for_kv_cache_config`.
    * `test_mamba_concurrency_unchanged_without_spec_decode` — bit-identical with `n_spec=0`.
    * `test_mamba_scratch_not_discounted_below_max_num_seqs` — a pool holding 19.4 requests with `max_num_seqs=64` keeps the old formula.
    * `test_pool_concurrency_limit_edge_cases` — no scratch, below/at/above the crossover, monotonicity and "never worse than the old formula" swept over pool sizes 1..2000, and a degenerate spec whose whole footprint is scratch.
* 2 new tests in `tests/v1/core/test_single_type_kv_cache_manager.py`, checking that the *allocator* respects the bound the planner now assumes:
    * `test_mamba_speculative_scratch_bounded_by_running_requests[0,3]` — 8 concurrent requests driven through two full prefill (16 chunks) + decode (40 steps) rounds; peak held blocks are exactly `8 * (2 + n_spec)`, the scratch share exactly `8 * n_spec`, and the pool is fully returned after each round.
    * `test_mamba_speculative_scratch_bytes_matches_spec` — `speculative_scratch_bytes` is exactly the scratch part of `max_memory_usage_bytes` for `n_spec` in {0, 1, 3}, and `0` for `FullAttentionSpec`.

```bash
pytest tests/v1/core/test_kv_cache_utils.py tests/v1/core/test_single_type_kv_cache_manager.py
```

* End-to-end serve of a real hybrid + MTP model, before/after, comparing reported KV cache size and max concurrency at identical memory, plus GSM8K accuracy, TTFT/decode timings, and an over-subscription run to confirm the `max_num_seqs` bound actually holds.
* `ruff format` / `ruff check` and the pre-commit hooks runnable without a full install.

`ruff format --check` and `ruff check` clean on all four changed files; `check-spdx-header`, `check-forbidden-imports`, `check-torch-cuda-call`, `check-root-lazy-imports` and `check-boolean-context-manager` all pass.

End-to-end: GLM-5.3-Flash W4A16-MTP (`canada-quant/GLM-5.3-Flash-W4A16-MTP`), tensor-parallel 4, MTP `num_speculative_tokens=3`, `--max-num-seqs 8`, `--max-model-len 32768`. KV pool 873 blocks of 14,611,968 B = 11.88 GiB/rank; per-request charge 45 blocks, of which 9 are Mamba speculative scratch.

| metric | before | after |
|---|---|---|
| GPU KV cache size | 635,699 tokens | **729,088 tokens (+14.7%)** |
| Maximum concurrency | 19.40x | **22.25x** |
| KV pool size | 11.88 GiB | 11.88 GiB (unchanged) |
| GSM8K (50 problems, greedy, conc 8) | 0.980 | 0.980 (twice) |
| TTFT / decode throughput | baseline | unchanged within run-to-run noise |

A run at concurrency 16 against `--max-num-seqs 8` queued cleanly with zero errors and no allocation failures, confirming that the running-request bound the reserve assumes is the bound the scheduler actually enforces.

Analytically for the same model at pipeline-parallel 4 (block size 4352, `n_spec=2`), 8 of the 25 per-request blocks are scratch, giving **+35.6%** (1,074,790 -> ~1,457k tokens). Not re-measured — the arithmetic is the same helper.

**Hardware note:** the sm_80 serving above ran on 4x NVIDIA CMP 170HX (GA100, 64 GB) using an out-of-tree Ampere sparse-attention backend. **That backend is not part of this PR** and nothing here depends on it — this change is hardware-agnostic capacity arithmetic in `vllm/v1/core/kv_cache_utils.py` and `vllm/v1/kv_cache_interface.py`. Any Hopper/Blackwell hybrid + spec-decode setup (Nemotron-H, Kimi Linear) should see the same relative gain, and a reviewer reproduction there would be very welcome.

Models without Mamba speculative scratch — every non-hybrid model, and every hybrid with speculative decoding off — report exactly the numbers they reported before.
