# [Bugfix][MoE] Keep FlashInfer BF16 MoE correct across load_weights refits

[Upstream PR](https://github.com/vllm-project/vllm/pull/62332) · state: open · merged: False

## Original PR description

## Purpose

Fixes #42821. Follow-up to https://github.com/vllm-project/vllm/pull/54699#issuecomment-6244567325.

FlashInfer TRT-LLM BF16 MoE (BlockMajorK, since #54699) and gated FlashInfer CUTLASS MoE (`[w3; w1]`) reorder each expert's rows in place during post-load processing, while the parameters keep their checkpoint shape and loader. A later `model.load_weights(...)` refit then writes checkpoint-layout bytes under the kernel. Nothing raises, and the experts are silently wrong. On `main`, only one refit pattern works:

| Refit after post-load processing | `main` | this PR |
|---|---|---|
| All experts, then post-load processing | correct | correct |
| All experts, no post-load processing (e.g. `reload_mode="direct"`, #58382) | wrong | correct |
| Some experts, then post-load processing | wrong (the others are converted twice) | correct |
| Some experts, no post-load processing (incl. sparse checkpoint patches) | wrong | correct |

## Implementation

Both layouts only reorder each expert's rows (TRT-LLM also tiles K into blocks), so every checkpoint shard maps to a fixed set of kernel rows.

- **Mark converted weights:** post-load processing attaches a layout writer to the weights it converts, and skips weights that already carry one. Running it again is therefore a no-op.
- **Refit through the writer:** a refit into converted weights gathers the shard's kernel rows into a checkpoint-layout copy, runs the existing loader on the copy (TP slicing, padding), and scatters the rows back. Rows the refit does not touch keep their values.
- **Unconverted loads unchanged:** cold start, layerwise reload and sharded RDT replay load unconverted tensors, so they take the existing path.
- **Cleanup:** the TRT-LLM post-load step no longer re-aligns the intermediate size. The experts already allocate it padded, so that step never padded.

**Cost.** One gather/scatter per shard, on refits only, plus one expert-sized scratch buffer per weight shape.

**Known limits (same as `main`).** DBRX's expert loader writes `param.data` directly. Weights restored from the IPC weight cache carry no writer.

**Related.**
- #56570 (closed) swizzled TRT-LLM slices on the fly. It was closed because full refits followed by post-load processing work after #54699. Compared with it, this PR leaves unconverted loads untouched, keeps partial and sparse refits correct, makes post-load processing idempotent, and covers CUTLASS.
- #42823 (closed as stale) routed every later load through layerwise reload.

## Validation

Hardware and software: GB300 (SM103), PyTorch 2.14.0+cu132, FlashInfer 0.7.2.

Steps: cold start, then a direct `model.load_weights(...)` of the same checkpoint, then `reload_weights()`. Each step fingerprints every parameter and runs GSM8K (1319 questions, 5-shot). In every configuration, this PR's weights after cold load and after the refit are bitwise identical to `main`'s cold load.

| Model, MoE backend | Params changed by the refit (`main` → this PR) | GSM8K `main`: cold / refit / reload | GSM8K this PR: cold / refit / reload |
|---|---|---|---|
| Qwen3-Omni-30B-A3B, TRT-LLM, TP=1 | 96 → 0 | 0.8544 / **0.0000** / 0.8529 | 0.8537 / 0.8529 / 0.8529 |
| Qwen3-Omni-30B-A3B, TRT-LLM, TP=2 | 96 → 0 per rank | — | 0.8491 / 0.8499 / 0.8499 |
| Qwen3-Omni-30B-A3B, CUTLASS | 48 → 0 | — | 0.8522 / 0.8628 / 0.8461 |
| Nemotron-3-Nano-30B-A3B-BF16 (non-gated, padded intermediate), TRT-LLM | 46 → 0 | 0.2745 / **0.0053** / 0.2745 | 0.2745 / 0.2745 / 0.2745 |

- **GSM8K noise:** on CUTLASS and TP=2, GSM8K moves by about one point between runs, including on the unchanged `reload_weights` path, while the weights stay bitwise identical.
- **Cold load time is unchanged:** Qwen3-Omni loads in 16.8 / 16.9 s on `main` and 16.1 / 16.1 s here.
