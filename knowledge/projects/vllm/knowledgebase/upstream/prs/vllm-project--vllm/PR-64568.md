# [Bugfix][Rust] Preserve nullable string parameters in the Muse parser ( # 64546  )

[Upstream PR](https://github.com/vllm-project/vllm/pull/64568) · state: open · merged: False

## Original PR description

## Overview

Fixes the Rust half of #64546. The Rust Muse parser keeps raw text only for parameters declared exactly `{"type": "string"}`, so `Optional[str]` parameters are JSON-decoded and `"10001"` reaches the client as the number `10001`.

Not a duplicate: #64539 fixes the same bug in the Python Muse, MiniCPM5 and Poolside V1 parsers but changes no files under `rust/`. This PR is the Rust counterpart, so both frontends agree once both land.

## Claims

- With the Rust frontend, `Optional[str]` parameters in Muse tool calls keep their raw text for all common spellings: `{"type": ["string", "null"]}`, `{"anyOf": [{"type": "string"}, {"type": "null"}]}`, and the `oneOf` form.
- Non-string and unconstrained parameters still JSON-decode as before.

## Validation

- New test `muse_preserves_nullable_string_parameters`, using the issue's `"10001"` example, covers the plain, type-list, `anyOf` and `oneOf` string forms plus a nullable integer and an untyped parameter. It fails without the fix with exactly the issue's output (`"zip_list": 10001`, ...) and passes with it.
  ```bash
  cargo test -p vllm-parser            # 625 passed
  cargo clippy -p vllm-parser --all-targets -- -D warnings   # clean
  cargo fmt -p vllm-parser --check     # clean
  ```

## Details

**Root cause:** `MuseUnifiedParser::new` built its set of string parameters with `schema.get("type").and_then(Value::as_str) == Some("string")`, which only matches a bare string type. Every nullable form failed the check, so those values went through JSON decoding.

**Fix:** read each parameter schema through the crate's existing `SchemaRoot::options` (also used by `tool/parameters.rs` and the output grammars), which already expands type arrays, `anyOf`/`oneOf`, `$ref`, and `nullable`. A parameter is treated as a string when any constrained option is a string. Options that are only `OptionSource::Any` (an untyped schema) are ignored, matching how `tool/parameters.rs` treats unconstrained schemas, so untyped values keep decoding.

**Deviations from the Python fix in #64539** (per `rust/AGENTS.md`), both from reusing the shared schema reader:
- `$ref` to a string definition is recognized; the Python helper doesn't resolve `$ref`.
- A string-only `enum` and `"nullable": true` on a string are recognized; the Python helper doesn't handle them.

In both cases Rust keeps raw text where Python would decode, which is the behavior #64546 asks for.

**Scope:** Muse Glimmer decodes values on purpose; it has no Rust parser, so it is unaffected.
