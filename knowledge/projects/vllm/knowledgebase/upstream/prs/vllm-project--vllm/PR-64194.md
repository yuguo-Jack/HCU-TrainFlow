# [Bugfix][Kernel] Fit Triton unified attention tiles into shared memory on SM75

[Upstream PR](https://github.com/vllm-project/vllm/pull/64194) · state: closed · merged: False

## Original PR description

## Overview

Triton unified attention launches a prefill tile that does not fit in 64KB of shared memory for 512-wide heads (Gemma 4 global layers). Halve that tile only when the compiled request exceeds the device limit.

Related: #38918, #57712. This is a different approach from the open #39018, which uses a fixed 98,304-byte cutoff and also edits FlexAttention. The estimate-and-halve pattern follows the Triton prefill fitter that landed via #60942 (see also #60631).

## Claims

- On CUDA devices with 65,536 bytes of shared memory, an fp16 head of size 512 launches tile 16 instead of tile 32 (98,304 bytes required).
- Head sizes 128 and 256, and head size 512 on devices with at least 98,304 bytes, keep tile 32.
- fp8 stays at tile 32.

## Validation

Reported failure (deployment record, vLLM 0.23.0+cu129; this commit was not re-run on that machine):

- 2× Tesla T4 (SM75, 65,536 bytes/block), Gemma 4 12B IT, FP16, TP=2, `--enforce-eager`
- `GET /health` returned 200. The first `/v1/chat/completions` request returned 500.
- Triton prefill kernel in `vllm/v1/attention/ops/triton_unified_attention.py`, tile 32, head size 512: `OutOfResources: shared memory, Required: 98304, Hardware limit: 65536`.
- Returning tile 16 when `head_size >= 512` and `element_size >= 2` made generation succeed.

Serving numbers from that tile-16 deployment (one sample each, functionality after the workaround, not a speedup claim for this commit):

| workload | result |
|---|---|
| short prompt, 128 output tokens | about 9.18 tok/s (decode 13.942 s) |
| 4 concurrent requests, 128 tokens each | 512 tokens in 14.834 s, about 34.52 tok/s aggregate |

Unit tests on this commit (CPU, shared-memory limit mocked, kernel launch mocked):

```bash
  tests/kernels/attention/test_triton_unified_attention.py::test_prefill_tile_fits_shared_memory -v
```

6 passed.

With the fitter replaced by the identity, the same 65,536-byte launch still passed `TILE_SIZE=32`. With the fitter, that case passes `TILE_SIZE=16`.

`pre-commit run` on the two files: `ruff-check`, `ruff-format`, `typos`, `check-spdx-header`, and `check-root-lazy-imports` passed.

L4 has about 101,376 bytes, so stock tile 32 still fits there; the new test mocks 65,536 bytes and does not need a T4. No end-to-end Gemma 4 run of this commit was possible here (no T4, no checkpoint).

## Details

`_get_tile_size` returns 32 for every prefill. Gemma 4 12B global layers use 16 query heads and 1 KV head, so `BLOCK_M` is 16. For fp16 the compiled kernel requests two copies of the Q tile `(BLOCK_M, HEAD_SIZE_PADDED)` and the K tile `(HEAD_SIZE_PADDED, TILE_SIZE)`:

`2 * element_size * head_size_padded * (BLOCK_M + TILE_SIZE) = 2 * 2 * 512 * (16 + 32) = 98304`.

That is the SM75 error. Launching with `num_stages=1` does not lower it (measured on #39018). Triton raises only when `shared > max_shared`, so a request equal to the limit is accepted. Tile 16 is `2 * 2 * 512 * (16 + 16) = 65536`, which fits a T4. Tile 16 is already a legal constexpr (fp16 decode uses it).

`_fit_tile_to_shared_memory` halves the tile while that estimate exceeds `get_max_shared_memory_bytes()` (cached). It stops at 16 for dtypes of 2 bytes or wider, and at 32 for fp8, matching the existing fp8 tile floor. The check runs only on CUDA, because the query is a CUDA device attribute. ROCm and XPU keep their current tiles. The read is a cached device attribute, not a per-step GPU sync.

#39018 compares the device with a fixed 98,304-byte cutoff and always jumps from 32 to 16 when the padded head is at least 512. It also edits FlexAttention, and its first version called the CUDA shared-memory op on XPU. This change uses the actual `BLOCK_M`, padded head, and dtype, and leaves a launch alone when the estimate already fits: head 256 on a T4 stays at 32 (49,152 bytes); head 512 on a device with at least 98,304 bytes stays at 32.

Limitations:

- No T4 re-run of this tree. The serving numbers are from the vLLM 0.23.0 tile-16 workaround, which selects the same tile this patch selects for Gemma 4 12B fp16.
- The factor of two and the `element_size` scaling are checked against the fp16 98,304-byte failure. fp32 head 512 is extrapolated: tile 32 estimates 196,608 bytes, so a 166,912-byte device (A100 opt-in) would drop to tile 16. That fp32 launch was not measured.
- If `BLOCK_M` is 32 (more than 16 queries per KV head), tile 16 still estimates 98,304 bytes and does not fit in 64KB. Gemma 4 12B global layers use `BLOCK_M=16`.
- `int4_per_token_head.py` calls `_get_tile_size` and does not use this fitter.
- ROCm is unchanged.

AI assistance (Grok 4.7 in Cursor) was used to investigate, implement, and test this change. The diff is two files. A human should review every line and run the attention kernel tests on a GPU before marking the PR ready.
