# [ROCm][PP] Stage hand-off on SDMA copy engines (--pp-sdma-handoff)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65658) · state: open · merged: False

## Original PR description

## Overview

With pipeline parallelism, each step's intermediate tensors go from one stage to the next over NCCL send / recv. On ROCm that peer copy runs as a blit kernel on the sender's CUs, so it slows whatever the sender computes next to it: an 8192^3 bf16 GEMM on the sender runs 5.1x slower while a 201 MiB tensor is copied to the next GPU (table below). In a TP1 x PP2 prefill of MiniMax-M3.1-Flash, a 16384-token step hands off several such tensors on both stages' compute path.

This PR adds an opt-in hand-off on SDMA copy engines, `--pp-sdma-handoff` (`ParallelConfig.pp_sdma_handoff`, off by default). It applies to PP2 x TP1 on gfx950 (MI355X), eager (`cudagraph_mode` NONE), both stages on one node; with the flag set and any of these unmet, the worker raises at init.
- The receiving stage allocates 3 slots and shares them with the sender over CUDA IPC.
- A sender thread waits for the step's event, then copies each tensor into the step's slot on two SDMA engines (no CUs).
- The stages sync slot reuse through two counters in `/dev/shm`: `ready` (sender) and `freed` (receiver, once the step that read the slot has run on its GPU). Shapes and non-tensor entries still go through the PP group's object send; those sends are reaped against `freed` (a gloo isend `Work` reports `is_completed()` False until `wait()`).

Eager only, because a CUDA graph replay reuses its output buffers while the copy may still read them. PP2 only, because a middle stage would relay tensors that alias its receive slots.

Why ROCr's `hsa_amd_memory_async_copy_on_engine` over ctypes rather than a HIP API: on HIP 7.16 (vLLM's ROCm image), `hipMemcpyBatchAsync` with `hipMemcpyFlagExtPreferCE` still runs device-to-device peer copies as a blit kernel (the flag only steers host <-> device batches), and `hipMemcpyAsync(kind=hipMemcpyDeviceToDeviceNoCU)` picks SDMA engines whose peer copy fails on MI355X (HSA status 4097), so the runtime skips the copy while returning `hipSuccess`. Explicit engines 2 and 4 work.

## Claims

- Sender compute next to the hand-off copy: +411% with torch's peer copy (what NCCL's path costs too), +1.4% with this PR's SDMA copy, at 64.5 GB/s instead of 59.3 GB/s.
- The receiver gets the tensors byte for byte, also when it reads a slot late while later steps refill the other slots.
- End to end, MiniMax-M3.1-Flash TP1 x PP2 prefill (16384-token steps): +3.6% throughput and -3.4% mean TTFT over NCCL, each of 4 alternated rounds between +3.0% and +3.9%; gsm8k unchanged.
- Off by default; without the flag nothing changes.

## Validation

MI355X, image `vllm/vllm-openai-rocm:nightly-40941f2c4ba96fba0a7e282a5355e89cd74d9ac5` (HIP 7.16.26361) with this PR's Python on top.

Copier cost, cuda:0 -> cuda:1, one 201 MiB bf16 tensor (16384 x 6144) copied in a loop while 8192^3 bf16 GEMMs run on the sender, then on the receiver:

| copier | GB/s | byte-exact | sender GEMM | receiver GEMM |
|---|---|---|---|---|
| torch peer copy (`y.copy_(x)`) | 59.3 | yes | +411% | +4.7% |
| `hipMemcpyBatchAsync`, 8 descriptors | 64.9 | yes | +257% | +0.7% |
| `hipMemcpyBatchAsync` + `hipMemcpyFlagExtPreferCE`, 8 descriptors | 65.0 | yes | +257% | +0.5% |
| `hipMemcpyAsync(kind=hipMemcpyDeviceToDeviceNoCU)` | - | no (copy skipped) | 0% | 0% |
| **this PR (`copy_on_engine`, engines 2 + 4)** | **64.5** | **yes** | **+1.4%** | **+0.6%** |

- `pytest tests/distributed/test_pp_sdma.py` on 2 GPUs: 4 passed (the PP2 hand-off over 8 steps through 3 slots with a late reader; the metadata-send reaping on CPU, with fakes and with real gloo isends).
- pre-commit clean on the changed files.

End to end: MiniMax-M3.1-Flash (MXFP4 experts), TP1 x PP2, `--enforce-eager`, `--max-num-batched-tokens 16384`, prefix caching off, NCCL vs `--pp-sdma-handoff` on the same 2 GPUs. Load: `vllm bench serve --dataset-name random --random-input-len 16384 --random-output-len 1 --ignore-eos --num-prompts 96 --max-concurrency 8` after a 16-prompt warm-up; 4 rounds, the side order flipped every round, a fresh server per side and round. Means over the rounds:

| metric | NCCL -> `--pp-sdma-handoff` |
|---|---|
| request throughput | 3.18 -> **3.29** req/s (+3.6%) |
| prefill throughput | 52.1K -> **53.9K** tok/s (+3.6%) |
| TTFT mean | 2427 -> **2345** ms (-3.4%) |
| TTFT median | 2451 -> **2361** ms (-3.7%) |
| TTFT p99 | 2892 -> **2787** ms (-3.7%) |

- Throughput gain per round: +3.8%, +3.5%, +3.0%, +3.9%; the NCCL side spans 3.175-3.183 req/s over its 4 rounds.
- gsm8k, first 200 test questions over chat completions (T 0): 193/200 with NCCL, 193/200 with `--pp-sdma-handoff`.
