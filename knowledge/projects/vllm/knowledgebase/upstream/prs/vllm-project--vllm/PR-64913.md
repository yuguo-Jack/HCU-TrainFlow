# [Docs][KV Connector] NIXL: pin --attention-backend for mixed GPU generations

[Upstream PR](https://github.com/vllm-project/vllm/pull/64913) · state: closed · merged: False

## Original PR description



## Overview

Document that a NIXL prefill/decode pair split across compute capability 10.x (B200/B300) and another CUDA GPU such as Hopper fails the handshake by default, and that pinning the same `--attention-backend` on both sides fixes it. Docs only.

## Claims

- With default settings, a compute capability 10.x instance and a Hopper instance auto-select different attention backends for non-MLA models (`FLASHINFER` vs `FLASH_ATTN`), and the handshake rejects every transfer with `NIXL compatibility hash mismatch`.
- Passing the same `--attention-backend` to both instances makes the pair work.
- The new section also notes that the hash includes the `model` argument as passed, so both instances need the same Hugging Face ID or local path.

## Validation

Setup: vLLM 0.31.0, Qwen3-8B BF16, TP 1, `--enforce-eager`, NixlConnector with UCX over TCP. One B300 host and one GH200 host. Each run sent 3 prompts twice (6 greedy requests). Each request ran as P/D and was also sent directly to the decode instance as a reference.

| Prefill → decode | Attention backends | Result |
|---|---|---|
| B300 → GH200 | defaults (B300 picks `FLASHINFER`, GH200 picks `FLASH_ATTN`) | decode logs `NIXL compatibility hash mismatch`; 6/6 requests return HTTP 500 |
| B300 → GH200 | `--attention-backend FLASHINFER` on both | 6/6 requests complete; for all 262 transferred blocks, decode-side per-layer KV checksums equal the prefill side's |
| GH200 → B300 | `--attention-backend FLASHINFER` on both | 6/6 complete, 262/262 blocks equal |

In the default run, the backend name was the only hash factor that differed: the passing runs changed nothing but `--attention-backend`. In the passing runs, greedy P/D outputs (48 tokens) matched the decode-only reference except where the reference's top-1/top-2 logprob margin at the first differing token was 0.0 or 0.125. Those are ties at bf16 resolution between two GPU generations, not transfer errors; the KV bytes were equal.

On current `main` the behavior is unchanged:
- `_get_backend_priorities` in `vllm/platforms/cuda.py` still puts `FLASHINFER` first for capability 10.x and `FLASH_ATTN` first otherwise (non-MLA).
- `compute_nixl_compatibility_hash` still hashes `attn_backend_name` and `model_config.model`.

The `model` note comes from reading the code; I did not run a mismatched-path case on GPUs. I also did not rerun the default-mismatch case on `main` itself; the code paths above are unchanged since 0.31.0.

Docs checks: `pre-commit run typos --files docs/features/nixl_connector_compatibility.md` and `pre-commit run markdownlint-cli2 --files docs/features/nixl_connector_compatibility.md` both pass.

## Details

- Flow: the decode instance receives a request with `kv_transfer_params`, its NIXL worker handshakes with the prefill side channel, and the compatibility hash is compared before the agent metadata is decoded. A mismatch raises `RuntimeError` and the request fails. The hash differs only because each instance auto-selects its backend for its own GPU.
- The new section goes under "KV cache layout" in `nixl_connector_compatibility.md`, next to the existing "What must match" list. That list already says "Attention backend", but it does not say that the default backend differs between GPU generations, so mixed-generation deployments hit the rejection without an obvious cause.
- Not a duplicate:
  - #60176 adds HMA-mismatch troubleshooting to the same file in a different section.
  - #60208 names the differing hash fields in the error message.
  - #64416 documents GH200 KV transfer integrity.
  - No open PR or issue covers mixed GPU generations.
- Size: the change is 13 lines of docs. It is not a tidy-up. It records a default-configuration failure for mixed-generation P/D, measured across real hosts, that the current docs do not explain.
- Whether the backend name should stay in the hash at all is a separate design question, raised by the RFC in #59111 (and affected by #62107, which adds a FlashInfer page-format flag to the hash).
