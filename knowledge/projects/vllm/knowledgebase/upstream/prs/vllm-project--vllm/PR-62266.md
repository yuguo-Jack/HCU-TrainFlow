# [Bugfix][Distributed] Register custom AR graph buffers only after a capture that did not raise

[Upstream PR](https://github.com/vllm-project/vllm/pull/62266) · state: open · merged: False

## Original PR description



## Overview

`CustomAllreduce.capture()` calls `register_graph_buffers()` in its `finally` block, so the call also runs while an exception from the capture propagates. `register_graph_buffers()` is a cross-rank collective (`dist.broadcast_object_list` on the CPU group). When one rank raises during CUDA graph capture (for example CUDA out of memory), the other ranks do not join this collective. The failing rank then waits until the gloo timeout (30 min by default) and does not report the original error. This PR registers the graph buffers only after a capture that did not raise.

## Claims

- An exception inside `CustomAllreduce.capture()` reaches the caller at once with its original message. Before this PR, it hung in the registration collective until the gloo timeout.
- A capture that succeeds is unchanged: it registers the graph buffers once at exit, as before.
- `_IS_CAPTURING` is reset on every exit path, as before.

## Validation

**CPU reproduction** (2 processes, gloo CPU group with a 20 s timeout, the real `CustomAllreduce.capture()` with `register_graph_buffers` replaced by the same broadcast loop without the CUDA IPC calls). Rank 0 raises inside `capture()`. Rank 1 waits in another collective, as a rank does when it waits for rank 0 in a GPU collective.

| Code | Rank 0 result |
|---|---|
| `main` (5be4266f5) | `RuntimeError: ... Timed out waiting ...` (gloo) after 20.0 s; the original error is lost |
| this PR | `RuntimeError: simulated CUDA OOM during graph capture` after 0.0 s |

**Unit test** `tests/distributed/test_custom_all_reduce.py::test_capture_registers_graph_buffers_only_after_success` (CPU only): fails on `main` (`assert registrations == []`), passes with this PR.

**Field observation** (8× A100-40GB, TP8, a serving build on vLLM 5555a2d8f): rank 0 raised `CUDA error: out of memory` in a CUDA graph capture with 40,441 of 40,960 MiB in use. The engine did not exit; the ranks stayed in the custom all-reduce capture exit until the 1800 s gloo timeout.

**GPU reproduction** (2x A100-SXM4-40GB, NVLink, driver 570.124.06, custom all-reduce on). `torch.distributed.run` with 2 ranks; rank 0 raises inside `graph_capture()` while rank 1 waits in a collective of the same capture; 90 s limit per run:

| Code | Rank 0 result |
|---|---|
| vLLM 5555a2d8f (same `capture()` as `main`) | still inside `graph_capture()` after 90 s (hang) |
| 5555a2d8f + this PR's `custom_all_reduce.py` | `RuntimeError: simulated CUDA OOM during graph capture` after 0.0 s |

## Details

**Root cause.** `capture()` is a `@contextmanager`:

```python
try:
    self._IS_CAPTURING = True
    yield
finally:
    self._IS_CAPTURING = False
    if not self.disabled:
        self.register_graph_buffers()
```

`register_graph_buffers()` does one `dist.broadcast_object_list` per rank on the CPU group. When the body raises on one rank only, the other ranks are usually blocked in a GPU collective of the same capture (or they have left the capture already). Thus the broadcast on the failing rank never completes, and the exception never reaches the caller.

**Fix.** Keep the `_IS_CAPTURING` reset in `finally`, and call `register_graph_buffers()` after the `try` block. When the body raises, the generator exits before the registration.

**Limitation.** After a failed capture, the C++ `graph_unreg_buffers_` list keeps the addresses that the failed capture recorded; only `register_graph_buffers()` clears it. This matters only if a caller catches the capture exception and captures again in the same process. No caller in vLLM does this: the MRV1 and MRV2 capture paths use `try/finally` without `except`, so the error ends the engine start. #46515 (open) adds a call that also clears this list when captured graphs are discarded.
