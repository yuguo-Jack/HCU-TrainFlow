# [Bugfix] Do not discard model output when tool_choice defaults to "none" with no tools declared

[Upstream PR](https://github.com/vllm-project/vllm/pull/49409) · state: open · merged: False

## Original PR description

FIX #49254

## Purpose

When a chat request declares **no tools**, the protocol defaults `tool_choice` to `"none"`. Since #45413, engine-based parsers handle that branch by running the full tool-parsing pipeline and then stripping the parsed tool calls (`delta_message.tool_calls = []` in `DelegatingParser._extract_tool_calls_streaming`). If the model emits tool-call syntax anyway — common for agentic-tuned models given tool-heavy context — its entire output is parsed into tool calls and then discarded: the client receives an empty response (`finish_reason: "stop"`, every chunk `"delta": {}`), with the generated tokens visible only in `logprobs`. That is exactly the symptom reported in #49254.

This is not model-specific: replaying the same shape through all ten engine-based parsers (gemma4, qwen3, seed_oss, glm4.7, kimi_k2, deepseek v3.2/v4, minimax_m2, nemotron_v3, inkling) loses the response identically. Gemma-4 became exposed when it was converted to the engine implementation in #45588.

## Fix

Gate the strip on the request actually declaring tools:

- **Tools declared + `tool_choice="none"`** (explicit opt-out): unchanged — run the pipeline, strip tool calls silently. This keeps the existing tested contract (`test_delegating_parse_tool_choice_none`, `assert_no_terminal_leakage`).
- **No tools declared** (defaulted `"none"`): run the same pipeline under the engine's existing `skip_tool_parsing` mode — reasoning is still extracted into the `reasoning` field, and tool syntax streams through incrementally as `content`. This matches what legacy (non-engine) parsers already do on this exact branch (`DeltaMessage(content=delta_text)` passthrough), so engine and non-engine parsers now behave consistently.

`skip_tool_parsing` is used rather than raw passthrough because parsers like gemma4 extract reasoning inside the same unified engine; raw passthrough would leak `<|channel>thought` markers into content.

Also fixes the test trace builder deriving request tools via truthiness (`if scenario.tool_calls`), which silently gave the `empty-tool-block` samples (`tool_calls=[]`) no-tools requests — those samples now declare a tool, matching their intent of exercising a tool-calling context.

## Why this is not duplicating an existing PR

No open PR references #49254. The two adjacent open PRs repair *different* branches of the same `tool_choice` plumbing and do not touch the `"none"` strip:

- #49228 fixes the `required`/named tool-choice streaming crash (#49216).
- #49346 fixes request *validation* (`protocol.py`) to accept `tools: []`. Verified compatible: this PR's gate uses truthiness, so the newly-legal `tools: []` correctly behaves like tools-absent (passthrough).

## Root cause commits

- `c4a3f9d13` (#45413) introduced the engine-based strip branch; before it, `tool_choice="none"` always returned `delta_text` as content.
- `76a373eff` (#45588) converted Gemma-4 to the engine implementation, exposing it to the branch (this is why the reporter observed it "worked before").

## Model evaluation (end-to-end on real hardware)

Served `nvidia/Gemma-4-26B-A4B-NVFP4` on an NVIDIA GB10 (`--tool-call-parser gemma4 --reasoning-parser gemma4 --enable-auto-tool-choice`) and ran the reporter's exact `replay_script.py` from #49254:

- **Before:** 3/3 runs returned a completely empty stream (only `"delta": {}` chunks; text visible in logprobs only) — exact reproduction of the issue, including `prompt_tokens: 17964`.
- **After:** 3/3 runs return the model's output as content, e.g. `<|tool_call>call:bash{command:<|"|>python3 -m analyzer ...<|"|>}<tool_call|>`.
- Semantics matrix on the live server, all correct: tools+`auto` → proper `get_weather` tool call; tools+explicit `"none"` → suppressed (unchanged); no tools → normal prose content.

## Notes for reviewers

- In the no-tools path, clients now see the model's raw tool syntax (special tokens included) as content — the same behavior legacy parsers have always had on this branch, and what the reporter's benchmark consumes. If a cleaner rendering is preferred, that's a follow-up policy decision.
- The explicit-opt-out case (tools declared + `"none"`) still silently strips a disobedient tool call, preserving the existing tested contract; whether that residual case should surface text somewhere is left to maintainers.

- bbrowning · comment · 2026-07-22T12:28:46Z · [source](https://github.com/vllm-project/vllm/pull/49409#issuecomment-5045767711)

The behavior today is if `tool_choice="none"` and the model generates a tool call, we discard it. The model should not generate a tool call to begin with when `tool_choice="none"` (because it will have no tools visible in its system/developer prompt), but some misbehaving models may get this wrong.

Your proposed fix would that instead of discarding it, we return that to the user. But, from the agent or user's point-of-view, won't that look exactly like we just leaked a tool call? And, it will leak special tokens into the response shown to the user. If we strip special tokens from the response, it will now look like partially garbled content shown to the user.

The user / agent explicitly said they did not want any tool calls by either omitting tools entirely or setting `tool_choice="none"` on the request. Why is the right thing to leak a tool call back as content as opposed to swallowing any generated tool calls and returning only the non-tool-call content the model output? Reasonable models should not be generating tool calls when they are given no tools.

In #49254, it's not a live agentic session but instead a synthetic replay test that is setup incorrectly, as it's showing multi-turn tool calls in a conversation but there are no `tools` passed in to the request at all. Basically, the test is setting the model up for failure here by creating fake tool call turns when the model normally would have never made any for a conversation without tools at all.

- freedomljc · comment · 2026-07-22T15:28:13Z · [source](https://github.com/vllm-project/vllm/pull/49409#issuecomment-5048100652)

Agreed on the fixture — it's malformed, and with `tools` declared in the request everything parses correctly end-to-end (verified against Gemma-4-26B-A4B-NVFP4). No objection to #49254 being resolved as a test-setup error on the reporter's side.

I'd still ask for a design ruling on this branch, though, because vLLM currently ships **both** behaviors for this exact situation, selected by parser implementation rather than by anything in the request:

```
# identical request: no tools declared, model emits only a tool call
hermes (legacy branch) → content = '<tool_call>\n{"name": "get_weather", ...}\n</tool_call>'
gemma4 (engine branch) → content = ''   (empty message, finish_reason "stop")
```

The non-engine arm of the same `tool_choice == "none"` branch (`abstract_parser.py:715`) has always passed the text through — so the "leaked tool call" concern describes what 28 of the 40 registered tool parsers already do today. Two side effects of the split:

- `deepseek_v3`/`v31` are legacy, `v32`/`v4` are engine: upgrading a checkpoint one generation flips the behavior for identical requests.
- `_engine_based` requires *both* parsers to be engine-based, so `--tool-call-parser qwen3_coder` passes through when paired with `--reasoning-parser deepseek_r1` but swallows when paired with `--reasoning-parser qwen3`.

Whichever direction is intended, I'm happy to implement it consistently:

1. **Passthrough is intended** → this PR as filed (aligns engine parsers with legacy behavior).
2. **Swallowing is intended** → I'll rework this PR to strip in the legacy arm as well. In that case I'd want to pair it with a guard so a fully-swallowed response doesn't come back as a bare empty message — that's the part of #49254 that still seems genuinely wrong to me: the client can't distinguish "model generated nothing" from "server discarded 400 tokens," and it triggers outside synthetic tests whenever a framework sends follow-up turns without re-declaring `tools`.
3. **Middle ground** → keep swallowing exactly as today, but when stripping would leave the *entire* response empty, return the model's text instead. Mixed content+tool responses keep the clean-content contract; only the all-tool-syntax case changes, from "empty" to "visible." This version passes the full parser suite with no test-expectation changes.

Which of these would you take?


- skyloevil · comment · 2026-07-22T17:08:42Z · [source](https://github.com/vllm-project/vllm/pull/49409#issuecomment-5049148471)

I agree that the replay fixture in #49254 is malformed and should be fixed separately. That said, this PR also exposes a real inconsistency: the same no-tools request can either pass through or swallow tool syntax depending on whether the parser is legacy or engine-based.
I’d lean toward option 2: suppress tool calls consistently rather than exposing raw control tokens as content. If suppression removes the entire generation, we should at least log and count that event so it isn’t indistinguishable from the model generating nothing.
Longer term, parsers with a dedicated tool-start token could block that token during decoding when no tools are available, avoiding both leaked syntax and empty responses.
