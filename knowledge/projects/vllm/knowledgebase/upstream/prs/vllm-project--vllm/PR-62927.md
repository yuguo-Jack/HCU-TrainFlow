# [ROCm][BugFix] Sanitize HIP-graph padding rows before AITER fused MoE call

[Upstream PR](https://github.com/vllm-project/vllm/pull/62927) · state: closed · merged: False

## Original PR description

## Purpose

`tests/kernels/moe/test_modular_kernel_combinations.py::test_aiter_moe_token_padding_garbage_rows[single_nan-fp8_tensor_tensor]` failed once in CI (https://buildkite.com/vllm/amd-ci/builds/15028) with:

```
AssertionError: AiterExperts output magnitude (mean |mk_out|=0.000000) looks
degenerate/zeroed vs. reference (mean |ref_out|=0.005310).
```

Every rerun since (including on the exact same commit/hardware) has passed, so this is an intermittent failure, not a deterministic one.

## Suspected mechanism (not experimentally confirmed -- see below)

AITER's CK 2-stage MoE kernels (`fused_moe_2stages` in `aiter/fused_moe.py`) allocate the post-stage1 intermediate activation buffer uninitialized (`a2 = torch.empty((token_num, topk, inter_dim), ...)`), and compute a single, batch-wide dynamic per-tensor activation scale over the whole buffer with no way to exclude any row (`per_tensor_quant_hip` asserts `num_rows is None`).

A token whose every topk slot is masked to `-1` -- vLLM's HIP-graph padding-token contract in `grouped_topk_router.py` (`topk_ids = topk_ids.masked_fill(is_padding, -1)`) -- never enters AITER's sorted token list, so its slice of that buffer is never written by stage1 and keeps whatever bits were already in that GPU memory. If that uninitialized slice happens to hold a large-magnitude value, the resulting shared scale inflates and every other (real) token's legitimate, small-magnitude activation gets crushed to exactly zero on fp8 quantization -- which matches the observed failure signature.

This is a plausible trigger of the same general bug class as https://github.com/ROCm/aiter/issues/6275 (a real `inf` value in an unrouted row poisoning a dynamic *input*-side scale) and https://github.com/ROCm/aiter/issues/6565 (uninitialized scratch buffers on the a8w4/gfx950 path, with a validated before/after fix). An AITER-side fix for this general `a2` buffer (https://github.com/ROCm/aiter/pull/6568, `torch.empty` -> `torch.zeros`) was proposed but closed by the AITER team as "not an appropriate solution... it introduces additional overhead due to zero padding"; the suggested alternative (https://github.com/vllm-project/vllm/pull/61816) only stops declaring `intermediate_pad` on the MXFP4 path, which does not apply to this `fp8_tensor_tensor` (non-MXFP4) case (this test's shapes already have `intermediate_pad=0`) and does not address the row-level exclusion mechanism described here.

**I was not able to experimentally confirm this mechanism is the cause of the one observed failure.** I tried to force it by deliberately priming the GPU allocator with large-magnitude values immediately before the AITER call (several tensor shapes, both a naive and a more thorough multi-size attempt), in an isolated single-trial-per-process script matching the real test's structure (one MoE call per freshly spawned subprocess, via the existing `parallel_launch_with_config` harness). This did not reproduce the failure, either with or without this patch (0/15 trials each). My best explanation is that the real trigger needs GPU memory contention from other, concurrent processes sharing the same physical GPU (plausible on a CI fleet running multiple shards per host), which a single-tenant sandbox can't reproduce. An earlier, methodologically flawed attempt (looping 20 iterations inside one process) appeared to show a difference between pre/post-fix, but that setup lets one iteration's tensors leak into the next iteration's allocator state in a way the real test never does, so I'm not relying on it.

What *is* directly confirmed by reading the code (not reproduced dynamically): `a2`'s `torch.empty` allocation, the sorting kernel's exclusion of `topk_ids=-1` tokens from `sorted_ids`, `per_tensor_quant_hip`'s unmaskable reduction, and `grouped_topk_router.py`'s real `topk_ids=-1` padding contract. All four are real, verified facts about the current code; only the end-to-end causal chain to this specific CI failure remains unproven.

## This change

Fix the underlying defect pattern entirely on vLLM's side, with no dependency on an AITER change: in `rocm_aiter_fused_experts`, detect tokens whose every topk slot is `-1` (padding) and, before calling into AITER:
- remap their `topk_ids` to a real, locally-owned expert id (so AITER's sort step actually includes the row and stage1 writes something for it), and
- zero their `hidden_states` (so what gets written is finite and harmless to the shared scale, rather than relying on a weight-of-zero that is only applied *after* the scale is computed).

This is scoped to the shared `rocm_aiter_fused_experts` entry point, so it covers all callers (`AiterExperts.apply()`, `quark_moe.py`, `deepseek_v4/amd/model.py`) uniformly. The added cost is a row-reduction and two `torch.where` calls over `hidden_states`/`topk_ids` only (not the larger post-stage1 intermediate buffer), and it is a no-op for the common case where no row is padding. Given the unproven causal chain above, this should be read as closing a real, confirmed defect pattern (an unmasked reduction over a buffer that can contain unwritten rows) rather than as a proven fix for the one observed CI flake.

## Why this isn't a duplicate

- `ROCm/aiter#6568` (AITER-side `a2` zero-init) was closed by the AITER team as not appropriate.
- `vllm-project/vllm#61816` fixes a different, MXFP4-only manifestation (dropping `intermediate_pad`); it does not touch the general `fused_moe_2stages` path or this `fp8_tensor_tensor` quant scheme, and this test's shapes already have `intermediate_pad=0`, so that PR has nothing to change for this case.
- No other open or recently-merged vLLM PR addresses `test_aiter_moe_token_padding_garbage_rows` or this failure signature (checked via `gh pr list`/`gh issue list` search).

## Test Result

- `test_aiter_moe_token_padding_garbage_rows` (all 15 param combos): 13 passed, 2 skipped (the 2 skips are the pre-existing, unrelated `ROCm/aiter#6275` inf/dynamic-scale skip) -- 0 failed.
- The previously-flaky `[single_nan-fp8_tensor_tensor]` case specifically: 9/9 passes across repeated runs -- but see the mechanism section above, this is not a forced reproduction and the original failure was never reliably forced to occur either before or after this patch.
- Broader `-k "aiter and not multigpu"` sweep of the same test file: 44 passed, 6 skipped (all 6 pre-existing, hardware/scheme-gated), 0 failed -- no regressions in sorting-backend dispatch, dispatch-policy forwarding, or the padding-matrix tests.

This is a correctness/robustness fix for MoE padding-token handling, not a change to any model's real-token output (padding-token output is always discarded by the router's own masking), so no model-accuracy evaluation applies.

- AndreasKaratzas · comment · 2026-10-25T03:52:49Z · [source](https://github.com/vllm-project/vllm/pull/62927#issuecomment-6393151034)

We looked into `test_aiter_moe_token_padding_garbage_rows` on MI300 (amd-ci [15340](https://buildkite.com/vllm/amd-ci/builds/15340), shards 1 and 5) and tried this PR against it. It does not fix the failure, and the root cause is inside AITER rather than in how vLLM routes padding rows.

**Root cause.** `fused_moe_2stages` allocates the second-stage activation with `a2 = torch.empty((token_num, topk, inter_dim))`, and stage 1 writes only the (token, k) slots that its sort keeps. For per-tensor fp8 with no static `a2_scale`, the next step is `dynamic_per_tensor_quant` over the whole buffer, so whatever stale memory sits in the unwritten slots sets the shared scale: a large finite value rounds every real row to fp8 zero (the CI signature, `mean|mk_out| = 0`), `inf` gives NaN. Per-token and block quant are unaffected because they scale row by row.

**Why this PR doesn't help.** Sending every all-`-1` padding row to one sentinel expert in all `topk` slots still leaves a slot unwritten, because AITER's sort keeps a single entry per (token, expert). With this PR applied, the unwritten slots are `[[1,0],[4,0],[7,0],[12,0]]` for garbage rows {1, 4, 7, 12}, and with allocator poisoning both failing params still give `mean|mk_out| = 0` in 5/5 runs each (MI350X, AITER v0.1.26). Separately, `sentinel_expert_id = (expert_mask >= 0).argmax()` is always 0, since `expert_mask` holds only 0s and 1s, so under EP it picks a non-local expert on every rank but 0.

**Fix.** Zero-initializing `a2` only on that path (`quant_type == QuantType.per_Tensor and a2_scale is None`) makes both params correct in 5/5 runs under the same poisoning (e.g. `mk 0.005483` vs `ref 0.005480`); we are opening it against AITER and will bump `AITER_BRANCH` once it lands. Until then we plan a ROCm-only test guard for those params referencing the AITER fix.
