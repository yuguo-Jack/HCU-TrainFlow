# [Bugfix][Spec Decode] Align MRV2 lm_head LoRA with logits rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/59341) · state: open · merged: False

## Original PR description

## Purpose

Fixes #59161.

Model Runner V2 built the lm_head LoRA mapping with one id per request. Under speculative decoding each request owns one bonus row plus one row per draft token (`cu_num_logits`), so an lm_head adapter missed its own request or landed on a neighbor. `make_lora_inputs` now repeats each request id by `np.diff(cu_num_logits_np)`.

Adaptive verification and MRV2 PCP both reject LoRA at startup, so those counts do not need a later refresh. With LoRA on, `cu_num_logits_np` is exact.

## Test Plan

PYTHONPATH=. python -m pytest tests/v1/worker/test_mrv2_lmhead_lora.py -v --tb=short

## Test Result

- 2 passed (CPU): the prompt mapping matches `cu_num_logits` (bonus + draft rows), a mixed batch does not leak an adapter id onto a neighbor, and two sampled-token rows per request are repeated.

- BeichenHuang · CHANGES_REQUESTED · 2026-10-18T02:02:33Z · [source](https://github.com/vllm-project/vllm/pull/59341#pullrequestreview-5561039110)

The fix is correct. I reproduced #59161 on H20 and this PR fixes it.

I used a rank-1 `lm_head` LoRA that pushes every even token id down by ≥30 nats, so a correctly applied adapter can never emit one. On MRV2 with spec decode (Qwen3-8B + ngram, Qwen3.5-4B-Base + MTP), main emits 1–59/128 even tokens per LoRA request. In batch-invariant mode, no-LoRA requests next to LoRA requests also change on main. With this PR: 0 even tokens, and spec on/off and solo/mixed outputs are identical.

One request: could this be cut down to the 3-line version from the issue? Adaptive verification (`vllm/config/vllm.py`, "not currently compatible with LoRA") and MRV2 PCP (`pcp_manager.py`, "does not support LoRA yet") both reject LoRA at startup. That makes the two `num_logits_per_req` refresh blocks and the `pcp_manager.py` change unreachable. Whenever LoRA is on, `cu_num_logits_np` is exact. (If those paths ever do become reachable, the unguarded `cu_num_logits.cpu()` would trip `VLLM_GPU_SYNC_CHECK`.) I ran the minimal version below through the same e2e test and the results match.
