# [Perf][HiSparse] Avoid repeated prefix scans; drive residency from the connector

[Upstream PR](https://github.com/vllm-project/vllm/pull/58965) · state: closed · merged: False

## Original PR description

Alternative to #57930, following the review thread at https://github.com/vllm-project/vllm/pull/57930#discussion_r4068549511. It keeps @S1ro1's prefix-scan cursor fix and folds in the restructure from S1ro1/vllm#9. That restructure removes the `resident_managers[0]` identity check that @NickLucche flagged: per-step residency work now runs in HiSparse-specific code, not in `HiSparseResidentManager.cache_blocks`.

### Changes

1. **Prefix-scan cursor** (from #57930, authored by @S1ro1, unchanged): `plan_prefix_materialization` now starts scanning at `max(ready_prefix_pages, importing_pages)`, so it no longer rescans pages it already knows are durable.
2. **Residency driven from the connector** (from S1ro1/vllm#9):
   - Removes the `HiSparseResidentManager.cache_blocks` override. Previously every resident group ran the shared `plan_prefix_materialization` and `update_residency` calls; #57930 limited this to one run per step with the identity check.
   - Adds `HiSparseCoordinator.advance_scheduled`. `HiSparseConnectorScheduler.build_connector_meta` already runs once per step and iterates every scheduled request. It now calls `advance_scheduled` just before `build_offload_command`, using the same finalized-token cap that `allocate_slots` used (`min(computed + scheduled, request.num_tokens)`). Spills planned in a step therefore still ship in that step.

### Behavior difference

`update_residency` has two side effects that used to run during scheduling and now run after it:
- releasing pinned-clean pages when a request acquires its hot region
- the low-pool watermark check that requests a hot region

For the rest of that scheduling pass, both now take effect one step later. Pages that become clean after a spill are unaffected, because they are released in `update_connector_output`, before scheduling. The net effect is a one-step delay at the transition, not a lost release.

Moving the calls into `HiSparseSourceManager.cache_blocks` was also tried, and it does not work. `allocate_slots` calls the coordinator's `cache_blocks` unconditionally, but the per-group loop skips managers with `enable_caching=False`. So with prefix caching off, the host manager never runs.

### Performance

See #57930 for @S1ro1's end-to-end B300 P/D measurements of the cursor + single-invocation fix. In their CPU microbenchmark (20 resident groups, 512 durable pages), request cache-update bookkeeping dropped from 512.01 to 6.63 µs/request. This PR keeps the single-invocation property: residency work runs once per scheduled request per step, regardless of how many resident groups there are. The end-to-end run has **not** been repeated on this revision.

### Tests

The HiSparse tests in `test_prefix_caching.py` expected residency work to happen inside `allocate_slots`. They now go through a small `_allocate_scheduled` helper that calls `allocate_slots` and then `advance_scheduled` with the same cap. The test diff is mostly this mechanical change.
