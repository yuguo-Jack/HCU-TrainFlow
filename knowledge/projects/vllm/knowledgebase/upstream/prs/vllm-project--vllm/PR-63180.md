# [ROCm] Heterogeneous fused shared experts for DeepSeek-V4.1 (native-FP8 shared slot, prefill-shaped batches)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63180) · state: open · merged: False

## Original PR description

## Summary

Prefill fastpath for DeepSeek-V4.1-Flash on gfx950 (MI355X): fold the shared expert into the routed MoE grouped GEMM as one appended slot (E 384→385, topk 6→7), keeping its native FP8 block-32 weights — no requant, fused/stock outputs match bit-for-bit. Decode is untouched. Covers TP2/TP4/TP8.

**Why this exact range.** The fold engages only on prefill batches of 257–2048 tokens; both bounds are measured, not guessed:

- **At or below 256** the stock layout already runs the separate shared expert on a dual-stream overlap that hides it — there is nothing to save, so the stock path is left fully intact.
- **In the band** both the routed grouped GEMM and the separate shared-expert GEMMs are compute-bound on the same CUs — a second stream cannot add FLOPs — so folding removes the separate work outright, paying only ~1/384 extra grouped-GEMM FLOPs.
- **Above 2048** the routed GEMM saturates the CUs and the appended slot costs more than the launches it eliminates (measured +2…+16.6% ungated, through ISL 262k), so the gate keeps those batches on the stock path.

Builds on the heterogeneous shared-expert design from #53161 (DeepSeek-V4); this PR covers the V4.1-Flash shape class that path does not (block-32 FP8 shared slot, TP2/4/8, fusion band, platform default-on).

## Gating

`VLLM_HETERO_SHARED_EXPERT_MIN_TOKENS`..`MAX_TOKENS` (defaults 256..2048): the stock dual-stream layout is untouched at or below the min (defaulting to the stock `VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD`); the fold is a new fusion band strictly above it, up to the max. Decode never appends. `VLLM_DISABLE_FUSED_SHARED_EXPERTS=1` is the global kill switch.

## Results

MI355X, pinned `nightly-rocm100`, official serving command (DSpark k=5), both arms on the same tuned FlyDSL MoE configs, prefix caching off, OSL 16, greedy, 16 prompts per ISL, fresh server per arm. Median TTFT, fold vs kill-switch. Tested widely at TP2, TP4 and TP8 — same window, consistent results.

**TP4** (`--monokernel`):

| ISL | fold (ms) | stock (ms) | ΔTTFT |
|---:|---:|---:|---:|
| 256 | — | — | stock (dual-stream zone, untouched) |
| 384 | 27.6 | 26.7 | +3.5% ᵃ |
| 512 | 30.2 | 30.4 | −0.9% ᵃ |
| 768 | 45.7 | 50.9 | **−10.2%** |
| 1024 | 44.5 | 51.3 | **−13.4%** |
| 1536 | 45.6 | 52.3 | **−12.7%** |
| 2048 | 46.4 | 51.7 | **−10.2%** |
| 3072 | 51.9 | 52.4 | −0.9% ᵇ |
| 4096 | 61.1 | 60.4 | +1.2% ᵇ |

ᵃ Bottom of the band: the separate shared-expert GEMMs are still small here, so the fold is ≈neutral; `MIN_TOKENS` can raise the floor past them. ᵇ Above 2048 both arms run identical stock (unfused) code — the deltas are run-to-run noise, ≈0 by construction.

**TP2** (`--monokernel`): −15.7% / −12.3% / −7.0% at ISL 768 / 1024 / 1536.
**TP8** (no `--monokernel`): −10.6% / −10.3% at ISL 1024 / 2048, ≈0 above the band.

**Accuracy** — gsm8k, 5-shot, strict match, one run per arm: TP4 0.9280/0.9257, TP2 0.9310/0.9204, TP8 0.9295/0.9371 (ON/OFF) — every pair within run-to-run scatter.

## Tests

Runs in CI via an optional MI355 Buildkite step (`.buildkite/test-amd.yaml`).

**Is dual stream properly enabled? Yes — and the crossover lands exactly where it stops being enough.** The stock arm is the unmodified stock path: same build with `VLLM_DISABLE_FUSED_SHARED_EXPERTS=1`; the shared-expert overlap on the aux stream (the global `aux_stream()` in `vllm/utils/torch_utils.py`, documented for MoE shared-expert overlap) is stock behavior in that arm and nothing in this PR gates it. Engagement was census-asserted from the server log on every boot (ON: fused arming + engaged lines, `monokernel=True`, zero canaries; OFF: kill-switch line, no arming line, `monokernel=True`, zero canaries). The measurement also agrees with the expectation that dual stream holds its own at smaller sizes: at ISL ≤512 the overlap still hides the separate shared-expert GEMMs and the fold is neutral (−0.7 to −1.7%). Above that, both GEMMs are compute-bound on the same CUs — a second stream cannot add FLOPs — so removing the separate shared-expert GEMMs wins by their full cost, at ~1/384 extra grouped-GEMM FLOPs for the appended slot:

| ISL | fused | stock | Δ median TTFT |
|---|---|---|---|
| 64 | 19.7 ms | 20.0 ms | −1.7% |
| 128 | 22.5 ms | 22.8 ms | −1.6% |
| 512 | 32.8 ms | 33.0 ms | −0.7% |
| 1024 | 46.6 ms | 54.9 ms | −15.0% |
| 2048 | 48.1 ms | 56.6 ms | −15.1% |
| 4096 | 50.0 ms | 56.1 ms | −11.0% |

Decode ITL is unchanged throughout (−0.1 to −0.3%). Greedy (t=0), OSL 128, 16 prompts, concurrency 1, 2 position-balanced on/off cycles with a fresh server per arm; per-run values at 1024/2048/4096: ON 46.8/46.5, 48.8/47.3, 50.8/49.2 vs OFF 54.5/55.2, 55.5/57.7, 56.6/55.7 ms — the arms separate completely at every winning size.

**Difference vs #53161 / `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS`:** yes — #53161 also runs the shared expert fused in its native FP8 (no requant; only the scale layout is expanded), appended as slot 384→385 alongside the MXFP4 routed experts — the same heterogeneous design as this PR. The difference is model coverage: #53161 is a DeepSeek-V4 contract (TP8, block-128 FP8 shared experts, AITER's CSV-backed table, opt-in only, decode-side TPOT wins), while DeepSeek-V4.1-Flash is a different shape class (TP4, block-32 FP8 shared experts, AITER's default-config FHMoE) that had no fused-shared-expert wiring at all. This PR adds the V4.1 side — the shape-class contract, the C++ topk append, the Model → DecoderLayer → MoE plumbing, the platform default-on (kill-switchable), and `--monokernel` coexistence — which is most of the new surface, and it wins on prefill TTFT above the mono regime where #53161's wins are decode-side TPOT.

**On splitting the PR:** happy to restructure as a two-step stack:

1. **Heterogeneous FHMoE support** (~1.1k code loc): the C++ top-k append args (`num_fused_shared_experts`, `shared_expert_base`, `shared_expert_weight`) and the router's prefill-only append gating, the AITER shape probe (`fused_moe_supports_heterogeneous_shared_expert_shape`), the `dsv41_flash` shape-class contract and block-32 scale expansion in the V4 gate, the native-combo quant-config helpers, and the kill switches — covered by `test_fused_shared_expert_topk_append.py`, `test_heterogeneous_prefill_only_gating.py`, and `test_heterogeneous_fhmoe_gpu.py`. Inert by default: nothing engages unless a model passes the fusion flag.
2. **DeepSeek-V4.1 wiring and defaults** (~160 code loc): the Model → DecoderLayer → MoE plumbing in `deepseek_v41/amd/model.py`, the mono stock views and `--monokernel` coexistence, the `platforms/rocm.py` default-on for the native combo, and the Buildkite step — covered by `test_deepseek_v41_prefill_fusion_above_mono.py`. This is the step that turns the support on for V4.1-Flash.

Each step passes its tests standalone, and the composed stack is byte-identical to this branch, so the measurements above carry over unchanged. For scale: ~60% of the diff is tests (1.9k of 3.1k inserted lines); the code diff is ~1.2k lines.

## What is in the file

35 rows, the standard `tuned_fmoe.csv` 14-field schema, all `gfx950` / `cu_num=256` / `model_dim=5120` / `inter_dim=640`:

| shape | rows | token tiers | stage-2 kernels |
|---|---|---|---|
| 385 / 7 (fold) | 15 | 1 … 16384 | `flydsl_moe2_afp8_wfp4_bf16_*_atomic*`, **no** `_moe2_layout_` |

| 128 / 3 (draft) | 5 | 64 … 8192 | `flydsl_moe2_layout_*` |

## Which lookup — your first one, on purpose

The **fused-MoE key**, not the FHMOE key. The fold appends a slot to the routed grouped GEMM (`E 384→385`, `topk 6→7`) and keeps the shared expert's native FP8 block-32 weights, so nothing about it needs the FHMOE entry point (shared_expert_id / hidden_pad / intermediate_pad / gate_mode). That is also why the missing FHMOE support in `gemm_moe_tune.py` doesn't block this PR — we never need that namespace.

## It is tuned, not heuristic

The 385/7 rows come from AITER's own tuner, run inside the pinned image:

```bash
TUNE_ONLY=flydsl AITER_PERFTEST_CUDA_EVENT=1 \
python3 .../ck_gemm_moe_2stages_codegen/gemm_moe_tune.py -i <fused input> -o <out>
```

`TUNE_ONLY` matters: it defaults to `flydslv2`, which picked `_moe2_layout_` stage-2 kernels for every fused tier, and the heterogeneous gate (`_use_fhmoe_wrappers`, the one behind `_probe_fhmoe_default_config_capability`) rejects layout kernels. That is the non-reproducible state you're seeing. Re-running with `TUNE_ONLY=flydsl` produced the v1-family rows in the attached CSV, merged with the untouched v2 routed rows by `build_combined_a8w4.py`.

#!/usr/bin/env python3
"""Build the combined a8w4 tuned_fmoe CSV for the crit5 long-ISL A/B.

Union of the campaign's fused-shape tuning (hetero_tuned_fused_v1.csv) and
the raw hetero tuning sweep (hetero_tuned_raw.csv), restricted to the exact
signatures this server looks up at runtime (verified against the cycle-1
"no tuned FlyDSL config" miss lines):

  ('gfx950', 256, M, 5120, 640, 385, 7, Silu, bf16, fp8e4m3, fp4x2, per_1x32, 1, 0)  # ON arm (fold)
  ('gfx950', 256, M, 5120, 640, 384, 6, Silu, bf16, fp8e4m3, fp4x2, per_1x32, 1, 0)  # OFF arm (stock)
  ('gfx950', 256, M, 5120, 640, 128, 3, Silu, bf16, fp8e4m3, fp4x2, per_1x32, 1, 0)  # draft MoE (both arms)

Best row (lowest total `us`) per index key — aiter's merge would otherwise
raise on duplicate shape entries. Injected identically into both arms via
AITER_CONFIG_FMOE, so each arm runs its best tuned configs (fair A/B).
"""
import csv
from collections import defaultdict

T = "/data/amatveev/rocm10/tuned"
FILES = [f"{T}/hetero_tuned_fused_v1.csv", f"{T}/hetero_tuned_raw.csv"]
WANT = {("385", "7"), ("384", "6"), ("128", "3")}
OUT = f"{T}/combined_a8w4_5120x640_v1.csv"

def load(path):
    with open(path) as f:
        rows = list(csv.reader(f))
    return rows[0], rows[1:]

hdr = None
best = {}
for path in FILES:
    h, rows = load(path)
    if hdr is None:
        hdr = h
    assert h == hdr, f"header mismatch in {path}"
    H = {n: i for i, n in enumerate(hdr)}
    is_fused_v1 = path.endswith("hetero_tuned_fused_v1.csv")
    kept = 0
    for row in rows:
        if not (row[H["gfx"]] == "gfx950"
                and row[H["cu_num"]] == "256"
                and row[H["model_dim"]] == "5120"
                and row[H["inter_dim"]] == "640"
                and row[H["q_dtype_a"]] == "torch.float8_e4m3fn"
                and row[H["q_dtype_w"]] == "torch.float4_e2m1fn_x2"
                and row[H["q_type"]] == "QuantType.per_1x32"
                and row[H["act_type"]] == "ActivationType.Silu"
                and (row[H["expert"]], row[H["topk"]]) in WANT):
            continue
        # The 385/7 fold shape goes through AITER's heterogeneous wrapper
        # (_use_fhmoe_wrappers), which only accepts the two-stage FlyDSL
        # family: kn1 'flydsl_moe1_*' and kn2 'flydsl_moe2_*' (NOT the
        # flydslv2 'flydsl_moe2_layout_*' family — the TUNE_ONLY default,
        # fhmoe-incompatible) with run_1stage=0. hetero_tuned_raw.csv's
        # 385/7 rows are layout-family (the first injection attempt armed
        # the fold OFF via the init probe), so the fused shape takes rows
        # ONLY from hetero_tuned_fused_v1.csv (tuned through the fhmoe
        # path). The 384/6 stock and 128/3 draft shapes run the plain
        # fused_moe path, which accepts any family — raw's layout rows are
        # fine there (and are the tuned best).
        if (row[H["expert"]], row[H["topk"]]) == ("385", "7"):
            if not is_fused_v1:
                continue
            kn1, kn2 = row[H["kernelName1"]], row[H["kernelName2"]]
            assert kn1.startswith("flydsl_moe1_"), f"bad kn1 {kn1}"
            assert kn2.startswith("flydsl_moe2_") and not kn2.startswith(
                "flydsl_moe2_layout_"
            ), f"bad kn2 {kn2}"
            assert row[H["run_1stage"]] == "0", "run_1stage must be 0"
        k = tuple(row[H[c]] for c in ("gfx", "cu_num", "token", "model_dim",
                                      "inter_dim", "expert", "topk", "act_type",
                                      "dtype", "q_dtype_a", "q_dtype_w", "q_type",
                                      "use_g1u1", "doweight_stage1"))
        us = float(row[H["us"]] or 1e9)
        if k not in best or us < float(best[k][H["us"]] or 1e9):
            best[k] = row
        kept += 1
    print(f"{path}: {kept} candidate rows")

with open(OUT, "w", newline="") as f:
    w = csv.writer(f)
    w.writerow(hdr)
    for k in sorted(best, key=lambda k: (int(k[5]), int(k[6]), int(k[2]))):
        w.writerow(best[k])
print(f"wrote {OUT}: {len(best)} rows")

cov = defaultdict(list)
for k in best:
    cov[(k[5], k[6])].append(int(k[2]))
for shape in sorted(cov):
    ms = sorted(cov[shape])
    print(f"  shape E/topk={shape[0]}/{shape[1]}: {len(ms)} Ms: {ms}")
    # the two measured prefill Ms must be tuned for the A/B shapes; the aux
    # draft-MoE shape (128/3) only has a partial grid — its uncovered Ms stay
    # heuristic in BOTH arms (identical), which is fine.
    if shape in {("384", "6"), ("385", "7")}:
        for need in (8192, 16384):
            assert need in ms, f"MISSING M={need} for shape {shape}"
assert len(best) == len(set(best)), "duplicate keys"
print("coverage OK (8192+16384 present for 384/6 and 385/7)")

## Independent repro of the prefill fusion — MI350X (gfx950), TP=4, real weights

Reproducing this PR's prefill fastpath claim on 8× **MI350X** (`AMD Instinct MI350 OAM`, gfx950, 256 CU, 1000 W cap; the PR measured on MI355X, same ISA but different GPU) with `vllm bench forward` (https://docs.vllm.ai/en/latest/cli/bench/forward/), at TP=4, on the head of this PR (c2a439500b, installed in `vllm/vllm-openai-rocm:nightly-rocm100-00b6c4c565a8732c131e1f452d4a17803bb0842b`), with the real `deepseek-ai/DeepSeek-V4.1-Flash-1017` weights.

The checkpoint is the shape class this PR targets: `deepseek_v41_text`, 384 routed experts + 1 shared, topk 6, FP8 block-32 weights with an mxp4 shared expert.

### What the timed graph contains

All measurements include the DSpark drafter: `--speculative-config` is passed and `--exclude-drafter` is **not**, so each captured graph is the target forward **plus** `drafter.propose()` of 5 drafts, with `lookahead = num_speculative_tokens + 1 = 6` KV slots reserved per request (`timing_scope=target_and_drafter` in the result JSON).

`vllm bench forward` has a single `execute_model` per replay — no scheduler, no step loop, no target sampling and no rejection sampling; `--iters`×`--samples` replays of that one forward. Target-only numbers are deliberately not reported: the drafter proposal is part of what a served TTFT pays for, so every arm below carries it.

**`vllm bench forward` replays one fixed batch per row by design, not fresh prompts: the PR that introduced it (#61339, "exact-shape forward timing") snapshots the KV blocks and restores them inside the graph "so in-place state … is identical across replays", and its `--kv-init` is zeros-only because random KV measured within 3 % on DeepSeek-V4.1 at ~100K context — token ids come from one seeded draw (`batch.py:50`), so repetitions differ only in timing while the rows differ only in shape.**

### Notes on methodology

**Not the PR's metric.** The PR reports end-to-end **TTFT** from a served model (`vllm bench serve`, OSL 16, greedy, DSpark k=5, prefix caching off, fresh server per setting). `vllm bench forward` times a target forward of a hand-built prefill-shaped batch: no sampling, no rejection sampling, no CPU step overhead, and all draft tokens are assumed accepted. Absolute numbers are therefore not comparable to the PR's TTFT table; the A/B delta is the comparable quantity, and none of the columns above is a TTFT measurement, so they can neither confirm nor refute the PR's TTFT percentages on their own.
**Prefix/KV state.** `vllm bench forward` disables prefix caching and zeroes the KV blocks per case, so the numbers are cold-prefill numbers with no cache hits.
