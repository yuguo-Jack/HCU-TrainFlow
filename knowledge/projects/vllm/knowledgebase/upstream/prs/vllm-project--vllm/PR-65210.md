# [Bugfix] Align extensible KV cache only for RDMA-registering connectors

[Upstream PR](https://github.com/vllm-project/vllm/pull/65210) · state: closed · merged: False

## Original PR description



## Overview

Fixes #65204. With the extensible KV cache (#56492), any KV connector makes the engine round the reserved KV capacity down to a multiple of the granule block alignment. CPU offloading (`--kv-offloading-size`) is a connector, so a model with a 5,657,600 B block stride (alignment 2048 blocks) and room for only 1375 blocks gets rounded to 0 blocks and fails to start.

## Claims

- The alignment, and the defragmenting commit after warmup, now apply only when a connector registers the device KV cache for RDMA (`KVTransferConfig.registers_kv_cache_memory()`: NIXL on device, Mooncake, MoRIIO, also inside `MultiConnector`). CPU offloading keeps its measured capacity.
- Registering connectors still get aligned segments. When alignment would reduce a usable reservation to 0 blocks, startup now fails with an error that names the alignment, instead of the misleading "decrease `max_model_len`" hint.

## Validation

New CPU-only test `test_extensible_kv_cache_granule_alignment_below_one_unit` in `tests/v1/core/test_kv_cache_planning.py`.

Before the fix (source reverted to `origin/main`):

```text
$ pytest tests/v1/core/test_kv_cache_planning.py -k below_one_unit
E   AssertionError: Regex pattern did not match.
E     Expected regex: 'multiple of 128 blocks'
E     Actual message: 'No available memory for the cache blocks. ...'
1 failed
```

With the fix:

```text
$ pytest tests/v1/core/test_kv_cache_planning.py tests/v1/worker/test_extensible_kv_cache.py \
    "tests/v1/engine/test_engine_args.py::test_kv_transfer_registers_kv_cache_memory"
84 passed, 16 skipped
```

(2 `test_estimate_max_model_len[Qwen/Qwen1.5-7B-*]` cases fail locally with and without this change because my offline environment has no cached model config; the 16 skips are CUDA-only tests.)

The predicate itself is already covered by `test_kv_transfer_registers_kv_cache_memory`, including `OffloadingConnector -> False` and `MultiConnector` nesting. Lint: `ruff check` and `ruff format --check` pass.

Not validated: the worker-side gates (`measure_kv_cache_blocks`, `extend_kv_cache`) run only on CUDA, and I have not reproduced the reported startup end-to-end on GPU.

## Details

Root cause: `EngineCore._initialize_kv_caches` ran `align_extensible_kv_cache_capacity` whenever `kv_transfer_config` was set, and the worker's `measure_kv_cache_blocks` aligned after warmup on the same condition. The alignment exists because a connector that registers each committed segment for RDMA needs that segment to be one physical chunk (see `granule_aligned_blocks`). CPU offloading copies blocks and registers nothing, so it doesn't need alignment. Both sites, and the `defragment` flag in `extend_kv_cache`, now use the existing `registers_kv_cache_memory()` predicate, which already gates ROCm support for the same connectors.

Changing only the engine side is not enough: the worker would still align the post-warmup measurement to 0 for CPU offloading.

The new error is raised only for `0 < num_blocks < alignment`. A count of 0 means a plain memory shortage and keeps the existing diagnostics. After warmup, the worker aligns before reporting its count, so a 0 there cannot be attributed to alignment; the reservation-stage check catches the common case, where capacity is already below one alignment unit.

Keeping an unaligned count for every connector, as also suggested in the issue, would break RDMA registration for NIXL, Mooncake and MoRIIO, so this PR does not do that.
