# [Bugfix][Frontend] Share the max_num_queued_tokens count across API servers

[Upstream PR](https://github.com/vllm-project/vllm/pull/65266) · state: open · merged: False

## Original PR description



## Overview

With several API server processes, `--max-num-queued-tokens` is checked against each process's own prefill backlog, so N API servers admit up to N times the cap. This shares the token count across API servers the way #54746 shares the request count.

Fixes #65265

## Claims

- With `--api-server-count` above 1, `--max-num-queued-tokens` rejects once the prefill backlog summed over all API servers reaches the cap, as the `SchedulerConfig` docs describe.
- The shared counters are allocated when either cap is set, not only with `--max-num-queued-reqs`.
- With one API server nothing changes.

## Details

- Each process already owns a 64-byte slot of 8 counters in `SharedAdmissionStats`, and the request count is counter 0. The prefill token total goes into counter 1, and `get_num_queued_tokens()` sums it over all slots, as `get_num_requests()` does.
- `OutputProcessor` writes the total when it can change: after `add_request` (including a streaming-input update), after `abort_requests`, and once at the end of `process_outputs` if a request left prefill, was rejected on arrival or got a new streaming input chunk. Nothing is written unless the counters are shared.
- `check_admission` reads the shared total when the counters exist, like the request cap.
- `APIServerProcessManager` allocates the counters when either cap is set.
- `docs/serving/data_parallel_deployment.md` and the `check_admission` docstring say both counts are shared across API servers and approximate.

Trade-offs:

- Like #54746's request count, the shared counts are read without a lock: requests that reach different API servers at the same moment can each be admitted, so a burst can pass the cap by up to one request per API server. The docs now say so.
- The written value is `get_num_queued_tokens()`, the walk over this process's requests that `check_admission` already does for each new request when the token cap is set. It runs once per add, abort or output batch, not once per finished request (on one 2.8 GHz Xeon core the walk takes 9 µs with 256 requests in flight, 68 µs with 1,024 and 346 µs with 4,096, half of them in prefill). A running total would be O(1), but every state change, streaming-input updates included, would have to keep it right, and #59097 also changes `get_num_queued_tokens`. I kept the walk and can switch if you prefer.
- With only `--max-num-queued-reqs` set the counters exist, so the token total is still written. If that matters, `AsyncLLM` can tell `OutputProcessor` whether the token cap is set.
- The count is still the full `prompt_len` of each request in prefill. Counting only the prefill work left, the other part #49445 deferred, is a separate change (discussed on #59097). Scheduler stats reach only one API server per step ([scheduler.py#L2662](https://github.com/vllm-project/vllm/blob/0e5b2ba118cfb3763a3640942e02dd8d93e8ed6c/vllm/v1/core/sched/scheduler.py#L2662)), so a scheduler-side count would also need sharing between API servers, and these counters could carry it.

No open issue or PR shares the token cap across API servers (searched `max_num_queued_tokens` and `SharedAdmissionStats`).
