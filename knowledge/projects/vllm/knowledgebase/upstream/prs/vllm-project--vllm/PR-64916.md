# [Spec Decode][Perf] Fuse DFlash2 candidate edge scoring into a Triton kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64916) · state: closed · merged: True

## Original PR description

## Purpose

The DFlash2 path selector scores every candidate pair for each draft step:
```
    S_t(a, b) = U_t(b) + <A(a) ⊙ H(h_t), B(b)>
```

The Qwen3 DFlash2 model did this with a compiled torch graph that runs several kernels (anchor clamp, gathers, a
concat, an elementwise product and an einsum). Beam carried its own Triton kernel, `candidate_edges`, that did the same thing.

This PR replaces both with a single Triton kernel, `dflash2_score_edges`, that both implementations call through `_score_edges`:
- One program per (request, step) gathers the anchor and candidate predecessor/successor rows, forms `A ⊙ H` in FP32, and computes the K×K edge block with `tl.dot`, then adds the unary term.
- The torch implementation remains as `_score_edges_reference`, which is used on CPU and in tests.
- Beam's `dflash2_ops.py` is deleted, and `DFlash2BeamCandidateSelector` calls `_score_edges`.

**Numerics.** The kernel and the reference now always return FP32 scores, and the edge term is no longer rounded to bf16. Before this PR, Beam's kernel stored scores in the unary dtype and the Qwen3 reference rounded the edge term to bf16. Inputs to the dot product stay bf16, because bf16 × bf16 products are exact in FP32. Mean absolute error against an FP64 reference drops from 7.2e-5 to 5.2e-5. The output is K-wide (`[num_reqs, steps, K, K]`), so storing it in FP32 costs negligible memory.

### End-to-end Benchmark

- **Sweep:** concurrency 1→256 in powers of two, with 4 × concurrency prompts (minimum 16) and one discarded warmup per server.
- **Sampling:** greedy, `--ignore-eos`.
- **Prefix caching:** off.
- **Workload:** SPEED-Bench `throughput_2k` / `low_entropy`, which has about 2.2K-token prompts, run through the chat endpoint with 2048 output tokens.
