# [Bugfix] Read step-start seq_lens without holding the CUDA driver context lock

[Upstream PR](https://github.com/vllm-project/vllm/pull/61622) · state: open · merged: False

## Original PR description



## Overview

Fixes #61621. Step-start `seq_lens` reads in attention metadata builders use `.cpu()` into pageable memory. While that copy waits for the previous step's GPU work, libcuda holds its context lock, so CUDA calls from every other thread in the process stall until the forward pass ends. This PR reads into pinned memory and waits on an event instead.

## Claims

- New `sync_copy_to_cpu()` in `vllm/utils/torch_utils.py`: pinned destination, `copy_(non_blocking=True)`, then a blocking `torch.cuda.Event` record + synchronize on the current stream. Falls back to `.cpu()` for non-CUDA tensors or without pinned memory.
- Used at the three step-start reads: `FlashInferMetadataBuilder.build()` (spec decode, or no `seq_lens_cpu_upper_bound`), `FlashInferMLASparseSM90Builder._kv_lens_host()` (no upper bound), and `make_local_attention_virtual_batches()`.
- The host waits for the same work as before, so the step's implicit host/device barrier is kept (see #61239). Only the driver lock is no longer held while waiting.
- In a stock engine (Llama-3.1-8B-Instruct, FlashInfer, MRV2, async scheduling, EAGLE3 k=3, H100), another thread's `cuEventRecord` was blocked 5.68 s / 5.64 s out of 14.7 s before this change and 1.20 s / 1.21 s after. Wall time is unchanged.

Mutation check: with the helper body replaced by `return t.cpu()`, the new test fails at `assert not copy_done.is_set()` (the side thread's launch waited for the copy).

Re-verified after rebasing onto `8a8e2baa0` (head `d2be95f5e988`) on GB10 (aarch64, driver 580.82.09) in `vllm/vllm-openai:nightly-77154ca6116ae34cbfe314beef1016bde9b63989`, whose four touched product files are byte-identical to `8a8e2baa0`. Results: full `tests/utils_/test_torch_utils.py` 38 passed, the new test 3/3 passed (and 20/20 in a loop), the mutation failed 3/3, and the torch-only repro from #61621 showed 1180 ms with `.cpu()` vs 0.1-0.2 ms with pinned + event.

The GB10 run also showed the test needs a warm-up: without one, the first `add_` launch in the process lazily loads its kernel module, and that load waits for the queued GPU work, so the test failed 6/12 with `CUDA_MODULE_LOADING=LAZY` and 0/12 with `EAGER`. The test now launches the side kernel and calls the helper once before timing anything.

End to end: `repro_engine.py` from #61621 (in-process engine, a side thread timing `cuEventRecord` on its own non-blocking stream every 2 ms, 3 rounds of 32 x 3000-token prompts, 256 output tokens, two runs each):

| main, after | EAGLE3 k=3 | 1.20 s / 1.21 s | 11 / 10 | 14.7 s |

The remaining ~1.2 s is a few long stalls with the engine thread in the forward pass (`linear`). They are the same on main without spec decode, where this builder path is not reached (1.84 s), so they are not from these reads.

Pre-commit (`pre-commit run --from-ref origin/main --to-ref HEAD`, Python 3.12 container): ruff check, ruff format, typos, mypy, check-test-tethering, SPDX, forbidden imports, torch.cuda call check and the other applicable hooks passed.

Not validated: the SM90 sparse MLA builder and `make_local_attention_virtual_batches` (chunked local attention) paths were not run end to end, since this hardware run had no model that uses them. The change there is the same one-line swap. Not tested on ROCm, where `t.is_cuda` is also true and the pinned + event path is taken. Other devices fall back to `.cpu()`.

## Details

Root cause: a synchronous `cudaMemcpy` D2H into pageable memory waits for the stream's earlier work while holding the CUDA context lock. Any other thread that enters the driver blocks for the rest of that wait (measured here: kernel launch and `cuEventRecord`), even on an idle non-blocking stream. `cudaEventSynchronize` on a blocking-sync event does not hold the lock while it waits. The torch-only repro in #61621 shows a 1.18 s stall for the other thread with `.cpu()` and 0.2 ms with pinned + event, on the same GPU work.

Design: one helper instead of per-backend changes, because other step-start reads (e.g. if #61239 restores the blocking read under async scheduling) can reuse it. The event is created per call; `torch.empty(pin_memory=True)` is served by the caching host allocator after the first step, so no `cudaHostAlloc` on the hot path. `blocking=True` matches the existing per-step events in the model runners (#47081). Call sites keep their existing `gpu_sync_allowed()` wrapping, since this is still a host sync.

Why this is not a duplicate: searched open/closed issues and PRs for `seq_lens.cpu`, pageable copies, driver/context lock, `cudaLaunchHostFunc`, and KV connector stalls. #57214 and #58684 removed some of these reads where a CPU upper bound is exact. #61239 is about the barrier those removals dropped, and it proposes bringing the blocking read back. #47081 changed spin events to blocking events. None of them addresses the lock held during a pageable D2H wait. #57352 (open) plans FlashInfer from CPU bounds with speculative decoding on fa2 and keeps the `.cpu()` fallback this PR changes, so the two compose. #59493 (open) makes FlashInfer's `plan()` staging buffer pageable, which is a separate race.
