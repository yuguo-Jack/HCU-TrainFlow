# [Quantization][OOT] Fix OnlineQuantizationConfig overriding the registered OOT online quantization config

[Upstream PR](https://github.com/vllm-project/vllm/pull/64056) · state: open · merged: False

## Original PR description

## Overview

`get_quant_config()` constructed `OnlineQuantizationConfig` directly at every one of
its online return sites, instead of the class selected by `register_quantization_config()`.
As a result an out-of-tree (OOT) backend's registered online-quantization config was
silently replaced by vLLM's own, and the only workaround was to monkeypatch the model
loader. Instantiate the resolved class when it actually is an `OnlineQuantizationConfig`
subclass.

Motivating consumer: vllm-ascend registers `AscendOnlineQuantizationConfig` for
`--quantization online` / `int8_per_channel_weight_only` and needs `get_quant_config()`
to build it. No upstream issue; found while adding OOT online-quantization support.

## Claims

- `--quantization <online method>` now instantiates the class returned by
  `get_quantization_config(<name>)`, so `register_quantization_config()` works for online
  quantization exactly as it already did for checkpoint formats.
- No behavior change for in-tree methods: every built-in online shorthand still resolves
  to vLLM's `OnlineQuantizationConfig`, including `mxfp4` / `mxfp8`, whose resolved class
  is a *checkpoint* config.
- 3 unit tests, added to the existing `tests/quantization/test_online.py`.

## Validation

Reproducer — registering a subclass for an online method name and asking for the config:

```python
register_quantization_config("my_online")(MyOnlineConfig)
cfg = weight_utils.get_quant_config(model_config, LoadConfig())
assert type(cfg) is MyOnlineConfig   # fails without the fix
```

Without the fix this yields `type(cfg) is OnlineQuantizationConfig`; with it,
`MyOnlineConfig`. The added tests encode exactly that assertion, so reverting the source
hunk turns them red.

```bash
# the new tests (fail before the fix, pass after)
python -m pytest tests/quantization/test_online.py -q -k registered_online_config

# regression guards: the ambiguous shorthands keep vLLM's own class
python -m pytest tests/quantization/test_online.py -q \
  -k "online_shorthand_selects_checkpoint_or_online_config"
```



CI: `tests/quantization/test_online.py` runs in the Intel XPU job
(`.buildkite/intel_jobs/test-intel.yaml`), which triggers on any `vllm/` change, so the
new tests are exercised there. The NVIDIA quantization areas do not run this file (their
directory-level `pytest quantization/` steps are commented out), so there is no GPU CI
coverage for it. The change is pure config construction executed before any weight is
loaded, and the CUDA/ROCm shorthand paths stay covered by the existing parameterized
tests in the same file.

## Details

### Root cause

1. `register_quantization_config(name)` is vLLM's OOT hook: it makes
   `get_quantization_config(name)` return the registered class.
2. `get_quant_config()` only used that class for `get_config_filenames()` and
   `from_config()`. At its online return sites it built `OnlineQuantizationConfig(...)`
   directly, and the early exit guarded with an identity test
   (`quant_cls is OnlineQuantizationConfig`), so a subclass never matched and fell through
   to the checkpoint-config file lookup.
3. Net effect: a registered OOT config was replaced by vLLM's, whose method classes pick
   CUDA/ROCm kernels (`init_fp8/int8/mxfp8_linear_kernel`, `select_fp8/int8/mxfp8_moe_backend`),
   so the platform could not serve online quantization at all.

### Implementation

Three return sites inside `get_quant_config()`:

| line | site | change |
| --- | --- | --- |
| 326 | unambiguous online method, args already resolved | `is` → `issubclass`; return `quant_cls` |
| 369 | online shorthand whose class declares no config filename | return `quant_cls` when it is an online config |
| 383 | online shorthand whose config file is absent | same as above |

`issubclass` rather than identity is required because two names are ambiguous: `mxfp4`
and `mxfp8` are both online shorthands and checkpoint `quant_method` values
(`_DEFERRED_ONLINE_SHORTHANDS`), and `get_quantization_config()` maps them to
`Mxfp4Config` / `ModelOptMxFp8Config`. At the two shorthand sites the branch is entered by
*name*, not by class type, so `quant_cls` may be a checkpoint config there; the guard keeps
vLLM's own implementation for those two names. They reach different branches
(`Mxfp4Config.get_config_filenames()` is `[]`, while `ModelOptMxFp8Config` returns
`hf_quant_config.json`, which does not exist for an unquantized checkpoint), which is why
both sites need the guard.

### Compatibility

Unchanged on purpose:

- all in-tree online shorthands still build `OnlineQuantizationConfig`;
- `--quantization fp8` (deprecated alias for `fp8_per_tensor`) keeps using it, because
  `quant_cls` there is `Fp8Config`, a checkpoint class;
- the online-overlay path (`--quantization <checkpoint method> --quantization-config ...`)
  also keeps using it: the online class cannot be derived from a checkpoint method name.
  Consequence: an OOT backend cannot override the overlay path. Supporting that needs a
  separate hook (e.g. a platform method returning the online config class) and is out of
  scope for this change.

### Complexity

+10/−2 non-test lines, one file. No new abstraction, dependency, or public API; the
registry that already governed checkpoint formats now governs the online path too. Tests
(+100 lines) are excluded from the complexity count.
