# [Bugfix][KV Connector] Name the differing fields on a NIXL compatibility hash mismatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/60208) · state: open · merged: False

## Original PR description

Refs #60124. Implements suggestion 1 from the issue: a NIXL compatibility hash mismatch now names the fields that disagree. Suggestion 2 (docs) is covered by #60176; suggestion 3 (a hint next to the "Turning off hybrid kv cache manager" warning) is left out on purpose, since it can only guess at the remote's config while the factor diff reports the actual disagreement at the point of failure.

## Overview

The mismatch error used to print two bare hashes plus a generic list of things that might differ. When the divergence is implicit, like the issue's MultiConnector-prefill case that silently turns the hybrid KV cache manager off on one side, finding it meant diffing two full deployment configs by hand.

The handshake payload now carries the compatibility factors alongside the hash, and the mismatch path diffs them and reports each disagreeing field, e.g.:

```
NIXL compatibility hash mismatch. Local: ac9aa5b3..., Remote: d6e05114.... Differing factors (local vs remote): is_hma_enabled: local=True, remote=False. Prefill and decode instances have incompatible configurations. ...
```

## Compatibility

- `compatibility_factors` is an optional payload field and msgspec ignores unknown keys, so mixed-version peers handshake fine in both directions: old decoders ignore the field, new decoders default it to `None`, and the error falls back to the previous message when a peer sends none.
- Hash inputs are unchanged: `auxiliary_layer_ids` canonicalizes tuple to list, and `json.dumps` (the `hash_factors` serializer) renders both identically, so same-config peers produce the same hash across versions. The existing compatibility-hash tests pin this.

## Validation

```bash
.venv/bin/python -m pytest tests/v1/kv_connector/unit/test_nixl_connector.py -q
```

177 passed, 2 failed: `test_abort_timeout_on_prefiller[ray]` and `[None]` fail identically on unmodified main in this environment (`torch.ops._C.init_cpu_memory_env` is absent from the precompiled CPU wheel), unrelated to this change.

New tests: the diff names `is_hma_enabled` for the issue's exact scenario (HMA on vs off), descends into `speculative_config` subfields, the factors survive a msgpack round trip diff-clean, and the payload is wire-compatible in both directions (old decoder ignores the new field, new decoder defaults it to None). Changed-file `ruff check` / `ruff format --check` clean with the pinned v0.14.0.

Not run: a real two-node NIXL handshake, no compatible hardware here. The change only adds a payload field and an error-message path; the transfer path itself is untouched.

No duplication: #60176 is docs-only and references the same issue; #55776 adds model revisions to the hash inputs, a different concern. No open PR sends or diffs the factors as of 2026-10-06.
