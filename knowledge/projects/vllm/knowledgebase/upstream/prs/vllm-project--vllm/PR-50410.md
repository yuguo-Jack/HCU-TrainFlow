# [Perf][Scheduler] Balance decode batches for PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/50410) · state: open · merged: False

## Original PR description

## Summary

Balance established decode requests across Model Runner V2 PP steps without limiting prefill or output-token recomputation. Applies to synchronous and asynchronous scheduling.

## Changes

- Compute a dynamic decode quota from the running decode count and PP size, capped by `ceil(max_num_active_seqs / pipeline_parallel_size)` (falling back to `max_num_seqs`).
- Add `--pp-min-decode-batch-size` (default `8`, minimum `1`) to avoid excessively small decode batches at low load. The active-request cap still takes precedence; this setting never waits for a batch to fill. Setting it to `max_num_seqs` restores a fixed quota.
- Share the quota between RUNNING and ready resumed decodes. With priority scheduling, interleave ready WAITING admissions with RUNNING requests by priority before allocating blocks. Pending KV transfers do not reserve decode slots. Preserve request-capacity limits and existing KV-holding queue precedence; do not preempt requests just to reclaim a quota slot.
- Check known decode state before cache/encoder preparation. Unknown resumed cache hits still require a lookup to distinguish decode from output-token recomputation. Release a scheduled decode slot when its request is preempted.
- Preserve the full graph capture range: uncapped prompt-finishing steps can still form larger uniform decode batches.
- Centralize PP microbatch policy for scheduler cadence and worker receive queues. MRV1, PP1, and XPU's explicit microbatch opt-out retain their existing scheduling policy.

- NVShreyas · comment · 2026-09-15T17:11:27Z · [source](https://github.com/vllm-project/vllm/pull/50410#issuecomment-5684652120)

Thanks for working on this @LostFox11. We independently observed the same underlying problem: with asynchronous PP scheduling, requests can become unevenly distributed across pipeline-step cohorts, producing persistent microbatch imbalance.

I replayed commit `d664efc` on a matched Kimi-K3 + DSpark workload and compared three scheduler policies:

- Model: Kimi-K3 with DSpark, 7 speculative tokens
- Hardware/topology: B200, TP8 × PP4
- Layer partition: `25,25,25,18`
- `max_num_seqs=32`
- Workload: 1,000-request Mooncake trace, concurrency 64

| Policy | Output tok/s | Total tok/s | Duration | Mean TTFT | Mean ITL |
|---|---:|---:|---:|---:|---:|
| Natural scheduling | 820.61 | 21,538.44 | 3,199.76 s | 99.50 s | 34.52 ms |
| This PR: global request cap | 753.24 | 19,770.37 | 3,486.09 s | 110.75 s | 34.78 ms |
| Decode-only cap | 1,008.94 | 26,481.66 | 2,606.01 s | 80.63 s | 28.25 ms |

Relative to natural scheduling, the current global cap:

- reduced throughput by 8.21%;
- increased duration by 8.95%;
- increased mean TTFT by 11.31%;
- increased P90 TTFT by 20.02%.

A decode-only version instead improved throughput by 22.95% over natural scheduling. It was 34.0% faster in output throughput than the current PR implementation (`1008.94` versus `753.24` tok/s).

The important behavioral difference is that the current loop condition:

```python
len(num_scheduled_tokens) < max_num_scheduled_reqs
```

caps all scheduled requests, including ordinary prefill and chunks that complete the prompt. On this prefix-reuse-heavy mixed workload, that is too restrictive. Based on the implementation and results, it likely leaves token-budget capacity unused when several small prefill chunks could otherwise be scheduled.

I suggest applying the balancing limit only to requests that were already in decode before the current scheduler step:

```python
is_decode = request.num_computed_tokens >= request.num_prompt_tokens

if is_decode and len(scheduled_decode_req_ids) >= decode_cohort_target:
    skip_for_this_step(request)
    continue
```

Then add the request to `scheduled_decode_req_ids` only after it is successfully scheduled. This should be applied in both the `RUNNING` and `WAITING` paths, with the count restored if a selected request is subsequently preempted.

This deliberately excludes:

- ordinary/chunked prefill;
- a chunk that reaches the prompt boundary during the current step;
- other requests that do not execute established decode.

At saturation, the initial target can remain:

```python
ceil(max_num_seqs / pipeline_parallel_size)
```

which gives 8 established decode requests per scheduler step for `max_num_seqs=32`, PP4.

We also profiled fixed-shape workloads. Balancing established decode cohorts improved output throughput by 4.74% on PP2 and 12.62% on PP4. On PP4, the natural scheduler formed persistent Q7/Q13/Q2/Q10 cohorts, while the decode-only limit produced Q8/Q8/Q8/Q8.

So I think the balancing mechanism in this PR is valuable, but the cap should count established decode requests rather than total scheduled requests. I can share the detailed benchmark configuration and profiles or help prepare the decode-only modification if useful.

@NVShreyas Thank you very much for the suggestion and the detailed analysis. We observed the same issue: limiting prefill requests can create uneven computational workloads across successive batches, introducing bubbles into the PP pipeline. This did degrade performance in most of the scenarios we tested.

We recently also encountered a different case: cross-node deployments, such as PP2TP8 across two nodes, processing large batches of 128K-token requests with a nearly 100% prefix-cache hit rate. In this scenario, leaving prefill admission unrestricted caused substantial host-side overhead, particularly in cross-node prompt token ID transfer, deserialization, and `cpu_copy`. Even though prefix caching eliminates most of the prefill computation, processing the long prompts on the host can still be expensive.

Nevertheless, I agree that avoiding a prefill request cap is the right approach for most workloads. Thank you again for highlighting this distinction.

Building on the decode-only balancing policy, I also think graph capture sizing should be adjusted accordingly. Since the request limit per decode batch becomes much smaller, the default decode-only capture range should reflect that limit rather than the global request capacity, avoiding unnecessarily large graph captures.
