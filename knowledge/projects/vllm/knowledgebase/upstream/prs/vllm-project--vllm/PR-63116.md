# [Bugfix][ROCm] Size AITER MLA persistent metadata for every decode query length

[Upstream PR](https://github.com/vllm-project/vllm/pull/63116) · state: closed · merged: True

## Original PR description

## Overview

`AiterMLAMetadataBuilder` sizes its persistent decode metadata buffers with one `get_mla_metadata_info_v1` call at `reorder_batch_threshold` (#45227), but it builds metadata for every query length up to that threshold, and aiter's buffer needs are not monotonic in the query length. A bf16 DSpark draft overflows the buffers and faults. This PR sizes them for the largest need of any query length up to the threshold.

Found by Hyperloom.

## Claims

- Fixes `HSA_STATUS_ERROR_MEMORY_FAULT` during warmup for Kimi-K3 with its DSpark draft (TP4, `num_speculative_tokens: 7`, bf16 KV cache).
- No change without speculative decoding (threshold 1, the same single call as before), or for 16-head fp8 KV caches up to threshold 8. Other configurations can get larger buffers, e.g. 32-head fp8 on gfx950, which is 64-wide at query length 3 and 128-wide at query length 4.
- Adds `test_builder_sizes_metadata_for_every_decode_qlen`.

## Validation

aiter v0.1.26 called directly on MI355X: 16 heads, 1024 requests, non-causal, bf16 Q/KV and metadata, compared with a PyTorch reference.

| Query length | Buffers sized for | Result |
|---|---|---|
| 7 | 8 | memory fault |
| 7 | 7 | matches (max abs err 0.003) |
| 5, 6 | 8 | memory fault |
| 4 | 8 | matches (max abs err 0.004) |

Kimi-K3 truncated to 8 layers (`--hf-overrides`, `--load-format dummy`) with its DSpark draft (`target_layer_ids` remapped), TP4, `--kv-cache-dtype auto`, CUDA graphs on, vLLM built from main at b3b0bc3059. Main faults during warmup; this PR starts and serves 24 concurrent requests.

Unit tests on MI355X against the built tree, `pytest tests/v1/attention/test_rocm_aiter_mla_mtp_split.py tests/v1/attention/test_rocm_aiter_mla_dcp_cprr.py`: this PR 113 passed. Main fails 21: the new test, and the cases of `test_builder_init_sizes_decode_metadata_and_filters_dcp_maps`, which now expects one sizing call per query length.

## Details

On gfx950, aiter tiles the `num_heads x qlen` packed query rows of a bf16 block by 64 when there are fewer than 128 of them, and by 128 otherwise. With 16 heads and 1024 requests, query lengths 5-7 need `work_info_set` (2558, 8) and `reduce_final_map` (2048, 2), while query length 8 needs (1279, 8) and (1024, 2). A DSpark draft runs `k`-token blocks under a `k + 1` threshold, so `k = 7` lands on the larger case. At 1024 requests the larger sizing adds about 55 KB of int32 buffers.

CI does not run a DSpark draft on MI355X. The results above use dummy weights; a real-weight Kimi-K3 run was not done. #41016 (closed) sized the batch dimension of these buffers; this PR sizes the query-length dimension.

AI assistance (Claude) was used to investigate and prepare this change. I reviewed every changed line and reproduced the results above.

- BaoYunkai · comment · 2026-10-29T11:30:55Z · [source](https://github.com/vllm-project/vllm/pull/63116#issuecomment-6495467987)

Thanks for taking a look!

1. aiter splits each request's packed query rows (num_heads × query length) into tiles, and the work-info and reduce buffers scale with the tile count. On gfx950 with bf16 and at most 64 heads (48 aside), 64–127 packed rows are tiled by 64, and 128 rows and up by 128. With 16 heads per rank, query length 4 is 64 rows (1 tile), 5–7 are 80–112 rows (2 tiles), and 8 is 128 rows (1 tile), so 5–7 need about twice the buffer size of 8. Calling aiter directly with 16 heads, 1024 requests and KV lengths of 7–63, query length 7 produced 2066 work items, while buffers sized for query length 8 hold 1279, and it faults. Other head counts and fp8 have similar jumps, e.g. 32-head fp8 uses 16-row tiles at query length 2 (4 tiles) but a single 128-row tile at 4.
2. The buffers are allocated per attention metadata builder, not per layer, and sized by `max_num_seqs`. With `max_num_seqs=1024`, the 16-head bf16 draft at threshold 8 goes from 56 KB to 112 KB (+55 KB). Across the head counts this backend runs at (16–128), bf16/fp8 and thresholds 2–16 on gfx950, the largest increase is +166 KB (32-head fp8 at threshold 4), and at most +208 KB with `AITER_ENABLE_EXPERIMENTAL=1` or DCP verify. Without speculative decoding nothing changes.
