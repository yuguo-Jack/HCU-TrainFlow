# [Performance][KV Offload] Avoid zero-filling the SimpleCPUOffload host KV pool

[Upstream PR](https://github.com/vllm-project/vllm/pull/64345) · state: closed · merged: True

## Original PR description



## Overview

Large `SimpleCPUOffloadConnector` host KV pools are zero-filled during startup even though CPU blocks become loadable only after a completed GPU-to-CPU store. The target configuration allocates about **175 GB per rank**; use `torch.empty` to avoid a redundant full-buffer write at that scale.

## Claims

- Removes eager zero-filling of the CPU KV pool while preserving tensor shapes, dtypes, capacity, and host registration.
- No end-to-end startup speedup is claimed; GPU pinning and serving validation are pending.

## Validation

Validation ran with this patch applied to upstream main `0fddee1f5869465a6235d2076f82f1ea70318064`. GitHub's subsequent merge preview contains identical offload runtime and test code; the intervening main changes add unrelated model recipes.

- `VLLM_PLUGINS='' .venv/bin/python -m pytest tests/v1/simple_kv_offload/test_scheduler.py tests/v1/simple_kv_offload/test_worker.py -q --maxfail=1`: **100 passed, 1 skipped**. The CUDA/ROCm worker module skipped on this macOS host; the passing scheduler tests cover CPU store/load bookkeeping, not GPU DMA.
- `pre-commit run --files vllm/v1/simple_kv_offload/worker.py`: all applicable hooks passed, including Ruff 0.14.0 and mypy. `git diff --check` passed.
- Allocation-only microbenchmark: Apple M4, macOS arm64, PyTorch 2.11.0, one CPU thread, 256 MiB `int8` tensor, seven alternating-order samples after two warmup iterations:

| Allocation | Median | Min–max |
| --- | --- | --- |
| `torch.zeros` | 3.616 ms | 3.592–3.618 ms |
| `torch.empty` | 0.750 µs | 0.625–2.500 µs |

This measures an unpinned allocation with a warm allocator. It excludes page population during registration, CUDA/ROCm registration, GPU store/load traffic, and model startup. It must not be extrapolated to a serving speedup. Required performance follow-up: compare allocation plus host registration at **175 GB per rank**, including the actual concurrent ranks per host, and measure end-to-end startup/output behavior. The existing Buildkite `v1-kv-offload` step covers the worker suite on CUDA and its ROCm mirror; those runs and the production-sized comparison remain pending.

<summary>Allocation-only reproducer</summary>

Run in a PyTorch 2.11.0 environment:

```sh
.venv/bin/python - <<'PY'
import statistics
import time
import torch

torch.set_num_threads(1)
samples = {"zeros": [], "empty": []}
for iteration in range(9):
    modes = ("zeros", "empty") if iteration % 2 == 0 else ("empty", "zeros")
    for mode in modes:
        start = time.perf_counter()
        if mode == "zeros":
            tensor = torch.zeros(256 * 1024**2, dtype=torch.int8, device="cpu")
        else:
            tensor = torch.empty(256 * 1024**2, dtype=torch.int8, device="cpu")
        elapsed = time.perf_counter() - start
        del tensor
        if iteration >= 2:
            samples[mode].append(elapsed)
for mode, values in samples.items():
    print(mode, "median/min/max seconds:", statistics.median(values), min(values), max(values))
PY
```

## Details

`vllm/v1/simple_kv_offload/worker.py` contains the only logic change and a brief safety comment. The manager inserts CPU block hashes in `_process_store_completion` after all workers report the store complete; CPU lookups and loads use that cache. Unwritten CPU blocks are therefore unavailable for loads. `cudaHostRegister` still runs and retains its page-faulting and pinning cost.

Duplicate-work check: #60130 replaces the per-layer allocations with a shared host mapping and optional HugeTLB pages; #54578 and #54792 add asynchronous initialization, and #54792 still allocates zeroed buffers. This PR is the minimal allocation-only change to the current synchronous path, without a buffer-layout or readiness redesign.
