# [Rust Frontend] Support --trust-request-chat-template

[Upstream PR](https://github.com/vllm-project/vllm/pull/62673) · state: closed · merged: True

## Original PR description

## Overview

Python refuses a request that brings its own chat template unless the server runs with `--trust-request-chat-template` (`OnlineRenderer.validate_chat_template`, `vllm/renderers/online_renderer.py`), with a 400: "Chat template is passed with request, but --trust-request-chat-template is not set. Refused request with untrusted chat template." The Rust frontend rejects the flag at startup and its HF renderer compiles and renders any request `chat_template`, so a request can run an arbitrary Jinja template on a server whose operator never opted in. This PR supports the flag and refuses untrusted request templates where the Rust frontend compiles them.

## Claims

- `--trust-request-chat-template` is accepted by `vllm serve` with the Rust frontend (through `--args-json`), `vllm-rs serve`, and `vllm-rs render`.
- Without the flag, a request `chat_template` on chat completions, `/tokenize`, or the render route returns 400 with Python's message; with it, the template is rendered as before.
- `/tokenize` now maps request validation errors from chat preparation to 400 instead of 500, as chat completions already does, so this refusal and other request errors there (for example a template's `raise_exception`) are client errors, as in Python.

| Request `chat_template` | Python | Rust before | Rust after |
|---|---|---|---|
| set, flag off | 400 | rendered | 400 |
| set, flag on | rendered | startup fails on the flag | rendered |

- `chat_template_refuses_untrusted_request_override` (`vllm-chat`): an untrusted HF renderer refuses a request template with a request validation error and still renders requests without one. It fails with the check removed. The existing override tests now run with a trusted renderer.
- `untrusted_request_chat_template_maps_to_invalid_request` (`vllm-server`): the error maps to 400 with Python's message through `chat_submit_error`, which `/tokenize` now uses.
- `frontend_config_trusts_request_chat_template_from_args_json` (`vllm-cmd`): the flag in `--args-json` reaches the server config.

## Details

The check sits where a request template is consumed: `HfChatRenderer::apply_chat_template`, the only place that compiles one. The renderer receives the flag once at load through `LoadModelBackendsOptions`, next to the server-default `chat_template`. The flag moves from the unsupported-argument list to the shared runtime arguments (and the `render` arguments).

Differences from Python, documented on the flag and on `ChatOptions.chat_template`:
- Only the HF renderer honors a request template. The native renderers (DeepSeek, Harmony, and the other model encoders) ignore it whether or not it is trusted, while Python refuses an untrusted one for every renderer except Harmony.
- A `chat_template` key inside `chat_template_kwargs` is not refused: Rust passes it to the template as an ordinary variable and never compiles it, while Python treats it as a template override.
- `--no-trust-request-chat-template` is not accepted, like the other inverse boolean spellings on the Rust CLI.

Not a duplicate: no open upstream PR implements this flag for the Rust frontend; vllm-project/vllm#62374 (configurable template fuel) leaves a TODO for request templates once this flag lands.
