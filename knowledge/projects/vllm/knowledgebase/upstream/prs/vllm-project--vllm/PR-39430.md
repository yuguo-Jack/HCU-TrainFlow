# fix(minimax_m2): avoid KeyError on split q/k/v NVFP4 weight scales

[Upstream PR](https://github.com/vllm-project/vllm/pull/39430) · state: open · merged: False

## Original PR description

## Summary

Fixes #39314

When loading the  checkpoint (or any checkpoint that stores attention weights as separate `q_proj`, `k_proj`, `v_proj` rather than fused `qkv_proj`), `MiniMaxM2Model.load_weights` crashes with:

```
KeyError: 'layers.0.self_attn.qkv_proj.k_scale'
```

**Root cause:**

The `stacked_params_mapping` loop rewrites weight names like
`model.layers.0.self_attn.k_proj.k_scale` → `model.layers.0.self_attn.qkv_proj.k_scale`.
The code then tries to remap that via `maybe_remap_kv_scale_name` (which correctly maps it to `attn.k_scale`), but only `break`s inside the successful-remap branch. When the remap succeeds but the `break` is inside the `if`, execution still falls through if the outer condition isn't met — and in cases where the remapped name isn't in `params_dict`, it falls all the way to the bare `params_dict[name]` lookup, which KeyErrors on the now-rewritten `qkv_proj.k_scale` name.

**Fix:**

Move the `break` outside the inner `if remapped_name is not None ...` block so that once a weight is identified as a `.k_scale` / `.v_scale` entry, we always `break` from the stacked-params loop after the remap attempt — whether the scale was loaded successfully or silently skipped.

## Test Plan

- Manual: Confirmed the code path that previously raised `KeyError` now correctly skips unloadable scale tensors with a logged warning (consistent with behavior for other scale-remap failures across the codebase).
- Existing `test_weight_utils.py` tests unchanged and passing locally.
