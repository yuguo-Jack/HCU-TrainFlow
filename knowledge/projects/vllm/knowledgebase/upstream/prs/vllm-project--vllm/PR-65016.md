# [Multimodal] Faster multimodal input path under concurrent image traffic (parallel preprocessing + sizable shm tensor arena)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65016) · state: open · merged: False

## Original PR description

## Purpose

Two independent fixes to the multimodal input path that show up under concurrent image traffic (many requests, each with a new image, processor cache off). One commit per change; each is opt-in or keeps today's default.

| # | Change (commit) | Why | Measured (MI355X, MiniMax-M3 VL, TP2, 8-row image sweep 512x512–2048x1600, c4–c256) | Opt-in | Test |
|---|---|---|---|---|---|
| 1 | Parallel multimodal preprocessing when the processor cache is off: the MM executor is sized by the existing `--renderer-num-workers` | image decode/resize/patchify runs on a single-worker executor and queues requests while the GPU waits | on a large-image row: +1.6% throughput, TPOT −65%, TTFT +23% (8-row geomean +0.5%, see below) | `--renderer-num-workers N` (default 1 = today) | unit test for the executor sizing |
| 2 | `--shm-tensor-arena-slots` / `--shm-tensor-arena-slot-mb` | fixed arena size; large images at high concurrency fall back to the slow pickled path (1,300+ fallbacks in one sweep) | fallbacks 1,300+ → 0, TTFT +9.1% better, throughput neutral (+0.2%) (A B B A, n=4) | new options, defaults = today's values | unit test for option plumbing and defaults |

Notes:
- (1) was measured with an equivalent switch that sized only the MM executor; `--renderer-num-workers` also sizes the tokenizer pool, so the exact PR form will be re-measured.
- Related: #50896 rejects `--renderer-num-workers > 1` with the mm cache on; (1) only applies with the cache off.
- (2): open to a structural alternative (growing arena / sizing from the model's max mm payload) if maintainers prefer.
- Consolidates #65017.

## Verified on this PR's head (2026-11-03)

Dedicated MI355X node, TP2, MiniMax-M3 VL (AttnFP8), vLLM nightly 40941f2c + this branch, full 8-row image sweep, A B B A (A = `--enable-shm-tensor-arena` defaults, B = A + `--renderer-num-workers 8 --shm-tensor-arena-slots 128 --shm-tensor-arena-slot-mb 48`):

- **8-row geomean throughput +0.5%** (A/A spread 0.8%): no measurable throughput gain on this row set, no regression (worst row −1.0%, inside its band).
- **2048x1600 image row (c16)**, the only row that moves in every pass: throughput +1.6%, median TPOT 29.3 → 10.3 ms, median TTFT 3.9 → 4.8 s. Large images are preprocessed in parallel, reach the engine together and batch their prefills.
- 512x512 / 768x1024 rows at c4–c256: flat (preprocessing is not the bottleneck there).
- shm arena sizing: no slow-path fallbacks with B.

The earlier +4.9% (8 rows, measured with an equivalent switch on a different stack) does not reproduce on this branch. A workload where preprocessing limits throughput (several or larger images per request at high concurrency) is where (1) should show; not covered by this row set.
