# [ROCm][MoE] Add opt-in AITER FlyDSL clamped MXFP4 BF16 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64640) · state: open · merged: False

## Original PR description

## Summary

Add an opt-in FlyDSL MoE backend for ROCm gfx942, using [ROCm/aiter#6995](https://github.com/ROCm/aiter/pull/6995). It keeps checkpoint MXFP4 weights and BF16 activations, and implements the model's clamped SiLU with BF16 rounding before activation. Existing defaults and backend priorities do not change.

Select it with `--moe-backend aiter_flydsl_mxfp4_bf16`. A supported AITER build containing the new API is required; the global dependency image is not updated by this PR.

## How Much Faster?

**The measured complete MoE operator is 3.15x faster at M8 and 2.50x at M32 than the pinned vLLM unfused implementation.** At the larger measured batches, the improvement is 1.53x-1.91x. These are operator results, not full-model serving speedups.

Target: MI325X/gfx942, H=5120, logical intermediate=288 padded to 384, 384 experts, top-6, clamp=10. M is token rows entering one TP-local MoE call, not client concurrency. Same inputs and weights; seed 101/uniform routing; five timed passes per candidate; median GPU kernel time:

| Token rows M | Before: vLLM unfused (us) | After: automatic AITER dispatch (us) | Operator speedup |
|---:|---:|---:|---:|
| 8 | 242.419 | 76.988 | **3.15x** |
| 32 | 496.073 | 198.185 | **2.50x** |
| 128 | 950.240 | 501.539 | **1.89x** |
| 512 | 1094.238 | 572.864 | **1.91x** |
| 4096 | 2233.506 | 1463.233 | **1.53x** |

Speedup = before/after latency. The measurement includes sorting, both GEMMs, activation and output reduction/zeroing; it excludes router scoring, shared experts, TP communication, attention and host launch gaps. It uses reused weights, not a cold-weight or full-model CUDA Graph protocol.

**Where the gain comes from:** the complete AITER MoE implementation is faster than the unfused comparator. Within that AITER implementation, the two qualified CSV entries add another **1.61x at M8** and **1.25x at M32** versus its same-math default tiles. Only those exact gfx942/304-CU shape keys select tuned tiles; unmatched batches keep the defaults. This is not a claim that adding clamp alone makes an existing kernel 3x faster. Across 12 decode holdouts, 11 established a strict timing margin; one M32 hot-routing case did not. No decode regression was detected in those holdouts.

These are the recorded earlier operator measurements using AITER `f52deef`; they were not rerun after the latest vLLM main merge. Source versions and the unchanged original measurements are retained below.

## Accuracy And Correctness

**No score decrease was observed in the paired 200-question GSM8K subset.** The real DeepSeek-V4.1-Flash checkpoint loaded at TP8, with the selected backend verified on all 40 layers of every rank.

| Backend | Correct / 200 | Accuracy | Truncated | Empty / invalid |
|---|---:|---:|---:|---:|
| `triton_unfused` | 196 / 200 | 98.0% | 1 | 0 / 0 |
| `aiter_flydsl_mxfp4_bf16` | 197 / 200 | 98.5% | 1 | 0 / 0 |

Same first 200 test questions, 5-shot prompts, greedy seed 0, thinking disabled, batches of 8, max 512 output tokens. Both runs exited 0. Paired outcomes: 196 both correct, 3 both wrong, 1 gained, 0 lost; the same question was truncated. Text changed on 137 questions. This single subset run is **not bitwise equivalence, proof of lossless accuracy, or evidence of general accuracy improvement**; the full 1,319-question set was not run.

All 15 synthetic numerical cases and 24 sampled real-checkpoint layer cases passed their stated gates. Automatic dispatch had maximum NRMSE 0.3723% versus the pinned vLLM expert and 0.4111% versus the sampled FP32 reference. Real-layer NRMSE was 0.3619%-0.4125%. BF16 atomic accumulation is not bitwise deterministic.
