# [Bugfix][Kernel] Give float32 Triton attention and fused MoE float32 accuracy

[Upstream PR](https://github.com/vllm-project/vllm/pull/62600) · state: open · merged: False

## Original PR description



## Overview

Fixes #62582. The Triton unified attention (`TRITON_ATTN`), prefill attention and fused-MoE kernels run float32 `tl.dot` in TF32 on NVIDIA. This PR gives them float32 accuracy by default (3xTF32 on CUDA), matching the PyTorch float32 matmuls in vLLM.

## Claims

- With float32 operands, the three kernels match a float64 reference to float32 accuracy (6–7e-6 relative to output RMS, the same as torch float32) instead of TF32 accuracy (~1.6e-2).
- On CUDA this uses `input_precision="tf32x3"`, which costs 2.1–5.3x the TF32 kernel time on B200 and 2.0–3.4x on H100. `"ieee"` would cost 5.3–14.3x (B200) and 4.0–9.6x (H100) for the same accuracy. Other platforms use `"ieee"`.
- The precision follows `VLLM_FLOAT32_MATMUL_PRECISION` through `torch.get_float32_matmul_precision()`. The default `"highest"` gives float32 accuracy; `"high"` / `"medium"` restore the previous TF32 behavior and speed.
- No change for fp16/bf16/fp8 operands.

## Details

**Root cause.** `tl.dot` defaults to `input_precision="tf32"` for float32 operands on NVIDIA, and these call sites don't set it. PyTorch float32 matmuls in vLLM run in IEEE because the GPU worker calls `torch.set_float32_matmul_precision(VLLM_FLOAT32_MATMUL_PRECISION)` with the default `"highest"`, so a float32 model mixes IEEE matmuls with TF32 attention and MoE. When a model is served with `dtype="float32"`, vLLM selects `TRITON_ATTN`.

**Fix.** A small helper, `vllm.triton_utils.fp32_dot_precision(dtype)`, returns `"tf32x3"` on CUDA (`"ieee"` elsewhere) for float32 when torch's float32 matmul precision is `"highest"`, and `None` (Triton's default) otherwise. Each launcher passes it as an `IN_PRECISION` constexpr, the same pattern `prefix_prefill.py` already uses, and the same CUDA/non-CUDA split that `selective_state_update_replayssm_output_only.py` uses for `"tf32x3"`. In fused MoE only the unquantized and `int8_w8a16` branches take it, since those are the only ones that can see float32 operands. For fp32 query, the unified attention kernel casts K/V to float32, so all its dots are float32 x float32.

**Tradeoff.** Float32 models get slower attention and MoE kernels (table above). Users who want the old speed can set `VLLM_FLOAT32_MATMUL_PRECISION=high`. fp16/bf16 models are unaffected. Picking `"tf32x3"` over `"ieee"` on CUDA keeps the slowdown at 2–5x rather than 5–14x for the same measured accuracy.

**Not covered here.** `prefix_prefill.py` keeps its own Turing-only `"ieee"` logic; it could move to the helper in a follow-up. ROCm and XPU (`"ieee"`) were not tested.

**Duplicate check.** No open or closed PR references #62582. The related #55466 (batch-invariant matmul) and #61931 (fp32 MoE tile configs on SM89) touch different code.
