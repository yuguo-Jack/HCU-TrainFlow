# [Bugfix][Frontend] Apply stop strings only after reasoning ends

[Upstream PR](https://github.com/vllm-project/vllm/pull/62095) · state: open · merged: False

## Original PR description



## Overview

Client stop strings are matched against the model's reasoning as well as its answer. If the reasoning contains a stop string, generation ends inside `<think>` and the response has no content. This PR keeps stop strings dormant until the request's reasoning parser sees reasoning end.

Fixes #62085. Also fixes #53066, and item 3 of #58647.

## Claims

- On a server with `--reasoning-parser`, chat requests (`/v1/chat/completions`, `/v1/messages`) whose prompt leaves the model mid-reasoning no longer stop inside the reasoning. Stop strings still apply to the response that follows.
- A stop string has to start in the response. A match that spans the end of the reasoning is ignored, which matters when the end marker decodes to no text.
- No change for requests without stop strings, prompts that are not mid-reasoning (thinking disabled), servers without a reasoning parser, or endpoints that do not resolve reasoning state (`/v1/completions`, `/v1/responses`, offline `LLM`).

## Validation

**End to end:** DeepSeek-V4.1-Flash, TP=8 on H100, `--reasoning-parser deepseek_v41`. The repro from #62085 is a classifier prompt with `stop_sequences: ["</block>"]`; it is the same request Claude Code's auto-mode safety check sends.

| Request | `main` | This PR |
|---|---|---|
| `/v1/messages`, `stop_sequences: ["</block>"]` | 100/100 empty (stopped inside reasoning) | **50/50 `<block>no`** |
| `/v1/chat/completions`, `stop: ["</block>"]` | `content: null` | **20/20 `<block>no`**, reasoning kept |
| `/v1/chat/completions`, thinking disabled (control) | `<block>no` | 20/20 `<block>no` (stop still applies) |

## Details

**Root cause.** `BaseIncrementalDetokenizer.update()` runs `check_stop_strings` over all detokenized text. With think-in-prompt templates (DeepSeek-V4/V4.1, Qwen3, GLM, ...), that text starts inside the reasoning. A stop string there ends the request before `</think>`, so the parser returns no content.

**Design.** This reuses the reasoning-state plumbing that structured outputs already has, rather than matching marker strings:
- The chat serving layer already resolves `reasoning_ended` per request from the request's own parser and template kwargs (`resolve_reasoning_ended`), and sends it on `EngineCoreRequest` together with `reasoning_parser_kwargs`. Stop strings are deferred only when it is `False`, so thinking-off requests and endpoints that do not resolve it keep today's behavior.
- A new `ReasoningEndFinder` in `detokenizer.py` finds the end of reasoning in the output token ids. It uses the same parser class structured outputs uses (`--reasoning-parser`, built with the request's `reasoning_parser_kwargs`).
  - Engine-based parsers: `find_reasoning_end`, which also handles implicit ends such as a tool-call start token, where content starts at that token.
  - Legacy parsers: `is_reasoning_end_streaming`.
- Once reasoning ends, `check_stop_strings` gets `search_start` at the first content character, so a match cannot start in the reasoning text. `min_tokens` and dropping overflow tokens after a stop are unchanged.
- `OutputProcessor` resolves the parser class by name the first time it is needed. Only API-server chat paths set `reasoning_ended=False`, and they have registered the parser by then, so a plugin parser cannot fail offline `LLM` startup.

**Cost.** Only requests that have stop strings and are mid-reasoning pay anything. On DeepSeek-V4.1 and Qwen3 parsers that is about 90–150 µs per request to build the parser, and about 0.7 µs per decode step until reasoning ends. There is no change to the model runner or scheduler, and no GPU work.

**Behavior change.** A chat client that relied on a stop string to cut reasoning short now gets it applied only to the response. This matches the OpenAI and Anthropic APIs, where stop sequences apply to the output text.

**Limitations.**
- `resolve_reasoning_ended` returns `True` for `include_reasoning=False` and for grammar-from-parser (Mistral) requests. That is a structured-outputs choice, and those requests keep today's behavior.
- `/v1/responses` does not resolve reasoning state yet.

**Related PRs.** #52486 and #38533 also target this.
- #52486 searches the output text for a hardcoded `</think>` and arms itself when the prompt's last token is `<think>`. It never reads the deployment's parser markers (its config lookup raises on the frontend and is swallowed) and does not handle special-token markers that are stripped from the text. It also conflicts with the current `update()`.
- #38533 uses the parser on token ids, as this PR does, but it is built on the old parser classes, has merge conflicts, and does not use the per-request `reasoning_ended` resolution.

Independent reproduction and confirmation, on a second model and a multi-rank layout.

**Repro** (vLLM at `e68efc685`, Qwen/Qwen3.5-2B, `--reasoning-parser qwen3`, `--data-parallel-size 4`, two nodes, 4 ranks each): a chat request with thinking on and a client `stop` string that the model happens to emit while still reasoning returns

```
finish_reason: "stop", content: "", reasoning_content: <truncated, never reaches the end marker>
```

so the caller gets a successful response with no answer at all. Identical on both nodes. We found it with a conformance check that asserts a stop string only applies to content, which is how we noticed it is not model-specific: it is the detokenizer applying `stop` to the whole token stream.

**With this PR** the same request returns the answer, and the stop string still terminates content as before.

- Applies cleanly on `e68efc685` (`git apply --3way`, all 5 files).
- This PR's own test file: **43 passed**. Disabling just the finder (`self._reasoning_end_finder = None`) fails **exactly the 8 new cases**, so the tests are pinning the behaviour they claim to.
- `tests/detokenizer` and `tests/v1/engine/test_output_processor.py`: identical results patched vs unpatched (only pre-existing failures from gated HF repos and no GPU).

**Why the approach looks right to us**, having compared it with #52486: resolving the reasoning end through the request's own reasoning parser over output token ids handles markers that decode to no text and multi-token chunks from speculative decoding, and arming only when the serving layer already resolved `reasoning_ended=False` leaves thinking-off requests, servers with no reasoning parser, `/v1/completions` and offline `LLM` on today's path. A hardcoded `</think>` search armed off `prompt_token_ids[-1]` misses other marker sets and breaks when the chat template appends a newline after the marker.

We are carrying this patch downstream until it lands. Happy to run further cases if that helps move it out of draft.

Arming on `reasoning_ended is False` causes three problems (CPU repro below):

1. **Legacy parsers whose end check needs streaming state never re-enable stop strings**, so a stop string in the answer never fires. The finder's [fresh parser copy](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/v1/engine/detokenizer.py#L63-L66) is never fed by `extract_reasoning_streaming`. Affected: `hunyuan_a13b` ([state starts as `"idle"`](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/reasoning/hunyuan_a13b_reasoning_parser.py#L72-L81), so every chat request, thinking off too), `muse_glimmer` ([ends only on a tool channel](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/reasoning/muse_glimmer_reasoning_parser.py#L138-L152)), and, from reading the code, `minimax_m3` with `thinking_mode: "enabled"`. Stateless parsers like `deepseek_r1` are fine, so arming only for those and for engine parsers with `reasoning_end_token_ids` would avoid it.
2. **Gemma 4 with thinking on, answer without a thought channel:** [`wait_for_reasoning=True`](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/parser/gemma4.py#L358-L361) makes `reasoning_ended=False`, but the output starts in content and no `<channel|>` ever comes. For parsers that start in `CONTENT`, holding stop strings only after the reasoning start token would also keep the case where the model opens its own channel working.
3. **`include_reasoning=False` and `/v1/responses` still stop inside the reasoning** ([`True`](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/entrypoints/openai/chat_completion/protocol.py#L611-L612), [`None`](https://github.com/vllm-project/vllm/blob/d5b4e80f73d71459d10fa88406cf4f70dce0c7c6/vllm/entrypoints/openai/responses/serving.py#L529)). Both set `reasoning_parser_kwargs`, so arming on it would cover them.

import inspect

from vllm.reasoning import ReasoningParserManager
from vllm.sampling_params import RequestOutputKind, SamplingParams
from vllm.tokenizers import get_tokenizer
from vllm.v1.engine import EngineCoreOutput, EngineCoreRequest
from vllm.v1.engine.output_processor import OutputProcessor


def run(tokenizer, parser_name, ctk, prompt, output, route):
    prompt_ids = tokenizer.encode(prompt, add_special_tokens=False)
    if route == "chat":
        reasoner_cls = ReasoningParserManager.get_reasoning_parser(parser_name)
        reasoner = reasoner_cls(tokenizer, chat_template_kwargs=ctk)
        reasoning_ended = reasoner.is_reasoning_end(prompt_ids)
    elif route == "chat, include_reasoning=False":
        reasoning_ended = True
    else:  # /v1/responses
        reasoning_ended = None
    kwargs = {}
    if "reasoning_parser" in inspect.signature(OutputProcessor.__init__).parameters:
        kwargs["reasoning_parser"] = parser_name
    processor = OutputProcessor(tokenizer, log_stats=False, **kwargs)
    request = EngineCoreRequest(
        request_id="r-int",
        external_req_id="r",
        prompt_token_ids=prompt_ids,
        mm_features=None,
        arrival_time=0,
        lora_request=None,
        cache_salt=None,
        data_parallel_rank=None,
        sampling_params=SamplingParams(
            skip_special_tokens=False,
            output_kind=RequestOutputKind.FINAL_ONLY,
            stop=["</block>"],
        ),
        pooling_params=None,
        reasoning_ended=reasoning_ended,
        reasoning_parser_kwargs={"chat_template_kwargs": ctk},
    )
    processor.add_request(request, None)
    for token_id in tokenizer.encode(output, add_special_tokens=False):
        outputs = processor.process_outputs(
            [EngineCoreOutput(request_id="r-int", new_token_ids=[token_id])]
        ).request_outputs
        if outputs:
            return f"stopped: {outputs[0].outputs[0].text!r}"
    return "stop string never fired"


qwen3 = get_tokenizer("Qwen/Qwen3-0.6B")
qwen3_prompt = "<|im_start|>user\nhi<|im_end|>\n<|im_start|>assistant\n<think>\n"
qwen3_output = "Output <block>no</block>.</think>\n\n<block>no</block> Done."
gemma4 = get_tokenizer("google/gemma-4-E2B-it")

cases = [
    ("qwen3", qwen3, "qwen3", {}, qwen3_prompt, qwen3_output,
     "chat, include_reasoning=False"),
    ("qwen3", qwen3, "qwen3", {}, qwen3_prompt, qwen3_output, "/v1/responses"),
    ("gemma4", gemma4, "gemma4", {"enable_thinking": True},
     "<|turn>user\nhi<turn|>\n<|turn>model\n", "<block>no</block> Done. More.",
     "chat"),
    ("hunyuan_a13b", get_tokenizer("tencent/Hunyuan-A13B-Instruct",
                                   trust_remote_code=True),
     "hunyuan_a13b", {}, "hi",
     "<think>\nok\n</think>\n<answer>\n<block>no</block>\n</answer>", "chat"),
    ("muse_glimmer", get_tokenizer("RedHatAI/Muse-Glimmer-30B-FP8-block"),
     "muse_glimmer", {}, "<|start|>user<|message|>hi<|eot|><|start|>assistant",
     " to=self<|message|>Think ok.<|eom|><|start|>assistant to=user<|message|>"
     "<block>no</block> Done.<|eot|>", "chat"),
]
for label, tokenizer, parser_name, ctk, prompt, output, route in cases:
    print(f"{label} [{route}]:", run(tokenizer, parser_name, ctk, prompt, output, route))
