# [Bugfix][Frontend] Apply stop strings only after reasoning ends

[Upstream PR](https://github.com/vllm-project/vllm/pull/62095) · state: open · merged: False

## Original PR description



## Overview

Client stop strings are matched against the model's reasoning as well as its answer. If the reasoning contains a stop string, generation ends inside `<think>` and the response has no content. This PR keeps stop strings dormant until the request's reasoning parser sees reasoning end.

Fixes #62085. Also fixes #53066, and item 3 of #58647.

## Claims

- On a server with `--reasoning-parser`, chat requests (`/v1/chat/completions`, `/v1/messages`) whose prompt leaves the model mid-reasoning no longer stop inside the reasoning. Stop strings still apply to the response that follows.
- A stop string has to start in the response. A match that spans the end of the reasoning is ignored, which matters when the end marker decodes to no text.
- No change for requests without stop strings, prompts that are not mid-reasoning (thinking disabled), servers without a reasoning parser, or endpoints that do not resolve reasoning state (`/v1/completions`, `/v1/responses`, offline `LLM`).

## Validation

**End to end:** DeepSeek-V4.1-Flash, TP=8 on H100, `--reasoning-parser deepseek_v41`. The repro from #62085 is a classifier prompt with `stop_sequences: ["</block>"]`; it is the same request Claude Code's auto-mode safety check sends.

| Request | `main` | This PR |
|---|---|---|
| `/v1/messages`, `stop_sequences: ["</block>"]` | 100/100 empty (stopped inside reasoning) | **50/50 `<block>no`** |
| `/v1/chat/completions`, `stop: ["</block>"]` | `content: null` | **20/20 `<block>no`**, reasoning kept |
| `/v1/chat/completions`, thinking disabled (control) | `<block>no` | 20/20 `<block>no` (stop still applies) |

## Details

**Root cause.** `BaseIncrementalDetokenizer.update()` runs `check_stop_strings` over all detokenized text. With think-in-prompt templates (DeepSeek-V4/V4.1, Qwen3, GLM, ...), that text starts inside the reasoning. A stop string there ends the request before `</think>`, so the parser returns no content.

**Design.** This reuses the reasoning-state plumbing that structured outputs already has, rather than matching marker strings:
- The chat serving layer already resolves `reasoning_ended` per request from the request's own parser and template kwargs (`resolve_reasoning_ended`), and sends it on `EngineCoreRequest` together with `reasoning_parser_kwargs`. Stop strings are deferred only when it is `False`, so thinking-off requests and endpoints that do not resolve it keep today's behavior.
- A new `ReasoningEndFinder` in `detokenizer.py` finds the end of reasoning in the output token ids. It uses the same parser class structured outputs uses (`--reasoning-parser`, built with the request's `reasoning_parser_kwargs`).
  - Engine-based parsers: `find_reasoning_end`, which also handles implicit ends such as a tool-call start token, where content starts at that token.
  - Legacy parsers: `is_reasoning_end_streaming`.
- Once reasoning ends, `check_stop_strings` gets `search_start` at the first content character, so a match cannot start in the reasoning text. `min_tokens` and dropping overflow tokens after a stop are unchanged.
- `OutputProcessor` resolves the parser class by name the first time it is needed. Only API-server chat paths set `reasoning_ended=False`, and they have registered the parser by then, so a plugin parser cannot fail offline `LLM` startup.

**Cost.** Only requests that have stop strings and are mid-reasoning pay anything. On DeepSeek-V4.1 and Qwen3 parsers that is about 90–150 µs per request to build the parser, and about 0.7 µs per decode step until reasoning ends. There is no change to the model runner or scheduler, and no GPU work.

**Behavior change.** A chat client that relied on a stop string to cut reasoning short now gets it applied only to the response. This matches the OpenAI and Anthropic APIs, where stop sequences apply to the output text.

**Limitations.**
- `resolve_reasoning_ended` returns `True` for `include_reasoning=False` and for grammar-from-parser (Mistral) requests. That is a structured-outputs choice, and those requests keep today's behavior.
- `/v1/responses` does not resolve reasoning state yet.

**Related PRs.** #52486 and #38533 also target this.
- #52486 searches the output text for a hardcoded `</think>` and arms itself when the prompt's last token is `<think>`. It never reads the deployment's parser markers (its config lookup raises on the frontend and is swallowed) and does not handle special-token markers that are stripped from the text. It also conflicts with the current `update()`.
- #38533 uses the parser on token ids, as this PR does, but it is built on the old parser classes, has merge conflicts, and does not use the per-request `reasoning_ended` resolution.
