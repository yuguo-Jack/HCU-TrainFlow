# [CI/Build] Rebuild lmcache against the image's torch

[Upstream PR](https://github.com/vllm-project/vllm/pull/65246) · state: open · merged: False

## Original PR description



## Overview

The `vllm/vllm-openai:v0.33.0` image ships an `lmcache` wheel built for torch 2.13 on torch 2.14. `lmcache.cuda_ops` fails to load, so KV offloading falls back or fails. This rebuilds `lmcache` against the installed torch, only when the import fails.

Fixes #53424. Supersedes #53441 (thanks @mehrdadbn9), which is stale against the current Dockerfile.

## Claims

- `import torch, lmcache.cuda_ops` succeeds in the built image.
- No rebuild when the wheel already matches torch.
- The build fails if the rebuilt extension still does not load.

## Validation

Published image (amd64 `sha256:91ee972ab751fb7180bc71c175865e36b091686600dca783d52b2511399810b3`):

```console
$ docker run --rm --entrypoint python3 vllm/vllm-openai:v0.33.0 -c "import torch, lmcache.cuda_ops"
ImportError: .../lmcache/cuda_ops.cpython-312-x86_64-linux-gnu.so: undefined symbol: _ZN3c104cuda29c10_cuda_check_implementationEiPKcS2_jb
```

The new Dockerfile block, run on that image on a native amd64 node (16 CPU, `CUDA_MAJOR=13`):

```console
      Built lmcache==0.5.6
Prepared 1 package in 8m 09s
 ~ lmcache==0.5.6
$ python3 -c "import torch, lmcache.cuda_ops, lmcache.lmcache_fs, lmcache.lmcache_native, lmcache.lmcache_redis; print(torch.__version__)"
2.14.0+cu130
```

- `pip freeze` differs only by the added `grpcio-tools==1.78.0`.
- A wheel built the same way has served GLM-5.3-Flash on H100 and B200, with LMCache host-cache store and reload checked.
- `pre-commit` and `shellcheck` pass on both files.
- Not run: a full `docker build`.

## Details

**Root cause:** the `lmcache` sdist pins `torch==2.13.0` for its build, and its wheels link private c10 symbols, so they load only on that torch. The existing `--no-build` fallback never runs: the wheel installs fine and fails only at import.

**Fix:** if the import fails, install the CUDA sparse/solver headers and `grpcio-tools` (matching `grpcio`), rebuild the same `lmcache` version with `--no-build-isolation`, recheck the import, then purge the headers. `LMCACHE_CUDA_MAJOR` follows `CUDA_MAJOR`. `.buildkite/scripts/install-kv-connectors.sh` gets the same logic.

**Why not #53441:** it always builds from source, hardcodes `lmcache >= 0.3.9`, has no import check, and targets an older Dockerfile.

**Trade-offs:** about 8 minutes on 16 CPUs, only on mismatched builds; `grpcio-tools` stays installed. The rebuild stops on its own once LMCache ships wheels for vLLM's torch.
