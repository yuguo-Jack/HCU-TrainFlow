# [Perf][MoE] Fuse padding skipping in grouped and Muse prepared routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/64955) · state: closed · merged: True

## Original PR description

## Overview

Skip CUDA-graph padding in Muse Spark's prepared NVFP4 routing path, and fuse existing grouped-routing padding masks into the CUDA top-k kernels. Padding produces `-1` expert IDs and zero weights without separate CUDA masking launches.

## Claims

- Muse's prepared TRT-LLM path now supplies its native padding mask to the existing fused router. The backend-specific fast path and matching-layout check gate this behavior.
- Grouped routing retains its existing backend opt-in and handles padding in all four CUDA kernel families. Existing XPU/AITER interfaces remain compatible.
- Eight isolated grouped-routing cases reduce five kernel launches to one, with 43.34–70.06% lower median operation span. This is not a whole-model speedup claim.

## Validation

- Isolated SM100 `_moe_C_stable_libtorch` build and all pre-commit hooks: passed.
- `.venv/bin/python -m pytest tests/kernels/moe/test_grouped_topk.py tests/kernels/moe/test_muse_spark_router.py -q`: **632 passed** on GB200.
- Five selected downstream sentinel test functions, including invalid expert IDs and poisoned finalizer slots: **27 passed**. Exact commands are in the [validation receipt](https://github.com/Inferact/vllm-perf-data/blob/main/research/moe-padding/2026-11-01/grouped-routing/validation.json).
- Five existing CPU Muse router tests: passed.

| Check | Result |
|---|---|
| Grouped routing, 8/128 tokens, four kernel families | Exact output parity; 43.34–70.06% lower isolated span; five kernels → one |
| Real-weight Muse, 100K KV, TP4/EP4, same instrumented graph | N7 mask off/on: 10.857728 → 9.822160 ms; N8 control: 10.006304 → 10.005904 ms |
| Actual parent vs patch, same rebuilt binary and identical real inputs/KV history | 16 active outputs and 2,880 active routing tensors byte-identical; patched padding IDs/weights exactly `-1`/zero |

[Grouped benchmark, all raw samples and traces](https://github.com/Inferact/vllm-perf-data/tree/main/research/moe-padding/2026-11-01/grouped-routing) uses 100 CUPTI spans per arm, reversed orders and cold L2. The comparator uses the same rebuilt CUDA operation with explicit postmasks. GPU clocks were not locked.

[Muse measurements and actual-source parity evidence](https://github.com/Inferact/vllm-perf-data/tree/main/models/meta-models/Muse-Spark-Open-816B-A42B-NVFP4/gb200/decode-buckets/2026-11-01/padding-mask) have an explicit qualification: all measurement/correctness phases completed, but the diagnostic harness retained captured NCCL graphs and hung during shutdown. Those jobs remain **FAILED**; separate reviewed completed-phase validators and independent audits checked the saved results after owned cleanup. A tiny two-rank experiment reproduced retained-graph teardown waiting and normal shutdown after release. No successful full-model harness shutdown is claimed. The actual-source comparison has no accepted timing samples; the timing comparison uses an instrumented graph, not stock production before/after.

The old Muse helper also passed the NaN-padding test; no before-failing numerical bug is claimed for that helper. The actual-source baseline instead demonstrates the missing call-site mask: its padded rows retain expert assignments, while the patch invalidates them with exact active-output parity.

## Details

Muse's prepared path calls `_compute_routing` directly, bypassing the common router wrapper. Its routed TRT-LLM experts support negative expert IDs. The mask is passed only on that prepared path; layout mismatches retain the existing behavior. The Triton fallback writes literal zero for padded weights, including when padded logits are nonfinite.

Grouped routing previously applied two `masked_fill` operations after routing; traces also show their two copy kernels. The optional mask is now consumed by the CUDA kernels. Rendered ModelOpt documentation, the generated environment reference, and CI source dependencies are updated.

Duplicate checks found no open Muse-specific or fused-grouped-padding PR. Related #50759 adds a generic fallback after `BaseRouter._compute_routing`; it misses Muse's direct prepared call and does not fuse the grouped kernels. This change addresses those distinct paths and preserves backend gates rather than adding blanket fallback masking. If #50759 merges first, its native-padding hook should recognize the grouped path to avoid applying a second mask.
