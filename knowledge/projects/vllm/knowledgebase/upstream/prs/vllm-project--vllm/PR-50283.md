# [Core] Add --enable-nan-fault-tolerance for NaN detection and request abort

[Upstream PR](https://github.com/vllm-project/vllm/pull/50283) · state: open · merged: False

## Original PR description

## Summary

- Adds `--enable-detect-nans-in-logits` CLI flag (replaces `VLLM_COMPUTE_NANS_IN_LOGITS` env var with a proper engine arg, keeps env var for backward compat)
- Adds `--enable-nan-fault-tolerance` CLI flag which implies `--enable-detect-nans-in-logits` and additionally:
  - **Aborts requests** when NaN values are detected in logits — during chunked prefill intermediate chunks, final chunks, or decode steps
  - **Forces KV cache block zeroing** on reuse (`needs_kv_cache_zeroing` returns `True`) to prevent stale NaN data from being read by subsequent requests
  - **Evicts the aborted request's blocks from the prefix cache** so a NaN-corrupted block that prefill committed to the cache cannot be matched (and read) as a prefix-cache hit by a later request with the same prefix
  - `delay_cache_blocks` keeps newly allocated GPU KV blocks out of prefix-cache lookups until the forward pass has written them and its logits have passed the NaN check.

Currently, `VLLM_COMPUTE_NANS_IN_LOGITS=1` only flags corrupted requests as a Prometheus metric (`vllm:corrupted_requests`). The request continues running to completion, meaning:

- Corrupted KV cache blocks can be reused via prefix caching
- NaN KV data gets offloaded to CPU/disk tiers
- In disaggregated PD, corrupted KV is transferred per-layer to decode instances via NIXL before the NaN is even detected in logits

This PR adds a fault-tolerance mode that aborts requests on NaN detection and zeroes freed blocks on reallocation, preventing corruption from propagating.

## Known Limitations

- **Logits-only detection:** corrupted KV can go undetected if checked logits remain finite.
- **CPU/disk offloading:** `delay_cache_blocks` gates GPU prefix publication only. Aborts do not invalidate offloaded copies, so subsequent requests can repeatedly reload corrupted KV.
- **Limited GPU eviction:** only the failed request's attached blocks are evicted. Historical copies and KV already consumed by other running requests are not comprehensively invalidated; zeroing happens on block reallocation.
- **NIXL:** KV may reach the decode instance before detection; aborting the producer cannot recall it.
- **Async Mamba/hybrid checkpoints:** delayed publication can use a later chunk's checkpoint metadata prematurely and trigger an assertion. This is independent of offloading and was reproduced with CPU-side metadata, not an end-to-end GPU run.

## End-to-end testing guide

Verified on the default (V2) GPU model runner with **async scheduling** using `Qwen/Qwen2-0.5B`. A healthy model rarely emits NaN logits on demand, so both tests use a one-line debug edit to force a NaN, then observe the two behaviors the flag controls: (A) the request is **aborted**, and (B) the freed KV blocks are **zeroed on reuse**.

### Part A — NaN in logits aborts the request

**1. Force a NaN.** In `vllm/v1/worker/gpu/sample/sampler.py`, inside `Sampler.__call__`, add one line immediately before:

```python
        num_nans = get_num_nans(logits) if self.compute_nans else None
```

so it reads:

```python
        logits[-1, 0] = float("nan")  # debug: force a NaN
        num_nans = get_num_nans(logits) if self.compute_nans else None
```

**2. Start the server** (async scheduling on):

```bash
vllm serve Qwen/Qwen2-0.5B \
    --enable-nan-fault-tolerance \
    --async-scheduling \
    --max-model-len 2048
```

The startup config confirms the implication: `enable_detect_nans_in_logits=True, enable_nan_fault_tolerance=True`.

**3. Send a request:**

```bash
curl -s -w '\nHTTP=%{http_code}\n' http://localhost:8000/v1/completions \
    -H 'Content-Type: application/json' \
    -d '{"model":"Qwen/Qwen2-0.5B","prompt":"The capital of France is","max_tokens":20,"temperature":0}'
```

Expected — the request is aborted instead of returning a (corrupt) completion:

```
HTTP=500
# engine log:
WARNING [scheduler.py] Request <id> aborted: 1 NaN values in logits
```

**Control:** restart the same server **without** `--enable-nan-fault-tolerance` (keeping the debug line). In this build, `enable_detect_nans_in_logits=False` without the flag, so the injected NaN is not detected and the identical request returns `HTTP=200` with a normal completion.

### Part B — freed KV blocks are zeroed on reuse

The flag also makes `needs_kv_cache_zeroing` return `True`, so every block is zeroed when it is (re)allocated to a request — the block a NaN-aborted request wrote is wiped before another request can reuse it. It does **not** zero the whole KV cache (that would be prohibitively expensive); it zeroes exactly the blocks each request touches, at allocation time.

**1. Observe the zeroing.** In `vllm/v1/worker/utils.py`, add a print at the top of `KVBlockZeroer.zero_block_ids`:

```python
    def zero_block_ids(self, block_ids: list[int]) -> None:
        """Zero the KV cache memory for the given block IDs."""
        print(f"[kv-zero] zeroing {len(block_ids)} block(s): {block_ids[:8]}", flush=True)  # debug
        if not block_ids or self._meta is None:
            return
```

**2. Serve with the flag** (keep the Part A NaN injection so requests abort and free their blocks):

```bash
vllm serve Qwen/Qwen2-0.5B --enable-nan-fault-tolerance --async-scheduling --max-model-len 2048
```

**3. Send a short and a long prompt:**

```bash
# short prompt (fits in one 16-token block)
curl -s -o /dev/null http://localhost:8000/v1/completions -H 'Content-Type: application/json' \
    -d '{"model":"Qwen/Qwen2-0.5B","prompt":"The capital of France is","max_tokens":20,"temperature":0}'

# long prompt (spans several blocks)
curl -s -o /dev/null http://localhost:8000/v1/completions -H 'Content-Type: application/json' \
    -d '{"model":"Qwen/Qwen2-0.5B","prompt":"Please summarize in great detail the following passage and then continue the narrative: once upon a time in a distant kingdom by the sea there lived a wise old scholar who studied the stars and the tides","max_tokens":16,"temperature":0}'
```

Expected — the number of zeroed blocks scales with each request's block footprint (block 0 is the reserved null block, so allocation starts at block 1). Each aborted request frees its blocks, and the next request re-zeroes them on reallocation:

```
[kv-zero] zeroing 1 block(s): [1]              # short prompt
[kv-zero] zeroing 4 block(s): [1, 2, 3, 4]     # long prompt
```

**Control:** restart **without** `--enable-nan-fault-tolerance`. `needs_kv_cache_zeroing` is `False`, so `[kv-zero]` never prints — no blocks are zeroed and requests complete normally.

### Part C — an aborted request's blocks are evicted from the prefix cache

This is the correctness case the eviction closes: prefill commits a full block to the prefix cache **at schedule time, before the forward writes KV**. If that forward produces NaN, the block is already matchable. The abort must evict it, or a later request with the same prefix would reuse the NaN KV as a cache hit (hits are never re-zeroed).

To make the NaN fire on a *real* request (not warmup, which also runs the sampler), arm it from a file instead of the always-on line in Part A. In `Sampler.__call__`, immediately before the `num_nans = ...` line:

```python
        import os as _dbg_os
        if _dbg_os.path.exists("/tmp/arm_nan"):
            _dbg_os.remove("/tmp/arm_nan")
            logits[-1, 0] = float("nan")  # debug: one real-request NaN
```

Add a log line at the top of `KVCacheManager.get_computed_blocks` to observe prefix-cache reuse, and one in `BlockPool.evict_blocks`:

```python
# get_computed_blocks, right before `return blocks, num_new_computed_tokens, ...`
        print(f"[prefix-hit] req={request.request_id} new_computed_tokens={num_new_computed_tokens}", flush=True)
# evict_blocks, first line
        print(f"[evict] block_ids={sorted(block_ids)}", flush=True)
```

Serve with the flag, then send the **same** prompt twice — the first arms and aborts, the second reuses (or, with the fix, does not):

```bash
vllm serve Qwen/Qwen2-0.5B --enable-nan-fault-tolerance --async-scheduling --max-model-len 2048

P="The capital of France is Paris and the capital of Germany is Berlin and the capital of Italy is Rome and the capital of Spain is"
touch /tmp/arm_nan
curl -s -w '\nHTTP=%{http_code}\n' http://localhost:8000/v1/completions -H 'Content-Type: application/json' \
    -d "{\"model\":\"Qwen/Qwen2-0.5B\",\"prompt\":\"$P\",\"max_tokens\":10,\"temperature\":0}"   # request #1
curl -s -w '\nHTTP=%{http_code}\n' http://localhost:8000/v1/completions -H 'Content-Type: application/json' \
    -d "{\"model\":\"Qwen/Qwen2-0.5B\",\"prompt\":\"$P\",\"max_tokens\":10,\"temperature\":0}"   # request #2
```

Expected — request #1 aborts (`HTTP=500`), its blocks are evicted, and request #2 gets **no** prefix-cache reuse of the NaN block:

```
[dbg-nan] ...                         # on request #1's forward
WARNING [scheduler.py] Request <id-1> aborted: 1 NaN values in logits
[evict] block_ids=[1, 2]              # NaN block(s) evicted from the prefix cache
[prefix-hit] req=<id-2> new_computed_tokens=0   # request #2 recomputes; does NOT reuse the NaN block
HTTP=200                              # request #2 completes cleanly
```

**Control:** temporarily disable the eviction (`if False and nan_block_ids:`). `[evict]` no longer prints and request #2 shows `new_computed_tokens=16` — it matches and reuses the block request #1 wrote during the NaN step. That reuse is exactly what the eviction prevents.

- fangyuchu · comment · 2026-08-03T04:07:41Z · [source](https://github.com/vllm-project/vllm/pull/50283#issuecomment-5162177310)

The overall design makes sense to me. I have two questions:

## 1. A (small) race window between schedule-time prefix-cache commit and output-time NaN detection

Full blocks are committed to the prefix cache at schedule time — before the forward writes their KV — while NaN detection only happens when that step's output is processed. With async scheduling, this interleaving is possible:

1. `schedule(N)`: A will fill block X this step → X becomes matchable in the prefix cache (KV not yet written).
2. `forward(N)`: A writes NaN KV into X.
3. `schedule(N+1)`: B gets a prefix-cache hit on X — `output(N)` hasn't been processed yet, so nobody knows X is corrupt.
4. `forward(N+1)`: B reads the NaN KV. Cache-hit blocks are never zeroed (they're not new allocations), so the zero-on-reallocation defense doesn't apply on this path.

My understanding is that this is largely self-containing: B's new tokens attend to every position of X, so the NaN almost certainly propagates into B's own logits. But could there be cases where B's KV cache gets corrupted while no NaN ever shows up in its logits? 

## 2. Could the KV-zeroing logic be abstracted for reuse by fault-tolerance recovery?

We're working on another scenario with similar problem: retry-after-failure with KV reuse, so a request can resume generation from its existing KV after a fault instead of recomputing from scratch ([<!-- link to retry PR -->](https://github.com/vllm-project/vllm/pull/50265)). One problem we're thinking about is very similar in shape to yours: when a DP/EP rank fails mid-step, the KV written for the in-flight token (e.g., the last token of the last block) can be corrupt on the surviving ranks — NaN or plain garbage — and we need to wipe precisely that KV before resuming. The fault cause differs (numerical NaN vs. rank failure), but the cleanup primitive is the same.

Your zeroing logic is close to what we'd need, but it's currently tied to the allocation-time path (whole blocks, driven by `new_block_ids_to_zero` in `SchedulerOutput`). Do you think the zeroing mechanism could be factored into a reusable, on-demand function — e.g., `zero_last_block_kv(self,request)` — so that a fault-recovery path can call it to thoroughly zero the KV of the corrupted token(s) after a fault is detected, whatever the cause?
