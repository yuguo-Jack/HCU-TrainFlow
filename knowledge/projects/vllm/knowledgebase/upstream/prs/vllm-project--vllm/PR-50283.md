# [Core] Add --enable-nan-fault-tolerance for NaN detection and request abort

[Upstream PR](https://github.com/vllm-project/vllm/pull/50283) · state: open · merged: False

## Original PR description

## Overview

Add `--enable-nan-fault-tolerance` for MRV2: abort on NaN logits and withhold the unchecked chunk from GPU prefix reuse and CPU offloading. Earlier validated prefixes stay reusable.

This consolidates [fork PR #5](https://github.com/elvircrn/vllm/pull/5) into this PR. The other open NaN fixes address individual kernels; this adds engine-level recovery.

## Claims

- `--enable-detect-nans-in-logits` exposes detection as an engine argument, retaining the legacy environment variable. Fault tolerance implies detection and requires MRV2.
- Check intermediate prefill, final prefill, and decode logits before publishing new KV. Abort the failing request without evicting earlier validated chunks.
- Delay `OffloadingConnector` and eager `SimpleCPUOffloadConnector` stores until validation. SimpleCPU lazy mode already selects published GPU blocks. No additional GPU-to-CPU status readbacks or KV scans.
- Zero newly allocated GPU blocks on reuse. Reject NaN fault tolerance at startup for Mamba-style models; NaN detection alone remains available.

## Validation

Rebased onto upstream main `0c2584929`. Preserves upstream speculative-stop accounting and offload-manager locking; NaN metrics work with engine arguments even when the legacy environment flag is off.

CPU-only scheduler regressions cover sync/async prefill, first/later chunk failures, eager/lazy offloading, late copy acknowledgements, and clean completion. The Mamba checkpoint change and its regression test have been removed.

Before this change, **739 passed, 2 skipped** across the affected scheduler, cache-manager, offload-worker, CPU-manager, and tier-manager suites. For the Mamba exclusion, four targeted configuration tests passed, and Ruff and diff checks passed. The full CPU suite has not been rerun after this change; no model or GPU kernels ran.

## Details

Scheduling advances computed-token counts before outputs arrive. Stores now stop at the completed-token boundary; GPU publication already waits for the logits check. A failed chunk stays unpublished, while earlier validated blocks can finish offloading and remain cache hits. Retries recompute the missing suffix normally.

### Known limitations

- **Mamba-style models:** NaN fault tolerance is rejected at startup. NaN detection without fault tolerance remains available.
- **Logits only:** finite logits do not prove KV is uncorrupted; earlier cached prefixes are retained, not retrospectively scrubbed.
- **External KV:** NIXL and other connectors are not covered. Existing corrupt CPU/disk entries are not invalidated. Disk stores downstream of these offload gates inherit the same admission boundary.
- **Custom samplers:** must supply per-request NaN counts.
- **Cost:** intermediate-prefill logits, NaN checks, block zeroing, and delayed cache availability add overhead. This update has not been benchmarked.

- fangyuchu · comment · 2026-08-03T04:07:41Z · [source](https://github.com/vllm-project/vllm/pull/50283#issuecomment-5162177310)

The overall design makes sense to me. I have two questions:

## 1. A (small) race window between schedule-time prefix-cache commit and output-time NaN detection

Full blocks are committed to the prefix cache at schedule time — before the forward writes their KV — while NaN detection only happens when that step's output is processed. With async scheduling, this interleaving is possible:

1. `schedule(N)`: A will fill block X this step → X becomes matchable in the prefix cache (KV not yet written).
2. `forward(N)`: A writes NaN KV into X.
3. `schedule(N+1)`: B gets a prefix-cache hit on X — `output(N)` hasn't been processed yet, so nobody knows X is corrupt.
4. `forward(N+1)`: B reads the NaN KV. Cache-hit blocks are never zeroed (they're not new allocations), so the zero-on-reallocation defense doesn't apply on this path.

My understanding is that this is largely self-containing: B's new tokens attend to every position of X, so the NaN almost certainly propagates into B's own logits. But could there be cases where B's KV cache gets corrupted while no NaN ever shows up in its logits? 

## 2. Could the KV-zeroing logic be abstracted for reuse by fault-tolerance recovery?

We're working on another scenario with similar problem: retry-after-failure with KV reuse, so a request can resume generation from its existing KV after a fault instead of recomputing from scratch ([<!-- link to retry PR -->](https://github.com/vllm-project/vllm/pull/50265)). One problem we're thinking about is very similar in shape to yours: when a DP/EP rank fails mid-step, the KV written for the in-flight token (e.g., the last token of the last block) can be corrupt on the surviving ranks — NaN or plain garbage — and we need to wipe precisely that KV before resuming. The fault cause differs (numerical NaN vs. rank failure), but the cleanup primitive is the same.

Your zeroing logic is close to what we'd need, but it's currently tied to the allocation-time path (whole blocks, driven by `new_block_ids_to_zero` in `SchedulerOutput`). Do you think the zeroing mechanism could be factored into a reusable, on-demand function — e.g., `zero_last_block_kv(self,request)` — so that a fault-recovery path can call it to thoroughly zero the KV of the corrupted token(s) after a fault is detected, whatever the cause?
