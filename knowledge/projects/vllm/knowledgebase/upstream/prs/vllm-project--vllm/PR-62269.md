# [Bugfix][DSv4.1] Keep the Engram all-to-all buffers in one allocator

[Upstream PR](https://github.com/vllm-project/vllm/pull/62269) · state: closed · merged: True

## Original PR description



## Overview

DeepSeek-V4.1 with host-offloaded, DP-sharded Engram tables (`cpu_offload: true`, `dp_shared_memory: false`, e.g. with `use_thp: true`) hangs in the first forward (memory profiling) when `--enable-cumem-allocator` is set. This receives the Engram all-to-all into a persistent buffer allocated next to its send buffer, so both come from the same allocator.

No open PR covers this (searched open PRs/issues for Engram all-to-all, cumem, `NCCL_LOCAL_REGISTER`). #62091 changes only the GPU-table path (`cpu_offload: false`), which has no all-to-all.

## Claims

- Fixes the hang: DSv4.1-Flash DEP2/DEP4 prefill with host DP-sharded Engram + `--enable-cumem-allocator` now starts and serves.
- No numerical change: the same bytes are exchanged, only the receive buffer's allocation changes. Peak memory is unchanged (the per-step `empty_like` of the same size becomes persistent).

## Validation

GB200 (4 GPUs/node), vLLM nightly 49cb2bbf image (CUDA 13.4, NCCL 2.32.3), env `NCCL_CUMEM_ENABLE=1 NCCL_MNNVL_ENABLE=1 NCCL_NVLS_ENABLE=1`. The changed code is identical on main.

Serving: `vllm serve deepseek-ai/DeepSeek-V4.1-Flash --data-parallel-size 4 --enable-expert-parallel --enable-cumem-allocator --engram-config '{"cpu_offload":true,"embedding_across_dp":true,"use_thp":true}' --max-num-batched-tokens 32768 --kernel-config '{"moe_backend":"deep_gemm_mega_moe"}' ...` (same hang with DEP2).

## Details

Root cause: `EngramBatch.__init__` runs during model init, inside the cumem pool when `--enable-cumem-allocator` is set, so `packed_rows` (the all-to-all send buffer) is a cumem allocation. The receive buffer was `torch.empty_like(rows)` in each forward, from the caching allocator. With NCCL local user-buffer registration on (the default), NCCL 2.32 hangs an all-to-all whose buffers mix the two allocators; the reproducer shows this without the model. I did not pin down the NCCL-internal reason (the serving logs show FABRIC IPC registration failures for some buffers, the reproducer hangs without them).

Allocating the receive buffer next to `packed_rows` keeps both in one allocator in either mode, and removes a per-step allocation. `_stage` is an eager break, so the persistent buffer does not affect CUDA graphs.
