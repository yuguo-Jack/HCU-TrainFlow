# [ROCm][Perf][GLM-5.3-Flash] Split decodes off the AITER FlashKDA prefill on gfx950 (do not merge)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64243) · state: open · merged: False

## Original PR description

## Motivation

On GLM-5.3-Flash MXFP4 (TP4, MI355X/gfx950) with the AITER FlashKDA prefill route from #63568 (`--kda-prefill-backend flashkda`), the 34 KDA layers of the most common prefill step, one 8192-token chunk with 8-15 decodes, take 44.0 ms of the 135.8 ms step. FlashKDA's kernels take 15.95 ms of that: FlashKDA counts each decode as a sequence when it plans its recurrence, so it stops segmenting, and its last pass walks the prefill's 256 chunks one after another (410 us per layer). Outside the input and output projections, most of the rest is the q|k|v conv (85 us per layer), copies that pack q, k, g and v for FlashKDA (52 us per layer), and `f_b` and `g_b` as two GEMMs.

This PR, with [ROCm/aiter#7084](https://github.com/ROCm/aiter/pull/7084), takes those KDA layers from 44.00 to 32.20 ms per step (FlashKDA from 15.95 to 5.52 ms), and the step from 135.8 to 122.1 ms (-10.1%). Over nine serving points, output throughput is -0.2% to +9.4% (geomean +4.4%), median TPOT -0.2% to -7.7% (geomean -4.4%) and median TTFT -8.6% as a geomean. GPQA Diamond is 0.919 against the baseline's 0.909, GSM8K 0.915 against 0.918 over four runs each, and NIAH at 65536 is 1.0 in both.

## Modifications

- **A. Pass FlashKDA only the prefills:** FlashKDA 15.95 → 5.5 ms per common prefill step, and all 34 layers segment again.
- **B. Run `f_b` and `g_b` as one batched GEMM:** 310 → 176 us per decode step at batch 16.
- **C. Read strided q, k, g and v in place on gfx950** (AITER, [ROCm/aiter#7084](https://github.com/ROCm/aiter/pull/7084)): copies 52.2 → 5.5 us per layer, 1.6 ms per common prefill step.
- **D. Use AITER's HIP prefill conv on gfx950:** conv 85.1 → 72.1 us per layer, 0.44 ms per common prefill step.

**A. Pass FlashKDA only the prefills** (`kda.py`). FlashKDA plans its recurrence from the block count over all sequences in the call: [`_choose_chunks_per_seg`](https://github.com/ROCm/aiter/blob/1dd826c42b38aa71adf058053b9c512a9b47d20f/aiter/ops/triton/_triton_kernels/kimi_delta_attn/flash_kda.py#L1047-L1079) computes `blocks = n_seqs * H * max(1, V // 32)` and turns segmentation off when that exceeds the CU count. #63568 passes `non_spec_query_start_loc`, so each decode counts as a one-token sequence. At 16 KDA heads per rank each sequence is 64 blocks, so one prefill with four or more decodes passes 256 CUs, and with one to three decodes FlashKDA still segments but sizes the segments for the extra sequences. A mixed step now runs its leading decodes through the same `fused_recurrent_kda` call as a plain decode step, and passes FlashKDA only the prefills, with the metadata builder's prefill-only [`prefill_query_start_loc`, `prefill_state_indices` and `prefill_has_initial_state`](https://github.com/vllm-project/vllm/blob/41f5146b5b3a5b3c89ceee6f804e5e535a72ccbb/vllm/v1/attention/backends/gdn_attn.py#L122-L125). Both kernels update the paged recurrent state in place and write their slices straight into the layer output; [Kimi-K3's ROCm layer](https://github.com/vllm-project/vllm/blob/41f5146b5b3a5b3c89ceee6f804e5e535a72ccbb/vllm/models/kimi_k3/amd/kda.py#L651-L695) splits its decodes off the AITER prefill the same way. Steps with spec-decode tokens keep the Triton chunk path, as in #63568. The two kernels compute the same recurrence, so the outputs agree to bf16.

**B. Run `f_b` and `g_b` as one batched GEMM** (`kda.py`). `f_b` and `g_b` read adjacent column slices of the same projection, and launched one after the other: 4.5 and 4.6 us per layer at 16 decode tokens. When [`is_tgemm_enabled()`](https://github.com/waqahmed-amd-fi/vllm/blob/58caa1d025f04958507ce15fae125855f170c89f/vllm/_aiter_ops.py#L2641-L2644) is true (gfx950 with AITER linear) and both projections use `UnquantizedLinearMethod`, their weights are views of one `[2, N, K]` buffer, which loading fills in place, and forward runs one `torch.bmm` against it at every token count: one 5.2 us GEMM per layer at decode. At an 8192-token prefill the server's `bmm` takes 33.7 us per layer against 29.6 us for the two calls, about 0.14 ms per prefill step; a one-GPU run of the same call takes 28.3 us against 29.3 us. Quantized projections, and builds where AITER's tuned GEMM is off, keep the two linear calls.

**C. Read strided q, k, g and v in place on gfx950** (AITER only: [ROCm/aiter#7084](https://github.com/ROCm/aiter/pull/7084), commit [d24a8a87](https://github.com/ROCm/aiter/commit/d24a8a8743e68ccccac7c893197a5a2c1934549d)). vLLM passes q, k and v as column slices of the merged conv output, at a token stride of 3 × H × D. On gfx950 FlashKDA packed them, and g, before K1 and passes A and C, about 52 us per layer at 8192 tokens; the gfx1250 kernels already read them in place. The gfx950 K1 now takes `stride_q`, `stride_k` and `stride_g`, and passes A and C take `stride_v`. `flash_kda_fwd` decides each operand after the kernel routes are known, and still packs an operand that a Triton kernel reads, whose rows are not 16-byte aligned, or whose span needs more than 32-bit offsets. Strided inputs give the packed result bit for bit.

**D. Use AITER's HIP prefill conv on gfx950** (`kda.py`, `_aiter_ops.py`). vLLM's [`_causal_conv1d_fwd_kernel`](https://github.com/vllm-project/vllm/blob/41f5146b5b3a5b3c89ceee6f804e5e535a72ccbb/vllm/model_executor/layers/mamba/ops/causal_conv1d.py#L593-L633) runs the 6144-channel q|k|v conv in programs of 8 tokens by 256 channels, one bf16 per thread per token: 85 us per layer in the common prefill step, about 2.4 TB/s. A prefill step of 4096 tokens or more now calls AITER's HIP [`causal_conv1d_split_qkv_hip_fn`](https://github.com/ROCm/aiter/blob/1dd826c42b38aa71adf058053b9c512a9b47d20f/aiter/ops/causal_conv1d_fwd_split_qkv.py#L90-L112) through the new `rocm_aiter_ops.causal_conv1d_prefill_split_qkv()`. It takes `causal_conv1d_fn`'s inputs, updates the conv state the same way, and returns q, k and v as contiguous tensors. The HIP kernel reads bf16 weights, while the layer's conv parameters are fp32 holding the checkpoint's bf16 values, so the first forward makes a bf16 copy of the merged weight and keeps it only if it equals the fp32 weight (one `torch.equal` per layer, under `gpu_sync_allowed()`); weights with true fp32 values keep vLLM's kernel. The wrapper runs 32-token tiles and builds their (sequence, chunk) schedule on the host from the metadata's 8-token one, as ceil(ceil(n / 8) / 4) = ceil(n / 32), once per step and without a device-to-host read. It passes `has_initial_state` as a uint8 view, which saves [AITER's cast](https://github.com/ROCm/aiter/blob/1dd826c42b38aa71adf058053b9c512a9b47d20f/aiter/ops/causal_conv1d_fwd_split_qkv.py#L140), a 4.3 us kernel per layer. Steps under 4096 tokens keep vLLM's kernel, which is as fast there: 27.5 against 27.3 us at 2716 tokens and 10.7 against 10.8 us at 576, on one GPU. q, k and v match `causal_conv1d_fn` to one bf16 rounding, and the conv state exactly. [Kimi-K3's ROCm layer](https://github.com/vllm-project/vllm/blob/41f5146b5b3a5b3c89ceee6f804e5e535a72ccbb/vllm/models/kimi_k3/amd/kda.py#L601-L617) calls AITER's Triton tile kernel for the same op, which takes 108-200 us for GLM's 6144 channels on one GPU.

### Impact on CUDA and on Other AMD Architectures

No change reaches CUDA. On ROCm:

| change | runs when |
| --- | --- |
| A | the AITER FlashKDA prefill route runs (gfx950, `--kda-prefill-backend flashkda`) and the step has no spec-decode tokens |
| B | `is_tgemm_enabled()` (gfx950 with AITER linear) and both projections are unquantized |
| C | AITER's gfx950 FlashKDA Gluon kernels get strided q, k, g or v that they can read |
| D | gfx950 with AITER on and its HIP conv importable, a width-4 conv without bias, a bf16 conv state, conv weights that hold bf16 values, and a prefill step of 4096 tokens or more |

Everything else keeps today's path: the Triton chunk path, the CUDA FlashKDA backend, spec-decode steps, quantized `f_b` and `g_b`, packed FlashKDA inputs, gfx1250 and AITER's Triton FlashKDA kernels, and `causal_conv1d_fn`. C changes no vLLM code; its strided inputs give the packed result bit for bit.

## Accuracy Tests

GPQA Diamond with sglang `run_eval` (thinking on, 100000 max tokens, temperature 1, top-p 0.95), and RULER NIAH (`niah_single_2` at 65536) and GSM8K (5-shot, all 1319 questions, through the completions endpoint) with `lm_eval`, on the server of the serving sweep below. One run per arm for GPQA and NIAH, and four for GSM8K:

| | baseline | this PR |
| --- | ---: | ---: |
| GPQA Diamond | 0.909 | 0.919 |
| NIAH (`niah_single_2`, 65536) | 1.0 | 1.0 |
| GSM8K strict-match, mean of 4 runs (range) | 0.918 (0.904-0.926) | 0.915 (0.911-0.917) |
| GSM8K flexible-extract, mean of 4 runs (range) | 0.918 (0.904-0.926) | 0.915 (0.911-0.920) |

Over the three GSM8K runs per arm that logged every answer, 149 questions were right only with the baseline and 143 only with this PR (strict-match, sign test p = 0.77). Each arm's own reruns disagree on 80 to 92 questions, as many as the two arms do. One GPQA run's standard error is about 0.02.

### Unit Tests

```bash
# On gfx950 with VLLM_ROCM_USE_AITER=1
python -m pytest tests/models/glm5next/test_kda_recurrent.py

# C, from the AITER checkout
python -m pytest op_tests/triton_tests/kimi_delta_attn -q
```

`test_aiter_flashkda_prefill_matches_triton` runs with 0 and with 3 decodes ahead of two prefills, checks that FlashKDA receives only the prefill rows, and matches the Triton chunk path to bf16 (A). It runs with vLLM's conv, with AITER's, and with AITER's asked for on conv weights with true fp32 values, which must keep vLLM's kernel (D). `test_aiter_conv1d_prefill_matches_vllm` runs AITER's conv as the layer calls it, on a strided q|k|v block with both conv-state layouts, at 740 and 5040 tokens; it matches `causal_conv1d_fn` to bf16 and the conv state exactly, and checks the 32-token schedule built from vLLM's 8-token one (D). `test_aiter_decode_route_follows_replayed_step` checks that the AITER layer's `f_b` and `g_b` weights are views of one `[2, N, K]` buffer, and that a mixed step matches the two-GEMM layer bit for bit (B). On MI355X the file gives 17 passed and 14 skipped, the skips being NVIDIA-only tests. AITER's `op_tests/triton_tests/kimi_delta_attn` gives 157 passed and 1 skipped on gfx950; its `test_strided_operands_match_packed` checks that the gfx950 Gluon kernels read the projection bands in place and match packed inputs bit for bit (C). The tests for A and D need gfx950 and AITER and skip elsewhere, and the serving and accuracy runs below were done outside CI.

## Future Work

- AITER: plan segments from the sequences long enough to segment, so callers that keep decodes in the FlashKDA call do not lose segmentation.
- Pass the prefill-only host bounds to FlashKDA as `cu_seqlens_cpu` once [ROCm/aiter#6912](https://github.com/ROCm/aiter/pull/6912) lands, so AITER no longer reads `cu_seqlens` from the GPU in every KDA layer.
- Select AITER FlashKDA for `--kda-prefill-backend auto` on gfx950 when its checks pass.
- At prefill sizes, keep the two `f_b` and `g_b` calls, which are about 0.14 ms per prefill step faster there. A size check has to live in a custom op, because `torch.compile` freezes a Python branch.
