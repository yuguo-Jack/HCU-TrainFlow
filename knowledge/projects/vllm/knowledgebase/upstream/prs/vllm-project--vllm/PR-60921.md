# [Bugfix] Fix ExllamaLinearKernel wrong output for group sizes such as 16 and 96

[Upstream PR](https://github.com/vllm-project/vllm/pull/60921) · state: open · merged: False

## Original PR description

## Overview

Fixes #60608. On CUDA with fp16 activations, `ExllamaLinearKernel` is selected for GPTQ `uint4b8`/`uint8b128` weights at `group_size=16` and gives about 0.6 relative error. This PR keeps Exllama selected, but sends the group sizes that the exllama kernels cannot handle to the plain GPTQ kernels in the same `gptq_gemm` op.

## Claims

- `ExllamaLinearKernel` now gives correct output for every group size it accepts. Before, it was correct only for 32, 64, multiples of 128 and a single group. Now the worst fp16 error is 0.0013. Before, it was 0.18–1.2 at the other sizes.
- Nothing changes at run time for G = 32, 64, multiples of 128 or a single group. The same kernels run and give the same numbers.
- `can_implement` and kernel selection do not change. No config that loaded before is refused now.
- A new numerical test in `tests/kernels/quantization/test_gptq.py` fails on the old code.

## Validation

Setup: 1 x NVIDIA GeForce RTX 5080 (sm_120, 16 GB), vLLM `81198e97b` (`0.31.1rc1.dev88+g81198e97b`) and torch `2.13.0+cu130`. The reporter used an RTX 5060, which has the same SM.

**Reproducer.** This is the reporter's `exllama_g16_repro.py` from the issue, unchanged. It needs no model. It builds synthetic GPTQ layers and calls `choose_mp_linear_kernel` and each kernel's `apply_weights`. Then it prints the relative L2 error against an fp32 reference (K=512, N=256).

```
python exllama_g16_repro.py
```

Exllama is the selected kernel at G=16 with fp16, both before and after the fix. Relative error for M = 1 / 8 / 64:

| fp16, K=512, N=256 | Before | After |
|---|---|---|
| uint4b8, G=16 | 0.6064 / 0.6321 / 0.6209 | 0.0009 / 0.0008 / 0.0009 | | uint8b128, G=16 | 0.5656 / 0.5991 / 0.6090 | 0.0010 / 0.0010 / 0.0009 | | uint4b8, G=32 | 0.0005 / 0.0005 / 0.0009 | 0.0005 / 0.0005 / 0.0009 | | uint8b128, G=32 | 0.0008 / 0.0008 / 0.0009 | 0.0008 / 0.0008 / 0.0009 |

Before the fix, it ran 4 times: 3 in the `vllm/vllm-openai` nightly image for this commit and 1 in an editable install. All 4 runs printed the same numbers. After the fix, it ran 2 times on the patched tree. One of those runs was a separate check. Both runs gave the same numbers within 0.0001 (`atomicAdd` order). All other kernels in the output did not change.

**New test.**

```
pytest tests/kernels/quantization/test_gptq.py
```

- This PR: 74 passed (72 new cases and the 2 existing tests).
- Old `exllama.py` from `81198e97b`: 32 failed, 42 passed. These are all the G=16 and G=96 cases with M=4 or M=64.
- The test covers each part of the fix. With the padding turned off, the 8 cases with N=200 and M=4 fail. Without the empty-batch check, the 16 cases with M=0 at G=16 and G=96 fail with `CUDA error: invalid argument`.

**Wider probes (not added to the tree), with this PR:**

- Old and new kernel on the same data, for uint4b8 and uint8b128. G = 8 to 384 and G = K, K = 96 to 2752, N = 72 to 1000, 14 values of M from 1 to 200, and zero points both built by the kernel and loaded from a checkpoint. The worst error is 0.0013. The old code gives 0.18–1.2 for every G that is not 32, 64, a multiple of 128 or K.
- Through `CompressedTensorsWNA16` (which picks Exllama at G=16 with fp16), N=200: 0.0006–0.0011.
- CUDA graph capture and replay, a 3D input with bias, and `torch.compile` with a backed or unbacked batch dim: all correct.

`pre-commit` passes on both changed files.

## Details

**Root cause.** The exllama kernels in `csrc/libtorch_stable/quantization/gptq/q_gemm.cu` split K into blocks of 128 rows. They walk each block 32 rows at a time (`k += 32`) and load the next group's scales only when `k == offset_k + groupsize`. This is right only for G = 32, 64, multiples of 128 or a single group. At G=16, a whole block uses the scales of its first group. A reference built this way matches the kernel output to within 0.0005–0.0009. At G=96, 160 and 192, the group switch happens at the wrong row. `can_implement` accepts any G that divides K. On CUDA with fp16, no earlier kernel accepts these sizes, so Exllama is picked. The tensors passed to the op are correct: the same tensors give 0.0008–0.0010 error with `use_exllama=False`.

**Fix** (only `exllama.py` changes, +37/−5):

- `use_exllama = G in (32, 64) or G % 128 == 0 or G == partition K`. When this is true, nothing changes at run time.
- When it is false, the weight is not shuffled, and `gptq_gemm(..., use_exllama=False)` runs. Those kernels find the group of each K row separately, so they work for any G.
- The plain small-batch kernel (M ≤ 8) writes whole blocks of 128 output columns and has no bounds check. When N is not a multiple of 128 and 2 ≤ M ≤ 8, it writes into the next output row (NaN, or 0.4–1.0 error). To avoid this, the weight, the scales and the zero points are padded to a multiple of 128 output features, and the output is cut back to N. Checkpoint zero points are padded too, because the kernel takes their row stride from the padded width.
- For M=0, the plain launcher uses a zero-size grid, and CUDA rejects the launch. The exllama branch guards against this, so M=0 worked before. The plain path now returns an empty output. The check is `guard_or_false(x_2d.shape[0] == 0)`, so `torch.compile` with an unbacked batch dim still works.
- A single group stays on the exllama kernels. Quark W4A16 per-channel sends `group_size = input_size_per_partition`. On the plain path, that shape was up to 2.5x slower for M ≤ 16. For example, uint8b128 with K=G=2752 and M=8 took 36.7 µs on the plain path and takes 14.9 µs on the exllama path.

**Limitations:**

- The ROCm RDNA3 W4A16 kernels named in the issue are not changed. They are separate HIP ops with no path that works for any group size. No ROCm GPU was available to test a change there.
- M=0 in a compiled graph with an unbacked batch dim still reaches the failing launch. The full fix is `if (a.size(0) == 0) return c;` in the C++ `gptq_gemm`, which was not built or tested here. vLLM's model runner does not run a compiled graph with 0 tokens.
- K that is not a multiple of 32 is a separate problem in compiled code. It is the same before and after this PR.
- On the exllama path, `F.pad(x, (0, 0))` copies the weight once at load time.
- The speed of the plain path at G=16 was not compared with other kernels. No model-level eval was run. Validation is at the layer level.
