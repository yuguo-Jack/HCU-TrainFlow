## Note: sparse MLA chunked-context tolerance

`test_sparse_backend_prefill_correctness[*-masked_mha_chunked_context]` is flaky across seeds on `main` as well. The test fixes `torch.manual_seed(42)`, and the new hd256 kernel happens to fail at that seed.

- **Cause:** the chunked-context path rounds the running context partial to bf16 at every chunk merge, and again in the final suffix merge. With outputs around 128, `rtol=atol=0.01` allows only about 1.3 bf16 ULP. Keeping the running partial in fp32 makes the case pass, which isolates the error to these extra roundings rather than the kernel.
- **Seed sweep:** `torch.manual_seed` patched across seeds 0–299, on B300. "Old" is `main` with stock FA4 (the dedicated hd256 kernel); "new" is this PR with #213.

| shape | kernel | seeds failing at rtol 0.01 | at 0.015 | at 0.02 |
|---|---|---|---|---|
| deepseek 192/128 | old / new | 21 / 21 | 0 / 0 | 0 / 0 |
| glm5 256/256 | old / new | 5 / 10 | 0 / 0 | 0 / 0 |
| glm53 256/256 (NoPE) | old / new | 1 / 6 | 0 / 0 | 0 / 0 |

- **New vs old kernel:** the new hd256 kernel exceeds 1 ULP on more seeds than the old dedicated kernel, at about the same rate as FA4's standard kernel on deepseek. The maximum error is the same 1.5 for both, and without chunked context both stay within 1 ULP.
- **Chosen tolerance:** `rtol=0.02` keeps at least 1.06 of margin on every seed. A follow-up could keep the running partial in fp32 instead. That would roughly double the partial buffer's memory and changes shared MLA code, so it is not done here.

### Blocker: Gemma 4 does not start on Hopper

On one H200, `RedHatAI/gemma-4-31B-it-FP8-dynamic` with this PR fails in `kernel_warmup`:

```
File ".../vllm_flash_attn/cute/interface.py", line 823, in _flash_attn_fwd
    validate_output_layout(out, "out", align_bytes=out_align_bytes)
AssertionError: out must have aligned strides and a contiguous last dimension
EngineCore failed to start.
```

FA#213 now requires a 32-byte aligned `out` at `head_dim_v == 512`. `FA4DenseAttentionKernel.get_warmup_keys` compiles SM90 hd512 keys through vLLM's own `compile_flash_attn_varlen_func_from_specs` in `vllm/vllm_flash_attn/flash_attn_interface.py`, which builds `out` with the default 16-byte alignment. The FA-side fix does not help, because this wrapper builds its own spec. With only the FA fix, the engine still fails with the same assertion.

The fix is the same line in vLLM's wrapper. It is on [`pr65203-review-fixes`](https://github.com/simon-veitner-redhat/vllm/tree/pr65203-review-fixes) as one commit, [`fa116c71b`](https://github.com/simon-veitner-redhat/vllm/commit/fa116c71b2393ee48a4ebc5d0810dfe58a9a1f67), on top of `d203078a1`:

```diff
     out = _make_compile_only_tensor_spec(
         (*q_shape[:-1], v_shape[-1]),
         q_dtype,
+        assumed_align=32 if v_shape[-1] == 512 else 16,
     )
```

On the H200 with this fix, the 5 FA4 warmup keys compile in 10.4 s and GSM8K (5-shot) is 0.6475 flexible / 0.6346 strict. The base (vLLM `28dd9c36`, FA `9ed6b129`) warms up in 14 s and scores 0.6467 / 0.6338.

### Known slowdown: Gemma 2 under forced FLASH_ATTN

Before this PR, hd256 with softcap (Gemma 2, `attn_logit_softcapping=50`) fell back to FA2 on SM100. Now it runs on FA4. Accuracy is unchanged (GSM8K 0.831 against 0.829), but FA4's softcap path is slower. On B300, FLASH_ATTN forced, same server flags, interleaved arms, one GSM8K pass (1319 questions, concurrency 256) takes:

| Arm | Wall time per pass (s) |
|---|---|
| FA4 with softcap (this PR) | 37.8, 37.5, 31.0, 32.9 |
| FA2 (`flash_attn_version=2`) | 21.3, 19.9, 23.5, 20.5 |
| FA4, softcap removed by hf override (timing only) | 12.2, 10.5 |

That is about 1.5x slower than FA2. No FA4 run logged a runtime JIT compile, so this is steady state. Block 128 does not recover it (41.9 s). B300 picks FlashInfer for Gemma 2 by default, so only users who force FLASH_ATTN see this. I am not asking for a change here; it may be worth a line in the description.

### Minor: validation env

The perf numbers reproduce under vLLM's own pins (cutlass-dsl 4.8.0, apache-tvm-ffi 0.1.11), which this PR keeps. The env in the description (4.8.1 / 0.1.15.post2) cannot run `vllm serve`: after CUDA-graph capture, the JIT monitor imports tilelang 0.1.12, which needs `apache-tvm-ffi<=0.1.11`, and it aborts with `TypeAttr __ffi_repr__ is already registered`. So please don't bump the pins for this sync. Not blocking.

### Coverage

We ran the paths whose FA2 fallback this PR removes, on B300, against the base `28dd9c36`. Accuracy is at base level for softcap, FP8 KV, blocks 16 to 256, mm_prefix, chunked prefill with prefix caching, DCP, windowed encoders (`embeddinggemma-300m`, cosine at least 0.9986 against FA2) and TurboQuant prefill (Qwen3.5-4B). Sinks, the mm encoder and MLA 256/256 have no small hd256 model, so we checked them with direct kernel calls only. DCP improves: on `gemma-2b-it`, TP 2 with DCP 2 scores 0.125 on FA4, against 0.089 on FA2 at the base and 0.125 for TP 2 without DCP.
