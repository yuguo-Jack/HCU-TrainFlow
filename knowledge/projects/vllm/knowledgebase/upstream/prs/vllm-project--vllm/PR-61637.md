# [ROCm][Bugfix] Use the kernel's K in the preshuffled MXFP4 GEMM tuned probe

[Upstream PR](https://github.com/vllm-project/vllm/pull/61637) · state: open · merged: False

## Original PR description

## Overview

`is_triton_gemm_afp4wfp4_presh_ws_tuned` looks up the AITER preshuffled config with K = 4 * k_bytes, but `gemm_afp4wfp4_preshuffle` loads it with 2 * K_bytes (`_get_config` doubles the byte K it gets). So with `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1` the M <= 64 preshuffle route was decided on the config file for twice the real K. I ran into this while measuring the preshuffle path for ROCm/aiter#6024.

## Claims

- the probe now checks the same `GEMM-AFP4WFP4_PRESHUFFLED-N=..-K=..` file the kernel loads
- Llama-3.1-8B MXFP4: down_proj (N=4096 K=14336, has a tuned file) now goes to preshuffle, gate_up (N=28672 K=4096, no file) stops running preshuffle on DEFAULT and goes to a4w4. qkv and o stay on a4w4
- output tokens are unchanged
- on its own its a routing fix, not a speedup. On Llama-3.1-8B with AITER's shipped down config it makes the env var path slower at 4 of 5 batch sizes. With the down config retuned in AITER it is 11-17% faster than before the fix at every batch, numbers below
- the env var is off by default and the probe is only used under it, so the default path doesnt change

## Validation

`test_preshuffled_tuned_probe_matches_kernel_config_lookup` mocks `get_gemm_config` in the probe's module and in the module of AITER's `_get_config`, then checks both resolve the same (name, N, K) for the four Llama-3.1-8B linears. The second `test_aiter_fp4_gemm_preshuffled_tuned_shapes` case moves from (M=32, K=8192, N=16384), which only passed because of the doubled K, to the Llama-3.1-8B down shape (M=32, K=14336, N=4096). `tests/kernels/quantization/test_rocm_mxfp4.py` on MI355X with AITER main 057e731ad: 5 failed / 56 passed before the fix (the 4 new cases and the moved one), 61 passed after.

Served amd/Llama-3.1-8B-Instruct-MXFP4-W4A4-MLCAL-C1000-GPTQ, TP=1 on one MI355X, `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, idle GPU, clock pinned with perf_determinism (sclk CV 0.043% under load), one process per run, compile and inductor caches off, arms interleaved (each arm once forward, once in reverse order). ms/token is decode only, the p50 wall of a 128 token run minus the p50 wall of a 1 token run, over 127 tokens, mean of 2 runs. "after + retuned" is this PR with the retuned AITER file from ROCm/aiter#6521 (one config json, nothing else):

| batch | before | after | after + retuned |
|---|---|---|---|
| 1 | 3.532 | 4.233 (+19.8%) | 3.082 (-12.8%) |
| 8 | 3.790 | 4.469 (+17.9%) | 3.360 (-11.3%) |
| 16 | 3.872 | 3.541 (-8.6%) | 3.434 (-11.3%) |
| 32 | 4.101 | 4.623 (+12.7%) | 3.573 (-12.9%) |
| 64 | 4.606 | 4.737 (+2.9%) | 3.812 (-17.2%) |

Token ids are identical between all three at every batch above and on 84 greedy prompts, and GSM8K (1319 questions, 4-shot greedy) is 706/1319 for all three with the same token ids on every question. For comparison the default path without the env var is 2.664 / 2.923 / 2.948 / 3.220 / 3.915 on the same stack, so on this model the env var path stays slower at bs1-32 even with the retune. I also logged every GEMM call: before, gate_up at M <= 64 ran preshuffle on DEFAULT and everything else ran a4w4; after, down at M <= 64 runs preshuffle with its tuned file and everything else runs a4w4. The served runs used a slightly older vLLM tree with this change applied, the probe and the ASM branch of `gemm_with_dynamic_quant` there are the same lines as main apart from main's `VLLM_BATCH_INVARIANT` check.

## Details

The slowdown comes from the down config that now gets picked up. `GEMM-AFP4WFP4_PRESHUFFLED-N=4096-K=14336.json` uses NUM_KSPLIT=1 with BLOCK_SIZE_N=64 for M_LEQ_8 and M_LEQ_32 / M_LEQ_64, and standalone (cudagraph, cold weights) that kernel takes 48.1 / 49.2 / 46.5 / 46.3 us at M=1/8/32/64, against 16.8 us at M=16 where M_LEQ_31 splits K 14 ways, and the ASM gemm_a4w4 it replaces is 23.8-27.1 us. bs16 is the one batch that got faster, which lines up. Thats a config problem on the AITER side, so I retuned the file there in ROCm/aiter#6521 instead of keeping the probe pointing at the wrong file: 12.1 / 13.6 / 13.6 / 18.1 us at the same M, bit identical output.

Other models should be affected the same way. On AITER main the gfx950 preshuffled dir has files for N=10240 / 8192 / 57344 at K=8192 and N=8192 K=28672 (the Llama-3.1-70B TP1 linears), and the old key looked for K=16384 / 57344 and missed all four. I havent measured those.

The other Triton probe in the file, `is_triton_gemm_w8a8_tuned`, passes K through unchanged and AITER's blockscale `_get_config` doesnt rescale it, so it doesnt have this problem.
