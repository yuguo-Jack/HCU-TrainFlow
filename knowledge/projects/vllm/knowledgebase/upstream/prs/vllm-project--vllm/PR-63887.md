- BugenZhao · comment · 2026-10-29T09:30:09Z · [source](https://github.com/vllm-project/vllm/pull/63887#issuecomment-6493038902)

After second thought I think you're right! I initially chose to abstract `TextLlm` mainly to align with the current `Generate` interface in `vllm-proto`, which Dynamo already uses as the boundary between router and worker. The main benefits of doing that were:

* vLLM still validates and normalizes the sampling parameters, so the internal `EngineCore` representation doesn't leak into the public interfaces in `vllm-proto`.
* The worker keeps the text layer, so it can detokenize and handle `stop_str` locally.

But it turns out that:

* `/inference/v1/generate` is already there as a boundary in pure token mode.
* The text layer is very valuable to keep on the frontend side, especially now that the vLLM Rust frontend detokenizes into text with per-token attributions instead of a plain string, which gives the parsers more information.
* `stop_str` can still be handled on the frontend side: on a match it just drops the stream, which aborts the request on the remote engine, at the cost of a few extra tokens.

> could the frontend integration be reused independently of `vllm-router`

Yes, that's the goal! What we want here is just a generic/remote version of `Llm`, so any system implementing that trait can integrate with the `server + chat + text` layers of the Rust frontend.
