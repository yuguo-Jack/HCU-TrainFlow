# [Perf][ROCm] Fuse hyperconnection up projection and gate mix on AMD

[Upstream PR](https://github.com/vllm-project/vllm/pull/64263) · state: open · merged: False

## Original PR description

## Purpose

On ROCm, each hyperconnection boundary runs the up projection (`input_mix_weight_up`, rank 320 → `hc_count × hidden`) as a GEMM and then a separate `hc_gate_mix` kernel that applies `sigmoid(gate) * x` per stream and averages the streams. At decode sizes both kernels are latency-bound, and the GEMM's output makes a round trip through HBM only to be read back by the gate mix.

This PR fuses the two into one Triton kernel, `amd_hc_up_gate_mix`:
- For each 16-column output tile, it computes each stream's gate with `tl.dot` over the rank.
- It rounds the gate to the activation dtype, which matches the unfused GEMM output.
- It accumulates `sigmoid(gate) * x` and divides by `hc_count`.

`mix()` and `combine_and_mix()` call the fused op unless batch-invariant mode is on. The op itself chooses by token count: it runs the fused kernel for 1–256 tokens and the existing GEMM + `hc_gate_mix` otherwise. The choice has to happen inside the op: vLLM compiles one graph for all batch sizes, so a Python branch on the token count in the model is resolved once and baked into every captured size.

Tiles come from an MI355X sweep at `hc_count=4`, hidden 2560, rank 320:
- ≤ 48 tokens: 16×16 tiles, `BLOCK_K` 32, 1 warp. This is latency-bound, and one wave per tile keeps the most programs in flight.
- > 48 tokens: 64×16 tiles, `BLOCK_K` 128, 4 warps.

Dtype-independent; no change to weights, KV cache or defaults.

## Test Plan

- Unit test `test_hc_ops_amd.py::test_hc_up_gate_mix_matches_unfused`. It compares against `hc_gate_mix(xn, F.linear(lowrank, w), hc_count)` at 1, 3, 16, 17, 48, 49, 100, 256 and 257 tokens, which covers both tile paths, ragged tiles and the unfused fallback, with atol/rtol 2e-2.
- Microbench of fused vs unfused, captured in CUDA graphs: `rocm_unquantized_gemm_impl` + `hc_gate_mix` vs `hc_up_gate_mix`, on MI355X (gfx950), two passes.
- Pending:
  - TP2 serving A/B (`vllm bench serve`, the same points as #64123), with and without this PR.
  - A short GSM8K check, because outputs are not bit-identical to the unfused path: the fused kernel accumulates the rank reduction in a different order. Max abs diff vs unfused is ≤ 0.002 in the microbench.

## Test Result

> **Status: not a win as tuned. Do not merge in this form.** A dummy-weight serving proxy on MI355X (TP2, real config with random weights, MXFP4 KV, MXFP4 experts) shows:
> - Before b2e10677a the fused path never ran in serving: the size check was a Python branch in the compiled region, so the unfused branch was baked in. C1 TPOT was 5.98 ms against 5.99 ms off.
> - With the fused path running, C1 decode is **0.35 ms per step (+5.8%) slower**, 6.32 ms against 5.95–5.99 ms off. C64 is unchanged (72.13 against 71.93–72.00 ms). Boot-to-boot noise is under 1%.
>
> These are proxy numbers, not a weights-on serving result.
>
> Cause: the microbench below reuses one weight, which stays in cache. With 96 distinct weights cycling, as in a decode step, the fused kernel is 0.65x at 1 token and 0.74–0.81x at 8–128 tokens (cold-cache table below).
>
> A cold-cache re-sweep of all 288 tilings found no winner. The best fused times are 8.43 / 8.55 / 9.06 / 11.29 µs at 1 / 8 / 32 / 128 tokens, against 5.47 / 6.82 / 6.94 / 9.66 µs unfused. Each best config is a one-warp 16×16 tile: the kernel cannot keep enough loads in flight to stream the weight from HBM, which the ROCm skinny GEMM is built to do. **Recommendation: close this PR.**

| tokens (cold cache, 96 weights) | 1 | 4 | 8 | 16 | 32 | 64 | 128 | 256 |
|---|---|---|---|---|---|---|---|---|
| unfused µs | 5.49 | 8.60 | 6.75 | 6.88 | 6.98 | 8.78 | 9.62 | 13.12 |
| fused µs | 8.38 | 8.44 | 8.46 | 8.51 | 8.92 | 11.80 | 12.30 | 12.76 |
| speedup | 0.65x | 1.02x | 0.80x | 0.81x | 0.78x | 0.74x | 0.78x | 1.03x |

Unit test: 9 passed (MI355X).

Warm-cache microbench (one weight reused, so it overstates the kernel; see the status note above). MI355X, µs per call, both passes agree to within 0.1 µs:

The fused path is capped at 256 tokens (`MAX_FUSED_UP_M`). That covers decode up to `--max-num-seqs 256`; above it the margin is thin, and the fused kernel loses at 1024.

Two calls per layer (attention and MLP hyperconnection) across 48 layers save about 0.1–0.17 ms per decode step. That estimate came from the warm-cache microbench, and the proxy serving run contradicts it (see the status note above).

**Serving numbers: pending.** The BF16 checkpoint used for the serving runs is currently unavailable on the test host. The serving A/B and the GSM8K check will be added here when it is back.
