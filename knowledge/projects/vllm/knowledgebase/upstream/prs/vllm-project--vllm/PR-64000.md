## Original PR description

# [Attention] Opt-in FA3 split cap for length-homogeneous decode batches

## Purpose

FA3 splits a request's KV range across `num_splits` partitions so that more CTAs can
work on one long sequence, and vLLM passes a flat upper bound —
`flash_attn_max_num_splits_for_cuda_graph`, default **32** — when capturing decode
CUDA graphs. The per-request split count is then chosen on device by
`prepare_varlen_num_blocks`:

```
num_splits = ceil(n_blocks / ceil(total_blocks * 1.1 * kv_heads / num_sms))
```

**Both ceilings round up, so `kv_heads * num_reqs * num_splits` overshoots the SM
count for some batch sizes.** The hdim-256 decode kernel occupies ~227 KB of shared
memory on Hopper, i.e. at most **one CTA per SM**, and each
(request, kv-head, split) triple is a persistent work item that streams its KV range
serially. Once the item count exceeds the SM count, the surplus items form a second
wave that runs with only a handful of CTAs resident.

This PR caps the budget to `max(2, num_sms // (kv_heads * num_reqs))`.

## Measured effect (H20, 78 SMs, 4 KV heads, head_dim 256, fp8 KV, 16 full-attn layers)

Isolated FA3 decode, b=7 @ 42,608 context, GPU exclusive + SM clock locked:

| `num_splits` | per layer | bandwidth | executed TFLOPS |
|---|---|---|---|
| 3 (what the heuristic picks today) | **1.506 ms** | 406 GB/s | 36.2% |
| **2 (this PR)** | **1.133 ms** | 539 GB/s | 48.6% |

**1.33x on the attention kernel**, which is 52% of the decode step for this model.
Two more batch sizes where the heuristic overshoots: b=4 (**capture size 4**) **1.53x**
(0.854 → 0.559 ms, two runs per arm) and b=8 (**capture size 8** — where real batches 5-8
land) **1.30x** (1.453 → 1.116 ms, one run per arm). Note what the cap keys on: the *padded
capture size*, not the batch size. Under the default CUDA-graph capture list a real batch of
5 replays as capture size 8, so the number that describes b=5 in a graph is the 1.30x above —
not the isolated 5-request kernel point (cap 32 → 4 splits vs cap 3 → 3 splits, 1.47x), which
this config never produces and which is therefore not quoted here.

### End to end on vLLM 0.32.0 (current code, flag off vs on)

7 requests of 48,008-63,992 tokens, decode-only steady state, no profiler, pooled over the window,
two runs per arm (24 intervals / ~554-626 steps each), same server binary with only the flag changed:

| arm | decode step | steps in 24 s |
|---|---|---|
| flag off (default) | 43.572 / 43.172 ms | 554 / 559 |
| **flag on** | **38.552 / 38.554 ms** | **626 / 626** |
| | **-4.82 ms = -11.1%** (observed range -10.7% … -11.5%) | |

The flag demonstrably took effect: the captured graph's memory pool drops 0.96 -> 0.58 GiB (fewer
split accumulators), and 72 more decode steps fit in the same 24 s window.

An earlier revision (which applied the cap unconditionally) measured **-8.8%** on vLLM **0.28.0**
with the same workload shape. The two percentages are not directly comparable (different vLLM
version, different baseline step time: 43.4 ms on 0.32.0 vs 50.5 ms on 0.28.0), so they are reported
separately rather than pooled.

End to end (7 requests, *unequal* prompt lengths 48k–64k, decode-only steady state,
no profiler, alternating runs: A 3 runs across 2 processes, B 2 runs in one process):
**50.46 ms → 46.05 ms step time (−8.8%)**. Under the authoritative (pooled) estimator A
contributes two clean runs (50.271 / 50.650 ms) and B only one (46.047 ms; the second B run
was discarded because its `tok/step` was 6.954, i.e. it partly overlapped request completion).
So the run-to-run spread is known **for A only (0.378 ms, 0.75%)**; for B there is no independent
repeat, and the −8.4%…−9.1% figure is the **range of observed combinations, not a confidence
interval**. Treat the effect as "~9% observed once with a stable control arm", not as a
replicated measurement.

Correctness evidence is kernel-level and **bounded, not a proof**. With identical q/KV/block_table
and only `num_splits` changed (32 -> 2), the attention output differs by 2.98% (max relative),
which is the same magnitude as each arm's own 2.5-2.9% distance from an fp32 SDPA reference.
Note what that reference is: it dequantizes **the same already-fp8 Q/K/V** to fp32 and computes
attention in fp32, so the ~2.8% is the kernel's own arithmetic deviation (fp8 MMA + online
softmax) from exact accumulation on identical inputs — it is *not* KV-cache quantization error.
For capture sizes that the cap does not change, the kernel configuration is bit-identical.
Capture/replay was checked separately: a CUDA graph was captured around the FA3 call at batch 8 /
48k context and replayed, for both `num_splits=2` and `num_splits=32`. Eager and replay agree
**bit-for-bit** (max abs diff 0.0) in both arms, including after mutating `q` (which moves the output
by 5.1e-3, so the replay is not vacuous). That covers the #62626-style concern for this path — the
accumulator sizes, combine grid and scheduler metadata layout all come out consistent.

What the 34 unit tests cover is the arithmetic of the cap and the precedence rules; they do not
exercise kernel numerics. What is **not** covered: performance on skewed batches beyond the shapes
tabulated below, and any shape where the uncapped formula would not have overshot.

Note on end-to-end token comparison: it is *not* a usable instrument for this change
in our setup. only **2 of 8** outputs were identical across repeated runs of the **same** configuration
(and one differed at the very first token, which is produced by prefill), while batch
size 1 is bit-reproducible — the irreproducibility comes from multi-request
prefill chunking/batch composition, not from the split path. The only way to force
determinism (`VLLM_BATCH_INVARIANT`) also pins `num_splits = 1`, i.e. it disables the
knob under test.

The kernel is not compute- or bandwidth-bound at this shape (2.8x / 9.5x above the
respective floors), and a single CTA reaches ~69% of per-SM tensor peak — the loss is
entirely the second wave.

## Why a shape-aware cap and not a smaller constant

* `num_splits` must be a function of the **capture size**: it sizes both the split
  accumulators and the FA3 combine kernel's grid, which a CUDA graph freezes at
  capture. `num_reqs` at build time is the padded capture size, so the value is
  identical at capture and replay (this is the failure mode of #62626).
* Batch 1 needs a **large** cap (18 with this formula) — a small global constant
  starves it.
* Batch ≥ 9 must **not** be driven to 1: `num_splits == 1` selects a different
  (`Split=false`) kernel instantiation, measured 13% slower at b=14 than 2 splits.
* A config value `<= 1` is passed through unchanged, preserving the documented
  `num_splits=1` workaround for #62626.

So no single constant works in both directions; the cap has to follow the shape.

## Scope and blast radius

* **Only** full-CUDA-graph decode (`max_num_splits` is 0 for eager and mixed/prefill
  steps, which keep FA3's own heuristic). Prefill-blocking tail latency is unaffected.
* For the shape in the table the cap only changes capture sizes **4 and 8**; every
  other capture size produces a bit-identical configuration. A test asserts this
  monotonicity and the one-wave invariant.
* Verified on 0.28.0 and on **0.32.0**: the split counts are identical
  (18 / 5 / 3 / 3 for b=1/4/7/8) and the 32→2 ratio reproduces (1.331x vs 1.329x),
  so this is not a stale-version artifact.
* SM90 still defaults to FA3 (the FA4 upgrade paths are hdim>256 / diff-KV sinks /
  dynamic causal), so the affected path is the default one on Hopper.

## Opt-in, and why it is not a default

The cap is behind `--attention-config.flash_attn_split_cap_for_uniform_decode`
(**default off**). The cap keys on the request *count*, while FA3 sizes each request's splits from
that request's own block count, so a skewed batch can be starved. Measured on H20 (isolated FA3
decode, identical tensors, only `num_splits` varies, 30 repeats, IQR <= 0.014 ms):

| request lengths | splits (cap=32 -> capped) | attention kernel | verdict |
|---|---|---|---|
| 8 x 42,608 (uniform) | 3 -> 2 | 1.51 -> **1.14 ms** | **1.32x faster** |
| 7 x 48k-64k (max/min 1.33) | 3 -> 2 | 1.97 -> **1.67 ms** | **1.18x faster** |
| 1 x 48k + 7 x 32k | 4,3,.. -> 2,.. | 1.13 -> 1.25 ms | 1.11x slower |
| 1 x 64k + 7 x 128 | 18,1,.. -> 2,1,.. | 0.225 -> 1.66 ms | 7.37x slower |

So the win is real for length-homogeneous decode batches (which is the workload this was measured
on) and a regression otherwise. The flag makes the caller assert the precondition instead of the
engine guessing from one step's lengths.

### Why a config flag rather than a per-batch check

`num_splits` is not just a heuristic: it sizes the split accumulators, the FA3 combine kernel's
grid, and the *layout* of the host-built scheduler metadata (`use_dynamic_split` depends on
`num_splits > 1`), and a CUDA graph freezes all three at capture. A decision that reads the current
batch's lengths would therefore differ between capture and replay of the same graph -- exactly the
failure mode described in #62626. Every input to `_resolve_num_splits` (the capture-size request
count, the SM count, the KV head count and this config value) is constant for a given graph.

### Precedence

`flash_attn_max_num_splits_for_cuda_graph <= 1` is returned verbatim, because `0` means "let FA3
use its own heuristic" (the value used outside full CUDA graphs and on FA2) and `1` is the
documented escape hatch for #62626. The cap can only lower the configured value, never raise it.

## Wiring validated through a real server

The three-way table below is a kernel-level benchmark that calls FA3 directly. The flag itself was
validated end to end by serving the model twice with the same binary, changing only the flag:

| | flag off | flag on | predicted |
|---|---|---|---|
| captured graph memory pool | 0.96 GiB | **0.58 GiB** | -0.37 GiB (accumulators at max capture size: `(32-2) x 512 x 24 x 256 x 4 B` = 377 MB) |
| decode steps in a fixed 24 s window | 554 / 559 | **626 / 626** | ~+13% |
| decode step | 43.572 / 43.172 ms | **38.552 / 38.554 ms** | -11.1% |

The 0.38 GiB drop matches the predicted accumulator shrink to within a few percent, which confirms
the flag actually reaches `num_splits` (32 -> 2) rather than being silently ignored. Both arms were
run twice; the on-arm reproduces to 0.005%, the off-arm to 0.92%.

## Why not just set `flash_attn_max_num_splits_for_cuda_graph=2`?

The existing knob is a single global bound: setting it to 2 also clamps batch 1, where FA3 wants 18
splits. Measured on H20 at 42,608 tokens (isolated FA3 decode, identical tensors, 30 repeats,
IQR <= 0.008 ms):

| batch | default (32) | global `=2` | this flag | flag vs global `=2` |
|---|---|---|---|---|
| **1** | 0.162 ms (18 splits, 72 items) | **1.108 ms** (2, 8) | **0.163 ms** (18, 72) | **6.8x faster** |
| **4** | 0.895 ms (5, 80) | 1.150 ms (2, 32) | **0.588 ms** (4, 64) | **2.0x faster** |
| **8** | 1.498 ms (3, 96) | 1.127 ms (2, 64) | 1.136 ms (2, 64) | same (1.008x) |

So the value is not "cap at 2": it is picking a *different* cap per capture size - leaving batch 1
alone, trimming batch 4 from 5 to 4 (1.5x faster than default) and batch 8 from 3 to 2. A global
`=2` cannot express that; it would cost 6.8x at batch 1.

## Relation to #35899

#35899 raised the budget **upward** when the batch *under*-fills the machine
(1 KV head, batch 1 → fill all SMs). This change is the complementary half: it
**lowers** the budget when the batch *over*-fills it. Both are `num_splits`
scheduling policies against the same `kv_heads * num_reqs * num_splits <= num_sms`
target; #35899's `compute_fa3_num_splits` floor and this cap could later be folded
into one function.

  direction**: it raises the budget when the batch *under*-fills the machine and explicitly never
  goes below 32. This PR lowers the budget when the batch *over*-fills it. See
  "Relation to #35899" above; the two are complementary halves of the same
  `kv_heads * num_reqs * num_splits <= num_sms` target and could later be folded into one helper.
- **#62626** (open) is a correctness bug in the same code path (`FULL` cudagraph + FA3 split-KV,
  combine-kernel grid frozen at capture). This PR does not touch that behaviour; it only caps the
  split budget, and the value is a pure function of the capture size, so capture and replay always
  agree.
- No open PR implements a shape-aware split budget.

## Reproduce

Hardware: H20 (78 SMs), vLLM 0.28.0 and 0.32.0, torch 2.13.0+cu130, GPU exclusive,
`nvidia-smi -lgc 1980` (runs at 1830 MHz under load, ~124 W, no power throttling).

Capture sizes in vLLM 0.28.0 are generated by `CompilationConfig.max_cudagraph_capture_size`
(`[1, 2, 4] + range(8, 256, 8) + range(256, max + 1, 16)` when no explicit list is set) —
here `max = 512`, so 51 entries: `1, 2, 4`, then `8..248` in steps of 8, then `256..512` in
steps of 16. Because `num_reqs` at build time is the padded capture size, only capture sizes
**4** and **8** are affected by this cap; every other capture size keeps its current
configuration.

```bash
# isolated FA3 decode, split sweep (1 / 2 / 3)
python bench_fa3_split_sweep.py      # cap 32 -> 3 splits, cap 2 -> 2 splits
# end-to-end, unequal lengths, no profiler
python bench_e2e_split_ab.py --port 9008 --lengths 48000,52000,54656,56000,58664,60008,63992
```

Benchmark scripts are available on request; the harness records warmup, repeats,
median, IQR and an environment snapshot per point.
