# [DeepSeek-V4.1] Enable Engram disk offload for memory-constrained nodes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62238) · state: open · merged: False

## Original PR description

## Purpose

DeepSeek-V4.1-Flash's Engram tables are about 197 GB, so they fit neither in GPU memory nor, with `cpu_offload`, in host memory on a 128 GB node. At TP=4, each rank owns about 50 GB of table rows on top of about 78 GB of weights. On an APU (Strix Halo, DGX Spark), host and GPU memory are the same RAM.

This PR adds `--engram-config '{"disk_offload": true}'`. The tables stay in the checkpoint's safetensors files:

- After loading, each rank memory-maps only its own row range, located through the safetensors header.
- Each step it gathers the distinct rows it needs through the page cache and copies them into fixed GPU buffers.
- The existing `_engram_lookup_kernel` (SORTED mode) runs over that compact table, so results are bit-identical to the in-memory table.

The gather needs the hash ids on the host, so the lookup is an `@eager_break_during_capture` segment. It runs with `--enforce-eager`, or with `VLLM_USE_BREAKABLE_CUDAGRAPH=1 -cc.cudagraph_mode=PIECEWISE`. Startup rejects other graph modes, the host-memory options, and models other than DeepSeek V4.1.

The change is in the shared Engram code and is not tied to a platform. It was tested on gfx1151 and should equally serve CUDA unified-memory machines such as DGX Spark (not tested there).

## Duplicate-work check

- #56757 (disk-backed DeepSeek-V4.1 Engram, NVIDIA-only) was closed unmerged.
- #59958 / #58815 / #58439 add file-backed PLE tables for Qwen4Exp on CUDA. This PR is an independent implementation for DeepSeek V4.1 and uses the same `disk_offload` name, so the two compose.

## Test Plan

```
pytest tests/kernels/test_engram.py -k "disk or reconstruct or matches_torch or rejects_empty or prepared_rows"
pytest tests/test_config.py -k engram
```

New tests check bit-exact lookups at TP 1/2/4/8 for single-file and sharded checkpoints, and a breakable-graph capture plus replay.

End-to-end: `deepseek-ai/DeepSeek-V4.1-Flash-1017` on 4x Strix Halo (gfx1151, 128 GB), TP=4 over Ray, `--enforce-eager`.

## Test Result

```
test_engram.py   64 passed, 12 skipped   (gfx1151)
test_config.py   49 passed
```

On `main` the model does not load on these nodes: the Ray worker dies pinning its ~47 GiB of table rows. With `disk_offload`:

| | |
|---|--:|
| table rows mapped per rank | 2 x 23.6 GiB |
| KV cache | 1.74M tokens |
| decode / prefill tok/s (tg128 / pp2048) | 11.0 / 208 |
| GSM8K, first 100 | 97/100 |

Graph mode is covered by the unit test only. On this cluster (RCCL over TCP), graph mode hangs on the first request in a collective; the same hang occurred with DeepSeek-V4-Flash on stock kernels.
