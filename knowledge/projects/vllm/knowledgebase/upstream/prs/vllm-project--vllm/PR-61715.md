# [Perf][Model Loader] DeepSeek V4.1 Flash mixed RunAI loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/61715) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Consolidate the DeepSeek V4.1 Flash RunAI loading stack: stream the VL wrapper, keep ordinary weights distributed, read shared CPU Engram tables once, and preserve/select the DSpark S3 weight source. This draft includes ported prior work and the experimental integration measured on eight H200s.

## Claims

- Keep TP1/DP8/EP8 ordinary loading distributed while oversized Engram shards load into CPU staging. Shared embeddings/scales have one reader; the small non-shared tensors in those shards still reach every GPU.
- Pass the reader process group to the streamer before metadata; only the single shared Engram CPU reader passes `None`. Independent readers retain shared filesystem queue sizing.
- Preserve streamed tensor lifetimes without materializing the full language checkpoint. Borrowed GPU tensors keep vLLM's normal clone; shared CPU embedding sources are consumed synchronously.
- Load the same-checkpoint DSpark draft from S3 and select its three required shards from the verified local index.
- Require `runai-model-streamer>=0.17.0` in the Python extra and Docker default, with matching 0.17.0 CI requirements and cloud adapters. Released Linux wheels require glibc 2.30; CUDA/CPU/ROCm lock generation targets 2.31, the lowest compatible target supported by the pinned `uv`. XPU already targets 2.39.

## Validation

Real DeepSeek V4.1 Flash revision `5254448`, eight H200s, TP1/DP8/EP8, Engram CPU offload and shared DP storage, DSpark5, RunAI **0.17.0**, `spans`, plus the separate streamer rank-discovery fix [model-streamer #252](https://github.com/dsx-ai-factory/model-streamer/pull/252). Ordinary staging remained **4 GiB/rank** (32 GiB node total under 0.17.0); oversized CPU staging remained **100 GiB**.

| Loading scope | Earlier S3 integration | Combined patched integration |
| --- | ---: | ---: |
| Ordinary 286.1 GiB | 585 s | 37.7 s |
| Engram 189.1 GiB | 140 s | 88.4 s |
| Target payload, ordinary plus Engram | 725 s | 126 s |
| Draft-containing 7.4 GiB | — | approximately 6 s |

This is the **combined stack/configuration result**, not the isolated effect of this PR: released 0.17.0 already supplies native read coalescing/ring improvements, and different nodes were used. One full model run per integration configuration; no repeated same-node A/B startup campaign is claimed.

The patched integration reached Ready with zero restarts. Full vLLM model loading, including approximately 150 s of host-table initialization, took **291 s**. Cold container-to-Ready took approximately **15m28s**, including regression preflight, setup and kernel/graph warmup. The two-minute payload time is not a two-minute server startup claim. Cached NFS/page-cache default-loader controls took 110–113 s for target weights and 265–279 s for full model loading; this does not claim a speedup over cached filesystem loading.

- Focused wrapper/loader/draft regressions: **12 passed**, 27 deselected, 9.62 s.
- Real eight-H200 shared Engram toy loading: **all eight ranks passed**, including FP8/scales, follower synchronization and independent GPU weights in the CPU shard.
- Updated process-group integration: **4 passed**, one unrelated GPT-2 download test deselected, 5.38 s. Covers the three distinct mixed-loader paths and real native borrowed-buffer cloning.
- Updated streamer dependency: **45 passed + 7 subtests**, no skips, 3.50 s. Real eight-process Gloo coverage verifies metadata/payload reader sizing, idle peers, a non-contiguous subgroup, sequential handles and caller-group lifetime; cleanup-failure coverage verifies environment restoration.
- Changed-file pre-commit checks and Linux-target mypy completed. Native macOS mypy reports two pre-existing Linux-only `os.posix_fadvise`/`os.POSIX_FADV_DONTNEED` errors; equivalent Linux-target checks passed.
- Dependency bump: CUDA/CPU/ROCm/XPU locks regenerated with `uv 0.11.1`; `prek run --files` passed all applicable hooks, including the four dependency resolvers and Docker version consistency. Existing unrelated pins were retained; regeneration also restored the `openai-harmony==0.0.8` transitive entry required by the already-pinned `gpt-oss` package.

The updated process-group tests ran on an isolated CPU-only Linux pod with the released native core 0.17.0 and the modified Python SDK from [model-streamer #252](https://github.com/dsx-ai-factory/model-streamer/pull/252), now at [0e0ebbb](https://github.com/SherifWaly/runai-model-streamer/commit/0e0ebbb8a97f3b8ccf42c62f3b5afcc632934c1c). **This revision requires that matching Python SDK; the released 0.17.0 Python API does not yet accept `process_group`.** The final dependency version must be set after the companion API is released. These tests do not establish a new model-loading or NFS performance result, and no revised serving deployment was validated.

## Details

The reproduction example explicitly selects the Python API frontend with `VLLM_USE_RUST_FRONTEND=0`. It supports an explicit local tokenizer metadata path for S3 deployment. This is independent of RunAI tensor loading. A separate eight-B200 canary using preserved image digest `e5c9e6bb82f645e8fca04e4d395743ee5ed473a62b98942d65f83c35d0c69301` and the cached filesystem loader reached Ready with zero restarts and passed 16 serving checks: health/model discovery, text, SSE streaming, image input, forced/automatic tool calls, concurrent requests directed to DP ranks 0–7, and per-engine metric deltas of exactly one request per rank. It validates the existing Python frontend and DP header routing; it does not validate this PR's loading changes or its rebased head. The H200 Python/S3 canary remains unvalidated because BAR's requested SUNK QoS has reached its 80-GPU quota.

Included prior work and attribution:

- **Ported VL streaming and its regression/CI wiring from #58857**, by @gitbisector; original author credit is retained in the commit trailer.
- **Adapted the model-owned draft shard-selection approach from #60759**, by @zhy76. This integration uses a verified local index and a DeepSeek V4.1 DSpark unused-weight predicate; it is not the full generic metadata-selection implementation from that PR.
- **Related draft-source fix #48023**, by @kunling-anyscale, and issue #42060. The recipe uses `method=dspark`, not `method=mtp`. This branch fixes the observed DSpark config-only-cache failure in its loader using a shallow copy of the resolved config; it does not cherry-pick the older generic speculative-config patch.

These pieces are deliberately included in one reviewable draft alongside the CPU Engram integration. Refreshed duplicate checks found the existing PRs above; their overlap is explicit. #61303 optimizes pinned GPU staging and #57195/#61553 change shared-storage inference/topology support; they do not implement this mixed RunAI single-reader path.

The current loader's sorted VL input retains the stream; the GPU streamer cannot safely stage the oversized CPU tables on an H200. Splitting GPU/CPU phases addresses that destination mismatch. Shared followers receive meta placeholders so the existing single-writer weight loaders retain equal call counts/barriers; non-shared tensors are broadcast as raw bytes. The streamer dependency scopes reader discovery before metadata: ordinary readers supply their process group, while the lone CPU reader passes `None` to avoid discovery collectives.

Before merge:

- Replace checkpoint-specific file-list/index opt-ins and private storage-owner discovery with a reviewed configuration/metadata contract; validate missing/stale index and shard failures.
- Harden collective/error ordering, tensor lifetime and configuration validation across supported topologies; test TP/PP, reload and multi-node compatibility explicitly.
- Re-run the model on the final head, complete request/acceptance/eval validation and human line review.
- Resolve/release the separate streamer dependency. It is not vendored into this vLLM diff.

All experiment switches default off. The documented initial scope is one eight-H200 DP/EP server. See `docs/models/extensions/runai_model_streamer.md` for the exact environment and staging configuration. This draft adds loader-time synchronization, not steady-state inference synchronization, and remains experimental until the items above are resolved.
