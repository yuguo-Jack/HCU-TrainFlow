# [CI] Run watermarking tests on GPU nightly

[Upstream PR](https://github.com/vllm-project/vllm/pull/59780) · state: open · merged: False

## Original PR description





## Overview

Add a nightly GPU step that runs `tests/watermarking`, so that its CUDA-gated tests run in CI. Today the directory only runs in the CPU step ":computer: (CPU) V1 Others". Those tests are marked `skipif(not current_platform.is_cuda_alike())`, so they skip on the CPU image.

The new step, ":nvidia: (H200 MIG 18GB) Watermarking Nightly", is `optional: true`. It runs only in builds with `NIGHTLY=1`, which on main are the scheduled full CI runs. The CPU step is unchanged.

Related: #59554, #59779. #59779 fixes draft watermarking under CUDA graphs and adds one more CUDA-gated test to this directory.

## Claims

- The 49 tests gated by `skipif(not current_platform.is_cuda_alike())` now run in nightly CI: 17 in `test_gumbel.py`, 6 in `test_prf.py`, 25 in `test_watermarking.py`, and the opt-125m engine test in `test_watermarking_e2e.py`. They cover the fused Gumbel and Philox kernels, accelerator parity of the repeated-context mask, draft-context deduplication, and end-to-end detection.
- The step does not run on PR builds or ordinary main builds. On those it appears as a manual "Run" block.
- PR coverage of the CPU-runnable tests is unchanged. `tests/watermarking` stays in the CPU step's dependencies and commands.
- The step takes about one minute on one GPU. It runs in each scheduled full CI run on main (nightly, daily and torch nightly), so about three times a day.

## Validation

The new step's command, run from `tests/` on one GPU:

```
cd tests
pytest -v -s watermarking
```

| run | result | pytest time |
|---|---|---|
| whole directory, this branch | 147 passed, 0 skipped | 50.4s |

This ran on an NVIDIA B300, not on an H200 MIG slice. To run the step on this PR's build, comment `/ci run nightly`, or unblock "Run :nvidia: (H200 MIG 18GB) Watermarking Nightly" in the Buildkite build.

The e2e test takes about 17s. Every other test takes about 2s or less, including Triton JIT on first use.

Pre-commit on `.buildkite/test_areas/misc.yaml` passes, including `check-buildkite-step-keys` and `check-test-tethering`. `check_test_tethering.py --all` also passes, and the step key `watermarking-nightly` is unique under `.buildkite/`.

## Details

**How nightly gating works.** The NVIDIA pipeline generator in vllm-project/ci-infra decides per step whether it auto-runs (`buildkite/pipeline_generator/buildkite_step.py`, `_step_should_run`). It checks `NIGHTLY == "1"` first and runs every step. Otherwise it returns early for `optional` steps, before the `RUN_ALL` and `source_file_dependencies` checks. A step that does not auto-run gets a `block: "Run <label>"` step in front of it. The schema comment in `.buildkite/test-amd.yaml` says the same: an optional step never runs by default "unless it's a scheduled nightly run".

`NIGHTLY=1` is set by each scheduled full CI run on main: "Full CI run - nightly" (about 06:00 UTC), "Full CI run - daily" (about 21:00 UTC) and "Full CI run torch nightly" (about 10:00 UTC, on a torch nightly image). Existing optional Nightly steps, such as ":nvidia: (B200) Spec Decode Eagle Nightly", run in all three. On a PR, `/ci run nightly` and the `ready-run-all-tests` label set it, and so does a manual build started with `.buildkite/scripts/trigger-ci-build.sh`. `/ci run all` sets only `RUN_ALL=1`, so it leaves this step blocked.

The label and key follow the existing nightly steps in `spec_decode.yaml`, `lm_eval.yaml` and `kernels.yaml`: a label ending in " Nightly", a key containing `nightly`, and `optional: true`. Those steps also keep a `source_file_dependencies` list. The NVIDIA generator ignores it for optional steps, but CI tooling such as the ci-infra test selector reads it.

**Why the whole directory.** The CUDA-gated tests do not share a name token (`-k cuda` selects 2 of the 49), and a marker would mean editing 49 tests in 4 files. Running the whole directory also picks up new CUDA tests, even if one lacks its `skipif`. The 98 ungated tests add about 15s to each run. They use explicit CPU tensors, so they exercise the same code paths there.

**Device.** `h200_18gb` is the smallest common single-GPU device. The e2e test runs with `gpu_memory_utilization=0.2`, a budget of about 3.6 GB on an 18 GB slice. It measured about 1 GiB outside the KV cache: 0.75 GiB for weights and non-torch memory, and 0.28 GiB peak activation.

**Timeout.** 15 minutes, which leaves headroom over the measured minute for a slower MIG slice and a cold model download.

**Source dependencies.** These follow `lm-eval-watermarking` in `lm_eval.yaml`, plus `tests/watermarking` and `vllm/v1/sample/ops/topk_topp_sampler.py`, which the watermark samplers call. `vllm/v1/worker/gpu/` covers the watermark sampler, Gumbel sampling and the speculator code the tests import.

**No `autorun_on_main`.** The NVIDIA generator's step model has no such field and drops it. Only the AMD Jinja template reads it. So the step does not run on every main commit.

**No AMD mirror.** Not validated on ROCm. I leave the MI355 mirror to the ROCm CI maintainers.
