# [Bugfix] Fit the Triton prefill attention tile to the device's shared memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/60848) · state: open · merged: False

## Original PR description

## Overview

Fit the Triton prefill attention tile to the device's opt-in shared memory so EmbeddingGemma 2 (and any `head_dim` 256 encoder-attention path) starts on 99 KiB GPUs. Fixes #60847.

## Claims

- `google/embeddinggemma-2` no longer fails at warmup with `OutOfResources: shared memory, Required: 163840, Hardware limit: 101376` on sm_86, sm_89 and sm_120 GPUs.
- No change on devices that already fit (A100 and H100 keep the 128 tile); non-CUDA platforms and non-CUDA (e.g. meta) tensors are untouched.

## Validation

- `tests/kernels/attention/test_triton_prefill_attention.py`: added `D=256` to `test_context_attention`. On an RTX 3060 (101,376 B) the bf16 case fails before the change with the error above, and the whole file passes after (33 passed). `ruff check` and `ruff format --check` clean.
- End to end: `vllm serve google/embeddinggemma-2 --runner pooling --dtype bfloat16 --max-model-len 4096` starts and serves on an RTX 5070 Ti (sm_120) and an RTX 3060 (sm_86) with this change applied to the `nightly-8cbd5d03` image; embeddings match sentence-transformers with cosine >= 0.9994 over 140 queries and 346 chunks, 0 errors in a 120 s load test at 8 concurrent clients.
- Reproduce: add `D=256` to the test parametrization on any GPU with a 99 KiB opt-in limit and run it on `main`.

## Details

Root cause: `get_block_size` returns 128 for 16-bit dtypes on capability >= 80, and the only shared-memory guard is `if Lk >= 512: BLOCK = min(BLOCK, 32)`. For `head_dim` 256 (Gemma 4 sliding-attention layers, which force `TRITON_ATTN` because FA4 does not support the heterogeneous head dims) the 128 tile needs 163,840 bytes. The new helper halves the tile while `3 * BLOCK * next_power_of_2(Lk) * element_size` exceeds `shared_memory_per_block_optin`, which gives 64 for `head_dim` 256 bf16 on a 101,376 B device. The factor 3 (Q, K and V tiles) is deliberately conservative: the compiled kernel needs less than that. The query is a cheap device-property lookup per call.

- gitbisector · comment · 2026-10-09T23:04:32Z · [source](https://github.com/vllm-project/vllm/pull/60848#issuecomment-6090757351)

Verified on GB10 (sm_121, 101376 B, triton 3.7.1): head-256 bf16 `context_attention_fwd` goes from `Required: 163840` to passing at BLOCK=64 (max abs err 8.7e-3 vs torch reference). One concern with the estimate: reading `kernel.metadata.shared` across D 64–512, bf16/fp32, BLOCK 16–128, the actual allocation is `(2 * BLOCK_DMODEL + BLOCK) * BLOCK * element_size` (exact, never exceeded). `3 * BLOCK * D * elem` gives 196608 for D=256 bf16 BLOCK=128 where the kernel needs 163840, so on A100 (166912 B per the CUDA docs) this would halve a tile that fits today. Using the measured bound keeps A100 at 128 and still fixes the 99 KiB parts and the fp32 head-512 case.
