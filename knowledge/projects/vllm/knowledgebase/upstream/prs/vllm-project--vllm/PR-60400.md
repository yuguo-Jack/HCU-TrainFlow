# [ROCm][Perf] GDN packed decode: tuned launch configs for gfx1100 and gfx1201

[Upstream PR](https://github.com/vllm-project/vllm/pull/60400) · state: open · merged: False

## Original PR description



## Overview

Add per-arch launch configs for the GDN packed decode kernel (`fused_recurrent_gated_delta_rule_packed_decode`, used by Qwen3.5 / Qwen3-Next GDN layers in every decode step) on ROCm gfx1100 and gfx1201. The kernel currently launches with `BV=32, num_warps=1` on every platform; on these RDNA3/RDNA4 GPUs that leaves it short of memory-level parallelism. Other platforms are unchanged.

## Claims

Kernel time vs the current default (`BV=32, num_warps=1`), geomean over 12 batch sizes B=1..512, at the per-GPU head counts of TP=1/2/4:

| GPU | SSM state | TP=1 | TP=2 | TP=4 |
|---|---|---|---|---|
| gfx1100 (Radeon Pro W7900) | bf16 | -10.0% | -7.5% | -6.4% |
| gfx1100 (Radeon Pro W7900) | fp32 | -5.9% | -6.7% | -6.8% |
| gfx1201 (Radeon AI Pro R9700) | bf16 | -7.6% | -8.6% | -8.9% |
| gfx1201 (Radeon AI Pro R9700) | fp32 | -10.0% | -7.9% | -8.9% |

- No batch size is slower than the default in these runs (per-batch tables below).
- No change on any other arch (CDNA, other RDNA, gfx1250) or on CUDA/XPU: the config table is empty there and the existing `BV=32, num_warps=1` is used.
- Kernel math, inputs, outputs and API are unchanged; only `BV`, `num_warps` and the AMD `waves_per_eu` hint differ.

## Validation

**Correctness.** `tests/kernels/fla/test_fused_recurrent_packed_decode.py` now runs at B = 1, 2, 4, 32, 64, 128, 256, 512 (previously 32 only), i.e. both sides of every batch switch and the large decode batches, for fp16/bf16/fp32 state and contiguous/strided `mixed_qkv`.
- gfx1100 (W7900) and gfx1201 (R9700): 50/50 pass on each, i.e. every table row incl. `waves_per_eu=2` on the GPU that selects it.

**Performance.** Standalone A/B of vLLM's kernel with the default config vs the new config, using the tensor layout vLLM passes in Qwen3.5 decode (H=16, HV=32 at TP=1, divided by TP; K=V=128; `mixed_qkv` as a strided view of the qkvz projection, `a`/`b` views of the ba projection, slot-indexed state cache). Each config is timed in a captured HIP graph that rotates over state slots so the state is read from DRAM on every launch (>=1 GB of state rotated; gfx1201 TP=1: 512 slot sets, >=512 MB, vs its 64 MB Infinity Cache); default and new alternate over 5 rounds, median reported. Every launch is checked against an fp32 torch reference (output and updated state). On both GPUs the run with this branch installed confirmed that vLLM's own launcher picks the new configs (identical timings).

## Details

**What changes.** A table in `fused_recurrent.py`, resolved once at import on ROCm, maps SSM state element size (2 bytes: bf16/fp16, 4 bytes: fp32) to `(max_batch, BV, num_warps, waves_per_eu)` rows; the launcher takes the first row with `B <= max_batch`. `waves_per_eu` is only passed when nonzero. A new exact `on_gfx1201()` helper is added next to `on_gfx1100()` (it does not match gfx1200 or gfx1250).

| GPU | state | batch → (BV, num_warps, waves_per_eu) |
|---|---|---|
| gfx1100 | bf16/fp16 | 1-4 → (16, 2, -); 5+ → (8, 2, 2) |
| gfx1100 | fp32 | 1-2 → (8, 1, -); 3+ → (32, 8, 2) |
| gfx1201 | bf16/fp16 | 1 → (8, 2, -); 2-63 → (8, 2, 2); 64+ → (8, 4, -) |
| gfx1201 | fp32 | 1 → (8, 1, -); 2+ → (8, 2, 2) |

**Why per batch size and per state dtype.** The kernel is bound by reading/writing the recurrent state (per sequence and layer: 1 MB in bf16, 2 MB in fp32 at TP=1). At small batches a few sequences do not fill the GPU, so smaller, wider splits win; from ~8 sequences on the kernel streams state from DRAM and one config is best up to 512. fp32 state moves twice the bytes per row, which shifts the best split. The rows were chosen from sweeps (BV 8-128, num_warps 1-8, num_stages 1-3, waves_per_eu 0/1/2/4) for each GPU and state dtype, preferring few rows that are robust across batch sizes and both state dtypes over per-batch optima.

**Why `waves_per_eu`.** On gfx1201, low-warp configs without the hint are erratic across batch sizes (e.g. BV=8/2 warps is -15% at B=1 but +125% at B=2); with `waves_per_eu=2` they are consistent.

**Cost.** CUDA graphs capture the chosen config per captured batch size, so replay has no added overhead; in eager mode the lookup is a few Python operations per call. Triton compiles one variant per distinct config (2-3 per GPU and dtype) during warmup/capture.

**Limitations.**
- Rows are selected by batch size; with TP>1 each GPU processes HV/TP heads, so the small-batch rows were tuned for more work per call than they see at TP=2/4. They remain faster than the default there (table above), with smaller gains for bf16 at B<=4 on gfx1100.
- All timings are DRAM-cold. In the model, small batches at TP=2/4 keep the state of all GDN layers in the Infinity Cache (e.g. TP=4, B=4, bf16: 24 MB); that cache-resident case was measured at TP=1 only (configs also faster there), not at TP=2/4.
- Small-batch results vary run to run by a few points: gfx1100 fp32 at TP=1, B=2 measured -1.4% here and +4.5% in another DRAM-cold run; in cache-resident sweeps gfx1201 bf16 at B=2 measured +1.5%.
- Tuned with the Qwen3.5 decode shape (K = V = 128). Other GDN head dims use the same rows (`BV` is clamped to `next_power_of_2(V)`).
- fp16 state uses the bf16 rows (same element size); it was not timed separately.
- No change for gfx1151 and other gfx11/gfx12 parts, which were not measured.
