# [Bugfix][Metrics] Count preemptions in the scheduler, not on resume

[Upstream PR](https://github.com/vllm-project/vllm/pull/65317) · state: open · merged: False

## Original PR description



## Overview

`vllm:num_preemptions` is counted from the request's `PREEMPTED` event, which only reaches the frontend with that request's next output. So a request that is preempted and then aborted before it resumes is never counted, and the rest are counted late. This counts preemptions in the scheduler and reports them in `SchedulerStats`, like the prefix cache stats.

## Claims

- Requests aborted while preempted are counted.
- The counter moves when the preemption happens, not when the request resumes.
- `vllm:request_num_preemptions` and `IterationStats.num_preempted_reqs` are unchanged.

## Validation

New test: a request is preempted by KV pressure and aborted, and the next step's stats go through `PrometheusStatLogger`.

```
pytest tests/v1/core/test_scheduler.py -k aborted_request_is_counted
main:     assert 0.0 == 1  (failed)
this PR:  passed
```

`tests/v1/core/test_scheduler.py` passes (286), and pre-commit passes.

End to end on CPU (SmolLM2-135M, 8 KV blocks, 8 concurrent requests, clients killed while some were preempted; true count from a temporary log line):

Each run had 2 real preemptions:

| Counted | main | this PR |
|---|---|---|
| 1 API server | 0, 1, 2, 2 | 2, 2, 2, 2 |
| 2 API servers | 0, 1, 1, 2 | 2, 2, 2 |
| no aborts (7 real) | 7 | 7 |

## Details

The `PREEMPTED` event stays as it is for the interval metrics (#13169); only the counter moves. An aborted request's events can't be applied on the frontend, which has already dropped it, so counting in the scheduler is the simpler fix.

No existing PR or issue covers this. Related: #38452 and #61492 fix the `Preemptions:` log field (small overlap in `loggers.py`), and #58037 adds a by-reason counter from the same event.

Not tested on GPU or with data parallelism. AI assistance (Claude Code) was used; I reviewed the change and ran the tests.
