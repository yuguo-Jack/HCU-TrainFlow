## Overview

Extract and complete the initialized-engine preparation/recovery sequence from vllm-project/vllm#51360. The snapshot CLI now validates recovered output before opening HTTP, using an internal session intended for reuse by ordinary serving (vllm-project/vllm#48193).

Draft for review. Base `6e517b15c1`, tested head `14903f61d1`; the two commits separate mechanical extraction from behavior changes.

## Claims

- Capture readiness follows completed rehearsal and communicator preparation.
- Communicator/memory recovery and a private output check finish before HTTP is bound. Failed or cancelled phases are terminal and retain a phase/error record.
- Parser/plugin validation happens before engine construction. Default ordinary-serving setup order is preserved.

## Details

Previously the controller checked recovered output through HTTP after the listener was bound. `SnapshotSession` performs that check privately first and preserves the controller's public check. Memory wake can resume scheduling, so this helper requires exclusive startup ownership until recovery succeeds. It is not a live-server admission gate. Memory release/restore policy remains separate from quiescence and validation.

This is the existing CLI portion of the roadmap. vllm-project/vllm#54940 and its stack cover external-controller/device and transport plumbing; vllm-project/vllm#52132 captures the engine subtree while retaining its frontend. This draft shares the current CLI sequence without adding those control surfaces or an artifact manager. Start review in `vllm/snapshot/engine.py`, then follow its caller in `vllm/snapshot/server.py`.

Ordinary-serving integration, donor continuation, TP2 and relocation remain follow-ups. No latency/throughput claim: the runs were instrumented. KV-token capacity was ordinary/snapshot 54,048/54,032 for MRV2 (the existing CLI also had 54,032) and 51,680/51,472 for MRV1; the V1 difference remains unattributed.

**Resilience and Maintainability Implications**
