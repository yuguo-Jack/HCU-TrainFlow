# [Bugfix][HiSparse][NIXL] Import full blocks without tail prefill on D

[Upstream PR](https://github.com/vllm-project/vllm/pull/57049) · state: closed · merged: True

## Original PR description

## Purpose

HiSparse currently rejects host imports whose computed-token count is not block aligned. This draft explores an alternative to #56946: receive the full final block and restore its contents into one writable GPU page, so a successful NIXL full-prompt import resumes with a single-token forward instead of prefilling the unaligned tail on D.

The idea is that we want to avoid having to run prefill on D, however short they might be (<block_size here), with north star being deploying D with decode-only CG (aligned with rest of cases).

### NIXL analogy: transfer capacity is not sequence length

NIXL already transfers physical blocks containing partially filled prompt tails. Moving the unused bytes does not make them computed tokens. HiSparse can use the same distinction:

| For a 32,019-token prompt, block size 128 | This approach |
| --- | --- |
| Real imported tokens | 32,019 |
| Host blocks received | 251 |
| Physical capacity | 32,128 token slots |
| Unused tail capacity ("holes") | 109 token slots |
| Prompt work on D after a full import | The usual last-token replay for logits |

The holes are unused rows within the request's final host block. They do not change token positions or sequence length, and generation fills them at their normal offsets. P does not compute dummy padding tokens. No sub-block allocator or NIXL wire-protocol change is required.

### Implementation and tradeoff

- Reserve one writable resident page for the final imported block, including aligned prompts whose last token is replayed.
- After a successful external receive, enqueue a full-page host-to-device restore on every TP rank. Copies run on the compute stream before the forward/CUDA-graph replay.
- Retain both endpoints until every participating worker completes its copy. Avoid publishing an uninitialized resident copy to prefix-cache users, and keep an incomplete host page unsealed.
- Register a completed, valid restored GPU page for later prefix hits only after all workers finish. Pending restores remain hidden, and incomplete pages and aborted requests are excluded. This incorporates [NickLucche/vllm#12](https://github.com/NickLucche/vllm/pull/12).
- Continue using the existing row-mirror and page-sealing paths for newly generated KV.

Compared with #56946, this transfers the final block and pays for one page of H2D copying per layer/rank rather than recomputing up to `block_size - 1` prompt tokens. It also reserves a resident tail page for aligned imports. The unused host rows are ordinary tail capacity, not extra logical tokens or permanent gaps between prompt and output. No performance improvement has been measured.

The intended benefit is to keep successful full-prompt P/D handoffs on single-token execution, compatible with decode-only graph capture. This is not a guarantee that D can never prefill: cache misses, failed transfers, preemption, or partial external hits can still require recomputation.

### Related work

Checked #56699 and its comments, open PRs mentioning it, and open PRs matching HiSparse import, landing, tail, partial, full block, and tail restore.

- #56946 addresses the same admission failure by rounding the imported prefix down and prefilling the remainder locally. This draft is the explicitly requested alternative that retains all real prompt KV and changes tail residency instead.
- The notify-only read and empty-region shape fixes are reused verbatim from #56946 (originally #55398). They prevent empty local destinations from entering region expansion when P and D have different cache-group layouts. They are independent of tail policy; empty receives notify P, and report `finished_recving` only when `awaiting_kvs=True`.
- #55398 chooses direct GPU landing for imported history when capacity permits. This draft preserves host landing and restores only the final page.
- #56109 concerns broader pool/residency management. This draft uses the current pool model.

Related to the deployment discussion in #56699; this does not claim to fix that issue's CUDA launch failure or establish end-to-end P/D correctness.
