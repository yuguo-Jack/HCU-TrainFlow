# [ROCm][MoRIIO] Support PP for prefill instance in PD disaggregated serving with MoRI WRITE mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64693) · state: open · merged: False

## Original PR description



## Overview

In WRITE mode, `MoRIIOConnector` assumes one prefill rank per TP index that writes every layer. With pipeline parallelism, the index is shared for the stages, so the stages collide on ports and the later ones fail to start. Each stage also numbers its layers from zero, so a stage that does write puts them on the decode instance's first layers. This PR lets a prefill instance under MoRIIO's WRITE mode use pipeline parallelism, with each stage writing the layers it holds to the decode addresses of those same layers and a decode rank finishing the transfer only after every stage has reported.



## Claims

- A prefill instance can now run with pipeline parallelism in WRITE mode. Each stage writes its own layers, and decoding starts only after every stage has reported.
- For MLA models the main gain is prefill capacity. On GLM-5.2 and GLM-5.3 (8 × MI355X), a TP1 × PP4 prefill instance holds about 4× the KV cache of a TP4 one (4.12× and 4.02×) and serves 41.9 % and 27.1 % more tokens per GPU on 32K-token prompts at 16 concurrent requests, with TTFT p50 down 42 % and 30 %.
- The peer's layer addresses are now looked up by layer name. This also fixes a case without pipeline parallelism where a decode instance with an MTP layer is fed by a prefill instance without MTP.
- Combinations the connector don't support fail at startup with an error that articulates the setting.

## Details

For MLA models, a TP*n* prefill instance keeps a full copy of each layer's latent KV on every TP rank. Splitting the layers across pipeline stages instead lets the same GPUs hold up to *n* times the tokens, which is what makes a TP1 × PP4 prefill instance attractive for models like GLM-5.2 and GLM-5.3.

With this PR, a WRITE transfer from a pipeline-parallel prefill instance goes through four steps.
1. The decode scheduler sends the block allocation (and, on a full prefix hit or an abort, the release) to the notify ports of the first stage, as for a pipeline-free prefill instance.
2. Each worker of the first stage forwards every message from the decode to the same worker of the later stages on its node.
3. Each stage writes the layers it holds into those blocks, at the decode addresses of the same layers.
4. Each stage sends `write_done`, and a decode rank finishes the transfer after the last one.

On main none of this holds. Every stage binds the same handshake and notify ports and registers the same MoRI engine key, so stage 1 fails to start. The decode side only notifies `range(prefill_tp)` ports, so with TP1 only stage 0 ever learns the decode blocks. And the peer's layer address comes from this worker's own registration order.

```
vllm/distributed/kv_transfer/kv_connector/v1/moriio/moriio_connector.py's MoRIIOConnectorWorker._remote_layer_mr_offset
idx = self.layer_base_addr_index[layer_name]
...
return remote_moriio_meta.kv_caches_base_addr[idx] - mr_base
```

So stage `s` writes its first layer at the decode's layer 0. On top of that, a decode rank finishes after `num_writers` messages, and `num_writers` comes from the TP mapping alone (1 for prefill TP1 → decode TP4), so it would start decoding after the first stage.

The layer lookup is also wrong without pipeline parallelism whenever the two instances register different layers. vLLM's KV planner groups layers by spec and puts a draft layer in its target's group, so for DeepSeek-V3.2, GLM-5.2 and GLM-5.3 the decode's MTP latent cache sits after the target latents and before every indexer cache. A prefill instance without MTP then silently writes indexer cache 0 into the decode's MTP region, and indexer cache `j` into region `j - 1`.

This PR makes the following changes.
- It adds a stage term to the port offset, `pp_rank * tp_size * dp_size_local`, so stage 0 keeps the ports of a pipeline-free instance, and it appends `:pp<rank>` to the MoRI engine key when PP > 1.
- It has each worker of the first stage forward the decode instance’s messages to the same worker of the later stages, so the decode instance and the router address the prefill instance as a pipeline-free one and need no pipeline size.
- It advertises `layer_base_addr_index` (layer name → region index) in the handshake and looks the peer's layers up by name. A peer without the field is only used when it registered the same number of regions, and otherwise the transfer fails with an error that names both counts.
- It sends `write_done` with `sender = [pp_rank, tp_rank]` and `num_writers` multiplied by `pp_size`. The decode rank counts distinct senders and marks the transfer settled, so late or repeated reports are dropped. Messages without a sender, from older peers, are counted per message, and a single writer's messages don't change.

Pipeline parallelism is only allowed on a WRITE-mode `kv_producer`. A READ-mode decode would have to read each layer from the stage that holds it, and a pipeline-parallel decode would need every producer to address its stages. A stage also refuses a block-outermost KV cache layout, because such a block packs every layer the worker holds, so its stride stops matching the decode's once a stage holds only some of the layers.

Notes:
- Over xGMI, main's completion wait can sleep out the full `transfer_timeout`, or fail with copies still in flight and send no `write_failed`. #64330 fixes the wait and the end-to-end runs were performed with the fix.
- GLM-5.2 and GLM-5.3 layers reuse the sparse-attention top-k of the nearest earlier indexer layer, so on main every pipeline stage must start on a layer that runs its own indexer (for GLM-5.2 at PP4, `VLLM_PP_LAYER_PARTITION=22,20,20,16`).

`pp_size` is read here, but nothing sets it. `request_finished` returns `tp_size` (L1672) but not `pp_size`. So a router that forwards the prefill's returned `kv_transfer_params` to the decode (the serial-WRITE / llm-d path described in `update_state_after_alloc`) leaves the decode thinking the prefill has PP=1.

For a TP1 x PP4 prefill, the decode then notifies only `notify_port + 0`. Stages 1-3 never get the allocation, wait `defer_timeout` (60 s), and send `write_failed`, so every request fails. I checked this with the returned keys: `get_peer_notify_ports(...)` gives `[61005]`, while the stages bind `61005..61008`.

Suggested fix: add `pp_size=self.vllm_config.parallel_config.pipeline_parallel_size,` next to `tp_size=` in `request_finished`.
