- ryansalatin · comment · 2026-10-18T00:35:06Z · [source](https://github.com/vllm-project/vllm/pull/62207#issuecomment-6243782852)

**Tool parser: string parameters that look like numbers are turned into numbers**

With `--tool-call-parser muse` (image `vllm/vllm-openai:muse-spark-open`), a tool parameter
whose JSON schema says `"type": "string"` arrives as a number when its value is all digits.

Example: a tool declares `{"text": {"type": "string"}}`. The model's reasoning says to pass
the text "25", and it emits:

    <atem:parameter name="text">25</atem:parameter>

The client receives `{"text": 25}` instead of `{"text": "25"}`. Values that are not valid JSON
are unaffected: `3%` and `1,500` arrive as strings.

Cause: `_decode_value` in `vllm/tool_parsers/muse_tool_parser.py` runs `json.loads` on every
parameter value and keeps the raw string only if that fails. ATEM parameter values carry no
quotes, so a string made of digits (or `true`, `null`, `[...]`) cannot be told apart from
JSON by its text alone, and the request's tool schema, which says what type is wanted, is not
consulted.

Suggested fix (tested locally on this image): look up each tool's parameter types from
`request.tools`, keep the raw text for parameters typed `"string"`, and decode the rest as
today. In our patch, `_parse_tool_calls` takes an extra `strings: dict[str, set[str]]`
(tool name -> string-typed parameters), built from `request.tools` and passed from both
`extract_tool_calls` and `extract_tool_calls_streaming`. Before: `{"text": 25}`; after:
`{"text": "25"}`; non-string parameters (e.g. arrays) unchanged. Happy to share the diff.
