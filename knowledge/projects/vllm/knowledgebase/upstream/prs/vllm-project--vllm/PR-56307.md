# [ROCm][Kernel] New "hip" GDN backend for gfx1151

[Upstream PR](https://github.com/vllm-project/vllm/pull/56307) · state: closed · merged: True

## Original PR description

## Purpose

GATED_DELTA_NET prefill runs as a chain of Triton kernels that communicate through DDR. At 2048 tokens, 32 MiB are stored and loaded back per layer.

This adds the chunked delta rule (WY representation / UT transform) as a single HIP kernel for RDNA3.5. One block walks the chunks of one (head, sequence) with the state resident in registers and the per-chunk intermediates in LDS, so `h`, `w` and `u` are never formed. A chunk of 32 tokens and the identity `v_new = Tinv (V beta - (K beta exp(g_cs)) S)` keep a whole chunk inside the 64 KB LDS budget.

The kernel is also more accurate than the path it replaces: everything between the inputs and the output stays fp32, where the Triton kernels round `h`, `w`, `u`, `Tinv` and `v_new` to bf16. Against an fp64 token-by-token reference its relative RMS error is 0.53x theirs, and the final state comes out at fp32 precision.

The kernel is exposed as a new GDN prefill backend, `hip`, next to `triton`, `flashinfer`, `cutedsl` and `aiter_flydsl`:

- `auto` selects it on gfx1151, the only RDNA3.5 part run on hardware. Elsewhere `auto` keeps Triton.
- `--gdn-prefill-backend hip` enables it on gfx1150–gfx1153 and fails closed where the op is not built. `--gdn-prefill-backend triton` opts out.
- Built only for gfx1150–gfx1153. bf16 and fp16 Q/K/V/output and head dimension 128; other models resolve to Triton, and any call the kernel cannot serve falls back to Triton per call.
- The Triton/FLA path is untouched.

Also adds a single-GPU benchmark that compares the two paths correctness-first, with model presets, mixed-cache preparation and incremental JSONL output.

<details>
<summary>What the benchmark does</summary>

**What it compares.** The Triton side calls the FLA entry point, `chunk_gated_delta_rule`; the HIP side calls the backend's wrapper, `chunk_gdn_hip_fwd`. Both are timed with their wrapper allocations, so the numbers are what each prefill backend costs per call.

**What it runs.** With no arguments it runs a fixed grid: 16 batches, from a single 32-token sequence up to 256 sequences of 256 tokens, against each of the four head shapes, which are the complete head counts of the Qwen3.5/3.6 family on one GPU. `--preset small|medium|dense|large` restricts the shapes. `--seqlens 941 --seqlens 1,4095` runs an explicit workload instead, repeatable, with `--hv`/`--hg` for its head counts and `--limit` to cut a run short. `--dtype` selects bf16 or fp16. `--dry-run` plans on CPU without importing torch, which is useful to see what a run would cover.

**How it times.** `triton.testing.do_bench` with quantiles, as elsewhere in this repository: it derives the repetition count from a first measurement and clears the L2 cache before each run, so every sample starts cold. Timing the public entry point means the samples include wrapper allocations and host launch gaps, which is what the model actually pays; `--raw-hip` additionally times the preallocated op on its own to separate that overhead from device time.

**What it checks before timing.** Output and final state are compared against the Triton path per sequence and head, with relative RMS and a finite check. `--check` skips timing entirely, and `--exact` adds an independent fp64 token-by-token recurrence, which is what decides whether the kernel is more accurate rather than merely different.

**Reading the output.** Progress goes to stdout; `--jsonl` writes one record per case with the median and the p10/p90 quantiles, the shapes, the inferred launch mode and the environment. Speedup is the Triton median over the HIP median, so above 1× is faster. Compare p10 and p90 before calling a small difference a regression: where those ranges overlap, the two paths are not conclusively different.

</details>

Hardware: one AMD Radeon 8060S (gfx1151). PyTorch `2.12.0+rocm10.1.0a20260803`, Triton `3.8.0+git4cff872c.rocm10.1.0a20260803`. Only gfx1151 has been run on hardware; the other three targets are compile-tested.

### Model-level accuracy

GSM8K on Qwen3.5-9B, whose linear layers are 32 value heads over 16 key heads at head dimension 128, which is the shape this kernel serves; 24 of its 32 layers are linear attention, so every prefill goes through it.

| Path | Accuracy (400 questions, 5-shot, temperature 0) | Correct | Invalid |
|---|---:|---:|---:|
| This kernel | **0.873** | 349/400 | 0.000 |
| Triton chain | **0.870** | 348/400 | 0.000 |

### End-to-end serving

Qwen3.5-9B through `vllm-bench`, 16 requests per point at a fixed input length and a single output token, so the measurement is prefill, which is the only phase this kernel touches. Two repetitions per point; the repetitions agree to within 0.35%, well inside the difference being reported.

| Input tokens | TTFT with kernel | TTFT with Triton | TTFT reduction | Prefill with kernel | Prefill with Triton | Speedup |
|---:|---:|---:|---:|---:|---:|---:|
| 2048 | 1132 ms | 1231 ms | 8.0% | 1809 tok/s | 1664 tok/s | 1.087x |
| 8192 | 5340 ms | 5754 ms | 7.2% | 1534 tok/s | 1424 tok/s | 1.077x |

The two sides are the same wheel and the same workload, differing only in which prefill path runs.

#### 1. 🔵 Nit: core_attn_out slice by element count breaks padded buffers
`vllm/model_executor/layers/mamba/ops/hip_gdn_chunk.py:75`

`chunk_gdn_hip_fwd` slices `core_attn_out[: v.numel()]` along dim 0 and then calls `.view(*v.shape)`. That works only for a 1-D buffer or an exact-size `[T, HV, V]` buffer; a buffer with more than T rows raises a `.view` shape error. The FLA and FlyDSL backends use `core_attn_out.reshape(-1)[:numel]`. No in-tree caller currently passes `core_attn_out` to `chunk_gated_delta_rule`, so this is a latent contract mismatch. Prefer `core_attn_out.reshape(-1)[: v.numel()].view(v.shape)`.

**Who is affected:** Only a future or external caller that hands `forward_hip` a padded output buffer; current in-tree prefill and warmup paths let the wrapper allocate.

_Verified by running it._

#### 2. 🔵 Nit: Host launcher skips input validation enabling OOB access
`csrc/rocm/rdna35_gdn_chunked.cu:590`

The `rdna35_gdn_chunked` launcher checks dtypes, head dim, `H % Hg` and arch. It does not check contiguity, matching shapes between q/k/v/g/beta/out/state, `cu_seqlens` dtype or device, or `n_seqs > 0`. A direct caller of the op with strided or mis-shaped tensors would get out-of-bounds or wrong results instead of a `TORCH_CHECK`. Adding `is_contiguous` and shape checks would harden the op.

**Who is affected:** Only direct users of `torch.ops._rocm_C.rdna35_gdn_chunked` on gfx115x; the vLLM prefill path always passes contiguous, consistent tensors.

#### 3. 🔵 Nit: Support predicate does not mirror all kernel asserts
`vllm/model_executor/layers/mamba/ops/hip_gdn_chunk.py:37`

The `is_hip_gdn_supported` docstring says it mirrors every kernel assertion. It inspects only q/v dtype and head dims, `cu_seqlens` and the batch dim, not k or g/beta dtypes. In-tree inputs always satisfy those checks, so this is a docstring overclaim; fix the docstring or add the missing checks.

**Who is affected:** Only callers that pass inconsistent k/g/beta dtypes; the in-tree prefill path cannot.

#### 4. 🔵 Nit: Chunk metadata built even for HIP backend that ignores it
`vllm/v1/attention/backends/gdn_attn.py:549`

With `gdn_prefill_backend == 'hip'`, the metadata builder still runs `_build_chunk_metadata` (CPU compute plus H2D copies) on each prefill step. The HIP kernel uses only `cu_seqlens`. Skipping it for 'hip', as is done for 'flashinfer', is safe because the FLA fallback rebuilds `chunk_indices` when they are `None`. This is a small per-step overhead, not a correctness issue.

**Who is affected:** gfx115x users of the 'hip' prefill backend pay a small CPU/H2D cost per prefill step.

**Related past reviews:** [#26807](https://github.com/vllm-project/vllm/pull/26807) on `vllm/v1/attention/backends/gdn_attn.py`
