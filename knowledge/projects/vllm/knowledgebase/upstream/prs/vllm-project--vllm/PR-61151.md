# [Test][CPU] Cover native slot-mapping fallback in CPU CI

[Upstream PR](https://github.com/vllm-project/vllm/pull/61151) · state: open · merged: False

## Original PR description

## Overview

Add native CPU regression coverage for the slot-mapping fallback fixed by #61992, and run it in the existing x86 and ARM CPU kernel jobs. Related: #61131.

## Claims

- Exercise the real `ComputeSlotMappingKernel` launcher, `KernelOverride`, and C++ `_C` operator with two hand-computed cases: one request, and multiple requests crossing a KV-block boundary.
- Select the native tests explicitly in both CPU kernel jobs. The test installs an instance-local override, so x86 CI exercises the C++ fallback even when triton-cpu is installed.
- Cover changes to the fallback, MRV1 block table, dispatcher, JIT-warmup code, CPU platform, and test file in the x86 job's trigger dependencies; native sources remain covered by the existing `csrc/cpu/` dependency.

## Validation

Validated on main `0c81a0371f586cc50a0daad6d216fbac21cf1a2d` (2026-10-29), on macOS arm64 with Python 3.14.6, PyTorch 2.13.0, and no Triton. The genuine prebuilt CPU `_C` extension was reused; the slot-mapping C++ source is unchanged relative to the local build checkout. This is component validation, not a full main distribution build.

| Check | Result |
| --- | --- |
| Two native regression cases on current main | 2 passed |
| Same cases with the pre-#61992 wrapper loaded in a temporary process | 2 failed with the original ambiguous Tensor-bool error |
| Native cases followed by the dispatcher suite | 14 passed, 1 skipped (requires Triton) |
| All 17 applicable pre-commit hooks, shell syntax, and `git diff --check` | Passed |
| Local CI selection/dependency checks and ARM script routing | Passed; ARM routing used a Docker stub |

The existing dispatcher suite alone has a Python 3.14 baseline failure: `test_cpu_slot_mapping_override_forwards_kernel_arguments` replaces `torch` with a fake that lacks `Tensor` before deferred annotations are evaluated. Its standalone result is 11 passed, 1 skipped, 1 failed. Running the native cases first caches those annotations, explaining the combined result above; this PR does not change or claim to fix that baseline issue.

Reproduction commands from a CPU-built checkout:

```bash
VLLM_TARGET_DEVICE=cpu VLLM_NO_USAGE_STATS=1 \
  .venv/bin/python -m pytest tests/kernels/test_cpu_slot_mapping.py \
  -q -p no:cacheprovider
VLLM_TARGET_DEVICE=cpu VLLM_NO_USAGE_STATS=1 \
  .venv/bin/python -m pytest tests/kernels/test_cpu_slot_mapping.py \
  tests/model_executor/test_triton_dispatcher.py -q -p no:cacheprovider
bash -n .buildkite/scripts/hardware_ci/run-cpu-test-arm.sh
git diff --check
```

The historical negative control substituted only the wrapper from `556ac15eb9^` in a temporary validation process, using the current launcher and the same native extension. Both cases failed at the obsolete assertion with `RuntimeError: Boolean value of Tensor with more than one value is ambiguous`; worktree production sources were never replaced.

All 17 applicable pre-commit hooks were selected by pre-commit's own file Classifier and run with the original pinned repository revisions and hook settings in a temporary configuration. The unfiltered invocation was stopped while installing unrelated hook environments. Linux x86/ARM hardware CI has not run for this revision. No new model evaluation or performance claim is made.

## Details

#61992 already repaired the fallback's obsolete argument list and added a mocked argument-forwarding regression. These tests add real tensor/C++ result checks through the launcher, while retaining main's production implementation. #51017 targets CUDA `BlockTable` behavior and does not exercise this native CPU fallback.

The local revision changes only `tests/kernels/test_cpu_slot_mapping.py`, `.buildkite/hardware_tests/cpu.yaml`, and `.buildkite/scripts/hardware_ci/run-cpu-test-arm.sh` (63 added lines). The expected slots are literal, hand-computed values; the override is local to each newly constructed owner. Padding, context parallelism, and generic signature validation are outside this contribution.

This protects the current MRV1 fallback used by CPU installations without Triton. #63373 proposes removing that path, so this coverage will need removal or replacement with the final CPU MRV2 implementation when that migration lands. It does not validate the different MRV2 path proposed in #61995.

Earlier engine validation remains documented in the [Linux x86 retest](https://github.com/vllm-project/vllm/pull/61151#issuecomment-6136950323) and [macOS OPT-125m retest](https://github.com/vllm-project/vllm/pull/61151#issuecomment-6173913422). Those results concern the earlier fix revision and are not presented as new main model-evaluation results.
