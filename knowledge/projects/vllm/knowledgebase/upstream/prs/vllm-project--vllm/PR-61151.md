# [Bugfix][CPU] Align slot-mapping fallback with kernel signature

[Upstream PR](https://github.com/vllm-project/vllm/pull/61151) · state: open · merged: False

## Original PR description



## Overview

Fix CPU inference without Triton failing on the first slot-mapping step after #57169. Align the CPU fallback with the current kernel signature. Fixes #61131.

## Claims

- Remove the obsolete `block_size` and `BLOCKS_PER_KV_BLOCK` arguments, match the kernel's parameter names, and forward `KV_CACHE_BLOCK_SIZE` to the existing C++ operator.
- Add a native CPU regression test through the real warmup launch and `KernelOverride`, covering one request and multiple requests crossing a KV-block boundary. Wire it into the x86 and ARM CPU kernel jobs.

## Validation

Tested against the issue's base commit `3fe917abb131` on macOS 26.4.1 arm64, Python 3.14.6, PyTorch 2.13.0, without Triton. The CPU `_C` extension was compiled from that commit; both comparison trees used the same extension.

The model check used float32, head dimension 64, prompt lengths 3 and 18, `enforce_eager=True`, TP=1, `max_model_len=64`, `max_num_batched_tokens=32`, `max_num_seqs=2`, and prefix caching disabled. Runtime tracing observed the real CPU fallback on prefill (21 tokens) and three decode steps (2 tokens each). The generated token IDs matched the reference: `[7, 7, 7, 51]` and `[4, 42, 42, 42]`. This is a small correctness smoke check, not an accuracy benchmark.

Independent Linux x86_64 retest by @SeverinVisionary on 2026-10-13 ([results](https://github.com/vllm-project/vllm/pull/61151#issuecomment-6136950323)): compared `5e0ac9d76` against parent `3fe917abb131` with `HAS_TRITON=False`. The small V1 `LLM.generate` check fails at the first slot-mapping call on the parent; with the fix, both outputs match the same-run Transformers reference.

This retest used each commit's exact Python sources with the same genuine CPU extension built from the parent; the native source is unchanged between the commits. It validates these Linux CPU cases through a component comparison, not a full fix-head distribution build. This independent retest did not exercise macOS or ARM, and upstream CPU CI remains pending.

Independent real-checkpoint retest by @saikishore-p ([results](https://github.com/vllm-project/vllm/pull/61151#issuecomment-6173913422)): Apple M1 Max (macOS 27.0.1 arm64), Python 3.12.12, PyTorch 2.14.0, Transformers 5.19.0, and `HAS_TRITON=False`. The reporter used a full editable CPU build of main `e2aabc8b15` with PR head `5e0ac9d76` applied on top. The original issue reproducer fails on that main and returns `[80, 81, 82]` with the fix. The native regression and dispatcher suites report 7 passed and 1 skipped with the fix.

With `facebook/opt-125m` (float32, `block_size=32`, `enforce_eager=True`, greedy, 40 generated tokens, `ignore_eos=True`), all three prompts produce token IDs identical to HF Transformers; the unpatched main fails on the first slot-mapping step. Prompt lengths were 6, 8, and 27 tokens, with the longest case crossing the 32- and 64-token KV-block boundaries during decode.

This is independently reported, checkpoint-specific correctness validation on that macOS CPU configuration. It is not a full CPU/vLLM test-suite run, broad model-accuracy evaluation, or performance benchmark, and does not cover other platforms or distributed execution. Upstream CPU CI remains pending.

```python
import tempfile

import torch
from transformers import LlamaConfig, LlamaForCausalLM

from vllm import LLM, SamplingParams

torch.set_num_threads(2)
torch.manual_seed(42)
config = LlamaConfig(
    vocab_size=64, hidden_size=256, intermediate_size=512,
    num_hidden_layers=2, num_attention_heads=4, num_key_value_heads=4,
    max_position_embeddings=256, bos_token_id=1, eos_token_id=2, pad_token_id=0,
)
config._attn_implementation = "eager"
reference = LlamaForCausalLM(config).eval()
prompts = [[1, 4, 7], [1] + list(range(3, 20))]
expected = []
with torch.inference_mode():
    for prompt in prompts:
        tokens = list(prompt)
        for _ in range(4):
            logits = reference(torch.tensor([tokens], dtype=torch.int64)).logits
            tokens.append(int(logits[0, -1].argmax()))
        expected.append(tokens[len(prompt):])

with tempfile.TemporaryDirectory() as checkpoint:
    reference.save_pretrained(checkpoint)
    del reference
    llm = LLM(
        model=checkpoint, skip_tokenizer_init=True, dtype="float32",
        enforce_eager=True, max_model_len=64, max_num_batched_tokens=32,
        max_num_seqs=2, enable_prefix_caching=False,
        distributed_executor_backend="uni", async_scheduling=False,
    )
    outputs = llm.generate(
        [{"prompt_token_ids": prompt} for prompt in prompts],
        SamplingParams(temperature=0, max_tokens=4, ignore_eos=True),
        use_tqdm=False,
    )
    actual = [list(output.outputs[0].token_ids) for output in outputs]
    assert actual == expected, (actual, expected)
    print(actual)
```

## Details

After #57169, the CPU wrapper retained two removed parameters. Because its names also differed from the kernel's, `KernelOverride` forwarded the launch positionally: the slot tensor became `block_size`, and the CP rank became `BLOCKS_PER_KV_BLOCK`. The obsolete assertion then evaluated a multi-element tensor as a bool before reaching C++.

This change restores the wrapper's contract and lets the existing dispatcher forward by name. The C++ mapping formula and GPU kernel are unchanged, and the CPU context-parallelism guard remains. The fallback is registered only on CPU without Triton; at this base that uses MRV1. Padding behavior and a generic override-signature validator are outside this fix. Linux/x86, Linux/ARM, CUDA, and multi-rank execution were not run locally; CPU CI registration is included, but upstream CI has not run yet.

No competing fix was found for #61131. The slot-mapping workarounds in #61127 and #61137 are excluded from those PRs; #60924 targets CPU MRV2 and does not change this fallback.
