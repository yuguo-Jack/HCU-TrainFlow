# [Kernel][ROCm] Flash-decoding sequence partitioning for the Triton paged decode path

[Upstream PR](https://github.com/vllm-project/vllm/pull/53384) · state: open · merged: False

## Original PR description

## Purpose

`kernel_paged_attention_2d` launches a grid of `(num_seqs, num_kv_heads)`. During
decode that is a handful of programs — on a small batch, single digits against a
device with hundreds of compute units — and each program walks its whole
sequence, so decode throughput falls off sharply with context length.

This splits the sequence across programs: one per `(seq, kv_head, partition)`
accumulating an unnormalised softmax numerator with its running max and
denominator, plus a reducer that combines the partials, applies sinks, divides,
and does the fp8 epilogue.

This is the same structure the ROCm custom kernel already uses internally via
`_PARTITION_SIZE_ROCM`. It is unavailable to anything that falls back to Triton
— which on ROCm includes **any hybrid mamba+attention model**, since those pad
the attention block size to match the mamba page size and
`use_rocm_custom_paged_attention` only accepts `block_size` 16 or 32.

### Cudagraph safety

The partition grid must **not** be sized from the runtime `max_seq_len`. Both
`RocmAttentionMetadataBuilder` and `TritonAttentionMetadataBuilder` set
`seq_lens` to 1 in `build_for_cudagraph_capture()`, and both declare
`AttentionCGSupport.ALWAYS`, so a grid derived from it is captured at ~1
partition and then **silently truncates the tail of every long sequence at
replay** — wrong results, not a slowdown. The bound comes from the block table's
width times the physical block size, which is fixed for the life of a captured
graph. Oversized grids are safe: surplus partitions return without storing, and
the reducer recomputes the partition count from the true per-sequence length.

The count takes the finest partition the scratch budget allows rather than
targeting occupancy at that bound, since the bound is `max_model_len` while real
requests are much shorter. A batch that already saturates the device is declined
outright, which keeps scratch small by construction.

## Test Plan

```
pytest tests/kernels/attention/test_triton_paged_decode_seq_partition.py
```

Compares partitioned against unpartitioned on identical tensors over ragged
batches (surplus partitions become the common case rather than an edge case) and
over block-table widths that emulate a captured graph. Two further tests assert
the partitioner is actually engaged — a declined path sends both arms through the
same code and passes regardless of correctness — and that a saturating batch
declines partitioning.

End-to-end: 2× MI210 (gfx90a), Qwen3.8-27B W8A8 TP=2, block_size 784,
head_size 256, **speculative decoding disabled** so this path is exercised.

## Test Result

17/17 pass.

End-to-end decode, TTFT excluded:

| context | before | after | |
|---|---|---|---|
| 2K | 33.7 | 26.5 | 0.79× |
| 41K | 5.5 | **28.4** | **5.2×** |
| 100K | 2.6 | **30.1** | **11.6×** |

Decode becomes essentially flat in context length. **Short context regresses
~21%**, which is the cost of sizing the grid for the cudagraph bound rather than
the live sequence; I have left that in the table rather than omit it.

Kernel level at batch 1: 20.6× at 41K, 30.2× at 102400. At batch 4: 7.3× and 8.4×.

### Important scope note

This path is **not** reached when speculative decoding is enabled: every step
then has `query_len > 1` and is routed to `context_attention_fwd` instead. With
spec decode on, this change measures as exactly zero end-to-end. The companion PR #53383
partitions that kernel's cached-context scan, which is where a spec-decode
deployment actually spends its time, and is the one to look at first if you are
running speculative decoding.

### Limitations

- **Only tested on gfx90a.** No NVIDIA hardware was available to me.
- The occupancy target and scratch budget defaults were tuned on one machine;
  both are exposed via `VLLM_TRITON_PA_TARGET_PROGRAMS` and
  `VLLM_TRITON_PA_SCRATCH_BUDGET_MB`, and the path can be disabled with
  `VLLM_TRITON_PA_SEQ_PARTITION=0`.
