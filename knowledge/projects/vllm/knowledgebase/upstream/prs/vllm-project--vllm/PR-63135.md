# [Bugfix][Multimodal] Resolve Qwen-Omni use_audio_in_video from merged processor kwargs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63135) · state: open · merged: False

## Original PR description



## Overview

Fix Qwen2.5-Omni / Qwen3-Omni crashing when `use_audio_in_video` is set at the engine level via `--mm-processor-kwargs`, and make the scoped `videos_kwargs` form work end to end. The flag now resolves from the merged engine + request kwargs at every detection point, with the HF `videos_kwargs` scope taking precedence, matching HF processor semantics.

## Claims

- Engine-level `--mm-processor-kwargs '{"use_audio_in_video": true}'` now works: prompt updates derive audio placeholders from the interleaved video placeholder instead of crashing on `video_audio_item_num != video_updates_num + audio_updates_num`.
- The scoped form `--mm-processor-kwargs '{"videos_kwargs": {"use_audio_in_video": true}}'` is honored consistently by the HF processor, the prompt updates, the model's MRoPE logic, and the renderer's media loading (previously ignored outside the HF processor).
- `_postprocess_hf_mm_data` records the effective flag, so model layers that gate MRoPE positioning on the `use_audio_in_video` tensor see the true value instead of always `False`.
- The "video without audio track" validation is no longer silently skipped when the flag is set at the engine level.
- The encoder profiler's video-only dummy input is paired with its companion audio item, so profiling works with the flag enabled.

New coverage:

- `test_videos_kwargs_scoped_use_audio_in_video`: the scoped form behaves like the flat one.
- `test_get_use_audio_in_video_prefers_video_scope`: flat/scoped resolution with scope precedence.
- `test_encoder_profiler_pairs_dummy_audio_with_video`: `get_dummy_mm_inputs({"video": 1})` succeeds with the flag set.
- `test_parse_video_resolves_use_audio_in_video_scope`: the renderer fetches the video's audio track for both forms.

Existing regression tests (`test_audio_in_video_cache_correctness`, `test_use_audio_in_video_without_audio_track`, `test_audio_in_video_metadata_only`) still pass.

## Details

Root cause: `use_audio_in_video` had four detection points reading it from unreliable sources — `_get_prompt_updates` and `_postprocess_hf_mm_data` read raw request-level `hf_processor_mm_kwargs` (empty when the flag is engine-level), `_get_hf_mm_inputs` gated its audio-track validation the same way, and the renderer's `parse_video` read only the flat namespace. The HF processor itself receives merged kwargs via `call_hf_processor`, so it interleaved audio while vLLM-side logic did not know.

The fix introduces `resolve_mm_processor_kwarg` / `get_use_audio_in_video` in `vllm/multimodal/utils.py` (flat-or-`videos_kwargs` resolution, scope wins) and uses the merged kwargs at every detection point. `BaseMultiModalProcessor._pair_dummy_mm_counts` is a new no-op hook on the dummy-input path, overridden by the Qwen-Omni processor to add one audio item per video. The online renderer now passes merged engine + request kwargs as `default_mm_processor_kwargs` so media loading sees engine-level config.

Tradeoffs: `get_merged_mm_kwargs` is a cheap dict merge (no GPU sync); the explicit merge in `_get_prompt_updates` is idempotent with the one inside `get_hf_processor`. Note: engines configured with `--mm-processor-kwargs` now include those kwargs in mm cache hashes (semantically correct, but existing cache entries keyed without them will miss once after upgrade). `_pair_dummy_mm_counts` changes the per-modality encoder-profile dummy batch when the flag is enabled, which is required for the HF processor to accept the dummy input.

Limitations: `resolve_mm_processor_kwarg` resolves a single scope level only. GPU E2E serving with real video files was not run locally (no GPU); CI's `tests/entrypoints/multimodal/openai/chat_completion/test_audio_in_video.py` covers that path.

🔴 Nemotron-Nano-Omni servers with engine-level `use_audio_in_video` will now fail chat requests whose video has no audio track; on the base branch such videos simply ran as video-only. The chat parser now sees the engine flag through the new `default_mm_processor_kwargs` merge (online_renderer.py:801). [also at: vllm/renderers/online_renderer.py:804 - Nemotron Nano Omni servers started with engine-level `use_audio_in_video` will now fail chat requests whose video has no audio track or audio over the duration cap.]

<details>
<summary>Why this was flagged</summary>

An operator runs Nemotron-Nano-Omni with `--mm-processor-kwargs '{"use_audio_in_video": true}'` and sends a chat request whose `video_url` points to a video with no audio stream. On the base branch the renderer passed only the request-level kwargs, so no audio was fetched. NanoNemotronVL `apply` (nano_nemotron_vl.py:709-746) then pulled audio from the bytes and quietly set has_audio=False for silent videos (lines 670-676). After this change, online_renderer.py:801-804 merges `mm_config.mm_processor_kwargs` into the parser kwargs. So `get_use_audio_in_video` is true at content_parser.py:511 (async) and :281 (sync), and the parser calls `fetch_audio(_async)` on the video URL. For a silent video, `load_audio_pyav` raises ValueError("No audio stream found.") (multimodal/media/audio.py:125), and the request fails in the renderer. The model's own graceful fallback is never reached.

**Verification:** After this change, online_renderer.py:801 sets `default_mm_processor_kwargs=recursively_merge_kwargs(mm_config.mm_processor_kwargs, request.mm_processor_kwargs)`, so the parser now sees the engine flag. PyAV raises `ValueError("No audio stream found.")` at media/audio.py:124-125. Either way the error propagates and the whole chat request fails instead of running video-only.

</details>
