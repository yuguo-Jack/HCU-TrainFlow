# [Bugfix][Attention] Use a 32-wide KV tile for FP8 queries in grouped DiffKV launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61928) · state: open · merged: False

## Original PR description



## Overview

Fix a Triton compile error in DiffKV grouped launches with an FP8 query. Because of it, MiMo-V2 with `--kv-cache-dtype fp8` on SM89/SM12x fails at startup with MTP, and dies on short prompts without speculative decoding. The fix keeps the KV tile at 32 or more for FP8 queries.

Fixes #61927. Follow-up to #58128 (FP8 KV cache and FP8 query for DiffKV) and #59085 (grouped 3D launches for DiffKV); the error is in v0.32.0rc0–rc2, not in v0.31.x.

```
triton.compiler.errors.CompilationError: at 223:15:
        acc += tl.dot(P.to(V.dtype), V)
               ^
Input shapes should have M >= 1, N >= 1 and K >= 32
```

## Claims

- `vllm serve` of MiMo-V2-Flash (reduced dummy-weight config) with `--kv-cache-dtype fp8` fails on `main` and serves with this change on an RTX PRO 6000 (SM120), in all of these cases:
  - MTP 1 and MTP 3.
  - No speculative decoding, with short prompts and with short last prefill chunks.
  - Eager, PIECEWISE, FULL_DECODE_ONLY and Model Runner V1.
- The added test cases fail on `main` (`K >= 32`, `assert 16 == 32`) and pass with this change.
- Only grouped launches with an FP8 query change: their tile goes from 16 to 32. That is the same FP8 minimum the decode path and `_get_tile_size` already use.
  - On CUDA, these launches failed to compile before.
  - On ROCm gfx942/gfx950 the query is also FP8, but AMD Triton has no K minimum. There these launches compiled with tile 16 and now use 32. This is not measured on ROCm.
  - BF16 queries are unchanged.

## Details

**Root cause.**
- On CUDA, `supports_quant_query_input` is set, so an FP8 KV cache also quantizes the query to FP8.
- The DiffKV kernel casts K and V to the query dtype (`K_load.to(Q.dtype)`, `V_load.to(Q.dtype)`). So `tl.dot(P.to(V.dtype), V)` is an FP8 dot that reduces over the KV tile.
- Triton's NVIDIA backend requires K >= 32 for 8-bit dots on every architecture (`min_dot_size`; same in 3.7.1 and 3.8.0).
- The launcher picks tile 32 for FP8 queries (`16 if q.element_size() >= 2 else 32`).
- #59085 then overrides that with `_SPEC_3D_TILE = 16` for grouped launches. A full-attention batch is grouped when all of these hold:
  - `1 < max_seqlen_q <= 16`;
  - its tokens fit the 3D scratch;
  - `num_seqs <= seq_threshold_3D`;
  - `max_seqlen_q × GQA > 16`.
- The condition (`spec_3d`) looks at the query length, not at whether the batch is decode-only, so short prefills match too. This PR does not change which batches are grouped.
- MiMo-V2 full-attention layers have 16 query heads per KV head up to TP4, so 2 query tokens already group. At TP8 (GQA 8) it takes 3 or more.

**How the two changes meet.**
- #59085 targets setups that keep the query in BF16 with an FP8 KV cache. With a BF16 query, tile 16 is valid.
- #58128 added the FP8 query.
- The FP8 query only reaches the grouped launch when both changes are present. The existing FP8-query test uses q_len 1 and 129, which do not take the grouped path, so it did not cover this case.

**Fix.** Clamp the tile to at least 32 for FP8 queries, after the grouped override. This follows #21197, which set the FP8 tile minimum by element size in the base kernel. Grid, `BLOCK_M` and warp count are unchanged.

**Alternative considered: don't group when the query is FP8.** I kept grouping so that FP8 follows the same path as BF16, which is #59085's design. Whether to group is a policy for both dtypes (cf. #58141), and a compile fix should not fork it by dtype.

The kernel timings agree. Against ungrouped, FP8 with tile 32 lands in the same range as BF16 with tile 16 as shipped. Grouped is also 6–14× faster (geomean) than the 2D path these batches used before #59085.

**Duplicate-work check.**
- No issue or PR reports this error. Searched: the error text, `K >= 32`, `TRITON_ATTN_DIFFKV`, DiffKV with fp8 / MTP, MiMo with fp8 / MTP.
- I looked through the diffs of the open DiffKV PRs and found none that changes the grouped tile for FP8 queries.
- #58141 touches the same grouping condition; the two changes are independent, apart from a possible small rebase.

**Limitations.**
- Validated end to end on SM120 only. SM89 is expected to behave the same, since the Triton constraint is architecture-independent.
- No full-weight model evaluation: MiMo-V2-Flash (309B) does not fit on the available GPUs. The kernel-level checks above show that the fixed path gives the same output as the ungrouped path.
- ROCm: grouped FP8-query launches move from tile 16 to 32 without a measurement (see Claims).
- CI coverage:
  - The GPU case runs on CUDA SM89+, so the L4 attention shards and the H100 DiffKV job should run it, and it should fail there on `main`.
  - The host-only check runs everywhere the file runs.
  - SM12x has no CI runner.
