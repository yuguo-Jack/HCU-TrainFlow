# [Bugfix][Attention] Use a 32-wide KV tile for FP8 queries in grouped DiffKV launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61928) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

In v0.33.0, MiMo-V2 with `--kv-cache-dtype fp8` crashes on an RTX PRO 6000 (SM120): with MTP the engine fails to start (default CUDA graph settings), and without speculative decoding it dies on the first short prompt. The failing code is identical in v0.32.0 and `main`, and SM89/SM11x GPUs take the same path. There MiMo-V2 uses Triton DiffKV, whose grouped launches pick a 16-wide KV tile that Triton cannot compile for an FP8 query. This keeps the tile at 32 or more for FP8 queries. Fixes #61927.

```
triton.compiler.errors.CompilationError: at 223:15:
        acc += tl.dot(P.to(V.dtype), V)
Input shapes should have M >= 1, N >= 1 and K >= 32
```

## Claims

- MiMo-V2-Flash with `--kv-cache-dtype fp8` starts and serves, with and without MTP (SM120, TP 1, reduced model, dummy weights).
- Only grouped launches with an FP8 query change, from tile 16 to 32: the FP8 minimum the other launch paths already use. BF16 queries are unchanged.

## Validation

End to end, RTX PRO 6000 (SM120), `vllm/vllm-openai:v0.33.0` vs. the same image plus this patch, MiMo-V2-Flash reduced to 4 layers with the real attention shapes, dummy weights, three requests per started server.

| KV cache | speculative decoding | v0.33.0 | this PR |
|---|---|---|---|
| fp8 | MTP 1 | engine fails to start | 3/3 served |
| fp8 | none | engine dies on the first (5-token) prompt | 3/3 served |
| auto (bf16) | MTP 1 | 3/3 served | 3/3 served |

On an earlier nightly with the same `triton_unified_attention_diffkv.py`, MTP 3 also failed to start, and with `--max-num-batched-tokens 256` a 256 + r token prompt died when the last chunk was r = 2, 5 or 8 tokens; this PR served all of them.

**Tests**

```

# v0.33.0 image + this PR: 102 passed, 96 skipped (cases that need FA3/FA4 as the reference)
# v0.33.0 image: the 2 new cases fail (K >= 32; assert 16 == 32)
```

The new GPU case groups an FP8 query (q_len 8, 8 query / 2 KV heads); the host check asserts the launch tile. CI runs this file in the L4 (SM89) attention kernels job and the H100 DiffKV job.

Logs of the earlier nightly runs: https://gist.github.com/yuy-blip/9984f7a03950ea5e84f150ae63b60881

## Details

**Root cause.** On CUDA an FP8 KV cache also quantizes the query, and the DiffKV kernel casts K and V to the query dtype, so `tl.dot(P.to(V.dtype), V)` is an FP8 dot over the KV tile. The launcher picks tile 32 for FP8, but #59085 then overrides it with `_SPEC_3D_TILE = 16` for grouped launches, and Triton's NVIDIA backend requires K >= 32 for 8-bit dots. #59085 targeted BF16 queries; the FP8 query came with #58128. Grouping does not check whether the batch is speculative, so short prompts and short last prefill chunks (2-16 tokens) take this path too.

**Scope.** MiMo-V2 picks Triton DiffKV when FA3/FA4 DiffKV is unavailable (FA3 needs SM9x, FA4 SM10x); below SM89 the Triton backend rejects an FP8 KV cache. Run on SM120 only; SM89 and SM11x should take the same path but were not run. On ROCm (except gfx90a/gfx11) the query is also FP8 on `main`, and these launches now use tile 32 instead of 16; not measured. No full-weight eval: the model does not fit, and on CUDA only launches that failed to compile change. Without this fix, `--kv-cache-dtype auto` avoids the crash.

**Not a duplicate:** no other issue or PR reports this error. Two open PRs touch the same `tile_size` line (a ROCm launch config and an XPU override), but neither handles grouped FP8 launches.
