# [WIP][Kernel] Enable GDN batch-invariant prefix caching

[Upstream PR](https://github.com/vllm-project/vllm/pull/55868) · state: open · merged: False

## Original PR description

## Purpose

Enable `VLLM_BATCH_INVARIANT=1` together with prefix caching on Qwen GDN hybrid models.

Today this fails at scheduler init (`NotImplementedError: ... does not yet support Mamba cache alignment`) because prefix cache puts GDN into mamba `align` mode while BIC needs a 64-token FLA grid.

This PR:

- Uses one shared grid `lcm(FLA_CHUNK_SIZE=64, mamba_state_block_size)` for prefill chunks and prefix-cache hits (hits are floored onto the grid; a full-prompt hit is not).
- Rounds hybrid `block_size` up to a multiple of 64 (1056 → 1088) so the grid stays usable for short prefixes.
- Temporarily includes GDN BIC from #49827 / #45819 so CI can run while those PRs are still open. Drop that commit when they land. 

Related: #49827, #45819, #48613, #42960.

I found with the help of claude an additional source of variance in my setup, separate from the temperature. The Marlin kernel seems to ignore batch-invariant mode and picks its own reduction strategy based on batch size.

What claude summaries : 

Our setup: vLLM v0.31.0 + this branch, RTX A5000 (sm_86), VLLM_BATCH_INVARIANT=1, a 4-bit compressed-tensors W4A16 checkpoint on TP=2. CompressedTensorsWNA16 selects MarlinLinearKernel through choose_mp_linear_kernel, which has no batch-invariance check. Marlin then chooses its exec config from size_m (small vs large batch thread configs in marlin.cu), so a row's K-reduction order depends on how many rows share the call. auto_awq.py already skips Marlin under VLLM_BATCH_INVARIANT, but the compressed-tensors path doesn't.

i.e. a model quantized with compressed-tensors w4a16 doesn't follow a exec path that is batch invariant.

What I see in my tests : 
The same request is bit-identical when sent alone, but its logprobs change as soon as other requests are in the batch, and greedy output diverges after a few dozen tokens (which happened a lot during my previous tests).

What Claude proposed as a solution : 
Marlin is called on fixed 64-row chunks under BI (padding the last one, atomic-add disabled). That made the outputs bit-identical alone vs concurrent on my tests, with negligible overhead (+2% slower, but was with small requests ~ 300-1500 tokens). Might be worth handling in the branch, or upstream.


Quick update on the Marlin issue, with results : 

**Setup:** vLLM v0.31.0 + this branch, 2× A5000 (sm_86), TP=2, `VLLM_BATCH_INVARIANT=1`, torch.compile + CUDA graphs, prefix caching, Qwen3.5 27B 4-bit (compressed-tensors W4A16 = Marlin). Temperature 0, 1500 generated tokens, logprobs compared bit-for-bit.

| Config | Same request, repeated | Alone vs. concurrent |
|---|---|---|
| Before fix |  identical | logprobs differ (4/4), text diverges after ~45 tokens |
