# [Model] Add Flint (RecursiveSI/flint)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62938) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds [Recursive's Flint](https://huggingface.co/RecursiveSI/flint), a MoE model with 40B total and 2.5B active parameters, with day-0 support for both released checkpoints:
- `RecursiveSI/flint`: BF16 safetensors;
- `RecursiveSI/flint-nvfp4-gguf`: an NVFP4 GGUF, served weight-only (W4A16).

The model lives in `vllm/models/flint/`, together with Flint-specific kernels for small-batch decode on a single Blackwell GPU.

## Claims

- **Architecture:** 49 layers.
  - Attention: 35 layers use a 513-token sliding window with RoPE; 14 use full attention with no positional encoding. All layers use GQA (32 query / 4 KV heads, head dim 128), per-head Q/K RMSNorm and learned attention sinks.
  - MoE: 256 experts with sigmoid top-6 routing and renormalized weights, plus a shared expert. Layers 0–1 are dense.
  - Context: 262K tokens. The untied LM head produces FP32 logits.
- **NVFP4 GGUF:**
  - Each 64-value superblock is 4 × (UE4M3 scale + 16 E2M1 codes), with an FP32 scale per tensor (per expert for MoE weights). It is repacked losslessly at load into the ModelOpt NVFP4 layout and runs on the existing W4A16 kernels.
  - Config and tokenizer come from the BF16 repo (`--hf-config-path`, `--tokenizer`).
  - It loads by HF repo ID or local path, and needs `gguf>=0.19.0`.
- **Numerics:** the kernels follow the reference implementation's rounding points.
  - FP32 fused add + RMSNorm, rounded once.
  - FP32 gate/up for the routed experts.
  - Exact SiLU after BF16 rounding for the shared expert.
  - FP32 RoPE table, BF16 router logits.
- **Speed:** single-GPU (TP=1) forward time on GB200 with 100K tokens of context, from `vllm bench forward`.

  | | stock vLLM layers | this PR |
  |:---|---:|---:|
  | NVFP4 decode, batch 1 | 4.81 ms | **1.78 ms** (2.7×) |
  | NVFP4 decode, batch 8 | 8.24 ms | 5.70 ms (1.45×) |
  | NVFP4 prefill, 8K tokens | 206.6 ms | 144.6 ms (1.43×) |
  | BF16 decode, batch 1 | 3.53 ms | 2.34 ms (1.51×) |

  Served end to end, batch-1 NVFP4 decode at 100K context takes 2.06 ms per token (about 485 tokens/s).
- **Kernels:**
  - fused Q/K norm + RoPE + KV-cache write (Triton);
  - small-batch MoE: a GEMV router with fused top-k, plus expert-indexed GEMVs, with FlashInfer's CuTe DSL W4A16 grouped GEMM for larger batches;
  - a small-batch NVFP4/BF16 dense GEMV (CuTe DSL) on the same packed weights;
  - norm and SiLU kernels with the reference's rounding;
  - CuTe DSL split-KV decode attention with sinks and sliding windows;
  - for up to 8 decode requests, a 7-kernel-per-layer path chained with programmatic dependent launch (346 kernels per forward instead of 1,096).
- **Fallback:** other configurations use vLLM's standard layers: TP > 1, EP, and GPUs outside the SM100 family such as sm_120.
- **Serving:** tool calling and reasoning use the existing `glm47` parsers; see the recipe in `recipes/models/RecursiveSI/flint.yaml`.

| GSM8K (1,319, chat, 16K max tokens) | 0.950 | 0.950 |

| MRCR (48 samples, up to 114K-token prompts; mean of 3 runs) | 0.47 | 0.46 |

- **Logit agreement:** prompt-logprob KL against an FP32 reference forward pass stays at the level of the stock-layer implementation: 0.21 / 0.04 / 0.11 for BF16 and 0.13 / 0.03 / 0.06 for NVFP4, over 2–6K-token prompts. The model is ill-conditioned in BF16; an independent BF16 implementation agrees with FP32 on only 90–96% of top-1 tokens. This KL criterion is therefore used instead of bitwise comparison.
- **Unit tests:** `tests/models/flint/` covers each kernel against a reference implementation, plus the GGUF repack. It runs in one new B200 CI step.

## Details

- **Changes to shared code:**
  - registry entries (model, config, test registry);
  - one docs row;
  - `docker/Dockerfile`: installs `gguf>=0.19.0` in the `vllm-openai` image, so the NVFP4 GGUF checkpoint loads out of the box.
  - `maybe_override_with_speculators`: skips speculators detection for a single local file, so a `.gguf` path can be passed as `--model`.
- **No torch.compile:** the model runs eagerly, and decode runs under CUDA graphs.
- **Rust frontend:** not supported yet for this recipe. It rejects `--exclude-tools-when-tool-choice-none`, `--hf-config-path` and `--tokenizer`; the recipe sets `VLLM_USE_RUST_FRONTEND=0`.
- **Known limitations:** prefill for short prompts is CPU-bound by eager kernel launches. Batch-1 decode time varies by a few percent between processes; this is GPU state, not configuration.
- **Not a duplicate:** no other open or closed vLLM PR or issue covers Flint.
- **AI assistance:** Claude Code was used to write the implementation, kernels and tests, and to run the benchmarks and evals. I reviewed the changes.

**CI fix (`6d3d1dfd89`):** the Flint B200 step failed with `ptxas error: Unexpected instruction types specified for 'cvt'` in the Triton NVFP4 MoE decode kernels.

**Cause.** `cvt.rn.bf16x2.e2m1x2` needs PTX ISA 9.2, which means ptxas 13.2 or newer. The CI image builds Triton from source, and that Triton uses the image's system ptxas from CUDA 13.0. The Triton wheel instead bundles a CUDA 13.3 `ptxas-blackwell`, which is why the tests passed locally. The CuTe DSL kernels use the same instruction but bring their own ptxas.

**Fix.** At import, `moe.py` checks which ptxas Triton will use for Blackwell (`get_ptxas(100).version`):
- **ptxas 13.2 or newer:** the decode keeps the BF16 form, so speed and outputs are unchanged.
- **Older ptxas:** it uses `cvt.rn.f16x2.e2m1x2` and an FP16 multiply. Every E2M1 × E4M3 product is exact in FP16 too. The exhaustive `test_dequant_exact` covers whichever form is active.

**Validation** (one GB200):
- `pytest tests/models/flint`: 165 passed, 1 skipped, both with CI's CUDA 13.0 ptxas (`TRITON_PTXAS_BLACKWELL_PATH`, FP16 path) and with the default ptxas (BF16 path).
- NVFP4 decode at batch 1/3/4/6, A/B on the same GPU: unchanged (within ±0.05%).
- An FP16-only version was 2–3% slower at batch 3–6, because widening FP16 to FP32 costs an instruction per element. That's why the BF16 path stays where ptxas supports it.

The other two failures are unrelated to this PR:
- `test_gptoss_mxfp4mxfp8_moe_flashinfer_cutlass`: the server could not start (`OSError: [Errno 98] Address already in use`).
- `test_w4a16_machete_bfloat16_deterministic`: a Machete nondeterminism check, which this PR does not touch.
