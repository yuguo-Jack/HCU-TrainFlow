# [ROCm][Perf][Qwen4Exp] Dispatch HC combine_and_mix to the AITER FlyDSL two-stage kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/59442) · state: open · merged: False

## Original PR description

## Purpose

🚨vLLM hook for [ROCm/AITER#5913](https://github.com/ROCm/aiter/pull/5913): need to wait until AITER merge + release🚨

Every HyperConnection boundary in Qwen3.8-Flash-Next (`qwen4_exp`) runs `GatedResidual.combine_and_mix` as five launches: combine+RMSNorm, the merged down+inject GEMM, SiLU, the up GEMM, and the gate mix. That happens twice per layer, so 95 times per decode step. At decode batch sizes the kernels are close to the per-launch floor, so the chain is mostly launch cost.

ROCm/aiter#5913 implements the whole boundary in FlyDSL. Its skinny decode path covers small token counts. This PR routes `combine_and_mix` through it on ROCm:

- `torch.ops.vllm.qwen4_exp_hc_two_stage_combine_and_mix` is a custom op. At `1 <= M <= VLLM_ROCM_HC_FLYDSL_MAX_M` (default 4) it calls `flydsl_gr_two_stage_combine_and_mix`. Otherwise it runs the existing Triton kernels and `rocm_unquantized_gemm_impl`, the same work as today's path.
- The M check is inside the op because the model is compiled once, with a symbolic token count. A Python branch on `x.shape[0]` in `forward` is resolved at trace time on the 16384-token profile run, which would compile the fast path out.
- The RMSNorm weight is folded into the down+inject weight once per layer, on the first (eager) call, so the fold never runs inside a graph capture. The f32 norm weight is cached next to it.
- The injection is returned in the same `[tokens, 336]` column-slice layout as the fallback, so Inductor's stride check against the fake passes on both paths.
- Opt-in via `VLLM_ROCM_HC_FLYDSL_TWO_STAGE=1`. The default is unchanged, and the path logs once when it is live.

- GSM8K 5-shot on the checkpoint card's recipe, both arms, same servers as the A/B.
