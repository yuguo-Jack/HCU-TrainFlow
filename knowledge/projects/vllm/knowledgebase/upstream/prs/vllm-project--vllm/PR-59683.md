# [Bugfix][Core] Keep the aligned sliding-window prefix hit when dropping the EAGLE block

[Upstream PR](https://github.com/vllm-project/vllm/pull/59683) · state: open · merged: False

## Original PR description

## Purpose

Before: in `SlidingWindowManager.find_longest_cache_hit`, when no full window of cached blocks is found, the cached run at the start of the prompt is used as the hit. With EAGLE and `alignment_tokens > block_size`, that run is aligned twice. It is re-aligned by its length *before* the EAGLE block is dropped, then the EAGLE block is dropped and the result is aligned again. The first alignment is wrong for EAGLE: the run already ends at a block that is aligned *after* the drop, so the hit loses up to one alignment unit.

Example: block size 2, `alignment_tokens=6`, sliding window 20, EAGLE on, blocks 0-10 cached and block 11 not. The run ends at block 9 (aligned for EAGLE: 9 * 2 % 6 == 0). The hit should be blocks 0-8 = 18 tokens, but the function returns 12 tokens.

After: the first re-alignment is removed. Without EAGLE it was a no-op, because the run always ends at an aligned block. With EAGLE the drop lands on an aligned length. The existing re-alignment after the EAGLE drop is kept.

This only changes how much of a cached prefix is reused (a shorter hit was still correct). It does not change model outputs, so no model eval is included.

Not a duplicate: I searched open PRs and issues for sliding-window / EAGLE / alignment prefix-cache fixes. The closest, #51295, fixes the EAGLE drop in the hybrid coordinator, not this fallback path in `SlidingWindowManager`, which is unchanged on main.
