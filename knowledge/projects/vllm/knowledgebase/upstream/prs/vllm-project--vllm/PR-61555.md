# [DSv4.1][PCP] Enable decode-only CUDA graphs with fixed DSpark

[Upstream PR](https://github.com/vllm-project/vllm/pull/61555) · state: open · merged: False

## Original PR description

## Overview

Enable NVIDIA DeepSeek-V4.1 PCP decode-only CUDA graphs by stabilizing graph-read metadata and sizing decode graphs by rank-local requests. Reuses the existing MRV2 graph implementation; prefill and bounded replay remain eager. Stacked on #59857, #61553 and #61554.

## Claims

- Preserve the addresses of gathered SWA positions, compressed cache slots and compressor ring-link metadata across graph replays.
- Use the largest rank-local request count for request-sharded decode graph dispatch, while retaining global input staging.
- Allow only V4.1 `FULL_DECODE_ONLY` on CUDA; speculative graphs require the existing flattened/varlen indexer path. Unsupported configurations retain explicit guards.
- In a small, matched four-H20 experiment, short-question output throughput was **5.22× at c1 and 4.51× at c4** versus eager. This is not a long-context or general throughput claim.

## Validation

Tested parent `9516299b96954da52ce7a7416c08db2b8b9db763` versus the frozen implementation in `b2e6404` (current Python files unchanged at `34c4a21`). Four H20 GPUs, TP1/PCP4/EP4, fixed DSpark5, Humming MoE FP8 activations, dense A16, `fp8_ds_mla`, shared CPU Engram, bounded replay ON, APC OFF, chunk8192, max-seqs64, max-len131072, utilization0.85 and `VLLM_GPU_SYNC_CHECK=error` in both arms. Same read-only checkpoint mount, native runtime, packages, backend dispatch and inputs. The container's existing native extensions were reused; this was not a clean native rebuild from the candidate commit.

**Fresh sequential Graph → Eager pair**, three measured repetitions per concurrency after separate warmup. Each repetition has the same four natural GSM8K questions (prompt lengths 63/60/78/110 tokens), temperature0, thinking disabled, natural EOS and real speculative acceptance. All measured answers passed; no cache hits or length truncation. Natural output lengths vary. Throughput includes the whole request round; TPOT is first-to-last content latency divided by generated tokens minus one. Reported TPOT is the median of each round's request medians.

## Details

Simply relaxing the graph guard is unsafe: captured kernels retain temporary compressor/cache metadata addresses, and a global request count mismatches request-sharded decode graph dimensions. This change uses persistent metadata buffers and the existing rank-local token dispatch machinery, adding only the corresponding request count. Global staging still reserves every request. No weight, quantization, acceptance-policy, attention kernel or graph-manager implementation changes.

Incremental production diff: **5 files, +101/−8**. Review against `9516299`; the GitHub diff against main also contains the dependency stack (#59857/#61553/#61554 and the parent's MoE padding prerequisite #60946). Existing V4.1 restrictions remain: PP=DP=DCP=1, no microbatching, KV transfer, APC or MegaMoE, fixed DSpark verification when enabled. Native speculative query metadata unable to refresh empty decode owners remains rejected. Prefill graphs and prefix caching are separate work.

Credit/reuse: merged #53867 supplies generic PCP decode-only FULL graph capture/padding but retained sparse-MLA rejection. #56107 supplies replicated DSpark. #53639 concerns generic rank-local token dispatch with replicated decode. This patch supplies V4.1 metadata stability and request-sharded graph sizing; it does not claim those existing generic optimizations. ROCm #58352 handles different ragged packing. Searches found no exact duplicate of this scoped implementation.
