# [Bugfix][HiSparse] Never allocate GPU pages without host backing

[Upstream PR](https://github.com/vllm-project/vllm/pull/59036) · state: closed · merged: True

## Original PR description

## Description

When the HiSparse host pool fills, `HiSparseSourceManager.allocate_new_blocks` gives new pages a null host entry. Those pages are never written back, so they never become clean and their GPU blocks can never be reclaimed: they stay pinned for the life of the request. Freeing host capacity does not fix it, because later allocations extend the host table and the freed blocks go to new tail pages, never to the old null ones. Host prefix publication for the request also stalls at the first null page.

The result is GPU KV pressure and preemptions that HiSparse is meant to prevent, plus lost host prefix-cache coverage, persisting after host capacity has recovered.

Fix: never allocate a page without host backing (alternative to #58963, which backfills null pages after the fact):

- `HiSparseSourceManager.get_num_blocks_to_allocate` requires host blocks for every page being allocated, not just external-load destinations, and reuses the existing admission sentinel when they don't fit. The scheduler then waits or preempts exactly as it does for GPU exhaustion.
- The best-effort `allocate_new_blocks` override (null padding) is deleted.
- `has_pending_reclamation` also reports host blocks that an in-flight write-back will return (freed request, spill not yet acked), so the scheduler waits a step instead of over-preempting.
- Startup rejects a host pool that cannot hold one `max_model_len` request (plus the null block and a copy-on-write tail), which would otherwise livelock.

## Effect on KV-cache memory over time

**Before.** While the host pool is full, every page a running request seals gets a null host entry and keeps its GPU block for the rest of the request. The pinned set only grows: host blocks freed later go to new tail pages, never to the old null ones. A request that decodes through a host-full window therefore holds GPU KV proportional to the tokens produced during that window, as if HiSparse were off for those pages, and releases it only when it finishes or is preempted. Across the batch, GPU free blocks drift down while the host stays full, and the scheduler preempts (and later recomputes) requests that HiSparse should have kept running. Prefix publication for those requests also stops at the first null page, so the host prefix cache never covers the rest of their context.

**After.** Every GPU-resident page has a host page, so its GPU footprint is transient: a sealed page is dirty until its write-back completes (about one step), stays pinned while within the two-page active tail, and is unpinned once the request can read from host (it has a hot region). Unpinned pages stay readable but count as free, so the GPU pool reclaims them under pressure. Per-request GPU usage is bounded by the hot region, the active tail and in-flight write-backs, independent of context length, for as long as the request runs.

The host pool becomes the hard capacity limit instead: running requests together hold one host block per computed page, and when it is full, new allocations wait or preempt even if GPU blocks are free. Since HiSparse only pays off when the host pool is much larger than the GPU pool, this replaces the gradual, hard-to-see GPU buildup above with a rare, explicit admission limit.

## Related

- #58963 fixes the same bug by backfilling host blocks for null pages after capacity frees up (one page per step). This PR prevents the null pages instead, which removes rather than adds state; only one of the two should land.
- #57457 also edits `HiSparseSourceManager.get_num_blocks_to_allocate` (counts GPU copies pinned by a host-prefix hit). The changes compose: its copy-pin count replaces this PR's final `return 0`.
- #58949's steady-state concurrency estimate assumes resident pages spill to host; this PR makes that hold under host pressure, and its host-pool gauges become the direct signal for the new admission limit.
