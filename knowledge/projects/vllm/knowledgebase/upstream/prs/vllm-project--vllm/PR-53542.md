# [Bugfix][SpecDecode] Preserve contiguous GDN state across runtime-K changes

[Upstream PR](https://github.com/vllm-project/vllm/pull/53542) · state: open · merged: False

## Original PR description

## Overview

Keep GDN speculative state tables contiguous and preserve every state slot when runtime K changes. Use the active uniform query length for Qwen GDN and Kimi KDA convolution, independently of state-table capacity.

Rebased onto `main` at `d15be0856d` on 2026-10-30. The original proposal to narrow the state-index table has been removed because it loses state needed after a larger-K step.

## Claims

- Both metadata construction and block-table remapping return contiguous speculative state indices.
- FULL-graph buffers retain their existing stable addresses and configured state capacity, including padding.
- Uniform speculative convolution uses the actual query length; ragged/adaptive verification retains the existing conservative bound.
- Previous accepted-token state slots remain accessible even after K decreases to zero.

No new performance or end-to-end model-quality claim is made.

## Details

### Contiguity feedback and state correctness

[The XPU feedback](https://github.com/vllm-project/vllm/pull/53542#issuecomment-5652463085) correctly identifies that slicing columns of a max-width tensor produces non-contiguous rows. Merely replacing that slice with a per-active-width staging buffer would fix contiguity but introduce a different correctness problem on current main: recurrence reads column `num_accepted_tokens - 1` from the previous step. That column can lie beyond the current query width.

Rebasing the original narrowing exposed failures in three existing zero-draft tests, including both GDN and Kimi KDA aligned-cache cases. The final implementation therefore keeps max-width state tables, makes eager views contiguous, and reuses main's stable contiguous FULL-graph buffers. `.contiguous()` is a no-op on those already-contiguous graph buffers. The active convolution width comes from the existing `uniform_spec_sequence_length` metadata instead of shrinking the state table. Adaptive verification keeps its current behavior because that field is unset when device query lengths may differ.

### XPU limitation

This does **not** resolve the independent native XPU active-width contract tracked in [vllm-xpu-kernels #593](https://github.com/vllm-project/vllm-xpu-kernels/issues/593): that interface and its launchers still derive iteration width from state-table capacity. Supporting reduced K there requires a kernel-side distinction between active query width and state capacity, with fresh XPU validation. Narrowing away previous accepted state slots is not a safe workaround.

### Non-duplicate scope

This uses main's existing uniform-query metadata and graph staging; it does not reimplement adaptive-K scheduling (#52559) or change the native XPU interface. The remaining changes are contiguous metadata outputs and decoupled convolution launch bounds.

- steveseguin · comment · 2026-09-13T09:32:44Z · [source](https://github.com/vllm-project/vllm/pull/53542#issuecomment-5652463085)

One follow-up from running this on Intel XPU with FULL cudagraphs under a dynamic schedule (`num_speculative_tokens_per_batch_size`, max K=3, our own patch that keeps full decode graphs per scheduled K instead of the PIECEWISE override):

The staging path

```python
spec_state_indices_tensor = self.spec_state_indices_tensor[:batch_size, :active_spec_width]
```

hands the kernel a **non-contiguous** column slice of the `[max_bs, num_spec+1]` buffer whenever `active_spec_width < num_spec + 1`. The XPU GDN op asserts contiguity, so capture of the K=1 graph dies with `RuntimeError: spec_state_indices_tensor must be contiguous`. The non-graph path is unaffected (the boolean-mask index makes a fresh contiguous tensor), which is why the earlier 12-user run passed.

What fixed it for us (lab overlay R306): one persistent, contiguous staging buffer per active width, allocated in `__init__` so capture never allocates:

```python
self.spec_state_indices_by_width = {self.num_spec + 1: self.spec_state_indices_tensor}
for w in range(2, self.num_spec + 1):
    self.spec_state_indices_by_width[w] = torch.empty((self.decode_cudagraph_max_bs, w), dtype=torch.int32, device=device)
...
staging = self.spec_state_indices_by_width[active_spec_width]
staging[:num_spec_decodes].copy_(spec_state_indices_tensor, non_blocking=True)
spec_state_indices_tensor = staging[:batch_size]          # contiguous row slice
spec_state_indices_tensor[num_spec_decodes:].fill_(NULL_BLOCK_ID)
```

Row slices of a per-width buffer stay contiguous and keep a stable address per (width, batch) graph. With that, the scheduled server on Qwen3.5-9B W4A16 (schedule `[[1,8,3],[9,16,1],[17,64,0]]`, max K=3, full decode graphs per K) captures and runs its full four-pass 1-64-user ladder: 16 users 992 tok/s exact against the sequential oracle on all four passes, 32 users 1190, 64 users 1631; one user 121.0/121.1 tok/s with the lab's strict gates 12/12. Worth folding into the PR since CUDA kernels that `.contiguous()`-check would hit the same thing.
