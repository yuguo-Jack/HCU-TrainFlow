# [CPU] Warm up the remaining sampling kernels before serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/64522) · state: open · merged: False

## Original PR description

## Purpose

On CPU with Model Runner V2, one to three Triton kernels still compile inside the first requests after a server start, adding ~1.5 s to their TTFT. The penalty is a fixed *count* of requests per start, not a fraction of traffic, so it breaches p95 or p99 at small request counts while the median never moves.

Three independent causes:

1. **Greedy sampling is never warmed.** `warmup_kernels` runs its greedy pass only under speculative decoding. MRV2 has no separate argmax kernel -- greedy is the temperature-0 branch inside `_gumbel_sample_kernel` -- and a batch needing no logits processing skips the FP32 upcast, so that kernel first sees model-dtype logits at request time.
2. **The JIT warmup registry never runs on CPU.** `CPUWorker` overrides `compile_or_warm_up_model` without calling `kernel_warmup()`, so `jit_warmup_registry.warmup()` never fires and the top-k/top-p variants the registry already declares are never built. Registering them alone is not enough for this reason.
3. **`idx_mapping` inherits numpy's alignment.** The CPU `async_tensor_h2d` hands back `torch.from_numpy(...)` unchanged when the dtype already matches, and `idx_mapping_np` is already int64, so `_prepare_prefill_inputs_kernel` sees a pointer that is 16-byte aligned during warmup and 8 mod 16 on a real batch. Triton specializes on pointer alignment, so that is a recompile warmup cannot predict. Copying numpy inputs into a torch allocation keeps the pointer aligned and keeps the aligned specialization.
