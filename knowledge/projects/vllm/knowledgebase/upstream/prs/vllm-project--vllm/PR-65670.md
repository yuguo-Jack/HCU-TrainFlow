## Overview

<!-- Summarize the change in 1-2 lines. Link relevant issues and PRs. -->

Add opt-in `vllm run-batch --output-order completion` so finished responses reach the output file without waiting for an earlier slow request. Input order remains the default.

Related to #60184. This is separate from #62895, which resumes records already on disk and explicitly leaves cancellation and write-order behavior unchanged. The proposed scope was explained in [the issue discussion](https://github.com/vllm-project/vllm/issues/60184#issuecomment-6528693500).

## Claims

<!-- State the accomplishments in a few concrete bullets: speedups, feature support, bug fixes, etc. -->

- Preserve the current input-order default; completion order is explicitly selected.
- Flush each finished response immediately in completion mode, keeping the existing in-flight limit, error handling, and cancellation cleanup.
- Document matching by `custom_id`, safe retries to a different file, and the unchanged upload-on-success behavior for URL outputs.

## Details

<!-- Explain motivation, design decisions, root cause, tradeoffs, and limitations concisely. Link or collapse lengthy supporting material. -->

In input-order mode, a slow early request can hold already-finished responses in the reorder buffer. An interrupted run loses those unwritten responses. Completion mode avoids that buffer: each response is written and flushed when its request finishes. Cancelled work still produces no additional output, and a dead engine still stops dispatch.

The change is deliberately opt-in. Consumers of completion-order output must use unique `custom_id` values instead of line positions. A partial output is not necessarily an input prefix. This does not add automatic resume, retries, or stronger filesystem durability guarantees. URL outputs remain staged and are uploaded only after the whole batch succeeds.

The tests reuse the existing launcher suite, add event-controlled real handlers and files, cover in-flight bounds and progress in both modes, and extend the existing real CLI routing test. The existing Entrypoints Unit Buildkite lane selects this test file.

Duplicate checks inspected the current #60184 discussion, #62895's explicit scope, and open PR searches for batch ordering, completion order, flushing, and cancellation. A contributor had offered a related shutdown-flush follow-up; the coordination note explains this different opt-in design and offers to step back if it overlaps.
