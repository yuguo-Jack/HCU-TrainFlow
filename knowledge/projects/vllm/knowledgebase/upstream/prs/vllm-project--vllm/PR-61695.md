# [CI] Fix B200 FusedMoE Layer Kernels hang on NVSHMEM IB setup

[Upstream PR](https://github.com/vllm-project/vllm/pull/61695) · state: closed · merged: True

## Original PR description



## Overview

`(B200) FusedMoE Layer Kernels` is failing ~24% of main runs (59/247 over the last two weeks), almost all of them by hanging until the 90 minute job timeout. The hang is in `test_moe_layer[False-deepep_low_latency-2-1-True]`, where NVSHMEM's InfiniBand transport setup fails and the spawned workers never exit. This PR keeps these single-node DeepEP tests on NVLink and off the NICs, and makes any future hang fail fast.

Alternative to the stalled draft #53332, which retries the launch instead of avoiding IB; details below.

## Claims

- The CUDA DeepEP cases of `test_moe_layer` no longer use NVSHMEM's IB transports. That is where every B200 hang starts. Both GPUs in each test are on the same node, connected by NVLink, so the IB path carries no test traffic anyway.
- `parallel_launch_with_config` kills its workers and raises `TimeoutError` after 15 minutes. `test_moe_layer` already turns that into a normal test failure, so a future hang costs one test instead of the whole job.
- The B200 job timeout drops from 90 to 45 minutes. Passing runs take 15–18 minutes, and the slowest passing run in the last two weeks took 36 minutes.

## Validation

**CI history (job logs from builds 94300–94498, 56 runs: 47 passed, 8 timed out, 1 failed fast).** All 8 timeouts show the same signature and then no further output until the job is cancelled:

```
ibrc.cpp:427:  non-zero status: 22 ibv_modify_qp failed
ibrc.cpp:1526: non-zero status: 7 ep_connect failed
init.cu:1047:  non-zero status: 7 nvshmem setup connections failed
```

**Local repro (2x B300 on one node).** IB is unusable on this box for an unprivileged user (8 MB memlock), which makes it a stand-in for a broken IB setup. Command:

```bash
pytest -v tests/kernels/moe/test_moe_layer.py -k deepep
```

| Case | Before | After |
|---|---|---|
| `test_moe_layer[False-deepep_low_latency-2-1-True]` | fails in NVSHMEM init (`ibrc.cpp:314: cq creation failed`) | passes (48/48 subcases) |
| `test_moe_layer[False-deepep_high_throughput-2-1-True]` | n/a | 191/192 subcases pass |

The one high-throughput miss is a local DeepGEMM JIT failure (`nvcc fatal: Failed to preprocess host compiler properties`), unrelated to this change. DeepEP high-throughput mode with 2 ranks allocates no RDMA buffer and does not initialise NVSHMEM.

**Launcher timeout.** Tested with a worker that sleeps forever and the timeout set to 30 s: it raised `TimeoutError` after 31 s, and no child processes were left behind. A normal launch still returns.

## Details

<details>
<summary>Root cause</summary>

- **It is the first NVSHMEM init that fails, not re-initialisation.** The test creates a new DeepEP low-latency buffer for each subtest, so a passing run initialises NVSHMEM 48 times. Each init logs 32 `cudaHostRegister` fallback warnings (1536 per passing run). All 8 hung runs stop after exactly 32, before the first subtest finishes. So the hang always happens on the first init of the job, never on a later one.
- **IBGDA is unavailable in these pods, so NVSHMEM falls back to IBRC.** The `cudaHostRegister ... error=800` / `ibgda_*` fallback warnings appear in passing runs too. The fallback IBRC queue-pair connect is what intermittently fails, and the worker group then hangs instead of exiting.
- **It looks host- or contention-related.** Timeouts hit dgxB200-09/12/14 (8 of 32 runs) and none of 01/11/16 (0 of 23). 5 of the 8 timeouts started within 2–5 minutes of another run of this job on the same host. Every B200 pod sees all of the node's NICs (the job's `nvidia-smi topo -m` lists 12), so concurrent pods share them. This is suggestive, not proven.

</details>

<details>
<summary>Why these settings</summary>

- `NVSHMEM_REMOTE_TRANSPORT=none` disables IBRC.
- `NVSHMEM_HCA_LIST=none` hides the NICs from IBGDA. DeepEP's low-latency buffer sets `NVSHMEM_IB_ENABLE_IBGDA=1` unconditionally, and `REMOTE_TRANSPORT=none` alone still tried IBGDA locally and failed.
- With no remote transport, NVSHMEM uses its P2P transport. DeepEP's low-latency kernels take the NVLink store path whenever `nvshmemi_get_p2p_ptr` returns a peer pointer, which is the case for every peer in a single-node test.
- The settings are applied through the existing `env_dict` hook, only for CUDA DeepEP backends. ROCm/MoRI paths are untouched.
- The CI pods for both jobs that run this file have their GPU pair on NVLink (`NV18` in the `nvidia-smi topo -m` of the B200 job and the H100 job). If a future runner had a GPU pair without peer access, the low-latency case would fail clearly rather than hang.

</details>

<details>
<summary>Relation to #53332</summary>

#53332 (draft, idle since Sep 14) adds an opt-in join timeout plus a single retry with NVSHMEM debug logging. It is framed around NVSHMEM re-initialisation. The B200 data above shows the failure is on the first init and in the IB transport, so this PR removes the IB dependency rather than retrying it. The timeout here applies to every `parallel_launch_with_config` caller: the longest single launch seen in a passing B200 run is ~195 s, against the 900 s limit.

The H100 SIGSEGV that #53332 also describes happened after `init failed for transport: IBGDA`. This change should avoid that too, but I have not reproduced it.

</details>

**Limitations.** This drops IB transport coverage from `test_moe_layer`. That coverage was never meaningful here: the tests are single-node, and IB setup on the CI pods only works via fallback. Multi-node DeepEP coverage belongs in a multi-node test.
