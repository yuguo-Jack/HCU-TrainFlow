# [ROCm][Perf][Muse Spark] Shard the MoE block's dense ops over tokens under EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/63722) · state: open · merged: False

## Original PR description

## Overview

Each Muse Spark MoE layer wraps the routed experts in dense work: an FP32 router, a BF16 pooler (8192 → 4096), a pre-expert RMSNorm and a BF16 unpooler (4096 → 8192). With TP8 + EP and DP1, every rank runs all of it on all tokens and then all-reduces the expert output. In an 8,192-token prefill step on MI300X that is about 2.3 ms per layer, 7/8 of it duplicated across ranks.

vLLM's sequence-parallel MoE branch (`sequence_parallel_chunk` + all-gather) would avoid this, but `use_sequence_parallel_moe` requires DP > 1 and an all2all backend.

With `--enable-expert-parallel`, EP over the whole TP group, DP1 and no sequence-parallel MoE (the EP group is TP-sized even without EP, so the flag is checked explicitly), this PR makes the block reduce the expert output itself (`reduce_results=False`). For 256 or more tokens each rank:

1. runs the router, pooler and pre-expert norm on its \(T/8\) token slice;
2. all-gathers the router logits and the pooled activations, so the experts still see all tokens;
3. reduce-scatters the expert output, which moves the same bytes as the all-reduce it replaces;
4. runs the unpooler on its slice and all-gathers the `[T, 8192]` result.

Below 256 tokens the block keeps one all-reduce. For AITER MXFP4 experts, which take one input row per route, the norm-and-expand runs after the gather.

`_validate_tp_post_norm_deployment` rejected any unreduced MoE output. It now rejects it only when the experts are TP-sharded (`needs_pre_norm_all_reduce`), the case where the reduction must run before the per-route post-expert norm. The fail-closed test case moves to TP8, and a new test checks that all three validators accept unreduced output under EP.

## Claims

- Removes about 2.0 ms of replicated work per layer at 8,192 tokens and adds about 0.4 ms of all-gather: about 110 ms projected per 622 ms EP8 prefill step.
- Serving PTPC-FP8, TP8 + EP on 8× MI300X, against the unpatched nightly: +0.6–8.7% total throughput at 8k input and +1.4–11.6% at 16k input (concurrency 1–64, 1k output, rising with concurrency), with median TTFT 15–30% lower. At 1k input, throughput is within +2% and median TTFT is 5–25% lower.
- GSM8K 5-shot is unchanged within error: 95.38% vs 95.30% flexible-extract (±0.6%). The reduction order changes, so outputs are not bit-identical.
- MXFP4 on 4× MI355X (gfx950), TP4 + EP, real weights: neutral to slightly negative. Total throughput is within ±2% at 1k input and 0.6–1.8% lower at 8k and 16k input for concurrency 16–64; with four ranks the replicated dense work the change removes is a smaller share of the step. GSM8K is unchanged within error (94.84% vs 94.92%).

## Details

- **Where the bytes go**, per layer at 8,192 tokens: all-gather of FP32 logits (8 MB) and pooled BF16 (64 MB), reduce-scatter of the BF16 expert output (64 MB, same as the all-reduce), and all-gather of the unpooled output (128 MB).
- **Threshold.** The block reuses the runner's `_TOKEN_SHARDED_MIN_TOKENS` (256), the threshold of its existing token-sharded TP finalize, where reduce-scatter + all-gather start to beat one custom all-reduce.
- **Padding.** `sequence_parallel_chunk` pads \(T\) to a multiple of the TP size; the padded rows are routed and dropped by the final `[:num_tokens]`.
- **Follow-up.** https://github.com/vllm-project/vllm/pull/63723 (stacked on this branch) keeps the residual stream sharded and reduce-scatters `o_proj`, for a further +3.5% at 8k c64 and +6.4% at 16k c64.
- **Limitations.** PTPC-FP8 serving and accuracy are measured on MI300X and MXFP4 on MI355X; other EP layouts (DP > 1, EP smaller than TP) keep the existing path.
