# [Feat] Add request-level preemption count histogram metric

[Upstream PR](https://github.com/vllm-project/vllm/pull/49984) · state: closed · merged: True

## Original PR description

## Purpose

This PR introduces request-level preemption tracking by adding a new `vllm:request_num_preemptions` histogram metric. It records the number of times a request is preempted (due to KV cache starvation) before it completes, providing better visibility into system performance and capacity limits under load.

## Test Plan

End-to-End Metrics integration tests passed successfully (`pytest tests/entrypoints/serve/instrumentator/test_metrics.py -v`). 

Additionally, I verified the preemption metric in an end-to-end simulation by severely constraining the KV cache to exactly 8 blocks and concurrently firing 4 long-generation requests, forcing the engine into starvation.

```python
import asyncio
import openai
import requests
from prometheus_client.parser import text_string_to_metric_families

from tests.utils import RemoteOpenAIServer

async def run_simulation():
    model_name = "TinyLlama/TinyLlama-1.1B-Chat-v1.0"
    
    server_args = [
        "--dtype", "bfloat16",
        "--enforce-eager",
        # Force the KV cache to exactly 8 blocks so it runs out extremely fast
        "--num-gpu-blocks-override", "8", 
        "--gpu-memory-utilization", "0.5",
        "--max-num-seqs", "4",
        "--max-model-len", "1024",
    ]
    
    print("Starting vLLM server with constrained memory...")
    with RemoteOpenAIServer(model_name, server_args) as server:
        client = openai.AsyncClient(base_url=server.url_for("v1"), api_key="test")
        
        async def send_req(i):
            print(f"[{i}] Request started")
            try:
                # We request a lot of tokens so the KV cache grows and causes preemption
                await client.completions.create(
                    model=model_name,
                    prompt=f"Please write a very very long essay about the history of artificial intelligence and its impact on modern society. Part {i}:",
                    max_tokens=600,
                    temperature=0.0,
                    extra_body={"ignore_eos": True}
                )
                print(f"[{i}] Request finished successfully")
            except Exception as e:
                print(f"[{i}] Request failed: {e}")
        
        # Fire 4 concurrent requests
        print("Sending 4 concurrent long-generation requests...")
        tasks = [send_req(i) for i in range(4)]
        await asyncio.gather(*tasks)
        
        print("Fetching metrics...")
        response = requests.get(server.url_for("metrics"))
        
        # Parse the metrics to find preemption count and buckets
        preemption_sum = 0
        buckets = {}
        for family in text_string_to_metric_families(response.text):
            if family.name == "vllm:request_num_preemptions":
                for sample in family.samples:
                    if sample.name == "vllm:request_num_preemptions_sum":
                        preemption_sum = sample.value
                    elif sample.name == "vllm:request_num_preemptions_bucket":
                        le = sample.labels.get("le", "unknown")
                        buckets[le] = sample.value
                        
        print(f"\n=> Total Preemptions Observed: {preemption_sum}")
        print("=> Histogram Buckets:")
        for le, count in buckets.items():
            print(f"   le=\"{le}\": {count}")
        
        if preemption_sum > 0:
            print("=> SUCCESS: We successfully simulated preemption!")
        else:
            print("=> FAILED: No preemptions occurred. The KV cache was too large or max_tokens was too small.")

if __name__ == "__main__":
    asyncio.run(run_simulation())
```

> Why do we need a histogram for this? It doesn't make sense to me beyond reporting the number from the last tick

Hi @mgoin, thanks for the question!

To clarify, this metric is a **per-request lifecycle metric** recorded upon request completion (in `finished_requests`), rather than an iteration/step-level counter.

While the existing `vllm:num_preemptions` tracks the total node-level preemption events over time, `vllm:request_num_preemptions` tracks the distribution of how many times an individual request was preempted throughout its lifetime before finishing.

Having a histogram for per-request preemptions helps operators understand preemption severity and thrashing:

1. **Distribution Insights**: Under memory pressure, it helps differentiate whether preemptions are evenly spread across requests (e.g., every request gets preempted once) or if specific long-context requests are suffering from severe thrashing (e.g., being preempted 5–10+ times).

2. **Consistency with vLLM Metric Architecture**: This aligns with the existing per-request metrics in `vllm/v1/metrics/loggers.py` (such as `vllm:request_prompt_tokens`, `vllm:request_queue_time_seconds`, and `vllm:e2e_request_latency_seconds`), which are all implemented as histograms recorded when a request finishes.

Hope this clarifies the motivation! Let me know if you have any thoughts on the bucket boundaries or naming.

- linamy85 · comment · 2026-10-28T13:21:43Z · [source](https://github.com/vllm-project/vllm/pull/49984#issuecomment-6470106438)

Hi @laurentperez, thanks for reporting this!

**Short answer:** In the codebase, it is impossible for a request to record a non-zero preemption in `vllm:request_num_preemptions` without also incrementing `vllm:num_preemptions_total`—both are updated on consecutive lines inside the exact same `EngineCoreEventType.PREEMPTED` event handler (`vllm/v1/metrics/stats.py`). When `vllm:num_preemptions_total` is `0`, the actual sum of preemptions recorded by the histogram (**`vllm:request_num_preemptions_sum`**) is also `0`.

The reason your right-hand chart (`Number of preemptions per requests [24h]`) shows `508`, `832`, ..., `2613` is that **every completed request (including those with `0` preemptions) is observed into the histogram via `.observe(0)`**:

1. **What `.observe(0)` updates in Prometheus**:
   - `vllm:request_num_preemptions_sum`: adds `0` (stays `0`, matching `vllm:num_preemptions_total`).
   - `vllm:request_num_preemptions_count`: increments by `1` for every completed request (it tracks the total number of observed requests, not preempted requests).
   - `vllm:request_num_preemptions_bucket{le="1.0"}` (and higher buckets up to `+Inf`): increments by `1` because the bucket boundaries are `[1, 2, 3, 4, 5, 10, 20]` (`0` was omitted because Ray's histogram wrapper rejects boundaries `<= 0`). Since `0 <= 1.0`, never-preempted (`0`) requests fall into the first bucket alongside singly-preempted (`1`) requests (as noted in `vllm/v1/metrics/buckets.py`).

2. **How to query actual preemption counts in PromQL**:
   If a Grafana panel queries `vllm:request_num_preemptions_count` or `vllm:request_num_preemptions_bucket`, it will plot the total number of completed requests rather than preemptions (and `histogram_quantile()` will interpolate within `(0, 1.0]`). Instead, try this:
   - **Total preemptions across completed requests**: `increase(vllm:request_num_preemptions_sum[24h])`
   - **Average preemptions per completed request**: `increase(vllm:request_num_preemptions_sum[24h]) / increase(vllm:request_num_preemptions_count[24h])`
   - **Requests preempted `>= 2` times**: `increase(vllm:request_num_preemptions_count[24h]) - increase(vllm:request_num_preemptions_bucket{le="1.0"}[24h])`
