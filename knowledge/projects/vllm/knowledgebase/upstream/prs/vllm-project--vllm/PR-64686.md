# [Bugfix][KV Offload][P2P] Clean up both roles on request finish

[Upstream PR](https://github.com/vllm-project/vllm/pull/64686) · state: closed · merged: True

## Original PR description

## Overview

Fix a small but meaningful P2P lifecycle bug in the documented `remote_kv_source` + `remote_decoder` combination. When the upstream source and downstream decoder use different peer sessions, `on_request_finished()` returns after finishing the source-side consumer session, leaving the decoder-side `_kv_to_session` entry until session teardown and potentially delaying server-round cleanup; these stale entries accumulate on long-lived peers.

## Claims

- Finish the source and destination roles independently for dual-role requests.
- Remove the destination request from `_kv_to_session` when the request finishes.
- Avoid calling `finish_request` twice when both roles use the same session and request ID.

## Details

`on_request_finished()` previously selected the source request ID first. With `remote_kv_source` present, it finished the source-side session and returned, so a legal dual-role request never removed its decoder-side `_kv_to_session` entry or finished the session serving that request.

The cleanup now handles both roles independently. The existing `P2PSession.finish_request()` path still performs the client and server role cleanup; the manager only routes each role to the correct session and suppresses duplicate cleanup when both roles share the same session and request ID.

No open PR covering this lifecycle bug was found.

This guard is reachable in a real flow, so let's keep it, but say why next to it. When the source and the decoder are the same node, both roles share one `P2PSession`. For example, in multi-turn with fixed P/D, P pulls the previous turn's decoded blocks back from D. The session D opened when it fetched the last turn is reused for P's outbound `remote_kv_source`. With the same `kv_request_id` for both roles, `finish_request` has already done the client and server cleanup, so a second call would be redundant.

```suggestion
            # Same node as source and decoder (e.g. multi-turn with fixed
            # P/D, P pulls the previous turn back from D): both roles share
            # one session, and finish_request above already finished the
            # server role for this id.
            if dest_session is not None and not (
                dest_session is source_session and dest_id == source_id
            ):
```

Could you also add a test for this shared-session case, covering both a shared and a distinct `kv_request_id`? The current test only covers two separate sessions.
