# [XPU] Add env overrides for DiffKV attention 2D launch and tile size

[Upstream PR](https://github.com/vllm-project/vllm/pull/53804) · state: open · merged: False

## Original PR description



## Purpose

`unified_attention_diffkv` picks between a 2D and a 3D (split-KV) launch, and derives
`tile_size` from that choice. The 3D path is taken only for decode-only batches
(`max_seqlen_q == 1`) with `num_seqs <= seq_threshold_3D`, so on a given deployment
prefill and decode can end up on structurally different kernel geometries with no way to
test one against the other short of editing the file.

This adds two debug overrides for that decision:

- `VLLM_XPU_DIFFKV_FORCE_2D=1` — force the 2D launch even for decode-only batches
- `VLLM_XPU_DIFFKV_TILE_SIZE=N` — override `tile_size`

Both default to the current behaviour, so nothing changes unless a variable is set.

Two knobs rather than one, because forcing 2D also moves `tile_size` from 16 to 32 for
>=2-byte dtypes; with only the first knob it is impossible to separate "the 3D grid is at
fault" from "`tile_size=16` is at fault".

Motivation: on 8x Intel Arc Pro B70 serving MiMo-V2.5-Pro (block-FP8, TP=8, so one KV head
per rank and `seq_threshold_3D = 128`), every decode batch takes the 3D launch and decode
stalls in a userspace spin on a device event that never signals, while prefill on the 2D
launch always completes. Forcing 2D is what made the model serve here. I am **not**
claiming that as a fix or as a root cause — the stall is intermittent and its mechanism is
still unknown, which is exactly why this is an opt-in override that defaults off rather
than a behaviour change. It makes the 2D/3D variable testable by users on hardware where
the two paths do not perform alike.

## Test Plan

1. Default behaviour unchanged: with neither variable set, confirm the `use_3d` predicate
   and `tile_size` are exactly as before, and that the flag parses as off when unset and
   when explicitly `0`.
2. Override behaviour: with `VLLM_XPU_DIFFKV_FORCE_2D=1`, confirm decode takes the 2D
   grid; with `VLLM_XPU_DIFFKV_TILE_SIZE=16`, confirm the tile size is honoured.
3. End-to-end serving of a DiffKV model that routes to `TRITON_ATTN_DIFFKV`:

vllm serve XiaomiMiMo/MiMo-V2.5-Pro --tensor-parallel-size 8 --dtype bfloat16
    --moe-backend triton --max-model-len 2048 --block-size 64 --enforce-eager
    --trust-remote-code

   run twice, once with `VLLM_XPU_DIFFKV_FORCE_2D=1` and once without, plus
   `lm_eval --tasks gsm8k --num_fewshot 5 --limit 10` for correctness.

## Test Result

Defaults are unchanged — `(force_2d, tile_override)` resolves to `(False, None)` when
unset and when set to `0`, `(True, None)` at `1`, and `(False, 16)` for
`VLLM_XPU_DIFFKV_TILE_SIZE=16`. With both unset, the `use_3d` expression and `tile_size`
assignment are identical to the current code.

End-to-end on 8x Intel Arc Pro B70, MiMo-V2.5-Pro block-FP8 at TP=8:

| `VLLM_XPU_DIFFKV_FORCE_2D` | decode outcome |
|---|---|
| unset (3D, current behaviour) | stalls at decode step 1-2, unrecoverable, in 8 consecutive runs |
| `1` (2D) | decode progresses; full benchmark completed 10/10 requests, and gsm8k 5-shot `--limit 10` scores 10/10 exact match on both `strict-match` and `flexible-extract` |

Stated plainly: the override is a mitigation, not a cure. Of five runs with it enabled,
three completed and two still stalled, so it moves onset rather than eliminating it, and
the underlying event-wait problem is unresolved. 2D decode also gives up KV-dim
parallelism and is slower in principle; on this configuration that is not the bottleneck
(an unrelated MoE code path dominates step time), but it is the reason the default is
unchanged.

vLLM's XPU CI cannot be run from this machine, so the above is the available evidence.
