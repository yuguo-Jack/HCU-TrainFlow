# [Spec Decode] Draft within the requests' top-k / top-p support

[Upstream PR](https://github.com/vllm-project/vllm/pull/56724) · state: open · merged: False

## Original PR description

## Overview

With probabilistic drafting, the V2 drafter samples from the whole vocabulary.
The target samples only inside the request's top-k / top-p.
So draft tokens outside that set are always rejected.

This PR applies the request's top-k / top-p to the draft, on the GPU.
It replaces the `NOTE(woosuk)` that skips this for simplicity and speed.
No open PR does this. #48932 also edits `dspark/speculator.py`.

## Claims

- More draft tokens are accepted.
- The output distribution does not change.
- Requests without top-k, and the default greedy drafting, are unchanged.

## Details

Two Triton kernels compute one threshold per row on each draft step.
The Gumbel kernel drops logits below it.
Nothing runs on the host, so CUDA graphs keep working.

Tradeoffs:
- About 0.02 ms per draft step with top-k, 0.002 ms without.
- Only rows with 1 ≤ top-k ≤ 1024 are masked.
- 413 non-test lines, 276 in the new `draft_support.py`.

<details>
<summary><b>How it works</b></summary>

1. The model runner hands the drafter the sampler's per-request top-k / top-p once. The drafter copies the current values into its own fixed-address tensors on every step, as it does with the temperature.
2. On each draft step two Triton kernels compute one threshold per row: the maximum of each vocabulary block (at most 4096 blocks), then the k-th largest block maximum by bisection and the top-p cut above it.
3. The Gumbel sampling kernel drops logits below the threshold, for sampling and for the cached draft logits, so rejection sampling stays exact.

Nothing is decided on the host, so it works inside the drafter's CUDA graphs. Rows without top-k and padding rows return at once.
The threshold never drops a token of the draft's own top-k / top-p set. It is exact for vocabularies up to 4096 tokens; above that it can keep a few extra tokens.
Logits at -inf (EAGLE3 heads with a reduced draft vocabulary) are skipped.
DSpark samples outside `sample_draft` and applies the same threshold there.
A draft watermarker gets the masked logits; the acceptance estimator gets them unmasked.

The sampler's `apply_top_k_top_p_triton` is not reused. On random logits at batch 32 (248k vocabulary, RTX 4090, inside a CUDA graph) it takes 0.22 ms per call, fp32 copy included, and it would run once per draft step, three times per proposal. The two kernels here compute only a threshold and take 0.023 ms; the whole draft-sampling step is 0.054 ms against 0.029 ms on `main`.

Added cost per draft step in a CUDA graph, 248k vocabulary, RTX 4090, measured on revision a87a7504d:

| batch | `top_k=20, top_p=0.95` | no top-k |
| --- | --- | --- |
| 1 | 0.019 ms | 0.002 ms |
| 8 | 0.019 ms | 0.002 ms |
| 32 | 0.024 ms | 0.003 ms |
