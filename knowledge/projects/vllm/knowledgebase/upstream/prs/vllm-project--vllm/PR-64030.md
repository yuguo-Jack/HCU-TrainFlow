# [Feature]: Remove the requirement for the --trust-remote-code flag to run Nemotron 3.5 Super VL

[Upstream PR](https://github.com/vllm-project/vllm/pull/64030) · state: closed · merged: False

## Original PR description



## Overview

Implements the feature request in issue https://github.com/vllm-project/vllm/issues/63470 (https://github.com/vllm-project/vllm/issues/63470) to remove the need to use the --trust-remote-code flag to run Nemotron 3.5 Super VL.

## Claims

This change brings the apache 2.0 code for the model configuration and processor into the vLLM codebase, removing the need to download remote code.

## Validation

NB: I don't currently have access to a GPU setup capable of running this model, so I would appreciate any support in validation.

What I have done so far:

Attempted to serve the model without the --trust-remote-code and confirmed that after the code change I see the same behaviour up until I see out-of-memory issues: that the model architecture successfully resolves.
Run pre-commit and resolved mismatches between linting standards and docstrings requirements.
After the update, attempted to serve the model with the --trust-remote-code flag, and confirmed I don't see new errors introduced by name conflicts etc. up until the out-of-memory crash.

## Details

I incorporated the additional files prodivded in the NVIDIA huggingface repo (https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4/tree/main), condensing into a single config file for the Reasoning and Radio classes to avoid naming clashes with the existing radio embedding models.

Where possible I have harmonised the vLLM linting with the docstring format requirements of the original files. I've needed to include a ruff 'noqa' command to avoid an issue where docstrings are not recognised- I've tried to follow the pattern set by qwen3_asr.py. I have included a new assertion and made minor adjustments to code style to avoid mypy errors for previously supported versions.

I have included the original copyright notice from the NVIDIA files at the top of the page, and a link to huggingface repo the original files these were adapted from.

- cv · comment · 2026-10-28T22:21:55Z · [source](https://github.com/vllm-project/vllm/pull/64030#issuecomment-6482167441)

Tested on a DGX Spark: with this PR, `nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4` loads and serves text, tool calls, and images without `--trust-remote-code`. Without it, vLLM v0.32.0 fails during model construction:

```
AttributeError: 'NemotronH_Omni_Reasoning_V3_Config' object has no attribute 'vit_hidden_size'. Did you mean: 'vision_hidden_size'?
```

Transformers 5.19's built-in `nemotron_h_omni` config renames `vit_hidden_size` to `vision_hidden_size` while loading, but `nano_nemotron_vl.py` still reads `config.vit_hidden_size`. Your config class keeps the checkpoint's field names, which fixes it.

### Setup

- **Hardware:** DGX Spark (GB10, compute capability 12.1), driver 580.142, 121 GiB unified memory.
- **vLLM:** the `vllm/vllm-openai` v0.32.0 image plus this PR's `vllm/` changes at `aed4cc8`, not a rebase onto `main`. Only the registration-list hunks in `configs/__init__.py` conflicted, and I inserted those entries by hand. I also applied #63218, and the startup log shows `Updating mamba_ssm_cache_dtype to 'float32' for NemotronH model`.
- **Model:** revision `da5b2650a835292c678994a1fa3fb653250fb508`, loaded from a snapshot that contains no repository `.py` files.
- **Arguments:** `--max-model-len 65536 --max-num-seqs 1 --max-num-batched-tokens 1024 --kv-cache-memory-bytes 8589934592 --enforce-eager --mamba-backend flashinfer --tool-call-parser qwen3_coder --enable-auto-tool-choice --reasoning-parser nemotron_v3`. Speculative decoding was off.

### Results

| Check | Result |
|---|---|
| Startup | Weights loaded in 453 s using 68.45 GiB; the engine was ready about 90 s later |
| Text | Reply `READY` to "Reply with exactly READY." through an agent harness |
| Tool calls | Two sequential tool calls (`terminal`, then `write_file`) with correct arguments and a correct final answer |
| Image | A 512×256 PNG with a red square and a blue circle, described correctly ("On the left side, there is a red square, and on the right side, there is a blue circle."), 314 prompt tokens |

Not tested: video, audio, contexts longer than these prompts, speculative decoding (MTP or the LiLiCorr drafter), CUDA graphs, tensor parallelism, and this PR rebased onto `main`.

### Registry name typo

`vllm/transformers_utils/processors/__init__.py` registers `"NeomtronHOmniProcessor"` in both `__all__` and the lazy-import map, but `processors/nemotron_h_omni.py` defines `NemotronHOmniReasoningV3ImageProcessor`. On the patched build:

```
>>> vllm.transformers_utils.processors.NeomtronHOmniProcessor
AttributeError: module 'vllm.transformers_utils.processors.nemotron_h_omni' has no attribute 'NeomtronHOmniProcessor'
>>> vllm.transformers_utils.processors.NemotronHOmniReasoningV3ImageProcessor
AttributeError: module 'processors' has no attribute 'NemotronHOmniReasoningV3ImageProcessor'
```

Registering `NemotronHOmniReasoningV3ImageProcessor` under its real name fixes both lookups.

The image request above went through `NanoNemotronVLProcessor` in `nano_nemotron_vl.py`, so it didn't exercise the new image processor. If serving never uses that class, the config alone may be enough for this PR.
