# [Perf][ROCm][Kernel] Add W4A8 int8-dot MXFP4 GEMV for RDNA3/RDNA3.5 d…

[Upstream PR](https://github.com/vllm-project/vllm/pull/60413) · state: open · merged: False

## Original PR description

## Overview

Adds an opt-in MXFP4 linear kernel for RDNA3/RDNA3.5 (gfx11) decode. For 1-8 tokens, activations are quantized to int8 per 32-element group, and each group is reduced with `v_dot4_i32_iu8` (`__builtin_amdgcn_sudot4`). E2M1 values times 2 are integers in [-12, 12], so weights map to int8 exactly through a 16-entry table; one fp32 multiply per group applies the E8M0 weight scale, the activation scale, and the 1/2. The approach follows ggml's MMVQ / q8_1 path (llama.cpp, MIT).

- Weights are read in the Quark OCP MX checkpoint layout (`[N, K/2]` uint8 E2M1, `[N, K/32]` uint8 E8M0). No repack, no extra weight memory.
- M > 8 (prefill) runs the same math as `EmulationMxfp4LinearKernel` (activation QDQ, dequant, `F.linear`).
- The M <= 8 / M > 8 split is inside a custom op, so torch.compile and CUDA graphs see one op.

Enable with:

```bash
VLLM_ROCM_MXFP4_W4A8=1
```

Opt-in because int8 activation rounding differs from the MXFP4 activation QDQ the checkpoint declares. With the flag off, or on non-gfx11 GPUs, kernel selection is unchanged.

Related: #46676 adds a W4A16 (fp32 FMA) scalar + WMMA MXFP4 kernel for gfx1100. This PR is independent: a different algorithm for the small-M regime (2-5x fewer instructions per weight at M = 1-8). The two PRs only touch the same registration lists.

## Benchmarks

AMD Strix Halo (gfx1151, RDNA 3.5), `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`, single stream (`--max-num-seqs 1`), CUDA graphs and torch.compile on, `vllm bench serve` random 128 in / 256 out.

### Comparison with #46676 and emulation (MTP=3, MXFP4 lm_head)

Same model, same machine, all three with the lm_head quantized to MXFP4 (see note). GSM8K 5-shot, lm-eval `local-completions`, greedy.

| Config | Decode kernel (M <= 8) | Decode tok/s | GSM8K (questions) |
|---|---|--:|--:|
| **This PR + MXFP4 lm_head** | W4A8 int8-dot GEMV | **28.89** | **96.51% (1319)** |
| #46676 + MXFP4 lm_head | W4A16 scalar FMA (WMMA for M > 8) | 26.19 | 96.51% (1319) |
| Emulation + MXFP4 lm_head | dequant + `F.linear` | 4.94 | 96.75% (1319) |

- 10% faster than #46676 at equal accuracy, 5.8x faster than the default emulation path.
- For reference, llama.cpp (ROCmFP4 4-bit GGUF, own quantization incl. lm_head) runs 29.1 tok/s at MTP=3 on the same machine.

**Note on activations:** this PR skips the checkpoint's MXFP4 activation QDQ when the flag is on. Decode quantizes activations to int8 per 32-element group (finer than MXFP4); prompts (M > 8) use bf16 activations. Applying the MXFP4 activation QDQ on prompts while decoding with int8 activations dropped GSM8K to ~80% in our runs, so the prompt path is weight-only, matching #46676.

**Note on the MXFP4 lm_head:** the checkpoint ships the lm_head ([248320, 5120]) in bf16, and this PR keeps it that way. For the comparison above, it was quantized to MXFP4 at load time (round-to-nearest, one E8M0 scale per 32 weights), the same for all three configs. It cuts the lm_head from 2.54 GB to 0.68 GB; with MTP=3 the lm_head is read 4 times per step (3 draft + 1 verify), so this is worth ~6 tok/s (22.45 â†’ 28.89). It is not part of this PR and will be proposed separately.

The model card reports 95.0% (bf16 base: 93.3%) with sampling and thinking-mode settings

## Validation

```bash
pytest tests/kernels/quantization/test_mxfp4_w4a8_rdna.py
pytest tests/kernels/quantization/test_mxfp4_kernel_selection.py
```

All pass on gfx1151. The new tests cover:

- output vs a reference implementation for M = 1..8, four shapes, fp16 and bf16;
- closeness to the bf16 dequantized result;
- M = 0 and M = 9 rejected by the op;
- `torch.library.opcheck`;
- CUDA graph capture and replay;
- dispatch for M = 1, 8, 9, 64 (kernel vs fallback);
- selection: chosen only with the flag on gfx11; MXFP6 and non-ROCm rejected.

Serve command used:

```bash
VLLM_ROCM_MXFP4_W4A8=1 vllm serve amd/Qwen3.8-27B-Quark-AWQ-MXFP4 \
  --trust-remote-code --max-model-len 4096 --max-num-seqs 1 \
  --gpu-memory-utilization 0.5 --limit-mm-per-prompt '{"image": 0, "video": 0}' \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}'   # MTP rows only
```

## Details

| File | Change |
|---|---|
| `csrc/rocm/mxfp4_w4a8_gemv.cu` | int8 activation quant + W4A8 GEMV, templated on M = 1..8 and fp16/bf16 |
| `csrc/rocm/ops.h`, `csrc/rocm/torch_bindings.cpp`, `CMakeLists.txt` | build and register `_rocm_C::mxfp4_w4a8_gemv` |
| `vllm/model_executor/kernels/linear/mxfp4/rdna_w4a8.py` | `RdnaW4A8MxFp4LinearKernel`, M-based dispatch in a custom op |
| `vllm/model_executor/kernels/linear/__init__.py` | first in the ROCm MXFP4 kernel list (selected only when supported) |
| `vllm/envs.py` | `VLLM_ROCM_MXFP4_W4A8` (default `False`) |
| `vllm/_custom_ops.py` | Python wrapper and fake impl |
| `tests/kernels/quantization/test_mxfp4_w4a8_rdna.py` | new tests |

- Device code is compiled only for `__GFX11__` (empty stubs elsewhere); the host entry point also checks for gfx11 at runtime.
- One wave per output column; lanes stride over the 32-weight groups along K, then a shuffle reduction. Accumulation is fp32 over the full K, one rounding to the output dtype.

Trade-offs and follow-ups:

- One extra activation-quant launch per linear (fusing it into the GEMV is a follow-up).
- M > 8 dequantizes per call, as the emulation kernel does; a faster prefill path is a separate PR.
