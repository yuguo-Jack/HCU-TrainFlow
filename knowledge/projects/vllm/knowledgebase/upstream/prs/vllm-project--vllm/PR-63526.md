# [LoRA] Keep loaded adapters across idle dummy batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/63526) · state: open · merged: False

## Original PR description

With data parallelism on an MoE model, idle ranks run `execute_dummy_batch` between steps to keep the expert collectives in lockstep. The dummy run went through the same LoRA setup as warmup. It registered `max_loras` dummy adapters with ids `1..max_loras`, which evicted real adapters from the CPU cache and reused real adapters whose ids matched. On exit it called `remove_all_adapters()`. Any engine serving LoRA traffic in that configuration dropped every adapter whenever it went idle, so the next request for any adapter reloaded it from disk.

Dummy LoRAs exist only so the dummy batch can select them. When a dummy run selects none (`num_active_loras=0`), they are no longer added or removed, and the punica mapping is still set to "no LoRA" for every token. The runtime dummy batch now selects none on both model runners. The V1 runner already passed 0. V2 hardcoded `max_loras`, so its `_dummy_run` now takes `num_active_loras` and keeps `max_loras` as the default for profiling and warmup. `num_active_loras` needs no agreement across DP ranks (`dp_utils.py`).

The same change fixes the V1 runner's external launcher + DP path, which calls `_dummy_run(1)` at runtime.

## Test

- `pytest tests/lora/test_lora_manager.py -k dummy_run_without_active_loras`: a dummy run with no active LoRAs keeps adapters 1 and 3 resident and in the same GPU slots, with and without `remove_lora`. Warmup with active dummy LoRAs behaves as before. Fails on main (`{1, 2, 3} != {1, 3}`, then flushed).
- `pytest tests/lora/test_lora_functions.py -k dummy_batch_keeps_loras`: end to end, `execute_dummy_batch` on a running engine keeps the loaded adapters on V1 and V2, eager and with CUDA graphs, and a LoRA request still runs afterwards. On one H200, all four cases pass with this change. On main all four fail with every adapter gone (`set() == {1, 3}`).
