# [KV Offload] Add a store trigger and isolated store trigger handlers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61426) · state: closed · merged: False

## Original PR description

## Overview

Phase 1 of #61396. Please put comments on the design in the RFC.

This PR gives the offloading manager the cause of each store. It also moves the
store code of the connector into one isolated handler for each store trigger.
It changes no behavior. The only trigger is `ON_COMPUTE`, which is the current
behavior. The next PR adds `ON_OVERWRITE` stores, lets the manager select its
triggers, and adds the `lazy` store mode on top of this API.

## Claims

- New `StoreTrigger` enum, with one value: `ON_COMPUTE` (the chunks are
  complete). Later PRs add more values.
- New `trigger` parameter on `OffloadingManager.prepare_store`, with no
  default. An out-of-tree manager must add it. `complete_store` gets
  `trigger` with the default `ON_COMPUTE`. The tiering manager gives the
  trigger to its primary tier. A promotion from a secondary tier uses
  `ON_COMPUTE`.
- The connector makes its store jobs through one `StoreTriggerHandler` for
  each trigger, in `offloading/store_triggers/`. `HANDLER_FOR_TRIGGER` gives
  the handler class of each trigger. `OnComputeStoreHandler` holds the store
  code of today.
- The handlers are isolated:
  - A handler does not know of other handlers. It keeps its own state. The
    ON_COMPUTE progress of each request moves from the request state into the
    handler.
  - The scheduler holds only global state. It gives the same hooks to each
    handler: load scheduled, request removed, and reset. The load hook gets the
    chunk range and the GPU block ids of the load.
  - A handler offers chunks only with its own trigger. The scheduler gives each
    store job its ID and its trigger. It tracks the jobs and the fences, makes
    the flushes, and completes each store with the trigger of its job.

New tests:

- A handler gets the chunk range and the GPU block ids of a load.
- Each path that removes a request tells the handlers. The paths are: a
  finished request with no store job, a finished request after its last store
  job, and a cache reset.
- Each store job gets the trigger of its handler.

CI runs these tests in the `v1/kv_offload` and `v1/kv_connector/unit` jobs of
`.buildkite/test_areas/misc.yaml`. CI also runs the gsm8k offloading eval of
`.buildkite/test_areas/lm_eval.yaml`, because the change is in
`vllm/v1/kv_offload/`.

End-to-end sanity test (Qwen3-8B, CPU offloading): I ran this revision against
`main` on one H100, with the eager store mode on both sides. The cpuoverflow and
multiturn workloads gave the same numbers on both sides, within noise. Zero
server errors on both sides. The affected pytest suites pass: 1119 passed, 1
skipped.

No model eval. The manager stores the same keys as on `main`.

## Details

- **Size.** The diff adds 996 lines and removes 611 lines in `vllm/`. Most of
  the added lines are the store code of `scheduler.py`, moved into
  `store_triggers/`. The scheduler dict `_jobs` becomes `_job_statuses`,
  because it holds a `TransferJobStatus` for each job ID.
- **Compatibility.** `prepare_store` needs the new `trigger` argument, so an
  out-of-tree manager must add it. The connector does not give `trigger` to
  `complete_store` for `ON_COMPUTE`, so a manager without that parameter keeps
  working. Four upstream tests in `test_events.py` called `prepare_store`
  without the trigger. This PR adds it.
- **Where the triggers come from.** In this PR the connector builds only the
  `ON_COMPUTE` handler, and the managers do not change. The next PR lets the
  manager select its triggers, in order, from its own store mode.
- **Why the load hook gets the block ids.** The request state gets the GPU
  block ids of a load only when the request is scheduled after the load. A
  handler that needs them at load time gets them from the hook, and keeps them
  itself.
- **Behavior of the handler move.** The check that no load is pending now
  also runs for the partial-tail and boundary stores. The store debug log no
  longer shows the job ID. There is no other change.
- **`StoreTrigger` and `OffloadPolicy`.** `OffloadPolicy` selects which chunks
  a request offers. `StoreTrigger` selects when the connector offers them.
- **Not a duplicate.** I ran the `gh` searches of `AGENTS.md` again on
  2026-10-21. #50087 (draft) adds a per-request `StorePolicy` with
  `ON_FINISH`, which a tier selects. This PR gives the cause of each store to
  the manager, and isolates the store code of each trigger. #51576 and #60000
  gate the jobs between tiers, not the stores from the GPU. #60000 and #52103
  change the same files, but they do not do the same work.
- **AI assistance.** Claude helped to write the code, the tests, and this
  text. I reviewed each changed line, and I ran the tests in Validation. I can
  explain each design choice.
