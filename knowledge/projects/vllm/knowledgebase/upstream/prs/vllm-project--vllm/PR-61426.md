# [KV Offload] Add a store trigger, store trigger handlers, and store_mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/61426) · state: open · merged: False

## Original PR description

## Overview

> [!NOTE]
> This PR is an implementation suggestion for #61396. It shows one way to
> implement phase 1, so that reviewers can see the API in code. The names, the
> config keys, and the split into PRs can change after the RFC review. Please
> put comments on the design in the RFC.

Phase 1 of #61396. This PR gives the offloading manager the cause of each
store, and it lets the connector select when it offers chunks. It changes no
behavior. The only store mode, `eager`, is the current behavior. The next PR
adds `ON_OVERWRITE` stores and the `lazy` mode on top of this API.

## Claims

- New `StoreTrigger` enum, with one value: `ON_COMPUTE` (the chunks are
  complete). Later PRs add more values.
- New `trigger` parameter on `OffloadingManager.prepare_store`, with no
  default. An out-of-tree manager must add it. `complete_store` gets
  `trigger` with the default `ON_COMPUTE`. The tiering manager gives the
  trigger to its primary tier. A promotion from a secondary tier uses
  `ON_COMPUTE`.
- The connector makes its store jobs through one `StoreTriggerHandler` for
  each trigger, in `offloading/store_triggers/`. `OnComputeStoreHandler`
  holds the store code of today. The scheduler gives the job IDs, tracks the
  jobs and the fences, and makes the flushes.
- New `store_mode` key in `kv_connector_extra_config`. A `StoreMode` enum maps
  each mode to its triggers, and the connector makes one handler for each
  trigger. The only mode is `eager` (`{ON_COMPUTE}`), and it is the default.
- The scheduler dict `_jobs` becomes `_job_statuses`, because it holds a
  `TransferJobStatus` for each job ID.

## Details

- **Compatibility.** `prepare_store` needs the new `trigger` argument, so an
  out-of-tree manager must add it. The connector does not give `trigger` to
  `complete_store` for `ON_COMPUTE`.
- **Where the mode lives.** The connector reads `store_mode` and selects the
  handlers. The manager gets only the trigger of each call. `prepare_store`
  already gives back a subset of the offer, so a manager can store fewer keys
  for a trigger.
- **Behavior of the handler move.** The check that no load is pending now
  also runs for the partial-tail and boundary stores. The store debug log no
  longer shows the job ID. There is no other change.
- **`StoreTrigger` and `OffloadPolicy`.** `OffloadPolicy` selects which chunks
  a request offers. `StoreTrigger` selects when the connector offers them.
- **Not a duplicate.** Checked on 2026-10-13 with the `gh` searches of
  `AGENTS.md`. #50087 (draft) adds a per-request `StorePolicy` with
  `ON_FINISH`, which a tier selects. This PR selects the triggers with one
  store mode, and gives the cause of each store to the manager. #51576 and
  #60000 gate the jobs between tiers, not the stores from the GPU. #60000 and
  #52103 change the same files, but they do not do the same work.
- **AI assistance.** Claude helped to write the code, the tests, and this
  text. I reviewed each changed line, and I ran the tests in Validation. I can
  explain each design choice.
