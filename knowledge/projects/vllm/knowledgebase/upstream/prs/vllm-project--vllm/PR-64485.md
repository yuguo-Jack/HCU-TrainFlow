# [Bugfix][EPLB] Start the async rearrangement interval after the last layer commits

[Upstream PR](https://github.com/vllm-project/vllm/pull/64485) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Async EPLB resets the rearrangement counter only when a cycle starts. A cycle
longer than `step_interval` therefore logs a negative "steps until the next
rearrangement" and starts the next rearrangement in the same step its last
layer commits. This PR counts the interval from the last layer's commit and
logs in-flight progress instead. If a cycle overruns, a warning names the
slowest EP ranks; when the ranks wait for each other inside a transfer, it
names all of them.

Related: #57883 (stall that shows the negative count), #60685 / #60686 (load
window credited to the wrong experts), #57905.

## Claims

- Async rearrangements no longer run back-to-back. The next interval starts
  when the last layer of the last in-flight model commits.
- With `step_interval >= window_size` (default 3000 / 1000), every window row
  that the next rearrangement uses is recorded after that commit, however long
  the cycle ran.
  - On main, a cycle longer than `step_interval - window_size` leaves
    pre-commit rows in the window. #60685 notes that async EPLB has its problem
    per layer. This also hits the defaults (3000 / 1000) once a cycle runs past
    2000 steps, which #60685 does not cover.
  - The `step_interval < window_size` case of #60685 is not fixed here. Nor
    are ranks that ran dummy steps (see Limitations).
- No more negative step counts.
  - While a cycle is in flight, the balancedness log shows
    `async rearrangement in progress: k/L layers committed`.
  - Every `step_interval` steps while a cycle is still running, rank 0 warns.
    The warning names the EP ranks whose async worker is furthest behind,
    and the layer and stage they are at. A stall like #57883 shows up even with
    `log_balancedness` off.
- Sync mode is unchanged.

## Details

**Root cause.** In `EplbState.step()`, `expert_rearrangement_step` is reset
just before `rearrange()` starts a cycle.
- When the counter reaches `step_interval` while a cycle is still in flight,
  the bail-out returns without resetting it. The counter keeps growing, so the
  log goes negative. A production log showed `-250` with
  `step_interval=1500`.
- The `step()` that commits the last layer then sees
  `counter >= step_interval` with nothing in flight, and starts the next cycle
  at once.
- That cycle's window is indexed by physical slot and scattered through the new
  map. So rows recorded before each layer's commit are credited to the wrong
  logical experts.

**Change.**
- After `_move_to_workspace`, once no model is still rebalancing, set the
  counter back to 0. The `_all_ranks_result_ready` all-reduce gates the commit,
  so it happens in the same step on every rank and the counter stays
  consistent.
- The main thread tracks `num_committed_layers` for the progress log.
- `rearrange()` sets `worker_progress` to -1. The async worker then writes
  `2 * layer` while transferring a layer, and `2 * layer + 1` once its result
  is published.
- When the warning fires, each rank writes its value into its own slot of a
  zero int64 tensor of EP size. A sum all-reduce over the EP CPU group then
  gathers them. This costs one small CPU all-reduce, only when the warning
  fires. While a cycle is in flight, async mode already does a CPU all-reduce
  on that group every step (`_all_ranks_result_ready`).

**Trade-off.** In async mode, the period goes from max(`step_interval`, D) to
`step_interval + D`, where D is the cycle length. Here D was 7.3-8.9 s with
the gloo communicator, or 140-370 steps under GSM8K load. With the default
interval of 3000 steps, that makes the period 5-12% longer: about 10% without
the drafter, and about 5% with MTP. The `step_interval` docstring now says when
the interval starts.

**Not done: clearing the window on commit.**
- When `step_interval >= window_size`, clearing changes nothing on ranks
  without dummy steps, because the window is fully overwritten after the
  commit.
- On a rank that ran dummy steps, clearing would only zero the stale rows.
  #60686's logical window fixes that without throwing data away.
- When `step_interval < window_size`, clearing shrinks the effective window
  to `step_interval`, which #60686's review objected to.

**Limitations.**
- The following also apply to sync mode on main:
  - With `step_interval < window_size`, some window rows still come from before
    the commit.
  - A rank that runs dummy steps keeps some old rows, because dummy steps do
    not advance the window ring.
  - #60686's logical-expert window credits those rows to the right experts in
    both cases.
- If the ranks are stalled inside a transfer collective, the warning lists all
  of them. It still names the layer.

**Not a duplicate.**
- #60686 changes how the window is recorded, not when rearrangements run. It
  keeps the counter overrun, the negative log and the back-to-back cycles.
- #57905 replaces the bail-out condition with a `cycle_in_flight` flag, set
  and cleared together with `rebalanced`.
  - The two flags differ only after the worker's coordinated stop, which needs
    the ranks to disagree on `rebalanced`.
  - It does not change the counter reset or the log, and it edits the same
    lines in `step()`.
- #62009 (merged) moved the balancedness log into a deferred queue. This branch
  merges main and computes the in-progress status when the entry is queued.

Good point, done in 4a71a57ba9.

- The async worker now records how far it has got in the current rearrangement: which layer, and whether that layer's result has been published.
- When the warning fires, every EP rank writes its progress into its own slot of an int64 tensor of EP size, and a sum all-reduce over the EP CPU group gathers them.
- Rank 0 then logs the ranks that are furthest behind and where they are:

```
Async EPLB rearrangement still in progress after 30 steps: 1/40 layers of <model> committed, slowest EP ranks [0, 1]: transferring layer 1
```

I didn't put it behind a flag:

- The all-reduce only runs when the warning fires, which is every `step_interval` steps while a cycle is overrunning.
- While a cycle is in flight, async mode already does a CPU all-reduce on the EP group every step (`_all_ranks_result_ready`).
- In a GB200 run with `step_interval=600`, the warning never fired.

What it can and cannot tell you:

- A rank stuck outside a collective is named in every warning while it stays stuck. For example, it may still be computing the new placement, or still finishing its own transfer after the others have published. In a two-rank gloo simulation, the warning named the delayed rank.
- When the ranks wait for each other inside a layer's transfer, they all report the same layer, so the warning lists all of them. It still names the layer. These waits are:
  - the coordinated-stop all-reduce at the start of each layer;
  - the communicator's exchange: the gloo/XCCL send/recv waits, the NIXL post-read barrier, or the symm_mem barriers.
- On GB200 (DP2, gloo communicator) I ran with `step_interval=30`, so every cycle overran but no rank was actually slow.
  - 91 of 94 warnings listed both ranks.
  - The other 3 named one rank because of a short race: that rank had not yet returned from the commit of layer N, while the other was already waiting for it at layer N+1.
