# [Bugfix][Spec Decode] Keep the rejection-sampling residual nonzero in fp32

[Upstream PR](https://github.com/vllm-project/vllm/pull/65176) · state: open · merged: False

## Original PR description



## Overview

Fixes #61383: when the residual `max(p - q, 0)` is tiny, MRV2 rejection sampling now resamples a token from the target's support instead of token 0.

When the draft puts almost all of its mass on the only token the target allows, fp32 rounds the residual to zero, and the resample emits token 0. This PR keeps the residual nonzero in fp32. It complements #64242 / #65103, which fix only the global log-sum-exp layer (see Details).

## Claims

- The rejected position samples from the target's support for draft gaps up to ~87. Before, it emitted token 0 (`!`) from gap ≈ 14 on, matching the issue's `grammar rejected tokens [756, 414, 0]`.
- All math stays in fp32. There is no fp64 math and no fallback path.
- Standard and block verification are both fixed.

## Details

**Root cause.** At the rejected position the target is one-hot on `"`, and `q(") = 1 - exp(-gap)`. Three fp32 steps each round the residual to zero:

| Step | main | Rounds from |
|---|---|---|
| Per-block sumexp | `sum(exp(x - max))`, including the max's own `1` | `1 + exp(-18)` → `1` |
| Global log-sum-exp | `max + log(sumexp)` | `25 + 8.3e-7` → `25` (gap ≈ 14) |
| Residual | `log_p + log1p(-exp(log_q - log_p))` | `exp(-1.5e-8)` → `1` |

With all three rounded away, the residual is `-inf` everywhere, and Gumbel argmax then returns index 0.

**Fix.**

- **The log-sum-exp is carried as `(max, correction)`.** `_compute_global_logsumexp` returns the pair, and `_log_softmax` computes `(x - max) - correction`. The two per-request `*_rejected_logsumexp` buffers passed to `_resample_kernel` become `[num_reqs, 2]`.
- **The stats kernel's per-block sumexp leaves out one max element** (`_compute_max_and_sumexp_excluding_max`; Barron, ["A Fix for Softmax"](https://jonbarron.info/softmaxfix/)). The merge takes `log1p` of the remainder. `_compute_max_and_sumexp` is unchanged because `acceptance_estimator.py` needs the standard sumexp.
- **The residual is `log_p + log(-expm1(log_q - log_p))` when `log_q < log_p`, and `-inf` otherwise.** The `delta < 0` test also covers the `-inf` and NaN cases. The kernel already used libdevice `log1p` here; `expm1` comes from the same library.

All three are needed:

- With the first two, the correction is exact, but gap ≥ 18 still fails at `exp(delta)`.
- `expm1` alone changes nothing, because `log_q` has already rounded to `0`.

**Relation to #64242 / #65103.**

- #64242 promotes the global log-sum-exp to fp64.
- #65103 replaces that with an fp32 `(hi, lo)` pair, which is equivalent to the first bullet above. It also fixes the one-hot residual mass and takes the target log-sum-exp from an fp64 op on the top-p on-load path.

Neither changes the per-block sumexp, which matters here on the draft side, nor the exp(delta) residual. Both still resample token 0 at large gaps:

#64242: the reproducer above emits ! at gap ≥ 18.
#65103 (ae6817425a): test_resample_stays_in_target_support, added unchanged to its test file, passes at gaps 10 and 14 but fails at gap 25 under both standard and block verification, with assert [1, 2, 0] == [1, 2, 3]. The other 134 tests in that file pass on the same setup.

If #65103 lands first, this PR reduces to a small follow-up on it: the stable per-block sumexp, the `expm1` residual and the test. I'm happy to rebase it that way.

**Not changed.**

- `_compute_local_residual_mass_kernel` and the one-hot `_compute_global_residual_mass` still use `exp` followed by a subtraction. They affect the precision of block verification's acceptance threshold, not which tokens can be emitted. #65103 fixes the one-hot case.
- If `p == q` exactly in fp32, the residual is mathematically empty and would need a fallback to sampling from the target. That is out of scope.
- MRV1's `vllm/v1/sample/rejection_sampler.py` was not examined.
