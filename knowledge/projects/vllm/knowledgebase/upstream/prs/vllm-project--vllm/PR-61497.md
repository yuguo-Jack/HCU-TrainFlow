# [Perf][Mamba] Reduce host overhead in the Mamba2 Triton SSD prefill path

[Upstream PR](https://github.com/vllm-project/vllm/pull/61497) · state: closed · merged: True

## Original PR description



## Overview

Reduces host overhead in the Mamba2 Triton SSD prefill path. This PR is
part of a series that brings piecewise CUDA graphs to Mamba2 prefill steps. Tested with #61293
applied, but it does not depend on it.
- Write prefill final states into ssm_state from the SSD scan when has_checkpoints is False (4 fewer launches per Mamba layer).
- Cache the autotuned config of the Triton SSD kernels, keyed on each launch's own arguments (skips Triton's per-launch key rebuild; 43 of the 84 µs saved per Mamba layer).
- Replace einops.rearrange with flatten/unflatten (same view, about 1.5 µs less host time per call).


## Claims

- Up to 1.08x output throughput (OTPS/gpu) on 1x B200 with Nemotron-3.5-Lightning-NVFP4-W4A4 and
  MTP=2: 1.04-1.08x at concurrency 4-64, 1.02x at 128 and 1.01x at 1-2.
- Host time of the prefill SSD scan plus its final-state write drops from 263 us to 179 us per Mamba
  layer, about 1.9 ms less per mixed step with 23 Mamba layers. Every prefill or mixed step also
  issues 4 fewer launches per Mamba layer.

## Details

The Mamba2 mixer runs eagerly in prefill and mixed prefill+decode steps, so its host-side overhead
lands directly on step latency. This matters most in two cases:

1. Short OSL: prefill and mixed steps come often, and each one interrupts the ITL of every running
   request.
2. A fast GPU with low-precision quantization (e.g. NVFP4 on B200): the prefill compute is too short
   to hide the CPU overhead.

Before this PR, a varlen SSD scan plus the final-state write spent 263 us of host time per Mamba
layer, mostly Python launch overhead, and each layer issued 4 extra launches to write final states
back. Changes, all on the default Triton SSD path:

- Write each sequence's final state into its `ssm_state` slot from `_state_passing_fwd_kernel`,
  replacing the index casts, gather and `index_put`. The checkpoint path and CPU path are unchanged.
- Add `launch_autotuned()`, which reuses the autotuner's chosen config and skips Triton's per-launch
  key rebuild. It builds its cache key from the launch's own arguments (the values of the kernel's
  autotune `key` arguments plus each argument's dtype, the information Triton's key holds), so callers
  keep no key list and the selected config is unchanged.
  - Same-node A/B with (two serves) vs without it (one serve): +1.0% to +2.5% OTPS/gpu at concurrency 4-64 (+2.5% at 64) and
    flat at 1-2 and 128; it accounts for 43 of the 84 us saved per layer.
- Drop 4 redundant device guards in the SSD wrappers.
- Replace `einops.rearrange` with `flatten`/`unflatten`.
- Cache `CudaPlatformBase.is_arch_support_pdl()`.
