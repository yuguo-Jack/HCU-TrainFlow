# [Bugfix][KV Offload] Refresh streaming request keys after preemption

[Upstream PR](https://github.com/vllm-project/vllm/pull/65640) · state: open · merged: False

## Original PR description

## Overview

With lookahead block hashing, a streaming input continuation can replace a token included in a cached block's hash. If the request is preempted, the scheduler recomputes its block hashes from the current tokens, but `OffloadingConnector` retains its previously recorded keys. It can then look up stale entries or skip storing the recomputed KV, causing later requests to miss the CPU cache and recompute the prefix.

Before looking up a resumed request, refresh each group's offload keys against the recomputed hashes. Preserve the unchanged prefix and rebuild only the changed suffix.

This is a follow-up to lookahead hash support in #61589 and #64096.

## Claims

- Offload lookups use the recomputed hashes after a streaming request resumes.
- Unchanged key prefixes are retained; only the changed suffix is rebuilt.

## Validation

On `main` at `0db3734d51`, the new unit test fails before the fix because the connector retains the old key, and passes with the fix.

pytest -q tests/v1/kv_connector/unit/offloading_connector/test_scheduler.py

**End-to-end:** Qwen3.5-0.8B, MTP with one speculative token, `OffloadingConnector`, and NVIDIA GB10. A two-part streaming request was resumed with `reset_prefix_cache(reset_running_requests=True, reset_connector=False)`. After it completed, the GPU prefix cache was reset and a second request reused the resulting prefix.

| | Before | After |
| --- | --- | --- |
| Second request's CPU cache hit | 0 tokens | 576 tokens |
| Second request's output tokens | `[198, 196, 196]` | `[198, 196, 196]` |

Before the fix, three KV groups had the new key but the MTP group did not, so the prefix could not be loaded. With the fix, all four groups hit and the 576-token prefix was loaded from CPU. This is a single functional run, not a latency benchmark.

## Details

While a streaming request's KV remains resident, its existing hash still describes that KV. When the request restarts from zero computed tokens, the core scheduler recomputes hashes for the current token sequence. The connector previously only appended keys, leaving already-recorded positions unchanged.

The connector now compares each group's last retained key with the corresponding recomputed hash. Because block hashes are chained, a mismatch permits a binary search for the first changed key; the existing incremental update then rebuilds the suffix. The check runs on resumed streaming requests with lookahead hashing and does not change resident KV handling.
