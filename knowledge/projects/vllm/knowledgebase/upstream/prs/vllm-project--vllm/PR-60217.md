# [ROCm] MoE balanced routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/60217) · state: open · merged: False

## Original PR description



## Overview

It is well known that expert parallelism often produces unbalanced workload between the ranks which may cause a significant performance regression. MoE balanced routing feature adds a load-penalized logit adjustment for MoE routing under expert parallelism (VLLM_MOE_BALANCE_ROUTING_EMA). Instead of correcting overflow after top-k selection, the router logits are adjusted before top-k so the router naturally avoids overloaded EP ranks.

## Claims

- Reduces all-to-all combine latency on DeepSeek-V3 with 8 EP ranks by steering tokens away from hot ranks before dispatch
- Tokens with strong expert preferences (large logit gap) are minimally affected; ambiguous tokens absorb most of the load shift
- Zero computational cost when all ranks are balanced
- No CPU-GPU synchronisation — penalty computation is pure tensor op; function returns unchanged logits during torch.compile tracing and CUDA-graph capture

## Validation

Vllm serve configuration:

```
export HSA_NO_SCRATCH_RECLAIM=1
export NCCL_MIN_NCHANNELS=112
export SAFETENSORS_FAST_GPU=1
export VLLM_ROCM_USE_AITER=1
export VLLM_ROCM_USE_AITER_MLA=1

vllm serve deepseek-ai/DeepSeek-V3 \
    --enable-expert-parallel \
    --gpu-memory-utilization 0.9 \
    --tensor-parallel-size 8
```

And for the balanced routing feature we simply add a single environment variable:

`export VLLM_MOE_BALANCE_ROUTING_EMA=1`

Results (MI350X):

| Configuration    | Request throughput (req/s) | Perf gain | Median TTFT (ms) | Median TPOT (ms) | GSM8K accuracy |
|------------------|---------------------------|----------------|------------|---|---|
| Baseline         | 3.28                      | - |  1958 | 67.13 | 0.95         |

Please note that some accuracy regression is inevitable, since some tokens aren't routed to the best expert. However, this accuracy regression is very small compared to the significant performance boost obtained in the above benchmark.

## Details

Mechanism. Each forward pass, the router logits are adjusted before top-k:

`adjusted_score(t, e) = logit(t, e) - λ * max(0, ema_load[rank(e)] / fair_share - 1)`

where ema_load is a [ep_size] float tensor on the GPU, updated each step from the previous step's topk_ids:

`ema_load = (1 - α) * ema_load + α * rank_counts`

and

`fair_share = ema_load.mean()`

Only ranks above their fair share are penalised; under-loaded ranks receive no bonus.

EMA (Exponential Moving Average). The term EMA appears in the env var names (VLLM_MOE_BALANCE_ROUTING_EMA), the new file balance_routing_ema.py, and the internal state tensor _ema_load. It refers to the smoothed per-rank token-slot count used to estimate load — a running average that weights recent steps more heavily than older ones, controlled by alpha.

Why proactive rather than reactive? Post-hoc overflow correction (redirecting tokens after top-k) requires a hard capacity threshold. Crossing it causes a sudden jump in the fraction of slots redirected, which tanks accuracy. The EMA penalty instead applies a smooth, continuously-scaled signal: at low load imbalance the penalty is near zero; at high imbalance it is proportional to the excess. There is no binary cliff.

Lambda stability. At high values of lambda the penalty can overshoot: all tokens flee the hot rank, it becomes cold, the formerly-cold rank becomes hot, and the system oscillates. lambda=2.0 (default) was empirically stable on DeepSeek-V3 with 8 EP ranks.

Shared-expert compatibility. Shared-expert columns (IDs ≥ num_experts, appended by VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS) are excluded from load counting via is_routed, so the fair-share denominator reflects only routed slots.

Limitations. The EMA lags by one step (penalty is based on the previous batch's routing). At low concurrency the per-step signal is noisy; alpha=0.1 provides enough smoothing for batch sizes typical of concurrent serving. The approach does not help during CUDA-graph-captured steps (returns unchanged logits), but the EMA warms up during non-captured (prefill) steps and remains valid during decode.

Relation to EPLB. vLLM already ships expert-parallel load balancing via --enable-eplb, which periodically reassigns expert weights across ranks using P2P transfers. This PR addresses a different tradeoff: EPLB eliminates imbalance at the cost of periodic weight movement and a step_interval lag before rebalancing takes effect. The EMA penalty operates entirely within the routing decision on every forward pass — no weight transfers, no rebalancing events — making it complementary rather than competing. The two features can be enabled simultaneously.
