# [Kernel][Perf] Optimize NVFP4 MoE quant cvt_fp16_to_fp4 on Blackwell 

[Upstream PR](https://github.com/vllm-project/vllm/pull/61511) · state: open · merged: False

## Original PR description



## Overview

Speeds up the NVFP4 MoE experts quant kernel (`scaled_fp4_experts_quant`, `silu_and_mul_scaled_fp4_experts_quant`) on B200 with tests to ensure numerical equivalence (and identical GSM8K accuracy and output token count vs main). At large `n_experts` the per-row expert search makes the op compute-bound on B200, so this PR cuts its cost with an incremental gallop/bisect lookup over shared-memory expert tables and fewer executed instructions per thread.

## Claims

- **`scaled_fp4_experts_quant` on B200:**  2.4–2.7× faster at 16384 tokens and 1.7–1.8× at 1024 tokens.
- **`silu_and_mul_scaled_fp4_experts_quant` on B200:** 3.8–3.9× faster at 16384 tokens and 2.1–2.2× at 1024 tokens.
- **Decode (1–16 tokens):** 1.35–3.0× faster for both ops, with the largest gain at `n_experts`=512.
- **One kernel for all sizes:** removes `main`'s separate low-latency kernel for small token counts; the new kernel is at least as fast at every measured size (1.35–3.0× at 1–16 tokens, on par at 64).
- **New correctness tests** for both ops: `tests/kernels/moe/test_nvfp4_moe.py`
- **New benchmarks** for both ops and various expert and token sizes: `benchmarks/kernels/benchmark_nvfp4_moe_quant.py`

## Validation

**Correctness:** new tests in `tests/kernels/moe/test_nvfp4_moe.py`, which run in CI under the `(B200) FP4 MoE Kernels` and `(B200) Kernels` steps.

- `test_scaled_fp4_experts_quant` checks each expert against `ref_nvfp4_quant`, vLLM's PyTorch-only NVFP4 reference (`nvfp4_emulation_utils.py`). Block scales must match exactly. FP4 values may be one E2M1 step off in fewer than 0.1% of elements.
- `test_silu_and_mul_scaled_fp4_experts_quant` compares against `silu(gate) * up` computed in fp64 and rounded once to bf16/fp16, then quantized with `scaled_fp4_experts_quant`. FP4 values may be one E2M1 step off in fewer than 2% of elements, and block scales one FP8 code off in fewer than 10%.
- Both tests also check that the one-step mismatches are unbiased: the signed sum stays within 4σ, so the errors don't systematically shrink or grow magnitudes.

## Details

**Shared code:** outside the experts kernel, the PR adds an `st64_cs` streaming-store helper to `cuda_vec_utils.cuh` and changes `nvfp4_utils.cuh`, which the dense NVFP4 and MXFP4 quant kernels also use. Each pair of per-element scale multiplies becomes one `__fmul2_rn`, a paired fp32 multiply that rounds exactly like two separate `__fmul_rn`, so those kernels' output is unchanged. It saves instructions in the memory-bound kernels that include this header.

**16 elements per thread:** the experts kernel now defines `NVFP4_ENABLE_ELTS16`. #32520 introduced it for the dense NVFP4 quant and activation+quant fusion kernels, and #37463 turned it on for the MXFP4 experts kernel. This kernel only got the signature update in #32520, and that PR gives no reason for leaving it out. Each thread now loads one 32 B vector (a single 256-bit load on SM100) and computes exactly one scale factor, so the max no longer has to be shuffled between two threads. The kernel relies on this: each thread writes one 64-bit output word and one scale-factor byte, both indexed directly by its vector index. This requires CUDA ≥ 12.9.

[Three approaches](https://github.com/thisisjimmyfb/vllm/tree/cvt_fp16_to_fp4) were tried, side by side behind a compile-time switch, and measured on B200:

1. **Grid-stride over packed vectors** (this PR): each thread quantizes one 16-element vector per iteration across a single wave of blocks and writes its scale-factor byte directly, uncoalesced.
2. **Per-tile blocks with staged SF writes**: blocks grid-stride over 128-row × 64-column tiles of the swizzled scale-factor layout, staging each tile's scale factors in shared memory so they are written out coalesced.
3. **Rotated SF-tile mapping**: tile-based like (2), but with the thread-to-vector mapping rotated so each warp writes a whole 32 B SF sector directly, without shared-memory staging.

The grid-stride loop was fastest. The tile variants only help the scale-factor writes, which are 1 byte per 8 bytes of FP4 output, and at large token counts the cost of leaving them uncoalesced is insignificant. At large expert counts, the kernel is compute-bound on B200 instead: the per-row expert search pushes it past the instruction budget that B200's bandwidth allows. There, the staging, synchronization and extra indexing of the tile variants cost more than they save. The grid-stride loop is the simplest per-element path, which leaves the most headroom for the expert search.

I have also asked Claude to analytically derive the performance model which seems to match the observation from ncu captures:

<summary><b>Performance model</b></summary>

### Executed instructions

The model counts **executed instructions per warp-iteration**, I: warp instructions issued per 32 vectors, measured with ncu as `smsp__inst_executed.sum / (V/32)`. Only paths actually taken count (a probe loop counts once per probe), predicated-off instructions still count, and a warp pays for its slowest lane. It is not the static count of SASS instructions in the loop.

| c_p | executed instructions per search probe | 8.5 (fitted) | assumed same |

### 1. The three limits

A launch costs a fixed amount plus the time to stream its V vectors, and the stream is limited either by DRAM bandwidth or by instruction issue:

> **T ≈ T₀ + max(T_mem, T_compute)**

- **Fixed cost:** T₀ = t_L + t_S + λ. That's launch and teardown, staging the expert tables (one memory round trip plus a barrier, since every table load is issued before any store), and the latency of the first input load. None of these depends on N.
- **Memory time:** T_mem = V·B / (η·BW).
- **Compute time:** T_compute = (V/32)·I / (S·P·f·u).

Whichever term dominates is the bottleneck:

| bottleneck | condition | meaning |
|---|---|---|
| **latency** | max(T_mem, T_compute) < T₀ | too little work to amortize the fixed round trips |
| **memory** | T_mem ≥ T₀ and I ≤ I\* | DRAM bandwidth sets the time |
| **compute** | T_compute ≥ T₀ and I > I\* | instruction issue sets the time |

The memory/compute boundary is the **instruction budget**, the largest I that still fits in the time DRAM needs for each vector:

> **I\* = 32·B·S·P·f·u / (η·BW)**

The latency boundary is a **token threshold**. At small N the loop is memory-limited, so the crossover is where T_mem = T₀:

> **N_lat = T₀ · η · BW · 16 / (B · topk · K)**

| | B200 | RTX PRO 6000 |
|---|---|---|
| DRAM bytes per issue slot (BW / S·P·f) | 6.6 | 0.91 |
| quant budget I\* | **≈ 199** | **≈ 1431** |
| T₀ | ≈ 4 µs (measured with ncu at 1–8 tokens, flat across E) | ≈ 4 µs (assumed) |
| quant N_lat (topk 10, K = 2560) | **≈ 370 tokens** | **≈ 90 tokens** |

B200's HBM delivers bytes so fast that every executed instruction counts, and it needs more tokens before bandwidth matters at all. The PRO 6000 has about 7× more issue slots per byte and reaches its bandwidth limit at fewer tokens.

The structure of T₀ is derived, but its parts are hardware latencies: λ ≈ 0.6–0.8 µs, and t_L ≈ 1–2 µs from an empty kernel with this grid. Their sum, t_L + 2λ ≈ 2.5–3.5 µs, is a little under the measured 4 µs; the rest is likely the final store drain and the search's dependent shared-memory loads. **Check:** at 256 tokens the model gives T ≈ 4 + 2.7 ≈ 6.7 µs, against about 7–8 µs measured (11.2 µs in the benchmark, minus 3–4 µs of event-timing overhead).

### 2. What decides memory against compute

Executed instructions are a fixed part plus the expert search: I ≈ I₀ + c_p · (probes per iteration). Two numbers then decide the memory/compute split.

**The GPU's probe budget**, how many search probes per iteration fit within I\*:

> **h = (I\* − I₀) / c_p** ≈ **6 on B200**, ≈ **150 on the RTX PRO 6000**

**The problem's mean jump**, how many experts a thread skips per iteration. Every thread runs from the first rows to the last, so over its n_it iterations it crosses about all E experts:

> **d = E / n_it = 16·E·G / (N·topk·K)**

**Probes per lookup.** A thread keeps its expert from the previous iteration. If the row has moved past it, the kernel either gallops from the current expert, costing about log₂(2d²) probes (finger search: O(log d)), or bisects the rest of the table, costing about log₂E. Its gallop condition n_it² > 2E is algebraically the same as 2d² < E, so it always takes the cheaper of the two:

> **probes ≈ min( log₂E, log₂(2d²) )**

The kernel is compute-bound when both searches exceed the budget:

> **compute-bound ⇔ E > 2ʰ and d > 2^((h−1)/2)**, i.e. **E > max( 2ʰ, 5.2 · N·topk·K / (16·G) )** on B200

### 3. Bottleneck map

| bottleneck | condition | B200 (h ≈ 6) | RTX PRO 6000 (h ≈ 150) |
|---|---|---|---|
| latency | N < N_lat: the fixed cost T₀ outweighs the streaming time | N < ~370 tokens | N < ~90 tokens |
| compute | N ≥ N_lat, E > 2ʰ **and** d > 2^((h−1)/2) | **E > max(55, N/36)** | never |
| memory | N ≥ N_lat, otherwise | E ≤ max(55, N/36) | all E |

Thresholds are for quant with topk 10 and K = 2560. For other shapes, N/36 becomes 5.2·N·topk·K/(16·G), and N_lat scales with 1/(topk·K).

**B200 map:**

| tokens N | E=32 | E=64 | E=128 | E=256 | E=512 | E=1024 | E=2048 |
|---|---|---|---|---|---|---|---|
| 64, 128, 256 | latency | latency | latency | latency | latency | latency | latency |
| 512–2048 | mem | **cmp** | **cmp** | **cmp** | **cmp** | **cmp** | **cmp** |
| 4096 | mem | mem | **cmp** | **cmp** | **cmp** | **cmp** | **cmp** |
| 8192 | mem | mem | mem | **cmp** | **cmp** | **cmp** | **cmp** |
| 16384 | mem | mem | mem | mem | **cmp** | **cmp** | **cmp** |
| 65536 | mem | mem | mem | mem | mem | mem | **cmp** |

**RTX PRO 6000 map:**

| tokens N | E=32 | E=64 | E=128 | E=256 | E=512 | E=1024 | E=2048 |
|---|---|---|---|---|---|---|---|
| 64 | latency | latency | latency | latency | latency | latency | latency |
| 128, 256 | mem | mem | mem | mem | mem | mem | mem |
| 512–2048 | mem | mem | mem | mem | mem | mem | mem |
| 4096 | mem | mem | mem | mem | mem | mem | mem |
| 8192 | mem | mem | mem | mem | mem | mem | mem |
| 16384 | mem | mem | mem | mem | mem | mem | mem |
| 65536 | mem | mem | mem | mem | mem | mem | mem |

**Legend:**
- **latency**: N < N_lat (≈ 370 tokens on B200, ≈ 90 on the RTX PRO 6000); the fixed cost T₀ outweighs the streaming time.
- **mem**: memory-bound; executed instructions fit within I\*, so DRAM bandwidth sets the time.
- **cmp**: compute-bound; the expert search pushes executed instructions past I\*, so instruction issue sets the time.

On the PRO 6000, no cell is compute-bound: reaching its budget would take about 150 search probes per iteration (h ≈ 150), and a search over E experts never needs more than log₂E, about 11 at E = 2048.

What this means:
- **Just above N_lat on B200, more than about 55 experts is compute-bound:** threads take few iterations, so each lookup is a near-full bisection.
- **Larger N pushes the compute boundary out in proportion (E ≈ N/36),** because each thread skips fewer experts per iteration and galloping stays cheap.
- **The prefill sizes this PR targets sit on the boundary.** At 16384 tokens, E=128 and E=256 are memory-bound and E=512 is compute-bound, which is why E=512 gains the most from cheaper lookups.
- **Below N_lat, only the fixed cost matters:** launch, staging and the first round trips, not the search or bandwidth.
- **On the PRO 6000 only bytes matter,** so cutting executed instructions barely changes its runtime. This is why B200 is the reference for this PR.

### 4. Fit and caveats

I₀ and c_p come from the B200 quant sweep at 16384 tokens (n_it ≈ 86, galloping):

| E | d | probes log₂(2d²) | measured I | model 150 + 8.5·probes | measured DRAM % of peak |
|---|---|---|---|---|---|
| 128 | 1.5 | 2.1 | 168 | 168 (anchor) | 83% |
| 256 | 3.0 | 4.2 | 184 | 185 | 78.5% |
| 512 | 6.0 | 6.1 | 202 | 202 (anchor) | 73% |

E=128 and E=512 set the constants; E=256 is a prediction, off by one instruction.

Caveats:
- **Cells near a boundary can go either way:** within a probe of h, or near N_lat, small changes in u, T₀ or the instruction count move them. That covers E=64 at 512–2048 tokens, E=128 at 4096, and the rows around 256–512 tokens on B200.
- **T₀ is measured, not derived bottom-up.** Microbenchmarks of an empty launch (t_L) and a staging-only kernel (t_S) would check that t_L + t_S + λ reproduces it.
- **Dependent shared-memory loads in long searches also lower u,** so E=512 measures 73% of DRAM peak rather than the about 79% the model predicts.
- **SiLU always bisects and isn't mapped;** its I₀ hasn't been measured. Its output has a quarter of quant's columns (K = 640), so at the same N its jumps are 4× larger, and its N_lat is about 2× higher in tokens (N_lat ∝ 1/(B·K), with B = 73 against 41).
- **The PRO 6000 numbers use spec bandwidth and boost clock, and assume B200's instruction counts and T₀.** A lower achieved bandwidth raises its budget I\* and N_lat.
- **The constants come from one capture.** An ncu sweep at 512, 1024 and 4096 tokens would test both predicted boundaries directly.
