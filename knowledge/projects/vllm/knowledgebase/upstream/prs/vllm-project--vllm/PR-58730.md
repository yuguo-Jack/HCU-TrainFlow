# [Bugfix] Clamp remote_prefill_cached_tokens override to [0, prompt_len]

[Upstream PR](https://github.com/vllm-project/vllm/pull/58730) · state: open · merged: False

## Original PR description

Fixes #58728

## Purpose

clamp the client-reachable `kv_transfer_params.remote_prefill_cached_tokens` override to `[0, prompt_len]` so `prompt_tokens_details.cached_tokens` and request metrics cannot report values outside the prompt length.

## Scope

- in: the override site in `vllm/v1/engine/output_processor.py` (`RequestState.remote_prefill_cached_tokens` application)
- out: broader `kv_transfer_params` hardening tracked separately (#54807, #55182, #51137, #56585, #56814)

## Why not duplicate

searched open PRs for `remote_prefill_cached_tokens` / `prompt_tokens_details` validation. the hardening PRs above cover registration, sub-dict types, tp_size and reserved keys, none clamps the accounting value. no issue existed, filed #58728.

## Validation

- red-green at the OutputProcessor level on current main (25b0add7):
  - before: remote=9999 with an 8-token prompt reports `num_cached_tokens=9999`; remote=-5 reports -5
  - after: clamped to 8 and 0 respectively, in-range passthrough unchanged (5 -> 5)
- new test `test_remote_prefill_cached_tokens_override_clamped` covers passthrough, upper clamp, lower clamp
- existing `test_remote_prefill_cached_tokens_override` stays green (in-range values unaffected)
- live repro on A10, nightly image, `--enable-prompt-tokens-details`: forged `cached_tokens: 9999` and `-5` in the API response, see issue transcript

command: `PYTHONPATH=. python <repro script>` (OutputProcessor constructed directly, no GPU needed for the unit path)

## Interpretation

this proves and fixes the bounds violation on the accounting value. in-range forged values from a client remain indistinguishable from router-supplied truth at this layer, which is the trust question under discussion in the linked hardening PRs.
