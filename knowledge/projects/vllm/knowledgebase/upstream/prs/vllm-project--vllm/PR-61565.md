# [Model] Support Decision 3.0 decision models (vllm-sr/d3)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61565) · state: closed · merged: True

## Original PR description



## Overview

Serve the Decision 3.0 decision models ([`vllm-sr/d3`](https://huggingface.co/vllm-sr/d3) and its smaller variants such as `vllm-sr/d3-mini` and `vllm-sr/d3-edge`) from their Hub checkpoints as they are: `vllm serve vllm-sr/d3`, then ask typed questions on `/v1/systemone`. Today these checkpoints do not load in vLLM (`Qwen3_5Model` is not a registered architecture and the readout is a separate file). This builds on vLLM's Qwen3.5 implementation, the structured decisions API (#60465 and its predecessors) and the Clef-Flash detection pattern (#61308).

## Claims

- **The published checkpoints load unchanged** (measured here: d3, d3-mini and d3-edge; see Follow-ups). A bare `Qwen3_5Model` checkpoint that ships a `decision_config.json` is detected and served as `D3ForSequenceClassification`. The 255-row answer-code readout (`readout.safetensors`) becomes the FP32 `score` head. The declared `noncausal_full_attention` makes the full attention layers bidirectional, while the Gated DeltaNet layers stay causal. Tied embeddings need nothing, and per-model `layer_types` are honoured (d3-edge: `llFllFllFFFF`).
- **`/v1/systemone` gives the checkpoint runtime's answers.** For each question, `D3Strategy` writes the prompt the checkpoint's own `d3_format.py` writes (byte-identical on 416 prompts), reads the question's codes from the classify head, and applies the option mask and the checkpoint temperature. It supports choice (up to 255 options), yes / no and score questions, text and JSON states, and images and videos read with the runtime's budgets (1.6 MP images; 2 fps, at most 32 frames of 0.2 MP).
- **Same decisions as the reference runtime on AMD Instinct MI325X.** Against `AutoModel.from_pretrained(..., trust_remote_code=True)`: 0 of 416 decisions changed on d3, 1 on d3-mini and 2 on d3-edge, all ties or near-ties. The median probability difference is 0.0024 to 0.0029.
- **Throughput.** On a mixed text / JSON / image / video load at 8 and 64 closed-loop clients, vLLM sustains 1.4x to 2.6x the rate of the checkpoint's own server (AutoModel behind HTTP, one request at a time).

## Details

- **Detection** follows Clef-Flash: `Qwen3_5ModelArchConfigConvertor` maps `architectures: ["Qwen3_5Model"]` plus `decision_config.json` to `D3ForSequenceClassification` and keeps the decision config on `hf_config`. Bare `Qwen3_5Model` checkpoints without that file are unaffected (they stay unsupported, as today).
- **Config hook** `D3ForSequenceClassificationConfig` validates `format_version` 1, `pooling: last` and the attention mode. It sets `is_causal=False` for `noncausal_full_attention`, so chunked prefill and prefix caching turn off by themselves, sets `id2label` to the 255 codes, and makes the classify head return raw code logits by default. Probabilities only exist over a question's own options, so `/classify` and `/pooling` callers mask and normalize themselves.
- **Model** (`d3.py`): `as_seq_cls_model(Qwen3_5ForConditionalGeneration)`, so no LM head is allocated and the `score` head is FP32. It adds a mapper for the bare-backbone keys, `readout.safetensors` as `score.weight` via `secondary_weights`, and a processing info that applies the runtime's media budgets. The checkpoint's processor config allows 16.7 MP images, while the runtime reads at most 1.6 MP; video frames use transformers' `cap_pixels_per_frame` with the runtime's 200,704-pixel cap.
- **Strategy**: one classify read per question. The media come first, so they are processed once per request and shared by its questions, and the encoder cache deduplicates the vision tower. Videos go through the existing `qwen3_vl` loader, whose sampling rule already matches the runtime's, with `max_frames=32`. A small change to the question builder, `DecisionLimits.labeled`, lets label-free strategies accept more options than the A to Z label set; the defaults of other strategies are unchanged.
- **Why not an example client**: the System One API already has question types on main, so the option mask and temperature belong in the strategy rather than in client code.
- **Tradeoffs and limits**
  - Start-up: with chunked prefill off, the profiling pass runs one `max_model_len`-token sequence. At the config's 262,144 tokens this dominates start-up (71 s of d3's 130 s warm start). `--max-model-len 32768` halves it, with no throughput change on this mix.
  - Memory: vLLM reserves `--gpu-memory-utilization` (0.92) of HBM. The Gated DeltaNet layers still keep per-request state, and the attention layers keep no KV.
  - Media under load: at 64 clients, text stays fast (d3-edge text p90 about 80 ms) while image and video requests queue (image p50 2.65 s), because decoding a new 300-frame 1080p video per request is CPU-bound. `--renderer-num-workers 4` did not change this.
  - Small-model latency: one request at a time, multi-question requests on the small models are slower than in process (d3-edge, 16 questions: 29.0 vs 21.2 ms), since each question is its own engine request.
  - API differences from the runtime: a request with an invalid or too-long question returns 400 instead of per-question errors; at most 64 questions per request (the API's limit); `confidence` and `usage` follow `/v1/systemone`'s definitions; option descriptions, instructions and score levels are rendered as text (non-string values go through `str`, where the runtime writes JSON); the runtime's optional `permutation_average` is not available.
  - Not measured: d3-flash, d3-nano and d3-lite (same layout and code path), CUDA GPUs, tensor parallelism, LoRA.
- **Not a duplicate**: no open or closed PR or issue covers these checkpoints, `decision_config.json` readout checkpoints, or bare `Qwen3_5Model` loading (searched for d3, Decision 3.0, `Qwen3_5Model`, `decision_config.json`, decider, readout). The Laya PR (#58429) adds an unrelated ModernBERT-based model.
- **AI assistance** was used for the code, tests, measurements and this description. The PR stays a draft until the submitter has reviewed every line.

## Follow-ups

- **The other five Decision 3.0 models** (`vllm-sr/d3-flash`, `vllm-sr/d3-mini`, `vllm-sr/d3-nano`, `vllm-sr/d3-lite`, `vllm-sr/d3-edge`) share d3's architecture and take the same code path: each Hub checkpoint is a bare `Qwen3_5Model` with a `d3-code-readout-v1` `decision_config.json` (`noncausal_full_attention`, 255 codes) and a `readout.safetensors`. The variations between them, tied embeddings and d3-edge's layer layout, are exercised by d3-mini and d3-edge.
- **d3-mini and d3-edge** already match the reference in this PR's measurements (1 and 2 of 416 decisions changed, all ties or near-ties; see the agreement and throughput tables under Validation).
- **A follow-up PR** will validate d3-flash, d3-nano and d3-lite, publish agreement and throughput for all five, and add them explicitly to the docs examples and tests where it makes sense.
