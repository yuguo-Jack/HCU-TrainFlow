# [Bugfix][KV Events] Emit BlockRemoved only for the last cached copy of a block hash

[Upstream PR](https://github.com/vllm-project/vllm/pull/58508) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Emit `BlockRemoved` only when the last physical copy of a prefix-cache hash disappears. This keeps KV-event consumers from discarding a prefix that the engine still caches.

## Claims

- Evicting one of several copies leaves the external hash resident until the final copy disappears.
- The guard applies to eviction and partial-prefix replacement or promotion through the shared event emitter.
- The change preserves the event schema, cache-group isolation, `BlockStored` behavior, and the internal `pop` contract.

## Validation

The existing eviction test checks that the first duplicate removal emits no event and the final removal emits the expected hash. It also checks single-copy removals.

```bash
.venv/bin/python3 -m pytest tests/v1/core/test_prefix_caching.py \
  -k 'maybe_evict_cached_block or kv_cache_events' -q --confcutdir=tests/v1/core
.venv/bin/python3 -m pytest tests/distributed/test_kv_cache_events.py \
  -q --confcutdir=tests/distributed
.venv/bin/pre-commit run --files \
  tests/v1/core/test_prefix_caching.py vllm/v1/core/block_pool.py
```

The refreshed branch passes the selected eviction/event tests (7 passed, 158 deselected) and event-schema tests (17 passed). The repository pre-commit hooks pass on both changed files.

End-to-end serving validation is pending for this revision. The unit commands exclude the root `tests/conftest.py` because the available environment lacks `tblib`. The regression already runs in the Buildkite CPU job.

## Details

vLLM can keep several physical blocks for the same prefix hash. On current `main`, removing any copy emits `BlockRemoved`, even while another copy remains available. A router that treats this event as hash eviction can underestimate the engine's cached prefix and choose another engine. This PR makes no throughput or latency claim.

The shared emitter checks the existing hash map after removal. The key includes the cache group, so another group's copy cannot suppress an event. Event-disabled execution returns before the added lookup. Event-enabled removal adds one dictionary lookup per removed hash. Hash relocation remains event-free. Both model runners use this scheduler-side cache pool, so a separate MRV2 change is unnecessary.

This existing PR overlaps [#55092](https://github.com/vllm-project/vllm/pull/55092), which fixes the same behavior through copy counts. This version retains the existing map-removal contract and adds a guard in the event emitter. The overlap needs maintainer coordination before either equivalent fix merges.

- aliceco01 · COMMENTED · 2026-10-17T09:53:46Z · [source](https://github.com/vllm-project/vllm/pull/58508#pullrequestreview-5557283414)

This fixes the spurious removal for consumers that keep a set of hashes, but `BlockStored` is still emitted for every copy, so consumers that count references would now keep hashes the pod has already evicted.

1. `vllm/v1/core/block_pool.py:620`: removal is now per hash, but stores are still per copy (`cache_full_blocks`, `cache_partial_block`). A hash with two copies gives two stores and one removal, so a consumer that counts references never gets back to zero. llm-d-router counts this way (`pkg/kvevents/event_dedup_filter.go`), so it would keep routing to prefixes the pod no longer holds. Either emit `BlockStored` only for the first copy as well, or keep per-copy events and expose the remaining count, as #48933 does.

2. #60616 documents `BlockRemoved` as per copy, and its `test_each_copy_of_a_hash_is_stored_and_removed` would fail with this change. The offloading connectors also stay per copy, so one stream would carry two meanings. Could the semantics be settled on #60616 first, and one of this PR, #55092 and #48933 picked?

3. `tests/v1/core/test_prefix_caching.py:3351`: the duplicate is built with `set_block_hash` and `insert` directly, so the test never goes through `cache_full_blocks`. A test that caches two real copies and evicts them, asserting store and removal counts per hash, would cover the real path.
