# [Spec Decode] Keep drafters within their rotary cache on the V2 model runner

[Upstream PR](https://github.com/vllm-project/vllm/pull/63251) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Keep V2 drafters from reading past their rotary cache when the target is served with a longer context (#57941). Where it's safe, the drafter's `max_position_embeddings` is raised to the target's `max_model_len`. Otherwise, on Model Runner V2, the engine's `max_model_len` is lowered to the drafter's, with a warning.

This incorporates the generalization from #57964 by @twu3202 (co-author on the second commit).

## Claims

- The `max_position_embeddings` override that already exists for EAGLE (#48894) now applies to every method except `draft_model`, including DFlash, DSpark and MTP. It's applied only when all of the drafter's RoPE types use that value just to size the cache: `default`, `linear`, `llama3`, `ntk`, `proportional`.
- On V2, any other drafter with a `max_model_len` below the target's lowers the engine's `max_model_len`, with a warning. That covers independent `draft_model` drafters and drafters whose RoPE type can't be extended (yarn, dynamic, longrope, ...). Today such a drafter crashes the engine with an illegal memory access on the first request past its limit.
- V1 is unchanged. It skips speculation past the drafter's limit (`_input_fits_in_drafter`), so the target's `max_model_len` stays as it is.

## Validation

- `tests/config/test_speculative_draft_limits_max_model_len.py` (new, CPU):
  - `draft_model` (2048) with an 8192 target: `max_model_len` is 2048 on V2 (this fails without the change) and stays 8192 on V1.
  - EAGLE-3 drafter (2048) with an 8192 Llama-3.1 target on V2: the cache is raised and `max_model_len` stays 8192. With the RoPE type treated as not extendable, `max_model_len` is lowered to 2048.
- `tests/config/test_speculative_draft_max_position_embeddings.py` (from #57964): which RoPE types allow raising the cache, and DFlash/DSpark drafters inheriting a 65536 target context.
- TODO: CI test results, and an end-to-end repro (`Qwen/Qwen3-4B` at 65536 with `z-lab/Qwen3-4B-DFlash-b16`, and with a `draft_model` drafter, sending a request longer than the drafter's limit).

## Details

Root cause: `SpeculativeConfig` sets `draft_model_config.max_model_len = min(draft, target)`. On V1, the model runner turns that into a check that skips speculation for longer batches. The V2 speculators never read the drafter's `max_model_len`: they clamp positions and sequence lengths against the target's, so they keep drafting past the drafter's rotary cache.

- **Raise when possible:** drafters other than `draft_model` take the target's positions. For cache-only RoPE types, `max_position_embeddings` only sizes `cos_sin_cache`, so raising it doesn't change the rotary frequencies. Other RoPE types either size the cache from `original_max_position_embeddings` or derive frequencies from `max_position_embeddings`, so raising it there would be wrong.
- **Otherwise cap:** making V2 skip speculation per batch would be less restrictive, but it adds branching to every V2 speculator. Capping `max_model_len` at config time is simple and safe. The tradeoff is that such deployments can't serve sequences longer than the drafter's limit even without speculation, and the warning says so. The check lives in `VllmConfig` because only it knows which model runner is in use. `SpeculativeConfig.draft_shares_target_positions()` holds the same condition as the override, so the two stay in sync.
- An explicit speculative `max_model_len` below the target's also caps the target, unless the drafter's cache is raised; V2 ignores that setting in that case.
