# [Bugfix][XPU] Prefer W8A8 FP8 linear kernel on XPUs with native FP8

[Upstream PR](https://github.com/vllm-project/vllm/pull/63792) · state: closed · merged: False

## Original PR description

## Purpose

On XPU, FP8 linear layers always run weight-only (W8A16), even on GPUs that can run FP8 GEMMs natively.

`_POSSIBLE_FP8_KERNELS[PlatformEnum.XPU]` lists `XPUW8A16FP8LinearKernel` before `XPUW8A8FP8LinearKernel`, and W8A16 accepts every FP8 layer. W8A16 converts the FP8 weights to 16-bit and runs a 16-bit GEMM. That is the right default for XPUs without FP8 matrix engines. Xe3p GPUs (Crescent Island, Nova Lake-P) have native FP8, so there the W8A8 kernel (`_xpu_C::fp8_gemm`, FP8 activations and weights) is faster. Today the only way to get it is `VLLM_DISABLED_KERNELS=XPUW8A16FP8LinearKernel`.

This PR makes `init_fp8_linear_kernel` prefer the native kernel. When all of these hold:
- the platform is XPU,
- `--linear-backend` is `auto`,
- the device is Xe3p, detected with `torch.ops._xpu_C.is_xe3p_arch()` from vllm-xpu-kernels,

it passes `force_kernel=XPUW8A8FP8LinearKernel`, the same hook ROCm uses for its batch-invariant FP8 kernel. If W8A8 cannot implement the layer, or is disabled with `VLLM_DISABLED_KERNELS`, selection falls back to the usual list order, which starts with W8A16.

Not affected:
- XPUs without native FP8 (e.g. Arc B-series): `is_xe3p_arch()` is false, so W8A16 stays the default.
- vllm-xpu-kernels builds without `is_xe3p_arch` (the op was added in vllm-project/vllm-xpu-kernels@f9f74e4, after the pinned 0.1.15.4): treated as no native FP8, so behaviour is unchanged until the pin moves.
- Other platforms: the change is in the XPU kernel only.
- Layers W8A8 cannot implement still get W8A16.
- An explicit `--linear-backend` (e.g. `xpu_woq`) is respected.

## Test Plan

On an Xe3p GPU, serve an FP8 online-quantized model with plain `--quantization fp8` and no `VLLM_DISABLED_KERNELS`, then check which kernel the log reports as selected. Run once with `is_xe3p_arch` available and once without it, to cover older vllm-xpu-kernels builds.

The test machine had a pre-release software stack, so the patch was applied to vLLM v0.32.0. The hunk is identical on `main`. Its vllm-xpu-kernels build exposes `_xpu_C::is_cri` but not `is_xe3p_arch`; for the first run, a test-only `torch.library` shim registered `is_xe3p_arch` as `is_cri`. Both ops were added together upstream.

```bash
vllm serve nvidia/Cosmos3-Nano --omni --quantization fp8 --cache-backend sea_cache --no-guardrails
```

## Test Result

Kernel selection, `init_fp8_linear_kernel` for a per-tensor and a per-token dynamic FP8 layer (both gave the same result):

| `is_xe3p_arch` | `--linear-backend` | `VLLM_DISABLED_KERNELS` | Selected |
|---|---|---|---|
| true | `auto` | - | `XPUW8A8FP8LinearKernel` |
| true | `xpu_woq` | - | `XPUW8A16FP8LinearKernel` |
| true | `auto` | `XPUW8A8FP8LinearKernel` | `XPUW8A16FP8LinearKernel` |
| missing | `auto` | - | `XPUW8A16FP8LinearKernel` (unchanged) |

End to end, the Cosmos3-Nano server log reports `Selected XPUW8A8FP8LinearKernel for Fp8PerTensorOnlineLinearMethod` with `is_xe3p_arch` available, and `XPUW8A16FP8LinearKernel` without it. The text-to-video outputs are bit-identical to the existing paths: with this PR they match a run with `VLLM_DISABLED_KERNELS=XPUW8A16FP8LinearKernel`, and without the op they match an unpatched run.

The generated images and videos were valid in both runs. With W8A8, video generation got noticeably faster; text-to-image was unchanged, because that request is host-bound. I left out absolute numbers because the hardware is pre-release.

I haven't run the XPU CI kernel tests on Arc B-series. On those GPUs, the new branch is skipped because `is_xe3p_arch()` is false.
