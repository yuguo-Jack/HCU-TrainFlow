# [ROCm][Perf][GLM-5.3-Flash] Shard the kpool indexer prefill rows across TP on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/60601) · state: open · merged: False

## Original PR description

## Overview

Enables #54951's TP row sharding of the long-context indexer prefill on ROCm, for GLM-5.3-Flash's kpool indexer (`vllm/models/glm5next/amd/sparse_indexer.py`). 

## Claims

- On MI325X at TP4, GLM-5.3-Flash at 131K in / 1K out:
  - output throughput +2.6% and TPOT +3.1% (7/7 concurrencies);
  - TTFT +2.0% (6/7);
  - gsm8k unchanged.
- It removes replicated indexer work: about 58 ms of a ~663 ms 16K-token prefill chunk on every rank (`fp8_mqa_logits` ~29 ms + `top_k_per_row_prefill` ~28 ms). Three quarters of that is redundant at TP4.
- No change on CUDA, where `MIN_TP_SHARD_ROWS_PER_RANK` stays 16384, or for ROCm indexers that don't read `row_shard_sizes`.

## Validation

**Unit tests:** `pytest tests/v1/attention/test_indexer_tp_row_shard.py` on this branch, in `vllm/vllm-openai-rocm:nightly-43b4aaea3e40e20ef53ce2bfecfa1b72060bf2b5` on MI325X: 50 passed.

pre-commit (ruff and the local hooks) is clean. mypy reports one error in `indexer.py` (`round_down` on an ndarray), which `main` has too.

**End to end:**
- Setup: MI325X (gfx942), TP4, GLM-5.3-Flash FP8.
- Benchmark: `vllm bench serve` random 131072 in / 1024 out, concurrency 2-16 × 20 prompts.
- Arms: same image and config, differing only in the threshold (2048 vs 16384 rows per rank, which means sharded vs replicated).

| | sharded vs replicated |
|---|---|
| Output throughput | +2.57% (7/7 rows) |
| TPOT | +3.09% (7/7) |
| TTFT | +1.99% (6/7) |
| gsm8k strict, 5-shot (stderr ±0.004) | 0.9757 → 0.9742 |

I also smoke-tested with MTP (k=5): long prompts shard and complete without errors.

These runs applied this change to #54951's head as of Sep 25. The rebase since then picked up #54951's own cleanups and the short-prefill fix below, which doesn't affect 131K prompts.

## Details

- **`vllm/models/glm5next/amd/sparse_indexer.py`** mirrors #54951's NVIDIA kpool change:
  - clip each chunk to the rank's shard after the unconditional K gather;
  - score only those rows;
  - rebuild the top-k buffer with one `all_gatherv` per layer, including the `index_kpool - 1` tail entries the expansion appends.

  Short prefills that skip MQA scoring also skip the exchange, as in #54951's eeb7409926.
- **`vllm/v1/attention/backends/mla/indexer.py`:** the gate admits ROCm (`is_cuda()` → `is_cuda_alike()`), and ROCm starts sharding at 2048 rows per rank. The 16384-row threshold chosen for Hopper never triggers at `max_num_batched_tokens=16384`, while on MI325X a single 16K chunk is already worth splitting.
- **`tests/v1/attention/test_indexer_tp_row_shard.py`:** the gate tests patch `is_cuda_alike`, which is what the gate now checks.
- **No new plumbing:** `all_gatherv` already exists on the CUDA-alike communicator that ROCm uses.
- **Follow-up:** exchanging the kpool ids instead of their expansion (4× fewer bytes) adds another +4.4% TTFT and +2.0% throughput on top. It's on `jin-amd/vllm:rocm/pr54951-pooled-exchange` and will be its own PR.

<summary><strong>What changed in this PR</strong></summary>

Enables TP row-sharding for replicated sparse-indexer prefill work on ROCm (notably GLM-5.3-Flash kpool), reducing redundant per-rank MQA/top-k computation by scoring per-rank contiguous row shards and exchanging only the final indices.

**Changes:**
- Add a cost-balanced TP row-sharding planner (`balanced_prefill_row_shard`) and a support gate that now admits CUDA-alike platforms (incl. ROCm), with a lower sharding threshold on ROCm.
- Plumb `row_shard_sizes` through prefill metadata and use it to shard scoring + `all_gatherv`-exchange top-k buffers (including kpool expansion tail) in GLM5Next AMD/NVIDIA indexers and the generic sparse indexer layer.
- Add unit tests covering correctness of TP row sharding (row independence + gate behavior + balancing logic).
