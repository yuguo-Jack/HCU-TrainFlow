# [AuxOutput] Keep routed experts while a KV cache tier caches their blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/58328) · state: open · merged: False

## Original PR description

## Purpose

Keep routed-expert (R3) outputs while a KV cache tier (the GPU prefix cache, or CPU offload) can return a hit on their block, and cap prefix hits at blocks whose outputs exist. This replaces the earlier store cache-policy approach of this PR, which is reverted.

### Problems on `main`

- **CPU offload crash.** R3 with `OffloadingConnector` crashes the worker when the whole prompt is a CPU hit:

  ```
  auxiliary output capture is not contiguous: expected=1184, actual=1199
  ```

  `_update_waiting_for_remote_kvs` resumes at `num_tokens - 1`, which is not on a block boundary.
- **Stale hits.** The SHM store evicts by LRU independently of the KV cache, so a KV hit can outlive the routed experts of its blocks.
- **Store overflow.** The store raises `cannot retain` once referenced objects exceed `max_bytes`. #62044 reports this at full KV.

### Design

All changes live in the existing aux output classes.

- **Retaining** (`AuxOutputSchedulerConnector`). When a request finishes or is preempted, the connector retains its GPU-cached full blocks (the full-attention group, else group 0). Their hashes go out as `retained_block_hashes` in the same metadata that releases the request's own references; the worker retains before it releases.
- **Releasing** (`released_block_hashes`), driven by `update_kv_cache_events`.
  - CPU residency is counted from the connector's CPU `BlockStored`/`BlockRemoved` events. A block the CPU tier evicts, and no other tier holds, is released at once.
  - A block the GPU evicts with no tier reporting it may still sit in a KV connector without residency events (`MooncakeStoreConnector`, LMCache). It stays retained in an LRU of up to `num_blocks` such blocks; the oldest is released beyond that. The scheduler therefore knows exactly which outputs exist, for every KV connector.
  - GPU evictions are processed in the same step's metadata, before the worker stores new outputs.
  - Residency is looked up in the tracked group's own block pool, which HiSparse replaces with a host pool.
  - Blocks of a pending async load stay retained until the request is scheduled.
- **Hit cap.** `max_cache_hit(request)` is the longest prefix of full blocks that are GPU-cached or retained, at most `num_tokens - 1`. The scheduler only calls the connector's `cap_local_hit` and `cap_external_hit`.
  - A local hit past it is dropped and recomputed. With a full-attention group this never happens: every GPU-cached block is retained or held by a running request. Only partial-block hits (`--prefix-match-unit` finer than the block size) and sparse sliding-window hits reach it; a Mamba or sliding-window hit cannot be cut at another boundary. `KVCacheManager` is unchanged.
  - External hits are trimmed to it, so a block whose outputs left the LRU is recomputed instead of failing the read. The total is aligned down to the block size, where capture resumes; this fixes the crash above.
- **Shorter external prefixes.** A trimmed external hit reaches the KV connector as a smaller `num_external_tokens` in `update_state_after_alloc`. Not every connector can load that, so `KVConnectorBase_V1.external_load_alignment` says what it can:
  - an int: the unit a shorter prefix must end on, and the scheduler aligns the trim down to it;
  - `None` (the default, so out-of-tree connectors are safe): only the whole hit, and a trimmed hit becomes 0 and is recomputed. Mamba models also trim to 0.

  | Connector | `external_load_alignment` | Change |
  |---|---|---|
  | `OffloadingConnector`, `SimpleCPUOffloadConnector` | 1 | none: they already load a shorter prefix |
  | `MooncakeStoreConnector` | 1 | asserted the whole hit; now loads the accepted prefix and drops the tail key boundary |
  | `LMCacheConnectorV1` | LMCache chunk size | asserted the whole hit; the wrapper now shortens the load spec. LMCache retrieves whole chunks, so an unaligned prefix fails to load |
  | in-tree `LMCacheMPConnector` | chunk size | loads the accepted chunks and frees the lookup locks of the rest |
  | `MultiConnector` | least common multiple of its connectors, `None` if any is `None` | |
  | others, including the `lmcache` package's `LMCacheMPConnector` | `None` | |
- **Store growth** (`BlockObjectStore`, SHM). When new objects do not fit after evicting every unreferenced one, the arena grows instead of raising, and logs:

  ```
  Auxiliary output store grows past max_bytes to <bytes> bytes: running requests and KV cache tiers reference all <n> objects.
  ```

  Referenced objects belong to running requests, to blocks a KV cache tier holds, or to the LRU, so growth is bounded by the KV tiers. R3 rows are about 0.4% of a token's KV on Qwen3-30B-A3B. The default `max_bytes` is now twice the KV cache: one half for blocks the GPU caches, one half for the LRU. GPU-only serving does not grow it.
- **Resets.**
  - A prefix-cache reset releases all retained blocks, even if the KV connector reset fails. The worker releases them in the old generation before switching.
  - `reset_connector_cache` drops CPU residency and releases every retained block no GPU block holds, including the LRU.
- **KV events.** With aux outputs enabled, KV cache events are turned on with `publisher="null"` if they were off; nothing is published. `self_describing_kv_events` also defaults to true in `kv_connector_extra_config` (and in each `MultiConnector` child's), so each CPU chunk names every block it holds.

### Limitations

- **KV connectors without residency events.** `OffloadingConnector` and `SimpleCPUOffloadConnector` (CPU mode) report CPU `BlockStored`/`BlockRemoved`, so their blocks stay retained while offloaded. `MooncakeStoreConnector`, `LMCacheConnectorV1`, `LMCacheMPConnector` and `SimpleCPUOffloadConnector` in disk mode do not: their external hits reach back only as far as the LRU, and older blocks are recomputed. The LRU holds as many blocks as the GPU KV cache.
- **Trims to a connector's unit.** With LMCache a trimmed hit loses up to one chunk (256 tokens by default) more than with a block-granular connector. A connector without `external_load_alignment` recomputes a trimmed hit in full.
- **In-tree `LMCacheMPConnector` is not covered end to end.** vLLM prefers the MP connector shipped by `lmcache` (0.4.7 and later); it does not declare a load unit, so its trimmed hits are recomputed (tested below). The in-tree fallback is used only with `lmcache` 0.4.4, which fails at startup with this vLLM (`expected storage_offset 0`) with or without this change.
- **Mooncake object store.** `MooncakeBlockObjectStore` (#57968) ignores retain/release and has a deployment-sized pool.
- **Partial-block hits** (`--prefix-match-unit` finer than the block size) are recomputed: a local one in full, a CPU one on Mamba hybrids too. Default block hashing has no partial blocks.

New tests:

- retaining and releasing across the GPU and CPU tiers;
- pending-load protection;
- releases on connector reset and on prefix-cache reset;
- the worker retaining in the sending generation;
- store growth with a warning;
- local and external hit capping, including to a connector's load unit and to 0 for whole-hit-only connectors;
- the LRU of evicted blocks no tier reports;
- `MooncakeStoreScheduler` and the `LMCacheConnectorV1` wrapper loading a shorter accepted prefix;
- `MultiConnector` combining its connectors' load units;
- evicted blocks released in the evicting step through a real scheduler.
