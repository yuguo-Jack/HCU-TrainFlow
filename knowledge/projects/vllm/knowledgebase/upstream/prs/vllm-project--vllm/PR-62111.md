# [Bugfix] Fix multi-layer MTP module selection for Qwen3.5 and Qwen3-Next

[Upstream PR](https://github.com/vllm-project/vllm/pull/62111) · state: open · merged: False

## Original PR description

## Overview

Multi-layer MTP (Multi-Token Prediction) speculative decoding for Qwen3.5 and Qwen3-Next silently uses only MTP module 0 for every draft step, instead of the distinct module trained for each step. This PR threads `spec_step_idx` through the drafter forward and fixes the multi-module routing so each draft step uses its own MTP module.

## Claims

- **Bug fix:** multi-layer MTP for Qwen3.5 (`Qwen3_5MTP` / `Qwen3_5MoeMTP`) and Qwen3-Next (`Qwen3NextMTP`) now selects `self.layers[spec_step_idx % num_mtp_layers]` per step instead of always module 0.
- **No output-correctness impact:** speculative decoding is lossless (the target verifies every drafted token). The bug only lowers the draft acceptance rate, and hence it directly affects **spec decoding speedup**, for multi-layer MTP checkpoints.
- **Latent today, future-proofing:** all currently published Qwen3.5 checkpoints ship `mtp_num_hidden_layers: 1`, so behavior is unchanged today; the fix activates correctly the moment a multi-layer MTP checkpoint ships.

## Validation

**Unit tests** (`tests/test_config.py`, no model weights — committed CI coverage):
- `use_multi_module_mtp()` detects `mtp_num_hidden_layers` both top-level and under a nested `text_config` (the multimodal Qwen3.5 layout).
- Outer `forward` threads `spec_step_idx` into the inner predictor (parametrized over Qwen3.5 and Qwen3-Next).
- Inner predictor selects a distinct module per draft step (`spec_step_idx % num_mtp_layers`): steps 0..3 → modules `[0, 1, 0, 1]`.

**Manual end-to-end** on ROCm (MI300-class GPU, `num_speculative_tokens=2`, `enforce_eager`). No public Qwen MTP checkpoint ships >1 MTP layer, so I built a synthetic 2-layer checkpoint from the real `Qwen/Qwen3.5-2B` by duplicating module 0 → module 1 (with a small perturbation so the modules differ), and compared the speculator actually selected before vs. after the fix on the **same** checkpoint:

| Checkpoint | Code | Speculator selected | mean accept len |
|---|---|---|---|
| synthetic 2-layer | before | `MTPSpeculator` (single-module) | 2.530 |
| synthetic 2-layer | after | `MultiModuleMTPSpeculator` | 2.543 |
| real `Qwen/Qwen3.5-2B` (1-layer) | before | `MTPSpeculator` | 2.515 |
| real `Qwen/Qwen3.5-2B` (1-layer) | after | `MTPSpeculator` | 2.557 |

The decisive signal is the **speculator class**: before the fix a 2-layer checkpoint silently falls back to the single-module speculator (reusing module 0 every step); after, it routes to `MultiModuleMTPSpeculator` and engages module 1 on step 2. Acceptance numbers are close only because the synthetic module 1 is a near-copy of module 0; a genuinely-trained module 1 would diverge. On the real 1-layer checkpoint the fix is a no-op (2.515 → 2.557 is within run-to-run noise), confirming no regression. The synthetic checkpoint is a multi-GB derived artifact, so it is not committed.

## Details

Three issues combined:

1. **Dropped `spec_step_idx`:** the outer `Qwen3_5MTP.forward` / `Qwen3NextMTP.forward` did not pass `spec_step_idx` to the inner multi-token predictor, so the per-step module selection always resolved to module 0.
2. **Routing field name:** `SpeculativeConfig.use_multi_module_mtp()` only recognized DeepSeek-style `num_nextn_predict_layers`. Qwen3.5 declares its module count via `mtp_num_hidden_layers`, so multi-layer Qwen3.5 MTP never routed to `MultiModuleMTPSpeculator` (the only speculator that varies `spec_step_idx`).
3. **Nested `text_config`:** on multimodal Qwen3.5 configs `mtp_num_hidden_layers` lives under the nested `text_config`, so the routing check falls back to `get_hf_text_config()`.

All three are required for multi-layer MTP to behave correctly.
