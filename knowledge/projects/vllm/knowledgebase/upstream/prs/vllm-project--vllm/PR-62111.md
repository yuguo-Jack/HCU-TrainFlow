# [Bugfix] Fix multi-layer MTP module selection for Qwen3.5 and Qwen3-Next

[Upstream PR](https://github.com/vllm-project/vllm/pull/62111) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Qwen3.5-family MTP drafters (`Qwen3_5MTP`, `Qwen3_5MoeMTP`; also used by Qwen3.6 / Qwen3.8 and Intern-S2 checkpoints) and Qwen3-Next (`Qwen3NextMTP`) ran **MTP module 0 for every draft step** when a checkpoint has more than one MTP module, instead of the module trained for that step. This PR makes each draft step use its own module on Model Runner V2, including in the default compiled configuration.

Not a duplicate: #35607 proposed only the `forward` part of this (closed unmerged in Mar 2026, as published Qwen3.5 checkpoints ship one MTP layer); no open PR addresses it.

## Claims

- **Bug fix (MRV2):** multi-module Qwen3.5 / Qwen3-Next drafting now uses module `i` for draft step `i`, in eager, default compiled (`VLLM_COMPILE` + CUDA graphs), and breakable-CUDA-graph modes. Previously every step reused module 0.
- **No behavior change for shipped checkpoints:** all published Qwen3.5 / 3.6 / 3.8 / Intern-S2 checkpoints have one MTP layer; their drafter keeps its current execution mode (compiled or CUDA graphs), and outputs and acceptance are identical to `main` (below). No published checkpoint of any MTP family changes routing.
- **Lossless:** the target verifies every draft token; this affects draft acceptance (speedup), not output.

## Validation

## Details

**Root causes (all needed for multi-module drafting to work):**
1. `Qwen3_5MTP.forward` / `Qwen3NextMTP.forward` did not pass `spec_step_idx` to the inner predictor, which selects `self.layers[spec_step_idx % num_mtp_layers]`. Their `**kwargs` silently accepted and dropped it; it is now a named parameter and `**kwargs` is removed (no caller passes anything else).
2. `use_multi_module_mtp()` only read `num_nextn_predict_layers`, but Qwen3.5 declares `mtp_num_hidden_layers` (nested in `text_config` for multimodal checkpoints), so it never routed to `MultiModuleMTPSpeculator`, the only speculator that varies `spec_step_idx`. `SpeculativeConfig.num_mtp_modules()` now reads the `n_predict` that `hf_config_override` already normalizes for every MTP family, so new multi-layer models use the multi-module speculator by default. `MultiModuleMTPSpeculator.capture()` uses the same count (it read `num_nextn_predict_layers` unconditionally, which Qwen3.5 configs lack).
3. **Compiled drafters reused module 0.** vLLM compiles the drafter once with all Dynamo guards dropped, so the Python-indexed module chosen on the first trace was replayed for every step. The other multi-module drafters (Inkling, Step-3.5, MiMo-V2, Qwen4Exp, MiniMax-M3) are not compiled, which is why this did not surface. The Qwen3.5 / Qwen3-Next drafter is now compiled only when it runs single-module (`support_torch_compile(enable_if=...)`); multi-module drafters run eager with full CUDA graphs over the draft loop, like the other multi-module drafters. Since #51012 the CUDA Qwen3.5 drafter is no longer compiled, so this gate now applies to Qwen3-Next and the ROCm Qwen3.5 drafter.
4. With multi-module routing, the local-argmax path calls `get_top_tokens(hidden_states, spec_step_idx=...)`; `Qwen3_5MTP` now accepts and ignores it, since the MTP modules share one `lm_head` (as in `compute_logits`).

**Scope:** Qwen3-Next already routed correctly via `num_nextn_predict_layers`; it needed only (1) and (3). Drafts with MTP index sharing (`index_share_for_mtp_iteration`, from the checkpoint or the override) and MiniMax-M3 stay on the single-module speculator, with TODOs: index sharing is only implemented there, and MiniMax-M3 is not yet verified with the multi-module speculator.

**Files:** since #51012, CUDA loads `Qwen3_5MTP` from `vllm/models/qwen3_5/nvidia/mtp.py`, while ROCm and Intern-S2 (`InternS2MobiusMTP`) still use `vllm/model_executor/models/qwen3_5_mtp.py`. Fixes (1) and (4) are applied to both files.



**Limitations:** Model Runner V1 never passes `spec_step_idx` for any MTP family (only Step-3.5's proposer does), so multi-module drafting there still uses module 0; MRV1 is deprecated and this PR targets MRV2. Multi-module Qwen drafters trade the compiled drafter for eager + full CUDA graphs; no shipped checkpoint takes that path.

Thanks @larryli2-amd. Addressed this in the latest commit. 

You're right about the mechanism: `use_local_argmax_reduction` validation only checks `hasattr(model, "get_top_tokens")`, which passes because `Qwen3_5MTP` inherits `LocalArgmaxMixin.get_top_tokens`. But that method takes only `hidden_states`, while `MultiModuleMTPSpeculator` calls it as `get_top_tokens(hidden_states, spec_step_idx=...)` — so it raised `TypeError` at runtime once this PR routes multi-layer Qwen3.5 to the multi-module path.

I went with the override option (as you also suggested) rather than rejecting the config, since the local-argmax path is otherwise valid for Qwen3.5. Added to `Qwen3_5MTP` (inherited by `Qwen3_5MoeMTP`):

```python
def get_top_tokens(  # type: ignore[override]
    self,
    hidden_states: torch.Tensor,
    spec_step_idx: int = 0,
) -> torch.Tensor:
    # Single shared lm_head across MTP modules, so spec_step_idx is ignored
    # (mirrors compute_logits). The multi-module speculator passes it, but
    # the inherited LocalArgmaxMixin.get_top_tokens does not accept it.
    return super().get_top_tokens(hidden_states)
```

Ignoring `spec_step_idx` is correct (not just a shim): Qwen3.5 uses a single shared `lm_head` across MTP modules, which is also why `compute_logits` ignores it. 
Also, added a parametrized regression test (`test_qwen3_5_mtp_get_top_tokens_accepts_spec_step_idx`, covering `Qwen3_5MTP` and `Qwen3_5MoeMTP`) that calls `get_top_tokens` with a non-zero `spec_step_idx`; it fails on `main` with the exact `TypeError` and passes with the override.

## 1. [High] `use_multi_module_mtp()` should read the already-normalized `n_predict` instead of re-implementing per-family field lookup

`SpeculativeConfig.hf_config_override` (≈L640–1000) already normalizes every MTP family's module count into `hf_config.n_predict` — including Qwen3.5 (`mtp_num_hidden_layers`, top-level or via `get_hf_text_config`, L915–935), Intern-S2 / Mobius (L936–958), Qwen4Exp (L845–861), Qwen3-Next, DeepSeek, etc. The new `_num_mtp_layers` helper duplicates that logic with a different, ad-hoc precedence (`num_nextn_predict_layers` → `mtp_num_hidden_layers` → text config → 1) and will drift again next time a new family adds a new field name (exactly the bug being fixed).

Suggested:
```python
n_predict = getattr(self.draft_model_config.hf_config, "n_predict", None) or 1
return min(n_predict, self.num_speculative_tokens) > 1
```
(Verify `n_predict` is always set for `method == "mtp"` draft configs; if not, fall back to `num_nextn_predict_layers` as before.) This also resolves review thread #2/#4 (the "why default 1 / add a warning" questions): a single source of truth makes the default explicit, and a `logger.warning_once` could be emitted in `hf_config_override` when `n_predict` is `None` for an MTP model. The default-1 originates from the LongCat-Flash / Step-3.5 PRs (#23991, #33523) per `git log -S`; worth citing in reply to thread #2.
