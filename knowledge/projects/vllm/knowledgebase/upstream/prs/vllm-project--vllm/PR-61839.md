# [ROCm][DSv4] EPLB for the AITER MegaMoE backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61839) · state: open · merged: False

## Original PR description



## Overview

DeepSeek-V4's AITER MegaMoE backend (`--moe-backend aiter_mega_moe`) rejected `--enable-eplb`. This PR hooks it into vLLM's EPLB, the same way the DeepGEMM MegaMoE path does. On DeepSeek-V4-Pro, ATOM's EPLB for the same kernels cuts the long-context prefill step by 14.6%. The last three commits are generic EPLB changes that MegaMoE EPLB needs on ROCm; each can be split out.

## Claims

- `--enable-eplb` works with `--moe-backend aiter_mega_moe`. It rebalances by permutation only (`num_redundant_experts=0`), as ATOM does.
- `EPLBConfig.max_rebalances` (new; default 0 = no limit, unchanged behaviour): stop after N rebalance points and keep the placement.
- ROCm: `torch_nccl` expert-weight transfers no longer hang RCCL.
- ROCm: the "skip rearrange" check no longer vetoes every MegaMoE rebalance.

Usage (sync EPLB; `torch_nccl` requires `use_async: false`):

```bash
vllm serve deepseek-ai/DeepSeek-V4-Pro --data-parallel-size 8 --enable-expert-parallel \
  --moe-backend aiter_mega_moe --all2all-backend mori_high_throughput \
  --enable-eplb --eplb-config '{"use_async": false, "communicator": "torch_nccl", "max_rebalances": 2}'
```

## Validation

The numbers below come from a lab branch: vLLM 77154ca6 plus this change, alongside unrelated local patches. Setup: DeepSeek-V4-Pro on 8x MI355X, TP1 x DP8 attention, EP8 AITER MegaMoE, DSpark draft. EPLB ran with window 100 / interval 200 and at most 2 rebalances. The lab counted only engine steps that contain a prefill; that counting is not part of this PR, and a larger window and interval in engine steps give a similar cadence.

Prefill probe: each of the 8 ranks prefills 8,107 new tokens at ~108K context next to 16 decoding requests:

| | EPLB off | EPLB on |
| --- | --- | --- |
| prefill step (ms, median of 6 rounds) | 1102 | 944 (-14.3%) |
| MegaMoE combine wait per step (ms, mean over ranks; worst rank) | 167 (180) | 36 (55) |
| MegaMoE stage1 / stage2 per step (ms) | 165 / 231 | 164 / 225 |
| decode step at 16 req/rank (ms) | 55.6 | 55.5 - 56.3 |

ATOM gets -14.6% on the same probe. The gain is the combine wait: the expert GEMM time per rank stays the same, but the busiest rank no longer holds every rank back.

- gsm8k (lm-eval, real speculative decoding) with EPLB on: 0.9719 / 0.9727 (two runs).
- A rebalance moves ~2.5k of each rank's 2.9k expert slots across 61 layers. The first one took 5.2-5.7 s in the probe and load runs, ~2.3 s of it RCCL connection setup, and up to ~12 s under heavier live traffic. Later ones take ~2.5 s. ATOM's migration takes 5.4 s.
- Stress test under load: 34 forced full-permutation rebalances while serving 32 concurrent requests, 0 request errors, correct greedy answers before and after.
- Unit tests (CPU): `tests/distributed/test_eplb_utils.py` (ring pairing, cap, per-layer imbalance) and `tests/models/test_deepseek_v4_aiter_mega_moe.py -m cpu_test` (weight views, remap before the runtime choice, MixtureOfExperts registration; importing it needs a ROCm build).

E2e and validation on this upstream branch are still to be added.

## Details

**MegaMoE EPLB (commit 1).**
- The AMD `DeepseekV4ForCausalLM` implements `MixtureOfExperts` over the MegaMoE layers only; other AMD MoE paths keep `num_moe_layers == 0`.
- `DeepseekV4AiterMegaMoEExperts.get_expert_weights()` returns per-expert row views of the finalized w13 / w2 weights and scales. The a16w4 shuffles are within-expert, so EPLB rewrites rows in place. MegaMoEV2 reads the weights by pointer at every launch, so CUDA graphs stay valid.
- `forward()` maps logical to physical ids with `eplb_map_to_physical_and_record` (load recording included) before the runtime choice. The fixed-slot decode runtime (#61262) and the prefill runtime therefore both dispatch physical ids. Per-expert slot capacity does not depend on placement.
- Redundant experts are rejected.
- The DSpark draft is not registered: its MoE only sees decode-sized batches, and it keeps its own static placement.

**`max_rebalances` (commit 2).** Every rebalance point blocks all EP ranks. A skipped point still pays an all-reduce, a host sync and the policy, and an applied one moves weights for seconds. When the placement only needs to adapt once (ATOM uses `ATOM_EPLB_MAX_REBALANCES=2` here), the cap stops further points; the remap stays and load recording stops.

**ROCm ring P2P order (commit 3), root cause.**
- `rearrange_expert_weights_inplace` posts a layer's sends and receives as one `batch_isend_irecv`: about 340 ops per rank here.
- With RCCL 2.27.7 on MI355X this deadlocks on some transfer plans. The trigger is a rank that sends to many peers while it also exchanges with one peer in both directions.
- It is deterministic for a given plan. A torch-only 8-GPU reproducer hangs on the same seeded plans every time, with one batch per layer and also with ATOM-style 32-expert chunks. In serving it killed the engine at the execute timeout during the first rebalance.
- The fix: on ROCm, `TorchDistNcclEplbCommunicator` runs the layer as ring batches. Batch d holds the sends to rank + d and the receives from rank - d, in the same d order on every rank, so a send and its receive meet in the same batch with one peer per direction.
- Results: 4k seeded plans in the reproducer and 4k plans through `rearrange_expert_weights_inplace` (random and default-policy plans), no hang, 0 misplaced rows, ~47 ms per layer.
- A no-op `EplbCommunicator.prepare_transfer()` hook lets the communicator create its group's communicator with a collective first, because a ring batch need not involve every rank. Other platforms keep one batch per layer.

**Per-layer skip check (commit 4).** The ROCm-only check skips a placement unless the rank-load imbalance improves by 5%. It summed each rank's load over all layers before taking max/mean, so per-layer skews on different ranks cancelled out. MegaMoE's per-layer max/mean of ~1.77 (to ~1.12 after rebalancing) read as 1.063 -> 1.118, and every rebalance was skipped. Each MoE layer waits for its busiest rank, so the check now uses the sum over layers of max over the sum over layers of mean, the same quantity `log_balancedness` reports.

**Not included / follow-ups.**
- This PR keeps the profile-time dummy rearrangement. With `torch_nccl` it all-gathers one layer of expert weights, and its load all-reduce creates the EP group's RCCL communicator, which MoRI otherwise never uses. Together that costs ~12 GiB of KV cache per rank here: 95.7 -> 83.3 GiB with EPLB on, vs 93.8 GiB in the lab with that step skipped. This can follow separately.
- `pynccl` transfers are not ring-ordered.
- No redundant experts.

AI assistance (Claude) was used to write this change, its tests and this description; the measurements come from the author's runs.
