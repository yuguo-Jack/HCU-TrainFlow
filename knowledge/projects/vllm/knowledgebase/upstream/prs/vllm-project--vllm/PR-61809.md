# [Bugfix] Validate draft-token capacity in forward benchmark

[Upstream PR](https://github.com/vllm-project/vllm/pull/61809) · state: closed · merged: True

## Original PR description

## Overview

Validate draft-token capacity in `vllm bench forward` before preparing a case's inputs. Fixes #61766: a verify case requiring three draft tokens currently reaches CUDA execution even when the runner has zero draft capacity.

## Claims

- Reject cases whose draft count exceeds the runner's resolved `num_speculative_steps`, with a case-specific `ValueError` and a `--speculative-config` hint.
- Preserve execution for ordinary decode and verify cases with sufficient capacity.
- Cover missing and insufficient capacity in the existing benchmark test suite, and document the requirement in the microbenchmark skill.

## Validation

| Check | Before | After |
| --- | --- | --- |
| Selected benchmark regression tests | 2 failed, 2 passed | 4 passed, 1 deselected |
| L4: `verify=2*4@64:3`, no speculative config | CUDA illegal memory access | Expected `ValueError`, no illegal memory access |
| L4: `decode=2*1@64` | Passed | Passed |
| L4: same verify, configured draft capacity 3 | Passed | Passed |

The patched GPU controls use the same publicly exported random Qwen3-0.6B checkpoint. Both successful cases have finite, deterministic outputs and graph-versus-eager relative RMS difference 0. These are correctness smoke checks, not model-quality or performance measurements.

The existing model-dependent pytest end-to-end case was deselected; three separate benchmark CLI runs provided GPU coverage. New tests live in `tests/benchmarks/test_forward_cli.py`, already included in the Buildkite benchmarks CLI job.

## Details

The benchmark builds scheduler inputs directly. Without speculative configuration, the observed runner has `num_speculative_steps=0` and a draft-token buffer of shape `[4, 0]`, yet the verify case schedules three draft tokens per request. The missing consistency check lets this invalid combination enter GPU input preparation. CUDA errors are asynchronous; no exact faulting kernel is claimed.

The guard runs at the start of `run_case`, before batch construction and input preparation, using resolved runner capacity rather than requiring a particular CLI configuration. Engine initialization still precedes the check. This is benchmark configuration validation; it does not change a CUDA kernel or repair computation under a valid configuration.

Duplicate checks: read #61766 and searched open PRs for the issue number and `bench forward`. No overlapping fix was found. #61692 adds profiling, not draft-capacity validation. The three affected files are unchanged on the latest upstream main checked before submission.

AI assistance was used for investigation, implementation, reproduction scripts, and executing the reported checks. The human submitter reviewed the proposed change in the associated discussion and authorized submission; the test executions reported here were performed by the agent.
