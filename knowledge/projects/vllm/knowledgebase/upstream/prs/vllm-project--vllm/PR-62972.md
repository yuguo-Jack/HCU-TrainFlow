# [Kernel][MoE] Add the NIXL EP v2
  elastic EP all2all backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/62972) · state: open · merged: False

## Original PR description

## Overview

Adds **NIXL EP v2** as the MoE all2all backend `nixl_ep_v2`. **One kernel pair** serves NVLink and RDMA, and NIXL
lets peers join and leave at runtime, so it supports **elastic EP without a restart**.

Across NVLink domains it is **up to 59% faster** than `nixl_ep` and **10-16% faster** than `deepep_v2`. Resizes have
**29-55% less downtime** than with `nixl_ep`.

**Status:** draft, work in progress; the NIXL change it builds on is also a draft, and both may still change.

**Depends on:** NIXL [`6485f7a5`](https://github.com/lishapira/nixl/commit/6485f7a5f5fb896c6bc5d02bc2a975746739c66d), which adds the kernels as `nixl.runtime.ep` (not in `ai-dynamo/nixl` yet).

**Related backends:**

- `deepep_v2` ([#41183](https://github.com/vllm-project/vllm/pull/41183)): no in-place resize; elastic EP tears down and rebuilds its buffer and CUDA graphs.
- `nixl_ep` ([#35627](https://github.com/vllm-project/vllm/pull/35627)): keeps its graphs, but has only low-latency kernels.

## Claims

- **Unified NVLink + RDMA kernels:** one dispatch/combine pair covers NVLink and RDMA in the same call.
- **NIXL transport:** peers connect and disconnect at runtime, with no fixed world or global communicator to rebuild.
- **Elastic EP:** resizes without a restart.
- **CUDA graphs:** remaining ranks keep their buffer and graphs across a resize.
- **Precisions:** BF16, block FP8, NVFP4.
- **Performance:**
  - vs `nixl_ep`: up to 14% higher throughput on one NVLink domain, up to 59% across domains.
  - vs `deepep_v2`: 10-16% faster across domains.
  - Elastic EP: 29-55% less downtime than `nixl_ep`.

## Performance

### End-to-end serving

DeepSeek-V4-Pro-NVFP4 on GB200, 1K input / 1K output tokens, disaggregated prefill and decode. Throughput is aggregate
output tokens/s across all decode GPUs.
DeepEPv2 and NIXL EPv2 both run on 26 SMs, for a fair comparison; DeepEPv2's SM count comes from a `deepep_v2`
setting that is not part of this PR.

## Details

### Why

- `deepep_v2`: no in-place resize; elastic EP tears down and rebuilds its buffer and CUDA graphs.
- `nixl_ep`: keeps its graphs across a resize, but has only low-latency kernels.
- `nixl_ep_v2`: keeps its graphs, and has NIXL EP v2's kernels for both decode and prefill.
  - Throughput vs `nixl_ep`: up to 14% higher on one NVLink domain, up to 59% higher across domains.
  - Across domains, 10-16% faster than `deepep_v2`.
  - Elastic EP: 29-55% less downtime per resize than `nixl_ep`.

<details>
<summary>Design</summary>

- **Manager:** one buffer per process, sized for the max EP size and shared by all MoE layers; no NCCL bootstrap.
- **Prepare-finalize:** a new class with standard activation format, async support and a reduced combine output.
- **Receive layouts:** exact in eager mode; padded or expanded under CUDA graphs.
- **Wire precision:** BF16 → BF16; block FP8 → FP8; NVFP4 → BF16 (NVFP4 with opt-in dispatch).
- **Elastic EP:** new ranks connect while serving goes on; the topology commits during the pause.

</details>

<details>
<summary>Changes by area</summary>

- **Backend:** manager, prepare-finalize and Triton kernel, factory and config wiring, six env vars, an availability check;
  one-line opt-ins in shared MoE and elastic EP code.
- **Elastic EP:** buffer and graph reuse on resize; the manager raises on a size the kernels cannot run.
- **Shared code:** the FlashInfer NVFP4 top-k fix, the modular-kernel test-tool fix, the warm-up of new elastic EP
  communicators moved to the commit, with the engine paused, on every platform (as ROCm already does), and their
  peers connected before the pause, a wait for the engines a scale-down removed to exit before the next scale, expert
  maps of reused CUDA graphs kept alive, a helper that builds expert ids for the expanded receive layout.
- **Tests:** three new kernel test files; the backend's cases in the MoE layer, modular-kernel and FlashInfer tests,
  with a fake-buffer helper; tests for the NVFP4 fix, the helper, the removed-engine wait and the NCCL setting helper;
  elastic EP test; four GSM8K configs.
- **Docs:** one row in the expert parallel deployment guide.

</details>

  (branch `nixl_ep_v2`), into vLLM's environment, either:

    [`contrib/build-wheel.sh`](https://github.com/lishapira/nixl/blob/6485f7a5f5fb896c6bc5d02bc2a975746739c66d/contrib/build-wheel.sh)

### Usage

```bash
vllm serve <model> --data-parallel-size <N> --enable-expert-parallel --all2all-backend nixl_ep_v2
```

- `VLLM_NIXL_EP_V2_DOMAIN_SIZE` (default 0: NIXL finds the domains; under elastic EP, one domain): GPUs per NVLink
  domain.
  Set it when a job spans more than one domain; every multi-domain result here set it.
- `VLLM_NIXL_EP_V2_NUM_SMS` (default 0: the buffer's launch grid): SMs per dispatch and combine.
- `VLLM_NIXL_EP_V2_EXPAND` (default 0): under CUDA graphs, the expanded receive layout instead of the padded one.
- `VLLM_NIXL_EP_V2_NVFP4_DISPATCH` (default 0): opt-in NVFP4 dispatch.
- `VLLM_NIXL_EP_V2_PREFER_OVERLAP` (default 1): buffer flag `prefer_overlap_with_compute`.
- `VLLM_NIXL_EP_V2_ALLOW_MULTIPLE_REDUCTION` (default 1): buffer flag `allow_multiple_reduction`.
- Elastic EP: add `--enable-elastic-ep --elastic-ep-max-dp-size <N> --enable-eplb --data-parallel-backend ray`.
