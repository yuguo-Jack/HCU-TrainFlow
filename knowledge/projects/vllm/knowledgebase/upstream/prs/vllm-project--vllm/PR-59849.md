# [Perf][DSv4.1] Register CPU-offloaded Engram tables at their exact size

[Upstream PR](https://github.com/vllm-project/vllm/pull/59849) · state: open · merged: False

## Original PR description



## Overview

Same fix as #59848, for DSv4.1. Default `cpu_offload` Engram tables use `pin_memory=True`, which rounds each table up to a power of two. Register them at exact size through the existing THP helper, without huge pages. cc @Juntian777: if you can run your #59327 lookup bench on GB200, it would show whether the GB10 speedup carries over; it doesn't block this PR.

## Claims

- TP2 per-rank table: 66 → 47.2 GiB host memory.
- GB10 lookup kernel: ~1.8× faster unsorted, 7–21% faster with #59327's sort.
- RTX PRO 6000 (PCIe): same memory saving, lookup speed unchanged.

## Validation

GB10, Engram lookup kernel, TP4 per-rank table, 32K tokens:

| memory | host | unsorted | sorted |
| --- | --- | --- | --- |
| `pin_memory` (before) | 33.1 GiB | 41.4 ms | 10.9 ms |
| exact `cudaHostAlloc` | 24.9 GiB | 41.4 ms | 10.9 ms |
| registered (this PR) | 24.3 GiB | 22.7 ms | 10.2 ms |

Exact size gives the memory saving; on GB10 the registered memory type gives the speed. These are 4 KiB pages, not THP.

RTX PRO 6000 Blackwell (PCIe Gen5 x16), same bench, TP4 per-rank table, 32K tokens:

| memory | host | unsorted | sorted |
| --- | --- | --- | --- |
| `pin_memory` (before) | 33.1 GiB | 14.9 ms | 11.2 ms |
| exact `cudaHostAlloc` | 24.7 GiB | 14.9 ms | 11.2 ms |
| registered (this PR) | 24.7 GiB | 14.9 ms | 11.2 ms |

Over PCIe the memory type makes no difference to speed, so the speedup is specific to GB10's coherent C2C link. GB200 has the same kind of link but isn't measured.

`pytest tests/kernels/test_engram.py tests/distributed/test_engram_dp_shard.py`: 116 passed on GB10. After rebasing onto #63009, 129 passed and 3 skipped (multi-GPU) on one RTX PRO 6000; the same files on main fail only the new small-page case.

Still needed before un-drafting: an E2E `cpu_offload` run.

## Details

- `_allocate_huge_page_storage(n)` → `_allocate_registered_storage(n, huge_pages)`, called once. The THP path and the sort are unchanged. A failed registration falls back to `pin_memory=True`.
- CUDA only; ROCm is unchanged. #63009 already allocates ROCm tables at their exact size, via huge pages.
- Why not just `use_thp`: it already registers at exact size, but it is opt-in and skips the sort, so default users were left with the rounding.
- Why not `PYTORCH_ALLOC_CONF=pinned_max_round_threshold_mb`: it gets the same exact size, but only for users who know to set it, and on GB10 it misses the faster lookup (the `cudaHostAlloc` rows above). Over PCIe it is equivalent.
