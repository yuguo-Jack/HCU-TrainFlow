# [Bugfix][Parser] GLM-4.7: stray arg tags must not leak into tool-call argument keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/54971) · state: open · merged: False

## Overview

The GLM-4.7 parser (`--tool-call-parser glm47`) can put stray `arg_key` tags into an argument **key**.

- Seen in production: `{"path</arg_key>": "/Users/user/Desktop/project"}`.
- The client rejects the call: `must have required property 'path'`.

Sibling fix for the Poolside parser: #56093.

## Claims

- Repeated or stray `<arg_key>` / `</arg_key>` tags no longer end up in the key.
- Both paths are fixed: complete calls (`_ARG_RE`) and streaming (`_PARTIAL_ARG_RE`).
- Well-formed input parses the same as before.
- No model eval: only malformed markup is affected.

## Details

**Root cause**

- The key was matched with `(?P<key>.*?)</arg_key>`.
- `.*?` is lazy, but it can still run past the first `</arg_key>`.
- It does that when the text right after it is not `<arg_value>`, e.g. a duplicated tag.
- Example: `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` → key `path</arg_key>`.

**Fix**

```python
_ARG_KEY = r"<arg_key>(?P<key>[^<]*+(?:<(?!/?arg_key>)[^<]*+)*+)(?:</arg_key>\s*)+"
```

- The key can contain `<`, but never an `arg_key` tag, so it stops at the first `</arg_key>`.
- `(?:</arg_key>\s*)+` skips duplicated closing tags.
- Both `_ARG_RE` and `_PARTIAL_ARG_RE` are built from `_ARG_KEY`.
- Possessive quantifiers avoid backtracking on long unterminated buffers during streaming. Same approach as #54678.

**Overlapping PRs**

- #61253 (merged): moved parsing into `_glm47_parse_args` and added the arg-value extender. It still uses `_ARG_RE` / `_PARTIAL_ARG_RE`. Its author also tested it with these regexes applied.
- #47190, #49249, #60842, #58418: other malformed-markup cases in the same file. No overlap in behavior; may conflict textually.

**Bug confirmed on base:** both stray-tag shapes reproduce the reported leak exactly. `_ARG_KEY` replaced `.*?` (which backtracks across its own `</arg_key>` delimiter to reach a following `<arg_value>`) with a possessive non-`<`-crossing key group:
- `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` → base produced key `path</arg_key>` (the exact production failure in the PR body); head → `{"path": "/tmp/x"}`.
- `<arg_key><arg_key>path</arg_key><arg_value>...` → base produced key `<arg_key>path`; head correct.

**Regression-proven:** all 5 new tests FAIL on base (4 param converter tests + the streaming e2e test), PASS on head. Full file: 20/20 pass on head vs 5 failed/15 passed on base (teardown `RuntimeError: Cannot access accelerator device` errors are the known CUDA-less noise, identical on both).

**No regressions on adjacent shapes** — probed base-vs-head over 22 inputs: well-formed single/multi-arg, `\s*` whitespace variants, keys containing `<` (e.g. `a<b`), arg_key-like markup inside values, empty keys/values, newlines, trailing partial values, junk prefix. Byte-identical output everywhere except the corrupt-key cases. One deliberate delta on the malformed two-keys-one-value input: base merged `a</arg_key><arg_key>b` into one corrupt key; head drops the value-less `a` and keeps `{"b": "1"}` — cleaner fail behavior, not a regression.

**Non-blocking note:** `vllm/tool_parsers/poolside_v1_tool_parser.py:82` uses the same `<arg_key>(.*?)</arg_key>\s*<arg_value>(.*?)</arg_value>` shape with stdlib `re` — same leak exists there (`findall` on `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` returns `[('path</arg_key>', '/tmp/x')]`). If poolside models can emit stray arg tags too, the same `[^<]*+(?:<(?!/?arg_key>)[^<]*+)*+` key pattern would apply. Out of scope for this PR, just flagging the sibling.

Nice work — clear root-cause writeup, the `_ARG_KEY` comment explains the backtracking subtlety precisely, and the streaming e2e test is exactly the right level to prove the engine path.
