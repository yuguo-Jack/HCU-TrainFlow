# [Bugfix][Parser] GLM-4.7: stray arg tags must not leak into tool-call argument keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/54971) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `--tool-call-parser glm47`, a duplicated `<arg_key>` or `</arg_key>` tag in the model output ends up inside the argument **name**. Seen in production as `{"path</arg_key>": "/Users/user/Desktop/project"}`, which the client rejects with `must have required property 'path'`. The key pattern is now bounded so it cannot cross an `arg_key` tag, in both the complete-call and the streaming regex.

Sibling fix for the Poolside parser: #56093.

## Claims

- Stray or repeated `arg_key` tags no longer reach the key, for complete calls (`_ARG_RE`) and streaming (`_PARTIAL_ARG_RE`).
- Well-formed tool calls parse exactly as before.
- No model eval: only the parsing of malformed markup changes.

## Details

**Root cause.** Both regexes matched the key with `(?P<key>.*?)</arg_key>\s*<arg_value>`. The lazy `.*?` still runs past the first `</arg_key>` when the next text is not `<arg_value>`, so a duplicated closing tag gets absorbed into the key. With a duplicated opening tag, the match simply starts at the first `<arg_key>`.

| Arguments in the model output | `main` | This PR |
| --- | --- | --- |
| `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` | `{"path</arg_key>": "/tmp/x"}` | `{"path": "/tmp/x"}` |
| `<arg_key><arg_key>path</arg_key><arg_value>/tmp/x</arg_value>` | `{"<arg_key>path": "/tmp/x"}` | `{"path": "/tmp/x"}` |

**Fix.** Both regexes now share one key pattern:

```python
_ARG_KEY = r"<arg_key>(?P<key>[^<]*+(?:<(?!/?arg_key>)[^<]*+)*+)(?:</arg_key>\s*)+"
```

- The key may contain `<`, but not an `arg_key` tag, so it stops at the first `</arg_key>`. Then `(?:</arg_key>\s*)+` consumes any duplicated closing tags.
- Possessive quantifiers avoid backtracking on long unterminated buffers during streaming. #54678 takes the same approach.
- One other malformed shape changes on purpose. Two keys followed by one value (`<arg_key>a</arg_key><arg_key>b</arg_key><arg_value>1</arg_value>`) used to produce a single corrupt key, `a</arg_key><arg_key>b`. It now produces `{"b": "1"}`.

**Overlapping PRs.**
- #61253 (merged) moved parsing into `_glm47_parse_args`, which still uses `_ARG_RE` / `_PARTIAL_ARG_RE`. Its author also tested it with these patterns applied.
- #47190, #49249, #58418 and #60842 handle other malformed-markup cases in the same file. None of them changes the key pattern, but a textual conflict is possible.
