# [Bugfix][Attention] Pin host tensors passed to the FlashInfer SM90 sparse MLA plan

[Upstream PR](https://github.com/vllm-project/vllm/pull/61399) · state: closed · merged: False

## Original PR description



## Overview

`FLASHINFER_MLA_SPARSE_SM90` passes pageable CPU tensors (qo/kv indptr, KV lengths) to `BatchMLAPagedAttentionWrapper.plan()`. The wrapper copies them to the GPU with `non_blocking=True`, so `VLLM_GPU_SYNC_CHECK=error` rejects the copy as an implicit sync. On GLM-5.3-Flash on H200 the engine dies on its first request. This PR stages the tensors in pinned memory, the same pattern #54660 applied to the FlashInfer backend.

## Claims

- GLM-5.3-Flash (H200, SM90 sparse MLA) now runs under `VLLM_GPU_SYNC_CHECK=error`. Before this change it failed on the first request.
- Every host tensor `plan()` copies to the device is now pinned. The reused staging buffers stay unpinned, as in `flashinfer.py`.
- No performance claim: DEP8 decode throughput is neutral within run-to-run noise (table below).

## Details

`_SM90State._plan` fills reusable CPU buffers (`_qo_cpu`, `_kv_cpu`, `_lens_cpu`) in place and passes them to the wrapper. With `use_cuda_graph=True`, the wrapper's `_stage_metadata` copies them into its reserved device buffers with `non_blocking=True`. From pageable memory CUDA may synchronize to stage that copy, which is what the sync check flags.

The fix passes a `.pin_memory()` copy of each buffer instead of making the buffers themselves pinned. PyTorch's caching host allocator keeps a pinned block alive until the async copy that reads it completes, so the next plan cannot overwrite in-flight data. Pinning the reused buffers directly would need explicit events to avoid that race. This mirrors `vllm/v1/attention/backends/flashinfer.py` since #54660.

Not a duplicate: no open PR touches this backend's plan staging. #58684 removed this plan's D2H sync; this change covers the H2D side.

Out of scope: `plan()` itself costs 4–6.5 ms per call, measured without the profiler. Most of that is FlashInfer's Python workload validation (`_fa_plan_work_count`), which runs over all `max_num_batched_tokens` rows, twice per plan. That belongs in a FlashInfer change.
