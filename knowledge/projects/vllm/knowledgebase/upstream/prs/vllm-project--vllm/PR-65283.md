# [Core] Priority scheduling: hold lower-priority prefill for first tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/65283) · state: open · merged: False

## Original PR description

## Overview

Builds on #65282: the first commit here is #65282's, and this PR's change is the second. With priority scheduling, a high-priority request's first tokens share every step with lower-priority prefill chunks, which make those steps long. This PR adds `--priority-prefill-budget-cap` (off by default): until a higher-priority request has its first `--priority-prefill-budget-cap-tokens` output tokens (16 by default), lower-priority prefills are held back.

## Claims

- With the cap on, prefills of a strictly lower priority, running or waiting, sit out the steps in which a higher-priority request awaits its first `--priority-prefill-budget-cap-tokens` output tokens, with or without async scheduling: from the step in which it fits (a free running slot and KV cache room for its whole sequence) or, with a running slot free, its KV connector load is done.
- A request that is not admitted, or a KV load still in flight, holds prefill back for at most that many steps, and a lower-priority request that holds KV blocks sits out only while a request of its priority or a lower one runs, which preemption takes first.
- Decodes are never held, nor is a request with one token left to compute, nor a prefill midway through an encoder input while a request it is held for needs encoder cache space.
- Off by default, and off it changes no schedule: 2,496 traced configurations schedule as #65282 does, step for step.
- Counters, `vllm:priority_prefill_held_steps` and `vllm:priority_prefill_held_tokens`, registered only with the cap on.
- On an RTX 5060 Ti, behind three lower-priority prefills, a priority 0 chat turn's 16th token comes after 560 ms instead of 1,374 ms on v0.32.0 (1,242 ms with #65282 alone).

## Details

- **Which requests hold prefill back.** The running requests with fewer than `--priority-prefill-budget-cap-tokens` output tokens, counting a step in flight as one token, since its draft tokens may be rejected. While a running slot is free, also a request whose KV load is done and, for its first `--priority-prefill-budget-cap-tokens` steps, a load in flight. And the highest-priority waiting request that is ready to run, if it fits as #65282 counts the room, for at most that many steps in which the waiting loop does not admit it. Only strictly lower priorities are held back, so at one priority nothing changes.
- **How.** A lower-priority running prefill gets no tokens in the step, and vLLM skips it as any request with none. A lower-priority waiting request is not admitted, but only after its prefix cache and KV connector lookups, so a KV load it needs starts meanwhile. A request with one token left samples like a decode and is never held. No room is made for a waiting request the cap holds back.
- **Requests that hold KV blocks.** The waiting loop drains them first, so one of a lower priority is skipped rather than waited on. It sits out only while a request of its priority or a lower one runs: while it waits, preemption cannot reach its blocks, and the higher-priority request could otherwise preempt only itself for them.
- **Encoder input.** A prefill midway through an encoder input whose output is cached goes on while a request it is held for needs encoder cache space: the cache frees that output only as the prefill consumes it.
- **KV loads.** With async KV loads from a CPU tier, a turn whose load was done still waited for budget the running loop left over, and agent prefill chunks left none for up to 4 s. So a done load holds prefill back, and a load in flight does for its first steps, since a load's completion is seen only at a step boundary.
- **Bounds.** Without a free running slot, neither a waiting request nor a KV load holds anything back, since neither could be admitted. A waiting request that fits but is not admitted, for example while its KV connector lookup is pending, holds for at most `--priority-prefill-budget-cap-tokens` steps.
- **Costs and limitations.** Lower-priority prefill makes no progress while higher-priority requests' first tokens are due back to back. On the A100 with 256 requests in flight (48 prompt and 64 output tokens, 10% at priority 0; an earlier revision), both changes take the priority 0 TTFT p99 from 574 to 177 ms and the priority 2 TTFT p99 from 1,086 to 7,971 ms.
- **Related.** Stage 2 of the RFC #62532 proposes holding running prefill back for a finished KV load under FCFS, which this PR does for higher priorities. #65339 reserves step budget for waiting requests with cached KV, and #64927 holds waiting requests back to batch their prefills; neither holds lower-priority prefill back for a request's first tokens.
- **The window.** `--priority-prefill-budget-cap-tokens` should cover the first output the application acts on, such as a voice agent's first sentence: 15 tokens at the median and 39 at most for this agent, which is why 48 tokens did better than 16. Open question: should the default stay at 16?

### [P1] Allow the encoder-cache owner to progress when the preferred request is blocked

With `--priority-prefill-budget-cap` enabled and chunked multimodal inputs allowed, this hold can create a circular wait even when KV capacity and a running slot are available:

1. A lower-priority running prefill A has encoded an image that fills the encoder cache, but its decoder has consumed only part of that image's placeholder range. The cache entry is still referenced and cannot be evicted.
2. A higher-priority waiting request B needs a different image. `_first_tokens_priority()` checks the free running slot and KV room, then this branch holds A.
3. B gets zero schedulable tokens from `_try_schedule_encoder_inputs()` because its image cannot fit in the encoder cache.
4. `_free_encoder_inputs()` can release A's entry only after A advances past the remaining image placeholders, which this hold prevents. The next scheduling step repeats the same state.

For example, `max_num_batched_tokens=8`, `max_num_seqs=2`, and `disable_chunked_mm_input=False` legitimately allow a 16-embedding image: `compute_mm_encoder_budget()` raises the encoder compute/cache budgets to 16. Start A at 8/16 image placeholders consumed, then enqueue B with a distinct 16-embedding image and higher priority. This does not require proactive KV preemption or a KV connector. The bounded hold for in-flight KV loads does not apply to this ordinary waiting request.

Without cancellation or another external state change, neither request can make further progress. Could the hold eligibility account for encoder-cache dependencies, or let the cache-owning prefill continue when the preferred request is blocked on that resource? A regression with these two distinct images and a one-image encoder cache would cover the case.

**Validation:** an isolated probe executing the exact hold condition/priority/encoder methods with the real `EncoderCacheManager` and encoder-budget calculation admits B at step 3 with the cap disabled; with it enabled, all 40 iterations retain the same referenced cache entry and schedule zero tokens for B. Requests and KV-capacity leaves are minimal fixtures. The persistent stall is supported by the code cycle above; this was not a full `Scheduler.schedule()`, model, or GPU-service reproduction.

**[P1] Prevent completed KV imports from indefinitely holding a prefill needed for admission**

At `4960575fe21f8d05aca7ca0e6e0b13b994802e68`, `_first_tokens_holders()` includes requests from `finished_recving_kv_req_ids` without an admission check or hold expiry. This can create a circular wait when an earlier KV-holding request cannot allocate its remaining blocks.

A deterministic CPU Scheduler reproducer uses priority scheduling, a 16-token budget, 15 KV blocks, three running slots, and the default 16-token hold window:

- A (priority 0, 96-token prompt) and R (priority 1, 65-token prompt) each import 64 cached tokens.
- C (priority 2, 96-token prompt) is running and has computed 80 tokens when both imports complete.
- A finalizes its import but needs two additional blocks with only one free. Its allocation fails and breaks the waiting scan before R is visited.
- R's retained completion ID continues to suppress C, even though C could finish its remaining prefill using the available block and then release its KV allocation.

**Steps 23–150 schedule no tokens.** The in-flight-load hold map is empty, and A's waiting hold counter stays at 1. Neither bounded hold mechanism expires R's completed-import hold.

The same workload completes on main, #65282, and #65283 with the cap disabled. The failure reproduces on the exact #65283 head and its unchanged stack applied to current main, including with hold windows of 1, 4, 16, and 64.

Could the completed-import hold be constrained so it cannot suppress the running work required to unblock admission? A deterministic regression covering an allocation-blocked holding-queue head followed by a completed import would prevent this liveness failure from returning.
