# [Bugfix] Propagate retryable multimodal cache errors

[Upstream PR](https://github.com/vllm-project/vllm/pull/61645) · state: closed · merged: False

## Original PR description



## Overview

This further improves #58975. That PR made multimodal cache-miss failures safe
for pooling; this PR completes the retryable-error contract for generation and
non-pooling serving paths, including background Responses requests.

## Claims

- Preserve structured retryable multimodal cache errors from EngineCore output
  processing through generation outputs and serving entrypoints.
- Return HTTP 503 `ServiceUnavailableError` where clients can resubmit retained
  inputs, while preserving ordinary internal failures as HTTP 500.
- Clean up all sibling requests when an `n > 1` child fails with a parent-scoped
  cache miss.
- Preserve retryable failures in Beam Search, batch Chat, token-in/token-out,
  speech-to-text, Realtime, and label-reading paths.
- Mark failed background Responses requests durably, terminate background
  streams, and retain `response.error` details for later retrieval.

## Details

EngineCore reports a multimodal cache miss as `FinishReason.ERROR` with
`mm_cache_miss_hashes`. After the bounded AsyncLLM retry is exhausted, the
generation path previously lost or downgraded that structured failure in
several output and serving layers. Parent sampling could also leave sibling
requests alive, while background Responses producers could exit without a
durable terminal state or retrievable error details.

This change converts the terminal output into a structured `RequestError`,
preserves it while outputs are aggregated, performs parent-scoped cleanup, and
maps `retryable=True` to the shared 503 serving error. Responses stores now use
a durable producer-finished signal and persist an OpenAI-compatible
`ResponseError` on failed background responses.

No additional automatic frontend replay is introduced: once the bounded
engine retry is exhausted, callers with replayable source input receive a
retryable failure and can resubmit the complete request.

### Why this is not duplicate work

The predecessor #58975 fixes the pooling-specific crash and propagation path;
this PR extends the contract to generation and non-pooling services.

- #38190 and #40418 cover foreground Responses `response.failed` events.
- #49721 covers background stream termination when a producer exits.
- #47184 covers successful Responses serialization with `error: null`.

None of them provides the EngineCore-to-frontend retryable error propagation,
parent sampling cleanup, cross-entrypoint 503 mapping, and background
non-streaming error retrieval covered here.

> From a first glance this is quite intrusive, perhaps it would be better to just automatically retry internally? cc @ywang96 @Isotr0py

@DarkLight1337 
Thanks for the suggestion. Before opening this PR, I had already implemented and evaluated an internal automatic-retry approach. I have now published it as draft PR [#61656](https://github.com/vllm-project/vllm/pull/61656) for comparison.
A P0 cache hit may produce an EngineInput that no longer contains the full multimodal tensor, so the server cannot simply resubmit it after P1 reports a miss. The internal-retry implementation therefore needs each serving frontend to retain its source input and provide a reconstruction factory that re-renders it with skip_mm_cache=True.
This increases the total change from 22 files (+789/-74) in this PR to 31 files (+1639/-165) in the internal-retry draft. After comparing the two approaches, we selected external retry for this PR because it has a smaller scope and clearer ownership: invalidate P0, return a structured retryable error, and let the caller resubmit the complete input.
The internal approach also still requires the same terminal fallback for non-replayable streaming inputs, requests that have already emitted output, and a second cache miss.
If you and the other maintainers prefer transparent internal retry, I am happy to refine and rebase #61656, complete its end-to-end validation, and adapt this PR accordingly while retaining the terminal retryable-error fallback. I would appreciate your guidance on which direction you prefer.
