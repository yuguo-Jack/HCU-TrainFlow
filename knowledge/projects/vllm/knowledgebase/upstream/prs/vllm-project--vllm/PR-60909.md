# [Bugfix] Pin long-lived host buffers at their exact size

[Upstream PR](https://github.com/vllm-project/vllm/pull/60909) · state: open · merged: False

## Original PR description

## Overview

torch's caching host allocator, which `pin_memory()` and `pin_memory=True` go through, rounds every block up to the next power of two. That's fine for short-lived staging buffers. But for buffers that live as long as the process the cache doesn't buy anything, and a buffer just over a power of two pins up to twice its size in page-locked memory the OS can't reclaim.

This adds a small `empty_pinned()` helper (`vllm/utils/pinned_memory.py`). It allocates exactly the requested size with `cudaHostAlloc` / `hipHostMalloc` through the existing `CudaRTLibrary` wrapper and frees it once the last view is gone. I've used it in the two GiB-sized places that don't already have an open PR:

- The private per-tensor CPU KV offload tier. CUDA normally uses one exactly registered region (#50094), but ROCm has been on the private tensors since #57160, so the rounding from #53042 is back there. Fixes #53042 on ROCm.
- CPU-resident weights, which is what the prefetch weight offloader leaves on the host (CUDA and ROCm). Two places allocate those: the offloader's own copy, and `device_loading_context`, which moves a CPU weight to the GPU for `process_weights_after_loading` and then copies it back into a new pinned tensor. The second copy is the one that stays, so both have to change.

XPU keeps torch's allocator.

## Claims

- The CPU KV tier on ROCm pins exactly what it asks for instead of rounding each tensor up to a power of two. In my repro that's 4.25 GiB less page-locked memory for a 4.75 GiB tier, with identical output.
- CPU-offloaded weights are pinned at their exact size too. With the prefetch offloader on Qwen3-1.7B that's 168 MiB less page-locked memory (main pins 1.25x the offloaded weights), with identical output.
- No change to what gets pinned or when, only how big the allocation is.

All 10 pass on CUDA (RTX A2000 Laptop, sm_86, torch 2.13.0+cu132). The pinned memory and KV tier tests also pass on ROCm (Radeon AI PRO R9700, gfx1201, ROCm 10.0, torch 2.13). To make sure the tests check the right thing, I ran them against the code from before this change too:

- With `empty_pinned` pinning through torch and the old `gpu_worker.py`, two fail on both platforms, as they should: the fallback test (it pins when pinning is off) and the KV tier test (the caching allocator holds 128 MiB for a 66 MiB tier).
- The `device_loading_context` test fails on main: a 33 MiB weight comes back in a 64 MiB pinned block.

The KV tier test passes `mmap_region=None`, so it takes the private path on CUDA as well. The new tests are in `tests/utils_`, `tests/v1/kv_offload` and `tests/model_executor`, which CI already runs on NVIDIA and AMD.

KV tier memory, stock `Qwen/Qwen3-8B` on vLLM v0.31.1rc0 (ROCm build), `--kv-offloading-size 4.75`, which makes 36 per-layer tensors of 141,623,296 B. Pinned is the engine process's page-locked mappings minus the same baseline without a tier (about 212 MB in both runs):

| | pinned for the tier | greedy output |
|---|---|---|
| main | 9,663,676,416 B (36 x 256 MiB, 1.82x the 5,100,273,664 B asked) | `05304724...` |
| this PR | 5,098,438,656 B (36 x 141,623,296 B) | `05304724...` (same) |

Weight offload, stock `Qwen/Qwen3-1.7B` on CUDA (RTX A2000), `--offload-backend prefetch --offload-group-size 4 --offload-num-in-group 1`, so 7 of 28 layers on the host. Pinned is the server's page-locked mappings minus a run without offload. I booted main and this branch alternately, twice each, and got the same numbers both times:

| | pinned for the offloaded weights | per layer (gate_up / down / qkv / o) | c=1 decode | greedy output |
|---|---|---|---|---|
| main | 880,803,840 B | 64 / 32 / 16 / 8 MiB | 9.72 tok/s | same |
| this PR | 704,643,072 B (the 0.7047 GB the offloader reports) | 48 / 24 / 16 / 8 MiB | 9.73 tok/s | same |

I first only changed the offloader's own copy, and on ROCm with Qwen3-8B that made no difference at all (5,544,337,408 B pinned either way, 9 x (256 + 128 + 64 + 32) MiB where the weights are 192 + 96 + 48 + 32 MiB). That's how I found the `device_loading_context` copy.

## Details

Why not the alternatives:

- `cudaHostRegister` over pageable memory needs unregister bookkeeping, and registering one big region is what #57160 moved ROCm away from (`cudaHostRegister failed` at TP8 with a 500 GiB tier).
- torch's `pinned_max_round_threshold_mb` turns the rounding off, but on torch 2.13 it can hand an exact-size cached block to a larger request and overflow it (pytorch/pytorch#192722, fixed on torch main but not in a release yet). It's also process-wide.
- `get_accelerator_view_from_cpu_tensor`'s unpinned branch (what #56413 relies on) returns a device view, and these two sites need host tensors.

Trade-offs: one `cudaHostAlloc` per buffer at startup instead of a cached block, so allocation is a bit slower, but it only happens once. torch doesn't track blocks it didn't allocate across `non_blocking` copies, so the copy stays async but torch won't keep the block alive for it. Every buffer here lives as long as its worker, so that can't free memory under a copy.

Other open PRs on the same rounding, each at a different site and not touched here: UVA weight offload #56413 / #58185, the Qwen4Exp PLE table #59848, DSv4.1 Engram tables #59849, the sleep-mode CPU backup #60003, and the XPU KV tier #51956. #57506 changes `CPUOffloadingWorker.shutdown` in the same file, so one of us will need a small rebase, but the changes don't overlap.

V1's `CpuGpuBuffer` and MRV2's `UvaBuffer` also pin through torch, but they're KiB to MiB, so I left them out to keep core components untouched. Happy to do them in a follow-up with the same helper if that's wanted.

AI assistance (Claude) was used to write the code, run the tests and measurements, and draft this description. I reviewed the change and the results before posting.

- lobo235 · comment · 2026-10-21T17:41:35Z · [source](https://github.com/vllm-project/vllm/pull/60909#issuecomment-6322552070)

Thanks, one helper for all of these sounds right to me.

On the failure behavior: I'd keep raising as the default. At the sites here, a failed `cudaHostAlloc` almost always means page-locked memory has run out. Falling back to `pin_memory=True` asks torch's caching allocator for the same bytes rounded up to the next power of two, so it either fails too or pins up to 2x what was asked, which is the problem this PR fixes. Silently pinning twice the memory seems worse to me than a clear error that names the size.

Your tables are a different case, because registration can fail for reasons that have nothing to do with how much memory is free (#57160 hit `cudaHostRegister failed` at TP8). So I'm happy to add an opt-in, e.g. `empty_pinned(..., fallback=True)`, that logs a warning with the requested size and falls back to `pin_memory=True`. Your call sites would pass it, and the decision would live in one place. If that works for you I'll add it here, or you can add it when you switch over.

Both options are in now, and I rebased on main.

`register=True` page-locks a page-aligned allocation with `cudaHostRegister` instead of calling `cudaHostAlloc`, and `fallback=True` falls back to torch's pinned allocator with a warning naming the requested size. Both default to off, so nothing changes for the call sites here and your two can switch over and pass what they need.

One thing worth passing on, since it cost me a round. My first cut backed the registered range with an anonymous `mmap`, and torch reported `is_pinned()` False for it on ROCm even though `hipHostRegister` returned success and device copies worked. Backing it with an ordinary allocation instead reports True; both are page-aligned, so the mapping was the only difference. torch picks the async copy path off `is_pinned()`, so if your helper registers a fresh mapping it's worth a look on your side.

Checked on a gfx1201 box: both paths pin exactly the requested size, stay out of torch's caching host allocator, round-trip to the device, and release when the last view goes, so a range can be registered again. No C2C link here, so I can't say anything useful about your GB10 numbers.
