# [ROCm][Perf] Fuse the DeepSeek-V4 MXFP4 indexer K writer into one kernel (gfx950)

[Upstream PR](https://github.com/vllm-project/vllm/pull/56834) · state: open · merged: False

## Original PR description

## Summary

On ROCm, merged #60834 writes the DeepSeek-V4 MXFP4 indexer K cache in two launches: a Triton pooling kernel into a bf16 scratch buffer, then aiter's `k_norm_rope_mxfp4_cache`. This PR writes the same cache with the existing fused compress + RMSNorm + RoPE + MXFP4 Triton kernel in one launch, adding a ROCm branch that reproduces aiter's rounding, scale and `cache_format()` page order.

- The written pages are **byte-identical** to #60834's, so #60834's scorer, accuracy and defaults are unchanged. Still opt-in via `--attention-config '{"indexer_kv_dtype":"mxfp4"}'`; gfx950 only, as before.
- Removes the pooling kernel and its bf16 scratch buffer (3 files, +179/−245).
- Not a duplicate of #60834: it only replaces #60834's K writer. Earlier FlyDSL scorer/planner changes are dropped from this PR.
- No new dependency: uses only the aiter ops #60834 already uses (no ROCm/aiter#5518, no signature probing). No new logits or workspace allocations. `fused_indexer_q.py` is untouched, and the ROCm branch in the shared fused kernel is a compile-time flag that defaults off, so the CUDA path is unchanged.

## Results (MI355X, DeepSeek-V4-Pro)

K writer, per indexer layer per step, CUDA-graph median (same inputs, byte-identical output):

| Tokens | Two-stage (#60834) us | Fused us | Saved us | Speedup |
|---:|---:|---:|---:|---:|
| 1 (decode) | 5.54 | 4.33 | 1.21 | 1.28x |
| 64 (decode) | 5.92 | 4.59 | 1.33 | 1.29x |
| 256 (decode) | 6.96 | 5.67 | 1.29 | 1.23x |
| 1024 (prefill) | 6.57 | 5.13 | 1.44 | 1.28x |
| 8192 (prefill) | 15.32 | 13.41 | 1.91 | 1.14x |

DeepSeek-V4-Pro has 30 indexer layers, so this saves about 36–57 us per step.

End to end, TP8, 8K in / 1K out, one session per arm, same image and inputs (`83c078d9` with and without this PR):

| | #60834 two-stage | This PR | Delta |
|---|---:|---:|---:|
| C16 output tok/s | 780.03 | 780.97 | +0.12% |
| C64 output tok/s | 1518.42 | 1516.73 | −0.11% |
| GSM8K (1319, 5-shot) | 1254 (95.07%) | 1254 (95.07%) | 0 |

The K writer is a small share of a step, so end-to-end throughput is neutral within noise; the gain is one fewer launch and buffer per indexer layer, with identical cache bytes.

## Tests

- `tests/kernels/attention/test_rocm_dsv4_mxfp4_indexer.py`: 3 passed on gfx950 (pages match aiter fed by torch pooling; warmup compiles the single launched variant).
- Byte comparison against #60834's two-stage writer: 0 differing bytes in 6 cases (multi-request, 1 to 9207 tokens, unmapped slots, inputs scaled 1e-3 and 1e3).
- GPU results above were measured on main `3d23773f` / `83c078d9`. The latest merge of main only resolved an import conflict in `amd/rocm.py`; the change lines and the files the fused kernel depends on are unchanged. Ruff and mypy pass on the merged head.

- shen-shanshan · COMMENTED · 2026-11-02T10:06:57Z · [source](https://github.com/vllm-project/vllm/pull/56834#pullrequestreview-5734350084)

1. FlyDSL performance vs. Triton

Based on your benchmarks, the FlyDSL path does not outperform the existing Triton MXFP4 path, while adding ~1,830 lines of code and a new backend/dependency. I suggest separating the K-production fusion from the FlyDSL scorer and landing the fusion independently if it can directly produce the RocmPagedMxfp4CacheLayout expected by the existing Triton scorer.

2. Dependency on unreleased aiter

The FlyDSL path currently depends on unreleased aiter#5518 and uses fragile runtime detection of private aiter function signatures, so the real path cannot be exercised on current released aiter or AMD CI. Please land and pin the required aiter version first, then replace the private-signature probing with a stable API/version check; until then, I suggest keeping this PR as draft.

3. Decode logits memory is not accounted for

Decode logits are not reserved during profiling, while prefill logits bypass the workspace manager, which can cause runtime OOMs for large-context, high-concurrency workloads (e.g. up to ~512 MiB of decode logits at 1M context). Please account for decode logits in profiling and allocate both prefill/decode logits through `current_workspace_manager()`, consistent with #60834.
