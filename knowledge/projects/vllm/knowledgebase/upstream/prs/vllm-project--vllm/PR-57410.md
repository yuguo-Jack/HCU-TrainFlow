# [Transformers backend] Fuse MoE routers that score after the top-k

[Upstream PR](https://github.com/vllm-project/vllm/pull/57410) · state: closed · merged: True

## Original PR description

Three related changes to the Transformers modeling backend's MoE path, smallest
to largest in blast radius.

## 1. `MoEBlockFuser._match_router` accepts scoring on either side of the top-k

`_match_router` only looked for `softmax`/`sigmoid` *upstream* of the routing
top-k. A family of HF routers scores the selection instead:

```python
# GraniteMoeTopKRouter, AriaTextTopKRouter, JetMoE, ...
top_k_logits, top_k_index = router_logits.topk(self.top_k, dim=-1)
top_k_weights = torch.softmax(top_k_logits, dim=-1)
```

These did not match, so the whole block fell back to routing in Transformers and
smuggling `topk_ids` through a custom op. They now fuse.

The two placements are equivalent: `sigmoid` is elementwise, so scoring before or
after the selection is identical; a `softmax` over the selected logits equals a
softmax over every logit with the selected weights renormalized, since the
full-vocabulary denominator cancels.

## 2. `renormalize` is read from the router's graph, not guessed from the config

vLLM's kernel always scores all `E` experts and then selects, so its weights sum
to less than 1. Reproducing a router that softmaxes the selection alone requires
`renormalize=True`. The previous logic was `norm_topk_prob` if present, else
`top_k > 1`, which is wrong for a router that uses raw softmax-over-all weights
(`RoutingMethodType.Default`) and for `top_k=1`, where renormalizing forces the
single gate to exactly 1.0.

`_match_router` now reports what the router actually does:

- `True` if it softmaxes the selection, or divides the top-k weights by their sum
  (the walk goes through the denominator's input cone, so it absorbs the
  `+ 1e-20` spelling that 17 models in Transformers use).
- `False` if a complete trace shows it does neither.
- `None` only if tracing stopped before it could tell, in which case the previous
  config logic still applies.

This is more reliable than reading the config, not less: `norm_topk_prob` is a
Python bool that fx resolves at trace time, so the graph already reflects it.
`Qwen3MoeTopKRouter` traces to 13 nodes with `sum`/`truediv` when the flag is on
and 11 without. It also handles per-layer heterogeneity for free, since `match()`
runs per block against that block's own router instance rather than indexing a
config list by `extract_layer_index`.

## 3. `_infer_meta` no longer recurses until the stack runs out

While tracing, fx patches `nn.Module.__getattr__` to record `get_attr` nodes.
`_infer_meta`'s `get_attr` branch read the parameter's value through that patched
hook, so inferring the meta value of a `get_attr` created another `get_attr`,
which inferred its meta value, and so on until `RecursionError` — swallowed by the
`contextlib.suppress(Exception)` in `create_proxy`, leaving a complete but
massively duplicated graph.

This fires for any module reading an `nn.Parameter` directly in `forward`, which
is every HF v5 `TopKRouter` and every `RMSNorm`. Nodes in the returned graph,
before and after:

| module | before | after |
| --- | --- | --- |
| `DeepseekV3TopkRouter` | 5519 | 31 |
| `GraniteMoeTopKRouter` | 1970 | 10 |
| `Qwen3MoeTopKRouter` | 1775 | 11 |
| `Qwen3MoeRMSNorm` | 600 | 12 |
| `Qwen3MoeMLP` (only `nn.Linear` children) | 7 | 7 |

How many repeats got recorded depended on how much stack was left, so repeated
traces of the same module disagreed with each other. Matching that only walked
`all_input_nodes` upstream survived this; anything reading `users` did not, which
is what made change 1 necessary to fix first.

Meta execution now runs under `_unpatched_modules()`, restoring both `__call__`
(which the `call_module` branch already did) and `__getattr__`.

for both `softmax` and `sigmoid`, and `renormalize` resolving to `True` for
divide-by-sum, `True` for an epsilon-offset denominator, `False` for a router that
scales its weights instead, and `None` for a router whose trace is cut short.

Spot-checked against the real Transformers routers on the meta device:

| router | `_match_router` |
| --- | --- |
| `GraniteMoeTopKRouter` | `('softmax', float32, True)` |
| `AriaTextTopKRouter` | `('softmax', None, True)` |
| `Qwen3MoeTopKRouter` (`norm_topk_prob=True`) | `('softmax', None, True)` |
| `Qwen3MoeTopKRouter` (`norm_topk_prob=False`) | `('softmax', None, False)` |
| `DeepseekV3TopkRouter` | `('sigmoid', float32, True)` |
| `DeepseekV2TopkRouter` | `('softmax', float32, False)` |
| `OlmoeTopKRouter` | `('softmax', None, False)` |
| `FlexOlmoTopKRouter` | `('softmax', None, False)` |

These agree with vLLM's native implementations, which hardcode the same values:
`granitemoe.py:106` `renormalize=True`, `olmoe.py:100` `renormalize=False`,
`deepseek_v2.py:381` `renormalize=config.norm_topk_prob`.
