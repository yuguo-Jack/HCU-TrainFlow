# [KV Offload] Let unfinished requests keep the chunks they will resume from

[Upstream PR](https://github.com/vllm-project/vllm/pull/57813) · state: open · merged: False

## Original PR description

## Summary

An offloaded chunk becomes evictable the moment its store completes, so the
prefix an *unfinished* request will resume from competes with everything else on
recency alone.

That is fine for serving, where a request either runs to completion or is
preempted and recomputed. It is not fine for a colocated RL rollout: generation
is paused for a weight update, the frozen requests touch nothing, they become
the LRU victims, and on resume they pay a full re-prefill even though their
blocks were already sitting in the CPU tier.

This adds `pin_in_flight_chunks` (default **off**) to the CPU offloading
manager. When enabled it refcounts the chunks observed by unfinished requests
and prefers evicting everything else; the refcount is released at request
finalization.

```
"kv_connector_extra_config": {"pin_in_flight_chunks": true}
```

## It cannot wedge the cache

Pinning is a preference, not a guarantee. If eviction cannot be satisfied
without touching pinned chunks, the manager retries with the original protected
set, so a cache holding nothing but in-flight chunks still admits new stores.
That fallback is covered by a test.

## Relationship to #50422

#50422 (`Session Aware Eviction Policy`) adds a new `CachePolicy` that groups a
session's blocks and evicts session-worst-first, tail-first, so a shared prefix
outlives its suffix. It orders eviction *within* the cache; it does not
distinguish a request that is still running from one that finished.

This PR is orthogonal and policy-agnostic: it is a lifetime signal in the
manager (`in flight` vs `finished`) that applies to `lru`, `arc`, a custom
policy, and to SAE if it lands. The two compose — SAE would still choose which
chunk dies first among the unpinned ones.

## Not a duplicate

Also checked: #50014 (protects unread *promotions* from speculative promotion
thrash — a different lifetime, inside the tiering path), #54327 (bounded
capacity for the filesystem tier), #38984 (SLRU policy). None of them expresses
"this request has not finished yet".

## Review rounds

A later adversarial round, told about the fixes already made (distinct-key scan
budget, ARC's carried `virtual_t1_size`, the capability flag replacing
signature sniffing, the two-argument call for out-of-tree policies, and the
keyword-only constructor argument) and asked for new defects, found two gaps in
what the pin actually covers.

**Fixed: a chunk still being stored was pinned only by its writer.**
`prepare_store` sorted an offered key into "not resident" or "resident and
ready". A chunk another request is *mid-store* on is neither, so it was never
recorded, and the pin counted only the writer. Two rollouts sharing a prefix —
the case this PR exists for — therefore lost the chunk the moment the writer
finished, while the reader was still unfinished. Reproduced in review and now
covered by `test_a_chunk_still_being_stored_is_pinned_by_its_second_reader`
on both policies.

The fix keeps the pin separate from cache-access accounting: pending chunks are
pinned through a new `_pin()` helper and tracked in `state.pinned_keys`, so
they do not enter `key_groups` or the reuse counters and nothing about policy
adaptation changes.

**Known limitation: a mixed GPU/CPU prefix hit does not pin the GPU-hit part.**
When part of the prefix is already in the GPU cache, the scheduler loads only
the suffix but advances `next_stored_chunk_idx` past the whole prefix
(`offloading/scheduler.py:1134`, `:1180`), so the manager never observes the
GPU-hit chunks and their CPU copies stay ordinary eviction candidates. If the
request is later preempted and those GPU blocks are lost, CPU prefix lookup
stops at the first missing chunk (`:700`), which costs the pinned suffix too.
Closing this means changing what the scheduler reports to the manager, which is
a different component's contract; this PR keeps the manager-side change and I
would rather do that separately than widen this one.

## End-to-end measurement

Ran this on 2 GB200 nodes (slurm job 30012, `nvcr`-style nightly image, DeepSeek-V4.1-Flash) with the phases designed to isolate *only* the pinning behaviour:

- CPU offload tier sized at **512 MiB** — deliberately smaller than the ~830 MB the flood stores, so eviction is forced.
- Between the rollout and the replay, `sleep(level=1, clear_connector_cache=false)` + wake, so the GPU prefix cache is empty and the replay can only be served by the tier. (`prefix_cache_hits_total` during replay is 0 in both phases, confirming that.)
- Same server binary, same prompts, same flood; the only difference is `pin_in_flight_chunks`.

| during replay | `pin_in_flight_chunks=True` | `False` |
|---|---|---|
| replay latency | **0.151 s** | 0.303 s |
| external prefix-cache hits | **4096 / 4125** | 0 / 4125 |
| bytes loaded from tier | **17.3 MB** | 0 |
| bytes re-stored to tier | 0 | 17.3 MB |

Without pinning, the unfinished request's chunks lose to the flood on recency and are evicted, so the replay recomputes them from scratch and stores them again — the `0 → 4096` hit column is the behaviour this PR is about. With pinning the same chunks survive and are loaded back, halving replay latency here.
