# [Perf][Qwen4Exp] Route the PLE shard copy through copy_weight_

[Upstream PR](https://github.com/vllm-project/vllm/pull/65692) · state: open · merged: False

## Original PR description



## Overview

Routes the Qwen4Exp PLE shard copy through `copy_weight_`, the follow-up named in #58868. Fixes #58726.

@Willian-Zhang, as you asked in #58868.

**Not a duplicate:** no open PR mentions #58726 or changes `vllm/models/qwen4_exp/common/ple.py`. The open PLE storage PRs (#58439, #58815, #62847) avoid or stage this copy for offloaded tables; this one speeds up the existing device-resident path.

## Claims

- On a DGX Spark serving a device-resident packed-NVFP4 PLE table (`cpu_offload: false`), main `Loading weights took` falls from about 213 s to about 76 s from a cold page cache, and start to `/health` from about 320 s to about 184 s.
- Output is unchanged: logprobs and greedy text were exactly equal to the old line in every run.
- Off integrated GPUs `copy_weight_` is a plain `copy_`. A dtype-converting copy skips the touch.

## Validation

**End to end, this branch.** `vllm serve` on one GB10, `Qwen3.8-Flash-Next-NVFP4-LIL-qad5500`, local NVMe, TP=1, four boots in the order old, new, new, old. Only `ple.py` differed. The checkpoint was evicted with `posix_fadvise` before each boot, and `mincore` reported 0% resident.

**Output.** Against the code it replaces, per `tests/AGENTS.md`: 16 fixed prompts with `temperature=0` and `seed=0`. All 566 prompt-token logprobs and all 16 48-token greedy completions were exactly equal across all four boots.

**Model evaluation not run.** `tests/evals/qwen4_exp` targets Qwen3.8-Flash-Next-FP8 with `--tensor-parallel-size 4` on H200/B200, which I don't have. This change does not alter the loaded weights, as the exact comparison above and the table check below show.

**Table copy alone, this branch.** The 128 `weight` and 128 `weight_scale` shards (28.8 GB), each copied by the real `_copy_embedding_shard_` into a GPU tensor of the shard's dtype, cold cache, two runs per arm. The old line took 176.8 s and 178.9 s; `copy_weight_` took 11.4 s and 10.2 s. Both tables compared equal with `torch.equal` after every run.

**Rebase.** The boots and table copy above ran just before a final rebase onto current `main`, which changed neither `ple.py` nor `model_executor/utils.py`. The tests below were rerun after it.

## Details

**Root cause:** `_copy_embedding_shard_` copied each shard with `target.copy_(source.to(device=target.device, dtype=target.dtype))`, straight from the safetensors mmap view. For a same-dtype source, the page faults land inside the driver copy, which #58726 measured as several times slower than faulting on the CPU.

**Scope:** `load_weights` in `nvidia/ngram_embedding.py` sends split table shards through `weight_loader` to this copy. Disk-offloaded tables take `accept_checkpoint_shard` instead. The `buffer.copy_` in the same function only handles the small hash buffers, so I left it alone.

**Other backends:** `amd/ple_layer.py` reaches the same copy. `copy_weight_` only touches pages when `is_integrated_gpu` is true, and otherwise runs a plain `copy_`. I only ran this on a GB10.

**Tradeoffs:** this is load-time only, so steady-state inference and CPU/GPU synchronization are untouched. The touch reads the pages it is about to copy, and the lowest available memory during boot was 4–5 GiB in both arms.

**CI coverage:** CI has no integrated GPU, so it can't exercise the touch path here. `test_ple.py` runs on H200 and MI355 through `models_basic.yaml`, and #58868 tests the helper with the gate forced on. I added no test because this is one line of wiring. Validation outside CI is above.
