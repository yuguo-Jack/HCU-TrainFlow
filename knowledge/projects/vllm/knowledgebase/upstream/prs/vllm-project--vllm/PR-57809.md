# [Bugfix] step3 tool parser: record streamed arguments so the finalizer does not duplicate them

[Upstream PR](https://github.com/vllm-project/vllm/pull/57809) · state: open · merged: False

## Original PR description

## Summary

`DelegatingParser.finalize_generation` runs `_append_unstreamed_tool_args` on **every** finished stream (`vllm/parser/abstract_parser.py:804` → `:658`), appending `ToolParser.get_remaining_unstreamed_args()` to the last tool call.

That helper decides what is still owed by diffing `prev_tool_call_arr[-1]["arguments"]` against `streamed_args_for_tool[-1]`:

```python
args = self.prev_tool_call_arr[index].get("arguments", {})
actual = self.streamed_args_for_tool[index] if index < len(...) else ""
```

step3 emits a tool call's arguments **in full** when the call completes (`step3_tool_parser.py:236-247`), but never records them — it stores the payload under `"parameters"` and leaves `streamed_args_for_tool` empty. So the helper reports the arguments as unstreamed and they are sent a second time.

## Reproduction

Driving the real parser one character at a time over a single tool call:

```
emitted to client               : {"city": "Paris"}
streamed_args_for_tool          : []
get_remaining_unstreamed_args() : {}
client finally sees             : {"city": "Paris"}{}
```

`json.loads` on that raises `Extra data: line 1 column 18`. The trailing `{}` rather than a full duplicate is the second half of the same root cause: the base reads `"arguments"`, step3 only ever writes `"parameters"`, so the diff is against an empty dict.

## Why this is a step3 deviation, not a base-class issue

Sibling parsers keep the two lists in step — hermes does both appends together (`hermes_tool_parser.py:230-232`):

```python
if i >= len(self.prev_tool_call_arr):
    self.prev_tool_call_arr.append({})
    self.streamed_args_for_tool.append("")
```

and hermes / granite / deepseekv3 all store the payload under `"arguments"`. step3 is the only one of the three parsers that touch `prev_tool_call_arr` without ever touching `streamed_args_for_tool`.

## The change

Record the emitted JSON under both names at the moment it is sent. Nothing about **what** is streamed changes — only the bookkeeping the finalizer consults.

## Verification

- 3 new tests in `TestStep3RecordsStreamedArgs`; full file is **12 passed, 8 xfailed** (was 9 passed, 8 xfailed)
- **Rollback counter-proof**: reverting the fix while keeping the tests fails exactly those 3 and nothing else
- Full `tests/tool_parsers/` run shows **no new failures** (18 → 15 pre-existing, the 3 resolved being this PR's own counter-proof tests); 1077 passed
- `ruff check` and `ruff format --check` clean on both files

The existing `xfail_streaming` markers on this parser cover parallel calls and streaming/non-streaming reconstruction; this is a distinct single-call issue and none of those markers change.
