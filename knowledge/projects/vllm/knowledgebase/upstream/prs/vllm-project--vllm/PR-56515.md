# [Docs] Document metrics whose names are set through variables

[Upstream PR](https://github.com/vllm-project/vllm/pull/56515) · state: open · merged: False

## Original PR description

## Purpose

Closes #56514.

`generate_metrics.py` only documented a metric when its `name=` was a string literal. Two files break that:

- Since #45163, `vllm/v1/spec_decode/metrics.py` creates its counters in a loop over `counter_specs`.
- `loggers.py` sets `vllm:cache_config_info` through a local variable.

As a result, metrics were missing from https://docs.vllm.ai/en/latest/usage/metrics/. On current `main` the Speculative Decoding table lists 1 of its 7 metrics; the missing ones include `vllm:spec_decode_num_drafts` and `vllm:spec_decode_num_draft_tokens`, which `acceptance_metrics.md` tells users to compute acceptance from.

The extractor now resolves `name=` and `documentation=` when either is a local variable in the same function, assigned a string or unpacked from a literal table. Loop targets are bound only inside the `for` body or comprehension that unpacks the table, one binding per row, so a function that mixes scalar-named metrics with a table loop does not cross-emit names or types (thanks to @ANTI-Tony for catching this in review).

Two guards make the docs build fail instead of silently dropping metrics:

- a scanned file contains a literal `vllm:*` name that was not extracted;
- a `_counter_cls` / `_gauge_cls` / `_histogram_cls` call's `name=` resolves to nothing, such as an f-string.

The three `vllm:diffusion_*` counters are defined in the same file, so they now show up in the Speculative Decoding table too.

No open PR or issue covers this (searched `generate_metrics`, `spec_decode_num_drafts`, `cache_config_info`, `metrics.md spec decode`).

## Test Plan

Ran the generator outside mkdocs, with `mkdocs_gen_files` stubbed, on this branch merged with current `main`:

- ANTI-Tony · comment · 2026-09-30T12:25:46Z · [source](https://github.com/vllm-project/vllm/pull/56515#issuecomment-5911263811)

I hit the same gap independently and had landed on a very similar fix, so I read this one closely
rather than open a duplicate. The diagnosis and the `raise` guard are both nice — failing the docs
build is stronger than what I had, which only logged a warning. Two problems I can reproduce, and a
test file I'm happy to hand over.

### 1. `collect_string_bindings` loses which binding belongs to which call site

`collect_string_bindings` flattens every value a local can hold into one flat list per name, with no
record of which assignment or which loop produced it. `_extract_kwarg` then returns that whole list,
and `visit_Call` emits one metric per element. So when a single function contains both a
scalar-assigned name and a table-driven loop, *every* call site emits *every* value.

```python
# repro.py — run against this branch's generate_metrics.py
import ast, logging
from pathlib import Path

src = Path("docs/mkdocs/gen_files/generate_metrics.py").read_text()
tree = ast.parse(src)
want = {"MetricExtractor", "collect_string_bindings", "is_metric_name"}
keep = [n for n in tree.body
        if isinstance(n, (ast.ClassDef, ast.FunctionDef)) and n.name in want]
ns = {"ast": ast, "logging": logging, "Path": Path, "logger": logging.getLogger("x")}
exec(compile(ast.Module(body=keep, type_ignores=[]), "<t>", "exec"), ns)

sample = '''
class C:
    def f(self):
        name = "vllm:x"
        doc = "Doc X."
        self._gauge_cls(name=name, documentation=doc)
        specs = [("vllm:a", "Doc A."), ("vllm:b", "Doc B.")]
        cs = [self._counter_cls(name=name, documentation=doc) for name, doc in specs]
'''
e = ns["MetricExtractor"]()
e.visit(ast.parse(sample))
for m in e.metrics:
    print(m["type"], m["name"], repr(m["documentation"]))
```

Expected three metrics: `gauge vllm:x`, `counter vllm:a`, `counter vllm:b`. Actual:

```
gauge   vllm:x 'Doc X.'
gauge   vllm:a 'Doc A.'
gauge   vllm:b 'Doc B.'
counter vllm:x 'Doc X.'
counter vllm:a 'Doc A.'
counter vllm:b 'Doc B.'
```

Six rows, and three of them carry the **wrong type** — `vllm:x` is documented as a counter, `vllm:a`
and `vllm:b` as gauges. Nothing catches it: the `raise` only compares against literal names that
were *missed*, so spurious and mistyped rows pass straight through, and the docs gain confidently
wrong entries.

Your PR body's "no duplicates" is accurate today, because no file currently scanned mixes the two
patterns in one function. It becomes wrong the first time someone adds a scalar-named metric to a
function that already has a spec table — which, given `spec_decode/metrics.py` is where the diffusion
counters landed, is a plausible next edit.

Scoping the loop-target bindings to the comprehension or `for` body they belong to, instead of to the
enclosing function, fixes this. In my version I bound loop targets only while visiting that
comprehension's `elt` and restored the outer scope afterwards, which keeps each call site seeing only
the values that can actually reach it. Happy to share that shape if useful, but your structure can
get there too by keying `strings` on the binding node rather than the function.

### 2. The guard can't see names that were never literals

`is_metric_name` collects `ast.Constant` strings, so the guard asks "was every literal `vllm:*`
extracted?". That covers today's two patterns, where the names do exist as literals in a table. It
does not cover a name that is *built*:

```python
self._counter_cls(name=f"vllm:{prefix}_total", documentation="D.")
```

extracts nothing and raises nothing — there is no literal to compare against. Worth softening the
claim in the PR description ("the docs build fails instead of silently dropping metrics next time"
holds only for literal-derived names), or extending the guard to also flag `_counter_cls` /
`_gauge_cls` / `_histogram_cls` calls whose `name=` resolved to nothing. The second is cheap and
would have caught this class directly rather than by proxy.

### 3. Offer: a pytest file

This change has no automated test — the plan is three manual generator runs. I wrote
`tests/tools/test_generate_metrics.py` (7 tests) while working on my own version: literal names,
comprehension expansion, a sequence rebound in both branches of an `if`/`else`, a name assigned a
constant, unresolvable names, and a regression guard asserting the four `vllm:spec_decode_*` metrics
plus `vllm:cache_config_info` reach the generated tables. It passes on my branch and fails 5/7 with
the extractor reverted, and needs no GPU. `tests/tools/` has precedent for repo-tooling tests.

Say the word and I'll post it here for you to fold in, or open it as a follow-up against your branch
once this lands — your call, I'd rather it ride along with your fix than compete with it.
