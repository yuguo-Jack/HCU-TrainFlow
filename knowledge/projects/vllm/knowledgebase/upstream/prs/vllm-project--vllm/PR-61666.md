# [Quantization] Support compressed-tensors MXFP6 (mxfp6-pack-quantized)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61666) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Load compressed-tensors `mxfp6-pack-quantized` checkpoints: MXFP6 (E2M3) weights with dynamic MXFP8 or 16-bit activations, routed to the existing MXFP6 linear kernels (Humming on CUDA). This follows @gau-nernst's [Qwen3.8-27B-MXFP6](https://huggingface.co/gaunernst/Qwen3.8-27B-MXFP6) Quark checkpoint, which showed MXFP6 MLPs + MXFP8 elsewhere fit a 27B model on a 32 GB GPU.

Bumps `compressed-tensors` from 0.17.0 to 0.20.1, the release line that ships MXFP6 (vllm-project/compressed-tensors#941: `num_bits=6` float = E2M3, `mxfp6-pack-quantized` format, `MXFP6A8`/`MXFP6A16` presets). LLM Compressor examples are in vllm-project/llm-compressor#3286.

## Claims

- New `CompressedTensorsW6A8Mxfp6` scheme for MXFP6 weights (4 values packed in 3 bytes, uint8 E8M0 scales, group 32). It takes its activation precision from the checkpoint: dynamic MXFP8 or none; anything else raises.
- Mixed MXFP6/MXFP8/FP8 compressed-tensors checkpoints (e.g. Qwen3.8-27B) load and run with torch.compile and CUDA graphs at TP=1 and TP=2.
- The packed layout is byte-identical to the Quark MXFP6 export that the Humming path already serves.
- Existing compressed-tensors checkpoints keep working on 0.20.1. Group/dynamic `actorder` checkpoints are still rejected, now by compressed-tensors itself while parsing.

## Validation

[nm-testing/Qwen3.8-27B-MXFP6A8](https://huggingface.co/nm-testing/Qwen3.8-27B-MXFP6A8): MXFP6A8 MLP + MXFP8 attention/GDN/MTP + FP8 per-channel `lm_head`, made with LLM Compressor's `model_free_ptq` (RTN, no calibration). GSM8K on one B300, `tests/evals/gsm8k/gsm8k_eval.py`, 5-shot, temperature 0, 1319 questions, `vllm serve <model> --max-model-len 8192 --language-model-only`, on this branch:

| Model | Runs | GSM8K mean (range) | Invalid |
|---|---|---|---|
| Qwen/Qwen3.8-27B (BF16) | 2 | 0.780 (0.777-0.783) | 0.000 |
| nm-testing/Qwen3.8-27B-MXFP6A8 | 5 | 0.752 (0.742-0.760) | 0.005-0.011 |

Scores vary between runs at temperature 0, so compare means. MXFP6A8 costs about 0.03 versus BF16. The same checkpoint on this PR's previous base (Humming 0.1.16, compressed-tensors 0.20.1) scored 0.759 (0.756-0.763, 3 runs), within run-to-run spread of this branch. An earlier revision of this PR reported 0.770 from a single run, which those repeats did not reproduce.

- Kernel selection: MXFP6 linears use `HummingMxFp6LinearKernel`, MXFP8 linears use `FlashInferCutedslMxfp8LinearKernel`, at TP=1 and TP=2. TP=2 smoke: 300 GSM8K questions, 0.740, no errors.
- Layout check (previous base, packing unchanged): given the same scales, the compressed-tensors packed weights are byte-identical to `gaunernst/Qwen3.8-27B-MXFP6`, and `humming.ops.weight.unpack_weight(..., 6)` decodes the same codes.
- `pytest tests/quantization/test_compressed_tensors.py` on B300 (SM103), compressed-tensors 0.20.1: 55 of 60 pass, including `test_compressed_tensors_mxfp6` ([nm-testing/Qwen3-0.6B-MXFP6A8](https://huggingface.co/nm-testing/Qwen3-0.6B-MXFP6A8)) and `test_compressed_tensors_mxfp4`. The 5 failures also fail with compressed-tensors 0.17.0 on the same tree, so they are not from the bump: `test_compressed_tensors_w8a8_logprobs[False-10-4-...]`, `no_enforce_eager`, `w4a8_fp8`, `transforms_perplexity`, `fp8_block_enabled[auto]`. The errors seen include `Int8 not supported on SM103` and no W4A8 scheme on this architecture; these need CI to confirm on the expected hardware. `test_compressed_tensors_moe_ignore_with_model` failed once and passed on rerun.

## Details

- Mirrors `CompressedTensorsW4A4Mxfp4` (packed `weight_packed` renamed to `weight` after loading) and reuses `init_mxfp6_linear_kernel`. The packed dim shards cleanly under TP because K per partition stays a multiple of 32.
- **Limitation:** MXFP6A8 needs Humming. `EmulationMxfp6LinearKernel` does not accept MXFP8 activations, so without Humming (e.g. ROCm) MXFP6A8 fails at load with "Failed to find a kernel"; weight-only `MXFP6A16` can use emulation.
- The scheme is named `W6A8` like the other MX schemes, and also serves weight-only (`MXFP6A16`) checkpoints.
- compressed-tensors 0.20 breaking changes checked against vLLM: `QuantizationArgs` rejects `actorder` group/dynamic/True while parsing, which made vLLM's guard unreachable, so it is removed and the test matches the new error. Python >=3.11 matches vLLM's floor, `psutil` is already a dependency, and vLLM does not serialize `QuantizationArgs` or subclass `OffloadCache`.
- Not a duplicate: no open vLLM PRs cover compressed-tensors MXFP6 or bump this pin. Existing MXFP6 support is Quark-only.
- AI assistance (Claude Code) was used. I reviewed the diff and ran the validation above.
