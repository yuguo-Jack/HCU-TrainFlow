# [Perf] V2 runner decode optimizations for NVIDIA Confidential Computing

[Upstream PR](https://github.com/vllm-project/vllm/pull/59981) · state: open · merged: False

## Original PR description



## Purpose

This PR supersedes #52226 by porting the NVIDIA Confidential Computing (CC) decode optimizations to the V2 GPU model runner, and fixes the UVA incoherence bug that makes V2 produce garbage under CC. 

The incoherence issue with UVA was initially reported in #57224 and independently fixed by @juhiechandra in #57404 via a runtime coherence probe in `is_uva_available()`. This PR instead gates UVA on CC detection and adds a staged-copy fallback so that disabling UVA does not reintroduce host-synchronous copy stalls.

### Background

NVIDIA Confidential Computing protects workloads in confidential VMs by encrypting PCIe traffic through bounce buffers. This has two consequences for the V2 runner:

1. **Pinned host memory is not coherent from the device.** The V2 runner's `UvaBufferPool` writes inputs into pinned host memory and has the GPU read them directly through the UVA mapping. Under CC the GPU sees a stale snapshot of that memory, so the model runner produces garbage.
2. **`cudaMemcpyAsync` on pinned memory is host-synchronous.** The issuing thread blocks until the copy, and everything already queued on its stream, completes. This causes:
   - **H2D input copies** on the compute stream to block the scheduler thread behind the in-flight forward pass.
   - **Per-step D2H token readback** to delay the next CUDA graph launch.

### Changes

All changes are gated on CC detection; non-CC code paths are untouched.

- **CC detection**: `Platform.is_confidential_compute()`, auto-detected via NVML on CUDA with a `VLLM_CONFIDENTIAL_COMPUTE=0/1` override.
- **UVA disabled under CC**: `is_uva_available()` returns `False` under CC, so the buffer pool falls back to explicit copies. A new `StagedH2DBuffer` mirrors each pinned host buffer into a device tensor on every `uva()` call, keeping the pool's invariant that a slot is only reused once no GPU reader is in flight.
- **Staged H2D input copies**: `staged_h2d()` in `vllm/v1/conf_compute_utils.py` issues the host-synchronous copy on an idle prep stream so the host only waits for the transfer itself, then orders the compute stream after it with `wait_stream` / `record_stream`. `async_tensor_h2d()` routes through this path under CC, so call sites in `encoder_decoder.py`, `encoder_only.py`, and `zero_block_ids()` need no CC-specific logic.
- **Deferred D2H output readback**: `AsyncOutput` and `AsyncPoolingOutput` record a source-ready event on the main stream at construction and issue the D2H copies from `get_output()` on the executor's output thread, instead of blocking the scheduler thread.

## Test Plan

- New unit tests in `tests/v1/worker/test_conf_compute_copies.py` covering UVA availability under CC, `staged_h2d()` with pinned and pageable sources, `async_tensor_h2d()` routing, `StagedH2DBuffer` pool round-trips, and deferred D2H semantics.
- Decode benchmark on Qwen3.5-397B-A17B-FP8, TP4, B300, CC enabled, comparing against the V2 runner with CC off and against the V2 runner on `main` with CC on.

Recording readiness on the producer stream assumes a registered stream only carries D2H copies after its `wait_stream()`, but that's not true for the output copy stream. In `AsyncOutput.__init__` (`async_utils.py`), `get_ep_all2all_manager().query_fault()` runs `(current != last).any()` on `copy_stream`, and `has_fault.to("cpu", non_blocking=True)` follows it. With this change, the readiness event for that copy is recorded on `main_stream`, which isn't ordered after the `.any()` kernel, so the worker can copy `has_fault` before it has been computed (EP fault detection + CC).

The simplest fix is probably to compute `has_fault` on the main stream before entering the copy-stream block. The general assumption is still fragile, though, so it would be worth stating in `register_d2h_stream()`'s docstring that a registered stream must not run kernels that produce data it then copies.

This shows that `cudaMemcpyAsync` waited for the work queued ahead of it, but skipping `cur.wait_stream(staging)` relies on something stronger: the copy *itself* must have completed by the time the call returns. A driver could wait for the stream to drain (e.g. before reusing a bounce buffer) and still finish the transfer asynchronously. Could we also record an event right after the copy and require that one to be complete too?

```python
        _orig_copy_(dst, src, non_blocking=True)
        after = torch.cuda.Event()
        _orig_cuda_event_record(after, stream)
        host_sync = bool(_orig_cuda_event_query(after))
```

Since `after` is recorded after the copy on the same stream, it being complete implies both the prior work and the copy are done.
