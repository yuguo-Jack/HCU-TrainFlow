# [CI][Feature] Meta-device mode for CPU-only end-to-end engine CI

[Upstream PR](https://github.com/vllm-project/vllm/pull/61407) · state: open · merged: False

## Original PR description

## Overview

Adds `VLLM_META_MODE`, an opt-in mode that runs the v1 engine end-to-end through Model Runner V2 (MRV2) on a CPU-only host with weights and KV cache on the PyTorch `meta` device. Large production models can then be validated structurally (construction, sharding, attention/MoE/quantization dispatch, scheduling, prefix caching, KV offload) without reserving a GPU node.

This work is one of the prerequisites for the vLLM Simulator proposed in RFC #61406: the same meta-device execution path provides the CPU-only engine initialization on which hardware-aware performance simulation builds.

> [!IMPORTANT]
> **Maintainer decision needed:** should the fake kernels in `_META_OVERRIDES` (`vllm/meta_mode.py`) be maintained by the owners of the corresponding modules? See [Decisions requested](#decisions-requested).

## Claims

- New `load_format="meta"` (`MetaModelLoader`) builds the model on `meta` with no checkpoint download and no weight initialization. Weights, the KV pool, and the L2 offload buffer use 0 real bytes.
- Production configurations run unchanged: real TP=8 + EP, PP=2, PCP=2, and DCP=2 ranks in the regular `MultiprocExecutor` over Gloo, with the requested quantization preserved (FP8 per-tensor, FP8 block-wise, ModelOpt NVFP4, `deepseek_v4_fp8`).
- New `tests/meta/test_meta_models.py` (9 cases) pins and asserts MRV2, and covers Kimi-K3, Qwen3.8-2.4T-A95B-FP8, DeepSeek-V4-Pro, GLM-5, and Qwen3-30B-A3B / DeepSeek-V2-Lite. It runs a full 8704-token prompt and checks a 4-round L1/L2 `SimpleCPUOffloadConnector` round-trip. Weights and KV stay on meta, while MRV2's value-carrying host bookkeeping runs through the Triton interpreter.
- When `VLLM_META_MODE` is unset, nothing changes: `vllm/meta_mode.py` is not imported, and every other branch depends on that env var, on `load_format == "meta"`, or on `tensor.is_meta`.

## Details

### Motivation

Integrating a large model raises the same questions every time. Does the production config construct? Are the TP/EP/DCP shards and KV shapes valid? Do attention, MoE, quantization, scheduling, and offload compose correctly? Small synthetic models miss architecture-specific paths, and GPU E2E runs are expensive and capacity-constrained.

### Design

Mode-wide setup is gated by `envs.VLLM_META_MODE`. Tensor-local fallbacks use `tensor.is_meta`, so they also hold for any caller that passes meta tensors. No vLLM class is monkeypatched. Some parts of the implementation draw on ideas from #59019.

- **Config / platform:** `VllmConfig.__post_init__` forces `enforce_eager` and `load_format="meta"`. It disables async scheduling only for PP>1, because the async sampled-token broadcast needs real values, and it drops `speculative_config`. `wrap_meta_platform` mixes four device-less capabilities over the detected platform: no pinned memory, zero memory usage, one compute unit, and 8 devices.
- **Worker / runner:** `init_device` runs on CPU with Gloo, then constructs the configured runner (MRV2 by default; the suite sets `VLLM_USE_V2_MODEL_RUNNER=1` and asserts it). The KV budget comes from the KV spec instead of profiling, and warmup is skipped. `self.device` stays `cpu`, so MRV2 request state and scheduling buffers keep real values, while weights, KV, intermediate tensors, and compute-only metadata use `meta`. Meta sampler outputs are materialized as constant host token ids before MRV2 feeds them back into request state and starts async output copy. `MetaAsyncOutput` wraps either runner's output and applies `num_scheduled_tokens × VLLM_META_TOKEN_LATENCY_MS`, preserving async-output overlap.
- **Kernels:** `register_meta_impls()` derives Meta kernels from operator schemas for leaf ops that return nothing or return an aliased input. A small override table covers ops whose outputs are independent of their inputs: FA2 `varlen_fwd`, FA3 `fwd`, FlashMLA sparse prefill/decode, and the DeepSeek-V4 quant insert. Native launches that cannot carry a `torch.library` kernel are intercepted by `install_launch_hooks()`: MRV2's host-only request-state/input/block-table Triton kernels run in the CPU interpreter, while model/attention launches and launches touching meta tensors are skipped. CuteDSL, TileLang, and `torch.cuda` Event/Stream/device queries remain shape-only stubs. DeepGEMM keeps its impls unbound and returns shape-only results.
- **Parallelism:** `GroupCoordinator` uses `device=meta` with `DeviceCommunicatorBase`, so collectives propagate shapes without payloads. EP uses `AgRsAll2AllManager`.
- **Offload:** `SimpleCPUOffloadWorker` skips pinned allocation and DMA when the KV cache is on `meta`, and every pending event polls as complete. All scheduler-side logic and hash bookkeeping run unchanged.
- **Quantization:** Narrow `is_meta` early returns in `process_weights_after_loading`/`apply` cover the Marlin FP8, ModelOpt NVFP4, and `requantize_with_max_scale` paths, which need real values for repacking or for `.item()`.

### Decisions requested

1. **Ownership of independent-output fake kernels** (`_META_OVERRIDES` in `vllm/meta_mode.py`). These ops return new tensors whose shapes cannot be derived from the schema, so someone has to write the shape logic.
   - **(a) Central table (current).** All meta fakes live in one place and are gated on meta, but meta-CI maintainers must track changes in kernels they do not own. A changed output shape is only caught when the E2E test fails.
   - **(b) Owner-maintained `register_fake` next to the op definition.** Each fake lives in the kernel's own module (`vllm_flash_attn`, FlashMLA, DeepSeek-V4) under its CODEOWNERS, and new ops with independent outputs would be expected to ship a fake. The meta mode keeps only the schema-derived defaults. This is how the first commit was structured.
   - With (b), the central table goes away. With (a), it should be shared with #59019's `OVERRIDES`.
2. **Launch-layer routing/stubs** (Triton, CuteDSL, TileLang, `torch.cuda` primitives). Is this acceptable as a temporary process-wide fallback, to be retired op by op once a fake exists?
3. **CI hardware availability and worker split.** Can CI provide a small amount of accelerator capacity—for example, an A10 as the CUDA execution substrate while structurally validating configurations intended for GB300-class deployments? If so, an alternative design is:
   - CPU-only jobs use `CPUWorker` / `CPUModelRunnerV2` for CPU runtime coverage.
   - GPU jobs use `GPUWorker` / `GPUModelRunnerV2`, while weights, KV cache, and model activations remain on `meta` and model compute remains shape-only.
   - Because parameter/KV storage and model compute consume almost no device memory or compute, one GPU host could exercise many large-model and parallel configurations. A real CUDA context could handle streams and value-carrying Triton bookkeeping, allowing most Triton and `torch.cuda` interception to be removed.
   - An A10 would not emulate GB300 numerics, kernels, memory capacity, or architecture-specific capability checks; it would only provide the CUDA control-plane substrate. Is that structural fidelity sufficient, and is such shared hardware capacity available?
4. **Initial CI scope.** Which models and quantization paths should the first CPU job require?

### Tradeoffs and limitations

- Scope is structural only: meta tensors carry no data, so numerics, kernel correctness, real communication, and performance are out of scope. GPU tests remain authoritative.
- Both Model Runner V1 and MRV2 retain meta paths, but the E2E suite pins MRV2 so regressions cannot silently fall back to MRV1. MRV2's host bookkeeping kernels are interpreted rather than GPU-launched; model-side Triton/CuteDSL launches remain shape-only no-ops.
- The launch-layer stubs are process-wide fallbacks, so meta tests must run in dedicated processes. The intent is to retire each stub once the owning kernel gains a `register_fake` / meta branch.
- Speculative decoding is dropped in meta mode because its acceptance loop has value-dependent boundaries.
- If every attention backend is rejected (no accelerator), meta mode picks the first backend that imports and matches the requested sparsity. Attention forward is faked, so the backend class is used only for metadata.
- **CI:** this PR adds no Buildkite job yet. The suite is CPU-only and needs the HF configs available locally. I propose starting it as a non-blocking CPU job and making it required once runtime and stability are proven.
