# [Frontend] Add granite_toolcall_parser for Granite 4.2 tool calling

[Upstream PR](https://github.com/vllm-project/vllm/pull/65216) · state: closed · merged: True

## Original PR description

## Purpose

Granite 4.2 emits tool calls in an XML format:

```
<tool_call>
<function=func_name>
<parameter=key>value</parameter>
</function>
</tool_call>
```

This PR adds a dedicated `granite_toolcall_parser` so Granite 4.2 ships with its own
tool-call parser name.

```bash
vllm serve ibm-granite/granite-4.2-8b \
    --tool-call-parser granite_toolcall_parser \
    --enable-auto-tool-choice
```

## Design

`GraniteToolCallParser` is a thin subclass of the existing `GraniteThinkingParser`. Granite 4.2
already drives both `<think>`/`</think>` reasoning and `<tool_call>` XML tool calls through a
single engine, so the subclass inherits the grammar, argument converter and streaming logic
unchanged and is exposed as a standalone `--tool-call-parser`.

- **No duplicated grammar** — the tool-call extraction is inherited, so future fixes to the shared
  parser engine flow in automatically.
- **Works standalone** — it extracts tool calls correctly whether or not
  `--reasoning-parser granite_thinking_parser` is also configured, and with any reasoning parser.
- **Both thinking modes** — behaves identically with `enable_thinking` on and off.

Changes:

- `vllm/parser/granite_toolcall.py` — `GraniteToolCallParser(GraniteThinkingParser)`
- `vllm/tool_parsers/granite_toolcall_parser.py` — tool-parser adapter shim
- `vllm/parser/engine/registered_adapters.py` — generate the adapters
- `vllm/tool_parsers/__init__.py` — register the `granite_toolcall_parser` key
- `docs/features/tool_calling.md` — document the Granite 4.2 row
- `tests/tool_parsers/test_granite_toolcall_parser.py` — parity test suite

## Test Plan

`tests/tool_parsers/test_granite_toolcall_parser.py` runs a shared corpus of model outputs through
both `granite_toolcall_parser` and the in-tree `qwen3_coder` parser (which handles the same XML
format) and asserts byte-identical results. Coverage:

- single / parallel / no-call / reasoning-then-call outputs
- every JSON argument type (int, float, bool, null, string, array, object)
- empty arguments, escaped strings, multiline values, whitespace inside tags
- malformed/partial inputs (missing closing tags, missing `>` on the function name, unclosed
  function names, consecutive calls without a closing tag)
- each case run in non-streaming, per-token streaming, and random-chunk streaming
- each case run with `enable_thinking` both `True` and `False`
- a standalone test confirming extraction works with no reasoning parser configured

## Test Result


- sfeng33 · CHANGES_REQUESTED · 2026-11-03T16:37:31Z · [source](https://github.com/vllm-project/vllm/pull/65216#pullrequestreview-5755997702)

Thanks for the PR. I think the Granite-named flag is fine to add, but the shape is bigger than it needs to be.

Granite 4.2 emits the same tool-call XML as Qwen3-Coder, and this PR shows that: the new class is empty and the parity tests pass because `qwen3_coder` already handles the format. So the parser is really an alias, and an alias does not need a new parser module, a new engine config, a second adapter pair, or a 500-line parity suite.

Subclassing `GraniteThinkingParser` also pulls the leading-newline strip into the tool path. That strip exists to clean up the chat template's newline after `</think>`. When the parser runs on its own with no reasoning parser, it changes plain content (for example `\n\nHello` becomes `Hello`) where `qwen3_coder` keeps it. The test corpus has no leading-newline case, so the parity tests do not catch this.

Suggestion: keep the `granite_toolcall_parser` name or anything that is preferred, but make it a registry alias that maps to `Qwen3EngineToolParser` in `vllm/tool_parsers/__init__.py`, the same way `qwen3` maps to `hermes` today. Then drop `vllm/parser/granite_toolcall.py`, the `registered_adapters.py` hunk, and the parity test file. One small test that the name resolves to the Qwen3 class is enough.
