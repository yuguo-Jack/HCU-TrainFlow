## Purpose

An opt-in decode path for the eager XPU Qwen3.5 / Qwen3.6 MoE model at TP2 on
two Xe2 GPUs: each decoder layer of a decode or MTP verify step runs as one
persistent kernel from vllm-xpu-kernels (GatedDeltaNet or full attention, then
the MoE with the shared expert), with both TP all-reduces inside the kernel
through mailboxes in the peer GPU's memory. Every other step runs the stock
layers.

Depends on:

- #64687 (the eager XPU Qwen3.5 model and its fused MoE). The first 9 commits
  of this branch are an earlier revision of #64687, unchanged. Please review
  them in #64687, not here; this branch will be rebased on #64687 as it
  progresses. Until then this PR stays a draft.
- vllm-project/vllm-xpu-kernels#685: the mono decode ops. The minimum
  vllm-xpu-kernels version is the first release that contains them, built with
  `MONO_DECODE_KERNELS_ENABLED`. Without them `--monokernel` is refused at
  startup with the missing op names; nothing else changes.

Scope: everything is under `vllm/models/qwen3_5/xpu/` and
`tests/models/qwen3_5/xpu_specialized_decode/`, except:

- `vllm/platforms/xpu.py`: one Level Zero driver key, set only under
  `--monokernel` (the comment there gives the reason);
- the docstring of the existing `KernelConfig.monokernel` option in
  `vllm/config/kernel.py`, which gains this deployment.

Inside `vllm/models/qwen3_5/xpu/`, one change touches #64687's logic: the MoE
block records `--monokernel` and the fused MoE then builds no plan.

How it works (details in `specialized_decode/README.md`):

- `--monokernel` with anything outside the supported deployment fails at
  startup with one `ValueError` that lists every reason (config in the model's
  `__init__`, loaded weights when the executor is built, caches at every bind).
  Every TP rank agrees on each verdict before anything collective runs.
- The model state (`model_state.Qwen3_5XpuModelState`) builds the executor
  after load and binds it to every KV cache vLLM allocates (the
  memory-profiling cache, then the real one).
- `plan()` picks the kernels per step from host metadata that is the same on
  every rank: a pure decode step of 1, 2, 4 or 8 rows, or a pure verify step
  whose rows x tokens have a verify kernel. Under FULL decode graphs the plan
  is baked in at capture.
- The MTP drafter's decoder layer and its norms + fc run on the kernels.
- Candidate sampling: on small steps that only need each request's top-k or
  argmax, the ranks swap the k best logits of their vocabulary shards instead
  of all-gathering the logits, and vLLM's sampler and rejection sampler run on
  the candidates (same distribution as the stock one).
- The kernels read the loaded weights and caches in place, without copies.
  Under `--monokernel` the fused MoE of #64687 is off (it would replace the
  shared expert's weights with row-major [K, N] copies), so the steps the mono
  kernels do not serve run the stock MoE; without `--monokernel` nothing of
  #64687 changes.
- Fail-stop: every in-kernel wait for the peer is bounded; a rank that gives up
  marks its health word, and every 16 steps the ranks agree over the TP CPU
  group and stop the engine together.

## Design

```text
startup                         after load                       every step (forward)
───────                         ──────────                       ────────────────────
--monokernel                    model state                      Qwen3_5Model.forward
  │                               (Qwen3_5XpuModelState)            │
  ▼                               │                                 ▼
config check in the model's       ├─ weight check                 plan() ── host metadata,
__init__ (runtime.unsupported)    │  (guards.weight_reasons)        │         same on every rank
  │  one ValueError listing       ├─ P2P mailboxes:                 ├─ pure decode, 1/2/4/8 rows
  │  every reason; TP ranks       │  Level Zero IPC regions,        │   → mono_decode_layer per layer
  │  agree before anything        │  dma-buf fd exchange (peer.py)  ├─ pure verify, rows x tokens
  │  collective runs              └─ bind_caches() at every         │   with a kernel
  ▼                                  initialize_kv_cache:           │   → mono_decode_layer_spec
platform: one Level Zero             mono_register_layer for        └─ anything else → vLLM's layers
driver key (platforms/xpu.py)        every layer + the MTP layer
                                                                    MTP drafter: plan_draft(),
                                                                    mono_mtp_prologue + its layer

                                                                  sampling: compute_sample_logits
                                                                    → mono_shard_topk candidates
                                                                    → vLLM sampler / rejection
                                                                      sampler on the candidates
                                                                  fail-stop: health word copy each
                                                                    step, TP agreement every 16 steps
```

- Hooks: the model files only call in. `model.py` runs the config check in the causal LM's `__init__`,
  `plan()` in `Qwen3_5Model.forward` and `step.layer(i)` in the layer loop, and returns the model state class.
  `mtp.py` registers the drafter and runs `plan_draft()`, the prologue and the layer kernel. Everything else is
  in `specialized_decode/runtime/` (`decode.py` planning and binding, `layers.py` vLLM tensors -> kernel
  launches, `peer.py` mailboxes and TP agreement, `guards.py` refusals and the fail-stop watch, `sampling.py`
  candidate sampling) and `model_state.py`.
- Graphs: under FULL decode graphs the plan is baked in at capture; a replay with fewer requests than its graph
  pads whole requests (sequence length 0, slot -1), which the kernels serve like real ones. Binding the caches
  inside a capture is an error.
- Weights and caches are vLLM's, read in place. The fused MoE of #64687 is off under `--monokernel` (it would
  replace the shared expert's weights with `[K, N]` copies); steps the mono kernels do not serve run the stock
  MoE.

## When it applies

`--monokernel` is opt-in; without it nothing here is built or run. With it, startup checks the deployment and
fails with one `ValueError` listing every unsupported setting. Supported:

- Hardware: two Xe2 (Battlemage) GPUs, tensor parallel size 2; vllm-xpu-kernels with the mono decode ops
  (vllm-project/vllm-xpu-kernels#685, built with `MONO_DECODE_KERNELS_ENABLED`).
- Model: a Qwen3.5 / Qwen3.6 MoE checkpoint with the 35B-A3B shapes (hidden 2048, 256 experts top-8, expert and
  shared expert intermediate 512, GatedDeltaNet 16 / 32 heads of 128, attention 16 / 2 heads of 256).
- Quantization and dtypes: online fp8 per-tensor weights (`--quantization fp8_per_tensor`; fp8 e4m3 linears and
  experts, per-tensor scales, one scale per expert), `--dtype float16`, fp16 norms and router, fp16 KV cache,
  fp32 recurrent state; lm_head stays fp16.
- Runtime: Model Runner V2 (`VLLM_USE_V2_MODEL_RUNNER=1`), no torch.compile (the eager model), FULL decode graphs
  (`FULL_DECODE_ONLY` or `FULL_AND_PIECEWISE`), block size a multiple of 64, `max_model_len` up to the kernels'
  limit (512K).
- Speculative decoding: none, or MTP with 1-7 speculative tokens.
- Refused: other TP sizes, pipeline / data / expert / context parallelism, EPLB, DBO, batch-sharded sampling,
  LoRA, KV transfer connectors, sleep mode, CPU weight offload, weight updates, routed-expert capture, other
  dtypes, quantizations, KV or state dtypes and block sizes, other speculative methods, adaptive verification,
  dynamic speculative decoding, the V1 model runner, torch.compile, non-FULL decode graphs, other shapes,
  platforms or GPUs.

Per step, at runtime:

- Mono kernels: a pure decode step of 1, 2, 4 or 8 rows, or a pure verify step of whole requests with rows x
  tokens of 2x2, 3x3, 4x2, 4x4, 6x3, 8x2, 8x4 or 8x8; the MTP drafter's passes whose rows have a kernel (its decoder layer as above, its norms +
  fc for 1, 2, 3, 4, 6 or 8 rows).
  Every other step (prefill, mixed, wider and PIECEWISE steps) runs vLLM's layers with the stock MoE.
- Candidate sampling: a decode or verify step of up to 8 rows whose requests are all greedy or sample with
  top_k <= 64 and need nothing over the whole vocabulary (no logprobs, penalties, logit bias, bad words, allowed
  tokens, min_tokens, min_p, structured output, seed or logits processors). Otherwise the full logits are
  all-gathered as usual.

- Hardware: 2x Intel Arc Pro B70 (32 GB), each on PCIe 5.0 x8 (32 GT/s, checked before every point), Intel Xeon
  w5-3435X; no other GPU work during the runs.
- Software: Linux 6.17.0-1007-intel, compute runtime 26.27.39122.11 (`libze-intel-gpu1`, `intel-opencl-icd`),
  Level Zero loader 1.32.0, oneAPI 2026.1, torch 2.15.0+xpu; vLLM = this branch (main 190df0b9 + #64687 + this PR);
  vllm-xpu-kernels = v0.1.16.4 with the mono decode ops of vllm-project/vllm-xpu-kernels#685 applied; base and
  `--monokernel` run the same build.
- Model: Qwen3.6-35B-A3B (bf16 checkpoint), online fp8 per-tensor weights (`--quantization fp8_per_tensor`),
  fp16 activations (`--dtype float16`), lm_head fp16, TP2.
- Server (base; `--monokernel` adds that flag only):

  ```bash
  VLLM_USE_V2_MODEL_RUNNER=1 VLLM_WORKER_MULTIPROC_METHOD=spawn \
  python3 -m vllm.entrypoints.openai.api_server --model Qwen3.6-35B-A3B \
    --dtype float16 --quantization fp8_per_tensor --tensor-parallel-size 2 \
    --block-size 64 --max-model-len 40960 --max-num-seqs 32 \
    --max-num-batched-tokens 40960 --kv-cache-memory 3435973837 \
    --gpu-memory-utilization 0.92 --no-enable-prefix-caching \
    --compilation-config '{"cudagraph_mode": "FULL_AND_PIECEWISE"}' \
    [--monokernel] [--speculative-config '{"method": "mtp", "num_speculative_tokens": K}']
  ```

  (32K prompts: `--max-num-batched-tokens 8192`.) Three short warm-up requests after startup.
- Client:

  ```bash
  vllm bench serve --backend vllm --dataset-name custom --dataset-path <prompts.jsonl> \
    --custom-output-len 256 --ignore-eos --seed 1 \
    --max-concurrency C --num-prompts $((C * N)) --save-result --save-detailed
  ```

  Prompts: a fixed set of ShareGPT conversations, about 1K tokens (32 prompts) or about 32K tokens (12 prompts);
  N = 6 prompts per concurrency slot at 1K. Sampling: the model's generation config
  (temperature 1.0, top_k 20, top_p 0.95).
- Metric: clean median TPOT. Per request, TPOT = sum of inter-token latencies / (output tokens - 1), after
  replacing the latencies longer than 20x the run's median (decode steps shared with another request's prefill) by
  that median; the table gives the median over requests. With MTP the acceptance length differs between runs, so
  those points will also list the acceptance length and the time per step (TPOT x acceptance length).
- Base and `--monokernel` alternate point by point; two rounds; the better round is reported. Without MTP the
  two rounds agree within 1 %; with MTP within 6 % (acceptance varies with sampling).
