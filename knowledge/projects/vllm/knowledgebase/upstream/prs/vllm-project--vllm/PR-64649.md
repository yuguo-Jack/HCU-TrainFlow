# [Bugfix][Scheduler] Cap the async-load spec margin at max_model_len

[Upstream PR](https://github.com/vllm-project/vllm/pull/64649) · state: open · merged: False

## Original PR description

## Overview

An async KV-connector load is admitted only if it fits in the free pool minus one spec decode step (#57104, per KV cache group since #59880). Near `max_model_len` that margin can exceed what the request can still use, so a load that fits the pool is never admitted and every request behind it waits. This PR caps each group's margin at the blocks left before `max_model_len`.

## Claims

- Each group's margin is capped at the blocks between the request's computed prefix and `max_model_len`. It is never larger than before, and it changes only for a request within one spec step of `max_model_len`.
- In the reproducer below, the stalled request is admitted, loads its remote KV and completes, and an unrelated request on the same server completes.

## Details

Root cause: admission reserves `_spec_decode_step_blocks`, a constant number of blocks per group for one spec decode step. Slots never extend past `max_model_len`, so a request within one step of the limit can use fewer blocks than that. When the load plus the full margin exceeds the whole pool, `allocate_slots` fails even with every block free, and the `break` in the waiting loop holds the queue behind the request.

The margin from #57104 and #59880 keeps its purpose. It is only reduced where the request cannot use the blocks, and startup already guarantees that one `max_model_len` sequence fits, so a lone request can always be promoted. Replacing the `break` with a skip would also unblock later requests, but it changes FCFS admission and leaves the impossible request stuck, so this PR does not do it. The scheduler change adds 21 lines and no GPU work.

CI: the test module is marked `cpu_test` and runs in the "(CPU) V1 Others" step. The end-to-end case needs two servers with a P2P tier, which no CI step provides, so it was validated locally as above.

Duplicate-work check: I searched open and closed PRs and issues for async load admission, waiting-queue head-of-line blocking and spec reservations. #45406 and #58442 (both closed, unmerged) address other async-load stalls. #64379 (open) speeds up async admission without changing its decisions. It rewrites the same `reserved_blocks` expression, so whichever lands second only needs `self._spec_decode_step_blocks` replaced by `self._spec_decode_step_margin(num_computed_tokens)`. I found no matching report or fix.
