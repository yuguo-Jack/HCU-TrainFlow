# [Bugfix][KV Offload] Preserve coordinator metadata and current eager-store placement

[Upstream PR](https://github.com/vllm-project/vllm/pull/60742) · state: open · merged: False

## Original PR description

## Overview

Keep SimpleCPU cache geometry and eager-store placement consistent with the device coordinator. Reconstructing only dataclass fields can lose plugin metadata; append-only request placement can retain stale page IDs after sliding-window recycling.

## Claims

- Keep the original configuration type and additional metadata while replacing CPU capacity and tensor descriptors.
- Leave the device configuration unchanged; retain the existing allocation calculation and shared-field behavior.
- Before selecting eager stores, use the existing connector block state to obtain the current request block table. Preserve the existing fallback when current placement is unavailable.

## Details

The pre-submission search and source comparison found no equivalent fix for these two SimpleCPU paths: current main still reconstructs CPU configuration with `dataclasses.replace` and selects eager stores from append-only request placement. Related work on transfer metrics, other connectors and physical-ID deduplication does not preserve this metadata or reject a single stale page belonging to another request.

`dataclasses.replace` copies declared dataclass fields and loses extra fields attached by hardware plugins. A shallow copy preserves those fields, after which this function replaces `num_blocks` and `kv_cache_tensors` with its existing derived values. This adds no transfer state machine, model predicate, environment variable, modelrunner behavior or new public option.

The eager-store selector now reads `KVConnectorBlockState.get_block_ids(req_id)` before choosing candidate pages. SWA recycling or copy-on-write can invalidate append-only placement; using the live table prevents saving a recycled page under the wrong request. This reuses the existing placement interface and changes neither the confirmation boundary nor CPU eviction policy. The metadata copy occurs during configuration derivation; the live-table lookup occurs in the existing scheduler store-selection path. Both fixes are needed by the tested hybrid configuration. The NPU integration also needs the companion Ascend implementation linked above; this change alone does not claim to enable NPU offload or provide the table's speedup.
