# [Spec Decode] Per-request cap on verified draft tokens (max_speculative_tokens)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63151) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `SamplingParams.max_speculative_tokens` (also accepted on the OpenAI chat and completion endpoints): a per-request upper bound on the draft tokens verified per step. `0` turns speculative decoding off for that request. Addresses the "per-request speculative decoding control" ask in #52258. Part of the tracking issue #63152.

```python
SamplingParams(max_tokens=256, max_speculative_tokens=1)
```
```bash
curl localhost:8000/v1/completions -d '{"model": "...", "prompt": "...", "max_speculative_tokens": 0}'
```

Not a duplicate: RFC #48202 / #48204 is about the proposer choosing per-request proposal lengths (DSpark confidence head); this is a client-side cap that composes with it and with the `num_speculative_tokens_per_batch_size` schedule. #59680 is a platform fallback for unsupported sampling params. No open PR adds a per-request cap.

## Claims

- A request verifies at most `min(max_speculative_tokens, K)` drafts per step, where K is `num_speculative_tokens` or the dynamic schedule's value for the step. Unset (default) is unchanged behavior.
- `max_speculative_tokens=0` gives token-identical output to an engine without speculative decoding.
- No throughput change when the field is unset or equals K.

## Validation

1x H100 (96 GB), this branch (upstream 271941177d + this commit, precompiled build), Qwen/Qwen3-1.7B, V2 model runner, async scheduling on, `{"method": "ngram_gpu", "num_speculative_tokens": 4, "prompt_lookup_max": 4, "prompt_lookup_min": 2}`, `VLLM_BATCH_INVARIANT=1`, greedy, 256 tokens, 32 prompts (16 copy-from-prompt, 16 free-form):

| run (32 prompts) | identical to no-spec engine | draft tokens | accepted | accepted by position 1/2/3/4 | drafts per step |
|---|---|---|---|---|---|
| no-spec engine, run 2 vs run 1 | 32/32 | - | - | - | - |
| `max_speculative_tokens=0` | 32/32 | 0 | 0 | 0/0/0/0 | - |
| unset | 32/32 | 14968 | 969 | 327/242/208/192 | 4.0 |
| `=1` | 32/32 | 4077 | 631 | 631/0/0/0 | 1.0 |
| `=2` | 32/32 | 7752 | 828 | 460/368/0/0 | 2.0 |
| `=4` (= K) | 32/32 | 14968 | 969 | 327/242/208/192 | 4.0 |
| mixed caps [unset, 0, 1, 2, 4] in one batch | 32/32 | 8086 | 710 | 352/183/90/85 | 2.68 |

Throughput, same engine, 32 concurrent requests, output tok/s (2 runs): unset 3913 / 3904, `=4` 3899 / 3909, `=0` 3618 / 3607.

On NVIDIA GB10 (DGX Spark) with the same scheduler logic on an earlier nightly (n-gram, schedule K=8/5/3/0 by batch size, FP8 KV): requests that copy from their prompt accept 2.5-2.9 tokens per step while chat accepts ~1.5, so letting copy-heavy requests use K=8 and capping the rest raised a rewording request at concurrency 1 from 137 to 149 tok/s (+9%) vs all requests at K=5. With the cap unset, batch throughput was unchanged.

Tests:

```
$ pytest -q tests/v1/core/test_scheduler.py tests/v1/core/test_async_scheduler.py tests/test_sampling_params.py -k "max_speculative_tokens or capped_request"
8 passed
$ pytest -v tests/v1/e2e/spec_decode/ngram_suffix/test_ngram_suffix.py -k max_speculative_tokens   # H100, MRV2 and MRV1
test_ngram_gpu_max_speculative_tokens[sync] PASSED
test_ngram_gpu_max_speculative_tokens[async] PASSED
```
The e2e test fails with the scheduler change reverted (capped requests verify 3 drafts per step).

Mixed caps in one batch (half unset, half `=1` or `=0`), 32 requests: 3525-3605 / 3485-3548 output tok/s vs 3510-3523 unset (H100 PCIe, 3 rounds): no measurable cost from the non-uniform verify batch.

## Details

- `Scheduler._num_spec_tokens_for(request)` returns `min(cap, num_spec_tokens)`.
- Sync scheduling: drafts are truncated per request in `update_draft_token_ids` before grammar validation.
- Async scheduling: each request's placeholder list is sliced to its cap (only when capped, so the shared list is reused otherwise); `update_draft_token_ids_in_output` already trims drafts to the scheduled count.
- A capped request is not padded to `1 + num_spec_tokens` on its first decode step, since padding would verify drafts it opted out of.
- The model runners already take per-request draft counts from `scheduled_spec_decode_tokens` (as for diffusion canvases and invalid drafts), so no runner change is needed.
- Validation: non-negative integer; values above K are no-ops so clients need not know the server's K; rejected for diffusion models, whose spec tokens are the canvas.
- Trade-off: a batch whose requests verify different numbers of drafts is not a uniform decode batch and runs piecewise CUDA graphs; at 32 requests on H100 this was not measurable (above). Uniform caps keep full graphs. The drafter still proposes K tokens for capped requests: the cap saves verification, not drafting.
- Docs: new "Per-request cap" section in the dynamic speculative decoding page.

Open question for reviewers: a first-class `SamplingParams` field vs an `extra_args` key. I chose a field for discoverability and OpenAI-endpoint validation.
