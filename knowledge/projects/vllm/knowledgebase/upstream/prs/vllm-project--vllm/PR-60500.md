# [Perf][Nemotron-Parse] Do image rescale/normalize on the device

[Upstream PR](https://github.com/vllm-project/vllm/pull/60500) · state: closed · merged: True

## Original PR description

## Overview

Opts `NemotronParseForConditionalGeneration` into vLLM's existing `mm_device_do_normalize` path, so the fixed 2048x1664 canvas travels to the device as `uint8` and the rescale/normalize happens in `FusedMMInputNorm` instead of as single-threaded CPU work inside the engine process.

Please do aware this change depends on pending tied embedding fix for nemoparse2.0 embedding.

The checkpoint ships its image processor as remote code, and its `preprocess(self, images, return_tensors=None, **kwargs)` **ignores** the `do_rescale` / `do_normalize` kwargs that `MultiModalConfig.merge_mm_processor_kwargs` injects when the feature is on: it always runs `ToTensor` and normalizes from `self.do_normalize`. Setting the model flag alone would therefore normalize twice. The `_call_hf_processor` override replays the processor's own pipeline up to (but not including) `ToTensor` to produce the raw canvas, and raises -- pointing at `--no-mm-device-do-normalize` -- if a checkpoint does not expose that pipeline, so "feature on => `uint8`" holds by construction.

## Claims

- `supports_mm_device_do_normalize = True`; `build_mm_input_norm()` builds the norm and `_process_image_input` applies it unconditionally, as in the other models that opt in. With the feature off that is `IdentityInputNorm`, i.e. a plain cast.
- With the feature off, behaviour is identical to today.
- Both published checkpoints are handled: v1.2 (albumentations `transform` branch) and 2.0 (`_pad_to_size` branch).
- Payload per request drops 40.89 MB fp32 -> 10.22 MB uint8.

## Details

`_build_uint8_canvas` depends on three attributes of the checkpoint's remote-code image processor: `_resize_with_aspect_ratio`, `_pad_to_size` and `transform`. Two are private by convention and none is a stable API. If they change, the lookup raises and the error names `--no-mm-device-do-normalize`, so the failure is loud instead of a silent loss of the speedup. The cleaner fix lives in the checkpoint: `preprocess` should honour its own `do_rescale` / `do_normalize` kwargs, after which this override can be deleted entirely. I am happy to drop the override and gate the feature on that instead if reviewers prefer.

Reproducing the `b37da04a78014080` output on `NVIDIA-Nemotron-Parse-2.0` additionally requires the tied-`lm_head` fix (#60272, a re-land of #53020); without it that checkpoint's output head is randomly initialized and the server emits garbage while reporting healthy. That fix is independent of this change and was applied only for the validation runs above.

Not covered: CUDA only (`forward_xpu` / `forward_oot` are untouched and untested); one image per request, which is this model's `get_supported_mm_limits`.

🟡 (optional) NemotronParseMultiModalProcessor._call_hf_processor decides to build the raw uint8 canvas purely from the merged do_rescale/do_normalize kwargs, never checking whether mm_device_do_normalize is actually enabled. If a caller sets mm_processor_kwargs do_rescale=False/do_normalize=False while mm_device_do_normalize is off (e.g. --no-mm-device-do-normalize), the override still returns a raw uint8 canvas, but self.input_norm is IdentityInputNorm (just a dtype cast), so the encoder gets unnormalized pixel data with no error. Fix: gate the canvas shortcut on the model's multimodal_config.mm_device_do_normalize flag itself, not only on the resulting do_rescale/do_normalize values, so it only fires when the device-norm feature is truly active.

<details>
<summary>Why this was flagged</summary>

Trigger: a request or server config sets mm_processor_kwargs={'do_rescale': False, 'do_normalize': False} while --no-mm-device-do-normalize is in effect (or the checkpoint's supports_mm_device_do_normalize path is otherwise disabled). _call_hf_processor (nemotron_parse.py:454-465) only inspects merged_kwargs['do_rescale']/['do_normalize'] via get_merged_mm_kwargs, not multimodal_config.mm_device_do_normalize. It then builds a uint8 HWC canvas and skips the real preprocess. build_mm_input_norm (mm_input_norm.py:349) returns IdentityInputNorm when mm_device_do_normalize is False, so _process_image_input (nemotron_parse.py:686) only casts dtype, no rescale/normalize. The encoder silently receives raw 0-255 pixel values instead of normalized floats, producing incorrect/garbage output with no exception, whereas on base branch do_rescale/do_normalize had no effect at all since the remote processor ignores them and always normalized correctly.

**Verification:** nit. The code path is real and demonstrable. `_call_hf_processor` (nemotron_parse.py:454-465) decides to build the uint8 canvas purely from `not merged_kwargs.get("do_rescale", True)` and `not merged_kwargs.get("do_normalize", True)`, never checking `mm_device_do_normalize`. `merge_mm_processor_kwargs` (config/multimodal.py:724-734) forces those two flags to False only when `self.mm_device_do_normalize` is truthy; when device-norm is off a user's explicit `mm_processor_kwargs={'do_rescale': False, 'do_normalize': False}` passes through unchanged.

</details>
