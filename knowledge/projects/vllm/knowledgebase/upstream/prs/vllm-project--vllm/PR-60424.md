# [HiSparse] Reserve and bound prefill staging memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/60424) · state: closed · merged: False

## Original PR description

**Closing: not worth the complexity.** Measured on a real model, the staging memory this PR reserves is not what limits HiSparse, and main does not crash in this scenario.

Investigated for scenario 2 of #60420: a long prompt whose KV spills to host, e.g. a 1M-token prefill misrouted to a HiSparse decoder.

**What it did:**
- Reserved HiSparse prefill staging in the shared workspace and split prefills into groups that fit.
- Bounded the `ensure_gpu_sources` temporaries by chunk size.
- Wrote mixed decode/prefill outputs in place.

**Result:** GLM-5.3-NVFP4 TP4, 4×B200, util 0.90, 24 decodes plus one 1.04M-token prompt. The prompt was forced to spill (`--num-gpu-blocks-override 160000`), and staging ran on every layer. The table shows the largest per-step peak above the profiled peak:

| main | + reserved staging | + bounded temporaries | + in-place outputs |
|---|---|---|---|
| +0.88 GiB | +0.88 | +0.66 | +0.67 |

All four completed; none OOMed.
- Staging copies one layer at a time (about 0.55 GiB at 1M tokens). The step peak is set elsewhere, so reserving staging does not lower it.
- Only the bounded temporaries help, and only by 0.22 GiB, against roughly 18 GiB of unused headroom at util 0.90.
- An earlier revision of this description claimed +1.53 → +0.57 GiB on the real model. Those runs never staged anything: the GPU KV pool held the whole prompt, so the claim was wrong.

The one reproducible crash (a 4-layer dummy model at util 0.97, OOM in the decode/prefill `torch.cat`) happens with all KV on GPU. #60417 fixes that.

Outputs were bit-identical to main (FlashInfer fp8, FlashMLA BF16, FA4) and unit tests passed on B200, but neither is a reason to land this. The DBO workspace issue found during review is filed separately.
