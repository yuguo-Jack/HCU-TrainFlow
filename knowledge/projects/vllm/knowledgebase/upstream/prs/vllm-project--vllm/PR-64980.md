# [Perf] W8A16 skinny GEMM for block-FP8 linear layers at 1-4 tokens on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/64980) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On H100 / H200, a block-scaled FP8 linear layer (128x128 weight blocks, e.g. `Qwen/Qwen3-8B-FP8`, the FP8 projections of Qwen3.5/3.6 MoE) runs `dynamic_flashinfer_deepgemm_blockscale_gemm`, which for a few tokens means FlashInfer's swapAB FP8 GEMM: quantize the BF16 activation to FP8 (`scale_1x128_kernel`), then a W8A8 GEMM. At one token this path reads the weight at 1.8-3.4 TB/s, and the extra quantization kernel adds about 1.7 us per layer.

This PR adds a W8A16 skinny GEMM for that case, written in CuTe DSL next to the BF16 skinny GEMM from #62956 and sharing its config class, compile cache and warmup registration (factored into a small base class):

- BF16 activation, FP8 E4M3 weight, one FP32 scale per 128x128 block, FP32 accumulation, BF16 output. The activation is not quantized.
- It reads the weight and scale tensors the FlashInfer / DeepGEMM path already keeps (row-major `(N, K)` FP8 and row-major `(N/128, K/128)` FP32 on SM90), so there is no extra memory and no new weight layout.
- `dynamic_flashinfer_deepgemm_blockscale_gemm` calls it when `SM90_SKINNY_FP8_GEMM_PLANS` has an entry for the weight shape and the token count, and the tensors have that layout. Everything else (other token counts, shapes, devices, batch-invariant mode) takes the existing path. The op runs eagerly inside the custom op, so the choice uses the runtime token count and is not frozen by `torch.compile`.
- Planned configs are registered from `process_weights_after_loading` and compiled by the CuTe DSL warmup before CUDA graph capture.

## Claims

- **E2E, H200, one request:** median TPOT -13.1% on Qwen3-8B-FP8 (4.41 -> 3.83 ms), -7.3% on Qwen3.6-35B-A3B-FP8 (3.95 -> 3.66 ms), -20.3% on Qwen3-4B-FP8 (3.61 -> 2.88 ms), -13.7% on Qwen3-14B-FP8 (6.60 -> 5.69 ms). Two requests: -1.0% (Qwen3-14B-FP8) to -10.2% (Qwen3-4B-FP8). Four and eight: unchanged within run-to-run spread.
- **`Qwen/Qwen3-32B-FP8` (added after opening; its cells are 1-token only):** median TPOT -12.6% at one request (12.902 -> 11.272 ms), unchanged at 2, 4 and 8 requests (FlashInfer path as before).
- **Accuracy:** per cell the output is closer to the dequantized FP32 reference than the W8A8 path (max error 2-3e-3 vs 2-3e-2 of the output scale), since the activation is not quantized. GSM8K 5-shot (1319 questions, greedy, 2 concurrent requests so decode runs the planned kernels) on Qwen3-8B-FP8, three rounds each with the GPUs rotated: W8A8 path 0.8893 / 0.8848 / 0.8848, this PR 0.8825 / 0.8802 / 0.8848 (means 0.8863 and 0.8825); the BF16 `Qwen/Qwen3-8B` on the same harness scores 0.8886 / 0.8893. The difference is inside the harness's round-to-round spread.
- **Kernels:** 35 plan cells, 1.15x-2.74x faster than the FlashInfer path with a cold L2.

## Details

- **4 tokens checked inside the model.** The isolated benchmark does not always predict the model at 4 tokens (seen with the BF16 skinny GEMM in #64979), so every 4-token cell was also checked with an nsys trace of 4 concurrent requests, summing the block-FP8 linear kernels per decode step (FlashInfer path = `scale_1x128_kernel` + `fp8_gemm_kernel_swapAB`). Qwen3.6-35B-A3B-FP8: 1420 -> 1061 us per step (160 GEMMs, 120 of them on the skinny kernel at 4 tokens), decode step 4673 -> 4534 us. Qwen3-4B-FP8: 2116 -> 2035 us per step (the o_proj cell; 36 GEMMs on the skinny kernel). Both kept. The remaining 4-token candidates lost in isolation and are not listed.
- **Why not the existing FP8 Marlin W8A16 path.** `prepare_fp8_layer_for_marlin` + `apply_fp8_marlin_linear` on the same block-FP8 weights (block scales expanded to group scales, repacked copy) measured 0.86x-1.01x of the FlashInfer path on H200 at 1-8 tokens for these shapes (e.g. Qwen3-8B o_proj 11.8 -> 11.7 us, QKV 12.8 -> 14.5 us), so switching the small-batch dispatch to Marlin would not help and would cost a second weight copy. A tensor-core (`mma.sync`) variant of this kernel without a weight relayout was also tried and stayed at 1.6-3.0 TB/s because of its strided per-warp access pattern; the SIMT kernel here reaches 2.1-3.6 TB/s at 1 token.
- **Kernel.** One CTA computes 1-4 outputs of one 128-row scale block; threads stride over K in 8- or 16-wide FP8 vectors (one scale block per vector), BF16 activations are read in 128-bit vectors, partial sums are reduced per warp and across warps through shared memory. PDL wait / launch-dependents as in the BF16 kernel.
- **Numerics depend on the token count.** At 1-4 tokens a planned layer skips the activation quantization, so its output differs from the W8A8 kernels at the rounding level (and is closer to the dequantized weights). The dynamic op already switched kernels at M = 32; `VLLM_BATCH_INVARIANT=1` keeps the existing behaviour (DeepGEMM only), as before.
- **Dispatch location.** The branch lives inside `dynamic_flashinfer_deepgemm_blockscale_gemm` because the token count must be read at run time: a Python branch in `apply_weights` would be specialized by `torch.compile`. That op is the SM90 default for block-FP8 layers; the DeepGEMM-only and CUTLASS kernels quantize the activation before their op and are unchanged.
- **Scope.** SM90 only (Blackwell keeps a packed UE8M0 scale layout and other kernels). TP=1 local shapes. MoE expert weights go through the fused MoE kernels and are not affected. Block-FP8 layers on other backends (CUTLASS, Triton, DeepGEMM-only) are unchanged.
- **H100.** Plans are keyed by capability `(9, 0)` and were measured on an H200 only.
