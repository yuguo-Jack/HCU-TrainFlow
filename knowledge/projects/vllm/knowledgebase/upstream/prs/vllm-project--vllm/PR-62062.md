# [Bugfix][Spec Decode] Keep data_parallel_index in DFlash/DSpark draft configs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62062) · state: open · merged: False

## Original PR description

## Purpose

With dense (independent) data parallelism, every DFlash/DSpark drafter on a node shares one torch.compile cache directory, so a cached restart loads artifacts compiled on another replica's GPU and crashes (`CUDA driver error: invalid argument` in the draft's compiled graph).

The draft parallel config is built with `replace(parallel_config, ...)`, which re-derives the `init=False` field `data_parallel_index` from `data_parallel_rank` (0 on independent DP ranks). Fix: copy the target's `data_parallel_index` into the DFlash and DSpark draft parallel configs. (Keeping the field across `replace` in `ParallelConfig` itself would be a broader alternative.)

## Test Plan

`pytest tests/v1/worker/test_dspark_utils.py`. E2E on H200: `vllm serve Qwen/Qwen3-4B --data-parallel-size 2` with `RedHatAI/Qwen3-4B-speculator.dspark`, cold then cached start: main writes only `rank_0_0/dspark_head` and the cached start crashes; with this change both replicas get their own draft cache dir and both starts serve.

AI assistance (Claude) was used; all changes were reviewed by the submitter.

- Siquan-Li · comment · 2026-10-18T10:57:45Z · [source](https://github.com/vllm-project/vllm/pull/62062#issuecomment-6249008332)

Following up from the analysis in #62285 (which we filed with partially incorrect scoping — correcting it here and consolidating, thanks for the patience).

While tracing the same mechanism end-to-end, we believe one more site still resets `data_parallel_index` to 0, with a narrower scope than we first claimed:

1. `SpeculativeConfig.create_draft_parallel_config` (`vllm/config/speculative.py:1726` on main) builds a **fresh** `ParallelConfig(...)`, copying only pp/tp/EP/backend fields. `data_parallel_rank` defaults to 0, so `draft_parallel_config.data_parallel_index == 0` from birth on independent dense DP ranks.

2. Its consumer, `StandaloneARSpeculator.load_draft_model` (`vllm/v1/worker/gpu/spec_decode/standalone_ar/speculator.py:101`), then does `replace(spec.draft_parallel_config, rank=...)`, which re-derives the index to 0 again. The standalone draft model (`method="draft_model"`) is therefore constructed under a config whose `data_parallel_index` is 0 on every replica.

**Scope correction vs. what we wrote in #62285:** this residual site does **not** affect DFlash/DFlash2/DSpark — DFlash overrides `load_draft_model` and builds via `load_dflash_model(target_model, self.vllm_config)` (so it uses the config this PR fixes), and DSpark is covered by this PR as well. Only the standalone `draft_model` method goes through the chain above.

**Suggested fix** (one line in `load_draft_model`, after the `replace(...)`):

```python
draft_vllm_config.parallel_config.data_parallel_index = (
    self.vllm_config.parallel_config.data_parallel_index
)
```

We have not yet produced a standalone repro through `method="draft_model"` + DP>1 — flagging the site based on code-path analysis since it shares the exact mechanism this PR fixes. Happy to run `method="draft_model"` + DP=2 on our H100 testbed and report back if that would help.
