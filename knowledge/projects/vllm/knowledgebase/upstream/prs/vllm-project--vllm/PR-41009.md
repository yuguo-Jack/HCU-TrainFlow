# Use nested compile_factors in config hashing

[Upstream PR](https://github.com/vllm-project/vllm/pull/41009) · state: closed · merged: False

## Original PR description

This PR addresses one narrow part of #39479: when collecting dataclass hash factors, check whether a nested field value exposes `compile_factors()` before normalizing it.

This keeps nested config objects from being treated as plain dataclass/value blobs when they already define their own compile-sensitive factor list.

I noticed #40246 covers a broader refactor in the same area, so I am opening this as draft. If maintainers prefer the broader PR, this can be closed; if a smaller CPU-only slice is useful, this PR keeps the change and test focused.

The implementation of `SupportsCompileFactors` support in `get_hash_factors` is shallow and does not correctly handle nested objects within containers or deeper levels of nesting.

Since `normalize_value` is recursive but currently unaware of the `SupportsCompileFactors` protocol, any object implementing this protocol that is nested inside a container (e.g., a list of sub-configs) will have its `compile_factors()` ignored. Instead, `normalize_value` will either use default dataclass field iteration or raise a `TypeError` if the object is not a dataclass.

To ensure consistent behavior across all levels of nesting, the `isinstance(..., SupportsCompileFactors)` check should be moved into `normalize_value` (ideally before the `is_dataclass` check). This allows `get_hash_factors` to be simplified back to a single `normalize_value(value)` call while providing full recursive support for the protocol.
