# [Model][Engram] Share Engram via RDMA to reduce DRAM redundancy cross instances

[Upstream PR](https://github.com/vllm-project/vllm/pull/64395) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Summary

DeepSeek V4.1 P/D deployments can hold a large immutable Engram table separately in every model instance. This draft adds an opt-in provider seam so instances can fetch selected rows from a shared host table, while the existing local-table path stays the default.

The prototype uses explicit GPU-initiated RDMA GET into local GPU buffers. The owner, checkpoint loader/validator, lease control, reader and provider now ship in vLLM; the NIXL GPU GET transport remains a separately built dependency. Public NIXL main does not currently provide the GET implementation used here: [NIXL #2544](https://github.com/ai-dynamo/nixl/pull/2544) is an interface draft, not that implementation. The tested ABI-3 shim can be built from the [legacy NIXL research snapshot](https://github.com/foraxe/nixl/tree/b5322e46f6e686ff16bdb3afb8a1a940a64e1163/research/vllm_engram_repro); it is not a supported current NIXL API.

This is related to [#64002](https://github.com/vllm-project/vllm/issues/64002) and [#64082](https://github.com/vllm-project/vllm/pull/64082). Their scale-up/shared-address designs and this explicit scale-out GET have different memory semantics. Metadata-only table parameters and checkpoint filtering overlap and would need reconciliation if either proposal lands first.

## Changes

- Bundle a checkpoint-backed table owner, lease control, reader and opt-in provider, and use metadata-only parameters while filtering remote table tensors before lazy checkpoint materialization.
- Support eager execution and experimental **breakable PIECEWISE** CUDA graphs. Remote GET runs at an eager graph boundary; FULL graphs are rejected. P-side prefill batches that require graph padding fall back to an exact-size eager path.
- Permit remote lookup prefetch to overlap decoder work. The remote producer follows the native bounded-replay policy by default; `rdma_keep_prefill_rows` retains all rows for conservative comparison.
- Retire readers at normal worker shutdown. Forced termination, in-flight cancellation and recoverable transport errors remain open.

This is experimental CUDA/DeepSeek V4.1/DP1 integration. Its CUDA serving measurements used single-threaded lazy safetensors loading. The generic per-tensor loader filter also supports threaded lazy loading and secondary sources; these additions have separate loader tests and support the Ascend integration in [vLLM-Ascend #20612](https://github.com/vllm-project/vllm-ascend/pull/20612). They do not change the CUDA transport or turn this into a supported NIXL GET API or production-ready storage service.

## Validation

H20 serving performance tests used source `bc49ec16216942c7d844ab544f565ec3fec479be`, before the later loader additions and main merges. They used one READ lane per TP rank with vLLM's prefetch stream; these measurements do not cover the separate SGLang QP16/read-plan path. The serving performance curves have not been rerun on the current PR head. Both performance experiments used the same DeepSeek V4.1 Flash checkpoint, TP4 per role, 512 input / 64 output tokens, disabled prefix caching, remote prefetch and piecewise graphs where supported. Each table entry below is the median of three per-round values; the local and shared arms ran sequentially.

### 3P1D serving

Three independent P instances and one D instance ran on two H20 hosts, two TP4 instances per host, with round-robin P routing. The shared arm used one immutable 188.83 GiB host table. This two-host layout includes shared CPU and NIC contention and is not a four-host production deployment.

| Client concurrency | Local TTFT p50 ms | Shared TTFT p50 ms | Local / shared output tok/s |
| ---: | ---: | ---: | ---: |
| 1 | 156.80 | 156.31 | 49.3 / 50.6 |
| 8 | 276.89 | 275.88 | 302.0 / 306.1 |
| 32 | 709.86 | 749.79 | 723.8 / 724.8 |
| 64 | 1099.57 | 1151.69 | 1059.1 / 1057.8 |
| 128 | 1596.57 | 1598.54 | 1488.0 / 1507.1 |

Both arms completed 2640/2640 measured requests. At C128, the median of round-level TTFT p99 was 2572.07 ms local and 2675.66 ms shared. Three sequential rounds do not establish a stable tail difference. Four local table copies versus one shared owner suggests approximately 566.49 GiB of table storage could be avoided, before auxiliary costs; this is an estimate, not a measured net system-memory saving.

### 1P1D serving and row correctness

In a separate TP4 P/TP4 D sweep at client concurrency 1, 4, 8, 16, 32, 64 and 128, shared versus local TTFT p50 ranged from -1.2% to +3.3%. Shared completed 2808/2808 measured requests; local completed 2807/2808 after one proxy connection failure. At C128, median round-level TTFT p99 was 7809.96 ms shared versus 7362.19 ms local.

Real-checkpoint reader checks compared 512 distinct rows per layer against the native Engram kernel bit-for-bit. A fresh cross-node lifecycle check used the PR's example provider and actual checkpoint rows: three reader create/close cycles each enqueued 16 interleaved reads over both Engram layers and two CUDA streams, closed before an explicit device synchronize, compared 128 packed outputs byte-for-byte (including invalid/padding IDs), rejected lookup after close, and restored the owner lease count. A separate initialization-failure probe verified that an already acquired owner lease is released when checkpoint setup fails. These checks cover specific cases, not arbitrary cancellation or a proven in-flight failure.

The earlier eager-only integration at `5763d12128` matched eight fixed greedy canaries across local and remote modes. Other Graph and concurrent runs showed generated-output variation even across native-table repeats. In the 3P1D C1 same-seed run, local/shared text hashes matched 13/24; an earlier native/native repeat matched 11/24. This does not rule out remote-specific differences. Model-quality, chunked-prefill numerical equivalence and general correctness are not yet established.

The actual provider's isolated bad-key test surfaced a device-side assertion and poisoned its CUDA context. It is not recoverable per-request handling. An earlier shutdown drain timeout was also observed; forced worker termination can retain an owner lease.

### Bundled owner and reader follow-up

The owner, lease control and reader do not require external SGLang Python modules. The full-owner 1P1D lifecycle below was tested at `b428a4564e`; the earlier signed commit `b44670606a` has the identical source tree. The current head `cc24fa52d0` consolidates the implementation and retains only the supported row264 layout. The only external part of this prototype path is the separately built experimental NIXL/DOCA GPU GET shim. The checked-in [setup and verification example](examples/disaggregated/engram_rdma/README.md) includes an optional tiny synthetic checkpoint generator and owner/reader commands.

- At `cc24fa52d0`, **11/11** consolidated owner checkpoint, lease control and reader initialization-failure tests passed on H20; the fake-provider GPU adapter check passed, including rejecting invalid row widths. A fresh small-checkpoint owner/reader run passed cross-node exact-row, 514-query, alternating-stream and normal lease-release checks; the full-checkpoint reader also passed the same row and stream checks.
- A newly started bundled owner and bundled reader on separate H20 nodes verified both synthetic checkpoint layers, invalid/padding rows and the 514-query boundary against checkpoint bytes. The reader returned its lease, then the owner drained, deregistered and exited normally. A separate bundled-reader test matched both layers, 514-query boundary and 16 alternating-stream queued reads against a preserved real checkpoint owner, then restored its lease count.
- A real DeepSeek V4.1 Flash TP4 single-instance request generated 16 output tokens using the bundled provider and an existing same-node owner. That model smoke preceded the final output-width guard and owner logging-only cleanup; those follow-up changes were independently covered by the adapter and owner tests. This is not a cross-node P/D or model-quality validation.
- A fresh bundled owner loaded and registered the full 188.83 GiB checkpoint. A real DeepSeek V4.1 Flash TP4+TP4 **1P1D** smoke using the bundled provider on both nodes produced 16 output tokens; the text matched the same prompt with the previous owner. After normal P/D shutdown the owner observed 8 attaches and 8 releases, then deregistered and exited with zero leases. The five bundled source modules matched commit `b428a4564e` by SHA-256 on both nodes. Engram rows used RDMA GET; the separate KV connector used TCP with `MC_FORCE_TCP=1` because these hosts lack the DMA-BUF capability needed by its RDMA path. This is one short functional request, not a performance comparison or model-quality result. Earlier KV startup failures and an occupied bootstrap port were resolved by this configuration; failed starts may leave owner leases retained.
- At `cc24fa52d0`, a fresh 1P1D TP4+TP4 smoke using the refactored provider and a retained real-checkpoint owner produced 16 tokens and matched the previous functional canary. The three refactored implementation files matched the tested sources on both nodes. It used the same RDMA Engram/TCP KV setup; this is not a benchmark or model-quality result.

The owner control protocol is not authenticated or encrypted; its ready file includes memory keys. Use a trusted network and protect metadata. Crash cleanup, automatic lease recovery and recoverable transport failure are not implemented; do not force-release a lease while GPU/NIC work may still be outstanding.
