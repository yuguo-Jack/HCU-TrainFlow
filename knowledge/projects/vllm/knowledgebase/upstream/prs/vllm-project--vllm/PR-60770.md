# [Bugfix][Frontend] Accept newline-separated parallel Hermes tool calls under tool_choice="required"

[Upstream PR](https://github.com/vllm-project/vllm/pull/60770) · state: open · merged: False

## Original PR description

## Purpose

FIX #60769

With `--tool-call-parser hermes` and `tool_choice="required"`, the structural tag joins tool calls with an empty separator. Hermes-style chat templates (Qwen2.5, QwQ, Qwen3, NousResearch Hermes 2 Pro / 2 Theta / 3 / 4) render a newline between parallel calls (`</tool_call>\n<tool_call>`), and Qwen3-0.6B and Qwen2.5-1.5B-Instruct write that newline under `auto`. The grammar masks it while still allowing EOS at the same position, so greedy decoding ends after the first call: a request that needs two or three calls returns one. The Python and Rust frontends build the same grammar.

This PR accepts either a newline or nothing between `required` calls (one framing per response): an `Or` of the newline-separated list and the existing back-to-back list, sharing the same tags. Back to back stays accepted because at least one hermes-parser template renders calls that way (vLLM's hermes CI adapter `minpeter/LoRA-Llama-3.2-1B-tool-vllm-ci`). Text between calls is still rejected.
- Python: `get_hermes_structural_tag` in `vllm/tool_parsers/structural_tag_registry.py` passes both separators to the shared `_hermes_style_structural_tag` helper. LongCat, which uses that helper since #60747, keeps its back-to-back-only list.
- Rust frontend: `HermesToolParser::build_visible_format` wraps the list from the shared Hermes builder in the same `Or` (the builder lives in the `xgrammar-structural-tag` crate; the same change there would let this override go).

Scope:
- Named tool choice and `parallel_tool_calls=false` are unchanged: they stop after the first call, and a second call is rejected with either separator (tests below).
- Reached by the change, as intended: Chat Completions and Responses `required`; the Anthropic Messages API's `tool_choice: {"type": "any"}`, which maps to `required`; and, on the Python frontend, `auto` with a strict tool (or `--tool-strict-level function`/`parameter`) plus a `response_format`, which reuses the `required` list inside its `Or` and had the same dropped-call bug (reproduced on Qwen2.5-1.5B-Instruct and Hermes-3-Llama-3.2-3B: 1 call instead of 2; 2 with this change, measured with its newline-only first version, which generates the same tokens on those prompts). `auto` without `response_format` is unchanged; the Rust frontend has no `auto` + `response_format` tool path.
- Grammar cost of the `Or` (xgrammar 0.2.8, Qwen3 tokenizer, `required` with 1 to 64 tools): expanded EBNF +11% to +14% characters and compiled grammar +0.4% to +1.0% bytes when the tools are non-strict or share one argument schema; with distinct strict schemas, +1% to +4% characters and +0.1% to +0.3% bytes at 4 to 64 tools. Compile time differed by no more than host noise (medians of 15 interleaved fresh compiles at 16 and 64 tools: 1.04x to 1.23x across two runs on a shared host).
- Pre-existing and unchanged: the Rust frontend's Hermes parser returns the whitespace between parallel calls as message content. With this change, Rust-frontend `required` responses that contain several calls carry `content: "\n"` (`"\n\n"` for three calls), as `auto` responses with several calls already do on main. The Python frontend returns empty content. I left that for a follow-up.

Found while validating #52841 (ERNIE 4.5 parsers for the Rust frontend), which reuses the Hermes builder. ERNIE's framing needs a different allowance (newline runs before, between and after calls), which #52841 handles itself; this change does not cover it.

Alternatives considered:
- A newline-only separator: rejects templates that write calls back to back, such as the CI adapter above, which is the same failure in reverse.
- Triggered tags for `required`, as xgrammar's builtin `qwen_3` builder does: admits free text between calls, a broader change to `required` semantics than this bug needs.

Not a duplicate: on 2026-10-09, `gh search issues` and `gh search prs` in vllm-project/vllm for "hermes required tool_choice parallel", "hermes structural tag separator", "tool_choice required parallel tool calls dropped", "structural_tag_registry hermes", "required tool_choice only first tool call", "hermes parallel_tool_calls", "Qwen3 tool_choice required multiple tool calls" and "parallel tool calls structural tag newline" return nothing for this bug. "tags_with_separator" returns related but different work: #55152/#55153 (guidance backend and new-format structural tags), #54808 (qwen3_coder/qwen3_xml ignoring `required`), #59190 (Kimi K3 grammar) and #59393 (grammar snapshots, merged).
