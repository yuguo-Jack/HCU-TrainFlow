# [Frontend] Add `srt` and `vtt` response formats for audio transcription/translation

[Upstream PR](https://github.com/vllm-project/vllm/pull/60336) · state: open · merged: False

## Original PR description



## Overview

Add the `srt` (SubRip) and `vtt` (WebVTT) `response_format` options to
`/v1/audio/transcriptions` and `/v1/audio/translations`, as in the
[OpenAI Audio API](https://platform.openai.com/docs/api-reference/audio/createTranscription).
Part of #25750 (claimed in [this comment](https://github.com/vllm-project/vllm/issues/25750#issuecomment-5884561428), no reply from the previous authors).

Continues #36966 by @majiayu000 (srt + vtt, auto-closed as stale on Sep 24) and
#46680 by @monish-rgb (srt only, needs-rebase since Jul 3, marked stale on Oct 2).
Both are credited as co-authors. This is the only open PR covering both formats on current `main`.

## Claims

- `response_format=srt` / `vtt` return subtitles rendered from the same segments as `verbose_json` (timestamp tokens + logprobs via `_get_verbose_segments`), as a `text/plain` body. No model-level changes.
- Same restrictions as `verbose_json`: the model must support segment timestamps (400 otherwise), and `stream=True` is rejected.
- Timestamps are exact: `round(seconds * 1000)` + `divmod`, so `11.54 s` renders as `00:00:11,540` (the `int((s % 1) * 1000)` approach in #36966 gave `,539`) and rounding never emits `,1000`.
- Cue text is sanitised: `-->` becomes `->`; VTT escapes `&` and `<`.

## Validation

```bash
# formatter unit tests, no GPU
pytest tests/entrypoints/speech_to_text/test_subtitle_formats.py
# e2e, whisper-large-v3-turbo
pytest tests/entrypoints/speech_to_text/transcription/test_transcription_validation_whisper.py -k "srt or vtt or subtitle"
# e2e, whisper-small (and gemma-3n for the 400 case)
pytest tests/entrypoints/speech_to_text/translation/test_translation_validation.py -k test_audio_srt_format
```

The `gemma-3n` parametrisation of the translation test (expects a 400) was not run locally; it runs in CI with the rest of `tests/entrypoints/speech_to_text`.

Manual run on `openai/whisper-large-v3-turbo` (RTX 4000 Ada) against both endpoints with a 15.9 s clip and a 48.8 s clip (chunked at 30 s), comparing word counts with `response_format=json`:

| endpoint | clip | cues | words srt/vtt | words json | timestamps |
|---|---|---|---|---|---|
| transcriptions | 15.9 s | 1 | 37 | 37 | 0.00 → 15.64 |
| transcriptions | 48.8 s (2 chunks) | 5 | 111 | 111 | 0.00 → 48.02, monotonic |
| translations | 15.9 s | 1 | 37 | 37 | 0.00 → 15.64 |
| translations | 48.8 s (2 chunks) | 1 | 37 | 66 | 29.50 → 48.02 |

`Content-Type` is `text/plain`, SRT cues are numbered from 1 across chunks, VTT starts with the `WEBVTT` header.

## Details

- `base/serving.py`: the `verbose_json` branches now key on `_SEGMENT_FORMATS = {"verbose_json", "srt", "vtt"}`; after segment aggregation the srt/vtt case returns a `str` instead of building a JSON response.
- `base/subtitle_formats.py` (new, ~50 lines): one timestamp formatter parameterised on the millisecond separator, plus `segments_to_srt` / `segments_to_vtt`.
- The two routers return `PlainTextResponse` when the serving layer yields a `str`.
- Docs: `docs/serving/online_serving/speech_to_text.md` lists the new formats.

**Known limitations.** Both come from the existing segment path and affect `verbose_json` the same way:

- On the chunked translation run the first chunk produced no closed timestamp segment and is missing from the output (`verbose_json` returns the same single 29.50 → 48.02 segment). This is #58029 / #53144; `srt`/`vtt` will follow the fix there (#53145).
- With the `foscolo` clip on `whisper-small` in translate mode the model emits no timestamp token at all, so `verbose_json`, `srt` and `vtt` all return an empty body. Filed as #59345. The translation e2e test therefore uses `mary_had_lamb`.

AI assistance (Claude) was used for the port, the timestamp fix, the tests and the docs. All changes were reviewed by hand.
