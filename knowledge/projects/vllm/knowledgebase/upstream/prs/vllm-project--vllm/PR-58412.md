# [Bugfix][Reasoning] Handle multi-token streaming deltas in the Hunyuan A13B parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/58412) · state: open · merged: False

## Original PR description

## Purpose

Fix a crash (and silent output loss under `python -O`) in streaming responses
when `--reasoning-parser hunyuan_a13b` is used together with any feature that
emits more than one token per generation step (speculative decoding, MTP).

No issue was filed for this; it appeared while auditing the streaming paths of
every reasoning parser for unhandled input shapes. Happy to file one if you
prefer that as the tracking entry.

## Problem

`HunyuanA13BReasoningParser.extract_reasoning_streaming()` assumed one token per
streaming delta:

```python
assert len(delta_token_ids) == 1
# Process each token in the delta
token = delta_token_ids[0]
```

The engine calls the parser once per generation step and passes the step's token
ids:

```python
# vllm/entrypoints/openai/chat_completion/serving.py
delta_message = parser.parse_delta(
    delta_text=delta_text,
    delta_token_ids=as_list(output.token_ids),
    ...
)
```

A step carries several tokens when speculative decoding or MTP is enabled, so
`len(delta_token_ids) > 1` reaches the parser and the assertion fires:

```
AssertionError
```

That surfaces as a failed request / broken stream. With `python -O` the
assertion is compiled out instead, and the parser processes only
`delta_token_ids[0]` while `delta_text` still describes the whole delta — so the
remaining tokens are silently dropped from the response.

Reproduced by driving the parser directly, feeding the same token ids in slices:

```
before:  delta size  1: reasoning= 11 content=  7  ok
         delta size  2: reasoning=  0 content=  0  AssertionError
         delta size  5: reasoning=  0 content=  0  AssertionError
after:   delta size  1: reasoning= 11 content=  7  ok
         delta size  2: reasoning= 11 content=  7  ok
         delta size  5: reasoning= 11 content=  7  ok
```

## Solution

Iterate the delta's tokens through the existing per-token state machine and
combine the emitted parts into one `DeltaMessage` (or `None` when nothing is
emitted, as before).

- Per-token text is decoded from the token ids when a delta holds more than one
  token, following the convention already used elsewhere in the tree
  (`MiniMaxM3ReasoningParser._decode_text` decodes token ids the same way).
- A single-token delta keeps using the engine's `delta_text` unchanged, so
  existing behaviour is preserved exactly.
- Empty deltas return `None` early.

This matches how the rest of the codebase treats deltas: `basic_parsers`,
`ernie45`, `hy_v4` and `step3` guard with `len(delta_token_ids) == 1` before a
single-token shortcut, `minimax_m3` iterates every token, and
`deepseekv3_tool_parser` / `deepseekv31_tool_parser` have explicit
`len(delta_token_ids) > 1` branches.

## Compatibility

No behaviour change for single-token deltas, which is what the parser was
written for. Multi-token deltas previously raised; they now produce the same
output as the equivalent sequence of single-token calls.

**Edge cases.**

| input | result |
|---|---|
| empty delta (`delta_token_ids=[]`) | returns `None`; was uncovered, now tested |
| single token | unchanged, still uses the engine's `delta_text` |
| multi-token, ASCII | identical to the single-token feed at steps 2/3/7/100 |
| multi-token, byte-fallback boundary (emoji) | **was corrupt** — see below |
| delta longer than `current_token_ids` | no crash |
| malformed input | no exception raised on any row |

The byte-boundary row was a real defect in this PR's own new code.
`_iter_delta_tokens` derived each token's text as `cur_text[len(prev_text):]`, which
assumes `decode(ids[:n])` is a prefix of `decode(ids[:n+1])`. Token 222 of
`tencent/Hunyuan-A13B-Instruct` is the second fragment of 🚀, and the prefix
relation breaks exactly there:

```
decode(ids[:4]) ends '... rocket \ufffd'
decode(ids[:5]) ends '... rocket 🚀'
```

so the slice took the wrong text and an emoji in reasoning content came out as
`\ufffd`. Text ending in `\ufffd` is now withheld until the character completes —
the guard `detokenize_incrementally` already applies
(`vllm/tokenizers/detokenizer_utils.py:261`). `test_per_token_text_reconstructs_the_delta`
fails on the two astral payloads without that change, and `test_empty_delta_returns_none`
covers the branch the coverage run flagged.

Verified: 27 passed for the file (21 before), `ruff check` and `ruff format --check`
clean. An emoji payload cannot be asserted through the streaming-equivalence test —
its harness derives `delta_text` as `tokenizer.decode(delta)`, which is lossy for a
slice that ends mid-character — so the astral case is asserted against the helper
directly instead.

**Cross-provider / backend.** `_iter_delta_tokens` is private to this detector and
called only from `extract_reasoning_streaming`, so no sibling inherits it: the other
parsers override `extract_reasoning_streaming` themselves and the shared base is
untouched. Both streaming entrypoints pass multi-token deltas —
`chat_completion/serving.py:659` and `responses/serving.py:1220-1225` both use
`as_list(output.token_ids)` — and the parser framework forwards `delta_token_ids` at
`abstract_parser.py:715`, which is also where an empty delta can arrive. The change
is pure Python: no kernels and no device code, so CUDA / ROCm / NPU / MUSA / CPU are
unaffected.
