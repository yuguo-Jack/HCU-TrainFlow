[Upstream PR](https://github.com/vllm-project/vllm/pull/57785) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #57759

An eager break that queues asynchronous work on a **side CUDA stream** and returns without joining (e.g. the pinned-host PLE UVA prefetch launched by `start_prefetch` in `vllm/models/qwen4_exp/nvidia/ngram_embedding.py`) leaves that work in flight when a later capture segment calls `capture_end()`. Depending on timing, one of two things happens:

1. **Intermittent crash**: the capture is invalidated and all workers raise `torch.AcceleratorError: CUDA error: operation not permitted` at `capture_end()` (the `cudaErrorStreamCaptureUnjoined/Invalidated` family). This is load-dependent — it succeeds on an idle host and fails under host load, because host load slows the PCIe UVA reads and widens the race window. Observed on 4x L20 TP4 with `--engram-config '{"cpu_offload": true}'` and `--compilation-config '{"cudagraph_mode": "FULL_AND_PIECEWISE"}'`.
2. **Silent corruption** (found while writing the regression test): the side-stream kernels leak past the capture and interleave with post-capture work.

**Fix**: join all outstanding device work in the *legal* window — after the previous segment has ended and before the next `capture_begin()` — by calling `torch.cuda.synchronize()` at the top of `BreakableCUDAGraphCapture._begin_segment()`.

Two properties worth highlighting:

- **Placement matters**: the sync must live in `_begin_segment`, *not* `_end_segment`. `_end_segment` runs while the segment's capture is still active (the sync would then itself be illegal and fails deterministically — verified on a rig while developing this fix). Only the between-segments window is valid.
- **Zero steady-state cost**: breakable capture happens once at startup (`profile_cudagraph_memory` / capture phase); serving-path replay is untouched.

## Test Plan

New regression test `test_eager_break_side_stream_work_is_joined_before_next_capture` in `tests/v1/cudagraph/test_breakable_cudagraph.py` mimics the PLE prefetch pattern: the eager-break fn forks a side stream, queues 256–2048 async kernels, and returns **without joining back**.

```python
# regression test sketch (full test in the diff)
side_stream = torch.cuda.Stream()

def prefetch_like():
    side_stream.wait_stream(torch.cuda.current_stream())
    with torch.cuda.stream(side_stream):
        for _ in range(256):
            y.add_(1.0)   # no join back

cap = BreakableCUDAGraphCapture()
with cap:
    x.add_(1.0)
    cap.add_eager(prefetch_like)
    x.add_(1.0)  # unfixed: capture_end invalidated / kernels leak
```

## Test Result

Verified on L20 (driver 535.183.01, torch 2.13.0+cu130):

- **Unfixed code**: the regression test fails deterministically on the first run — the side-stream adds leak past the capture and corrupt post-capture zeroing (`518` instead of `256`, i.e. leaked kernels re-adding after the zeroing), no synthetic host load needed.
- **Fixed code**: the regression test passes; replay produces exact results across repeated runs.
- **End-to-end** (4x L20 TP4, Qwen3.8-Flash-Next-FP8 with `cpu_offload` + `FULL_AND_PIECEWISE`): patched build survives restarts under synthetic host load (CPU spinners + concurrent direct reads of the checkpoint) that reproduces the original production failure (`cudaErrorNotPermitted` at FULL capture 1/2 on all 4 workers); unpatched nightly failed under the same conditions.
- **Performance unchanged**: TPOT C1 12.3 ms / C16 26.9 ms, identical to unpatched (the sync is startup-only).

- quanliu1991 · comment · 2026-10-09T08:01:18Z · [source](https://github.com/vllm-project/vllm/pull/57785#issuecomment-6076941218)

Closing without merge.

Re-reading the code and re-running the experiments, this fix does not target the failure it claims to fix (see my closing comment on #57759):

- The reported crash is raised in the FULL `torch.cuda.graph(...)` branch of `cudagraph_utils.py`, which never calls `BreakableCUDAGraphCapture._begin_segment()`. A sync there cannot affect that path, and `torch.cuda.graph.__enter__` already synchronizes before `capture_begin`.
- In the breakable path, `start_prefetch` and `_finalize_prefetch` are both eager breaks, so fork and join both land in eager gaps. I could not make an unjoined-in-gap fork fail under any load in a standalone repro, so the extra `synchronize()` in `_begin_segment` is redundant rather than protective.
- @peakcrosser7's point about the regression test is also correct: the test as written has a race independent of graph capture and would not prove the fix.

I agree with @ZJY0516 that the breakable capture code should not be specialized for the prefetch pattern. If I get a reliable reproduction I will open a new PR with a fix that actually addresses the failing path.
