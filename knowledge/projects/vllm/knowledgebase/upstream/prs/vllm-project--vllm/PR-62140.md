# [Doc] Fix NGINX load balancer config: fail_timeout, streaming and keep-alive

[Upstream PR](https://github.com/vllm-project/vllm/pull/62140) · state: open · merged: False

## Original PR description

## Overview

The NGINX config in `docs/deployment/nginx.md` has three problems that show up when you serve real traffic through it. This PR fixes the config and adds a short note on each setting.

## Claims

- **`fail_timeout=10000s` turns a short outage into a ~2.8 hour one.** NGINX uses `fail_timeout` both as the failure window and as how long it keeps a failed server out. After 3 errors, a healthy vLLM server gets no traffic for 10,000 s. If every server fails at once, NGINX answers `502 no live upstreams` to every request for that long, even after the servers are healthy.
- **Streaming is buffered.** NGINX buffers proxied responses by default, and vLLM doesn't send `X-Accel-Buffering: no`. Streamed tokens reach the client in batches of about 4 KB (about 15 tokens) instead of one at a time, so the first token is late and the stream is choppy.
- **Missing keep-alive guidance.** vLLM closes idle connections after 5 s (`VLLM_HTTP_TIMEOUT_KEEP_ALIVE`). If upstream keepalive is turned on without a shorter `keepalive_timeout`, NGINX sometimes reuses a connection vLLM is closing, and the request fails with `502` (`Connection reset by peer`). Each such failure also counts towards `max_fails`, which feeds the first problem.

## Validation

A local reproduction with Docker and no GPU: two stand-ins for vLLM's OpenAI server (FastAPI and uvicorn with vLLM's 5 s idle keep-alive, streaming chunks shaped like vLLM's at one token every 20 ms), behind `nginx:1.27` (1.27.5). "Current" is the config in the docs today. "Proposed" is this PR's config, copied from the doc. It passes `nginx -t` and markdownlint.

| Test | Current | Proposed |
|---|---|---|
| Streaming, time to first token, 64-token answer (median of 20) | 364 ms | 27 ms |
| Streaming, time to first token, 512-token answer (median of 10) | 373 ms | 29 ms |
| One server down for 10 s, then back: traffic to it for the rest of the test (55 s) | none | its half, from the moment it was back |
| Both servers down for 5 s, then back: requests failing afterwards | all, to the end of the test (25 s) | none once `fail_timeout` expired, ~5 s later |
| Keep-alive race: bursts of 32 every ~5 s against a busy server, 270 s | 3 of 1,664 `502` (current config + `keepalive 32`) | 0 of 1,664 |

Notes:

- The keep-alive race is timing-dependent and rare locally. With an idle server, NGINX notices the close in time, so the stand-in's event loop is blocked in 50 ms slices to model an API server that's busy streaming many responses. It gave the same result, 3 of 1,664 vs. 0, in two separate runs. On real hardware (2x RTX 5090, Qwen2.5-7B-Instruct, vLLM 0.30.0, NGINX 1.27.5 with keepalive and `max_fails=1`), this mismatch produced 1,574 `502 no live upstreams` errors at 768 concurrent users while both vLLM servers were healthy, because a few resets marked both servers failed. With `keepalive_timeout 4s` and `max_fails=3 fail_timeout=10s`, the same sweep had 0 errors up to 1,024 users.
- The streaming delay depends on chunk size and decode speed. Faster decoding shrinks it, but tokens still arrive in batches.
- `fail_timeout=10s` is NGINX's default. `max_fails=3` is kept from the current doc.

Reproduction scripts, raw results and the chart code: <https://github.com/manuhalapeth/LLM-Inference-Ops/tree/main/upstream/vllm_nginx_docs>

## Details

- **Root cause:** each problem comes from an NGINX default or setting that doesn't fit long-lived, streaming LLM requests. `fail_timeout` controls both the failure window and how long a server stays out. `proxy_buffering` is on by default. And the idle timeout on NGINX's side of a keepalive connection has to be shorter than vLLM's, or the two race.
- **Tradeoffs:** a shorter `fail_timeout` means NGINX tries a truly dead server again sooner (one failed attempt per 10 s, and connection errors are retried on the next server). `keepalive` is optional. It's included with the right timeout because people commonly add it for performance and then hit the race.
- **Not a duplicate:** I found no open issue or PR about this config. #39738 adds HAProxy and renames this file to `loadbalancer.md`, but doesn't change the NGINX config. If it lands first, I'll rebase onto the new file.
- AI assistance was used for coding the reproduction and for drafting. I reviewed every changed line, ran every test above, and found the original problem while running my own vLLM deployment.
