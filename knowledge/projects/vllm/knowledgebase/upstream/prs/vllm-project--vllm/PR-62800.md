# [Bugfix] Fix KV cache pages for hybrid models with draft layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62800) · state: open · merged: False

## Original PR description

## Overview

This PR fixes how vLLM picks KV cache pages when a model mixes layer types, which is what speculative decoding with a draft model on a hybrid (attention plus linear-attention) target does. FlashInfer now chooses kernel pages per layer, padded manager pages can split into kernel pages, and hybrid block alignment counts the drafter's KV. It is independent of #62961, #62962, #62963 and #62964, and of #63279, which carries the FA4 dense warmup coverage that started in this PR.

## Claims

- FlashInfer kernel pages follow each layer's own query and KV head counts. An MHA draft layer next to a GQA target otherwise gets the target's large pages, and its metadata builder rejects them at startup.
- A padded manager page splits into uniformly strided kernel pages, and manager-page boundaries are kept. Interleaved layers and non-divisible padding still fail with a clear error.
- Hybrid block alignment includes the drafter's KV bytes per token. When a draft has more KV per token than the target, it sets the common page size, and every recurrent-state page is padded up to it. For a 64-layer Qwen3.5-style GDN model with a one-layer draft that is a 5.2x padding, and the KV pool holds about 61 concurrent requests of 2.5k tokens.

## Not a duplicate

I ran the duplicate-work searches from `AGENTS.md` §1 (open PRs, with keywords on kernel block size, padded pages, hybrid drafter block size and Mamba page padding). They found related work, and none of it makes the same fix. This PR uses no code from them.

- #58630 passes each layer's KV spec into kernel block-size selection. This PR fills in the query-head count that the FlashInfer check needs from that spec, so the two are complementary.
- #60252 and #58207 change how a hybrid model picks its group or block size. They leave the drafter's KV out of the alignment.
- #59297 (draft) moves kernel-block mapping into each attention group, with a per-group kernel-block stride. It is a larger refactor of the mapping that the padded-page split here relies on, and if it lands first, the split here becomes a stride choice in its mapping.
- #50169 fixes KV allocation for sliding-window drafters. This PR fixes the page alignment that a full-attention drafter on a hybrid target forces.

## Includes and credits

This PR contains no code from other open PRs.

## Details

- Query-head geometry is non-layout cache metadata (`compare=False`), so cache-spec equality and merging stay as they are. Both runners refresh it when they form attention groups. When the geometry is unknown or there is no config, the conservative small pages stay, so block-size planning that runs before the runners form groups stays conservative too.
- The alignment change builds a fresh spec for the draft, so the draft does not inherit the target's value-head dimension. Speculative-state reservations are unchanged.
- All GPU measurements are on B300.

- TheEpicDolphin · COMMENTED · 2026-11-02T03:28:42Z · [source](https://github.com/vllm-project/vllm/pull/62800#pullrequestreview-5731809086)

Although tracking `num_query_heads` in `AttentionSpec` is a straightforward way to address the issue for FlashInfer, I don't think it's the right long-term solution. `KVCacheSpec` properties should describe the memory layout of the KV cache, and q heads have no effect on that. It also gets dropped when specs are merged, since `FullAttentionSpec.merge` doesn't carry it over. #53002 avoided adding q heads to the spec for the same reason.

Metadata builders already get the number of q heads for an attention group from `get_num_attention_heads_from_layers`, which takes a list of layer names. I think the best direction is a `get_supported_kernel_block_sizes_for_layers(kv_cache_spec, layer_names)` method on `AttentionBackend` that defaults to `get_supported_kernel_block_sizes`, with FlashInfer overriding it to derive the num q heads. What do you think about this direction?
