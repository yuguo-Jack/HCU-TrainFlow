# [ROCm][MLA][DCP] Serve the non-causal DSpark draft on TRITON_MLA under DCP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64261) · state: open · merged: False

## Original PR description


## Overview

TRITON_MLA can now serve a non-causal multi-token MLA draft (DSpark) while the MLA KV cache is sharded by decode context parallelism (DCP), on gfx942 (CDNA 3). This is a follow-up to #54546 by @YukioZzz, who asked us to take it over. His two commits are kept as authored by him, and he is co-author on ours. The PR needed more than a conflict fix, because #51065 removed the code it edited.

## Details

**Root cause.** #51065 moved the reorder-threshold setup into `MLACommonMetadataBuilder.__init__`. `_init_reorder_batch_threshold` clamps the threshold to 1 under DCP unless the builder passes `supports_dcp_with_varlen`, and TRITON_MLA does not pass it.

#54546 declared `supports_non_causal_multi_token_dcp` on TRITON_MLA, which is enough for backend selection and `_validate_dspark_dcp_support`. But the draft builder would still keep threshold 1, so FULL cudagraph capture of the 7-token draft block would trip `assert m.max_query_len <= self.reorder_batch_threshold` in `build_for_cudagraph_capture`. Its logits workspace would also be sized for one row per request.

**Why not `supports_dcp_with_varlen=True` in TRITON_MLA.** That would also raise the threshold for causal TRITON_MLA groups under DCP, such as an MTP or Eagle target. Their multi-token verify would then reach `forward_mqa` and hit `assert self.dcp_world_size == 1, "causal multi-token decode is not supported with DCP"`. Today those batches run as prefill.

**Change.** The common builder keeps the spec-decode threshold under DCP for a non-causal group whose backend declares `supports_non_causal_multi_token_dcp`. This is the same capability `_validate_dspark_dcp_support` already checks for that group. TRITON_MLA declares the flag only on gfx942 (`get_cdna_version() == 3`), which is where this has been validated. TRITON_MLA reserves its workspace after `super().__init__()`, so the reservation sees the final threshold.

**Why gfx942 only.** Other ROCm targets (gfx950, gfx90a, RDNA) keep today's behavior: a forced TRITON_MLA draft under DCP is rejected at startup. On gfx950, the default DSpark draft backend is ROCM_AITER_MLA, whose non-causal ASM decode kernels already declare DCP support, so TRITON_MLA is only an opt-in fallback there. The TRITON_MLA change is chip-independent: it repeats `seq_lens` and `block_table` rows for the same `decode_attention_fwd` kernel that already runs single-token DCP decode on those targets. Widening the gate should only need a GSM8K run at DCP 8 next to DCP 1 on the new target.

**Impact on other backends.**

- FlashInfer MLA and TokenSpeed MLA: no change. They already pass `supports_dcp_with_varlen=True`.
- ROCM_AITER_MLA: changes only for a non-causal group under DCP when none of its DCP verify routes is configured. In practice that is gfx950 with `cp_kv_cache_interleave_size != 1`, because every AITER DCP verify route needs interleave size 1, and AITER rejects non-causal groups on gfx942. By code reading, this config fails on main, because the threshold is clamped to 1:
  - With FULL cudagraphs, the draft capture hits the same `max_query_len <= reorder_batch_threshold` assert as TRITON_MLA.
  - Without FULL cudagraphs, `_mtp_decode_qlen = 1` closes the persistent-schedule gate in `_build_decode`. The schedule is what carries the non-causal mask, and the builder's own comment says a closed gate makes AITER raise a `KeyError` mid-run.

With this PR, the group keeps `1 + num_speculative_tokens`, which is consistent with the capability AITER already declares. 
- Builders without the flag: no change.

**Other drafters.** Backend selection does not check the speculative method, but only K3 DSpark builds non-causal MLA layers today. `K3DSparkDecoderLayer` is the only place that passes `non_causal_multi_token_decode=True`. The other `DeepseekV2MLAAttention` users (`deepseek_eagle3`, `longcat_flash`) leave the default `False`. The other DSpark drafters do not build these layers: Qwen3, MuseSpark and Gemma4 DSpark are not MLA, and DeepSeek-V4 DSpark uses the sparse MLA backends. A future non-causal MLA drafter would get the same treatment, which is correct as long as its rows share one KV extent, which is what the flag means.

**Limitation.** The flag is evaluated per metadata builder. The draft's TRITON_MLA builder also builds metadata for the target's causal verify batches, and these are now classified as decode. Draft layers never run attention on that metadata: DSpark's context-KV precompute only writes KV. A future drafter that runs causal attention through the same builder under DCP would hit the `forward_mqa` assert above at runtime rather than produce wrong output.

Good question, that's a good point. I checked exactly which configs this reaches. FlashInfer MLA and TokenSpeed already pass supports_dcp_with_varlen=True, so nothing changes there. For ROCM_AITER_MLA, non-causal kernels only exist on gfx950, and on gfx950 with cp_kv_cache_interleave_size == 1 AITER already passes supports_dcp_with_varlen=True through its DCP verify route, so this is a no-op too. That config is broken on main: AITER declares supports_non_causal_multi_token_dcp, so it passes backend selection and _validate_dspark_dcp_support, but the threshold is clamped to 1. That gives _mtp_decode_qlen = 1, so the schedule buffers are sized for qlen 1 and the persistent gate is closed for the draft block: FULL cudagraph capture trips the max_query_len <= reorder_batch_threshold assert, and eager mode hits the KeyError the builder's comment describes.

So the change makes the threshold honor the same capability the builder already validates. I'd rather keep it in the common builder than add a TRITON_MLA-local override: #51065 removed exactly that kind of per-backend threshold override, and a local one would leave AITER's validation and threshold disagreeing. Only DSpark drafts build non-causal MLA layers, so the worst case on that AITER path is lower acceptance, not wrong output.
