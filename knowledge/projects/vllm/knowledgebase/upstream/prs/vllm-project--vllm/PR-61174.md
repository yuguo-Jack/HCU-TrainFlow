# [Bugfix][Spec Decode] Clear stale shared block-table rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/61174) · state: closed · merged: True

## Original PR description

## Overview

A larger MTP decode graph can read stale shared block-table rows after the target batch shrinks, allowing padded work to address another request's cache or state.

Move shared-row cleanup into `BlockTables`, as suggested in review.

## Claims

- Clear previously active rows during gather and dummy preparation, using the existing buffers and gather kernel.
- Preserve active rows, returned views, and independent PCP output buffers.
- Remove the MTP caller workaround without changing model math.

## Details

`BlockTables` tracks potentially dirty shared rows. Gather clears through `max(num_reqs_padded, previous_dirty_rows)`; dummy preparation follows the same rule and tracks rows that profiling may populate. External `out` buffers leave shared tracking unchanged.

Regressions cover real/dummy transitions, shrink/grow/empty batches, independent outputs, and physical KPool slots under eager execution and CUDA Graph replay. PCP has unit coverage; distributed PCP serving was not tested.

The full serving run used sync-check `warn`: strict mode reports a separately reproduced, unchanged SM90 MLA metadata copy. The affected BlockTables methods passed all 17 tests under strict checking.

Duplicate checks found no other shared-row lifecycle fix: #45005 handles legacy slot mappings; #60767 handles sliding-window columns.

Thanks for tracking this bug down!

I think the responsibility of zeroing padding rows should instead belong to `BlockTables`, rather than each caller. What are your thoughts on having `BlockTables` track the number of potentially dirty requests for the shared `self.input_block_tables` buffer in `gather_block_tables`, like this:
```
def gather_block_tables(self, idx_mapping, num_reqs_padded, out=None, out_ptrs=None):
    ...
    num_reqs = idx_mapping.shape[0]
    num_rows = num_reqs_padded
    if out is None:
        num_rows = max(num_rows, self._num_dirty_rows)
        self._num_dirty_rows = num_reqs
    # Rows >= num_reqs are zeroed by the kernel.
    _gather_block_tables_kernel[(self.num_kv_cache_groups, num_rows)](...)
    return tuple(bt[:num_reqs_padded] for bt in out)
```
`get_dummy_block_tables` would have to do the same, and zero `[:max(n, self._num_dirty_rows)]` and set `self._num_dirty_rows = n`. But this would guarantee that every row of the shared buffer past the current num requests is always zeroed. This should prevent the issue from surfacing again for any other caller or speculator.
