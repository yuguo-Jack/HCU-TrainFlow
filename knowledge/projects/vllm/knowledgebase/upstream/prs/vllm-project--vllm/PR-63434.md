# [Bugfix][Frontend] Pass the caller's prompt_token_ids to the chat derender parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/63434) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Non-streaming chat derender passes the parser only `generate_response.prompt_token_ids`, which generate sets only when `return_token_ids` is on. In the usual render → generate → derender flow the parser therefore never sees the prompt. Since #61857, parsers read the prompt to tell whether it already closed reasoning, so they misclassify the output here. This affects response template parsers as well as Qwen3. For example, with Qwen3 and `continue_final_message` after a closed `</think>`, the answer comes back as `reasoning`.

## Claims

- The parser gets the engine's `prompt_token_ids` when the generate response has them and falls back to the caller's `prompt_token_ids` otherwise. The engine's take precedence because the caller may send only a suffix.
- `DerenderChatRequest.prompt_token_ids` and `derenderer.md` now say that chat derender with a parser needs the full prompt IDs in both modes. The docs also note that a suffix starting after the last reasoning marker still misparses, the same as sending no IDs.

## Validation

New E2E test through the render server (`Qwen/Qwen3-0.6B --reasoning-parser qwen3`, no GPU):

CPU is enough here. Derender only decodes and parses token IDs that were already generated, and the render server loads just the tokenizer.

```
$ pytest tests/entrypoints/scale_out/derender/test_derender.py::test_e2e_parser_uses_caller_prompt_token_ids
# without the fix:  AssertionError: assert None == ' is 42.'
# with the fix:     PASSED
```

Response template parser given a suffix (`test_prompt_suffix_parses_like_full_prompt_or_no_prompt`, a two-turn prompt whose generation prompt opens reasoning, output `plan<channel|>answer<turn|>`):

| prompt IDs given to the parser | reasoning | content |
| --- | --- | --- |
| none (before this PR) | `None` | `plan<channel\|>answer` |
| full prompt | `plan` | `answer` |
| suffix from the start anchor | `plan` | `answer` |
| suffix past the anchor, with the reasoning opener | `plan` | `answer` |
| suffix past the reasoning opener | `None` | `plan<channel\|>answer` |

A suffix parses like the full prompt while it still holds the opener and like no prompt after that. It is never worse than the empty prefix the parser had before.

The same holds through derender with a real checkpoint: `google/gemma-4-E2B-it`'s response template (`--reasoning-parser hf`), 15 suffix lengths (last 1–12, 16, 24 and 32 IDs) on 4 prompts (opening reasoning, mid-reasoning, closed reasoning, and the model writing its own). Every suffix parsed like either the full prompt or no prompt. For example, a prompt ending in `<|channel>thought\n` parses correctly from the last 3 IDs, the first that include `<|channel>`.

```
$ pytest tests/parser/test_response_template.py
75 passed
$ pytest tests/entrypoints/scale_out/derender/test_derender.py tests/entrypoints/scale_out/derender/test_derender_stream.py
214 passed, 1 xfailed
```

## Details

- #61857 made the parsers honor a prompt-closed reasoning block in non-streaming parse and reasoning token counts, but didn't touch derender.
- Not a duplicate: no open PR changes this call (searched "derender prompt_token_ids" and "derender reasoning"). #64041's reasoning counts build on it and #63357 touches the next line, so this should go in first.
