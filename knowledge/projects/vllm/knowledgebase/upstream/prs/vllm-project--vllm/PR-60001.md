# [Metrics] Export scheduler-state gauges as 0 before the first stats with --api-server-count > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/60001) · state: open · merged: False

## Original PR description



## Overview

Fixes #59988. With `--api-server-count > 1`, `vllm:num_requests_running`, `vllm:num_requests_waiting`, `vllm:num_requests_waiting_by_reason` and `vllm:kv_cache_usage_perc` have no samples until the first scheduler stats arrive. This PR sets them to 0 when `PrometheusStatLogger` creates them.

## Claims

- An idle server with `--api-server-count > 1` reports these gauges as 0, the same as with one API server.
- Nothing changes with one API server (these gauges already reported 0). With more than one, a logger created while another process already has stats (an API server that starts later, or elastic EP scale-up) reports 0 until the next scheduler stats, the same reset that one API server already does on scale-up.

## Validation

- New test `tests/v1/metrics/test_prometheus_multiproc.py` (`cpu_test`). It creates the logger in a subprocess with `PROMETHEUS_MULTIPROC_DIR` set, the way an API server process does, and reads the aggregated registry the way `/metrics` does. It runs with and without a KV consumer, so it also covers `vllm:num_requests_kv_fetch_by_stage`. On main it fails (`get_sample_value('vllm:num_requests_running', ...)` is `None`); with the fix it passes.
- `pytest tests/v1/metrics` in a CPU-only container (`VLLM_TARGET_DEVICE=cpu`), rebased on main `f8471164b`: 111 passed. The 2 failures in `test_engine_logger_apis.py` start a real engine and fail the same way on main in that environment; `test_ray_metrics.py` was left out (needs Ray).
- The behavior before the fix, measured on GPU with main `7867d6c52`, is in #59988: with `--api-server-count 2`, the idle scrape has 0 samples for each of these gauges, and 1 after the first request.
- `pre-commit run --files <the two files>`: all hooks pass.

Duplicate check: no open PR addresses #59988.

## Details

These gauges use `multiprocess_mode="mostrecent"` (added for `kv_cache_usage_perc` in #28792 so that each process doesn't export its own copy). In that mode prometheus_client keeps the sample with the newest timestamp, and a gauge that was never set has timestamp 0, so it is dropped. vLLM only set these gauges in `record()` when scheduler stats arrive, so an idle multi-API-server deployment exported nothing for them. Each API server process now sets them to 0 at startup, the same way `record_sleep_state()` already sets defaults for the sleep-state gauges. The first real stats have a newer timestamp and replace the 0.

`num_requests_kv_fetch_by_stage` exists only for KV consumers; the loop covers it when present.

- apex-mochen · COMMENTED · 2026-10-09T12:54:04Z · [source](https://github.com/vllm-project/vllm/pull/60001#pullrequestreview-5470277306)

Independent verification from a third party — I reproduced #59988 and had a competing fix, which I've now closed as a duplicate of this one. Three things I checked in the source, in case they're useful:

**1. Coverage — no `mostrecent` gauge is left unseeded.** `PrometheusStatLogger.__init__` creates six gauges with `multiprocess_mode="mostrecent"`: `num_requests_running` (:522), `num_requests_waiting` (:532), `num_requests_waiting_by_reason` (:542), `num_requests_kv_fetch_by_stage` (:567), `engine_sleep_state` (:588), `kv_cache_usage_perc` (:614). This PR seeds five of them; the sixth is already seeded by `self.record_sleep_state()` at the end of `__init__` (:611).

**2. Key safety.** The loop indexes these dicts by `engine_indexes` while the dicts are built from `self.per_engine_labelvalues` (:500) — but that dict is constructed as `{idx: [model_name, str(idx)] for idx in engine_indexes}` (:497), so the two key sets are identical, and the existing `record_sleep_state()` (:1279) iterates `self.engine_indexes` in exactly the same way. No `KeyError` path.

**3. On @nickharris808's late-starting-logger point**, which as far as I can tell is still open: the behaviour they measured — a startup `.set(0)` on a `mostrecent` gauge temporarily overwriting an existing non-zero sample published by another process — is not introduced by this PR. `vllm:engine_sleep_state` is itself a `mostrecent` gauge (:588, :596), and `__init__` already calls `self.record_sleep_state()` unconditionally (:611), which `.set()`s `awake`/`weights_offloaded`/`discard_all` for every engine on every construction. So this PR extends an existing in-repo semantic to five more gauges rather than creating a new one. If that reset is judged wrong, the decision point is `record_sleep_state()`'s constructor call as much as this loop — worth settling before merge either way.

The test shape here is also the only shape that can actually exercise this: a fresh interpreter with `PROMETHEUS_MULTIPROC_DIR` set, since prometheus_client picks the multiprocess value class at import time.

- nickharris808 · comment · 2026-10-07T02:59:42Z · [source](https://github.com/vllm-project/vllm/pull/60001#issuecomment-6029985345)

A late-starting logger is a separate case from the cold-start and subsequent-update checks above.

At [head `4dff949`, the initialization loop](https://github.com/roy6n23/vllm/blob/4dff9497a1ee6977009fee323dad03163336402a/vllm/v1/metrics/loggers.py#L624) unconditionally calls `.set(0)` for each engine's scheduler-state gauges. For `mostrecent`, that startup value gets a newer timestamp than an already-existing stats value from another process.

A bounded subprocess fixture executed that exact extracted loop with `prometheus-client==0.26.0`, real multiprocess storage and `MultiProcessCollector`, using the same engine/model labels:

| Sequence | Without startup seed | With extracted startup seed |
|---|---:|---:|
| Stats writer sets running requests to 7 | 7 | 7 |
| A later process creates the same labeled child | 7 | 0 |
| A later stats update sets it to 9 | 9 | 9 |

The zero is temporary: the next newer stats update replaces it. But the interval between logger creation and that update differs from “nothing changes after the first scheduler stats.”

Is constructing/reconstructing an API-server logger while another process already has stats a supported lifecycle? If so, a regression case should preserve the existing nonzero sample during that interval, or the PR should explicitly document the startup-reset behavior. This concern does not contradict the reported successful cold-start/load checks.

Scope: Python 3.12.13; one real `mostrecent` gauge was aliased to the three scheduler-state properties solely to exercise the extracted initialization loop, with empty reason/stage maps. Fresh subprocesses shared a local metrics directory. This check did not instantiate the full vLLM logger, restart an API server, run the engine/model, or measure how long the zero lasts in a real deployment.


- roy6n23 · comment · 2026-10-11T04:18:12Z · [source](https://github.com/vllm-project/vllm/pull/60001#issuecomment-6105364488)

Thanks for checking this. Yes, a logger can be created while another process already has stats, in two places: API server processes start independently, so one can be serving before another has created its logger, and elastic EP scale-up recreates the `StatLoggerManager` (`AsyncLLM._scale_elastic_ep`).

In both cases the 0 only lasts until the next scheduler stats. The engine sends stats every step while requests are running, so that is at most one step, and with no requests 0 is the right value.

This is also what already happens without this PR. With one API server, the scale-up path unregisters and recreates the metrics, so these gauges restart at 0 (the TODO there says so). `vllm:engine_sleep_state`, also `mostrecent`, is reset by `record_sleep_state()` in `__init__` in every mode, as @apex-mochen pointed out. So I'd rather keep the startup value than add per-process state to preserve the old sample. I've updated the second claim in the description to say this.

Follow-up after re-checking the latest diff (`9b9c59e`) locally, on the CPU platform (`VLLM_TARGET_DEVICE=cpu` — the mode the CPU job uses, `.buildkite/test_areas/misc.yaml:226` runs `-m 'cpu_test' v1/metrics`, so the new test is in the right job).

Red → green: on the PR base (`f8471164bf`, with only the test file copied in) both parametrizations fail with `AssertionError: ('vllm:num_requests_running', '0') / assert None == 0`; on `9b9c59e` both pass. `tests/v1/metrics/` as a whole: 111 passed.

Two checks the test does not cover, both behave as intended:
- The actual `--api-server-count 2` topology: two processes constructing the logger produce a 0 aggregate for every engine label (plain and KV-consumer), shared through the multiproc dir.
- Update path: a child that calls `record(SchedulerStats(num_running_reqs=7, num_waiting_reqs=3, num_skipped_waiting_reqs=1, kv_cache_usage=0.5), engine_idx=1)` after construction reports 7 / 4 / 0.5 with `capacity=3, deferred=1`, and engine 0 keeps the seeded 0. The seed does not suppress later writes.

On the late-starting-logger question (@nickharris808): the reset window is bounded by one engine step. `Scheduler.update_from_output` attaches `make_stats()` to the outputs of every step that runs (`vllm/v1/core/sched/scheduler.py:2418-2432`); it returns `None` only when `log_stats` is off, in which case no `PrometheusStatLogger` is constructed at all (`vllm/v1/engine/async_llm.py:196`). The stats reach one front-end per step, and the other API servers see the value through the shared multiproc dir, so any live server republishes the true value on its next step. The elastic scale-up path is consistent with the seed as well: `_scale_elastic_ep` recreates the manager with `engine_idxs=list(range(new_data_parallel_size))` (`vllm/v1/engine/async_llm.py:1254-1262`) and the TODO there already documents reset-on-recreate.

Two optional test nits, neither a defect:
1. The test pins only the startup value. Recording a non-zero `SchedulerStats` in the child and asserting the parent sees it would also pin that later writes replace the seed.
2. The reasons are hardcoded as `("capacity", "deferred")` while production uses `WAITING_REASON_CAPACITY`/`WAITING_REASON_DEFERRED` (`vllm/v1/metrics/loggers.py:43-44`). Importing them would keep coverage complete if a third reason is added, the way `KV_FETCH_STAGES` is imported.

For the record, at `9b9c59e` no test CI has run yet (`pre-run-check` fails on the label gate, `pre-commit`/`Check format` are skipped, DCO is green), so the runs above are the executed evidence for the new test so far.
