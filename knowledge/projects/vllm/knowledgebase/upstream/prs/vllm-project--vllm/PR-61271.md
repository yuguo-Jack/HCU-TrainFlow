# [ROCm][Perf][Qwen3.8] Mono decode follow-up: MXFP6 projections, attention front kernel, router through o_proj

[Upstream PR](https://github.com/vllm-project/vllm/pull/61271) · state: open · merged: False

## Original PR description

## Summary

This draft follows #60833. On `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` with TP8 on MI355X, a first measurement puts the mono decode step 0.94 ms faster at 1M context (median ITL 9.39 ms to 8.45 ms, with the caveats under Validation). It also moves the GDN and attention projections from MXFP4 to MXFP6 E2M3, which keeps the gsm8k answers as short as with bf16 projections.

The branch is stacked on #60833 at `1301a7cfcf`, which runs MTP verify steps on the mono kernels and is itself stacked on #60683. So the first 11 commits are those two PRs, and only the last 6 are new. Also, I think that the MXFP6 commit belongs in #60833 itself. I described how to make those weights in [this comment](https://github.com/vllm-project/vllm/pull/60833#issuecomment-6131614852).

## What this PR does

1. **A slot per pick at 2-3 rows, and the K2 load order.** At 2 and 3 rows, K2 gives every expert pick its own slot instead of building the union of the picked experts. At 2 rows, the fused shared expert also starts before the route lands. K2 also issues some loads in a better order, and the comment next to each change explains why. The W4A16 option of the first version is gone, because the MXFP6 projections replace it and W4A16 does not match the stock decode.
2. **MXFP6 E2M3 projections.** `VLLM_QWEN38_FAKE_MXFP6_PROJ=1` rounds the bf16 `in_proj_qkvz`, `out_proj`, `qkv_proj` and `o_proj` to MXFP6 after loading, so prefill multiplies the same values that decode reads. `VLLM_QWEN38_MONO_FP6=1` packs MXFP6 copies of them, and K1 and K2 multiply those copies with the bf16 rows (W6A16).
3. **Attention front kernel.** One launch runs the residual add, `input_layernorm`, the MXFP6 `qkv_proj`, the q and k norms, RoPE and the FP8 KV cache write of a full-attention layer. The attention then runs with q only, so vLLM does not write the cache again. Every row has its own position and KV cache slot, so the kernel also runs the full-attention layers of MTP verify steps.
4. **Router logits through `o_proj` in K2.** A folded bf16 weight, the router rows times the norm's (1 + w) times this rank's `o_proj` rows, gives the router logits straight from the core rows. So K2 routes before the all-reduce and the norm have built the x rows.
5. **K1 task placement for the MXFP6 `in_proj`.** K1 puts the q, k and v rows, which the conv of every GDN task waits for, on CTAs with one task, and the z rows on CTAs with two tasks. The outputs stay the same bit for bit.
6. **Tests.** K1 with the MXFP6 `in_proj_qkvz` at 1, 2, 5 and 8 rows against vLLM's ops, and bit for bit against the build without the task placement. K2 with the MXFP6 `o_proj` and `rm`, with and without the attention output gate, and at 2 rows. The replay test adds an MXFP6 layer with `rm`.

## Numerics

Unlike #60833, two of these changes do not keep the stock decode numerics bit for bit. MXFP6 is a different weight format, and the folded router weight rounds the logits differently. The gsm8k score and the needle prompts below stay within noise.

## Validation

These numbers are from the first version of this branch, on #60833 at `6a1c13b2fc`, before the port. `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8 on MI355X, `vllm/vllm-openai-rocm:nightly-8cbd5d03006c33185f402249ff2b448efd594986` with the branch on top. The #60833 arm serves the projections in online MXFP4 with the targets of the #60833 description. This PR's arm serves them in bf16 with `--quantization-config.targets '{"*shared_expert*": "mxfp4"}'` and adds the two MXFP6 switches.

| | #60833 at `6a1c13b2fc` | This PR |
|---|---|---|
| Median ITL, 2 requests of 1M input and 1000 output tokens at concurrency 2 | 9.39 ms | 8.45 ms |
| gsm8k 5-shot, flexible-extract, `max_gen_toks` 2048 | 0.9477 ± 0.0061 | 0.9469 ± 0.0062 |
| Mean gsm8k answer length | 560 characters | 449 characters |
| Passphrase found in a needle prompt of 2k, 128k and 1M tokens | yes | yes |

The ITL numbers are one run of each arm and are preliminary. Both arms also ran the FlyDSL paged-attention decode of ROCm/aiter#5949 in `ROCM_AITER_FA`, which is not in vLLM, so the difference between them is the mono kernels. I will rerun both arms on `1301a7cfcf` without it. The gsm8k numbers come from `lm_eval` against `/v1/completions` with 8 concurrent requests.

## Notes

- The two MXFP6 switches are plain environment variables for now. Before review, one switch in `vllm/envs.py` will replace them.
- The MXFP6 path needs the bf16 weights of these projections, which prefill and steps wider than 8 rows still read, and adds packed MXFP6 copies of 184 projections, 3.92 GB a GPU. At `--gpu-memory-utilization 0.9` the KV cache goes from 81.44 GiB (7.33M tokens) with the online MXFP4 targets of #60833 to 71.71 GiB (6.45M tokens) a GPU. A W6A16 GEMM for prefill would let the bf16 weights go.
- The attention front kernel has no test against the model's ops yet.
