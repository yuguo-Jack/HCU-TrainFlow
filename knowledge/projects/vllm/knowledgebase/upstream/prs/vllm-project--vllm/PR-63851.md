# [Bugfix][Prefix Caching] Keep hybrid evictions on a prefix every KV cache group can hit

[Upstream PR](https://github.com/vllm-project/vllm/pull/63851) · state: open · merged: False

## Original PR description



## Overview

A hybrid prefix hit needs every KV cache group, but a finished request's blocks enter the LRU free queue one group at a time, so pool pressure evicts one group's head while the other groups' blocks stay cached and can never be hit. This PR frees a request's blocks by token position across all groups and uncaches the blocks no lookup can reach. Related: RFC #57111, #48532, #61282, #63808 (see "Why this is not a duplicate").

## Claims

- After a hybrid request is freed, pool pressure evicts its tail token positions first in every group, so its remaining blocks always form a prefix that every group can hit. Before, a full-attention group could lose its head (hit drops to 0) while the Mamba or sliding-window blocks of the same request stayed cached.
- The immediate (`KVCacheManager.free`) and deferred (`pop_blocks_for_free`, used with async scheduling + KV connector consumers) free paths now produce the same order.
- Full-attention blocks past the last position every group can resume from (for example the last cached Mamba state under sparse retention, or decode tokens) lose their hashes when the request is freed, so they are reused before other requests' older, still-hittable cache.
- Outputs cannot change: only free order and cache membership of unreachable blocks change. Default behavior for dense (single-group) models is unchanged.
- Scheduler-side cost on hybrid models: about +5% scheduler KV time per request in the benchmark below (one cache-hit lookup per freed request). No GPU work, no synchronization.

## Details

**Root cause.** `KVCacheCoordinator.free` freed each group with its own `free_blocks(reversed(blocks))` call, so the queue held `[group0 tail..head, group1 tail..head, ...]`. LRU then evicted group 0 entirely, head included, before any block of group 1. A hit needs all groups, so the hit fell to 0 while group 1's blocks stayed cached and unusable. The deferred path reversed one flat list instead, which produced yet another order.

**Fix.**

1. `pop_blocks_for_free` returns the request's blocks in eviction order: by the token position each block ends at, tail first across all groups (ties keep the group order). The group with the most blocks is copied in reversed slices and the other groups' blocks are merged into it, so the common case does no per-block sort (128k-token request, FA + GDN + SWA: about 0.15 ms instead of 1.3 ms for a full sort). `free` and the scheduler's deferred drain both free this list as-is. Single-type managers now return their index-aligned table; the null head is trimmed in the coordinator.
2. `HybridKVCacheCoordinator.drop_unreachable_tail(request)` runs the normal cache-hit lookup on the request's own hashes when it is freed. Blocks that start past that hit, are held only by this request, and carry a hash lose the hash. With EAGLE, one scheduler block is kept, because the lookup drops one EAGLE unit at the end of the request's own tokens. It does nothing when a group has `retains_longer_hit` (HiSparse host tier), because that tier publishes pages after the request ends and can extend the reachable hit later.

**Limits.** The lookup in (2) sees the GPU prefix cache only. If another cached chain depends on these blocks through a hit point that was itself evicted earlier, that chain loses its hit; this needs an evicted junction plus a cached deeper branch and was not observed in tests.

**Why this is not a duplicate.**

- #48532 makes the deferred path match the immediate path's per-group order. This PR changes both paths to a cross-group order, which also removes that mismatch; #48532's change would be superseded.
- #61282 frees attention groups before Mamba groups and keeps the Mamba prompt-boundary state alive for the request's lifetime. The group-order part is superseded by the position order here; the lifetime part is independent and still needed.
- #63808 adds an opt-in `mamba_aware_lru` policy that demotes superseded Mamba tip states, which are still hittable. This PR is on by default and only uncaches blocks no lookup can reach, plus the cross-group order; the two compose.
- RFC #57111 proposes checkpoint-aware ordering plus segmented recomputation. This PR is the ordering-only subset that needs no new scheduler state; it is a prerequisite for clean partial hits, not a replacement for segmented recompute.
