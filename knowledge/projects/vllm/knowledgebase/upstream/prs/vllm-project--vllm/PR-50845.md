# [Bugfix][MoE] Bound expert_map gathers on data-derived expert ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/50845) · state: open · merged: False

## Original PR description

## Summary

Four MoE kernels index `expert_map` with an expert id taken from `topk_ids`,
guarding the gather with a sign check only (`expert_id >= 0` / `expert_id < 0`).
`topk_ids` is data, not a loop bound: the routers allocate it with
`torch.empty` and do not always overwrite every slot, so a stale slot can hold
an arbitrary positive value. When that happens the gather reads far past the
end of `expert_map` and the context dies with a Warp MMU fault on **every** rank.

`get_local_expert_id()` in `csrc/libtorch_stable/moe/moe_align_sum_kernels.cu`
already applies exactly the missing bound:

```cpp
int expert_id = topk_ids[idx];
if (expert_id >= num_experts || expert_id < 0) {
  return -1;
}
```

This PR bounds the other four consumers the same way. **Updated after review:**
an id at or past `expert_map`'s length is a producer bug, so instead of
skipping the slot the kernels stop with a clear message (CUDA `printf` +
trap; the Triton kernels use a predicated PTX trap, since `tl.device_assert`
is compiled out outside Triton debug mode, and fall back to
`tl.device_assert` on other platforms). `-1` remains the not-routed sentinel,
and the loads stay bounded, so the map is never read out of bounds even
before the trap fires.

## Relationship to the root cause

These gathers were the *victims*, not the cause. The garbage expert ids
originated upstream: the sampler could emit a token id equal to `vocab_size`,
and DeepSeek-V4's hash-MoE router turned that into a garbage expert id by
gathering past its lookup table. Both are fixed separately in #50843 (sampler) and #50844 (DSv4 hash router). This PR is the
defence-in-depth layer: a producer bug anywhere upstream now fails loudly at
the first consumer with the offending id, instead of an anonymous Warp MMU
fault (or silently routing on whatever memory follows the map), and it fixes
one gather that was unguarded outright.

## Evidence

Hit in production on DeepSeek-V4-Flash (TP2 + `--enable-expert-parallel`,
so `expert_map` is non-null), reproducible under bursty concurrency in
90 s – 5 min. CUDA core dump, both TP ranks:

```
CUDA Exception: Warp MMU Fault
errorpc  _swiglu_limit_pad_aware_kernel
         vllm/model_executor/layers/fused_moe/utils.py:545
```

SASS at `errorpc` is the `expert_map` gather, and the index register holds the
bad id:

```
IMAD.SHL.U32 R6,R4,0x4,RZ     ; expert_id * 4
IADD.64      R6,R6,R8         ; expert_map_ptr + expert_id*4
@!P0 BRA ...                  ; skip if !(expert_id >= 0)
*> LDG.E R8,desc[UR10][R6.64] ; <-- FAULT

R4 = 0x66E65F78 = 1726373752
R4 = 0x3F988A43 = 1066961475   (as float32: 1.1917)
```

The model has 256 experts. Both observed ids are float bit patterns — the
allocation's previous tenant — which is what an unwritten `torch.empty` slot
looks like.

Bounding only the Triton kernel moved the fault to `moe_sum_vec_kernel`
(`moe_sum_pad_aware_skip`, same unguarded pattern), which is why all four
sites are fixed together.

Note `moe_fused_mul_sum_kernel`'s gather was not merely missing an upper
bound — it was entirely unmasked, with no sign check either, so it would also
fault on the ordinary `-1` unrouted sentinel on any model taking that path.

## Changes

- `csrc/libtorch_stable/moe/moe_align_sum_kernels.cu` — `moe_sum_pad_aware_skip()`
  bounds `expert_id` against `num_experts`, threaded through the vec / dynamic /
  scalar `moe_sum` kernels from `expert_map->numel()`.
- `vllm/model_executor/layers/fused_moe/utils.py` — `_swiglu_limit_pad_aware_kernel()`
  and `_count_expert_num_tokens()` bound the gather.
- `vllm/model_executor/layers/fused_moe/moe_fused_mul_sum.py` —
  `moe_fused_mul_sum_kernel()` bounds the gather (it was previously entirely
  unmasked).

No legitimate id is rejected: valid ids live in `[0, expert_map.numel())` by
construction, which is the new bound.

`gpt_oss_triton_kernels_moe.py` already clamps its gather and is unchanged.

## Test

Four regression tests feed the observed `0x3F988A43` bit pattern or the first
id past the map through each consumer and check, in a subprocess (a trap
poisons the CUDA context), that the kernel traps; in-process they check that
`-1` slots are skipped and in-range results are exact:

- `tests/kernels/moe/test_moe.py::test_moe_sum_pad_aware_traps_on_expert_id_outside_map`
- `tests/kernels/core/test_activation.py::test_swiglu_limit_pad_aware_traps_on_expert_id_outside_map`
- `tests/kernels/moe/test_count_expert_num_tokens.py::test_count_expert_num_tokens_traps_on_expert_id_outside_map`
- `tests/kernels/moe/test_moe_fused_mul_sum.py::test_expert_id_outside_map_traps`

Validated on 2× RTX PRO 6000 (SM120): the affected test files pass (moe_sum 172,
count 150, fused_mul_sum 116, activation 523), and DeepSeek-V4-Flash (TP2 + EP)
and Qwen3.8-Flash-Next-FP8 (TP2 + EP) served 20/10-minute randomized-concurrency
stress runs (601K/251K tokens) with no trap.

Today an out-of-range id is already ignored in the worst way: the gather reads past the map, and the token is routed with whatever happens to be in that memory. We hit this from a stale `torch.empty` slot. The bound stops that read; the question is what to do instead of silently skipping. Two options:

1. Keep the bound, so the kernels never read out of bounds, and add a debug-only device assert (off by default) so a buggy map fails loudly in tests and CI.
2. Replace the masking with an unconditional device-side assert, so a buggy map kills the engine with a clear error in production too.

I'm happy to do either. If you'd rather have loud failures everywhere, I'll switch to (2). #50844 (DSv4 `tid2eid`) would follow the same choice. Which do you prefer?

- alexbi29 · comment · 2026-10-23T02:16:35Z · [source](https://github.com/vllm-project/vllm/pull/50845#issuecomment-6355784923)

@bnellnm done in `1f762e6d6e`, going with option 2:

- An id at or past `expert_map`'s length now stops the kernel with the offending id instead of skipping the slot. `-1` is still the not-routed sentinel.
- CUDA (`moe_sum`): `printf` + `__trap()`, the same pattern as `hisparse_kernels.cu`.
- Triton (count / swiglu-limit / fused-mul-sum): `tl.device_assert` is compiled out unless Triton runs in debug mode, and enabling `debug=True` per kernel also turns on integer-overflow sanitizing for every add/mul. So this uses a small predicated PTX `trap` helper on CUDA, with a `tl.device_assert` fallback on other platforms.
- The loads stay bounded, so nothing reads past the map even before the trap fires.
- Side fix: the pad-aware `moe_sum` without an `expert_map` no longer applies a bound of 0, which would have skipped every slot. No in-tree caller hits that combination today.

The out-of-range tests now check the trap in a subprocess, since a trapped kernel poisons the CUDA context. #50844 got the same treatment (`94ac10393a`). Validation on SM120 is in the description.
