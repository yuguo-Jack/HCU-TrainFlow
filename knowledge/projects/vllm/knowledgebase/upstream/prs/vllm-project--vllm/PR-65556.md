# [Bugfix] Llama4 pythonic parser: strip <|python_end|> even without <|python_start|>

[Upstream PR](https://github.com/vllm-project/vllm/pull/65556) · state: open · merged: False

## Original PR description

## Purpose
Fix a silent tool-call drop in the Llama-4 pythonic tool parser.

## Problem
In `Llama4PythonicToolParser.extract_tool_calls` (non-streaming), the `<|python_end|>` removal is nested **inside** the `if model_output.startswith("<|python_start|>")` block:
```python
if model_output.startswith("<|python_start|>"):
    model_output = model_output[len("<|python_start|>") :]
    model_output = model_output.replace("<|python_end|>", "")   # only runs with a start token
```
When a Llama-4 response emits `<|python_end|>` **without** a leading `<|python_start|>`, the sentinel survives → `ast.parse` raises `SyntaxError` → the exception is swallowed → the tool call is silently dropped.

Repro: `model_output = "[get_weather(city='Paris')]<|python_end|>"`
- Current: `tools_called=False`, call lost.
- Expected: `tools_called=True`, one `get_weather(city='Paris')` call.

The **streaming** path (same file) already strips `<|python_end|>` unconditionally, so the two paths disagree on identical input — strong evidence this is an unintended bug (the module comment even notes Llama 4 "sometime will output those tokens").

## Fix
Dedent the `<|python_end|>` strip so it runs regardless of the start token, matching the streaming path.

## Test
Added a parametrized non-streaming case `end_token_without_start_nonstreaming` to `tests/tool_parsers/test_llama4_pythonic_tool_parser.py` asserting the call is still extracted. It fails before the fix (call dropped) and passes after.

*(Note: verified the parse-path divergence with an isolated reproduction of the exact strip + regex + `ast.parse` logic; vLLM's full test env needs the CUDA/torch stack, so the parametrized test runs in CI.)*
