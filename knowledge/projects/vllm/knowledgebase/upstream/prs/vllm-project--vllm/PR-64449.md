# [Bugfix][Rust Frontend] Send the DP rendezvous in coordinated-DP INIT

[Upstream PR](https://github.com/vllm-project/vllm/pull/64449) · state: closed · merged: True

## Original PR description

## Overview

Fix managed `vllm-rs serve` hanging at startup when a MoE model's data parallel engines come from more than one launcher, as in multi-node internal DP LB: the Rust handshake owner now sends the DP rendezvous in INIT, as the Python frontend does.

Bottom of a stack: this PR → vllm-project/vllm#64450 (handshake owner serves a range of DP ranks) → vllm-project/vllm#64451 (hybrid and external DP LB in `vllm-rs serve`). It fixes a bug on `main` on its own.

## Claims

- Internal DP LB with a MoE model and engines from several launchers (rank 0 on `vllm-rs serve`, other nodes on `vllm-rs serve --headless --data-parallel-start-rank ...`) starts and serves. On `main` it hangs in the gloo rendezvous.
- INIT `parallel_config` is typed: `HandshakeParallelConfig` carries an optional `DataParallelRendezvous`, encoded as its four fields or as `{}`.
- Dense models and single-launcher deployments are unchanged: they still receive `{}`.

## Details

Root cause: MoE DP ranks form cross-rank torch process groups (the engine-level stateless DP group and the workers' DP world group) at `data_parallel_master_ip` and the ports in `ParallelConfig`. Each launcher's `ParallelConfig` draws its own free ports, so the ranks only agree when the handshake owner overwrites them through INIT `parallel_config`. The Python frontend does this for coordinated DP; the Rust handshake owner always sent `{}`. That works while one launcher spawns every engine. With a second launcher (another node, or a second `vllm-rs serve --headless` on the same node), each side dials its own ports and the rendezvous never completes.

Fix: when the in-process coordinator runs (coordinated DP: MoE with DP > 1), the handshake owner binds five ephemeral ports on the handshake host, which is `--data-parallel-address` and the host the engines already dial, releases them, and sends `data_parallel_master_ip`, `data_parallel_master_port`, `_data_parallel_master_port_list`, and `data_parallel_size` to every engine. Port allocation lives in a new private module, `transport/dp_rendezvous.rs`.

Differences from the Python frontend:

- `_coord_store_port` is not sent. The Rust frontend hosts no coordination TCPStore, so engines take the pre-allocated ports, as in Python without a store. Like Python's fallback, a port released before use can in principle be taken by another process in between.
- `VLLM_PORT` does not constrain these ports, consistent with the Rust frontend's other sockets (ZMQ input/output, coordinator), which all bind ephemeral ports.
