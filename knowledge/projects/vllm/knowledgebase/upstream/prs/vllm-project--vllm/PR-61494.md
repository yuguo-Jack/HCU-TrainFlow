# [Bugfix][Parser] Stream Gemma4 string tool arguments incrementally

[Upstream PR](https://github.com/vllm-project/vllm/pull/61494) · state: closed · merged: True

## Original PR description



## Overview

Stream Gemma4 `<|"|>` string tool arguments incrementally and in linear time by adopting the `arg_value_extender` hook from #61253, and fix the engine so a live extender runs before the `arg_structural_chars` gate. Follow-up to #61253; same root cause as the DeepSeek symptom in #52846 / #58780.

## Claims

- Gemma4 string argument bodies now stream token by token. Before, a value without one of `,:{}[]<` arrived as a single fragment when its closing delimiter did.
- Long string arguments no longer cost quadratic parser time. A 32 KB code value drops from 7.0 s to 0.15 s of parser CPU on this machine; the converter runs a constant 8 times instead of 5008.
- Accumulated streamed arguments are byte-identical to the previous streaming path and to non-streaming extraction, including streams cut inside a value.
- Engine: a live extender now receives every delta. Before, the `arg_structural_chars` gate dropped non-structural deltas from the open value and the stream truncated at the next conversion. GLM, the only previous extender user, sets no gate and is unaffected. `ParserEngineConfig` rejects an extender without `arg_converter` or with `stream_arg_deltas=False`, which the engine silently ignored.

## Details

**Root cause.** `_compute_arg_delta` returned early for any delta without an `arg_structural_chars` character, before consulting a live extender. Gemma4 sets that gate to `,:{}[]<`, so a body delta like `Paris` never reached the extender or the converter, and the whole value was emitted when the close arrived. Every delta that did pass the gate re-parsed the full argument text, which is quadratic in value length and is why code-like values, full of structural characters, were the worst case.

**Engine change.** The gate now applies only when no extender is live; a live extender sees every delta. The factory is called after each accepted conversion and decides whether the raw text ends in an open value, because the engine cannot tell from converted JSON (converters serialise an open raw value as a closed JSON string). The `arg_value_extender` comment documents this and the lexer invariant extenders rely on: a terminal is never split across deltas, except that a held partial terminal is flushed as text at end of stream or before a token-ID terminal. The `_safe_arg_prefix` docstring is corrected to say the flag describes the returned prefix.

**Gemma4 extender.** `_parse_gemma4_fields` reports the key of an unterminated trailing string so the factory can confirm it is also the last key in the parsed dict (a duplicate key would otherwise stream into the wrong slot). The hard part is that `_gemma4_arg_converter` hides a tail of the open value until more text arrives: `.strip()` removes trailing whitespace, one trailing `}` or excess `)` is dropped as the call-body closer, and `_strip_partial_delim` removes a partial `<|"|>`. The extender keeps exactly that tail unemitted and uses it as the window that detects a split close, so its output stays a prefix of every later conversion, including the final flush of a truncated stream. `_drop_call_closer` is shared with the converter so the two cannot drift. Unlike GLM's tags, `<|"|>` is not a lexer terminal, so the window is required rather than defensive.

**Tradeoffs.** Prose values now cost about three times the parser time because every token is emitted instead of one lump; absolute numbers stay small and linear (87 ms for 32 KB). `Gemma4Parser` accepts `parser_engine_config` as an override, matching `Glm47MoeParser`, so tests can swap the converter or extender.

**Limitations.** A duplicate top-level key whose first value already streamed cannot be extended; both the old and new paths stop at the same point. That is pre-existing behaviour in the area of #53739. No model eval was run: this machine has no GPU. The change alters only when argument fragments are emitted, and the tests pin the accumulated text to the non-streaming result; a reviewer with a Gemma4 checkpoint could confirm by streaming a long file-write tool call with and without the change and diffing the concatenated arguments.

**Not a duplicate.** No open PR adds an extender to any parser (`gh pr list --search arg_value_extender` is empty). #58780 fixes the same symptom for DeepSeek by relaxing the gate in the engine, which keeps the quadratic cost; that engine hunk is superseded by the reorder here, and the DeepSeek extender can follow as its own PR.
