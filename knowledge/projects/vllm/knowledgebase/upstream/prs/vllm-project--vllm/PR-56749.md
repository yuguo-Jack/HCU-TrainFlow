# [Bugfix] Make DSA prefill top-k deterministic on equal scores

[Upstream PR](https://github.com/vllm-project/vllm/pull/56749) · state: open · merged: False

## Original PR description

## Draft status — known integration issue (19 September 2026)

**Do not merge the current diff yet.** Our follow-up audit found that the helper returns absolute column indices, while the native prefill operator and its consumers expect indices relative to each row's `ks`. For a nonzero row start, that mismatch can select the wrong KV entries. The original CPU expectations also used the wrong coordinate convention.

A local correction now returns relative indices and preserves `-1` padding. A regression covering nonzero row starts fails against the published helper; the corrected local suite passes all 11 CPU tests and applicable changed-file checks. **That correction has not been pushed to this PR.** GPU/model results from our separately patched deployment do not qualify this published revision.

This PR remains draft pending the correction, appropriate integration/model validation, and the submitting human's line-by-line review and testing required by `AGENTS.md`. No human review or human-run tests are claimed. The historical validation below describes the original revision and must not be read as resolving this newly identified contract error.

---

## Purpose

The same long prompt should not change which compressed-context tokens sparse attention uses, or the generated answer, just because several indexer scores were exactly equal. Today the DeepSeek prefill path calls `ops.top_k_per_row_prefill`. On equal finite logits that kernel can emit different index sets for the same row when the row batch changes, so later attention sees a different KV subset.

This PR replaces that prefill call with a stable value-desc / index-asc selector: columns in `[ks, ke)` only, equal scores keep the smaller column index, unused slots stay `-1`.

## Changed behavior

- File: `vllm/model_executor/layers/sparse_attn_indexer.py` (code owner @zyongye).
- Prefill only. Decode still uses `indexer_topk.py` (`persistent_topk` / `cooperative_topk` / `top_k_per_row_decode` / …).
- No new CUDA kernel. The selector is `torch.argsort(..., descending=True, stable=True)` plus a validity mask, matching a production wrap that overwrote the CUDA result.

- LoongPei · comment · 2026-09-30T02:50:53Z · [source](https://github.com/vllm-project/vllm/pull/56749#issuecomment-5903108156)

**Independent data on 8×H20 (SM90), DeepSeek-V3.2, vLLM 0.30: equal-score ties in `top_k_per_row_prefill` are the only run-to-run non-determinism we found in the first six layers, they make TP ranks disagree, and the tie rule of this PR removes the rerun divergence end to end.**

A note first, given the draft status above: our A/B below used our own implementation of the same rule (value-descending, ties at the smaller column, request-relative indices with `-1` padding, applied to the kernel's output), not this PR's helper. So it does not validate the published revision, but it does support the approach.

Setup: DeepSeek-V3.2, TP8 on 8×H20, `fp8_ds_mla` KV, `--enforce-eager`, the NCCL settings of batch-invariant mode (so the all-reduces are deterministic). 24 real coding-agent requests of 16K–100K tokens, 156 prefill forwards, 8192-token chunks.

Method: a small plugin re-runs every op of layers 0–5 on all 8 ranks right after the real call, on bit-identical copies of its inputs, and compares the two results bitwise. Cache blocks written by an op are snapshotted and restored, so the model runs as if each op ran once.

- **Bitwise identical on every call**: all FP8 linear layers (`fused_qkv_a_proj`, `q_b_proj`, `o_proj`, indexer `wq_b` / `wk_weights_proj`, dense MLP, shared experts), the MoE router, the fused all-reduce + RMSNorm, `fused_norm_rope` (including both cache writes), `fused_q`, `fp8_fp4_mqa_logits` (compared inside each row's `[ks, ke)`), the indexer K gather and the index conversion. Thousands of calls each, on all ranks.
- **`top_k_per_row_prefill` is not.**
  - The output order differs in about 6144 of 8192 rows on every call, as expected from atomic ordering.
  - The selected set also changes: rerunning on the same logits changed at least one row's set in 3.9% of calls (722 of 18,624), 775 rows in total.
  - All 775 are exact ties: the key swapped in and the key swapped out have exactly the k-th score. Example, layer 1, row 6448: positions 5532 and 4345, both −0.8091567754745483.
  - Rerunning with the out-of-window part of the logits buffer set to −inf gives the same swaps, so this is not the uninitialized region.
- **Across TP ranks**: each rank runs its own copy of the indexer. In 9.0% of layer-chunk calls (210 of 2,328), at least one row got a different set on different ranks. The heads on different ranks then attend to different keys for the same token, and the all-reduce spreads the difference to every rank.
- **End to end**: a few such events per 8192-token chunk across 61 layers make 42–58% of single-request reruns diverge within 128 greedy tokens. Sorting the top-k output alone does not help.

A/B, 36 single-request rerun pairs each, eager, deterministic NCCL settings (the tie rule applied after both the prefill and the decode top-k):

| Arm | Reruns diverging within 128 tokens | Step-0 top-5 bitwise equal |
|---|---|---|
| sort only | 19/36 (median first divergence at token 4) | 0/36 |
| tie rule + sort | 0/36 | 36/36 |

Rows with an ambiguous tie at the k-th score, as counted by the rule: 82,524 of 208 million prefill rows (about 1 in 2,500) and 184 of 491,576 decode rows, identical on all 8 ranks. The kernel resolves most of them the same way every time; the few it does not are enough.

- Col-5555 · comment · 2026-09-30T14:18:24Z · [source](https://github.com/vllm-project/vllm/pull/56749#issuecomment-5913136014)

The Limits section is right that GLM's kpool prefill still calls `top_k_per_row_prefill`. We hit
exactly this on GLM-5.3-Flash (GB10, TP=2; details in #54521): exact ties at the 512th pool in
prefill, broken differently from run to run and from rank to rank, enough to change the answer.

An alternative that covers both paths (and decode) without touching the Python callers: make the
op itself deterministic. We did that behind an environment switch read by the two C++ launchers
(`top_k_per_row_prefill` and `persistent_topk`), using one kernel: an exact radix select of the
k-th key over an order-preserving uint32 key (counting only), then one pass in index order that
emits everything above the k-th key plus the lowest-index elements equal to it, placed by block
prefix sums. Output: indices relative to the row start, ascending, `-1` padding for short rows;
ties by lowest index; keys compared bit-exactly with the same order the stock kernels use
(+0 above −0, NaN with the sign bit clear above +inf).

Cost on GB10: 92 µs for a 2,048-row prefill chunk at 2,476 pools (217 µs at 8,192), 8 µs per
decode row at 2,476 pools. We have not measured the stock kernels at the same shapes.

On your coordinate issue: agreed that consumers expect row-relative indices; both stock kernels
return them (the prefill kernel subtracts `rowStart` on its strided path; the vectorised path
indexes from the row start).

Happy to share the patch if an op-level switch is of interest.
