# [Spec Decode] Keep the trailing prefix-cache block for hybrid models

[Upstream PR](https://github.com/vllm-project/vllm/pull/61911) · state: open · merged: False

## Original PR description

## Description

Regarding: EAGLE/MTP prefix caching on hybrid (attention + Mamba) models

When serving GLM-5.3-Flash with MTP in P/D on B300s, I noticed every warm turn missed one more cached block than the same deployment with speculation off. With a fixed 77K-token shared prefix, MTP hits exactly 73,728 tokens (32 blocks) every time while spec off hits 76,032 (33 blocks), so each turn recomputes ~2.3K extra prompt tokens, about 60% more prefill work, which is what saturates prefill and drives TTFT up under load

I find that the main cause is the EAGLE trailing-block drop. It exists so a request never reuses the draft-layer KV slot at a producer's chunk end, since that slot was written with the producer's lookahead token. With one MTP head (or EAGLE) that is a single slot, and a stale one can only lower acceptance, since target verification keeps outputs exact. For regular attention the drop costs one ordinary block, but in Mamba `align` mode the attention block is sized to hold a Mamba state page (2304 tokens on GLM-5.3-Flash), so the drop recomputes a whole block on every prefix hit

This makes `disable_eagle_block_drop` default to auto (`bool | None = None`) and resolves it in `VllmConfig` right after the hybrid config hooks, so the scheduler, workers and KV connectors all read the same value:
```text
disable = method in {eagle, eagle3, mtp}
          and is_hybrid and enable_prefix_caching and mamba_cache_mode == "align"
          and num_prefill_lookahead_tokens == 1
```
an explicit setting still wins, and multi-module MTP (several lookahead slots per chunk boundary), DFlash/DSpark and non-hybrid models keep the drop

I tested this on GLM-5.3-Flash NVFP4 with MTP7 in 1P/1D NIXL (prefill DEP TP4×DP2/EP8, decode 2× TP4, NVFP4 KV, 1M context, 16 B300s) using native AgentX (`semianalysis_cc_traces_weka_062126`, 900 s per point, one run each), comparing the current drop against `disable_eagle_block_drop=true` on our internal fork, which carries the same drop logic:

| C | TTFT p50 drop → keep | out tok/s drop → keep | prefill prefix hit drop → keep | draft acceptance drop → keep |
|---|---|---|---|---|
| 64 | 500 → 517 ms | 1,293 → 1,303 | 0.876 → 0.892 | 0.409 → 0.417 |
| 128 | 723 → 639 ms | 3,402 → 3,398 | 0.842 → 0.859 | 0.385 → 0.379 |
| 256 | 1,097 → 946 ms | 5,366 → 5,427 | 0.841 → 0.858 | 0.398 → 0.398 |
| 384 | 6,576 → 2,544 ms | 6,487 → 6,896 | 0.803 → 0.826 | 0.395 → 0.391 |

acceptance doesn't move, and the gain shows up once prefill becomes the bottleneck (C64/C128 are within single-run noise). Correctness gates, including ~990K-token retrieval, tool calls and streaming, passed with the block kept. I also tried `--prefix-match-unit` below the block size, which shrinks the drop to one hash unit, but mid-block hits copy a whole block per KV group on this model and were slower overall, so it isn't a substitute today
