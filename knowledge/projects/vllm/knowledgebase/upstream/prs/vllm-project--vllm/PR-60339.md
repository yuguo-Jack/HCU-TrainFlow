# [Spec Decode][MRV2] Suffix decoding speculator for Model Runner V2

[Upstream PR](https://github.com/vllm-project/vllm/pull/60339) · state: open · merged: False

## Original PR description

## Purpose

`method="suffix"` today needs Arctic Inference, runs on the CPU, forces Model Runner V1 and disables async scheduling. With this PR it runs on Model Runner V2 with a GPU speculator, with async scheduling and without Arctic. V1 keeps using Arctic. This is the "suffix" item in #47172. The speculator builds on `ngram_gpu` (#40704) and borrows from #52097 (thanks @zip95297).

## How it works

- **Own history:** the longest suffix match within the request's prompt and output, up to `suffix_decoding_max_tree_depth`. Same kernel layout as `ngram_gpu`.
- **Cross-request corpus:** finished responses go into a GPU token ring (`suffix_decoding_corpus_tokens`, default 1M). A hash index on each request's last 2 and last 4 tokens returns up to 16 candidate positions. Each is verified and extended to its full suffix match, so the index is only an entry point for suffix matching, and collisions or overwritten documents can't produce wrong drafts.
- **Frequency vote:** candidates vote on the continuation, as in SuffixDecoding. The longer of the own-history and corpus matches wins.
- **Adaptive verification** (`enable_adaptive_verification`): per-slot confidences, learned online by source, match length and position, let the runner trim slots that aren't worth verifying.
- **Seeded requests** draft only from their own history. Corpus drafts change as other requests finish, and under sampling the drafts affect which tokens are drawn, so this keeps `seed=` outputs reproducible (Arctic on V1 isn't: 2/4 in the test below).
- **Runtime properties:**
  - No host sync on the propose path. Finished requests are ingested by one GPU program per (document, block).
  - TP ranks stay identical without collectives: ingestion is in sorted id order, inserts use `atomic_max`, and the statistics are integer counters.
  - About 36 MB of GPU memory at the defaults.

<details>
<summary><b><ins>How a corpus lookup works (diagram)</ins></b></summary>

```
Request history:  ... "report" "the" "camera" "at" "the" "north" "gate"
                                          └──── last 4 ────┘
                                                       └─ last 2 ┘

1) LOOK UP          hash(last 4), hash(last 2) -> buckets, 8 slots each
                    (slot = newest occurrence in each of the last 8 documents)

2) EXTEND BACKWARDS each candidate against the request (up to 24 tokens):
   request:   report the camera at the north gate
   corpus:    log:   the camera at the north gate     -> match length 6
   stale or colliding candidate -> length 0, dropped

3) VOTE + DRAFT     candidates matching >= L tokens vote on the next k tokens;
                    the chain with the highest summed probability wins

4) COMPARE          with the longest match in the request's own history;
                    the longer match wins, empty slots get the last token
```

Ingestion when a request finishes: `[last 3 prompt tokens | response]` is appended to the ring, and every position is indexed under the 2 and 4 tokens before it: `table[hash][doc % 8] = max(existing, (doc, pos))`.

</details>

## Taken from #52097

Cross-request matching on the GPU with no host sync; ingestion from `RequestState` in an `on_requests_finished` hook (skipping preempted requests); sorting finished ids for TP consistency; committed lengths from the device; the Spec-Bench replay method.

## Why a hash index

| Index | Propose cost (L4) | Notes |
|---|---|---|
| Suffix tree (Arctic, V1) | CPU, per request | Host sync, so no MRV2 or async scheduling |
| Suffix array (#52097) | 0.3–4.5 ms (library, eager) | Background rebuilds, epochs and a CPU collective for TP; up to 532 MB (as reported) |
| Brute-force GPU scan | 0.3–1.2 ms at batch 128 | Exact; cost grows with batch × corpus |
| **Hash index + vote (this PR)** | **11–33 µs** (GPU time), flat to a 4M-token corpus | No rebuilds; within 0.4% of an exact search at 256K, 1M and 4M tokens |

One difference from Arctic: corpus matches need at least 2 tokens, while own-history matches can still be 1. Storing the last 3 prompt tokens with each response lets a response's first tokens be drafted from the corpus.

## Results (NVIDIA L4, greedy)

**Acceptance.** Replay of 21,299 greedy Qwen2.5-1.5B requests with 5.1M output tokens:
- **Mix:** UltraChat, Alpaca, GSM8K, Spec-Bench, code edit, rewrite and templated JSON.
- **Setup:** waves of 64 requests, 1M-token corpus, k=8. The table shows mean tokens per step.
- **Arctic** runs via `arctic_inference` and also sees responses still being generated.
- **Kernel check:** the kernel matches the replay on all 1,280 sampled drafts.

| Drafter | All | Code edit | Rewrite | Templated JSON |
|---|---|---|---|---|
| Own history only | 1.651 | 5.50 | 4.74 | 1.65 |
| **This PR** | **1.937** | 5.45 | 4.69 | 4.25 |
| Exact corpus search + vote (upper bound) | 1.964 | 5.46 | 4.70 | 4.29 |
| Arctic (V1), k=8 | 1.923 | 5.12 | 4.07 | 3.89 |
| Arctic (V1), k=24 | 1.948 | 5.89 | 4.37 | 4.11 |

Acceptance is on par with Arctic. The gains are throughput: GPU-resident, async, and trimmed by adaptive verification.

## Open questions

1. **Adaptive verification by default?** Without it, V2 suffix decoding loses throughput from concurrency 32 up. But it needs full CUDA graphs and a backend that replays variable-length decode batches (which excludes FA2 on pre-Hopper GPUs). It also costs memory: on an L4 with Qwen2.5-7B its CUDA-graph capture took about 50 s and 1.9 GiB, vs 2 s and 0.05 GiB without it (capping `max_cudagraph_capture_size` at 32 barely changed this). That left 44K instead of 80K tokens of KV cache. At 24K-token contexts with 3 concurrent requests, the prefix cache hit rate fell from 50% to 0.1% and requests were re-prefilled, which is where the 0.28x long-context number comes from. GPU utilization stayed at 98%, so it's capacity, not a host sync.
2. **Default `num_speculative_tokens`.** It currently defaults to `suffix_decoding_max_tree_depth` (24). That suits V1's variable-length drafts, but V2 verifies all k slots. Should V2 default lower, for example 8?
3. **Low-concurrency trimming.** Adaptive verification is about 5–10% below verifying every slot at concurrency 1. Tune it here (for example with a more optimistic prior) or later?
4. **Corpus default.** 4M tokens adds about 2–3% acceptance, but the index grows from 32 MB to 128 MB.
5. **Tokens past the stop point.** Under async scheduling a finished request can carry a few tokens past the stop point into the corpus. Pass the scheduler's final length down?
6. **Arctic-only options** (`max_spec_factor`, `min_token_prob`) are ignored on V2. Is that OK, or warn?

## Follow-ups

- Exclude filler slots from spec-decode metrics for GPU drafters, as #52097 does.
- Index responses while they're still being generated. That's likely why Arctic is ahead on the templated VLM workload (4.89 vs 4.52 tok/step).
- aarch64 benchmarks.
