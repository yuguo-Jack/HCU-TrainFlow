# Add Kimi video chunk splitting

[Upstream PR](https://github.com/vllm-project/vllm/pull/45545) · state: open · merged: False

## Original PR description

## Summary

This PR adds Kimi video chunk splitting for decoded video inputs.

- adds a Kimi-specific splitter that converts decoded video frames plus metadata into model-native `video_chunk` entries with timestamp prompts
- preserves decoded video metadata for processors that explicitly require full video splitting
- keeps the existing optional splitter fallback behavior for other multimodal processors
- adds focused coverage for Kimi timestamping/frame conversion, an existing real video asset, and the chat utility resolver behavior

## Motivation

The Kimi multimodal processor expects video to arrive as native `video_chunk` items. OpenAI-compatible `video_url` requests are decoded by vLLM into video frames first, so Kimi needs a bridge from decoded video frames back into those model-native chunks. Without that bridge, video requests can reach the Kimi processor in a shape it cannot consume.

The `video_chunk` shape, `make_chunk_prompt` format, timestamp formatting, and `temporal_merge_kernel_size` chunking mirror the reference Kimi vision processor shipped with [`nvidia/Kimi-K2.5-NVFP4`](https://huggingface.co/nvidia/Kimi-K2.5-NVFP4/blob/main/kimi_k25_vision_processing.py); this PR adapts that model-native shape to vLLM's already-decoded frame path instead of re-decoding a URL or byte stream.

## Behavior

- Processors can declare that a video splitter is required.
- When splitting is required, the chat utility resolver passes decoded video metadata through to the splitter instead of silently falling back to unsplit video handling.
- Kimi uses that hook to split decoded video frames into timestamped `video_chunk` entries.
- `vision_chunk` UUIDs are rebuilt after splitting so `mm_uuids["vision_chunk"]` stays aligned with the emitted chunk list.
- A single emitted chunk keeps the original client UUID. Multiple emitted chunks use stable `-0`, `-1`, ... suffixes.
- Video chunks without a client-provided UUID keep `None`, matching the image path.

## Scope

This is intentionally limited to Kimi video preprocessing plus the generic resolver hook needed to pass video metadata through when a processor declares that splitting is required. It does not add network/media-fetch hardening, deployment-specific flags, or new checked-in binary video assets.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Honor Kimi sample_fps before chunking decoded videos**

For Kimi `video_url` requests where the caller does not set `media_io_kwargs` to pre-sample, `MediaConnector.fetch_video` reaches `VideoBackend.load_bytes` with the default `num_frames=-1`/`fps=-1`, so `pil_frames` contains every decoded frame. This loop then chunks every frame and ignores `image_processor.media_proc_cfg['sample_fps']`, while Kimi's native splitter first samples frame indices at the configured sample FPS; a normal 30fps clip can therefore emit roughly 30x more `video_chunk` prompts/tokens than intended, hurting latency/memory and changing the model's temporal input.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Keep UUID slots for anonymous split chunks**

When a Kimi request mixes a UUID-bearing vision item with a video that has no UUID, this branch assigns `None` to every split video chunk. In the sync `HfRenderer.render_messages` path, `rebuild_mm_uuids_from_mm_data()` rebuilds `vision_chunk` UUIDs by keeping only non-`None` item UUIDs; because at least one other item has a UUID, it overwrites the list with too few entries. `ProcessorInputs.get_mm_hashes()` later indexes that shorter UUID list for every `vision_chunk` item, so the request fails instead of hashing the anonymous chunks. Preserve the `None` slots, or avoid rebuilding from a filtered list, for split chunks.
