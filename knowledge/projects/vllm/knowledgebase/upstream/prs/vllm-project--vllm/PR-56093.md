# [Bugfix][Parser] Poolside: stray arg_key tags must not leak into tool-call argument keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/56093) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`--tool-call-parser poolside_v1` has the same leak as GLM-4.7 (#54971): a duplicated `<arg_key>` or `</arg_key>` tag ends up inside the argument **name**, e.g. `{"content</arg_key>": "hi"}`. `func_arg_regex` now uses the same bounded key pattern. Manny7717 flagged this call site while reviewing #54971.

## Claims

- Stray or repeated `arg_key` tags no longer reach the key.
- Well-formed tool calls parse exactly as before.
- No model eval: only the parsing of malformed markup changes.

## Validation

CPU only (macOS, Python 3.12, torch 2.14.1). Run on 2026-10-14 against `82d956c73` (`main` at `7115b70c0`). The commits after it only merge `main`.

| `poolside_v1_tool_parser.py` taken from | `pytest tests/tool_parsers/test_poolside_v1_tool_parser.py` |
| --- | --- |
| this PR | 17 passed |
| `main` | **2 failed**, 15 passed |

The new test, `test_extract_tool_calls_ignores_stray_arg_key_tags`, runs `extract_tool_calls` on a repeated closing tag, a repeated opening tag, and a well-formed control. The 2 failures on `main` are the two malformed cases.

`ruff check` and `ruff format --check` pass on the changed files.

Local-only workaround: vLLM's autouse teardown calls `torch.accelerator.empty_host_cache()`, which segfaults on CPU-only macOS torch. For these runs it was stubbed out with a local pytest plugin. Nothing in the repo was changed for this.

## Details

**Root cause.** `func_arg_regex` matched the key with `(.*?)</arg_key>\s*<arg_value>`. The lazy `.*?` still runs past the first `</arg_key>` when the next text is not `<arg_value>`, so a duplicated closing tag gets absorbed into the key. With a duplicated opening tag, the match simply starts at the first `<arg_key>`.

| Arguments in the model output | `main` | This PR |
| --- | --- | --- |
| `<arg_key>content</arg_key></arg_key><arg_value>hi</arg_value>` | `{"content</arg_key>": "hi"}` | `{"content": "hi"}` |
| `<arg_key><arg_key>content</arg_key><arg_value>hi</arg_value>` | `{"<arg_key>content": "hi"}` | `{"content": "hi"}` |

**Fix.** The same key pattern as #54971:

```python
self.func_arg_regex = re.compile(
    r"<arg_key>([^<]*+(?:<(?!/?arg_key>)[^<]*+)*+)(?:</arg_key>\s*)+"
    r"<arg_value>(.*?)</arg_value>",
    re.DOTALL,
)
```

- The key may contain `<`, but not an `arg_key` tag, so it stops at the first `</arg_key>`. Then `(?:</arg_key>\s*)+` consumes any duplicated closing tags.
- This file imports `regex as re`, which supports possessive quantifiers.
- `func_arg_regex` is only used in `extract_tool_calls`. The streaming path does not use it.
- One other malformed shape changes on purpose. Two keys followed by one value (`<arg_key>a</arg_key><arg_key>b</arg_key><arg_value>1</arg_value>`) used to produce a single corrupt key, `a</arg_key><arg_key>b`. It now produces `{"b": "1"}`.

**Overlapping PRs.**
- #54678 fixes backtracking in `func_detail_regex` and adds regex timeouts. It leaves `func_arg_regex` unchanged, but it edits nearby lines, so one of the two may need a small rebase.
