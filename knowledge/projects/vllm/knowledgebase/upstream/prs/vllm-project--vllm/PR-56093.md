# [Bugfix][Parser] Poolside: stray arg_key tags must not leak into tool-call argument keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/56093) · state: open · merged: False

## Original PR description

## Purpose

`PoolsideV1ToolParser.func_arg_regex` captures the argument key with a plain
`.*?`:

```python
self.func_arg_regex = re.compile(
    r"<arg_key>(.*?)</arg_key>\s*<arg_value>(.*?)</arg_value>", re.DOTALL
)
```

A non-greedy `.*?` guarantees only the *shortest match consistent with the
rest of the pattern*, not that it stops at the first literal `</arg_key>`.
If `\s*<arg_value>` fails to match right after that first occurrence, the
engine backtracks and lets `.*?` cross the boundary to reach a *later*
`</arg_key>`, silently absorbing a stray `<arg_key>`/`</arg_key>` tag into
the parsed key.

This is the identical defect class and identical fix shape as the GLM-4.7
leak fixed in #54971 (reviewer Manny7717 flagged this exact call site in
that PR's review, at `vllm/tool_parsers/poolside_v1_tool_parser.py:82`).
The fix bounds the key to runs of non-`<` text, so the capture group can
never cross its own delimiter:

```python
self.func_arg_regex = re.compile(
    r"<arg_key>([^<]*+(?:<(?!/?arg_key>)[^<]*+)*+)(?:</arg_key>\s*)+"
    r"<arg_value>(.*?)</arg_value>",
    re.DOTALL,
)
```

This file uses the third-party `regex` module (`import regex as re`), not
stdlib `re` — `regex` has always supported possessive quantifiers (`*+`)
regardless of interpreter version, so (unlike a stdlib-`re` site) no
non-possessive fallback is needed here. The repo's `requires-python` is
`>=3.11,<3.15`; the tests were run on 3.13.15, and a 20,000-case randomized
differential check (see Test Result) against the old pattern found no
divergence on well-formed input and no leaked `<` in malformed input.

### Not a duplicate

2026-10-10. The only PR that overlaps the fix is #54678
("[Bugfix][Security] Fix catastrophic backtracking in the poolside_v1 and

targets a different defect class (ReDoS/timing) in the *same file*'s
`func_detail_regex`, and adds a `timeout=` guard around all three regex
call sites in `extract_tool_calls`, including `func_arg_regex.findall(...)`
— but it leaves `func_arg_regex`'s *pattern* itself untouched (verified
against its current diff), so the key-leak this PR fixes is still present
whether or not #54678 lands first. The two PRs touch nearby but disjoint
lines in the same `__init__`, so whichever lands second needs a small
textual update, not a merge of duplicate work. #45724 ("[CI] Add test suite
for PoolsideV1ToolParser") adds tests for the same parser and may conflict in
the test file only.
