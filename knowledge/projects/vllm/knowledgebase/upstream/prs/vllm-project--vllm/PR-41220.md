# [Kernel] Add H20-3e FP8 block-scaled GEMM tuned configs for DeepSeek-V4-Flash expert shapes

[Upstream PR](https://github.com/vllm-project/vllm/pull/41220) · state: open · merged: False

## Original PR description

## What

H20-3e Triton-tuned configs for the two expert GEMM shapes used by DeepSeek-V4-Flash:

- `N=2048, K=7168` — gate / up projection
- `N=7168, K=2048` — down projection

Without these the fallback uses `BLOCK_SIZE_M=64` for any M, which pads decode batches (M=1–32) heavily and tanks Tensor Core utilization.

## Speedup vs fallback (BM=64,BN=128,BK=128,ns=2)

`N=2048, K=7168`:

| M | best (BM,BN,BK,ns) | speedup |
|---|---|---|
| 1 | (16,64,128,4) | 1.79× |
| 4 | (16,64,128,4) | 1.64× |
| 8 | (16,64,128,4) | 1.62× |
| 16 | (16,64,128,3) | 1.63× |
| 32 | (16,64,128,4) | 1.57× |
| 64+ | fallback already optimal | ≈1.0× |

`N=7168, K=2048`:

| M | speedup |
|---|---|
| 1 | 1.60× |
| 4 | 1.23× |
| 8 | 1.17× |
| 16 | 1.16× |

`BLOCK_SIZE_M=16` is the consistent winner for M≤32 — the fallback's BM=64 wastes 50–98% of issue slots on padding for these shapes.

## Files

- `vllm/model_executor/layers/quantization/utils/configs/N=2048,K=7168,device_name=NVIDIA_H20-3e,...json` (new)
- `vllm/model_executor/layers/quantization/utils/configs/N=7168,K=2048,device_name=NVIDIA_H20-3e,...json` (new)
- `benchmarks/kernels/benchmark_w8a8_block_fp8.py` — added the two shapes to `get_weight_shapes()` so future re-tuning runs pick them up regardless of TP size

Addresses gemini-code-assist's suggestion to list both shapes explicitly rather than relying on TP=8 of `(7168, 16384)` to coincidentally produce K=2048.

## Acc

GEMM block-size only — math unchanged. End-to-end DeepSeek-V4-Flash-FP8 with greedy decode produced 30/30 string-identical outputs vs the fallback path on a math/factual mini-suite.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The 'down' projection shape `(7168, 2048)` should be explicitly included in the `dsv4_flash` list. Relying on it being present in `k_tp` is fragile because it only results in the correct shape when `tp_size=8` (via `16384 // 8`). If the benchmark is run with a different TP size (e.g., `tp_size=4` or `tp_size=2`), this specific expert shape will be missed during tuning, leading to sub-optimal performance for DeepSeek-V4-Flash on those configurations. Explicitly adding it ensures that the benchmark script remains robust and independent of the TP configuration used for tuning.

```suggestion
    # DeepSeek-V4-Flash expert shapes (intermediate_size=2048 per expert).
    # gate/up: N=2048, K=7168 (neither N nor K is TP-split at per-expert level)
    # down:    N=7168, K=2048 (neither N nor K is TP-split at per-expert level)
    dsv4_flash = [(2048, 7168), (7168, 2048)]
```
