# [Config] Hash MambaConfig in the compile cache identity

[Upstream PR](https://github.com/vllm-project/vllm/pull/64873) · state: open · merged: False

## Original PR description

## Overview

`VllmConfig.compute_hash()` omits `mamba_config`, so two configs that differ only in Mamba settings collapse to one AOT/compile cache key and reuse each other's compiled artifact. This folds `MambaConfig` into the cache identity.

## Claims

- Bug fix: configs differing only in `mamba_config` now produce distinct compile cache hashes instead of colliding.
- Covers the Mamba settings that change the compiled mixer: `backend`, `enable_stochastic_rounding`, `stochastic_rounding_philox_rounds`, `ssu_algorithm`.
- No change to model behavior; only the cache identity is corrected.

## Validation

Reproduce the collision on a fresh `VllmConfig`:

```bash
python -c "
from vllm.config.mamba import MambaConfig, MambaBackendEnum
from vllm.config import VllmConfig
c1, c2, c3 = VllmConfig(), VllmConfig(mamba_config=MambaConfig(backend=MambaBackendEnum.FLASHINFER)), VllmConfig(mamba_config=MambaConfig(stochastic_rounding_philox_rounds=4))
print(c1.compute_hash(), c2.compute_hash(), c3.compute_hash())
"
```

- Before this change all three print `14d03884cc` (collision). After, they print `30d3023943` / `6bd3c3b2d3` / `b89ca637ad`.
- `test_vllm_config_hash_covers_mamba` fails without the `mamba_config` factor include and passes with it (red-green).
- Targeted config hash + mamba tests: `8 passed`. `pre-commit run --files vllm/config/mamba.py vllm/config/vllm.py tests/test_config.py` passes (mypy, SPDX, config-docstring checks).
- Full `tests/test_config.py` on this head: `43 failed / 454 passed / 9 skipped`. The 43 are pre-existing environmental failures (HF model-download `OSError` for `meta-llama`/`RedHatAI` ids and `test_ir_op_priority_ctx`), none of which touch `compute_hash` or Mamba; the hash/mamba tests all pass. No GPU serving or model-quality evaluation is claimed.

Prepared with AI assistance. I reviewed every changed line and ran the validation above; the pre-existing full-suite environmental failures are kept separate from the change's own evidence.

## Details

`compute_hash` is the identity for the persistent AOT/compile cache (`aot_compile_hash_factors` and the runtime compile cache both key on `vllm_config.compute_hash()`). It is documented to capture every config that affects the graph from input ids to final hidden states. `mamba_config` was missing from the factor list even though it changes the compiled graph:

- `MambaMixer2`'s decode path branches on `mamba_config.backend` and calls a different custom op per backend (`selective_state_update_replayssm_flashinfer` vs `selective_state_update_replayssm_output_only`).
- `enable_stochastic_rounding` / `stochastic_rounding_philox_rounds` specialize the compiled Triton kernel (e.g. the `USE_RS_ROUNDING` template arg), and `ssu_algorithm` selects the update algorithm.

Because the traced code hash is identical across these settings (same source files), the config hash was the only separator and it ignored `mamba_config`, so the cache served the wrong compiled artifact. The fix adds `MambaConfig.compute_hash()` (reusing the existing `hash_factors(get_hash_factors(...))` pattern) and folds it into `VllmConfig.compute_hash()` alongside the other always-present configs.

This is a cache-identity correction: changing Mamba settings now correctly causes a recompile rather than reusing an artifact built for a different backend/kernel.
