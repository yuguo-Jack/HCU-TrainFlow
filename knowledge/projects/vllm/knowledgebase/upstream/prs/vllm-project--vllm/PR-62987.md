# [Perf][Spec Decode] Enable torch.compile for GLM-4 MoE MTP draft model

[Upstream PR](https://github.com/vllm-project/vllm/pull/62987) · state: open · merged: False

## Original PR description

## Overview

This PR adds `@support_torch_compile` to `Glm4MoeMTP`, as `DeepSeekMTP`, `Qwen3NextMTP`, `ExaoneMoeMTP` and
`OpenPanguMTP` already have. The change is identical to #44508 by @omirosh, who is credited as
co-author. #44508 has been open since June without an approval and is behind main, so this re-submits the same change on current
main with H100 evidence. @omirosh has agreed to close #44508 once this lands.

## Claims

- **What changes:** the GLM-4 MoE MTP drafter runs through vLLM's compiled and piecewise-CUDA-graph path instead of
  eager mode. This enables the fusion passes and cuts the number of kernel launches between target verifications.
- **Measured effect:** about 3% higher throughput and 3% lower TPOT on GLM-4.5-Air-FP8 (TP4, current main), with
  acceptance and gsm8k unchanged. An earlier TP8 GLM-4.7-derived run showed 9.1% lower mean E2E latency.

## Validation

- **Lint:** `ruff check`, `ruff format --check` and `mypy` (py3.11) are clean.
- **E2E on current main** (post-merge image `059e2de6`, `zai-org/GLM-4.5-Air-FP8`, TP4 on 4×H100, k=3, MRV2).
  Both arms include the normalized-feedback fix (the change consolidated in #62234), and the pair was repeated with the GPU halves swapped.
  - Workload: gsm8k (1,319 questions, temperature 0) plus `vllm bench serve` (random 1024 in / 256 out, 400
    prompts, concurrency 32).

  | | Output tok/s | Mean TPOT | gsm8k wall time | gsm8k | Mean accept. len |
  |---|---|---|---|---|---|
  | eager drafter (2 runs) | 1338.5 / 1331.1 | 22.69 / 22.77 ms | 25.45 / 24.78 s | 0.898 / 0.917 | 3.135 / 3.139 |
  | **this PR** (2 runs) | **1376.5 / 1371.3** | **22.02 / 22.08 ms** | **24.45 / 24.06 s** | 0.920 / 0.918 | 3.144 / 3.146 |

  - Averaged: +2.9% throughput, −3.0% TPOT, −3.4% gsm8k wall time.
  - On main without that fix (single pair): +1.1% throughput, −3.1% gsm8k wall time.
- **Earlier E2E A/B (context):** GLM-4.7-derived FP8 checkpoint, TP8, 8×H100, vLLM 0.28, k=3, agentic multi-turn
  traffic, matched 2,083-request replay. Mean E2E latency went from 7.14 s to 6.50 s (−9.1%), and the median
  kernels between target verifications fell from 482 to 236.

## Details

- **Signature:** `dynamic_arg_dims` is inferred from the existing annotations (`input_ids`, `positions`,
  `hidden_states`, `intermediate_tensors`, `inputs_embeds` on dim 0). `spec_step_idx` is a Python int.
- **Limitation:** the compiled wrapper drops Dynamo guards. A checkpoint with `num_nextn_predict_layers > 1` would
  therefore reuse the graph traced for layer 0 on later draft steps. Speculation is lossless, so the cost would be
  acceptance, not correctness. Every published GLM-4.x checkpoint (4.5, 4.5-Air, 4.6, 4.7) has one MTP layer, and
  `DeepSeekMTP` uses the same pattern. An `enable_if` gate on a single MTP layer can be added if reviewers prefer.
- **Tests:** none added. The already-decorated MTP models (`Qwen3NextMTP` #24526, `ExaoneMoeMTP` #31621,
  `OpenPanguMTP` #27521) also shipped the decorator without a dedicated compile test. `Glm4MoeMTP` already
  has a `tests/models/registry.py` entry. A GLM MTP e2e case would need a checkpoint larger than CI allows.
- **Relation to #62234:** independent of the GLM-4 MTP normalized-feedback fix in #62234. The two touch different
  parts of `glm4_moe_mtp.py` and merge cleanly in either order. The gain above was measured with that fix applied, and
  separately on plain main.
