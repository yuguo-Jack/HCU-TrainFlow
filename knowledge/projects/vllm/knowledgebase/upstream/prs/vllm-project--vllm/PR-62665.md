# [Bugfix][CPU] Reject unsupported --kv-cache-dtype at CPU attention backend selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/62665) · state: closed · merged: True

## Original PR description

## Overview

Fixes #62664. The CPU platform now rejects `--kv-cache-dtype` values its attention backends can't handle, at backend selection instead of silently accepting them.

## Claims

- `turboquant_*`, `ultraquant_4bit`, `nvfp4` and `int8_per_token_head` on CPU fail at startup with a clear `ValueError`. Before this, turboquant/ultraquant ran and produced garbage (see the issue).
- `fp8*` is accepted only on hosts with AVX-512 or AMX, the same rule the kernel already enforces after weight loading.
- The MLA path on CPU accepts only unquantized dtypes.
- `auto`, `bfloat16` and `float16` are unchanged.

## Validation

macOS arm64 (Apple M4 Pro), CPU source build, on main @ e4a676cdc2.

| Check | main | this PR |
|---|---|---|
| `pytest tests/kernels/attention/test_cpu_attn.py -k "kv_cache_dtype_validation or rejects_quantized"` | 6 failed, 5 passed | 11 passed |
| `test_cpu_attn.py`, `tests/platforms/test_cpu.py`, `test_attention_selector.py`, `tests/config/test_kv_cache_dtype.py` | | 912 passed, 0 failed (x86-only cases skipped) |
| `pre-commit run --files <changed files>` | | passed |
| `LLM("Qwen/Qwen2.5-0.5B-Instruct", kv_cache_dtype=...)` | `auto` OK; `turboquant_k8v4` garbage; `fp8` fails after weight load | `auto` OK ("Paris"); `turboquant_k8v4`, `ultraquant_4bit`, `fp8` raise `ValueError` before weight load |

I could not run on x86. The AVX-512 path, where fp8 is accepted, is covered by the test through a monkeypatched ISA check.

Update: @adenzhou1350 independently tested this on Linux x86 with AVX-512 (no AMX): the 11 tests pass, the parent commit fails 6, and `turboquant_k8v4` is rejected before weight loading (see their comment).

## Details

- Root cause: unlike CUDA/ROCm/XPU, `CpuPlatform.get_attn_backend_cls` never checked the backend's supported KV cache dtypes, so `CPUAttentionBackend.supported_kv_cache_dtypes` was never enforced. The CPU kernel treats any dtype other than fp8 as `auto`, so the unsupported formats got bf16 writes into a uint8 cache.
- I override `supports_kv_cache_dtype` instead of calling the full `validate_configuration`. The full check also validates head size and block size, which would change behaviour for models that work today.
- Custom dtypes registered through #52670 are rejected on CPU until the CPU backend declares support for them.
- Compatible with #61168: its `ultraquant_4bit` routing returns before this check, and the test doesn't parametrize `ultraquant_4bit`.
- CI: the test is in `test_cpu_attn.py` (CPU kernel tests job). That job doesn't list `vllm/platforms/cpu.py` as a dependency. I left the CI config alone.
