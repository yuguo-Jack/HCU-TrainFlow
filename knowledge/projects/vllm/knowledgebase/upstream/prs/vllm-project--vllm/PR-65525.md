# [ROCm][UMBP][Muse Spark] Support UMBP for Muse Spark Open, keeping the decode monokernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/65525) · state: open · merged: False

## Original PR description

## Overview

Wire `UMBPStoreConnector` (standalone mode) to Muse Spark Open on ROCm. The stock path already worked; the `--monokernel` deployment guard refused every KV connector. It now accepts a connector that only restores whole blocks of this cache layout, so UMBP and the monokernel run together. Follows #64715 (DeepSeek-V4.1-Flash); the `only_restores_canonical_kv` API is the same hunk as in #64715 and #63002, so this PR rebases away once either merges. Draft for review.

## Claims

- Muse Spark Open (TP8, expert parallel, DSpark) serves with `UMBPStoreConnector`, with and without `--monokernel`. Prefixes evicted from the GPU prefix cache are restored from the pool.
- With `--monokernel`, a KV connector no longer disables the kernels when it only restores canonical blocks (UMBP). Other connectors are still refused.
- No change for other connectors, models or platforms.

## Validation

8x MI355X, standalone UMBP server (`mori` 1.2.3.post1), upstream main `c1d8fade8d` plus #65125 (a separate Muse DSpark loader fix needed to start the draft on main).

**Restore smoke (stock and `--monokernel`).** ~19K-token prompt, `POST /reset_prefix_cache`, resend: 19,280 of 19,285 tokens restored from the pool. Greedy output is identical between GPU prefix hits and UMBP restores (4 repeats each, one distinct answer in both).

**Guard test.** `pytest tests/models/test_muse_spark_rocm_mono.py -k deployment_guard`: 3 passed (UMBP accepted, `ExampleConnector` refused).

**AgentX** (`semianalysis_cc_traces_weka_062126`, synthetic acceptance 4.05, DSpark K=7, prefix caching, c40, TP4 + expert parallel, stock decode since the monokernel needs TP8). GPU KV pool is 6.7M tokens, so the working set overflows it. Two 4-GPU servers ran at the same time, a UMBP arm and a baseline arm, so each pair shares the machine. UMBP pool 768 GiB, default connector options.

| Arm | Runs | Completed requests | Output tok/s | TTFT p90 | ITL p50 / p90 | Restored tokens |
|---|---|---|---|---|---|---|
| baseline | 4 | 298-315 | 140-155 | 257-348 s | 13.3-18.2 / 131-139 ms | - |
| UMBP (eager store, default) | 2 | 362-368 | 174-195 | 158-168 s | 11.8-12.9 / 171-200 ms | 23-35% |
| UMBP with `lazy_offload` (#61797) | 2 | 292-299 | 118-120 | 173-253 s | 22-28 / 196-198 ms | 23% |

Eager UMBP is +12% to +38% output tok/s and 35-55% lower TTFT p90, at about 30% worse ITL p90. `lazy_offload` was about 15% slower than the baseline in both runs. Four baseline runs vary by about 5%.

At TP8 (monokernel, GPU pool 21M tokens, c13) nothing is evicted and UMBP is 7-9% slower (interactivity p50 238 vs 263, p90 117 vs 126): the connector stores blocks after every step and nothing is restored. At c128 both arms are overloaded (max-num-seqs 16) and equal.

## Details

- **Why UMBP is safe for the kernels:** the connector namespace fingerprints every per-layer KV spec, so only whole blocks written by this cache layout can be restored. The kernels read KV through the block table and write through the slot mapping, as before.
- **Muse needs no TP-replicated-group dedup** (the other half of #64715): its GQA KV is sharded by head, one distinct copy per rank.
- **Known cost:** with eager stores UMBP adds tail ITL at c40 (p90 about +30%) and a small overhead when nothing is evicted. The lazy-offload option from #61797 was slower in both runs.
- **Two UMBP engines on one node:** two standalone servers running engines at the same time blocked in MORI (stores submitted, none completed, requests stalled), so the pairs above run one UMBP arm against one baseline arm.
- **Not covered:** CI cannot run the kernels (8x MI355X and the checkpoint). Runs are short single-point measurements, so treat the numbers as indicative.
- **Docs:** `vllm/models/muse_spark/amd/mono/README.md` now states the connector rule.
- **Not a duplicate:** open-PR searches for Muse Spark and UMBP, and for `only_restores_canonical_kv`, found only #64715 and #63002 (DeepSeek, same base API).
