# [Rust Frontend] Reject silently dropped request fields on chat, completions, and generate

[Upstream PR](https://github.com/vllm-project/vllm/pull/62434) · state: open · merged: False

## Original PR description



## Overview

The Python frontend honors several request fields on chat, completions, and `/inference/v1/generate` that the Rust frontend silently drops: chat and tokenize ignore unknown keys through serde defaults, and completions and generate collect them into an unused catch-all map. A client that sets one of these fields today gets a 200 with output that ignores it. This PR declares each field on the Rust DTO and returns an explicit 400 for non-default values, while absent, `null`, and Python's default value still pass, so requests from SDKs that send defaults are unaffected. It also fixes two trivial gaps: `length_penalty: 1.0` is accepted, and generate's `sampling_params.extra_args` reaches the engine.

## Claims

- Chat and completions return 400 for `return_weight_versions: true`; chat returns 400 for `return_prompt_text: true`; completions returns 400 for any `prompt_embeds` (Python also rejects it unless `--enable-prompt-embeds`, which the Rust frontend does not support).
- `/inference/v1/generate` returns 400 for `output_mode: "text"`, for non-empty `sampling_params.stop` or `include_stop_str_in_output: true`, and for any `sampling_params.trace_decode_token_ids`. `output_mode` is typed as an enum mirroring Python's `OutputMode`, and `stop` reuses the `StringOrArray` type chat and completions use, so malformed values fail deserialization as in Python.
- Chat and completions accept `length_penalty: 1.0` (Python's default), which previously got a 400; other values are still rejected.
- `/inference/v1/generate` accepts `sampling_params.extra_args` (Python's `SamplingParams` field name) as an alias of `vllm_xargs`, so it reaches the engine instead of being dropped.

## Details

Field-by-field Python anchors (all checked on current `main`):

| Route | Field | Python default | Python consumer | Rust behavior after this PR |
|---|---|---|---|---|
| chat, completions | `length_penalty` | `1.0` | beam search only | accept `1.0`; 400 otherwise (unchanged) |
| chat | `return_prompt_text` | `None` | adds `prompt_text` to the response | 400 when `true` |
| chat, completions | `return_weight_versions` | `false` | adds per-choice `weight_versions` spans | 400 when `true` |
| completions | `prompt_embeds` | `None` | renderer; 400 unless `--enable-prompt-embeds` | 400 when present |
| generate | `output_mode` | `"tokens"` | `"text"` returns detokenized text and decoded logprobs | 400 for `"text"` |
| generate | `sampling_params.stop`, `include_stop_str_in_output` | `None`, `false` | detokenizer stop matching | 400 for non-empty `stop` or `true` |
| generate | `sampling_params.trace_decode_token_ids` | `None` | engine trace replay; 400 unless `--enable-trace-replay` | 400 when present |
| generate | `sampling_params.extra_args` | `None` | engine `extra_args` | serde alias of `vllm_xargs` |

Ownership and layering:

- Protocol fields belong to the server DTOs, so every check sits at the HTTP boundary in each route's existing `validate_request_compat`, before lowering, using `bail_invalid_request!`.
- Generate sampling fields that the shared `vllm_text::SamplingParams` does not model are declared on the existing `GenerateSamplingParams` wrapper, next to `n`, which exists to reject such keys explicitly instead of dropping them.
- `extra_args` is a `#[serde(alias)]` on `vllm_text::SamplingParams::vllm_xargs`. That type is flattened into the generate DTO and already owns the field; lowering and transfer-param merging are unchanged.

Limitations and follow-ups:

- `stop` / `include_stop_str_in_output` and `output_mode: "text"` on the generate route are rejected until the route detokenizes. Both need the same text-layer detokenizer on the token-only route and are left as a follow-up; vllm-project/vllm#51904 (open, no activity since 2026-09-29) implements stop strings there and would replace this placeholder.
- `return_weight_versions` is a placeholder only. The spans already reach the engine output, and `/inference/v1/generate` already returns them; wiring them through chat and completions (including stop-string truncation) is a separate change.
- `length_penalty` only matters for beam search, which the Rust frontend does not implement; vllm-project/vllm#47705 (open, no activity since 2026-08-05) adds beam search and replaces this check.

Behavior change: requests that set these fields to non-default values used to get a 200 with the field ignored and now get a 400. The most likely case is P/D pipelines that render with the Python frontend and generate with the Rust frontend while forwarding client stop strings: generation used to run past the stop, and now fails explicitly. Python render's empty `stop: []` and `include_stop_str_in_output: false` still pass.

Not a duplicate: open PR searches for each field found no PR adding these checks. The related open PRs are vllm-project/vllm#51904 and vllm-project/vllm#47705 above, which implement the features behind two of the placeholders, and vllm-project/vllm#56814, which touches `vllm_xargs` reserved keys and is orthogonal to the `extra_args` alias.
