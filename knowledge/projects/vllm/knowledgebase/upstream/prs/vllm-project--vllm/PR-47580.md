# [Perf] Keep H2D transfers dense in fused-MoE weight loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/47580) · state: open · merged: False

## Original PR description

## Purpose

Fix the root cause of #31624: ModelOpt Llama-4 (Scout/Maverick FP8) checkpoints take 68s-495s to load depending on hardware, dominated by H2D copies from non-contiguous CPU tensors.

These checkpoints store expert weights fused as `[num_experts, hidden_in, hidden_out]`. `Llama4Model.load_moe_expert_weights` transposes to the runtime orientation with a stride-only view, so `RoutedExperts._load_w13`/`_load_w2` end up calling `expert_data.copy_(loaded_weight)` with a non-contiguous CPU source. ATen materializes `src.contiguous()` on the CPU first, and for fp8 that gather has no vectorized path, so it costs 3-4s per expert tensor. That is where the load time goes.

Per https://github.com/vllm-project/vllm/issues/31624#issuecomment-3706297841, the fix should keep the CPU weights contiguous rather than move checkpoint tensors to the GPU. This PR does that by flipping the strided side of the copy to the destination:

```python
expert_data.transpose(-1, -2).copy_(loaded_weight.transpose(-1, -2))
```

`loaded_weight.transpose(-1, -2)` undoes the earlier view and recovers the contiguous on-disk slab at zero cost, so the H2D transfer is dense. The layout transform runs as a strided device-side write into the existing parameter storage. No copy of `loaded_weight` is retained in GPU memory at any point; ATen's transient staging buffer is allocator-managed inside the copy op. TP-narrowed slabs (unit inner stride, padded row pitch) degrade to host row-run memcpys instead of an elementwise gather and then take the same dense path. That is the case that defeated the shard-first experiment in the issue thread.

Implemented as one helper (`_copy_h2d_dst_strided`) applied at the three expert-weight copy sites in `routed_experts.py`. Contiguous sources are unaffected (byte-identical behavior). Since the fix lives in the fused-MoE loader rather than `llama4.py`, it applies to any model whose checkpoints arrive transposed.

Prior attempts on the issue, for context:

| Approach | Load time | Status |
|---|---:|---|
| Baseline | 68-78s | |
| Full-tensor CPU `.contiguous()` | 88s | worse than baseline |
| Final-slice CPU `.contiguous()` (#32081) | ~60s | independently benchmarked; #46766 takes the same approach |
| GPU-first transpose | 23-37s | rejected over GPU memory lifecycle |

This PR targets the 23-37s class without moving checkpoint tensors to the GPU.

Rebased onto main. The conflict was with #54699, which landed in `_load_w2` a few hours ago, so it is worth spelling out how it resolved rather than just saying "rebased".

#54699 added a bounded write for a strided destination:

```python
if (loaded_weight CPU and expert_data CUDA and not expert_data.is_contiguous() and ndim == 2):
    loaded_weight = loaded_weight.contiguous()
    # chunked row copies, to cap the device temporary
```

That keys on the **destination** being strided. This PR keys on the **source** being strided. They are not the same condition, and both can hold at once, which matters because this PR deliberately moves the stridedness onto the destination. That is precisely the pattern #54699 exists to bound. So taking either side alone would have been wrong: dropping theirs regresses a memory bugfix, dropping mine keeps the CPU gather.

Resolved by composing them. The chunked write is now `_copy_h2d_bounded`, and every path through `_copy_h2d_dst_strided` routes its destination write through it:

| source | path | CPU gather | destination write |
|---|---|---|---|
| transposed view | undo transpose | none | bounded |
| TP-narrowed | row-run contiguate | row-runs, not elementwise | bounded |
| doubly strided | unavoidable gather | elementwise | bounded |
| already dense | passthrough, the #54699 case | none | bounded |

So #54699's guarantee holds on all four, including the two this PR adds, and the CPU gather is still removed in the case the issue is about.

Two notes:

- I did not extend this to the bias load at the bottom of `weight_loader`. It is 1-D, so neither `ndim >= 2` here nor `ndim == 2` in #54699 applies, and biases are small enough that neither rationale does either. Left deliberately.
- Tests: added a strided-destination parametrization across all three source layouts and a direct test that `_copy_h2d_bounded` splits a strided write and passes a contiguous one through. Verified byte-identical to `dst.copy_(src)` for all eight source/destination-layout combinations, and that a 17 MB strided write becomes 16 chunks of about 1.05 MB rather than one 17 MB staging buffer. `ruff check` and `ruff format` clean.

What I have **not** verified is peak device memory on real hardware, because `pre-run-check` still has not let CI run on this and I do not have a GPU attached at the moment. My original description said no extra device memory is *retained*, which is about retention rather than peak, and #54699 is specifically about peak. If a maintainer adds `ready` I would rather the runner settle that than keep asserting it.

- JosephYouNew · comment · 2026-10-26T11:17:19Z · [source](https://github.com/vllm-project/vllm/pull/47580#issuecomment-6414699984)

Thanks for this PR — the dst-side flip is the right fix for #31624, and the
byte-identical contract (uint8-view comparison to defeat fp8 NaN equality) plus
the broadcast-chunk test give me good confidence. A few concrete points from a
line-by-line pass on top of current main:

**1. Bounded chunking can exceed the 1 MiB bound when rows are few.**
`_copy_h2d_bounded` computes `num_chunks = cdiv(src.nbytes, _H2D_CHUNK_BYTES)`,
but `torch.chunk(..., dim=0)` cannot produce more chunks than rows. For a
strided dst with e.g. 2 rows × 2 MiB, `cdiv` says 4 while `chunk` yields 2, so
each staged temporary is 2 MiB rather than the documented ~1 MiB bound. Real
MoE slabs have hundreds of rows so this is theoretical today, but the clamp is
one line:

```python
num_chunks = min(max(cdiv(src.nbytes, _H2D_CHUNK_BYTES), 1), dst.shape[0] or 1)
```

**2. Coverage gap: the "neither orientation is dense" fall-through is untested.**
The three tested layouts (contiguous / transposed / tp_narrowed) all route to
the first two branches. `_copy_h2d_dst_strided`'s last-resort path
(`src.contiguous()` + bounded dst write) is only reachable with a non-unit
inner stride, e.g. `base.transpose(-1, -2).narrow(1, 0, 16)`. Adding that as a
fourth `layout` in `_make_src` would pin down the fallback's correctness too.

**3. Fourth copy site intentionally left as plain `copy_`?**
`routed_experts.py:815` (the `w2` bias path in the expert-bias branch) still
uses `expert_data.copy_(loaded_weight)`. I believe that's fine — expert biases
are 1-D/small so the helper's `ndim >= 2` guard would fall straight through —
but worth a one-line comment in the PR description so future readers don't
read it as an oversight.

**4. Datapoint request for the TP>1 row-run path.**
The `stride(-1) == 1` branch (TP-narrowed slabs) still pays a row-run memcpy
on the host; @jadechip's 2.2x B200 datapoint was TP=2, while the per-copy
microbenchmarks are TP=1. A sentence in the PR body on expected gain for
TP>1 (where the row-run branch is the hot path) would set expectations
correctly for operators.

Also confirming the PR applies cleanly on current main: the `_load_w2` inline
block it removes matches main byte-for-byte, and `cdiv` is already imported,
so no rebase obstacles from the last month of main.

Nice work — the generalization to `routed_experts.py` (any transposed fused-MoE
checkpoint, not just Llama-4/ModelOpt) is what makes this the fix #31624
needs, rather than another `.contiguous()` patch.

happy to help test or benchmark follow-ups.
