# [Benchmark] Add per-case kernel profiles to vllm bench forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/61692) · state: closed · merged: True

## Original PR description



## Overview

Add `--profile-dir` to `vllm bench forward` (#61339): a per-kernel GPU time breakdown of each benchmarked batch, in a form an agent or a script can read and compare directly.

## Claims

- `--profile-dir DIR`: after timing, each case's graph is replayed 3 more times under `torch.profiler`. Every rank writes `DIR/<case>.rank<r>.trace.json.gz` (Perfetto) and `DIR/<case>.rank<r>.kernels.json` (GPU time per kernel per forward, sorted, with call counts and one full name per group). Rank 0's top kernels are printed and included in `--output-json`.
- Only the timed forward is counted: the in-graph KV restore and rank rendezvous that precede it in each replay are left out (reported as `pre_forward_us`), so the profile accounts for the same interval as `median_us`.
- `python -m vllm.benchmarks.forward.profile A.kernels.json [B.kernels.json]` prints one summary, or a per-kernel diff of two (e.g. before/after a change) sorted by the largest change.
- Nsight Systems: each case's 3 profiled replays always run between `cudaProfilerStart`/`Stop` in an NVTX range `forward/<case>`, so `nsys profile --capture-range=cudaProfilerApi --capture-range-end=repeat --cuda-graph-trace=node` records just them, one small report per case (and per rank with `torchrun --no-python nsys ...`). `--profile-dir` and nsys can't share CUPTI; combining them fails with a clear message.
- Timing runs before profiling, so reported latencies are unchanged; without a profiler the extra 3 replays per case are the only cost.

## Validation

```

```

Llama-3.2-1B, 1 GPU: profiled forward span vs timed median: decode 1291 vs 1265 us, prefill 4755 vs 4498 us, prefix hit 1782 vs 1770 us (profiler overhead; prefill's own sample spread was 1.75%). Decode excluded 512 restore copies per replay (~830 us), as intended.

Nsight Systems (2025.5), Llama-3.2-1B: one ~680 KB report per case; `nsys stats --report nvtx_sum` shows the `forward/<case>` range and `cuda_gpu_kern_sum` matches the JSON summary (48 calls = 16 layers x 3 replays). ## Details

- Each replay's GPU activities are split into the `len(state_views)` restore copies (one copy each), the rendezvous all-reduce (multi-rank), and the forward. The summary checks that the activities divide evenly into replays and raises otherwise.
- Kernel names are grouped without return type, template and function arguments (`void ns::foo<T>(...)` -> `ns::foo`); generic launchers keep their first template argument (`cutlass::device_kernel<Op>`), CuTe DSL names drop their per-shape suffix. Non-kernel activities (memcpy/memset) keep their names.
- `span_us` is first-to-last forward activity and should track `median_us`; `busy_us` sums kernel durations and can exceed it with multi-stream overlap.
- Why both: `torch.profiler` needs no extra tooling, is scoped per case in-process, and is tested in CI, so it backs the agent-facing JSON summary and diff. Nsight Systems adds NVTX, NCCL, CPU-side and GPU-metric views that many users reach for; the capture range makes it record only the benchmarked replays instead of the whole process (load, JIT, warmup, timing).
- The model-microbenchmark skill gets a short "Kernel breakdown" section on both workflows (including keeping `--capture-range-end=repeat`, since nsys's default stops after the first case and leaves the bench hanging).
- Size: `profile.py` ~200 lines plus ~40 lines of wiring; tests and docs ~60.
