# [Attention] Enable FA4 sparse MQA decode on Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/55866) · state: closed · merged: True

## Original PR description

[Attention] Enable FA4 sparse MQA decode on Blackwell

This adds `FLASH_ATTN_MLA_SPARSE_FA4`, a sparse MLA backend for Blackwell with a BF16 KV cache. The FA4 CuTe DSL kernel from vllm-project/flash-attention#195 serves decode batches and the decode rows of mixed HiSparse batches. Every other batch runs on the trtllm-gen lane, as in `FLASHINFER_MLA_SPARSE`. At 16 or fewer query heads per rank the backend is the first choice, with and without HiSparse; above that head count it stays opt-in.

The first commit, "Share sparse MLA MQA cache handling", will go up as its own PR and is only here until it lands. It moves index conversion and the HiSparse lane split from the FA3 and FlashInfer sparse MLA backends into `SparseMLACommonImpl.forward_mqa`, so a backend implements only `_forward_mqa_kernel(..., is_decode)`. The design is by @LucasWilkinson. One FA3 behaviour changes with it: FA3's plain path converts top-k through the index group's shared buffer, as FlashInfer already did, instead of once per layer. The values are identical while the layers of a group share block stride, block table and request ids, which index groups guarantee. A test pins leader and follower layers.

The second commit is the FA4 backend on top of that hook:

- `flash_attn_varlen_func` forwards `gather_kv_indices`, `gather_kv_valid_length` and `q_v` to FA4.
- The impl subclasses `FlashInferMLASparseImpl`. Its hook runs the FA4 decode kernel when `is_decode`, otherwise FlashInfer's trtllm-gen call with the LSE converted to base e.
- The metadata builder subclasses the FlashInfer TRTLLM builder and declares `UNIFORM_BATCH` CUDA graph support. Inheriting the builder brings the DCP workspace pre-size: an earlier version of this PR used the default 394 MiB trtllm workspace on its prefill lane and crashed under DCP 2 on a prefill step of about 8192 tokens, where the softmax-stats slab needs 513 MiB.
- The backend class subclasses the FlashInfer TRTLLM backend for its gates (PCP with DCP rejected, head dims) and adds the FA4 gates: `index_topk` a multiple of 128, and a supported gathered head count under DCP.
- Under HiSparse, decode reads the hot buffer through the shared lanes. The inherited `autotune_hisparse_decode` compiles the FA4 kernel before graph capture.
- FA4 shares FlashInfer's masked-MHA thresholds.
- FA4 joins `_uses_flat_kv_cache`, since it reads the same flat KV cache as FlashInfer.

The last commit bumps the flash-attention pin to vllm-project/flash-attention 2e3a6694, which has #195 and the sparse decode split-rule tuning for DCP shapes (vllm-project/flash-attention#200).

## Performance

GLM-5.2 NVFP4-FP8 with BF16 KV on B300, TP4, FA4 against `FLASHINFER_MLA_SPARSE` from the same tree (this PR on `main` d71f662606), change in median ITL (negative favours FA4). Plain and DCP 2 are averaged over two runs. The HiSparse column assumes #59309 is merged: it applies that PR's diff, pins the MoE autotune tactics so both backends run the same MoE kernels, and averages two server starts with two runs each.

| Input / concurrency / output | TP4 plain | TP4 DCP 2 | TP4 HiSparse |
|---|---:|---:|---:|
| 4096 / 8 / 256 | -4.2% | -6.7% | -0.8% |
| 4096 / 128 / 256 | -4.3% | -2.3% | +1.3%* |
| 32768 / 16 / 256 | -5.3% | -5.1% | +0.2% |

\* One FA4 run measured 35.2 ms against 33.4 to 33.7 ms for the other three; without it the figure is +0.1%.

Under HiSparse FA4 is on par with FlashInfer, which did not justify a separate priority order. Per decode step, FA4's attention kernels take about 190 µs less than FlashInfer's at 4096 / 8, but start-to-start variance in all-reduce time is larger than that difference. On current `main`, #59235 makes HiSparse about 0.45 ms per decode step slower for both backends, because it writes `request_ids` in every layer. #59309 moves those writes into the group leader's resolve, which brings the 57 follower layers' 171 kernels per step back out of the decode graph.

## Validation

- `pytest tests/v1/attention/test_sparse_mla_backends.py`: 475 passed, 672 skipped. `pytest tests/v1/e2e/general/test_hisparse.py`: 5 passed (FlashInfer and FA4). The FlashInfer, KV cache layout, backend selection and masked-MHA routing tests pass as well.
- Serving, GLM-5.2 NVFP4-FP8, TP4, HiSparse, GSM8K (500 questions, 5-shot): FA4 0.936, FA4 with MTP 0.948, FlashInfer 0.946. No invalid responses; 8K, 16K and 30K needle prompts answered correctly.
- FlashInfer on the shared base: latency within noise of `main`, plain generations byte-identical.
- The FA3 sparse backend did not run on hardware here (SM90 kernel, SM100 machine); its change is covered by unit tests only.

AI-assisted. The September 7 upstream search found no matching open FA4 sparse-MLA integration PR; related platform-specific work does not provide this SM100 backend.
