# [Bugfix][KV Offload] Derive the namespace cache dtype from the KV cache specs

[Upstream PR](https://github.com/vllm-project/vllm/pull/56928) · state: open · merged: False

## Original PR description

Closes #56894

## What

The native offloading secondary-tier namespace identity is built from `cache_config.cache_dtype` on the scheduler side. Sparse MLA workers normalize that field in place (`fp8` -> `fp8_ds_mla`) inside `MLAAttention` construction, which runs in the worker process. With the default `uni` executor the worker shares the EngineCore process so the scheduler sees the rewrite; with `mp` it never leaves the worker. The same model then writes to two different namespaces depending on the executor, cross-engine hits drop to zero, and a TP1 engine that later gains `--distributed-executor-backend mp` can no longer see the blocks it wrote before restart.

## How

The KV cache specs travel from the workers at registration, so `MLAAttentionSpec.cache_dtype_str` carries the normalized dtype string under both executors. `build_offloading_config` now derives the model identity dtype from the specs when they agree on one, and keeps the config knob when they do not or carry no string (non-MLA specs leave `cache_dtype_str` at its `None` default, so nothing changes for everyone else).

First ping, four weeks in with CI green. The failure this closes is quiet but real: the offload namespace identity is derived from cache_dtype, sparse MLA workers rewrite that field inside their own process, and under the mp executor the scheduler never learns about it, so the same model writes to two namespaces and cross-engine hits drop to zero. Deriving the namespace from the KV cache specs keeps every executor on one identity. Could a maintainer take a look when there is a moment?
