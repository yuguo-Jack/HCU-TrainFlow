# [Bugfix][Model] Fix EXAONE-4.5 image inputs: ViT received un-normalised pixels

[Upstream PR](https://github.com/vllm-project/vllm/pull/61104) · state: closed · merged: True

## Original PR description



## Overview

EXAONE-4.5 (`Exaone4_5_ForConditionalGeneration`) produces garbage for any request that contains an image on every release since #50411 (v0.29.0, v0.30.0, v0.31.0, main). Text-only requests are unaffected.

Root cause: the class inherits `supports_mm_device_do_normalize = True` from `Qwen2_5_VLForConditionalGeneration`, so `mm_device_do_normalize` defaults to on and the HF processor is told `do_rescale=False, do_normalize=False`. But `EXAONE4_5_VisionTransformer` is constructed without `input_norm`, so the inherited `Qwen2_5_VisionTransformer` uses `IdentityInputNorm` and the ViT receives raw 0–255 pixels.

Two smaller issues in the same constructor are fixed alongside, since they are the same missing wiring relative to the parent class:

- `self.model_config` and `self.video_pruning_rate` are never set, but the inherited `embed_multimodal` / encoder-CUDA-graph paths read them (`AttributeError` with `--compilation-config '{"cudagraph_mm_encoder": true}'`).
- The MTP drafter (`Exaone4_5MultiTokenPredictor`) builds its `Exaone4DecoderLayer` without `cache_config`, so the drafter's attention ignores `--kv-cache-dtype`.

## Claims

- With the fix, image requests give coherent answers and are identical to the pre-#50411 behaviour (processor-side normalisation); text-only outputs and MTP acceptance are unchanged.
- No API change: the device-side normalisation feature stays on by default for this model, now with the correct normalisation module (`build_mm_input_norm(model_config)`), exactly as `Qwen2_5_VLForConditionalGeneration` does.
- Users on affected releases can work around it with `--no-mm-device-do-normalize`.

## Validation

`LGAI-EXAONE/EXAONE-4.5-33B-FP8`, TP=2, 2× A100-SXM4-40GB, greedy, thinking off, image = the model card's `assets/exaone45_input1.jpg` (a bowl of kimchi):

| | "Describe this image in one sentence." | gsm8k-50 (text only) |
|---|---|---|
| main (default flags) | `The\n</think>\n</think>one\n</think>…/or/or/or/or/or…` | 0.90 |
| this PR (default flags) | `A person in a light blue shirt is serving freshly made kimchi from a large black bowl into a smaller black dish, …` | 0.90 |

Second prompt ("What objects are in this image? List them.") shows the same pattern: `/or/or/or…` before, a correct itemised list (kimchi, dark ceramic bowl, …) after.

- `pre-commit` passes (ruff, mypy, typos).
- CI: the model is 33B and not in the multimodal generation test lists; the processing test (`tests/models/multimodal/processing/test_common.py`) already covers it and still passes.

## Details

- `exaone4_5.py`: `EXAONE4_5_VisionTransformer.__init__` gains `input_norm` and forwards it to `Qwen2_5_VisionTransformer`; `Exaone4_5_ForConditionalGeneration.__init__` passes `input_norm=build_mm_input_norm(self.model_config)` and sets `self.model_config` / `self.video_pruning_rate` like the parent.
- `exaone4_5_mtp.py`: pass `cache_config=vllm_config.cache_config` to the MTP decoder layer.

Not in this PR (follow-ups): `Exaone4Model` lacks `EagleModelMixin` although the VLM advertises `SupportsEagle3` (asserts at load); `EXAONE4_5_VisionTransformer` builds and discards the full Qwen2.5 MHA block stack in `super().__init__` before replacing it with GQA blocks.

Duplicate-work check: no open PR or issue mentions EXAONE-4.5 image output, `mm_device_do_normalize` for EXAONE, or `exaone4_5` (searched `exaone4_5`, `EXAONE-4.5`, `mm_device_do_normalize input_norm`; the closed #45071 / #42281 are different bugs).
