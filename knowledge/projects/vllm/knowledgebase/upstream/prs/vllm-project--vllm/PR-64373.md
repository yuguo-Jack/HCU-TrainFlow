# [Quantization][GLM-5.3] Let online quantization reach the BF16 attention projections

[Upstream PR](https://github.com/vllm-project/vllm/pull/64373) · state: open · merged: False

## Original PR description

## Overview

GLM-5.3-Flash builds its BF16 attention projections (KDA, MLA, DSA indexer) with `quant_config=None`, so online quantization requested with `--quantization-config '{"targets": ...}'` silently skips them. This PR passes them only that explicitly requested online config, so they can run in MXFP8. Related: #59833, #55741 (see Details).

## Claims

- **Online quantization now reaches the 112 BF16 attention projections** of GLM-5.3-Flash when `--quantization-config` names them. On `nvidia/GLM-5.3-Flash-NVFP4`, the targets under Recommended configuration now quantize 196 layers (attention + shared experts) instead of 84 (shared experts only).
- **No behavior change otherwise:** without `--quantization-config` nothing changes; the checkpoint's own method never applies to these BF16 weights; `kv_b_proj` stays unquantized; the `--quantization mxfp8` / `fp8_per_*` shorthands keep these projections BF16, as today. No change to shared quantization code, no new flag.
- **Recommended, behavior-preserving configurations** (MXFP8 on the 128 non-KDA projections for aggregated serving; MXFP8 on all 196 on prefill instances only for disaggregated serving) keep accuracy and output length unchanged on 7 benchmarks, and give +2% output throughput (aggregated) and up to +12% (disaggregated, prefill-bound) on GB300.
- MXFP8 on all 196 projections in aggregated serving is faster still (+8% on GB300), but measurably shortens reasoning; this PR describes it as an opt-in with that disclosure.

## Details

### Why the projections were unreachable

GLM-5.3-Flash loads its attention projections as BF16 in every checkpoint:

- KDA `in_proj_qkvbfg_a`, `f_b_proj`, `g_b_proj`, `o_proj`;
- MLA `fused_qkv_a_proj`, `q_b_proj`, `o_proj`;
- DSA indexer `wq_b`.

The KDA and indexer projections are BF16 in every official checkpoint. The MLA projections are BF16 in the NVFP4 checkpoint and block-FP8 in the Z.ai FP8 checkpoint, which vLLM dequantizes to BF16 at load (`_try_load_fp8_attn_proj`). The model therefore builds all of them with no quant config: MLA passes `quant_config=None`, and KDA clears `vllm_config.quant_config` around its constructor. With `--quantization modelopt_fp4 --quantization-config '{"targets": {...}}'`, composition with the checkpoint method works for the shared-expert linears (84 layers) but silently skips the 112 attention projections. No warning is printed.

### What changes

`bf16_projection_quant_config()` in a new hardware-neutral `vllm/models/glm5next/quant_config.py` (following the model-level `quant_config.py` of `deepseek_v4` / `deepseek_v41`) returns the config these projections get:

- with a quantized checkpoint, the online config composed through `--quantization-config` (any form);
- with a BF16 checkpoint (`--quantization online`), that config only when it names `targets`;
- otherwise `None`, as today.

Layers that match no online target get `UnquantizedLinearMethod` (existing `OnlineQuantizationConfig` behavior), so the user picks the projections with the `targets` regex. `kv_b_proj` is pinned to `quant_config=None`, because it is absorbed into the W_UK / W_UV bmm weights after loading. Loading is unchanged; the change is construction-time only, with no effect on the forward path when no target matches.

The MLA attention module (`self_attn.attn`) and the indexer now also receive the online config instead of `None`. The online config returns no method for non-linear layers, so the KV-cache scales stay at their defaults, as before. A `targets` pattern that also matches `self_attn.attn` is now rejected at startup ("online quantization is not supported for MLAAttention"), as for DeepSeek-V2, whose MLA attention already receives the quant config; before, it was silently ignored. The recommended patterns below name the projections, so they do not match it.

| file | change |
|---|---|
| `vllm/models/glm5next/quant_config.py` | new: `bf16_projection_quant_config()` (32 lines) |
| `vllm/models/glm5next/common/model.py` | MLA gets `bf16_projection_quant_config(quant_config)` instead of `None` |
| `vllm/models/glm5next/common/kda.py` | KDA projections get the same; the fused conv is unchanged |
| `vllm/models/glm5next/common/attention.py` | `kv_b_proj` pinned to `None` |
| `tests/models/glm5next/test_online_quantization.py` | new, 2 tests (12 parametrized cases) |

No docs change: the projections now follow the existing contract in `docs/features/quantization/online.md` ("Online quantization on unquantized layers from partially-quantized checkpoints"). The GLM-5.3-Flash-specific recommendation stays in this description.

### Recommended configuration

All measurements use NVIDIA's NVFP4 checkpoint, [`nvidia/GLM-5.3-Flash-NVFP4`](https://huggingface.co/nvidia/GLM-5.3-Flash-NVFP4) (revision `da920bb`). Its routed experts and dense MLPs are NVFP4. The 196 projections studied are BF16:

| group | projections | layers |
|---|---|---|
| KDA (34 linear-attention layers) | `in_proj_qkvbfg_a`, `o_proj` | 68 |
| MLA / DSA (11 layers: 3, 7, ..., 43) | `fused_qkv_a_proj`, `q_b_proj`, `o_proj`, `indexer.wq_b` | 44 |
| shared expert (42 MoE layers) | `gate_up_proj`, `down_proj` | 84 |

We tested MXFP8 (E4M3 values, one E8M0 scale per 32 elements, for weights and dynamic activations). Accuracy holds in every configuration. However, MXFP8 on the **68 KDA in/out projections at decode** measurably changes reasoning behavior: traces get 20-30% shorter on AIME/GPQA, with fewer hesitation and self-correction tokens, and accuracy on hard long-output problems trends lower (not significant). The other 128 projections leave behavior unchanged.

| deployment | recommended config | behavior vs BF16 |
|---|---|---|
| **aggregated (or any decode-serving instance)** | **MXFP8 on the 128 non-KDA projections** (MLA, indexer `wq_b`, shared expert); KDA in/out stay BF16 | unchanged: accuracy and output length match BF16 on 7 benchmarks |
| **disaggregated** | **MXFP8 on all 196 projections on the prefill instances only**; decode instances unchanged | decode, which produces nearly all of the output tokens, runs exactly as today |
| opt-in, aggregated | MXFP8 on all 196 projections | **changed**: shorter reasoning, and a possible 1-2 point cost on hard long-output problems |

- **Where the throughput comes from:** the prefill-heavy, large-M GEMMs. The largest projection is KDA `in_proj_qkvbfg_a` (4096 → 24,896), so excluding the KDA projections keeps only part of the gain in aggregated serving (+2% instead of +8% on GB300).
- **Why prefill-only is behavior-preserving:** the behavior change comes from MXFP8 numerics at decode, which pick each next token. With MXFP8 only on prefill instances, prefill computes the KV cache and KDA state in MXFP8, while every generated token after the first comes from BF16 decode. An aggregated variant with exactly that split (MXFP8 for GEMMs of ≥ 2048 tokens, BF16 weights kept for decode; not part of this PR, it needs a second weight copy) showed no length change and no accuracy change: macro +0.09 pt [-0.43, +0.61] over 8 benchmarks. The disaggregated deployment itself was not accuracy-tested.
- **Use the cuBLASLt MXFP8 kernel** (`--kernel-config '{"linear_backend_per_quant": {"mxfp8": "torch"}}'`). On SM10x, the automatic choice (FlashInfer CuTe-DSL) was markedly slower for these shapes at large M. The kernel priority is a separate follow-up.

Commands for the NVFP4 checkpoint. Each regex covers layers 0-44, so the MTP layer (45) is excluded; the K=128 KDA gate projections, `kv_b_proj`, the indexer `wk_weights_proj` and the dense MLPs never match.

<summary>Other checkpoints and other FP8 schemes</summary>

Other checkpoints (static analysis; only the NVFP4 checkpoint was run):

| checkpoint | how to use it |
|---|---|
| shared experts BF16 (NVIDIA NVFP4, RedHat / LibertAI NVFP4, W4A16 quants) | the regexes above |
| shared experts already quantized (Z.ai FP8, RadixArk NVFP4, AMD Quark) | drop the `mlp.shared_experts` alternative (44 or 112 attention layers). With it, those checkpoint methods cannot re-quantize (no `dequantize_weight`) and loading fails, as on `main`. For the FP8 checkpoint, the MLA weights go FP8 → BF16 (load-time dequant) → MXFP8. |
| BF16 (`zai-org/GLM-5.3-Flash-BF16`) | add `--quantization online`; `--quantization-config` alone is ignored (existing behavior) |

`--quantization-config` does not reach the MTP draft today (existing behavior), so the MTP layer keeps the checkpoint method. If #49900 lands, the regexes above still exclude layer 45.

- **Do not use a per-tensor activation scale on these layers at decode.** One scale shared by every row of a decode batch couples all requests. FP8 per-tensor W+A at every batch size was broken in our runs: AIME 94-97% → 53-60%, MATH-500 98% → 65%, with 20-25% runaway repetition loops. Upstream's online `fp8_per_tensor` uses per-token activation scales on CUTLASS-capable GPUs and does not have this coupling; we did not evaluate it.
- **Per-channel FP8 (`fp8_per_channel`) on all 196** mostly avoids the behavior change but also keeps only a small part of the throughput gain, so it offers nothing over the non-KDA MXFP8 config.

</details>

### Limitations

- Hardware-neutral, but validated on NVIDIA only; ROCm uses the same code path (MXFP8 via `RocmDotScaledMxfp8LinearKernel`) and is untested.
- CI covers the wiring and the helper (unit tests); no CI job serves GLM-5.3-Flash (191 GB checkpoint). End-to-end validation was done outside CI as listed above.
- The disaggregated prefill-only configuration was measured for throughput, not for accuracy (see the aggregated equivalent above).
