# [Model] Apply Transformers checkpoint renamings during weight loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/60666) · state: open · merged: False

## Original PR description

## Overview

Apply the weight renamings Transformers uses for each checkpoint (`transformers.conversion_mapping`) during weight loading, and update models so they no longer hand-map legacy checkpoint names. Supersedes #60131: GLM-5.3-Flash now uses the Transformers module names, so PEFT adapters trained with Transformers resolve without special-casing.

## Claims

- `get_checkpoint_renaming_mapper` builds the Transformers model on the meta device and takes the `WeightRenaming`s from `get_model_conversion_mapping`, so sub-model renamings are scoped exactly as in Transformers. `WeightConverter`s are skipped because vLLM fuses weights itself.
  - Renamings depend only on the `model_type`, even for custom code configs, because vLLM runs its own implementation either way.
  - vLLM's own config classes are converted to the native Transformers config class first. If the model still can't be built, the unscoped renamings of the `model_type` are used.
  - Regex quantization targets (`re:...`) are rewritten with the same renamings (`WeightsMapper.map_regex`), so e.g. Laguna NVFP4's `re:.*shared_expert\.(...)$` still matches the renamed `shared_experts`.
- The renamings are applied once, to the checkpoint weights, in `DefaultModelLoader` and `RunaiModelStreamerLoader`, so `hf_to_vllm_mapper` only has to map from current Transformers names.
  - LoRA, quantization configs and the `--mm-encoder-only` shard filter use the renamings followed by the model's mapper.
  - Drafts loaded from the target's checkpoint (MTP, DSpark) use the target's renamings.
  - The Transformers modeling backend no longer collects the renamings itself.
- Model updates. Every registered example checkpoint whose names Transformers renames was checked: ~80 architectures, ~70 of them native vLLM models.
  - **Renamed to the Transformers names:**
    - Mixtral, MiniMax-M2, MiniMax-M3, PhiMoE: `block_sparse_moe` -> `mlp`
    - Laguna: `shared_expert` -> `shared_experts`, gate bias
    - DeepSeek-V4: all backends + MTP/DSpark/VL
    - GLM-5.3-Flash: `forget_gate`, `attn_hc`/`ffn_hc`
    - MiMo-V2: `sinks`
    - CohereASR, DeepSeek-OCR-2, Step-VL encoder
    - GTE/Nomic-BERT, Inkling, HY-V3, HY-V4 (attention), Exaone-MoE
  - **Mapping from the new names:** VLM container prefixes (`model.language_model.` etc.) for the llava family, Granite-4-Vision, PaliGemma, Gemma3, Cohere2-Vision, LFM2-VL, Aria, ColPali, Qianfan-OCR, HyperCLOVAX, Kimi-K2.5, PaddleOCR-VL, Step-3.7, Qwen2-VL/2.5-VL, Qwen3.5 and the Qwen2-Audio family (AudioFlamingo3, GLM-ASR, Granite Speech). Also Granite MoE, Ernie-4.5, HRM, Gemma4-Unified, Cosmos3, Cosmos3-Edge, AXK1.
  - **Manual mappings removed:** legacy checkpoint names now covered, e.g. Qwen2-VL's `model.` -> `language_model.model.`, Bert's `LayerNorm.gamma/beta`, Aria's original-checkpoint entries, HY-V3 router names, Granite MoE suffixes, Cosmos3 flat-layout regexes, DeepSeek-V4 `head`/`embed`/`.ffn.gate.bias`.

## Validation

**Load check:** each affected model was built on the meta device with 2 decoder layers, and its real `load_weights` was fed meta tensors shaped like the real checkpoint (from the Hub safetensors headers). On the shared checker, the branch is never worse than `main` (88 architecture/checkpoint pairs):

| Result | Pairs |
|---|---|
| Same params loaded, same missing set as `main` | 54 |
| Same harness error on `main` and branch (FP8/NVFP4 kernels on CPU, per-layer config lists not truncated, tokenizer/processor needed, Mistral-format-only models) | 34 |

The models in the second row were re-checked with per-model checker variants that work around the harness limits. On those, the branch also loads the same params as `main` (DeepSeek-V4 + MTP/DSpark/VL, HY-V4, GLM-5.3-Flash, Kimi-K2.5, Laguna NVFP4, Step-3.7 + MTP, Inkling, Mistral-format models). A few models load more on the branch than on `main`:
- HyperCLOVAX: errors on `main`.
- Step-3.7 MTP: errors on `main`.
- Laguna and Exaone-MoE: `main` silently drops `e_score_correction_bias`.

On Laguna NVFP4 the renamed `shared_experts` linears get the same `CompressedTensorsW4A4Fp4` scheme as on `main`.

**LoRA (GLM-5.3-Flash):** `...self_attn.forget_gate.f_b_proj.lora_A.weight` and the flat `...self_attn.f_b_proj...` both resolve to the existing `...self_attn.forget_gate.f_b_proj` module. On `main`, the `forget_gate` name matches no module (#60131).

## Details

- **Limitations:** the bitsandbytes, GGUF and tensorizer loaders do not apply the renamings.
- **Non-idempotent renamings:** a few Transformers renamings are not idempotent (AXK1, MiniMax-M3 `e_score_correction_bias`). Loading applies them once. Adapters or reloaded weights that already use the new names may be renamed twice.
- **Regex quant targets:** `map_regex` only applies renamings between plain names. It replaces whole segments, and may skip the shared leading segments only after a `.*`/`.+` wildcard. Regex renamings and complex quant patterns are left unchanged.
- **Follow-ups that still map back to existing vLLM names.** These modules are shared with models Transformers doesn't rename, or would need kernel rework:
  - CLIP/SigLIP `vision_model`
  - HY-V4 hyper-connections (`hpc_ihc.py`)
  - MiniMax-M3 indexer and DeepSeek-V4 indexer nesting
  - Qianfan-OCR's InternViT
  - Kimi vision tower and Kimi-Linear MoE/KDA (shared with Kimi-K3)
  - DeepSeek-OCR SAM encoder (shared with OCR v1)
  - Step-3.5 MoE names (shared with Step-3.5-Flash)
  - VLM language-model containers (`language_model.model` vs `model.language_model`)
- **f_a_proj LoRA:** LoRA on GLM-5.3-Flash `f_a_proj` (fused in `in_proj_qkvbfg_a`) is still unsupported, as on `main`.
