# [Bugfix][Frontend] Honor --response-role and echo in chat derender

[Upstream PR](https://github.com/vllm-project/vllm/pull/63357) · state: open · merged: False

## Original PR description

## Overview

Chat derender always returned `role: "assistant"` and ignored `echo`, so it didn't match `/v1/chat/completions` for the same tokens. This fixes that for `/v1/chat/completions/derender` (batch and stream) and adds `--response-role` to generate `output_mode: "derender"` (batch and stream).

Fixes #63356. Related: #56851, #63103, #63148.

**Depends on #63434. See https://github.com/vllm-project/vllm/pull/63434#issuecomment-6579638244.**

## Claims

- `/derender` returns the same role as chat: `--response-role` or the last message's role when `add_generation_prompt` is false.
- `/derender` supports `echo` for text content. In batch it's prepended to `content`. In a stream it goes at the start of the first chunk, along with the role.
- Generate `output_mode: "derender"` uses `--response-role`, in batch and on the first chunk of each choice in a stream.
- `vllm serve` and `vllm launch render` both pass `--response-role` to the derenderer.
- Chat serving, batch chat and derender share one implementation of the role and echo logic.
- `add_generation_prompt: false` with empty `messages` returns `--response-role` instead of a 500.

## Validation

New unit tests cover batch (with and without a parser), streaming on the plain and parser paths and generate derender. They fail on `main` and pass with this change.

```bash
pytest tests/entrypoints/scale_out/derender/test_derender.py \
  tests/entrypoints/scale_out/derender/test_derender_stream.py -q

pytest tests/entrypoints/openai/chat_completion/test_serving_chat.py \
  tests/entrypoints/openai/chat_completion/test_message_assembly.py \
  tests/entrypoints/scale_out/token_in_token_out -q
```

`test_derender_parity.py` now runs its server with `--response-role` bot, checks role in every batch case, and adds an echo + continue_final_message case. 

## Details

`OnlineDerenderer` had no `response_role` and hardcoded `"assistant"` in five places. The generate stream added in #63103 hardcoded it too. `echo` wasn't handled anywhere.

The role and echo logic moved into `get_chat_response_role()` and `get_echo_content()` in `message_assembly.py`, next to the shared message assembly from #63148.

Streaming doesn't send echo as its own chunk the way chat does. Each derender call returns exactly one chunk, so the echo goes in the same chunk as the role and `role_sent` already tracks it.
`DerenderStreamState` is unchanged. Clients that concatenate deltas get the same text as from chat.

Known limits:

- `/derender` builds echo from the raw `messages`, while chat uses the parsed conversation. Refusal and thinking parts and multimodal placeholders aren't echoed. This is documented in `derenderer.md`.
- Generate derender can't do echo or the last message's role because `parse_context` doesn't carry `messages`, `add_generation_prompt` or `echo`. It's documented in `token_in_token_out.md` and the wire format question is on #63356.
- Harmony `echo: true` still returns a 500. That's not new and is tracked in #XXXXX.

Small change in coupled chat: streaming echo used to pass list content straight into `DeltaMessage.content` which only takes a string. It's now joined into text like the batch path.

Docs: `derenderer.md` says the render server needs the same `--response-role` as the chat server and explains how role and echo work. `token_in_token_out.md` now lists `derender` as an `output_mode` value.

🟡 (optional) Derender `echo` can return different text than /v1/chat/completions for the same request, so the parity this PR claims fails for some content parts. `_echo_content` reads the raw `request.messages`, while coupled chat echoes the parsed `conversation`. `get_echo_content` keeps only parts with a `"text"` key. That drops `refusal` and `thinking` parts, which chat parsing turns into text. It also drops the multimodal placeholders that the string content format inserts. Fix: derive the echo text with the same text extraction chat parsing uses (`MM_PARSER_MAP` / `TEXT_PART_TYPES`), so both endpoints produce the same string.

<details>
<summary>Why this was flagged</summary>

Trigger: a request with `echo: true` and `add_generation_prompt: false` / `continue_final_message: true`, whose last assistant message has list content containing a `{"type": "refusal", "refusal": ...}` or `{"type": "thinking", "thinking": ...}` part. Coupled chat (serving.py) calls `get_echo_content(conversation, role)` on the parsed conversation. There, `parse_chat_message_content_part` maps those parts to text via `MM_PARSER_MAP` (chat_message.py:103-116), so the echo includes them. The derenderer (online_derenderer.py:167) calls `get_echo_content(request.messages, role)` on the raw messages. message_assembly.py skips any part without a `"text"` key, so the refusal or thinking text disappears from derender `content`. Image parts under the string content format show the same gap: coupled echo includes the placeholder text and derender does not. test_derender_parity.py only covers plain string content, so it does not catch this. On the base branch derender ignored echo completely, so this mismatch is new with the feature.

**Verification:** The derenderer's `_echo_content` (online_derenderer.py:164-167) calls `get_echo_content(request.messages, role)` on the raw request messages. Coupled chat calls `get_echo_content(conversation, role)` on the parsed conversation. So chat's echo includes the refusal or thinking text, and the derenderer's echo drops it. On the base branch the derenderer ignored echo completely.

</details>
