# [Rust Frontend] Support --custom-histogram-buckets

[Upstream PR](https://github.com/vllm-project/vllm/pull/62826) · state: closed · merged: True

## Original PR description

## Overview

Python's `--custom-histogram-buckets` (vllm-project/vllm#48867) replaces the default bounds of a bucket family across all of its histograms. The Rust frontend rejects the flag at startup (placeholder from vllm-project/vllm#62431) and hardcodes the bucket lists per histogram. This PR implements it with the same families and validation as Python.

## Claims

- `--custom-histogram-buckets '{"time_to_first_token": [0.5, 1.0], ...}'` now starts the Rust frontend, and every histogram in a listed family exports the custom bounds; unlisted families keep their defaults. It works under `vllm-rs serve` and through `--args-json`.
- Keys and bounds are validated like `ObservabilityConfig.custom_histogram_buckets`: known family names, non-empty, finite, > 0, strictly increasing, no booleans. Invalid input fails startup.

- `custom_buckets_replace_listed_family_defaults` renders a fresh registry: listed families (`time_to_first_token`, `inter_token_latency` through `request_time_per_output_token_seconds`, `request_tokens` without a `max_model_len`, and the scheduler's `kv_cache_residency`) use the custom bounds, and an unlisted one keeps its defaults. `custom_buckets_are_validated_like_python` pins the errors. `custom_histogram_buckets_reach_frontend_config` checks both launch paths and that invalid bounds fail startup. The existing `request_token_buckets_are_capped_at_max_model_len` still passes.

## Details

`vllm-metrics` owns the buckets of its histograms, so the family table and its validation live there, in a new `buckets` module mirroring `vllm/v1/metrics/buckets.py`:

- The default lists, moved verbatim from `request.rs` and `scheduler.rs`.
- `BucketFamily`, keyed like `BucketFamilyKey`, and `CustomHistogramBuckets`, which validates on deserialization.
- A `FamilyHistogram` constructor per family that reads one shared `BucketConfig`: custom bounds when the family is listed, else the defaults. It replaces `RequestTokensHistogram`, whose deferred `max_model_len` cap moves into the same config; a custom `request_tokens` list does not need `max_model_len`, as in Python.

The registry is process-global and built lazily, so the bounds are fixed after construction and before first use, the pattern `set_max_model_len` already uses: the server, which owns startup ordering, calls `Metrics::set_custom_histogram_buckets` at the start of `build_state`, before the engine connection can record anything. The CLI only parses JSON into that type. Histograms outside the families (HTTP duration, Mooncake, NIXL) keep their own buckets, as in Python. The flag is not forwarded to the managed engine under `vllm-rs serve`, since only the frontend logger reads it.

- `CustomHistogramBuckets` implements `Eq` by hand so `SharedRuntimeArgs` keeps deriving it; validated bounds are finite, so equality is reflexive.
- Open Python PRs vllm-project/vllm#59807 and vllm-project/vllm#59808 would allow a 0 bound for count families; the Rust check mirrors current `main` and would follow.

Not a duplicate: no open upstream PR implements this flag in Rust.
