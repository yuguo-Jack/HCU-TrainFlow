# [XPU][Model] Gemma4: route MoE with topk_softmax on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/63330) · state: open · merged: False

## Original PR description


## Overview

On XPU, Gemma4's MoE routing now uses the `topk_softmax` MoE op (`_moe_C`; its XPU kernel ships in vllm-xpu-kernels) instead of the Triton `_gemma4_routing_kernel` (#39083). The math is the same: softmax over all experts, top-k, renormalize, then the per-expert scale. On Arc Pro B70 the Triton kernel costs ~55 µs per call regardless of the token count, which is ~0.6 ms/step over 30 MoE layers at small batch.

## Claims

- Routing call (incl. the router projection), Arc Pro B70, under XPU graphs: **57 µs → 12 µs** for 1–16 tokens; expert ids identical to the torch reference.
- gemma-4-26B-A4B, TP=4, XPU graphs, ShareGPT prompts, output throughput: **+8.6 % at batch 1, +5.1 % at batch 8**, neutral at batch 32/64 (4× Arc Pro B60). Same trend on 4× Arc Pro B70.
- Accuracy unchanged: gsm8k 5-shot 0.7255 → 0.7263 (± 0.012).
- CUDA/ROCm paths unchanged.

## Details

- **Why Triton is slow here:** `_gemma4_routing_kernel` runs one program per token and sorts all 128 experts with `tl.sort`; on XPU that lowers to a long serial sequence (~55 µs even for one token). `topk_softmax` is the existing `_moe_C` MoE routing op that the generic fused-MoE router (`fused_topk`) already uses; with `renormalize=True` it is exactly Gemma4's routing, so the change is a dispatch plus a scale gather (no new kernel).
- **Scope:** dispatch is XPU only; the CUDA/ROCm branch (`is_cuda_alike()`) keeps the Triton kernel. No new dependency: `topk_softmax` ships in current vllm-xpu-kernels releases.
- **No host sync:** the scale gather and multiply stay on device; the path is captured in XPU graphs.
- **Gains fade with batch size** because the routing cost is fixed per call while the expert GEMMs grow.
- **Related, not a duplicate:** searched vllm `gemma4 router`, `gemma4 routing`, `topk_softmax xpu`, `moe router xpu` and vllm-xpu-kernels `router`, `topk_softmax`, `gemma4` (2026-10-22). #39083 added the Triton kernel this replaces on XPU. vllm-xpu-kernels#629 (open) adds a new single-launch router op (router GEMV + softmax top-k) for ≤ 16 tokens; it would save another ~5 µs/call (measured 6.3–7.5 µs incl. the projection) but needs that kernels PR to land, Gemma4 router pre-scaling/`per_expert_scale` handling, and a fallback above 16 tokens. This PR needs no new kernel and can be the fallback for that later. No open vllm PR changes Gemma4 routing on XPU.
