# [Metrics][LoRA] Publish LoRA load events and expose loaded adapters in metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/54830) · state: open · merged: False

## Original PR description

## Stack

1. #51433 engine notification channel 
2. #54830 LoRA load events, doorbell, and Python Prometheus metrics (this PR)
3. #54833 Rust frontend consumer for the same metrics

Each PR is based on `main` and includes the commits of the ones before it; review only the last commits of each.

End-to-end testing on the Rust frontend needs #54836 (`--lora-modules` support), tracked separately.

Note: the metrics report worker-side residency. `/v1/unload_lora_adapter` on the Python server only drops the frontend registry entry (#54839), so an unloaded adapter keeps its series until LRU eviction. This bug is now actually visible!

- atantawi · comment · 2026-09-03T11:19:34Z · [source](https://github.com/vllm-project/vllm/pull/54830#issuecomment-5524911017)

Downstream consumer here — @wseaton pointed me at this stack from
llm-d/llm-d-router#1500. Putting the consumer-side case on the record, since "who needs
this metric" is what a metrics PR usually has to answer.

**llm-d-router's LoRA scorer is broken today in two directions, and this PR fixes both.**
It parses `vllm:lora_requests_info` into `ActiveModels` / `WaitingModels` and scores
endpoints in four tiers. Read at llm-d-router `7f1a611e` against vLLM `67e86d1e6f`:

- `LoRARequestStates.update_scheduler_stats` (`vllm/v1/metrics/stats.py:637-639`) is the
  only writer of either dict and writes every key of `self.requests` into **both**;
  `loggers.py:1168-1172` renders each as `",".join(...keys())`. The two label values are
  two renderings of one key set, so the router's "adapter queued to load" tier is **dead
  code** — `waiting` implies `active`, tested first.
- Its capacity tier tests `len(active)+len(waiting) < max_lora`, which is `2N` for `N`
  active adapters and trips at `N ≥ max_lora/2`. Meanwhile an adapter resident with no
  traffic is invisible, so a full pod can read as empty. One expression, wrong in both
  directions.

Confirmed by running the router's own extractor and scorer, kept as mutation-tested Go
tests: with `running = waiting = "target,other"` and `max_lora = 4`, a queued target scores
`1.0` instead of the intended `0.6`, and a cold target scores `0.0` with two of four slots
free. Filed as llm-d/llm-d-router#2605 before I knew this stack existed.

`vllm:num_gpu_loaded_lora_adapters` against `max_lora` is exactly the comparison that
capacity tier fails to be, and `vllm:lora_adapter_loaded{level="gpu"}` is the residency its
tier names already claim to test. On cardinality, since that is the usual objection to a
per-adapter label: it is bounded by `max_cpu_loras`, not by the registered population, which
in our survey of adapter populations runs to 10²–10³ per base-model family with only a
handful resident.

I read the producer rather than the label names — misreading a label name is what put me
wrong on the llm-d thread to begin with — and the residency claim holds: `activate_adapter`
evicts only at `len(_active_adapters) >= lora_slots` and `_apply_adapters` only ever adds,
so an idle adapter stays in `gpu_adapters`. Three questions from that reading:

1. **Running vs queued stays unavailable.** The stack leaves the info-metric alone, so a
   consumer still cannot reconstruct `scheduled_loras` (`scheduler.py:764-769`, `814-824`) —
   the quantity a capacity-aware scheduler actually wants. Is splitting the running set in
   scope here, or is the intent that consumers use residency plus activity and not try?
2. **TP > 1 labelling.** The gather flattens every rank and the labels carry no rank, so
   `_record_lora_load_event` is last-write-wins per `engine_idx` against
   `_lora_loaded_series`. Identical sets across ranks make that idempotent — guaranteed, or
   can a transient disagreement flap a series?
3. **The idle-engine claim.** `docs/design/metrics.md` says the gauges update "including on
   an idle engine with statically configured adapters". I could not confirm that
   `--lora-modules` puts the adapter in the *worker's* cache before the first request, as
   opposed to the frontend registry #54839 is about. Worth a test if scrape-before-traffic
   is load-bearing.

- atantawi · comment · 2026-09-24T21:01:59Z · [source](https://github.com/vllm-project/vllm/pull/54830#issuecomment-5822188452)

Downstream consumer again (llm-d-router, i.e. the gateway API inference extension this PR's docs name by name). Two things in the deprecation half read wider than what the PR ships, and both land on that consumer. Quoting the text rather than line numbers, since this branch has been rebased several times — read at `95ade06b`, and re-read there today.

**1. The Rust registry's deprecation notice names successors that frontend does not register.**

`rust/src/metrics/src/scheduler.rs` now registers `vllm:lora_requests_info` with this help string:

> Running stats on lora requests. DEPRECATED: encodes adapter names into comma-separated label values; superseded by vllm:lora_adapter_loaded, vllm:num_gpu_loaded_lora_adapters and vllm:num_cpu_loaded_lora_adapters.

That is word for word the string in `vllm/v1/metrics/loggers.py`, where all three successors are real — that file registers `vllm:num_gpu_loaded_lora_adapters`, `vllm:num_cpu_loaded_lora_adapters` and `vllm:lora_adapter_loaded`. In the Rust tree they are not: across the whole `rust/` directory at this head, those three names occur in exactly one place, the help string itself. Registering them is #54833, which is still a draft.

So a `VLLM_USE_RUST_FRONTEND` deployment that reads the notice is pointed at families it does not have, and has to keep scraping the deprecated one. Either landing the Rust-side notice with #54833 rather than ahead of it, or naming the frontend in the string, would fix that.

**2. "It is still emitted unchanged" is a per-frontend statement made globally.**

`docs/design/metrics.md` says the family "is now deprecated. It is still emitted unchanged, and follows the deprecation policy before it is hidden and removed", and that "Downstream users such as the gateway API inference extension should migrate to the metrics below". Unchanged relative to which frontend's rendering? The two differ today, in this tree, in three observable ways:

- **Label set.** Python's labels are `max_lora`, `waiting_lora_adapters`, `running_lora_adapters`; Rust's `LoraInfoLabels` carries only the two adapter labels, as its own expect-test spells out: `vllm:lora_requests_info{running_lora_adapters="a,b",waiting_lora_adapters="c"}`. The same doc bullet notes that "the `max_lora` label on the deprecated gauge above only appears once an adapter has served" — behind the Rust frontend it never appears at all.
- **Whether the series exists with nothing in flight.** `LoraInfoExporter::update` derives its labels from `(!running.is_empty() || !waiting.is_empty()).then_some(...)` and removes the previous series, so the family disappears once the last request drains; `lora_info_emits_clears_stale_and_drains` asserts exactly that ("All requests done: series removed entirely"). The Python logger has no such guard — it calls `.labels(**lora_info_labels).set_to_current_time()` whenever the gauge exists, so a record with both sets empty keeps a series whose two adapter label values are empty strings. A scraper that reads absence as "no LoRA configured" and empty label values as "configured but idle" gets opposite answers from the two frontends.
- **Running versus waiting.** `LoRARequestStates.update_scheduler_stats` writes every tracked adapter into *both* `waiting_lora_adapters` and `running_lora_adapters`, and `loggers.py` renders each as `",".join(...keys())`, discarding the counts — so in the Python rendering both label values always carry the same key set, and an adapter with only queued requests still appears as running. The Rust registry partitions adapter names by an exclusive per-request phase (#45030), so that adapter appears in `waiting_lora_adapters` only. We had this wrong on our side for a while and corrected our own docs for it.

None of the three is a stated contract, which is what makes "unchanged" load-bearing: it is the sentence a downstream scraper is pointed at for the whole deprecation window. Scoping it — "still emitted unchanged by the Python frontend", plus a line on what the Rust frontend does — would be enough for us.

**Checked and not a finding, noted so nobody spends time on it:** the doc's `multiprocess_mode` for this family going from `"livemostrecent"` to `"sum"` is a correction of a stale doc rather than a change — `loggers.py` carries `multiprocess_mode="sum"` on `main` as well.
