# [Core] Prevent zero-collapse deadlock in _mamba_block_aligned_split

[Upstream PR](https://github.com/vllm-project/vllm/pull/40757) · state: open · merged: False

## Original PR description

## Summary

Fixes a permanent scheduling deadlock in hybrid Mamba/DeltaNet models
(e.g. Qwen3.5-35B-A3B) when processing multiple large multimodal inputs.

When the encoder cache cannot hold two adjacent images simultaneously,
a gap < `block_size` between images is truncated to 0 by block alignment,
creating a no-progress loop. This PR skips the alignment when it would
collapse `num_new_tokens` to 0, consistent with the existing "simply not
cached" exception documented in the code.

Fixes #40707

## Changes

- `vllm/v1/core/sched/scheduler.py`: 3-line change in
  `_mamba_block_aligned_split` — when alignment would produce 0,
  keep the original sub-block value.
- `tests/v1/core/test_mamba_block_aligned_split.py`: Comprehensive
  unit tests covering all branches, including the deadlock scenario.

## Safety Analysis

The Mamba running state is correctly maintained by `preprocess_mamba`
(in `vllm/v1/worker/mamba_utils.py`) via `mamba_state_idx` even for
sub-block chunks. Only the block-boundary state checkpoint is skipped,
which is consistent with the existing code comment: "if num_new_tokens
is less than block_size, the state is simply not cached, requiring no
special handling."

### Impact scope

- **Models with Mamba layers + `mamba_cache_mode="align"`**: This is
  the only configuration where `_mamba_block_aligned_split` is invoked
  (gated by `need_mamba_block_aligned_split` at `scheduler.py` L252-254,
  condition: `has_mamba_layers and cache_config.mamba_cache_mode == "align"`).
  The fix only changes behavior when alignment would produce 0
  (`num_new_tokens < block_size` in a middle chunk). Normal alignment
  (values ≥ `block_size`) is completely unaffected.
- **All other models** (pure attention, models with Mamba but
  `mamba_cache_mode != "align"`, encoder-decoder, etc.): Zero impact —
  `_mamba_block_aligned_split` is never called.
- **Pure text + Mamba + align mode**: The function IS called, but the
  zero-collapse scenario is practically unreachable because there is no
  encoder cache contention to create sub-block-size gaps. The fix is
  still safe in this path — it only preserves a positive `num_new_tokens`
  that the scheduler already intended to schedule.
