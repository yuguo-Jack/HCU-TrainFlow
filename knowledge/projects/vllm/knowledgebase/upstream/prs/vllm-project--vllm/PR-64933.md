# [Bugfix] Spawn workers when CUDA forward compatibility is enabled

[Upstream PR](https://github.com/vllm-project/vllm/pull/64933) · state: open · merged: False

## Original PR description



## Overview

Use the existing spawn policy when CUDA forward compatibility is enabled, so offline LLM workers read the selected compatibility directory at process startup. This fixes the default fork path of the opt-in introduced by #33992.

## Claims

- Multiprocessing LLM inference loads the selected compatibility driver and PTX compiler, including loads through both `libcuda.so.1` and `libcuda.so`.
- Reuses `_maybe_force_spawn`, path selection and worker startup; the behavioral change is three lines, with no new dependency or public configuration.
- Documents the main-guard requirement and the startup library path required for in-process inference.

## Validation

Tested base: `0c63ce9f0e0b5b2782f0f30cb491069dac158bb2`. H100 80GB, driver 535.161.08, official CUDA 13 compatibility package 580.196.07, Python 3.12.16, PyTorch 2.14.0+cu130, Qwen3-0.6B, MRV2. Runs enabled `VLLM_GPU_SYNC_CHECK=error`.

| Check | Before | After |
| --- | --- | --- |
| New real-worker regression | Fails with driver API 12040 too old | Passes |
| Compatibility, lazy initialization, context and process utility suites | — | 56 passed in 73.00s |
| Fixed 32-question GSM8K slice, 5-shot | 12/32 with startup compatibility path | 12/32 with compatibility opt-in |
| Exact output comparison | 3,074 generated tokens | Identical text, token IDs and logprobs; no length truncation |

```bash
export VLLM_CUDA_COMPATIBILITY_PATH=/path/to/cuda-13.0/compat
export VLLM_TEST_MODEL=/path/to/Qwen3-0.6B
export VLLM_ENABLE_CUDA_COMPATIBILITY=0
export VLLM_GPU_SYNC_CHECK=error
LD_LIBRARY_PATH="$VLLM_CUDA_COMPATIBILITY_PATH${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
  .venv/bin/python -m pytest \
  tests/cuda/test_cuda_compatibility_path.py \
  tests/cuda/test_platform_no_cuda_init.py \
  tests/cuda/test_cuda_context.py \
  tests/utils_/test_system_utils.py -v --tb=short
UV_SYSTEM_CERTS=true .venv/bin/pre-commit run --all-files
```

The regression removes the selected compatibility directory from the child startup environment and uses the default worker method. Its independent control disables the opt-in and sets the path before Python starts. A public worker RPC checks both driver names, CUDA contexts, real PTX compilation with the disk cache disabled, and loaded library paths. The existing CUDA Platform CI step selects the test.

Explicit fork/spawn, torch-first, startup-configured in-process inference and an initialized parent CUDA context passed. Normal generation also passed with test-only function serialization disabled. The GSM8K comparison used greedy decoding, batch invariance, eager mode and a 2 GiB KV cache; it is a small output regression, with no performance claim. Full pre-commit passed: exit 0, 36 hooks passed.

The reproducer uses real hardware and normal LLM inference under controlled configuration. No production incident for this defect has been established.

## Details

Changing `LD_LIBRARY_PATH` after Python starts does not update the process's dynamic loader or a forked copy. A spawned worker reads the updated environment from startup and resolves the compatibility library set normally:

```text
existing compatibility path selection
  → updated environment
  → existing spawn policy
  → fresh worker loads the selected libraries
```

The compatibility opt-in now selects spawn on CUDA, including when the startup path was already correct. This follows vLLM's existing spawn mechanism and PyTorch's fresh-process guidance for CUDA, but changes requirements for existing fork callers. A separate real-GPU comparison confirmed the migration cost:

| Startup path configured, opt-in enabled, fork requested | Result |
| --- | --- |
| Original policy, script without a main guard | Generation succeeds, exit 0 |
| Patched policy, same unguarded script | Multiprocessing bootstrapping error, exit 1 |
| Patched policy, `if __name__ == "__main__":` guard added | Generation succeeds, exit 0, identical tokens |

Please assess this compatibility tradeoff during review. Spawn also has startup overhead and does not inherit arbitrary parent state as fork does. With `VLLM_ENABLE_V1_MULTIPROCESSING=0`, or direct CUDA calls in the parent, configure `LD_LIBRARY_PATH` before starting Python. The patch does not replace libraries in the current process.

The validated scope is workers created through vLLM's multiprocessing context. Externally launched Ray workers and torchrun ranks are outside this validation scope.

Duplicate checks on 2026-11-01 found no open or merged PR for this worker-policy fix. #33992 introduced the opt-in; its open-PR reference search was empty. Exact opt-in, loader-function and compatibility/spawn searches found #36579 (Marlin diagnostics), #63688 (deployment docs), #38476 (attention backend), and closed #34821, #53135 and #29592; none implements this policy change. Searches cannot rule out unpublished work.

The unchanged patch applies cleanly to checked main `564ac0de1b228568cafcbfbe8ccaccc82d6023eb`. GPU results remain tied to the stated base; latest main, other GPUs/drivers, multi-GPU and Ray deployments were not rerun. The actual H200 MIG CI image, compatibility package and each subprocess's 180-second cold-start limit remain unverified on that CI hardware.
