# [Core] Validate custom logits processor arguments in EngineCore

[Upstream PR](https://github.com/vllm-project/vllm/pull/64221) · state: open · merged: False

## Original PR description

## Overview

Run the custom logits processor argument validation (`validate_params`) in `EngineCore` too, so a frontend that cannot run the Python hooks, such as the Rust frontend, gets a 400 for a bad argument instead of a dead engine. The Rust frontend CI step now runs `test_invalid_custom_logitsproc_arg`.

## Claims

- A request with an invalid custom logits processor argument (`vllm_xargs`) now finishes with `RequestError(code="validation_error")` in the engine core instead of failing inside the model runner. Under the Rust frontend it returns 400, as under the Python frontend; before, the engine core reported a fatal failure and every later request got a 500.
- The Python frontend's behavior does not change: it still rejects in `InputProcessor`, and the engine-side check passes for anything that got through.

## Validation

- `pytest tests/v1/engine/test_engine_core.py -k validates_custom_logits_processor_args`: 2 passed (both cases fail without the engine call).
- `pytest tests/test_sampling_params.py tests/v1/engine/test_input_processor_trace_replay.py tests/v1/worker/test_logits_processor_loader.py`: 80 passed.
- `pre-commit run --files <changed files>`: all hooks pass, including ruff, mypy and the Buildkite checks.
- E2E on GB200: `pytest -v -s v1/logits_processors/test_custom_online.py` (the command this PR enables in the Rust frontend OpenAI Coverage step) with `VLLM_USE_RUST_FRONTEND=1` and this change: 4 passed, including both `test_invalid_custom_logitsproc_arg` cases. On `main`, both of those cases fail with a 500 (`engine core reported fatal failure`). With the Python frontend and this change, both pass.

## Details

The Python frontend runs each custom logits processor's `validate_params` hook in `InputProcessor` (`vllm/v1/engine/input_processor.py`). The Rust frontend cannot run Python hooks, so it forwards `vllm_xargs` unchecked. The bad argument then fails inside the model runner when the processor reads it, and the engine core shuts down: one malformed request takes the server down.

`EngineCore.preprocess_add_request` now runs the same validator before building the `Request`. A rejected argument raises `VLLMValidationError`, which the input thread already turns into a finished output with `RequestError(code="validation_error")`; the Rust frontend maps that to 400 with the message since vllm-project/vllm#62872. The validator builder moves unchanged from `InputProcessor._build_logits_processors_params_validator` into `vllm/v1/engine/logits_processor_validation.py`, so the frontend and the engine core build it the same way for both model runners.

**Placement.** The consumer of `vllm_xargs` is the logits processor running in the engine, so the engine core is the one place every frontend passes through before it. The check runs after the multimodal receiver-cache update, so a rejected request keeps the sender and receiver caches in step, and before `Request` construction, like the structured-output validation in the same path. Alternatives considered: a per-request validation RPC over the utility channel, and a parameter schema declared in the engine handshake.

**CI.** The Rust frontend OpenAI Coverage step (NVIDIA and AMD) drops its `-k "not test_invalid_custom_logitsproc_arg"` exclusion and lists `vllm/v1/engine/logits_processor_validation.py` among its source dependencies, so it runs when the shared validator changes.

**Known behavior.** Under the V1 runner with speculative decoding, the validator also checks installed entry-point plugins that the runner then skips. This is unchanged from the Python frontend, which already rejects such requests in `InputProcessor`; the Rust frontend now returns the same 400.

Not a duplicate: no open PR moves logits processor argument validation into the engine. AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
