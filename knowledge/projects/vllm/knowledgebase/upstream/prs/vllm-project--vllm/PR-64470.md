# [Bugfix] Compute NIXL EP per-tensor FP8 scale over valid rows only

[Upstream PR](https://github.com/vllm-project/vllm/pull/64470) · state: open · merged: False

## Original PR description

## Purpose

Fixes #64456. Thank you to @fangyuchu for the detailed report and for pinpointing the root cause so precisely.

With `--all2all-backend nixl_ep` and `--quantization fp8_per_tensor`, the dynamic per-tensor FP8 scale was computed over the entire fixed-capacity NIXL receive buffer, including stale rows past each expert's `expert_num_tokens`. Those leftover values inflated the scale and corrupted the quantized valid rows (the reporter measured 0/32 on the first 32 GSM8K questions with DP=2 + NIXL EP + FP8, vs 19/32 single-GPU FP8).

This PR threads `expert_num_tokens` from `NixlEPPrepareAndFinalize._receiver` into `_do_quant`, which now computes the dynamic per-tensor scale over valid rows only (a masked absmax, matching the kernel's `absmax / quant_max` formula). The quantized output keeps its full buffer shape; only the scale changes.

Deliberately untouched, since their scales never mix rows or are fixed:

- per-token quantization and block quantization;
- static per-tensor scales (`a1_scale is not None`);
- the fp8-dispatch paths (the block-128 early return, and dequant-then-requant, which now also benefits from the valid-rows scale);
- NVFP4/MXFP formats (not dynamic per-tensor FP8/INT8).

The masked scale computation adds no host sync and keeps all shapes static (one extra elementwise pass over the receive buffer, only for dynamic per-tensor quantization).

**Why this is not a duplicate:** no open PR references #64456, and the issue timeline shows no competing fix. The similarly titled open PR #54683 fixes a different backend and mechanism — the naive DP/EP all-gather path in `naive_dp_ep.py`, where rank-local scales were gathered — while this PR fixes the NIXL EP receive buffer in `nixl_ep.py`.

## Test Plan

Tensor-level reproducer (pure torch, no GPU needed — this environment has no GPU, so the reporter's end-to-end GSM8K run could not be repeated here; that check is left for CI/reviewers with NIXL-capable hardware):

```python
import torch

FP8_E4M3_MAX = 448.0

torch.manual_seed(0)
num_experts, max_tokens, hidden = 2, 4, 8
expert_num_tokens = torch.tensor([2, 3])

buf = torch.zeros(num_experts, max_tokens, hidden)
buf[0, :2] = torch.randn(2, hidden) * 0.5
buf[1, :3] = torch.randn(3, hidden) * 0.5
buf[0, 2:] = 1000.0  # stale leftovers
buf[1, 3:] = -1000.0  # stale leftovers
valid = torch.cat(
    [buf[e, :n] for e, n in enumerate(expert_num_tokens.tolist())]
)

scale_before = buf.abs().max() / FP8_E4M3_MAX
scale_after = valid.abs().max() / FP8_E4M3_MAX
print(f"scale BEFORE (full buffer): {scale_before.item():.6f}")
print(f"scale AFTER (valid rows only): {scale_after.item():.6f}")
print(f"inflation factor: {(scale_before / scale_after).item():.1f}x")

def quantize(x, scale):
    return torch.clamp(
        x / scale, -FP8_E4M3_MAX, FP8_E4M3_MAX
    ).to(torch.float8_e4m3fn)

q_before = quantize(valid, scale_before)
q_after = quantize(valid, scale_after)
rel_before = ((q_before.float() * scale_before - valid).abs()
              / valid.abs().clamp(min=1e-6)).max()
rel_after = ((q_after.float() * scale_after - valid).abs()
             / valid.abs().clamp(min=1e-6)).max()
print(f"max rel. error of valid rows BEFORE: {rel_before.item():.3f}")
print(f"max rel. error of valid rows AFTER: {rel_after.item():.3f}")
print(f"quantized valid rows identical: {torch.equal(q_before, q_after)}")
```

One FP8 edge case worth covering: the helper applies the INT8 `1e-10` scale floor to FP8 too. At `6a787584`, a CPU check of the exact helper gives:

```python
x = torch.full((2, 4, 8), 1e-12, dtype=torch.float32)
s = _dynamic_per_tensor_scale_for_valid_rows(x, torch.tensor([1, 2]), 448.0)
# s = 1e-10; valid-only absmax / 448 = 2.23214294e-15
```

The same head's [`absmax_reduction_flat` / strided reduction](https://github.com/vllm-project/vllm/blob/6a787584fccc3bb78ce1e623dd2b610e328d3d31/csrc/libtorch_stable/quantization/w8a8/fp8/common.cu#L127-L180) uses float absmax/quant_max without that floor. With real CPU Torch FP8 casting, this changes the quantized magnitude from 448 to 0.009765625 and introduces about 2.34% relative reconstruction error for this synthetic input; BF16 shows the same scale discrepancy.

Could the nonzero FP8 scale preserve that formula, with zero handled separately, while retaining INT8's existing floor? My component controls have 5 passes / 2 failures; they extract the unchanged helper AST and do not import the complete module or execute CUDA/NIXL. This is a numerical boundary observation, not evidence of model-accuracy loss or a full-PR verdict.
