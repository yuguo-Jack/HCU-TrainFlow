# [Bugfix][Kernel] Canonicalize Marlin MoE token order

[Upstream PR](https://github.com/vllm-project/vllm/pull/52532) · state: open · merged: False

## Original PR description

## Purpose

Fixes #52525.

`moe_align_block_size()` guarantees expert grouping but does not guarantee the ordering of routed token IDs within an expert. For Marlin MoE, semantically equivalent within-expert orderings can select different physical block positions in the multi-threadblock split-K path and therefore follow different floating-point reduction trees.

The resulting BF16 differences are small, but they can propagate through later layers and affect autoregressive generation.

This change canonicalizes `sorted_token_ids` within each contiguous expert region before entering the Marlin MoE kernel.

The canonicalization:

- preserves expert assignment and `expert_ids`
- preserves `num_tokens_post_padded`
- keeps the inactive alignment-buffer tail from affecting the active prefix
- preserves the existing single-token decode fast path

The change is intentionally Marlin-specific because arbitrary within-expert ordering remains a valid contract for the general MoE alignment operation.

## Test Plan

- Add a focused regression test for two equivalent within-expert token orderings.
- Poison the inactive alignment-buffer tail with different arbitrary values and verify that it cannot affect the canonical active prefix.
- Validate the canonicalization helper at the routing-buffer size where the issue was isolated.
- Validate the underlying raw-vs-canonical Marlin behavior on SM120 hardware.

## Test Result

The regression case canonicalizes both equivalent layouts to the same active prefix:

`[1, 3, 4, 6, 7, 8, 9, 9, 0, 2, 5, 9]`

A same-forward Marlin W13 A/B experiment used identical input activations, quantized weights and scales, `expert_ids`, `num_tokens_post_padded`, top-k weights, launch parameters, and separately zeroed output/workspace buffers. The only changed input was the legal ordering of `sorted_token_ids`.

The originally isolated geometry was:

- M = 8192
- K = 4096
- N = 2048
- top_k = 6
- block_size_m = 64
- global_num_experts = 256
- local_num_experts = 128

Across 3 requests and 2 TP ranks, all 6 raw-vs-canonical comparisons produced different W13 tensors.

Observed numerical differences were small:

- max BF16 ULP distance: 4
- representative max absolute difference: 0.0078125
- representative RMS difference: ~1.50e-5
- non-finite values: 0

Canonicalizing the routed token order removed the captured W13 divergence and the downstream layer-0 divergence.

A GPU microbenchmark of the canonicalization helper on an NVIDIA RTX PRO 6000 Blackwell Max-Q with a 65,280-slot routing buffer averaged 0.226 ms/call over 200 iterations.

- vision2031 · comment · 2026-08-30T23:54:10Z · [source](https://github.com/vllm-project/vllm/pull/52532#issuecomment-5472047583)

Confirming this fix on GB10 / sm_121a (DGX Spark class), serving Qwen3.8-Flash-Next W4A16 (Intel AutoRound, GPTQ-Marlin path, 512-expert MoE) on the `qwen38-flash-next` dev image (0.1.dev20073).

Symptoms before the fix, all at temperature 0 with fixed seed:
- run-to-run first-token logprob jitter (~0.5–2.4 max delta) from ~100-token prompts;
- intermittent catastrophic divergence (top-5 token sets differ, max logprob delta ~92) once prompts exceed ~528 tokens — consistent with near-tie MoE routing flips amplifying the split-K ordering differences described in #52525;
- long generations (250 tok) over long contexts diverged between identical requests (both cached and cold-vs-cached).

`VLLM_MARLIN_USE_ATOMIC_ADD=0` and a deterministic QSA top-k did not change any of this (MoE Marlin path already runs `use_atomic_add=False` here).

I ported this PR's `_canonicalize_marlin_moe_token_order` onto the dev image as an overlay (the function + single call site apply cleanly). Result: bit-exact zero logprob deltas across prompt lengths 100 → 122k tokens, identical greedy outputs cold vs prefix-cache-hit, measured cost ~2% single-stream decode (30.5 vs 31.0 tok/s) and no measurable prefill change (≥2,270 tok/s at 174k-token prompts, MTP=3, chunked prefill 8192).

Would love to see this merged - on sm_121 all int4/AWQ checkpoints route through moe_wna16_marlin (machete is Hopper-only), so this PR is currently the only practical determinism fix for 4-bit MoE on DGX Spark class hardware.

- CarrotSwordsman · comment · 2026-09-01T13:54:32Z · [source](https://github.com/vllm-project/vllm/pull/52532#issuecomment-5495049832)

I independently reproduced #52525 on an NVIDIA H20 (Hopper, sm_90) and tested the exact canonicalization implemented in this PR. It restores bitwise reproducibility in this environment.

Environment:

- GPU: NVIDIA H20, sm_90
- Driver: 535.247.01
- CUDA: torch cu128 build; local toolkit 12.1
- vLLM: 0.11.0 wheel
- torch: 2.8.0+cu128
- dtype / quantization: BF16 / Marlin uint4b8
- geometry: M=2048, K=1024, N=512, E=16, top_k=4, block_size_m=64

With byte-identical, seeded `topk_ids`, five consecutive `moe_align_block_size` calls produced different legal layouts:

- 32,356 differing `sorted_token_ids` entries across four comparisons
- 0 differences in `expert_ids`
- 0 differences in `num_tokens_post_padded`
- identical token multisets
- 548 blocks whose contents changed, confirming cross-block reassignment rather than only within-block permutation

The stock `fused_marlin_moe` path was correspondingly nondeterministic: across three identical calls, the worst pair differed in 868,053 / 2,097,152 output elements, with max absolute difference 0.001953125. Freezing the alignment output made the path bit-identical, while zeroing the intermediate GEMM outputs did not restore determinism.

I then transplanted `_canonicalize_marlin_moe_token_order` from this PR into the probe without otherwise changing the vLLM 0.11.0 fused path:

- Applying it to all five unstable alignment outputs reduced the alignment differences from 32,356 to 0.
- Wrapping the stock fused path with it reduced output differences from 868,053 / 2,097,152 to 0 / 2,097,152 across three calls.
- Sorting only within each block had no numerical effect, but this PR sorts the full contiguous expert region. Relative to one frozen raw layout, that full-region canonicalization changed 1,017,312 / 2,097,152 output elements (max absolute difference 0.000976562), demonstrating that it selects one deterministic cross-block layout.

So both the issue and the proposed fix reproduce independently on Hopper sm_90 / CUDA 12, not only the reporter's Blackwell sm_120 / CUDA 13 setup.
