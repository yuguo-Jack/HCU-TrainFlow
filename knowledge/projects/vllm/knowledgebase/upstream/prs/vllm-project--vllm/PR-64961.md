# [Bugfix][Frontend] Convert Responses content parts to chat parts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64961) · state: open · merged: False

## Original PR description



## Overview

Fixes #64789. Role-bearing `/v1/responses` input items and list tool outputs now reach the renderers with chat content parts, so `input_text` requests render on `--tokenizer-mode mistral` models instead of returning 400.

```diff
 _construct_message_from_response_item(item)
-  if item is a ResponseFunctionToolCallOutputItem:
-    return a tool message with item.output
   if item is a function or custom tool output:
     output = the item as a dict
+    if output is not a string:
+      pass every part through _to_chat_content_part
     return a tool message
   if item has a role:
-    return item
+    if content is a list:
+      return a new message with every part passed through _to_chat_content_part
+    return item
```

| Responses part | Chat part |
|---|---|
| `input_text`, `output_text` | `text` with the same text |
| `input_image` with a string `image_url` | `image_url` with `url` and `detail`, without `detail: "original"`. Other fields stay on the part, including `file_id` |
| `input_image` without a URL, any other part | unchanged |

The same table applies to role `content` and to `output` on `function_call_output` and `custom_tool_call_output`. String content and string `output` stay as they are.

## Claims

- `input_text` parts in system and user items render on Mistral tokenizers and produce the same tokens as string content.
- `input_text` parts in `function_call_output` and `custom_tool_call_output` render on Mistral tokenizers and produce the same tokens as a string `output`.
- `input_image` parts with a URL become `image_url` parts that `mistral-common` accepts, with `detail` kept unless it is `original`, which chat parts cannot carry.
- HF render results stay the same, with the exceptions listed under Blast Radius.

## Details

**Root cause:** `_construct_message_from_response_item` returned role-bearing items and list tool outputs as they arrived. `parse_chat_messages` accepts both part formats, which hid this on HF. The Mistral renderer passes the original messages to the tokenizer, and `mistral-common` only accepts chat parts.

Request validation gives a list tool output one of four shapes:

| Item | Output after validation | On main, list output |
|---|---|---|
| `function_call_output` | list of dicts | 400 on Mistral |
| `function_call_output` with `id`, `status` and `created_by` | `ResponseFunctionToolCallOutputItem` with SDK objects as parts | 500 on every renderer: `isinstance(item, ResponseFunctionToolCallOutputItem)` passed the objects on |
| `custom_tool_call_output` | one-shot iterator, because the SDK types this `output` as `Iterable` | 200 on Mistral with an empty tool result: `parse_chat_messages` consumed the iterator, and the tokenizer got it empty |
| `custom_tool_call_output` with `id` and `status` | `ResponseCustomToolCallOutputItem`, dumped to dicts | 400 on Mistral |

**Why here:** this is the layer that promises chat messages, so every renderer gets chat format and no renderer changes. A Mistral-only fix would leave the same mismatch for any renderer that forwards original messages.

**Not a duplicate:** on 2026-11-01 I searched open PRs for `64789 in:body`, `input_text mistral`, `input_text`, `function_call_output`, `custom_tool_call_output`, and the two people who offered to work on the issue. None makes this conversion. #35508 touches the same function for assistant and reasoning history, #48237, #49130 and #64941 handle assistant empty or refusal content, and #64861 and #64934 map the `developer` role. The assistant branches are untouched here. For tool outputs: #54786 accepts list `function_call_output` in `harmony.py` only, #61340 defaults `detail` in `protocol.py`, and #56285 changes this branch only to the form main already has. #50782 edits `tool_call_id` in the `ResponseFunctionToolCallOutputItem` branch that this PR removes, so whichever lands second needs a small rebase.

**Decisions:**

- `detail: "original"` is dropped. `ResponseInputImageParam` allows it, but chat `ImageURL` rejects it with a `ValidationError`, so keeping it would break requests that work on HF today. vLLM ignores `detail` when parsing.
- Extra part fields such as `cache_control` and `uuid` are kept, because the HF path passes them on. `file_id` is kept for the same reason. `ChatCompletionRequest.from_openai` reads only `image_url` from an image part, so it accepts `file_id`, and the Mistral tokenizer gives the same tokens with `file_id` set, `null` or absent.
- `ResponseFunctionToolCallOutputItem` no longer has its own branch. The generic branch already dumps SDK items to dicts, so one path now covers strings, dict parts and SDK parts.
- The tool output branch checks for "not a string" rather than for a list, so it also covers the one-shot iterator.
- `/v1/responses` rejects `text` parts during request validation, so the HF test compares against a `text` part on the chat route. It sets `add_special_tokens: true` because the Responses route renders with the tokenizer default.
- The regression tests use `RemoteLaunchRenderServer` rather than `RemoteOpenAIServer`. It runs the same `OnlineRenderer.render_responses` as `/v1/responses` over real HTTP, without a GPU or weights.

**Limitations:**

- `input_image` was not rendered through a real vision model, with or without `file_id`. The evidence is the unit tests and `ChatCompletionRequest.from_openai` from `mistral-common`, which accepts the converted parts. On the non-vision Magistral render server such a request now returns the same 500 as a chat `image_url` request (`Can't load image processor`), where it was a 400 before.
- An `input_image` in a tool output converts, but Mistral still returns 400 with `Unexpected content chunk types in tool message: ['ImageURLChunk']`. `mistral-common` raises that for any image in a tool message, so the conversion layer cannot fix it.
- `/v1/responses` generation was not run, since that needs weights and a GPU.
- `output_text` conversion is covered by a unit test only. Over HTTP, assistant history takes the existing branches, and the Mistral test checks that result.
- Out of scope: `input_text` sent to Chat Completions, `input_file` and `input_audio`, and the `developer` role, which still returns `Unknown message role: developer` on Mistral.

**Door:** two-way. This is request translation only, with no new API surface.

**Blast Radius:** Responses-input. On non-Harmony models, the conversion covers list `content` on role-bearing items and non-string `output` on function and custom tool outputs. It does not cover string content, `instructions`, or stored `previous_response_id` history. Assistant history takes the existing branches first, which keep only the first part's text, so it never reaches the conversion. Harmony does not use this function.

Three behavior changes reach HF models:

- System `input_text` parts that start with `x-anthropic-billing-header` are now stripped like `text` parts, because `_strip_claude_code_billing_header` only matches `text`.
- `input_image` `detail` moves under `image_url`, so chat templates no longer see it as a top-level field of the image part.
- A `function_call_output` with `id`, `status` and `created_by` and a list `output` renders instead of returning 500.

One more reaches only Mistral models: `custom_tool_call_output` with a list `output` used to return 200 with an empty tool result, and now renders the output, so the prompt for those requests changes.
