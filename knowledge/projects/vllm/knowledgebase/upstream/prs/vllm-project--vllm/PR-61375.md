# [Bugfix][KV Offload] Store the chunk of a loaded partial tail

[Upstream PR](https://github.com/vllm-project/vllm/pull/61375) · state: open · merged: False

## Original PR description



## Overview

After a load that ends in a partial tail, the OffloadingConnector scheduler never stores the chunk that holds the tail. Each later lookup of the same prefix stops at the same partial tail, and the request computes all tokens after it again. This PR starts the store of a full-attention group at the chunk of the partial tail.

Related: #61019 (draft) changes the copy-on-write hand-off store of partial tails with EAGLE/MTP groups. It does not change `next_stored_chunk_idx`, and its head (3276fddc9) merges with this PR without a conflict.

Duplicate check: I searched the open and closed issues and PRs for `next_stored_chunk_idx`, "partial tail" and "offload". #56795, #52771 and #51761 report other defects of the store index. No issue or PR reports this case.

AI assistance was used for this PR (Claude Code): the root-cause analysis, the patch, the test and this description. I reviewed every changed line and the test results.

## Claims

- After a load that ends in a partial tail, the connector stores the chunk of the tail when the chunk is full. The next lookup of the prefix then goes past it.
- On a hybrid MLA + KDA model with partial tails and 32 concurrent agent sessions, the prompt tokens left to compute after the cache hits fall from 12,220 to 3,613 per warm turn, and the output throughput rises from 317 to 515 tok/s.

End to end, on an older base: nightly 21d93d0d8 (2026-10-05). The lines that this PR changes are the same in that base and in main. Both runs have the same other local patches.

- Model: GLM-5.3-Flash (MLA and KDA layers; the KDA groups use Mamba cache mode `align`), W4A16 checkpoint with BF16 activations, 2× H200, TP=2, no expert parallelism.
- MTP with 3 probabilistic draft tokens, block verification and `disable_eagle_block_drop`.

- OffloadingConnector with a 330 GiB CPU tier and no disk tier.
- Load: simulated coding-agent sessions, 16 and then 32 concurrent sessions, 8 minutes per level. Each session starts new, and its context grows from about 75K to 140K tokens (6K shared prefix). One run per configuration; the run-to-run difference of this load is about ±1 % at 16 and ±3 % at 32 sessions.

| Metric (16 / 32 sessions) | Without the fix | With the fix |
|---|---|---|
| Output tok/s | 474 / 317 | 472 / 515 |
| Computed prefill tokens per request | 6,561 / 19,597 | 6,603 / 9,213 |
| Prompt tokens left after the cache hits, warm turns at 32 sessions | 12,220 | 3,613 |
| Prompt tokens from the CPU tier, 32 sessions | 74.7 % | 89.2 % |
| Warm TTFT p50 | 0.9 / 5.9 s | 0.9 / 2.1 s |

Without the fix, the CPU-tier hit of a session at 32 sessions stays at one boundary for several turns. For example, it stays at 114,752 tokens for prompts of 138K, 139K, 144K and 145K tokens, and each of these turns computes 24K–30K tokens again. At 16 sessions the computed prefill does not change (6,561 and 6,603 tokens per request).

## Details

Root cause: `update_state_after_alloc` sets `num_chunks = cdiv(num_cached_tokens, tokens_per_chunk)`. This count includes the chunk of a partial tail. For the chunk-level policy, `next_stored_chunk_idx = num_chunks` then treats that chunk as a hit chunk. The load fills the chunk only up to the tail boundary, and the request computes the rest of it. The store starts at the next chunk, so the full chunk is never stored, and its key never becomes a hit. Example: a load to 114,752 tokens with 2,304-token chunks gives `num_chunks = 50`, and the store skips chunk 49.

Fix: for a full-attention group (`sliding_window_size_in_chunks is None`), the store starts one chunk earlier when the load ends in a partial tail. Sliding-window, chunked-local and Mamba groups keep the skip: their block for that chunk can hold the tail state, which is not the state at the chunk end. The Mamba groups store their boundary states through the copy-on-write path (`requires_cow_source`).

Scope: the change has an effect only when `supports_partial_tail` is true (a Mamba group in align mode, one block per chunk) and a load ends in a partial tail. In all other cases `next_stored_chunk_idx` is unchanged.

Cost: one more chunk store per load that ends in a partial tail. The CPU tier did not have that chunk before.
