# [Bugfix] Keep default max_tokens in rendered sampling_params

[Upstream PR](https://github.com/vllm-project/vllm/pull/65389) · state: closed · merged: True

## Original PR description

## Overview

In scale-out serving, `/v1/chat/completions/render` and `/v1/completions/render` with `max_tokens` 16 return `sampling_params` without `max_tokens`, so `/inference/v1/generate` produces 700 (chat) and 40943 (completions) tokens instead of 16; a `/v1/completions/render` request without `max_tokens` defaults to 16 and takes the same path. `SamplingParams` omits fields equal to their defaults, and generate reads the absent key as not sent. `GenerateRequest` now writes `max_tokens` back into the dumped `sampling_params` when the request set it.

Fixes #65388

## Claims

- Render → generate with `max_tokens` 16 stops at 16 tokens with `length` on chat and completions, instead of 700 and 40943 tokens.
- `/v1/completions/render` with `max_tokens` omitted or `null` returns `max_tokens` 16, and generate stops at 16 tokens as coupled `/v1/completions` does, instead of 40943.
- `/v1/chat/completions/render` with `max_completion_tokens` 16, `/v1/messages/render` with `max_tokens` 16 and `/v1/responses/render` with `max_output_tokens` 16 return `max_tokens` 16 instead of leaving it out.
- No change for a generate body that omits `max_tokens`: its dump still omits the key, and generate applies the server default.

## Details

**Root cause.** `SamplingParams` is a `msgspec.Struct` with `omit_defaults=True` and `max_tokens` default 16, so `GenerateRequest.model_dump()`, which render returns, leaves out `max_tokens` when it is 16. Generate's `is_sampling_param_provided("max_tokens")` checks the keys of the raw `sampling_params` dict, so `serve_tokens` treats the absent key as not sent and replaces it with the `get_max_tokens` server default. `CompletionRequest.max_tokens` defaults to 16 and `normalize_null_max_tokens` maps `null` to it, so completions requests without `max_tokens` take the same path.

**Fix.** A wrap `model_serializer` on `GenerateRequest` writes `sampling_params.max_tokens` back after the normal dump when `is_sampling_param_provided("max_tokens")` is True and the key is missing. In-process requests (render) count every field as provided; a body parsed without `max_tokens` dumps unchanged.

**Related PRs.**
- #42329 — added `is_sampling_param_provided` and the server-side `max_tokens` default in `serve_tokens`. It introduced the fallback that the absent key triggers.
- #35684 — added `_serialize_msgspec`, which dumps `SamplingParams` with `msgspec.to_builtins`. It introduced the dump that leaves out default fields.


Only `max_tokens` is written back: `serve_tokens` is the only caller of `is_sampling_param_provided`, and other omitted defaults (`top_k` 0, `min_tokens` 0) parse back to the same value.
Generate cannot fix this on its side: once the key is absent, a resolved 16 and an unsent limit look the same.
The fix is on the serializing side, so a render server on main talking to a generate server with this PR still drops 16.
