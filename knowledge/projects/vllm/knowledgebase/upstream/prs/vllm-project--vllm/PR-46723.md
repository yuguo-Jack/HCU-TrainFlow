# [Rust Frontend] Avoid redundant decode per token in incremental detokenizer

[Upstream PR](https://github.com/vllm-project/vllm/pull/46723) · state: open · merged: False

## Original PR description

## Purpose

`DecodeStream::push_token` (the per-token streaming detokenization path) called
`tokenizer.decode()` twice per token: once to diff out the newly produced text,
and a second time only to recompute the `prefix` used as the next iteration's
byte offset. Since only `prefix.len()` is read downstream, and — for a
context-independent decoder — the retained tokens decode to exactly the suffix
already produced by the first decode, that second call is redundant. Reusing
the slice removes one of the two `decode()` calls per token.

This reuse is only sound when `decode(a ++ b) == decode(a) ++ decode(b)` at
token boundaries. That holds for byte-level decoders but not for
context-dependent ones such as Metaspace/SentencePiece, where a retained token
renders differently in isolation (e.g. a stripped leading space), which would
make `prefix.len()` wrong and silently swallow a token. So the fast path is
gated on a new `Tokenizer::decode_is_context_independent()` (default `false`);
context-dependent decoders keep the original re-decode behavior. The gate is
matched on the decoder itself — byte-level fastokens, and the HF backend when
its top-level decoder is `ByteLevel` — rather than on the backend enum.

## Test Plan

```bash
cargo test -p vllm-tokenizer
cargo bench -p vllm-tokenizer --bench hf -- tokenizer_incremental_decode
```

- `streaming_matches_full_decode_real_tokenizer`: streams a real byte-level BPE
  tokenizer (ASCII + CJK + emoji, so tokens routinely split multi-byte
  characters across boundaries) and asserts the incremental output is
  byte-identical to a full `decode()`.
- `streaming_matches_full_decode_metaspace`: a Metaspace tokenizer stays on the
  re-decode path and streams correctly (the leading-space case the fast path
  would break).
- `adversarial_byte_streams_match_full_decode`: streams byte sequences with
  invalid UTF-8 at and across token boundaries (lone lead bytes, stray
  continuations, permanently invalid bytes, literal U+FFFD output, dangling
  lead byte at flush) and asserts streamed output equals a one-shot decode.
- `tokenizer_incremental_decode` benchmarks both the fastokens byte-level and HF
  backends (the path had no benchmark before this PR).

## Test Result

- 44 tests pass; `clippy -D warnings` and `rustfmt --check` clean.
- Criterion (Qwen/Qwen3.5-0.8B tokenizer, ~2.8k-token stream, isolated target
  dir per variant, alternated runs):

  | `tokenizer_incremental_decode` | before | after |
  |---|---|---|
  | `fastokens` (byte-level; default loader path) | 425–457 µs | ~334 µs (**~21–26%**) |
  | `hf_tokenizers` (fallback backend) | ~1.18 ms | ~745 µs (**~37%**) |

I went back and re-measured this properly rather than argue from the old numbers. Setup: A/B on the crate bench (Qwen/Qwen3.5-0.8B `tokenizer.json`, ~2.8k-token stream), a separate cargo target dir per variant, binaries executed in alternating rounds to cancel machine drift.

| `tokenizer_incremental_decode` | merge-base | before last commit | now |
|---|---|---|---|
| `fastokens` (byte-level; default loader path) | 425–457 µs | ~337 µs (**-21–26%**) | ~334 µs |
| `hf_tokenizers` (fallback backend) | ~1.18 ms | ~1.18 ms (no change) | ~745 µs (**-37%**) |

Measuring surfaced a gap in the previous revision, which the new commit fixes:

1. The gate matched on the backend enum, so an hf-loaded tokenizer with a ByteLevel decoder — context-independent by the same argument as the fastokens byte-level backend — never took the fast path. That was also the only backend `bench_incremental_decode` exercised, so the bench showed nothing for its own optimization. The gate now checks the decoder property instead, conservatively (top-level `ByteLevel` only; `Sequence`-wrapped decoders stay on the re-decode path), and the bench covers both backends. Metaspace behavior is unchanged and its regression test still passes.
2. The fast path's soundness reduces to "`from_utf8_lossy` composes at the clean boundaries the `ends_with('\u{FFFD}')` guard enforces", so I added a streamed-vs-full-decode test that puts invalid UTF-8 at and across token boundaries: lone lead bytes, stray continuations, permanently invalid bytes, literal U+FFFD output, and a dangling lead byte at flush.

Repro: `cargo bench -p vllm-tokenizer --bench hf -- tokenizer_incremental_decode`.

On whether it's critical enough: per ~2.8k-token streamed response this saves roughly 90 µs on the default path and 440 µs on the hf fallback — modest per request, but it's the per-output-token hot path shared by every concurrent stream, and the change is small and opt-in behind a decoder property that defaults to `false`. That said, if you'd still rather not carry it right now, that's fine — happy to close and revive if frontend CPU shows up in profiles.

- blasrodri · comment · 2026-07-08T15:50:06Z · [source](https://github.com/vllm-project/vllm/pull/46723#issuecomment-4916629717)

A note on the direction here: I went looking at how other Rust inference stacks handle per-token detokenization, and this PR's core idea — that byte-level decode composes at token boundaries, so there's no need to re-decode a growing window — is exactly what `toktrie` (used by mistral.rs) does in production: it precomputes a flat `token_id → bytes` table once and streams by accumulating bytes and emitting the longest valid-UTF-8 prefix. vLLM's Python path (HF `DecodeStream`) and upstream `tokenizers` both still re-decode per step (`step_decode_stream` calls `decode()` twice per token on a growing window), so the memoization isn't something those paths already do.

This PR takes the conservative first step (2 decodes/token → 1). The same reasoning extends cleanly to **0 decodes/token** by memoizing the `id → bytes` table (flat `Vec<u8>` + offsets, matching toktrie's layout) and selecting it for byte-level backends, with `DecodeStream` kept as the fallback for context-dependent tokenizers. I have that prototyped with equivalence tests against the current path — happy to fold it in here or land it as a follow-up.

Either way, the open question is still whether detok CPU is worth optimizing for your deployments — glad to hear your read before doing more.

For Metaspace/SentencePiece-style decoders, this caches the full-context delta instead of the text produced by the retained IDs. For example, tokens `▁Hello`, `▁world`, `!` decode as `[0,1] -> "Hello world"`, but after draining `[0]`, the retained `[1]` decodes to `"world"` because Metaspace strips the leading replacement at the start of a slice; caching `" world"` makes the next `decode([1,2]) == "world!"` hit `string.len() <= prefix_len`, so `!` is never emitted or flushed. The old second decode produced the correct retained-prefix length, so this fast path needs to be limited to context-independent decoders or recompute here.
