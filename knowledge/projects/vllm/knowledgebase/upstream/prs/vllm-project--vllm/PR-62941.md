# [Perf][DSv4.1] Pack DSpark verify positions into one FlashMLA head tile on SM90

[Upstream PR](https://github.com/vllm-project/vllm/pull/62941) · state: open · merged: False

## Original PR description

## Overview

On SM90, packs each request's DSpark verify positions (1 + K tokens) into one 64-row FlashMLA head tile, instead of padding every position to 64 rows. This targets DeepSeek-V4.1 at TP8, where each rank has 8 heads. It sits behind `VLLM_DSV41_PACK_SPEC_DECODE=1`, off by default. Depends on vllm-project/FlashMLA#34 (per-row slot masks); FlashMLA is temporarily pinned to that branch.

## Claims

- On H20, at DeepSeek-V4.1 TP8 c1-layer shapes with DSpark K=3 (98 requests × 4 positions, SWA 128 + top-k 512), the per-layer sparse-MLA decode cost goes from 334 µs to 147–282 µs, i.e. 1.12–2.29× faster. This includes all overheads: the packed kernel, the Q/O repack, and the amortized key-union build. The spread comes from how much the 4 positions' top-k lists overlap.
- Output is the same as the unpacked path up to bf16 rounding: each position still sees exactly its own keys and attention sink.
- *Projected, not yet measured:* +4–7% end-to-end decode throughput at the current production load (~39 running requests per TP8 replica), and +8–11% at c100–128. The basis: sparse MLA decode is 11 ms of a ~55 ms DSpark cycle at c98 in a production trace.

## Details

- **Why it helps.** FlashMLA's SM90 sparse decode tiles heads by 64 (the WGMMA M). With 8 heads per rank, 7/8 of every tile is padding. Profiling on H20 shows this kernel is bound by tensor throughput (about 80% of the measured bf16 WGMMA peak), so the padding is real cost. A request's 1 + K verify positions attend nearly the same SWA window, and often overlapping top-k sets. So slot `s` of one tile holds position `s`'s heads, the key list becomes the union, and vllm-project/FlashMLA#34's per-key bitmask restores each slot's own keys. That is 4× fewer tiles, and at most `|SWA ∪| + |top-k ∪| ≤ 131 + 2048` key rows per request, versus 4 × 640 today.
- **Changes.**
  - `ops/packed_sparse_decode.py`:
    - `merge_slot_indices` (Triton) sorts and dedups each request's keys and ORs their slot bits.
    - `pack_slot_rows` and `unpack_slot_rows` are single strided copies.
  - `DeepseekV4FlashMLAAttention._forward_decode_packed`:
    - Builds the SWA union once per step, and the top-k union once per index source (8 per step).
    - Keeps one `FlashMLASchedMeta` per index source, because split plans depend on the union lengths.
    - Builds the attention sink lazily, so that tile row `r` uses head `r % n_local_heads`; unused rows stay `-inf`.
- **Gate.** SM90 only, padded heads = 64, `(1 + K) × n_local_heads ≤ 64` (TP8 with K ≤ 7), and only steps where every decode request is exactly 1 + K tokens wide. Production DSpark runs with `enable_adaptive_verification: false`, so that holds on every verify step. Other steps take the existing path unchanged.
- **Tradeoffs and limits.**
  - At 16 requests with fully disjoint top-k lists, the union-build overhead wins and packing is 0.87×. That range is covered by #59418's small-head kernel.
  - The packed path adds a per-step metadata cache field on `DeepseekSparseSWAMetadata`; nothing else in shared code changes.
  - CUDA-graph capture of the per-source schedule metadata is not yet verified, which is one of the TODOs above.
- **Not a duplicate.**
  - #59418 (mine) covers ≤16 decode tokens per step, with an m16 `mma.sync` kernel; above that it falls back to FlashMLA, which is the range this PR targets.
  - vllm-project/FlashMLA#31 is an h32/small-heads SM90 kernel, which helps few-query steps.
  - #62633 targets SM10x mega-attention at TP2/TP4.
  - None of them packs multiple queries into one WGMMA tile.
- **CI.** The new test needs SM90 and skips elsewhere; whether CI's SM90 runners pick it up is TODO. The pin to the FlashMLA fork will be reverted to an upstream commit once vllm-project/FlashMLA#34 merges.
