# [Perf][Sampler] Histogram-bracket top-p for large p-only batches

## Overview

Top-p masking of large batches with no active top-k now uses a new Triton pipeline, inside `apply_top_k_top_p_triton`. It replaces the monolithic `_topk_topp_kernel` for p-only CUDA batches of ≥ 32 rows. That kernel runs one program per row and searches the pivot with repeated full-vocabulary sweeps. With a 200k vocabulary it costs 0.8–2.1 ms for 256 rows.

Such batches reach `apply_top_k_top_p` from these callers:

- **The sampler, when the fused FlashInfer sampler is not used:** the Model Runner V2 sampler falls back to `apply_top_k_top_p` + Gumbel sampling when the batch has a greedy or seeded request, when processed logprobs or the sampling mask are requested, or when FlashInfer sampling is unavailable or off. The V1 sampler does the same in `forward_native`. Decode with ≥ 32 concurrent requests and one greedy request among them is enough.
- **The V1 rejection sampler:** it masks every verification row's fp32 logits with `apply_top_k_top_p`.
- **The Model Runner V2 rejection sampler,** when it processes the logits before verifying: `apply_sampling_params` copies them to fp32 and masks them here.

**Relation to #65101–#65103.** Those PRs add a bf16 top-p cutoffs op to the Model Runner V2 rejection sampler. The verify kernels then mask each row at its cutoff as they load the logits. Their gate runs before `apply_sampling_params` and skips it, so the batches it takes never reach this code. On GB300 their op is 1.7–1.8× faster than this PR on those batches (details below), so this PR does not compete there. It covers what their gate leaves to the stock path:

- non-bf16 logits (fp32 heads, fp16 models, or an FP32 logits gather);
- GPUs other than SM90 / SM100 / SM103;
- batches with logits processors (penalties, logit bias, bad words, custom), thinking-budget forcing, `min_p`, processed logprobs or the sampling mask;
- the V1 rejection sampler and the non-FlashInfer sampler paths above.

No gate is needed here to defer to their op: when it applies, `apply_top_k_top_p` is not called. Earlier revisions of this description used speculative-decoding verification as the motivating case. This revision drops that framing and keeps the code path unchanged.

The new path finds the exact top-p boundary in four streaming passes per row, each split over several programs per row:

1. min/max;
2. sum of exp plus a 4096-bin histogram of `max − x`;
3. the exact mass above the boundary bracket, plus a gather of the bracket's tokens;
4. the mask.

Two small per-row kernels sit between the passes. One brackets the boundary from the histogram's count bounds, tightened near p = 1 by bounding each prefix's mass as the exact total minus the bounds of the bins below it. The other runs a fine histogram over the gathered tokens and sorts the few tokens left in the fine bracket by (logit desc, index asc).

Half-precision logits upcast to fp32 (bf16 especially) often put hundreds of exactly tied tokens in the fine bracket, too many to sort. Those rows walk the bracket's distinct values downwards instead, adding each value's mass, and resolve the boundary value's ties by index. If even the gather overflowed, the same walk runs over the whole row. Mass sums use Kahan-compensated fp32.

## Details

- `vllm/v1/sample/ops/topp_histogram_triton.py` (new): six kernels and their dispatchers.
  - **Programs per row:** aim for 4 programs per SM, with slices of ≥ 4096 tokens.
  - **Scratch:** one grow-only workspace per device, rounded up to powers of two. About 50 MB at 256 rows and 170 MB at 2048 rows. It is allocated lazily, like the monolithic kernel's buffer cache.
- **Bracket safety:** the coarse/fine bracket uses count × exp bounds with a 1e-5 relative margin, so the exact boundary always lies inside it.
- **Crowded brackets:**
  - A fine bracket of more than 256 tokens, or a coarse bracket that overflows the gather capacity (2 × 8192 / slices tokens per slice), is resolved exactly by the distinct-value walk.
  - The fine-bracket case is the common one on real bf16 logits, about 1% of rows. Over the gathered tokens the walk costs little.
  - Over the whole row it is slow. It never happens on real logits at p ≤ 0.999, only on synthetic rows with extreme ties.
  - Only a bracket with more than 64 distinct values beyond the scratch keeps its whole coarse bracket: a superset within about one bin width of the boundary, whose mass still reaches `p`.
  - **Worst case:** adversarial rows (> 16k distinct values in one coarse bin) cost 2.9 ms per call at 64 rows. At 256 rows they cost 5.0 ms with every row adversarial, or 3.2 ms with one.
- **Cost of exactness:** on the real logits the per-call time is 127 µs at 64 rows (113 µs without the walk) and 375 µs at 256 rows (370 µs).
- `topk_topp_triton.py`:
  - routes p-only CUDA batches of ≥ 32 rows to the new path;
  - stops warming up the monolithic kernel for p-only rows on CUDA, and the split kernels' p-only variants for batches of ≥ 32 rows;
  - clears the new scratch in `reset_buffer_cache`.
- **Related open PRs:**
  - #65101–#65103 (bf16 top-p cutoffs applied on load in the Model Runner V2 rejection sampler) take the common verification case and are faster there. This PR covers the batches that still reach `apply_top_k_top_p`.
  - #60993 (opt-in FlashInfer top-k/top-p) and #48928 (FlashInfer top-p in the MRV2 rejection sampler) add alternative backends.
  - #62596 replaces the monolithic kernel's pivot.
  - This PR leaves the monolithic kernel alone and covers the large-batch p-only case natively in Triton.

Heads-up on an overlapping approach to the same speculative-decoding verify batches, so reviewers can compare the two:

- #65101 (draft) adds `topp_cutoffs_lse`, a one-launch CUDA op: each bf16 row is counted into a shared-memory histogram over its 16-bit values by one thread-block cluster, and the cutoff is found from the counts.
- #65102 (draft) applies those cutoffs as the rejection kernels load the raw target logits, so temperature + top-p chunks skip the fp32 copy and the mask kernel; #65103/#65104 reuse the op's log-sum-exp in the rejection sampler.

How it differs from this PR:

- **Ties:** keeps every token tied with the cutoff value; this PR breaks the boundary tie by index.
- **Exactness:** sums are exact 2⁻⁴⁰ fixed-point integers with an error bound, and rows within the bound are redone in fp64, so the cutoff matches an fp64 ties-kept reference and does not depend on reduction order. This PR uses Kahan fp32 and may move the boundary by one tied token near fp32 rounding of p.
- **Output:** also returns the fp64 log-sum-exp of the kept tokens, which the rejection sampler uses in place of its own stats pass.
- **Scope:** bf16 logits on SM90 / datacenter Blackwell only (thread-block clusters, ~150-200 KB of shared memory per CTA); this PR is a general Triton path.
- **Speed:** on GB300 at V = 202,048, 256 rows, the op measured 122 µs (CUPTI, cold L2, synthetic rows); this PR reports 370 µs for the same shape. Not measured side by side.

Happy to run both on the same dumped verify rows if that helps.

The six kernels in this module are never registered for JIT warmup, contrary to the PR description ("All kernels are registered for JIT warmup").

`triton_kernel_dispatcher_with_warmup` does not self-register; the only call sites are explicit `.register_warmup()` calls, and `register_top_k_top_p_warmups()` in `vllm/v1/sample/ops/topk_topp_sampler.py` still lists only `_topk_topp` and the three `_topp_split_*` dispatchers. At the same time `_topk_topp_warmup_inputs` (topk_topp_triton.py) now stops warming the monolithic kernel for p-only batches >= 32 on CUDA.

Net effect: the first p-only step with >= 32 rows after warmup JIT-compiles six kernels (one of them with a 4096-bin histogram, a sort and nested loops) on the hot path. That is a multi-second stall for one decode step, a warning with `--jit-monitor-mode=warn`, and a hard failure with `--jit-monitor-mode=error` (the `tests/jit_monitor` CI step runs in that mode).

Suggested fix: register all six launchers under `current_platform.is_cuda()` in `register_top_k_top_p_warmups`, and add a small test that asserts `get_warmup_keys()` is non-empty for each.

For p above about 0.995, `cl >= target` never fires and `last_bin` falls back to `NB - 1`, i.e. the bracket covers the whole tail. Even at p = 0.99 it is already too wide.

I re-implemented the coarse stage in pure Python (not a GPU run) on an LM-like bf16 row, V = 200064, max-min about 29:
- p = 0.95: 543 tokens in the bracket
- p = 0.99: about 21k tokens (gather capacity is 2 x 8192 = 16384 per row)
- p = 0.995 / 0.999: `last_bin` = 4095, 150k+ tokens

The tests only go up to p = 0.99 (`rand * 0.98 + 0.01`), and the real-logit validation is p = 0.95 only. top_p = 0.99 and 0.999 are common user settings.

Suggested fix: accumulate the exact per-bin mass in the coarse pass so the bracket width is limited by rounding rather than by bin width, or at least add tests for p in {0.99, 0.995, 0.999} and a documented fallback.

Cost cliff and silent loss of exactness in the overflow path (related to the comment on `last_bin`).

When any slice's candidate count exceeds `SLICE_CAP`, the row is resolved by this single-program-per-row walk over the whole vocabulary: up to `MAX_DISTINCT` = 64 iterations, each making two full-row sweeps (plus a third on the hit) in CHUNK <= 1024 steps. For V = 200k that is on the order of 25k dependent chunk iterations per row (I did not measure it, but it is orders of magnitude above the 0.3-0.4 ms of the normal path), and the kernel's latency is that of its slowest row, so one such row stalls the whole batch. The PR text says this was only seen on synthetic tie-heavy rows; natural rows with p >= 0.99 reach it.

If the 64 distinct values do not reach the target (`mode = 2.0` here and at the fine-bracket walk), the row keeps its entire coarse bracket. With `last_bin == NB - 1` that is every token, so top-p is effectively off for that row, with no log or counter. In my Python re-implementation of the walk, p = 0.99 / 0.995 / 0.999 on a bf16-like row all end in mode 2.

Suggested: bound the worst-case cost (a refinement pass over the bracket instead of a distinct-value walk, or route flagged rows to a sort-based fallback), and expose the number of mode-2 rows for debugging.

The workspace cache is keyed on the exact batch size and never evicted.

`key = (device, batch_size, slices, slice_cap)`, and `slices`/`slice_cap` are functions of `batch_size`, so every distinct verification-batch size gets its own set of scratch tensors (about 20 MB at 256 rows per the description; `hist` is programs x 16 KB and `cand_x`/`cand_i` are programs x slice_cap x 8 B, which is roughly 170 MB at 2048 rows). With speculative decoding the row count is num_reqs x (1 + draft tokens) and moves with concurrency, so over a server's lifetime many sizes get cached (32..max_num_seqs x (K+1) is up to ~2000 candidates). This is device memory that is allocated lazily at runtime, after vLLM's memory profiling sized the KV cache, and is only released by `reset_buffer_cache`. Numerical cancellation in the fine-bracket bounds: `(x_hi - ff * w2) - row_max`.

`x_hi = row_max - first_bin * w` is rounded to fp32 at the magnitude of `row_max`, then `ff * w2` is subtracted and `row_max` subtracted again. The absolute error of that exponent is about ulp(|row_max|). The coarse stage avoids this by working in `-(bin * w)` directly, which is why the 1e-5 `_BOUND_MARGIN` suffices there. Here the error is about 4e-6 at |row_max| in [32, 64) and 8e-6 in [64, 128), and exceeds the margin at about 128 and above (ulp 1.5e-5). `fb = (x_hi - x) * inv_w2` has the same problem, with the fine bin width as small as 7e-6 nats. For models with large logit scales the fine bracket can then miss the true boundary, and the boundary token is chosen from the wrong set.

Suggested: compute the exponent as `-(first_bin * w + ff * w2)` (and the bin index from `row_max - x`, not `x_hi - x`) so no large terms cancel.

Signed zero: the sort order and the mask comparison disagree.

`orderable()` works on the raw bits, so +0.0 and -0.0 are distinct keys (+0.0 sorts above -0.0). The mask kernel compares with float `==` / `>`, where they are equal. If the boundary token is a -0.0 and some +0.0 tokens have a larger index, those +0.0 tokens (ranked above the boundary) are dropped by `x == boundary_x & idx <= boundary_i`, so the kept mass can fall below p; the reverse case keeps lower-ranked -0.0 tokens. It needs exact zero logits (plausible with bf16 / quantized logits), but it is cheap to avoid: canonicalize -0.0 to +0.0 before building the key (e.g. `x + 0.0`) or compare bit patterns in the mask kernel.
