# [Model] Support hotwords for Qwen3-ASR

[Upstream PR](https://github.com/vllm-project/vllm/pull/62522) · state: open · merged: False

## Original PR description



## Overview

`Qwen3ASRForConditionalGeneration.get_generation_prompt` never reads `stt_params.hotwords`, so `hotwords` sent to `/v1/audio/transcriptions` is silently dropped for Qwen3-ASR, while Fun-ASR and MOSS-Transcribe-Diarize (#62329) consume it. This PR renders the hotwords into the system-turn context, which is the official SDK's `context` channel and already carries `prompt` since #35415. The hotwords go first, then the prompt, one per line.

**Why not just `prompt`?** #43430 tried this before and was closed as stale. On it, @DarkLight1337 noted that it is "more like supporting a custom system prompt rather than having actual hotwords". That is fair for Qwen3-ASR: unlike MOSS, its model card has no hotword template, so the list goes into the context as-is (adding a prefix made no difference, see Details). The value is that `hotwords` then means the same thing across Fun-ASR, MOSS-Transcribe-Diarize and Qwen3-ASR, which `prompt` cannot provide, because its meaning differs per model:
- Qwen3-ASR: context.
- Whisper: preceding text (`<|prev|>`).
- MOSS-Transcribe-Diarize: replaces the default instruction.
- Kimi-Audio: an instruction before the audio.

A client that sends a hotword list today gets it applied on Fun-ASR and MOSS, and silently dropped on Qwen3-ASR. Unlike #43430, this PR keeps the request `prompt` instead of replacing it. The `system_prompt` / `user_prompt` split suggested there touches every STT model and is left out; I'm happy to follow up on it.

Not a duplicate: `gh pr list --state open --search "hotwords"` only returns #62398 (VibeVoice-ASR, its own model file). #36018 (`response_prefix`, last updated 08-25) edits the same function; `git merge-tree` shows no conflict.

## Claims

- `hotwords` now takes effect for Qwen3-ASR, alone or together with `prompt`.
- Requests without hotwords are unchanged token for token. The one exception: a whitespace-only `prompt` or `hotwords` no longer emits a system turn that holds only spaces.
- `hotwords=X` renders the same tokens as the existing `prompt=X` path, so it inherits that path's behavior; end to end, the two agree as closely as two identical runs do.
- With a short relevant list, B-WER drops by 20-30% on LibriSpeech and hard-hotword misses more than halve on Aishell1-NE (tables below).

## Validation

Setup: RTX 6000 Ada, nightly wheel 953fa44 plus this patch (its Qwen3-ASR prompt and sanitizer code match the current base), `vllm serve Qwen/Qwen3-ASR-{0.6B,1.7B}`, `temperature=0`.

**Unit tests**: `pytest tests/models/multimodal/processing/test_qwen3_asr.py -k generation_prompt_context`. Before the patch, 5 failed (`blank`, `hotwords`, `prompt-and-hotwords`, `sanitized-hotwords`, `hotwords-forced-language`) and 2 passed (`none`, `prompt`); after, 7 passed. The tests decode the real prompt token ids.

## Details

- **Root cause**: #39674 added `TranscriptionRequest.hotwords` / `SpeechToTextParams.hotwords`, but each model has to map the field into its own prompt, and the Qwen3-ASR implementation never read it.
- **Rendering**: the list is passed through verbatim (sanitized like `prompt`), with no label. Adding `热词：` or `Hotwords: ` in front made no difference: CER and B-WER moved by ≤0.3 points on both models. The SDK examples also pass bare context.
- **Hotwords before the prompt**: this was measured with 5 prompts per language (generic, domain, instruction, long background, cross-language), 0/20/100 distractors on Aishell and N=100 on test-other, both models, compared with paired sign tests.
  - Aishell: hotwords-first wins on hard-hotword hits, 276:84 (p=5e-25) on 0.6B and 252:122 (p=2e-11) on 1.7B, which is +3 to +5 points of recall with short lists.
  - English: on par. 0.6B B-WER is 16.67% vs 16.84%; 1.7B is 12.25% vs 11.99%, i.e. prompt-first is slightly better there.
- **Order is per model**: #62398 (VibeVoice-ASR, open) puts the prompt before the hotwords for its own model. The order here is what measured best for Qwen3-ASR.
- **Scope**: `/v1/audio/transcriptions`, plus `/v1/audio/translations`, which shares the code path (only transcriptions was benchmarked). `/v1/realtime` keeps its own fixed prompt (#61031 wires `prompt` / `language` into it). With #61031 merged, a realtime request has no `hotwords`, so its prompt stays the same.
- **Docstring**: it claimed that the SDK's `_build_messages` omits the system role without context. It always emits one (`{"role": "system", "content": context or ""}`). The docstring now says so; the no-context prompt is kept as before.

<details>
<summary>Limitations (model behavior, not this patch)</summary>

- **The benefit decays with list length.** Same lists plus n distractors:

| distractors (Aishell / test-other) | 0 / 0 | 20 / 100 | 100 / 1000 | no hotwords |
|---|---|---|---|---|
| 1.7B Aishell hard-hotword recall | 79.5% | 72.2% | 55.6% | 31.7% |
| 1.7B test-other B-WER | 7.85% | 12.62% | 16.58% | 16.86% |

  1000 English hotwords are ~3500 tokens against ~90 audio tokens per utterance. The docs already advise keeping lists short.
- **1.7B occasionally recites the list.** With ≥20 Mandarin distractors, 0-2 of 808 utterances per list size append the hotword list after the transcript. These runs sent the list through `prompt`, so this predates the patch; callers can bound it with `max_completion_tokens`.
- **Eval caveats**: greedy decoding only; English normalization is lowercasing and punctuation stripping, with no number normalization; distractors are drawn at random from the benchmark lists.

</details>
