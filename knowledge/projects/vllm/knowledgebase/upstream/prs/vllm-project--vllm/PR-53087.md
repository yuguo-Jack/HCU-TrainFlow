# [Bugfix][KV Offload] Bound primary HIT_PENDING waits

[Upstream PR](https://github.com/vllm-project/vllm/pull/53087) · state: open · merged: False

## Original PR description



## Purpose

Fixes #49829.

`TieringOffloadingManager.lookup()` returned `HIT_PENDING` indefinitely when a primary-tier write stalled. The scheduler kept polling the same key and could defer the affected request until its client timed out.

This PR:

- tracks the `HIT_PENDING` deadline independently for each `(request, key)`;
- returns a stable `MISS` for the rest of the request after the deadline, so the scheduler can recompute the block locally without starting another secondary-tier promotion;
- clears deadline state when the lookup resolves, the request finishes, or the cache is reset;
- exposes `hit_pending_timeout_s` in `kv_connector_extra_config`, with a default of 5 seconds;
- reports deadline expirations through `vllm:kv_offload_tiering_hit_pending_timeouts`;
- documents the new configuration option.

This does not duplicate an existing PR. An open-PR search for #49829 currently finds #52571, which fixes the P2P abort lifecycle and explicitly does not change the scheduler timeout or generic `HIT_PENDING` behavior. A separate open-PR
search for `HIT_PENDING` deadlines returned no matching implementation.

- liranschour · comment · 2026-08-20T10:39:31Z · [source](https://github.com/vllm-project/vllm/pull/53087#discussion_r3820776885)

File: `vllm/v1/kv_offload/tiering/manager.py` · line None

**The deadline resets on every failed promotion round, so a request can still be deferred indefinitely.**

Clearing on *any* non-pending result includes the `MISS` produced when `complete_write(success=False)` removes the block. Each failed promotion round therefore hands the request a fresh full window, and the bound becomes "5 s of *consecutive* pending", not "5 s of deferral for this request".

I confirmed it against this head — 20 rounds of *(primary MISS -> promote -> 3 s pending -> write fails -> re-promote)* burn **60 fake seconds with `MISS` never once returned to the scheduler**:

```python
m.primary_tier.lookup.return_value = LookupResult.MISS
results.append(m.lookup(key, ctx))                       # promote -> HIT_PENDING
m.primary_tier.lookup.return_value = LookupResult.HIT_PENDING
now[0] += 3.0
results.append(m.lookup(key, ctx))                       # pending, < 5 s
m.primary_tier.lookup.return_value = LookupResult.MISS   # write failed
results.append(m.lookup(key, ctx))                       # clears deadline, re-promotes
# after 20 rounds: elapsed 60.0 s, LookupResult.MISS not in results
```

That is exactly the repeated-failing-promotion pathology from #49820 / #49877 that the issue thread cites as a cause of these hangs, so I don't think it can be left out of scope here.

Minimal fix: clear the entry only when the primary returns `HIT` — a genuinely resolved read — rather than on any non-pending result:

```python
elif primary_hit is LookupResult.HIT:
    self._clear_primary_pending_lookup(key, req_context)
```

The entry then survives failed rounds and the request gets a *total* per-key budget. Nothing legitimate regresses: a key that resolves to `HIT` still clears, and a later eviction plus re-promotion starts fresh because the entry is already gone. A per-request total deferral budget would also work if you prefer bounding at that level. Either way it's worth a regression test — the current suite only covers a *permanently* pending write, which is the easier case.

Overwriting `primary_hit` here means the deadline-firing call reports a **synthetic primary-tier miss** into the hit-rate metrics: `on_lookup` below receives `MISS`, so `_observe_resolved_lookup` bumps `BLOCK_QUERIES{tier=primary}` with no corresponding hit — for a block that *is* resident, just not readable yet.

Suggest keeping the observed verdict separate from the returned one, and passing `HIT_PENDING` to `on_lookup` (which ignores it) on the synthetic downgrade. `HIT_PENDING_TIMEOUTS` already carries the signal, so nothing is lost and the primary hit rate stays truthful.

The issue asked to "count **or** log" expirations. A counter alone means a leaked primary write is invisible to anyone not scraping Prometheus — and the leak also leaves the block permanently pinned and non-evictable (`_num_write_pending_blocks` is never decremented), so CPU cache capacity shrinks silently.

This PR rightly doesn't try to fix the leak, but a rate-limited `logger.warning` naming the key would make it diagnosable at the point of failure.

if not math.isfinite(hit_pending_timeout_s) or hit_pending_timeout_s <= 0:
