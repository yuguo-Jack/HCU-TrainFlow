# [ROCm] Bump AITER to v0.1.26

[Upstream PR](https://github.com/vllm-project/vllm/pull/62486) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Bump the ROCm base images to AITER [v0.1.26](https://github.com/ROCm/aiter/releases/tag/v0.1.26), and fix a test bug that the bump exposed.

With only the version bump, `test_aiter_fused_moe_mi350_mxfp4_w4a16_accuracy` failed in this PR's CI ([build 95937](https://buildkite.com/vllm/ci/builds/95937/list), step "(MI355 DPX) FP4 and INT4 MoE Kernels"). This is not a regression in v0.1.26. The test has always compared AITER's SwiGLU-OAI MoE against a SiLU reference. It only passed because of an AITER v0.1.25 dispatch bug that ran SiLU instead of SwiGLU. [ROCm/aiter#6478](https://github.com/ROCm/aiter/pull/6478) fixes that bug in v0.1.26, so the kernel's output is now correct and the wrong reference fails.

## Claims

- `AITER_BRANCH` moves from `v0.1.25` to `v0.1.26` in `docker/Dockerfile.rocm_base` and `docker/Dockerfile.rocm_72_base`.
- `ref_moe_forward` in `tests/kernels/moe/test_rocm_aiter_moe.py` gains a `"swigluoai"` activation (alpha 1.702, clamp 7, `up + 1`, the same formula as CK-Tile's `ck_tile::moe::Swiglu`). The MI350 MXFP4 W4A16 accuracy test now uses it, so the test checks the activation it actually requests.
- With v0.1.26 and the test fix, all three commands of the "(MI355 DPX) FP4 and INT4 MoE Kernels" step pass on gfx950 (see Validation).

## Details

**Root cause.** CK-Tile's `moe_dispatch` selects a kernel by `(activation, has_bias, split_k)`, and `has_bias` comes from whether a bias tensor is passed. In AITER ≤ v0.1.25, `gen_instances.py` built SwiGLU kernels only with `has_bias=true`. A SwiGLU call with no bias therefore reached `moe_gemm1_heuristic_dispatcher<..., Swiglu, false, ...>`, which had no specialization. Its primary template is `static MoeKernel dispatch(...) {}`, an empty body with no return, which is undefined behavior. In practice it ran a SiLU kernel. The test calls `rocm_aiter_fused_experts` with `MoEActivation.SWIGLUOAI` and no bias, so it was scored against that SiLU result and matched. [ROCm/aiter#6478](https://github.com/ROCm/aiter/pull/6478), which is in v0.1.26, generates the missing no-bias SwiGLU kernel and makes the unspecialized dispatcher throw. The kernel now computes gpt-oss SwiGLU, so the test's SiLU reference fails.

**Impact on real models.** gpt-oss checkpoints have expert biases, so they take the with-bias kernel, which computed SwiGLU on v0.1.25 as well (zero-bias row above). Any caller that used SwiGLU without bias on AITER ≤ v0.1.25 was silently getting SiLU. This PR fixes that path for them.

**Why the test fix is in this PR.** The corrected reference fails on v0.1.25 (no-bias row above), so it has to land together with the bump.

**Duplicate check.** No open vLLM PR references this test or AITER v0.1.26 (`gh pr list --search "mi350_mxfp4_w4a16"` and `--search "aiter v0.1.26"`). On the AITER side, #6478 and #6620 are both already in v0.1.26, and neither changes this test's no-bias path.
