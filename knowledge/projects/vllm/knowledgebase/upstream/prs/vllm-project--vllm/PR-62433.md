# [Bugfix] Accept 16-byte cache strides in DeepSeek CuTeDSL gather

[Upstream PR](https://github.com/vllm-project/vllm/pull/62433) · state: open · merged: False

## Original PR description

## Overview

Allow the CuTeDSL DeepSeek gather kernel to accept 16-byte-aligned cache block strides. This fixes rejection of valid packed V4.1 MXFP8 caches during MRV2 warmup.

## Claims

- Relax only the block-stride specialization from 32 to 16 bytes, matching the kernel's existing 128-bit copies. The 32-byte base-pointer alignment is unchanged.
- Extend the existing writer/FlashMLA/gather comparison to include odd row padding; retain all numerical assertions and the three record formats.

## Validation

## Details

An MXFP8 record is 528 bytes. An odd number of padded rows can therefore produce a block stride divisible by 16 but not 32, even when the allocation's base pointer is 32-byte aligned. The current fake-tensor stride constraint rejects that layout before the gather executes. The existing copies require 16-byte alignment; lowering this stride constraint leaves the base alignment and data/scale addressing unchanged.

The additional padding case is accepted by FlashMLA decode and the Triton gather; after the fix, CuTeDSL agrees with them under the existing assertions. The existing aligned cases and NVFP4 control also pass.

AI assistance was used. The human submitter reviewed and confirmed understanding of every changed line. Open-PR searches for dequant gather, CuTeDSL stride and the exact module name found no matching fix. The broad SM12x PR #41834 is closed; its cited gather still had the 32-byte stride constraint and did not address this change. This is an independently reproduced startup bug, not a performance cleanup.
