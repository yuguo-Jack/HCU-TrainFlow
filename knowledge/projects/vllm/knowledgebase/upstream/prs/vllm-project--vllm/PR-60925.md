# [CI] Accept whitespace around /ci commands and reply instead of going silent

[Upstream PR](https://github.com/vllm-project/vllm/pull/60925) · state: closed · merged: True

## Original PR description



## Overview

`/ci` comment commands no longer fail silently. Whitespace around a command is accepted, and if a command is unrecognized or the run fails, the bot posts a reply saying so. This came out of [PR 60695](https://github.com/vllm-project/vllm/pull/60695#issuecomment-6090300738), where a `/ci run` got no response at all.

## Claims

- `/ci run\r\n`, ` /ci run `, etc. are parsed as `/ci run`, because `parse_command` now strips surrounding whitespace.
- The workflow now runs for any comment that starts with `/ci` or `/amd-ci`. If the command isn't recognized, the bot reacts 👎 and replies with the list of supported commands. Previously these comments were skipped by the job `if:` without any reply.
- If the job fails (script exception, checkout/uv setup failure, etc.), a final `if: failure()` step comments on the PR with a link to the workflow run.

## Validation

```bash
cd .github/workflows/scripts && uv run --no-project --python 3.12 -m unittest test_run_ci_command
# Ran 56 tests ... OK
```

The new unit tests cover whitespace stripping, detection of command attempts (`/ci rn`, `/CI run` count; `/cifoo`, `/amdci run`, and `please /ci run` don't), the unrecognized-command reply, and idempotency through the existing comment marker. pre-commit passes, including actionlint. The workflow change itself is only exercised once this lands, because `issue_comment` workflows run from the default branch.

## Details

**Root cause (PR 60695):** Dao007forever's comment was created with the body `"/ci run\r\n"` (the GraphQL `userContentEdits` history shows it). The job gate is an exact string match, so run [37999392817](https://github.com/vllm-project/vllm/actions/runs/37999392817) was `skipped`. Editing the comment to `/ci run` a minute later had no effect, because the workflow only triggers on `created`. Permissions were not the problem: the same user's `/ci run` earlier that day triggered Buildkite #93909.

- I kept the trigger to `created` only. The reply asks people to post a new comment, and an edit to an already-answered comment would be deduplicated by the marker anyway.
- The reply doesn't echo the user's comment back, so arbitrary markdown or @-mentions can't be reflected through the bot.
- Tradeoff: comments starting with `/ci` or `/amd-ci` that aren't valid commands now start a short job on `vllm-runners` and get one bot reply. Comments where the first word is something like `/cifoo` still start the job, but the script exits without replying.
- Overlap check: the only other open PR touching this script is my stale draft [PR 51239](https://github.com/vllm-project/vllm/pull/51239), which covers acknowledgement ordering and deleted comments, not parsing or feedback.
