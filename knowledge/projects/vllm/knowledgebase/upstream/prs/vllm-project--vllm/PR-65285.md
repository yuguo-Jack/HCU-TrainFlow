# [Perf][Core] Cache parked async KV loads' admission reservations

[Upstream PR](https://github.com/vllm-project/vllm/pull/65285) · state: open · merged: False

## Original PR description



## Overview

Async KV load admission (#44560) checks each new load against the blocks every in-flight prefill still needs. To get that total it calls `_request_remaining_blocks` for every in-flight request, and it does so again on every admission. A P/D decode instance under a burst parks thousands of loads, so one `schedule()` makes (loads admitted) × (loads parked) calls. This PR caches each parked load's reservation and keeps a running total, so an admission computes only its own.

## Claims

- For one `schedule()` that admits k async loads while M are parked, `_request_remaining_blocks` is called about k·M times on main, about M + k times with #64379, and k times with this PR.
- With 4096 loads parked, a `schedule()` that admits 8 more takes 47.2 ms on main, 12.7 ms with #64379 and 5.4 ms with this PR. A per-step cap (#61725) turns a burst into many steps like this one. A single uncapped burst of 4096 loads takes 8.05 s on main, 77 ms with #64379 and 63 ms with this PR.
- Admission decisions do not change. HiSparse loads are not cached, because HiSparse's count depends on the host pool's free blocks. They are still summed on demand, as on main.

```python
import gc
import time

from tests.v1.core.utils import create_requests, create_scheduler, mock_kv
from vllm.v1.outputs import EMPTY_MODEL_RUNNER_OUTPUT


def add(scheduler, n: int, prefix: str) -> None:
    ids = [f"{prefix}{i}" for i in range(n)]
    for request in create_requests(n, num_tokens=80, max_tokens=10, req_ids=ids):
        scheduler.add_request(request)


def timed_schedule(scheduler) -> float:
    gc.collect()
    start = time.perf_counter()
    output = scheduler.schedule()
    elapsed = time.perf_counter() - start
    scheduler.update_from_output(output, EMPTY_MODEL_RUNNER_OUTPUT)
    return elapsed


def run(parked: int, admitted: int) -> float:
    """Best-of-5 ms of one schedule() parking `admitted` loads beside `parked`."""
    best = float("inf")
    for _ in range(5):
        scheduler = create_scheduler(
            max_num_seqs=parked + admitted,
            num_blocks=(parked + admitted) * 8 + 100,
            use_kv_connector=mock_kv(matched_tokens=64, is_async=True),
        )
        if parked:
            add(scheduler, parked, "parked")
            timed_schedule(scheduler)
        add(scheduler, admitted, "new")
        best = min(best, timed_schedule(scheduler))
    return best * 1e3


for parked, admitted in [(0, 256), (0, 1024), (0, 4096), (256, 8), (1024, 8), (4096, 8)]:
    print(f"parked {parked:5d}  admitted {admitted:5d}: {run(parked, admitted):9.2f} ms")
```

## Details

- **When the cache is refreshed.** The inputs to a parked load's reservation change only at these points, and each one calls `_reserve_parked`:
  - when the load is parked;
  - when invalid blocks are reported for it;
  - when its receive finishes, after the connector's `update_connector_output` (failed receives always appear in `finished_recving`);
  - when `_update_waiting_for_remote_kv` promotes it.

  The entry is dropped when the request is scheduled or freed.
- **Prefill chunks** in `_inflight_prefills` are few, and they are still summed on demand.
- **Relation to other PRs:**
  - #64379 sums the reservation once per `schedule()` instead of once per admission. That is linear per step. But with a per-step cap, a burst becomes many steps that each admit a few loads while thousands stay parked, and every step recomputes all of them. Here a step computes only the loads it admits. In a single uncapped step both approaches are linear.
  - #61725 (cap on new async loads per step) is complementary.
  - #59901 (drop a failed load's reservation once its blocks are freed) is orthogonal. With this PR it would call `_unreserve_parked` instead of removing the request from `_inflight_prefills`.
- **What is left.** The waiting loop still peeks at every parked load in `kv_holding_waiting`, about 1 µs per load (about 4 ms at 4096 here). This PR does not change that.
